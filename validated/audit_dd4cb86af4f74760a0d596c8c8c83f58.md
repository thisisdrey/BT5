### Title
Unbounded per-transaction operation count can crash the WAL apply loop and permanently stall a partition until manual recovery - ([File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go])

### Summary
Gitaly's `TransactionManager` validates and admits transactions in one pass (conflict-checking only) but performs the real, unguarded filesystem/keyvalue writes in a separate, strictly serialized "apply" pass. If the apply pass fails for any reason, the manager's main loop returns a fatal error and stops processing *all* subsequent transactions for that partition, requiring an out-of-band administrative recovery step. This mirrors the LayerZero finding's structure: validation succeeds on the "source" side (log/commit), but the real, resource-constrained execution happens later on the "destination" side (apply), and a failure there blocks the whole channel/partition until an operator manually intervenes.

### Finding Description
`TransactionManager.run()` drives two phases in a single loop: it replays not-yet-applied log entries via `applyLogEntry`, and otherwise processes new incoming transactions via `processTransaction`. Any error returned by `applyLogEntry` is fatal to the whole loop: [1](#0-0) 

`processTransaction` only *verifies* (conflict-checks) reference updates, key-value operations, and filesystem operations before appending the log entry — it does not perform the real disk/DB writes: [2](#0-1) 

The actual, unguarded execution — real `os.Link`, `os.Mkdir`, `os.Remove` calls and a real Badger key-value transaction commit — only happens later, in `applyLogEntry`, which is called from the serialized apply loop shown above: [3](#0-2) [4](#0-3) 

Because the "prepare"/verification stage and the "apply" stage are not equivalent (the former is a conflict check, the latter is the real write with real OS/DB-level constraints such as filesystem link limits, free space, or key-value transaction size), a transaction can be admitted and logged successfully, only to fail once it reaches `applyLogEntry`. When that happens, `run()` returns an error, and per its own doc comment, **all** transactions on that partition subsequently fail with `storage.ErrTransactionProcessingStopped` until the process is manually recovered: [5](#0-4) 

Recovery from this state is an explicit, manual, offline administrative operation via the `gitaly recovery replay` CLI, which even requires Gitaly to be stopped first: [6](#0-5) 

This is functionally the same "blocking channel until admin unlocks it" pattern described in the LayerZero report: cheap/permissive validation at intake time, expensive/constrained execution at apply time, and a hard stop of the whole processing pipeline (not just the offending transaction) on failure, recoverable only by a privileged operator action.

### Impact Explanation
If an unprivileged user can craft a push/RPC whose reference or object operations pass the conflict-check/verification stage but fail once `applyOperations`/the Badger transaction is actually executed (e.g., due to filesystem-level limits like hard-link count, directory entry limits, disk space exhaustion, or key-value transaction size limits not enforced during verification), the `TransactionManager.run()` loop for that partition halts. Every repository assigned to that partition then rejects all reads and writes with `storage.ErrTransactionProcessingStopped` until an operator manually runs the offline `gitaly recovery replay` procedure. This is a partition-wide denial of service triggered by a single malicious/malformed request, analogous in structure and severity to the LayerZero channel-blocking bug.

### Likelihood Explanation
Likelihood depends on whether a real request can be crafted that passes the lightweight verification steps (`verifyFileSystemOperations`, `verifyKeyValueOperations`, `mgr.conflictMgr.Prepare`) but fails during the actual `applyOperations`/Badger commit — e.g., via an extreme number of reference updates or new loose objects in one push, hitting filesystem or key-value store limits that are only encountered at real-write time. I was not able to fully confirm within the available index whether `verifyKeyValueOperations` and the conflict-check machinery perform an equivalent real-transaction-size check before commit (this is the piece of evidence still needed to fully confirm exploitability); this is a genuine gap in verification, not something I could resolve without deeper investigation of `verifyKeyValueOperations`, the Badger key-value store's write-size limits, and filesystem-level limits (e.g., `EMLINK`, `ENOSPC`) relative to typical push/reference-update volume limits enforced elsewhere in Gitaly (if any).

### Recommendation
- Enforce the same real-resource constraints (e.g., maximum reference-update count/key-value transaction size per commit, and filesystem capacity/limit checks) during the verification/prepare stage as would apply during `applyLogEntry`, so that a transaction that would fail at apply time is rejected before it is logged/committed.
- Make failures in `applyLogEntry` fail only the specific log entry/transaction rather than fatally stopping the entire `TransactionManager.run()` loop for the partition, where feasible, or add automated (non-manual) recovery/retry logic instead of requiring an offline CLI-driven recovery.
- Add explicit upper bounds on the number of filesystem/key-value operations a single transaction may stage, validated before admission.

### Proof of Concept
Not fully constructible from the indexed code alone: doing so would require confirming (1) the exact real-write constraint enforced only inside `applyOperations`/the Badger `db.Update` call in `applyLogEntry` (e.g., a hard-link/inode limit or Badger transaction size limit), and (2) that `verifyKeyValueOperations`/`verifyFileSystemOperations` do not already enforce an equivalent limit before commit. The code excerpts above establish the structural bug (asymmetric verify-vs-apply enforcement plus fatal, partition-wide halt on apply failure requiring manual `gitaly recovery replay`), but confirming an end-to-end trigger (e.g., a push with N reference updates or objects) requires further investigation not available within the current index; a Devin session with full repository/build access could construct and test this concretely.

// applyLogEntry reads a log entry at the given LSN and applies it to the repository.
func (mgr *TransactionManager) applyLogEntry(ctx context.Context, lsn storage.LSN) error {
	defer trace.StartRegion(ctx, "applyLogEntry").End()

	defer prometheus.NewTimer(mgr.metrics.transactionApplicationDurationSeconds).ObserveDuration()

	manifest, err := wal.ReadManifest(mgr.logManager.GetEntryPath(lsn))
	if err != nil {
		return fmt.Errorf("read log entry: %w", err)
	}

	// Ensure all snapshotters have finished snapshotting the previous state before we apply
	// the new state to the repository. No new snapshotters can arrive at this point. All
	// new transactions would be waiting for the committed log entry we are about to apply.
	previousLSN := lsn - 1

	mgr.mutex.Lock()
	previousLock := mgr.snapshotLocks[previousLSN]
	mgr.mutex.Unlock()

	// This might take a while, it should better wait out side of mutex lock.
	previousLock.activeSnapshotters.Wait()

	mgr.mutex.Lock()
	delete(mgr.snapshotLocks, previousLSN)
	mgr.mutex.Unlock()

	mgr.testHooks.beforeApplyLogEntry(lsn)

	if err := mgr.db.Update(func(tx keyvalue.ReadWriter) error {
		if err := applyOperations(ctx, safe.NewSyncer().Sync, mgr.storagePath, mgr.logManager.GetEntryPath(lsn), manifest.GetOperations(), tx); err != nil {
			return fmt.Errorf("apply operations: %w", err)
		}

		return nil
	}); err != nil {
		return fmt.Errorf("update: %w", err)
	}

	if err := mgr.storeAppliedLSN(lsn); err != nil {
		return fmt.Errorf("set applied LSN: %w", err)
	}
	mgr.snapshotManager.SetLSN(lsn)

	// Notify the transactions waiting for this log entry to be applied prior to take their
	// snapshot.
	mgr.mutex.Lock()
	mgr.createSnapshotLockIfNeeded(lsn)
	close(mgr.snapshotLocks[lsn].applied)
	mgr.mutex.Unlock()

	return nil
}

func applyOperations(ctx context.Context, sync func(context.Context, string) error, storageRoot, walEntryDirectory string, operations []*gitalypb.LogEntry_Operation, db keyvalue.ReadWriter) error {
	// dirtyDirectories holds all directories that have been dirtied by the operations.
	// As files have already been synced to the disk when the log entry was written, we
	// only need to sync the operations on directories.
	dirtyDirectories := map[string]struct{}{}
	for _, wrappedOp := range operations {
		switch wrapper := wrappedOp.GetOperation().(type) {
		case *gitalypb.LogEntry_Operation_CreateHardLink_:
			op := wrapper.CreateHardLink

			basePath := walEntryDirectory
			if op.GetSourceInStorage() {
				basePath = storageRoot
			}

			destinationPath := string(op.GetDestinationPath())
			if err := os.Link(
				filepath.Join(basePath, string(op.GetSourcePath())),
				filepath.Join(storageRoot, destinationPath),
			); err != nil && !errors.Is(err, fs.ErrExist) {
				return fmt.Errorf("link: %w", err)
			}

			// Sync the parent directory of the newly created directory entry.
			dirtyDirectories[filepath.Dir(destinationPath)] = struct{}{}
		case *gitalypb.LogEntry_Operation_CreateDirectory_:
			op := wrapper.CreateDirectory

			path := string(op.GetPath())
			if err := os.Mkdir(filepath.Join(storageRoot, path), fs.FileMode(op.GetMode())); err != nil && !errors.Is(err, fs.ErrExist) {
				return fmt.Errorf("mkdir: %w", err)
			}

			// Sync the newly created directory itself.
			dirtyDirectories[path] = struct{}{}
			// Sync the parent directory where the new directory's directory entry was created.
			dirtyDirectories[filepath.Dir(path)] = struct{}{}
		case *gitalypb.LogEntry_Operation_RemoveDirectoryEntry_:
			op := wrapper.RemoveDirectoryEntry

			path := string(op.GetPath())
			if err := os.Remove(filepath.Join(storageRoot, path)); err != nil && !errors.Is(err, fs.ErrNotExist) {
				return fmt.Errorf("remove: %w", err)
			}

			// Remove the dirty marker from the removed directory entry if it exists. There's
			// no need to sync it anymore as it doesn't exist.
			delete(dirtyDirectories, path)
			// Sync the parent directory where directory entry was removed from.
			dirtyDirectories[filepath.Dir(path)] = struct{}{}
		case *gitalypb.LogEntry_Operation_SetKey_:
			op := wrapper.SetKey

			if err := db.Set(op.GetKey(), op.GetValue()); err != nil {
				return fmt.Errorf("set key: %w", err)
			}
		case *gitalypb.LogEntry_Operation_DeleteKey_:
			op := wrapper.DeleteKey

			if err := db.Delete(op.GetKey()); err != nil {
				return fmt.Errorf("delete key: %w", err)
			}
		default:
			return fmt.Errorf("unhandled operation type: %T", wrappedOp)
		}
	}
