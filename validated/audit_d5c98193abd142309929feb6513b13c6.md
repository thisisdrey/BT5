## Title
Missing timeout enforcement in `VerifyTransferProof` precompile allows worker-thread-pool exhaustion / indefinite VM-thread blocking - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The containerd advisory describes a goroutine leak caused by an I/O-drain phase that computes a deadline/timeout but never actually enforces it, letting the wait block forever when a child process misbehaves. `PrecompiledContracts.VerifyTransferProof` (the Sapling shielded-transfer proof-verification precompile) has the same defect: it computes a bounded wait via `CountDownLatch.await(getCPUTimeLeftInNanoSecond(), TimeUnit.NANOSECONDS)` but discards the boolean result and unconditionally calls `future.get()` (no timeout) on every submitted worker task [1](#0-0) .

### Finding Description
`VerifyTransferProof.doExecute` submits spend/output/binding-signature verification tasks to one of two shared fixed-size (5-thread) executors, `workersInConstantCall` / `workersInNonConstantCall` [2](#0-1) . It then waits on a `CountDownLatch` with an intended CPU-time-based deadline, but the `withNoTimeout` result is never checked before the code proceeds to call `future.get()` on every future in a loop [1](#0-0) . `Future.get()` with no arguments blocks indefinitely until the task completes.

This is functionally different from the sibling precompile `BatchValidateSign`, which performs the identical pattern but correctly checks the flag and aborts with `Program.Exception.notEnoughTime` when the timeout elapses instead of falling through to unbounded `future.get()` calls [3](#0-2) . The `VerifyTransferProof`/`VerifyMintProof` sibling code path lacks this guard.

Both `workersInConstantCall` and `workersInNonConstantCall` are built via `ExecutorServiceManager.newFixedThreadPool`, which is a plain `Executors.newFixedThreadPool` backed by an unbounded `LinkedBlockingQueue` [4](#0-3) . Because the pool is shared across all concurrent calls to this precompile (both from real transactions and constant/`eth_call` style calls), any slow or stuck submitted task — whether due to native `librustzcash` computation taking longer than the CPU-time budget under load, or a burst of concurrently submitted verification requests queueing behind the 5 fixed workers — causes the calling VM execution thread (and thus the thread executing the transaction or serving the constant-call HTTP/JSON-RPC request) to block on `future.get()` past the intended CPU-time limit, with no cancellation of the outstanding tasks.

### Impact Explanation
Any account can reach this path by broadcasting a `ShieldedTransferContract` transaction or by invoking the `VerifyTransferProof` precompile address through `TriggerConstantContract`/`TriggerSmartContract`, all of which are exposed via unauthenticated HTTP/JSON-RPC endpoints (`TriggerConstantContractServlet`, `TronJsonRpcImpl`) and the transaction broadcast path in `Wallet`/`Manager`. Repeated or concurrent submission of shielded-transfer proof verification calls saturates the fixed 5-thread pools and their unbounded queues; because the CPU-time budget check result is ignored, the threads that submitted the work (transaction-processing or constant-call HTTP threads) block on `future.get()` without a bound, tying up node execution resources analogous to the containerd goroutine leak, and can accumulate across repeated calls to exhaust available executor/queue capacity and stall further shielded-transfer verification and its callers, degrading or halting node responsiveness to legitimate requests.

### Likelihood Explanation
Reaching this code requires only a well-formed shielded-transfer proof-verification call of the correct byte length (validated purely by size checks in `execute`) [5](#0-4) ; the attacker does not need valid cryptographic proof content to reach the thread-pool submission and blocking-wait logic, since the blocking wait happens before/regardless of proof correctness. No special privileges, staking, or governance role is required — merely broadcastable transactions or constant-call/API access.

### Recommendation
In `VerifyTransferProof.doExecute` (and equivalent Sapling verification precompiles), check the `withNoTimeout` result returned by `CountDownLatch.await(...)` the same way `BatchValidateSign` does: if the deadline elapses, cancel outstanding futures and throw `Program.Exception.notEnoughTime(...)` instead of falling through to unconditional `future.get()` calls. Additionally, consider bounding queue depth for `workersInConstantCall`/`workersInNonConstantCall` or applying a timeout to `future.get()` itself to guarantee bounded blocking regardless of code path.

### Proof of Concept
1. Submit (or repeatedly submit via `TriggerConstantContract`) well-formed-length payloads targeting the `VerifyTransferProof` precompile (`SIZE` in `{2080, 2368, 2464, 2752}`) with `spendCount`/`receiveCount` set to the maximum allowed (2 each), so 5 tasks are queued per call into a 5-thread pool [6](#0-5) .
2. Fire many such calls concurrently (constant calls are cheap for callers and consume no gas from a real balance in read-only mode, or a burst of shielded transactions), saturating the shared fixed pool and its unbounded queue.
3. Because the `withNoTimeout` check is skipped, callers proceed straight to `future.get()` and block until each of their queued tasks is eventually scheduled and completes, well past the intended per-call CPU-time budget, occupying the calling threads (VM execution / HTTP request threads) for the duration [1](#0-0) .
