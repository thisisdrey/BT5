### Title
StackerDB unsolicited-push acknowledgment advertises chunk versions before they are durably committed, allowing a false-inventory race - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` computes and sends a `StackerDBChunkInv` acknowledgment that claims the local replica now holds a pushed chunk's `slot_version`, but the actual database write for that chunk happens later, asynchronously, in the relayer thread. Because chunk storage enforces monotonic slot versions (`StaleChunk`) and the push-handling path explicitly skips the write-frequency check, an attacker can race two validly-signed pushes for the same slot through two different connections so that the acknowledgment sent to one peer claims a `slot_version` that this node never actually ends up storing. This breaks the equality between "advertised/committed inventory" and "what is actually in the StackerDB," analogous to the ResolvStaking bug where the accumulated-rewards state (`accumulatedRewardsPerToken`) was advanced independently of, and inconsistently with, the actually-realized claimable state.

### Finding Description
`handle_unsolicited_StackerDBPushChunk` builds the reply inventory from `make_StackerDBChunksInv_or_Nack` (a fresh read of `get_slot_versions`), runs `validate_received_chunk` (signature, size, staleness against *that* read, and max-writes only — write frequency is intentionally not checked here per the function's own doc comment), and then unconditionally patches the in-memory `data.slot_versions[slot_id]` to the pushed chunk's version before sending the `StackerDBChunkInv` reply back over the wire: [1](#0-0) 

This reply is signed and sent immediately (`sign_for_p2p_reply` / `send_p2p_message`), while the actual chunk is only queued for storage by returning `(false, true)`, meaning "forward to relayer for processing": [2](#0-1) 

The relayer later performs the real, authoritative write via `process_pushed_stacker_db_chunks` → `process_stacker_db_chunks`, which calls `try_replace_chunk` per chunk and simply drops (debug-logs) any chunk that fails with `StaleChunk`: [3](#0-2) 

`try_replace_chunk` itself re-checks the slot's current on-disk version and signer, and rejects (does not store) if the version is not strictly newer than what's already stored: [4](#0-3) 

The write-frequency check that would otherwise throttle repeated writes to a slot is explicitly *not* enforced at the unsolicited-push layer, by design, per this comment: [5](#0-4) 

Because the same signer can legitimately produce (and gossiping peers can legitimately relay) two consecutive chunk versions (`v`, `v+1`) for the same slot in quick succession, two `StackerDBPushChunk` messages can arrive at a victim node on two different connections and both pass `handle_unsolicited_StackerDBPushChunk`'s validation (each reads the pre-write `slot_versions`, so both see the older version as "expected" and both look acceptable). Both acknowledgments are sent out immediately, each promising the corresponding peer that the node now has its respective version. Only one write can actually win at commit time in `try_replace_chunk` (the second, whichever commits later, is rejected as `StaleChunk` and silently dropped by the relayer). The peer that received the ack for the losing chunk was told — via a signed `StackerDBChunkInv` — that this node has a `slot_version` it does not actually have and never stores. Any node computing chunk-fetch schedules from this now-incorrect inventory will believe the version is already replicated here and will not re-request it, i.e., a benign/false chunk-inventory desynchronization is induced purely by message timing from an unprivileged remote peer, no chunk forgery or key compromise required.

### Impact Explanation
This is a "false inventory" issue: the local node broadcasts (via a legitimately signed P2P reply) an inventory claim about chunk data it does not actually hold, which can mislead the requesting peer's download-scheduling logic (`StackerDBSync`) into skipping the legitimate resync of that slot/version, causing missing/never-repaired StackerDB replication of otherwise-valid signer data (e.g. signer messages, miner block proposals) for that node's view of the network. This matches the High-impact category of "steering a node off the tip via false inventory" in the accepted-impact list, since it degrades correct propagation/synchronization of StackerDB state without requiring any privileged role, node secret, or another party's key.

### Likelihood Explanation
Likelihood is low-to-moderate: exploitation depends on winning a timing race between two concurrent unsolicited pushes for the same slot arriving on separate connections before the relayer commits either. This can happen incidentally during normal gossip/relay of consecutive signer chunk versions, and can plausibly be amplified by an attacker who controls two connections to the victim and deliberately sends both versions nearly simultaneously (no signing key of the victim or contract owner is needed — only a legitimately-signed chunk from the actual slot owner needs to be replayed/raced by the attacker, similar to how any peer could "grief" another party's checkpoint by triggering an update whose effects are lost).

### Recommendation
Do not send the `StackerDBChunkInv` acknowledgment with the patched (optimistic) `slot_version` until the chunk write has actually been durably committed by the relayer. Either move the acknowledgment to after storage confirmation, or have `handle_unsolicited_StackerDBPushChunk` perform the store itself synchronously (inside the same code path that produces the ack) so the version advertised is guaranteed to match what's on disk, eliminating the race window between "ack sent" and "chunk actually stored."

### Proof of Concept
1. Configure a StackerDB slot owned by key `K` with current stored `slot_version = N`.
2. Have the legitimate owner (or an attacker replaying previously-gossiped, validly-signed chunks) sign two chunks for the same slot: `chunk_v(N+1)` and `chunk_v(N+2)`.
3. Open two separate P2P connections to the victim node and send `StackerDBPushChunk(chunk_v(N+1))` on connection A and `StackerDBPushChunk(chunk_v(N+2))` on connection B nearly simultaneously, before either is processed by the relayer.
4. Both calls to `handle_unsolicited_StackerDBPushChunk` read the same pre-write `slot_versions` (still `N`), pass `validate_received_chunk` (`data.slot_version < *expected_version` is false for both since `expected_version == N`), and each patches its own `StackerDBChunkInv` reply to advertise its respective pushed version, then sends that reply back on its own connection (`stackslib/src/net/stackerdb/mod.rs:794-814,858-870`).
5. Both `(false, true)` results are forwarded to the relayer; `process_stacker_db_chunks` calls `try_replace_chunk` for each — only the chunk that reaches `try_replace_chunk` first while `slot_version > slot_validation.version` succeeds; the other fails `StaleChunk` and is dropped (`stackslib/src/net/relay.rs:2409-2437`, `stackslib/src/net/stackerdb/db.rs:424-429`).
6. The peer whose chunk lost the race was already told (Step 4) that the node holds its version, when in fact the node's DB now holds a different version (or the same version it already had), producing a divergence between advertised inventory and committed chunk state.

    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));

        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
