### Title
NullPointerException in `UnDelegateResourceActuator.execute()` from dereferencing an unvalidated "unlock" `DelegatedResourceCapsule` - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
`UnDelegateResourceActuator.validate()` accepts an `UnDelegateResourceContract` transaction as long as *either* the "lock" or the "unlock" `DelegatedResourceCapsule` exists and their **combined** balance covers the requested amount. It never verifies that the "unlock" record itself is non-null when the whole undelegate amount can be satisfied purely from an expired "lock" record. `execute()` then unconditionally fetches the same "unlock" record and calls methods on it without a null check, causing a `NullPointerException` for a value that `validate()` never guaranteed to exist — mirroring the referenced kernel bug where `xfs_attri_recover_work` dereferences/releases an inode pointer that the failed `iget` call never set.

### Finding Description
In `validate()`: [1](#0-0) 
only the *sum* of `unlockResourceCapsule` and `lockResourceCapsule` balances is checked against `unDelegateBalance`. `unlockResourceCapsule` is allowed to be `null` as long as `lockResourceCapsule` alone (when expired) covers the requested amount.

In `execute()`, the same "unlock" key is fetched again and dereferenced without any null guard: [2](#0-1) 

`unlockResource.addFrozenBalanceForBandwidth(...)` / `addFrozenBalanceForEnergy(...)` will throw `NullPointerException` when `unlockResource` is `null`, because `execute()` never checks for this case the way `validate()` implicitly allowed it to occur (analogous to `xfs_attri_recover_work` calling `irele()`/dereferencing an inode pointer that `xlog_recovery_iget()` never populated on failure).

### Impact Explanation
`Actuator.execute()` is invoked during block application in `Manager` for every transaction packed into a block. An uncaught `NullPointerException` thrown from inside a contract-type actuator during block processing is not a normal `ContractExeException`/`ContractValidateException` — it propagates as a runtime exception and can crash/halt block processing on any node that applies this transaction (including all validating and non-validating full nodes and SRs), producing a denial-of-service / potential chain halt or split (nodes that hit the exception vs. those that don't, depending on processing order/state). This satisfies the "node crash or halt" / "chain split" criteria for High severity.

### Likelihood Explanation
This is reachable by a normal, unprivileged account through two ordinary, already-supported transaction types:
1. `DelegateResourceContract` with `lock = true` (creates only the "lock" `DelegatedResourceCapsule` entry, never the "unlock" entry) — see `delegateResource()` in `DelegateResourceActuator.java`.
2. After the lock period naturally expires (attacker only needs to wait; no malicious SR/witness/peer/timing manipulation required), the same account submits `UnDelegateResourceContract` for the entire delegated balance.

Because `validate()` only requires the *combined* lock+unlock balance to satisfy the request, and the "unlock" record was never created, `execute()`'s unconditional `unlockResource.addFrozenBalanceForBandwidth/Energy(...)` call throws NPE. No special privileges, contract deployment, or race condition are required — a single crafted pair of transactions from any account is sufficient.

### Recommendation
In `execute()`, mirror the null-safety already used for `lockResource`/`receiverCapsule` elsewhere in the same method: guard all dereferences of `unlockResource` with a null check (e.g., initialize a new `DelegatedResourceCapsule` when absent, similar to how `DelegateResourceActuator.delegateResource()` handles a missing capsule), and correspondingly adjust the balance bookkeeping so that funds delegated via the "lock" bucket alone can still be undelegated without touching a non-existent "unlock" record. Add regression tests covering: lock-only delegation reaching full expiry, then undelegating the full balance with no prior unlock entry.

### Proof of Concept
1. Account A calls `DelegateResourceContract` to Account B with `lock=true`, `balance=X`, resource=BANDWIDTH. This creates only the "lock" `DelegatedResourceCapsule` (`createDbKeyV2(A,B,true)`); no "unlock" record (`createDbKeyV2(A,B,false)`) exists.
2. Wait until `dynamicStore.getLatestBlockHeaderTimestamp() > delegatedResourceCapsule.getExpireTimeForBandwidth()` (lock period elapses).
3. Account A submits `UnDelegateResourceContract` with `balance=X`, resource=BANDWIDTH, `receiverAddress=B`.
   - `validate()`: `unlockResourceCapsule == null`, `lockResourceCapsule != null` and expired → `delegateBalance = lockResourceCapsule.getFrozenBalanceForBandwidth() >= X` → validation passes.
   - `execute()`: `unlockResource = delegatedResourceStore.get(unlockKey)` returns `null`; `unlockResource.addFrozenBalanceForBandwidth(-X, 0)` throws `NullPointerException`, aborting block application on the node executing this transaction.
