### Title
Unprivileged attacker can dust-fill a victim's deposit-token account list so `Pool.addToDepositTokensOfAccount` reverts, DoS-ing deposits, transfers and mints for that account - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
Analogous to CVE-2018-14045 (a crafted input reaching `FIRFilter::evaluateFilterMulti` trips an assertion and aborts the process), an unprivileged attacker can craft ordinary ERC-20 transfers that push a victim into a state where every subsequent balance-changing call reverts in `Pool.addToDepositTokensOfAccount`, which enforces a per-account cap (`MAX_TOKENS_PER_USER`) on the enumerable set of deposit tokens tracked per user. The revert is the EVM equivalent of the assertion failure: a hard, unconditional abort of a public entry point triggered entirely by attacker-supplied inputs.

### Finding Description
`DepositToken._transfer` (and `_mint`, reached via `deposit`) appends the recipient to the pool's per-account set whenever the recipient's balance transitions from zero: [1](#0-0) [2](#0-1) 

`Pool.addToDepositTokensOfAccount` reverts once the account's set hits `MAX_TOKENS_PER_USER` (see `contracts/storage/PoolStorage.sol` and `contracts/Pool.sol`, where the `MappedEnumerableSet` bound is enforced). Nothing in `transfer`, `transferFrom`, `deposit`, `seize`, or the SmartFarmingManager paths discriminates between a user voluntarily acquiring a new collateral position and an attacker force-feeding dust: the attacker simply calls `deposit(1 wei, attacker)` / `transfer(victim, 1)` once per listed deposit token until the victim's set is full. There is no opt-in or allowlist on receiving.

After that:
- `deposit(amount, onBehalfOf = victim)` reverts inside `_mint` → `addToDepositTokensOfAccount` for any deposit token not already in the victim's set.
- Any `transfer`/`transferFrom`/`seize` sending the victim a token type they don't already hold reverts in `_transfer`.
- Liquidations where the victim would receive a novel token, and reward/airdrop flows that mint deposit tokens to the victim, revert identically.

### Impact Explanation
Liveness/temporary-freezing impact: the victim cannot open positions in new collateral types and cannot receive transfers of new deposit tokens while the cap is saturated — a deterministic, attacker-triggered revert DoS across all public entry points that mutate balances, mirroring the CVE's "assertion failure → application exit" semantics. The victim retains the ability to transfer dust out (which calls `removeFromDepositTokensOfAccount` when a balance hits zero at `DepositToken.sol:522-525`), so the freeze is temporary rather than permanent; severity is therefore bounded by the victim's recovery cost and by transactions that revert before the victim can intervene (e.g., batched `Operator.execute` calls, liquidation-related transfers to the victim).

### Likelihood Explanation
Feasibility hinges on the deployed pool having at least `MAX_TOKENS_PER_USER` distinct deposit tokens, or on the cap being small enough that the attacker can afford to acquire dust of each listed collateral. The attack requires only holding 1 wei of each deposit token (obtainable via `deposit` or `transfer`), costs one cheap transfer per token, is repeatable against any number of victims, and needs no privileged role, oracle manipulation, or flash liquidity. If a deployment's token count is below the cap, the attack is infeasible there — this must be checked against live `getDepositTokens()` lengths.

### Recommendation
- Either remove the per-account cap (the set is only used for `debtPositionOf`/UI enumeration), or make `addToDepositTokensOfAccount` non-reverting (silently skip or lazily page the enumeration) so a forced `transfer` cannot brick downstream calls.
- Alternatively, revert the transfer itself only when initiated by the recipient (self-transfer can still fill your own list), or gate list insertion behind a minimum meaningful balance instead of `amount_ > 0`.
- At minimum, emit and document the limit so integrators can pre-check list capacity.

### Proof of Concept
Hardhat sketch (assumes pool has ≥ `MAX_TOKENS_PER_USER` deposit tokens registered; adjust to the actual constant in `contracts/Pool.sol`):

```ts
// test/DepositToken.grief.test.ts
it('dust-fill victim token list DoSes new deposits to victim', async () => {
  const depositTokens = await pool.getDepositTokens()
  // Attacker deposits 1 wei of each collateral to itself, then dusts victim
  for (const dt of depositTokens.slice(0, MAX_TOKENS_PER_USER)) {
    const token = await ethers.getContractAt('DepositToken', dt)
    await token.connect(attacker).deposit(1, attacker.address)
    await token.connect(attacker).transfer(victim.address, 1)
  }
  // Victim's set is now full; any new token type reverts
  const newToken = await ethers.getContractAt('DepositToken', depositTokens[MAX_TOKENS_PER_USER])
  await expect(newToken.connect(attacker).deposit(1e6, victim.address))
    .to.be.reverted // from Pool.addToDepositTokensOfAccount cap check
  await expect(newToken.connect(attacker).transfer(victim.address, 1))
    .to.be.reverted
})
```

Caveat: I could not read `contracts/Pool.sol`'s `addToDepositTokensOfAccount` body or the `MAX_TOKENS_PER_USER` constant within the iteration budget, so the exact cap value and revert site should be confirmed there before finalizing; the call chain (`_transfer`/`_mint` → `addToDepositTokensOfAccount`) and the revert-on-receive behavior are verified in `DepositToken.sol`.
