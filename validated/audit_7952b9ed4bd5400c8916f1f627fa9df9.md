### Title
`DebtToken.repay()` can be griefed by a dust repayment on behalf of the victim, forcing revert of the victim's full/partial repayment — (File: contracts/DebtToken.sol)

### Summary
`DebtToken.repay(address onBehalfOf_, uint256 amount_)` is permissionless: `onBehalfOf_` may be any account while `msg.sender` is the payer (`contracts/DebtToken.sol:418-457`). The function burns exactly `amount_` (minus `repayFee`) of the victim's debt, and the requested amount is validated against the *current* debt balance twice: at `balanceOf(onBehalfOf_) - _repaid` inside the `debtFloorInUsd` check (`DebtToken.sol:446`) and at the `BurnAmountExceedsBalance` check in `_burn` (`DebtToken.sol:528-529`). An attacker who observes a victim submitting `repay(victim, X)` where `X ≈ balanceOf(victim)` can front-run with `repay(victim, 1)` — burning 1 wei of their own synthetic tokens at near-zero cost — causing the victim's transaction to revert on underflow / `BurnAmountExceedsBalance`. This is repeatable every block.

### Finding Description
The relevant flow in `repay()`:

```solidity
// contracts/DebtToken.sol
(_repaid, _fee) = quoteRepayOut(amount_);
...
uint256 _newDebtInUsd = _pool.masterOracle().quoteTokenToUsd(
    address(_syntheticToken),
    balanceOf(onBehalfOf_) - _repaid   // L446: underflows once debt < _repaid
);
...
_syntheticToken.burn(_msgSender, _repaid);
_burn(onBehalfOf_, _repaid);          // L529: BurnAmountExceedsBalance if balance < _repaid
```

Because `repay` accepts an arbitrary `onBehalfOf_` and the payer is always `msg.sender`, any third party can shrink a target's debt between quote-time and execution-time. The victim's signed transaction embeds a stale `amount_`, so the subtraction and the balance check revert. Synthetic tokens use 18 decimals, so a 1-wei repayment is economically free (modulo the proportional `repayFee`, also ~0 at 1 wei).

Note: the `debtFloorInUsd` check (`DebtToken.sol:442-450`) does **not** prevent the attacker's dust repay — repaying 1 wei leaves the victim's debt virtually unchanged, so it stays above the floor and passes.

A mitigating factor exists: `repayAll()` (`DebtToken.sol:466-495`) reads `balanceOf(onBehalfOf_)` at execution time and is immune to this griefing. However, `repay()` is still exposed publicly, is used by fixed-amount integrations (e.g., `SmartFarmingManager` leverage/flashRepay flows that compute repay amounts off-chain), and callers cannot always substitute `repayAll` (e.g., partial repayments, or callers holding exactly `amount_` synths). The original Timeswap finding was confirmed medium under the same reasoning — a workaround existing does not eliminate the DoS on the canonical entry point.

### Impact Explanation
- Temporary denial of service on `repay()` for any targeted account, repeatable at ~zero attacker cost (1 wei of synthetic token per attempt).
- While a victim's repay is blocked, interest keeps accruing on the debt, and a deteriorating position approaches liquidation thresholds — the DoS directly endangers the victim's collateral.
- Third-party integrations or routers that call `repay()` with a pre-computed amount (off-chain or via `quoteRepayIn`) are permanently DoS-able since the amount is fixed in calldata.

### Likelihood Explanation
- Attack requires only an unprivileged EOA holding a trivial amount of the synthetic token and mempool front-running capability (or a private-mempool sandwich bot). No privileged role, oracle manipulation, or flash loan is needed.
- Cost per grief is ~1 wei of synth + gas; the attacker can repeat indefinitely.
- Constraint: the attack only reverts *fixed-amount* `repay` calls. `repayAll` calls land successfully regardless, and liquidation (`Pool.liquidate` → `DebtToken.burn`) is unaffected. This reduces severity from "protocol-wide" to "per-tx griefing of the `repay` entrypoint," matching the original medium rating.

### Recommendation
Move DoS protection into `DebtToken.repay()` itself: cap the effective repayment at the account's current debt rather than reverting, e.g.

```solidity
uint256 _balance = balanceOf(onBehalfOf_);
if (_repaid > _balance) {
    (_repaid, _fee) = quoteRepayOut(quoteRepayIn(_balance)); // recompute for _balance
    // or simpler: clamp amount_ before quoteRepayOut
}
```

Alternatively, treat `amount_ > balanceOf(onBehalfOf_)` as "repay all" (`_repaid = _balance`) so stale overestimates succeed instead of reverting. Document that integrators should prefer `repayAll` for full-debt closures.

### Proof of Concept
Reproducible in the existing Hardhat suite (`test/DebtToken.test.ts` setup):

```ts
// setup: user1 has issued 100 msUSD debt (balanceOf(user1) == 100e18),
//        attacker holds >= 1 wei of msUSD.

// 1. Victim quotes and signs a full repayment.
const amountIn = (await msUSDDebt.quoteRepayIn(await msUSDDebt.balanceOf(user1.address)))._amount;
// victim tx (pending): msUSDDebt.connect(user1).repay(user1.address, amountIn)

// 2. Attacker front-runs with a dust repayment on behalf of the victim.
await msUSDDebt.connect(attacker).repay(user1.address, 1);

// 3. Victim's tx now reverts: BurnAmountExceedsBalance (or underflow at L446).
await expect(
  msUSDDebt.connect(user1).repay(user1.address, amountIn)
).to.be.revertedWithCustomError(msUSDDebt, 'BurnAmountExceedsBalance');

// 4. Repeat step 2 on every resubmission — attacker spends ~1 wei + gas each time.
```

Invariants checked: `whenNotShutdown`, `nonReentrant`, and `onlyIfSyntheticTokenExists` are all satisfied on the deployed configuration; `debtFloorInUsd` does not block a 1-wei dust repay. The only escape is the victim switching to `repayAll`, which — as in the original Timeswap report — makes the workaround a de facto requirement rather than a convenience.
