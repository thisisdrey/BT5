### Title
Hash-mismatched attachment content never demotes/excludes the serving peer from `sources` in `get_prioritized_attachments_requests` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`BatchedRequestsResult::faulty_peers` (download.rs:963) is populated *only* when a peer's HTTP response has status code 404 (download.rs:900-904); a peer that returns HTTP 200 with content whose hash does not match the expected `content_hash` is never inserted into `faulty_peers`. Even where `faulty_peers` is populated, `get_prioritized_attachments_requests` (download.rs:404-478) never consults it — `sources` is rebuilt purely from `self.peers` (download.rs:454-458) for every peer whose inventory bit is set, with no exclusion filter for peers known to have served bad/mismatched content.

### Finding Description
The claimed equality — "trusted-peer-count == peers-that-have-not-served-invalid-content" — is broken. Tracing the code:

1. `get_prioritized_attachments_requests` builds, for each missing attachment, a fresh `sources: HashMap<UrlString, ReliabilityReport>` by iterating every peer that advertises the attachment bit in its inventory page, unconditionally pulling the peer's `ReliabilityReport` from `self.peers` (download.rs:434-458). There is no reference to `faulty_peers`, nor to any per-peer "hash mismatch" flag, in this function.
2. `faulty_peers: HashMap<usize, UrlString>` (download.rs:963) is only populated in the polling loop of the request FSM, and only for the HTTP status-code-404 case (download.rs:900-904). A malicious peer that returns HTTP 200 with attachment bytes that fail the hash check is routed to `state.succeeded.insert(request, Some(response))` (download.rs:909) exactly like a legitimate peer — it is never routed into `faulty_peers`.
3. `AttachmentRequest::get_most_reliable_source` (download.rs:1074-1079) simply selects `max_by_key(|(_, v)| v.score())` over whatever is in `sources` for that request — since the malicious peer is never removed from `sources` nor is any exclusion tracked persistently, it remains eligible for selection on every subsequent `get_prioritized_attachments_requests()` call, and if it is the only (or highest-scoring) peer advertising that attachment, it will be re-selected.

Root cause: the fault-detection surface (`faulty_peers`) is scoped only to transport-level status (404), and the attachment-serving pipeline has no wiring from "hash-mismatch on `succeeded` response" back into either `faulty_peers` or into `self.peers`'s `ReliabilityReport` in a way that is enforced at the `sources`-building step in `get_prioritized_attachments_requests`. Even if some other code path (not found in the searched sections) decrements a reliability score after a hash mismatch is detected downstream, that only affects ranking via `.score()`, not exclusion — the peer stays a valid member of `sources` and can still be chosen again, particularly when it is the sole peer advertising the attachment.

### Impact Explanation
A remote, unprivileged peer that is being crawled for Atlas attachments can repeatedly serve HTTP 200 responses with content that fails the `content_hash` check for a given attachment. Because this response type is never inserted into `faulty_peers` and `sources` is rebuilt without any persistent exclusion of previously-detected-bad peers, the same malicious peer can be re-selected via `get_most_reliable_source` on the very next batch of `get_prioritized_attachments_requests`. This matches the "attachment/BNS mismatch" High-impact category: the node repeatedly fetches, hashes, and discards non-canonical attachment content from a peer that has already proven it serves invalid data, wasting bounded but repeatable node compute/bandwidth on a read path with no forward progress, and the node has no way to converge on peers that actually hold canonical content when the misbehaving peer keeps re-entering the candidate set.

### Likelihood Explanation
Low attacker cost and fully remote: any node operator can run a peer, advertise the relevant attachment in its `/v2/attachments/inv` inventory response, and then serve deliberately wrong bytes from `/v2/attachments/<hash>`. No secret, admin role, or privileged StackerDB slot is required — only the ability to be crawled as an Atlas peer, which any P2P-connected node can be. The behavior is repeatable indefinitely since there is no state that "remembers" the peer served bad content in a way that blocks future `sources` inclusion.

### Recommendation
Extend hash-verification failures (not just HTTP 404) to populate `faulty_peers` (or an equivalent persistent "bad peer" set keyed by `UrlString`), and filter `self.peers` / `sources` construction in `get_prioritized_attachments_requests` (download.rs:454-458) against that set so a peer that has ever served hash-mismatched attachment content is excluded from being selected as a source for subsequent requests, not merely down-ranked by score.

### Proof of Concept
Rust test plan in `stackslib/src/net/atlas/tests.rs` (or a new test module):
1. Construct an `AttachmentsBatchStateContext` with one peer `P` whose `ReliabilityReport` is registered in `self.peers`, and an `AttachmentsBatch` requiring one attachment with `content_hash = H`.
2. Simulate `extend_with_inventories` so `P`'s inventory bit for the target attachment is set, then call `get_prioritized_attachments_requests()` and confirm `P` is present in `sources` for the resulting `AttachmentRequest`.
3. Simulate a completed download batch where `P`'s HTTP 200 response body hashes to `H' != H` (i.e., populate `results.succeeded` with mismatched content) and process it through whatever downstream attachment-acceptance logic exists, then assert whether `P` was added to `faulty_peers` — expect this assertion to fail, showing `faulty_peers` remains empty for hash-mismatch cases.
4. Call `get_prioritized_attachments_requests()` again for a second/same attachment and assert `P` is still present in `sources` and can still be returned by `AttachmentRequest::get_most_reliable_source()` — demonstrating the peer was never excluded.
