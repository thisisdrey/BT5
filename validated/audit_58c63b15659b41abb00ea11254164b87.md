### Title
StackerDB per-slot write-frequency restriction (`write_freq`) is never enforced on chunk acceptance, allowing signers to bypass the configured rate limit - (File: `stackslib/src/net/stackerdb/db.rs`)

### Summary
The StackerDB control-plane smart contract can configure `write_freq`, a minimum wall-clock interval between successive writes to a given slot [1](#0-0) . However, the actual chunk write path, `StackerDBTx::try_replace_chunk` and its helper `insert_chunk`, only validates the signature, staleness (version), and max write count — it never compares the stored `write_time` against `config.write_freq` before accepting a new chunk [2](#0-1) [3](#0-2) . The `write_time` column exists purely for bookkeeping/informational purposes and is updated on every write, but nothing reads it back for validation in the write path.

### Finding Description
`write_freq` is intended to bound how often an authenticated stacker may write to their own slot (a per-slot rate limit set by the controlling smart contract, analogous to the "time-validation implementation" in the Moodle report that was supposed to restrict *when* an action may occur) [1](#0-0) .

The only place `write_freq` is actually consulted is inside `StackerDBSync::run`, where it throttles the *local* node's own outbound sync loop from restarting sync rounds too often — this is a self-throttle, not an authorization check on incoming writes [4](#0-3) .

The equality/fault broken here is: "declared write-interval restriction" vs. "enforced write-interval restriction." The two entry points that actually persist a chunk from a remote party — the HTTP `POST /stackerdb` handler (`poststackerdbchunk.rs`, which calls `try_replace_chunk`) and the P2P push/pull sync paths (`validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs:649-718`, and `insert_chunk`/`try_replace_chunk` in `db.rs`) — never check `data.write_time`/`config.write_freq` before storing. `validate_received_chunk`'s own doc comment explicitly states "does not check write frequency, since the caller has different ways of doing this" [5](#0-4) , but no caller actually performs that check on the acceptance side — only the version and max-writes bounds are enforced [6](#0-5) .

The `Error::TooFrequentSlotWrites` variant exists in `net::mod.rs` [7](#0-6) , indicating that a write-frequency-rejection code path was designed, but it is never constructed/returned anywhere in `try_replace_chunk`, `insert_chunk`, or `validate_received_chunk` — confirming the check was dropped or never wired up on the write-acceptance side.

### Impact Explanation
Any signer authorized to write to a StackerDB slot (a legitimately authenticated but restricted party, analogous to Moodle's "remote authenticated users") can submit chunk updates far more frequently than the smart-contract-configured `write_freq` intends, via either the HTTP `POST /stackerdb` endpoint or unsolicited P2P `StackerDBPushChunk` messages. This is bounded compute/storage DoS on StackerDB replicas that rely on `write_freq` to limit churn, write amplification across the P2P gossip/replication network (since every accepted chunk is broadcast to a subset of neighbors), and undermines application-level assumptions (e.g., signer message cadence in signer coordination StackerDBs) that depend on the rate limit for correctness/anti-spam guarantees.

### Likelihood Explanation
High likelihood for any party with a StackerDB slot allocation. No special privilege beyond being an authorized signer for a slot is needed. Given the max-write-count (`max_writes`) constraint still exists as an upper bound and version numbers strictly increase, the attacker is capped by `max_writes`, but can exhaust that cap arbitrarily fast (as fast as the network/CPU allows) instead of at the intended `write_freq` cadence, defeating the purpose of the restriction well within the configured window.

### Recommendation
Enforce `write_freq` in `StackerDBTx::try_replace_chunk` (or `insert_chunk`) by comparing the existing slot's `write_time` (already available via `SlotValidation`) against `get_epoch_time_secs()` and `config.write_freq`, returning `Error::TooFrequentSlotWrites` when a write arrives before the deadline. Ensure this check applies uniformly to both the HTTP POST path and any P2P chunk-acceptance path that ultimately calls into the DB write functions.

### Proof of Concept
1. Configure a StackerDB contract with `write-freq: u3600` (once per hour) and `max-writes: u1000000`, and allocate a slot to a test signer key.
2. Using the test signer's private key, sign and submit a chunk via `POST /v2/stackerdb/{addr}.{name}/chunks` (per `poststackerdbchunk.rs`) incrementing `slot_version` each time.
3. Immediately repeat step 2 in a tight loop (no delay) — each request succeeds because `try_replace_chunk` only checks `slot_desc.verify`, `slot_version > slot_validation.version`, and `slot_version <= config.max_writes`; it never checks elapsed time since the last `write_time` [8](#0-7) .
4. Observe that writes are accepted at arbitrary speed, well beyond the intended one-per-hour cadence, until `max_writes` is exhausted — confirming `write_freq` provides no actual protection on the acceptance path.
