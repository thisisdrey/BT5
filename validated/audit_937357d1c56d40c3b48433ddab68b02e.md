### Title
Unbounded HTTP response buffering in libsigner's `run_http_request` enables remote memory-exhaustion DoS of the signer - (File: libsigner/src/http.rs)

### Summary
`run_http_request` in `libsigner/src/http.rs` reads an entire HTTP response from the node into an unbounded `Vec<u8>` via `sock.read_to_end(&mut buf)` before any length validation occurs, mirroring the KubeEdge viaduct WSClient flaw where the full body is read into memory with no cap.

### Finding Description
`run_http_request` writes the request, then does: [3](#0-2) 
There is no `Content-Length` cap check, no streaming with a maximum size, and no early abort — `read_to_end` will keep growing `buf` for as long as the peer keeps sending bytes (bounded only by the configured socket read timeout, not by data volume). Only after the full buffer is materialized does `decode_http_response`/`decode_http_body` run. `decode_http_body`'s chunked-path does bound the *decoded* size via `HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into())` [4](#0-3) , but that only limits decoding after the entire raw (possibly non-chunked) response has already been buffered in `run_http_request`; the non-chunked path returns `buf.to_vec()` with no cap at all [5](#0-4) .

This function is the sole HTTP transport used by `StackerDBSession` for every signer→node RPC: `list_chunks`, `get_chunks`, `get_latest_chunks`, and `put_chunk` all funnel through `rpc_request` → `run_http_request` [6](#0-5) . Of these, only `get_latest_chunks` performs a size check on `body_bytes.len()`, and it does so *after* the unbounded read has already completed [2](#0-1) ; `list_chunks`, `get_chunks`, and `put_chunk` (which reads the ack response) have no size check whatsoever.

### Impact Explanation
A stacks node the signer is configured to talk to (which need not be fully trusted/honest — it could be a malicious, compromised, or MITM'd endpoint) can respond to any signer RPC with an arbitrarily large HTTP body. The signer process will buffer the entire response in memory before any size validation, allowing repeated requests to exhaust signer memory and crash the signer process — a remote, unauthenticated memory-exhaustion DoS against the signer, directly analogous to the KubeEdge viaduct WSClient issue (CVE-2022-31080).

### Likelihood Explanation
Every signer performs periodic StackerDB polling (`list_chunks`/`get_chunks`) against its configured node, so a malicious or compromised node is trivially able to trigger this on every poll cycle with no special privileges beyond being the endpoint the signer is configured to reach.

### Recommendation
Cap the raw response size read in `run_http_request` (e.g., limit `read_to_end` via a `Read::take(MAX_MESSAGE_LEN)` or stream-and-check length as data arrives), reject responses whose declared or actual `Content-Length`/body length exceeds `MAX_MESSAGE_LEN`/the StackerDB chunk-size limit *before* fully buffering, and apply the same size check uniformly across `list_chunks`, `get_chunks`, `get_latest_chunks`, and `put_chunk`, not just `get_latest_chunks`.

### Proof of Concept
1. Stand up a TCP listener acting as the "node" that the `StackerDBSession` connects to.
2. On receiving any HTTP request from the signer, respond with `HTTP/1.1 200 OK\r\nContent-Length: <huge>\r\n\r\n` followed by an effectively endless stream of bytes (or simply keep writing bytes without closing the connection) up to the process's available memory.
3. Observe that `run_http_request`'s `sock.read_to_end(&mut buf)` keeps allocating and growing `buf` until the socket read times out or the process runs out of memory, causing the signer to OOM/crash before any size check (in `get_latest_chunks`) or content parsing (`decode_http_response`) is ever reached.
