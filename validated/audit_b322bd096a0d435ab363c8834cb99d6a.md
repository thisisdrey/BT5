### Title
Liquidity index fails to accrue due to double truncating-division in `calc-liquidity-rate`, causing lenders to lose accrued yield - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and all sibling vault contracts)

### Summary
The `next-liquidity-index` accrual path uses `calc-liquidity-rate`, which performs two sequential BPS-scaled (1e4 precision) integer divisions to derive the supply-side interest rate from the borrow rate. In common configurations (moderate borrow rate, low utilization, and non-trivial reserve fee), this rate truncates to `0` even though real borrower interest is being accrued via the separate borrow `index`. Because the multiplier computed from a `0` rate equals `INDEX-PRECISION` (no growth), `lindex` fails to advance for that accrual call, and the yield never gets reflected — it is not merely delayed, since subsequent calls with the same low-utilization/low-rate conditions repeat the same truncation to `0`. This directly mirrors the Surge Protocol M-9 bug class: a legitimate non-zero interest quantity is silently zeroed out by insufficiently-scaled integer division before it is applied to update contract state.

### Finding Description
`calc-liquidity-rate` computes the supply APY as: `util_applied = borrow_rate * util / BPS`, then `result = util_applied * (BPS - reserve_fee) / BPS`. [2](#0-1)  Both `borrow_rate` and `util` are BPS-scaled (`BPS = u10000`) values with no extra precision headroom, so their product divided by `BPS` can easily collapse small fractional rates to `0` before the second division is even applied.

This `liquidity-rate` feeds `next-liquidity-index`, which computes `time-delta` and, if non-zero, calls `calc-multiplier-delta liquidity-rate time-delta false` — note the `round-up` flag is `false`, i.e. it uses `mul-div-down`, which truncates toward zero rather than guaranteeing a minimum increment. [3](#0-2)  If `liquidity-rate` is `0`, the multiplier is exactly `INDEX-PRECISION`, so `calc-index-next` leaves `lindex` unchanged. [4](#0-3) 

By contrast, the borrow-side `next-index` calls `calc-multiplier-delta rate time-delta true`, using `mul-div-up`, which by construction returns at least `1` whenever the numerator is non-zero — so borrowers' debt (`index`) keeps accruing correctly even at very small rates. [5](#0-4)  This asymmetry (round-up for debt, round-down/truncate for liquidity) means debt can grow while the corresponding liquidity/supply-side yield silently does not, for the affected accrual calls.

`accrue()` persists whichever new `index`/`lindex` values were computed, and only updates `last-update` if at least one of the two indices changed — so a stuck `lindex` combined with a moving `index` still updates `last-update`, permanently consuming that time window without lender yield ever being recovered for it. [6](#0-5) 

### Impact Explanation
`lindex` is the sole basis for pricing all zTokens (`zSTX`, `zsBTC`, `zstSTX`, `zUSDC`, `zUSDH`, `zstSTXbtc`) both as redeemable vault shares and, critically, as collateral value in the protocol's oracle pricing logic: `mul-div-down usdc-price lindex INDEX-PRECISION`. [1](#0-0)  If `lindex` fails to accrue while borrowers are still being charged interest, lenders permanently lose the yield corresponding to those accrual windows — it is not double-counted or recovered later, since the missed growth factor is simply absent from the compounding multiplier chain. This is a permanent freezing/loss of unclaimed yield for lenders, matching the in-scope "High" impact category (theft/permanent freezing of unclaimed yield).

### Likelihood Explanation
This requires no privileged access or malicious action — it occurs naturally whenever utilization and/or reserve-fee-adjusted borrow rate fall into ranges where the double BPS-division in `calc-liquidity-rate` truncates to zero, which is a routine market condition (e.g., low utilization periods with a moderate reserve-fee setting), not an edge case requiring adversarial setup. Any ordinary depositor/lender is affected passively simply by holding the vault's zToken.

### Recommendation
Increase the internal precision used for `liquidity-rate` (e.g., carry it in the same `INDEX-PRECISION`-scale, not BPS-scale, until the final multiplier step), or ensure `calc-liquidity-rate`'s divisions round using the same round-up semantics as the borrow-side calculation so a genuinely non-zero rate cannot be truncated to exactly `0` before being applied to `next-liquidity-index`. Alternatively, do not update `last-update` unless the liquidity index actually advanced, mirroring the "don't persist state when computed interest is 0" fix applied upstream in Surge.

### Proof of Concept
1. Vault configured with borrow rate `~1%` (BPS `100`) and current utilization `~1%` (BPS `100`), and `fee-reserve` set to `2000` (20%).
2. `calc-liquidity-rate`: `util_applied = 100*100/10000 = 1`; `result = 1*(10000-2000)/10000 = 8000/10000 = 0` (integer division truncates). [2](#0-1) 
3. `next-liquidity-index` computes `liquidity-rate = 0`, so `multiplier = calc-multiplier-delta(0, time-delta, false) = INDEX-PRECISION + 0 = INDEX-PRECISION`. [7](#0-6) 
4. `calc-index-next(lindex, INDEX-PRECISION) = lindex` unchanged, while `next-index` for the borrow side still increases (since it uses `mul-div-up`, guaranteeing growth for the same non-zero borrow rate). [8](#0-7) 
5. Any user calling `accrue`, `deposit`, `redeem`, `system-borrow`, or `system-repay` (all of which trigger `accrue`) locks in this state: `last-update` advances, borrower debt grows, but `lindex` (and thus zToken valuation/collateral price) does not, for that time window — permanently losing that yield for lenders. [9](#0-8)
