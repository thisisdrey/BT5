## Finding: Unbounded in-memory read of HTTP responses in the signer's StackerDB RPC client

### Title
Signer-to-node RPC client buffers unbounded HTTP responses before any size check, enabling memory-exhaustion DoS - (File: `libsigner/src/http.rs`)

### Summary

### Finding Description
`run_http_request` in `libsigner/src/http.rs` is the transport function used by `StackerDBSession::rpc_request` (`libsigner/src/session.rs:162-172`) to talk to a Stacks node's StackerDB RPC endpoints (`list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk`). It sends the request and then does:

```rust
let mut buf = vec![];
sock.read_to_end(&mut buf)?;
let (headers, body_offset) = decode_http_response(&buf)?;
``` [1](#0-0) 

`Read::read_to_end` grows `buf` without any upper bound until EOF. Only *after* the entire response has been buffered does the code parse headers via `decode_http_response` and then decode the body via `decode_http_body`, which for chunked bodies applies a `MAX_MESSAGE_LEN` cap only inside `HttpChunkedTransferReader` — i.e., after the unbounded raw bytes are already resident in memory:

```rust
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    ...
    let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
    let mut decoded_body = vec![];
    fd.read_to_end(&mut decoded_body)?;
``` [2](#0-1) 

For a non-chunked (Content-Length or connection-close-terminated) response, there is no length cap applied at all before or during the raw read — `sock.read_to_end` will accept as many bytes as the peer sends.

This is the same fault class as the reported OpenClaw bug: the response payload is fully materialized in memory (`arrayBuffer`/`read_to_end`) before any `maxBytes`/length enforcement runs, so `content-length` (or its absence, or a lie about it) does not gate memory usage.

By contrast, the node-side HTTP server code in `stackslib/src/net/httpcore.rs` and the `stackslib/src/net/api/*` request handlers consistently reject oversized bodies against a known `content-length` *before* reading the payload (e.g. `MAX_PAYLOAD_LEN` checks in `postblock_v3.rs`, `postmicroblock.rs`, `posttransaction.rs`, and the `BoundReader`-wrapped preamble/payload readers in `stackslib/src/net/httpcore.rs`), and the P2P protocol enforces `MAX_MESSAGE_LEN` via a `Preamble.payload_len` check before allocating buffers (`stackslib/src/net/codec.rs`). The `libsigner` client-side transport is the outlier that has no analogous pre-read bound. [3](#0-2) [4](#0-3) 

### Impact Explanation
`StackerDBSession` is the signer's RPC client to a configured Stacks-node host over a plaintext TCP connection (no TLS) (`libsigner/src/session.rs:127-136`). Any party able to respond on that TCP connection — e.g. a network-position (MITM) attacker on the path between the signer and its configured node, or a compromised/malicious node the signer is pointed at — can send an HTTP response of unbounded size (with a false or missing `Content-Length`, or simply streaming indefinitely with `Connection: close`) and force the signer process to allocate memory without limit until the process is killed by the OOM killer or the host becomes unresponsive. This is an availability-loss (DoS) condition against signer software, matching CWE-400.

### Likelihood Explanation
The `StackerDBSession` code path is exercised on every routine signer operation (`list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk`), so a compromised/malicious peer at the other end of that connection, or a MITM on the unencrypted TCP link, can trigger the unbounded read on essentially every request cycle with a single crafted response — no authentication or special privileges are needed beyond being the party that answers the socket.

### Recommendation
Wrap the socket read in `run_http_request` with a bounded reader (e.g. `stacks_common::util::retry::BoundReader`) capped at `MAX_MESSAGE_LEN`/`STACKERDB_MAX_CHUNK_SIZE` (as appropriate for the expected response), and reject/abort the read once the cap is exceeded, mirroring the pattern already used in `stackslib/src/net/httpcore.rs` (`BoundReader::from_reader(..., HTTP_PREAMBLE_MAX_ENCODED_SIZE)`) and in `decode_http_body`'s chunked path (`HttpChunkedTransferReader::from_reader(..., MAX_MESSAGE_LEN)`), so unbounded reads never occur, regardless of `Content-Length` correctness.

### Proof of Concept
1. Configure a `StackerDBSession` (or `stacks-signer`) to talk to a TCP endpoint controlled by the attacker (or interpose as a MITM on the plaintext connection to the configured node).
2. Have the attacker endpoint accept the HTTP request and reply with `HTTP/1.1 200 OK\r\nConnection: close\r\n\r\n` followed by an unbounded stream of bytes (no `Content-Length`, never closing the connection promptly).
3. `run_http_request`'s `sock.read_to_end(&mut buf)` will keep growing `buf` in memory for as long as bytes keep arriving, exhausting the signer process's memory.
