## Analysis

The `SimplexFacet` report is a case where a security-relevant selector array — used to register which functions are reachable/permitted — is missing an entry, silently breaking the intended access surface. The exact Rust analog in this repository is `InstanceFilter<RuntimeCall>::filter` used by `pallet-proxy`, which is a match/array-style allow/deny list of `RuntimeCall` variants that determines what a proxy delegate is permitted to execute on behalf of the proxied account. As with `simplexSelectors`, correctness depends entirely on the list being exhaustive — an omitted call variant is a direct, exploitable access-control gap rather than a mere unreachable function.

In `asset-hub-westend-runtime`, `ProxyType::NonTransfer` is defined to allow everything **except** an explicit block-list of value-moving pallets: [1](#0-0) 

This list includes `Balances`, `Assets`, `NftFractionalization`, `Nfts`, `Uniques`, `Scheduler`, `Treasury`, `Vesting::vested_transfer`, `ConvictionVoting`, `Referenda`, and `Whitelist`. `pallet_asset_conversion` (the AMM/swap pallet configured elsewhere in this same runtime file) is not present in this block-list, so `RuntimeCall::AssetConversion(..)` falls through to `true` (allowed) under `ProxyType::NonTransfer`.

### Title
Missing `AssetConversion` entry in `ProxyType::NonTransfer` filter permits value transfer by a "non-transfer" proxy - (File: `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs`)

### Summary
`ProxyType::NonTransfer::filter` is intended to prevent a proxy delegate from moving the proxied account's value. It is implemented as a negated match over an explicit list of value-transferring pallets/calls, analogous to the `simplexSelectors` registration array in the external report. `pallet_asset_conversion` swap extrinsics (which accept an arbitrary `send_to` beneficiary and move the proxied account's tokens into a different account) are absent from that list, so they are treated as non-transfer and permitted.

### Finding Description
`InstanceFilter::filter` for `ProxyType::NonTransfer` returns `!matches!(c, RuntimeCall::Balances{..} | RuntimeCall::Assets{..} | ... | RuntimeCall::Whitelist(..))`. Any `RuntimeCall` variant not enumerated in this list evaluates to `true`, i.e., permitted. Just like the `simplexSelectors` array that must be manually kept in sync with the facet's function set, this filter must be manually kept in sync with every pallet capable of moving value out of the proxied account. `pallet_asset_conversion`'s swap calls (`swap_exact_tokens_for_tokens`, `swap_tokens_for_exact_tokens`) take a `send_to: AccountId` parameter and settle output tokens/native balance to that arbitrary account — functionally a transfer of the proxied account's balance/assets, yet the pallet is not in the exclusion list.

### Impact Explanation
A delegate holding only a `NonTransfer` proxy over a victim account — a permission specifically granted under the assumption that it cannot move funds — can call `AssetConversion::swap_exact_tokens_for_tokens` (or the exact-output variant) through `pallet_proxy::proxy`, swapping the victim's `Balances`/`Assets` holdings and directing the output to an account the delegate controls. This is unauthorized execution/origin-escalation with direct value loss from the proxied account to an unintended beneficiary, which fits the accepted impact categories (origin escalation via a public wrapper, and fund loss to the wrong beneficiary).

### Likelihood Explanation
Medium-to-High. The only precondition is holding a `NonTransfer` proxy (a routinely-granted, "safe" proxy type meant for non-financial delegation) — no privileged role, governance, or malicious infrastructure is required. `pallet-proxy`'s `proxy` extrinsic is a normal public entry point, and `pallet_asset_conversion` is deployed on this runtime, so the path is directly reachable by any account with proxy delegation set up.

### Recommendation
Add `RuntimeCall::AssetConversion(..)` (and any other current or future value-moving pallets, e.g. anything that accepts a `send_to`/`beneficiary`/`dest` parameter) to the `ProxyType::NonTransfer` exclusion list in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs`, mirroring the pattern already used for `Balances`, `Assets`, `Nfts`, etc. Consider adding a compile-time or test-based invariant (e.g., enumerating all `RuntimeCall` variants and asserting each is explicitly classified) to prevent future additions of value-transferring pallets from silently bypassing `NonTransfer`.

### Proof of Concept
1. Account `A` grants `pallet_proxy::add_proxy(delegate = B, proxy_type = ProxyType::NonTransfer)`.
2. `B` calls `pallet_proxy::proxy(real = A, call = RuntimeCall::AssetConversion(pallet_asset_conversion::Call::swap_exact_tokens_for_tokens { path: [DOT, USDT], amount_in: ALL_OF_A_BALANCE, amount_out_min: 0, send_to: B, keep_alive: false }))`.
3. `InstanceFilter::filter` evaluates `ProxyType::NonTransfer` against this call; since `AssetConversion` is absent from the block-list, `!matches!(...)` returns `true` and the call is dispatched with `A`'s origin.
4. `A`'s DOT balance is swapped and the output USDT is sent to `B`, resulting in value leaving `A`'s account despite `B` holding only a `NonTransfer` proxy.

*Note: I was unable to independently verify at runtime whether `pallet_asset_conversion` is wired with `RuntimeOrigin` such that proxy-dispatched calls succeed without additional filtering elsewhere (e.g., a `BaseCallFilter`); this would need to be confirmed by running the asset-hub-westend runtime's proxy/asset-conversion integration tests, which is best done in a full Devin session with build/test access.*
