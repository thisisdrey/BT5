### Title
Permissionless `vesting::distribute` Permanently Blocked by Single Shareholder with Frozen or Unregistered APT Store — (`aptos-move/framework/aptos-framework/sources/vesting.move`)

---

### Summary

`vesting::distribute` and `staking_contract::distribute` are permissionless entry functions that iterate over all shareholders and push APT to each via `aptos_account::deposit_coins`. Because the loop is atomic and `deposit_coins` aborts if the recipient's APT fungible-asset store is frozen **or** if the recipient has no registered CoinStore and has disabled direct coin transfers, a single shareholder can permanently wedge the entire distribution for every other participant. `terminate_vesting_contract` calls `distribute` unconditionally before doing anything else, so it is also permanently blocked.

---

### Finding Description

**Permissionless entry points:**

`vesting::distribute` carries no authentication check — any caller may invoke it. [1](#0-0) 

Inside, it iterates every shareholder and calls `aptos_account::deposit_coins` for each share: [2](#0-1) 

`aptos_account::deposit_coins` has two abort paths relevant here:

**Path A — direct-transfer disabled, no CoinStore:** [3](#0-2) 

If `coin::is_account_registered<AptosCoin>(to)` is false (e.g., the account was migrated to FA-only and the legacy `CoinStore` was removed) **and** `can_receive_direct_coin_transfers(to)` is false (the shareholder called `set_allow_direct_coin_transfers(false)`), the function aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`. Both conditions are fully under the shareholder's own control — no privileged actor is required.

**Path B — frozen FA store:**

`coin::deposit` now routes entirely through the fungible-asset layer: [4](#0-3) 

`primary_fungible_store::deposit` calls `fungible_asset::deposit`, which calls `deposit_sanity_check`: [5](#0-4) 

If the recipient's primary FA store is frozen, the assert fires and the entire transaction reverts.

The formal spec for `deposit_coins` confirms both abort conditions: [6](#0-5) 

**Cascade to `terminate_vesting_contract`:**

`terminate_vesting_contract` calls `distribute` unconditionally before any other state change: [7](#0-6) 

If `distribute` is permanently wedged, the admin can never terminate the contract, and the remaining active stake can never be unlocked to the withdrawal address.

**Same root cause in `staking_contract::distribute`:**

`staking_contract::distribute` is also permissionless and calls `aptos_account::deposit_coins` inside `distribute_internal`: [8](#0-7) [9](#0-8) 

Because `vesting::withdraw_stake` calls `staking_contract::distribute` internally, the vesting distribution is doubly exposed.

---

### Impact Explanation

A single shareholder can permanently freeze the vesting balances of **all** other shareholders in the same contract. Concretely:

- All pending APT rewards and vested principal are locked inside the vesting contract's staking pool indefinitely.
- `terminate_vesting_contract` is also blocked, so the admin cannot recover funds to the withdrawal address.
- The impact is permanent freezing of user-controlled staking/vesting balances — matching the allowed impact gate for "permanent freezing of staking balances."

---

### Likelihood Explanation

The non-privileged trigger (Path A) requires only two self-service actions by a shareholder:

1. Call `set_allow_direct_coin_transfers(false)` — a standard public entry function available to any account.
2. Ensure no `CoinStore<AptosCoin>` exists at their address (e.g., operate as an FA-only account after the coin-FA migration, or simply never register APT on a fresh account).

Both steps are fully unprivileged and reversible by the attacker at will, meaning they can selectively block distribution at any time after being added as a shareholder. Because vesting contracts are long-lived (months to years), the window for exploitation is large.

---

### Recommendation

Replace the push-to-each-recipient loop with a pull model: record each shareholder's claimable amount in storage during `distribute`, and let each shareholder withdraw their own share in a separate transaction. This eliminates the ability of any single recipient to abort the global distribution.

As a shorter-term mitigation, wrap each `deposit_coins` call in a try-catch (or equivalent guard) so that a failed deposit for one recipient is skipped (and the amount is held in escrow for later claim) rather than reverting the entire transaction.

```
Preconditions
─────────────
• A vesting contract exists with shareholders [Alice, Bob, Mallory].
• Mallory is a shareholder (admin included her address at contract creation).

Attack steps (all unprivileged)
────────────────────────────────
1. Mallory calls:
       aptos_account::set_allow_direct_coin_transfers(mallory_signer, false)
   This sets DirectTransferConfig.allow_arbitrary_coin_transfers = false for Mallory's address.

2. Mallory ensures she has no CoinStore<AptosCoin> (operates as FA-only account,
   or simply never registered APT on a fresh address).

3. Anyone calls:
       vesting::distribute(contract_address)

4. Inside distribute(), the loop reaches Mallory's entry:
       aptos_account::deposit_coins(mallory_address, share_of_coins)
   → coin::is_account_registered<AptosCoin>(mallory_address) == false
   → can_receive_direct_coin_transfers(mallory_address) == false
   → abort EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS

5. The entire transaction reverts. Alice and Bob receive nothing.
   Coins extracted from the pool mid-loop are rolled back into the contract.

6. Every future call to distribute() hits the same abort.
   terminate_vesting_contract() also aborts at line 775 (distribute call).
   Alice's and Bob's vested APT is permanently locked.
```
