### Title
Unbounded permissionless registration via dust `DepositToken` transfers lets an attacker fill a victim's `MAX_TOKENS_PER_USER` account list, DoSing deposits and debt issuance — ([File: contracts/Pool.sol](contracts/Pool.sol), [contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The MagicSea M-3 bug class — permissionlessly filling a bounded registration set to DoS legitimate additions — has a direct analog in Metronome. `Pool` tracks, per account, which `DepositToken`s and `DebtToken`s it holds via `depositTokensOfAccount`/`debtTokensOfAccount`, and `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once `MAX_TOKENS_PER_USER = 30` combined entries exist (`Pool.sol:79,143-148`). `DepositToken._transfer` and `_mint` register the recipient unconditionally whenever their prior balance is zero (`DepositToken.sol:486-488, 517-520`), with no opt-in and no minimum amount. An unprivileged attacker can therefore spam 1-wei transfers of every deposit token in the pool to a victim until the cap is reached; afterwards `DepositToken.deposit`/`_mint` and `DebtToken.issue`/`mint` (via `_mint` → `addToDebtTokensOfAccount`) revert for any *new* token the victim touches, blocking collateral top-ups and borrowing.

### Finding Description
- `Pool.sol:79` — `MAX_TOKENS_PER_USER = 30`; `Pool.sol:143-148` — `onlyIfAdditionWillNotReachMaxTokens` reverts once the combined per-account list reaches 30 (confirmed by tests in `test/Pool.test.ts:1386-1416`).
- `DepositToken._mint` (`DepositToken.sol:486-488`) and `DepositToken._transfer` (`DepositToken.sol:517-520`) call `pool.addToDepositTokensOfAccount` on a zero prior balance with `amount_ > 0` — a 1-wei dust transfer registers the recipient.
- `transfer`/`transferFrom` are public and only check the *sender's* unlocked balance (`DepositToken.sol:348-376`); there is no consent or whitelist on the receiver side.
- `DebtToken._mint` similarly calls `pool.addToDebtTokensOfAccount` (`DebtToken.sol:597-600`); `issue` requires `debtPositionOf` health but any new `DebtToken` mint to a capped account reverts.
- Deposit tokens are transferable collateral receipts; the pool can host up to 30 deposit tokens (`addDepositToken` cap, `Pool.sol:703`), so a determined attacker holding dust of each can fill all 30 slots.

### Impact Explanation
For an EOA victim the damage is temporary (they can transfer dust out to free slots at ~30 txs of gas). The severe case is a **contract victim that cannot call `transfer`** — e.g., a smart account, a contract receiving via `deposit(amount, onBehalfOf=contract)` or via `seize` during liquidation (`DepositToken.sol:343-345`, which routes through `_transfer` and also registers the recipient). Once capped, that contract can never hold a new collateral or debt token: deposits revert in `_mint` → `addToDepositTokensOfAccount`, and `issue`/`mint` revert in `addToDebtTokensOfAccount`. For a contract whose only recovery path is depositing more collateral (e.g., an underwater leveraged position), this turns into a permanent inability to deleverage/rescue — liveness DoS with indirect fund loss through forced liquidation, matching M-3's "registrations are permanently bricked" shape.

### Likelihood Explanation
Attack requires no privileges: acquire a dust balance of each enabled `DepositToken` (a minimal deposit per token) and `transfer` 1 wei to the victim. Cost scales with the number of deposit tokens (attacker's dust is also recoverable afterward by transferring out, which removes entries). Feasibility depends on the deployed number of deposit/debt tokens; with few collaterals enabled the cap may be unreachable, so impact is bounded by `min(registeredTokens, 30)` minus the victim's existing entries. For liquidation-critical griefing it must be timed before the victim tops up.

### Recommendation
- Cap per-account lists but make *removal* of unsolicited entries trivial: allow `transfer`/`transferFrom` to also work when balance is dust, and/or add a `Pool.sweepDust(token, account)` permissionless cleanup that removes zero-balance entries (currently `removeFromDepositTokensOfAccount` only fires when a transfer zeroes the balance, which is fine for EOAs but not for contracts that can't initiate transfers).
- Enforce a minimum first-registration amount, or only register on `deposit`/`issue` (mint path) rather than on arbitrary inbound `transfer`/`seize`.
- Alternatively, stop tracking per-account token lists on-chain entirely (the lists appear to be a bookkeeping/gas-saving device) or iterate `depositTokens`/`debtTokens` directly.

### Proof of Concept
Hardhat/Foundry fork sketch (mirrors the repo's existing test harness in `test/Pool.test.ts`):

```ts
// Setup: pool with N deposit tokens d1..dN enabled, victim = contract with no transfer() fn
for (const dt of depositTokens) {
  await underlying.connect(attacker).approve(dt.address, MIN);
  await dt.connect(attacker).deposit(MIN, attacker.address);   // attacker gets dust-capable shares
}
// Fill victim's list
for (const dt of depositTokens) {
  await dt.connect(attacker).transfer(victimContract.address, 1); // registers victim in depositTokensOfAccount
}
// victim list == 30 -> MAX_TOKENS_PER_USER reached
await expect(
  depositToken.connect(anyone).deposit(1e6, victimContract.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(
  debtToken.connect(victimContract).issue(1e18, victimContract.address) // or via SFM mint
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
// victimContract cannot call DepositToken.transfer -> entries are permanent for it
```

Note: if the deployed pool has fewer than 30 enabled tokens and the victim already holds some, the attacker's reachable fill capacity may be insufficient to hit the cap — the finding is strongest where total enabled deposit+debt tokens ≥ 30 or the victim is a contract already near the limit. If you consider EOA-only victims, impact degrades to cheap self-recoverable griefing; if the grading rules exclude recoverable liveness DoS, this should be scored accordingly.
