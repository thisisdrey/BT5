### Title
DelegatedResourceAccountIndex toAccounts/fromAccounts lists can be grown unbounded by a single account, causing unbounded response cost on `GetDelegatedResourceAccountIndex` queries - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`Wallet.getDelegatedResourceAccountIndex` / `getDelegatedResourceAccountIndexV2`, which back the `GetDelegatedResourceAccountIndex(V2)` HTTP/gRPC query endpoints, return the *entire* `toAccounts`/`fromAccounts` list stored for an address with no pagination or size limit. This list is grown, one entry at a time and without any cap, whenever an account calls `FreezeBalanceContract` (with `receiverAddress`) or `DelegateResourceContract` to delegate resources to a new distinct receiver address. An attacker can cheaply delegate to a large number of distinct throwaway addresses, inflating their own index entry, and any subsequent query for that address becomes expensive to build and serialize — the same bug class as `TellerV2.getBorrowerLoanIds` returning an unbounded borrower-controlled array.

### Finding Description
`DelegatedResourceAccountIndexCapsule.addToAccount` / `addFromAccount` simply append to a `repeated bytes` protobuf field with no bound: [1](#0-0) 

This is invoked from the (legacy, non-optimized) delegation path in `FreezeBalanceActuator.delegateResource`, once per unique receiver address, with no limit on the number of distinct receivers a single owner account can accumulate: [2](#0-1) 

Even when the "optimized" delegation path is active (`supportAllowDelegateOptimization`), the index is rebuilt at read time by scanning *all* delegate records with a given prefix and materializing them into an in-memory list with no cap: [3](#0-2) 

The `Wallet` layer exposes this unbounded list directly to callers of the query API, with no offset/limit parameters: [4](#0-3) 

This is wired into the HTTP servlet (`GetDelegatedResourceAccountIndexServlet`/`V2Servlet`) and the gRPC `RpcApiService`, both of which are unauthenticated, publicly reachable full-node query endpoints: [5](#0-4) 

A test in the codebase confirms that repeatedly delegating to new receiver addresses linearly grows `toAccountsList` with no server-side cap (100 addresses used only as a test size, not an enforced limit): [6](#0-5) 

### Impact Explanation
Because the query path (`getDelegatedResourceAccountIndex`/`V2`) always loads and serializes the complete `toAccounts`/`fromAccounts` list with no pagination, an attacker who inflates their own account's delegate index (by issuing many small, cheap `FreezeBalanceContract`/`DelegateResourceContract` transactions to distinct throwaway receiver addresses) can make every subsequent read of that address's delegated-resource index disproportionately expensive to construct and transmit. Since this endpoint is exposed unauthenticated over HTTP and gRPC on full nodes, this is a resource-exhaustion / denial-of-service vector against the node's query-serving capability for that address (and, at sufficient scale, against node responsiveness generally), matching the "API the node can no longer serve" impact bar.

### Likelihood Explanation
Likelihood is limited by cost: each additional entry requires a valid `FreezeBalanceContract` or `DelegateResourceContract` transaction with a positive frozen/delegated balance to a new receiver address, so growing the list to a large size requires the attacker to broadcast (and pay bandwidth/energy for) that many transactions and lock some TRX per entry. This raises the cost floor relative to the original TellerV2 report (where submitting a bid had no analogous cost), making the attack non-trivial but still linear and unbounded — an attacker with moderate capital can still grow the list arbitrarily large over time, since there is no protocol-level cap on the number of distinct delegation targets per account.

### Recommendation
- Add pagination (offset/limit) to `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` in `Wallet.java`, analogous to `getPaginatedProposalList`/`getAssetIssueList(offset, limit)`.
- Enforce a maximum number of distinct delegation targets (`toAccounts`/`fromAccounts`) per account in `FreezeBalanceActuator`/`DelegateResourceActuator` validation, rejecting new delegations once the cap is reached.
- Alternatively, cap the number of entries returned by `DelegatedResourceAccountIndexStore.getWithPrefix` and document/enforce a hard limit at both write and read time.

### Proof of Concept
1. Attacker account `A` repeatedly broadcasts `FreezeBalanceContract` (or `DelegateResourceContract`) transactions from `A`, each specifying a distinct, freshly generated `receiverAddress` and a minimal positive `frozenBalance`/delegated balance.
2. Each transaction causes `FreezeBalanceActuator.delegateResource` (or the corresponding `DelegateResourceActuator` logic) to append the new receiver to `A`'s `DelegatedResourceAccountIndexCapsule.toAccounts` list via `addToAccount`, as shown in `FreezeBalanceActuatorTest.testMultiFreezeDelegatedBalanceForBandwidth` growing the list to 101 entries with no rejection.
3. Once the list contains a very large number of entries (limited only by attacker's willingness to pay transaction/lock costs), any client calls `GET /wallet/getdelegatedresourceaccountindex?value=<A>` (or the gRPC equivalent).
4. `GetDelegatedResourceAccountIndexServlet.fillResponse` → `Wallet.getDelegatedResourceAccountIndex` → `DelegatedResourceAccountIndexStore.getIndex`/`getWithPrefix` loads and serializes the entire list into the JSON/protobuf response with no truncation, imposing unbounded server-side cost and response size for a single query of address `A`.

  public DelegatedResourceAccountIndexCapsule getIndex(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = get(address);
    if (indexCapsule != null) {
      return indexCapsule;
    }
    return getWithPrefix(FROM_PREFIX, TO_PREFIX, address);
  }

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
