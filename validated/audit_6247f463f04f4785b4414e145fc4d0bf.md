### Title
Use of stale/lagging EMA (time-weighted) price instead of real-time spot price to size borrowing power can create protocol bad debt when spot price gaps rapidly - ([File: programs/marginfi/src/state/marginfi_account.rs])

### Summary
The `RequirementType::get_oracle_price_type` mapping deliberately uses the EMA/time-weighted price for `Initial` (borrow) and `Equity` requirement checks, while `Maintenance` (liquidation) checks use the real-time/spot price. This mirrors the UXD bug class: a derivative/lagging price (EMA) is used to size the value extracted from the protocol (borrow power), while a different, more current price (spot) governs when the protocol can act (liquidate) to protect itself. If the EMA and true spot price diverge sharply (e.g., a fast market crash or pump, or an oracle-manipulable move), a borrower can extract liabilities priced against a stale, favorable EMA before the real-time price and liquidation mechanism can catch up, leaving the protocol with under-collateralized debt.

### Finding Description
`RequirementType::get_oracle_price_type` explicitly routes `Initial`/`Equity` (borrow-power) valuations to `OraclePriceType::TimeWeighted` (EMA), and only `Maintenance` (liquidation trigger) to `OraclePriceType::RealTime` (spot): [1](#0-0) 

The README explicitly documents this as an intentional design trade-off, directly analogous to WarTech9's acknowledgment in the original report ("It's a design decision to use the PERP price..."): [2](#0-1) 

`PythPushOraclePriceFeed::get_price_of_type` implements the split, returning `get_ema_price()` for `TimeWeighted` and `get_unweighted_price()` for `RealTime`, with confidence-interval biasing applied only around whichever base price was selected: [3](#0-2) 

This means a user's *borrowing power* (how much they can extract as new debt) is calculated off a smoothed/lagging price, while the protocol's only defense mechanism — liquidation — only reacts to the *current* spot price via `Maintenance` checks. In a scenario where spot price drops rapidly (a genuine market move, or an oracle/venue-specific dislocation such as those already handled specially for Kamino/Drift/Solend/staked integrations elsewhere in `price.rs`), the EMA will still report an inflated valuation for a period. During that window:
- A borrower can deposit collateral and immediately borrow the maximum allowed under the (stale, high) EMA-priced initial health check, extracting liability value that is not backed by the true (spot) value of their collateral.
- Because `Maintenance`/liquidation logic uses the spot price, the account may already be unhealthy by spot-price terms at the moment the debt is created, but liquidation can only occur after the fact — by which time the borrowed funds have already been withdrawn.
- The confidence-interval adjustment (Low/High bias) is applied only to the *same* price type (EMA for borrow, spot for liquidation) and does not bound the *EMA-to-spot* divergence itself, so it does not protect against this specific class of gap.

### Impact Explanation
This can result in the protocol extending loans against collateral that, by the time the transaction lands, is already worth materially less in spot terms than the EMA implies. The excess extracted value becomes unbacked debt (bad debt) that must ultimately be socialized via the bankruptcy/insurance mechanism (`lending_pool_handle_bankruptcy`), which pulls from the insurance fund and socializes losses among other lenders in the affected bank — a direct insolvency/bad-debt impact analogous to UXD's peg destabilization from Perp-vs-spot price gaps.

### Likelihood Explanation
This requires a rapid, large divergence between EMA and real-time spot price for a given oracle feed — plausible during flash crashes, thin-liquidity assets, or an oracle/venue-level price dislocation, and is acknowledged by the maintainers as an accepted design trade-off rather than a bug that's actively mitigated (matching the "Medium" severity classification and maintainer acknowledgment in the original UXD report: "a design decision... valid in certain market conditions"). Given the confidence-interval buffer is comparatively small (max default 10%, clamp to 5% typical) and EMA lag can exceed this under stress, likelihood is non-trivial but conditioned on specific volatile market conditions, not an always-exploitable path.

### Recommendation
Bound the allowed divergence between the time-weighted (EMA) price used for `Initial`/`Equity` requirement checks and the real-time (spot) price for the same oracle feed — e.g., reject or clamp borrow-power calculations when `|EMA - RealTime| / RealTime` exceeds a configurable threshold, similar to the existing confidence-interval clamp. Alternatively, use the more conservative (lower, for assets; higher, for liabilities) of the EMA and spot prices when computing `Initial`/`Equity` requirement values, consistent with the protocol's existing "conservative" pricing philosophy for confidence intervals.

### Proof of Concept
Not independently reproducible from the indexed code alone — a full PoC would require simulating a Pyth push oracle feed where `ema_price` and `price` diverge sharply within a single slot/transaction window (as is already exercised for confidence/staleness in `programs/marginfi/tests/misc/risk_engine_flexible_oracle_checks.rs` and the fuzzer's `flow_oracle_move` harness in `trident-tests/fuzz_0/test_fuzz.rs`), then demonstrating that a borrow sized against the stale EMA immediately produces a maintenance-unhealthy (spot-priced) position that could not be raised under real-time pricing alone. This would need to be validated with a running Devin session against the actual test fixtures, since the index does not include the full oracle-feed test-mocking logic needed to construct this exact divergence scenario with certainty.

impl RequirementType {
    /// Get oracle price type for the requirement type.
    ///
    /// Initial and equity requirements use the time weighted price feed.
    /// Maintenance requirement uses the real time price feed, as its more accurate for triggering liquidations.
    pub fn get_oracle_price_type(&self) -> OraclePriceType {
        match self {
            RequirementType::Initial | RequirementType::Equity => OraclePriceType::TimeWeighted,
            RequirementType::Maintenance => OraclePriceType::RealTime,
        }
    }

impl PriceAdapter for PythPushOraclePriceFeed {
    fn get_price_of_type(
        &self,
        price_type: OraclePriceType,
        bias: Option<PriceBias>,
        oracle_max_confidence: u32,
    ) -> MarginfiResult<I80F48> {
        let price = match price_type {
            OraclePriceType::TimeWeighted => self.get_ema_price()?,
            OraclePriceType::RealTime => self.get_unweighted_price()?,
        };

        match bias {
            None => Ok(price),
            Some(price_bias) => {
                let confidence_interval = self.get_confidence_interval(
                    matches!(price_type, OraclePriceType::TimeWeighted),
                    oracle_max_confidence,
                )?;

                let biased_price = match price_bias {
                    PriceBias::Low => price
                        .checked_sub(confidence_interval)
                        .ok_or_else(math_error!())?,
                    PriceBias::High => price
                        .checked_add(confidence_interval)
                        .ok_or_else(math_error!())?,
                };

                Ok(biased_price)
            }
        }
    }
