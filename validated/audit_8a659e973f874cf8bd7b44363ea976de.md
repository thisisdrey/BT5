### Title
Off-by-one in `MarketOrderIdListCapsule.getAllOrder` returns one more order than the requested limit - (File: chainbase/src/main/java/org/tron/core/capsule/MarketOrderIdListCapsule.java)

### Summary
`MarketOrderIdListCapsule.getAllOrder(MarketOrderStore, long limit)` is intended to cap the number of orders returned to `limit`, but the bounds check `if (count > limit) break;` is evaluated *after* the current order has already been appended to the result list and after `count` has been incremented, so the loop always adds one extra order before the break condition trips.

### Finding Description
```
public List<MarketOrderCapsule> getAllOrder(MarketOrderStore orderStore, long limit)
    throws ItemNotFoundException {

  List<MarketOrderCapsule> result = new ArrayList<>();

  long count = 0;
  byte[] orderId = this.getHead();
  if (!ByteArray.isEmpty(orderId)) {
    MarketOrderCapsule makerOrderCapsule = orderStore.getUnchecked(orderId);
    while (makerOrderCapsule != null) {
      result.add(makerOrderCapsule);
      makerOrderCapsule = makerOrderCapsule.getNextCapsule(orderStore);
      count++;
      if (count > limit) {
        break;
      }
    }
  }
  return result;
}
``` [1](#0-0) 

Tracing the loop: on the `limit`-th iteration, `count` becomes `limit` and the guard `count > limit` is false, so the loop does not stop. On the next (`limit+1`-th) iteration the order is appended to `result` **first**, then `count` becomes `limit+1`, and only then does the guard trigger the `break`. The net effect is that `result` always contains `limit + 1` entries instead of the intended `limit`, exactly mirroring the Footium `maxGenerationId`/`generationId >= maxGenerationId` off-by-one pattern: the boundary comparison is checked one step too late (post-increment, post-append) instead of before the element is added.

This is the same class of bug used elsewhere in this file correctly — the sibling helper `getOrderSize` increments before comparing to a fixed sentinel, but here the increment/append ordering relative to the limit check is inverted, producing an off-by-one over-count.

### Impact Explanation
This method backs the read path used to enumerate a market order list (via `Wallet` and, transitively, exposed gRPC/HTTP/JSON-RPC query APIs that list market orders for a token pair/account). Because it returns one more element than the caller-specified/expected limit, any caller relying on the `limit` parameter to bound iteration, pagination, or resource sizing (e.g. building responses, bounding loop iterations for the same reasons `MAX_MATCH_NUM`/`MAX_ACTIVE_ORDER_NUM` bounds exist elsewhere in the market module) will process/return one extra `MarketOrderCapsule` than intended. This is a boundary/logic defect consistent with the "documentation/intended max vs. actual max" class of bug from the reference report, but based on the code reachable here it manifests as a data/count correctness issue in a read-only query path rather than a fund-theft or unauthorized-mint primitive — I could not confirm within the available context that this off-by-one is used anywhere to bound a security-critical accounting invariant (e.g., total resource caps enforced elsewhere such as `MAX_MATCH_NUM` in `MarketSellAssetActuator`, which has its own separate, correctly-ordered bound check).

### Likelihood Explanation
The defect triggers deterministically whenever an order list has more than `limit` linked entries and the API is invoked with that `limit` — no adversarial input beyond a sufficiently long order chain is required. However, because `getAllOrder`'s only located caller context found is a read path (`Wallet.java`), the practical security impact is limited to over-returning by one record rather than corrupting consensus state or account balances.

### Recommendation
Move the bound check before appending to the result (pre-increment/pre-append), e.g.:
```java
while (makerOrderCapsule != null && count < limit) {
  result.add(makerOrderCapsule);
  makerOrderCapsule = makerOrderCapsule.getNextCapsule(orderStore);
  count++;
}
```
so that `result.size()` never exceeds `limit`.

### Proof of Concept
Given a `MarketOrderIdListCapsule` whose linked list contains `limit + 1` (or more) orders, calling `getAllOrder(orderStore, limit)` returns a list of size `limit + 1`:
1. Build an order chain with `limit + 1` nodes.
2. Call `getAllOrder(orderStore, limit)`.
3. Observe `result.size() == limit + 1`, i.e., one more than the caller-specified cap — confirmed purely from source-code trace of the loop/guard ordering shown above [1](#0-0) .

**Note on confidence/limitations:** I was unable to fully trace all call sites and confirm the downstream security-critical impact of this off-by-one (e.g., whether any consensus-affecting logic — as opposed to a query/API listing path — relies on this exact `limit` boundary), because the tool budget was exhausted before I could inspect the `Wallet.java` usage in full. I could not find a stronger, more clearly fund-impacting off-by-one analog (matching all criteria: unprivileged-reachable, concrete unauthorized operation/theft/freezing/crash) elsewhere in the areas searched (asset issuance, freeze/unfreeze, delegate resource, vote counting, account permission key limits, bandwidth/energy limit checks, VM call-depth checks, and the `MarketSellAssetActuator` match-count check) — those all either use correctly-ordered boundary comparisons or, in the `MarketSellAssetActuator.matchOrder` case, throw a `ContractValidateException`/`ContractExeException` that would cause the whole transaction to fail and its state changes to be rolled back, negating exploitability.
