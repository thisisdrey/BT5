### Title
Permanent freeze of `WalletContract` funds via gas-exhaustion abort of `nep_141_storage_balance_callback` while `has_in_flight_tx` is stuck at `true` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`rlp_execute` persists `has_in_flight_tx = true` as soon as it schedules a promise, and the flag can only be reset by the `#[private]` callbacks `address_check_callback`, `nep_141_storage_balance_callback`, and `rlp_execute_callback`. Because NEAR function-call receipts are atomic (a panicking/OOG receipt discards all of its own state writes), an attacker who controls the NEP-141 token contract that the wallet's Ethereum-emulated `ERC20Transfer` action targets can make `storage_balance_of` return an oversized/adversarial JSON payload that makes `serde_json::from_slice` in `nep_141_storage_balance_callback` exceed the callback's fixed static gas, causing the whole callback receipt (including the `self.has_in_flight_tx = false;` write at its top) to be rolled back, permanently leaving the flag `true`.

### Finding Description
`rlp_execute` sets `self.has_in_flight_tx = true` right after scheduling a promise [1](#0-0) . For an `EthEmulationKind::ERC20Transfer`, `inner_rlp_execute` schedules `storage_balance_of` on the attacker-chosen `target` token contract, followed by `.then(ext.nep_141_storage_balance_callback(...))`, with `callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())` — a fixed base of 15 Tgas plus whatever gas value the signer put in their Ethereum transaction for the transfer action [2](#0-1) .

`nep_141_storage_balance_callback` resets the in-flight flag as its very first statement, then deserializes the promise result via `serde_json::from_slice::<Option<StorageBalance>>(&value)`, where `value` is fully controlled by the (attacker-deployed) `token_id` contract: [3](#0-2) 

Because a NEAR function-call receipt that traps/aborts (e.g. `Exceeded the prepaid gas`) discards *all* state mutations made during that call, if `serde_json::from_slice` on an adversarially large/expensive JSON payload consumes more gas than the callback's static budget, the receipt fails atomically and the earlier `self.has_in_flight_tx = false;` write is rolled back — leaving the persisted state exactly as it was before the callback ran, i.e. `has_in_flight_tx == true`. No public method other than the three `#[private]` callbacks (only invocable by the contract itself as part of a promise chain that must actually complete) ever clears the flag [4](#0-3) . From that point, every future call to `rlp_execute` short-circuits with the "transaction already in progress" error [5](#0-4) , forever.

The attacker's only requirement is to deploy their own NEP-141-shaped contract (fully within an unprivileged attacker's capability) whose `storage_balance_of` returns a large or gas-expensive JSON value (e.g. a huge numeric literal that `serde_json` must scan character-by-character before failing type validation), and to have any wallet's `rlp_execute` be invoked with an `ERC20Transfer` targeting that contract with an action gas value too small to cover parsing the oversized response. Existing checks (nonce/signature validation, the single-in-flight-tx guard itself, and per-call gas metering) do not prevent this: gas metering is exactly the mechanism exploited, and the in-flight guard is the very thing being permanently mis-set.

### Impact Explanation
This results in a permanent freeze of the wallet's ability to execute any subsequent Ethereum-emulated action via `rlp_execute` (transfers, function calls, key management), since the entry point is unconditionally gated by `has_in_flight_tx` with no recovery path. This matches the NEAR bounty category of "permanent freezing of user funds," since funds held by the account become permanently unspendable through the wallet-contract interface.

### Likelihood Explanation
The attacker only needs to deploy an ordinary wasm contract mimicking a NEP-141 token — no validator/node/social-engineering access is required, matching the allowed attacker capabilities. The remaining precondition is that some wallet's `rlp_execute` call targets the attacker's malicious "token" with an action-gas value insufficient to cover parsing an inflated response; this is plausible whenever a wallet/dApp is induced to interact with an unknown/attacker-supplied token contract with default/low gas values (a common pattern for ERC-20-style interactions), and is fully repeatable/deterministic once achieved (the flag never self-heals).

### Recommendation
- Do not mutate `has_in_flight_tx` before all fallible/attacker-influenced work (e.g., `serde_json::from_slice` on external promise results) in each callback; instead compute the outcome first and clear the flag only right before returning, or (more robustly) restructure the callback so the reset happens via a state write that is guaranteed regardless of parsing outcome (e.g., wrap parsing in a way that cannot abort the whole receipt, such as bounding/capping the size of `value` before parsing, or using a cheaper/streaming validation that fails fast without full-buffer scanning).
- Bound the size of cross-contract call results before calling `serde_json::from_slice`, and/or allocate callback gas proportional to a worst-case bounded payload size rather than a fixed constant plus attacker-uncontrolled user gas.
- Consider adding an explicit, permissionless "unstick" mechanism (e.g., a self-callback with a timeout/height-based recovery) so a stuck `has_in_flight_tx` cannot brick the account forever even if a callback aborts for unrelated reasons (e.g., host-level bugs, protocol gas repricing).

### Proof of Concept
Runtime/test-loop integration test plan:
1. Deploy a `WalletContract` for an eth-implicit account and fund it.
2. Deploy a malicious "NEP-141-like" contract whose `storage_balance_of` method returns a large/adversarial JSON payload (e.g., a value with a very long digit sequence for an integer field) sized so that `serde_json::from_slice` in `nep_141_storage_balance_callback` costs more gas than `NEP_141_STORAGE_BALANCE_CALLBACK_GAS + action.gas()`.
3. Craft and submit a signed RLP Ethereum transaction emulating an `ERC20Transfer` with `target` set to the malicious contract and a modest `gas` value for the transfer action, and call `rlp_execute` with it.
4. Advance blocks until the `nep_141_storage_balance_callback` receipt is applied; assert the receipt execution outcome is `Failure`/`Exceeded the prepaid gas.`.
5. Call `get_nonce`/`rlp_execute` again (with a trivial valid action) on the same account across several subsequent blocks and assert every call returns `ExecuteResponse { success: false, error: Some("Error: transaction already in progress, please try again later.") }` indefinitely, confirming the wallet is permanently frozen.

    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
