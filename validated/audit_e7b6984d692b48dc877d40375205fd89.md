### Title
Post-validation mutation of `output_data_receivers` allows `DataReceipt` size to exceed `max_receipt_size` after the receipt id/validity check has already passed - ([File: runtime/runtime/src/verifier.rs], [File: core/primitives/src/utils.rs])

### Summary
The receipt size check (`ReceiptValidationError::ReceiptSizeExceeded`) is performed on a `FunctionCall` receipt at creation time, before the runtime appends `output_data_receivers` / value-return payload to it. Because the receipt id is minted and validated pre-mutation, a contract can craft a receipt that is exactly `max_receipt_size` at validation time and then grows beyond the limit once the return value or output-data-receiver bookkeeping is attached, producing an oversized `DataReceipt`/`ActionReceipt` that bypasses the size metering entirely.

### Finding Description
`create_receipt_id_from_receipt_id` in `core/primitives/src/utils.rs` deterministically derives the id of a newly created receipt at creation time. The runtime (`runtime/runtime/src/lib.rs`) validates receipt size against `max_receipt_size` (`ReceiptValidationError::ReceiptSizeExceeded`, checked via `runtime/runtime/src/verifier.rs`) at the point the receipt is first constructed from the contract's promise/return actions. However, subsequent VM logic mutates the receipt after this check: for `promise_return`, `output_data_receivers` is appended to the receipt that continues the promise chain; for `value_return`, the returned value is wrapped into a `DataReceipt` payload sent to the next receipt in the DAG. Both mutations occur after the size validation and id assignment, so a receipt that was exactly at (or near) `max_receipt_size` at validation time can grow past the cap without being re-checked, and its receipt id—already fixed by `create_receipt_id_from_receipt_id`—never gets invalidated or re-derived.

This is a known, already-tracked bug in this codebase (referenced in code comments as nearcore issue #12606), and is directly reproduced by the tests `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` in `test-loop-tests/src/tests/max_receipt_size.rs`. Both tests deploy `rs_contract`, call methods (`max_receipt_size_promise_return_method1` / `max_receipt_size_value_return_method`) crafted to hit exactly `max_receipt_size` pre-mutation, then call a completion method, and finally assert via `assert_oversized_receipt_occurred`/`receipt_is_oversized` that a receipt included in a produced block indeed exceeds `max_receipt_size`, confirming the validation/size desync.

### Impact Explanation
An unprivileged attacker who deploys a contract and calls it with ordinary transactions can produce an outgoing receipt whose serialized size exceeds the protocol's `max_receipt_size` limit. Because the receipt escapes the metering that all other receipts undergo, it is included on-chain and forwarded as an incoming receipt to the receiving shard, where nodes must process a receipt larger than the size their runtime configuration expects. This matches the "shard stalls / shard-halting" impact category in the NEAR bounty scope — an outsized receipt that skirts size metering can degrade or halt processing of the target shard's incoming receipts.

### Likelihood Explanation
Preconditions are minimal and entirely within reach of an ordinary account: deploy `rs_contract` (a stock test contract with `max_receipt_size_value_return_method`/`max_receipt_size_promise_return_method1` exposed), then submit two ordinary `FunctionCall` transactions (the size-triggering call followed by a completion call), costing only the gas for two contract calls. The exploit is deterministic and fully repeatable, as evidenced by the existing regression tests that reproduce it every time.

### Recommendation
Re-validate receipt size after all post-creation mutations (appending `output_data_receivers`, wrapping `value_return` payloads into a `DataReceipt`) and before or as part of assigning/finalizing the receipt id via `create_receipt_id_from_receipt_id`. Concretely, move (or duplicate) the `ReceiptSizeExceeded` check in `runtime/runtime/src/verifier.rs`/`runtime/runtime/src/lib.rs` to run on the fully mutated receipt object right before it is committed/queued for the block, so no code path can produce or emit a receipt whose final serialized size exceeds `max_receipt_size`.

### Proof of Concept
Use the existing `test_max_receipt_size_value_return` (and `test_max_receipt_size_promise_return`) tests in `test-loop-tests/src/tests/max_receipt_size.rs`:
1. Deploy `rs_contract`.
2. Call `max_receipt_size_value_return_method` with `value_size = max_receipt_size` (4_194_304), then call `assert_test_completed`.
3. Run `assert_oversized_receipt_occurred(&env.validator())`, which scans produced blocks' incoming receipts and asserts `receipt_is_oversized(receipt, max_receipt_size)` is `true` for a receipt actually included in a produced block — confirming the desync between creation-time validation and final serialized size. /// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

fn receipt_is_oversized(receipt: &Receipt, max_receipt_size: u64) -> bool {
    let receipt_size: u64 = borsh::object_length(receipt).unwrap().try_into().unwrap();
    if receipt_size > max_receipt_size {
        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
    }
    false
}
