No vulnerability found for this question.

This exact attack scenario (an attacker packing many `AddKeyAction`s in one receipt against an account with many pre-existing keys, following a large read) is already the scenario the codebase's `EnforceStorageProofLimitForAllActions` protocol feature was built to catch, and it is directly tested by the very test referenced in the question.

The relevant check runs after **every** action in `apply_action_receipt`, not just after the whole receipt finishes: it snapshots `recorded_storage_size_upper_bound()` before the receipt, and after each action's `apply_action` call it computes `recorded_by_receipt = trie.recorded_storage_size_upper_bound() - size_before` and sets `ActionErrorKind::ReceiptStorageProofSizeExceeded` as soon as that exceeds `per_receipt_storage_proof_size_limit`, breaking the action loop immediately. [1](#0-0) 

This means the overshoot past the limit is bounded to at most the storage proof recorded by a single `AddKey` action (one access-key trie lookup/insert), not an unbounded amount accumulated over N actions — the loop stops and fails the receipt at the first action that pushes the running total over the limit, exactly matching `ActionErrorKind::ReceiptStorageProofSizeExceeded`. [2](#0-1) 

The exact test proposed in the question already exists in the repo and asserts the expected failure: `test_add_keys_after_large_read_exceed_receipt_storage_proof_limit` builds a receipt with a large read followed by `NUM_ADDED_KEYS` `AddKeyAction`s against an account with `NUM_EXISTING_KEYS = 16` pre-existing keys, and asserts that at `PROTOCOL_VERSION` (with `EnforceStorageProofLimitForAllActions` enabled) the receipt fails with `ActionErrorKind::ReceiptStorageProofSizeExceeded { limit }`, that the failing action index is one of the `AddKey`s (not the read), and that none of the added keys were persisted to state (rollback on failure). [3](#0-2) [4](#0-3) 

The test also demonstrates the pre-fix behavior for contrast: at `feature_version - 1` (before `EnforceStorageProofLimitForAllActions`), the same receipt succeeds because only `FunctionCall` actions were bounded by the in-VM `RecordedStorageCounter`, confirming the fix specifically closes this gap. [5](#0-4) 

Since the check fires per-action (not only at receipt end) and the receipt is rolled back on failure (per `apply_action_receipt`'s commit/rollback semantics), the attacker cannot push the chunk's recorded storage proof past the hard per-receipt bound in a way that would let a chunk producer include an out-of-bounds witness that validators would reject — the runtime itself refuses to let the receipt succeed, and the overshoot is bounded to one action's worth of trie nodes. There is no reachable path here that causes state-root divergence, fund loss, or shard halting; the code path is functioning as designed and already covered by an existing regression test.
