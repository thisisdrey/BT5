### Title
Silent assertion-guard bypass in `EnergyProcessor.calculateGlobalEnergyLimit` allows divide-by-zero energy-limit miscalculation - (File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java)

### Summary
The pam_usb bug class is: a defensive check implemented with a language `assert` construct that is silently stripped in normal production builds, so the guarded invariant is never enforced at runtime, and the code after it runs on the assumption the invariant always held. The direct analog in java-tron is `EnergyProcessor.calculateGlobalEnergyLimit()`, which uses a bare Java `assert` as the only guard against a zero `totalEnergyWeight` divisor before performing energy-limit arithmetic. Java assertions are disabled by default unless the JVM is started with `-ea`; standard node startup scripts do not pass this flag, so in every real deployment this `assert` is a no-op, exactly mirroring the `-DNDEBUG` situation in the report.

### Finding Description
`calculateGlobalEnergyLimit` computes an account's energy limit from the network-wide `totalEnergyWeight`: [1](#0-0) 

The only protection against a zero/negative `totalEnergyWeight` when `allowNewReward()` is `false` is:
```java
if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
  return 0;
} else {
  assert totalEnergyWeight > 0;
}
``` [2](#0-1) 

If `allowNewReward()` is `false` while `totalEnergyWeight` is `0` (or negative), the early-return branch is skipped, the `assert` is compiled/executed as a no-op in production (default JVM assertions-disabled behavior), and control falls through to:
```java
long energyWeight = frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
``` [3](#0-2) 

Unlike the C `assert(data != NULL)` case, which turns into a NULL dereference crash, this Java division is a `double` division, so `x / 0.0` yields `Infinity` rather than throwing. Casting `Infinity` to `long` yields `Long.MAX_VALUE`, so any account satisfying `frozeBalance >= TRX_PRECISION` is granted an effectively unlimited energy limit from `calculateGlobalEnergyLimit()`, which directly feeds `useEnergy()`'s check `energy > (energyLimit - newEnergyUsage)`: [4](#0-3) 

This is the exact same bug class as the report: a guard implemented as a language-level `assert` that the deployed runtime silently omits, letting the "impossible" state (here, division by a zero/degenerate weight) reach code that assumed the guard had already rejected it.

### Impact Explanation
If this branch is reached in a live network, energy metering — the mechanism that limits how much computation an account may spend for free based on staked/frozen TRX — is defeated for any account with a nonzero frozen-for-energy balance: it receives an unbounded energy allowance instead of a proportionally computed one. This lets a normal signed transaction (a `TriggerSmartContract` call) consume unmetered TVM computation, which is an "unbacked" resource-accounting bypass and a node-resource-exhaustion vector, both explicitly in scope (TVM energy metering).

### Likelihood Explanation
Exploitability depends on chain-wide state, not solely on attacker-controlled transaction fields: `totalEnergyWeight` must be `0` (or negative) while `allowNewReward()` is `false` at the same time. `totalEnergyWeight` is a network aggregate maintained by `DynamicPropertiesStore`/maintenance-cycle logic, not directly settable by a single transaction, so I cannot construct a concrete, self-contained proof-of-concept transaction sequence that forces this exact combination purely from the analyzed code; it would require confirming whether `allowNewReward()`-off networks (or newly bootstrapped/private networks) can ever reach `totalEnergyWeight == 0` in practice. This uncertainty means the finding demonstrates the code-level defect (a stripped runtime guard on a divide-by-zero/degenerate-input path in the energy-metering hot path) with high confidence, but I cannot fully verify attacker-triggerable reachability of the vulnerable state from a single unprivileged transaction with the information available.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` with an explicit runtime check (`if (totalEnergyWeight <= 0) { return 0; }` or throw), independent of `allowNewReward()`, so the divisor is always validated regardless of JVM assertion settings. More broadly, audit all production (non-test) `assert` usages in `chainbase`/`actuator`/`framework` main sources — e.g. `ResourceProcessor.increase()`'s `assert now > lastTime;` [5](#0-4)  and `TrieImpl.java`'s asserts  — and convert any that guard against invalid/attacker-influenced state into explicit conditional checks that throw or fail safely, since Java assertions are disabled by default in production JVMs.

### Proof of Concept
Not fully constructible from the available code alone: reproducing the vulnerable state requires driving live `DynamicPropertiesStore` values (`totalEnergyWeight == 0` with `allowNewReward() == false`), which is network/maintenance-cycle state rather than a single transaction parameter. Conceptually: (1) reach or construct a chain state where no account has frozen balance for energy under the old model and the `allowNewReward` proposal is not yet activated, so `totalEnergyWeight` settles at `0`; (2) have any account with `frozeBalance >= TRX_PRECISION` (e.g., from a stray legacy freeze) call `calculateGlobalEnergyLimit()` via a `TriggerSmartContract` transaction; (3) observe `useEnergy()` grant a near-`Long.MAX_VALUE` energy limit instead of `0`, allowing unmetered contract execution.
