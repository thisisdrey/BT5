### Title
`ExchangeTransactionActuator`'s slippage check (`expected`) is validated against an exchange-rate computation that mutates state as a side effect, decoupling the checked value from the applied value - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
`ExchangeTransactionActuator` exposes the same class of slippage-enforcement bug as the Velvet Capital `_minMintAmount` finding: a user-supplied minimum-output guard (`expected`) is checked against a value computed at one point in the actuator lifecycle, but the value actually credited to the user's account is produced by an independent, later recomputation of the same non-idempotent function, `ExchangeCapsule.transaction()`. Because `transaction()` is not a pure/read-only calculator — it mutates the `Exchange` protobuf balances as a side effect every time it is called — the value validated in `validate()` and the value credited in `execute()` are not guaranteed to derive from the same effective pool state.

### Finding Description
`ExchangeTransactionActuator.doValidate()` fetches a fresh `ExchangeCapsule` and calls: [1](#0-0) 
to compute `anotherTokenQuant`, checking it against the user-supplied `tokenExpected` (the slippage floor, analogous to `_minMintAmount`).

Separately, `execute()` fetches the exchange capsule again and calls the same method: [2](#0-1) 
to compute the amount that is actually credited to the account and persisted via `Commons.putExchangeCapsule(...)`.

The root cause is that `ExchangeCapsule.transaction()` is not side-effect-free: it computes the swap output and, in the same call, overwrites `firstTokenBalance`/`secondTokenBalance` on the capsule: [3](#0-2) 

This mirrors the reported pattern in Velvet Capital's `VaultManager._depositAndMint`, where `_verifyUserMintedAmount` is checked against a `tokenAmount` computed before fee-mutating logic runs, so the checked value and the final applied value can diverge. Here, the two calls to `transaction()` (one in `validate()`, one in `execute()`) are structurally two independent applications of a state-mutating function to what should conceptually be a single quote-then-apply operation, rather than a single "compute-once, verify, then apply the same result."

### Impact Explanation
If the two `get()` calls in `validate()` and `execute()` return the same underlying mutable `ExchangeCapsule` object (e.g., due to any object-level caching in the store/revoking-DB layer between the two calls of the same transaction, or due to any future refactor that reuses one fetched capsule instance across the two actuator phases), the balance mutation performed inside `validate()`'s call to `transaction()` would already be applied to the in-memory object before `execute()` calls `transaction()` again — causing the AMM balance shift to be applied twice and the actually credited `anotherTokenQuant` in `execute()` to be computed from an already-shifted, non-representative pool state that was never checked against the user's `expected` minimum. This would silently break the slippage invariant the `expected` field exists to enforce, and corrupt on-chain exchange pool balances (a double-application of the swap effect), which is an unbacked-balance risk for the `Exchange`/`ExchangeV2` pools.

I was not able to fully confirm, within the available tooling, whether `AccountStore`/`ExchangeStore.get()` returns a shared mutable instance versus a freshly-deserialized copy on each call in the current TRON store implementation (`TronStoreWithRevoking`/cache layer) — this determines whether the divergence is currently exploitable in production or only latent. This is the key open question that would need direct inspection of the store's caching/`getUnchecked`/LRU-cache behavior to resolve with certainty.

### Likelihood Explanation
Likelihood is Medium: exploitability depends entirely on store-level object caching behavior between the `validate()` and `execute()` phases of the same actuator invocation, which I could not conclusively verify. If capsules are always freshly deserialized on every `get()` (no shared-reference caching), the two `transaction()` calls are independent and produce consistent results, and the bug is not exploitable. If any caching returns the same object reference across the two calls (which is a known pattern risk in this codebase, given other stores use in-memory maps/caches), the divergence becomes live on every `ExchangeTransactionContract` processed.

### Recommendation
Refactor `ExchangeCapsule.transaction()` into a pure calculation (no mutation of `this.exchange`) plus a separate `applyTransaction(...)` mutator, so `validate()` only ever computes a quote without mutating any capsule, and `execute()` computes the quote once, checks it against `expected`, and then applies the mutation exactly once using that same value — removing any possibility that the checked amount and the applied amount can diverge.

### Proof of Concept
Not independently reproducible from static review alone: an exploit demonstration would require confirming that `chainBaseManager.getExchangeStore()`/`getExchangeV2Store()` `.get()` returns a cached, shared `ExchangeCapsule` instance across the `validate()` and `execute()` calls of the same `ExchangeTransactionActuator` invocation (rather than a fresh deserialization each time). If confirmed, a PoC would call `validate()` then `execute()` on a crafted `ExchangeTransactionContract` and assert that the exchange pool balances after `execute()` reflect the swap effect applied twice, and that `ret.getExchangeReceivedAmount()` does not match a quote computed from the pre-`validate()` pool state that was actually checked against `expected`.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
