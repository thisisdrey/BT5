Audit Report

## Title
`pallet-uniques::transfer_ownership` silently drops undelivered deposit on best-effort `repatriate_reserved`, permanently locking the original owner's reserved funds - (File: `substrate/frame/uniques/src/lib.rs`)

## Summary
`Pallet::transfer_ownership` calls `T::Currency::repatriate_reserved(&details.owner, &new_owner, details.total_deposit, Reserved)` and discards the `Ok(remainder)` return value, then unconditionally reassigns `details.owner = new_owner`. Since `repatriate_reserved` is documented as best-effort (moving up to `value`, returning any un-moved remainder rather than failing), a partial move leaves part of the deposit stuck under the old owner while ownership records fully transfer to the new owner, with no permission path left for the old owner to recover the residual reserve.

## Finding Description
In `transfer_ownership` at `substrate/frame/uniques/src/lib.rs` lines 886-897, the deposit move via `repatriate_reserved` is invoked with `?`, which only propagates a hard `Err`; a partial-success `Ok(non_zero_remainder)` is silently ignored. Immediately afterward, `CollectionAccount` is updated and `details.owner` is unconditionally set to `new_owner`, regardless of whether the full `total_deposit` was actually moved. This means if the old owner's reserved balance under `Reserved` status is less than `total_deposit` at call time (e.g., due to overlapping holds, partial unreserves, or other reserve-consuming operations), only part of the deposit transfers, yet ownership and all associated bookkeeping (`CollectionAccount`, `details.owner`) move entirely to the new owner. The sibling pallet `pallet-assets::transfer_ownership` was patched in exactly this way (capturing the remainder and enforcing `ensure!(remaining.is_zero(), Error::<T, I>::IncompleteDepositTransfer)`), confirming this is a recognized bug class that was fixed there but not carried over to `pallet-uniques`.

## Impact Explanation
Once ownership transfers, only the `new_owner` (or its appointed team) can invoke further owner-gated calls (`transfer_ownership`, `destroy`, etc.) on the collection. The prior owner has no permissioned path to trigger unreserve/repatriation of any residual reserved deposit tied to that collection, resulting in a permanent lock of the original owner's funds. This matches the accepted "permanent user-fund ... lock" impact class for the Polkadot SDK program, and is reachable via an unprivileged, permissionless public extrinsic (`transfer_ownership`) requiring no validator, governance, or admin privilege.

## Likelihood Explanation
The condition is reachable whenever the old owner's actually-reserved balance under `Reserved` status is less than `details.total_deposit` at call time, which can occur through interleaved holds/freezes or other reserve-consuming operations, including ones the owner could arrange themselves before calling `transfer_ownership`. No governance or admin action is required, and the exploit path is fully deterministic and repeatable given the described balance-state precondition.

## Recommendation
Mirror the fix applied to `pallet-assets::transfer_ownership`: capture the `Ok(remainder)` from `repatriate_reserved` and reject the dispatch (rolling back all storage writes) if the remainder is non-zero, e.g. introduce an `IncompleteDepositTransfer` error and add `ensure!(remaining.is_zero(), Error::<T, I>::IncompleteDepositTransfer);` immediately after the `repatriate_reserved` call in `substrate/frame/uniques/src/lib.rs`.

## Proof of Concept
1. Owner `A` creates a collection; `total_deposit = D` is reserved from `A` under `Reserved` status.
2. Before calling `transfer_ownership`, reduce `A`'s reserved balance available under `Reserved` status below `D` (e.g., via a competing reserve/slash operation affecting the same reserve bucket).
3. `B` calls `set_accept_ownership(collection)`.
4. `A` calls `Uniques::transfer_ownership(collection, B)`; `repatriate_reserved(A, B, D, Reserved)` moves only `D' < D` and returns `Ok(D - D')`, which is discarded by the `?` operator.
5. Assert: `Collection::get(collection).owner == B`, while `A` still has `D - D'` reserved for this collection with no owner-permission path to retrieve it, and `B` is recorded as responsible for a deposit it never fully received.
