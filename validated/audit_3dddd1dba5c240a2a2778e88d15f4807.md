### Title
Unvalidated ABI length field causes unbounded allocation / `OutOfMemoryError` in `ValidateMultiSign`/`BatchValidateSign` precompiles - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()` decode attacker-controlled calldata into an array of `DataWord`s and then read length fields (`bytesLen`, `sigArraySize`) directly from that untrusted data. These lengths are passed into `extractBytes()`, which calls `Arrays.copyOfRange(data, offset, offset + len)` without first verifying that `len` fits within the bounds of the actual input buffer. This is the same bug class as CVE-2023-32726 (RDLENGTH not checked against the actual response buffer before being used to size a copy): an attacker-supplied length field is trusted and used to size a buffer/copy operation without validating it against the real remaining data size.

### Finding Description
In `extractBytesArray`/`extractSigArray`: [1](#0-0) 

`len`, `bytesOffset`, and `bytesLen` are all derived from `words[...].intValueSafe()`, which reads raw 32-byte words straight from the transaction's calldata (`intValueSafe()` returns `Integer.MAX_VALUE` for out-of-range values rather than throwing). `bytesLen` is never checked against `data.length` before being handed to `extractBytes`, which performs:

```java
private static byte[] extractBytes(byte[] data, int offset, int len) {
    return Arrays.copyOfRange(data, offset, offset + len);
}
```

`Arrays.copyOfRange` allocates a new array of size `len` regardless of the source array's actual size (it zero-pads if `to > original.length`), so a single crafted length word (up to `Integer.MAX_VALUE`, i.e. ~2 GB) forces the JVM to attempt a huge allocation.

This code path is reached from: [2](#0-1) 
(`ValidateMultiSign.execute`, precompile address `0x...a`) and [3](#0-2) 
(`BatchValidateSign.doExecute`, precompile address `0x...9`).

The `isValidAbiEncoding` guard, which only activates under `VMConfig.allowTvmOsaka()`, merely checks that the overall calldata length is word-aligned and consistent with a header/item-word layout — it does **not** bound-check the individual dynamic length fields (`bytesLen`, `sigArraySize`) against the real buffer size: [4](#0-3) 

Critically, `ValidateMultiSign.execute()` has **no surrounding try/catch** for unexpected errors, unlike `BatchValidateSign.execute()`, which wraps `doExecute()` in `catch (Throwable t)`: [5](#0-4) 

An `OutOfMemoryError` (a `Throwable`, not an `Exception`) raised inside `ValidateMultiSign.execute()` will therefore propagate out of the precompile call uncaught unless some higher-level `Program`/`Runtime` layer happens to catch `Throwable`/`Error` generically — I was unable to confirm within the available context whether `Program.java` or the calling `Runtime` wraps precompile invocation in a catch-all for `Throwable`/`Error`. If it does not, the resulting `OutOfMemoryError` can destabilize or crash the node process executing the transaction.

### Impact Explanation
Any unprivileged account can broadcast a `TriggerSmartContract` transaction that calls precompile address `0x...a` (`ValidateMultiSign`) or `0x...9` (`BatchValidateSign`) with crafted calldata containing an oversized length word. This forces an attempted multi-gigabyte array allocation on every node that executes/validates the transaction, which can trigger `OutOfMemoryError`. Because `ValidateMultiSign` lacks the `catch (Throwable t)` safety net that `BatchValidateSign` has, this can escape as an uncaught `Error` during transaction execution, potentially crashing or destabilizing the node (denial of service across the network, since every full node must execute the transaction to reach consensus).

### Likelihood Explanation
High reachability: the precompiles are called via a normal signed `TriggerSmartContract`/`CREATE` transaction from any account with enough energy to cover the (attacker-controllable, low) energy cost formula (`getEnergyForData` scales only with `data.length`, not with the attacker-chosen internal length fields). No special privilege, contract deployment trust, or witness/SR role is required — a single crafted calldata is sufficient.

### Recommendation
- In `extractBytesArray` and `extractSigArray`, validate that `bytesOffset`/`bytesLen` (and the derived `offset + len`) are within `[0, data.length]` before calling `extractBytes`, and reject with `Pair.of(false/true, DATA_FALSE/EMPTY_BYTE_ARRAY)` otherwise (consistent with the existing `isValidAbiEncoding` rejection pattern).
- Extend `isValidAbiEncoding` (or add a new check) to bound every dynamically-derived offset/length against `data.length` rather than only verifying total-length alignment.
- Wrap `ValidateMultiSign.execute()` in the same defensive `catch (Throwable t)` pattern already used in `BatchValidateSign.execute()`, so unexpected `Error`s (`OutOfMemoryError`, etc.) are converted into a normal precompile failure result rather than propagating.

### Proof of Concept
Craft calldata for `validatemultisign(address,uint256,bytes32,bytes[])` where the `bytes[]` array's length-prefix word for one signature element is set to a large value (e.g. `0x7fffffff`) instead of a real byte length, while keeping the overall calldata short. When `VMConfig.allowTvmOsaka()` is disabled (pre-activation, no `isValidAbiEncoding` check at all) or even when enabled (since `isValidAbiEncoding` doesn't validate this specific field), `extractBytesArray` computes `bytesLen = 0x7fffffff` and calls `extractBytes(data, offset, 0x7fffffff)`, which attempts `Arrays.copyOfRange(data, offset, offset + 0x7fffffff)` — an attempted ~2GB allocation from a single transaction, executable by any account able to submit a `TriggerSmartContract` call to precompile address `0x...a`.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
