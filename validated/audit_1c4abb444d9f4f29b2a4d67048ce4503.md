### Title
Unbounded array-index parsing in `ValidateMultiSign`/`BatchValidateSign` precompiles can crash the TVM on malformed calldata - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts parse attacker-controlled calldata into a `DataWord[]` array and then use attacker-controlled offset/length fields taken directly from that array to index further into the same array, without validating that the computed indices stay within bounds. This is structurally the same bug class as the reported ClamAV OOXML CVE-2022-20698: an "invalid pointer read" while parsing a crafted, untrusted structured input, causing the parsing routine to crash.

### Finding Description
`PrecompiledContracts.extractBytes32Array` computes a length straight from calldata and loops without any bound check against the backing array: [1](#0-0) 

`extractBytesArray` and `extractSigArray` only validate the initial `offset` argument, but the per-item `bytesOffset`/`bytesLen` values used inside the loop (`words[offset + i + 1]`, `words[offset + bytesOffset + 1]`) are taken from attacker data and are not bounds-checked against `words.length`: [2](#0-1) 

In `ValidateMultiSign.execute`, the header word `words[3]` is used both to index `words` directly (`words[words[3].intValueSafe() / WORD_SIZE]`) and to drive `extractBytesArray`/`extractSigArray`, and this happens *before* the method's only `try/catch(Throwable)` block, which wraps solely the signature-verification loop, not the parsing/extraction step: [3](#0-2) 

The `isValidAbiEncoding` guard that would normally reject malformed-length calldata is only applied when `VMConfig.allowTvmOsaka()` is enabled: [4](#0-3) 

Test code in the repo explicitly documents that pre-activation of TIP-854, this precompile has "no outer catch," so a too-short/malformed input "raises inside the decoder" as "the existing behaviour": [5](#0-4) 

By contrast, `BatchValidateSign.execute` wraps its entire `doExecute` in a top-level `try { } catch (Throwable t)`, converting any parsing exception into a normal `DATA_FALSE` return instead of propagating it: [6](#0-5) 

`ValidateMultiSign.execute` has no equivalent outer guard around the parsing/extraction path, so an uncaught `ArrayIndexOutOfBoundsException` (or `NegativeArraySizeException` from an attacker-supplied negative/huge length) raised in `extractBytes32Array`/`extractBytesArray`/`extractSigArray` or the direct `words[...]` indexing at line 1067 will propagate out of `execute()`.

### Impact Explanation
Whether this is exploitable to actually crash a node depends on whether the caller of `PrecompiledContract.execute()` (i.e., `Program.callToPrecompiledAddress` in the TVM interpreter) unconditionally catches `Throwable`/`RuntimeException` for all precompile invocations, or whether that containment was added only as part of the TIP-854 activation logic gated by `VMConfig.allowTvmOsaka()`. The test comments strongly suggest the latter for the pre-activation code path: "this precompile has no outer catch" is stated as a currently-accepted, documented behavior. If the general VM dispatch loop (`Program`/`VMActuator`) does not have an unconditional top-level catch around precompile execution for all transaction processing paths, then a crafted `TriggerSmartContract` transaction (an unprivileged, broadcastable transaction any account can send) that calls the `ValidateMultiSign` precompiled address with malformed calldata could throw an uncaught exception during block/transaction application, which is a node crash/DoS class finding, directly analogous to the ClamAV OOXML CVE.

### Likelihood Explanation
Reaching this code requires only a single `TriggerSmartContract` transaction that performs a `CALL`/`STATICCALL` to the `ValidateMultiSign` (or `BatchValidateSign`, before its self-contained catch was added — noting `BatchValidateSign` already has a catch) precompiled contract address with a small, malformed calldata buffer, which is fully within reach of an unprivileged contract caller. This requires no special permissions, keys, or SR/witness status.

### Recommendation
Add explicit bounds validation for all attacker-derived offsets/lengths before indexing into `words` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` (matching the existing `offset > words.length - 1` style guard, but also checking `offset + i + 1` and `offset + bytesOffset + 1` against `words.length` on every loop iteration), and wrap the entirety of `ValidateMultiSign.execute` (not just the signature-verification loop) in the same defensive `try/catch(Throwable)` pattern already used in `BatchValidateSign.execute`, independent of the `VMConfig.allowTvmOsaka()` feature flag.

### Proof of Concept
I could not fully confirm end-to-end node-crash impact because I was unable to inspect `Program.callToPrecompiledAddress` and `VMActuator`'s exception handling in enough depth within the available searches to determine whether a top-level catch exists for all code paths (only test-file references were found, not the full method bodies). Conceptually, the PoC would be: construct calldata for `ValidateMultiSign` where the ABI word at index 3 (`words[3]`) is set to a very large or negative value such that `words[3].intValueSafe() / WORD_SIZE` produces an out-of-range index into the `words` array, then submit this as the `data` field of a `TriggerSmartContract` transaction calling the `ValidateMultiSign` precompiled address (`0x0...09` per TVM precompile numbering) with `VMConfig.allowTvmOsaka()` disabled (pre-activation network state), and observe whether the resulting `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` propagates uncaught through transaction execution.

**Note on confidence**: Because I ran out of tool-call budget before reading `Program.callToPrecompiledAddress` and `VMActuator` in full, I cannot definitively confirm whether an uncaught exception here actually escapes to crash node processing versus being caught generically elsewhere in the VM/transaction-execution stack. This is a plausible, code-supported analog to the CVE's bug class (parser crash on malformed structured input reachable from an untrusted party), but the ultimate DoS impact needs verification against the full precompile-dispatch exception-handling code before treating it as fully confirmed.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
