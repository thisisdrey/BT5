Audit Report

## Title
`ERC20Transactor` credits the XCM holding register with the requested amount instead of the amount actually moved by the ERC20 contract, allowing unbacked value creation from non-standard ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` move ERC20 tokens into/out of the XCM holding register by calling `IERC20::transfer` and trusting only its boolean return value, without verifying the actual balance delta of the checking account or beneficiary. Because any contract whose location matches `(0, [AccountKey20 {..}])` is accepted by `ERC20Matcher` with no allow-listing, an attacker-deployed non-standard ERC20 (fee-on-transfer, rebasing, etc.) that returns `true` while moving a different amount than requested can cause the XCM executor to credit/propagate a nominal `amount` not backed by the real balance movement.

## Finding Description
`withdraw_asset_with_surplus` calls `IERC20::transferCall` to move `amount` from the user to `TransfersCheckingAccount`, and on a decoded `is_success == true` unconditionally credits `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` [1](#0-0) . `deposit_asset_with_surplus` mirrors this for the outbound transfer from the checking account to the beneficiary, treating a decoded `Ok(true)` as full success without checking the beneficiary's balance delta [2](#0-1) . Neither function reads `balanceOf` before/after the transfer — there is no such call anywhere in the file [3](#0-2) .

`Erc20Credit` is explicitly documented as a self-declared imbalance type with no runtime-level balance enforcement, relying entirely on the ERC20 contract's own accounting [4](#0-3) .

Critically, `ERC20Matcher` performs no allow-listing: it is defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>` [5](#0-4) , and `IsLocalAccountKey20::contains` matches *any* location of the shape `(0, [AccountKey20 {..}])` [6](#0-5) . Since `pallet-revive` allows anyone to permissionlessly deploy a contract at an arbitrary address, any user-deployed contract's address qualifies as a valid XCM asset id for this transactor — unlike the sibling `FungiblesTransactor`, which requires `NonZeroIssuance` as an allow-list proxy [7](#0-6) . `ERC20Transactor` is wired into the production `AssetTransactors` tuple for Asset Hub Westend [8](#0-7) .

## Impact Explanation
An attacker can deploy a non-standard ERC20 contract (fee-on-transfer, deflationary, or otherwise manipulated `transfer()` logic) that returns `true` while moving an amount different from `value`. Using this contract's address as the XCM asset id through `withdraw_asset_with_surplus`/`deposit_asset_with_surplus`, the executor's holding register is credited/debited by the nominal requested `amount` rather than the real balance change in `TransfersCheckingAccount` or the beneficiary. Subsequent XCM instructions (`DepositAsset`, teleport, reserve transfer) then propagate this nominal, unbacked amount — matching the "theft or unbacked mint or unlock" impact category, since holding-register value is created that is not fully backed by tokens actually locked in the checking account.

## Likelihood Explanation
The exploit requires only an unprivileged attacker who can (1) deploy an arbitrary contract via `pallet-revive` and (2) submit an XCM message/execute call using that contract's address as the asset. `ERC20Matcher`/`IsLocalAccountKey20` confirm there is no allow-listing gate — any `AccountKey20` location is matched, so any freshly deployed contract qualifies immediately, with no registration step analogous to `pallet-assets`. This makes the attack fully self-contained and repeatable without relayer, validator, or governance involvement.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, query `balanceOf` of the relevant account (checking account or beneficiary) before and after the `transfer()` call, and only credit/return the actual observed delta, erroring if the delta does not equal the requested `amount`.

## Proof of Concept
1. Deploy a fee-on-transfer ERC20-like contract via `pallet-revive` whose `transfer()` deducts `amount` from the sender but credits the recipient with `amount - fee`, while still returning `true`.
2. Submit an XCM message that `WithdrawAsset`s this contract's token via `ERC20Transactor::withdraw_asset_with_surplus`.
3. Because `is_success` is the only check performed (`erc20_transactor.rs` lines 191–203), the holding register is credited with the full nominal `amount` even though `TransfersCheckingAccount` only received `amount - fee`.
4. A subsequent `DepositAsset`/teleport step propagates the full nominal amount to a destination, creating value not backed by the real locked balance.
