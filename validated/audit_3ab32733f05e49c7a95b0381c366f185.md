### Title
OOB read in `InputZipFile::ProcessCentralDirEntry`'s extra-field TLV loop when processing an attacker-supplied JAR - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar` is Bazel's C++ tool used to build interface jars for Java targets (`java_common.run_ijar`, `java_import`, `stamp_jar`) [1](#0-0) . It memory-maps and parses the ZIP central directory of the input jar, which can be a jar downloaded from an untrusted HTTP mirror/registry (e.g. via `http_jar`/`http_archive`/Maven coordinates) that a victim's build consumes as a dependency [2](#0-1) . `InputZipFile::ProcessCentralDirEntry` reads the extra-field length from the untrusted file and then walks a TLV loop over the extra fields without ever validating individual entries against the parsed buffer boundary, mirroring the rtl8723bs `update_beacon_info()` IE-loop OOB-read pattern (advance by attacker-declared length with insufficient bound checks).

### Finding Description
`ProcessCentralDirEntry` reads `extra_field_length` directly from the mmap'd, attacker-controlled jar and computes the end pointer `p = p + extra_field_length` (also attacker-controlled, unchecked against the actual mapped file size beyond a coarse signature check) [3](#0-2) . It then loops:

```cpp
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
``` [4](#0-3) 

Unlike `InputZipFile::ProcessLocalFileEntry`, which calls `EnsureRemaining()` before consuming `file_name_length_`/`extra_field_length_` bytes [5](#0-4) , `ProcessCentralDirEntry` has **no bounds check at all**: not on the header read (`get_u2le`/`get_u4le` reading beyond the mapped file), not on `data_size` extending `extra_p` past the declared extra-field end `p`, and not verifying that `extra_p` even stays within the mapped input file (`zipdata_in_` .. `zipdata_in_ + input_file_->Length()`). The loop's exit condition `extra_p != p` only detects exact equality; if a crafted `data_size` causes `extra_p` to overshoot `p`, the loop keeps iterating and dereferencing `get_u2le(extra_p)`/`get_u8le(extra)` further and further past the mapped region, exactly analogous to the kernel bug where `i += (pIE->length + 2)` advanced past `len` without a bound check. The code comment "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" is an assumption that does not hold for a maliciously crafted extra-field length, since nothing forces `extra_field_length` to be consistent with the recorded name/comment lengths or the file size.

### Impact Explanation
A hostile jar (served from an attacker-controlled or compromised URL/mirror that a victim's `http_jar`/`http_archive`/Maven dependency resolves to) can craft a central directory entry with an oversized/inconsistent `extra_field_length` and `data_size` fields to make `ijar` read memory beyond the mmap'd input file. This is a high-confidence out-of-bounds read that can crash the `ijar` action (denial of build) or leak adjacent process memory content into `ijar`'s decision-making (e.g., into the zip64 size/offset fields it trusts, `*uncompressed_size = get_u8le(extra)`), potentially corrupting the produced interface jar with attacker-influenced values derived from out-of-bounds memory.

### Likelihood Explanation
Every project that builds Java targets depending on third-party jars runs `ijar` on those jars by default (interface jar generation is on by default for `java_library`/`java_import` deps). An attacker who controls the content served at a jar's download URL (with a compromised mirror, or where sha256 pinning is absent/mismatched but still fetched) can trivially embed a malformed extra field in the central directory of an otherwise valid-looking zip, requiring no privileged access to the victim's machine.

### Recommendation
Add explicit bounds checks in `InputZipFile::ProcessCentralDirEntry`, mirroring `EnsureRemaining()`/`ExtraField::find()`'s safe pattern used elsewhere in the codebase (e.g. `src/tools/singlejar/zip_headers.h`'s `ExtraField::find`, which checks `start + sizeof(ExtraField) > end` and `start + extra_field->size() > end` before dereferencing) [6](#0-5) :
1. Validate `file_name_length`, `extra_field_length`, and `file_comment_length` against `input_file_->Length()`/remaining central directory bytes before advancing `p`.
2. Inside the extra-field loop, break/error if fewer than 4 bytes remain before reading `header_id`/`data_size`, and break/error if `extra_p + data_size` would exceed `p` (the declared extra-field end) or the mapped file end.

### Proof of Concept
A `BuildIntegrationTestCase`/`third_party/ijar/test` style reproduction:
1. Construct a minimal valid ZIP/jar with one central directory entry.
2. Set `extra_field_length` in that CDH entry to a small value (e.g. 4), but craft the 4 bytes so that `data_size` (bytes 3-4) is a large value (e.g. `0xF000`), similar to the existing malformed-extra-field regression test for singlejar's LH parsing (`CreateZipWithMalformedExtraField` in `output_jar_simple_test.cc`) [7](#0-6) , but placed in the ijar central-directory extra field instead (which lacks the equivalent guard).
3. Place this crafted jar at the end of the mmap'd region (small file) so that `extra_p += data_size` walks well past `zipdata_in_ + input_file_->Length()`.
4. Run `ijar <crafted.jar> out.jar` (or trigger via `java_import`/`run_ijar`) under ASan; observe a heap-buffer-overflow (read) report inside `InputZipFile::ProcessCentralDirEntry`.
