### Title
Unhardened Bancor-curve `Exchange` calculation can leave a pool reserve unvalidated and negative when `allowHardenExchangeCalculation()` is off, freezing withdrawals for later traders - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeTransactionActuator`/`ExchangeWithdrawActuator` let any signed account trade against a TRX↔TRC10 "Exchange" bonding-curve pool via `ExchangeCapsule.transaction()`. When the `allowHardenExchangeCalculation` hard-fork flag is off (the legacy path, selected by `hardenedCalc=false`), the reserve-balance update is applied with **no bounds check**, while the hardened path explicitly guards against a negative-reserve outcome: [1](#0-0) 
This mirrors the reported bug class: asymmetric/imprecise price computation lets a participant extract more than the pool can back, so the reserve for one token can be driven negative and persisted, after which subsequent (including the "last") holders of that token cannot redeem their share because the pool balance no longer backs it.

### Finding Description
`ExchangeCapsule.transaction()` selects between two `Processor` implementations depending on the `hardenedCalc` flag (itself gated by `dynamicStore.allowHardenExchangeCalculation()`, read via `allowHarden()` in `AbstractExchangeActuator`): [2](#0-1) 

- The legacy `ExchangeProcessor` computes the Bancor-style relay/output amounts entirely with `double` arithmetic and truncates with a raw `(long)` cast, with **no protection against floating-point overshoot**: [3](#0-2) 
- The hardened `SafeExchangeProcessor` performs the same math with `BigDecimal`, and critically, `ExchangeCapsule.transaction()` only checks for a negative resulting reserve **when `hardenedCalc` is true**: [4](#0-3) 

Because the guard `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0))` is short-circuited by `hardenedCalc`, on chains/points in time where the harden fork has not activated, a trade that causes `exchangeFromSupply()` to (due to `double` precision loss near the edges of the curve, e.g. selling a very large fraction of one side of the pool) return an amount greater than the actual reserve will still be accepted and persisted: [5](#0-4) 
The actuator then unconditionally credits the trader with `anotherTokenQuant` and commits the (now negative) `ExchangeCapsule`: [6](#0-5) 
`ExchangeWithdrawActuator`'s own validation only enforces `firstTokenBalance < tokenQuant || secondTokenBalance < anotherTokenQuant` at withdraw time — it does not prevent the underlying `transaction()` result from itself under/over-counting due to legacy-path floating-point error: [7](#0-6) 

This is the same root cause pattern as the external report: an unvalidated/asymmetric price computation (here, unguarded floating-point Bancor math on the legacy path) lets one trade extract more value than the reserve holds, so once the reserve is corrupted, later participants who try to redeem their share of that same reserve cannot get paid (their sell/withdraw reverts or their computed share becomes wrong/unbacked).

### Impact Explanation
If a trade on the legacy (non-hardened) path causes `exchangeFromSupply`/`exchangeToSupply` `double` rounding to overshoot the true reserve, `ExchangeCapsule.transaction()` silently stores a negative token balance for the exchange. Later:
- Other participants trying to trade against or withdraw from that pool receive incorrect/undersized amounts, or their transactions fail because the store no longer has enough real reserve to back the recorded balance — an unbacked-balance / permanent freezing-of-funds condition for exchange participants, matching the "last user can't sell" impact class from the report.
- Since `ExchangeCapsule` state is chain-consensus state, this corruption is also permanently recorded on-chain once committed.

### Likelihood Explanation
Reachable by any account with an existing TRC10/TRX `Exchange` pool and enough balance to submit `ExchangeTransactionContract`/`ExchangeWithdrawContract` transactions — no special privilege required. The trigger condition (extreme ratios or repeated small/large trades pushing `double` precision to its edge) is a normal usage pattern of an AMM-style pool, so it is plausible under sustained/adversarial trading, though it requires the harden flag to be inactive and specific numeric conditions to manifest the overshoot, which I could not fully reproduce/prove numerically within this review — this should be validated with targeted fuzzing/PoC by a background engineer.

### Recommendation
Make the negative-reserve check unconditional (i.e., remove the `hardenedCalc &&` guard) so both processors reject any trade that would drive `newFirstTokenBalance` or `newSecondTokenBalance` below zero, or retire the legacy `ExchangeProcessor` entirely in favor of the `BigDecimal`-based `SafeExchangeProcessor` for all trades regardless of the hard-fork flag.

### Proof of Concept
Not independently reproduced. Suggested approach for the engineering team: construct an `ExchangeCapsule` with `allowHardenExchangeCalculation()` disabled, set extreme/edge-case reserve ratios (e.g., very small `buyTokenBalance` relative to `sellTokenBalance`, or `sellTokenQuant` close to the full reserve), invoke `ExchangeTransactionActuator.execute()` repeatedly, and assert whether `ExchangeCapsule.getFirstTokenBalance()`/`getSecondTokenBalance()` can go negative — analogous to the existing `SafeExchangeProcessor` test `testHardenedOverflowDetection`/`testSafeProcessorNoOvershootForTypicalInputs`, but run against the **legacy** `ExchangeProcessor` path without the hardened guard, per `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java` and `framework/src/test/java/org/tron/core/capsule/utils/ExchangeProcessorTest.java`.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
