Found the analog. `ValidateMultiSign.execute` in `PrecompiledContracts.java` reads attacker-controlled length/offset words from the raw precompile input and uses them directly to index into the `words` array and to size/copy byte arrays, mirroring the kernel bug class of trusting a length field from an untrusted structure before it is used in a copy operation.

### Title
Missing bounds validation of attacker-controlled offset/length words in `ValidateMultiSign` precompile leads to out-of-bounds array access - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`ValidateMultiSign.execute(byte[] rawData)` parses the raw call data of the TVM precompiled contract at address used for multi-sig validation. It reads `words[3]` (a byte offset into the ABI-encoded blob), converts it to a word index (`words[3].intValueSafe() / WORD_SIZE`), and immediately uses that index to read `words[offset]` inside `extractSigArray`/`extractBytesArray`, and further to read `words[offset + i + 1]` in a loop, without first checking that `offset` (or `offset + count`) is within the bounds of the `words` array produced by `DataWord.parseArray(rawData)`. This is directly analogous to the CVE class described in the report: a length/offset value sourced from an untrusted structure is used to drive a copy/array-index operation without validating it against the actual buffer size.

### Finding Description
`ValidateMultiSign.execute` is reachable by any account issuing a `TriggerSmartContract` that performs a `CALL`/`STATICCALL` to the multi-sign validation precompiled address (this precompile is dispatched by `PrecompiledContracts.getContractForAddress` and invoked from `Program.callToPrecompiledAddress`, see [1](#0-0) ).

`words[3]` is fully attacker controlled (part of the ABI-encoded call data) and is only checked for a size cap (`MAX_SIZE`) on the *value read at that offset*, not on whether `words[3]/WORD_SIZE` itself is a valid index into `words`. There is also no check that `words.length` is at least 4 before `words[3]` is accessed, nor that `words` has enough elements for `words[offset]`, `words[offset + i + 1]` used inside `extractBytesArray`/`extractSigArray`/`extractBytes32Array`:
```

The `offset > words.length - 1` guard only protects the *first* read (`words[offset]`), not the subsequent per-item reads `words[offset + i + 1]` for `i` up to `len - 1`. `len` itself is fully attacker-controlled via `words[offset].intValueSafe()`, so a crafted call data can pass the `sigArraySize > MAX_SIZE` guard used only when `VMConfig.allowTvmSelfdestructRestriction()` is enabled — but the non-restricted branch (`extractBytesArray`) has no such pre-check on `len` at all before allocating `new byte[len][]` and looping `words[offset + i + 1]`, and `extractSigArray` similarly loops `words[offset + i + 1]` for `i` in `[0, len)` with only the single upfront bound check on `offset`:
```
private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  for (int i = 0; i < len; i++) {
    int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
    bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, SIG_LENGTH);
  }
``` [4](#0-3) 

A caller can supply a large `len` (up to `Integer.MAX_VALUE`) combined with a small `words.length`, causing `words[offset + i + 1]` to throw `ArrayIndexOutOfBoundsException` once `offset + i + 1 >= words.length`, or supply a large `len` alone to force allocation of an oversized `byte[len][]`/`byte[0][]` triggering `OutOfMemoryError`/`NegativeArraySizeException` depending on sign. `extractBytes` further calls `Arrays.copyOfRange(data, offset, offset + len)` with an attacker-influenced `offset` computed from `bytesOffset`, which can itself throw `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` on `rawData` if it exceeds bounds:
```
private static byte[] extractBytes(byte[] data, int offset, int len) {
  return Arrays.copyOfRange(data, offset, offset + len);
}
``` [5](#0-4) 

### Impact Explanation
`PrecompiledContract.execute` is invoked from `Program.callToPrecompiledAddress`, and while a thrown exception there is intercepted only for `Program.Exception` type through `result.getException()` handling; unchecked runtime exceptions such as `ArrayIndexOutOfBoundsException`, `NegativeArraySizeException`, or `OutOfMemoryError` originating from `contract.execute(data)` propagate up through the TVM execution stack. Depending on how the outer actuator/transaction executor handles arbitrary `RuntimeException`/`Error` versus the expected `ContractExeException`/`Program.Exception` hierarchy, this can crash transaction processing for the node applying the block (potential node halt / DoS) or, in the case of `OutOfMemoryError` from a huge `new byte[len][]` allocation, degrade or crash the whole JVM process serving the node. This is reachable by any unprivileged account issuing a `TriggerSmartContractContract` transaction that calls the multi-sign validation precompiled address with crafted ABI data — no special permission, stake, or witness role required.

### Likelihood Explanation
High. The precompile is called directly by ordinary contract-calling transactions; the attacker fully controls `rawData` (and thus `words[3]`, the derived `offset`, and the `len` value at `words[offset]`). No additional preconditions (permissions, balances, prior state) are required beyond issuing a smart-contract call transaction with sufficient energy to reach the precompile.

### Recommendation
In `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, validate that `offset + len` (and each per-item derived index/offset such as `bytesOffset + offset + 2`, and the `extractBytes` `offset`/`offset+len` range against `data.length`) stays within the bounds of `words`/`data` before allocating or indexing, returning an empty/failure result instead of allocating unbounded arrays or indexing past the array length. Additionally cap `len` to `MAX_SIZE` (or a similarly small sane bound) immediately after reading `words[offset]` in both `extractBytesArray` and `extractSigArray`, mirroring the existing `sigArraySize > MAX_SIZE` check that currently only applies under the `allowTvmSelfdestructRestriction` feature flag.

### Proof of Concept
1. Craft a `TriggerSmartContractContract` transaction whose target contract calls the multi-sign validation precompiled address (the fixed precompile address handling `ValidateMultiSign`) via `CALL`.
2. Construct `rawData` such that:
   - `words[0]`, `words[1]`, `words[2]` are arbitrary valid placeholders (address/permissionId/data).
   - `words[3]` encodes a byte offset that resolves to a word index `offset` near the end of the (short) `words` array.
   - The value at `words[offset]` (`len`) is set to a large positive integer, e.g. `0x7fffffff`.
3. Submit the transaction (no `allowTvmSelfdestructRestriction` sig-count pre-check triggers when the flag is disabled, or set `offset` so the pre-check for `sigArraySize` itself indexes past `words.length`).
4. `extractBytesArray`/`extractSigArray` executes `words[offset + i + 1]` for increasing `i`, exceeding `words.length` and throwing `ArrayIndexOutOfBoundsException`, or attempts `new byte[len][]` with `len = 0x7fffffff`, throwing `OutOfMemoryError`, during transaction execution on the validating/applying node.
