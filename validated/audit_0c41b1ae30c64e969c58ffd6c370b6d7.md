### Title
Unsolicited `StackerDBPushChunk` inventory reply advertises a chunk version before it is actually committed to the local StackerDB - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary

### Finding Description
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates a pushed chunk with `validate_received_chunk`, and — on success — immediately patches the in-memory `StackerDBChunkInvData.slot_versions` entry to the pushed chunk's `slot_version` and sends that patched inventory back to the peer as the reply, while simultaneously signalling that the chunk should be forwarded to the relayer for actual storage (`Ok((false, true))`): [1](#0-0) [2](#0-1) 

The actual persistence of the chunk happens later, out-of-band, in the relay thread via `process_stacker_db_chunks`, which calls `try_replace_chunk` against the live DB state at that later point in time: [3](#0-2) 

`try_replace_chunk` independently re-checks slot ownership, staleness (`slot_version <= slot_validation.version`), and `max_writes`, and only inserts the row if all checks pass: [4](#0-3) 

Because the inventory-patch-and-reply happens in the P2P conversation thread at time T1, based on the `slot_versions` snapshot fetched via `get_stacker_db_configs`/`make_StackerDBChunksInv_or_Nack` at that moment, while the durable write happens later at T2 in the relay thread against whatever the DB's live state is *then*, there is a window in which:
- another peer's chunk for the same slot with an equal-or-higher `slot_version` can be committed first by the relay thread, causing `try_replace_chunk` to return `Error::StaleChunk` for the chunk that was already advertised as accepted, or
- the relay's `try_replace_chunk` call can otherwise fail (e.g. `TooManySlotWrites`, `BadSlotSigner` from a slot-ownership change), in which case `process_stacker_db_chunks` simply logs and `continue`s without storing the chunk: [5](#0-4) 

In either case, the node has already told the requesting peer (via the `StackerDBChunkInv` reply) that it now holds `slot_version` for that slot, but the chunk was never actually written to the local StackerDB. This breaks the "served vs. committed" invariant that the StackerDB module's own design doc describes — `StackerDBChunkInvData` is supposed to reflect what a node *has* replicated, and neighbors use it to decide what to fetch and from whom (rarest/newest-first scheduling): [6](#0-5) 

### Impact Explanation
A remote, unauthenticated peer can trigger this mismatch simply by racing two `StackerDBPushChunk` messages for the same slot (from itself and/or an accomplice) against a victim node. Any neighbor of the victim that subsequently queries the victim's inventory, sees the falsely-advertised (higher) `slot_version`, and treats the victim as already having that data may under-prioritize re-fetching that chunk from other, genuinely up-to-date replicas, or may issue a `StackerDBGetChunk` to the victim and receive a stale-version NACK. This matches the "steering a node off the tip via false inventory" pattern called out as an in-scope High-impact class, since it can misdirect a StackerDB sync scheduler's download decisions across the network for signer/miner message replication built on StackerDB.

### Likelihood Explanation
Triggering the race only requires an attacker (or two colluding low-cost identities) sending ordinary, validly-signed `StackerDBPushChunk` messages for the same slot in quick succession — no privileged key, no consensus interaction, and no large traffic volume is needed, just correct timing relative to the victim's relay-thread processing loop. The bug is inherent to the split between "validate + patch inventory + reply" (synchronous, in the P2P conversation handler) and "commit to DB" (asynchronous, in the relay thread), so it is reliably reachable, though the exact window size depends on relay-loop scheduling.

### Recommendation
Do not patch/return the advertised `slot_version` in the `StackerDBChunkInv` reply until the chunk has actually been durably stored (i.e., move the inventory-patch logic to occur only after `try_replace_chunk` succeeds in the relayer, or have `handle_unsolicited_StackerDBPushChunk` perform the store itself before composing the reply, re-validating with the up-to-date `slot_validation` state under the same lock/transaction used for the write).

### Proof of Concept
1. Attacker controls (or colludes with) two peers, A and B, both eligible signers for the same StackerDB slot `S` in contract `C` (or one attacker key reused for consecutive pushes to its own owned slot).
2. Peer A sends `StackerDBPushChunk{contract_id: C, chunk_data: {slot_id: S, slot_version: 5, sig: valid}}` to victim node V.
3. `handle_unsolicited_StackerDBPushChunk` on V validates A's chunk against the current stored version (say version 3), patches the in-memory `slot_versions[S] = 5`, and immediately replies to A with a `StackerDBChunkInv` claiming version 5 is present, returning `(false, true)` to forward the chunk to the relay thread for storage. [7](#0-6) 
4. Before the relay thread actually calls `try_replace_chunk` for A's chunk, peer B sends its own validly-signed chunk for slot `S` with `slot_version: 6`, which the relay thread commits first (`try_replace_chunk` succeeds, current version becomes 6).
5. When the relay thread later processes A's buffered/forwarded chunk (`slot_version: 5`), `try_replace_chunk` returns `Error::StaleChunk` (5 <= 6), so A's chunk is dropped (`continue` in `process_stacker_db_chunks`): [8](#0-7) 
6. V's DB now actually holds version 6, not 5 — yet the reply already sent to A in step 3 (before the collision was even possible) advertised "I now have version 5", and any third peer that queried V's inventory in that same window would have observed the false "version 5 present" state even though it was never committed under that exact chunk/signature. Because inventory replies are computed purely from the pre-store patch rather than the post-commit DB state, a neighbor relying on that inventory snapshot can be misled about which chunk bytes V actually possesses for slot `S`, independent of whether V's version counter later moves higher via a different chunk.

        if (chunk.len() as u64) > self.config.chunk_size {
