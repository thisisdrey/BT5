### Title
Replay window bypass via unlocked Check/Decrypt/Update race in `ConnectionState.Decrypt` and `VerifyRelay` - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement anti-replay protection using a sliding-bitmap window (`Bits`) with a separate `Check()` (pre-decrypt) and `Update()` (post-decrypt) call. These two calls are protected individually by `decryptLock`, but the lock is **released between `Check` and `Update`**, and AEAD decryption itself happens outside the lock [1](#0-0) . This mirrors the reported bug class: two accounting operations that are supposed to jointly enforce a single invariant ("this message counter has been consumed exactly once") are not reconciled atomically, so a duplicate/split submission of the same counter can slip through both checks before the tally (the replay bitmap) is updated.

### Finding Description
The replay window abstraction (`Bits`) is deliberately structured as a two-phase check: `Check(i)` (read-only, "is `i` still unseen") and `Update(i)` (write, "mark `i` seen") [2](#0-1) [3](#0-2) . `ConnectionState.Decrypt` calls `Check` under `decryptLock`, releases the lock, performs the actual AEAD decrypt (`DecryptDanger`, which does not touch or reserve the counter), then re-acquires `decryptLock` to call `Update`:

```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
if !result {
    return nil, ErrAlreadySeen
}

out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)
cs.decryptLock.Unlock()
``` [1](#0-0) 

The identical pattern exists for relay traffic in `VerifyRelay` [4](#0-3) .

Nebula supports multiple concurrent UDP-reader goroutines (`listen.routines` / `SO_REUSEPORT`), each independently invoking `readOutsidePackets` → `handleOutsideMessagePacket` for inbound datagrams that hash to different queues [5](#0-4) [6](#0-5) [7](#0-6) . If an attacker (who does not hold a valid CA-signed certificate and therefore cannot forge new traffic, but can duplicate/replay a previously observed on-wire ciphertext) sends the exact same encrypted packet twice in quick succession, the two copies can be picked up by two different reader routines and processed concurrently. Both goroutines can execute `Check(messageCounter)` before either has executed `Update(messageCounter)`, because the lock is dropped in between. Both `Check` calls will return `true` (not yet marked seen), both will successfully decrypt (decryption is deterministic and does not consume the window state), and both plaintexts will be delivered — once each — to the tun interface or to the relay-forward path. This defeats the entire purpose of the anti-replay window: the two counters ("has been checked" vs "has been recorded") are never reconciled atomically, exactly analogous to the reported bug where two separately-incremented "no action" tallies were never reconciled against each other.

This is a regression-prone area: the CHANGELOG for this codebase already documents two closely related, previously-fixed defects — "Advance the replay window on relayed packets so a relay drops replayed frames instead of re-forwarding them" and "Lock replay window updates so concurrent readers can't corrupt it" [8](#0-7)  — confirming that replay-window concurrency/consistency in exactly this code path is a recognized, real class of vulnerability, and that the check-then-update pattern was not made atomic even after those fixes.

### Impact Explanation
An attacker positioned to observe and duplicate on-wire UDP datagrams (a standard network MITM/duplication capability, not requiring any CA-signed certificate or the ability to complete a handshake) can cause a single legitimately-encrypted data-plane packet to be delivered twice to the receiving tun device, or a single relay frame to be forwarded twice by a relay node. This is a concrete traffic-replay vulnerability: the anti-replay guarantee `Bits`/`ConnectionState` is designed to provide is bypassed for packets racing across the `Check`→decrypt→`Update` window. Depending on the encapsulated payload, duplicate delivery can cause application-level replay effects (e.g., duplicate execution of a command carried in the tunnel, or resource exhaustion via repeated forwarding through a relay).

### Likelihood Explanation
Exploitation requires: (1) capturing one legitimate ciphertext packet on the wire (feasible for any on-path attacker, and explicitly exercised as a capability in the project's own relay-replay test) [9](#0-8) , and (2) causing two copies of it to be processed concurrently by different reader goroutines, which requires a multi-routine (`listen.routines > 1`) deployment — a supported and documented configuration, not an edge case. The race window (time between `Check`'s unlock and `Update`'s lock, spanning a full AEAD decrypt) is generally small but nonzero, and under network conditions where duplicate packets naturally arrive close together (or are intentionally sent close together by an attacker), the race is realistically triggerable, especially against a busy node under load where scheduling delays widen the window.

### Recommendation
Make the "is this counter already used" check and "mark this counter used" tally update atomic with respect to each other — i.e., hold `decryptLock` (or an equivalent single critical section) across the entire `Check` + decrypt-authentication + `Update` sequence, or use a single atomic `CheckAndReserve`-style operation on `Bits` that immediately marks the counter as provisionally consumed before decryption begins (rolling back only on authentication failure). This removes the TOCTOU window instead of relying on two separately-locked calls to reconcile the same piece of state, mirroring the root-cause fix recommended in the reference report: don't split a single tally invariant across multiple, unsynchronized bookkeeping operations.

### Proof of Concept
1. Establish two Nebula nodes with `listen.routines` set to more than 1 (multi-queue UDP, e.g. Linux with `SO_REUSEPORT`), matching `e2e/tunnels_test.go`'s relay-replay harness style setup.
2. Have node A send one data-plane (or relay) packet to node B; capture the raw ciphertext datagram as it leaves A (as done in `TestRelayReplayProtection`) [10](#0-9) .
3. Inject the captured datagram at B twice, back-to-back with minimal delay, timed so they are dispatched to two different reader goroutines/queues.
4. Observe whether B's tun device (or, for a relay node, the relay-forward path) delivers/forwards the payload twice instead of the expected single delivery plus a rejected duplicate — demonstrating that `Check`/`Update` on `cs.window` raced instead of serializing.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (f *Interface) listenOut(i int) {
	var li udp.Conn
	if i > 0 {
		li = f.writers[i]
	} else {
		li = f.outside
	}

	ctCache := firewall.NewConntrackCacheTicker(f.ctx, f.l, f.conntrackCacheTimeout)
	lhh := f.lightHouse.NewRequestHandler()
	plaintext := make([]byte, udp.MTU)
	h := &header.H{}
	fwPacket := &firewall.Packet{}
	nb := make([]byte, 12, 12)

	err := li.ListenOut(func(fromUdpAddr netip.AddrPort, payload []byte) {
		f.readOutsidePackets(ViaSender{UdpAddr: fromUdpAddr}, plaintext[:0], payload, h, fwPacket, lhh, nb, i, ctCache.Get())
	})

	// An error after teardown began is shutdown noise, the closed flag covers resources
	// Close releases itself and the cancelled ctx covers ones torn down by their owners
	// reacting to it, like the user device pipes
	if err != nil && !f.closed.Load() && f.ctx.Err() == nil {
		f.l.Error("Error while reading inbound packet, closing", "error", err)
		f.onFatal(err)
	}

	f.l.Debug("underlay reader is done", "reader", i)
}
