### Title
Floating-point Bancor-formula exchange math in `ExchangeProcessor` enables rounding-bias drain of on-chain TRX/TRC10 Exchange pools - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The BGM incident on BSC was a classic AMM price-manipulation attack: an attacker manipulated a low-liquidity pool's price through swaps, exploiting the pool's math to extract value that should not have been extractable. java-tron ships a very similar constant-relay ("Bancor formula") AMM primitive — the on-chain `Exchange`/`ExchangeV2` — that anyone can create and trade against via `ExchangeTransactionContract`. Unless the `allowHardenExchangeCalculation` dynamic parameter has been activated network-wide, all trades are still executed through the legacy `ExchangeProcessor`, which relies on `double`-precision floating point (`Math.pow`) instead of exact `BigDecimal` arithmetic [1](#0-0) . Floating point rounding in this formula is not guaranteed to be conservative in the pool's favor, so an attacker can repeatedly trade tiny, carefully chosen amounts to accumulate a systematic rounding advantage and drain the counter-token reserve of any exchange pool they can reach.

### Finding Description
`ExchangeCapsule.transaction()` selects between the legacy `ExchangeProcessor` (double-precision) and the newer `SafeExchangeProcessor` (BigDecimal, exact) purely based on the `hardenedCalc` flag, which is derived from the `allowHardenExchangeCalculation` dynamic property [2](#0-1) . The legacy path (`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`) performs the Bancor relay computation with `double` math and `Math.pow`, converting to `long` via truncation [3](#0-2) . Unlike the hardened `SafeExchangeProcessor`, which uses `BigDecimal` with 18-digit precision and explicit `RoundingMode` control [4](#0-3) , the legacy processor's floating-point `pow` computation can produce results that are not monotonically consistent with the true Bancor curve, allowing rounding to occasionally favor the trader instead of the pool.

`ExchangeTransactionActuator` invokes this math directly on every trade and updates on-chain balances with the processor's output, with no protection against the underlying precision behavior beyond a caller-specified `tokenExpected` minimum-output check [5](#0-4) , which does not prevent an attacker from choosing trade sizes that intentionally trigger favorable rounding. Because any account can call `ExchangeTransactionContract` against any existing pool (`ExchangeCreateContract` pools are permissionless to trade against), this is reachable by an unprivileged transaction broadcaster.

### Impact Explanation
Repeated exploitation of favorable rounding in the floating-point Bancor formula lets an attacker extract more of the counter-token than they should be entitled to on a per-trade basis. Over many transactions this can drain a pool's `firstTokenBalance`/`secondTokenBalance` reserves below what the exchange creator and other traders deposited, resulting in real, unbacked loss of funds for the exchange's other stakeholders — directly analogous to the value-extraction mechanism in the BGM incident.

### Likelihood Explanation
Exploitation requires no privileged role — any address can create or trade against an `Exchange`/`ExchangeV2` pool via `ExchangeTransactionContract`, and the vulnerable arithmetic path is active whenever the `allowHardenExchangeCalculation` hard-fork parameter has not yet been switched on for the network. Since the flag is committee-controlled and its default/activation state can lag on live networks, the legacy floating-point path remains a realistic attack surface until hardening is fully activated.

### Recommendation
- Ensure `allowHardenExchangeCalculation` is activated network-wide as early as possible so all exchange trades route exclusively through `SafeExchangeProcessor`.
- Consider deprecating and removing the double-precision `ExchangeProcessor` entirely from the execution path (test-only) rather than keeping it reachable via a toggle, to eliminate any window where floating-point rounding can be abused.
- Add invariant checks after each trade (e.g., constant-product/relay-supply consistency assertions) to detect and reject any trade whose net effect on the pool's `firstTokenBalance`/`secondTokenBalance` deviates from the exact Bancor-formula expectation beyond a strict tolerance.

### Proof of Concept
1. An attacker creates or identifies an existing low-liquidity `Exchange` pool (e.g., via `ExchangeCreateContract`).
2. While `allowHardenExchangeCalculation` is not yet enabled, the attacker repeatedly submits small `ExchangeTransactionContract` trades sized to trigger favorable truncation in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (double `Math.pow` truncated to `long`) [3](#0-2) .
3. Each trade passes the actuator's `tokenExpected` slippage check because the attacker sets `tokenExpected` to the (favorably-rounded) amount they anticipate, per `ExchangeTransactionActuator` validation [5](#0-4) .
4. Repeating this over many transactions accumulates a rounding-driven surplus, incrementally draining the pool's counter-token reserve beyond what the attacker's deposited tokens should entitle them to.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
