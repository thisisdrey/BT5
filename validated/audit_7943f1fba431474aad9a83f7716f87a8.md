## Analysis Result

I found the finding below by tracing the confirmed bug-class (accepting unauthenticated network data as authoritative, with no verification of source or sender identity) against `libsigner`'s HTTP event-receiver transport, which is explicitly in-scope.

### Title
Unauthenticated HTTP Event Listener Accepts Forged Miner/Signer Events from Any Network Peer - (File: `libsigner/src/events.rs`)

### Summary
`SignerEventReceiver::bind`/`next_event` in `libsigner/src/events.rs` opens a plain `tiny_http` server socket and processes any POST to `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, or `/new_block` with no verification of the caller's identity — no shared secret, no TLS client cert, no source-address allow-list. `SignerHttpRequest`/`decode_http_request` in `libsigner/src/http.rs` similarly only parses headers/body; it doesn't check for an `Authorization` header analogous to the node-side `auth_token` config seen in `stackslib/src/config/mod.rs` (`pub auth_token: Option<String>` — used to protect `/v3/block_proposal` on the *node*'s HTTP server, not the signer's listener).

### Finding Description
This mirrors the RADIUS bug class: an unauthenticated network attacker who can reach the listening port can inject data that the receiving process treats as authoritative without validating its origin. [1](#0-0) 
`bind()` starts a bare `HttpServer::http(listener)` with no authentication layer. [2](#0-1) 
`next_event()` dispatches any POST to `process_event`, keyed only by URL path — any TCP client that reaches the socket can submit a `StackerDBChunksEvent`, `BlockValidateResponse`, `BurnBlockEvent`, or `StacksBlockEvent` payload.

Downstream validation is only partial: for the `.signer-XXX-YYY` boot contract lane, individual chunks are still checked against a real signer's recovered public key (`chunk.recover_pk()`) [3](#0-2) 
but for the `.miners` lane, chunks are deserialized with **no signature check at all**: [4](#0-3) 
The `SignerEvent::MinerMessages(messages)` path only requires that `T::consensus_deserialize` succeed — it never calls `chunk.verify()`/`recover_pk()` against the expected miner key. Compare this to the "owner signature" gate that legitimately protects StackerDB writes at the P2P/RPC layer (`validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs:679-697`, and `poststackerdbchunk.rs`'s `BadSigner` check), which this HTTP-ingestion code path bypasses entirely because it isn't reading from the StackerDB replica at all — it's trusting whatever `StackerDBChunksEvent` JSON arrives over this unauthenticated socket, including the chunk contents.

Also, `BlockValidateResponse` (from `/proposal_response`) and `BurnBlockEvent`/`StacksBlockEvent` (from `/new_burn_block`, `/new_block`) carry **no cryptographic signature at all** in this transport — they are trusted purely because they arrived on this socket.

### Impact Explanation
If this listener is reachable over the network (not strictly bound to loopback — `bind()` takes an arbitrary `SocketAddr` from operator config, and nothing in this code enforces loopback-only binding), an unauthenticated attacker can:
- Inject forged `MinerMessages` (no signature check) that the signer's runloop treats as legitimate messages from the miner, influencing signer state without any cryptographic proof of origin.
- Inject forged `BlockValidateResponse`/burn-block/Stacks-block events that drive the signer's local state machine (`handle_block_validate_response`, tenure/burn-block bookkeeping), potentially steering signing decisions or wasting compute — a "serving non-canonical state as canonical" analog, since the signer has no way to distinguish a real node-originated event from a forged one at the transport layer.

This is weaker than a full consensus-signature bypass (the `.signer-XXX-YYY` lane still checks `chunk.recover_pk()`), but the `.miners` lane and the non-StackerDB event types (`proposal_response`, `new_burn_block`, `new_block`) have no equivalent authentication, which is a direct structural analog of the RADIUS bug: "first packet on the port is treated as authoritative, no verification of sender."

### Likelihood Explanation
Exploitability depends entirely on network exposure of the bind address used for this listener, which is operator/deployment-configured and not enforced to loopback-only within this code. I could not fully verify from the indexed files whether all production deployments bind this exclusively to `127.0.0.1` (that binding decision happens in `stacks-signer`/`stacks-node` startup code, which I was not able to fully trace within the given scope and iteration budget). This uncertainty is a material caveat.

### Recommendation
Add an authenticated channel (shared secret / HMAC over the request body, or mTLS) for all endpoints on this listener, not just rely on per-message signature checks that currently exist only for the `.signer-XXX-YYY` StackerDB lane. Extend the same "recover public key, verify against expected signer/miner set" check used in the `.signer-XXX-YYY` branch to the `.miners` `MinerMessages` branch, and add authentication to `/proposal_response`, `/new_burn_block`, and `/new_block`.

### Proof of Concept
1. Identify or reach the TCP port bound by `SignerEventReceiver::bind()` for a target signer node.
2. Craft a JSON body matching `StackerDBChunksEvent` with `contract_id` pointing at the `.miners` boot contract, containing an attacker-chosen `StackerDBChunkData` (no valid signature required, since the `MinerMessages` path never verifies it).
3. POST it to `http://<signer-ip>:<port>/stackerdb_chunks`.
4. Observe that `process_event::<T, StackerDBChunksEvent>` deserializes and forwards this as `SignerEvent::MinerMessages(...)` into the signer runloop without any signature check, confirmed at [4](#0-3) .

    fn next_event(&mut self) -> Result<SignerEvent<T>, EventError> {
        self.with_server(|event_receiver, http_server, _is_mainnet| {
            // were we asked to terminate?
            if event_receiver.is_stopped() {
                return Err(EventError::Terminated);
            }
            debug!("Request handling");
            let request = http_server.recv()?;
            debug!("Got request"; "method" => %request.method(), "path" => request.url());

            if request.url() == "/status" {
                request
                .respond(HttpResponse::from_string("OK"))
                .expect("response failed");
                return Ok(SignerEvent::StatusCheck);
            }

            if request.method() != &HttpMethod::Post {
                return Err(EventError::MalformedRequest(format!(
                    "Unrecognized method '{}'",
                    request.method(),
                )));
            }
            debug!("Processing {} event", request.url());
            if request.url() == "/stackerdb_chunks" {
                process_event::<T, StackerDBChunksEvent>(request)
            } else if request.url() == "/proposal_response" {
                process_event::<T, BlockValidateResponse>(request)
            } else if request.url() == "/new_burn_block" {
                process_event::<T, BurnBlockEvent>(request)
            } else if request.url() == "/shutdown" {
                event_receiver.stop_signal.store(true, Ordering::SeqCst);
                Err(EventError::Terminated)
            } else if request.url() == "/new_block" {
                process_event::<T, StacksBlockEvent>(request)
            } else {
                let url = request.url().to_string();
                debug!(
                    "[{:?}] next_event got request with unexpected url {}, return OK so other side doesn't keep sending this",
                    event_receiver.local_addr,
                    url
                );
                ack_dispatcher(request);
                Err(EventError::UnrecognizedEvent(url))
            }
        })?
