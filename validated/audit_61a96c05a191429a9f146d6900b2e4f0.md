### Title
Chunked-transfer reader silently truncates the body on premature connection close, allowing a MITM/relay to feed the signer node a truncated StackerDB/RPC response with no error - ([File: stacks-common/src/util/chunked_encoding.rs])

### Summary
`HttpChunkedTransferReader`/`HttpChunkedTransferReaderState::do_read` (`stacks-common/src/util/chunked_encoding.rs`) does not distinguish "the remote peer closed the connection after sending the terminal `0\r\n\r\n` chunk" from "the remote peer closed the connection mid-stream, before any terminal chunk was sent." Both cases are surfaced to callers as ordinary EOF (`read()` returning `0`), so `Read::read_to_end()` completes successfully with a truncated buffer and no error, exactly analogous to the OHTTP advisory's "missing final-chunk enforcement" bug class.

### Finding Description
`read_chunk_boundary`, the state used while waiting for the next `<len>\r\n` chunk header, does the following on underlying-stream EOF: [1](#0-0) 

```rust

    assert_eq!(self.parse_step, HttpChunkedTransferParseMode::ChunkBoundary);
    let mut b = [0u8; 1];
    let nr = fd.read(&mut b)?;
    if nr == 0 {
        return Ok(nr);
    }
    ...
```

It simply returns `Ok(0)` and leaves `parse_step` at `ChunkBoundary` (not `EOF`). The driving loop in `do_read` treats this the same as a graceful stop: [2](#0-1) 

Only the `ChunkTrailer` branch explicitly transitions to the `EOF` state, and only when `last_chunk_size == 0` (i.e., a `0`-length terminal chunk was actually parsed): [3](#0-2) 

Crucially, nothing downstream checks `state.is_eof()` after `read()`/`read_to_end()` returns. The public `Read` impl simply forwards the decoded byte count: [4](#0-3) 

The real-world consumer is `decode_http_body` in `libsigner/src/http.rs`, used by `run_http_request`, which is the transport used by `StackerDBSession::rpc_request` (`libsigner/src/session.rs`) for every signer→node StackerDB RPC (`list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk`'s ack): [5](#0-4) [6](#0-5) 

`decode_http_body` calls `fd.read_to_end(&mut decoded_body)?;` with no post-check that the chunked stream actually reached its terminal `0`-chunk. `Read::read_to_end` treats a `0`-byte `read()` as normal EOF and returns `Ok(())`, so an attacker (an on-path relay/proxy, or anyone who can interpose on the signer↔node TCP session — e.g. the operator's own reverse proxy, or a MITM if TLS is not used) can cut the outer TCP stream immediately after any legitimate, fully-formed chunk (i.e., after its `\r\n` trailer, while still in `ChunkBoundary` state), and the signer will treat whatever bytes were received so far as the complete, valid response body — with no decode error, no exception, and no distinguishing signal from a normal, complete response.

This differs from the analogous "known length" code path (`stackslib/src/net/connection.rs`, `consume_payload_known_length`), which explicitly compares buffered bytes against the declared length before accepting a payload — the chunked-body path has no equivalent completeness check.

### Impact Explanation
The impact is bounded compute/read-endpoint style state confusion rather than a network-wide propagation vulnerability: a truncated StackerDB chunk retrieved via `get_chunks`/`get_latest_chunks` would fail any hash/signature check performed by the caller against the *intended* full chunk (since a truncated blob has a different SHA512/256 digest and won't match a signed `SlotMetadata.data_hash`), so it would not be accepted as a legitimate signed chunk into storage. However, for responses whose content is JSON-deserialized directly without such a cryptographic binding (e.g. `list_chunks`'s `Vec<SlotMetadata>` via `serde_json::from_slice`, or `put_chunk`'s `StackerDBChunkAckData` ack), a truncated JSON body will typically just fail to parse and surface as a `Deserialize` error rather than silently succeed with corrupted data — this limits the exploitable blast radius primarily to a denial-of-service / confusing-error condition on signer↔node RPC rather than a state-corrupting write. I was not able to fully verify, within the remaining budget, whether any caller of `decode_http_body`/`run_http_request` in this codebase consumes a body whose byte-for-byte prefix is a "valid-looking but incomplete" structure that would parse successfully as a distinct, incorrect value (which would elevate this to serving non-canonical data as canonical). Given that uncertainty, this is best characterized as **Medium**: a masked stream-truncation defect that can produce unreliable/incomplete RPC results without any error signal, potentially causing the signer to act on stale/incomplete data it believes is complete.

### Likelihood Explanation
Exploitation requires the ability to interpose on the TCP connection between the signer and the node (or between any two `HttpChunkedTransferReader` consumers) and close it at a chosen byte offset — a capability available to a relay operator, a misconfigured/malicious reverse proxy, or a genuine on-path MITM when the signer↔node RPC link is not otherwise integrity-protected. No cryptographic material or privileged role is required; only network position, matching the "on-path adversary" precondition in the source advisory.

### Recommendation
After the chunked read loop completes (both in `HttpChunkedTransferReader::read`/`do_read` and specifically in `decode_http_body`), explicitly check `state.is_eof()` (i.e., `parse_step == EOF`, meaning a `0`-length terminal chunk was actually parsed) before treating the accumulated buffer as a complete, valid body. If the underlying reader reaches EOF while `parse_step` is anything other than `EOF`, return an explicit `UnexpectedEof`/`ChunkedError` instead of a silent `Ok(0)`, so `read_to_end` and all callers observe a hard error rather than a falsely "complete" truncated body.

### Proof of Concept
1. Have `StackerDBSession::rpc_request` (or any `run_http_request` caller) issue a chunked-encoded response request against a node the attacker controls the path to (relay/proxy in the middle).
2. Server sends a valid response with `Transfer-Encoding: chunked` and a legitimate first chunk, e.g. `HTTP/1.1 200 OK\r\nTransfer-Encoding: chunked\r\n\r\na\r\n0123456789\r\n` — then closes the TCP connection immediately, withholding the terminal `0\r\n\r\n` chunk and any further chunks.
3. `decode_http_body` → `HttpChunkedTransferReader::read_to_end` reads the one complete 10-byte chunk, then on the next `read()` call `read_chunk_boundary` sees the socket EOF and returns `Ok(0)` while `parse_step` is still `ChunkBoundary`.
4. `read_to_end` returns `Ok(())` with `decoded_body == b"0123456789"` and no error — the caller has no way to tell this is a truncated body vs. a genuinely complete 10-byte response.

    pub fn do_read<R: Read>(&mut self, fd: &mut R, buf: &mut [u8]) -> io::Result<(usize, usize)> {
        let mut decoded = 0;
        let mut consumed = 0;
        while decoded < buf.len() {
            match self.parse_step {
                HttpChunkedTransferParseMode::ChunkBoundary => {
                    let count = self.read_chunk_boundary(fd)?;
                    if count == 0 {
                        break;
                    }
                    consumed += count;
                }
                HttpChunkedTransferParseMode::Chunk => {
                    let nr = self.read_chunk_bytes(fd, &mut buf[decoded..])?;
                    if nr == 0 && self.parse_step == HttpChunkedTransferParseMode::Chunk {
                        // still trying to read the chunk, but got 0 bytes
                        break;
                    }
                    decoded += nr;
                    consumed += nr;
                }
                HttpChunkedTransferParseMode::ChunkTrailer => {
                    let count = self.read_chunk_trailer(fd)?;
                    if count == 0 {
                        break;
                    }
                    consumed += count;
                    if self.last_chunk_size == 0 {
                        // we're done
                        trace!("finished last chunk");
                        self.parse_step = HttpChunkedTransferParseMode::EOF;
                        break;
                    }
                }
                HttpChunkedTransferParseMode::EOF => {
                    break;
                }
            }
        }
        Ok((decoded, consumed))
    }

/// Decode an HTTP body, given the headers.
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
