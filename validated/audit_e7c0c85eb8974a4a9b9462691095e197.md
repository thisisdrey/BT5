## Analog Found: Permissionless dust deposits can block admin `lending_pool_close_bank`

### Title
Unprivileged front-run deposits can indefinitely block bank closure - (File: `programs/marginfi/src/instructions/marginfi_group/close_bank.rs`)

### Summary
`lending_pool_close_bank` gates bank closure on the bank having zero open positions and zero total asset/liability shares. Any unprivileged user can permissionlessly open a fresh `MarginfiAccount` and deposit into the target bank via `lending_account_deposit`, which requires no admin authorization and only checks that the bank isn't paused/reduce-only. This mirrors the KelpDAO pattern (a removal/close operation gated on a manipulable "zero balance" invariant, defeated by an external front-run deposit), causing the admin's close operation to revert until it is manually retried after clearing the new position.

### Finding Description
`lending_pool_close_bank` requires: [1](#0-0) 

These checks (`lending_position_count == 0`, `borrowing_position_count == 0`, `total_asset_shares`/`total_liability_shares` zero) are the exact analog of the KelpDAO `NodeDelegator` zero-balance check. The instruction is admin-gated (`has_one = admin`), but the state it depends on (bank position counters/shares) is mutated by the fully permissionless `lending_account_deposit` instruction: [2](#0-1) 

Any signer can create a new `MarginfiAccount` under their own authority and deposit an arbitrary (even dust) amount into the exact bank an admin is attempting to close, so long as the bank is not paused/reduce-only (`validate_bank_state(&bank, InstructionKind::FailsIfPausedOrReduceState)` at line 60 of `deposit.rs`) and doesn't have `TOKENLESS_REPAYMENTS_ALLOWED` set. This increments `lending_position_count` and `total_asset_shares`, which will cause a subsequent `lending_pool_close_bank` call to fail with `MarginfiError::BankCannotClose`.

Because deposit is unprivileged and cheap, an attacker (or simply an innocuous depositor) can repeat this after every admin withdrawal attempt, indefinitely blocking the bank-close workflow, exactly matching the "front-run 1 wei deposit to revert removal" bug class from the report. The admin's only mitigation is to pause the bank first (`configure_bank`), which is not enforced or required by `lending_pool_close_bank` itself — nothing in the on-chain logic prevents an admin from attempting `lending_pool_close_bank` without pausing, and even with pausing there is a race window between clearing positions and setting the pause flag in which any depositor can insert a fresh dust position.

### Impact Explanation
This is a liveness/DoS issue on an admin operation (permanent lock of `lending_pool_close_bank` until manual intervention), not a fund-theft or insolvency bug. It matches the "permanent lock/freeze" category accepted by the validation rules: the admin-intended state transition (bank closure) can be blocked indefinitely by an unprivileged actor. Impact is limited to operational inconvenience/griefing of the admin's bank-retirement workflow; it does not directly cause loss of user funds, bad debt, or unauthorized transfers.

### Likelihood Explanation
Likelihood is moderate: it requires the admin to attempt bank closure without first pausing the bank, or to race the pause/close sequence — a plausible operational sequence, since nothing in the codebase enforces pause-before-close ordering. The attack itself is cheap (dust deposit into a bank), and the deposit instruction imposes no minimum, so it can be triggered by anyone at negligible cost.

### Recommendation
Enforce that `lending_pool_close_bank` can only be attempted (or that deposits into the bank cannot occur) once the bank is already in a terminal `Paused`/`ReduceOnly`/close-pending state, e.g. require the bank to carry a flag (set atomically by the admin) that blocks all further deposits before the zero-position check is evaluated, closing the race window between "admin decides to close" and "bank actually stops accepting deposits."

### Proof of Concept
1. Admin decides to close `Bank X` (bank previously had `CLOSE_ENABLED_FLAG`, no `TOKENLESS_REPAYMENTS_ALLOWED`, not paused).
2. Admin withdraws/repays all existing positions so `lending_position_count == 0`, `total_asset_shares == 0`.
3. Before the admin's `lending_pool_close_bank` transaction lands, an unrelated user creates a new `MarginfiAccount` and calls `lending_account_deposit` on `Bank X` with a minimal amount (e.g. 1 native unit), per `programs/marginfi/src/instructions/marginfi_account/deposit.rs`.
4. `Bank X.lending_position_count` becomes 1 and `total_asset_shares` becomes nonzero.
5. Admin's `lending_pool_close_bank` call fails with `MarginfiError::BankCannotClose` (checks at `programs/marginfi/src/instructions/marginfi_group/close_bank.rs:27-37`).
6. Attacker repeats step 3 after every subsequent admin withdrawal, indefinitely blocking bank closure until the admin pauses the bank (a separate, unenforced precondition).
