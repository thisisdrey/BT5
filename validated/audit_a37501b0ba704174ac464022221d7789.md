### Title
Deleted account's postponed action receipt survives `remove_account` and re-executes with self-authorization against the re-created account of the same name - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` (used by `action_delete_account`) removes `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie entries for an account, but never removes `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` entries keyed by that account's `receiver_id`. If an account has a self-addressed action receipt postponed on missing input data when it is deleted and then re-created with the same `AccountId`, the stale postponed receipt survives, and its actions are later executed against the brand-new account state once the outstanding `DataReceipt`s arrive.

### Finding Description
`set_postponed_receipt` stores a postponed `ActionReceipt` under `TrieKey::PostponedReceipt{receiver_id, receipt_id}` (`core/store/src/utils/mod.rs:120-127`), together with `TrieKey::PendingDataCount{receiver_id, receipt_id}` and one `TrieKey::PostponedReceiptId{receiver_id, data_id}` per still-missing input (`runtime/runtime/src/lib.rs:1608-1655`, `process_action_receipt`).

`remove_account` (`core/store/src/utils/mod.rs:504-575`), called from `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`), only removes `TrieKey::Account`, `TrieKey::ContractCode`, access keys/gas-key nonces, and `TrieKey::ContractData`. It does not iterate or delete `PostponedReceipt`, `PendingDataCount`, or `PostponedReceiptId` entries for the account. `action_delete_account` itself has no check for outstanding postponed/pending receipts before allowing deletion — it only validates storage usage and gas-key balance (`runtime/runtime/src/actions.rs:326-363`).

When a subsequent `DataReceipt` for one of the two missing `input_data_ids` arrives, `process_receipt` (`runtime/runtime/src/lib.rs:1367-1474`) unconditionally writes `ReceivedData` and looks up `PostponedReceiptId`/`PendingDataCount` under the (unchanged) `receiver_id`, with no check that the receiving account still exists or is the "same" account. Once the pending count hits zero it calls `get_postponed_receipt` and executes it via `apply_action_receipt` (`runtime/runtime/src/lib.rs:772-861`). Inside `apply_action_receipt`, the account is fetched fresh (`let mut account = get_account(state_update, account_id)?;` at `lib.rs:853`), and `actor_id` is initialized purely from `receipt.predecessor_id()` (`lib.rs:855`) — there is no linkage back to the account's identity/incarnation at the time the receipt was postponed.

Administrative actions (`AddKey`, `DeleteKey`, `DeployContract`, `Stake`, `DeleteAccount`) are only permitted when `actor_id == account_id` (the `ActorNoPermission` check, documented in `chain/jsonrpc/openapi/openapi.json:1918-1941`: "can be proceed only if sender=receiver or the first TX action is a `CreateAccount` action"). This check is a pure string/`AccountId` comparison; it has no concept of account "incarnation." A postponed receipt authored as a self-call (`predecessor_id == receiver_id == X`) will therefore pass this check identically whether it executes against the original X or a freshly re-created X of the same name, since `actor_id` (== old X) and `account_id` (== new X) are the same `AccountId` value.

Exploit flow:
1. Attacker's contract at account `X` sends itself an action receipt `R1` with two `input_data_ids` (e.g., embedding privileged actions such as `AddKey` with `FullAccess`, or other administrative actions). Since `predecessor_id == receiver_id == X`, it passes `ActorNoPermission`. Because two inputs are outstanding, `process_action_receipt` postpones it: `TrieKey::PostponedReceipt{X, R1}`, `TrieKey::PendingDataCount{X, R1}`, and two `TrieKey::PostponedReceiptId{X, data_id}` entries are written.
2. Before the two `DataReceipt`s land, attacker submits `DeleteAccount` for `X` (with zero locked balance to avoid `DeleteAccountStaking`, and small enough storage to avoid `DeleteAccountWithLargeState`). `remove_account` clears `Account`/keys/code/data for `X` but leaves the `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries intact.
3. Attacker (or the parent account) re-creates `X` via `CreateAccount`, deploying new code and funding it, establishing a fresh `Account` record and (initially) no access keys.
4. When the two outstanding `DataReceipt`s are eventually delivered to `X`, `process_receipt` finds the leftover `PostponedReceiptId` links, decrements `PendingDataCount` to 0, fetches `R1` via `get_postponed_receipt`, and executes it via `apply_action_receipt` against the **new** `X`'s account/state, with `actor_id = predecessor_id = X`, which trivially satisfies self-authorization on the new account.

None of the standard protections (signature/nonce checks, access-key permission checks, gas metering, storage-staking, or size limits) apply here, because this path never re-validates a transaction — it is pure receipt-apply logic that trusts `predecessor_id == account_id` as sufficient authorization, and the state used to determine "does this account exist / is this the right account" is not cleaned up on deletion.

### Impact Explanation
This breaks the invariant that a promise/postponed receipt cannot outlive the account root it was authorized against. It allows self-privileged administrative actions (e.g., `AddKey` with `FullAccess`, `Stake`, `DeployContract`, or `DeleteAccount`) to be injected into a freshly re-created account without that account's new owner/contract ever authorizing them — an authorization escalation across account incarnations of the same `AccountId`. Depending on the actions embedded in `R1`, this can lead to compromise/hijacking of the new account (e.g., attacker granting themselves a full-access key on the recreated account without the recreation transaction including it), which maps to the "authorization escalation across accounts or promises" bounty category. Because the account is freshly funded/created by whoever recreated `X`, this could also be used to grief or hijack accounts recreated by third parties who reuse a previously-deleted name, or self-attack for stealth privilege injection that survives a supposed account "reset."

### Likelihood Explanation
Fully reachable by an unprivileged funded account using only standard, publicly available actions: `FunctionCall` promises with multiple `input_data_ids`, `DeleteAccount`, `CreateAccount`, and `DataReceipt` delivery (implicit, driven by whichever contract call was supposed to resolve the two dependencies). No validator/node/protocol-level access is required. The attacker fully controls the timing (can hold back delivering the two dependent data receipts until after delete+recreate). The only preconditions are: the account has zero locked balance and reasonably small state (to pass `DeleteAccountAction` checks), and the attacker can construct a self-call receipt with two outstanding `input_data_ids`, which is a standard cross-contract-call/promise pattern (`promise_and`/multi-dependency callbacks). This is fully repeatable and low-cost (only gas + minimal storage deposits).

### Recommendation
`remove_account` (`core/store/src/utils/mod.rs`) should also iterate and remove `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` entries for the account being deleted, mirroring the existing access-key/gas-key/contract-data cleanup pattern (prefix-iterate using `receiver_id` and remove all matches). Additionally, `action_delete_account` should reject deletion (or `remove_account` should refund/burn) any account that still has pending/postponed receipts, similar to the existing `gas_key_balance_to_burn`/`storage_usage` checks, so that deletion cannot silently orphan in-flight promises.

### Proof of Concept
Runtime apply-path integration test (in `runtime/runtime/src/tests/apply.rs` or `test-loop-tests`):
1. Create account `X`, deploy a contract that, on some call, creates a self-promise (`predecessor_id == receiver_id == X`) with two `input_data_ids` that are never immediately satisfied, causing the action receipt `R1` to be postponed. Assert `get_postponed_receipt(state_update, &X, R1)` returns `Some(..)` and `get(state_update, &TrieKey::PendingDataCount{receiver_id:X, receipt_id:R1})` returns `Some(2)`.
2. Submit `DeleteAccount` for `X` (with a valid beneficiary, zero locked balance). Assert `get_account(state_update, &X)` is now `None`, but `get_postponed_receipt(state_update, &X, R1)` is still `Some(..)` (demonstrating the leak).
3. Submit `CreateAccount` for `X` from a parent/attacker account, funding it and deploying new code. Assert the new `Account` record exists and has no access keys.
4. Deliver the two `DataReceipt`s for the outstanding `input_data_ids` addressed to `X`. Assert that this triggers execution of `R1`'s actions (e.g., an embedded `AddKey` with `FullAccess`) against the **new** `X`, verified by checking that the new access key now exists on `X`'s freshly created account — despite the fact that this key was never included in `X`'s `CreateAccount`/setup transaction.
