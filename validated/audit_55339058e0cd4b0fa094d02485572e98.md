## Title
Deposit share-rounding to zero causes silent loss of depositor funds - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`)

### Summary
The external report describes a rounding bug where `optionShare = optionTokenBalance * 1e18 / totalOptionTokenSupply` can floor to `0` when the divisor grows large relative to the numerator, silently zeroing out a user's entitlement while their deposit/stake is still consumed. The same rounding-to-zero class is reachable in Zest's vault `deposit` flow via `convert-to-shares-preview`, and unlike the `redeem` path, `deposit` has no floor guard against a zero result.

### Finding Description
Each vault (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`) computes minted shares for a deposit with: [1](#0-0) 
```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```
This is a floor division (`mul-div-down`), the exact same mathematical pattern as the reported `optionTokenBalance * 1e18 / totalOptionTokenSupply`: when `total-assets` (`ta`) is large relative to `amount * total-supply` (`ts`), the result rounds down to `0`.

The `deposit` function then uses this value directly without a non-zero floor check: [2](#0-1) 
```
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      ...
      (inkind (convert-to-shares-preview amount)))
    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))
    ...
    (ok inkind)))
```
There is no `(asserts! (> inkind u0) ...)` guard here. By contrast, the sibling `redeem` function explicitly protects against a zero output: [3](#0-2) 
```
(define-public (redeem (amount uint) (min-out uint) (recipient principal))
  (let (
    ...
    (inkind (convert-to-assets-preview amount)))
  (asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
  (asserts! (not (get redeem states)) ERR-PAUSED)
  (asserts! (> amount u0) ERR-AMOUNT-ZERO)
  (asserts! (> inkind u0) ERR-OUTPUT-ZERO)
  (asserts! (>= inkind min-out) ERR-SLIPPAGE)
  ...
```
The asymmetry is the root cause: `redeem` checks `ERR-OUTPUT-ZERO`, `deposit` does not. If `min-out` is left at `u0` (the natural default when a caller does not want slippage protection, or when a contract wrapper simply forwards a small `amount`), `(>= inkind min-out)` (i.e., `0 >= 0`) passes trivially, the underlying tokens are pulled from the depositor via `receive-underlying`, `assets` is increased by the full deposited `amount`, but `ft-mint? zft 0 recipient` mints zero shares. The depositor's tokens are absorbed into the vault's asset pool while the depositor receives no shares representing a claim on them — a direct, permanent loss of the deposited principal for that specific transaction, exactly analogous to the reported winner receiving `0` due to share-rounding.

### Impact Explanation
This is a permanent freezing/loss of the depositor's principal funds for the specific transaction affected: assets are transferred into the vault (`receive-underlying`, `var-set assets`) but zero vault shares are minted to the recipient, so the depositor has no mechanism to reclaim the value — it becomes an unclaimed/undistributed surplus effectively socialized to existing shareholders. This matches the in-scope "vault share math and interest accrual" impact area and constitutes at least temporary/permanent freezing of the depositor's funds.

### Likelihood Explanation
The likelihood scales with the vault's `total-assets`/`total-supply` ratio (share price). As a lending vault accrues significant interest over time (`total-assets-preview` grows via `debt-preview`/`total-borrowed` while `total-supply` stays comparatively smaller), the share price rises, shrinking the amount of `amount` needed to trigger flooring to zero. Small deposits — e.g., dust deposits, or deposits routed through third-party integrations/wrapper contracts that don't set a meaningful `min-out` — become increasingly likely to round to zero as the vault matures. This requires no privileged action and is reachable from an ordinary principal's `deposit` call.

### Recommendation
Add an explicit zero-share guard in `deposit`, mirroring `redeem`'s `ERR-OUTPUT-ZERO` check, e.g. `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` before minting, in all affected vault contracts (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`).

### Proof of Concept
1. Let the vault accrue enough interest so that `total-assets-preview` / `total-supply-preview` (share price) exceeds a threshold where `amount * ts / ta` floors to `0` for a small `amount` (e.g., `amount = 1` unit of underlying while share price > 1 unit-per-share due to accrued interest).
2. Caller invokes `deposit(amount=1, min-out=0, recipient=caller)`.
3. `convert-to-shares-preview` returns `inkind = 0` via `mul-div-down`.
4. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes since `0 >= 0`.
5. `receive-underlying` pulls `1` unit from caller; `var-set assets` increases by `1`; `ft-mint? zft 0 recipient` mints zero shares.
6. Caller has permanently lost their `1` unit deposit with no shares to redeem it.
