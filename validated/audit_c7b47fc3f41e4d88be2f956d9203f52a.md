### Analysis

**Push/pop symmetry is guaranteed by construction.** `InvokeContext::process_instruction` explicitly documents and enforces that `pop()` is called if and only if `push()` succeeded, independent of the executed instruction's result: [1](#0-0) 

The comment "MUST pop if and only if push succeeded, independent of result. Thus, the `.and()` instead of an `.and_then()`" is key: `Result::and` takes an already-evaluated `Result` value as its argument, so `self.pop()` is evaluated eagerly and unconditionally right after `process_executable_chain` returns — regardless of whether that chain errored deep in a CPI stack. If `push()` itself fails (e.g., `CallDepth` at max stack), the function returns early via `?` before any pop is attempted, which is correct since nothing was pushed. This makes `TransactionContext`'s `instruction_stack` symmetric by construction at every nesting level, including `native_invoke_signed`, which delegates entirely to `process_instruction`: [2](#0-1) 

A test explicitly verifies stack-height symmetry after a forced `CallDepth` failure at max depth: [3](#0-2) 

**Account lock release is entirely decoupled from instruction-level push/pop.** The write/read locks tracked in `ThreadAwareAccountLocks` (banking-stage scheduler path) are released in `SchedulingCommon::complete_batch`, called unconditionally whenever a `FinishedConsumeWork` message arrives for a batch — independent of whether any individual transaction inside that batch succeeded, failed, or errored deep in a CPI chain: [4](#0-3) 

Likewise, at the bank/replay level, `TransactionBatch`'s `Drop` implementation and `unlock_failures` always release locks regardless of per-transaction execution outcome: [5](#0-4) 

An `InstructionError` returned deep inside a CPI simply becomes the transaction's execution status (a normal, expected outcome type — SVM transactions routinely "fail" with an `InstructionError` while still being committed/counted and having their locks released). It never causes a panic, an unbalanced `instruction_stack`, or a skipped unlock, because lock release doesn't depend on VM-internal call-stack bookkeeping at all — it depends on batch completion signaling, which always occurs once the bank finishes processing the batch.

Given both the instruction-stack symmetry guarantee (enforced by the intentional `.and()` design and covered by unit tests) and the complete decoupling of the scheduler's/bank's lock lifecycle from CPI-internal errors, there is no reachable path by which an attacker-controlled deep-CPI error strands a write lock in `ThreadAwareAccountLocks` or leaves `TransactionContext`'s instruction stack unbalanced.

    /// For every error result, if the corresponding transaction is
    /// still locked, unlock the transaction and then record the new error.
    pub fn unlock_failures(&mut self, transaction_results: Vec<Result<()>>) {
        assert_eq!(self.lock_results.len(), transaction_results.len());
        // Shouldn't happen but if a batch was marked as not needing an unlock,
        // don't unlock failures.
        if !self.needs_unlock() {
            return;
        }

        let txs_and_results = transaction_results
            .iter()
            .enumerate()
            .inspect(|(index, result)| {
                // It's not valid to update a previously recorded lock error to
                // become an "ok" result because this could lead to serious
                // account lock violations where accounts are later unlocked
                // when they were not currently locked.
                assert!(!(result.is_ok() && self.lock_results[*index].is_err()))
            })
            .filter(|(index, result)| result.is_err() && self.lock_results[*index].is_ok())
            .map(|(index, _)| (&self.sanitized_txs[index], &self.lock_results[index]));

        // Unlock the accounts for all transactions which will be updated to an
        // lock error below.
        self.bank.unlock_accounts(txs_and_results);

        // Record all new errors by overwriting lock results. Note that it's
        // not valid to update from err -> ok and the assertion above enforces
        // that validity constraint.
        self.lock_results = transaction_results;
    }
}
