### Title
`socialize-debt` write-down uses stale (non-accrued) index/lindex instead of first accruing pending interest - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and other `vault-*.clar` vaults; `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The reported Certora finding (M-06) shows that `_deRegisterKnot` snapshots `accumulatedETHPerFreeFloatingShare` without first calling the function that brings that accumulator up to date, so the snapshot is stale and stakers permanently lose the unaccrued portion. The same structural bug class exists in Zest's vault `socialize-debt` function: it performs a debt write-down/index-haircut snapshot using the raw `index`/`lindex` state variables directly, without first calling `accrue`, unlike every other state-mutating vault entry point (`system-borrow`, `system-repay`, `flashloan`) which explicitly call `(try! (accrue))` as their first operation.

### Finding Description
Every vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) exposes `system-borrow` and `system-repay`, both of which begin their `let` binding with `(u (try! (accrue)))` before reading `index`/`lindex`/`total-borrowed`, guaranteeing interest accrued since `last-update` is applied before any principal mutation: [1](#0-0) 

`socialize-debt`, however, reads `index`/`lindex`/`total-borrowed`/`assets` straight from storage without calling `accrue` first, then computes `debt-reduction` and the haircut `new-lindex` from these stale values and commits them directly: [2](#0-1) 

In the market orchestrator, `socialize-debt-asset` calls the vault's `socialize-debt` (the stale write-down) and only afterwards refreshes the cache by calling `vault-accrue`, i.e. accrual happens after the write-down has already been committed on the reduced principal, not before it on the full pre-write-down principal: [3](#0-2) 

The `next-index`/interest-rate mechanics that `accrue` relies on are time-delta based (`stacks-block-time` minus `last-update`), confirming that any elapsed time since the last accrual call carries real, un-applied interest at the moment `socialize-debt` executes: [4](#0-3) 

Because `socialize-debt` never brings `index`/`lindex`/`total-borrowed` up to date before computing the write-down, any interest that accrued on the full (pre-haircut) principal between the last accrual and the socialize-debt call is silently dropped: it is neither credited to `assets`/`total-borrowed` before the reduction, nor reflected in the `lindex` haircut math, nor captured by the treasury-LP mint logic inside `accrue` (which runs afterward on the already-reduced `principal-scaled`). This is structurally identical to the Certora M-06 root cause: a value that must be “fully accrued” before being snapshotted/written down is snapshotted using an out-of-date accumulator.

### Impact Explanation
Interest that accrued on the debt between `last-update` and the moment `socialize-debt` runs is permanently unaccounted for — it is never minted into `assets`/supplier value, and the subsequent `accrue` call only advances the index starting from the already-reduced principal. Depositors (suppliers) of that vault permanently lose the yield that had already economically accrued on the full principal for that elapsed period. This lands squarely on **High – permanent freezing/theft of unclaimed yield**, matching the explicitly in-scope impact class for interest accrual and socialize-debt.

### Likelihood Explanation
`socialize-debt` is reached from `market.clar`'s liquidation-shortfall path (`socialize-debt-asset` inside the liquidation flow), which is triggered by ordinary, unprivileged liquidator calls — no DAO or privileged action is required. Any liquidation that leaves a bad-debt remainder to be socialized, and where any nonzero time has elapsed since the vault's `last-update` (essentially any block where the vault hasn't been touched immediately prior), triggers the loss. Given liquidations naturally occur asynchronously relative to other vault activity, this is a realistically frequent condition, not an edge case.

### Recommendation
Call `(try! (accrue))` as the first operation inside `socialize-debt` in every `vault-*.clar` contract (mirroring `system-borrow`/`system-repay`), so that `index`, `lindex`, `total-borrowed`, and `assets` are fully up to date — and any due treasury-LP mint has occurred — before the debt write-down and lindex haircut are computed and committed.

### Proof of Concept
1. At time `T0`, vault's `last-update = T0`, `index = I0`, `lindex = L0`, `total-borrowed = B`.
2. Time passes to `T1 > T0` with no other vault interaction; interest has economically accrued (would push index to `I1 > I0` if `accrue` were called) but is not yet realized on-chain.
3. A liquidation leaves bad debt for that borrower/asset; `market.clar`'s `socialize-debt-asset` is invoked at `T1`, calling the vault's `socialize-debt` directly.
4. `socialize-debt` computes `debt-reduction = scaled-amount * I0 / PRECISION` and `new-lindex` from `old-total-assets` computed with the stale `I0`, instead of `I1` — understating the true debt being written off and mis-computing the supplier haircut, discarding the `I1 - I0` interest that had accrued on the full principal.
5. `market.clar` then calls `vault-accrue` to refresh the cache, but this now operates on the already-reduced `principal-scaled`, so the dropped interest for the elapsed `T0→T1` window on the pre-reduction principal is never recovered — suppliers permanently lose that yield. [2](#0-1) [3](#0-2)
