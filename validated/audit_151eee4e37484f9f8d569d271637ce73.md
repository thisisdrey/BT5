### Title
Inconsistent Interpretation of Malformed `Content-Length` in Stacks HTTP Request Parser Enables Request Smuggling - (File: `stackslib/src/net/http/request.rs`)

### Summary
`HttpRequestPreamble::consensus_deserialize` silently discards an unparseable `Content-Length` header value instead of rejecting the request, causing the node's HTTP framing logic to treat a request with a malformed length as having a zero-byte body. This creates exactly the "inconsistent interpretation of HTTP requests" condition described in CVE-2022-24801 (Twisted): the Stacks node's own parser disagrees with any RFC 7230–compliant front end/proxy about where a request ends, enabling classic HTTP request smuggling / desync attacks against the node's RPC or p2p-HTTP listener over a persistent (keep-alive) connection.

### Finding Description
When parsing a request preamble, the `content-length` header is parsed like this: [1](#0-0) 

```rust
} else if key == "content-length" {
    // parse
    content_length = match value.parse::<u32>() {
        Ok(len) => Some(len),
        Err(_) => None,
    };
    seen_headers.insert(key);
}
```

Any value that fails to parse as a `u32` — e.g. `-1`, non-numeric garbage, or an out-of-range number like `4294967296` (this is even asserted as expected/benign behavior in the existing test `test_parse_reserved_header`, see `stackslib/src/net/http/tests.rs:71-73`) — is silently converted to `None` rather than causing the request to be rejected. `get_content_length()` then coerces `None` to `0`: [2](#0-1) 

This contrasts sharply with the equivalent code path for HTTP *responses*, `HttpResponsePreamble::consensus_deserialize`, which explicitly treats a malformed `Content-Length` as a hard parse error: [3](#0-2) 

This request-side value of `0` is exactly what is fed into the connection framing state machine via `ProtocolFamily::payload_len`: [4](#0-3) 

which `Connection<P>::consume_preamble` / `consume_payload_known_length` use to decide exactly how many subsequent bytes belong to the current message and where the *next* pipelined message begins on the same socket: [5](#0-4) 

Because the Stacks parser silently treats an invalid `Content-Length` as "no body" (0 bytes), while an RFC-7230-conformant intermediary (reverse proxy, load balancer, or front-end) in front of the node's RPC HTTP endpoint (`stackslib/src/net/rpc.rs`, registered/dispatched via `stackslib/src/net/server.rs`) would either reject the malformed value outright or interpret it differently, the two parsers disagree about the message boundary. This is precisely the "inconsistent interpretation of HTTP requests" bug class from the reference advisory (CWE-444), applied here to break the equality between "bytes the front-end thinks belong to request N" and "bytes the Stacks node thinks belong to request N+1".

### Impact Explanation
On a persistent (keep-alive) HTTP connection to a Stacks node's RPC/p2p-HTTP port sitting behind a proxy, an attacker can craft a request whose `Content-Length` header fails `u32` parsing (e.g. `Content-Length: -1` or an overflowing value) followed by attacker-controlled bytes. The proxy will forward the request/body based on its own (RFC-compliant) interpretation, while the Stacks node will treat the request as zero-length and immediately try to parse the following attacker-supplied bytes as a brand-new HTTP request/preamble on the same connection. This is a request-smuggling primitive: it lets an attacker inject requests that the node will process as if they originated independently on the connection, potentially bypassing intermediary access controls (IP allow-listing, rate limiting, WAF rules) that are applied per logical HTTP request by the front end but not re-validated by the node, and/or causing responses to be associated with the wrong request in downstream systems. This matches the "request smuggling or auth bypass" Critical impact category.

### Likelihood Explanation
The RPC/p2p-HTTP listener accepts unauthenticated remote connections by default, and constructing a request with an unparseable `Content-Length` value requires no special privileges — it's a single crafted HTTP request. The main precondition (consistent with the original advisory's caveat) is that the node sits behind another HTTP parser/proxy that interprets the same malformed header differently, which is a common deployment pattern for Stacks nodes' public RPC endpoints.

### Recommendation
Reject requests with an unparseable `Content-Length` header the same way `HttpResponsePreamble::consensus_deserialize` does for responses, i.e. return a `CodecError::DeserializeError` instead of silently mapping `Err(_) => None` for request `Content-Length` parsing in `stackslib/src/net/http/request.rs`. Additionally, consider validating that the header contains no `+`/`-` sign and only digit characters (matching the CVE-2022-24801 remediation) before invoking `u32::from_str`.

### Proof of Concept
1. Establish a persistent connection to a Stacks node's HTTP RPC port through an RFC-7230-strict/lenient front-end proxy that keeps the connection alive.
2. Send:
```
GET /v2/info HTTP/1.1\r\n
Host: <host>\r\n
Content-Length: -1\r\n
Connection: keep-alive\r\n
\r\n
GET /v2/blocks/... HTTP/1.1\r\n
Host: attacker\r\n
X-Forwarded-For: 127.0.0.1\r\n
\r\n
```
3. The proxy forwards this as it interprets `Content-Length: -1` (commonly by treating the whole thing as one oversized/invalid request, or passing it through untouched).
4. The Stacks node's parser sets `content_length = None` (line 392-398 quoted above) → `get_content_length() == 0` → treats the `GET /v2/info` request as having no body and immediately begins parsing the following `GET /v2/blocks/...` bytes as an entirely separate, second smuggled request on the same connection — one the proxy never intended to forward as a discrete request (e.g., it may carry a spoofed `X-Forwarded-For` that the proxy would have stripped/overwritten had it seen it as a top-level request).
