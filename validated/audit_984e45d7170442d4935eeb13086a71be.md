Audit Report

## Title
`process_delivery_receipt` ignores the Ethereum-reported `success` flag and pays relayer rewards for failed deliveries - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`DeliveryReceipt::success` is decoded from the Ethereum `InboundMessageDispatched` event log but is never inspected by `Pallet::process_delivery_receipt`, which unconditionally pays the relayer reward and removes the `PendingOrder` regardless of whether the dispatch on Ethereum succeeded or failed. This allows an unprivileged relayer to submit a valid receipt proof for a *failed* dispatch and still collect the full relayer fee meant for successful delivery.

## Finding Description
`DeliveryReceipt` is decoded in `TryFrom<&Log>` with an explicit `success: bool` field sourced from the Solidity event `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)`: [1](#0-0) . This field is populated correctly during decode: [2](#0-1) .

`submit_delivery_receipt` is a public, `ensure_signed`-gated extrinsic that verifies the proof via `T::Verifier::verify`, decodes the receipt, and forwards it to `process_delivery_receipt` with no inspection of `success`: [3](#0-2) .

`process_delivery_receipt` only checks `receipt.gateway` against `T::GatewayAddress` and looks up the `PendingOrder` by `receipt.nonce`; it then unconditionally pays `order.fee` to the reward account and removes the order — `receipt.success` is never read: [4](#0-3) .

A grep across the whole `bridges/snowbridge/**` tree confirms the only reference to `.success` in this context is the field's own definition/decode site — it is never read anywhere else in the pallet logic, meaning no other guard compensates for this omission. The existing `PendingOrders` removal (settlement) only prevents replay of the *same* nonce; it does not prevent the first, legitimate call from mispaying based on a decoded-but-discarded outcome flag.

## Impact Explanation
This matches the "duplicate settlement or payout" / unbacked-payout category in the impact gate: bridge-controlled reward funds are paid out via `T::RewardPayment::register_reward` for message deliveries that Ethereum itself reported as failed (`success = false`), which is incorrect payout of `order.fee` to `reward_account`. The failed-delivery record is also discarded (`PendingOrders::remove`) with no distinguishing event, losing any basis for reprocessing or penalizing.

## Likelihood Explanation
The exploit path requires only an unprivileged, `ensure_signed` relayer submitting a genuine proof for a real Ethereum event where the target contract commands reverted (e.g., due to insufficient gas or contract-side revert) — no privileged actor, governance action, or compromised infrastructure is needed. This is directly reachable through the public `submit_delivery_receipt` extrinsic, and the test suite exercising this pallet only covers the `success: true` path, meaning this behavior is untested and would go unnoticed under normal test coverage.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`:
- If `true`: pay the reward and remove the order as today.
- If `false`: settle/remove the order without paying the reward (or apply a distinct reduced/no-reward path), and emit a distinct event (e.g., `MessageDeliveryFailed`) instead of `MessageDelivered`.

## Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce] = { fee > 0, ... }`: [5](#0-4) .
2. The message's commands are dispatched on Ethereum and fail (e.g., revert), so the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer submits a valid Merkle/receipt proof for this event via `submit_delivery_receipt`; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success = false` correctly.
4. `process_delivery_receipt` runs: since `order.fee > 0`, `T::RewardPayment::register_reward` is invoked and the order is removed — identical to the success path, paying the relayer despite the failed delivery.
5. A unit test asserting no reward registration (or a distinct failure event) when submitting a receipt with `success = false` would fail against current code, confirming the bug.

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
