### Title
Reward tokens accrued during zero-stake windows are permanently orphaned in `pallet-asset-rewards` (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` streams reward tokens to stakers at a fixed `reward_rate_per_block`, exactly like the Blend backstop streams emissions at a fixed EPS to reserves. Just as Blend loses a reserve's EPS-derived emissions whenever that reserve's `supply == 0` (because `update_emission_data` skips accrual but the EPS clock still advances), `pallet-asset-rewards`'s `reward_per_token` skips reward-per-token accrual whenever `total_tokens_staked == 0`, while `update_pool_rewards` unconditionally advances `last_update_block` to "now" on every call. This permanently discards the reward-rate-derived value for any zero-stake window, leaving previously-deposited reward tokens stranded in the pool account with no staker entitled to them.

### Finding Description
The core accrual function: [1](#0-0) 

returns the *unchanged* `reward_per_token_stored` when `total_tokens_staked.is_zero()`, meaning none of the reward-rate budget for the elapsed blocks is folded into the accumulator.

Immediately after, `update_pool_rewards` is called and unconditionally resets the reward clock: [2](#0-1) 

This pairing is invoked from every public extrinsic that touches the pool — `stake`, `unstake`, and `harvest_rewards` — via `update_pool_and_staker_rewards`: [3](#0-2) [4](#0-3) [5](#0-4) 

`unstake` is a fully permissionless, unprivileged operation the staker calls on their own tokens, so any staker (or the last remaining staker) can trivially drive `total_tokens_staked` to zero at any time. The pool's reward-asset budget, however, is funded independently and continuously via the permissionless `deposit_reward_tokens` call or direct transfers to the pool account: [6](#0-5) 

Once `total_tokens_staked` returns to zero (e.g. the sole staker unstakes), every subsequent block's worth of `reward_rate_per_block` that would have been earned during that window is silently dropped: no formula anywhere retroactively credits it, and `last_update_block` moves forward past the gap the moment any staker re-enters via `stake`. The tokens corresponding to that gap remain in the pool's `T::AccountId` reward account. They are not attributable to any staker (the reward-per-token math never accounted for them) and can only be swept out via `cleanup_pool`, which itself requires `PoolStakers::iter_key_prefix(pool_id).next().is_none()` — i.e. the pool must be completely empty of stakers: [7](#0-6) 

If the pool has *any* remaining staker (even one who joined after the zero-stake gap), the orphaned reward-asset balance from that gap can never be recovered by the admin (cleanup is blocked) nor claimed by any staker (the math never assigned it to them). It sits permanently in the pool account, unbacked by any entitlement — the same fund-loss/lock pattern as the Blend "gulped emissions lost when reserve supply is 0" report, except here the trigger is a normal, unprivileged `unstake` rather than an admin emissions-config choice.

### Impact Explanation
This is a permanent fund lock of reward-asset tokens that legitimately belong to the reward pool but become unclaimable by any beneficiary once a zero-stake gap occurs and the pool is subsequently repopulated with stakers. It matches the required impact class "permanent user-fund or bridge-state lock" — value that should conserve and settle to a rightful beneficiary is instead stranded with no code path assigning or releasing it while the pool remains active. No malicious peer, validator, relayer, or governance actor is needed: the trigger is a single unprivileged account calling `unstake` on its own stake, an entirely ordinary and expected user action.

### Likelihood Explanation
Any pool with a single staker (common for freshly created pools, or pools that experience full unwind-and-reenter cycles) will hit this the moment that staker calls `unstake` for their full balance and later someone (the same or a different account) calls `stake` again. This requires no special configuration, admin cooperation, or timing precision — it is a routine sequence of public extrinsics. Given `pallet-asset-rewards` pools can trivially reach `total_tokens_staked == 0` (e.g., between the last unstake and the next stake), the likelihood of triggering the orphaned-balance condition is high in real deployments with modest staker counts.

### Recommendation
Track reward accrual for zero-stake windows explicitly instead of silently discarding it. Options: (1) when `total_tokens_staked` is zero, still accumulate an "unassigned rewards" counter (or delay `last_update_block` advancement until the pool has stakers again) so the gap's rewards can either be rolled forward and credited to the first staker who re-enters, or reserved for return to `admin` via `cleanup_pool` even ­while stakers exist for *other*, unrelated periods. At minimum, `cleanup_pool`'s `NonEmptyPool` guard should be relaxed to allow the admin to reclaim only the un-accruable "gap" balance without needing to fully close the pool, mirroring the Blend recommendation of not letting unattributed budget become permanently stuck when the entity meant to receive it currently has no eligible recipient.

### Proof of Concept
1. Admin calls `create_pool` with `reward_rate_per_block = R`, `staked_asset_id`, `reward_asset_id`, and funds the pool account with `deposit_reward_tokens(pool_id, R * N)` for some large `N` blocks of runway.
2. Staker `A` calls `stake(pool_id, amount)` at block `B0`. `pool_info.total_tokens_staked` becomes `amount`.
3. At block `B1`, `A` calls `unstake(pool_id, amount, None)` for their full stake. `update_pool_and_staker_rewards` correctly accrues rewards for `[B0, B1]` into `reward_per_token_stored`; `total_tokens_staked` becomes `0`; `last_update_block = B1`.
4. Blocks pass with `total_tokens_staked == 0` from `B1` to `B2` (no extrinsic calls the accrual logic in this window since no one is staked).
5. Staker `B` calls `stake(pool_id, amount2)` at block `B2`. `reward_per_token` is called with `pool_info.total_tokens_staked == 0` (pre-update value from storage), hits the `is_zero()` branch, and returns `reward_per_token_stored` unchanged — none of `R * (B2 - B1)` reward-asset budget is folded in. `update_pool_rewards` then sets `last_update_block = B2`, permanently closing off that window.
6. `R * (B2 - B1)` worth of reward-asset tokens remain in the pool account, unbacked by any `reward_per_token_stored` increment. As long as staker `B` (or any other staker) remains in the pool, `cleanup_pool`'s `ensure!(stakers.is_none(), Error::<T>::NonEmptyPool)` blocks the admin from reclaiming this specific residual balance — it is permanently orphaned while the pool stays active.

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

		pub fn unstake(
			origin: OriginFor<T>,
			pool_id: PoolId,
			amount: T::Balance,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Check the staker has enough staked tokens.
			ensure!(staker_info.amount >= amount, Error::<T>::NotEnoughTokens);

			// Unfreeze staker assets.
			T::AssetsFreezer::decrease_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_sub_assign(amount)?;
			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_sub_assign(amount)?;

			if staker_info.amount.is_zero() && staker_info.rewards.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			// Emit event.
			Self::deposit_event(Event::Unstaked { caller, staker, pool_id, amount });

			Ok(())
		}

		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
