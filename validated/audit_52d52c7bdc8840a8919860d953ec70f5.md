### Title
Missing slippage protection (no minimum-expected-amount check) in `ExchangeWithdrawActuator` allows front-run sandwich losses when reducing exchange liquidity - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawContract`, used to remove liquidity from a TRON Bancor-style `Exchange` pair, only carries a `token_id` and `quant` (the amount of one side to withdraw) but has no `expected`/minimum-out field for the calculated `anotherTokenQuant` the withdrawer will receive of the paired token [1](#0-0) . This is unlike `ExchangeTransactionContract`, which does include an `expected` field that is explicitly checked against the trade output before execution [2](#0-1) .

### Finding Description
In `ExchangeWithdrawActuator.execute()`, `anotherTokenQuant` (the counter-asset amount returned to the withdrawer) is computed purely from the pool's *current* `firstTokenBalance`/`secondTokenBalance` ratio at execution time via a proportional multiply/divide, with no lower bound supplied by the caller: [3](#0-2) 

`doValidate()` only checks that `anotherTokenQuant` is `> 0`, that the exchange has enough balance, and a small "precision" tolerance check — it never compares `anotherTokenQuant` against any caller-supplied minimum, because the contract type provides none: [4](#0-3) 

By contrast, `ExchangeTransactionActuator` (a swap, i.e. adding to the pool on one side and buying the other) does enforce a user-supplied `expected` minimum before allowing the trade to proceed: [5](#0-4) 

This asymmetry is the direct analog of the reported Uniswap V3 issue: `decreaseLiquidity()` there has `amount0Min`/`amount1Min` hard-coded to `0`, while here `ExchangeWithdrawContract` structurally has no minimum-output field at all for the reduce-liquidity path, even though the sibling swap-path (`ExchangeTransactionContract`) does enforce one.

Since the pool ratio (`firstTokenBalance`/`secondTokenBalance`) can be moved arbitrarily between the time an `ExchangeWithdrawContract` is signed/broadcast and the time it is packed into a block, any other account can submit an `ExchangeTransactionContract` (swap) against the same `exchange_id` immediately before the withdraw executes, worsening the ratio the withdrawer receives (classic sandwich/front-run). Because the block producer controls transaction ordering within the block and pending transactions are visible in the mempool/network, this is trivially executable by any unprivileged account issuing ordinary signed transactions — no special privilege beyond being the pool creator (who is the only address authorized to call withdraw at all, verified at doValidate() line 181) is needed to be victimized. [6](#0-5) 

### Impact Explanation
An exchange creator withdrawing liquidity can be forced to receive materially less of the counter-asset than the pool state implied when they signed the transaction, because there is no way to specify (and thus no way for the chain to enforce) a minimum acceptable `anotherTokenQuant`. This is a concrete loss-of-funds vector for the withdrawing account (the actor performing an unauthorized value-extraction against them is any front-running transaction sender), matching the "theft of funds via slippage" impact class validated for the analog report.

### Likelihood Explanation
Likelihood is high: any account can observe a pending `ExchangeWithdrawContract` and submit a competing `ExchangeTransactionContract` on the same `exchange_id` with a higher priority fee/earlier placement to shift the ratio before the withdraw executes — this requires no special permissions, just a standard signed transaction broadcast, exactly the kind of unprivileged actor path in scope.

### Recommendation
Add an `expected`/minimum-out field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`) and enforce `anotherTokenQuant >= expected` in `ExchangeWithdrawActuator.doValidate()`, rejecting the transaction with a `ContractValidateException` if the pool ratio has moved unfavorably beyond the caller's tolerance.

### Proof of Concept
1. Account A (pool creator) observes pool `exchange_id=1` with `firstTokenBalance=100_000_000`, `secondTokenBalance=200_000_000`, and broadcasts `ExchangeWithdrawContract{exchange_id:1, token_id:first, quant:10_000_000}` expecting ~`20_000_000` of the second token, per the ratio computation at [7](#0-6) .
2. Before A's transaction is packed, attacker B submits an `ExchangeTransactionContract` swapping heavily into `secondTokenID`, which is validated purely against B's own `expected` field and executes atomically, moving `secondTokenBalance` down sharply (validated via `exchangeCapsule.transaction(...)` in `ExchangeTransactionActuator`) [5](#0-4) .
3. A's withdraw then executes against the now-skewed ratio; `doValidate()` has no minimum-out check to reject this, so it proceeds and A receives far less than `20_000_000` of the second token, with no on-chain mechanism to have prevented it.
