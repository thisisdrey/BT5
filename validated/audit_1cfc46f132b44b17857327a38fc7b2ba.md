### Title
`mt_resolve_withdraw` accepts an under-reported `used` amount from an attacker-controlled `token`/receiver pair, letting the Verifier refund tokens it no longer custodies - ([File: contracts/defuse/src/contract/tokens/nep245/withdraw.rs])

### Summary
`mt_resolve_withdraw` clamps the `used` value returned by `mt_batch_transfer_call` only from above (`used.0 = used.0.min(amount.0)`), never validating a lower bound. An attacker who deploys and controls the `token` (NEP-245) contract named in `mt_withdraw` can genuinely deliver the full requested amount to their own receiver while lying in the promise result that only a fraction was `used`, causing Defuse to re-credit the sender for tokens that were, in reality, already fully transferred out of Defuse's custody at that token contract.

### Finding Description
Binding claimed broken: for token `"a"`, `amount_debited (100) == amount_delivered_to_receiver_on_real_MT_contract + amount_recredited_to_sender`. The code path:

- `mt_withdraw` → `internal_mt_withdraw` debits the sender's Defuse-ledger balance for `TokenId = Nep245TokenId(token, token_id)` via `self.withdraw(...)` [1](#0-0) , then schedules `do_mt_withdraw` which calls `ext_mt_core::ext_on(token).mt_batch_transfer_call(receiver_id, token_ids, amounts, ..., msg)` [2](#0-1) .
- `mt_resolve_withdraw` then trusts whatever the promise callback from `token` returns as `used`, only capping it from above: `used.0 = used.0.min(amount.0)` and refunds `amount.0 - used.0` back into the sender's Defuse balance via `self.deposit(...)` [3](#0-2) .

Nothing in this callback (nor in `deposit`/`withdraw` in `contracts/defuse/src/contract/tokens/mod.rs`) independently verifies that the refunded amount actually corresponds to tokens that came back into Defuse's real custody at `token` — the entire trust boundary is the JSON payload returned by the `token` contract's `mt_batch_transfer_call`/`mt_on_transfer` resolution.

Attacker exploit: the attacker deploys their own malicious NEP-245 contract `F` and their own receiver contract `R`. They deposit into Defuse from `F` (crediting Defuse-ledger `TokenId(F,"a")=100`, `TokenId(F,"b")=200`, backed by real custody Defuse believes it holds at `F`). They then call `mt_withdraw(token=F, receiver_id=R, token_ids=["a","b"], amounts=[100,200], msg=Some(...))`. Inside `F`'s implementation of `mt_batch_transfer_call`, the attacker's code actually transfers the full 100 of `"a"` to `R` in `F`'s real ledger (so `R` truly holds 100 of `"a"`), but the promise result returned to Defuse's `mt_resolve_withdraw` reports `used=[U128(50), U128(500)]`. The line-243 clamp reduces `"b"`'s inflated `500` down to `200` (no exploit there), but accepts `"a"`'s `50` verbatim since it is below `amount.0=100`. Defuse then re-credits the sender 50 units of `TokenId(F,"a")` via `deposit`, even though `F` never actually returned those 50 units to Defuse's custody — they are sitting with `R`.

Net effect: Defuse's internal ledger now claims 50 more units of `TokenId(F,"a")` than actually remain custodied at `F`, while the attacker's receiver `R` genuinely holds the full 100. This is exactly the scenario the `Rules` explicitly authorize the attacker to construct ("deploy and control their own FT/NFT/MT and receiver contracts"), and none of the listed guards (`assert_one_yocto`, `#[private]`, `#[pause]`, access-control, checked arithmetic) constrain the semantic honesty of the external token contract's resolved `used` value — only an upper-bound clamp exists, with no lower-bound validation against the real amount transferred.

### Impact Explanation
This produces a resolver credit that does not match what actually failed to settle — a Critical-impact category by the stated rules ("a refund or resolver credit that does not match what failed to settle"). It breaks the invariant that the Verifier's aggregate ledger claims for a `TokenId` must never exceed what is actually custodied at the underlying token contract. If any other party ever shares balance under the same `TokenId(F, token_id)` (e.g. is fooled into trusting/depositing into `F`), the attacker's inflated, uncustodied ledger claim can later be withdrawn again, draining real value belonging to that other depositor. Repeatable per withdrawal batch and per token id inside a batch; blast radius scales with how many parties share the attacker-controlled token's `TokenId` namespace.

### Likelihood Explanation
Preconditions are fully attacker-controlled and low-cost: deploy a NEP-245 contract (`F`) and a receiver contract (`R`), deposit into Defuse from `F`, then call `mt_withdraw` with `msg` set (call path) so `mt_batch_transfer_call`'s JSON result feeds `mt_resolve_withdraw`. No privileged role, relayer key, or victim key is required — only standard NEAR contract deployment and a signed `mt_withdraw`/`execute_intents` call. This is fully reproducible in a `near-workspaces` sandbox test.

### Recommendation
Do not trust the external token contract's self-reported `used` amount as the sole source of truth for how much was actually retained by the receiver. Either (a) require `mt_batch_transfer_call` semantics to be verified against an authoritative record of what was actually returned to the Defuse account (e.g., track real balance deltas of the withdrawing account at the token contract before/after, not just the promise-callback JSON), or (b) treat every NEP-245 `token` contract used for withdrawal as fully trusted only if it is on an allow-list, since the correctness of the refund logic in `mt_resolve_withdraw` is otherwise entirely dependent on the honesty of an arbitrary, attacker-deployable contract.
