### Title
Duplicate witness addresses in a `VoteWitnessContract` allow doubled voting-reward payout - ([File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java])

### Summary
`VoteWitnessActuator` does not deduplicate the witness addresses supplied in a single `VoteWitnessContract`. Unlike the TVM-native vote path (`VoteWitnessProcessor`), which explicitly merges votes for the same witness into a `Map<ByteString, Long>` before applying them, the legacy actuator path appends each vote entry directly to the account's repeated `votes` list. This lets a user cast multiple vote entries for the *same* witness address in one transaction, producing duplicate entries in `AccountCapsule`'s votes list. Reward computation later iterates this list per-entry and sums the reward contribution of each entry, so a duplicated witness entry causes the voter's reward to be paid out multiple times for the same underlying vote weight — an analog of the reported `MainRewarder` bug where an unchecked, duplicated array entry is iterated during payout.

### Finding Description
In `VoteWitnessActuator.validate()`, votes are only checked for validity (`witness exists`, `voteCount > 0`) and summed for the tron-power cap; there is no check that `vote.getVoteAddress()` values are unique within the contract: [1](#0-0) 

In `countVoteAccount`, the executor blindly `forEach`s over `voteContract.getVotesList()` and calls `accountCapsule.addVotes(...)` and `votesCapsule.addNewVotes(...)` for every entry, without merging duplicates by address: [2](#0-1) 

Because `addVotes`/`addNewVotes` append to a protobuf repeated field (not a map), submitting the same witness address twice in the contract (e.g. `[ (W, 5), (W, 5) ]`) results in the account's `votesList` containing two separate `Vote` entries for `W`, each with vote count 5 — rather than one merged entry of 10.

By contrast, the TVM-native path explicitly guards against this by merging into a map keyed by vote address before persisting: [3](#0-2) 

The reward computation in `MortgageService.computeReward` (and the TVM-equivalent `VoteRewardUtil.computeReward`) simply iterates `accountCapsule.getVotesList()` and, for each entry, adds `deltaVi * userVote` to the total reward: [4](#0-3) [5](#0-4) 

Since the loop has no deduplication and simply sums per-entry, two entries for the same witness with the same vote counts effectively double that witness's contribution to the voter's reward — even though the voter's `tronPower` was only ever used to back a single vote weight for that witness.

### Impact Explanation
This allows a voter to inflate their own delegation/voting reward beyond what their staked `tronPower` legitimately supports, by simply splitting their vote for one witness into multiple entries in the same `VoteWitnessContract` transaction. Because `MortgageService.withdrawReward`/`VoteRewardUtil.withdrawReward` credit `allowance`, which is later paid out as real TRX balance via `WithdrawBalanceContract`/native `WithdrawRewardProcessor`, this is a concrete theft-of-funds vector: rewards are drawn from the shared reward pool (funded by block rewards / brokerage) beyond what the voter is entitled to, at the expense of other stakers.

### Likelihood Explanation
The attack requires only a single signed `VoteWitnessContract` (or its TVM-native contract-based path, though that one already deduplicates) referencing the same witness address multiple times — a transaction any unprivileged account holder can broadcast. No special privileges are needed, and the reward accrues automatically over subsequent maintenance cycles, making this straightforward and low-cost to exploit for any voter with any positive `tronPower`.

### Recommendation
In `VoteWitnessActuator`, merge votes by witness address before both the tron-power-sum validation and persistence, mirroring the `HashMap`-based deduplication already implemented in `VoteWitnessProcessor.execute` (lines 54–86). Specifically:
- In `validate()`, accumulate per-witness vote counts in a map and reject duplicate addresses or use the merged sum for both the cap check and downstream persistence.
- In `countVoteAccount()`, aggregate `voteContract.getVotesList()` into a `Map<ByteString, Long>` keyed by vote address (summing counts) before calling `accountCapsule.addVotes` / `votesCapsule.addNewVotes`, so each witness produces exactly one entry.

### Proof of Concept
1. Freeze balance to obtain `tronPower` sufficient to cover `2 * voteCount` for witness `W` (e.g., 10 TRX-power).
2. Submit a `VoteWitnessContract` from the owner account with votes list `[ (W, 5), (W, 5) ]`. `validate()` passes because `sum = 10 <= tronPower`.
3. `countVoteAccount` appends two separate `Vote(W, 5)` entries into `accountCapsule`'s votes list (no merge), as shown at: [6](#0-5) 
4. After maintenance cycles accrue reward for `W`, call `withdrawReward`/`queryReward` for the owner: `MortgageService.computeReward` iterates the votes list and adds `deltaVi * 5` twice (once per duplicate entry), doubling the reward relative to a single merged `Vote(W, 10)` entry, as seen at: [7](#0-6) 
5. The voter withdraws the inflated `allowance` as real TRX balance via the withdraw-reward path.

**Note on verification limits:** I was unable to directly view the source of `AccountCapsule.addVotes` / `VotesCapsule.addNewVotes` in the index to fully confirm they are simple repeated-field appenders (protobuf builder wrappers) rather than map-merging methods; this is inferred from standard java-tron protobuf `Account.votes`/`Votes.newVotes` being `repeated Vote` fields and from the explicit contrasting merge logic present in `VoteWitnessProcessor`. If `addVotes`/`addNewVotes` were found to internally merge by address, this finding would not hold — a Devin session with full file access should confirm the implementation of these two capsule methods before treating this as conclusively validated.

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
