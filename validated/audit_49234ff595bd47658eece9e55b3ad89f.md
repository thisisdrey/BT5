### Title
Per-IP connection rate limiter can be bypassed by never completing the handshake, allowing a single-IP attacker to exhaust `max_concurrent_connections()` slots and starve legitimate clients - (streamer/src/nonblocking/quic.rs)

### Summary
`ClientConnectionTracker::new` gates admission on `qos.max_concurrent_connections()` at `streamer/src/nonblocking/quic.rs:371-379`, and the per-IP `ConnectionRateLimiter::is_allowed` check that runs before it only reflects tokens consumed by **completed** handshakes via `register_connection`. Because `register_connection` is only invoked after a successful handshake in `setup_connection` (`streamer/src/nonblocking/quic.rs:483`), an attacker who deliberately never completes the handshake never gets rate-limited by IP, letting them repeatedly occupy tracker slots up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) each and refill them as fast as the accept loop processes new `Incoming`s.

### Finding Description
The accept loop in `run_server` (`streamer/src/nonblocking/quic.rs:304-411`) performs, per incoming connection:
1. A global rate check: `overall_connection_rate_limiter.current_tokens() == 0` (read-only check, no token consumption here) [1](#0-0) .
2. A per-IP check: `rate_limiter.is_allowed(&incoming.remote_address().ip())` [2](#0-1) .
3. `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())`, which is the only thing standing between an unlimited number of pending connections and admission into the "open connections" slot pool [3](#0-2) .

Critically, `ConnectionRateLimiter::is_allowed` only inspects `current_tokens`; it does not consume any token itself [4](#0-3) . Tokens are only consumed by `register_connection`, which is called in `setup_connection` **after the QUIC handshake completes successfully** [5](#0-4) . If the peer's IP has never registered a successful connection, `self.limiter.current_tokens(ip)` returns `None`, and `is_allowed` returns `true` unconditionally [4](#0-3) .

This means an attacker that intentionally stalls the handshake (e.g., completes only the Initial packet and never sends further Handshake packets, or delays just under `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` = 2s, at `streamer/src/nonblocking/quic.rs:80`) will:
- Pass the per-IP `is_allowed` check every single time, because it never triggers `register_connection`.
- Get a `ClientConnectionTracker` slot (incrementing `stats.open_connections`) as long as `open_connections < max_concurrent_connections()`.
- Get counted in `stats.outstanding_incoming_connection_attempts` for up to 2 seconds (`QUIC_CONNECTION_HANDSHAKE_TIMEOUT`) before `setup_connection`'s `timeout(...)` fires and the `ClientConnectionTracker` is dropped, freeing the slot [6](#0-5) .

Since the attacker never advances to a successful connection, `register_connection` is never called, so the per-IP rate limiter state for that IP is never depleted — the attacker can reopen a fresh stalling connection immediately after each timeout (or open many in parallel, up to the QUIC endpoint's willingness to hand out new `Incoming`s), continuously refilling `open_connections` toward `max_concurrent_connections()`. Once at capacity, legitimate clients hit the `Err` branch and get `refused_connections_too_many_open_connections` incremented and `incoming.refuse()` called (`streamer/src/nonblocking/quic.rs:371-379`), even though the attacker never established a real connection or consumed any resource priced by the per-IP limiter.

The only remaining backstop is the global `overall_connection_rate_limiter` (`MAX_CONNECTION_BURST` = 1000, `TOTAL_CONNECTIONS_PER_SECOND` = 2500, at `streamer/src/nonblocking/quic.rs:73-76`) — but this bucket also is only *read* (`current_tokens() == 0`) before admission and only *consumed* after a successful handshake (`overall_connection_rate_limiter.consume_tokens(1)` in `setup_connection`, `streamer/src/nonblocking/quic.rs:495-508`). So it similarly does not deplete when the attacker never completes handshakes, meaning it does not throttle this particular attack pattern either — the attacker is bounded only by however fast the OS/QUIC endpoint can hand `Incoming` connections to `run_server`'s accept loop, not by either rate limiter.

### Impact Explanation
This is a QoS/connection-tracker starvation issue: a single unstaked attacker IP can keep `stats.open_connections` pinned near `max_concurrent_connections()` (`SimpleQos::max_concurrent_connections` = `max_staked_connections * 5/4`, `streamer/src/nonblocking/simple_qos.rs:422-425`, or the analogous `SwQos` bound) using connections that never contribute real traffic, causing legitimate unstaked/staked peers' `ClientConnectionTracker::new` calls to fail and be refused via `incoming.refuse()`. This matches the "QoS evasion / resource-starvation" bounty category — TPU ingress admission for legitimate clients can be denied without the attacker ever completing a handshake, being staked, or being individually rate-limited for the specific behavior that causes the starvation.

### Likelihood Explanation
Preconditions are minimal and match the unprivileged threat model: an unstaked remote attacker with a single IP that can open QUIC connections to the leader's public TPU port and control how much of the handshake it completes (e.g., a custom UDP/QUIC client that sends only the Initial packet or artificially delays Handshake completion). No stake, no gossip, no operator misconfiguration, no multiple IPs required — the bypass relies purely on `is_allowed` never being decremented before `register_connection`. This is straightforwardly repeatable: each stalled attempt costs the attacker one QUIC Initial packet and ties up a slot for up to 2 seconds, after which it can be immediately replaced.

### Recommendation
Charge the per-IP and global rate limiters at admission time (when `ClientConnectionTracker::new` succeeds, before the handshake even begins) rather than only after a successful handshake, e.g., call `rate_limiter.register_connection`/`overall_connection_rate_limiter.consume_tokens` at `streamer/src/nonblocking/quic.rs:371-379` prior to admitting to the "outstanding" pool, refunding the token if `incoming.accept()` immediately errors. Alternatively, introduce a distinct, tightly-bounded sub-pool specifically for "handshake pending" slots per source IP, so a single IP cannot occupy an unbounded fraction of `max_concurrent_connections()` with unauthenticated/incomplete handshakes.

### Proof of Concept
Integration test plan (in `streamer/src/nonblocking/quic.rs` test module, using existing `setup_quic_server` helpers):
```rust
#[tokio::test(flavor = "multi_thread")]
async fn test_slow_handshake_starves_legit_client() {
    // Configure server with a small max_concurrent_connections (via SimpleQosConfig/SwQosConfig
    // max_staked_connections/max_unstaked_connections) for a tight bound, e.g., 4.
    let SpawnTestServerResult { server_address, stats, cancel, .. } =
        setup_quic_server(None, QuicStreamerConfig::default_for_tests(), <small-limits-config>);

    // Attacker: repeatedly open raw QUIC connections from the SAME IP that send only the
    // Initial packet and never complete the handshake (e.g. drop the Connecting future
    // without ever awaiting a full handshake, or use a client endpoint configured with a
    // deliberately-broken TLS config that stalls post-Initial).
    for _ in 0..N {
        let endpoint = make_stalling_client_endpoint(&server_address).await;
        // do not await connect() to completion; let it run past our observation window
        tokio::spawn(async move { let _ = endpoint.connect(server_address, "localhost").unwrap().await; });
    }

    // Give the accept loop a moment to admit attacker connections into the tracker.
    tokio::time::sleep(Duration::from_millis(200)).await;

    // Legitimate client attempts a normal, fast handshake.
    let legit_result = make_client_endpoint(&server_address, None).await; // or timeout-wrapped connect

    // Assertion: expect stats.refused_connections_too_many_open_connections > 0
    // and/or legit_result fails/times out, demonstrating starvation despite
    // legitimate per-IP/global rate limiters never having been depleted for the attacker IP.
    assert!(stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed) > 0);
}
```
Expected result on the current code: the attacker's stalled connections occupy all `max_concurrent_connections()` slots, `refused_connections_too_many_open_connections` increments for the legitimate client, and `stats.connection_rate_limited_per_ipaddr`/`connection_rate_limited_across_all` remain at 0 for the attacker's IP, confirming the rate limiters never engaged.
