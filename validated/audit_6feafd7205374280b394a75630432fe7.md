### Title
Contract accounts in the airdrop merkle tree can never claim their allocation - ([File: contracts/utils/RecurringAirdrop.sol](contracts/utils/RecurringAirdrop.sol))

### Summary
`RecurringAirdrop.claim()` binds the merkle leaf and the payout destination to `msg.sender`, with no way for a third party to claim on behalf of another account. Any contract address included in a distribution leaf (multisigs without arbitrary-call support, smart wallets, other protocol contracts) cannot call `claim()` itself, and no one else can trigger the claim for it. Its allocation is permanently frozen. `MetAirdrop` inherits the same `claim()` and additionally routes rewards through `ESMET.lockFor()`, which contract recipients may also be unable to manage.

### Finding Description
In `RecurringAirdrop.claim()` the leaf is computed as `keccak256(abi.encodePacked(msg.sender, amount_))` and the reward is sent to `msg.sender` [1](#0-0) . There is no `account_` parameter, so an EOA cannot submit a proof for a contract's leaf — the proof would only verify against the caller's own address. Unlike the rest of the protocol, this contract does not use `SynthContext`/`Operator.execute`, so the meta-sender path cannot be used to claim on a contract's behalf either. `MetAirdrop._transferReward` then locks claimed MET into esMET via `ESMET.lockFor(to_, ...)` [2](#0-1) , meaning even a contract that could call `claim()` must also be able to interact with esMET's unlock flow. Because `claimed[account]` accumulates across root updates, the inability persists for every future distribution as well.

### Impact Explanation
Any contract address captured in a merkle leaf permanently loses its entire airdrop allocation: funds remain in the airdrop contract and can never be released to the entitled account (no admin rescue path exists for claiming on behalf either — `sweep` is governor-only and does not fix per-account accounting). This is permanent freezing of user funds, matching the TrufMigrator bug class exactly.

### Likelihood Explanation
Airdrop snapshots are taken over token-holder sets, which naturally include contract addresses (Gnosis Safes without the claim module loaded at signing time, vesting contracts, multisigs, other protocols' treasuries). No attacker action is needed; the loss is structural for any such leaf. Likelihood depends on whether any leaf is a contract unable to self-call, which is a common occurrence in token-holder distributions.

### Recommendation
Add an `account_` parameter to `claim()` so anyone can trigger a claim for any leaf while the reward still goes to the leaf's owner:

```solidity
function claim(address account_, uint256 amount_, bytes32[] calldata proof_) external nonReentrant {
    bytes32 _leaf = keccak256(abi.encodePacked(account_, amount_));
    ...
    _transferReward(account_, _claimable);
}
```

This is safe because claiming is strictly beneficial to the leaf owner (or, for `MetAirdrop`, owners who do not want esMET locking can be given a recipient parameter).

### Proof of Concept
Hardhat test sketch:

```ts
// Deploy a contract that cannot make arbitrary calls (e.g., a bare receiver contract
// or a smart wallet without a claim path).
const recipientContract = await ethers.deployContract("NonCallableRecipient");

// Build a merkle tree whose leaf is (recipientContract.address, amount)
const leaf = keccak256(abi.encodePacked(recipientContract.address, amount));
const root = /* tree root */;
await airdrop.connect(governor).updateMerkleRoot(root, proofsFileHash);

// 1) The contract itself cannot call claim() — it has no function to do so.

// 2) A third party attempting to claim on its behalf fails proof verification,
//    because the leaf binds msg.sender:
await expect(
  airdrop.connect(helper).claim(amount, proofForRecipientContract)
).to.be.revertedWithCustomError(airdrop, "InvalidProof");

// 3) The allocation is stuck: recipientContract's leaf exists, claimed[] is 0,
//    but no EOA can ever produce a valid proof for it.
expect(await airdrop.claimed(recipientContract.address)).to.eq(0);
```

Note: the `InvalidProof` revert in step 2 demonstrates the constraint directly — the proof is valid for `recipientContract` but the contract re-derives the leaf from `msg.sender`.

```text
    function claim(uint256 amount_, bytes32[] calldata proof_) external nonReentrant {
        if (merkleRoot == bytes32(0)) revert NothingToClaim();

        bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
        if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();

        uint256 _claimable = amount_ - claimed[msg.sender];
        if (_claimable == 0) revert NothingToClaim();

        claimed[msg.sender] += _claimable;

        _transferReward(msg.sender, _claimable);

        emit RewardClaimed(msg.sender, _claimable);
    }
```

```text
        uint256 _end = updatedAt + lockPeriod;

        if (_end < block.timestamp) {
            MET.safeTransfer(to_, amount_);
            return;

        token.safeApprove(address(ESMET), amount_);
        ESMET.lockFor(to_, amount_, _remainLockPeriod);
    }
```
