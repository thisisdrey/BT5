### Title
Malicious data-url peer can serve mismatched attachment bytes, causing `resolve_attachment` to use the wrong hash and permanently drop the real attachment - (File: stackslib/src/net/atlas/download.rs)

### Summary
When `AttachmentsBatchStateMachine::DownloadingAttachment` receives an HTTP 200 response for an `AttachmentRequest`, `AttachmentsBatchStateContext::extend_with_attachments` decodes the response and stores the returned `Attachment` bytes without ever checking them against the `content_hash` that was actually requested. Later, `AttachmentsDownloader::run` resolves the batch entry using `Hash160` of the *received* bytes rather than the requested hash, so a malicious/compromise data-url can serve unrelated (but valid-JSON) bytes to keep the real attachment's batch entry unresolved until retries are exhausted and the batch is dropped.

### Finding Description
The requested equality is `resolved_hash == requested_content_hash`. Tracing the code:

- `AttachmentsBatchStateContext::get_prioritized_attachments_requests` builds an `AttachmentRequest` carrying the exact `content_hash` it wants [1](#0-0) .
- The request is issued and, on success, `extend_with_attachments` decodes the HTTP response via `decode_atlas_get_attachment()` and inserts `response.attachment` into `self.attachments: HashSet<Attachment>` — the `request` (and its `content_hash`) is discarded here, with no comparison to `attachment.hash()` [2](#0-1) .
- `decode_atlas_get_attachment` itself performs no hash validation — it merely JSON-deserializes the body into a `GetAttachmentResponse { attachment }` [3](#0-2) .
- In `AttachmentsDownloader::run`, when the state machine reaches `Done`, the code iterates `context.attachments.drain()` and calls `context.attachments_batch.resolve_attachment(&attachment.hash())` — i.e., it resolves using the hash of whatever bytes were actually received, not the hash that was originally requested [4](#0-3) .

Because a malicious peer that owns the resolved data URL for the batch can return any JSON body of the form `{"attachment": "<hex>"}` for the GET `/v2/attachments/<hash>` request path, it can serve bytes `Y` whose `Hash160::from_data(Y)` differs from the requested `X.content_hash`. The response is accepted as a success (`state.succeeded.insert(request, Some(response))` after only checking HTTP status != 404) [5](#0-4) , decoded without hash verification, and `resolve_attachment(hash(Y))` is invoked instead of `resolve_attachment(X.content_hash)`. The real batch entry for `X` therefore remains unresolved, `has_fully_succeed()` stays false, `bump_retry_count()` increments each round, and once `retry_count >= max_attachment_retry_count` the batch is dropped with the log "Atlas: dropping batch ... retries count exceeded" [6](#0-5) .

No existing guard catches this: there is no comparison anywhere between the `AttachmentRequest.content_hash` and the decoded `Attachment`'s actual hash before it is used to resolve the batch entry.

### Impact Explanation
A remote peer that legitimately serves as a data-url source for a batch (reachable simply by being an outbound sync peer with a `data_url` returned by `network.get_data_url`) can cause a specific, real, valid BNS attachment to be permanently marked unavailable/dropped from the node's Atlas download queue, without ever needing to forge signatures or bypass any auth. This matches "High - attachment/BNS mismatch" impact: state (the BNS attachment resolution) that no canonical activity actually failed to produce is nonetheless treated as permanently unresolved by the victim node. The attacker does not corrupt the AtlasDB with wrong data (since `Attachment::hash()` is used as the storage key so `insert_instantiated_attachment` stores `Y` under `hash(Y)`, not under `X`), but the victim's queue for the real `X` never gets satisfied and is discarded after `max_attachment_retry_count` retries.

### Likelihood Explanation
The attacker only needs to run/control a peer whose advertised `data_url` is used for a batch and needs to be selected among `get_outbound_sync_peers` — a normal, unprivileged operating condition for any node participating in Atlas sync. It requires no secret, no signature forgery, and can be repeated on every batch cycle involving that data-url, deterministically starving the attachment. This is remotely triggerable by returning a crafted valid-JSON HTTP body to a `GET /v2/attachments/:hash` style request.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, verify `Hash160::from_data(&response.attachment.content) == request.content_hash` before inserting into `self.attachments`; if the hash mismatches, treat it as a failed/faulty response (`report.bump_failed_requests()` and/or mark the peer faulty) instead of silently accepting it.

### Proof of Concept
Rust unit test in `stackslib/src/net/atlas/download.rs` (or `tests.rs`):
1. Construct an `AttachmentsBatch` tracking one instance with `content_hash = X = Hash160::from_data(b"real-content")`.
2. Build an `AttachmentRequest { content_hash: X, .. }` and simulate a `BatchedRequestsResult` with `succeeded` containing this request mapped to a fabricated `StacksHttpResponse` whose JSON body is `GetAttachmentResponse { attachment: Attachment::new(b"attacker-content".to_vec()) }` (`Y != X`).
3. Call `AttachmentsBatchStateContext::extend_with_attachments` with this result, then simulate `AttachmentsDownloader::run`'s `Done` handling logic: for each attachment in `context.attachments`, call `attachments_batch.resolve_attachment(&attachment.hash())`.
4. Assert `attachments_batch.has_fully_succeed()` is still `false` (since `resolve_attachment` was invoked with `hash(Y)`, not `X`).
5. Repeat the retry loop `max_attachment_retry_count` times to show the batch is ultimately dropped (matching the "Atlas: dropping batch ... retries count exceeded" log path) while the entry for `X` was never resolved.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn decode_atlas_get_attachment(self) -> Result<GetAttachmentResponse, NetError> {
        let contents = self.get_http_payload_ok()?;
        let contents_json: serde_json::Value = contents.try_into()?;
        let resp: GetAttachmentResponse = serde_json::from_value(contents_json)
            .map_err(|_e| NetError::DeserializeError("Failed to load from JSON".to_string()))?;
        Ok(resp)
    }
