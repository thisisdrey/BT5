### Title
`deposit` with `amount = u1` is a valid minimal-capital trigger for the `accrue` underflow once drift exists - (`File: local-testing/contracts/vault/vault-stx.clar` and sibling vault contracts)

### Summary
`accrue`'s internal expression `(- (total-assets-preview) reserve-inc)` is computed entirely from pre-existing vault state (`principal-scaled`, `index`, `total-borrowed`, `assets`, `fee-reserve`) and never references the caller-supplied `amount` [2](#0-1) . Because `deposit` calls `(try! (accrue))` unconditionally before consuming `amount`, a `deposit` call with `amount = u1` is exactly as capable of tripping the underflow as a deposit of any other size, once the underlying drift/low-reserve state exists.

### Finding Description
`accrue` computes:
```
old-debt = scaled-principal * idx / PRECISION
new-debt = scaled-principal * next-idx / PRECISION
debt-delta = max(0, new-debt - old-debt)
reserve-inc = debt-delta * fee-reserve / BPS
treasury-lp = if reserve-inc > 0: reserve-inc * total-supply / (total-assets-preview - reserve-inc) else 0
``` [2](#0-1) 

`total-assets-preview` is `current-assets (var-get assets) + max(0, debt-preview - total-borrowed)` [3](#0-2) . Algebraically, `total-assets-preview - reserve-inc = current-assets + (old-debt - total-borrowed) - (reserve-inc - debt-delta) + ...`; the key reduction shows the subtraction goes negative whenever `current-assets` (actual on-hand cash in the `assets` var, as opposed to lent-out principal) is smaller than `reserve-inc`, which happens when most liquidity has been borrowed out (`current-assets` near zero) and/or `total-borrowed` has drifted close to or above the true `debt-preview` (via repeated small `borrow`/`repay`/`redeem` rounding), so the `interest` term collapses toward `0` while `debt-delta`/`reserve-inc` remain positive from index accrual since `last-update`.

Since this expression is state-only (no dependency on the `amount` argument passed into whichever public function calls `accrue`), any subsequent call to `accrue` — through `deposit`, `redeem`, `system-borrow`, `system-repay`, or even `transfer` (which also calls `(try! (accrue))` at line 754) [4](#0-3)  — will hit the exact same underflow and abort with the same Clarity runtime error, regardless of the argument values supplied. `deposit`'s `let`-binding order confirms `accrue` executes before `amount`, `min-out`, or any deposit-specific check is evaluated [5](#0-4) . Therefore `deposit u1 u0 tx-sender` reaches the vulnerable subtraction identically to a deposit of any larger amount, and no existing `asserts!` (pause checks, `ERR-AMOUNT-ZERO`, `ERR-SLIPPAGE`, `ERR-SUPPLY-CAP-EXCEEDED`) runs before `accrue`, so none of them can intercept or prevent the abort.

### Impact Explanation
Once the underflow condition is present, every public entry point in the vault that calls `accrue` (`deposit`, `redeem`, `system-borrow`, `system-repay`, `transfer`) unconditionally reverts, since Clarity aborts on uint subtraction underflow with no recovery path inside the contract. This is a permanent, protocol-wide freeze of the vault (Critical - permanent freezing of funds), affecting every existing depositor/borrower, not just the caller who triggers it.

### Likelihood Explanation
This specific sub-question establishes that the *cost of the triggering call itself* is negligible (a `u1` deposit, essentially free besides gas), independent of the size of the drift-inducing prior operations. This materially increases the attack's feasibility: even if crafting the drift state via `borrow`/`repay`/`redeem` cycles requires some capital or many iterations of tiny-amount operations, the final "detonator" call costs the attacker essentially nothing and is repeatable by any unprivileged principal with a funded wallet. This is not a capital-scaling attack — it is a state-scaling attack, decoupling attacker cost from protocol-wide impact.

### Recommendation
In `accrue`, guard the subtraction so `treasury-lp` mint is skipped (rather than the whole function aborting) whenever `reserve-inc >= total-assets-preview`, e.g.:
```clarity
(treasury-lp (if (and (> reserve-inc u0) (> (total-assets-preview) reserve-inc))
                 (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc))
                 u0))
```
Additionally, audit and fix the root-cause rounding/drift between `principal-scaled`/`index`-derived debt and `total-borrowed` in `system-repay` (and `redeem`) so `total-borrowed` cannot drift above true debt over repeated small operations, since that drift is what collapses the `interest` term to zero and enables `reserve-inc` to exceed `total-assets-preview` even with otherwise-healthy `current-assets`.

### Proof of Concept
Clarinet/vitest simnet plan (local fork):
1. Deploy vault, initialize, set a low `fee-reserve`/borrow rate to allow controlled interest accrual.
2. Deposit a moderate amount to seed `assets`.
3. `system-borrow` most of the available liquidity so `current-assets` (`var-get assets`) is left near zero.
4. Perform repeated small `system-repay` calls (dust amounts) interleaved with `mine-block`/time advancement to accumulate rounding drift between `total-borrowed` and the true `principal-scaled`-derived debt, checking via a read-only helper (e.g., a test-only wrapper exposing `total-borrowed` vs `total-debt`) that `total-borrowed` approaches or exceeds `debt-preview`.
5. Advance blocks/time further so `next-index` produces a nonzero `debt-delta` (and thus `reserve-inc > 0`) on the next `accrue` call, while `current-assets` remains below `reserve-inc`.
6. Call `deposit(u1, u0, tx-sender)` from an unprivileged test wallet.
7. Assert the call aborts with a Clarity runtime underflow error (not a normal `err` response) — confirmed by simnet reporting a runtime panic rather than an `(ok ...)`/`(err ...)` result.
8. Assert that subsequent calls to `deposit`, `redeem`, `system-borrow`, and `system-repay` (from any account) also abort identically, proving permanent freeze.

Note: full confirmation that the "drift" precondition (`total-borrowed` exceeding true `debt-preview`) is actually reachable through realistic `borrow`/`repay`/`redeem` sequences requires inspecting `calc-principal-ratio-reduction` and `mul-div-down`/`mul-div-up` rounding directions, which were not fully retrieved in this session; this should be verified in the simnet PoC before treating the precondition as proven, but the finding in this question — that once drift exists, a `u1` deposit is a fully sufficient and negligible-cost trigger — is directly supported by the code shown above.
