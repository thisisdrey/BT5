### Title
Unbounded array allocation from unvalidated length field in TVM precompiled-contract ABI decoding - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The external Thrift advisory describes an "Allocation of Resources Without Limits" bug where a length field taken from untrusted binary input is used to allocate memory without validating it against the actual remaining payload or any sane upper bound. The same bug-class pattern exists in java-tron's TVM precompiled-contract calldata decoders, which read a 256-bit length word straight out of attacker-controlled contract calldata and use it to size a Java array before any bound check is performed.

### Finding Description
`PrecompiledContracts.extractBytesArray` and `PrecompiledContracts.extractBytes32Array` decode ABI-encoded dynamic arrays from precompiled-contract input (`data`/`words`), which is fully attacker-controlled contract calldata reaching these methods through a normal `CALL`/`STATICCALL` to a TVM precompile: [1](#0-0) 

Both methods read `len` via `words[offset].intValueSafe()` — an int decoded directly from a 32-byte word supplied in the transaction's calldata — and immediately allocate `new byte[len][]` (an array of `len` byte-array references) with **no check that `len` is consistent with the actual size of the `words`/`data` buffer and no upper bound on `len` at all**. This mirrors the Thrift issue: a length prefix from untrusted binary data drives a memory allocation with no size-limit enforcement before the allocation happens.

`extractSigArray` has the identical pattern: [2](#0-1) 

Compare this to the RLP decoder in the same codebase (`framework/src/main/java/org/tron/core/capsule/utils/RLP.java`), which explicitly calls `verifyLength(length, msgData.length - pos - lengthOfLength)` before any allocation: [3](#0-2) 

and to `ContractEventParser.subBytes`, which bounds-checks `start`/`length` against `src.length` before allocating: [4](#0-3) 

The precompiled-contract array extractors lack this equivalent guard — `len` is taken from `words[offset].intValueSafe()` as a raw 32-bit-attacker-controlled integer, and `new byte[len][]` is allocated up front, before the loop that would normally fail on out-of-bounds `words[offset + i + 1]` access.

### Impact Explanation
If `len` can reach values on the order of hundreds of millions (bounded only by `intValueSafe()`'s int range, since a DataWord is a 256-bit value truncated/clamped to an int), the JVM will attempt to allocate a reference array of that size (`new byte[len][]` allocates `len * 8` bytes just for the reference array on a 64-bit JVM, i.e. up to ~16GB for `len` near `Integer.MAX_VALUE`) before the code ever touches `data`/`words` again. This can trigger an `OutOfMemoryError` on the node processing the transaction, which — depending on where/how it propagates in the TVM execution path — can crash or hang the full node/validator process, i.e., a node-crash/halt condition reachable by any account able to submit or trigger execution of a `TriggerSmartContract` that calls into the affected precompile.

### Likelihood Explanation
Reachability requires only a signed `TriggerSmartContract` transaction (or an internal `CALL`) that invokes the TVM precompile(s) using these helpers with crafted calldata containing a large length word at the relevant offset — no special privilege, SR/witness status, or victim contract cooperation is needed. The energy-metering check in `callToPrecompiledAddress` (`actuator/src/main/java/org/tron/core/vm/program/Program.java:1734`) is performed based on `contract.getEnergyForData(data)` *before* `execute(data)` runs, but whether that energy computation itself bounds `len` for these particular decoders was not confirmed within the available context — the `execute()` path that calls the vulnerable extractor could still be reached with energy sufficient to pass a cheap pre-check while the extractor performs an oversized allocation. I was not able to fully verify, from the indexed code, which specific precompiled contract(s) invoke `extractBytesArray`/`extractBytes32Array`/`extractSigArray` in their `execute()` methods, nor confirm the exact energy-cost formula guarding them, since the surrounding context (lines beyond ~503 and the callers) was not retrieved in the available search results before the iteration budget was exhausted.

### Recommendation
Add explicit bound checks in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` (and any similar decoders) analogous to `RLP.verifyLength`/`ContractEventParser.subBytes`: validate that `len` is non-negative and consistent with the number of remaining `words`/bytes in `data` (e.g., `offset + 1 + len <= words.length`) before allocating `new byte[len][]`, and reject with `Pair.of(false, EMPTY_BYTE_ARRAY)` otherwise. Additionally verify that `getEnergyForData` for the precompiles calling these helpers charges energy proportional to the *declared* length before any allocation occurs, so a cheap calldata cannot trigger an outsized allocation.

### Proof of Concept
Concrete PoC could not be fully constructed without confirming the specific precompiled contract(s) (e.g. `ValidateMultiSign`/`BatchValidateSign`, referenced in nearby test files such as `framework/src/test/java/org/tron/common/runtime/vm/ValidateMultiSignContractTest.java`) that call `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, since their `execute()` bodies and exact calldata layout beyond line 503 were not retrieved. Conceptually: craft a `TriggerSmartContract` calldata word at the `offset` position consumed by one of these helpers to an extremely large 32-bit value (e.g. `0x7FFFFFFF`), submit it as calldata to the affected precompile address, and observe the node attempt `new byte[0x7FFFFFFF][]`, causing an `OutOfMemoryError` during transaction execution.

  protected static byte[] subBytes(byte[] src, int start, int length) {
    if (ArrayUtils.isEmpty(src)) {
      throw new OutputLengthException("source data is empty");
    }
    if (start < 0 || start >= src.length || length < 0 || length > src.length - start) {
      throw new OutputLengthException(

    }

    System.arraycopy(src, start, dst, 0, length);
