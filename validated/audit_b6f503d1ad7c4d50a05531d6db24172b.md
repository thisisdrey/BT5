## Title
Terminal relay endpoint trusts attacker-supplied `RelayFromAddr` instead of the authenticated peer identity - ([File: relay_manager.go])

### Summary
`relayManager.handleCreateRelayRequest` binds the relay's `PeerAddr` to `from := protoAddrToNetAddr(m.RelayFromAddr)`, a value taken directly from the attacker-controlled `NebulaControl` payload, without ever checking that `from` equals `h.vpnAddrs[0]`, the vpn address that was actually cryptographically bound to `h` during the Noise handshake and certificate verification. This mirrors the 1inch `notifyFor` bug class: a privileged state-mutating operation is keyed by an arbitrary attacker-chosen identity parameter instead of the caller's own authenticated identity.

### Finding Description
When a peer wants to reach a target through a relay, it sends a `NebulaControl_CreateRelayRequest` containing `RelayFromAddr` (claimed initiator) and `RelayToAddr` (target). `HandleControlMsg` only validates that these fields are non-nil [1](#0-0) , then dispatches to `handleCreateRelayRequest`, which reads `from` straight out of the message: [2](#0-1) 

The only sender-identity check performed is that `from` is not one of *my own* vpn addresses (self-relay guard): [3](#0-2) 

There is no check that `from == h.vpnAddrs[0]` — i.e., that the claimed "relay-from" identity actually matches the identity of the authenticated `HostInfo h` that sent this control packet (a HostInfo whose identity was established via `handleIncomingHandshake`/cert verification, see `handshake_manager.go` `continueHandshake`). When I am the relay target, the code creates/completes relay state keyed to the attacker-chosen `from` but associated with the real (already-authenticated) `HostInfo h`: [4](#0-3) 

`AddRelay` stores `PeerAddr: vpnIp` (i.e., the attacker-supplied `from`) on `relayHostInfo.relayState` (which is `h`, the attacker's real hostinfo): [5](#0-4) 

This is structurally identical to the reported bug class: an operation intended to update/authorize state "for account X" instead trusts an unverified caller-supplied `X` rather than the caller's own verified identity (`balanceOf(msg.sender)` vs. `balanceOf(account)` in the original report; here, `h.vpnAddrs[0]` vs. attacker-declared `from`).

### Impact Explanation
Because relay routing on the forwarding/decryption path is driven by `PeerAddr` (`hostinfo.relayState`) rather than by the cryptographically verified vpn address of the connecting peer, an authenticated-but-untrusted peer can register itself in a relay's `Relays`/`relayState` tables as the relay endpoint for an arbitrary victim vpn address it does not own. Any subsequent lookup by `PeerAddr` (e.g. `QueryVpnAddrsRelayFor` used in `outside.go`'s `handleOutsideRelayPacket` `ForwardingType` branch) will resolve traffic addressed to that victim's address to the attacker's `HostInfo`, causing the relay to route/decrypt-and-forward victim-destined relay traffic to the attacker instead of the real victim — a remote state-poisoning condition affecting the relay's routing table that can enable traffic misdirection/interception for arbitrary claimed vpn addresses, without requiring the attacker to hold a certificate for the victim's address.

### Likelihood Explanation
Any node that already has a valid, CA-signed certificate and can complete a normal handshake with a relay node (a standard, unprivileged interaction, `relay.am_relay: true` is a common deployment setting) can trivially send a crafted `header.Control` / `NebulaControl_CreateRelayRequest` message with an arbitrary `RelayFromAddr`. No race condition, timing, or additional bypass is required beyond crafting the protobuf payload, making this straightforward to trigger.

### Recommendation
In `handleCreateRelayRequest` (and analogously in `handleCreateRelayResponse`/`EstablishRelay`), reject the request unless the claimed `RelayFromAddr` matches the authenticated peer's own vpn address(es), i.e. add a check such as `if !slices.Contains(h.vpnAddrs, from) { discard }` before using `from` to create or complete relay state. Only the authenticated `h.vpnAddrs` value derived from the verified handshake/certificate should ever be trusted as the relay-from identity; the message field should, at most, be used for logging/diagnostics.

### Proof of Concept
1. Attacker `A` (holding a valid CA-signed cert for vpn address `A_ip`) establishes a normal tunnel to relay node `R` (`relay.am_relay: true`).
2. `A` sends a `header.Control` packet containing `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: victim_ip, RelayToAddr: R_ip, InitiatorRelayIndex: idx}` where `victim_ip` is any arbitrary vpn address `A` does not own (not `A_ip`, not `R`'s own address).
3. `R.relayManager.HandleControlMsg` → `handleCreateRelayRequest` sees `target == R`'s address, takes the branch at lines 447-524, and calls `AddRelay(rm.l, h /* == A's HostInfo */, f.hostMap, from /* == victim_ip */, ...)`, registering `A`'s HostInfo as the terminal relay endpoint for `victim_ip`.
4. Any peer that subsequently relays traffic through `R` addressed to `victim_ip` (e.g. because `R` is legitimately serving as `victim`'s relay too, or because `R`'s hostmap resolves `PeerAddr == victim_ip` to `A`'s HostInfo) gets forwarded to `A` instead of the real victim, confirming the relay-state poisoning.
