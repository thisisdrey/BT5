### Title
Vault `deposit()` Can Mint Zero Shares While Consuming the Full Deposit Amount — Permanent Loss of Depositor Funds ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
Zest's zToken vaults (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`, and their `local-testing` counterparts) convert a deposited underlying `amount` into shares using a rounding-down formula, exactly the rounding-in-favor-of-the-protocol pattern described in the StUSR report. Unlike `redeem()`, which explicitly guards against a zero-output conversion, `deposit()` has no such guard, so a user can transfer their full underlying `amount` into the vault while receiving zero zTokens in return, permanently losing those funds.

### Finding Description
`convert-to-shares-preview` rounds down when converting an underlying `amount` into shares: [1](#0-0) 

`deposit()` uses this value (`inkind`) as the number of shares to mint, but only enforces a user-supplied `min-out` slippage check — it does **not** assert `inkind > u0`: [2](#0-1) 

Because `min-out` defaults to whatever the caller passes (commonly `u0` when no explicit minimum is desired), if the vault's asset-to-share ratio (`total-assets-preview` / `total-supply-preview`) is high enough — e.g., after enough interest has accrued via `accrue()` and treasury-LP minting — a small enough `amount` will produce `inkind = 0` from `mul-div-down`. The `>= inkind min-out` check trivially passes when `min-out` is `0`, so the transaction proceeds: `receive-underlying` pulls the full `amount` from the depositor, `ft-mint? zft 0 recipient` mints nothing, and `assets` is still increased by the full deposited amount — silently donating the depositor's principal to existing shareholders.

By contrast, `redeem()` in the very same contract explicitly guards against this exact zero-output rounding case: [3](#0-2) 

The absence of the equivalent `ERR-OUTPUT-ZERO` check on the `deposit()` path is the root cause — the same rounding-to-zero hazard that the StUSR report flags for `transfer()`/`transferFrom()` (full input consumed, zero output credited) is reachable here via an ordinary user's own `deposit()` call.

### Impact Explanation
This is a **Critical** impact: permanent, protocol-caused loss of a depositor's own funds. The underlying asset is pulled from the caller and added to `assets`, increasing the value of all existing zToken holders' shares, while the depositor receives zero zTokens and has no path to reclaim the lost principal. Because these zTokens are also used directly as collateral in the market (via `supply-collateral-add`), any integration/aggregator that computes an expected minted-share amount and does not itself defend against zero-share outputs would also be exposed to silently losing user funds during automated deposit flows.

### Likelihood Explanation
This requires no privileged access and is reachable by any ordinary principal calling `deposit()` directly. It becomes more likely as a vault's asset base grows relative to its share supply (via ordinary interest accrual/treasury-LP minting over time on `v0-vault-usdc`, `v0-vault-sbtc`, etc.), making rounding-to-zero achievable with progressively larger (but still small relative to total assets) deposit amounts. It is also more likely for any caller who passes `min-out = u0` (a common default/naive integration pattern), since the existing slippage check offers no protection in that case.

### Recommendation
Add an explicit zero-output guard to `deposit()`, mirroring the one already present in `redeem()`:
```
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
This should be added immediately alongside the existing `deposit()` preconditions in every vault contract (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`), so that a deposit which would mint zero shares reverts instead of silently consuming the depositor's underlying assets.

### Proof of Concept
1. Let a vault's `total-assets-preview` grow substantially larger than `total-supply-preview` (a natural outcome of interest accrual over time via `accrue()`, since `treasury-lp` minting only partially offsets share dilution).
2. A user calls `deposit(amount, u0, recipient)` with a small `amount` such that `mul-div-down(amount, total-supply-preview, total-assets-preview) == u0`.
3. `(>= inkind min-out)` → `(>= u0 u0)` passes.
4. `receive-underlying` transfers the full `amount` from the user into the vault.
5. `ft-mint? zft u0 recipient` mints zero zTokens to the user.
6. `assets` is incremented by the full `amount`.
7. Result: the user's `amount` is fully absorbed into the vault's asset pool with zero corresponding shares issued — a permanent, unrecoverable loss of their deposited funds.
