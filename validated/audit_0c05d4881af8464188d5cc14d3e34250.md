### Title
Unbounded array length from attacker-controlled calldata causes memory-exhaustion DoS in precompiled multisig validators - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray`, `extractBytes32Array`, and the `ValidateMultiSign`/`BatchValidateSign` precompiled contracts read an array-length value straight out of attacker-controlled TVM calldata and use it to size a Java array (`new byte[len][]`) **before** any sanity bound is enforced, unless the `allowTvmSelfdestructRestriction` hard-fork feature is active. This mirrors the ALPINE-CVE-2026-60081 bug class: an unbounded, attacker-supplied index/length value taken from parsed input is used directly to allocate a data structure, letting a remote party force excessive memory consumption.

### Finding Description
`extractBytesArray` and `extractBytes32Array` take `len` directly from a `DataWord` decoded out of the raw call data and immediately allocate an array of that size with no upper bound: [1](#0-0) 

These helpers are invoked from the `ValidateMultiSign` precompile. The `MAX_SIZE` bound check that would normally prevent an oversized allocation is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is true; when it is false, `extractBytesArray` is called unconditionally with the raw, unchecked length, and the `signatures.length > MAX_SIZE` guard only runs *after* the array has already been allocated: [2](#0-1) 

The same pattern repeats in `BatchValidateSign.doExecute`: the `sigArraySize`/`addrArraySize` bound checks against `MAX_SIZE` are gated behind the same feature flag, while `extractBytesArray`/`extractSigArray`/`extractBytes32Array` are called regardless: [3](#0-2) 

Both precompiles are reachable from an ordinary, unprivileged smart-contract call: any account can send a `TriggerSmartContract`/`CALL` whose target address is the well-known precompile address for `validatemultisign`/`batchvalidatesign`, supplying calldata where the length word encoded at the computed offset is a very large integer. Because the bound check that limits this length to `MAX_SIZE` (16) only runs when the `allowTvmSelfdestructRestriction` proposal is activated on the chain, any network (private chain, test network, or a chain where that specific proposal has not yet been enabled) is exposed to unbounded `new byte[len][]` allocation triggered by a single transaction.

### Impact Explanation
An attacker-controlled length value used directly for array allocation can force the node to attempt allocating a very large array of object references in a single TVM call. This is a memory-exhaustion / resource-abuse condition analogous to the referenced CVE (unbounded index used for allocation in a parser), and on an affected node/network it can lead to `OutOfMemoryError` and node instability or crash, which is a legitimate high-severity finding class per the report's own bug class definition (DoS via unbounded allocation from parsed input).

### Likelihood Explanation
Exploitability strictly depends on the `allowTvmSelfdestructRestriction` chain parameter being disabled. Where mainnet TRON has already activated this hard-fork proposal, the length is bounded to `MAX_SIZE` before allocation and the issue does not manifest. On any deployment (private/consortium chain, test network, or a chain where the associated proposal is not yet enabled) where the flag is off, the vulnerable path is trivially reachable by any account issuing a single `TriggerSmartContract` transaction with crafted calldata — no special privilege required.

### Recommendation
Move the `MAX_SIZE` bound checks (and generally, validation that the parsed length is non-negative and reasonably small) so they execute unconditionally, before calling `extractBytesArray`, `extractSigArray`, or `extractBytes32Array`, regardless of the `allowTvmSelfdestructRestriction()` flag state. Additionally, add a hard sanity cap directly inside `extractBytesArray`/`extractBytes32Array`/`extractSigArray` themselves so that the array-length value read from calldata can never exceed a safe maximum before the array is allocated.

### Proof of Concept
1. Craft calldata for a call to the `ValidateMultiSign` precompiled contract (or `BatchValidateSign`) on a chain/network where `allowTvmSelfdestructRestriction` is not enabled.
2. Set the `DataWord` at the computed signature-array offset (i.e., `words[3]` pointing to a length word for `ValidateMultiSign`, or `words[1]`/`words[2]` for `BatchValidateSign`) to a very large integer value (e.g., close to `Integer.MAX_VALUE`).
3. Broadcast a `TriggerSmartContract` transaction whose `contract_address` is the precompile's dispatch address and `data` is the crafted calldata above, per `PrecompiledContracts.getContractForAddress` dispatch logic [4](#0-3) .
4. During execution, `extractBytesArray`/`extractBytes32Array` executes `new byte[len][]` with the attacker-supplied `len` before the `MAX_SIZE` check runs, causing an oversized allocation attempt [5](#0-4) .

Note: I was unable to fully confirm the exact numeric clamping behavior of `DataWord.intValueSafe()` (its implementation lives in `common/src/main/java/org/tron/common/runtime/vm/DataWord.java`, which my final search pass could not retrieve in full) — this determines the precise maximum array size an attacker can force in one call. This should be verified directly in that file before finalizing severity/PoC sizing.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
