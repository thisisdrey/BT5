### Title
Missing content-hash verification on downloaded attachments allows serving/storing non-canonical BNS attachment data - (File: `stackslib/src/net/atlas/download.rs`)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` inserts a peer-supplied `Attachment` into `self.attachments` purely based on a successful HTTP decode, without ever comparing the attachment's content against the `AttachmentRequest.content_hash` that was requested. This lets any peer answer with arbitrary attachment bytes, which are later stored via `insert_instantiated_attachment` under whatever hash the attacker's bytes produce, unrelated to any on-chain commitment.

### Finding Description
The broken equality is `response.attachment.hash() == request.content_hash`. In `extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`), the code does:
```rust
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
```
No comparison is made between `response.attachment` (or its hash) and `request.content_hash`, even though `request` (the original `AttachmentRequest`) is available in scope and destructured from `results.succeeded.drain()` at line 534. `decode_atlas_get_attachment` (`stackslib/src/net/api/getattachment.rs:159-165`) also performs no such check — it merely JSON-deserializes the body into a `GetAttachmentResponse`.

Downstream, in `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:153-169`), the accepted attachments are processed by computing `attachment.hash()` from the *received* bytes (not the originally requested hash `H`):
```rust
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;
    ...
    context.attachments_batch.resolve_attachment(&attachment.hash())
}
```
Because resolution is keyed by the attacker-controlled bytes' own hash rather than the requested `H`, a malicious peer can supply `bytes_X` with `Hash160::from_data(bytes_X) = H' != H`. This gets inserted into `atlasdb` as a validated attachment under `H'` (which is disconnected from any on-chain name-operation commitment), while the actual pending instance for `H` remains unresolved and gets retried/eventually evicted. There is no signature or origin check anywhere in this path (`AttachmentRequest.sources` is just a URL/reliability bookkeeping structure, not a cryptographic origin proof).

### Impact Explanation
This matches the "High" impact category for attachment/BNS mismatch: a remote, unprivileged peer serving arbitrary bytes for a requested content hash results in the node storing "validated" attachment data (`atlasdb.insert_instantiated_attachment`) that was never actually committed by a confirmed name operation on-chain. The requesting node's actual pending instance for `H` never resolves via this path (since resolution matches on the wrong hash), causing legitimate BNS metadata to never be filled in from this peer while the attacker's unrelated data occupies attachment storage. This is a data-integrity issue on the p2p HTTP surface reachable by any peer configured as a "source" in an in-flight `AttachmentRequest`, which merely requires being an outbound sync peer that claims (via its inventory response) to have the attachment.

### Likelihood Explanation
- Preconditions: the node must have a pending unresolved `AttachmentInstance` with `content_hash == H` (this arises naturally from BNS name operations), and the attacker's peer must be selected as a request source, which merely requires the peer to report (via `GetAttachmentsInvResponse`) that it has that page/index bit set — an unauthenticated, self-reported inventory.
- Attacker cost: trivially low — run any peer node, populate its own inventory response to claim it has the attachment, and answer the follow-up `/v2/attachments/<H>` GET with a JSON body of the attacker's choosing.
- Reachable: `/v2/attachments/:hash` is a normal RPC/P2P endpoint, and `AttachmentsInventoryRequest`/`AttachmentRequest` peer selection has no authentication beyond being an outbound sync peer.
- Repeatable: every downloader cycle (`AttachmentsDownloader::run`), for every attachment hash the attacker chooses to lie about.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after decoding the response, compute `response.attachment.hash()` and compare it against `request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed/faulty request (`report.bump_failed_requests()` and/or register the peer as faulty) rather than silently accepting the data. This restores the required equality check before the data is ever persisted via `insert_instantiated_attachment`.

Build an `AttachmentsBatchStateContext` with an `AttachmentRequest { content_hash: H, sources, .. }` and a `BatchedRequestsResult` whose `succeeded` map pairs that request with a `StacksHttpResponse` built via `StacksHttpResponse::decode_atlas_get_attachment`-compatible JSON body containing `Attachment { content: bytes_X }` where `Hash160::from_data(bytes_X) = H' != H`.
