Audit Report

## Title
Unbounded, size-independent `receipt_proof` in Snowbridge `submit` extrinsic allows underpriced computational DoS - (File: `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`)

## Summary
The `submit` extrinsic in `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs` accepts a `Box<EventProof>` whose `Proof.receipt_proof` field is an unbounded `Vec<Vec<u8>>` [1](#0-0)  yet the dispatch weight is a fixed constant computed from a single fixed-size benchmark fixture [2](#0-1) , so the charged weight does not scale with the number/size of proof nodes an unprivileged caller supplies. This lets a signed relayer submit a proof-verification workload whose actual computational cost is decoupled from the declared/charged weight.

## Finding Description
`submit()` is callable by any signed account via `ensure_signed(origin)` [3](#0-2) , and dispatches directly to `T::Verifier::verify(&event.event_log, &event.proof)`, which for the Ethereum beacon-client verifier reaches `verify_receipt_inclusion` → `verify_receipt_proof` [4](#0-3) [5](#0-4) . `Proof.receipt_proof: Vec<Vec<u8>>` carries no `MaxEncodedLen`/`BoundedVec` bound in the primitives crate [1](#0-0) , and `verify_proof` iterates every supplied node, RLP-decoding and hashing it.

The `#[pallet::weight(T::WeightInfo::submit())]` annotation is a fixed constant regardless of the size of `event: Box<EventProof>` [6](#0-5) , and the underlying benchmark only ever exercises `T::Helper::initialize_storage()`, a single fixed-size fixture, never varying `receipt_proof` size or node count [7](#0-6) .

The only practical bound on attacker-supplied `receipt_proof` size is the extrinsic/block length limit. BridgeHub-style runtimes configure `BlockLength` with a 5MB max block size, of which the `Normal` dispatch class gets 75% (~3.75MB) [8](#0-7) [9](#0-8) . That byte-size ceiling is far larger than what the fixed ~60ms weight benchmark accounts for, so an attacker can submit a `submit()` call whose `receipt_proof` contains up to ~3.75MB of filler trie-node bytes while being charged the same fixed weight as a call with a tiny, legitimate proof.

Existing guards reviewed and found insufficient:
- `OperatingMode` halted check and `ensure_signed` only gate *who* can call, not *how large* the proof can be.
- The block/extrinsic length limit bounds absolute size but is not tied to the pallet's declared weight, so the disconnect between "charged compute" and "actual compute" persists up to the multi-megabyte length ceiling.
- No `BoundedVec`/`MaxEncodedLen` exists on `Proof.receipt_proof` to cap node count or per-node size independent of total transaction length.

## Impact Explanation
This matches the accepted impact category "public underpriced work that degrades block production or stalls bridge processing." Because weight for `submit()` is fixed irrespective of proof size, an unprivileged signed account can craft calls whose real CPU cost (RLP decoding and repeated hashing over up to megabytes of attacker-controlled `Vec<Vec<u8>>` data) substantially exceeds the ~60ms weight budget the runtime uses for block-inclusion accounting, potentially causing block-production slowdowns on BridgeHub chains running this pallet.

## Likelihood Explanation
- `submit` requires only a signed origin — no allow-list, governance, or relayer permission is enforced beyond `ensure_signed` [10](#0-9) .
- `receipt_proof` has no pallet-level or primitive-level bound on node count or per-node size [1](#0-0) , so oversized submissions are not rejected at decode time — only the general block/extrinsic length limit applies.
- The benchmark that derives the fixed weight constant never varies proof size, so the constant is not a conservative upper bound for large, adversarial proofs [7](#0-6) .
- The attack is trivially repeatable by any funded account and does not require compromising a relayer, validator, or prover.

## Recommendation
- Make `submit()`'s weight scale with the size/number of `receipt_proof` entries (e.g., `T::WeightInfo::submit(receipt_proof.len(), total_bytes)`), analogous to how message-queue/XCMP pallets scale weight with message size.
- Add an explicit bound on `Proof.receipt_proof` (e.g., `BoundedVec<BoundedVec<u8, MaxNodeSize>, MaxProofNodes>`) so the worst case is both bounded and benchmarkable.
- Extend benchmarks to vary proof size/node count so the declared weight is a genuine upper bound, and apply the same audit to `inbound-queue`, `inbound-queue-v2`, and `ethereum-client` for similar fixed-weight/variable-input mismatches.

## Proof of Concept
1. Build a valid `EventProof`/`Proof.execution_proof` (as in `make_inbound_fixture()`) so `Verifier::verify` reaches `verify_receipt_proof`.
2. Replace `proof.receipt_proof` with a large `Vec<Vec<u8>>` (thousands of large filler byte arrays), sized up to the `Normal` dispatch class's extrinsic length limit (~3.75MB on BridgeHub-style runtimes).
3. Call `InboundQueue::submit(origin, Box::new(forged_event))` from a signed account repeatedly.
4. Measure actual wall-clock time spent in `verify_receipt_proof`/`verify_proof` versus the fixed weight charged by `T::WeightInfo::submit()` (~60ms constant) to demonstrate the size-independence of the charged weight versus proof size.
