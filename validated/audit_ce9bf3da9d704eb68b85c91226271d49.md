### Title
Merging additional freeze/delegate balance overwrites the expiration time unconditionally, allowing earlier-than-intended unfreeze - (File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java)

### Summary
`FreezeBalanceActuator` (the legacy `FreezeBalanceContract` path) and its underlying `DelegatedResourceCapsule` merge helper always **overwrite** the resource's lock-expiration timestamp with the value computed from the *most recent* freeze call, instead of taking the maximum of the old and new expiration times weighted by the combined amount. This is the same root-cause class as the reported `PointsModule._setMintUnlockTime` bug: a merge/average calculation for a "lock until" timestamp that does not correctly account for previously-locked funds, letting a user shorten the effective lock of an already-locked (larger) balance.

### Finding Description
When a user calls `FreezeBalanceContract` more than once for the same resource, the actuator computes a brand-new `expireTime = now + duration` and simply overwrites the stored expiration with it, then adds the new amount to the existing balance: [1](#0-0) 

For the self-freeze branch, `accountCapsule.setFrozenForBandwidth/setFrozenForEnergy(newFrozenBalance, expireTime)` sets the expiry field directly to the newly computed value — there is no comparison against the account's existing (potentially much later) expiry.

For the delegated-resource branch (`receiverAddress` set), the same pattern occurs in `delegateResource()`, which calls `DelegatedResourceCapsule.addFrozenBalanceForBandwidth/addFrozenBalanceForEnergy`: [2](#0-1) 

Both methods add the new balance to the existing balance but **unconditionally replace** `expireTimeForBandwidth`/`expireTimeForEnergy` with whatever expiry was passed in for the latest call — they never take `max(oldExpireTime, newExpireTime)`.

The only guard on the freeze duration is a min/max range check, not a monotonicity check against any prior lock: [3](#0-2) 

Because `minFrozenTime` and `maxFrozenTime` are independent, committee-adjustable `DynamicPropertiesStore` values, a chosen `frozenDuration` anywhere between them is accepted on every call — there is no requirement that a subsequent freeze's duration be at least as long as the time remaining on the previous freeze (contrast this with `DelegateResourceActuator.validRemainTime`, which *does* enforce this for the newer `DelegateResourceContract`/lock-period model): [4](#0-3) 

The legacy `FreezeBalanceContract` path has no equivalent check.

### Impact Explanation
A user can freeze/delegate a large balance for the maximum allowed duration to obtain bandwidth/energy/TRON_POWER weight (and to have a receiver acquire delegated resource weight), then immediately submit a second, small `FreezeBalanceContract` transaction with the minimum allowed duration. Because the expiry is overwritten rather than weighted/maxed, the *entire combined balance* (large + small) inherits the short expiry. The user can then call `UnfreezeBalanceActuator` after only the short duration to withdraw the whole combined balance back to spendable TRX — well before the originally-intended lock period. This lets an account (or its resource-receiving counterpart) redeem locked TRX and reverse resource-weight accounting earlier than the protocol intends, undermining the freeze/lock guarantee that resource weight and voting power correspond to genuinely time-locked TRX.

### Likelihood Explanation
Exploitability depends on `minFrozenTime` differing from `maxFrozenTime` (both are runtime-adjustable dynamic properties controlled by the committee, not hard consensus constants), so the attack surface exists whenever the network allows a range of freeze durations rather than a single fixed value. Given the code path is directly reachable by any account holder via a plain `FreezeBalanceContract`/`UnfreezeBalanceContract` transaction pair with no special privileges, likelihood is assessed as Medium (contingent on current parameter configuration) but the underlying logic flaw itself is unconditionally present.

### Recommendation
In `DelegatedResourceCapsule.addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy`, and in `AccountCapsule.setFrozenForBandwidth`/`setFrozenForEnergy` (self-freeze), the expiration time should be updated to `Math.max(existingExpireTime, newExpireTime)` rather than being unconditionally overwritten, so that adding more locked balance never shortens the effective unlock time of previously-locked funds. Alternatively, enforce a `validRemainTime`-style check (as already done in `DelegateResourceActuator`) in `FreezeBalanceActuator.validate()` requiring the new `frozenDuration` to be at least as long as the remaining time on any existing freeze for that resource/receiver pair.

### Proof of Concept
1. Account A calls `FreezeBalanceContract` with `frozenBalance = 1000 TRX`, `frozenDuration = maxFrozenTime` (e.g., 30 days), `resource = BANDWIDTH`, no receiver. `AccountCapsule.setFrozenForBandwidth(1000 TRX, now+30d)` is stored. [5](#0-4) 
2. Immediately after, Account A calls `FreezeBalanceContract` again with `frozenBalance = 1 TRX`, `frozenDuration = minFrozenTime` (e.g., 3 days), same resource, no receiver. The actuator computes `expireTime = now + 3d` and calls `setFrozenForBandwidth(1001 TRX, now+3d)`, overwriting the stored expiry for the whole 1001 TRX.
3. After 3 days (instead of the originally intended 30), Account A calls `UnfreezeBalanceContract` and successfully withdraws the entire 1001 TRX back to spendable balance, since the stored expiry (`now+3d`) has already passed.

  private void validRemainTime(ResourceCode resourceCode, long lockPeriod, long expireTime,

      throw new ContractValidateException(
