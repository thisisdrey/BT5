### Title
Improper Validation of Array Index in Zip64 Extra Field Attribute Access Leads to Out-of-Bounds Read During Archive/Jar Processing - ([File: src/tools/singlejar/zip_headers.h])

### Summary
`Zip64ExtraField::attr64(int index)` in [1](#0-0)  indexes into the variable-length `attr_[]` array without validating `index` against the field's actual declared `attr_count()`. Multiple call sites in the same header compute this index from unrelated 32-bit size fields rather than from the Zip64 field's own declared payload size, allowing an attacker-crafted archive entry to force a read past the end of the declared Zip64 extra-field payload — the same bug class as CVE-2023-40477 (improper validation of an array index leading to a read past the end of an allocated buffer).

### Finding Description
`CDH::compressed_file_size()`, `LH::uncompressed_file_size()`/`compressed_file_size()`, and `CDH::local_header_offset()` all look up a Zip64 extra field and then call `attr64(index)` where `index` is computed from *other* fields (`compressed_file_size32()`, `uncompressed_file_size32()`), not from the size the Zip64 extra field itself declares (`payload_size()` / `attr_count()`): [2](#0-1) [3](#0-2) 

`Zip64ExtraField::find()` only validates that the *declared* field (header + `payload_size()`) fits inside the extra-fields buffer — it never confirms that `payload_size()` is large enough for the number of attributes the caller intends to read: [4](#0-3) 

Per the ZIP64 spec, a Zip64 extra field must carry an entry for every corresponding 32-bit field that is set to `0xFFFFFFFF`, in a fixed order (uncompressed size, compressed size, offset). Nothing in this code enforces that invariant. A crafted Central Directory Header can set `compressed_file_size32 = uncompressed_file_size32 = 0xFFFFFFFF` (forcing `index = 1` in `compressed_file_size()`) while shipping a Zip64 extra field whose `payload_size` only covers a single 8-byte attribute (`attr_count() == 1`). The resulting `attr64(1)` read is out of bounds of the *declared* field, spilling into whatever bytes follow in the extra-fields/CDH/mmap'd-file buffer.

This is distinct from the existing "malformed extra field" bounds check in `output_jar.cc`, which only validates that each `ExtraField` record (via `ef->size()`) stays inside the outer `extra_fields_length()` region during copy loops (as exercised by `OutputJarSimpleTest.MalformedExtraField`, which `ASSERT_DEATH`s on structurally-invalid fields): [5](#0-4) 

That guard does not run inside `attr64()`, and does not cross-check the number of Zip64 attributes against the 32-bit fields that reference them. A search of the codebase confirms `attr_count()` is used only in its own definition and in unit tests — never as a guard before calling `attr64()` in `zip_headers.h`, `output_jar.cc`, `input_jar.cc`, or `transient_bytes.h`.

The corrupted size/offset value returned by `attr64()` then propagates into size and copy-length computations used for `memcpy`/read operations while merging JAR entries (e.g., `num_bytes`, `copy_from`, `compressed_file_size()`/`uncompressed_file_size()` consumers in `OutputJar::AddJar` and `TransientBytes::ReadEntryContents`/`DecompressEntryContents`), turning a single out-of-bounds index read into a broader out-of-bounds memory access during archive/jar processing.

### Impact Explanation
An attacker who controls the bytes of a `.jar`/`.zip` file that Bazel's `singlejar` tool processes (e.g., a third-party jar consumed via `java_import`, a prebuilt dependency jar fetched through `http_jar`/`http_archive`, or any archive that ends up as an input to a jar-merging action) can craft a Zip64 extra field whose declared payload is smaller than the number of 64-bit attributes the code will index into. This causes `singlejar` to read memory beyond the bounds implied by the archive's own structure, which can crash the build process (denial of service for that build invocation) or corrupt the derived size values used to copy archive entry bytes into the output jar, potentially copying unintended memory content into build outputs. Because the checksum/`sha256`/`integrity` pin on an `http_archive`/`http_jar` only verifies byte-identity of the downloaded file — not the internal structural validity of the ZIP64 metadata — a hostile origin/mirror can serve a byte-for-byte "valid" (hash-matching) archive that still triggers this out-of-bounds access when Bazel/`singlejar` processes it.

### Likelihood Explanation
Exploitation requires the ability to publish or serve an archive/jar (with the crafted Zip64 extra field) that becomes an input to `singlejar`/`ijar`-adjacent zip processing. Any project consuming external `.jar` dependencies (a very common real-world scenario) satisfies this precondition. No special build flags are needed; the vulnerable code path executes unconditionally whenever such an entry's 32-bit size fields signal a ZIP64 extension, on any current release using this header.

### Recommendation
In `Zip64ExtraField::attr64()`, validate `index < attr_count()` before dereferencing `attr_[index]`, and return/propagate an explicit parse error (consistent with the existing "malformed extra field" `diag_errx` pattern) instead of silently reading past the declared payload. Additionally, when resolving `compressed_file_size()`, `uncompressed_file_size()`, and `local_header_offset()`, verify that the Zip64 extra field actually contains an attribute for every corresponding 32-bit field marked `0xFFFFFFFF`, per APPNOTE 4.5.3, rejecting archives where the declared `payload_size()` is inconsistent with the required attribute count.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style reproduction:
1. Construct a ZIP Central Directory Header (and matching Local File Header) with `compressed_file_size32 = uncompressed_file_size32 = 0xFFFFFFFF`.
2. Attach a Zip64 extra field (tag `0x0001`) with `payload_size = 8` (declaring only one 64-bit attribute), instead of the two attributes required when both compressed and uncompressed sizes are marked as 64-bit.
3. Feed this crafted `.jar`/`.zip` as a `--sources` input to `singlejar` (as done in `OutputJarSimpleTest.MalformedExtraField`, [6](#0-5) , but omitting the extra-field-length overflow this existing test targets).
4. Observe that `CDH::compressed_file_size()` computes `index = 1` and calls `attr64(1)`, reading 8 bytes past the field's declared 8-byte payload — verifiable via ASan/valgrind showing a heap-buffer-overflow read, or via a unit test asserting the returned size is garbage/inconsistent rather than triggering a controlled parse error.

class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
