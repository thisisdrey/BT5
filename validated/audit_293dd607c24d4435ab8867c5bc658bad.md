### Title
`ValidateMultiSign` TVM precompile ignores permission type and operations-scope restrictions enforced everywhere else - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` precompiled contract, reachable by any smart contract via the `validatemultisign(address,uint256,bytes32,bytes[])` opcode, authorizes based solely on `weight >= threshold` for a `Permission` fetched by an attacker-supplied `permissionId`. Unlike every other on-chain permission-verification path in java-tron, it never checks that the permission's `type` is `Active`, and it never checks the permission's `operations` bitmap that scopes which contract/operation types a key is allowed to authorize.

### Finding Description
Every genuine transaction-signing permission check in java-tron enforces two things when `permissionId != 0`: (1) the permission must be of type `Active`, and (2) the specific operation being authorized must be present in that permission's 32-byte `operations` bitmap, via `checkPermissionOperations`: [1](#0-0) [2](#0-1) 

The same pattern is repeated in the JSON/HTTP sign-weight helper: [3](#0-2) 

However, `PrecompiledContracts.ValidateMultiSign.execute`, which any TVM contract can invoke to authenticate an address's approval, fetches the permission by ID and checks only accumulated signature weight against the threshold — it never inspects `permission.getType()` and never calls `checkPermissionOperations`/`WalletUtil.checkPermissionOperations`: [4](#0-3) 

This means:
- A key that only holds a narrowly-scoped `Active` permission (operations bitmap restricted to, e.g., `TransferContract` only) can be used through this precompile to "validate" approval for arbitrary purposes that a calling smart contract gates on `validatemultisign` — the operations-bitmap restriction the account owner configured is silently ignored.
- A `Witness` permission (`PermissionType.Witness`, normally holding a single block-signing key with threshold 1 and no operations at all) can also satisfy `getPermissionById` and pass the weight check, even though on-chain transaction processing rejects any use of a non-`Active` permission for authorizing anything but signature-only bookkeeping. `checkPermission` in `TransactionCapsule` explicitly throws `"Permission type is error"` in this situation, but the precompile has no equivalent guard.

This is the same bug class as the referenced CVE: a security check (permission/subresource scope) is enforced along the "normal" path (regular transaction signing) but is missing on an equally reachable, alternate path (the TVM precompile) that dApps and off-chain integrators are expected to trust as an authorization primitive.

### Impact Explanation
Any contract deployer can build (or an attacker can already have deployed) a dApp — multisig wallet, vault, DAO, exchange contract — that gates privileged operations (fund transfers, governance actions, order execution) behind `validatemultisign`, trusting it to enforce the same operations-scope guarantees as the chain's native permission system. Because the precompile ignores permission type and operations bitmap, an account's narrowly-scoped Active key (or even its Witness key) can be replayed to authorize actions the key was never intended to approve, letting an attacker bypass the intended access-control policy of any contract relying on this precompile — leading to unauthorized asset movement or unauthorized privileged contract actions.

### Likelihood Explanation
Reachable from any TVM call with no special privilege — an ordinary transaction/contract call that invokes the `validatemultisign` opcode. Exploitation only requires that: (a) the target account has configured multiple permissions (e.g., a narrow Active permission for one purpose and reuses the same/derivable keys elsewhere), and (b) a contract in the ecosystem uses `validatemultisign` as an authorization gate expecting it to respect permission scoping. This is a realistic and common integration pattern for smart-contract wallets on Tron.

### Recommendation
In `PrecompiledContracts.ValidateMultiSign.execute` (and the related `BatchValidateSign` precompile if it shares this logic), mirror the checks performed in `TransactionCapsule.checkPermission` / `WalletUtil.checkPermissionOperations`: when `permissionId != 0`, require `permission.getType() == PermissionType.Active`; additionally, since the precompile has no intrinsic "contract type" to check operations against, document/enforce that only `Active`-type permissions (with defined semantics for precompile-based validation) are accepted, rejecting `Owner`/`Witness` permission IDs unless explicitly intended.

### Proof of Concept
1. Create account `A` with:
   - Default Owner permission.
   - An `Active` permission (`permissionId = 2`) whose `operations` bitmap authorizes only `TransferContract` (as constructed in `ValidateMultiSignContractTest.testDifferentCase`, see [5](#0-4) ).
2. Deploy a contract `Vault` that calls `validatemultisign(A, 2, hash, sigs)` before executing an arbitrary privileged action (e.g., releasing funds), trusting that permission `2` was meant only for transfers.
3. Sign `hash` (unrelated to any transfer) with the keys of permission `2`; call `Vault`'s privileged function with those signatures.
4. `ValidateMultiSign.execute` returns `DataWord.ONE()` because `totalWeight >= threshold`, without ever checking that permission `2` is scoped to transfers only — `Vault` executes the privileged action it should have refused, demonstrating the scope-check bypass, exactly as in the referenced K8s subresource-permission mismatch (`GHSA-92hx-3mh6-hc49`).

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
