### Title
TVM `CREATE2` opcode fails to reset RETURNDATA buffer on early failure paths (pre-Osaka), allowing stale RETURNDATA from a prior call to leak into subsequent `RETURNDATASIZE`/`RETURNDATACOPY` reads - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.createContract2()` (the `CREATE2` opcode handler) only clears the `returnDataBuffer` field when the `allowTvmOsaka` hard-fork flag is enabled. Every other externally-observable call primitive (`CREATE`, `CALL`/`CALLCODE`/`DELEGATECALL`/`STATICCALL` via `callToPrecompiledAddress`, and message calls) resets `returnDataBuffer = null` unconditionally right before dispatching the sub-call. Until the Osaka proposal is activated on-chain, a `CREATE2` that takes an early failure path (balance check, max call-depth, or address-collision checks in `createContractImpl`) leaves the buffer populated with whatever data was returned by the attacker's *previous* external call, which a contract can then read via `RETURNDATASIZE`/`RETURNDATACOPY` as if it were the result of the `CREATE2`.

### Finding Description
`Program.java` resets the return-data buffer at the top of every call-type handler except the pre-Osaka `CREATE2` path: [1](#0-0) [2](#0-1) [3](#0-2) 

`createContract()` (`CREATE`) and `callToPrecompiledAddress()` unconditionally clear `returnDataBuffer` before proceeding. `createContract2()` (`CREATE2`) only does so `if (VMConfig.allowTvmOsaka())`. In the non-Osaka branch, the subsequent early-return paths inside `createContractImpl` (insufficient balance, max call depth) call `stackPushZero()` and `return` without ever touching `returnDataBuffer`: [4](#0-3) 

Only the “contract-run-halted” branch of `createContractImpl` explicitly assigns `returnDataBuffer = createResult.getHReturn();` on revert/exception; the earlier short-circuit returns skip this assignment entirely: [5](#0-4) 

This is confirmed by the project's own regression test, which documents the exact pre/post-Osaka behavioral difference for a failed `CREATE2`: [6](#0-5) [7](#0-6) 

i.e., "failed CREATE2 keeps the previous 32-byte return data buffer" (pre-Osaka) vs "failed CREATE2 clears the previous return data buffer after Osaka" — this is a first-party acknowledgment that the pre-fix behavior is wrong.

### Impact Explanation
`RETURNDATASIZE`/`RETURNDATACOPY` are relied upon by Solidity-generated code and factory/proxy patterns to fetch the result of the most recent external call (e.g. verifying constructor return data of a deployed contract, decoding a call's return value, or low-level `abi.decode(returndata,...)` patterns). Because the returndata channel is not refreshed for a failing `CREATE2` before Osaka activation, a contract can be made to observe return data from an *unrelated, attacker-chosen prior call* instead of the actual (empty/failed) result of the `CREATE2`. Any downstream contract logic that trusts `RETURNDATA` immediately following a `CREATE2` (common in minimal-proxy/factory deployment verification, or generic decode-after-create helper libraries) can be tricked into treating a failed deployment as if it produced attacker-controlled data, potentially leading to incorrect authorization/validation decisions, corrupted application state, or facilitation of further exploitation in composed contracts. This is a genuine violation of TVM/EVM call semantics rather than a benign inconsistency, matching the report's bug class of "return channel" state being incorrectly retained/overwritten across an execution boundary.

### Likelihood Explanation
Trivially reachable: any account can deploy a contract that performs a `CALL`/`STATICCALL` to obtain attacker-controlled return data followed by a `CREATE2` that is made to fail deterministically (e.g., deploying to a colliding address, or insufficient endowment), then reads `RETURNDATASIZE`/`RETURNDATACOPY`. No special privileges, witness/committee status, or network position are required — only ordinary transaction broadcast/contract deployment capability. The bug is gated purely on the `allowTvmOsaka` committee proposal not yet being active, which is the current/default state absent explicit activation.

### Recommendation
Make the `returnDataBuffer` reset in `createContract2()` unconditional (matching `createContract()` and `callToPrecompiledAddress()`), rather than gating it behind `VMConfig.allowTvmOsaka()`. If backward-compatibility for existing chain state is a concern, consider whether this must remain hard-fork-gated, but ensure any production network is aware it is exposed to this issue until Osaka is activated, and that the fix is deployed with high priority given the state-consistency implications.

### Proof of Concept
1. Deploy Contract A with two calls chained in a single transaction:
   - `staticcall` (or `call`) to any address that returns 32+ bytes of attacker-chosen data (e.g., a trivial helper contract that does `return(0, 32)` with a crafted word).
   - Immediately follow with a `CREATE2` opcode invocation that is forced to fail before actual sub-execution, e.g. by targeting a salt/init-code combination that collides with an already-existing contract address (triggering the `contractAlreadyExists` short-circuit) or by exhausting balance so `endowment > balance` (triggering the early `stackPushZero(); return;` in `createContractImpl`).
2. Immediately execute `RETURNDATASIZE` and `RETURNDATACOPY` after the failed `CREATE2`.
3. On a network where `allowTvmOsaka` is not active, the copied return data equals the data from the first call (attacker-controlled), not the empty/failed `CREATE2` result — as verified by `TvmIssueVerifierTest.verifyTvmOsakaFixesWithSolidity()` asserting `BigInteger.valueOf(32)` (non-zero prior-call marker) for the pre-Osaka case versus `BigInteger.ZERO` once Osaka is enabled.
