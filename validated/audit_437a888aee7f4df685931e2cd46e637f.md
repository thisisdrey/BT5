### Title
Optimistic inventory ack in `handle_unsolicited_StackerDBPushChunk` advertises a chunk as stored before it is actually persisted - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates a pushed `StackerDBChunkData`, then immediately patches its outbound `StackerDBChunkInvData.slot_versions` to reflect the new (higher) version and signs/sends that inventory reply back to the peer — all *before* the chunk has actually been written to the local StackerDB. The real persistence (`try_replace_chunk`) only happens later, when the message is handed off to the relayer's `process_stacker_db_chunks`.

### Finding Description
`validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:649-718`) checks size, expected version, signer, staleness, and write-count, and returns `Ok(true)` if the chunk *appears* acceptable: [1](#0-0) 

In `handle_unsolicited_StackerDBPushChunk`, once `validate_received_chunk` passes, the code patches the in-memory inventory vector that is about to be sent back to the peer, setting the slot's version to the *new* value — before any DB write occurs: [2](#0-1) 

The function then immediately signs and transmits this patched `StackerDBChunkInv` as a P2P reply, and only *afterwards* returns `(false, true)`, i.e. "don't buffer, forward to relayer": [3](#0-2) 

Actual persistence happens later and separately, in `StacksMessageType::StackerDBPushChunk` when it reaches the relayer's `process_stacker_db_chunks`, which calls `tx.try_replace_chunk` and silently `continue`s (drops the chunk without any correction message) on any `Error` including `StaleChunk`: [4](#0-3) 

Crucially, `try_replace_chunk`'s staleness check uses `<=` (reject if `slot_version <= slot_validation.version`), while `validate_received_chunk`'s staleness check uses strict `<` against the just-snapshotted inventory: [5](#0-4) 

This is the same bug class as the reported IRM issue: an optimistic state update ("I now hold version V") is committed and *externally advertised* before the underlying operation that is supposed to produce that state (`try_replace_chunk`) is confirmed to have succeeded. If two chunks for the same slot arrive concurrently from different peers (or from the same peer in quick succession), both can pass `validate_received_chunk` against the same locally-computed inventory snapshot, both nodes get told "accepted, I have version V", but only one insert can actually win at the DB layer — the other is dropped by `process_stacker_db_chunks` with no compensating NACK/ChunkInv correction sent to the peer that was already told it succeeded. Equivalently, if the DB write is later invalidated by an out-of-band clear (contract-driven slot eviction) or fails for any other reason, the advertised inventory diverges from the true stored data hash/version.

### Impact Explanation
This breaks the equality between "advertised inventory (`StackerDBChunkInvData.slot_versions`)" and "actual stored chunk state" for an unprivileged, remote-triggerable path (any StackerDB replica peer pushing chunks). Downstream StackerDB sync logic (`StackerDBSync`) uses inventory responses to decide what to fetch/skip from peers, and depends on the invariant that an acked/advertised slot version corresponds to real stored data. A node advertising a version it does not actually hold can cause peers to skip re-fetching genuinely missing/new data (believing it is already replicated), delaying propagation of legitimately signed StackerDB content (used e.g. for miner block-proposal signer messages) across the network. This is a state-consistency defect in an unauthenticated inventory bookkeeping path, though it does not itself allow storing unsigned data (the underlying signature checks in `try_replace_chunk` still gate what can ultimately be persisted).

### Likelihood Explanation
Triggering the race requires only sending two (or more) validly signed `StackerDBPushChunk` messages targeting the same slot in quick succession — something any StackerDB-replicating peer that knows a valid signer key for a slot, or that simply forwards/replays observed valid chunks from two connections, could attempt without special privileges. No cryptographic break is needed, only timing between the inventory-patch/reply and the eventual `try_replace_chunk` call in the relayer.

### Recommendation
Do not patch/announce the inventory version, nor send the `StackerDBChunkInv` reply confirming acceptance, until the chunk has actually been durably written via `try_replace_chunk`/`process_stacker_db_chunks`. If the design intentionally defers persistence to the relayer for architectural reasons, the ack path should reflect the *previously confirmed* on-disk version rather than the optimistically-patched one, and `process_stacker_db_chunks` should emit a correcting inventory update (or NACK) when a chunk it was about to relay/store turns out stale/rejected, so peers do not retain a false belief that the chunk was stored.

### Proof of Concept
1. Node `A` maintains a StackerDB config for slot `S` with current stored version `V0`, owned by signer `K`.
2. Attacker (or two independent legitimate senders relaying the same signer's traffic) opens two connections/messages to `A`:
   - Message 1: `StackerDBPushChunk` for slot `S`, version `V0+1`, correctly signed by `K`.
   - Message 2 (sent right after, before message 1 reaches the relayer/DB write): another `StackerDBPushChunk` for the same slot `S`, also version `V0+1` (or `V0+2`), signed by `K`.
3. `A.handle_unsolicited_StackerDBPushChunk` runs `validate_received_chunk` against the freshly-computed inventory (still showing `V0` for both messages, since the DB hasn't been updated yet) — both messages pass validation.
4. `A` patches its outbound inventory and replies to both senders with `StackerDBChunkInv` claiming slot `S` is now at the pushed version, then forwards both to the relayer.
5. `process_stacker_db_chunks` processes both: the first `try_replace_chunk` call succeeds and bumps the stored version to `V0+1`; the second call for the same/lower version now fails with `StaleChunk` and is silently dropped (`continue`) with no follow-up correction sent to the second sender.
6. The second sender/peer has been told (step 4) that `A` now holds the chunk it pushed, but `A` never actually stored that specific chunk instance — a false, unaudited allegation of persisted state that can propagate through subsequent inventory-based sync decisions.
