### Title
`remove_account` never clears `TrieKey::PostponedReceipt`, so a stale postponed receipt survives unlimited account delete/recreate cycles - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` in `core/store/src/utils/mod.rs` removes the `Account`, `ContractCode`, all `AccessKey`/gas-key entries, and all `ContractData` entries for a deleted account, but it contains no logic that scans for or removes `TrieKey::PostponedReceipt` entries keyed to that `receiver_id`. Since the function's control flow is identical on every invocation (it does not track history or check for pre-existing postponed receipts), it fails to clear a stale postponed receipt on the *first* delete just as much as on the *second*, *third*, or *Nth* delete of the same account name.

### Finding Description
`remove_account` explicitly enumerates and removes: `TrieKey::Account` (line `core/store/src/utils/mod.rs:509`), `TrieKey::ContractCode` (line 510), all access-key/gas-key entries via `trie_key_parsers::get_raw_prefix_for_access_keys` (lines 516-553), and all `ContractData` entries via `trie_key_parsers::get_raw_prefix_for_contract_data` (lines 556-573). At no point does it call `remove_postponed_receipt` (defined at line 129-135 in the same file) or iterate over any prefix corresponding to `TrieKey::PostponedReceipt`, which is keyed by `(receiver_id, receipt_id)`.

Because `remove_account`'s implementation is stateless with respect to how many times the account name has been deleted/recreated before, the code path taken on owner2's `DeleteAccount` (second cycle) is byte-for-byte identical to the code path taken on owner1's `DeleteAccount` (first cycle): both call the exact same function with the exact same logic, and both leave any `PostponedReceipt` entry untouched. There is no mechanism anywhere in `remove_account` that becomes "smarter" or accumulates cleanup obligations across repeated deletions. [1](#0-0) [2](#0-1) 

### Impact Explanation
This confirms that the persistence property holds irrespective of how many unrelated parties reuse the account name in between: the postponed receipt keyed to `receiver_id = <account name>` remains resolvable at any future point once its missing input data is supplied, and it will execute against whichever account currently occupies that name. If the postponed action receipt encodes a `DeleteAccount` action with the attacker set as beneficiary, or a `Transfer`/`FunctionCall` action, firing it against a later owner's funded account constitutes theft of funds and an authorization escalation across accounts (the action was authorized under owner1's original transaction context but executes against owner3's account state).

### Likelihood Explanation
I was not able to fully trace the receipt-resolution path in `runtime/runtime/src/lib.rs` (i.e., how `resolve_received_data` / `apply_action_receipt` handle a postponed receipt whose input data finally arrives, and whether any account-existence or account-identity check is performed at resolution time) before running out of tool budget. That verification is necessary to confirm whether firing the stale receipt against owner3's account actually causes fund loss/escalation, or whether some other check (e.g., the account must still have the same `AccessKey` referenced, or a receipt validity check tied to account creation height) blocks execution. Without confirming that resolution path, I can validate the storage-layer half of the question (that `remove_account` never clears postponed receipts, and that this is invariant across repeated cycles) but cannot fully validate the end-to-end fund-theft/escalation claim.

### Recommendation
Extend `remove_account` to also iterate and remove all `TrieKey::PostponedReceipt` entries (and likely `TrieKey::ReceivedData` / `TrieKey::PromiseYieldReceipt` entries) with matching `receiver_id`, using the same trie-prefix-iteration pattern already used for access keys and contract data, so that no residual receipt can be resolved against a differently-owned account occupying the same name in the future.

### Proof of Concept
Integration test (runtime test-loop) plan:
1. Create account `a` owned by `owner1`; have `owner1` schedule an `ActionReceipt` targeting `a` that is postponed pending an `input_data_id` that is never supplied (e.g., via a cross-contract call whose promise result predecessor never resolves), so a `TrieKey::PostponedReceipt` for `receiver_id = a` is persisted in the trie.
2. Have `owner1` submit `DeleteAccount` for `a` with `owner1` as beneficiary. Assert via direct trie lookup (`get_postponed_receipt`) that the `PostponedReceipt` entry for `a` still exists after the account is deleted.
3. Have `owner2` recreate account `a` (via `CreateAccount`) and then immediately delete it again with `owner2` as beneficiary. Assert again via `get_postponed_receipt` that the same stale entry persists unchanged.
4. Have `owner3` recreate account `a` and fund it.
5. Deliver the missing input data (satisfying the postponed receipt's dependency) and assert that the previously postponed receipt executes against `owner3`'s account, and, depending on the encoded action, observe fund transfer/deletion-with-attacker-beneficiary against `owner3`'s balance — confirming the cross-owner authorization escalation.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }
