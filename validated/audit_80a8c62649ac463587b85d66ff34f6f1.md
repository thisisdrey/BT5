### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign`/`BatchValidateSign` precompiles causes node OOM / DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Consensys/gnark advisory describes an out-of-memory DoS caused by allocating a slice whose size (`nbCommitments`) is taken directly from untrusted deserialized input, without validating it against a sane upper bound before calling `make([]...)`. The analogous pattern exists in java-tron's `PrecompiledContracts` helper methods `extractBytesArray`, `extractBytes32Array`, and `extractSigArray`, which allocate `byte[len][...]` where `len` comes straight from attacker-supplied EVM/TVM call data (`words[offset].intValueSafe()`), reachable by any account that calls the `ValidateMultiSign` (`0x66`) or `BatchValidateSign` precompiled contract from a smart contract.

### Finding Description
`extractBytesArray` and `extractBytes32Array` compute the array length directly from call data with no bound check: [1](#0-0) 

`intValueSafe()` can return up to `Integer.MAX_VALUE` (2^31-1) for any oversized word: [2](#0-1) 

In `ValidateMultiSign.execute`, the size-bounding check (`sigArraySize > MAX_SIZE`) that would normally reject an oversized array is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is true; the unbounded call to `extractBytesArray`/`extractSigArray` is otherwise reached unguarded: [3](#0-2) 

The same pattern (size check gated behind the same feature flag, unbounded array allocation otherwise) exists in `BatchValidateSign.doExecute`, which additionally calls `extractBytes32Array` for the address list: [4](#0-3) 

Even when the `allowTvmSelfdestructRestriction` flag is active, the outer array-length bound (`MAX_SIZE`, e.g. 5 or 16) only limits the *count* of signatures/addresses; `extractBytesArray` independently re-reads a second untrusted length (`bytesLen`) per element from call data and allocates a byte array of that size via `Arrays.copyOfRange`, with no upper bound: [5](#0-4) [6](#0-5) 

This is directly analogous to the gnark issue: a size/count field is taken from attacker-controlled serialized/encoded input and used to size a slice/array allocation before any sanity bound is applied, producing multi-gigabyte allocations that can crash the JVM with `OutOfMemoryError`.

By contrast, the ZK Sapling `VerifyTransferProof` precompile in the same file correctly clamps analogous counts (`spendCount`, `receiveCount`) to a range of 1–2 *before* any array allocation, showing the codebase is aware of this class of bug elsewhere but did not apply the same discipline consistently in `ValidateMultiSign`/`BatchValidateSign`: [7](#0-6) 

### Impact Explanation
Any account can deploy or call a contract that invokes the `ValidateMultiSign` (address `0x0000...66`) or `BatchValidateSign` precompile with crafted call data containing an oversized length word. This triggers allocation of a `byte[][]` (or nested `byte[]`) sized by an attacker-controlled 32-byte word, up to `Integer.MAX_VALUE` elements/bytes, causing large heap allocations and potential `OutOfMemoryError`/JVM crash on any full node or SR node that executes the transaction — a node crash/halt DoS reachable from a single unprivileged transaction, matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
Reachability depends on whether `allowTvmSelfdestructRestriction` (a hard-fork feature switch gating the bound check) is enabled on the target network. Where it is disabled (private/test networks, or networks that have not yet activated this specific proposal), the size check is entirely skipped and the bug is trivially reachable by any caller. Where it is enabled, the outer array-length bound narrows exposure for `extractSigArray`/`extractBytes32Array`, but `extractBytesArray`'s inner untrusted `bytesLen` remains completely unbounded regardless of the flag, so a smaller-but-still-unbounded allocation vector persists even on hardened networks. I could not fully verify from the index whether `allowTvmSelfdestructRestriction` is unconditionally true on current mainnet default configuration (only that it is a `DynamicPropertiesStore`/proposal-controlled flag), which affects exact exploitability on any given deployment.

### Recommendation
- Enforce the `MAX_SIZE` bound unconditionally (not gated behind `VMConfig.allowTvmSelfdestructRestriction()`) before calling `extractBytesArray`, `extractSigArray`, or `extractBytes32Array` in both `ValidateMultiSign` and `BatchValidateSign`.
- Inside `extractBytesArray`, validate the per-element `bytesLen` against a fixed sane maximum (e.g. signature/data size expected by the ABI) before allocating, mirroring the fixed-length approach already used in `extractSigArray`.
- Add an explicit upper bound check on `len` in `extractBytes32Array`/`extractBytesArray` themselves (defense in depth), independent of caller-side checks, similar to the `spendCount`/`receiveCount` clamping already done in `VerifyTransferProof`.

### Proof of Concept
1. Deploy a contract that performs a low-level `staticcall`/`call` to precompile address `0x0000000000000000000000000000000000000066` (ValidateMultiSign) or the BatchValidateSign address.
2. Craft `rawData` per the ABI layout expected by `ValidateMultiSign.execute` (`address`, `permissionId`, `data`, then an offset word at index 3 pointing to a "signature array" location).
3. At the referenced array-length word (`words[offset]` in `extractBytesArray`/`extractSigArray`), place a large value (e.g. `0x7FFFFFFF`).
4. On a network/configuration where `allowTvmSelfdestructRestriction` is not active (or, for `extractBytesArray`, regardless of that flag, by controlling the inner `bytesLen` word), invoke the contract call; `extractBytesArray`/`extractSigArray`/`extractBytes32Array` will attempt to allocate an array sized by the attacker-controlled value, causing a large heap allocation/`OutOfMemoryError` on the executing node.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
