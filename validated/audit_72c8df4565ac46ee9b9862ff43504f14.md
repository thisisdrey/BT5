### Title
Floating-point precision loss in `ExchangeProcessor`'s Bancor-formula math causes divergent/imprecise exchange settlement amounts - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
`ExchangeTransactionActuator` and `ExchangeInjectActuator`/`ExchangeWithdrawActuator` settle TRC10 bancor-style exchange pools by calling `ExchangeCapsule.transaction()`, which by default routes to `ExchangeProcessor` [1](#0-0) . That processor computes the swapped amount using native Java `double` arithmetic and `Math.pow`-based exponentiation to emulate the bancor supply formula [2](#0-1) , which is directly analogous to the reported Curve oracle issue: fixed/floating point exponentiation (`powDown`/`Maths.pow`) is used to compute a financial exchange rate, and rounding/precision loss in that computation directly determines how many tokens a counterparty receives from a signed, user-broadcastable transaction (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`).

### Finding Description
`ExchangeProcessor.exchangeToSupply` and `exchangeFromSupply` perform the core bancor-relay calculation entirely in `double` precision, taking a ratio of `long` balances and raising `1 + quant/newBalance` to a fractional power (`0.0005` then `2000.0`) via `Maths.pow` [3](#0-2) . This is the exact same anti-pattern flagged in the external report: chained multiply/divide/`powDown` operations on fixed-point-like values accumulate rounding error at each step, and the final cast `(long) issuedSupply` / `(long) exchangeBalance` truncates any residual fractional value [4](#0-3) .

The codebase itself acknowledges this is a real, exploitable-precision problem: a `SafeExchangeProcessor` using `BigDecimal` with 18-digit scale was introduced as a "hardened" alternative [5](#0-4) , and a dedicated regression test (`testStrictMath`) explicitly demonstrates that the legacy `ExchangeProcessor` (double math) and the `useStrictMath`/`SafeExchangeProcessor` paths produce **different** results for the same inputs across dozens of real-world-scale token balances [6](#0-5) . The test only asserts inequality between the naive-double and strict-double paths, and equality between strict-double and BigDecimal — it does not bound or characterize how large the naive-double error can get in production, where `hardenedCalc`/`allowHarden()` defaults determine which processor actually executes for a given transaction [1](#0-0) .

Because `firstTokenBalance`/`secondTokenBalance` and `sellTokenQuant` are attacker/user-controlled (any account can submit `ExchangeTransactionContract` with arbitrary quantities against pools with arbitrary — including adversarially chosen — balances), an attacker can select balance/quantity combinations that maximize double-precision rounding error in `Maths.pow`, extracting more `buyTokenQuant` than the exact bancor formula would yield, or forcing another party's expected settlement (validated only via `anotherTokenQuant < tokenExpected` in `ExchangeTransactionActuator.doValidate`) to be manipulated by a few units through crafted, repeated small trades.

### Impact Explanation
Precision loss/rounding error in `ExchangeProcessor.exchange()` directly changes on-chain token balances recorded in `ExchangeCapsule` and each account's TRC10 asset ledger via `ExchangeTransactionActuator.execute` [7](#0-6) . Systematic rounding bias (favoring the trader over the pool, or vice versa) compounded over many transactions constitutes value extraction from the exchange pool / other liquidity participants — an unbacked-balance style issue, since tokens are minted/transferred based on an imprecise computation rather than the exact bancor invariant. This is Medium severity: it does not crash the node, but it can misallocate real TRC10 asset value between counterparties in a reproducible, exploitable way for any account submitting `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions.

### Likelihood Explanation
Any unprivileged, signed transaction broadcaster can trigger this path — no special permission is required beyond owning the exchange pool's tokens, and `ExchangeTransactionActuator`/`ExchangeCapsule.transaction()` use the vulnerable `ExchangeProcessor` by default whenever hardened calculation is not forced [1](#0-0) . The existence of `SafeExchangeProcessor`, a `useStrictMath` dynamic property, and the `testStrictMath` test proving divergence across many real inputs [8](#0-7)  confirms this is a known, reproducible discrepancy rather than a theoretical concern, though I could not fully verify from the available index whether the hardened/BigDecimal path (`allowHarden()`/`SafeExchangeProcessor`) is already the enforced default on mainnet or still opt-in via a chain parameter — this would materially affect current exploitability and should be confirmed against `DynamicPropertiesStore`/`ProposalUtil` activation logic before treating this as immediately live.

### Recommendation
Make the `BigDecimal`-based `SafeExchangeProcessor` computation the sole, mandatory path for all exchange settlement (remove or hard-fail the legacy double-based `ExchangeProcessor`), and add explicit, audited rounding-direction rules (always round in favor of the pool, never the trader) with a maximum-slippage/tolerance bound enforced in `doValidate()` for `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`, replacing ad-hoc post-hoc "Not precise enough" heuristics with the exact same math used at execution time.

### Proof of Concept
Not independently reproducible from the indexed context alone (no runtime access), but the divergence is already demonstrated in-repo: `ExchangeProcessorTest.testStrictMath` feeds identical `(sellBalance, buyBalance, sellQuant)` triples into `new ExchangeProcessor(supply, false)` (legacy double math) and `SafeExchangeProcessor.INSTANCE`/strict-double variants, and asserts the legacy result differs from the BigDecimal-verified result for every one of the ~48 real-scale test vectors provided [6](#0-5) . Any user submitting an `ExchangeTransactionContract` against a pool where the non-hardened `ExchangeProcessor` path is active will realize this same divergence between the "true" bancor amount and the actually-settled `buyTokenQuant`.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
