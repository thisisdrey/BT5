### Title
Pre-division of vote rate before multiplying by total reward causes users to receive fewer TRX rewards than owed - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes a voter's share of a standby-witness/SR reward using the same flawed operation order as the reported KyberSwap issue: it first divides `userVote` by `totalVote` (as a `double`) and only then multiplies by `totalReward`, instead of multiplying first and dividing once. This is invoked from the "old reward algorithm" path used by `computeReward(beginCycle, endCycle, accountCapsule)` → `getOldReward(...)`, which is reached whenever an account withdraws its voting reward via `WithdrawBalanceActuator`, a standard signed transaction any account can broadcast. [1](#0-0) 

### Finding Description
The reward-share formula is implemented as:
```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
``` [2](#0-1) 

This is mathematically equivalent to `userVote * totalReward / totalVote`, but by dividing `userVote/totalVote` first into a `double` and then multiplying, the calculation:
1. Loses precision immediately in the division step when `userVote/totalVote` is not exactly representable in binary floating point (which is essentially always, since `totalVote` is an arbitrary integer).
2. Compounds the rounding error when the resulting fractional `double` is multiplied by `totalReward` and then implicitly truncated to `long` when added to `reward` (loss on the `+=` widening/narrowing and on truncation).

This is the exact bug class from the external report: computing `a/b * c` (early division causing loss of significant digits) instead of `a*c/b` (single division at the end, or full-precision integer/BigInteger math). The codebase elsewhere explicitly avoids this pattern using `BigInteger` multiply-then-divide (e.g., `deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD)` in the "new algorithm" path just a few lines below), confirming that the "old algorithm" path is the outlier still using the imprecise double-based order of operations. [3](#0-2) 

`computeReward(long,long,AccountCapsule)` invokes `getOldReward(...)` (which internally calls the vulnerable per-cycle `computeReward(cycle, votes)`) for any cycle prior to `newRewardAlgorithmEffectiveCycle`: [4](#0-3) 

This reward computation is reached by `withdrawReward(byte[] address)` and `queryReward(byte[] address)`, which are called when a user submits a `WithdrawBalanceContract` transaction via `WithdrawBalanceActuator`, or when a client queries reward balance through the wallet API/`GetReward` endpoints. [5](#0-4) 

### Impact Explanation
Because the division happens before the multiplication and the result is a `double` truncated to `long`, individual voters systematically receive a reward slightly less than their exact proportional entitlement (`userVote * totalReward / totalVote`), especially for accounts with large vote counts, large `totalReward` values, or vote ratios that do not reduce cleanly. Cumulative rounding-down across many voters/cycles results in a persistent shortfall — some TRX credited to no specific account (effectively lost/unbacked from the perspective of legitimate reward recipients) — matching the "users receive fewer tokens than intended" impact class. This affects any unprivileged account that voted for a standby witness/SR and withdraws its reward before the network reached `newRewardAlgorithmEffectiveCycle` (chains/testnets/older segments still relying on the old algorithm), so it is reachable purely by submitting an ordinary signed `WithdrawBalanceContract` transaction.

### Likelihood Explanation
This is triggered deterministically on every withdrawal for cycles under the "old algorithm," not requiring any special privileges, adversarial conditions, or malicious actors — only ordinary integer vote counts and reward amounts, which are extremely common (any `userVote/totalVote` ratio that isn't an exact power-of-two fraction triggers precision loss). Given the old-algorithm code path remains reachable for accounts with rewards accrued in earlier cycles, likelihood is high for those specific cycles, though the newer "Vi" (BigInteger-based) algorithm used for post-cutover cycles is not affected.

### Recommendation
Replace the floating-point pre-division with integer/BigInteger math that multiplies before dividing once, mirroring the pattern already used in the new-algorithm branch:
```java
long userVote = vote.getValue();
reward += BigInteger.valueOf(userVote)
    .multiply(BigInteger.valueOf(totalReward))
    .divide(BigInteger.valueOf(totalVote))
    .longValue();
```
This eliminates the double-precision division-before-multiplication rounding loss and ensures voters receive their full proportional share, consistent with the recommendation in the original report (`(a * c) / b` instead of `(a / b) * c`).

### Proof of Concept
1. Configure two voters for the same SR in a pre-cutover cycle: voter A with `userVote = 7`, voter B with `userVote = 3`, `totalVote = 10`, and `totalReward = 100` (from `delegationStore.getReward(cycle, srAddress)`).
2. Exact expected rewards: A = `7*100/10 = 70`, B = `3*100/10 = 30`, sum = 100 (no loss).
3. Using values where the ratio is not exact, e.g. `userVote = 1`, `totalVote = 3`, `totalReward = 10`: exact reward = `10/3 = 3.33`, floor = 3. Using the current formula, `voteRate = (double)1/3 = 0.3333333333333333`; `reward += voteRate * 10 = 3.333333333333333` truncated to `long` when added — for many combinations of larger integers (e.g., `userVote` and `totalVote` near `Long.MAX_VALUE` boundaries or with vote/reward magnitudes in the trillions of sun), the double-precision multiplication after division loses low-order bits that a `BigInteger` multiply-then-divide would have preserved, producing a strictly smaller (or in edge cases inconsistent) result than the precise integer computation, which can be reproduced by comparing `computeReward` against a `BigInteger`-based reimplementation across a range of `(userVote, totalVote, totalReward)` triples, similar to the existing precision-comparison test pattern found in `ExchangeProcessorTest.testStrictMath`.   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
