### Title
Unbounded growth of an account's `assetV2` map via `TransferAssetContract` can bloat account state indefinitely - (`chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java`)

### Summary
`TransferAssetActuator.execute()` calls `toAccountCapsule.addAssetAmountV2(...)`, which inserts a new key into the account's `assetV2` map for every distinct TRC10 token ID a receiver is sent, and `reduceAssetAmountV2` never removes the map entry even when the balance for that token drops to zero. Like `vestingRecipients` in the referenced report, this is a storage structure that only grows and has no disposal mechanism, so any account that receives many distinct token types accumulates a permanently growing set of dust entries.

### Finding Description
`AccountCapsule.addAssetAmountV2()` inserts a new entry into `assetV2Map` for each new token ID sent to an account: [1](#0-0) 

`reduceAssetAmountV2()` only subtracts from the stored value; it never calls anything equivalent to `clearAssetV2`/removes the map key when the balance reaches zero: [2](#0-1) 

The only way to zero out the whole map is `clearAssetV2()`/`clearAsset()`, which are not invoked from the transfer/reduce path: [3](#0-2) 

`TransferAssetActuator.execute()` is reachable by any unprivileged transaction broadcaster with a signed `TransferAssetContract`, and unconditionally calls `addAssetAmountV2` on the receiver account with no cap on the number of distinct token IDs the receiver can accumulate: [4](#0-3) 

Every subsequent operation that loads that `AccountCapsule` (any transaction touching the account, block application, `GetAccount` API responses via `Wallet`/`TronJsonRpcImpl`, etc.) must deserialize/reserialize the entire `Account` protobuf, including the ever-growing `assetV2` map, since there is no mechanism analogous to the report's suggested "remove element with zero balance" fix.

### Impact Explanation
An attacker who issues many distinct TRC10 tokens (paying the asset-issuance fee once per token) can send a minimal (even 1-unit) transfer of each token to a victim address. Because dust entries are never pruned, the victim's `Account` proto grows without bound as more distinct token IDs are sent to it. This inflates the size of every `GetAccount`/`GetAccountNet`/JSON-RPC `eth_getBalance`-equivalent response for that address, increases the serialization/deserialization cost paid by the node on every block/transaction touching the account, and can eventually make retrieval of that account's full state costly or push responses past practical/API message-size limits — mirroring the exact failure mode ("retrieval will eventually fail") called out in the referenced report for `allVestingRecipients()`.

### Likelihood Explanation
Likelihood is moderate rather than high: unlike the original report (where interacting with the vesting contract is free/expected usage), attackers here must pay an asset-issuance fee (`AssetIssueFee`, historically 1024 TRX) for each new distinct token ID they want to plant on the victim, so growing the map to a size that causes real service disruption requires nontrivial capital outlay proportional to the number of dust entries. However, no additional permission is required beyond a normal signed transaction, the attack is fully repeatable/incremental, and the entries are permanent (never cleaned), so a sufficiently funded attacker can degrade a specific target account over time.

### Recommendation
When `reduceAssetAmountV2` reduces a token's balance to zero, remove that key from `assetV2Map` (and from the legacy `assetMap`) instead of leaving a zero-valued entry, analogous to the report's suggested mitigation of removing recipients once their vesting is fully withdrawn. Additionally, consider capping the number of distinct asset entries a single account can hold, or introducing pagination for any account-asset-map queries to prevent a single call from having to materialize an unbounded map.

### Proof of Concept
1. Attacker issues N distinct TRC10 tokens (`AssetIssueContract`), paying the asset-issuance fee for each.
2. For each of the N tokens, attacker submits a `TransferAssetContract` sending 1 unit to victim address `V`.
3. Each transfer causes `TransferAssetActuator.execute()` to call `toAccountCapsule.addAssetAmountV2(...)`, adding a new entry to `V`'s `assetV2Map`.
4. Attacker can optionally transfer the tokens back out of `V` (or to a burn/self-address) via further transfers; because `reduceAssetAmountV2` never deletes the map entry, `V`'s `assetV2Map` size never decreases even when all balances are zero.
5. Repeating steps 1–4 for large N causes `V`'s serialized `Account` protobuf to grow monotonically, increasing the cost of every future `GetAccount` call and every actuator/block-processing step that loads/saves `V`'s `AccountCapsule`.

Note: I could not directly execute this against a running node in this environment; the finding is based on static code analysis of `AccountCapsule`, `TransferAssetActuator`, and related stores. I was also unable to fully confirm within available context whether any client-side or protocol-level cap on distinct asset IDs per account exists elsewhere in the codebase (e.g., in `AccountAssetStore` optimization paths) — this should be verified further if pursued.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }
