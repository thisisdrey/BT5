Based on my research, the strongest and most concrete finding is a validation gap in the TRX/TRC10 bancor-style Exchange feature, which is the closest analog in java-tron to the "crowdsale success/failure without checking raised amount" bug class: a numeric invariant that gates a state-changing operation is only enforced in one code path and missing in sibling code paths that mutate the same shared state.

### Title
Exchange pool balance invariant only enforced in the "hardened" TRC10 bancor-relay calculation path, not in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeCapsule.transaction()` was recently hardened with `SafeExchangeProcessor` and an explicit invariant check that the resulting pool balances (`newFirstTokenBalance`/`newSecondTokenBalance`) must stay non-negative — but that check is only executed when `hardenedCalc` is `true`, i.e. only from `ExchangeTransactionActuator` and only after the committee-gated dynamic parameter `AllowHardenExchangeCalculation` is enabled. [1](#0-0) 
The sibling actuators that also mutate the same `Exchange`/`ExchangeCapsule` balances — `ExchangeInjectActuator` and `ExchangeWithdrawActuator` — never call this hardened path and never validate that the post-transaction balances stay non-negative or that the constant-product/relay math stays consistent; `ExchangeWithdrawActuator` in particular computes the counterpart quantity with raw `BigInteger` division and calls `subtractExact` directly on the pool balances with no lower-bound check. [2](#0-1) 

### Finding Description
The bug-class analog from the report is: a critical numeric precondition (`raisedWei >= minRaiseWei`) is enforced for one state transition but omitted for the sibling/opposite transition, allowing the state machine to reach an inconsistent state. In java-tron's Exchange (TRC10 bancor-relay market) feature, the same pattern occurs at the capsule level:

- `ExchangeCapsule.transaction(...)` computes new pool balances and, only `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0))`, throws `ContractValidateException("Exchange balance must be >=0 after transaction")`. [3](#0-2) 
- `ExchangeTransactionActuator` is the only caller that passes `allowHarden()` (i.e., `dynamicStore.allowHardenExchangeCalculation()`) into `transaction(...)`, in both `doValidate()` and `execute()`. [4](#0-3) [5](#0-4) 
- `ExchangeInjectActuator.execute()` and `ExchangeWithdrawActuator.execute()` never call `ExchangeCapsule.transaction()` at all; they independently reimplement the pool-balance arithmetic (`floorDiv`/`multiplyExact` for inject, raw `BigInteger` divide for withdraw) and write the resulting balances back via `exchangeCapsule.setBalance(...)` with no equivalent non-negative/consistency check anywhere in their `validate()` or `execute()` methods. [6](#0-5) [7](#0-6) 
- `AbstractExchangeActuator` only gates plain `addExact`/`subtractExact` overflow-safety behind `allowHarden()`; it exposes no shared invariant-check helper that `ExchangeInjectActuator`/`ExchangeWithdrawActuator` reuse from the hardened `ExchangeCapsule.transaction()` path. [8](#0-7) 

Because a normal user can freely call `ExchangeWithdrawContract`/`ExchangeInjectContract` (any account, no special permission needed — this is a market-maker-style TRC10/TRX pool), a broadcaster can drive the exchange pool balances into an inconsistent or corrupted state (e.g. via the `withdraw` quantity computed by integer `BigInteger` division combined with a crafted `quant`, or by chaining withdraw/inject calls) without ever hitting the invariant guard that was specifically added to `ExchangeTransactionActuator`'s hardened path. This is exactly analogous to the ICO bug where one state transition ("Milestone_ICOSuccessful") got the new check but its logical sibling ("Milestone_ICOFailed") did not.

### Impact Explanation
If pool balances can be pushed to zero, negative (protected against by `subtractExact` throwing on true underflow, but not against becoming a degenerate/zero balance) or otherwise inconsistent via `ExchangeWithdrawActuator`/`ExchangeInjectActuator` without the same invariant that `ExchangeTransactionActuator` enforces, subsequent `ExchangeTransactionActuator` trades against that same exchange pool (which is shared state, keyed by `exchangeId`) can compute an incorrect `anotherTokenQuant`, allowing a caller to receive more TRX/TRC10 tokens than the pool should be able to back — an unbacked-balance / theft-of-funds condition against other liquidity participants in the exchange pool.

### Likelihood Explanation
`ExchangeWithdrawActuator` and `ExchangeInjectActuator` are reachable by any account that owns exchange-pool balance (the exchange creator, or via crafted issuance/injection sequences) through a normal signed `ExchangeWithdrawContract`/`ExchangeInjectContract` transaction — no special permission or SR/committee role is required to trigger this path. The `AllowHardenExchangeCalculation` dynamic parameter only needs to be enabled by governance once for `ExchangeTransactionActuator`'s hardened check to matter; the omission in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` exists regardless of that flag's state, making it always reachable.

### Recommendation
Extract the non-negative/consistency invariant check that currently lives only inside `ExchangeCapsule.transaction()`'s `hardenedCalc` branch into a shared helper (e.g. a `checkExchangeBalance` method on `ExchangeCapsule`), and call it unconditionally from `ExchangeInjectActuator.execute()` and `ExchangeWithdrawActuator.execute()` after computing `newFirstTokenBalance`/`newSecondTokenBalance`/`anotherTokenQuant`, mirroring the check already present in the hardened `ExchangeTransactionActuator` path. Additionally, consider making the invariant check unconditional (not gated by `hardenedCalc`) in `ExchangeCapsule.transaction()` itself.

### Proof of Concept
Not independently reproducible without a running node/test harness; the analysis is based on static comparison of `ExchangeCapsule.transaction()` (which enforces the invariant only when `hardenedCalc` is true) against `ExchangeInjectActuator.execute()` and `ExchangeWithdrawActuator.execute()` (which mutate the same `ExchangeCapsule` balances via independent arithmetic with no equivalent invariant check at all). A concrete exploit sequence would need to be validated in a test harness (e.g. extending `ExchangeWithdrawActuatorTest`/`ExchangeInjectActuatorTest`) by crafting a sequence of `ExchangeInjectContract`/`ExchangeWithdrawContract` transactions that drive a pool's `firstTokenBalance`/`secondTokenBalance` to values that would have been rejected by `ExchangeCapsule.transaction()`'s hardened invariant, then following up with an `ExchangeTransactionContract` trade to demonstrate the pool paying out more than it holds.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  protected boolean allowHarden() {
    return chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation();
  }

  public long subtractExact(long x, long y) {
    return allowHarden() ? StrictMathWrapper.subtractExact(x, y) : x - y;
  }

  public long addExact(long x, long y) {
    return allowHarden() ? StrictMathWrapper.addExact(x, y) : x + y;
