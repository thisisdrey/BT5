### Title
Unbounded per-resolution Git subprocess/CPU work in `ResolveConflicts` allows RPC-handler DoS - (File: `internal/gitaly/service/conflicts/resolve_conflicts.go`)

### Summary
`ConflictsService.ResolveConflicts` accepts a client-controlled, unbounded-size JSON array of conflict `resolutions` and then iterates over every element performing multiple expensive Git operations (subprocess `cat-file` reads, blob writes, and full-content scanning/hashing) per entry, with no limit on the number of resolutions, on duplicate entries for the same path, or on the accumulated JSON payload size. This lets an ordinary, authenticated Gitaly client (e.g. via the GitLab conflict-resolution UI/API) trigger unbounded CPU and process-spawn cost per RPC call, mirroring the reported bug class of an unbounded per-element verification loop driven by attacker-controlled length.

### Finding Description
The RPC streams `FilesJson` chunks into an in-memory buffer with no size cap: [1](#0-0) 

That buffer is unmarshalled into `[]conflict.Resolution` with no limit on element count: [2](#0-1) 

`validateResolveConflictsHeader` only validates header fields (OIDs, branches, user) and never bounds the size or count of `resolutions`: [3](#0-2) 

The core work loop in `resolveConflictsWithGit` iterates over every entry of the client-supplied `resolutions` slice. For each entry that references a *real* conflicted path (from `checkedConflictedFiles`, which is only used as a presence check, not deduplicated), the loop performs: a `catfile` object read, a second `catfile` object read for the "ours" content, a full-file line-by-line scan/hash in `conflict.Resolve` (SHA1 over section IDs per line), a `WriteBlob` git subprocess invocation, and a `tree.Add`: [4](#0-3) 

Because `checkedConflictedFiles[path] = true` is simply overwritten and never checked for prior processing, an attacker can repeat the *same* valid conflicted path arbitrarily many times inside the `resolutions` JSON array, forcing the server to redo the full expensive per-file resolution work (multiple Git subprocess spawns, object reads, blob hashing/scanning) once per duplicate — with no upper bound on how many duplicates can be supplied, analogous to the reported unbounded `while` loop that re-executes expensive verification per user-controlled chunk.

### Impact Explanation
Each iteration performs several Git subprocess invocations (`cat-file`, `hash-object` via `WriteBlob`) plus in-process hashing/scanning of the full blob content (up to `fileLimit` = 200 KiB per file). A crafted request with a very large number of duplicate resolution entries referencing the same (or few) actually-conflicted files can force the Gitaly node handling the request to spawn a very large number of Git subprocesses and perform proportional CPU work within a single RPC call, exhausting CPU, process table, and file-descriptor resources on that node and degrading or blocking other RPCs — a denial-of-service of the handler, consistent with the "RPC-handler resource limits" category identified as in-scope.

### Likelihood Explanation
`ResolveConflicts` is reachable by any ordinary authenticated Gitaly client through the normal conflict-resolution workflow (e.g., GitLab's merge-request "resolve conflicts" feature calls this RPC), and the request payload (`resolutions` JSON, per-file `sections`/`old_path`/`new_path`) is fully attacker-controlled with no validation on element count, duplication, or overall streamed byte size. No special privileges beyond making an authorized Gitaly RPC call are required, making this readily triggerable.

### Recommendation
- Impose an explicit upper bound on the total size of the accumulated `FilesJson` stream and on the number of entries in the parsed `resolutions` array before processing.
- Deduplicate/track already-processed paths and reject (or ignore) resolutions referencing an already-resolved conflicted path, rather than silently redoing the expensive work.
- Consider bounding processing cost by capping the number of Git subprocess invocations per RPC and/or applying the existing Gitaly concurrency/backpressure limiter categories to this RPC.

### Proof of Concept
1. Create a repository with one real merge conflict for a single file `a` between two commits (`ours`/`theirs`).
2. Call `ResolveConflicts` with a valid header, then stream a `FilesJson` payload containing a JSON array with a very large number (e.g., hundreds of thousands) of resolution objects, all referencing the same real conflicted path (`old_path`/`new_path`: `a`) with valid `sections`, e.g.:
```json
[
  {"old_path": "a", "new_path": "a", "sections": {"<sectionID>": "head"}},
  {"old_path": "a", "new_path": "a", "sections": {"<sectionID>": "head"}},
  ... (repeated N times)
]
```
3. Because `checkedConflictedFiles["a"]` is present, each duplicate entry passes the validity check in [5](#0-4)  and re-executes the full per-file resolution pipeline (two `catfile` object reads, `conflict.Resolve` scan/hash, `WriteBlob`, `tree.Add`), causing CPU and Git-subprocess cost to scale linearly with N with no server-side cap, exhausting resources for the duration of the single RPC call.
