### Title
Floor-rounded `anotherTokenQuant` in `ExchangeInjectActuator` lets an exchange creator repeatedly skew a TRC10 exchange pool's price to extract value - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator.execute` computes the matching-side deposit amount (`anotherTokenQuant`) with `floorDiv(multiplyExact(otherBalance, tokenQuant), thisBalance)` [1](#0-0) , always rounding **down** the amount the depositor must contribute to keep the pool ratio unchanged. This is the same rounding-direction defect described in the report: the party performing the operation systematically contributes/receives a slightly favorable amount versus the exact pool ratio, and this can be repeated to accumulate drift.

### Finding Description
`ExchangeCapsule` implements a bancor-style two-token liquidity pool (`firstTokenBalance`/`secondTokenBalance`) used by `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator` [2](#0-1) . When injecting liquidity, the caller supplies `tokenQuant` of one token and the contract computes how much of the *other* token must also be supplied to preserve the current price ratio:

```
anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance);
``` [3](#0-2) 

Both balances are then increased by the exact `tokenQuant` and the *floor-rounded* `anotherTokenQuant` [4](#0-3) , meaning the injector contributes strictly less of the second token than the true ratio requires whenever the division is inexact. This nudges the pool's effective exchange rate in the injector's favor by a tiny amount every call, exactly analogous to the Sundial bug class where a systematically-rounded amount lets an actor repeatedly bias account/pool state in their own favor. Unlike `ExchangeWithdrawActuator`, which enforces a "Not precise enough" tolerance check (`remainder / anotherTokenQuant > 0.0001`) to bound rounding drift [5](#0-4) , `ExchangeInjectActuator.doValidate` performs no such precision/tolerance check — it only rejects `anotherTokenQuant <= 0` [6](#0-5) . There is therefore no safeguard preventing repeated small injections from cumulatively skewing the pool price away from its fair value, after which the actor (or a colluding trader) can extract the mispriced difference via `ExchangeTransactionActuator` trades against the drifted pool.

### Impact Explanation
Each single inject only shifts the ratio by a sub-unit amount, but because the operation is repeatable with no cumulative-drift check, an attacker can perform it many times to materially bias the pool's price, then trade against the pool (or withdraw) at the skewed rate, extracting value that rightfully belongs to other liquidity/token holders of that exchange pool — an unbacked-balance/loss-of-funds pattern for the pool, consistent with the report's remediation theme (verify economic health non-decreasing, and bound rounding-driven small-amount edge cases).

### Likelihood Explanation
Exploitation requires the caller to be the **creator** of the target `ExchangeCapsule` (`ExchangeInjectContract` requires `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` [7](#0-6) ), which limits the attack surface compared to a fully permissionless actor, but exchange creation itself is permissionless (any address can issue/create an exchange as an asset issuer), so an attacker can trivially become the "creator" of their own pool and then attract counterparties to trade against it, or use the technique against pools they control that other unwary users interact with. Each call is a normal, cheap (`calcFee()` returns 0) broadcastable transaction, so the operation is easily automatable and repeatable at scale.

### Recommendation
Apply the same tolerance/precision safeguard used in `ExchangeWithdrawActuator` (or an exact-ratio requirement) to `ExchangeInjectActuator`, rejecting injections whose computed `anotherTokenQuant` deviates from the true ratio by more than a negligible bound, and/or round in the direction that does not benefit the caller (round up the amount the injector must pay, symmetric with how a fair AMM should always round against the price-setting party).

### Proof of Concept
Conceptual: given `firstTokenBalance = 3`, `secondTokenBalance = 10` and `tokenQuant = 1` (injecting into `firstToken`), the exact required `anotherTokenQuant` is `10*1/3 = 3.33`, but `floorDiv` yields `3`, so the injector contributes `3` instead of `3.33+`, shifting the ratio from `3:10` to `4:13` (fair would be `4:13.33`). Repeating this operation N times compounds the discount versus the fair ratio; since no tolerance check exists (unlike `ExchangeWithdrawActuator`'s `"Not precise enough"` guard), nothing stops N from being arbitrarily large, allowing cumulative price manipulation of the pool before trading against it via `ExchangeTransactionActuator`.

Note: I was not able to fully trace a complete end-to-end quantitative exploit chain (inject-drift amount vs. resulting trade profit) within the available context, since that would require executing/simulating the full sequence of inject+transaction calls against `ExchangeCapsule` state — this determination would benefit from a live Devin session with codebase execution access to confirm the magnitude of extractable value.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
