### Title
Vote-reward accounting lets a voter earn full-cycle SR rewards for votes cast just before cycle rollover, diluting rewards owed to long-term voters - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.withdrawReward`/`queryReward` compute a voter's share of a super-representative's (SR) accumulated cycle reward as `userVote / totalVote` (old algorithm) or via a Vi-accumulator keyed by cycle (new algorithm), where `totalVote` / the vote-count snapshot used in the divisor is the SR's vote total that was frozen at the *previous* maintenance cycle boundary, not the vote total that actually existed while the reward was accruing. A voter's own vote snapshot, however, is taken from whatever votes are active in the account at the moment `withdrawReward` is invoked (called automatically from `VoteWitnessActuator`/`VoteWitnessProcessor` on every vote). This produces the same "instant, disproportionate reward capture" behavior described in the reference report.

### Finding Description
The reward flow is:

1. Every vote transaction calls `mortgageService.withdrawReward(ownerAddress)` first (settling the account with its *old* vote snapshot), then overwrites the account's vote list with the new votes: [1](#0-0) .

2. `withdrawReward` snapshots the *current* (just-updated) vote list as `AccountVote` for `endCycle = currentCycle` and advances `beginCycle`/`endCycle` bookkeeping: [2](#0-1) .

3. Meanwhile, the SR's total vote weight used as the *denominator* for reward-share calculations for a given cycle is fixed once per cycle, during `doMaintenance()`, using the witness's vote count *at the moment of the previous maintenance*, before any votes cast during the upcoming cycle are tallied: [3](#0-2) . New votes cast during a cycle are queued in `VotesStore` and only tallied into the witness's vote count at the *next* maintenance boundary via `countVote`: [4](#0-3) .

4. `computeReward` divides the SR's *whole-cycle* accumulated reward by this stale `totalVote` and multiplies by `userVote` for the voter's snapshot: [5](#0-4) . The new algorithm's Vi-based per-cycle accumulator (`accumulateWitnessVi`) has the same structural coupling — it also divides `reward` by `voteCount` for the same cycle key that is set at the prior maintenance boundary: [6](#0-5) .

Because a voter's own personal snapshot is taken from votes existing *right now* (immediately after casting the vote transaction), but is retroactively counted starting at `endCycle = currentCycle` (the cycle already in progress, whose reward pool and vote-total denominator were already fixed from the prior cycle boundary), a user can:
- Vote for an SR at any point inside a cycle, immediately becoming eligible (per their own `AccountVote` snapshot) for a share of that SR's entire in-progress cycle reward, computed against a denominator (`totalVote`) that does not yet reflect their newly added votes and was fixed before they participated.
- Immediately call `WithdrawBalanceContract`/`withdrawbalance` (or the TVM `withdrawreward` opcode via `WithdrawRewardProcessor`/`Program.withdrawReward`) to claim the `allowance` that was credited by this reward computation, and then unvote in the same or a following cycle without ever having contributed real stake for the period the reward accrued over.

This mirrors the reported LMPVault issue: a participant enters (votes) after value (reward pool) has already accumulated, and is able to extract a proportional share of that accumulated value based on a stake snapshot that was never actually held during accrual, at the expense of voters who held their votes the entire time (their share is diluted because the reward pool is shared with the late entrant using a stale/inconsistent total-vote denominator).

### Impact Explanation
This allows unauthorized redistribution of TRX rewards from long-term voters to a newly-voting account that never bore the SR's performance risk for the period, i.e. theft of protocol rewards belonging to other voters via account-level unauthorized value extraction — reachable purely through signed `VoteWitnessContract`/`WithdrawBalanceContract` transactions (or their TVM equivalents, `voteWitness`/`withdrawreward` opcodes) issued by any unprivileged account. No special privilege is required; only timing of votes relative to the cycle/maintenance boundary and the `WithdrawBalanceContract`'s 24-hour cooldown (`witnessAllowanceFrozenTime`, seen in `WithdrawBalanceActuator.validate`) constrains repeatability, but a single exploit per SR cycle can still misallocate rewards, especially valuable when large stake enters near reward-payout time.

### Likelihood Explanation
Exploitability requires only observing public chain state (current cycle boundary timing, SR reward accumulation), and issuing ordinary `VoteWitnessContract` and `WithdrawBalanceContract`/`withdrawreward` transactions — actions any account can already legitimately perform. No contract deployment, flash loan, or privileged role is needed, making this readily reachable, though the magnitude of theft is bounded by how much reward has accrued for the target SR within the exposure window and the 24h withdrawal cooldown.

### Recommendation
Track and use a time/cycle-consistent vote weight for reward computation: either (a) only start counting a voter's stake toward reward calculation starting at the *next* full cycle after the vote is cast/tallied by `countVote` (i.e., align the per-account snapshot cycle with the same cycle boundary used to fix `totalVote`/`witnessVi`), or (b) accrue rewards continuously pro-rata to time-weighted vote-seconds rather than per-cycle whole snapshots, so a voter who joins mid-cycle cannot claim rewards accrued before their votes were tallied into the SR's counted total.

### Proof of Concept
Conceptual reproduction on java-tron (cannot be fully validated without a live testnet/unit-test run in this session):
1. Let SR `W` accumulate block/tx-fee rewards over cycle `N` via `MortgageService.payReward`, with `totalVote` for cycle `N` fixed at maintenance boundary (previous cycle's `W.getVoteCount()`), per `MaintenanceManager.doMaintenance` (`setWitnessVote(nextCycle, ...)`).
2. Late in cycle `N` (before the next maintenance triggers), attacker submits `VoteWitnessContract` voting a large TRX-power stake for `W`. `VoteWitnessActuator.countVoteAccount` calls `mortgageService.withdrawReward(attacker)` (settling with the old, empty vote snapshot) then sets the attacker's new votes.
3. On the next call to `withdrawReward` (triggered either by another vote, `WithdrawBalanceContract`, or TVM `withdrawreward`), `MortgageService.withdrawReward` computes `computeReward(beginCycle, endCycle=N, accountCapsule)` using the attacker's freshly-set vote as `userVote` against `delegationStore.getWitnessVote(N, W)`— a total that does not include the attacker's new stake and reflects only what existed at the prior boundary — crediting the attacker's `allowance` with a share of `W`'s full-cycle reward pool for `N`.
4. Attacker calls `WithdrawBalanceContract` (subject to the 24h cooldown check in `WithdrawBalanceActuator.validate`) to move `allowance` into `balance`, then unvotes, having captured reward for a cycle in which their stake was not actually counted in the SR's total vote weight used to compute the reward pool's denominator.

Full confirmation would require running a modified version of the existing `DelegationServiceTest`/`VoteTest`/`ComputeRewardTest` unit tests with an added "vote late in cycle then withdraw" scenario to numerically demonstrate the disproportionate allowance, similar to the LMPVault PoC in the reference report.

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private void accumulateWitnessVi(long cycle, byte[] address) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long voteCount = getWitnessVote(cycle, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
