## Analog Vulnerability Found

### Title
Exchange (TRC10 AMM) price/ratio math ignores per-token `precision` (decimals), causing severe mispricing across differently-scaled TRC10 assets - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`, `ExchangeInjectActuator.java`, `ExchangeTransactionActuator.java`, `ExchangeWithdrawActuator.java`, `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The Caviar `Pair.price()` bug arises because the formula assumes both tokens share the same 18-decimal scale, but the base token's actual decimals were never normalized into the calculation. Java-tron's TRC10 **Exchange** module (`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeTransactionActuator`, `ExchangeWithdrawActuator`, and the underlying `ExchangeCapsule`/`ExchangeProcessor`) exhibits the same class of bug: it performs all constant-ratio and Bancor-curve arithmetic directly on raw `firstTokenBalance`/`secondTokenBalance` integer quantities, without ever reading or normalizing for each TRC10 asset's independently configurable `precision` field.

### Finding Description
TRC10 assets support a per-asset `precision` (0-6) set at issuance time via `AssetIssueActuator.validate()`: [1](#0-0) 

This means two different TRC10 tokens can legitimately have different decimal scales (e.g. token A with precision 0, token B with precision 6), just like ERC20 tokens can have different decimals in the Caviar report.

However, none of the Exchange actuators (`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeTransactionActuator`, `ExchangeWithdrawActuator`) ever fetch or apply `precision`/decimals when computing ratios. Balances are taken and combined as raw `long` quantities:

- Pool creation stores raw balances directly: [2](#0-1) 

- Injection computes the counterpart amount as a simple cross-multiplication of raw balances, with no decimal normalization: [3](#0-2) 

- The core swap math (`ExchangeCapsule.transaction` → `ExchangeProcessor`/`SafeExchangeProcessor`) uses the Bancor formula purely on raw `long` balances passed in, with no decimals adjustment anywhere: [4](#0-3) [5](#0-4) 

- Withdrawal likewise computes the counterpart amount as `secondBalance * quant / firstBalance` on raw integers: [6](#0-5) 

A grep across all `Exchange*Actuator.java` and `ExchangeCapsule`/`ExchangeProcessor` files confirms zero references to `precision`/`getPrecision` — the `precision` field that the protocol explicitly defines for TRC10 assets is never consulted by the Exchange subsystem. This is structurally identical to the Caviar bug: a price/ratio formula silently assumes uniform decimal scale, when the underlying assets are not guaranteed to share one.

### Impact Explanation
Because `precision` is asset-issuer-controlled (0-6, validated only in `AssetIssueActuator`), any user can:
1. Issue two TRC10 tokens with different `precision` values (e.g., token A precision 0, token B precision 6).
2. Call `ExchangeCreateContract` via `ExchangeCreateActuator` to create an AMM pool pairing these tokens with balances chosen so the *raw* quantities look like a fair 1:1 (or any) ratio, while the *real* value ratio (accounting for decimals) is off by up to `10^6`.
3. Any counterparty who injects liquidity (`ExchangeInjectContract`) or swaps (`ExchangeTransactionContract`) trusting the apparent raw-balance price is implicitly trading at a massively distorted rate, because the pool math never rescales for the differing `precision`.
4. This allows an attacker to drain the mispriced side of the pool from any liquidity provider or trader who is unaware of the decimal mismatch — a concrete unauthorized-value-transfer / theft-of-funds scenario reachable purely through signed `ExchangeCreateContract`, `ExchangeInjectContract`, and `ExchangeTransactionContract` transactions, with no privileged role required.

### Likelihood Explanation
This is directly reachable by any unprivileged account:
- Issuing TRC10 tokens with different `precision` is a normal `AssetIssueContract` (open to anyone, subject to fee).
- Creating an Exchange pool between arbitrary TRC10 tokens is a normal `ExchangeCreateContract` action (`ExchangeCreateActuator`), also open to anyone.
- No validation anywhere in the Exchange actuators checks or reconciles the `precision` of the two paired tokens, so likelihood of triggering the mispricing is high — it doesn't require any race condition, chain-halting, or privileged access, only ordinary token issuance and exchange creation/injection/trading, matching the report's low bar for triggering the analogous ERC20-decimals bug.

### Recommendation
When creating (`ExchangeCreateActuator`), injecting (`ExchangeInjectActuator`), trading (`ExchangeTransactionActuator`), and withdrawing (`ExchangeWithdrawActuator`) from an Exchange, normalize both `firstTokenBalance`/`secondTokenBalance` (and quant amounts) to a common decimal base using each token's `precision` value (fetched via `AssetIssueStore`/`AssetIssueV2Store`) before performing any ratio or Bancor-curve computation in `ExchangeCapsule.transaction`, `ExchangeProcessor`, and `SafeExchangeProcessor`. Alternatively, reject `ExchangeCreateContract`s that pair tokens with differing `precision` values, or explicitly document/enforce that Exchange pools operate on raw units only and surface this to callers so UI/wallet layers cannot silently misinterpret quoted prices.

### Proof of Concept
1. Issue TRC10 token `A` with `precision = 0` and TRC10 token `B` with `precision = 6` via `AssetIssueActuator` (`allowSameTokenName` enabled).
2. Call `ExchangeCreateActuator` with `firstTokenBalance = 1_000_000` (token A, precision 0 → represents 1,000,000 whole units) and `secondTokenBalance = 1_000_000` (token B, precision 6 → represents 1 whole unit), which the actuator accepts unmodified: [2](#0-1) 
3. The pool now reports an apparent 1:1 raw ratio, but in real value terms it is 1,000,000 A-tokens : 1 B-token.
4. A counterparty calling `ExchangeTransactionActuator` to sell token B against this pool (via `ExchangeCapsule.transaction` → `ExchangeProcessor.exchange`) receives token A at the raw 1:1-ish Bancor rate, effectively obtaining ~1,000,000x more real economic value than they paid, while the pool/liquidity provider is drained of token A.
