### Title
Split Check/Update Replay-Window Locking in `ConnectionState.Decrypt` Allows Concurrent Reader Routines to Double-Accept a Duplicate Packet - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement the replay-window guard as two separately-locked operations (`window.Check` then, after the AEAD decrypt "interaction," `window.Update`) rather than a single atomic check-and-mark. This is the same class of bug as the reported `BondManager.executeWithdrawBond()` issue: a state *check* is performed, an expensive *interaction* (external/attacker-influenced work) happens in between, and only afterward is the *effect* (state mutation) applied — violating Checks-Effects-Interactions. Nebula's UDP listener spawns multiple concurrent reader routines that all funnel packets into `readOutsidePackets` → `ConnectionState.Decrypt` for the *same* `HostInfo`/`ConnectionState`, so the same race window that let the Relayer over-withdraw bond funds lets two concurrently-processed duplicate/replayed packets both pass the replay `Check` before either has recorded its `Update`.

### Finding Description
`ConnectionState.Decrypt` (and the relay-frame analog `VerifyRelay`) reads: [1](#0-0) 

The sequence is:
1. `cs.decryptLock.Lock(); result := cs.window.Check(...); cs.decryptLock.Unlock()`
2. AEAD `DecryptDanger(...)` — performed **without holding the lock**
3. `cs.decryptLock.Lock(); result = cs.window.Update(...); cs.decryptLock.Unlock()`

Steps 1 and 3 are each individually locked, but the lock is *released* between them while step 2 (the "interaction") runs. This is structurally identical to the reported bug pattern: a check against shared accounting state, an external/expensive operation, and a deferred state update — with no lock/mutex held across the whole sequence to make the check-then-update atomic.

Nebula's UDP layer is configured to run several reader goroutines concurrently (the `listen.routines` / worker-loop pattern in `interface.go`), each independently calling `readOutsidePackets` → `hostinfo.ConnectionState.Decrypt(...)` for packets arriving on the same connection: [2](#0-1) 

If two copies of the same UDP datagram (a legitimate retransmit duplicate, or an attacker-replayed capture of a still-valid ciphertext/counter) are picked up by two different reader routines at nearly the same time, both can execute step 1 (`Check`) before either executes step 3 (`Update`), because the lock is dropped in between. Both `Check` calls will see "not yet marked" and return `true`, both routines will proceed to decrypt (step 2) and hand the plaintext up to `handleOutsideMessagePacket`/`connectionManager.In`/roaming logic, i.e. the packet gets processed twice even though the replay window is designed to guarantee "processed at most once per counter." Only the first `Update` call actually marks the bit; the second `Update` call will (correctly) report a duplicate and return `ErrAlreadySeen`, but by then the decrypted payload has already been delivered once via the first Decrypt success and once again through the second Decrypt success that happened before the first Update ran — i.e. the "effects" (payload delivery to firewall/tun/roaming/connection-manager state) have already occurred for both copies before the "checks-effects" ordering could stop the second one.

This mirrors the report's root cause exactly: "plan → interact → finalize" split across the same resource, with the finalize step (`Update`) not atomic with the check (`Check`), enabling a race that breaks the single-use invariant the replay window exists to enforce.

### Impact Explanation
The nebula replay window is the mechanism that prevents duplicate/replayed AEAD-authenticated data-plane and relay-frame messages from being processed more than once (see the explicit regression test guarding this invariant for relay frames, `TestRelayReplayProtection`, which states the intended contract as "a relay must reject replayed relay frames"). The `Check`-then-decrypt-then-`Update` race allows an attacker who can cause concurrent delivery of the same captured, still-in-window ciphertext (e.g., by sending it twice in quick succession to a multi-routine listener) to have it accepted twice by the receiving side's data plane before the replay window closes on the duplicate. This can cause double delivery of an inside packet to the local firewall/tun stack, double execution of side effects tied to `connectionManager.In(hostinfo)`/roaming, or, for relayed traffic, double forwarding — i.e., remote-state poisoning / replay-protection bypass under concurrency, the exact impact class called out in the "Validate" rules (traffic replay bypass).

### Likelihood Explanation
Exploitability is contingent on hitting the race window: the attacker needs the target to be running with multiple UDP reader routines (a common, non-default-off configuration) and needs two copies of the same valid ciphertext delivered to two different OS-level reader goroutines close enough in time to land between `Check` and `Update` on the same `ConnectionState`. This is achievable by an off-path attacker who captures a UDP datagram in flight and re-injects it (a classic replay attempt) immediately alongside the original — no valid certificate or privileged position is required beyond the ability to observe/replay UDP packets, which is the stated in-scope threat model (no CA-signed certificate needed). The race window is narrow (bounded by one AEAD decrypt operation) but non-zero, and is exactly the scenario the existing `TestRelayReplayProtection` regression test was written to prevent for the sequential case — that test does not exercise concurrent delivery via multiple reader routines, so this concurrency gap is not covered.

### Recommendation
Hold `cs.decryptLock` across the entire check-decrypt-update sequence (or otherwise make the counter reservation atomic with the check), following the same Check-Effects-Interactions fix recommended in the source report: reserve/mark the counter *before* performing the expensive/attacker-influenced decrypt, and roll back the reservation only if decryption fails. Concretely, refactor `Decrypt`/`VerifyRelay` in `connection_state.go` so that the replay-window bit is claimed under a single lock acquisition that also covers the decision to proceed, e.g.:
1. Lock, `Check`, and speculatively `Update`/reserve the counter atomically, then unlock.
2. Perform `DecryptDanger` outside the lock.
3. If decryption fails, unreserve/clear the bit (or otherwise ensure that a failed decrypt cannot leave the counter permanently consumed) — but never let two callers both pass step 1 for the same counter.

### Proof of Concept
1. Configure a nebula node with more than one UDP listener routine (multi-routine `listen` configuration) so packets for the same tunnel can be picked up by different goroutines concurrently.
2. Establish a tunnel and capture a single legitimate in-window data-plane (or relay) UDP frame, as done in `TestRelayReplayProtection`: [3](#0-2) 
3. Instead of injecting the captured frame sequentially (as the existing test does), inject two copies of the exact same captured frame *simultaneously* from two goroutines so they are picked up by two different reader routines and reach `ConnectionState.Decrypt` for the same `HostInfo` at nearly the same wall-clock instant.
4. Observe (with instrumentation/log counters on `handleOutsideMessagePacket`/`connectionManager.In` or on the relay-forward path) that under the right timing both copies pass `window.Check` and are processed as valid before `window.Update` on the first copy commits, resulting in the payload/relay frame being delivered/forwarded twice instead of the single time the replay window is supposed to guarantee — the same double-count effect described by `bits_test.go`'s dupe-counter invariant, but observed as duplicated *effects* rather than duplicated dupe-counter increments, because the check and the mark are not atomic across the decrypt.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
