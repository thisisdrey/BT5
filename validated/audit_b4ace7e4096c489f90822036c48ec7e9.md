### Title
Unbounded per-account growth of DelegatedResourceAccountIndex entries allows public API caller to trigger unbounded memory allocation (CWE-770 DoS) - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
Analogous to the OpenSSL QUIC issue (unbounded allocation of per-connection state until accepted by the app), java-tron's `DelegatedResourceAccountIndexStore` lets an unprivileged, low-cost transaction ("DelegateResourceContract") create an unbounded number of index entries associated with a single account address, and the public read APIs (`getdelegatedresourceaccountindex`, `getdelegatedresourceaccountindexv2`, plus their gRPC equivalents) then load and materialize **all** of those entries into memory with no cap, unlike every other list-returning API in the codebase (`MARKET_COUNT_LIMIT_MAX`, `maxLogFilterNum`, `MAX_MATCH_NUM`, etc.).

### Finding Description
`DelegateResourceContract` (`DelegateResourceActuator.calcFee()` returns `0`, [1](#0-0) ) is a fee-free, unprivileged action any account with frozen `FrozenBalanceV2` can broadcast. Each call to `delegateResource()` writes a new index entry keyed by `V2_FROM_PREFIX + owner + receiver` and `V2_TO_PREFIX + receiver + owner`: [2](#0-1) 

There is no limit anywhere on the number of *distinct receiver addresses* a single owner can delegate to (or vice versa) — each distinct receiver produces a brand new, permanent DB key. Compare this with `DelegatedResourceCapsule` (bounded per owner/receiver pair) — the index, by contrast, has no cap on the number of pairs.

When a client queries `GetDelegatedResourceAccountIndexV2` for an address, the store performs a raw, unbounded prefix scan and builds the *entire* result list in memory with no limit and no pagination: [3](#0-2) 

This is exposed through the public HTTP and gRPC APIs, reachable by any anonymous client: [4](#0-3) [5](#0-4) [6](#0-5) 

Unlike other multi-item read paths in the codebase — e.g. market order/pair listing which enforces `MARKET_COUNT_LIMIT_MAX` ( [7](#0-6) ), JSON-RPC log/block filters capped by `maxLogFilterNum`/`maxBlockFilterNum` ( [8](#0-7) ), and order matching capped by `MAX_MATCH_NUM` ( [9](#0-8) ) — the delegated-resource index has **no such cap**, either on write (actuator) or read (store/servlet).

This matches CWE-770 "Allocation of Resources Without Limits or Throttling": an attacker who controls one funded account and any modest number of distinct target addresses (which can even be freshly-derived, non-existent, addresses since `receiverAddress` need not already exist in `AccountStore` at delegation time in some flows) can grow the index for their address indefinitely at effectively zero on-chain fee cost, and any repeated query against that address (by the attacker or anyone else, including block explorers) forces the node to allocate and serialize the full unbounded list on every request.

### Impact Explanation
Repeated invocation lets an attacker grow the per-account index to an arbitrary size stored permanently in the state database. Every subsequent call to `getdelegatedresourceaccountindexv2` (or the legacy v1 endpoint, or the gRPC equivalents `GetDelegatedResourceAccountIndex`) for that address forces the node to scan and materialize the entire unbounded list into a `List<DelegatedResourceAccountIndexCapsule>`, sort it, and serialize the full protobuf response. Because these HTTP/gRPC endpoints are rate-limited per request/IP but not scaled to response size, a small number of such queries against an attacker-inflated address can consume disproportionate CPU/memory/network per request, degrading or crashing the serving node (an API the node can no longer serve) — the same class of "resource allocation without limit → DoS" impact as the OpenSSL QUIC advisory.

### Likelihood Explanation
High for the DoS-of-a-serving-node scenario: the write path (`DelegateResourceContract`) is a normal, permission-less, essentially fee-free transaction type available to anyone with frozen `FrozenBalanceV2`, and the read path is a completely public, unauthenticated API. No special privileges (SR/witness/committee/p2p) are required — only a funded account and standard `broadcasttransaction`/HTTP query flows.

### Recommendation
- Enforce a per-owner (and per-receiver) maximum number of distinct delegated-resource index entries in `DelegateResourceActuator.validate()`/`DelegateResourceProcessor`, similar to other count caps in the codebase (`MARKET_COUNT_LIMIT_MAX`, `WITNESS_COUNT_LIMIT_MAX`).
- Add a hard cap (configurable, similar to `jsonRpcMaxLogFilterNum`) to `DelegatedResourceAccountIndexStore.getWithPrefix`/`getV2Index`/`getIndex`, returning a bounded/paginated result and rejecting or truncating with an error once the limit is exceeded, instead of unconditionally materializing the whole prefix scan.
- Consider charging a per-entry fee for `DelegateResourceContract` (currently `calcFee() == 0`) to raise the cost of index inflation.

### Proof of Concept
1. Fund one account and freeze balance via `FreezeBalanceV2Contract` to obtain delegable `FrozenBalanceV2`.
2. Broadcast a large number (e.g. tens of thousands) of low-value `DelegateResourceContract` transactions from this owner address, each targeting a distinct receiver address (receivers do not need to be pre-funded/active). Each transaction has `calcFee() == 0`, so the marginal on-chain cost is minimal (only bandwidth/energy).
3. After these transactions are confirmed, call `GET /wallet/getdelegatedresourceaccountindexv2?value=<owner_address>` (or the gRPC `GetDelegatedResourceAccountIndex` call) against the target node.
4. Observe that the node performs a full, unbounded prefix scan (`DelegatedResourceAccountIndexStore.getWithPrefix`) and allocates/serializes the entire (attacker-controlled-size) list per request; repeating this query rapidly (or from multiple IPs) degrades or crashes the node's API service, analogous to the unbounded-queue exhaustion described in ALPINE-CVE-2026-14456.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
