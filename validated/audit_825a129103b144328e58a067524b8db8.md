### Title
Boundary condition in `MetAirdrop._transferReward` locks rewards instead of transferring them at `_end == block.timestamp` - (File: contracts/MetAirdrop.sol)

### Summary
`MetAirdrop._transferReward` uses a strict-less-than comparison (`_end < block.timestamp`) to decide whether the `lockPeriod` has fully elapsed. At the exact boundary block (`block.timestamp == updatedAt + lockPeriod`), the lock period has already elapsed by definition, yet the code falls into the esMET locking path and locks the user's reward for at least `ESMET.MINIMUM_LOCK_PERIOD() + 1`. This is the same bug class as the reported Gitcoin finding: an off-by-one timestamp boundary (`>`/`>=` / `<`/`<=`) causing a time-gated modifier/branch to behave incorrectly at the equality edge.

### Finding Description
In `MetAirdrop._transferReward`, `_end` is computed as `updatedAt + lockPeriod`, i.e., the moment the lock period ends [1](#0-0) . The intended semantic is "if the lock period has passed, transfer liquid `MET`". The check `if (_end < block.timestamp)` requires the current block to be strictly *after* `_end`; at `block.timestamp == _end` the function instead routes into the esMET lock path [2](#0-1) . In that branch, `_remainLockPeriod` is clamped to `_min = ESMET.MINIMUM_LOCK_PERIOD() + 1` because `_end - block.timestamp == 0`, so `ESMET.lockFor(to_, amount_, _min)` locks the claimed `MET` into esMET for the minimum lock duration [3](#0-2) . Any user can reach this via the public `RecurringAirdrop.claim(amount_, proof_)` entry point [4](#0-3) .

### Impact Explanation
A user who claims at exactly `block.timestamp == updatedAt + lockPeriod` has their entire claimable `MET` locked into esMET for `MINIMUM_LOCK_PERIOD` instead of receiving liquid `MET`, even though the intended `lockPeriod` has already fully elapsed. This is a temporary freezing of unclaimed yield (the claimer's reward is locked and non-transferable for the esMET minimum lock duration), with no way to claim liquid tokens afterwards since `claimed[msg.sender]` is already incremented [5](#0-4) .

### Likelihood Explanation
The trigger window is a single timestamp value, so natural occurrence is unlikely; however, `claim` is a permissionless entry point and no privileged actor is needed to hit the boundary — the claimer themselves (or an attacker front-running/affecting block landing such that a user's claim transaction lands in the boundary block) can produce it. The esMET lock is real and enforced by an external contract, so the freeze is guaranteed once the boundary block is hit.

### Recommendation
Align the boundary with the elapsed-time semantic: treat `block.timestamp >= _end` (i.e., `_end <= block.timestamp`) as "lock period finished":

```solidity
// contracts/MetAirdrop.sol
if (_end <= block.timestamp) {
    MET.safeTransfer(to_, amount_);
    return;
}
```

### Proof of Concept
Foundry (fork not strictly required; can run against deployed mainnet `MetAirdrop` where `ESMET`, `MET` are immutable constants):

```solidity
function test_boundaryLock() public {
    // metAirdrop: deployed MetAirdrop, alice: merkle recipient
    uint256 end = metAirdrop.updatedAt() + metAirdrop.lockPeriod();

    // Land the claim exactly on the boundary block
    vm.warp(end);
    vm.prank(alice);
    metAirdrop.claim(amount, proof); // leaf: keccak256(abi.encodePacked(alice, amount))

    // Expected: alice received liquid MET
    // Actual: alice's MET was locked in esMET for MINIMUM_LOCK_PERIOD + 1,
    //         since _remainLockPeriod = max(0, MIN+1) = MIN+1
    assertEq(met.balanceOf(alice), 0);
    // esMET position for alice is locked until end + MINIMUM_LOCK_PERIOD + 1
}
```

A second claim of the delta (`amount_ - claimed`) cannot rescue the frozen funds because the first claim already consumed the entitlement and routed it into `ESMET.lockFor`.

```text
    function _transferReward(address to_, uint256 amount_) internal override {
        uint256 _end = updatedAt + lockPeriod;

        if (_end < block.timestamp) {
            MET.safeTransfer(to_, amount_);
            return;
        }

        uint256 _min = ESMET.MINIMUM_LOCK_PERIOD() + 1;
        uint256 _max = ESMET.MAXIMUM_LOCK_PERIOD();

        // Ensures valid lock period
        uint256 _remainLockPeriod = Math.min(Math.max(_end - block.timestamp, _min), _max);

        token.safeApprove(address(ESMET), 0);
        token.safeApprove(address(ESMET), amount_);
        ESMET.lockFor(to_, amount_, _remainLockPeriod);
```

```text
    function claim(uint256 amount_, bytes32[] calldata proof_) external nonReentrant {
        if (merkleRoot == bytes32(0)) revert NothingToClaim();

        bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
        if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();

        uint256 _claimable = amount_ - claimed[msg.sender];
        if (_claimable == 0) revert NothingToClaim();

        claimed[msg.sender] += _claimable;

        _transferReward(msg.sender, _claimable);

        emit RewardClaimed(msg.sender, _claimable);
    }
```
