### Title
Unauthenticated pingback-handshake pubkey-hash check ignores forged `addrbytes`/`port`, allowing frontier poisoning at a third-party address - (File: `stackslib/src/net/neighbors/walk.rs`)

### Summary
`check_handshake_pubkey_hash` in the pingback-handshake path only verifies that the reported public key hashes to the expected `NeighborAddress.public_key_hash`; it never checks that the `HandshakeAcceptData.handshake.addrbytes`/`port` match the `NeighborAddress` (or the real connection endpoint) that the peer walk is resolving. Because the follow-on `add_or_schedule_replace_neighbor` call keys the stored `Neighbor` record directly off `data.handshake` (attacker-controlled `addrbytes`/`port`), an attacker who legitimately owns a pubkey (verified only by signature/hash) can get an arbitrary third-party address written into the local frontier and PeerDB, associated with their own key.

### Finding Description
In `pingback_handshakes_try_finish` [1](#0-0) , the peer node reads back a `HandshakeAccept`/`StackerDBHandshakeAccept` from a peer it is pingback-walking to, builds `peer_nk` purely from the self-declared `data.handshake.addrbytes`/`port`, and then calls:

```
if !Self::check_handshake_pubkey_hash(&peer_nk, data, &naddr) { continue; }
self.neighbor_db.add_or_schedule_replace_neighbor(network, &message.preamble, &data.handshake, db_data, &mut self.neighbor_replacements)?;
```

`check_handshake_pubkey_hash` [2](#0-1)  only compares `Hash160::from_node_public_key_buffer(&data.handshake.node_public_key)` against `naddr.public_key_hash` — it never validates `nk`/`addrbytes`/`port` against `naddr` or the real TCP peer.

`add_or_schedule_replace_neighbor` then calls `Neighbor::load_and_update(&tx, ..., handshake)` [3](#0-2)  which derives the stored `NeighborKey` (and thus the PeerDB slot address) from the same attacker-controlled `handshake.addrbytes`/`port`, and either inserts it as new (`neighbor_from_handshake.save`) or schedules a replacement of an existing slot [4](#0-3) .

The `naddr.public_key_hash` used as the "expected" value for this check originates from the attacker's own genuinely-owned key (established, e.g., when the attacker's inbound connection was first recorded as a pingback candidate), so the pubkey-hash equality legitimately holds. But because the address fields of the actual `Handshake`/`HandshakeAccept` payload are self-reported and, per `validate_handshake` in `chat.rs`, are **not** checked against the socket address for inbound connections [5](#0-4) , and are not cross-checked at all in the pingback-handshake-finish path, the attacker can set `addrbytes`/`port` to any third-party (victim) address in this reply while presenting a correctly-hashing key. The result: the stored `Neighbor` claims "victim IP:port belongs to attacker's key," entirely attacker-controlled.

This differs from the outbound `handle_handshake_accept` path (`walk.rs:676-737`) and `neighbor_handshakes_begin`/`neighbor_handshakes_try_finish` (`walk.rs:1091-1231`), which both check the resolved address against `cur_neighbor.addr` or the target `NeighborAddress` before trusting it. The pingback path has no equivalent address-consistency check.

### Impact Explanation
A forged `Neighbor` record (victim address + attacker-owned pubkey) is written into the local PeerDB/frontier via `add_or_schedule_replace_neighbor` → `Neighbor::load_and_update`/`save`, an unauthenticated write to persistent peer state. Frontier contents are relayed to other crawling peers through `GetNeighbors`/`Neighbors` responses, so the forged mapping can propagate network-wide, matching the "unauthenticated write to state" / "network-wide propagation of forged data" Critical categories. The practical effect is peer-graph poisoning: nodes that later act on this record may attempt outbound connections to the victim's address believing it hosts the attacker's identity, and PeerDB slots can be evicted/replaced by these forged entries.

### Likelihood Explanation
The attacker needs no privileges: any remote peer that can complete a normal signed handshake (using its own real keypair) with the target node can become a "pingback" candidate and later respond during `pingback_handshakes_try_finish` with a `HandshakeAccept` whose `addrbytes`/`port` fields are forged. No secrets, admin role, or victim cooperation are required, and the flow is part of the node's routine, automatic neighbor-walk state machine, so it is repeatable each time the target performs a pingback walk against the attacker.

### Recommendation
In `pingback_handshakes_try_finish`, after `check_handshake_pubkey_hash` succeeds, additionally verify that `data.handshake.addrbytes`/`port` are consistent with `naddr.addrbytes`/`port` (or, if unroutable/private, resolve to the actual observed socket address of the connection, as is done for outbound handshakes), rejecting the reply otherwise before calling `add_or_schedule_replace_neighbor`. Apply the same address-consistency check used in `handle_handshake_accept`/`neighbor_handshakes_try_finish` uniformly to the pingback path.

### Proof of Concept
Add a test in `stackslib/src/net/neighbors/walk.rs` (or `net::neighbors` test module) using the existing mock `NeighborComms`:
1. Construct a `NeighborWalk` in `PingbackHandshakesFinish` state with a `naddr` whose `public_key_hash` corresponds to an attacker-controlled keypair `attacker_sk`.
2. Feed a reply via the mock comms: `StacksMessageType::HandshakeAccept(HandshakeAcceptData { handshake: HandshakeData { node_public_key: attacker_pubkey, addrbytes: VICTIM_ADDR, port: VICTIM_PORT, .. }, .. })`.
3. Call `pingback_handshakes_try_finish`.
4. Assert that `check_handshake_pubkey_hash` returns `true` (pubkey hash matches `naddr`), and that `add_or_schedule_replace_neighbor`/the mock `PeerDB` now contains (or attempted to insert) a `Neighbor` keyed at `NeighborKey { addrbytes: VICTIM_ADDR, port: VICTIM_PORT, .. }` — demonstrating the frontier/PeerDB stores an attacker-controlled record pointed at a third-party victim address with no addr/port cross-check.
