## Title
Unbounded HTTP response body read in `libsigner`'s StackerDB RPC client — no default limit on response size (analog of GHSA-m77f-652q-wwp4 / CVE-2022-3212) - (File: `libsigner/src/http.rs`)

### Summary
`run_http_request` in `libsigner/src/http.rs` reads an entire HTTP response into memory with `sock.read_to_end(&mut buf)` before any `Content-Length` or size check is applied. There is no upper bound on how much data will be buffered, so a malicious or compromised RPC endpoint (a StackerDB replica/node that a signer is configured to talk to) can stream an arbitrarily large or effectively infinite response and force the signer process to allocate unbounded memory, exactly the missing-default-body-limit class of bug described in the axum-core advisory (CVE-2022-3212 / CWE-770).

### Finding Description
`libsigner/src/http.rs::run_http_request` performs the request/response cycle for `StackerDBSession` (used by `stacks-signer` to talk to a StackerDB-hosting node): [1](#0-0) 

```
sock.write_all(req_txt.as_bytes())?;
sock.write_all(payload)?;

let mut buf = vec![];

sock.read_to_end(&mut buf)?;
```

`read_to_end` keeps calling `read()` and appending to `buf` until the socket returns EOF or errors — there is no cap on `buf.len()`. Only *after* this unbounded read completes does the code parse headers (`decode_http_response`) and, for the chunked-transfer-encoding case, apply a size limit via `HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into())`: [2](#0-1) 

For non-chunked responses the raw bytes are simply copied (`buf.to_vec()`), again with no bound tied to `Content-Length` or any hard maximum. Because the size-limiting logic (`MAX_MESSAGE_LEN`) is only reachable after the entire response has already been buffered by `read_to_end`, it provides no protection against the primary allocation.

This is invoked from `StackerDBSession::rpc_request`, which is the transport used by `list_chunks`, `get_chunks`, `get_latest_chunks`, and other `SignerSession` methods that periodically poll a configured stacks node/StackerDB replica: [3](#0-2) [4](#0-3) 

By contrast, the equivalent server-side/P2P code paths in `stackslib` (e.g. `stackslib/src/net/httpcore.rs` `ProtocolFamily for StacksHttp::payload_len`/`consume_preamble`, and `stackslib/src/net/connection.rs::buffer_message_bytes`) enforce `MAX_MESSAGE_LEN`/`HTTP_PREAMBLE_MAX_ENCODED_SIZE` bounds *before* buffering payload bytes, so the same class of bug does not exist there. `libsigner/src/http.rs`'s client-side reader lacks this discipline entirely.

### Impact Explanation
A stacks node that a signer connects to (per its configuration, `StackerDBSession::host`) is not fully trusted once compromised, Byzantine, or subject to a network-level attacker/MITM able to respond on that TCP connection. Such a party can respond to any RPC call (`list_chunks`, `get_chunks`, `get_latest_chunks`, etc.) with a response that never terminates or is extremely large; because `read_to_end` has no size cap, the signer process will keep growing its buffer, exhausting memory and crashing (OOM), a remote unauthenticated/unauthorized-write-adjacent Denial of Service against signer infrastructure — critical to network operation since signers must be continuously available to sign blocks.

### Likelihood Explanation
The bug requires only a single malicious/compromised response from whatever host the `StackerDBSession` targets; the `socket_timeout` set via `set_read_timeout` only bounds the time between *individual* `read()` calls, not the total transfer, so a slow trickle of bytes indefinitely defeats it while `read_to_end` keeps accumulating data. No authentication or special privilege is needed by the responder beyond being the (or a spoofed/MITM) endpoint the signer is talking to.

### Recommendation
Bound the response read in `run_http_request` by:
- Parsing/validating `Content-Length` (or applying a hard maximum such as `MAX_MESSAGE_LEN`) before reading the body, and
- Using a bounded reader (similar to `BoundReader`/`HttpChunkedTransferReader` already used elsewhere in the codebase) instead of unconditional `read_to_end`, so both the headers and the body are capped regardless of what the remote peer declares or sends.

### Proof of Concept
1. Stand up a TCP listener masquerading as (or MITM-ing) the configured StackerDB host for a `StackerDBSession`.
2. On `rpc_request`/`run_http_request` connecting, respond with a valid status line/headers and then continuously write body bytes (optionally without ever closing the connection, or trickling slowly to stay under `socket_timeout` per read).
3. Observe the signer's memory usage grow unbounded in `sock.read_to_end(&mut buf)` at `libsigner/src/http.rs:251`, eventually causing an out-of-memory crash.

/// Decode an HTTP body, given the headers.
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
