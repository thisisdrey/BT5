### Title
`net/http.CrossOriginProtection` unconditionally allows GET/HEAD/OPTIONS requests, enabling Cross-Site WebSocket Hijacking (CSWSH) on any WebSocket upgrade endpoint it is used to protect - ([File: src/net/http/csrf.go])

### Summary
`CrossOriginProtection.Check` (added in Go 1.25) treats `GET`, `HEAD`, and `OPTIONS` as "safe methods" and returns `nil` immediately, before evaluating `Sec-Fetch-Site` or `Origin` at all. Because a WebSocket handshake is performed via an HTTP `GET` request carrying `Connection: Upgrade`, any application that relies on `CrossOriginProtection.Handler` to guard a WebSocket-upgrade endpoint gets zero cross-origin protection — the exact CSWSH primitive described in the Dozzle advisory (an origin check that always accepts the request, combined with browser-attached auth cookies), except here the bypass is built into the stdlib defense itself rather than a custom `CheckOrigin: func() bool { return true }`.

### Finding Description
Attacker-controlled page → browser issues `new WebSocket("wss://victim.example/ws")`, which the browser sends as an HTTP `GET` request with `Upgrade: websocket`, the victim's session cookie, `Origin: https://attacker.example`, and (in modern browsers) `Sec-Fetch-Site: cross-site` → server entry point is any `http.Handler` wrapped with `(*http.CrossOriginProtection).Handler` (`src/net/http/csrf.go:206-218`) → `Check` (`src/net/http/csrf.go:134-175`) hits the very first switch:
```go
switch req.Method {
case "GET", "HEAD", "OPTIONS":
    // Safe methods are always allowed.
    return nil
}
```
This unconditionally short-circuits before the `Sec-Fetch-Site` check and before the `Origin`-vs-`Host` comparison that the same function performs for unsafe methods (`src/net/http/csrf.go:141-174`) → the wrapped handler is invoked and, if it upgrades the connection (`w.(http.Hijacker).Hijack()` / `websocket.Upgrader.Upgrade`), a fully authenticated bidirectional WebSocket session is established cross-origin. The doc comment even warns generically that "applications [should] not perform any state changing actions due to requests with safe methods" (`src/net/http/csrf.go:22-24`), but a WebSocket upgrade is precisely such a stateful, session-establishing action riding on a nominally "safe" `GET`.

### Impact Explanation
Any Go service that uses `net/http`'s built-in `CrossOriginProtection` as its cross-origin defense for a WebSocket endpoint (e.g., terminal/exec/attach-style handlers, live log/event streams) is left with no origin protection at all for that endpoint, mirroring the CVE-2026-44985 impact: an attacker on any origin can hijack the victim's authenticated WebSocket session to read or inject data through it. This is a stdlib security-boundary defect (`net/http`), so it falls on Go's PUBLIC security track as a hardening/documentation gap in a documented security primitive, since it silently defeats developer expectations that `CrossOriginProtection` blocks cross-origin browser requests.

### Likelihood Explanation
Reachable by an ordinary unauthenticated attacker hosting a webpage; the only precondition is a victim with an existing session (cookie) visiting the attacker's page while authenticated to a Go service that uses `CrossOriginProtection.Handler` to guard a route that also performs a protocol upgrade (WebSocket). No credentials, privileged access, or malicious server control are required — matching the "unprivileged web attacker + victim browser" premise.

### Recommendation
Document explicitly (and ideally enforce) that `CrossOriginProtection` must not be relied upon to protect WebSocket-upgrade endpoints, since the handshake always arrives as a "safe" `GET`/`HEAD`. Either (a) have `Check` treat requests carrying `Connection: Upgrade` / `Upgrade: websocket` headers as non-safe regardless of method, forcing the `Sec-Fetch-Site`/`Origin` checks to run, or (b) add prominent documentation on `CrossOriginProtection` stating it does not protect protocol-upgrade requests and that callers must perform their own `Origin` validation (e.g., via `gorilla/websocket`'s `CheckOrigin`) for such endpoints.

### Proof of Concept
```go
package http_test

import (
	"net/http"
	"net/http/httptest"
	"testing"
)

// Simulates a WebSocket-upgrade handler "protected" by CrossOriginProtection.
func TestCrossOriginProtectionAllowsCrossOriginWebSocketUpgrade(t *testing.T) {
	protection := http.NewCrossOriginProtection()
	handler := protection.Handler(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// Stand-in for websocket.Upgrader.Upgrade(w, r, nil)
		w.WriteHeader(http.StatusSwitchingProtocols)
	}))

	req := httptest.NewRequest("GET", "https://victim.example/ws", nil)
	req.Header.Set("Connection", "Upgrade")
	req.Header.Set("Upgrade", "websocket")
	req.Header.Set("Sec-Fetch-Site", "cross-site") // browser explicitly flags cross-site
	req.Header.Set("Origin", "https://attacker.example")
	req.AddCookie(&http.Cookie{Name: "session", Value: "victim-secret"})

	w := httptest.NewRecorder()
	handler.ServeHTTP(w, req)

	// EXPECTED (if protected): 403 Forbidden, cross-site request rejected.
	// ACTUAL: 101 Switching Protocols — CrossOriginProtection allowed it
	// because GET is unconditionally treated as a "safe method".
	if w.Code != http.StatusForbidden {
		t.Fatalf("cross-origin WebSocket upgrade was NOT blocked by CrossOriginProtection: got %d, want %d (CSWSH)", w.Code, http.StatusForbidden)
	}
}
```

```go
// Check applies cross-origin checks to a request.
// It returns an error if the request should be rejected.
func (c *CrossOriginProtection) Check(req *Request) error {
	switch req.Method {
	case "GET", "HEAD", "OPTIONS":
		// Safe methods are always allowed.
		return nil
	}

	switch req.Header.Get("Sec-Fetch-Site") {
	case "":
		// No Sec-Fetch-Site header is present.
		// Fallthrough to check the Origin header.
	case "same-origin", "none":
		return nil
	default:
		if c.isRequestExempt(req) {
			return nil
		}
		return errCrossOriginRequest
	}

	origin := req.Header.Get("Origin")
	if origin == "" {
		// Neither Sec-Fetch-Site nor Origin headers are present.
		// Either the request is same-origin or not a browser request.
		return nil
	}

	if o, err := url.Parse(origin); err == nil && o.Host == req.Host {
		// The Origin header matches the Host header. Note that the Host header
		// doesn't include the scheme, so we don't know if this might be an
		// HTTP→HTTPS cross-origin request. We fail open, since all modern
		// browsers support Sec-Fetch-Site since 2023, and running an older
		// browser makes a clear security trade-off already. Sites can mitigate
		// this with HTTP Strict Transport Security (HSTS).
		return nil
	}

	if c.isRequestExempt(req) {
		return nil
	}
	return errCrossOriginRequestFromOldBrowser
}
```

```go
// Handler returns a handler that applies cross-origin checks
// before invoking the handler h.
//
// If a request fails cross-origin checks, the request is rejected
// with a 403 Forbidden status or handled with the handler passed
// to [CrossOriginProtection.SetDenyHandler].
func (c *CrossOriginProtection) Handler(h Handler) Handler {
	return HandlerFunc(func(w ResponseWriter, r *Request) {
		if err := c.Check(r); err != nil {
			if deny := c.deny.Load(); deny != nil {
				(*deny).ServeHTTP(w, r)
				return
			}
			Error(w, err.Error(), StatusForbidden)
			return
		}
		h.ServeHTTP(w, r)
	})
}
```
