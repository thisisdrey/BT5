## Title
Initiator-side handshake completion enforces `remote_allow_list` against the pre-verification target address instead of the certificate-verified `vpnAddrs`, unlike the responder path — ([File: handshake_manager.go])

### Summary
`HandshakeManager.beginHandshake` (responder path) and `HandshakeManager.continueHandshake` (initiator-completion path) use two different, inconsistent inputs when enforcing the lighthouse `remote_allow_list` against an incoming peer. The responder checks the allow list against the full, certificate-verified set of `vpnAddrs` derived from the just-validated peer certificate. The initiator instead checks the allow list against the *pre-verification*, locally-assumed `hostinfo.vpnAddrs` (the address it originally intended to handshake with), and never re-runs the check against the actual verified `vpnAddrs` it computes afterward.

### Finding Description
In the responder flow, `validatePeerCert` is called only *after* the peer certificate has been cryptographically verified, and it applies `GetRemoteAllowList().AllowAll(vpnAddrs, via.UdpAddr.Addr())` using the full `vpnAddrs` list taken from the verified certificate's networks: [1](#0-0) 

In the initiator flow (`continueHandshake`), the allow-list check happens *before* `machine.ProcessPacket` verifies the peer's certificate, and it uses `hostinfo.vpnAddrs` — the address the initiator originally targeted (e.g. from `StartHandshake`), not anything derived from the peer's certificate: [2](#0-1) 

After the certificate is verified, the function derives the real `vpnAddrs` set from `remoteCert.Certificate.Networks()` and only checks that one entry matches the *original* target (`correctHostResponded`); it does not re-invoke the `remote_allow_list` check against this newly-derived, verified `vpnAddrs` set: [3](#0-2) 

This mirrors the external report's root cause: two code paths that are supposed to enforce the same security invariant select different values (pre- vs post-verification identity/address) for that enforcement, and only one of them is checked against the value that is actually cryptographically authenticated. A peer certificate can legitimately encode multiple VPN networks; on the initiator side, only the single originally-targeted address is ever checked against `remote_allow_list`, so any additional network entries carried in the verified certificate bypass that firewall-style control entirely — a control that the responder path applies uniformly to the whole verified set.

### Impact Explanation
`remote_allow_list` is Nebula's mechanism for restricting which physical/underlay addresses are permitted to be associated with a given VPN identity — a firewall-style trust control at the handshake layer. Because the initiator path checks this control against stale, unverified data instead of the certificate-verified `vpnAddrs`, additional VPN addresses asserted by a peer's certificate are not subjected to the same enforcement that the responder side applies. This is an inconsistent, incomplete enforcement of an authentication/allow-list boundary reachable by any untrusted peer initiating or completing a handshake, without requiring a CA-signed certificate beyond what the protocol already requires for any peer.

### Likelihood Explanation
This code path executes on every initiator-side handshake completion (`continueHandshake`), so the inconsistency is reachable in normal peer-to-peer operation whenever a responding certificate encodes more than one VPN network/address, making it a straightforward divergence to trigger without any special privileges.

### Recommendation
Apply `GetRemoteAllowList().AllowAll(...)` consistently using the certificate-verified `vpnAddrs` (post `machine.ProcessPacket`) in `continueHandshake`, mirroring `validatePeerCert`'s behavior in `beginHandshake`, rather than (or in addition to) checking the pre-verification `hostinfo.vpnAddrs`.

### Proof of Concept
1. Configure a `remote_allow_list` that permits underlay address `A` only for VPN address `10.0.0.5`.
2. Node `M` initiates a handshake toward `10.0.0.5` (`hostinfo.vpnAddrs = [10.0.0.5]`) via underlay address `A` — the pre-verification allow-list check in `continueHandshake` (line 833) passes.
3. The peer's real certificate, once verified, also asserts an additional network, e.g. `10.0.0.6`, which is not covered by the allow list for address `A`.
4. Because `correctHostResponded` only requires that `10.0.0.5` be among the verified networks, the handshake completes and `hostinfo.vpnAddrs` is overwritten with the full verified set including `10.0.0.6` (line 966) without the allow list ever being checked against `10.0.0.6`, unlike what would occur on the responder side via `validatePeerCert`.
