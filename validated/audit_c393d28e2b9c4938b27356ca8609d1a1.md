### Title
Serialized-writes locking is bypassed for real `git push` traffic because the `reference-transaction` hook client skips the `preparing` phase, reintroducing the cross-node ABBA ref-lock deadlock - ([File: cmd/gitaly-hooks/hooks.go])

### Summary
Praefect's "serialized writes" feature is supposed to prevent a cluster-wide deadlock by acquiring a repository-scoped lock during the `preparing` phase of Git's `reference-transaction` hook, *before* any Gitaly node takes an on-disk ref lock. However, the hook client binary that Git actually invokes on every real push (`cmd/gitaly-hooks/hooks.go`) unconditionally short-circuits the `preparing` case and never forwards it to Gitaly's `ReferenceTransactionHook` RPC. Consequently, for ordinary user pushes the Praefect-side lock is never acquired, and the exact deadlock scenario the feature was built to eliminate remains fully reachable by two concurrent, unprivileged pushes.

### Finding Description
`doc/serialized_writes.md` explains that the fix for the ABBA-style cluster deadlock is to serialize transactions **before** any node takes an on-disk ref lock, using the new `preparing` phase of Git's `reference-transaction` hook: [1](#0-0) 

The write path for the lock lifecycle is driven entirely by which `VoteTransactionRequest_Phase` is received: `PREPARING_PHASE` acquires the write lock, `PREPARED_PHASE` renews it, `COMMITTED_PHASE` releases it: [2](#0-1) 

Praefect's `lockRepoForTransaction` implements exactly this: it only stores a lock in `mgr.repoLocks` when it observes `PREPARING_PHASE`; for `PREPARED_PHASE`/`COMMITTED_PHASE` it looks the stored lock up, and if none is found it explicitly logs and *skips* the lock/renew logic entirely, assuming this only happens for old Git builds that don't emit the `preparing` phase at all: [3](#0-2) 

`internal/gitaly/hook/referencetransaction.go` correctly maps a `preparing` state to `voting.Preparing` and would cast the serializing vote if it were invoked: [4](#0-3) 

The problem is that for a real `git push`, Git itself invokes the external `reference-transaction` hook binary with `preparing`/`prepared`/`committed` as `argv[1]`, and that binary (`cmd/gitaly-hooks/hooks.go`'s `referenceTransactionHook`) unconditionally returns `nil` for the `preparing` case without ever calling the `ReferenceTransactionHook` RPC, based on a stale comment claiming the server handler is a "no-op": [5](#0-4) 

This means the `PREPARING_PHASE` vote is never sent to Praefect for real, Git-driven pushes — only Gitaly's *internal* write paths (`repoutil.Create`, `update_with_hooks.go`, `objectpool/fetch.go`, `transaction/voting.go::CommitLockedFile`, etc., listed in the doc) drive the `Preparing` phase directly through the `hook.GitLabHookManager.ReferenceTransactionHook` Go API rather than through the external hook binary: [6](#0-5) 

Because `mgr.repoLocks` never gets populated for the ordinary push path, when the `prepared`/`committed` votes for that same transaction later arrive, `lockRepoForTransaction` finds no stored lock and silently no-ops (log message: "skipping lock check: no preparing phase recorded"). No PostgreSQL-backed write lock is ever taken or held for that repository during the push's ref-locking window.

### Impact Explanation
Without the pre-lock serialization, two ordinary, unprivileged users can independently push to the same repository with overlapping ref sets, racing each other across Gitaly nodes. As `doc/serialized_writes.md` describes, this reproduces the classic distributed deadlock: Node 1 locks ref A for transaction T1 and ref B for T2, while Node 2 locks ref B for T1 and ref A for T2. Neither transaction can proceed past the on-disk lock because each is waiting on the other node's quorum, and neither can release its lock until quorum is reached — a genuine cluster-wide deadlock/DoS of the write path for that repository, triggered purely by concurrent, otherwise legitimate pushes.

### Likelihood Explanation
This does not require a privileged actor, a leaked token, a malicious peer, or a MITM: two ordinary users (or one user with concurrent client threads/CI jobs) pushing to the same repository with overlapping branches is a normal, easily reproducible condition in any actively used Gitaly Cluster. The bug is deterministic given the code path shown — the `preparing` case is unconditionally skipped, not behind a feature flag check, so the serialization the feature promises is dormant for the primary user-facing entry point (real `git push`) while only functioning for a subset of internal RPC-driven write paths.

### Recommendation
Remove the early `return nil` for the `preparing` case in `cmd/gitaly-hooks/hooks.go`'s `referenceTransactionHook`, and forward it to the `ReferenceTransactionHook` RPC the same way `prepared`/`committed`/`aborted` are handled, so that ordinary `git push` traffic actually participates in the pre-lock serialization Praefect implements. Additionally, add integration/regression test coverage that exercises the *external* hook binary path (not just the internal `hook.GitLabHookManager` Go API) to confirm the `PREPARING_PHASE` vote is cast for genuine pushes, since the current tests (e.g. `TestPraefectWriteSerialization_HangAfterPrepared`) only exercise the internal manager/lock behavior and would not have caught this gap.

### Proof of Concept
1. Deploy a Gitaly Cluster (Praefect) with the `PraefectSerializedWrite` feature flag enabled and at least two Gitaly nodes/replicas.
2. From two separate unprivileged clients, concurrently `git push` to the same repository, each updating two overlapping branches (`A` and `B`) such that the reference-transaction hook fires per-ref on each node in a different order (e.g., due to differing packing/hook invocation ordering as called out in `internal/gitaly/hook/updateref/update_with_hooks.go`).
3. Observe via logs/metrics that no `repository_reference_write_locks` row is created for either transaction's `PREPARING_PHASE` (because the external hook script returns early for `preparing`), and that both transactions proceed straight to on-disk ref locking on both nodes concurrently.
4. Confirm the two transactions deadlock exactly as described in `doc/serialized_writes.md`'s "Why Serialize Writes" section — each waiting on the other's quorum — until an RPC-level timeout eventually cancels one side, demonstrating the reintroduced DoS window that the serialized-writes feature was designed to close.

```markdown
The problem is that at the `prepared` phase, **on-disk ref locks have already
been taken**. With two concurrent transactions T1 and T2 updating overlapping
refs A and B:

1. Node 1: T1 locks A, T2 locks B
1. Node 2: T2 locks A, T1 locks B

Each transaction is now waiting for the other to release a lock, and neither
can release until quorum is reached for its own lock. The cluster is
deadlocked.

The fix is to serialize transactions **before** any node has taken an on-disk
ref lock. If only one transaction per repository can advance past this point at
a time, lock acquisition order is globally consistent and the deadlock above
cannot occur.
```

```markdown
`internal/praefect/transactions/manager.go` owns the lock lifecycle. A
repository-scoped write lock backed by PostgreSQL is acquired, renewed, and
released according to the phase of each `VoteTransaction` call:

| Phase            | Action                                                  |
|------------------|---------------------------------------------------------|
| `PREPARING_PHASE`| `WriteLockManager.Lock` — block until exclusive access  |
| `PREPARED_PHASE` | `lock.Renew` — keep the lock alive across phases        |
| `COMMITTED_PHASE`| `lock.Unlock` — release once the write is durable       |

If any phase fails before commit, the deferred
`unlockRepoForTransaction` releases the lock so the next transaction can
proceed. Transactions that are explicitly stopped or canceled
(`StopTransaction`, `cancelTransaction`) also release the lock to avoid
stranding it in PostgreSQL.
```

```go
func (mgr *Manager) lockRepoForTransaction(ctx context.Context, transactionID uint64, storageName, repoRelativePath string,
	phase gitalypb.VoteTransactionRequest_Phase,
) error {
	if featureflag.PraefectSerializedWrite.IsDisabled(ctx) {
		return nil
	}

	switch phase {
	case gitalypb.VoteTransactionRequest_PREPARING_PHASE:
		lock, err := mgr.repoWriteLockMgr.Lock(ctx, storageName, repoRelativePath, transactionID)
		if err != nil {
			return fmt.Errorf("try lock: %w", err)
		}
		mgr.repoLocks.Store(transactionID, lock)

	case gitalypb.VoteTransactionRequest_PREPARED_PHASE, gitalypb.VoteTransactionRequest_COMMITTED_PHASE:
		v, ok := mgr.repoLocks.Load(transactionID)
		if !ok {
			// No Preparing was cast for this transaction. This happens when Git itself drives
			// the reference-transaction hook on a Git build that doesn't emit "preparing"
			// (i.e. pre-2.54). Skip lock work; serialization is dormant for this path
			// until GIT_VERSION_PREV is bumped past 60d8c1e9.
			mgr.logger.WithFields(log.Fields{
				"transaction.id": transactionID,
				"phase":          phase.String(),
			}).DebugContext(ctx, "skipping lock check: no preparing phase recorded")
			return nil
		}
		lock := v.(datastore.RepoLock)
		if err := lock.Renew(ctx); err != nil {
			return err
		}
	}
```

```go
func referenceTransactionHook(ctx context.Context, payload gitcmd.HooksPayload, hookClient gitalypb.HookServiceClient, args []string) error {
	if len(args) != 1 {
		return fmt.Errorf("reference-transaction hook is missing required arguments, got %q", args)
	}

	var state gitalypb.ReferenceTransactionHookRequest_State
	switch args[0] {
	case "preparing":
		// state = gitalypb.ReferenceTransactionHookRequest_PREPARING
		// Skip invoking the RPC for the "preparing" phase as the server-side handler
		// is currently a no-op for this state.
		return nil
	case "prepared":
		state = gitalypb.ReferenceTransactionHookRequest_PREPARED
	case "committed":
		state = gitalypb.ReferenceTransactionHookRequest_COMMITTED
	case "aborted":
		state = gitalypb.ReferenceTransactionHookRequest_ABORTED
	default:
		return fmt.Errorf("reference-transaction hook has invalid state: %q", args[0])
	}
```
