### Title
Inverted expiration check in `lookup_peer` treats expired peer keys as valid and valid keys as invalid - (File: stackslib/src/net/p2p.rs)

### Summary
`PeerNetwork::lookup_peer` in `stackslib/src/net/p2p.rs` is documented to "Get the neighbor if we know of it and it's public key is unexpired," but the implementation's comparison is inverted: it returns `Some(neighbor)` when the neighbor's key is *already expired* (`expire_block < cur_block_height`), and returns `None` (i.e., "unknown/not usable") when the key is still valid. [1](#0-0) 

### Finding Description
The function's contract, per its own doc comment, is to return the stored `Neighbor` only if its public key has not expired relative to the current burnchain block height:

```rust
/// Get the neighbor if we know of it and it's public key is unexpired.
fn lookup_peer(
    &self,
    cur_block_height: u64,
    peer_addr: &SocketAddr,
) -> Result<Option<Neighbor>, net_error> {
    ...
    match neighbor_opt {
        None => Ok(None),
        Some(neighbor) => {
            if neighbor.expire_block < cur_block_height {
                Ok(Some(neighbor))
            } else {
                Ok(None)
            }
        }
    }
}
``` [2](#0-1) 

This is precisely inverted: `neighbor.expire_block < cur_block_height` means the key's expiry block has already passed (expired), yet in that branch the function returns `Some(neighbor)` (treats it as valid/usable). Conversely, when the key is still within its valid window (`expire_block >= cur_block_height`), the function returns `None`, effectively discarding a currently-valid, non-expired peer entry as if it were unknown.

This mirrors the bug class in the referenced report: expired credentials/tokens (here, a peer's handshake public key with its `expire_block`) are not correctly excluded from being considered valid — the equality/comparison that should gate "is this credential still current" is broken, so an expired credential passes the gate while a currently valid one fails it.

For comparison, the equivalent and correctly-implemented check exists elsewhere in the same file, `Neighbor::load_by_address`, which correctly treats `peer.expire_block < block_height` as "expired" and returns `None`: [2](#0-1) 
This asymmetry confirms `lookup_peer`'s logic is the inverted/buggy one relative to the codebase's own established pattern for "unexpired" checks (e.g., `Neighbor::load_by_address` at lines 94-113 in `stackslib/src/net/neighbors/neighbor.rs`, which correctly returns `None` for `peer.expire_block < block_height`).

If so, this inversion could cause the node to treat a peer whose signing key has expired as still trusted (an auth-gate failing open for stale/expired keys) while spuriously discarding legitimate, currently-valid peer state — a "serving stale/expired identity as canonical" defect analogous to the reported issue.

### Recommendation
Fix the comparison in `lookup_peer` to match its documented intent and the pattern used elsewhere in the codebase (e.g. `Neighbor::load_by_address`):
```rust
if neighbor.expire_block < cur_block_height {
    Ok(None)          // expired -> not usable
} else {
    Ok(Some(neighbor)) // unexpired -> usable
}
```
A background engineer should also trace all call sites of `lookup_peer` to confirm what security decision relies on its output, in order to precisely characterize the real-world impact of this inversion.
