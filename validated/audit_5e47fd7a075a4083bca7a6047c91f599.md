## Title
Missing user-supplied slippage/min-out protection on Kamino/Solend/Drift/JupLend deposit and withdraw instructions - (File: `programs/marginfi/src/instructions/kamino/deposit.rs`, `programs/marginfi/src/instructions/kamino/withdraw.rs`, `programs/marginfi/src/instructions/solend/deposit.rs`, `programs/marginfi/src/instructions/drift/withdraw.rs`, `programs/marginfi/src/instructions/juplend/deposit.rs`, `programs/marginfi/src/instructions/juplend/withdraw.rs`)

### Summary
Like the ERC4626Router `liquidate()`/`invest()`/`fulfillRedeemRequest()` bug, marginfi's external-protocol wrapper instructions (`kamino_deposit`, `kamino_withdraw`, `solend_deposit`, `solend_withdraw`, `drift_withdraw`, `juplend_deposit`, `juplend_withdraw`) compute an "expected" collateral/share/token amount from the *current on-chain exchange rate at execution time* and validate the CPI result against that freshly computed value, but never let the caller supply a user-chosen minimum/maximum bound reflecting the rate they saw when they built and signed the transaction.

### Finding Description
Each of these instructions follows the same pattern: read the current reserve/market state, compute `expected_collateral_amount` / `expected_shares` from it, perform the CPI, then assert the actual delta matches (or is within 1 unit of) that expectation: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

This check only proves *internal consistency* (the CPI behaved as the reserve's state predicted at the moment of execution) — it does nothing to protect the caller against the reserve's exchange rate having moved (via legitimate interest accrual, or via an attacker manipulating utilization/borrow rate in a preceding transaction in the same slot/bundle) between the time the user signed the transaction and the time it lands on-chain. None of these instructions accept a caller-supplied `min_collateral_out`, `min_shares_out`, or `max_amount_in` parameter, confirmed by the absence of any `min_out`/`slippage`/`minimum_amount` handling in these paths.

This is architecturally the same gap called out in the report for ERC4626Router: the deposit/withdraw functions "have validation ... but this does not protect against slippage," because the validation is derived from state read inside the same instruction rather than from the caller's original intent.

### Impact Explanation
If a Kamino/Solend/Drift/JupLend reserve's exchange rate can be shifted between when a user constructs a `kamino_deposit`/`solend_deposit`/etc. transaction and when it executes (e.g., a large borrow/repay or interest-rate model transaction landing first in the same slot/bundle), the user could receive materially fewer collateral tokens (on deposit) or fewer underlying tokens (on withdraw) than they intended, with the instruction still succeeding because the "expected" value is recomputed from the already-shifted state. This is a value-loss/slippage issue for the depositing/withdrawing user, not a protocol-wide insolvency vector, since marginfi's own share accounting (`bank_account.deposit_no_repay`/`withdraw`) is always kept internally consistent with whatever amount was actually received.

### Likelihood Explanation
Exploitability is significantly lower than the EVM analog cited in the report. Solana transactions are atomic, so an attacker cannot literally sandwich (interleave arbitrary manipulation between the rate read and the CPI) within the victim's own transaction — the rate read and the CPI execute back-to-back inside the same instruction/transaction. To realize the vulnerability, an attacker needs a leader/searcher-level ability to land a manipulating instruction (e.g. a large Kamino/Solend borrow) in the same slot immediately before the victim's transaction, which requires either colluding with a block producer, using Jito-style bundles, or exploiting normal price volatility/interest accrual over time between signing and landing. This is real but requires more infrastructure than a generic EVM mempool sandwich attack, and mrgn's own risk-model documentation (guides for Kamino/JupLend integrations) already flags reserve-state related risks; there is no explicit mitigation for this specific slippage scenario in the reviewed code paths.

### Recommendation
Add an optional caller-supplied slippage bound to each of `kamino_deposit`, `kamino_withdraw`, `solend_deposit`, `solend_withdraw`, `drift_deposit`, `drift_withdraw`, `juplend_deposit`, `juplend_withdraw` (e.g., `min_collateral_out: Option<u64>` for deposits, `min_underlying_out: Option<u64>` for withdraws), and `require!` the actual received/burned amount respects that bound before finalizing marginfi-side accounting, mirroring the fix already applied in ERC4626Router PR #244.

### Proof of Concept
Not independently reproducible from static review: it requires the ability to land a rate-manipulating instruction (e.g., a Kamino/Solend borrow spike) in the same slot/bundle immediately ahead of a victim's `kamino_deposit`/`solend_deposit`/`juplend_deposit` transaction, which is outside what can be demonstrated purely from the indexed source. The code-level root cause (absence of any caller-supplied min/max bound in the deposit/withdraw instruction signatures) is directly confirmed by inspection of the cited files.
