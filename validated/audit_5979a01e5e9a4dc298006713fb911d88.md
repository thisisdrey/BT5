### Title
NULL pointer dereference on `AssetIssueV2Store` lookup in `UpdateAssetActuator.execute()` - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateAssetActuator.java`)

### Summary
`UpdateAssetActuator.execute()` unconditionally fetches an `AssetIssueCapsule` from `assetIssueV2Store` keyed by `accountCapsule.getAssetIssuedID()` and immediately dereferences it, without a null check, mirroring the `es58x_dev->udev->serial` NULL-dereference bug class: a field assumed to always be populated is dereferenced without validation, and `validate()` does not actually guarantee that assumption for the code path taken in `execute()`.

### Finding Description
In `execute()`: [1](#0-0) 
```
AccountCapsule accountCapsule = accountStore.get(ownerAddress);
...
assetIssueCapsuleV2 = assetIssueStoreV2.get(accountCapsule.getAssetIssuedID().toByteArray());
assetIssueCapsuleV2.setFreeAssetNetLimit(newLimit);
```
This lookup and dereference happen **before** the `allowSameTokenName` branch, i.e. for every call regardless of which token-naming mode is active.

`validate()`, however, only checks the `AssetIssueV2Store` entry conditionally: [2](#0-1) 
```
if (dynamicStore.getAllowSameTokenName() == 0) {
  if (account.getAssetIssuedName().isEmpty()) { ... }
  if (assetIssueStore.get(account.getAssetIssuedName().toByteArray()) == null) { ... }
} else {
  if (account.getAssetIssuedID().isEmpty()) { ... }
  if (assetIssueV2Store.get(account.getAssetIssuedID().toByteArray()) == null) { ... }
}
```
When `allowSameTokenName == 0`, `validate()` never checks `assetIssueV2Store` for the `AssetIssuedID` key at all — it only validates `assetIssueStore` (the legacy V1 store) keyed by `AssetIssuedName`. If an account's `AssetIssuedID` field is empty or does not correspond to any entry in `assetIssueV2Store` (e.g., accounts whose asset metadata was migrated/backfilled inconsistently by `AssetUpdateHelper.updateAccount()`, which populates `AssetIssuedID` from a name→id map that can be absent for some entries — [3](#0-2) ), then `assetIssueStoreV2.get(...)` in `execute()` returns `null`, and the very next line `assetIssueCapsuleV2.setFreeAssetNetLimit(newLimit)` throws an unguarded `NullPointerException`.

### Impact Explanation
Since `UpdateAssetContract` is reachable by any account that has previously issued an asset (broadcastable transaction type processed through the standard actuator flow, see `RuntimeImpl.execute()` [4](#0-3) ), a crafted/legacy account state can cause `execute()` to throw an unchecked `NullPointerException` rather than a handled `ContractExeException`. Because `RuntimeImpl.execute()` (and block application in `Manager`) only catches `ContractValidateException`/`ContractExeException` around actuator invocation, an uncaught `NullPointerException` at this call site can propagate out of the intended exception-handling path during block processing, risking node-level instability/crash when replaying or processing such a transaction — a node crash/DoS impact analogous to the kernel NULL-deref bug.

### Likelihood Explanation
Likelihood is moderate: it requires an account whose `AssetIssuedName` is non-empty (so passes the `allowSameTokenName==0` V1 checks) but whose `AssetIssuedID` is empty/stale/unmapped in `assetIssueV2Store`. This state is plausible for accounts that issued assets prior to full V1→V2 asset-store synchronization, or through the migration helper `AssetUpdateHelper.updateAccount()`, which can leave `AssetIssuedID` unset if `assetNameToIdMap` lacks the corresponding name key. An attacker/account owner who discovers such a state (or engineers it) can broadcast an `UpdateAssetContract` transaction to trigger the crash deterministically.

### Recommendation
Add a null check on `assetIssueCapsuleV2` (and mirror the corresponding V1 check on `accountCapsule.getAssetIssuedID()`/store lookup) immediately after the `assetIssueStoreV2.get(...)` call in `execute()`, throwing a `ContractExeException` instead of allowing the raw `NullPointerException` to propagate — consistent with how other actuators guard `AccountCapsule`/`AssetIssueCapsule` lookups. Additionally, extend `validate()` to check `assetIssueV2Store` for the `AssetIssuedID` key even when `allowSameTokenName == 0`, so the invariant assumed by `execute()` is actually enforced before execution.

### Proof of Concept
1. Produce (via legacy issuance/migration path or by directly manipulating account state in a test/private network) an `AccountCapsule` where `AssetIssuedName` is non-empty and matches an entry in `assetIssueStore`, but `AssetIssuedID` is empty or does not match any key in `assetIssueV2Store`.
2. Broadcast an `UpdateAssetContract` transaction from that account (with `allowSameTokenName == 0`).
3. `validate()` passes because it only checks `assetIssueStore` in this mode.
4. `execute()` calls `assetIssueStoreV2.get(accountCapsule.getAssetIssuedID().toByteArray())`, which returns `null`.
5. The following line `assetIssueCapsuleV2.setFreeAssetNetLimit(newLimit)` throws `NullPointerException`, uncaught by the actuator's `try/catch(InvalidProtocolBufferException)` block.
