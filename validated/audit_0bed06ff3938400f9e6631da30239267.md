### Title
Unvalidated attacker-controlled offset/length in `extractSigArray`/`extractBytesArray` causes out-of-bounds array access reachable via the `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The libarchive CVE is an out-of-bounds read caused by trusting an attacker-supplied length/offset field while decoding a crafted archive without validating it against the buffer bounds. The closest reachable analog in java-tron is the manual ABI-array decoding helpers used by the `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts, which compute byte offsets and lengths directly from attacker-controlled calldata words and then slice the raw input buffer without full bounds checking.

### Finding Description
`extractSigArray` and `extractBytesArray` compute an index (`bytesOffset`) and, for `extractBytesArray`, a length (`bytesLen`) purely from `DataWord` values taken out of the caller-supplied `data`/`rawData` byte array: [1](#0-0) [2](#0-1) 

The extracted offset/length are passed straight into `extractBytes`, which performs `Arrays.copyOfRange(data, offset, offset + len)`: [3](#0-2) 

`Arrays.copyOfRange` throws `ArrayIndexOutOfBoundsException` when `from` is negative or greater than `data.length` (integer overflow of the multiplication `(bytesOffset + offset + 2) * WORD_SIZE` can easily produce such a value), and `new byte[len][]` in the callers can throw `NegativeArraySizeException`/`OutOfMemoryError` if `len` (an `intValueSafe()` of a fully attacker-controlled 256-bit word) is negative or huge.

These helpers are invoked from `ValidateMultiSign.execute()`: [4](#0-3) 

Note that `ValidateMultiSign.execute()` only wraps the *post-extraction* permission/weight logic in a `try { ... } catch (Throwable t)` block; the call to `extractSigArray`/`extractBytesArray` at lines 1072-1074 sits **outside** that try block, so any `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` thrown while slicing `rawData` is uncaught within `execute()`. By contrast, `BatchValidateSign.execute()` explicitly wraps its whole body (`doExecute`) in a `try { ... } catch (Throwable t)`, which suggests the missing guard on `ValidateMultiSign` is an oversight relative to its sibling precompile: [5](#0-4) 

The codebase does contain a newer, hard-fork-gated mitigation (`isValidAbiEncoding` + `VMConfig.allowTvmOsaka()`) that performs coarse length validation before parsing, but this only activates when that specific hard fork flag is enabled, and even when enabled it does not fully bound every derived offset used inside `extractSigArray`/`extractBytesArray` (it only checks total-length modular alignment, not that every computed `bytesOffset`/`bytesLen` stays within `data.length`): [6](#0-5) [7](#0-6) 

### Impact Explanation
Any account can reach these precompiles by broadcasting a `TriggerSmartContract` (or having a deployed contract) that calls the `ValidateMultiSign` precompiled address with crafted calldata containing out-of-range offset/length words. If the resulting exception propagates uncaught out of `PrecompiledContracts` and is not otherwise generically caught at the VM `Program`/interpreter layer, it can abort transaction/block execution in an unexpected way rather than cleanly reverting, which is a node-availability risk during transaction processing or block replay. I was not able to fully confirm, within the available context, whether the outer VM call-dispatch layer in `Program.java` generically catches all `Throwable`/`RuntimeException` from precompile execution (my last tool call to inspect that specific catch behavior was cut off before I could review it), so the exact blast radius (clean revert vs. execution-halting exception) is uncertain and should be verified directly against `actuator/src/main/java/org/tron/core/vm/program/Program.java`.

### Likelihood Explanation
Likelihood is high for triggering the exception path: constructing calldata with an out-of-range offset word requires no special privilege, just any account able to invoke a contract that calls the precompiled address (or a directly deployed proxy contract), consistent with the "unprivileged transaction broadcaster / contract deployer" reachability required by the scope rules.

### Recommendation
- Add explicit bounds validation in `extractSigArray` and `extractBytesArray` (and in `extractBytes`) that rejects negative or out-of-range `bytesOffset`/`bytesLen`/computed absolute offsets before slicing `data`, independent of the `allowTvmOsaka()` feature flag.
- Wrap the `extractSigArray`/`extractBytesArray` calls in `ValidateMultiSign.execute()` in the same defensive `try { ... } catch (Throwable t)` pattern already used in `BatchValidateSign.execute()` so malformed input degrades to a `DATA_FALSE`/revert result instead of an uncaught runtime exception.
- Clamp `len` derived from `intValueSafe()` to a sane maximum before array allocation to prevent `NegativeArraySizeException`/excessive allocation attempts.

### Proof of Concept
Craft a `TriggerSmartContract` transaction whose target executes a `STATICCALL`/`CALL` to the `ValidateMultiSign` precompiled address (`getPermissionId`/multi-sig validation precompile) with calldata where word `[3]` (the signatures-array pointer) encodes an offset that, after the `bytesOffset = words[offset+i+1].intValueSafe() / WORD_SIZE` computation and `(bytesOffset + offset + 2) * WORD_SIZE` arithmetic, resolves to a value negative or far beyond `rawData.length`. This drives `extractBytes`'s `Arrays.copyOfRange(data, offset, offset+len)` call outside the array bounds, throwing an uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` from within `ValidateMultiSign.execute()` before the surrounding `try/catch` in the code is reached.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
