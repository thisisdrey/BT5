### Title
User-controlled `gas` field in `Command::CallContract` is trusted without a minimum bound, enabling permanent gas-starvation of Snowbridge outbound messages - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs`)

### Summary
The Snowbridge outbound queue (Polkadot → Ethereum direction) computes the gas amount forwarded to the Gateway contract on Ethereum for each command. For most commands this gas figure is a hardcoded, protocol-chosen constant. For `Command::CallContract`, however, the gas value is taken verbatim from the caller-supplied `gas` field with no lower bound enforced, structurally identical to the LayerZero report's unchecked `_dstGasForCall`.

### Finding Description
`ConstantGasMeter::maximum_dispatch_gas_used_at_most` computes the gas to embed in the committed message for each `Command` variant: [1](#0-0) 

For every other command (`SetOperatingMode`, `Upgrade`, `UnlockNativeToken`, `RegisterForeignToken`, `MintForeignToken`) the gas is a fixed constant computed by the protocol. But for `CallContract`, the gas is `*gas_limit`, taken straight from the `Command::CallContract { gas, .. }` field: [2](#0-1) 

This value flows unchanged into `OutboundCommandWrapper.gas` and then into the ABI-encoded `CommandWrapper.gas` that is committed into the merkle root and ultimately consumed by the Ethereum Gateway contract to bound the gas forwarded to the `target` contract: [3](#0-2) 

`do_process_message` performs no validation that `gas` in `CallContract` is above any protocol-enforced minimum (e.g., enough to cover the EIP-150 63/64 rule buffer or the base cost of recording a delivery receipt on the Ethereum side, as `ConstantGasMeter`'s own doc comment for other commands explicitly accounts for). Nothing in `do_process_message` rejects a `CallContract` command with e.g. `gas: 1`.

This is the exact broken invariant from the external report: a user-facing message field that determines how much execution budget the destination side receives is fully attacker/user-controlled and unenforced by the sending side, while the destination (Ethereum Gateway) treats delivery as consumed/settled regardless of whether the forwarded call succeeds or runs out of gas.

### Impact Explanation
On Ethereum, the Gateway's inbound message processing charges/refunds relayers based on gas actually used up to the committed `gas` value and marks the nonce as processed regardless of whether the forwarded `CallContract` execution itself succeeds (this mirrors the LayerZero delivery-receipt semantics called out in the original report — the message transitions to a terminal state on the destination even if the forwarded call fails due to insufficient gas). Because `gas` is attacker-controlled with no minimum, a malicious or careless BridgeHub-side sender of `CallContract` commands can under-fund the destination execution, causing:
- Guaranteed reverts of the intended cross-chain contract call on Ethereum.
- Fund loss for relayers/paying parties if refund accounting assumes successful gas metering matching `maximum_dispatch_gas_used_at_most`.
- No local (Substrate-side) mechanism to detect or prevent this before commitment, since the outbound queue commits and charges fees purely from `T::WeightToFee`/`GasMeter` output without a floor check on user-supplied gas.

This does not directly "permanently block the bridge lane" the way LayerZero's STORED state does (Snowbridge's V2 outbound queue is nonce-based per-message, not a single blocking channel), so the severity is lower than the original High-severity LayerZero finding — but it is a real instance of the same missing-minimum-gas invariant, causing guaranteed failed dispatch and fee/gas mischarging on the destination chain for an unprivileged, user-reachable code path (`CallContract` commands originate from XCM `Transact`/system pallet calls that plausibly accept user-influenced parameters depending on runtime wiring).

### Likelihood Explanation
Likelihood is High for triggering the broken invariant (any caller who can construct a `Command::CallContract` with an arbitrarily low `gas` value will trigger it — no signature or privileged role is needed to set the field itself), but the overall exploitability depends on which unprivileged origin can actually get raw `Command::CallContract` gas values accepted by the runtime's message-construction layer. `Command::CallContract` requires access via the `snowbridge-pallet-system-v2`/`EthereumBlobExporter` message path — I could not verify from the index whether an ordinary user (rather than governance or an XCM-`Transact` origin already checked elsewhere) can set `gas` for this specific command in the current runtime wiring, so likelihood for full unprivileged exploitation is uncertain and would need code review in `bridges/snowbridge/pallets/system-v2` and its associated XCM converter.

### Recommendation
Enforce a protocol-defined minimum gas floor for `Command::CallContract` (and any other future user-suppliable gas commands) inside `ConstantGasMeter::maximum_dispatch_gas_used_at_most` or `do_process_message`, e.g. `max(user_supplied_gas, MIN_CALL_CONTRACT_GAS)`, and reject/clamp values below the floor before the message is queued and committed, mirroring the protection already applied to the other hardcoded-gas commands.

### Proof of Concept
1. Construct a `Command::CallContract { target, calldata, gas: 1, value }`.
2. Submit it via whatever path constructs `snowbridge_outbound_queue_primitives::v2::Message` (e.g. via `snowbridge-pallet-system-v2::send` or `EthereumBlobExporter::deliver`).
3. `do_process_message` computes `gas: T::GasMeter::maximum_dispatch_gas_used_at_most(&command)` = `1` (verbatim, per `ConstantGasMeter::maximum_dispatch_gas_used_at_most` at [4](#0-3) ), with no lower-bound check, and commits the message with this gas value into `MessageLeaves`.
4. Once relayed and delivered to the Ethereum Gateway, the forwarded call to `target` will run out of gas and revert, while the Gateway's delivery-receipt/reward mechanism treats the message as delivered — reproducing the underlying "insufficient forwarded gas accepted as valid, destination execution guaranteed to fail" invariant from the original report.

```rust
impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer.maximum_required_gas
			},
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}
```
