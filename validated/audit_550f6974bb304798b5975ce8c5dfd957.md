### Title
Unbounded per-voter iteration in `MaintenanceManager.countVote` / `Wallet.getPaginatedNowWitnessList` allows growth of `VotesStore` to degrade block maintenance and API availability - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
Each `VoteWitnessContract` (and its TVM equivalent `VoteWitnessProcessor`) writes one `VotesCapsule` entry keyed by voter address into `VotesStore`, one entry per distinct account that has ever cast a vote in the current maintenance cycle. Any unprivileged account can create such an entry cheaply by freezing a small amount of TRX and voting. At every maintenance boundary, `MaintenanceManager.doMaintenance()` calls `countVote(votesStore)`, which does a full linear scan over every entry currently in `VotesStore` (a `while (dbIterator.hasNext())` loop with no cap) before it can compute witness vote deltas and continue block application. The same unbounded full-table scan is reachable synchronously from a read-only API through `Wallet.getPaginatedNowWitnessList`.

### Finding Description
`VoteWitnessProcessor.execute` / `VoteWitnessActuator.countVoteAccount` create or update one `VotesStore` entry per unique voting account: [1](#0-0) 

The only bound enforced on a single voting transaction is on the number of distinct witnesses voted for in that transaction (`MAX_VOTE_NUMBER`), not on the number of distinct accounts that can each cast one vote and add their own entry to `VotesStore`: [2](#0-1) 

`MaintenanceManager.doMaintenance()`, invoked from `applyBlock()` on every maintenance-time-crossing block (i.e., a normal part of block application, not gated behind any privileged role), calls `countVote`, which iterates the entire `VotesStore` and deletes each entry: [3](#0-2) [4](#0-3) 

This loop is unbounded by the number of *distinct voter accounts*, which is only constrained by how many TRC10/TRX accounts an attacker is willing to fund with a minimal freeze-and-vote (freezing an amount as small as `1` TRX is sufficient to cast a vote, as shown in test code using `1L` as vote count). As the number of unique voter entries grows (e.g., attacker creates thousands/millions of accounts, each freezing a small stake and voting once per cycle), `countVote`'s in-memory `HashMap` accumulation and the underlying RocksDB iteration cost scale linearly and must complete synchronously as part of block application before the block can be finalized — this is exactly the "iterate over an ever-growing, attacker-influenced array/store" anti-pattern described in the external report (the `allFNUHolders` array there is analogous to the un-capped set of `VotesStore` keys here).

The identical unbounded scan is also reachable directly and synchronously from a read-only gRPC/HTTP API call, `Wallet.getPaginatedNowWitnessList`, via its own `countVote(votesStore)` helper that iterates the full `VotesStore` on every invocation: [5](#0-4) [6](#0-5) 

This means an attacker can force a full linear scan of `VotesStore` on every call to `getpaginatednowwitnesslist` (a public wallet API), not only once per maintenance cycle. Because there is no cap on `VotesStore` size, an attacker willing to spend the freeze/vote fees can grow this store arbitrarily, driving up CPU/latency for every subsequent maintenance cycle and every call to this API.

### Impact Explanation
If the number of `VotesStore` entries grows large enough (via mass account creation + cheap freeze + vote), the mandatory, synchronous `countVote` scan inside `doMaintenance()` could slow down or stall block application at maintenance boundaries, since maintenance is not optional and runs inline with block processing (`applyBlock`). This directly threatens node liveness/availability at chain-wide maintenance boundaries (potential denial-of-service / chain halt risk), and separately, the same unbounded scan is exposed synchronously to unauthenticated clients through `getPaginatedNowWitnessList`, letting an attacker degrade or exhaust API-serving resources without needing any privileged role.

### Likelihood Explanation
Exploitation only requires unprivileged capabilities explicitly in scope: signed `AccountCreateContract`, minimal `FreezeBalanceV2`/`FreezeBalance`, and `VoteWitnessContract` transactions per attacker-controlled account, or the TVM path via `VoteWitnessProcessor`. No SR/witness/committee privilege, no consensus-node compromise, and no network-level attack is needed — only transaction fees and minimal frozen stake per account, which can be automated cheaply at scale. This is a "medium" likelihood, resource/fee-bound attack, comparable to other list-growth DoS vectors in EVM/TVM-style chains.

### Recommendation
- Bound the total number of unique `VotesStore` entries processed per maintenance cycle, e.g., by paginating/batching the `countVote` scan across multiple blocks, or by capping the number of distinct voters tracked, similar to `UNFREEZE_MAX_TIMES` caps elsewhere.
- Consider deriving vote totals from account-level TronPower/vote fields incrementally (e.g., accumulate witness vote deltta at vote time instead of during a full-table scan at maintenance), removing the need to iterate the entire `VotesStore`.
- Rate-limit or cap `Wallet.getPaginatedNowWitnessList` computation, or precompute/cache vote deltas so this API does not perform a full `VotesStore` scan on every call.
- Add an economic floor (minimum freeze amount) to `VoteWitnessContract`/`VoteWitnessProcessor` sufficient to make mass-account vote-spam economically costly relative to the resulting store growth.

### Proof of Concept
1. Programmatically create N attacker-controlled accounts (`AccountCreateContract`).
2. For each account, freeze a minimal amount of TRX (`FreezeBalanceV2Contract`) sufficient to cast 1 vote, then submit `VoteWitnessContract` for any existing witness — this is checked only against `MAX_VOTE_NUMBER` per transaction and account TronPower, not against total `VotesStore` size [2](#0-1) .
3. Each such transaction inserts/updates one entry keyed by the voter's address in `VotesStore` [1](#0-0) .
4. Repeat at scale (thousands to millions of unique voter accounts) within one maintenance cycle.
5. Observe that at the next maintenance boundary, `MaintenanceManager.doMaintenance()`'s call to `countVote` must scan every accumulated entry synchronously as part of `applyBlock`, and that repeated calls to the `getpaginatednowwitnesslist` API each independently perform the same full-table scan, both scaling linearly with attacker-created entries [4](#0-3) [6](#0-5) .

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  public WitnessList getPaginatedNowWitnessList(long offset, long limit) throws
      MaintenanceUnavailableException {
    if (limit <= 0 || offset < 0) {
      return null;
    }
    if (limit > WITNESS_COUNT_LIMIT_MAX) {
      limit = WITNESS_COUNT_LIMIT_MAX;
    }

    /*
      In the maintenance period, the VoteStores will be cleared.
      To avoid the race condition of VoteStores deleted but Witness vote counts not updated,
      return retry error.
      Only apply to requests that rely on the latest block,
      which means the normal fullnode requests with HEAD cursor.
    */
    boolean isMaintenance = chainBaseManager.getDynamicPropertiesStore().getStateFlag() == 1;
    if (isMaintenance && !Args.getInstance().isSolidityNode() && getCursor() == Cursor.HEAD) {
      String message =
          "Service temporarily unavailable during maintenance period. Please try again later.";
      throw new MaintenanceUnavailableException(message);
    }
    // It contains the final vote count at the end of the last epoch.
    List<WitnessCapsule> witnessCapsuleList = chainBaseManager.getWitnessStore().getAllWitnesses();
    if (offset >= witnessCapsuleList.size()) {
      return null;
    }

    VotesStore votesStore = chainBaseManager.getVotesStore();
    // Count the vote changes for each witness in the current epoch, it is maybe negative.
    Map<ByteString, Long> countWitness = countVote(votesStore);

    // Iterate through the witness list to apply vote changes and calculate the real-time vote count
    witnessCapsuleList.forEach(witnessCapsule -> {
      long voteCount = countWitness.getOrDefault(witnessCapsule.getAddress(), 0L);
      witnessCapsule.setVoteCount(witnessCapsule.getVoteCount() + voteCount);
    });

    // Use the same sorting logic as in the Maintenance period
    WitnessStore.sortWitnesses(witnessCapsuleList,
        chainBaseManager.getDynamicPropertiesStore().allowWitnessSortOptimization());

    List<WitnessCapsule> sortedWitnessList = witnessCapsuleList.stream()
        .skip(offset)
        .limit(limit)
        .collect(Collectors.toList());

    WitnessList.Builder builder = WitnessList.newBuilder();
    sortedWitnessList.forEach(witnessCapsule ->
        builder.addWitnesses(witnessCapsule.getInstance()));

    return builder.build();
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
  }
