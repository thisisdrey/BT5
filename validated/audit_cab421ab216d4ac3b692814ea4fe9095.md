### Title
`kamino_harvest_reward` may permanently lock Kamino farm reward tokens by only transferring the pre/post balance delta - ([File: programs/marginfi/src/instructions/kamino/harvest_reward.rs])

### Summary
`kamino_harvest_reward` computes the amount of reward tokens to sweep to the global fee wallet as `post_transfer_balance - pre_transfer_balance` around the Kamino Farms `harvest_reward` CPI, exactly mirroring the Notional `claimCOMPAndTransfer()` pattern that Sherlock rated High. If reward tokens ever land in `user_reward_ata` outside of the delta measured by this single call (e.g. a harvest that lands funds without being immediately swept, a prior partial/failed sweep, or any front-run harvest into the same account), those tokens are never transferred out because only the delta — not the full account balance — is moved to the destination.

### Finding Description
The instruction pattern is: [1](#0-0) 

```
pre_transfer_balance = balance(user_reward_ata)
cpi_harvest_rewards(reward_index)          // Kamino Farms CPI, pays into user_reward_ata
post_transfer_balance = balance(user_reward_ata)
received = post_transfer_balance - pre_transfer_balance
cpi_transfer_obligation_owner_to_destination(received)  // only sweeps `received`
```

`user_reward_ata` is a long-lived token account owned by the bank's `liquidity_vault_authority` PDA (a deterministically-derivable address), not a fresh/ephemeral account created and closed within the same instruction: [2](#0-1) 

The final transfer only moves the just-computed `received` amount, not the full current balance of `user_reward_ata`: [3](#0-2) 

This is the identical root cause identified in the Notional H-1 report: measuring `after - before` around an externally-triggerable claim call, then sweeping only the delta instead of the account's full balance. In Notional's case, anyone could call `COMPTROLLER.claimComp()` directly to zero out the delta for a subsequent `claimCOMPAndTransfer()` call, permanently stranding COMP already sitting in the contract. Here, any tokens that land in `user_reward_ata` without being captured as `received` in the same instruction invocation (whether via direct calls to the Kamino Farms program using the same known PDA-owned ATA, or via any harvest that occurs outside of this exact call) are never subsequently recoverable, because no other marginfi instruction sweeps the full balance of `user_reward_ata` — every call to `kamino_harvest_reward` only ever transfers the incremental amount produced by its own `cpi_harvest_rewards` call.

Notably, the sibling instruction `drift_claim_bad_debt` in the same codebase avoids this exact flaw by sweeping the **entire** balance of the claimant token account rather than the delta: [4](#0-3) 
This asymmetry confirms `kamino_harvest_reward`'s delta-based sweep is the flawed pattern, not an intentional design choice.

I was not able to fully verify from the indexed code whether Kamino's real on-chain Farms program permits an arbitrary caller to directly invoke `harvest_reward` targeting the PDA-owned `user_reward_ata` without going through marginfi (the codebase only exposes the CPI interface via `kamino_mocks::kamino_farms`, not the full external Kamino Farms program source). This is a limitation of what the index can confirm.

### Impact Explanation
If reward tokens accumulate in `user_reward_ata` outside of what a single `kamino_harvest_reward` call's delta captures, those funds become permanently stuck: there is no instruction that sweeps the full balance of `user_reward_ata`, only the just-harvested delta. This is a permanent lock/freeze of reward funds intended for the global fee wallet (and, per the protocol's docs, meant to eventually be redistributed to depositors of the wrapped Kamino bank), satisfying the "permanent lock/freeze" impact bar.

### Likelihood Explanation
`kamino_harvest_reward`'s `Accounts` struct contains no signer/authority check limiting who may invoke it — it is permissionless by design, consistent with other harvest-style instructions in this codebase. The precondition for triggering the lock (external rewards landing in the persistent, PDA-owned `user_reward_ata` outside of the instruction's own before/after window) is analogous to the front-runnable `claimComp()` call in the Notional finding, though full confirmation of external callability of Kamino's real `harvest_reward` against an arbitrary destination ATA could not be verified from the available Kamino Farms program source in this index.

### Recommendation
Sweep the full current balance of `user_reward_ata` to `destination_token_account` after the harvest CPI, rather than only the pre/post delta — mirroring the approach already used in `drift_claim_bad_debt.rs`'s `cpi_transfer_to_destination`.

### Proof of Concept
1. Attacker (or any other actor/process) sends reward-mint tokens into `user_reward_ata` (owned by the bank's `liquidity_vault_authority` PDA) outside of a `kamino_harvest_reward` call's own before/after window — e.g., by directly invoking the underlying Kamino Farms `harvest_reward` for the same obligation/user_state prior to marginfi's instruction landing in the same slot.
2. `pre_transfer_balance` measured in `kamino_harvest_reward` now already includes those tokens.
3. `cpi_harvest_rewards` runs; suppose it credits little/no additional reward this call (already harvested by the attacker), so `post_transfer_balance - pre_transfer_balance` ≈ 0.
4. `cpi_transfer_obligation_owner_to_destination(received)` transfers ~0 tokens to `destination_token_account`.
5. The pre-existing reward balance remains stuck in `user_reward_ata` indefinitely, since no instruction sweeps its full balance — only ever the just-computed delta.

pub fn kamino_harvest_reward(
    ctx: Context<KaminoHarvestReward>,
    reward_index: u64,
) -> MarginfiResult {
    let pre_transfer_balance = accessor::amount(&ctx.accounts.user_reward_ata.to_account_info())?;
    ctx.accounts.cpi_harvest_rewards(reward_index)?;
    let post_transfer_balance = accessor::amount(&ctx.accounts.user_reward_ata.to_account_info())?;
    let received = post_transfer_balance - pre_transfer_balance;
    ctx.accounts
        .cpi_transfer_obligation_owner_to_destination(received)?;
    Ok(())
}

    pub fn cpi_transfer_obligation_owner_to_destination(&self, amount: u64) -> MarginfiResult {
        let program = self.token_program.to_account_info();
        let accounts = TransferChecked {
            from: self.user_reward_ata.to_account_info(),
            to: self.destination_token_account.to_account_info(),
            authority: self.liquidity_vault_authority.to_account_info(),
            mint: self.reward_mint.to_account_info(),
        };
        let bump = self.bank.load()?.liquidity_vault_authority_bump;
        let signer_seeds: &[&[&[u8]]] =
            bank_signer!(BankVaultType::Liquidity, self.bank.key(), bump);
        let cpi_ctx = CpiContext::new_with_signer(program.key(), accounts, signer_seeds);
        let decimals = self.reward_mint.decimals;
        transfer_checked(cpi_ctx, amount, decimals)?;
        Ok(())
    }

    fn cpi_transfer_to_destination(&self) -> MarginfiResult<u64> {
        let amount = accessor::amount(&self.claimant_token_account.to_account_info())?;
        if amount == 0 {

        }

        let accounts = Transfer {

            authority: self.liquidity_vault_authority.to_account_info(),

        let signer_seeds: &[&[&[u8]]] =
            bank_signer!(BankVaultType::Liquidity, self.bank.key(), bump);
        let cpi_ctx = CpiContext::new_with_signer(self.token_program.key(), accounts, signer_seeds);

        token::transfer(cpi_ctx, amount)?;
        Ok(amount)
    }
