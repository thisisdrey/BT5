### Title
Missing `target == current_account_id` check for `ADD_KEY_SELECTOR`/`DELETE_KEY_SELECTOR` allows AddKey/DeleteKey actions to be routed to an attacker-chosen third-party account - (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Finding Description
`parse_tx_data` decodes the Ethereum calldata selector and, for `FUNCTION_CALL_SELECTOR`/`TRANSFER_SELECTOR`, explicitly enforces `target.as_str() != receiver_id.as_str()` against the decoded payload before accepting the action [1](#0-0) . For `ADD_KEY_SELECTOR`/`DELETE_KEY_SELECTOR` no such check exists — the decoded `Action::AddKey`/`Action::DeleteKey` is returned tagged as `ParsableTransactionKind::SelfNearNativeAction` with zero validation of `target` [2](#0-1) .

In `parse_rlp_tx_to_action`, the `SelfNearNativeAction` branch only rewrites the action into a self-transfer when `target_kind == TargetKind::EthImplicit(_)`. For `TargetKind::CurrentAccount` **and** `TargetKind::OtherNearAccount(_)`, the original `AddKey`/`DeleteKey` action is passed through unchanged, tagged `TransactionKind::NearNativeAction` [3](#0-2) .

`TargetKind` is computed generically from the relationship between `target` and the signed Ethereum transaction's `tx.to` field (via `parse_target`/`extract_address`), independent of what calldata selector was actually used [4](#0-3) . Since `tx.to` is fully controlled by the wallet owner at signing time and `account_id_to_address` is a one-way hash the signer can compute forward for *any* known account name, the signer can set `tx.to = account_id_to_address("victim.near")` while embedding `ADD_KEY_SELECTOR`/`DELETE_KEY_SELECTOR` calldata, then have any relayer submit `target = "victim.near"`, which will validate as `TargetKind::OtherNearAccount("victim.near")`.

Finally, in `inner_rlp_execute`, `TransactionKind::NearNativeAction` falls into the default match arm which calls `action_to_promise(target, action)` — using the raw, attacker/relayer-supplied `target`, not `context.current_account_id` [5](#0-4) . `action_to_promise` then issues `Promise::new(target).delete_key(...)` (unrestricted key type) or `Promise::new(target).add_access_key_allowance_with_nonce(...)` (FunctionCall-only, FullAccess is rejected) [6](#0-5) . This sends the AddKey/DeleteKey action to whatever `target` account was supplied, not necessarily the current wallet-contract account, whereas honest usage (see the `register_relayer` test) always sets `target` equal to the wallet's own `current_account_id` for these self-actions [7](#0-6) .

### Impact Explanation
Because the base NEAR receipt-processing model does not require predecessor == receiver authorization for `AddKey`/`DeleteKey` actions delivered via a promise, the wallet contract's security for these self-actions depends entirely on it always targeting `context.current_account_id`. The missing check here breaks that invariant: `DeleteKey` can be routed to remove a key from an unrelated `target` account (if the attacker knows a public key on that account, e.g. any public on-chain key), which can permanently freeze that account if it deletes its sole full-access key; `AddKey` can attach an unauthorized function-call access key to an unrelated `target` account. This maps to the "permanent freezing of user funds" / "authorization escalation across accounts" bounty categories.

### Likelihood Explanation
Preconditions: the transaction signer (an ordinary funded NEAR account owning an eth-implicit wallet-contract account) crafts a normal, validly-signed RLP transaction using `ADD_KEY_SELECTOR`/`DELETE_KEY_SELECTOR` calldata but sets an unrelated `tx.to` value that hashes to a chosen victim account; any relayer (including the attacker themselves) submits `rlp_execute` with `target = victim_account`. No leaked keys, no validator/node privilege, no signature bypass — only crafting of the `tx.to`/`target` pair, which is entirely within an ordinary user's control. The exploit is deterministic and repeatable for any known victim account name.

fn parse_target(target: &AccountId, current_address: Address) -> TargetKind<'_> {
    match extract_address(target) {
        Ok(address) => {
            if address == current_address {
                TargetKind::CurrentAccount
            } else {
                TargetKind::EthImplicit(address)
            }
        }
        Err(_) => TargetKind::OtherNearAccount(target),
    }

fn action_to_promise(target: AccountId, action: near_action::Action) -> Result<Promise, Error> {
    match action {
        near_action::Action::FunctionCall(action) => Ok(Promise::new(target).function_call(
            action.method_name,
            action.args,
            action.deposit,
            action.gas,
        )),
        near_action::Action::Transfer(action) => Ok(Promise::new(target).transfer(action.deposit)),
        near_action::Action::AddKey(action) => match action.access_key.permission {
            near_action::AccessKeyPermission::FullAccess => {
                Err(Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey)))
            }
            near_action::AccessKeyPermission::FunctionCall(access) => Ok(Promise::new(target)
                .add_access_key_allowance_with_nonce(
                    action.public_key,
                    access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
                    access.receiver_id,
                    access.method_names.join(","),
                    action.access_key.nonce,
                )),
        },
        near_action::Action::DeleteKey(action) => {
            Ok(Promise::new(target).delete_key(action.public_key))
        }
    }
