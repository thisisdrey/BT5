### Title
NULL pointer dereference in `Wallet.setAssetNetLimit` when an account's free-asset-usage map references an asset not present in the AssetIssue store — ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getAccountNet` (reachable from the unauthenticated `/wallet/getaccountnet` HTTP endpoint and the corresponding gRPC `GetAccountNet` API) calls the private helper `setAssetNetLimit`, which iterates over the keys of an account's free-asset-net-usage map and unconditionally calls `.getFreeAssetNetLimit()` on the result of `chainBaseManager.getAssetIssueStore().get(key)` (or `getAssetIssueV2Store().get(key)`) without checking for `null`.

### Finding Description
`AssetIssueStore`/`AssetIssueV2Store` return `null` when the queried key does not exist. `setAssetNetLimit` assumes every asset ID recorded in an account's `AllFreeAssetNetUsage`/`AllFreeAssetNetUsageV2` map (populated on the `AccountCapsule` from `frozen`/`asset` protobuf fields, which are attacker-populated at account-creation/asset-participation time and not re-validated against the current live asset table on every read path) still corresponds to an existing `AssetIssueCapsule` in the store:
```java
allFreeAssetNetUsage.keySet().forEach(asset -> {
  byte[] key = ByteArray.fromString(asset);
  assetNetLimitMap
      .put(asset, chainBaseManager.getAssetIssueStore().get(key).getFreeAssetNetLimit());
});
``` [1](#0-0) 
If the asset entry was deleted, never actually created, or the account's usage map contains a stale/forged token key (e.g. through the AllowSameTokenName toggle switching between v1/v2 asset ID spaces, or through data left over from asset issue deletion/expiry paths), `get(key)` returns `null` and the subsequent `.getFreeAssetNetLimit()` call throws an unhandled `NullPointerException`.

This is structurally the same bug class as CVE-2020-10703: a lookup keyed on a value that is not guaranteed to always resolve (libvirt's storage-pool-by-target-path lookup for pools lacking a target path; here, an asset-ID lookup for an asset that no longer/never existed in the store) is dereferenced without a null-check, on a code path reachable by any unauthenticated caller.

`getAccountNet` is the caller and is exposed both via HTTP (`GetAccountNetServlet`→`wallet.getAccountNet`) and gRPC (`WalletGrpc.getAccountNet`), requiring no authentication, just a valid account address: [2](#0-1) 

### Impact Explanation
A crafted account (owned by any unprivileged user, since asset participation/creation contracts are freely broadcastable) whose free-asset-usage map contains a reference to an asset ID that has since been removed/expired/never fully committed causes any full node's `GetAccountNet` HTTP/gRPC handler to throw a bare `NullPointerException`. Depending on how the calling servlet's exception handling wraps this (`Util.processError`), this can crash the request thread or, in unguarded HTTP threads, propagate an uncaught exception. Because this is a widely-used, read-only, unauthenticated API queried by wallets/exchanges continuously, an attacker can reliably trigger repeated exceptions against any full node that indexes such an account — a denial-of-service against the node's query-serving capability, matching the CVE's "unprivileged read-only user causes daemon-level failure" impact class.

### Likelihood Explanation
Medium. It requires crafting an account state where the free-asset-usage map contains a key that is absent from the current `AssetIssueStore`/`AssetIssueV2Store`. This is plausible via legitimate flows (asset participation followed by deletion/expiry timing, or `AllowSameTokenName` proposal toggling mid-lifecycle, which changes which store — V1 vs V2 — governs lookups) rather than requiring a wholly new attack primitive, but it does require some multi-step setup and is not a one-shot single-transaction trigger like the `libvirt` bug.

### Recommendation
Add a null-check after each `AssetIssueStore`/`AssetIssueV2Store` lookup in `setAssetNetLimit`, e.g.:
```java
AssetIssueCapsule assetIssueCapsule = chainBaseManager.getAssetIssueStore().get(key);
if (assetIssueCapsule != null) {
  assetNetLimitMap.put(asset, assetIssueCapsule.getFreeAssetNetLimit());
}
```
and mirror the same guard for the V2-store branch, returning a sane default (e.g. skip the entry or use `0`) instead of dereferencing a possibly-null capsule.

### Proof of Concept
1. Create an account and have it participate in an asset issue (`ParticipateAssetIssueContract`) so the account's `frozen`/asset usage map records the asset's token ID key.
2. Cause the underlying `AssetIssueCapsule` for that key to become absent from the live `AssetIssueStore`/`AssetIssueV2Store` reachable by `setAssetNetLimit` (e.g., via the `AllowSameTokenName` proposal transition, which changes which store id-space is authoritative, or via asset-issue related deletion/expiry flows) while the account still carries the corresponding key in its usage map.
3. Call `GET /wallet/getaccountnet?address=<account>` (or the gRPC `GetAccountNet`) against the node.
4. `Wallet.getAccountNet` → `setAssetNetLimit` executes `chainBaseManager.getAssetIssueStore().get(key).getFreeAssetNetLimit()`, `get(key)` returns `null`, and the call throws a `NullPointerException`, crashing/erroring the handling thread for this unauthenticated read API — an unprivileged-client-reachable denial of service, analogous to CVE-2020-10703.     if (chainBaseManager.getDynamicPropertiesStore().getAllowSameTokenName() == 0) {
