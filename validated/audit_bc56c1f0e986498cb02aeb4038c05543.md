### Title
Unvalidated attacker-controlled array length in `BatchValidateSign`/`ValidateMultiSign` precompile input causes uncontrolled heap allocation and node OOM/crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The QEMU CVE describes a virtio-blk device that fails to validate the size of a guest-supplied descriptor before performing a write, causing an out-of-bounds heap write / DoS in the host process. The reachable java-tron analog is in the `BatchValidateSign` and `ValidateMultiSign` TVM precompiled contracts: the array-length fields (`len`) embedded in the ABI-encoded call data are read directly with `intValueSafe()` and used to size Java arrays (`new byte[len][]`) before any bound is enforced, when the array-size guard is not active.

### Finding Description
`extractBytes32Array` and `extractBytesArray` in `PrecompiledContracts.java` read an attacker-supplied length word from the decoded call-data words and immediately allocate an array of that size: [1](#0-0) 

These helpers are invoked from `BatchValidateSign.doExecute` (precompile address `0x66`, reachable via a plain `CALL`/`STATICCALL` opcode from any deployed contract) to build the `signatures` and `addresses` arrays from user-supplied call data: [2](#0-1) 

The only bound on `len` (`MAX_SIZE = 16`) is applied in a block that is gated behind `VMConfig.allowTvmSelfdestructRestriction()`: [3](#0-2) 

`allowTvmSelfdestructRestriction` is a committee-activated chain proposal read from `DynamicPropertiesStore`/`ProposalUtil`, not a compile-time constant — it defaults to inactive until Super Representatives vote to enable it. On any deployment where that specific proposal has not been activated (a private/side chain, a freshly bootstrapped network, or a mainnet fork that has not enabled it), the `MAX_SIZE` guard is skipped entirely, so `extractBytesArray`/`extractBytes32Array` allocate `new byte[len][]` with `len` fully attacker-controlled (up to `Integer.MAX_VALUE` via `intValueSafe()`), well before any subsequent bound is enforced. This mirrors the CVE's root cause: a length/offset value taken from an untrusted request is used to size a write/allocation before validation.

The `execute()` wrapper only catches `Throwable` after the fact: [4](#0-3) 
but a request for a reference array of e.g. `Integer.MAX_VALUE` entries fails with `OutOfMemoryError`, which is thrown during heap exhaustion — by the time this `Throwable` is caught, the JVM heap has already been driven to exhaustion, which in the HotSpot/G1 collector can starve or crash unrelated concurrent threads (block application, P2P, RPC handlers) in the same process before or as this catch executes.

### Impact Explanation
A successful trigger causes an `OutOfMemoryError` inside the node's TVM execution, which is process-wide and not isolated per-transaction; depending on JVM state, this can crash the full-node process or force garbage-collector thrashing severe enough to stall block production and RPC service (denial of service), matching the "node crash or halt" acceptance bar for this scan.

### Likelihood Explanation
This precompile is directly callable by any contract (and thus by any unprivileged transaction broadcaster who deploys or calls a trigger contract) via a single `CALL` to precompiled address `0x66`/`0x67` — no special privilege, SR/witness role, or additional preconditions are required beyond crafting the ABI-encoded input. The only limiting factor is whether the `allowTvmSelfdestructRestriction` proposal is active on the target chain.

### Recommendation
Move the `MAX_SIZE` bound check (or an equivalent hard cap) so that it unconditionally applies before `extractBytes32Array`/`extractBytesArray` allocate arrays, independent of `VMConfig.allowTvmSelfdestructRestriction()`, and additionally validate `len` against the actual remaining `words.length` (as `extractBytesArray` already partially does) to prevent unbounded allocation regardless of proposal activation state.

### Proof of Concept
1. Deploy a contract that performs `CALL(gas, 0x0000...0066, 0, in, insize, out, outsize)`.
2. Construct `in` as ABI-encoded input for `batchvalidatesign(bytes32,bytes[],address[])` where the length word for the `bytes[]` (or `address[]`) array is set to a very large value (e.g., `0x7FFFFFFF`) instead of the real element count.
3. On a network where `allowTvmSelfdestructRestriction` has not been activated, invoke the contract; `BatchValidateSign.doExecute` calls `extractBytesArray`/`extractBytes32Array` with `len = 0x7FFFFFFF`, attempting `new byte[0x7FFFFFFF][]`, exhausting the JVM heap and triggering `OutOfMemoryError` in the node process.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
