### Title
Deterministic panic in `get_child_congestion_info_not_finalized` causes synchronized shard-wide halt, not state-root divergence - ([File: chain/chain/src/resharding/manager.rs])

### Summary
`get_child_congestion_info` is invoked both when the resharding split is first materialized by the shard's own node (via `process_memtrie_resharding_storage_update`) and later by every chunk validator re-deriving `ImplicitTransitionParams::Resharding` during stateless validation of the child chunk's witness. In both call sites the inputs (`parent_trie` rooted at the parent's finalized `state_root`, and `parent_congestion_info` taken from the parent block's committed `ChunkExtra`) are consensus-determined values, not node-local state, so any input that trips the `checked_sub().expect()` or the trailing `assert_eq!` will do so identically on every node that performs the recomputation.

### Finding Description
`get_child_congestion_info` is documented as needed for `ImplicitTransitionParams::Resharding` chunk validation [1](#0-0) , and is called from `process_memtrie_resharding_storage_update` with `parent_trie` built from `tries.get_trie_for_shard(*parent_shard_uid, *parent_chunk_extra.state_root())` and `parent_congestion_info = parent_chunk_extra.congestion_info()` [2](#0-1) . Both of these values — the parent state root and the parent `CongestionInfo` — come from the parent block's committed `ChunkExtra`, which is a piece of consensus state identical across all honest nodes that have applied the parent chunk (block producer, chunk producer, and every chunk validator recomputing the same resharding transition for witness validation).

Inside `get_child_congestion_info_not_finalized`, for the right child, the code iterates `ReceiptGroupsQueue::load(parent_trie, shard_id)` (also derived from the same `parent_trie`) and calls:
```
congestion_info.remove_buffered_receipt_gas(gas).expect(...)
congestion_info.remove_receipt_bytes(bytes).expect(...)
...
assert_eq!(congestion_info.buffered_receipts_gas(), 0);
``` [3](#0-2) 

Since `parent_trie` and `parent_congestion_info` are identical, deterministic functions of the parent block's finalized state on every node performing the computation (there is no node-local randomness, wall-clock timing, or peer-dependent input feeding this function), any receipt-group/congestion-info bookkeeping mismatch that causes an underflow or the assertion to fail will do so with the same inputs, same code path, and same outcome on the block producer and on every chunk validator simultaneously. There is no branch here where one node's local view of `parent_trie`/`parent_congestion_info` could differ from another's while both are validating the same block — both reads are keyed off consensus-agreed roots/`ChunkExtra` fields, not off local mempool, local flat-state cache staleness, or timing-sensitive inputs.

### Impact Explanation
This confirms the failure mode is a **synchronized shard-wide crash** (halting consensus/liveness) rather than **state-root divergence**: no node can produce a differing state root because none of them successfully execute past the panic — they all abort identically before committing the child `ChunkExtra`/state root. This matches the NEAR bounty category of "shard-halting panic," not "state-root divergence and chain split," since a chain split requires some nodes to diverge on the *value* they compute, whereas here the entire population of nodes performing the computation dies on the same crafted parent congestion state before any diverging value could be produced or gossiped.

### Likelihood Explanation
The precondition for this to be reachable is that `ReceiptGroupsQueue`'s recorded buffered gas/bytes for the right-hand child's constituent shards diverges from what `CongestionInfo::remove_buffered_receipt_gas`/`remove_receipt_bytes` expects to be able to subtract — i.e., an accounting bug that lets these two pieces of derived congestion bookkeeping drift apart during ordinary receipt buffering/processing prior to a shard split. Whether an unprivileged attacker (ordinary funded account submitting transactions) can, through normal transaction/receipt traffic alone, drive that drift is a separate question about the correctness of the buffered-gas/bytes accounting elsewhere in the runtime; I did not locate and could not confirm within available tool calls a concrete attacker-controlled transaction sequence that produces such a mismatch. Resharding itself is not attacker-triggered (it fires on a protocol-scheduled shard-layout change), so the attacker's role would be limited to shaping the buffered congestion state ahead of a resharding boundary that they do not control the timing of.

### Recommendation
Replace the `.expect()` calls on `remove_buffered_receipt_gas`/`remove_receipt_bytes` and the trailing `assert_eq!` in `get_child_congestion_info_not_finalized` with graceful `Result`-returning error propagation (e.g., `Error::Other`/`StorageError`) so that a bookkeeping mismatch degrades to a recoverable chunk-application error rather than an unrecoverable process panic, and add saturating/checked accounting with logging to detect drift between `ReceiptGroupsQueue` and `CongestionInfo` before it reaches this code path.

### Proof of Concept
Unit test in `chain/chain/src/resharding/manager.rs` test module:
1. Construct a `parent_trie` (via `TestTriesBuilder`) with a `ReceiptGroupsQueue` reporting buffered gas/bytes greater than the `parent_congestion_info`'s recorded buffered gas/bytes (craft the two independently to be inconsistent).
2. Call `ReshardingManager::get_child_congestion_info(&parent_trie, &parent_shard_layout, parent_congestion_info, &child_shard_layout, &right_child_uid, RetainMode::Right)` twice with byte-for-byte identical arguments.
3. Assert both calls panic (`std::panic::catch_unwind`) with the same message (`"Buffered gas must not exceed congestion info buffered gas"` or the `assert_eq!` message), demonstrating that identical inputs deterministically yield identical fatal outcomes on repeated/independent invocations — consistent with every node crashing synchronously rather than diverging.
