### Title
Unauthenticated on-behalf deposit/transfer fills a victim's collateral-token list to `MAX_TOKENS_PER_USER`, blocking them from adding collateral and forcing liquidation - ([File: contracts/DepositToken.sol])

### Summary
`DepositToken.deposit(amount_, onBehalfOf_)` lets any unprivileged caller mint deposit-token balances into an arbitrary `onBehalfOf_` account, and `transfer` does the same to any recipient. Both paths call `pool.addToDepositTokensOfAccount(account_)` in `_mint`/`_transfer` without the victim's consent, which reverts once the account's deposit-token set reaches `MAX_TOKENS_PER_USER`. An attacker can therefore force-write entries into a victim's account state (the BOLA analog: unauthorized data manipulation of another user's object) and permanently cap their collateral list.

### Finding Description
In `contracts/DepositToken.sol`, `deposit` mints msdTOKEN to a caller-chosen `onBehalfOf_`:

- `deposit` pulls underlying from the caller but credits `onBehalfOf_` (`_mint(onBehalfOf_, _deposited)`) — `contracts/DepositToken.sol:211-237`.
- `_mint` registers the token on the beneficiary: `pool.addToDepositTokensOfAccount(account_)` — `contracts/DepositToken.sol:485-488`.
- The same registration happens on plain `transfer`/`transferFrom` via `_transfer` for the recipient — `contracts/DepositToken.sol:517-520`, gated only by `_revertIfLocked` on the sender (`transfer` at `contracts/DepositToken.sol:348-354`), which is trivially satisfied when the sender has no debt.
- `addToDepositTokensOfAccount` in `contracts/Pool.sol` reverts once the account's `MappedEnumerableSet` of deposit tokens hits `MAX_TOKENS_PER_USER` (cap exists specifically to bound `debtPositionOf` iteration).

Neither path requires any authorization from the victim — there is no opt-in, no signature, no `msg.sender == onBehalfOf_` check. The only constraints are `whenNotPaused`, `onlyIfDepositTokenExists`, `onlyIfDepositTokenIsActive` (inside `_mint`), and `maxTotalSupply`, none of which protect the victim's list.

### Impact Explanation
Once the victim's deposit-token set is full:

- Every `deposit` of a *new* collateral type reverts at `addToDepositTokensOfAccount`, as does any incoming `transfer`/`seize` credit of a new token.
- A victim holding an open debt position cannot top up with additional collateral types. If their position deteriorates (price move or accrued interest via `DebtToken.accrueInterest`), they are blocked from improving health and become liquidatable through `Pool.liquidate` — a direct, attacker-induced loss.
- Recovery requires burning an existing balance to zero to remove a set entry, which may itself be impossible if the position's unlocked balance (`unlockedBalanceOf`) is constrained by debt — i.e., the victim's collateral can be effectively frozen for withdrawal below the healthy threshold while deposits are also blocked.

This is a temporary-to-permanent freezing of position functionality plus induced liquidation risk — matching the BOLA impact of unauthorized state writes to another user's account.

### Likelihood Explanation
- Attacker cost is dust amounts (`amount_` must merely be nonzero) of each deposit-token underlying, or dust msdTOKEN transfers — no capital lockup, flash-loanable underlying is fine since only the minted share needs to persist.
- No privileged role, keeper, or oracle manipulation is needed; all entry points are public (`DepositToken.deposit`, `DepositToken.transfer`), and equally reachable via `Operator.execute` since `SynthContext._msgSender()` resolves to the real caller anyway.
- Attack scales with the number of registered deposit tokens per pool; each pool has multiple collaterals (USDC, WETH, vaUSDC, etc.), and the attacker can also mint fresh variety by depositing each distinct underlying.

### Recommendation
- Only allow `deposit` to credit `_msgSender()`, or require `onBehalfOf_ == _msgSender()` unless the caller is a whitelisted contract (e.g., `NativeTokenGateway`, `SmartFarmingManager`).
- Alternatively, make `addToDepositTokensOfAccount` non-reverting on unsolicited tokens: track "enabled collateral" per user explicitly (opt-in set) so that received dust doesn't consume the bounded list, and skip zero-user-opinion entries in `debtPositionOf`.
- Apply the same fix to `_transfer` (e.g., don't count tokens the recipient never enabled, or let `deposit`/transfer registrations bypass the cap while user-initiated deposits enforce it).

### Proof of Concept
Hardhat fork sketch (pool = an existing Metronome pool, e.g., mainnet Pool1 with multiple DepositTokens):

```solidity
// victim: has an open debt position (depositTokenA collateral + msXXX debt)
// attacker: unprivileged EOA holding dust of each underlying

// 1) Attacker fills victim's deposit-token list to MAX_TOKENS_PER_USER
for (uint i; i < depositTokens.length; ++i) {
    DepositToken dt = depositTokens[i];
    underlying[i].approve(address(dt), DUST);
    dt.deposit(DUST, victim);            // credits victim, adds token to victim's list
}
// attacker can also: dt.transfer(victim, DUST) for tokens they already hold

// 2) Victim tries to deposit a new collateral type to avoid liquidation
vm.prank(victim);
newCollateral.approve(address(newDepositToken), amount);
vm.expectRevert();                        // addToDepositTokensOfAccount: MAX_TOKENS_PER_USER
newDepositToken.deposit(amount, victim);

// 3) Price moves / interest accrues -> victim is unhealthy
//    anyone liquidates; victim could not add collateral to defend the position
pool.liquidate(synthetic, victim, amount, depositTokenToSeize);
```

Asserts: step 2 reverts for the victim (but succeeds for a fresh account), and step 3's liquidation succeeds, demonstrating attacker-induced loss of the victim's ability to manage their position.

Caveat: the exact revert inside `Pool.addToDepositTokensOfAccount` and the `MAX_TOKENS_PER_USER` constant value should be confirmed in `contracts/Pool.sol` (the constant is referenced in the codebase but its enclosing lines were not fully retrieved in this scan); the trigger and call chain shown above are verified in `DepositToken.sol`.
