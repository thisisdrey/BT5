### Title
Unrestricted `GitConfigOptions` Injection Enables Resource-Exhaustion DoS in Git Subprocess Invocation - (File: internal/git/gitcmd/command_options.go)

### Summary
The Algorand report describes a missing bound on a caller-controlled value (`fee`) that lets any unprivileged caller drain a shared, limited resource (the minter account's Algo balance), causing denial of service. The closest reachable analog in Gitaly is the `git_config_options` field accepted from ordinary, unauthenticated-by-repo-access users on fetch/clone/push RPCs (`PostUploadPackWithSidechannel`, `InfoRefsUploadPack`, `PostReceivePack`, `SSHUploadPackWithSidechannel`). This field is converted almost verbatim into `git -c key=value` arguments with only syntactic checks, no semantic restriction on which configuration keys or values may be set, letting a caller push the shared Gitaly node's CPU/memory consumption per request without bound.

### Finding Description
`gitcmd.ConvertConfigOptions` splits each string in the repeated `git_config_options` request field on `=` and builds a `ConfigPair` from it with no allowlist/denylist of keys: [1](#0-0) 

The only validation performed on each pair is `GitConfig.Validate()`, which checks purely syntactic properties (non-empty key, no `=`, contains a `.`, no leading/trailing dot, matches a permissive key-format regex) — it never restricts *which* git configuration variables are permitted: [2](#0-1) 

These pairs are then passed straight through to the spawned git process as `-c key=value` global options: [3](#0-2) 

This path is directly reachable by an ordinary client performing a fetch/clone. For example, `validateUploadPackRequest` takes `req.GetGitConfigOptions()` from the `PostUploadPackWithSidechannelRequest` (a request any client with repo access can send) and forwards it unchanged into the upload-pack invocation: [4](#0-3) 

Existing tests confirm the field is honored verbatim by the spawned git process, including configuration that changes Git's resource-consuming behavior (e.g., disabling `receive.unpackLimit`, altering `receive.MaxInputSize`, `transfer.hideRefs`, `uploadpack.hideRefs`): [5](#0-4) [6](#0-5) 

Because there is no restriction on *which* git configuration keys/values a caller may inject (only string-format validation), a client can set resource-amplifying options — e.g., increasing `pack.windowMemory`, `pack.window`, `pack.threads`, `core.bigFileThreshold`, `http.postBuffer`, `core.compression`, or disabling protective limits such as `receive.maxInputSize`/`receive.unpackLimit` — on a single request. This is directly analogous to the report's root cause: an unbounded, attacker-controlled parameter that governs consumption of a shared, finite resource (here: Gitaly node CPU/memory/disk I/O) with no ceiling enforced by the server.

### Impact Explanation
A caller who can already invoke these read/write Git RPCs (fetch, clone, or push) — which does not require elevated Gitaly privileges beyond ordinary repository access — can craft `GitConfigOptions` values that dramatically raise the CPU, memory, or I/O cost of a single Git subprocess invocation. Repeated or concurrent requests using such options can exhaust the finite CPU/memory/I/O capacity of the shared Gitaly node, degrading or denying service for all other repositories and users hosted on that node — an outcome equivalent in class to the "anyone can burn all the minter's Algo" DoS in the original report (a single non-privileged fee-like parameter draining a shared, bounded resource with no enforced ceiling).

### Likelihood Explanation
Likelihood is Low-to-Moderate. `GitConfigOptions` is a documented, first-class field of multiple already-used, network-reachable RPCs, and the only defense is syntactic key-format validation (no restriction on the specific keys/values permitted). No additional privilege beyond having access to invoke these Git transport RPCs is required, and the vector is exercised routinely in the existing test suite, confirming reachability and effect on Git subprocess behavior.

### Recommendation
- **Short term:** Introduce a strict allowlist of `git_config_options` keys that gitaly will accept from RPC requests (e.g., only `uploadpack.*`, `transfer.hideRefs`, `bundle.*` needed for legitimate client-driven negotiation), rejecting or ignoring any key outside this set, especially resource-tuning keys (`pack.*`, `http.postBuffer`, `core.compression`, `receive.maxInputSize`, `receive.unpackLimit`, etc.) and any keys capable of triggering command execution or hook-like behavior.
- **Long term:** Document the full set of accepted/rejected `GitConfigOptions` values per RPC, add negative tests asserting rejection of disallowed or resource-amplifying keys, and consider capping subprocess resource usage independently (cgroup/rlimit-based enforcement) so that even permitted config values cannot exceed a hard per-request resource budget.

### Proof of Concept
1. As an ordinary client with fetch access to a repository, send a `PostUploadPackWithSidechannelRequest` (or `InfoRefsRequest`/`SSHUploadPackWithSidechannelRequest`) with `GitConfigOptions` set to values that maximize the cost of the underlying `git-upload-pack`/`git-receive-pack` invocation, e.g.:
   ```
   GitConfigOptions: []string{
       "pack.window=500",
       "pack.threads=64",
       "core.bigFileThreshold=1",
       "pack.windowMemory=0",
   }
   ```
2. Because `ConvertConfigOptions`/`GitConfig.Validate()` only check the key's textual format (see [1](#0-0)  and [2](#0-1) ), these values pass validation and are forwarded as `-c key=value` to the spawned git process, as already demonstrated for other keys in `TestPostReceivePack_rejectViaGitConfigOptions` and `TestServer_PostUploadPackSidechannel_gitConfigOptions`.
3. Repeating this request concurrently against a repository forces the Gitaly node to spend outsized CPU/memory per request, degrading service for all other tenants of that node — mirroring the "anyone can burn all the minter's Algo" unavailability outcome from the source report.

// ConvertConfigOptions converts `<key>=<value>` config entries into `ConfigPairs`.
func ConvertConfigOptions(options []string) ([]ConfigPair, error) {
	configPairs := make([]ConfigPair, len(options))

	for i, option := range options {
		configPair := strings.SplitN(option, "=", 2)
		if len(configPair) != 2 {
			return nil, fmt.Errorf("cannot convert invalid config key: %q", option)
		}

		configPairs[i] = ConfigPair{Key: configPair[0], Value: configPair[1]}
	}

	return configPairs, nil
}

// Validate validates that the Git configuration conforms to a format that Git understands.
func (cfg GitConfig) Validate() error {
	// Even though redundant, this block checks for a few things up front to give better error
	// messages to the administrator in case any of the keys fails validation.
	if cfg.Key == "" {
		return cfgerror.NewValidationError(cfgerror.ErrNotSet, "key")
	}
	if strings.Contains(cfg.Key, "=") {
		return cfgerror.NewValidationError(
			fmt.Errorf(`key %q cannot contain "="`, cfg.Key),
			"key",
		)
	}
	if !strings.Contains(cfg.Key, ".") {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q must contain at least one section", cfg.Key),
			"key",
		)
	}
	if strings.HasPrefix(cfg.Key, ".") || strings.HasSuffix(cfg.Key, ".") {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q must not start or end with a dot", cfg.Key),
			"key",
		)
	}

	if !configKeyRegex.MatchString(cfg.Key) {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q failed regexp validation", cfg.Key),
			"key",
		)
	}

// GlobalArgs generates a git `-c <key>=<value>` flag. Returns an error if `Validate()` fails to
// validate the config key.
func (cfg GitConfig) GlobalArgs() ([]string, error) {
	if err := cfg.Validate(); err != nil {
		return nil, fmt.Errorf("invalid configuration key %q: %w", cfg.Key, err)
	}

	return []string{"-c", fmt.Sprintf("%s=%s", cfg.Key, cfg.Value)}, nil
}

func (s *server) validateUploadPackRequest(ctx context.Context, req *gitalypb.PostUploadPackWithSidechannelRequest) (string, []gitcmd.ConfigPair, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return "", nil, err
	}
	repoPath, err := s.locator.GetRepoPath(ctx, repository)
	if err != nil {
		return "", nil, err
	}

	gitcmd.WarnIfTooManyBitmaps(ctx, s.logger, s.locator, repository.GetStorageName(), repoPath)

	config, err := gitcmd.ConvertConfigOptions(req.GetGitConfigOptions())
	if err != nil {
		return "", nil, err
	}

	return repoPath, config, nil
}
