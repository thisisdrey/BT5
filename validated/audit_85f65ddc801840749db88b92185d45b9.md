### Title
Integer overflow in `debug/elf` GNU version-table parsing causes negative-index slice panic on 32-bit builds - (File: src/debug/elf/file.go)

### Summary
`File.dynamicVersions` and `File.dynamicVersionNeeds` in `src/debug/elf/file.go` compute byte offsets into a section-data slice by converting untrusted `uint32` fields (`aux`, `vnext`) directly to `int` and adding them to a running index (`j := i + int(aux)`). On 32-bit Go builds (`GOARCH=386`/`arm`, where `int` is 32 bits), an attacker-controlled `uint32` with the high bit set converts to a negative `int`, producing a negative `j` that bypasses the `j+8 > len(d)` bounds check and causes a negative-index slice panic when parsing a crafted ELF file. This is the direct Go analog of the CVE-2017-15932 pattern in radare2's `store_versioninfo_gnu_verdef()`, where a signed/32-bit integer computed from attacker-controlled version-definition offsets goes negative and is used for memory access.

### Finding Description
Entry point: any program that calls `elf.NewFile`/`elf.Open` on an untrusted binary and then calls `(*File).DynamicSymbols`, `(*File).ImportedSymbols`, `(*File).DynamicVersions`, or `(*File).DynamicVersionNeeds` — all of which funnel into `gnuVersionInit` [1](#0-0) , which calls `dynamicVersions` and `dynamicVersionNeeds`.

In `dynamicVersions`, the code reads the `aux` field (offset to the first `verdaux` entry) as a `uint32` straight from attacker-controlled section bytes and converts it with `int(aux)`: [2](#0-1) 

The same pattern (`j := i + int(aux)` and `j += int(next)` from a `uint32`) exists in `dynamicVersionNeeds`: [3](#0-2) 

On architectures where `int` is 32 bits, converting a `uint32` value such as `0x80000000` or larger yields a negative `int`. This makes `j := i + int(aux)` negative, and the guard `if j+8 > len(d) { break }` does not protect against it, because a negative `j+8` is not `> len(d)`. Execution proceeds to `d[j : j+4]`, which is a negative-index slice operation and panics with `runtime error: slice bounds out of range [:-N]`.

### Impact Explanation
A crafted ELF file (e.g., a binary uploaded to an analysis service, a plugin, or a build artifact processed by any tool using `debug/elf`) can crash any Go program built for a 32-bit target that calls the affected accessor methods, via an unrecoverable panic. This matches Go's PUBLIC track criteria for a "plausible malicious-input parser panic" — an unauthenticated/ordinary user supplies a file, and a normal victim workflow (binary inspection/analysis) parses it with the standard library.

### Likelihood Explanation
Any tool built with `GOOS/GOARCH` combinations where `int` is 32 bits (386, arm, and other 32-bit targets) that parses third-party or user-supplied ELF binaries via `debug/elf` and calls `DynamicSymbols`, `ImportedSymbols`, `DynamicVersions`, or `DynamicVersionNeeds` is reachable. The attacker only needs to supply a malformed but structurally valid-looking ELF file with an `SHT_GNU_VERDEF` or `SHT_GNU_VERNEED` section containing an `aux`/`next` field with the high bit set.

### Recommendation
Validate `aux`/`next`/`vnext`/`nameoff` fields before converting to `int`: reject values greater than `len(d)` (or `math.MaxInt32` bound-appropriate check) prior to arithmetic, or perform the offset arithmetic in `uint64`/`uint32` and only convert to `int` after confirming the result fits within `[0, len(d)]`. Apply the same fix to both `dynamicVersions` and `dynamicVersionNeeds`.

### Proof of Concept
```go
package elf_test

import "testing"

// This test documents the vulnerable computation directly, since building a
// full ELF binary with a crafted SHT_GNU_VERDEF section is verbose. The
// panic manifests when GOARCH is 32-bit (int is int32) and aux/next fields
// have their high bit set.
func TestNegativeOffsetPanic32Bit(t *testing.T) {
	// Simulate the vulnerable computation from dynamicVersions:
	//   j := i + int(aux)
	// with aux read as uint32 from attacker data.
	var i int = 0
	var aux uint32 = 0x80000000 // attacker-controlled offset, MSB set

	// On 32-bit builds, int(aux) is negative.
	j := i + int(aux)

	d := make([]byte, 32) // simulated section data

	defer func() {
		r := recover()
		if r == nil {
			t.Fatal("expected panic from negative slice index, got none")
		}
		t.Logf("recovered expected panic: %v", r)
	}()

	// This is the exact vulnerable sink pattern used in dynamicVersions/
	// dynamicVersionNeeds: the bounds check "j+8 > len(d)" does not catch
	// negative j on 32-bit builds, so this indexing panics.
	if j+8 > len(d) {
		t.Fatal("bounds check unexpectedly caught the overflow")
	}
	_ = d[j : j+4]
}
```
Expected assertion on a 32-bit build (`GOARCH=386` or `arm`): the slice expression `d[j : j+4]` panics with `runtime error: slice bounds out of range [-N:]`, demonstrating that `File.dynamicVersions`/`File.dynamicVersionNeeds` can be driven into a negative-index panic by a crafted ELF `SHT_GNU_VERDEF`/`SHT_GNU_VERNEED` section on 32-bit targets.

// gnuVersionInit parses the GNU version tables
// for use by calls to gnuVersion.
// It reports whether any version tables were found.
func (f *File) gnuVersionInit(str []byte) (bool, error) {
	// Versym parallels symbol table, indexing into verneed.
	vs := f.SectionByType(SHT_GNU_VERSYM)
	if vs == nil {
		return false, nil
	}
	d, _ := vs.Data()

	f.gnuVersym = d
	if err := f.dynamicVersions(str); err != nil {
		return false, err
	}
	if err := f.dynamicVersionNeeds(str); err != nil {
		return false, err
	}
	return true, nil
}
