### Title
Cross-message-type StackerDB chunk replay due to signature not binding to contract/message context - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::sign`/`verify` compute the signed digest from only `slot_id`, `slot_version`, and `data_hash` [1](#0-0) . This mirrors the LID-5 bug class: the signature omits part of the context that the receiving system uses to authorize an action (there, `depositCalldata`; here, the target StackerDB contract/message type). Because multiple `.signers-{cycle_mod}-{msg_id}` StackerDB contracts for the same reward cycle are populated with the *identical* signer→slot_id mapping (all read from the same `stackerdb-get-signer-slots-page`) [2](#0-1) [3](#0-2) , a signature that authenticates a chunk for one message-type contract (e.g. `BlockResponse`, `signers-0-1`) also verifies successfully as a legitimate chunk for a different message-type contract for the same signer/slot (e.g. `StateMachineUpdate`, `signers-0-2`, or `BlockPreCommit`, `signers-0-3`), since the contract identity is never part of what's signed.

### Finding Description
A `StackerDBChunkData`'s signature is produced over `SlotMetadata::auth_digest()`, which hashes `slot_id || slot_version || data_hash` only [4](#0-3) . Verification recovers the pubkey from this same narrow digest and checks it against the address that the *local per-contract* config says owns that slot [5](#0-4) , and both the HTTP write path (`poststackerdbchunk`) and the p2p validation path (`StackerDBs::validate_received_chunk`) look up `get_slot_signer(smart_contract_id, slot_id)` for the specific target contract before calling `SlotMetadata::verify` [6](#0-5) [7](#0-6) .

Because the signature never binds to the smart-contract identity, any bytes that produce a valid `(slot_id, slot_version, data_hash, sig)` tuple for signer S in contract A are equally valid for signer S in contract B, provided S occupies the same slot_id in B. This is guaranteed by design: for a given reward cycle, `signers-{c}-1` (BlockResponse), `signers-{c}-2` (StateMachineUpdate), and `signers-{c}-3` (BlockPreCommit) all pull their slot assignments from the same `stackerdb-signer-slots-{c mod 2}` list [8](#0-7) [2](#0-1) , i.e., signer S is always at the same slot index across all three message-type StackerDBs in that cycle.

An unprivileged network participant who observes (via the public P2P StackerDB gossip or the public HTTP `/v2/stackerdb/.../chunks` GET endpoint) a legitimately signed chunk that a signer S posted to contract A can repost the exact same bytes (slot_id, slot_version, sig, data) to contract B for the same reward cycle. As long as the target slot's expected version in B is not higher than the replayed `slot_version` (trivially true for an as-yet-unwritten slot, version 0/1), `try_replace_chunk`/`validate_received_chunk` will accept it as a validly-signed, authentic chunk from signer S for contract B — even though S never authorized any content under that contract or message type.

### Impact Explanation
This breaks the intended "signature authenticates X for this specific StackerDB" equality: the same signature is accepted as authorization to write into an entirely different logical channel (message type) than the signer intended. This is an unauthenticated/unauthorized write into StackerDB state under a forged provenance claim (data attributed to signer S's message channel B that S never sent there), and the forged data is also propagated network-wide via `StackerDBPushChunk`/gossip once accepted (`node.set_relay_message(StacksMessageType::StackerDBPushChunk(...))`) [9](#0-8) . Downstream consumers (e.g. `StackerDBListener`, miner/signer coordination logic) that trust that whatever occupies a given message-type contract's slot for signer S is genuinely S's intent for that message type can be fed replayed/cross-context payloads, potentially causing parse failures, stale/duplicate signer messages, or state-machine desynchronization for signers and miners that rely on these channels (`BlockResponse`, `StateMachineUpdate`, `BlockPreCommit`) for consensus-adjacent coordination.

### Likelihood Explanation
High feasibility: no private key or privileged role is required — only observing an already-published, validly-signed chunk (which is by design broadcast/publicly retrievable) and reposting the identical bytes to a different StackerDB contract via the standard public POST endpoint or unsolicited P2P push path. The exploit requires no cryptographic forgery, only replaying legitimate messages into the wrong context, and the signer-slot alignment across the sibling `.signers-{cycle}-N` contracts is a deterministic consequence of the current design (`stackerdb-get-signer-slots-page`), not an edge case.

### Recommendation
Bind the signature to the full write context, not just slot metadata. Include the StackerDB contract identifier (and ideally reward cycle / message-type discriminant) in the `SlotMetadata::auth_digest()` computation, e.g. `hash(contract_id || slot_id || slot_version || data_hash)`, and thread the `smart_contract_id` through `sign`/`verify`/`recover_pk` so a chunk cannot be replayed across sibling StackerDB contracts that happen to share a signer/slot assignment.

### Proof of Concept
1. Signer S is assigned slot `0` in both `signers-0-1` (BlockResponse) and `signers-0-2` (StateMachineUpdate) for reward cycle `c`, since both are derived from the same `stackerdb-signer-slots-0` list.
2. S legitimately signs and posts a `BlockResponse` chunk: `StackerDBChunkData{slot_id:0, slot_version:1, sig, data}` to `signers-0-1`, using `chunk.sign(&S_privkey)` which signs only `slot_id||slot_version||data_hash` [10](#0-9) .
3. An observer captures this chunk (public GET/gossip) and POSTs the identical `(slot_id, slot_version, sig, data)` tuple to `signers-0-2` via `/v2/stackerdb/{S}/signers-0-2/chunks`.
4. `try_replace_chunk` looks up the slot-0 signer for `signers-0-2` (also S), and `SlotMetadata::verify` succeeds because the digest never included which contract the chunk targets [5](#0-4) .
5. The chunk is accepted, stored as slot 0 v1 of `signers-0-2`, and relayed network-wide as a `StackerDBPushChunk`, even though the payload is a serialized `BlockResponse` message being injected into the `StateMachineUpdate` channel — content S never authorized for that channel.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
