### Title
Stale StackerDB signer authorization survives a signer-set revocation — old signer can still write chunks after being removed - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::create_or_reconfigure_stackerdbs` (`stackslib/src/net/stackerdb/mod.rs`, `create_or_reconfigure_stackerdbs`) decides whether to push a freshly-loaded StackerDB signer configuration down into the on-disk `chunks` table (which is the actual enforcement point for write authorization) with this guard:

```
} else if (new_config != stackerdb_config && !new_config.signers.is_empty())
    || (new_config == stackerdb_config
        && new_config.signers.len() != self.get_slot_versions(&stackerdb_contract_id)?.len())
{
    self.reconfigure_stackerdb(&stackerdb_contract_id, &new_config) ...
}
``` [1](#0-0) 

If the newly-evaluated authoritative config (`new_config`, from `StackerDBConfig::from_smart_contract`) has an **empty** `signers` list (i.e., the controlling contract revoked all writers — a legitimate "rug-pull protection"/deauthorization action, or the same result produced when contract evaluation transiently fails and falls back to `StackerDBConfig::noop()`), and it differs from the previously stored config, the reconfiguration branch is **skipped entirely**. The on-disk `chunks` table (queried through `get_slot_signer`) is left untouched, so it continues to list the old, now-deauthorized signer address for every slot.

### Finding Description
Write authorization for a StackerDB chunk is enforced by comparing a signature to the address recorded in the `chunks.signer` column, not to the live, authoritative `signers` list from the smart contract:

```rust
let addr = match self
    .stackerdbs
    .get_slot_signer(smart_contract_id, data.slot_id)?
{
    Some(addr) => addr,
    None => return Ok(false),
};
let slot_metadata = data.get_slot_metadata();
if !slot_metadata.verify(&addr)? { ... }
``` [2](#0-1) 

`get_slot_signer` reads directly from the persisted `chunks` table:
```rust
pub fn get_slot_signer(&self, smart_contract: &QualifiedContractIdentifier, slot_id: u32) -> Result<Option<StacksAddress>, net_error> {
    let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
    let sql = "SELECT signer FROM chunks WHERE stackerdb_id = ?1 AND slot_id = ?2";
    ...
}
``` [3](#0-2) 

The only place that ever updates this stored `signer` value is `reconfigure_stackerdb`, which resets a slot's signer/version/data whenever the authoritative signer for that slot changes:
```rust
if let Some(existing_validation) = self.get_slot_validation(smart_contract, slot_id)? {
    if existing_validation.signer == *principal { continue; }
}
// new slot, or existing slot with a different signer -> reset row
``` [4](#0-3) 

The bug is that `create_or_reconfigure_stackerdbs` never calls `reconfigure_stackerdb` when the freshly loaded `new_config.signers` is empty but differs from the stored config — this is exactly the case where an authoritative revocation (all writers removed) has occurred: [5](#0-4) 

This produces a persistent equality break: **authoritative signer set (contract-level, now `[]`) vs. stored/enforced signer (DB row, still the old address)**. Any peer holding the old, revoked signing key can continue to push validly-signed chunks; `validate_received_chunk`/`try_replace_chunk` will accept them because they check only the stale DB row, never the current authoritative `signers` list.

### Impact Explanation
This is an unauthenticated/unauthorized write to StackerDB state: a signer who has been explicitly deauthorized by the controlling smart contract (an on-chain, node-independent, remotely-observable action) retains the practical ability to push and have accepted new chunk versions into the StackerDB replica, because the enforcement path (`get_slot_signer` → `SlotMetadata::verify`) is never refreshed to reflect the revocation. This matches the "unauthenticated/unauthorized write to state or StackerDB" Critical-impact category, since a remote, otherwise-unprivileged (post-revocation) actor can continue writing gossip data that other nodes will propagate as legitimate for that StackerDB (e.g., signer message gossip), effectively resurrecting the LUKSO-style "stale permission after ownership/authorization change" bug class in this codebase's chunk-authorization layer.

### Likelihood Explanation
Triggering requires only that the authoritative signer set for a StackerDB contract legitimately transitions to empty (a normal governance/rotation action already anticipated by the code, since it is explicitly checked for) while a previous signer set was non-empty. No attacker action beyond continuing to sign with an already-known, previously-valid key is needed — this can happen naturally any time an operator revokes all current signers, or transiently whenever contract evaluation temporarily yields `StackerDBConfig::noop()` (also empty `signers`) is mistaken for a genuine empty-signer state and, combined with a subsequent legitimate empty-signer refresh, delays or defeats revocation. This is a remote, unprivileged concern once a key is orphaned/revoked, and does not require the node's secret or an admin role.

### Recommendation
Do not special-case "new config has empty signers" to skip reconfiguration when it genuinely differs from the previous config. If the intent of the `!new_config.signers.is_empty()` guard is only to protect against transient contract-evaluation failures (`noop()` fallback masquerading as an empty signer set), distinguish that failure case explicitly (e.g., propagate an `Option`/`Result` sentinel from `create_or_reconfigure_stackerdbs`'s config-loading step rather than conflating "load failed" with "load succeeded, signers legitimately empty"), and always call `reconfigure_stackerdb` (or otherwise wipe/replace stale `signer` rows) whenever the authoritative signer for a slot has actually changed — including to the empty set.

### Proof of Concept
1. Deploy/observe a StackerDB-controlling contract with signer `S1` assigned to slot 0; node loads config via `StackerDBConfig::from_smart_contract`, `create_stackerdb` seeds `chunks.signer = S1`.
2. `S1` pushes a validly-signed chunk; it's accepted (`validate_received_chunk` matches `get_slot_signer == S1`).
3. Contract owner calls the revocation function, causing `stackerdb-get-signer-slots` to now return an empty list for this DB. On the next `refresh_stacker_db_configs` pass, `StackerDBConfig::from_smart_contract` returns `new_config.signers == []`, `new_config != stackerdb_config` (old config had `S1`).
4. In `create_or_reconfigure_stackerdbs`, `(new_config != stackerdb_config && !new_config.signers.is_empty())` is `false` (signers is empty) and the second branch (`new_config == stackerdb_config`) is also `false` → the `if/else if` never calls `reconfigure_stackerdb`; `chunks.signer` for slot 0 remains `S1`.
5. `S1` (revoked) continues to sign and push chunks; `validate_received_chunk`/`try_replace_chunk` still accept them because `get_slot_signer` still returns `S1`, so the chunk is written to state and, if pushed unsolicited/gossiped, propagated to peers as legitimate StackerDB content for that contract.     pub fn reconfigure_stackerdb(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slots: &[(StacksAddress, u32)],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let mut total_slots_read = 0u32;
        for (principal, slot_count) in slots.iter() {
            total_slots_read =
                total_slots_read
                    .checked_add(*slot_count)
                    .ok_or(net_error::OverflowError(
                        "Slot count exceeeds u32::MAX".to_string(),
                    ))?;
            let slots_before_principal = total_slots_read - slot_count;
            for cur_principal_slot in 0..*slot_count {
                let slot_id = slots_before_principal + cur_principal_slot;
                if let Some(existing_validation) =
                    self.get_slot_validation(smart_contract, slot_id)?
                {
                    // this slot already exists.
                    if existing_validation.signer == *principal {
                        // no change
                        continue;
                    }
                }

                debug!("Reset slot {} of {}", slot_id, smart_contract);

                // new slot, or existing slot with a different signer
                let qry = "INSERT OR REPLACE INTO chunks (stackerdb_id,signer,slot_id,version,write_time,data,data_hash,signature) VALUES (?1,?2,?3,?4,?5,?6,?7,?8)";
                let mut stmt = self.sql_tx.prepare(qry)?;
                let args = params![
                    stackerdb_id,
                    principal.to_string(),
                    slot_id,
                    NO_VERSION,
                    0,
                    vec![],
                    Sha512Trunc256Sum([0u8; 32]),
                    MessageSignature::empty(),
                ];

                stmt.execute(args)?;
            }
        }
        debug!("Shrink {} to {} slots", smart_contract, total_slots_read);
        self.shrink_stackerdb(stackerdb_id, total_slots_read)?;
        Ok(())
    }
