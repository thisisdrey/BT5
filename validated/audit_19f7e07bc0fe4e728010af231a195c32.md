## Title
Concurrency-limiter admission uses the raw, unvalidated `relative_path` as the lock key while the actual repository identity is resolved (and normalized) later — attacker-controlled path variants bypass per-repo concurrency limits and starve legitimate requests - ([File: internal/grpc/middleware/limithandler/middleware.go])

## Summary
Gitaly's per-repository concurrency limiter admits requests into its queue using `LimitConcurrencyByRepo`, which keys solely on `info.Repository.GetRelativePath()` — the raw, attacker-supplied string taken directly off the incoming RPC message before any path validation, cleaning, or existence check occurs. [1](#0-0) 
The real identity of a repository is only established later, inside the handler, via `Locator.GetRepoPath`/`ValidateRepository`, which normalizes/cleans and validates the path against the storage root. [2](#0-1) 
This mirrors the H-03 root cause pattern: a weak, cheap check performed at admission time (string-only lock key) versus a stronger, authoritative check performed later during actual processing (validated/cleaned path) — allowing an attacker to defeat the intended resource-protection gate.

## Finding Description
The `[[concurrency]] max_per_repo` mechanism exists specifically to prevent a single repository from monopolizing Gitaly's resources: "Limit the number of concurrent RPCs that are in flight on each Gitaly node for each repository per RPC." [3](#0-2) 
The limiter groups requests into buckets by the value returned from `getLockKey`, and each bucket gets an independent semaphore of size `max_per_repo` plus its own bounded queue (`limitsByKey` map, lazily created per key). [4](#0-3) 

The key is computed with `LimitConcurrencyByRepo`, which reads `info.Repository.GetRelativePath()` straight from `RequestInfo`, itself populated directly from the client's protobuf `Repository` message with no cleaning or validation: [5](#0-4) [1](#0-0) 

Because the interceptor chain places the limit handler after auth but still ahead of any locator-based path validation performed inside the actual RPC handlers, the limiter treats two relative-path strings as different "repositories" even when they resolve to the exact same on-disk repository once cleaned by `storage.ValidateRelativePath`/`filepath.Join` inside `Locator.GetRepoPath`. `ValidateRelativePath` only rejects paths that escape the storage root; it does not canonicalize semantically-equivalent variants (e.g. redundant `./` segments, differing trailing slashes, duplicated path separators) which `filepath.Join`/`Clean` will silently collapse to the same absolute path. [6](#0-5) 

Consequently, a client can submit `max_per_repo`-exceeding numbers of concurrent RPCs against the same physical repository merely by supplying cosmetically different but path-equivalent `relative_path` values on each request. Each distinct string gets admitted as its own limiter bucket (own `max_per_repo` allotment, own queue), so the aggregate concurrency actually hitting the single physical repository is unbounded by the configured cap, while the limiter's accounting/metrics (`gitaly_requests_dropped_total`, per-key monitor events) report the traffic as spread across many "different" repositories.

## Impact Explanation
This defeats the very purpose of `[[concurrency]] max_per_repo`, which exists to stop I/O storms on a single repository from exhausting Gitaly node resources. [7](#0-6) 
An attacker with ordinary push/fetch access to one repository can flood it with concurrent expensive RPCs (e.g. `PostUploadPackWithSidechannel`) by varying only the relative-path string per request, spawning far more concurrent git subprocesses against that repository than intended. This causes resource exhaustion (CPU, memory, file descriptors, disk I/O) for that repository and, transitively, for the whole Gitaly node serving co-located repositories/legitimate clients — a DoS of the RPC-handler resource-limiting mechanism itself, analogous to the txpool being stuffed with items that pass a weak admission gate but defeat the protection the gate was meant to enforce.

## Likelihood Explanation
The attack requires only the ability to send RPCs referencing a repository with attacker-influenced `relative_path` framing (e.g. through client libraries/gateways that pass through path fields, or any RPC caller who controls the `Repository` message field verbatim). No privileged access, leaked tokens, or MITM position is needed — an ordinary authenticated caller of Gitaly (as used by GitLab Workhorse/Rails/gitlab-shell paths that proxy `Repository.RelativePath`) is sufficient once it's possible to express the same physical path in multiple string forms.

## Recommendation
- Compute the concurrency-limiter lock key from the *normalized/validated* relative path (i.e., resolve via the locator's path-cleaning logic, or at minimum `filepath.Clean` combined with `storage.ValidateRelativePath` against the storage root) before deriving `LimitConcurrencyByRepo`'s key, so equivalent paths always collapse to one bucket.
- Alternatively, move admission-time keying to use a canonical repository identity (storage name + resolved on-disk path, or repository ID where already available) rather than the raw untrusted string field.
- Add a regression test asserting that two path-equivalent-but-textually-different `relative_path` values for the same repository share a single concurrency bucket and are jointly bound by `max_per_repo`.

## Proof of Concept
1. Configure `[[concurrency]] rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"`, `max_per_repo = 1`.
2. As an ordinary client with access to repository `group/project.git`, issue N concurrent `PostUploadPackWithSidechannel` RPCs, each specifying a syntactically distinct but path-equivalent `relative_path` for the same physical repository (e.g. `group/project.git`, `group/./project.git`, `group//project.git`, `group/project.git/`), all of which `filepath.Join`/`Clean` collapse to the same on-disk path once inside the handler via `Locator.GetRepoPath`.
3. Observe (via `internal/grpc/middleware/limithandler/middleware.go`'s `getLockKey` / `internal/limiter/concurrency_limiter.go`'s `limitsByKey`) that each variant is treated as a separate key, so all N requests are admitted concurrently despite `max_per_repo = 1`, spawning N concurrent `git-upload-pack` processes against the single repository — exceeding the configured protection and consuming node resources beyond the intended bound.

(Note: full confirmation that `filepath.Join`/`ValidateRelativePath` indeed collapses these specific variants to an identical absolute path was not traced end-to-end through every locator implementation due to index limits; the core defect — that the lock key is derived from the raw untrusted string prior to any normalization/validation performed later by the locator — is confirmed directly from the cited source.)

// ValidateRelativePath validates a relative path by joining it with rootDir and verifying the result
// is either rootDir or a path within rootDir. Returns clean relative path from rootDir to relativePath
// or an ErrRelativePathEscapesRoot if the resulting path is not contained within rootDir.
func ValidateRelativePath(rootDir, relativePath string) (string, error) {
	absPath := filepath.Join(rootDir, relativePath)
	if rootDir != absPath && !strings.HasPrefix(absPath, rootDir+string(os.PathSeparator)) {
		return "", ErrRelativePathEscapesRoot
	}

	return filepath.Rel(rootDir, absPath)
}

# Request limiting in Gitaly

In the GitLab ecosystem, Gitaly is the service that is at the bottom of the
stack for Git data access. This means that when there is a surge of
requests to retrieve or change a piece of Git data, the I/O happens in Gitaly.
This can lead to Gitaly being overwhelmed due to system resource exhaustion
because all Git access goes through Gitaly.

If there is a surge of traffic beyond what Gitaly can handle, Gitaly should
be able to push back on the client calling. Gitaly shouldn't subserviently agree
to process more than it can handle.

We employ concurrency limiting as our primary backpressure mechanism in Gitaly.

type ConcurrencyLimiter struct {

	// calculated adaptively from an outside calculator.

	// maxQueueLength is the maximum number of operations allowed to wait in a queued state.
	// This limit is global and applies before the concurrency limit. Subsequent incoming
	// operations will be rejected with an error immediately.
	maxQueueLength int
	// maxQueueWait is a time duration of an operation allowed to wait in the queue.
	maxQueueWait time.Duration
	// SetWaitTimeoutContext is a function for setting up timeout context. If this is nill, context.WithTimeout is
	// used. This function is for internal testing purpose only.
	SetWaitTimeoutContext func() context.Context

	// monitor is a monitor that will get notified of the state of concurrency-limited RPC
	// calls.
	monitor ConcurrencyMonitor

	m sync.RWMutex
	// limitsByKey tracks all concurrency limits per key. Its per-key entries are lazily created
	// and will get evicted once there are no concurrency-limited calls for any such key
