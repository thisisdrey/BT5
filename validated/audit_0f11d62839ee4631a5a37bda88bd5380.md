### Title
Rate limiter reset on reconfiguration allows bypassing outflow caps - (File: programs/marginfi/src/state/rate_limiter.rs)

### Summary
Reconfiguring a bank's or group's hourly/daily outflow rate limit fully wipes the accumulated outflow counters for that window, regardless of how much capacity was already consumed. Any admin-triggered rate-limit update (`configure_bank_rate_limits` / `configure_group_rate_limits`) instantly restores full outflow capacity for the affected window, mirroring the C4 finding where `_updateAddress` fully replenished `bufferStored` on any config change.

### Finding Description
`RateLimitWindow::initialize` is the function invoked whenever hourly or daily limits are (re)configured: [1](#0-0) 

It unconditionally zeroes `prev_window_outflow` and `cur_window_outflow` and resets `window_start` to the current timestamp — discarding any outflow already recorded in the window. This is invoked directly from the macro-generated `configure_hourly`/`configure_daily` methods used by both the bank-level and group-level limiters: [2](#0-1) 

These are called from the admin-facing instructions: [3](#0-2) [4](#0-3) 

Both instructions are gated to `admin` or `delegate_limit_admin`, per `is_admin_or_limit_admin`. However, exactly like the original MultiRateLimited bug, the reset is triggered by a routine, expected admin action (adjusting a numeric cap), not by any privilege escalation — the impact lands on unprivileged users who consume borrow/withdraw capacity. Whenever the admin/delegate_limit_admin calls `configure_bank_rate_limits` or `configure_group_rate_limits` to change either the hourly or daily cap (e.g., raising a limit in response to growth, or making any adjustment at all), the counter for that window is unconditionally zeroed rather than being capped/preserved relative to the new limit. Users who have already exhausted (or partially used) the hourly/daily outflow capacity for withdrawals/borrows immediately regain full capacity, even though no time has actually elapsed in the real window.

### Impact Explanation
The bank and group rate limiters exist as a defense-in-depth control to cap net outflow (withdraws/borrows) per hour/day at both the per-bank (native token) and per-group (USD) level, as described in the rate-limiting guide:



Because reconfiguration silently resets the accumulated outflow to zero, any legitimate/expected admin adjustment of a rate limit (which is documented as a normal, recurring admin operation) effectively multiplies the outflow allowed within a single "real" hour/day — undermining the intended cap. If the limiter is being relied upon during a live incident (e.g., to slow drainage during a suspected exploit or oracle manipulation event) an admin narrowing the limit to react to the incident actually hands back full capacity to any address that had already exhausted the window, defeating the purpose of the control at the worst possible time.

### Likelihood Explanation
Rate-limit reconfiguration is a normal, expected admin/delegate_limit_admin action (the codebase explicitly supports independent hourly/daily updates and documents "Set to 0 to disable" as a routine action). No malicious admin is required — every legitimate limit adjustment triggers the reset. The condition (some users having already consumed outflow capacity in the current window at the time of reconfiguration) is common under normal operation, especially right when an admin decides a limit needs adjusting due to observed usage.

### Recommendation
When reconfiguring `hourly`/`daily` windows, preserve the already-accumulated outflow (weighted for elapsed time) instead of resetting to zero, capping it at the new `max_outflow` if necessary — analogous to the recommended fix in the referenced report (`bufferStored = min(new_cap, old_buffer)`). Concretely, `RateLimitWindow::initialize` (or a new "reconfigure" variant used by `configure_hourly`/`configure_daily`) should retain `prev_window_outflow`/`cur_window_outflow` (clamped to the new `max_outflow`) rather than always zeroing them, so that in-progress consumption in the current window survives a limit update.

### Proof of Concept
1. Admin sets `hourly_max_outflow = 1000` USDC on a bank via `configure_bank_rate_limits`, initializing the window at `t0`.
2. A user borrows/withdraws 1000 USDC, consuming full hourly capacity (`cur_window_outflow = 1000`), confirmed by the reset behavior tested for the group limiter's inflow/outflow ordering: [5](#0-4) 
3. Minutes later (still within the same hour), the admin calls `configure_bank_rate_limits` again (e.g., to bump the limit to 1200, or even to reapply the same 1000 value for unrelated reasons).
4. `configure_hourly` → `initialize` resets `cur_window_outflow` to `0` and `window_start` to now: [1](#0-0) 
5. The user can immediately borrow/withdraw up to the full new limit again, despite the real hourly window not having elapsed — doubling (or more) their effective outflow within the intended window.

```rust
pub fn configure_bank_rate_limits(
    ctx: Context<ConfigureBankRateLimits>,
    hourly_max_outflow: Option<u64>,
    daily_max_outflow: Option<u64>,
) -> MarginfiResult {
    let mut bank = ctx.accounts.bank.load_mut()?;
    let clock = Clock::get()?;

    if let Some(hourly) = hourly_max_outflow {
        check!(
            is_valid_rate_limit_amount(hourly),
            MarginfiError::InvalidConfig
        );
        bank.rate_limiter
            .configure_hourly(hourly, clock.unix_timestamp);
        msg!(
            "Bank hourly rate limit configured: {} native tokens",
            hourly
        );
    }

    if let Some(daily) = daily_max_outflow {
        check!(
            is_valid_rate_limit_amount(daily),
            MarginfiError::InvalidConfig
        );
        bank.rate_limiter
            .configure_daily(daily, clock.unix_timestamp);
        msg!("Bank daily rate limit configured: {} native tokens", daily);
    }

    Ok(())
}
```
