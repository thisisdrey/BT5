### Title
`native_withdraw` / `storage_deposit` / `auth_call` debit wNEAR before `near_withdraw`/transfer succeeds, with no refund path on failure - ([File: contracts/defuse/src/contract/tokens/nep141/native.rs])

### Summary
`Contract::native_withdraw` (and the analogous `storage_deposit` and deposit-bearing `auth_call` paths) call `self.withdraw(...)` to subtract the user's wNEAR balance *before* the cross-contract `near_withdraw` unwrap and the follow-on `Promise::new(receiver_id).transfer(amount)` in `do_native_withdraw` are executed. If the named `receiver_id` does not exist on-chain (or `near_withdraw` itself fails), the transfer action fails, `require!` panics, and there is no callback that re-credits the signer, permanently destroying the debited value from the signer's perspective.

### Finding Description
The invariant under test is: `wNEAR debited from account A == NEAR delivered to receiver_id, OR wNEAR credited back to A`.

Trace of `native_withdraw` in `contracts/defuse/src/contract/intents/state.rs`:
```
self.withdraw(owner_id, [(wnear_token_id, amount)], Some("withdraw"), false)?;   // debit happens synchronously, immediately
ext_wnear::near_withdraw(amount)
    .then(Self::do_native_withdraw(withdraw))   // fire-and-forget via .detach()
``` [1](#0-0) 

`do_native_withdraw` in `contracts/defuse/src/contract/tokens/nep141/native.rs`:
```rust
#[private]
pub fn do_native_withdraw(withdraw: NativeWithdraw) -> Promise {
    require!(promise_result_checked_void(0).is_ok(), "near_withdraw failed");
    Promise::new(withdraw.receiver_id).transfer(withdraw.amount)
}
``` [2](#0-1) 

Unlike `ft_withdraw`'s path, which schedules `ft_resolve_withdraw` to re-credit any unused amount back to the sender [3](#0-2) , `native_withdraw`'s chain ends with `.detach()` and has **no resolve/callback that re-credits the signer's internal wNEAR ledger**. If `receiver_id` does not exist, the `Promise::new(receiver_id).transfer(amount)` action fails at the protocol level (account does not exist), the deposited NEAR is refunded by the NEAR protocol back to the *contract's own account* (not to the user's internal balance), and the signer's internal wNEAR balance — already subtracted in `self.withdraw(...)` — is never restored. The same missing-refund pattern applies to `storage_deposit` and the deposit-bearing branch of `auth_call`, both of which debit first via `self.withdraw(...)` and then call `near_withdraw` followed by a callback with no re-credit path [4](#0-3) .

This is explicitly acknowledged in the intent documentation itself:
```rust
/// This will subtract from the account's wNEAR balance, and will be sent to the account specified as native NEAR.
/// NOTE: the `wNEAR` will not be refunded in case of fail (e.g. `receiver_id`
/// account does not exist).
pub struct NativeWithdraw { ... }
``` [5](#0-4) 
and similarly for `MtWithdraw::storage_deposit`: `"NOTE: the wNEAR will not be refunded in case of fail"` [6](#0-5) .

Attacker/victim flow: a signer (attacker against themselves, or an attacker crafting a batch on a victim's behalf if the victim signs it, e.g. via a phishing-adjacent `msg`/relayer flow) submits a `NativeWithdraw{ receiver_id: <nonexistent account>, amount }` intent through `execute_intents`. The debit happens synchronously and irreversibly in the same transaction; the failure is only discovered asynchronously in a later receipt, by which point there is no code path to restore the balance.

### Impact Explanation
The signer's wNEAR balance is permanently reduced with no corresponding NEAR delivered to any receiver and no re-credit to the signer — this is a direct case of "user funds permanently frozen (unrecoverable without a privileged action)," matching the Critical severity bucket. It is repeatable for every `NativeWithdraw`, `StorageDeposit`, and deposit-bearing `AuthCall` intent where the receiver/target does not exist or otherwise causes the final transfer/call to fail, so the blast radius is any user who (or whose signed intent) specifies a bad receiver, whether by mistake or via crafted payload.

### Likelihood Explanation
No special privilege is required — any signer can submit a `NativeWithdraw` (or storage-deposit-bearing `FtWithdraw`/`MtWithdraw`/`AuthCall`) intent to `execute_intents` naming a receiver account that does not exist. The precondition (non-existent receiver) is trivial to satisfy and entirely attacker-controlled. Attacker cost is limited to the wNEAR amount they choose to withdraw (if targeting their own funds this is self-inflicted unless combined with a signed-batch relay scenario), and the flaw is deterministic and reproducible in a sandbox test.

### Recommendation
Add a resolver callback (analogous to `ft_resolve_withdraw`) for `native_withdraw`, `storage_deposit`, and the deposit-bearing `auth_call` path that inspects the result of the final transfer/`do_native_withdraw`/`do_auth_call` promise and re-credits the signer's internal wNEAR balance via `self.deposit(...)` when the transfer fails, mirroring the existing NEP-141 withdraw resolve pattern.

### Proof of Concept
`cargo test` plan (near-workspaces sandbox, extending `tests/src/tests/defuse/intents/native_withdraw.rs`):
1. Deposit wNEAR into the intents contract for `user`, recording `balance_before = defuse.mt_balance_of(user, wnear_token_id)`.
2. Sign and submit via `execute_intents` a `NativeWithdraw { receiver_id: "nonexistent-account.near".parse().unwrap(), amount }` where `nonexistent-account.near` has never been created on the sandbox.
3. Await final execution of all receipts (`wait_until::<Final>()`), then assert:
   - `defuse.mt_balance_of(user, wnear_token_id) == balance_before - amount` (debit occurred), and
   - the receiver account's balance/existence check confirms NEAR was never delivered (`view_account("nonexistent-account.near")` fails / account still doesn't exist).
4. Assert there is no subsequent internal credit event for `user` restoring `amount`, proving `balance_before - amount != NEAR delivered + NEAR refunded to user`, i.e., the equality binding is violated and funds are permanently stuck.

#[near]
impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
