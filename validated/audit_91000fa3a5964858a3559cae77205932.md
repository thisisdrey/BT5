### Title
Handshake public-key rebind on an already-authenticated connection accepted without proof of possession of the new key - (File: stackslib/src/net/chat.rs)

### Summary
`ConversationP2P::validate_handshake` only calls `message.verify_secp256k1(&handshake_data.node_public_key)` when `self.connection.get_public_key()` is `None`; once a connection already has a public key (the `Some(_)` branch), the function performs only an address/port sanity check and never verifies that the *new* claimed `node_public_key` actually signed the handshake. `update_from_handshake_data` (chat.rs:1131-1167) then unconditionally calls `self.connection.set_public_key(Some(pubk.clone()))`, silently "upgrading" the session identity from key A to key B.

### Finding Description
The intended equality is: *the public key recorded as `self.connection.get_public_key()` must equal the public key that produced the signature of the most recently accepted message on this connection.* This equality is broken in the re-key path. [1](#0-0) 

- If `get_public_key()` is `None`, the code verifies the message was signed by the claimed `node_public_key` (line 1063), so the first handshake is safe: a session can only be bootstrapped to key A if the message was actually signed by A.
- If `get_public_key()` is `Some(A)` (already established), the code enters the `Some(_)` branch and performs **only** an outbound address/port match check — it never calls `verify_secp256k1` against the new `handshake_data.node_public_key` (B), and it never re-checks that the message was signed by B.

Any inbound message on the wire, including a subsequent `Handshake`, is authenticated at the transport/session layer using the *currently known* key (A), because that is the only key the connection trusts at that point. Consequently, a peer that holds only key A's private key can construct and sign (with A) a second `Handshake` payload whose `node_public_key` field claims to be an arbitrary key B (which the attacker need not control at all). This message passes the session-level signature check (it is legitimately signed by A, the key the connection currently trusts) and then reaches `validate_handshake`'s `Some(_)` branch, which does not re-validate B. `update_from_handshake_data` then executes unconditionally: [2](#0-1) 

setting `self.connection`'s trusted public key to B, with `updated = true`, even though B never signed anything. All bookkeeping fields (`peer_expire_block_height`, `handshake_addrbytes`, `handshake_port`, `data_url`, `peer_services`) derived from the handshake are also blindly overwritten from attacker-controlled data at this point.

The only anti-flip-flop guard in `validate_handshake` is the branch on `get_public_key() == Some(_)`, and that branch's logic addresses address/port consistency for outbound peers only — it does not enforce "the new key must sign the rekey request," which is the actual security property needed to prevent an unauthorized identity change on an existing, already-trusted connection.

### Impact Explanation
An attacker who holds a single valid keypair (A) and completes one legitimate handshake can subsequently relabel that same live connection as belonging to an arbitrary different public key B without ever proving possession of B's private key. Downstream consumers of `ConversationP2P` that rely on `get_public_key()` (or the neighbor/`PeerDB` records populated from `update_from_handshake_data`) will treat frames on this socket as coming from identity B going forward, and record a (socket-address, B) association in the peer's neighbor state, without any cryptographic proof B authorized it. This is a session-identity/authentication-integrity violation (auth bypass on the P2P conversation layer): it lets one connection falsely claim to be an arbitrary other network identity, which can pollute the target node's neighbor table / trust bookkeeping and be repeated at will for any B chosen by the attacker (as often as they can complete a handshake and immediately re-handshake).

I was not able to fully trace, within the available search budget, whether any privileged write path (e.g., StackerDB chunk admission) authorizes purely off `ConversationP2P::get_public_key()` rather than off the per-chunk signature verified independently against the slot owner's key hash; if such a path exists, this becomes a Critical unauthorized-write bypass, but that dependency chain requires further verification (`p2p.rs` / `stackerdb/mod.rs` message dispatch was not fully inspected in this session).

### Likelihood Explanation
- Attacker only needs to be a normal remote peer capable of completing one handshake with its own real keypair A — no privileged role, secret, or additional peer key is required.
- The second, key-swapping `Handshake` must be signed with A (which the attacker already controls) yet can name an arbitrary `node_public_key` field (B); no cryptographic material for B is needed.
- Reachable directly on the P2P port with no rate limiting beyond normal message processing.
- Fully repeatable per connection and can be repeated across separate connections to different combinations of A/B.

### Recommendation
In `ConversationP2P::validate_handshake`, when `self.connection.get_public_key()` is `Some(cur_pubk)` and the incoming `handshake_data.node_public_key != cur_pubk`, require that the message be independently verified against the *new* claimed key (`message.verify_secp256k1(&handshake_data.node_public_key)`) before allowing `update_from_handshake_data` to call `set_public_key`. This proves possession of the new private key for any rekey, matching the security guarantee already provided for first-time handshakes in the `None` branch.

### Proof of Concept
1. In a `stackslib::net::chat` test harness (similar to existing `test_convo_handshake_accept`-style tests in `chat.rs`), establish `convo_1` (attacker, holding real keypair A) and `convo_2` (victim) and perform a normal signed `Handshake`/`HandshakeAccept` exchange so `convo_2.connection.get_public_key() == Some(A)`.
2. From `convo_1`, construct a second `StacksMessage` of type `Handshake` whose `HandshakeData.node_public_key` is set to an arbitrary key B (generate a fresh `Secp256k1PrivateKey`/`PublicKey` for B, but do **not** sign with B's key), sign the outer message with A's private key (`convo_1`'s existing session key), and send it over the same socket to `convo_2`.
3. Feed the bytes to `convo_2.handle_handshake(...)` and assert `convo_2.connection.get_public_key() == Some(B)` — despite the message never having been signed by B's private key.
4. Assert this contradicts the expected security property (that `get_public_key()` only ever equals a key that has cryptographically signed a message on that connection), demonstrating the auth-bypass at `stackslib/src/net/chat.rs:1058-1092` and `1149-1167`.

        match self.connection.get_public_key() {
            None => {
                // if we don't yet have a public key for this node, verify the message.
                // if it's improperly signed, it's probably a poorly-timed re-key request (but either way the message should be rejected)
                message
                    .verify_secp256k1(&handshake_data.node_public_key)
                    .map_err(|_e| {
                        debug!(
                            "{:?}: invalid handshake: not signed with given public key",
                            &self
                        );
                        net_error::InvalidMessage
                    })?;
            }
            Some(_) => {
                // for outbound connections, the self-reported address must match socket address if we already have a public key.
                // (not the case for inbound connections, since the peer socket address we see may
                // not be the same as the address the remote peer thinks it has).
                // The only exception to this is if the remote peer does not yet know its own
                // public IP address, in which case, its handshake addrbytes will be the
                // any-network bind address (0.0.0.0 or ::)
                if self.stats.outbound
                    && (!handshake_data.addrbytes.is_anynet()
                        && (self.peer_addrbytes != handshake_data.addrbytes
                            || self.peer_port != handshake_data.port))
                {
                    // wrong peer address
                    debug!(
                        "{:?}: invalid handshake -- wrong addr/port ({:?}:{:?})",
                        &self, &handshake_data.addrbytes, handshake_data.port
                    );
                    return Err(net_error::InvalidHandshake);
                }
            }
        };
