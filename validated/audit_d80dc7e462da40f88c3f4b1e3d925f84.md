### Title
Unbounded stall of Nakamoto confirmed-tenure download via repeated empty `GetTenureBlocks` responses - (File: `stackslib/src/net/download/nakamoto/tenure_downloader.rs`, `stackslib/src/net/download/nakamoto/tenure_downloader_set.rs`)

### Summary
`NakamotoTenureDownloader::try_accept_tenure_blocks` treats an empty tenure-blocks payload as `Ok(None)` ("nothing to do") without advancing the `GetTenureBlocks` cursor and without returning an error. Because `NakamotoTenureDownloaderSet::run` only calls `mark_failed_and_deprioritize_peer` on the `Err(..)` branch of `handle_next_download_response`, a peer that always answers with an empty block list is never marked as failed, never deprioritized, and its assigned tenure is never rescheduled to another peer. If that peer is the only one advertising the tenure, the tenure download stalls indefinitely.

### Finding Description
The state machine's tenure-block acceptance logic short-circuits on empty payloads: [1](#0-0) 

This returns `Ok(None)` without touching `self.state`, so `NakamotoTenureDownloadState::GetTenureBlocks(block_cursor, ..)` remains exactly as it was.

`handle_next_download_response` forwards this `Ok(None)` unchanged and merely resets `idle = true`: [2](#0-1) 

In `NakamotoTenureDownloaderSet::run`, the response-handling loop treats `Ok(None)` as a no-op continue, with no call to `mark_failed_and_deprioritize_peer`: [3](#0-2) 

`mark_failed_and_deprioritize_peer`/`mark_failure` (which populates `attempt_failed_tenures` and `deprioritized_peers`) is only invoked from the `Err(e)` arms of `send_next_download_request` and `handle_next_download_response`: [4](#0-3) 

Since the connection stays valid (HTTP 200 with a well-formed but empty JSON array), `neighbor_rpc.is_dead_or_broken` never fires, so the downloader is never cleared via `clear_downloader`, and `downloader.is_done()` never becomes true. Consequently, in `make_tenure_downloaders`, once a downloader for consensus hash `ch` exists, `has_downloader_for_tenure(ch)` is true forever, so the tenure is never re-scheduled to a different peer even though it was already popped from `schedule` at assignment time: [5](#0-4) 

Each `run()` pass will call `try_advance_from_chainstate` (no-op for `GetTenureBlocks`) then `send_next_download_request`, which re-issues the exact same `GetTenureBlocks(block_cursor, ..)` HTTP request to the same peer indefinitely: [6](#0-5) 

Attack: an attacker-controlled peer that is (or becomes) the sole neighbor advertising a given confirmed tenure `CH` in the node's `available_tenures`/`tenure_block_ids`, and that always answers `GetNakamotoTenure` requests for that tenure with a technically well-formed but empty block list, causes the corresponding `NakamotoTenureDownloader` to loop forever in `GetTenureBlocks` without ever failing, being deprioritized, or being reassigned to another peer.

### Impact Explanation
The affected tenure's downloader permanently wedges on the malicious peer. Because tenure downloaders are chained (the N+1'st tenure feeds start-block data into the Nth), this can block the confirmed-tenure catch-up pipeline for that portion of history, keeping the node stalled behind the canonical tip for that tenure slot as long as the attacker keeps responding. The attacker expends negligible effort (one canned empty response repeated) to hold a download slot hostage indefinitely, with no way for the existing logic to detect or route around it. This is a logic-level liveness/DoS defect reachable from an unprivileged remote peer over the P2P RPC surface, not a crash or data-forgery bug, and is repeatable at will.

### Likelihood Explanation
Preconditions: the attacker must be (or become) the only neighbor whose inventory claims to serve consensus hash `CH` in the node's currently known peer set for that tenure — plausible in a network with few peers or when the honest peers serving `CH` are temporarily unavailable/slow to be discovered. No secret, admin role, or privileged state is required; the attacker only needs to run a normal P2P-connected peer and answer `GetNakamotoTenure` requests with an empty array. The condition is fully attacker-controlled and trivially repeatable across `run()` passes.

### Recommendation
In `try_accept_tenure_blocks`, treat repeated empty responses for the same `block_cursor` as a failure after a bounded number of attempts (or immediately), rather than silently returning `Ok(None)` with no state change. Alternatively, track per-downloader empty-response counts in `NakamotoTenureDownloaderSet::run` and call `mark_failed_and_deprioritize_peer` + `clear_downloader` once a threshold is exceeded, so the tenure gets rescheduled to another peer/reinserted into `schedule`.

### Proof of Concept
Rust net test plan (in `stackslib/src/net/tests/download/nakamoto.rs` style):
1. Construct a `NakamotoTenureDownloader` in `GetTenureBlocks(end_block_id, t0)` state via `NakamotoTenureDownloaderSet::make_tenure_downloaders` with a single neighbor `naddr` advertising tenure `ch`.
2. Loop `N = 1000` times calling `downloaders.run(&mut network, &mut neighbor_rpc, &mut chainstate)`, mocking `neighbor_rpc.collect_replies` to always return, for `naddr`, an HTTP 200 response decoding (via `decode_nakamoto_tenure`) to `vec![]`.
3. Assert after the loop that:
   - `downloader.state` is still `GetTenureBlocks(end_block_id, ..)` (unchanged cursor),
   - `downloaders.attempt_failed_tenures.get(&ch)` is `None`/`0`,
   - `downloaders.deprioritized_peers.get(&naddr)` is `None`,
   - `downloaders.has_downloader_for_tenure(&ch)` is still `true`, and the tenure was never re-added to another peer's schedule — demonstrating the unbounded stall described above.

    pub fn send_next_download_request(
        &mut self,
        network: &mut PeerNetwork,
        neighbor_rpc: &mut NeighborRPC,
    ) -> Result<bool, NetError> {
        if neighbor_rpc.has_inflight(&self.naddr) {
            debug!("Peer {} has an inflight request", &self.naddr);
            return Ok(true);
        }
        if neighbor_rpc.is_dead_or_broken(network, &self.naddr) {
            return Err(NetError::PeerNotConnected(format!(
                "Failed to send next download request to {:?}: connection is dead or broken",
                &self.naddr
            )));
        }

        let Some(peerhost) = NeighborRPC::get_peer_host(network, &self.naddr) else {
            // no conversation open to this neighbor
            neighbor_rpc.add_dead(
                network,
                &self.naddr,
                DropReason::DeadConnection("No authenticated connection open".into()),
                DropSource::NakamotoTenureDownloader,
            );
            return Err(NetError::PeerNotConnected(format!(
                "No authenticated connection open to {:?} for tenure download",
                &self.naddr
            )));
        };

        let request = match self.make_next_download_request(peerhost) {
            Ok(Some(request)) => request,
            Ok(None) => {
                return Ok(true);
            }
            Err(_) => {
                return Ok(false);
            }
        };

        neighbor_rpc.send_request(network, self.naddr.clone(), request)?;
        self.idle = false;
        Ok(true)
    }

    fn mark_failure(attempt_failed_tenures: &mut HashMap<ConsensusHash, u64>, ch: &ConsensusHash) {
        if let Some(failures) = attempt_failed_tenures.get_mut(ch) {
            *failures = (*failures).saturating_add(1);
        } else {
            attempt_failed_tenures.insert(ch.clone(), 1);
        }
    }
