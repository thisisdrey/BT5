### Title
Unsolicited StackerDB push handler advertises a chunk version in its inventory reply before the chunk is actually committed to the local replica - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates an unsolicited `StackerDBPushChunkData` (signature, freshness, size, write-count) and then immediately patches the `StackerDBChunkInv` reply it is about to send back to the sender, marking the pushed slot as being at the new `slot_version` — before the chunk has actually been written to the local StackerDB replica via `StackerDBTx::try_replace_chunk`/`insert_chunk`. The actual database write only happens later, asynchronously, when the message is forwarded to the relayer for processing. This creates a window in which the node's advertised inventory (what it tells peers it has) is ahead of its committed state (what is actually durable on disk), i.e. a "served vs. committed" equality break, analogous to the HomoraBank report's core defect where a value is recorded as pending but treated in some paths as if it were already resolved/committed.

### Finding Description
`validate_received_chunk` (stackslib/src/net/stackerdb/mod.rs:649-718) only checks that a pushed chunk (a) fits the configured `chunk_size`, (b) is signed by the slot's registered owner, (c) is not stale relative to `expected_versions`, and (d) does not exceed `max_writes`. It performs no database write.

In `handle_unsolicited_StackerDBPushChunk` (stackslib/src/net/stackerdb/mod.rs:742-870), after this validation succeeds for the `StackerDBChunkInv` branch, the code does:

```
// patch inventory -- we'll accept this chunk
let Some(slot_version) = data.slot_versions.get_mut(chunk_data.chunk_data.slot_id as usize) ...
*slot_version = chunk_data.chunk_data.slot_version;
``` [1](#0-0) 

and then, if `send_reply` is true, immediately signs and sends this patched `StackerDBChunkInv` back to the peer as this node's current view of the slot:

```
let resp = self.sign_for_p2p_reply(event_id, preamble.seq, payload)?;
let handle = self.send_p2p_message(...)?;
``` [2](#0-1) 

At no point in this function is `StackerDBTx::try_replace_chunk` (stackslib/src/net/stackerdb/db.rs:400-438) called to actually persist the chunk into the `chunks` table. The comment on the function itself acknowledges this constraint: "Note that this can happen *during* a StackerDB sync's execution, so be very careful about modifying a state machine's contents! The only modification possible here is to wakeup the state machine..." — i.e. this handler is explicitly not supposed to perform the durable write; that is deferred to the relayer, which processes the message later (out of this function's control flow, and only if `send_reply` is false, per the "forward to relayer" return path at stackslib/src/net/stackerdb/mod.rs:858-860).

This mirrors the report's bug class: a fact about state (interest/fee accrual, here "I now have version N of this chunk") is computed and used to answer external queries (here, telling a peer "my inventory is now version N") before the corresponding durable state change (here, the actual chunk write; there, incrementing `totalDebt`) has taken effect. Any remote, unauthenticated peer that can open a P2P connection and push a chunk can trigger this gap merely by sending a validly-signed `StackerDBPushChunkData` — no elevated privileges or node secrets are required.

### Impact Explanation
This falls into the "steering a node off the tip via false inventory" High-impact category explicitly enumerated in scope. A peer that requests the local node's `StackerDBChunkInv` in the window between the reply being sent and the chunk actually being committed will believe the node already has the latest chunk. If that requesting peer then also tells other replicas that this node has the new version (e.g., in chunk-inventory gossip or reward-cycle sync bookkeeping such as `add_pushed_chunk`/`recalculate_chunk_request_schedule` in stackslib/src/net/stackerdb/sync.rs), or if it simply performs a `StackerDBGetChunk` against this node before the relayer catches up, it can be served stale data or a `NoSuchSlot`/mismatch response inconsistent with the inventory it was just given — an inventory/state mismatch that can stall or misdirect StackerDB synchronization for the affected contract (e.g., a signer-set or miner StackerDB), which is used by consensus-adjacent processes such as signer message replication.

### Likelihood Explanation
Likelihood is moderate: any peer with an established, authenticated P2P connection (this is a normal, unprivileged operation — no signer key or node secret is required, only a chunk signed by the slot's already-registered owner, which any user with a StackerDB slot can produce) can push a chunk and immediately observe the discrepancy between the returned inventory ack and the actual, not-yet-written chunk. The relayer's processing delay (queueing, buffering limits `max_buffered_stackerdb_chunks`, or a temporarily busy event loop) widens this window, making it easier to race a subsequent `StackerDBGetChunk`/`StackerDBChunkInv` request against the not-yet-persisted write.

### Recommendation
Do not patch/advertise the new slot version in the `StackerDBChunkInv` reply until the chunk has actually been persisted (i.e., only after a successful `StackerDBTx::try_replace_chunk` call, or after confirmation from the relayer that the write succeeded). If the write must remain deferred to the relayer for architectural reasons, the immediate reply should reflect only the previously-committed inventory state, and the updated version should only be advertised in a subsequent `StackerDBChunkInv` sent after the relayer's write completes.

### Proof of Concept
1. Establish an authenticated P2P connection to a target node running a StackerDB contract.
2. Craft a `StackerDBPushChunkData` for a slot you own, properly signed, with a fresh `slot_version` that passes `validate_received_chunk`.
3. Send it as an unsolicited message; the target immediately replies with a `StackerDBChunkInv` reporting the new `slot_version` for that slot (stackslib/src/net/stackerdb/mod.rs:794-807, 862-870), even though the relayer has not yet executed the write.
4. Immediately issue a `StackerDBGetChunk` request (or observe the target's chunk inventory being propagated to third-party peers) for that slot/version before the relayer processes the buffered push; the response can reflect the pre-write (stale) chunk data or fail, demonstrating the served-inventory vs. committed-data mismatch.

Note: due to indexing/tool limits I was not able to fully trace the exact relayer code path in `stackslib/src/net/relay.rs` that performs the deferred `try_replace_chunk` write for `StackerDBPushChunkData`, so the precise timing/size of the race window could not be measured from source alone; this would need to be confirmed with a live/integration test.
