### Title
DOS of Exchange Withdrawal via Front-Run Ratio Manipulation - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeWithdrawActuator` enforces a strict "precise enough" ratio check between the withdrawn token amount and the exchange pool's *live* balances at execution time. Because those live balances (`firstTokenBalance`/`secondTokenBalance`) can be altered by anyone via a trivial `ExchangeTransactionContract` trade immediately before the withdrawal is mined, an attacker can front-run a pending `ExchangeWithdrawContract` to shift the ratio just enough to make the check fail, causing the legitimate withdrawal to revert. This mirrors the "strict ratio verification + attacker-manipulable balance" DOS pattern described in the external report (donate-then-deposit against Vault ratio checks).

### Finding Description
`ExchangeWithdrawActuator.doValidate()` computes the counterpart withdrawal amount from the *current* pool ratio and requires it to match the client-specified `tokenQuant` to within a 0.01% tolerance: [1](#0-0) 

This is directly analogous to the Vault's `ratiosMatch(balances, amts)` check: the transaction's expected outputs are compared against the *current* on-chain balances at execution time, not a value pinned when the transaction was signed.

Crucially, `firstTokenBalance`/`secondTokenBalance` are not immutable per-account ledger entries but a shared AMM-style pool state that is mutated by *any* account calling `ExchangeTransactionActuator` (a trade), which applies a Bancor-style relay formula and updates the same two balances used in the withdrawal ratio check: [2](#0-1) [3](#0-2) 

Since `ExchangeTransactionContract` (trade) is callable by any unprivileged account and only requires holding a negligible amount of one of the pool tokens (or TRX) plus the small `calcFee()`, an attacker can observe a pending `ExchangeWithdrawContract` in the mempool and submit a minimal trade transaction with higher priority/fee ahead of it. This trade perturbs `firstTokenBalance`/`secondTokenBalance` by even a small amount, which is enough to push the precomputed `anotherTokenQuant` outside the 0.01% tolerance window enforced in the withdraw's validate step, causing `"Not precise enough"` to be thrown and the victim's withdrawal to fail (this is functionally the "donate followed by deposit()" analog from the report, replacing "direct token donation" with "a permissionless negligible trade" — the same effect on the shared ratio state).

### Impact Explanation
Any account that created a Bancor-style Exchange pool and wants to withdraw its liquidity can be permanently or repeatedly denied that ability by any unprivileged attacker who monitors the mempool and front-runs with negligible trades. This is a denial-of-service against a legitimate, previously-valid, signed transaction, forcing the victim to repeatedly resubmit (each time incurring fees) while the attacker can grief indefinitely at low cost — matching the class of "an API the node can no longer serve as intended" / DOS of a protocol operation.

### Likelihood Explanation
The attack requires only:
1. Visibility of the pending `ExchangeWithdrawContract` in the mempool (or knowledge that the victim regularly withdraws), and
2. Submission of a normal `ExchangeTransactionContract` trade with a minimal quantity and enough fee/priority to be included first.

No special privileges, staking, or resource costs beyond ordinary transaction fees are required, making this trivially and repeatedly executable by anonymous transaction broadcasters targeting exchange creators.

### Recommendation
Loosen or remove the tight (0.01%) precision/ratio check in `ExchangeWithdrawActuator.doValidate()`, or snapshot the pool ratio the withdrawal is validated against in a way that is not trivially manipulable by an interleaved trade in the same or adjacent block (e.g., compute the withdrawal purely from the requested token quantity and pool share proportional to total supply, rather than requiring the caller-supplied `tokenQuant` to match an externally-perturbable live ratio to high precision). Alternatively, allow a slippage/tolerance parameter set by the caller (similar to `ExchangeTransactionActuator`'s `tokenExpected` slippage-protection field) instead of a hardcoded tight tolerance that anyone can violate via front-running.

### Proof of Concept
1. Exchange creator `A` builds and signs an `ExchangeWithdrawContract` for `tokenQuant` computed against the exchange's current `firstTokenBalance`/`secondTokenBalance`, expecting `anotherTokenQuant` to pass the 0.01% precision check.
2. Attacker `B` observes `A`'s pending transaction in the mempool.
3. `B` submits an `ExchangeTransactionContract` trading a minimal amount of either pool token, which is processed by `ExchangeCapsule.transaction()` and updates the pool's `firstTokenBalance`/`secondTokenBalance` (see [2](#0-1) ), with a higher fee/priority so it lands in the same or an earlier block than `A`'s withdrawal.
4. When `A`'s `ExchangeWithdrawContract` executes, `doValidate()` recomputes `anotherTokenQuant` against the now-shifted balances; the recomputed remainder now exceeds the 0.01% tolerance (as demonstrated by existing test `SameTokenNameCloseNotPreciseEnough2` / `hardenedPrecisionCheckFailsWhenImprecise`, which show how a small balance perturbation trips `"Not precise enough"`): [4](#0-3) 
5. `A`'s withdrawal reverts with `ContractValidateException("Not precise enough")`, and `B` can repeat this indefinitely to keep denying `A`'s withdrawal.

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {

          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc

          : secondTokenBalance - buyTokenQuant;

          : firstTokenBalance - buyTokenQuant;

          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;
