### Title
Protocol fee bypass on `Nep245`/`Imt` `TokenDiff` intents via unit-delta splitting - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` waives the protocol fee for `Nep245`/`Imt` tokens whenever the per-intent `|delta| <= 1`, and `TokenDiff::execute_intent` computes/collects the fee independently for each `TokenDiff` intent in a batch instead of on the aggregate token_in amount. A solver can split a large fungible `Nep245`/`Imt` token_in amount `N` (`N > 1`) into `N` signed `TokenDiff` intents each with `delta == -1` on the same `token_id`, causing every individual fee computation to hit the zero-fee branch, so the total fee collected by `fee_collector` is `0` instead of `Pips::fee_ceil(fee, N)`.

### Finding Description
The binding that should hold is: `sum(fees_collected[T] for each TokenDiff::execute_intent call in the batch) == Pips::fee_ceil(protocol_fee, sum(|negative deltas of T| across the batch))`.

In `TokenDiff::execute_intent`, for each negative delta the fee is computed strictly from that single intent's `amount = delta.unsigned_abs()`: [3](#0-2) 

`TokenDiff::token_fee` explicitly zeroes the fee for `Nep245`/`Imt` (and `Nep171`) tokens when `amount <= 1`: [4](#0-3) 

A `DefuseIntents` payload can carry an arbitrary `Vec<Intent>`, and each is executed independently with no shared/aggregated fee-accumulator across intents in the same signed batch: [2](#0-1) 

Attack: the solver deposits/holds `N` units of a `Nep245` token `T` (a multi-token id representing a fungible balance, e.g. a wrapped fungible asset under NEP-245) and signs one `DefusePayload` (or several `MultiPayload` entries) containing `N` separate `TokenDiff` intents, each with `diff = {T: -1, token_out: +k}` (k chosen per intent to keep balances net to zero, or paired with other counterparty intents so the batch nets to zero as required by the Verifier's invariant). For each such intent, `amount = 1`, so `Self::token_fee(T, 1, fee)` returns `Pips::ZERO`, hence `fee_ceil(1) = 0`. Summed across all `N` intents, `fees_collected[T] = 0`. Had the solver instead signed a single `TokenDiff` with `delta = -N`, `token_fee(T, N, fee)` would return the nonzero `fee`, and `fee.fee_ceil(N) > 0` for typical fee configs. No existing guard (`MultiPayload::verify`, nonce checks, `TransferMatcher::finalize`) aggregates deltas per token across intents before calling `token_fee`, so the zero-fee threshold is evaluated per-intent rather than per aggregate token_in flow, defeating the intended fee logic.

### Impact Explanation
This under-collects protocol fees credited to `fee_collector` for `Nep245`/`Imt` token_in flows — a direct case of "protocol fees bypassed or over-collected" (Critical per the stated impact categories). The `fee_collector`'s expected balance is reduced by the entire fee that should have applied to the aggregate token_in amount. It's repeatable by any solver for any `Nep245`/`Imt` token and any batch size `N`, as long as the solver can structure the counterparty side of the trade (their own account, or coordinate with a counter-signer) to net the batch to zero. The bug only exists for `Nep245`/`Imt` token types since `Nep141` fees are computed by amount regardless of size and `Nep171` (true NFTs) can never have `|delta| > 1` legitimately.

### Likelihood Explanation
Any unprivileged account holding `Nep245`/`Imt` balances of size `N > 1` and one signing key can execute this by simply signing `N` `TokenDiff` intents instead of one — no special role, deposit `msg` trick, or contract deployment is required. It costs only extra transaction/gas overhead for the additional intents in the batch, which is proportional to `N` but requires no permission and can be repeated on every future trade of that token type. Preconditions are minimal: solver-controlled fungible `Nep245`/`Imt` balance and a way to net the batch to zero (either self-trading via two of their own accounts, or with any willing counterparty), both freely achievable by an attacker.

### Recommendation
Compute the fee zero-threshold based on the aggregate negative delta per `token_id` across the entire `DefuseIntents`/batch (or across all `TokenDiff` intents sharing the same signer and token), not per individual `TokenDiff` intent. Alternatively, remove the `amount <= 1` fee waiver for `Nep245`/`Imt` (fungible-capable) token types entirely, or require it to be based on batch-level aggregation performed once by the engine before dispatching to individual `TokenDiff::execute_intent` calls.

### Proof of Concept

1. Set up `Env` with a nonzero `fee` (e.g. `Pips::ONE_PERCENT`) and `fee_collector`.
2. Create a solver account with `Nep245` token `T` balance of `N = 100` (e.g. via `deposit`/`mt_on_transfer`).
3. Case A (single intent): sign one `TokenDiff` with `diff = {T: -100, token_out: +closure}` and `execute_intents`. Assert `fee_collector`'s balance of `T` equals `Pips::ONE_PERCENT.fee_ceil(100)` (nonzero).
4. Case B (split): sign 100 separate `TokenDiff` intents in one `DefuseIntents`/`MultiPayload`, each `diff = {T: -1, token_out: +closure_delta(token_out, ...)}`, balanced against a counterparty (or paired self-consistent deltas) so the batch invariant holds, and `execute_intents`. Assert `fee_collector`'s balance of `T` is `0`.
5. Assert the two `fee_collector` balances differ (Case A > 0, Case B == 0), proving the binding `sum(fees_collected) == Pips::fee_ceil(fee, sum(|deltas|))` is violated when deltas are split into unit-sized `TokenDiff` intents.
