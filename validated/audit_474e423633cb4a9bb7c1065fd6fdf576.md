### Title
Attacker fills a victim's (or the fee collector's) per-account token list to `MAX_TOKENS_PER_USER` via dust deposit-token transfers, permanently reverting any new-token mint/transfer/issue for that account (DoS) - ([File: contracts/Pool.sol](contracts/Pool.sol) / [contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The bug class of CVE-2025-50077 is an easily-triggered availability failure (hang/crash → in EVM terms, a forced revert that blocks protocol operations). The closest reachable Metronome analog is the `MAX_TOKENS_PER_USER` accounting in `Pool`, combined with the permissionless `DepositToken.transfer`/`deposit(onBehalfOf_)` paths: any EOA can force-add entries to an arbitrary account's `depositTokensOfAccount` set without the victim's consent, and once `debtTokensOfAccount + depositTokensOfAccount >= 30`, every subsequent operation that would add a *new* token to that account reverts with `UserReachedMaxTokens`.

### Finding Description
- `Pool.MAX_TOKENS_PER_USER = 30`, and the modifier `onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30`. It guards `addToDebtTokensOfAccount` and `addToDepositTokensOfAccount` ( [1](#0-0) [2](#0-1) [3](#0-2) ).
- `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's balance is zero — there is no opt-in and the `to_` side is never checked for consent ( [4](#0-3) ).
- `DepositToken._mint` does the same, so `deposit(amount_, onBehalfOf_)` lets anyone push a new entry onto *any* account's list by depositing dust on their behalf ( [5](#0-4) [6](#0-5) ).
- `DepositToken.transfer` only validates the *sender's* unlocked balance via `_revertIfLocked(_msgSender, amount_)`; the recipient has no way to refuse ( [7](#0-6) ).

Attack: an unprivileged attacker deposits (or transfers) dust amounts of each registered `DepositToken` to a target account until `depositTokensOfAccount.length(target) + debtTokensOfAccount.length(target) == 30`. From that block onward:

1. `deposit(amount, victim)` for any deposit token the victim doesn't already hold reverts — the victim cannot add a new collateral type.
2. `DebtToken` minting a *new* synthetic for the victim reverts via `addToDebtTokensOfAccount` — the victim cannot borrow a new asset.
3. The same applies to `Pool.feeCollector()`: both `deposit` and `_withdraw` mint/transfer the fee to `feeCollector` ( [8](#0-7) [9](#0-8) ). If the attacker fills the fee collector's list, **every** deposit/withdraw on a not-yet-held deposit token reverts pool-wide while fees are non-zero.

### Impact Explanation
The invariant that breaks is liveness/availability of core flows (deposit, issue/borrow, withdraw fee paths) — directly mirroring the CVE's "complete DOS" impact:

- **Per-victim DoS + forced liquidation**: a victim whose position approaches the liquidation threshold cannot deposit a new collateral type to restore health; their only recourse is shedding a dust token, which is impossible once their position is unhealthy — `unlockedBalanceOf` returns 0 when `_issuableInUsd == 0` and debt > 0, so the attacker-dust tokens are locked and cannot be transferred out to free a slot ( [10](#0-9) ). The position is then liquidated, converting a pure DoS into loss of funds.
- **Pool-wide temporary DoS via feeCollector**: once the fee collector's list is at cap, deposits and withdrawals that mint fee tokens for any deposit token the collector doesn't already hold revert, freezing those flows until the fee collector manually transfers tokens out.
- The revert is repeatable and costs the attacker only dust amounts of underlying plus gas.

### Likelihood Explanation
- Fully permissionless: requires only an EOA, a dust amount of each listed collateral, and the public `deposit`/`transfer` entry points. No privileged role, oracle manipulation, or malicious endpoint is needed — satisfying the unprivileged-attacker model.
- Feasibility depends on deployed configuration: the attacker can contribute at most `number of registered DepositTokens` entries on their own, so the attack fills the cap when `registeredDepositTokens + victim's existing entries ≥ 30`, or outright whenever the pool lists ≥30 deposit tokens. The cap-check exists precisely because the account lists are iterated in `debtOf`/`depositOf`/`debtPositionOf`, so the number of listed collaterals is expected to grow over time ( [11](#0-10) ).
- No modifier stops it: `transfer` has no pause check on the recipient side, `addToDepositTokensOfAccount` only validates `msg.sender` is a registered token, and the cap check is the bug's own trigger.
- Cost is linear in dust + gas; a single attacker contract can batch the fills.

### Recommendation
- Only count tokens for which the account has a *meaningful* position, or exempt dust: e.g., enforce a minimum mint/transfer amount to trigger `addToDepositTokensOfAccount`, or add the entry lazily on first deposit by the account owner rather than on any incoming transfer.
- Allow accounts (and the fee collector) to remove entries themselves, e.g., a permissionless `removeFromDepositTokensOfAccount` triggered on transfer-out to `address(0)`-equivalent flows, or let `transfer` skip `addToDepositTokensOfAccount` for recipients that opted out.
- Alternatively, replace the revert-on-cap with a cap enforced only for debt tokens (the DoS-critical list for `debtPositionOf`), letting deposit-token entries grow or be tracked off-chain for reward purposes.
- Separately, make the fee-collector mint path resilient: don't let fee minting revert the user operation (e.g., accrue fees to a per-token balance instead of minting deposit tokens to the collector).

### Proof of Concept
Hardhat test outline (fork or fixture with ≥1 registered `DepositToken`):

```solidity
// Assume pool has D registered DepositTokens: dt[0..D-1]
// 1. Attacker deposits dust of each dt[i] on behalf of victim (or transfers).
for (uint i; i < D; ++i) {
    underlying[i].approve(address(dt[i]), dust);
    dt[i].deposit(dust, victim);            // _mint -> addToDepositTokensOfAccount(victim)
}
// 2. Victim already holds K tokens such that D + K >= MAX_TOKENS_PER_USER (30).
//    (Or D >= 30 alone, depending on registered collaterals.)

// 3a. Victim cannot deposit a new collateral type:
vm.expectRevert(UserReachedMaxTokens.selector);
dtNew.deposit(amount, victim);              // reverts in _mint -> addToDepositTokensOfAccount

// 3b. Victim cannot borrow a synthetic whose DebtToken isn't in their list:
vm.expectRevert(UserReachedMaxTokens.selector);
debtTokenNew.issue(amount, victim);         // reverts in addToDebtTokensOfAccount

// 3c. If victim's position is unhealthy (issuable == 0, debt > 0):
assertEq(dtDust.unlockedBalanceOf(victim), 0);   // cannot shed dust -> slot permanently occupied
// -> victim cannot add collateral -> position gets liquidated.

// 4. Pool-wide variant: set victim = pool.feeCollector(); every deposit/withdraw
//    that mints a NEW fee token to the collector reverts while depositFee > 0.
```

Expected result: steps 3a/3b revert with `UserReachedMaxTokens`, reproducing a repeatable, attacker-triggered denial of service; on a mainnet/Base fork this is exercised against the deployed `Pool` and its registered deposit tokens.
