### Title
Relayer tip payments can be silently lost with no tracking/refund when `AddTip::add_tip` races the `PendingOrders` removal in Snowbridge outbound queue v2 - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

### Summary
This is a structural analog of the TokenSender bug: a value transfer (relayer tip) is accepted/charged from a user off-chain of the storage that ultimately pays it out, but the underlying `PendingOrder` used to accrue that payout can be removed by a normal, unprivileged flow (`submit_delivery_receipt`) *before* the tip is applied. When that happens, `AddTip::add_tip` fails with `AddTipError::UnknownMessage`, the tip amount is not recorded anywhere, and — just like the TokenSender case — there is no mapping or later-claim mechanism for the user whose tip could not be applied.

### Finding Description
`PendingOrders` stores the fee/reward owed for an outbound message keyed by `nonce`, created in `do_process_message` and removed once a relayer submits a valid delivery receipt via `submit_delivery_receipt` → `process_delivery_receipt`: [1](#0-0) 

`AddTip::add_tip` is the only path for topping-up an existing order's fee; it explicitly returns `AddTipError::UnknownMessage` if the corresponding `PendingOrder` no longer exists: [2](#0-1) 

`do_process_message` itself documents that it does **not** roll back storage on error, underscoring that this pallet's storage transitions (order creation/removal) are treated as final, one-shot state changes with no compensating path: [3](#0-2) 

The race: any unprivileged relayer can call `submit_delivery_receipt` for a message nonce as soon as the corresponding Ethereum delivery proof exists. If a user (via `system-frontend`/XCM) submits a tip top-up for that same nonce in the same or an adjacent block, the tip call can arrive *after* the relayer's receipt has already removed the `PendingOrder`. `add_tip` then fails with `UnknownMessage`. Unlike `pallet_bridge_relayers::RelayerRewards` (a proper claim ledger with `RewardRegistered`/`RewardPaid` events and a `claim_rewards` extrinsic — see `bridges/modules/relayers/src/lib.rs:399-432`), there is no equivalent fallback storage for a tip that arrives "too late": the amount the caller intended to pay/commit is neither applied to a reward nor refunded nor tracked for manual resolution.

This is the same bug class already acknowledged and partially fixed in this exact code family: `prdoc/stable2509/pr_9746.prdoc` documents "Snowbridge Inbound Queue V2 relayer tip payout fix... Fixes a bug where relayer tips were not properly paid out, causing the tips to be lost since it had already been burnt," which was fixed only for `snowbridge-pallet-inbound-queue-v2`: [4](#0-3) 

The outbound-queue-v2's `AddTip` implementation retains the same unguarded `Option`-based lookup-and-fail pattern that caused that prior bug, but for the *outbound* delivery-receipt/tip race instead of the inbound tip/process-message race.

### Impact Explanation
A user's tip funds (charged/reserved via the calling `system-frontend`/`system-v2` extrinsic before invoking `add_tip`) can be irrecoverably lost from the relayer-incentive accounting: the tip is neither applied to `PendingOrders` (removed already) nor captured by `pallet-bridge-relayers`' `RelayerRewards` claim ledger. This matches the report's core invariant break — "payment attempted, payee not made whole, no tracking or later-claim path" — applied to Snowbridge's public tip/reward flow rather than TokenSender. Impact is bounded to fee/tip amounts (not principal bridged assets), but funds are lost with no on-chain recourse for the affected user, and centralization/manual-intervention risk is reintroduced exactly as flagged in the source report.

### Likelihood Explanation
Medium. The race requires only two independent, permissionless actions racing on ordering: a relayer's `submit_delivery_receipt` and a user's tip top-up for the same nonce, both of which are normal, expected usage patterns (the very purpose of `add_tip` is to top up tips for *slow-to-process* messages, meaning tip-adders are naturally more likely to interact with orders near their resolution window). No malicious actor, governance, or privileged role is required — any relayer processing a legitimate delivery receipt at the "wrong" time triggers the loss for any user who tipped concurrently.

### Recommendation
Mirror the `pallet-bridge-relayers` reward-ledger design already used elsewhere in this codebase: when `add_tip` fails because the order no longer exists, do not simply return an error that discards the amount. Instead:
- Track "orphaned" tips (nonce → amount) in dedicated storage, or
- Have callers of `add_tip` (system-frontend/system-v2) treat `AddTipError::UnknownMessage` as "already delivered — route the tip amount directly to `RewardPayment::register_reward` for a resolvable relayer/claimer" instead of discarding it, similar to the fix already applied for `snowbridge-pallet-inbound-queue-v2` in pr_9746.

### Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrders::<T>::insert(nonce, order)` with some `fee`.
2. A relayer submits a valid Ethereum event log/proof via `submit_delivery_receipt(origin, event)` for that `nonce`; `process_delivery_receipt` runs, pays out `order.fee` via `RewardPayment::register_reward`, and calls `PendingOrders::<T>::remove(nonce)`.
3. Concurrently (same or next block), a user's tip transaction for the same `nonce` — which already charged/reserved the tip amount on the calling side — invokes `AddTip::add_tip(nonce, amount)`.
4. `PendingOrders::<T>::try_mutate_exists(nonce, ...)` finds `None` and returns `Err(AddTipError::UnknownMessage)` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:486-494`).
5. The already-collected tip `amount` is not applied to any reward, not stored anywhere, and not refunded — permanently lost, with no claim mechanism analogous to `pallet-bridge-relayers::RelayerRewards`.

	impl<T: Config> AddTip for Pallet<T> {
		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			PendingOrders::<T>::try_mutate_exists(nonce, |maybe_order| -> Result<(), AddTipError> {
				match maybe_order {
					Some(order) => {
						order.fee = order.fee.saturating_add(amount);
						Ok(())
					},
					None => Err(AddTipError::UnknownMessage),
				}
			})
