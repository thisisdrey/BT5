### Title
StackerDB Chunk Signature Omits Contract/Lane Binding — Cross-Contract Replay of Validly-Signed Signer Chunks - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest for a StackerDB chunk from only `(slot_id, slot_version, data_hash)` — it never binds the signature to the StackerDB smart-contract identity (or network id). Because multiple `.signers-<set>-<message_id>` StackerDB contracts for the same signer set share an *identical* slot→signer assignment (they all read from the same `stackerdb-get-signer-slots-page`), a validly-signed chunk broadcast by a signer for one contract (e.g. the `BlockResponse` lane) can be replayed verbatim into a different sibling contract (e.g. `StateMachineUpdate`/`BlockPreCommit` lane) that has an independent, lower version counter for the same `slot_id`. This is directly analogous to the reported EIP-4337 chainId-omission bug: an authentication digest that fails to bind a signature to its intended execution/storage context, enabling replay across contexts that share the same signer key.

### Finding Description
The signed digest is: [1](#0-0) 

It hashes only `slot_id`, `slot_version`, and `data_hash` — no `smart_contract_id`, no `message_id`/lane, no chain/network identifier.

The write-acceptance path (`StackerDBTx::try_replace_chunk`) verifies the signature only against the *slot owner recorded for this specific contract*, and checks version freshness/`max_writes`, but nothing ties the signed bytes to that contract: [2](#0-1) 

The same lack of contract binding exists in the p2p-facing acceptance check used for both scheduled downloads and unsolicited pushes: [3](#0-2) 

Critically, the slot-to-signer assignment is *shared* across all message-id lanes of a signer set. `.signers` maintains one shared list per signer-set page, and each `.signers-<set>-<message_id>` contract simply proxies to that same page: [4](#0-3) [5](#0-4) 

Each of these contracts is registered as its own independent StackerDB with its own persistent per-`(stackerdb_id, slot_id)` version counter (`databases`/`chunks` schema, keyed by `smart_contract_id`): [6](#0-5) 

Consequently, signer address `S` occupies the *same* `slot_id` in `signers-1-1`, `signers-1-2`, and `signers-1-3` simultaneously. A chunk `(slot_id=k, slot_version=v, sig, data)` that `S` validly signs and pushes to `signers-1-1` is signature-valid, and equally acceptable as-is by `try_replace_chunk`/`validate_received_chunk` for `signers-1-2` or `signers-1-3`, as long as that sibling contract's independently-tracked version for slot `k` is still `< v`. Nothing in the signed bytes, nor in the storage/verification code, rejects this cross-contract replay. `StackerDBChunkData::verify`/`recover_pk` reuse the same `auth_digest`, so the wrong-contract chunk passes `slot_desc.verify(&slot_validation.signer)` unconditionally: [7](#0-6) 

I was unable to fully verify from the index whether a downstream payload-type filter in `libsigner/src/events.rs` (`signer_message_payload_matches_lane`, referenced but whose body I could not retrieve) would neutralize the *interpretation* of a replayed chunk for the miner-facing `SignerEvent` construction. However, that filter — if present — only affects one consumer's read-side interpretation; it does not prevent the underlying StackerDB write/storage/gossip acceptance shown above, which is the actual authentication boundary being broken.

### Impact Explanation
This breaks the "signed for contract A" vs. "stored/gossiped as contract B" equality: an unprivileged party who observes (via normal StackerDB replication, which is inherently public/unauthenticated to read) a validly-signed chunk broadcast for one signer-message lane can inject it, unmodified, into a sibling lane's StackerDB replica on any node, causing that node to accept and further gossip it as legitimate content it never was for that contract. This is an unauthorized write into StackerDB state, and per the report's own severity criteria, unauthenticated/unauthorized write to state and network-wide propagation of forged (out-of-context) data qualify as **Critical**. Whether the immediate downstream consumer discards the wrong-typed payload is orthogonal to the fact that the StackerDB layer itself accepted and propagated data outside its authenticated scope, and the digest is used generically by all `StackerDBChunkData` consumers, not just signer messages — any future or existing use of multiple StackerDB contracts sharing a signer/slot mapping is equally exposed.

### Likelihood Explanation
Likelihood is high: it requires no privileged access, no consensus/signer-decision compromise, and no cryptographic break — only observing one legitimately-signed, publicly-gossiped StackerDB chunk and resubmitting its exact bytes to a different (but slot-compatible) contract endpoint via the ordinary `POST /v2/stackerdb/{contract}/chunks` RPC or the p2p `StackerDBPushChunk` message. The precondition (identical slot ordering across `signers-<set>-*` contracts) is guaranteed by the current `.signers` contract design, not an edge case.

### Recommendation
Include the target `smart_contract_id` (and ideally a network/chain identifier) inside `SlotMetadata::auth_digest()`, e.g. hash `smart_contract_id.to_string()` (or its serialized `QualifiedContractIdentifier`) alongside `slot_id`, `slot_version`, and `data_hash`. This requires threading the contract identifier into `SlotMetadata::sign`/`verify`/`auth_digest` and `StackerDBChunkData::sign`/`verify`/`recover_pk`, and updating all callers (`try_replace_chunk`, `validate_received_chunk`, `handle_unsolicited_StackerDBPushChunk`, and the signer-side `StackerDB::send_message_*`) to supply/check it. Existing on-disk/gossip formats and clients would need a coordinated version bump since this changes the signed payload.

### Proof of Concept
1. Attacker (or any observing peer) captures a `StackerDBPushChunkData` a signer `S` legitimately signed and pushed to contract `signers-1-1` (BlockResponse lane): `{slot_id: k, slot_version: v, sig, data}` where `sig` recovers to `S` via `auth_digest()` = `H(k || v || sha512_256(data))`.
2. Because `signers-1-1`, `signers-1-2`, `signers-1-3` for the same signer set all expose identical `stackerdb-get-signer-slots-page` output (`stackslib/src/chainstate/stacks/boot/signers.clar:39-43`), `S` also owns `slot_id = k` in `signers-1-2`. That contract's independent `chunks` row for `(stackerdb_id_2, k)` is at some `version < v` (e.g. `0`, since `S` hasn't yet written there).
3. Attacker crafts a new `StackerDBPushChunkData { contract_id: signers-1-2, chunk_data: { slot_id: k, slot_version: v, sig, data } }` (byte-for-byte reuse of the captured `sig`/`data`) and sends it as an unsolicited push, or POSTs it to `/v2/stackerdb/<signers-1-2>/chunks`.
4. `validate_received_chunk`/`try_replace_chunk` recompute `auth_digest()` from `(k, v, data_hash)` — identical to what `S` signed originally — recover the same pubkey, confirm it matches the recorded owner of slot `k` in `signers-1-2`, confirm `v` is newer than the target's stored version, and accept/store the chunk (`stackslib/src/net/stackerdb/mod.rs:679-717`, `stackslib/src/net/stackerdb/db.rs:411-437`).
5. The node now stores and gossips this chunk as authentic `signers-1-2` content, even though `S` never signed anything intended for that contract/lane.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )

        let pubkh = Hash160::from_node_public_key(&pubk);

/// Helper methods for StackerDBChunkData messages
impl StackerDBChunkData {
    /// Create a new StackerDBChunkData instance.
    pub fn new(slot_id: u32, slot_version: u32, data: Vec<u8>) -> StackerDBChunkData {
        StackerDBChunkData {
            slot_id,
            slot_version,
            sig: MessageSignature::empty(),
            data,
        }
    }

    /// Calculate the hash of the chunk bytes.  This is the SHA512/256 hash of the data.
    pub fn data_hash(&self) -> Sha512Trunc256Sum {
        Sha512Trunc256Sum::from_data(&self.data)
    }

    /// Create an owned SlotMetadata describing the metadata of this slot.
    pub fn get_slot_metadata(&self) -> SlotMetadata {
        SlotMetadata {
            slot_id: self.slot_id,
            slot_version: self.slot_version,
            data_hash: self.data_hash(),
            signature: self.sig.clone(),
        }
    }

    /// Sign this given chunk data message with the given private key.
    /// Sets self.signature to the signature.
    /// Fails if the underlying signing library fails.
    pub fn sign(&mut self, privk: &StacksPrivateKey) -> Result<(), Error> {
        let mut md = self.get_slot_metadata();
        md.sign(privk)?;
        self.sig = md.signature;
        Ok(())
    }

    pub fn recover_pk(&self) -> Result<StacksPublicKey, Error> {
        let digest = self.get_slot_metadata().auth_digest();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(digest.as_bytes(), &self.sig)
            .map_err(|ve| Error::VerifyingError(ve.to_string()))
    }

    /// Verify that this chunk was signed by the given
    /// public key hash (`addr`).  Only fails if the underlying signing library fails.
    pub fn verify(&self, addr: &StacksAddress) -> Result<bool, Error> {
        let md = self.get_slot_metadata();
        md.verify(addr)
    }
}
