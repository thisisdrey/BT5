### Title
Same-height AddKey re-creation after DeleteKey resets the nonce checkpoint below previously-consumed nonces, enabling replay of already-executed transactions - ([File: runtime/runtime/src/access_keys.rs], [File: runtime/runtime/src/verifier.rs])

### Summary
`initial_nonce_value` reseeds a recreated access key's nonce purely from the current `block_height`, with no memory of the nonce actually reached by the deleted key. Combined with the `NonceMode::Monotonic` check `tx_nonce <= current_nonce` in `verify_nonce`, an attacker who deletes and immediately (same block height) re-adds their own access key can replay previously broadcast/executed transactions signed with that key whose nonce falls in `(new_seed, old_max]`.

### Finding Description
`initial_nonce_value(block_height) = (block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` is used both when a key is first created and whenever it is re-added via `add_regular_key`/`add_gas_key`: [1](#0-0) [2](#0-1) 

`action_delete_key`/`delete_regular_key` fully removes the access key trie row via `remove_access_key`, discarding the last-consumed nonce value entirely — no ledger of previously used nonces survives deletion: [3](#0-2) 

`verify_nonce`'s Monotonic branch only compares against the *currently stored* `current_nonce` (which after re-creation equals `initial_nonce_value(new_height)`), and independently bounds nonces by `block_height * MULTIPLIER` at time of signing/inclusion, not by the key's creation height: [4](#0-3) 

After successful verification, the access key's `nonce` field is simply set to `tx_nonce`: [5](#0-4) 

Exact reachable band:
- **Same-height recreation** (DeleteKey followed by AddKey of the identical public key within the same block height `H` as the key's last use): `new_seed = (H-1)*M == old_seed`. Since every nonce the key ever validly consumed satisfies `tx_nonce > old_seed` (that was required to pass Monotonic originally), *all* of the attacker's previously executed transactions on that key (up to `old_max`, the highest consumed nonce) again satisfy `tx_nonce > new_seed` and are replayable — not just a partial subrange, but the full historical set.
- **Cross-height recreation** (`H_new > H_last_used`, where `H_last_used` is the height at which the highest-nonce transaction was actually applied): the `NonceTooLarge` bound guarantees `old_max < H_last_used * M`. If `H_new >= H_last_used + 1`, then `new_seed = (H_new-1)*M >= H_last_used*M > old_max`, which closes the gap completely — no previously-consumed nonce is replayable.
- Therefore the replayable band is exactly `(new_seed, old_max]` whenever `H_new <= H_last_used`, and empty whenever `H_new > H_last_used`.

Nothing else in the transaction-validation path (signature check, access-key permission check, action validation, gas metering) detects that `tx_nonce` was already consumed by a deleted-and-recreated key, because the runtime's sole replay defense is the per-access-key `nonce` counter, which this delete/recreate cycle resets.

### Impact Explanation
This breaks the "each signed transaction executes at most once" invariant (double-spend/replay category). An account owner (or anyone who controls a full-access key on that account) can, using only ordinary, unprivileged actions (`DeleteKey` + `AddKey` with the same public key, both self-authorized), cause a previously executed and finalized transaction (e.g., a `Transfer` or `FunctionCall`) signed under that key to become valid again and re-execute, provided the recreation happens at the same block height as (or an earlier-bounded height relative to) the original usage. Any protocol- or application-level logic that treats a transaction's nonce as a durable, never-reusable identifier for idempotency is defeated.

### Likelihood Explanation
Preconditions are fully attacker-controlled and cheap: the attacker needs a funded account with a full-access key able to submit `DeleteKey`/`AddKey` actions on the target key, and must arrange for the delete+recreate to land in the same block height as (or before the height following) the transaction(s) to be replayed — achievable by batching actions in one transaction or coordinating submissions within a single chunk. No validator, RPC-operator, or network-layer privilege is required, matching the allowed attacker model. The exploit is deterministic and repeatable for every recreation cycle.

### Recommendation
Do not reseed a recreated key's nonce purely from `block_height`. Either (a) persist the maximum nonce ever consumed by a given public key on the account (e.g., in a tombstone/removed-keys index) and take the max of that and `initial_nonce_value(block_height)` when re-adding the key, or (b) forbid `AddKey` from reusing a public key that was deleted within the current or a recent block/height window unless the new seed is proven to exceed the historical maximum.

### Proof of Concept
Unit test in `runtime/runtime/src/verifier.rs` (or an integration/test-loop test):
1. At height `H`, add a full-access key with `AddKeyAction`; sign and apply tx `T1` with nonce `N1 = initial_nonce_value(H) + 1`; assert success and that the stored `access_key.nonce == N1`.
2. At the same height `H`, submit `DeleteKeyAction` followed by `AddKeyAction` for the same public key.
3. Attempt to re-apply `T1` (same nonce `N1`, same signed bytes) — assert `verify_nonce`/`verify_and_charge_tx_ephemeral` returns `TxVerdict::Success` (i.e., no `InvalidNonce` error), demonstrating replay.
4. Repeat step 2 but at height `H+1` (or higher) instead of `H`; re-attempt `T1` and assert it is now rejected with `InvalidTxError::InvalidNonce`, confirming the cross-height case closes the gap.
5. Parametrize `tx_nonce` over `[new_seed, old_max]` to confirm the accept/reject boundary matches `(new_seed, old_max]` for same-height recreation and the empty set for post-height recreation.

```rust
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
```
