## Analog Found

### Title
Exchange withdraw lacks slippage protection allowing sandwich extraction of pool funds - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator` computes the amount of the paired token to return based on the exchange pool's *current* balance ratio at execution time, with no way for the caller to specify a minimum acceptable output. This is the same bug class as the GMX report: a token conversion/settlement derived from a pool's live ratio is executed with zero slippage tolerance, so it can be sandwiched to extract value.

### Finding Description
`ExchangeTransactionContract` (the "swap" contract) explicitly carries an `expected` field used as a slippage bound: [1](#0-0) . `ExchangeTransactionActuator.doValidate()` enforces this bound by rejecting the transaction if the computed output is below `tokenExpected`: [2](#0-1) .

`ExchangeWithdrawContract`, however, has no equivalent field: [3](#0-2) . In `ExchangeWithdrawActuator.execute()`, the paired-token amount (`anotherTokenQuant`) returned to the caller is computed purely from the exchange's `firstTokenBalance`/`secondTokenBalance` ratio at the moment of execution, with no floor check against caller expectations: [4](#0-3) . The only validation performed elsewhere (`doValidate`) is a "not precise enough" rounding-drift check, not a user-supplied minimum: [5](#0-4) .

Because the exchange pool ratio can be moved by anyone via `ExchangeTransactionActuator` (an unprivileged, permissionless "order placer" action) in a preceding transaction within the same block/interval, an attacker can front-run a pending `ExchangeWithdrawContract` transaction with a large trade that skews the ratio, let the withdrawal execute at the skewed ratio, then back-run to restore the ratio — a classic sandwich attack extracting value from the withdrawer.

### Impact Explanation
The withdrawer (the exchange's creator, who is the only account authorized to withdraw per `doValidate`'s creator check) receives a paired-token amount computed at an attacker-manipulated ratio instead of the fair market ratio, resulting in concrete loss of funds transferred out of the pool to the sandwiching attacker. This is a direct value-extraction / theft-of-funds impact via an on-chain, permissionless mechanism (repeated `ExchangeTransactionContract` calls), matching the "unauthorized... theft... of funds" acceptance criteria.

### Likelihood Explanation
Any unprivileged account can submit `ExchangeTransactionContract` transactions to move the pool ratio, and can observe pending `ExchangeWithdrawContract` transactions in the transaction pool before they are included in a block, making the sandwich straightforward to execute for any liquidity pool with sufficient trade volume/size asymmetry.

### Recommendation
Add an `expected`/minimum-output field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`) and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()`, rejecting withdrawals whose computed `anotherTokenQuant` falls below the caller-specified minimum.

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` transaction from the exchange creator for `exchangeId` withdrawing `tokenQuant` of `firstTokenID`.
2. Attacker submits an `ExchangeTransactionContract` swap that sells a large amount of `secondTokenID` into the pool immediately before the withdrawal is applied, skewing `firstTokenBalance`/`secondTokenBalance` (see ratio math in `ExchangeWithdrawActuator.execute()`, lines 77-89).
3. The pending withdrawal executes, computing `anotherTokenQuant` at the skewed ratio, returning less value to the creator than the pre-manipulation ratio would have.
4. Attacker submits a second `ExchangeTransactionContract` swap reversing the initial trade, restoring the ratio and capturing the value taken from the withdrawer, minus fees.
