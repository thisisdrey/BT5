### Title
Unbounded `addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight` in `RepositoryImpl` (TVM native-contract path) can drive global resource weight counters negative, corrupting network-wide bandwidth/energy accounting — (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
The `repayDebt` finding is a class of bug where a global aggregate counter (`totalDebt`) is decremented by an unbounded/attacker-influenced amount without a floor check, while individual accounting entries are managed separately — eventually causing the aggregate to underflow and permanently DOS the accounting logic. The same structural pattern exists in java-tron between the two implementations of the TRON Power/Bandwidth/Energy weight counters: the actuator-facing `DynamicPropertiesStore` clamps the result at zero, but the TVM native-contract-facing `RepositoryImpl` (reachable from any Solidity contract call via `freezeBalanceV2`/`unfreezeBalanceV2`/`cancelAllUnfreezeV2` precompiles) does not.

### Finding Description
`DynamicPropertiesStore.addTotalNetWeight/addTotalEnergyWeight/addTotalTronPowerWeight` explicitly floors the result at zero whenever the `allowNewReward` hard fork is active: [1](#0-0) [2](#0-1) 

However, `RepositoryImpl` — the storage abstraction used exclusively by TVM native contracts (i.e. code reachable from a user-deployed smart contract calling the freeze/unfreeze/delegate precompiles) — implements the identical-named methods with **no clamping at all**: [3](#0-2) 

These unguarded `RepositoryImpl` methods are invoked directly by the native-contract processors that back TVM opcodes for freezing/unfreezing/delegating TRX for bandwidth, energy and TRON Power — e.g. `FreezeBalanceV2Processor.execute`, `UnfreezeBalanceV2Processor.updateTotalResourceWeight`, `UnfreezeBalanceProcessor.execute`, and `CancelAllUnfreezeV2Processor.updateFrozenInfoAndTotalResourceWeight`: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

Notably, `UnfreezeBalanceProcessor.java` contains an inline comment "`// adjust total resource, used to be a bug here`" right above the unguarded call, indicating this exact class of accounting bug (global counter drifting incorrectly relative to per-account state) has previously manifested in this code area, yet the fix that was applied to the non-VM `DynamicPropertiesStore` path (the zero-floor clamp) was never mirrored into the `RepositoryImpl` path used by TVM contracts. [8](#0-7) 

Just as `Vault.repayDebt()` allowed `totalDebt` to be decremented independently of consistent per-borrower bookkeeping (any caller repaying any borrower's debt), the `RepositoryImpl` total-weight counters are decremented on a per-account, per-call basis using floating-point-derived deltas (`(double) unDelegateBalance / ... `, `/ TRX_PRECISION` integer division producing rounding, and cache read/re-read races across multiple internal calls within a single contract execution). Any accumulation of rounding error or a code path that computes a decrease larger than what was actually contributed to the total (e.g. via the `receiverCapsule.getAcquiredDelegatedFrozenV2BalanceForBandwidth() < unDelegateBalance` "suicide/re-create" fallback branches seen in `UnDelegateResourceProcessor.execute`, which reset acquired balances to `0` regardless of the true delegated amount) can push `totalNetWeight`/`totalEnergyWeight`/`totalTronPowerWeight` below the true sum of live frozen balances, and — because `RepositoryImpl` has no floor — below zero, since it is never re-clamped by `DynamicPropertiesStore`'s guard code once the VM commits its dirty dynamic-properties cache. [9](#0-8) 

### Impact Explanation
`totalNetWeight`/`totalEnergyWeight`/`totalTronPowerWeight` are the global denominators used across the network to compute every account's bandwidth/energy allotment from `totalNetLimit`/`totalEnergyCurrentLimit` (seen used, e.g., in `unDelegateMaxUsage = ... * dynamicStore.getTotalNetLimit() / repo.getTotalNetWeight()`). If these globals become negative or erroneously small/large due to unguarded arithmetic reachable purely through TVM contract execution (any user can deploy and call a contract that freezes/unfreezes/delegates resources), the derived per-account bandwidth/energy limits for the **entire network** become corrupted — potentially granting unlimited or zero free bandwidth/energy to accounts network-wide, effectively DOSing normal resource-based transaction processing or letting attackers bypass energy/bandwidth metering entirely (a form of unbacked resource issuance analogous to unbacked balance).

### Likelihood Explanation
This requires no privileged access — any unprivileged account can deploy a smart contract and call the built-in freeze/unfreeze/delegate/undelegate precompiles supported by `VMConfig.allowTvmFreezeV2`/`allowTvmVote`, which is the exact "asset issuer/contract deployer/order placer" class of actor this scan targets. However, I was not able to fully trace, within the remaining tool budget, a concrete step-by-step transaction sequence that forces the global counter to a negative value in the current head of this branch (i.e., I could not exhaustively rule out that the underlying deltas are always internally consistent). The asymmetry between the two `addTotalXWeight` implementations (clamped vs. unclamped) is concretely confirmed, but a full proof-of-concept sequence producing an actual underflow was not completed due to the investigation cutoff.

### Recommendation
Mirror the zero-floor clamp from `DynamicPropertiesStore.addTotalNetWeight/addTotalEnergyWeight/addTotalTronPowerWeight` into `RepositoryImpl`'s equivalent methods (`actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java:1196-1217`), so that TVM-triggered decrements can never push the global weight counters below zero, consistent with the non-VM actuator path. Additionally, audit all `UnDelegateResourceProcessor`/`UnfreezeBalanceV2Processor` fallback branches that reset acquired/delegated balances to `0` on mismatch (the "contract suicide/re-create" cases) to ensure the corresponding total-weight adjustment reflects the actual amount removed rather than the full requested `unDelegateBalance`/`unfreezeBalance`.

### Proof of Concept
Not independently reproduced within the available investigation window; the finding is based on static comparison of the clamped (`DynamicPropertiesStore`) vs. unclamped (`RepositoryImpl`) implementations of the same three counter-update methods, both of which are exercised by TVM-reachable native contract processors (`FreezeBalanceV2Processor`, `UnfreezeBalanceV2Processor`, `UnfreezeBalanceProcessor`, `CancelAllUnfreezeV2Processor`, `UnDelegateResourceProcessor`) as cited above. A full working exploit transaction sequence would need to be constructed and validated against the live contract/VM test harness (e.g. extending `framework/src/test/java/org/tron/common/runtime/vm/FreezeV2Test.java`) to confirm actual underflow is achievable in practice.
