### Title
`debtFloorInUsd` combined with `maxLiquidable` permanently blocks liquidation of mid-sized underwater positions, trapping bad debt - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` enforces two bounds on the repay amount: `amountToRepay_` cannot exceed `maxLiquidable` (default 50%) of the account's total debt, and the remaining debt after repayment must be either zero or at least `debtFloorInUsd`. For any position whose debt value lies in the window `(debtFloorInUsd, 2 * debtFloorInUsd)`, no valid `amountToRepay_` exists: repaying enough to satisfy the floor requires repaying the whole debt, which exceeds the 50% cap, while any repay within the cap leaves a remainder between 0 and the floor and reverts with `RemainingDebtIsLowerThanTheFloor`. The liquidation transaction "crashes" for every liquidator input, exactly mirroring the DoS class of ALPINE-CVE-2017-3302.

### Finding Description
In `Pool.liquidate` at `contracts/Pool.sol:567`, the cap check is `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` → revert. At `contracts/Pool.sol:571-578`, if `debtFloorInUsd > 0`, the post-repayment debt value `_newDebtInUsd` must be `0` or `>= debtFloorInUsd`. With `maxLiquidable = 0.5e18`, a liquidator can repay at most half the debt, so a full repay (`_newDebtInUsd == 0`) is unreachable. For a position with debt `D` where `debtFloorInUsd < D < 2 * debtFloorInUsd` (in USD terms), every allowed `amountToRepay_ <= 0.5 * D` produces `0 < _newDebtInUsd < debtFloorInUsd` and reverts. An unprivileged attacker can deliberately mint a synthetic position sized into this window (using only public `DebtToken.issue`/`SmartFarmingManager.leverage` entry points), let it drift unhealthy via normal price movement or same-transaction oracle-priced swaps, and it becomes permanently unliquidatable.

### Impact Explanation
The unhealthy position cannot be liquidated by anyone, ever, while the debt keeps accruing interest via `DebtToken.accrueInterest`. As collateral value continues to fall relative to the debt, the account becomes deeply insolvent and the protocol is forced to absorb the shortfall (bad debt socializes across depositors / synthetic holders). This is protocol insolvency plus a permanent freeze of the liquidation path — both accepted impacts. `quoteLiquidateMax` (`contracts/Pool.sol:419-440`) does not rescue this: it returns the same capped repay amount that `liquidate` then rejects.

### Likelihood Explanation
Requires `debtFloorInUsd > 0` on the deployed configuration (it is a governor-set parameter exposed in deployed `Pool.json` ABIs across mainnet, base, optimism, hemi, swell) and a debt position in the affected window — precisely the small-to-mid-size positions the floor is meant to deter, so the deadlock hits exactly the population it targets. Any EOA can create such a position permissionlessly; no privileged role, malicious oracle, or external dependency is needed. Likelihood is high whenever the floor is nonzero, since attackers can mass-open in-window positions cheaply.

### Recommendation
Apply the floor check only to the pre-liquidation debt, or exempt full / capped liquidations: e.g., allow the repay that brings `_newDebtInUsd` below the floor when `amountToRepay_` already equals the maximum permitted (`min(maxLiquidable * debt, amount needed to zero out)`), or treat `amountToRepay_ == _debtTokenBalance` as always allowed regardless of `maxLiquidable`. Alternatively, clamp the max liquidable amount upward so a repay can always reach either zero remainder or `>= debtFloorInUsd` remainder.

### Proof of Concept
Reproducible on a Hardhat/Foundry fork of any deployed pool with `debtFloorInUsd > 0` (e.g., mainnet `Pool`):
1. Attacker deposits collateral and calls `DebtToken.issue` to mint `msUSD` so total debt `D` satisfies `debtFloorInUsd < D < 2 * debtFloorInUsd` (e.g., floor $100 → mint ~$150).
2. Move the position unhealthy (collateral price drop on fork via oracle price update, or swap-driven).
3. Liquidator calls `pool.liquidate(msUSD, attacker, amountToRepay, msUsdDepositToken)`:
   - `amountToRepay = D` → reverts `AmountGreaterThanMaxLiquidable` (D > 0.5·D).
   - `amountToRepay = 0.5·D` → `_newDebtInUsd ≈ $75`, which is `> 0 && < $100` → reverts `RemainingDebtIsLowerThanTheFloor`.
4. Any `amountToRepay` in between reverts on one of the two checks. Assert `vm.expectRevert` for all inputs across the domain; debt remains unliquidatable and grows via `accrueInterest`.

Uncertainty: whether `debtFloorInUsd` is currently nonzero on each deployed pool was not confirmable from the indexed artifacts (no deploy script setting it was found); the mechanism holds whenever it is set, which is the configuration the parameter exists for.
