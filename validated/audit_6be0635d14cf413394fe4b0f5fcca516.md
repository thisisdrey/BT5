### Title
Reliance on a Java `assert` instead of an explicit check allows `calculateGlobalEnergyLimit` to divide by an unvalidated `totalEnergyWeight`, yielding an unbacked energy allowance - (File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java)

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit` computes an account's usable energy limit from `totalEnergyWeight`, but the only guard against a zero/invalid `totalEnergyWeight` when `allowNewReward()` is disabled is a Java `assert` statement, which is a no-op in production (JVM assertions are disabled by default, i.e. no `-ea` flag). This mirrors the reported Flatcoin issue: a rate/limit-computing function consumes several stored inputs without validating them, relying on an assumption instead of an enforced check.

### Finding Description
In `calculateGlobalEnergyLimit`: [1](#0-0) 

```java
long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
  return 0;
} else {
  assert totalEnergyWeight > 0;
}
...
long energyWeight = frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```

The explicit `if` check for `totalEnergyWeight <= 0` is only executed when `allowNewReward()` returns `true`. When `allowNewReward()` is `false`, the code path falls to `assert totalEnergyWeight > 0;`. Java assertions are stripped/ignored at runtime unless the JVM is started with `-ea`; production nodes do not enable this flag, so the assertion performs no validation whatsoever, exactly the class of bug flagged in the report ("no check to ensure that the input arguments are valid").

If `totalEnergyWeight` is `0` (e.g., early-chain state, a private/test network, or any configuration where the legacy reward path is still active), the final expression divides `totalEnergyLimit` by `0` as a `double`. Java double division by zero does not throw — it yields `Infinity` (or `NaN` if `totalEnergyLimit` is also `0`). Casting `Infinity` to `long` in Java produces `Long.MAX_VALUE`.

### Impact Explanation
An account whose calculated `energyLimit` becomes `Long.MAX_VALUE` bypasses the resource-accounting model entirely: `useEnergy` compares `energy > (energyLimit - newEnergyUsage)` before charging energy consumption. [2](#0-1) 
With an effectively infinite `energyLimit`, this check never blocks execution, letting the caller invoke smart contracts and consume energy without having frozen/staked the corresponding TRX ("unbacked" resource — analogous to an unbacked balance). This can be used to execute unlimited contract calls for free, which stresses node CPU/storage resources without the economic backing the resource model is designed to enforce, a resource-exhaustion/DoS-class impact on the node.

### Likelihood Explanation
The vulnerable branch is only reached when `dynamicPropertiesStore.allowNewReward()` is `false` and `totalEnergyWeight` is `0`. On a live mainnet where the "new reward" hard fork has long been activated, this is unlikely to trigger. However, it remains a genuine unenforced invariant in the code (identical bug class to the audited report) and is directly reachable by any ordinary transaction/contract call through `useEnergy` on any network state or configuration where `allowNewReward()` is disabled or not yet activated (e.g., private chains, sidechains, or early-genesis states that reuse this code path).

### Recommendation
Replace the `assert totalEnergyWeight > 0;` with an explicit runtime check (e.g., `if (totalEnergyWeight <= 0) { return 0; }`) so the safety guarantee does not depend on JVM assertion flags, matching the pattern the report recommends: add explicit validation for all inputs feeding a rate/limit computation before performing division.

### Proof of Concept
1. Configure/observe a node state where `allowNewReward()` returns `false` (legacy reward path) and `totalEnergyWeight == 0` (no accounts have frozen balance for energy under the legacy accounting, or a fresh/private network state).
2. Any account calls `useEnergy` while invoking a smart contract via a normal `TriggerSmartContract` transaction with `frozeBalance >= TRX_PRECISION`.
3. `calculateGlobalEnergyLimit` executes the `assert` branch (no-op in production), then computes `energyWeight * (totalEnergyLimit / 0.0)` → `Infinity`, cast to `Long.MAX_VALUE`.
4. `useEnergy`'s check `energy > (energyLimit - newEnergyUsage)` is always false, so energy is granted without limit, and the account can consume arbitrary energy for free. [3](#0-2)

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
