### Title
Dust transfers fill a victim's per-account token list, DoSing their deposits — unvalidated recipient bookkeeping (`contracts/Pool.sol`)

### Summary
`Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER` on the *recipient's* `depositTokensOfAccount`/`debtTokensOfAccount` mapped list whenever a `DepositToken` balance goes from 0 to non-zero. The recipient never opted in: `DepositToken` calls back into the pool on any inbound transfer/mint, and `addToDepositTokensOfAccount` reverts the whole transaction with `UserReachedMaxTokens` once the list is full. An unprivileged attacker can therefore push dust amounts of every registered `DepositToken` (plus debt tokens via `issue` dust positions they take on the victim's behalf where permitted, or simply dust `DepositToken.transfer`) to a target address, filling its token list so that all subsequent deposits, transfers-in, mints, and liquidation-related collateral transfers to that account revert.

This mirrors the Neutron bug class: a value accepted into per-account state (the "address pair") is not validated against the downstream consumer's limit, so the consumer (any entry point calling `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`) crashes on every subsequent operation.

### Finding Description
- `Pool.addToDepositTokensOfAccount(address account_)` is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts `UserReachedMaxTokens()` when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` (`Pool.sol:143-148`, `Pool.sol:216-220`).
- `addToDebtTokensOfAccount` applies the same combined check (`Pool.sol:204-208`).
- `DepositToken` invokes `addToDepositTokensOfAccount` whenever a recipient's balance transitions from zero — this happens on `transfer`, `transferFrom`, `deposit(to_ = victim)`, and `seize` during liquidation. The attacker only needs to call `deposit(dust, victim)` or `transfer(victim, dust)` once per registered deposit token.
- Because the counter counts deposit tokens *and* debt tokens together, an attacker can also inflate the victim's list through `DebtToken.issue` dust mints that record debt on a chosen `to_`-adjacent path or via `SmartFarmingManager`-driven flows; even deposit tokens alone suffice since `MAX_TOKENS_PER_USER` is bounded by registered deposit/debt tokens.
- No `onlyIfSmartFarmingManager`/`onlyPool`/pause flag protects the victim-side bookkeeping; the only requirement is that the caller is a whitelisted token, which every deployed `DepositToken`/`DebtToken` is.

### Impact Explanation
Once the victim's `depositTokensOfAccount + debtTokensOfAccount` list reaches `MAX_TOKENS_PER_USER`:

- `DepositToken.deposit(..., victim)`, `transfer(victim, ...)`, `transferFrom(..., victim, ...)` for any *new* token type revert with `UserReachedMaxTokens` — temporary freezing of the victim's ability to receive additional collateral and to open new positions.
- `DebtToken._mint` → `pool.addToDebtTokensOfAccount(account_)` reverts when the victim tries to issue debt against a new debt token (`DebtToken.sol:598-600`), blocking new borrows.
- `Pool.liquidate` flows that cause the liquidator-recipient (if it's the victim position being topped up) or `DepositToken.seize` transfers to a previously-unseen token list can revert, interfering with liquidations.
- Recovery requires the victim to actively zero out balances of enough attacker-inserted tokens (transferring dust away so `removeFromDepositTokensOfAccount` runs, `Pool.sol:630-634`), i.e., the victim must spend gas and potentially interact with every inserted token before normal protocol use resumes — a temporary freezing of funds/liveness break.

### Likelihood Explanation
- Attacker is fully unprivileged: only needs dust balances of each whitelisted `DepositToken`'s underlying and calls `deposit(amount, victim)` or `DepositToken.transfer(victim, dust)`.
- The number of tokens needed equals `MAX_TOKENS_PER_USER` *combined* entries, bounded by the number of whitelisted deposit/debt tokens, so cost scales linearly with registered tokens and dust deposits cost only gas + negligible token amounts.
- No oracle manipulation, privileged role, or malicious endpoint is required; reentrancy guards and pause flags do not stop it on the deployed configuration, and `_revertIfLocked` does not apply because the attacker only pushes tokens *to* the victim, never withdraws locked collateral.

### Recommendation
- Let the beneficiary control list membership: make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` opt-in (only when `account_ == _msgSender()` or when the account initiated the deposit/mint), or
- Decouple the revert from transfers: if the list is full, skip adding rather than reverting (tracking rewards/health via a different mechanism), or
- Exempt pure transfers/mints *to* an account from the max check and enforce `MAX_TOKENS_PER_USER` only on actions the account itself initiates (`deposit` where `to_ == msg.sender`, `issue`, `leverage`), so unsolicited dust cannot consume a victim's slots.

### Proof of Concept
Reproducible in the existing Hardhat suite (pattern from `test/Pool.test.ts` `depositTokensOfAccount` describe block):

```ts
// victim is a fresh account; pool has N = MAX_TOKENS_PER_USER registered deposit tokens
for (const dt of allDepositTokens) {
  await underlyingOf(dt).mint(attacker.address, 1) // dust
  await underlyingOf(dt).connect(attacker).approve(dt.address, 1)
  await dt.connect(attacker).deposit(1, victim.address) // fills victim's list
}

// Any further inbound token of a new type to the victim reverts:
await expect(
  otherDepositToken.connect(attacker).deposit(1, victim.address)
).revertedWithCustomError(pool, 'UserReachedMaxTokens')

// Victim cannot deposit collateral of a new type either:
await expect(
  otherDepositToken.connect(victim).deposit(parseEther('10'), victim.address)
).revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Note: if the deployed `MAX_TOKENS_PER_USER` exceeds the number of registered deposit + debt tokens, the attacker must split entries across both lists; the combined check in `onlyIfAdditionWillNotReachMaxTokens` (`Pool.sol:143-148`) is what makes either vector sufficient. The exact trigger hook inside `DepositToken` (transfer hook calling `addToDepositTokensOfAccount`) should be confirmed against `contracts/DepositToken.sol` — index coverage showed the reference exists there but the hook's exact lines were not retrieved in this pass.
