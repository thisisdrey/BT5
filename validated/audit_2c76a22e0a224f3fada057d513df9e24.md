Based on my investigation, the vulnerability described is real.

### Title
Unauthenticated content-hash write allows AtlasDB poisoning via forged attachment content - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` in `stackslib/src/net/atlas/download.rs` inserts `response.attachment` into `self.attachments: HashSet<Attachment>` without checking that `Hash160::from_data(&attachment.content)` equals the requested `AttachmentRequest.content_hash`. `StacksHttpResponse::decode_atlas_get_attachment` (in `stackslib/src/net/api/getattachment.rs`) simply deserializes JSON and performs no hash verification either, so a malicious data-serving peer can return arbitrary bytes for any requested content hash.

### Finding Description
The claimed equality — `Hash160::from_data(&attachment.content) == request.content_hash` — is never checked anywhere in the code path.

- `AttachmentsBatchStateContext::get_prioritized_attachments_requests` builds an `AttachmentRequest { content_hash, sources, .. }` for a missing attachment based on on-chain data [1](#0-0) .
- The request is sent to a peer and the response is decoded via `decode_atlas_get_attachment`, which only parses JSON into a `GetAttachmentResponse { attachment }` with no hash check at all [2](#0-1) .
- `extend_with_attachments` then takes that decoded response and unconditionally inserts `response.attachment` into `self.attachments`, keyed only by success/failure of decoding, never comparing `request.content_hash` (available in the same loop via `request.get_url()`/`request`) against the actual hash of `attachment.content` [3](#0-2) .
- In `AttachmentsDownloader::run`, when the state machine reaches `Done`, every attachment in `context.attachments` is drained and passed straight to `network.atlasdb.insert_instantiated_attachment(&attachment)` — again with no re-verification against the hash that was originally requested/expected [4](#0-3) .

The only hash-based indexing that occurs uses `attachment.hash()` (i.e., the hash *of the possibly-forged content itself*), used to look up `find_all_attachment_instances` — this hash is derived from the attacker's own bytes, not compared against `request.content_hash`, so it does not serve as a hash-check gate; it merely determines which on-chain attachment instances get "resolved" by this attacker-controlled hash value [5](#0-4) . Any attacker-controlled `content` that legitimately hashes to some value will get paired with whatever attachment instances in the DB reference that same hash — meaning an attacker could serve *any* content whose hash matches *some* known instance hash and have it accepted; but the more direct issue per the question is that a peer could return content whose hash does **not** match the specific `content_hash` that was requested for a *different* on-chain reference, and no code path rejects that mismatch. There's no code in `extend_with_attachments`, `decode_atlas_get_attachment`, or `AttachmentsDownloader::run` that compares the response's actual content hash against the `AttachmentRequest.content_hash` that solicited it.

### Impact Explanation
A single unprivileged peer serving Atlas attachment-download HTTP responses can cause the requesting node to store attacker-chosen bytes in its AtlasDB via `insert_instantiated_attachment`, associated with `attachment.hash()` computed from the attacker's own payload. Because `find_all_attachment_instances(&attachment.hash())` is used to find on-chain instances referencing that hash, if the attacker's chosen bytes happen to hash to a value referenced by a legitimate on-chain BNS/Atlas instance, this results in unauthenticated write of forged content associated with that on-chain reference, which can then propagate to other peers that sync from this node's AtlasDB (network-wide propagation of forged data) — matching the Critical category of "unauthenticated/unauthorized write to state" and "network-wide propagation of forged data."

### Likelihood Explanation
The precondition is only that the victim node selects the attacker as one of its `sources`/outbound sync peers for an `AttachmentRequest` (which happens naturally in the normal Atlas sync flow when a peer's inventory claims to have the attachment) — no secret, signature, or privileged role is required. The attacker just needs to run/serve a normal peer's `/v2/attachments/:hash` HTTP endpoint (or the client-side response handling for it) and return a crafted JSON body. This is fully repeatable per download cycle.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (or immediately after `decode_atlas_get_attachment`), verify `Hash160::from_data(&response.attachment.content) == request.content_hash` before inserting into `self.attachments`; treat a mismatch as a faulty-peer response (bump `report.bump_failed_requests()` and optionally mark the peer as faulty/deregister), never inserting mismatched content.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/tests.rs` (or a new test in `download.rs`'s test module):
1. Construct an `AttachmentRequest` with a known `content_hash: Hash160 = H` for some `sources` peer URL.
2. Build a `BatchedRequestsResult` whose `succeeded` map contains that request paired with `Some(StacksHttpResponse)` whose JSON body is `GetAttachmentResponse { attachment: Attachment { content: b"forged-bytes".to_vec() } }`, where `Hash160::from_data(b"forged-bytes") != H`.
3. Call `AttachmentsBatchStateContext::extend_with_attachments(context, &mut results)`.
4. Assert that `context.attachments` contains the forged `Attachment` (proving no hash check rejected it) — e.g., `assert!(context.attachments.iter().any(|a| a.content == b"forged-bytes"))`.
5. Optionally extend to `AttachmentsDownloader::run` to show `network.atlasdb.insert_instantiated_attachment` is invoked on the mismatched attachment at `stackslib/src/net/atlas/download.rs:161`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
