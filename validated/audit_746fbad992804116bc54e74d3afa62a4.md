### Title
`FetchRemote` Bypasses Pre-Receive/Update Hook Enforcement, Allowing Protected-Branch and Push-Rule Controls to be Circumvented via Mirroring - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
The `FetchRemote` RPC, used to implement repository pull mirroring, updates repository references through a raw `updateref.Updater` instead of the hook-invoking `UpdaterWithHooks` used by ordinary push paths (`UserUpdateBranch`, `UserFFBranch`, receive-pack). As a result, references fetched from a (user-configured) remote are written to the repository without ever executing the `pre-receive` and `update` custom hooks that GitLab relies on to enforce protected-branch rules, push rules, and other access-control policies.

### Finding Description
In a normal `git push`, reference changes flow through `UpdaterWithHooks.UpdateReference`, which explicitly invokes `PreReceiveHook`, `UpdateHook`, and the `ReferenceTransactionHook` before committing the update via `updateref.Updater`: [1](#0-0) 

These hooks are the mechanism by which GitLab enforces protected branches, push rules, and other repository-level access policies — analogous to the "validation-associated hooks" in the external report that are supposed to gate every state-changing operation.

`FetchRemote`, however, performs the exact same class of operation — mutating refs in a repository — through a completely different, hook-free code path. It builds a plain `updateref.Updater` directly on the (quarantined) repository and commits ref updates without ever calling `hookManager.PreReceiveHook` or `hookManager.UpdateHook`: [2](#0-1) [3](#0-2) [4](#0-3) 

The underlying `Repo.FetchRemote` further explicitly supports disabling even the reference-transaction hook via `DisableTransactions`/`WithDisabledHooks`, which `fetchRemoteAtomic` sets to `true` for the dry-run fetch phase: [5](#0-4) [6](#0-5) 

This mirrors the report's core bug class exactly: two logically-equivalent operations (a ref update caused by `git push` vs. a ref update caused by `FetchRemote`/mirroring) exist, but only one of them runs the full hook chain that is supposed to gate the operation. Just as the "deferred action" path in the report let an attacker reach a privileged execution function while skipping the hooks that enforce a session key's spending limit, `FetchRemote` lets a mirror-configured ref update reach the exact same destination (an updated branch ref) while skipping the hooks that enforce protected-branch and push-rule policy.

### Impact Explanation
Any ordinary project maintainer able to configure a pull mirror (a standard, unprivileged GitLab feature reachable via `FetchRemote`'s `RemoteParams.Url` field) can cause ref updates — including to protected branches — that never pass through `pre-receive`/`update` hook validation. If GitLab's protected-branch enforcement, commit signing requirements, file-size limits, or push-rule logic is implemented purely in these hooks, an attacker who controls (or can redirect, e.g., via a malicious/attacker-influenced mirror source URL) the upstream remote can push arbitrary history onto branches that are supposed to be protected from direct pushes, bypassing controls that a normal `git push` from the same account would be subject to. This is a policy/access-control bypass rooted in an inconsistent hook-execution guarantee between two RPCs that perform the same underlying git object, exactly the class of issue flagged in the report ("checking only ... is insufficient; [the operation] must trigger all associated validation hooks").

### Likelihood Explanation
Reaching this path requires only standard, unprivileged actions available to any project owner/maintainer: configuring a repository mirror (which invokes `FetchRemote` with an attacker-influenced or attacker-controlled `RemoteParams.Url`) or otherwise triggering the `FetchRemote` RPC/CLI command with a crafted remote. No elevated Gitaly credentials beyond what mirroring already requires are needed, and the hook-skipping behavior is unconditional in the current code (not behind a feature flag guarding it against protected refs).

### Recommendation
Route `FetchRemote`'s reference updates through the same hook-invoking updater (`UpdaterWithHooks`) used for push-based operations, or at minimum invoke the equivalent `pre-receive`/`update` custom hooks (with the quarantine directory in scope) before committing fetched ref updates, so that GitLab's protected-branch and push-rule policies are consistently enforced regardless of whether a ref change originates from `git push` or from repository mirroring.

### Proof of Concept
1. As a project maintainer, configure a pull mirror for a repository whose `main` branch is marked "protected" (no direct pushes allowed) with an attacker-influenced remote URL.
2. Have the mirrored remote's `main` branch contain history that would be rejected by GitLab's `pre-receive` policy check if pushed directly (e.g., unsigned commits, bypassing a push rule, or a force-push to `main`).
3. Trigger `FetchRemote` (automatically on mirror update or manually via the RPC).
4. Observe in `fetchRemoteAtomic` that reference updates are applied via `updateref.New(ctx, quarantineRepo)` directly, with no `hookManager.PreReceiveHook`/`UpdateHook` invocation anywhere in the call path, confirmed at [3](#0-2)  and [4](#0-3) , contrasted with the hook-invoking `UpdateReference` used by push paths at [1](#0-0) .
5. The protected branch is updated with content that a direct `git push` from the same user would have been rejected for, demonstrating the hook/access-control bypass.

func (s *server) FetchRemote(ctx context.Context, req *gitalypb.FetchRemoteRequest) (*gitalypb.FetchRemoteResponse, error) {
	if err := s.validateFetchRemoteRequest(ctx, req); err != nil {
		return nil, err
	}

	if req.GetTimeout() > 0 {
		var cancel context.CancelFunc
		ctx, cancel = context.WithTimeout(ctx, time.Duration(req.GetTimeout())*time.Second)
		defer cancel()
	}

	tagsChanged, repoChanged, err := s.fetchRemoteAtomic(ctx, req)
	if err != nil {
		return nil, err
	}

	return &gitalypb.FetchRemoteResponse{TagsChanged: tagsChanged, RepoChanged: repoChanged}, nil
}
