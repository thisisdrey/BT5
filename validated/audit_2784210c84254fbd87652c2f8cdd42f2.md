Audit Report

## Title
`LocalAssetOwner` origin check for `register_token` ignores the asset's `Freezer`/`Admin` roles, letting a self-created asset's owner permanently freeze bridge-locked balances - ([File: bridges/snowbridge/runtime/runtime-common/src/v2/register_token.rs])

## Summary
`LocalAssetOwner::try_origin` only verifies `who == AssetInspect::owner(asset_id)` before allowing an asset to be registered for bridging to Ethereum via `SnowbridgeSystemFrontend::register_token`, without checking whether the asset's separate `Freezer`/`Admin` roles are neutralized. Because `pallet_assets::create` is a fully permissionless call that makes the creator the Owner, Issuer, Admin, and Freezer simultaneously by default, an attacker can create an asset, register it for bridging, wait for users to bridge value into the Ethereum sovereign account (or accumulate balances), and then call `freeze`/`freeze_asset` to permanently block transfers of that asset — locking bridge-held and user funds.

## Finding Description
`LocalAssetOwner::try_origin` in [1](#0-0)  checks only `who != owner` and returns success — it never inspects the asset's `Freezer` or `Admin` fields. This type is wired as one branch of `RegisterTokenOrigin` for `snowbridge_pallet_system_frontend::Config` on Asset Hub Westend, alongside `ForeignAssetOwner` and a root fallback: [2](#0-1) .

`pallet_assets::create` is documented as a permissionless function, and by default the creator becomes Owner, Issuer, Admin, and Freezer of the new asset class in one call. `freeze` and `freeze_asset` in `substrate/frame/assets/src/lib.rs` require only `origin == d.freezer`, with no cross-check against the Owner role, meaning Owner and Freezer being the same account (the default state after `create`) is fully legitimate and unrestricted from the pallet's perspective.

The `register_token` call in `bridges/snowbridge/pallets/system-frontend/src/lib.rs` (lines 217-252) invokes `T::RegisterTokenOrigin::ensure_origin(origin, &asset_location)`, which for a `TrustBackedAssets`-instance asset resolves to `LocalAssetOwner`. Once the origin check passes, the asset is committed for bridging via `build_register_token_call`/`send_transact_call`, which dispatches `RegisterToken` to BridgeHub with no further validation of the asset's mutable authority roles.

I confirmed via code inspection that:
- `LocalAssetOwner` has no reference to `Freezer`/`Admin`, only `AssetInspect::owner`.
- The wiring in `bridge_to_ethereum_config.rs` uses the `Assets` pallet instance (trust-backed assets), which is populated through the permissionless `pallet_assets::create` path.
- No allowlist, filter, or additional check exists in `system-frontend`'s `register_token` call or in the Snowbridge codebase (`bridges/snowbridge/**/*.rs`) referencing `freeze`/`Freezer`/`frozen`, confirming there is no mitigating control anywhere in the bridging flow.

This means the exact same attacker-created key that passes the origin check for registering the bridged asset also retains standing authority to call `pallet_assets::freeze` (targeting a specific account, e.g., the Ethereum sovereign account holding bridge-locked balances) or `pallet_assets::freeze_asset` (freezing the entire asset class) at any point after registration, with no bridge-specific safeguard preventing it.

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" category in the impact gate: an attacker who created and self-registered a trust-backed asset for bridging can subsequently freeze the Ethereum sovereign/reserve account (blocking all incoming/outgoing settlement of that asset across the bridge) or freeze the entire asset class, permanently preventing withdrawal/redemption of any value locked against that bridged token — with no governance or admin action required from anyone but the attacker themselves.

## Likelihood Explanation
The attack requires no special privilege: `pallet_assets::create` is public and grants the caller Owner+Freezer roles by default; `register_token`'s `LocalAssetOwner` origin check is satisfied purely by `who == owner`; and `freeze`/`freeze_asset` are gated only on `origin == d.freezer`. The entire path — create asset, register for bridging, wait for value to accumulate, then freeze — is reachable purely through public extrinsics without collusion, relayer compromise, or leaked keys, making this a self-inflicted-but-externally-triggerable attack against any third party who trusts and bridges the asset.

That said, this scenario hinges on victims choosing to bridge/hold an asset created and controlled entirely by the attacker (a "rug-pull"-style asset), rather than the bridge onboarding a pre-existing, broadly-trusted asset whose authority the attacker doesn't control. The register-token origin check's purpose is to verify only that the caller has standing to *initiate* registration of an asset they already fully control — it was not designed as (and current pallet_assets semantics do not provide) a mechanism to bind or neutralize mutable roles at registration time. Since the Freezer capability already exists and is exercisable independently of bridging (the attacker could freeze their own asset regardless of whether it was ever registered with Snowbridge), the bridge registration flow does not grant any *new* capability to the attacker — it only means third parties who bridge such a self-created, unvetted asset inherit the pre-existing freeze risk of that asset. This is consistent with general permissionless-asset risk in `pallet_assets` rather than a flaw specific to the bridge's proof/state-acceptance or settlement logic.

## Recommendation
If tighter guarantees are desired for bridging local trust-backed assets, `LocalAssetOwner`/`ForeignAssetOwner` should additionally verify (via `pallet_assets::roles::Inspect`) that the asset's `Freezer`/`Admin` are relinquished (e.g., set to a burn address or the Owner itself only via an immutable binding) before or at registration time, or the frontend pallet should document/enforce that only assets vetted by governance (e.g., via `force_create`, sufficient assets with locked teams) are eligible for `register_token`.

## Proof of Concept
1. Attacker calls `pallet_assets::create(origin=Attacker, id=X, admin=Attacker, min_balance=1)`; Attacker becomes Owner/Admin/Issuer/Freezer of asset `X`.
2. Attacker calls `SnowbridgeSystemFrontend::register_token(origin=Attacker, asset_id=X, ...)`; `LocalAssetOwner::try_origin` passes since `who == owner`.
3. Third-party users bridge asset `X` to Ethereum, accumulating balance in the Ethereum sovereign account on Asset Hub.
4. Attacker calls `pallet_assets::freeze(origin=Attacker, id=X, who=<ethereum_sovereign>)` or `freeze_asset(origin=Attacker, id=X)`.
5. Subsequent transfer/burn/redeem operations on asset `X` fail with `Error::Frozen`, blocking settlement for any user who bridged that asset.
