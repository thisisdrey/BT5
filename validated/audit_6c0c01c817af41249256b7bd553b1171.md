### Title
Unprivileged attacker can fill a victim's per-account token lists with dust deposit-token transfers, reverting all new deposit/mint/receive paths (`UserReachedMaxTokens`) - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` caps the combined per-account `depositTokensOfAccount` + `debtTokensOfAccount` lists at `MAX_TOKENS_PER_USER = 30` and reverts any *addition* once the cap is reached. Any holder of a `DepositToken` (msdTOKEN) can push entries into an arbitrary victim's list by transferring 1-wei dust, because `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero. An attacker who dusts the victim with every listed deposit token saturates the list, after which every code path that would add a *new* token to the victim's account — `DepositToken.deposit(..., onBehalfOf_=victim)`, `DebtToken.issue/mint`, receipt of any msdTOKEN transfer — reverts with `UserReachedMaxTokens`. ### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`. [2](#0-1) 
- `DepositToken._transfer` adds the token to the recipient's list on a zero→nonzero balance transition, with no opt-in and no minimum amount. [4](#0-3) 
- Attack path (unprivileged): attacker deposits a tiny amount into each listed deposit token, then calls `transfer(victim, 1)` on each one. Each call adds that token to `depositTokensOfAccount[victim]` because the victim's `_recipientBalanceBefore == 0`.
- Once saturated: `DebtToken.issue`/`mint` for a synthetic the victim doesn't already owe reverts (it calls `addToDebtTokensOfAccount`); `DepositToken.deposit(amount, victim)` for any collateral the victim doesn't already hold reverts (`_mint` → the same zero-balance add path at `DepositToken.sol:486-488`); `SmartFarmingManager.leverage` for the victim reverts on any new-token leg.
- Neither `SynthContext` meta-sender checks, `nonReentrant`, `whenNotPaused`, lock checks (`_revertIfLocked` only guards the sender's *outgoing* balance), nor supply caps prevent this — the victim's consent is never required for a `transfer`.

### Impact Explanation
The victim suffers a sustained denial of service on all position-expanding operations: cannot open new collateral types, cannot mint new synthetic debt, cannot receive msdTOKEN transfers, and cannot be leveraged via `SmartFarmingManager`. This is a temporary freezing of the victim's position/funds utility — the attacker can cheaply re-dust slots as fast as the victim clears them (each cleared slot costs the victim a transfer transaction). Existing balances remain withdrawable, so this is not permanent freezing, which bounds severity at Medium — matching the DoS class of the reference report.

### Likelihood Explanation
Requires only an EOA plus dust amounts of each listed deposit token (acquired via `deposit` with `amount_=1`-scale values or dust purchases). Feasibility depends on the pool listing enough deposit tokens to fill 30 slots; on deployments with ≥30 listed collaterals the attack is fully self-contained. If the pool has fewer deposit tokens, the attacker can partially saturate and combine with the victim's existing debt-token entries. Cost is linear and small; no privileged role, oracle manipulation, or governance action needed.

### Recommendation
- Remove the per-account add on plain `transfer`, or track per-account tokens lazily (compute collateral value by iterating pool-level `depositTokens` and checking `balanceOf > 0` instead of storing per-account sets).
- Alternatively, exempt sub-dust amounts (e.g., ignore `amount_` below a threshold for list insertion) and/or only add to the list on `deposit`/`mint` paths where the recipient is `onBehalfOf_` chosen by the payer.
- If the list is kept, do not revert on cap — allow additions beyond 30 or make `addTo*TokensOfAccount` a no-op at capacity so griefing cannot brick recipient flows.

### Proof of Concept
Hardhat fork sketch (repeatable):
1. For each `dt` in `pool.getDepositTokens()`: `dt.deposit(1, attacker)` (or dust-buy underlying) then `dt.transfer(victim, 1)`.
2. After 30 entries, assert `pool.getDepositTokensOfAccount(victim).length + pool.getDebtTokensOfAccount(victim).length == 30`.
3. Assert `dtNew.deposit(100e18, victim)` reverts `UserReachedMaxTokens`, `debtToken.issue(victim, 1)` reverts `UserReachedMaxTokens`, and `dt.transfer(victim, 1)` from a third party reverts.
4. Show victim `withdraw`/`repay` still works but any new-token operation reverts until the victim spends gas clearing dust (and the attacker re-dusts cleared slots).

Caveat I could not fully verify within the index: the exact revert site inside `DebtToken.issue`/`addToDebtTokensOfAccount` (grep confirmed the calls exist but not their full bodies) and the number of deposit tokens listed on each live deployment; the attack requires enough listed collaterals (plus the victim's own debt entries) to reach 30.
