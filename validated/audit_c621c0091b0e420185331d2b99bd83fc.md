### Title
Global stake-weighted stream-throttling threshold in the QUIC streamer can be gamed by unstaked/low-stake load to throttle legitimate staked traffic - (File: streamer/src/nonblocking/stream_throttle.rs)

### Summary
The Opus/Shrine finding shows that a *global* health metric (system-wide LTV) is compared against a fixed fraction of a threshold to flip a binary "recovery mode" switch that then reduces the collateral threshold applied to *all* troves, including ones an attacker did not touch, letting the attacker manufacture liquidations of otherwise healthy positions by pushing the shared metric across the trigger point. The QUIC streamer's stake-weighted QoS throttle contains the same structural pattern: a single shared, globally-observed load metric (`StakedStreamLoadEMA`) is compared against a fixed 95% threshold to flip a global `staked_throttling_enabled` flag that then changes the stream-admission formula applied to *every* staked connection, not just the connection(s) that drove the load up.

### Finding Description
`StakedStreamLoadEMA` maintains one process-wide EMA of stream load (`current_load_ema`) that is incremented by every staked connection's streams via `increment_load` [1](#0-0) . When the EMA crosses `staked_throttling_on_load_threshold` (95% of the max staked load budget for the window) the atomic flag `staked_throttling_enabled` is flipped on for the whole streamer instance, as exercised by `test_staked_throttling_on_off` [2](#0-1)  and configured via `staked_throttling_on_load_threshold` in `new()` [3](#0-2) .

Once that single global switch is on, `available_load_capacity_in_throttling_duration` changes the per-connection stream budget formula for *every* staked peer from a flat/generous allotment to one scaled purely by `stake / total_stake` of the fixed `max_staked_load_in_throttling_window`, with only a minimal floor above the unstaked budget: [4](#0-3) 

This is the direct analog of `scale_threshold_for_recovery_mode`: a shared, globally observable aggregate (Shrine's system LTV / streamer's load EMA) is compared to a fixed multiplier of a limit (`RECOVERY_MODE_THRESHOLD_MULTIPLIER` 0.7 / `STAKED_THROTTLING_ON_LOAD_THRESHOLD_RATIO` 0.95), and crossing it degrades the effective allowance (trove threshold / per-connection stream budget) applied to *all* other unrelated participants, not just the party that pushed the metric over the line.

The streamer's per-connection admission (`SwQos::try_add_connection` / `cache_new_connection`) already grants staked connections a per-connection uni-stream budget proportional to their own stake independent of this EMA (`compute_max_allowed_uni_streams_with_rtt` in `streamer/src/nonblocking/swqos.rs` lines 147-179), so a handful of staked (even relatively low-stake) connections can legitimately open connections and drive up `load_in_recent_interval`/`current_load_ema` purely through normal, protocol-permitted traffic, flipping the shared `staked_throttling_enabled` switch. Any other, well-behaved staked validator's TPU/TPU-forward traffic then has its effective stream quota recomputed under the harsher stake-ratio formula for the remainder of the smoothing window, even though it did not contribute to (and cannot control) the shared EMA state.

### Impact Explanation
Because `staked_throttling_enabled` and `current_load_ema` are single shared, mutable pieces of state read by every staked connection's `on_new_stream` path (`max_streams_per_throttling_interval` -> `available_load_capacity_in_throttling_duration`, `swqos.rs` lines 292-298, 496-516), an unprivileged (but staked, or a coalition of low/medium-stake) peer can unilaterally cause the leader's QUIC streamer to apply the harsher stake-ratio throttling formula to the entire set of staked peers currently connected, reducing the effective transaction throughput/QoS available to unrelated, legitimately-behaving stakers during the throttling window. This is a griefing / QoS-degradation vector rather than a node crash, and does not itself allow bypassing fees or forging blocks; the "throttling" behavior is still a soft rate limiter, not an admission bypass, so the blast radius is reduced throughput for honest stakers during the active window rather than data loss or consensus impact.

### Likelihood Explanation
The trigger condition only requires driving process-wide staked stream load to 95% of the configured window budget, which is achievable by ordinary (permitted) staked traffic from one or a modest number of low/medium stake keys without any privileged role, matching the "unprivileged-user analog" and QUIC/UDP streamer scope explicitly called out in the prompt. Unlike the Shrine case, this only shifts *rate-limiting fairness*, not final admission/liquidation, so real-world impact is bounded and self-healing once the EMA decays (`update_ema`/`update_ema_if_needed`), lowering severity relative to the original high-risk finding.

### Recommendation
Avoid making a single global boolean/EMA gate the throttling formula for all peers uniformly. Instead, base each connection's admission/throttle decision only on its own recent behavior (already tracked via `ConnectionStreamCounter`), and/or require sustained per-connection contribution to the aggregate load before that connection is subjected to the harsher ratio, so that one or a few connections cannot unilaterally alter the effective quota of unrelated staked peers. Consider decaying the shared EMA faster relative to burst windows, or partitioning the aggregate load tracking so the throttling decision correlates with the specific connections causing the load rather than applying uniformly to the whole staked population.

### Proof of Concept
1. Establish `N` staked QUIC connections (any real stake, even below `min_stake_ratio`) sufficient to sustain the load rate needed to push `StakedStreamLoadEMA::current_load_ema` above `staked_throttling_on_load_threshold` (95% of `max_staked_load_in_ema_interval`), as demonstrated deterministically in `test_staked_throttling_on_off` by setting load/EMA values above/below the threshold [2](#0-1) .
2. Once `staked_throttling_enabled` flips true, any other staked connection's `on_new_stream` call resolves its budget via `available_load_capacity_in_throttling_duration`, which now uses the stake-ratio branch instead of the full `max_staked_load_in_throttling_window`, as shown by `test_staked_capacity_shares_when_throttled` (a stake of 10/100 total is capped down to `max_unstaked_load_in_throttling_window + 1`, i.e., barely above unstaked) [5](#0-4) .
3. Any low/medium-stake validator connected at that time observes its effective QUIC stream quota collapse toward the unstaked minimum, even though it never exceeded its own individually-assigned rate, for the duration of the throttling window.

    pub(crate) fn available_load_capacity_in_throttling_duration(
        &self,
        peer_type: ConnectionPeerType,
        total_stake: u64,
    ) -> u64 {
        match peer_type {
            ConnectionPeerType::Unstaked => self.max_unstaked_load_in_throttling_window,
            ConnectionPeerType::Staked(stake) => {
                if self.staked_throttling_enabled.load(Ordering::Relaxed) {
                    // 1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked
                    // clients get at least 1 more number of streams than unstaked connections.
                    self.max_staked_load_in_throttling_window
                        .saturating_mul(stake)
                        .checked_div(total_stake)
                        .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
                        .max(self.max_unstaked_load_in_throttling_window + 1)
                } else {
                    self.max_staked_load_in_throttling_window
                }
            }
        }
    }
