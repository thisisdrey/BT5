### Title
Attacker can fill a victim's per-account token list via dust `DepositToken` transfers, reverting all future deposits, transfers, and liquidations that add a new token - ([File: contracts/Pool.sol])

### Summary
`Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert once a victim's combined token list reaches `MAX_TOKENS_PER_USER = 30`. Any unprivileged user can dust-transfer distinct `DepositToken`s to a victim to fill this list, after which every code path that adds a new token to the victim reverts.

### Finding Description
Each `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's balance goes from 0 to >0 [1](#0-0) . The Pool enforces a hard cap: if `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` it reverts with `UserReachedMaxTokens` [2](#0-1) .

An attacker deposits small amounts into each listed collateral, then `transfer()`s 1 wei of each `DepositToken` to the victim. `transfer` only checks the *sender's* unlocked balance [3](#0-2) , so no consent is needed. Once the victim's list is full:

- `deposit(amount, onBehalfOf_ = victim)` on any collateral the victim doesn't already hold reverts inside `_mint` → `addToDepositTokensOfAccount` [4](#0-3) .
- `transfer`/`transferFrom`/`seize` to the victim of a new token reverts.
- Any path minting a new `DebtToken` to the victim (e.g. `issue` on a new synthetic) reverts via `addToDebtTokensOfAccount` [5](#0-4) .

If the victim has outstanding debt, `unlockedBalanceOf` returns less than their balance [6](#0-5) , so the victim cannot even transfer the attacker's dust out to free slots — the dust is locked collateral. The victim must fully repay debt to regain the ability to remove the filler tokens.

### Impact Explanation
Temporary freezing of funds / denial of service: a victim with open debt cannot onboard new collateral (e.g. to improve health and avoid liquidation), cannot receive new deposit/debt tokens, and cannot evict the filler tokens while locked. The freeze persists until the victim repays debt in full. This mirrors CVE-2021-3559's pattern — an unprivileged actor weaponizing a per-object listing mechanism to crash/DoS operations on another user's account.

### Likelihood Explanation
Fully unprivileged: the attacker only needs to deposit dust into ~15–30 distinct `DepositToken`s and call `transfer`. Cost is bounded by dust value plus gas; no privileged role, oracle manipulation, or timing dependency is required. The cap check sits on the exact path the attacker controls (recipient list insertion).

### Recommendation
- Make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` a no-op (or silently skip tracking) instead of reverting when the cap is hit, and make `debtPositionOf`/`depositOf`/`debtOf` robust to untracked tokens — or better, derive positions from balances rather than a per-account list.
- Alternatively, allow recipients to remove tokens with zero-relevant balance, or exempt `seize`/liquidation transfers from the cap so liquidators aren't blocked.

### Proof of Concept
Hardhat sketch (fork any deployment with ≥2 listed deposit tokens):

```ts
// attacker fills victim's list to MAX_TOKENS_PER_USER
for (const dt of depositTokens) {
  await underlying.connect(attacker).approve(dt.address, DUST);
  await dt.connect(attacker).deposit(DUST, attacker.address);
  await dt.connect(attacker).transfer(victim.address, 1);
}
// victim now has 30 tokens; if victim has debt, dust is locked and can't be sent back
await expect(
  newDepositToken.deposit(1e6, victim.address) // any token victim doesn't hold
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Note: if the victim is debt-free they can transfer the dust out to clear slots, so practical impact is concentrated on indebted accounts — exactly those that most need to add collateral. If the intended scoring bar excludes cap-revert griefing as "temporary freezing" because a debt-free victim can self-recover, this should be downgraded; the locked-dust case for indebted accounts is the compelling variant.
