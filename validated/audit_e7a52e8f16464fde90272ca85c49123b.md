### Title
StackerDB chunk signatures are not domain-separated by contract, enabling cross-StackerDB chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs` binds a StackerDB chunk signature only to `slot_id`, `slot_version`, and `data_hash`. It does not include the smart contract identifier (`QualifiedContractIdentifier`) of the StackerDB the chunk is destined for. Because Stacks deploys many distinct StackerDB replicas that share the identical `(signer, slot_id)` assignment for a given signer set (e.g. the family of `signers-{set}-{message_id}` contracts, one per `MessageSlotID`, all reading the same slot list via `stackerdb-get-signer-slots` from `.signers`), a single valid signature produced for one contract's chunk is also a valid signature for the same `(slot_id, slot_version, data_hash)` tuple in any other contract where that address happens to own the same slot. This breaks the "authenticated for context A" vs "accepted as authentic in context B" equality.

### Finding Description
- `SlotMetadata::auth_digest()` (`libstackerdb/src/libstackerdb.rs:159-166`) computes `Sha512_256(slot_id || slot_version || data_hash)` — no contract/DB identifier is mixed in. [1](#0-0) 
- `SlotMetadata::verify()` and `StackerDBChunkData::verify()` only recover the public key from this digest and check the resulting `Hash160` against the caller-supplied `principal` (address) — again with no notion of which StackerDB contract this check is being performed for. [2](#0-1) 
- The actual per-contract binding happens only in `StackerDBSync::validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:649-718`), which looks up `get_slot_signer(smart_contract_id, data.slot_id)` for the *target* contract and then calls `slot_metadata.verify(&addr)`. It never checks that the signature was produced *for this specific contract* — only that the recovered address matches whoever is assigned to that slot ID in the current DB. [3](#0-2) 
- Multiple StackerDB contracts deliberately reuse identical `(signer, num-slots)` assignments. Each `signers-{set}-{message_id}` contract just proxies to `.signers stackerdb-get-signer-slots-page`, so every message-type-specific StackerDB for a given signer set has the *same* slot-to-signer mapping. [4](#0-3) [5](#0-4) 
- This is directly confirmed by the test `signers_db_get_slots`, which asserts that for a given signer set, every `message_id` contract (0..`SIGNER_SLOTS_PER_USER`) returns the exact same signer-slot list. [6](#0-5) 

Because the same address owns slot `N` across every message-type StackerDB in a signer set, and the signed digest commits only to `(slot_id, slot_version, data_hash)`, an attacker who observes (via public HTTP GET or P2P StackerDB gossip — no privileges required) a valid, previously-broadcast chunk signed by that address for contract A can resubmit the identical `(slot_id, slot_version, sig, data)` tuple to a different sibling contract B (any `signers-{set}-{other_message_id}` where the signer occupies the same slot). `validate_received_chunk`/`try_replace_chunk` for contract B will accept it as long as `slot_version >= expected_version_for_B` and `<= max_writes_for_B` — both easily satisfiable for a freshly-initialized or behind sibling DB slot. This lets the attacker plant data authenticated for one message type's replica into a different message type's replica without ever holding the signer's private key.

### Impact Explanation
This is an unauthorized write to StackerDB state: data cryptographically authenticated only for context A is accepted and stored as authentic in context B, satisfying the "authenticated vs. stored" equality break called out in scope. Consumers of the target StackerDB (e.g. `stacks-node/src/nakamoto_node/stackerdb_listener.rs`'s `InitialChunksLoader`, or `stacks-signer` code reading `SignerMessage`s from a specific `MessageSlotID` contract) will read attacker-replayed bytes and attempt to deserialize them as the wrong `SignerMessage` variant, corrupting the miner/signer's view of that slot's latest chunk. This can desynchronize signer state-machine views or feed stale/foreign-context data into consensus-adjacent tooling — a remote, unauthenticated write primitive requiring no secret key.

### Likelihood Explanation
Requires only public passive observation of one legitimately-signed chunk (chunks are broadcast openly via StackerDB push/pull and served over the read-only HTTP StackerDB API) plus a normal, unauthenticated write to a sibling contract's slot — both trivially reachable by any remote peer. The version-window constraint (`slot_version` must be `>=` expected and `<=` `max_writes`) is easily met for early/behind slots, which is the common case immediately following a reward-cycle rollover when new sibling `signers-{set}-{message_id}` StackerDBs are freshly created (`NO_VERSION`/version 0).

### Recommendation
Bind the StackerDB chunk signature to the destination contract by including the `QualifiedContractIdentifier` (or a stable numeric StackerDB ID) in `SlotMetadata::auth_digest()`, e.g. `hash(contract_id || slot_id || slot_version || data_hash)`, and thread the contract identifier through `sign`/`verify`/`recover_pk` in `libstackerdb/src/libstackerdb.rs` and all call sites in `stackslib/src/net/stackerdb/mod.rs` and `stackslib/src/net/api/poststackerdbchunk.rs`. This is a wire/consensus-adjacent format change and needs versioning/compat handling for existing signers.

### Proof of Concept
1. Observe (via HTTP `GET /v2/stackerdb/{signer}-1-0/... ` or via P2P `StackerDBPushChunk`) a chunk broadcast by signer `S` for contract `.signers-1-0` (e.g. `MessageSlotID::BlockResponse`), with `slot_id = k`, `slot_version = v`, `sig`, `data`.
2. Determine that `S` also owns `slot_id = k` in the sibling contract `.signers-1-3` (e.g. `MessageSlotID::StateMachineUpdate`), per `stackerdb-get-signer-slots-page` returning identical assignments for all `signers-1-*` contracts.
3. Submit an HTTP POST (`poststackerdbchunk`) to `.signers-1-3` with the *same* `slot_id`, `slot_version`, `sig`, and `data` originally signed for `.signers-1-0`.
4. `validate_received_chunk`/`try_replace_chunk` recovers the same public key `S` from the same `(slot_id, slot_version, data_hash)` digest, matches the expected signer for slot `k` in `.signers-1-3`, and — provided `slot_version` clears that DB's `expected_version`/`max_writes` checks — accepts and stores it, even though `S` never authorized this data for `.signers-1-3`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
