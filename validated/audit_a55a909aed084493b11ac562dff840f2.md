### Title
Relay `from` address is taken from unauthenticated message field instead of the verified sender's certificate identity - (File: relay_manager.go)

### Summary
`handleCreateRelayRequest` derives the relay-for address (`from`) solely from the peer-supplied `m.RelayFromAddr` field of the `NebulaControl` message, rather than validating it against the actual certificate identity (`h.vpnAddrs`) of the already-authenticated host `h` that sent the control message.

### Finding Description
`HandleControlMsg` unmarshals a `NebulaControl` message from `d` and only checks that `msg.RelayFromAddr` / `msg.RelayToAddr` are non-nil before dispatching to `handleCreateRelayRequest`: [1](#0-0) 

`handleCreateRelayRequest` then uses `from := protoAddrToNetAddr(m.RelayFromAddr)` — a value taken entirely from the packet payload — as the identity for which relay state is installed, checked, and to whom `CreateRelayResponse` will describe as `relayFrom`: [2](#0-1) 

The only identity checks performed are that `from` is not one of *my own* addresses, and that `target` is one of mine: [3](#0-2)  There is no check that `from` actually equals (or is contained in) `h.vpnAddrs`, i.e. the VPN address(es) bound to the certificate that was cryptographically verified for the connection over which this control message arrived. `h` is the already-authenticated remote (its identity was established during the noise handshake and stored as `h.vpnAddrs`), yet the relay state keyed by `AddRelay(..., h, f.hostMap, from, ...)` is installed using the attacker-suppliable `from` value instead of `h.vpnAddrs[0]`: [4](#0-3) 

This is structurally identical to the reported `depositFor()` flaw: the function should act on behalf of the authenticated sender (`h`, analogous to `msg.sender`) but instead trusts a caller-declared parameter (`m.RelayFromAddr`, analogous to `account`) for a security-relevant decision — here, which VPN address gets registered as being relayed-for through this terminal host.

### Impact Explanation
A host `h` with a valid, CA-signed certificate for its own vpn address can send a `CreateRelayRequest` control message claiming `RelayFromAddr` = some other victim's VPN address that `h` does not own. Because there's no cross-check between `from` and `h.vpnAddrs`, the relay logic will install `TerminalType`/`Established` relay state on the local hostmap under `h`, associated with a spoofed victim address, and will send a `CreateRelayResponse` claiming the relay `relayFrom` is that victim address. Any subsequent forwarded/relayed traffic addressed as coming "from" that victim is treated as legitimately relayed through `h`, which can lead to traffic being misdirected/forged as originating from the victim's overlay IP within the relay path, and can poison relay/hostmap state (`h.relayState`) with attacker-chosen identities not backed by their certificate.

### Likelihood Explanation
Reachable by any peer that has completed a normal handshake (no need for a CA-signed cert for the *victim* identity — only the attacker's own valid cert to establish the underlying tunnel to send the Control message). No lighthouse/relay-node compromise is required; the attacker just sends a crafted `CreateRelayRequest` over their own legitimate encrypted tunnel. This is a directly reachable, unauthenticated-field trust issue in message handling.

### Recommendation
In `handleCreateRelayRequest` (and `handleCreateRelayResponse`), validate that `from` (`m.RelayFromAddr`) is consistent with the sender's authenticated identity where applicable, or otherwise ensure `AddRelay`/relay-state operations are scoped using `h`'s verified `vpnAddrs` rather than blindly trusting attacker-supplied address fields from the control message body.

### Proof of Concept
1. Attacker establishes a normal, valid Nebula tunnel to victim host `V` using their own legitimate certificate (`h` = attacker's HostInfo on `V`'s side).
2. Attacker sends a `NebulaControl` message of type `CreateRelayRequest` with `RelayToAddr` = `V`'s own address (so `target` passes the "is the target of the relay me?" check) and `RelayFromAddr` = some third-party victim's VPN address that the attacker does not control/own.
3. `V.handleCreateRelayRequest` accepts the message, since only `from == V` and `target == V` are excluded, and installs `TerminalType`/`Established` relay state keyed by the spoofed `from` address on the attacker's `HostInfo`, then replies with `CreateRelayResponse` describing that relay as valid.
4. Downstream relay-forwarded traffic can now be associated with the spoofed victim address without ever verifying the attacker holds a certificate for it.
