Audit Report

## Title
Unbacked-mint via `ERC20Transactor` trusting a malicious contract's `transfer()` return value as proof of value movement - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` mints an `AssetsInHolding` credit of `Erc20Credit(amount)` into the XCM executor's holding register solely because a `bare_call` to `IERC20::transfer` returned `true` and did not revert, with no independent verification of an actual balance movement on the checking account. [1](#0-0)  Because the asset id matched by `assets_common::ERC20Matcher` is any location of the form `{parents: 0, interior: X1(AccountKey20{key, network})}` — i.e., an arbitrary `H160` contract address with no allowlist, registration, or "sufficiency" check — an attacker can deploy their own `pallet-revive` contract implementing a fake `IERC20.transfer()` that always returns `true` without moving any real value, and use it as the asset id for a `WithdrawAsset` XCM instruction. [2](#0-1) 

## Finding Description
The withdraw path calls `Matcher::matches_fungibles` to resolve the XCM `Asset` to an `H160` contract address and amount, then issues a `bare_call` transferring `amount` from the XCM-origin's mapped account to the `TransfersCheckingAccount`. [3](#0-2)  If the call does not revert and the ABI-decoded boolean is `true`, the code unconditionally constructs `AssetsInHolding::new_from_fungible_credit` with `Erc20Credit(amount)` — a type explicitly documented as not enforcing runtime-level balance constraints, deferring that enforcement entirely to the (attacker-controlled) contract. [4](#0-3) [5](#0-4) 

The `ERC20Matcher` used to resolve which contract is being targeted is `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, where `IsLocalAccountKey20` accepts *any* location consisting of a bare `AccountKey20` junction, and `AccountKey20ToH160` converts that junction's `key` directly to the target `H160` address with no whitelist or registry lookup. [6](#0-5)  This is confirmed by the feature's own PRDoc, which states asset ids of this form are matched and the corresponding `transfer` function is invoked "in the smart contract whose address is `key`" — i.e., any deployed contract, chosen by the caller. [7](#0-6)  The transactor is wired into Asset Hub Westend's `AssetTransactors` tuple, so it is reachable via `pallet_xcm::execute`/the `IXcm` precompile. [8](#0-7) 

The mirrored `deposit_asset_with_surplus` path has the same unverified trust assumption on the return value of `transfer()`. [9](#0-8) 

No existing guard reads `balanceOf` before/after the call to confirm real value moved; the only checks performed are "did the call revert" and "did it ABI-decode to `true`" — both of which are fully controlled by the called contract's code, which the attacker authors.

## Impact Explanation
This is an unbacked-mint primitive: an unprivileged attacker can cause the XCM executor to credit its holding register with a fabricated `Erc20Credit` amount that has zero real backing, purely by deploying a contract whose `transfer()` always returns `true`. That credit is a first-class value inside `AssetsInHolding` and is available to subsequent instructions in the same XCM program (e.g. `DepositAsset`, `ExchangeAsset`). The exact corrupted value is the `Erc20Credit(u128)` amount inserted into `AssetsInHolding` at `erc20_transactor.rs:198-201`, which is not backed by any verified balance delta on the checking account. This matches the "theft or unbacked mint or unlock" category of the impact gate.

I was not able to fully confirm within the available context whether `pallet_asset_conversion`'s pool-creation logic on Asset Hub Westend permits pairing an arbitrary/unregistered `AccountKey20`-based Location (i.e., the attacker's own fake-ERC20 asset id) with a real asset like DOT — the runtime's `pallet_asset_conversion::Config` (`AssetKind`, `PoolId`, and any pool-creation restrictions) could not be located within the tool budget. If pool creation requires the asset kind to already be a "sufficient"/registered asset, the described pool-drain step of the PoC would not work as stated, though the core unbacked-mint-into-holding primitive itself is confirmed and does not depend on pool mechanics — any downstream logic that accepts this holding credit at face value (deposit to a beneficiary account treated as real value, or any pallet/precompile that trusts XCM holding contents without independent verification) would suffice to realize the impact.

## Likelihood Explanation
High for the core primitive: deploying a `pallet-revive` contract and calling `pallet_xcm::execute` are both permissionless actions requiring no privileged role, relayer, or validator behavior. The `ERC20Matcher`'s acceptance of any `AccountKey20` location with no allowlist, combined with the transactor's return-value-only trust model, means nothing in the current code path prevents this. The full economic exploitation depends on what downstream consumer treats the fake credit as real value (verified above for the transactor itself, unverified for the specific pool-drain scenario in the PoC).

## Recommendation
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` should not rely solely on the boolean return of `transfer()`. Read the checking account's `balanceOf` before and after the `bare_call`, and mint/burn `Erc20Credit` only equal to the observed real balance delta, following checks-effects-interactions (snapshot pre-state, perform the interaction, verify post-state, then credit/debit holding). Additionally, consider restricting `ERC20Matcher`/`IsLocalAccountKey20` to require some form of registration or "sufficiency" marker for contracts before they can be used as XCM fungible asset ids, rather than accepting any bare `AccountKey20` address.

## Proof of Concept
1. Deploy a `pallet-revive` contract `FakeERC20` implementing `IERC20` whose `transfer(address,uint256)` always `return true` and performs no real storage accounting.
2. Its address resolves via `ERC20Matcher`/`IsLocalAccountKey20` as the location `{parents:0, interior: X1(AccountKey20{key: <FakeERC20 address>, network: None})}` — no registration step is required. [6](#0-5) 
3. Call `pallet_xcm::execute` with `WithdrawAsset((FakeERC20Location, HUGE_AMOUNT))`. `withdraw_asset_with_surplus` calls `transfer(checking_account, HUGE_AMOUNT)` on `FakeERC20`, receives `true`/no revert, and credits `HUGE_AMOUNT` of `Erc20Credit` into XCM holding with no real balance ever moved. [10](#0-9) 
4. Write a Rust integration test (in the style of `asset-hub-westend/tests/tests.rs`'s ERC20 withdraw/deposit tests) asserting that after step 3, the resulting `AssetsInHolding` contains `HUGE_AMOUNT` of the `FakeERC20` asset id despite `FakeERC20`'s internal ledger (if it had one) never having recorded any transfer — demonstrating the corrupted value is the `Erc20Credit` amount in holding, unbacked by any verified contract-side balance change.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
