Based on my research, the strongest and most concrete analog to the iToken inflation attack in java-tron is the TRC10 Bancor-style `Exchange` market, where any unprivileged, signed transaction can create a virtually-reserved AMM pool and immediately exploit precision/truncation loss against counterparties.

### Title
Precision-loss/rounding exploitation in TRC10 Exchange pools via unrestricted low-reserve pool creation - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
`ExchangeCreateContract` lets any account create a TRC10↔TRX or TRC10↔TRC10 Bancor-style liquidity pool with reserves as small as `1` unit on each side, and `ExchangeTransactionContract` lets any account trade against any existing pool. Just like the iToken report's "small totalSupply → attacker manipulates exchange rate, rounding steals underlying assets," a pool created with minimal reserves causes the bonding-curve math in `ExchangeProcessor`/`SafeExchangeProcessor` to apply severe integer/floating-point truncation, letting a pool operator or a fast/sandwiching trader extract more value from counterparties than they should receive.

### Finding Description
`ExchangeCreateActuator.doValidate()` only rejects a pool when `firstTokenBalance <= 0 || secondTokenBalance <= 0` and enforces an upper bound (`balanceLimit`), but places no minimum-liquidity floor comparable to Uniswap-style "MINIMUM_LIQUIDITY" protections: [1](#0-0) 
This means an attacker-controlled account can create an exchange with, e.g., `firstTokenBalance=1`, `secondTokenBalance=1`.

Trading against that pool goes through `ExchangeCapsule.transaction()`, which uses a virtual `supply = 1_000_000_000_000_000_000L` bonding-curve relay and truncates results with `(long) issuedSupply` / `(long) exchangeBalance` (non-hardened path) or `BigDecimal...setScale(0, RoundingMode.DOWN)` (hardened path): [2](#0-1) [3](#0-2) 
With reserves this small, the `quant/newBalance` and `supplyQuant/supply` ratios used in the `pow()` calls are dominated by truncation error, so the "another token" amount a trading counterparty receives can be rounded far below the fair-value amount, while the pool (and its creator, who alone can withdraw via `ExchangeWithdrawContract`) retains the difference. This is analogous to the iToken bug: a party (the pool creator, standing in for the "attacker" who controls `totalSupply`) keeps reserves artificially small so that later interactions round in their favor and against the counterparty.

### Impact Explanation
A user who is directed to (or unaware of the low-liquidity state of) an attacker-created Exchange and submits `ExchangeTransactionContract` can receive systematically less than expected due to compounded truncation in `exchangeToSupply`/`exchangeFromSupply`, resulting in real, unrecoverable loss of TRX/TRC10 assets for that specific trade. The magnitude is bounded by the trade size and per-pool balance limits, so it is a theft-of-funds issue scoped to the pool's participants rather than a chain-wide accounting break.

### Likelihood Explanation
Reachable purely through two ordinary signed transactions — `ExchangeCreateContract` (attacker) and `ExchangeTransactionContract` (victim) — with no special privileges required. The `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validations do check for `anotherTokenQuant <= 0` and precision bounds in "hardened" mode, but `ExchangeCreateActuator` has no analogous minimum-reserve floor, so the vulnerable low-liquidity state is trivially reachable at pool creation time. [4](#0-3) 
The practical severity is reduced because a victim must voluntarily choose to trade against a specific, low-reserve, likely-obviously-illiquid pool identified by `exchangeId` — this is comparable to interacting with any untrusted DEX pool and is not a systemic, unavoidable path like the shared iToken vault in the original report.

### Recommendation
Add a minimum-liquidity/minimum-notional-value requirement in `ExchangeCreateActuator.doValidate()` (and correspondingly in `ExchangeInjectActuator`) so pools cannot be created or maintained with reserves so small that the bonding-curve truncation in `ExchangeProcessor`/`SafeExchangeProcessor` becomes economically significant, and consider always enforcing the "hardened" precision checks (currently gated behind `allowHarden()`/`dynamicStore.allowStrictMath()`) for all exchange trades regardless of configuration.

### Proof of Concept
1. Attacker submits `ExchangeCreateContract` with `firstTokenId = TRX`, `firstTokenBalance = 1`, `secondTokenId = <TRC10>`, `secondTokenBalance = 1` — accepted per `ExchangeCreateActuator.doValidate()` (`actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java:201-208`).
2. A counterparty submits `ExchangeTransactionContract` against this `exchangeId`, calling `ExchangeCapsule.transaction()` (`chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java:124-168`), which internally truncates via `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (`chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java:17-39`).
3. Compare the counterparty's received `anotherTokenQuant` against the fair-value amount computed with full precision (e.g., via `BigDecimal` without the final truncation) to demonstrate the shortfall retained by the pool/creator.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
