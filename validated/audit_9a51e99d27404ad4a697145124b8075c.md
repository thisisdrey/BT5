### Title
Missing pubkey-hash verification in neighbor-of-neighbor handshake accept allows PeerDB identity spoofing - (File: stackslib/src/net/neighbors/walk.rs)

### Summary
`NeighborWalk::handle_neighbor_handshake_accept` stores the `HandshakeAcceptData` into the PeerDB frontier via `add_or_schedule_replace_neighbor` without validating that `Hash160(data.handshake.node_public_key)` matches the `naddr.public_key_hash` that was originally gossiped for that address. The sibling `pingback_handshakes_try_finish` path performs this exact check via `check_handshake_pubkey_hash` before persisting, showing the omission is inconsistent and unintentional.

### Finding Description
During neighbor-of-neighbor discovery, `cur_neighbor` returns a `GetNeighbors` reply containing a list of `NeighborAddress { addrbytes, port, public_key_hash }` entries. The walk state machine sends a `Handshake` to each gossiped address and later processes the reply in `neighbor_handshakes_try_finish` (walk.rs ~1147-1230), which calls `self.handle_neighbor_handshake_accept(network, naddr, &message.preamble, data, db_data)` (walk.rs:1224-1230). That function immediately calls `self.neighbor_db.add_or_schedule_replace_neighbor(network, preamble, &data.handshake, db_data, &mut self.neighbor_replacements)` (walk.rs:1104-1110) with no prior call to `Self::check_handshake_pubkey_hash(nk, data, naddr)`.

`add_or_schedule_replace_neighbor` (db.rs:368-426) calls `Neighbor::load_and_update(&tx, preamble.peer_version, preamble.network_id, handshake)`, which loads/creates a `Neighbor` record keyed by the handshake's own `addrbytes`/`port`/`public_key`, and then `save`/`save_update` writes it into `PeerDB`. Nothing in this chain cross-checks against `naddr.public_key_hash`. This means a malicious `cur_neighbor` can advertise `NeighborAddress{addr=X, public_key_hash=H(pubkey_A)}` to make the victim connect to address X, then have the responder at X (which may be attacker-controlled or a legitimate third party being impersonated) answer with `HandshakeAccept{node_public_key=pubkey_B}` where `H(pubkey_B) != H(pubkey_A)`, and the victim will still persist `pubkey_B` for that slot in its PeerDB.

In contrast, `pingback_handshakes_try_finish` (walk.rs:1683-1725) explicitly calls `check_handshake_pubkey_hash(&peer_nk, data, &naddr)` (walk.rs:1714) and skips the record via `continue` on mismatch before ever calling `add_or_schedule_replace_neighbor`, demonstrating the intended invariant that is missing on the neighbor-handshake path.

### Impact Explanation
An attacker who is walked as `cur_neighbor` (any node the victim connects to during its normal peer-walk) can cause the victim to record a public key for a `NeighborAddress` that was never authenticated as matching the gossiped hash. This corrupts the victim's frontier/PeerDB with attacker-chosen key material for an address slot, which downstream logic (StackerDB peer resolution, further outbound handshakes, replacement selection) trusts as authentic. This is an unauthenticated/unauthorized write into persistent node state, matching the "Critical" impact category for unauthenticated writes to state.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to be selected as a walk target (`cur_neighbor`), which happens naturally as any reachable peer participating in the gossip network, and needs to answer the follow-up `GetNeighbors`/`Handshake` sequence — both of which are standard, unprivileged P2P interactions requiring no secret or special role. This is repeatable on every walk cycle.

### Recommendation
Add a `Self::check_handshake_pubkey_hash(&nkey, data, &naddr)` check inside `handle_neighbor_handshake_accept` (or at its call site in `neighbor_handshakes_try_finish`, mirroring `pingback_handshakes_try_finish`) prior to calling `add_or_schedule_replace_neighbor`, and skip/drop the reply (mark the connection dead/broken) on mismatch instead of persisting it.

### Proof of Concept
Add a Rust test in `stackslib::net::neighbors::walk` analogous to existing pingback tests:
1. Construct a `NeighborAddress` `naddr` with `public_key_hash = Hash160::from_node_public_key_buffer(&pubkey_X)`.
2. Build a `HandshakeAcceptData` whose `handshake.node_public_key = pubkey_Y` (Y != X), with a valid signature/preamble as required by the message parsing layer.
3. Call `walk.handle_neighbor_handshake_accept(&mut network, naddr.clone(), &preamble, &data, None)` directly (bypassing the network layer, matching how existing unit tests drive this function).
4. Assert: `network.peerdb_conn()` (or the returned `Neighbor`) shows the stored entry's `public_key == pubkey_Y` for the address, i.e., `resolved_handshake_neighbors.get(&naddr).public_key != naddr.public_key_hash`'s expected preimage — demonstrating the accept was stored despite the hash mismatch.
5. Contrast with an equivalent `pingback_handshakes_try_finish` test using the same mismatched data, which should `continue` (reject) and leave the PeerDB unmodified, confirming path inconsistency.
