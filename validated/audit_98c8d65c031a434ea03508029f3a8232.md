## Title
DPoS voting rewards use per-account (not per-witness, not time-weighted) cycle snapshots, allowing full-cycle reward credit for votes held only part of a cycle and stale-window credit leakage when reallocating votes between witnesses - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`, `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`, `actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java`)

## Summary
This is a structural analog of the Acala "incentive accumulation sandwich" bug class: rewards are accrued for a discrete accounting interval (the DPoS "cycle", driven by `MaintenanceManager.doMaintenance()`), and the per-share (per-vote) reward rate for that interval (`Vi`) is fixed at cycle boundaries rather than time-weighted within the cycle. A voter's payout uses whatever vote weight is recorded in their *latest saved snapshot* (`AccountCapsule.getVotesList()`), applied uniformly across the *entire* `[beginCycle, endCycle)` window in `DelegationStore`/`MortgageService`, regardless of how long within that window the vote was actually held or whether it was reallocated to a different witness partway through.

## Finding Description
Reward accrual works as follows:
- Each cycle, `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(curCycle, witness, witness.getVoteCount())`, which computes a global per-vote reward index `Vi` for that witness for that cycle, using the *witness's total vote count fixed at the start of the cycle*. [1](#0-0) [2](#0-1) 

- A voter's claimable reward for the range `[beginCycle, endCycle)` is computed as `deltaVi * userVote`, where `userVote` comes from a single stored `AccountCapsule` snapshot that applies uniformly to the *entire* multi-cycle span, not per-cycle actual holdings: [3](#0-2) 

- `beginCycle`/`endCycle` bookkeeping is tracked **per address**, not per witness or per vote allocation, in `DelegationStore`: [4](#0-3) 

- Every vote-changing transaction (`VoteWitnessContract`) triggers `mortgageService.withdrawReward(ownerAddress)` **before** applying the new vote allocation, using the *old* vote list to snapshot/settle rewards, then overwrites the account's vote list with the new allocation: [5](#0-4) 

- In `withdrawReward`, when the caller's current cycle equals `beginCycle`, and a stale snapshot exists (or is created) for `endCycle`, the *previous* votes list (including votes that may have already been reassigned to a different witness) is persisted via `repository.updateAccountVote(address, endCycle, accountCapsule)`, to be redeemed once that cycle's `Vi` becomes available later: [6](#0-5) 
The TVM-exposed analog (`WithdrawRewardProcessor`/`VoteRewardUtil`, reachable from any contract via native voting precompiles) implements the identical logic: [7](#0-6) 

Because `Vi(cycle)` for a given cycle is only computed retroactively at the *next* maintenance boundary, and the credited `userVote` is whatever was snapshotted at the moment the account last touched its vote allocation (not a time-weighted average of holdings during the cycle), a voter who casts a vote near the start of a cycle and reallocates/withdraws it *before* that cycle's maintenance runs (i.e., before `Vi` for that cycle is even computed) is nonetheless credited the **full cycle's** reward for that vote weight once it is later computed and redeemed — exactly mirroring Acala's "single deposit captures the whole period's fixed reward" flaw. Additionally, since bookkeeping is per-address (not per-witness), reallocating part of a vote set to a brand-new witness can carry forward a stale `beginCycle` window, causing reward misattribution across witnesses that were never actually voted for during that historical window.

## Impact Explanation
An attacker holding a large amount of already-frozen TRON Power (bandwidth/energy/TP freeze, which itself has a minimum lock but does not need to be re-frozen to change votes) can repeatedly reallocate votes across witnesses at cycle boundaries via `VoteWitnessContract` (or the TVM `voteWitness` native contract), capturing full-cycle `Vi`-based rewards without holding the vote for the complete cycle, and diluting honest long-term voters' share of that witness's fixed cycle reward pool (`delegationStore.addReward`/`payReward`). This directly reduces the rewards honest long-term SR voters receive, causing an unbacked, unfair reward-value transfer to short-term/flash voters — a fund-value-leakage issue impacting the DPoS voting incentive system's fairness guarantees.

## Likelihood Explanation
Exploitation requires only an unprivileged, already-TRON-Power-holding account issuing ordinary `VoteWitnessContract` transactions (or TVM `voteWitness`/`withdrawReward` calls) timed around cycle (`maintenance`) boundaries — no special privilege, no malicious SR/witness collusion, and no freeze/unfreeze cost is required to move votes between witnesses. The attack surface (reachable via a normal broadcast transaction) and lack of any minimum-holding-per-vote-allocation enforcement make this readily reachable, though actual profitability depends on cycle length (mainnet default is hours, not one block) and the size of TRON Power an attacker can marshal, similar to the "assumptions" caveat noted by the judge in the original Acala finding.

## Recommendation
Track vote weight contributions to a witness's reward pool on a time-weighted (or per-cycle-committed) basis rather than crediting the full cycle's `Vi` to whatever vote snapshot exists when reward is finally computed. Specifically:
- Make `beginCycle`/`endCycle`/vote snapshots per (address, witness) pair rather than per address only, so partial reallocations do not inherit stale windows for newly-voted witnesses.
- Require a vote to be present for the witness at both the start and end of a cycle (i.e., unaffected by any vote-change transaction during the cycle) before it is eligible for that cycle's `Vi`-based reward, or otherwise pro-rate reward by actual holding duration within the cycle.

## Proof of Concept
1. Attacker holds unallocated TRON Power (already frozen, no need for further freeze/unfreeze).
2. Near the very end of cycle `N`, attacker calls `VoteWitnessContract` to vote a large amount `V` for witness `W`. `VoteWitnessActuator.countVoteAccount()` snapshots the (empty) prior vote via `mortgageService.withdrawReward()`, then records `V` for `W`. [8](#0-7) 
3. `MaintenanceManager.doMaintenance()` transitions to cycle `N+1`, folding `V` into `W`'s vote total for cycle `N+1` (`delegationStore.setWitnessVote(nextCycle, ...)`). [9](#0-8) 
4. Partway through cycle `N+1` (before the maintenance that computes `Vi(N+1)`), attacker calls `VoteWitnessContract` again to reassign `V` away from `W` to another witness (or clears the vote). Per `withdrawReward`'s branch logic, the *old* vote-for-`W` snapshot (`V`) is persisted keyed to `endCycle = N+2` rather than immediately settled. [10](#0-9) 
5. At a later withdrawal (`withdrawReward`/`queryReward`), `computeReward(beginCycle=N+1, endCycle=N+2, snapshot)` uses `deltaVi` for cycle `N+1` multiplied by `V`, crediting the attacker the **full** cycle `N+1` reward for witness `W`, even though the vote was withdrawn/reallocated before cycle `N+1`'s `Vi` was even computed — diluting `W`'s other voters who held the entire cycle. [3](#0-2)

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    if (dynamicStore.supportAllowNewResourceModel()

      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }

  public static void withdrawReward(byte[] address, Repository repository) {
    if (!VMConfig.allowTvmVote()) {
      return;
    }
    AccountCapsule accountCapsule = repository.getAccount(address);
    long beginCycle = repository.getBeginCycle(address);
    long endCycle = repository.getEndCycle(address);
    long currentCycle = repository.getDynamicPropertiesStore().getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account, repository);
        adjustAllowance(address, reward, repository);
        reward = 0;
      }
      beginCycle += 1;
    }
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      repository.updateBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule, repository);
      adjustAllowance(address, reward, repository);
    }
    repository.updateBeginCycle(address, endCycle);
    repository.updateEndCycle(address, endCycle + 1);
    repository.updateAccountVote(address, endCycle, accountCapsule);
  }
