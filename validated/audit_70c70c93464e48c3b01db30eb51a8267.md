### Title
Unvalidated attachment payloads are unconditionally persisted forever via `insert_instantiated_attachment`, regardless of any confirmed `AttachmentInstance` match - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsDownloader::run`'s `Done` branch stores every downloaded `Attachment` into `AtlasDB` via `insert_instantiated_attachment` unconditionally, even when `find_all_attachment_instances(&attachment.hash())` (computed from the actual received bytes) returns empty, meaning no confirmed on-chain `AttachmentInstance` ever referenced that hash. Because rows inserted with `was_instantiated = 1` are never evicted by any code path (eviction only targets `was_instantiated = 0` rows), an outbound peer selected to serve an `AttachmentRequest` can supply payloads whose hash does not match any committed name-operation hash, and those bytes are stored permanently.

### Finding Description
In `AttachmentsBatchStateMachine::Done`, the downloader iterates `context.attachments.drain()` (attachments fetched over HTTP from a peer selected via `network.get_outbound_sync_peers()`), and for each one: [1](#0-0) 

it recomputes `attachment.hash()` from the bytes it actually received (not the originally requested `content_hash` embedded in the `/v2/attachments/{content_hash}` URL), looks up `find_all_attachment_instances(&attachment.hash())`, and then calls `network.atlasdb.insert_instantiated_attachment(&attachment)` **unconditionally**, regardless of whether `attachments_instances` came back empty. `insert_instantiated_attachment` writes the row with `was_instantiated = 1`: [2](#0-1) 

Rows with `was_instantiated = 1` are never subject to any eviction routine. The only eviction functions in `AtlasDB`, `evict_expired_uninstantiated_attachments` and `evict_k_oldest_uninstantiated_attachments`, both filter explicitly on `was_instantiated = 0`: [3](#0-2) 

So any attachment content that a malicious peer supplies in response to an `AttachmentRequest`, whether or not it corresponds to any confirmed `AttachmentInstance`, is persisted indefinitely, one row per distinct content hash. The `AttachmentRequest`'s URL embeds the requested `content_hash`, but nothing in the shown code path verifies that the *response body*'s hash equals the *requested* `content_hash` before the bytes are accepted into `context.attachments`; the recomputation of `attachment.hash()` at the `Done` stage is used only to decide pairing with a confirmed `AttachmentInstance` for the `resolved_attachments` output, not to gate storage.

### Impact Explanation
A malicious peer holding a legitimate outbound P2P/HTTP connection that gets selected to serve any `AttachmentRequest` (this happens naturally as part of normal Atlas attachment-inventory syncing) can respond with arbitrary content instead of the attachment matching the requested hash. Each such response results in a permanent row in the node's `attachments` table that no confirmed name operation ever committed to, breaking the invariant that stored attachment bytes correspond to a hash referenced by a confirmed `AttachmentInstance`. Since `was_instantiated = 1` rows are never evicted, repeated interactions (one per batch/content-hash the node is legitimately trying to resolve) let the attacker grow the node's Atlas storage without bound tied to any consensus-committed state. This matches the "attachment/BNS mismatch" / unbounded-storage-from-unvalidated-data class of High-severity impact.

### Likelihood Explanation
Preconditions: the attacker must be an outbound peer the node is actively syncing Atlas attachments with (`network.get_outbound_sync_peers()`), which is achievable by any peer that legitimately connects and advertises reachable data URLs — no privileged role or secret needed. The attacker only needs to answer legitimate `AttachmentRequest`s (already naturally directed at it because the node considers it a valid data source) with mismatched payloads. This is repeatable indefinitely across the many attachment instances any node processes over time, and requires no special timing beyond normal Atlas sync behavior.

### Recommendation
Before calling `insert_instantiated_attachment`, verify that `attachment.hash()` equals the `content_hash` of at least one `attachment_instance` actually being resolved (i.e., only persist attachments when `attachments_instances` returned by `find_all_attachment_instances` is non-empty, or otherwise validate against the originally-requested `AttachmentRequest.content_hash`). Discard/penalize peers whose responses fail this check (mark them as faulty, akin to the 404 handling), instead of unconditionally storing arbitrary bytes.

### Proof of Concept
Add a `stackslib::net::atlas::download` test that:
1. Constructs an `AttachmentsBatchStateContext`/`Done` state manually (or drives `AttachmentsDownloader::run` with a mocked peer HTTP client) such that `context.attachments` is populated with several `Attachment { content: <random bytes> }` values whose `hash()` does not match any `AttachmentInstance` inserted into a fresh `AtlasDB` via `queue_attachment_instance`/`mark_attachment_instance_checked`.
2. Call `AttachmentsDownloader::run` (or directly execute the `Done` branch logic) and then assert:
   - `atlas_db.find_all_attachment_instances(&attachment.hash())` returns empty (no confirmed instance), and
   - `atlas_db.find_attachment(&attachment.hash())` (which only matches `was_instantiated = 1` rows) returns `Some(attachment)`, proving the unvalidated content was persisted despite no consensus-committed reference, and that `atlas_db.evict_expired_uninstantiated_attachments()` / `evict_k_oldest_uninstantiated_attachments()` do not remove it (since these only touch `was_instantiated = 0` rows), demonstrating unbounded growth of never-evicted, non-committed attachment rows.

    pub fn evict_k_oldest_uninstantiated_attachments(&mut self, k: u32) -> Result<(), db_error> {
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE hash IN (SELECT hash FROM attachments WHERE was_instantiated = 0 ORDER BY created_at ASC LIMIT ?)",
            params![k],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_expired_uninstantiated_attachments(&mut self) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let cut_off = now - self.atlas_config.uninstantiated_attachments_expire_after as i64;
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE was_instantiated = 0 AND created_at < ?",
            params![cut_off],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
