### Title
Unconditional Overwrite of `AssetIssuedID`/`AssetIssuedName` in `AssetIssueActuator` Permanently Freezes Prior Token's Frozen Supply - (File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java)

### Summary
`AssetIssueActuator` lets any account issue a TRC10 token and records the issued token as the account's "own" asset via `AccountCapsule.setAssetIssuedName`/`setAssetIssuedID`. These fields are later used by `UnfreezeAssetActuator` as the sole lookup key to credit back frozen supply. `validate()` does not check whether the account has already issued a token when `AllowSameTokenName` is enabled, so an account can issue a second token, silently overwriting the pointer to the first token and orphaning any of its still-frozen supply.

### Finding Description
`AssetIssueActuator.execute` always calls: [1](#0-0) 
which unconditionally sets `assetIssuedName`/`assetIssuedID` to the newly issued token, regardless of whether the account previously issued a different token with an outstanding `FrozenSupply`.

`AssetIssueActuator.validate()` only rejects re-issuance under the legacy `AllowSameTokenName == 0` name-collision check: [2](#0-1) 
When `AllowSameTokenName == 1` (the state used on current networks), there is no check preventing the same owner from issuing a second, unrelated token — nothing analogous to "does this account already have `assetIssuedID` set with pending frozen supply."

The frozen supply created at issuance time (`FrozenSupply` -> `Frozen` list, added at lines 96-120 of the same file) is stored on the `AccountCapsule` itself, not keyed by token id: [3](#0-2) 

`UnfreezeAssetActuator.execute` credits the unfrozen amount back using `accountCapsule.getAssetIssuedID()` (or `getAssetIssuedName()` pre-fork) as the *only* reference to which token the frozen balance belongs: [4](#0-3) 

Because `assetIssuedID` is a single scalar field on the account (see the protobuf definition: `bytes asset_issued_ID = 57;`), reissuing a second token overwrites this pointer before the first token's frozen supply is unfrozen. When the unfreeze time later arrives and `UnfreezeAssetActuator` runs, `addAssetAmountV2` is called with the *new* token's id/name, crediting the unfrozen amount to the wrong asset (the second token) instead of the originally frozen token. This mirrors the reported Solidity bug class: a single mutable "token identity" state variable that gets overwritten by an unrelated, later operation, silently redirecting fund flows meant for the original token.

### Impact Explanation
Any token holder amounts that were frozen at issuance (`FrozenSupply`) for the *first* token become permanently unrecoverable as that specific asset: the unfreeze operation will mint/credit the amount into the *second* issued token's balance instead of the first, and there is no path in `UnfreezeAssetActuator` or elsewhere to redirect it back. This is a permanent-freezing-of-funds condition for the first token's frozen supply (the tokens that should have been returned to the issuer's balance of token A are instead credited as token B), a concrete on-chain fund-accounting bug reachable via ordinary user transactions, not requiring any node privilege.

### Likelihood Explanation
Reachable with two ordinary signed transactions from a single asset-issuer account: (1) issue token A with a `FrozenSupply` entry, (2) before the frozen period expires, issue token B (allowed since `AllowSameTokenName` validation does not block repeat issuance by the same owner). No special privileges, precompiles, or witness/committee role is required — only the ability to broadcast `AssetIssueContract` transactions, which any account can do given the `AssetIssueFee`. This is fully within the reachable-by-any-broadcaster class allowed by the rules.

### Recommendation
In `AssetIssueActuator.validate()`, reject issuance if the owner account already has a non-empty `assetIssuedID` (or `assetIssuedName` pre-fork) with any outstanding, unexpired `FrozenSupply`/`Frozen` entries, or alternatively track frozen supply per-token-id rather than as a single unkeyed list on `AccountCapsule`, so that `UnfreezeAssetActuator` can unambiguously credit the correct token regardless of subsequent issuances by the same account.

### Proof of Concept
1. Account `X` sends `AssetIssueContract` for token `A` with a `FrozenSupply` entry (`frozenAmount`, `frozenDays`). `AssetIssueActuator.execute` sets `X.assetIssuedID = A` and appends the `Frozen` entry to `X`'s `frozen_supply` list.
2. Before `A`'s frozen period expires, `X` sends a second `AssetIssueContract` for token `B` (no `AllowSameTokenName==0` collision, since names/ids differ). `AssetIssueActuator.execute` overwrites `X.assetIssuedID = B`.
3. After `A`'s frozen period expires, `X` sends `UnfreezeAssetContract`. `UnfreezeAssetActuator.execute` computes `unfreezeAsset` from the expired `Frozen` entry (originally created for `A`), but calls `accountCapsule.addAssetAmountV2(accountCapsule.getAssetIssuedID()...)`, which now resolves to `B`, crediting the unfrozen balance to token `B` instead of `A`.
4. Token `A`'s frozen supply is effectively lost/misdirected — holders/issuer cannot recover it as token `A`.
