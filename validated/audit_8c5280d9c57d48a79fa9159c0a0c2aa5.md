Audit Report

## Title
Unbounded `receipt_proof: Vec<Vec<u8>>` in Snowbridge inbound queue `submit` processed with a fixed, non-size-scaled weight - (File: `bridges/snowbridge/primitives/verification/src/lib.rs`, `bridges/snowbridge/pallets/inbound-queue/src/lib.rs`, `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`)

## Summary
`Proof.receipt_proof` is declared as a plain `Vec<Vec<u8>>` with no `BoundedVec` wrapper or explicit length/size check, and it is decoded straight from the public, signed `submit` extrinsic in both `inbound-queue` and `inbound-queue-v2` pallets. Both pallets' `submit` calls are weighted with a fixed constant (`Weight::from_parts(70_000_000, 0)` / `3601` PoV bytes for v1, `Weight::from_parts(60_000_000, 0)` / `3774` PoV bytes for v2) that does not scale with the size of the attacker-supplied `event`/`proof`, so the declared weight does not track the actual verification cost.

## Finding Description
`Proof` is defined with an unbounded `receipt_proof: Vec<Vec<u8>>` field: [1](#0-0) 

It flows in from the public `submit` extrinsic in `inbound-queue`, which is weighted with a fixed `T::WeightInfo::submit()` regardless of `event`'s size: [2](#0-1) 

and analogously in `inbound-queue-v2`: [3](#0-2) 

Both weight implementations return fixed constants with no per-byte/per-element scaling component: [4](#0-3) [5](#0-4) 

The proof is passed to `Verifier::verify` → `verify_receipt_inclusion`, which calls into `verify_receipt_proof`, which iterates the entire caller-supplied `proof: &[Vec<u8>]` via `alloy_trie::proof::verify_proof`: [6](#0-5) [7](#0-6) 

I searched the pallets, `bridges/snowbridge/primitives/verification`, and `bridges/snowbridge/primitives/core` for any `BoundedVec`, `MaxEncodedLen`-based cap, or explicit `ensure!(...len() <= MAX...)` guard on `receipt_proof`/`EventProof` and found none — only unrelated `BoundedVec`/`MaxEncodedLen` usages in outbound-queue, system, and beacon-primitive types. `calculate_delivery_cost` in `inbound-queue` does scale the relayer-reward *fee* by `event.encode().len()`, but that is a balance-transfer calculation, not the extrinsic's declared *weight* used for block-weight accounting — the `#[pallet::weight(...)]` annotation on `submit` remains the fixed constant in both pallets.

## Impact Explanation
This matches the gate's "public underpriced work that degrades block production or stalls bridge processing" category. The `submit` extrinsic's declared weight (compute and PoV) is fixed, but the actual execution cost of verifying `receipt_proof` (SCALE-decoding, then trie-node-by-node verification via `alloy_trie::proof::verify_proof`) grows with the number and size of attacker-supplied byte vectors in `receipt_proof`. An attacker who submits a maximally-sized (but still within block/extrinsic length limits) `receipt_proof` pays only the fixed weight, causing execution time and PoV consumption disproportionate to the weight charged, which can degrade BridgeHub block production throughput.

## Likelihood Explanation
`submit` requires only `ensure_signed(origin)`, so any ordinary signed account can call it with no governance, relayer collusion, or off-chain trust assumption needed. The only constraint is the outer block/extrinsic length limit (not found to be pallet-specific to `receipt_proof`), which bounds the input but does not make the weight charge proportional to it — the mismatch between declared weight and actual work remains within that bound.

## Recommendation
- Bound `receipt_proof` with a `BoundedVec` (fixed max node count and max node size reflecting realistic Ethereum receipt-trie depth/branch sizes) instead of a raw `Vec<Vec<u8>>`.
- Reject proofs exceeding the bound before invoking `verify_receipt_proof`/`Verifier::verify`.
- Make `submit`'s declared weight a function of `event.encode().len()` (or `proof.receipt_proof` length/size), analogous to `receive_messages_proof_weight` used in `bridges/modules/messages`, so PoV/compute weight tracks the untrusted input size.

## Proof of Concept
1. Construct an `EventProof` whose `proof.receipt_proof` contains many maximal-size byte vectors (bounded only by outer block/extrinsic length limits) rather than a realistic small number of genuine Ethereum receipt-trie nodes.
2. Submit via `InboundQueue::submit(origin, event)` (v1) or `InboundQueueV2::submit(origin, Box::new(event))` (v2).
3. Observe `verify_receipt_proof` iterates the full attacker-supplied `receipt_proof` before failing verification, while the call is charged only the fixed constant weight (`70_000_000`/`3601` for v1, `60_000_000`/`3774` for v2) shown in `weights.rs`, independent of the actual `receipt_proof` size supplied.

```rust
	fn verify(event_log: &Log, proof: &Proof) -> Result<(), VerificationError> {
		// Refuse to verify any Ethereum-side proof while the beacon light client is halted.
		// Governance halts the light client when it suspects a compromise (e.g. sync committee
		// takeover), at which point any signed headers/receipts must be treated as untrusted.
		// Covers every Verifier consumer, including `inbound_queue_v2::submit` and
		// `outbound_queue_v2::submit_delivery_receipt` (which would otherwise still drain
		// pending relayer rewards while the bridge is halted).
		ensure!(!Self::operating_mode().is_halted(), VerificationError::Halted);

		Self::verify_execution_proof(&proof.execution_proof)
			.map_err(|e| InvalidExecutionProof(e.into()))?;

		Self::verify_receipt_inclusion(
			proof.execution_proof.execution_header.receipts_root(),
			event_log.tx_index,
			&proof.receipt_proof,
			event_log,
		)?;

		Ok(())
	}
```

```rust
pub fn verify_receipt_proof(
	receipts_root: H256,
	tx_index: u64,
	proof: &[Vec<u8>],
) -> Option<ReceiptEnvelope> {
	let key = receipt_trie_key(tx_index);
	let root = B256::from_slice(receipts_root.as_bytes());
	let proof_nodes: Vec<Bytes> = proof.iter().map(|node| Bytes::copy_from_slice(node)).collect();

	// Call verify_proof with None to extract the value from an inclusion proof. For inclusion
	// proofs, alloy_trie returns ValueMismatch with the extracted value in `got`. The proof is
	// already cryptographically verified during this traversal.
	let value = match verify_proof(root, key, None, proof_nodes.iter()) {
		Ok(()) => return None, // Exclusion proof - key does not exist
		Err(ProofVerificationError::ValueMismatch { path, got: Some(v), expected: None })
			if path == key =>
		{
			v.to_vec()
		},
		Err(_) => return None,
	};

	ReceiptEnvelope::decode(&mut value.as_slice()).ok()
}
```
