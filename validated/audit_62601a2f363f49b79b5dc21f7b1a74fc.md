Based on the investigation, I found a structurally analogous bug: a self-referential account-id parameter passed by a caller which the runtime cannot honor, causing the associated value to be permanently burned instead of reaching the intended recipient — the same bug class as the Sophon referral issue (passing the depositor's own address into a beneficiary/referral slot silently defeats the payout).

### Title
`DeleteAccount` beneficiary set to the account being deleted causes the remaining balance to be silently burned instead of paid out - (File: runtime/runtime/src/actions.rs)

### Summary
`DeleteAccountAction::beneficiary_id` is a free-form `AccountId` chosen by the signer, with no validation that it differs from the account being deleted. If a caller supplies its own (about-to-be-deleted) account id as `beneficiary_id` — a pattern that is in fact the *default* used by the test helper `NodeUser::delete_account` — the runtime creates a refund-style `Transfer` receipt to an account that has just been removed from state, and that receipt is then burned rather than returned to anyone.

### Finding Description
`action_delete_account` computes the account's remaining balance and immediately queues a payout receipt to `beneficiary_id`, then removes the account from state in the same call: [1](#0-0) 

There is no check that `beneficiary_id != account_id`; `validate_delete_action` only checks that the id is syntactically valid: [2](#0-1) 

The generated receipt is explicitly excluded from the implicit-account-creation exception that normally lets a `Transfer` action create a fresh account for an unused, well-formed account id — the comment states this is intentional so that account-deletion refunds do not spuriously create accounts: [3](#0-2) 

Because of this, when the beneficiary Transfer receipt is later executed, it hits `AccountDoesNotExist` for an ordinary (non-implicit) `beneficiary_id` that happens to equal the just-deleted account. Since `Receipt::new_balance_refund` is the same "refund" constructor used for deposit/gas refunds (predecessor is `system`), and refund-receipt semantics burn the deposit on failure rather than bouncing it back: [4](#0-3) [5](#0-4) 

the remaining balance is permanently lost. Notably, the codebase's own convenience helper for deleting an account defaults `beneficiary_id` to the signer's own id — i.e., the same account being deleted — showing how natural/likely this self-referential misuse is: [6](#0-5) 

This is the direct structural analog of the Sophon bug: there, passing `address(this)` (the depositor itself) into an external referral parameter silently defeats the reward because the referral mechanism rejects self-referrals. Here, passing the account's own id (the entity being removed) into the beneficiary parameter silently defeats the payout because the target no longer exists when the transfer executes, and the failure path burns funds instead of returning them.

### Impact Explanation
Any account (EOA, contract-controlled account, or account acting as a relayer/vault) that deletes itself with `beneficiary_id` equal to its own account id loses its entire remaining native token balance — the funds are burned rather than transferred to the beneficiary or refunded to any party. This is a concrete, permanent loss of funds directly caused by protocol behavior with no way to recover the balance afterward.

### Likelihood Explanation
Likelihood is non-trivial because this exact pattern (`beneficiary_id == account_id`) is the *default* behavior exercised by the repository's own `NodeUser::delete_account` helper, indicating it is an easy and unremarkable mistake for a wallet, SDK, or contract-driven account-closure flow to make (e.g., "delete and refund myself" being the naive first implementation, analogous to a DeFi contract naively passing `address(this)` as a referral).

### Recommendation
Reject or reinterpret `DeleteAccountAction` when `beneficiary_id == account_id` at validation time (`validate_delete_action` in `runtime/runtime/src/action_validation.rs`), or special-case the beneficiary payout in `action_delete_account` (`runtime/runtime/src/actions.rs`) to detect self-beneficiary and either error out early or route the balance through a path that does not depend on the just-deleted account existing.

### Proof of Concept
1. Fund account `alice.near`.
2. Submit `DeleteAccount { beneficiary_id: "alice.near" }` signed by `alice.near` targeting `alice.near` (this is exactly what `NodeUser::delete_account("alice.near", receiver)` constructs via `delete_account_with_beneficiary_set(signer_id.clone(), receiver_id, signer_id)`).
3. `action_delete_account` computes `account_balance = account.amount()`, pushes `Receipt::new_balance_refund(&"alice.near", account_balance)`, then removes `alice.near` from state (`runtime/runtime/src/actions.rs:364-371`).
4. When the generated Transfer receipt to `alice.near` is later processed, `alice.near` no longer exists; `check_transfer_to_nonexisting_account` (`runtime/runtime/src/actions.rs:857-877`) denies implicit re-creation for this refund case, producing `AccountDoesNotExist`.
5. Because the receipt's predecessor is `system` (refund semantics), the failure burns `account_balance` per `runtime/runtime/src/lib.rs:993-1001` instead of crediting it anywhere — the balance is permanently lost.
