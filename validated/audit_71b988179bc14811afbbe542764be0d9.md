### Title
Cross-contract StackerDB chunk replay via un-bound signature (`SlotMetadata::auth_digest`) - ([File: stackslib/src/net/api/poststackerdbchunk.rs], [File: libstackerdb/src/libstackerdb.rs], [File: stackslib/src/net/stackerdb/db.rs])

### Summary
`StackerDBChunkData`'s signature only commits to `(slot_id, slot_version, data_hash)` via `SlotMetadata::auth_digest` and never includes the target contract identifier. `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` validates the chunk purely against the per-contract `slot_validation.signer` address for the contract given in the URL path, so any previously-observed, validly-signed chunk for contract A can be reposted (by anyone, no key required) to a different configured StackerDB contract B, as long as B assigns the same signer address to the same `slot_id` and B's current slot version is lower than the replayed one.

### Finding Description
`RPCPostStackerDBChunkRequestHandler::try_parse_request` extracts `contract_identifier` solely from the URL path via `request::get_contract_address(captures, "address", "contract")`, independent of the JSON body's `StackerDBChunkData`, which carries no contract field at all. [1](#0-0) 

The signature's authenticated content is computed by `SlotMetadata::auth_digest`, which hashes only `slot_id`, `slot_version`, and `data_hash` — no contract identifier is included. [2](#0-1) 

`try_handle_request` takes the path-derived `contract_identifier` and calls `tx.try_replace_chunk(&contract_identifier, &stackerdb_chunk.get_slot_metadata(), &stackerdb_chunk.data)`. [3](#0-2) 

`try_replace_chunk` looks up `slot_validation` (which holds the configured signer address for that slot) *for the contract passed in*, then calls `slot_desc.verify(&slot_validation.signer)`. If the same `StacksAddress` happens to be configured for `slot_id` in contract B as it is in contract A, a chunk signed once for A verifies successfully for B too, since the signature never encodes which contract it authorizes. [4](#0-3) 

Because StackerDB chunk contents are public (served via chunk-read endpoints and gossiped as `StackerDBPushChunk` over P2P), an unprivileged remote attacker who never holds any private key can simply capture a chunk that a signer legitimately published for contract A and POST the identical bytes to contract B's `/v2/stackerdb/:address/:contract/chunks` endpoint. If contract B has the same signer assigned to the same slot with a current version lower than the replayed `slot_version`, and the replayed version does not exceed `max_writes`, `try_replace_chunk` accepts it, overwrites B's slot 0 with A's data, and on success the node also relays it network-wide as a `StackerDBPushChunk` gossip message. [5](#0-4) 

The `handle_unsolicited_StackerDBPushChunk`/`validate_received_chunk` gossip path exhibits the identical flaw: it resolves `smart_contract_id`-specific `get_slot_signer` and verifies `slot_metadata.verify(&addr)`, again with no contract binding in the signature itself. [6](#0-5) 

None of the existing guards (chunk-size cap, version-must-increase, `max_writes` cap, signer-address check) verify that the signature was produced *for this specific contract*; they only check that the recovered address matches whatever address is configured for that slot in the target contract. This breaks the intended invariant that a signature authorizes writes only to the contract context it was created for.

### Impact Explanation
An unprivileged party (no private key, no special role — anyone who can observe a public chunk and send an HTTP POST or gossip a P2P message) can forge a write to a StackerDB slot in a contract that the actual signer never targeted or approved, provided the node's configuration happens to assign the same address to the same slot index across two different StackerDB contracts (a realistic scenario across reward-cycle signer-set contracts or overlapping committee assignments). This is an unauthenticated/unauthorized write to StackerDB state, and on success it is also relayed network-wide via `StackerDBPushChunk`, propagating the forged/misplaced chunk to other peers. This matches the Critical impact category ("unauthenticated/unauthorized write to state or StackerDB, network-wide propagation of forged data"), and it is repeatable for every future increasing `slot_version` up to `max_writes`.

### Likelihood Explanation
Preconditions: (1) two StackerDB contracts configured on the target node, (2) the same `StacksAddress` assigned to the same `slot_id` in both, (3) the attacker has observed one contract's published/gossiped chunk (trivially available since chunks are public). No admin secret, no privileged role, and no key material of the signer are needed by the attacker — only knowledge of a publicly broadcast message. The attacker cost is a single HTTP POST or P2P push replay. Cross-cycle signer-set contracts (e.g., successive reward-cycle StackerDB contracts) frequently retain overlapping signer committees at matching indices, making the same-slot/same-signer precondition realistically achievable, though it depends on node/contract configuration rather than being universal.

### Recommendation
Bind the contract identifier into the signed digest. Modify `SlotMetadata::auth_digest` (and the corresponding `sign`/`verify`/`recover_pk` call sites in `libstackerdb/src/libstackerdb.rs`) to include the `QualifiedContractIdentifier` (or a stable hash of it) in the hashed preimage, and update `StackerDBChunkData::get_slot_metadata`/`sign`/`verify` call sites throughout `stackslib` and `stacks-signer` to pass the target contract context. This requires a protocol/version bump since it changes the wire-signed content.

### Proof of Concept
Rust test in `stackslib::net::api::tests::poststackerdbchunk` (or `stackslib::net::stackerdb::tests::db`):
1. Create two StackerDB contracts, A and B, each with `slot_id = 0` assigned to the same `StacksAddress` derived from private key `pk`.
2. Build `StackerDBChunkData { slot_id: 0, slot_version: 1, data: b"for-A".to_vec(), .. }`, sign it with `pk` (`chunk.sign(&pk)`).
3. Call `tx.try_replace_chunk(&contract_A, &chunk.get_slot_metadata(), &chunk.data)` — assert `Ok(())`.
4. Without re-signing, call `tx.try_replace_chunk(&contract_B, &chunk.get_slot_metadata(), &chunk.data)` — assert this **also** returns `Ok(())`, proving the identical signature/chunk intended for A was accepted for B.
5. Equivalent HTTP-level PoC: instantiate `RPCPostStackerDBChunkRequestHandler`, POST the JSON body to `/v2/stackerdb/<addrB>/<contractB>/chunks`, and assert `StackerDBChunkAckData.accepted == true`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }
