### Title
Leftover `PromiseYieldReceipt`/`PromiseYieldStatus`/yield-id state survives `DeleteAccount` and can be resumed under a recreated account of the same name, letting a former tenant inject a self-authorized callback into a new tenant's contract - ([File: core/store/src/utils/mod.rs], [File: runtime/runtime/src/ext.rs])

### Summary
`remove_account` (invoked by `action_delete_account`) purges `Account`, `ContractCode`, access/gas keys and `ContractData`, but never touches `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::PromiseYieldTimeout`, or `TrieKey::YieldIdToDataId`/`DataIdToYieldId` entries scoped to that account. Since these keys are indexed purely by account-name (`receiver_id`) with no incarnation/generation binding, a `PromiseYieldReceipt` created by a prior occupant of an account name is still resumable after the account is deleted and a new account is created under the identical name, causing the old occupant's self-authorized callback to execute against the new occupant's live contract state.

### Finding Description
`remove_account` at [1](#0-0)  removes `TrieKey::Account`, `TrieKey::ContractCode`, all access keys/gas-key nonces, and `TrieKey::ContractData`, but contains no logic that iterates or removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, the `PromiseYieldTimeout` queue entry, or the `YieldIdToDataId`/`DataIdToYieldId` mappings for the deleted `account_id`.

`TrieKey::PromiseYieldReceipt { receiver_id, data_id }` is keyed only by the account name string and the `data_id`, with no concept of "which incarnation of this account name" created it: [2](#0-1) .

`submit_promise_resume_data` — the host-function backend invoked from `promise_yield_resume` — looks the receipt up solely by `self.account_id` (the account currently executing the receipt) and the caller-supplied `data_id`, with no check tying it to the account's "creation epoch" or any other incarnation marker: [3](#0-2) . If `has_promise_yield_receipt`/`has_promise_yield_status` return true, it unconditionally creates a `PromiseResume` receipt.

When that resume receipt is processed, `get_promise_yield_receipt(state_update, account_id, data_receipt.data_id)` again keys only by account name, retrieves whatever `PromiseYieldReceipt` is stored (which may be the pre-deletion tenant's), and executes it via `apply_action_receipt`: [4](#0-3) . That yield receipt's `predecessor_id == receiver_id == account_id` (a self-call), which is the trust boundary most NEAR contracts rely on (`assert_self()`/`#[private]`) to gate sensitive internal callback logic.

Exploit flow:
1. Tenant1 legitimately controls `slot.factory.near` and calls `promise_yield_create(method_name, arguments, ...)`, obtaining `data_id`. This persists a `PromiseYieldReceipt{receiver_id: "slot.factory.near", data_id}` whose single `FunctionCall` action targets the account itself with tenant1-chosen `method_name`/`arguments`.
2. The factory later runs `DeleteAccount` on `slot.factory.near` (legitimate marketplace/factory lifecycle) — `remove_account` wipes the account/keys/code/data but leaves the `PromiseYieldReceipt` (and status/timeout/yield-id) entries behind.
3. The factory `CreateAccount`s `slot.factory.near` again and deploys the (typically identical, templated) tenant contract for tenant2, adding tenant2's keys.
4. Tenant1 (who still knows `data_id` from step 1, and never needed a key on the account to have obtained it) invokes any public entry point on tenant2's freshly deployed contract that forwards a caller-supplied `data_id` into `promise_yield_resume` (a standard, expected usage pattern for the yield/resume capability model). `submit_promise_resume_data` matches on `self.account_id == "slot.factory.near"` and the leftover `data_id`, so it succeeds and schedules a `PromiseResume`.
5. That resume causes the runtime to fetch and execute the *stale* `PromiseYieldReceipt`, invoking `method_name`/`arguments` chosen by tenant1 as a self-call (`predecessor_id == receiver_id == slot.factory.near`) against tenant2's now-deployed contract/state — bypassing any access-key or `predecessor_id`-based authorization the new contract relies on for that "private" method.

None of the existing checks (signature/nonce/access-key permission, gas metering, storage staking, size limits) address this because the resume path is entirely receipt-internal state lookup keyed by account name; there is no invalidation of yield state on `DeleteAccount`, and no revalidation that the currently-live account is the same "instance" that created the yield.

### Impact Explanation
This is an authorization-escalation-across-promises bug: an unprivileged former tenant (who holds no keys on the recreated account) can inject an arbitrary, self-authorized `FunctionCall` (with attacker-chosen method name and arguments, decided before the account was ever recreated) into a new tenant's live contract, spoofing the `predecessor_id == receiver_id == current_account_id` trust boundary that private/self-only methods depend on. In a factory/marketplace pattern reusing identical contract templates across tenants (as posited), this lets tenant1 trigger tenant2's private callback methods (e.g., fund-release, settlement, escrow-finalization logic) without tenant2's or the factory's authorization, potentially moving or corrupting tenant2's post-recreation funds/state. This matches the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Preconditions: (1) an account name is deleted and recreated (a normal factory/marketplace pattern, not requiring any special privilege — any two ordinary users interacting with a shared factory contract can trigger this lifecycle); (2) the new contract exposes a caller-supplied-`data_id` resume entry point, which is the expected/idiomatic use of the yield-resume capability model; (3) the reused/templated contract has a matching method name from the old `promise_yield_create` call that does something sensitive when invoked as a self-call. Cost to the attacker is a single `promise_yield_create` call plus a later `promise_yield_resume`-triggering transaction — ordinary transaction fees only. The attack is deterministic and repeatable in any deployment matching this account-reuse/templated-contract pattern.

### Recommendation
Purge all promise-yield-related state for an account when it is deleted: in `remove_account` (or in `action_delete_account`), iterate and remove `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, and any `YieldIdToDataId`/`DataIdToYieldId` mappings scoped to `account_id` (mirroring the existing access-key/contract-data cleanup), and additionally invalidate/skip any already-enqueued `PromiseYieldTimeout` entries pointing at the deleted account. As defense in depth, consider binding yield state to an account "incarnation" identifier (e.g., a monotonically increasing per-account creation nonce) so that even undiscovered leftover entries cannot be resumed against a different incarnation of the same account name.

### Proof of Concept
Test-loop integration test (analogous to existing tests in `test-loop-tests/src/tests/yield_resume.rs` and `yield_timeouts.rs`):
1. Create factory + template contract; have factory `CreateAccount` a sub-account `slot.factory.near` and deploy the template, granting tenant1 a key (or make it a self-owned tenant account for simplicity).
2. As tenant1, call `promise_yield_create` with `method_name = "sensitive_self_only_method"` and crafted `arguments`; capture the returned `data_id` (e.g., via `call_yield_create_return_data_id`).
3. Assert via `get_yield_data_ids_in_state`-style helper (as in `test-loop-tests/src/tests/yield_timeouts.rs:122-151`) that the `PromiseYieldReceipt` exists in state.
4. Issue `DeleteAccount` for `slot.factory.near` (beneficiary = factory), then `CreateAccount` + `DeployContract` for the same account name with tenant2 as the new controller (new access key, fresh state, e.g. a fresh balance simulating tenant2's deposit).
5. Assert (bug reproduction) that the stale `PromiseYieldReceipt` entry for `data_id` is *still* present in state after recreation using the same state-iteration helper.
6. As tenant1 (using a separate account with no key on the recreated `slot.factory.near`), invoke a public resume-forwarding method on the newly deployed contract instance with the old `data_id`, and assert `promise_yield_resume` returns success (`1`) and that `"sensitive_self_only_method"` executes against tenant2's new account state (e.g., check a storage side-effect or balance change attributable to tenant1's original arguments) — demonstrating a self-call was triggered without tenant2's or the factory's authorization.
7. Expected (fixed) behavior: after adding cleanup of yield-related trie keys to `remove_account`, step 5's assertion should show no leftover `PromiseYieldReceipt`, and step 6's resume call should return `0` (failure), with no side effects on tenant2's contract.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
