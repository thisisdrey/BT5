### Title
Repository-wide reference write lock has no fairness guarantee, allowing cheap push-loop griefing to DoS all other writers to a repository - (File: `internal/praefect/transactions/manager.go`, `internal/praefect/datastore/lock_manager.go`)

### Summary
Praefect's serialized-write feature introduces a single, repository-scoped write lock (`repository_reference_write_locks`, keyed only by `virtualStorage|relativePath`) that must be held by exactly one in-flight write transaction at a time before any node is allowed to advance its `reference-transaction` hook past the `PREPARING` phase. This is architecturally the same "single shared status/slot" pattern as the reported SteadeFi bug: any actor able to reach the resource (there, `Open`→`Deposit`/`Withdraw`; here, "lock free"→"lock held") can flip it cheaply and repeatedly, starving every other legitimate caller that needs the same slot, with no fee, cost scaling, or fairness mechanism to bound the griefing.

### Finding Description
`lockRepoForTransaction` acquires the write lock on `PREPARING_PHASE` via `mgr.repoWriteLockMgr.Lock`, and it is only released on `COMMITTED_PHASE` (or on a failed `PREPARING`/`PREPARED` phase): [1](#0-0) 

`RepoReferenceWriteLockManager.Lock` uses a plain UPSERT-with-guard pattern in Postgres to try to grab the row; failing that, the caller registers on a notification channel and retries once notified: [2](#0-1) 

Crucially, when the lock is released, **all** waiters are woken simultaneously with no queue ordering: [3](#0-2) 

Every waiter then races to re-run the same UPSERT (`tryLock`), with no notion of arrival order, priority, or backoff fairness: [4](#0-3) 

Because the lock ID is scoped only to `virtualStorage|relativePath` and not to the requesting user/token, any client with ordinary write (push) access to a repository can drive a tight loop of trivial reference-update pushes (e.g., no-op force-updates or single small-ref pushes that transfer no new objects) against that repository. Each push cycles the lock through `PREPARING`→`PREPARED`→`COMMITTED` quickly and then immediately re-registers for the next acquisition. A locally-automated attacker with low per-request latency can consistently win the thundering-herd race against legitimate, network-latency-bound clients pushing to the same repository, starving them out of the shared write lock indefinitely — exactly the same "cheap operation flips shared status and blocks everyone else" pattern as the original report, just realized through a lock row instead of a `status` enum.

### Impact Explanation
While one attacker holds/re-wins the lock, all other write RPCs to that repository (branch/tag updates, other users' pushes, GitLab-driven merges, etc.) that go through the reference-transaction hook queue behind the Postgres row and effectively stall, producing denial of service for every legitimate writer of the shared repository. Unlike a crash or resource exhaustion bug, this requires no elevated privilege — only the write access an ordinary contributor already has to push to the repo — and can be sustained indefinitely at negligible cost to the attacker (small, cheap ref-update pushes) versus availability loss for all collaborators.

### Likelihood Explanation
The write-lock code path is reachable directly from an ordinary user's push once `featureflag.PraefectSerializedWrite` is enabled — it fires on every `reference-transaction` hook invocation triggered by a normal `git push`/branch update, with no extra RPC or privileged interface required: [5](#0-4) 

The lack of fairness in the notification fan-out (`Notified` broadcasting to all waiters, `tryLock`'s racey UPSERT) is a design gap rather than a rare edge case, so any attacker automating rapid, minimal pushes can realistically exploit it once the feature is active.

### Recommendation
- Introduce fairness to the lock hand-off (e.g., FIFO queue of waiters per `lockID`, or token/ticket-based ordering) instead of broadcasting release to all waiters and letting them race the UPSERT.
- Consider rate-limiting or per-identity throttling of `PREPARING_PHASE` lock acquisitions for the same repository, so a single actor cannot dominate reacquisition after every release.
- Bound the maximum time/iterations a single client can be granted priority re-acquisition of the same repository lock in a short window.

### Proof of Concept
1. Enable `featureflag.PraefectSerializedWrite` and target a repository `R` with write access as an ordinary (non-admin) user.
2. Run a tight local loop that repeatedly performs the smallest possible ref-update push to `R` (e.g., toggling a branch between two known commits with `--force`, so no new objects need transferring) back-to-back with no delay between iterations.
3. Concurrently, have a normal, network-latency-bound client attempt legitimate pushes to `R`.
4. Because the lock manager (`internal/praefect/datastore/lock_manager.go`) wakes all waiters on release and lets them race a plain UPSERT with no ordering, and the attacker's loop re-registers/re-attempts far faster than a remote legitimate client can, the legitimate client's pushes are starved from acquiring `WriteLockManager.Lock` and stall until the attacker stops, demonstrating repository-wide DoS via a griefing loop of cheap, fee-less operations.

func (mgr *Manager) lockRepoForTransaction(ctx context.Context, transactionID uint64, storageName, repoRelativePath string,
	phase gitalypb.VoteTransactionRequest_Phase,
) error {
	if featureflag.PraefectSerializedWrite.IsDisabled(ctx) {
		return nil
	}

	switch phase {
	case gitalypb.VoteTransactionRequest_PREPARING_PHASE:
		lock, err := mgr.repoWriteLockMgr.Lock(ctx, storageName, repoRelativePath, transactionID)
		if err != nil {
			return fmt.Errorf("try lock: %w", err)
		}
		mgr.repoLocks.Store(transactionID, lock)

	case gitalypb.VoteTransactionRequest_PREPARED_PHASE, gitalypb.VoteTransactionRequest_COMMITTED_PHASE:
		v, ok := mgr.repoLocks.Load(transactionID)
		if !ok {
			// No Preparing was cast for this transaction. This happens when Git itself drives
			// the reference-transaction hook on a Git build that doesn't emit "preparing"
			// (i.e. pre-2.54). Skip lock work; serialization is dormant for this path
			// until GIT_VERSION_PREV is bumped past 60d8c1e9.
			mgr.logger.WithFields(log.Fields{
				"transaction.id": transactionID,
				"phase":          phase.String(),
			}).DebugContext(ctx, "skipping lock check: no preparing phase recorded")
			return nil
		}
		lock := v.(datastore.RepoLock)
		if err := lock.Renew(ctx); err != nil {
			return err
		}
	}
	return nil
}

// Notified signals all goroutines waiting on the released lock_id by closing their channels,
// then removes them from the waiters map.
func (d *lockReleaseDispatcher) Notified(n glsql.Notification) {
	lockID := LockID(n.Payload)
	d.mu.Lock()
	chs := d.waiters[lockID]
	delete(d.waiters, lockID)
	d.mu.Unlock()
	for _, ch := range chs {
		close(ch) // wake all waiters
	}
}

// Lock acquires the write lock for a given virtualStorage, relativePath and txnID,
// blocking until the lock is acquired or ctx is cancelled.
func (r *RepoReferenceWriteLockManager) Lock(ctx context.Context, virtualStorage, relativePath string, txnID uint64,
) (RepoLock, error) {
	for {
		res := r.tryLock(ctx, virtualStorage, relativePath, txnID)
		if res.Err != nil {
			return RepoLock{}, res.Err
		}
		if res.Acquired {
			return RepoLock{Unlock: res.Unlock, Renew: res.Renew}, nil
		}

		select {
		case <-ctx.Done():
			res.Deregister()
			return RepoLock{}, fmt.Errorf("wait for lock: %w", ctx.Err())
		case <-res.NotificationCh:
			// wait for the lock to release
		}
	}

func (r *RepoReferenceWriteLockManager) tryLock(ctx context.Context, virtualStorage, relativePath string, txnID uint64,
) tryLockResult {
	lockID := repoLockID(virtualStorage, relativePath)
	// Register for a lock release notification before attempting the INSERT, so
	// that no release event can be missed between a failed attempt and the caller
	// beginning to wait, thus eliminating the race window between contention detection
	// and notification.
	notificationCh, deregister := r.handler.RegisterForLockRelease(lockID)

	query := `
INSERT INTO repository_reference_write_locks as locks (lock_id, holder_txn_id, expired_at)
VALUES ($1, $2, NOW() + $3::interval)
ON CONFLICT (lock_id) DO UPDATE
  SET holder_txn_id = EXCLUDED.holder_txn_id,
      expired_at    = EXCLUDED.expired_at
WHERE locks.expired_at < NOW() OR locks.holder_txn_id = $2
RETURNING lock_id, holder_txn_id, expired_at;`
