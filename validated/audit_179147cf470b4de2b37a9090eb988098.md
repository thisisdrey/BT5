### Title
Unbounded array allocation from attacker-controlled length word in TVM precompiled-contract input parsing — potential node OOM/crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array` and `PrecompiledContracts.extractBytesArray` read a "count" value directly out of the ABI-encoded calldata (`words[offset].intValueSafe()`) and immediately use it to allocate a two-dimensional `byte[][]` array (`new byte[len][]`) with no upper bound check on `len` before the allocation. [1](#0-0) 

### Finding Description
`extractBytes32Array` takes a `len` derived from an attacker-supplied `DataWord` in the precompiled-contract call data and allocates `new byte[len][]` with no sanity/limit check on `len` before the allocation happens: [2](#0-1) 

`extractBytesArray` follows the identical pattern — it reads `len` from `words[offset].intValueSafe()` and allocates `byte[len][]` before any per-element bounds validation is applied: [3](#0-2) 

Both helpers are invoked from precompiled-contract `execute()` paths that are reachable directly by any account issuing a `TriggerSmartContract`/`CALL` to the relevant precompile address, or indirectly through any deployed contract that calls into it. Because `DataWord.intValueSafe()` only clamps to `Integer.MAX_VALUE` rather than validating against the actual remaining calldata size, an attacker can craft a single word (e.g. a large hex value) that decodes to a very large "count," causing the JVM to attempt an allocation of an array with billions of null `byte[]` references (an `Integer.MAX_VALUE`-sized `byte[][]`) or subsequently loop `len` times performing further `arraycopy`/`extractBytes` allocations. This mirrors the CVE-2019-20012 bug class: a length/count value taken directly from untrusted input is used to size a memory allocation without validating it against the actual available data, leading to excessive/uncontrolled memory allocation.

This differs from the constant-bounded precompiled-contract handling elsewhere in the same file — e.g. `ModExp.execute` explicitly checks parsed lengths against an `UPPER_BOUND` before use: [4](#0-3) 
No equivalent bound exists for the `len` values consumed in `extractBytes32Array` / `extractBytesArray`.

### Impact Explanation
An attacker who can call a TVM precompiled contract that uses `extractBytes32Array`/`extractBytesArray` (via `TriggerSmartContract` or an intermediate contract) can trigger an attempted multi-gigabyte (or `Integer.MAX_VALUE`-sized) array allocation inside the SR/full node's JVM. This can throw an `OutOfMemoryError` in the execution thread, and depending on how that error propagates through the TVM execution/`Runtime` machinery, it can destabilize or crash the node process, denying service to legitimate users — a reachable node-crash/halt condition from a single, unprivileged, signed transaction or contract call.

### Likelihood Explanation
The path is reachable by any unprivileged account: crafting the calldata word that decodes to a large `len` requires no special privilege, only the ability to send a transaction invoking the affected precompile. The main uncertainty is which precompiled contract(s) actually invoke `extractBytes32Array`/`extractBytesArray` with attacker-fully-controlled offsets before other bounds are enforced elsewhere in the call chain (this could not be fully re-verified due to the iteration limit), so likelihood should be validated against the exact invocation context (e.g. `SIGNATURE_VERIFY_TYPE`/multi-signature precompiles that consume these helpers).

### Recommendation
Add explicit upper-bound and calldata-size validation on `len` before allocating in `extractBytes32Array` and `extractBytesArray` (and similarly `extractSigArray`), analogous to the `UPPER_BOUND` check already used in `ModExp`. Validate that `offset + len * elementStride` does not exceed `data.length`/`words.length` before allocation, and reject (return an execution failure) rather than allocate when the declared count is inconsistent with the actual supplied data size.

### Proof of Concept
1. Construct a `TriggerSmartContract` transaction that calls a precompiled contract address using `extractBytes32Array`/`extractBytesArray` for its argument decoding.
2. In the ABI-encoded calldata, set the word at the expected "array length" offset to a very large value (e.g. `0x7fffffff`), while providing calldata far shorter than what such a length would require.
3. Broadcast the transaction; on execution, `PrecompiledContracts.extractBytes32Array`/`extractBytesArray` computes `len = words[offset].intValueSafe()` and immediately executes `new byte[len][]`, attempting a huge allocation.
4. Repeated or single such calls can induce `OutOfMemoryError` in the node's TVM execution thread, potentially destabilizing the node.

Note: I was not able to fully trace, within the available iterations, the exact precompiled-contract dispatch entries that call `extractBytes32Array`/`extractBytesArray` at runtime (e.g., confirming whether an upstream bounds check already limits `offset`/`len` in every caller). This should be verified against `PrecompiledContracts.getContractForAddress` and each precompile's `execute()` method before treating this as fully confirmed.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
