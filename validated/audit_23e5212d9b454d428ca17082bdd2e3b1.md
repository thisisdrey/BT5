### Title
Legacy slash/reward path into DAP staging silently burns dust when the account is unfunded, unlike the fungible path which defensively guards it - ([File: substrate/frame/dap/src/lib.rs])

### Summary
`pallet_dap` has two parallel `OnUnbalanced` entry points that feed the same `staging_account()` before `on_idle` drains it into the buffer: the fungible-trait path (`impl<T: Config> OnUnbalanced<CreditOf<T>> for Pallet<T>`) and the legacy-`Currency` path (`DapLegacyAdapter`). The two paths are not consistent in how they truncate/handle dust relative to the existential deposit, mirroring the Notional bug where one code path (`updateAccountDebt`) truncated dust while the sibling path (`_updateTotalSecondaryDebt`) did not.

### Finding Description
The primary path uses `T::Currency::resolve(&staging, amount)`, which is fallible: if `staging` is unfunded and the incoming credit is below ED, `resolve` returns an `Err`, and the pallet explicitly guards this with a `defensive!` log (funds are effectively dropped/burned, but the failure is surfaced): [1](#0-0) 

The legacy path, `DapLegacyAdapter`, instead calls `C::resolve_creating(&staging, amount)`, which is documented in the sibling `accumulate-and-forward` pallet's equivalent adapter as being "infallible" but **silently burning** the imbalance whenever the destination is below ED and unfunded: [2](#0-1) 

Compare this to the twin implementation in `pallet_accumulate_and_forward::LegacyAdapter`, which explicitly checks `C::total_balance(&accumulation_account).saturating_add(numeric_amount) < C::minimum_balance()` and fires a `defensive!` warning *before* calling `resolve_creating`, because the author recognized that `resolve_creating` silently burns dust in that scenario: [3](#0-2) 

`DapLegacyAdapter::on_nonzero_unbalanced` has no such pre-check. It calls `C::resolve_creating` directly without verifying that `staging` is sufficiently funded, and without emitting any `defensive!` warning or event when the deposit would land below ED and be discarded. This is the direct structural analog to the audit finding: one accounting path (`Pallet<T>` fungible `on_nonzero_unbalanced`) truncates/guards dust explicitly, while the sibling path handling the *same* underlying value (slashes/burns routed through legacy `Currency::slash`, e.g. from `pallet_referenda` or other legacy-`Currency` consumers configured with `type Slash = DapLegacyAdapter<Runtime, Balances>`) does not apply the same guard, silently dropping funds instead of defensively logging or reverting.

### Impact Explanation
Any pallet still using the legacy `Currency` trait (explicitly called out in the doc comment: `pallet_referenda`) that is wired to slash/burn into `DapLegacyAdapter` can have its slashed/burned funds silently disappear from total issuance accounting expectations if the `staging_account` happens to be below ED at the time (e.g., right after `on_idle` drains it to exactly ED, or on a freshly deployed chain before the staging account is funded). Because `resolve_creating` reports success unconditionally, the pallet has no way to detect or recover the loss, unlike the primary fungible path which at least defensively flags it. This breaks the invariant that "any burn source wired to [the buffer] ... and its explicit budget allocation share" (per the doc comment on `buffer_account`) is fully accounted for, causing under-accounted dust to accumulate invisibly — a public, permissionless-to-trigger accounting inconsistency in a treasury/reward-payout style component.

### Likelihood Explanation
This requires no privileged actor: it is triggered purely by the natural low-balance state of `staging_account` (which only holds ED between `on_idle` drains) combined with any legacy-`Currency`-based slash/burn event routed to `DapLegacyAdapter`. Since `on_idle` intentionally drains `staging` down to exactly ED after each cycle, there is a window in every block cycle where a legacy slash smaller than the gap to ED (which is 0, since staging is left at exactly ED) is fine, but any sequence where the account transiently sits below ED (e.g., before first funding, or if `on_idle` weight is exhausted and drains partially) would result in a silent burn on the legacy path. The lack of a defensive check compared to its sibling pallet's identical use case increases the likelihood this was an unintentional omission rather than a considered design choice.

### Recommendation
Add the same pre-check used in `pallet_accumulate_and_forward::LegacyAdapter` to `DapLegacyAdapter::on_nonzero_unbalanced`: before calling `C::resolve_creating`, verify `C::total_balance(&staging).saturating_add(numeric_amount) >= C::minimum_balance()` and emit a `defensive!` warning (or better, refuse to silently lose funds) when this condition is not met, so both `OnUnbalanced` paths into DAP staging behave consistently with respect to dust/ED truncation.

### Proof of Concept
1. Deploy a runtime with `pallet_dap` configured, `staging_account()` unfunded (balance = 0), and a legacy-`Currency` consumer (e.g. a mock `pallet_referenda`-style pallet) with `type Slash = DapLegacyAdapter<Runtime, Balances>`.
2. Trigger a legacy slash of an amount less than `ExistentialDeposit` (e.g. via `Currency::slash`), producing a `NegativeImbalance` passed into `DapLegacyAdapter::on_nonzero_unbalanced`.
3. Observe: `C::resolve_creating(&staging, amount)` returns without funding `staging` (balance remains 0), and `total_issuance` decreases by the slashed amount with no corresponding credit anywhere — the funds are burned with no `Unexpected`/`defensive!` event, unlike the fungible `Pallet<T>::on_nonzero_unbalanced` path which would have logged `defensive!("🚨 Failed to deposit slash to DAP staging account...")` in the same scenario via `T::Currency::resolve`'s `Err` branch.
4. Compare against `pallet_accumulate_and_forward::LegacyAdapter::on_nonzero_unbalanced`, which under the identical scenario emits `defensive!("🚨 LegacyAdapter: deposit to accumulation account will be silently burned...")` before calling `resolve_creating`, demonstrating the missing guard is an inconsistency between the two pallets' otherwise-identical legacy adapters.

impl<T: Config> OnUnbalanced<CreditOf<T>> for Pallet<T> {
	fn on_nonzero_unbalanced(amount: CreditOf<T>) {
		let staging = Self::staging_account();
		let numeric_amount = amount.peek();

		// Funds land in the staging account; `on_idle` will drain them into the buffer and
		// deactivate them there.  Deactivation is intentionally deferred so that active issuance
		// does not flicker down-then-up within the same block.
		let _ = T::Currency::resolve(&staging, amount).inspect_err(|_| {
			defensive!(
				"🚨 Failed to deposit slash to DAP staging account - funds burned, it should never happen!"
			);
		});

impl<T: Config, C> OnUnbalanced<LegacyNegativeImbalance<T::AccountId, C>> for LegacyAdapter<T, C>
where
	C: Currency<T::AccountId>,
{
	fn on_nonzero_unbalanced(amount: LegacyNegativeImbalance<T::AccountId, C>) {
		let accumulation_account = Pallet::<T>::accumulation_account();
		let numeric_amount = amount.peek();
		// NOTE: `resolve_creating` is "infallible" because it returns `()`, but it silently burns
		// the imbalance if it is less than ED and the destination is empty. We guard against this
		// by making misconfigured runtimes clearly visible. See crate-level docs for the
		// pre-funding requirement.
		if C::total_balance(&accumulation_account).saturating_add(numeric_amount) <
			C::minimum_balance()
		{
			frame_support::defensive!(
				"🚨 LegacyAdapter: deposit to accumulation account will be silently burned — \
				 ensure the accumulation account is pre-funded with at least ED!"
			);
		}
		C::resolve_creating(&accumulation_account, amount);
		log::debug!(
			target: LOG_TARGET,
			"💸 Deposited (legacy) {numeric_amount:?} to accumulation account"
		);
	}
}
