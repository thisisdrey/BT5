### Title
Stale postponed `DeployContract` receipts survive `DeleteAccountAction` and execute on a recreated account of the same name, allowing unauthorized contract takeover - (File: `core/store/src/utils/mod.rs` / `runtime/runtime/src/lib.rs` / `runtime/runtime/src/actions.rs`)

### Summary
`remove_account` (used by `action_delete_account`) only removes `TrieKey::Account`, `TrieKey::ContractCode`, `TrieKey::AccessKey`/gas keys, and `TrieKey::ContractData`, but never purges `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount` entries for the deleted account. If an attacker leaves a self-addressed postponed `ActionReceipt` containing `DeployContract` pending on their own account (predecessor_id == receiver_id == attacker account) and then deletes that account before the awaited `DataReceipt` arrives, the stale entries remain keyed by the plain `AccountId` string. When the account name is later reused by an unrelated party and the delayed `DataReceipt` finally arrives, `process_receipt` looks the postponed receipt up purely by `AccountId` and executes it against whatever account currently occupies that name.

### Finding Description
`process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) stores an incoming `ActionReceipt` under `TrieKey::PostponedReceipt{receiver_id, receipt_id}` plus `TrieKey::PostponedReceiptId{receiver_id, data_id}` and `TrieKey::PendingDataCount{receiver_id, receipt_id}` whenever any `input_data_ids` are not yet in state (`core/store/src/utils/mod.rs:120-143`, `runtime/runtime/src/lib.rs:1608-1655`). These keys are addressed solely by `AccountId` string (`core/primitives/src/trie_key.rs:214-219`), with no account "generation"/nonce component.

`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` (`core/store/src/utils/mod.rs:504-575`), which removes only `Account`, `ContractCode`, access/gas keys, and `ContractData`. It does not scan for or remove any `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` rows tied to `account_id`.

Later, when the missing `DataReceipt` finally arrives, `process_receipt` (`runtime/runtime/src/lib.rs:1386-1455`) looks up `TrieKey::PostponedReceiptId{receiver_id, data_id}` purely by the receiver `AccountId`. If found, it fetches the postponed `Receipt` via `get_postponed_receipt` and, once the pending-count reaches zero, calls `apply_action_receipt` against the account object that currently exists at that `AccountId` — with no check that this is "the same" account instance that created the postponed receipt.

Inside action execution, `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`) authorizes `DeployContract` solely by `actor_id == account_id` (string equality). `actor_id` is derived from the stored receipt's `predecessor_id`, which was fixed at receipt-creation time when the attacker made a self-call (`predecessor_id == receiver_id == attacker's original account name`). Because this is a pure string comparison with no binding to the specific account "incarnation," the check still passes against the recreated account, and `action_deploy_contract` installs the attacker's bytecode on the new owner's account and funds.

Attack flow:
1. Attacker deploys a contract on account `X` (a normal account, e.g. a self-registered TLA or subaccount) and calls a method that produces two dependent receipts via a promise chain: one long-latency dependency producing `DataReceipt{data_id}` after several cross-shard hops, and one `ActionReceipt{receiver_id: X, predecessor_id: X, actions: [DeployContract(evil_wasm)], input_data_ids: [data_id]}` chained with `promise_then`. The latter lands on `X`'s shard first and is stored as a postponed receipt (`PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`, all keyed by `X`).
2. Before `data_id`'s `DataReceipt` resolves, attacker submits `DeleteAccountAction` on `X`. `action_delete_account`/`remove_account` deletes the account but leaves the three postponed-receipt trie entries intact.
3. Account name `X` becomes available; an unrelated party later creates a new account `X` (e.g., re-registering a freed top-level account name) and funds/uses it normally.
4. The originally-scheduled `DataReceipt{data_id}` eventually arrives at `X`. `process_receipt` finds the still-present `PostponedReceiptId`, decrements `PendingDataCount` to zero, fetches the old `PostponedReceipt`, and calls `apply_action_receipt`, which runs `check_actor_permissions` (passes, `actor_id == account_id == "X"`) and then `action_deploy_contract`, silently installing the attacker's bytecode on the new owner's account.

No existing check ties the postponed receipt to a specific account existence generation, and account deletion does not invalidate or purge it.

### Impact Explanation
This breaks the authorization-exactness invariant: an action authorized by a *previous* occupant of an account name executes against a *different, unrelated* occupant without their consent. Concretely it enables contract takeover of a victim's freshly-created/funded account — the attacker can deploy arbitrary wasm (e.g., a contract that immediately drains the account's balance via further self-calls, or backdoors any tokens/NFTs later deposited into it), i.e., theft of funds via authorization escalation across accounts, matching the "theft of funds via contract takeover" bounty category.

### Likelihood Explanation
Every step is reachable by an ordinary unprivileged account holder: deploying a contract, creating a multi-hop promise chain, and submitting a `DeleteAccountAction`, are all standard, unprivileged operations. The attacker fully controls the shape/length of the promise chain that produces the delayed `DataReceipt`, so they can create as large a window as needed between "postponed receipt created" and "account deleted." The remaining precondition — that the exact account name gets reused by a different party — is realistic for accounts whose names become available again after deletion (e.g., freed top-level names available for re-registration), a normal occurrence on NEAR, not requiring any social engineering, privileged access, or key compromise. This is fully repeatable by any attacker choosing account names they expect to be reused.

### Recommendation
When deleting an account, purge all `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` entries (and orphan any pending `ReceivedData`/`PromiseYieldReceipt`/`PromiseYieldStatus`/yield-id-mapping rows) keyed by that `account_id` inside `remove_account`, mirroring the existing iteration-and-removal pattern already used there for access keys and contract data. Alternatively/additionally, bind postponed receipts to the target account's identity (e.g., include the account's creation nonce/version in the trie key, or explicitly re-validate at execution time that the account existing at delivery is the same one the receipt was authorized against) so that a resurrected postponed receipt can never execute against an unrelated account occupying the same name.

### Proof of Concept
Runtime-level integration test (in `runtime/runtime/tests` or `test-loop-tests`) using `apply()`:
1. Create account `X`, deploy a contract with a method that: (a) issues a cross-contract call chain of several hops to another contract to generate an eventual `DataReceipt{data_id}`, and (b) via `promise_then`, schedules a `DeployContract(evil_wasm)` action receipt targeting `X` itself with `input_data_ids: [data_id]`.
2. Apply the chunk containing the initial call; assert `get_postponed_receipt` returns `Some` for `(X, receipt_id)` and `TrieKey::PostponedReceiptId{receiver_id: X, data_id}` exists.
3. Submit and apply a `DeleteAccountAction` transaction for `X` in a subsequent block; assert `get_account(state_update, X)` is `None`, but assert the `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` rows for `X` are still present in the trie (demonstrating the leak).
4. Recreate account `X` via a fresh `CreateAccountAction` + `Transfer` from an unrelated account, and deploy a legitimate benign contract on it.
5. Deliver the originally-pending `DataReceipt{data_id}` (simulating its eventual arrival) to `X`'s shard and apply.
6. Assert that `Account::contract()` (or `AccountContract` field) of `X` now equals the attacker's `evil_wasm` code hash — demonstrating the takeover — and flag this as the vulnerability (expected/fixed behavior: the assertion should instead show the recreated account's contract hash is unaffected, i.e., the postponed receipt must be dropped/rejected because its target account no longer exists in its original form).
