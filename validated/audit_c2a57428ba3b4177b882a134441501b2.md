Audit Report

## Title
Missing deadline check in `AtomicSwap::claim_swap` lets the target claim reserved funds indefinitely, defeating the source's time-bound reclaim guarantee - (File: `substrate/frame/atomic-swap/src/lib.rs`)

## Summary
`create_swap` reserves the source's funds and stores a `PendingSwap` with an `end_block` deadline, and `cancel_swap` correctly enforces `block_number() >= swap.end_block` before returning reserved funds to the source. `claim_swap`, however, performs no equivalent check and lets the target repatriate the reserved balance from the source at any time after `end_block`, as long as `cancel_swap` has not already executed and removed the entry.

## Finding Description
`create_swap` reserves `value` via `action.reserve(&source)` and stores `PendingSwap { source, action, end_block: block_number() + duration }` keyed by `(target, hashed_proof)`. [1](#0-0) 

`cancel_swap` enforces the deadline (`block_number() >= swap.end_block`) before calling `swap.action.cancel(&swap.source)` and removing the entry. [2](#0-1) 

`claim_swap`, called by `target`, fetches the `PendingSwap`, checks only that `swap.action == action`, and then calls `swap.action.claim(&swap.source, &target)` — which invokes `C::repatriate_reserved(source, target, value, Free)` for `BalanceSwapAction` — with no check of `swap.end_block` against the current block number. [3](#0-2) [4](#0-3) 

This is inconsistent with the sibling implementation in `pallet-nfts`'s atomic-swap feature (`do_claim_swap`), which enforces `ensure!(now <= swap.deadline, Error::<T, I>::DeadlineExpired)` before completing a claim, confirming that a symmetric deadline check on the claim path is the intended safety property for this commit/claim/cancel pattern. [5](#0-4) 

The corrupted/unchecked value is `PendingSwap.end_block` — authoritative on the cancel path, silently ignored on the claim path. [6](#0-5) 

## Impact Explanation
Because `claim_swap` never checks the deadline, the target can withhold the revealed proof past `end_block` and submit `claim_swap` at any later block, as long as `cancel_swap` has not yet executed. This creates a race: whichever of `claim_swap`/`cancel_swap` lands first wins, so the source's balance — reserved via `ReservableCurrency::reserve` — can be unexpectedly repatriated to the target well after the source considers the swap expired and reclaimable. This is a genuine settlement/custody defect (unbacked/duplicate-style repatriation of reserved value to the wrong party) rather than a mere UX quirk, since `cancel_swap`'s own explicit deadline gate signals that the pallet's design intent is time-bound exclusivity, and the analogous `pallet-nfts` implementation enforces exactly this symmetric check on its claim path.

## Likelihood Explanation
No privileged actor, governance action, or compromised infrastructure is required. Any two unprivileged accounts using only the pallet's public extrinsics (`create_swap`, `claim_swap`, `cancel_swap`) can trigger this: the target simply needs to hold the proof and submit `claim_swap` after `end_block`, racing the source's `cancel_swap`. No front-running of a third party is needed since the target can act unilaterally at any time before the source cancels. The exploit is reachable and repeatable via the pallet's own public API exactly as documented.

## Recommendation
Add an explicit deadline check to `claim_swap`, mirroring `cancel_swap` and the `pallet-nfts` implementation, e.g.:
```rust
ensure!(
    frame_system::Pallet::<T>::block_number() < swap.end_block,
    Error::<T>::DurationPassed,
);
```
placed before calling `swap.action.claim(&swap.source, &target)`, and add a corresponding `DurationPassed` error variant.

## Proof of Concept
1. `source` calls `create_swap(target, hashed_proof, action=BalanceSwapAction::new(V), duration=D)` at block `N`; `V` is reserved from `source`, and `end_block = N + D` is recorded.
2. Block `N + D` passes with no claim submitted by `target`.
3. At block `N + D + k` for arbitrary `k`, `target` submits `claim_swap(proof, action)`. Since `claim_swap` never checks `end_block`, `swap.action.claim(&source, &target)` succeeds via `repatriate_reserved`, moving `V` from `source`'s reserved balance to `target`'s free balance, and the pending entry is removed.
4. If `source` attempts `cancel_swap` after this point, it fails with `Error::NotExist` since the entry is already gone — the source has irreversibly lost the reserved value to the target despite the deadline having passed.
5. This can be encoded as a Rust unit test in `substrate/frame/atomic-swap/src/tests.rs`: create a swap with a short `duration`, advance the block number past `end_block` without calling `cancel_swap`, then call `claim_swap` and assert it still succeeds (`Ok(())`) and funds move — demonstrating the missing check.

			origin: OriginFor<T>,
			proof: Vec<u8>,
			action: T::SwapAction,
		) -> DispatchResult {
			ensure!(proof.len() <= T::ProofLimit::get() as usize, Error::<T>::ProofTooLarge);

			let target = ensure_signed(origin)?;
			let hashed_proof = blake2_256(&proof);

			let swap =
				PendingSwaps::<T>::get(&target, hashed_proof).ok_or(Error::<T>::InvalidProof)?;
			ensure!(swap.action == action, Error::<T>::ClaimActionMismatch);

			let succeeded = swap.action.claim(&swap.source, &target);

			PendingSwaps::<T>::remove(target.clone(), hashed_proof);

			Self::deposit_event(Event::SwapClaimed {
				account: target,
				proof: hashed_proof,
				success: succeeded,
			});

			Ok(())
		}
