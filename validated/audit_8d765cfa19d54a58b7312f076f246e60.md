## Analysis Result

The manifest is fetched from an S3-style `ObjectStorage` (`ReadManifest`) and is written into that store by any Gitaly node during MVCC session `Publish`. Manifests are content-addressed by their SHA-256 trailer and are validated on read by `ParseManifest`, so this is data that a party with write access to the backing object store (or an MVCC session that Publishes a crafted manifest) can influence, and it's parsed by every Gitaly node/RPC before it can execute Git commands. This is a boundary condition path, but I could not fully confirm within the available context whether an ordinary unprivileged Git push/fetch client can smuggle an arbitrary raw manifest body into the store (versus Gitaly always constructing manifests itself via `SerializeManifest`). Given the "Reject ... no-impact analogs" rule and my inability to concretely prove that an *ordinary user's* push/fetch/RPC can supply a malformed manifest body (as opposed to only internal, Gitaly-generated manifests), I cannot confidently confirm this as a reachable analog from an unprivileged actor.

### Title
Signed 64-bit-to-int truncation of chunk offsets in MVCC manifest parser bypasses bounds checks - (File: internal/git/mvcc/manifest.go)

### Summary
`parseChunks` in `internal/git/mvcc/manifest.go` converts attacker/producer-controlled 64-bit chunk offsets from the manifest TOC directly to Go's platform-sized `int` via `int(binary.BigEndian.Uint64(...))`, then uses that value in a bounds check (`chunkOffsetInFile > dataEnd`) before using it as a slice index. This mirrors the reported Solidity bug class: an unchecked narrowing/truncating cast of an attacker-influenced integer that is later relied upon for a security-relevant bounds check, allowing the check to be bypassed by a value that wraps to something that satisfies the (now incorrect) comparison.

### Finding Description [1](#0-0) 

`parseChunks` reads TOC entries as `uint64` offsets and casts them straight to `int`:
```go
chunkOffsetInFile := int(binary.BigEndian.Uint64(data[chunkOffset+4 : chunkOffset+tocChunkSize]))
...
nextChunkOffsetInFile := int(binary.BigEndian.Uint64(data[nextChunkStart+4 : nextChunkStart+tocChunkSize]))

if chunkOffsetInFile > dataEnd || nextChunkOffsetInFile > dataEnd || nextChunkOffsetInFile < chunkOffsetInFile {
    return nil, fmt.Errorf("chunk %d has out-of-bounds offsets [%d, %d)", i, chunkOffsetInFile, nextChunkOffsetInFile)
}
```
On the 64-bit platforms Gitaly runs on, Go's `int` is 64-bit and signed. A `uint64` value greater than `math.MaxInt64` (e.g., `0x8000000000000000` or higher) truncates to a *negative* `int` when cast. A negative `chunkOffsetInFile`/`nextChunkOffsetInFile` will satisfy `chunkOffsetInFile > dataEnd` as false (since it's negative, always "less than" `dataEnd`), so the intended out-of-bounds check is silently bypassed. The resulting negative offset is then propagated into `manifestChunk.offset`/`.size` and used downstream in `ParseManifest`, e.g.:
```go
start := pathChunk.offset + i*pw
record := data[start : start+pw]
``` [2](#0-1) 
A negative `start` here causes a Go runtime slice-bounds panic rather than the intended validation error. This is the same underlying bug class as the reported `uint128` truncation issue: an unchecked narrowing cast of an externally influenced value is trusted for downstream bounds/limit logic, letting a crafted value defeat the check it was meant to satisfy.

### Impact Explanation
The direct consequence in Go is a runtime panic (slice bounds out of range) rather than memory corruption, because Go bounds-checks slice operations at runtime. If this panic is not recovered by a top-level handler, it can crash the Gitaly process handling the manifest, denying service to that node until a supervisor restarts it. If a recover/goroutine boundary swallows the panic per-RPC, the impact is limited to a single request failure instead of a full crash.

### Likelihood Explanation
Exploitability depends entirely on whether an untrusted actor can inject an arbitrary raw manifest byte stream that gets fed to `ParseManifest`/`parseChunks` under a passing SHA-256 self-integrity check (an attacker who can write to the manifest object-storage bucket, or forge/compute a manifest whose SHA-256 trailer matches, could set this up in `parseManifestHeader`/`parseChunks`). Since manifests are normally produced only by `SerializeManifest` inside Gitaly itself and consumed by `ParseManifest`, I was unable to confirm within the available codebase context that a normal unprivileged Git push/fetch/RPC caller can cause a crafted raw manifest with out-of-range TOC offsets to be written and subsequently read by another Gitaly node. This uncertainty is significant and should be validated with a full read of the MVCC storage/write path (`internal/git/mvcc/cache.go`, `internal/git/mvcc/storage_local.go`, and the S3-backed `ObjectStorage` implementation) before treating this as confirmed high-severity.

### Recommendation
- Reject `uint64` offsets that exceed `math.MaxInt64` (or, better, `len(data)`) *before* casting to `int`, e.g. `if off > uint64(len(data)) { return error }`, performing the comparison in `uint64` space rather than after a narrowing cast.
- Apply the same guard consistently to every `int(binary.BigEndian.Uint64(...))` / `int(binary.BigEndian.Uint32(...))` conversion in `internal/git/mvcc/manifest.go` (`parseChunks`, `objsChunk`, `refsChunk` handling) so that all bounds decisions are made in the unsigned/wide type domain, mirroring the recommended `SafeCast`-style mitigation from the original report.
- Add fuzz/unit tests feeding TOC offsets at and beyond `math.MaxInt64`/`math.MaxUint64` boundaries to ensure `ParseManifest` returns a clean error instead of panicking.

### Proof of Concept
Not independently verified against a running binary; conceptually:
1. Construct a raw manifest body with a valid header (`magic`, `version=1`, `numChunks`, `pathWidth`, `hashAlgo`), and a TOC entry whose 8-byte big-endian offset field is set to `0xFFFFFFFFFFFFFFFF` (or any value `> math.MaxInt64`).
2. Recompute and append the correct trailing SHA-256 over the crafted payload so `ParseManifest`'s checksum validation at [3](#0-2)  passes.
3. Feed the bytes to `mvcc.ParseManifest`. The cast `int(binary.BigEndian.Uint64(...))` in `parseChunks` yields a negative `chunkOffsetInFile`, which passes the `> dataEnd` check, producing a `manifestChunk` with a negative `offset`.
4. Subsequent chunk processing (e.g., PATH-record slicing) indexes `data` with the negative offset, triggering a Go runtime slice-bounds panic instead of the intended validation error.

I was unable to actually execute this PoC against the codebase in this session (no code execution available), so this should be validated by a background engineer with a unit test in `internal/git/mvcc/manifest_test.go`.
