### Title
Divergent reward calculations between `VoteRewardUtil` (TVM vote-reward precompile) and `MortgageService` (native reward accounting) cause inconsistent witness-vote reward payouts - (File: actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java)

### Summary
Similar to the IdleCDO issue where `virtualPrice()` and `_updatePrices()` computed a tranche's value using two divergent implementations, java-tron maintains **two independent implementations** of the vote-reward calculation formula that are supposed to compute the same quantity — the reward owed to an address for its SR votes over a cycle range. `MortgageService.computeReward()` [1](#0-0)  branches between an "old" proportional-distribution algorithm and a "new" Vi-delta fixed-point algorithm depending on `dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle()`, while `VoteRewardUtil.computeReward()` [2](#0-1)  — used by the TVM vote-reward precompile reachable from any smart contract — unconditionally applies only the Vi-delta algorithm to the entire `[beginCycle, endCycle)` range, with no old-algorithm branch at all.

### Finding Description
`MortgageService.computeReward(beginCycle, endCycle, accountCapsule)` explicitly splits computation at the cycle where the new reward algorithm became effective: [3](#0-2) 

For cycles before that switch, it calls `getOldReward()`, which either sums the per-cycle proportional reward (`voteRate * totalReward` using `double` arithmetic) or delegates to `RewardViCalService.getNewRewardAlgorithmReward()` depending on `allowOldRewardOpt()`: [4](#0-3) [5](#0-4) 

By contrast, `VoteRewardUtil.computeReward()` — invoked by `withdrawReward()`/`queryReward()`, which back the TVM's vote-withdrawal/vote-query precompile callable from any deployed contract — performs no such branching. It always walks `beginCycle` to `endCycle` using only Vi-delta accounting: [6](#0-5) 

Both code paths read/write the *same* underlying `AccountCapsule` allowance and the *same* `beginCycle`/`endCycle`/`AccountVote` bookkeeping fields via `DelegationStore`/`Repository`, so they are not simply two disjoint features — they are alternate entry points into the *same* stored reward state for the *same* account, exactly mirroring the IdleCDO pattern of two implementations computing the same balance differently.

### Impact Explanation
Because `VoteRewardUtil` skips the old-algorithm branch that `MortgageService` applies for cycles preceding `getNewRewardAlgorithmEffectiveCycle()`, an account whose unwithdrawn reward window spans pre-switch cycles can be paid a different amount depending on which path is used to withdraw:
- Native `WithdrawBalanceContract` (goes through `MortgageService.withdrawReward()`), or
- A smart-contract call into the TVM vote-reward precompile (goes through `VoteRewardUtil.withdrawReward()`).

Since both mutate the shared `beginCycle`/`endCycle`/allowance state, whichever path executes first "consumes" the cycle range and updates checkpoints, potentially permanently under- or over-crediting the account relative to what the other implementation would have computed — an accounting-invariant violation that can result in incorrect account balances (either unbacked allowance credited to a user, or permanent loss of legitimately earned reward), reachable purely by calling a smart contract from a normal transaction.

### Likelihood Explanation
This requires a chain that has undergone the reward-algorithm migration (i.e., `getNewRewardAlgorithmEffectiveCycle()` set to a value greater than an account's outstanding `beginCycle`) and a voter with an un-withdrawn reward window overlapping the old algorithm's cycles, followed by a call through the TVM's vote precompile (`queryReward`/`withdrawReward` opcode path) instead of the native withdrawal transaction. This is a realistic scenario on any long-lived network that adopted the new reward algorithm after go-live, and the precompile is callable by any deployed contract without special privilege.

### Recommendation
Consolidate the reward-calculation logic into a single shared implementation (e.g., have `VoteRewardUtil.computeReward()` delegate to the same algorithm-switching logic used in `MortgageService.computeReward()`/`getOldReward()`, or extract a common utility used by both), so that the TVM precompile path and the native withdrawal path always agree on the reward owed for a given cycle range and account.

### Proof of Concept
1. On a network where `getNewRewardAlgorithmEffectiveCycle()` = N (> 1), have an account vote for a witness at cycle 1 and never withdraw, so `beginCycle` stays at an old cycle < N with `endCycle` advancing forward each cycle.
2. Call the TVM vote-reward precompile's `withdrawReward`/`queryReward` (via `VoteRewardUtil`) for that address — the returned/paid reward is computed solely via Vi-delta over `[1, endCycle)`.
3. Separately, reset the same scenario and instead invoke `MortgageService.withdrawReward()`/`queryReward()` (native path) — the returned/paid reward instead uses `getOldReward()` (proportional distribution or `RewardViCalService`) for `[1, N)` plus Vi-delta for `[N, endCycle)`.
4. Compare the two resulting reward amounts for cycles spanning the old→new algorithm boundary; discrepancies (due to differing precision — `double` proportional math vs `BigInteger` fixed-point Vi math) demonstrate the same-class inconsistency reported in the external analog.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
