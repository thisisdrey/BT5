### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.toAccounts`/`fromAccounts` lists via repeated `FreezeBalanceContract` delegation causes linear-scan cost and unbounded state growth - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.delegateResource()` (the legacy, non-optimized delegation path used when `AllowDelegateOptimization` is off) appends the receiver/owner address into the `toAccounts`/`fromAccounts` repeated fields of `DelegatedResourceAccountIndexCapsule` with no cap on the number of distinct counterparties. Any unprivileged account can broadcast repeated `FreezeBalanceContract` transactions (1 TRX minimum, each to a freshly generated receiver address) to grow this list without bound, exactly analogous to the reported unbounded-array pattern in Hubble's `ClearingHouse.updatePositions()`.

### Finding Description
In `FreezeBalanceActuator.delegateResource()`:
```
List<ByteString> toAccountsList = ownerIndexCapsule.getToAccountsList();
if (!toAccountsList.contains(ByteString.copyFrom(receiverAddress))) {
  ownerIndexCapsule.addToAccount(ByteString.copyFrom(receiverAddress));
}
``` [1](#0-0) 

there is no limit on the number of entries that can be added to `toAccounts`/`fromAccounts`. Every call with a new, previously unseen receiver address:
1. Performs a `List.contains()` linear scan over the entire existing list (O(n)).
2. Serializes/deserializes and rewrites the whole `DelegatedResourceAccountIndex` protobuf capsule to the KV store on every single delegation call.

The corresponding un-delegation path in `UnfreezeBalanceActuator` similarly copies the full list into an `ArrayList`, does a linear `remove()`, and rewrites the entire list back: [2](#0-1) 

`FreezeBalanceActuator.validate()` only bounds the *count of frozen entries per resource type* (`frozenCount == 0 || frozenCount == 1`), not the number of distinct delegation counterparties: [3](#0-2) 

This is confirmed by the project's own test, `testMultiFreezeDelegatedBalanceForBandwidth`, which freezes/delegates to 100 distinct newly generated receiver addresses from a single owner and asserts the `toAccounts` list simply keeps growing to `RECEIVE_COUNT + 1` entries with no cap enforced: [4](#0-3) 

Once `AllowDelegateOptimization` is enabled, the legacy indexes are still readable/convertible via `DelegatedResourceAccountIndexStore.convert()`, which itself iterates the entire (unbounded) `toList`/`fromList` in a loop calling `delegate()` for each entry — i.e., the unbounded-size liability persists and is paid for lazily at conversion time: [5](#0-4) 

Compare this against `VoteWitnessActuator`, which explicitly enforces `MAX_VOTE_NUMBER` on the analogous vote list before it can grow: [6](#0-5) 
No equivalent cap exists for the delegated-resource index list.

### Impact Explanation
An attacker who controls one funded account can generate an arbitrarily large number of throwaway receiver addresses and, using ordinary `FreezeBalanceContract` transactions delegating the minimum 1 TRX each, grow their own `DelegatedResourceAccountIndexCapsule.toAccounts` (and the corresponding receivers' `fromAccounts`) without any protocol-imposed bound. Because each new delegation call performs a full linear scan (`contains`) plus a full read/rewrite of the growing protobuf list, the cost of each subsequent freeze/unfreeze/delegate operation involving that account increases (worsening bandwidth/energy cost predictability and processing time), and the on-disk/in-memory size of a single account's index capsule grows unbounded. This degrades processing of transactions touching that account and inflates state size, which is a resource-exhaustion / performance-degradation risk to the node processing path — the same class of issue as the reported unbounded-array DoS, though bounded here by the attacker's own TRX/fee cost per entry (so it is not a free attack, tempering severity to Medium rather than High).

### Likelihood Explanation
Likelihood is Medium: the vulnerable legacy path is only exercised when `AllowDelegateOptimization` (a chain parameter set via proposal) is disabled; on production networks where this optimization has been enabled, the *newer* per-pair key-prefixed index storage (`DelegatedResourceAccountIndexStore.delegate/unDelegate` with `FROM_PREFIX`/`TO_PREFIX`/`V2_*_PREFIX` keys) is used, which avoids the single-growing-list issue. However, the legacy in-object list append is still reachable on any chain/testnet where that parameter has not been turned on, and the `convert()` migration path still walks the full unbounded list when triggered, meaning historical or maliciously-grown indexes are not free of cost even after the optimization is toggled on.

### Recommendation
- Enforce an explicit maximum size on `toAccounts`/`fromAccounts` in `DelegatedResourceAccountIndexCapsule`/`FreezeBalanceActuator.delegateResource()` and `DelegateResourceActuator`, analogous to `MAX_VOTE_NUMBER` for votes, rejecting further delegation to new counterparties beyond the cap (or requiring the account to withdraw/consolidate old entries first).
- Avoid using `List.contains()` linear scans on a value that can be attacker-grown; if a duplicate-check is required, use a keyed/indexed structure instead of a repeated field, or migrate fully to the prefixed key-value scheme (removing the legacy list-based `DelegatedResourceAccountIndexCapsule` code path entirely) so no unbounded protobuf list needs to be loaded/rewritten per call.
- Bound the cost of `DelegatedResourceAccountIndexStore.convert()` (e.g., process in batches) so migration of a maliciously grown legacy index cannot itself become an expensive/DoS-prone operation.

### Proof of Concept
1. Ensure `AllowDelegateOptimization` is not yet enabled on the target chain (default/legacy state).
2. From a single funded account `A`, repeatedly broadcast `FreezeBalanceContract` transactions, each delegating the minimum allowed frozen balance (1 TRX, `BANDWIDTH` or `ENERGY` resource) to a freshly generated, never-before-used receiver address `R_i` (`i = 1..N`), as demonstrated by the existing test harness pattern in `FreezeBalanceActuatorTest.testMultiFreezeDelegatedBalanceForBandwidth` (which does exactly this for `N=100` and confirms unmatched growth of the index list).
3. Observe that `DelegatedResourceAccountIndexCapsule` for account `A` (`toAccounts`) and for each `R_i` (`fromAccounts`) grows linearly with no enforced cap, and that each subsequent freeze call incurs an O(n) `contains()` scan over the growing list, with the whole capsule being re-serialized on every call.
4. Repeating this for a sufficiently large `N` (bounded only by the attacker's available TRX for the 1 TRX-per-delegation minimum and transaction fees) demonstrates unbounded growth of on-chain state and increasing processing cost per subsequent operation touching account `A`, mirroring the "unbounded array" DoS pattern described in the source report.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
