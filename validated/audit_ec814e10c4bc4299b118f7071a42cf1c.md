### Title
Half-open QUIC connection churn from a single IP can exhaust the global `ClientConnectionTracker` slot budget and starve legitimate TPU senders - (File: streamer/src/nonblocking/quic.rs)

### Finding Description
In `run_server`, every `Incoming` connection is gated by three checks in this order: `overall_connection_rate_limiter.current_tokens() == 0` [1](#0-0) , `rate_limiter.is_allowed(&incoming.remote_address().ip())` [2](#0-1) , and `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())` [3](#0-2) . Only the third check actually consumes a resource before the handshake completes — it increments the global `stats.open_connections` counter and is bounded only by `qos.max_concurrent_connections()`, a value with no per-IP dimension [4](#0-3) .

The per-IP `ConnectionRateLimiter` (`is_allowed`/`register_connection`) is deliberately *not* consumed until the handshake completes in `setup_connection`, per the code's own comment: "we should only modify server state once source IP is verified" [5](#0-4)  and [6](#0-5) . Likewise `overall_connection_rate_limiter` is only checked (not consumed) at the accept stage and only actually consumed on successful handshake [7](#0-6) .

This means an attacker that opens `Incoming` connections and lets each one sit through `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2 seconds, `setup_connection`'s `timeout(...)`) without completing the handshake never triggers `register_connection`, so the per-IP rate limiter never sees this IP as abusive and does not throttle it [8](#0-7) [9](#0-8) . Meanwhile, every such half-open attempt still consumes one global `ClientConnectionTracker` slot for up to 2 seconds, and this slot pool (`qos.max_concurrent_connections()`) is shared across staked and unstaked peers and all source IPs, with no per-IP cap applied at this stage.

By continuously opening new connections (from new ephemeral source ports, which doesn't matter since the limiter keys on IP not port) faster than the 2-second timeout expires them, a single unstaked/unstaked-source IP can keep the global slot pool saturated, causing `ClientConnectionTracker::new` to fail for legitimate senders and increment `refused_connections_too_many_open_connections` [3](#0-2) .

### Impact Explanation
This is a QoS-evasion / connection-starvation issue: an unstaked, unprivileged attacker can consume the shared, IP-agnostic connection-attempt budget (`qos.max_concurrent_connections()`, sized around `max_staked_connections * 5/4` in `simple_qos.rs` [10](#0-9) ) by holding many concurrent half-open handshakes, causing legitimate staked and unstaked connection attempts to be refused (`incoming.refuse()`) at the TPU ingress before stake/QoS classification ever occurs. This matches the described bounty category: unfair capture/starvation of connection/QoS capacity by an unstaked client, without needing to complete a single handshake or spend any stake.

### Likelihood Explanation
Preconditions are minimal: only UDP reachability to the TPU QUIC port, no stake, and the ability to open many concurrent QUIC `Initial` packets while withholding the `Handshake` packet (or simply not completing it) so the connection stays in-flight for the full `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` window. Because `is_allowed`/`register_connection` are IP-keyed and require an actual completed handshake to fire, this per-IP limiter provides zero protection against attempt churn, and the `ClientConnectionTracker` cap that does apply is global rather than per-IP, so the attack does not need IP rotation or spoofing — a single IP can churn indefinitely. This is straightforward to reproduce and repeat continuously as long as the attacker keeps generating half-open `Connecting` futures faster than they time out.

### Recommendation
Add a per-IP cap on outstanding/in-flight (pre-handshake) connection attempts, independent of the post-handshake `ConnectionRateLimiter`, e.g., track `outstanding_incoming_connection_attempts` per source IP (not just globally) and reject/ignore new `Incoming` connections from an IP that already holds too many concurrent unverified attempts. Alternatively, reserve a portion of `qos.max_concurrent_connections()` slots exclusively for post-handshake-verified peers, or lower `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` further while adding an IP-scoped concurrency limit at the `ClientConnectionTracker::new` gate so a single unverified IP cannot consume more than a small fraction of the global pool.

### Proof of Concept
Integration test plan (extending existing test infra in `streamer/src/nonblocking/quic.rs`/`simple_qos.rs` tests using `make_client_endpoint`/`setup_quic_server`):
1. Configure a test server with a small `max_concurrent_connections`-inducing config (small `max_staked_connections`/`max_unstaked_connections` per `SimpleQosConfig`/`SwQosConfig`).
2. From a single test client IP (loopback with multiple ephemeral ports, or `quinn::Endpoint`s bound to the same IP), repeatedly open `Connecting` futures that send only QUIC `Initial` and never send the final `Handshake` completion (e.g., a raw UDP socket sending crafted Initial packets, or a client endpoint configured to stall on handshake) — hold each for close to but under `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, and immediately open a replacement once one times out.
3. Concurrently attempt a legitimate `make_client_endpoint` connection from a different IP/port as a "victim" and assert it is refused (`ConnectionError` / rejection) while the attacker sustains the churn.
4. Assert via `StreamerStats`: `outstanding_incoming_connection_attempts` stays pinned near `qos.max_concurrent_connections()`, `refused_connections_too_many_open_connections` increments for the victim's attempts, and `connection_rate_limited_per_ipaddr` for the attacker's IP remains 0 (proving the per-IP limiter never engaged).
5. After stopping the attacker's churn, assert the victim's connection succeeds, confirming the starvation was caused solely by attempt churn rather than a legitimate limit.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
}

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }
