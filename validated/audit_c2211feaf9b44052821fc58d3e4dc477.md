Audit Report

## Title
Snowbridge outbound-queue-v2 pays relayer reward and finalizes delivery without checking `DeliveryReceipt::success` - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`process_delivery_receipt` decodes an Ethereum `InboundMessageDispatched` event into a `DeliveryReceipt` carrying an explicit `success: bool` field [1](#0-0) , but the function never inspects `receipt.success` before paying the relayer and permanently closing the pending order [2](#0-1) . Any relayer who submits a valid inclusion proof for a genuine but failed Ethereum-side dispatch is unconditionally rewarded, and the message is marked "delivered" regardless of actual execution outcome.

## Finding Description
`do_process_message` creates a `PendingOrder{nonce, fee, block_number}` for every outbound command, intended to be settled only once execution on Ethereum is confirmed [3](#0-2) . The Ethereum gateway's `InboundMessageDispatched` event explicitly records a `success` boolean precisely so downstream logic can distinguish successful from failed dispatch [4](#0-3) , and `DeliveryReceipt::try_from` faithfully decodes this field from the raw log [5](#0-4) .

However, `submit_delivery_receipt` is a plain signed extrinsic reachable by any relayer with a valid proof [6](#0-5) , and the subsequent `process_delivery_receipt` only checks `receipt.gateway == T::GatewayAddress::get()` and that a `PendingOrder` exists for `receipt.nonce` — it pays `order.fee` to the reward account and removes `PendingOrders[nonce]` unconditionally, emitting `MessageDelivered` in all cases [7](#0-6) . `receipt.success` is decoded but never read in this function. No other guard in the pallet (the `Error` enum only covers gateway mismatch, unknown nonce, verification failure, and envelope decode failure [8](#0-7) ) compensates for this omission.

## Impact Explanation
Every genuine but reverted/failed Ethereum-side execution still results in the relayer being paid `order.fee` and the `PendingOrder` being permanently removed via `<PendingOrders<T>>::remove(nonce)`, foreclosing any retry or reconciliation for that message. This is a duplicate/incorrect settlement of bridge payout state — the pallet advances message/reward state to a terminal "delivered" status without the corresponding execution having succeeded, directly matching the required impact category of duplicate settlement/payout and bridge-state advancing without atomic dispatch-execution-settlement success.

## Likelihood Explanation
High. No malicious relayer, governance action, or privileged actor is required — a normal, protocol-anticipated execution failure on Ethereum (signaled by the very `success` field the event was designed to carry) combined with any honest relayer submitting the resulting receipt deterministically triggers the incorrect settlement.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only pay the reward and remove the `PendingOrder` when `success == true`. When `success == false`, retain the order for retry/resubmission or transition it to an explicit failure state, and emit a distinct event (e.g., `MessageDispatchFailed`) instead of `MessageDelivered`.

## Proof of Concept
1. A command is enqueued via `do_process_message`, creating `PendingOrders[nonce]` with `fee > 0` [9](#0-8) .
2. The message is relayed to Ethereum but execution reverts, so the emitted `InboundMessageDispatched` event carries `success = false`.
3. Any relayer submits `submit_delivery_receipt` with a valid proof; `T::Verifier::verify` succeeds since the event is genuine, and `DeliveryReceipt::try_from` correctly decodes `success: false`.
4. `process_delivery_receipt` checks only `receipt.gateway`, pays `order.fee`, removes `PendingOrders[nonce]`, and emits `MessageDelivered { nonce }` — identical to the success path — despite the command never having executed on Ethereum [10](#0-9) .

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
