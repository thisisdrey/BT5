### Title
Rewards owed to Genesis Representative accounts are permanently irretrievable in `WithdrawBalanceActuator` / `WithdrawRewardProcessor` - (File: `actuator/src/main/java/org/tron/core/actuator/WithdrawBalanceActuator.java`, `actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawRewardProcessor.java`)

### Summary
Block/vote rewards accrued by a witness are unconditionally accumulated into the account's `allowance` field regardless of whether the witness is a Genesis Representative (GP). However, the only two code paths that move `allowance` into spendable `balance` — `WithdrawBalanceActuator` and the TVM native `WithdrawRewardProcessor` — both unconditionally reject any Genesis witness address before any transfer happens. There is no alternate mechanism (clawback, treasury redirect, etc.) to release these funds, so rewards legitimately earned by GP accounts become permanently locked, mirroring the "funds owed become irretrievable due to an unconditional address-based rejection" pattern described in the report.

### Finding Description
`MortgageService.payReward` (called from `payBlockReward` / `payTransactionFeeReward` / `payStandbyWitness`) unconditionally credits a witness's `allowance` via `adjustAllowance`, with no exception for Genesis Representatives: [1](#0-0) 

To ever spend that `allowance`, an account must call `WithdrawBalanceContract`, whose `validate()` throws whenever the owner address matches a Genesis witness: [2](#0-1) 

The `execute()` path, which actually moves `allowance` into `balance`, is only reached after `validate()` succeeds, so it is never executed for GP accounts: [3](#0-2) 

The same unconditional block exists in the TVM-based reward-withdrawal native contract used under the stake-v2/vote-reward model: [4](#0-3) 

Both paths guard against the exact same condition — `CommonParameter.getInstance().getGenesisBlock().getWitnesses()` containing the owner address — with no fallback path (e.g., redirecting to a treasury/blackhole, or allowing withdrawal after some condition). Since these are the *only* two entry points that convert `allowance` into `balance`, any reward that accrues to a Genesis Representative address is permanently stuck: it is counted in the account's `allowance`/reward bookkeeping forever but can never be transferred out via a signed transaction.

### Impact Explanation
Funds legitimately earned as block rewards, transaction fee rewards, and standby-witness/vote rewards for Genesis Representative accounts are permanently frozen with no recovery path — matching "permanent freezing of funds" impact. This is directly reachable by any holder of a Genesis Representative private key simply broadcasting a `WithdrawBalanceContract` or triggering the TVM `withdrawReward` opcode; both paths deterministically revert before any state change, so the reward can never be claimed by that legitimately signed transaction. There is no code path in the actuator or native contract that redirects these funds elsewhere (e.g., to a treasury/blackhole address) as the mitigation for the original Golom finding recommends, so the funds are not just inaccessible to the GP account — they are permanently unspendable, not burned to a recognized sink and not distributed to anyone.

### Likelihood Explanation
High likelihood of occurrence in practice: Genesis Representatives are a fixed, known set of addresses (`CommonParameter.getInstance().getGenesisBlock().getWitnesses()`), and reward accrual via `payReward`/`adjustAllowance` happens automatically as part of normal block production and fee distribution, with no way to opt out. Any attempt by the GP owner (or anyone submitting a transaction on their behalf) to withdraw accrued rewards will deterministically fail at `validate()`. This is a structural, deterministic condition, not requiring any special attacker action beyond simply calling the standard withdraw path.

### Recommendation
If Genesis Representatives are intentionally meant to forfeit rewards, do not accrue rewards for them at all in `MortgageService.payReward`/`adjustAllowance` (skip crediting `allowance` for GP addresses). If instead the intent is only to prevent GP addresses from withdrawing until some condition, implement a clawback/redirect: when `WithdrawBalanceActuator`/`WithdrawRewardProcessor` detect a GP address, redirect the accrued `allowance` to the blackhole/treasury address (burning or redistributing it) instead of throwing an unconditional `ContractValidateException` that leaves the funds in permanent limbo.

### Proof of Concept
1. A Genesis Representative witness produces blocks / receives transaction fees; `MortgageService.payBlockReward`/`payTransactionFeeReward` call `payReward`, which calls `adjustAllowance(witnessAddress, brokerageAmount)`, incrementing the witness account's `allowance` field over many blocks.
2. The witness (or anyone) submits a `WithdrawBalanceContract` transaction with `owner_address` set to the GP address.
3. `WithdrawBalanceActuator.validate()` executes the `isGP` check at lines 112-119, finds the address in `genesisBlock.getWitnesses()`, and throws `ContractValidateException`, so `execute()` (which would move `allowance` into `balance`) never runs.
4. Equivalently, if the account tries `withdrawReward()` via a TVM contract call, `WithdrawRewardProcessor.validate()` performs the identical `isGP` check and throws before any state mutation.
5. Because these are the only two code paths that convert `allowance` into `balance`, the GP account's accrued reward remains in `allowance` indefinitely with no way to ever claim, redirect, or otherwise dispose of it.

    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
