## Title
Reconfiguration guard skips shrinking a `StackerDB` when the new signer set is empty, leaving revoked signers able to write accepted chunks - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` decides whether to call `reconfigure_stackerdb` (which rewrites the on-disk slot→signer bindings used for signature authorization) using a condition that requires the *new* signer list to be non-empty before a config-change is honored. If a StackerDB contract's signer set drops to zero (e.g., all registered signers are removed on-chain), the node never applies that change to its local replica, so previously-authorized (now revoked) signers remain valid `slot_validation.signer` entries in the database and can keep writing/propagating chunks that the network treats as authenticated.

### Finding Description
`create_or_reconfigure_stackerdbs` computes `new_config` from the smart contract for each StackerDB replica and only calls `self.reconfigure_stackerdb(...)` under this condition: [1](#0-0) 

```rust
} else if (new_config != stackerdb_config && !new_config.signers.is_empty())
    || (new_config == stackerdb_config
        && new_config.signers.len()
            != self.get_slot_versions(&stackerdb_contract_id)?.len())
{
    // only reconfigure if the config has changed
    // (that second check on the length is needed in case the node is a victim of
    // #5142, which was a bug whereby a stackerdb could never shrink)
    if let Err(e) = self.reconfigure_stackerdb(&stackerdb_contract_id, &new_config) {
        ...
    }
}
```

If the contract's signer set becomes empty (`new_config.signers.is_empty()`), the first disjunct `(new_config != stackerdb_config && !new_config.signers.is_empty())` is false regardless of whether the config actually changed, because of the explicit `!new_config.signers.is_empty()` guard. The second disjunct only fires when `new_config == stackerdb_config` (i.e. no change) and slot counts mismatch — it cannot fire when the config just transitioned to empty. Consequently `reconfigure_stackerdb` (and its underlying `shrink_stackerdb`/slot rebinding in `stackslib/src/net/stackerdb/db.rs`) is never invoked, and the previously-created slot rows retain their old `signer` field: [2](#0-1) 

Chunk authorization is checked purely against the stored `slot_validation.signer` from the DB, not against the live smart-contract signer set: [3](#0-2) 

The peer-to-peer receive path (`validate_received_chunk`) similarly authenticates against `self.stackerdbs.get_slot_signer(...)`, i.e. the stale, un-shrunk DB state: [4](#0-3) 

Since `new_stackerdb_configs.insert(stackerdb_contract_id, new_config)` always stores the "correct" (empty) config in memory regardless of whether the DB was actually reconfigured, the in-memory view of the DB and the on-disk slot bindings diverge — the node believes there are no signers, but the persisted slot table still authorizes the old signer set for writes and relay. This is exactly the "equality that fails open" pattern from the reported bug class: the guard intended to prevent a stackerdb from failing to shrink (issue #5142) was written with an extra condition that defeats itself precisely in the all-signers-removed case, mirroring the reported `totalFeeShare == 0 && !unlocked` vs `&& unlocked` inversion.

### Impact Explanation
A previously-legitimate but now-deauthorized signer (or any party who compromised such a key) can continue to have their StackerDB chunk writes accepted and relayed across the network as authenticated data, even though the current canonical smart-contract state says there are no signers for that DB. This is an authorization state that is not refreshed to match canonical on-chain state — non-canonical (stale) authorization data continues to be served/enforced as canonical, allowing forged/unauthorized state to propagate through StackerDB replication. This matches the "High" impact bucket (serving non-canonical state as canonical) in the rules.

### Likelihood Explanation
This requires a StackerDB-controlling contract to transition its signer set to empty (a normal, contract-driven configuration change, not requiring any node secret or privileged party), after which the condition failure is deterministic on every node's periodic `create_or_reconfigure_stackerdbs` call. The comment referencing issue #5142 shows this exact reconfigure/shrink logic has already been buggy once before, indicating the code path is fragile and under-tested for the "config vanishes" edge case.

### Recommendation
Remove the `!new_config.signers.is_empty()` guard from the first disjunct so that any real change to signers (including transitioning to empty) triggers `reconfigure_stackerdb`, e.g.:
```rust
} else if new_config != stackerdb_config
    || new_config.signers.len() != self.get_slot_versions(&stackerdb_contract_id)?.len()
{
    ...
}
```
This ensures the on-disk slot/signer bindings are always shrunk/cleared to match the canonical contract-derived config, closing the window where revoked signers retain write authorization.

### Proof of Concept
Not independently executed (index/tooling constraints — this is a static code-path analysis, not a live repro). To confirm: deploy/modify a StackerDB-controlling test contract so `stackerdb-get-signer-slots` returns an empty list after previously returning a non-empty list; drive `create_or_reconfigure_stackerdbs` across that transition (as exercised in `stackslib/src/net/stackerdb/tests/db.rs` `test_reconfigure_stackerdb`); then attempt `try_replace_chunk` signed by the old signer key and observe it still succeeds because `get_slot_validation` still returns the old signer, since `reconfigure_stackerdb`/`shrink_stackerdb` was never invoked.

    pub fn reconfigure_stackerdb(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slots: &[(StacksAddress, u32)],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let mut total_slots_read = 0u32;
        for (principal, slot_count) in slots.iter() {
            total_slots_read =
                total_slots_read
                    .checked_add(*slot_count)
                    .ok_or(net_error::OverflowError(
                        "Slot count exceeeds u32::MAX".to_string(),
                    ))?;
            let slots_before_principal = total_slots_read - slot_count;
            for cur_principal_slot in 0..*slot_count {
                let slot_id = slots_before_principal + cur_principal_slot;
                if let Some(existing_validation) =
                    self.get_slot_validation(smart_contract, slot_id)?
                {
                    // this slot already exists.
                    if existing_validation.signer == *principal {
                        // no change
                        continue;
                    }
                }

                debug!("Reset slot {} of {}", slot_id, smart_contract);

                // new slot, or existing slot with a different signer
                let qry = "INSERT OR REPLACE INTO chunks (stackerdb_id,signer,slot_id,version,write_time,data,data_hash,signature) VALUES (?1,?2,?3,?4,?5,?6,?7,?8)";
                let mut stmt = self.sql_tx.prepare(qry)?;
                let args = params![
                    stackerdb_id,
                    principal.to_string(),
                    slot_id,
                    NO_VERSION,
                    0,
                    vec![],
                    Sha512Trunc256Sum([0u8; 32]),
                    MessageSignature::empty(),
                ];

                stmt.execute(args)?;
            }
        }
        debug!("Shrink {} to {} slots", smart_contract, total_slots_read);
        self.shrink_stackerdb(stackerdb_id, total_slots_read)?;
        Ok(())
    }
