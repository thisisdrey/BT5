### Title
Self-triggered `last-borrow-block` griefing lets an underwater borrower indefinitely block liquidation - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
The `liquidate` function's anti-flashloan safeguard reverts any liquidation attempt if the borrower's position recorded a borrow in the current block, exactly mirroring the OpenLeverage TWAP-deviation-revert pattern flagged in the external report: a defensive price/timing check that, instead of merely blocking attackers, can be weaponized by the borrower themselves to prevent liquidation during a market downturn, risking protocol insolvency.

### Finding Description
`liquidate` reads `last-borrow-block` from the position and asserts it does not equal the current `stacks-block-height`, throwing `ERR-LIQUIDATION-BORROW-SAME-BLOCK` unconditionally if it does — there is no minimum debt threshold or exception for legitimately unhealthy positions [2](#0-1) . This field is stamped to `stacks-block-height` on *every* successful `debt-add-scaled` call in `market-vault`, which only requires `scaled-amount > 0` — no minimum borrow size is enforced [1](#0-0) . `borrow` in `market.clar` calls `debt-add-scaled` after only checking `amount > 0`, `debt` is enabled for the asset, and that the position remains healthy post-borrow — but a borrower already near the liquidation threshold and not yet crossing it can still add a dust amount of new debt (e.g. `u1`) each time a block advances, resetting `last-borrow-block` to the newest block [5](#0-4) . Because liquidation is only blocked for the exact block matching `last-borrow-block`, an attacker (the borrower, or their own deployed contract) can watch the mempool/chain tip and, once per block, submit a minimal `borrow` transaction that keeps `last-borrow-block == stacks-block-height` perpetually, so any competing `liquidate` transaction landing in that same block is always rejected. If the borrower can consistently win this per-block race (e.g., by paying higher fees or automating the borrow call), liquidators are permanently prevented from closing the position while the underlying collateral price continues to fall, exactly the scenario the OpenLeverage report warned about: a price/timing safeguard meant to stop external attackers instead stops legitimate defensive liquidations during a crash.

### Impact Explanation
If a borrower can reliably self-grief every block, their position accrues bad debt as collateral value falls further, and once the position becomes deeply underwater, liquidators recover less than the debt owed. The gap is ultimately covered by lender vault (`vault-*`) depositors via socialized bad debt, so this is a protocol insolvency vector — a permanent freezing/loss of user (lender) funds — matching the Critical/High impact classes for this program (protocol insolvency / permanent freezing of funds).

### Likelihood Explanation
Exploitation requires the borrower to win a same-block race against liquidators every block during a price crash, which needs consistent block-inclusion priority (e.g., fee bidding or a privileged relationship with a block builder) and is only economically rational once their position is deeply underwater and they intend to abandon it. This makes the likelihood moderate: it is not a one-shot exploit but a sustained griefing strategy bounded by transaction-fee competition, so it is more of a tail-risk during volatile markets rather than a routinely reachable bug.

### Recommendation
Do not let an unconditional same-block check block *all* liquidations. Instead: (1) only apply the anti-flashloan window when the position was *healthy* before the same-block borrow (i.e., skip the same-block check if the position is already past `ltv-liq-partial` prior to accounting for the new debt), and/or (2) enforce a minimum borrow amount so dust self-borrows cannot cheaply reset `last-borrow-block` every block, and/or (3) use a rolling time-based check (e.g., block height must differ by N, but only suppress liquidation of the *newly added* debt amount rather than the entire position).

### Proof of Concept
1. Borrower opens a position near (but not exceeding) the partial-liquidation LTV threshold.
2. As collateral price drops and the position crosses `ltv-liq-partial`, a liquidator submits `liquidate`.
3. Each block, before the liquidator's transaction can land, the borrower (or their bot/contract) submits `borrow` with `amount = u1` (any enabled debt asset), which succeeds because it only requires `amount > 0` and the post-borrow LTV can still exceed the borrow threshold check for existing debt if e.g. LTV-BORROW check uses pre-existing debt vs. new incremental amount that keeps position marginally "healthy" per `is-healthy-with-mask`, or is executed while collateral partially recovers momentarily — regardless, each successful `borrow` resets `last-borrow-block = stacks-block-height`.
4. Any `liquidate` call landing in that same block reverts with `ERR-LIQUIDATION-BORROW-SAME-BLOCK` per [2](#0-1) , regardless of how far past the liquidation threshold the position is.
5. Repeating step 3 every block indefinitely prevents liquidation while the market continues to fall, growing bad debt.
