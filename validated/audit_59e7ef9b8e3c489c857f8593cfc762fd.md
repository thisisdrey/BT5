### Title
Self-beneficiary `DeleteAccountAction` permanently burns the account's remaining balance instead of transferring it - (File: `runtime/runtime/src/actions.rs`)

### Summary
The reported RMM-core bug is a missing check that a user-supplied recipient address is not the contract itself, causing funds to become permanently stuck. NEAR's `DeleteAccountAction` has an analogous unvalidated recipient field, `beneficiary_id`, which an ordinary account owner fully controls when signing a `DeleteAccount` action (or via `promise_batch_action_delete_account` from a contract they own). If a user sets `beneficiary_id` equal to the very account being deleted, the balance-refund receipt created for that beneficiary is delivered only after the account has already been removed from state, causing the refund to fail and the tokens to be permanently burnt rather than returned to any account.

### Finding Description
`action_delete_account` computes the account's remaining balance and pushes a `Receipt::new_balance_refund` addressed to `delete_account.beneficiary_id`, and only afterwards calls `remove_account` to delete the account from state: [1](#0-0) 

The only validation performed on `beneficiary_id` is that it is a syntactically valid account id — there is no check that it differs from the account being deleted: [2](#0-1) 

Because the balance-refund receipt is emitted as a new receipt (not applied atomically with the deletion), by the time it is actually processed the target account no longer exists in state (it was already removed by `remove_account` in the same action). When this refund receipt (`predecessor_id == "system"`, a single `Transfer` action) is processed, `apply_action` computes `implicit_account_creation_eligible = is_the_only_action && !is_refund`, which evaluates to `false` for refunds: [3](#0-2) 

With `implicit_account_creation_eligible == false`, `check_transfer_to_nonexisting_account` returns `AccountDoesNotExist` because refund receipts are explicitly excluded from implicit account creation ("Refunds don't automatically create accounts, because refunds are free and we don't want some type of abuse"): [4](#0-3) 

Per the protocol's refund semantics, when a refund receipt's execution fails, its deposit is burnt rather than returned to anyone: [5](#0-4) [6](#0-5) 

This is the exact analog of the RMM-core bug: an unprivileged, ordinary signer supplies a recipient (`beneficiary_id`) equal to the entity being emptied (the account itself), and due to lack of validation, the funds end up unrecoverable — except here the outcome is strictly worse than "stuck," since the tokens are provably burnt (removed from total supply) rather than merely held by an existing account.

### Impact Explanation
This causes permanent, unrecoverable loss of the user's remaining account balance at deletion time — real economic loss for any account owner who mistakenly (or is tricked by a wallet/dApp bug into) setting their own account id as `beneficiary_id` in a `DeleteAccountAction`. Because the tokens are burnt rather than sent to a live account, this is not just "funds temporarily stuck" but a genuine deflationary loss of user funds, matching the "permanent freezing/loss of funds" impact bar.

### Likelihood Explanation
Likelihood is moderate: it requires the user (or a wallet/relayer constructing the transaction on their behalf) to set `beneficiary_id` to the same account being deleted. This is a plausible operator/UI mistake (directly analogous to a user passing their own address to a `withdraw`-style call), and nothing in transaction/action validation (`validate_delete_action`, `action_validation.rs:399-403`) prevents it. It is reachable purely from an ordinary signer's `DeleteAccount` action or via a deployed contract calling `promise_batch_action_delete_account` with a caller-supplied beneficiary, requiring no validator/operator privileges.

### Recommendation
- **Short term:** Add a validation check (in `validate_delete_action` in `runtime/runtime/src/action_validation.rs`, or in `action_delete_account` in `runtime/runtime/src/actions.rs`) that rejects a `DeleteAccountAction` whose `beneficiary_id` equals the account being deleted (`account_id`), returning a clear `ActionsValidationError`/`ActionErrorKind` instead of silently generating a refund receipt doomed to fail.
- **Long term:** Consider whether refund receipts targeting an account that no longer exists (or never will) should be caught earlier/synchronously in `action_delete_account` rather than deferred to a separate receipt that fails and burns funds; add fuzz/property tests (e.g., an Echidna-style invariant) asserting that `DeleteAccount` never results in tokens burnt when the beneficiary is any valid, distinct account.

### Proof of Concept
1. Create account `alice.near` with a non-zero balance and no locked stake.
2. `alice.near` signs a transaction containing a single `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "alice.near".parse().unwrap() })` targeting itself (i.e., `receiver_id == signer_id == "alice.near"`), analogous to the existing test pattern in the codebase: [7](#0-6) 
3. `action_delete_account` computes `account_balance = account_ref.amount()`, pushes `Receipt::new_balance_refund(&"alice.near", account_balance)`, then calls `remove_account`, deleting `alice.near` from state: [1](#0-0) 
4. When the emitted balance-refund receipt (predecessor `system`, receiver `alice.near`) is later processed, `apply_action` finds `is_refund == true`, so `implicit_account_creation_eligible == false`; `check_account_existence`/`check_transfer_to_nonexisting_account` returns `AccountDoesNotExist` since the account no longer exists: [4](#0-3) 
5. Because this is a refund receipt whose execution failed, the deposit (the account's entire prior balance) is added to `other_burnt_amount` and permanently removed from total supply, rather than returned to any account: [6](#0-5)

    config: &RuntimeConfig,
    account_id: &AccountId,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    if implicit_account_creation_eligible
        && account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts)
    {
        // OK. It's implicit account creation.
        // Notes:
        // - Transfer action has to be the only action in the transaction to avoid
        // abuse by hijacking this account with other public keys or contracts.
        // - Refunds don't automatically create accounts, because refunds are free and
        // we don't want some type of abuse.
        // - Account deletion with beneficiary creates a refund, so it'll not create a
        // new account.
        Ok(())
    } else {
        Err(ActionErrorKind::AccountDoesNotExist { account_id: account_id.clone() }.into())
    }
}

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.
