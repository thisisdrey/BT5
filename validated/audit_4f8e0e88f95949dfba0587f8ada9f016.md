### Title
Unchecked array-length read causes out-of-bounds read (crash) in TVM precompile input decoding - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The CVE describes a heap-based buffer over-read in GPAC's ISO media box parser, where a length value taken directly from untrusted input is used to index into a buffer without validating it against the buffer's actual size. The analogous pattern in java-tron is in `PrecompiledContracts.extractBytes32Array`, which decodes ABI-encoded precompile call data by reading an attacker-controlled length word and then iterating that many words out of the `DataWord[]` array without any bounds check.

### Finding Description
`extractBytes32Array` reads the element count directly from calldata and loops over it without verifying that `offset + i + 1` stays within `words.length`: [1](#0-0) 

This is inconsistent with the sibling method `extractBytesArray`, defined immediately below it in the same class, which does perform an explicit bounds check (`if (offset > words.length - 1) return new byte[0][];`) before reading the length word, but still does not bound the subsequent loop reads (`words[offset + i + 1]`, `words[offset + bytesOffset + 1]`) against `words.length`: [2](#0-1) 

Because `len` (and `bytesLen`/`bytesOffset`) is fully attacker-controlled (it is decoded from the ABI-encoded `data` parameter passed into the precompiled contract, e.g. via `ValidateMultiSignContract`/batch-validate-sign style precompiles reachable from a TVM `CALL`/`STATICCALL` to the reserved precompile address), a caller can craft an input where the declared array length is much larger than the actual `words` array, causing reads past the end of the backing `DataWord[]`/byte buffer.

### Impact Explanation
An out-of-bounds array read in a precompile invoked from a smart contract will throw an unchecked `ArrayIndexOutOfBoundsException` inside the TVM execution path. Depending on how the surrounding VM exception handling classifies this (see `VM.play`'s generic `RuntimeException` catch block, which treats unknown exceptions specially and logs/records a runtime failure rather than a controlled revert), this can manifest as inconsistent/uncaught failure behavior during contract execution for every node executing the same transaction. Because all full nodes process the same transaction deterministically, a reliable, reproducible OOB read triggered by any contract call is a low-cost griefing/crash vector against precompile execution rather than a fund-theft bug, and severity should be scoped to a node-crash-on-execution class, not corruption of consensus state.

### Likelihood Explanation
This code path is reached by any account able to invoke a contract that calls the affected precompiled contract with attacker-supplied ABI-encoded input, which is the class of anonymous/unprivileged contract-call access explicitly in scope. No special privileges are required, only correctly formed but malicious calldata.

### Recommendation
Add an explicit bounds check in `extractBytes32Array` (and tighten the existing check in `extractBytesArray`) so that the declared length can never cause `offset + i + 1` (or the nested `bytesOffset`/`bytesLen` derived indices) to exceed `words.length`, returning an empty/error result or throwing a controlled, caught exception instead of letting a raw `ArrayIndexOutOfBoundsException` propagate out of precompile decoding.

### Proof of Concept
Construct an ABI-encoded call to a precompiled contract that uses `extractBytes32Array` (e.g., a multi-signature validation precompile), where the length word at `words[offset]` is set to a large value (e.g., `0xFFFFFFFF` truncated via `intValueSafe()`), while the actual `words` array only contains the minimum number of words for a well-formed call. Executing this from a deployed contract via `STATICCALL`/`CALL` to the precompile address triggers the unbounded loop in: [1](#0-0) 
causing an out-of-bounds array access during decoding.

**Note on confidence**: I could not fully trace which concrete precompiled contract class(es) invoke `extractBytes32Array` (the index did not surface the exact call sites/class definitions such as `BatchValidateSign` or `ValidateMultiSign` contract bodies), so I was unable to confirm the exact opcode/address dispatch path end-to-end within the available index. The bounds-check gap itself is directly confirmed in the source shown above.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
