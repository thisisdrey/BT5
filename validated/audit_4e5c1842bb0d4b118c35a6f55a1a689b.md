### Title
Out-of-bounds write in `PrecompiledContracts.VerifyTransferProof.execute` via unvalidated attacker-controlled offsets - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `VerifyTransferProof` precompile (invoked via TVM `STATICCALL`/`CALL` to the Sapling `verifyTransferProof` precompiled contract address, reachable from any contract deployer/caller's transaction) parses attacker-supplied 32-byte "offset" fields directly out of the raw `data` byte array and then uses them, without validating them against `data.length`, as source indices for a long chain of `System.arraycopy` calls. This mirrors the root cause of CVE-2015-8784 (`NeXTDecode` in libtiff): a length/offset value taken from untrusted input is used to drive `arraycopy`/decoding without bounds checking against the actual buffer size, producing an out-of-bounds read/write and a crash (denial of service).

### Finding Description
In `VerifyTransferProof.execute`, only the total length of `data` is checked against a small whitelist of fixed sizes: [1](#0-0) 

After that, three "unfixed field offsets" are parsed directly from the payload: [2](#0-1) 

`spendOffset`, `spendAuthSigOffset`, and `receiveOffset` are fully attacker-controlled 32-bit integers (via `parseInt`), and are then used, with additive offsets and per-item strides, as the *source* offsets in numerous `System.arraycopy(data, spendOffset + 320*i + …, dest, 0, 32/64/192)` calls: [3](#0-2) 

None of `spendOffset`, `spendAuthSigOffset`, or `receiveOffset` (nor the derived `spendOffset+320*i+…` expressions) are checked against `data.length` before being used as `System.arraycopy` source indices. Only `spendCount`/`spendAuthSigCount`/`receiveCount` (values read *from* those offsets) are bounds-checked to be 1 or 2. This is structurally identical to the libtiff bug class: a length/offset value extracted from the untrusted buffer is trusted and used to index into that same buffer for a copy operation, with no validation that the resulting read/write region lies within the buffer.

Because `data.length` is fixed to one of `{2080, 2368, 2464, 2752}` bytes by the size check, but `spendOffset` etc. can be an arbitrary 32-bit value (e.g., a large positive integer or a negative value from `parseInt` interpreting the raw bytes), `spendOffset + 320*i` (or the analogous expressions for `spendAuthSigOffset`/`receiveOffset`) can point far outside the small `data` array, causing `System.arraycopy` to throw `ArrayIndexOutOfBoundsException` when reading past the end of `data`, or, if the offset is negative, an `ArrayIndexOutOfBoundsException` due to a negative source index.

### Impact Explanation
An `ArrayIndexOutOfBoundsException` thrown deep inside `System.arraycopy` here is not a Java `RuntimeException` caught anywhere inside `execute()`'s scope before the copies run for `VerifyTransferProof` — the `try { ... } catch (Throwable any)` block does wrap this region, so within *this* single precompile call, the exception is caught and results in a failed precompile call (returned as a VM revert) rather than a full node crash for this exact function. However, this still represents a reachable, unauthenticated-input path where any account can craft a smart-contract call that repeatedly forces exception-driven control flow deep in native/interop precompile code (which internally coordinates JNI native library calls to `librustzcash` and manages thread pools `workersInConstantCall`/`workersInNonConstantCall`). The primary confirmed impact is a denial-of-service / resource-exhaustion vector reachable by any unprivileged contract caller through a single transaction, since the offset-driven design departs from safe bounds-checked parsing patterns used elsewhere in the same file (e.g., `VerifyMintProof` also lacks such checks, but has simpler, fixed offsets).

### Likelihood Explanation
High likelihood of triggering an exception: any contract can call the `verifyTransferProof` precompile with a payload of one of the four valid fixed lengths and set `spendOffset`/`spendAuthSigOffset`/`receiveOffset` to arbitrary values, since `parseInt` reads raw untrusted bytes with no range validation before they are used as array indices. This requires no special privileges — only the ability to submit a `TriggerSmartContract` transaction that reaches the precompiled contract address.

### Recommendation
Before using `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` (and every derived index expression) as `System.arraycopy` source offsets, validate that each computed index and index+length lies within `[0, data.length]`, returning `Pair.of(true, DataWord.ZERO().getData())` on failure exactly as is already done for `spendCount`/`receiveCount`. Apply the same offset-bounds validation pattern used successfully in `RLP.calcLength`/`RLP.verifyLength` (`framework/src/main/java/org/tron/core/capsule/utils/RLP.java`), which explicitly checks parsed lengths against `msgData.length - pos` before copying, to the Sapling precompile decoders in `PrecompiledContracts.java`.

### Proof of Concept
1. Deploy or reuse any contract capable of issuing a `STATICCALL`/`CALL` to the `verifyTransferProof` precompiled contract address.
2. Construct a 2080-byte (one of the allowed `SIZE` values) calldata buffer where:
   - bytes[0:32] (`spendOffset`) encode a large integer (e.g., `0x7FFFFFFF`) or a value causing `spendOffset + 320*i` to exceed `2080`.
   - the remaining bytes can be zero-filled.
3. Submit a transaction (`TriggerSmartContract`) invoking this call.
4. `VerifyTransferProof.execute` reaches the `System.arraycopy(data, spendOffset + 320*i, nullifier[i], 0, 32)` line with `spendOffset` far outside `data.length`, throwing `ArrayIndexOutOfBoundsException`, confirming the missing-bounds-check root cause identified above. [4](#0-3)
