Missing slippage/minimum-output enforcement in `ExchangeTransactionActuator` enables bonding-curve price-manipulation theft analogous to Eminence - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java)

### Summary
The Eminence hack exploited a bonding-curve AMM where an attacker could manipulate the curve's spot price within a short window (mint/burn cycle) and force a victim's subsequent trade to execute at a manipulated, unfavorable price, extracting value with no minimum-output check enforced on-chain. TRON's native `Exchange`/`ExchangeTransactionContract` mechanism is structurally the same primitive: a single reserve pool priced by a Bancor-style bonding curve (`ExchangeProcessor`/`SafeExchangeProcessor`), reachable directly by any unprivileged, signed transaction. The actuator that executes trades against this curve never enforces the caller-supplied minimum-received amount, allowing the same class of price-manipulation extraction.

### Finding Description
`ExchangeTransactionContract` carries a `tokenExpected`/`getExpected()` field that is clearly intended as slippage protection (the minimum amount of the other token the trader expects to receive). In `doValidate()` it is checked only for being `> 0`: [1](#0-0) 

However, `execute()` computes the actual output via the bonding curve (`exchangeCapsule.transaction(...)`) and never compares it against `tokenExpected` before crediting the trade: [2](#0-1) 

The bonding-curve math itself lives in `ExchangeCapsule.transaction()`, which instantly mutates `firstTokenBalance`/`secondTokenBalance` reserves based on a Bancor-relay formula (`ExchangeProcessor`/`SafeExchangeProcessor`), the same style of curve Eminence used: [3](#0-2) [4](#0-3) 

Because there is no on-chain enforcement of `tokenExpected`, any attacker who can get their exchange-buy/sell transactions ordered around a victim's transaction (front-run/back-run within the same block, which any unprivileged transaction broadcaster can attempt) can move the pool's reserve ratio before the victim's trade executes, causing the victim to receive an amount far below what they intended — exactly the "manipulate the bonding curve then extract value from the resulting mispriced trade" pattern from the Eminence report, minus only the flash-loan primitive (not needed here since java-tron has no atomic composability requirement — sequential same-block transactions suffice).

### Impact Explanation
An attacker can sandwich any `ExchangeTransactionContract` trade: submit a manipulating trade before the victim's transaction and a reversing trade after it, extracting the difference as unauthorized value transfer from the victim to the attacker. Because `tokenExpected` is validated for positivity but never enforced against the realized output, the protocol offers no on-chain protection against this, making systematic value extraction from TRX/TRC10 exchange pools possible — a concrete theft-of-funds impact reachable purely through unprivileged, signed transactions.

### Likelihood Explanation
High for any liquid Exchange pool: the attack requires only ordinary account balance and gas/bandwidth to submit two additional exchange transactions surrounding a target trade in the same block — no special privileges, precompiles, or contract deployment needed. The `Exchange` feature (TRX10/TRX Bancor-style exchange) is a long-standing core java-tron feature exposed directly through `ExchangeTransactionContract` and the corresponding wallet/gRPC/HTTP APIs.

### Recommendation
Enforce `tokenExpected` in `ExchangeTransactionActuator.execute()` (or `doValidate()` immediately before mutating state): after computing `anotherTokenQuant` from `exchangeCapsule.transaction(...)`, reject the transaction with `ContractExeException`/`ContractValidateException` if `anotherTokenQuant < tokenExpected`. This restores the minimum-received/slippage guarantee that the field was designed for and blocks profitable sandwich extraction.

### Proof of Concept
1. Attacker observes a pending `ExchangeTransactionContract` transaction from a victim in the mempool trading `tokenID` for `anotherTokenID` on exchange `exchangeId`.
2. Attacker submits Tx A: a large trade in the same direction as the victim, shifting `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction()` so that the bonding-curve price is now unfavorable for the next trade of `tokenID`.
3. Victim's transaction executes: `ExchangeTransactionActuator.execute()` computes `anotherTokenQuant` off the now-manipulated reserves; since `tokenExpected` is never checked against this value, the trade succeeds with the victim receiving far less than intended.
4. Attacker submits Tx B: reverses their position by trading back, realizing the price difference as profit funded by the victim's loss.

Note: I could not find any TVM/precompile-level flash-loan primitive in java-tron equivalent to Eminence's mint/burn-in-one-call; the exploit path here relies on transaction ordering within a block rather than atomic composability, which is the closest reachable analog given the constraints of this codebase.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
