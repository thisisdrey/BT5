#NoV ulnerability found for this question. [1](#0-0) 

The `NotifyOnTransfer` struct includes an optional `state_init` field that can be provided by the attacker through the `msg` parameter in token callbacks. [2](#0-1) 

When `do_auth_call` executes, it applies the `state_init` action before calling `on_auth()` in the same receipt.

**The binding to verify:**
```
code_at_derived_account_id == code_committed_by_StateInit.global_contract_id
```

**Analysis:**

The NEP-616 protocol guarantees that a deterministic account ID is derived as `"0s" .. hex(keccak256(borsh(StateInit))[12..32])`, where `StateInit = global_contract_id + initial_storage`. [3](#0-2) 

When a `state_init` action is executed on NEAR:
1. The protocol derives the account ID from the `StateInit` hash
2. If the account does not exist, it creates it with the code referenced by `global_contract_id` and the initial storage
3. If the account **already exists**, the protocol **silently reuses the existing account** without modifying its code or storage

The attacker's proposed exploit:
1. Attacker deploys a contract at a deterministic ID independently (with their own code)
2. Attacker sends a token callback with a `state_init` that derives to the same ID but references a different `global_contract_id`
3. Attacker expects the protocol to deploy new code at that ID

**Why this fails:**

NEP-616 and NEAR's account model do not allow code replacement via `state_init` on an already-initialized account. The protocol treats `state_init` as an initialization action only. If an account exists, the action succeeds but does not change the account's code or state. This is a **protocol-level guarantee**, not a contract-level one.

The binding holds because:
- The code executing at the derived account ID is whatever was deployed there first (either by the attacker independently, or by a legitimate `state_init` call)
- The `global_contract_id` in the `StateInit` only determines what code is deployed **if the account does not yet exist**
- Once an account exists, subsequent `state_init` calls to the same derived ID are no-ops with respect to code

The attacker cannot:
- Deploy code at a deterministic ID they don't control the initial `state_init` for
- Replace code at an already-initialized deterministic ID via `state_init`
- Cause a mismatch between the code and the `global_contract_id` commitment

The invariant is maintained by the NEAR protocol itself, not by contract-level guards. [4](#0-3)
