Based on my research, I found a strong analog in the java-tron `Exchange*` (TRC10 bonding-curve exchange) subsystem. This is reachable by any unprivileged account via `ExchangeTransactionContract`/`ExchangeWithdrawContract`, matching the "unprivileged actor exploits reward math via many small operations from many accounts" pattern in the DEOS report.

### Title
Floating-point precision loss in legacy `ExchangeProcessor` bonding-curve math allows value extraction via repeated small trades - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
The default (non-hardened) TRC10 Bancor-style exchange calculation in `ExchangeProcessor` performs the core AMM formula using Java `double` arithmetic (`Math.pow`/`Maths.pow`) rather than exact/decimal math, then truncates the result to `long`. Because this is invoked from a publicly reachable actuator (`ExchangeTransactionActuator`) with attacker-controlled trade sizes, repeated small trades can accumulate rounding-favorable outcomes analogous to the DEOS `luckydraw` "wool-pulling" pattern where an attacker automates many small, cheap operations for a disproportionately large aggregate return.

### Finding Description
`ExchangeCapsule.transaction()` selects between the legacy `ExchangeProcessor` (double-based) and the newer `SafeExchangeProcessor` (BigDecimal-based, exact-overflow-checked) depending on the `allowHardenExchangeCalculation` dynamic property, gated behind `AbstractExchangeActuator.allowHarden()`: [1](#0-0) [2](#0-1) 

The legacy processor computes the bonding-curve exchange using floating-point `pow` and truncates via a `(long)` cast, which discards fractional remainder in the attacker's favor for each trade: [3](#0-2) 

Both `ExchangeTransactionActuator.execute()`/`doValidate()` and `ExchangeWithdrawActuator` route unprivileged, attacker-supplied `tokenQuant` values straight into this calculation with no minimum trade size or per-account/per-block rate limiting: [4](#0-3) 

The unit test `testStrictMath` in the repository itself demonstrates that the legacy (double, non-strict) path and the strict/hardened path produce *different* results for the same inputs (`Assert.assertNotEquals(anotherTokenQuant, result)`), confirming the precision divergence is real and quantifiable: [5](#0-4) 

This is directly analogous to the DEOS incident: instead of exploiting a lottery odds bug, an attacker here exploits a floating-point/truncation bias in a value-conserving AMM formula, executed automatically many times (potentially from many Sybil accounts to bypass any per-account limits) to accumulate profit that should not exist under an exact/conserved-value model.

### Impact Explanation
Each individual trade's bias is small (sub-unit rounding), but because the operation is cheap (`calcFee()` returns `0` for `ExchangeTransactionActuator`) and unlimited in repetition/account count, an attacker can programmatically repeat the trade thousands of times across many accounts to drain the counter-token reserve of the exchange pool at the expense of other liquidity participants/injectors — an unbacked-balance / theft-of-funds condition consistent with the reported "over 300 accounts... thousands of EOS accumulated" pattern.

### Likelihood Explanation
High: the vulnerable path is the *default* code path (hardened calculation is opt-in via a committee-gated dynamic property), the actuators are reachable by any signed transaction from any account, trade fees are zero, and account creation on TRON is cheap, mirroring the low-cost Sybil account creation described in the DEOS report.

### Recommendation
Enable `allowHardenExchangeCalculation` (the `SafeExchangeProcessor`/BigDecimal exact-math path) by default, or remove the legacy double-based `ExchangeProcessor` code path entirely so all exchange trades use exact decimal arithmetic with proper truncation-direction control (rounding always in favor of the pool, never the trader), plus add balance-invariant checks (as already partially done in the hardened path) to reject any trade sequence that would decrease total pool value.

### Proof of Concept
1. Create an `Exchange` pool via `ExchangeCreateContract` with a chosen `firstTokenBalance`/`secondTokenBalance` ratio.
2. Leave `allowHardenExchangeCalculation` at its default (disabled) value so `ExchangeCapsule.transaction()` uses `ExchangeProcessor` (double math).
3. From a low-balance account, repeatedly submit small `ExchangeTransactionContract` trades (buy/sell cycles) — as shown by `ExchangeCapsuleTest.testExchange` and `ExchangeProcessorTest.testStrictMath`, the double-math result differs from the exact result on the same inputs, and each cycle costs 0 fee (`ExchangeTransactionActuator.calcFee()` returns 0).
4. Repeat via newly created accounts to scale the exploit, analogous to the DEOS `luckydraw` Sybil-account automation. [6](#0-5) 

**Caveat**: I was unable to directly view the default numeric value assigned to `allowHardenExchangeCalculation` in `DynamicPropertiesStore.java` before running out of tool calls; my analysis assumes it follows the same "default 0 / opt-in via committee proposal" pattern as other `allow*` feature flags in java-tron (e.g., `allowSameTokenName`). If this flag is enabled by default in this specific fork, the legacy vulnerable path would not be reachable and this finding would not apply — this should be verified directly in a follow-up session before treating this as confirmed-exploitable.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
