### Title
Unbounded resource exhaustion via stalled SSHReceivePack streams with no stdin idle timeout - (File: internal/gitaly/service/ssh/receive_pack.go)

### Summary
`sshReceivePack` spawns a goroutine that performs `io.Copy(pw, stdin)` from a `streamio.NewReader` wrapping `stream.Recv()`, with no per-message or per-stream idle timeout. An unprivileged client with push access can open the stream, send only the mandatory first `SSHReceivePackRequest`, and then withhold further `Stdin` chunks indefinitely while keeping the TCP/HTTP2 connection alive, causing the copy goroutine, the `os.Pipe()` file descriptors, and the spawned `git receive-pack` child process to remain alive for the life of the connection.

### Finding Description
`SSHReceivePack` reads the first request, validates it via `validateFirstReceivePackRequest`, and calls `sshReceivePack` [1](#0-0) . Inside `sshReceivePack`, `stdin` is a `streamio.NewReader` that calls `stream.Recv()` on demand [2](#0-1) . A dedicated `os.Pipe()` is created and a goroutine does `io.Copy(pw, stdin)` followed by `pw.Close()`, explicitly to prevent `cmd.Wait()` from blocking forever on the internal `exec.Cmd` stdin-copy goroutine [3](#0-2) . The comment at lines 119-124 explicitly acknowledges: "if the client never closes stdin, the goroutine may outlive the RPC" [4](#0-3) .

There is no read/inactivity deadline placed on `stream.Recv()` and no context-driven cancellation tied to elapsed time without data — only the transport-level gRPC keepalive settings (`MinTime: 10s`, `Time: 5m`, no explicit `Timeout`) apply, which detect dead TCP connections at the HTTP/2 ping layer, not idle application data [5](#0-4) . An attacker's gRPC client library will transparently answer HTTP/2 PING frames without the attacker's application code ever needing to send further protobuf `Stdin` messages, so the connection stays "alive" from gRPC's perspective while `stream.Recv()` blocks forever waiting for the next frame.

Because the spawned `git-receive-pack` process (`cmd`, line 160) also blocks reading from `pr` (the read end of the pipe), `cmd.Wait()` at line 172 blocks indefinitely as well, keeping a full process, two pipe file descriptors, and the copy goroutine alive per stalled request. No default per-RPC concurrency limit is configured for `SSHReceivePack` in the shipped config, so nothing bounds the number of concurrent stalled invocations an authenticated pushing user (or many colluding users on their own forks) can create.

### Impact Explanation
Each stalled stream consumes: one OS pipe (2 FDs), one Go goroutine, and one live `git receive-pack` OS process for as long as the attacker keeps the TCP connection responsive to HTTP/2 pings. Repeating this concurrently (from the attacker's own repos/forks, which they are entitled to push to) exhausts Gitaly's file descriptors, process table entries, and goroutines, degrading or crashing the shared Gitaly node and thereby all repositories it serves — a resource-exhaustion / availability impact matching GitLab's DoS bounty class.

### Likelihood Explanation
The only precondition is push access to any repository, including a user's own fork — a capability every non-guest GitLab user has. The exploit requires only opening a bidirectional gRPC stream, sending one valid first message, and never sending a second message while letting the underlying HTTP/2 client answer transport pings automatically. This is trivial to script and fully repeatable, and no elevated privilege, secret, or non-default configuration is required.

### Recommendation
Bound the lifetime of the stdin-copy goroutine and the RPC independent of transport-level keepalive: enforce an application-level inactivity timeout on `stream.Recv()` (e.g., wrap the read in a `context.WithTimeout`/`select` that cancels the stream/aborts the RPC if no `Stdin` chunk arrives within a bounded interval), and/or apply a default concurrency limit for `SSHReceivePack`/`SSHUploadPack` per user or per repository so that stalled streams cannot accumulate unbounded goroutines, pipes, and child processes.

### Proof of Concept
```go
func TestSSHReceivePack_StalledStreamLeaksResources(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, repo, _ := setupSSHService(t) // reuse existing test setup helpers
    client, conn := newSSHClient(t, cfg.SocketPath)
    defer conn.Close()

    before := runtime.NumGoroutine()

    const n = 50
    for i := 0; i < n; i++ {
        stream, err := client.SSHReceivePack(ctx)
        require.NoError(t, err)
        require.NoError(t, stream.Send(&gitalypb.SSHReceivePackRequest{
            Repository: repo,
            GlId:       "user-1",
        }))
        // Deliberately send no further messages and do not close the stream.
    }

    time.Sleep(2 * time.Second) // allow goroutines/pipes to be created
    after := runtime.NumGoroutine()

    // Expect goroutine count to have grown roughly by n and to not be reclaimed,
    // demonstrating unbounded per-request resource retention.
    require.Greater(t, after-before, n/2)
}
```
Expected result: goroutine count grows by approximately `n` and does not shrink until the connection is forcibly closed or the process's keepalive `Time` (5 minutes) elapses, demonstrating unbounded per-stream resource retention for the duration the attacker keeps the connection responsive to HTTP/2 pings.

	// `io.Reader` and never closed, the goroutine will never end. This leads to
	// `cmd.Wait()` being blocked indefinitely.

	// problem for the `SSHReceivePack` RPC, so a pipe and goroutine have been
	// created explicitly to prevent `cmd.Wait()` from blocking indefinitely.

	}

		// already allows.
