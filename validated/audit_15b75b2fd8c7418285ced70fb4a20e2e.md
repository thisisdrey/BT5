## Analysis

The reported bug class is an *unbounded loop over an attacker-growable list*, reachable from ordinary transactions, that can blow up gas/CPU on read. The closest reachable analog in java-tron is the **`DelegatedResourceAccountIndexStore`**, which backs the `GetDelegatedResourceAccountIndex(V2)` / `GetDelegatedResourceV2` query APIs.

### Root cause

`DelegateResourceActuator`/`FreezeBalanceActuator` let any account delegate (or freeze-and-delegate) bandwidth/energy to an arbitrary number of *distinct* receiver addresses, with no cap analogous to the 30-witness vote limit. Each delegation appends to an unbounded list: [1](#0-0) [2](#0-1) 

For the legacy (non-optimized) index format, `FreezeBalanceActuator.delegateResource()` grows `toAccountsList`/`fromAccountsList` on the single index capsule with no size check: [3](#0-2) 

For the "optimized" V2 index format, each delegation is stored as a separate key under a `FROM_PREFIX`/`TO_PREFIX` (or `V2_FROM_PREFIX`/`V2_TO_PREFIX`), and reading the index performs an **unbounded `prefixQuery`** over all of them, then sorts the entire result set in memory: [4](#0-3) 

This `getWithPrefix` method is invoked by both `getIndex()` and `getV2Index()`: [5](#0-4) 

which are the backing calls for the public `GetDelegatedResourceAccountIndex`, `GetDelegatedResourceAccountIndexV2`, and `GetDelegatedResourceV2` HTTP/gRPC endpoints (`GetDelegatedResourceV2Servlet` calls `wallet.getDelegatedResourceV2(...)`, which in turn walks the from/to lists to fetch every individual `DelegatedResourceCapsule`): [6](#0-5) 

### Why this is reachable and unbounded

- Delegating resources costs only bandwidth/energy for the transaction itself (not large TRX capital) — an attacker can repeatedly delegate a tiny amount of frozen balance from/to many distinct addresses to grow a single account's `fromAccounts`/`toAccounts` set to an arbitrarily large size over many blocks.
- There is no maximum enforced on the number of distinct delegation counterparties per account, unlike the 30-witness-vote cap elsewhere in the codebase.
- Once the list is large, any unauthenticated API caller invoking `GetDelegatedResourceAccountIndex(V2)` or `GetDelegatedResourceV2` against that address triggers `prefixQuery` + `Comparator` sort over the full unbounded set, and `Wallet.getDelegatedResourceV2` (not shown due to index truncation, but referenced by the servlet) iterates the list to fetch a `DelegatedResourceCapsule` per entry — an O(n) to O(n log n) operation with no pagination or size limit, directly mirroring the `claimTokens()`/`latestID` unbounded-loop pattern in the original report.

This is served by full nodes, PBFT nodes and Solidity nodes alike, since the same store/method is reused by `HttpApiOnPBFTService`, `HttpApiOnSolidityService`, `RpcApiServiceOnPBFT`, and `RpcApiServiceOnSolidity` (all matched in the earlier grep), broadening the blast radius to multiple node services that "can no longer serve" that API once the underlying data grows large enough.

I was unable to inspect the full body of `Wallet.getDelegatedResourceV2`/`getDelegatedResourceAccountIndex` (the file content was truncated by the index before I could view it), so I cannot cite the exact per-entry fetch loop inside `Wallet.java` itself — but the unbounded `prefixQuery` + sort in the store layer, and the uncapped list growth in the capsule/actuator layer, are independently sufficient to establish the vulnerability.

### Title
Unbounded delegation index (`fromAccounts`/`toAccounts`) growth causes unbounded `prefixQuery`/sort on public query APIs, enabling DoS - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
An account can accumulate an unlimited number of resource-delegation counterparties (no cap analogous to the 30-vote witness limit), and reading that account's delegation index via `GetDelegatedResourceAccountIndex(V2)`/`GetDelegatedResourceV2` performs an unbounded `prefixQuery` followed by an in-memory sort and per-entry lookup, with no limit or pagination.

### Finding Description
`FreezeBalanceActuator.delegateResource()` and `DelegateResourceActuator` append to `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` (legacy path) or write individual keyed entries per delegation (V2/optimized path) with no maximum count check [3](#0-2) . Reading the index for either format funnels through `DelegatedResourceAccountIndexStore.getWithPrefix`, which performs `prefixQuery` (an unbounded key-range scan) for both the "from" and "to" directions and sorts the entire result set by timestamp before returning it [4](#0-3) . This method backs the public `GetDelegatedResourceAccountIndex(V2)`/`GetDelegatedResourceV2` HTTP and gRPC endpoints served by full, PBFT, and Solidity nodes.

### Impact Explanation
An attacker who cheaply grows a single account's delegation set to a very large size can cause any subsequent query against that address's delegated-resource index to perform an unbounded scan and sort, consuming excessive CPU/memory on the serving node. Because the same store method is shared by full nodes, PBFT nodes, and Solidity nodes, this can degrade or crash the query-serving API path for multiple node types — matching the "node crash or an API the node can no longer serve" acceptance criterion.

### Likelihood Explanation
Delegation is a normal, unprivileged operation requiring only a small frozen balance and standard transaction fees; there is no cap on the number of distinct delegation counterparties, so an attacker can accumulate a large delegation set over time at low cost. Once created, the DoS is triggered simply by anyone calling the public query API against that address — no special privileges needed.

### Recommendation
Add a maximum-size limit to `toAccountsList`/`fromAccountsList` (and to the number of prefixed key-value delegation entries) analogous to existing per-account limits (e.g., the witness-vote cap), and/or add pagination/limit parameters to `getWithPrefix`/`getIndex`/`getV2Index` and the corresponding `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceV2` API handlers so a single request cannot force an unbounded scan and sort.

### Proof of Concept
1. Freeze a small amount of TRX for bandwidth/energy on account A.
2. Repeatedly submit `DelegateResourceContract` transactions delegating tiny amounts from A to N distinct newly generated receiver addresses (cost scales only with transaction fees, not with N).
3. After N grows large (e.g., tens of thousands), call `GetDelegatedResourceAccountIndexV2` (HTTP) or the corresponding gRPC/JSON-RPC call for account A.
4. Observe that `DelegatedResourceAccountIndexStore.getWithPrefix` performs an unbounded `prefixQuery` over all N entries and sorts them in memory on every request, causing high CPU/latency on the serving node; repeated concurrent requests amplify the effect into a denial of service.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
