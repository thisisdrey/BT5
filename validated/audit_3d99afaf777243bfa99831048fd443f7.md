### Title
`transferAllToken` performs unchecked, unsafe TRC10 asset transfer on SELFDESTRUCT with no validation - ([File: actuator/src/main/java/org/tron/core/vm/utils/MUtil.java])

### Summary
The Blueberry `HardVault.deposit()` bug class is "no validation before crediting/moving a token, only an amount check." The java-tron analog is `MUtil.transferAllToken()`, which moves **all** TRC10 asset balances from a self-destructing contract to its beneficiary during the `SELFDESTRUCT` opcode, but — unlike the sibling helpers `transfer()` and `transferToken()` in the same file — it performs **no validation at all**: no address validity check, no same-address check, no asset-existence check, and critically, no overflow-safe arithmetic.

### Finding Description
In `MUtil.java`, `transfer()` and `transferToken()` both call `VMUtils.validateForSmartContract(...)` before moving balances, which validates addresses, checks the asset actually exists (`deposit.getAssetIssue(...)`), and uses `addExact` to check for overflow: [1](#0-0) [2](#0-1) 

By contrast, `transferAllToken()` — invoked from `Program.java` as part of `SELFDESTRUCT`/`suicide` handling — has none of these checks: [3](#0-2) 

Specifically:
- It never calls `VMUtils.validateForSmartContract` or any equivalent.
- It uses plain `+` (`toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount`) instead of the `addExact`-based overflow check used everywhere else in the same class and in `VMUtils.validateForSmartContract` (compare with `RepositoryImpl.addTokenBalance`, which also enforces bounds via `addAssetAmountV2`): [4](#0-3) 
- It does not check `fromAddress != toAddress`, nor that `toAddress` is a valid/allowed destination.
- It bypasses the asset-issue-existence and per-asset limit checks that `AssetIssueCapsule`/`AccountCapsule.addAssetAmountV2` normally perform through the standard `addTokenBalance` code path (`RepositoryImpl.addTokenBalance`, lines 871-900), instead writing raw protobuf map values directly via `Protocol.Account.Builder.putAssetV2`.

This mirrors the reported bug class precisely: a token-moving code path exists that skips the validation logic present in "sibling" functions that handle the same kind of operation, creating a route for unchecked/unsafe token accounting.

### Impact Explanation
Because the merge of asset balances during `SELFDESTRUCT` uses unchecked `long` addition instead of `addExact`, a contract owner/deployer can craft a self-destructing contract holding large TRC10 balances that, when merged into the beneficiary's existing balance, silently overflows `long`, producing a corrupted (potentially negative or wrapped) balance in the beneficiary account. This can result in **an unbacked/incorrect balance** — either inflating (unbacked balance / theft of funds when spent later) or corrupting (permanent freezing of funds) the beneficiary's or destructing contract's own token accounting. It also skips asset-issue existence checks, meaning stale/invalid `tokenId` entries in an account's asset map could be propagated without the same guardrails enforced elsewhere in the code (e.g., in `TransferAssetActuator.validate()` or `VMUtils.validateForSmartContract`).

### Likelihood Explanation
Any unprivileged contract deployer can trigger this by deploying and self-destructing a contract that holds TRC10 token balances close to `Long.MAX_VALUE` relative to the beneficiary's existing balance for the same `tokenId` — a scenario fully reachable via a single signed `TriggerSmartContract` transaction executing `SELFDESTRUCT`, requiring no special privileges.

### Recommendation
Add the same validation used in `MUtil.transfer()`/`transferToken()` to `transferAllToken()`: validate `fromAddress`/`toAddress`, verify asset existence via `deposit.getAssetIssue(tokenId)`, and use overflow-safe (`addExact`) arithmetic when merging `AssetV2` map entries, or route through `Repository.addTokenBalance` (which already enforces this) instead of manipulating the protobuf builder maps directly.

### Proof of Concept
1. Deploy Contract A; have it accumulate a TRC10 token balance `X` for `tokenId=T`.
2. Have beneficiary account B already hold a TRC10 balance `Y` for the same `tokenId=T`, chosen such that `X + Y > Long.MAX_VALUE`.
3. Trigger Contract A's `SELFDESTRUCT(B)`.
4. `MUtil.transferAllToken(deposit, A, B)` is invoked (via `Program.java`'s suicide handling), executing `toBuilder.getAssetV2Map().getOrDefault(T, 0L) + amount` without overflow checking, silently wrapping the resulting `long` value in B's `AssetV2` map — corrupting B's TRC10 balance for token `T` without any transaction failure or validation error, unlike the equivalent `transferToken` path which would have rejected/failed under `VMUtils.validateForSmartContract`'s `addExact` overflow check.

  public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }

  @Override
  public long addTokenBalance(byte[] address, byte[] tokenId, long value) {
    byte[] tokenIdWithoutLeadingZero = ByteUtil.stripLeadingZeroes(tokenId);
    AccountCapsule accountCapsule = getAccount(address);
    if (accountCapsule == null) {
      accountCapsule = createAccount(address, Protocol.AccountType.Normal);
    }
    long balance = accountCapsule.getAssetV2(new String(tokenIdWithoutLeadingZero));
    if (value == 0) {
      return balance;
    }

    if (value < 0 && balance < -value) {
      throw new RuntimeException(
          StringUtil.createReadableString(accountCapsule.createDbKey())
              + " insufficient balance");
    }
    if (value >= 0) {
      accountCapsule.addAssetAmountV2(tokenIdWithoutLeadingZero, value, getDynamicPropertiesStore(),
          getAssetIssueStore());
    } else {
      accountCapsule
          .reduceAssetAmountV2(tokenIdWithoutLeadingZero, -value, getDynamicPropertiesStore(),
              getAssetIssueStore());
    }
    Key key = Key.create(address);
    accountCache.put(key, Value.create(accountCapsule,
         accountCache.get(key).getType().addType(Type.DIRTY)));
    return accountCapsule.getAssetV2(new String(tokenIdWithoutLeadingZero));
  }
