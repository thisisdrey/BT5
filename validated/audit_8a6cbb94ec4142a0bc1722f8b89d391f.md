### Title
NativeWithdraw to a non-existent receiver_id permanently strands unwrapped NEAR in the Verifier's own account with no re-credit path - (File: contracts/defuse/src/contract/tokens/nep141/native.rs)

### Summary
`State::native_withdraw` in `contracts/defuse/src/contract/intents/state.rs` debits `owner_id`'s wNEAR `token_balances` and schedules `ext_wnear::near_withdraw` followed by `Contract::do_native_withdraw`. `do_native_withdraw` only checks that `near_withdraw` succeeded and then fires `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)` with no further resolve/callback to detect failure or re-credit the owner. If `receiver_id` is a named account that was never created, the transfer action fails at the protocol level (NEAR does not auto-create non-implicit accounts on transfer), leaving the unwrapped NEAR permanently held by the Verifier contract's own account with no bookkeeping entry pointing to it.

### Finding Description
The binding claimed by the ledger is:
`internal_sub_balance(owner_id, wNEAR, amount) == NEAR delivered to receiver_id OR re-credited to owner_id.token_balances`

Tracing the code:
1. `State::native_withdraw` (`contracts/defuse/src/contract/intents/state.rs:212-240`) calls `self.withdraw(owner_id, [(wnear_token_id, amount)], ..., false)`, which internally invokes `internal_sub_balance`, debiting `owner_id`'s wNEAR balance immediately and synchronously — this happens in the same transaction, unconditionally, before any promise resolves.
2. It then schedules `ext_wnear::near_withdraw(amount)` (unwraps wNEAR into real NEAR credited to the Verifier's own account) `.then(...)` `do_native_withdraw(withdraw)`.
3. `Contract::do_native_withdraw` (`contracts/defuse/src/contract/tokens/nep141/native.rs:11-19`):
```rust
#[private]
pub fn do_native_withdraw(withdraw: NativeWithdraw) -> Promise {
    require!(
        promise_result_checked_void(0).is_ok(),
        "near_withdraw failed",
    );
    Promise::new(withdraw.receiver_id).transfer(withdraw.amount)
}
```
This only verifies that `near_withdraw` (step 2) succeeded. It then fires a bare `Promise::new(receiver_id).transfer(amount)` with **no `.then(...)` resolve callback**. There is no mechanism anywhere in this function, or reachable from it, that inspects whether the final `transfer` promise itself succeeds or fails, and therefore no code path that re-credits `owner_id.token_balances` if the transfer fails.

If `withdraw.receiver_id` is a syntactically valid but never-created named account (e.g. `"nonexistent-account.near"`), the NEAR protocol's `Transfer` action fails at execution because transferring to a non-existent, non-implicit account does not create it — the receipt fails with `AccountDoesNotExist`. Since `do_native_withdraw` has no continuation, the failed promise silently vanishes: the debit from `owner_id.token_balances` already committed in step 1 is never reversed, and the unwrapped NEAR (already credited to the Verifier's own account balance by `near_withdraw` in step 2) has no on-chain owner reference tying it back to `owner_id`.

Because `withdraw.amount`, `withdraw.receiver_id` are attacker-controlled fields inside a self-signed `DefusePayload::NativeWithdraw` intent, and the attacker is withdrawing their own wNEAR balance to an account they name, an attacker (or, more relevantly, any signer including one testing this innocuously) can trigger this loss of the binding by naming a receiver_id that does not exist. No privileged role, relayer key, or victim signature is required — the signer only withdraws from their own account, but the funds become permanently unrecoverable by anyone, including that very signer.

None of the existing guards (`MultiPayload::verify`, `has_public_key`, `verify_intent_nonce`, `Lock::get_mut`, `#[private]`) address this — they authenticate the signer and intent but do not validate `receiver_id` existence, and `#[private]` on `do_native_withdraw` only restricts the caller to be the contract itself (i.e., it's a valid callback), it does nothing about the missing resolve/re-credit logic for the final transfer.

### Impact Explanation
Real NEAR value (unwrapped from wNEAR) becomes permanently stranded in the Verifier contract's own account balance with no ledger entry (`token_balances`) crediting it to any account, while the corresponding wNEAR debit from `owner_id` already occurred and is never reversed. This matches "user funds permanently frozen" / "funds owed by the ledger exceed what it can pay out" (Critical): the Verifier's actual NEAR balance is no longer matched by the sum of all `token_balances` entries it is obligated to honor, since the withdrawn amount vanished from the ledger without a corresponding real-world delivery. This is repeatable per attempt/per account — every native withdraw naming a non-existent receiver strands the same class of funds, growing the shortfall each time.

### Likelihood Explanation
Preconditions: an account with a wNEAR balance in the Verifier (attacker's own funds are sufficient — they don't need anyone else's balance) and a `NativeWithdraw` intent naming any named account string that has never been created on-chain. This is trivial and cheap to trigger (just craft a `receiver_id` string, no special deploys needed) and fully reproducible by any unprivileged signer against their own balance, and by extension, this pattern could also affect any other user who happens to specify a mistyped/non-existent receiver, so the frozen-funds condition is not an intentional attacker exploit for profit, but the described impact (Critical: permanently frozen NEAR, ledger insolvency) is real and directly demonstrable in-repo.

### Recommendation
Add a resolve callback after the `Promise::new(receiver_id).transfer(amount)` in `do_native_withdraw` that checks the transfer's success, and on failure re-credits `withdraw.amount` of wNEAR (or re-wraps into wNEAR) back into `owner_id`'s `token_balances`, mirroring the resolve/re-credit pattern used elsewhere for `ft_withdraw`/`mt_withdraw`/`nft_withdraw` transfers.

### Proof of Concept
```rust
// tests/src/tests/defuse/intents/native_withdraw.rs (extend existing test file)
#[tokio::test]
async fn native_withdraw_to_nonexistent_receiver_strands_near() {
    // setup: sandbox env, deploy defuse contract, deploy wnear, register owner_id,
    // deposit + wrap NEAR so owner_id has wNEAR token_balances == amount

    let owner_balance_before = get_wnear_token_balance(&defuse, &owner_id).await;
    assert_eq!(owner_balance_before, amount);

    let receiver_id: AccountId = "this-account-was-never-created.near".parse().unwrap();

    // sign and submit MultiPayload with DefusePayload::NativeWithdraw { receiver_id, amount }
    execute_intents(&defuse, &owner_signer, vec![native_withdraw_intent(receiver_id.clone(), amount)])
        .await
        .unwrap(); // outer tx succeeds; async promise chain fails internally

    // Binding check 1: owner_id's wNEAR balance was debited
    let owner_balance_after = get_wnear_token_balance(&defuse, &owner_id).await;
    assert_eq!(owner_balance_after, 0); // debited by `amount`, never reverted

    // Binding check 2: receiver_id's on-chain NEAR balance is unchanged / account still doesn't exist
    assert!(!account_exists(&worker, &receiver_id).await);

    // Binding check 3: owner_id.token_balances was never re-credited
    assert_eq!(owner_balance_after, 0); // no re-credit occurred anywhere

    // Binding check 4 (insolvency): Verifier's own NEAR balance now holds `amount`
    // that is unaccounted for by any token_balances entry.
}
```
