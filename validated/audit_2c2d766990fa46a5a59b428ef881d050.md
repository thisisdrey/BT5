### Title
EIP-8246 self-destruct-to-self incorrectly preserves nonce, code and storage of a pre-existing account - ([File: core/state/statedb.go])

### Summary
When a **pre-existing** contract self-destructs to itself under the Amsterdam/EIP-8246 rules (or otherwise ends the block self-destructed with a non-zero balance), `StateDB.finaliseAmsterdam` is supposed to reduce the account to a "balance-only" account: nonce reset to 0, code cleared, storage cleared, balance preserved — exactly as the in-code comment for EIP-8264 states. The implementation, however, initializes the replacement state object from the account's pre-block `origin` record instead of a fresh/empty account, so the persisted account retains its old nonce, old code hash and old storage root. This is directly analogous to the reported Fusion-Swap bug: an entity is supposed to be “closed”/reset (the order/account identity wiped) but stale data from before the reset survives and can be exploited by any subsequent interaction with that address.

### Finding Description
In `core/state/statedb.go`, the Amsterdam finalise path handles a self-destructed account as follows: [1](#0-0) 

```go
case obj.selfDestructed:
    // EIP-8264: accounts marked for self-destruction, instead of
    // being deleted, are modified as follows:
    // - nonce is reset to 0,
    // - balance is unchanged,
    // - code is cleared,
    // - all storage is cleared
    if !obj.Balance().IsZero() {
        o := newObject(s, obj.address, obj.origin)
        o.setBalance(new(uint256.Int).Set(obj.Balance()))
        s.setStateObject(o)
        s.markUpdate(addr)
    } else {
        ...
    }
```

`newObject` is defined as: [2](#0-1) 

```go
func newObject(db *StateDB, address common.Address, acct *types.StateAccount) *stateObject {
	origin := acct
	if acct == nil {
		acct = types.NewEmptyStateAccount()
	}
	return &stateObject{
		...
		origin: origin,
		data:   *acct,
		...
	}
}
```

Because `obj.origin` is passed as `acct` and it is *not nil* whenever the account existed **before this block** (i.e. it was an already-deployed contract with real nonce/code/storage), `newObject` sets `o.data = *obj.origin`. This copies the pre-block `Nonce`, `CodeHash` and storage `Root` verbatim into the new object. Only `Balance` is subsequently overwritten by `o.setBalance(...)`. Consequently, the account committed to the trie via `updateStateObject`/`s.trie.UpdateAccount(obj.Address(), &obj.data, ...)` still carries:

- the account's **original nonce** (not reset to 0),
- the account's **original code hash** (not cleared to the empty-code hash),
- the account's **original storage root** (not reset to `EmptyRootHash`).

In addition, since this branch does **not** add the address to `s.stateObjectsDestruct` (unlike the zero-balance branch a few lines below or the pre-Amsterdam `Finalise` path), `handleDestruction` never runs `deleteStorage` for this account, so the old storage trie nodes are never pruned either — the stale storage root that ends up back in the account leaf actually resolves to real, un-deleted data.

Compare with the correct, pre-Amsterdam behavior which always deletes the object and marks it for destruction regardless of balance: [3](#0-2) 

The net effect: a contract that self-destructs to itself (permitted starting Amsterdam per the custom `opSelfdestruct6780` since the balance-burn is skipped for `this == beneficiary`) is **not actually reset**. Its code remains fully callable (`GetCode`/`EXTCODEHASH` still return the pre-destruct bytecode), its storage remains fully readable, and its nonce is not zeroed, while only its balance is updated. [4](#0-3) 

### Impact Explanation
This breaks the state-transition equality between the documented/spec'd behavior (EIP-8264/EIP-8246: nonce=0, code cleared, storage cleared, balance preserved) and what Geth actually persists (old nonce, old code, old storage root, new balance). Any client that implements the specified semantics correctly will compute a different post-state (and thus a different state root) for a block containing such a self-destruct-to-self transaction, causing a **consensus split** on an Amsterdam-activated chain. It also means SELFDESTRUCT effectively fails to destroy a pre-existing contract's code/storage in this path — the "destroyed" contract keeps running with its old logic and old storage for any subsequent call in the same or later blocks, which can be leveraged to make other contracts/accounts interact with stale, supposedly-removed state (the same "reinitialization/stale-identity" class of bug as the reported Fusion-Swap issue, where closing an entity did not actually clear its persisted data before it could be reused).

### Likelihood Explanation
This is deterministically triggered by any single transaction where a pre-existing contract (one that existed prior to the current block, so `origin != nil`) self-destructs to itself and ends the transaction with a non-zero balance (either because it held balance before self-destructing, or because it receives further value transfers later in the same block/transaction, as demonstrated by the existing `TestEIP8246SelfdestructRefunded` test pattern applied to a pre-existing account instead of a freshly `CREATE`d one). No adversarial network conditions or races are required — it is a deterministic bug in the Amsterdam finalisation path.

### Recommendation
When constructing the balance-only replacement object in `finaliseAmsterdam`, do not seed `data` from `obj.origin`. Build a fresh/empty account (nonce 0, empty code hash, empty storage root) and only carry over the balance, e.g. call `newObject(s, obj.address, nil)` (keeping `obj.origin` separately for journalling/deletion purposes) and explicitly ensure the address is still added to `s.stateObjectsDestruct` so its previous storage trie is pruned, matching the exact "case (c)/(d)" account-deletion handling already used in the zero-balance branch.

### Proof of Concept
1. Deploy a contract `A` in block N with non-zero code, non-zero nonce (>0 from EIP-158), and a non-empty storage slot, `origin` account persisted to disk.
2. In block N+1 (post-Amsterdam activation), call `A`, which executes `SELFDESTRUCT` with `beneficiary == address(A)` (self-destruct to self) — under `opSelfdestruct6780`/EIP-8246 this skips the balance burn, so `A`'s balance remains non-zero if it held funds before, or gets funded again afterward in the same transaction (same pattern as `TestEIP8246SelfdestructRefunded`, but with `A` being pre-existing rather than freshly `CREATE`d).
3. After block N+1 is finalized/committed, query the state: `GetNonce(A)` returns the old nonce (not 0), `GetCodeHash(A)`/`GetCode(A)` returns the old bytecode (not empty), and `GetState(A, slot)` still returns the pre-destruct storage value — none of which match the EIP-8264 comment's specified "nonce reset to 0 / code cleared / storage cleared" behavior, and would not match a correctly-implementing client's computed state root for the same block.

func opSelfdestruct6780(pc *uint64, evm *EVM, scope *ScopeContext) ([]byte, error) {
	if evm.readOnly {
		return nil, ErrWriteProtection
	}
	var (
		this        = scope.Contract.Address()
		balance     = evm.StateDB.GetBalance(this)
		top         = scope.Stack.pop1()
		beneficiary = common.Address(top.Bytes20())
		newContract = evm.StateDB.IsNewContract(this)
	)
	// Contract is new and will actually be deleted.
	if newContract {
		if this != beneficiary { // Skip no-op transfer when self-destructing to self.
			evm.StateDB.AddBalance(beneficiary, balance, tracing.BalanceIncreaseSelfdestruct)
			evm.StateDB.SubBalance(this, balance, tracing.BalanceDecreaseSelfdestruct)
		} else if !evm.chainRules.IsAmsterdam {
			// Self-destructing to self burns the balance prior to EIP-8246.
			// EIP-8246 (Amsterdam) removes this burn: the balance is left
			// untouched and the account is preserved as a balance-only account
			// at transaction finalization (unless its balance is zero, in which
			// case EIP-161 deletes it).
			evm.StateDB.SubBalance(this, balance, tracing.BalanceDecreaseSelfdestruct)
		}
		evm.StateDB.SelfDestruct(this)
	}
