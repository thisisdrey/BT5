### Title
StackerDB chunk signatures are not bound to the target StackerDB contract, permitting cross-contract chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
The OpenClaw advisory describes an approval that was cryptographically valid but not bound to the specific target (`nodeId`) it was issued for, letting it be replayed against a different target under the same operator trust domain. The analogous fault class in this repo is StackerDB chunk authentication: a chunk's signature commits only to `(slot_id, slot_version, data_hash)` and is verified against a signer address that is looked up *per contract*, but the signed digest itself never includes the `contract_id`/`QualifiedContractIdentifier`. If the same signer address happens to own the same `slot_id` in two different StackerDB contracts (which is realistic across reward-cycle-scoped signer contracts using stable slot assignment), a chunk validly signed and broadcast for contract A can be replayed verbatim (same signature, same slot_id, same data) into contract B's write endpoint and pass all authentication checks there.

### Finding Description
The signed digest for a StackerDB chunk is computed by `SlotMetadata::auth_digest`, which hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`SlotMetadata::verify` recovers the public key from this digest and compares it only to the `principal: &StacksAddress` passed in by the caller — the contract identity is never part of what is signed or verified: [2](#0-1) 

On write, `RPCPostStackerDBChunkRequestHandler::try_handle_request` takes the `contract_identifier` from the URL path and the chunk from the request body, then calls `tx.try_replace_chunk(&contract_identifier, &stackerdb_chunk.get_slot_metadata(), &stackerdb_chunk.data)`: [3](#0-2) 

The per-contract owner lookup and signature check happen inside the storage/validation layer (`get_slot_signer(contract_id, slot_id)` followed by `slot_metadata.verify(&addr)`), as also exercised in the gossip validation path: [4](#0-3) 

Because the signed bytes never include `contract_id`, this check only proves "this address signed slot `slot_id`/`slot_version`/`data_hash`" — not "this address signed it *for this specific StackerDB contract*." An attacker who observes a broadcast/posted chunk for contract A can resend the identical `StackerDBChunkData` (slot_id, slot_version, sig, data) to a different contract B's `POST /v3/stackerdb/{contract_id}/chunks` endpoint or push it over gossip; it will be accepted as a legitimate write to contract B whenever the same signer occupies that same `slot_id` in contract B's `StackerDBConfig::signers` list. This is exactly the "authenticated-for-A vs. accepted-as-B" equality break described in the report, mirrored architecturally in the missing target binding (`nodeId` → `contract_id`).

### Impact Explanation
This allows an unprivileged network peer to write attacker-chosen (but previously-observed) chunk data into a StackerDB contract that never authorized it, effectively an unauthorized/unauthenticated write to state for a mismatched target. Concretely, capturing a valid signer message for reward-cycle StackerDB N and replaying it into StackerDB N+1 (or another contract with overlapping slot ownership) could inject a stale or wrongly-scoped signer message (e.g., a `BlockResponse`/vote payload) as if freshly signed for that contract, potentially confusing signer-set consumers reading from that DB, or occupying/poisoning a slot with cross-cycle data. This falls under "unauthenticated/unauthorized write to state or StackerDB" per the scoring rubric.

### Likelihood Explanation
Exploitability depends on the same signer address owning the identical `slot_id` in two contracts the attacker can target — this is plausible in this codebase because slot assignment (`StackerDBConfig::signers`, built from the smart-contract signer set) is frequently derived deterministically from a stable ordering that can coincide across cycles/contracts for the same address, and no code path prevents the coincidence from being exploitable. An attacker only needs to observe one legitimately-broadcast chunk (chunks are gossiped/replicated network-wide by design) and re-POST/re-gossip it to a different contract endpoint — no secret key or privileged role is required.

### Recommendation
Include the target `contract_id` (or a domain separator derived from it) in `SlotMetadata::auth_digest`, so a chunk signature is cryptographically bound to the specific StackerDB contract it was authorized for, analogous to binding `nodeId` into the `exec.approval` digest in the referenced fix. This requires a coordinated protocol/version bump since it changes what gets signed.

### Proof of Concept
1. Signer `S` owns `slot_id=3` in StackerDB contract `A` (e.g. reward-cycle-N signer contract) and also owns `slot_id=3` in contract `B` (e.g. reward-cycle-N+1 contract, or any other contract with matching slot layout).
2. `S` legitimately signs and posts a chunk to `A`: `chunk = StackerDBChunkData{slot_id:3, slot_version:5, sig, data}` via `POST /v3/stackerdb/A/chunks`, handled by `RPCPostStackerDBChunkRequestHandler` → `try_replace_chunk(&A, ...)`, which succeeds because `slot_metadata.verify(&addr_of_S_in_A)` passes (`libstackerdb/src/libstackerdb.rs:181-193`).
3. An observer captures this chunk (via gossip/HTTP response or by observing the mempool of StackerDB pushes) and replays the exact same bytes to `POST /v3/stackerdb/B/chunks`.
4. `RPCPostStackerDBChunkRequestHandler::try_handle_request` (`stackslib/src/net/api/poststackerdbchunk.rs:179-201`) calls `try_replace_chunk(&B, ...)`, which looks up `get_slot_signer(B, 3)` = `addr_of_S_in_B` (same address as in A) and calls `slot_metadata.verify(&addr_of_S_in_B)` — this succeeds because the digest never included `A` or `B`, so the chunk is accepted into contract `B`'s slot 3 even though `S` never signed anything intending it for `B`.     /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
