## Finding

### Title
Vault `transfer` authorizes fund movement using `tx-sender` instead of `contract-caller`, enabling a malicious contract to drain a victim's vault shares - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and the other v0-vault-* contracts)

### Summary
Every ZEST v2 vault (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-ststxbtc`, `v0-vault-usdc`, `v0-vault-usdh`) exposes a public `transfer` function that authorizes moving `zft` (vault share) balances from an arbitrary `from` principal if **either** `tx-sender` or `contract-caller` matches `from`: [1](#0-0) 

This is structurally the same flaw as the TradeCallee report: authorization is granted based on the original transaction signer (`tx-sender`, the Clarity analog of Solidity's `tx.origin`) rather than the immediate caller (`contract-caller`, the analog of `msg.sender`). Because `tx-sender` persists unchanged through nested `contract-call?` invocations (unless explicitly reset via `as-contract`), any intermediate contract in the call chain can piggyback on the original signer's identity to authorize a transfer they did not intend.

### Finding Description
The `transfer` function's precondition is:
```clarity
(asserts! (or (is-eq tx-sender from) (is-eq contract-caller from)) (err u4))
``` [1](#0-0) 

The `is-eq contract-caller from` branch is the correct, safe check — it authorizes only the direct/immediate caller. The `is-eq tx-sender from` branch, however, is dangerous: it lets *any* contract in a multi-hop call chain successfully call `transfer` and move `from`'s (the original signer's) balance, as long as `from` is set to `tx-sender`. `tx-sender` does not change as calls traverse intermediate untrusted contracts on Stacks (only `as-contract` resets it), which is exactly the `tx.origin`-style trust assumption the external report warns about.

Concretely: Alice calls a contract deployed by Eve for some ostensibly unrelated purpose. Inside that call, Eve's contract does:
```clarity
(contract-call? .v0-vault-stx transfer alice-balance tx-sender EVE-ADDRESS none)
```
Since `tx-sender` at this point is still Alice (the original transaction signer), and `from` is set to that same value, the `asserts!` passes even though `contract-caller` (Eve's contract) is not Alice. The vault then executes `(ft-transfer? zft amount from to)`, moving Alice's zSTX shares to Eve.

This same pattern is duplicated identically across all six vault contracts: [2](#0-1) [3](#0-2) [4](#0-3) 

### Impact Explanation
This is a **Critical** finding: it allows direct theft of user funds at rest. Any user holding vault shares (zSTX, zsBTC, zstSTX, zUSDC, zUSDH, zstSTXbtc — the funds users deposited into the lending protocol) can have their entire vault share balance transferred to an attacker simply by interacting with any malicious contract that includes a `transfer` call in its logic. Since these vault shares represent the user's principal deposits/collateral in the market, this results in complete, irreversible loss of the victim's deposited assets — no ordinary transaction signature specific to the transfer is required beyond the victim's original, unrelated call.

### Likelihood Explanation
Likelihood is high given normal usage patterns: users routinely interact with third-party/aggregator/frontend contracts in the Stacks ecosystem. Any attacker able to get a victim to invoke a contract call (a dApp, a "helper" contract, an airdrop claim, etc.) that ultimately performs a nested `contract-call?` into one of these vault `transfer` functions can execute the exploit deterministically — there is no probabilistic or race-condition component, and no privileged access or DAO compromise is needed.

### Recommendation
Remove the `is-eq tx-sender from` disjunct from the `transfer` authorization check in all vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`). Authorization should rely solely on `contract-caller` (the immediate, verifiable caller), i.e.:
```clarity
(asserts! (is-eq contract-caller from) ERR-AUTHORIZATION)
```
If cross-contract delegated transfers are a required feature (e.g., the market contract moving shares on behalf of users), that should be implemented via an explicit allowance/approval mechanism rather than relying on `tx-sender` identity propagation through arbitrary call chains.

### Proof of Concept
1. Alice deposits STX into `v0-vault-stx`, receiving zSTX shares recorded in the `zft` fungible token ledger, with `tx-sender` = Alice for that transaction.
2. Eve deploys a malicious contract `evil.clar` containing:
   ```clarity
   (define-public (bait)
     (contract-call? .v0-vault-stx transfer
       (unwrap-panic (contract-call? .v0-vault-stx get-balance tx-sender))
       tx-sender
       'EVE_ADDRESS
       none))
   ```
3. Eve convinces Alice (via a dApp, phishing link, or "claim reward" UI) to call `(contract-call? .evil bait)`.
4. Inside `evil.clar`'s execution, `tx-sender` is still Alice (unchanged since no `as-contract` was used), while `contract-caller` as seen by `v0-vault-stx` is `evil.clar`.
5. The vault's check `(or (is-eq tx-sender from) (is-eq contract-caller from))` passes because `tx-sender` equals `from` (Alice), even though the direct caller is Eve's contract.
6. `(ft-transfer? zft amount from to)` executes, moving Alice's entire zSTX balance to Eve's address [1](#0-0) .
