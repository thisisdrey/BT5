### Title
Unvalidated attacker-controlled field offsets in TVM zk-SNARK `verifyTransferProof` precompile enable out-of-bounds array access - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `VerifyTransferProof.execute` precompiled contract parses `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` directly from attacker-controlled `data` and uses them, combined with attacker-controlled `spendCount`/`receiveCount`, to index into `data` via `System.arraycopy` without validating that the computed offsets and lengths actually fit within `data.length`. [1](#0-0) 

### Finding Description
This is analogous to CVE-2016-8632's root cause: the code validates only the overall input buffer size (`data.length` must be one of `{2080, 2368, 2464, 2752}`, and `spendCount`/`receiveCount` are constrained to `[1,2]`), but the *relationship* between attacker-supplied offsets (`spendOffset`, `spendAuthSigOffset`, `receiveOffset` — described in a code comment as "unfixed field offset") and the fixed-size buffer is never checked before those offsets are used to compute array indices for `System.arraycopy` calls. [2](#0-1) 

Because `spendOffset`/`receiveOffset`/`spendAuthSigOffset` come straight from `parseInt(data, 0/32/64)`, a malicious contract caller can set these to arbitrary values (including negative or very large offsets) that, when combined with `320*i`, `288*i`, or `64*i` strides, point far outside the bounds of `data`. Java's array bounds checking prevents true memory corruption (unlike the C heap overflow in the kernel CVE), but this pattern is the direct analog of "does not validate the relationship between... length and... size," producing out-of-bounds accesses on a broadcastable-transaction-reachable VM opcode/precompile path (a `CALL` to the zk-SNARK precompile address from any contract). [3](#0-2) 

### Impact Explanation
If the resulting `ArrayIndexOutOfBoundsException` (or `NegativeArraySizeException` from a negative offset difference) is not fully caught within the precompile's execution path before propagating to VM/block-application code, this could cause the transaction executor thread to fail unexpectedly during normal contract execution or, worse, during block replay, causing divergent behavior between nodes or halting block application — both of which are in-scope high-impact classes (node crash/halt, chain split) per the validation criteria. I was not able to confirm within the available context whether `VerifyTransferProof.execute` wraps this specific code region in a `catch (Throwable ...)` block analogous to the one seen in the neighboring `VerifyMintProof.execute` implementation; that surrounding try/catch scope was not visible before the tool budget was exhausted. [4](#0-3) 

### Likelihood Explanation
Any account can trigger this by deploying a trivial contract that calls the shielded-transfer precompile with a crafted `data` payload matching one of the allowed fixed lengths but containing out-of-range offset words. No special privileges (CAP_NET_ADMIN analog) are required beyond the ability to broadcast a contract-call transaction, matching the "unprivileged transaction broadcaster / contract deployer" threat model in scope.

### Recommendation
Before using `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` for any `System.arraycopy` call, explicitly validate that each offset is non-negative and that `offset + requiredLength <= data.length` for every read performed in the spend/receive parsing loops, returning `Pair.of(true, DataWord.ZERO().getData())` (transaction failure) on violation instead of allowing an exception to propagate, mirroring the existing `catch (Throwable any)` handling used elsewhere in `VerifyProof` subclasses.

### Proof of Concept
Craft calldata of exactly 2080 bytes (a valid `SIZE` entry) where the first three 32-byte words (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) are set to large or negative values (e.g., `0x7FFFFFFF` or `-1`) rather than legitimate in-buffer offsets, while keeping `leafCount < TREE_WIDTH - 1`. Deploy a contract that performs a `CALL` (or `STATICCALL`) to the `verifyTransferProof` precompile address with this payload and broadcast the transaction; the subsequent `parseInt(data, spendOffset)` / `System.arraycopy(data, spendOffset + 320*i, ...)` calls will read/index outside `data`'s bounds.
