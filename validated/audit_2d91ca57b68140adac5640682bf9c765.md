### Title
Unbounded/negative array-length allocation in `ValidateMultiSign` precompile signature parsing causes uncaught crash - (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE describes a heap-buffer-overflow class of bug: an attacker-controlled length field taken from crafted input is used to size/index a buffer without adequate validation, in a parser that is reachable from external data. The analogous root cause in java-tron is in the `ValidateMultiSign` TVM precompiled contract, where a caller-supplied word is used directly as an array length for `new byte[len][]` without a lower-bound check, and the call site sits outside any exception guard.

### Finding Description
`ValidateMultiSign.execute()` decodes the ABI-encoded calldata for the `validateMultiSign` precompile and extracts a caller-controlled signature array size straight from the calldata word pointed to by the offset field `words[3]`: [1](#0-0) 

When `VMConfig.allowTvmSelfdestructRestriction()` is active, the code only rejects the size if it is *greater* than `MAX_SIZE`:
```
int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
if (sigArraySize > MAX_SIZE) {
  return Pair.of(true, DATA_FALSE);
}
```
`intValueSafe()` can return a negative `int` for an attacker-chosen 32-byte word (e.g. any value whose top bit is set once truncated to `int`). A negative `sigArraySize` passes the `> MAX_SIZE` check (negative is not greater than `MAX_SIZE`), so execution continues into `extractSigArray`/`extractBytesArray`: [2](#0-1) 

Both helpers immediately execute `byte[][] bytesArray = new byte[len][];` with the attacker-controlled `len`. A negative `len` throws `NegativeArraySizeException`; a very large positive `len` (up to `Integer.MAX_VALUE`) attempts to allocate an oversized reference array and can throw `OutOfMemoryError`.

Critically, this parsing call in `ValidateMultiSign.execute()` is **not** wrapped in any try/catch — the `try { ... } catch (Throwable t)` block in that method only starts later, around the permission/weight-calculation loop: [3](#0-2) 

This is in contrast to the sibling precompile `BatchValidateSign`, whose `execute()` wraps the entire `doExecute()` call (which performs the same unguarded `extractBytesArray`/`extractSigArray` logic) in a top-level `try { return doExecute(data); } catch (Throwable t) { ... }`: [4](#0-3) 

Because `ValidateMultiSign` lacks this outer guard, a `NegativeArraySizeException` or `OutOfMemoryError` raised while sizing `bytesArray`/`bytes32Array` propagates directly out of `execute()` uncaught by the precompile itself.

Additionally, even when `allowTvmSelfdestructRestriction()` is disabled (older/legacy path), `extractBytesArray` is invoked with no size check at all before it, so `len` is fully attacker-controlled from calldata.

### Impact Explanation
An uncaught `Error`/`RuntimeException` thrown deep inside precompiled-contract execution during transaction processing risks propagating up through the TVM interpreter loop. If the enclosing call stack (`Program`, actuator, `Manager` block application) does not catch `Throwable`/`Error` at every layer, this can crash the transaction-processing thread or the node itself while executing a smart-contract call — a denial-of-service condition reachable by any account that can broadcast a `TriggerSmartContract` transaction calling the `validateMultiSign` precompile (address `0x100...e`) with a single crafted call. This matches the CVE's own impact category (crafted length field causing a DoS).

### Likelihood Explanation
The precompile is reachable by any unprivileged account via a normal `TriggerSmartContract`/`CALL` to the fixed precompile address; no special privileges, SR/witness role, or prior state are required — only a crafted 32-byte word placed at the calldata offset used as the signature-array length. The negative-length bypass requires only crafting a large enough value in that word so `intValueSafe()` truncates to a negative `int`; the oversized-positive-length path requires no bypass at all when the feature flag is off. Both are straightforward to construct.

### Recommendation
- In `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, validate `len >= 0` and enforce a sane upper bound (e.g. `MAX_SIZE` for `ValidateMultiSign`) *before* allocating `new byte[len][]`.
- In `ValidateMultiSign.execute()`, perform the `sigArraySize` bound check unconditionally (not gated behind `allowTvmSelfdestructRestriction()`), and check `sigArraySize >= 0` in addition to `<= MAX_SIZE`.
- Wrap the calldata-parsing section of `ValidateMultiSign.execute()` in the same defensive `try/catch (Throwable)` pattern already used by `BatchValidateSign.execute()`, returning `Pair.of(true, DATA_FALSE)` on any decoding failure instead of allowing the exception to propagate.

### Proof of Concept
1. Craft calldata for `validateMultiSign(address,uint256,bytes32,bytes[])` where the dynamic offset word `words[3]` points to a length word whose raw 32 bytes decode (via `DataWord.intValueSafe()`) to a negative `int` (e.g., a word with the high bit set beyond the safe range) or to an extremely large positive value.
2. Broadcast a `TriggerSmartContract` transaction that `CALL`s the `validateMultiSign` precompile address with this calldata.
3. `ValidateMultiSign.execute()` reaches `extractBytesArray`/`extractSigArray` and executes `new byte[len][]` with the attacker-supplied `len`, throwing `NegativeArraySizeException` or `OutOfMemoryError` uncaught by the method (no enclosing try/catch at that point), unlike `BatchValidateSign`.
4. Confirm via `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java` lines 1066-1078 and 399-412 that the size check is insufficient (only checks upper bound, not lower bound / not present at all pre-feature-flag) and that no exception guard surrounds this call in `ValidateMultiSign`, as opposed to `BatchValidateSign` (lines 1144-1154).
