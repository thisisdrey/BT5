### Title
Committee can permanently freeze user funds locked in active Market orders by disabling `ALLOW_MARKET_TRANSACTION`, since `MarketCancelOrderActuator` also requires the feature to be enabled - (File: actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java)

### Summary
This is the java-tron analog of the UXD centralization-risk report: an admin/governance action that disables a feature (unregistering a depository / removing a whitelist entry) leaves users unable to redeem funds they already deposited under the old state. In java-tron, the TRC10 on-chain order-book market has an equivalent pattern: placing an order via `MarketSellAssetActuator` locks the seller's TRX/token into escrow (removed from the account balance and held only inside `MarketOrderStore`/`MarketAccountStore`), and the *only* way to release the unfilled remainder back to the user is `MarketCancelOrderActuator`. Both actuators gate on the same feature flag, `DynamicPropertiesStore.supportAllowMarketTransaction()`, which is controlled by the committee proposal `ALLOW_MARKET_TRANSACTION`.

### Finding Description
`MarketSellAssetActuator.validate()` locks funds into an order only when the market feature is enabled: [1](#0-0) 

Funds are escrowed out of the user's account balance/asset map at execution time: [2](#0-1) 

The only transaction type that can return the unmatched remainder of an order to its owner is `MarketCancelOrderActuator`, and its `validate()` unconditionally re-checks the very same feature flag before allowing cancellation of an already-existing, already-escrowed order: [3](#0-2) 

The actual return-of-funds logic that a successful cancel would trigger: [4](#0-3) 

Because `supportAllowMarketTransaction()` is a single shared dynamic-property flag toggled by the committee via a normal chain-parameter proposal (`ALLOW_MARKET_TRANSACTION`, handled in `ProposalUtil`/`ProposalService`), there is no code path that special-cases "cancel my own pre-existing order" when the market is disabled. If the committee turns the flag off (or it is off for any operational reason such as a chain fork/parameter regression) while active orders exist, every order owner is permanently unable to cancel and reclaim the sell-token remainder held in escrow — mirroring the UXD bug where unregistering a depository and/or de-whitelisting an asset blocks the `redeem` path for funds already deposited under the old configuration.

### Impact Explanation
Active TRC10/TRX amounts locked in unmatched or partially-matched market orders become permanently unreachable for the order owner once `ALLOW_MARKET_TRANSACTION` is disabled, since `MarketCancelOrderActuator.validate()` rejects any cancellation attempt with `ContractValidateException("Not support Market Transaction, need to be opened by the committee")` regardless of the order's ownership or state. This is a permanent freezing-of-funds condition driven entirely by a centralized governance parameter, with no alternative on-chain mechanism (no auto-expiry, no batch admin refund) to recover the escrowed balance while the flag stays off.

### Likelihood Explanation
Toggling `ALLOW_MARKET_TRANSACTION` is a normal, already-implemented committee proposal path (same mechanism used to enable other protocol features), so no exotic conditions are needed — only that active orders exist at the moment the flag transitions from enabled to disabled. Given this is a standard governance lever rather than an attacker-controlled exploit, likelihood depends on committee/witness behavior, but the code offers zero technical safeguard against this freeze scenario, unlike some other single-shot ("only allowed to be 1") proposal types in `ProposalUtil`.

### Recommendation
Decouple order cancellation from the "new order creation / matching" feature gate: `MarketCancelOrderActuator.validate()` and `execute()` should not require `supportAllowMarketTransaction()` to be true for orders that already exist, so users can always retrieve escrowed funds for orders placed while the feature was enabled. Alternatively, treat `ALLOW_MARKET_TRANSACTION` as a "create new order" switch only, and always allow `MarketCancelOrderContract` transactions to proceed independent of that flag's current state.

### Proof of Concept
1. Committee enables `ALLOW_MARKET_TRANSACTION` (value 1) via proposal.
2. User broadcasts `MarketSellAssetContract` through `MarketSellAssetActuator`; funds (TRX or TRC10) are deducted from the user's account and locked into a `MarketOrderCapsule` in `MarketOrderStore` (`actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java:134`, `:527-535`). The order remains partially/fully unmatched (`sellTokenQuantityRemain > 0`).
3. Committee later disables `ALLOW_MARKET_TRANSACTION` (sets value back to 0) via a subsequent proposal.
4. User broadcasts `MarketCancelOrderContract` to reclaim the unmatched remainder. `MarketCancelOrderActuator.validate()` throws `ContractValidateException("Not support Market Transaction, need to be opened by the committee")` (`actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java:168-171`), so the transaction is rejected on every subsequent attempt.
5. The user's escrowed TRX/TRC10 remains locked in `MarketOrderStore` indefinitely with no other actuator or API path capable of returning it while the flag is disabled.
