### Title
Split-lock replay-window check/update in `ConnectionState.Decrypt`/`VerifyRelay` allows duplicate packet processing across concurrent readers - (File: connection_state.go)

### Summary
Nebula's data-plane packet processing runs across multiple UDP reader goroutines (one per queue) that all funnel through `Interface.readOutsidePackets` and ultimately call `ConnectionState.Decrypt` or `ConnectionState.VerifyRelay`. Both functions follow the same pattern seen in the reported `BabylonCore.participate` reentrancy bug: an anti-replay check is performed, an expensive/externally-observable operation is executed *without holding the lock*, and only afterward is the authoritative state (the replay window) updated — with the lock dropped in between each step.

### Finding Description
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split what should be one atomic "check-then-commit" replay operation into three separately-locked steps: [1](#0-0) 

```
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)   // step 1: check only
cs.decryptLock.Unlock()
...
out, err = cs.dKey.DecryptDanger(...)          // step 2: no lock held
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)   // step 3: commit
cs.decryptLock.Unlock()
```

`VerifyRelay` has the identical shape. [2](#0-1) 

Just as `BabylonCore.participate` performed the state-changing `mint` external call before updating `listing.currentTickets`, here `window.Check` is used to gate entry, but the window bitmap is not marked "seen" (via `window.Update`) until *after* the AEAD decryption/verification completes — and the lock is released between the two calls. `Bits.Check` only inspects the current bitmap; it does not reserve or claim the slot: [3](#0-2) 

Because `Interface.readOutsidePackets` is invoked concurrently from multiple UDP-reader goroutines/queues (`q int` parameter, per-queue readers), two threads that receive the *same* duplicated ciphertext packet (same `messageCounter`) at nearly the same time can both pass `Check` before either calls `Update`, both successfully decrypt/verify (AEAD decryption is deterministic and does not depend on the window state), and both proceed to hand their plaintext output to the caller path: [4](#0-3) 

Only one of the two subsequent `Update` calls will end up marking the counter as a duplicate and returning `false`/`ErrAlreadySeen`, but that check happens *after* `DecryptDanger` has already run and, critically, only gates the return value of `Decrypt`/`VerifyRelay` itself — the race window between `Check` and `Update` is exactly the "moved-mint" defect pattern from the external report, and duplicate acceptance windows are a hallmark of anti-replay TOCTOU (check-then-act) bugs.

### Impact Explanation
An attacker who can duplicate/replay a single captured ciphertext UDP datagram at the network layer (trivial for any on-path or off-path attacker capable of sending duplicate UDP packets, no valid certificate needed since this occurs on the already-decrypting fast path for any established tunnel) can race the two decrypt/update sequences and potentially get the same message accepted twice by the local `Bits` window bookkeeping and interface-level processing before de-duplication commits, contrary to Nebula's stated anti-replay guarantee. Depending on which processing branch is reached twice (e.g. `header.Message` → written to TUN, or `header.LightHouse` / `header.Control` handling), this can cause duplicate delivery of a single wire message to the local network stack or duplicate handling of control/lighthouse messages — a remote state-poisoning/duplication effect stemming directly from the check/commit split.

### Likelihood Explanation
Exploitation requires only the ability to send duplicate UDP datagrams to a victim node with which the attacker already has (or observes) an established, decrypting tunnel — no cryptographic material or valid certificate is needed, since the race is purely on the local replay-window bookkeeping, not on decryption itself. The race window is narrow (time between `Check`/`Unlock` and the following `Lock`/`Update`), but Nebula's UDP receive path uses multiple queues/goroutines specifically to increase concurrency, which increases the practical likelihood of interleaving two duplicate packets across two goroutines during that window.

### Recommendation
Merge the check-and-commit into a single atomic operation instead of separate `Check` then `Update` calls straddling an unlocked decrypt operation. Concretely, hold `decryptLock` (or perform an equivalent atomic "reserve" operation on `Bits`) across the entire check → decrypt → commit sequence, or restructure `Bits` to expose a single method that atomically checks-and-reserves the slot before decryption begins, only rolling back the reservation if decryption subsequently fails. This mirrors the report's remediation of moving the state-mutating call to the end (or guarding the whole critical section), ensuring no two concurrent calls can observe a not-yet-marked counter simultaneously.

### Proof of Concept
1. Establish a Nebula tunnel between two nodes.
2. Capture one valid encrypted `header.Message` UDP packet destined for the victim.
3. Send two copies of that exact packet to the victim in rapid succession such that they land on two different UDP-reader goroutines/queues at nearly the same time.
4. Because both goroutines call `hostinfo.ConnectionState.Decrypt` and both may execute `cs.window.Check` before either executes `cs.window.Update` (lock is released in between), both may pass the replay check and both proceed to `DecryptDanger`, which succeeds deterministically for both. One or both plaintexts then reach `handleOutsideMessagePacket`, potentially causing the duplicate packet to be written to the TUN device twice instead of being rejected as a replay.

Note: I was unable to execute this PoC in a live environment; the analysis is based on static code review of `connection_state.go`, `bits.go`, and the call sites in `outside.go`. Confirming the exact race timing and whether downstream consumers (`f.readers[q].Write`, lighthouse/control handlers) are idempotent enough to make duplicate delivery harmless would require dynamic/concurrency testing, which is outside the scope of this static review.

```go
func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
```

```go
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
```

```go
// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
```
