### Title
Argument/transport injection via unsanitized `remote` URL in `git_repository` enabling arbitrary command execution through Git's `ext::` transport - (File: tools/build_defs/repo/git_worker.bzl)

### Summary
Bazel's `git_repository` repo rule (and its Bzlmod `source.json` `type: "git_repository"` equivalent, where `remote` is a registry-supplied field forwarded verbatim, per `docs/external/registry.mdx`) passes the attacker-influenced `remote` string directly as a positional argument to `git remote add origin <remote>` and `git fetch origin` in `tools/build_defs/repo/git_worker.bzl`, with no scheme allow-list, no `GIT_ALLOW_PROTOCOL` restriction, and no leading-dash/argument-injection guard.

### Finding Description
`git_repo()` in `tools/build_defs/repo/git_worker.bzl` builds the `_GitRepoInfo.remote` field from `ctx.attr.remote` [1](#0-0) , then `_update()` calls `add_origin(ctx, git_repo, ctx.attr.remote)` which executes `_git(ctx, git_repo, "remote", "add", "origin", remote)` [2](#0-1) , ultimately invoked through `_execute()` which runs `git -c core.fsmonitor=false remote add origin <remote>` via `ctx.execute` [3](#0-2) . Because the value is passed as a distinct argv element (not shell-concatenated), classic shell metacharacter injection is blocked — but Git itself interprets certain URL schemes as transport helpers. Git's `ext::<command>` transport (and `fd::`) executes the embedded shell command when Git tries to connect, so a `remote` value such as `ext::sh -c "touch pwned"` results in arbitrary command execution during `git fetch origin` without any injected shell metacharacters at the Bazel/Starlark layer. No code in `git.bzl` or `git_worker.bzl` filters the scheme of `remote`, and no `GIT_ALLOW_PROTOCOL` environment variable is set to disable dangerous transports (confirmed absent via search — only occurrences of `GIT_ALLOW_PROTOCOL`/`ext::` in the whole repo are in unrelated Windows batch-launcher code, not in the repo-rule fetch path).

The `remote` value can originate from an attacker in the covered threat model in two ways: (1) a Bzlmod registry `source.json` of `type: "git_repository"` supplies `remote` directly per the registry format spec [4](#0-3) , and a hostile/compromised third-party `--registry` (explicitly in-scope per the "hostile origin server, mirror or registry" carve-out) can set `remote = "ext::sh -c ..."`; (2) any repository rule invocation (e.g., transitive dependency declaring its own `git_repository` with an untrusted-origin-controlled remote string, such as a value read from a build file the victim's build consumes) reaches the same code path.

### Impact Explanation
If reached, this results in arbitrary command execution on the machine running the Bazel build during the fetch phase — equivalent to remote code execution, matching the pdf-image analog's "attacker could execute arbitrary shell commands" impact. This breaks the invariant that untrusted registry/URL content should remain inert data consumed only by the Git binary as a network address, not as a code-execution vector.

### Likelihood Explanation
Medium-to-high if reachable: no sha256/integrity-style verification applies to `remote` (integrity pinning only covers archives/patches, not the git remote URL), and there is no allow-list on the URL scheme. However, I was not able to fully confirm within available tool budget whether the Java-side `RegistryFunction`/`GitRepositoryFunction` (if any exists) adds an additional scheme filter before Starlark evaluation, since no matching Java source was found via `grep_search` for `remote_patches|remote_file_urls|createRepoSpec` and I could not directly open `ModuleFileFunction`/`RegistryFunction` Java sources to check for such a filter. This is a genuine gap in my verification.

### Recommendation
Validate/allow-list the `remote` attribute's URL scheme in `git.bzl`/`git_worker.bzl` (restrict to `http(s)://`, `git://`, `ssh://`, `file://`, and plain SCP-like syntax), and/or explicitly set `GIT_ALLOW_PROTOCOL` in the environment passed to all `git` subprocess invocations in `_execute()` to exclude `ext`, `fd`, and other transport-helper schemes.

### Proof of Concept
A `src/test/shell/bazel/starlark_git_repository_test.sh`-style test can register a `git_repository` (or a Bzlmod module via a local test registry, as scaffolded in `src/test/py/bazel/bzlmod/test_utils.py`) with:
```
git_repository(
    name = "pwn",
    remote = "ext::sh -c 'touch $PWD/pwned; git init .; exit 1'",
    commit = "0000000000000000000000000000000000000000",
)
```
then run `bazel fetch @pwn//...` and assert the marker file `pwned` was created, demonstrating command execution triggered purely by the `remote` attribute value during `add_origin`/`fetch` in `git_worker.bzl`.

**Caveat on confidence**: I could not verify from the available Starlark/doc sources alone whether a Java-side registry ingestion layer (not found by my searches) sanitizes the `remote` field before it reaches `git.bzl`. If such sanitization exists, this finding would not hold; I was unable to locate or rule out its existence within my tool-call budget, and I explicitly flag this as unresolved rather than asserting a guaranteed bypass. If you want, I can start a Devin session to inspect `ModuleFileFunction`/registry-related Java sources directly to close this gap.

def _update(ctx, git_repo):
    ctx.delete(git_repo.directory)

    init(ctx, git_repo)

def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.
    # See https://github.com/bazelbuild/bazel/issues/21438
    start = ["git", "-c", "core.fsmonitor=false"]
    return ctx.execute(
        start + args,
        environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS,
        working_directory = str(git_repo.directory),
    )
