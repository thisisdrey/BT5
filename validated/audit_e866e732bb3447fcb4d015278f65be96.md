I found a concrete analog. In `handleCreateRelayRequest`, when the local node is acting as a middle-man relay (`am_relay`), the `RelayFromAddr` field inside the `NebulaControl_CreateRelayRequest` message is attacker-controlled plaintext-derived data taken at face value, without ever checking it against the cryptographically-verified identity (`h.vpnAddrs`) of the peer that actually sent the message over the authenticated tunnel `h`.

### Title
Relay forwarding trusts attacker-supplied `RelayFromAddr` instead of the verified sender identity - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` uses `m.RelayFromAddr` (decoded into `from`) — a field taken directly from the `NebulaControl` protobuf payload sent by the peer — as the "owner" identity for relay bookkeeping (`AddRelay(..., from, ...)`, `h.relayState.QueryRelayForByIp(from)`), instead of validating that `from` actually matches the sending peer's certificate-verified `vpnAddrs` on `HostInfo h`. This mirrors the ERC721 bug class: the code checks "is the target me" and various state-machine invariants, but never checks that the claimed relay-from identity actually belongs to the peer (`creator`) presenting the request, i.e. no equivalent of `creator == owner`.

### Finding Description
`relay_manager.go:426-604`, function `handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl)`: [1](#0-0) 

`from` is derived purely from `m.RelayFromAddr`, a value fully controlled by whoever is holding the tunnel `h` (an already-handshaked peer, i.e. no CA-signed certificate needed beyond normal peer status — this is reachable by any legitimate-but-malicious member of the mesh). The only identity check performed is `f.myVpnAddrsTable.Contains(from)` (am-I-the-source) and, further down, `f.myVpnAddrsTable.Contains(target)` (am-I-the-target). There is no check that `from` equals one of `h.vpnAddrs` (the addresses actually bound to `h`'s verified certificate). [2](#0-1) 

When target == me, the code calls `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` and then indexes `h.relayState` by the attacker-chosen `from` value — not by `h.vpnAddrs[0]`. Compare with the certificate/handshake path, which is careful to always tie `vpnAddrs` to the cryptographically verified certificate (e.g. `handshake_manager.go` `validatePeerCert`/`continueHandshake`'s `correctHostResponded` check at [3](#0-2) ). No such tie exists here — `h` (the authenticated tunnel) and `from` (the claimed identity inside the message) are never cross-checked against each other, exactly like the ERC721 bug where `creator` (the message sender) was never checked against `owner` (the actual NFT owner derived from on-chain state).

The forwarding branch (`else` at line 525) has the same gap: `target := protoAddrToNetAddr(m.RelayToAddr)` is used to look up `peer := rm.hostmap.QueryVpnAddr(target)` and install `AddRelay(rm.l, peer, f.hostMap, from, nil, ForwardingType, Requested)` — again keyed by attacker-supplied `from`, with `h.vpnAddrs` never consulted.

### Impact Explanation
A member of the mesh that has legitimately handshaked (any peer, without needing to compromise a CA-signed cert) can send a `CreateRelayRequest`/claim an arbitrary `RelayFromAddr` that does not correspond to any address in its own certificate. Because relay state (`RelayState.relayForByAddr`, `relayForByIdx`) is keyed by this unverified address, this can be used to:
- Register bogus/poisoned relay entries for arbitrary victim vpnAddrs on the relay node (`h`), confusing which HostInfo is considered the legitimate relay-for-X.
- Potentially intercept or redirect traffic destined for a victim's vpnAddr through the attacker's own tunnel `h`, since subsequent packets addressed to that relay index/vpnAddr on `h` will be treated as belonging to the claimed victim identity — a form of remote state poisoning of the relay hostmap.
This satisfies the "remote state poisoning" impact category permitted by the rules (analogous to the fake-listing/state-poisoning impact of the original ERC721 finding, where anyone could inject state associated with an identity they don't own).

### Likelihood Explanation
Any connected peer can trigger this: it only requires completing a normal handshake (no special privilege) and then sending a crafted `NebulaControl_CreateRelayRequest`/`CreateRelayResponse` control message with a `RelayFromAddr`/`RelayToAddr` that doesn't match its own certificate's vpn addresses. The relay code path is reached automatically whenever `am_relay` is enabled on a node, which is a common relay-server configuration. This is a moderate/high likelihood misuse since it requires no cryptographic break, just a modified but authenticated payload field.

### Recommendation
In `handleCreateRelayRequest` (and `handleCreateRelayResponse`), validate that `from` (`RelayFromAddr`/`OldRelayFromAddr`) is contained within `h.vpnAddrs` (the certificate-verified addresses of the HostInfo that actually sent the control message) before using it to install or query relay state. Reject the message (log and return) if `from` is not one of `h`'s own verified vpn addresses, mirroring the `correctHostResponded`/`validatePeerCert` pattern already used in the handshake path.

### Proof of Concept
1. Peer `E` (evil) completes a normal handshake with relay node `R` (which has `relay.am_relay = true`), obtaining a valid `HostInfo` `h` on `R` with `h.vpnAddrs = [E_addr]`.
2. `E` sends `R` a `NebulaControl_CreateRelayRequest` with `RelayFromAddr = V_addr` (a victim's vpn address it does not own) and `RelayToAddr = R_addr` (or another reachable target).
3. In `handleCreateRelayRequest`, `from := protoAddrToNetAddr(m.RelayFromAddr)` yields `V_addr`; since target==me path is taken, `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` registers relay state on `h` keyed by `V_addr`, with no check that `V_addr ∈ h.vpnAddrs`.
4. `R`'s relay hostmap now associates `E`'s tunnel `h` with victim `V`'s address for relay purposes, even though `E` never proved ownership of `V_addr` via certificate/handshake — enabling relay-state confusion/poisoning analogous to the original "anyone can create a listing for another user's NFT" bug.
