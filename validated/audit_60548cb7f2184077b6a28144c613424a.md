### Title
Missing contract-id binding in StackerDB chunk signatures allows cross-StackerDB chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the digest that a StackerDB signer signs from only `slot_id`, `slot_version`, and `data_hash` — it never includes the StackerDB's `QualifiedContractIdentifier` (or any other DB-scoping value). Any signed `StackerDBChunkData` that is valid for one StackerDB replica is therefore also a valid, verifiable signature for any *other* StackerDB replica in which the same signer address is assigned the same `slot_id`, letting an attacker replay an old/foreign chunk into a different StackerDB and have it accepted as authentic.

### Finding Description
The signing/verification digest is: [1](#0-0) 

and verification recovers the public key from this digest and compares only against the `principal` address the caller supplies: [2](#0-1) 

Note that the digest commits to `slot_id`, `slot_version`, and `data_hash` only. The binding to a *specific StackerDB instance* (the `QualifiedContractIdentifier`) is supplied entirely out-of-band by the verifying code, not by the signed data itself.

Both write paths look up the expected signer address for `(contract_id, slot_id)` and then call `verify()`/`try_replace_chunk`, trusting that a passing signature check means the chunk was authored *for that DB*:

- The local RPC path `try_replace_chunk` verifies against the DB's own `slot_validation.signer` and otherwise only checks chunk size, staleness, and write-count — it never checks that the signature was produced with this specific `smart_contract`/`stackerdb_id` in mind: [3](#0-2) 

- The P2P unsolicited-push path `validate_received_chunk` does the same: it fetches `get_slot_signer(smart_contract_id, data.slot_id)` and calls `slot_metadata.verify(&addr)`, with no contract binding in the signed payload itself: [4](#0-3) 

- The HTTP `POST /v2/stackerdb/:principal/:contract/chunks` handler passes the request's `contract_identifier` straight into `try_replace_chunk`, and on success re-broadcasts the chunk to the P2P network as a `StackerDBPushChunk`, so a successfully-replayed chunk propagates network-wide: [5](#0-4) [6](#0-5) 

Because the digest never includes `contract_id`, whenever the same signer principal is configured as the owner of the same `slot_id` in two different StackerDB smart contracts (e.g. across two signer-set StackerDB instances for different reward cycles, or any deployment reusing the same signer/slot layout across contracts — this is a realistic Stacks Nakamoto signer topology, not a contrived edge case), a chunk that is validly signed for contract A will also pass `verify()`/`try_replace_chunk()`/`validate_received_chunk()` for contract B. An attacker who can observe or request that chunk from contract A (StackerDB reads require no authentication) can submit it unmodified as a POST or a `StackerDBPushChunk` targeting contract B's matching slot, and it will be accepted and stored as if the signer had authored it for B, then relayed to the whole network.

### Impact Explanation
This is an unauthenticated/unauthorized write to StackerDB state and network-wide propagation of forged/foreign data: a chunk never authored for contract B is accepted into contract B's DB and gossiped as legitimate to all replicas, because the equality actually being enforced ("signature recovers to the configured slot signer") is weaker than the equality the protocol needs ("signature was produced by the signer specifically for this StackerDB instance and slot"). This can be used to inject stale or attacker-chosen-timing data (any chunk the signer legitimately signed for another DB) into a different StackerDB, corrupting the replicated data other nodes rely on for that contract.

### Likelihood Explanation
Exploitation requires no privileged access — StackerDB chunks are read via unauthenticated GET endpoints and pushed/gossiped via unauthenticated P2P messages and the unauthenticated `POST .../chunks` RPC. The only precondition is that the same signer address own the same `slot_id` across two live StackerDB contracts, which is a plausible and even expected configuration pattern (e.g. consecutive reward-cycle signer-set StackerDBs) rather than a contrived scenario, since slot layouts are frequently derived deterministically from the same underlying stacker/signer set.

### Recommendation
Include the target `QualifiedContractIdentifier` (or an equivalent StackerDB instance identifier such as `stackerdb_id`) inside `SlotMetadata::auth_digest()` so that signatures are cryptographically bound to a specific StackerDB, and reject any chunk whose signature was not produced against a digest containing the contract the write is targeting.

### Proof of Concept
1. Configure two StackerDB contracts, A and B, where slot `0` is owned by the same signer address in both (e.g. two signer-set StackerDBs across reward cycles with identical slot assignment).
2. Signer signs a `StackerDBChunkData{slot_id: 0, slot_version: 1, data}` for contract A via `StackerDBChunkData::sign` — see `libstackerdb/src/libstackerdb.rs` `sign`/`get_slot_metadata` [7](#0-6) .
3. Attacker fetches this signed chunk from contract A's public read endpoint (no privileges needed).
4. Attacker POSTs the identical `slot_id`, `slot_version`, `sig`, `data` to contract B's `/v2/stackerdb/:addr/:contract/chunks` endpoint (or relays it as a `StackerDBPushChunk` targeting contract B).
5. `try_replace_chunk`/`validate_received_chunk` for contract B looks up B's slot-0 signer (the same address), calls `slot_desc.verify(&signer)`, which succeeds because `auth_digest()` never referenced contract A or B — the chunk is stored in B and rebroadcast to the network as legitimate B data.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
