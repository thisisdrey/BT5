## Analog Identified: `pallet-asset-rewards` skips reward accrual but still advances `last_update_block` when a pool has zero stakers

### Title
Reward-per-token checkpoint advances even when `total_tokens_staked == 0`, permanently forfeiting streamed rewards for empty pools - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` streams reward tokens to stakers based on elapsed blocks (`reward_rate_per_block`), similar to Curve's `LiquidityGauge`. Just like the Curve bug, `update_pool_rewards` unconditionally advances `last_update_block` to the current block even when the pool has no stakers, while `reward_per_token` (correctly) refuses to accrue `reward_per_token_stored` in that same zero-stake case. The result: reward tokens that were already deposited/streamed for the empty-pool window are silently dropped from the accounting and become recoverable only through `cleanup_pool`, which any staker can block indefinitely by keeping a dust amount staked.

### Finding Description
`reward_per_token` explicitly short-circuits and does not accrue anything when the pool is empty: [1](#0-0) 

But `update_pool_rewards`, which is called unconditionally right after `reward_per_token` in `update_pool_and_staker_rewards`, still moves `last_update_block` forward to "now" regardless of whether `total_tokens_staked` was zero: [2](#0-1) 

Because `last_update_block` is the checkpoint used to compute `rewardable_blocks_elapsed` in future calls, once it is bumped forward during a zero-stake window, the blocks that elapsed while the pool was empty are permanently excluded from any future `reward_per_token` computation — there is no mechanism to "catch up" that window later. This is the exact analog of the Curve `LiquidityGauge` bug: `last_update` (there `last_update_block` here) is updated even though `totalSupply` (`total_tokens_staked`) is zero, permanently orphaning reward tokens that were meant to be streamed for that period.

This checkpoint update is triggered from the completely public, unpermissioned `stake` extrinsic — any signed account can call it: [3](#0-2) 

Note that `update_pool_and_staker_rewards` is invoked with the pool's state *before* the new stake amount is added, so on the very first stake into an empty pool (or the first stake after everyone has fully unstaked), `total_tokens_staked` is still zero when `reward_per_token`/`update_pool_rewards` run.

The only way to recover reward tokens sitting unattributed in the pool's pot account is `cleanup_pool`, which requires the pool to have **zero stakers at call time**: [4](#0-3) 

Any unprivileged account can prevent this recovery path forever simply by keeping a minimal stake (e.g., 1 unit) in the pool, since `stakers.is_none()` will never be true, and `NonEmptyPool` will always be returned to the admin.

### Impact Explanation
Reward tokens funded into the pool (via `deposit_reward_tokens`, itself callable by anyone) for any block range during which the pool had zero stakers are never credited to `reward_per_token_stored`, and there is no code path to later reclaim them for legitimate reward distribution. Combined with an unprivileged staker who keeps a dust amount staked, the admin's only fund-recovery mechanism (`cleanup_pool`) can be blocked indefinitely, causing a permanent fund lock for those unaccounted reward tokens — directly matching the "permanent user-fund lock" impact category.

### Likelihood Explanation
This requires no privileged actor, malicious validator/collator, or governance action — any two unprivileged signed accounts can trigger it: (1) create a pool and let it sit empty for at least one block (or let it become fully unstaked at some point), which any staker can trivially engineer by calling `unstake` for their full balance and waiting, and (2) keep a minimal stake indefinitely to block `cleanup_pool`. The precondition (a pool transiently having zero stakers while already funded, or first-staker delay after `create_pool`) is a normal, easily reachable operational state, not a contrived edge case.

### Recommendation
Only advance `last_update_block` (and therefore the "elapsed blocks" checkpoint) when `total_tokens_staked > 0`, mirroring the fix Curve applied: `last_update` should only be updated when `totalSupply > 0`. Concretely, in `update_pool_rewards`, skip updating `last_update_block` when `pool_info.total_tokens_staked.is_zero()`, so that once staking resumes, the elapsed-blocks window still starts from the last time the pool had nonzero stake, ensuring streamed rewards for the empty period are not silently discarded. Alternatively/additionally, allow `cleanup_pool` (or an equivalent admin reclaim path) to recover the pot balance in excess of what remains claimable, independent of whether stakers are currently present.

### Proof of Concept
1. Admin calls `create_pool` with `reward_rate_per_block = R` and funds the pool via `deposit_reward_tokens`.
2. No one stakes for `N` blocks (pool sits at `total_tokens_staked == 0`), during which `R * N` reward tokens' worth of streaming was "intended" for this window per the rate model.
3. Account `A` calls `stake(pool_id, 1)`. Internally: `Pools::get(pool_id)` shows `total_tokens_staked == 0` → `reward_per_token` returns the unchanged stored value → `update_pool_rewards` sets `last_update_block = current_block` anyway (per `substrate/frame/asset-rewards/src/lib.rs:780`). The `N`-block window is now permanently excluded from any future accrual calculation.
4. Account `A` never fully unstakes (keeps `>0` staked forever). `cleanup_pool` therefore always fails with `Error::<T>::NonEmptyPool` (`substrate/frame/asset-rewards/src/lib.rs:704`), so the admin can never reclaim the pot's leftover balance corresponding to the skipped `N`-block window, even after pool `expiry_block` passes.

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

			Ok(())

		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
		}

		///
		/// Should be called prior to any operation involving a staker.
		///
		/// Returns the updated pool and staker info.
		///
		/// NOTE: this function has no side-effects. Side-effects such as storage modifications are
		/// the responsibility of the caller.
		pub fn update_pool_and_staker_rewards(
			pool_info: &PoolInfoFor<T>,
			staker_info: &PoolStakerInfo<T::Balance>,
		) -> Result<(PoolInfoFor<T>, PoolStakerInfo<T::Balance>), DispatchError> {
			let reward_per_token = Self::reward_per_token(&pool_info)?;
			let pool_info = Self::update_pool_rewards(pool_info, reward_per_token)?;

			let mut new_staker_info = staker_info.clone();
			new_staker_info.rewards = Self::derive_rewards(&staker_info, &reward_per_token)?;
			new_staker_info.reward_per_token_paid = pool_info.reward_per_token_stored;
			return Ok((pool_info, new_staker_info));
		}

		/// Computes update pool reward state.
		///
		/// Should be called every time the pool is adjusted, and a staker is not involved.
		///
		/// Returns the updated pool and staker info.
		///
		/// NOTE: this function has no side-effects. Side-effects such as storage modifications are
		/// the responsibility of the caller.
		pub fn update_pool_rewards(
			pool_info: &PoolInfoFor<T>,
			reward_per_token: T::Balance,
		) -> Result<PoolInfoFor<T>, DispatchError> {
			let mut new_pool_info = pool_info.clone();
			new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
