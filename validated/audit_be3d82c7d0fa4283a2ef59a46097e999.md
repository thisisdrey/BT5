### Title
Old Operator's Beneficiary Cannot Receive Commission After `switch_operator` — (`File: aptos-move/framework/aptos-framework/sources/staking_contract.move`)

---

### Summary

In `staking_contract.move`, `distribute_internal` redirects commission to a beneficiary only when `recipient == operator` (the **current** operator). After `switch_operator` is called, the old operator's pending commission is recorded in the distribution pool under `old_operator`'s address, but the staking contract is re-keyed to `new_operator`. When `distribute` is later called, `distribute_internal` receives `new_operator` as `operator`, so the check `recipient == operator` evaluates to `old_operator == new_operator` → **false**, and the commission is sent directly to `old_operator`, bypassing `old_operator`'s beneficiary entirely.

---

### Finding Description

**Step 1 — Commission is queued for `old_operator` inside `switch_operator`:** [1](#0-0) 

`distribute_internal` is called first with `old_operator` as the `operator` argument (correctly redirecting any already-inactive stake to the beneficiary). Then `request_commission_internal(old_operator, ...)` is called, which calls `add_distribution(operator, staking_contract, operator, commission_amount)` — recording `old_operator` as the recipient in the distribution pool for the newly-unlocked commission. [2](#0-1) 

The staking contract is then re-keyed to `new_operator`.

**Step 2 — `distribute_internal` only redirects when `recipient == operator` (the current operator):** [3](#0-2) 

When `distribute(staker, new_operator)` is called later, `distribute_internal` receives `operator = new_operator`. The distribution pool still contains `old_operator` as a recipient. The guard `if (recipient == operator)` evaluates to `old_operator == new_operator` → **false**. The commission is deposited directly to `old_operator`, not to `beneficiary_for_operator(old_operator)`.

**Step 3 — The existing test confirms the broken invariant:** [4](#0-3) 

The test asserts `beneficiary_address` balance is unchanged after the switch — which is treated as correct behavior, but it means the beneficiary silently loses the commission that `old_operator` earned before the switch.

---

### Impact Explanation

An operator sets a beneficiary via `set_beneficiary_for_operator`. The staker then calls `switch_operator`. The commission accrued up to the switch point is queued for `old_operator` in the distribution pool. When that commission is later distributed, it is sent to `old_operator` instead of the designated beneficiary. The beneficiary permanently loses their entitled APT commission rewards; those funds are diverted to `old_operator`. This is a direct, unprivileged-triggerable loss of user-controlled on-chain APT.

---

### Likelihood Explanation

The `set_beneficiary_for_operator` feature is a live, enabled mainnet feature (gated by `features::operator_beneficiary_change_enabled()`). Any staker can call `switch_operator` at any time. The combination is realistic in normal validator operations (e.g., operator rotation). No special privileges are required beyond being the staker of the contract. [5](#0-4) 

---

### Recommendation

In `distribute_internal`, replace the narrow `recipient == operator` guard with an unconditional `beneficiary_for_operator` lookup for every recipient:

```move
// Before (broken):
if (recipient == operator) {
    recipient = beneficiary_for_operator(operator);
};

// After (fixed):
recipient = beneficiary_for_operator(recipient);
```

Since `beneficiary_for_operator` returns the address itself when no beneficiary is set, this is a safe no-op for recipients without a beneficiary and correctly redirects for all operators — including `old_operator` after a switch. [6](#0-5) 

---

### Proof of Concept

1. `staker` creates a staking contract with `operator1` at 10% commission.
2. `operator1` calls `set_beneficiary_for_operator(operator1, beneficiary)`.
3. The stake pool earns rewards; `operator1` does **not** call `request_commission` yet.
4. `staker` calls `switch_operator(staker, operator1, operator2, 10)`.
   - Inside: `request_commission_internal(operator1, ...)` queues `commission_amount` for `operator1` in the distribution pool.
   - Staking contract is re-keyed to `operator2`.
5. Lockup expires; `distribute(staker, operator2)` is called.
   - `distribute_internal(staker, operator2, staking_contract)` runs with `operator = operator2`.
   - `recipient = operator1`; check `operator1 == operator2` → false.
   - `commission_amount` APT is sent to `operator1`, not `beneficiary`.
6. `beneficiary` receives 0 APT from this commission. `operator1` receives the full commission despite having delegated it to `beneficiary`.
