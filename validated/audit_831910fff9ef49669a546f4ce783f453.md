### Title
Protocol-treasury reward silently lost (permanently un-credited yoctoNEAR) when the treasury account is also a validator - ([File: chain/epoch-manager/src/reward_calculator.rs])

### Summary
`RewardCalculator::calculate_reward` inserts the treasury's reward into `res` keyed by `protocol_treasury_account`, then later inserts each validator's reward keyed by `account_id` into the same map. If `protocol_treasury_account` is also a selected validator for that epoch, the second insert overwrites the first, discarding the treasury credit while `epoch_actual_reward` (used as `minted_amount`, added to `total_supply`) already counted both amounts. Downstream, `Runtime::update_validator_accounts` only credits the treasury separately when it is *not* in `stake_info`, so when it is a validator the treasury share is never credited to any account, causing a real, permanent reduction in circulating (credited) supply relative to `total_supply`.

### Finding Description
In `calculate_reward`:
- `res.insert(self.protocol_treasury_account.clone(), epoch_protocol_treasury)` at [1](#0-0) 
- `epoch_actual_reward` is initialized to `epoch_protocol_treasury` at [2](#0-1) 
- The per-validator loop unconditionally does `res.insert(account_id, reward)` and `epoch_actual_reward = epoch_actual_reward.checked_add(reward)` for every account in `validator_block_chunk_stats`, including one equal to `protocol_treasury_account` [3](#0-2) 

Because `res` is a `HashMap`, the second `insert` for the same key overwrites the first, so `res[protocol_treasury_account]` ends up holding only the validator reward, not `epoch_protocol_treasury + validator_reward`. Meanwhile `epoch_actual_reward` (returned as `minted_amount`, ultimately added to `total_supply` per `core/primitives/src/block.rs` new_total_supply logic) still includes both amounts, so `sum(res.values()) == epoch_actual_reward - epoch_protocol_treasury`, strictly less than the declared minted amount.

The downstream consumer confirms this is not reconciled: `Runtime::update_validator_accounts` [4](#0-3)  credits the treasury account separately from `validator_rewards` only `if !validator_accounts_update.stake_info.contains_key(account_id)` [5](#0-4) . If the treasury account is a validator (i.e. present in `stake_info`), this special-case branch is skipped entirely, and the earlier per-stake-account loop only adds `validator_rewards.get(account_id)` (i.e., the overwritten, treasury-share-stripped value) to `account.locked()` [6](#0-5) . There is no code path that recovers the lost `epoch_protocol_treasury` amount once it is overwritten in the `res`/`validator_rewards` map.

Attacker path: an ordinary funded account submits a normal `Stake` transaction with nonzero stake, behaves as a normal validator (produces blocks/chunks/endorsements to stay above kickout/online thresholds), and gets selected into the validator set for a future epoch. This requires no special privilege beyond staking — any funded account can submit `Stake` actions. If `genesis_config.protocol_treasury_account` happens to equal (or is later set/known to equal) this account (e.g., is a chain where the treasury account is a normal, staking-capable account, or the attacker controls that specific account_id), the bug triggers automatically at every epoch boundary where that account validates.

Existing checks (signature/nonce/access-key/gas/storage-staking) are irrelevant here — they gate transaction admission, not the epoch-boundary reward map construction, which is an internal epoch-manager computation with no validation that `protocol_treasury_account` is disjoint from the validator set.

### Impact Explanation
This is a token-inflation/token-loss bug: `total_supply` (declared via `minted_amount`) is increased by `epoch_protocol_treasury` every affected epoch, but that amount is never credited to any account's `amount`/`locked` balance — it is permanently and silently removed from usable/circulating supply with no reconciliation, violating the value-conservation invariant (`sum(credited amounts) == declared minted amount`). This matches the "token inflation or loss" bounty category — specifically silent token destruction/loss of protocol treasury funds, recurring every epoch that the condition holds.

### Likelihood Explanation
Preconditions: the account with `account_id == genesis_config.protocol_treasury_account` must be selected into the validator set for an epoch. On networks where the treasury account is a normal, staking-capable account (not administratively barred from staking), any accountholder — including the treasury account's controller or an attacker who somehow acquires/uses that same account_id — can submit a `Stake` transaction and, with ordinary uptime, get selected as validator, deterministically triggering the bug every such epoch. Cost is just the price of a `Stake` transaction and maintaining a normal validator (feasible, no exotic race or edge case), and the effect is repeatable every epoch. The bug is purely a `HashMap` key-collision defect in `calculate_reward`.

### Recommendation
Do not use a single flat `HashMap` keyed only by `account_id` to store the treasury reward and validator rewards under the risk of aliasing. Either:
1. Check if `account_id == self.protocol_treasury_account` inside the loop and use `entry(account_id).and_modify(|r| *r = r.checked_add(reward).unwrap()).or_insert(reward)` instead of a blind `insert`, ensuring rewards for the same account accumulate rather than overwrite; or
2. Keep the treasury reward tracked in a separate field/tuple element rather than merging it into the validator reward map, and have `update_validator_accounts` always add the treasury share independent of whether the account is also a staking validator.

### Proof of Concept
Unit test in `chain/epoch-manager/src/reward_calculator.rs`:
```rust
#[test]
fn test_treasury_reward_lost_when_treasury_is_validator() {
    let epoch_length = 1000;
    let max_inflation_rate = Ratio::new(1, 100);
    let treasury_account: AccountId = "near".parse().unwrap();
    let reward_calculator = RewardCalculator {
        num_blocks_per_year: 1000,
        epoch_length,
        protocol_reward_rate: Ratio::new(1, 10), // nonzero treasury share
        protocol_treasury_account: treasury_account.clone(),
        num_seconds_per_year: 1000,
        genesis_protocol_version: PROTOCOL_VERSION,
    };
    // "near" (the treasury account) is ALSO a selected validator this epoch.
    let validator_block_chunk_stats = HashMap::from([(
        treasury_account.clone(),
        BlockChunkValidatorStats {
            block_stats: ValidatorStats { produced: 1000, expected: 1000 },
            chunk_stats: ChunkStats::new_with_production(1000, 1000),
        },
    )]);
    let validator_stake = HashMap::from([(treasury_account.clone(), Balance::from_yoctonear(500_000))]);
    let total_supply = Balance::from_yoctonear(1_000_000_000);
    let (rewards, actual_minted) = reward_calculator.calculate_reward(
        validator_block_chunk_stats,
        &validator_stake,
        total_supply,
        PROTOCOL_VERSION,
        epoch_length * NUM_NS_IN_SECOND,
        ValidatorOnlineThresholds {
            online_min_threshold: Ratio::new(9, 10),
            online_max_threshold: Ratio::new(99, 100),
            endorsement_cutoff_threshold: None,
        },
        max_inflation_rate,
    );
    let sum_credited: u128 = rewards.values().map(|b| b.as_yoctonear()).sum();
    // Expect FAIL on current code: sum_credited < actual_minted, i.e. treasury share is lost.
    assert_eq!(sum_credited, actual_minted.as_yoctonear(),
        "sum of credited rewards must equal actual minted amount; treasury share was silently dropped");
}
```
Expected result on current code: the assertion fails because `sum_credited == actual_minted - epoch_protocol_treasury` (strictly less), demonstrating the map-total/minted-total mismatch. A companion integration test can extend `test_validator_reward` in `chain/chain/src/runtime/tests.rs` (or the `test-loop-tests` inflation harness) with a validator whose `account_id` equals `genesis_config.protocol_treasury_account`, then assert `view_account(treasury).amount + locked` only grew by the validator reward, not `validator_reward + protocol_treasury_reward`, while `total_supply` grew by the full sum — confirming permanent loss at the runtime/state level via `update_validator_accounts` [4](#0-3) .

    fn update_validator_accounts(
        &self,
        state_update: &mut TrieUpdate,
        validator_accounts_update: &ValidatorAccountsUpdate,
    ) -> Result<(), RuntimeError> {
        for (account_id, max_of_stakes) in &validator_accounts_update.stake_info {
            if let Some(mut account) = get_account(state_update, account_id)? {
                if let Some(reward) = validator_accounts_update.validator_rewards.get(account_id) {
                    tracing::debug!(target: "runtime", %account_id, %reward, locked = %account.locked(), "account adding reward to stake");
                    let locked = account.locked().checked_add(*reward).ok_or_else(|| {
                        RuntimeError::UnexpectedIntegerOverflow("update_validator_accounts".into())
                    })?;
                    account.set_locked(locked).or_inconsistent_state(account_id)?;
                }

                tracing::debug!(target: "runtime",
                       %account_id, locked = %account.locked(), %max_of_stakes,
                       "account stake and max of stakes"
                );
                if account.locked() < *max_of_stakes {
                    return Err(StorageError::StorageInconsistentState(format!(
                        "FATAL: staking invariant does not hold. \
                         Account stake {} is less than maximum of stakes {} in the past three epochs",
                        account.locked(),
                        max_of_stakes)).into());
                }
                let last_proposal = *validator_accounts_update
                    .last_proposals
                    .get(account_id)
                    .unwrap_or(&Balance::ZERO);
                let return_stake = account
                    .locked()
                    .checked_sub(max(*max_of_stakes, last_proposal))
                    .ok_or_else(|| {
                        RuntimeError::UnexpectedIntegerOverflow(
                            "update_validator_accounts - return stake".into(),
                        )
                    })?;
                tracing::debug!(target: "runtime", %account_id, %return_stake, "account return stake");
                let locked = account.locked().checked_sub(return_stake).ok_or_else(|| {
                    RuntimeError::UnexpectedIntegerOverflow(
                        "update_validator_accounts - set_locked".into(),
                    )
                })?;
                account.set_locked(locked).or_inconsistent_state(account_id)?;
                account.set_amount(account.amount().checked_add(return_stake).ok_or_else(
                    || {
                        RuntimeError::UnexpectedIntegerOverflow(
                            "update_validator_accounts - set_amount".into(),
                        )
                    },
                )?);

                set_account(state_update, account_id.clone(), &account);
            } else if *max_of_stakes > Balance::ZERO {
                // if max_of_stakes > 0, it means that the account must have locked balance
                // and therefore must exist
                return Err(StorageError::StorageInconsistentState(format!(
                    "Account {} with max of stakes {} is not found",
                    account_id, max_of_stakes
                ))
                .into());
            }
        }

        if let Some(account_id) = &validator_accounts_update.protocol_treasury_account_id {
            // If protocol treasury stakes, then the rewards was already distributed above.
            if !validator_accounts_update.stake_info.contains_key(account_id) {
                let mut account = get_account(state_update, account_id)?.ok_or_else(|| {
                    StorageError::StorageInconsistentState(format!(
                        "Protocol treasury account {} is not found",
                        account_id
                    ))
                })?;
                let treasury_reward = *validator_accounts_update
                    .validator_rewards
                    .get(account_id)
                    .ok_or_else(|| {
                        StorageError::StorageInconsistentState(format!(
                            "Validator reward for the protocol treasury account {} is not found",
                            account_id
                        ))
                    })?;
                account.set_amount(account.amount().checked_add(treasury_reward).ok_or_else(
                    || {
                        RuntimeError::UnexpectedIntegerOverflow(
                            "update_validator_accounts - treasure_reward".into(),
                        )
                    },
                )?);
                set_account(state_update, account_id.clone(), &account);
            }
        }
        state_update.commit(StateChangeCause::ValidatorAccountsUpdate);

        Ok(())
    }
