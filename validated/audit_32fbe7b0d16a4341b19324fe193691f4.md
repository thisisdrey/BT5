### Title
`remove_account` fails to clear postponed-receipt bookkeeping, letting a stale self-targeted `ActionReceipt` execute with self-privilege against a re-created account of the same name - (`core/store/src/utils/mod.rs`)

### Summary
`remove_account` deletes `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie entries for a deleted account, but never touches `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` entries left behind by `process_action_receipt` when a self-targeted `ActionReceipt` is still waiting on `DataReceipt`s. If the account is deleted while such a receipt is postponed and the account name is later re-created, the arriving `DataReceipt`s will still resolve the stale postponed receipt and execute its actions against the brand-new account, with `predecessor_id == receiver_id` ("self") privilege that the new account owner never granted.

### Finding Description
`process_action_receipt` persists postponed-receipt bookkeeping keyed only by `receiver_id`/`receipt_id`/`data_id`, independent of whether an `Account` record currently exists at that id: [1](#0-0) 

`remove_account`, invoked from `action_delete_account`, removes `Account`, `ContractCode`, access/gas keys, and `ContractData`, but has no logic to scan for or purge any outstanding `PostponedReceipt`, `PendingDataCount`, or `PostponedReceiptId` entries for the account being deleted: [2](#0-1) 

`action_delete_account` performs storage-usage, gas-key-balance, and locked-stake checks, but nothing that inspects pending postponed receipts before calling `remove_account` and clearing the in-memory `account`: [3](#0-2) 

When a later `DataReceipt` arrives, `process_receipt` looks up `TrieKey::PostponedReceiptId` purely by `receiver_id`/`data_id`, decrements `PendingDataCount`, and once it reaches zero fetches and executes the postponed `ActionReceipt` — with no check that the account entity is the same one that existed when the receipt was postponed: [4](#0-3) 

`apply_action_receipt` then simply loads whatever account currently exists at that id via `get_account` and executes the stale receipt's actions against it: [5](#0-4) 

Because the stale receipt's `predecessor_id == receiver_id` (the account addressed itself), `check_actor_permissions` treats every action in it as self-authorized ("sir") regardless of the fact that the account underneath has been deleted and re-created with entirely different ownership, keys, or contract code — violating the invariant that a promise must not carry privileges its creator did not actually hold on the (new) target account.

### Impact Explanation
Any action carried in the stale postponed `ActionReceipt` — `Transfer`, or a `FunctionCall` invoking `#[private]`/self-only methods common in `near-sdk` contracts — executes against the freshly re-created account with full self-call ("sir") privilege. This can drain funds transferred into the recreated account or invoke privileged self-only contract logic (state resets, minting, ownership changes) that the new account owner never authorized. This falls under authorization escalation across accounts/promises and potential theft of user funds.

### Likelihood Explanation
Exploitation requires: (1) an attacker-controlled account issuing itself an `ActionReceipt` with unmet `input_data_ids` (a normal `promise_then`-on-self pattern), (2) deleting that account via `DeleteAccountAction` before the data arrives, (3) the exact same account name being re-created later (requires either the attacker controlling the parent account for a sub-account name, or an unrelated party independently picking the freed name), and (4) the pending `DataReceipt`s eventually resolving after re-creation, which requires the attacker to control the delivery timing of the underlying cross-contract calls (e.g., via a promise-yield-style multi-block delay) to widen the window between deletion and re-creation. All of this is achievable by an ordinary account holder issuing self-signed transactions and deploying their own contracts — no privileged access needed — but the timing window for an *unrelated* victim to reuse the exact same freed account name while the trap is still armed is narrow, making organic (non-colluding) exploitation opportunistic rather than trivially repeatable at will.

### Recommendation
When `remove_account` (or `action_delete_account`) deletes an account, also enumerate and remove any `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` entries keyed by that `receiver_id` (mirroring the existing access-key/contract-data prefix iteration already performed in `remove_account`), so no dangling postponed-receipt state can be matched against a future re-creation of the same account name. Alternatively, reject `DeleteAccountAction` while any postponed receipt exists for the account, similar to the existing locked-stake check.

### Proof of Concept
Runtime integration test (in `runtime/runtime/src/tests/apply.rs` style, using `setup_runtime`):
1. Create account `victim.near` with initial balance and a deployed contract.
2. Submit a receipt whose `ActionReceipt` has `receiver_id == predecessor_id == "victim.near"` and two `input_data_ids` (unmet), containing a `Transfer` (or `FunctionCall` to a self-only method) action — assert it is stored as `PostponedReceipt`/`PendingDataCount`/two `PostponedReceiptId` entries via `get_postponed_receipt`.
3. Submit a `DeleteAccountAction` receipt for `victim.near` (locked == 0) with a distinct beneficiary; commit and confirm `get_account(..., "victim.near")` is `None`, but `get_postponed_receipt` for the earlier receipt_id still returns `Some`.
4. Submit a `CreateAccount`+`Transfer` receipt re-creating `victim.near` with a fresh balance and no contract, commit.
5. Deliver the two `DataReceipt`s for the original `data_id`s; assert the runtime executes the stale `ActionReceipt`, mutating the newly created account's `Account.amount`/state despite the new owner never authorizing that action, confirming the authorization/value-conservation invariant violation.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
