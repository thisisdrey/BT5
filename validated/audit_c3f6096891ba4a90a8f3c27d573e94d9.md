Both the transaction packet deduper (`core/src/sigverify_stage.rs`) and the shred deduper (`turbine/src/sigverify_shreds.rs`) share the same structural pattern as the reported bug: a hard-coded probabilistic bound (bloom-filter capacity / false-positive-rate) is assumed to hold, and when real-world load pushes past that assumption, the "security check" (dedup) starts failing in a way that silently disables core functionality (dropping legitimate, never-seen transactions) rather than failing safe. This is directly analogous to the oracle's hard-coded `minPrice`/`maxPrice` bound that, once breached, disables swaps rather than degrading gracefully.

### Title
Deduper bloom-filter saturation causes valid transactions to be silently discarded as false-positive duplicates - (File: perf/src/deduper.rs)

### Summary
`Deduper` (a Bloom filter used to drop duplicate network packets before sigverify) is sized with a fixed `num_bits` and monitored against a fixed `false_positive_rate` threshold that is only checked periodically (every 10ms) by a background "servicer" thread, not synchronously with each `dedup()` call. Any unprivileged sender that can push enough distinct packets into the shared filter within a reset window can drive the real false-positive rate towards saturation before the next periodic check resets it, causing concurrently-arriving, legitimate, unique transactions from unrelated users to be marked as duplicates and silently discarded — never reaching sigverify or banking stage.

### Finding Description
`Deduper::dedup` sets bits in a shared bit array keyed only by the raw packet payload hash, with no notion of sender identity or stake: [1](#0-0) . The saturation check (`maybe_reset`) computes the current false-positive rate from `popcount` and only resets the filter if it is already saturated or a time-based `reset_cycle` has elapsed: [2](#0-1) . In `SigVerifyStage`, this check runs asynchronously on a background thread on a 10ms poll loop, decoupled from the actual `dedup()` calls happening concurrently in the worker pool: [3](#0-2) . The dedup call itself is on the hot path for every incoming non-vote/TPU-vote packet batch, and any packet whose hash collides in the shared bit array is immediately marked `discard`, with no cross-check against true duplication: [4](#0-3) . The filter's own test suite documents the exact bound being relied upon (`get_capacity`) and shows that once `popcount` exceeds this capacity, `false_positive_rate()` exceeds the configured threshold: [5](#0-4) . The equivalent shred-path deduper explicitly documents the same class of risk in a code comment, acknowledging that false positives can block legitimate block-repair "until the deduper is reset after `DEDUPER_RESET_CYCLE`" (5 minutes for shreds): [6](#0-5) [7](#0-6) .

### Impact Explanation
Because the shared `Deduper` is keyed only on packet bytes, an unprivileged attacker who submits a sufficient volume of distinct packets (even garbage ones, as long as `packet.data(..)` succeeds) directly to the TPU packet ingestion path can drive the filter's popcount above its designed capacity. During the window before the next periodic `maybe_reset` observes and clears the saturation, unrelated honest users' legitimate, never-before-seen transactions can collide in the bit array and be marked `discard`, i.e. silently dropped before signature verification or banking stage — mirroring the reported bug class where a hard-coded bound, once exceeded, disables the intended core function (here, transaction ingestion) instead of failing safe. This is a transaction-landing DoS against arbitrary victims sharing the deduper state, not just the attacker.

### Likelihood Explanation
The filter capacities are fixed and computable from the code: for the TPU non-vote/vote streams (`DEDUPER_NUM_BITS = 63_999_979`, `DEDUPER_FALSE_POSITIVE_RATE = 0.001`), the test suite confirms saturation begins at roughly ~2,023,857 distinct entries: [8](#0-7) , with a worst-case exposure window of `MAX_DEDUPER_AGE = 2s` before a scheduled reset: [9](#0-8) . Reaching this volume requires a sustained, high packet-rate flood, but requires no stake, no special privilege, and no signature validity — packets only need to reach `packet.data(..)` before verification occurs.

### Recommendation
Decouple saturation detection from the fixed polling interval (e.g., check/react to saturation inline in the hot dedup path, or shrink the reset cycle), size the filter dynamically based on observed ingress rate rather than a fixed constant, and/or partition or rate-limit dedup state by sender/connection so that one unprivileged flooder cannot degrade the false-positive rate for all other senders' distinct, legitimate transactions.

### Proof of Concept
Not independently executable from static analysis, but the vulnerable path is fully traceable in-repo: `perf/src/deduper.rs` `test_dedup_capacity` and `test_dedup_saturated` (lines 200-300) empirically demonstrate that once `popcount` crosses the documented capacity for a given `(num_bits, false_positive_rate)` pair, `false_positive_rate() >= threshold` and previously-unseen inputs begin colliding; `core/src/sigverify.rs::run_transaction_task` (lines 282-298) shows that any such collision unconditionally discards the packet with no secondary verification, and `core/src/sigverify_stage.rs::servicer` (lines 260-294) shows the saturation check/reset only runs on a fixed 10ms/2s cadence, decoupled from the hot dedup path where the false-positive damage occurs.

    pub fn maybe_reset<R: Rng>(
        &self,
        rng: &mut R,
        false_positive_rate: f64,
        reset_cycle: Duration,
    ) -> bool {
        assert!(0.0 < false_positive_rate && false_positive_rate < 1.0);
        let _reset_guard = self.reset_guard.lock().unwrap();
        let saturated = self.false_positive_rate() >= false_positive_rate;
        if saturated || self.state.load().started_at.elapsed() >= reset_cycle {
            self.reset(rng);
        }
        saturated
    }

    // Returns true if the data is duplicate.
    #[must_use]
    #[allow(clippy::arithmetic_side_effects)]
    pub fn dedup(&self, data: &T) -> bool {
        let mut out = true;
        let state = self.state.load();
        for random_state in state.random_states.iter() {
            let hash: u64 = random_state.hash_one(data) % self.num_bits;
            let index = (hash >> 6) as usize;
            let mask: u64 = 1u64 << (hash & 63);
            let old = self.bits[index].fetch_or(mask, Ordering::Relaxed);
            if old & mask == 0u64 {
                self.popcount.fetch_add(1, Ordering::Relaxed);
                out = false;
            }
        }
        out
    }

    fn servicer(
        exit: Arc<AtomicBool>,
        mut non_vote_state: ServicerState,
        mut tpu_vote_state: ServicerState,
    ) -> JoinHandle<()> {
        let mut last_print = Instant::now();
        Builder::new()
            .name("solSigVerSvc".to_string())
            .spawn(move || {
                let mut rng = rand::rng();
                while !exit.load(Ordering::Relaxed) {
                    for state in [&mut non_vote_state, &mut tpu_vote_state] {
                        if state.deduper.maybe_reset(
                            &mut rng,
                            DEDUPER_FALSE_POSITIVE_RATE,
                            MAX_DEDUPER_AGE,
                        ) {
                            state.stats.num_deduper_saturations += 1;
                        }
                    }
                    if last_print.elapsed() > SigVerifierStats::REPORT_INTERVAL {
                        non_vote_state
                            .stats
                            .maybe_report_and_reset(non_vote_state.metrics_name);
                        tpu_vote_state
                            .stats
                            .maybe_report_and_reset(tpu_vote_state.metrics_name);
                        last_print = Instant::now();
                    }
                    thread::sleep(Duration::from_millis(10));
                }
            })
            .unwrap()
    }
