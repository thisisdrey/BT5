Audit Report

## Title
Relayer reward paid regardless of message execution outcome due to unchecked `DeliveryReceipt.success` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`process_delivery_receipt` decodes an Ethereum `InboundMessageDispatched` event into a `DeliveryReceipt` struct that carries an explicit `success: bool` field, but the function pays the relayer reward and deletes the `PendingOrders` entry based only on `order.fee > 0` and a valid nonce, never inspecting `receipt.success`. This allows a relayer to be rewarded for messages whose execution on Ethereum actually failed.

## Finding Description
`DeliveryReceipt` is decoded from the `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` Ethereum event and includes the `success` field capturing whether the dispatched command actually executed successfully on the gateway contract on Ethereum. [1](#0-0) 

In `submit_delivery_receipt`, any signed account can submit an `EventProof`; the pallet verifies the log authenticity via `T::Verifier::verify` (which only attests the log is a genuine on-chain Ethereum log, not that the underlying dispatch succeeded) and decodes it into `DeliveryReceipt`, then calls `process_delivery_receipt`. [2](#0-1) 

Inside `process_delivery_receipt`, the code checks `receipt.gateway`, resolves `reward_account`, fetches the `PendingOrder` by `receipt.nonce`, and unconditionally calls `T::RewardPayment::register_reward` whenever `order.fee > 0`, then removes the `PendingOrders` entry — `receipt.success` is decoded but never read. [3](#0-2) 

A grep across the entire `bridges/snowbridge` tree confirms `receipt.success` (or any `.success` field access) is referenced only at its struct definition and nowhere in the reward-payment or settlement logic, verifying the missing check is not compensated elsewhere.

## Impact Explanation
This is a theft/unbacked-payout of relayer reward funds: any relayer holding a valid Ethereum log/proof for a failed dispatch (`success: false`, e.g. a reverted or out-of-gas command execution on the gateway) can call `submit_delivery_receipt` and receive `order.fee` from `T::RewardPayment::register_reward` exactly as if the message had succeeded. Because `PendingOrders::remove(nonce)` executes unconditionally right after, the order state is destroyed regardless of outcome, permanently precluding any later reconciliation, retry, or fee-clawback for that nonce. This breaks the intended settlement invariant that reward should be conditioned on actual successful delivery/execution, causing over-payment/leakage from the relayer reward pool without correct binding to delivery outcome.

## Likelihood Explanation
The failed-dispatch case (`success: false`) is a legitimate, permissionless-to-observe outcome on Ethereum (e.g., gas exhaustion or revert in gateway command execution) requiring no malicious peer, validator, governance action, or leaked key. Any relayer who possesses the true Ethereum event log and merkle/receipt proof for that failed dispatch can call the public, signed extrinsic `submit_delivery_receipt` and be rewarded identically to the success path — the flaw is deterministically reachable and repeatable per failing nonce.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only invoke `T::RewardPayment::register_reward` when `receipt.success == true`. For the `false` case, define explicit handling (e.g., emit a distinct `MessageDeliveryFailed` event, and decide whether to forfeit, refund to sender, or otherwise account for the fee) rather than treating both outcomes identically and unconditionally removing `PendingOrders`.

## Proof of Concept
1. A message is enqueued and `do_process_message` creates `PendingOrder { nonce, fee, .. }` in `PendingOrders`. [4](#0-3) 
2. On Ethereum, the gateway's command execution for that nonce reverts/fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds an `EventProof` for that failed-execution log and calls `submit_delivery_receipt(origin, event)`. [5](#0-4) 
4. `process_delivery_receipt` verifies the proof and gateway, decodes `success: false` into `receipt`, but proceeds to `register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee)` and then `PendingOrders::remove(nonce)` regardless. [6](#0-5) 
5. The relayer is rewarded for a message that never executed successfully on Ethereum, and the `PendingOrders` state needed to detect or correct this is gone — a Rust unit test constructing a `DeliveryReceipt { success: false, .. }` and asserting `Balances`/reward ledger change after calling `process_delivery_receipt` would reproduce this deterministically.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
