### Title
Permissionless, non-atomic pool account migration in `pallet-asset-conversion-ops` leaves liquidity split across two accounts and silently unreachable to normal pool operations - (File: `substrate/frame/asset-conversion/ops/src/lib.rs`)

### Summary
`pallet_asset_conversion_ops::migrate_to_new_account` is the direct analog of Connext's `setWrapper`: it changes the "wrapper" (the account that actually custodies pool funds) from a prior derivation (`T::PriorAccountIdConverter`) to a new one (`T::PoolLocator::address`), but every other part of `pallet-asset-conversion` (swap, add/remove liquidity, quoting) keeps resolving a pool's holding account purely from `T::PoolLocator::address(pool_id)` [1](#0-0) . Exactly like `canonicalToAdopted` continuing to point at the old wrapper `X` after `setWrapper(Y)`, `Pools::<T>` and all pool-operation code continue to treat the pool as fully usable via the new address the instant a runtime upgrade changes `PoolLocator`, while the actual liquidity is still sitting in the old (`PriorAccountIdConverter`) account until someone permissionlessly calls `migrate_to_new_account` for that specific pair.

### Finding Description
- `pallet-asset-conversion`'s core operations derive the pool's holding account solely from `T::PoolLocator::address(pool_id)` — there is no per-pool stored account, and no flag recording whether a pool has been migrated to the new derivation scheme [2](#0-1) .
- `pallet_asset_conversion_ops::migrate_to_new_account` is a permissionless (`ensure_signed` only, no origin filter) extrinsic that moves `asset1`, `asset2`, and `lp_token` balances, one pool-pair at a time, from `prior_account` to `new_account` [3](#0-2) .
- Because migration is pool-by-pool and voluntary, after a runtime upgrade that changes the account-derivation logic (e.g., adding the `PalletId` seed introduced in `pr_3250.prdoc`), **every existing pool instantly starts being addressed by `PoolLocator::address` (the new account) by `swap_exact_tokens_for_tokens`, `add_liquidity`, `remove_liquidity`, and RPC quoting**, even though its actual reserves are still held at `PriorAccountIdConverter`'s account, until this specific migration extrinsic is run for that exact asset pair.
- During this window (which can be arbitrarily long, since migration is optional and per-pair), the pool's `Pools::<T>` entry (`exists`) reports the pool as live, so callers do not receive `PoolNotFound`; instead:
  - `add_liquidity` against the new (empty) account computes reserves against a near-zero balance, producing a badly mispriced LP mint (essentially the first-liquidity-provider bootstrap formula) even though real reserves already exist elsewhere.
  - `swap_exact_tokens_for_tokens` executes against a wrong/empty reserve, producing incorrect (potentially unbounded) price impact, or fails.
  - The rightful liquidity providers holding LP tokens tied to the *old* account's reserve cannot redeem against the *new* account, because `remove_liquidity` burns LP for a share of whatever balance is in `PoolLocator::address(pool_id)` — the wrong account.
- This precisely mirrors the Connext root cause: the wrapper/account was changed at one point (`PoolLocator`), but the rest of the system (all pool math and settlement in `pallet-asset-conversion`) still keys off the assumption that the current locator always points at the account holding the funds, when in fact stale (prior) association can persist per-pool until an explicit, unprivileged, opt-in fixup call is made.

### Impact Explanation
This can cause direct fund loss/misappropriation for liquidity providers and swappers: value can be extracted from a pool whose real balance sits in the "prior" account by interacting with the "new" account address as if it were the live pool, and legitimate LP holders can be unable to redeem the correct value of their position (fund lock) until migration executes. This fits the "duplicate settlement or payout," "permanent user-fund... lock," and "runtime bugs that compromise intended behavior" impact categories, since ordinary (non-privileged, non-relayer, non-admin) transaction senders drive the mismatch merely by calling standard, public `pallet-asset-conversion` extrinsics before someone calls the migration extrinsic.

### Likelihood Explanation
The trigger condition is a runtime upgrade of `PoolLocator`'s account-derivation scheme (which the SDK explicitly supports and has already exercised once, per `pr_3250.prdoc`, moving from `AccountIdConverterNoSeed` to a `PalletId`-seeded scheme). Migration is per-pool-pair and requires a specific extrinsic call; nothing prevents normal `swap`/`add_liquidity`/`remove_liquidity` calls from proceeding against not-yet-migrated pools in the interim, so likelihood is high whenever such an upgrade lands and is not synchronized with an atomic, mandatory, on-chain migration of every existing pool (the current design leaves it opt-in and unprivileged).

### Recommendation
Make account-derivation migration atomic and mandatory rather than an optional per-pool user-triggered extrinsic: either (a) run a chain-wide, weight-metered `SteppedMigration` that force-migrates every pool at upgrade time before the new `PoolLocator` becomes active, or (b) store the pool's actual holding account (or a "migrated" flag) inside `Pools::<T>` and have `swap`/`add_liquidity`/`remove_liquidity` resolve the account from that stored value (falling back to `PriorAccountIdConverter` only when unmigrated), so pool operations always target the account that truly custodies the reserves, closing the same gap the Connext report highlighted for `canonicalToAdopted`.

### Proof of Concept
1. Assume a runtime upgrade lands with a new `T::PoolLocator` derivation (as introduced by `pr_3250.prdoc`); existing pool `(A, B)` retains its liquidity at `PriorAccountIdConverter::try_convert((A,B))`.
2. Immediately post-upgrade, before anyone calls `pallet_asset_conversion_ops::migrate_to_new_account`, call `pallet_asset_conversion::add_liquidity(A, B, ...)`. The pallet computes reserves via `T::PoolLocator::address((A,B))`, which is empty, so the LP-mint math treats this as a fresh pool bootstrap.
3. Existing LP holders whose tokens represent a share of the old account's balance now hold claims against a stale reserve baseline; a caller can also call `swap_exact_tokens_for_tokens` against the empty "new" account to obtain a mispriced trade or to force `PoolNotFound`/reserve errors, while the pool is still recorded as existing in `Pools::<T>` [4](#0-3) .
4. Only when `migrate_to_new_account(A, B)` is eventually and voluntarily called does the true balance move to the address that `pallet-asset-conversion` has already been treating as canonical, at which point any interactions executed in step 2/3 have already produced incorrect settlement.

*Note: I was not able to fully trace every downstream consumer of `PoolLocator::address` inside `substrate/frame/asset-conversion/src/swap.rs` and `liquidity.rs` (e.g., exact reserve-lookup call sites) due to tool/iteration limits; a Devin session with full repository access should confirm the precise reserve-lookup code paths in `swap.rs`/`liquidity.rs` and validate whether any additional guard (e.g., an implicit `PoolNotFound` check tied to balance) already mitigates this before finalizing severity.*

			origin: OriginFor<T>,
			asset1: Box<T::AssetKind>,
			asset2: Box<T::AssetKind>,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;
			let info = Pools::<T>::get(&pool_id).ok_or(Error::<T>::PoolNotFound)?;

			let (prior_account, new_account) =
				Self::addresses(&pool_id).ok_or(Error::<T>::InvalidAssetPair)?;

			let (asset1, asset2) = pool_id.clone();

			// Assets that must be transferred to the new account id.
			let balance1 = T::Assets::total_balance(asset1.clone(), &prior_account);
			let balance2 = T::Assets::total_balance(asset2.clone(), &prior_account);
			let lp_balance = T::PoolAssets::total_balance(info.lp_token.clone(), &prior_account);

			ensure!(!balance1.is_zero(), Error::<T>::ZeroBalance);
			ensure!(!balance2.is_zero(), Error::<T>::ZeroBalance);
			ensure!(!lp_balance.is_zero(), Error::<T>::ZeroBalance);
