### Title
Revoked StackerDB signers retain write access when config reload falls back to `noop()` or drops to zero signers - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` decides whether to apply a freshly-loaded `StackerDBConfig` to the local, persisted slot/signer table. The gating condition skips the actual reconfiguration whenever the newly computed config has an **empty** signer list, which happens both when the controlling contract legitimately revokes all writers and — more importantly — whenever `StackerDBConfig::from_smart_contract` fails for any reason and falls back to `StackerDBConfig::noop()` (which always sets `signers: vec![]`). In that case the on-disk `chunks` table keeps the stale, previously-authorized signer for each slot, so a signer who has been removed/disabled in the controlling smart contract keeps being treated as the legitimate slot owner by `validate_received_chunk`, which authenticates incoming writes purely against the persisted `get_slot_signer` value, not the freshly-computed authorization set.

### Finding Description
The revocation/authorization decision lives in the smart contract and is read into an in-memory `StackerDBConfig` on each reload: [1](#0-0) 

When this read fails (transient Clarity read error, reorg, epoch mismatch, etc.) the code falls back to `StackerDBConfig::noop()`, whose `signers` field is always empty: [2](#0-1) 

The reconfigure decision is then: [3](#0-2) 

`(new_config != stackerdb_config && !new_config.signers.is_empty())` is false whenever `new_config.signers` is empty (the `noop()` case, or a legitimate reduction of the signer set to zero), and the second disjunct only fires when `new_config == stackerdb_config`, which is false immediately after such a fallback (an empty-signers `noop()` config generally differs from the previous non-empty config). As a result, `reconfigure_stackerdb` — the only code path that rewrites the persisted `signer` column for each slot — is never called, and the local `chunks` table keeps mapping slots to the *old*, now-revoked signer: [4](#0-3) 

Chunk-write authorization is validated purely against this persisted mapping via `get_slot_signer`, independent of the current, canonical on-chain authorization state: [5](#0-4) 

This breaks the equality that should hold between "authorized signer per current chain state" and "signer accepted for writes by the local replica." A validator/signer that the smart contract has disabled continues to be treated by any node that hits this fallback path as if it were still trusted, mirroring the `ValidatorService` issue where a disabled validator's delegations (and the associated write/lock privileges) are not revoked along with the enable/disable flag.

### Impact Explanation
Any node that experiences a transient config-reload failure (which is not attacker-controlled traffic volume, but ordinary operational conditions such as a burnchain reorg, momentary Clarity read failure, or a legitimate emptying of the signer set) will keep accepting and storing chunk writes signed by a signer key that the contract has since revoked. Because `StackerDBPushChunk` handling both stores the chunk locally and forwards it to the relayer / other peers for propagation, a revoked/disabled signer's key can be used to keep writing data that gets treated as authentic and gossiped network-wide, i.e. unauthorized write to StackerDB state and propagation of stale/forged authorization to peers. This matches the "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" impact classes.

### Likelihood Explanation
The `unwrap_or_else(... StackerDBConfig::noop())` fallback is reached on ordinary, non-adversarial failure conditions (any error from `StackerDBConfig::from_smart_contract`, e.g. transient read-only Clarity evaluation issues, reorgs, or epoch boundaries), so the vulnerable code path is exercised during normal node operation, not just a rare corner case. Any party who already possesses a StackerDB slot signing key and later gets disabled by the controlling contract can trivially attempt to keep writing; they need no special privilege beyond the key they already had before revocation.

### Recommendation
Decouple the "should we reconfigure" decision from whether the new signer list happens to be empty. When a legitimate new config is obtained (including the boot `.miners` case) and it differs from the stored config, revoke/reconfigure slots regardless of whether `new_config.signers` is empty, while distinguishing that case from load *failures*: on load failure, keep the previous config's slots as they are (do not silently fabricate a `noop()` config as `new_config` and store it as the new source of truth), so a persistent authoritative record isn't permanently displaced by a transient fallback, and so a genuine on-chain revocation (signers becomes empty) is actually applied via `reconfigure_stackerdb`/`shrink_stackerdb`.

### Proof of Concept
1. Node A subscribes to StackerDB contract `C` and signer `S` (private key `sk`) legitimately owns slot `N`.
2. The smart contract `C` is updated on-chain to disable/remove signer `S` (analogous to `ValidatorService.disableValidator`).
3. On Node A's next call to `create_or_reconfigure_stackerdbs`, suppose `StackerDBConfig::from_smart_contract` for `C` throws (e.g., because of a transient reorg or Clarity read error) — this is common and not attacker controlled — causing `new_config = StackerDBConfig::noop()` with `signers: vec![]`.
4. Because `new_config.signers.is_empty()`, the branch at `stackslib/src/net/stackerdb/mod.rs:414-428` is skipped; `reconfigure_stackerdb` is never invoked, so the `chunks` table for `C` still maps slot `N` to `S`.
5. The holder of `sk` (formerly `S`, now revoked on-chain) sends a `StackerDBPushChunk` for slot `N` signed with `sk`. `validate_received_chunk`/`get_slot_signer` still return `S` as the authorized signer, the chunk is accepted, stored, and forwarded for further gossip — despite `S` no longer being an authorized signer per the current contract state.

    /// Config that does nothing
    pub fn noop() -> StackerDBConfig {
        StackerDBConfig {
            // Cap the chunk size at the protocol-wide maximum rather than u64::MAX.
            // `noop()` is used as a fallback whenever a replica's real config can't be
            // loaded (see `create_or_reconfigure_stackerdbs`), and it can transiently
            // overwrite a good in-memory config on a failed refresh. Since the DB slots
            // persist independently of the config, writes can still land on existing
            // slots while `noop()` is active, so its chunk-size limit must never be
            // looser than `STACKERDB_MAX_CHUNK_SIZE`.
            chunk_size: STACKERDB_MAX_CHUNK_SIZE as u64,
            write_freq: 0,
            max_writes: u32::MAX,
            hint_replicas: vec![],
            max_neighbors: 8,
            signers: vec![],
        }
    }

    pub fn reconfigure_stackerdb(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slots: &[(StacksAddress, u32)],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let mut total_slots_read = 0u32;
        for (principal, slot_count) in slots.iter() {
            total_slots_read =
                total_slots_read
                    .checked_add(*slot_count)
                    .ok_or(net_error::OverflowError(
                        "Slot count exceeeds u32::MAX".to_string(),
                    ))?;
            let slots_before_principal = total_slots_read - slot_count;
            for cur_principal_slot in 0..*slot_count {
                let slot_id = slots_before_principal + cur_principal_slot;
                if let Some(existing_validation) =
                    self.get_slot_validation(smart_contract, slot_id)?
                {
                    // this slot already exists.
                    if existing_validation.signer == *principal {
                        // no change
                        continue;
                    }
                }

                debug!("Reset slot {} of {}", slot_id, smart_contract);

                // new slot, or existing slot with a different signer
                let qry = "INSERT OR REPLACE INTO chunks (stackerdb_id,signer,slot_id,version,write_time,data,data_hash,signature) VALUES (?1,?2,?3,?4,?5,?6,?7,?8)";
                let mut stmt = self.sql_tx.prepare(qry)?;
                let args = params![
                    stackerdb_id,
                    principal.to_string(),
                    slot_id,
                    NO_VERSION,
                    0,
                    vec![],
                    Sha512Trunc256Sum([0u8; 32]),
                    MessageSignature::empty(),
                ];

                stmt.execute(args)?;
            }
        }
        debug!("Shrink {} to {} slots", smart_contract, total_slots_read);
        self.shrink_stackerdb(stackerdb_id, total_slots_read)?;
        Ok(())
    }
