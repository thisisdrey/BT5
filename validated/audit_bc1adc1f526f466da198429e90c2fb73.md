### Title
Out-of-bounds read via unvalidated Zip64 extra-field attribute index in `CDH`/`LH` size accessors - ([File: src/tools/singlejar/zip_headers.h])

### Summary
### Finding Description
`CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, and `CDH::local_header_offset()` (and the analogous `LH` accessors) select which 64-bit slot to read from a parsed `Zip64ExtraField` based solely on whether the corresponding 32-bit field equals `0xFFFFFFFF` (`ziph::zfield_has_ext64`), computing an `attr_no` index that is then passed to `Zip64ExtraField::attr64(index)`: [1](#0-0) 

`attr64()` performs a raw indexed read (`le64toh(attr_[index])`) with no check that `index < attr_count()` for that specific extra field instance: [2](#0-1) 

`Zip64ExtraField::find()` (via `ExtraField::find`) only validates that the extra field's *declared* `size()` (`sizeof(ExtraField) + payload_size()`) fits inside the enclosing `extra_fields()` buffer — it never checks that `payload_size()` is large enough to contain the number of 64-bit attributes the caller is about to index into: [3](#0-2) 

This is the direct structural analog of the CVE: a value taken from attacker-controlled header data (here, the 32-bit size/offset "escape" markers `0xFFFFFFFF`, analogous to the unvalidated relocation-type field) is used to derive an index/offset into a data structure without validating that index against the structure's actual bounds, allowing a read past the end of the declared payload.

### Impact Explanation
`InputJar` (`src/tools/singlejar/input_jar.cc`) memory-maps and parses attacker-influenced JAR/ZIP files that are inputs to the `singlejar` merging tool — content that originates from build dependencies/artifacts, not from the trusted root-repo Starlark. A JAR crafted so that `compressed_file_size32`/`uncompressed_file_size32` (or their `LH` equivalents) are set to `0xFFFFFFFF` while the accompanying Zip64 extra field's declared `payload_size()` is smaller than required (e.g., 0 or 8 bytes instead of the 24 needed for three 8-byte attributes) causes `attr64(attr_no)` to read 8 bytes beyond the extra field's own payload. Because the containing memory-mapped file may end shortly after that extra field (e.g., it is the last entry's extra data in a small/truncated file), this read can go past the mapped region, causing a crash (SIGSEGV) or, if it stays within the mapping but outside the intended field, disclosure of adjacent heap/file bytes into computed sizes/offsets — matching the CVE's "crash or unintended memory contents" characterization (CWE-125, out-of-bounds read).

### Likelihood Explanation
An attacker only needs to supply/construct an untrusted `.jar`/`.zip` file that a build consumes via `singlejar` (e.g., as an `http_archive`/`http_jar` dependency or a build input). No checksum bypass is required to trigger this — a legitimately downloaded, integrity-verified but maliciously-crafted archive triggers it, since sha256/integrity checks validate byte content, not internal structural consistency of the Zip64 extra field. The bound check in `ExtraField::find` gives a false sense of validation but does not defend the specific `attr64(index)` accesses in `CDH`/`LH`, making this readily reachable whenever `singlejar` processes a hostile input jar.

### Recommendation
In `Zip64ExtraField`, expose and enforce `attr_count()` at every `attr64(index)` call site (or centrally inside `attr64()` itself) before dereferencing `attr_[index]`, and have `CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, `CDH::local_header_offset()`, and the `LH` equivalents treat a mismatch between the required `attr_no` and the field's actual `attr_count()` as a corrupt-archive error rather than performing the read.

### Proof of Concept
A `BuildIntegrationTestCase`/shell test analogous to the existing `src/test/shell/bazel/starlark_repository_test.sh` extraction tests (e.g. `test_extract_non_readable_file_zip`) could craft a ZIP whose central directory entry sets `compressed_file_size32`/`uncompressed_file_size32` to `0xFFFFFFFF` but attaches a Zip64 extra field with `payload_size() < 24` (e.g., only 8 bytes, one attribute), positioned at (or near) the end of the mapped file, then run it through `singlejar` (or a unit test directly instantiating `CDH` over a crafted byte buffer sized to end exactly at the truncated extra field) and observe an out-of-bounds/ASan-detected read when `local_header_offset()`/`compressed_file_size()` is invoked. I was not able to execute this PoC in this environment — it relies on the existing `zip_headers_test.cc` test harness patterns; unavailability of tool execution here means this is a proposed reproduction outline rather than a confirmed crash.                                 const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
