### Title
Fee-on-transfer NEP-141 tokens allow crediting internal balances for tokens never actually received - insolvency of the token ledger - ([File: contracts/defuse/src/contract/tokens/nep141/deposit.rs])

### Summary
`ft_on_transfer` in the Defuse contract credits a depositor's internal multi-token balance with the exact `amount` value reported by the token contract's `ft_transfer_call` payload, without ever checking how many tokens were actually received into Defuse's own NEP-141 balance for that token. For any NEP-141 token whose `ft_transfer`/`ft_transfer_call` implementation deducts a fee (or otherwise delivers less than the nominal `amount` while still invoking `ft_on_transfer(amount)` with the pre-fee amount), Defuse will mint internal balance/`total_supplies` that is not backed by an equal increase of its own token holdings.

### Finding Description
`ft_on_transfer` unconditionally trusts the `amount` parameter passed by the token contract and credits it to the receiver's balance: [1](#0-0) 

```rust
fn ft_on_transfer(&mut self, sender_id: AccountId, amount: U128, msg: String) -> PromiseOrValue<U128> {
    ...
    self.deposit(
        receiver_id.clone(),
        [(token_id.clone(), amount.0)],
        Some("deposit"),
    )
    .unwrap_or_else(|err| err.panic());
    ...
}
```

There is no comparison of Defuse's actual NEP-141 balance for `token` before and after the transfer — the code assumes `amount` == tokens actually received. `self.deposit` mints this amount both into the user's `token_balances` and into the global `total_supplies` ledger, which is the invariant later relied upon by withdrawals: [2](#0-1) 

For any token contract that applies a fee/burn during transfer (a "fee-on-transfer" NEP-141 implementation is not prohibited by the NEP-141 standard, and can be freely deployed on NEAR, unlike an audited allow-list), the sender's `ft_transfer_call` can report an `amount` to `ft_on_transfer` that is larger than what the receiving contract account's on-chain token balance actually increased by. Defuse has no allow-list or verification restricting deposits to fee-free tokens; `TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()))` accepts any caller as a valid token.

Because the `total_supplies`/`token_balances` ledger now records more tokens than Defuse's real custody balance for that `token`, the equality that must hold — `sum(token_balances for token) == token.balance_of(defuse_contract)` — is broken. Withdrawals via `ft_withdraw` (`internal_ft_withdraw` → `do_ft_withdraw`) will decrement the internal ledger and attempt `ft_transfer`/`ft_transfer_call` for the requested (inflated) amount, but the promise will fail once actual custody is exhausted, at which point later depositors of the same token are unable to withdraw their legitimately-owed balance — a Critical loss/freeze of funds for other users of the same token, caused entirely by an unprivileged, unauthorized depositor choosing to deposit a fee-on-transfer token.

The same unconditional-trust pattern exists for MT deposits and both `ft_resolve_deposit`/`resolve_deposit_internal` refund flows, none of which reconcile against Defuse's actual custodial balance.

### Impact Explanation
This breaks the fundamental custody/conservation binding of the vault: the internal accounting ledger (`total_supplies`/`token_balances`) no longer equals the tokens actually held by the Defuse contract for a given NEP-141 asset. Any unprivileged user can trigger this simply by depositing a fee-on-transfer token via `ft_transfer_call`, permanently reducing what the contract can pay out to other legitimate holders of the same `TokenId` — i.e., funds get permanently frozen/unavailable for some depositors, matching the "funds permanently frozen" / conservation-violation criteria for Critical-severity impact.

### Likelihood Explanation
Likelihood is moderate to high in practice: no code path verifies the sender token behaves per the (implicit) fee-free NEP-141 assumption, and any account can deploy or use an existing fee-on-transfer NEP-141 token and call `ft_transfer_call` into Defuse. No privileged role, RPC interception, or victim key is required — a single unprivileged attacker/depositor using a fee-on-transfer token is sufficient to desynchronize the ledger for that `TokenId`.

### Recommendation
Before crediting `amount` in `ft_on_transfer`/`mt_on_transfer` (and in the corresponding refund/resolve paths), compare Defuse's own `ft_balance_of`/holdings for `token` before and after the transfer (or otherwise measure the real amount received) rather than trusting the `amount` value supplied by the caller/token contract, and credit only the actually-received amount.

### Proof of Concept
1. Deploy (or use) a NEP-141 token `FEE_FT` whose `ft_transfer`/`ft_transfer_call` implementation deducts, e.g., 10% fee on every transfer, but still invokes `ft_on_transfer(sender_id, amount=<pre-fee amount>, msg)` on the receiver.
2. User A calls `FEE_FT::ft_transfer_call(defuse, amount=1000, msg="")`. Defuse's actual `FEE_FT` balance only increases by 900, but `ft_on_transfer` credits User A with 1000 in `token_balances`/`total_supplies` (see `contracts/defuse/src/contract/tokens/nep141/deposit.rs:38-43`).
3. User B similarly deposits and is credited legitimately for the (lesser) real amount they can be paid from custody.
4. User A calls `ft_withdraw` for 1000 `FEE_FT`. Defuse attempts to `ft_transfer` 1000 tokens it does not fully hold; once the real balance (900 from A + whatever B deposited) is insufficient for subsequent legitimate withdrawals, later users cannot withdraw their full legitimately-credited balance — resulting in stuck/frozen funds for other holders of the same `TokenId`.

```rust
    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        require!(amount.0 > 0, "zero amount");

        let token_id = TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()));

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {
            DepositMessage::new(sender_id.clone())
        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());
```
