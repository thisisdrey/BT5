### Title
Witness reward permanently stuck when a Super Representative has zero votes in a reward cycle, with no rescue mechanism - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService` accumulates per-cycle voter rewards for each witness in `payReward` via `delegationStore.addReward(cycle, witnessAddress, value)`, to later be distributed to voters proportional to their vote share for that witness in that cycle. If the recorded total vote count for that witness/cycle is zero, the stored reward amount can never be attributed to any voter and there is no function anywhere in the codebase to reclaim or redistribute it, mirroring the reported `Gauge`/`CLGauge`/`Bribes` issue where `notifyRewardAmount` deposits become permanently stuck when total supply is zero and no rescue exists.

### Finding Description
`MortgageService.payReward` splits each block/standby/transaction-fee reward into a brokerage portion (paid immediately as allowance to the witness) and a remainder that is stored per-cycle for later voter distribution: [1](#0-0) 

That remainder is looked up later in `computeReward(cycle, votes)` (old algorithm) which explicitly skips distribution whenever the stored total vote for that witness/cycle is zero: [2](#0-1) 

The new VI-based algorithm has the same behavior — `DelegationStore.accumulateWitnessVi` and `RewardViCalService.accumulateWitnessVi` skip accumulation into `witnessVi` (and thus into any user's future reward computation) whenever `voteCount == 0`, only forwarding the previous VI unchanged: [3](#0-2) [4](#0-3) 

The witness's per-cycle vote count used here is captured once per maintenance cycle in `MaintenanceManager.doMaintenance`: [5](#0-4) 

If a witness produces blocks (and thus earns block/transaction-fee rewards distributed via `payReward`) in a cycle during which its own recorded `voteCount` for that cycle is `0` (e.g., a brand-new SR that has not yet accumulated any votes, or one whose voters fully unvote in the same cycle it is still active/producing), the reward amount added via `delegationStore.addReward` for that (cycle, witness) pair is written to storage but can never be picked up by `computeReward`/`accumulateWitnessVi`, since both check `totalVote == 0` / `voteCount == 0` and simply skip. No caller in `MortgageService`, `DelegationStore`, or `RewardViCalService` ever revisits or reclaims that stored reward value — there is no equivalent of a "rescue" function that redirects or refunds it once it is known unattributable.

### Impact Explanation
The reward value is real TRX previously earmarked for voter payout and moved out of the immediately payable path (only the brokerage share is credited to the witness's `allowance`); the remainder is a promise recorded only as a database entry keyed by `(cycle, witness, "reward")`. Once total vote for that cycle is zero, that promised value is unbacked by any future claim path — it is permanently frozen/unclaimable by any account, matching the "permanent freezing of funds" impact criterion. This is a protocol-level accounting bug analogous to the `Gauge`/`Bribes` `notifyRewardAmount` issue: value is deposited into a per-period bucket that requires nonzero "total supply" (total vote) to ever be paid out, and no rescue exists.

### Likelihood Explanation
Low likelihood in practice, consistent with the original report's severity rating: it requires a witness to become part of the active/standby set and produce blocks (or receive standby pay) in a cycle where its own recorded vote count for that specific cycle is exactly zero — a narrow timing condition (e.g., a witness losing all votes at the exact boundary of a maintenance cycle while still temporarily active, or brand-new SR registration edge cases). This does not require any privileged actor; it can occur through normal, unprivileged vote/unvote transactions interacting with the deterministic maintenance-cycle scheduling.

### Recommendation
Add a mechanism in `MortgageService`/`DelegationStore` to detect per-cycle reward entries whose associated total vote is zero and redirect that value (e.g., roll it forward into the next cycle's brokerage pool, credit it back to the witness, or fold it into the standby-witness/block-reward pool) rather than leaving it as an orphaned, unreachable value in `delegationStore`.

### Proof of Concept
1. A witness `W` is newly added to the standby/active list with `voteCount == 0` for the current cycle (e.g., immediately after registration, before `MaintenanceManager.doMaintenance` has recorded any votes for it in `delegationStore.setWitnessVote`).
2. `W` produces a block (or otherwise earns fee reward) in this cycle; `MortgageService.payBlockReward` → `payReward` computes `brokerageAmount` (paid to `W`'s allowance) and calls `delegationStore.addReward(cycle, W, remainder)` for the non-brokerage remainder. [1](#0-0) 
3. Any voter who later delegates to `W` and calls `withdrawReward`/`queryReward` computes rewards via `computeReward(cycle, votes)`, which reads `delegationStore.getWitnessVote(cycle, W)` — recorded as `0` for that cycle — and explicitly `continue`s, never distributing the stored `remainder`. [2](#0-1) 
4. No API, actuator, or maintenance routine ever re-reads or redistributes this stored value; it remains permanently inaccessible to any account.

```java
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
```

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

```java
  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
```
