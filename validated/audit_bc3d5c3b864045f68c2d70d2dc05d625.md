### Title
Stale in-memory `AccountCapsule` overwrite causes lost maker-side settlement in `MarketSellAssetActuator` (self-trade fund loss) - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.execute()` keeps a single in-memory `AccountCapsule` for the taker throughout order creation and matching, and only persists it once at the very end of the method. However, whenever a resting maker order is matched, the settlement helpers `addTrxOrToken(MarketOrderCapsule, long)` and `returnSellTokenRemain(MarketOrderCapsule)` independently re-load the maker's account **from the store**, mutate it, and immediately `put()` it back. If the taker happens to match against their own resting order (self-trade — nothing in `validate()`/`matchOrder()` prevents this), the maker-side write is a stale snapshot that is missing all changes made earlier to the same account by the taker-side logic. The final `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` for the taker then unconditionally overwrites the store again with the taker's stale copy, silently discarding the maker-side credit that was just written. This is the same root-cause class as the Raydium AMM bug: a cached/stale copy of account state used for a later mutating operation causes a fund-settlement step to be lost.

If `makerOrderCapsule.getOwnerAddress()` equals the taker's own address (self-trade — a user can trivially place a taker order that matches their own earlier resting order at the same price, since no ownership check exists in `matchOrder`/`matchSingleOrder`/`validate()`), then `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` loads a second, independent `AccountCapsule` object for the same key, credits it with the buy-token proceeds, and persists it immediately. But this in-store update is subsequently clobbered when the taker-side object (`accountCapsule` from `execute()`, which never saw this credit) is written back at line 148, because both objects are separate in-memory copies of the same underlying key with no re-read/merge before the final write.

### Impact Explanation
The maker-side settlement (the buy-token amount the user is owed for filling their own resting order) is silently discarded, while the corresponding sell-token was already deducted/locked from the account when the resting order was originally created. This produces a permanent loss of user funds (an unbacked/incorrect balance) without any error or transaction failure — the transaction reports `SUCESS` while under-crediting the account. This matches the "permanent freezing/loss of funds" and "unbacked balance" impact classes.

### Likelihood Explanation
Reachable by any unprivileged account: place a `MarketSellAssetContract` order, then place a second `MarketSellAssetContract` order (or `MarketCancelOrder`-timed sequence) in the opposite direction at a matching price from the same account, causing the new taker order to match the account's own earlier resting maker order in `matchOrder`. No special permission, no reliance on validators/witnesses, and no obviously guarded check prevents self-matching in `MarketSellAssetActuator.validate()` or `matchOrder()`.

### Recommendation
Do not persist stale in-memory account copies. Either:
1. Route all account mutations (taker and maker) through a single per-address in-memory cache within `execute()`/`matchOrder()`/`matchSingleOrder()` that is flushed once at the end, ensuring the taker and maker credits for the same address are merged, or
2. Explicitly detect self-trades (`makerOrderCapsule.getOwnerAddress().equals(takerAccountCapsule.getAddress())`) and apply both legs to the same in-memory `AccountCapsule` object before any partial `accountStore.put()`s occur, or
3. Re-read the account immediately before the final `accountStore.put()` in `execute()` and merge/rebase any changes rather than blindly overwriting.

### Proof of Concept
1. Account `A` places a sell order: sell 100 TokenX for 200 TokenY (`MarketSellAssetActuator`, resting on the book since no matching counter-order exists).
2. Account `A` places a second order that crosses the book at a matching price: sell 200 TokenY for 100 TokenX.
3. In `execute()` for the second transaction, `accountCapsule` for `A` is loaded once (line 114-115), fee/sell-token deducted in memory.
4. `matchOrder` → `matchSingleOrder` matches against `A`'s own resting order from step 1; `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` (lines 550-562) reloads `A`'s account fresh from the store (missing the in-memory deduction/credits from step 3), credits it with TokenX proceeds, and writes it back immediately.
5. At the end of `execute()`, line 148 `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` overwrites the store with the taker-side in-memory copy of `A`, which does not include the TokenX credit added in step 4 — that credit is lost even though `A`'s TokenY was already spent to fund the maker order in step 1.
