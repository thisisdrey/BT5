Audit Report

## Title
`ERC20Transactor` withdraw/deposit performs unconditional ERC20 `transfer` without a zero-amount guard, letting a zero-value-revert token abort XCM asset transfers - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` build and dispatch an `IERC20::transferCall { value: EU256::from(amount) }` for whatever `amount` `Matcher::matches_fungibles` resolves, with no `amount > 0` check before the external call. [1](#0-0) [2](#0-1)  This is confirmed to be reachable from the XCM executor's `WithdrawAsset` handling, which iterates every asset item in the instruction and calls `Config::AssetTransactor::withdraw_asset_with_surplus(asset, ...)` unconditionally, with no zero-amount filtering anywhere in that path. [3](#0-2) 

## Finding Description
Both entry points obtain `amount` directly from `Matcher::matches_fungibles(what)` on the XCM `Asset { fun: Fungible(amount), .. }` and pass it straight into `IERC20::transferCall` with no zero check, unlike the Snowbridge v1/v2 XCM converters, which explicitly `ensure!(amount > 0, ZeroAssetTransfer)` before constructing native-token unlock commands. [4](#0-3)  The Snowbridge test suite explicitly documents and tests this guard for a `Fungible(0)` asset, confirming it is a recognized, defended-against case elsewhere in the same repository. [5](#0-4) 

The xcm-executor's `WithdrawAsset` instruction processing loops over `assets.inner()` and calls the configured `AssetTransactor::withdraw_asset_with_surplus` for each item with no amount validation, so a `Fungible(0)` asset item passed in a legitimate/crafted XCM program reaches `ERC20Transactor` unmodified. [6](#0-5)  `ERC20Transactor` is wired into Asset Hub Westend's XCM configuration as a live `TransactAsset`. [7](#0-6) 

Contrast this with the other in-repo fungible/fungibles adapters (`fungible_adapter.rs`, `fungibles_adapter.rs`), which also don't explicitly zero-check, but delegate to `Fungible::withdraw`/`Assets::withdraw` — frame's balances/assets pallets treat a zero-amount withdraw as an inexpensive no-op internally rather than dispatching an external, attacker-controlled contract call that can arbitrarily revert. [8](#0-7)  `ERC20Transactor` is qualitatively different because the "asset implementation" is an arbitrary, permissionlessly-deployable `pallet-revive` contract fully controlled by whoever registers the asset, so a contract that reverts on `transfer(_, 0)` will cause `did_revert() == true`, and the transactor returns `Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))`, aborting the surrounding XCM instruction. [9](#0-8) 

## Impact Explanation
A failing `withdraw_asset`/`deposit_asset` step for a zero-amount leg aborts the enclosing XCM instruction (`WithdrawAsset`'s per-asset loop returns early on the first error, and the whole instruction is processed inside `Config::TransactionalProcessor::process`, which rolls back holding/fees on error). [10](#0-9)  If other real-value assets are batched in the same `WithdrawAsset`/`DepositAsset` instruction alongside a zero-amount ERC20-PNA leg, or if the transactional rollback semantics don't fully protect against partial state depending on instruction structure, this can cause an otherwise-valid multi-asset XCM message to fail purely due to attacker-controlled zero-transfer-revert behavior of one registered token. This aligns with the "public underpriced work that degrades block production or stalls bridge processing" / message-processing-integrity impact class, since it lets an unprivileged party render specific legitimate XCM programs involving a given PNA-ERC20 non-executable without any privileged capability.

## Likelihood Explanation
Likelihood is moderate: it requires (1) a registered ERC20-backed asset (deployable permissionlessly via `pallet-revive`) whose `transfer` implementation reverts on `value == 0`, fully attacker-controlled, and (2) an XCM program presenting a `Fungible(0)` item for that asset id to `ERC20Transactor`, which is confirmed reachable unfiltered through the executor's `WithdrawAsset` handling. [6](#0-5)  No governance, validator, or relayer privilege is needed. Whether a *practical, unprivileged* XCM program naturally produces a `Fungible(0)` item for a specific ERC20 asset (versus being trivially filtered by asset registration, `Matcher`, or upstream fee-computation logic before reaching the transactor) was not fully traced in this session, but the direct case — crafting an XCM message containing an explicit `Asset { id: <erc20_asset>, fun: Fungible(0) }` in a `WithdrawAsset`/`InitiateTransfer` instruction sent by an unprivileged origin — is not rejected anywhere in the executor or transactor before the external contract call.

## Recommendation
Add an explicit `amount == 0` guard at the top of both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`, mirroring the `ensure!(amount > 0, ZeroAssetTransfer)` pattern in the Snowbridge converters, and either short-circuit to a trivial success (treating a zero-value transfer as a no-op, consistent with frame's fungible/fungibles trait semantics) or return a deterministic `XcmError` before making the external `bare_call`, so behavior does not depend on an arbitrary, attacker-controlled ERC20 contract's implementation quirks.

## Proof of Concept
1. Deploy via `pallet-revive` an ERC20 contract whose `transfer` reverts when `value == 0` (trivial modification of the standard template).
2. Register this contract as an XCM-fungible asset id recognized by the `Matcher` configured for `ERC20Transactor` on Asset Hub Westend (`cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`).
3. Send an unprivileged XCM message containing a `WithdrawAsset` (or `InitiateTransfer`/`DepositAsset`) instruction with an asset item `Asset { id: <erc20_asset>, fun: Fungible(0) }`, optionally batched with a real-value asset.
4. Observe the xcm-executor's `WithdrawAsset` loop calling `ERC20Transactor::withdraw_asset_with_surplus` with `amount = 0` [11](#0-10) , the underlying `IERC20::transferCall { value: 0 }` reverting, `did_revert()` returning true, and the transactor returning `Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))`, aborting the instruction. [12](#0-11)
