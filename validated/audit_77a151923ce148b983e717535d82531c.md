### Title
Out-of-bounds read in `InputZipFile::ProcessCentralDirEntry`'s extra-field parsing loop via attacker-crafted ZIP central directory - (File: `third_party/ijar/zip.cc`)

### Summary
`third_party/ijar/zip.cc` (`ijar`, used by Bazel to build interface jars / process jar-like archives that can originate from `.jar` files downloaded via `http_archive`/`http_jar`/`http_file`/Maven-style dependencies) parses the ZIP central directory without validating the `extra_field_length` sub-record sizes against the bounds of the extra-field block or the mapped file.

### Finding Description
`FindZipCentralDirectory` validates that `central_dir_offset + central_dir_size <= in_length` [1](#0-0) , and `InputZipFile::ProcessLocalFileEntry` guards its reads with `EnsureRemaining()` [2](#0-1) . However, `InputZipFile::ProcessCentralDirEntry`, which walks each central-directory header, reads `file_name_length`, `extra_field_length`, `file_comment_length` directly from attacker-controlled bytes and then iterates the extra-field block with **no bound checking against `extra_field_length` for each sub-record's declared `data_size`**: [3](#0-2) 

Specifically:
```
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
```
If a malicious archive declares a sub-record `data_size` that does not evenly divide the remaining `extra_field_length` (e.g. `data_size` larger than the remaining bytes in the extra-field block, or non-zero remainder), `extra_p` can jump past `p` (the end of the extra-field block) and the `while (extra_p != p)` loop condition never becomes true again, causing the loop to keep calling `get_u2le(extra_p)`/`get_u4le`/`get_u8le` on `extra_p` far beyond the intended extra-field region — reading past the parsed file name/comment, past the end of the current central-directory record, and potentially past the mapped file buffer entirely (heap/mmap out-of-bounds read), since there is no check that `extra_p` stays `<= p` or within `input_file_->Length()`. This mirrors the CVE-2025-3407 bug class: a size/count field taken directly from untrusted content is used to index/advance into a buffer without validating it against the actual buffer bounds (`h_count`/`v_count` in `stbhw_build_tileset_from_image` ≈ `data_size` in `ProcessCentralDirEntry`'s extra-field loop).

Unlike `EnsureRemaining()`-guarded paths (`ProcessLocalFileEntry`, `SkipFile`), the central-directory extra-field walk has no equivalent bound check, and the earlier `central_dir_offset + central_dir_size <= in_length` check only bounds the *overall* central directory region, not the internal consistency of each entry's `extra_field_length` versus its actual sub-record sizes.

### Impact Explanation
An attacker who controls the content served at a URL consumed by `http_archive`/`http_jar`/`http_file` (or any hostile registry/mirror serving a jar that a Bazel build unpacks/processes with `ijar`) can craft a ZIP central directory with a corrupted extra-field `data_size` to cause `ijar`/the build tooling to read out of bounds of the mapped input file, potentially crashing the build process (SIGSEGV on unmapped pages) or leaking adjacent process memory. This satisfies "read outside the repository / exec root" in spirit as an OOB read of the file mapping used during archive processing, though the leaked memory is limited to the local process's own address space contents.

### Likelihood Explanation
Moderate: `ijar`'s ZIP central-directory extra-field parser is reached whenever Bazel needs to build an interface jar for a downloaded/pre-built `.jar` (a routine and common part of Java rules), so the code path is easily reachable from build-time artifacts sourced from remote/untrusted origins (dependency archives). Exploitation requires only crafting a ZIP archive with an inconsistent `extra_field_length`/`data_size`, which is straightforward and does not require access to the victim's machine or any privileged position (a hostile origin server or mirror serving the artifact is sufficient), and there is no checksum on individual bytes of extra fields (checksums like `sha256`/`integrity` cover the whole archive file, not the extra-field internal parsing logic, so a mismatch would only be caught if the whole file hash differs from what's pinned — an attacker with no pinned hash, or targeting an initial/unpinned fetch, can still trigger this).

### Recommendation
In `InputZipFile::ProcessCentralDirEntry`, bound the extra-field walk explicitly: track remaining bytes in the extra-field block and verify `data_size <= remaining` before advancing `extra_p`, and change the loop condition from `extra_p != p` to `extra_p < p` (or equivalent) combined with a break on any `data_size` that would overrun `p`. Additionally, validate that `file_name_length + extra_field_length + file_comment_length` does not overrun the bounds of the mapped file/central directory before dereferencing.

### Proof of Concept
A reproducible test would follow the pattern of `src/test/shell/bazel/external_integration_test.sh`'s `test_prefix_stripping_zip`-style tests, but instead constructing a hand-crafted ZIP whose central directory entry sets `extra_field_length` to a small value (e.g., 4) while an embedded fake extra-field sub-record declares `data_size` larger than that (e.g., 0xFFFF), then invoking `ijar` (or a `java_import`/`http_jar`-driven build) on this file and observing a crash/OOB read (e.g., via `third_party/ijar/zip_test.cc` fixtures or a new `IjarZipTest` case using `ZipExtractor::Create` on the crafted file and asserting a bounded/graceful error rather than a crash). I was not able to execute or fully trace `zip_test.cc`/`ijar_test` harnesses within the indexed context to confirm a ready-made JUnit/shell integration point exists — this would need to be authored as part of remediation.
