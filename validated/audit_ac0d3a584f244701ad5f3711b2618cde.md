### Title
StackerDB chunk signatures omit the contract identifier, enabling cross-contract signature replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest for a StackerDB chunk from only `slot_id`, `slot_version`, and `data_hash` — it never binds the signature to the specific StackerDB smart-contract (replica) the chunk belongs to. Because the Nakamoto signer-message StackerDB replicas (`signers-<cycle>-1`, `signers-<cycle>-2`, `signers-<cycle>-3`) all derive their slot→signer assignment from the *same* underlying signer list for a given reward cycle, the same signer address occupies the *same* `slot_id` in every one of these sibling contracts. A signature that authenticates a chunk for one contract therefore also authenticates the identical `(slot_id, slot_version, data)` tuple in a sibling contract, allowing any remote/unprivileged peer to replay a validly-signed chunk observed in one StackerDB replica into another.

### Finding Description
The signed digest is:
```rust
fn auth_digest(&self) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
``` [1](#0-0) 

Note the absence of the `QualifiedContractIdentifier` (the StackerDB smart contract) from the digest. `verify()` only checks that the recovered pubkey hash matches the expected `principal`: [2](#0-1) 

On the storage/write path, `StackerDBTx::try_replace_chunk` accepts a chunk purely based on: (1) size, (2) the recorded per-slot signer for *that* contract, (3) `slot_desc.verify(&slot_validation.signer)`, (4) monotonic version, (5) max-writes — none of which reference the contract identifier that was actually signed over: [3](#0-2) 

The same pattern is repeated for gossip-received/pushed chunks in `PeerNetwork::validate_received_chunk`, which resolves the expected signer strictly from the target `smart_contract_id`'s own slot table and then calls `slot_metadata.verify(&addr)`: [4](#0-3) 

The three sibling signer-message contracts for a given reward cycle/signer-set (`signers-<cycle>-1/2/3`) all resolve their slot assignment through the *same* page lookup in the `.signers` boot contract:
```clarity
(define-read-only (stackerdb-get-signer-slots)
    (contract-call? .signers stackerdb-get-signer-slots-page u1))
``` [5](#0-4) 
and the underlying page (`stackerdb-signer-slots-0`/`-1`) is set once per reward-cycle set and shared by every message-id contract of that set: [6](#0-5) 

Consequently, signer `S` occupies identical `slot_id` in `signers-X-1` (BlockResponse), `signers-X-2` (StateMachineUpdate), and `signers-X-3` (BlockPreCommit). A `StackerDBChunkData{slot_id, slot_version, sig, data}` legitimately posted/broadcast for `signers-X-1` is byte-for-byte valid — signature, slot id, version, and data-hash all still check out — when replayed against the corresponding slot in `signers-X-2` or `signers-X-3`, as long as that sibling contract's own version counter for the slot is still behind the replayed version. Nothing in `try_replace_chunk`, `insert_chunk`, or `validate_received_chunk` re-derives or checks which contract the signature was actually produced for.

This breaks the intended equality "signed-for-contract-A chunk == authorized only for contract A." The digest conflates identical `(slot_id, slot_version, data)` tuples across different StackerDB replicas that happen to share a signer-to-slot mapping, so authentication for contract A is silently accepted as authentication for contract B.

### Impact Explanation
An unprivileged remote peer that merely observes a legitimately-signed, publicly gossiped chunk (chunk contents and signatures are not secret — they are broadcast over the p2p StackerDB sync/push protocol and served over HTTP `/v2/stackerdb/...`) can:
1. Take that chunk (unmodified: same `slot_id`, `slot_version`, `sig`, `data`).
2. Submit it (via HTTP POST `.../chunks` or via `StackerDBPushChunk` p2p message) against a *different* signer-message-lane StackerDB contract for the same reward cycle/signer set.
3. Have the node accept and store it as a legitimately signed chunk for that other contract, because `try_replace_chunk`'s signature check never verifies contract identity.
4. Have the node re-broadcast the (forged-for-this-contract) chunk to the network via `Relayer::process_stacker_db_chunks`, since successful storage triggers `broadcast_message`: [7](#0-6) 

This is an unauthenticated write into a StackerDB replica the signer never authorized data for, plus network-wide re-propagation of that forged-context data — matching the "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" impact categories. It also lets an attacker consume/advance a signer's per-slot version counter and `max_writes` budget in the wrong lane purely by replaying public data, degrading that signer's ability to publish legitimate updates in that lane (griefing/DoS on a specific slot).

### Likelihood Explanation
High likelihood of triggerability: exploitation requires no privileged access, no node secret, and no cooperation from the signer whose key is being replayed — only observation of one publicly-broadcast, validly-signed StackerDB chunk and a single unauthenticated HTTP POST or p2p `StackerDBPushChunk` message to a sibling contract. The three signer-message-lane contracts sharing identical slot assignment are a permanent, deterministic feature of the `.signers` boot-contract design (not a rare coincidence), so the precondition (same signer occupying same slot id in ≥2 contracts) holds for essentially every signer, every reward cycle.

### Recommendation
Bind the StackerDB contract identity into the signed digest so a chunk's signature cannot be replayed across StackerDB replicas:
- Add the `QualifiedContractIdentifier` (or a chain/consensus-scoped domain separator that includes it) into `SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs`, and update `sign`/`verify`/`recover_pk` call sites accordingly (`libstackerdb/src/libstackerdb.rs`, `stackslib/src/net/stackerdb/db.rs`, `stackslib/src/net/stackerdb/mod.rs`, `stackslib/src/net/stackerdb/sync.rs`).
- This is a wire/consensus-relevant change to the signed payload, so it needs a version bump / migration plan for existing deployed signers.

### Proof of Concept
1. Observe (via p2p gossip or `GET /v2/stackerdb/<addr>.signers-5-1/chunks/<slot_id>/<version>`) a validly signed `StackerDBChunkData{slot_id: 3, slot_version: 7, sig, data}` written by signer `S` into `signers-5-1` (BlockResponse lane) for reward cycle 5.
2. Confirm (via `.signers` boot contract read-only calls, which are public) that signer `S` also occupies `slot_id: 3` in `signers-5-2` (StateMachineUpdate lane) for the same reward cycle, per the shared `stackerdb-get-signer-slots-page` lookup.
3. POST the identical `slot_id`, `slot_version`, `sig`, and `data` bytes to `.../signers-5-2/chunks` (or send it as a `StackerDBPushChunk` p2p message targeting `signers-5-2`), assuming the target slot's current version in `signers-5-2` is `< 7`.
4. Observe the node accept and store the chunk (`try_replace_chunk` returns `Ok`) and re-broadcast it via `process_stacker_db_chunks`, even though `S` never signed anything intended for `signers-5-2`.

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
