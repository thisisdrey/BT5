### Title
Concurrency limiter for `git-pack-objects` can be bypassed by spoofing `RemoteIp` as loopback/unparseable, enabling unlimited-cost pack generation - (File: internal/gitaly/service/hook/pack_objects.go)

### Summary
`PackObjectsHookWithSidechannel` decides whether to run `git-pack-objects` through the `packObjectsLimiter` (which bounds concurrency/cost) or to run it completely unthrottled, based solely on whether the client-supplied `remote_ip` field parses to a non-loopback IP address. A caller who controls this field can force the "no limiter" branch on every call, exactly mirroring the reported analog: a cost-gating parameter can be set to a value (loopback/empty/unparseable) that makes the expensive, resource-consuming operation still execute while completely skipping the mechanism meant to bound its cost.

### Finding Description
In `packObjectsHook`, the branch selecting the limited vs. unlimited code path is: [1](#0-0) 

```
servedBytes, created, err := s.packObjectsCache.Fetch(ctx, cacheKey, output, func(w io.Writer) error {
    ipAddr := net.ParseIP(req.GetRemoteIp())
    ...
    // Ignore loop-back IPs
    if ipAddr != nil && !ipAddr.IsLoopback() {
        return s.runPackObjectsLimited(ctx, w, ipAddr.String(), req, args, stdin, cacheKey)
    }
    return s.runPackObjects(ctx, w, req, args, stdin, cacheKey)
})
```

Only `runPackObjectsLimited` funnels the request through `s.packObjectsLimiter.Limit(...)`, the per-key concurrency limiter documented as protecting Gitaly from overload by concurrent `git-pack-objects` invocations: [2](#0-1) 

If `req.RemoteIp` is empty, malformed, or explicitly set to a loopback address (`"127.0.0.1"`, `"::1"`), `net.ParseIP` either returns `nil` or a loopback address, and the code falls straight into the unlimited `runPackObjects` path, which unconditionally spawns a `git-pack-objects` subprocess: [3](#0-2) 

The request field itself is fully attacker-controlled: `PackObjectsHookWithSidechannelRequest.remote_ip` is a plain string field with no server-side validation tying it to the actual peer address of the connection: [4](#0-3) 

`TestServer_PackObjectsHookWithSidechannel_invalidArgument` confirms the RPC only validates the repository, sidechannel address, and `pack-objects` argument shape — it never validates or checks `remote_ip` against the real connection peer: [5](#0-4) 

This is the same bug class as the report: a field that gates an expensive/limited resource (VRF request vs. `git-pack-objects` concurrency slot) can be set to a value (zero `craftAmount` vs. loopback/empty `remote_ip`) that lets validation/limiting be skipped while the costly operation still runs.

### Impact Explanation
`git-pack-objects` is CPU- and memory-intensive; the concurrency limiter and its associated queueing (`PackObjectsLimiting.MaxConcurrency`/`MaxQueueSize`) exist specifically to bound how many of these processes can run in parallel, per the load-management design docs: [6](#0-5) 

An attacker who can invoke `PackObjectsHookWithSidechannel` with a spoofed `remote_ip` can issue arbitrarily many concurrent, unthrottled `git-pack-objects` invocations against any repository they can fetch, exhausting CPU/memory on the Gitaly node and causing a denial of service for all repositories/tenants served by that node — the resource-exhaustion analog of "draining a rate/cost-limited resource for free."

### Likelihood Explanation
The `remote_ip` field is a normal request field with no cryptographic binding to the actual TCP peer, and no additional authorization is required beyond whatever credentials let a client call `HookService.PackObjectsHookWithSidechannel` (the same credentials used for ordinary fetch/clone operations that legitimately trigger this hook). Setting it to `""` or `"127.0.0.1"` requires no special privilege, and the branching logic is a single, easily reachable `if` condition in the hot path of every fetch.

### Recommendation
Do not derive the limiter bypass decision from a client-supplied field. Options:
- Use the actual gRPC peer address (from `peer.FromContext`) or a value stamped by Gitaly itself when constructing the internal `HooksPayload`, rather than trusting `req.RemoteIp` verbatim.
- If loop-back exemption is still desired (e.g., for the case of Gitaly-hooks running on localhost), always route through the limiter and only vary the limiting key, rather than skipping the limiter entirely.
- At minimum, always subject every call to `s.packObjectsLimiter` (e.g., always call `runPackObjectsLimited` with a fallback key such as `"unknown"`) so no request can ever run outside the concurrency bound.

### Proof of Concept
1. As a client with valid Gitaly credentials capable of invoking `HookService` RPCs (the same trust level as one that can trigger `git fetch`/`git clone`), send repeated `PackObjectsHookWithSidechannel` requests directly, each with:
   - `Repository`: any accessible repository,
   - `Args`: `["pack-objects", "--revs", "--thin", "--stdout"]` (valid pack-objects invocation),
   - `RemoteIp`: `""` or `"127.0.0.1"`.
2. Each request causes `ipAddr` to be `nil` or loopback, so `packObjectsHook` calls `s.runPackObjects` directly, bypassing `s.packObjectsLimiter` entirely.
3. Fire many such requests concurrently (varying `stdin`/args slightly to avoid the `packObjectsCache` hit path in `computeCacheKey`, which caches by `Repository+Args+GitProtocol+stdin`) to spawn unlimited concurrent `git-pack-objects` subprocesses, unconstrained by `PackObjectsLimiting.MaxConcurrency`/`MaxQueueSize`, exhausting node resources.

*Note:* Full confirmation of exactly which client roles are permitted to call `HookService.PackObjectsHookWithSidechannel` directly (versus only via the internal `gitaly-hooks` binary) was not verified in the available index; this should be checked against the service's authorization/interceptor configuration before treating this as fully externally reachable by an ordinary fetch client.

func (s *server) runPackObjectsLimited(
	ctx context.Context,
	w io.Writer,
	limitkey string,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.ReadCloser,
	key string,
) error {
	ctx = context.WithoutCancel(ctx)

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	defer stdin.Close()

	if _, err := s.packObjectsLimiter.Limit(
		ctx,
		limitkey,
		func() (interface{}, error) {
			return nil,
				s.runPackObjectsFn(
					ctx,
					s.gitCmdFactory,
					w,
					req,
					args,
					stdin,
					key,
				)
		},
	); err != nil {
		return err
	}

	return nil
}

func runPackObjects(
	ctx context.Context,
	gitCmdFactory gitcmd.CommandFactory,
	w io.Writer,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.Reader,
	key string,
) error {
	repo := req.GetRepository()

	counter := &helper.CountingWriter{W: w}
	sw := pktline.NewSidebandWriter(counter)
	stdout := bufio.NewWriterSize(sw.Writer(stream.BandStdout), pktline.MaxSidebandData)
	stderrBuf := &bytes.Buffer{}
	stderr := io.MultiWriter(sw.Writer(stream.BandStderr), stderrBuf)

	defer func() {
		packObjectsGeneratedBytes.Add(float64(counter.N))
		customFields := log.CustomFieldsFromContext(ctx)
		if customFields != nil {
			customFields.RecordMetadata("pack_objects_cache.key", key)
			customFields.RecordSum("pack_objects_cache.generated_bytes", int(counter.N))
			if total := totalMessage(stderrBuf.Bytes()); total != "" {
				customFields.RecordMetadata("pack_objects.compression_statistics", total)
			}
		}
	}()

	cmd, err := gitCmdFactory.New(ctx, repo, args.subcmd(),
		gitcmd.WithStdin(stdin),
		gitcmd.WithStdout(stdout),
		gitcmd.WithStderr(stderr),
		gitcmd.WithGlobalOption(args.globals()...),
	)
	if err != nil {
		return err
	}
	if err := cmd.Wait(); err != nil {
		return fmt.Errorf("git-pack-objects: stderr: %q err: %w", stderrBuf.String(), err)
	}
	if err := stdout.Flush(); err != nil {
		return fmt.Errorf("flush stdout: %w", err)
	}
	return nil
}

```markdown
### Cost-Aware Admission

A separate admission layer that sits before the concurrency limiter in the
gRPC interceptor chain. If a request can be served from
[`streamcache`](../internal/streamcache/cache.go), it bypasses the concurrency
limiter entirely and proceeds directly to the handler. Currently this applies
to:

- [`PostUploadPackWithSidechannel`](../internal/gitaly/service/smarthttp/upload_pack.go) (clone/fetch)

```plaintext
Request -> Cost-Aware Admission -> Concurrency Limiter -> Handler
                 |
           (cache hit?)
                 |
           bypass limiter -> Handler directly
```

The concurrency limiter today treats every request as equally expensive. In
practice, requests served from cache consume minimal resources (disk streaming)
while cache misses run full Git subprocess pipelines. Rather than feeding the
limiter a cost hint (which still consumes a limiter slot), cache-hit requests
skip the limiter entirely — keeping the concurrency limiter pure and ensuring
limits designed for expensive operations do not penalize cheap ones.

This separation also keeps the concurrency limiter's responsibility narrow: every
request that reaches it is treated as expensive.
```
