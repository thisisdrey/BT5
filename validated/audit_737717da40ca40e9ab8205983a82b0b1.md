### Title
Burned Accumulation-Account Funds Are Permanently Unrecoverable on Destination-Side Teleport Rejection - (File: `polkadot/xcm/xcm-builder/src/forwarder.rs`)

### Summary
`TeleportForwarderForAccountId32::forward` (used by `pallet_accumulate_and_forward` to periodically forward collected fees, dust, and coretime revenue) burns tokens locally and teleports them to a destination staging account. The local burn is only rolled back if the **local** XCM executor errors; once `prepare_and_execute` reports `Outcome::Complete`, the burn is final, but delivery/execution success at the destination is not verified end-to-end. If the destination-side `DepositAsset` to the staging account fails (e.g., staging account not funded to ED, filtered, or the destination pallet misconfigured), the teleported assets become trapped on the destination chain with no automatic recovery path — this is functionally identical to the reported "escrowed funds with no recovery mechanism when the remote pathway fails" bug class, except here the funds are actually burned (destroying supply) rather than merely escrowed.

### Finding Description
`forward()` builds an XCM program: `WithdrawAsset` → `InitiateTransfer{Teleport}`, wrapped in `with_transaction`, and only rolls back on **local** execution failure [1](#0-0) . The doc comment on the adapter itself acknowledges the gap: "Once the local executor reports success, the message is queued and any destination-side rejection results in trapped assets at the destination with no automatic recovery path." [2](#0-1) 

The remote program sent to the destination is `ReceiveTeleportedAsset` → `AliasOrigin(source)` → `UnpaidExecution` → `DepositAsset { beneficiary: StagingLocation }`, with no `SetAssetClaimer` set for the pallet's own recovery, unlike the pattern used elsewhere in the codebase (e.g., the Snowbridge v2 message exporter, which explicitly parses `SetAssetClaimer` to allow claiming trapped assets on failure) [3](#0-2) . Compare this to the report's `SetAssetClaimer` recommendation flagged in `bridges/snowbridge/docs/v2.md`, which the Snowbridge exporter design explicitly implements to let originators reclaim trapped funds on error — a safeguard absent here.

`pallet_accumulate_and_forward::Pallet::on_idle` treats `Forwarder::forward` as binary success/failure: on `Ok(())` it fires `ForwardSucceeded` and considers the funds gone (they were already burned inside `forward`); it has no mechanism to detect or react to destination-side rejection since that happens asynchronously, after the block in which `on_idle` ran [4](#0-3) . The pallet's own doc explicitly states "Accumulated funds are burnt upon forwarding... and the same funds are minted at the destination when the sent message is received" [5](#0-4)  — an invariant that silently breaks if the destination-side deposit fails after the burn is committed.

The existing test suite only verifies the local-failure rollback path (router failure before delivery), not the destination-rejection path [6](#0-5) , confirming the destination-failure scenario is untested and unguarded.

### Impact Explanation
When the destination-side `DepositAsset` to the `StagingLocation` fails (staging account not pre-funded to ED, temporary filter misconfiguration, or `pallet_dap`/receiving pallet issue), the teleported value is:
1. Already burned/destroyed on the source chain (total issuance permanently reduced there), and
2. Trapped in the destination's `AssetTrap` with no `SetAssetClaimer` wired for automatic recovery by the source pallet.

This is a permanent, protocol-level fund loss (accumulated transaction fees, dust, and coretime revenue meant to fund treasury/DAP), matching the "permanent user-fund or bridge-state lock" and "theft or unbacked mint or unlock" (inverse: unbacked burn) categories in the impact gate. Unlike the original report's admin-recoverable escrow, here recovery would require governance action to manually claim trapped assets at destination and re-mint at source — the pallet provides no such mechanism at all.

### Likelihood Explanation
The `on_idle` hook runs automatically and unconditionally once `TransferPeriod` and `MinTransferAmount` thresholds are met, with no dependency on a malicious actor — a temporary misconfiguration of the destination `StagingLocation`, insufficient ED funding of the staging account, or a transient failure in the destination message queue is sufficient to trigger permanent loss on that forward cycle. Because forwarding happens periodically and automatically (not user-triggered), this can recur every `TransferPeriod` until detected, silently draining protocol funds with only a `ForwardSucceeded` event (misleadingly indicating success) even though the funds never landed.

### Recommendation
- Wire a `SetAssetClaimer` (or equivalent claim-back mechanism) into the remote XCM program so that failed `DepositAsset` at destination traps assets claimable by the source's sovereign/pallet account.
- Add an XCM query/callback (similar to `pallet_xcm`'s `Querier`/`ReportError` mechanism used elsewhere in the codebase) so `pallet_accumulate_and_forward` can detect destination-side execution failure and either retry, re-mint locally, or surface an alert instead of firing a `ForwardSucceeded` event based solely on local delivery.
- At minimum, pre-verify (or governance-fund) the destination staging account's ED before enabling this pathway, and add integration tests exercising destination-side rejection (not just local router failure) to confirm behavior under that condition.

### Proof of Concept
1. Configure `pallet_accumulate_and_forward` with `TeleportForwarderForAccountId32` targeting a destination chain whose `StagingLocation` account is not funded to the existential deposit (or whose message-queue/pallet processing the incoming XCM is temporarily paused/filtered).
2. Accumulate fees/dust above `MinTransferAmount` in the accumulation account.
3. Let `on_idle` fire at a `TransferPeriod` multiple; `forward()` executes locally to `Outcome::Complete` (burn committed, `ForwardSucceeded` emitted) because local XCM execution only validates sending, not destination execution.
4. On the destination, the incoming `ReceiveTeleportedAsset`/`DepositAsset` program fails (e.g., `NotHoldingFees`/ED violation) and assets are trapped with no claimer set — funds are unrecoverable through any pallet-provided path, only through manual chain-level intervention (governance), and total issuance at the source has already been permanently reduced without a corresponding mint at the destination.

/// Verify that when the XCM router fails (simulating a mid-program failure after `WithdrawAsset`
/// has debited the source account), `forward` rolls back all storage changes via
/// `with_transaction`. Both the source balance and total issuance must remain unchanged.
#[test]
fn forward_rolls_back_balance_and_issuance_on_xcm_failure() {
	let source: AccountId = AccountId32::from([1u8; 32]);
	let initial_balance = 1_000u128;

	new_test_ext(source.clone(), initial_balance).execute_with(|| {
		let initial_issuance = Balances::total_issuance();

		ROUTER_SHOULD_FAIL.with(|f| f.set(true));
		let result = TeleportForwarderForAccountId32::<
			TestXcmConfig,
			AssetHubLocation,
			HereLocation,
			AccumulationInterior,
		>::forward(source.clone(), 500u128);
		ROUTER_SHOULD_FAIL.with(|f| f.set(false));

		assert!(result.is_err(), "expected forward to fail when router fails");
		assert_eq!(
			Balances::balance(&source),
			initial_balance,
			"source balance must be unchanged after XCM failure"
		);
		assert_eq!(
			Balances::total_issuance(),
			initial_issuance,
			"total issuance must be unchanged after XCM failure"
		);
	});
