### Title
Privilege escalation via AccountPermissionUpdateContract: an Active-permission key can rewrite Owner/Witness permissions and seize full account control - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateActuator` allows any signer that meets the weight/threshold of *any* valid permission on the account (not necessarily the Owner permission) to completely overwrite that account's Owner, Witness, and Active permission structures. Because the actuator's own `checkPermission` validation does not exclude `AccountPermissionUpdateContract` from the set of operations an Active permission is allowed to authorize, an account owner who delegates a scoped, low-privilege Active key (e.g., to an exchange, bot, or co-signer, intended only for limited operations such as transfers) inadvertently — or by default configuration — grants that key the ability to replace the account's Owner permission entirely, seizing irrevocable control of the account. This mirrors the Vvveb CVE-2026-34427 pattern: a "profile save"/self-update endpoint that is supposed to only touch the caller's own limited attributes instead accepts a privileged field (`role_id`) that elevates the caller to the highest privilege tier.

### Finding Description
The multi-sig permission model in java-tron distinguishes three permission classes: Owner (`id=0`, full control), Witness (`id=1`), and Active (`id>=2`, scoped by a 256-bit `operations` bitmap of allowed `ContractType`s). Transactions specify a `permission_id`; the signature-weight check only validates that the signer(s) satisfy the threshold of the *referenced* permission and, for Active permissions, that the bitmap allows the specific contract type being executed: [1](#0-0) 

The critical gap is that `AccountPermissionUpdateContract` (the contract type used to *change* the permission structure itself, including the Owner permission) is not treated specially and is not excluded from the set of operations an Active permission may authorize. The actuator's own bitmap validation in `checkPermission` only rejects unknown/unsupported bits, not this specific self-referential contract type: [2](#0-1) 

The accompanying test `checkAvailableContractTypeCorrespondingToCode` explicitly documents that only `ClearABIContract` and `UpdateBrokerageContract` are excluded from the default/available-operations bitmap — every other `ContractType`, including `AccountPermissionUpdateContract`, is considered a valid, assignable operation for an Active permission: [3](#0-2) 

When `execute()` runs, it unconditionally overwrites the account's Owner, Witness, and Active permissions with whatever the submitted `AccountPermissionUpdateContract` contains — it performs no comparison against the pre-existing Owner permission and does not require that the transaction be authorized by permission id 0: [4](#0-3) 

Consequently, any account holding an Active permission whose operations bitmap includes the `AccountPermissionUpdateContract` bit (which is the default posture unless the account owner has manually stripped that bit) can submit a self-authorized `AccountPermissionUpdateContract` transaction, satisfy only the Active permission's (potentially very low) threshold, and replace the Owner permission entirely — for example, setting themselves as the sole Owner key with threshold 1. This is functionally identical to the Vvveb bug class: a caller uses a scoped "update my own record" operation to write into a privileged field it should never be allowed to touch, and thereby escalates to the account's highest privilege tier.

### Impact Explanation
This allows an attacker who has been granted, or who otherwise controls, only a scoped Active-permission key on a victim account (e.g., a co-signer, automated trading key, exchange withdrawal key, or DApp-delegated key with default multisig setup) to unilaterally strip the true Owner's control and become the sole Owner of the account. This is a concrete unauthorized account-takeover primitive: the attacker gains permanent control over the account's funds, TRX/TRC10/TRC20 balances, staked/frozen resources, and voting power, and can lock out the legitimate owner irreversibly. This satisfies the "concrete unauthorized account operation" and "permanent freezing/theft of funds" impact bar.

### Likelihood Explanation
Exploitation requires only that the victim account has, at some point, granted an Active permission whose operations bitmap includes the `AccountPermissionUpdateContract` bit — which, per the framework's own test-documented default availability bitmap, is the out-of-the-box behavior unless deliberately restricted. This is a very common real-world configuration for multi-sig wallets, exchange hot-wallet key delegation, and smart contract/DApp integrations that grant a "convenience" Active key without carefully pruning every bit in the 256-bit operations mask. No special network position, no compromised validator/witness, and no additional privilege is required — a single signed transaction from a holder of such an Active key is sufficient.

### Recommendation
- In `AccountPermissionUpdateActuator.validate()` / `checkPermission()`, explicitly reject any Active permission whose `operations` bitmap sets the bit corresponding to `ContractType.AccountPermissionUpdateContract`, mirroring the existing exclusion for `ClearABIContract`/`UpdateBrokerageContract`.
- Additionally, enforce in `TransactionCapsule.checkPermission` / `TransactionUtil` that transactions of type `AccountPermissionUpdateContract` may only be authorized using `permission_id == 0` (the Owner permission), never a delegated Active permission, since this contract type inherently modifies the account's root authorization structure.
- Audit existing accounts' active permissions and provide a migration/warning path for any that currently have this bit set.

### Proof of Concept
1. Account `A` (Owner) creates an Active permission `P` (id=2) for delegated key `K`, using the default/available operations bitmap (which includes the `AccountPermissionUpdateContract` bit), with threshold 1 and only `K` as a key — a common "convenience delegation" setup.
2. Attacker, controlling `K`'s private key, crafts an `AccountPermissionUpdateContract` transaction for owner address `A`, setting:
   - `owner` permission = new Permission with `K` as sole key, threshold 1.
   - `actives` = whatever attacker wants going forward.
3. Attacker signs the transaction with `K` and sets `permission_id = 2` (referencing Active permission `P`).
4. `TransactionCapsule.validateSignature` / `checkWeight` confirms `K` satisfies `P`'s threshold (1) and that `P`'s bitmap allows `AccountPermissionUpdateContract` — transaction is accepted.
5. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)` and overwrites `A`'s Owner permission with the attacker-controlled one, per [5](#0-4) .
6. Attacker `K` is now the sole Owner of account `A`; the original owner's key no longer has any authority over the account.
