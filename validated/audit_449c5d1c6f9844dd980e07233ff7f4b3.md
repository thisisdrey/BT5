### Title
Unbounded byte-array allocation from unclamped `intValueSafe()` length operand in `CODECOPY`/`EXTCODECOPY` causes uncaught `OutOfMemoryError` - (File: actuator/src/main/java/org/tron/core/vm/OperationActions.java)

### Summary
The undici bug is a class of "attacker supplies a numeric protocol parameter that is checked for format but not for a safe range, and the value is fed into a size-sensitive allocation without a try/catch, causing an unhandled exception that crashes the process." The closest reachable analog in java-tron is `codeCopyAction()`/`extCodeCopyAction()` in the TVM interpreter, where a stack operand (fully controlled by a deployed contract's bytecode, reachable by any unprivileged contract deployer/caller) is converted with `DataWord.intValueSafe()` and used directly to allocate a `byte[]` with no upper-bound check.

### Finding Description
`codeCopyAction()` and `extCodeCopyAction()` both pop a `lengthData` operand from the EVM stack and convert it via `intValueSafe()`: [1](#0-0) 

`intValueSafe()` only guards against negative/overflowed values by clamping to `Integer.MAX_VALUE`; it performs no upper-bound/sanity check against a reasonable memory limit: [2](#0-1) 

The same unclamped-length pattern is repeated in `extCodeCopyAction`: [3](#0-2) 

Because `lengthData` can be set to `Integer.MAX_VALUE` (~2 GB) by simply pushing a sufficiently large stack value in contract bytecode, `new byte[lengthData]` in both handlers attempts a multi-gigabyte heap allocation. This throws `java.lang.OutOfMemoryError`, which is a JVM `Error`, not an `Exception`. I was unable to find a `catch (Throwable)`/`catch (OutOfMemoryError)` wrapper around the TVM opcode dispatch loop in `VM.play`/`Program` in the code I could inspect—the only related identifier found was the unrelated custom `Program.OutOfMemoryException` (used for EVM memory-expansion gas accounting, referenced in `RuntimeImpl.java`), which is a distinct checked exception thrown by `checkMemorySize`, not the actual `java.lang.OutOfMemoryError` thrown by `new byte[...]`.

This mirrors the undici root cause exactly: (1) an input-format-only validation function (`isValidClientWindowBits()` / `intValueSafe()`) that does not bound the value to a safe operational range, (2) a size-sensitive constructor call (`createInflateRaw()` / `new byte[lengthData]`) not wrapped in a try-catch for the corresponding exception/error type, and (3) the resulting unhandled `Error` propagating up the call stack.

### Impact Explanation
If the allocation-triggered `OutOfMemoryError` is not caught anywhere in the transaction-execution call chain (`Manager.processTransaction` → `RuntimeImpl` → `VM.play` → `OperationActions`), it can propagate out of the executing thread. Depending on which thread runs block/transaction application (e.g., the thread inside `Manager.pushBlock`/`processBlock`), an uncaught `Error` here can abort in-flight block processing, corrupt in-memory state consistency, or take down the node process—matching the "node crash or halt" acceptance criterion. Because this triggers during normal contract-code execution (`CODECOPY`/`EXTCODECOPY` are extremely common opcodes emitted by the Solidity compiler for constructor code and library code copying), a single deployed malicious contract, once triggered, could DoS any full node that executes it.

### Likelihood Explanation
Any unprivileged account can deploy a contract or call an existing contract that executes `CODECOPY`/`EXTCODECOPY` with a large length operand — no special privilege, large balance, or specific witness/SR role is required. This is directly reachable through `TriggerSmartContract`/`CreateSmartContract` broadcast transactions, which are processed by every full node validating the chain, making the reachable surface very broad.

### Recommendation
- In `codeCopyAction()` and `extCodeCopyAction()`, clamp `lengthData` to the actual EVM memory-expansion/energy-accounted size (which is already limited by `checkMemorySize`/`Program.OutOfMemoryException` logic used elsewhere) *before* allocating `codeCopy`, rather than allocating a raw `byte[lengthData]` first.
- Alternatively, wrap the allocation with the existing energy-based memory bound check so that array size is always derived from the already-charged/limited memory region, never directly from an unclamped 32-byte stack word.

### Proof of Concept
1. Deploy a minimal contract whose bytecode contains a `CODECOPY` (or `EXTCODECOPY`) instruction with the length operand set to a large value close to `Integer.MAX_VALUE` (e.g., `0x7fffffff`), e.g., via raw bytecode crafted with `PUSH4 0x7fffffff PUSH1 0x00 PUSH1 0x00 CODECOPY`.
2. Broadcast a `TriggerSmartContract`/`CreateSmartContract` transaction invoking this bytecode with sufficient `fee_limit` to reach the `CODECOPY` opcode (the OOM occurs before any successful gas-metered memory write, since the array is allocated directly).
3. Observe the executing full node's JVM throw `java.lang.OutOfMemoryError` from `OperationActions.codeCopyAction`/`extCodeCopyAction`; verify whether this is caught anywhere in `RuntimeImpl`/`Manager`'s transaction-processing exception handling.

**Note on confidence:** I was not able to fully trace whether some outer layer (e.g., `RuntimeImpl.execute()`, the JVM's `Thread.UncaughtExceptionHandler`, or a generic `catch (Throwable)`) already contains the OOM within the executing thread without crashing the whole node process — the codebase index did not surface such a catch-all around `VM.play`. This should be verified against the full `RuntimeImpl.java` and `VM.java` source before treating this as fully confirmed; if such a catch-all exists and merely fails the single transaction (similar to how `Program.OutOfMemoryException` is caught elsewhere), the practical impact would be reduced to a per-transaction failure rather than a node crash.

```java
  public static void codeCopyAction(Program program) {
    byte[] fullCode = program.getCode();

    int memOffset = program.stackPop().intValueSafe();
    int codeOffset = program.stackPop().intValueSafe();
    int lengthData = program.stackPop().intValueSafe();

    int sizeToBeCopied = lengthData;
    if ((long) codeOffset + lengthData > fullCode.length) {
      sizeToBeCopied = fullCode.length < codeOffset ? 0 : fullCode.length - codeOffset;
    }

    byte[] codeCopy = new byte[lengthData];

    if (codeOffset < fullCode.length) {
      System.arraycopy(fullCode, codeOffset, codeCopy, 0, sizeToBeCopied);
    }

    program.memorySave(memOffset, codeCopy);
    program.step();
```

```java
   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
```
