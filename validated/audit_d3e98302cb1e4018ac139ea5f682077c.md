### Title
Downloaded Atlas attachments bypass `attachments_max_size` enforcement - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AtlasDB::should_keep_attachment` (which enforces `AtlasConfig.attachments_max_size`) is only invoked on the write path used by `POST /v2/transactions` for contract-call attachments [1](#0-0) . The peer-to-peer attachment download path (`AttachmentsDownloader::run` -> `extend_with_attachments` -> `insert_instantiated_attachment`) never calls `should_keep_attachment` or otherwise checks `attachment.content.len()` against `attachments_max_size` before writing the content BLOB. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`AttachmentRequest`s are chosen from a peer's inventory via `get_prioritized_attachments_requests` [5](#0-4) . A peer that legitimately advertises an attachment in `GetAttachmentsInvResponse` can respond to the follow-up `GET /v2/attachments/{hash}` with a `GetAttachmentResponse` containing arbitrarily large `attachment.content` bytes: `try_parse_response`/`decode_atlas_get_attachment` merely hex-decode a JSON string and construct an `Attachment` with no explicit size cap tied to `attachments_max_size` [6](#0-5) . `extend_with_attachments` then unconditionally inserts the decoded `Attachment` into `self.attachments` on success [7](#0-6) , and `AttachmentsDownloader::run`'s `Done` branch calls `insert_instantiated_attachment` for every attachment in that set with no size check [8](#0-7) . `insert_instantiated_attachment` writes `attachment.content` directly into the `attachments.content` BLOB column with no length gate against `self.atlas_config.attachments_max_size` [4](#0-3) . By contrast, the only place `attachments_max_size` is enforced is `should_keep_attachment`, used exclusively by the RPC-submitted contract-call attachment path in `posttransaction.rs` [9](#0-8) [1](#0-0) .

The only bound on response size that remains is the generic HTTP body/message size limit in the connection/codec layer (`MAX_PAYLOAD_LEN`), which is orders of magnitude larger than the default `attachments_max_size` (1 MiB, `ATTACHMENTS_MAX_SIZE_MIN`) [10](#0-9) . That generic cap is a blunt DoS backstop, not an enforcement of the Atlas-specific size policy, so a peer can serve content well above the network's configured `attachments_max_size` and still fit under the generic HTTP limit.

### Impact Explanation
A malicious (but otherwise unprivileged, self-run) peer that answers a legitimate `AttachmentInstance` content-hash request can cause the victim node to store attachment content far larger than its configured `attachments_max_size` in its local `attachments` SQLite table, and this attachment is subsequently marked available and can itself be re-served to other peers (`find_attachment` is used by `getattachment.rs`'s handler), propagating storage bloat outward. This is a storage/disk exhaustion issue tied to the Atlas subsystem rather than a memory-safety crash or a consensus-breaking forgery, so it falls into the "bounded compute/storage DoS on a subsystem" category rather than the Critical bucket, and is repeatable per distinct attachment instance the attacker's peer is chosen to serve.

### Likelihood Explanation
Preconditions are modest: the attacker must run a peer that is selected as a download source for at least one queued `AttachmentInstance` (achieved simply by advertising the hash as present in its inventory response, which is not otherwise verified against the true content size before download). No secret, admin role, or privileged key is required — this matches the "unprivileged peer serving arbitrary bytes over its RPC/P2P HTTP port" threat model. The cost to the attacker is trivial (serve one oversized HTTP response); the impact accumulates each time such a request is fulfilled by the malicious peer.

### Recommendation
Enforce `attachments_max_size` (or an equivalent bound) in the download path before or during `insert_instantiated_attachment`/`insert_uninstantiated_attachment` — e.g., check `attachment.content.len() as u32 > atlas_config.attachments_max_size` inside `extend_with_attachments` (rejecting/treating as a failed request) or inside `insert_instantiated_attachment` itself (mirroring `should_keep_attachment`'s check), and treat oversized responses as a faulty/failed peer request so the reliability report is decremented.

```rust
// stackslib/src/net/atlas/tests.rs (extend of existing test module)
#[test]
fn test_oversized_downloaded_attachment_bypasses_max_size() {
    let atlas_config = AtlasConfig {
        contracts: HashSet::new(),
        attachments_max_size: 16, // small cap
        max_uninstantiated_attachments: 10,
        uninstantiated_attachments_expire_after: 10,
        unresolved_attachment_instances_expire_after: 10,
        genesis_attachments: None,
    };
    let mut atlas_db = AtlasDB::connect_memory(atlas_config.clone()).unwrap();

    // Simulate a GetAttachmentResponse decoded from a malicious peer with
    // content far exceeding attachments_max_size (16 bytes).
    let oversized_attachment = Attachment::new(vec![0xAA; 1_000_000]);

    // Exact call made by AttachmentsDownloader::run's Done branch
    // (download.rs:159-162), with NO should_keep_attachment gate:
    atlas_db.insert_instantiated_attachment(&oversized_attachment).unwrap();

    // Assert it was stored despite exceeding attachments_max_size.
    let stored = atlas_db.find_attachment(&oversized_attachment.hash()).unwrap();
    assert!(stored.is_some());
    assert!(stored.unwrap().content.len() as u32 > atlas_db.atlas_config.attachments_max_size);
}
```
This demonstrates that `insert_instantiated_attachment` (the exact call made from `AttachmentsDownloader::run`, `download.rs:159-162`) accepts and persists content exceeding `AtlasConfig.attachments_max_size`, whereas the equivalent RPC POST path (`posttransaction.rs:233-236`) would reject it via `should_keep_attachment`.

```rust
    pub fn get_prioritized_attachments_requests(&self) -> BinaryHeap<AttachmentRequest> {
        let mut queue = BinaryHeap::new();
        let mut enqueued = HashSet::new();
        for ((contract_id, pages, _), peers_responses) in self.inventories.iter() {
            let missing_attachments = match self
                .attachments_batch
                .attachments_instances
                .get(contract_id)
            {
                None => continue,
                Some(missing_attachments) => missing_attachments,
            };
            // Note: we're getting missing_attachments (attachment_id: content_hash)
            for (attachment_index, content_hash) in missing_attachments.iter() {
                let page_index = attachment_index / AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;
                // Since there's a limit in the number of pages that a node can request,
                // we can potentially have multiple inventory request at once.
                if !pages.contains(&page_index) {
                    continue;
                }

                if enqueued.contains(content_hash) {
                    debug!("Atlas: {} already enqueued", content_hash);
                    continue;
                }

                let mut sources = HashMap::new();
                let position_in_page =
                    attachment_index % AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;

                for (peer_url, response) in peers_responses.iter() {
                    // Considering the response, look for the page with the index
                    // we're looking for.
                    let search_page = response.pages.iter().find(|page| page.index == page_index);

                    let has_attachment = search_page
                        .and_then(|search_page| {
                            search_page.inventory.get(position_in_page as usize)
                        })
                        .map(|result| *result == 1)
                        .unwrap_or(false);

                    if !has_attachment {
                        debug!(
                            "Atlas: peer does not have attachment ({}, {}) in its inventory {:?}",
                            page_index, position_in_page, response.pages
                        );
                        continue;
                    }

                    let report = self
                        .peers
                        .get(peer_url)
                        .expect("Atlas: unable to retrieve reliability report for peer");
                    sources.insert(peer_url.clone(), report.clone());
                }

                if sources.is_empty() {
                    warn!("Atlas: could not find a peer including attachment in its inventory");
                    continue;
                }

                // Success, we found at least one inventory including the attachment we're looking for.
                let request = AttachmentRequest {
                    sources,
                    content_hash: content_hash.clone(),
                    stacks_block_height: self.attachments_batch.stacks_block_height,
                    canonical_stacks_tip_height: self.attachments_batch.canonical_stacks_tip_height,
                };
                enqueued.insert(content_hash);
                queue.push(request);
            }
        }
        queue
    }
```

```rust
    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
```

```rust
    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }
```

```rust
    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
```
