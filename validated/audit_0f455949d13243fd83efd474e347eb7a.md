## Analysis

The external report's core broken invariant: **an entity is referenced purely by a monotonically-assigned index (`batchIndex`), and the code that consumes that index later never re-binds it to the content hash that was true at submission time.** If the content behind that index changes (via reorg) between submission and consumption, the wrong entity gets acted upon and value moves incorrectly.

The direct structural analog exists in `snowbridge-pallet-outbound-queue-v2`.

`Nonce<T>` is a strictly incrementing counter, and each committed outbound message is assigned the next nonce value in `do_process_message`: [1](#0-0) 

The resulting `PendingOrder` that is stored — and later consulted to pay the relayer reward — carries **only** `{ nonce, fee, block_number }`, with no hash/topic binding to the actual message content that produced it: [2](#0-1) 

When the relayer later proves delivery on Ethereum, `process_delivery_receipt` looks the order up **by `nonce` alone** and pays `order.fee`: [3](#0-2) 

Note that the `DeliveryReceipt` decoded from the Ethereum event log does carry a `topic` field (the message identity commitment on the source side): [4](#0-3) 

but `receipt.topic` is **never compared against anything** in `process_delivery_receipt` — it's decoded, never validated against the `PendingOrders[nonce]` entry or the `Messages`/`MessageLeaves` content that was actually committed for that nonce.

### Title
Reward settlement in `outbound-queue-v2` binds only to `nonce`, not to message content — analog of index-only batch referencing - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

### Summary
`process_delivery_receipt` in `snowbridge-pallet-outbound-queue-v2` settles relayer rewards purely by looking up `PendingOrders` keyed on the numeric `nonce` from the Ethereum receipt. The `PendingOrder` value stores only `nonce`, `fee`, and `block_number` — it never records the hash/topic of the actual `OutboundMessage` that was committed under that nonce. `receipt.topic`, which is decoded from the Ethereum-side `InboundMessageDispatched` event, is never checked against the message content bound to that nonce on the BridgeHub side.

### Finding Description
The nonce→message binding is established once, at commit time, inside `do_process_message`, by simply taking `Nonce::<T>::get().checked_add(1)` — the next sequential integer — and writing a `PendingOrder{ nonce, fee, block_number }` with no cryptographic tie to the message body (`OutboundMessage`/`OutboundMessageWrapper`) that produced that nonce. [1](#0-0) 

Later, `process_delivery_receipt` re-derives *no* commitment check at all: it validates only `receipt.gateway == T::GatewayAddress::get()`, fetches `PendingOrders::<T>::get(nonce)`, and pays `order.fee` to the resolved reward account, then removes the order. [3](#0-2) 

This is structurally identical to the Rollup.sol `challengeState(batchIndex)` bug: the settlement logic trusts that "whatever is stored at index N right now" is still the same logical entity that was originally intended when the index was first observed/referenced, with no hash re-binding at consumption time. If — due to BridgeHub chain re-org/fork-choice change before finality, differing message-queue processing order across competing forks, or any path that causes a different `OutboundMessage` to occupy slot `nonce` than the one the relayer actually delivered and proved on Ethereum — `process_delivery_receipt` will pay out `order.fee` for whatever message is currently sitting at that nonce, which may carry a different (larger or smaller) fee than the message the relayer actually relayed. The `receipt.topic` field exists specifically to allow this binding check but is dead — decoded and never compared.

### Impact Explanation
This breaks the "Message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" invariant: settlement (`register_reward`) is driven by an index whose content-identity is not re-verified at settlement time. Depending on which message occupies the reused/reordered nonce, this can result in over-payment of relayer rewards (drain of bridge reward funds) or a relayer being paid for a different, unrelated message than the one it actually delivered — i.e., theft/unbacked payout or duplicate/incorrect settlement, both explicitly in-scope impact categories (theft/unbacked mint or unlock, duplicate settlement or payout).

### Likelihood Explanation
The trigger requires the nonce↔message binding at the BridgeHub side to diverge between two states observed before/after a chain re-org of unfinalized blocks (a normal occurrence in Substrate parachains prior to finality, not requiring a malicious validator/relayer). Unlike the L1 Rollup.sol case where an attacker can deliberately race two conflicting transactions into the same slot, here the underlying trigger is a plain chain fork/reorg reordering `on_finalize`/message-queue processing, which is a routine occurrence class the report explicitly calls in-scope ("issue about... re-org leading to financial loss... is valid").

### Recommendation
Store a content commitment (e.g., the `message_abi_encoded_hash`/`MessageLeaves` entry, or the full `OutboundMessageWrapper` hash) inside `PendingOrder` at commit time, and require `process_delivery_receipt` to verify that `receipt.topic` (or an equivalent hash derived from the receipt) matches the stored commitment for `nonce` before paying `order.fee`, mirroring the fix pattern of re-checking `committedBatches[_batchIndex] == _batchHash` in the referenced Rollup.sol patch.

### Proof of Concept
1. BridgeHub commits message A at `nonce = N` with `fee = 100` in fork F1; `PendingOrders[N] = {nonce: N, fee: 100, block_number: B}`.
2. Before F1 finalizes, a chain fork/reorg occurs; in canonical fork F2, a different message B (originating a different XCM/fee) is committed and assigned the same `nonce = N` because `Nonce<T>` is derived purely from sequential counting, giving `PendingOrders[N] = {nonce: N, fee: 500, block_number: B'}`.
3. A relayer had already relayed message A to Ethereum (as observed in F1) and obtained a valid Ethereum-side proof/receipt referencing `nonce = N`.
4. Relayer submits `submit_delivery_receipt`/`process_delivery_receipt` against canonical fork F2's state; `PendingOrders::<T>::get(N)` returns message B's order (`fee = 500`), which is paid out even though message A (fee 100) was the one actually delivered — no check ever compares `receipt.topic` to the content behind `PendingOrders[N]`. [5](#0-4)

			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
