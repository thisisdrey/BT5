### Title
Rounding-to-zero in `UnDelegateResourceActuator` lets an account reclaim delegated TRX while leaving accrued bandwidth/energy usage debt with the receiver, letting the owner escape a portion of its resource "consumption cost" - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
`UnDelegateResourceActuator.execute()` computes the amount of already-consumed bandwidth/energy usage (`transferUsage`) that must be moved back from the receiver to the owner when a delegation is partially withdrawn, using floating-point (`double`) division: `transferUsage = (long) (receiverCapsule.getNetUsage() * ((double)(unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()))` [1](#0-0) . When `unDelegateBalance` is a small fraction of the receiver's total frozen balance (e.g. a large account delegated a huge amount, and the owner un-delegates only a tiny slice at a time), this floating-point multiply-then-truncate rounds down to `0`, exactly like the `interest` computation in the reported Beedle bug rounding to `0` for tokens with small decimals.

### Finding Description
The same computation pattern exists twice: once in the plain actuator path reachable directly by a signed `UnDelegateResourceContract` transaction [2](#0-1) , and once in the TVM native-contract path used by contract calls (`UnDelegateResourceProcessor`) [3](#0-2) .

Root cause: `transferUsage` and `unDelegateMaxUsage` are derived by casting the ratio `unDelegateBalance / receiverCapsule.getAllFrozenBalanceForBandwidth()` (or `...ForEnergy()`) to `double`, multiplying, and truncating to `long`. If this ratio is small enough that `receiverCapsule.getNetUsage() * ratio < 1`, the result truncates to `0`. Subsequently:

```java
if (Objects.nonNull(receiverCapsule) && transferUsage > 0) {
    processor.unDelegateIncrease(ownerCapsule, receiverCapsule, transferUsage, BANDWIDTH, now);
}
``` [4](#0-3) 

Because `transferUsage == 0`, the `unDelegateIncrease` call that would otherwise transfer the receiver's average-usage window entry back to the owner is skipped entirely. The receiver retains its full recorded `netUsage`/`energyUsage` (and the window size backing it) even though part of the frozen balance that funded that usage has just been withdrawn by the owner. Meanwhile the owner regains `unDelegateBalance` as its own `frozenBalanceForBandwidthV2`/`frozenBalanceForEnergyV2` with **no** corresponding usage debt subtracted (`transferUsage=0`), effectively creating "free" (already-amortized) bandwidth/energy capacity for the owner — the resource-accounting analogue of the interest that a Beedle borrower never pays.

An attacker acting as owner can automate many small `DelegateResourceContract` + `UnDelegateResourceContract` cycles (or use `UnDelegateResourceContract` calls from a smart contract via the native-contract path) against a large receiver account so that each individual `unDelegateBalance` is small relative to `receiverCapsule.getAllFrozenBalanceFor{Bandwidth,Energy}()`, deliberately forcing `transferUsage` to `0` on every call while still reclaiming the underlying TRX balance.

### Impact Explanation
Repeatedly triggering the zero-rounding path allows an attacker to accumulate freshly available bandwidth/energy balance on the owner side without any of the already-consumed usage being deducted from the receiver's accounting or transferred as a liability to the owner. This produces an inconsistency between the aggregate frozen-balance-backed resource capacity and the actual usage ledger, letting the attacker obtain resource capacity (bandwidth/energy, which is otherwise a scarce, purchasable/freezable asset) that is not properly backed by consumption accounting — an unbacked-balance style issue in the resource economy, satisfying the "unbacked balance" impact criterion.

### Likelihood Explanation
The path is reachable by any account owner holding a `DelegatedResourceCapsule` via a single signed `UnDelegateResourceContract` transaction (no special privilege required), and is also reachable from TVM contract execution through `UnDelegateResourceProcessor`. Exploitation requires choosing `unDelegateBalance` values small relative to the receiver's total frozen balance and issuing them repeatedly, which is straightforward to script and requires only the delegation/un-delegation dance (delegate then progressively un-delegate in small increments), making the likelihood moderate-to-high for a motivated actor targeting large delegatee accounts.

### Recommendation
Compute `transferUsage` (and `unDelegateMaxUsage`) using integer/`BigInteger` arithmetic (or ceiling-rounding as already done elsewhere in `ResourceProcessor.divideCeilExact`) instead of floating-point `double` multiply/divide, and ensure the computation never silently floors non-zero proportional usage to `0` — mirroring the "hardened" `BigInteger`-based computations already used for `usageToBalance` and `calculateGlobalEnergyLimit` in `RepositoryImpl` [5](#0-4) . At minimum, round up (ceiling) rather than truncate when `unDelegateBalance > 0` and `receiverCapsule.getNetUsage() > 0`, so a proportional share of usage debt is always transferred.

### Proof of Concept
1. Account `R` (receiver) accumulates `getAllFrozenBalanceForBandwidth() = 1_000_000_000_000` (1e12) sun via delegations from many owners, and has `netUsage = 999` (bandwidth points used).
2. Owner `O` had delegated `unDelegateBalance = 500` sun (a tiny slice) to `R`, locked resource.
3. `O` calls `UnDelegateResourceContract` with `unDelegateBalance = 500`.
4. In `execute()`:
   `transferUsage = (long)(999 * ((double)500 / 1_000_000_000_000)) = (long)(4.995e-7) = 0`.
5. `transferUsage > 0` is `false`, so `processor.unDelegateIncrease(...)` is never invoked — `R`'s `netUsage` window is left completely untouched even though `O` withdrew `500` sun of the balance that backed it.
6. `O` regains `500` sun as its own `frozenBalanceForBandwidthV2` with zero usage debt.
7. Repeating steps with many owners each un-delegating small slices from the same large receiver systematically produces a growing gap between total frozen-balance-backed capacity and the usage ledger, all with normal, unprivileged transactions.

  private long usageToBalance(long usage, long totalWeight, long totalLimit) {
