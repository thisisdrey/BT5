### Title
Unauthenticated attachment-cache griefing via `/v2/transactions` bypasses on-chain commitment check in `should_keep_attachment` - (File: `stackslib/src/net/atlas/db.rs`)

### Summary
`AtlasDB::insert_uninstantiated_attachment` (`stackslib/src/net/atlas/db.rs:511-536`) admits attacker-supplied attachment blobs into the uninstantiated-attachment cache without verifying the attachment's hash corresponds to any real, pending on-chain `AttachmentInstance`. The only gate, `should_keep_attachment` (`stackslib/src/net/atlas/db.rs:249-266`), checks only the target contract-call identifier and attachment size, not content-hash correspondence to a queued instance. An unprivileged remote client can therefore fill the cache with garbage and trigger FIFO eviction (`evict_k_oldest_uninstantiated_attachments`, `db.rs:538-547`) of legitimately queued attachments before their real `AttachmentInstance` is processed.

### Finding Description
The claimed equality — "attachments retained with `was_instantiated=0` == bytes that a confirmed `AttachmentInstance.content_hash` will eventually reference" — is broken. The only reachable path to `insert_uninstantiated_attachment` is the RPC handler `RPCPostTransactionRequestHandler::try_handle_request` in `stackslib/src/net/api/posttransaction.rs:230-251`:

```
if network.get_atlasdb().should_keep_attachment(&contract_call.to_clarity_contract_id(), attachment) {
    network.get_atlasdb_mut().insert_uninstantiated_attachment(attachment)...
}
```

`should_keep_attachment` (`db.rs:249-266`) only verifies (1) the transaction's contract-call target is in the configured whitelist (e.g. the `bns` contract) and (2) the attachment size is under `attachments_max_size`. It never checks that `Hash160::from_data(attachment.content)` matches any `content_hash` in `attachment_instances`, nor that the accompanying transaction will actually emit a matching atlas print event on execution.

`mempool.submit` / `will_admit_mempool_tx` (`stackslib/src/chainstate/stacks/db/blocks.rs:6571-6676`) only performs *structural* admission checks — valid signature, minimum fee (`MINIMUM_TX_FEE`/`MINIMUM_TX_FEE_RATE_PER_BYTE`), valid/chained nonce (up to `MAXIMUM_MEMPOOL_TX_CHAINING`), existing contract and public function. It does not execute the contract call, so it cannot determine whether the call will actually commit to the attached content hash. Consequently, an attacker who owns any funded account can repeatedly:

1. Construct low-fee, nonce-sequential `ContractCall` transactions targeting the whitelisted BNS contract with a function/args combination that is syntactically valid but produces content_hash != anything ever emitted on-chain.
2. POST each with `PostTransactionRequestBody{tx, attachment}` to `/v2/transactions` (`posttransaction.rs:298-317`).
3. Each accepted tx pushes a fabricated blob into `attachments` with `was_instantiated=0`.
4. Once `count_uninstantiated_attachments() >= max_uninstantiated_attachments` (default `MAX_UNINSTANTIATED_ATTACHMENTS_MIN = 50_000`, `stackslib/src/net/atlas/mod.rs:53`), `evict_k_oldest_uninstantiated_attachments` deletes strictly by `created_at ASC` (`db.rs:538-547`), with no distinction between attacker junk and a legitimate attachment submitted by an honest BNS user whose transaction is still pending confirmation.

This matches the exact mechanic in the test `test_evict_k_oldest_uninstantiated_attachments` (`stackslib/src/net/atlas/tests.rs:889-1017`), which demonstrates FIFO eviction irrespective of legitimacy — it simply hasn't been exercised with an adversarial mix of legitimate vs. fabricated entries.

### Impact Explanation
An unprivileged remote party can grief the Atlas attachment cache: legitimate BNS attachments (e.g., a real name-registration payload posted by an honest user awaiting block confirmation) can be evicted from the `attachments` table before the corresponding `AttachmentInstance` arrives via `check_attachment_instances` (`stackslib/src/net/atlas/download.rs:246-262`), because `find_uninstantiated_attachment` will return `None` once evicted. This forces the node to instead fall into the "unknown attachment" branch and attempt a full peer-download of an attachment for which the true content is otherwise already locally available, causing legitimate BNS attachment resolution to fail or be delayed — a High-severity "attachment/BNS mismatch" scenario. Effects are per-node (each node's own AtlasDB) and are repeatable for as long as the attacker can fund minimum-fee transactions.

### Likelihood Explanation
The attacker needs: a funded Stacks account able to pay `MINIMUM_TX_FEE` per transaction, the ability to reach the node's RPC port (`/v2/transactions`, unauthenticated), and knowledge of the whitelisted contract (public, e.g. `bns`). No admin role, RPC secret, or privileged key is required — this fits the "unprivileged remote peer" threat model. The attack is bounded by the cost of ~50,000 minimum-fee transactions to fully overflow the default `max_uninstantiated_attachments`, which is a moderate but non-trivial cost (mitigated somewhat by `MAXIMUM_MEMPOOL_TX_CHAINING` limiting how many un-mined transactions per account can sit in the mempool simultaneously, requiring either multiple accounts or waiting for chain confirmations between chained batches).

### Recommendation
In `insert_uninstantiated_attachment` / `should_keep_attachment`, require that an inbound attachment either (a) already has a matching queued/unresolved `AttachmentInstance.content_hash` in `attachment_instances`, or (b) is bounded per-origin-account/contract-call so that unresolved, uncorrelated attachments cannot cheaply exhaust the shared cache. Additionally, consider evicting preferentially by "least likely to correspond to a real instance" (e.g., attachments with no matching queued instance after some grace period) rather than strict `created_at ASC`, or maintain separate quotas/priority for attachments submitted alongside a mempool-accepted contract-call versus attachments that have no corroborating on-chain data at all.

### Proof of Concept
Extend `stackslib/src/net/atlas/tests.rs` similarly to `test_evict_k_oldest_uninstantiated_attachments`:
1. Insert one "legitimate" uninstantiated attachment `A` (simulating an honest user's pre-submitted attachment).
2. Loop-insert `max_uninstantiated_attachments` fabricated attachments unrelated to any `AttachmentInstance` (simulating attacker flood via repeated `/v2/transactions` posts with garbage contract-calls to the whitelisted contract).
3. Assert `atlas_db.find_uninstantiated_attachment(&A.hash())` returns `None` (evicted) before a hypothetical `AttachmentInstance` referencing `A.hash()` is ever queued/resolved — demonstrating the legitimate entry was destroyed by unrelated, unauthenticated attacker traffic.

This can be complemented by an RPC-level test that drives `RPCPostTransactionRequestHandler` with crafted `PostTransactionRequestBody{tx, attachment}` payloads targeting the whitelisted contract with syntactically valid but semantically unrelated contract-call arguments, confirming `should_keep_attachment` accepts them purely on contract-id/size grounds.     pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_k_oldest_uninstantiated_attachments(&mut self, k: u32) -> Result<(), db_error> {
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE hash IN (SELECT hash FROM attachments WHERE was_instantiated = 0 ORDER BY created_at ASC LIMIT ?)",
            params![k],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())

        clarity_connection: &mut T,
        chainstate_config: &DBConfig,
        has_microblock_pubkey: bool,
        tx: &StacksTransaction,
        tx_size: u64,
    ) -> Result<(), MemPoolRejection> {
        // 1: must parse (done)

        // 2: it must be validly signed.
        let epoch = clarity_connection.get_epoch();

        StacksChainState::process_transaction_precheck(chainstate_config, tx, epoch)
            .map_err(MemPoolRejection::FailedToValidate)?;

        // 3: it must pay a tx fee
        let fee = tx.get_tx_fee();

        if fee < MINIMUM_TX_FEE || fee / tx_size < MINIMUM_TX_FEE_RATE_PER_BYTE {
            return Err(MemPoolRejection::FeeTooLow(
                fee,
                cmp::max(MINIMUM_TX_FEE, tx_size * MINIMUM_TX_FEE_RATE_PER_BYTE),
            ));
        }

        // 4: check if transaction is valid in the current epoch
        if !StacksBlock::validate_transaction_static_epoch(tx, epoch) {
            return Err(MemPoolRejection::Other(
                "Transaction is not supported in this epoch".to_string(),
            ));
        }

        // 5: the account nonces must be correct
        let (origin, payer) =
            match StacksChainState::check_transaction_nonces(clarity_connection, tx, true) {
                Ok(x) => x,
                // if errored, check if MEMPOOL_TX_CHAINING would admit this TX
                Err((e, (origin, payer))) => {
                    // if the nonce is less than expected, then TX_CHAINING would not allow in any case
                    if e.actual < e.expected {
                        return Err(e.into());
                    }

                    let tx_origin_nonce = tx.get_origin().nonce();

                    let origin_max_nonce = origin.nonce + 1 + MAXIMUM_MEMPOOL_TX_CHAINING;
                    if origin_max_nonce < tx_origin_nonce {
                        return Err(MemPoolRejection::TooMuchChaining {
                            max_nonce: origin_max_nonce,

                            principal: tx.origin_address().into(),

                        });
