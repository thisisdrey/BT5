### Title
Unbounded client-supplied `estimated_len` causes integer overflow in `minimum_fee` computation - ([File: stackslib/src/net/api/postfeerate.rs])

### Summary
`RPCPostFeeRateRequestHandler::try_parse_request` accepts an attacker-controlled `estimated_len` field from the JSON body and only lower-bounds it with `max(body.estimated_len, payload_data.len())`, never validating an upper bound. This value flows unchecked into `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` in `estimate_tx_fee_from_cost_and_length`, which can overflow `u64` arithmetic.

### Finding Description
In `try_parse_request` (stackslib/src/net/api/postfeerate.rs:180-181), `estimated_len` is computed as `std::cmp::max(body.estimated_len.unwrap_or(0), payload_data.len() as u64)`. The only size check applied is `preamble.get_content_length()` against `MAX_PAYLOAD_LEN` (line 152-158), which bounds the size of the HTTP *request body* — not the numeric magnitude of the JSON integer `estimated_len` field. An attacker can send a tiny JSON body such as `{"estimated_len": 18446744073709551615, "transaction_payload": "0x..."}` (well under `MAX_PAYLOAD_LEN`) with a small valid `transaction_payload`, so `max()` selects the attacker's huge value.

This unbounded `u64` is later used at stackslib/src/net/api/postfeerate.rs:112: `let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;`. With `estimated_len` near `u64::MAX`, this multiplication overflows.

I verified the second half of the question's claim — that the oversized `estimated_len` also steers `metric.from_cost_and_len`'s `scalar_cost` out of proportion — is **not** valid: `ProportionalDotProduct::calculate_len_proportion` (stackslib/src/cost_estimates/metrics.rs:61-67) computes `1_f64.min(tx_len as f64 / block_size_limit as f64)`, which clamps the length proportion to `PROPORTION_RESOLUTION` regardless of how large `tx_len` is, so `scalar_cost` is not exploitable this way, and `UnitMetric::from_cost_and_len` ignores length entirely.

The `minimum_fee` overflow, however, is real: there is no `checked_mul`/`saturating_mul`, and no cap comparing `estimated_len` to `MAX_PAYLOAD_LEN`-scale values before the multiplication.

### Impact Explanation
In a release build (default, no `overflow-checks = true` found in any Cargo.toml in the repo), the multiplication silently wraps, producing an incorrect (often much smaller, potentially near-zero) `minimum_fee` floor applied to `RPCFeeEstimateResponse.estimations[*].fee`. This lets a remote, unauthenticated caller manipulate the fee-rate floor returned by a public read endpoint (`/v2/fees/transaction`) that wallets/bridges rely on for fee decisions — a "bounded compute DoS/state-serving distortion" style High-severity issue for a read endpoint, since the served numbers no longer reflect the real minimum fee tied to the actual transaction size. In a debug build (overflow checks enabled by default), the same multiplication panics, crashing the request-handling thread — but this only manifests on debug builds, which are not the production/hardened deployment target, so I cannot confirm remote crash on a typical release-mode node.

### Likelihood Explanation
The endpoint is a public, unauthenticated JSON RPC route with no special preconditions: any TCP client that can reach the RPC port and craft a small valid HTTP POST can trigger this with a single request, and it's fully repeatable. Requires the node to have cost/fee estimators enabled (`rpc_args.get_estimators_ref()` returns `Some`), which is the common default configuration for RPC-fee-serving nodes.

### Recommendation
Clamp `body.estimated_len` to a sane upper bound (e.g., `MAX_PAYLOAD_LEN` or the epoch's block size limit) before taking `max()` with the decoded payload length, and use `checked_mul`/`saturating_mul` for `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE`, returning a `400 Bad Request` if the supplied value exceeds the bound rather than silently accepting arbitrary `u64` values.

### Proof of Concept
Add a net test to `stackslib/src/net/api/tests/postfeerate.rs` (or equivalent) that:
1. Constructs a `FeeRateEstimateRequestBody` with a small valid hex `transaction_payload` (e.g., a token-transfer payload) and `estimated_len: Some(u64::MAX)`.
2. Sends it via `try_parse_request` directly (unit-level) or through the full HTTP handler stack to `/v2/fees/transaction`.
3. Asserts that `self.estimated_len` after parsing is clamped to a bounded value (e.g., `<= MAX_PAYLOAD_LEN`) rather than `u64::MAX`, and that `estimate_tx_fee_from_cost_and_length`'s `minimum_fee` computation does not wrap/panic — i.e., compare `RPCFeeEstimateResponse.estimations[i].fee` against a value consistent with `MINIMUM_TX_FEE_RATE_PER_BYTE * payload_data.len()` rather than a wrapped/near-zero result from `u64::MAX * MINIMUM_TX_FEE_RATE_PER_BYTE`.
4. On the current code, running with `RUSTFLAGS="-C overflow-checks=on"` (or a debug build) reproduces a panic at stackslib/src/net/api/postfeerate.rs:112; in release mode the test should assert the wrapped/incorrect `minimum_fee` value to demonstrate the corrupted output.
