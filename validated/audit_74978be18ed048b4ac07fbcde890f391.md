### Title
Exchange pool balance can be driven inconsistent/negative via floating-point Bancor math unless the `allowHardenExchangeCalculation` hard fork is active - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeTransactionActuator` lets any account swap tokens against a TRC10/TRX liquidity pool created by `ExchangeCreateActuator`. The pool's internal accounting (`firstTokenBalance`/`secondTokenBalance`) is updated purely from a floating-point relay-supply (Bancor-style) calculation. The code only checks that the resulting pool balances are non-negative when the chain-level `allowHardenExchangeCalculation` flag is enabled; when it is not, the pool's recorded balances can diverge from what it can actually pay out, mirroring the report's core issue of a contract's promised payouts exceeding its enforced backing.

### Finding Description
`ExchangeCapsule.transaction()` computes the counter-token amount using `ExchangeProcessor.exchange()`, which relies on `double`/`Maths.pow` floating point arithmetic: [1](#0-0) 

The resulting new balances are written back into the `ExchangeCapsule` unconditionally, and are only defensively checked for negativity when `hardenedCalc` is true: [2](#0-1) 

`ExchangeTransactionActuator` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` in both `doValidate()` and `execute()`, where `allowHarden()` simply reflects a `DynamicPropertiesStore` flag rather than any per-transaction guarantee: [3](#0-2) [4](#0-3) 

Unlike the `ExchangeCreate`/`ExchangeWithdraw` paths — which explicitly enforce `accountCapsule.getBalance()`/`assetBalanceEnoughV2` and (for withdraw) `firstTokenBalance < tokenQuant` sufficiency checks before mutating state — the transaction path only validates the *seller's* wallet has funds and that the buyer receives at least `tokenExpected`. It never independently confirms the pool's asset reserve is sufficient to cover `anotherTokenQuant` before crediting the buyer, i.e., the contract trusts its own floating-point derived bookkeeping rather than a hard reserve check, exactly the class of bug described in the report: state is updated to reflect a payout obligation without a corresponding enforced balance guarantee.

### Impact Explanation
If the double-precision Bancor computation and the pool's true reserves diverge (rounding/precision drift accumulated across many trades, or edge-case ratios), the `ExchangeCapsule`'s recorded `firstTokenBalance`/`secondTokenBalance` can end up understating what was actually paid out. Because these are the only source of truth used by subsequent `ExchangeWithdraw`/`ExchangeTransaction` calls, later legitimate participants (including the pool creator) can be left unable to withdraw or trade the token amounts the pool's own bookkeeping still claims to hold — funds effectively frozen or under-collateralized, matching the "contract might not have enough balance for winner/withdrawer to claim" impact category.

### Likelihood Explanation
Medium: this requires the `allowHardenExchangeCalculation` hard-fork flag to be inactive (its very existence, and the `StrictMathWrapper`/`hardenedCalc` guard added around this logic, indicates the java-tron team identified and patched exactly this floating-point precision risk). On any node/network where that feature has not been activated, any unprivileged account can trigger the vulnerable path simply by broadcasting ordinary `ExchangeTransactionContract` transactions against an existing pool — no special privilege needed.

### Recommendation
Enforce reserve-sufficiency checks in `ExchangeTransactionActuator`/`ExchangeCapsule.transaction()` unconditionally (not gated behind `allowHarden()`), and ensure the hardened, integer/BigInteger-safe calculation path (as already used in `ExchangeWithdrawActuator`'s `BigDecimal` precision checks) is the only code path, so the exchange pool's recorded balance can never be advanced beyond what it can actually pay out regardless of chain-parameter activation state.

### Proof of Concept
1. Deploy/observe an `Exchange` pool created via `ExchangeCreateContract` on a network/version where `allowHardenExchangeCalculation` is not yet activated (`allowHarden()` returns `false`).
2. Repeatedly broadcast `ExchangeTransactionContract` swaps chosen to maximize floating-point rounding drift in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (e.g., very small/very large disproportionate `sellTokenQuant` relative to pool balances).
3. Because `ExchangeCapsule.transaction()` only guards `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` when `hardenedCalc` is `true`, the non-hardened path applies the `double`-derived balances directly with no reserve-sufficiency cross-check against actual held assets.
4. Over many iterations the pool's recorded balances can end up inconsistent with what was truly received/paid, so a subsequent `ExchangeWithdrawContract`/`ExchangeTransactionContract` call by the pool creator or another trader (relying on `exchangeCapsule.getFirstTokenBalance()`/`getSecondTokenBalance()`) fails to be fully backed, demonstrating the pool cannot guarantee payout of its recorded obligations.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
