### Title
SSRF via `git://` (and SSH) remote URLs bypasses `http.followRedirects` disable, allowing internal git-daemon/SSH probing - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
Gitaly's `FetchRemote`/`CreateRepositoryFromURL` handlers set `http.followRedirects=false` only to stop HTTP 30x redirect-based SSRF, but they never validate or restrict the URL *scheme* of `RemoteParams.Url`. An attacker-controlled URL using `git://` (or `ssh://`, or SCP-like `user@host:path`) is passed unmodified into `remote.<name>.url` and fetched by `git fetch`, completely bypassing the HTTP-specific mitigation and allowing the Gitaly host to establish direct connections to arbitrary internal git-daemon or SSH endpoints.

### Finding Description
`validateFetchRemoteRequest` in [1](#0-0)  only checks that the repository is valid and that the URL is non-empty — it performs no scheme allowlisting (no rejection of `git://`, `ssh://`, or scp-like syntax).

`buildCommandOpts` then takes `req.GetRemoteParams().GetUrl()` directly and, when no `resolved_address` is supplied (which is the normal/optional case, entirely attacker/caller controlled), sets it verbatim as `remote.inmemory.url` without any scheme check: [2](#0-1) . Only when a `resolved_address` is present does `gitcmd.GetURLAndResolveConfig` run, and even then it recognizes `git://` as a valid, supported scheme (assigning it a default port of 9418) rather than rejecting it — see the scheme switch in `getURLAndResolveConfigForURL`: [3](#0-2) . The function `GetURLAndResolveConfig` itself dispatches `git://` to the same HTTP-based resolve path but ultimately still allows the underlying `git fetch` to use the native git protocol, and it explicitly supports `ssh://` and SCP-like syntax as well: [4](#0-3) .

The `http.followRedirects=false` config pair referenced in `command_description.go` only affects Git's `http`/`https` transport helper (`git-remote-http`); it has no effect whatsoever on the native `git://` protocol (handled by `git-daemon`/`git-remote-git`) or on `ssh://` transport (handled by `git-remote-ssh` / the `ssh` command). Since no code path anywhere in `fetch_remote.go` or `create_repository_from_url.go` restricts `RemoteParams.Url` to `http(s)` schemes, an attacker who controls `RemoteParams.Url` (via `FetchRemote` or `CreateRepositoryFromURL`, both reachable from unprivileged pull-mirror/import/fork configuration in GitLab Rails) can supply `git://127.0.0.1:9418/internal.git` or an internal `ssh://` target, and Gitaly's `git fetch`/`git clone` will connect directly to that endpoint — with the redirect-disabling protection providing no defense.

### Impact Explanation
This allows SSRF-class probing/reading of internal network services reachable from the Gitaly host over the `git://` protocol (any exposed `git-daemon`) or SSH, entirely bypassing the intended HTTP-redirect SSRF mitigation. An attacker can enumerate internal hosts/ports (via connection timing/errors) and, where a git-daemon or SSH git service is reachable, exfiltrate repository contents/refs from that internal service into their own Gitaly-hosted repository. This matches GitLab's SSRF impact class (unauthorized internal network access / internal service interaction) — though impact is bounded to git-protocol/SSH-speaking internal services and requires such an internal git-daemon/SSH endpoint to exist and be reachable from Gitaly.

### Likelihood Explanation
Fully exploitable by an unprivileged user with no special role: any user who can trigger a `FetchRemote` or `CreateRepositoryFromURL` request with an attacker-chosen `RemoteParams.Url`/`Url` (e.g., via "import project by URL", pull mirroring, or repository push-mirror configuration in GitLab, which pass through to these Gitaly RPCs) can supply a `git://` or `ssh://` URL. No resolved-address, admin privilege, or special configuration is required — the only precondition is that GitLab Rails/API forwards the user-supplied URL to Gitaly without independently blocking non-HTTP(S) schemes, which is consistent with the RPC's proto documentation stating support "Works with HTTP/HTTPS/Git/SSH protocols" [5](#0-4) .

### Recommendation
Enforce a scheme allowlist in `validateFetchRemoteRequest` (and the analogous validation in `create_repository_from_url.go`) that rejects any `RemoteParams.Url`/`Url` whose scheme is not explicitly permitted by policy (typically `http`/`https` only, or a small allowlist agreed upon with GitLab Rails), returning `InvalidArgument` for `git://`, `ssh://`, and bare/SCP-like URLs unless SSH-based mirroring is an intentionally supported, separately-vetted feature. If `git://` and `ssh://` must remain supported for legitimate mirroring, apply equivalent internal-network protections for those protocols (e.g., DNS-rebinding-safe resolved-address enforcement mandatory for all schemes, and integration with GitLab Rails' URL-blocker/allowlist for internal IP ranges) rather than relying solely on `http.followRedirects`.

### Proof of Concept
```go
func TestFetchRemote_GitProtocolSSRF(t *testing.T) {
    cfg, client := setupRepositoryService(t)
    ctx := testhelper.Context(t)

    // Simulate an internal git-daemon serving a sentinel repo on loopback.
    _, remoteRepoPath := gittest.CreateRepository(t, ctx, cfg)
    gittest.WriteCommit(t, cfg, remoteRepoPath, gittest.WithBranch("main"))
    port := gittest.GitDaemonServer(t, ctx, cfg, remoteRepoPath) // exports via `git daemon`

    repoProto, _ := gittest.CreateRepository(t, ctx, cfg)

    _, err := client.FetchRemote(ctx, &gitalypb.FetchRemoteRequest{
        Repository: repoProto,
        RemoteParams: &gitalypb.Remote{
            Url: fmt.Sprintf("git://127.0.0.1:%d/%s", port, filepath.Base(remoteRepoPath)),
        },
    })
    // Expected today: err == nil, fetch succeeds — proving http.followRedirects=false
    // provides no protection for the git:// scheme.
    require.NoError(t, err)
}
```
Expected/desired behavior after fix: `validateFetchRemoteRequest` should reject the `git://` URL with `InvalidArgument` before any connection is attempted.

```go
func buildCommandOpts(ctx context.Context, opts *localrepo.FetchOpts, req *gitalypb.FetchRemoteRequest) error {
	remoteURL := req.GetRemoteParams().GetUrl()
	var config []gitcmd.ConfigPair

	for _, refspec := range getRefspecs(req.GetRemoteParams().GetMirrorRefmaps()) {
		config = append(config, gitcmd.ConfigPair{
			Key: "remote.inmemory.fetch", Value: refspec,
		})
	}

	if resolvedAddress := req.GetRemoteParams().GetResolvedAddress(); resolvedAddress != "" {
		modifiedURL, resolveConfig, err := gitcmd.GetURLAndResolveConfig(remoteURL, resolvedAddress)
		if err != nil {
			return fmt.Errorf("couldn't get curloptResolve config: %w", err)
		}

		remoteURL = modifiedURL
		config = append(config, resolveConfig...)
	}

	config = append(config, gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL})
```

```go
func (s *server) validateFetchRemoteRequest(ctx context.Context, req *gitalypb.FetchRemoteRequest) error {
	if err := s.locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	if req.GetRemoteParams() == nil {
		return structerr.NewInvalidArgument("missing remote params")
	}

	if req.GetRemoteParams().GetUrl() == "" {
		return structerr.NewInvalidArgument("blank or empty remote URL")
	}

	return nil
}
```
