### Title
Per-IP QUIC connection rate limiter can be bypassed via handshake churn, allowing unstaked attacker to exhaust global `ClientConnectionTracker` slots - ([File: streamer/src/nonblocking/quic.rs])

### Summary
The per-IP connection rate limiter uses a check-then-act pattern split across two call sites: `ConnectionRateLimiter::is_allowed` is checked *before* `incoming.accept()` in `run_server`, while the actual token consumption (`register_connection`) only happens *after* the handshake completes in `setup_connection`. Because `is_allowed` never mutates state, an attacker who fires many QUIC initial packets from a single IP without completing the handshake can pass the per-IP check repeatedly and consume many `ClientConnectionTracker` slots (bounded only by the global `qos.max_concurrent_connections()`), well beyond `max_connections_per_ipaddr_per_min`.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:304-411`), each incoming connection is processed as follows: [1](#0-0) 
1. `rate_limiter.is_allowed(&incoming.remote_address().ip())` is checked — this is a **read-only** query against `KeyedRateLimiter`'s current token count and does not consume/decrement anything (`streamer/src/nonblocking/connection_rate_limiter.rs:34-40`). [2](#0-1) 
2. If allowed, a `ClientConnectionTracker` is created, consuming one of the global `qos.max_concurrent_connections()` slots (`streamer/src/nonblocking/quic.rs:371-379`, `ClientConnectionTracker::new` at `streamer/src/nonblocking/quic.rs:236-251`). [3](#0-2) 
3. `incoming.accept()` is called and `setup_connection` is spawned as a background task via `tasks.spawn(...)` — the main loop does **not** wait for this task and immediately continues to the next `select!` iteration (`streamer/src/nonblocking/quic.rs:384-399`).
4. Only inside `setup_connection`, after `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting).await` resolves with a successful handshake, is `rate_limiter.register_connection(&from.ip())` called, which actually decrements the token bucket (`streamer/src/nonblocking/quic.rs:471-493`). [4](#0-3) 

Because step 4 (the only mutating operation) only fires after a full, successfully-completed handshake, and step 3 dispatches handshake processing asynchronously without blocking the accept loop, an attacker can send many QUIC Initial packets from the same source IP in rapid succession and deliberately stall or abandon each handshake (e.g., never send the final handshake flight). Each such attempt:
- passes `is_allowed` (still returns `true` since no tokens have been consumed for that IP yet),
- consumes a `ClientConnectionTracker` slot immediately (bounded only by the global `qos.max_concurrent_connections()`, not by the per-IP limit),
- occupies that slot for up to the full `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` duration before being dropped and the tracker released.

This effectively decouples the intended per-IP admission control (`max_connections_per_ipaddr_per_min`, default 8/min) from the actual resource consumption gate, letting a single unstaked, unauthenticated IP claim a disproportionate share of the shared, global connection-slot pool that is meant to be fairly distributed/rate-limited across many IPs. The existing `overall_connection_rate_limiter` (a global token bucket, `MAX_CONNECTION_BURST`/`TOTAL_CONNECTIONS_PER_SECOND`) partially mitigates the *rate* of new incoming attempts server-wide, but does not restore per-IP fairness — a single attacker IP can still consume a large fraction of that global rate budget and the global slot pool before its own per-IP register-time limiter would ever trigger.

### Impact Explanation
This falls under the "unfair capture of QoS/connection slots, starving legitimate senders of TPU capacity" category referenced in the question. A single unstaked attacker IP can occupy a disproportionate number of `ClientConnectionTracker`/`max_concurrent_connections` slots for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, degrading the leader's ability to accept legitimate staked/unstaked connections during that window, i.e., a connection-slot-exhaustion / QoS-evasion DoS from a single IP that the per-IP limiter was specifically designed to prevent.

### Likelihood Explanation
Preconditions match the scope exactly: attacker needs only one IP, no stake, and reachability to the TPU/TPU-fwd QUIC port. The attack requires no protocol violation beyond simply not completing/delaying the QUIC handshake, which is trivial to script (open N `Connecting` futures / send N Initial packets and never advance them). It is fully repeatable — the attacker can refresh the burst every `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` window indefinitely. The only throttle on total volume is the global `overall_connection_rate_limiter`, which limits total incoming attempts across all IPs, not this specific IP's share.

### Recommendation
Consume the per-IP rate-limit token at accept time (before/at `incoming.accept()`), not at handshake completion, or reserve a token optimistically at check time and release it if the handshake never completes. Alternatively, track "pending handshake attempts per IP" separately with its own bounded cap enforced at the same point `is_allowed` is checked, so an IP cannot hold more than a small number of concurrent unconfirmed connection attempts regardless of handshake completion.

### Proof of Concept
Integration test plan (extends the existing `streamer/src/nonblocking/connection_rate_limiter.rs` test module and `run_server` integration tests):
1. Configure `QuicStreamerConfig { max_connections_per_ipaddr_per_min: N, .. }` with small `N` (e.g., 2) and a `qos.max_concurrent_connections()` set much larger (e.g., 100).
2. From a single test client IP, open `M > N` (e.g., 20) parallel QUIC `Connecting` futures within `< WAIT_FOR_CONNECTION_TIMEOUT`/`QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, deliberately not completing the TLS handshake (e.g., drop the client endpoint before finishing, or use a custom transport that stalls after sending Initial).
3. Assert via `stats.outstanding_incoming_connection_attempts` / `stats.open_connections` (exposed via `StreamerStats`) that more than `N` connection attempts from the single IP were simultaneously admitted into `ClientConnectionTracker` (i.e., `open_connections` count from one IP exceeds `max_connections_per_ipaddr_per_min`), demonstrating that `is_allowed` failed to bound concurrent unconfirmed attempts per IP.
4. Expected (failing) assertion: `open_connections_from_single_ip <= max_connections_per_ipaddr_per_min` — the PoC should show this assertion is violated, confirming the TOCTOU gap between `is_allowed` and `register_connection`.

    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
