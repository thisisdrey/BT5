Audit Report

## Title
`Pallet::unbond` computes unbonding balance from stale point/balance ratio without applying pending slash - (File: substrate/frame/nomination-pools/src/lib.rs)

## Summary
`pallet-nomination-pools`, under the `DelegateStake` strategy, tracks slashes lazily via `T::StakeAdapter::pending_slash(pool)`, but the pool's point↔balance ratio (`bonded_pool.points` vs. underlying active stake) is only corrected when `do_apply_slash` runs. `withdraw_unbonded` defensively calls `do_apply_slash` before computing withdrawal amounts, but the sibling `unbond` extrinsic does not, allowing a member to dissolve points into balance using a stale pre-slash ratio.

## Finding Description
`unbond` at [1](#0-0)  calls `Self::get_member_with_pools`, `bonded_pool.ok_to_unbond_with`, reward payout, and then directly `bonded_pool.dissolve(unbonding_points)` to compute `unbonding_balance`, followed by `T::StakeAdapter::unbond`. There is no call to `Self::do_apply_slash` anywhere in this path. By contrast, `withdraw_unbonded_other_with_state` explicitly calls `Self::do_apply_slash(&member_account, None, false)` before computing withdrawal amounts, treating `NothingToSlash` as an expected, tolerable case but otherwise aborting defensively. Because `pending_slash` on the pool's stake account can become non-zero as soon as an offence is reported (before any permissionless `apply_slash` call executes), `bonded_pool.points`/active stake used by `dissolve` in `unbond` can reflect a pre-slash ratio. `member_pending_slash` at [2](#0-1)  confirms that the member-level slash amount is derived from the discrepancy between `actual_balance` (via `StakeAdapter::member_delegation_balance`) and `expected_balance` (`pool_member.total_balance()`), a discrepancy that only closes once `do_apply_slash` runs.

## Impact Explanation
This allows an unbonding member to lock in a favorable pre-slash exchange rate into `SubPoolsStorage`, effectively transferring the economic burden of a reported slash onto remaining or later-unbonding members. This breaks the "settle exactly once, pro-rata, to the correct amount" invariant for staking/asset accounting — a legitimate value-conservation violation matching the required impact category of runtime behavior compromising intended settlement correctness.

## Likelihood Explanation
The precondition (a slash reported/pending but not yet applied via `apply_slash`) is normal, expected transient runtime state — the codebase's own comment on `withdraw_unbonded` acknowledges pending slash may not have been applied yet. Any unprivileged pool member can call the public `unbond` extrinsic at any time, including in the window between a slash being reported and `apply_slash` being called by anyone, requiring no special privilege — only timing.

## Recommendation
Add a call to `Self::do_apply_slash(&member_account, None, false)` (tolerating `Error::<T>::NothingToSlash`) near the start of `unbond`, before `bonded_pool.dissolve` and `T::StakeAdapter::unbond` are invoked, mirroring the defensive sync already performed in `withdraw_unbonded`.

## Proof of Concept
1. Configure a pool using the `DelegateStake` strategy; member Alice holds `points` worth balance `X`.
2. Trigger an offence causing a slash against the pool's stash account, so `T::StakeAdapter::pending_slash(pool)` becomes non-zero, but do not call `apply_slash`.
3. Have Alice call `unbond` (`substrate/frame/nomination-pools/src/lib.rs:2257-2296`). Observe that `bonded_pool.dissolve(unbonding_points)` computes `unbonding_balance` from the pre-slash ratio, since no `do_apply_slash` call occurs in this path.
4. Later call `apply_slash` for the pool; verify remaining members' recorded balances absorb a disproportionately larger share of the slash than they would have if Alice's unbond had been computed post-slash, and compare against `withdraw_unbonded`'s explicit `do_apply_slash` call at `substrate/frame/nomination-pools/src/lib.rs:2417-2432`, which prevents the same issue for withdrawals.

		// only executed in tests: ensure the member account is correct.

		let pool_account = Pallet::<T>::generate_bonded_account(pool_member.pool_id);
		// if the pool doesn't have any pending slash, it implies the member also does not have any
		// pending slash.
		if T::StakeAdapter::pending_slash(Pool::from(pool_account.clone())).is_zero() {
			return Ok(Zero::zero());
		}

		// this is their actual held balance that may or may not have been slashed.
		let actual_balance = T::StakeAdapter::member_delegation_balance(member_account)
			// no delegation implies the member delegation is not migrated yet to `DelegateStake`.
			.ok_or(Error::<T>::NotMigrated)?;

		// this is their balance in the pool
		let expected_balance = pool_member.total_balance();

		// return the amount to be slashed.
		Ok(actual_balance.saturating_sub(expected_balance))
	}
