### Title
Active-permission holders can rewrite an account's Owner permission via `AccountPermissionUpdateContract`, enabling full ownership takeover - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator` treats any valid "Active" multisig permission whose operations bitmap includes the `AccountPermissionUpdateContract` bit as sufficient authorization to rewrite the account's entire permission structure — including the Owner permission itself — with no requirement that the transaction actually satisfy Owner-level control or preserve the legitimate owner's keys. This mirrors the AVideo bug class: a narrow-purpose permission (an Active key meant only to authorize specific contract types) is reused by an actuator as a blanket gate for a far more powerful, security-critical action (full ownership/permission reassignment), creating an authorization boundary that is asymmetric with the account's real intent.

### Finding Description
Signature/permission checking for any contract is generic and keyed only on `permissionId` and the `Active` permission's `operations` bitmap: [1](#0-0) 

and [2](#0-1) 

Both simply check: is `permissionId != 0`? If so, is the permission type `Active`, and does its 32-byte `operations` bitmap have the bit set for `contract.getTypeValue()`? There is no special case anywhere in this path that treats `AccountPermissionUpdateContract` (a contract type that can rewrite Owner/Witness/Active permissions) differently from a narrow-scope contract type like `TransferContract` or `AssetIssueContract`.

`AccountPermissionUpdateActuator.validate()` then only checks *structural* correctness of the submitted `Owner`/`Witness`/`Active` permissions (key counts, weights, threshold, distinct addresses, valid contract-type bits) — it never checks that the signer holds Owner-level authority, nor that the new Owner permission still includes the previous owner's keys: [3](#0-2) 

`execute()` then unconditionally overwrites all permissions on the account with whatever was submitted: [4](#0-3) 

So if an account owner ever grants an `Active` permission (e.g., intended only to let a low-trust key sign `AssetIssueContract` or `TransferContract` transactions) whose `operations` bitmap also happens to include the bit for `AccountPermissionUpdateContract` — whether by owner mistake, a buggy wallet UI, or a deliberately crafted "innocuous-looking" permission template — the holder of that single Active key can submit an `AccountPermissionUpdateContract` transaction that replaces the account's `Owner` permission with a permission containing only the attacker's own key and a low threshold. This is the exact analog of the AVideo flaw: `Permissions::canModerateVideos()` (a narrow, documented-as-limited permission) was reused by `videoAddNew.json.php` as an authorization gate for full video edit/ownership transfer, exceeding its documented scope and letting a "moderator" achieve owner-equivalent control. Here, an `Active` permission (documented/intended as scoped to specific contract types for day-to-day operations) is reused by the same generic gate to authorize the single most powerful account operation — full permission/ownership rewrite — with no differentiation of privilege level required for that specific contract type.

### Impact Explanation
Once the attacker's Active key rewrites the Owner permission, they gain unilateral control of the account: they can subsequently sign any transaction as Owner (permissionId 0), including transferring all TRX/TRC10/TRC20 balances, withdrawing rewards, unfreezing/undelegating resources, voting, or issuing further permission changes — effectively a full, permanent account takeover. This satisfies "concrete unauthorized account operation / theft of funds" since the attacker obtains unrestricted signing authority over the victim account's assets and votes with only a single, narrowly-scoped Active key that the account owner believed was limited to specific, low-impact contract types.

### Likelihood Explanation
Exploitation requires only that some existing Active permission on the account has the `AccountPermissionUpdateContract` bit set in its `operations` bitmap — a configuration mistake or oversight that is easy to make given wallets/tools often construct operations bitmaps programmatically (e.g., by enabling broad categories of "commonly used" contract types) and given the actuator provides no warning or restriction when this bit is included. Any single-key Active permission with just this bit reachable, and threshold satisfiable by that one key, allows the attack in a single signed transaction from an otherwise unprivileged token holder — no special node/witness/committee access needed.

### Recommendation
- Special-case `AccountPermissionUpdateContract` (and any other contract type capable of rewriting `Owner`/`Witness` permissions) in `TransactionCapsule.checkPermission` / `TransactionUtil.checkPermissionOperations` so that it can only ever be authorized via `permissionId == 0` (the Owner permission), regardless of whether an Active permission's bitmap happens to include that bit.
- In `AccountPermissionUpdateActuator.validate()`, explicitly reject `AccountPermissionUpdateContract` transactions unless the signing permission used is Owner, and/or require that the new Owner permission cannot be submitted by a non-Owner signer at all.
- Consider rejecting attempts to set the `AccountPermissionUpdateContract` bit inside any `Active` permission's operations bitmap at validation time, since granting it is equivalent to granting full account ownership and should not be representable as a "scoped" Active permission.

### Proof of Concept
1. Victim account owner creates an `Active` permission (e.g., named "AssetOps") with one key belonging to a semi-trusted party, intending it to authorize only `AssetIssueContract`/`TransferAssetContract` operations, but the operations bitmap (built via a script/tool) also has the bit for `AccountPermissionUpdateContract` set (contract type value corresponding bit in the 32-byte bitmap, per `TransactionUtil.checkPermissionOperations` at line 178).
2. Attacker (holder of that Active key) crafts and signs an `AccountPermissionUpdateContract` transaction with `permissionId` set to the Active permission's id, setting:
   - `owner` = a new `Permission` of type `Owner` containing only the attacker's key with threshold satisfied by that one key,
   - `actives`/`witness` as required minimally to pass `AccountPermissionUpdateActuator.validate()` structural checks.
3. Broadcast the transaction. `TransactionCapsule.checkPermission` (line 635-645) and `TransactionUtil.checkPermissionOperations` (line 171-180) pass because the bit for `AccountPermissionUpdateContract` is set in the attacker's Active permission's operations bitmap; `AccountPermissionUpdateActuator.execute()` (line 34-69) then overwrites the account's Owner permission with the attacker-controlled one.
4. Attacker now signs subsequent transactions with `permissionId = 0` as the sole Owner and transfers out all account balances/resources — full account takeover from what was intended to be a narrowly scoped Active key.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

  @Override
  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule result = (TransactionResultCapsule) object;
    if (Objects.isNull(result)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    long fee = calcFee();
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);

      byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
      AccountCapsule account = accountStore.get(ownerAddress);
      account.updatePermissions(accountPermissionUpdateContract.getOwner(),
          accountPermissionUpdateContract.getWitness(),
          accountPermissionUpdateContract.getActivesList());
      accountStore.put(ownerAddress, account);

      adjustBalance(accountStore, ownerAddress, -fee);
      if (chainBaseManager.getDynamicPropertiesStore().supportBlackHoleOptimization()) {
        chainBaseManager.getDynamicPropertiesStore().burnTrx(fee);
      } else {
        adjustBalance(accountStore, accountStore.getBlackhole(), fee);
      }

      result.setStatus(fee, code.SUCESS);
    } catch (BalanceInsufficientException | InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      result.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }

    return true;
  }

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
  }
