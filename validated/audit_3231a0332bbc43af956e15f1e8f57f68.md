### Title
Lack of access control in `Loans.pay` allows attacker to pull USDC from any borrower - ([File: tare-io__tare-contracts/contracts/Loans.sol](tare-io__tare-contracts/contracts/Loans.sol))

### Summary
The `Loans.pay` function lacks a check to ensure that the `amount` of tokens being transferred is authorized by the `borrower`. While the function is restricted to the borrower or an admin, it pulls funds from the `borrowers[loanId]` address regardless of who the caller is. If an admin or a compromised admin account calls `pay` with a specific `loanId`, they can force a transfer of USDC from that loan's borrower to the `Loans` contract, even if the borrower did not intend to make a payment at that time.

### Finding Description
In `Loans.sol`, the `pay` function is designed to allow borrowers to repay their loans. It uses the `onlyBorrowerOrAdmin(loanId)` modifier, which permits either the registered borrower or a protocol admin/guardian to trigger the call. [1](#0-0) 

The implementation then calls the internal `_deposit` function, passing `borrowers[loanId]` as the `from` address. [2](#0-1) 

The `_deposit` function (inherited from `LoansLedger.sol`) executes `currency.safeTransferFrom(from, address(this), uint256(int256(amount)))`. 

The root cause is identical to the seed report: the `from` address is used in a `safeTransferFrom` call without verifying that the `msg.sender` has the authority to spend those specific funds, other than the broad `onlyBorrowerOrAdmin` check. While the borrower can call it themselves, the `Admin` role can also call it to pull funds from the borrower's wallet into the protocol's cash account (`ACC_BORROWER_PAYMENT_CLEARING`) as long as the borrower has granted an ERC20 allowance to the `Loans` contract.

### Impact Explanation
An admin can unilaterally move USDC from a borrower's wallet into the protocol. While the funds remain within the protocol's ledger assigned to that loan, this constitutes an unauthorized reassignment of assets and a permission bypass. In a decentralized protocol, an admin should not have the power to "force-pull" unlimited funds from users' wallets simply because they approved the contract for legitimate repayments. This violates the principle of least privilege and can be used to grief borrowers or manipulate ledger balances.

### Likelihood Explanation
The likelihood is medium. It requires the attacker to have `ADMIN_ROLE` or `GUARDIAN_ROLE`. However, the Tare protocol's security model (as seen in `RESEARCHER.md` and `SmartAccountFactory.sol`) emphasizes that even privileged roles should be bound by strict invariants. The ability for an admin to trigger a `transferFrom` on a user's wallet without a specific signature or intent for that transaction is a classic access control vulnerability.

### Recommendation
Modify the `pay` function to ensure that if the caller is an admin, they can only move funds that the borrower has explicitly authorized for that specific transaction, or restrict the `from` address to `msg.sender` so that only the party providing the funds can trigger the transfer.

```solidity
function pay(uint64 loanId, int128 amount, ...) external {
    // ...
    _deposit(loanId, ..., msg.sender, ...); // Pull from caller instead of stored borrower
}
```

### Proof of Concept
1. A Borrower creates a loan and approves the `Loans` contract for 1,000,000 USDC (intending to pay over time).
2. The Loan is `Active`.
3. An Actor with `ADMIN_ROLE` calls `Loans.pay(loanId, 1_000_000, block.timestamp, "0x...")`.
4. The `onlyBorrowerOrAdmin` modifier passes because the caller is an Admin.
5. The contract executes `currency.safeTransferFrom(borrowers[loanId], address(this), 1_000_000)`.
6. 1,000,000 USDC is pulled from the Borrower's wallet without their consent. [3](#0-2)
