### Title
Bridged-in supply cap on `SyntheticToken._mint` turns inbound LayerZero transfers into stuck failed messages - ([File: contracts/SyntheticToken.sol](contracts/SyntheticToken.sol))

### Summary
The Avahi bug class is an unprivileged user reaching an assertion by requesting a feature path (`AVAHI_LOOKUP_USE_WIDE_AREA`) that is effectively disabled/unsupported, crashing the daemon. The Metronome analog is the bridge-receive path: `ProxyOFT._creditTo` calls `SyntheticToken.mint`, and `_mint` hard-reverts with `SurpassMaxBridgingSupply` whenever the net bridged-in supply would exceed the governor-set `maxBridgedInSupply` cap [1](#0-0) . Because `ProxyOFT` inherits `NonblockingLzAppUpgradeable`, the failed delivery is not reverted at the endpoint — it is caught by `excessivelySafeCall` and stored in `failedMessages` [2](#0-1) . An unprivileged attacker can saturate the cap so that *other users'* inbound bridge transfers deterministically fail and remain stuck.

### Finding Description
On the receiving chain, `lzReceive` → `_blockingLzReceive` → `nonblockingLzReceive` → `_sendAck` → `_creditTo` → `syntheticToken.mint(to, amount)` [3](#0-2) . In `_mint`, when the caller is the ProxyOFT, `totalBridgedIn += amount_` is applied and the transaction reverts if `bridgedInSupply() > maxBridgedInSupply`, where `bridgedInSupply() = totalBridgedIn - totalBridgedOut` [4](#0-3) . `maxBridgedInSupply` is a finite, governor-configured cap (deployed configs set it well below `type(uint256).max`).

Attack path from an unprivileged account:

1. On a source chain where the synth's pool is active, deposit collateral into a `DepositToken` and call `DebtToken.issue` to mint synths natively on that chain (no bridging history required).
2. Call `ProxyOFT.sendFrom` on the source chain, bridging the synths to the victim chain and to the attacker's own address. This mints on the victim chain, increasing `totalBridgedIn` there.
3. Repeat/scale until `bridgedInSupply() == maxBridgedInSupply` on the victim chain (or bridge in an amount so that `bridgedInSupply + victimPendingAmount > cap`).
4. Any subsequent legitimate user bridging the same synth into that chain has their message fail inside `_mint` with `SurpassMaxBridgingSupply`, get stored in `failedMessages`, and the user's tokens are burned on the source chain but never credited on the destination.

Retries via `retryMessage` re-execute `_nonblockingLzReceive` and revert again as long as the cap is saturated [5](#0-4) . The attacker can maintain the freeze by keeping their bridged-in balance parked; the freeze only lifts when net outflows (`totalBridgedOut` growing via other `sendFrom` burns) reduce `bridgedInSupply`, or the governor raises `maxBridgedInSupply`.

No modifier prevents this: `_creditTo`/`mint` have no pause check on the receive path (only `_debitFrom` checks `isBridgingActive`/`isDestinationChainSupported` [6](#0-5) ), and `onlyIfCanMint` passes because the caller is the legitimate ProxyOFT.

### Impact Explanation
Temporary freezing of victims' bridged funds. Tokens are burned on the source chain while the credit on the destination chain is stored as a failed message that cannot be retried until the cap condition clears. Duration is attacker-controllable (they can keep topping up the cap as outflows occur) and recovery requires either organic bridge-out volume or a governor cap increase. This matches the "temporary freezing of funds" impact class.

### Likelihood Explanation
Requires an unprivileged attacker to (a) hold or mint synths on a source chain — possible via normal `deposit` + `issue` — and (b) bridge them in, incurring LZ fees and locking collateral. The cap saturation is bounded by `maxBridgedInSupply - bridgedInSupply`; for synths with tight caps this is cheap. It is griefing (no direct profit), which lowers motivation but keeps it well within the unprivileged-threat model. The layered defense (`NonblockingLzApp`) actually makes the failure persistent rather than atomic, which is what converts a per-transaction revert into a queue of stuck messages.

### Recommendation
- Treat cap overflow on the receive path as creditable-but-deferred instead of reverting: e.g., mint only up to remaining cap and escrow the excess, or have `_creditTo` catch `SurpassMaxBridgingSupply` and park tokens in the ProxyOFT for later pull-claim by the recipient.
- Alternatively, let `retryMessage` partially settle, and/or allow the stored failed message to be resolved permissionlessly by routing the minted amount to a claimable balance rather than re-executing the same reverting `_mint`.
- Monitor `MessageFailed` events and auto-raise/alarm on `maxBridgedInSupply` saturation.

### Proof of Concept
Foundry fork sketch (victim chain fork, e.g., mainnet):

```solidity
// setup: msUSD SyntheticToken + ProxyOFT on dst chain, pool on src chain
// 1) On src fork: attacker deposits vaUSDC, issues msUSD, calls
//    proxyOFT_src.sendFrom(attacker, DST_CHAIN_ID, attacker, fillAmt)
//    where fillAmt >= maxBridgedInSupply - bridgedInSupply on dst.
//    Deliver via lzEndpoint.receivePayload(...) → mint succeeds, cap now full.
// 2) Victim on src calls proxyOFT_src.sendFrom(victim, DST_CHAIN_ID, victim, vAmt)
//    → tokens burned on src (totalBridgedOut_src += vAmt).
// 3) Deliver victim's packet on dst: _blockingLzReceive catches revert
//    SurpassMaxBridgingSupply → failedMessages[chain][src][nonce] set;
//    victim balance unchanged.
// 4) proxyOFT_dst.retryMessage(...) reverts again while cap saturated.
//    Assert victim funds are unrecoverable until attacker bridges out or
//    governor calls updateMaxBridgedInSupply.
```

The existing test `test/foundry/CrossChains.t.sol` already demonstrates payload delivery via `lzEndpoint.receivePayload`, so only the cap-saturation step and the `failedMessages` assertion need to be added. Note: whether the attack is economically practical depends on the deployed `maxBridgedInSupply` values per synth/chain; on chains where the cap is `type(uint256).max` or far above circulation, the attack is not reproducible — that parameter check is a prerequisite in the PoC.

```text
    function retryMessage(uint16 _srcChainId, bytes calldata _srcAddress, uint64 _nonce, bytes calldata _payload) public payable virtual {
        // assert there is message to retry
        bytes32 payloadHash = failedMessages[_srcChainId][_srcAddress][_nonce];
        require(payloadHash != bytes32(0), "NonblockingLzApp: no stored message");
        require(keccak256(_payload) == payloadHash, "NonblockingLzApp: invalid payload");
        // clear the stored message
        failedMessages[_srcChainId][_srcAddress][_nonce] = bytes32(0);
        // execute the message. revert if it fails again
        _nonblockingLzReceive(_srcChainId, _srcAddress, _nonce, _payload);
        emit RetryMessageSuccess(_srcChainId, _srcAddress, _nonce, payloadHash);
```
