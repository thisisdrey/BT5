### Title
Pingback handshake verification checks only the public-key hash, not the reported address, allowing an attacker to bind a forged victim IP:port to their own key in the peer frontier DB - (File: stackslib/src/net/neighbors/walk.rs)

### Summary
`NeighborWalk::check_handshake_pubkey_hash` (stackslib/src/net/neighbors/walk.rs:1663-1680) only validates that the `HandshakeAcceptData.handshake.node_public_key` hashes to the expected `naddr.public_key_hash`; it never checks that `handshake.addrbytes`/`handshake.port` match the address the node actually pingback-probed (`naddr`). `pingback_handshakes_try_finish` then passes `&data.handshake` straight into `add_or_schedule_replace_neighbor`, which persists the self-reported (attacker-controlled) address into the peer database.

### Finding Description
The pingback flow exists to confirm that a self-reported inbound peer address is truly reachable by whoever holds the claimed private key: the node connects out to `naddr` (an address an inbound peer previously claimed to have) and expects a signed `HandshakeAccept` back [1](#0-0) .

When the reply arrives, `pingback_handshakes_try_finish` extracts `data` from `HandshakeAccept`/`StackerDBHandshakeAccept` and calls `check_handshake_pubkey_hash(&peer_nk, data, &naddr)` before persisting the neighbor: [2](#0-1) 

`check_handshake_pubkey_hash` computes `Hash160::from_node_public_key_buffer(&data.handshake.node_public_key)` and compares it only to `naddr.public_key_hash` - it never compares `data.handshake.addrbytes`/`data.handshake.port` to `naddr.addrbytes`/`naddr.port`: [3](#0-2) 

Once this passes, `add_or_schedule_replace_neighbor` calls `Neighbor::load_and_update(&tx, preamble.peer_version, preamble.network_id, handshake)`, where `handshake` is `&data.handshake` — the self-reported struct from the reply, not the originally-probed `naddr`: [4](#0-3) 

The signature-verification path for a fresh session (`validate_handshake` in chat.rs) only checks that a self-reported `addrbytes`/`port` matches the *socket* peer address for the `Handshake` message type on established outbound sockets with a *known* prior public key; it is not applied to `HandshakeAccept` payloads received in reply to our own outbound handshake, and in any case it only guards the raw TCP peer's declared address against the raw TCP peer's actual socket - it does nothing to bind `naddr` to `data.handshake.addrbytes/port` in the pingback code path: [5](#0-4) 

Exploit flow:
1. Attacker owns a keypair `K` (hash `H`) and a reachable address `A` (their own listening socket). They connect inbound and self-report `A` in a `Handshake`, causing the node to later schedule a pingback probe to `naddr = {addrbytes: A, port: A_port, public_key_hash: H}`.
2. The node's pingback machinery connects out to `A` and sends a fresh `Handshake`.
3. The attacker's listener at `A` replies with a `HandshakeAccept` (or `StackerDBHandshakeAccept`) whose `handshake.node_public_key = K` (so the hash still equals `H`, satisfying `check_handshake_pubkey_hash`) but whose `handshake.addrbytes`/`handshake.port` are set to an arbitrary third-party victim `V:P_v`. The attacker signs this message with their own private key `K`, so the signature check succeeds - no forgery of cryptographic material is required.
4. `check_handshake_pubkey_hash` returns `true` since it only checks the hash, and `add_or_schedule_replace_neighbor` stores/updates a `Neighbor` keyed by `handshake.addrbytes/port = V:P_v` with public key `K` into the peer DB.

The equality the design is supposed to guarantee - "the network address stored for pubkey-hash `H` == the address that was actually pingback-probed and answered" - is broken, because storage uses the self-reported field inside the payload rather than the previously-probed `naddr`.

### Impact Explanation
The attacker unauthenticatedly writes a forged `(pubkey_hash=H, addr=V:P_v)` binding into the local node's peer frontier DB, where `V:P_v` is an address the attacker does not control. Since this record is a legitimate-looking `Neighbor` entry, it will subsequently be served to other peers via peer-discovery (`GetNeighbors`/`Neighbors`) responses, causing other nodes across the network to attempt outbound connections toward the victim `V:P_v`, misdirecting P2P traffic and polluting frontier data network-wide. This is repeatable per pingback cycle and per victim target chosen by the attacker, matching the Critical category "unauthenticated write to state" and "network-wide propagation of forged data."

### Likelihood Explanation
Preconditions are met by an ordinary unprivileged remote attacker: they need only (a) make an inbound P2P connection to the target node and self-report a reachable address `A` they control, and (b) run a listener at `A` that answers the resulting pingback `Handshake` with a crafted `HandshakeAccept` bearing their own valid key/signature but forged `addrbytes`/`port`. No secrets, privileged roles, or victim cooperation are needed, and the P2P port is remotely reachable by design. The attack is fully repeatable and can target any chosen victim IP:port per pingback cycle.

### Recommendation
In `check_handshake_pubkey_hash` (or immediately before calling `add_or_schedule_replace_neighbor` in `pingback_handshakes_try_finish`), also require that `data.handshake.addrbytes == naddr.addrbytes && data.handshake.port == naddr.port` (respecting the same any-net exception logic already used in `validate_handshake`), rejecting/logging mismatches instead of persisting them. Persist the neighbor using the originally-probed `naddr` address rather than trusting `data.handshake.addrbytes/port` for pingback-derived neighbors.

### Proof of Concept
Rust test in `stackslib::net::neighbors::walk` (or a new integration test alongside existing walk tests):
1. Construct a `NeighborAddress naddr` with `public_key_hash = H` (hash of a test keypair `K`) and `addrbytes/port = A`.
2. Build a `HandshakeAcceptData` whose `handshake.node_public_key = K` (so hash matches `H`) but `handshake.addrbytes/port = V` (a different address than `A`).
3. Call `NeighborWalk::check_handshake_pubkey_hash(&peer_nk, &data, &naddr)` and assert it returns `true`.
4. Call `self.neighbor_db.add_or_schedule_replace_neighbor(network, &preamble, &data.handshake, None, &mut replacements)`.
5. Load the resulting `Neighbor` from the peer DB (or from the returned tuple) and assert `neighbor.addr.addrbytes/port == V`, not `A` — demonstrating the forged victim address was stored under the attacker's legitimately-hashing public key.

    /// Does a given handshakedata represent an expected public key hash?
    fn check_handshake_pubkey_hash(
        nk: &NeighborKey,
        data: &HandshakeAcceptData,
        naddr: &NeighborAddress,
    ) -> bool {
        let neighbor_pubkey_hash =
            Hash160::from_node_public_key_buffer(&data.handshake.node_public_key);
        if neighbor_pubkey_hash != naddr.public_key_hash {
            debug!(
                "Neighbor {:?} had an unexpected pubkey hash: expected {:?} != {:?}",
                nk, &naddr.public_key_hash, &neighbor_pubkey_hash
            );
            return false;
        }

        true
    }
