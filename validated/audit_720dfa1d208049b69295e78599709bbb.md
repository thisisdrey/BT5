### Title
Unvalidated Archive Extraction in `CreateRepositoryFromSnapshot` Allows Path Traversal / Tar Extraction Escape - (File: internal/gitaly/service/repository/create_repository_from_snapshot.go)

### Summary
`CreateRepositoryFromSnapshot` fetches an archive from a caller-supplied HTTP URL and pipes it directly into `tar -C <path> -xvf -` without any validation of the archive's contents or entry paths.

### Finding Description
Analogous to the reported "insufficient validation of `initialize` arguments" bug class — where user-controlled parameters are consumed by a privileged initialization routine without sanity checks — `CreateRepositoryFromSnapshot`'s `untar` helper takes the caller-provided `HttpUrl`/`HttpAuth`/`ResolvedAddress` fields, downloads whatever content the remote endpoint returns, and extracts it straight into the newly created repository directory using the system `tar` binary with no allow-list, no path-prefix check, and no rejection of `../` entries, symlinks, or absolute paths inside the archive: [1](#0-0) 
The developers' own comment acknowledges the gap explicitly: [2](#0-1) 
The only checks performed before extraction are on the *target* repository (`ValidateRepository`) and on the resolved IP format of the HTTP address — none constrain what the archive itself may contain: [3](#0-2) [4](#0-3) 
This mirrors the "unsafe initialization" pattern in the external report: a routine that establishes the initial state of a resource (there, a smart contract; here, a Gitaly repository directory) trusts caller-supplied input without validating it, and the action can only be performed once per resource (repository creation), so there is no natural place to re-validate afterward.

### Impact Explanation
Because `tar` is invoked with default (non-restrictive) extraction semantics, a malicious or compromised HTTP endpoint returning the archive (reachable via `HttpUrl`, and via `ResolvedAddress` for DNS-rebinding mitigation only, not content validation) can include entries with `../` relative paths or absolute paths/symlinks to write files outside of the intended repository directory (`path`). This is a classic tar-extraction path-traversal issue that can lead to arbitrary file write/overwrite on the Gitaly node's filesystem — a storage escape outside of the newly created repository's directory tree, and a potential root for further compromise (e.g., overwriting hooks, config files elsewhere on disk).

### Likelihood Explanation
`CreateRepositoryFromSnapshot` is a `MUTATOR` RPC callable through the standard `RepositoryService`, and it is present in the `repositoryCreatingRPCs` set that the storage transaction middleware handles specially for repository creation: [5](#0-4) 
Any client able to invoke this RPC (whether internal migration tooling or, in a misconfigured/compromised environment, an ordinary authenticated caller as flagged by the code comment "before pointing this RPC at endpoints not under our control, it should undergo a lot of hardening") controls the `HttpUrl` fully, making the content of the returned archive attacker-influenced whenever the target HTTP endpoint is untrusted or compromised.

### Recommendation
- Do not shell out to system `tar` on untrusted archive content. Use a Go tar reader that explicitly validates each header's `Name` (reject `..`, absolute paths, and symlinks/hardlinks pointing outside the destination) before writing.
- Clean and verify the resolved path for every entry is contained within `path` (the target repository directory) before extraction, analogous to `storage.ValidateRelativePath` already used elsewhere in the locator.
- Restrict which callers may invoke `CreateRepositoryFromSnapshot` to trusted internal services, and/or restrict `HttpUrl` targets to an allow-list, complementing the existing DNS-rebinding mitigation (`ResolvedAddress`).

### Proof of Concept
1. Host an HTTP endpoint that returns a tar stream containing an entry such as `../../../etc/cron.d/evil` (or a symlink entry pointing outside the target directory followed by a regular file write through that symlink).
2. Call `CreateRepositoryFromSnapshot` with `HttpUrl` pointing at that endpoint and a `Repository` target.
3. `untar` pipes the response directly into `tar -C <repoPath> -xvf -`; since neither Gitaly nor its `tar` invocation restricts entry paths, the malicious entry is written outside `repoPath`, demonstrating the extraction escape.

Note: I could not verify from the indexed code whether any additional gRPC interceptor (e.g., an internal-only auth policy) restricts callers of `CreateRepositoryFromSnapshot` beyond the standard Gitaly auth token, since that would require inspecting deployment-specific server registration/interceptor configuration not fully covered in the available index.

func newResolvedHTTPClient(httpAddress, resolvedAddress string) (*http.Client, error) {
	url, err := url.ParseRequestURI(httpAddress)
	if err != nil {
		return nil, structerr.NewInvalidArgument("parsing HTTP URL: %w", err)
	}

	port := url.Port()
	if port == "" {
		switch url.Scheme {
		case "http":
			port = "80"
		case "https":
			port = "443"
		default:
			return nil, structerr.NewInvalidArgument("unsupported schema %q", url.Scheme)
		}
	}

	// Sanity-check whether the resolved address is a valid IP address.
	if net.ParseIP(resolvedAddress) == nil {
		return nil, structerr.NewInvalidArgument("invalid resolved address %q", resolvedAddress)
	}
