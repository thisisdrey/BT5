### Title
Public `register_token`/`add_tip` extrinsics swap the caller's tip/fee asset with no slippage protection - ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

### Summary
`Pallet::swap_and_burn` in `snowbridge-pallet-system-frontend` calls `pallet_asset_conversion`'s `Swap::swap_exact_tokens_for_tokens` and hardcodes `amount_out_min` to `None`, explicitly commented `// No minimum amount required`. This is invoked from the public, unprivileged extrinsics `register_token` and `add_tip` whenever the caller pays with a non-Ether fee/tip asset, mirroring exactly the UniswapV3 `amountOutMinimum = 0` bug from the external report.

### Finding Description
`swap_fee_asset_and_burn` is reached from two public, signed extrinsics: `register_token` [1](#0-0) 
and `add_tip` [2](#0-1) .

Both eventually call `swap_and_burn`, which performs an AMM swap of the caller's tip/fee asset into Ether via `pallet_asset_conversion::Swap::swap_exact_tokens_for_tokens`, but passes `None` for the `amount_out_min` parameter: [3](#0-2) 

Compare this to `pallet_asset_conversion`'s own dispatchable, which correctly requires and enforces `amount_out_min`, rejecting the swap via `Error::<T>::ProvidedMinimumNotSufficientForSwap` if the output is insufficient: [4](#0-3) 

The `Swap` trait itself explicitly documents that `amount_out_min` is the caller-controlled mechanism to bound slippage: [5](#0-4) 

By always passing `None`, `system-frontend` unconditionally opts out of this protection for every single swap it performs on behalf of the calling account, regardless of the pool's current price or depth.

### Impact Explanation
Since `ether_gained` computed from this unprotected swap directly determines the amount of Ether burned for teleport to Ethereum (used to fund `register_token`'s cross-chain execution fee and `add_tip`'s relayer tip) [6](#0-5) ,
an attacker who can move the relevant `pallet_asset_conversion` pool's price against the victim in the same block (e.g., by having a large position and executing a manipulating trade immediately before the victim's `register_token`/`add_tip` extrinsic lands) can force the victim's swap to execute at an arbitrarily bad price. This results in: (a) the caller's tip/fee asset being drained for far less Ether than intended, and (b) potentially insufficient Ether being burned/teleported to cover the intended registration or tip amount, silently harming the fee payer's fund value with no ability to bound the loss. This is a direct, unbacked-value-loss / underpriced-work class impact — the caller pays a market-determined amount of tokens but has no way to cap how bad the received amount can be.

### Likelihood Explanation
Both `register_token` and `add_tip` are open to any signed origin (no privileged access needed), and the swap path (`tip_asset_location` -> `ether_location`) is attacker-observable ahead of time. Any account, not just a validator/collator, can submit ordinary swap transactions against the same `pallet_asset_conversion` pool to move its price before a target's transaction executes in the same block, since transaction ordering within a block is influenced by tip/priority rather than requiring a compromised node. The complete absence of any `amount_out_min` bound (not merely a suboptimal default) makes every call to these entry points unconditionally exposed, rather than only exposed under unusual pool conditions.

### Recommendation
Add an `amount_out_min` (or equivalent minimum acceptable Ether amount) parameter to `register_token` and `add_tip`, threaded through `swap_fee_asset_and_burn` / `swap_and_burn` into the `Swap::swap_exact_tokens_for_tokens` call instead of hardcoding `None`. Reject the extrinsic (returning `Error::<T>::SwapError` or similar) if the realized output does not meet the caller-specified minimum, mirroring the protection already implemented in `pallet_asset_conversion::Pallet::do_swap_exact_tokens_for_tokens`.

### Proof of Concept
1. Attacker observes a pending `register_token` or `add_tip` extrinsic from a victim account that pays with `TIP_ASSET`, to be swapped into `ETHER` via the pool `(TIP_ASSET, ETHER)`.
2. Before the victim's extrinsic executes (e.g., by submitting a higher-priority/tip transaction in the same block), the attacker executes a large `swap_exact_tokens_for_tokens` or `add_liquidity`/`remove_liquidity` sequence that skews the pool's reserves so that `TIP_ASSET -> ETHER` price is temporarily very unfavorable.
3. The victim's extrinsic proceeds to call `swap_and_burn`, which invokes `T::Swap::swap_exact_tokens_for_tokens(..., None, ...)` at `bridges/snowbridge/pallets/system-frontend/src/lib.rs:301-308`. Because `amount_out_min` is `None`, this call succeeds even though `ether_gained` is far below the fair-market amount.
4. The attacker restores the pool to its original state in a follow-up transaction within the same block (or across nearby blocks), extracting the value the victim overpaid, exactly analogous to the sandwich-attack primitive described in the H-7 report against `UniV3SwapInput()`.

		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}
