### Title
Unbounded array allocation from attacker-controlled length in TVM precompiled-contract array decoders causes node OOM/crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.java` contains helper methods `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` that decode variable-length arrays embedded in precompiled-contract call data. Each of them reads a length word directly from attacker-supplied `DataWord[] words` (i.e., attacker-controlled EVM/TVM calldata) via `words[offset].intValueSafe()` and immediately allocates a Java array of that size with `new byte[len][]`, with no upper bound check on `len` before allocation: [1](#0-0) [2](#0-1) [3](#0-2) 

This mirrors the `fulgur` bug class: a size value taken directly from attacker-controlled input is used to size an allocation / drive a loop with no `MAX_*` cap, so a small malicious payload can force an outsized allocation and CPU work.

### Finding Description
`intValueSafe()` on `DataWord` clamps the decoded 256-bit word to a safe `int` range (up to `Integer.MAX_VALUE`) rather than validating it against any protocol-relevant bound such as remaining calldata length or a small array-count ceiling. Each of the three helper functions then does:

```
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
```

before any check that `len` is consistent with the actual size of `data`/`words`. A caller that reaches one of these decoders with attacker-supplied precompiled-contract input can set that length word to a large value (e.g., `0x7FFFFFFF`), causing the JVM to attempt to allocate an array of that many object-array references in one shot. This is functionally identical to the `fulgur` issue: an attacker-controlled numeric field taken from untrusted input drives an unbounded allocation/loop with no cap, at negligible cost to the caller but high memory/CPU cost to the processing node.

Unlike the bounded case seen in `VerifyTransferProof` (where `spendCount`/`receiveCount` are explicitly checked to be in `[1,2]` before array allocation, see lines 1496-1509), these three generic array-extraction helpers perform no analogous bound check.

### Impact Explanation
Any account able to submit a transaction that triggers a smart-contract `CALL`/`STATICCALL` into a precompiled contract whose input is parsed with one of these helpers can force the executing full node to attempt a very large heap allocation. This can throw `OutOfMemoryError` or cause severe GC pressure/CPU stalls during transaction execution across all nodes that process the block (since TVM execution during block application is deterministic and re-executed by every validator), resulting in node crash or halted service — a concrete "node crash or halt" impact class permitted by the validation rules.

### Likelihood Explanation
Exploitation requires only a single, cheaply-crafted transaction/contract call whose calldata reaches one of the vulnerable decoders with a maliciously large length word; no special privilege, stake, or witness/SR role is needed. The likelihood of triggering the code path is high given it's a normal, uncontrolled/unprivileged transaction-broadcaster-reachable path, but I was not able to fully confirm within the available tool budget which specific precompiled contract(s) invoke `extractBytesArray`/`extractBytes32Array`/`extractSigArray` at runtime (the grep only matched their definitions and the 8 internal call-sites within `PrecompiledContracts.java`; I could not trace the specific precompiled-contract dispatch entry — e.g., a batch-signature-validation precompile — before running out of iterations). This caller identification is necessary to fully confirm the exact attacker-reachable entry point and its energy-cost accounting, so I flag this as an area needing further verification via a Devin session with full file access.

### Recommendation
Add an explicit upper bound check on `len` immediately after `words[offset].intValueSafe()` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` — e.g., reject if `len` is negative, exceeds a small protocol-defined maximum, or is inconsistent with `words.length`/`data.length` — before performing `new byte[len][]`, mirroring the existing bound check already applied to `spendCount`/`receiveCount` in `VerifyTransferProof`.

### Proof of Concept
Not fully verified end-to-end due to tool-call budget exhaustion before identifying the exact precompiled-contract caller/address that dispatches to these decoders; a background Devin session with full repository/build access would be needed to (1) locate the precompiled-contract `execute()` method(s) that invoke `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, (2) craft calldata for that contract's specific ABI layout with the length word set to a large value (e.g., `0x7FFFFFFF`), and (3) confirm the resulting `OutOfMemoryError`/excessive allocation during `TransactionTrace`/TVM execution.
