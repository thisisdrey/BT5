### Title
Non-atomic check-then-update of the replay window lets a duplicate/racing packet bypass replay protection - ([File: connection_state.go])

### Summary
Nebula's per-tunnel replay protection (`Bits.Check` / `Bits.Update`) is split into two separate, independently-locked steps inside `ConnectionState.Decrypt` and `ConnectionState.VerifyRelay`. The lock protecting the replay window is released between the "is this counter already seen" check and the "mark this counter as seen" update, with AEAD decryption happening in the unlocked gap. This is structurally the same root cause as the reported DeFi bug: a piece of shared accounting state (there, the liquidity index; here, the replay-window bitmap) is read for a decision, then a state-changing operation is performed, and only afterward is the shared state actually updated — instead of atomically updating the state as part of the decision. Any caller that observes the stale state in between reaches an outcome computed from data that is about to become invalid.

### Finding Description
In `connection_state.go`, `Decrypt` performs:
1. `cs.decryptLock.Lock(); result := cs.window.Check(l, messageCounter); cs.decryptLock.Unlock()` [1](#0-0) 
2. AEAD decryption of the packet outside the lock: `cs.dKey.DecryptDanger(...)` [2](#0-1) 
3. Only afterward: `cs.decryptLock.Lock(); result = cs.window.Update(l, messageCounter); cs.decryptLock.Unlock()` [3](#0-2) 

`VerifyRelay` follows the identical pattern for relayed packets. [4](#0-3) 

`Bits.Check` only reads the bitmap to decide "not yet seen"; it does not mark the counter as consumed — that happens later in `Bits.Update`, which sets the bit and advances `current`. [5](#0-4) [6](#0-5) 

Because `Check` and `Update` are two separate critical sections rather than one atomic "check-and-set", if the packet-processing path for a given `ConnectionState` can run concurrently for the same tunnel (e.g., two copies of the same on-wire packet arriving close together, or duplicate delivery via network retransmission/relay paths), both copies can pass `Check` (neither has been marked seen yet), both can successfully decrypt (the ciphertext/counter pair is valid and hasn't been consumed), and only the `Update` step will finally reject the second one as a duplicate — after the decrypted plaintext of the "replay" has already been produced and, in `Decrypt`'s caller (`readOutsidePackets`), already handed off to roaming/connection-manager/tun-delivery logic. This mirrors the audited bug precisely: state that should gate the transfer (the treasury payout / here, packet delivery) is read once for a decision but the authoritative update that should have invalidated that decision for other actors happens too late, after externally visible effects have already occurred.

### Impact Explanation
This weakens the sliding-window replay/duplicate-suppression guarantee described in the code's own comments (`bits.go`'s extensive documentation of window semantics), allowing an attacker who can inject duplicate copies of a previously valid on-wire packet within the race window to have that packet processed twice by the receiving node (e.g., duplicate delivery to the tun device, or duplicate side effects in `handleHostRoaming`/`connectionManager.In`). While Nebula packets are authenticated (an attacker without the shared session key cannot forge new content), on-path or off-path adversaries capable of duplicating/racing already-observed ciphertext (e.g., link-layer duplication, relay-path duplication, or an attacker retransmitting a captured packet before the legitimate copy's `Update` completes) can cause double-processing of a single authenticated message, undermining the anti-replay property the window is specifically designed to enforce.

### Likelihood Explanation
Exploitability depends on being able to win a race between two decrypt attempts for the same counter on the same `ConnectionState`, which requires either genuinely concurrent packet delivery (e.g., via the relay path, where `VerifyRelay` and `Decrypt` for the same tunnel could be invoked from different goroutines) or extremely fast duplicate injection. This is a real but timing-dependent condition, not a trivially one-shot exploit; nonetheless it is reachable purely at the network layer by any attacker who can observe/replay traffic on the wire, with no CA-signed certificate required.

### Recommendation
Merge `Check` and `Update` into a single atomic "check-and-mark" operation performed under one lock acquisition, so that no other decrypt attempt for the same counter can observe an unmarked window between the decision and the state mutation — analogous to updating the interest rate atomically with the liquidity-affecting transfer in the referenced fix. Concretely, decrypt only after atomically reserving the counter slot (or decrypt-then-atomically-commit using compare-and-swap on the bit), never leaving a window where two callers can both see the counter as "not yet seen."

### Proof of Concept
Conceptual PoC (timing-dependent, not a guaranteed single-shot reproduction):
1. Capture a valid encrypted packet with `messageCounter = N` for an established tunnel.
2. Fire two goroutines that both invoke `ConnectionState.Decrypt` (or `VerifyRelay`, for the relay path) with the same captured packet at nearly the same time, e.g. via two near-simultaneous UDP deliveries (real duplicate delivery or attacker-injected replay racing the legitimate packet).
3. Because `cs.window.Check` is called and unlocked before `cs.dKey.DecryptDanger` runs, both goroutines can pass the `Check` for counter `N` before either has called `Update`, and both will successfully decrypt — verified by instrumenting/logging inside `Decrypt` to show two successful `DecryptDanger` calls for the same `messageCounter` prior to `Update` being called for either. func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
