### Title
Front-running of `ParticipateAssetIssueContract` causes victims to pay bandwidth/fee for a failed asset purchase — ([File: actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java])

### Summary
`ParticipateAssetIssueActuator` (the analog of the reported Dutch-auction "mint") lets any account buy a limited, non-replenishing supply of a TRC10 token from its issuer. Whether a participation succeeds depends entirely on the issuer account's remaining asset balance at the moment the transaction is processed. Because transaction ordering inside a block is controlled by whoever builds/broadcasts transactions (not by the victim), an attacker who observes a pending `ParticipateAssetIssueContract` transaction can submit a competing transaction that drains the remaining supply first, causing the victim's transaction to fail validation — after the victim has already paid bandwidth/energy for the transaction.

### Finding Description
`ParticipateAssetIssueActuator.validate()` checks that the issuer (`toAccount`) has enough remaining asset balance to satisfy the exchange: [1](#0-0) 

and `execute()` performs the actual reduction from the issuer account and reverts with `ContractExeException` if the reduce fails: [2](#0-1) 

This exchange draws from a strictly decreasing, shared pool (the issuer's remaining `AssetV2`/`Asset` balance, ultimately bounded by `total_supply` set in `AssetIssueContract`), exactly like the decreasing/limited NFT id pool in the reported Dutch-auction bug. Whoever's transaction is processed first consumes part of that fixed pool; anyone processed afterward, once the pool is exhausted, fails.

Crucially, transactions are validated and executed sequentially and atomically per-transaction inside `Manager.processTransaction`, in the order they appear in `processBlock`'s loop: [3](#0-2) 

Within `processTransaction`, bandwidth/resource consumption (`consumeBandwidth`) happens *before* the actuator's `validate()`/`execute()` runs via `trace.exec()`: [4](#0-3) 

So the sequence for the victim's transaction is: bandwidth/fee is deducted first, then `trace.exec()` → actuator `validate()`/`execute()` runs and can fail with `ContractValidateException("Asset balance is not enough !")` if a front-running transaction already consumed the remaining supply. This mirrors the reported issue precisely: a user can be front-run out of a limited, decreasing allocation and still be charged for the attempt.

An unprivileged party can achieve the front-run simply by observing the victim's pending `ParticipateAssetIssueContract` in the mempool/pushTransactionQueue and broadcasting their own competing `ParticipateAssetIssueContract` (or, if they are the block producer/witness, ordering their own transaction first) buying up the remainder of the issuer's asset supply before the victim's transaction is packed into a block.

### Impact Explanation
The victim pays bandwidth/energy fees for a transaction that ultimately fails to deliver the purchased TRC10 tokens, because a front-runner drained the fixed/limited supply first. This is a resource-loss/fee-loss impact tied directly to a normal, broadcastable user transaction type (`ParticipateAssetIssueContract`) reachable by any account — not a privileged or SR-only path. It does not cause fund theft or an unbacked balance (the TRX "cost" is refunded to the account in that it's never actually charged if `validate()` fails before transfer, but the bandwidth/energy consumption is non-refundable), so the severity is bounded to wasted resources for ordinary participants, matching the analog's stated "Medium" severity classification (failed mint / wasted gas, no direct fund theft).

### Likelihood Explanation
Likelihood is moderate: it requires (a) an ongoing `AssetIssueContract` with a small remaining supply near exhaustion, and (b) an attacker willing to race a competing `ParticipateAssetIssueContract`. Because TRON block producers control transaction ordering (not a public gas-auction mempool like Ethereum), the "front-running" vector is most reliably exploitable by the witness/block producer itself, or by any node with faster broadcast/priority to the current producer, rather than by arbitrary users purely via gas bidding. This is a normal MEV-style race condition inherent to any limited/decreasing on-chain resource allocation model, matching the bug class of the reported analog.

### Recommendation
- Do not consume bandwidth/energy for a transaction whose actuator `validate()` fails due to insufficient asset/issuer availability, or refund the resource cost on such validation failures.
- Consider adding a per-transaction reservation/queueing mechanism, or a partial-fill semantics (fill up to the remaining available amount instead of an all-or-nothing reduce) for `ParticipateAssetIssueActuator`, similar to the report's "multi-phase" or partial-allocation recommendation, to reduce the impact of front-running near supply exhaustion.

### Proof of Concept
1. Issuer creates an `AssetIssueContract` with `total_supply` = N and starts the sale window (`startTime`/`endTime`).
2. As the remaining issuer `AssetV2` balance nears zero (e.g., N tokens left where N is small), a legitimate buyer B broadcasts `ParticipateAssetIssueContract` requesting an amount that would exactly consume the remaining N tokens.
3. An attacker observes B's pending transaction and broadcasts (or, as a witness, orders) a competing `ParticipateAssetIssueContract` that consumes the remaining supply first.
4. When B's transaction is processed in `Manager.processTransaction`, `consumeBandwidth` deducts B's bandwidth (per [5](#0-4) ), then `ParticipateAssetIssueActuator.validate()` throws `ContractValidateException("Asset balance is not enough !")` (per [6](#0-5) ), leaving B's transaction failed but bandwidth/energy already spent.
