### Title
Postponed-receipt/PendingDataCount rows survive DeleteAccount, enabling authorization escalation on reused account IDs - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` removes `TrieKey::Account`, `TrieKey::ContractCode`, access keys/gas keys, and `TrieKey::ContractData`, but does not remove `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` entries keyed by the deleted account's `receiver_id`. [1](#0-0)  An attacker can create a postponed self-receipt on their own account, delete that account while the receipt is still pending, and if the account name is later reused, delivering the withheld `DataReceipt` resumes the stale postponed receipt against the new account's state.

### Finding Description
`process_action_receipt` stores an `ActionReceipt` as postponed when not all `input_data_ids` are available, writing `TrieKey::PendingDataCount{receiver_id, receipt_id}`, `TrieKey::PostponedReceiptId{receiver_id, data_id}` for each missing input, and the receipt itself via `set_postponed_receipt` (`TrieKey::PostponedReceipt{receiver_id, receipt_id}`). [2](#0-1)  These keys are indexed purely by `receiver_id` and `receipt_id`/`data_id` — they carry no binding to a specific "incarnation" of the account (no nonce, no creation timestamp, no account-state hash).

`action_delete_account` calls `remove_account(state_update, account_id)` unconditionally as part of `DeleteAccountAction` processing. [3](#0-2)  `remove_account` only removes `TrieKey::Account`, `TrieKey::ContractCode`, access-key/gas-key entries (via a prefix iterator), and `TrieKey::ContractData` (also via a prefix iterator). [4](#0-3)  There is no corresponding prefix-cleanup call for `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` rows belonging to the account, even though these are legitimate, first-class trie keys scoped by `receiver_id` per `core/primitives/src/trie_key.rs`. [5](#0-4) 

When a matching `DataReceipt` later arrives for that `receiver_id`/`data_id`, `process_receipt`'s `Data` branch looks up `TrieKey::PostponedReceiptId`, decrements `TrieKey::PendingDataCount`, and once it hits zero, fetches and executes the stale `TrieKey::PostponedReceipt` via `apply_action_receipt`, with no check that the account still corresponds to the same account that existed when the receipt was postponed. [6](#0-5) 

Exploit flow:
1. Attacker submits an `ActionReceipt` with `predecessor_id == receiver_id == "victim.near"` (a self-targeted receipt) whose actions include `AddKey{full_access}` and whose `input_data_ids` reference a `DataReceipt` the attacker controls/withholds. This gets stored as postponed via `process_action_receipt`.
2. Attacker (owner of `victim.near`) submits `DeleteAccountAction` on `victim.near` with zero locked balance, satisfied by `action_delete_account`'s checks (storage-usage limit, gas-key-burn limit) — none of which inspect postponed-receipt state. [7](#0-6)  `remove_account` runs but leaves the `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` rows for `victim.near` untouched.
3. Any party re-creates `victim.near` via `CreateAccountAction`.
4. The attacker (or anyone with the withheld `DataReceipt`) delivers it. `process_receipt`'s Data-receipt path finds the leftover `PostponedReceiptId`, decrements `PendingDataCount` to zero, retrieves the old postponed `ActionReceipt`, and executes it against the newly created account via `apply_action_receipt`.

At execution time, the resumed receipt still has `predecessor_id == receiver_id == "victim.near"`, so any actor-permission checks that treat "receipt sent by the account to itself" as authorized (self-calls bypass access-key checks since the receipt was already authorized when originally created) would grant the `AddKey{full_access}` action on the new incarnation of `victim.near`, which never authorized it. This violates authorization exactness: the promise/receipt should not carry privileges the new account owner never granted.

### Impact Explanation
This is authorization escalation / account takeover on any account name reused after deletion: the new owner of a re-created account can have a full-access key silently added by a stale postponed receipt from a prior owner, giving the attacker (or whoever crafted/holds the withheld `DataReceipt`) full control of the "new" account without the new owner's consent. This matches the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Preconditions: attacker must control the account being deleted (to construct the self-targeted postponed receipt and later delete it), the account must have zero locked balance at deletion time (ordinary requirement, cheap to satisfy), and the account name must be reused afterward. Reuse of a deleted account name is a normal, permissionless operation on NEAR (anyone can create an account with a free name once vacated) — the attacker does not need to control who creates the new account, only the timing of withholding/releasing the `DataReceipt`. Cost is limited to normal gas/storage fees for one ActionReceipt, one DeleteAccount, and later relaying one DataReceipt; no validator or privileged access is required. The scenario is fully repeatable since the missing trie-key cleanup is deterministic in `remove_account`.

### Recommendation
In `remove_account` (`core/store/src/utils/mod.rs`), before/while removing account state, also purge any `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` entries whose `receiver_id` equals the deleted account, using prefix iteration analogous to the existing access-key/contract-data cleanup (or maintain an explicit iterable index of postponed-receipt ids per account so `DeleteAccountAction` can reject/burn them synchronously). Alternatively, reject `DeleteAccountAction` outright while any postponed receipt is still pending for that account.

### Proof of Concept
Runtime integration test:
1. Set up account `victim.near` with a full-access key controlled by "attacker".
2. Submit an `ActionReceipt` with `predecessor_id = receiver_id = "victim.near"`, `input_data_ids = [data_id]`, `actions = [AddKeyAction{public_key: attacker_pk2, access_key: full_access}]`. Verify it is stored as postponed (`TrieKey::PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` present).
3. Submit `DeleteAccountAction` on `victim.near` (zero locked balance) from the attacker's key; assert it succeeds and `TrieKey::Account{victim.near}` is gone, but assert (bug reproduction) that `TrieKey::PostponedReceipt{receiver_id: victim.near, receipt_id}` and `TrieKey::PendingDataCount` still exist in the trie.
4. Submit `CreateAccountAction` recreating `victim.near` (e.g., by a different, unrelated party funding it), with no keys added except its own.
5. Deliver the withheld `DataReceipt{receiver_id: victim.near, data_id}`.
6. Assert that `attacker_pk2` now exists as a full-access key on `victim.near`, proving the new account gained a privilege its actual creator never authorized.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
