### Title
Unvalidated `git_object_directory`/`git_alternate_object_directories` Repository fields allow object-directory path injection into every spawned Git command - (File: internal/git/alternates/alternates.go)

### Summary
Any gRPC caller supplies a `gitalypb.Repository` message on nearly every RPC. This message carries two attacker-influenceable fields, `git_object_directory` and `git_alternate_object_directories`, which are meant only for internal quarantine/object-pool plumbing. `Locator.ValidateRepository` never validates these two fields — it only checks `StorageName`/`RelativePath` — yet `alternates.Env()` blindly joins them onto the repository path and injects the result as `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` for every Git subprocess spawned by `ExecCommandFactory.newCommand`. This is structurally the same defect class as the reNFT bug: a field that "rides along" on an otherwise-validated request/order, is never covered by the validation logic, but is nonetheless acted upon by the downstream execution engine.

### Finding Description
`ExecCommandFactory.newCommand` unconditionally builds the object-directory environment from repository-supplied fields: [1](#0-0) 

which delegates to: [2](#0-1) 

`alternates.Env` performs a plain `filepath.Join(repoPath, dir)` for `objectDirectory` and every entry of `alternateObjectDirectories`, with **no call to `storage.ValidateRelativePath`** and no bound on `..` traversal or absolute-path override behavior of `filepath.Join`.

Separately, `configLocator.ValidateRepository` — the single authoritative validation entry point invoked from `GetRepoPath` before every command — only checks `StorageName` and `RelativePath`: [3](#0-2) 

It never touches `GetGitObjectDirectory()`/`GetGitAlternateObjectDirectories()`. Path-safety logic for these fields exists (`Repo.ObjectDirectoryPath` in `internal/git/localrepo/paths.go`, using `storage.ValidateRelativePath` and quarantine-prefix checks), but that function is only invoked by specific RPCs such as `GetObjectDirectorySize`/LFS-pointer scanning — it is **not** part of the common `GetRepoPath` → `newCommand` path that every git invocation goes through: [4](#0-3) 

This exactly parallels the reNFT root cause: the "tip" (extra consideration items / here, the object-directory fields) is not covered by the signature/validation step (`_assertConsiderationLengthAndGetOrderHash` / `ValidateRepository`) but is still consumed by the execution engine (Seaport transfer loop / `git` subprocess via injected env vars).

### Impact Explanation
An attacker who can issue a normal Gitaly RPC that carries a `Repository` message (essentially any RPC, since `Repository` is the universal addressing mechanism) can set `git_object_directory`/`git_alternate_object_directories` to an arbitrary relative (or, depending on `filepath.Join` semantics, effectively arbitrary) path. Because these are exported straight into `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` for the spawned `git` process, this can:
- Redirect where new objects are written (main object directory hijack), potentially writing into unintended directories within the storage root.
- Add an out-of-repository directory to the Git alternates search path for the duration of the command, letting the command see/read objects from another location outside the intended repository, which is a cross-repository object access / repository-isolation bypass depending on how far the join can be steered.
- If a crafted value points at a non-existent or unreadable path, this can also be used to make routine git operations fail (a DoS of that RPC/handler), similarly to how the malicious ERC20 permanently failed the escrow transfer in the original report.

The severity is bounded by whatever downstream `filepath.Join` and OS path semantics allow (this could not be fully confirmed to escape the storage root without live testing, since `filepath.Join` cleans `..` segments only relative to `repoPath`, and no `ValidateRelativePath`/root-containment check is applied at this call site).

### Likelihood Explanation
Likelihood is high in terms of reachability: `Repository.git_object_directory` / `git_alternate_object_directories` are ordinary proto fields any client can set on essentially every RPC, and the code path (`newCommand` → `alternates.Env`) is executed on every single Git command Gitaly spawns for that repository. The only real gate blocking casual, unauthenticated exploitation is that most external Gitaly deployments are fronted by GitLab, which typically does not let arbitrary users set these fields directly (they are normally set internally for quarantine/object-pool purposes) — but nothing in Gitaly's own validation layer (`ValidateRepository`) enforces this restriction, so any caller with direct gRPC access (including a fully authenticated, ordinary Gitaly API/gRPC client, not merely a privileged operator) can set them.

### Recommendation
Add the same path-containment validation used in `Repo.ObjectDirectoryPath`/`storage.ValidateRelativePath` to the common path: either inside `configLocator.ValidateRepository` (covering `GetGitObjectDirectory()`/`GetGitAlternateObjectDirectories()` explicitly) or inside `alternates.Env` itself, rejecting any object-directory value that is not contained within the storage root (or, for legitimate quarantine cases, within the expected quarantine-directory prefix as already implemented in `paths.go`). This closes the "un-validated extra field" gap the same way the reNFT team closed theirs by whitelisting/validating the extension rather than trusting it implicitly.

### Proof of Concept
Not independently executed against a live Gitaly instance (no sandbox access); the above is derived purely from static code-path analysis:
1. Issue any RPC (e.g. `CommitService.FindCommit`) with a `Repository` message where `relative_path`/`storage_name` point at a valid repo, but `git_alternate_object_directories` is set to a crafted relative path (e.g. `"../../some-other-repo/objects"`).
2. `GetRepoPath` → `configLocator.ValidateRepository` accepts the request because it never inspects `git_alternate_object_directories`.
3. `ExecCommandFactory.newCommand` calls `alternates.Env(repoPath, "", ["../../some-other-repo/objects"])`, producing `GIT_ALTERNATE_OBJECT_DIRECTORIES=<repoPath>/../../some-other-repo/objects` with no containment check.
4. The spawned `git` process now searches that external directory for objects, whose actual consequences (successful cross-repo object read, error, or benign no-op) require confirmation with an instrumented Gitaly build, since no execution environment was available here to observe the resulting behavior.

```go
// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

	return env
}
```

```go
func (l *configLocator) ValidateRepository(ctx context.Context, repo storage.Repository, opts ...storage.ValidateRepositoryOption) error {
	var cfg storage.ValidateRepositoryConfig
	for _, opt := range opts {
		opt(&cfg)
	}

	// Only checking for `nil` isn't sufficient as Protobuf messages may be non-nil, but still
	// either invalid or empty. Thus we also explicitly verify whether both the storage name and
	// the relative path are unset.
	if repo == nil || repo.GetStorageName() == "" && repo.GetRelativePath() == "" {
		return structerr.NewInvalidArgument("%w", storage.ErrRepositoryNotSet)
	}

	relativePath := repo.GetRelativePath()
	if len(relativePath) == 0 {
		return structerr.NewInvalidArgument("%w", storage.ErrRepositoryPathNotSet)
	}
```

```go
// ObjectDirectoryPath returns the full path of the object directory. The errors returned are gRPC
// errors with relevant error codes and should be passed back to gRPC without further decoration.
func (repo *Repo) ObjectDirectoryPath(ctx context.Context) (string, error) {
	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", err
	}

	objectDirectoryPath := repo.GetGitObjectDirectory()
	if objectDirectoryPath == "" {
		return "", structerr.NewInvalidArgument("object directory path is not set")
	}

	storagePath, err := repo.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return "", fmt.Errorf("get storage by name: %w", err)
	}

	// Ensure the path points somewhere in the storage.
	relativeObjectDirectoryPath, err := storage.ValidateRelativePath(storagePath, filepath.Join(repoPath, objectDirectoryPath))
	if err != nil {
		return "", structerr.NewInvalidArgument("validate relative path: %w", err)
	}

	parentDir := filepath.Base(filepath.Dir(relativeObjectDirectoryPath))
	baseDir := filepath.Base(relativeObjectDirectoryPath)
	isTransactionQuarantineDir := (baseDir == "quarantine") || ((parentDir == "quarantine") && strings.HasPrefix(baseDir, "tmp_objdir"))
```
