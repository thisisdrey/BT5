### Title
"Always-allowed" peer trust and denylist status is keyed by IP:port, not by public key, so a re-keyed/rotated peer at the same address inherits a prior peer's trust and ban exemptions - ([File: stackslib/src/net/db.rs])

### Summary
`PeerDB` stores per-peer trust flags (`allowed` / `denied`) keyed only by `(network_id, addrbytes, port)`. When a new handshake arrives from an address that already has a DB row, `Neighbor::load_and_update` loads that row (with its `allowed`/`denied` values) *before* checking whether the handshake's public key matches the key on record, and only afterwards overwrites `public_key` with the newly-presented key. The merged record (still carrying the old `allowed` value) is then persisted via `save_update` → `PeerDB::update_peer`. This mirrors the reported bug class: an identity that is looked up by a reusable, non-cryptographic key (IP:port, analogous to a username) inherits privileges/credentials that were only ever proven for a different actual identity (the previous public key, analogous to a deleted user's original account).

### Finding Description
`Neighbor::load_and_update` in [1](#0-0)  looks up the existing DB row purely by `NeighborKey` (network_id + addrbytes + port):
```
let peer_opt = PeerDB::get_peer(conn, network_id, &addr.addrbytes, addr.port)...
let (mut neighbor, present) = match peer_opt {
    Some(neighbor) => { let mut ret = neighbor; ret.addr = addr.clone(); (ret, true) }
    None => { ... }
};
...
neighbor.handshake_update(conn, handshake_data)?;
```
`handshake_update` [2](#0-1)  overwrites `self.public_key` with whatever key is in the new handshake, but never resets `allowed`/`denied`, which remain whatever was stored for the *previous* occupant of that address:port.

This merged `Neighbor` is what gets saved back to the DB:
- In `handle_handshake`, when the connection's key is upgraded, the code loads-and-updates then calls `neighbor.save_update(&tx, None)` → `PeerDB::update_peer` [3](#0-2) .
- `PeerDB::update_peer` [4](#0-3)  writes `neighbor.allowed`/`neighbor.denied` to the DB row, and only drops StackerDB replica records on a key change — it does **not** reset the trust (`allowed`) flag.

`allowed < 0` ("always allowed") is a security-relevant trust flag: 
- It exempts a peer from connection pruning: `prune_connections` in [5](#0-4)  skips pruning if `neighbor.allowed < 0`.
- It exempts a peer from being penalized/banned for misbehavior: `process_bans` in [6](#0-5)  explicitly skips punishing a misbehaving connection if `neighbor.is_allowed()` is true.
- It is used to seed neighbor walks and is force-included in fresh-neighbor selection: [7](#0-6) , and always prioritized for outbound crawling in `instantiate_walk_to_always_allowed` [8](#0-7) .

So: an operator marks a specific, cryptographically-identified peer (address+pubkey) as trusted (`allowed = -1`) via `set_allow_peer` [9](#0-8) . If the IP:port is later reused by a different actor (e.g., dynamic-IP reassignment, NAT/hosting churn, or an attacker who can reach the node from that same source address, e.g. a shared/cloud IP or via a routable NAT-punched connection) and that actor's handshake presents an unrelated public key, the code will load the pre-existing "always-allowed" row for that address, splice in the attacker's public key, and persist the *same* trust flag for the new key without ever verifying that the new key belongs to the entity the operator originally trusted. Note the same equality gap works for `denied` too: `insert_or_replace_peer` [10](#0-9)  and `update_peer` only drop **StackerDB** slot data (not deny status) on key change, but the important direction here is exploitable escalation of trust rather than persistence of a ban.

### Impact Explanation
This does not directly forge chain data or bypass block validation, but it lets a remote, previously-unauthenticated actor inherit ban immunity and pruning-exemption ("always-allowed") status intended for a specific trusted operator/peer, purely by reusing that peer's network address once its original key is gone/rotated. This can be used to entrench a malicious connection that would otherwise be pruned or banned for misbehavior, and to get preferential selection in neighbor walks — a bounded but real network-integrity weakening. It does not meet the "Critical" bar (no unauthenticated write to state/StackerDB, no forged data propagation), so it best maps to a lesser/edge-case issue: identity binding is by IP rather than key for the `allowed`/`denied` trust attributes.

### Likelihood Explanation
Exploitation requires the attacker to actually source traffic from an address:port that a node operator has explicitly whitelisted as "always allowed" and to complete a valid handshake from a different keypair at that address — this is plausible in NAT/dynamic-IP/hosting-provider scenarios or IP churn, but is not a low-effort, always-reachable primitive; it depends on address reuse timing and on the operator having configured `allowed` entries at all (this is an operator opt-in mechanism, not default P2P authentication). This lowers confidence that it rises to "High" severity under the strict scope rubric here.

### Recommendation
Bind trust decisions (`allowed`/`denied`) to the authenticated public key, not solely to `(network_id, addrbytes, port)`. When `Neighbor::load_and_update` observes that the incoming handshake's public key differs from the on-file public key for that address, it should not carry over `allowed`/`denied` state to the new key; instead treat it as a new identity (reset trust to default, requiring the operator to re-affirm via `set_allow_peer` for the new key) analogous to how `PeerDB::insert_or_replace_peer` / `update_peer` already drop associated StackerDB records on key change.

### Proof of Concept
1. Operator marks peer `P` at `1.2.3.4:20444` with public key `K1` as always-allowed (`PeerDB::set_allow_peer`, `allowed = -1`).
2. `P` disappears (key rotated/decommissioned); address `1.2.3.4:20444` is later reachable by attacker `A`, who possesses key `K2`.
3. `A` connects and completes a `Handshake` from `1.2.3.4:20444`. In `ConversationP2P::handle_handshake`, `update_from_handshake_data` detects the key changed (`updated = true`), and since `self.stats.outbound` may be true for an established/oubound-tracked slot, `Neighbor::load_and_update` is invoked: it fetches the DB row for `1.2.3.4:20444` (still `allowed = -1` from step 1), sets `public_key = K2`, and `save_update` writes this back via `PeerDB::update_peer`.
4. From this point, `A`'s connection under `K2` is exempt from `process_bans` and `prune_connections`, and is preferentially selected by `instantiate_walk_to_always_allowed`, despite never having been vetted by the operator.

                u64_to_sql(now_secs)?,

        db: DB,

                None
            } else {
                Some(peer)

            peer

            // no allowed peers in DB that aren't us. Try a different strategy

                network.get_local_peer()

        let w = NeighborWalk::new(
            db,
            comms,
            &allowed_peer,
            true,
            network.get_walk_pingbacks().clone(),
            network.get_connection_opts(),
        );

        debug!(
            "{:?}: instantiated neighbor walk to always-allowed peer {:?}",
            network.get_local_peer(),
            &allowed_peer
        );
