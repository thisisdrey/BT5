### Title
Missing `INITIAL_INDEX` fallback in `_calculateTokenDelta` lets an attacker inflate `tokensAccruedOf` by 1e18x and drain the reward token balance - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` only back-fills `accountIndexOf` to `INITIAL_INDEX` when `_tokenIndex > INITIAL_INDEX`. When a token's index is still exactly `INITIAL_INDEX` (i.e., in the same block a reward speed is first set, or whenever `deltaTimestamps == 0`), a first-time account with `accountIndexOf == 0` gets `_deltaIndex = INITIAL_INDEX - 0 = 1e18`, crediting `balance * 1e18` reward tokens. Since `updateBeforeMintOrBurn`, `updateBeforeTransfer`, and `claimRewards` are all public, an unprivileged attacker can trigger this path and then call `claimRewards` to drain the distributor's entire `rewardToken` balance.

### Finding Description
The bug class is identical to the Symmetrical H-6 report: a pending/accrued accounting ledger is updated by the wrong amount because a boundary case is not handled, silently inflating a balance that later gates fund withdrawals.

In `contracts/RewardsDistributor.sol`:

```solidity
// contracts/RewardsDistributor.sol:223-230
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The fallback `_accountIndex = INITIAL_INDEX` is only applied when `_tokenIndex > INITIAL_INDEX` (strictly greater). When `_tokenIndex == INITIAL_INDEX` exactly, `_accountIndex` stays `0`, so `_deltaIndex = 1e18` and `_tokensDelta = balanceOf(account_).wadMul(1e18) ≈ balance * 1e18`. The result is stored by `_updateTokensAccruedOf` into `tokensAccruedOf[account_]` (lines 261-265).

The state `_tokenIndex == INITIAL_INDEX` is reached legitimately: `_updateTokenSpeed` initializes `tokenStates[token_] = TokenState({index: INITIAL_INDEX, ...})` when a speed is first set (lines 296-299). In the same block (or whenever `block.timestamp == _supplyState.timestamp`, or more generally before the index advances past `1e18`), `_calculateTokenIndex` returns `(0, 0)` and the stored index remains exactly `INITIAL_INDEX`.

Attack path, all public entry points, no privileges:

1. Attacker deposits/mints a small amount of the deposit token (or debt token) so `token_.balanceOf(attacker) > 0`. Deposit amount is chosen such that `balance * 1e18 <= rewardToken.balanceOf(distributor)` (a ~`poolRewardBalance / 1e18`-sized position suffices; the attacker can mint dust debt via `DebtToken.issue`/`flashIssue`+`mint` through `SmartFarmingManager.leverage` or directly via `DebtToken.issue`).
2. Governor (or `tokenSpeedKeeper` via `syncTokenSpeed`) calls `updateTokenSpeed`/`updateTokenSpeeds` to activate rewards for that token. The attacker sees this in the mempool and calls the permissionless `updateBeforeMintOrBurn(token, attacker)` — or the permissionless `claimRewards(attacker, [token])` — in the same block, before the index advances past `INITIAL_INDEX`.
3. `tokensAccruedOf[attacker]` becomes `attackerBalance * 1e18`.
4. Attacker calls `claimRewards(attacker)`; `_transferRewardIfEnoughTokens` (lines 248-256) sees `amount_ <= rewardToken.balanceOf(this)` and transfers the entire reward balance to the attacker.

### Impact Explanation
Direct theft of the entire accrued-but-unclaimed `rewardToken` balance held by the distributor — i.e., theft of all other users' unclaimed yield. This satisfies the "theft of unclaimed yield" acceptance criterion. The inflated `tokensAccruedOf` also permanently corrupts the per-account ledger (the same "silently inflated pending balance breaks accounting" invariant as the Symmetrical finding): even if under-funded, the oversized accrual stays on the books.

### Likelihood Explanation
- `updateBeforeMintOrBurn`, `updateBeforeTransfer`, and `claimRewards` are all permissionless (lines 134-191); no modifier restricts the caller.
- The vulnerable window opens deterministically the moment a token's speed transitions from `0` to `>0` (a routine governance operation, also callable by the keeper via `syncTokenSpeed`), and persists for the whole block containing that transaction since `deltaTimestamps == 0` leaves the index at `INITIAL_INDEX`. On any chain with public mempools the tx can be front-run; the attacker only needs their call ordered in the same block.
- The attacker controls the magnitude via their token balance, so they can tune `tokensDelta` to be `<=` the distributor's reward balance to satisfy the `amount_ <= _balance` check in `_transferRewardIfEnoughTokens`.
- `nonReentrant` on `claimRewards` and the `onlyIfTokenExists`/index guards do not block the path; the state check `tokenStates[_token].index > 0` is already satisfied because the index was just initialized to `1e18`.

### Recommendation
Treat `accountIndexOf == 0` as "uninitialized at `INITIAL_INDEX`" regardless of the current index value:

```diff
// contracts/RewardsDistributor.sol
- if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
+ if (_accountIndex == 0) {
     _accountIndex = INITIAL_INDEX;
 }
```

or equivalently initialize `accountIndexOf` to `INITIAL_INDEX` the first time an account is touched for a token, so that `_deltaIndex` is `0` until real accrual occurs. Also consider restricting who may pass arbitrary `account_` values to `updateBeforeMintOrBurn`/`claimRewards`, since crediting rewards to arbitrary accounts on demand amplifies the window.

### Proof of Concept
Hardhat-style fork test sketch (contracts exist under `contracts/`, tests under `test/`):

```ts
// test/RewardsDistributor.exploit.test.ts
it('inflates accrued rewards and drains rewardToken', async () => {
  // given: alice deposits so she holds a deposit-token balance
  await msdMET.connect(alice).deposit(depositAmt, alice.address)
  const aliceBal = await msdMET.balanceOf(alice.address)

  // fund distributor with reward tokens (pre-existing accrual for all users)
  await rewardToken.mint(rewardsDistributor.address, REWARD_POOL)
  // alice picks depositAmt so that aliceBal * 1e18 <= REWARD_POOL

  // when: governor sets speed and, in the same block, alice pokes the index path
  await setAutomine(false)
  await feeProviderOrGov // governor tx
  await rewardsDistributor.connect(governor).updateTokenSpeed(msdMET.address, speed)
  // same-block call; index is still exactly INITIAL_INDEX = 1e18
  await rewardsDistributor.connect(alice).updateBeforeMintOrBurn(msdMET.address, alice.address)
  await mine()

  // then: accrued is inflated by ~1e18 instead of ~0
  expect(await rewardsDistributor.tokensAccruedOf(alice.address)).to.eq(aliceBal.mul(parseEther('1')))

  // and: alice drains the distributor
  await rewardsDistributor.connect(alice).claimRewards(alice.address)
  expect(await rewardToken.balanceOf(alice.address)).to.eq(REWARD_POOL)
  expect(await rewardToken.balanceOf(rewardsDistributor.address)).to.eq(0)
})
```

The key assertions: (a) before the index advances past `INITIAL_INDEX`, `tokensAccruedOf[alice]` equals `balance * 1e18` rather than `0`; (b) `claimRewards` transfers the full distributor reward balance to the attacker.
