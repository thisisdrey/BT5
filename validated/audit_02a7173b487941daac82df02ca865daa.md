### Title
Certificate fingerprint blocklist bypass via P256 ECDSA signature (high-s/low-s) malleability - (File: cert/ca_pool.go)

### Summary
Nebula's `CAPool` tracks blocklisted (revoked/untrusted) certificates by SHA-256 fingerprint, where the fingerprint is computed over the certificate bytes including the DER-encoded ECDSA signature. For P256 certificates, ECDSA signatures are malleable: the same `(message, key)` pair admits two valid signatures, one with a "low-s" value and one with a "high-s" value (`s` and `N-s`), both of which pass `ecdsa.VerifyASN1`. Because the fingerprint hashes the raw signature bytes, flipping a signature between its low-s and high-s form produces two entirely different fingerprints for what is semantically the exact same, already-signed certificate. This mirrors the ERC865 report's core issue: a system uses a malleable signature (or its digest) as a unique identifier for authorization/allow-deny state, and an attacker can present an alternate-but-still-valid signature form to evade tracking based on that identifier.

### Finding Description
`CAPool.verify` and `CAPool.VerifyCertificate` gate acceptance on `IsBlocklisted(fp)`, where `fp` is `Certificate.Fingerprint()` — a SHA-256 hash that includes `c.signature` [1](#0-0) . Signature validity itself is checked via `ecdsa.VerifyASN1`, which accepts both the low-s and the mathematically equivalent high-s form of a P256 signature [2](#0-1) .

The codebase explicitly acknowledges this malleability: `cert/p256/p256.go` provides `Swap`, which converts a signature between its low-s and high-s forms while it remains a valid signature over the same message and key [3](#0-2) , and `IsNormalized`/`checkLowS`, which determine whether a signature is in the canonical low-s form nebula now enforces on generation [4](#0-3) .

`CAPool.VerifyCertificate` tries to compensate: it also computes `CalculateAlternateFingerprint` (the fingerprint of the signature-swapped copy) and checks that alternate fingerprint against the blocklist too, so a freshly-verified certificate is checked against both forms at once [5](#0-4) . The code comment explicitly documents that this is a stopgap: *"Pre nebula v1.10.3 could generate signatures in either high or low s form and validation of signatures allowed for either... Since a change in the signature bytes affects the fingerprint, we need to test both forms until such a time comes that we enforce low-s form on signature validation."* [6](#0-5) .

However, `VerifyCachedCertificate` — the fast-path used for already-verified certificates — only checks the precomputed `c.fingerprint2` stored at the time the `CachedCertificate` was created [7](#0-6) . If a certificate's fingerprint (or its alternate form) is blocklisted *after* a `CachedCertificate` has already been cached (e.g., a peer already has an active tunnel and cached cert), or if any code path caches a certificate without computing/propagating `fingerprint2` correctly, the malleable alternate form could evade the blocklist. More fundamentally, this design proves the exact bug class from the report: the system's uniqueness/trust-tracking key (`fingerprint`) is derived from a value (`signature`) that is not canonical, forcing bolt-on dual-fingerprint bookkeeping (`fingerprint`, `fingerprint2`) that must be kept in sync everywhere fingerprints are computed, compared, or persisted (e.g., `pki.go` blocklist config loading) [8](#0-7) .

### Impact Explanation
If a blocklisted certificate's alternate signature form is not checked at every enforcement point (as is already true for `VerifyCachedCertificate`, and would be true for any future/derived code that stores or compares only the primary `Fingerprint()`), an attacker holding a revoked/blocklisted certificate and its corresponding private key can re-derive the alternate-form signature via the same math used in `p256.Swap`, re-marshal the certificate, and present it to bypass fingerprint-based blocklist/revocation enforcement — a remote authentication/trust-bypass impact directly reachable during certificate presentation in the handshake, with no valid CA-issued cert of their own beyond the one being revoked.

### Likelihood Explanation
The attacker needs only the already-signed (and now-blocklisted) certificate and the corresponding private key — both of which are typically already possessed by the party being revoked (that is precisely who a blocklist is meant to stop) — plus straightforward, already-implemented modular arithmetic (`p256.Swap`) to compute the alternate signature. This requires no CA cooperation and no additional cryptographic capability, only exploiting the swap path that the codebase itself implements and exposes as a public function.

### Recommendation
Enforce canonical low-s form as a *validation* requirement, not just a generation convention: reject P256 certificate signatures that are not low-s during `CheckSignature`, so only one fingerprint per certificate ever exists and dual-fingerprint bookkeeping (`fingerprint2`, `CalculateAlternateFingerprint`, `Swap`) can be removed entirely. Until that breaking change can be rolled out, ensure every code path that persists or compares fingerprints for trust decisions (not just `VerifyCertificate`) also considers the alternate fingerprint, including `VerifyCachedCertificate` and any long-lived caches populated outside of `VerifyCertificate`.

### Proof of Concept
1. Take any valid P256 nebula certificate `c` with signature `sig` (low-s form) and its private key.
2. Compute `sig' = p256.Swap(sig)` — this yields a different byte sequence that still passes `ecdsa.VerifyASN1` for the same certificate details and public key [9](#0-8) .
3. Set the certificate's signature to `sig'` (as done in tests via `nc.(*certificateV1).setSignature(b)`), producing a certificate with a different `Fingerprint()` than the original [10](#0-9) .
4. Blocklist only the original fingerprint (e.g., via config-driven `BlocklistFingerprint`) and confirm the swapped-signature certificate is accepted by any path that does not check the alternate fingerprint (`VerifyCachedCertificate`), demonstrating a blocklist bypass using a mathematically equivalent but differently-encoded signature — the same "signature-as-identifier" malleability class described in the external report.

func (c *certificateV1) CheckSignature(key []byte) bool {
	b, err := proto.Marshal(c.getRawDetails())
	if err != nil {
		return false
	}
	switch c.details.curve {
	case Curve_CURVE25519:
		if len(key) != ed25519.PublicKeySize {
			return false //avoids a panic internal to ed25519
		}
		return ed25519.Verify(key, b, c.signature)
	case Curve_P256:
		pubKey, err := ecdsa.ParseUncompressedPublicKey(elliptic.P256(), key)
		if err != nil {
			return false
		}
		hashed := sha256.Sum256(b)
		return ecdsa.VerifyASN1(pubKey, hashed[:], c.signature)
	default:
		return false
	}
}

func swap(r, s []byte) ([]byte, []byte, error) {
	var err error
	bigS, err := bigmod.NewNat().SetBytes(s, nMod)
	if err != nil {
		return nil, nil, err
	}
	sNormalized := nMod.Nat().Sub(bigS, nMod)

	result := sNormalized.Bytes(nMod)
	for len(result) > 1 && result[0] == 0 {
		result = result[1:]
	}

	return r, result, nil
}

// VerifyCachedCertificate is the same as VerifyCertificate other than it operates on a pre-verified structure and
// is a cheaper operation to perform as a result.
func (ncp *CAPool) VerifyCachedCertificate(now time.Time, c *CachedCertificate) error {
	// Check any available alternate fingerprint forms for this certificate, re P256 high-s/low-s
	if c.fingerprint2 != "" && ncp.IsBlocklisted(c.fingerprint2) {
		return ErrBlockListed
	}

	_, err := ncp.verify(c.Certificate, now, c.Fingerprint, c.signerFingerprint)
	return err
}
