### Title
Stale aggregated oracle price is returned indefinitely once fresh submissions expire - ([File: substrate/frame/honzon/oracle/src/default_combine_data.rs])

### Summary
`pallet-oracle`'s default aggregation strategy, `DefaultCombineData`, filters incoming raw price submissions by an `ExpiresIn` window, but when too few fresh submissions remain it silently falls back to `prev_value` — the last aggregated value stored in `Values` — with **no freshness check on `prev_value` itself**. This is the exact broken invariant described in the external report: "if there has been no recent observation... assume the latest observation is still accurate." Any consumer of `pallet_oracle::Pallet::get`/`DataProvider::get` will keep receiving an arbitrarily stale price forever, with no on-chain signal that the value is stale, as long as the oracle never regains enough live feeders.

### Finding Description
`combine_data` in [1](#0-0)  retains only the raw `values` whose `timestamp + expires_in > now`, then requires at least `MinimumCount` fresh values to compute a new median:

```rust
values.retain(|x| x.timestamp.saturating_add(expires_in) > now);
let count = values.len() as u32;
let minimum_count = MinimumCount::get();
if count < minimum_count || count == 0 {
    return prev_value;
}
```

The `prev_value` passed in is simply `Self::values(key)` — the previously aggregated `TimestampedValue` stored in `Values<T, I>`, fetched in `combined()` at [2](#0-1) . There is no check anywhere that `prev_value.timestamp` is itself still within `ExpiresIn` of `now`. Once returned, this old `prev_value` is written straight back into `Values` in `do_feed_values`:

```rust
if let Some(combined) = Self::combined(key) {
    <Values<T, I>>::insert(key, combined);
}
``` [3](#0-2) 

So `Values[key]` can retain an old timestamp forever, and every downstream caller of `Pallet::get(key)` — which only returns `.value`, discarding the timestamp — has no way to detect staleness via that API: [4](#0-3) . The `DataProvider` trait itself, used generically by any consuming pallet, exposes only the value, not the timestamp: [5](#0-4) .

This differs qualitatively from a normal "not enough data yet" bootstrap condition: it applies equally after the feed has been live and then goes quiet (e.g., oracle operators removed via `change_members_sorted`, membership churn, network partition, or an operator simply stopping submissions), exactly mirroring the L2-sequencer-downtime scenario in the report where the last known price is extrapolated forward with no explicit staleness gate.

### Impact Explanation
This is a runtime bug that compromises intended behavior of the oracle price feed: consumers built on `DataProvider`/`Pallet::get` (e.g. collateral pricing modules, PSM-style pegs, or any downstream logic wired to `pallet-oracle` in a runtime) will act on a frozen, arbitrarily old price with no protocol-level staleness signal. If the value is used for collateralization checks, redemption pricing, or liquidation triggers, this can lead to acceptance of stale state and consequent value mispricing (over/under-collateralization, incorrect liquidation/redemption amounts) — matching the "forged or stale state acceptance" and "theft or unbacked mint" impact classes in the gate criteria, contingent on how a given runtime wires a pricing consumer to this oracle.

### Likelihood Explanation
No privileged actor, governance action, or malicious relayer/validator is required. The condition triggers purely from the natural/foreseeable event of oracle operators falling below `MinimumCount` fresh submissions within `ExpiresIn` (default `ConstU64<3600>`/`ConstU32<600>` per the runtime configs seen), which can happen from ordinary operator inactivity, membership rotation, or targeted "silence" pressure on a minority of required feeders. No unpriveleged attacker action is even needed to keep this state alive indefinitely once triggered — it self-perpetuates because `prev_value` is fed back as the new `prev_value` on every subsequent call while feeds remain sparse.

### Recommendation
Apply the same expiry check to `prev_value` before returning it as a fallback, e.g. only return it if `prev_value.timestamp.saturating_add(expires_in) > now`, otherwise return `None`. Additionally, expose the staleness/timestamp through `DataProvider::get` (or add a staleness-aware API) so downstream consumers can independently reject stale prices rather than relying solely on the oracle pallet's internal state.

### Proof of Concept
1. Configure `pallet_oracle::DefaultCombineData<T, ConstU32<3>, ConstU64<3600>>` (as in [6](#0-5) ) with 3 members required and a 3600-time-unit expiry.
2. Three operators feed a price at `t = 0`; with 3 fresh values, `combine_data` computes and stores the median in `Values[key]` with `timestamp = 0`.
3. All operators stop feeding (or are removed from `Members`). Time advances to `t = 100000` (far beyond `expires_in`).
4. Call `Pallet::get(key)` — it still returns the medianed value from `t = 0`, because `Values[key]` was never invalidated; nothing purges or age-checks it.
5. Any pallet trusting `pallet_oracle::Pallet::get` as a live price will use this 100000-time-unit-old value with no indication of staleness — the on-chain analog of the UniV3 "assume latest observation still holds" flaw.

	fn combine_data(
		_key: &<T as Config<I>>::OracleKey,
		mut values: Vec<TimestampedValueOf<T, I>>,
		prev_value: Option<TimestampedValueOf<T, I>>,
	) -> Option<TimestampedValueOf<T, I>> {
		let expires_in = ExpiresIn::get();
		let now = T::Time::now();

		values.retain(|x| x.timestamp.saturating_add(expires_in) > now);

		let count = values.len() as u32;
		let minimum_count = MinimumCount::get();
		if count < minimum_count || count == 0 {
			return prev_value;
		}

		let mid_index = count / 2;
		// Won't panic as `values` ensured not empty.
		let (_, value, _) =
			values.select_nth_unstable_by(mid_index as usize, |a, b| a.value.cmp(&b.value));
		Some(value.clone())
	}
