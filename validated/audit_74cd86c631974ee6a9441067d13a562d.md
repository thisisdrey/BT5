### Title
Free-form compute-unit-price inflation lets forged packets bypass the sigverify priority floor and force full ed25519 verification - (File: core/src/sigverify.rs, core/src/transaction_priority.rs)

### Summary
The scheduler-published `SchedulerPriorityFloor` is compared against a priority value computed purely from unsigned/unverified packet bytes via `calculate_priority_from_bytes` → `calculate_priority_and_cost`, using only the message's declared `compute_unit_price` and cost-model cost, with no signature check. An attacker can set an arbitrarily high `compute_unit_price` in a `ComputeBudgetInstruction::set_compute_unit_price` instruction while filling the signature slots with garbage bytes (cryptographically invalid but format-valid), making `reward` — and thus `priority` — arbitrarily large, so `apply_priority_floor_to_batch` never drops the packet regardless of the published floor.

### Finding Description
In `core/src/sigverify.rs::run_transaction_task` (`core/src/sigverify.rs:266-331`), the flow per batch is: dedup → (if floor > 0) `apply_priority_floor_to_batch` → `sigverify::ed25519_verify_serial`. `apply_priority_floor_to_batch` (`core/src/sigverify.rs:413-440`) calls `calculate_priority_from_bytes(bank, data)` (`core/src/transaction_priority.rs:73-88`), which:
1. Parses the raw bytes into a `SanitizedTransactionView` (format-only sanitization, no signature verification: `try_new_sanitized`).
2. Computes `cost` via `CostModel::calculate_cost_for_executed_transaction` — deterministic function of declared instructions/limits, not of validity.
3. Computes `fee_details`/`reward` via `solana_fee::calculate_fee_details`, which uses the message's declared `compute_unit_price` (a `ComputeBudgetInstruction::set_compute_unit_price` value the attacker fully controls) and the bank's `lamports_per_signature` — again independent of whether signatures are valid or the payer has funds.
4. `priority = reward * 1_000_000 / (cost + 1)` (`core/src/transaction_priority.rs:60-64`).

None of these steps check signature validity or account balances. This is confirmed by the crate's own test `higher_compute_unit_price_yields_higher_priority` (`core/src/transaction_priority.rs:154-165`), which shows `priority` is monotonic in attacker-supplied `compute_unit_price` alone.

Because `apply_priority_floor_to_batch` runs strictly before `ed25519_verify_serial` (`core/src/sigverify.rs:302-331`), an attacker can craft a well-formed but unsigned/garbage-signed transaction with a huge `compute_unit_price`, guaranteeing `priority > floor` for any floor the scheduler publishes, so the packet is never marked `discard` by the floor check and is passed on to full `ed25519_verify_serial`. The signature check itself is expensive relative to computing/faking a `compute_unit_price` field, and it will ultimately fail (or, if the attacker also has a cheap valid keypair, at least produces zero real fee since the transaction pays no actual priority fee unless it lands), meaning the CPU cost of verification is not gated by the anti-DoS floor mechanism that was specifically introduced for this purpose (per the module doc comment "Sigverify drops at-or-below-floor arrivals").

### Impact Explanation
This defeats the purpose of the priority-floor QoS mechanism (`SchedulerPriorityFloor`) under scheduler saturation: instead of shedding low-value spam before the CPU-expensive `ed25519_verify_serial` step, the floor can be evaded for free by any unstaked remote sender simply by writing a large `u64` into the compute-unit-price instruction of an otherwise garbage packet. This allows disproportionate, cheap-to-generate CPU load on the sigverify thread pool exactly during the saturation window when the floor is supposed to be protecting it, fitting the "grossly underpriced pre-fee work" / QoS-evasion category.

### Likelihood Explanation
Preconditions are attacker-controlled and easy to reach: only requires the scheduler buffer to be saturated (`SATURATION_BUFFER_PCT = 99%`, reachable via ordinary traffic flooding by the same attacker) so that a nonzero floor is published (`update_scheduler_priority_floor`, `core/src/banking_stage/transaction_scheduler/scheduler_controller.rs:333-352`). Crafting the packet requires no cryptographic work — just serializing a `VersionedTransaction`-shaped byte buffer with a `set_compute_unit_price` instruction set to `u64::MAX` and arbitrary signature bytes matching the declared signature count for parseability. This is fully repeatable and scriptable at line rate.

### Recommendation
Do not let attacker-controlled fee/priority fields alone gate expensive downstream work. Options: (1) bound the priority computed pre-signature-verification by a fee the sender can plausibly pay (e.g., cap `compute_unit_price` contribution to some sanity ceiling before verification), (2) perform a cheap, cost-bounded pre-check (e.g., signature-count sanity, minimum instruction plausibility) that resists free inflation, or (3) require a lightweight proof-of-work/stake-weighted QoS credential ahead of trusting self-reported priority for filtering purposes, rather than trusting unauthenticated message content as a spam-filtering signal.

fn apply_priority_floor_to_batch(
    batch: &mut PacketBatch,
    floor: u64,
    bank: &Bank,
) -> (usize, bool) {
    let mut dropped: usize = 0;
    let mut any_kept = false;
    for mut packet in batch.iter_mut() {
        if packet.meta().discard() {
            continue;
        }
        let Some(data) = packet.data(..) else {
            // Zero-length or otherwise unreadable: leave to downstream
            // stages to reject.
            any_kept = true;
            continue;
        };
        // Unparseable packets are kept and left for downstream rejection.
        match calculate_priority_from_bytes(bank, data) {
            Some(priority) if priority <= floor => {
                packet.meta_mut().set_discard(true);
                dropped = dropped.saturating_add(1);
            }
            _ => any_kept = true,
        }
    }
    (dropped, !any_kept)
}

pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
    let fee_details = solana_fee::calculate_fee_details(
        transaction,
        bank.fee_structure().lamports_per_signature,
        transaction_configuration.priority_fee_lamports,
        bank.fee_features(),
    );
    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    (
        reward
            .saturating_mul(MULTIPLIER)
            .saturating_div(cost.saturating_add(1)),
        cost,
    )
}

/// Evaluate raw packet bytes against the pf-floor, returning the computed
/// priority.
///
/// Returns `None` if the bytes don't parse as a valid transaction, in which
/// case the caller should leave the packet to downstream stages to reject.
pub(crate) fn calculate_priority_from_bytes(bank: &Bank, data: &[u8]) -> Option<u64> {
    let view = SanitizedTransactionView::try_new_sanitized(data, &sanitize_config()).ok()?;
    let runtime_tx = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    )
    .ok()?;
    let transaction_configuration = runtime_tx
        .transaction_configuration(&bank.feature_set)
        .ok()?;
    let (priority, _cost) =
        calculate_priority_and_cost(bank, &runtime_tx, &transaction_configuration);

    Some(priority)
}

    /// Update the scheduler priority floor.
    ///
    /// Semantics: when the retained scheduler buffer is nearly full, drop
    /// arrivals that are at-or-below the current queue-min priority, i.e. no
    /// better than what the bounded scheduler candidate set would evict.
    fn update_scheduler_priority_floor(&mut self, num_dropped_on_capacity: usize) {
        let buffer_size = self.container.buffer_size();
        let saturated = self
            .saturation_state
            .update(buffer_size, num_dropped_on_capacity);
        let priority_floor = if saturated {
            self.container
                .get_min_max_priority()
                .map_or(0, |(min, _)| min)
        } else {
            0
        };

        self.saturation_state.publish_floor(priority_floor);
    }
