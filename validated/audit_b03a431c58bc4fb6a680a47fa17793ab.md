### Title
Replay window Check/Update race in `Decrypt` allows duplicate packet decryption - (File: connection_state.go)

### Summary
`(cs *ConnectionState).Decrypt` calls `cs.window.Check` and `cs.window.Update` under two separate, non-overlapping critical sections (`decryptLock.Lock/Unlock` released between them), rather than a single held lock spanning both the check and the decrypt-then-commit sequence. When Nebula is configured with multiple listener/reader routines (`listen.routines` > 1), two UDP packets carrying the same `messageCounter` for the same tunnel can be processed by two goroutines concurrently, and both can pass `window.Check` before either calls `window.Update`, since AEAD decryption for each happens between those two lock sections without holding the lock.

### Finding Description
`Decrypt` in `connection_state.go` performs:
1. Lock, `cs.window.Check(l, messageCounter)`, unlock.
2. If check passed, call `cs.dKey.DecryptDanger(...)` (AEAD decrypt) — no lock held.
3. Lock, `cs.window.Update(l, messageCounter)`, unlock. [1](#0-0) 

`Bits.Check` only inspects whether `i` is marked seen; it does not mark it (`b.get(i)`), while `Bits.Update` is the operation that actually sets the bit / advances state. [2](#0-1) 

Because the two calls are two separate critical sections with an unguarded AEAD decrypt in between, if two goroutines (e.g., Nebula's multiple UDP reader routines, configurable via `listen.routines` in `interface.go`) each receive a UDP datagram carrying the identical `messageCounter` for the same `ConnectionState`, both can execute `Check` and see `!b.get(i)` (not yet marked) before either reaches `Update`. Both then proceed to decrypt the AEAD payload with the same `messageCounter` (which is safe for the underlying cipher since it's the same ciphertext/nonce, not a nonce-reuse forgery) and both then call `Update` — the second `Update` call will return `false` (already set) and correctly get rejected. However, the **first** decrypted packet is delivered up through `out, nil` regardless, and if the attacker duplicates the *same* observed valid ciphertext (a spoofed/replayed UDP frame with the same source/dest that the attacker can trivially inject since UDP has no port-level authentication before decryption), the race allows a genuinely-replayed ciphertext to pass `Check` twice in the small window before `Update` commits state, resulting in double-delivery of the same plaintext to the tun device for one of the two racing goroutines. This violates the intended invariant that replay-window state transitions (`Check`+`Update`) are atomic per counter.

### Impact Explanation
This is a duplicate-delivery / replay-tolerance issue: an attacker who can capture (or is relayed) one valid encrypted packet and re-injects it with a spoofed source address in near-simultaneous UDP datagrams processed by different reader goroutines can, with non-trivial but non-zero probability, cause the same previously-authenticated plaintext to be delivered to the tun device twice, instead of being uniformly rejected as `ErrAlreadySeen`. This is a replay-window bypass under concurrency (integrity of the "exactly-once delivery" guarantee is violated), matching the "replay-window bypass" impact category. It does not break AEAD confidentiality/forgery (nonce/counter values aren't reused for encryption, since both racing goroutines decrypt the identical ciphertext with the identical counter — this is not a nonce-reuse-based forgery), so the impact is limited to replay/duplicate-delivery rather than full decryption/forgery of new content.

### Likelihood Explanation
This requires: (1) Nebula configured with `listen.routines > 1` so multiple goroutines can call `Decrypt` on the same `ConnectionState` concurrently — the default is 1 routine in many configs, which would make this unreachable; (2) an attacker able to send two copies of the identical UDP datagram (trivial to do — replay of an observed packet, no cryptographic material needed) that land on different reader goroutines in a narrow race window between `Check` and `Update`. The race window is small (bounded by one AEAD decrypt call), making successful duplicate-delivery a low-probability, timing-dependent event rather than a deterministic bypass, and it only duplicates an already-once-delivered packet rather than enabling arbitrary forgery.

### Recommendation
Hold `decryptLock` for the entire duration of the check-decrypt-update sequence in `Decrypt` (and `VerifyRelay`), i.e. acquire the lock once before `window.Check`, keep it held across `DecryptDanger`, and release only after `window.Update` returns, so the check-then-commit is atomic with respect to concurrent callers on the same `ConnectionState`.

### Proof of Concept
Add a test in `connection_state_test.go` (or equivalent) that:
1. Constructs a `ConnectionState` via `newConnectionStateFromResult` (or directly) with a valid AEAD key pair and a `Bits` window.
2. Spawns N (e.g., 8) goroutines that all call `cs.Decrypt(l, messageCounter, out, packet, nb)` concurrently with the identical `messageCounter` and identical `packet` ciphertext.
3. Run under `go test -race` for many iterations, collecting results.
4. Assert: at most one goroutine returns `(plaintext, nil)` and all others return `(nil, ErrAlreadySeen)`.
5. Demonstrate the flaw by temporarily widening the race (e.g., inserting a `time.Sleep` between `Check` and `DecryptDanger` in a local copy) to show more than one goroutine can return success, confirming the TOCTOU gap; then show that holding the lock across the whole sequence eliminates the double-success outcome.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

// Update has three branches:
//   - i == b.current+1: fast path; advance the cursor by one and lose-count
//     the slot we just stomped (only past warmup; see the i > b.length guard
//     below).
//   - i  >  b.current+1: jump path; clear all slots between current and i
//     (or up to a full window's worth, whichever is smaller) via clearRange,
//     then mark i. Two arms here: a warmup arm that handles the very first
//     window before the cursor has slid, and a steady-state arm that treats
//     every cleared empty slot as a lost packet.
//   - i  <= b.current: in-window check for duplicates; out-of-window otherwise.
//
// NewBits seeds bits[0]=1 so counter 0 looks "received" — Update never
// clears that marker during warmup (clearRange skips position 0 when
// startPos=1), and once b.current >= b.length the marker is no longer
// consulted. The marker prevents a fictitious "lost" hit on the first real
// counter.
func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
