### Title
Unauthenticated miner-message chunks accepted by `TryFrom<StackerDBChunksEvent> for SignerEvent<T>` - (File: libsigner/src/events.rs)

### Summary
The conversion from a raw `StackerDBChunksEvent` into a `SignerEvent` treats the `.miners` StackerDB lane differently from the `.signers-X-Y` lane: for `.signers-X-Y` chunks the code explicitly recovers and validates the signer's public key from the chunk signature (`chunk.recover_pk()`) before accepting the payload, but for `.miners` chunks it skips signature recovery entirely and blindly deserializes and forwards every modified slot's bytes as a trusted `MinerMessages` payload.

### Finding Description
`TryFrom<StackerDBChunksEvent> for SignerEvent<T>` branches on the contract name: [1](#0-0) 
For the miner lane, every chunk in `event.modified_slots` is deserialized via `T::consensus_deserialize` and pushed straight into `SignerEvent::MinerMessages` with no signature check at all.

Compare this to the signer lane just below it: [2](#0-1) 
Here, `chunk.recover_pk()` is called and any chunk whose signature can't be recovered is dropped via `filter_map`/`None`.

The `StackerDBChunksEvent` is populated purely from whatever the node's StackerDB event dispatcher reports as "modified slots" for that contract — i.e., chunks that were stored in the local StackerDB replica. Because StackerDB writes are already gated by `try_replace_chunk`'s slot-signer check ( [3](#0-2) ) or by `validate_received_chunk`'s equivalent check ( [4](#0-3) ), a chunk stored under an *existing* slot ID always carries a signature that verifies against that slot's assigned signer address. However, the equality being relied upon by the `.miners` branch — "chunk is present in `modified_slots` for the miners contract" implies "chunk was written by the party lawfully authorized for that slot" — is never itself checked *at the point of consumption* in `libsigner`. Any code path that later reconfigures slot ownership, or any additional consumer (e.g. a differently configured event observer, replay tooling, or a future contract with more slots/writers) that feeds `StackerDBChunksEvent` data into this same conversion function without the node-level slot-authorization guarantee holding, will have its `.miners` messages accepted without any signature check, whereas the almost-identical `.signers-X-Y` branch does check.

The docstring updated in `signer_message_payload_matches_lane` explicitly notes that miner messages are exempted from the signer-message type-checking that other lanes get: [5](#0-4) 
i.e., the asymmetry between the two lanes' validation levels is intentional in terms of payload-type checking, but it also carries over to signature verification, which has no such justification: miner-authored `BlockProposal`/`BlockPushed` messages have no other authenticity check performed inside `libsigner` before being surfaced to the running signer's `SignerRunLoop`.

### Impact Explanation
If the equality "modified_slots for `.miners` implies signer-verified" is ever violated by an upstream caller or a future refactor (e.g. `StackerDBChunksEvent` populated from an unauthenticated or partially-validated source, or a new slot added to the miners contract with different write semantics), a forged/garbage `MinerMessages` payload would be forwarded straight into the signer's decision pipeline unauthenticated, whereas the equivalent `.signers` lane would reject it. This is a real asymmetry in the trust model between two code paths that should offer equal guarantees, and it means the signature check for `.miners` chunks lives entirely outside `libsigner`, undocumented at the point of use — a latent trap for any future consumer of `TryFrom<StackerDBChunksEvent>`.

### Likelihood Explanation
Low likelihood as a standalone remote exploit against the current node/StackerDB pipeline, since `try_replace_chunk` and `validate_received_chunk` do gate writes to the underlying StackerDB by slot signer today. The risk is entirely in the missing defense-in-depth at the `libsigner` boundary: this function has no way to independently confirm authenticity, unlike its sibling branch, so any regression or alternate integration bypasses signer authentication silently rather than failing loudly.

### Recommendation
Add an explicit signer/authenticity check for the `.miners` branch mirroring the `.signers-X-Y` branch (recover and validate `chunk.recover_pk()` against the known miner's public key hash, or otherwise verify chunk provenance) inside `TryFrom<StackerDBChunksEvent> for SignerEvent<T>`, rather than relying solely on an implicit invariant enforced only in `stackslib::net::stackerdb`.

### Proof of Concept
1. Construct a `StackerDBChunksEvent` with `contract_id` set to the `.miners` boot contract name and `modified_slots` containing a chunk whose `sig` field is `MessageSignature::empty()` (or any arbitrary/forged signature) and whose `data` is a validly-encoded `T` (e.g., `BlockProposal`).
2. Call `SignerEvent::<T>::try_from(event)`.
3. Observe that the resulting `SignerEvent::MinerMessages(messages)` includes the deserialized message with no signature validation attempted — contrast with an identical construction against a `.signers-0-1` contract chunk with a forged/empty signature, which is filtered out by the `chunk.recover_pk()` check and never surfaces in `SignerEvent::SignerMessages`.

/// Whether a `SignerMessage` payload type is the one expected for the given contract message id.
///
/// `lane_message_id` is the trailing number in the `signers-X-{lane_message_id}` boot
/// contract. Each signer-message contract is dedicated to exactly one `SignerMessage`
/// variant, so the payload's type-prefix byte must map to the same numeric `MessageSlotID`.
///
/// Miner-only payloads (`BlockProposal`, `BlockPushed`, `MockProposal`, `MockBlock`) are not
/// written to a signer contract and never match.
fn signer_message_payload_matches_lane(
    payload_kind: SignerMessageTypePrefix,
    lane_message_id: u32,
) -> bool {
    payload_kind
        .msg_id()
        .is_some_and(|slot| slot.to_u32() == lane_message_id)
}
