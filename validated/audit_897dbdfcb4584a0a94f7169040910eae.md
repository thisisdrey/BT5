### Title
Stale/zero account index in `RewardsDistributor` credits a full-balance reward delta when the token index still equals `INITIAL_INDEX` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary

The bug class behind CVE-2017-6469 is "code path uses a data structure that was never allocated/initialized." The Metronome analog is `RewardsDistributor._calculateTokenDelta`: when a token's reward `TokenState` has just been allocated (`index == INITIAL_INDEX`) but a user's per-account `accountIndexOf` was never initialized, the function computes `_deltaIndex = _tokenIndex - 0 = INITIAL_INDEX` instead of initializing the account index to `INITIAL_INDEX`. The uninitialized account slot is treated as index `0`, inflating `_tokensDelta` to `balance * 1e18` worth of claimable rewards.

### Finding Description

In `contracts/RewardsDistributor.sol`:

```solidity
function _calculateTokenDelta(
    TokenState memory _tokenState,
    IERC20 token_,
    address account_
) private view returns (uint256 _tokenIndex, uint256 _tokensDelta) {
    _tokenIndex = _tokenState.index;
    uint256 _accountIndex = accountIndexOf[token_][account_];

    if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
        _accountIndex = INITIAL_INDEX;
    }

    uint256 _deltaIndex = _tokenIndex - _accountIndex;
    _tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
}
``` [1](#0-0) 

The fallback only initializes `_accountIndex` to `INITIAL_INDEX` when `_tokenIndex > INITIAL_INDEX`. When `_tokenIndex == INITIAL_INDEX` — i.e., the token state was allocated by `_updateTokenSpeed` (`tokenStates[token_] = TokenState({index: INITIAL_INDEX, ...})` at line 298) but the global index has not yet grown — `_accountIndex` stays `0` and `_deltaIndex` becomes `1e18`. `wadMul` then yields `_tokensDelta = balanceOf(account_)`.

`_updateTokensAccruedOf` writes this delta into `tokensAccruedOf[account_]` (lines 261–266), which is paid out by `claimRewards` via `_transferRewardIfEnoughTokens` (lines 150–168, 248–256).

The window is reachable by an unprivileged attacker:

1. Governor calls `updateTokenSpeed(token_, speed_ > 0)`, which allocates `TokenState{index: INITIAL_INDEX, timestamp: now}` (line 298).
2. In the same block (before `_deltaTimestamps > 0` accrues index growth), the attacker triggers any path that calls `_updateTokensAccruedOf` on an account holding `DepositToken`/`DebtToken` balance:
   - `DepositToken.transfer` → `updateRewardsBeforeTransfer` → `IRewardsDistributor.updateBeforeTransfer` (guarded only by `tokenStates[token_].index > 0`, which is `INITIAL_INDEX > 0` = true, line 187).
   - `DebtToken.issue`/`repay`, `DepositToken.deposit`/`withdraw`/`flashWithdraw` → `updateBeforeMintOrBurn` (line 176). Note mint paths check the pre-mint balance, so an attacker must hold balance first (e.g., deposit earlier, or transfer an existing balance).
3. `_calculateTokenIndex` returns `(0, 0)` because `_deltaTimestamps == 0`, so `_updateTokenIndex` is a no-op and `_tokenIndex` stays `1e18` (lines 271–282, 197–212).
4. `_calculateTokenDelta` returns `_tokensDelta = balance`, so `tokensAccruedOf[attacker] += balance`.
5. Attacker calls `claimRewards(attacker)`; `_transferRewardIfEnoughTokens` transfers `rewardToken` up to the distributor's balance (lines 248–256).

The same underflow-free miscrediting also occurs whenever `speed` is `0` (index stays `INITIAL_INDEX` indefinitely — lines 209–211 only bump the timestamp), though the token must have been allocated first, which only happens via a nonzero speed.

### Impact Explanation

Direct theft of unclaimed yield: the attacker is credited `tokensAccruedOf` equal to their deposit/debt token balance (denominated in reward tokens), which drains the distributor's `rewardToken` balance — funds intended for legitimate reward accrual of all users. With a large deposit (including same-block deposit → transfer via a contract, since deposits mint before rewards update in `deposit`, the attacker can hold a pre-existing balance from a prior tx), the theft is bounded only by the distributor's `rewardToken` inventory.

### Likelihood Explanation

- Requires a same-block window after `updateTokenSpeed` activates a new reward token (front-running/sandwiching a governor transaction is within the allowed attacker model and feasible via bundles on mainnet or public L2 mempools).
- No privileged role needed for the exploit path: `updateBeforeTransfer`/`updateBeforeMintOrBurn`/`claimRewards` are callable through public `DepositToken`/`DebtToken`/`RewardsDistributor` functions.
- Modifiers don't block it: `nonReentrant` on `claimRewards` only protects the claim function itself; the crediting happens in unguarded `updateBefore*` hooks. Pause flags on `DepositToken` do not cover `RewardsDistributor` directly.
- Magnitude scales with attacker-controlled balance, so a whale or flash-funded position maximizes the theft.

### Recommendation

Initialize the account index whenever the stored index is uninitialized and the token state exists, not only when it has grown:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

Equivalently, treat `_accountIndex == 0` as "no recorded index" and default it to `INITIAL_INDEX` whenever `tokenStates[token_].index > 0`. Alternatively, skip delta accrual when `_deltaIndex == 0` would otherwise be produced by an uninitialized account against a just-allocated token state.

### Proof of Concept

Hardhat test sketch (against deployed-style upgradeable contracts, mock `rewardsDistributor`/`pool` wiring as in `test/DepositToken.test.ts`):

```typescript
// Setup: pool with DepositToken (msdToken) and RewardsDistributor (rd) registered
// alice deposits underlying beforehand and holds msdToken balance B

// 1. Governor activates reward speed for msdToken
await rd.connect(governor).updateTokenSpeed(msdToken.address, parseEther('1'));
// tokenStates[msdToken] = { index: 1e18, timestamp: now }

// 2. Same block: attacker (alice) triggers updateBeforeTransfer via a self-transfer
await msdToken.connect(alice).transfer(alice.address, 1); // or transfer to bob

// 3. tokensAccruedOf[alice] == alice's msdToken balance (should be ~0)
expect(await rd.tokensAccruedOf(alice.address)).eq(await msdToken.balanceOf(alice.address));

// 4. Fund distributor and claim
await rewardToken.mint(rd.address, amount);
await rd.connect(alice).claimRewards(alice.address);
// alice steals rewardToken equal to her deposit balance (capped by distributor balance)
```

A Foundry fork test can pin `block.timestamp` to the governor `updateTokenSpeed` block, call `msdToken.transfer` as a holder, then assert `tokensAccruedOf` and the claimed `rewardToken` amount.
