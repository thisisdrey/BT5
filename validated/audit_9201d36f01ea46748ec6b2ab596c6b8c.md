## Analysis: AMM-style price manipulation analog in java-tron's `Exchange` (TRX/TRC10 relay-pool) feature

The JUDAO incident is a flash-loan-assisted AMM reserve/price manipulation on an external DEX pool. The closest reachable analog in java-tron is the native `Exchange` module — a Bancor-style relay-token liquidity pool for TRX↔TRC10 pairs that any unprivileged account can trade against via a single signed `ExchangeTransactionContract`.

### Title
Floating-point Bancor relay-formula rounding in `ExchangeProcessor` allows single-transaction reserve/price manipulation and pool drainage - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeCapsule.transaction()` [1](#0-0)  computes AMM-style swap output using `ExchangeProcessor`, which by default (unless the `AllowHardenExchangeCalculation` committee proposal is active) performs the Bancor relay math with `double` floating-point arithmetic and `Math.pow` [2](#0-1) . This is invoked directly from `ExchangeTransactionActuator.execute()`, reachable by any account submitting a broadcastable `ExchangeTransactionContract` [3](#0-2) .

### Finding Description
Unlike the JUDAO PancakeSwap pool (external, product-formula AMM manipulated by flash-loaned capital), java-tron's `Exchange` is a first-party, protocol-level liquidity pool. Pool state (`firstTokenBalance`/`secondTokenBalance`) is fully attacker-observable and directly moved by `ExchangeCapsule.transaction()` based on the output of `ExchangeProcessor.exchange()` [4](#0-3) .

The non-hardened path (the default unless a committee proposal enables `allowHardenExchangeCalculation`, see `AbstractExchangeActuator.allowHarden()` [5](#0-4) ) uses `double`-precision `Math.pow` calls with exponents `0.0005` and `2000.0` to model the constant-supply relay-token curve [6](#0-5) . This floating-point implementation is not guaranteed to be monotonic or self-consistent for round-trip trades: because output amounts are truncated via `(long) issuedSupply` / `(long) exchangeBalance` casts and the internal `supply` state is mutated with each call, a sequence of large trades (a big sell followed by a reversing large sell) executed by a single account can walk the pool through floating-point/rounding edge cases that don't cancel out — extracting net value from the pool's reserves without providing equivalent input, exactly as flash-loan/manipulation attacks extract value from AMM pools by moving the price sharply and reverse-trading before it recovers.

Unlike the hardened `SafeExchangeProcessor`, which uses `BigDecimal` with explicit `RoundingMode` and `longValueExact()` [7](#0-6) , the default `ExchangeProcessor` path offers no such precision guarantees. There is also no protection limiting how much a single trade can move the pool price/reserves relative to pool depth — only a static absolute `EXCHANGE_BALANCE_LIMIT` cap unrelated to price-impact [8](#0-7) , and the caller-supplied `expected` slippage floor only protects the caller's own trade, not the pool from being drained by the caller across sequential trades [9](#0-8) .

### Impact Explanation
Because the Exchange pool holds real TRX and TRC10 asset balances contributed by the market maker who created/injected into the pool, an attacker who can systematically extract more value than they deposit via repeated large trades causes a concrete, permanent loss of pooled funds — the same end-state as the JUDAO incident (drained BUSD-JUDAO liquidity). This affects any TRX/TRC10 Exchange pair created via `ExchangeCreateActuator`, not just a hypothetical single asset.

### Likelihood Explanation
Any account with sufficient TRX/TRC10 balance can call `ExchangeTransactionContract` directly — no special permission, SR/witness status, or contract deployment is required [10](#0-9) . The floating-point Bancor math path is the *default* production code path (hardened math requires an explicit committee proposal to be activated), so the vulnerable arithmetic is live unless the proposal has been passed on the target chain.

### Recommendation
Force the hardened `SafeExchangeProcessor` (BigDecimal-based, exact rounding) as the only calculation path for `ExchangeCapsule.transaction()`, removing the double-precision `ExchangeProcessor` fallback, or add price-impact/slippage limits per trade relative to pool depth in `ExchangeTransactionActuator.doValidate()`.

### Proof of Concept
Conceptually: repeatedly call `ExchangeTransactionContract` alternating sell direction on the same exchange pair with tokenQuant values chosen to land on floating-point rounding boundaries in `exchangeToSupply`/`exchangeFromSupply` (`chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java` lines 17-39). Each such round-trip, when `allowHardenExchangeCalculation` is not yet enabled, can leave the attacker's combined asset+TRX balance net positive relative to the pool's, cumulatively draining `firstTokenBalance`/`secondTokenBalance` in `ExchangeCapsule` over many transactions — the existing unit test `ExchangeCapsuleTest.testExchange` (`framework/src/test/java/org/tron/core/capsule/ExchangeCapsuleTest.java` lines 108-143) demonstrates the non-hardened vs. hardened math divergence in practice on the same reserves.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
