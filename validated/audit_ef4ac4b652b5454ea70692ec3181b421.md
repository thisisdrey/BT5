### Title
Newly reward-enabled DepositToken/DebtToken lets existing holders instantly claim `balanceOf` worth of reward token - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._updateTokenSpeed` initializes a newly listed token's `tokenStates[token_].index` to `INITIAL_INDEX` (1e18). `_calculateTokenDelta` only back-fills a missing `accountIndexOf` to `INITIAL_INDEX` when the current index is **strictly greater** than `INITIAL_INDEX`. While the token index is still exactly `INITIAL_INDEX` (the same block/timestamp the speed was set, or any period where supply was 0 so the index never moved), an account with `accountIndexOf == 0` keeps `_accountIndex = 0`, producing `_deltaIndex = 1e18` and `_tokensDelta = balanceOf(account).wadMul(1e18) = balanceOf(account)`. A pre-existing holder can therefore instantly accrue reward tokens equal to their full share balance via the permissionless `claimRewards`/`updateBeforeMintOrBurn` paths — the exact analog of a newly added vault inheriting a zeroed `lastRewardPerShare` checkpoint.

### Finding Description
Relevant code in `contracts/RewardsDistributor.sol`:

- Token initialization on first non-zero speed (lines 294–303):
```solidity
} else if (newSpeed_ > 0) {
    if (tokenStates[token_].index == 0) {
        tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp.toUint32()});
        tokens.push(token_);
    }
```
- Account delta calculation (lines 222–230):
```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```
- Permissionless entry points: `claimRewards(address[],IERC20[])` (line 150) and `updateBeforeMintOrBurn` (line 175, explicitly "may be called by anyone") iterate `tokens` and call `_updateTokensAccruedOf`, then `_transferRewardIfEnoughTokens` (lines 248–256) pays out if the distributor holds enough `rewardToken`.

When the governor calls `updateTokenSpeed(token, speed>0)` for a DepositToken/DebtToken that already has holders, `index` is set to `INITIAL_INDEX` at the current timestamp. `_calculateTokenIndex` only advances the index when `_deltaTimestamps > 0 && _speed > 0`; within the same block the index remains `INITIAL_INDEX`. The strict `>` comparison means the `accountIndexOf == 0` fallback is skipped, so `deltaIndex = 1e18` and the holder is credited `balanceOf` reward tokens — for rewards that were never distributed, i.e., retroactive accrual from a zero-equivalent checkpoint.

### Impact Explanation
Theft of unclaimed yield: an attacker holding (or flash-acquiring and holding through the block) a large DepositToken/DebtToken balance receives `balanceOf` units of `rewardToken` instantly, paid out of the `RewardsDistributor`'s reward token balance that is meant to be emitted pro-rata over time at `tokenSpeeds`. The payout is capped only by the distributor's reward token balance (`_transferRewardIfEnoughTokens` pays `min(accrued, balance)`), so a sufficiently large holder drains the entire reward reserve in one call, and `tokensAccruedOf` is reset only for that account, leaving honest users' future emissions unfunded.

### Likelihood Explanation
Requires only unprivileged actions: the attacker must hold shares of a token at the moment its speed is first set (or front-run the governor's `updateTokenSpeed` transaction, or act in any window where the index is still exactly `INITIAL_INDEX`, e.g., when total supply was 0 during elapsed time). `claimRewards` has no `onlyGovernor`/ SynthContext restriction and `nonReentrant` does not block this. Existing holders of DepositToken/DebtToken are common, and reward-token funding typically precedes or accompanies speed configuration, so the window is realistic whenever governance enables rewards on an already-live market. No keeper, governor key, oracle manipulation, or privileged role is needed by the attacker.

### Recommendation
- Initialize the per-token index in a way that never lets `accountIndexOf == 0` resolve to `0` delta base: change the fallback to `if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) _accountIndex = INITIAL_INDEX;` (i.e., clamp to `INITIAL_INDEX` or to the current index whenever the stored account index is 0).
- Alternatively, when a token is first listed, also record `accountIndexOf` lazily as `_tokenIndex` (not `INITIAL_INDEX`) so no past or same-block accrual is credited to pre-existing balances.

### Proof of Concept
Hardhat-style outline (repo uses Hardhat; existing suite `test/RewardDistributor.test.ts` provides the fixture pattern with mocked `msdTOKEN1`):

```ts
// 1. Deploy Pool + DepositToken (msdTOKEN1) + RewardsDistributor; fund distributor with rewardToken.
// 2. Attacker deposits collateral and holds depositToken balance B BEFORE rewards are enabled.
//    (mint already happened while tokenStates.index == 0, so no index bookkeeping ran)
// 3. Governor calls: rewardsDistributor.updateTokenSpeed(msdTOKEN1, speed)
//    -> tokenStates = {index: 1e18, timestamp: now}
// 4. In the SAME block (or via automine off), attacker calls:
await rewardsDistributor.claimRewards(attacker.address, [msdTOKEN1.address]);
//    _calculateTokenDelta: accountIndex==0, tokenIndex==1e18 (not > INITIAL_INDEX)
//    -> deltaIndex = 1e18 -> tokensDelta = B
//    -> _transferRewardIfEnoughTokens transfers min(B, rewardToken balance) to attacker.
expect(await rewardToken.balanceOf(attacker.address)).to.eq(B); // stolen reward reserve
```

The same path is reachable via `updateBeforeMintOrBurn(msdTOKEN1, attacker)` followed by `claimRewards(attacker)`, since both functions are callable by anyone.
