### Title
Integer-division rounding to zero in `MarketSellAssetActuator.matchSingleOrder` allows a maker's asset to be given away for free (`equal-fill` branch) - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes cross-rate conversions with a floor-dividing helper, `MarketUtils.multiplyAndDivide`. Two of the three fill branches (the "taker > maker" branch) explicitly guard against the division rounding down to `0` and return the leftover asset to the maker in that case. The third branch — the "taker == maker" (exact fill) branch — performs the identical rounding division but has **no such guard**, so it is reachable to fully close a maker's order (`setSellTokenQuantityRemain(0)`, mark `INACTIVE`) while crediting the maker with `0` tokens.

### Finding Description
In `matchSingleOrder` [1](#0-0) , `takerBuyTokenQuantityRemain` is computed via `MarketUtils.multiplyAndDivide(...)`, which does a floor integer division, and the code explicitly checks for a `0` result and bails out.

When `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` ("taker == maker" exact-fill branch), the code computes `makerBuyTokenQuantityReceive` with the same rounding-down division: [2](#0-1) 

Unlike the third ("taker > maker") branch, which performs an identical computation and explicitly checks `if (makerBuyTokenQuantityReceive == 0)` to return the maker's remaining sell tokens instead of consuming the order for free [3](#0-2) , the "taker == maker" branch has no such zero-check. It unconditionally does `makerOrderCapsule.setSellTokenQuantityRemain(0)` and marks the maker order `INACTIVE`, then later calls `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` with `makerBuyTokenQuantityReceive == 0` [4](#0-3) .

`MarketUtils.multiplyAndDivide` truncates via integer floor division, so any pair of order ratios/remainders that make `R*B < S` (maker's remaining sell qty * maker's original buy qty < maker's original sell qty) will floor to `0`, and it is possible to reach this exact-fill branch with integers (e.g. `makerSellQuantity=100`, `makerBuyQuantity=99`, maker remaining sell quantity `R=1`, taker remaining sell (paying) quantity `t=1` produces `takerBuyTokenQuantityRemain = floor(1*100/99) = 1 == R`, triggering the exact-fill branch, while `makerBuyTokenQuantityReceive = floor(1*99/100) = 0`).

### Impact Explanation
This is a concrete, permanent, unauthorized loss of a maker's asset: the maker's remaining sell-token balance is zeroed out and the order marked completed/inactive, but the maker receives `0` of the buy token in return — the sold asset is effectively given away for free to the taker (theft of funds / permanent freezing-equivalent loss for the maker). This is reachable purely from an unprivileged, ordinary transaction broadcaster placing `MarketSellAssetContract` orders (an order placer scenario explicitly in scope), with no special privileges required — only carefully chosen small residual order quantities/ratios.

### Likelihood Explanation
Reaching the exact numeric conditions requires the attacker (or an unlucky ordinary user) to place orders whose remaining quantities happen to satisfy `floor(t*S/B) == R` and `R*B < S` simultaneously. This is achievable deterministically by the taker: an attacker can create the maker order themselves (or wait for a naturally-partially-filled maker order) and then submit a taker order with a computed sell quantity `t` to intentionally trigger the exact-fill branch while making `makerBuyTokenQuantityReceive` round to zero. Because `MarketOrder` quantities are attacker-controlled `long` values with no minimum granularity enforced relative to price ratios (`validate()` only checks `sellTokenQuantity <= 0` and against a coarse `quantityLimit`, not against price-ratio precision) [5](#0-4) , this is practically exploitable and repeatable, not merely a low-probability edge case.

### Recommendation
Add the same zero-result guard used in the "taker > maker" branch to the "taker == maker" exact-fill branch: if `makerBuyTokenQuantityReceive == 0` after `MarketUtils.multiplyAndDivide`, return the maker's remaining sell-token quantity to the maker (via `returnSellTokenRemain`) instead of zeroing it out and marking the order inactive with no consideration received.

### Proof of Concept
1. Create maker order: sell token A quantity `100`, buy token TRX quantity `99` (ratio `S=100 : B=99`), and have it partially filled elsewhere until `makerOrderCapsule.getSellTokenQuantityRemain() == 1`.
2. Submit a taker `MarketSellAssetContract` order selling `TRX` quantity `1` against buying token `A`, matching against the above maker price.
3. In `matchSingleOrder`: `takerBuyTokenQuantityRemain = multiplyAndDivide(1, 100, 99) = floor(100/99) = 1`, which equals `makerOrderCapsule.getSellTokenQuantityRemain() == 1`, entering the "taker == maker" branch.
4. `makerBuyTokenQuantityReceive = multiplyAndDivide(1, 99, 100) = floor(99/100) = 0`.
5. Code executes `makerOrderCapsule.setSellTokenQuantityRemain(0)` and marks the maker order `INACTIVE`, then credits the maker with `addTrxOrToken(makerOrderCapsule, 0)` — the maker's last `1` unit of token A is consumed with `0` TRX paid, while the taker receives `1` unit of token A via `addTrxOrToken(takerOrderCapsule, 1, ...)` without a corresponding deduction of their own sell-side (TRX) balance in this branch.
