### Title
Unbounded per-field memory allocation in `git check-attr` output parsing via attacker-controlled `.gitattributes` content - ([File: internal/git/gitattributes/check_attr.go])

### Summary
`CheckAttrCmd.Check` reads each NUL-delimited field of `git check-attr --stdin -z` output using `bufio.Reader.ReadBytes('\000')` with no cap on the size of an individual field. Because the third field (`info`/attribute value) is derived directly from attacker-controlled `.gitattributes` content, a repo owner can craft a huge, NUL-free attribute value that forces Gitaly to buffer that entire value in memory for a single `Check()` call, and repeat this over many requested paths to multiply the memory pressure.

### Finding Description
`gitattributes.CheckAttr` spawns `git check-attr --stdin -z --source=<revision>` and `CheckAttrCmd.Check(path)` parses the output as `<path>\0<attribute>\0<info>\0` triples using `c.stdout.ReadBytes('\000')` in a loop bounded only by `c.count` (number of requested attribute names), not by field length: [1](#0-0) 

`bufio.Reader.ReadBytes` has no maximum size; it grows its internal slice until the delimiter is found or EOF/error occurs. The `info` field for a custom (non-boolean) gitattributes value is whatever string is assigned in the `.gitattributes` file (e.g. `*.txt myattr=<huge-string>`), and git-check-attr does not truncate or limit this value's length. Since `.gitattributes` content is fully attacker-controlled (any repo owner can push it), an attacker can craft an attribute value of hundreds of MB or more with no embedded NUL byte, and that value is buffered wholesale into Go memory on the read of one triple.

This is reachable from `GetFileAttributes`, which calls `gitattributes.CheckAttr` and then `checkAttrCmd.Check(path)` for every path in `in.GetPaths()`, an attacker-controlled repeated field: [2](#0-1) 

`validateGetFileAttributesRequest` only checks that `Revision`, `Paths`, and `Attributes` are non-empty; it does not bound the number of paths nor inspect `.gitattributes` content or size: [3](#0-2) 

There is no `storage.ValidateRelativePath`, revision validation, or size-limiting mechanism in this path that would cap the size of a single attribute value returned by `git check-attr`. Requesting many paths (`in.GetPaths()` has no upper bound enforced) each matching the crafted pattern multiplies the allocation, since each `Check(path)` call re-reads the same oversized value from the persistent subprocess stream.

### Impact Explanation
A malicious `.gitattributes` blob combined with a `GetFileAttributes` request for many paths causes the Gitaly process to allocate memory proportional to attacker-chosen data size times number of requested paths, with no upper bound. This can exhaust process memory and crash or degrade the Gitaly node, causing denial of service for all repositories co-located on that storage node (repository/service crash, matching GitLab's "Denial of Service" bounty impact class for a Gitaly RPC handler).

### Likelihood Explanation
The only precondition is push access to a repository the attacker controls (a standard unprivileged capability — fork/import/push), and the ability to call `GetFileAttributes` (an ordinary, non-privileged RPC exposed to any client with repository read access, e.g. via GitLab Rails on file browsing/attribute lookups). No special configuration, secrets, or privileged roles are required, making this straightforward and repeatable.

### Recommendation
Bound the size of individual fields read via `ReadBytes('\000')`, e.g. by using `io.LimitReader` per field or a `bufio.Reader` size cap, and reject/abort the `check-attr` parsing with an error once a configurable maximum field length is exceeded. Additionally consider capping the number of paths processed per `GetFileAttributes` request and enforcing a maximum `.gitattributes` line/value length consistent with reasonable attribute usage.

func (s *server) GetFileAttributes(ctx context.Context, in *gitalypb.GetFileAttributesRequest) (*gitalypb.GetFileAttributesResponse, error) {
	if err := validateGetFileAttributesRequest(ctx, s.locator, in); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(in.GetRepository())

	checkAttrCmd, finishAttr, err := gitattributes.CheckAttr(ctx, repo, git.Revision(in.GetRevision()), in.GetAttributes())
	if err != nil {
		return nil, structerr.New("check attr: %w", err)
	}

	defer finishAttr()

	var attrValues []*gitalypb.GetFileAttributesResponse_AttributeInfo

	for _, path := range in.GetPaths() {
		attrs, err := checkAttrCmd.Check(path)
		if err != nil {
			return nil, structerr.New("check attr: %w", err)
		}

		for _, attr := range attrs {
			attrValues = append(attrValues, &gitalypb.GetFileAttributesResponse_AttributeInfo{Path: path, Attribute: attr.Name, Value: attr.State})
		}
	}

	return &gitalypb.GetFileAttributesResponse{AttributeInfos: attrValues}, nil

func validateGetFileAttributesRequest(ctx context.Context, locator storage.Locator, in *gitalypb.GetFileAttributesRequest) error {
	if err := locator.ValidateRepository(ctx, in.GetRepository()); err != nil {
		return err
	}

	if len(in.GetRevision()) == 0 {
		return errors.New("revision is required")
	}

	if len(in.GetPaths()) == 0 {
		return errors.New("file paths are required")
	}

	if len(in.GetAttributes()) == 0 {
		return errors.New("attributes are required")
	}

	return nil
