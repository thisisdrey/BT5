### Title
Stale `PromiseYield`/`YieldIdToDataId`/`DataIdToYieldId` trie state survives `remove_account`, allowing yield-resume replay against a re-created account - ([File: core/store/src/utils/mod.rs:505-575], [File: runtime/runtime/src/ext.rs:428-440])

### Summary
`remove_account` in `core/store/src/utils/mod.rs` only removes the `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie rows for a deleted account, but never touches `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId` rows. Because `get_data_id_for_yield_id`/`submit_promise_resume_data_with_yield_id` resolve purely by `account_id` text with no binding to account "generation," a caller who knows a `yield_id` chosen before account deletion can still resolve/resume it once the same account name is re-created.

### Finding Description
`create_promise_yield_receipt_with_id` writes bidirectional mappings via `set_yield_id_mapping` [1](#0-0) , storing `TrieKey::YieldIdToDataId`/`TrieKey::DataIdToYieldId` keyed only by `receiver_id` (= the calling account) and the attacker-chosen `yield_id` [2](#0-1) . `submit_promise_resume_data_with_yield_id` resolves the mapping purely against `self.account_id` and the supplied `yield_id`, with no check that the mapping was created by the current "incarnation" of the account [3](#0-2) .

`remove_account`, invoked when an account is deleted, removes `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`, but never issues `state_update.remove(...)` for `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId` [4](#0-3) . The dedicated cleanup helper `remove_yield_id_mappings` exists in the same file but is never called from `remove_account` [5](#0-4) .

As a result, after `x.near` is deleted and re-created, the stale `YieldIdToDataId`/`DataIdToYieldId`/`PromiseYieldStatus`/`PromiseYieldReceipt` rows persist in state and remain resolvable by anyone who knows the original `yield_id`. If the redeployed contract's own logic ever calls the `promise_yield_resume_with_yield_id` host function with a caller-supplied `yield_id` (a common oracle/callback pattern), it will unknowingly resume the pre-deletion parked receipt, which then executes its originally-specified `FunctionCall` action against the *current* code deployed at that account name — feeding attacker-controlled data into a callback the new account owner never intended to expose to that data.

### Impact Explanation
This is an authorization/state-integrity gap: account re-creation is expected to start from a clean slate, but promise-yield bookkeeping silently survives `remove_account`. This can let an attacker inject data into (or trigger) a parked promise-yield callback against a re-created account under the same name, which the new owner has no way to detect or prevent, matching the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Exploitability is contingent on: (1) the attacker owning/controlling `x.near` prior to deletion and choosing their own `yield_id` (cheap, fully attacker-controlled); (2) the account being deletable while a promise-yield receipt is still parked (no explicit check in `DeleteAccount` blocks this); and (3) the re-created account's new contract independently invoking `promise_yield_resume_with_yield_id` with a caller-controlled `yield_id` value. Conditions (1) and (2) are directly reachable by an unprivileged attacker at negligible cost. Condition (3) depends on the victim's contract design (e.g., generic oracle/callback-resume patterns are common), making this feasible but not universally triggerable against arbitrary contracts.

### Recommendation
Extend `remove_account` to also enumerate and remove `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` rows for the account being deleted (using the existing `remove_promise_yield_receipt`, `remove_promise_yield_status`, and `remove_yield_id_mappings` helpers), mirroring the cleanup already done for access keys and contract data.

### Proof of Concept
Unit test in `core/store/src/utils/mod.rs` (or a runtime integration test):
1. Set up a `TrieUpdate`, call `set_yield_id_mapping(&mut su, &account_id, yield_id, data_id)`, `set_promise_yield_status(&mut su, &account_id, data_id, Yielded)`, and write a `PromiseYieldReceipt` for `(account_id, data_id)`.
2. Call `remove_account(&mut su, &account_id)`.
3. Assert `get_data_id_for_yield_id(&su, &account_id, yield_id)` still returns `Some(data_id)`, `has_promise_yield_status(&su, &account_id, data_id)` and `has_promise_yield_receipt(&su, account_id.clone(), data_id)` still return `true` — proving the rows were not purged despite account removal, confirming the mapping remains resolvable if the account name is later re-created and the same `data_id`/`yield_id` are queried again.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
