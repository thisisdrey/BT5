### Title
Unverified peer inventory claims allow a single colluding peer to become the exclusive source for an attachment request, and `extend_with_attachments` stores the response without validating it against `content_hash` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::get_prioritized_attachments_requests` builds `AttachmentRequest.sources` purely from unauthenticated peer-reported inventory bits, with no check that the bit corresponds to real matching bytes. `extend_with_attachments` then inserts whatever `Attachment` a queried peer returns directly into `self.attachments` with no comparison to the `content_hash` that was requested, so a lying peer's garbage payload is accepted as if it satisfied the request.

### Finding Description
In `get_prioritized_attachments_requests` (download.rs:404-478), for each missing `(attachment_index, content_hash)` the code iterates `self.inventories` responses from `self.peers` (populated from unauthenticated `network.get_outbound_sync_peers()`), and treats `search_page.inventory.get(position_in_page) == 1` as sufficient proof of possession: [1](#0-0) 
There is no cryptographic or content-based verification tying the inventory bit to `content_hash` — it is a self-reported claim from `GetAttachmentsInvResponse.pages[].inventory`. If only one peer (the attacker) claims the bit, `sources` will contain exactly that peer and the request is issued to them.

Later, when the actual attachment bytes are fetched, `extend_with_attachments` (download.rs:530-558) does: [2](#0-1) 
It calls `response.decode_atlas_get_attachment()` and, on success, unconditionally does `self.attachments.insert(response.attachment)` — there is no assertion that `Attachment::hash()` (or any content-hash) of the returned bytes equals `request.content_hash`. The `AttachmentRequest` struct carries `content_hash` (used for prioritization/dedup via `enqueued.insert(content_hash)` at line 473) but it is never used to validate the response payload before insertion.

Consequently, the "peer claims to have attachment X" and "peer actually served bytes matching hash(X)" equality is never enforced along this code path: the first equality (inventory bit) is attacker-controlled with no proof-of-possession, and the second equality (served bytes vs. requested hash) is not checked at all in `extend_with_attachments`.

### Impact Explanation
This matches the "attachment/BNS mismatch" impact category. An attacker running an ordinary outbound-reachable peer can advertise itself as holding the attachment for a `content_hash` it never received (as tracked by the node's `AttachmentInstance` events from chain state), forcing the requesting node to fetch from it exclusively when no honest peer also advertises the same bit for that page/position. The attacker's arbitrary response bytes are decoded and inserted into `self.attachments` unconditionally. If the resulting `Attachments` collection is subsequently persisted (via `AtlasDB` insertion paths keyed off the state-machine `Done` context) without a hash re-check at that later stage, the node would end up associating unverifiable data with an attachment instance whose provenance was supposed to be verified on-chain (`content_hash` from `attachments_instances`). This is repeatable per attachment/page the node is missing.

### Likelihood Explanation
The attacker only needs to run a normal Stacks P2P peer, be discovered via `get_outbound_sync_peers()`, and respond to `GET /v2/attachments/{hash}`-style RPC with a crafted `GetAttachmentsInvResponse`/`Attachment` payload. No secret, no privileged role, no StackerDB slot ownership, and no special timing is required — this is reachable from any outbound-connectable peer slot. The main precondition for full exploitation (making the attacker the *exclusive* source) is that no other peer in `self.peers` advertises the same bit; if honest peers also serve the attachment correctly, `sources` will contain them too and the honest data may still be accepted as `succeeded`, but the vulnerable code path still stores whichever peer's response decodes successfully with no cross-validation between multiple sources' content.

### Recommendation
In `extend_with_attachments`, after `response.decode_atlas_get_attachment()` succeeds, compute the content hash of `response.attachment` (e.g. `Attachment::hash()`) and compare it against `request.content_hash` before calling `self.attachments.insert(...)`; on mismatch, treat it as a failed/faulty response (`report.bump_failed_requests()` and mark the peer as unreliable/faulty) instead of silently accepting it. Additionally, consider requiring inventory claims to be corroborated by at least one additional independent peer, or by opportunistic hash verification once bytes are fetched, before trusting a single peer's inventory bit as sufficient grounds for exclusive sourcing.

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/tests.rs` or a new test module):
1. Construct an `AttachmentsBatchStateContext` with one `AttachmentInstance`/`content_hash` in `attachments_instances`, and a single mocked peer in `self.peers`/`self.inventories` whose `GetAttachmentsInvResponse.pages[0].inventory[position] = 1` for that `content_hash`, despite not having matching content.
2. Call `get_prioritized_attachments_requests()` and assert the resulting `AttachmentRequest.sources` contains exactly that one peer (proving the request was issued based solely on the unverified claim) — assert on `queue.pop().unwrap().sources.contains_key(&mocked_peer_url)`.
3. Simulate `BatchedRequestsResult::succeeded` containing that peer mapped to an HTTP response whose `decode_atlas_get_attachment()` yields an `Attachment` with content that does **not** hash to `content_hash`.
4. Call `extend_with_attachments(&mut results)` and assert `context.attachments` now contains the mismatched `Attachment` — i.e. `assert_ne!(stored_attachment.hash(), content_hash)` while `context.attachments.contains(&stored_attachment)` is true, proving the mismatch survives unrejected through this function.
