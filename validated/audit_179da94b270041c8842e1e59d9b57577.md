### Title
Stake-weighted QoS is locked in at connection establishment and never re-evaluated, allowing evasion of stake-based throughput limits after stake changes - (File: streamer/src/nonblocking/swqos.rs)

### Summary
This is a plausible analog to the reported "rate change" bug class. In the external report, a global exchange rate (`vETHPerRestakedLST`) is updated, but the contract fails to account for the fact that user deposits should be rewarded based on the rate at deposit time and duration held. An attacker games the mismatch between the moment a rate/permission snapshot is taken and the moment it's actually consumed. In `agave`'s QUIC streamer, an analogous "snapshot vs. reality" mismatch exists: the stake used to compute a peer's QUIC throughput allowance (streams-in-flight, per-peer connection caps, eviction priority) is captured **once**, at `build_connection_context()`, from the live `StakedNodes` table, and is **never refreshed** for the lifetime of that QUIC connection.

### Finding Description
`SwQos::build_connection_context()` reads the peer's current stake via `get_connection_stake()` and freezes it into `SwQosConnectionContext { peer_type, total_stake, .. }`: [1](#0-0) 

This frozen `peer_type`/`total_stake` is what drives every subsequent QoS decision for the entire life of the connection:
- The number of concurrent uni-directional streams allowed (`compute_max_allowed_uni_streams_with_rtt`), set once in `cache_new_connection()`: [2](#0-1) 
- The per-throttling-interval stream budget via `max_streams_per_throttling_interval()`, which reuses the same cached `conn_context.total_stake`: [3](#0-2) 
- Eviction resistance: `prune_random()` uses `ConnectionEntry::stake()`, which is the `peer_type` stored at connection-add time, to decide which connections survive when the staked table is full: [4](#0-3) [5](#0-4) 

Meanwhile, the actual stake map (`StakedNodes`) *is* periodically refreshed in the background by `staked_nodes_updater_service.rs`, but nothing in the QUIC connection-handling path (`handle_connection` in `streamer/src/nonblocking/quic.rs`) re-queries that live table or re-derives `peer_type`/`total_stake` for already-established connections. The comment at `streamer/src/nonblocking/quic.rs:606-609` even acknowledges this pattern for RTT ("if it gets stale during connection lifetime it is not the end of the world") but the same staleness applies to stake, which has a materially larger security impact since it directly governs the QoS/DoS-resistance budget, not just a stat.

This mirrors the report's root cause exactly: a mutable, security-relevant parameter (`vETHPerRestakedLST` rate / here, live stake) is captured at one point in time and used to grant a benefit (redemption amount / here, elevated QUIC throughput and eviction priority) without re-validating it against the parameter's current value.

### Impact Explanation
An entity that holds delegated stake at connection-establishment time (or that arranges for a large stake delegation for a single epoch/moment) can open a long-lived QUIC connection to the TPU while its stake is high, receive the correspondingly large `max_concurrent_uni_streams` allowance and high resistance to `prune_random` eviction, and then have that stake reduced or withdrawn — all while the connection continues to enjoy the original, no-longer-justified QoS treatment. Because QUIC connections in this streamer are not periodically re-validated against the live stake table, this is a QoS evasion vector: it lets a peer retain disproportionate bandwidth/stream budget and priority over honestly-current unstaked or low-stake connections, undermining the fairness/DoS-resistance goal that the stake-weighted QoS mechanism (`SwQos`) exists to enforce.

### Likelihood Explanation
This does not require any special validator/operator privilege — any pubkey capable of temporarily holding/delegating stake (which is a permissionless on-chain action) can trigger the favorable snapshot, then reduce its stake while keeping the QUIC connection alive using standard client-side keep-alives. The staked_nodes table is refreshed periodically in the background (`staked_nodes_updater_service.rs`), but no corresponding re-check exists on the per-connection hot path, so the staleness window is bounded only by how long the QUIC connection is kept open by the client (which is under attacker control, subject to server-side idle timeouts).

### Recommendation
Periodically re-evaluate `peer_type`/`total_stake` for open connections (e.g., on each stake-table refresh or at a fixed cadence) and recompute `max_concurrent_uni_streams` / eviction stake accordingly, rather than freezing these values for the entire connection lifetime in `SwQosConnectionContext`/`ConnectionEntry`.

### Proof of Concept
Not independently executable from static analysis alone; based on code inspection:
1. Attacker delegates a large stake, then opens a QUIC connection to the TPU; `build_connection_context()` captures the current high stake into `SwQosConnectionContext`, and `cache_new_connection()` sets `max_concurrent_uni_streams` accordingly.
2. Attacker keeps the QUIC connection alive (client-side keep-alive) and reduces/withdraws the stake in a subsequent epoch.
3. `staked_nodes_updater_service` updates the live `StakedNodes` table, but the already-open connection's `SwQosConnectionContext`/`ConnectionEntry` is never re-derived from it — confirmed by the absence of any refresh call in `streamer/src/nonblocking/{swqos,quic}.rs` (verified via `grep_search` for `refresh_stake`/`update_stake`/`recompute`, which found no matches in `streamer/src`).
4. The attacker's connection continues to receive the original high-stake stream allowance and eviction priority, evading the QoS system's intended stake-proportional throttling.

Note: I was not able to find any background task that re-derives per-connection QoS parameters after connection establishment; this absence is based on the index available and should be double-checked against the full `streamer` crate (including any `quic.rs` idle-timeout / periodic-refresh logic not captured by my searches) in a full Devin session if further confirmation is needed.

impl QosController<SwQosConnectionContext> for SwQos {
    fn build_connection_context(&self, connection: &Connection) -> SwQosConnectionContext {
        let remote_address = connection.remote_address();
        get_connection_stake(connection, &self.staked_nodes).map_or(
            SwQosConnectionContext {
                peer_type: ConnectionPeerType::Unstaked,
                total_stake: 0,
                remote_pubkey: None,
                in_staked_table: false,
                remote_address,
                stream_counter: None,
                last_update: Arc::new(AtomicU64::new(timing::timestamp())),
            },
            |(pubkey, stake, total_stake)| {
                // The heuristic is that the stake should be large enough to have 1 stream pass through within one throttle
                // interval during which we allow max (MAX_STREAMS_PER_MS * STREAM_THROTTLING_INTERVAL_MS) streams.

                let peer_type = {
                    let max_streams_per_ms = self.staked_stream_load_ema.max_streams_per_ms();
                    let min_stake_ratio =
                        1_f64 / (max_streams_per_ms * STREAM_THROTTLING_INTERVAL_MS) as f64;
                    let stake_ratio = stake as f64 / total_stake as f64;
                    if stake_ratio < min_stake_ratio {
                        // If it is a staked connection with ultra low stake ratio, treat it as unstaked.
                        ConnectionPeerType::Unstaked
                    } else {
                        ConnectionPeerType::Staked(stake)
                    }
                };

                SwQosConnectionContext {
                    peer_type,
                    total_stake,
                    remote_pubkey: Some(pubkey),
                    in_staked_table: false,
                    remote_address,
                    last_update: Arc::new(AtomicU64::new(timing::timestamp())),
                    stream_counter: None,
                }
            },
        )

    // Randomly selects sample_size many connections, evicts the one with the
    // lowest stake, and returns the number of pruned connections.
    // If the stakes of all the sampled connections are higher than the
    // threshold_stake, rejects the pruning attempt, and returns 0.
    pub(crate) fn prune_random(&mut self, sample_size: usize, threshold_stake: u64) -> usize {
        let num_pruned = std::iter::once(self.table.len())
            .filter(|&size| size > 0)
            .flat_map(|size| {
                let mut rng = rng();
                repeat_with(move || rng.random_range(0..size))
            })
            .map(|index| {
                let connection = self.table[index].first();
                let stake = connection.map(|connection: &ConnectionEntry<S>| connection.stake());
                (index, stake)
            })
            .take(sample_size)
            .min_by_key(|&(_, stake)| stake)
            .filter(|&(_, stake)| stake < Some(threshold_stake))
            .and_then(|(index, _)| self.table.swap_remove_index(index))
            .map(|(_, connections)| connections.len())
            .unwrap_or_default();
        self.total_size = self.total_size.saturating_sub(num_pruned);
        num_pruned
    }
