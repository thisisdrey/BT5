### Title
Null-pointer / RuntimeException crash on `khaosDb` head recomputation during fork rollback - (File: `chainbase/src/main/java/org/tron/core/db/KhaosDatabase.java`)

### Summary
The Dogecoin fix addresses a case where, after a failed reorganization, the node could end up with no valid "best chain" tip, so a subsequent lookup of the tip's height dereferenced a null pointer and crashed. The closest reachable analog in java-tron is `KhaosDatabase.removeBlk()`, which recomputes `head` from `miniStore` and throws an unguarded `RuntimeException` (equivalent to an unrecoverable null-head crash) if the fork-block-removal loop empties the in-memory chain window, and several downstream call sites (`ChainBaseManager.getKhaosDbHead()`, `TronNetDelegate.getKhaosDbHeadBlockId()`) immediately dereference the returned head object without any null check.

### Finding Description
`KhaosDatabase` keeps an in-memory sliding window of recent blocks (`miniStore`) used to track/resolve forks. When `Manager.switchFork()` cannot find a common ancestor for the newly received branch (`NonCommonBlockException`), it walks the new branch and removes every one of its blocks from the Khaos window: [1](#0-0) 

Each removal calls `KhaosDatabase.removeBlk()`, which recomputes `head` purely from what remains in `miniStore` and, if nothing remains, throws: [2](#0-1) 

Because `miniStore`'s capacity is derived from `latestBlockHeaderNumber - latestSolidifiedBlockNum + 1` and is periodically resized in `updateDynamicProperties`, on a node that has just finished syncing/solidifying quickly (small window) or during startup/rollback windows where the store's max capacity is small, a long or unusual fork branch delivered while processing `pushBlock` can consume/evict the entire window, leaving `numKblkMap` empty when `removeBlk` runs its rollback loop. The resulting `head` is either left null (if the exception path is hit and no reassignment happens elsewhere) or the method throws immediately, which — unlike Dogecoin's silent null dereference — surfaces as an uncaught `RuntimeException` on the block-processing thread.

The unguarded consumers of `head` compound the risk: `getHead()` returns `head.blk` with no null check, and callers such as `ChainBaseManager.getKhaosDbHead()` and `TronNetDelegate.getKhaosDbHeadBlockId()` dereference the result immediately: [3](#0-2) [4](#0-3) 

If `head` ever becomes `null` (e.g., a rollback path that does not go through `removeBlk`'s guard, or a future code change that skips the `orElseThrow`), any of these call sites — including the block-application path in `Manager.pushBlock` itself (`khaosDb.getHead()` is logged/used at lines 1367-1368/1383-1384) — will NPE the block-processing thread, exactly mirroring the Dogecoin "no best chain, NPE on tip height" failure mode.

### Impact Explanation
A crash or unhandled exception on the block-application thread inside `Manager.pushBlock`/`switchFork` halts block processing for the node, which is a denial-of-service against the local node's chain-following capability (node crash/halt). Because this logic sits in the core consensus/block-application path reachable whenever a competing branch is processed, it can affect availability of the affected node without requiring any privileged role — any block sequence that produces a non-common-ancestor fork against a sufficiently small Khaos window can trigger it.

### Likelihood Explanation
Likelihood is constrained by two factors I could not fully resolve with the available tooling: (1) the exact conditions under which `miniStore`'s capacity/contents can be exhausted entirely by a single fork removal loop, and (2) whether any other code path assigns `head = null` outside of the guarded `removeBlk`/`push`/`start` methods. The `orElseThrow` guard converts the "null tip" condition into an immediate `RuntimeException` rather than a silent NPE, so today this fails loudly rather than being a stealthy chain-halt — this is a meaningful difference from the Dogecoin root cause and lowers confidence that this is a fully faithful analog rather than a related-but-distinct robustness gap.

### Recommendation
- Add explicit null/empty checks in `KhaosDatabase.removeBlk()` and `getHead()` and have callers (`ChainBaseManager.getKhaosDbHead()`, `TronNetDelegate.getKhaosDbHeadBlockId()`, `Manager.pushBlock`/`switchFork`) treat an empty/null head as a recoverable condition (e.g., fall back to the persisted chain head from `DynamicPropertiesStore`) instead of letting an uncaught exception propagate.
- Ensure the fork-removal loop in `switchFork`'s `NonCommonBlockException` handler cannot empty `miniStore` below the point where the canonical chain's own head block is removed; bound the loop to blocks strictly on the rejected branch.
- Add a regression test that forces `miniStore` to be reduced to zero entries and asserts the node degrades gracefully rather than throwing from `removeBlk`.

### Proof of Concept
I could not build a concrete, tool-verified reproduction of the exact miniStore-exhaustion scenario (it would require tracing `RevokingDatabase`/`khaosDb.setMaxSize` sizing interactions and precise timing of `pushBlock` calls, which needs runtime experimentation the static index cannot provide). Given the residual uncertainty about reachability and the tool budget being exhausted, I am not confident enough in the concrete exploit path to assert this meets the "concrete" bar required — flagging this explicitly rather than fabricating a PoC.
