### Title
Unbounded in-memory buffering of `git-fetch --porcelain` output enables attacker-controlled remote to exhaust Gitaly memory - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
`fetchRemoteAtomic` buffers the entire stdout of `git-fetch --porcelain` into an unbounded `bytes.Buffer` before any parsing occurs, and the refspec used (`refs/*:refs/*` by default) matches every ref advertised by the remote. An attacker who owns a repository can point `FetchRemote`'s `RemoteParams.Url` at a Git server they control and have it advertise millions of refs pointing at the same existing object, causing Gitaly to buffer gigabytes of porcelain status lines in memory with no size cap.

### Finding Description
In `fetchRemoteAtomic`, `stdout` and `stderr` are plain `bytes.Buffer` values passed directly as `opts.Stdout`/`opts.Stderr`: [1](#0-0) 

These are forwarded into `Repo.FetchRemote`, which passes them straight through as `gitcmd.WithStdout`/`gitcmd.WithStderr`: [2](#0-1) 

Because `cfg.stdout`/`cfg.stderr` are non-nil here, the command layer's built-in protection is bypassed. `internal/command/command.go` only applies the bounded `stderrBuffer` (capped at `maxStderrBytes` = 10KB) when the caller does **not** supply an explicit writer; when an explicit writer is supplied (as `fetch_remote.go` does for both stdout and stderr), the raw writer is used unmodified with no size limit: [3](#0-2) 

The refspec applied to the fetch defaults to `refs/*:refs/*` when the caller (GitLab Rails, for a mirror pull) doesn't set `MirrorRefmaps`: [4](#0-3) 

The full command runs to completion (`cmd.Wait()`) before any scanning begins — the `gitcmd.NewFetchPorcelainScanner(&stdout, objectHash)` only starts reading after `quarantineRepo.FetchRemote` returns: [5](#0-4) [6](#0-5) 

An attacker who controls the mirror URL (via a mirror-pull import, which an unprivileged project owner can configure) can run a malicious Git server that advertises millions of refs all pointing at one small, already-known object (avoiding the need to transfer a huge pack). With `--porcelain --verbose`, `git-fetch` writes one status line per updated ref (~90-100 bytes including two full OIDs and a ref name) to stdout. For 10 million refs this is roughly 1GB of buffered memory in a single RPC invocation, with no cap, no streaming/backpressure, and no request-side limit on ref count enforced by Gitaly itself.

### Impact Explanation
This is a memory-exhaustion / crash vector against `gitaly-server`: a single `FetchRemote` call from a malicious mirror target can force Gitaly to allocate gigabytes of heap for one RPC, potentially causing OOM-kill of the process (or cgroup) and disrupting all repositories served by that Gitaly node/cgroup — a resource-exhaustion DoS matching GitLab's "Denial of Service" bounty impact class for shared infrastructure components.

### Likelihood Explanation
Preconditions are minimal and match ordinary product functionality: any GitLab user who can create/own a project and configure a pull mirror (or otherwise trigger `FetchRemote` with an attacker-controlled URL) can point it at a server they run. No admin privileges, secrets, or Gitaly-internal access are required, and the attack is fully repeatable (repeated fetch/mirror-sync attempts). The only operational cost to the attacker is running a Git server capable of advertising a large ref set, which is inexpensive to construct (many refs → one object).

### Recommendation
Bound the porcelain stdout/stderr capture in `fetchRemoteAtomic`, e.g. by wrapping the buffers with a size-limited writer (similar in spirit to `internal/command.stderrBuffer` / `maxStderrBytes`) that truncates or errors out once a maximum size is exceeded, or by streaming/parsing the porcelain output incrementally via a pipe (`gitcmd.WithSetupStdout()` + `bufio.Scanner` on the live pipe) instead of buffering the entire output before scanning. Additionally, consider enforcing a configurable maximum number of refs/refspec matches for `FetchRemote` mirror imports.
