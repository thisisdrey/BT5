### Title
Missing `withdrawReward` accounting hook before freezing/delegating TRX balance leads to stale vote-cycle checkpoints and reward miscalculation - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`, `FreezeBalanceV2Actuator.java`, `DelegateResourceActuator.java`, `UnDelegateResourceActuator.java`)

### Summary
This is analogous to the Sherlock finding where `LEther.sol`'s `depositEth()`/`redeemEth()` and `LToken.sol`'s `collectFrom()` skip the `beforeDeposit`/`beforeWithdraw` accounting hooks (`updateState()`) that other value-moving paths call, causing stale interest/accounting state. In java-tron, the analogous "accounting-state checkpoint" hook is `mortgageService.withdrawReward(ownerAddress)` (and its TVM-side counterpart `VoteRewardUtil.withdrawReward`), which must be called before an account's stake/frozen-balance state is mutated so that `beginCycle`/`endCycle`/`accountVote` snapshots used for reward computation stay consistent.

### Finding Description
Several actuators that mutate an account's frozen/delegated TRX balance consistently call `mortgageService.withdrawReward(ownerAddress)` as the very first step before mutating balances, exactly mirroring the "hook-before-value-move" pattern the report calls out:

- `UnfreezeBalanceActuator.execute()`: `mortgageService.withdrawReward(ownerAddress);` [1](#0-0) 
- `UnfreezeBalanceV2Actuator.execute()`: same pattern [2](#0-1) 
- `VoteWitnessActuator.countVoteAccount()`: same pattern [3](#0-2) 
- `WithdrawBalanceActuator.execute()`: same pattern [4](#0-3) 

However, `FreezeBalanceActuator.execute()`, `FreezeBalanceV2Actuator.execute()`, `DelegateResourceActuator.execute()`, and `UnDelegateResourceActuator.execute()` mutate the account's frozen/delegated balance and the global `TotalTronPowerWeight`/`TotalNetWeight`/`TotalEnergyWeight` (which directly feed reward-share computation in `MortgageService.payReward`/`computeReward`) **without ever calling `withdrawReward`** first:

- `FreezeBalanceActuator.execute()` directly reads `accountCapsule`, mutates frozen balances and calls `addTotalWeight(...)` without any `mortgageService.withdrawReward` call. [5](#0-4) 
- `FreezeBalanceV2Actuator.execute()` similarly mutates frozen-v2 balances and total weights with no reward-checkpoint call. [6](#0-5) 
- `DelegateResourceActuator.execute()` mutates both owner's and receiver's frozen/delegated balances with no checkpoint call at all. [7](#0-6) 
- `UnDelegateResourceActuator.execute()` likewise mutates owner and receiver balances/usages without calling `withdrawReward`. [8](#0-7) 

The reward accounting model in `MortgageService.withdrawReward()` and `VoteRewardUtil.withdrawReward()` relies on checkpointed `beginCycle`/`endCycle` and a snapshot of the account's vote/frozen state (`delegationStore.setAccountVote`) taken exactly at the time reward is settled: [9](#0-8) . Because `FreezeBalance*`/`Delegate*`/`UnDelegate*` change the underlying frozen/delegated balance and total weight state without first settling/checkpointing the account's outstanding reward at the pre-mutation state, any reward computed later (in the next cycle checkpoint by `VoteWitnessActuator` or `UnfreezeBalance*`) is computed over a period during which the account's weight changed mid-cycle without a boundary being recorded, which is the same "stale interest/accounting state" class of defect described in the source report (`updateState()`/hook must run before the balance-changing operation to avoid using out-of-date state).

### Impact Explanation
Because these code paths are reachable by any account via a simple, unprivileged, signed `FreezeBalanceContract`, `FreezeBalanceV2Contract`, `DelegateResourceContract`, or `UnDelegateResourceContract` transaction, an attacker (or even an ordinary user unintentionally) can freeze/unfreeze or delegate/undelegate TRX repeatedly within a single voting cycle to manipulate the total weight and their own vote power without ever triggering a reward checkpoint. This can result in reward amounts computed by `computeReward` being calculated against an incorrect (stale or manipulated) weight/vote state for part of a cycle, causing either the depositor/voter or other voters sharing the same super-representative reward pool to receive an inaccurate (too high or too low) reward allocation — i.e., miscalculated shares of the reward pool, mirroring the "permanently losing value due to inaccurate calculations" impact in the source finding.

### Likelihood Explanation
The likelihood is bounded by the fact that reward computation in `withdrawReward` is anchored to `votesList` snapshots, not directly to `FreezeBalance`/`Delegate` weight changes — so the practical exploitability (whether this produces a provably exploitable value-extraction path versus a benign accounting quirk) could not be fully confirmed from the code alone. Full confirmation would require tracing `computeReward`'s exact use of `getTronPower()`/`totalTronPowerWeight` across a maintenance-cycle boundary in `MortgageService`/`DelegationStore`, which was not completely available in the indexed context.

### Recommendation
Add `mortgageService.withdrawReward(ownerAddress)` (and, for the receiver in `DelegateResourceActuator`/`UnDelegateResourceActuator`, `withdrawReward(receiverAddress)`) as the first operation in `FreezeBalanceActuator.execute()`, `FreezeBalanceV2Actuator.execute()`, `DelegateResourceActuator.execute()`, and `UnDelegateResourceActuator.execute()`, consistent with `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `VoteWitnessActuator`, and `WithdrawBalanceActuator`, so that reward/cycle checkpoints are always settled before the account's weight-affecting balance state is mutated.

### Proof of Concept
Not independently reproducible from static code inspection alone — a full PoC would require running a test similar to `framework/src/test/java/org/tron/common/runtime/vm/VoteTest.java`'s `testRewardAlgorithmNo2`, but interleaving `FreezeBalanceV2Actuator`/`DelegateResourceActuator` calls mid-cycle and asserting the resulting reward differs from the expected linear allocation. This was not executed as part of this analysis; confidence in the concrete financial impact is therefore moderate rather than fully proven.

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }
