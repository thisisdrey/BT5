## Title
RETURNDATA corruption via aliased memory in CALL-family opcodes (`ret = common.CopyBytes(ret)` fix missing) - (File: `core/vm/instructions.go`)

## Summary
The CVE-2021-39137 fix required copying the `ret` byte-slice returned from a call/precompile **before** it is written into memory via `Memory.Set`, because `Memory.Set` mutates the same backing array that `ret` (and hence `evm.returnData`) still points to when the caller did not defensively copy call input/output. In this repository's `core/vm/instructions.go`, the four CALL-family opcode handlers (`opCall`, `opCallCode`, `opDelegateCall`, `opStaticCall`) write `ret` into memory and then assign `evm.returnData = ret` **without** the `common.CopyBytes(ret)` step that the official patch introduced, reproducing the exact aliasing pattern described in the post-mortem.

## Finding Description
Each of the CALL-family opcodes fetches call input directly from EVM memory without copying it: [1](#0-0) 
`args := scope.Memory.GetPtr(inOffset.Uint64(), inSize.Uint64())` returns a slice that aliases the interpreter's memory backing array rather than a defensive copy: [2](#0-1) 

When the target of the call is a precompile such as the identity/`dataCopy` precompile, the precompile can return the same (unc-copied) slice it received as `ret`. After the call returns, the opcode handler writes `ret` back into memory at `retOffset`: [3](#0-2) 
and only afterwards assigns: [4](#0-3) 

`Memory.Set` performs an in-place `copy()` directly into the shared backing store: [5](#0-4) 

Because `args` (input to the precompile), `ret` (its output), and `m.store` (the interpreter's memory) are all views over the *same underlying array* — the same pattern as the original bug — if the caller chooses `inOffset`/`retOffset` such that the source and destination ranges overlap but are shifted, the `copy()` call in `Memory.Set` overwrites the very bytes that `ret` (and therefore `evm.returnData`) still references. This is precisely the corruption pattern documented in the post-mortem: [6](#0-5) 

The upstream fix inserted `ret = common.CopyBytes(ret)` immediately before each `scope.Memory.Set(...)` call in `opCall`, `opCallCode`, `opDelegateCall`, and `opStaticCall`: [7](#0-6) 

This exact `common.CopyBytes(ret)` line is **absent** from the current implementations of all four opcodes in this repository: [8](#0-7) [9](#0-8) [10](#0-9) [11](#0-10) 

Also, `opReturnDataCopy` reads directly from `evm.returnData` and copies it into memory via the same `Memory.Set` in-place `copy()`: [12](#0-11) 
If `evm.returnData` is corrupted for the reasons above, any subsequent `RETURNDATACOPY` (or `RETURNDATASIZE`) in the same or a parent frame observes the wrong data, and any state derived from it (storage writes, hashed values, control flow) diverges from what a spec-compliant EVM would compute — breaking the state-root equality between implementations, exactly as happened in the original CVE-2021-39137 mainnet split at block 13107518.

## Impact Explanation
This breaks the equality "the `stateRoot` a Geth node commits for a block matches what other spec-compliant clients compute for the same block." A single maliciously crafted transaction that calls `dataCopy`/identity precompile with an overlapping-but-shifted input/output memory range, followed by reading `RETURNDATACOPY`, can cause execution to branch on corrupted returndata and thus commit a divergent state root — a Critical/High consensus-split bug identical in class to the original CVE, since every Geth node running this code builds/validates blocks with the corrupted (non-canonical) result.

## Likelihood Explanation
The trigger conditions are unprivileged and fully attacker-controlled from within a single transaction: choose `inOffset`/`inSize` for the call to the `dataCopy` precompile and `retOffset`/`retSize` for the memory write such that the ranges overlap but are shifted (exactly the pattern in the original PoC and the state test embedded in the post-mortem). No special node configuration, peer cooperation, or privileged role is required — any account with enough gas can construct and send the transaction.

## Recommendation
Apply the same fix as the historical patch: insert `ret = common.CopyBytes(ret)` immediately before `scope.Memory.Set(retOffset.Uint64(), retSize.Uint64(), ret)` in `opCall`, `opCallCode`, `opDelegateCall`, and `opStaticCall` in `core/vm/instructions.go`, so that `evm.returnData` is decoupled from the interpreter's `Memory` backing array before the in-place `copy()` in `Memory.Set` can mutate it.

## Proof of Concept
Reuse the state test embedded in the repository's own post-mortem document, which reproduces the bug via the `dataCopy` precompile called with overlapping-but-shifted memory ranges and then reads via `RETURNDATACOPY`/`SHA3`, producing a `stateRoot` that diverges from the spec-correct result: [13](#0-12)

func opReturnDataCopy(pc *uint64, evm *EVM, scope *ScopeContext) ([]byte, error) {
	memOffset, dataOffset, length := scope.Stack.pop3()

	offset64, overflow := dataOffset.Uint64WithOverflow()
	if overflow {
		return nil, ErrReturnDataOutOfBounds
	}
	// we can reuse dataOffset now (aliasing it for clarity)
	var end = dataOffset
	end.Add(dataOffset, length)
	end64, overflow := end.Uint64WithOverflow()
	if overflow || uint64(len(evm.returnData)) < end64 {
		return nil, ErrReturnDataOutOfBounds
	}
	scope.Memory.Set(memOffset.Uint64(), length.Uint64(), evm.returnData[offset64:end64])
	return nil, nil
}

func opCall(pc *uint64, evm *EVM, scope *ScopeContext) ([]byte, error) {
	stack := scope.Stack
	// Pop gas. The actual gas in evm.callGasTemp.
	// We can use this as a temporary value
	temp := stack.pop()
	gas := evm.callGasTemp
	// Pop other call parameters.
	addr, value, inOffset, inSize, retOffset, retSize := stack.pop(), stack.pop(), stack.pop(), stack.pop(), stack.pop(), stack.pop()
	toAddr := common.Address(addr.Bytes20())
	// Get the arguments from the memory.
	args := scope.Memory.GetPtr(inOffset.Uint64(), inSize.Uint64())

	if evm.readOnly && !value.IsZero() {
		return nil, ErrWriteProtection
	}
	if !value.IsZero() {
		gas += params.CallStipend
	}

	// Execution gas for the forward was already pre-deducted by the dynamic
	// gas table (see makeCallVariantGasCallEIP*); only the state reservoir
	// needs to be handed off to the child here.
	childBudget := NewGasBudget(gas, scope.Contract.Gas.StateGas)
	ret, result, err := evm.Call(scope.Contract.Address(), toAddr, args, childBudget, &value)

	if err != nil {
		temp.Clear()
	} else {
		temp.SetOne()
	}
	stack.push(&temp)

	if err == nil || err == ErrExecutionReverted {
		scope.Memory.Set(retOffset.Uint64(), retSize.Uint64(), ret)
	}
	scope.Contract.refundGas(result, evm.Config.Tracer, tracing.GasChangeCallLeftOverRefunded)

	// If the call frame reverts or halts exceptionally, the charged state-gas
	// is refilled back to the state reservoir in Amsterdam.
	if evm.chainRules.IsAmsterdam && err != nil && !value.IsZero() && evm.StateDB.Empty(toAddr) {
		scope.Contract.refundState(params.AccountCreationSize*evm.Context.CostPerStateByte, evm.Config.Tracer, tracing.GasChangeRefundAccountCreation)
	}
	evm.returnData = ret
	return ret, nil
}

// Set sets offset + size to value
func (m *Memory) Set(offset, size uint64, value []byte) {
	// It's possible the offset is greater than 0 and size equals 0. This is because
	// the calcMemSize (common.go) could potentially return 0 when size is zero (NO-OP)
	if size > 0 {
		// length of store may never be less than offset + size.
		// The store should be resized PRIOR to setting the memory
		if offset+size > uint64(len(m.store)) {
			panic("invalid memory: store empty")
		}
		copy(m.store[offset:offset+size], value)
	}
}

// GetPtr returns the offset + size
func (m *Memory) GetPtr(offset, size uint64) []byte {
	if size == 0 {
		return nil
	}

	// memory is always resized before being accessed, no need to check bounds
	return m.store[offset : offset+size]
}
