## Title
Null `tokenId`/`tokenValue` in JSON-RPC `buildTransaction` request causes `NullPointerException` via unboxing in `BuildArguments.availableTransferAsset()` - (File: framework/src/main/java/org/tron/core/services/jsonrpc/types/BuildArguments.java)

### Summary
`BuildArguments` is the DTO that the JSON-RPC HTTP endpoint (`eth_call`/`buildTransaction`, etc.) deserializes an anonymous client's request body into via Jackson/Lombok setters. Fields such as `tokenId` and `tokenValue` are declared as boxed `Long` with default values (`0L`), but Jackson deserialization can override those defaults with an explicit JSON `null`, exactly as in the referenced Go/`gofiber` report where a `gencodec:"required"`-style expectation did not survive JSON deserialization.

### Finding Description
`tokenId` and `tokenValue` are declared as nullable `Long` wrapper fields with default initializers: [1](#0-0) 

When an unprivileged JSON-RPC client sends `{"tokenId": null, "tokenValue": null, ...}`, Jackson invokes the Lombok-generated `setTokenId(null)` / `setTokenValue(null)`, replacing the default `0L` with an actual Java `null` — the same class of bug flagged in the external report: struct/field defaults or "required" annotations do not prevent JSON deserialization from producing `null`.

That null value is later used in `availableTransferAsset()`, which is called unconditionally from `getContractType(Wallet)` while routing the request to the correct contract type: [2](#0-1) [3](#0-2) 

The expression `tokenId > 0 && tokenValue > 0` requires unboxing the `Long` to a primitive `long` for the `>` comparison. If either field is `null`, this throws an uncaught `NullPointerException`, analogous to the Go report's `big.Int.Cmp(nil)` panic caused by a nil `Fee` bypassing the `gencodec:"required"` expectation during JSON parsing.

### Impact Explanation
This is reachable from the JSON-RPC HTTP API (`TronJsonRpcImpl`, used by `buildTransaction`/`eth_call`-style methods) by any anonymous API client sending a crafted request — no authentication or signed transaction required. I was not able to fully trace, within the remaining tool budget, whether the JSON-RPC dispatch layer (`TronJsonRpcImpl`) wraps this call path in a catch-all `try/catch` that would only fail the individual request versus one that propagates the `NullPointerException` up through the JSON-RPC framework and potentially destabilizes the underlying servlet/HTTP thread handling. This is the key uncertainty: if the exception is caught per-request (which appears to be the dominant pattern in the sibling HTTP servlets I inspected, e.g. `TriggerSmartContractServlet`, `DeployContractServlet`), the practical impact is degraded to a single failed request rather than a server crash. If it is not caught at that layer (unverified), it could deny service for that JSON-RPC method to legitimate users.

### Likelihood Explanation
Trivial to trigger: any anonymous client can send a single JSON-RPC POST request with `"tokenId": null` or `"tokenValue": null` and reach `availableTransferAsset()` through the normal `getContractType` code path used to classify `to`-less/`to`-set transactions.

### Recommendation
In `BuildArguments`, treat `tokenId`/`tokenValue` (and any other boxed numeric fields relied upon for unboxed comparisons) as untrusted after deserialization: null-check before unboxing, e.g. `tokenId != null && tokenId > 0 && tokenValue != null && tokenValue > 0`, or normalize nulls back to `0L` in the setters/constructor rather than relying on field initializers, which Jackson can bypass.

### Proof of Concept
```
POST /jsonrpc
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "method": "buildTransaction",
  "params": [{
    "from": "0xabd4b9367799eaa3197fecb144eb71de1e049abc",
    "to": "0x548794500882809695a8a687866e76d4271a1abc",
    "tokenId": null,
    "tokenValue": null,
    "value": "0x1f4"
  }],
  "id": 1
}
```
This causes Jackson to set `tokenId`/`tokenValue` to `null` on the `BuildArguments` instance; the subsequent call to `getContractType()` → `availableTransferAsset()` unboxes the null `Long`, throwing `NullPointerException`.

**Note on verification limits:** I could not fully confirm, within the available tool iterations, whether an outer exception handler in `TronJsonRpcImpl` catches this `NullPointerException` gracefully (limiting impact to a per-request error response) or whether it propagates further. A Devin session with full codebase access should trace `TronJsonRpcImpl`'s `buildTransaction`/`eth_call` implementations and the JSON-RPC dispatcher's exception handling to confirm actual blast radius before treating this as a confirmed denial-of-service.

  public ContractType getContractType(Wallet wallet) throws JsonRpcInvalidRequestException,
      JsonRpcInvalidParamsException {
    // Fail fast on bad hex / conflict before the state lookup;
    // calldataEquals relies on resolveData() having validated hex first.
    String resolvedData = resolveData();
    validateCallDataConflict();

    ContractType contractType;

    // to is null
    if (paramStringIsNull(to)) {
      // data is null
      if (paramStringIsNull(resolvedData)) {
        throw new JsonRpcInvalidRequestException("invalid json request");
      }

      contractType = ContractType.CreateSmartContract;
    } else {
      // to is not null
      byte[] contractAddressData = addressCompatibleToByteArray(to);
      BytesMessage.Builder build = BytesMessage.newBuilder();
      BytesMessage bytesMessage = build.setValue(ByteString.copyFrom(contractAddressData)).build();
      SmartContract smartContract = wallet.getContract(bytesMessage);

      // check if to is smart contract
      if (smartContract != null) {
        contractType = ContractType.TriggerSmartContract;
      } else {
        // tokenId and tokenValue: trc10, value: TRX
        if (availableTransferAsset()) {
          contractType = ContractType.TransferAssetContract;
        } else {
          if (StringUtils.isNotEmpty(value)) {
            contractType = ContractType.TransferContract;
          } else {
            throw new JsonRpcInvalidRequestException("invalid json request");
          }
        }
      }
    }

    return contractType;
  }
