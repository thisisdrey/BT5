### Title
Stale postponed receipts and pending data-dependency links survive `DeleteAccount` and execute against the re-created account - (`core/store/src/utils/mod.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`remove_account` (called by `action_delete_account`) deletes the `Account`, contract code, access keys, and contract data, but never purges `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceipt`, or `TrieKey::ReceivedData` rows for that account. Because these keys are namespaced only by `(receiver_id, data_id/receipt_id)` — with no per-account "incarnation" counter — a postponed action receipt created before deletion remains latent in the trie and can be triggered by a later-arriving `Data` receipt after the same account name has been re-created, causing the stale receipt's actions to execute against the new account's state.

### Finding Description
`process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) stores, for every unmet `input_data_id`, a `TrieKey::PostponedReceiptId{receiver_id, data_id}` link plus `TrieKey::PendingDataCount{receiver_id, receipt_id}` and the serialized receipt under `TrieKey::PostponedReceipt{receiver_id, receipt_id}` [1](#0-0) .

The `Data` arm of `process_receipt` (`runtime/runtime/src/lib.rs:1386-1473`) blindly trusts whatever is stored under those keys: it looks up `PostponedReceiptId{receiver_id, data_id}`, decrements `PendingDataCount`, and once it reaches zero fetches and executes the postponed receipt via `apply_action_receipt` [2](#0-1) . There is no check that the account which owns `receiver_id` today is the same "incarnation" that originally created the postponed receipt.

`remove_account` (`core/store/src/utils/mod.rs:505-575`), invoked from `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`), removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData`, but has no logic at all for `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, or `ReceivedData` [3](#0-2) . These rows are simply left in the trie.

Because the data_id itself is generated deterministically and returned to the calling contract (e.g. `create_promise_yield_receipt`/`create_promise_yield_receipt_with_id` in `runtime/runtime/src/ext.rs:353-400` hand back the generated `data_id` to the contract), an attacker who owns account `X` can:
1. Submit an action receipt to `X` with an unmet `input_data_id = D` (postponing it, populating `PostponedReceiptId{X, D}` / `PendingDataCount{X, ...}` / `PostponedReceipt{X, ...}`), where the postponed actions are attacker-authored (e.g. `FunctionCall`s or `Transfer`s).
2. Set up a *separate*, attacker-controlled promise chain (e.g. via `promise_yield_create`) that will eventually emit the resolving `Data` receipt for `(X, D)`, whose timing the attacker controls by choosing when to send the resume transaction (bounded by the yield-timeout window).
3. `DeleteAccount` on `X` — `remove_account` clears the account/keys/contract data but leaves the postponed-receipt trie rows behind.
4. Wait for `X` to be re-created (top-level NEAR account names become available for anyone to register again once deleted) by an unrelated party who deploys their own contract at `X`.
5. Trigger the pending `Data` receipt for `(X, D)` at the chosen time. `process_receipt`'s `Data` arm finds the still-present `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` rows, and executes the old, attacker-authored action receipt against the *new* account's state.

No existing check (signature, nonce, access-key, or receipt validation) intervenes here: receipts are not access-key-signed (`Receipts are not signed... trusted because their hash has been signed by 2/3 of chunk validator stake` per `runtime/runtime/AGENTS.md:62`), and `apply_action_receipt` performs no comparison between the account's identity/generation at postponement time and at execution time.

### Impact Explanation
This is an authorization-escalation / unexpected-code-execution bug: actions authored by a previous, unrelated account owner can be executed against a freshly created account under the same name, with the runtime treating them as ordinary receipts targeting the new account's contract/storage. Depending on the postponed actions (e.g., `FunctionCall` invoking privileged methods, or a `Transfer`), this could corrupt state or move funds on the new account without its owner's consent — matching the "authorization escalation across accounts" bounty category.

### Likelihood Explanation
The attacker needs only ordinary unprivileged capabilities (deploy own contract, submit transactions, control timing of a yield/resume chain, and delete their own account) — no validator/node access. The main precondition is that the account name becomes available to (and is in practice reused by) a different party after deletion, which is a normal, permitted NEAR occurrence for released top-level account names. Precise timing control (delaying the resolving `Data` receipt until after re-creation) is achievable via the yield/resume mechanism, whose timeout window is attacker-controlled up to the protocol's configured yield-timeout length. The attack is deterministic and repeatable once these conditions are met.

### Recommendation
`remove_account` (`core/store/src/utils/mod.rs`) should also enumerate and remove all `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, and `ReceivedData` (and promise-yield-related) trie entries scoped to the account being deleted, mirroring the existing access-key/contract-data cleanup loops. Alternatively/additionally, `action_delete_account` could reject deletion while the account still has any pending postponed receipts or unresolved data dependencies, or the trie keys could incorporate an account "incarnation" counter so that a re-created account never observes leftover state from the previous incarnation.

### Proof of Concept
Runtime apply-path integration test:
1. Create account `X`, deliver an `ActionReceipt` to `X` with `input_data_ids = [D]` (unmet), causing `process_action_receipt` to write `PostponedReceiptId{X,D}`, `PendingDataCount{X, receipt_id}`, `PostponedReceipt{X, receipt_id}`.
2. Apply a `DeleteAccount` receipt (or call `action_delete_account`/`remove_account` directly) for `X`. Assert (documenting the bug) that `PostponedReceiptId{X,D}` / `PendingDataCount{X, receipt_id}` / `PostponedReceipt{X, receipt_id}` still exist in the trie after deletion.
3. Apply a `CreateAccount` action for `X` again (new "incarnation", fresh balance/contract).
4. Deliver a `Data` receipt with `receiver_id = X`, `data_id = D`.
5. Assert that the stale postponed action receipt from step 1 does **not** execute against the new account (currently it does execute via `process_receipt`'s `Data` arm, which is the vulnerability); after the fix, the `Data` receipt should either be a no-op or fail cleanly, and the leftover keys should have been purged during `DeleteAccount` in step 2.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
