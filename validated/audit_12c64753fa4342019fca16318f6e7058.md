### Title
Unprivileged relayer can permanently brick an eth-implicit wallet by starving the fixed-gas result callback in `rlp_execute` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the eth-implicit wallet global contract) exposes `rlp_execute`, a permissionless entry point that anyone (a "relayer") can call on behalf of an eth-implicit account, mirroring the report's pattern of a function reachable by an unprivileged third party that can push the contract into a state its normal, intended flow never anticipated, permanently locking user funds/functionality.

### Finding Description
`rlp_execute` is callable by **any** `predecessor_account_id` — there is no check that the caller is the account owner; this is by design so that untrusted relayers can submit a user's signed Ethereum transaction. Before dispatching, it sets an in-memory-then-persisted guard `self.has_in_flight_tx = true` and only resets it to `false` inside a `#[private]` callback, `rlp_execute_callback`: [1](#0-0) 

For the generic action path (and other paths that eventually chain into it), the *final* callback that resets the guard is always attached only a hardcoded, fixed gas budget, `RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, regardless of how large the return value of the invoked `target` method turns out to be: [2](#0-1) 

Inside that callback, an arbitrary-sized byte buffer coming back from the target contract's execution (`PromiseResult::Successful(value)`) is copied and (de)serialized into the `ExecuteResponse` return value: [3](#0-2) 

If the `target` method returns a sufficiently large payload (up to the protocol's max register/return-value size), processing it inside the fixed 5 Tgas budget can exceed the gas limit and panic the callback receipt. In nearcore's runtime, when a receipt's execution fails, **all state changes made during that receipt are rolled back** (only committed on success): [4](#0-3) 

Because `self.has_in_flight_tx = false;` is one of those state writes performed inside the failing/OOG callback, it is discarded along with everything else, leaving `has_in_flight_tx` permanently `true` in persisted state. Every subsequent call to `rlp_execute` immediately short-circuits with the "transaction already in progress" error and never reaches `inner_rlp_execute` again: [5](#0-4) 

There is no other authorized way to submit a NEAR-native transaction for an eth-implicit account (it has no NEAR access keys of its own — the wallet contract *is* the sole authorization mechanism), so once the flag is stuck, the account can never execute another action, including moving out any NEAR balance it holds.

### Impact Explanation
This causes a permanent freeze of funds/functionality for the affected eth-implicit account: any NEAR tokens held by the account (and any NEP-141/ERC-20-style balances routed through it) become permanently unusable, since `rlp_execute` — the only entry point capable of producing a signed action on behalf of the account — is permanently disabled. This matches the "permanent freezing of funds" acceptance criterion, and the trigger is reachable by an ordinary, unprivileged relayer (any account can call `rlp_execute`), consistent with the report's "anyone can call ... on any user" bug class.

### Likelihood Explanation
The relayer must submit a validly owner-signed RLP transaction (the wallet still verifies the embedded Ethereum signature before decoding an action), so an attacker cannot forge arbitrary target/method pairs. However:
- Any relayer that is handed (or intercepts/observes) a legitimately signed transaction whose target method happens to return a non-trivial payload can choose to relay it, deliberately or incidentally triggering the freeze — the wallet contract's whole design assumes relayers are untrusted third parties, so this is squarely within its threat model.
- Because the callback's gas budget is a fixed constant independent of the actual data size returned by the target call, this is a deterministic, reproducible failure mode rather than a rare edge case; it requires no more than an ordinary large-returning method call and a relayer willing (or careless) enough to submit it.

I was not able to fully confirm the exact ECDSA/RLP-signature verification code path (no matches found in the available index for `recover`/`ecdsa` under `runtime/near-wallet-contract`), so the precise scope of relayer-controllable inputs (e.g., whether gas/target can be freely chosen by the relayer vs. fully fixed by the signed payload) could not be exhaustively verified from the indexed contents alone.

### Recommendation
Make the final result-processing callback's gas allocation scale with (or be capped safely against) the size of data returned by the target call, and/or ensure `has_in_flight_tx` is reset via a mechanism that is robust to callback failure/gas exhaustion (e.g., reset the flag in a step that is guaranteed to execute regardless of the downstream callback's success/failure, or add a timeout/self-recovery path similar to promise-yield timeouts) so that an out-of-gas failure in the result-processing step cannot permanently strand the guard in the "in-flight" state.

### Proof of Concept
1. User signs (or a relayer intercepts) a valid RLP-encoded Ethereum transaction whose `target` is a contract/method known to return a very large payload (near the maximum permitted return/register size) and whose Near action falls into the default action path in `inner_rlp_execute`.
2. Any relayer account calls `wallet_contract.rlp_execute(target, tx_bytes_b64)`. `has_in_flight_tx` becomes `true`, and the target's function call executes successfully with its own generously allocated gas, returning the large payload.
3. The final `rlp_execute_callback` receipt, allocated only the fixed `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas), attempts to copy/serialize the large `Some(value)` into `ExecuteResponse` and exhausts its gas, causing the receipt to fail.
4. Per nearcore's receipt-apply logic, the failed receipt's state changes (including `self.has_in_flight_tx = false`) are rolled back; `has_in_flight_tx` remains `true` in persisted contract state.
5. Every future call to `rlp_execute` on this wallet contract now immediately returns the "transaction already in progress" error, permanently bricking the eth-implicit account and stranding any NEAR balance it holds. [6](#0-5) [4](#0-3)

    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
