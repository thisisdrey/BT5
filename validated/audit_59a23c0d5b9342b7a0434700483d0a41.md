### Title
Unbounded-slippage AMM swap in XCM fee-refund path allows value extraction from asset-conversion pools - ([File: cumulus/primitives/utility/src/lib.rs])

### Summary
`SwapFirstAssetTrader`, the `WeightTrader` used by Asset Hub (Rococo/Westend) and other parachain XCM configs, swaps a user's non-native fee asset into the `Target` fee asset via `pallet-asset-conversion`'s `SwapCredit`. The initial `buy_weight` swap correctly protects the user with a minimum-output bound, but the `refund_weight` path converts any unused fee back into the original asset by calling `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min = None`, i.e. with no slippage protection at all.

### Finding Description
In `buy_weight`, the swap is properly bounded: [1](#0-0) 

But in `refund_weight`, the reverse swap that returns unspent fee to the user is executed with no minimum: [2](#0-1) 

This call goes straight into `pallet_asset_conversion::Pallet::<T>::swap_exact_tokens_for_tokens` (via the `SwapCredit` trait), which explicitly treats `amount_out_min: None` as "accept any output": [3](#0-2) 

The pool's constant-product pricing (`get_amount_out`) is fully public and can be shifted arbitrarily within a single block by any account that can afford to submit swap extrinsics against the same pool (`swap_exact_tokens_for_tokens` / `swap_tokens_for_exact_tokens`, call indices 3 and 4, callable by any signed origin) immediately before the XCM message executes its refund. Since the refund executes inside on-chain message processing at a point whose relative ordering to other extrinsics in the block is attacker-influenceable (extrinsics ordering within a block, or transaction pool ordering before the block author includes/executes the incoming XCM), an attacker can:
1. Observe or predict that a `SwapFirstAssetTrader`-based refund will occur (a common, high-frequency operation on Asset Hub given routine XCM messages paying fees in non-native assets).
2. Submit a large swap against the same asset-conversion pool to move the price against the refund's `Target -> original asset` leg.
3. Let the refund execute at the manipulated price, receiving far fewer `refund_swap_asset` tokens back into the XCM `payment` holding than the pool's un-manipulated price would produce.
4. Reverse the initial swap afterward, extracting the value drained from the refund.

Existing guards do not stop this: `do_swap_exact_tokens_for_tokens`/`do_swap_exact_credit_tokens_for_tokens` only check `amount_out_min` when `Some` is supplied — when `None`, the `ensure!` bound is skipped entirely, so *any* nonzero `amount_out` is accepted regardless of how unfavorable.

### Impact Explanation
This is a public, unprivileged, underpriced-swap issue occurring inside routine XCM message execution on live Asset Hub runtimes (Rococo/Westend, and reused by Penpal and the staking-async parachain template), all of which wire `SwapFirstAssetTrader` into their `xcm_config.rs`. Value that should return to the fee-payer (or, if unclaimed, remain economically neutral) can instead be siphoned into the AMM pool/attacker via price manipulation, which is a form of "theft ... unbacked mint or unlock"-adjacent fund loss and directly matches the report's "lack of slippage checks / price manipulation via front-running" bug class, now located in a real polkadot-sdk swap-trader path rather than the external report's Solana program.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: it requires no privileged access, malicious validator/collator, or leaked keys — only ability to submit ordinary signed `swap_*` extrinsics against the same asset-conversion pool used for the fee asset, which is a normal, permissionless action. The main constraints are pool liquidity depth (larger pools require more capital to move materially) and precise timing/ordering control, but this fits squarely within the "public underpriced work" and "unauthorized value extraction via public entrypoint" impact categories, not the excluded "front-run-only" or "malicious relayer/validator" categories, since the attacker here is an ordinary user exploiting a genuinely missing check in the refund code path.

### Recommendation
Do not call `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min = None` in `refund_weight`. Track the amount originally taken from the user for the corresponding portion of `weight` being refunded (or use `quote_price_exact_tokens_for_tokens` at `buy_weight` time to remember the effective rate) and pass a computed minimum acceptable output, erring on the side of returning the refund in `Target` asset (skip the reverse swap) if a safe minimum cannot be established, consistent with how `buy_weight` already enforces `Some(fee)` protection.

### Proof of Concept
1. Configure a parachain using `SwapFirstAssetTrader` (as Asset Hub Westend/Rococo do) with an asset-conversion pool for `(NonNativeAsset, Target)`.
2. User submits an XCM message that overpays for weight using `NonNativeAsset`; `buy_weight` swaps into `Target` with a proper `Some(fee)` bound.
3. Before/around the block that processes the XCM's `refund_weight` call, attacker submits `AssetConversion::swap_exact_tokens_for_tokens` (or `swap_tokens_for_exact_tokens`) trades against the same pool to push the `Target -> NonNativeAsset` price down.
4. `refund_weight` executes its `SwapCredit::swap_exact_tokens_for_tokens(vec![Target, NonNativeAsset], refund, None)` call (`cumulus/primitives/utility/src/lib.rs:540-544`) and accepts whatever reduced `NonNativeAsset` amount the manipulated pool returns — no `ProvidedMinimumNotSufficientForSwap` check triggers because `amount_out_min` is `None`.
5. Attacker reverses their initial trade, capturing the value that should have been refunded to the fee payer.
