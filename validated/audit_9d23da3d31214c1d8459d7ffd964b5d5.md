### Title
Oracle price resolution reverts instead of degrading gracefully, causing unrelated market entry points (withdraw/borrow/repay) to permanently or temporarily brick when any enabled asset's price feed is missing/stale/low-confidence - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`price-resolve` in `v0-4-market.clar` reverts (`ERR-ORACLE-PYTH`, `ERR-ORACLE-DIA`, `ERR-ORACLE-INVARIANT`, `ERR-PRICE-CONFIDENCE-LOW`) whenever the underlying oracle call fails or returns stale/invalid data, rather than degrading gracefully. Health/value calculations that aggregate prices across a user's *entire* enabled asset set (via `price-multi-resolve`/`iter-price-multi`/`get-asset-value`) propagate this single failure to abort the whole computation.

### Finding Description
`resolve-pyth` and `resolve-dia` use `unwrap!`/`try!` around external oracle calls with no fallback path: [1](#0-0) 

`price-resolve` further enforces `oracle-price-legal` and `oracle-timestamp-fresh`, asserting into `ERR-ORACLE-INVARIANT` on any positivity or staleness violation - it never returns a sentinel "unavailable" value: [2](#0-1) 

`price-multi-resolve`/`iter-price-multi` batch-resolve prices for the full set of a user's collateral+debt assets and abort the entire batch (`ERR-ORACLE-MULTI`) if any single entry fails: [3](#0-2) 

`get-asset-value`, used in per-asset value calculations feeding health checks, directly calls `price-resolve` with no fallback: [4](#0-3) 

This matches the reported bug class: an oracle-facing price function that should tolerate "price unavailable" (return zero/degrade) instead reverts the caller, and here that caller is not an isolated view function but the *core health-check pipeline* shared by withdraw, borrow, repay, and liquidation entry points that must recompute a user's aggregate collateral/debt USD value across every enabled asset, not just the asset being acted upon.

### Impact Explanation
Because health computation is asset-set-wide, a single asset's oracle disruption (feed removed/never populated, confidence spike beyond `max-confidence-ratio`, or staleness beyond `max-staleness`) blocks health-dependent operations for *every* user who has that asset enabled as collateral or debt, even when their intended action (e.g., withdrawing a completely different, healthy asset, or repaying debt to improve their position) has nothing to do with the broken feed. This is a temporary freezing of funds for affected users until the feed is restored/updated - the qualifying "High" impact class (temporary freezing of funds) in this scope. If the feed issue is one this contract itself can trigger or prolong (e.g., a confidence check `check-confidence` tied to `max-confidence-ratio` at line 306, or the monotonic timestamp/staleness gate at lines 362-371), the freeze duration and scope are attacker/market-influenced rather than purely third-party, keeping it in scope per the rules ("Oracle manipulation caused by a bug in THIS code stays in scope").

### Likelihood Explanation
Likelihood is moderate: it requires a real-world condition where an asset's Pyth/DIA feed is temporarily unavailable, stale beyond `max-staleness`, or fails the confidence check - none of which requires DAO compromise, privileged access, or leaked keys. Given six supported assets, each with its own feed and staleness window, the probability that at least one feed degrades at some point (RPC hiccup, publisher gap, thin liquidity causing wide confidence intervals) is non-trivial over the contract's operating lifetime, and every such event freezes all cross-asset operations for affected users, not just interactions with the broken asset.

### Recommendation
Distinguish between "price truly unavailable" and "price violates business invariants" at the point where a single asset's price is being resolved as part of a larger position-wide computation:
- For batch/health computations (`price-multi-resolve`, `iter-price-multi`, `get-asset-value` used inside health checks), consider allowing withdraw/repay operations that strictly *improve* a position's health to proceed even if an unrelated collateral/debt asset's price cannot be resolved, by excluding that asset's stale/broken value only from the computation being validated when doing so cannot be exploited to under-value debt or over-value collateral (i.e., conservative substitution rather than hard revert), or provide a dedicated escape-hatch path (e.g., pause/allow-list per stale asset) so unaffected users are not collaterally blocked.
- At minimum, add unit tests exercising the "missing/stale/low-confidence price for a *different* asset than the one being withdrawn/repaid" scenario, mirroring the referenced Compound `open-oracle` test gap, to make this deliberate/accepted-risk decision explicit and documented rather than an unverified side effect of shared health-check code.

### Proof of Concept
1. User A deposits sBTC and stSTX as collateral and borrows STX, with all three feeds healthy (`enabled` mask includes STX, sBTC, stSTX).
2. The stSTX Pyth/DIA-derived feed (via `resolve-ststx`/`call-ststx-ratio`) becomes stale beyond its configured `max-staleness`, or the Pyth feed's confidence ratio temporarily exceeds `var-get max-confidence-ratio` (`check-confidence`, line 306).
3. User A attempts to `repay` part of the STX debt (an action that only improves health and involves no interaction with stSTX pricing directly), or attempts to `withdraw` sBTC collateral while keeping the position within a safe LTV.
4. Both entry points internally recompute total collateral/debt USD value across *all* enabled assets (via `price-multi-resolve`/`get-asset-value`) to validate the resulting position is healthy.
5. Because stSTX's price resolution fails `oracle-price-legal`/`oracle-timestamp-fresh`/`check-confidence`, `price-resolve` reverts with `ERR-ORACLE-INVARIANT`/`ERR-PRICE-CONFIDENCE-LOW`, propagating through `iter-price-multi`/`price-multi-resolve` as `ERR-ORACLE-MULTI`, and the entire `repay`/`withdraw` transaction reverts - even though neither action required stSTX's price to be resolved for correctness (repay reduces debt with the debt-asset price only; a partial sBTC withdrawal that keeps the position safe does not need stSTX's exact value beyond "still enabled").
6. User A's funds (the STX debt position or the sBTC collateral) are frozen until the stSTX feed recovers, despite the user's action not touching the disrupted asset. [5](#0-4)

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
  (acc { output: (list 64 uint), valid: bool, aids: (list 64 uint), idx: uint }))
  (let ((valid (get valid acc))
        (skip? (asserts! valid acc))
        (asset-ids (get aids acc))
        (idx (get idx acc))
        ;; resolve price - will use cache for ztokens
        (price (unwrap! (price-resolve oracle-data) (merge acc { valid: false })))
        (next (unwrap-panic (as-max-len? (append (get output acc) price) u64))))
    { output: next,
      valid: true,
      aids: asset-ids,
      idx: (+ idx u1) }))
