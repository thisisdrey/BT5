Audit Report

## Title
Relayer reward is paid and delivery order is settled without checking `DeliveryReceipt.success` - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`process_delivery_receipt` in the Snowbridge V2 outbound queue decodes a `DeliveryReceipt` carrying a `success: bool` field derived from Ethereum's `InboundMessageDispatched` event, but never inspects that field before paying the relayer reward via `T::RewardPayment::register_reward` and irreversibly removing the `PendingOrder`. This lets a relayer be rewarded for messages whose dispatch on Ethereum actually failed.

## Finding Description
`DeliveryReceipt::try_from` in `bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs` correctly decodes the `success` field from the `InboundMessageDispatched` Ethereum log [3](#0-2) . `submit_delivery_receipt`, a permissionless signed extrinsic, verifies the proof, decodes the receipt, and calls `process_delivery_receipt` [4](#0-3) . Inside `process_delivery_receipt`, only `receipt.gateway` (origin check) and `receipt.nonce` (replay/existence check via `PendingOrders::get`) are consulted; `receipt.success` is never read anywhere in the function body before `register_reward` is called and `PendingOrders::remove` settles the order and emits `MessageDelivered` [5](#0-4) . Neither the gateway check nor the pending-nonce check examines dispatch outcome, so they do not prevent this. The generic `RewardLedger::register_reward` bookkeeping mechanism used for payment has no concept of delivery success either, so it cannot compensate for this gap.

## Impact Explanation
This matches the impact-gate category of duplicate/incorrect settlement or payout and public underpriced work degrading bridge processing: any relayer whose message dispatch reverted on Ethereum (`success == false`) is still paid the full `order.fee` via `register_reward`, and the `PendingOrder` is removed and `MessageDelivered` is emitted as if delivery succeeded, misleading downstream consumers of that event/state about actual execution outcome.

## Likelihood Explanation
High likelihood and fully reachable by an unprivileged external actor: `submit_delivery_receipt` is a public signed extrinsic requiring only a validly proven Ethereum event log for `InboundMessageDispatched`, regardless of its `success` value. No malicious peer, governance, or privileged actor is needed — a relayer submitting proof for a legitimately failed dispatch (which occurs in normal operation, e.g., insufficient gas or reverted execution on Ethereum) triggers the unconditional payout path every time.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `receipt.success == true`. For `success == false`, still resolve/settle the `PendingOrder` per intended failure-handling design, but withhold the reward and emit a distinct event (e.g., `MessageDeliveryFailed`) instead of `MessageDelivered`.

## Proof of Concept
1. A message enqueued via `do_process_message` creates a `PendingOrder { nonce, fee, block_number }` with `fee > 0` [6](#0-5) .
2. On Ethereum, the corresponding message dispatch reverts, and the Gateway contract emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid receipt/proof for this event (ordinary honest relayer behavior, no proof forgery needed) and calls `submit_delivery_receipt`.
4. `DeliveryReceipt::try_from` decodes `success = false` correctly [7](#0-6) .
5. `process_delivery_receipt` proceeds unconditionally: `order.fee > 0` triggers `register_reward(&reward_account, ..., order.fee)`, then `PendingOrders::remove(nonce)` and `Event::MessageDelivered { nonce }` are emitted [8](#0-7) , despite the failed on-chain dispatch. A unit test asserting `receipt.success == false` results in reward being withheld does not exist in the current test suite.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
