Audit Report

## Title
Missing idempotency guard lets any account re-trigger `RegisterForeignToken` dispatch to Ethereum for an already-registered token - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

## Summary
`register_token` in `pallet-snowbridge-system-v2` only wraps the `ForeignToNativeId` storage write with `if !contains_key(token_id) { insert }`, but unconditionally proceeds to build and send `Command::RegisterForeignToken` to the outbound queue and emit `Event::RegisterToken` regardless of whether the token is already registered. The identical pattern exists in `pallet-snowbridge-system::do_register_token`. Since the call is reachable by any account through `pallet-snowbridge-system-frontend::register_token` (documented as "All origins are allowed"), an attacker can repeatedly re-trigger redundant outbound messages for an already-registered token.

## Finding Description
The reachable call chain is `pallet-snowbridge-system-frontend::register_token` (gated only by `T::RegisterTokenOrigin::ensure_origin`, which merely requires that `asset_id` be nested within the caller's own location) [1](#0-0)  → XCM `Transact` → `pallet-snowbridge-system-v2::register_token`, gated by `T::FrontendOrigin` which is satisfiable by any account routed through the frontend [2](#0-1) .

Inside `register_token`, the guard is scoped only to the storage insert:
```rust
if !ForeignToNativeId::<T>::contains_key(token_id) {
    ForeignToNativeId::<T>::insert(token_id, location.clone());
}
```
Execution then unconditionally continues to build `Command::RegisterForeignToken`, call `Self::send(message_origin, command, amount)`, and `Self::deposit_event(Event::<T>::RegisterToken { .. })`, with no `ensure!`/early-return tied to the `contains_key` check [3](#0-2) . The identical structure exists in the governance-facing `do_register_token` in `pallet-snowbridge-system` [4](#0-3) . There is no separate `Error::<T>::AlreadyRegistered`/`TokenAlreadyRegistered` variant or check anywhere in either pallet gating the command dispatch itself; the only related error variants concern location conversion, sending, and reanchoring failures, none of which cover the "already registered" case.

## Impact Explanation
Each call resolving to an already-registered `token_id` still produces a full `Command::RegisterForeignToken` message enqueued to the Snowbridge outbound queue and delivered to the Ethereum Gateway, consuming outbound-queue capacity, relayer processing, and Ethereum gas exactly as a first-time registration would — this matches the accepted "public underpriced work that degrades block production or stalls bridge processing" impact category. Because the frontend `register_token` allows any account owning (or nesting) an asset location to call it, and the amount/fee paid per call is caller-controlled (see the test invocation with `amount = 1` in `register_all_tokens_succeeds`) [5](#0-4) , an attacker can cheaply flood the outbound channel with redundant `RegisterForeignToken` commands for tokens already bridged.

## Likelihood Explanation
High likelihood: `register_token` in `pallet-snowbridge-system-frontend` is explicitly documented as accepting "All origins," requiring only that `asset_id` be nested within the caller's own consensus location, and the missing guard is deterministically reachable on every call with no race condition, governance action, or privileged assumption required [6](#0-5) .

## Recommendation
Convert the `contains_key` check into a hard `ensure!` that short-circuits the entire function before `Command::RegisterForeignToken` is constructed and sent, in both `pallet-snowbridge-system::do_register_token` and `pallet-snowbridge-system-v2::register_token`:
```rust
ensure!(!ForeignToNativeId::<T>::contains_key(token_id), Error::<T>::TokenAlreadyRegistered);
ForeignToNativeId::<T>::insert(token_id, location.clone());
```

## Proof of Concept
1. Account `A` calls `pallet-snowbridge-system-frontend::register_token(asset_id = A's own asset location, metadata, fee_asset)`; this succeeds, the XCM `Transact` reaches BridgeHub, `ForeignToNativeId` is populated, and `Command::RegisterForeignToken` is enqueued [2](#0-1) .
2. Account `A` (or any account whose location nests the same `asset_id`) calls `register_token` again with the identical `asset_id`.
3. `ForeignToNativeId::<T>::contains_key(token_id)` is `true`, so the storage insert is skipped, but execution proceeds unconditionally to `Self::send(message_origin, command, amount)` and `Self::deposit_event(...)`, enqueuing a second `Command::RegisterForeignToken` for the same token.
4. Repeating step 2 enqueues arbitrarily many duplicate `RegisterForeignToken` commands into the Snowbridge outbound queue for an already-registered token, with no on-chain rejection — reproducible as a unit test asserting that a second `register_token` call for the same `token_id` still emits `Event::RegisterToken` and queues a new outbound message.

		pub fn register_token(
			origin: OriginFor<T>,
			sender: Box<VersionedLocation>,
			asset_id: Box<VersionedLocation>,
			metadata: AssetMetadata,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let sender_location: Location =
				(*sender).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;
			let asset_location: Location =
				(*asset_id).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;

			let location = Self::reanchor(asset_location)?;
			let token_id = TokenIdOf::convert_location(&location)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			if !ForeignToNativeId::<T>::contains_key(token_id) {
				ForeignToNativeId::<T>::insert(token_id, location.clone());
			}

			let command = Command::RegisterForeignToken {
				token_id,
				name: metadata.name.into_inner(),
				symbol: metadata.symbol.into_inner(),
				decimals: metadata.decimals,
			};

			let message_origin = Self::location_to_message_origin(sender_location)?;
			Self::send(message_origin, command, amount)?;

			Self::deposit_event(Event::<T>::RegisterToken {
				location: location.into(),
				foreign_token_id: token_id,
			});

			Ok(())
		}

		pub(crate) fn do_register_token(
			location: &Location,
			metadata: AssetMetadata,
			pays_fee: PaysFee<T>,
		) -> Result<(), DispatchError> {
			let ethereum_location = T::EthereumLocation::get();
			// reanchor to Ethereum context
			let location = location
				.clone()
				.reanchored(&ethereum_location, &T::UniversalLocation::get())
				.map_err(|_| Error::<T>::LocationConversionFailed)?;

			let token_id = TokenIdOf::convert_location(&location)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			if !ForeignToNativeId::<T>::contains_key(token_id) {
				ForeignToNativeId::<T>::insert(token_id, location.clone());
			}

			let command = Command::RegisterForeignToken {
				token_id,
				name: metadata.name.into_inner(),
				symbol: metadata.symbol.into_inner(),
				decimals: metadata.decimals,
			};
			Self::send(SECONDARY_GOVERNANCE_CHANNEL, command, pays_fee)?;

			Self::deposit_event(Event::<T>::RegisterToken {
				location: location.clone().into(),
				foreign_token_id: token_id,
			});

			Ok(())
		}
