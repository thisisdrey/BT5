### Title
Stale `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId` entries survive `remove_account`, letting a deleted account's parked yield fire self-privileged actions against a same-named recreated account - ([File: core/store/src/utils/mod.rs])

### Summary
The `PromiseYieldTimeout` queue row itself is correctly account-agnostic (keyed only by a global per-shard index) and is properly excluded from `remove_account`'s per-account-prefix cleanup, so that part of the invariant holds. However, `remove_account` fails to delete the account-keyed `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, and `TrieKey::DataIdToYieldId` entries tied to the deleted `account_id`, so a pending yield callback can outlive account deletion and later fire against a newly recreated account of the same name with self-call (`predecessor_id == receiver_id`) privilege.

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:505-575`) only removes `TrieKey::Account`, `TrieKey::ContractCode`, `TrieKey::AccessKey`/`GasKeyNonce`, and `TrieKey::ContractData` entries for the account being deleted [1](#0-0) . It never scans or removes `TrieKey::PromiseYieldReceipt { receiver_id, data_id }`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId`, all of which embed `account_id` directly in the trie key (unlike `TrieKey::PromiseYieldTimeout { index }`, which is correctly account-agnostic and keyed only by a global queue index) [2](#0-1) [3](#0-2) .

When a `PromiseYield` receipt is processed it is stored under `PromiseYieldReceipt{receiver_id, data_id}` and a corresponding entry is enqueued in the global `PromiseYieldTimeout` queue carrying `{account_id, data_id, expires_at}` in its *value* [4](#0-3) [5](#0-4) .

`action_delete_account` calls `remove_account` but never touches these yield structures [6](#0-5) . If the account is later recreated under the same `account_id` (permitted for sub-accounts by `action_create_account`/`check_account_existence`, which only checks `account.is_none()` - it has no memory of prior incarnations) [7](#0-6) , the stale `PromiseYieldReceipt` remains addressable at the same trie key.

When `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3116`) eventually dequeues the timeout entry, it checks `state_update.contains_key(&promise_yield_key)` where `promise_yield_key = TrieKey::PromiseYieldReceipt{receiver_id: queue_entry.account_id, data_id: queue_entry.data_id}` [8](#0-7) . Because `remove_account` never removed this key, the check succeeds even though the account was deleted and recreated, and the code synthesizes a `PromiseResume` receipt with `predecessor_id = receiver_id = queue_entry.account_id` [9](#0-8) , forwarding it into normal receipt processing, which then finds and executes the original, pre-deletion yield receipt's actions against the current (new) account [10](#0-9) .

Since PromiseYield/resume is used as a self-call pattern, the resumed action receipt runs with `predecessor_id == current_account_id()`, which many contracts treat as an implicit "internal/private" authorization check. An attacker who controls the original account can pre-arrange the parked yield's callback actions (e.g., a privileged self-call method invocation with attacker-chosen arguments), delete the account, and have those actions fire with self-call trust against whatever contract/state a different party later deploys under the same reused account name.

### Impact Explanation
This is an authorization escalation: a receipt manufactured under the old occupant's control executes with self-predecessor privilege against a subsequently and independently created account of the same name, bypassing checks (`predecessor_id == current_account_id()`) that legitimate contracts rely on for privileged/internal callbacks. This matches the "authorization escalation across accounts or promises" bounty category and could be leveraged to drain funds or hijack state of the new account's contract, depending on what "private" callback logic exists in the recreated contract.

### Likelihood Explanation
Exploitation requires: (1) attacker deploys a contract to a sub-account they control and issues a `promise_yield_create` targeting a privileged self-callback with attacker-chosen data before deleting the account, (2) the account is deleted, (3) a third party creates a new account with the exact same `account_id` before the timeout height is reached, and (4) that third party's contract has a callback/private method reachable via the crafted action that an attacker benefits from invoking with self-predecessor trust. Steps 1–2 are fully attacker-controlled and cheap; step 3 (predicting/racing account-name reuse) is the main constraint, and is most plausible in systems that deterministically allocate/rotate per-user sub-accounts (e.g., `user123.app.near` patterns), reducing but not eliminating feasibility. This is a scoped, code-path-confirmed gap rather than a mainnet-guaranteed high-frequency issue.

### Recommendation
Extend `remove_account` (or `action_delete_account`) to also purge account-scoped yield-related state on deletion: iterate and remove `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, and `TrieKey::DataIdToYieldId` entries under the deleted `account_id`'s prefix (mirroring the existing access-key/contract-data prefix scans in `remove_account`), and/or have `resolve_promise_yield_timeouts` additionally validate that the resolved `PromiseYieldReceipt`'s original account "epoch"/existence is consistent (e.g., tombstone deleted accounts until all their pending yields are drained) before forwarding the resume.

### Proof of Concept
1. Runtime apply-path integration test (in `runtime/runtime/src/tests` or `test-loop-tests`):
   - Create sub-account `A` with a contract exposing a `#[private]` method `privileged_action` gated on `predecessor_id() == current_account_id()`.
   - From `A`, call a method invoking `promise_yield_create` targeting `A::privileged_action` with attacker-chosen args, producing entries `PromiseYieldReceipt{A, data_id}` and `PromiseYieldTimeout{index}` with `expires_at = H`.
   - Submit `DeleteAccount` for `A` (attacker is actor, succeeds).
   - Assert (regression check) that `PromiseYieldReceipt{A, data_id}` still exists in state after deletion (demonstrating the gap).
   - Recreate `A` as a sub-account with a new, unrelated contract (simulating a new occupant) before block height `H`.
   - Advance the chain to height `H`, triggering `resolve_promise_yield_timeouts`.
   - Assert that `privileged_action` executes (or its side effects appear) against the *new* `A` contract instance, proving the misfire; the correct/fixed behavior should assert no such execution occurs (e.g., the resume receipt is dropped or the callback fails due to missing/cleared state).
