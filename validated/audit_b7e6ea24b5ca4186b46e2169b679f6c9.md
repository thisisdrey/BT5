### Title
Attacker-controlled `RelayFromAddr`/`RelayToAddr` in `NebulaControl` messages is never validated against the sender's authenticated VPN address, allowing relay-state poisoning - ([File: relay_manager.go])

### Summary
The `PlaceOrder`-style bug in the external report is a data-validation gap: a nested, self-declared identity field inside an authenticated message (`exec_id`) is trusted at face value instead of being checked against the actual routing/identity context. Nebula's relay control protocol has the same class of flaw: `handleCreateRelayRequest`/`handleCreateRelayResponse` trust the `RelayFromAddr`/`RelayToAddr` fields carried inside an authenticated `NebulaControl` message without ever checking that `RelayFromAddr` actually equals the sending peer's own certificate-bound VPN address.

### Finding Description
`HandleControlMsg` unmarshals the `NebulaControl` payload and, for `CreateRelayRequest`/`CreateRelayResponse`, only checks that `RelayFromAddr`/`RelayToAddr` are non-nil before dispatching: [1](#0-0) 

`handleCreateRelayRequest` then derives `from := protoAddrToNetAddr(m.RelayFromAddr)` and only rejects it if it happens to equal one of *my own* VPN addresses: [2](#0-1) 

Critically, there is no check that `from` matches `h.vpnAddrs[0]` — the VPN address that `h` (the already-authenticated, cert-verified peer sending this control message) actually owns. The code proceeds to look up/insert relay state keyed by the attacker-supplied `from` value rather than by the peer's verified identity: [3](#0-2) 

The analogous processing happens on the response side in `EstablishRelay`, which resolves relay state purely by index (`InitiatorRelayIndex`/`ResponderRelayIndex`) but logs/reasons about `RelayFromAddr`/`RelayToAddr` without validating them against the connection's peer certificate: [4](#0-3) 

This mirrors the report's root cause exactly: a field embedded in a nested/inner structure of an otherwise-authenticated message (here, the claimed relay-from VPN address) is never cross-checked against the outer, already-verified identity (the peer's certificate-bound `vpnAddrs`), so a legitimate-but-malicious authenticated peer can assert an arbitrary "from" identity that the relay logic will trust and act on — just as a nested `PlaceOrder.exec_id` was trusted without being checked against the enclosing execution contract's identity.

### Impact Explanation
Because relay state (`hostinfo.relayState`, keyed by IP) is inserted/updated using the unauthenticated `from`/`target` fields rather than the sender's certificate-verified `vpnAddrs`, a compromised or malicious peer that has completed a normal handshake (i.e., holds a valid CA-signed certificate, so it is not excluded by the "no CA-signed certificate" scope restriction — the attack is performed by an authenticated peer sending a crafted control message, which is reachable without any additional trust) can cause a relay node to install `TerminalType`/`ForwardingType` relay entries associated with an arbitrary victim VPN address it doesn't own. Later relay data-plane traffic (`handleOutsideRelayPacket` / `SendVia`) is routed and accounted for based on these poisoned `PeerAddr`/`relayState` entries: [5](#0-4) 
This is remote state poisoning of the relay's routing tables, which can result in relay traffic being mis-forwarded, relay slots being wasted/hijacked for a spoofed peer identity, or one peer's relay path being disrupted/impersonated by another authenticated peer — without validating that the identity in the control message actually matches the identity established at the Noise/cert layer.

### Likelihood Explanation
Exploitation only requires being an authenticated Nebula peer capable of sending a `header.Control` message (any node with a valid, CA-signed cert that can complete a handshake with a relay-capable node) — no lighthouse spoofing, no invalid certificate, and no privileged host access is required. The `RelayFromAddr`/`RelayToAddr` fields are entirely attacker-chosen at the protocol layer, and the validation performed (`HandleControlMsg`, `handleCreateRelayRequest`) never ties them back to the sender's own `vpnAddrs`, making this straightforward to trigger via a single crafted `NebulaControl` message.

### Recommendation
In `handleCreateRelayRequest` (and correspondingly in `handleCreateRelayResponse`/`EstablishRelay`), require that `RelayFromAddr` be verified against `h.vpnAddrs` (the certificate-bound addresses of the connection that delivered the control message) before using it to key or mutate any `relayState`. Reject and log any `CreateRelayRequest`/`CreateRelayResponse` whose claimed `RelayFromAddr` does not correspond to the sending peer's verified identity, mirroring the exec_id-style recommendation of validating identity fields for every message (including relayed/forwarded ones) rather than trusting embedded values.

### Proof of Concept
1. Establish two independent, legitimately-authenticated Nebula tunnels to a relay-capable node `R`: attacker node `A` (cert address `A_ip`) and victim node `V` (cert address `V_ip`), both with valid CA-signed certs.
2. From `A`, send `R` a `header.Control` message of type `NebulaControl_CreateRelayRequest` with `RelayFromAddr = V_ip` (not `A_ip`) and `RelayToAddr` set to some target `T_ip` that `R` can reach.
3. `handleCreateRelayRequest` on `R` only checks `f.myVpnAddrsTable.Contains(from)` (fails, since `from=V_ip != R`) and then treats the request as if it legitimately originated from `V_ip`, inserting/updating relay state under `h.relayState` (where `h` is actually `A`'s HostInfo) keyed by `V_ip`, per [3](#0-2) .
4. Observe that `R`'s relay tables and subsequent `CreateRelayResponse`/data-plane relay forwarding now associate `A`'s tunnel with the victim's claimed identity `V_ip`, without `R` ever verifying that `A`'s certificate actually grants it `V_ip`.

func (rm *relayManager) EstablishRelay(relayHostInfo *HostInfo, m *NebulaControl) (*Relay, error) {
	relay, ok := relayHostInfo.relayState.CompleteRelayByIdx(m.InitiatorRelayIndex, m.ResponderRelayIndex)
	if !ok {
		var relayFrom, relayTo any
		if m.RelayFromAddr == nil {
			relayFrom = m.OldRelayFromAddr
		} else {
			relayFrom = m.RelayFromAddr
		}
		if m.RelayToAddr == nil {
			relayTo = m.OldRelayToAddr
		} else {
			relayTo = m.RelayToAddr
		}

		rm.l.Info("relayManager failed to update relay",
			"relay", relayHostInfo.vpnAddrs[0],
			"initiatorRelayIndex", m.InitiatorRelayIndex,
			"relayFrom", relayFrom,
			"relayTo", relayTo,
		)
		return nil, fmt.Errorf("unknown relay")
	}

	return relay, nil
}

func (f *Interface) handleOutsideRelayPacket(hostinfo *HostInfo, via ViaSender, out []byte, packet []byte, h *header.H, fwPacket *firewall.Packet, lhf *LightHouseHandler, nb []byte, q int, localCache firewall.ConntrackCache) {
	// Successfully validated the thing. Get rid of the Relay header and the AEAD tag
	signedPayload := packet[header.Len : len(packet)-hostinfo.ConnectionState.dKey.Overhead()]
	// Pull the Roaming parts up here, and return in all call paths.
	f.handleHostRoaming(hostinfo, via)
	// Track usage of both the HostInfo and the Relay for the received & authenticated packet
	f.connectionManager.In(hostinfo)
	f.connectionManager.RelayUsed(h.RemoteIndex)

	relay, ok := hostinfo.relayState.QueryRelayForByIdx(h.RemoteIndex)
	if !ok {
		// The only way this happens is if hostmap has an index to the correct HostInfo, but the HostInfo is missing
		// its internal mapping. This should never happen.
		hostinfo.logger(f.l).Error("HostInfo missing remote relay index",
			"relayRemoteIndex", h.RemoteIndex,
		)
		return
	}

	switch relay.Type {
	case TerminalType:
		// If I am the target of this relay, process the unwrapped packet
		// From this recursive point, all these variables are 'burned'. We shouldn't rely on them again.
		via = ViaSender{
			UdpAddr:   via.UdpAddr,
			relayHI:   hostinfo,
			relay:     relay,
			IsRelayed: true,
		}
		f.readOutsidePackets(via, out[:0], signedPayload, h, fwPacket, lhf, nb, q, localCache)
	case ForwardingType:
		// Find the target HostInfo relay object
		targetHI, targetRelay, err := f.hostMap.QueryVpnAddrsRelayFor(hostinfo.vpnAddrs, relay.PeerAddr)
		if err != nil {
			hostinfo.logger(f.l).Info("Failed to find target host info by ip",
				"relayTo", relay.PeerAddr,
				"relayFrom", hostinfo.vpnAddrs[0],
				"error", err,
			)
			return
		}

		// If that relay is Established, forward the payload through it
		if targetRelay.State == Established {
			switch targetRelay.Type {
			case ForwardingType:
				// Forward this packet through the relay tunnel, rebuilding it in place.
				// Encode overwrites the old outer header, and the new AEAD tag lands where the old one was
				fwdBuf := packet[:0:len(packet)] // Cap to len(packet) to protect memory from a larger parent buffer
				f.SendVia(targetHI, targetRelay, signedPayload, nb, fwdBuf, true)
			case TerminalType:
				hostinfo.logger(f.l).Error("Unexpected Relay Type of Terminal")
				return
			default:
				if f.l.Enabled(context.Background(), slog.LevelDebug) {
					hostinfo.logger(f.l).Debug("Unexpected targetRelay Type", "from", via, "relayType", targetRelay.Type)
				}
				return
			}
		} else {
			hostinfo.logger(f.l).Info("Unexpected target relay state",
				"relayTo", relay.PeerAddr,
				"relayFrom", hostinfo.vpnAddrs[0],
				"targetRelayState", targetRelay.State,
			)
			return
		}
	default:
		if f.l.Enabled(context.Background(), slog.LevelDebug) {
			hostinfo.logger(f.l).Debug("Unexpected relay type", "from", via, "relayType", relay.Type)
		}
	}
}
