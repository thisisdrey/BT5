### Title
`remote_allow_list` restriction is skipped entirely for relayed handshakes, allowing full bypass - ([File: handshake_manager.go])

### Summary
Nebula lets an operator restrict which UDP source addresses are allowed to complete a handshake with `lighthouse.remote_allow_list` / `remote_allow_ranges`. This is the nebula analog of the "reduced weight for delegated stake" control in the external report: it is a configurable trust reduction/restriction that applies to a normal (direct) actor. Just as the 0x report showed the reduced weight can be fully bypassed by wrapping delegated stake in an external contract that presents itself as a directly-owned staker, nebula's `remote_allow_list` check can be fully bypassed by routing the handshake through a relay, which is treated as an entirely different, unchecked code path.

### Finding Description
The `remote_allow_list` check is only performed `if !via.IsRelayed`, both in `HandshakeManager.validatePeerCert` and in `HandshakeManager.continueHandshake`: [1](#0-0) [2](#0-1) 

When a handshake arrives with `via.IsRelayed == true` (i.e., it arrived wrapped inside a `MessageRelay` frame forwarded by a relay peer, as handled in `handleOutsideRelayPacket`), the `AllowAll` gate on `f.lightHouse.GetRemoteAllowList()` is never invoked: [3](#0-2) 

`RemoteAllowList.AllowAll` is the function that enforces this address-based trust restriction: [4](#0-3) 

Because the check is keyed off `via.IsRelayed` rather than any property of the actual originating peer, a peer that would be denied a direct handshake by `remote_allow_list` can simply route its handshake initiation through any relay node (an "external contract"-equivalent intermediary that repackages the peer's traffic) and completely bypass the address restriction, exactly mirroring how the ZRX weight-reduction was bypassed by wrapping delegated stake in an external contract that presented as a direct staker.

### Impact Explanation
`remote_allow_list` is a network-trust boundary control — operators use it to restrict which source networks/addresses are permitted to even attempt a handshake (e.g., blocking handshakes originating from untrusted network ranges while still allowing valid certificates). Skipping this check for all relayed traffic means the restriction provides no real security guarantee once any relay is reachable in the mesh: any certificate holder who would otherwise be denied by the allow list can reach the target by relaying through a cooperating (or unwittingly-used) relay node, defeating the intended access restriction on that host.

### Likelihood Explanation
Any node configured with `use_relays: true` (a common, documented configuration for NAT traversal) exposes this path. No special privileges are needed by the attacker beyond a valid nebula certificate and reachability to some relay in the mesh — this is not a "malicious lighthouse/relay operator" scenario but a structural gap in how the check is gated (`via.IsRelayed`), so it is reachable by any certificate holder attempting to circumvent an address-based restriction on a target.

### Recommendation
Apply the `remote_allow_list` check uniformly regardless of `via.IsRelayed`, evaluating it against the true originating peer's identity/address information available after the relay unwrap (or explicitly document and enforce that relayed handshakes are validated against the relay's own allow-listed status plus the terminal peer's certificate-derived network, not skipped altogether). At minimum, the decision to exempt relayed handshakes from `remote_allow_list` should be an explicit, documented policy choice rather than an implicit skip, since it currently defeats the feature's purpose for any relay-reachable attacker.

### Proof of Concept
1. Configure host `A` with `lighthouse.remote_allow_list` denying UDP addresses in attacker's network range, and `relay.use_relays: true`.
2. Configure host `R` as a relay (`relay.am_relay: true`) reachable by both `A` and attacker host `E` (whose address is in the denied range).
3. `E` initiates a handshake to `A` directly — per `validatePeerCert`/`continueHandshake`, `via.IsRelayed == false`, so `AllowAll` runs and denies the handshake as configured.
4. `E` instead initiates the handshake via `R` (relay path), producing a `MessageRelay`-wrapped handshake that `A` processes through `handleOutsideRelayPacket` → `readOutsidePackets` with `via.IsRelayed == true`.
5. In `validatePeerCert`/`continueHandshake`, the `if !via.IsRelayed` guard causes the `remote_allow_list` check to be skipped entirely, and the handshake with `E` completes despite the configured restriction.

func (al *RemoteAllowList) AllowAll(vpnAddrs []netip.Addr, udpAddr netip.Addr) bool {
	if !al.AllowList.Allow(udpAddr) {
		return false
	}

	for _, vpnAddr := range vpnAddrs {
		if !al.getInsideAllowList(vpnAddr).Allow(udpAddr) {
			return false
		}
	}

	return true
}
