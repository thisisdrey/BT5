### Title
Permanent freezing of funds when `DeterministicStateInitAction` cannot match a pre-funded, address-determining `DeterministicAccountStateInit` payload - (File: `runtime/runtime/src/action_validation.rs`, `runtime/runtime/src/actions.rs`)

### Summary
NEAR's deterministic accounts (NEP‑616) are a CREATE2-style construct: the account id is `derive_near_deterministic_account_id(state_init)`, a hash of the exact `DeterministicAccountStateInit` bytes [1](#0-0) . As with Solidity `CREATE2`, users can pre-fund this deterministically-computed address via a plain `Transfer` before the account is actually initialized with code/data, exactly as the docs describe: "A `Transfer` can also deposit a balance before the `DeterministicStateInitAction`. The account will not be usable, however, until the `DeterministicStateInitAction` is also executed." [2](#0-1) . Crucially, such a transfer-created deterministic account gets **no access key** [3](#0-2) , so the only way to ever make the funds spendable is to later submit a matching `DeterministicStateInitAction`.

### Finding Description
`validate_deterministic_state_init` requires that the account id derived from the *exact* `state_init` payload equals the receiver id, and separately enforces per-entry key/value length limits on `state_init.data`: [4](#0-3) 

Because the address is a hash of the full `state_init` (including all `data` entries), the address and the validity of the payload are coupled in the same way the Solidity report describes for `CREATE2` salts derived from tranche percentages: if the intended `state_init` violates `DeterministicStateInitKeyLengthExceeded`/`DeterministicStateInitValueLengthExceeded`, the *only* fix is to shrink/alter the data — but doing so changes the hash and therefore the derived account id, producing a different address than the one that was pre-funded. There is no way to submit a `DeterministicStateInitAction` that both (a) hashes to the already-funded receiver id and (b) passes the length-limit validation, once the offending `state_init` has been chosen and an address funded against it.

Unlike a normal implicit account, a deterministic account created purely via `Transfer` (with `AccountContract::None`) has no access key and no code — it cannot sign transactions and cannot execute any receipt to move its own balance. The relevant docs and tests confirm the general implicit-creation flow, including that `NearDeterministic` transfers do not add an access key [5](#0-4)  and [6](#0-5) .

This mirrors the reported Solidity bug precisely: an address is derived deterministically from parameters that must also satisfy a separate correctness/limit check; if the check fails, the parameters can never be "fixed" without invalidating the very address that funds were sent to, and the account has no other escape hatch (no clawback-analog exists in nearcore for this path).

### Impact Explanation
If a user (or, more realistically, an off-chain integration/tool building a `DeterministicAccountStateInit`) miscalculates the size of a `data` entry (e.g., off by a few bytes over `max_length_storage_key`/`max_length_storage_value`) and funds the resulting deterministic address via `Transfer` before verifying the `DeterministicStateInitAction` would succeed, the funds become permanently unrecoverable: the account exists (created by the successful `Transfer`), has a balance, but can never receive code or an access key, since the one `state_init` payload that hashes to that address is permanently rejected by validation, and any corrected payload hashes to a different address. This is a genuine "permanent freezing of funds" outcome reachable purely through unprivileged, ordinary client transactions (`Transfer` + `DeterministicStateInitAction`), with no admin/relayer/validator privilege required.

### Likelihood Explanation
This requires a specific but realistic sequence: (1) an integrator computes a `DeterministicAccountStateInit` off-chain containing data that slightly exceeds `max_length_storage_key`/`max_length_storage_value` (a mistake, not a malicious act, similar to the tranche-percentage mismatch in the Solidity report), (2) funds are sent to the derived address via `Transfer` before the `DeterministicStateInitAction` is verified to succeed (i.e., "counterfactual funding," the same class of behavior the external report calls out), and (3) the `DeterministicStateInitAction` is submitted afterward and fails validation. This is a foot-gun for tooling/integrators building on deterministic accounts rather than something exploitable by an attacker against a victim's existing funds, so likelihood is moderate rather than high, but the class of usage (funding before verifying deploy-ability) is exactly the "counterfactual deployment" pattern called out in the source report as the trigger.

### Recommendation
- Do not tie the *validity/size limits* of `state_init.data` to the identity-deriving hash without providing any escape path: consider allowing partial/incremental data initialization (so an oversized dataset can be split across multiple successful `DeterministicStateInitAction` calls without changing the account id), or validate the payload against limits before it is ever hashed into an address recommended for funding (e.g., a canonical "predict address" RPC/view helper that performs the same validation as the actual action, so integrators can catch violations before funding).
- Consider allowing recovery of the pre-funded balance from a stuck, codeless deterministic account (e.g., via a protocol-level action that lets the original sender reclaim funds sent to a deterministic account that can never be successfully initialized), analogous to the "extend clawback" remediation accepted in the source report.
- At minimum, strongly document (and provide tooling/SDK guards) warning integrators never to fund a deterministic address before confirming, on-chain or via an equivalent validation library, that the exact `state_init` bytes pass `validate_deterministic_state_init`.

### Proof of Concept
1. Off-chain, construct `DeterministicAccountStateInit::V1 { code, data }` where one entry's key or value exceeds `max_length_storage_key`/`max_length_storage_value` (test shows the boundary is 2048 bytes for keys, 4194304 for values) [7](#0-6) .
2. Compute `det_account = derive_near_deterministic_account_id(&state_init)` [8](#0-7) .
3. Send a `Transfer` action from any funded account to `det_account`. This succeeds and creates the account with a balance and no access key, per the documented behavior [2](#0-1) .
4. Submit `Action::DeterministicStateInit(DeterministicStateInitAction { state_init, deposit })` targeting `det_account`. This fails with `DeterministicStateInitKeyLengthExceeded`/`DeterministicStateInitValueLengthExceeded` [9](#0-8) .
5. Any attempt to shrink `data` to pass the length check changes `det_account`'s derived id (since it's a hash over the whole payload), meaning that corrected payload targets a different, unfunded account — the original `det_account` retains its balance forever with no code and no access key, and thus no path to ever spend or reclaim the funds.

*Note: full end-to-end confirmation would require running this exact sequence in a local NEAR node/test-loop harness (e.g. extending `test-loop-tests/src/tests/deterministic_account_id.rs`), which is not something achievable via static code search alone; the analysis here is based on the validation and creation logic cited above.*

```rust
/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}
```

```rust
fn validate_deterministic_state_init(
    limit_config: &LimitConfig,
    action: &DeterministicStateInitAction,
    receiver_id: &AccountId,
) -> Result<(), ActionsValidationError> {
    validate_global_contract_identifier(action.state_init.code())?;

    let derived_id = derive_near_deterministic_account_id(&action.state_init);

    if derived_id != *receiver_id {
        return Err(ActionsValidationError::InvalidDeterministicStateInitReceiver {
            derived_id,
            receiver_id: receiver_id.clone(),
        });
    }

    // State init entries must not violate limits of individual state keys and values.
    for (key, value) in action.state_init.data() {
        if key.len() as u64 > limit_config.max_length_storage_key {
            return Err(ActionsValidationError::DeterministicStateInitKeyLengthExceeded {
                length: key.len() as u64,
                limit: limit_config.max_length_storage_key,
            }
            .into());
        }

        if value.len() as u64 > limit_config.max_length_storage_value {
            return Err(ActionsValidationError::DeterministicStateInitValueLengthExceeded {
                length: value.len() as u64,
                limit: limit_config.max_length_storage_value,
            }
            .into());
        }
    }

    Ok(())
}
```
