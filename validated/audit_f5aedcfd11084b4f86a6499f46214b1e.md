### Title
Forwarding-relay state silently orphaned on rehandshake leaves initiator's relay path permanently stuck (`Requested`/`PeerRequested` never re-established) - (File: `connection_manager.go`, `relay_manager.go`)

### Summary
When a Nebula node acting as a middleman/forwarding relay (`ForwardingType`) rehandshakes with the initiator (e.g. due to certificate rotation, roaming, or a race that produces a new primary `HostInfo`), its in-flight, not-yet-used relay state (`Requested`/`PeerRequested`) is not migrated to the new primary `HostInfo`. The initiator keeps retrying against the (now correctly-resolved) new primary hostinfo, but that hostinfo has no memory of the relay negotiation, so the relay path can never complete — mirroring the reported bug class where an in-progress, escrowed state becomes permanently unrecoverable once a concurrent state transition (sunset/recovery, here: rehandshake/primary-swap) invalidates the context the recovery path depended on.

### Finding Description
`connectionManager.migrateRelayUsed` is the only place that copies relay-for state from an old `HostInfo` to a newly-promoted primary `HostInfo` during a rehandshake: [1](#0-0) 

For entries that already exist on the new hostinfo, it explicitly skips `PeerRequested` and `Disestablished` states ("do nothing"), and for entries that don't yet exist on the new hostinfo, it only migrates them if `cm.relayUsed` shows the relay index has actually carried traffic: [2](#0-1) 

A `ForwardingType` relay is created in the `PeerRequested` state on the middleman the moment it forwards a `CreateRelayRequest` downstream, *before* any traffic has flowed through it: [3](#0-2) 

Because no traffic has crossed the relay yet, `cm.relayUsed` has no entry for it, so `migrateRelayUsed` never carries this half-established relay state forward when the middleman's primary hostinfo toward the initiator changes. The old hostinfo holding that `PeerRequested` state is demoted/eventually torn down, and its relay bookkeeping is lost. Only a fully-final `unlockedDeleteHostInfo` marks relays `Disestablished` (which itself doesn't apply here, since this is a non-final primary swap, not the last hostinfo): [4](#0-3) 

The initiator, unaware of this, continues retrying its own `Requested` relay entry by resending `CreateRelayRequest` to the middleman's freshly-resolved primary hostinfo: [5](#0-4) 

Since the middleman's new primary hostinfo has no record of the original downstream relay negotiation with the target, the retried request restarts the handshake/relay sequence from scratch on the middleman side, but the previously-issued relay index and any state tied to it on the vanished old hostinfo is gone — and if the target-side `CreateRelayResponse` for the original attempt does eventually arrive, `handleCreateRelayResponse` looks up the peer hostinfo relay state via `QueryVpnAddr`/`QueryRelayForByIp` against the *current* primary, finds nothing matching, and silently drops it: [6](#0-5) 

The comment in `AddRelay` acknowledges the general shape of this class of bug ("a relay standing on an unlinked hostinfo would never carry traffic, and its Relays entry could never be reclaimed"), but the fix there only guards index allocation, not the pre-existing in-flight `PeerRequested` state on the demoted hostinfo: [7](#0-6) 

### Impact Explanation
A relay-dependent tunnel establishment between two peers behind restrictive NATs can be silently and durably wedged: the initiator keeps resending `CreateRelayRequest`s that never resolve into a completed relay, and no automatic mechanism reconstructs the lost middleman-side state, because the migration logic in `migrateRelayUsed` is explicitly gated on prior traffic usage. This is a remote state-poisoning / connectivity-denial condition confined to the relay negotiation path (no cryptographic material or authentication is bypassed), reachable purely through normal protocol timing (rehandshake racing with a first-time forwarding relay setup) without needing a CA-signed certificate beyond what's already required to be a Nebula peer.

### Likelihood Explanation
This requires the middleman's tunnel toward the initiator to rehandshake (certificate rotation, roaming/NAT rebind, or connection-manager driven rehandshake) while acting as a first-time forwarding relay for that initiator — i.e., before any traffic has flowed over the relay. This is a plausible, not rare, timing window in real deployments that use relays and periodically rotate certificates or roam, but it is not trivially attacker-triggerable without some influence over rehandshake timing on the relay node.

### Recommendation
In `connectionManager.migrateRelayUsed` (and in `hostmap.unlockedDeleteHostInfo`/`unlockedMakePrimary` paths generally), migrate *all* `relayState.CopyAllRelayFor()` entries to the new primary hostinfo regardless of whether `cm.relayUsed` shows prior traffic, or at minimum re-send/regenerate the negotiation for `Requested`/`PeerRequested` entries the same way it already does for `Requested`. Alternatively, add a background sweep that detects relay entries stuck in `Requested`/`PeerRequested` beyond a timeout and either retries with a fresh index against the current primary or actively notifies the initiator to restart relay selection, instead of silently dropping the state.

### Proof of Concept
1. Peer A (initiator) has no direct route to Peer C, and knows Peer B as a relay; A initiates a handshake to C via B.
2. B (`am_relay=true`) receives the `CreateRelayRequest` from A on hostinfo `hb1` (A<->B tunnel), creates `PeerRequested` relay-for state on `hb1`, and forwards `CreateRelayRequest` to C — see `relayManager.handleCreateRelayRequest` "target is not me" branch (`relay_manager.go:525-604`).
3. Before C's `CreateRelayResponse` reaches B, B's tunnel to A rehandshakes (e.g. B's certificate is rotated, per `connectionManager.tryRehandshake`), producing a new primary hostinfo `hb2` for the A<->B tunnel.
4. `connectionManager.migrateRelayUsed` runs for `hb1`'s `relayForByAddr` (empty since it hasn't been used) — no entry for the pending `PeerRequested` relay is present, so nothing migrates onto `hb2`.
5. A continues to resend `CreateRelayRequest` to B, now resolved to `hb2`; if C's original `CreateRelayResponse` eventually arrives at B, `handleCreateRelayResponse` cannot find matching state for it against `hb2` and drops it (`relay_manager.go:344-380`).
6. The relay never establishes for that attempt; A's relay-based path to C is stuck until unrelated external factors (e.g. full handshake timeout and restart, or B's process cycling) eventually reset state.

func (cm *connectionManager) migrateRelayUsed(oldhostinfo, newhostinfo *HostInfo) {
	relayFor := oldhostinfo.relayState.CopyAllRelayFor()

	for _, r := range relayFor {
		existing, ok := newhostinfo.relayState.QueryRelayForByIp(r.PeerAddr)

		var index uint32
		var relayFrom netip.Addr
		var relayTo netip.Addr
		switch {
		case ok:
			switch existing.State {
			case Established, PeerRequested, Disestablished:
				// This relay already exists in newhostinfo, then do nothing.
				continue
			case Requested:
				// The relay exists in a Requested state; re-send the request
				index = existing.LocalIndex
				switch r.Type {
				case TerminalType:
					relayFrom = cm.intf.myVpnAddrs[0]
					relayTo = existing.PeerAddr
				case ForwardingType:
					relayFrom = existing.PeerAddr
					relayTo = newhostinfo.vpnAddrs[0]
				default:
					// should never happen
					panic(fmt.Sprintf("Migrating unknown relay type: %v", r.Type))
				}
			}
		case !ok:
			cm.relayUsedLock.RLock()
			if _, relayUsed := cm.relayUsed[r.LocalIndex]; !relayUsed {
				// The relay hasn't been used; don't migrate it.
				cm.relayUsedLock.RUnlock()
				continue
			}
			cm.relayUsedLock.RUnlock()
			// The relay doesn't exist at all; create some relay state and send the request.
			var err error
			index, err = AddRelay(cm.l, newhostinfo, cm.hostMap, r.PeerAddr, nil, r.Type, Requested)
			if err != nil {
				cm.l.Error("failed to migrate relay to new hostinfo", "error", err)
				continue
			}
