The repository in scope is a mirror of the Go standard library itself (`crypto/tls`, `net/http`, etc.), not an application that consumes TLS to talk to a message broker. The external report describes an *application-layer* bug in `oslo.messaging`'s RabbitMQ driver, which fails to pass the expected broker hostname down into the TLS stack, so hostname verification never happens even though certificate-chain validation is enabled.

Within this repo, the actual `crypto/tls` implementation already enforces the corresponding check correctly:
- `Client()` requires callers to set either `ServerName` or `InsecureSkipVerify` [1](#0-0) , and `makeClientHello` rejects configs that set neither [2](#0-1) .
- `dial()` (used by `tls.Dial`/`DialWithDialer`) automatically infers `ServerName` from the connection address when it isn't explicitly set, ensuring hostname verification has a value to check against [3](#0-2) .
- `verifyServerCertificate` passes `DNSName: c.config.ServerName` into `x509.VerifyOptions` and only skips this when `InsecureSkipVerify` is explicitly set by the caller [4](#0-3) .
- `Conn.VerifyHostname` explicitly documents and enforces that hostname isn't verified when `InsecureSkipVerify` was used [5](#0-4) , matched by an existing regression test `TestVerifyHostname` [6](#0-5) .

There is no analogous production Go code path in this repository where a hostname/`ServerName` is silently dropped or omitted before the TLS handshake despite certificate validation being enabled — the library's own client dial and handshake logic always ties `ServerName` to the verification `DNSName`. The bug described in the advisory is specific to the oslo.messaging Python application's own driver code (not present here), so no reachable, provable Go analog exists in this repo.

```go
// VerifyHostname checks that the peer certificate chain is valid for
// connecting to host. If so, it returns nil; if not, it returns an error
// describing the problem.
func (c *Conn) VerifyHostname(host string) error {
	c.handshakeMutex.Lock()
	defer c.handshakeMutex.Unlock()
	if !c.isClient {
		return errors.New("tls: VerifyHostname called on TLS server connection")
	}
	if !c.isHandshakeComplete.Load() {
		return errors.New("tls: handshake has not yet been performed")
	}
	if len(c.verifiedChains) == 0 {
		return errors.New("tls: handshake did not verify certificate chain")
	}
	return c.peerCertificates[0].VerifyHostname(host)
}
```

```go
	}
```
