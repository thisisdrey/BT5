### Title
Out-of-bounds/uncaught-exception read in `ValidateMultiSign`/`BatchValidateSign` precompile array decoding - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts decode caller-supplied calldata into a `DataWord[]` array and then use attacker-controlled offset/length words to index into that array and into the raw `data` byte buffer, with no bounds validation unless the Osaka hardfork flag is active.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute()` and `PrecompiledContracts.BatchValidateSign.doExecute()` parse the raw call data with `DataWord.parseArray(rawData)` and then compute array offsets purely from attacker-supplied words, e.g.: [1](#0-0) 
and the shared helpers used to materialize the arrays: [2](#0-1) 

The only defense (`isValidAbiEncoding`, which checks the total length is a multiple of `WORD_SIZE` and matches a header/item layout) is gated behind `VMConfig.allowTvmOsaka()`: [3](#0-2) [4](#0-3) 

Even when `isValidAbiEncoding` passes, `bytesOffset`, `bytesLen`, and array-length fields come straight from `intValueSafe()` on attacker-controlled `DataWord`s and are used unchecked as array indices (`words[offset + i + 1]`) and as offsets/lengths into `data` for `Arrays.copyOfRange` in `extractBytes`: [5](#0-4) 
Because Java arrays are always bounds-checked at the JVM level, a genuine silent memory over-read (as in the TensorFlow CWE-125 case) is not directly possible; instead these unchecked offsets/lengths translate into `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` thrown from deep inside `extractBytesArray`/`extractSigArray`/`extractBytes` before the code reaches its own `try { ... } catch (Throwable t)` wrapper. Looking at `ValidateMultiSign.execute()`, the array construction calls at lines 1072-1074 sit *outside* the inner `try` block that only wraps the permission-weight loop (lines 1082-1118); an exception thrown while building `signatures` is not caught locally.

The `BatchValidateSign.execute()` wraps `doExecute()` in its own outer `try/catch (Throwable t)` and swallows the exception, returning a zero result — that path is safe: [6](#0-5) 
but `ValidateMultiSign.execute()` has no such outer guard, so any exception thrown while decoding the signature array propagates out of `execute()` into `Program.callToPrecompiledAddress`, which calls `contract.execute(data)` with no surrounding try/catch: [7](#0-6) 

There is existing test evidence (`TIP-854`) confirming this exact pre-activation failure mode is a known, accepted risk in the codebase for these two precompiles: [8](#0-7) [9](#0-8) 

Both precompiles are reachable by any contract via a plain `CALL`/`STATICCALL`/`DELEGATECALL` opcode to their fixed addresses, resolved in `PrecompiledContracts.getContractForAddress`: [10](#0-9) 
via the standard `exeCall` dispatch used by all CALL-family opcodes: [11](#0-10) 

### Impact Explanation
This is reachable by any unprivileged contract deployer/caller who can craft calldata for a `CALL` to the `validateMultiSign`/`batchValidateSign` precompile addresses. Where the pre-Osaka `ValidateMultiSign` path throws an uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` from `extractBytesArray`/`extractSigArray`/`extractBytes`, that exception is not a Java-level "read of arbitrary memory" (JVM bounds-checking prevents that), but it does propagate as an unexpected `RuntimeException` out of `Program.callToPrecompiledAddress` with no local handling in `ValidateMultiSign`, unlike the sibling `BatchValidateSign` contract which explicitly guards against this. Depending on how far up the call stack such a runtime exception is ultimately caught (this could not be fully confirmed within the available index — I was not able to trace the full exception-handling chain in `Runtime`/`VM` execution loop with the tools available), this is either (a) a contained, transaction-level revert (low severity, effectively a bug-parity gap rather than a security bypass), or (b) if any code path in block application / batch verification does not catch generic `RuntimeException`, an uncaught exception could destabilize processing of that transaction/block. I could not verify path (b) conclusively with the available search tools, so I am not able to assert High/Critical impact (chain halt, RCE, fund theft) with confidence for this specific analog.

### Likelihood Explanation
High reachability: a single crafted TRC20-style contract call to a fixed, well-known precompile address is enough to trigger the code path, requiring no special privileges, keys, or coordination — only a normal signed transaction invoking `CALL`.

### Recommendation
Bring `ValidateMultiSign.execute()` in line with `BatchValidateSign.execute()` by wrapping the entire body (including `DataWord.parseArray`, offset extraction, and `extractBytesArray`/`extractSigArray` calls) in a `try { ... } catch (Throwable t) { return Pair.of(true, DATA_FALSE); }`, and make the `isValidAbiEncoding` bounds check unconditional (not gated behind `VMConfig.allowTvmOsaka()`) for both precompiles so malformed/short calldata is rejected deterministically instead of relying on incidental JVM bounds-check exceptions.

### Proof of Concept
Not independently reproduced in this analysis (index-only investigation); the existing `testTip854PreActivationNoOp` test in `ValidateMultiSignContractTest.java` already demonstrates that calling `ValidateMultiSign.execute()` with a too-short input (`new byte[(5 + 1) * 32]`) while `VMConfig.initAllowTvmOsaka(0)` can raise an uncaught `RuntimeException` from the decoder, matching the documented pre-activation failure mode: [8](#0-7)

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }

  private static byte[] extractBytes(byte[] data, int offset, int len) {
    return Arrays.copyOfRange(data, offset, offset + len);
  }

  public static void exeCall(Program program, DataWord adjustedCallEnergy,
      DataWord codeAddress, DataWord value, DataWord tokenId, boolean isTokenTransferMsg) {

    DataWord inDataOffs = program.stackPop();
    DataWord inDataSize = program.stackPop();

    DataWord outDataOffs = program.stackPop();
    DataWord outDataSize = program.stackPop();

    program.memoryExpand(outDataOffs, outDataSize);
    int op = program.getCurrentOpIntValue();
    MessageCall msg = new MessageCall(
        op, adjustedCallEnergy, codeAddress, value, inDataOffs, inDataSize,
        outDataOffs, outDataSize, tokenId, isTokenTransferMsg);

        PrecompiledContracts.getContractForAddress(codeAddress);
    if (contract != null) {
      if (program.isConstantCall()) {
        contract =  PrecompiledContracts.getOptimizedContractForConstant(contract);
      }
      program.callToPrecompiledAddress(msg, contract);
    } else {
      program.callToAddress(msg);
    }
    program.step();
  }
