### Title
Unprivileged attacker can fill a victim's per-account token list to `MAX_TOKENS_PER_USER` via dust `DepositToken` transfers, DoSing the victim's deposits of new collateral types and issuance of new debt - (File: contracts/Pool.sol)

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined number of deposit tokens and debt tokens tracked per account. Every `DepositToken` transfer (including a permissionless `transfer`/`transferFrom` of 1 wei) registers the token in the recipient's list when their prior balance was zero. An attacker can therefore permissionlessly push a victim's list to the cap, after which any action that would register a *new* token — `DepositToken._mint` (deposit of a new collateral) and `DebtToken` issuance (`addToDebtTokensOfAccount`) — reverts with `UserReachedMaxTokens`. This is the Metronome analog of the CVE-2019-2537 bug class (attacker-driven denial of service / availability loss): an unprivileged user can hang core protocol operations for a chosen victim.

### Finding Description
The invariant that breaks is liveness of position management:

- `DepositToken._transfer` adds the token to the **recipient's** list whenever the recipient's previous balance was zero, with no opt-in or minimum amount [1](#0-0) 
- The same happens on mint: `_mint` calls `pool.addToDepositTokensOfAccount(account_)` when `balanceBefore == 0` [2](#0-1) 
- `Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are both gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts `UserReachedMaxTokens()` once `debtTokensOfAccount + depositTokensOfAccount >= 30` [3](#0-2) [4](#0-3) 
- `DepositToken.transfer` / `transferFrom` are fully public; the only check is `_revertIfLocked(sender, amount)` on the **sender's** position — the attacker keeps no debt, so nothing blocks dust sends [5](#0-4) 

Attack path (all public, unprivileged):
1. Attacker deposits dust into each of the pool's registered deposit tokens (needs only `amount_ > 0`; there is no minimum deposit).
2. Attacker calls `depositToken_i.transfer(victim, 1)` for each distinct deposit token. Each call registers token `i` in `depositTokensOfAccount[victim]`.
3. Once the combined list reaches 30 (attacker can also force the victim's existing deposits/debts to count), the victim cannot: deposit any *new* collateral type (`_mint` → `addToDepositTokensOfAccount` reverts), or issue a synth whose `DebtToken` they don't already hold (`issue` → `addToDebtTokensOfAccount` reverts).

Concretely dangerous scenario: a victim approaching liquidation front-run/stuffed with dust can no longer deposit a *new* collateral type to heal their position, and gets liquidated — converting a temporary DoS into realized loss of funds.

No privileged role is required: `addToDepositTokensOfAccount` is only restricted to being called *by* a registered deposit token, which the attacker reaches via ordinary transfers. Modifiers that could stop this (`whenNotPaused`, `nonReentrant`, `SynthContext._msgSender`) do not apply to plain `transfer`, and there is no minimum-transfer or opt-in guard.

### Impact Explanation
- Denial of service on `deposit` (new collateral types) and `issue` (new debt tokens) for a targeted account — direct availability impact matching the CVE class.
- Escalation to loss of funds: a victim unable to add collateral during a price move is liquidated where a rescue deposit would have saved them.
- Recovery is possible (the victim can `transfer` each dust token's full balance out so `removeFromDepositTokensOfAccount` fires [6](#0-5) ), so this is a *temporary* freeze / griefing rather than permanent fund lock — but it costs the victim gas and can be re-applied repeatedly, and it cannot be prevented by the victim since anyone can send them deposit tokens.

### Likelihood Explanation
- Cost: trivially cheap — 1 wei per token per account; a single batch of ≤30 transfers locks the victim.
- Constraint: effectiveness depends on the number of registered deposit tokens in the pool (up to 30 per `addDepositToken` cap [7](#0-6) ) minus tokens the victim already holds; on deployments with many listed collaterals, any account can be fully locked out of new positions.
- Front-running makes the "blocked rescue deposit → liquidation" scenario realistic for positions near the health boundary.

### Recommendation
- Do not add tokens to a recipient's list on plain transfers; only register on protocol-level actions (`deposit`/`_mint`), or require the recipient to have opted in.
- Alternatively, keep the accounting list but do not let list membership gate *receiving*: move the `UserReachedMaxTokens` check to the initiator's action (deposit/issue) rather than `addToDepositTokensOfAccount`, so inbound dust cannot block a user.
- A simpler mitigation is a minimum meaningful transfer/deposit amount, though the clean fix is decoupling list registration from unsolicited transfers.

### Proof of Concept
Hardhat test sketch (against the existing test harness in `test/Pool.test.ts`, real `DepositToken`/`Pool` deployment, not mocks for the token contracts):

```ts
// setup: pool with N registered deposit tokens dt_0..dt_{k-1}, k == MAX_TOKENS_PER_USER
const max = await pool.MAX_TOKENS_PER_USER() // 30

// attacker deposits dust and sends 1 wei of each deposit token to victim
for (const dt of depositTokens) {
  await underlying.connect(attacker).approve(dt.address, MaxUint256)
  await dt.connect(attacker).deposit(1, attacker.address)
  await dt.connect(attacker).transfer(victim.address, 1)
}

expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(max)

// victim can no longer deposit a new collateral type
await newUnderlying.connect(victim).approve(newDepositToken.address, MaxUint256)
await expect(
  newDepositToken.connect(victim).deposit(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// victim can no longer issue a synth whose DebtToken they don't hold
await expect(
  newDebtToken.connect(victim).issue(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Fork-reproduction notes: on a live deployment, iterate `pool.getDepositTokens()` and repeat the deposit+transfer loop until `getDepositTokensOfAccount(victim).length == 30`; then any `deposit()` into a collateral the victim does not already hold reverts. Caveat: where the victim already holds several tokens, the attacker may only partially fill the list — the attack fully blocks new positions only when `registeredTokens >= 30 - (victim's existing entries)`; it reliably blocks victims whose lists are already near the cap, and partially reduces headroom otherwise.
