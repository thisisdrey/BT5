### Title
Multi-signature threshold bypass via ECDSA signature malleability in `ValidateMultiSign` TVM precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE describes a server that mishandles possession of superfluous/duplicate authentication credentials, effectively letting one credential be counted as if it were multiple independent authorizations. The java-tron analog is in the TVM precompiled contract `ValidateMultiSign`, which underlies Solidity-level `validatemultisign` used by multi-sig smart-contract wallets. Its per-signature de-duplication check only rejects an *exact* duplicate `(recoveredAddress, rawSignatureBytes)` pair, not a duplicate *signer address*. Because ECDSA signatures are malleable (a signature `(r, s, v)` has a second valid form `(r, n-s, 1-v)` that recovers to the same address), a holder of a single private key can submit two distinct-looking but cryptographically equivalent signatures and have their weight counted twice toward the permission threshold.

### Finding Description
`ValidateMultiSign.execute` loops over all provided signatures, recovers each signer address, and tracks already-seen `(address, signature)` pairs: [1](#0-0) 

The de-dup guard is:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
```
This only skips a signature when the *exact same signature bytes* for that address have been seen before. If the same address is recovered again but with a different, malleable variant of the signature, the code does **not** `continue` — it falls through and adds `weight` to `totalWeight` again: [2](#0-1) 

Compare this to the analogous on-chain check `TransactionCapsule.checkWeight`, which de-duplicates strictly by **address** (post fork `VERSION_4_7_1`) rather than by raw signature bytes, precisely to avoid this malleability class of double counting: [3](#0-2) 

The precompile lacks this address-based de-duplication, so an attacker who controls only one authorized key (with weight below the permission threshold) can derive a second, still-valid signature for the same message via ECDSA malleability and submit both. `getWeight` will return the same non-zero weight both times, and `totalWeight` will reach `permission.getThreshold()` using only one real private key: [4](#0-3) 

The precompile is invoked directly from any TVM contract via `TriggerSmartContract`, i.e. reachable by any unprivileged contract caller, with no special privilege required — it is a pure computational precompile bound to a fixed address in `PrecompiledContracts`.

### Impact Explanation
Smart contracts implementing multi-signature wallets or governance on TRON via the `validatemultisign` builtin rely on this precompile to enforce that a threshold of *distinct* authorized keys approved an action. This bug allows an attacker holding a single authorized key (with insufficient weight alone) to forge a second "signer" credential from the same key and satisfy the threshold, bypassing the multi-sig authorization model. This can lead to unauthorized transfers/withdrawals from funds gated by such contracts — a concrete unauthorized-account-operation/theft-of-funds impact.

### Likelihood Explanation
Exploitation only requires: (1) deploying or interacting with any contract that uses `validatemultisign` (or being a party with any single authorized key of a targeted multi-sig contract account), and (2) computing the standard ECDSA malleable counterpart of one's own valid signature — a trivial, well-known operation (negate `s` mod curve order, flip recovery id). No special network position or additional secrets are needed, making this highly likely to be exploitable wherever the precompile is used to gate value-moving operations.

### Recommendation
Change the de-duplication logic in `ValidateMultiSign.execute` (and the structurally similar `BatchValidateSign`, if it has comparable per-address weight accounting) to track and reject **already-seen recovered addresses**, not raw signature bytes — mirroring the address-keyed dedup already used in `TransactionCapsule.checkWeight`. Additionally, normalize/canonicalize `s` (low-s enforcement) before signature verification to eliminate one class of malleability outright.

### Proof of Concept
1. Deploy (or target) an account with an `Active` permission requiring threshold `T`, where key `K1` alone has weight `< T`.
2. Sign the message hash with `K1` to get signature `sig1 = (r, s, v)`.
3. Compute the malleable counterpart `sig2 = (r, n-s, 1-v)` (still a valid ECDSA signature recoverable to `K1`'s address).
4. Call the `ValidateMultiSign` precompile (via a TVM contract or directly encoding calldata) with `signatures = [sig1, sig2]`.
5. Observe `totalWeight = weight(K1) + weight(K1) >= T`, so the precompile returns `dataOne()` (success) even though only one real key participated, as shown by the loop logic at `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1088-1110`.
