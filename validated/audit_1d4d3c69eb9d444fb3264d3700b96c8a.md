### Title
`debtFloorInUsd` / `maxLiquidable` interaction makes a band of unhealthy positions impossible to liquidate, permanently locking collateral and bad debt - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` applies two independent checks to the repaid amount: it must be `<= maxLiquidable` fraction of the account's debt, and the *remaining* debt must be either zero or `>= debtFloorInUsd`. For any account whose debt (in USD) falls in the interval `(debtFloorInUsd, debtFloorInUsd / maxLiquidable)`, every possible liquidation amount reverts: a full repayment exceeds `maxLiquidable`, and any partial repayment leaves a remainder below the floor. This is the same bug class as the external report — a "remainder must be >= minimum" check that blocks a legitimate operation and locks funds in place.

### Finding Description
In `Pool.liquidate`:

```solidity
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}

if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_),
        _debtTokenBalance - amountToRepay_
    );
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
``` [1](#0-0) 

Let `D` = account's debt in USD and `m` = `maxLiquidable` (e.g. 0.5e18). The first check allows `amountToRepay <= m·D`. The second allows only `remaining == 0` or `remaining >= debtFloorInUsd`, i.e. `amountToRepay >= D - floor` or `amountToRepay == D`.

- If `D <= floor` the position can still be fully liquidated only if `D <= m·D` fails — actually `D <= floor` means full repay is the only option, and it is blocked whenever `m < 1`. Positions with `D < floor` are entirely unliquidatable when `maxLiquidable < 1e18`.
- More generally, when `floor < D <= floor / m`, partial liquidation is capped at `m·D` which leaves `D - m·D < floor` (revert), and full liquidation `D > m·D` (revert). Dead zone.

Example with deployed-style parameters `maxLiquidable = 50%`, `debtFloorInUsd = $3,000`: an account with `$4,000` debt → max allowed repay is `$2,000`, leaving `$2,000 < $3,000` → `RemainingDebtIsLowerThanTheFloor`; repaying all `$4,000` → `AmountGreaterThanMaxLiquidable`. No liquidator can touch the position. The same floor check exists in `DebtToken.repay` (lines 442–451), but the borrower retains `repayAll` as an escape; the liquidator has no equivalent — `liquidate` is the only path to clear third-party bad debt.

`PoolMock`-based unit tests confirm both reverts independently (`test/Pool.test.ts` lines 408–450) but never test their intersection.

### Impact Explanation
Positions inside the dead zone cannot be liquidated at all. If such a position becomes undercollateralized, its bad debt is permanently locked in the protocol — liquidators are forced to watch losses accrue while seized collateral would not cover the debt anyway. The account's collateral is likewise frozen against the unpayable-by-liquidator debt (only the borrower self-repaying via `repay`/`repayAll` can clear it). An attacker can deliberately engineer this: deposit collateral, issue debt sized into the dead zone, then wait for/advance a price move making the position unhealthy — guaranteed unliquidatable bad debt, i.e., protocol insolvency risk with frozen funds. This matches the report's "borrower locks funds via a minimum-amount check" pattern.

### Likelihood Explanation
Requires `debtFloorInUsd > 0` and `maxLiquidable < 1e18`. Both are governor-set parameters (`updateDebtFloor`, `updateMaxLiquidable` in `Pool.sol`) and the NatSpec/dev docs indicate the floor exists specifically to keep liquidations profitable, so a nonzero floor is the intended production configuration; `maxLiquidable < 100%` is standard for this codebase's tests. I could not confirm the exact on-chain values from the indexed deployment artifacts (they contain ABIs, not storage state), so likelihood is conditional on configuration — but the flaw is in code logic, not a parameter mistake: even with sane values the dead zone always exists whenever `floor > 0` and `m < 1`.

### Recommendation
In `Pool.liquidate`, bypass `maxLiquidable` when the repayment would bring the remaining debt to zero or to `>= debtFloorInUsd` — e.g., compute the minimum amount that satisfies the floor (`D - floor` in token terms) and the full-repay amount, and allow the liquidator to repay `min(maxLiquidableAmount, neededToReachFloor)` rounded up to the floor-clearing amount, or simply skip the `maxLiquidable` check when `amountToRepay_ == _debtTokenBalance`. Apply the same "sweep to zero or above floor" relaxation to `DebtToken.repay` so partial repayments can always land exactly on the boundary.

### Proof of Concept
Reproducible in the existing Hardhat setup (`test/Pool.test.ts` liquidate suite):

```ts
// given: pool.updateDebtFloor(toUSD('3,000')); pool.updateMaxLiquidable(parseEther('0.5'));
// alice has 1 msETH debt ($4,000) and is unhealthy
const debt = await msEthDebtToken.balanceOf(alice.address); // 1 msETH = $4,000

// partial repay of 50% -> leaves $2,000 < floor
await expect(
  pool.connect(liquidator).liquidate(msEth.address, alice.address, debt.div(2), msdMET.address)
).revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');

// full repay -> exceeds maxLiquidable
await expect(
  pool.connect(liquidator).liquidate(msEth.address, alice.address, debt, msdMET.address)
).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

// any amount in between hits one of the two reverts -> position is unliquidatable
```

Assert that `debtPositionOf(alice)._isHealthy` is false and remains so, and that no `amountToRepay` value in `(0, debt]` succeeds.
