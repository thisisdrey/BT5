### Title
Dust-transfer griefing fills victim's token list to `MAX_TOKENS_PER_USER`, DoS-ing deposits and inbound transfers/seizes of new collateral - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces a per-account cap of 30 combined debt+deposit token entries via `onlyIfAdditionWillNotReachMaxTokens` in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` (Pool.sol:143-148, 204-220). `DepositToken._transfer` and `_mint` unconditionally call `pool.addToDepositTokensOfAccount(recipient)` whenever the recipient's balance goes from 0 to >0 (DepositToken.sol:486-489, 517-520). Because `DepositToken.transfer`/`transferFrom` are permissionless and any holder can send dust to an arbitrary `to_`, an unprivileged attacker can stuff a victim's `depositTokensOfAccount` set with 1-wei amounts of every listed deposit token until the combined count hits 30. After that, every path that would add a *new* token type to the victim reverts with `UserReachedMaxTokens`: `deposit(amount_, onBehalfOf_=victim)`, `transfer`/`transferFrom` to the victim, `seize` proceeds directed at the victim (e.g., a dedicated liquidator contract or SmartFarmingManager position account), and any `DebtToken.issue` for a synthetic the victim doesn't already hold.

### Finding Description
- `DepositToken.transfer(to_, amount_)` → `_transfer` → `pool.addToDepositTokensOfAccount(to_)` when `balanceOf[to_] == 0 && amount_ > 0` (DepositToken.sol:348-354, 517-520).
- `addToDepositTokensOfAccount` reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30` (Pool.sol:143-148, 216-220).
- Attack cost: deposit dust (`deposit(1 wei, attacker)` per listed deposit token, then `transfer(victim, 1)`), or even simpler `deposit` reverts are avoided since transfer only needs unlocked balance, which dust always has.
- Once filled: `DepositToken.deposit(amount_, onBehalfOf_=victim)` → `_mint` → `addToDepositTokensOfAccount` reverts for any token the victim doesn't already hold; the same holds for `seize`/`_mint` in `Pool.liquidate` when the victim is the recipient, and for new `DebtToken` issuance to the victim.

### Impact Explanation
Availability impact analogous to the CVE's hang/DoS: the victim is temporarily unable to (a) receive any new collateral type, including third-party `deposit(onBehalfOf_)` top-ups intended to cure an unhealthy position, (b) open debt in any new synthetic, and (c) act as a liquidation/fee recipient for tokens not already in their set. A position that could only be saved by adding a *different* collateral asset can be forced into liquidation. The freeze is temporary — the victim can self-unbrick by transferring dust balances back out to shrink the set — matching the "temporary freezing of funds" acceptance bar.

### Likelihood Explanation
- Fully unprivileged: needs only public `transfer`/`deposit` calls and dust capital; no governor/oracle/keeper involvement.
- Main limitation: only ~30 deposit tokens can ever exist (`addDepositToken` caps at `MAX_TOKENS_PER_USER`, Pool.sol:703), so filling exactly 30 requires the pool to list enough tokens and the victim to hold few types; on current deployments with fewer than 30 collaterals the cap may be unreachable via deposit tokens alone (debt tokens cannot be pushed to a victim — `issue` adds to the caller's own list). This bounds the attack to pools with enough listed collaterals and victims whose combined count is near the cap.

### Recommendation
Do not count attacker-pushable entries against the cap — e.g., drop the `onlyIfAdditionWillNotReachMaxTokens` revert in `addToDepositTokensOfAccount` (or only enforce the cap on user-initiated additions like `deposit`/`issue` where the account is the caller), or whitelist-free-list bookkeeping so transfers to third parties cannot consume a victim's slots.

### Proof of Concept
Fork test (Hardhat) sketch:
```ts
// victim starts with 0 deposit tokens
for (const dt of allDepositTokens /* up to 30 listed */) {
  await underlying.connect(attacker).mint(attacker.address, 1);
  await underlying.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1, attacker.address);   // attacker holds dust
  await dt.connect(attacker).transfer(victim.address, 1);    // fills victim's list
}
// victim's combined token count == MAX_TOKENS_PER_USER
// Any new-token deposit to victim now reverts:
await underlying.mint(savior.address, parseUnits("100", 18));
await underlying.connect(savior).approve(newDepositToken.address, MAX);
await expect(
  newDepositToken.connect(savior).deposit(parseUnits("100", 18), victim.address)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
// Same revert hits DebtToken.issue for a synthetic the victim doesn't hold.
```
Validated code path: `DepositToken.transfer` → `_transfer` (DepositToken.sol:498-525) → `Pool.addToDepositTokensOfAccount` → `onlyIfAdditionWillNotReachMaxTokens` revert (Pool.sol:143-148).

Caveat: I verified this path directly in `Pool.sol`/`DepositToken.sol`; whether enough deposit tokens are listed on a given deployment to reach 30 (given debt tokens share the same counter) is the main open variable for a specific fork PoC.
