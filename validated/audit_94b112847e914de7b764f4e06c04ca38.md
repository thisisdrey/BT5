### Title
Naming-pattern-only pool identity check lets an attacker-controlled repository bypass pool-safety pruning and dangling-repository cleanup - (File: internal/gitaly/storage/repository_path.go)

### Summary
The Sudoswap finding is about a "trust" decision (is this contract a legitimate clone?) that is made by checking only a partial signature (54 bytes of proxy bytecode) instead of validating the full set of identity-relevant parameters, allowing an attacker-fabricated object to be accepted as authentic and used to unlock privileged behavior. The closest analog in Gitaly is `storage.IsPoolRepository` / `IsRailsPoolRepository` / `IsPraefectPoolRepository`, which decide whether a repository is treated as a trusted "object pool" purely by pattern-matching its `RelativePath` string, not by verifying that the directory is actually a pool that other repositories are alternated to.

### Finding Description
`IsRailsPoolRepository` and `IsPraefectPoolRepository` classify a repository as a pool solely from its `RelativePath` shape: [1](#0-0) 

This "is it a pool" check is then relied upon in multiple security-relevant contexts as if it were a real identity/ownership verification:

- `HeuristicalOptimizationStrategy.ShouldPruneObjects` disables pruning entirely for anything the naming check considers a pool, "to not lose data" / avoid corrupting pool members: [2](#0-1) 

- `PruneUnreachableObjects` RPC explicitly refuses to prune any repository for which `RepositoryInfoForRepository` (which sets `IsObjectPool` from `storage.IsPoolRepository`) reports `IsObjectPool == true`: [3](#0-2) [4](#0-3) 

- `gitalybackup restore` skips deletion of "dangling" repositories (repos present on disk but not part of the restore set) if they satisfy the same naming check: [5](#0-4) 

- The storage manager middleware also branches special-case handling of `DeleteObjectPool` based purely on this naming check: [6](#0-5) 

Because the check is purely syntactic (regex on `RelativePath`), any ordinary caller who can choose or influence a repository's relative path (e.g. via repository creation, fork, import from URL/bundle/snapshot, or replication, all of which are reachable via ordinary RPCs) could shape the path to satisfy the pool-path regex even though the repository is not an actual object pool linked as an alternate to any member. `IsRailsPoolRepository` requires that the two leading hex path components equal the first four hex digits of a 64-hex-char final path segment — a matchable, attacker-computable constraint, not a value derived from or checked against the repository's real relationship to other repos. `IsPraefectPoolRepository` is similarly just a positional-numeric regex on the path (`@cluster/pools/xx/xx/<id>`).

This mirrors the Sudoswap bug's root cause: a downstream, security-relevant decision ("is this a trusted pool", "should we treat objects specially/exempt from cleanup") is derived from a partial/pattern check of an identifier rather than a verification of the full trust relationship (i.e., that the directory is actually referenced as an alternate object store by other repositories, as `ObjectPool.FromProto`'s `pool.IsValid(ctx)` call additionally attempts to verify).

### Impact Explanation
An attacker-influenced repository whose relative path is crafted to match the pool-path regex would be exempted from `ShouldPruneObjects`/`PruneUnreachableObjects`, permanently accumulating stale/unreachable loose and cruft objects that can never be pruned — a storage-based denial-of-service vector. It would also be silently excluded from the dangling-repository cleanup performed during `gitalybackup restore`, letting an attacker plant a repository directory that persists indefinitely outside of Rails' bookkeeping even though the restore's contract is to prune anything not part of the backup set. Both are argument/config-driven bypasses of storage cleanup and resource-limit safeguards reachable through ordinary repository-creation/import/backup-restore paths, without needing token compromise, MITM, or a malicious peer — consistent with the report's DoS/handler-resource-limit category.

### Likelihood Explanation
Reaching this requires only that an ordinary, unprivileged actor be able to influence a repository's `RelativePath` to satisfy the regex constraints in `railsPoolDirRegexp`/`praefectPoolDirRegexp`. In the normal Gitaly/Rails flow, relative paths for repositories are derived server-side (hashed project paths, or `DeriveReplicaPath`/`DerivePoolPath` for Praefect-managed repos), which likely limits direct attacker control in the fully-managed GitLab deployment. However, Gitaly itself does not perform any additional verification when checks like `ShouldPruneObjects`, `PruneUnreachableObjects`, or `restore`'s dangling-repo removal consult `IsPoolRepository` — there is no independent confirmation that the path actually functions as a pool (i.e., is aliased into via `objects/info/alternates` by other repositories), unlike `ObjectPool.FromProto`/`FromRepo` which do call `pool.IsValid` for pool-specific RPCs. This makes the likelihood **moderate-to-low without a demonstrated path-injection primitive**, and I could not confirm within this codebase whether any RPC allows a caller to set an arbitrary `RelativePath` matching the pool regex (the `CreateRepositoryFromURL`/`CreateRepositoryFromBundle`/`ReplicateRepository`/`CreateRepositoryFromSnapshot` request paths were not fully traced for validation of `RelativePath` against this specific regex).

### Recommendation
Do not rely on `RelativePath` pattern-matching alone to grant pool-exemption from pruning/cleanup safeguards. Where these decisions gate destructive-vs-safe operations (`ShouldPruneObjects`, `PruneUnreachableObjects`, restore's dangling-repository removal, and the `DeleteObjectPool`/middleware special case), corroborate the naming check with an actual structural verification — e.g., requiring the path to also pass `ObjectPool.IsValid`/`ValidateGitDirectory`-style checks, or verifying that at least one other repository in the storage actually references it via `objects/info/alternates` — before treating a repository as an exempt/trusted pool. At minimum, restrict which RPCs are allowed to set a `RelativePath` that satisfies the pool-path regexes so the invariant "path matches pool regex ⇒ is actually a pool" is enforced at write time rather than assumed at read time.

### Proof of Concept
Not independently reproducible from the indexed codebase alone: doing so would require confirming a concrete RPC/import path where a caller can set `RelativePath` to a value matching `railsPoolDirRegexp` (`@pools/<aa>/<bb>/<64-hex-starting-with-aabb>.git`) or `praefectPoolDirRegexp` (`@cluster/pools/<aa>/<bb>/<numeric-id>`), then invoking `PruneUnreachableObjects` on it and observing that pruning is skipped (`structerr.NewInvalidArgument("pruning objects for object pool")`) despite the repository never having been linked as a real object pool. This RPC path/validation gap was not fully confirmed within the available index, so this should be validated with a live Devin session having full repository access before treating it as a confirmed exploit.

// IsRailsPoolRepository returns whether the repository is a pool repository generated by Rails.
func IsRailsPoolRepository(repo Repository) bool {
	matches := railsPoolDirRegexp.FindStringSubmatch(repo.GetRelativePath())
	if matches == nil || !strings.HasPrefix(matches[3], matches[1]+matches[2]) {
		return false
	}

	return true
}

// IsPraefectPoolRepository returns whether the repository is a Praefect generated object pool repository.
func IsPraefectPoolRepository(repo Repository) bool {
	return praefectPoolDirRegexp.MatchString(repo.GetRelativePath())
}

// IsPoolRepository returns whether the repository is an object pool.
func IsPoolRepository(repo Repository) bool {
	return IsRailsPoolRepository(repo) || IsPraefectPoolRepository(repo)
}

// ShouldPruneObjects determines whether the repository has stale objects that should be pruned.
// Object pools are never pruned to not lose data in them, but otherwise we prune when we've found
// enough stale objects that might in fact get pruned.
func (s HeuristicalOptimizationStrategy) ShouldPruneObjects(context.Context) (bool, PruneObjectsConfig) {
	// Pool repositories must never prune any objects, or otherwise we may corrupt members of
	// that pool if they still refer to that object.
	if s.info.IsObjectPool {
		return false, PruneObjectsConfig{}
	}

	// When we have a number of loose objects that is older than two weeks then they have
	// surpassed the grace period and may thus be pruned.
	if s.info.LooseObjects.StaleCount <= LooseObjectLimit {
		return false, PruneObjectsConfig{}
	}

	return true, PruneObjectsConfig{
		ExpireBefore: s.expireBefore,
	}
}
