### Title
Bridged-in supply cap can be saturated to freeze victims' in-flight `sendFrom` transfers on the destination chain - ([File: contracts/SyntheticToken.sol](contracts/SyntheticToken.sol))

### Summary
Cross-chain transfers via `ProxyOFT.sendFrom` burn the synthetic token on the source chain and mint it on the destination chain. The destination mint in `SyntheticToken._mint` reverts with `SurpassMaxBridgingSupply` whenever `bridgedInSupply() > maxBridgedInSupply`. An unprivileged attacker can deliberately saturate the bridged-in cap by bridging their own tokens into the destination chain, causing victims' in-flight messages to fail and be stored as `failedMessages`. Since `retryMessage` reverts while the cap remains saturated, the victim's tokens are burned on the source chain and frozen on the destination chain until the cap is raised or enough supply bridges back out — mirroring the Holograph "job can't execute until external condition changes" freeze.

### Finding Description
- `ProxyOFT.sendFrom` → `_send` → `_debitFrom` calls `syntheticToken.burn(from_, amount_)`, which also enforces `maxBridgedOutSupply` on the source. [1](#0-0) 
- On the destination chain, `NonblockingLzAppUpgradeable._blockingLzReceive` wraps `_nonblockingLzReceive` in `excessivelySafeCall`; any revert stores `failedMessages[srcChainId][srcAddress][nonce] = keccak256(payload)`. [2](#0-1) 
- `_sendAck` → `ProxyOFT._creditTo` → `syntheticToken.mint` → `_mint`, which reverts `SurpassMaxBridgingSupply` when `bridgedInSupply() > maxBridgedInSupply` and `SurpassMaxSynthSupply` when `totalSupply > maxTotalSupply`. [3](#0-2) 
- Recovery is only via `retryMessage`, which deletes the stored hash and re-executes `_nonblockingLzReceive`; it reverts again if the mint still fails. [4](#0-3) 
- `bridgedInSupply()` is `MAX(totalBridgedIn - totalBridgedOut, 0)`, so an attacker holding/buying msSynth on the source can `sendFrom` a large amount into the destination to push `bridgedInSupply` to `maxBridgedInSupply`. Every victim message already in flight then fails on receive, while `bridgedInSupply` stays pinned because the attacker's tokens remain on the destination. [5](#0-4) 

### Impact Explanation
Victim tokens are irreversibly burned on the source chain and cannot be minted on the destination while the cap is saturated — temporary freezing of user funds (potentially indefinite if the attacker keeps the cap saturated or `isActive` is toggled off). Unlike Holograph there is a public retry path, but retries revert under the pinned-cap condition, so funds are stranded until external state changes.

### Likelihood Explanation
Requires the attacker to control enough of the synthetic token to fill `maxBridgedInSupply` and pay LZ fees — capital cost, no protocol profit, pure griefing. A more likely non-adversarial trigger: normal bridging volume legitimately reaching the cap, at which point all in-flight transfers freeze until governor raises the cap or outflows occur. The same freeze applies when `isActive` is false or `totalSupply` hits `maxTotalSupply`, with no expiry/refund path back to the origin chain.

### Recommendation
- On destination-side mint failure, either store enough data to credit the user on the source chain (a refund path) or queue the amount so victims can claim once headroom exists, rather than requiring a retry that reverts under the same condition.
- Alternatively, enforce the bridged-in limit on the source side (e.g., reserve/check projected `bridgedInSupply` before burn) so messages can't arrive that the destination cannot fulfill.

### Proof of Concept
```solidity
// Destination chain, victim's sendFrom already dispatched on source:
// 1. Attacker calls ProxyOFT.sendFrom(attacker, dstChainId, attacker, X)
//    where X pushes bridgedInSupply() to == maxBridgedInSupply on dest.
// 2. Endpoint delivers victim's packet; lzReceive ->
//    _blockingLzReceive -> nonblockingLzReceive -> _sendAck ->
//    _creditTo -> syntheticToken.mint reverts SurpassMaxBridgingSupply.
// 3. excessivelySafeCall catches it; failedMessages[src][srcAddr][nonce] = hash.
// 4. Anyone calls retryMessage(src, srcAddr, nonce, payload) ->
//    mint reverts again while bridgedInSupply == cap.
// 5. Victim's tokens remain burned on source, unminted on dest,
//    until cap is raised or bridgedOut grows (bridgedInSupply shrinks).

// mock endpoint deliver two packets; first (attacker, size N) succeeds,
// second (victim) emits MessageFailed; assert retryMessage reverts with
// SurpassMaxBridgingSupply while bridgedInSupply() == N.

    function _blockingLzReceive(uint16 _srcChainId, bytes memory _srcAddress, uint64 _nonce, bytes memory _payload) internal virtual override {
        (bool success, bytes memory reason) = address(this).excessivelySafeCall(gasleft(), 150, abi.encodeWithSelector(this.nonblockingLzReceive.selector, _srcChainId, _srcAddress, _nonce, _payload));

    function retryMessage(uint16 _srcChainId, bytes calldata _srcAddress, uint64 _nonce, bytes calldata _payload) public payable virtual {
        // assert there is message to retry
        bytes32 payloadHash = failedMessages[_srcChainId][_srcAddress][_nonce];
        require(payloadHash != bytes32(0), "NonblockingLzApp: no stored message");
        require(keccak256(_payload) == payloadHash, "NonblockingLzApp: invalid payload");
        // clear the stored message
        failedMessages[_srcChainId][_srcAddress][_nonce] = bytes32(0);
        // execute the message. revert if it fails again
        _nonblockingLzReceive(_srcChainId, _srcAddress, _nonce, _payload);
        emit RetryMessageSuccess(_srcChainId, _srcAddress, _nonce, payloadHash);
    }
```
