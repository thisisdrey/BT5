Confirmed: `validate_bank_state` in `programs/marginfi/src/utils/general.rs` unconditionally errors with `MarginfiError::BankKilledByBankruptcy` on `BankOperationalState::KilledByBankruptcy`, before the `InstructionKind` match — meaning this check applies to *every* instruction kind, admin or not, deposit/withdraw/borrow/repay/liquidate alike.

### Title
Permanent, admin-unrecoverable lock of depositor funds via `BankOperationalState::KilledByBankruptcy` - (File: `programs/marginfi/src/utils/general.rs`)

### Summary
`lending_pool_handle_bankruptcy` can permanently kill an entire bank (`BankOperationalState::KilledByBankruptcy`) when socialized bad debt exceeds total remaining assets. Once killed, `validate_bank_state` unconditionally rejects every operation on that bank — deposit, withdraw, borrow, repay, and liquidation — for every account, including calls made by the group admin. There is no instruction anywhere in the program that can move a bank out of `KilledByBankruptcy` back to `Operational`/`ReduceOnly`, so any *other*, unrelated, solvent depositor who still has a legitimate balance in that bank has their funds permanently frozen with no path to recovery — mirroring the CashManager analog where KYC checks locked funds even from the trusted admin.

### Finding Description
In `programs/marginfi/src/instructions/marginfi_group/handle_bankruptcy.rs::lending_pool_handle_bankruptcy`, after socializing bad debt, the code checks the return of `bank.socialize_loss(socialized_loss)`: [1](#0-0) 
if `kill_bank` is true (bad debt exceeded liabilities/assets available in the bank), `bank.config.operational_state` is set to `KilledByBankruptcy` — a state that per the guide is documented as "irrecoverable" and can only be set programmatically, never manually or reversed by an admin: [2](#0-1) 

The gate enforcing this state applies globally and unconditionally, ahead of any per-instruction-kind logic or admin bypass: [3](#0-2) 

Every user-facing instruction (deposit, withdraw, borrow, repay) calls `validate_bank_state` and will hard-fail with `BankKilledByBankruptcy` once the bank enters this state — with no carve-out for the admin, unlike the `ACCOUNT_FROZEN` flag mechanism (which explicitly allows `group.admin` to keep operating a frozen account, see `account_not_frozen_for_authority`/`is_signer_authorized` used in `LendingAccountWithdraw`): [4](#0-3) 

No `lending_pool_configure_bank` or any other admin instruction can transition `KilledByBankruptcy` back to a workable state, and the documentation explicitly confirms this is a dead end: [5](#0-4) 

The only mainnet-gated recovery mechanism (`super_admin_deposit`/`super_admin_withdraw`) is compiled but `panic!`s if invoked on mainnet, and is intended for a completely different purpose (crediting recovered off-chain funds), not for un-bricking a `KilledByBankruptcy` bank's `operational_state`: [6](#0-5) 

### Impact Explanation
Any solvent depositor with an active, healthy balance in a bank that later gets a *different* bankrupt account push it into `KilledByBankruptcy` state loses all ability to withdraw their own funds, permanently. This is a direct, protocol-level permanent lock/freeze of unprivileged-user funds in the core accounting/bankruptcy path, with zero admin remediation path on-chain — the same class of harm as the CashManager report (funds locked even from a trusted admin), except here it can affect an entire bank's worth of unrelated depositors rather than a single sanctioned user.

### Likelihood Explanation
This requires bad debt from one bankrupt account to exceed the bank's total remaining liabilities/assets (an extreme, but reachable, real-world scenario during a severe price crash or oracle failure combined with insufficient insurance fund coverage) — it is a documented, intentional design outcome of `handle_bankruptcy`, not a theoretical edge case; `kill_bank`/`socialize_loss` is core, always-reachable logic invoked by permissionless or admin bankruptcy settlement calls.

### Recommendation
Add an explicit, admin-only (or `risk_admin`-only) escape hatch instruction that allows moving a bank out of `KilledByBankruptcy` at least far enough to let existing solvent depositors withdraw their remaining balances (e.g., permit `withdraw`/`repay` to bypass the `KilledByBankruptcy` check when invoked by the admin/risk_admin, analogous to how `ACCOUNT_FROZEN` already exempts the admin), or provide a dedicated instruction to sweep/redistribute a killed bank's remaining vault balance back to depositors pro-rata.

### Proof of Concept
1. Bank B has depositor A (healthy, solvent) and borrower C (undercollateralized).
2. Borrower C's collateral collapses in value; `handle_bankruptcy` is called on C, and the bad debt exceeds Bank B's total remaining assets/liabilities, so `bank.socialize_loss` returns `kill_bank = true`, setting `bank.config.operational_state = BankOperationalState::KilledByBankruptcy` (`handle_bankruptcy.rs:208-211`).
3. Depositor A calls `lending_account_withdraw` to retrieve their unrelated, still-solvent funds. `validate_bank_state` is invoked and immediately returns `MarginfiError::BankKilledByBankruptcy` regardless of caller (`utils/general.rs:266-269`), since the check occurs before any per-`InstructionKind` or authority-based branching.
4. The group admin attempts the same operation on behalf of depositor A (e.g., emergency withdraw via admin authority) — this also fails identically because `validate_bank_state` has no admin-authority bypass condition.
5. No configuration instruction exists to revert `operational_state` away from `KilledByBankruptcy` (confirmed absent in `configure_bank` and admin instruction set per `guides/ADMIN/BANK_STATE.md:60-75`), so depositor A's funds remain permanently locked in the bank's liquidity vault.

### Emergency-only instructions (mainnet-disabled)

Two instructions are compiled into the program but guarded to `panic!` if invoked on the mainnet
deployment, following the same pattern as `lending_pool_clone_bank`:

- `super_admin_deposit` — transfers tokens from the admin's account into a bank's liquidity
  vault and raises `asset_share_value`, crediting the gain proportionally to existing depositors.
  Intended for crediting recovered funds back to affected depositors after an incident.
- `super_admin_withdraw` — the inverse: pulls tokens from a bank's liquidity vault (to a
  hard-coded recovery wallet on live networks) and lowers `asset_share_value`. Additionally
  refuses to run if the resulting share value would drop to ≤ `0.8`, as a safety rail.

They live in source, not on a separate branch, so that they keep compiling against current types
in CI and remain ready to enable via a targeted deployment if a future incident genuinely
requires them. On mainnet they are inert. On staging/localnet they are available for reproducing
specific bank states during testing.
