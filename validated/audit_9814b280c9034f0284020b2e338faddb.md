### Title
Unsolicited dust deposits / transfers let an attacker fill a victim's `MAX_TOKENS_PER_USER` slot list and DoS collateral top-ups and debt issuance - (File: `contracts/Pool.sol`)

### Summary
`Pool` tracks every deposit token and debt token an account touches in per-account enumerable sets (`depositTokensOfAccount`, `debtTokensOfAccount`) capped at `MAX_TOKENS_PER_USER = 30` ( [1](#0-0) [2](#0-1) ). Entries are added whenever an account's balance of a token goes 0 → >0 — via `DepositToken._transfer`, `DepositToken._mint` and `DebtToken._mint` ( [3](#0-2) [4](#0-3) [5](#0-4) ). Crucially, `DepositToken.deposit(amount_, onBehalfOf_)` lets anyone mint deposit-token balances to an arbitrary beneficiary ( [6](#0-5) ), and `DepositToken.transfer` is unrestricted for unlocked balances ( [7](#0-6) ). An attacker can therefore push dust balances of every listed collateral into a victim's account until the combined set length hits 30, after which `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` ( [8](#0-7) ).

### Finding Description
This is the availability/DoS analog of CVE-2024-21162 (easily-triggered denial of service): a permissionless code path deterministically reverts once an attacker-controlled precondition is met. Once the victim's slot list is full:

- `DepositToken.deposit(x, victim)` reverts for any collateral token the victim does not already hold, because `_mint` → `addToDepositTokensOfAccount` hits `onlyIfAdditionWillNotReachMaxTokens`.
- `DebtToken.issue` reverts for any synthetic the victim has not yet borrowed, because `_mint` → `addToDebtTokensOfAccount` reverts ( [9](#0-8) ).
- `SmartFarmingManager` leverage paths that mint a new debt token for the victim fail the same way.
- `Pool.liquidate` calls `DepositToken.seize` → `_transfer` to the liquidator; if the liquidator's own list is full the liquidation of that collateral reverts, though a liquidator can self-mitigate ( [10](#0-9) ).

The victim's existing balances still withdraw (burns remove entries, never add), so the precise impact is: the victim cannot open new collateral/debt positions and cannot add a *new* collateral type to rescue an unhealthy position — a temporary freezing of protocol functionality and, for a position that is under-collateralized in one asset but could be saved with another, forced liquidation.

### Impact Explanation
Temporary freezing of funds / griefing: the victim's ability to deposit new collateral types and to issue debt is completely blocked until they manually empty one of the dusted token balances (transfer it out so `removeFromDepositTokensOfAccount` runs). Where the victim is near the liquidation threshold, blocking `deposit` of a fresh collateral type can convert the DoS into an avoidable liquidation loss. The attacker only pays dust amounts of underlying collateral plus gas.

### Likelihood Explanation
Reachable by any EOA through public entry points (`deposit(onBehalfOf_)`, `transfer`) with no privileged role, oracle manipulation, or governance action. The main constraint is feasibility of reaching 30 entries: only deposit tokens can be pushed (debt tokens are non-transferable and `issue` mints to the caller), so the attack requires the pool to list enough distinct deposit tokens to cover `30 − (victim's current entries)`. The repo's mainnet deployment shows ~12+ deposit tokens for `Pool1` (DAI, FRAX, USDC, WETH, WBTC, sfrxETH, VaETH/VaUSDC/VaFRAX/VaRETH/VaSTETH/VaCBETH, etc.); whether any live pool reaches 30 pushable tokens could not be fully confirmed from the indexed deployment metadata, so likelihood is conditional on listing count and is otherwise medium-low.

### Recommendation
- Do not count attacker-pushed dust toward the cap: skip `addToDepositTokensOfAccount` for `onBehalfOf_ != payer` deposits below a minimum, or track a minimum meaningful balance.
- Alternatively, let the victim evict entries: add a public `removeDustToken(token)` that anyone can call when an account's balance is below a threshold, or auto-skip zero/near-zero balances in `debtPositionOf`/`depositOf` loops.
- Keep the cap as a gas bound for `debtPositionOf` iteration, but make membership opt-in for received transfers (only add on `deposit` where `onBehalfOf == payer`).

### Proof of Concept
Reproducible Hardhat sketch (fork or local fixture with N listed `DepositToken`s):

```typescript
// attacker dusts victim with every listed deposit token
for (const dt of depositTokens) {
  const underlying = await ethers.getContractAt('ERC20', await dt.underlying())
  await underlying.mint(attacker.address, 1n)
  await underlying.connect(attacker).approve(dt.address, 1n)
  await dt.connect(attacker).deposit(1n, victim.address) // adds dt to victim list
}
// optionally transfer unlocked dust for tokens attacker already holds
// await dt.connect(attacker).transfer(victim.address, 1n)

// victim is now at MAX_TOKENS_PER_USER -> any new token add reverts
await expect(newDepositToken.connect(victim).deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')
await expect(newDebtToken.connect(victim).issue(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

If deployed pools do not list enough distinct deposit tokens to reach 30 slots, this vector is not reachable in practice and the finding should be downgraded accordingly — that enumeration could not be fully verified against live deployments from the indexed artifacts.

        IPool _pool = pool;
        IERC20 _underlying = underlying;
        address _msgSender = _msgSender();
        address _treasury = address(_pool.treasury());

        if (_msgSender == _treasury) revert TreasuryCanNotDeposit();

        uint256 _balanceBefore = _underlying.balanceOf(_treasury);
        _underlying.safeTransferFrom(_msgSender, _treasury, amount_);
        amount_ = _underlying.balanceOf(_treasury) - _balanceBefore;

        (_deposited, _fee) = quoteDepositOut(amount_);
        if (_fee > 0) {
            _mint(_pool.feeCollector(), _fee);
        }

        _mint(onBehalfOf_, _deposited);

        emit CollateralDeposited(_msgSender, onBehalfOf_, amount_, _deposited, _fee);
    }
