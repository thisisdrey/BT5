Confirmed analog found in the java-tron order matching engine, structurally identical to the ArrakisV2 bug: an amount owed *to* a counterparty is computed with floor-rounding while the amount the transaction sender *receives* is taken from the exact, unrounded escrowed balance — so the taker underpays for what it collects.

### Title
Order matching in `MarketSellAssetActuator` rounds the maker's proceeds down, letting the taker underpay for the tokens it receives - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchSingleOrder` settles a TRC10 order match by computing `makerBuyTokenQuantityReceive` — the amount the maker is paid — via `MarketUtils.multiplyAndDivide`, which performs a floor division. In the "taker > maker" branch, the taker's escrowed sell-token debit is set to exactly this rounded-down value, while the taker unconditionally receives the maker's *full, unrounded* `getSellTokenQuantityRemain()`. The lost fraction is never charged to anyone.

### Finding Description
In `matchSingleOrder` (taker > maker branch): [1](#0-0) 

`takerBuyTokenQuantityReceive` is set to `makerOrderCapsule.getSellTokenQuantityRemain()` — the exact amount escrowed by the maker.
`makerBuyTokenQuantityReceive` is computed as `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`, i.e. `floor(makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity)`: [2](#0-1) 

The taker's own remaining sell-token balance is then debited by exactly `makerBuyTokenQuantityReceive` (the rounded-down value): [3](#0-2) 

Finally, both sides are settled: the taker is credited the full (unrounded) `takerBuyTokenQuantityReceive`, and the maker only the rounded-down `makerBuyTokenQuantityReceive`: [4](#0-3) 

This is the same root cause as the ArrakisV2 report: a proportional amount that a party "must supply" is truncated instead of rounded up, so the party benefiting from the trade (here, the taker who triggers the transaction) pays less than the exact proportional price for what it receives. The counterparty (maker, an order placer who already escrowed tokens when creating the order) receives less value than it is owed, and the shortfall (up to `makerSellQuantity - 1` units of precision, scaled) is not accounted for anywhere — it is neither returned to the maker nor charged to the taker.

### Impact Explanation
Every time a `MarketSellAssetContract` transaction (a taker order) is matched against an existing maker order where the taker's demand fully consumes the maker's remaining quantity ("taker > maker" branch), the maker is systematically underpaid by up to a rounding unit while the taker fully collects the proportionally larger, unrounded amount. This is a direct value-transfer discrepancy inside the on-chain exchange: value that belongs to the maker is effectively taken by the taker on every affected match. Because this is core DEX settlement logic reachable by any account submitting a `MarketSellAssetContract` transaction, and repeated/automated across many small-quantity orders, it enables systematic, repeatable value extraction from maker order placers — a Medium severity issue matching the pattern and rationale of the original report (protocol should always round in favor of the vault/counterparty, not the caller).

### Likelihood Explanation
The condition triggers whenever `makerSellRemainQuantity * makerBuyQuantity` is not evenly divisible by `makerSellQuantity`, which is common with arbitrary user-chosen order ratios and quantities. Any account can place a `MarketSellAssetContract` as a taker to trigger this path against resting maker orders; no special privileges are required, matching the "order placer" actor explicitly in scope.

### Recommendation
Round `makerBuyTokenQuantityReceive` (and the symmetric `takerBuyTokenQuantityReceive`/`makerBuyTokenQuantityReceive` computation in the "taker == maker" branch, which also uses `multiplyAndDivide`) using ceiling division when computing what a counterparty is owed, or otherwise ensure the amount debited from the paying side always matches, or exceeds, the amount credited to the receiving side plus any rounding remainder, so that no value is created or destroyed by truncation. Alternatively, track and settle the truncated remainder (e.g., accrue it back to the maker) instead of silently dropping it.

### Proof of Concept
Example: maker order sells 100 A for 3 TRX (`makerSellQuantity=100`, `makerBuyQuantity=3`, ratio 33.33 A per TRX). Taker order wants to buy A with more TRX than the maker's full remaining quantity requires (taker > maker branch), so `makerSellRemainQuantity = 100` (full remaining) is consumed:
- `makerBuyTokenQuantityReceive = floor(100 * 3 / 100) = 3` (exact here, so use a non-exact case)
- Use `makerSellRemainQuantity = 100`, `makerBuyQuantity = 7`, `makerSellQuantity = 100` → exact again; pick `makerSellRemainQuantity=1`, `makerBuyQuantity=100`, `makerSellQuantity=3` (i.e., maker order originally sold 3 A for 100 TRX, 1 A remains): `makerBuyTokenQuantityReceive = floor(1*100/3) = 33` TRX.
- The taker's own sell-token quantity remaining is decremented by exactly 33 TRX: `takerOrderCapsule.setSellTokenQuantityRemain(subtractExact(remain, 33))`.
- The taker receives `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain() = 1` A token (the full 1 A), for only 33 TRX paid, whereas the exact proportional price (100/3 TRX per A) for 1 A is `33.33` TRX. The maker is shortchanged `0.33` TRX-equivalent that is permanently lost from the system rather than returned to the maker or the maker's still-open capital.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
