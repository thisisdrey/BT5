### Title
Hardcoded `MAX_SIZE = 5` in `ValidateMultiSign`/`BatchValidateSign` precompiles is inconsistent with the dynamically configurable `TOTAL_SIGN_NUM` permission-key limit - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`AccountPermissionUpdateActuator` allows an account's `Permission` (owner/witness/active) to contain up to `dynamicStore.getTotalSignNum()` keys, a chain parameter stored in `DynamicPropertiesStore` (`TOTAL_SIGN_NUM`) that defaults to 5 but is a mutable, committee-adjustable dynamic parameter, not a compile-time constant. The TVM precompiles `ValidateMultiSign` and `BatchValidateSign`, which smart contracts use to verify multi-signature permissions on-chain, instead hardcode `MAX_SIZE = 5` and reject any signature array larger than 5. If `TOTAL_SIGN_NUM` is ever raised above 5 (the code enforces no upper bound tying it to the precompile's constant), accounts can legitimately create/keep permissions with 6+ keys via `AccountPermissionUpdateActuator`, but those permissions become unusable through `ValidateMultiSign`/`BatchValidateSign`, exactly mirroring the Balancer bug class: two independent hardcoded/derived "max items" limits for the same conceptual entity (signers/tokens) that can silently diverge, breaking a legitimate, unprivileged on-chain operation.

### Finding Description
- `AccountPermissionUpdateActuator.checkPermission()` bounds the number of keys in a permission only by the dynamic parameter `TOTAL_SIGN_NUM`: [1](#0-0) 
- `TOTAL_SIGN_NUM` is a persisted dynamic property (default 5) that can be changed independently of the VM code: [2](#0-1) [3](#0-2) 
- The `ValidateMultiSign` precompile (address `0x0a`), reachable from any smart contract call (i.e., from any unprivileged transaction that triggers a contract using this opcode), hardcodes `MAX_SIZE = 5` and rejects any signature set larger than that, regardless of the account's actual configured `TOTAL_SIGN_NUM`: [4](#0-3) 
- The sibling `BatchValidateSign` precompile (address `0x09`) has the same independently hardcoded `MAX_SIZE = 16` bound, unrelated to `TOTAL_SIGN_NUM`: [5](#0-4) 

This is the same bug shape as the external report: one code path (`AccountPermissionUpdateActuator`, the "creation"/configuration path) allows up to N items (keys), while a second, independently maintained code path that must operate on the same entity (`ValidateMultiSign`, the "consumption" path used by TVM contracts) enforces its own smaller, hardcoded cap. Any divergence between `TOTAL_SIGN_NUM` and the precompile's `MAX_SIZE` renders otherwise-valid permissions unusable via the precompile.

### Impact Explanation
If `TOTAL_SIGN_NUM` is raised (a legitimate, in-scope committee/chain-parameter operation, and independent of `PrecompiledContracts.java`), any account with a permission configured with more than 5 keys can no longer authorize actions through `ValidateMultiSign`, even though the account/permission itself is valid per `AccountPermissionUpdateActuator`. This breaks the multi-sig authorization flow relied upon by smart contracts and wallets (e.g., DApps implementing threshold custody), effectively locking such accounts out of TVM-mediated multi-sig verification — a denial-of-service on a specific, legitimate account operation reachable by ordinary users invoking a smart contract. It does not directly cause fund theft, but it can freeze the ability of legitimate multi-sig holders to authorize contract-mediated actions, and any protocol relying on `ValidateMultiSign` succeeding for accounts with valid permissions up to the chain's advertised `TOTAL_SIGN_NUM` limit would silently fail.

### Likelihood Explanation
`TOTAL_SIGN_NUM` is designed to be a tunable chain parameter (it is initialized on first startup and has get/set accessors), and no code path in `PrecompiledContracts.ValidateMultiSign`/`BatchValidateSign` reads or is bound to this dynamic value — the caps there are compile-time constants. The only barrier to triggering this divergence is a governance-level change (raising `TOTAL_SIGN_NUM`), which is a normal, foreseeable chain-parameter update rather than an attack; once such a change is made, the mismatch affects every account whose permission key count falls between the old and new limits, and is triggered by an ordinary, unprivileged TVM call to the `ValidateMultiSign`/`BatchValidateSign` precompiles.

### Recommendation
Tie the `MAX_SIZE` constants in `PrecompiledContracts.ValidateMultiSign` and `PrecompiledContracts.BatchValidateSign` to `DynamicPropertiesStore.getTotalSignNum()` (or the max of `TOTAL_SIGN_NUM` and `BatchValidateSign`'s intended larger multiple), instead of hardcoding `5`/`16`, so that a permission that is valid per `AccountPermissionUpdateActuator` is always processable by these precompiles. Alternatively, cap `TOTAL_SIGN_NUM` updates (via the proposal/parameter validation path) to never exceed the precompile's hardcoded `MAX_SIZE`, and add a regression test that asserts the two limits stay in sync across proposal changes.

### Proof of Concept
1. Committee submits and passes a proposal (or the parameter is otherwise updated) raising `TOTAL_SIGN_NUM` from 5 to, e.g., 8, via `DynamicPropertiesStore.saveTotalSignNum(8)`.
2. A user account calls `AccountPermissionUpdateContract` (via `AccountPermissionUpdateActuator`) to set an `Active` permission with 8 distinct keys and threshold requiring, say, 6 signatures — this passes `checkPermission()` because `8 <= dynamicStore.getTotalSignNum()` (now 8). [1](#0-0) 
3. A smart contract subsequently calls the `validatemultisign(address,uint256,bytes32,bytes[])` precompile with 6 signatures for this permission.
4. `ValidateMultiSign.execute()` immediately returns `DATA_FALSE` because `signatures.length (6) > MAX_SIZE (5)`, even though the permission and signature count are fully valid per the account's own configured limit: [6](#0-5) 
This demonstrates the account is unable to use a legitimately-configured multi-sig permission through the TVM precompile, purely due to the hardcoded constant being out of sync with the dynamic chain parameter it is supposed to mirror.
