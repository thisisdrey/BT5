### Title
Self-destructed contract storage and per-contract auxiliary state are never cleared, allowing residual data to be inherited by a contract redeployed to the same address via `CREATE2` - (File: `chainbase/src/main/java/org/tron/core/db/TransactionTrace.java`)

### Summary
When a TVM contract self-destructs, java-tron's cleanup routine only removes the contract's ABI, bytecode, account record and contract-metadata entry. It never deletes the contract's key-value storage slots (`StorageRowStore`) nor the auxiliary `ContractStateStore` entry. Since `CREATE2` lets a deployer redeploy bytecode deterministically to the exact same address after a prior instance self-destructed, the newly created contract will read leftover storage values written by the destroyed contract — the same class of bug as the reported audit finding, where removal of a module/contract leaves stale parameter data in storage that is later inherited/reused.

### Finding Description
The suicide/self-destruct path in the TVM (`Program.suicide` / `Program.suicide2` in `actuator/src/main/java/org/tron/core/vm/program/Program.java`) marks the contract address for deletion via `getResult().addDeleteAccount(...)` and `markSelfDestruct(owner)` [1](#0-0) .

After the transaction executes, `TransactionTrace.finalization()` iterates the delete-account list and calls `deleteContract(address)`: [2](#0-1) 

`deleteContract` only clears the ABI store, code store, account store and contract store: [3](#0-2) 

The same limited scope exists in `RepositoryImpl.deleteContract`, which is the `Repository` implementation used by the VM's storage abstraction: [4](#0-3) 

Neither cleanup path touches the contract's persistent key-value storage (the `Storage`/storage-row backing store obtained via `Repository.getStorage(address)` and committed through `commitStorageCache` in `RepositoryImpl`) [5](#0-4) , nor the `ContractStateStore` entry that tracks per-contract state (e.g. nonce/versioning used by `isNewContract`/`markSelfDestruct`) [6](#0-5) .

Because TVM supports `CREATE2` (deterministic address = `keccak(sender, salt, initcode)`), the same deployer can self-destruct a contract and later redeploy identical or different bytecode at the exact same address using the same salt. The new contract instance will read the old contract's un-cleared storage slots on first access (since the storage backing store still contains entries keyed by that address), exactly mirroring the reported bug class where "execution settings ... still remain in storage even when removed," permitting stale, unauthorized, or attacker-controlled state to resurface.

### Impact Explanation
A contract redeployed via `CREATE2` to a previously self-destructed address can inherit stale storage values it did not initialize — e.g., balances, allowances, ownership flags, or access-control bits set by the prior instance. Depending on how the new contract's constructor/logic assumes storage starts at zero, this can lead to unauthorized privilege (e.g. an attacker pre-seeding a storage slot that later becomes an "owner"/"admin" flag), incorrect accounting, or bypass of initialization guards — a concrete state-corruption/unauthorized-operation vector reachable by any account able to deploy contracts and trigger self-destruct, i.e. a plain, unprivileged transaction broadcaster.

### Likelihood Explanation
The precondition is fully attacker-controlled: any account can deploy a `CREATE2` contract, self-destruct it, and redeploy to the same address in a later transaction — no validator/witness/committee privilege is required. `CREATE2` support and `SELFDESTRUCT` are both first-class TVM opcodes exposed to ordinary contract calls, so this is reachable purely through the contract-execution/trigger-smart-contract path.

### Recommendation
When processing `getDeleteAccounts()` / self-destructed addresses in `TransactionTrace.deleteContract` (and the analogous `RepositoryImpl.deleteContract`), also clear:
- All storage-row entries for the address (iterate and delete via the storage row store / trie root reset), and
- The `ContractStateStore` entry for the address.

Alternatively, follow the EIP-6780-style mitigation of only allowing storage-clearing suicide within the same transaction as contract creation, and otherwise disallow `CREATE2` redeployment to an address whose storage has not been fully purged.

### Proof of Concept
1. Deployer `D` deploys contract `C` via `CREATE2` with salt `S`, writing a storage slot `slot[0] = X` (e.g., representing "initialized"/"owner" state).
2. `D` calls a function on `C` that triggers `SELFDESTRUCT`. `TransactionTrace.finalization()` runs `deleteContract(address)`, wiping ABI/code/account/contract-metadata but leaving `slot[0] = X` in the storage store.
3. `D` redeploys new bytecode via `CREATE2` with the same salt `S`, landing on the identical contract address (`address = keccak(D, S, initcode)`).
4. On first execution, the new contract's `SLOAD slot[0]` returns the stale value `X` left from step 1, even though the new contract's constructor never wrote it — demonstrating unintended inheritance of prior "removed" contract state, analogous to the reported `executionInfo` residue bug.
