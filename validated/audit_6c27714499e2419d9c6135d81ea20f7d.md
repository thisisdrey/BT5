### Title
Split-Lock Check-Then-Update Race in Replay-Window Validation Enables Duplicate Packet Processing / Replay Bypass - (File: connection_state.go)

### Summary
The reported smart-contract issue is a classic TOCTOU (time-of-check/time-of-use) bug: a security-relevant check (`maxTotalSupply` cap) is validated separately from the state-mutating action it is meant to gate, leaving a window in which two operations can race and the invariant enforced by the check is silently violated. The same bug *class*—splitting a "check" and its corresponding "commit" into two separately-locked critical sections—exists in Nebula's replay-window handling in `ConnectionState.Decrypt` and `ConnectionState.VerifyRelay`.

### Finding Description
`Decrypt` and `VerifyRelay` in `connection_state.go` validate an incoming message counter against the replay window and then decrypt/verify the packet, finally recording the counter as "seen," but the three steps are not atomic:

```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
...
out, err = cs.dKey.DecryptDanger(...)   // no lock held here
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)
cs.decryptLock.Unlock()
``` [1](#0-0) 

`window.Check` only tests whether the counter would be considered a replay against the *current* window state; it does not mark the counter as consumed. `window.Update` is the step that actually records the counter into the bitmap. Because the read path (`listenIn`/`listenOut`) can run with multiple concurrent reader goroutines (`tun.routines` / `listen.routines`) sharing the same `ConnectionState` for a tunnel, two packets carrying the *same* `messageCounter` (e.g., a captured-and-replayed packet sent twice, or duplicated by an on-path relay/attacker) can each acquire `decryptLock`, run `Check`, and get `true` before either one reaches `Update`. Both then proceed to `DecryptDanger` and are treated as valid, non-replayed traffic.

This is structurally identical to the vault bug: the "cap check" (`Check`) and the "state mutation that enforces the cap for future callers" (`Update`) are decoupled across two independently-lockable regions, and an attacker who can get two racing operations to interleave (front-running the mutation with another check) causes the guarantee ("no counter is processed twice") to be violated.

### Impact Explanation
The replay window's entire purpose is to guarantee exactly-once processing of the counter space in the underlying Noise/AEAD transport (`traffic decryption/forgery/replay` protections). If a captured ciphertext with counter `N` is duplicated on the wire (something any network-path attacker can do without holding a valid Nebula certificate, since it is a pure retransmission of already-observed traffic) and the two copies land on different reader goroutines close enough in time, both can pass `Check` and be independently decrypted and delivered to the application/tun device. This is a duplicate-delivery / replay-window bypass: an out-of-band attacker who can duplicate/relay UDP datagrams (no cert required, just IP-level packet duplication or a compromised relay) can cause a single legitimate ciphertext to be accepted and processed twice, defeating the intended AEAD nonce/replay protection this window exists to guarantee.

### Likelihood Explanation
Nebula explicitly supports multiple concurrent reader routines (`routines` config, and the routine-local `conntrackCache`) which is exactly the concurrency model needed to expose the race — the code was clearly written with concurrency in mind (hence the `decryptLock`), but the lock scope does not cover the full check-decrypt-update sequence. Triggering the race requires precise timing (the duplicate packets must be processed by two different routines within the small window between `Check` and `Update`), so this is not trivially reliable, but it is a genuine, reachable protocol-level race rather than a theoretical one, and does not require the attacker to possess a CA-signed certificate — only the ability to capture and retransmit a UDP datagram belonging to an existing tunnel.

### Recommendation
Hold `decryptLock` across the entire check-decrypt-update sequence (or perform an atomic "check-and-reserve" step before decryption, then a final "commit" after successful decryption, using a single critical section) so that no second reader can observe the pre-Update window state for the same counter. Alternatively, use a lock-free CAS-based bitmap update where the "check" and "mark seen" happen as a single atomic operation prior to invoking `DecryptDanger`.

### Proof of Concept
Not independently verifiable without the ability to run concurrent goroutines against a live tunnel and control packet arrival timing; the race is inferred from the code structure (`Check` and `Update` split across separate lock acquisitions with unlocked decryption in between) at [1](#0-0) , combined with Nebula's multi-routine reader design at [2](#0-1) . Reproducing this concretely would require: (1) establishing a tunnel with `routines > 1`, (2) capturing one legitimate encrypted packet, (3) sending two copies of it simultaneously so they are picked up by two different reader goroutines before either completes its `Update`, and (4) observing whether both are delivered instead of the second being dropped as `ErrAlreadySeen`.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

		}

	}

}
