`pallet-inbound-queue-v2` correctly gates its `submit` entrypoint with `ensure!(!OperatingMode::<T>::get().is_halted(), Error::<T>::Halted);` [1](#0-0) , but the sibling `pallet-outbound-queue-v2`'s `submit_delivery_receipt` extrinsic has **no such check at all**, even though the pallet defines an `Error::<T>::Halted` variant that is never referenced or raised anywhere in the file [2](#0-1) . That fix relies entirely on `T::Verifier::verify` returning `VerificationError::Halted` — it does not add a direct `ensure_not_halted`/`OperatingMode` check inside `outbound-queue-v2` itself, unlike `inbound-queue-v2` which has its own independent, pallet-level `OperatingMode` storage and check in addition to relying on the verifier.

### Title
`submit_delivery_receipt` in Snowbridge outbound-queue-v2 lacks its own halt/operating-mode gate and relies solely on the verifier - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The `PolygonZkEVM.sol` report shows a public, permissionless function (`consolidatePendingState`) that omitted a halt check other similarly-sensitive functions had, letting execution continue and interfere with emergency cleanup. The exact analog exists in `snowbridge-pallet-outbound-queue-v2`: its public `submit_delivery_receipt` extrinsic has no pallet-level `OperatingMode`/halted check and no defensive use of its own declared `Error::<T>::Halted`, unlike the structurally identical `inbound-queue-v2::submit`, which independently checks `OperatingMode::<T>::get().is_halted()` before calling the verifier.

### Finding Description
`inbound-queue-v2::submit` performs a defense-in-depth check: it reads its own `OperatingMode` storage and errors out with `Error::<T>::Halted` before ever calling `T::Verifier::verify` [6](#0-5) . `outbound-queue-v2::submit_delivery_receipt` performs the analogous privileged action (paying relayer rewards from `PendingOrders`) but goes straight to `T::Verifier::verify(...)` with no pallet-side halted check, despite declaring an identical `Error::<T>::Halted` variant that is dead code [7](#0-6) . The pallet has no `OperatingMode` storage item or `set_operating_mode` call at all, meaning the only thing standing between "governance declared an emergency" and "this pallet keeps paying rewards" is whatever `T::Verifier` (the ethereum-client pallet) does internally.

### Impact Explanation
If the configured `T::Verifier` for a given runtime does not itself enforce a halt (e.g., is bypassed, misconfigured, or a future/alternate verifier implementation is wired in without the halt-forwarding behavior that `pr_11856` added specifically to `pallet-ethereum-client`), `submit_delivery_receipt` remains fully callable during an active emergency stop. This directly matches the required-impact class of "public underpriced work that... stalls bridge processing" and duplicate/incorrect settlement: reward payouts (`T::RewardPayment::register_reward`) and removal of `PendingOrders` entries continue during exactly the window governance intended to freeze, undermining the emergency response and creating an inconsistency between the two "v2" queue pallets that are otherwise meant to behave symmetrically.

### Likelihood Explanation
Medium: today the fix is centralized in the shared `Verifier` implementation for the default runtime wiring, so in the current concrete BridgeHub runtime configuration the halt does propagate. But the vulnerability is structural — `outbound-queue-v2` has zero independent enforcement, so any change to `T::Verifier`, alternate verifier config, or future pallet reuse silently reintroduces the exact bug the report class describes, exactly as it did before PR 11856 for both `inbound_queue_v2::submit` and `outbound_queue_v2::submit_delivery_receipt`.

### Recommendation
Add pallet-local `OperatingMode` storage (as `inbound-queue-v2` and legacy `outbound-queue` already have) plus a `set_operating_mode` governance call, and gate `submit_delivery_receipt` with `ensure!(!OperatingMode::<T>::get().is_halted(), Error::<T>::Halted)` before invoking the verifier — mirroring `inbound-queue-v2::submit` — so the halt check does not solely depend on the verifier implementation.

### Proof of Concept
1. Configure a runtime where `pallet-outbound-queue-v2::Config::Verifier` is any implementation that does not itself short-circuit on halted state (i.e., not the exact `pallet-ethereum-client` post-`pr_11856` behavior — for example a test/mock verifier, or a future replacement verifier).
2. Governance halts the bridge via whatever mechanism sets that verifier's own halted flag (e.g., `pallet-ethereum-client::set_operating_mode(Halted)`).
3. Call `outbound_queue_v2::submit_delivery_receipt(event)` as any relayer with a valid Ethereum event proof for an existing `PendingOrders` entry.
4. Because `outbound-queue-v2` has no local halt check, `T::Verifier::verify` (in this misconfigured/alternate case) succeeds, `process_delivery_receipt` executes, the reward is paid via `T::RewardPayment::register_reward`, and the `PendingOrders` entry is removed — all while the bridge is supposed to be fully halted.
