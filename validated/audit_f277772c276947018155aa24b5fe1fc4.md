### Title
Legacy (non-hardened) TRX/TRC10 exchange pool math permits floating-point rounding drain of `Exchange`/`ExchangeV2` pools - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeTransactionContract`, broadcastable by any account holding TRX/TRC10 tokens, invokes `ExchangeCapsule.transaction()`, which by default (when the `allowHardenExchangeCalculation` chain parameter is not active) routes through `ExchangeProcessor` — a Bancor-relay-style AMM implemented with `double` floating point arithmetic and no post-transaction balance invariant check.

### Finding Description
`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` to compute `anotherTokenQuant` for a pool swap and mutate the pool balances. [1](#0-0) 

Inside `ExchangeCapsule.transaction()`, when `hardenedCalc` is `false` (the legacy/default path), a plain `ExchangeProcessor` is used and the resulting new pool balances are applied without any sanity check; the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` guard is only executed `if (hardenedCalc && ...)`: [2](#0-1) 

`ExchangeProcessor.exchangeToSupply` / `exchangeFromSupply` compute the relay-token math entirely with `double` and `Maths.pow`, casting the final result to `long` with implicit truncation and no explicit rounding-direction control: [3](#0-2) 

By contrast, the project has already implemented a fix path, `SafeExchangeProcessor`, that performs the same relay math with `BigDecimal`, explicit `RoundingMode.DOWN`, and enforces the non-negative balance invariant — but this path is only used when `hardenedCalc` (the `allowHardenExchangeCalculation` dynamic property) is enabled: [4](#0-3) 

The existence of this hardened replacement confirms the underlying bug class: the default double-precision Bancor formula in `ExchangeProcessor` is susceptible to repeated small-trade rounding exploitation (an attacker can perform successive `ExchangeTransactionContract` calls with carefully sized `quant`/`expected` values to accumulate favorable rounding on each trade), draining the pool's TRX/TRC10 reserves over many transactions in the same spirit as the Wise Lending V2 logic-flaw drain (repeated exploitation of imprecise pool accounting rather than a single overflow). No flash-loan primitive exists in java-tron, but the actuator is reachable directly and repeatedly by any unprivileged account, and there is no atomicity requirement for the exploit to work — it only requires the "harden" flag to be inactive.

### Impact Explanation
Successful exploitation permanently drains real TRX/TRC10 assets from the `Exchange`/`ExchangeV2` pool into the attacker's account balance, an unauthorized transfer of funds meeting the "theft of funds" bar. Because the check preventing negative pool balances is gated behind the `hardenedCalc` flag, a network where that hard-fork feature has not yet been activated remains exposed to floating-point rounding drain and, in the worst case, negative/underflowed pool balances that break future price computations for all `ExchangeTransactionContract` users of that market.

### Likelihood Explanation
Likelihood depends entirely on whether `allowHardenExchangeCalculation` is active on the target network at the current block height; while active, this path is inert since `SafeExchangeProcessor` is used. Exploitation while inactive requires no special privilege — a single account can iteratively submit small `ExchangeTransactionContract` transactions against an open `Exchange`, which is a normal user-facing DEX operation, making the attack straightforward to script once the exact rounding bias is characterized against a specific pool's balances.

### Recommendation
Complete migration to `SafeExchangeProcessor`/`BigDecimal` math and the non-negative-balance invariant unconditionally (not gated by `allowHardenExchangeCalculation`), or accelerate activation of the corresponding hard fork parameter network-wide; additionally, apply the negative-balance guard in `ExchangeCapsule.transaction()` regardless of `hardenedCalc`.

### Proof of Concept
1. On a network/testnet where `allowHardenExchangeCalculation` (`allowHarden()`) is not yet activated, create or locate an `Exchange`/`ExchangeV2` pool via `ExchangeCreateContract`.
2. Repeatedly submit `ExchangeTransactionContract` transactions from a single account with small `quant` values chosen so that `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`'s `double`-truncation consistently rounds in the trader's favor (verified via `ExchangeCapsuleTest.testExchange`, which already documents the differing outputs between the non-hardened and hardened paths for the same trade sizes) [5](#0-4) .
3. Observe the pool's `firstTokenBalance`/`secondTokenBalance` (as tracked in `ExchangeCapsule`) degrade over many iterations while the attacker's TRX/TRC10 asset balance grows disproportionately relative to what was deposited, confirming value extraction from the pool without a corresponding legitimate trade value.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
