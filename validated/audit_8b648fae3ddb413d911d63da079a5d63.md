Audit Report

## Title
`success` field of Ethereum `DeliveryReceipt` is decoded but never checked before paying relayer reward and settling the order - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
The Snowbridge V2 outbound queue's `process_delivery_receipt` unconditionally pays the relayer's full reward and removes the `PendingOrder` from storage whenever a validly-proven `DeliveryReceipt` is submitted, without ever inspecting the decoded `receipt.success` field that indicates whether the Ethereum-side dispatch actually succeeded. This means dispatch failures on Ethereum are settled identically to successes on Polkadot.

## Finding Description
The Ethereum Gateway emits `InboundMessageDispatched(uint64 nonce, bytes32 topic, bool success, bytes32 reward_address)` for every dispatched message regardless of outcome [1](#0-0) , and this is decoded into `DeliveryReceipt` including the `success: bool` field [2](#0-1) .

`Pallet::process_delivery_receipt` validates only `receipt.gateway` and looks up `receipt.nonce` in `PendingOrders`; it never reads `receipt.success` (or `receipt.topic`) before registering the reward and removing the order [3](#0-2) . A repository-wide search confirms `success` is referenced nowhere in the `outbound-queue-v2` pallet besides the struct definition it's decoded into, i.e., the field is fully dead once decoded. The public `submit_delivery_receipt` extrinsic is callable by any signed account after proof verification, with no additional gating on the success outcome [4](#0-3) . The order that gets unconditionally settled was created with the message's `fee` at commit time [5](#0-4) .

## Impact Explanation
Because reward payout and permanent order removal happen identically whether `receipt.success` is `true` or `false`, there is no differentiation in Polkadot-side accounting between "message executed successfully on Ethereum" and "message dispatch reverted/failed on Ethereum." This violates the invariant that bridge rewards and payout state must only advance/settle after execution is known to have succeeded, matching the "Message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" pivot. Once `PendingOrders::remove(nonce)` executes, the failure is silently and permanently discarded with no recourse for re-queueing or differentiated reward accounting — the exact wrong value corrupted is the reward payout amount/decision and the `PendingOrders` settlement state, which advance to "delivered" and "rewarded" even on a proven `success: false` receipt.

## Likelihood Explanation
This is reachable by any unprivileged relayer via the public `submit_delivery_receipt` extrinsic using a legitimately-obtained, valid Merkle/receipt proof of a genuine `InboundMessageDispatched` event — no forged proof or privileged access is required. A `success: false` outcome (e.g., due to insufficient gas or a reverting downstream contract call) is a normal, expected occurrence in bridge operation, not a contrived edge case, making the likelihood of hitting this code path high during ordinary operation.

## Recommendation
- Branch explicitly on `receipt.success` in `process_delivery_receipt`.
- On `success == false`, skip or reduce the reward payout and route the order to a distinct failure-handling path instead of the same `PendingOrders::remove` + `MessageDelivered` settlement used for successful dispatch.
- Emit a distinct event (e.g., `MessageDispatchFailed`) so downstream consumers can distinguish outcomes.
- Add unit tests asserting no reward registration occurs when a valid receipt with `success: false` is submitted.

## Proof of Concept
1. A message with nonce `N` and non-zero `fee` is committed, creating a `PendingOrder` [5](#0-4) .
2. The relayer relays the message to Ethereum; the destination call reverts, so the Gateway legitimately emits `InboundMessageDispatched(nonce=N, topic, success=false, reward_address)`.
3. The relayer builds a genuine Merkle/receipt proof for this log and calls `submit_delivery_receipt`; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success: false` correctly.
4. `process_delivery_receipt` checks `gateway` and finds the `PendingOrders` entry, then unconditionally calls `T::RewardPayment::register_reward(&reward_account, .., order.fee)` and removes the order, exactly as it would for `success: true`.
5. The relayer receives full reward and `MessageDelivered { nonce }` is emitted, despite the on-chain Ethereum proof itself indicating dispatch failure.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
