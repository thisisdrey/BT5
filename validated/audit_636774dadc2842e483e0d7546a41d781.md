## Title
Data race on `CommonParameter.ENERGY_LIMIT_HARD_FORK` bypassing the VMConfig snapshot isolation, causing non-deterministic energy-limit enforcement across threads - (File: `common/src/main/java/org/tron/core/vm/config/VMConfig.java`)

### Summary
`VMConfig` was explicitly hardened so that VM configuration flags are published as an immutable, `volatile`-referenced `Snapshot` object, with a `ThreadLocal` override for constant calls that must not pollute the concurrently-running block-processing (HEAD) path. [1](#0-0) 
However, one flag — the "hard fork" energy-limit flag — was left outside this mechanism: `initVmHardFork` writes directly to the plain static field `CommonParameter.ENERGY_LIMIT_HARD_FORK` instead of going through the `Snapshot`/volatile-publish path. [2](#0-1) [3](#0-2) 

### Finding Description
`ConfigLoader.load(storeFactory, isolate)` is the single entry point that refreshes VM configuration from `DynamicPropertiesStore`. It is called both from the block-processing (HEAD, `isolate=false`) path and from constant-call/JSON-RPC execution paths (`isolate=true`) that can run on separate threads concurrently with block application. Every field except the hard-fork flag is written into a fresh `Snapshot` object and installed either into the `volatile globalSnapshot` or into a `ThreadLocal<Snapshot>`, guaranteeing safe publication and thread isolation: [4](#0-3) [5](#0-4) 

But `VMConfig.initVmHardFork(checkForEnergyLimit(ds))` is invoked unconditionally at the top of `load()`, for both `isolate=true` and `isolate=false` calls, and writes straight into `CommonParameter.ENERGY_LIMIT_HARD_FORK`, a plain static field with no `volatile` qualifier and no `ThreadLocal` isolation: [6](#0-5) 

This is functionally identical to the kernel bug class described in the report: a globally shared, frequently-toggled configuration value (`sysctl_icmp_echo_enable_probe` in the kernel, `CommonParameter.ENERGY_LIMIT_HARD_FORK` here) is written by one thread and read by others (`VMConfig.getEnergyLimitHardFork()`) without any `volatile`/atomic guarantee — meaning readers on other CPU cores/threads are not guaranteed to observe the write in a timely or ordered fashion, and there is no memory barrier ensuring visibility.

Because `ConfigLoader.load()` is invoked from constant-call execution (e.g., `eth_call`/`triggerConstantContract` served via the JSON-RPC/Wallet query paths) on worker threads distinct from the block-application thread in `Manager`, an unprivileged API client issuing constant calls concurrently with block processing can race the write to `ENERGY_LIMIT_HARD_FORK` against the block-processing thread's read of the same field during real transaction execution/energy accounting.

### Impact Explanation
`ENERGY_LIMIT_HARD_FORK` gates how energy-limit ("out of energy") checks are performed for TVM execution. Because it is a shared mutable static that is written from a constant-call/query thread without any synchronization or `volatile` semantics, and read from the block-application thread, different threads/nodes can transiently observe stale or torn values depending on scheduling — the same non-determinism class the kernel fix addresses (undefined/inconsistent reads of a racily-updated flag). In a consensus system, any source of non-deterministic VM/energy-limit behavior driven by thread scheduling rather than deterministic block content is a correctness hazard: it can cause a node to enforce a different energy-limit hard-fork behavior than its peers for the same transaction, which is the kind of state divergence that can lead to chain-split-class problems in a validating node fleet.

### Likelihood Explanation
The write path (`ConfigLoader.load`) is reached on every constant call / JSON-RPC `eth_call` served by the node in parallel with ongoing block processing — both are normal, unauthenticated, and highly frequent operations, so the racing writer and racing reader are both trivially reachable by any external API client without special privileges. No attacker-controlled malicious input is even required beyond issuing ordinary read-only contract calls while blocks are being applied, which happens continuously on any public full node.

### Recommendation
Bring `CommonParameter.ENERGY_LIMIT_HARD_FORK` (or better, migrate this flag into the existing `VMConfig.Snapshot`/`globalSnapshot`+`localSnapshot` mechanism) so that it is published the same way as every other flag in `VMConfig`: either mark the field `volatile` and ensure the constant-call (`isolate=true`) path never writes the shared global instance, or move `allowHardFork`-style state into `Snapshot` so isolate-scoped calls only affect their `ThreadLocal` view, consistent with the isolation guarantees already implemented and unit-tested for every other flag in `VMConfigIsolationTest`. [7](#0-6) 

### Proof of Concept
1. Deploy any contract and repeatedly call it via `triggerConstantContract`/`eth_call` on a full node's JSON-RPC endpoint (unprivileged, read-only), triggering `ConfigLoader.load(storeFactory, true)` on request-handling threads.
2. Concurrently, the node's block-processing thread applies incoming blocks, which also invokes `ConfigLoader.load(storeFactory, false)` and therefore `VMConfig.initVmHardFork(...)`, writing to the same non-volatile `CommonParameter.ENERGY_LIMIT_HARD_FORK` field that step 1's threads are also writing/reading concurrently.
3. Because there is no `volatile`/synchronization on this specific field (unlike the rest of `VMConfig`), the block-processing thread's `VMConfig.getEnergyLimitHardFork()` read used during energy-limit enforcement is not guaranteed to observe a consistent, correctly-ordered value, exposing a genuine data race under concurrent, entirely unprivileged API traffic.

   * A constant call's thread-local config view must not pollute the global config that the
   * (concurrent) block-processing path reads. This is the core Problem-2 guarantee.

  @Test
  public void testLocalConfigDoesNotPolluteGlobalAcrossThreads() throws InterruptedException {
    VMConfig.initAllowTvmOsaka(1);            // global (HEAD) view: activated
    assertTrue(VMConfig.allowTvmOsaka());     // no thread-local -> reads global

    VMConfig.Snapshot local = new VMConfig.Snapshot();
    local.allowTvmOsaka = false;              // simulate a not-yet-solidified snapshot
    VMConfig.setLocalSnapshot(local);

    // this thread now sees its own (solidity) view...
    assertFalse(VMConfig.allowTvmOsaka());

    // ...but another thread (e.g. block processing) must still see the global HEAD value.
    AtomicBoolean otherThreadSaw = new AtomicBoolean(false);
    Thread t = new Thread(() -> otherThreadSaw.set(VMConfig.allowTvmOsaka()));
    t.start();
    t.join();
    assertTrue("global config must be unaffected by another thread's local view",
        otherThreadSaw.get());

    // after dropping the local view, this thread falls back to the global value again.
    VMConfig.clearLocalSnapshot();
    assertTrue(VMConfig.allowTvmOsaka());
  }
