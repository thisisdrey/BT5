Audit Report

## Title
`success` field of Snowbridge V2 delivery receipt is decoded but never checked before paying relayer reward - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt::try_from` decodes the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event log into a `DeliveryReceipt` struct that includes a `success: bool` field, but `Pallet::process_delivery_receipt` never reads or checks this field before paying the relayer's reward via `T::RewardPayment::register_reward`. <cite repo="Lauraivanka/polkadot-sdk--010" path="bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs" start="10-27" /> <cite repo="Lauraivanka/polkadot-sdk--010" path="bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs" start="445-480" /> Consequently, a relayer can obtain full reward for a message whose dispatched command actually reverted on Ethereum, as long as they submit a valid inclusion proof of the emitted event.

## Finding Description
`submit_delivery_receipt` is a signed, permissionless extrinsic that any account can call, requiring only `ensure_signed`. <cite repo="Lauraivanka/polkadot-sdk--010" path="bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs" start="298-317" /> After `T::Verifier::verify` confirms the Ethereum event log's inclusion and well-formedness — which proves only that the log was emitted, not that the underlying dispatched command executed successfully — the log is decoded via `DeliveryReceipt::try_from`, capturing `success` directly from the event payload. <cite repo="Lauraivanka/polkadot-sdk--010" path="bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs" start="38-51" />

`process_delivery_receipt` then: validates the gateway address, resolves `reward_account`, looks up the `PendingOrder` by nonce, and unconditionally pays `order.fee` via `T::RewardPayment::register_reward` whenever `fee > 0`, before removing the pending order and emitting `MessageDelivered`. <cite repo="Lauraivanka/polkadot-sdk--010" path="bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs" start="453-480" /> `receipt.success` is never referenced in this function or anywhere else in the pallet — confirmed by a grep across `bridges/snowbridge/pallets/outbound-queue-v2/` showing no occurrences of `success` outside the decode struct. This means the reward payout path treats "event log observed" as equivalent to "command executed successfully," which is not the case: `success = false` and `success = true` receipts are processed identically.

## Impact Explanation
This is a public underpriced work / broken payout invariant: reward settlement is decoupled from the actual successful message dispatch on Ethereum, allowing rewards to be paid for failed cross-chain executions as long as a valid proof of the (possibly failure-indicating) event log is produced. This violates the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically," and can be used to drain the relayer reward pool for non-productive work.

## Likelihood Explanation
High: `submit_delivery_receipt` requires only a signed origin (any account) and a standard proof of a genuinely emitted Ethereum event log — no privileged role or compromised trust assumption beyond the pallet's own expected relayer flow is needed. <cite repo="Lauraivanka/polkadot-sdk--010" path="bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs" start="307-311" /> Any command that reverts on the Ethereum Gateway (e.g., insufficient gas budget or failing downstream call) still results in the `InboundMessageDispatched` event with `success = false` being emitted, and the relayer submitting that proof collects the reward exactly as if it had succeeded.

## Recommendation
Gate the reward payment in `process_delivery_receipt` on `receipt.success`, e.g. `ensure!(receipt.success, Error::<T>::DeliveryFailed);` before calling `T::RewardPayment::register_reward`, or otherwise explicitly document/design a reduced-reward path for proof-of-relaying-only versus full reward for successful execution, so that mere event-log delivery is not conflated with successful command execution.

## Proof of Concept
1. A command dispatched through the V2 outbound queue pipeline reaches the Ethereum Gateway and reverts during execution; the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
2. Any signed account obtains a standard event-log inclusion proof for this event and calls `submit_delivery_receipt(origin, event)` on BridgeHub. <cite repo="Lauraivanka/polkadot-sdk--010" path="bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs" start="298-317" />
3. `T::Verifier::verify` succeeds, `DeliveryReceipt::try_from` correctly decodes `success = false`, but `process_delivery_receipt` still pays the full `order.fee` to `reward_account`. <cite repo="Lauraivanka/polkadot-sdk--010" path="bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs" start="464-473" />
4. `PendingOrders` is cleared and `MessageDelivered` is emitted, indistinguishable from a genuinely successful delivery, with the reward paid for a failed execution.
