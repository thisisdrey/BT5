The reported PoolTogether bug class — a deposit function that trusts the caller-supplied `_depositAmount` for share/accounting math instead of measuring the actual balance increase after the underlying-token transfer — has a direct analog in Zest's tokenized vault `deposit` function.

### Title
Vault `deposit` mints shares and increments accounted `assets` using the caller-supplied `amount` instead of the actual balance increase from the underlying transfer - (File: mainnet/contracts/vault/v0-vault-ststx.clar and sibling vaults)

### Summary
Every tokenized vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) implements `deposit` by computing the shares to mint from the nominal `amount` argument, calling `receive-underlying` to pull the underlying token, and then unconditionally recording `assets` as increased by that same nominal `amount` — without ever comparing the vault's actual underlying-token balance before and after the transfer.

### Finding Description
In `deposit`, `inkind` (shares to mint) is computed from `amount` via `convert-to-shares-preview` before any transfer occurs: [1](#0-0) 

`receive-underlying` simply calls the underlying SIP-010 token's `transfer` for the requested `amount` and returns `true` regardless of what the vault's balance actually became: [2](#0-1) 

The vault does maintain a helper that queries the real underlying balance, `ubalance`, but it is never called from `deposit` to reconcile the nominal transfer amount against the real balance delta: [3](#0-2) 

After the transfer, `deposit` blindly sets `(var-set assets (+ current-assets amount))` using the nominal `amount`, then mints `inkind` shares to the recipient: [4](#0-3) 

`assets` (not the live `ubalance`) is exactly what backs share pricing for both future deposits and redemptions via `total-assets` / `convert-to-shares-preview` / `convert-to-assets-preview`: [5](#0-4) 

This is precisely the bug class from the report: the contract trusts the requested transfer amount for its internal accounting instead of measuring the contract's actual balance increase. If the underlying token contract for any reason delivers less than `amount` to the vault on `transfer` (e.g. a future governance-approved underlying migration, a non-standard SIP-010 implementation, or any token-level behavior that doesn't move exactly `amount` into the vault, such as `ststx-token` or `ststxbtc-token-v2`, which are external, non-Zest-controlled LST wrapper tokens), the vault's `assets` variable becomes permanently inflated relative to its real, redeemable underlying balance. The same pattern repeats identically in `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, and `v0-vault-ststxbtc.clar`.

### Impact Explanation
Once `assets` diverges above the vault's real token balance, share price (`convert-to-shares-preview`/`convert-to-assets-preview`) is computed on a false denominator: new depositors receive fewer shares than warranted by real backing, while later redeemers computing `inkind` off the inflated `assets` figure can find the vault unable to fully honor withdrawals with real underlying tokens once the shortfall surfaces — this is a permanent freezing of funds / protocol insolvency scenario, since `send-underlying` moves real tokens out of the vault while accounting believes more is available than physically exists.

### Likelihood Explanation
Likelihood depends on the underlying SIP-010 token ever failing to deliver the exact requested `amount` to the vault's balance on `transfer`. For the currently deployed collateral tokens this requires a change in token behavior (e.g. any future non-conforming or fee-bearing token, or unexpected behavior in the external LST wrapper contracts `ststx-token` / `ststxbtc-token-v2`), so likelihood is contingent on external token behavior rather than being trivially triggerable today, but the vault code provides zero defense-in-depth against it despite a balance-check helper (`ubalance`) already existing in the contract.

### Recommendation
In `deposit` (and correspondingly in `receive-underlying`), read the underlying token balance via `ubalance` (or equivalent) immediately before and after the transfer, compute the actual received delta, and use that delta — not the caller-supplied `amount` — both for the `var-set assets` update and, ideally, re-derive `inkind` from the actual delta before minting shares. Apply the same fix uniformly across `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, and `v0-vault-ststxbtc.clar`.

### Proof of Concept
1. Assume (or a future DAO-approved migration introduces) an underlying token whose `transfer` call can deliver less than the requested `amount` to the recipient (e.g. a fee-charging or capped transfer implementation) for `UNDERLYING` in `v0-vault-ststx.clar`.
2. A user calls `deposit` with `amount = 1000`; `inkind` shares are computed from the full `1000` via `convert-to-shares-preview`.
3. `receive-underlying` calls `transfer 1000 ...`, but the vault's real balance only increases by, say, `950`.
4. `deposit` still executes `(var-set assets (+ current-assets 1000))` and mints the full `inkind` shares computed on `1000`.
5. `assets` is now `50` higher than the vault's real underlying balance. Over repeated deposits (or a single large one), the gap grows until redemptions computed via `convert-to-assets-preview` (based on the inflated `assets`) cannot be fully paid out from the vault's real token holdings, freezing/insolvency-risking other depositors' funds.

(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
