## Analysis

The core broken invariant in the external report: a "destruct"-style cleanup function transfers remaining tokens to another party, but the transfer is not guarded — if it fails, the destructive/irreversible cleanup proceeds anyway, and the un-transferred value is effectively lost/locked with no documented recovery path.

The closest local analog is `Pallet::<T>::dissolve_pool` in `pallet-nomination-pools`, which permanently destroys a pool's reward account while **ignoring** the result of the final balance transfer to the depositor, and then **unconditionally zeroes** the account's balance regardless of whether that transfer succeeded. [1](#0-0) 

```rust
// This shouldn't fail, but if it does we don't really care. Remaining balance can consist
// of unclaimed pending commission, erroneous transfers to the reward account, etc.
let reward_pool_remaining = T::Currency::reducible_balance(
    &reward_account,
    Preservation::Expendable,
    Fortitude::Polite,
);
let _ = T::Currency::transfer(
    &reward_account,
    &bonded_pool.roles.depositor,
    reward_pool_remaining,
    Preservation::Expendable,
);

defensive_assert!(
    T::Currency::total_balance(&reward_account) == Zero::zero(),
    "could not transfer all amount to depositor while dissolving pool"
);
// NOTE: Defensively force set balance to zero.
T::Currency::set_balance(&reward_account, Zero::zero());
```

`dissolve_pool` is called as part of the permissionless pool-destruction flow once a pool has no remaining members and its state is `Destroying`, reachable from the ordinary member/last-leaver extrinsics in `pallet-nomination-pools` (no privileged origin needed). [2](#0-1) 

### Title
Silent-failure token burn on pool dissolution: `dissolve_pool` zeroes reward-account balance even if the depositor refund transfer fails - (File: `substrate/frame/nomination-pools/src/lib.rs`)

### Summary
When the last members leave a nomination pool and its bonded/reward accounts are dissolved, `dissolve_pool` attempts to transfer the reward account's remaining reducible balance to the pool depositor. The `Result` of that transfer is discarded with `let _ = ...`, and the function unconditionally forces the reward account's balance to zero via `T::Currency::set_balance(&reward_account, Zero::zero())` immediately afterward. If the transfer fails for any reason, the remaining tokens are not redirected anywhere — they are erased from total issuance accounting by the forced zeroing, i.e. burned, with no event, no error, and no documented recovery path.

### Finding Description
`dissolve_pool` is the pool analog of "destruct": it permanently removes `RewardPools`, `SubPoolsStorage`, `Metadata`, `ReversePoolIdLookup`, and finally the bonded pool's account, exactly like `PolicyProposals.destruct()` permanently destroys the proposal contract. Just as in the external report, the code path that is supposed to return "unrefunded" value to a rightful party (there: `policy`; here: `bonded_pool.roles.depositor`) is not enforced to succeed:

- The transfer's `DispatchResult` is thrown away (`let _ = T::Currency::transfer(...)`).
- A `defensive_assert!` only logs in production builds; it does not stop execution or prevent the subsequent state mutation.
- `T::Currency::set_balance(&reward_account, Zero::zero())` runs unconditionally right after, forcibly setting the account's balance to zero. If the prior transfer partially or fully failed, this operation destroys value rather than "trapped" dust: any balance that failed to reach the depositor is deleted from the ledger, not preserved or escrowed.

A realistic failure mode for the initial transfer: if `reward_pool_remaining` is non-zero but below `ExistentialDeposit` and the depositor's account has since been reaped (e.g., after `withdraw_unbonded` fully exits the depositor and dust is swept), `T::Currency::transfer` to a non-existent account with an amount below the ED returns an error rather than creating the account, so the transfer fails and is swallowed. The dissolution then proceeds and the reward-account remainder is burned by the following `set_balance(0)`.

This mirrors the bug report's exact defect class: the "destruct"-equivalent operation transfers value to a target, that transfer is not guaranteed to succeed, and the destructive state change (account zeroing / pool removal) proceeds regardless — silently converting a legitimate depositor refund into a permanent loss, with the discrepancy undocumented (only a passing code comment "we don't really care").

### Impact Explanation
This falls under "permanent user-fund lock" / "theft or unbacked mint or unlock" adjacent territory: value that is rightfully owed to the pool depositor upon dissolution can be permanently destroyed instead of paid out, with no compensating mechanism, no event, and silent failure handling. Because pool dissolution is a normal, unprivileged lifecycle event (final member leaving/withdrawing), this is reachable without any privileged actor, malicious validator, or governance action — it is a pure accounting/state-machine bug in `pallet-nomination-pools`.

### Likelihood Explanation
Triggering requires the reward account to hold a small remaining balance (dust from commission rounding, direct/erroneous transfers into the reward account, etc.) at the moment the last member fully exits and dissolution runs, combined with the depositor's account having been reaped in the interim. This is a plausible, unprivileged sequence of ordinary pool operations rather than a contrived edge case, though it depends on specific dust/ED conditions, which lowers likelihood from "trivial" to "moderate."

### Recommendation
- Do not discard the result of the transfer to the depositor; instead, on failure, escrow the residual amount (e.g., to the pool pallet's own account or the treasury) rather than force-zeroing it, and emit an event recording the outcome.
- Replace the unconditional `set_balance(&reward_account, Zero::zero())` with a data-preserving path that either retries with `Preservation::Expendable`/`Precision::BestEffort` semantics that account for the actual delta, or documents and enforces that any leftover truly is dust below one currency unit (not an arbitrary sub-ED balance).
- Upgrade the `defensive_assert!` to a hard failure (or a metered/tracked event) so operators can detect when dissolution loses funds, consistent with how `pallet-revive`'s `do_terminate` wraps the whole destruction sequence in `with_transaction` and rolls back atomically on failure rather than committing a partial, value-losing state.

### Proof of Concept
1. Create a nomination pool; let commission accrue such that the reward account carries a small `reward_pool_remaining` balance below `ExistentialDeposit`.
2. Have the pool depositor fully withdraw all funds via the standard unbond/withdraw flow so their account balance drops to zero and is reaped (removed from `System` accounts).
3. Have the final remaining pool member leave, triggering `dissolve_pool`.
4. Observe: `T::Currency::transfer(&reward_account, &depositor, reward_pool_remaining, Preservation::Expendable)` fails because the destination account does not exist and the amount is below ED; the error is discarded.
5. `T::Currency::set_balance(&reward_account, Zero::zero())` executes unconditionally, permanently destroying `reward_pool_remaining` instead of it reaching the depositor — no error is surfaced to the caller of the dissolving extrinsic, and no event records the loss.
