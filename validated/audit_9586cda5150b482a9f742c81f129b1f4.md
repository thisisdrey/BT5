### Title
Unvalidated caller-supplied account key lets an attacker fill a victim's `depositTokensOfAccount`/`debtTokensOfAccount` sets to `MAX_TOKENS_PER_USER`, freezing the victim's deposits and mints - (File: contracts/Pool.sol)

### Summary
The bug class in the external report is "improper input validation on a key that is written into a shared/global container, corrupting behavior for others" (prototype pollution via `txTimestampCache[__proto__]`). The Metronome analog lives in `Pool.addToDepositTokensOfAccount(address account_)` / `Pool.addToDebtTokensOfAccount(address account_)` in `contracts/Pool.sol:204-220`. These functions accept a fully attacker-controlled `account_` key and unconditionally write into `depositTokensOfAccount` / `debtTokensOfAccount` (`MappedEnumerableSet` in `contracts/storage/PoolStorage.sol`), guarded only by `onlyIfAdditionWillNotReachMaxTokens` which reverts once `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER (30)` (`contracts/Pool.sol:143-148`). The set mutation is driven from public, unprivileged entry points: `DepositToken.deposit(amount_, onBehalfOf_)` (`contracts/DepositToken.sol:211-237` → `_mint` → `pool.addToDepositTokensOfAccount(account_)` at lines 485-488) and `DepositToken.transfer`/`transferFrom` (`_transfer` → `pool.addToDepositTokensOfAccount(recipient_)` at lines 517-520). There is no validation that `account_` consented to receive the entry — analogous to writing `cache[__proto__][txId]` without validating the key.

### Finding Description
`DepositToken._mint` and `DepositToken._transfer` call `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance goes 0 → >0 (`contracts/DepositToken.sol:485-488, 517-520`). The `account_`/`recipient_` argument is attacker-chosen via `deposit(amount_, victim)` or `transfer(victim, dust)`. The only guard, `onlyIfAdditionWillNotReachMaxTokens`, makes the *entry point* revert once the victim's combined token list reaches 30 — it does not prevent the attacker from pushing the victim's list to exactly 30.

Concretely: an attacker deposits 1 wei (or transfers dust) of each of the pool's registered deposit tokens `onBehalfOf`/`to` the victim. Once `depositTokensOfAccount[victim]` has 30 entries:

- `DepositToken.deposit(amount_, victim)` → `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens()` revert — victim cannot open a collateral position in any token type they don't already hold.
- `DebtToken.mint` → `addToDebtTokensOfAccount` → same combined-length check reverts — victim cannot mint a synthetic asset they don't already hold (so they cannot mint the synth needed to repay or to rebalance).
- Any third-party `deposit onBehalfOf` the victim, `SmartFarmingManager.leverage`, and liquidation-rescue top-ups with a new collateral type all revert.

This is the direct structural analog: an unvalidated, caller-controlled key (`account_`) is written into a shared bookkeeping container whose global invariant (`MAX_TOKENS_PER_USER`) then corrupts the protocol's logic for that account — exactly the "write `cache[key][id]` with `key = __proto__`" pattern, expressed in EVM storage terms.

### Impact Explanation
Temporary freezing of funds / griefing leading to loss. A victim whose list is filled cannot add collateral of a new type or mint a new debt token. If the victim's position drifts unhealthy while blocked, they cannot deposit a different collateral to restore health and can be liquidated (loss via `Pool.liquidate`). Recovery requires the victim to burn gas transferring each dust position out (a balance→0 transfer triggers `removeFromDepositTokensOfAccount`, `contracts/DepositToken.sol:522-525`), which is ~30 transactions; during that window deposits/mints stay frozen. For smart-wallet/vault victims that cannot call `transfer` on the deposit tokens, the freeze can persist until the dust is liquidated or seized. The corruption is to *per-account* state rather than global state, but the invariant broken (account's ability to mutate its own position list) is the closest Solidity-equivalent impact to prototype pollution: liveness of the victim's position management is destroyed by unprivileged writes.

### Likelihood Explanation
Cheap and unprivileged: the attacker needs only dust balances of the pool's deposit tokens (up to 30 distinct collaterals), obtainable via `deposit` of minimal amounts — `deposit` only requires `amount_ > 0` (`contracts/DepositToken.sol:215`). No privileged role, no oracle manipulation, no flash loan needed; `MAX_TOKENS_PER_USER` is hardcoded to 30 (`contracts/Pool.sol:79`). The only mitigations are that `depositTokens` itself is capped at 30 entries (`addDepositToken`, `contracts/Pool.sol:703`) and that the victim can self-clean by transferring dust out — but nothing prevents re-filling, and a liquidator can even re-fill the list via `seize`-mediated transfers is not needed; plain `transfer`/`deposit(onBehalfOf)` suffices, repeatable after each cleanup.

### Recommendation
Require recipient opt-in or bound attacker-forced entries: (a) restrict `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` to the `_msgSender`'s own account when invoked from `_transfer`/`_mint` triggered by a third party — i.e., only track a token in the set if the credited account initiated the action (deposit-to-self or explicit opt-in); or (b) drop the hard `MAX_TOKENS_PER_USER` revert and instead iterate lazily / paginate `depositOf`/`debtOf`; or (c) make unsolicited small transfers not register in the per-account set (minimum-balance threshold before `add`).

### Proof of Concept
Foundry sketch (assume deployed `Pool` `p`, deposit tokens `d0..d29`, attacker EOA):

```solidity
function test_FillVictimTokenList() public {
    // d0..dN are the pool's registered DepositTokens (< 30 needed, plus victim's existing entries)
    address victim = makeAddr("victim");

    // victim already holds one collateral type and debt
    // attacker deposits 1 wei of each underlying on behalf of victim
    for (uint i; i < 30; ++i) {
        IERC20 underlying = dTokens[i].underlying();
        deal(address(underlying), attacker, 2);
        vm.startPrank(attacker);
        underlying.approve(address(dTokens[i]), 2);
        // fills depositTokensOfAccount[victim]; last call may revert at 30, so use transfer for the tail
        dTokens[i].deposit(1, victim);
        vm.stopPrank();
    }

    assertEq(p.getDepositTokensOfAccount(victim).length, 30);

    // victim can no longer deposit a collateral type they don't hold
    vm.expectRevert(UserReachedMaxTokens.selector);
    vm.prank(victim);
    newCollateral.deposit(100e18, victim); // addToDepositTokensOfAccount reverts inside _mint

    // victim can no longer mint a synthetic they don't already have
    vm.expectRevert(UserReachedMaxTokens.selector);
    vm.prank(victim);
    newDebtToken.mint(victim, 1e18); // addToDebtTokensOfAccount reverts (combined length >= 30)
}
```

Note: the last `deposit` that would push the list over 30 reverts inside `_mint`, so the attacker should cap the fill at exactly `MAX_TOKENS_PER_USER - existingEntries` entries — sufficient to block all *new* token types. The scenario is reproducible on a fork of the deployed Base/mainnet pools; exact registered deposit-token count per pool determines how many attacker actions are needed (verify `p.getDepositTokens().length` and the victim's current `getDepositTokensOfAccount`/`getDebtTokensOfAccount` lengths).
