### Title
Unvalidated attacker-controlled array index in `ValidateMultiSign` precompile causes uncaught `ArrayIndexOutOfBoundsException` during TVM execution - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract parses raw call data supplied by the caller into a `DataWord[]` array and then uses an attacker-controlled offset word to index directly into that same array, without bounds-checking the index before dereferencing it. Unlike its sibling `BatchValidateSign`, this code path is not wrapped in a `try/catch`, so a crafted offset causes an unhandled `ArrayIndexOutOfBoundsException` to propagate out of `execute()`. This mirrors the libsoup `sniff_mp4` bug class: externally supplied, attacker-controlled data is used to index/parse a buffer without validating that the derived offset/length is within bounds, leading to a crash of the code path handling the request.

### Finding Description
`ValidateMultiSign.execute` parses `rawData` into fixed 32-byte words and then, when `VMConfig.allowTvmSelfdestructRestriction()` is enabled, computes an array index directly from attacker-supplied word `words[3]`: [1](#0-0) 

```
DataWord[] words = DataWord.parseArray(rawData);
...
if (VMConfig.allowTvmSelfdestructRestriction()) {
  int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
  ...
}
```

`words[3].intValueSafe() / WORD_SIZE` is fully attacker-controlled (any caller can set `words[3]` to an arbitrary value in the ABI-encoded call data). This value is used as an index into `words` with no bounds check (`words.length` is `rawData.length / WORD_SIZE`), so a value that is negative, zero, or larger than `words.length - 1` causes `ArrayIndexOutOfBoundsException` at line 1067. This statement executes *before* the `try { ... } catch (Throwable t) { ... }` block further down (lines 1082-1117), which only wraps the signature-recovery/weight-checking logic — the vulnerable indexing operation is unprotected.

This function is registered as a TVM precompiled contract, invoked by the `getContractForAddress` dispatch in the same file [2](#0-1) , and is reachable by any address that a smart contract `CALL`s to, including via `eth_call`/`triggerConstantContract`-style constant calls that require no fee and no broadcast.

The contrast with `BatchValidateSign` is instructive: it performs the analogous unbounded index computation (`words[words[1].intValueSafe() / WORD_SIZE]`) but its entire `execute()` body is wrapped in `try { return doExecute(data); } catch (Throwable t) { ... }`, so it safely degrades to a default return value. [3](#0-2) 

`ValidateMultiSign` lacks this protection.

### Impact Explanation
An unhandled `ArrayIndexOutOfBoundsException` thrown deep inside precompiled-contract execution propagates up through the TVM opcode dispatch and `Program`/`VMActuator` execution stack. If this call happens during real block-application (`Manager` processing a transaction from a block), an uncaught runtime exception escaping transaction execution risks aborting/breaking block application for that transaction stream, and if it happens on the constant-call/query path (`triggerConstantContract`, `eth_call`) it will crash that particular request handler at minimum. Given the crash originates from any contract's `CALL` to a fixed, unauthenticated precompile address, this is reachable by any anonymous API client or contract deployer, satisfying the "crash" impact criterion the scan is looking for (analogous to the libsoup NPE, which lets a remote party crash the client via crafted data).

### Likelihood Explanation
High. Triggering the vulnerable branch requires only: (1) `VMConfig.allowTvmSelfdestructRestriction()` enabled (an already-activated TVM feature flag in later java-tron chain configs), and (2) a `CALL`/constant-call to the `ValidateMultiSign` precompile address with a crafted `words[3]` offset value. No special permissions, balance, or state are required — the caller only needs to construct call data, which can be done via a plain `triggerConstantContract`/`eth_call` JSON-RPC/HTTP request, making this trivially reachable by an anonymous API client.

### Recommendation
Add explicit bounds validation before using any attacker-supplied word as an array index in `ValidateMultiSign.execute` (and audit `extractSigArray`/`extractBytesArray` similarly), e.g.:
```java
int sigOffset = words[3].intValueSafe() / WORD_SIZE;
if (sigOffset < 0 || sigOffset >= words.length) {
  return Pair.of(true, DATA_FALSE);
}
int sigArraySize = words[sigOffset].intValueSafe();
```
Alternatively/additionally, wrap the entire `execute()` body in `try { ... } catch (Throwable t) { return Pair.of(true, DATA_FALSE); }`, consistent with `BatchValidateSign`, so malformed input degrades gracefully instead of throwing.

### Proof of Concept
1. Deploy or use any contract that performs a low-level `CALL` (or use `eth_call`/`triggerConstantContract`) to the `ValidateMultiSign` precompiled contract address with ABI-encoded input where word[3] (the "signature array offset" word) is set to a value such that `words[3]/32` is negative or exceeds the total number of 32-byte words in the supplied data (e.g., set word[3] = `0xFFFFFFFF` or a very large positive value while keeping `rawData` short).
2. Send this as a constant call via the node's JSON-RPC/HTTP API (no fee/broadcast required) or embed it in a transaction that invokes the precompile.
3. Execution reaches `words[words[3].intValueSafe() / WORD_SIZE]` at PrecompiledContracts.java:1067 and throws `ArrayIndexOutOfBoundsException`, which is not caught anywhere in this call path, propagating out of `execute()` and up the TVM call stack for that request/transaction.
