### Title
Unauthenticated `RecvError` control message allows any off-path attacker to remotely tear down a victim's tunnel - (File: outside.go / interface.go)

### Summary
The external report describes an ownership-confusion bug: `RubiconRouter.offerWithETH()` registers the router contract as the offer's owner instead of the real caller, so `cancelForETH()` accepts a cancellation request from *anyone*, not just the true owner, and destroys/refunds the offer. The root cause is that a destructive "cancel" action is authorized against an identity that was never cryptographically tied to the real requester.

Nebula has an analogous flaw in its `RecvError` control message path: the handler that tears down a tunnel is reached and acts on unauthenticated, attacker-visible/spoofable data (a plaintext `RemoteIndex` plus the UDP source address), rather than anything cryptographically bound to the peer's certificate/session.

### Finding Description
In `readOutsidePackets`, `header.RecvError` is dispatched immediately after basic header parsing, before any decryption or hostmap/session validation: [1](#0-0) 

`handleRecvError` looks the sender-controlled `h.RemoteIndex` up in the reverse-index table and only checks that the UDP source address matches whatever the hostinfo's currently recorded remote is: [2](#0-1) 

`RemoteIndex` is not secret - it is embedded in cleartext in the header of every packet nebula ever sends for that tunnel (visible to any network observer, on- or off-path), and the "ownership" check that gates the destructive action (`closeTunnel` + `handshakeManager.DeleteHostInfo`) is nothing but a comparison against the peer's last-known UDP `AddrPort`, which is trivially spoofable over UDP. There is no certificate check, no MAC/AEAD validation, and no proof that the sender actually possesses the session keys for that tunnel — exactly the same class of failure as RubiconRouter's cancel path, which authorized a destructive action based on an identity value that was never proven to belong to the caller.

### Impact Explanation
An attacker who has observed a single packet exchanged between two nebula nodes (trivial for any passive on-path observer, or any node relaying/forwarding UDP traffic) learns the victim's `RemoteIndex`. The attacker can then send a single spoofed UDP packet with:
- Source address = the real peer's last-known `AddrPort` (spoofed, no reply needed — this is a blind/fire-and-forget attack)
- `header.RecvError` type and the harvested `RemoteIndex`

This causes the receiving node to immediately call `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, destroying a live, authenticated tunnel with no cryptographic proof of the sender's identity. This is a remote, unauthenticated (no CA-signed certificate required) denial-of-service / state-poisoning primitive against any established Nebula tunnel — directly matching the "remote state poisoning" / DoS impact category.

### Likelihood Explanation
- Reachability requires no CA-signed certificate and no successful handshake at all - the code path is hit before `Decrypt` or any hostinfo/cert check.
- The only two inputs needed (`RemoteIndex`, peer `AddrPort`) are both learnable by passively observing traffic between the victim and its peer (e.g., a compromised link, shared network segment, or any relay position), and UDP source-address spoofing for a blind send is a well-established low-cost attack.
- The check in `handleRecvError` (`hr.IsValid() && hr != addr`) is the *only* gate, and it degrades to no protection at all if the address is spoofed correctly.

### Recommendation
Do not act on `RecvError` (or any other pre-authentication control message) using only a plaintext index/address comparison. At minimum:
- Require `RecvError` handling to be tied to a MAC/AEAD-protected value (e.g., authenticate the error notification using the tunnel's established session keys instead of relying on cleartext index + address matching), or
- Rate-limit and heavily discount `RecvError`-triggered teardown, treating it only as a hint to retry a handshake rather than an authority to immediately delete hostinfo state, and
- Require corroborating evidence (e.g., a subsequent failed liveness/Test round-trip) before performing a destructive `DeleteHostInfo`/`closeTunnel`, since the current design conflates "sender is on the correct source address" with "sender possesses the session."

### Proof of Concept
1. Establish two nebula nodes A and B with a valid tunnel; observe (via passive sniffing on shared infrastructure, or by simply being one of the two nodes' upstream/relay path) any packet from B to A, and record the `RemoteIndex` field from the header (sent in cleartext) and A's currently known `AddrPort` for B (also observable/knowable via the lighthouse or previous traffic).
2. Craft a UDP datagram with header `Type = header.RecvError`, `RemoteIndex` = harvested index, and send it to A with a spoofed source address equal to B's `AddrPort`.
3. `readOutsidePackets` on A dispatches directly to `f.handleRecvError(via.UdpAddr, h)` [3](#0-2)  without any decryption/authentication.
4. `handleRecvError` finds the hostinfo via `QueryReverseIndex(h.RemoteIndex)`, sees `hr == addr` (spoofed match), and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)` [4](#0-3) , tearing down A's tunnel to B with no proof the attacker ever held B's session keys or certificate.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
