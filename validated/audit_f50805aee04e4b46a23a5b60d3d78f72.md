Audit Report

## Title
`add_tip` in Snowbridge inbound-queue-v2 lets any signed account write unbounded, unvalidated entries into `Tips` for nonces that may never exist - (File: `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`)

## Summary
`AddTip::add_tip` in `snowbridge-pallet-inbound-queue-v2` only checks `amount > 0` and that the nonce has not already been consumed (`!Nonce::<T>::get(nonce)`), then unconditionally inserts into the unbounded `Tips` storage map keyed by an attacker-supplied `u64` nonce, with no check that the nonce corresponds to a real, in-flight, or plausible-future message. [2](#0-1)  This is reachable end-to-end by any signed AssetHub account via `snowbridge-pallet-system-frontend::add_tip` → XCM `Transact` → `snowbridge-pallet-system-v2::add_tip`, which forwards to `InboundQueue::add_tip` without any relationship check between caller and nonce beyond `FrontendOrigin::ensure_origin`. [3](#0-2) [4](#0-3) 

## Finding Description
`Tips` is declared as an unbounded `StorageMap<_, Blake2_128Concat, u64, u128, OptionQuery>` with no cap on entries. [5](#0-4) 

The inbound `AddTip::add_tip` implementation validates only that the amount is non-zero and that the nonce is not already marked as consumed in `NonceBitmap` (via `Nonce::<T>::get(nonce)`); it does not check that the nonce is close to, or will ever be, an actual nonce assigned by a real Ethereum event: [2](#0-1) 

This is in clear contrast to `outbound-queue-v2`'s `AddTip::add_tip`, which requires the nonce to reference an *existing* `PendingOrders` entry (a message that was actually enqueued and assigned that nonce), rejecting any nonce with `AddTipError::UnknownMessage` if no such order exists: [6](#0-5) 

The only code path that removes an entry from `Tips` is `process_message`, called from `submit` after successful verification of an actual Ethereum event proof, and it `take`s the tip keyed by the real nonce contained in the verified message: [7](#0-6)  Inbound nonces are only ever consumed for messages that pass `T::Verifier::verify` against a genuine Gateway event log. [8](#0-7) 

The end-to-end reachable path is: any signed AssetHub account calls `SnowbridgeSystemFrontend::add_tip(message_id, asset)`, which swaps/burns an arbitrary nonzero fee asset and forwards a `Transact` XCM with a caller-chosen `message_id` (containing the nonce) to BridgeHub. [9](#0-8)  On BridgeHub, `EthereumSystemV2::add_tip` checks only `T::FrontendOrigin::ensure_origin(origin)`, which validates that the XCM originated from the frontend pallet's fixed location (`AllowFromEthereumFrontend`, i.e., AssetHub's frontend pallet index), not that the caller has any relationship to the specific nonce being tipped, then dispatches directly to `InboundQueue::add_tip(nonce, amount)`: [4](#0-3) [1](#0-0) 

Because the key space is the full `u64` range and there is no requirement that the nonce be currently in-flight or plausible, an attacker can call `add_tip` for arbitrary/never-to-arrive nonces (e.g., far beyond any nonce that will realistically be relayed), and each such call permanently inserts a `Tips` entry that can never be reclaimed by `process_message`, since that only occurs for the exact nonce of a message that actually arrives from Ethereum.

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" impact category. Each call costs the attacker only a minimal nonzero tip amount plus fixed extrinsic weight, yet permanently grows the `Tips` storage map on BridgeHub with no expiry, cap, or reaping mechanism, since removal is only triggered by actual message processing at that exact nonce. Repeated calls with distinct bogus/future nonces cause unbounded, low-cost storage growth in `pallet-inbound-queue-v2`'s state, inflating PoV weight and node storage over time without requiring any privileged, relayer, validator, or malicious-node capability.

## Likelihood Explanation
Likelihood is high. The path requires only a signed AssetHub account holding a minimal amount of any fee-eligible asset, and calls a fully public, documented, user-facing extrinsic (`SnowbridgeSystemFrontend::add_tip`). No governance, relayer, or validator collusion is needed. The discrepancy between the inbound (`Nonce`-consumed-only check) and outbound (`PendingOrders`-existence check) implementations of the same `AddTip` trait for the two sibling pallets strongly indicates this is an oversight rather than an intended design choice, since the outbound pallet demonstrates the correct guard pattern was known and implementable.

## Recommendation
In `snowbridge-pallet-inbound-queue-v2::AddTip::add_tip`, validate nonce plausibility before inserting into `Tips`, mirroring the outbound-queue-v2 existence check against `PendingOrders`. Since inbound nonces are not pre-registered like outbound `PendingOrders`, consider: rejecting nonces that are implausibly far ahead of the highest recently-observed nonce (bound the acceptable "future" window), and/or maintaining a bounded cap on the total number of outstanding `Tips` entries (rejecting or requiring a deposit/reaping mechanism once the cap is reached), so unprivileged callers cannot create unbounded, non-reclaimable persistent state.

## Proof of Concept
1. On AssetHub, as any signed, unprivileged account `attacker` holding a minimal balance of a fee-eligible asset, call `SnowbridgeSystemFrontend::add_tip(origin = signed(attacker), message_id = MessageId::Inbound(nonce), asset = Asset{ id: <fee asset>, fun: Fungible(1) })` for a `nonce` far beyond any nonce that will realistically be relayed from Ethereum (e.g., a value well beyond the current inbound nonce progression).
2. This is forwarded via `add_tip` XCM `Transact` to BridgeHub, where `EthereumSystemV2::add_tip` checks only `T::FrontendOrigin::ensure_origin` and dispatches to `InboundQueue::add_tip(nonce, amount)`.
3. `Tips::<T>::mutate(nonce, ...)` unconditionally inserts the entry (only `amount > 0` and "nonce not yet consumed" are checked) — no check exists that `nonce` corresponds to an actual pending/soon-to-arrive message, unlike `outbound-queue-v2`'s `PendingOrders::get(nonce).ok_or(...)` guard.
4. Repeat with many distinct bogus, never-to-arrive nonces at minimal per-call cost; each call permanently grows `Tips` storage since removal only happens via `process_message` for that exact nonce, which will never occur for a fabricated/never-relayed nonce. A Rust unit test in `inbound-queue-v2`'s test module calling `Pallet::<T>::add_tip(u64::MAX - 1, 1)` repeatedly, followed by asserting persistent growth of `Tips` with no corresponding `process_message` call, would reproduce this.

	impl<T: Config> Pallet<T> {
		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}
