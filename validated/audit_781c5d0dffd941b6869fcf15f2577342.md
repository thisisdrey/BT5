**Analysis:** The premise fails at multiple points in the checked pipeline:

1. **Banking ingestion already validates compute-budget before scheduling.** In `TransactionViewReceiveAndBuffer::try_handle_packet`, every packet is parsed and its `transaction_configuration(&working_bank.feature_set)` is computed; a failure returns `PacketHandlingError::ComputeBudget` and the packet is dropped before ever being inserted into the scheduling container. [1](#0-0) 

2. **Pre-execution bank checks re-validate compute budget before any SVM execution.** `Bank::check_age_and_compute_budget_limits` calls `tx.transaction_configuration(feature_set)` and turns a failure into a `TransactionError` (`invalid_compute_budget` counter incremented), which prevents the transaction from being executed at all — it never reaches `load_and_execute` / `execute_batch`'s successful-execution path. [2](#0-1) 

3. **`PrioritizationFeeCache::update` only ever receives fee-paying, already-committed transactions.** Both `Committer::commit_transactions` and `execute_batch` filter the transactions passed to `update` via `commit_result.was_fee_paying()`, meaning a transaction that failed the compute-budget/lock checks upstream would not be "fee paying" and would not reach `update` with a malformed compute-budget in the first place. [3](#0-2) [4](#0-3) 

The `transaction_configuration().is_err() || lock_result.is_err()` check inside `PrioritizationFeeCache::update` is redundant defense-in-depth that only affects fee-cache statistics (used for `getRecentPrioritizationFees` RPC estimates), not consensus, execution, or commitment. Since malformed-compute-budget transactions are rejected before scheduling (`receive_and_buffer.rs`) and again before execution (`check_age_and_compute_budget_limits`), the claimed call sequence "packet → sigverify only → execute_batch → PrioritizationFeeCache::update silently drops it" does not reflect the actual reachable path — sanitization beyond signature verification occurs at ingestion and pre-execution stages, not merely post-execution. No verification bypass, invalid recorded block, QoS evasion, or underpriced execution results from this decoupling.
