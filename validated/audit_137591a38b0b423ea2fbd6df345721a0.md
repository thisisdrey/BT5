### Title
Active permission holders can be granted authority over `AccountPermissionUpdateContract`, letting a lower-privilege "operator" key overwrite the account's Owner permission and rewrite/replace all other Active ("operator") keys - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
Tron's multi-sig model defines three permission tiers per account: `Owner` (id 0, full authority), `Witness` (id 1), and `Active` (ids 2-9, scoped by an `operations` bitmap to specific contract types) — analogous to the Vault's "admin" vs. "operator" roles. `AccountPermissionUpdateActuator` is the actuator responsible for creating/changing all three permission tiers, but nothing in its `validate()`/`execute()` path enforces that this specific, security-critical contract type may only be authorized by the `Owner` permission.

### Finding Description
Transaction authorization for any contract, including `AccountPermissionUpdateContract`, is decided purely by which `permission_id` the transaction specifies and whether the signer(s) meet that permission's weight/threshold — not by any contract-type-specific privilege rule: [1](#0-0) 

If `permissionId != 0` (i.e. an Active/"operator" key is used instead of Owner), the only extra check is `checkPermissionOperations`, which merely tests whether the bit for this contract's type is set in that Active permission's `operations` bitmap: [2](#0-1) 

`AccountPermissionUpdateActuator.validate()` itself performs the same generic bitmap check (`checkPermission`) against `dynamicStore.getAvailableContractType()` for every submitted `Active` permission, without special-casing `AccountPermissionUpdateContract` (protocol type 46) to require Owner-only authorization: [3](#0-2) 

Once validation passes, `execute()` unconditionally overwrites the account's Owner permission, Witness permission, and the entire list of Active permissions with whatever was supplied in the transaction: [4](#0-3) [5](#0-4) 

So if an account owner (intentionally, or by copying a template) enables the `AccountPermissionUpdateContract` bit in any Active permission's 32-byte `operations` field — which the codebase's own test explicitly demonstrates is representable/settable in the default bitmap encoding — that Active key ceases to be a scoped "operator" and instead gains the ability to unilaterally rewrite the Owner permission (replacing the true owner's keys), add or remove any other Active ("operator") permissions, and (for witness accounts) rewrite the Witness permission, all without any additional owner-level signature: [6](#0-5) 

This mirrors the reported Vault pattern exactly: a role meant to have narrower, delegated authority (`Active`/operator) is not structurally prevented from performing the privileged administrative action (updating the roles themselves), because the access-control check is generic (bitmap-based) rather than specific to the sensitive operation.

### Impact Explanation
An Active-permission key that is compromised, or that was scoped too broadly by an account operator, can seize full control of the account: overwrite the Owner permission with attacker-controlled keys, delete legitimate co-signers/operators from Active permissions, and (for SR accounts) hijack the Witness signing permission. This is a concrete unauthorized account takeover / privilege escalation with no path for the true owner to recover control after the transaction lands on-chain, matching the "High" impact class described in the source report.

### Likelihood Explanation
Exploitation requires that the targeted account's Active permission already has the `AccountPermissionUpdateContract` operation bit enabled — this is a configuration decision by the account owner (or default template usage), not enforced or restricted by protocol code. Given that `checkAvailableContractTypeCorrespondingToCode` demonstrates this bit is representable/available for Active permissions in the same bitmap that governs ordinary "operator" operations, any wallet/dApp/service that grants broad "all contract types" style Active keys (a common convenience pattern for multisig services) would be exposed. Likelihood is therefore dependent on real-world permission configuration but is not blocked by any protocol-level safeguard.

### Recommendation
Enforce that `AccountPermissionUpdateContract` can only be authorized via the account's `Owner` permission (`permission_id == 0`), regardless of what bits are set in any Active permission's `operations` field. This should be added as an explicit check in `AccountPermissionUpdateActuator.validate()` and/or in `TransactionCapsule.checkPermission`/`validateSignature`, so that permission-management transactions cannot be delegated to Active ("operator") keys the way ordinary scoped operations can.

### Proof of Concept
1. Account owner creates an Active permission (id 2) whose 32-byte `operations` bitmap includes the bit for `AccountPermissionUpdateContract` (type 46), alongside other intended operations, and assigns it to a co-signer/service key — a plausible configuration since the bitmap check treats this type like any other contract type: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java` lines 124-146.
2. The holder of that Active key crafts an `AccountPermissionUpdateContract` transaction with `Contract.Permission_id = 2` (their own Active permission), setting `owner` to a new `Permission` containing only their own key, and `actives` to a list that excludes the original legitimate signers.
3. `TransactionCapsule.checkPermission` (lines 635-645) allows the transaction because `permissionId != 0` only requires the Active permission to have the corresponding operation bit set — which it does.
4. `AccountPermissionUpdateActuator.execute()` calls `AccountCapsule.updatePermissions` (lines 1301-1320), overwriting the account's Owner permission and Active permission list with the attacker's supplied values, giving the former Active-key holder full/exclusive control of the account and permanently excluding the original owner and other operators.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
