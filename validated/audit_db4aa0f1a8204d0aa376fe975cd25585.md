### Title
Unbounded growth of DelegatedResourceAccountIndex entries lets an attacker make the `GetDelegatedResourceAccountIndexV2` API (and its underlying `getWithPrefix` reconstruction) run out of resources - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`DelegateResourceActuator.execute()` records every resource delegation by writing a new key-value pair into `DelegatedResourceAccountIndexStore` via `delegateV2()`, with no cap on how many distinct receiver addresses a single account may delegate to. `calcFee()` for this actuator returns `0`, so the only cost to the attacker is the bandwidth/energy of broadcasting the transactions plus a minimum 1 TRX of frozen balance that can be re-delegated to a new address, undelegated, and delegated again. Any later reconstruction of that account's index (`getV2Index`/`getWithPrefix`, exposed through the `GetDelegatedResourceAccountIndexV2` gRPC/HTTP API) must scan and sort every entry for that address, giving an attacker a cheap way to make this query arbitrarily expensive — the exact "unbounded loop / growth without limit" bug class described in the Multipool report, but landing here in an index rebuilt for every read instead of a fixed-size loop.

### Finding Description
`DelegateResourceActuator.validate()` and `execute()` contain no restriction on the number of unique `(owner, receiver)` delegation pairs an account can create: [1](#0-0) [2](#0-1) 

Each successful delegation calls `DelegatedResourceAccountIndexStore.delegateV2()`, which writes two new keys (`V2_FROM_PREFIX+from+to` and `V2_TO_PREFIX+to+from`) per delegation — the store never merges or bounds these entries: [3](#0-2) 

Whenever the account's full index is needed (e.g. via the public `getDelegatedResourceAccountIndexV2` API), `getV2Index()`/`getWithPrefix()` performs a `prefixQuery` over every key matching that address's prefix, materializes them into a `List`, and sorts by timestamp before returning: [4](#0-3) 

Because `validate()` never limits the count of distinct receivers and the actuator charges no fee (`calcFee()` returns 0), an attacker can cheaply grow this per-account index to an arbitrarily large size (limited only by bandwidth/energy costs of broadcasting many transactions, which is inexpensive), then trigger the expensive read path by querying `GetDelegatedResourceAccountIndexV2` for that address. This mirrors the Multipool bug class: an actor-controlled, unbounded list is iterated (here: scanned + sorted) inside a code path that untrusted parties can trigger.

### Impact Explanation
A full node serving `GetDelegatedResourceAccountIndexV2` (available over both gRPC `RpcApiService` and HTTP `GetDelegatedResourceAccountIndexV2Servlet`, reachable by any anonymous API client) can be forced to allocate and sort a very large in-memory list on every such query for the attacker-controlled address. Repeated or concurrent queries against such an address can consume excessive CPU/memory on the serving node, degrading or denying that API for legitimate users — matching the "API the node can no longer serve" impact criterion. Because the underlying `DelegatedResourceAccountIndexStore` entries persist in the chain state (written via a normal `DelegateResourceContract`), this growth is also replicated on every full/solidity node, so the DoS surface is not limited to a single node's cache.

### Likelihood Explanation
The path is reachable purely with a single account's signed transactions (`DelegateResourceContract`) and requires no privileged role, malicious SR/witness/committee, or network-level attack — only a modest amount of frozen bandwidth/energy (as little as 1 TRX) that can be repeatedly delegated to distinct receiver accounts and (optionally) recycled via `UnDelegateResourceContract`. `calcFee()` returning `0` for delegation removes the primary economic disincentive that limits how large the index can grow; the cost is bounded chiefly by transaction bandwidth, which is cheap to acquire. This makes the attack economically practical for a persistent low-cost actor, though building a sufficiently large index (millions of entries) to cause serious node-level resource exhaustion would still require sustained transaction volume, which moderates the likelihood to Medium rather than trivial/immediate.

### Recommendation
- Enforce a maximum number of distinct delegation receivers/senders per account (analogous to `MAX_VOTE_NUMBER` used in `VoteWitnessActuator`), rejecting further `DelegateResourceContract` transactions once the per-account index size exceeds the cap.
- Alternatively/additionally, paginate or cap the number of entries returned/scanned by `getWithPrefix()`/`getV2Index()`, and/or require the caller of `GetDelegatedResourceAccountIndexV2` to specify an offset/limit similar to `getPaginatedNowWitnessList`.
- Consider adding a minimal fee to `DelegateResourceActuator.calcFee()` (or a per-entry storage cost) proportional to the number of distinct receivers to disincentivize unbounded growth.

### Proof of Concept
1. Attacker account freezes the minimum resource (`FreezeBalanceV2Contract`) to obtain ≥1 TRX of delegatable bandwidth/energy.
2. Attacker repeatedly broadcasts `DelegateResourceContract` transactions delegating the minimum 1 TRX to N distinct, already-existing, non-contract receiver addresses (existing addresses can be reused/created cheaply); `calcFee()` charges nothing extra beyond normal bandwidth. [5](#0-4) 
3. Each call adds two entries to `DelegatedResourceAccountIndexStore` for the attacker's address with no upper bound check in `validate()`. [6](#0-5) 
4. Any client calls `GetDelegatedResourceAccountIndexV2` for the attacker's address; the node executes `getWithPrefix()`, performing an unbounded `prefixQuery` + sort over all N entries, consuming CPU/memory proportional to N on every invocation. [4](#0-3) 

Note: I was not able to directly inspect the `prefixQuery` implementations in `Chainbase.java`/`LevelDbDataSourceImpl.java`/`RocksDbDataSourceImpl.java` within the available search results to precisely quantify the per-entry cost or confirm the absence of any implicit range limit at the storage-engine level; this should be verified in a live/full-context review (e.g., a Devin session with full repository access) before finalizing severity.

  public void delegateV2(byte[] from, byte[] to, long time) {
    byte[] fromKey = Bytes.concat(V2_FROM_PREFIX, from, to);
    DelegatedResourceAccountIndexCapsule toIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(to));
    toIndexCapsule.setTimestamp(time);
    this.put(fromKey, toIndexCapsule);

    byte[] toKey = Bytes.concat(V2_TO_PREFIX, to, from);
    DelegatedResourceAccountIndexCapsule fromIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(from));
    fromIndexCapsule.setTimestamp(time);
    this.put(toKey, fromIndexCapsule);
  }

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
