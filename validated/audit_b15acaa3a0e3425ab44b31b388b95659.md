## Analysis Result

### Title
Eth-implicit wallet contract pays the relayer refund fee unconditionally, even when the emulated action fails - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `WalletContract::rlp_execute` entry point (callable by any unprivileged relayer account, not just accounts holding an access key on the wallet) fires a fee-refund `Transfer` promise to the calling relayer *before* the actual emulated base-token/ERC-20 transfer promise is even attempted, and that refund is not chained to (or reverted by) the outcome of the underlying action. This mirrors the FrankenDAO `castVote` bug class: a caller collects a payout that is supposed to be conditioned on a substantive action succeeding (a real vote / a real value transfer), but the runtime never actually verifies that the condition held before paying out.

### Finding Description
`inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330-410`) parses the user-signed Ethereum transaction, and, for `EOABaseTokenTransfer`/`ERC20Transfer` kinds with a non-zero `fee`, immediately creates an independent promise that transfers `fee` to `predecessor_account_id` (the relayer): [1](#0-0) 

This refund promise is **not** `.then()`-chained to the promise that performs the actual value movement (built later in the same function, e.g. via `action_to_promise(target, action)` at line 469, or the NEP-141 `storage_balance_of`/`storage_deposit`/`ft_transfer` chain at lines 433-458). The success/failure of the real transfer is only observed afterwards in `rlp_execute_callback` (`lib.rs:276-317`), which merely refunds the *caller's attached NEAR deposit* on failure — it does nothing to claw back or prevent the relayer fee that was already dispatched as a sibling receipt.

Consequently, the wallet's fee payment to the relayer is authorized purely by the presence of a valid signed Ethereum transaction with a non-zero fee field; it has no dependency on the wrapped Near action (transfer/FunctionCall) actually completing successfully.

### Impact Explanation
Because the fee-refund receipt is unconditional and independent of the outcome of the wrapped action, any relayer that submits (or is handed) a validly-signed emulated transfer/ERC-20 transfer whose underlying action is doomed to fail (e.g., insufficient token balance for `ft_transfer`, a receiver contract that rejects the call, a bad `storage_deposit` interaction, or any other failure surfaced only in `rlp_execute_callback`) still collects the fee out of the wallet's own NEAR balance, while the user's intended value transfer never happens. This is a concrete loss of funds from the eth-implicit account: NEAR leaves the wallet to pay for "service" that was never rendered, and it happens once per signed nonce (bounded by the in-flight-tx guard and nonce monotonicity), so it is a real, if per-transaction, drain rather than a repeatable unlimited exploit.

### Likelihood Explanation
Exploitation only requires an actor to relay a transaction whose failure is predictable to that actor before submission (e.g., a relayer that inspects the target token contract's balance/allowances or a receiver account's state before relaying). No signature forgery or access-key compromise is needed — the relayer is any account able to call `rlp_execute` as `predecessor_id`, which per the design doc is intentionally open to "any relayer" (`docs/DataStructures/Account.md:126-129`, `runtime/near-wallet-contract/.../lib.rs` comment at lines 367-373). The comment in the code even acknowledges "Relayers should also verify the fee before sending to make sure the user's signed transaction will refund enough to cover the relayer's gas costs" — showing the authors assumed honest relayers would only claim the fee for successful relays, but the contract does not enforce that assumption.

### Recommendation
Chain the relayer fee-refund transfer to the resolution of the emulated action's promise (e.g., dispatch it from within `rlp_execute_callback` only on `PromiseResult::Successful`, or attach it as a subsequent step of the same promise chain) instead of firing it eagerly and independently in `inner_rlp_execute`. This ensures the relayer fee is paid only when the wrapped action actually completed successfully.

### Proof of Concept
1. Deploy the wallet contract for an eth-implicit account `W` (as in `test_wallet_contract_interaction`/`test_base_token_transfer_with_relayer_refund`, `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/emulation.rs:132-200`).
2. User signs an Ethereum `ERC20Transfer` (or `EOABaseTokenTransfer`) with a non-zero `fee`, but for an amount/target guaranteed to fail on-chain (e.g., transferring more ERC-20 tokens than `W` actually holds, or to a receiver contract that will reject the `ft_transfer`/`storage_deposit` sequence).
3. A relayer (any account, e.g. `worker.root_account()`), aware the transfer will fail, calls `rlp_execute` with this signed transaction as in `rlp_execute_from(&relayer, receiver_id.as_str(), &signed_transaction, ...)`.
4. `inner_rlp_execute` fires the `fee` transfer to the relayer immediately (`lib.rs:381-384`); the subsequent `action_to_promise`/NEP-141 chain then fails, and `rlp_execute_callback` returns `success: false`.
5. Result: the relayer's balance increases by `fee` (as demonstrated by `final_relayer_balance` assertions in the existing tests) even though `W`'s intended token/asset transfer never took place — funds left `W` with no corresponding value delivered.
