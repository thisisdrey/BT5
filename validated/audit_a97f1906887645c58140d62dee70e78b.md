### Title
`process_delivery_receipt` ignores the `DeliveryReceipt.success` flag and unconditionally pays the relayer reward for failed Ethereum-side message execution - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` that carries a `success: bool` field describing whether the outbound message actually executed successfully on Ethereum, but the field is never checked before paying the relayer reward and permanently closing the pending order. [1](#0-0) [2](#0-1) 

### Finding Description
`submit_delivery_receipt` is a public, unprivileged, signed extrinsic. It verifies the Ethereum event log/proof (a genuine, correctly-verified log — no malicious prover is required) and decodes it into a `DeliveryReceipt`: [3](#0-2) 

`DeliveryReceipt` is decoded straight from the Ethereum `InboundMessageDispatched` event, which explicitly carries a `success` flag indicating whether the corresponding command execution on the Gateway contract succeeded or reverted: [4](#0-3) 

`process_delivery_receipt` then only validates the gateway address and that a `PendingOrder` exists for `receipt.nonce`. It never reads or enforces `receipt.success` before paying the reward and removing the order: [5](#0-4) 

This is structurally identical to the reported bug class: the contract/pallet stores an economically meaningful field (`tolerance` in the report, `success` here) that is intended to gate an irreversible payout, but the production code path that actually performs the payout never consults it. The `PendingOrder` struct persisted in storage doesn't even retain the `success`/completion semantics — only `nonce`, `fee`, `block_number` — so there is no way downstream to distinguish a genuinely delivered-and-executed message from one that reverted on Ethereum: [6](#0-5) 

Because the reward is paid and the order removed regardless of `success`, this violates the required invariant that "receipts and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." A relayer whose relayed transaction results in the Gateway emitting `success = false` (e.g. because the dispatched command reverted due to insufficient dispatch gas, an invalid payload accepted by the outbound queue's gas meter estimate, or any legitimate on-chain execution failure) still submits a wholly valid Merkle/beacon proof of that real event, and is unconditionally rewarded the full `order.fee` as if the message had executed correctly.

### Impact Explanation
This allows unbacked reward payout on BridgeHub for messages that did not actually execute successfully on Ethereum, i.e. relayer rewards decoupled from delivered value. Given a source of legitimately-failing commands (out-of-gas dispatch, revert conditions on the Gateway, etc. — none of which require a malicious relayer, prover, or validator, just a message whose execution fails for ordinary reasons), an attacker acting as an ordinary relayer can systematically farm relayer rewards for failed deliveries. This is a direct impact on the "duplicate settlement or payout" and "theft or unbacked mint or unlock" categories from the impact gate, since it settles (and permanently closes, via `PendingOrders::remove`) a payout that should not have been finalized.

### Likelihood Explanation
Likelihood is Medium: it requires no privileged actor, malicious peer, or compromised prover — any relayer submitting a genuine, correctly-proven Ethereum event for a message whose execution failed on Ethereum (`success = false`) triggers the flawed path. Command execution failures on Ethereum (insufficient dispatch gas relative to `GasMeter` estimate, reverts in downstream XCM execution) are a normal occurrence in bridge operation, not an exotic edge case, making the precondition realistically reachable.

### Recommendation
1. Add `ensure!(receipt.success, Error::<T>::DeliveryFailed)` (or an explicit failure-handling branch) in `process_delivery_receipt` before paying any reward.
2. If failed deliveries should still allow the pending order to be resolved (e.g., to unblock nonce processing or allow retry), separate "order resolution" from "reward payment": only call `T::RewardPayment::register_reward` when `receipt.success == true`; on failure, emit a distinct event (e.g. `MessageDeliveryFailed`) and handle fee refund/retry logic explicitly rather than silently paying the relayer.
3. Persist enough context in `PendingOrder` (e.g., topic/id) to allow reconciling receipts against the exact committed message, and cross-check `receipt.topic` against the original message identity for the given nonce.

### Proof of Concept
1. A message is enqueued and committed via `do_process_message`, creating `PendingOrders[nonce] = { nonce, fee, block_number }` with a non-zero `fee`. [7](#0-6) 
2. The message is relayed to Ethereum, and its dispatched command reverts/fails during execution on the Gateway (e.g., insufficient gas budget relative to the pallet's `GasMeter::maximum_dispatch_gas_used_at_most` estimate, or an unrelated execution-time revert). The Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid proof for this genuine event log and calls `submit_delivery_receipt(event)`. `T::Verifier::verify` succeeds (real proof, real log) and `DeliveryReceipt::try_from` decodes `success = false` correctly.
4. `process_delivery_receipt` checks only `receipt.gateway == GatewayAddress` and `PendingOrders::get(nonce).is_some()`; both pass. Because `receipt.success` is never read, `order.fee > 0` still triggers `T::RewardPayment::register_reward(&reward_account, ..., order.fee)`, and `PendingOrders::remove(nonce)` permanently closes the order. [8](#0-7) 
5. The relayer is paid the full fee for a message that never executed successfully on Ethereum, and the order can never be resubmitted or reconciled — an unbacked, non-reversible payout.

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
