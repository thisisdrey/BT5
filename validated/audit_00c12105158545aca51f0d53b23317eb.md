### Title
Hardened exchange-withdraw precision check assumes floor-division rounding stays within an arbitrary 0.01% band, permanently DoS'ing legitimate `ExchangeWithdrawContract` transactions - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The C4 finding flags a hardcoded 0.1% deviation assumption in `ethPerDerivative()` that always reverts once frxETH departs from a 1:1 peg with ETH, DoS'ing withdrawals. `ExchangeWithdrawActuator.doValidate()` contains an analogous baked-in assumption: when `allowHardenExchangeCalculation` is enabled, it recomputes `anotherTokenQuant` from the exchange pool ratio and rejects the transaction with `"Not precise enough"` if the floor-division result deviates from the precise (4-decimal) ratio by more than 0.0001 (0.01%) of `anotherTokenQuant`.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` computes `anotherTokenQuant` via integer `divideToIntegralValue`, then — only in the "hardened" code path — independently recomputes the same ratio with 4-decimal `BigDecimal` rounding and compares the two: [1](#0-0) 

If the relative difference between the integer-truncated result and the rounded decimal result exceeds `0.0001` (0.01%) of `anotherTokenQuant`, the transaction is rejected with `ContractValidateException("Not precise enough")`, permanently blocking that withdraw amount for that exchange pool state: [2](#0-1) 

This threshold is a fixed, hardcoded assumption about how close floor division and rounded division "should" be. For pools with small token balances or with `secondTokenBalance`/`firstTokenBalance` skewed heavily relative to `tokenQuant`, integer truncation naturally produces a relative error that can exceed 0.01% of a small `anotherTokenQuant`, exactly as in the report's peg-deviation scenario: a legitimate, non-malicious state (small pool balances, small withdraw amounts) causes the hardcoded tolerance check to always fail and revert.

The `allowHarden()` gate reads a chain-wide dynamic property, `getDynamicPropertiesStore().allowHardenExchangeCalculation()`, meaning once this feature is activated by proposal, every `ExchangeWithdrawContract` from any account (the exchange creator) routes through this rigid precision check: [3](#0-2) 

### Impact Explanation
Any account that is the creator of a `bancor`-style TRC10/TRX exchange pool (`ExchangeCapsule`) can be permanently blocked from withdrawing (`ExchangeWithdrawContract`) their own liquidity whenever the pool's token ratio and requested `tokenQuant` combination causes floor-division truncation to exceed the fixed 0.01% band. Since `anotherTokenQuant` is deterministically derived from on-chain pool state (`firstTokenBalance`, `secondTokenBalance`) plus the caller-supplied `tokenQuant`, and pool state changes with every `ExchangeInjectActuator`/`ExchangeTransactionActuator` call from arbitrary accounts, the creator has limited control over avoiding the trap — an attacker (or ordinary trading activity) can shift the pool into a ratio/precision state that makes the creator's specific withdraw request always fail this check, effectively freezing the creator's ability to withdraw liquidity of certain amounts.

### Likelihood Explanation
Reaching this code requires only: (1) the `AllowHardenExchangeCalculation` dynamic parameter being enabled via governance proposal (this is an already-supported, documented proposal in `ProposalUtil`/`ProposalService`), and (2) a normal, unprivileged `ExchangeWithdrawContract` broadcast by the exchange creator. No malicious SR/witness/peer behavior is needed — the DoS trigger is purely arithmetic rounding on attacker- or market-influenced pool balances, directly mirroring the "small margin causes revert on legitimate operation" mechanism in the reported frxETH issue.

### Recommendation
Remove or loosen the hardcoded 0.0001 (0.01%) precision-mismatch revert, or make the tolerance proportional to token decimal granularity/`tokenQuant` size rather than a flat percentage of `anotherTokenQuant`. Alternatively, always accept the integer floor-division result (which is what `execute()` actually applies) and drop the secondary decimal-based validation entirely, since it does not protect against manipulation but only introduces spurious reverts.

### Proof of Concept
1. Governance enables `AllowHardenExchangeCalculation` (chain-wide dynamic property).
2. An exchange pool exists with `firstTokenBalance`/`secondTokenBalance` such that, for a legitimate creator withdraw of `tokenQuant`, `bigSecondTokenBalance.multiply(bigTokenQuant).divideToIntegralValue(bigFirstTokenBalance)` truncates enough that the 4-decimal rounded value differs from the truncated integer by more than 0.01% of the truncated value (easily arranged with small balances/quant, e.g. `anotherTokenQuant` in the single digits).
3. Creator broadcasts `ExchangeWithdrawContract` with that `tokenQuant`.
4. `doValidate()` computes the two values as shown in `ExchangeWithdrawActuator.java:218-235`/`256-271`, finds the relative remainder exceeds `0.0001`, and throws `ContractValidateException("Not precise enough")`, rejecting the transaction and leaving the creator unable to withdraw that amount as long as the pool remains in that ratio.
