## Title
Reused/reverted account permission keys allow replay of previously-invalidated signed transactions - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` lets an account owner overwrite its owner/witness/active permissions (keys, threshold, operations) at any time with no restriction against reverting to a previously-used permission set, and TRON has no account-level nonce that would invalidate old signatures once a permission changes. Transaction validity instead relies solely on (1) an expiration timestamp and (2) checking the signature weight against whatever permission is *currently* stored for the account at the moment the transaction is processed. This reproduces the exact bug class from the external report: a transaction that was signed and momentarily became "invalid" due to a key/permission change can silently become valid again if the permission is later reverted to its prior state, and can then be broadcast/replayed by anyone who still holds a copy of it.

### Finding Description
`AccountPermissionUpdateActuator.execute()` directly overwrites the account's permissions with no history/blacklist check: [1](#0-0) 

Signature validation for any transaction is performed against whatever permission is currently in the `AccountStore` at the moment of processing — not the permission that existed when the transaction was signed: [2](#0-1) [3](#0-2) 

There is no per-account nonce. Replay protection is solely time-based via `checkExpiration`/`validateCommon`, and duplicate protection only rejects transactions that were *already included in a block* (via `TransactionCache`/`TransactionStore`), not transactions that were previously rejected due to signature/permission mismatch: [4](#0-3) [5](#0-4) [6](#0-5) 

A transaction that fails `validateSignature` (e.g., because the permission was changed after it was signed) is simply rejected from the pending pool / P2P propagation with a `ValidateSignatureException`; the transaction itself is never blacklisted or invalidated. Because expiration windows can be configured up to `trx.expiration.timeInMilliseconds` (default 60s) and up to `Constant.MAXIMUM_TIME_UNTIL_EXPIRATION`, the signed transaction remains "live" and re-broadcastable by any peer/anonymous client that retained a copy of it, via `broadcastTransaction`/`TransactionsMsgHandler.handleTransaction`: [7](#0-6) [8](#0-7) 

### Impact Explanation
If an account owner updates permissions (e.g., rotating out a suspected-compromised key) and later reverts to a previous permission set (e.g., undoing the rotation after determining it was a false alarm, or restoring from a backup config), any transaction that was signed under the original permission, broadcast, and rejected as invalid *during the interim* (because it required weight from keys no longer present) becomes valid again once the original permission returns. Since the transaction is not blacklisted, is still within its expiration window, and may already be cached by network peers or retained by the original signer/an observer, it can be resubmitted and executed unexpectedly — resulting in an unauthorized account operation (e.g., a transfer, permission change, resource delegation, or other TRON contract action) that the account owner believed was voided. This can cause unauthorized loss of funds/assets or unintended state changes.

### Likelihood Explanation
The precondition (an account owner reverting a permission update to a prior key set within the transaction's expiration window) is a plausible operational scenario (key-rotation mistakes, restoring from backup signer configuration, multi-sig quorum reshuffling). No special privilege beyond normal `AccountPermissionUpdateContract` submission (something account owners routinely do) is required, and the replaying party can be any unprivileged network participant who retained the previously-broadcast, previously-rejected transaction — this matches an "unprivileged transaction broadcaster" threat actor.

### Recommendation
- Introduce a monotonically increasing permission-version/nonce per account that is stored in the account and bound into the signature-verification hash (or checked in `TransactionCapsule.validateSignature`/`checkWeight`), so that any prior signature becomes permanently invalid once permissions change, even if a later update reverts to the same key material.
- Alternatively, in `AccountPermissionUpdateActuator.execute()`/`validate()`, maintain a per-account history/blacklist of previously used key sets and reject re-setting to any prior permission configuration.
- Add unit tests exercising: sign under permission P1 → change to P2 → attempt (and observe rejection of) the P1-signed transaction → revert to P1 → confirm the old transaction is still rejected.

### Proof of Concept
1. Account `A` has active permission `P1 = {keys: [K1], threshold: 1}`.
2. Attacker/observer captures a transaction `T` (e.g., a `TransferContract`) signed by `K1` under `P1`, broadcast via `broadcastTransaction`, with a default 60s expiration.
3. Before `T` is included in a block, the account owner submits `AccountPermissionUpdateContract` changing active permission to `P2 = {keys: [K2], threshold: 1}` (e.g. rotating away from a suspected leaked key `K1`). `T` is now rejected by `Manager.processTransaction`/`validateSignature` (`checkWeight` fails against `P2`), so it never lands in a block and the owner assumes it's void.
4. The owner submits another `AccountPermissionUpdateContract` reverting active permission back to `P1 = {keys: [K1], threshold: 1}` (e.g. after determining `K1` wasn't actually compromised), still within `T`'s expiration window.
5. The attacker/observer resubmits `T` via `broadcastTransaction`/`TransactionsMsgHandler`. `validateSignature` now succeeds against the restored `P1`, and `T` executes — even though the owner believed it had been voided in step 3.

  public static long checkWeight(Permission permission, List<ByteString> sigs, byte[] hash,
      List<ByteString> approveList)
      throws SignatureException, PermissionException, SignatureFormatException {
    long currentWeight = 0;
    if (sigs.size() > permission.getKeysCount()) {
      throw new PermissionException(
          "Signature count is " + (sigs.size()) + " more than key counts of permission : "
              + permission.getKeysCount());
    }
    HashMap addMap = new HashMap();
    for (ByteString sig : sigs) {
      if (sig.size() < 65) {
        throw new SignatureFormatException(
            "Signature size is " + sig.size());
      }
      String base64 = TransactionCapsule.getBase64FromByteString(sig);
      byte[] address = SignUtils
          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
      if (weight == 0) {
        throw new PermissionException(
            ByteArray.toHexString(hash) + " is signed by " + encode58Check(address)
                + " but it is not contained of permission.");
      }
      if (ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)) {
        base64 = encode58Check(address);
      }
      if (addMap.containsKey(base64)) {
        throw new PermissionException(encode58Check(address) + " has signed twice!");
      }
      addMap.put(base64, weight);
      if (approveList != null) {
        approveList.add(ByteString.copyFrom(address)); //out put approve list.
      }
      currentWeight += weight;
    }
    return currentWeight;
  }

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
