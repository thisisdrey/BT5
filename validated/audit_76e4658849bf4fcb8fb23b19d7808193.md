### Title
Permanent cross-repository partition-assignment poisoning blocks legitimate fork/create operations - ([File: internal/gitaly/storage/storagemgr/partition_assigner.go])

### Summary
Gitaly's WAL-enabled storage manager assigns every repository a `PartitionID` the first time it is targeted by a repository-creation-capable RPC, and persists that assignment immediately and independently of whether the triggering RPC/transaction ultimately succeeds. An ordinary user who can direct a cheap, failing (or otherwise abandoned) repository-creation request at a target relative path — the same way `depositFor(victim, 0, duration)` cheaply set `_unlockTime` for a victim in the St1inch report — can pre-assign a "standalone" partition ID to that path. When the legitimate owner later performs a pooled operation on the same path (e.g. `CreateFork`, which links the new repository into the same partition as its origin/pool via `partitionWithRelativePath`), the mismatch between the pre-existing assignment and the newly computed hint permanently blocks the legitimate operation.

### Finding Description
`partitionAssigner.getPartitionID` ( [1](#0-0) ) computes a `partitionHint` from an "additional" relative path (the origin/pool repository for forks or object pools) and then resolves the target repository's own partition via `getPartitionIDRecursive`. If the target relative path was already assigned into a *different* partition than the hint, the call fails outright with `ErrRepositoriesAreInDifferentPartitions`: [2](#0-1) 

Crucially, partition assignment for a not-yet-existing repository is explicitly allowed for repository-creation requests: [3](#0-2) 

and the assignment write is committed to the key-value store immediately via a standalone write batch, decoupled from the outcome of the surrounding WAL transaction/RPC: [4](#0-3) [5](#0-4) 

This mirrors the St1inch bug class exactly: a cheap, minimal-cost call (`depositFor(victim, 0, duration)`) that only needs to touch a shared per-account/per-path invariant is enough to durably alter state for a target that the caller does not own, and a later, legitimate operation on that same target is rejected because of a hard invariant check (`ChangeAmountAndUnlockTimeForExistingAccount` in St1inch vs. `ErrRepositoriesAreInDifferentPartitions` in Gitaly) that has no path to reconcile or override the earlier, illegitimate state.

Concretely:
1. An attacker knows (or can predict/observe) the relative path `P` that a victim intends to use for a forked or pooled repository — this is analogous to the "crafted RPC field" vector, since Gitaly RPCs do not themselves verify higher-level ownership of `P`; that check happens above Gitaly (e.g., in Rails) but the relative path is nonetheless a value the calling layer supplies per-request and is reachable purely via RPC input.
2. The attacker issues a plain (non-pooled) repository-creation RPC targeting `P` with no `partitionWithRelativePath`/alternate set. This is enough to trigger `getPartitionIDRecursive` and permanently persist a standalone `PartitionID` for `P` in `partitionAssignmentTable`, even if the RPC subsequently fails or is aborted for any unrelated reason (the assignment write already flushed to the KV store before the surrounding transaction commits or rolls back).
3. The victim's legitimate `CreateFork`/pooled-repository RPC for the same path `P` computes a partition hint from the origin/pool repository. Because `P` is already bound to the attacker's standalone partition, the hint mismatch check trips and the legitimate creation is permanently denied with `ErrRepositoriesAreInDifferentPartitions` — there is no self-healing or remediation path in this code.

### Impact Explanation
This is a low-cost, one-shot Denial-of-Service against Gitaly's repository/fork-creation path: a single crafted or racing creation attempt from any client that can direct a relative-path parameter is enough to poison the storage-layer partition table for that path, permanently and irrecoverably (short of manual operator intervention on the key-value store) preventing legitimate pooled/fork creation there — directly analogous to how a single frontrun `depositFor(victim, 0, X)` call permanently blocks the victim's `withdraw`/`withdrawTo`.

### Likelihood Explanation
Exploitability depends on the attacker being able to target the exact relative path the victim will later use for a pooled repository/fork before the victim's legitimate request lands — a race or path-prediction condition, similar in spirit to the original frontrunning report. Within Gitaly's own trust boundary this is straightforward: the relative path is just an RPC field with no built-in ownership check inside `partition_assigner.go`, and any repository-creation code path (`isRepositoryCreation == true`) triggers the durable assignment regardless of ultimate RPC success.

### Recommendation
Do not persist a partition assignment as a side effect of a repository-creation attempt that later fails or never completes; tie the `partitionAssignmentTable.setPartitionID` write to the actual, successful creation of the repository (e.g., perform it transactionally as part of WAL commit, or verify the repository was actually created on disk before finalizing the assignment). Additionally, consider re-validating/allowing re-assignment for relative paths that were assigned but where the corresponding repository was never actually created, so a later legitimate pooled-creation request is not permanently blocked by an orphaned assignment.

### Proof of Concept
Not independently executable from the index alone (requires a running Gitaly WAL-enabled cluster to demonstrate ordering); the control flow supporting the PoC is fully shown above:
1. Attacker calls a repository-creation RPC (e.g. `CreateRepository`) targeting relative path `P` with no pool/alternate, causing `partitionAssigner.assignPartitionID` to persist a standalone `PartitionID` for `P` via `partitionAssignmentTable.setPartitionID` — this happens even if the attacker's overall RPC subsequently errors out (e.g., invalid seed data), because the assignment write is a separate, already-flushed KV write (`internal/gitaly/storage/storagemgr/partition_assigner.go:290-315`, `80-91`).
2. Victim calls `CreateFork` (or any pooled-repository-creating RPC) targeting the same relative path `P`, supplying the origin/pool repository as `partitionWithRelativePath`.
3. `getPartitionID` (`internal/gitaly/storage/storagemgr/partition_assigner.go:156-190`) computes `partitionHint` from the origin/pool, then resolves `P`'s already-persisted (attacker-set) partition, finds a mismatch, and returns `ErrRepositoriesAreInDifferentPartitions`, permanently denying the victim's legitimate fork/create request for `P`.

Note: I was not able to fully trace, within the indexed portions of the codebase, the exact gRPC-layer wiring that maps a specific externally reachable RPC's target/additional-repository fields into `isRepositoryCreation`/`partitionWithRelativePath` in `middleware.go`, since the middleware file's relevant logic was only partially visible in the final search results. A Devin session with full repository access would be needed to confirm the precise RPC(s) and required request shape to trigger this end-to-end.

func (pt *partitionAssignmentTable) setPartitionID(relativePath string, id storage.PartitionID) error {
	wb := pt.db.NewWriteBatch()
	if err := wb.Set(pt.key(relativePath), id.MarshalBinary()); err != nil {
		return fmt.Errorf("set: %w", err)
	}

	if err := wb.Flush(); err != nil {
		return fmt.Errorf("flush: %w", err)
	}

	return nil
}

func (pa *partitionAssigner) getPartitionID(ctx context.Context, relativePath, partitionWithRelativePath string, isRepositoryCreation bool) (storage.PartitionID, error) {
	var partitionHint storage.PartitionID
	if partitionWithRelativePath != "" {
		var err error
		// See if the target repository itself is already in a partition. If so, we should assign the other repository
		// in the same partition if it is not yet partitioned.
		if partitionHint, err = pa.partitionAssignmentTable.getPartitionID(relativePath); err != nil {
			if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
				return 0, fmt.Errorf("get possible partition id: %w", err)
			}

			// There was no assignment.
			partitionHint = 0
		}

		// Get or assign the alternate into a partition. If the target repository was already assigned into a partition,
		// assign the alternate in the same partition. The hinted repository should always exist already as it is an object pool, or
		// the origin repo of a fork.
		if partitionHint, err = pa.getPartitionIDRecursive(ctx, partitionWithRelativePath, false, partitionHint, false); err != nil {
			return 0, fmt.Errorf("get additional relative path's partition ID: %w", err)
		}
	}

	// Get the repository's partition, or assign if it yet wasn't assigned, assign it with the alternate.
	ptnID, err := pa.getPartitionIDRecursive(ctx, relativePath, false, partitionHint, isRepositoryCreation)
	if err != nil {
		return 0, fmt.Errorf("get partition ID: %w", err)
	}

	if partitionHint != 0 && ptnID != partitionHint {
		return 0, ErrRepositoriesAreInDifferentPartitions
	}

	return ptnID, nil
}

func (pa *partitionAssigner) assignPartitionID(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID) (storage.PartitionID, error) {
	// Check if the repository has an alternate. If so, it needs to go into the same
	// partition with it.
	ptnID, err := pa.getAlternatePartitionID(ctx, relativePath, recursiveCall, partitionHint)
	if err != nil {
		if !errors.Is(err, gitstorage.ErrNoAlternate) {
			return 0, fmt.Errorf("get alternate partition ID: %w", err)
		}

		ptnID = partitionHint
		if ptnID == invalidPartitionID {
			// The repository has no alternate. Unpooled repositories go into their own partitions.
			// Allocate a new partition ID for this repository.
			ptnID, err = pa.allocatePartitionID()
			if err != nil {
				return 0, fmt.Errorf("acquire partition id: %w", err)
			}
		}
	}

	if err := pa.partitionAssignmentTable.setPartitionID(relativePath, ptnID); err != nil {
		return 0, fmt.Errorf("set partition: %w", err)
	}

	return ptnID, nil
}
