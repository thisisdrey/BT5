Audit Report

## Title
Relayer reward is paid on Snowbridge outbound delivery even when Ethereum dispatch failed - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`process_delivery_receipt` decodes a `DeliveryReceipt` containing a `success: bool` field from an authentically verified `InboundMessageDispatched` Ethereum event log, but never checks this field before paying the relayer reward. The payout gate only checks `order.fee > 0`, so relayers are paid the full fee even when the dispatched message reverted on the Ethereum Gateway contract.

## Finding Description
`DeliveryReceipt` is decoded from the `InboundMessageDispatched` Solidity event, capturing `success` directly from the on-chain log: [1](#0-0) . The decode implementation in `TryFrom<&Log>` faithfully copies `event.success` into the struct field without any further use: [2](#0-1) .

The `submit_delivery_receipt` extrinsic is public and unprivileged (any signed account can call it), verifies the log via `T::Verifier::verify`, decodes the receipt, and forwards it to `process_delivery_receipt`: [3](#0-2) .

`process_delivery_receipt` checks the gateway address and looks up the `PendingOrder` by nonce, but the only condition gating the reward payout is `order.fee > 0` — `receipt.success` is not referenced anywhere in this function: [4](#0-3) .

The `PendingOrder` stored during message commitment only tracks `nonce`, `fee`, and `block_number` — there is no separate success/failure accounting: [5](#0-4) .

Because the log is genuinely emitted by the Gateway contract on any command execution outcome (the Solidity event includes `success` precisely to distinguish dispatch outcomes), a `success=false` event is legitimate on-chain data, not a forged or malicious value — the pallet simply fails to bind this authentic value into the payout invariant.

## Impact Explanation
This matches the "duplicate settlement or payout" / broken invariant class described in the impact gate: message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically. Here, `T::RewardPayment::register_reward` is invoked with the full `order.fee` regardless of whether the corresponding Ethereum-side dispatch actually succeeded, letting relayers collect full rewards for messages that produced no successful cross-chain effect, degrading the bridge's incentive design and draining the reward pool.

## Likelihood Explanation
High likelihood: `submit_delivery_receipt` is a public, unprivileged extrinsic callable by any signed account holding a valid delivery proof, no privileged or malicious-actor assumption is required, and the underlying `success=false` log is authentic (emitted by the real Gateway contract whenever a dispatched command reverts, e.g., due to insufficient gas or a reverting downstream command). This makes the issue reachable via ordinary bridge usage, not merely via a compromised relayer.

## Recommendation
Gate reward payment on `receipt.success`. On `success == false`, either withhold the full reward, pay a reduced gas-refund amount, or route the fee through a distinct failure-handling path rather than unconditionally calling `T::RewardPayment::register_reward` with `order.fee`. Add a unit test asserting that a `success=false` receipt does not result in full reward payout.

## Proof of Concept
1. A message is committed via `do_process_message`, creating a `PendingOrder` with a nonzero `fee`.
2. The relayer delivers the message to the Ethereum Gateway; execution reverts and the contract emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer submits this authentic proof via `submit_delivery_receipt`; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success: false` correctly.
4. `process_delivery_receipt` proceeds to call `T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee)` unconditionally since only `order.fee > 0` is checked [6](#0-5) .
5. The relayer receives the full reward despite the message failing to execute on Ethereum.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
