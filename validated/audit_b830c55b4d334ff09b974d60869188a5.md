### Title
Witness brokerage (commission) fee silently rounds down to 0 for small per-transaction rewards - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.payReward()` computes a Super Representative's brokerage commission using floating-point arithmetic and truncates it to a `long`. When the reward `value` passed in (in particular the per-transaction fee reward paid via `payTransactionFeeReward`) is small enough relative to the brokerage rate, `brokerageAmount` truncates to `0`, so the SR receives no commission on that reward chunk and the entire value is instead credited to the voter reward pool. Because transaction fees are attacker/user controlled (any transaction broadcaster picks the fee paid, and this fee is paid to the block-producing witness), this is directly analogous to the reported `Allo.sol` issue where a percentage-based fee computed via truncating division/rounding is bypassed by using small amounts, and the effect compounds by repeating the action many times.

### Finding Description
`payReward()` is implemented as: [1](#0-0) 

```
private void payReward(byte[] witnessAddress, long value) {
  long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
  int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
  double brokerageRate = (double) brokerage / 100;
  long brokerageAmount = (long) (brokerageRate * value);
  value -= brokerageAmount;
  delegationStore.addReward(cycle, witnessAddress, value);
  adjustAllowance(witnessAddress, brokerageAmount);
}
```

This method is invoked both from `payBlockReward()` and `payTransactionFeeReward()`: [2](#0-1) 

`payTransactionFeeReward(witnessAddress, value)` is called from `Manager.java` while processing each transaction's fee payout to the block-producing witness (`Manager.java` references `payTransactionFeeReward`), meaning `value` is the (attacker-selectable) transaction fee actually paid for a single broadcast transaction, not an aggregate over the block/cycle.

Because `brokerageRate = brokerage / 100.0` (e.g. `0.2` for 20%) and `brokerageAmount = (long)(brokerageRate * value)` truncates towards zero, any `value` where `brokerageRate * value < 1` produces `brokerageAmount == 0`. For a witness with a `brokerage` of e.g. 20 (20%), any transaction fee below 5 SUN yields zero brokerage; more generally, the minimum fee needed for a nonzero brokerage cut is `ceil(1 / brokerageRate)` SUN. An unprivileged transaction broadcaster fully controls the fee amount charged per transaction (bandwidth/energy fee), so a user (or a colluding SR economically incentivized to minimize its own “tax” being skimmed, or simply due to protocol design flaw) can cause the SR to receive `0` brokerage on many small-fee transactions where a proportional share was actually due, systematically diverting funds that should go to the witness's own allowance into the voter reward pool instead (`delegationStore.addReward`), one truncation at a time.

This mirrors the `Allo.sol` bug class exactly: a percentage fee computed via a truncating operation on a per-call basis, which can be driven to zero by choosing (or repeating) sufficiently small input amounts, defeating the intended fee/commission mechanism cumulatively across many calls.

### Impact Explanation
Impact is confined to a systematic misallocation of SR commission revenue rather than any user's principal balance being stolen or the chain halting. Each individual transaction's misallocated amount is at most a few SUN, but the flaw is structural: it applies to every transaction fee payout on every block, indefinitely, for every witness with `brokerage > 0`, meaning the aggregate value siphoned away from witnesses' commission into the shared reward pool over time could be non-trivial. This does not create unbacked balance or double-spend (the total value paid is conserved, just split incorrectly between the SR allowance and the delegator pool), so it is best characterized as a reward-accounting/fund-misallocation bug rather than fund creation, keeping it at Medium severity — analogous to the referenced report's Medium rating for `Allo.sol`.

### Likelihood Explanation
High likelihood of occurrence in normal operation: transaction fees for simple TRC10/TRX transfers or low-resource-usage calls are commonly a small number of SUN, well within the range that truncates brokerage to 0 for typical brokerage rates (default is 20, per `DelegationStore.DEFAULT_BROKERAGE = 20`). No special privilege is needed — every ordinary user transaction that pays a small fee to the current witness triggers this code path via block processing. [3](#0-2) 

### Recommendation
Avoid floating point and per-call truncation for brokerage calculation. Compute `brokerageAmount` using integer math consistently (e.g., `value * brokerage / 100` using `long`/`BigInteger` with a single truncation), and/or accumulate the fractional remainder across calls (carry-over remainder pattern) so that small repeated payments still converge to the correct proportional brokerage over time, similar to how `DelegationStore.DECIMAL_OF_VI_REWARD`-scaled fixed-point math is used elsewhere in the reward pipeline (e.g., `RewardViCalService.accumulateWitnessVi`). [4](#0-3) 

### Proof of Concept
1. Assume a witness has `brokerage = 20` (20%) for the current cycle (`DelegationStore.getBrokerage` default is `DEFAULT_BROKERAGE = 20`).
2. An unprivileged user broadcasts a transaction whose net/energy fee charged is, say, `4` SUN, which is credited to the block-producing witness via `Manager` calling `mortgageService.payTransactionFeeReward(witnessAddress, 4)`.
3. Inside `payReward`: `brokerageRate = 0.2`; `brokerageAmount = (long)(0.2 * 4) = (long)(0.8) = 0`.
4. The full `4` SUN is added to `delegationStore.addReward(cycle, witnessAddress, 4)` (the shared voter pool), and `adjustAllowance(witnessAddress, 0)` gives the witness nothing, even though 20% (0.8 SUN, rounding to at least some nonzero share over many repetitions) was economically due.
5. Repeating step 2 across many small-fee transactions across a cycle causes the witness's commission to be repeatedly truncated to zero, cumulatively diverting the SR's due commission into the delegator reward pool. [1](#0-0)

  private void accumulateWitnessVi(long cycle, byte[] address) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long voteCount = getWitnessVote(cycle, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
