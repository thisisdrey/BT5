### Title
Unbounded, uncapped `DelegatedResourceAccountIndexCapsule` list growth enables a delegation-based DoS on any resource delegatee - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
The reported bug is a `MAX_DELEGATES`-capped-but-still-too-large array causing gas exhaustion on victim operations in a HyperEVM voting-escrow contract. The java-tron analog is stronger: when the chain has not enabled the `AllowDelegateOptimization` proposal, `FreezeBalanceActuator.delegateResource` (and `UnfreezeBalanceActuator`'s corresponding cleanup path) store delegation relationships as unbounded `repeated ByteString` lists inside a single `DelegatedResourceAccountIndexCapsule` record — with **no size cap at all**, unlike the reported contract's (still-too-generous) 1024 cap.

### Finding Description
Any unprivileged account can call `FreezeBalanceContract` with `receiverAddress` set to an arbitrary victim address to delegate bandwidth/energy. In the legacy (non-optimized) code path, `FreezeBalanceActuator.delegateResource` appends the counterparty address into the victim's `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList`: [1](#0-0) 

This capsule is a single protobuf record (`repeated bytes to_accounts` / `repeated bytes from_accounts`) with no `MAX_DELEGATES`-style limit enforced anywhere in `DelegatedResourceAccountIndexCapsule`: [2](#0-1) 

Because `delegateResource` runs for any amount (as small as the minimum freeze amount) from any number of distinct throwaway sender addresses, an attacker can grow a victim's `fromAccountsList` without bound, cheaply, from many different accounts. Every subsequent unfreeze against that account must locate and mutate this same list with linear scan/rebuild operations: [3](#0-2) 

Additionally, once/if `AllowDelegateOptimization` is enabled via governance, `DelegatedResourceAccountIndexStore.convert()` is invoked from `delegateResource`/unfreeze paths to migrate any pre-existing legacy list into the new per-entry key format — and this migration iterates the **entire** old list synchronously inside a single transaction's execution: [4](#0-3) 

Unlike the analogous `UnfreezeBalanceV2Actuator`/`AccountCapsule.getUnfreezingV2Count`, which the codebase enforces with a bounded `UNFREEZE_MAX_TIMES` limit for the newer V2 unfreeze-request list, there is no equivalent bound anywhere for the legacy `DelegatedResourceAccountIndex` lists. This is confirmed by `FreezeBalanceActuatorTest.testMultiFreezeDelegatedBalanceForBandwidth`, which demonstrates the list simply keeps growing and being persisted/read back without any cap check: [5](#0-4) 

None of these operations charge energy/bandwidth proportional to list size (`FreezeBalanceActuator.calcFee()` returns 0), so the attacker's cost of growing the list is flat regardless of victim list size, while the victim's (and every full node's) cost of processing subsequent unfreeze/delegate/convert operations on that account grows linearly (or worse, when `convert()` fires) with the number of accumulated delegations.

### Impact Explanation
An attacker can force unbounded growth of a victim's `DelegatedResourceAccountIndexCapsule`, causing:
- Increasing CPU/serialization cost on every node applying blocks containing operations against the victim address (`UnfreezeBalanceActuator`, `FreezeBalanceActuator`, and the one-time `convert()` migration), which is single-threaded synchronous block application in `Manager`.
- Potential prolonged or effectively failing transactions for the victim trying to unfreeze/withdraw/delegate, since there is no corresponding gas/energy metering to bound this cost, and no protocol-level cap analogous to `MAX_DELEGATES`.
- This can escalate to node performance degradation/slow block application under adversarial delegation flooding, which is a network-wide availability concern reachable purely through unprivileged `FreezeBalanceContract` broadcasts.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the attacker to fund many small freeze/delegate transactions (bandwidth/energy cost only, no large capital required since minimum freeze amounts are small), and the severity scales with how many accounts execute the legacy (non-`AllowDelegateOptimization`) path, or trigger `convert()` after a large pre-existing legacy list. On networks/testnets that have not activated `AllowDelegateOptimization`, this path is always live.

### Recommendation
- Enforce an explicit maximum count (analogous to `MAX_DELEGATES`) on `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` in `FreezeBalanceActuator.delegateResource`, rejecting new delegations once the cap is reached.
- Bound the work performed by `DelegatedResourceAccountIndexStore.convert()` per transaction (e.g., process in chunks or reject/queue conversion when the legacy list exceeds a safe size), rather than iterating an attacker-inflatable list synchronously within a single actuator execution.
- Consider charging bandwidth/energy proportional to list size for delegate/unfreeze operations touching these lists, so the cost is not asymmetric between attacker and victim/network.

### Proof of Concept
1. Deploy/observe a java-tron network where `AllowDelegateOptimization` proposal is not enabled (legacy path active), or is enabled but the victim account already carries the old-format index that will later hit `convert()`.
2. From N distinct funded accounts, each freeze a minimal amount of TRX with `FreezeBalanceContract.receiver_address` set to the victim address, invoking `FreezeBalanceActuator.delegateResource` each time and appending to the victim's `fromAccountsList` (as shown reachable in `FreezeBalanceActuatorTest.testMultiFreezeDelegatedBalanceForBandwidth`, which builds a list of over 100 entries with no rejection).
3. Repeat with large N (thousands+) — no cap check anywhere prevents this.
4. Have the victim attempt `UnfreezeBalanceContract`/`DelegateResourceContract`/enable `AllowDelegateOptimization` (triggering `convert()`); observe processing time/cost scale linearly with the attacker-inflated list, with no compensating energy/bandwidth charge to the attacker.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
