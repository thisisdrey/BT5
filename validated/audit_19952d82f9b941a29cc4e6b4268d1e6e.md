### Title
Stale `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` entries survive `remove_account`, allowing a pre-deletion promise to execute privileged actions against a later-recreated account of the same name - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` (`core/store/src/utils/mod.rs:505-575`) purges `Account`, `ContractCode`, access/gas keys and `ContractData`, but never removes `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount` entries for the account being deleted. If the account had an outstanding action receipt with unmet `input_data_ids` at the time `DeleteAccount` executed, that postponed receipt (and its `receiver_id`-keyed linkage) is left in the trie after the account is gone. When the same account name is later recreated and the missing `DataReceipt` eventually arrives, `process_receipt`/`apply_action_receipt` will execute the stale receipt's actions (e.g. `AddKey`, `DeployContract`, `Stake`) against the new account, because `check_actor_permissions` (`runtime/runtime/src/actions.rs:753,762`) only compares `actor_id != account_id` as plain `AccountId` strings, with no notion of account "generation"/identity across deletion and recreation.

### Finding Description
- `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) stores an incoming action receipt as postponed when any `input_data_ids` is unmet: it writes `TrieKey::PostponedReceiptId{receiver_id, data_id}` for each missing id, `TrieKey::PendingDataCount{receiver_id, receipt_id}`, and `set_postponed_receipt` → `TrieKey::PostponedReceipt{receiver_id, receipt_id}` (`core/store/src/utils/mod.rs:120-127`).
- `action_delete_account` (`runtime/runtime/src/actions.rs:314-389`) calls `remove_account(state_update, account_id)` (line 371) and then sets `*account = None`. `remove_account` (`core/store/src/utils/mod.rs:505-575`) removes only `Account`, `ContractCode`, `AccessKey`/gas-key-nonce entries, and `ContractData`. It never scans for or removes `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` keys tied to `account_id` as `receiver_id`.
- `check_actor_permissions` gates `AddKey`, `DeployContract`, `Stake`, `DeleteKey`, `DeployGlobalContract`, `UseGlobalContract`, `WithdrawFromGasKey`, and `DeleteAccount` on `actor_id == account_id` (`runtime/runtime/src/actions.rs:750-768`), a bare string comparison with no binding to a specific account "incarnation" (no creation nonce/hash is checked).
- Later, when a `Data` receipt for the dangling `data_id` arrives, `process_receipt` (`runtime/runtime/src/lib.rs:1367-1474`) looks up `TrieKey::PostponedReceiptId{receiver_id: account_id, data_id}` — which is still present — decrements `PendingDataCount`, and once it hits zero, fetches and executes the surviving `ready_receipt` via `apply_action_receipt`, with no re-validation tying the receipt to the account state that existed when it was created.
- Since `actor_id` is derived from `receipt.predecessor_id()` (`runtime/runtime/src/lib.rs:855`) captured inside the *original* postponed receipt, and the receiver account has meanwhile been fully replaced (new keys, new owner, new storage), a receipt originally authorized against the old account's identity is executed with full privilege against the new account, purely because the account-name string still matches.
- Nothing in the deletion or account-creation path invalidates or re-derives these queue keys; `action_create_account` (`runtime/runtime/src/actions.rs:167-` ) only validates naming rules and account non-existence, it has no interaction with `PostponedReceipt*` state at all.

### Impact Explanation
This is an authorization-escalation-across-accounts bug: a promise crafted while a name was owned by one party can retroactively execute privileged self-actions (`AddKey` with a full-access key, `DeployContract`, `Stake`) on whoever later legitimately claims and funds the same account name, without their consent. This directly matches the "authorization escalation across accounts or promises" bounty category and can lead to backdoored keys / hijacked contracts / arbitrary staking that results in theft of the recreated account's funds.

### Likelihood Explanation
The primitives required — self-targeted `FunctionCall` promise with a dangling `then()`/data dependency, followed by `DeleteAccount` (self-beneficiary, storage below `MAX_ACCOUNT_DELETION_STORAGE_USAGE`), followed by account-name reuse via ordinary `CreateAccount`, followed by natural delivery of the outstanding `DataReceipt` — are all reachable by an unprivileged account owner using standard transactions and their own deployed contract; no validator, node, or protocol-level privilege is needed. The attacker fully controls when the postponed receipt is created and can arrange for the matching `DataReceipt` to be produced deterministically by their own promise chain, making the attack repeatable at will. The main precondition is that the same account name gets reused after deletion, which is normal/expected on NEAR for sub-accounts (and any account whose owner deliberately vacates and re-offers the name).

### Recommendation
Extend `remove_account` in `core/store/src/utils/mod.rs` to also purge any outstanding queue state keyed by `receiver_id == account_id`: iterate and remove `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, and `TrieKey::PendingDataCount` entries for the account (mirroring the existing access-key/gas-key/contract-data iteration pattern), and clear any corresponding `TrieKey::ReceivedData` entries. Alternatively/defense-in-depth, bind postponed receipts to an account "incarnation" (e.g. store and check a created-height/account-generation marker) so a receipt authorized against a since-deleted account cannot execute against a differently-created account of the same name.

### Proof of Concept
Runtime integration test (test-loop or `runtime/runtime` unit test) plan:
1. Create account `acc` with an access key; deploy a minimal contract on `acc`.
2. Send a `FunctionCall` receipt where `acc` calls itself, producing a promise `P` with `output_data_receivers`/`input_data_ids` such that `P` cannot be immediately satisfied (its `input_data_ids` reference a not-yet-delivered data receipt), and whose action list includes `AddKey(attacker_pubkey, FullAccess)`. Confirm via `get_postponed_receipt`/state inspection that `TrieKey::PostponedReceipt{receiver_id: acc, receipt_id: P}` and `TrieKey::PostponedReceiptId{receiver_id: acc, data_id}` are written.
3. Submit a `DeleteAccount{beneficiary_id: acc}` receipt from `acc` (storage usage below `MAX_ACCOUNT_DELETION_STORAGE_USAGE`); assert it succeeds and `get_account(acc)` returns `None`.
4. Assert `TrieKey::PostponedReceipt{receiver_id: acc, receipt_id: P}` still returns `Some(..)` from state (proving the asymmetry).
5. Submit `CreateAccount` for `acc` from a third party with a fresh key, funding it.
6. Deliver the outstanding `Data` receipt satisfying `P`'s `input_data_ids`.
7. Assert the postponed receipt executes successfully and `attacker_pubkey` now has `FullAccess` on the recreated `acc` account — demonstrating cross-incarnation authorization escalation.
