### Title
`try_replace_chunk` never enforces the StackerDB contract's `write-freq` bound, letting a slot owner write far more frequently than the network's timing invariant permits - (File: `stackslib/src/net/stackerdb/db.rs`)

### Summary
The GNTDeposit bug is a bound (a timelock) that the contract advertises and that other parties rely on for verification, but that is never actually enforced at the point of state mutation. The analogous fault in this repo is `StackerDBConfig.write_freq` — the "minimum wall-clock time between writes to the same slot," which a StackerDB smart contract stipulates and which peers rely on to schedule chunk propagation — being checked only on the *read/sync* path, never on the actual write path that an authenticated-but-otherwise-unprivileged slot owner can hit directly over HTTP.

### Finding Description
`StackerDBConfig` defines `write_freq` as "minimum wall-clock time between writes to the same slot" [1](#0-0) , and it is parsed straight from the controlling smart contract's `write-freq` field [2](#0-1) .

The only place this value is consulted is `StackerDBSync::make_chunk_request_schedule`, which skips *fetching* a chunk from a peer if it was written too recently: `if self.write_freq > 0 && write_ts + self.write_freq > now { ... continue; }` [3](#0-2) . This is explicitly a "don't bother re-fetching yet" optimization, not an authorization gate — the code comment for `validate_downloaded_chunk` even states "no need to validate the timestamp, because we already skipped requesting it if it was written too recently" [4](#0-3) .

The actual write path, `StackerDBTx::try_replace_chunk`, only checks: chunk-size cap, slot-signer verification, `slot_version <= slot_validation.version` (staleness), and `slot_version > config.max_writes` (write count) — there is no `write_time`/`write_freq` check anywhere in this function [5](#0-4) . `insert_chunk` merely records the new `write_time = now` on every accepted write, without ever comparing it against the prior `write_time` plus `write_freq` [6](#0-5) .

This write path is directly reachable by any principal holding a valid slot-signing key via the unauthenticated (no admin/session, just a valid slot signature) `POST /v2/stackerdb/:principal/:contract/chunks` RPC endpoint, which calls `tx.try_replace_chunk(...)` and, on success, immediately relays the chunk to the network as a `StackerDBPushChunk` gossip message [7](#0-6) [8](#0-7) . `net_error::TooFrequentSlotWrites` exists as an error variant with a `Display` impl [9](#0-8)  but is never constructed anywhere in the write path — it is dead code, confirming the rate-limit was intended but not wired into enforcement, exactly mirroring the GNTDeposit pattern of a promised bound that isn't actually checked at the moment new state is committed.

### Impact Explanation
Any legitimate slot signer (e.g., a Nakamoto signer or miner registered as a StackerDB writer) can bump `slot_version` and overwrite their own slot at will, with no throttling, bypassing the `write-freq` invariant that the controlling smart contract and other replicas' schedulers assume holds. Because `try_replace_chunk` immediately triggers `StackerDBPushChunk` gossip to the whole network on every successful write [8](#0-7) , an attacker-controlled or compromised slot owner can flood the network with far more StackerDB chunk writes/propagations than the protocol's rate-limit design allows, consuming bandwidth/storage/CPU across all replicas at a rate the contract author explicitly tried to bound. This also rapidly exhausts the (also independently checked but unrelated) `max_writes` budget faster than intended, and undermines any downstream logic (e.g. signer message cadence assumptions) that relies on `write_freq` as a genuine rate limit rather than a soft fetch-scheduling hint. This is a bounded but real availability/integrity gap in an unauthenticated-by-admin-role-but-node-facing write path, matching the "bounded compute/propagation DoS on a read/write endpoint" class.

### Likelihood Explanation
High. No special access is required beyond already holding a valid StackerDB slot-writer key (which is by design given to many parties, e.g. signers) — this is not a privileged/administrative role. The bypass requires no race condition or timing trick: it is simply that the code path enforcing the bound was never written into `try_replace_chunk`. It can be triggered on demand and repeatedly.

### Recommendation
In `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs`), after loading `slot_validation`, compare `get_epoch_time_secs()` against `slot_validation.write_time + self.config.write_freq` and reject with `net_error::TooFrequentSlotWrites` (already defined) if the deadline has not elapsed, mirroring the check that currently only exists in the sync-fetch scheduler. This closes the gap between the advertised contract invariant and the actual enforcement point, consistent with the GNTDeposit remediation principle of enforcing the timelock at the state-mutating operation itself rather than only at a downstream consumer.

### Proof of Concept
1. Deploy/observe any StackerDB contract with `write-freq > 0` (e.g. via `StackerDBConfig::from_smart_contract`, see `stackslib/src/net/stackerdb/config.rs:422-437`).
2. As a registered slot signer, submit `POST /v2/stackerdb/:principal/:contract/chunks` with `slot_version = 1` — accepted, per `poststackerdbchunk.rs:197-209` calling `try_replace_chunk`.
3. Immediately (well within `write_freq` seconds) submit another `POST` with `slot_version = 2`, signed by the same key.
4. `try_replace_chunk` (`db.rs:398-439`) only checks size/signer/staleness/max-writes — none of which fail — so the write is accepted immediately, and `insert_chunk` records a fresh `write_time` (`db.rs:374-396`) with no gap enforced. The chunk is then relayed network-wide (`poststackerdbchunk.rs:315-324`), despite `write_freq` supposedly disallowing writes this close together.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
}
