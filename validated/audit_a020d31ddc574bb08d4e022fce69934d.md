### Title
`VesperGateway.withdraw` lacks slippage/min-out protection, so Vesper strategy losses are silently passed to withdrawers - ([File: contracts/VesperGateway.sol](contracts/VesperGateway.sol))

### Summary
`VesperGateway.withdraw` unwraps a user's `msdToken` position into the Vesper vToken's underlying asset via `vToken_.withdraw(_vTokenAmount)` and forwards whatever amount comes back, with no user-specified minimum output and no max-loss bound. If the Vesper pool cannot cover the redemption from idle funds and must pull from strategies operating at a loss (or charging withdrawal fees), the user burns the full share amount but receives less underlying than the share price implies — the exact loss-realization scenario described in the Yearn report. Unlike calling Vesper directly, the gateway gives the caller no parameter to cap or preview this loss.

### Finding Description
In `VesperGateway.withdraw`, the flow is:

1. Pull `amount_` `msdTokens` from the caller and burn them via `_depositToken.withdraw(amount_, address(this))`, which pulls `vToken` shares out of the `Treasury` at face value.
2. Call `vToken_.withdraw(_vTokenAmount)` on the Vesper pool.
3. Forward `balanceAfter - balanceBefore` underlying to the caller. [1](#0-0) 

There is no `minAmountOut_`/slippage argument in `IVesperGateway` and no comparison of `_underlyingAmount` against the vToken's `pricePerShare()` value of the burned shares. [2](#0-1)  Vesper pools (like Yearn vaults) hold only a portion of assets idle; a redemption larger than the pool's free balance forces withdrawals from the strategy queue, which can realize a loss or apply a withdrawal fee. The code even acknowledges this asymmetry elsewhere — `AMO._withdrawFromVesper` explicitly notes "Vesper pool may withdraw less... than requested" and measures actual output by balance delta. [3](#0-2)  The same acknowledgment exists at the gateway (balance-delta accounting) but the shortfall is absorbed entirely by the end user rather than checked.

Notably, `DepositToken.withdraw` itself is safe — it only moves vToken shares 1:1 from the `Treasury` via `treasury().pull(to_, _withdrawn)`. [4](#0-3)  The loss is introduced solely at the Vesper redemption step inside the gateway, where the user's msdTokens are already burned and cannot be recovered if the output is unacceptable.

### Impact Explanation
A user redeeming via `VesperGateway.withdraw` can receive materially less underlying than the msdToken/vToken value they burned, losing the difference to Vesper strategy losses or withdrawal fees. Because `msdToken` burn precedes the Vesper call and there is no min-out check, the user cannot abort on a bad quote — the position is already closed. This is a direct loss of user funds on a core user-facing exit path, and the protocol offers no way (e.g., a `withdrawUnderlying(uint256 minOut)` variant) to bound it.

### Likelihood Explanation
Requires no attacker action and no privileged role: any user calling `VesperGateway.withdraw` on a registered pool while the underlying `VPool` has insufficient idle liquidity will hit it. Likelihood is conditional on the external Vesper pool's state (free balance vs. queued strategy withdrawals at a loss), which is precisely the third-party condition the source report flags. It is not exploitable by an unprivileged attacker for theft, but the missing-protection bug class is fully present on Metronome's own code, and users have no on-chain mechanism to protect themselves.

### Recommendation
Add a `minUnderlyingOut_` parameter to `VesperGateway.withdraw` (and its interface) and revert if the balance-delta `_underlyingAmount` is below it, so users can cap realized losses. Alternatively, let users supply a Vesper `maxLoss`-style tolerance and pass it through, or document prominently that gateway withdrawals may return less than the share-value equivalent and that users should check the VPool's free balance/`pricePerShare` before redeeming — noting they can always withdraw vTokens directly via `DepositToken.withdraw` and redeem from Vesper themselves when conditions are favorable.

### Proof of Concept
Hardhat/fork sketch against a live Vesper VPool (e.g., vaUSDC):

```ts
// 1. Deposit underlying through the gateway
await underlying.approve(gateway.address, amount);
await gateway.deposit(pool.address, vToken.address, amount); // mints msdVToken

// 2. Make the VPool's idle balance < redemption size
//    (on a fork: pick a vToken whose pool keeps most funds in strategies,
//     or impersonate the pool's keeper to rebalance into a strategy,
//     or use a large amount_ exceeding pool.token().balanceOf(pool))

// 3. Withdraw via gateway — no way to set minOut
const expected = shares.mul(await vToken.pricePerShare()).div(1e18);
await msdToken.approve(gateway.address, msdBal);
await gateway.withdraw(pool.address, vToken.address, msdBal);
const received = await underlying.balanceOf(user) - before;

// 4. Assert loss: received < expected because VPool realized
//    strategy loss / withdrawal fee, and gateway absorbed it silently
expect(received).to.be.lt(expected);
```

The key observation reproducible on a fork: `gateway.withdraw` burns the full `msdToken` amount and transfers the post-`vToken.withdraw` balance delta without any floor, so any Vesper-side shortfall is borne entirely by the caller.
