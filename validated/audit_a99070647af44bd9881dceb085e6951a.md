### Title
Stale `LatestConsumeTime`/`LatestConsumeTimeForEnergy` when delegated resource is reclaimed via `UnfreezeBalanceActuator` and `UnfreezeBalanceProcessor` - ([File: actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java], [File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceProcessor.java])

### Summary
The reported bug class is: a struct field representing a "locked"/"acquired" amount is decremented, but the paired "last updated"/"last consume time" bookkeeping field used to compute decayed usage is never refreshed, leaving stale accounting state. The same class of bug is reachable in java-tron whenever a receiver's `AcquiredDelegatedFrozenBalanceForBandwidth`/`AcquiredDelegatedFrozenBalanceForEnergy` is reduced during an `UnfreezeBalanceContract` (either via the normal actuator or the TVM native-contract equivalent), without correspondingly refreshing `LatestConsumeTime`/`LatestConsumeTimeForEnergy` and running the bandwidth/energy usage recovery pass first — unlike the newer `UnDelegateResourceActuator`/`UnDelegateResourceProcessor`, which explicitly perform this update.

### Finding Description
When an account delegates frozen TRX to a receiver for BANDWIDTH/ENERGY, the receiver's usable resource limit is proportional to `AcquiredDelegatedFrozenBalanceForBandwidth/Energy`. The receiver's actual current usage (`NetUsage`/`EnergyUsage`) decays over time relative to `LatestConsumeTime`/`LatestConsumeTimeForEnergy`, computed in `BandwidthProcessor.increase()`/`recovery()` [1](#0-0)  and the analogous `EnergyProcessor.updateUsage`.

The newer delegation-removal path, `UnDelegateResourceActuator`, correctly calls `bandwidthProcessor.updateUsageForDelegated(receiverCapsule)`/`energyProcessor.updateUsage(receiverCapsule)` to first "settle" the decayed usage, then decrements the acquired balance, and finally refreshes `setLatestConsumeTime(now)`/`setLatestConsumeTimeForEnergy(now)` [2](#0-1) .

In contrast, the legacy `UnfreezeBalanceActuator.execute()` (still reachable through a plain, signed `UnfreezeBalanceContract` transaction against a delegated resource) decrements `receiverCapsule`'s acquired delegated balance for BANDWIDTH/ENERGY but never calls `updateUsageForDelegated`/`updateUsage`, nor sets `LatestConsumeTime`/`LatestConsumeTimeForEnergy` on the receiver: [3](#0-2) 

The identical omission exists in the TVM native-contract path `UnfreezeBalanceProcessor.execute()`, invoked from smart-contract `unfreezeBalance` calls, which also mutates `receiverCapsule`'s acquired balance via `safeAddAcquiredDelegatedFrozenBalanceForBandwidth/Energy` without touching `LatestConsumeTime`/`LatestConsumeTimeForEnergy`: [4](#0-3) 

This is the direct analog of the reported bug: `vouch.locked -= amount` without `vouch.lastUpdated = block.number`, causing any subsequent computation keyed off `lastUpdated` to be stale.

### Impact Explanation
Because `LatestConsumeTime` is left stale relative to the newly-reduced resource weight, the next time the receiver consumes bandwidth/energy, `BandwidthProcessor.increase()`/`recovery()` computes decay using the outdated timestamp against a smaller (already-adjusted) limit, producing an incorrect `NetUsage`/`EnergyUsage` recomputation. Depending on the elapsed time and direction of the discrepancy, this can let a receiver briefly retain a higher effective usage allowance than it should (resource accounting drift), or conversely cause usage to be miscalculated when the account is queried, degrading fairness of the global bandwidth/energy pool that all other accounts share. This maps to "unbacked" resource accounting rather than direct token theft, but is a concrete state-integrity flaw in a broadly-reachable code path.

### Likelihood Explanation
Both `UnfreezeBalanceActuator` and `UnfreezeBalanceProcessor` are reachable by any account owner who has delegated frozen balance to a receiver, simply by broadcasting an `UnfreezeBalanceContract` transaction (or a corresponding `unfreezeBalance` native TVM call from a contract) once the lock period expires. No special privilege is required — it is a normal user-facing operation, and the delegate/undelegate/freeze flow is exercised frequently in practice, making the stale-timestamp condition easy to trigger.

### Recommendation
In both `UnfreezeBalanceActuator.execute()` and `UnfreezeBalanceProcessor.execute()`, before or after adjusting `receiverCapsule`'s `AcquiredDelegatedFrozenBalanceForBandwidth`/`AcquiredDelegatedFrozenBalanceForEnergy`, mirror the pattern used in `UnDelegateResourceActuator`: call `bandwidthProcessor.updateUsageForDelegated(receiverCapsule)` / `energyProcessor.updateUsage(receiverCapsule)` to settle decayed usage, and then call `receiverCapsule.setLatestConsumeTime(now)` / `setLatestConsumeTimeForEnergy(now)` so that subsequent usage decay calculations use a correctly synchronized timestamp.

### Proof of Concept
Note: I was not able to fully trace whether this legacy `UnfreezeBalanceContract` code path (guarded by `dynamicStore.supportDR()`) is still actively reachable on current mainnet configuration versus being fully superseded by `UnfreezeBalanceV2Contract`/`UnDelegateResourceContract` — this depends on runtime hard-fork/proposal state that isn't fully determinable from static code alone. Assuming `supportDR()` is enabled (as it has been historically) and the account still has legacy (pre-FreezeV2) delegated resources, the following triggers the issue:
1. Account A freezes and delegates BANDWIDTH to Account B via `FreezeBalanceContract` with a receiver address, populating `DelegatedResourceCapsule` and B's `AcquiredDelegatedFrozenBalanceForBandwidth`.
2. Account B consumes bandwidth, updating `NetUsage`/`LatestConsumeTime`.
3. After the lock period expires, Account A submits `UnfreezeBalanceContract` targeting the same receiver B.
4. `UnfreezeBalanceActuator.execute()` reduces B's `AcquiredDelegatedFrozenBalanceForBandwidth` at [5](#0-4)  without calling `bandwidthProcessor.updateUsageForDelegated(receiverCapsule)` or updating `LatestConsumeTime`.
5. On B's next transaction, `BandwidthProcessor.useAccountNet()`/`updateUsage()` recomputes `NetUsage` decay using the stale `LatestConsumeTime` against B's now-reduced `netLimit` (derived from the smaller acquired balance), yielding a usage value inconsistent with what would have resulted from a properly settled recovery pass — demonstrating the accounting drift analogous to the `vouch.lastUpdated` staleness in the referenced report.
