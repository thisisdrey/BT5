### Title
No vulnerability — `contract_id` is part of `Nep171TokenId` identity, preventing cross-contract collisions - (File: crates/primitives/token-id/src/nep171.rs)

### Summary
The `Nep171TokenId` struct derives `PartialEq, Eq, Hash` over both `contract_id` and `nft_token_id` fields, and its `Display`/`Debug` implementation formats both fields as `"{contract_id}:{nft_token_id}"`. Since `nft_on_transfer` always constructs the `TokenId` using `env::predecessor_account_id()` (the real calling contract) rather than any attacker-supplied contract identifier, a fake NFT contract `fakepix.near` calling with `token_id="#42"` produces a `TokenId::Nep171(Nep171TokenId{contract_id: "fakepix.near", nft_token_id: "#42"})`, which is a distinct map key, distinct `Display` string, and distinct hash from `Nep171TokenId{contract_id: "realpix.near", nft_token_id: "#42"}`.

### Finding Description
The claimed binding to test is: `TokenId::Nep171(fakepix.near, "#42") == TokenId::Nep171(realpix.near, "#42")`. Tracing the code:

- `nft_on_transfer` in [1](#0-0)  builds `core_token_id` via `Nep171TokenId::new(env::predecessor_account_id(), token_id.clone())`. The `contract_id` field is always bound to `env::predecessor_account_id()`, which NEAR runtime guarantees is the actual calling contract account (`fakepix.near` in the attack scenario), not an attacker-controlled string embedded in `msg` or `token_id`.
- `Nep171TokenId` derives `PartialEq, Eq, Ord, Hash` over both fields (`contract_id`, `nft_token_id`) as shown in [2](#0-1) , so two instances with different `contract_id` are unequal and hash to different buckets — meaning `total_supplies.add(...)` in [3](#0-2)  operates on genuinely separate map entries.
- `Display`/`Debug` for `Nep171TokenId` explicitly includes `contract_id` in the formatted string (`"{contract_id}:{nft_token_id}"`) per [4](#0-3) , so the two token IDs also serialize to different strings used in `mt_mint`/`mt_burn` events and any string-keyed lookups.
- The `NftAlreadyDeposited` check at [5](#0-4)  only fires when `total_supply > 1` for the *same* key, which cannot happen across `fakepix.near` and `realpix.near` since they are different keys entirely.

Both sides of the equality diverge (`fakepix.near != realpix.near`) before and after the call, so the binding holds — this is the expected/safe outcome, confirmed also by the existing integration test pattern in [6](#0-5)  which builds distinct `Nep171TokenId` keys per issuer contract.

### Impact Explanation
None. The deposit of a fake NFT from `fakepix.near` with `token_id="#42"` creates and credits a wholly separate `TokenId` (`fakepix.near:#42`) with its own independent `total_supplies` counter and its own balance entry for the depositor. It cannot drain, block, or otherwise interact with the real NFT's `total_supplies` entry keyed by `realpix.near:#42`. No value moves from the Verifier's genuine `realpix.near` NFT balance, and no invariant is violated.

### Likelihood Explanation
N/A — the described attack path does not exist because the binding the question is testing for (accidental collision) does not occur in the code as written. The `contract_id` is always sourced from `env::predecessor_account_id()`, which is unforgeable by the calling contract itself acting as the NFT sender.

### Recommendation
No fix required for this path. (General best practice, out of scope: nothing to change here since `env::predecessor_account_id()` is the correct and only source of truth for `contract_id`.)

fn cross_contract_nft_token_id_no_collision() {
    let real = Nep171TokenId::new("realpix.near".parse().unwrap(), "#42".to_string());
    let fake = Nep171TokenId::new("fakepix.near".parse().unwrap(), "#42".to_string());

    // Binding under test: real == fake ?
    assert_ne!(real, fake);
    assert_ne!(real.to_string(), fake.to_string());

    use std::collections::hash_map::DefaultHasher;
    use std::hash::{Hash, Hasher};
    let mut h1 = DefaultHasher::new();
    real.hash(&mut h1);
    let mut h2 = DefaultHasher::new();
    fake.hash(&mut h2);
    assert_ne!(h1.finish(), h2.finish());
}
