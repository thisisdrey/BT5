## Title
Out-of-bounds read while scanning ZIP central directory entries in `InputZipFile::ProcessCentralDirEntry` - (File: `third_party/ijar/zip.cc`)

### Summary
`third_party/ijar/zip.cc` implements the `ijar`/zip-extraction library that Bazel's build actions use to read ZIP/JAR archives — including interface-jar generation for every compile-time jar dependency and the extraction path used by `zip_main.cc`. Unlike `InputZipFile::ProcessLocalFileEntry`, which calls `EnsureRemaining()` before consuming every variable-length field, `InputZipFile::ProcessCentralDirEntry` advances its cursor `p` through attacker-controlled 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) and scans the "extra fields" sub-records with **no bounds check whatsoever** against the size of the mapped input file. [1](#0-0) 

### Finding Description
`ProcessCentralDirEntry` reads:
```
p += 16;  // skip to 'compressed size' field
*compressed_size = get_u4le(p);
*uncompressed_size = get_u4le(p);
u2 file_name_length = get_u2le(p);
u2 extra_field_length = get_u2le(p);
u2 file_comment_length = get_u2le(p);
...
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
p += file_comment_length;
``` [2](#0-1) 

None of these arithmetic advances are checked against `input_file_->Length()` — contrast with `ProcessLocalFileEntry`, which explicitly guards every read with `EnsureRemaining()`:
```
if (EnsureRemaining(file_name_length_, "file_name") < 0) { return -1; }
file_name_ = p;
p += file_name_length_;
if (EnsureRemaining(extra_field_length_, "extra_field") < 0) { return -1; }
``` [3](#0-2) 

Because `file_name_length`, `extra_field_length`, and `file_comment_length` are 16-bit values fully controlled by whoever crafted the ZIP/JAR (an unprivileged dependency author, mirror, or archive host — no MITM needed), a malicious archive can set these fields so that `p` (and the inner `extra_p`) walks past the end of the `mmap`'d file buffer. The subsequent `get_u4le`/`get_u2le` calls in the same function and in the next loop iteration of `InputZipFile::ProcessNext()` / `CalculateOutputLength()` then dereference memory beyond the mapped region — an out-of-bounds read directly analogous to the unchecked buffer scan in `string_scan_range()` from CVE-2017-16358 (radare2 scanned attacker-supplied binary content past the buffer end because no remaining-length check was performed before reading the next chunk).

`ProcessCentralDirEntry` is invoked in a tight loop by both `InputZipFile::ProcessNext()` (used whenever ijar/the zip extractor reads an entry, including interface-jar creation for `java_import`/`java_library` deps fetched via `http_archive`, `http_jar`, or Maven-style rules) and `InputZipFile::CalculateOutputLength()` (used to size the ijar output before writing): [4](#0-3) 

Neither of these callers wraps the call in any additional length validation, so the missing check in `ProcessCentralDirEntry` is the sole guard that is absent.

### Impact Explanation
A hostile ZIP/JAR delivered as a build dependency (e.g., served by a compromised or malicious mirror behind an `http_archive`/`http_jar` rule, or committed to an untrusted branch that CI builds) is parsed by this code the moment Bazel needs to inspect or interface-jar the archive. The crafted central-directory length fields let an attacker cause the process to read heap memory outside the mapped file, which can crash the Bazel build (denial of service via SIGSEGV) or, depending on heap layout, leak adjacent process memory contents into subsequently written output (e.g., truncated/garbage class data or file names copied via `memcpy`/`strncmp` against out-of-bounds pointers). This is a genuine memory-safety violation triggered purely by untrusted archive bytes, not by a compromised local machine or credentials.

### Likelihood Explanation
Every `.zip`/`.jar` fetched through `http_archive`, `http_jar`, or referenced as a `java_import` dependency is a plausible trigger path once its bytes reach `ijar`'s zip reader. sha256/integrity checks on the download only verify that the fetched bytes match a pinned hash — they do **not** protect against a malicious *but hash-pinned* archive that the victim's `MODULE.bazel`/`WORKSPACE` intentionally references (e.g., a first-time dependency addition, or a lockfile update to a new version published by an attacker-controlled package). No sandboxing or bounds validation exists in `ProcessCentralDirEntry` itself, so the likelihood of triggering an OOB read given attacker-controlled archive content is high; the only uncertainty is whether the resulting read crashes the process or merely reads unmapped-but-not-immediately-faulting memory, which depends on allocator/mmap layout.

### Recommendation
Add the same `EnsureRemaining()`-style bounds check used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry` before every pointer advance (`file_name_length`, `extra_field_length`, `file_comment_length`, and each `data_size` inside the extra-fields loop), verifying against `input_file_->Length()` (or an explicit end-of-buffer pointer passed into the function) before dereferencing. Additionally bound the `while (extra_p != p)` loop so a corrupt `data_size` cannot advance `extra_p` past `p`, and reject/short-circuit central directory entries whose declared lengths exceed the remaining mapped file size instead of continuing to scan.

### Proof of Concept
A minimal `BuildIntegrationTestCase`/shell reproduction:
1. Construct a well-formed ZIP End-of-Central-Directory + a single central directory header (`CDH`) whose `file_name_length`/`extra_field_length`/`file_comment_length` fields sum to a value that runs past the actual file length (e.g., set `extra_field_length = 0xFFFF` while the physical file is only a few hundred bytes).
2. Point an `http_archive`/`http_jar` (or invoke `third_party/ijar/zip_main.cc`'s `extract`/list mode directly, as exercised in `third_party/ijar/test/zip_test.sh`) at this crafted archive with a correct `sha256` for the crafted bytes.
3. Run the extraction/ijar path (`devtools_ijar::ZipExtractor::Create(...)->ProcessAll()` or `CalculateOutputLength()`), observing a crash (ASan: heap-buffer-overflow READ) or corrupted output inside `InputZipFile::ProcessCentralDirEntry`, confirming the OOB read occurs purely from parsing attacker-supplied length fields with no remaining-bytes validation. ```text
bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}

```text
u8 InputZipFile::CalculateOutputLength() {
  const u1* current = central_dir_;

  u8 compressed_size = 0;
  u8 uncompressed_size = 0;
  u8 skipped_compressed_size = 0;
  u4 attr;
  u8 offset;
  char filename[PATH_MAX];

  while (true) {
    u8 file_compressed, file_uncompressed;
    if (!ProcessCentralDirEntry(current,
                                &file_compressed, &file_uncompressed,
                                filename, PATH_MAX, &attr, &offset)) {
      break;
    }

    if (processor->Accept(filename, attr)) {
      compressed_size += (u8) file_compressed;
      uncompressed_size += (u8) file_uncompressed;
    } else {
      skipped_compressed_size += file_compressed;
    }
  }

  // The worst case is when the output is simply the input uncompressed. The
  // metadata in the zip file will stay the same, so the file will grow by the
  // difference between the compressed and uncompressed sizes.
  return (u8) input_file_->Length() - skipped_compressed_size
      + (uncompressed_size - compressed_size);
}
