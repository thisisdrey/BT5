The root cause is exactly as described: `validate_receipt` in `runtime/runtime/src/verifier.rs` only checks `ReceiptSizeExceeded` when `mode == ValidateReceiptMode::NewReceipt`, at the moment a receipt is created via `new_result.new_receipts` in `runtime/runtime/src/lib.rs`.### Title
Receipt size validated once at creation but mutated afterward via promise-return rewiring, allowing storage/forwarding of receipts exceeding `max_receipt_size` - ([File: runtime/runtime/src/verifier.rs])

### Summary
`validate_receipt` in `runtime/runtime/src/verifier.rs` enforces `ReceiptSizeExceeded` only when `mode == ValidateReceiptMode::NewReceipt`, and this check runs immediately after a receipt is produced in `Runtime::apply_action`'s loop over `new_result.new_receipts` in `runtime/runtime/src/lib.rs`. Because `promise_return`-driven DAG rewiring (via `ReceiptManager::create_action_receipt` appending to `output_data_receivers` in `runtime/runtime/src/receipt_manager.rs`) and large `value_return` bytes are attached to an already-validated receipt *after* this one-time check, an attacker can craft a receipt that is exactly at the size limit at validation time and grows beyond `max_receipt_size` before being persisted/forwarded.

### Finding Description
`validate_receipt` (`runtime/runtime/src/verifier.rs:527-542`) computes `borsh::object_length(receipt)` and rejects it only in `ValidateReceiptMode::NewReceipt` mode, called once, right when a receipt is created in `Runtime::apply_action`, at `runtime/runtime/src/lib.rs:914-925`.

The `ReceiptManager` (`runtime/runtime/src/receipt_manager.rs`) allows an already-created receipt (identified by `receipt_index`) to be mutated later: `create_action_receipt` at lines 111-137 pushes new entries into an *existing* receipt's `output_data_receivers` (lines 118-124) when a later promise (created via `promise_batch_then`) depends on it. This is exactly what happens with `promise_batch_create` + `promise_batch_then` DAG construction combined with `promise_return`: an unprivileged contract can build a promise DAG where an intermediate receipt `C` is initially sized to sit exactly at `max_receipt_size` (validated and passed at creation), and a subsequent execution step (triggered by `promise_return` rewiring the DAG, per the `test_max_receipt_size_promise_return` scenario) appends `output_data_receivers` or attaches a large `value_return` to that already-validated receipt, pushing its serialized size above `max_receipt_size`. Since `validate_receipt` was only invoked once, at creation time, this larger receipt is never re-validated before being persisted/forwarded on-chain.

This is a known, already-acknowledged defect in the codebase itself: the accompanying test file explicitly documents it as a bug with a public tracking issue reference. See the comment directly above `test_max_receipt_size_promise_return`: [1](#0-0) 

The test constructs the exact attacker flow described: a contract method builds `[A -then-> B]`, and when `A` executes it creates a new promise `C` and does `promise_return`, changing the DAG to `[C -then-> B]`, where `C`'s receipt is sized to be exactly `max_receipt_size` before the `output_data_receivers` addition pushes it over the limit: [2](#0-1) 

A second variant achieves the same effect via a large `value_return`, wrapped in a data receipt that becomes oversized: [3](#0-2) 

Both tests conclude by asserting `assert_oversized_receipt_occurred`, which walks the chain's incoming receipt proofs / receipt proofs and asserts that a receipt exceeding `max_receipt_size` was actually included on-chain: [4](#0-3) 

The reason existing checks fail: `validate_receipt`'s size gate is a point-in-time check tied to `ValidateReceiptMode::NewReceipt`, called exactly once per receipt right after it's produced in the action-execution loop (`runtime/runtime/src/lib.rs:914-925`), with no re-validation hook anywhere later in the pipeline (e.g., after `ReceiptManager` finalizes cross-receipt wiring, or before receipts are written to the trie / included in outgoing receipt lists).

### Impact Explanation
This matches the "shard-halting panic" / consensus-liveness category: oversized receipts, once persisted and included in `ChunkStateWitness`/`source_receipt_proofs`, contribute to aggregate stateless-validation witness size. If validators' computed true sizes exceed the documented ~21MiB budget (`docs/misc/state_witness_size_limits.md`), chunk endorsement can fail, stalling shard progress. This is a metering-totality violation: not every byte ending up in a persisted/forwarded receipt is checked against `max_receipt_size`.

### Likelihood Explanation
The attack requires only an unprivileged, self-funded account: deploy a contract using `promise_batch_create`/`promise_batch_then`/`promise_return` (or a large `value_return`) as demonstrated in the referenced tests, and call it. No validator, network, or privileged access is needed; the cost is only the gas/deposit for a single transaction plus contract deployment. It's fully repeatable since the size arithmetic (`base_receipt_size` + `args_size` to reach exactly `max_receipt_size`, `max_receipt_size = 4_194_304`) is deterministic given the fixed base receipt template computed via `borsh::object_length`, per `runtime/runtime/src/verifier.rs:534-535` and the test's own precomputation logic (`test-loop-tests/src/tests/max_receipt_size.rs:174-177`).

### Recommendation
Re-validate receipt size (`ReceiptValidationError::ReceiptSizeExceeded`) after all `ReceiptManager` mutations are finalized — i.e., after `output_data_receivers` wiring from `promise_batch_then`/`promise_return` and after `value_return`/data receipt construction — and before receipts are persisted to the trie or added to outgoing receipt lists. This likely means moving or adding a `validate_receipt` call at the point where `ReceiptManager::action_receipts`/`data_receipts` are finalized into actual `Receipt`/`DataReceipt` objects, rather than solely immediately after `apply_action` produces `new_result.new_receipts`.

### Proof of Concept
Reuse the existing test-loop integration tests already present in the repo, which reproduce this exact scenario:
- `test_max_receipt_size_promise_return` (`test-loop-tests/src/tests/max_receipt_size.rs:129-208`): deploy contract, call `max_receipt_size_promise_return_method1` with `args_size` computed so promise `C`'s receipt is exactly `max_receipt_size` before `output_data_receivers` is appended, then call `assert_test_completed`, and finally assert `assert_oversized_receipt_occurred(&env.validator())`.
- `test_max_receipt_size_value_return` (`test-loop-tests/src/tests/max_receipt_size.rs:216-267`): call `max_receipt_size_value_return_method` with `value_size = max_receipt_size`, then `assert_test_completed`, and assert `assert_oversized_receipt_occurred`.

Expected assertion (already implemented in `receipt_is_oversized`, `test-loop-tests/src/tests/max_receipt_size.rs:422-428`): `borsh::object_length(receipt) > max_receipt_size` for a receipt found in the chain's incoming receipt proofs — currently this assertion succeeds, confirming the bug is present and unpatched in this codebase.

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

fn receipt_is_oversized(receipt: &Receipt, max_receipt_size: u64) -> bool {
    let receipt_size: u64 = borsh::object_length(receipt).unwrap().try_into().unwrap();
    if receipt_size > max_receipt_size {
        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
    }
    false
}
