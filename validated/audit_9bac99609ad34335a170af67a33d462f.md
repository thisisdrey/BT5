### Title
Direct lamport donation to a SVSP stake/on-ramp account inflates staked-collateral price without going through any deposit hook - ([File: programs/marginfi/src/state/price.rs])

### Summary
Confirmed: `lending_pool_add_bank_permissionless` lets *any unprivileged user* create a `StakedWithPythPush` bank for an arbitrary validator's Single Validator Stake Pool (SVSP), and the resulting LST/SOL exchange rate used by marginfi's oracle is derived by reading the **raw lamport balance** of the pool's stake account and on-ramp account, not through any protocol-tracked deposit/withdraw hook.

### Finding Description
`staked_pool_net_asset_value()` computes the pool NAV purely from `AccountInfo::lamports()` of the `sol_pool` (native stake account) and `pool_onramp` account, minus each account's rent-exempt reserve: [1](#0-0) 

This NAV is then divided by the LST mint's total supply to produce a `multiplier` that scales the Pyth SOL price into the effective USD price of the staked-collateral bank's deposited token: [2](#0-1) 

Because `AccountInfo::lamports()` reflects the *actual* on-chain balance, and Solana's System Program allows anyone to transfer lamports to **any** account regardless of its owner (no CPI/authorization from the destination program is required to receive lamports), a user can transfer SOL directly into the `sol_pool` stake account or the `pool_onramp` account without going through the SVSP program's stake/deposit instruction. This directly inflates `sol_pool_adjusted_balance` and thus the `multiplier`/price used by marginfi the moment it's next read — exactly the "donation bypasses the accounting hooks" bug class described in the HydraDX report, where a direct transfer to the AMM/StableSwap pool changes the effective exchange rate without going through any tracked update path.

Compounding this, `lending_pool_add_bank_permissionless` is fully permissionless — any user can create a staked-collateral bank for a validator pool with a small/attacker-controlled LST supply: [3](#0-2) [4](#0-3) 

There is no code path that clamps `sol_pool_adjusted_balance` to the value implied by legitimately-staked/delegated lamports (e.g. the stake account's `Delegation.stake` field, as the deprecated `legacy_staked_pool_delegated_value()` used to do) — the new NAV formula intentionally counts *all* lamports in the stake+on-ramp accounts above rent-exemption, with no distinction between lamports delegated via the SVSP program and lamports sent via a bare `SystemProgram::transfer`.

### Impact Explanation
An attacker who is a dominant/sole holder of a given validator's LST supply (trivial to arrange since bank creation and staking to a validator pool are both permissionless) can:
1. Deposit their LST as collateral into a marginfi staked-collateral bank.
2. Directly transfer additional lamports into the pool's `sol_pool` or `pool_onramp` account, inflating `sol_pool_adjusted_balance / lst_supply` (the price multiplier) for their own (near-100%-owned) LST supply.
3. Borrow SOL against the now-inflated collateral value in the same or a subsequent transaction (health check re-reads the live price via `get_health_components` / `OraclePriceFeedAdapter::try_from_bank`, both of which call the exact same NAV computation) — see `borrow.rs`'s use of `check_account_init_health` combined with the live oracle price: [5](#0-4) 
4. Redeem/unstake through the SVSP program to recover the donated lamports (since they own essentially all outstanding LST for that pool), leaving the marginfi bank collateralized far below the debt actually taken out.

This results in the protocol accruing bad debt / undercollateralized borrows — a concrete insolvency risk in core accounting, not merely a "stale/misleading price" observation as in the original disputed HydraDX report. It is stronger than the original finding because it demonstrates an economically rational extraction path (borrow-then-reverse-the-donation) rather than only "the oracle becomes outdated."

### Likelihood Explanation
Medium-to-High. All preconditions are permissionless: creating a staked bank (`lending_pool_add_bank_permissionless`), staking/creating an LST for an arbitrary validator, and sending lamports to any account (no special privilege needed — the stake/on-ramp accounts are just SOL accounts). The attack is most powerful for low-liquidity/attacker-dominated validator pools (thin LST supply), which is realistic given the permissionless bank-creation flow explicitly targets "long-tail" validators not yet listed.

### Recommendation
- Do not treat raw `AccountInfo::lamports()` of the stake/on-ramp accounts as ground truth for NAV. Cross-check the reported balance against the stake account's actual `Delegation.stake` (as `legacy_staked_pool_delegated_value` did) or otherwise validate that lamports above the expected delegated/on-ramp amount are not counted, so unsanctioned SystemProgram transfers cannot inflate NAV.
- Alternatively, require a minimum LST supply / minimum total pool NAV before a staked bank is eligible for collateral use, to prevent single-holder domination of the pool used for pricing.
- Consider bounding per-instruction price multiplier deltas (circuit breaker) similar to protections already present for other oracle types, to catch a single-transaction NAV jump caused by a donation.

### Proof of Concept
1. Attacker calls `lending_pool_add_bank_permissionless` for a validator with (initially) zero/negligible stake, creating a `StakedWithPythPush` bank — permissionless per `programs/marginfi/src/lib.rs:94-100`.
2. Attacker stakes SOL to that validator and deposits into the SVSP single pool via the standard SVSP flow, receiving LST 1:1 (near-100% of the pool's LST supply since they're the first/only depositor), then deposits this LST into the marginfi bank as collateral.
3. Attacker sends a plain `SystemProgram::transfer` of `D` lamports directly to the pool's `sol_pool` stake account (or `pool_onramp` account) — no SVSP program interaction required.
4. Attacker calls `lending_pool_pulse_bank_price_cache` or triggers a live price read (e.g. via `lending_account_borrow`); `staked_pool_net_asset_value()` (`programs/marginfi/src/state/price.rs:106-122`) now reports NAV inflated by `D`, and the `multiplier` computed at `price.rs:393-395` scales up the reported USD price of the attacker's LST collateral.
5. Attacker borrows SOL up to the new inflated collateral limit (health check passes using the live-computed inflated price, per `get_health_components`).
6. Attacker withdraws stake through the SVSP program, recovering approximately `D` lamports back (since they hold ~100% of the pool's LST supply), leaving the bank's asset backing reduced relative to the debt issued — a bad-debt/insolvency condition for the marginfi group.

fn staked_pool_net_asset_value(
    pool_stake_info: &AccountInfo,
    pool_onramp_info: &AccountInfo,
    rent: &Rent,
) -> MarginfiResult<u64> {
    let pool_rent_exempt_reserve = rent.minimum_balance(pool_stake_info.data_len());
    let onramp_rent_exempt_reserve = rent.minimum_balance(pool_onramp_info.data_len());

    let main_stake_value = pool_stake_info
        .lamports()
        .saturating_sub(pool_rent_exempt_reserve);
    let onramp_value = pool_onramp_info
        .lamports()
        .saturating_sub(onramp_rent_exempt_reserve);

    Ok(main_stake_value.saturating_add(onramp_value))
}
