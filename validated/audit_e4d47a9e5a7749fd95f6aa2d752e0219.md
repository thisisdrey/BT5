### Title
Amount-independent `last-borrow-block` refresh in `debt-add-scaled` allows griefing/perma-blocking of liquidation via micro borrow/repay - ([File: mainnet/contracts/market/v0-market-vault.clar])

### Finding Description
`debt-add-scaled` unconditionally sets `last-borrow-block` to `stacks-block-height` on every call that passes `(> scaled-amount u0)`, with no minimum size requirement tied to the position's actual debt: [1](#0-0) 

The comment explicitly states this field exists as "Oracle frontrunning protection: record current block when borrowing," implying downstream logic (in `v0-4-market.clar`'s `liquidate`) gates liquidation based on whether the current block equals (or is too close to) `last-borrow-block` for the account's registry entry.

Critically, `debt-remove-scaled` (repay) only calls `refresh`, which updates `mask` and `last-update` but never touches or resets `last-borrow-block`: [2](#0-1) [3](#0-2) 

Because the field is bumped by any nonzero `scaled-amount` — including `u1` — a position with a large, underwater debt can be kept perpetually "just borrowed" by repeatedly calling `debt-add-scaled` (via the market's `borrow` entrypoint) with a trivial amount each block. Since `debt-add-scaled` is amount-agnostic in how it updates `last-borrow-block`, the guard's cost to defeat scales with attacker-chosen micro-amount, not with the protected debt size.

### Impact Explanation
This breaks the SOLVENCY invariant: an attacker can indefinitely block liquidation of a large, undercollateralized position with negligible round-trip capital (interest/fees on `u1`), while the real debt continues accruing interest unpaid and unliquidated. This causes lender/supplier losses that grow unboundedly relative to the attacker's cost, matching the in-scope **Critical - protocol insolvency** category.

### Likelihood Explanation
Preconditions are attacker-controlled and unprivileged: any ordinary principal with an existing large debt position that has gone underwater, plus enough liquidity to execute `borrow u1` / `repay u1` each block. The action is fully repeatable and only requires ordinary public-function calls (`borrow`, `repay`) already reachable to any user; no DAO, oracle, or privileged access is needed. This makes the griefing economically trivial and continuously repeatable for as long as the attacker is willing to pay the marginal interest on `u1`.

### Recommendation
Decouple the oracle-frontrunning guard from `last-borrow-block` being refreshable at arbitrary amounts. Options: (a) tie the "recently borrowed" cool-down check to whether the *new* scaled debt materially changes the account's health factor / total debt (not just non-zero), (b) apply the guard per-asset increase relative to existing debt or require a minimum meaningful delta before refreshing `last-borrow-block`, or (c) make the guard block only oracle-price-staleness within the same transaction/block rather than persistently blocking liquidation across many blocks by trivial re-triggering.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Deploy market stack; set up one collateral asset and one debt asset with a price feed.
2. Attacker deposits collateral, borrows a large amount via `borrow` (market entrypoint) so `debt-add-scaled` records `last-borrow-block = B0`.
3. Advance blocks and manipulate/allow the oracle price (or just interest accrual) so the position becomes underwater (health factor < 1).
4. In block `B1`, liquidator calls `liquidate` and assert it reverts due to the same-block/recency guard tied to `last-borrow-block`.
5. In the same block `B1`, attacker calls `repay u1` (`debt-remove-scaled`) then `borrow u1` (`debt-add-scaled`), asserting `last-borrow-block` is now `B1`.
6. Repeat steps 4–5 for N further blocks, asserting `liquidate` reverts every time while the large debt's accrued interest (`get-account-scaled-debt` scaled value converted via index) grows each block.
7. Compute and assert: attacker's total cost (interest on `u1` borrow/repay operations) stays near-zero and constant, while the unliquidated large debt's owed value grows unbounded — demonstrating supplier loss disproportionate to attacker cost.

Note: I was unable to retrieve the exact `liquidate` function body in `v0-4-market.clar` that consumes `last-borrow-block` before this session ended (tool budget exhausted), so the precise guard condition (e.g., strict equality vs. a block-count window) should be confirmed in `mainnet/contracts/market/v0-4-market.clar` before finalizing the fix, though the root cause in `v0-market-vault.clar` (amount-independent refresh, asymmetric with repay) is confirmed directly from the code shown above.

(define-public (debt-remove-scaled (account principal) (scaled-amount uint) (asset-id uint))
  (let ((states (var-get pause-states))
        (entry (resolve account))
        (user-id (get id entry))
        (mask (get mask entry))
        (remaining (try! (remove-user-scaled-debt user-id asset-id scaled-amount)))
        (nmask (if (is-eq remaining u0)
                      (mask-update mask asset-id false false) ;; debt, remove
                      mask))
        (updated-entry (merge entry (refresh nmask))))
