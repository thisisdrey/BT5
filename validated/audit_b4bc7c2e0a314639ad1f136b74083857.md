## Answer

**Binding claimed:** `Σ(wNEAR debited from signer_id across the batch) == Σ(NEAR that reaches receiver_id) + Σ(NEAR refunded/re-credited to signer_id)`. I traced this end to end in `native_withdraw` / `do_native_withdraw` and it does **not** hold — there is no refund path at all for a failed final transfer.

### Title
Missing refund/resolver on `do_native_withdraw`'s terminal `Promise::new(receiver_id).transfer(amount)` permanently burns signer's wNEAR on transfer failure - (File: `contracts/defuse/src/contract/tokens/nep141/native.rs`)

### Summary
`native_withdraw` synchronously subtracts the wNEAR amount from the signer's `token_balances` and then fires a detached `near_withdraw().then(do_native_withdraw)` promise chain. `do_native_withdraw` only checks that `near_withdraw` succeeded, then unconditionally sends `Promise::new(receiver_id).transfer(amount)` with no follow-up callback to verify success or refund on failure — unlike `ft_withdraw`/`mt_withdraw`, which both chain a `*_resolve_withdraw` callback that credits back the amount if the final transfer fails.

### Finding Description
The synchronous debit happens in `native_withdraw`: [1](#0-0) 

The debit itself removes funds from `token_balances` immediately, before any async transfer completes: [2](#0-1) 

The terminal callback only guards the `near_withdraw` step and then fires the final transfer with **no subsequent `.then()` and no resolver**: [3](#0-2) 

Contrast with `ft_withdraw`, which chains a resolver after the final transfer that refunds the unsent amount back into the sender's ledger: [4](#0-3) [5](#0-4) 

And `mt_withdraw`, same pattern with `mt_resolve_withdraw`: [6](#0-5) 

`NativeWithdraw` has no analogous `native_resolve_withdraw`. If the terminal `Promise::new(receiver_id).transfer(amount)` action fails on-chain — which happens when `receiver_id` is a non-existent named account (e.g., deleted between the `withdraw` intent being processed and the promise executing) — NEAR's protocol-level refund of the attached balance returns the tokens to the *predecessor of that failed receipt*, i.e., the Defuse contract's own raw NEAR balance, not to any user-tracked ledger entry. Since there is no callback observing this failure, `token_balances` is never re-credited: the signer's wNEAR debit is permanent and unrecoverable via any contract-level accounting.

The two-intents-same-`receiver_id` framing in the question is just one practical way an attacker triggers this deterministically (racing account deletion against the second detached chain while the first succeeds), but the root cause is independent of batching or aggregation — a single `NativeWithdraw` to any account that fails to exist at settlement time triggers the same unrecoverable loss. `promise_result_checked_void(0)` in `do_native_withdraw` only checks index 0 (the `near_withdraw` result within the same callback invocation); it cannot and does not check the result of the `Promise::new(...).transfer(...)` it itself schedules, because that promise's result is never observed by any subsequent callback.

### Impact Explanation
Any `NativeWithdraw` intent whose `receiver_id` fails to receive the transfer (deleted account being the demonstrable case) causes the signer's already-debited wNEAR to vanish from the internal ledger with the underlying NEAR silently accruing to the Defuse (Verifier) contract's own account balance, untracked by any user's balance. This is user funds permanently frozen / lost with no compensating credit — a batch whose balance changes do not net to zero, matching the Critical impact category. The attack is repeatable per attacker-controlled receiver account and scales with withdrawal amount and batch size (any number of `NativeWithdraw` intents targeting soon-to-be-deleted accounts in the same or parallel transactions).

### Likelihood Explanation
The attacker needs: wNEAR balance in Defuse (their own funds, freely obtainable via deposit), a `receiver_id` account they control and can delete via a separate `DeleteAccount` transaction, and correct timing so the deletion lands between the intent's synchronous debit and the async `Promise::new(receiver_id).transfer(...)` execution. This is entirely within an unprivileged attacker's capability — no role, relayer key, or victim key needed — and is a standard NEAR receipt-ordering race that is feasible to reproduce deterministically in a `near-workspaces`/sandbox test by controlling both transactions' submission order.

### Recommendation
Add a `native_resolve_withdraw` callback chained after `do_native_withdraw`'s `Promise::new(receiver_id).transfer(amount)`, mirroring `ft_resolve_withdraw`/`mt_resolve_withdraw`: check `promise_result_checked_void` on the transfer result, and if it failed, credit `withdraw.amount` of wNEAR back to the signer's `token_balances` via `self.deposit(...)`.

### Proof of Concept
`cargo test` plan (near-workspaces sandbox, in `tests/src/tests/defuse/intents/native_withdraw.rs`):
1. Create `signer` account, deposit 6 NEAR of wNEAR into Defuse for `signer`.
2. Create `receiver_a` as a fresh throwaway account (attacker-controlled) with minimal balance.
3. Build a `MultiPayload` with two `NativeWithdraw{receiver_id: receiver_a, amount: 3 NEAR}` intents signed by `signer`, same nonce-batch, submitted via `execute_intents`.
4. In parallel, submit a `DeleteAccount` transaction for `receiver_a` timed to land after the first `do_native_withdraw`'s transfer executes but before the second's.
5. Assert: `signer`'s wNEAR balance in Defuse == 0 (both 3 NEAR legs debited).
6. Assert: `receiver_a`'s real NEAR gain == 3 NEAR (only first leg landed) — since `receiver_a` no longer exists, query balance is impossible; instead assert total NEAR balance of Defuse contract account increased by 3 NEAR (the failed transfer's refund) with **no** corresponding credit anywhere in `token_balances`.
7. Assert the binding fails: `receiver_a_real_gain (3 NEAR) + signer_recredited (0 NEAR) < 6 NEAR` debited, proving the missing 3 NEAR is unrecoverable by `signer` and sits untracked in the Verifier's own balance.

    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
