### Title
Non-constant-time authorization comparison enables timing side-channel password recovery leading to authenticated block broadcast forgery - (File: stackslib/src/net/api/postblock_v3.rs)

### Summary
`RPCPostBlockRequestHandler::try_parse_request` compares the attacker-supplied `authorization` header directly against the configured RPC password using Rust's default `String`/`&str` `!=` operator, which performs a byte-wise, early-exit comparison rather than a constant-time one. Because the comparison result gates the `authenticated` flag that in turn permits `broadcast=1` (network-wide relay of the posted Nakamoto block), it becomes theoretically possible to lever residual timing differences of `auth_header != password` to reconstruct the password character-by-character.

### Finding Description
At [1](#0-0)  the handler does:
```rust
if let Some(password) = &self.auth {
    if let Some(auth_header) = preamble.headers.get("authorization") {
        if auth_header != password {
            return Err(Error::Http(401, "Unauthorized".into()));
        }
        authenticated = true;
    }
}
```
`auth_header != password` resolves to `str`'s `PartialEq`, which is implemented via `[u8]` slice equality; the standard library's slice equality short-circuits and returns as soon as a differing byte (or differing length) is found. This means the number of byte comparisons performed — and therefore the CPU time spent in this branch — is a monotonic function of the length of the matching prefix between the guessed value and the true secret. If `authenticated` is later required for `broadcast && !authenticated` at [2](#0-1) , an attacker who can distinguish these timing differences over repeated requests could iteratively refine a guess of the configured `auth` secret, byte by byte, eventually reconstructing it and forging a valid `authorization` header to submit `broadcast=1` POSTs that get accepted, processed via `Relayer::process_new_nakamoto_block_ext`, and relayed network-wide via `node.set_relay_message(StacksMessageType::NakamotoBlocks(...))` at [3](#0-2) . No constant-time comparison primitive (e.g. `subtle::ConstantTimeEq` or a manual XOR-accumulate compare) is used anywhere in this code path, and the same naive-comparison pattern recurs in the other RPC auth-gated handlers (`blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`, `fastcallreadonly.rs`, `postblock_proposal.rs`), confirming there is no existing mitigation anywhere in this request-handling layer.

### Impact Explanation
If the timing channel is exploitable in practice, an unprivileged remote attacker could recover the node operator's configured RPC `auth` password without ever holding it, then use it to submit authenticated `broadcast=1` `/v3/blocks/upload/` requests that are stored/processed and relayed to the rest of the network as legitimate uploaded blocks — an authentication bypass leading to network-wide propagation of attacker-supplied data, matching the Critical severity category ("network-wide propagation of forged data", "auth bypass").

### Likelihood Explanation
The endpoint is reachable by any remote party able to connect to the RPC port and requires no privileged role or prior secret knowledge, satisfying the "unprivileged remote attacker" model. However, actual exploitability is highly speculative: the signal being measured is a handful of nanoseconds of CPU time embedded within a full HTTP request/response round trip (TCP handshake, header parsing, TLS/plaintext framing, OS scheduling, and network jitter), which in practice overwhelms the sub-microsecond timing differences from a short-circuiting byte comparison over a password-length string. No code in this repository amplifies or isolates the signal, and there is no batching/oracle mechanism that would make per-byte timing measurable with the precision required over a real network path.

### Recommendation
Replace the plain `!=` comparison with a constant-time equality check (e.g., using the `subtle` crate's `ConstantTimeEq`, or a manual loop that XORs all bytes and only branches after processing the full length) for the `authorization` header comparison in `postblock_v3.rs`, and audit/fix the same pattern in `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`, `fastcallreadonly.rs`, and `postblock_proposal.rs`.

### Proof of Concept
A Rust `stackslib::net` unit test can be written to time `auth_header != password` comparisons over strings that share increasing common prefixes with the secret (e.g., 0, 25%, 50%, 75%, 100% matching prefix length), averaging over many iterations, and assert whether the mean comparison time correlates with prefix length. If the measured timing signal is statistically distinguishable above noise for in-process comparisons (isolated from HTTP-round-trip jitter), it confirms the code-level lack of constant-time protection at `stackslib/src/net/api/postblock_v3.rs` line 106, even though real-world exploitation over an actual network RPC round trip is not demonstrated here.
