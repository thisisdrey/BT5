### Title
Dust transfers of `msdToken` fill a victim's `depositTokensOfAccount` list up to `MAX_TOKENS_PER_USER`, DoS-ing deposits/mints of new collateral types and liquidation payouts - (File: contracts/Pool.sol, contracts/DepositToken.sol)

### Summary
`DepositToken._transfer` adds the deposit token to the recipient's per-account token list via `Pool.addToDepositTokensOfAccount` when the recipient's balance transitions from zero. That list is bounded by `MAX_TOKENS_PER_USER`, and once full, adding a new entry reverts. An attacker can permissionlessly send 1-wei dust transfers of every listed `msdTOKEN` to a victim, exhausting the list and causing any subsequent first-time receipt of a *new* collateral type to revert. This mirrors the HAX CMS bug class: attacker-controllable input reaching a code path that throws on unvalidated state, producing denial of service.

### Finding Description
- `DepositToken.transfer`/`transferFrom` are public and only require the sender's unlocked balance to cover the amount (`_revertIfLocked`), with no minimum amount and no recipient consent: `DepositToken.sol:348-376`.
- `_transfer` (and `DepositToken._mint` on first deposit, `DepositToken.sol:211-236`) calls `pool.addToDepositTokensOfAccount(recipient)` when `balanceOf(recipient)` goes 0 → >0.
- `Pool.addToDepositTokensOfAccount` enforces the `MAX_TOKENS_PER_USER` cap (same constant used for `depositTokens` in `addDepositToken`, `Pool.sol:703`) and reverts once the victim's list is full.
- An attacker therefore deposits a dust amount into each listed collateral, then calls `transfer(victim, 1)` for each `msdTOKEN`, filling the victim's list.
- Afterwards: (a) the victim's `deposit()` of any collateral they haven't held before reverts inside `_mint` → `addToDepositTokensOfAccount`, and (b) `Pool.liquidate`'s `DepositToken.seize` path reverts when the liquidator's list is full — a liquidator targeted the same way cannot be paid out in a new collateral token, degrading liquidation of underwater positions.

### Impact Explanation
The invariant broken is liveness of deposit/transfer flows. The victim is temporarily unable to open positions in collateral types they do not already hold, and a liquidator whose list is filled cannot receive seized collateral in new tokens, slowing or blocking liquidation of bad debt (protocol insolvency risk amplifier). Recovery requires the victim to fully zero out one dust token (transfer it back out so `removeFromDepositTokensOfAccount` fires on `balanceOf == 0`) — costing per-token transactions while the attacker can refill slots cheaply. Cost to the attacker is bounded by dust deposits across the pool's listed `DepositToken`s; impact is a temporary freezing of the victim's deposit functionality and of new-token receipts, satisfying the accepted impact class (temporary freezing of funds/functionality).

### Likelihood Explanation
- Fully unprivileged: `transfer` is a public ERC-20 entry point; no role, oracle, or governance action is required.
- `nonReentrant`, `whenNotPaused`, and `SynthContext._msgSender` checks do not prevent the attack — the attacker acts as their own sender.
- No health check or `onlyIfCanMint`-style guard gates `addToDepositTokensOfAccount`.
- Griefing is repeatable: the attacker can re-dust slots as the victim clears them.
- Attack cost scales with the number of listed deposit tokens and is repaid only by forcing the victim to spend gas to clear entries.

### Recommendation
- Do not add tokens to `depositTokensOfAccount` on unsolicited `transfer`/`seize` receipts below a minimum threshold, or track the deposit-token set only for collateral actually locked via `deposit`/`_mint` (i.e., count the position, not the token receipt).
- Alternatively, make `addToDepositTokensOfAccount` non-reverting on capacity (drop oldest/zero-balance entries, or allow overflow) so that dust receipts cannot brick first-time deposits.
- A cheaper mitigation: in `_transfer`, only call `addToDepositTokensOfAccount` when `amount_` (or resulting balance) exceeds a dust threshold; enforce the same floor in `seize`.

### Proof of Concept
Hardhat sketch against the deployed pool configuration:

```ts
// setup: pool with N listed deposit tokens, debtFloor/caps as deployed
const victim = bob.address;
const listed = await pool.getDepositTokens(); // msdMET, msdVaETH, ...

for (const dt of listed) {
  const depositToken = await ethers.getContractAt('DepositToken', dt);
  const underlying = await ethers.getContractAt('ERC20', await depositToken.underlying());
  // attacker deposits dust into each collateral
  await underlying.connect(attacker).approve(dt, DUST);
  await depositToken.connect(attacker).deposit(DUST, attacker.address);
  // dust-transfer fills victim's per-account list
  await depositToken.connect(attacker).transfer(victim, 1);
  expect(await pool.depositTokensOfAccount(victim)).to.contain(dt);
}
// victim's list == MAX_TOKENS_PER_USER
// a NEW deposit token is added by governor, or victim tries a collateral type never held
const tx = newDepositToken.connect(victim).deposit(amount, victim.address);
await expect(tx).reverted; // reverts inside addToDepositTokensOfAccount (list full)
```

Verification steps: confirm `Pool.addToDepositTokensOfAccount` reverts at `MAX_TOKENS_PER_USER` and that `DepositToken._transfer`/`_mint` invoke it on 0→>0 balance transitions; confirm `removeFromDepositTokensOfAccount` fires only when balance returns to zero, establishing the recovery/clearing path described in Impact.
