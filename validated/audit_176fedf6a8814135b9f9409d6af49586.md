### Title
Shielded spending-key material accepted via HTTP GET query parameters, exposing secrets in URLs/logs - (File: `framework/src/main/java/org/tron/core/services/http/GetExpandedSpendingKeyServlet.java`)

### Summary
The Full Node HTTP API exposes several Sapling shielded-key derivation endpoints (`/wallet/getexpandedspendingkey`, `/wallet/getakfromask`, `/wallet/getnkfromnsk`) that accept the raw secret key material (`sk`, `ask`, `nsk`) as a plain HTTP GET query parameter (`value`). Because these are GET requests, the secret hex value becomes part of the request URL, which is the exact bug class described in the SonarQube advisory (CWE-532): sensitive material placed in URL parameters ends up recorded in any HTTP access log, reverse proxy log, load-balancer log, browser history, or `Referer` header along the request path.

### Finding Description
`GetExpandedSpendingKeyServlet.doGet` reads the raw spending-key seed directly from the query string and immediately derives the full Sapling expanded spending key (`ask`, `nsk`, `ovk`) from it: [1](#0-0) 

The related derivation servlets follow the identical unsafe pattern, pulling `ask`/`nsk` straight out of `request.getParameter("value")` on a GET request: [2](#0-1) [3](#0-2) 

`ask`/`nsk` are the spend-authorizing and proof-authorizing components of the Sapling expanded spending key used to derive full viewing/spend authority over shielded notes: [4](#0-3) 

These servlets are wired into the publicly reachable Full Node HTTP API through `FullNodeHttpApiService`, and the HTTP layer (`HttpService`/`RateLimiterServlet`) does no scrubbing of the request URI before it could be logged — in fact `HttpService`'s own error handler logs `request.getRequestURI()` (without the query string in this case, but any front-end reverse proxy, Jetty NCSA-style logging, or CDN access log placed in front of the node would record the full URL including the `value=<secret>` query parameter): [5](#0-4) 

The POST variants of these same endpoints correctly avoid this by putting the secret in the JSON body, confirming the GET path is the unsafe outlier: [6](#0-5) 

### Impact Explanation
An attacker who can read HTTP access logs, browser history, or reverse-proxy/CDN logs positioned in front of a full node that offers these endpoints to end users (e.g., a wallet backend or public JSON API gateway) can recover the raw Sapling spending-key components (`sk`, `ask`, `nsk`) submitted via GET. Recovery of these values allows full reconstruction of shielded spend authority and permits an attacker to spend/steal the victim's shielded (Sapling) TRC-20/TRX balances — a concrete unauthorized account operation / theft of funds impact, matching CWE-532's sensitive-information-disclosure class from the referenced advisory.

### Likelihood Explanation
Exploitation requires the secret to be submitted via GET rather than POST/body, which is possible today for any client since both doGet and doPost are implemented and doGet is fully functional. Any deployment that fronts the node with a standard access-logging reverse proxy, API gateway, or CDN (a very common production pattern) will passively capture the secret in its logs without any special attacker action beyond convincing/observing a client using the GET form (or the client's own tooling/SDK defaulting to GET, which is common for read-style “getX” API names). This is a realistic, low-effort information-disclosure path rather than a purely theoretical one.

### Recommendation
Remove or deprecate the GET variants (`doGet`) for `GetExpandedSpendingKeyServlet`, `GetAkFromAskServlet`, and `GetNkFromNskServlet` (and any other endpoint accepting private/spending key material via query parameters), forcing POST-with-body usage exclusively for secret-bearing requests. If backward compatibility must be preserved, at minimum document the risk, disable these endpoints by default (already possible via `disabledApiList`, see `HttpApiAccessFilter`), and ensure operational guidance instructs operators never to enable access logging of the query string for these routes. [7](#0-6) 

### Proof of Concept
```
GET /wallet/getexpandedspendingkey?value=<32-byte-hex-spending-key-seed> HTTP/1.1
Host: victim-fullnode:8090
```
Any HTTP access log, reverse proxy log, or browser history capturing this request line discloses the raw spending-key seed in cleartext, from which the shielded spend-authority (`ask`, `nsk`, `ovk`) is deterministically derivable, enabling theft of the associated shielded funds.

    @Override
    public void handle(String target, Request baseRequest, HttpServletRequest request,
        HttpServletResponse response) throws IOException, ServletException {
      if (response.getStatus() == HttpStatus.PAYLOAD_TOO_LARGE_413) {
        Throwable cause = (Throwable) request.getAttribute(RequestDispatcher.ERROR_EXCEPTION);
        logger.info("Reject oversized request, uri: {}, detail: {}",
            request.getRequestURI(), cause == null ? "413" : cause.getMessage());
        baseRequest.setHandled(true);
        ByteBuffer body = badMessageError(HttpStatus.PAYLOAD_TOO_LARGE_413,
            HttpStatus.getMessage(HttpStatus.PAYLOAD_TOO_LARGE_413),
            baseRequest.getResponse().getHttpFields());
        response.getOutputStream().write(BufferUtil.toArray(body));
        return;
      }
      super.handle(target, baseRequest, request, response);
    }
