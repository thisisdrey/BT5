### Title
Unprivileged attacker can saturate a victim's per-account token list (`MAX_TOKENS_PER_USER`) with dust deposits/transfers, blocking the victim from opening new collateral or debt positions - (contracts/Pool.sol, contracts/DepositToken.sol)

### Summary
`Pool` tracks each account's deposit/debt tokens in `depositTokensOfAccount` / `debtTokensOfAccount` and hard-reverts any addition once the combined count reaches `MAX_TOKENS_PER_USER = 30` (`onlyIfAdditionWillNotReachMaxTokens`, contracts/Pool.sol:143-148). Entries are added from `DepositToken._transfer`/`_mint` whenever a recipient's balance goes from 0 to >0 (contracts/DepositToken.sol:518-520, 486-488). Both `DepositToken.transfer(to_, ...)` and `DepositToken.deposit(amount_, onBehalfOf_)` are permissionless entry points, so an attacker can push dust balances of every listed collateral into an arbitrary victim account until the 30-slot cap is hit, after which the victim's deposits into any new collateral type and any minting of a new synthetic (debt token) revert with `UserReachedMaxTokens`.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` are gated only by `_revertIfSenderIsNotDepositToken`/`_revertIfSenderIsNotDebtToken` plus the max-tokens modifier (contracts/Pool.sol:204-220).
- `DepositToken._transfer` adds the token to `recipient_`'s set without the recipient's consent; `deposit()` mints to an arbitrary `onBehalfOf_` (contracts/DepositToken.sol:211-237, 498-526).
- Attack: the attacker deposits a minimal amount of each supported collateral into their own account (or directly via `deposit(dust, victim)`), then calls `transfer(victim, 1 wei)` for every deposit token the victim doesn't already hold, until `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30`.
- From then on, for any `DepositToken` the victim does not already hold, `deposit(..., onBehalfOf_=victim)` and any inbound `transfer` to the victim revert, and `DebtToken.issue`/`mint` for a synthetic the victim has no debt in reverts via `addToDebtTokensOfAccount`. Critically, a victim who needs to add a *different* collateral type to restore health before liquidation cannot do so.
- No modifier stops this: `transfer`/`deposit` are `whenNotPaused`/`nonReentrant` only, no opt-in or whitelist on recipients; `SynthContext` sender resolution doesn't restrict them. The debt-side fill is only achievable through the victim's own borrowing, but the deposit side alone fully consumes the shared 30-slot budget.

### Impact Explanation
Temporary freezing of funds / liveness break: the victim cannot deposit any new collateral type, cannot receive deposit tokens, and cannot open debt in any new synthetic while saturated. If the victim's only held collaterals can't cover a needed health recovery (or they hold no collateral yet), they cannot add a new collateral to avoid liquidation — effectively blocking the only remedy transaction. Recovery requires the victim to spend gas transferring out or withdrawing each dusted token (up to 30 transactions worth of slot clearing). Matches the CVE bug class (attacker-triggered denial of service / hang-equivalent revert on a core protocol function).

### Likelihood Explanation
The attack is fully unprivileged and only costs dust amounts of real collateral (which is even lost to the victim) plus gas. It requires the pool to list more deposit tokens than the victim currently holds — realistic since pools list many collaterals and users typically hold few. The constraint that `addToDepositTokensOfAccount` reverts instead of silently no-op'ing makes the griefing deterministic and repeatable; the attacker can front-run any of the victim's deposit/mint transactions to re-saturate slots whenever one frees up.

### Recommendation
- Make unsolicited additions not count, or not revert: e.g., only add to the account list on explicit `deposit`/`issue` initiated by the account itself (or via Operator on its behalf), not on inbound `transfer`/`seize`/third-party `deposit(onBehalfOf_)`.
- Alternatively, decouple the cap check from `transfer` (allow transfers to overflow the list, or skip list insertion for transfer recipients) so griefed recipients don't propagate DoS.
- Provide a `removeFromDepositTokensOfAccount`-callable escape or auto-prune zero/dust entries so victims can cheaply recover.

### Proof of Concept
Hardhat sketch (repo already uses smock/hardhat tooling; see `test/Pool.test.ts` `should revert when reach max tokens` at test/Pool.test.ts:1386-1416 for the saturation primitive):

```ts
// given: pool with >= 2 deposit tokens listed (msdA, msdB, ...); victim holds none
// attacker: for each listed depositToken not held by victim:
await underlyingA.approve(msdA.address, 1)
await msdA.deposit(1, attacker)          // attacker mints dust share
await msdA.transfer(victim, 1)           // adds msdA to victim's list (Pool.sol:216)

// repeat until debtTokensOfAccount(victim) + depositTokensOfAccount(victim) == 30

// then: victim cannot onboard a new collateral type
await expect(msdNew.connect(victim).deposit(amount, victim))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// and cannot mint a synthetic they don't already owe
await expect(debtToken.connect(victim).issue(amount, victim))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

The existing unit test demonstrates the revert path; the PoC differs only in that `addToDepositTokensOfAccount` is triggered via `transfer`/`deposit(onBehalfOf)` targeting an unwilling `victim` rather than a self-funded account.
