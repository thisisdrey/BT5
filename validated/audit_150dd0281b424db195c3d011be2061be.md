### Title
Reliability credit granted without content-hash verification — attacker peer inflates ranking via mismatched attachments - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` credits a peer's `ReliabilityReport` as successful the moment its HTTP response decodes as a `GetAttachmentResponse`, without ever comparing the returned attachment's hash to the requested `content_hash`. An attacker peer can therefore serve any content — including content that doesn't match the requested hash — and still be rewarded with a successful-request credit, inflating its `score()` and making `AttachmentRequest::get_most_reliable_source`/`Ord::cmp` prefer it for future requests.

### Finding Description
The broken equality is: `reliability_credit_awarded == actual_hash_verified_success`. In practice, credit is awarded on HTTP decode success alone.

In `extend_with_attachments`: [1](#0-0) 
the loop does `response.decode_atlas_get_attachment()`, and on `Ok`, immediately does `self.attachments.insert(response.attachment); report.bump_successful_requests();` — there is no check that `response.attachment.hash() == request.content_hash` before granting the success credit.

The only place a hash-based reconciliation happens is later, in `AttachmentsDownloader::run`'s `Done` arm: [2](#0-1) 
which calls `network.atlasdb.find_all_attachment_instances(&attachment.hash())` — i.e., it looks up *whatever hash the attachment actually has*, not the hash that was requested. If a malicious peer returns content whose hash doesn't match `content_hash`, this lookup simply finds zero matching pending instances (since no `AttachmentInstance` was tracking that wrong hash), so no `resolved_attachments` entry is produced for the *requested* instance and the batch is (eventually) retried. But by this point `context.peers` (with the report already bumped successful) has been captured and is written back into `self.reliability_reports`: [3](#0-2) 
The credit given in `extend_with_attachments` is never rolled back based on the later hash mismatch outcome.

This directly affects ranking: `ReliabilityReport::score()` and `Ord` are purely a function of `total_requests_sent`/`total_requests_success`: [4](#0-3) 
and `AttachmentRequest::get_most_reliable_source`/`Ord::cmp` prefer peers with a higher `score()`, and `Requestable::get_url()` for `AttachmentRequest` always resolves to `get_most_reliable_source()`: [5](#0-4) 
so a peer that has served zero hash-correct attachments but many "successful" (HTTP 200, decodable) mismatched ones will out-rank honest peers and be chosen as the download source for future `AttachmentRequest`s.

Exploit flow: attacker peer advertises (in its `/v2/attachments/inv` response) that it has the attachment for a given `content_hash`/page — nothing here is validated against real content either — then when queried via `GET /v2/attachments/{content_hash}`, returns a syntactically valid `GetAttachmentResponse` body containing arbitrary attachment bytes with a different hash. The response is HTTP 200 and decodes fine, so `bump_successful_requests()` fires unconditionally. Repeating this on every batch, the attacker's `total_requests_success` grows monotonically while never having served one hash-correct attachment, permanently entrenching it in the ranking used by `get_most_reliable_source`.

### Impact Explanation
The attacker doesn't get a chance to have bad data "accepted as canonical" per se in this repo/version — the `Done` arm's hash-keyed lookup (`find_all_attachment_instances(&attachment.hash())`) prevents unrelated content from being paired with an unrelated `AttachmentInstance`, so wrong-hash data is not resolved as the *requested* attachment in this pass. But the reliability bookkeeping bug still causes a real, repeatable outcome: an attacker peer that never once serves the correct attachment can nonetheless become and remain the top-ranked/most-preferred source (`get_most_reliable_source`) for all future attachment requests, at the expense of honest peers who occasionally fail (e.g., due to timeouts) and thus rank lower. This degrades attachment-resolution reliability/availability by steering repeated attempts toward the attacker (who can then simply always return junk/wrong-hash data), producing sustained resolution failures — a form of read-endpoint availability degradation for BNS attachment resolution, without requiring any privileged role, matching the "attachment/BNS mismatch"-adjacent High-severity category via persistent steering toward an unreliable/malicious source.

### Likelihood Explanation
Low cost, fully remote, and repeatable: the attacker only needs to run an ordinary outbound-sync peer with a reachable HTTP data URL, respond to `/v2/attachments/inv` claiming to have arbitrary attachments, and respond to `/v2/attachments/{hash}` with any well-formed (but wrong-content) `GetAttachmentResponse`. No secret, no privileged role, no signature bypass is needed — the request/response cycle for attachments has no authentication and no hash-binding check at the point credit is awarded. This can be repeated on every `AttachmentsDownloader::run` cycle to keep inflating the score.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, before calling `report.bump_successful_requests()`, verify that `response.attachment.hash() == request.content_hash`; if it doesn't match, treat it as a failed request (`report.bump_failed_requests()`) and do not insert the attachment into `self.attachments`. This ties the reliability credit to actual verified-correct content rather than mere HTTP-decodability.

### Proof of Concept
Rust unit test in `stackslib/src/net/atlas/tests.rs` (or a new test in `download.rs`'s test module):
1. Construct an `AttachmentsBatchStateContext` with one `peers` entry `ReliabilityReport::empty()` for URL `"http://attacker"`.
2. Build a `BatchedRequestsResult<AttachmentRequest>` where `succeeded` contains one `AttachmentRequest { content_hash: H1, sources: {"http://attacker": report}, ... }` mapped to `Some(StacksHttpResponse)` whose body decodes via `decode_atlas_get_attachment()` into an `Attachment` whose `hash()` is `H2 != H1`.
3. Call `context.extend_with_attachments(&mut results)`.
4. Assert: `context.peers.get("http://attacker").unwrap().total_requests_success == 1` even though `H2 != H1` — i.e., `bump_successful_requests()` fired despite content-hash mismatch, proving `reliability_credit_awarded != actual_hash_verified_success`.
5. Optionally chain into `AttachmentsDownloader::run`'s `Done` arm behavior to show `resolved_attachments` remains empty for the originally-requested instance (hash mismatch causes `find_all_attachment_instances(&attachment.hash())` to return nothing) while `self.reliability_reports` for the attacker peer still reflects the bumped success count.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

impl AttachmentRequest {
    pub fn get_most_reliable_source(&self) -> (&UrlString, &ReliabilityReport) {
        self.sources
            .iter()
            .max_by_key(|(_, v)| v.score())
            .expect("Atlas: trying to select an Url out of an empty set")
    }
}

impl Hash for AttachmentRequest {
    fn hash<H: Hasher>(&self, state: &mut H) {
        self.content_hash.hash(state)
    }
}

impl Ord for AttachmentRequest {
    fn cmp(&self, other: &AttachmentRequest) -> Ordering {
        other.sources.len().cmp(&self.sources.len()).then_with(|| {
            let (_, report) = self.get_most_reliable_source();
            let (_, other_report) = other.get_most_reliable_source();
            report.cmp(other_report)
        })
    }
}

impl PartialOrd for AttachmentRequest {
    fn partial_cmp(&self, other: &AttachmentRequest) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}

impl Requestable for AttachmentRequest {
    fn get_url(&self) -> &UrlString {
        let (url, _) = self.get_most_reliable_source();
        url
    }
