### Title
Debt interest accrual rounds in users' favor — `totalSupply_` grows faster than the sum of per-account debts, so interest minted to `feeCollector` is not fully backed by borrower debt - ([File: contracts/DebtToken.sol](contracts/DebtToken.sol))

### Summary
`DebtToken._calculateInterestAccrual()` updates two quantities independently: `totalSupply_` is grown by `rate.wadMul(totalSupply_)` and `debtIndex` is grown by `rate.wadMul(debtIndex)`, both via `WadRayMath.wadMul` (half-up). User debt is then derived as `principalOf[account] * debtIndex / debtIndexOf[account]` with truncating integer division. Because the index is scaled from a fixed `1e18` base while the supply is scaled from a much larger number, and because each user's balance divides down, the sum of all users' `balanceOf` debts is systematically *less than or equal to* `totalSupply_`. The accrued difference is minted to `pool.feeCollector()` as real synthetic tokens, so the protocol pays out more interest than borrowers owe.

### Finding Description
In `_calculateInterestAccrual()` (lines 551-566):

```solidity
_interestAmountAccrued = _interestRateToAccrue.wadMul(totalSupply_);
_debtIndex += _interestRateToAccrue.wadMul(_debtIndex);
```

and in `accrueInterest()` (lines 169-178), `totalSupply_ += _interestAmountAccrued` and the same amount is minted to the fee collector. Meanwhile each user's balance in `balanceOf()` (lines 196-206) is `(_principal * _debtIndex) / debtIndexOf[account_]` — plain integer division that rounds *down*, in the borrower's favor. `wadMul` rounds half-up on the supply/index side. The result mirrors the reported `accrueFee()` bug: the recorded/claimable total debt exceeds what the sum of borrowers actually owes, and the excess is minted as spendable synthetic tokens to `feeCollector`.

The gap compounds with the number of accounts and the number of accruals. `repayAll` and `_burn` (lines 525-535) use the rounded-down `balanceOf` as the payoff, so the shortfall is never recovered from borrowers; it accumulates permanently in `totalSupply_` vs. the true aggregate debt.

### Impact Explanation
Each `accrueInterest` can mint up to ~(#accounts + 1) wei-scale synthetic units to `feeCollector` that are not backed by borrower debt (backing implicitly comes from other depositors' collateral). Over long periods and many borrowers/accruals this produces unbacked synthetic supply and "bad debt" in the pool accounting — the same solvency-invariant break as the reference finding. Magnitude per accrual is small, so it is a slow protocol-fee over-claim rather than an immediately drainable amount.

### Likelihood Explanation
The discrepancy triggers automatically on every block where interest accrues and multiple accounts exist — no privileged action, no manipulation, and no special market conditions needed. It is purely a function of ordinary operation (borrow, repay, liquidate all call `accrueInterest`). However, realizing a material amount requires sustained accumulation, and an attacker cannot meaningfully amplify it beyond creating many dust debt positions (bounded by `debtFloorInUsd` and `MAX_TOKENS_PER_USER`-style limits on the pool side).

### Recommendation
Round in the protocol's favor as in the reference fix: compute the user balance with rounding up in `balanceOf()` (`principal * index / indexOf` using a ceiling division, e.g. `wadMul` replaced by a `divUp`), or accrue `debtIndex`/`totalSupply_` with floor rounding consistently so that the sum of balances never falls below `totalSupply_`. Then harden `_burn`/`repayAll` against underflow like the reference `_repay()` adjustment:

```solidity
principalOf[account_] = _accountBalance > amount_ ? _accountBalance - amount_ : 0;
totalSupply_ = totalSupply_ > amount_ ? totalSupply_ - amount_ : 0;
```

so the last repayer is not blocked by an off-by-one dust debt.

### Proof of Concept
Hardhat fork test sketch:

```ts
// 1. Two users deposit collateral and issue msUSD debt (dust-scale positions to
//    maximize per-account truncation), e.g. issue 1 wei each after setting
//    debtFloorInUsd = 0 (test config) or many small borrowers.
await msUSDDebt.updateInterestRate(parseEther('0.1'));

// 2. Accrue over a period.
await time.increase(SECONDS_PER_YEAR);
await msUSDDebt.accrueInterest();

// 3. Compare recorded total debt vs sum of per-account debts.
const total = await msUSDDebt.totalSupply();
let sum = 0n;
for (const u of users) sum += (await msUSDDebt.balanceOf(u.address)).toBigInt();

// total - sum > 0, and the excess was minted to feeCollector:
const feeBalance = await msUSD.balanceOf(feeCollector.address);
expect(total).to.be.gt(sum);               // unbacked accrual
expect(feeBalance).to.be.gt(0);            // fee collector over-claims
```

The repository's own tests already expose the symptom: `test/DebtToken.test.ts` lines 726-727 and 937-985 only assert `closeTo` between `totalSupply()` and `balanceOf()`, i.e. they tolerate — rather than rule out — the divergence described here.
