## Title
StackerDB reconfiguration is skipped when the on-chain signer set legitimately becomes empty, leaving stale (possibly revoked) signers authorized to write - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` decides whether to push a freshly-fetched `StackerDBConfig` into the on-disk replica (which re-derives per-slot signer authorization) only under specific conditions. When the newly loaded config's signer list is empty, the reconfiguration is unconditionally skipped even if the config genuinely changed, so the previously-persisted slot-to-signer bindings remain in force.

### Finding Description
`create_or_reconfigure_stackerdbs` at [1](#0-0)  gates the call to `reconfigure_stackerdb` (which rewrites each slot's authorized `signer` per [2](#0-1) ) behind:

```
} else if (new_config != stackerdb_config && !new_config.signers.is_empty())
    || (new_config == stackerdb_config
        && new_config.signers.len() != self.get_slot_versions(&stackerdb_contract_id)?.len())
{
    // only reconfigure if the config has changed
    // (that second check on the length is needed in case the node is a victim of
    // #5142, which was a bug whereby a stackerdb could never shrink)
```

If `new_config.signers` is empty (e.g., the controlling contract now returns no signers — a legitimate state transition, such as a reward-cycle rollover where a signer set has not yet been established, or a contract intentionally clearing its signer list), the first branch's `!new_config.signers.is_empty()` guard is false, and the second branch only fires if the *old* config happens to equal the new one. Consequently `reconfigure_stackerdb` is never invoked, and the previously-stored `chunks.signer` values from `try_replace_chunk`'s authorization path — `get_slot_validation` / `SlotMetadata::verify` in [3](#0-2)  — keep referencing the *old* signer set indefinitely. This mirrors the "increaser does not change" bug class: a control value (`signers`, analogous to the Solidity `increaser`) is supposed to be updated from the authoritative source (the contract) but the setter path silently no-ops for a valid input, so the previously accepted value continues to govern authorization.

The in-memory `stacker_db_configs` map is still updated to the new (empty) config at [4](#0-3) , so the network layer believes the DB has no signers/slots, while the on-disk replica (used by `try_replace_chunk` for actual write authorization) still has the old slots and old `signer` column intact and enforced.

### Impact Explanation
This is a "stale authorization served as canonical" defect: an address that the current chain state no longer authorizes to write (because the controlling contract now reports zero signers for this cycle) can still successfully submit signed chunks that get accepted by `try_replace_chunk`, because the persisted slot's `signer` was never cleared. Depending on deployment (e.g. `.signers-*` contracts across reward-cycle boundaries), this could let a previous cycle's signer continue writing chunks that get gossiped as legitimate replica data after their authorization should have lapsed, which is a form of unauthorized write to network state.

### Likelihood Explanation
The trigger condition (a `from_smart_contract`-derived config legitimately returning an empty `signers` vector on a cycle boundary or contract state change, distinct from the failure fallback to `StackerDBConfig::noop()` which is already handled by the `existing_contract_ids` create path) is plausible but requires a somewhat specific contract-state sequence to reach; I could not fully verify from the available code whether `from_smart_contract` ever legitimately returns non-`noop` configs with an empty `signers` list in practice for `.signers-*`/`.miners` contracts, versus only doing so via the `unwrap_or_else` `noop()` fallback path (which is excluded from this bug since `noop()` configs presumably compare unequal only via the first branch, and `noop().signers` is also empty — so the same skip applies there too, but that path is a config-load failure, not a legitimate state transition). This uncertainty affects confidence in real-world reachability.

### Recommendation
Change the condition so that any config change (`new_config != stackerdb_config`) triggers reconfiguration regardless of whether `new_config.signers` is empty, e.g. by removing the `&& !new_config.signers.is_empty()` guard, or by explicitly reconfiguring to clear/wipe slots when the new signer list is empty (mirroring the shrink behavior already present in `reconfigure_stackerdb`/`shrink_stackerdb`).

### Proof of Concept
Not independently reproduced with a running node; derived from static analysis of the guard logic in `create_or_reconfigure_stackerdbs` [1](#0-0)  compared against the actual authorization check in `try_replace_chunk` [5](#0-4) , which shows that write authorization is bound to whatever was last persisted via `reconfigure_stackerdb`, not the freshly computed in-memory config.
