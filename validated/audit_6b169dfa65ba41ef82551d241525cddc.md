Audit Report

## Title
Off-by-one in BEEFY future-block-voting equivocation check (`<` instead of `<=`) - (File: substrate/frame/beefy/src/equivocation.rs)

## Summary
In `check_equivocation_proof`, the `FutureBlockVotingProof` branch rejects a proof only if `vote.commitment.block_number < frame_system::Pallet::<T>::block_number()`, meaning a vote whose `block_number` is exactly equal to the current block number is not rejected and is instead treated as valid evidence of "future block voting." This lets an unprivileged reporter submit a genuinely signed present-block vote as future-block-voting equivocation evidence, triggering a 50% slash against an honest authority.

## Finding Description
The doc comment on `FutureBlockVotingProof` states its purpose is to prove "an authority voted for a future block" [2](#0-1) . "Future" implies `block_number` strictly greater than the chain's current height. The guard implemented is:

```rust
if vote.commitment.block_number < frame_system::Pallet::<T>::block_number() {
    return Err(Error::<T>::InvalidFutureBlockVotingProof);
}
``` [3](#0-2) 

When `vote.commitment.block_number == frame_system::Pallet::<T>::block_number()`, the condition evaluates to `false`, so the guard does not reject the proof. Execution proceeds to only check the vote signature's validity before returning `Ok(())`, accepting the proof as valid future-block-voting misbehavior evidence even though the targeted block is the current block, not a future one [4](#0-3) .

This is reachable from the public extrinsics `report_future_block_voting` (signed) and `report_future_block_voting_unsigned` (validated via `ValidateUnsigned`), both routing to `T::EquivocationReportSystem::process_evidence` → `check_equivocation_proof` [5](#0-4) .

## Impact Explanation
`check_equivocation_proof`'s outcome gates whether a slashable offence is reported; `FutureBlockVotingProof` carries a fixed 50% slash fraction [6](#0-5) . Because of the off-by-one, a vote targeting the *current* block (not a future block) can be mis-accepted as future-block-voting evidence, causing an honest validator to be wrongly slashed 50% and reported as an offender — a runtime bug that compromises intended slashing behavior and can result in unwarranted loss of a validator's funds.

## Likelihood Explanation
Exploitation requires only observing/possessing a genuinely signed BEEFY vote message whose `commitment.block_number` equals the block number at the time the report extrinsic is included, and submitting the public `report_future_block_voting`/`report_future_block_voting_unsigned` extrinsic in that exact block. No malicious validator, governance, or leaked-key assumption is needed; it is a public dispatch reachable by any signed account or via unsigned validated extrinsic, making it feasible and repeatable given the narrow timing window (must land the report in the same block as the vote's `block_number`).

## Recommendation
Change the comparison to correctly identify non-future blocks:
```rust
if vote.commitment.block_number <= frame_system::Pallet::<T>::block_number() {
    return Err(Error::<T>::InvalidFutureBlockVotingProof);
}
```
This ensures only strictly future block numbers (`> current`) are accepted as valid future-block-voting equivocation evidence.

## Proof of Concept
1. Let `N = frame_system::Pallet::<T>::block_number()` at the block in which the report extrinsic will be included.
2. Obtain a genuine signed BEEFY `VoteMessage` from authority `A` whose `commitment.block_number == N`.
3. Submit `report_future_block_voting_unsigned(equivocation_proof = FutureBlockVotingProof { vote }, key_owner_proof)` in block `N`.
4. The check `vote.commitment.block_number < frame_system::Pallet::<T>::block_number()` evaluates `N < N == false`, so the guard is skipped; the signature check passes; `check_equivocation_proof` returns `Ok(())`.
5. `process_evidence` reports the offence with `slash_fraction = 50%` against authority `A`, even though `A`'s vote targeted the current block, not an actual future block.
