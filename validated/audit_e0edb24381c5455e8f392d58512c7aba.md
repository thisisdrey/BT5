### Title
Attached deposit silently retained by the wallet contract when the address-registrar or NEP-141 lookup call fails, instead of being refunded to the external caller - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The eth-implicit `WalletContract::rlp_execute` entry point is `#[payable]` and records any deposit attached by an external (non-self) caller in a `CallerDeposit` struct so it can be refunded if the eventual cross-account action fails [1](#0-0) . This refund is correctly performed in `rlp_execute_callback` on `PromiseResult::Failed` [2](#0-1) , but the same `caller_deposit` is silently dropped (never refunded) in the failure branches of `address_check_callback` and `nep_141_storage_balance_callback`, which are the callbacks used after querying an *external, unprivileged* helper contract (the address registrar, or a NEP-141 token's `storage_balance_of`).

### Finding Description
`inner_rlp_execute` computes `caller_deposit` from the attached deposit whenever the predecessor differs from the current account (i.e., a relayer/external caller pays for the transaction) [3](#0-2) . For two transaction kinds this deposit is threaded through an intermediate cross-contract call before reaching `rlp_execute_callback`:

- `EOABaseTokenTransfer` with an `address_check`, which first calls the external address registrar and only reaches `rlp_execute_callback` (and thus the refund logic) if the lookup succeeds and parses correctly [4](#0-3) .
- `ERC20Transfer`, which first calls the token contract's `storage_balance_of` before ever reaching `rlp_execute_callback` [5](#0-4) .

In `address_check_callback`, when the address-registrar promise fails, or when its returned value cannot be deserialized, the function returns an `ExecuteResponse { success: false, .. }` directly — without ever using `caller_deposit` to issue a refund transfer: [6](#0-5) 

The same pattern occurs in `nep_141_storage_balance_callback` on `PromiseResult::Failed`, on JSON-parse failure, and on the "expected function call action" branch — none of these paths touch `caller_deposit` before returning a failure response [7](#0-6) [8](#0-7) .

Because `rlp_execute` is `#[payable]`, the NEAR protocol credits the attached deposit to the wallet contract's own account balance unconditionally when the `FunctionCall` action itself executes without panicking (per the runtime's action-execution semantics, deposits are transferred as part of executing the action, independent of the Rust-level return value) [9](#0-8) . Returning `ExecuteResponse{success:false,...}` (rather than panicking) is a *successful* execution outcome from the runtime's point of view, so none of the protocol-level automatic refund machinery (`refund_unspent_gas_and_deposits`, deposit refunds on failed receipts) is triggered [10](#0-9) . The only way the caller gets its deposit back is if the contract explicitly re-transfers it — which these two failure branches omit.

This is the exact bug class from the external report: an external/asynchronous call (here, the address-registrar lookup or a token's `storage_balance_of` query) can fail or return unexpected data, and the calling contract has no "catch" path that forwards/refunds the already-received funds, so they end up stuck with the wrong party.

### Impact Explanation
Any external account (typically a relayer paying the deposit on behalf of an ETH-emulated transaction) that calls `rlp_execute` targeting either (a) another eth-implicit account (triggering `address_check`) or (b) an ERC-20 transfer (triggering the NEP-141 storage-balance check) can have its attached deposit permanently retained by the target wallet contract if the intermediate helper call fails or returns malformed data — a state fully reachable via an ordinary, unprivileged registrar/token contract being down, buggy, or adversarial. The caller receives `ExecuteResponse{success:false}` and no funds back, while the wallet contract's balance is permanently increased by the deposit amount. This is a concrete, permanent loss of funds for the caller (and unearned gain for the wallet account), matching the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
This requires only an ordinary relayer/external signer to invoke `rlp_execute` with two specific transaction shapes (base-token transfer to another eth-implicit address, or an ERC-20 transfer) while attaching a deposit, combined with the downstream external contract (address registrar or NEP-141 token) failing or returning malformed output — plausible under normal operating conditions (e.g., registrar/token contract paused, out of gas, or temporarily unavailable), with no privileged/node-level access needed.

### Recommendation
In `address_check_callback` and `nep_141_storage_balance_callback`, refund `caller_deposit` (via `env::promise_batch_create`/`promise_batch_action_transfer`, mirroring `rlp_execute_callback`) in every early-return failure branch (`PromiseResult::Failed`, JSON-deserialize errors, and the "expected FunctionCall action" mismatch), before constructing the failing `ExecuteResponse`.

### Proof of Concept
1. An external relayer account `R` calls `rlp_execute` on wallet contract `W` (an eth-implicit account) with `tx_bytes_b64` encoding an `EOABaseTokenTransfer` whose `target` is another eth-implicit account, attaching `N` yoctoNEAR as deposit.
2. `inner_rlp_execute` computes `caller_deposit = Some(CallerDeposit{account_id: R, yocto_near: N})` and issues `address_registrar.lookup(...).then(address_check_callback(target, action, caller_deposit))` [11](#0-10) .
3. The address registrar contract call fails (e.g., it panics, is paused, or does not exist).
4. `address_check_callback` observes `PromiseResult::Failed` and returns `ExecuteResponse{success:false, error: Some("Call to Address Registrar contract failed")}` without refunding `caller_deposit` to `R` [12](#0-11) .
5. `R`'s `N` yoctoNEAR, already credited to `W`'s balance by the protocol when the payable `rlp_execute` FunctionCall executed, is never returned; `R` has permanently lost it while `W` keeps it.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
