### Title
Unbounded `contractType` from `getTypeValue()` causes out-of-bounds `ByteString.byteAt` access in permission-operations check - (File: `chainbase/src/main/java/org/tron/common/utils/WalletUtil.java`)

### Summary
`WalletUtil.checkPermissionOperations` (mirrored in `actuator/src/main/java/org/tron/core/utils/TransactionUtil.java`) computes a byte-array index from `contract.getTypeValue()`, the raw wire integer of the `Transaction.Contract.type` protobuf enum field, without validating it is within `[0, 255]`. This is the same bug class as the nanoMODBUS CVE: an attacker-controlled field taken directly off the wire is used as an index into a small fixed-size buffer (`operations`, a 32-byte `ByteString`) without a bounds check.

### Finding Description
`checkPermissionOperations` is: [1](#0-0) 

```java
public static boolean checkPermissionOperations(Permission permission, Contract contract)
    throws PermissionException {
  ByteString operations = permission.getOperations();
  if (operations.size() != 32) {
    throw new PermissionException(...);
  }
  int contractType = contract.getTypeValue();
  boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
  return b;
}
```

`contract.getTypeValue()` returns the raw `int32` that was on the wire for the `ContractType` enum field [2](#0-1) . Because protobuf3 open enums preserve unrecognized numeric values via the `*Value()` accessor, an attacker who crafts a raw transaction can set this field to **any int32** (e.g. `2000000000`, `-8`, `Integer.MIN_VALUE`), not just a value corresponding to a defined `ContractType`. There is no validation of `contractType` before it is divided by 8 and used as an index into the fixed 32-byte `operations` buffer via `ByteString.byteAt(index)`.

`ByteString.byteAt` performs its own bounds check and throws `IndexOutOfBoundsException` for any index outside `[0,31]` — this differs from the C original (which would corrupt memory), but in java-tron it manifests as an **uncaught, unchecked `RuntimeException`** thrown from deep inside transaction/signature validation.

The duplicate implementation in `TransactionUtil.checkPermissionOperations` has the identical flaw: [3](#0-2) 

### Impact Explanation
`checkPermissionOperations` is reached from the core signature-validation path for any multi-sig transaction that uses a non-default active permission (`permissionId != 0`):
- `TransactionCapsule.checkPermission` → called from `TransactionCapsule.validateSignature` (used during `validatePubSignature`, part of standard transaction acceptance) and from `TransactionCapsule.addSign` [4](#0-3) .
- `Wallet.getTransactionApprovedList` / `getTransactionSignWeight` (query API endpoints reachable by any client) also call this code directly [5](#0-4)  and [6](#0-5) .

In `validatePubSignature`, only `SignatureException | PermissionException | SignatureFormatException` are caught [7](#0-6)  — an `IndexOutOfBoundsException` from `byteAt` is **not** caught there and will propagate as an unhandled `RuntimeException` through the transaction-validation call chain. Depending on where in `Manager`/transaction-pool processing this is invoked, this can crash the processing thread or the node (denial of service on the whole node, i.e., "node crash/halt"), which meets the Critical impact bar even though it does not achieve memory corruption/RCE in the JVM sandbox (Java always bounds-checks array/`ByteString` access).

### Likelihood Explanation
High: any account with an `AccountPermissionUpdateContract`-based active permission (a normal, supported multisig feature) can be targeted by a transaction whose `Contract.type` field is set to an out-of-range raw value. Constructing such a transaction requires only building a raw protobuf `Transaction` with a manually-crafted `type` field (bypassing the typed enum setter, e.g. via reflection/raw serialization or a modified client), then submitting it via broadcast or via the `getTransactionApprovedList`/`getTransactionSignWeight` query APIs — both are plain unauthenticated/unprivileged API calls that do not require the transaction be otherwise valid, and both directly reach the vulnerable code without gating on the actuator's `ContractType` dispatch first.

### Recommendation
Bound-check `contractType` before using it as an index in both `WalletUtil.checkPermissionOperations` and `TransactionUtil.checkPermissionOperations`:
- Reject (throw `PermissionException`) if `contractType < 0 || contractType > 255` before computing `contractType / 8` / `contractType % 8`.
- Alternatively, validate `contract.getType() != ContractType.UNRECOGNIZED` first, since `getType()` normalizes unrecognized wire values to the sentinel `UNRECOGNIZED` value, and use that check to short-circuit before calling `getTypeValue()`.

### Proof of Concept
1. Build an account with a custom Active `Permission` (via `AccountPermissionUpdateContract`), which requires `permissionId != 0` on subsequent transactions signed with that permission — a normal, supported feature.
2. Construct a raw `Transaction` whose `raw_data.contract[0].type` field is serialized with an out-of-range varint (e.g. `2000000000`), and `permission_id` set to the custom permission's id. This bypasses the generated Java enum setter by writing the wire bytes directly (e.g., using `CodedOutputStream`/reflection or a patched protobuf builder), which is possible because protobuf's wire format does not enforce enum range.
3. Submit the transaction via `broadcastTransaction`/`getTransactionApprovedList`/`getTransactionSignWeight`.
4. `checkPermissionOperations` computes `contractType / 8` (≈ 250000000), calls `operations.byteAt(250000000)` on a 32-byte `ByteString`, which throws `IndexOutOfBoundsException`, an unchecked exception not caught by the surrounding `catch` clauses in `validatePubSignature`/`validateSignature`, propagating up the call stack.
