## Cross-StackerDB signature replay due to missing contract binding in `SlotMetadata::auth_digest()` - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::sign`/`verify` authenticate a StackerDB chunk write using a digest that commits only to `slot_id`, `slot_version`, and `data_hash` — it never binds the signature to the specific StackerDB (`QualifiedContractIdentifier`) the write is destined for. Because many Nakamoto signer StackerDB contracts (`signers-0-{message_id}` / `signers-1-{message_id}`) intentionally reuse the exact same slot→signer-address mapping for a given signer set, a chunk that is validly signed and broadcast for one message-type StackerDB is also a validly-signed chunk for every other StackerDB contract that shares that mapping. This lets an unprivileged network peer replay an observed, legitimately-signed chunk into a different (wrong-purpose) StackerDB replica, without possessing any private key.

### Finding Description
`SlotMetadata::auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`sign()`/`verify()` operate purely on this digest and a `StacksAddress` principal — with no reference to which StackerDB contract the chunk is for: [2](#0-1) 

Both server-side write paths validate a chunk purely by (a) looking up the *expected signer address* for `(smart_contract_id, slot_id)` from local config/DB, and (b) calling `slot_desc.verify(&addr)` — which, per the digest above, doesn't care which contract that lookup came from:
- HTTP POST path: `StackerDBTx::try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` [3](#0-2) 
- P2P push path: `StackerDBs::validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs` [4](#0-3) 

Critically, by design, many signer-message StackerDBs share an identical slot-to-signer mapping. The `.signers` boot contract stores exactly two lists (`stackerdb-signer-slots-0`/`-1`, one per signer-set parity), and every `signers-{set}-{message_id}` contract (for all `message_id` in `0..SIGNER_SLOTS_PER_USER`) simply forwards to the same underlying page: [5](#0-4) [6](#0-5) 

This is explicitly confirmed by the test `signers_db_get_slots`, which iterates every `signers-{set}-{message_id}` contract for a given `signer_set` and asserts they all return the identical signer-slot list/order: [7](#0-6) 

Consequently, `slot_id -> signer address` is identical across every `signers-0-*` contract (and separately, every `signers-1-*` contract) for a given reward cycle. Since the signature over a chunk never commits to the target contract, a signature produced to authorize slot `N` in `signers-0-A` (e.g., the "block response" message DB) is bit-for-bit valid to authorize slot `N` in `signers-0-B` (e.g., a different message-type DB, such as a mock-signature or transaction DB) for the *same* signer address. The chunk bytes themselves are public — they are broadcast via P2P (`StackerDBPushChunk`) and independently servable via the unauthenticated `GET` StackerDB endpoints — so no secret is required for a remote, unprivileged peer to capture and cross-post a valid chunk to a different contract.

### Impact Explanation
This breaks the intended equality "signed by X for DB=D, slot=N, version=V" vs. what the node actually enforces: "signed by X for slot=N, version=V" (any D with the same slot→X mapping). An attacker can inject or overwrite content in a StackerDB contract other than the one the original signer intended, as long as the replayed `slot_version` exceeds the target replica's current stored version and the payload fits the target's `chunk_size` (all signer StackerDBs share the same `CHUNK_SIZE` per `signers.clar`). This is an unauthorized write into another logically-scoped StackerDB slot without possession of the signer's private key — matching the "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" impact categories, since a successfully stored chunk is then rebroadcast to peers via `process_stacker_db_chunks`: [8](#0-7) 

The severity depends on what downstream consumers (e.g. `libsigner` message parsers, block-response aggregation) do when they encounter a message of the wrong type/DB context, but at minimum it is a forged-data propagation and slot-squatting/DoS primitive against a specific message-type StackerDB (an attacker can "consume" a signer's slot in an unrelated DB, preventing the legitimate signer from later writing a higher version there without further replay).

### Likelihood Explanation
High, in principle: any peer replicating both source and target StackerDBs can observe a valid chunk publicly (broadcast or read via HTTP GET) and resubmit it verbatim to the sibling contract via the standard `POST /v2/stackerdb/.../chunks` endpoint or P2P push — no cryptography needs to be broken. The primary constraint is version/ordering: the replay must land before/instead of the legitimate write to the target slot for that version, and the practical value depends on how tightly the various signer message types are semantically distinguished by consumers.

### Recommendation
Include a domain-separating identifier in `SlotMetadata::auth_digest()` — at minimum the target `QualifiedContractIdentifier` (and ideally the current reward cycle / signer-set discriminator) — so that a signature is only valid for the specific StackerDB it was created for:
```rust
fn auth_digest(&self, smart_contract: &QualifiedContractIdentifier) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(smart_contract.to_string().as_bytes());
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
This requires updating `sign()`/`verify()` call sites (`StackerDBChunkData::sign`/`verify`, `try_replace_chunk`, `validate_received_chunk`, and all signer/miner clients that build `StackerDBChunkData`) to pass the contract ID being written to, and is a breaking wire-format/protocol change requiring careful rollout coordination.

### Proof of Concept
1. Have signer key `K` legitimately sign and publish chunk `(slot_id=N, slot_version=V, data)` for contract `signers-0-A` (any message-type StackerDB where `K` occupies slot `N`), e.g., via `StackerDBChunkData::sign` as used in `stacks-node/src/nakamoto_node/signer_coordinator.rs` (`send_miners_message`) or the signer client.
2. As an unrelated network peer, fetch this chunk publicly — either observed from `StackerDBPushChunk` gossip or via the unauthenticated chunk-download RPC.
3. Determine (via the public `.signers` contract calls, e.g. `stackerdb-get-signer-slots-page`) that `signers-0-B` (a sibling message-type contract for the same signer set) assigns the same slot `N` to the same address `K` — guaranteed by design per `signers_db_get_slots`.
4. Re-POST the identical `(slot_id=N, slot_version=V', sig, data)` tuple (bumping `slot_version` if needed to exceed `signers-0-B`'s current stored version for slot `N`) to `signers-0-B`'s StackerDB endpoint.
5. Observe `try_replace_chunk`/`validate_received_chunk` accept the write because `slot_desc.verify(&addr)` succeeds — the signature was never bound to `signers-0-A`, so it validates equally for `signers-0-B`. The node then stores and rebroadcasts the cross-posted chunk as if `K` had legitimately written it to `signers-0-B`.

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
