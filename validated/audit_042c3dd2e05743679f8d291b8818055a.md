### Title
`FederatedKeyless` Public Key Incorrectly Mapped to `AnyPublicKey::Keyless` in `SingleKeySignature` REST API Conversion, Causing Federated Keyless Transaction Submission to Always Fail — (`File: api/types/src/transaction.rs`)

---

### Summary

In `TryFrom<&SingleKeySignature> for AccountAuthenticator`, the `PublicKey::FederatedKeyless` arm calls `AnyPublicKey::keyless(key)` instead of `AnyPublicKey::federated_keyless(key)`. The parallel `MultiKeySignature` path correctly calls `AnyPublicKey::federated_keyless(key)`. This is the direct Aptos analog of the ZetaChain M-03 bug: one path (SingleKeySignature) silently mishandles a valid key type (FederatedKeyless), while the sibling path (MultiKeySignature) handles it correctly.

---

### Finding Description

In `api/types/src/transaction.rs`, the `TryFrom<&SingleKeySignature> for AccountAuthenticator` implementation converts each `PublicKey` variant to the corresponding `AnyPublicKey` variant. All variants are handled correctly **except** `PublicKey::FederatedKeyless`:

```rust
// api/types/src/transaction.rs, lines 2109-2114
PublicKey::FederatedKeyless(ref p) => {
    let key = p.value.inner().try_into().context(
        "Failed to parse given public_key bytes as AnyPublicKey::FederatedKeyless",
    )?;
    AnyPublicKey::keyless(key)   // ← BUG: should be AnyPublicKey::federated_keyless(key)
},
``` [1](#0-0) 

The `try_into()` call attempts to deserialize the raw bytes of a `FederatedKeylessPublicKey` as a `KeylessPublicKey` (the type inferred from the `AnyPublicKey::keyless(key)` call). Because `FederatedKeylessPublicKey` has a different BCS layout (it contains an additional `jwk_addr: AccountAddress` field prepended before the inner `KeylessPublicKey`), this deserialization will fail, and the entire conversion returns an error. [2](#0-1) 

The **correct** implementation exists in two other places in the same file:

1. `TryFrom<&PublicKey> for AnyPublicKey` (line 1982–1984) correctly calls `AnyPublicKey::federated_keyless(...)`: [3](#0-2) 

2. `TryFrom<&MultiKeySignature> for AccountAuthenticator` (lines 2250–2255) also correctly calls `AnyPublicKey::federated_keyless(key)`: [4](#0-3) 

The asymmetry is exact: `MultiKeySignature` → correct; `SingleKeySignature` → wrong. This mirrors the ZetaChain pattern where `AddToOutTxTracker` handled Bitcoin correctly but `AddToInTxTracker` did not.

---

### Impact Explanation

Any REST API client that submits a `SingleKeySignature` transaction with a `FederatedKeyless` public key will receive a deserialization error from the API layer. The transaction is rejected before it ever reaches the mempool or VM. Federated keyless account holders — whose accounts are derived from `AnyPublicKey::FederatedKeyless` — cannot submit transactions via the standard REST API single-key path. Their on-chain assets are inaccessible through this path.

The `get_authenticators` function in `types/src/keyless/mod.rs` matches on `AnyPublicKey::FederatedKeyless` to extract federated keyless authenticators for JWK validation at the custom `jwk_addr`. If the wrong variant were somehow stored (e.g., if deserialization accidentally succeeded), the federated JWK lookup would be skipped and the transaction would fail validation at the VM level. [5](#0-4) 

---

### Likelihood Explanation

Any user with a federated keyless account who submits a transaction via the REST API using the `SingleKeySignature` format will trigger this bug. The REST API is the primary production submission path. The `FederatedKeyless` scheme is a documented, supported authenticator type. The bug is deterministic: every such submission fails.

---

### Recommendation

Change line 2113 in `api/types/src/transaction.rs` from:

```rust
AnyPublicKey::keyless(key)
```

to:

```rust
AnyPublicKey::federated_keyless(key)
```

This matches the correct behavior already present in `TryFrom<&PublicKey> for AnyPublicKey` and `TryFrom<&MultiKeySignature> for AccountAuthenticator`.

---

### Proof of Concept

1. Create a federated keyless account with a `FederatedKeylessPublicKey` (containing a `jwk_addr` and inner `KeylessPublicKey`).
2. Construct a `SingleKeySignature` REST API payload with `public_key.type = "federated_keyless"` and the BCS-serialized `FederatedKeylessPublicKey` bytes.
3. Submit via `POST /v1/transactions`.
4. The `TryFrom<&SingleKeySignature> for AccountAuthenticator` conversion is invoked. The `PublicKey::FederatedKeyless` arm calls `p.value.inner().try_into()` targeting `KeylessPublicKey`. BCS deserialization of `FederatedKeylessPublicKey` bytes as `KeylessPublicKey` fails (the leading `jwk_addr` bytes corrupt the parse).
5. The API returns an error. The transaction is never submitted.
6. Repeat with `MultiKeySignature` containing the same `FederatedKeyless` key: it succeeds, confirming the bug is isolated to the `SingleKeySignature` path. [6](#0-5) [7](#0-6)
