## Title
Updating `TOTAL_ENERGY_LIMIT` via a committee proposal fails to recompute `TOTAL_ENERGY_TARGET_LIMIT`, causing incorrect adaptive energy limit adjustment - (File: `framework/src/main/java/org/tron/core/consensus/ProposalService.java`)

### Summary
`DynamicPropertiesStore` caches a derived value, `TOTAL_ENERGY_TARGET_LIMIT`, computed as `TOTAL_ENERGY_LIMIT / ratio` (default ratio 14400, or the configured `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO`). This cached target is compared against the rolling `TOTAL_ENERGY_AVERAGE_USAGE` in `EnergyProcessor.updateAdaptiveTotalEnergyLimit()` to decide whether the network-wide adaptive energy limit (`TOTAL_ENERGY_CURRENT_LIMIT`) should shrink or expand each maintenance cycle. When the `TOTAL_ENERGY_LIMIT` chain parameter itself is changed through a proposal, `TOTAL_ENERGY_TARGET_LIMIT` is never recalculated, so the tuning target becomes stale relative to the new base limit — directly analogous to `BondBaseSDA.setIntervals` failing to refresh `meta.tuneBelowCapacity` after changing `tuneInterval`.

### Finding Description
`ProposalService.process` handles multiple proposal types that influence the adaptive-energy tuning system:

- `case TOTAL_ENERGY_LIMIT`: only calls `saveTotalEnergyLimit(entry.getValue())` — it does **not** touch `TOTAL_ENERGY_TARGET_LIMIT`. [1](#0-0) 

- By contrast, `case ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` and the one-time `ALLOW_ADAPTIVE_ENERGY` activation branch both correctly recompute `TOTAL_ENERGY_TARGET_LIMIT = TOTAL_ENERGY_LIMIT / ratio` whenever the ratio changes: [2](#0-1) [3](#0-2) 

This asymmetry shows the derived relationship `targetLimit = totalLimit / ratio` is understood by the code (it's maintained on ratio-change and on adaptive-energy activation) but is missed on the `TOTAL_ENERGY_LIMIT` value-change path, leaving `TOTAL_ENERGY_TARGET_LIMIT` stale exactly like `meta.tuneBelowCapacity` was stale after `BondBaseSDA.setIntervals` changed `tuneInterval`.

The stale target is consumed on every block by the adaptive-energy tuning logic that every unprivileged TVM contract-calling transaction relies on for its available energy: [4](#0-3) 

The only place `TOTAL_ENERGY_TARGET_LIMIT` is otherwise initialized is at genesis / DB bootstrap (`getTotalEnergyLimit() / 14400`), which is a one-time default, not a resync on later parameter changes: [5](#0-4) 

### Impact Explanation
`TOTAL_ENERGY_CURRENT_LIMIT` is the actual per-cycle cap on network energy dispensed to all TVM contract calls/deployments (an unprivileged, permissionless action reachable by any account). If `TOTAL_ENERGY_LIMIT` is increased (e.g., committee raises total network energy capacity) without a corresponding recompute of `TOTAL_ENERGY_TARGET_LIMIT`, the target stays anchored to the old, smaller base:
- `updateAdaptiveTotalEnergyLimit()` will keep comparing current average usage against the outdated (too-low) target, causing the adaptive current limit to be perpetually throttled/shrunk (`CONTRACT_RATE`) even though usage is well within the intended new capacity — degrading throughput/energy availability for every contract caller on the network.
- Conversely, if `TOTAL_ENERGY_LIMIT` is decreased, the stale (too-high) target keeps signaling "expand," so `TOTAL_ENERGY_CURRENT_LIMIT` will be allowed to grow beyond the new, lower `totalEnergyLimit` bound intended by the parameter change (bounded only by `totalEnergyLimit * adaptiveResourceLimitMultiplier`), letting the network dispense more energy than the newly configured ceiling was meant to allow.

This is a resource-metering correctness bug affecting the adaptive energy mechanism used by every contract-calling transaction network-wide — not a low/no-impact issue, since it directly misprices/misallocates the shared energy resource that underpins TVM execution for all users.

### Likelihood Explanation
The trigger is a legitimate, expected governance action (a proposal changing `TOTAL_ENERGY_LIMIT`) — not a malicious-SR/committee scenario; committees are expected to periodically tune network-wide resource limits over time as network usage grows. Every such adjustment silently leaves `TOTAL_ENERGY_TARGET_LIMIT` stale until either `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` is separately proposed (which happens to also refresh the target) or `ALLOW_ADAPTIVE_ENERGY` is toggled from 0 (a one-time event). In practice this makes the bug highly likely to manifest after any standalone `TOTAL_ENERGY_LIMIT` adjustment, persisting until an unrelated proposal happens to correct it.

### Recommendation
In `ProposalService.process`, in the `case TOTAL_ENERGY_LIMIT` branch, recompute and save `TOTAL_ENERGY_TARGET_LIMIT` using the currently configured `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` immediately after `saveTotalEnergyLimit`, mirroring the logic already used in the `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` and `ALLOW_ADAPTIVE_ENERGY` cases, e.g.:
```java
case TOTAL_ENERGY_LIMIT: {
  manager.getDynamicPropertiesStore().saveTotalEnergyLimit(entry.getValue());
  manager.getDynamicPropertiesStore().saveTotalEnergyTargetLimit(
      entry.getValue() / manager.getDynamicPropertiesStore().getAdaptiveResourceLimitTargetRatio());
  break;
}
```

### Proof of Concept
1. Assume default state: `TOTAL_ENERGY_LIMIT = L0`, ratio `R` (default 14400), so `TOTAL_ENERGY_TARGET_LIMIT = L0 / R` (see initialization at [5](#0-4) ).
2. A committee proposal of type `TOTAL_ENERGY_LIMIT` is approved, setting the new limit `L1 = 2 * L0` via `ProposalService.process` → `case TOTAL_ENERGY_LIMIT` ( [1](#0-0) ). `TOTAL_ENERGY_TARGET_LIMIT` remains `L0 / R` (stale, half of what it should be relative to `L1`).
3. On subsequent blocks, any unprivileged account submits TVM contract-call transactions consuming energy, driving `TOTAL_ENERGY_AVERAGE_USAGE` up via `updateTotalEnergyAverageUsage()`.
4. `EnergyProcessor.updateAdaptiveTotalEnergyLimit()` compares `totalEnergyAverageUsage` against the stale `targetTotalEnergyLimit = L0/R` instead of `L1/R` ( [6](#0-5) ). Because the stale target is half of the intended value, average usage crosses it far earlier than intended, causing `TOTAL_ENERGY_CURRENT_LIMIT` to be scaled down (`CONTRACT_RATE`) even though usage is well within the newly-doubled capacity `L1` — throttling energy availability for all contract-calling transactions network-wide despite the committee's intent to expand capacity.

  public void updateAdaptiveTotalEnergyLimit() {
    long totalEnergyAverageUsage = dynamicPropertiesStore
        .getTotalEnergyAverageUsage();
    long targetTotalEnergyLimit = dynamicPropertiesStore.getTotalEnergyTargetLimit();
    long totalEnergyCurrentLimit = dynamicPropertiesStore
        .getTotalEnergyCurrentLimit();
    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyLimit();

    long result;
    if (totalEnergyAverageUsage > targetTotalEnergyLimit) {
      result = scaleByRate(totalEnergyCurrentLimit,
          AdaptiveResourceLimitConstants.CONTRACT_RATE_NUMERATOR,
          AdaptiveResourceLimitConstants.CONTRACT_RATE_DENOMINATOR);
    } else {
      result = scaleByRate(totalEnergyCurrentLimit,
          AdaptiveResourceLimitConstants.EXPAND_RATE_NUMERATOR,
          AdaptiveResourceLimitConstants.EXPAND_RATE_DENOMINATOR);
    }
    long upperBound = hardenCalculation()
        ? BigInteger.valueOf(totalEnergyLimit).multiply(BigInteger.valueOf(
            dynamicPropertiesStore.getAdaptiveResourceLimitMultiplier())).longValueExact()
        : totalEnergyLimit * dynamicPropertiesStore.getAdaptiveResourceLimitMultiplier();
    result = min(max(result, totalEnergyLimit, this.disableJavaLangMath()),
        upperBound, this.disableJavaLangMath());

    dynamicPropertiesStore.saveTotalEnergyCurrentLimit(result);
    logger.debug("Adjust totalEnergyCurrentLimit, old: {}, new: {}.",
        totalEnergyCurrentLimit, result);
  }
