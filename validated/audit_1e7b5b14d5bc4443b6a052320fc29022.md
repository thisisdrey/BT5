## Finding

Analog identified in the git repository rule's submodule handling in `tools/build_defs/repo/git_worker.bzl`.

### Title
Malicious Git submodule URL bypasses Git's protocol sandboxing to read arbitrary local paths during `git_repository` fetch - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`'s submodule update path force-enables the `file` transport for submodules (`protocol.file.allow=always`), removing Git's own protection against submodule-URL-driven local path traversal, and does not set any `GIT_ALLOW_PROTOCOL`/`protocol.allow` restriction otherwise.

### Finding Description
When `init_submodules` or `recursive_init_submodules` is set on a `git_repository`, Bazel runs: [1](#0-0) 

`update_submodules` explicitly passes `-c protocol.file.allow=always` to `git submodule update --init [--recursive] --checkout --force`. This override was added to work around Bazel issue #17040 (see the comment at lines 211-214), but it also disables Git's normal restriction on submodules being able to specify local `file://` (or bare absolute path) URLs in `.gitmodules`.

The `.gitmodules` file and its submodule URLs are part of the fetched repository's own content, i.e., attacker-controlled data if the attacker has write access to the branch/tag/commit that the victim's `git_repository` rule checks out (exactly the threat model of CVE-2021-34426: "a malicious actor with write access to a user's Git repository"). Since Bazel does not otherwise restrict the transport allow-list (no `GIT_ALLOW_PROTOCOL` is set anywhere in the execution helper): [2](#0-1) 

a malicious `.gitmodules` entry with a `file://` or plain absolute local path (e.g., pointing at another local git-cloneable directory such as a sibling checkout, `.ssh`, cache directories, or CI-runner-local repos) will be honored by `git submodule update`, cloning that local directory's tracked content into the external repository tree that Bazel subsequently builds from.

This breaks the "fetched content stays contained to its declared source" invariant: the `git_repository` rule is supposed to materialize only the content of the declared `remote` at the declared `commit`/`tag`/`branch`, but a submodule reference inside that content can redirect a `git submodule update` invocation to read from any other local path reachable by the build machine's Git binary.

### Impact Explanation
An attacker who can push a branch/tag/commit to a repository referenced by a `git_repository` rule (or influence an untrusted PR branch that CI builds with `init_submodules = True`) can cause the victim's build to copy the contents of an arbitrary local directory (any other checked-out git repository on the build host, potentially containing credentials, other proprietary source trees, or CI secrets baked into a git-tracked file) into the fetched external repository's file tree, where it becomes readable to genrules/build actions and can be exfiltrated or leaked through build outputs. This is a read-outside-repository containment violation reachable purely from attacker-published Git content.

### Likelihood Explanation
Requires `init_submodules`/`recursive_init_submodules = True` (default `False`, but common for large aggregate projects) and requires the attacker to control the content fetched by the `git_repository` (write access to the source repo, or an untrusted branch built by CI). This mirrors the exact precondition of CVE-2021-34426 and is plausible in CI pipelines that build external/community-contributed branches.

### Recommendation
Do not force `protocol.file.allow=always` for submodule updates driven by remote/attacker-suppliable repository content. Instead, scope the allowance narrowly (e.g., only allow `file://` submodules when the top-level `remote` itself is a local path, or require an explicit opt-in attribute on `git_repository`), and set an explicit `GIT_ALLOW_PROTOCOL`/`protocol.allow` allow-list (e.g., `https`/`ssh`/`git` only, denying `file`/`ext`) for all git invocations issued by Bazel's git worker, restoring Git's default submodule protocol sandboxing.

### Proof of Concept
1. Attacker-controlled repo `evil.git` at some `tag`/`commit` contains a `.gitmodules` file:
   ```
   [submodule "leak"]
       path = leak
       url = file:///home/victim/.ssh
   ```
   (or an absolute path to another local git repository on the CI runner, e.g. a sibling checkout containing secrets tracked in git).
2. Victim's `MODULE.bazel` declares:
   ```python
   git_repository(
       name = "dep",
       remote = "https://example.com/evil.git",
       tag = "v1",
       recursive_init_submodules = True,
   )
   ```
3. During `bazel build`, `_update` invokes `update_submodules(ctx, git_repo, recursive = True)`, which runs `git -c protocol.file.allow=always submodule update --init --recursive --checkout --force`. Git happily clones `file:///home/victim/.ssh` into `external/+git_repository+dep/leak/`, materializing the victim's private SSH directory contents inside the Bazel-managed external repository tree, which is then readable to any build rule referencing `@dep//...`.
4. A `BuildIntegrationTestCase`/`src/test/shell/bazel/starlark_git_repository_test.sh`-style test can be constructed analogous to `test_git_repository_refetched_when_commit_changes` (in `src/test/shell/bazel/starlark_git_repository_test.sh`) that creates a local "victim" directory with a sentinel file, creates a "submodule-referencing" repo whose `.gitmodules` points at that victim directory via `file://`, sets `recursive_init_submodules = True`, and asserts the sentinel file ends up copied into the Bazel external repository output, proving cross-directory containment is broken. def update_submodules(ctx, git_repo, recursive = False):
```text
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```
