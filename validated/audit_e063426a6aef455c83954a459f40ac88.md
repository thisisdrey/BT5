### Title
Unstaked QUIC traffic can saturate the shared `packet_batch_sender` channel via `try_send`, dropping legitimate staked packets - (File: streamer/src/nonblocking/quic.rs)

### Summary
`handle_chunks` pushes every finished stream's packet onto a single bounded `crossbeam_channel::Sender<PacketBatch>` shared by all connections (staked and unstaked) via `packet_sender.try_send(packet_batch)`, with no priority ordering. [1](#0-0)  The per-connection stream throttle for unstaked peers is a fixed budget (`MAX_UNSTAKED_TPS = 200` per connection) that is not counted into the shared load EMA used for dynamic staked throttling, so many concurrent unstaked connections can aggregate to a large sustained packet rate into the shared channel and cause `TrySendError::Full` for packets from any sender, including staked ones, once the fixed-capacity channel (e.g., `TPU_CHANNEL_SIZE = 50_000` in `core/src/tpu.rs`) fills up. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`handle_chunks` is the terminal point of the QUIC stream-reassembly path: once a stream finishes, it builds a `PacketBatch::Single(packet)` and calls `packet_sender.try_send(packet_batch)` on a single `Sender<PacketBatch>` that is shared across *all* connections on that streamer instance, regardless of `ConnectionPeerType` (staked or unstaked). [5](#0-4) [1](#0-0)  This is a plain bounded crossbeam channel with no separate lanes or priority scheduling between traffic classes; production wiring in `core/src/tpu.rs` sizes this channel at `TPU_CHANNEL_SIZE = 50_000` for the general (non-vote) TPU QUIC streamer. [4](#0-3) 

Admission to the channel is gated only by per-connection stream throttling (`throttle_stream` / `ConnectionStreamCounter`), which enforces a rate cap per individual connection, not an aggregate cap across all unstaked connections. For unstaked connections, `available_load_capacity_in_throttling_duration` always returns the fixed `max_unstaked_load_in_throttling_window` (derived from `MAX_UNSTAKED_TPS = 200`), independent of how many unstaked connections exist. [6](#0-5)  Critically, `increment_load` — which feeds the EMA used to determine whether staked-vs-staked fairness throttling kicks in — only accumulates load for staked peers (`if peer_type.is_staked() { load_in_recent_interval.fetch_add(...) }`); unstaked stream volume is never counted into the shared EMA. [3](#0-2)  Consequently there is no mechanism that limits the *aggregate* unstaked throughput funneling into the shared channel as the number of unstaked connections grows (bounded only by `max_unstaked_connections`, a config value, and `max_concurrent_connections`, which itself allows 25% headroom over configured limits: `(max_staked_connections + max_unstaked_connections) * 5 / 4`). [7](#0-6) 

When the shared channel fills, `try_send` fails with `TrySendError::Full` for *whichever* caller happens to invoke it while full — this includes packets from staked connections that are otherwise fully compliant with their own QoS budget. The failure is only recorded in stats (`total_handle_chunk_to_packet_send_full_err`) and the packet is silently dropped; there is no re-queue, retry, or priority-based preemption of already-buffered unstaked packets to make room for staked ones. [8](#0-7)  Existing QoS/throttle guards (stream-count throttling per connection, connection-table caps) bound each individual unstaked connection and the count of unstaked connections, but do not bound or rate-limit the *shared downstream ingress channel* itself in a way that protects staked senders once many unstaked connections are opened concurrently, each operating within its own allotted budget.

### Impact Explanation
This is a QoS-evasion / ingress-fairness violation: an unstaked, unprivileged client population (opening many parallel connections, each staying within its individually allotted throttle) can collectively occupy the shared `packet_batch_sender` channel's finite capacity, causing legitimate staked senders' packets to be dropped at the streamer→sigverify boundary via `TrySendError::Full`, denying banking-stage ingress to staked traffic despite the staked traffic itself never exceeding any of its own QoS limits. This matches the bounty's "QoS evasion / unstaked traffic starving staked traffic sharing the same downstream channel" category described in the prompt's scope.

### Likelihood Explanation
Feasibility depends on the deployed `max_unstaked_connections` config and the size of `TPU_CHANNEL_SIZE`. Because `max_unstaked_connections` is validator-configurable (and by default permits some nonzero pool of unstaked connections, e.g., used broadly for RPC/light clients submitting transactions), an attacker can open up to that connection cap from many source IPs/ports (each an "unprivileged, unstaked remote client" per the scope), each sending small streams at up to `MAX_UNSTAKED_TPS` (~200/s), i.e. entirely within its individually allotted throttle. Aggregate throughput scales linearly with the number of unstaked connections opened, and because unstaked load is excluded from the shared EMA that would otherwise trigger cross-class throttling protection, the attack is repeatable and does not require any staked/leader/gossip control — only sustained parallel QUIC connections to the leader's public TPU port.

### Recommendation
- Separate ingress channels (or apply weighted/priority scheduling, e.g., separate bounded channels per `ConnectionPeerType` merged with priority draining) so that staked packets cannot be blocked by a full unstaked-only queue.
- Include unstaked stream volume in the shared load EMA (or maintain a separate aggregate unstaked load counter) so that aggregate unstaked ingress, not just per-connection ingress, is throttled as it approaches the shared channel's capacity.
- Consider reserving a guaranteed minimum channel slot budget for staked traffic (e.g., separate bounded sub-channels merged fairly downstream), rather than a single first-come-first-served channel drained by `try_send`.

### Proof of Concept
Integration test plan (extending existing test harness in `streamer/src/nonblocking/quic.rs`, e.g. `test_throttling_check_no_packet_drop`):
1. Use `setup_quic_server` with a small `bounded(N)` channel (e.g., `N = 50`) as `packet_sender`, and a `SwQosConfig` permitting many unstaked connections (`max_unstaked_connections` set high, e.g. 100) and one staked peer via `staked_nodes` with nonzero stake.
2. Spawn ~50 unstaked client `Connection`s (or reuse via `make_client_endpoint`) each opening uni streams and calling `finish()` at their allotted throttle rate (~200 tps each) concurrently, without draining `receiver` (simulate slow sigverify/dedup consumer by not calling `receiver.try_recv()` for a window).
3. Concurrently, from a staked client connection (constructed with a keypair present in `staked_nodes`), attempt to open/finish a stream and record whether the corresponding packet is successfully delivered end-to-end (i.e., appears in `receiver`) versus dropped.
4. Assert expectation of correct behavior: staked sender's packet delivery success rate stays above a guaranteed floor (e.g., ≥ 95%) even while the channel is saturated by unstaked traffic; also assert `stats.total_handle_chunk_to_packet_send_full_err` attributable to staked packets remains near zero.
5. Current code is expected to fail this assertion: because `try_send` treats all senders equally on the shared channel and unstaked load isn't counted in the EMA, the staked packet can be dropped (`TrySendError::Full`) purely due to prior unstaked occupancy of the channel, demonstrating the starvation.

    pub(crate) fn available_load_capacity_in_throttling_duration(
        &self,
        peer_type: ConnectionPeerType,
        total_stake: u64,
    ) -> u64 {
        match peer_type {
            ConnectionPeerType::Unstaked => self.max_unstaked_load_in_throttling_window,
            ConnectionPeerType::Staked(stake) => {
                if self.staked_throttling_enabled.load(Ordering::Relaxed) {
                    // 1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked
                    // clients get at least 1 more number of streams than unstaked connections.
                    self.max_staked_load_in_throttling_window
                        .saturating_mul(stake)
                        .checked_div(total_stake)
                        .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
                        .max(self.max_unstaked_load_in_throttling_window + 1)
                } else {
                    self.max_staked_load_in_throttling_window
                }
            }
        }
    }
