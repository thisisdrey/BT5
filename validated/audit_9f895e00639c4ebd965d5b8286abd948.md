Audit Report

## Title
Unprotected slippage in Snowbridge tip/fee swap allows sandwich attack to devalue bridge tips and registration fees - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`swap_and_burn` in `pallet-snowbridge-system-frontend` calls `T::Swap::swap_exact_tokens_for_tokens` with `amount_out_min` hardcoded to `None`, so the underlying `pallet-asset-conversion` AMM swap accepts any output amount. This function is reachable from the unprivileged, signed extrinsics `add_tip` and `register_token`, allowing an attacker to sandwich the swap and reduce the `ether_gained` value that is subsequently forwarded to BridgeHub as the reward/fee amount.

## Finding Description
`swap_and_burn` is called from `swap_fee_asset_and_burn`, which is invoked by both `register_token` (reachable by any origin whose `asset_id` is nested in itself) and `add_tip` (reachable by any signed account) whenever the supplied fee/tip asset differs from `EthereumLocation`. [1](#0-0) [2](#0-1) [3](#0-2) 

`swap_and_burn` performs the swap via `T::Swap::swap_exact_tokens_for_tokens`, explicitly passing `None` for `amount_out_min`, with the comment "No minimum amount required": [4](#0-3) 

The AMM implementation in `pallet-asset-conversion` (`do_swap_exact_tokens_for_tokens`) does support a caller-supplied `amount_out_min` and does enforce `ProvidedMinimumNotSufficientForSwap` when one is provided — confirmed by the guard logic and by the existing test `swap_should_not_work_if_too_much_slippage` — but the guard is skipped entirely when `None` is passed, exactly as done by `swap_and_burn`: [5](#0-4) [6](#0-5) 

Since the constant-product pool's exchange rate is public, same-block-manipulable state, an unprivileged account can front-run the victim's `add_tip`/`register_token` call with a swap that skews the price, let the victim's uncapped swap execute at the degraded rate, then back-run to restore the pool and capture the extracted value — a standard sandwich attack requiring no privileged role.

The resulting `ether_gained` is not a purely local value: it is forwarded as the `amount` field in the XCM `Transact` call dispatching `EthereumSystemCall::AddTip`/`EthereumSystemCall::RegisterToken` on BridgeHub: [7](#0-6) [8](#0-7) 

## Impact Explanation
The manipulated `amount` recorded via `AddTip`/`RegisterToken` becomes the reward/fee value credited on the Ethereum side, so a sandwich attacker can systematically cause the relayer reward or registration fee actually registered to be lower than what the tipper paid in full, breaking value conservation in the bridge reward/fee-forwarding path even though the caller's input tokens are fully consumed. This matches the "bridge rewards ... must conserve value and settle exactly once to the rightful beneficiary and amount" pivot in the review scope.

## Likelihood Explanation
High. `add_tip` requires only `ensure_signed`, and `register_token` requires only that `asset_id` be nested within the caller's own origin location — neither imposes any restriction related to swap pricing. The `AssetConversion` pool reserves are ordinary public on-chain state movable by any account issuing standard swap extrinsics in the same block, so this is a repeatable, low-cost sandwich attack requiring no special node, validator, or off-chain role, consistent with the "front-run-only ideas" exclusion not applying here since the exploit is a full sandwich (front + back run) rather than front-run alone.

## Recommendation
Do not pass `None` for `amount_out_min` in `swap_and_burn`. Derive a bounded minimum acceptable output — e.g., via `QuotePrice::quote_price_exact_tokens_for_tokens` with an explicit tolerance, or by exposing a caller-supplied `min_ether_out`/slippage parameter on `register_token`/`add_tip` — and pass `Some(min)` into `T::Swap::swap_exact_tokens_for_tokens` so the swap reverts via `Error::<T>::ProvidedMinimumNotSufficientForSwap` rather than settling at an attacker-manipulated price.

## Proof of Concept
1. Attacker observes a pending `add_tip(message_id, tip_asset)` or `register_token` extrinsic from the victim in the transaction pool.
2. Attacker submits `AssetConversion::swap_exact_tokens_for_tokens` swapping a large amount of `tip_asset` into `ether_location` first in the same block, skewing pool reserves against further `tip_asset -> ether` swaps.
3. Victim's extrinsic executes, internally calling `swap_and_burn` → `Swap::swap_exact_tokens_for_tokens(..., None, ...)`, which accepts the degraded rate because the `ProvidedMinimumNotSufficientForSwap` check at `substrate/frame/asset-conversion/src/lib.rs:997-1002` is skipped when `amount_out_min` is `None`.
4. Attacker submits a reverse `ether -> tip_asset` swap to restore pool reserves and realize the arbitrage profit.
5. The `ether_gained` forwarded as `AddTip.amount`/`RegisterToken.amount` to BridgeHub is measurably lower than fair value, reducing the relayer reward/registration fee credited despite the victim paying the full intended amount. This can be reproduced as a Rust unit test in `bridges/snowbridge/pallets/system-frontend/src/tests.rs` by simulating a pool-reserve shift between quoting and executing `add_tip`, then asserting `ether_gained` is below the pre-sandwich expected value.

		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

fn swap_should_not_work_if_too_much_slippage() {

		let user = 1;

		let token_2 = NativeOrWithId::WithId(2);

		create_tokens(user, vec![token_2.clone()]);

			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),

		assert_ok!(Balances::force_set_balance(
			RuntimeOrigin::root(),
			user,
			10000 + get_native_ed()
		));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(user), 2, user, 1000));

		let liquidity1 = 10000;
		let liquidity2 = 200;

			RuntimeOrigin::signed(user),
