## Title
Actuators validate address format but not the reserved zero/null address, allowing permanent loss of TRX and TRC10 assets - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`)

### Summary
Multiple actuators reachable by ordinary signed transactions (`TransferActuator`, `TransferAssetActuator`, `ParticipateAssetIssueActuator`, `DelegateResourceActuator`, `UnDelegateResourceActuator`, `FreezeBalanceActuator`, `UnfreezeBalanceActuator`) validate a destination/receiver address using only `DecodeUtil.addressValid`, which checks length and the network prefix byte but never rejects the all-zero address body (e.g. `0x41` followed by 20 zero bytes). This mirrors the reported class of bug ("constructor not checked for non-existent address"): the code accepts a syntactically valid but semantically null/unowned address, and funds sent there become permanently unspendable because no private key corresponds to the all-zero hash.

### Finding Description
`DecodeUtil.addressValid` only verifies array length and the `addressPreFixByte`: [1](#0-0) 

`TransferActuator.validate()` relies solely on this check for both `ownerAddress` and `toAddress`, and only rejects the case where `toAddress` equals `ownerAddress`; it never rejects the reserved zero address: [2](#0-1) 

The same pattern (format check only, no zero-address rejection) is repeated in `TransferAssetActuator.validate()`: [3](#0-2) 

and in the resource-delegation actuators (`DelegateResourceActuator`, `UnDelegateResourceActuator`, `FreezeBalanceActuator`), which additionally auto-create the receiver account if it does not exist yet, meaning an all-zero `receiverAddress` will silently succeed and become a real, but unowned, account entry: [4](#0-3) [5](#0-4) 

Since these code paths are reachable directly from `TransferContract`/`TransferAssetContract`/`DelegateResourceContract` transactions broadcast by any signer, an unprivileged transaction broadcaster can send TRX or TRC10 tokens to the zero address, and those assets are permanently unrecoverable because no key controls that address.

### Impact Explanation
Funds (TRX or TRC10 balances) transferred to the reserved zero address are permanently frozen/burned, since the actuators do not distinguish "valid address format" from "spendable, key-controlled address." This is a fund-freezing bug class analogous to the reported constructor issue: a value-moving code path lacks a check for the non-existent/zero address, and consequently value can become permanently locked in an unbacked account.

### Likelihood Explanation
Likelihood is moderate: it requires a user (or wallet/exchange integration bug, or malicious counterpart soliciting a transfer) to set the destination address to all zeros. Because `DecodeUtil.addressValid` treats this as a perfectly valid address, no validation failure alerts the sender, and the transaction executes successfully, silently locking the funds forever.

### Recommendation
Add an explicit check in `DecodeUtil.addressValid` (or at each call site) that rejects the reserved zero address (`addressPreFixByte` followed by 20 zero bytes), in addition to the existing length/prefix checks, for all address fields used in fund-moving or resource-delegating actuators (`TransferActuator`, `TransferAssetActuator`, `DelegateResourceActuator`, `UnDelegateResourceActuator`, `FreezeBalanceActuator`, `UnfreezeBalanceActuator`, and the corresponding native-contract processors).

### Proof of Concept
1. Construct a `TransferContract` with `ownerAddress` set to a funded account and `toAddress` set to `0x41` + 20 zero bytes (a syntactically valid 21-byte address per `DecodeUtil.ADDRESS_SIZE`/prefix check).
2. Sign and broadcast the transaction.
3. `TransferActuator.validate()` passes both `DecodeUtil.addressValid(ownerAddress)` and `DecodeUtil.addressValid(toAddress)` checks (lines 104-109) and the `Arrays.equals(toAddress, ownerAddress)` self-transfer check does not trigger.
4. `execute()` credits the balance to the zero-address account (creating it if necessary), and since no private key exists for the all-zero hash, the transferred TRX is permanently inaccessible.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
