Based on my research, I found a plausible structural analog in java-tron, but it is weaker than the original finding because it depends on a committee-controlled governance parameter rather than a purely permissionless state change. I'll present it with that caveat, since it is the closest reachable equivalent I could verify.

### Title
Committee-toggled `unfreezeDelayDays`/`supportUnfreezeDelay` gate can permanently lock already-frozen TRX from V2 unfreeze/undelegate paths - (File: actuator/src/main/java/org/tron/core/actuator/WithdrawExpireUnfreezeActuator.java)

### Summary
`WithdrawExpireUnfreezeActuator`, `UnfreezeBalanceV2Actuator`, and `UnDelegateResourceActuator` all gate their `validate()` on `dynamicStore.supportUnfreezeDelay()`, which is derived from the committee-controlled `unfreezeDelayDays` parameter. This mirrors the reported bug class: a mutable, globally-scoped "enabled" flag governs whether previously-locked/deposited funds can be withdrawn, and if that flag is later disabled, funds already committed under the old state become unreachable through the normal exit path.

### Finding Description
Users freeze TRX for resources via `FreezeBalanceV2Contract`. To retrieve that TRX later, they must go through one of three actuators, each of which requires the feature flag to remain enabled: [1](#0-0) [2](#0-1) [3](#0-2) 

`supportUnfreezeDelay()` is backed by the committee proposal `unfreezeDelayDays` (`getUnfreezeDelayDays`, proposal type #70) as documented in the config comments: [4](#0-3) 

If the committee (via normal on-chain proposal governance, not a "malicious" committee action) lowers `unfreezeDelayDays` back to 0 after users have already frozen balances or delegated resources under the V2 model, `supportUnfreezeDelay()` flips to `false`. From that point, an ordinary user broadcasting a `WithdrawExpireUnfreezeContract`, `UnfreezeBalanceV2Contract`, or `UnDelegateResourceContract` transaction will always fail validation with "Not support ... transaction, need to be opened by the committee", exactly as demonstrated in `WithdrawExpireUnfreezeActuatorTest`/`DelegateResourceActuatorTest`: [5](#0-4) 

There is no fallback path for balances that were frozen/delegated specifically through the V2 mechanism once the flag is disabled — the V1 `UnfreezeBalanceActuator`/`UnfreezeAssetActuator` paths operate on different account fields (`Frozen`/legacy delegation records) and do not release V2 `frozenV2`/`unfrozenV2`/`delegatedFrozenV2` balances.

### Impact Explanation
If this global feature flag is toggled off after being on, any TRX frozen via `FreezeBalanceV2Contract`, delegated via `DelegateResourceContract`, or already in the unfreezing/expired-unfreeze pending state, cannot be withdrawn to the owning account's spendable balance through any actuator — permanently freezing user funds until/unless the committee re-enables the parameter. This matches the "permanent freezing of funds" impact category.

### Likelihood Explanation
This requires a legitimate committee proposal to actually reduce `unfreezeDelayDays` back to 0 after it was previously non-zero; I was not able to fully verify within the available budget whether `ProposalUtil`/the proposal validation logic explicitly disallows lowering this parameter back to 0 once raised, or whether `FreezeBalanceV2Actuator` itself also requires `supportUnfreezeDelay()` at freeze time (which would make the enable/disable symmetric and reduce risk). This uncertainty is significant, and readers should verify `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java` and `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceV2Actuator.java` directly before treating this as a confirmed exploitable bug.

### Recommendation
- Confirm whether `ProposalUtil` permits lowering `unfreezeDelayDays` from a positive value back to 0 after users have frozen/delegated balances under the V2 model.
- If so, either disallow such downgrades once V2 freeze/delegate activity exists, or ensure the withdrawal/undelegate actuators are not gated by the same toggle used to gate the freeze/delegate actuators, so that funds committed under an "enabled" state always remain retrievable regardless of later governance changes.

### Proof of Concept
1. Committee enables V2 resource model and sets `unfreezeDelayDays` > 0 (`supportUnfreezeDelay()` → true).
2. User broadcasts `FreezeBalanceV2Contract` to freeze TRX for bandwidth/energy.
3. User (or receiver) later broadcasts `DelegateResourceContract` or simply waits for the unfreeze-delay period.
4. Committee proposal reduces `unfreezeDelayDays` back to 0 (`supportUnfreezeDelay()` → false).
5. User broadcasts `WithdrawExpireUnfreezeContract` / `UnfreezeBalanceV2Contract` / `UnDelegateResourceContract` — validation fails with "Not support ... transaction, need to be opened by the committee" as shown in the referenced actuator code, and the frozen TRX cannot be recovered through any other actuator.
