### Title
Active-permission holder can escalate to full Owner control via `AccountPermissionUpdateContract` self-inclusion - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateActuator` allows a transaction signed under a low-threshold **Active** permission (rather than the account's high-threshold **Owner** permission) to completely rewrite the account's Owner permission, Witness permission, and all Active permissions, as long as the signing Active permission's operations bitmap includes the `AccountPermissionUpdateContract` type. This mirrors the Rancher PRTB bug class: a permission that legitimately grants a narrow capability (here, "can send transactions of contract-type X") is reused to grant a much broader capability (full account takeover) because the authorization check never re-validates that the *effect* of the action (rewriting Owner) requires Owner-level authority.

### Finding Description
Signature/permission validation for any transaction is performed by `TransactionCapsule.checkPermission` / `validateSignature`, which only checks that the signing `Permission` is of type `Active` and that the target contract's type bit is set in that permission's `operations` bitmap: [1](#0-0) 

There is no special case that forbids `AccountPermissionUpdateContract` (the contract type that rewrites Owner/Witness/Active permissions) from being included in an Active permission's operations bitmap, nor any requirement that this specific contract type be signable only via the Owner permission (`permissionId == 0`).

The actuator's own validation, `AccountPermissionUpdateActuator.checkPermission`, only rejects operation bits that fall outside `dynamicStore.getAvailableContractType()` — i.e., it validates that the *new* permission's declared operations are legal contract types, not that the *signer's own* permission is authorized to redefine ownership: [2](#0-1) 

And `execute()` simply overwrites all permissions with whatever the contract specifies, with no check that the caller's permission "outranks" what it is replacing: [3](#0-2) 

Because `AccountPermissionUpdateContract` is a normal, "available" contract type (it is not excluded from `getAvailableContractType`, unlike e.g. `ClearABIContract`/`UpdateBrokerageContract`, as shown by the test enumerating excluded types), an account owner (or anyone who creates an Active permission for a delegate) can — intentionally or by mistake — grant a delegate Active permission with a low weight/threshold the `AccountPermissionUpdateContract` bit set: [4](#0-3) 

That delegate can then sign a new `AccountPermissionUpdateContract` themselves (satisfying only the low Active threshold) and set the Owner permission's keys/threshold to themselves, set the Witness permission arbitrarily (if the account is a witness), and grant any Active permission any operations bitmap up to the full available set — effectively converting a narrowly-scoped delegated capability into unrestricted control of the account, bypassing the higher-security Owner threshold the account holder originally configured.

### Impact Explanation
This allows unauthorized account takeover: a party holding only a low-weight/low-threshold Active permission (e.g., a co-signer intended only to authorize specific limited operations) can unilaterally rewrite the Owner permission to remove the original owner's keys and install their own, permanently locking out the legitimate owner and gaining full custody of the account's funds and permission structure. This is a concrete unauthorized account operation / theft-of-funds primitive consistent with the severity bar (High), directly analogous to the Rancher PRTB privilege-escalation bug where a narrowly-granted capability (`escalate` verb) was reused to grant arbitrary broader permissions.

### Likelihood Explanation
Exploitability depends on whether an Active permission with the `AccountPermissionUpdateContract` operation bit set already exists for the target account (self-granted by the owner for convenience, or via a template/default operations set that is not curated). Nothing in the codebase prevents such a grant, and the actuator's validation logic treats `AccountPermissionUpdateContract` the same as any ordinary contract type, so the misconfiguration is easy to introduce (e.g., copying "all contract types enabled" into a delegated Active permission) and, once present, is trivially exploitable by any holder of that Active permission's keys meeting only that permission's (lower) threshold.

### Recommendation
Enforce that `AccountPermissionUpdateContract` can only be authorized via the Owner permission (`permissionId == 0`), regardless of whether a lower Active permission's operations bitmap includes that bit — i.e., special-case this contract type in `TransactionCapsule.checkPermission`/`validateSignature` (and/or reject it in `AccountPermissionUpdateActuator.checkPermission`'s allowed-operations check) so a delegated Active permission can never be used to redefine the account's own permission structure.

### Proof of Concept
1. Owner account `A` creates an Active permission `P2` with threshold 1, containing delegate key `D`, and (intentionally or via a permissive default) includes the `AccountPermissionUpdateContract` type bit in `P2`'s operations, via `AccountPermissionUpdateActuator`/`AccountPermissionUpdateContract` signed by Owner.
2. Delegate `D` crafts a new `AccountPermissionUpdateContract` for account `A`, with `permissionId = 2` (pointing at `P2`), setting `Owner` permission to `{keys: [D], threshold: 1}`, replacing the original Owner keys.
3. `D` signs this transaction with only their own private key, satisfying `P2`'s threshold of 1 (verified via `TransactionCapsule.checkPermission`/`checkWeight` at [5](#0-4) ).
4. `AccountPermissionUpdateActuator.execute` applies the update unconditionally, overwriting the Owner permission of `A` with `D`'s key [3](#0-2) .
5. `D` now solely controls account `A`'s Owner permission, having escalated from a narrow delegated Active role to full account ownership.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
