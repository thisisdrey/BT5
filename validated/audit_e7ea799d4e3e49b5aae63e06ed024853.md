### Title
Self-borrow griefing bypasses liquidation same-block guard, allowing indefinite deferral of liquidation on an already-unhealthy position - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`debt-add-scaled` in `v0-market-vault.clar` unconditionally refreshes `last-borrow-block` to the current `stacks-block-height` on every borrow, regardless of amount or whether the position is already unhealthy. `liquidate` in `v0-4-market.clar` rejects any liquidation attempt if `last-borrow-block` equals the current block (`same-block-check` at line 1431), so a borrower can call `borrow` with a trivial amount (e.g. `u1`) each block to keep resetting this stamp and block all liquidators indefinitely.

### Finding Description
`debt-add-scaled` writes `last-borrow-block: stacks-block-height` on every call with no minimum size or health-state condition: [1](#0-0) 

`liquidate` reads that same field and reverts if it equals the current block: [2](#0-1) 

The stated intent of this guard, per the comment, is to stop flash-loan-style attacks where a user borrows into an unhealthy position and gets liquidated in the same block before the market can react. It is not designed to be, but functions as, a mechanism for an already-unhealthy borrower to indefinitely block liquidation: the borrower (who controls their own account and can call `borrow` for any amount ≥ 1, since the only amount check is `> scaled-amount u0` at line 454) can call `borrow(debt-ft, u1, none, none)` once per block. Each such call re-executes `debt-add-scaled`, resetting `last-borrow-block` to the current block, which causes any `liquidate` call submitted afterward in that same block to hit `ERR-LIQUIDATION-BORROW-SAME-BLOCK` and revert — even though the position was already liquidatable from a prior block and the new borrow itself is trivial and non-flashloan.

There is no check in `borrow`/`debt-add-scaled` that distinguishes "new borrow that could create an unhealthy position this block" from "borrower refreshing an already unhealthy position to grief liquidators," and no check in `liquidate` that looks at whether the position was already unhealthy in a prior block (e.g. no separate "was-unhealthy-last-block" or LTV-at-last-borrow tracking). The guard is keyed purely on block equality of a mutable, attacker-controlled timestamp field, with no cost or capital requirement beyond a `u1`-sized borrow (subject only to whatever minimal reserve/liquidity exists for that asset) and gas.

### Impact Explanation
This is a temporary freezing of a liquidator's ability to seize collateral on an unhealthy position, matching the "High - temporary freezing of funds" impact category from the rules. Because the borrower can repeat this every block, the position's LTV can continue to climb (via price movement or interest accrual) while liquidation is deferred block after block, which the question also identifies as a path toward compounding bad debt / insolvency risk if sustained — the borderline Critical concern is the escalation potential, but the concretely provable impact per block is the freezing of liquidation rights against that position.

### Likelihood Explanation
Fully feasible for any unprivileged attacker: it requires only that the attacker (borrower) already holds a liquidatable position (self-controlled, no privileged access needed), a small amount of the debt asset (or the ability to borrow `u1` scaled units, bounded only by available liquidity for that asset/market), and the ability to call `borrow` once per Stacks block. No flashloan, no oracle manipulation, no third-party dependency — purely a call-ordering/self-account griefing pattern reachable by an ordinary principal. It is trivially repeatable every block for as long as the attacker is willing to keep transacting.

### Recommendation
Decouple the same-block anti-flashloan guard from a value that the borrower can refresh at will while already unhealthy. Options: (1) only update `last-borrow-block` when the borrow would push the position from healthy to unhealthy (i.e., check health before/after the borrow and skip the stamp update if the position was already unhealthy before this borrow); (2) track the block at which the position first became unhealthy and gate liquidation same-block protection off that value instead of the most recent borrow; (3) impose a minimum borrow size relative to existing position size/health so trivial "stamp-refresh" borrows aren't possible; or (4) allow liquidation same-block if the account was already below the liquidation threshold prior to this block's borrow call (snapshot LTV at start of block).

### Proof of Concept
Clarinet/vitest simnet test plan (`local-testing`):
1. Set up a market with an asset with a price feed, and register a borrower account with sufficient collateral to borrow near the liquidation threshold LTV.
2. Have the borrower call `borrow` to bring the position to just under `LTV-LIQ-PARTIAL`.
3. Advance one block, then move the oracle price (or accrue interest) so that the position's current LTV now exceeds `LTV-LIQ-PARTIAL` (making it liquidatable as of the start of the new block).
4. In the same block: have the borrower call `borrow(debt-ft, u1, none, none)` first (refreshing `last-borrow-block` to current `stacks-block-height`), then have a distinct liquidator principal call `liquidate` on that position.
5. Assert `liquidate` returns `(err ERR-LIQUIDATION-BORROW-SAME-BLOCK)`.
6. Repeat steps 3-5 across multiple subsequent blocks (borrower keeps issuing `u1` borrows each block right before the liquidator's call), asserting `liquidate` reverts every block while independently asserting (via a read-only LTV getter) that the position's LTV remains at or above the liquidation threshold throughout — demonstrating indefinite deferral of a legitimately liquidatable position.
