### Title
Diff parser byte-limit accounting drift allows bypass of `MaxBytes`/`SafeMaxBytes` enforcement - ([File: internal/gitaly/diff/diff.go])

### Summary
The Sherlock report describes a fee-accounting bug where a resource cap (fees) is computed against one quantity (total submitted `funds`) while the loop that actually consumes the resource operates on a different, drifting quantity (`fundsAvailable`), so the two never stay in sync and the charged amount diverges from the real amount consumed. Gitaly's diff parser has the same root-cause shape: it increments a cumulative counter (`bytesProcessed`) using one measurement (`Diff.byteCount`) but later decrements the same counter using a different, larger measurement (`len(Diff.Patch)`) when a diff is pruned. The mismatch causes `bytesProcessed` to drift downward every time a file is pruned, silently weakening (and eventually defeating) the `MaxBytes`/`SafeMaxBytes` resource limits that are meant to bound the cost of Gitaly's diff-related RPCs.

### Finding Description
`Parser.Parse()` tracks how much data has been processed via two counters, `linesProcessed` and `bytesProcessed`, which are incremented from the values recorded on the just-parsed `Diff`: [1](#0-0) 

`Diff.byteCount` is only incremented for actual content lines (`+`, `-`, ` `, `\`, binary markers) via `consumeChunkLine(..., updateStats=true)`; hunk header lines (`@@ ... @@`) are explicitly excluded from this count: [2](#0-1) [3](#0-2) 

However, `Diff.Patch` is appended to for *every* consumed chunk line regardless of whether `updateStats` is true, i.e. it also contains the hunk-header bytes that were deliberately excluded from `byteCount`: [4](#0-3) 

When a diff is pruned — either because cumulative "safe" limits were exceeded (`CollapseDiffs`) or because the single-file `MaxPatchBytes` limit was exceeded — `prunePatch()` decrements `bytesProcessed` by `len(parser.currentDiff.Patch)` instead of by the `byteCount` value that was actually added to it: [5](#0-4) [6](#0-5) 

Because `len(Patch) >= byteCount` always (Patch is a superset that also contains hunk-header bytes), every prune subtracts more from `bytesProcessed` than was ever added for that file. Over a diff stream with many files/hunks, this causes `bytesProcessed` to drift progressively below the true amount of data actually parsed and buffered by the server. The cumulative limit check: [7](#0-6) 

compares this drifted (artificially low) `bytesProcessed` against `MaxBytes`, so the intended cap on total diff size processed per request is effectively weakened or defeated the more files/hunks are pruned, exactly mirroring the Sherlock bug's pattern of a resource cap being computed from an accounting variable that has fallen out of sync with the quantity that was truly consumed.

### Impact Explanation
`Limits.EnforceLimits`, `MaxBytes`, `SafeMaxBytes`, `CollapseDiffs`, and `MaxPatchBytes` exist specifically to bound the CPU/memory cost of diff generation for RPCs such as `CommitDiff`/`RawDiff`/`RawPatch`, which are reachable by any ordinary user requesting a diff (e.g. via merge request views or `git diff`-equivalent RPCs) and whose limit fields are populated from client-controlled request parameters. If an attacker can construct a commit/diff with many files that each trigger per-file pruning (`TooLarge`) or repo-wide collapsing (`Collapsed`) — using long hunk-header context lines (`@@ ... @@ <long function-context text>`) to maximize the `len(Patch)` vs `byteCount` gap on each pruned file — the cumulative `bytesProcessed` counter can be driven far below the real bytes consumed. This delays or entirely prevents the `MaxBytes`/`SafeMaxBytes` circuit breaker from tripping, letting Gitaly continue to buffer and process a diff stream well beyond its configured resource ceiling — a DoS of the diff-serving RPC handler through resource-limit bypass.

### Likelihood Explanation
The `EnforceLimits`/`MaxBytes`/`SafeMaxBytes`/`CollapseDiffs`/`MaxPatchBytes` fields are ordinary, client-settable fields on diff RPC requests, and the trigger condition (files whose patches exceed `MaxPatchBytes`, or cumulative safe limits) is a normal outcome of large diffs, which any user can produce by pushing commits with large files/renames to a repository they control. No privileged access, race condition, or malicious peer is required — only crafting a diff whose hunk headers are large relative to their content lines, which is entirely within the normal capabilities of `git diff` output (e.g. via long function-context lines picked up by hunk headers).

### Recommendation
In `prunePatch()`, decrement `bytesProcessed` by the same quantity that was added to it (`parser.currentDiff.byteCount`), not by `len(parser.currentDiff.Patch)`:
```go
func (parser *Parser) prunePatch() {
    parser.linesProcessed -= parser.currentDiff.lineCount
    parser.bytesProcessed -= parser.currentDiff.byteCount
    parser.currentDiff.ClearPatch()
}
```
This keeps the running total symmetric with what was actually added, preventing artificial drift that can defeat the `MaxBytes`/`SafeMaxBytes` protections.

### Proof of Concept
1. Send a `CommitDiffRequest` (or equivalent) with `EnforceLimits: true`, a modest `MaxPatchBytes`, and a reasonably small `MaxBytes`/`SafeMaxBytes`.
2. Target a commit containing many modified files, each with hunks that include long function-context text after `@@ ... @@` (git includes surrounding function signature/context in the hunk header when available) but whose actual `+`/`-`/context content lines are kept just under `MaxPatchBytes` so each file gets pruned via the `TooLarge` path repeatedly across the diff stream.
3. Observe that `parser.bytesProcessed` (and thus the `maxBytesExceeded` check at [7](#0-6)  ) fails to trip even though many megabytes of hunk-header + content data have been read and buffered by the server, because each `prunePatch()` call over-subtracts by the hunk-header byte count as shown at [5](#0-4) .

func consumeChunkLine(reader *bufio.Reader, diff *Diff, skipPatch, updateStats bool) error {
	// The code that follows would be much simpler if we used
	// bufio.Reader.ReadBytes, but that allocates an intermediate copy of
	// each line which adds up to a lot of allocations. By using ReadSlice we
	// can copy bytes into currentDiff.Patch without intermediate
	// allocations.
	var byteCount int
	for done := false; !done; {
		line, err := reader.ReadSlice('\n')
		if updateStats && byteCount == 0 && len(line) > 0 {
			if line[0] == '+' {
				diff.LinesAdded++
			} else if line[0] == '-' {
				diff.LinesRemoved++
			}
		}
		byteCount += len(line)

		switch {
		case errors.Is(err, bufio.ErrBufferFull):
			// long line: keep reading
		case err != nil && !errors.Is(err, io.EOF):
			return fmt.Errorf("read chunk line: %w", err)
		default:
			done = true
		}

		if !skipPatch {
			diff.Patch = append(diff.Patch, line...)
		}
	}

	if updateStats {
		diff.byteCount += byteCount
		diff.lineCount++
	}

	return nil
}
