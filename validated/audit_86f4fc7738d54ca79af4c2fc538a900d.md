### Title
Unauthenticated `RecvError` packet allows remote state poisoning by spoofed UDP source - (File: outside.go)

### Summary
The reported bug class is an event/message listener that accepts and acts on data from any source without an origin check, leading to spoofing and unauthorized state changes. Nebula's UDP listener is architecturally equivalent to the extension's "all URLs" content script: `ListenOut` hands every inbound datagram to `readOutsidePackets` regardless of who sent it [1](#0-0) . Most packet types are protected downstream by AEAD decryption or the noise handshake, but `header.RecvError` is a fully unencrypted, unauthenticated control message that is acted upon based only on attacker-controllable UDP header fields and a same-looking source address.

### Finding Description
In `readOutsidePackets`, `header.RecvError` packets are dispatched to `handleRecvError` before any cryptographic verification (this branch is reached even before hostinfo/ConnectionState checks that gate the encrypted-packet path): [2](#0-1) 

`handleRecvError` looks up the tunnel purely by the attacker-supplied `RemoteIndex` field and compares the packet's UDP source address to the address currently recorded for that tunnel. If they match, it tears the tunnel down: [3](#0-2) 

Because `RecvError` carries no MAC/AEAD tag (it's parsed straight from the cleartext header, unlike `Message`/`Test`/`LightHouse`/`Control` types which require `hostinfo.ConnectionState.Decrypt` first), the only "authentication" is a source-IP/port equality check. UDP source addresses are trivially spoofable on many networks (no ingress filtering, off-path attacker with predictable/known 5-tuple, or an on-path/same-NAT attacker), and `RemoteIndex` values, while random 32-bit numbers, are transmitted in the clear on every packet of an active tunnel and can be observed by a passive on-path attacker. An attacker who can spoof the source address of one peer, or observe traffic to learn the current `RemoteIndex` and address pair, can forge a single unencrypted `RecvError` packet and force `closeTunnel` + `DeleteHostInfo`, poisoning both hostmap and handshake-manager state without holding any valid certificate or completing any handshake.

This is the closest reachable analog to the report's core issue: a listener/handler that processes attacker-supplied data based on a same-origin-style check that is not cryptographically enforced, rather than actual authentication.

### Impact Explanation
A successful forged `RecvError` collapses an active, fully-authenticated tunnel between two legitimate peers, forcing a costly re-handshake and creating a window of connectivity loss/DoS. Because the check is address-equality rather than a MAC, it does not protect against source-address spoofing, which is a known-weaker trust model than the mutually authenticated Noise/AEAD tunnel traffic. It does not achieve certificate/handshake bypass, decryption, or traffic forgery, so this is a remote state-poisoning / DoS-class impact, not a full authentication bypass.

### Likelihood Explanation
Exploitation requires either (a) the ability to spoof UDP source address/port for one of the two tunnel endpoints as observed by the other, which is feasible on networks without egress/ingress filtering or for an on-path/same-subnet attacker, plus (b) knowledge of the correct `RemoteIndex`, which is sent in cleartext in every packet header of the tunnel and is therefore observable by anyone who can see the traffic. The maintainers themselves flagged `recv_error` as security-sensitive, disabling it "when a packet is received outside the allowable counter window" in a prior fix, corroborating that this control path is treated as attack surface: [4](#0-3) . Likelihood is therefore moderate, gated on network position/spoofability rather than possession of a CA-signed certificate.

### Recommendation
Do not rely on UDP source-address equality as the trust boundary for `RecvError`. Either (a) require `RecvError` responses to be tied to a fresh, unpredictable nonce/challenge issued by the sender of the original packet so a third party cannot replay/forge a valid-looking error, (b) rate-limit and require multiple corroborating signals (e.g. combine with the counter-window check already added) before tearing down a tunnel, or (c) authenticate `RecvError` using the existing tunnel's derived keys (even a short MAC) instead of trusting the cleartext header and address match alone.

### Proof of Concept
1. Establish a tunnel between hosts `A` and `B`; observe (or be positioned on-path to sniff) any packet on the tunnel to learn `RemoteIndex` (sent in cleartext in the 4-byte header field on every packet) and the currently active `CurrentRemote` address of `A` as seen by `B`.
2. As attacker `E`, craft a raw UDP packet with header `Type=header.RecvError`, `RemoteIndex=<observed index>`, and spoof the source address to match `A`'s address as known to `B` (`hi.CurrentRemote`), then send it to `B`'s listening port.
3. `B`'s `readOutsidePackets` routes the packet to `handleRecvError` (`outside.go:82`) without any decryption/authentication step; `hostinfo.GetRemote() == addr` passes because the source is spoofed to match, and `B` calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` (`outside.go:572-574`), tearing down the legitimate tunnel state on `B`'s side purely from a spoofed, unauthenticated packet. func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
