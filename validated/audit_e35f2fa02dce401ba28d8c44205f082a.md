Based on the code, the closest reachable analog to the Ploutoz Finance "price manipulation → drain assets" pattern in java-tron is the legacy TRC10 Bancor-style `Exchange` module, whose default (non-hardened) swap-price computation uses floating-point `double` math instead of exact arithmetic, and can be executed by any unprivileged account via a `ExchangeTransactionContract`.

### Title
Floating-point precision loss in legacy Exchange price calculation allows profitable drain of exchange pool reserves - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeCapsule.transaction()` is reachable from any signed `ExchangeTransactionContract` broadcast by an unprivileged account via `ExchangeTransactionActuator`. By default (`ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal not yet activated), it uses the legacy `ExchangeProcessor`, which computes the bancor-formula swap output using Java `double` (`Math.pow`) arithmetic rather than exact `BigDecimal`/integer math.

### Finding Description
`ExchangeCapsule.transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath, boolean hardenedCalc)` selects between `SafeExchangeProcessor.INSTANCE` (BigDecimal-based, exact) and `new ExchangeProcessor(supply, useStrictMath)` (double-based) depending on `hardenedCalc`, which is controlled by `dynamicStore.allowHardenExchangeCalculation()`. [1](#0-0) 

The default/legacy `ExchangeProcessor.exchangeToSupply` and `exchangeFromSupply` compute the bancor-relay formula with `double` and `Math.pow`, introducing floating-point rounding error in both directions of the swap: [2](#0-1) 

This is exactly the class of bug the "hardened" mode was later introduced to fix, replacing the double math with `BigDecimal` computation in `SafeExchangeProcessor`, gated behind `ALLOW_HARDEN_EXCHANGE_CALCULATION` (fork `VERSION_4_8_2`): [3](#0-2) [4](#0-3) 

Because the harden flag is a value that must be explicitly proposed/activated by committee (it is not on by default), any chain where this proposal has not been passed still routes all `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` traffic through the imprecise double-math path from `ExchangeTransactionActuator.execute()`: [5](#0-4) 

An attacker who repeatedly submits small trades in alternating directions can exploit the systematic rounding bias of the double-based `pow` computation (analogous to how the Ploutoz attacker repeatedly manipulated the oracle-derived price to extract more value than deposited) to accumulate a profit at the exchange pool's expense across many transactions, since `validate()` only checks a user-specified `tokenExpected` slippage floor and does not defend against precision-based value leakage over many rounds.

### Impact Explanation
Successful exploitation lets any unprivileged account extract more value out of a TRC10 `Exchange` pool (funded by other users/injectors) than it puts in, over repeated transactions—an unbacked-balance/theft-of-funds condition against exchange pool participants, satisfying the "unauthorized... theft... of funds" bar.

### Likelihood Explanation
Medium: this requires the target chain/network to not have activated `ALLOW_HARDEN_EXCHANGE_CALCULATION`, and requires an attacker to perform iterative probing/trading (bounded by `MarketSellFee`/transaction fees) to consistently harvest the rounding bias; the existence of the "hardened" fix strongly signals the underlying double-math path is recognized internally as imprecise/exploitable.

### Recommendation
Make `SafeExchangeProcessor`/BigDecimal-exact computation the default and unconditional path for all Exchange actuators (`ExchangeTransactionActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`), removing the `useStrictMath`/`hardenedCalc` double-math branch, or force-activate `ALLOW_HARDEN_EXCHANGE_CALCULATION` in genesis/hard-fork defaults so no float-math path remains reachable by unprivileged transactions.

### Proof of Concept
1. On a network where `ALLOW_HARDEN_EXCHANGE_CALCULATION == 0` (default), create/participate in a TRC10 `Exchange` pool via `ExchangeCreateContract`.
2. Broadcast repeated `ExchangeTransactionContract` transactions alternating sell direction with quantities chosen so the double-based `Math.pow` rounding in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` [2](#0-1)  consistently rounds in the attacker's favor (as demonstrated by the differing legacy-vs-hardened results asserted in `ExchangeProcessorTest.testStrictMath`, where legacy double results systematically diverge from the exact `SafeExchangeProcessor` result: `Assert.assertNotEquals(anotherTokenQuant, result); Assert.assertEquals(safeResult, result);`) [6](#0-5) .
3. Over many iterations, net token balance extracted from the pool exceeds what was deposited, draining value from other pool participants.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
