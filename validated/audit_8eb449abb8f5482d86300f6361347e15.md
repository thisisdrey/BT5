### Title
Backing/dispute-statement era-points forfeited when a validator is no longer in the *current* active set at reward time - ([File: polkadot/runtime/parachains/src/reward_points.rs])

### Summary
`RewardValidatorsWithEraPoints::reward_only_active` (used for both parachain-backing rewards and dispute-statement rewards) resolves the *historical* validator identity for the session in which the work was done, but then gates payout by checking membership in the **currently active** validator set at the moment the reward call executes, not the set active during `session_index`. This mirrors the RAAC gauge bug: work/weight is earned while "active", but the reward distribution step checks a live "active" flag taken at distribution time, so honest, already-earned era points are silently discarded (never redistributed to the correct party, just dropped from the total) if session rotation happens to move the validator out of the *current* set before the reward call fires.

### Finding Description
`reward_only_active` in [1](#0-0)  does:

1. Look up `validators = session_info::AccountKeys::<C>::get(&session_index)` — this correctly resolves account IDs for the *session in which the backing/dispute vote occurred* (a historical snapshot).
2. Compute `active_set: BTreeSet<_> = C::ValidatorSet::validators()` — this is the **current** validator set at the time this function runs, not the set for `session_index`.
3. Filter the resolved accounts through `active_set.contains(v)` before calling `R::reward_by_ids`.

This function is called from two places with a materially different timing between "when the qualifying action happened" and "when the reward call executes":
- `reward_backing` — called for candidate backing in `session_index = shared::CurrentSessionIndex::<C>::get()` [2](#0-1) . Backing/inclusion normally happens close in time to the session, so drift is small but non-zero across a session boundary.
- `reward_dispute_statement` — called with an explicit, possibly **much older** `session` parameter [3](#0-2) . Disputes can be raised and resolved many sessions/eras after the disputed candidate's session, since dispute conclusion depends on collecting supermajority/byzantine-threshold votes which can straddle session and era boundaries. A validator that correctly cast a dispute statement while a member of session `N`'s active set can have rotated out of the validator set by the time the dispute concludes and `reward_dispute_statement` executes, even though their vote was equally valid and required for reaching the threshold.

The reward points recorded via `R::reward_by_ids` (routed to `pallet-staking`/`pallet-staking-async`'s `reward_by_ids`, e.g. [4](#0-3)  or the async equivalent [5](#0-4) ) directly determine `validator_reward_points`/`total_reward_points`, which are the denominator/numerator used to split the era's staking payout (`Perbill::from_rational(validator_reward_points, total_reward_points)` in `do_payout_stakers_by_page`). If a filtered-out validator's points are simply dropped (not credited to `era_rewards.individual`, and also not added to `era_rewards.total` since the whole reward record is skipped before reaching `R::reward_by_ids`), those era points are lost outright — precisely the "gauge shut down before distribution -> loses accumulated rewards" pattern, except here the trigger is ordinary session rotation rather than an explicit admin action, and the loss is of already-completed dispute/backing work rather than of already-collected pool revenue.

There is no compensating mechanism that credits points based on the validator's set membership at the time the work occurred (`session_index`); the guard uses `C::ValidatorSet::validators()` unconditionally at call time, with no way to recover the correct historical set for comparison.

### Impact Explanation
This directly compromises intended validator-incentive behavior in a way that matches "runtime bugs that compromise intended behavior" in the impact gate: validators can perform correct, honest, threshold-contributing work (backing a candidate, or casting a dispute statement that helps resolve a dispute) and receive **zero** era points for it purely because of session rotation timing outside their control, reducing their share of `ErasValidatorReward`/staking payout for that era. This is a value-conservation/settlement-correctness defect (rewards computed from a wrong "active" snapshot rather than the historically-correct one), not merely an economic inefficiency — the era-point ledger itself becomes wrong, and the wrongness is silent (no error, no event indicating forfeiture).

### Likelihood Explanation
This requires no privileged actor, malicious peer, or governance action — it can occur under completely normal validator set churn (elections, chilling, slashing-induced removal, rotation for any of the usual reasons) between the session in which a dispute-worthy statement is submitted and the (unbounded, threshold-dependent) time the dispute concludes. Given that `session_index` for `reward_dispute_statement` is explicitly a parameter distinct from "now," the divergence is a designed possibility, not an edge case requiring adversarial timing.

### Recommendation
`reward_only_active` should gate on the validator set that was active during `session_index` (i.e., derived consistently with `session_info::AccountKeys::<C>::get(&session_index)`), not on `C::ValidatorSet::validators()` at call time. If the intent is genuinely to only reward validators who are *currently* active (e.g., to avoid rewarding since-slashed/removed identities), that intent should be reconciled with dispute semantics explicitly — e.g., by snapshotting the eligible-for-reward set at the same historical point used to resolve identities, or by tracking forfeited-but-earned points so they are visible/recoverable rather than silently vanishing from `era_rewards.total`.

### Proof of Concept
1. Validator `V` is a member of the active validator set during session `N` and backs a candidate / casts a valid dispute statement that is part of session `N`'s dispute resolution.
2. Several sessions pass; through ordinary rotation (election results, chilling, etc.) `V` is no longer part of `C::ValidatorSet::validators()` — the *current* active set — while still being correctly resolvable via `session_info::AccountKeys::<C>::get(N)`.
3. The dispute for session `N`'s candidate concludes later (or, for backing, the reward call fires after rotation) and `crate::disputes::RewardValidators::reward_dispute_statement(N, validators)` (or `reward_backing`) is invoked.
4. Inside `reward_only_active`, `active_set.contains(v)` evaluates `false` for `V`, so `V` is filtered out of `rewards` before `R::reward_by_ids` is ever called.
5. `V` receives no `ErasRewardPoints` credit for session `N`'s dispute vote/backing despite having done the qualifying work while legitimately active, permanently reducing `V`'s share of that era's `payout_stakers` distribution with no corresponding event or recovery path.

	fn reward_only_active(
		session_index: SessionIndex,
		indices: impl IntoIterator<Item = ValidatorIndex>,
		points: u32,
	) {
		let validators = session_info::AccountKeys::<C>::get(&session_index);
		let validators = match validators
			.defensive_proof("account_keys are present for dispute_period sessions")
		{
			Some(validators) => validators,
			None => return,
		};
		// limit rewards to the active validator set
		let active_set: BTreeSet<_> = C::ValidatorSet::validators().into_iter().collect();

		let rewards = indices
			.into_iter()
			.filter_map(|i| validators.get(i.0 as usize).cloned())
			.filter(|v| active_set.contains(v))
			.map(|v| (v, points));

		R::reward_by_ids(rewards);
	}

	/// Add reward points to validators using their stash account ID.
	///
	/// Validators are keyed by stash account ID and must be in the current elected set.
	///
	/// For each element in the iterator the given number of points in u32 is added to the
	/// validator, thus duplicates are handled.
	///
	/// At the end of the era each the total payout will be distributed among validator
	/// relatively to their points.
	///
	/// COMPLEXITY: Complexity is `number_of_validator_to_reward x current_elected_len`.
	fn reward_by_ids(validators_points: impl IntoIterator<Item = (T::AccountId, u32)>) {
		if let Some(active_era) = ActiveEra::<T>::get() {
			<ErasRewardPoints<T>>::mutate(active_era.index, |era_rewards| {
				for (validator, points) in validators_points.into_iter() {
					*era_rewards.individual.entry(validator).or_default() += points;
					era_rewards.total += points;
				}
			});
		}
	}

	/// Add reward points to validators using their stash account ID.
	///
	/// As a side effect, accumulates `weight × points` into [`ErasSumWeightedPoints`] for the
	/// active era, where `weight` is the validator's [`ErasValidatorIncentiveWeight`]. This
	/// keeps the denominator of the weighted-points share up to date without iterating every
	/// validator at payout time.
	pub(crate) fn reward_active_era(
		validators_points: impl IntoIterator<Item = (T::AccountId, u32)>,
	) {
		if let Some(active_era) = ActiveEra::<T>::get() {
			let mut sum_weighted_points_delta: BalanceOf<T> = Zero::zero();
			<ErasRewardPoints<T>>::mutate(active_era.index, |era_rewards| {
				for (validator, points) in validators_points.into_iter() {
					let weight =
						ErasValidatorIncentiveWeight::<T>::get(active_era.index, &validator)
							.unwrap_or_else(Zero::zero);

					let recorded = match era_rewards.individual.get_mut(&validator) {
						Some(individual) => {
							individual.saturating_accrue(points);
							true
						},
						None => {
							// not much we can do -- validators should always be less than
							// `MaxValidatorSet`.
							era_rewards.individual.try_insert(validator, points).defensive().is_ok()
						},
					};

					// Keep the denominator aligned with `individual`, which is the source used
					// by payouts and try-state recomputation. A defensive overflow may leave
					// points unrecorded; those points must not be counted in
					// `ErasSumWeightedPoints`.
					if recorded && !weight.is_zero() {
						sum_weighted_points_delta = sum_weighted_points_delta.saturating_add(
							weight.saturating_mul(IncentiveWeight::<T>::from(points)),
						);
					}

					era_rewards.total.saturating_accrue(points);
				}
			});
			if !sum_weighted_points_delta.is_zero() {
				ErasSumWeightedPoints::<T>::mutate(active_era.index, |sum| {
					*sum = sum.saturating_add(sum_weighted_points_delta);
				});
			}
		}
	}
