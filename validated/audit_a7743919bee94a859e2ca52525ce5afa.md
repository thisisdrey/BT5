## Analysis

The BYToken exploit pattern — a permissionless, anyone-callable operation that mutates a liquidity pool's reserve ratio, followed by tiny repeated trades that extract disproportionate value from the resulting mispriced pool — has a direct structural analog in java-tron's built-in **TRC10 Exchange (Bancor-style AMM)**. `ExchangeTransactionActuator` is fully permissionless (any account can call it against any existing exchange pair) and its swap math is delegated to `ExchangeCapsule.transaction()`, which by default (non-hardened path) uses the double-precision, floating-point Bancor formula in `ExchangeProcessor` rather than the `BigDecimal`-based `SafeExchangeProcessor`.

### Title
Permissionless TRC10 Exchange swaps use floating-point Bancor math that permits reserve-ratio drift and value extraction via repeated tiny trades - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeTransactionActuator.execute()` lets any signed transaction call the AMM swap function against an `ExchangeCapsule` pool with no access control beyond having sufficient balance/asset. [1](#0-0) 
The swap output is computed by `ExchangeCapsule.transaction()`, which selects a legacy `ExchangeProcessor` (double/`Math.pow`-based) unless the chain-wide `allowHardenExchangeCalculation` proposal is enabled, in which case the exact `SafeExchangeProcessor` (`BigDecimal`) path is used instead. [2](#0-1) 

### Finding Description
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` perform the Bancor "relay" conversion using `double` arithmetic and `Math.pow`, then truncate with a `(long)` cast. [3](#0-2) 
This is materially different from the hardened `SafeExchangeProcessor`, which performs the same computation with `BigDecimal` at 18-digit precision and rounds deterministically. [4](#0-3) 
The project's own test suite explicitly demonstrates that the legacy and hardened processors diverge on the same inputs (`Assert.assertNotEquals(anotherTokenQuant, result)` for legacy-vs-strict, contrasted with `assertEquals(safeResult, result)` for hardened-vs-strict), confirming the floating-point path is not equivalent/safe. [5](#0-4) 

Because `ExchangeTransactionActuator` is open to any caller and directly mutates `firstTokenBalance`/`secondTokenBalance` on every call with no minimum-trade-size floor and no slippage protection beyond a caller-supplied `tokenExpected` (which the attacker themselves controls), [6](#0-5) 
an attacker can, within a single block/transaction sequence, perform a chain of trades that (a) skews the pool ratio using large trades, then (b) repeatedly executes minimum-size trades that benefit from floating-point rounding/truncation error accumulated in the double-based formula — mirroring the "corner buy → donate/skew reserve → drain via many minimal trades" sequence in the BYToken PoC (`BUY1` corner trade, `DONATE`+`sync` reserve skew, then five 1-wei `swapExactTokensForTokensSupportingFeeOnTransferTokens` calls). The `ExchangeInjectActuator`/`ExchangeWithdrawActuator` (creator-only) additionally use floor-division (`floorDiv`) for the "anotherTokenQuant" computed from ratios, [7](#0-6) 
compounding rounding drift that a permissionless `ExchangeTransactionActuator` caller can then exploit against the resulting skewed pool state.

### Impact Explanation
Repeated exploitation of the floating-point truncation/rounding divergence lets an attacker extract TRX or TRC10 token value from the AMM pool beyond what the exact Bancor invariant would allow, i.e., an unauthorized transfer of value out of the exchange pool funded implicitly by other liquidity participants — a concrete unbacked-balance/theft-of-funds condition reachable purely through a sequence of ordinary, permissionless `ExchangeTransactionContract` transactions.

### Likelihood Explanation
Any account with minimal TRX/asset balance can submit `ExchangeTransactionContract` transactions against any existing TRC10 exchange pool; no special privilege, whitelist, or governance action is required, and the vulnerable double-precision path is the default unless the `allowHardenExchangeCalculation` chain parameter has been activated by committee proposal. Exchanges created with small reserves or that receive skewing trades are most exposed, analogous to how the BYToken pool was cornered before the burn trigger.

### Recommendation
Make the hardened `SafeExchangeProcessor` (`BigDecimal`-based) the default and only path for exchange swap accounting, removing the legacy double/`Math.pow` code path in `ExchangeProcessor`, or otherwise enforce invariant checks (e.g., verify the constant-product/Bancor invariant is non-decreasing after each trade) inside `ExchangeCapsule.transaction()` regardless of which processor is selected, and add a minimum trade-size/rate-limiting guard in `ExchangeTransactionActuator` to prevent invariant-eroding micro-trades.

### Proof of Concept
Not independently reproduced against this codebase; the analog is inferred from the BYToken PoC's "corner buy → reserve-skewing donate/sync → burn → repeated 1-unit trade drain" structure mapped onto the java-tron TRC10 Exchange's permissionless `ExchangeTransactionActuator` and its floating-point `ExchangeProcessor` swap math, as evidenced by the actuator/test code cited above. A concrete PoC would require constructing an `ExchangeCreateContract` pool, executing a sequence of `ExchangeTransactionContract` trades sized to maximize double-precision truncation error, and measuring pool balances before/after to quantify extractable value — this would need to be built and run in a Devin session with full repository/test-harness access.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
