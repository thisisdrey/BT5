The `phase4Users`-style bug depends on an eligibility mapping that is credited once but not cleared/consumed before the next period reuses the same key, letting a user redeem into a later period's pool. I checked the closest structural analogs in this repository:

- `PortfolioVault`'s async claim pools (`claimableDepositAssets/Shares`, `claimableRedeemAssets/Shares`) are explicitly decremented by the exact claimed amount inside `_claimDeposit`/`_claimRedeem`, and the aggregate counters (`totalPendingDepositAssets`, `totalClaimableRedeemAssets`) are kept in lockstep, per the documented conservation invariant. [1](#0-0) 
- `LoansExchange` offers are fully deleted (`delete _offers[offerId]`) on both accept and cancel paths before any settlement, so a stale offer struct can never be reused across cycles. [2](#0-1) 
- The vault's curated NAV loan list (`_navLoanIds` / `_navLoanIndex`) is explicitly cleared on `setLoans` and swap-and-popped on every removal, preventing stale entries from carrying into a new cycle. [3](#0-2) 
- `Loans.investorWithdraw`/`servicerWithdraw`/`originatorWithdraw` recompute payable amounts fresh from the ledger each call (`_getNetPayable`, `_getNetInterestPayableToInvestor`, etc.) rather than relying on a period-scoped eligibility flag, so there is no dangling "already credited but not consumed" balance that a later call could double-spend. [4](#0-3) 

None of these paths exhibit the AirdropBroker root cause (a period-keyed credit mapping left non-zero and reusable after the intended period ends). I did not find a reachable, unprivileged trigger producing a corrupted balance, owner, or claimable amount matching this bug class in the current scope.
