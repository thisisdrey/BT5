### Title
`GetAttachmentResponse::deserialize` and the attachment download path never enforce `AtlasConfig.attachments_max_size` - ([File: stackslib/src/net/atlas/mod.rs])

### Summary
`GetAttachmentResponse::deserialize` (stackslib/src/net/atlas/mod.rs:69-76) hex-decodes an attacker-controlled string from an HTTP response body and wraps it in `Attachment::new(bytes)` with no size check at all. The downstream download path in `stackslib/src/net/atlas/download.rs` that consumes this response and calls `extend_with_attachments` also never references `attachments_max_size` (confirmed by the absence of any `attachments_max_size` usage in `download.rs`, unlike `mod.rs`, `db.rs`, `config/mod.rs`, and `tests.rs`), so an oversized attachment can flow all the way to storage.

### Finding Description
`GetAttachmentResponse::deserialize`: [1](#0-0) 
performs `hex_bytes(&hex_encoded)` and constructs `Attachment::new(bytes)` directly from a remote peer's HTTP response, with no comparison of `bytes.len()` against `AtlasConfig.attachments_max_size` anywhere in this function or in its caller `StacksHttpResponse::decode_atlas_get_attachment`: [2](#0-1) 

`AtlasConfig.attachments_max_size` is defined and validated only as a config-level minimum bound (`AtlasConfig::validate` at mod.rs:116-121), not as a per-attachment enforcement point: [3](#0-2) 

Critically, a repo-wide search for `attachments_max_size` shows it appears in `mod.rs`, `config/mod.rs`, `db.rs`, and `tests.rs`, but is entirely absent from `download.rs` — the module responsible for actually processing peer-supplied `GetAttachmentResponse` payloads and inserting them via `extend_with_attachments`. This confirms that no code on the attachment-fetch path checks the decoded content length before it is accepted and merged into the batch state.

An attacker does not need to break Hash160 preimage resistance: they can legitimately publish (via a normal BNS/Atlas-tracked contract call) an attachment instance whose `content_hash` corresponds to content of their own choosing (of arbitrary size), because they control the content before hashing it. When the victim node's Atlas subsystem then issues `GET /v2/attachments/{hash}` to fetch it, the attacker's node (or any peer relaying the attacker's malicious response) can return a JSON body containing a multi-hundred-MB hex string that legitimately hashes to the expected `content_hash`. The hash-match check (present elsewhere in download.rs) will pass because the hash is genuinely correct — but the size is never bounded.

### Impact Explanation
A malicious peer can force victim nodes to accept and persist attachments far larger than the configured `attachments_max_size` (default/minimum 1 MiB), consuming attacker-controlled amounts of disk in `AtlasDB`. This is a storage-exhaustion vector reachable via a single crafted RPC-style response from any peer serving attachment data the victim requests, matching the "High: attachment/BNS mismatch"-adjacent resource-exhaustion category via the RPC/Atlas surface, repeatable per attachment hash the attacker registers.

### Likelihood Explanation
Preconditions: the attacker needs only to (1) register/announce an attachment instance whose content hash matches oversized content they control (achievable through normal, permissionless Atlas/BNS attachment-instance flow), and (2) respond to the victim's `GET /v2/attachments/{hash}` request with the oversized hex payload. No RPC secret, peer key, or privileged role is required — this fits the unprivileged remote-peer threat model. The cost to the attacker is bounded only by their own bandwidth to serve the oversized response once; the resulting storage cost to the victim is asymmetric and repeatable across many distinct attachment hashes.

### Recommendation
Enforce `attachments_max_size` at the point the attachment bytes are first materialized: in `GetAttachmentResponse::deserialize` (reject if `bytes.len() as u32 > attachments_max_size`, though the deserializer currently has no access to `AtlasConfig`, so this check should instead be added immediately after `decode_atlas_get_attachment()` is called in the download path, before the attachment is merged via `extend_with_attachments`), rejecting any response whose decoded content exceeds `atlas_config.attachments_max_size` prior to insertion into the batch/`AtlasDB`.

### Proof of Concept
1. Construct a `StacksHttpResponse` with a JSON body `"<200MB-hex-string>"` matching the `GetAttachmentResponse` serialize format.
2. Call `StacksHttpResponse::decode_atlas_get_attachment()` on it and observe it succeeds, returning `GetAttachmentResponse { attachment }` with `attachment.content.len()` in the hundreds of megabytes.
3. Trace this response object into the download path (`download.rs`) and confirm no call site compares `attachment.content.len()` to `atlas_config.attachments_max_size` before `extend_with_attachments` is invoked, i.e., assert `attachment.content.len() as u32 > atlas_config.attachments_max_size` holds true after the call, proving the bound `content.len() <= attachments_max_size` is violated.

impl<'de> Deserialize<'de> for GetAttachmentResponse {
    fn deserialize<D: serde::Deserializer<'de>>(d: D) -> Result<GetAttachmentResponse, D::Error> {
        let payload = String::deserialize(d)?;
        let hex_encoded = payload.parse::<String>().map_err(de_Error::custom)?;
        let bytes = hex_bytes(&hex_encoded).map_err(de_Error::custom)?;
        let attachment = Attachment::new(bytes);
        Ok(GetAttachmentResponse { attachment })
    }

impl StacksHttpResponse {
    pub fn decode_atlas_get_attachment(self) -> Result<GetAttachmentResponse, NetError> {
        let contents = self.get_http_payload_ok()?;
        let contents_json: serde_json::Value = contents.try_into()?;
        let resp: GetAttachmentResponse = serde_json::from_value(contents_json)
            .map_err(|_e| NetError::DeserializeError("Failed to load from JSON".to_string()))?;
        Ok(resp)
    }
