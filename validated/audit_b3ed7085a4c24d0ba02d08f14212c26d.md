### Title
Unauthenticated flooding of `AtlasDB::insert_uninstantiated_attachment` via `POST /v2/transactions` can evict a legitimately-referenced attachment before it is instantiated - ([File: stackslib/src/net/atlas/db.rs])

### Summary
`RPCPostTransactionRequestHandler::try_handle_request` lets any remote peer attach an arbitrary `Attachment` blob to a `ContractCall` transaction and have it stored via `AtlasDB::insert_uninstantiated_attachment`, gated only by `should_keep_attachment` (a contract-id watch-list check), not by whether the attachment's hash is actually referenced by a pending `AttachmentInstance`. Because `insert_uninstantiated_attachment`'s eviction logic (`evict_k_oldest_uninstantiated_attachments`) purely evicts by `created_at` age with no check for whether an attachment is still needed by an unresolved `AttachmentInstance`, an attacker can fill the `attachments` table with junk up to `max_uninstantiated_attachments` and force eviction of a legitimately committed attachment before `check_attachment_instances`/`find_uninstantiated_attachment` can consume it.

### Finding Description
The broken equality: the set of rows in the `attachments` table with `was_instantiated = 0` should be a superset (or at least contain) every `Attachment` referenced by an outstanding on-chain `AttachmentInstance` commitment until it is instantiated. In practice, insertion is unconditional aside from a contract-id allow-list check, and eviction has no awareness of which attachments are still "wanted" by a pending `AttachmentInstance`.

Code path:
- `RPCPostTransactionRequestHandler::try_handle_request` accepts a JSON POST body containing a `StacksTransaction` and an optional `attachment`. If the tx is a `TransactionPayload::ContractCall` and `network.get_atlasdb().should_keep_attachment(contract_id, attachment)` returns true, it calls `network.get_atlasdb_mut().insert_uninstantiated_attachment(attachment)` [1](#0-0) .
- `insert_uninstantiated_attachment` checks `count_uninstantiated_attachments()` against `atlas_config.max_uninstantiated_attachments`; if at/over the limit it evicts `to_delete` oldest rows via `evict_k_oldest_uninstantiated_attachments`, then unconditionally inserts (`INSERT OR REPLACE`) the new attachment with `was_instantiated = 0` [2](#0-1) .
- `evict_k_oldest_uninstantiated_attachments` deletes the `k` oldest rows from `attachments` where `was_instantiated = 0`, ordered strictly by `created_at`, with no join against `attachment_instances` to see if any pending, unresolved `AttachmentInstance.content_hash` still points at that row [3](#0-2) .
- Later, `find_uninstantiated_attachment(content_hash)` is used by the downloader/check logic to look up an attachment by hash among `was_instantiated = 0` rows; if it was evicted, this returns `None` and the legitimate `AttachmentInstance` can never be resolved from local storage [4](#0-3) .

Exploit flow: an attacker crafts many signed `StacksTransaction` with `TransactionPayload::ContractCall` targeting a contract on Atlas's watched-contract list (e.g., the BNS contract configured in `AtlasConfig`), each paired with a distinct junk `Attachment` payload whose hash matches nothing that will ever be committed on-chain. Each POST to `/v2/transactions` that passes `mempool.submit` and `should_keep_attachment` results in one more row inserted via `insert_uninstantiated_attachment`. Once `max_uninstantiated_attachments` junk rows accumulate, every subsequent insert (including a genuinely relevant attachment that a real BNS operation will reference) triggers eviction of the oldest row — which, due to insertion ordering, can be the legitimately-needed attachment inserted earlier by a real client, rather than the attacker's own junk.

Existing guards fail because: `should_keep_attachment` only filters by contract id (a public, known value), not by whether the attachment hash corresponds to an actual pending `AttachmentInstance` commitment; and the eviction query has no `NOT IN (SELECT content_hash FROM attachment_instances WHERE is_available = 0)` style exclusion, so it can delete rows that are still awaited by unresolved instances.

### Impact Explanation
A legitimate BNS attachment (e.g., a name registration/update's zone file) that has a confirmed `AttachmentInstance` commitment on-chain can become permanently unresolvable locally on the victim node: `find_uninstantiated_attachment` will return `None` for it, and the corresponding attachment/BNS state served to clients from that node will not match what the chain actually committed to. This matches the "attachment/BNS mismatch" High-severity category. The attack is repeatable indefinitely at low cost per message (each POST is one HTTP request with a signed tx), and any remote peer with `/v2/transactions` access can perform it against any node exposing that RPC endpoint.

### Likelihood Explanation
Preconditions: attacker needs (a) network reachability to the victim's RPC port, (b) the ability to produce validly-signed `StacksTransaction`s that pass `mempool.submit` (any funded/nonce-valid account, not privileged), and (c) knowledge of a contract id on the node's `AtlasConfig` watch list (public/well-known, e.g. BNS). No admin role, RPC secret, or peer key ownership is required. The number of messages needed equals `max_uninstantiated_attachments` (a bounded, moderate config value), making this cheap and fully automatable and repeatable against any publicly-reachable Stacks node.

### Recommendation
Modify eviction to exclude attachments that are still referenced by an unresolved `AttachmentInstance` (i.e., join against `attachment_instances WHERE is_available = 0` and exclude those `content_hash`es from the eviction candidate set), or track a "reserved" flag on `attachments` rows that are known to be referenced by a pending, unchecked/unresolved instance, and never evict reserved rows. Additionally, consider rate-limiting or requiring `should_keep_attachment` to verify the attachment hash actually corresponds to a known/expected pending `AttachmentInstance` content hash before accepting the insert.

### Proof of Concept
Rust net test (in `stackslib/src/net/atlas/tests.rs`, extending existing `insert_uninstantiated_attachment`/`evict_k_oldest_uninstantiated_attachments` tests):
1. Construct an `AtlasDB` with `AtlasConfig::max_uninstantiated_attachments = N`.
2. Insert a legitimate attachment `legit` via `insert_uninstantiated_attachment(&legit)`, and separately insert a matching `AttachmentInstance` row (via `insert_new_attachment_instance` or equivalent) referencing `legit.hash()`, with `is_available = 0`.
3. Loop, calling `insert_uninstantiated_attachment(&junk_i)` for `i` in `0..N` with distinct junk attachments.
4. Assert `atlasdb.find_uninstantiated_attachment(&legit.hash())` — if it returns `None` (and `count_uninstantiated_attachments() == N` with `legit` no longer present), this confirms eviction destroyed a still-referenced attachment before `check_attachment_instances` could resolve it, proving the vulnerability at `evict_k_oldest_uninstantiated_attachments` (db.rs:538-547).

    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_k_oldest_uninstantiated_attachments(&mut self, k: u32) -> Result<(), db_error> {
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE hash IN (SELECT hash FROM attachments WHERE was_instantiated = 0 ORDER BY created_at ASC LIMIT ?)",
            params![k],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }
