## Title
User's wNEAR `storage_deposit` amount is debited from internal balance but never refunded on failure in `ft_withdraw`/`mt_withdraw` - (File: `contracts/defuse/src/contract/tokens/nep141/withdraw.rs`)

### Summary
When a member calls `ft_withdraw()` (or `mt_withdraw()`) with an optional `storage_deposit`, both the withdrawn token amount and the `storage_deposit` (in wNEAR) are debited from the user's internal Defuse balance in a single `withdraw()` call [1](#0-0) . However, the resolver callback `ft_resolve_withdraw` only knows about and can refund the withdrawn token `amount` - it has no parameter for `storage_deposit` and therefore can never restore it to the user, no matter which downstream promise (`near_withdraw`, `storage_deposit`, or `ft_transfer`) fails [2](#0-1) .

### Finding Description
`internal_ft_withdraw()` subtracts both the withdrawal `amount` and `storage_deposit` from the owner's internal ledger balance up front: [1](#0-0) 

It then kicks off a promise chain: `near_withdraw(storage_deposit)` on the wNEAR contract → `do_ft_withdraw()` (which does `storage_deposit()` on the target token contract, then `ft_transfer`/`ft_transfer_call`) → `ft_resolve_withdraw()`: [3](#0-2) 

`ft_resolve_withdraw()` is only given `token, sender_id, amount, is_call` - i.e., information about the *withdrawn token*, not the `storage_deposit`. It computes `used` from the result of the last promise in the chain (the `ft_transfer`/`ft_transfer_call`) and refunds only `amount - used` of the withdrawn token back into the internal ledger: [4](#0-3) 

If `near_withdraw()` fails (e.g. insufficient gas, or wNEAR contract issue) or the subsequent `storage_deposit()` call on the target token fails, `do_ft_withdraw()`'s `require!(promise_result_checked_void(0).is_ok(), "near_withdraw failed")` panics, causing the entire downstream promise (and hence the `ft_transfer`) to never execute or to fail. Regardless of this outcome, the user's `storage_deposit` amount was already irreversibly subtracted from their internal Defuse balance in `withdraw()`, and the wNEAR was either never unwrapped (still sitting as wNEAR balance on the wNEAR contract, owned by Defuse) or was unwrapped into real NEAR held by the Defuse contract account itself and then never delivered to anyone. Since `ft_resolve_withdraw` has no channel to refund `storage_deposit`, this value is permanently stranded from the user's perspective: debited from their ledger, but never delivered to the intended `storage_deposit` recipient nor refunded to the user.

The same pattern repeats identically in `mt_withdraw`/`do_mt_withdraw`/`mt_resolve_withdraw`: [5](#0-4) [6](#0-5) 

This breaks the conservation binding: **value debited from user ≠ value delivered + value refunded**. It is directly analogous to the Spartan `removeLiquiditySingle()` bug, where one leg of a compound multi-token operation (SPARTA) was debited from the user but never routed back to them because the resolver/callback logic that returns funds only accounted for one of the two moved assets (TOKENs), stranding the other (SPARTA) in the intermediary contract.

### Impact Explanation
This is a Critical-class finding under the given rubric: funds are permanently frozen/lost from the user's perspective. The `storage_deposit` wNEAR amount is deducted from the user's internal Defuse balance but the code path that could restore it (`ft_resolve_withdraw` / `mt_resolve_withdraw`) is structurally unaware of it, so it can never be credited back regardless of promise outcome. Any transient failure in the `near_withdraw` or target-contract `storage_deposit` call (gas exhaustion, target contract rejecting the storage deposit, insufficient attached balance edge cases, etc.) causes silent, permanent loss of the `storage_deposit` amount for that user.

### Likelihood Explanation
The `storage_deposit` option is a standard, documented parameter of `ft_withdraw`/`mt_withdraw` used whenever withdrawing to a receiver that isn't registered on the target token contract - a common and expected usage pattern, not a contrived edge case. Any cross-contract call failure at the `near_withdraw()` or `storage_deposit()` stage (both external calls to other contracts, subject to normal NEAR gas/promise failure modes) will trigger this loss, making it a plausible occurrence in production rather than a purely theoretical scenario.

### Recommendation
Thread the `storage_deposit` amount through `do_ft_withdraw`/`do_mt_withdraw` into `ft_resolve_withdraw`/`mt_resolve_withdraw` (or use a separate resolver parameter/promise index) so that on any failure of `near_withdraw`, the target `storage_deposit`, or the final transfer, the `storage_deposit` amount is deposited back into the user's internal balance exactly as the main withdrawal `amount` already is. Alternatively, restructure the promise chain so a single resolver observes the outcome of each individual sub-step (near_withdraw, storage_deposit, transfer) and refunds each independently.

### Proof of Concept
1. User has internal balance of `X` of `token` and `Y` yoctoNEAR-equivalent of wNEAR.
2. User calls `ft_withdraw(token, receiver_id, amount=X, storage_deposit=Some(Y), msg=None)` where `receiver_id` is not registered on `token`.
3. `internal_ft_withdraw` immediately subtracts `X` of `token` and `Y` of wNEAR from user's internal balance [1](#0-0) .
4. `near_withdraw(Y)` is called on the wNEAR contract. Assume it fails or runs out of gas.
5. `do_ft_withdraw` panics at `require!(promise_result_checked_void(0).is_ok(), ...)` [7](#0-6) , so no `storage_deposit()` or `ft_transfer` occurs.
6. `ft_resolve_withdraw` runs with `promise_result_checked_void(0)` (or json check) failing, refunds `X` (the token `amount`) back to the user via `self.deposit(...)` [8](#0-7)  — but `Y` (the `storage_deposit` wNEAR) is never mentioned in this call and is never refunded.
7. Result: user's internal balance is missing `Y` of wNEAR permanently, with no promise anywhere crediting it back to the user or delivering it to the intended `receiver_id`'s storage deposit.

#[near]
impl Contract {
    const FT_RESOLVE_WITHDRAW_GAS: Gas = Gas::from_tgas(5);
    const DO_FT_WITHDRAW_GAS: Gas = Gas::from_tgas(5)
        // do_ft_withdraw() method is called externally
        // only with storage_deposit
        .saturating_add(STORAGE_DEPOSIT_GAS);

    #[private]
    pub fn do_ft_withdraw(withdraw: FtWithdraw) -> Promise {
        let min_gas = withdraw.min_gas();
        let p = if let Some(storage_deposit) = withdraw.storage_deposit {
            require!(
                promise_result_checked_void(0).is_ok(),
                "near_withdraw failed",
            );

            ext_storage_management::ext(withdraw.token)
                .with_attached_deposit(storage_deposit)
                .with_static_gas(STORAGE_DEPOSIT_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .storage_deposit(Some(withdraw.receiver_id.clone()), None)
        } else {
            Promise::new(withdraw.token)
        };

        let p = ext_ft_core::ext_on(p)
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(min_gas)
            // distribute remaining gas here
            .with_unused_gas_weight(1);
        if let Some(msg) = withdraw.msg {
            p.ft_transfer_call(
                withdraw.receiver_id,
                withdraw.amount.into(),
                withdraw.memo,
                msg,
            )
        } else {
            p.ft_transfer(withdraw.receiver_id, withdraw.amount.into(), withdraw.memo)
        }
    }

    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
