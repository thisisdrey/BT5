### Title
Heap out-of-bounds read via unbounded extra-field chain parsing in JAR central directory — (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` parses each ZIP/JAR central directory entry from an attacker-controlled `.jar`/`.zip` file with no bounds checking against the mapped input file, and its "extra field" sub-parsing loop walks a chain of variable-length records using an attacker-controlled 16-bit `data_size` with no validation that the record stays within the declared `extra_field_length` region or within the mapped file at all.

### Finding Description
`ProcessCentralDirEntry` reads the fixed 46-byte central directory header fields, `file_name_length`, `extra_field_length`, and `file_comment_length` directly off the mapped file pointer `p` with **no call to `EnsureRemaining`** (that check is only used inside `ProcessLocalFileEntry` for local headers) [1](#0-0) .

After advancing past the (unchecked) file name, it walks the extra-field area as a chain of length-prefixed sub-records:
```
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
``` [2](#0-1) 

This is structurally the same bug class as the CVE-2023-35970 analog: a chained/length-prefixed table (`chain_table` in GTKWave, extra-field chain here) is walked using an attacker-supplied `data_size` field with no check that `extra_p + 4 <= end` before reading `header_id`/`data_size`, and no check that `extra_p + data_size <= p` (the declared end of the extra-field region) before advancing. If a crafted entry sets `data_size` so that `extra_p` overshoots `p` instead of landing exactly on it, the loop's `extra_p != p` termination condition never becomes true through normal convergence — the loop continues reading 4-byte header/size pairs from memory past the intended extra-field boundary, and past the end of the mapped input file entirely, since there is no bound derived from `input_file_->Length()` anywhere in this function. Each iteration performs `get_u2le`/`get_u4le`/`get_u8le` reads (the `ZIP64_EXTRA_FIELD_TAG` branch reads 8-byte values) from attacker-influenced, unchecked offsets — a heap-based out-of-bounds read chain directly analogous to the FST `chain_table`/`FST_BL_VCDATA_DYN_ALIAS2` heap overflow.

Both `InputZipFile::ProcessNext` (used by the general zip extraction/rewriting API, e.g. singlejar's `AddJar`) and `InputZipFile::CalculateOutputLength` invoke `ProcessCentralDirEntry` in a loop over the whole central directory of an input jar with no additional bounds validation before or after the call [3](#0-2) , so any caller that opens an untrusted `.jar`/`.zip` (ijar interface-jar generation, singlejar merging of dependency jars) reaches this unchecked parser directly on attacker-supplied bytes.

### Impact Explanation
An attacker who serves a malicious `.jar`/`.zip` file that a victim's Bazel build consumes as an input (e.g., via a dependency fetched without a verified checksum, or via a mutable mirror/registry entry) can craft a central directory extra-field chain whose `data_size` values cause the parsing loop to walk arbitrarily far past the mapped file buffer. This is a heap-based out-of-bounds read that can crash the build tool (ijar/singlejar) or, depending on memory layout, read adjacent heap/mapped memory into subsequently used size fields (e.g., the ZIP64 branch feeds OOB-read 64-bit values directly into `*uncompressed_size`/`*compressed_size`/`*offset`), which downstream size/offset computations (`CalculateOutputLength`, `AddJar`) then trust for further processing.

### Likelihood Explanation
Reaching this code only requires supplying a syntactically-valid-looking central directory with a crafted extra field chain inside a `.jar`/`.zip`; no privileged access, MITM, or credentials are needed — only that the victim's build processes the attacker-supplied archive with ijar or singlejar without the archive having been rejected earlier by checksum/integrity verification (e.g., an unpinned or incorrectly-scoped dependency).

### Recommendation
Add explicit bounds checks in `ProcessCentralDirEntry` and its extra-field loop: verify `extra_field_length`/`file_name_length`/`file_comment_length` do not exceed the remaining mapped-file length before advancing `p`, and inside the extra-field loop verify `extra_p + 4 <= p` before reading `header_id`/`data_size`, and `extra_p + data_size <= p` before advancing, aborting/erroring otherwise (mirroring the containment checks already present in `singlejar`'s `OutputJar::WriteEntry`/`AppendToDirectoryBuffer`, e.g. `ziph::byte_ptr(ef) + ef->size() > ziph::byte_ptr(ef_end)` [4](#0-3) ).

### Proof of Concept
A JUnit/`src/test/shell` reproducer would: (1) construct a minimal valid ZIP central directory entry, (2) append an extra-field chain whose first sub-record declares `data_size = 0xFFFF` (or a value engineered so `extra_p` never re-equals `p`), (3) truncate the file shortly after so the extra-field region is near the end of the mapped file, and (4) invoke `ijar`/`singlejar`'s zip-processing entrypoint (`ProcessNext`/`CalculateOutputLength`) on this crafted file and observe an out-of-bounds read/crash (e.g., via ASan) originating in `ProcessCentralDirEntry`'s extra-field loop rather than a clean parse error.
