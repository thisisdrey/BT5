### Title
Unbounded stdin size hashed and buffered to disk in `PackObjectsHookWithSidechannel` cache-key computation enables DoS - (File: `internal/gitaly/service/hook/pack_objects.go`)

### Summary
`computeCacheKey` in the `PackObjectsHookWithSidechannel` handler hashes an attacker-controlled, size-unbounded stream (the `git upload-pack` negotiation payload sent over the sidechannel) while simultaneously buffering the entire stream to a temporary file, with no upper bound on the amount of data that can be fed into this path. This mirrors the reported bug class: a validation/keying step that consumes unbounded caller-supplied bytes with no size limit before any authorization or resource check is applied, letting an ordinary client waste server CPU, memory, and disk.

### Finding Description
`PackObjectsHookWithSidechannel` is invoked as part of every `git fetch`/`clone` (`upload-pack`) request that uses the pack-objects cache. It calls `s.packObjectsHook`, which calls `s.computeCacheKey`: [1](#0-0) 

`computeCacheKey` builds a `sha256` hash over the marshaled request prefix and then over `stdinReader` via `bufferStdin`: [2](#0-1) 

`bufferStdin` reads from `r` (the sidechannel connection controlled entirely by the connecting git client — the negotiation lines such as `want`/`have`) with `io.Copy(f, io.TeeReader(r, h))`, hashing every byte and writing it to an unbounded temp file, with no cap on the total number of bytes read. Unlike normal gRPC request fields (which are bounded by the gRPC max message size), the sidechannel stream used here bypasses that limit entirely — `GetSidechannel` in `internal/gitaly/hook/sidechannel.go` just returns a raw `net.Conn` for the caller to read as much as it wants. The handler is reached from `PackObjectsHookWithSidechannel`, which only validates the repository and parses `pack-objects` arguments before invoking the hook — it never validates or caps the size of the negotiation payload: [3](#0-2) 

Because a git client fully controls the pktline negotiation body it sends when initiating upload-pack (e.g., via crafted `have`/`want` lines or arbitrary extra bytes appended to the negotiation stream), it can send an arbitrarily large stream to be both hashed and written to disk before the cache key is even computed, i.e., before any request-size-based cost or authorization decision is made.

### Impact Explanation
An ordinary, unauthenticated-relative-to-repository-content git client performing a normal fetch/clone can force the Gitaly node to hash and persist to a temporary file an unbounded amount of attacker-supplied data on every request, consuming CPU (hashing), disk I/O and space (temp file), and memory (buffering), without any pre-check limiting the payload size. This is a resource-exhaustion / DoS vector against the RPC handler analogous to the reported bug: unconstrained size of attacker data fed into a cryptographic hash used purely for cache-key derivation.

### Likelihood Explanation
The path is reached on the default `upload-pack`/fetch flow whenever the pack-objects cache is enabled (a supported, documented production configuration — see `doc/design_pack_objects_cache.md`), requiring no special privileges beyond being able to initiate a fetch against a repository, making this readily reachable by any ordinary user or automated CI-like client.

### Recommendation
Enforce an explicit upper bound on the number of bytes read from the sidechannel negotiation stream before hashing/buffering in `bufferStdin` (e.g., reject or truncate once a configured maximum negotiation size is exceeded), and apply that limit prior to writing data to the temp file or into the hash function.

### Proof of Concept
A client can perform a normal `git fetch` against a repository served by a Gitaly node with the pack-objects cache enabled, but instead of sending a well-formed, short pktline negotiation, it opens the sidechannel connection used for `PostUploadPackWithSidechannel`/SSH `upload-pack` and streams an arbitrarily large amount of data (e.g., gigabytes of repeated `have <oid>\n` pktlines or padding) before closing the write side. Because `bufferStdin` (`internal/gitaly/service/hook/pack_objects.go:342-367`) unconditionally copies and hashes the full stream with no size cap, the server will spend CPU hashing and disk I/O persisting the entire attacker-chosen payload for every such request, regardless of what a legitimate negotiation would normally require.

func (s *server) computeCacheKey(ctx context.Context, req *gitalypb.PackObjectsHookWithSidechannelRequest, stdinReader io.Reader) (string, io.ReadCloser, error) {
	cacheHash := sha256.New()

	repository := req.GetRepository()
	if tx := storage.ExtractTransaction(ctx); tx != nil {
		// The cache uses the requests as the keys. As the request's repository in the RPC handler has been rewritten
		// to point to the transaction's repository, the handler sees each request as different even if they point to
		// the same repository. Restore the original request to ensure identical requests get the same key.
		repository = tx.OriginalRepository(req.GetRepository())
	}

	cacheKeyPrefix, err := protojson.Marshal(&gitalypb.PackObjectsHookWithSidechannelRequest{
		Repository:  repository,
		Args:        req.GetArgs(),
		GitProtocol: req.GetGitProtocol(),
	})
	if err != nil {
		return "", nil, err
	}
	if _, err := cacheHash.Write(cacheKeyPrefix); err != nil {
		return "", nil, err
	}
	stdin, err := bufferStdin(stdinReader, cacheHash)
	if err != nil {
		return "", nil, err
	}
	cacheKey := hex.EncodeToString(cacheHash.Sum(nil))
	return cacheKey, stdin, nil
}

func bufferStdin(r io.Reader, h hash.Hash) (_ io.ReadCloser, err error) {
	f, err := os.CreateTemp("", "PackObjectsHook-stdin")
	if err != nil {
		return nil, err
	}
	defer func() {
		if err != nil {
			f.Close()
		}
	}()

	if err := os.Remove(f.Name()); err != nil {
		return nil, err
	}

	_, err = io.Copy(f, io.TeeReader(r, h))
	if err != nil {
		return nil, err
	}

	if _, err := f.Seek(0, io.SeekStart); err != nil {
		return nil, err
	}

	return f, nil
}
