### Title
`RepositorySize` undercounts on-disk usage for object-pool members, enabling storage-quota bypass - (File: internal/gitaly/service/repository/size.go)

### Summary
`RepositorySize` is documented as returning "the complete on-disk repository size" and is the primary size-reporting RPC used to enforce storage limits on a repository [1](#0-0) . However, its implementation only walks the member repository's own directory and never adds in the size of objects that live in a linked object pool, even though a large share of a fork's actual object data can be deduplicated into that pool [2](#0-1) .

### Finding Description
`RepositorySize` computes `dirSizeInBytes(path, filter)` using only the repository's own path, with no awareness of `objects/info/alternates` or of any linked object pool [2](#0-1) . `dirSizeInBytes` walks strictly the directory tree rooted at that single repository path [3](#0-2) .

This is a genuine internal inconsistency, not merely an external assumption: the newer `RepositoryInfo` RPC deliberately checks whether the repository is linked to an object pool and explicitly adds the pool's size into the reported total, precisely because "the response reflects the complete stats" [4](#0-3) . `RepositorySize` has no equivalent logic. Gitaly's own test suite demonstrates the effect: repacking a repository that is linked to an object pool causes deduplicated objects to move into the pool, after which `RepositorySize` reports the member repository as having shrunk to essentially zero, even though the objects still exist on disk (in the pool) [5](#0-4) .

Because object pools are created by GitLab specifically to deduplicate objects shared between a repository and its forks/pool members , and pool linkage/growth is driven entirely by ordinary user actions (creating a fork, pushing to a repo that gets linked to a pool, `FetchIntoObjectPool` housekeeping), an ordinary user can cause substantial amounts of object data to be attributed to the pool rather than to the member repository whose size is being measured and enforced.

### Impact Explanation
`RepositorySize` is the RPC used by callers (e.g. GitLab's repository storage-size enforcement) to decide whether a repository has exceeded its configured storage quota. Because the RPC silently omits the pool's contribution, a repository that is a member of an object pool can host or reference arbitrarily large amounts of actual on-disk data while `RepositorySize` continues to report a small or shrinking size (as shown by `TestRepositorySize_poolMember` reporting a drop from ~19 KiB to 1 KiB after linking to a pool and repacking) [6](#0-5) . This allows storage-quota checks built on top of this RPC to be bypassed, leading to unbounded, uncounted disk consumption — a resource-exhaustion/DoS condition against the storage node that is not caught by the intended limiting mechanism.

### Likelihood Explanation
Object pools are a normal, user-triggered feature (forking, `LinkRepositoryToObjectPool`, `FetchIntoObjectPool`, and repacking/housekeeping) , so any user capable of forking a repository or triggering housekeeping can produce this discrepancy without any special privilege. The gap is deterministic (not a race or a timing issue) and is already reproduced by Gitaly's own regression test, confirming the behavior is consistent and reliably triggerable [5](#0-4) .

### Recommendation
Mirror the approach already used by `RepositoryInfo`: when computing `RepositorySize`, detect whether the repository has an alternates link to an object pool via `stats.AlternatesInfoForRepository`/`RepositoryInfoForRepository`, and if so, add the pool's on-disk size to the reported total, exactly as `repository_info.go`'s `mergePoolInfo`/pool-size addition already does [4](#0-3) . Alternatively, have downstream quota-enforcement logic switch to `RepositoryInfo`'s size field instead of `RepositorySize` for enforcement purposes.

### Proof of Concept
1. Create a repository and write a large, packable blob so it can be deduplicated (as in `TestRepositorySize_poolMember`) [7](#0-6) .
2. Call `RepositorySize`; note the reported size reflects the full blob (e.g., ~19 KiB).
3. Create an object pool from the repository and link the repository to it (`LinkRepositoryToObjectPool`), then run `OptimizeRepository` to repack/deduplicate [8](#0-7) .
4. Call `RepositorySize` again: the reported size drops to ~1 KiB even though the large blob still physically exists on disk inside the pool repository [9](#0-8) .
5. Any quota/limit logic relying on `RepositorySize` will therefore undercount the repository's true storage footprint, allowing continued growth in the (uncounted) pool.

func (s *server) RepositorySize(ctx context.Context, in *gitalypb.RepositorySizeRequest) (*gitalypb.RepositorySizeResponse, error) {
	repository := in.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}
	repo := s.localRepoFactory.Build(repository)

	path, err := repo.Path(ctx)
	if err != nil {
		return nil, err
	}

	filter := snapshot.NewDefaultFilter(ctx)
	sizeInBytes, err := dirSizeInBytes(path, filter)
	if err != nil {
		return nil, fmt.Errorf("calculating directory size: %w", err)
	}

	return &gitalypb.RepositorySizeResponse{Size: sizeInBytes / 1024}, nil
}

func dirSizeInBytes(dirPath string, filter snapshot.Filter) (int64, error) {
	var totalSize int64

	if err := filepath.WalkDir(dirPath, func(path string, d fs.DirEntry, err error) error {
		if err != nil {
			// It can happen that we try to walk a directory like the object shards or
			// an empty reference directory that gets deleted concurrently. This is fine
			// and expected to happen, so let's ignore any such errors.
			if errors.Is(err, os.ErrNotExist) {
				return nil
			}

			return err
		}

		if d.IsDir() {
			return nil
		}

		relPath, err := filepath.Rel(dirPath, path)
		if err != nil {
			return fmt.Errorf("calculating path relative to repo root: %w", err)
		}

		if !filter.Matches(relPath) {
			return nil
		}

		fi, err := d.Info()
		if err != nil {
			// The file may have been concurrently removed.
			if errors.Is(err, os.ErrNotExist) {
				return nil
			}

			return fmt.Errorf("retrieving file info: %w", err)
		}

		totalSize += fi.Size()

		return nil
	}); err != nil {
		return 0, fmt.Errorf("walking directory: %w", err)
	}

	return totalSize, nil
}

func TestRepositorySize_poolMember(t *testing.T) {
	t.Parallel()

	ctx := testhelper.Context(t)

	cfg, client := setupRepositoryService(t)

	repo, repoPath := gittest.CreateRepository(t, ctx, cfg)

	// Write a large, reachable blob that would get pulled into the object pool. Note that the data must be part of
	// a packfile or otherwise it won't get pulled into the object pool. We thus repack the repository first before
	// linking it to the pool repository.
	gittest.WriteCommit(t, cfg, repoPath, gittest.WithBranch(git.DefaultBranch), gittest.WithTreeEntries(
		gittest.TreeEntry{Mode: "100644", Path: "16kbblob", Content: string(incompressibleData(16 * 1000))},
	))

	_, err := client.OptimizeRepository(ctx, &gitalypb.OptimizeRepositoryRequest{
		Repository: repo,
		Strategy:   gitalypb.OptimizeRepositoryRequest_STRATEGY_HEURISTICAL,
	})
	require.NoError(t, err)

	expectedSize := 19
	if testhelper.IsReftableEnabled() || gittest.ObjectHashIsSHA256() {
		expectedSize = 20
	}

	requireRepositorySize(t, ctx, client, repo, int64(expectedSize))

	// We create an object pool now and link the repository to it. When repacking, this should cause us to
	// deduplicate all objects and thus reduce the size of the repository.
	gittest.CreateObjectPool(t, ctx, cfg, repo, gittest.CreateObjectPoolConfig{
		LinkRepositoryToObjectPool: true,
	})

	_, err = client.OptimizeRepository(ctx, &gitalypb.OptimizeRepositoryRequest{
		Repository: repo,
		Strategy:   gitalypb.OptimizeRepositoryRequest_STRATEGY_HEURISTICAL,
	})
	require.NoError(t, err)

	requireRepositorySize(t, ctx, client, repo, 1)
}
