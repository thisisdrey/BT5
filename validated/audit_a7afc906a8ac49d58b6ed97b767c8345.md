### Title
DNS TXT certificate-query authorization is based solely on spoofable UDP source address - (File: dns_server.go)

### Summary
The Nebula lighthouse DNS responder gates certificate-disclosure queries (`TXT`, which return a full peer or self certificate) on a check of the *packet's claimed source address* rather than any cryptographically-verified identity. This is structurally the same class of bug as the Surge `transferFrom` finding: an authorization decision is made using an untrusted identity comparison (`msg.sender`/`from` in the ERC20 case, UDP source address here) instead of a properly authenticated one, and the check's scope/trust boundary does not match the guarantees the transport actually provides.

### Finding Description
`dnsServer.parseQuery` only answers `dns.TypeTXT` queries (which return the full marshalled certificate JSON via `QueryCert`) after checking `d.isSelfNebulaOrLocalhost(w.RemoteAddr().String())`: [1](#0-0) 

`isSelfNebulaOrLocalhost` derives trust purely from the connection's reported remote address — either loopback or membership in `myVpnAddrsTable` — with no cryptographic binding to that address: [2](#0-1) 

`QueryCert` then returns the raw certificate for the requested VPN IP, pulled either from local cert state or from the hostmap that only contains handshake-authenticated peers: [3](#0-2) 

The DNS server is started via `github.com/miekg/dns`, and `getDnsServerAddr` derives a UDP/TCP listen address straight from `lighthouse.dns.host`/`lighthouse.dns.port` config: [4](#0-3) 

For plain UDP DNS, the "remote address" the Go `net.PacketConn`/`dns.ResponseWriter` reports is simply the source IP/port taken from the received UDP packet header — it is **not cryptographically authenticated in any way**. Unlike Nebula's overlay traffic (which is protected by Noise handshakes, AEAD, and the encrypted tunnel), a raw UDP packet delivered to the DNS listener's underlay socket can have an arbitrary spoofed source IP, exactly like any other unauthenticated UDP datagram. This means `isSelfNebulaOrLocalhost` is checking an attacker-controlled field and treating it as a trust anchor, in the same way the Surge `transferFrom` bug misapplied an identity comparison (`spender == from`) as an authorization gate without confirming the comparison actually reflects a trustworthy identity.

### Impact Explanation
If `lighthouse.dns.host` is bound to a non-loopback / reachable underlay address (a legitimate and documented lighthouse DNS use case — the DNS "smart nameserver" feature is meant to be queried by other Nebula nodes over the underlay network), an off-path attacker on the same underlay segment/route (e.g., anyone able to send UDP packets toward the lighthouse's DNS port, including from within the same LAN/cloud network where source-IP spoofing is often possible) can forge a UDP packet whose source address matches one of the lighthouse's own VPN addresses or `127.0.0.1`. This bypasses `isSelfNebulaOrLocalhost` and lets the attacker retrieve TXT-encoded certificates (via `QueryCert`) for arbitrary VPN addresses known to the lighthouse's hostmap — a remote-state disclosure of certificate/identity material (names, groups, networks, fingerprints, issuer) for hosts in the mesh, without ever holding a valid CA-signed certificate or completing a Noise handshake.

### Likelihood Explanation
Likelihood depends on network position: UDP source-address spoofing toward the lighthouse's DNS listener is feasible on networks that do not enforce BCP38/ingress filtering (common on many cloud/VPS underlay networks), and the DNS listener address is attacker-reachable by design (it must be reachable by other Nebula nodes over the underlay to serve its purpose). No valid Nebula certificate or handshake is required — only the ability to reach the configured `lighthouse.dns.host:port` and forge a UDP source address, which satisfies the "no CA-signed certificate" reachability constraint.

### Recommendation
Do not use the transport-reported source address as an authorization signal for TXT/certificate disclosure. Either:
- Require TCP-only for TXT queries and only trust `w.RemoteAddr()` when the underlying transport is connection-oriented (TCP), since UDP source addresses are not authenticated; or
- Require that TXT certificate queries only be served over the loopback interface (as `am_lighthouse`/dns feature intends to be a local resolver) and disable them entirely for the UDP overlay listener, since the value of certificate JSON is sensitive metadata; or
- Bind the DNS "smart" TXT responder to loopback only, and document that any underlay-exposed nameserver socket must not be treated as identity-authenticated.

### Proof of Concept
Not independently executable from the index alone (no packet-capture/network test harness was inspected for this path), but the exploit path is derivable directly from the code:
1. Configure a lighthouse with `lighthouse.serve_dns: true`, `lighthouse.am_lighthouse: true`, and `lighthouse.dns.host` bound to a reachable underlay address (not `127.0.0.1`), per `getDnsServerAddr`. [4](#0-3) 
2. From a network position capable of spoofing UDP source addresses toward that host:port, craft a raw UDP DNS packet whose IP source is set to one of the lighthouse's own VPN addresses (or `127.0.0.1`) and whose DNS question asks for a `TXT` record of a target Nebula hostname.
3. `parseQuery` calls `isSelfNebulaOrLocalhost(w.RemoteAddr().String())`, which parses the spoofed source and finds it in `myVpnAddrsTable`, returning `true`. [2](#0-1) [1](#0-0) 
4. `QueryCert` is invoked and returns the marshalled certificate for the target hostname/IP, which is written back into the DNS TXT answer and sent to the (spoofed, attacker-controlled) source address if the attacker can also intercept/receive replies, or purely used as an oracle if reply visibility isn't required for the disclosure goal (e.g., combined with off-path techniques). [3](#0-2)

func (d *dnsServer) QueryCert(data string) string {
	if len(data) < 2 {
		return ""
	}
	ip, err := netip.ParseAddr(data[:len(data)-1])
	if err != nil {
		return ""
	}

	// The hostmap only ever contains peers we have handshaked with, so it never carries an entry for ourselves.
	// Answer self lookups straight from the local cert state.
	if cs := d.certState(); cs != nil && cs.myVpnAddrsTable != nil && cs.myVpnAddrsTable.Contains(ip) {
		c := cs.GetDefaultCertificate()
		if c == nil {
			return ""
		}
		b, err := c.MarshalJSON()
		if err != nil {
			return ""
		}
		return string(b)
	}

	hostinfo := d.hostMap.QueryVpnAddr(ip)
	if hostinfo == nil {
		return ""
	}

	q := hostinfo.GetCert()
	if q == nil {
		return ""
	}

	b, err := q.Certificate.MarshalJSON()
	if err != nil {
		return ""
	}
	return string(b)
}

func (d *dnsServer) isSelfNebulaOrLocalhost(addr string) bool {
	a, _, _ := net.SplitHostPort(addr)
	b, err := netip.ParseAddr(a)
	if err != nil {
		return false
	}

	if b.IsLoopback() {
		return true
	}

	cs := d.certState()
	if cs == nil || cs.myVpnAddrsTable == nil {
		return false
	}
	//if we found it in this table, it's good
	return cs.myVpnAddrsTable.Contains(b)
}

func getDnsServerAddr(c *config.C) string {
	dnsHost := strings.TrimSpace(c.GetString("lighthouse.dns.host", ""))
	// Old guidance was to provide the literal `[::]` in `lighthouse.dns.host` but that won't resolve.
	if dnsHost == "[::]" {
		dnsHost = "::"
	}
	return net.JoinHostPort(dnsHost, strconv.Itoa(c.GetInt("lighthouse.dns.port", 53)))
}
