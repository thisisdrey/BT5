### Title
DoS of repository-wide write serialization lock via unbounded quorum wait in Praefect's `reference-transaction` voting - ([File: internal/praefect/transactions/manager.go])

### Summary
Praefect serializes writes to a repository using a PostgreSQL-backed, repository-scoped lock (`RepoReferenceWriteLockManager`) that is acquired at the `PREPARING_PHASE` of the `reference-transaction` hook vote and only released on vote failure or at `COMMITTED_PHASE`. Because the lock is held while the RPC handler blocks waiting for quorum from all configured voters, an unprivileged pusher whose push transaction never reaches quorum (e.g. due to a stalled/partial push against one of several replicas) can keep the whole-repository write lock held for as long as their gRPC context remains open, blocking every other legitimate write to that repository, analogous to how the Sherlock report's attacker held a shared liquidity/utilization state to make a legitimate operation (liquidation) permanently revert.

### Finding Description
The Sherlock finding's essential root cause is: a shared, per-resource gate (protocol liquidity) that is normally expected to allow a critical operation (liquidation) can be manipulated/starved by an unprivileged actor, causing the operation to fail indefinitely and cheaply for the attacker.

The gitaly/Praefect analog is the repository write-serialization lock introduced for atomic multi-node writes: [1](#0-0) 
This lock is acquired when a Gitaly node casts a `Preparing` vote for a push's reference-transaction hook, *before* any on-disk ref lock is taken, and is only released on failure or at commit: [2](#0-1) 

The `Lock()` call blocks until the per-repository row is acquired, and once acquired the handler proceeds to wait for vote quorum from all configured voters before advancing phases or unlocking: [3](#0-2) 

The test suite explicitly demonstrates that a transaction which registers with a vote threshold higher than the votes actually cast will block indefinitely inside quorum collection *while holding the repository lock*, and the lock is only released when the calling gRPC context is cancelled: [4](#0-3) 

Because the lock is keyed per `virtualStorage|relativePath` (i.e., the whole repository, not per-ref or per-branch), any push (from any user with write access to that repository) that reaches the `Preparing` phase but is deliberately slow-rolled or partially delivered (so quorum among the repository's Gitaly replicas cannot be reached) will hold this single global write lock for the entire repository. All other legitimate writers to the same shared repository (a common scenario for public/forked/team repositories) are blocked from writing until the stalling client's context is torn down.

### Impact Explanation
This directly parallels the "DoS on liquidation when utilization is high" bug class: a state that is meant to gate one operation can be driven into a stuck condition by an ordinary, unprivileged actor and used to indefinitely block a *different, legitimate* operation on a shared resource (here, the whole repository's write path) at very low cost (just keeping one push connection open/slow). Every subsequent push/write RPC to the same repository queues on `WriteLockManager.Lock` and will not proceed until: (a) the stalling client's context is cancelled, (b) the lock's 20-second TTL expires and gets stolen, or (c) `StopTransaction`/`cancelTransaction` fires. If the attacker keeps re-issuing similar stalling pushes, they can indefinitely deny writes to the repository for other users — a genuine availability impact on a core Gitaly/Praefect write path, reachable purely through the normal push flow.

### Likelihood Explanation
The lock renewal TTL (20s, hard-coded) provides a partial mitigation: if the stalling client never renews (renew only happens at `PREPARED_PHASE`), the row will eventually expire and be "stolen" by a waiting transaction. This limits worst-case single-hold duration to roughly the time the client can keep the initial `Preparing` RPC call open without ever completing prepared/committed phase, plus repeated re-triggering. Exploitation requires the attacker to have write access to the target repository (which they may have on shared/forked repos) and to control at least one participating Gitaly replica's timing (e.g., through slow network I/O or repeated small pushes), which is a moderate but plausible bar — comparable to the escrowed "medium severity, DoS of time-sensitive function" categorization the report's judges eventually settled on. This is not a definite, unconditional loss of funds analog, but a reachable, low-cost handler DoS.

### Recommendation
- Bound the time a `PREPARING_PHASE` vote can hold the repository-wide write lock independent of the client's gRPC context (e.g., an internal timeout shorter than, or in addition to, client-context cancellation) so a stalled/slow-rolled push cannot occupy the lock beyond a fixed ceiling.
- Ensure the lock TTL/renew semantics are enforced from the *first* acquisition (not only from `PREPARED_PHASE` onward), so that a transaction stuck in quorum collection at `PREPARING_PHASE` is also subject to expiry and can be stolen by another waiter promptly.
- Consider making the write lock more fine-grained (e.g., per set of conflicting refs, similar to how Git's own ref-locking works) rather than whole-repository, to reduce blast radius for stalled transactions.
- Add metrics/alerting on long-held `repository_reference_write_locks` rows (the `lockHoldDuration` metric mentioned in `RepoReferenceWriteLockManager` already exists — it should be used to detect and proactively cancel abusive/stalled holders).

### Proof of Concept
Not independently reproduced against a live cluster; the described behavior is directly evidenced by the existing test `TestPraefectWriteSerialization_ContextCancellationReleasesLock`, which shows a transaction with `threshold=3` casting only 1 vote at `PREPARING_PHASE`, blocking in quorum collection while holding the DB-backed repository lock, and remaining locked until the gRPC context is explicitly cancelled: [5](#0-4) 
An attacker with push access could reproduce this in practice by initiating a push whose reference-transaction hook casts a `Preparing` vote on one replica while stalling delivery to the other replicas long enough to prevent quorum, then holding the connection open as long as possible (re-issuing before/at the 20s TTL boundary) to keep the repository-wide write lock continuously occupied. Full exploit development and multi-node timing verification would require a live Praefect + multi-Gitaly-node test cluster, which was not available for direct execution here.

// Lock acquires the write lock for a given virtualStorage, relativePath and txnID,
// blocking until the lock is acquired or ctx is cancelled.
func (r *RepoReferenceWriteLockManager) Lock(ctx context.Context, virtualStorage, relativePath string, txnID uint64,
) (RepoLock, error) {
	for {
		res := r.tryLock(ctx, virtualStorage, relativePath, txnID)
		if res.Err != nil {
			return RepoLock{}, res.Err
		}
		if res.Acquired {
			return RepoLock{Unlock: res.Unlock, Renew: res.Renew}, nil
		}

		select {
		case <-ctx.Done():
			res.Deregister()
			return RepoLock{}, fmt.Errorf("wait for lock: %w", ctx.Err())
		case <-res.NotificationCh:
			// wait for the lock to release
		}
	}
}

func (mgr *Manager) unlockRepoForTransaction(ctx context.Context, transactionID uint64, returnedErr error, phase gitalypb.VoteTransactionRequest_Phase) {
	if featureflag.PraefectSerializedWrite.IsDisabled(ctx) {
		return
	}

	// Decide whether this call releases the write lock. The lock spans all the
	// phases of one transaction and is only released when either the vote
	// failed (so callers can't advance to the next phase) or the committed
	// phase completes. Phases outside the reference transaction hook
	// lifecycle (e.g. SYNCHRONIZED_PHASE) never acquired a lock.
	var shouldUnlock bool
	switch phase {
	case gitalypb.VoteTransactionRequest_PREPARING_PHASE,
		gitalypb.VoteTransactionRequest_PREPARED_PHASE:
		shouldUnlock = returnedErr != nil
	case gitalypb.VoteTransactionRequest_COMMITTED_PHASE:
		shouldUnlock = true
	default:
		return
	}

	if !shouldUnlock {
		return
	}

	mgr.releaseRepoLockOnPhase(transactionID, phase.String())
}
