Audit Report

## Title
Nonce commit coupled to unrelated fallible downstream steps in `pallet-inbound-queue::submit` permanently halts a bridge channel - ([File: bridges/snowbridge/pallets/inbound-queue/src/lib.rs])

## Summary
`submit()` commits the strictly-sequential `Nonce<T>` bump before performing fallible fee-burn (`burn_fees`), XCM conversion (`do_convert`), and XCM send (`send_xcm`) steps, but because FRAME automatically wraps the entire dispatchable in `with_storage_layer`, any `Err` from those later steps rolls back the nonce bump along with everything else. Since the pallet requires the exact successor nonce and exposes no mechanism to skip or force-advance a stuck nonce, a single message whose embedded fee exceeds what the destination's sovereign account can pay (a value fully controlled by the Ethereum-side message sender) permanently and irrecoverably stalls the entire inbound channel.

## Finding Description
`submit()` verifies the light-client proof, decodes the envelope, looks up the channel, and then commits the nonce bump via `Nonce<T>::try_mutate` (lines 256–267), all before attempting `burn_fees` (line 298), `do_convert` (line 288), and `send_xcm` (line 301). [9](#0-8)  Because `#[pallet::call]` methods are compiled to run inside `frame_support::storage::with_storage_layer`, which rolls back all storage writes on `Err`, any failure in the downstream steps reverts the nonce bump too, leaving `Nonce<T>` at the pre-message value. [1](#0-0) 

`burn_fees` withdraws the message's embedded `fee` (denominated in the parent asset) from the destination parachain's sovereign account via `T::AssetTransactor::can_check_out`/`withdraw_asset`, and returns `TokenError::FundsUnavailable` if that account cannot cover the amount. [6](#0-5)  The `fee` value is a plain `u128` embedded in the `Command::SendToken`/`SendNativeToken`/`RegisterToken` payload originating from the Ethereum Gateway contract, decoded and passed through unmodified by `MessageToXcm::convert`. [3](#0-2)  There is no check in `submit` or `burn_fees` that the fee is bounded relative to the sovereign account's actual balance prior to committing the nonce.

Because `Nonce<T>` enforces exact sequential succession (`envelope.nonce != nonce.saturating_add(1)` → `InvalidNonce`), once nonce N fails to commit durably, nonce N+1 (and all higher nonces) can never be accepted. [8](#0-7)  The only other call in the pallet, `set_operating_mode`, can only halt/resume the pallet globally — it cannot skip, force-advance, or replace a stuck nonce for a channel. [7](#0-6) 

## Impact Explanation
This is a permanent bridge-state lock: once a message with an unpayable fee (or a message that fails in `do_convert`/`send_xcm` deterministically) becomes the next-expected nonce for a channel, no further Ethereum→Polkadot messages for that channel can ever be delivered. All queued asset transfers for that destination freeze indefinitely, and there is no operator-controlled repair function short of a runtime upgrade. This matches the "permanent user-fund or bridge-state lock" and "stalls bridge processing" impacts in the accepted impact gate.

## Likelihood Explanation
The triggering condition is directly reachable by an unprivileged actor: any Ethereum-side user constructing a `SendToken`/`SendNativeToken`/`RegisterToken` command with a `fee` value exceeding the destination's sovereign account balance produces a message that, once its nonce becomes the channel's next-expected nonce, fails deterministically in `burn_fees` every time it (or a later nonce) is retried. The relayer submitting the proof need not be malicious — it need only submit a valid, permissionless proof for an ordinary user's message. No governance, validator, or relayer compromise is required, and the failure is 100% reproducible for that specific fee/balance combination.

## Recommendation
Decouple nonce advancement from unrelated downstream fallibility: commit the nonce bump unconditionally once the message is verified as authentic and correctly sequenced, and treat `burn_fees`/`do_convert`/`send_xcm` failures as non-fatal to nonce progression (e.g., emit a failure event and skip dispatch of that message, analogous to `pallet-message-queue`'s permanent/unprocessable classification). Alternatively, split the nonce-commit into its own non-rolled-back storage layer (e.g., via an inner `with_storage_layer` boundary that commits before attempting the downstream operations) or add a root-only extrinsic to force-advance/skip a stuck nonce per channel.

## Proof of Concept
1. Configure a destination parachain's sovereign account on BridgeHub with a balance in the parent asset near zero.
2. Have a user on Ethereum call the Gateway contract to emit a `SendToken`/`SendNativeToken` message whose embedded `fee` field exceeds that sovereign account's spendable balance.
3. A relayer submits the resulting `EventProof` via `submit`; proof verification, envelope decode, channel lookup, and the `Nonce<T>::try_mutate` bump all succeed, then `Self::burn_fees(channel.para_id, fee)?` at line 298 returns `Err(TokenError::FundsUnavailable)`.
4. FRAME's `with_storage_layer` wrapper rolls back all storage changes for the extrinsic, including the nonce bump; `Nonce<T>` for the channel remains at its pre-message value.
5. Any resubmission of the same nonce fails identically as long as the sovereign account remains underfunded; any submission of the next nonce fails with `InvalidNonce` per the check at line 261, permanently stalling the channel.
