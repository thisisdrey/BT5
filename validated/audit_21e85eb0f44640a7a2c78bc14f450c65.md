### Title
Exchange inject/withdraw operations execute against pool state with no slippage/minimum-output protection, enabling sandwich attacks - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
TRON's on-chain Bancor-style Exchange feature lets any account create a liquidity pool (`ExchangeCreateContract`) and trade against it via `ExchangeTransactionContract`. Unlike `ExchangeTransactionContract`, which explicitly protects the trader with a caller-supplied `expected` minimum-output field checked in `ExchangeTransactionActuator`, the `ExchangeInjectContract` and `ExchangeWithdrawContract` paths compute the counter-asset amount purely from the pool's live balances at validate/execute time, with no caller-supplied bound on acceptable output. This mirrors exactly the root cause described in the Derby report: slippage/min-out is derived from already-mutated pool state rather than fixed by the transaction's own calldata.

### Finding Description
In `ExchangeInjectActuator.doValidate()`/`execute()`, `anotherTokenQuant` is derived solely from `firstTokenBalance`/`secondTokenBalance` read at the moment of processing: [1](#0-0) 
There is no equivalent of the `expected`/minimum-output check that `ExchangeTransactionActuator` enforces: [2](#0-1) 

Similarly, `ExchangeWithdrawActuator` computes the proportional counter-asset payout strictly from current pool ratios with no caller-supplied bound: [3](#0-2) 

Because any unprivileged account can submit `ExchangeTransactionContract` trades against the same exchange (`ExchangeTransactionActuator.execute`, reachable via `Commons.getExchangeStoreFinal(...).get(exchangeId)` and `exchangeCapsule.transaction(...)`): [4](#0-3) 
an attacker can skew the exchange's `firstTokenBalance`/`secondTokenBalance` ratio immediately before a pending inject/withdraw transaction lands, and revert the skew immediately after, extracting value from the counterparty exactly as described for the Swap library's `amountOutMinimum` calculated from already-modified pool state.

### Impact Explanation
An exchange creator's inject/withdraw calls have no protection against pool-ratio manipulation, so an attacker can sandwich these calls: pump one side of the pool with a trade, force the victim's inject/withdraw to settle at the skewed ratio, then reverse the trade to lock in a profit taken from the victim's assets. This is a direct, unbacked value transfer/theft of funds for the exchange creator, matching the "concrete unauthorized... theft... of funds" bar.

### Likelihood Explanation
Exchange creation, trading (`ExchangeTransactionContract`), injecting, and withdrawing are all reachable by ordinary signed transactions from any account; no SR/witness/committee privilege is required to execute the sandwich, only ordinary transaction broadcasting and normal block-inclusion ordering around the victim's transaction.

### Recommendation
Add a caller-supplied bound (minimum/maximum acceptable counter-asset amount, analogous to `expected` in `ExchangeTransactionContract`) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` at both validate and execute time so pool-state manipulation between broadcast and inclusion cannot silently change the outcome beyond the caller's tolerance.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction from the exchange creator targeting exchange `X` with tokens A/B.
2. Attacker submits an `ExchangeTransactionContract` trade against exchange `X` to skew `firstTokenBalance`/`secondTokenBalance` (e.g., dump A to inflate B's relative price), processed by `ExchangeTransactionActuator.execute` (lines 61-91 above).
3. The creator's inject/withdraw transaction executes against this skewed ratio in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` (no min/max check exists), causing the creator to inject more value than intended or withdraw a less valuable asset mix than expected.
4. Attacker submits a reverse `ExchangeTransactionContract` trade restoring the ratio, realizing arbitrage profit extracted from the creator's inject/withdraw.
