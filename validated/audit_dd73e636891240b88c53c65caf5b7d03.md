### Title
Nakamoto block-replay endpoint serves non-canonical staged block state as if canonical - (File: stackslib/src/net/api/blockreplay.rs)

### Summary
`RPCNakamotoBlockReplayRequestHandler` accepts any `block_id` and passes it straight into `remine_nakamoto_block`, which resolves tenure/parent solely via the staging-blocks DB lookups `get_tenure_and_parent_block_id` and `get_nakamoto_block_rowid`, with no check that the block is on the canonical Nakamoto fork. An authorized caller (holder of the replay secret) can request replay of any staged-but-orphaned/non-canonical block and receive full transaction receipts, execution costs, events, and a `valid_merkle_root` flag presented with the same shape as a canonical-block replay, with no indicator of non-canonicity.

### Finding Description
The broken equality is: *the JSON served by `/v3/blocks/replay/:block_id` should reflect the canonical chain state (`chainstate.nakamoto_blocks_db()`'s canonical fork), or explicitly say it does not*. Instead:

- `try_parse_request` (blockreplay.rs:590-600) only validates that `block_id` is 64 hex chars and decodes it into a `StacksBlockId` — no canonicity check exists at parse time.
- `remine_nakamoto_block` (blockreplay.rs:192-197) calls `chainstate.nakamoto_blocks_db().get_tenure_and_parent_block_id(block_id)`, which is a staging-DB lookup keyed purely by `block_id`; it returns tenure/parent info for *any* stored (staged) block regardless of whether that block ever became canonical.
- The subsequent `get_nakamoto_block_rowid` (blockreplay.rs:201-204) and `open_nakamoto_block` calls likewise fetch by `block_id` from the staging blocks store with no canonical-fork filter.
- The block is deserialized, fully re-mined against its (possibly non-canonical) parent header, transactions are executed, receipts are generated, and `valid_merkle_root` is computed and returned to the caller (blockreplay.rs:339-401) — all framed identically to a canonical replay response, with no `is_canonical` field in `RPCReplayedBlock` (blockreplay.rs:493-521).

Thus a block that lost a fork race (staged, deserializable, but never confirmed canonical) is replayed and served with full receipts/merkle validity exactly as though it were the canonical block at that height, silently breaking the assumption that replay output corresponds to state actually committed to the canonical tip.

### Impact Explanation
An authenticated user of this endpoint (someone who holds the dedicated replay secret, which per the endpoint's own design is meant only to gate CPU-expensive replay, not chain-state selection) can retrieve full transaction receipts, VM errors, events, and "merkle root validity" for orphaned/non-canonical Nakamoto blocks presented identically to canonical results. This matches the specified High-severity category "serving non-canonical state as canonical," since a consumer of this API (e.g., tooling, dashboards, automated auditors) has no way to distinguish a canonical replay from a stale-fork replay from the response shape alone. This is repeatable for any block_id present in the staging DB, and does not require privileged/admin access beyond the endpoint's own designated secret.

### Likelihood Explanation
Preconditions: the node must have the block-replay endpoint enabled (`self.auth` configured) and the caller must know the replay secret — which per the question's threat model is treated as a low-privilege "compute gate," not an arbitrary-state-selection privilege. The attacker additionally needs a `block_id` of a staged-but-non-canonical block, which is learnable via normal gossip/inventory (any block a node has staged, even if it lost a fork race, is known via P2P/`consensus_hash`+parent linkage). No local access, no admin role, and no bypass of the secret is required — only the documented replay credential and knowledge of a non-canonical `block_id`. This is straightforward and repeatable per-request.

### Recommendation
Before proceeding with replay, verify the requested `block_id` is on the canonical Nakamoto fork (e.g., cross-check against `NakamotoChainState`'s canonical tip / `StacksChainState::get_stacks_chain_tip`, or confirm the block's tenure and height match the canonical header at that height) and reject with a distinct error (or set an explicit `is_canonical: false` field) if it is not, rather than silently serving replay output in the same shape as canonical replay.

### Proof of Concept
1. In `stackslib::net::api::blockreplay` tests, construct a `NakamotoChainState`/`StacksChainState` test harness with two competing Nakamoto blocks at the same tenure height (fork A confirmed canonical, fork B staged but orphaned), following patterns used in `chainstate::nakamoto` fork tests.
2. Stage fork B's block into the nakamoto staging blocks DB (so `get_nakamoto_block_rowid` and `get_tenure_and_parent_block_id` succeed for it) without making it canonical.
3. Construct `RPCNakamotoBlockReplayRequestHandler` with a configured `auth` secret, issue a request to `/v3/blocks/replay/:block_id` using fork B's `block_id` with a correct `Authorization` header.
4. Assert: currently, `try_handle_request` returns `200 OK` with a fully populated `RPCReplayedBlock` (including `valid_merkle_root` and `transactions`) for the non-canonical block — this is the bug. Expected/fixed behavior: request should be rejected (e.g., 404/409) or the response must explicitly mark the block as non-canonical.
