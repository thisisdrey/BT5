## Title
CREATE2 contract deployment can be front-run and permanently griefed via deterministic address collision - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
Java-tron's TVM `CREATE2` opcode computes the new contract address deterministically from public inputs (`salt`, sender/factory address, and the hash of the init code), exactly the pattern flagged in the Aloe `Factory.createMarket` report. Because the resulting address is fully predictable before the transaction is mined, an attacker who observes a pending `CREATE2` deployment in the mempool can compute the same target address and race to occupy it first, causing the legitimate deployer's transaction to permanently fail for that specific `(sender, salt, initcode)` combination.

### Finding Description
`CREATE2` is dispatched from the TVM opcode table to `create2Action`, which pops `value, inOffset, inSize, salt` and calls `program.createContract2(...)`: [1](#0-0) 

The deterministic address is computed as `keccak256(prefix ++ sender ++ salt ++ keccak256(initcode))`, implemented in `WalletUtil.generateContractAddress2` and documented at the Solidity level in the test fixtures: [2](#0-1) [3](#0-2) 

This address is entirely a function of public data: the calling (factory) contract's address, the caller-supplied `salt`, and the init bytecode hash — nothing ties it to a specific transaction nonce or unpredictable value. Once `createContractImpl` computes `newAddress`, it checks whether an account/contract already occupies that address: [4](#0-3) 

If `contractAlreadyExists` is true, the create is rejected with a `BytecodeExecutionException`, reverting the create call (and typically the whole triggering transaction): [5](#0-4) 

Any unprivileged account can call `TriggerSmartContract` against a factory contract that performs `CREATE2` with attacker-visible `salt`/`initcode` parameters (this is the standard, publicly reachable `TriggerContract` API path used throughout the TVM test suite, e.g. `Create2Test.testCreate2`): [6](#0-5) 

Because the salt and factory address are visible in the pending transaction's calldata (mempool), a watcher can submit their own transaction calling the same factory function with the same `salt`/`initcode`, get it mined first (e.g., by paying more energy/bandwidth or by broadcasting sooner), and cause the resulting `newAddress` to already exist by the time the victim's transaction executes — permanently blocking that victim from ever deploying to that specific deterministic address for that salt, mirroring the reported `Factory.createMarket` frontrunning DoS in Aloe.

### Impact Explanation
Any factory-pattern contract on java-tron relying on `CREATE2` with a caller-controlled or otherwise front-runnable `salt` can have its deployment griefed: the intended deployer's transaction reverts (wasting energy/bandwidth), and the specific deterministic address becomes permanently unusable for that exact `salt` value from that legitimate deployer/factory context, since `newAddress` collision is a hard failure with no retry-with-different-salt fallback built into the VM. This is a functional denial-of-service against deployment-dependent DeFi patterns (e.g., counterfactual wallet/market/pool factories) deployed on TVM, not merely a resource-only nuisance, because the specific target contract can never be created once occupied.

### Likelihood Explanation
Any account can trigger the vulnerable factory's `CREATE2`-based function via a standard `TriggerSmartContract`, and `salt`/init-code parameters are visible in the mempool before confirmation, making front-running straightforward with commodity mempool-watching bots — the same low-cost condition used in the original report.

### Recommendation
This is a pattern-level risk inherent to `CREATE2` and not a java-tron core bug per se; mitigation is at the smart-contract-author level: factory contracts deployed on TVM should bind `msg.sender` (or another value unpredictable/uncontrollable by a front-runner) into the `salt`, or gate deployment behind access control, so that a third party cannot reproduce and pre-occupy the deterministic target address.

### Proof of Concept
1. A factory contract on TVM exposes `deploy(bytes code, uint256 salt)` which internally executes the `CREATE2` opcode (as in `Create2Test.testCreate2`): [6](#0-5) 
2. Alice broadcasts `TriggerSmartContract` calling `deploy(code, salt=100)`.
3. An attacker observes this in the mempool, extracts `code` and `salt`, and broadcasts an identical `deploy(code, salt=100)` call from a different account against the same factory, but with a higher energy fee/priority so it gets mined first.
4. The attacker's transaction executes `createContractImpl`, and `newAddress = generateContractAddress2(factoryAddress, salt, code)` is created and marked as an existing contract.
5. Alice's transaction now executes; `getContractState().getAccount(newAddress)` finds the account already exists as a contract, `contractAlreadyExists=true` is set, and her `CREATE2` call fails with `BytecodeExecutionException("Trying to create a contract with existing contract address...")`, reverting her transaction: [5](#0-4) 
6. Alice can never deploy to that specific address again with that `salt`, causing a permanent, repeatable griefing/DoS for factory-pattern contracts relying on `CREATE2`.

    // Predict CREATE2 address without deploying
    //
    // TRON CREATE2 formula (differs from standard EVM):
    //   address = keccak256(prefix ++ sender[20] ++ salt[32] ++ keccak256(code)[32])[12:]
    //
    // - Standard EVM uses 0xff as prefix (magic byte)
    // - TRON replaces it with the address prefix byte (0x41 for mainnet, 0xa0 for testnet)
    // - This value is hardcoded at compile time by tron-solc
    //
    function getCreate2Addr(uint256 salt) public view returns (address) {
        bytes memory bytecode = type(FreezeContract).creationCode;
        bytes32 hash = keccak256(
            abi.encodePacked(
                bytes1(0x41),       // TRON mainnet address prefix
                address(this),      // 20-byte factory address
                salt,               // 32-byte salt
                keccak256(bytecode) // 32-byte code hash
            )
        );
        return address(uint160(uint256(hash)));
    }
