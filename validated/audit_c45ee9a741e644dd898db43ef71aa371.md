### Title
Attacker can grief taker's market orders by fragmenting maker liquidity, causing legitimate `MarketSellAssetContract` transactions to revert - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchOrder` walks the maker order book at the best price and matches against it one order at a time, capping the number of individual maker orders it will traverse at `MAX_MATCH_NUM = 20` [1](#0-0) . If a taker's sell order needs to consume more than 20 distinct maker orders at the best price to be filled, `matchOrder` throws `ContractExeException("Too many matches...")` [2](#0-1) , which propagates out of `execute()` and aborts the whole transaction — exactly the "one bad element in a batch reverts everything" bug class described in the report, but reachable here through the exchange/market order matching path.

### Finding Description
`execute()` deducts the fee, transfers/locks the sell-side balance, creates and persists the taker's order, and then calls `matchOrder()` to walk the order book [3](#0-2) . Inside `matchOrder`, the code repeatedly pops the head order at the best price and calls `matchSingleOrder`, incrementing `matchOrderCount` for every maker order consumed; once this exceeds `MAX_MATCH_NUM` (20) it throws `ContractExeException`, unconditionally reverting the entire actuator execution [4](#0-3) .

Order placement (`MarketSellAssetContract`) has no minimum-quantity constraint and is cheap for an attacker — any unprivileged account can place many small maker orders at the best price for a given trading pair (up to `MAX_ACTIVE_ORDER_NUM = 100` per price level per the order book design). Because the taker in `MarketSellAssetActuator` has no control over which maker orders it matches against — matching is fully automatic and always starts from the best price — an attacker can deliberately fragment liquidity at the best price into more than 20 tiny orders. Any subsequent legitimate taker whose order size requires walking through more than 20 of these orders to be filled at that price will have their entire transaction fail with `ContractExeException`, even though the taker acted in good faith and had sufficient balance. The existing test `exceedMaxMatchNumLimit` in the actuator test suite demonstrates this exact revert condition is reachable by ordinary contract execution [5](#0-4) .

### Impact Explanation
This is a griefing/denial-of-service vector against the on-chain exchange: an attacker with a small amount of capital and multiple market-sell transactions can permanently deny larger takers from executing valid trades against the best available price for a token pair, forcing their transactions to fail (consuming their bandwidth/energy fee for nothing) or forcing them to match at a worse price after waiting for the attacker's orders to clear. This does not itself steal funds or crash the node, but it is a reachable, unprivileged, and repeatable disruption of the exchange/market order handling functionality that the audit scope explicitly includes.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to predict/target a trading pair and price level a victim intends to trade at, and to place and maintain more than `MAX_MATCH_NUM` (20) small orders at that price, which is inexpensive (bounded by `MAX_ACTIVE_ORDER_NUM = 100` per price bucket) and requires no special privileges — any account holding a small amount of the asset can do this via a normal `MarketSellAssetContract` broadcast.

### Recommendation
Instead of aborting the whole transaction when the match limit is exceeded, the actuator should stop matching gracefully at `MAX_MATCH_NUM` and leave the taker's remaining unmatched quantity in the order book (as is already done for partial fills), rather than throwing `ContractExeException` and reverting all state changes made in the transaction. This avoids letting an attacker's cheap order fragmentation force a hard revert of a victim's otherwise valid trade.

### Proof of Concept
1. Attacker repeatedly submits `MarketSellAssetContract` transactions creating 21+ small sell orders for pair (A→B) at the lowest available price (each order is independently valid and cheap).
2. Victim submits a `MarketSellAssetContract` for pair (B→A) with a quantity that would need to walk through all 21 attacker orders at that price to fill.
3. `matchOrder` increments `matchOrderCount` past `MAX_MATCH_NUM` (20) while iterating the attacker's fragmented orders and throws `ContractExeException("Too many matches. MAX_MATCH_NUM = 20")` [2](#0-1) , exactly as reproduced in `MarketSellAssetActuatorTest.exceedMaxMatchNumLimit` [6](#0-5) .
4. The victim's transaction fails entirely, and they cannot fill their order against the best price as long as the attacker maintains the fragmented order book.

  @Test
  public void exceedMaxMatchNumLimit() throws Exception {

    InitAsset();

    int start = 10;
    int limit = MarketSellAssetActuator.getMAX_MATCH_NUM();
    int step = 1;
    int end = start + step * limit;

    //(sell id_1  and buy id_2)
    String sellTokenId = TOKEN_ID_ONE;
    String buyTokenId = TOKEN_ID_TWO;
    long buyTokenQuant = 400L;
    long sellTokenQuant = buyTokenQuant * (end / start + 1);

    byte[] ownerAddress = ByteArray.fromHexString(OWNER_ADDRESS_FIRST);
    AccountCapsule accountCapsule = dbManager.getAccountStore().get(ownerAddress);
    accountCapsule.addAssetAmountV2(sellTokenId.getBytes(), sellTokenQuant,
        dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
    dbManager.getAccountStore().put(ownerAddress, accountCapsule);
    Assert.assertEquals(sellTokenQuant,
            (long) accountCapsule.getAssetV2MapForTest().get(sellTokenId));

    // Initialize the order book

    // at least limit+1 times
    for (int i = start; i <= end; i += step) {
      addOrder(buyTokenId, (long) start, sellTokenId, i, OWNER_ADDRESS_SECOND);
    }

    // this order(taker) need to match 21 times
    MarketSellAssetActuator actuator = new MarketSellAssetActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, sellTokenId, sellTokenQuant, buyTokenId, buyTokenQuant));

    String errorMessage =
        "Too many matches. MAX_MATCH_NUM = " + MarketSellAssetActuator.getMAX_MATCH_NUM();
    try {
      TransactionResultCapsule ret = new TransactionResultCapsule();
      actuator.validate();
      actuator.execute(ret);
      fail(errorMessage);
    } catch (ContractExeException e) {
      Assert.assertEquals(errorMessage, e.getMessage());
    } catch (Exception e) {
      Assert.assertTrue(false);
    }
  }
