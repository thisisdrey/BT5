### Title
Front-runnable `init_global_fee_state` allows a first-caller to permanently seize the global fee admin role and redirect protocol fees - ([File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs])

### Summary
The external report describes an EVM proxy pattern where an uninitialized logic contract's `initialize()` can be called by anyone before the real deployer does, letting an attacker seize privileged ownership and later destroy the contract via `delegatecall`+`selfdestruct`. marginfi-v2 is a Solana/Anchor program, so there is no `delegatecall`/`selfdestruct`/proxy-logic-contract concept, and that literal exploit path does not exist. However, the same root-cause bug class — a privileged, one-time "initialize" instruction that lacks any deployer/authority gating and is racing against the real deployment — is reachable through `init_global_fee_state`.

### Finding Description
`init_global_fee_state` creates the singleton `FeeState` PDA (seeded only by the constant `FEE_STATE_SEED`, with no dependency on the caller) and unconditionally sets the caller-supplied `admin_key` as `fee_state.global_fee_admin` and caller-supplied `fee_wallet` as `fee_state.global_fee_wallet`: [1](#0-0) 

The corresponding `Accounts` struct requires only an arbitrary `payer: Signer` — there is no admin/upgrade-authority check gating who may call this instruction: [2](#0-1) 

Because the PDA is derived solely from the fixed seed `FEE_STATE_SEED`, its address is known/derivable by anyone before the protocol deployer submits the initialization transaction. Since the account uses Anchor's `init` constraint (not `init_if_needed`), whoever's transaction lands first permanently claims the account; any subsequent legitimate initialization attempt by the real deployer fails because the account already exists. This mirrors the report's root cause: a privileged one-time initializer that is not called atomically/protectedly at deploy time, allowing an unprivileged attacker to claim the privileged role first.

Once an attacker controls `global_fee_admin`, they can call `edit_fee_state` (gated only by `has_one = global_fee_admin`) to further modify `global_fee_wallet`, fee rates, `pause_delegate_admin`, etc.: [3](#0-2) 

Critically, `global_fee_wallet` directly determines where every bank's collected program fees are sent across the entire protocol via `lending_pool_collect_bank_fees`, which validates the destination ATA against `fee_state.global_fee_wallet`: [4](#0-3) [5](#0-4) 

### Impact Explanation
If the deployment/init transaction for `init_global_fee_state` is front-run, the attacker permanently becomes `global_fee_admin` for the entire program (this is a global, program-wide singleton, not scoped to any group). This is an unauthorized, permanent state takeover of a privileged role. Concretely, the attacker can then set `global_fee_wallet` to an address they control, causing all subsequently collected program fees from every bank in every group to be transferred to the attacker via `lending_pool_collect_bank_fees` — a direct, protocol-wide unauthorized transfer of funds. The attacker can also raise fee parameters (`program_fee_rate`, `program_fee_fixed`, `liquidation_max_fee`, etc.) up to whatever bounds the type/validation allows, and control `pause_delegate_admin`. Because the PDA cannot be re-initialized once claimed, remediation would require a program upgrade rather than a normal admin transaction, making this a persistent compromise until patched.

### Likelihood Explanation
This requires the attacker to win a race against the deployer's own initialization transaction. It is unprivileged (any funded Solana account can submit the transaction) and requires no special access — the PDA and required instruction data are fully derivable from public information (program ID, IDL). Historically this exact "unprotected/racy program initializer" bug class is well known and has been exploited on Solana; likelihood depends entirely on operational discipline at deploy time (i.e., whether `init_global_fee_state` is called atomically/protectedly, e.g., in the same transaction as program deployment or via a deployer-restricted flow) — the on-chain code itself provides no protection against it.

### Recommendation
- Gate `InitFeeState` to a known/trusted authority (e.g., require the account to be signed by the program's upgrade authority, checked via the `BPFLoaderUpgradeable` program state, or hardcode/verify against an expected pubkey) instead of accepting an arbitrary signer.
- Alternatively/additionally, ensure the initialization instruction is always submitted atomically in the same transaction as program deployment/upgrade so no window exists for front-running.
- Add an explicit on-chain check comparing the caller against a known deployer key before allowing `FeeState` to be created, so a malicious first-caller cannot seize `global_fee_admin`.

### Proof of Concept
1. Deployer publishes/upgrades the marginfi program to program ID `P`, planning to call `init_global_fee_state` next to set up the legitimate admin/fee wallet.
2. Attacker Mallory derives the `FeeState` PDA using seeds `[FEE_STATE_SEED]` and program ID `P` (public information), matching the seeds in `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs:43-51`.
3. Mallory submits `init_global_fee_state(admin_key = Mallory, fee_wallet = Mallory_wallet, ...)` before the deployer's transaction lands (e.g., via higher priority fee/faster RPC). The instruction succeeds because `InitFeeState` only requires `payer: Signer`, with no deployer check (`programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs:37-55`).
4. The deployer's own `init_global_fee_state` call now fails (`FeeState` PDA already initialized).
5. Mallory is now `fee_state.global_fee_admin`. She can call `edit_fee_state` to set `global_fee_wallet` to her own token wallet (`programs/marginfi/src/instructions/marginfi_group/edit_global_fee.rs:10-38`).
6. Any future `lending_pool_collect_bank_fees` call across any bank in the protocol validates the `fee_ata` against Mallory's `global_fee_wallet` (`programs/marginfi/src/instructions/marginfi_group/collect_bank_fees.rs:26-38`) and transfers accrued program fees to her (`collect_bank_fees.rs:127-163`), diverting protocol-wide fee revenue to the attacker indefinitely.

// Runs once per program to init the global fee state.
use anchor_lang::prelude::*;
use marginfi_type_crate::{
    constants::FEE_STATE_SEED,
    types::{FeeState, WrappedI80F48},
};

#[allow(unused_variables)]
pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}
