## Analog Found: Unsynchronized shared `JumpTable` mutated concurrently by unauthenticated `triggerConstantContract`/`estimateEnergy` requests

### Title
Race condition on the shared, unsynchronized `OperationRegistry` `JumpTable` reachable via `triggerConstantContract`/`estimateEnergy` — (File: `actuator/src/main/java/org/tron/core/vm/OperationRegistry.java`)

### Summary
The Rust advisory describes `LockWeak<T>` unconditionally implementing `Send` with no bound requiring `T: Sync`, letting multiple threads concurrently touch a non-thread-safe value with no synchronization. The closest analog in java-tron is `OperationRegistry`, which holds process-wide, plain (non-volatile, non-synchronized) `JumpTable` singletons — `CONSTANT_CALL_TABLE` and the entry in `tableMap` — that get mutated in place on every single opcode-table lookup via `prepareAndGetTable()`, with zero locking, while being concurrently read by `VM.play()` on other threads.

### Finding Description
`JumpTable` stores opcodes in a plain array with no synchronization at all: [1](#0-0) 

`OperationRegistry` keeps one shared instance for all non-constant transactions (`tableMap.get(LATEST_VERSION)`) and one shared instance for all constant calls (`CONSTANT_CALL_TABLE`): [2](#0-1) 

Every VM execution calls `prepareAndGetTable`, which fetches the shared table and **mutates it in place** (`table.set(...)` on `ADJUSTED_MLOAD`/`DEFAULT_MLOAD`, vote-witness cost variant, self-destruct variant) based on current `VMConfig` flags, with no lock: [3](#0-2) 

`VMActuator.execute` calls this once per execution right before dispatching bytecode with `VM.play`, so the table can be mutated and read interleaved across threads without any happens-before relationship: [4](#0-3) 

Crucially, the constant-call path (`triggerConstantContract` / `estimateEnergy`), which any anonymous HTTP/gRPC/JSON-RPC client can invoke without authentication, runs `VMActuator(true)` directly on the calling RPC thread with **no locking whatsoever** — unlike the state-changing transaction path (`Manager.pushTransaction`), which is wrapped in `synchronized (transactionLock)` / `synchronized (this)`: [5](#0-4) [6](#0-5) [7](#0-6) 

gRPC/HTTP frameworks dispatch each `TriggerConstantContract`/`EstimateEnergy` request on its own pooled worker thread, so any number of these requests can execute `VM.play(program, OperationRegistry.prepareAndGetTable(true))` concurrently, each one calling `table.set(...)` on the very same `CONSTANT_CALL_TABLE` object other threads are simultaneously reading via `table.get(op)` inside opcode dispatch. There is no `synchronized`, no `volatile` on the backing array, and no per-thread copy — the situation is structurally identical to `LockWeak<T>` handing out unsynchronized shared access to mutable state from multiple threads.

### Impact Explanation
Because the write (`table.set`) and the read (`table.get`) that drives opcode energy costing/enablement have no synchronization or memory barrier, one thread's in-flight VM execution can observe an `Operation` variant (e.g., `ADJUSTED_MSTORE` vs `DEFAULT_MSTORE`, `RESTRICTED_SUICIDE` vs `ADJUSTED_SUICIDE`) that was written for a *different, concurrently executing* constant call with a different feature-flag view, or a torn/half-updated table produced by two threads racing `adjustMemOperations`/`adjustVoteWitness`/`adjustSelfdestruct` in `adjustTable()`. This can cause inconsistent energy metering and inconsistent opcode-enablement decisions within a single call's execution — an anonymous API client can trigger incorrect gas accounting and non-deterministic constant-call results served by the node's public RPC/HTTP interface, which is the "API the node can no longer serve correctly" class of impact called out in the rules (results returned to different clients for the same call can differ depending on unrelated concurrent traffic).

### Likelihood Explanation
No privileges are required: any client can send concurrent `TriggerConstantContract`/`EstimateEnergy` (gRPC, HTTP, and JSON-RPC `eth_call`/`eth_estimateGas`) requests, and `estimateEnergy` itself issues many rapid successive constant calls per single client request during its binary search, further increasing contention on the shared table. gRPC/HTTP servers process such requests on multi-threaded pools by design, so triggering the race requires no more than ordinary concurrent API traffic.

### Recommendation
Give each `VMActuator`/constant-call execution its own independent `JumpTable` copy (or make the mutation-then-read sequence atomic/synchronized, or make `adjustTable` produce an immutable table per configuration snapshot rather than mutating a shared singleton in place). At minimum, guard `prepareAndGetTable`/`adjustTable` with a lock or eliminate in-place mutation of `CONSTANT_CALL_TABLE`/`tableMap` entries so concurrent readers never observe partially-updated state.

### Proof of Concept
1. Deploy any contract exercising `MSTORE`/`MLOAD`/`VOTEWITNESS`/`SUICIDE` opcodes.
2. Fire many concurrent `TriggerConstantContract` (or `eth_call`) requests against the node's public gRPC/HTTP endpoints while toggling or relying on ambient `VMConfig` states (e.g., mixed calls hitting `estimateEnergy`'s internal retries) so that `adjustTable()` is invoked repeatedly and concurrently on `CONSTANT_CALL_TABLE`.
3. Observe (via added instrumentation/log of `Operation` identity returned by `table.get(op)` during dispatch) that a call sees an operation cost-variant that does not match its own thread's `VMConfig` snapshot, or gets sporadic/non-reproducible energy usage between identical calls made purely due to concurrent unrelated traffic — demonstrating an unsynchronized read/write race on the shared `JumpTable`.

  public static JumpTable prepareAndGetTable(boolean isConstantCall) {
    JumpTable table = getTable(isConstantCall);
    // Apply configuration-dependent changes once at the top level.
    adjustTable(table);
    return table;
  }

  public static JumpTable getTable(boolean isConstantCall) {
    return isConstantCall ? CONSTANT_CALL_TABLE : tableMap.get(LATEST_VERSION);
  }

  private static void adjustTable(JumpTable table) {
    // Make the corresponding changes, excluding opcode activation.
    adjustMemOperations(table);
    adjustVoteWitness(table);
    adjustSelfdestruct(table);
  }
