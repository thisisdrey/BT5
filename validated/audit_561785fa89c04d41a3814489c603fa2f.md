Based on my research, I found a genuine local analog worth flagging: the `success` field of `DeliveryReceipt` in the Snowbridge outbound queue v2 pallet is never checked before paying out relayer rewards.

### Title
Relayer reward is paid on Snowbridge outbound delivery receipt regardless of `receipt.success` value - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`Pallet::<T>::process_delivery_receipt` decodes a `DeliveryReceipt` containing a `success: bool` field (mirroring the yearn-vaults pattern where a boolean result/trigger exists but its value is never inspected by the caller before taking an irreversible action), but the function pays the relayer reward and removes the pending order unconditionally, without checking `receipt.success`.

### Finding Description
`process_delivery_receipt` fetches the `PendingOrder` for the given nonce, and if `order.fee > 0` unconditionally calls `T::RewardPayment::register_reward` and removes the order, regardless of whether the delivery on Ethereum actually succeeded: [1](#0-0) 
The `DeliveryReceipt` struct explicitly carries a `success` boolean (used in tests such as `receipt.success = true`), signaling that the caller is expected to check whether the message execution on Ethereum succeeded before crediting a reward: [2](#0-1) 
There is no `ensure!(receipt.success, ...)` or equivalent guard anywhere in `process_delivery_receipt` — the field is decoded from the verified proof but its value is discarded before the reward-and-removal logic executes.

### Impact Explanation
This is analogous to the `tendTrigger`/`harvestTrigger` bug class: a boolean result that documents an invariant ("only pay reward for successful delivery") is never checked at the call site that performs the fund-affecting action. If Ethereum-side execution of the outbound message fails (e.g., reverted gateway call), a relayer could still submit a valid Merkle/receipt proof of the (failed) transaction inclusion, and the pallet would register a full relayer reward and remove the `PendingOrder`. This results in unbacked/incorrect reward payout not tied to actual successful message delivery, and it also causes the pending order to be permanently cleared (losing the ability to reprocess/retry), i.e., duplicate/incorrect settlement of bridge relayer rewards.

### Likelihood Explanation
Any unprivileged relayer can trigger this by submitting `submit_delivery_receipt` (which calls into `process_delivery_receipt`) with a `receipt` whose underlying Ethereum event proof is for a failed execution — no malicious peer/validator/governance actor is required, only crafting/obtaining a valid proof of a reverted or failed delivery transaction, which is a normal Ethereum-side outcome outside the relayer's control but not outside their ability to submit.

### Recommendation
Explicitly gate the reward payment and order removal on `receipt.success`, mirroring the recommended fix pattern for the `tendTrigger` bug: check the boolean invariant before performing the fund-affecting side effect, e.g.:
```rust
ensure!(receipt.success, Error::<T>::DeliveryFailed);
```
or handle the `false` branch distinctly (e.g., emit a `MessageDeliveryFailed` event and decide whether/how to retry or slash, without crediting the reward).

### Proof of Concept
1. A message is queued via the outbound queue v2 pallet, creating a `PendingOrder { nonce, fee, .. }` with `fee > 0`. [3](#0-2) 
2. On Ethereum, the message execution fails/reverts (e.g., gateway call reverts), still emitting a receipt/event that can be proven via Merkle proof (as in the delivery-receipt verification flow described in the pallet docs). [4](#0-3) 
3. Relayer submits `submit_delivery_receipt` with a `DeliveryReceipt { nonce, success: false, .. }` and a valid proof of inclusion.
4. `process_delivery_receipt` is invoked; since it never checks `receipt.success`, it pays the relayer reward and removes the `PendingOrder` as if delivery had succeeded: [5](#0-4) 
5. Result: relayer reward credited for a failed delivery, and the order is irrecoverably removed from `PendingOrders`.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
