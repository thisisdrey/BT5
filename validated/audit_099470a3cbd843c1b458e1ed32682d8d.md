### Title
Unrestricted `remote.inmemory.url` allows `ext::`/`fd::` transport-helper invocation via `FetchRemoteRequest.RemoteParams.Url` - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`buildCommandOpts` sets `remote.inmemory.url` directly from the attacker-supplied `RemoteParams.Url` with no scheme allowlist, and `validateFetchRemoteRequest` only checks that the URL is non-empty. Because Git's `ext::`/`fd::` remote helpers are classified as "user" protocols and are permitted by default unless `GIT_PROTOCOL_FROM_USER=0` or `protocol.ext.allow=never`/`GIT_ALLOW_PROTOCOL` is set, and Gitaly's `ExecCommandFactory` does not set any such restriction, a crafted URL can turn `git fetch` into an arbitrary command execution primitive.

### Finding Description
`FetchRemote` validates the request via `validateFetchRemoteRequest`, which only checks `req.GetRemoteParams().GetUrl() == ""` [1](#0-0) . No scheme allowlist, no rejection of `ext::`, `fd::`, or other helper syntaxes is performed anywhere before the URL reaches `buildCommandOpts`.

`buildCommandOpts` takes `remoteURL := req.GetRemoteParams().GetUrl()` and, absent a `ResolvedAddress` (which is the common case for user-configured pull mirrors), appends it unmodified as `remote.inmemory.url` config: `config = append(config, gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL})` [2](#0-1) . This config is passed into `git fetch inmemory` via `gitcmd.WithConfigEnv(config...)` [3](#0-2)  and then executed by `quarantineRepo.FetchRemote(ctx, "inmemory", opts)` [4](#0-3) .

The only URL-scheme-aware logic in the code path is `GetURLAndResolveConfig`, and it is only invoked when `RemoteParams.ResolvedAddress` is set (used for SSRF-mitigation via IP pinning), applying a scheme check (`http`, `https`, `git`) solely for the curl-resolve config, not as a general allowlist [5](#0-4) . When `ResolvedAddress` is empty (the normal case), this scheme check is bypassed entirely, and `remoteURL` flows straight into `remote.inmemory.url` with zero scheme validation.

Examining the shared Git execution environment that Gitaly configures for every git invocation, `setupGitExecutionEnvironments` sets `GIT_TERMINAL_PROMPT=0`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_SYSTEM=/dev/null`, `XDG_CONFIG_HOME=/dev/null`, but does **not** set `GIT_PROTOCOL_FROM_USER=0`, `GIT_ALLOW_PROTOCOL`, or `protocol.ext.allow`/`protocol.file.allow` config [6](#0-5) . No occurrences of `GIT_ALLOW_PROTOCOL`, `protocol.ext`, or `protocol.file` restrictions were found anywhere in the production Gitaly code (only in test/support files), confirming this hardening is entirely absent.

Git's remote-helper resolution treats a URL of the form `<transport>::<arg>` as an invocation of `git-remote-<transport>`; for the built-in `ext` helper, `<arg>` is executed as a shell command (`git-remote-ext(1)`). Because Gitaly never sets `GIT_PROTOCOL_FROM_USER=0` (which is the mechanism Git itself uses to prevent transitive/automated invocations, e.g. from recursive submodules, from reaching `ext::`/`file::`), and this is a top-level, directly-invoked `git fetch` rather than a recursive/submodule fetch, Git's default "user" protocol policy permits the `ext` helper to run. Supplying `RemoteParams.Url = "ext::sh -c $@|sh . echo pwned"` (or similar) as `remote.inmemory.url` therefore causes `git-remote-ext` to fork the attacker-chosen command with the privileges of the `gitaly` process.

### Impact Explanation
This constitutes remote command execution on the Gitaly node under the `gitaly` service account, from an unprivileged user who can only configure a `FetchRemoteRequest`/pull-mirror URL for their own repository. This maps to GitLab's highest-severity RCE class ("Remote Code Execution") since it allows arbitrary command execution outside of the intended git object database/transport sandbox, going well beyond a simple network fetch — a total violation of the "git is never re-configured by attacker input" invariant, and a severe escalation from repository-scoped access to host-level code execution.

### Likelihood Explanation
Precondition is only that the attacker can set `RemoteParams.Url` on a `FetchRemote` call for a repository they control — e.g., by configuring a pull mirror URL (a normal, low-privilege GitLab feature) or by directly crafting the internal gRPC call if reachable. No secrets, no special role, no race condition, and no additional exploitation steps are required; it is fully deterministic and repeatable on every fetch. The main uncertainty is whether GitLab Rails independently validates/allowlists mirror URL schemes before calling into Gitaly (out of scope per the audit rules to assume this exists), and whether the actual installed Git binary was compiled/patched with hardened defaults, but nothing in the Gitaly codebase itself defends against this input.

### Recommendation
Before setting `remote.inmemory.url`, parse `remoteURL` and reject/allowlist schemes explicitly (e.g., only allow `http`, `https`, `git`, `ssh`, and SCP-like syntax); reject `ext::`, `fd::`, `file://`, and any other non-network transport helper syntax. Additionally, defensively set `GIT_PROTOCOL_FROM_USER=0` (or `-c protocol.ext.allow=never -c protocol.file.allow=never`) as part of every git invocation Gitaly issues, so that even if a helper-style URL slips through, Git itself refuses to invoke the helper.

func TestFetchRemote_ExtProtocolRCE(t *testing.T) {
    cfg, repoProto, _ := setupRepositoryService(t)

    req := &gitalypb.FetchRemoteRequest{

    require.FileExists(t, marker)

Expected (vulnerable) result: the `touch` command executes and creates the marker file on the Gitaly host, proving arbitrary command execution via the `ext::` remote helper reached through `remote.inmemory.url`.

func buildCommandOpts(ctx context.Context, opts *localrepo.FetchOpts, req *gitalypb.FetchRemoteRequest) error {
	remoteURL := req.GetRemoteParams().GetUrl()
	var config []gitcmd.ConfigPair

	for _, refspec := range getRefspecs(req.GetRemoteParams().GetMirrorRefmaps()) {
		config = append(config, gitcmd.ConfigPair{
			Key: "remote.inmemory.fetch", Value: refspec,
		})
	}

	if resolvedAddress := req.GetRemoteParams().GetResolvedAddress(); resolvedAddress != "" {
		modifiedURL, resolveConfig, err := gitcmd.GetURLAndResolveConfig(remoteURL, resolvedAddress)
		if err != nil {
			return fmt.Errorf("couldn't get curloptResolve config: %w", err)
		}

		remoteURL = modifiedURL
		config = append(config, resolveConfig...)
	}

	config = append(config, gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL})

func (s *server) validateFetchRemoteRequest(ctx context.Context, req *gitalypb.FetchRemoteRequest) error {
	if err := s.locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	if req.GetRemoteParams() == nil {
		return structerr.NewInvalidArgument("missing remote params")
	}

	if req.GetRemoteParams().GetUrl() == "" {
		return structerr.NewInvalidArgument("blank or empty remote URL")
	}

	return nil
}

func getURLAndResolveConfigForURL(remoteURL, resolvedAddress string) (string, []ConfigPair, error) {
	u, err := url.ParseRequestURI(remoteURL)
	if err != nil {
		return "", nil, fmt.Errorf("couldn't parse remoteURL: %w", err)
	}

	port := u.Port()

	if port == "" {
		switch u.Scheme {
		case "http":
			port = "80"
		case "https":
			port = "443"
		case "git":
			port = "9418"
		default:
			return "", nil, fmt.Errorf("unknown schema provided: %s", u.Scheme)
		}
	}
