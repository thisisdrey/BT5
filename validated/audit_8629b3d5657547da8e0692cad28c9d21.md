Based on my investigation, I found a genuine analog: an out-of-bounds read in `third_party/ijar/zip.cc`'s central-directory parser, structurally identical to the CVE's pattern (length-prefixed fields consumed without a "sufficient bytes remain" check before reads/copies).

### Title
Out-of-bounds read via unchecked ZIP central-directory length fields in ijar - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar (the interface-jar generator invoked automatically for Java compile-time dependency jars) reads `file_name_length`, `extra_field_length`, and `file_comment_length` from an attacker-supplied ZIP central directory entry and advances/dereferences the input cursor by these attacker-controlled 16-bit values with **no bounds check** against the actual mapped file size, unlike its sibling `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before every read.

### Finding Description
`ProcessCentralDirEntry` reads the fixed fields of a central directory record and then: [1](#0-0) 
copies `file_name_length` bytes from `p` into a fixed `filename[PATH_MAX]` buffer and advances `p` by the full, unclamped `file_name_length`. It then walks the "extra field" chain using `extra_field_length` and internal `data_size` sub-fields, and finally advances past `file_comment_length`: [2](#0-1) 
None of these advances or reads are preceded by any check that the declared length is within the bounds of the memory-mapped input file. Contrast this with the local-file-header parser `ProcessLocalFileEntry`, which explicitly guards every variable-length read with `EnsureRemaining()`: [3](#0-2) 
The only global bound check performed before iterating entries is on the *aggregate* central directory size in `FindZipCentralDirectory`: [4](#0-3) 
This does not constrain any individual entry's `file_name_length`/`extra_field_length`/`file_comment_length`, so a crafted entry near the end of an otherwise "valid" central directory can cause `p` (and the `memcpy` source pointer) to run past `zipdata_in_ + input_file_->Length()`, i.e., past the end of the `mmap`'d region — an out-of-bounds read of the process's memory. This is invoked from `InputZipFile::ProcessNext()` and `InputZipFile::CalculateOutputLength()`, both driven directly by attacker-controlled ZIP bytes: [5](#0-4) 
`ijar` is Bazel's automatic tool for stripping Java jars to interface-only form for compilation; it runs on any jar consumed as a Java compile-time dependency, including jars fetched by `http_jar`/`http_archive`/Maven-resolved artifacts. Because the attacker fully controls the jar's bytes, they can make the file pass its own declared sha256/integrity checksum (the checksum only proves "this is the file I intended," not that it's well-formed), so checksum verification does not prevent this class of bug — the vulnerability is inside the parser that trusts length fields in checksum-verified but still attacker-crafted content.

### Impact Explanation
An out-of-bounds read on a `mmap`'d file can read adjacent heap/mapped memory (potentially including other build inputs, environment data, or unrelated heap allocations residing near the mapping) and copy up to `PATH_MAX-1` bytes of that memory into the `filename` buffer, which is then used and can be echoed in diagnostics or influence generated output; alternatively it can run past the mapped region entirely and cause a `SIGSEGV`. This matches the CVE class (out-of-bounds read enabling information disclosure) and, per policy, is only in scope because it stems from mis-trusted length fields in content the attacker fully controls — not from a MITM or malicious peer.

### Likelihood Explanation
Any Bazel Java build that consumes an externally-supplied jar (via `http_jar`, `http_archive`, or a resolved Maven dependency) as a compile-time dependency will run it through `ijar`. An attacker who serves/publishes such a jar (with a crafted central directory entry containing an oversized `file_name_length`/`extra_field_length`/`comment_length`) needs no special access — this exactly matches the "unprivileged origin server/publisher" attacker model in scope.

### Recommendation
Add `EnsureRemaining()`-style bounds checks in `ProcessCentralDirEntry` before reading/copying `file_name_length`, iterating the extra-field chain (`extra_field_length` and each `data_size`), and skipping `file_comment_length`, mirroring the checks already present in `ProcessLocalFileEntry`.

### Proof of Concept
A JUnit/`src/test/shell` reproduction would construct a minimal ZIP whose End-Of-Central-Directory and central-directory-size fields are internally consistent (passing the `FindZipCentralDirectory` aggregate check), but where the sole central directory entry declares `file_name_length` (or `extra_field_length`/`comment_length`) larger than the number of bytes actually remaining in the file/mapping. Running the `ijar` binary (or the `test_download_then_extract` style flow that feeds such a crafted jar into a Java compile action) on this file under AddressSanitizer would surface a heap-buffer-overflow/out-of-bounds-read report from `ProcessCentralDirEntry`, whereas an analogous malformed *local* file header field is already correctly rejected by `EnsureRemaining()` in `ProcessLocalFileEntry`, demonstrating the missing parity check.

bool InputZipFile::ProcessNext() {
  // Process the next entry in the central directory. Also make sure that the
  // content pointer is in sync.
  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }
  u4 signature = get_u4le(p);
  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}
