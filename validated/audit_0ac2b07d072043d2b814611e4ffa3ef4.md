### Title
Uninitialized `accountIndexOf` read lets a holder claim reward tokens equal to their full balance when a reward is activated at `INITIAL_INDEX` - ([File: contracts/RewardsDistributor.sol])

### Summary
Analogous to the NULL-pointer dereference (dereferencing data at an uninitialized/null location), `RewardsDistributor._calculateTokenDelta` dereferences the never-initialized `accountIndexOf[token_][account_]` slot (default `0`) and computes `_deltaIndex = _tokenIndex - _accountIndex`. The initialization fallback only applies when `_tokenIndex > INITIAL_INDEX`, so at the exact moment a governor activates a reward speed (`_tokenIndex == INITIAL_INDEX`), a pre-existing holder gets `_deltaIndex == 1e18` and is credited `balance` units of the reward token.

### Finding Description [1](#0-0) 

`_calculateTokenDelta` reads `accountIndexOf[token_][account_]`; for an account whose `DepositToken`/`DebtToken` position was created before the reward token was activated, `updateBeforeMintOrBurn`/`updateBeforeTransfer` skipped index updates because `tokenStates[token_].index == 0` [2](#0-1) . When the governor later calls `updateTokenSpeed` with `newSpeed_ > 0`, the state is set to `index: INITIAL_INDEX` (1e18) [3](#0-2) .

In `_calculateTokenDelta`, the zero-accountIndex fallback requires `_tokenIndex > INITIAL_INDEX`, which is false when `_tokenIndex == INITIAL_INDEX`. Therefore `_deltaIndex = 1e18 - 0 = 1e18` and `_tokensDelta = balance.wadMul(1e18) = balance` [4](#0-3) . `claimRewards` then transfers `tokensAccruedOf[account_]` up to the distributor's reward-token balance [5](#0-4) .

### Impact Explanation
An unprivileged attacker can steal the reward tokens held by the distributor (unclaimed yield of all users). Using a flash-loan-sized `DepositToken` position created while rewards are inactive, the attacker claims in the same block/timestamp the governor activates the speed — `_updateTokenIndex` does not advance the index because `_deltaTimestamps == 0`, leaving `_tokenIndex == INITIAL_INDEX`, so the bug pays out `balance` reward tokens. The attacker then withdraws collateral and unwinds. Invariant broken: reward accrual correctness — an account with zero accrued history receives `wadMul(balance, INITIAL_INDEX)` worth of rewards.

### Likelihood Explanation
Requires only normal protocol operation: a reward token speed being activated after users already hold deposit/debt tokens — a routine configuration sequence on a live pool (e.g., enabling a new reward or re-enabling at index `INITIAL_INDEX` semantics via `syncTokenSpeed`/`updateTokenSpeed`). All checks pass: `claimRewards` is permissionless (`nonReentrant` only), `updateBeforeMintOrBurn` silently no-ops pre-activation, and `_transferRewardIfEnoughTokens` pays up to the contract's balance. The attacker needs same-block execution relative to the governor's activation transaction, achievable by watching the mempool or via `Operator.execute` bundling.

### Recommendation
Treat an unset `accountIndexOf` as initialized to `INITIAL_INDEX` whenever the token state exists — change the fallback to `_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX` (or `>=`), i.e., also clamp when `_tokenIndex == INITIAL_INDEX`. Equivalently, initialize `accountIndexOf` to `INITIAL_INDEX` on first touch, or set `tokensDelta` to 0 when `_accountIndex == 0`.

### Proof of Concept
Reproducible Hardhat fork PoC (mainnet pool, distributor funded with reward token):

```solidity
// test/RewardsDistributorNullIndex.t.sol (Foundry)
function test_claimDrainsRewards_atInitialIndex() public {
    // Setup: pool with a DepositToken and RewardsDistributor holding rewardToken,
    // where tokenStates[msdToken].index == 0 (rewards not yet activated).

    // 1. Attacker deposits collateral while rewards inactive
    //    -> _mint -> updateBeforeMintOrBurn no-ops, accountIndexOf[msd][attacker] stays 0
    underlying.approve(address(msdToken), DEPOSIT_AMOUNT);
    msdToken.deposit(DEPOSIT_AMOUNT, attacker);
    assertEq(rewardsDistributor.accountIndexOf(msdToken, attacker), 0);

    // 2. Same block: governor activates the reward speed
    vm.prank(governor);
    rewardsDistributor.updateTokenSpeed(msdToken, speed); // index = INITIAL_INDEX = 1e18

    // 3. Same timestamp: _updateTokenIndex no-ops (deltaTimestamps == 0),
    //    accountIndex==0 and tokenIndex==INITIAL_INDEX -> deltaIndex = 1e18
    uint256 balBefore = rewardToken.balanceOf(attacker);
    vm.prank(attacker);
    rewardsDistributor.claimRewards(attacker);

    // Attacker receives ~DEPOSIT_AMOUNT units of rewardToken
    assertEq(rewardToken.balanceOf(attacker) - balBefore, msdToken.balanceOf(attacker));
}
```

Uncertainty noted: the exploit window is the same timestamp as the activation transaction (or any moment before the index exceeds `INITIAL_INDEX`, which happens on the next accrual once `speed > 0` and time passes). This is the strongest null/uninitialized-read analog I could verify in scope; the rest of the codebase consistently guards zero addresses and zero indexes.

```text
    function _calculateTokenDelta(
        TokenState memory _tokenState,
        IERC20 token_,
        address account_
    ) private view returns (uint256 _tokenIndex, uint256 _tokensDelta) {
        _tokenIndex = _tokenState.index;
        uint256 _accountIndex = accountIndexOf[token_][account_];

        if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
            _accountIndex = INITIAL_INDEX;
        }

        uint256 _deltaIndex = _tokenIndex - _accountIndex;
        _tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
    }
```
