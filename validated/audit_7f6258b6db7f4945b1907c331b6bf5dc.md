### Title
Loop-back IP check in `PackObjectsHook` bypasses the per-key concurrency limiter, enabling unlimited concurrent `git-pack-objects` spawns - (File: internal/gitaly/service/hook/pack_objects.go)

### Summary
The external report describes an EVM gas-accounting bypass: certain error paths in `minievm`'s call/create tracer skip charging gas, and because gas is normally charged upfront by the interceptor but not for calls dispatched through a nested/precompiled path (`dispatchMessage`), an attacker can repeat the free operation to DoS the chain. The essential bug class is "a resource-accounting/limiting mechanism is bypassed on a specific code path that is reachable by an ordinary caller, allowing unlimited/unmetered repetition of an expensive operation." The closest analog in Gitaly is the `RemoteIp`-based bypass of the pack-objects concurrency limiter in `packObjectsHook`.

### Finding Description
`packObjectsHook` in Gitaly decides whether to run `git-pack-objects` under a dedicated concurrency limiter (`s.packObjectsLimiter`, keyed by remote IP) or to run it completely unthrottled, based solely on whether the parsed `RemoteIp` looks like a loopback address: [1](#0-0) 

```go
servedBytes, created, err := s.packObjectsCache.Fetch(ctx, cacheKey, output, func(w io.Writer) error {
    ipAddr := net.ParseIP(req.GetRemoteIp())
    ...
    // Ignore loop-back IPs
    if ipAddr != nil && !ipAddr.IsLoopback() {
        return s.runPackObjectsLimited(ctx, w, ipAddr.String(), req, args, stdin, cacheKey)
    }
    return s.runPackObjects(ctx, w, req, args, stdin, cacheKey)
})
```

`runPackObjectsLimited` enforces `s.packObjectsLimiter.Limit(...)`, a per-remote-IP concurrency/queue limiter with metrics (`gitaly_pack_objects_in_progress`, `gitaly_pack_objects_dropped_total`), as exercised in `TestPackObjects_concurrencyLimit`: [2](#0-1) 

By contrast, `runPackObjects` runs `git-pack-objects` with no concurrency gate at all: [3](#0-2) 

`RemoteIp` in the `PackObjectsHookWithSidechannelRequest` is populated from `payload.UserDetails.RemoteIP` inside `gitaly-hooks`' `packObjectsHook`: [4](#0-3) 

This `RemoteIP` field ultimately originates from data supplied via the Git protocol/HooksPayload chain (e.g., via the `user_details`/`remote_ip` metadata that gitlab-shell/workhorse forward from the client-facing hop), not from an authenticated, network-verified peer address of the actual pack-objects requester at the Gitaly RPC layer itself. Any caller able to influence this value to a loopback-looking string (e.g., `127.0.0.1`, `::1`) causes the accounting/limiting step to be skipped entirely for that fetch, mirroring the `minievm` situation where a specific error/condition path removed the accounting step that is applied on all other paths.

### Impact Explanation
If the loopback check can be satisfied by an untrusted client (a normal `git fetch`/`git clone` caller), that caller's pack-objects generation escapes the dedicated concurrency limiter that exists specifically to protect Gitaly from CPU/memory exhaustion caused by parallel `git-pack-objects` invocations (this is the exact protection the pack-objects cache/limiter subsystem was built for, per `doc/design_pack_objects_cache.md`). Repeating such unmetered, unthrottled fetches — each spawning a full `git-pack-objects` subprocess — can exhaust CPU, memory, and I/O on the Gitaly node, denying service to other tenants/repositories on the same node, analogous to how repeated "free" EVM calls could exhaust chain resources without being throttled by the gas mechanism.

### Likelihood Explanation
Likelihood depends on whether `RemoteIp`/`UserDetails.RemoteIP` is attacker-controllable end-to-end from an ordinary git operation without additional privileged trust boundaries (e.g., only trusted from GitLab Rails/workhorse, or always populated with the real socket peer address). Based solely on the code paths found, `RemoteIp` is a plain string field on the request/payload that is forwarded from upstream components rather than derived from a low-level, tamper-resistant TCP peer address at the point the limiter decision is made in `pack_objects.go`. I could not fully trace, within the available index, the exact upstream population/validation of `UserDetails.RemoteIP` (e.g., in gitlab-shell/workhorse) to confirm whether it is authenticated or filtered before reaching Gitaly, so likelihood is uncertain and should be validated by a background agent with full repository access, including gitlab-shell/workhorse if in scope.

### Recommendation
- Do not rely on a client/pipeline-supplied `RemoteIp` string to decide whether to bypass the concurrency limiter; instead, base the bypass decision on the actual, verified peer of the internal Gitaly↔Gitaly-hooks sidechannel connection (which is genuinely loopback), separate from the `RemoteIp` metadata field used only for limiter keying/labeling.
- Alternatively, always run `git-pack-objects` through `runPackObjectsLimited` and only special-case the *limiter key* (not the presence of limiting) for loopback-originated calls, so all execution paths are subject to some accounting.
- Add a regression test asserting that pack-objects requests whose `RemoteIp` field is attacker-suppliable and set to a loopback value are still subject to the `packObjectsLimiter`.

### Proof of Concept
Not independently reproduced (no execution environment available). Based on static review of `internal/gitaly/service/hook/pack_objects.go` L65-87 and `cmd/gitaly-hooks/hooks.go` L456-475, the theoretical exploitation sequence is:
1. An attacker issuing a `git fetch`/`git clone` request causes gitaly-hooks to invoke `packObjectsHook`, sending a `PackObjectsHookWithSidechannelRequest` whose `RemoteIp` field is populated from `payload.UserDetails.RemoteIP`.
2. If this value can be influenced to resolve to a loopback address (e.g., `127.0.0.1`), `s.packObjectsHook` takes the `s.runPackObjects` branch, skipping `s.packObjectsLimiter.Limit(...)` entirely.
3. Repeating this request concurrently spawns unlimited concurrent `git-pack-objects` processes for the same or different repositories, unconstrained by `gitaly_pack_objects_in_progress`/`gitaly_pack_objects_dropped_total` limits, exhausting node resources — a resource-accounting bypass DoS analogous to the reported EVM finding.

```go
func (s *server) runPackObjects(
	ctx context.Context,
	w io.Writer,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.ReadCloser,
	key string,
) error {
	// We want to keep the context for logging, but we want to block all its
	// cancellation signals (deadline, cancel etc.). This is because of
	// the following scenario. Imagine client1 calls PackObjectsHook and
	// causes runPackObjects to run in a goroutine. Now suppose that client2
	// calls PackObjectsHook with the same arguments and stdin, so it joins
	// client1 in waiting for this goroutine. Now client1 hangs up before the
	// runPackObjects goroutine is done.
	//
	// If the cancellation of client1 propagated into the runPackObjects
	// goroutine this would affect client2. We don't want that. So to prevent
	// that, we suppress the cancellation of the originating context.
	ctx = context.WithoutCancel(ctx)

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	defer stdin.Close()

	return s.runPackObjectsFn(ctx, s.gitCmdFactory, w, req, args, stdin, key)
}
```

```go
func (s *server) runPackObjectsLimited(
	ctx context.Context,
	w io.Writer,
	limitkey string,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.ReadCloser,
	key string,
) error {
	ctx = context.WithoutCancel(ctx)

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	defer stdin.Close()

	if _, err := s.packObjectsLimiter.Limit(
		ctx,
		limitkey,
		func() (interface{}, error) {
			return nil,
				s.runPackObjectsFn(
					ctx,
					s.gitCmdFactory,
					w,
					req,
					args,
					stdin,
					key,
				)
		},
	); err != nil {
		return err
	}

	return nil
}
```
