### Title
Uint underflow in `Table.parseRefBlock` reftable parsing causes index computation errors / potential DoS - (File: internal/git/reftable/reftable.go)

### Summary
`Table.parseRefBlock` and `Table.getBlockRange` in Gitaly's reftable reader perform unchecked `uint` subtractions when computing block boundaries and restart offsets from values embedded in a reftable file (block length and restart count). If a table file contains values that don't satisfy the implicit invariants the code assumes (e.g. `currentBS < 2` or `3*RestartCount` larger than `currentBS`), the subtraction wraps around because Go's `uint` arithmetic does not panic on underflow, silently producing a huge value rather than reverting/erroring the way the analogous Solidity code was expected to.

### Finding Description
`parseRefBlock` reads a block-length value directly from the table bytes and later derives the restart-table offset: [1](#0-0) 

```go
func (t *Table) parseRefBlock(src []byte, headerOffset, blockStart, blockEnd uint) ([]git.Reference, error) {
	currentBS := t.extractBlockLen(src, blockStart+headerOffset)
	...
	if err := binary.Read(bytes.NewBuffer(src[blockStart+currentBS-2:]), binary.BigEndian, &b.RestartCount); err != nil {
		return nil, fmt.Errorf("reading restart count: %w", err)
	}

	b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)
	...
}
```

`currentBS` comes from `extractBlockLen`, which parses 3 bytes directly out of the file content (`internal/git/reftable/reftable.go:198-201`). Both `blockStart+currentBS-2` (used as a slice index) and `blockStart + currentBS - 2 - 3*uint(b.RestartCount)` are unchecked `uint` subtractions:
- If `currentBS < 2`, the expression `blockStart+currentBS-2` underflows to a value close to `math.MaxUint`, which is then used to index into `src[blockStart+currentBS-2:]`, producing an out-of-range slice panic.
- If `b.RestartCount` (also read straight from file bytes) is large enough that `3*uint(b.RestartCount)` exceeds `blockStart+currentBS-2`, `RestartStart` wraps to a huge `uint` value. That value is then used as a loop bound (`idx < b.RestartStart`) and as a slice bound in `getRefsFromBlock`, again causing out-of-range slice panics rather than a controlled error.

This mirrors the reported bug class: an arithmetic operation that assumes its operands satisfy an implicit ordering invariant (`baseSettlementFeePercentage >= stepSize*maxStep` in the Solidity code) is performed with an unsigned type that wraps instead of reverting, and the wrapped value is used downstream where a bounded/valid value was expected.

### Impact Explanation
A reftable file with crafted/corrupted block-length or restart-count fields causes `GetReferences()` to either panic (index out of range) or compute nonsensical offsets, aborting whatever request depends on reading references from that table. Reftable parsing is invoked from reference-listing and repository/backup/replication code paths (`internal/git/localrepo/refs.go`, `internal/gitaly/service/repository/replicate.go`, `internal/backup/repository.go`), i.e. this is on paths that walk repository storage, so a malformed reftable (e.g. arriving via replication, backup restore, or an imported repository directory) can cause a goroutine panic and disrupt request handling for that repository, i.e., a denial of service for reference-listing style operations on the affected repository.

### Likelihood Explanation
Reftable files are supposed to be internally generated and consistent, so this is unlikely to be triggered by a well-formed table under normal operation. It requires an unusual, corrupted, or maliciously crafted reftable byte stream — via a compromised/failed write, replicated corrupted data, or backup/restore of an untrusted repository — to reach the vulnerable arithmetic, which lowers likelihood compared to a directly-user-controlled numeric input.

### Recommendation
Add explicit bounds validation before performing the subtractions in `parseRefBlock` (e.g. ensure `currentBS >= 2` and `3*uint(RestartCount) <= currentBS-2` before computing `RestartStart`), and similarly guard `extractBlockLen`/`getBlockRange` against out-of-range slice indices, returning a descriptive parse error instead of allowing `uint` underflow to propagate into slice indexing or loop bounds.

### Proof of Concept
Construct (or corrupt) a `.ref` reftable file where the block's length byte-triplet (parsed by `extractBlockLen`) encodes a value less than 2, or where the trailing 2-byte `RestartCount` is set to a large value (e.g. `0xFFFF`) relative to the block size. Call `Table.GetReferences()` (reached via e.g. `localrepo.GetReferences` when the repository uses the reftable backend) on this table; the underflowed `uint` computation in `parseRefBlock` will produce an out-of-bounds slice index and panic, as shown by the unchecked expressions at [2](#0-1) .

// parseRefBlock parses a block and if it is a ref block, provides
// all the reference updates.
func (t *Table) parseRefBlock(src []byte, headerOffset, blockStart, blockEnd uint) ([]git.Reference, error) {
	currentBS := t.extractBlockLen(src, blockStart+headerOffset)

	fullBlockSize := t.blockSize
	if fullBlockSize == 0 {
		fullBlockSize = currentBS
	} else if currentBS < fullBlockSize && currentBS < (blockEnd-blockStart) && src[blockStart+currentBS] != 0 {
		fullBlockSize = currentBS
	}

	b := &block{
		BlockStart:    blockStart + headerOffset,
		FullBlockSize: fullBlockSize,
	}

	if err := binary.Read(bytes.NewBuffer(src[blockStart+currentBS-2:]), binary.BigEndian, &b.RestartCount); err != nil {
		return nil, fmt.Errorf("reading restart count: %w", err)
	}

	b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)

	return t.getRefsFromBlock(src, b)
}
