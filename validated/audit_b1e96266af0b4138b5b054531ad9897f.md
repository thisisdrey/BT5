## Title
Potential 32-bit integer overflow bypasses central directory bounds check in `FindZipCentralDirectory` - (File: `third_party/ijar/zip.cc`)

### Summary
`third_party/ijar/zip.cc`'s `FindZipCentralDirectory` reads the End of Central Directory (EOCD) fields `central_dir_size` and `central_dir_offset` as 32-bit `u4` values directly from attacker-controlled zip/jar bytes, then validates them with `cd.central_dir_offset + cd.central_dir_size > in_length` before trusting the resulting central directory pointer. [1](#0-0) 

### Finding Description
`cd.central_dir_size` and `cd.central_dir_offset` are both declared/read as `u4` (`uint32_t`, per `third_party/ijar/common.h`). [2](#0-1) 
In the bounds check:
```
if (cd.central_dir_offset + cd.central_dir_size > in_length) { ... }
*central_dir = end_of_central_dir - cd.central_dir_size;
``` [3](#0-2) 
both operands are 32-bit unsigned integers, so `cd.central_dir_offset + cd.central_dir_size` is computed with 32-bit wraparound *before* being widened for comparison against `in_length`. A crafted EOCD record can pick `central_dir_offset` and `central_dir_size` such that their true (unwrapped) sum exceeds `in_length`, but the 32-bit wrapped sum is small enough to pass the check, since `in_length`'s type is `size_t` (64-bit on most target platforms) and the addition itself does not get promoted to 64-bit prior to overflow. This is directly analogous to the reported Rollkit issue, where an unvalidated height/size value was used before an overflow-safety check was added.

I was not able to fully confirm within tool budget whether `end_of_central_dir - cd.central_dir_size` (used to derive `*central_dir`, i.e., the actual pointer used for parsing) is independently re-validated elsewhere (e.g., in `ProcessCentralDirEntry`/`InputZipFile::ProcessNext`) in a way that fully neutralizes the effect of a bypassed bounds check via this specific overflow. The pointer arithmetic `end_of_central_dir - cd.central_dir_size` is a subtraction of a pointer and an untrusted 32-bit value that is not obviously re-checked against the buffer start.

### Impact Explanation
`FindZipCentralDirectory` is reached by ijar (`zip.cc`), which is used both for the standalone `ijar`/`zipper` tools and as a component of jar processing during the build. If the bounds check can be bypassed via overflow, the derived `central_dir` pointer could point outside the memory-mapped/allocated input buffer, leading `ProcessCentralDirEntry` (and subsequent entry parsing / decompression / extraction) to read out-of-bounds memory when processing a maliciously crafted `.zip`/`.jar` archive supplied as a `http_archive`/`http_jar` source, or any archive consumed by this code path. This matches the "read outside the repository/exec root/output base" class described in the mapping, applied to memory bounds rather than filesystem paths — an attacker-controlled archive byte stream driving out-of-bounds memory access.

### Likelihood Explanation
Requires the attacker to control the exact byte content of an archive that Bazel processes with this ijar code path (e.g., an `http_jar`/`http_archive` target, or any jar consumed by `singlejar`/`ijar` tooling) and to know target-specific pointer/buffer-size details for a to construct a genuinely exploitable input (out-of-bounds read amount and location). Existing sha256/integrity checks on `http_archive`/`http_jar` downloads (documented at `tools/build_defs/repo/http.bzl`) would need to be bypassed or absent for an attacker-controlled file to reach this code with default flags — if the archive already matches a pinned checksum, this is not a remotely exploitable vector for a hostile origin server since Bazel would refuse to proceed on checksum mismatch. This lowers likelihood substantially: the concrete attacker model in scope (hostile origin/mirror serving unexpected bytes) is stopped by the checksum requirement when one is declared; without a checksum, it is already a known-non-hermetic, user-accepted risk documented by Bazel itself.

### Recommendation
Cast `cd.central_dir_offset` and `cd.central_dir_size` to a 64-bit type (e.g., `u8`) before performing the addition in the bounds check in `FindZipCentralDirectory`, matching the `u8`-based bounds handling already used elsewhere for ZIP64 fields, and add an explicit lower-bound check that `cd.central_dir_size <= (end_of_central_dir - bytes)` before computing `*central_dir = end_of_central_dir - cd.central_dir_size`. [4](#0-3) 

### Proof of Concept
A reproducible proof of concept was not constructed within the current investigation — a JUnit/shell test would need to build a crafted zip file with an EOCD record where `central_dir_offset + central_dir_size` overflows 32 bits (e.g., `central_dir_offset = 0xFFFFFFF0`, `central_dir_size = 0x20`, giving a wrapped sum of `0x10`) against a small `in_length`, then invoke `ZipExtractor::Create`/`ProcessAll` and observe an out-of-bounds read or corrupted parse, ideally under ASan. This would extend the existing `third_party/ijar/test/zip_test.sh` (which already tests oversized zips and path traversal) with an overflow-specific case. [5](#0-4) 

**Caveat:** I could not fully verify within the available tool budget whether downstream code (e.g. `ProcessCentralDirEntry`, `InputZipFile::ProcessNext`) independently re-validates the derived `central_dir` pointer against the mapped buffer bounds in a way that would prevent actual out-of-bounds access even if this specific check is bypassed by overflow. This should be confirmed by a deeper trace of `zip.cc` before treating this as conclusively exploitable.
