Based on my investigation, I found a concrete analog in the TVM opcode handling.

### Title
Unbounded array allocation in TVM `CODECOPY`/`EXTCODECOPY` opcodes can trigger `OutOfMemoryError` from attacker-controlled length - (File: `actuator/src/main/java/org/tron/core/vm/OperationActions.java`)

### Summary
The CVE-2018-10958 bug class is: an attacker-controlled "size" field flows directly into a memory-allocation call (`new byte[...]` equivalent) without an upper bound check, causing an unrecoverable abort/crash. The same pattern exists in java-tron's TVM bytecode interpreter for the `CODECOPY` and `EXTCODECOPY` opcodes.

### Finding Description
`codeCopyAction` and `extCodeCopyAction` pop a `lengthData` value from the EVM/TVM stack and convert it with `intValueSafe()`, then immediately allocate a byte array of that size: [1](#0-0) [2](#0-1) 

`intValueSafe()` is designed to avoid `ArithmeticException` on overflow, but it does so by clamping any value that doesn't fit into 4 bytes (or is negative) to `Integer.MAX_VALUE`, rather than rejecting it: [3](#0-2) 

Because a contract can push an arbitrary 256-bit stack value as the `length` operand of `CODECOPY`/`EXTCODECOPY`, `lengthData` becomes `Integer.MAX_VALUE` (≈2^31-1), and the subsequent `byte[] codeCopy = new byte[lengthData];` attempts to allocate ~2 GB in a single contiguous array. This is analogous to the Exiv2 bug where an oversized, attacker-supplied size value is passed straight into an allocation routine (`zlibUncompress`) without a sane upper bound, leading to abort.

Unlike the VM's `Memory` class, which has an explicit, energy-metered `extend()`/`checkMemorySize()` path that throws a catchable `Program.OutOfMemoryException` before allocating memory in chunks, the array creation in `codeCopyAction`/`extCodeCopyAction` happens directly via a raw Java array allocation, independent of that guarded memory-extension mechanism. A raw `new byte[Integer.MAX_VALUE]` throws `java.lang.OutOfMemoryError`, a JVM `Error` (not an `Exception`), which is not guaranteed to be caught by the actuator/executor's normal `try { ... } catch (Exception e)` transaction-execution handling.

### Impact Explanation
If `OutOfMemoryError` thrown from this array allocation escapes the transaction execution's exception handling (which is designed around catchable VM/actuator exceptions such as `Program.OutOfMemoryException`, `ContractValidateException`, etc.), it can propagate up through block processing/`Manager` block application, potentially crashing the node process or leaving it in an inconsistent state. Even if the JVM manages to only fail the single allocation (throwing but not crashing the whole process due to sufficient heap), it still represents an inconsistent, un-metered, uncontrolled resource consumption path that bypasses the energy-based memory-extension safeguards other parts of the interpreter enforce.

### Likelihood Explanation
Any account can trigger this by deploying or calling a smart contract containing a `CODECOPY` or `EXTCODECOPY` opcode with a very large `length` operand (e.g., `0xFFFF...FF` pushed via `PUSH32`). This requires only a signed `TriggerSmartContract`/`CreateSmartContract` transaction with sufficient `feeLimit` to reach the opcode — no special privileges are needed.

### Recommendation
Bound `lengthData` (and the resulting `sizeToBeCopied`) against the VM's actual configured memory/energy limits (as already done via `Memory.extend`/`checkMemorySize`) before allocating `codeCopy`, or reuse the metered `Program.memorySave`/`Memory.extend` path so oversized allocations are rejected with the catchable `Program.OutOfMemoryException` rather than a raw `new byte[]` that can throw an uncatchable `OutOfMemoryError`.

### Proof of Concept
1. Deploy or call a contract whose bytecode contains: `PUSH32 0xffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff` (huge length) `PUSH1 0x00` (codeOffset) `PUSH1 0x00` (memOffset) `CODECOPY` (or `EXTCODECOPY` with an address pushed first).
2. Submit as a `TriggerSmartContract`/`CreateSmartContract` transaction with a large `feeLimit`.
3. Execution reaches `codeCopyAction`/`extCodeCopyAction` in `OperationActions.java`, computing `lengthData = Integer.MAX_VALUE` via `intValueSafe()`, then executing `new byte[lengthData]`, attempting a ~2 GB allocation and throwing `OutOfMemoryError`.

**Note on confidence:** I was unable to fully trace, within the tool budget, whether the top-level VM execution loop (`VM.java`/actuator dispatch) wraps opcode execution in a handler broad enough to catch `java.lang.Error` (as opposed to only `Exception`), which would determine whether this actually crashes the node process versus just failing the single transaction. This should be verified directly in the repository before treating the crash/DoS impact as fully confirmed.

  public static void codeCopyAction(Program program) {
    byte[] fullCode = program.getCode();

    int memOffset = program.stackPop().intValueSafe();
    int codeOffset = program.stackPop().intValueSafe();
    int lengthData = program.stackPop().intValueSafe();

    int sizeToBeCopied = lengthData;
    if ((long) codeOffset + lengthData > fullCode.length) {
      sizeToBeCopied = fullCode.length < codeOffset ? 0 : fullCode.length - codeOffset;
    }

    byte[] codeCopy = new byte[lengthData];

    if (codeOffset < fullCode.length) {
      System.arraycopy(fullCode, codeOffset, codeCopy, 0, sizeToBeCopied);
    }

    program.memorySave(memOffset, codeCopy);
    program.step();
  }

  /**
   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()
   */
  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }
