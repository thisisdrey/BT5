Based on the code examined, the core factual claim holds: `Pallet::do_process_message` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` decodes the caller/XCM-derived `fee` field and stores it verbatim into `PendingOrder`, with no minimum-value check anywhere in the pipeline, and `process_delivery_receipt` only gates payout on `order.fee > 0`.

Audit Report

## Title
Outbound-Queue-V2 delivery `fee` is user-supplied and unbounded down to 1, allowing near-zero-cost spam of relayer-processed Ethereum messages - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Pallet::do_process_message` decodes a `Message { origin, id, fee, commands }` and stores it as `PendingOrder { nonce, fee, block_number }` without validating `fee` against any minimum, and `SendMessage::validate` in `send_message_impl.rs` only checks payload size, not fee amount. At payout time, `process_delivery_receipt` only checks `order.fee > 0` before crediting the relayer, so a caller can set `fee = 1` and pass every check while consuming real merkle-commitment, storage, and dispatch-gas-metering resources on Bridge Hub for each message.

## Finding Description
`do_process_message` decodes the message and unconditionally stores the caller-supplied `fee` into `PendingOrders`: [1](#0-0) [2](#0-1) . `SendMessage::validate` in `send_message_impl.rs` enforces only a payload-size bound, no fee floor. The payout path checks only `order.fee > 0`: [3](#0-2) . This confirms no minimum-fee enforcement exists between message intake and reward payout — the only guard on the economic value of the message is a trivially-satisfiable `> 0` check.

The design document explicitly names the intended, but apparently unimplemented, mitigation for this exact scenario ("impose a minimum relayer reward of at least the existential deposit 0.1 DOT ... to stop spamming messages with 0 rewards") [4](#0-3) .

However, further investigation shows the project did add a related mitigation after this design-doc gap was identified: `snowbridge-pallet-system-frontend`'s `add_tip` mechanism (PR "Snowbridge - Message reward topups") allows relayers/users to top up a message's reward post-hoc if the original fee is too low to be profitable to process [5](#0-4) . This is a market-based fix (relayers simply won't process unprofitable messages, and someone can voluntarily top them up) rather than a hard minimum-fee floor, meaning the underlying claim — that no minimum floor exists at the pallet level — is factually accurate. The `MaxMessagesPerBlock`/`Yield` mechanism in `do_process_message` bounds per-block spam volume but does not prevent per-message underpricing: [6](#0-5) .

## Impact Explanation
Any account able to originate an outbound v2 message can set `fee = 1`, causing the pallet to still perform full merkle-leaf accounting, gas-metering (`GasMeter::maximum_dispatch_gas_used_at_most`), and per-block merkle-root commitment work for each such message, while relayers are paid negligibly. This matches the "public underpriced work that degrades block production or stalls bridge processing" impact category, though it is mitigated in severity by (a) the `MaxMessagesPerBlock` bound capping worst-case per-block work, and (b) the existence of the tip top-up mechanism as a market-level remediation once a message is deemed unprofitable — relayers are economically incentivized simply not to process fee=1 messages, so they don't get delivered/settled, though they still occupy queue slots and commitment work.

## Likelihood Explanation
High for triggering the underpriced-message condition itself (any unprivileged account via `snowbridge_pallet_system_v2::Pallet::send` or XCM `ExportMessage` routed through `EthereumBlobExporter::deliver` can set `fee=1`), matching the claim's likelihood assessment. No privileged actor or relayer collusion is required to *create* underpriced messages.

## Recommendation
Enforce a minimum `fee` (e.g., existential-deposit-equivalent, or a governance-configurable `MinimumOrderFee`) in `do_process_message` or in `SendMessage::validate`, rejecting messages whose fee is below the floor, rather than relying solely on the reactive `add_tip` mechanism and the `fee > 0` payout check.

## Proof of Concept
1. Call `snowbridge_pallet_system_v2::Pallet::send` (or route an XCM `ExportMessage`) constructing a `Message` with `fee = 1`.
2. `do_process_message` accepts it, storing `PendingOrder { fee: 1, .. }` [2](#0-1) .
3. Repeat up to `MaxMessagesPerBlock` times per block; each message consumes full merkle-commit/gas-metering work while only nominally satisfying the relayer-reward check in `process_delivery_receipt` [3](#0-2) .

			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
