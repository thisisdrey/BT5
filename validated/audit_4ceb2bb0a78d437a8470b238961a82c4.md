### Title
Unbounded growth of `DelegatedResourceAccountIndex.toAccounts`/`fromAccounts` lists via repeated `FreezeBalanceContract` with distinct receivers, causing linear-scan DoS on unfreeze and query paths - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
When the network parameter `allowDelegateOptimization` is not enabled (legacy delegate-index mode), every call to `FreezeBalanceContract` that delegates resources to a new receiver address appends an entry to an unbounded, single-object protobuf list (`DelegatedResourceAccountIndexCapsule.toAccountsList` / `fromAccountsList`) keyed by the owner/receiver address. There is no cap on how many distinct receiver addresses one account can accumulate, mirroring the CrabNetting `withdraws` array pattern: an attacker can call the actuator repeatedly with minimal frozen amounts and many unique receiver addresses to grow this list arbitrarily.

### Finding Description
In the legacy (non-optimized) delegate path of `FreezeBalanceActuator.delegateResource`, the owner's and receiver's `DelegatedResourceAccountIndexCapsule` are fetched, and a new entry is appended to `toAccountsList` / `fromAccountsList` for every new distinct counterparty, with only a `contains()` de-duplication check but no maximum size enforcement: [1](#0-0) 

The underlying capsule stores these as flat repeated fields with simple add/remove helpers and no bound: [2](#0-1) 

This list is later consumed in two ways that scale linearly (or worse) with its size:
1. `UnfreezeBalanceActuator`, when releasing a fully-unfrozen delegation, copies the full list into an `ArrayList`, performs a linear `remove(...)`, and rewrites the entire capsule back to the store: [3](#0-2) 
2. The wallet/API query path (`Wallet.getDelegatedResourceAccountIndex`, exposed via gRPC/HTTP) reads and serializes the entire list back to callers, so a bloated index directly inflates response size and processing cost for every query against that address.

Because `FreezeBalanceContract` is a standard, low-cost, unprivileged transaction type (only requiring the attacker's own balance to freeze a minimal amount, e.g. `1 TRX` per call, to a new throwaway receiver address each time), an attacker can drive this array to an arbitrary size over many blocks. Unlike `UnfreezeBalanceV2`/`FreezeBalanceV2` (the newer resource model), which uses per-pair store keys (`DelegatedResourceAccountIndexStore.delegateV2`/`convert`) instead of a single growing array, the legacy path retains the vulnerable pattern shown in the audited CrabNetting contract: unbounded appends to a list that is later linearly scanned/rewritten.

### Impact Explanation
As the index list for a targeted address grows unbounded:
- Every subsequent `UnfreezeBalanceContract` that finalizes a delegation to/from that address must deserialize, copy, linearly scan, and rewrite the entire (growing) list — degrading with size and eventually risking exceeding the block's energy/processing budget for that transaction, effectively locking users out of unfreezing (denial of service on withdrawal), directly analogous to the reported `dequeueCrab` DoS.
- Read APIs (`getDelegatedResourceAccountIndex` via `TronJsonRpcImpl`/`Wallet`) serving this data to any anonymous API client would return increasingly large payloads and consume increasing node resources per request, degrading the affected query path.
- The capsule is rewritten wholesale on each update (`this.delegatedResourceAccountIndex = ... .build()`), so update cost also grows with list size, worsening over time as more delegate/undelegate operations are targeted at the poisoned address.

### Likelihood Explanation
This is reachable purely through routine, unprivileged `FreezeBalanceContract` transactions signed by any account, requiring no special privilege — the constraint is only that `allowDelegateOptimization` (a committee-controlled chain parameter) must not be enabled, which gates whether the legacy unbounded-array code path is active versus the newer keyed-store (`delegateV2`) path. On chains/forks where this parameter has not been turned on (or during any window before it is proposed/activated), the vulnerable legacy path is fully exercised by ordinary users, making exploitation straightforward and cheap (minimal frozen amounts, many throwaway receiver addresses).

### Recommendation
Replace the flat repeated-field `toAccounts`/`fromAccounts` lists with a keyed/paginated store design (as already implemented for the V2 delegate path via `DelegatedResourceAccountIndexStore.delegateV2`/`convert`, which stores each delegation under its own DB key), and retire or cap the legacy in-object list growth path (e.g., enforce a maximum number of tracked counterparties per account, or force delegate optimization to be always-on rather than parameter-gated) to eliminate the unbounded per-account array and the linear rewrite/scan pattern on unfreeze.

### Proof of Concept
1. On a network/fork where `allowDelegateOptimization` is not yet enabled (default `0` unless activated by committee proposal), have attacker account `A` send repeated `FreezeBalanceContract` transactions with `receiver_address` set to a freshly generated address each time and a minimal `frozen_balance` (e.g., `1_000_000` sun) and `resource=BANDWIDTH`/`ENERGY`.
2. Each transaction executes `FreezeBalanceActuator.delegateResource`, appending a new entry into `A`'s `DelegatedResourceAccountIndexCapsule.toAccountsList` (and the corresponding receiver's `fromAccountsList`), as shown in [4](#0-3) , with no upper bound check.
3. Repeat thousands of times (feasible given the low per-call resource cost) to grow the list to a size where the linear `remove`/rewrite in `UnfreezeBalanceActuator` ( [3](#0-2) ) or the full-list serialization in `Wallet.getDelegatedResourceAccountIndex` becomes measurably expensive, degrading unfreeze processing and query latency for the targeted address.
