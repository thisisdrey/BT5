### Title
StackerDB chunk signatures omit the target contract identifier, enabling cross-StackerDB chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` binds a StackerDB chunk signature only to `slot_id`, `slot_version`, and `data_hash` — never to the `QualifiedContractIdentifier` of the StackerDB it is written to. Because the `.signers-{set}-{msg}` StackerDB contracts for the same reward-cycle parity all reuse the identical signer→slot_id assignment, a chunk validly signed by a signer for one `.signers` StackerDB (e.g. BlockResponse) can be replayed verbatim by any unprivileged peer into a sibling `.signers` StackerDB (e.g. StateMachineUpdate or BlockPreCommit) where that signer occupies the same slot, and it will pass all authenticity checks.

### Finding Description
`SlotMetadata::auth_digest()` computes the signed message as `sha512/256(slot_id || slot_version || data_hash)`, with no domain separator for which StackerDB/contract the chunk belongs to: [1](#0-0) 

Both the chunk-write authorization path (`StackerDBTx::try_replace_chunk`) and the sync/gossip validation path (`StackerDBs::validate_received_chunk`, used by both `StackerDBSync::validate_downloaded_chunk` and `handle_unsolicited_StackerDBPushChunk`) authenticate a chunk purely by checking that `SlotMetadata::verify()` recovers to the address configured as the owner of that `slot_id` *in that particular contract* — they never verify that the signature was produced for this specific contract instance: [2](#0-1) [3](#0-2) 

The RPC write path (`RPCPostStackerDBChunkRequestHandler`) accepts any contract identifier and chunk from an unauthenticated remote peer and calls `try_replace_chunk` directly: [4](#0-3) 

The signer-slot assignment scheme guarantees that the *same* signer occupies the *same* `slot_id` across every `.signers-{set}-{msg}` contract for a given reward-cycle parity, since all such contracts read from the same shared slot list (`stackerdb-get-signer-slots-page`): [5](#0-4) 
and the different StackerDB contracts (`BlockResponse`, `StateMachineUpdate`, `BlockPreCommit`) are just different `msg_id` suffixes of the same signer contract family, keyed only by reward cycle and message id: [6](#0-5) 

Because the signature covers none of this contract-identifying context, a chunk `(slot_id=I, slot_version=V, sig, data=D)` legitimately produced and gossiped by signer `S` for `.signers-X-1` remains a byte-for-byte valid, verifiable chunk for `.signers-X-2` or `.signers-X-3` at the same `slot_id=I`, since `S` owns that slot in all three contracts and `auth_digest()` is identical in both contexts. This is the direct analog of the reported bug class: an authentication value (here, a signature; there, a "random" derived value) is computed over an incomplete view of the context it is meant to bind to, so a valid tuple for one context can be transplanted into another and still validate.

### Impact Explanation
Any unprivileged peer that observes a chunk broadcast via `StackerDBPushChunk` gossip, or fetched via the public read RPC, can replay it into a sibling StackerDB contract (same reward cycle, different message type) that the honest signer also participates in, as long as the replayed `slot_version` exceeds the sibling contract's currently stored version for that slot. This is an unauthenticated write into StackerDB state that the attacker does not hold signing authority for in that specific context:
- It can be used to squat/poison a victim signer's slot in a sibling StackerDB, forcing the honest signer to notice and bump the version to reclaim it (denial-of-service on legitimate signer publishing).
- The relaying node will then re-broadcast the forged-context `StackerDBPushChunk` to its neighbors via `process_stacker_db_chunks`, propagating the misattributed data network-wide: [7](#0-6) 
- Downstream consumers that key trust purely off "recovered signer address for this slot" (e.g. `StackerDBListener`'s state-machine evaluator, which associates a `StateMachineUpdate` chunk with the recovered signer's address) can be fed attacker-chosen bytes under an honest signer's identity in a StackerDB they never intended to write: [8](#0-7) 

### Likelihood Explanation
No secret key, admin role, or bandwidth flood is required — only the ability to observe one legitimately gossiped/queryable chunk and re-submit it (via the standard `POST /v2/stackerdb/{contract}/chunks` RPC or a crafted `StackerDBPushChunk` p2p message) to a different, publicly known sibling contract for the same reward cycle. The slot-assignment mapping needed to find a matching `slot_id` in the sibling contract is derived from public on-chain `.signers` state.

### Recommendation
Include the target `QualifiedContractIdentifier` (or an equivalent per-StackerDB domain separator) in `SlotMetadata::auth_digest()` so a signature is only valid for the specific StackerDB it was created for, mirroring the GHSA-7p92-x423-vwj6 fix of hashing the complete relevant transcript state instead of a partial/context-free subset. Update `sign`/`verify` call sites in `libstackerdb`, `stackslib/src/net/stackerdb/*`, and any serialization compatibility path accordingly.

### Proof of Concept
1. Signer `S` (address `A`) legitimately signs and publishes `StackerDBChunkData{slot_id: I, slot_version: V, sig, data: D}` to `.signers-X-1` (BlockResponse contract) for reward cycle `X`; the chunk is observable via p2p gossip (`StackerDBPushChunk`) or the public read endpoint.
2. Attacker (no private key needed) reads the shared `.signers` slot table and confirms `A` also owns `slot_id = I` in `.signers-X-2` (StateMachineUpdate contract) for the same reward cycle, and that `.signers-X-2` slot `I`'s currently stored version is `< V`.
3. Attacker sends `POST /v2/stackerdb/.signers-X-2/chunks` with the identical `(slot_id=I, slot_version=V, sig, data=D)` copied from step 1 (`RPCPostStackerDBChunkRequestHandler`, `stackslib/src/net/api/poststackerdbchunk.rs`).
4. `SlotMetadata::verify()` recomputes `auth_digest()` = `sha512/256(I || V || hash(D))`, identical to what `S` originally signed, recovers to `A`, matches `.signers-X-2`'s configured owner of slot `I` — verification succeeds and `try_replace_chunk` stores the chunk (`stackslib/src/net/stackerdb/db.rs`), overwriting whatever `S` had legitimately published there.
5. The receiving node broadcasts `StackerDBPushChunkData{contract_id: .signers-X-2, chunk_data: D}` to its neighbors via `process_stacker_db_chunks`, propagating the cross-context replay across the network.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
