### Title
`ValidateMultiSign` precompile signs over `(address, permissionId, data)` without binding to the calling contract, enabling signature replay across unrelated dApps - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `validatemultisign(address,uint256,bytes32,bytes[])` TVM precompile lets any smart contract verify off-chain, EIP-712-style multisig authorizations by recovering signer addresses from a hash it builds itself. That hash is `SHA256(accountAddress || permissionId || data)`, where `data` is an arbitrary 32-byte value chosen by the calling contract. Nothing in the signed payload binds it to the identity of the calling contract, the chain, or the purpose of the authorization, so the same signature can be replayed to satisfy `validatemultisign` in a completely different, unrelated contract.

### Finding Description
`ValidateMultiSign.execute` builds the message that signers are expected to have signed as: [1](#0-0) 

and then recovers each supplied signature against that `hash`, accumulating key weights against the target account's `Permission`: [2](#0-1) 

The three inputs that go into the signed hash — `address` (the TRON account whose permission is being checked), `permissionId`, and `data` (a caller-supplied `bytes32`) — say nothing about *which contract* is asking for the authorization. This mirrors the root cause described in the reference report: the signed proof commits to the parties and the amount/purpose payload, but not to the specific application/instance requesting the check. In `CrosschainMerkleDistributor.claimBySignature`, the missing binding was the specific airdrop/root; here it is the specific calling contract (dApp) that consumes the `validatemultisign` result.

Any TRC20/dApp built to use `validatemultisign` as an authorization mechanism (e.g., "have the active-permission signer(s) of account X approve a withdrawal of amount Y") typically derives `data` as a hash of application parameters such as amount, recipient, and a nonce. Because `permissionId` defaults to commonly reused values (e.g. owner permission `0` or a single active permission), it is realistic for two independent dApps operated by/for the same account to end up computing an identical `data` value for logically distinct actions (e.g. two contracts both computing `keccak256(amount, recipient)`) or for an attacker-controlled dApp to intentionally mirror the parameter layout of a legitimate one to induce the same `data` value. The signature obtained (or observed) for one dApp is then a fully valid signature for `validatemultisign` in the second, unrelated dApp — the precompile itself cannot distinguish the two contexts because it never mixes in the address of the contract that invoked it.

### Impact Explanation
`validatemultisign` performs on-chain permission-weight verification that dApp logic then uses to gate privileged actions (transfers, withdrawals, order execution, etc.), analogous to how `claimBySignature` gated an airdrop claim in the referenced report. A replayed authorization allows an unrelated contract to satisfy a multisig check it was never intended to satisfy, letting an attacker-controlled or copy-cat contract move funds or execute privileged operations on behalf of the account without a fresh, purpose-bound authorization — a concrete unauthorized account operation / theft-of-funds vector reachable purely by deploying a contract and issuing ordinary transactions/calls, no privileged role required.

### Likelihood Explanation
Exploitation requires only: (1) an EOA to have signed a `validatemultisign`-style proof for one dApp, and (2) a second dApp (which the attacker controls or deploys) that also calls `validatemultisign` with the same `address`/`permissionId`/`data` triple. Since `data` is fully attacker/dApp-defined and there is no requirement that it embed the consuming contract's address, an attacker can deliberately construct a dApp whose parameter-hashing scheme collides with a popular/target dApp's scheme, or simply observe and replay signatures for use cases that naturally produce colliding `data` (shared account, shared default permission, same computed hash of amount+recipient across two integrations). This is entirely reachable from ordinary contract deployment and transaction/call submission with no special privileges.

### Recommendation
Include contract-identity/domain separation in the hash that `validatemultisign` recovers signatures against — e.g., mix in the address of the calling contract (`msg.sender`/`this`, obtainable inside `ValidateMultiSign.execute` via the `Program`/call context), the chain ID, and/or an explicit protocol version/domain tag, similar to EIP-712 domain separators. This prevents a signature produced for one contract's authorization scheme from validating against an unrelated contract's `validatemultisign` call, without changing the precompile's core permission-weight semantics.

### Proof of Concept
1. Account `A` (default owner permission id `0`, threshold satisfied by a single key) signs a multisig authorization intended for DApp1: `data1 = sha256(amount=100, recipient=R)`, producing `hash = SHA256(A || 0 || data1)` and signature `sig`. DApp1 calls `validatemultisign(A, 0, data1, [sig])` to authorize a withdrawal of 100 to `R`.
2. An attacker deploys DApp2, whose parameter-hashing convention happens to (or is engineered to) compute the identical `data2 = sha256(amount=100, recipient=R) == data1` for a different action (e.g., approving a different kind of transfer or an order fill).
3. Attacker submits `sig` (captured from DApp1's transaction log, since TRON transactions/inputs are public) to DApp2's function, which internally calls `validatemultisign(A, 0, data1, [sig])`.
4. `ValidateMultiSign.execute` recomputes the same `hash`, recovers the same signer, and returns success (`dataOne()`), because nothing in the precompile's hash construction (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1062-1064`) ties the check to DApp1 specifically — DApp2 accepts an authorization never intended for it.
