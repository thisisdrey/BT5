## Title
Missing Defensive Error Handling for Oracle Price Resolution Causes Total DoS of Liquidation, Borrow, and Withdraw - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
Every price lookup in `v0-4-market.clar` is resolved through `price-resolve`, which propagates any failure from the underlying Pyth/DIA calls straight through `try!` with no fallback, and is then invoked via `unwrap-panic` in `get-assets`. There is no defensive "try/catch" (Clarity's `match`/graceful-degrade pattern) around this external call chain, so a single failing/blocked price feed reverts the entire transaction for any operation that touches that asset — including `liquidate`.

### Finding Description
`resolve-pyth` and `resolve-dia` call the external oracle contracts and immediately `unwrap!`/`try!` the result into `ERR-ORACLE-PYTH` / `ERR-ORACLE-DIA` on failure with no fallback path: [1](#0-0) 

`price-resolve` further wraps this with `try!`, so any revert from the oracle call (feed not found, feed frozen/blocked, decode failure) aborts the whole call chain rather than being caught and handled: [2](#0-1) 

`get-assets` then resolves prices for *all* assets in a user's position mask via `unwrap-panic` on `price-multi-resolve`, meaning if even one asset's oracle call fails, the entire price list resolution — and thus every function that depends on it — reverts: [3](#0-2) 

`liquidate` calls `get-assets` (via the position mask) as a mandatory step before it can compute `total-collateral-usd`/`total-debt-usd` and perform the health check: [4](#0-3) 

Since Pyth publishers/governance can withdraw a feed, and DIA (or the Pyth storage contract) can revert on a stale/missing key, this single point of failure means any borrower holding at least one collateral or debt asset whose price feed is currently failing becomes completely unliquidatable — even while deeply undercollateralized — for as long as that feed stays broken. The same `get-assets`/`price-resolve` path also gates `borrow`, `withdraw`, and `repay` health checks (via `get-asset-value`/`get-notional-evaluation`), so the same class of failure can additionally block withdrawals and repayments for affected users.

### Impact Explanation
Because liquidation is blocked for any position whose asset set includes the failing/blocked feed, bad debt on that asset can accumulate without bound while the protocol has no way to seize collateral. This constitutes temporary freezing of funds (liquidation and withdraw functionality) and risks protocol insolvency if the position continues to accrue debt or the collateral price moves further before the feed is restored — matching the in-scope "temporary freezing of funds" / insolvency impact classes.

### Likelihood Explanation
Pyth feeds can be removed/paused by Pyth governance, and the DIA oracle call is a raw external `contract-call?` that can revert for reasons outside Zest's control (e.g., stale threshold enforced by Pyth's own `read-price-with-staleness-check`, or DIA key removal). None of these require any privileged action on Zest's side or DAO compromise — an ordinary borrower's `liquidate`/`borrow`/`withdraw` call is directly affected whenever the underlying oracle infra hiccups on any asset in their position.

### Recommendation
Wrap the external oracle calls (`call-pyth`/`resolve-pyth`, `call-dia`/`resolve-dia`) in `match`/graceful-degrade logic instead of unconditional `unwrap!`/`try!`, and provide a defined fallback (e.g., using the last valid cached price for a bounded grace window, or explicitly excluding the failing asset from a health computation as debt/collateral of last resort) so a single feed outage cannot deadlock liquidation, borrowing, and withdrawal for the entire position.

### Proof of Concept
1. An asset's Pyth price feed (e.g., `PYTH-USDC`) becomes unavailable — governance removes/pauses the feed, or `pyth-storage-v4 get-price` reverts due to internal staleness enforcement.
2. A borrower holds that asset as collateral or debt and becomes severely undercollateralized (LTV > `LTV-LIQ-PARTIAL`).
3. Any liquidator calls `liquidate` on that borrower; `get-assets` → `price-multi-resolve` → `price-resolve` → `resolve-pyth` → `call-pyth` reverts with `ERR-ORACLE-PYTH`, and `get-assets`'s `unwrap-panic` aborts the transaction entirely.
4. The position cannot be liquidated until the feed is restored, during which time bad debt can grow, and other users (LPs in the affected vault) bear the risk of that debt going unrecovered.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
