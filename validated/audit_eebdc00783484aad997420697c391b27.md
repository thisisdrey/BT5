### Title
Unbounded iteration over an account's market order list in `Wallet.getMarketOrderByAccount` - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
`Wallet.getMarketOrderByAccount`, which backs the public `GetMarketOrderByAccount` HTTP/gRPC query, iterates over the **entire** `orders` list stored in a `MarketAccountOrderCapsule` with no size cap, unlike sibling market query methods that explicitly bound their work.

### Finding Description
`getMarketOrderByAccount` fetches the caller-supplied account's `MarketAccountOrderCapsule` and does an unbounded `forEach` over `marketAccountOrderCapsule.getOrdersList()`, doing a store lookup (`marketOrderStore.get`) for every entry: [1](#0-0) 

Compare this to the other market-listing RPCs in the same class, `getMarketPairList` and `getMarketOrderListByPair`, which both explicitly cap iteration with `MARKET_COUNT_LIMIT_MAX`: [2](#0-1) [3](#0-2) 

`getMarketOrderByAccount` has no equivalent limit clause, so it always processes the full list regardless of size.

Every order an account places via `MarketSellAssetActuator` appends an order id to that account's `MarketAccountOrderCapsule` through `addOrders`: [4](#0-3) 

Because placing a market order is a normal, cheap, unprivileged transaction (`MarketSellAssetContract`), any account can grow its own order list arbitrarily large by repeatedly issuing small sell orders. `MarketSellAssetActuator`'s validate/execute path (reviewed) contains no cap on the number of active orders an account may accumulate — the only bound found in the market subsystem (`MAX_MATCH_NUM`) limits matching work per transaction, not per-account order-list size.

Once such an account exists, any anonymous client can call the HTTP endpoint `GetMarketOrderByAccountServlet` (or the equivalent gRPC `GetMarketOrderByAccount`), which calls `wallet.getMarketOrderByAccount` directly with no pagination or limit parameter: [5](#0-4) 

This forces the node to walk and deserialize the full order list (and perform a store lookup per order) on every single request for that account, which is the same "unbounded iteration over all indexes" bug class as the referenced PoolTemplate finding — attacker-inflatable list size directly drives the work done per query/transaction.

### Impact Explanation
An attacker can cheaply inflate their own account's order-id list to an arbitrarily large size, then repeatedly hit the public `GetMarketOrderByAccount` HTTP/gRPC endpoint for that account. Each call forces the full node to perform O(n) store reads/deserializations with no upper bound, which can be used to consume node CPU/IO resources and degrade or deny availability of this query path for other users — matching the "API the node can no longer serve" impact category. This does not require any protocol/consensus-level exploit and requires only a normal signed transaction plus a normal API request.

### Likelihood Explanation
Likelihood is high: placing many market sell orders is a routine, low-cost, unprivileged transaction (`MarketSellAssetContract`) available to any account, and the vulnerable query endpoint is a standard, unauthenticated public API (`GetMarketOrderByAccountServlet` / gRPC `GetMarketOrderByAccount`) that any client can call repeatedly.

### Recommendation
Add a limit/pagination parameter to `getMarketOrderByAccount` analogous to `MARKET_COUNT_LIMIT_MAX` used in `getMarketPairList`/`getMarketOrderListByPair`, capping the number of orders processed and returned per call, and/or enforce a maximum number of concurrently active orders per account in `MarketSellAssetActuator`'s validation logic.

### Proof of Concept
1. From a funded account, repeatedly submit `MarketSellAssetContract` transactions (small sell quantities) to grow that account's `MarketAccountOrderCapsule.orders` list to a large size (e.g., tens of thousands of entries) — each call appends via `MarketAccountOrderCapsule.addOrders` with no cap enforced by `MarketSellAssetActuator`.
2. Call the public HTTP endpoint `GET /wallet/getmarketorderbyaccount?value=<attacker_address>` (or the gRPC `GetMarketOrderByAccount` RPC) repeatedly.
3. Observe that each request causes `Wallet.getMarketOrderByAccount` to iterate the full unbounded order list and perform a `marketOrderStore.get` per order, consuming node resources proportional to the attacker-controlled list size, unlike the capped `getMarketOrderListByPair`/`getMarketPairList` calls.
