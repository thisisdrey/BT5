### Title
`Pool.liquidate` CHECK-fail dead zone: `maxLiquidable` cap combined with `debtFloorInUsd` makes unhealthy positions permanently un-liquidatable - ([File: contracts/Pool.sol])

### Summary
The upstream bug is a `CHECK` failure: a malformed input shape triggers a hard assertion that DoSes the op. The Metronome analog is a hard-revert dead zone in `Pool.liquidate`: for any account whose debt (in USD) falls into `(debtFloorInUsd, 2 * debtFloorInUsd)`, **every** possible `amountToRepay_` input hits one of two revert guards, so the function fails on all inputs. Liquidations of such positions are permanently bricked, guaranteeing bad debt accrual and protocol insolvency.

### Finding Description
`liquidate` enforces two independent bounds on the caller-chosen `amountToRepay_`:

1. **Upper bound** — repay cannot exceed `maxLiquidable` (default 50%) of the account's debt:
   `if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) revert AmountGreaterThanMaxLiquidable();` [1](#0-0) 

2. **Lower bound via floor** — the *remaining* debt must be either 0 or ≥ `debtFloorInUsd`:
   `if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) revert RemainingDebtIsLowerThanTheFloor();` [2](#0-1) 

For a position with total debt `D` (in USD) such that `debtFloorInUsd < D < 2 * debtFloorInUsd`:

- Full repayment (`amountToRepay_ = D`) requires `wadDiv = 1e18 > maxLiquidable = 0.5e18` → `AmountGreaterThanMaxLiquidable`.
- Any allowed partial repayment `amountToRepay_ ≤ 0.5 * D` leaves remaining debt `D - amountToRepay_ ≥ 0.5 * D`, which is `> 0` and `< debtFloorInUsd` → `RemainingDebtIsLowerThanTheFloor`.

There is no input that satisfies both checks — an unconditional CHECK-fail on every call. The same deadlock does **not** exist on the voluntary path: `DebtToken.repay` has the floor check but no `maxLiquidable` cap [3](#0-2) , and `repayAll` bypasses the floor entirely [4](#0-3) . Only the incentivized liquidation path is deadlocked, and no liquidator will repay debt for free.

An attacker can deliberately manufacture this state permissionlessly: deposit collateral, `DebtToken.issue` a debt just above `debtFloorInUsd` (the `_mint` floor check only requires `balanceBefore + amount_ >= floor` [5](#0-4) ), then let the collateral price drift down (or nudge it within the same-block oracle tolerance) until the position is unhealthy. From that point `liquidate` reverts on all inputs while interest keeps accruing via `_calculateInterestAccrual` [6](#0-5) .

### Impact Explanation
Protocol insolvency. `liquidate` is the only profitable mechanism for clearing underwater debt; once a position enters the dead zone it can never be liquidated, while its debt keeps growing with accrued interest and its collateral keeps losing value. The shortfall is socialized across the pool as bad debt. This is reachable with `maxLiquidable = 0.5e18` (the value set in `initialize` [7](#0-6) ) and any nonzero `debtFloorInUsd` — both live configuration values, not hypothetical governor mistakes.

### Likelihood Explanation
Medium. Reachability is permissionless: any EOA can open a debt position sized into the dead zone via `DebtToken.issue`, and normal market movement (allowed: same-transaction oracle moves) tips it unhealthy. The only prerequisite is `debtFloorInUsd > 0`, which is a deployed-config value on Metronome pools. Positions can also fall into the zone organically via interest accrual shrinking headroom, so the trap exists even without an attacker deliberately engineering it.

### Recommendation
In `Pool.liquidate`, relax one of the two checks when they conflict: e.g. allow `amountToRepay_` up to the full debt balance when `D - maxLiquidable * D < debtFloorInUsd` (i.e. permit full-repayment liquidation for sub-2×floor positions), or skip the `RemainingDebtIsLowerThanTheFloor` check when `amountToRepay_ == _debtTokenBalance` and the `maxLiquidable` cap is what blocks it. Concretely, compute `_maxLiquidable = max(_debtTokenBalance.wadMul(maxLiquidable), minAmountThatClearsFloorOrRepaysAll)` so every unhealthy position has at least one valid liquidation input.

### Proof of Concept
Hardhat sketch against the existing fixtures (`test/` E2E setup provides pool, depositToken, debtToken, msUSD):

```ts
// governor config: debtFloorInUsd = $1_000, maxLiquidable = 0.5e18 (default)
// 1. Alice deposits collateral worth ~$4,000, issues debt of $1,500 (dead zone: 1000 < 1500 < 2000)
await depositToken.deposit(parseEther('4'), alice.address)
await debtToken.issue(usd('1500'), alice.address)

// 2. Collateral price drops (or alice's position is pushed unhealthy via oracle update)
await setCollateralPrice(/* lower */)
expect((await pool.debtPositionOf(alice.address))._isHealthy).to.eq(false)

// 3. Liquidator tries every possible amountToRepay — all revert
const debt = await debtToken.balanceOf(alice.address)
await expect(
  pool.connect(liq).liquidate(msUSD.address, alice.address, debt, depositToken.address)
).to.be.revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable')

await expect(
  pool.connect(liq).liquidate(msUSD.address, alice.address, debt.div(2), depositToken.address)
).to.be.revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor')

// any partial amount in (0, debt/2] also reverts with RemainingDebtIsLowerThanTheFloor
// position is permanently un-liquidatable -> guaranteed bad debt
```

Uncertain points: I verified the guard logic in `Pool.sol`/`DebtToken.sol` but did not check whether `quoteLiquidateMax`/`maxLiquidable` or the `SmartFarmingManager` flash-liquidation path provides an escape hatch that repays full debt; `flashRepay` routes back through `debtToken` repay/burn rather than `Pool.liquidate`'s seize path, which likely leaves the incentive-less deadlock intact, but a full PoC run would be needed to confirm no keeper-side workaround exists.
