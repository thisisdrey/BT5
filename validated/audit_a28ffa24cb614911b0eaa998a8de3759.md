### Title
Buffer over-read parsing untrusted ZIP central directory entries in ijar - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in the ijar ZIP reader parses attacker-controlled length fields (`file_name_length`, `extra_field_length`, `file_comment_length`, and ZIP64 extra-field `data_size`) taken directly from a ZIP file's central directory and advances/dereferences the input cursor `p` based on those values without ever calling the `EnsureRemaining()` bounds check that every other parsing path in the same file (`ProcessLocalFileEntry`, `SkipFile`, `ProcessFile`, `UncompressFile`) uses before reading or skipping data.

### Finding Description
`InputZipFile` memory-maps an input ZIP/JAR file and walks the on-disk central directory records via `ProcessCentralDirEntry` (`third_party/ijar/zip.cc` lines 493-545). Contrast this with `ProcessLocalFileEntry` (lines 332-418), which validates every field read with `EnsureRemaining(n, "state")` — a helper that checks the cursor offset against `input_file_->Length()` before any pointer advance (lines 158-170) — and with `SkipFile`/`ProcessFile`, which do the same before skipping/reading file data (lines 420-479).

`ProcessCentralDirEntry` has no such checks: [1](#0-0) 
- It reads `file_name_length`, `extra_field_length`, `file_comment_length` as raw `u2` values straight from attacker-controlled bytes.
- It computes `len = min(file_name_length, filename_size-1)` and does `memcpy(filename, p, len)` — this specific memcpy is bounded to the fixed-size `filename[PATH_MAX]` output buffer, but `p` itself is advanced by the full unchecked `file_name_length` afterward: `p += file_name_length;` with no verification that `p` stays inside the mapped file.
- The subsequent extra-field loop is worse: [2](#0-1) 
This loop reads `header_id`/`data_size` via `get_u2le(extra_p)` (which itself unconditionally dereferences 2 bytes at `extra_p` and advances it) and, for the ZIP64 tag, calls `get_u8le(extra)` to read 8 bytes from `extra`, all driven purely by attacker-supplied `extra_field_length`/`data_size` values with **no check that `extra_p`, `extra`, or the 2/8-byte reads stay within `zipdata_in_ .. zipdata_in_ + input_file_->Length()`**. If `extra_field_length` (attacker-controlled, up to 0xFFFF) or a nested `data_size` field is crafted to run past the actual mapped file/central-directory bytes, `get_u2le`/`get_u8le`/`get_u4le` will read out-of-bounds memory adjacent to the `mmap`'d region — a classic buffer over-read, directly analogous to vim's `find_next_quote` over-read on hostile input (CVE-2022-1629), except here the "content" is a maliciously crafted archive consumed by an unprivileged victim's build rather than a text file opened in an editor.

This differs categorically from the already-hardened `ProcessLocalFileEntry`/`EnsureRemaining` path, showing the omission in `ProcessCentralDirEntry` is a genuine gap rather than intended design; the surrounding comment even claims ("Note that the central directory is always followed by another data structure that has a signature, so parsing it this way is safe") an invariant that is not actually enforced for the length-driven `extra_field`/`file_comment`/`file_name` skips.

### Impact Explanation
`InputZipFile`/ijar is used to parse ZIP/JAR archives that are not necessarily produced by the trusted root repository — e.g., prebuilt `.jar` files fetched via `http_archive`/`http_jar`/Maven-style external dependencies and then processed by the `ijar` tool to generate interface jars during the build. A hostile origin server or mirror serving such a jar (or an attacker-controlled dependency in an untrusted branch that CI builds) can craft a central directory entry with an oversized `extra_field_length`/nested ZIP64 `data_size` to make the parser read memory beyond the mapped file. Depending on heap/mmap layout this can crash the `ijar` process (denial of service) or leak adjacent process memory into the crafted interface jar's derived filename/attribute fields, which could influence build outputs. This is a genuine memory-safety defect in native C++ code that processes untrusted, dependency-supplied bytes, matching the bug class of the reference CVE.

### Likelihood Explanation
Reachability requires only that a build depend on an external, unprivileged-attacker-served jar/zip archive processed by `ijar` (a routine occurrence for Java targets using `java_import`/`http_jar`/Maven-resolved jars) — no privileged access, MITM position, or trusted-root Starlark control is needed. Because `sha256`/integrity checks (when present) verify the *whole file* before extraction, they do not prevent an attacker who legitimately controls the served artifact's bytes (e.g., publishes a new/matching version, or the checksum is intentionally omitted, which `http_archive` explicitly permits) from crafting a ZIP with these specific malformed central-directory length fields, since checksum verification says nothing about the internal structural validity of the ZIP fields being parsed.

### Recommendation
Add `EnsureRemaining()` (or an equivalent bounds check against `zipdata_in_ + input_file_->Length()`) before every pointer advance/read in `ProcessCentralDirEntry`, including: after reading `file_name_length`/`extra_field_length`/`file_comment_length` and before `p += file_name_length`, `p += extra_field_length`, `p += file_comment_length`; and inside the extra-field loop, validate that `extra_p + 4` (for the tag+size fields) and `extra_p + data_size` never exceed the mapped-file end before dereferencing `get_u2le`/`get_u8le`/`get_u4le`.

### Proof of Concept
A reproducible test can be added alongside the existing ijar zip tests (e.g. `third_party/ijar/test/zip_test.sh` or a new `InputZipFileTest` in the `third_party/ijar` test tree) that:
1. Crafts a minimal valid EOCD + one central directory header whose `extra_field_length` (or comment_length) is set to a large value (e.g. 0xFFFF) while the actual file is truncated shortly after the CDH, i.e. the extra-field/comment bytes claimed do not exist in the mapped file.
2. Invokes `ZipExtractor::Create()`/`ProcessAll()` (as done in `third_party/ijar/zip_main.cc`'s `extract()`/`DetermineArchiveContents` style call, or via `PartialZipExtractor::UnzipUntil` in `src/main/cpp/archive_utils.cc`) on this crafted file.
3. Observes (under ASan/valgrind) an out-of-bounds heap/mmap read triggered inside `ProcessCentralDirEntry`'s extra-field loop, rather than a clean `EnsureRemaining`-style error message, demonstrating the missing bounds check. [3](#0-2) [4](#0-3)

```text
  // abort with an error message.  "state" is the name of the field
  // we're about to read, for diagnostics.
  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
  }
```

```text
bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
```
