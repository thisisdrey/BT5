### Title
`redeem` skips the live-decimals drift check enforced by `mint`, letting stale decimal scaling mis-price PSM payouts - (File: substrate/frame/psm/src/lib.rs)

### Summary
`pallet-psm` was built specifically to fix the Fei-style "decimals not accounted for" class of bug by scaling between an internal stablecoin and external assets using per-asset decimal snapshots [1](#0-0) . `mint` protects itself against snapshot drift by calling `ensure_decimals_match`, which halts with `Error::DecimalsMismatch` if live asset metadata no longer agrees with the decimals recorded at registration [2](#0-1) . `redeem`, however, reads the stored snapshot values directly and performs the external-asset payout calculation without ever re-validating them against live metadata [3](#0-2) .

### Finding Description
`mint` obtains `(ext_decimals, internal_decimals)` through `Self::ensure_decimals_match(&info, &internal_asset, &external_asset, &external)?`, a call that is documented to return `Error::DecimalsMismatch` "if live decimals diverged from the snapshot taken at registration" [4](#0-3) .

`redeem` bypasses this entirely:
```
let ext_decimals = external.decimals;
let internal_decimals = info.internal_decimals;
``` [5](#0-4) 
It then feeds these unchecked, potentially stale values straight into `internal_to_external` to compute `external_out`, which is the exact amount transferred out of the PSM reserve to the caller [6](#0-5) .

Because both entry points share the same `ExternalAssets` snapshot storage but only one of them re-validates it against the live fungibles metadata, a permissionless-asset owner can:
1. Register their own asset (Asset Hub supports permissionless asset creation) as an approved external for a PSM at some initial `decimals` value, establishing the `AssetDecimals`/`ExternalAssets.decimals` snapshot used for scaling.
2. As the asset's metadata admin, later call `pallet_assets::set_metadata` to change the live `decimals` value of that same asset — a capability that belongs to the asset owner, not to PSM governance, and is therefore outside the "privileged admin abuse" exclusion for the PSM instance itself.
3. Call `redeem` on the PSM: `mint` on this same drifted asset would be rejected with `DecimalsMismatch`, but `redeem` has no such gate and will still compute `external_out` using the stale scaling factor derived from the outdated snapshot decimals — the very same class of "conversion computed with the wrong decimals count" defect described in the Fei report, just isolated to one of the two dispatchable paths instead of all of them.

This directly reproduces the external report's root cause — an amount-conversion routine that trusts a decimals value without re-confirming it is still valid at the time of the transfer — except here the codebase demonstrably knows this check is required (it is implemented for `mint`) yet omits it for `redeem`.

### Impact Explanation
If live decimals drift (whether via the asset-owner path above, or via any future migration/registration edge case), `redeem` will settle external-asset amounts to the reserve/caller based on incorrect scaling while `mint` would have refused the same asset. This can result in the PSM reserve paying out either far more or far less external asset than the internal amount burned actually warrants — a direct fund-loss/fund-lock condition on PSM-held collateral, reachable without any Devin-excluded actor (no malicious validator, relayer, or PSM admin required; only the ordinary permission an asset creator already has over their own asset's metadata).

### Likelihood Explanation
Likelihood depends on how PSM external assets are onboarded. Where external assets are permissionless (self-created stablecoin-like assets on Asset Hub), the asset owner already controls `set_metadata`, so triggering the drift condition is entirely within an ordinary user's capability once their asset is approved on a PSM instance. Where onboarding is restricted to well-known assets (USDC/USDT) whose decimals virtually never change, the practical likelihood is much lower, but the code path itself provides no defense-in-depth regardless of onboarding policy — the asymmetry between `mint`'s guard and `redeem`'s lack of one is a genuine logic gap, not a theoretical one.

### Recommendation
Route `redeem` through the same `ensure_decimals_match` check that `mint` uses (or a read-only variant of it) before computing `external_out`, so both mint and redeem paths fail closed with `Error::DecimalsMismatch` whenever live metadata has drifted from the registration snapshot, instead of only enforcing this on one of the two dispatchables.

### Proof of Concept
1. `create_psm` for an internal asset with 6 decimals.
2. Attacker creates their own external asset `X` (self-administered, 6 decimals) and gets it approved via `add_external_asset`, snapshotting `ext_decimals = 6`.
3. Attacker `mint`s a modest amount of internal stablecoin against `X`, both operations pass since decimals match.
4. Attacker (as `X`'s metadata admin) calls `pallet_assets::set_metadata` to change `X`'s live decimals to a different value.
5. Attacker calls `mint` again with `X` — reverts with `Error::DecimalsMismatch` as expected, confirming the guard exists and functions [7](#0-6) .
6. Attacker calls `redeem` for the internal amount minted in step 3 — this succeeds and settles `external_out` computed via `internal_to_external(internal_net, ext_decimals, internal_decimals)` using the untouched stale snapshot decimals, with no equivalent drift check ever invoked [8](#0-7) , demonstrating that `redeem` operates on a decimals assumption `mint` would have refused to trust.

			ensure!(current_debt >= effective_internal_net, Error::<T>::InsufficientReserve);
