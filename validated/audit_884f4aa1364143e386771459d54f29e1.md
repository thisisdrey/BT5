### Title
Unrestricted Unicode bytes allowed in contract/account names enable IDN-homograph and RTLO-based transaction/contract spoofing - (File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java)

### Summary
Java-tron enforces printable-ASCII, readable-character restrictions on asset names, token abbreviations, and account IDs via `TransactionUtil.validReadableBytes` (bytes must be in `0x21`–`0x7E`), but it deliberately omits this restriction for two other user-controlled, wallet/explorer-rendered identity fields: the `AccountUpdateContract.account_name` field (checked only for length via `validAccountName`/`validBytes`) and the smart-contract `SmartContract.name` field set at deployment (checked only for length via `VMActuator.checkContractNameLength`). Any unprivileged account holder or contract deployer can therefore set an account or contract "display name" containing arbitrary Unicode bytes, including Unicode bidirectional-override control characters (e.g. U+202E RIGHT-TO-LEFT OVERRIDE) or homoglyph characters that visually impersonate ASCII names, exactly the bug class described in CVE-2019-6795 (IDN homographs and RTLO characters rendered without visual distinction, enabling social engineering).

### Finding Description
`AssetIssueActuator.validate()` calls `TransactionUtil.validAssetName`/`validTokenAbbrName`, which route through `validReadableBytes`, rejecting any byte outside the printable ASCII range. `SetAccountIdActuator`/account-id validation similarly uses `validAccountId` → `validReadableBytes`. However:

- `UpdateAccountActuator.validate()` only calls `TransactionUtil.validAccountName(accountName)`, which calls `validBytes` — this only enforces a max length of 200 bytes (or emptiness) and does not restrict the byte/character content at all.
- `VMActuator.checkContractNameLength()`, invoked from `create()` when deploying a smart contract via `CreateSmartContract`, only checks that the protobuf-encoded name is not longer than 32 bytes; it performs no character filtering. The project's own test (`ContractNameValidationTest.countsMultibyteNameUsingProtobufBytesAfterActivation`) demonstrates that even non-ASCII multibyte content (Chinese characters) is accepted as long as the byte-length limit is respected.

Both `account_name` and smart contract `name` are attacker-controlled strings included directly in broadcastable, signed transactions (`AccountUpdateContract`, `CreateSmartContract`) that reach `Manager`/actuator execution with no further sanitization, and are subsequently exposed through Wallet query APIs and JSON-RPC/HTTP responses for rendering by wallets, block explorers, and other clients. An attacker can encode a name containing an RTLO character to reverse the visual order of subsequent characters (e.g., making `"eltit dooG"` display as `"Good title"` reversed, or spoofing a legitimate account/contract's visible name) or use homoglyph characters (Cyrillic/Greek look-alikes) that are visually indistinguishable from a targeted legitimate account or token-contract name, while the underlying bytes (and thus the address the wallet actually resolves/signs against) differ.

### Impact Explanation
This can be leveraged for social engineering that leads to concrete loss of funds: a user could be tricked into sending TRX/TRC-10/TRC-20 assets or approving a contract interaction with a malicious account or contract that visually appears identical, in explorers or wallet UIs that render the raw `account_name`/contract `name` field, to a trusted counterpart (exchange deposit account, well-known DApp, etc.). Because the on-chain identity is still the attacker's own address, this constitutes a phishing/spoofing primitive that can result in unauthorized transfers of funds to the attacker-controlled account, satisfying the "concrete unauthorized account operation / theft of funds" impact bar.

### Likelihood Explanation
Likelihood is high for the account-name case: any account holder can call `AccountUpdateContract` (subject only to `getAllowUpdateAccountName`/uniqueness checks) to set a spoofed name, with no special privileges required. For contract names, any address can deploy a `CreateSmartContract` transaction with a crafted `name` field, again requiring no special privilege beyond normal transaction broadcast and paying the deployment fee/energy.

### Recommendation
Apply the same readability/charset restriction already used for asset names and account IDs (`TransactionUtil.validReadableBytes`, restricting to printable ASCII `0x21`–`0x7E`, or an explicit Unicode bidi-control/blacklist filter if broader Unicode support is desired) to `TransactionUtil.validAccountName` and to `VMActuator.checkContractNameLength`/the smart-contract name field, rejecting bytes/code points such as U+202E, U+202D, and other bidirectional format characters, and consider normalizing/flagging confusable homoglyph sequences before allowing the name to be persisted or rendered.

### Proof of Concept
1. 2. 3. Equivalently, craft a `CreateSmartContract` transaction whose `SmartContract.name` field contains a homoglyph string resembling a popular token/DApp contract name (≤32 bytes, e.g. using Cyrillic look-alike characters); `VMActuator.checkContractNameLength` (actuator/src/main/java/org/tron/core/actuator/VMActuator.java:467-475) only enforces byte length and accepts it, as confirmed by the existing `ContractNameValidationTest` in the repo showing acceptance of non-ASCII 32-byte names.
