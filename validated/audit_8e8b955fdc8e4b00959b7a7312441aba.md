### Title
Argument injection via unsanitized `remote` field in `FindRemoteRepository` RPC - (File: internal/gitaly/service/remote/find_remote_repository.go)

### Summary
`FindRemoteRepository` passes the fully attacker/user-controlled `FindRemoteRepositoryRequest.remote` field directly into the `Args` slot of a `gitcmd.Command` invocation of `git ls-remote`, rather than the `PostSepArgs` slot that Gitaly's own command-construction code explicitly reserves for untrusted positional input. This mirrors the oracle bug's root cause — external/untrusted input is consumed and trusted without the validation that the surrounding framework itself documents as required.

### Finding Description
`FindRemoteRepository` builds the git invocation like this: [1](#0-0) 

`req.GetRemote()` is placed into `Command.Args`, and `Args` documents its own unsafe usage explicitly: [2](#0-1) 

The `Args` field's doc explicitly warns: "these arguments must not be flags and thus cannot start with `-`... it may be unsafe to use this field in the case where arguments are directly user-controlled. In that case it is advisable to use `PostSepArgs` instead." `PostSepArgs` places a `--` separator before the values so that Git treats everything after it strictly as positional, never as an option. `find_remote_repository.go` does not use `PostSepArgs`, so if `req.GetRemote()` begins with `-`, Git will parse it as a flag to `git-ls-remote(1)` rather than as the repository/URL argument, and `"HEAD"` shifts to be interpreted differently as well.

`git-ls-remote` supports options such as `--upload-pack=<path>`, which specifies the executable Git invokes to service the "remote" side of the protocol. For local/file transports this can cause Git to directly execute an attacker-supplied path, and combined with attacker control over `remote` (and potentially other fields on comparable RPCs), this is the same class of "insufficiently validated external input trusted for a security-relevant decision" that the oracle report flags — except here the consequence is option/argument injection into a locally-spawned Git subprocess rather than a stale price.

This is directly comparable in shape to `CreateRepositoryFromURL`'s `cloneFromURLCommand`, which similarly accepts a raw URL string and passes it as a positional `Args` entry to `git clone` (also without `PostSepArgs`), though `url.Parse` at least forces a syntactically valid URL there, reducing (but not eliminating) the same class of risk: [3](#0-2) [4](#0-3) 

`FindRemoteRepository`, in contrast, performs **no** validation whatsoever on `req.GetRemote()` beyond checking it is non-empty: [5](#0-4) 

### Impact Explanation
`FindRemoteRepository` is an accessor RPC reachable by any client permitted to call Gitaly's `RemoteService` (e.g., GitLab's "check connection"/mirror-import validation flow, which is triggered by an ordinary project owner configuring a remote/import URL — an unprivileged, user-supplied RPC field per the analog rules). A crafted `remote` value beginning with `-` can be parsed by `git-ls-remote(1)` as a command-line option instead of a repository locator. Depending on which options are reachable in this argument position (e.g., `--upload-pack=<path>`), this can result in Gitaly's git subprocess invoking an attacker-chosen executable, i.e., argument injection escalating to command execution on the Gitaly host — a direct violation of the RPC's intended read-only/accessor scope.

### Likelihood Explanation
Likelihood is high for an ordinary, authenticated GitLab user who can trigger repository-URL validation/import flows that call `FindRemoteRepository` with a user-supplied string. No special privileges, leaked tokens, or MITM position are required — only the ability to submit an arbitrary string as a "remote URL" through a normal product feature, which is precisely the "crafted RPC field" class called out as in-scope by the validation rules.

### Recommendation
Route `req.GetRemote()` (and any other externally supplied value used as a Git command's positional/URL argument) through `gitcmd.Command.PostSepArgs` instead of `Args`, so Git's `--` separator forces the value to be treated strictly as a positional argument and never as an option. Additionally, apply an explicit allow-list/format check (e.g., reject values with a leading `-`, or require a valid scheme/path as `CreateRepositoryFromURL` partially does) before constructing the command, consistent with the `Command.Args` documentation's own guidance.

### Proof of Concept
1. As an ordinary GitLab user, initiate a project import/mirror configuration flow (or directly call the `FindRemoteRepository` gRPC method if reachable) supplying:
   `remote = "--upload-pack=/tmp/exploit.sh"`
2. Gitaly constructs and executes:
   `git ls-remote --upload-pack=/tmp/exploit.sh HEAD`
3. Because `remote` was placed in `Args` (not `PostSepArgs`), Git parses `--upload-pack=/tmp/exploit.sh` as an option rather than the intended repository/URL positional argument.
4. When Git resolves the (now missing/ambiguous) repository target through a transport that honors `--upload-pack` (e.g., local/file-based resolution), it invokes the attacker-specified path as the "remote" service program, yielding execution of attacker-controlled code on the Gitaly node.

Note: I was not able to fully trace the internal `commandDescription.args()` validator (only its call sites, not its full body) to confirm with certainty whether it rejects leading-`-` values across all subcommands; the `Args` field's own documentation strongly implies no such protection exists, which is the basis for this analog. Further verification of `commandDescription.args()` and of which `ls-remote` options are actually exploitable in Gitaly's supported transports would strengthen the PoC.

```go
func (s *server) FindRemoteRepository(ctx context.Context, req *gitalypb.FindRemoteRepositoryRequest) (*gitalypb.FindRemoteRepositoryResponse, error) {
	if req.GetRemote() == "" {
		return nil, structerr.NewInvalidArgument("empty remote can't be checked.")
	}

	var output bytes.Buffer
	cmd, err := s.gitCmdFactory.NewWithoutRepo(ctx,
		gitcmd.Command{
			Name: "ls-remote",
			Args: []string{
				req.GetRemote(),
				"HEAD",
			},
		},
		gitcmd.WithStdout(&output),
	)
	if err != nil {
		return nil, structerr.NewInternal("error executing git command: %w", err)
	}
```
