### Title
Unpriced ALT resolution amplification in banking-stage packet intake enables cheap packets to force expensive AccountsDb work before any fee is charged - (File: core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs)

### Summary
`TransactionViewReceiveAndBuffer::try_handle_packet` resolves every v0 transaction's Address Lookup Table (ALT) references against `AccountsDb` before the transaction's fee-payer is validated. This lets an unprivileged network sender force disproportionately expensive `AccountsDb` reads/deserializations per packet, for transactions that never pay a fee and are ultimately dropped, mirroring the reported cross-chain pattern where cheap upstream actions force expensive, uncompensated downstream work.

### Finding Description
In `translate_to_runtime_view`, the processing order is:
1. Sanitize the transaction view.
2. Cheaply check `view.total_num_accounts() > transaction_account_lock_limit` — this uses only the *declared* counts from the message (static keys + declared ALT lookup index counts), not the resolved addresses.
3. Only then call `load_addresses_for_view`, which for `TransactionVersion::V0` calls `bank.load_addresses_from_ref`, which iterates every declared address-table lookup and invokes `Bank::load_addresses_from_ref` → `accounts.load_lookup_table_addresses_into`, i.e., real `AccountsDb` account loads and `AddressLookupTable::deserialize` calls for each referenced ALT account. [1](#0-0) [2](#0-1) [3](#0-2) 

Crucially, `Consumer::check_fee_payer_unlocked` — the check that determines whether the sender can even pay the transaction fee — runs *after* this ALT resolution work, later in `handle_packet_batch_message`: [4](#0-3) [5](#0-4) 

Because the pre-resolution lock-limit check only counts *declared* lookup indexes (not actual resolved keys), an attacker can build a single v0 transaction referencing up to `transaction_account_lock_limit` (bounded by `MAX_TRANSACTION_SIZE`/protocol limits) distinct ALT accounts, each contributing one lookup entry. Every such packet forces the receive-and-buffer thread to perform that many separate `AccountsDb` loads and ALT deserializations — all before the code ever checks whether the sender's fee payer has any balance at all. If the fee payer has zero balance (or the transaction otherwise fails `check_fee_payer_unlocked`), the transaction is simply dropped (`num_dropped_on_fee_payer`) with no fee ever collected, but the `AccountsDb` work has already been paid for by the validator, not the sender.

This is the on-node analog of the Across bug class: a cheap, unprivileged action (submitting a signed but fee-less/underfunded v0 packet with many ALT lookups) forces disproportionately expensive downstream work (multiple `AccountsDb` reads/deserializations) on infrastructure that has no way to recoup the cost, because the cost-bearing check (fee-payer validation) is deferred until *after* the expensive work is done.

### Impact Explanation
This allows an unprivileged sender who can merely get packets past QUIC/sigverify (a keypair costs nothing to generate; a signature is cheap to produce) to impose non-trivial, uncompensated CPU/disk I/O load on every banking-stage receive-and-buffer thread. Sustained low-cost spam of such packets increases CPU and I/O pressure on the leader/forwarding validators handling transaction intake, degrading throughput for legitimate transactions — a QoS evasion / underpriced pre-fee work condition, consistent with the accepted vulnerability classes.

### Likelihood Explanation
The path is reachable by any network participant able to submit QUIC/TPU packets (no stake or special role required); it only requires constructing a valid v0 transaction referencing multiple existing ALT accounts (public information) with a fee payer that need not have any funds. QUIC's stream/connection throttling limits per-connection rate but does not account for the asymmetric cost of ALT resolution relative to a plain transfer, so the disparity persists across the allowed throughput.

### Recommendation
Reorder the checks in `translate_to_runtime_view`/`handle_packet_batch_message` so that a cheap fee-payer existence/balance check (or at least an existence check) is performed *before* resolving ALT addresses, or otherwise bound/rate-limit the cost of ALT resolution independent of per-connection stream throttling (e.g., charge or cap the number of distinct ALT accounts resolved per unit time per connection/IP, or defer full ALT resolution until after a lightweight fee-payer solvency check).

### Proof of Concept
Conceptually:
1. Craft a v0 `VersionedTransaction` whose fee payer is a fresh/near-empty keypair (no funds required), signed validly so it passes sigverify.
2. Include `transaction_account_lock_limit`-worth of address-table lookups, each pointing at a distinct existing ALT account with a single index, keeping `total_num_accounts()` within the pre-check limit (as already exercised by the existing `test_receive_and_buffer_too_many_keys` test structure, which demonstrates that such multi-ALT transactions reach `load_addresses_for_view` before lock/fee checks fully gate them): [6](#0-5) 
3. Send a continuous stream of such packets. Each one forces multiple `AccountsDb` loads/deserializations in `try_handle_packet` before `check_fee_payer_unlocked` rejects it and it is dropped (`num_dropped_on_fee_payer`), meaning the attacker pays no fee for the induced `AccountsDb` work.

Note: I was not able to execute this against a running validator to measure the exact CPU/I/O amplification factor; the finding is based on tracing the code path and confirming the ordering of checks (ALT resolution before fee-payer validation) via the cited source, not on a live benchmark.

pub(crate) fn translate_to_runtime_view<D: TransactionData>(
    data: D,
    bank: &Bank,
    transaction_account_lock_limit: usize,
    sanitize_config: &SanitizeConfig,
) -> Result<(RuntimeTransaction<ResolvedTransactionView<D>>, u64), PacketHandlingError> {
    // Parsing and basic sanitization checks
    let Ok(view) = SanitizedTransactionView::try_new_sanitized(data, sanitize_config) else {
        return Err(PacketHandlingError::Sanitization);
    };

    let Ok(view) = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    ) else {
        return Err(PacketHandlingError::Sanitization);
    };

    // Discard non-vote packets if in vote-only mode.
    if bank.vote_only_bank() && !view.is_simple_vote_transaction() {
        return Err(PacketHandlingError::Sanitization);
    }

    if usize::from(view.total_num_accounts()) > transaction_account_lock_limit {
        return Err(PacketHandlingError::LockValidation);
    }

    let (loaded_addresses, deactivation_slot) = load_addresses_for_view(&view, bank)?;

    let Ok(view) = RuntimeTransaction::<ResolvedTransactionView<_>>::try_new(
        view,
        loaded_addresses,
        bank.get_reserved_account_keys(),
    ) else {
        return Err(PacketHandlingError::Sanitization);
    };

    // Validate no duplicate accounts (must be after resolution to catch ALT duplicates)
    if validate_account_locks(view.account_keys(), transaction_account_lock_limit).is_err() {
        return Err(PacketHandlingError::LockValidation);
    }

    Ok((view, deactivation_slot))
}

/// Load addresses from ALTs (if necessary) and return the
/// [`LoadedAddresses`] with the minimum deactivation slot.
pub(crate) fn load_addresses_for_view<D: TransactionData>(
    view: &SanitizedTransactionView<D>,
    bank: &Bank,
) -> Result<(Option<LoadedAddresses>, Slot), PacketHandlingError> {
    match view.version() {
        TransactionVersion::Legacy | TransactionVersion::V1 => Ok((None, u64::MAX)),
        TransactionVersion::V0 => bank
            .load_addresses_from_ref(view.address_table_lookup_iter())
            .map(|(loaded_addresses, deactivation_slot)| {
                (Some(loaded_addresses), deactivation_slot)
            })
            .map_err(|_| PacketHandlingError::ALTResolution),
    }
}

impl Bank {
    /// Load addresses from an iterator of `SVMMessageAddressTableLookup`,
    /// additionally returning the minimum deactivation slot across all referenced ALTs
    pub fn load_addresses_from_ref<'a>(
        &self,
        address_table_lookups: impl Iterator<Item = SVMMessageAddressTableLookup<'a>>,
    ) -> Result<(LoadedAddresses, Slot), AddressLoaderError> {
        let slot_hashes = self
            .transaction_processor
            .sysvar_cache()
            .get_slot_hashes()
            .map_err(|_| AddressLoaderError::SlotHashesSysvarNotFound)?;

        let mut deactivation_slot = u64::MAX;
        let mut loaded_addresses = LoadedAddresses::default();
        for address_table_lookup in address_table_lookups {
            deactivation_slot = deactivation_slot.min(
                self.rc
                    .accounts
                    .load_lookup_table_addresses_into(
                        &self.ancestors,
                        address_table_lookup,
                        &slot_hashes,
                        &mut loaded_addresses,
                    )
                    .map_err(into_address_loader_error)?,
            );
        }

        Ok((loaded_addresses, deactivation_slot))
    }
