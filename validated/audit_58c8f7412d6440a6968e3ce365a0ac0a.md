Audit Report

## Title
Relayer reward paid regardless of on-chain execution outcome (`success` field ignored) - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt` decodes the Ethereum `InboundMessageDispatched(nonce, topic, bool success, reward_address)` event and carries an explicit `success: bool` field indicating whether the referenced message actually executed successfully on the Ethereum Gateway contract. `Pallet::process_delivery_receipt`, invoked by the public `submit_delivery_receipt` extrinsic, never inspects `receipt.success` before paying the relayer reward and clearing the pending order, so a relayer can claim the full reward for a message whose execution reverted.

## Finding Description
`DeliveryReceipt::try_from` decodes the `success` flag straight from the Ethereum log: [1](#0-0) . The public extrinsic `submit_delivery_receipt` verifies the log proof, decodes it into a `DeliveryReceipt`, and forwards it unmodified to `process_delivery_receipt`: [2](#0-1) .

Inside `process_delivery_receipt`, the only checks performed are that the gateway address matches and that a `PendingOrder` exists for the nonce; the reward is then unconditionally registered (when `order.fee > 0`) and the pending order is removed — `receipt.success` is never read: [3](#0-2) . A grep across the Snowbridge crates confirms `receipt.success`/`event.success` is referenced only during decode, never in any downstream payout or settlement check. This means proof of log inclusion (i.e., that *some* `InboundMessageDispatched` event fired) is treated as sufficient proof of successful delivery, even when the decoded payload explicitly states `success = false`.

## Impact Explanation
Any unprivileged relayer using the ordinary public `submit_delivery_receipt` entrypoint can submit a genuine, correctly verified event proof for a message that reverted on Ethereum (`success: false`) and still receive the full `order.fee` reward via `T::RewardPayment::register_reward`, while the `PendingOrder` is removed as if delivery succeeded. This is an unbacked payout — value paid out without the corresponding successful bridge delivery — directly violating the required invariant that bridge receipts and payout state must only advance after execution and settlement succeed atomically, and matches the allowed "theft or unbacked mint"/"duplicate settlement or payout" impact classes.

## Likelihood Explanation
No malicious peer, validator, or privileged actor is required. A normal relayer submitting a real, valid Ethereum log proof for a legitimately-failed dispatch (e.g., due to gas exhaustion or a reverting downstream call in the Gateway contract) triggers the bug. Since `success` is already decoded and available on the struct but simply unused in the payout path, this is a straightforward missing-check defect rather than a complex multi-step exploit, making it easily and repeatably triggerable in normal operation.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only invoke `T::RewardPayment::register_reward` when `receipt.success == true`. When `success == false`, still resolve/remove the `PendingOrder` (or mark it failed) but skip the reward payment, and emit a distinct event (e.g., `MessageDeliveryFailed`) so downstream systems can react appropriately, potentially enabling retry or refund logic.

## Proof of Concept
Using the existing test harness in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs`: insert a `PendingOrder { nonce, fee: 1_000_000, block_number }` into `PendingOrders`, then construct a `DeliveryReceipt` with `success: false` for that nonce and matching `gateway`, and call `Pallet::<Test>::process_delivery_receipt(relayer, receipt)` directly (bypassing proof verification, as `process_delivery_receipt` is a `pub` pallet function independent of the extrinsic's verifier check). Assert the call returns `Ok(())`, that the relayer's registered reward balance increases by `order.fee`, and that `PendingOrders::<Test>::get(nonce)` becomes `None` — demonstrating full reward payout despite `success == false`.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
