### Title
Protocol fee bypassed on `Nep245`/`Imt` (MT) transfers via unit-delta `TokenDiff` splitting - (contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` waives the fee whenever the *per-intent* `|delta|` on a `Nep245Token`/`Imt` `TokenId` is `<= 1`, but `TokenDiff::execute_intent` computes and collects this fee independently for every `TokenDiff` intent in a batch, with no aggregation across intents on the same `TokenId`. A signer can therefore move an arbitrarily large MT balance by issuing `N` separate `TokenDiff` intents (in one or several `MultiPayload`s), each with `delta = -1` on the same `Nep245TokenId`/`Imt` id, paying zero fee on every leg, whereas a single intent with `delta = -N` would owe `protocol_fee`.

### Finding Description
The binding that should hold is: `fees_collected(sum of legs moving total -N on token T) == fees_collected(single TokenDiff with delta=-N on token T)`, both governed by the same `protocol_fee`. This does not hold for `Nep245`/`Imt` tokens.

`TokenDiff::token_fee` (contracts/defuse/core/src/intents/token_diff.rs:207-216) exempts MT/IMT amounts `<= 1` from any fee: [1](#0-0) 

`TokenDiff::execute_intent` (contracts/defuse/core/src/intents/token_diff.rs:59-79) iterates the `diff` map of the *current* `TokenDiff` instance, computing `fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)` per `(token_id, delta)` pair, then applies the delta directly to the signer's balance via `internal_apply_deltas` and accumulates `fees_collected` — all scoped to this single intent's execution: [2](#0-1) 

Because `diff` is a `BTreeMap<TokenId, i128>`, a single `TokenDiff` can only carry one delta entry per `TokenId`. To move `-N` on the same `Nep245TokenId` while keeping each leg's `amount == 1` (and thus fee-exempt per the `amount > 1` guard), the attacker must issue `N` distinct `TokenDiff` intents, each with `delta = -1` on that token. Nothing in `execute_intent` tracks cumulative `amount` moved on a given `TokenId` across multiple `TokenDiff` intents within the same payload/batch — each call to `token_fee` only sees the single intent's own `amount`. The batch-wide invariant enforced elsewhere (`TransferMatcher::finalize` / `UnmatchedDeltas`, contracts/defuse/core/src/engine/state/deltas.rs) only checks that the total supply deltas across all accounts for a token net to zero (i.e., the `-N` must be matched by a `+N` counterparty elsewhere in the batch); it performs no fee reconciliation, so it does not detect or prevent this leg-splitting.

Attacker's exact construction: sign one `MultiPayload` containing `N` `TokenDiff` intents, each `{ diff: {token_id: Nep245TokenId(mt_contract, mt_key) -> -1} }`, matched by a counterparty (or the attacker's own solver-side intent) supplying the offsetting `+N` (or `N` separate `+1` legs) on the receiving side. Each of the `N` legs independently evaluates `token_fee(token_id, 1, protocol_fee) == Pips::ZERO`, so `fees_collected` is `0` for every leg, and the aggregate `fees_collected` sent to `fee_collector` for the whole `-N` transfer is `0`, versus `protocol_fee.fee_ceil(N)` that a single `-N` `TokenDiff` would have paid.

Existing guards do not stop this: signature/nonce verification (`MultiPayload::verify`, `verify_intent_nonce`) only authenticates who signed and prevents replay, not fee aggregation; `TransferMatcher::finalize`'s `UnmatchedDeltas` check only guarantees the batch's total token deltas net to zero, which is fully satisfiable while still bypassing fees leg-by-leg.

### Impact Explanation
This results in systematic under-collection of `protocol_fee` on `Nep245`/`Imt` (MT) asset flows — a direct match for the "protocol fees bypassed" Critical category. The `fee_collector` account (contracts/defuse/core/src/intents/token_diff.rs:96-101) receives strictly less value than it is entitled to for any MT trade an attacker chooses to split into unit legs; the loss accrues to the protocol/fee_collector, and the attack is fully repeatable across any `Nep245TokenId`/`Imt` id, any account, and any batch size `N` (bounded only by gas/tx size, which is out of scope per the rules but does not prevent smaller-N repeated exploitation across multiple transactions).

### Likelihood Explanation
Preconditions are minimal and match an ordinary solver/user: the attacker only needs a Verifier balance of the MT token they wish to move (`>= N`) and a nonzero `protocol_fee`, both realistic and unprivileged. Constructing `N` `TokenDiff` intents with `delta = -1` each is trivial client-side (no special contract calls, no privileged roles, no locked-account bypass needed). The only cost is transaction/gas size for larger `N`, which does not eliminate the vulnerability — it only bounds how much fee can be bypassed in a single call, and the attack is trivially repeatable across many transactions to bypass fees on arbitrarily large aggregate volume over time.

### Recommendation
Compute/aggregate the fee-exemption threshold per `TokenId` across the whole batch (or session) rather than per individual `TokenDiff` intent — e.g., track cumulative `|delta|` per `(signer, TokenId)` within `Engine`'s batch-processing state before applying the `amount > 1` exemption, or remove/restrict the MT/NFT unit-exemption entirely and only special-case genuine NFT semantics (`Nep171`, or MT ids known to represent unique/non-fungible items) rather than exempting by raw `amount` threshold, since `amount` is attacker-controlled per-intent and trivially splittable.

### Proof of Concept
```rust
// contracts/defuse/core/src/intents/token_diff.rs (or tests/src/tests/defuse/intents/token_diff.rs)
// cargo test bypass_fee_via_unit_split -- --nocapture

#[test]
fn bypass_fee_via_unit_split() {
    let fee = Pips::ONE_PERCENT; // nonzero protocol_fee
    let mt_token_id: TokenId = Nep245TokenId::new(
        "mt.near".parse().unwrap(), "ft1".to_string()
    ).into();

    const N: u128 = 1000;

    // Side A: single TokenDiff with delta = -N (expected fee path)
    let fee_single = TokenDiff::token_fee(&mt_token_id, N, fee).fee_ceil(N);
    assert!(fee_single > 0, "single -N leg should incur nonzero fee");

    // Side B: N TokenDiff intents each with delta = -1 (attacker's split)
    let mut fee_split_total: u128 = 0;
    for _ in 0..N {
        let fee_leg = TokenDiff::token_fee(&mt_token_id, 1, fee).fee_ceil(1);
        fee_split_total += fee_leg;
    }

    // BINDING (should hold, but is violated):
    // fee_collected(N unit legs) == fee_collected(one -N leg)
    assert_eq!(fee_split_total, 0, "each unit leg is fee-exempt");
    assert_ne!(
        fee_split_total, fee_single,
        "fee bypass confirmed: split legs collect 0 vs {fee_single} for equivalent aggregate transfer"
    );
}
```
A full end-to-end confirmation (recommended for a background agent with sandbox access) would use `near-workspaces`/`defuse_sandbox`: deposit `N` MT units to a solver account, sign a `MultiPayload` with `N` `TokenDiff` intents (`delta = -1` each) matched by a counterparty's offsetting `+N`, execute via `execute_intents`, and assert `fee_collector`'s post-balance is `0` — then repeat with a single `delta = -N` `TokenDiff` and assert `fee_collector`'s balance equals `protocol_fee.fee_ceil(N) > 0`, demonstrating the divergence.
