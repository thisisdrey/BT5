### Title
AMM-style exchange pools allow a pool creator to sandwich a victim's `ExchangeTransaction` within a single block by atomically manipulating pool reserves via `ExchangeInject`/`ExchangeWithdraw` — ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
The Sherlock report describes an attacker using a flash loan to atomically inflate a shared state variable (`TotalDebt`) right before calling `liquidate`, forcing a victim's position underwater within the same transaction flow, then reverting the manipulation after profiting. The equivalent root-cause pattern in java-tron is the bancor-formula TRC10 exchange: the pool reserves (`firstTokenBalance`/`secondTokenBalance`) stored in `ExchangeCapsule` are shared, mutable state that any pool's creator can move atomically via `ExchangeInjectContract`/`ExchangeWithdrawContract`, then move back, sandwiching a taker's `ExchangeTransactionContract` inside the same block.

### Finding Description
`ExchangeInjectActuator.execute` and `ExchangeWithdrawActuator.execute` let the exchange **creator** (any address that itself created the pair via `ExchangeCreateContract`) directly change `firstTokenBalance`/`secondTokenBalance` on demand: [1](#0-0) 

`doValidate()` only checks that the caller is the pool's creator — it does not prevent the creator from repeatedly injecting/withdrawing to move the exchange rate arbitrarily within the balance-limit bounds: [2](#0-1) 

The taker-side `ExchangeTransactionActuator`/`MarketSellAssetActuator` matching path computes the amount received purely from the current pool reserves at execution time (bancor formula), with no block-level price protection beyond the caller-supplied `expected` minimum on `ExchangeTransactionContract`: [3](#0-2) 

Because a single block can contain: (1) attacker's `ExchangeInject` (moves price against victim), (2) victim's `ExchangeTransaction` (executed at the manipulated price, still passing because it clears the caller's `expected` floor), (3) attacker's `ExchangeWithdraw` (restores/extracts value) — the attacker extracts value from the victim's trade exactly analogous to Bob manipulating `TotalDebt` via a flash loan to force Alice's liquidation and reverse the state afterward. This requires only unprivileged, ordinary signed transactions (`ExchangeCreateContract` to become creator of a pool, then `ExchangeInjectContract`/`ExchangeWithdrawContract`), reachable purely through the standard transaction broadcast path.

### Impact Explanation
An attacker who creates (or already controls) an exchange pair can, within a single block, deliberately worsen the exchange rate a victim's `ExchangeTransaction`/`MarketSellAssetActuator` order receives (down to the caller-specified `expected` floor) and pocket the difference by reversing the injection/withdrawal afterward. This is a concrete theft-of-funds vector against any counterpart trading against that pool, mirroring the reported class of "force an unfavorable outcome on another user via atomic state manipulation within one block."

### Likelihood Explanation
Likelihood is constrained by the requirement that the attacker be the exchange's creator, but since any account can create an arbitrary TRC10 exchange pair via `ExchangeCreateContract` and then advertise/attract trades against it (or target an existing pool it created), this is fully reachable by an unprivileged transaction broadcaster with no special permissions, using only standard broadcastable contracts.

### Recommendation
Add slippage/price-impact protections that account for intra-block reserve changes (e.g., disallow creator inject/withdraw and taker matching against the same pool within the same block, or use a time-weighted/committed price), and/or restrict the magnitude/frequency of `ExchangeInject`/`ExchangeWithdraw` operations relative to pending taker orders in the same block.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` to create pool P(tokenA, TRX) with initial reserves.
2. Victim broadcasts `ExchangeTransactionContract` selling tokenA for TRX with a permissive `expected` minimum.
3. Within the same block, attacker's transaction ordered first calls `ExchangeInjectContract` (as pool creator) to shift `firstTokenBalance`/`secondTokenBalance` unfavorably for the victim (per `ExchangeInjectActuator.execute`, lines 60-83).
4. Victim's `ExchangeTransactionContract` executes at the manipulated reserves, receiving close to the `expected` floor instead of the fair-market amount.
5. Attacker's subsequent transaction in the same block calls `ExchangeWithdrawContract` to restore/extract the shifted balance, realizing the difference as profit — analogous to Bob's flash-loan-driven forced liquidation of Alice in the original report.
