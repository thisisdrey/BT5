### Title
Dangling postponed action receipts (PostponedReceipt/PendingDataCount/PostponedReceiptId) survive account deletion, allowing privilege bleed into a recreated account - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` (core/store/src/utils/mod.rs:505-575) deletes `TrieKey::Account`, `ContractCode`, access keys/gas keys, and `ContractData`, but never removes `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` entries keyed by the account as `receiver_id`. Because `process_action_receipt` (runtime/runtime/src/lib.rs:1593-1658) and the data-arrival path in `process_receipt` (runtime/runtime/src/lib.rs:1367-1474) resolve and execute postponed receipts purely by `(receiver_id, data_id/receipt_id)` lookups with no check that the account is still the same incarnation, a postponed receipt created for a deleted account can later fire against a freshly recreated account of the same name.

### Finding Description
- `set_postponed_receipt`/`process_action_receipt` store an `ActionReceipt` under `TrieKey::PostponedReceipt{receiver_id, receipt_id}`, plus `TrieKey::PendingDataCount{receiver_id, receipt_id}` and one `TrieKey::PostponedReceiptId{receiver_id, data_id}` per unresolved `input_data_id` (runtime/runtime/src/lib.rs:1608-1655, core/store/src/utils/mod.rs:120-127).
- `action_delete_account` calls `remove_account` (runtime/runtime/src/actions.rs:371) which only clears `Account`, `ContractCode`, access/gas keys, and `ContractData` (core/store/src/utils/mod.rs:509-573). It never scans/removes `PostponedReceipt`, `PendingDataCount`, or `PostponedReceiptId` for the account.
- The `Data`-receipt branch of `process_receipt` (runtime/runtime/src/lib.rs:1398-1455) looks up `TrieKey::PostponedReceiptId{receiver_id, data_id}` unconditionally, decrements `PendingDataCount`, and on reaching zero fetches and executes the stale `PostponedReceipt` via `apply_action_receipt` — with no check that the receiver account is the same incarnation that existed when the receipt was postponed.
- Exploit flow: attacker's contract on `x.a.near` issues a self-directed promise chain (`promise_then`) whose second leg batches `promise_batch_action_add_key_with_full_access`, deliberately gated on an `input_data_id` from a promise the attacker controls and can delay resolving. This creates a postponed `AddKey` receipt under `x.a.near`. In the same or a later block, the attacker (as the actor, since `locked == 0`) submits `DeleteAccount{beneficiary_id: attacker}` on `x.a.near`, which passes `check_actor_permissions` and calls `remove_account`, deleting the account but leaving the postponed `AddKey` receipt bookkeeping intact. The attacker (from parent `a.near`) then issues `CreateAccount` to recreate `x.a.near`; a victim, seeing what looks like a fresh/unused account, deposits funds and adds their own key. When the attacker finally delivers the pending Data receipt, `process_receipt` finds the stale `PostponedReceiptId`/`PendingDataCount` entries still present, decrements to zero, and executes the stale `AddKey` action against the *current* (victim-funded) account — granting the attacker a full-access key with no signature or authorization from the victim.
- No existing check (nonce, access-key permission, `check_actor_permissions`, or an account-incarnation/epoch marker) prevents this, because the postponed-receipt trie keys are not scoped to an account "generation" and are never invalidated by `remove_account`.

### Impact Explanation
This breaks authorization exactness across account incarnations: an account-deletion + recreation cycle allows an attacker to plant a privileged action (adding a full-access key) that executes against a completely different (victim-owned) incarnation of the same account name. This falls under authorization escalation across accounts, leading directly to theft of the victim's deposited funds once the attacker uses the illegitimately added full-access key to drain the account.

### Likelihood Explanation
The attacker needs only ordinary account/contract capabilities: control of a parent account `a.near`, ability to fund and delete a subaccount `x.a.near` (locked balance must be zero, which the attacker controls), and the ability to construct a promise chain with a controllable/delayable data dependency, plus a subsequent `CreateAccount` on the same name to lure a victim. No validator, node, or protocol-level privilege is required, and the flow is repeatable against any freshly-recreated sub-account name if a victim can be induced to reuse it before the dangling receipt resolves.

### Recommendation
In `remove_account` (core/store/src/utils/mod.rs), iterate and remove all `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` entries keyed by the account being deleted (mirroring the existing access-key/contract-data cleanup loops), so no action receipt or its input-data bookkeeping can survive account deletion and later be resolved against a re-created incarnation of the same account.

### Proof of Concept
Runtime integration test plan (runtime/runtime/src/tests/apply.rs style, similar to `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Set up `x.a.near` with a deployed contract; submit a `FunctionCall` receipt that issues `promise_then` chaining to a `promise_batch_action_add_key_with_full_access` batch, whose input data dependency will not resolve in this apply call.
2. Assert via direct trie inspection that `TrieKey::PostponedReceipt{receiver_id: x.a.near, ..}`, `TrieKey::PendingDataCount{...}`, and `TrieKey::PostponedReceiptId{...}` are present.
3. Submit `DeleteAccount{beneficiary_id: attacker}` receipt on `x.a.near` (self-actor, `locked == 0`), then re-assert the same three trie key families are still present after `remove_account` returns (demonstrating the cleanup gap).
4. Submit `CreateAccount` for `x.a.near` from `a.near`, followed by a victim `Transfer` and `AddKey` (victim's own key) to the recreated account.
5. Deliver the pending `DataReceipt` completing the dependency; assert `process_receipt`'s `pending_data_count` reaches 0, the stale postponed `AddKey` receipt executes, and the attacker's full-access public key is now present on the account — without any signature or authorization from the victim who funded/owns the recreated account.
