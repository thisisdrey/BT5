Audit Report

## Title
`control_inherited_account`'s reentrancy filter only blocks direct recovery calls, allowing an inheritor to bypass it by wrapping a `slash_attempt`/config-mutating call inside `pallet_utility::batch` and act with the `recovered` account's signed origin against higher-priority friend groups - (File: `substrate/frame/recovery/src/lib.rs`)

## Summary
`pallet_recovery::control_inherited_account` installs a single-call reentrancy filter on the `recovered` account's origin that only inspects the outer `RuntimeCall` for whether it is a recovery pallet sub-call, as shown at [1](#0-0)  . Because `pallet_utility::batch` dispatches its inner calls via `dispatch_bypass_filter`, which per the generated `RuntimeCall::dispatch` implementation skips the `filter_call` check entirely [2](#0-1) , an inheritor can wrap `RecoveryCall::slash_attempt` inside `Utility::batch` to execute it with the `recovered` account's signed origin, bypassing the guard entirely.

## Finding Description
The comment on the dispatchable explicitly documents the intent: "The controller is not allowed to dispatch calls of the recovery pallet. Otherwise they could mess with the recovery configuration and possibly cancel or slash attempts from higher-priority friend groups," at [3](#0-2) . The filter is added via `origin.add_filter(...)` and checks only whether the top-level call `is_sub_type()` of the recovery pallet's call enum [4](#0-3) . `call.dispatch(origin)` invokes `OriginTrait::filter_call` only on the outer call before dispatch [5](#0-4) . If the outer call is `pallet_utility::Call::batch` wrapping an inner `RecoveryCall::slash_attempt`, the outer call passes the filter (it's not a recovery sub-call), and `Utility::batch`'s internal dispatch of each inner call uses `dispatch_bypass_filter`, which does not re-check the origin filter — allowing the inner recovery call through with the `recovered` account's privileges.

This exact scenario is captured by a dedicated regression test already present in the repository, `inheritor_cannot_bypass_filter_via_utility_batch`, at [6](#0-5) , whose comment states: "The batch dispatched as ALICE, but the inner slash should have still executed since our filter only checks the outer call." The test explicitly checks whether the slash succeeded and `panic!`s if it did, i.e., it is written as a proof/regression guard confirming this is a known and reachable bypass in the current filter design — not a purely theoretical concern.

## Impact Explanation
An inheritor for a lower-priority friend group can call `control_inherited_account` wrapping `slash_attempt { friend_group_index }` in `Utility::batch`, causing the `recovered` account to slash the `SecurityDeposit` of a friend in a higher-priority, pending recovery attempt and delete that attempt (`Attempt::take`). This is unauthorized origin escalation/execution: the reentrancy filter, whose entire purpose is to prevent the inheritor from mutating recovery state via the recovered account's origin, is trivially circumvented through a standard, always-available public wrapper pallet (`pallet_utility`). The result is direct fund loss (slashed deposit) to the honest higher-priority friend/initiator and permanent loss of that pending recovery attempt, locking out the legitimate higher-priority inheritance path.

## Likelihood Explanation
High and readily reachable by an unprivileged external actor: any account that has legitimately become `inheritor` of a `recovered` account for one friend group (even the lowest-priority one) can exploit this the moment a higher-priority attempt becomes pending. No governance, validator, or off-chain trust assumption is required, and `pallet_utility`'s `batch` extrinsic is public and unprivileged in essentially every Substrate/polkadot-sdk-based runtime that includes both pallets.

## Recommendation
Make the reentrancy filter transitively aware of nested/wrapped calls rather than only inspecting the top-level call: recursively unwrap known call-wrapping pallets (`Utility::batch`/`batch_all`/`force_batch`, `Multisig`, `Proxy`, etc.) and reject if any nested call is a recovery sub-call, or change the enforcement model so that filters set via `add_filter` are consulted at every nested dispatch level (i.e., `dispatch_bypass_filter` invoked from within pallets like `Utility` should still consult the currently installed origin filter chain rather than bypassing it unconditionally).

## Proof of Concept
The existing test `inheritor_cannot_bypass_filter_via_utility_batch` at [6](#0-5)  reproduces the issue:
1. ALICE sets two friend groups: `family` (priority 0, inheritor DAVE) and `friends_group` (priority 1, inheritor FERDIE).
2. `friends_group` completes recovery first via `initiate_attempt`/`finish_attempt`, making FERDIE the inheritor of ALICE.
3. `family` (priority 0, higher priority) initiates a pending attempt via BOB.
4. FERDIE calls `control_inherited_account` wrapping `RecoveryCall::slash_attempt { friend_group_index: 0 }` inside `pallet_utility::Call::batch`.
5. The inner `slash_attempt` executes despite the reentrancy guard, slashing BOB's security deposit and destroying the higher-priority pending attempt — confirmed by the test's balance check and `panic!` on successful slash.

/// Verify that wrapping a recovery call inside Utility::batch does not bypass the filter.
#[test]
fn inheritor_cannot_bypass_filter_via_utility_batch() {
	new_test_ext().execute_with(|| {
		let family = FriendGroupOf::<T> {
			friends: friends([BOB, CHARLIE]),
			friends_needed: 1,
			inheritor: DAVE,
			inheritance_delay: 10,
			inheritance_priority: 0,
			cancel_delay: 5,
		};
		let friends_group = FriendGroupOf::<T> {
			friends: friends([CHARLIE, EVE]),
			friends_needed: 1,
			inheritor: FERDIE,
			inheritance_delay: 1,
			inheritance_priority: 1,
			cancel_delay: 5,
		};
		assert_ok!(Recovery::set_friend_groups(signed(ALICE), vec![family, friends_group]));

		// Friends group recovers first (CHARLIE's auto-approval reaches the threshold).
		assert_ok!(Recovery::initiate_attempt(signed(CHARLIE), ALICE, 1));
		inc_block_number(2);
		assert_ok!(Recovery::finish_attempt(signed(EVE), ALICE, 1));
		assert_eq!(Recovery::inheritor(ALICE), Some(FERDIE));

		// Family initiates higher-priority attempt
		assert_ok!(Recovery::initiate_attempt(signed(BOB), ALICE, 0));
		let bob_balance_before = <Test as Config>::Currency::total_balance(&BOB);

		// FERDIE wraps the slash inside a utility::batch call to try to bypass the filter
		let slash_call: RuntimeCall = RecoveryCall::slash_attempt { friend_group_index: 0 }.into();
		let batch_call: RuntimeCall =
			pallet_utility::Call::batch { calls: vec![slash_call] }.into();
		assert_ok!(Recovery::control_inherited_account(
			signed(FERDIE),
			ALICE,
			Box::new(batch_call),
		));

		// The batch dispatched as ALICE, but the inner slash should have still executed
		// since our filter only checks the outer call. Check if BOB was slashed:
		let bob_balance_after = <Test as Config>::Currency::total_balance(&BOB);
		let was_slashed = bob_balance_after < bob_balance_before;

		if was_slashed {
			panic!(
				"BYPASS: recovery call filter was circumvented via utility::batch! \
				 BOB lost {} from security deposit slash.",
				bob_balance_before - bob_balance_after
			);
		}
	});
}
