Audit Report

## Title
`process_delivery_receipt` ignores the `DeliveryReceipt.success` flag and unconditionally pays the relayer reward for failed Ethereum-side message execution - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` that carries a `success: bool` field indicating whether the outbound message's dispatched command actually executed successfully on the Ethereum Gateway contract, but the field is never checked before paying the relayer reward and permanently removing the `PendingOrder`. This decouples relayer reward payout from actual successful message execution on Ethereum.

## Finding Description
`submit_delivery_receipt` is a public, unprivileged, signed extrinsic that verifies a genuine Ethereum event log/proof via `T::Verifier::verify` and decodes it into a `DeliveryReceipt` via `DeliveryReceipt::try_from` [1](#0-0) . `DeliveryReceipt` is decoded directly from the Ethereum `InboundMessageDispatched` event, which explicitly carries a `success` flag describing whether the corresponding dispatched command succeeded or reverted on the Gateway contract [2](#0-1) .

`process_delivery_receipt` only checks the gateway address (`T::GatewayAddress::get() == receipt.gateway`) and that a `PendingOrder` exists for `receipt.nonce`; it never reads `receipt.success` anywhere before paying `order.fee` via `T::RewardPayment::register_reward` and removing the order via `<PendingOrders<T>>::remove(nonce)` [3](#0-2) . The `PendingOrder` struct itself stores only `nonce`, `fee`, and `block_number`, with no field to persist delivery/success semantics for later reconciliation [4](#0-3) . A grep across the entire pallet confirms there is no reference to `success`, a `DeliveryFailed` error, or a `MessageDeliveryFailed` event anywhere in the codebase — the field is fully unused after decoding.

This violates the invariant that message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically. Here, decode and proof-verification succeed, but execution status (`success = false`) is silently discarded, and settlement (reward payment + order removal) proceeds regardless.

## Impact Explanation
This permits unbacked reward payout on BridgeHub for messages whose execution on Ethereum did not succeed — the relayer is paid `order.fee` and the `PendingOrder` is irreversibly removed via `PendingOrders::remove(nonce)`, even when the Gateway emitted `success = false`. This matches the "duplicate settlement or payout" and "theft or unbacked mint or unlock" categories of the impact gate, since a payout is finalized and made irreversible despite the underlying condition (successful execution) it is supposed to be conditioned on not being met.

## Likelihood Explanation
Likelihood is Medium: no privileged actor, malicious peer, or compromised prover is required — any relayer submitting a genuine, correctly-proven Ethereum event log for a message whose dispatched command failed on Ethereum (e.g., insufficient dispatch gas relative to the `GasMeter` estimate computed in `do_process_message` via `T::GasMeter::maximum_dispatch_gas_used_at_most`, or any ordinary execution-time revert) triggers this flawed path. Such execution failures are a normal, expected occurrence in cross-chain message dispatch, not a contrived edge case.

## Recommendation
1. Add `ensure!(receipt.success, Error::<T>::DeliveryFailed)` (or an equivalent explicit branch) in `process_delivery_receipt` before calling `T::RewardPayment::register_reward`.
2. If failed deliveries should still resolve/unblock the pending order, separate order resolution from reward payment: only pay the reward when `receipt.success == true`; on failure, emit a distinct event (e.g., `MessageDeliveryFailed`) and handle fee refund/retry logic explicitly.
3. Persist enough context in `PendingOrder` (e.g., `topic`) to cross-check `receipt.topic` against the originally committed message for the given nonce, preventing reconciliation ambiguity.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrders[nonce] = { nonce, fee, block_number }` with `fee > 0` [4](#0-3) .
2. The message is relayed to Ethereum; its dispatched command reverts/fails during execution on the Gateway (e.g., insufficient dispatch gas). The Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid proof for this genuine event and calls `submit_delivery_receipt(event)`; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` correctly decodes `success = false` [1](#0-0) .
4. `process_delivery_receipt` checks only the gateway address and pending-order existence, both of which pass; `order.fee > 0` triggers `T::RewardPayment::register_reward`, and `PendingOrders::remove(nonce)` permanently closes the order regardless of `receipt.success` [5](#0-4) .
5. The relayer is paid the full fee for a message that never executed successfully on Ethereum, with no path to reconcile or reverse the payout.

			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
