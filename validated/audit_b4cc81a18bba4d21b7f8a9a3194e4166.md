### Title
Unbounded array allocation from attacker-controlled length in `BatchValidateSign` precompile causes OutOfMemoryError / node crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `batchvalidatesign` TVM precompile (contract address `0x…09`) parses an "addresses" array length directly out of attacker-supplied calldata and immediately allocates a Java array of that size via `extractBytes32Array()`, before validating that the calldata actually contains that many elements. A single crafted smart-contract call with a few hundred bytes of calldata can set the encoded length word to a value near `Integer.MAX_VALUE`, forcing the node to allocate a multi-gigabyte object-reference array, exhausting heap memory and crashing/hanging the executing full node — the same "small input, unvalidated size, huge unbacked allocation" pattern as the reported OpenCV decompression-bomb CVE.

### Finding Description
`PrecompiledContracts.extractBytes32Array()` reads the array length straight from a `DataWord` decoded from the raw call data and allocates the outer array with that length with no upper bound and no check that the calldata is long enough to actually contain that many 32-byte words: [1](#0-0) 

This helper is invoked unconditionally in `BatchValidateSign.doExecute()` to build the `addresses` array: [2](#0-1) 

The only size guard in this method (`addrArraySize > MAX_SIZE`) is applied **only when `VMConfig.allowTvmSelfdestructRestriction()` is active**: [3](#0-2) 

When that consensus flag is not yet activated on a given network (it is a chain-parameter-gated hard-fork switch, off by default until miners/committee vote it on), `extractBytes32Array(words, words[2].intValueSafe() / WORD_SIZE)` is reached with **no size check at all**. `DataWord.intValueSafe()` returns an `int` derived from the 256-bit word supplied by the caller, so an attacker fully controls the value passed as `len`. Setting this word to e.g. `0x7FFFFFFF` causes:

```java
byte[][] bytes32Array = new byte[Integer.MAX_VALUE][];
```

which alone requires on the order of 8–16 GB just for the object-reference backing array (before any element is populated), triggering an immediate `OutOfMemoryError`.

The same unguarded pattern also exists in `extractBytesArray()`/`extractSigArray()` for the `signatures` array whenever the flag is off (`VMConfig.allowTvmSelfdestructRestriction() ? extractSigArray(...) : extractBytesArray(...)`), and in `ValidateMultiSign.execute()` which has the identical guard shape.

This is directly analogous to the reported CVE: an untrusted, attacker-controlled "size" field is used to drive a memory allocation before the size is validated against the actual bounds of the input, producing memory exhaustion.

### Impact Explanation
A successful call to the `BatchValidateSign`/`ValidateMultiSign` precompiles with a crafted length field causes an `OutOfMemoryError` inside the TVM execution thread of a full node. Depending on JVM configuration and available heap, this can crash the node process or destabilize it (GC storms, other transactions failing to execute), denying service to the network — this matches "node crash or halt" in the accepted-impact list. Because it is reachable by any account able to make a contract call (including via `TriggerConstantContract`/`triggersmartcontract` JSON-RPC/HTTP entry points into `Wallet`), no special privilege is required.

### Likelihood Explanation
Exploitability is contingent on the `allowTvmSelfdestructRestriction` hard-fork parameter being disabled on the target network (its default/activation state could not be confirmed from the available index — this needs to be checked against the live chain parameters/`ForkController` state for the specific deployment). On any network where it is not yet activated, exploitation requires only a single call transaction with a small, cheaply-computed calldata payload (energy cost is computed from `data.length`, which is unrelated to the declared array length, so the attacker pays for a tiny transaction but triggers a multi-GB allocation) — making it trivial and cheap for an unprivileged, anonymous contract caller to trigger.

### Recommendation
- Validate the declared array length in `extractBytes32Array()`, `extractBytesArray()`, and `extractSigArray()` against both a hard cap (e.g., `MAX_SIZE`) and the actual available `words.length`/`data.length` **before** allocating the array, independent of the `allowTvmSelfdestructRestriction` flag.
- Move the `sigArraySize`/`addrArraySize` bound checks in `BatchValidateSign.doExecute()` and `ValidateMultiSign.execute()` out of the feature-flag-gated block so they always apply.
- Reject calls where `offset + len` exceeds `words.length` before allocating, mirroring the bound-check style already used elsewhere (e.g., `RLP.verifyLength`, `ContractEventParser.subBytes`).

### Proof of Concept
1. Construct calldata for `batchvalidatesign(bytes32,bytes[],address[])` where the ABI head correctly points to a `signatures` offset and an `addresses` offset.
2. At the word pointed to by the addresses offset, place the length value `0x000000000000000000000000000000000000000000000000000000007FFFFFFF` instead of a small legitimate count.
3. Submit this as calldata in a `TriggerSmartContract`/`TriggerConstantContract` call (via HTTP `wallet/triggerconstantcontract` or gRPC) targeting the `0x…09` precompiled address, on a network where `allowTvmSelfdestructRestriction` is not activated.
4. `BatchValidateSign.doExecute()` calls `extractBytes32Array(words, addrOffsetWordIndex)`, which executes `new byte[2147483647][]`, causing an immediate `OutOfMemoryError` in the node's VM execution thread.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
