### Title
Recreating an access key with the same public key resets its nonce baseline below previously‑executed nonces, enabling transaction replay - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
When an access key is deleted and a new key is added with the *same* public key, the new key's nonce is unconditionally reseeded from the current block height rather than continuing from the deleted key's nonce. Because `transaction_validity_period` (the block-hash freshness window, ~1 day on mainnet) is checked independently of the nonce, a previously signed and already-executed `SignedTransaction` for that account/key can be resubmitted and re-executed after the key is deleted and recreated, as long as its referenced `block_hash` is still within the validity window and its nonce is below the freshly reseeded baseline.

### Finding Description
Access keys are addressed in the trie by `(account_id, public_key)`. `action_delete_key` fully removes the key entry [1](#0-0) , and `action_add_key` allows re-adding a key with the same public key once the old entry is gone (`AddKeyAlreadyExists` only fires while the key still exists) [2](#0-1) .

For a regular key, `add_regular_key` unconditionally overwrites the nonce with `initial_nonce_value(block_height)`, with no reference to any nonce the same public key previously reached: [3](#0-2) 

```rust
fn add_regular_key(...) {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    ...
}
```

`initial_nonce_value` is `(block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER (1_000_000)` [4](#0-3) . This seed is only guaranteed to be non-decreasing across time relative to fresh transactions signed *at* the current height; it has no relationship to a nonce that the very same public key already consumed in an earlier block (e.g. a nonce far below the current block's `1_000_000`-wide window).

Nonce verification (`verify_nonce`) only compares the tx's nonce against the *currently stored* access-key nonce; it has no memory of the key's prior incarnation once the key row was deleted and recreated: [5](#0-4) 

The only other check gating tx replay is the block-hash freshness check, which is orthogonal to nonces and allows any block-hash referenced within `transaction_validity_period` (86400 blocks ≈ 1 day on mainnet, documented at `docs/RuntimeSpec/Scenarios/FinancialTransaction.md:61-63`): [6](#0-5) 

The nearcore documentation itself flags this exact hazard as something a *wallet* must avoid by preserving the nonce on key recreation, confirming the protocol does not enforce it: [7](#0-6) 

Consequently: if an account's access key `K` is deleted and later re-added with the same public key (a fully permitted, unprivileged self-service operation, exactly like `setPosMode` in the referenced report is a self-service call that defeats a downstream enforcement check), the new key's nonce baseline can be lower than a nonce `K` already consumed earlier in the same validity window. Any previously broadcast/included `SignedTransaction` from that signer/key pair (public on-chain data) with a nonce in that now-reopened range becomes valid again and can be resubmitted by anyone holding a copy of it (the receiver, a relayer, or any chain observer), causing the runtime to execute the same action set (e.g., a `Transfer`, `FunctionCall`, etc.) a second time.

### Impact Explanation
This is a double-spend/replay primitive against the account whose key was recreated: an already-executed, previously-final transaction can be re-applied, duplicating its financial effect (e.g. double transfer/double invocation of a paid function call) without a fresh authorization from the signer. This matches the explicitly accepted impact category "double-spend/replay."

### Likelihood Explanation
Exploitation requires only two ordinary, unprivileged actions available to any full-access key holder: `DeleteKey` followed by `AddKey` with the identical public key (a supported, documented operation pattern — see the `swap_key` helper used throughout the integration tests, which chains exactly `DeleteKey` + `AddKey` in one transaction) [8](#0-7) . It does not require any validator/network/epoch privilege. The attacker needs a previously broadcast `SignedTransaction` for that account (trivially obtainable since transactions are public), and the exploit window is bounded only by `transaction_validity_period`, which is large on mainnet (~1 day).

### Recommendation
When adding a regular or gas key whose public key matches a key that previously existed on the account, do not blindly reseed the nonce from `initial_nonce_value(block_height)`. Either:
- Persist a per-account "highest nonce ever used" record per public key (or globally) that survives `DeleteKey`, and seed new keys to at least that value, or
- Require `initial_nonce_value` seeding to be monotonic against the maximum nonce previously observed for that exact public key on that account (not just derived from block height), closing the gap that lets deletion+recreation move the nonce baseline backward.

### Proof of Concept
1. Alice's account has full-access key `K` at nonce `N` after executing `Tx1` (e.g., `Transfer(1000 NEAR)` to Bob) at block height `H`, where `N` is within `[(H-1)*1_000_000, H*1_000_000)`.
2. At block height `H' <= H + transaction_validity_period`, Alice submits a single transaction with actions `[DeleteKey(K), AddKey(K, FullAccess)]` (`swap_key`-style, same public key) — a normal, permitted operation: `action_delete_key` removes the key row [9](#0-8) , then `action_add_key`/`add_regular_key` recreates it with `nonce = (H'-1)*1_000_000`, which is `<= N` whenever `H' <= H` or `N` falls in the low part of block `H`'s nonce window.
3. Anyone (Bob, a relayer, or a chain indexer) resubmits the original raw bytes of `Tx1`. `check_transaction_validity_period` passes because `Tx1.block_hash` is still within the window [6](#0-5) , and `verify_nonce` passes because `Tx1`'s nonce `N > current stored nonce (H'-1)*1_000_000` [5](#0-4) .
4. `Tx1` is re-executed: Alice's `Transfer(1000 NEAR)` to Bob is applied a second time, without any new authorization from Alice.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}

pub fn check_transaction_validity_period(
    chain_store: &ChainStoreAdapter,
    prev_block_header: &BlockHeader,
    base_block_hash: &CryptoHash,
    transaction_validity_period: BlockHeightDelta,
) -> Result<(), InvalidTxError> {
    let base_header =
        chain_store.get_block_header(base_block_hash).map_err(|_| InvalidTxError::Expired)?;

    metrics::CHAIN_VALIDITY_PERIOD_CHECK_DELAY
        .observe(prev_block_header.height().saturating_sub(base_header.height()) as f64);

    // First check the distance between blocks
    if prev_block_header.height() > base_header.height() + transaction_validity_period {
        return Err(InvalidTxError::Expired);
    }

    // Then check if there is a path between the blocks (`base` is an ancestor of `prev`)
    validity_period_validate_is_ancestor(&base_header, prev_block_header, chain_store)
}
