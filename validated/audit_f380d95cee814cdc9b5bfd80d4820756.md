### Title
Unauthenticated `RecvError` packets allow forged tunnel teardown (DoS) - ([File: outside.go])

### Summary
Nebula's `RecvError` message type carries no signature, HMAC, or other cryptographic authentication root — it is a bare 16-byte header sent and accepted entirely outside the Noise-authenticated channel. An attacker who can spoof or observe/replay traffic on the path can trigger `handleRecvError` to tear down an established, authenticated tunnel using nothing but the destination's `localIndexId` and a matching source `UDPAddr`. This is the same bug class as the reported `StoreChunksRequest` issue: a message that drives real state changes (tunnel teardown) with no signature/authentication root tying it to a legitimate sender.

### Finding Description
`RecvError` packets are built and parsed as unencrypted, unauthenticated control messages: [1](#0-0) 

They are handled in `readOutsidePackets` before any decryption/authentication is applied — the type is dispatched right alongside `Handshake` in the "Unencrypted packets" branch: [2](#0-1) 

`handleRecvError` looks up the local hostinfo purely by the attacker-supplied `h.RemoteIndex` and the only "authentication" performed is comparing the packet's UDP source address against the currently known remote address of that hostinfo: [3](#0-2) 

If the comparison passes, `f.closeTunnel(hostinfo)` is called, which deletes the hostinfo from the hostmap: [4](#0-3) 

There is no HMAC, no Noise cipher-state involvement, and no certificate/PKI check anywhere in this path — unlike `Handshake` messages (which carry an HMAC over the Noise payload, see `handshake/handshake.proto`) or data-plane `Message`/`Control` packets (which are AEAD-decrypted via `ConnectionState.Decrypt`, see `outside.go:126`). The only "root of trust" for `RecvError` is a UDP source-address string match, which is:
- Trivially satisfiable by an off-path attacker who can spoof source IP/port (UDP has no handshake to validate the return path), or
- Trivially satisfiable by any on-path/MITM observer who can read the plaintext `RemoteIndex` from any other packet in the flow (it's sent in cleartext in every packet header) and knows the victim's real remote address.

This is architecturally the same defect as the reported analog: a control-plane message (`StoreChunksRequest` there, `RecvError` here) that causes the recipient to take a consequential action (service a chunk-storage request / tear down a tunnel) without any signature or other cryptographic binding to a legitimate, authenticated sender.

### Impact Explanation
A forged `RecvError` causes `closeTunnel` to be called, deleting the hostinfo and forcing a fresh handshake. Repeated forged packets let an attacker who can spoof/guess the (index, source-address) pair repeatedly tear down a victim's tunnels, denying service and forcing constant re-handshaking — directly analogous to the "DOS of the DA node" impact called out in the reference report. Nebula's own project history treats `recv_error` handling as security-sensitive: it added a config knob (`listen.send_recv_error`, and later `accept_recv_error`) specifically because of exposure/spoofing concerns (see CHANGELOG 1.10.1 and the 1.6.0-era security note), confirming this is a recognized risk surface, not a false positive.

### Likelihood Explanation
- No CA-signed certificate or valid-peer status is required by the attacker — `RecvError` is processed before any tunnel/cert validation.
- The `RemoteIndex` value needed is broadcast in cleartext in the header of every other packet on the flow, so any observer of the traffic (or a relay in relayed setups) can harvest it.
- The source-address check is the only gate, and UDP source addresses are well known to be spoofable without needing to complete any handshake, especially on networks without strict egress/ingress filtering.
- The default configuration (`recvErrorAlways`) accepts these packets from any endpoint unless the operator has explicitly hardened `accept_recv_error`.

### Recommendation
Bind `RecvError` (and any other message type that triggers state changes) to the authenticated Noise session, e.g., by requiring it be sent as an AEAD-protected data-plane message (like `CloseTunnel`) rather than a bare unauthenticated header, or by adding an HMAC/signature computed over the message using session key material established during the handshake. At minimum, do not rely solely on UDP source-address matching as an authentication root for actions that mutate connection state.

### Proof of Concept
1. Establish a legitimate tunnel between `A` and `B`; observe any packet from `B` to learn `B`'s `RemoteIndex` for the tunnel with `A` (sent in cleartext in the header of every packet, per `header` encoding used throughout `outside.go`).
2. From an attacker-controlled position capable of spoofing UDP source address `A`'s real remote address (or from an on-path observer), send a `RecvError` packet to `A` per `sendRecvError`'s wire format (`header.Encode(..., header.RecvError, 0, index, 0)`) with `index` = the learned `RemoteIndex`.
3. `A.handleRecvError` (outside.go:541) finds the hostinfo via `QueryReverseIndex`, the spoofed source address matches `hostinfo.GetRemote()`, and `closeTunnel` is invoked — tearing down the legitimate tunnel with no cryptographic proof the request came from `B`.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
