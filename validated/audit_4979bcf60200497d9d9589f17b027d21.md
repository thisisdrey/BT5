### Title
Uninitialized reward index defaults to global `INITIAL_INDEX`, granting instant reward equal to full token balance - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
Prototype pollution lets an attacker-controlled field become the *default* inherited value for an object, bypassing validation. The analog in `RewardsDistributor` is the default/fallback account index: when `accountIndexOf[token][account] == 0` (never initialized), the code falls back to a shared sentinel (`INITIAL_INDEX`) only if the current token index is *strictly greater* than `INITIAL_INDEX`. In the window where `tokenStates[token].index == INITIAL_INDEX` (a freshly speed-enabled token, before any time elapses), the fallback is skipped, the account index stays `0`, and `_deltaIndex = INITIAL_INDEX - 0 = 1e18`, crediting the caller `tokensAccruedOf = balance * 1e18 / 1e18 = balance` — i.e. a default "prototype" value of 0 is inherited as if it were a legitimately accrued index.

### Finding Description
In `_calculateTokenDelta` (`contracts/RewardsDistributor.sol:217-231`):

```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When a governor sets a nonzero speed for a new token, `_updateTokenSpeed` stores `TokenState({index: INITIAL_INDEX, timestamp: now})` (`contracts/RewardsDistributor.sol:298`). Until `block.timestamp` advances, `_updateTokenIndex` leaves `index == INITIAL_INDEX`. Any account with `accountIndexOf[token][account] == 0` then computes `_deltaIndex = 1e18` and `_tokensDelta = balanceOf(account)`, because the strict `>` comparison prevents the `INITIAL_INDEX` fallback from applying at equality.

`updateBeforeMintOrBurn` is explicitly permissionless ("may be called by anyone", `contracts/RewardsDistributor.sol:173-180`), so an unprivileged EOA can trigger `_updateTokensAccruedOf` directly in the same block the speed is set, writing `tokensAccruedOf[attacker] += attackerBalance`. `claimRewards` then pays out via `_transferRewardIfEnoughTokens` (`contracts/RewardsDistributor.sol:248-256`) as long as the distributor holds enough `rewardToken`.

No modifier stops this: `updateBeforeMintOrBurn` has no access control and no nonReentrant requirement on the accounting path; `claimRewards` is `nonReentrant` but that does not prevent a plain sequential call. `onlyIfTokenExists`/`onlyGovernor` guard only the speed-setting path, which is a legitimate configuration action — the bug is the equality-edge default handling afterward.

### Impact Explanation
An attacker holding a large balance of a newly speed-enabled `DepositToken`/`DebtToken` (which can be obtained via flash loan or a fresh deposit, since `balanceOf` is read at accrual time) can instantly accrue claimable rewards equal to their full token balance, draining the distributor's `rewardToken` reserves that were intended to be emitted over time to all suppliers/borrowers. This is theft of unclaimed yield from honest users and can exhaust the distributor's balance.

### Likelihood Explanation
Requires calling `updateBeforeMintOrBurn` (or `claimRewards`) within the same `block.timestamp` in which the governor first sets `tokenSpeeds[token] > 0` for that token. This is observable in the mempool and can be done via backrunning/bundling; the function is public and requires no privilege. The attacker only needs token balance at call time (flash-loanable or depositable in the same transaction sequence is not possible across the speed-setting tx, but on chains with 1-2s blocks and public mempools, sandwiching the governance tx is feasible). Impact is capped by `rewardToken.balanceOf(distributor)` and the attacker's token balance, which can be very large via deposit.

### Recommendation
Change the fallback condition so the sentinel default applies at equality as well:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

or initialize `accountIndexOf` for all existing holders / treat `_accountIndex == 0` as `_tokenIndex` when `tokenStates[token_]` was just created. Alternatively, in `_updateTokenSpeed`, record `accountIndexOf` lazily but clamp `_deltaIndex` so a zero account index can never produce a positive delta when the token index is still `INITIAL_INDEX`.

### Proof of Concept
Hardhat-style reproduction (against the existing test scaffolding in `test/`):

```ts
// setup: pool, depositToken (msdToken), distributor initialized with rewardToken,
// distributor funded with rewardToken, user holds `balance` of msdToken
// (e.g. via msdToken.deposit(amount, user.address))

// 1. Governor enables rewards for the token
await distributor.connect(governor).updateTokenSpeed(msdToken.address, speed);

// 2. In the SAME block (same timestamp), attacker calls the permissionless hook
await distributor.connect(attacker).updateBeforeMintOrBurn(msdToken.address, attacker.address);

// 3. tokenStates.index == INITIAL_INDEX, accountIndexOf == 0
//    => _deltaIndex = 1e18 => tokensAccruedOf[attacker] == balanceOf(attacker)
expect(await distributor.tokensAccruedOf(attacker.address)).to.eq(
  await msdToken.balanceOf(attacker.address)
);

// 4. Attacker claims real rewardToken immediately
await distributor.connect(attacker).claimRewards(attacker.address);
// attacker receives min(accrued, distributor rewardToken balance)
```

Key assertion: without the fix, `tokensAccruedOf[attacker]` equals their full token balance instead of `0` (no time has elapsed, so no rewards should have accrued). After the fix (`>=`), the delta is `0` and nothing is claimable.
