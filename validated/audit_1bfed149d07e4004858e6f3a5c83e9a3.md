Audit Report

## Title
LP share price manipulation via direct asset donation to `AssetConversion` pool account causes depositor fund loss through rounding - (File: `substrate/frame/asset-conversion/src/lib.rs`)

## Summary
`pallet-asset-conversion` computes pool reserves from the *live* balance of the deterministic pool account via `Self::get_balance` rather than from pallet-tracked state that is mutated only through `add_liquidity`/`remove_liquidity`/`swap`. This allows any unprivileged account to inflate the reserve-to-LP-supply ratio by directly transferring assets to the pool account, causing subsequent legitimate depositors to receive a floor-rounded, disproportionately small LP-token mint whose lost value is redistributed pro-rata to existing LP holders (the attacker).

## Finding Description
`do_add_liquidity` reads reserves directly from live balances rather than internal state: [1](#0-0) 

For non-initial deposits, the LP mint amount is computed via floor (integer) division against these live reserves and `total_supply`, gated only by a fixed absolute `MintMinLiquidity` threshold rather than a proportional guard: [2](#0-1) 

`do_remove_liquidity` uses the same live-balance-derived reserves to compute withdrawal amounts: [3](#0-2) 

Because reserves are simply `T::Assets::balance(asset, pool_account)` rather than pallet-tracked accounting, any account can transfer assets directly to the deterministic, publicly-derivable pool account (via `T::PoolLocator::address`) without minting any LP tokens, inflating `reserve1`/`reserve2` independently of `total_supply`. A subsequent depositor's `lp_token_amount = floor(amount * total_supply / reserve)` then truncates a larger absolute amount of value than normal (because each LP token now represents a much larger quantity of underlying assets), and that truncated remainder is absorbed into pool reserves, benefiting existing LP holders — including the attacker who orchestrated the donation — proportionally to their existing share upon a later `remove_liquidity` call. The only existing guard, `ensure!(lp_token_amount > T::MintMinLiquidity::get())`, is a fixed constant and does not scale with the inflation ratio, so it does not prevent the rounding-driven value transfer; it only prevents dust-level mints, forcing the victim to contribute proportionally more before the deposit is even accepted, which does not eliminate the loss.

## Impact Explanation
This is a fund-conservation violation in a public, permissionless AMM pallet deployed on Asset Hub–style runtimes: value contributed by an honest depositor is misappropriated by an unprivileged actor purely through public `transfer` and `add_liquidity`/`remove_liquidity` extrinsics, without any admin, governance, or validator privilege. This matches the "Balances, assets... conserve value and settle exactly once to the rightful beneficiary and amount" pivot, and the exact corrupted values are the `reserve1`/`reserve2` figures used in `mul_div` for both minting (`do_add_liquidity`) and redemption (`do_remove_liquidity`), which diverge from the actual LP-backing state tracked only via `total_supply`.

## Likelihood Explanation
The exploit requires only two ordinary, unprivileged extrinsics: an initial `add_liquidity` call to become an LP holder above the fixed `MintMinLiquidity` threshold, and a standard asset `transfer` to the deterministic pool account address (independently derivable by any account via `T::PoolLocator::address`, with no protection against arbitrary incoming transfers). No relayer, validator, governance, or off-chain component is involved, making this fully attacker-controlled and repeatable across any asset-conversion pool.

## Recommendation
Track pool reserves as pallet-internal storage mutated only by `add_liquidity`, `remove_liquidity`, and `swap` (Uniswap V2-style `reserve0`/`reserve1` state with an explicit, access-controlled `sync`/`skim` mechanism) instead of trusting the live balance of the pool account returned by `get_balance`. Additionally, consider bounding how far the live balance may diverge from the tracked reserve before requiring an explicit reconciliation step, and/or introducing a proportional minimum-mint guard rather than only the fixed `MintMinLiquidity` constant.

## Proof of Concept
1. Alice creates a pool for `(Native, AssetX)` and calls `add_liquidity` with `201`/`201`, receiving `101` LP tokens while `100` are permanently minted to the pool account per `T::MintMinLiquidity` (`substrate/frame/asset-conversion/src/lib.rs:858-877`); `total_supply = 201`.
2. Alice computes the deterministic pool account address via `T::PoolLocator::address` and sends an ordinary `transfer` of `1_000_000_000` of `Native` and `AssetX` directly to it, bypassing `add_liquidity`; `total_supply` is unchanged while `reserve1`/`reserve2` (read via `get_balance`, `substrate/frame/asset-conversion/src/lib.rs:813-814`) jump to `~1_000_000_201`.
3. Bob calls `add_liquidity` with a real contribution; `lp_token_amount = floor(amount * 201 / reserve)` truncates a meaningful fraction of Bob's contribution's true proportional share due to the inflated reserve (`substrate/frame/asset-conversion/src/lib.rs:868-877`), and the fixed `InsufficientLiquidityMinted` check does not compensate for this since it is a flat threshold, not proportional.
4. Alice calls `remove_liquidity` for her `101` LP tokens; her redemption is computed as `floor(lp_redeem_amount * reserve / total_supply)` (`substrate/frame/asset-conversion/src/lib.rs:919-921`) against the reserve inflated partly by her donation and partly by Bob's under-compensated deposit, letting her recapture value disproportionate to her original contribution.
