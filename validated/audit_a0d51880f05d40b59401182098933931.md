### Title
Relay control messages trust attacker-supplied `RelayFromAddr` identity instead of the authenticated peer's certificate-bound VPN address - (File: `relay_manager.go`)

### Summary
`handleCreateRelayRequest` in `relay_manager.go` accepts a `CreateRelayRequest` control message from an already-authenticated peer `h` and uses the message's self-reported `RelayFromAddr` field (`from`) — not `h`'s certificate-bound VPN address (`h.vpnAddrs[0]`) — as the identity that gets registered in `h.relayState` and later used for relay routing decisions.

### Finding Description
When a `NebulaControl_CreateRelayRequest` is received, the handler decodes `from := protoAddrToNetAddr(m.RelayFromAddr)` directly from the wire message payload sent by peer `h`: [1](#0-0) 

It then only checks whether `from` equals *my own* address (self-relay protection), never that `from` matches the sender's own authenticated `h.vpnAddrs[0]`: [2](#0-1) 

When the relay target is "me", the code inserts a `TerminalType, Established` relay entry into `h.relayState`, keyed by the attacker-controlled `from` value, with no comparison against `h.vpnAddrs`: [3](#0-2) 

This is structurally identical to the reported `Treasury.sol` bug: a security-relevant identity parameter (`from` in `deposit()`, `RelayFromAddr` here) is taken from caller/attacker-supplied input rather than being derived from the verified identity of the actual authenticated caller (`msg.sender` in Solidity, `h`'s certificate/VPN address bound during the Noise handshake in Nebula, e.g. as validated in `validatePeerCert`: [4](#0-3) ). The relay subsystem correctly authenticates *that a message came from `h`*, but not *that `h` is entitled to claim identity `from`*.

The same unchecked `from` binding is used symmetrically in `AddRelay`, which stores `PeerAddr: vpnIp` inside `relayState` without any certificate-based verification: [5](#0-4) . This `PeerAddr` later drives forwarding lookups such as `QueryVpnAddrsRelayFor(hostinfo.vpnAddrs, relay.PeerAddr)` in the data path: [6](#0-5) .

### Impact Explanation
Any authenticated peer `h` (i.e., any node that has completed a normal, valid handshake — no CA-signed cert of the victim needed) can send a `CreateRelayRequest` claiming `RelayFromAddr` equal to a legitimate victim node's VPN address. This poisons the relay state on the target node (`h.relayState`), registering the attacker's own hostinfo/connection as the authoritative `TerminalType`/`Established` relay endpoint for the victim's VPN address. Consequences:
- Remote relay-state poisoning: legitimate future `CreateRelayRequest`s that genuinely originate from the real victim can collide with the attacker-installed state (`existingRelay.RemoteIndex != m.InitiatorRelayIndex` checks in the `Established`/`Disestablished` branches will reject them as mismatches), disrupting the victim's ability to establish relayed connectivity through this node.
- On the "target is not me" (forwarding) branch, the same unverified `from` is used to install `ForwardingType` relay entries keyed by the spoofed address on intermediate relay nodes, extending the poisoning across the relay mesh.

This does not bypass the underlying Noise/AEAD encryption of any specific peer's tunnel, but it does corrupt the relay routing/identity bookkeeping that Nebula relies on to know "who owns this VPN address on this relay", which is a remote state-poisoning vulnerability reachable by any authenticated (but otherwise unprivileged) peer.

### Likelihood Explanation
High reachability: no CA-signed certificate of the victim is required — only a normal, valid Nebula certificate for the attacker's own node, which is enough to complete a handshake and become an authenticated peer `h`. From there, sending a crafted `Control`/`CreateRelayRequest` message with an arbitrary `RelayFromAddr` is trivial and requires no race condition or privileged position (unlike the wrong-responder/evil-lighthouse tests in `handshakes_test.go`, which are already defended against, this path has no equivalent identity check).

### Recommendation
In `handleCreateRelayRequest` (and symmetrically in `handleCreateRelayResponse`), reject the request/response unless the message's declared `RelayFromAddr` equals the authenticated sender's own certificate-bound VPN address (`h.vpnAddrs`), mirroring how `validatePeerCert` binds handshake-derived identity to the certificate. Only trust `from` when it can be proven to be `h`'s own identity; for the "I am the middle-man" forwarding case, derive the from-identity from the already-authenticated hostinfo rather than from unauthenticated request fields.

### Proof of Concept
1. Attacker node `Evil` completes a normal, valid handshake with `Target` using its own legitimately-issued certificate (VPN address `evil-ip`), becoming an authenticated `HostInfo` `h` on `Target`.
2. `Evil` sends `Target` a `Control` message of type `NebulaControl_CreateRelayRequest` with `RelayFromAddr = victim-ip` (the real Victim's VPN address) and `RelayToAddr = target-ip` (Target's own address).
3. `Target.handleCreateRelayRequest` sees `target == me`, finds no existing relay for `from = victim-ip` in `h.relayState`, and calls `AddRelay(..., h, f.hostMap, victim-ip, &m.InitiatorRelayIndex, TerminalType, Established)` — installing state on `Evil`'s own hostinfo claiming it is the terminal relay endpoint for Victim's VPN address, without any check that `Evil`'s certificate/`h.vpnAddrs` actually is `victim-ip`.
4. If the real `Victim` later attempts to establish a genuine relay through `Target` for the same address, its `CreateRelayRequest`/`CreateRelayResponse` exchange collides with the attacker-poisoned state (index mismatch checks reject it), disrupting Victim's connectivity through this relay.

func AddRelay(l *slog.Logger, relayHostInfo *HostInfo, hm *HostMap, vpnIp netip.Addr, remoteIdx *uint32, relayType int, state int) (uint32, error) {
	hm.Lock()
	defer hm.Unlock()
	for range 32 {
		index, err := generateIndex(l)
		if err != nil {
			return 0, err
		}

		_, inRelays := hm.Relays[index]
		if !inRelays {
			// Avoid standing up a relay that can't be used since only the primary hostinfo
			// will be pointed to by the relay logic
			//TODO: if there was an existing primary and it had relay state, should we merge?
			if !hm.unlockedMakePrimary(relayHostInfo) {
				// The tunnel was torn down after the caller grabbed relayHostInfo. A relay standing
				// on an unlinked hostinfo would never carry traffic, and its Relays entry could
				// never be reclaimed since the delete-time cleanup has already run.
				return 0, errors.New("relay hostinfo is no longer in the hostmap")
			}

			hm.Relays[index] = relayHostInfo
			newRelay := Relay{
				Type:       relayType,
				State:      state,
				LocalIndex: index,
				PeerAddr:   vpnIp,
			}

			if remoteIdx != nil {
				newRelay.RemoteIndex = *remoteIdx
			}
			relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)

			return index, nil
		}

func (hm *HandshakeManager) validatePeerCert(via ViaSender, remoteCert *cert.CachedCertificate) ([]netip.Addr, bool, bool) {
	f := hm.f
	vpnNetworks := remoteCert.Certificate.Networks()

	// The cert package rejects host certs with no networks at parse time, so
	// reaching this state would mean an invariant was bypassed elsewhere.
	// Refuse explicitly so downstream code (which indexes vpnAddrs[0]) can't
	// panic if that invariant ever changes.
	if len(vpnNetworks) == 0 {
		f.l.Info("No networks in certificate",
			"from", via, "cert", remoteCert)
		return nil, false, false
	}

	vpnAddrs := make([]netip.Addr, len(vpnNetworks))
	anyVpnAddrsInCommon := false

	for i, network := range vpnNetworks {
		if f.myVpnAddrsTable.Contains(network.Addr()) {
			f.l.Error("Refusing to handshake with myself",
				"vpnNetworks", vpnNetworks,
				"from", via,
				"certName", remoteCert.Certificate.Name(),
				"certVersion", remoteCert.Certificate.Version(),
				"fingerprint", remoteCert.Fingerprint,
				"issuer", remoteCert.Certificate.Issuer(),
			)
			return nil, false, false
		}
