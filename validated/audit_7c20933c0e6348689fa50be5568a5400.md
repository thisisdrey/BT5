### Title
Stale `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` trie entries survive `DeleteAccount`, allowing a self-planted promise to execute privileged actions (`AddKey`/`DeployContract`/`DeleteKey`) against a re-created account of the same name - ([File: core/store/src/utils/mod.rs])

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:505-575`) only clears `TrieKey::Account`, `TrieKey::ContractCode`, the `AccessKey`/gas-key prefix, and `TrieKey::ContractData` for the deleted account: [1](#0-0) [2](#0-1) 

It never iterates or removes `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount`, all of which are keyed by `receiver_id` (i.e. the account being deleted) as confirmed by their definitions in `core/primitives/src/trie_key.rs` and their writers/readers in `runtime/runtime/src/lib.rs`. Because a postponed `ActionReceipt` is stored keyed only by account name and not by any account "generation"/creation nonce, once the account name is freed by `DeleteAccount` and re-registered via `CreateAccount`, the trie entries for the outstanding postponed receipt are still present and addressed to the (new) account of the same name. When the corresponding `DataReceipt` finally arrives, the runtime resumes the postponed receipt and applies its actions against whatever account currently occupies that name. If the original postponed receipt had `predecessor_id == receiver_id == account_id` (a self-addressed promise), the runtime's actor-permission rule for self-actions (`check_actor_permissions`, `runtime/runtime/src/actions.rs`) treats `actor_id == receiver_id` as sufficient authorization for `AddKey`/`DeployContract`/`DeleteKey`, without re-validating that the account's identity/lineage is unchanged since the receipt was created.

This breaks the invariant that a promise must not carry owner privilege across account re-creations: the account-deletion cleanup path is asymmetric — it deletes the account's live state but not its outstanding "future" obligations recorded in the postponed-receipt trie keys.

### Impact Explanation
If exploited against a name that changes ownership between delete and re-create (e.g. an account-name marketplace, a squatted/dropped name, or any workflow where a different party re-registers a freed `AccountId`), the former owner's dangling postponed receipt can silently plant a full-access key (or replace the deployed contract) on the new owner's account — an authorization escalation across account lifetimes / account takeover. This matches the NEAR bug-bounty category for authorization escalation across accounts/promises.

### Likelihood Explanation
Exploitability hinges on the attacker being able to keep an `input_data_ids` dependency of a self-addressed receipt unresolved for the multi-transaction window needed to run `DeleteAccount` and `CreateAccount`. Under normal `Promise::then`/`promise_and` semantics, the producing receipt's execution deterministically generates the corresponding `DataReceipt` fairly quickly (same or a few blocks later), which limits — but does not eliminate — the attacker's window; cross-shard congestion or attacker-controlled delay of the producing receipt could be used to widen this window. No special privileges beyond an ordinary funded account and self-deployed contracts are required, and the account-deletion/re-creation primitives are unrestricted (`DeleteAccount` succeeds with no locked balance, `CreateAccount` on a freed name is always permitted).

### Recommendation
`remove_account` (or the `DeleteAccount` action handler in `runtime/runtime/src/actions.rs`) must also enumerate and remove `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, and `TrieKey::PendingDataCount` entries for the account being deleted (and correspondingly free/refund the associated postponed receipts) before the account is deleted, or reject `DeleteAccount` while any postponed receipts are outstanding for that account.

### Proof of Concept
Runtime apply-path integration test (in `runtime/runtime/src/tests/apply.rs` style):
1. Create account `victim.test` and, via a receipt, place it into a postponed state: send a self-addressed `ActionReceipt` with `predecessor_id == receiver_id == "victim.test"`, `actions = [AddKeyAction(full_access)]`, and `input_data_ids = [bogus_data_id]` that is never produced by execution.
2. Assert `TrieKey::PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` exist for `victim.test`.
3. Submit `DeleteAccount { beneficiary_id: <attacker-controlled> }` from `victim.test` and apply it; assert `Account`/`AccessKey` entries are gone but the postponed-receipt trie keys are still present.
4. Submit `CreateAccount` re-registering `victim.test` with a fresh key controlled by a different (victim) key pair.
5. Deliver a `DataReceipt` with `data_id == bogus_data_id`, causing the postponed receipt to resume.
6. Assert that the new `victim.test` account's access-key set now contains the attacker-planted full-access key that `CreateAccount` did not add — demonstrating unauthorized privilege injection into the re-created account.
