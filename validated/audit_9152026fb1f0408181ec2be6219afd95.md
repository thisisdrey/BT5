## Analog Found: Unbacked Exchange‑Pool Balance via Floating‑Point Exchange Math (No Negative-Balance Check on Legacy Path)

### Title
Floating-point Bancor pricing in the default (non-hardened) `ExchangeCapsule.transaction()` path allows exchange-pool balances to go negative, letting a caller extract more token/TRX value than the pool holds - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
The Ankr incident stemmed from a liquid-staking contract whose internal accounting could produce a token balance that was not actually backed by underlying collateral, which was then redeemed against a lending pool for real value. `java-tron`'s built-in Bancor-style Exchange (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeTransactionContract`) has an analogous accounting weak point: the default (`hardenedCalc == false`) arithmetic path in `ExchangeCapsule.transaction()` computes new pool balances using `double`/`Math.pow` floating-point math and only rejects the result if `hardenedCalc` is true.

### Finding Description
`ExchangeCapsule.transaction()` [1](#0-0)  computes `buyTokenQuant` via `ExchangeProcessor.exchange()`, which relies on `Math.pow`-based floating point calculations in `exchangeToSupply`/`exchangeFromSupply` [2](#0-1) . After computing the new balances, the method only validates for negative resulting balances `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0))` [3](#0-2) . When `hardenedCalc` (`allowHarden()`) is not active, the new pool balances are stored unconditionally, even if the floating-point rounding drives a token's pool balance below the amount actually deposited, or even negative.

`ExchangeTransactionActuator.execute()` invokes this same unguarded path: `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` [4](#0-3) , then unconditionally credits `anotherTokenQuant` to the caller's TRX balance or TRC10 asset balance via `addAssetAmountV2`/`setBalance` [5](#0-4) , and persists the (possibly unbacked) pool state with `Commons.putExchangeCapsule` [6](#0-5) . Validation in `doValidate()` only bounds the *upper* limit of a token balance (`balanceLimit`) and checks `tokenExpected` is met [7](#0-6) ; it never re-derives or bounds the resulting counter-token pool balance for the non-hardened path, so nothing stops a sequence of small/edge-case trades from causing the double-precision Bancor formula to output more tokens than the pool actually holds — i.e., the caller redeems value the pool never received, exactly analogous to Ankr's unbacked-mint-then-redeem pattern, but here achieved through floating-point drift in the on-chain constant-"virtual-supply" AMM math instead of a staking-contract accounting bug.

The `hardenedCalc`/`SafeExchangeProcessor` path exists specifically to add integer/negative-balance safety, confirming the un-hardened path is the known-weaker legacy code still reachable whenever `allowHarden()` (a chain parameter) is not enabled.

### Impact Explanation
If exploitable (via crafted `tokenQuant`/pool-balance ratios exploiting `double` rounding in `Math.pow`), an attacker can repeatedly extract TRX or TRC10 tokens from an Exchange pool beyond what was deposited, directly draining pool liquidity that other participants funded — a concrete theft-of-funds / unbacked-balance condition reachable by any account that creates or trades against an Exchange via a single signed `ExchangeTransactionContract`. This matches the "unbacked balance / theft of funds" impact bar required for a valid analog.

### Likelihood Explanation
Likelihood depends on whether `allowHarden()` (chain parameter for `AllowHardenExchangeCalculation`, see the dedicated `SafeExchangeProcessor`/hardened tests in `ExchangeTransactionActuatorTest`) is enabled on a given network. On any deployment where the hardening proposal is not active, the legacy floating-point path is unconditionally reachable by an unprivileged trader through the public `ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract` — no special privileges are required, only exchange participation.

### Recommendation
- Make the negative/insufficient-balance check in `ExchangeCapsule.transaction()` unconditional (not gated behind `hardenedCalc`), or fully retire the floating-point `ExchangeProcessor` in favor of `SafeExchangeProcessor` for all networks regardless of the `allowHarden` flag.
- Add a network-wide upgrade/hard-fork parameter to force-enable hardened exchange math, and add invariant checks in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`/`ExchangeTransactionActuator` that recompute pool balances from stored token reserves before persisting.

### Proof of Concept
A concrete PoC requires enumerating specific `firstTokenBalance`/`secondTokenBalance`/`tokenQuant` combinations that trigger `double` rounding divergence large enough to make `newFirstTokenBalance`/`newSecondTokenBalance` in `ExchangeProcessor.exchange()` inconsistent with true conservation (i.e., `buyTokenQuant` computed via floating point exceeds what `sellTokenQuant` actually funds). This requires running `ExchangeProcessor.exchange()` (and its `Maths.pow` dependency) offline with adversarial small-balance/large-quant inputs to find a divergence; the code paths and missing check are established above, but I could not fully derive an exact triggering numeric example from static review alone. package org.tron.core.capsule;

import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.Maths;

@Slf4j(topic = "capsule")
public class ExchangeProcessor implements ExchangeCapsule.Processor {

  private long supply;
  private final boolean useStrictMath;

  public ExchangeProcessor(long supply, boolean useStrictMath) {
    this.supply = supply;
    this.useStrictMath = useStrictMath;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

}
