### Title
`NativeWithdraw` has no resolver to re-credit the signer when the final `Promise::new(receiver_id).transfer(amount)` fails, permanently destroying escrowed wNEAR - (File: contracts/defuse/src/contract/tokens/nep141/native.rs)

### Summary
`Contract::native_withdraw` debits the signer's internal wNEAR ledger balance and then chains `near_withdraw()` → `do_native_withdraw()`, whose only action is `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)`. Unlike the sibling `ft_withdraw`/`mt_withdraw` flows, this path has no `*_resolve_withdraw` callback that inspects the transfer's promise result and re-credits the ledger on failure, so an attacker-chosen non-existent `receiver_id` causes the escrowed NEAR to be lost from the ledger's accounting while never reaching the intended recipient.

### Finding Description
The binding that must hold is: `wnear_debited(signer_id) == near_delivered(receiver_id) + near_recredited(signer_id)`.

Trace:
1. `Contract::native_withdraw` (contracts/defuse/src/contract/intents/state.rs:212-240) calls `self.withdraw(owner_id, [(wNEAR TokenId, amount)], ...)`, which debits the signer's internal wNEAR balance via `internal_sub_balance` (state.rs:171-195) — this is the ledger-side debit, executed synchronously and irreversibly within this receipt.
2. It then schedules `ext_wnear::near_withdraw(...)` and chains `.then(do_native_withdraw(withdraw))` (state.rs:223-237).
3. `Contract::do_native_withdraw` (contracts/defuse/src/contract/tokens/nep141/native.rs:12-19) only checks that `near_withdraw` succeeded (`promise_result_checked_void(0)`), then returns `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)` as the final action in the chain — with **no further `.then()` callback**.
4. Contrast this with `internal_ft_withdraw`/`internal_mt_withdraw` (contracts/defuse/src/contract/tokens/nep141/withdraw.rs:53-107, contracts/defuse/src/contract/tokens/nep245/withdraw.rs:59-125), both of which append a `ft_resolve_withdraw`/`mt_resolve_withdraw` callback (withdraw.rs:154-195, nep245/withdraw.rs:200-257) that inspects the final transfer's promise result and calls `self.deposit(sender_id, ...)` to refund any amount that failed to transfer.
5. Native withdraw has no equivalent. If `receiver_id` is a syntactically valid but non-existent (non-implicit) `AccountId`, the NEAR runtime's `Transfer` action to that receiver fails (the account does not exist), and there is no contract logic anywhere in this call chain that detects the failure and calls `internal_add_balance`/`deposit` to restore the signer's wNEAR ledger entry.
6. Because the failed NEAR ultimately refunds to the predecessor (the defuse contract's own account, not the signer's ledger balance), the escrow ledger permanently understates what the contract actually holds relative to what it recorded as delivered — the signer's wNEAR was debited, nothing was delivered to `receiver_id`, and nothing was recredited to the signer.

No existing guard prevents this: `withdraw()` performs the balance debit before the NEAR transfer is attempted and does not validate `receiver_id` existence; `do_native_withdraw` only guards the `near_withdraw` step, not the final `transfer`.

### Impact Explanation
The signer's escrowed wNEAR balance is debited and never restored, and no NEAR reaches `receiver_id` — this is a permanent, unauthorized loss of the signer's funds with no compensating credit anywhere in the ledger, matching "a batch whose balance changes do not net to zero so the Verifier owes more than it custodies." The attacker (an unprivileged signer acting against their own or any account they control) can repeat this per `NativeWithdraw` intent submitted, against any amount they hold, though this destroys the attacker's own funds rather than stealing from others — the practical exploitation value is that it demonstrates a missing-refund path also usable by any relayer/UI bug or accidental misconfiguration, and more importantly it is asymmetric with `ft_withdraw`/`mt_withdraw`, which correctly refund on failure, showing the guard was omitted specifically for `native_withdraw`.

### Likelihood Explanation
Trivial to trigger: any unprivileged holder of internal wNEAR balance can sign a `MultiPayload` containing a single `NativeWithdraw{ receiver_id, amount }` intent with `receiver_id` set to any syntactically valid NEAR account name that has never been created (e.g., `"nonexistent-account.near"`). No special role, relayer key, or victim key is required — the attacker only withdraws against their own already-owned wNEAR balance.

### Recommendation
Add a private `#[private]` resolver method (analogous to `ft_resolve_withdraw`/`mt_resolve_withdraw`) chained after the final `Promise::new(receiver_id).transfer(amount)` in `do_native_withdraw`, which checks the transfer's promise result via `promise_result_checked_void` and, on failure, calls `self.deposit(...)` (or `internal_add_balance`) to re-credit the signer's wNEAR balance for the failed amount.

impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
}

#[near]
impl MultiTokenWithdrawResolver for Contract {
    #[private]
    fn mt_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        token_ids: Vec<defuse_nep245::TokenId>,
        amounts: Vec<U128>,
        is_call: bool,
    ) -> Vec<U128> {
        require!(
            token_ids.len() == amounts.len() && !amounts.is_empty(),
            "invalid args"
        );

        let mut used = if is_call {
            // `mt_batch_transfer_call` returns successfully transferred amounts
            match promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len()) {
                Ok(Ok(used)) if used.len() == amounts.len() => used,
                Ok(_) => vec![U128(0); amounts.len()],
                // do not refund on failed `mt_batch_transfer_call` due to
                // NEP-141 vulnerability: `mt_resolve_transfer` fails to
                // read result of `mt_on_transfer` due to insufficient gas
                Err(_) => amounts.clone(),
            }
        } else {
            // `mt_batch_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amounts.clone()
            } else {
                vec![U128(0); amounts.len()]
            }
        };

        self.deposit(
            sender_id,
            token_ids
                .into_iter()
                .zip(amounts)
                .zip(&mut used)
                .filter_map(|((token_id, amount), used)| {
                    // update min during iteration
                    used.0 = used.0.min(amount.0);
                    let refund = amount.0.saturating_sub(used.0);
                    if refund > 0 {
                        Some((Nep245TokenId::new(token.clone(), token_id).into(), refund))
                    } else {
                        None
                    }
                }),
            Some(REFUND_MEMO),
        )
        .unwrap_or_else(|err| err.panic());

        used
    }
}
