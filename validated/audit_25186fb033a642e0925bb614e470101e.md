### Title
Stale in-memory account overwrite in market order self-matching causes permanent loss of maker credit - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
An unprivileged account can submit a `MarketSellAssetContract` transaction (via `MarketSellAssetActuator`) that matches against its own resting order (self-trade). Because the maker-side balance credit is applied to a freshly-fetched `AccountCapsule` from `accountStore` while the taker-side object is a separately held in-memory reference that is written back to the same DB key at the very end of `execute()`, the maker credit gets silently overwritten and lost when the taker and maker are the same account.

### Finding Description
In `MarketSellAssetActuator.execute()` [1](#0-0) , the taker's `AccountCapsule` is loaded once from `accountStore` and passed by reference through `matchOrder()`/`matchSingleOrder()`. All taker-side balance updates during matching are performed in-memory on this single object via `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule)` [2](#0-1) , and it is only persisted at the very end of `execute()` via `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` [3](#0-2) .

In contrast, the maker-side credit is applied by the two-argument overload `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` [4](#0-3) , which independently re-fetches the maker's account from `accountStore.get(...)`, mutates it, and immediately calls `accountStore.put(...)` — persisting the credited balance right away, inside `matchSingleOrder()` at line 490.

If a taker's order matches against a maker order that belongs to the **same account** (self-trade — nothing in `validate()` or `matchOrder()` prevents an account from matching its own resting order), both code paths operate on the *same DB key* but with two distinct, unsynchronized `AccountCapsule` objects:
1. The maker-side `addTrxOrToken(makerOrderCapsule, num)` immediately commits the maker credit to `accountStore`.
2. At the end of `execute()`, the taker's stale in-memory `accountCapsule` (which does not reflect the maker credit written in step 1) is written back to the same key, overwriting and erasing the credit applied in step 1.

The net effect: the account is debited for the sell side (fee + sold asset) but the maker-side buy credit it should have received from matching its own order is silently discarded.

### Impact Explanation
This is a concrete unbacked-balance/fund-loss bug reachable by any account submitting a single signed `MarketSellAssetContract` transaction that self-matches. The affected account permanently loses the tokens/TRX it was owed as the maker side of the match — the sold asset is debited, the order is marked filled/inactive and removed from the order book, but the corresponding proceeds are dropped. This constitutes permanent loss of a user's own funds through normal, unprivileged use of the on-chain order-matching feature, without needing any privileged role, matching the "permanent freezing/loss of funds" impact category.

### Likelihood Explanation
Triggering this requires only: (1) TRON Market Transaction feature enabled (`supportAllowMarketTransaction`), (2) the same account placing a resting sell order for pair (A,B) and later placing an opposite sell order for pair (B,A) that price-matches its own resting order. Both steps are ordinary, permissionless operations available to any account via `MarketSellAssetContract`, so likelihood is high for any user who (intentionally or accidentally) crosses their own orders.

### Recommendation
In `matchSingleOrder()`, detect when `makerOrderCapsule.getOwnerAddress()` equals the taker account's address and, in that case, apply both the taker-side and maker-side balance mutations to the **same in-memory `AccountCapsule` instance** (or otherwise synchronize/merge the two updates) before any `accountStore.put()` call, rather than allowing two independently-fetched copies of the same account to be persisted where the later write silently overwrites the earlier one. More generally, `addTrxOrToken(MarketOrderCapsule, long)` should not perform its own store fetch/put independently of the taker's already-loaded account object when the owner addresses coincide.

### Proof of Concept
1. Enable market transactions (`supportAllowMarketTransaction` = true, as required for `MarketSellAssetActuator.validate()`).
2. Account `X` submits `MarketSellAssetContract`: sell 100 of token A for 200 of token B → order O1 rests in the book (no match, empty book).
3. Account `X` (same account) submits `MarketSellAssetContract`: sell 200 of token B for 100 of token A → this order matches O1 exactly (`takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` branch in `matchSingleOrder`).
4. During `matchSingleOrder`: `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` fetches account `X` fresh from `accountStore`, credits it with the maker proceeds (100 of token A), and calls `accountStore.put()` immediately.
5. Back in `execute()`, the taker-side `accountCapsule` object (loaded before matching began, held in memory, and updated only for taker-side credit) is written via `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` at line 148 — this stale copy overwrites the DB entry from step 4, discarding the 100 token A maker credit.
6. Final state: account `X` paid the sell-side asset+fee for both orders but received only the taker-side credit; the maker-side credit (100 token A) is unbacked/lost, verifiable by comparing pre- and post-transaction total asset supply held by account `X` vs. expected balance from order arithmetic.
