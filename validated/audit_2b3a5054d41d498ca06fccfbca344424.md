## Title
Exchange trade math relies on double-precision floating point Bancor formula, enabling profit extraction via crafted trades against a TRC10 Exchange pool - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

## Summary
The reported incident describes a flash-loan attack that manipulated an AMM-style pool's price/reserve math within a single set of transactions to extract value. The closest reachable analog in java-tron is the TRC10 `Exchange` (Bancor-relay) pool, which any unprivileged account can trade against via `ExchangeTransactionActuator`. The core exchange calculation is performed by `ExchangeProcessor`, which is used by default (when `allowHardenExchangeCalculation` is not enabled) and uses `double`-precision floating point arithmetic (`Math.pow`) to compute swap outputs, rather than exact integer/BigDecimal math. This is the same bug class that underlies AMM flash-loan/precision exploits: rounding and floating-point error in reserve math can be leveraged by an attacker issuing a sequence of ordinary, unprivileged `ExchangeTransactionContract` trades to skew a pool's reported reserves and extract value beyond what exact math would allow, and it also causes non-deterministic-looking reserve drift that a hardened `SafeExchangeProcessor` (BigDecimal-based) was later introduced to fix.

## Finding Description
`ExchangeCapsule.transaction()` selects the processor used for every trade against a TRC10 exchange pool: [1](#0-0) 

When `hardenedCalc` (i.e., `dynamicStore.allowHardenExchangeCalculation()`) is not enabled, every trade is routed to `ExchangeProcessor`, which implements the Bancor relay formula purely with Java `double` arithmetic and `Math.pow`: [2](#0-1) 

This is invoked directly from the unprivileged, publicly reachable `ExchangeTransactionActuator.execute()`, which any signed transaction from any account can trigger against any existing exchange pool by specifying a `tokenId`/`quant`: [3](#0-2) 

Because the legacy path performs floating point division, `Math.pow`, and truncation to `long` (`(long) issuedSupply`, `(long) exchangeBalance`) instead of exact arithmetic, the computed swap amounts can diverge from the mathematically correct Bancor-formula result. An attacker can construct a sequence of trades (buy then sell, or a series of small/large trades) that exploits this floating-point rounding/truncation asymmetry to extract more value from the pool than they put in, gradually or immediately draining pool reserves — the AMM analog of the reported flash-loan/price-manipulation attack. The project's own `SafeExchangeProcessor` (BigDecimal-based, `RoundingMode.HALF_UP`/`DOWN`) exists specifically as a "hardened" replacement for this exact math, and unit tests explicitly document precision differences between the legacy and hardened processors: [4](#0-3) [5](#0-4) 

Whether hardening is active is entirely controlled by the `allowHardenExchangeCalculation` dynamic property flag checked in `AbstractExchangeActuator.allowHarden()`: [6](#0-5) 

If this proposal/flag has not been activated on a given network (or a fork/testnet has it disabled), all `ExchangeTransactionContract` trades use the vulnerable floating-point path.

## Impact Explanation
If the floating-point legacy math is the active path, an attacker fully controlling only unprivileged `ExchangeTransactionContract` calls (no special permission required) can repeatedly trade against a pool to exploit rounding/truncation bias in the Bancor relay computation, extracting real TRX/TRC10 asset value from the pool balance held by `ExchangeCapsule`. This is a fund-theft/drain vector directly analogous to the reported flash-loan attack against a DEX pool, reachable purely through the actuator's `execute()`/`validate()` transaction path.

## Likelihood Explanation
Medium. Exploitation requires that the network still permits legacy (non-hardened) exchange math (`allowHardenExchangeCalculation` disabled), and requires the attacker to find/construct a beneficial sequence of trade sizes where floating-point truncation favors them over the exchange (the existing tests already show up-to-±1-unit divergence between legacy and hardened results, confirming the primitive exists but the practical profit magnitude per trade is small and would need to be repeated or amplified across favorable reserve ratios). Because it's reachable from any signed transaction with no special privilege, and the codebase itself required introducing `SafeExchangeProcessor` as a fix, the bug class is real, but constructing a profitable attack sequence at scale (like the 40 ETH loss in the report) would require careful selection of pool reserves/quantities.

## Recommendation
- Make `SafeExchangeProcessor` (BigDecimal-based) the default/only processor for `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` execution, removing the floating-point `ExchangeProcessor` path entirely rather than gating it behind an optional dynamic property.
- If the double-precision path must remain for backward compatibility, ensure `allowHardenExchangeCalculation` is unconditionally enabled on all active networks and add invariant checks (e.g., product-of-reserves cannot increase within a single trade) in `ExchangeCapsule.transaction()` regardless of which processor computed the result.
- Add fuzz/property tests exercising both processors across a wide range of reserve ratios and quantities to bound the maximum extractable divergence and confirm it is not economically exploitable.

## Proof of Concept
1. Attacker (any account) observes an `Exchange` pool (`ExchangeCapsule`) with reserves `firstTokenBalance`/`secondTokenBalance`, on a network where `allowHardenExchangeCalculation == 0` (legacy math active — see `AbstractExchangeActuator.allowHarden()`).
2. Attacker submits an `ExchangeTransactionContract` (`ExchangeTransactionActuator`) selling `tokenID` for `anotherTokenID` with a `quant` chosen so that the `ExchangeProcessor.exchange()` double-precision computation (`exchangeToSupply`/`exchangeFromSupply`, `Math.pow`, truncation to `long`) yields an `anotherTokenQuant` more favorable to the attacker than the exact/BigDecimal-correct Bancor result (as demonstrated by the up-to-±1-unit divergence documented in `ExchangeCapsuleTest.testTransactionLegacyVsHardenedProcessorSelection`).
3. Attacker repeats step 2 across multiple trades/pool states (potentially alternating buy/sell direction) to accumulate the per-trade rounding bias, draining value from the pool's `firstTokenBalance`/`secondTokenBalance` recorded in `ExchangeCapsule`, analogous to how the flash-loan attacker manipulated 0xODexPool's pricing within transactions to profit ~$61k.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  public void testTransactionLegacyVsHardenedProcessorSelection() throws Exception {
    // Same input produces deterministic results in both modes.
    ExchangeCapsule legacy = new ExchangeCapsule(
        ByteString.copyFromUtf8("owner"), 100L, 0L,
        "abc".getBytes(), "def".getBytes());
    legacy.setBalance(100_000_000L, 100_000_000L);
    long legacyResult = legacy.transaction("abc".getBytes(), 1_000_000L, true, false);

    ExchangeCapsule hardened = new ExchangeCapsule(
        ByteString.copyFromUtf8("owner"), 101L, 0L,
        "abc".getBytes(), "def".getBytes());
    hardened.setBalance(100_000_000L, 100_000_000L);
    long hardenedResult = hardened.transaction("abc".getBytes(), 1_000_000L, true, true);

    Assert.assertTrue("Both must return positive", legacyResult > 0 && hardenedResult > 0);
    Assert.assertTrue("Hardened must not exceed pool",
        hardenedResult <= 100_000_000L);
    // Allow ±1 difference due to BigDecimal vs double precision
    Assert.assertTrue("Results should be within 1 unit",
        StrictMathWrapper.abs(legacyResult - hardenedResult) <= 1);
  }
