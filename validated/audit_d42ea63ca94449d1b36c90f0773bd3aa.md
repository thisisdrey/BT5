### Title
Missing Slippage Protection in ExchangeInject/ExchangeWithdraw Actuators Enables Sandwich Attacks Against TRON's Bancor-style Exchange Pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` — unlike `ExchangeTransactionContract`, which carries an `expected` minimum-output field — provide no user-specified bound on the counter-token amount computed at execution time. An unprivileged transaction broadcaster can sandwich a victim's inject/withdraw transaction with `ExchangeTransactionContract` trades to skew the pool ratio, forcing the victim to either contribute far more of the counter-token than intended (inject) or receive far less than intended (withdraw), with no on-chain mechanism to reject the unfavorable execution.

### Finding Description
The `ExchangeTransactionContract` message includes an `expected` field that is explicitly checked in `ExchangeTransactionActuator`: [1](#0-0) 

This gives a trader slippage protection: the transaction reverts if the pool ratio shifted unfavorably between submission and execution.

By contrast, `ExchangeInjectContract` has only `owner_address`, `exchange_id`, `token_id`, and `quant` — no expected/min-max bound: [2](#0-1) 

`ExchangeWithdrawContract` has the identical shape, also lacking any bound field: [3](#0-2) 

In `ExchangeInjectActuator.execute()`, the counter-token amount (`anotherTokenQuant`) the caller must contribute is computed purely from the exchange pool's *current on-chain* balances at execution time, proportionally to `tokenQuant`: [4](#0-3) 

and is unconditionally deducted from the caller's balance/asset holdings: [5](#0-4) 

Symmetrically, in `ExchangeWithdrawActuator.execute()`, the amount of the counter-token returned to the withdrawer is likewise computed from the live pool ratio with no lower bound the caller can enforce: [6](#0-5) 

Because the TVM/actuator pipeline processes transactions in block order and the pool ratio (`firstTokenBalance`/`secondTokenBalance`) is mutable state that any account can shift by submitting an `ExchangeTransactionContract` trade, an attacker (or a proposing/packing party) can:
1. Observe a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction in the mempool.
2. Submit an `ExchangeTransactionContract` trade immediately before it to skew `firstTokenBalance`/`secondTokenBalance` in the attacker's favor.
3. Let the victim's inject/withdraw execute at the manipulated ratio — forcing the victim to pay in more of the second asset than they intended (inject) or receive less back than expected (withdraw).
4. Submit a second `ExchangeTransactionContract` trade to reverse the ratio, extracting the difference as profit (classic sandwich attack) — the same fee model as `MarketSellAssetActuator`'s order matching but without any of `ExchangeTransactionActuator`'s `expected` guard.

This mirrors the reported Flatmoney issue: a value derived from mutable/attacker-influenceable state (there, Chainlink price; here, the on-chain pool ratio) is used to unconditionally settle a user's funds without a user-supplied bound, causing fund loss under adversarial ordering.

### Impact Explanation
A victim submitting `ExchangeInjectContract` or `ExchangeWithdrawContract` can lose funds to a sandwiching attacker who manipulates the Bancor-style pool ratio via ordinary `ExchangeTransactionContract` trades executed immediately before and after the victim's transaction in the same block, since neither contract type exposes a way to cap the required/expected counter-token amount. This is a concrete theft-of-funds vector reachable by any account holder with only a signed transaction, satisfying the "unauthorized... theft ... of funds" bar.

### Likelihood Explanation
Any account can submit `ExchangeTransactionContract` transactions cheaply and pool ratio manipulation for a single-block sandwich requires no special privilege — only a large-enough trade relative to the target pool's liquidity, and the ability to observe/predict block ordering (mempool visibility or self-packing). Since Inject/Withdraw contracts are used regularly by liquidity providers, and there is no code path enforcing a bound, exploitation only requires standard transaction submission by an unprivileged actor.

### Recommendation
Add `expected`/bound fields (a minimum acceptable `anotherTokenQuant` for inject and withdraw, analogous to `ExchangeTransactionContract.expected`) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce them in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`'s `execute()`/`validate()` methods, rejecting the transaction if the pool-ratio-derived amount falls outside the caller-specified tolerance.

### Proof of Concept
1. Attacker observes victim's pending `ExchangeInjectContract(exchange_id=X, token_id=A, quant=Q)` in the mempool.
2. Attacker submits `ExchangeTransactionContract` selling a large amount of token B into pool X, shifting `firstTokenBalance`/`secondTokenBalance` sharply in the attacker's favor (per `ExchangeCapsule.transaction`, `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java:124-169`).
3. Victim's inject executes: `ExchangeInjectActuator` computes `anotherTokenQuant` from the now-skewed ratio (`actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java:71-83`) and deducts a much larger amount of token B from the victim than intended, with no check against the victim's expectations.
4. Attacker submits a reversing `ExchangeTransactionContract` trade to restore the ratio and realize profit extracted from the victim's excess contribution.
