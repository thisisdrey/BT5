### Title
Unbounded `estimated_len` from client causes integer-overflow panic (debug) / wrapped fee (release) in `POST /v2/fees/transaction` - (File: stackslib/src/net/api/postfeerate.rs)

### Summary
The `try_parse_request` handler for `POST /v2/fees/transaction` computes `estimated_len` as `max(body.estimated_len.unwrap_or(0), payload_data.len())`, where `body.estimated_len` is a fully attacker-controlled `u64` from the JSON body with no upper bound. This value is later multiplied by `MINIMUM_TX_FEE_RATE_PER_BYTE` in `estimate_tx_fee_from_cost_and_length`, causing an arithmetic overflow.

### Finding Description
In `try_parse_request` [1](#0-0) , `payload_data.len()` is bounded by the `MAX_PAYLOAD_LEN` check on the HTTP body at [2](#0-1) , but `body.estimated_len` comes straight from the deserialized JSON field `estimated_len: Option<u64>` [3](#0-2)  with no range validation. `std::cmp::max` only enforces a *floor* equal to the real payload length — it never *caps* `estimated_len` at any maximum. An attacker can submit a small, valid `transaction_payload` hex string alongside `"estimated_len": 18446744073709551615` (u64::MAX) or any large value, and this exact value flows unmodified into `self.estimated_len`, then into `try_handle_request` [4](#0-3) , and finally into `estimate_tx_fee_from_cost_and_length`, where `let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;` [5](#0-4)  is computed. Since `MINIMUM_TX_FEE_RATE_PER_BYTE` is a fixed positive constant, any `estimated_len > u64::MAX / MINIMUM_TX_FEE_RATE_PER_BYTE` causes this multiplication to overflow — panicking in debug builds (`overflow-checks`/`debug_assertions` on) or silently wrapping in release builds, producing an incorrect `fee` value served in the JSON response. No other guard in this path bounds `estimated_len` from above.

### Impact Explanation
For nodes built with debug assertions or overflow checks enabled, a single malicious POST request crashes the RPC-handling thread/task (unauthenticated DoS), repeatable indefinitely by any remote client that can reach the node's RPC port — no authentication or privileged role is required. For release builds without overflow checks, the wrapped `minimum_fee` silently corrupts the fee estimate returned to any wallet or tool querying `/v2/fees/transaction`, an integrity failure served to unauthenticated callers.

### Likelihood Explanation
This requires no special preconditions: the endpoint is public/unauthenticated RPC, reachable by any remote peer with network access to the node's RPC port, the attacker only needs a small valid transaction payload (easy to construct, e.g., a minimal `TokenTransfer`) plus an oversized `estimated_len` JSON field, and the request is trivially repeatable at negligible attacker cost.

### Recommendation
Cap `estimated_len` to a sane maximum (e.g., `MAX_PAYLOAD_LEN` or the chain's maximum transaction/block size) when validating the request body, rejecting requests where `body.estimated_len` exceeds that bound, and/or use `checked_mul`/`saturating_mul` when computing `minimum_fee` in `estimate_tx_fee_from_cost_and_length` to avoid overflow regardless of input.

### Proof of Concept
Rust test in `stackslib::net::api::postfeerate::tests` (or an integration-style test using `RPCPostFeeRateRequestHandler`):
1. Build a valid small `TransactionPayload::TokenTransfer` and hex-encode its `consensus_serialize` bytes.
2. Construct a `FeeRateEstimateRequestBody { estimated_len: Some(u64::MAX / MINIMUM_TX_FEE_RATE_PER_BYTE + 1), transaction_payload: <hex> }` and serialize to JSON as the POST body with `Content-Type: application/json` and correct `Content-Length`.
3. Call `try_parse_request` directly (or drive the full HTTP handler) and then `RPCPostFeeRateRequestHandler::estimate_tx_fee_from_cost_and_length` with the resulting `estimated_len`.
4. Assert: in a build with overflow checks, the call panics at `let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;` (`postfeerate.rs:112`); in a release build, assert `minimum_fee` (and thus `estimate.fee`) is a wrapped/incorrect small value inconsistent with `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` computed in `u128`.
