### Title
FetchRemote allows unbounded resource hold via unset/zero Timeout with malicious slow remote - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`FetchRemote` only bounds the RPC's execution time when the caller sets `req.GetTimeout() > 0`; if `Timeout` is omitted (default `0`), no context deadline is applied and the underlying `git-fetch(1)` process, quarantine directory, and `updateref.Updater` goroutines can run indefinitely against an attacker-controlled remote. A slow-loris remote (never completing ref advertisement or trickling bytes) can hold these resources open for the lifetime of the connection, since Gitaly enforces no server-side default ceiling.

### Finding Description
In `FetchRemote` (`internal/gitaly/service/repository/fetch_remote.go:30-47`), the context is only wrapped with a timeout conditionally:

```go
if req.GetTimeout() > 0 {
    var cancel context.CancelFunc
    ctx, cancel = context.WithTimeout(ctx, time.Duration(req.GetTimeout())*time.Second)
    defer cancel()
}
``` [1](#0-0) 

If `Timeout` is left at its zero value (the protobuf default), `ctx` is passed unmodified into `fetchRemoteAtomic`, which spawns `git-fetch(1)` against the caller-supplied remote URL via `quarantineRepo.FetchRemote(ctx, "inmemory", opts)` [2](#0-1) . The remote URL, resolved address and other fetch parameters are taken directly from `req.GetRemoteParams()` (`buildCommandOpts`, lines 260-304), so the attacker fully controls the fetch destination, including the ability to run a slow-loris HTTP/SSH server there. `command.New` (`internal/command/command.go:192-260`) only terminates a spawned process when its context is done; absent a caller-supplied deadline, `ctx.Done()` never fires until the parent gRPC call itself is cancelled by the client or the process ends on its own. No other layer in this code path substitutes a default ceiling — the concurrency limiter (`internal/gitaly/config/config.go` `ConcurrencyLimits`) only bounds how many concurrent requests are admitted/queued per repo, not how long an admitted request may run.

While the fetch process runs, the code holds open the quarantine directory, and after fetch completion, additional reference-transaction resources: `prunedUpdater`/`refUpdater` (`updateref.New`, lines 135-154) which spawn `git-update-ref(1)` subprocesses and vote via `transaction.VoteOnContext`. But the primary and largest exposure is the `git-fetch(1)` process itself, which can be kept alive indefinitely by a network peer that never finishes sending data.

### Impact Explanation
This matches GitLab's "Denial of Service (DoS) of a Gitaly RPC handler" bounty impact class. An attacker who can trigger `FetchRemote` toward a URL they control (e.g., configuring a pull mirror or import source and omitting/zeroing the RPC's `Timeout` field, or if Rails ever forwards a default of 0) can pin a `git-fetch` process and its associated file descriptors/sockets/CPU slot for that repository/storage shard indefinitely, exhausting per-shard process/thread budgets under repeated exploitation, degrading service for other tenants on the same Gitaly node/storage.

### Likelihood Explanation
Feasibility depends on whether GitLab Rails, in the normal FetchRemote-triggering flow (pull mirroring / repository import), always sets a nonzero `Timeout` before calling Gitaly. If Rails always supplies a timeout in this path, the attacker cannot reach this at the gRPC layer without control over the RPC field itself, which the rules state the attacker does control ("push/fetch, fork or import a repository they own, and so control RPC fields"). Given the stated threat model — attacker fully controls RPC fields — reaching Gitaly with `Timeout=0` is straightforward and repeatable; the only precondition is control of the remote endpoint (trivial, e.g., a server the attacker operates) and ability to invoke the RPC with no/zero timeout.

### Recommendation
Enforce a mandatory server-side maximum timeout ceiling in `FetchRemote` regardless of the client-supplied value, e.g. clamp `req.GetTimeout()` to a configured maximum and always apply `context.WithTimeout` (falling back to a sane default, such as several minutes, when the request's `Timeout` is zero or negative), rather than only conditionally wrapping the context when `Timeout > 0`.

### Proof of Concept
```go
func TestFetchRemote_NoTimeoutSlowLoris(t *testing.T) {
    // Start a slow-loris TCP listener on the "remote" side that accepts the
    // connection but never completes the smart-HTTP ref advertisement,
    // trickling at most 1 byte per second.
    ln := startSlowLorisGitServer(t)
    defer ln.Close()

    cfg, repoProto, _ := setupRepositoryService(t)
    client := newRepositoryClient(t, cfg)

    req := &gitalypb.FetchRemoteRequest{
        Repository: repoProto,
        RemoteParams: &gitalypb.Remote{
            Url: "http://" + ln.Addr().String() + "/slow.git",
        },
        // Timeout intentionally left unset (0) to simulate attacker-controlled default.
    }

    done := make(chan error, 1)
    go func() {
        _, err := client.FetchRemote(context.Background(), req)
        done <- err
    }()

    select {
    case <-done:
        t.Fatal("expected FetchRemote to hang indefinitely without a timeout ceiling")
    case <-time.After(30 * time.Second):
        // Confirms the RPC/goroutine and underlying git-fetch process remain
        // blocked well past any reasonable bound, demonstrating the missing
        // server-side ceiling.
    }
}
```
Expected assertion: with the current implementation, the RPC does not return within the test window because no context deadline was ever applied; after applying a fix that enforces a maximum timeout, the RPC should fail with a deadline-exceeded error within the configured ceiling.
