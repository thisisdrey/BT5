### Title
Instruction-data cost truncation (integer-division round-down) lets transactions underpay compute-unit cost for the final partial data page - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::get_instructions_data_cost` computes the compute-unit cost attributable to instruction data size using integer division, which truncates (rounds down) instead of rounding up. This mirrors the EIP-4626 rounding-direction defect in the referenced report: the "vault" (here, the validator/network cost-accounting model) must always round in its own favor, but this function instead rounds in favor of the transaction submitter, systematically underpricing part of the instruction data.

### Finding Description
`get_instructions_data_cost` is defined as: [1](#0-0) 

```rust
fn get_instructions_data_cost(transaction: &impl TransactionMeta) -> u16 {
    transaction.instruction_data_len() / (INSTRUCTION_DATA_BYTES_COST as u16)
}
```

`INSTRUCTION_DATA_BYTES_COST` is derived as `140 / COMPUTE_UNIT_TO_US_RATIO` (`140/30 = 4`, integer-truncated): [2](#0-1) 

Because plain `/` truncates toward zero, any instruction data length that is not an exact multiple of `INSTRUCTION_DATA_BYTES_COST` (4 bytes) loses the remainder entirely from cost accounting — up to 3 bytes per transaction go completely uncosted, and transactions with `instruction_data_len < 4` are costed as `0` regardless of size.

This is inconsistent with how the codebase treats an analogous case, `calculate_pages_for_bytes`, used for loaded-accounts-data-size costing, which explicitly rounds up via `saturating_add(PAGE_SIZE - 1).saturating_div(PAGE_SIZE)`: [3](#0-2) 

The asymmetry shows the codebase's own convention is to round cost calculations up (in the protocol's favor), while `get_instructions_data_cost` violates that convention and rounds down (in the submitter's favor) — exactly the rounding-direction inversion flagged in the EIP-4626 report, but here applied to the CU cost-accounting/QoS pricing model rather than to vault share pricing.

### Impact Explanation
The cost model output (`TransactionCost::sum()`, which folds in `data_bytes_cost`) feeds directly into (1) the banking-stage/cost-tracker's block-cost and per-account-cost limit enforcement, and (2) the transaction-priority calculation used for scheduling and forwarding (`calculate_priority_and_cost`, `calculate_priority`), which use `cost.sum()` as the denominator for priority ranking: [4](#0-3) [5](#0-4) 

Since instruction data-length costing is truncated rather than rounded up, an attacker submitting many transactions engineered to have instruction-data lengths that are 3 bytes over a multiple of 4 can slightly underpay compute-unit cost relative to actual resource consumption, marginally under-accounting block-cost-limit usage and marginally over-representing priority (since `cost.sum()` used as the denominator is undercounted). Given `INSTRUCTION_DATA_BYTES_COST` = 4, the maximum single-transaction undercount is only 3 CU worth of `data_bytes_cost` (bounded, since `u16`), which is a very small, per-transaction, bounded QoS mispricing rather than a large unbounded exploit.

### Likelihood Explanation
The condition is deterministic and trivially reachable by any unprivileged user simply by choosing instruction data lengths not aligned to 4 bytes — no special permissions or race conditions are required. However, the magnitude of underpricing per transaction is minuscule (at most 3 compute units out of the multi-hundred/thousand CU cost of a typical transaction), so while the bug is 100% reproducible, its practical impact on block-cost accounting or QoS/priority ordering is negligible at the observed scale.

### Recommendation
Change `get_instructions_data_cost` to round up (consistent with `calculate_pages_for_bytes`'s pattern), e.g.:
```rust
fn get_instructions_data_cost(transaction: &impl TransactionMeta) -> u16 {
    transaction
        .instruction_data_len()
        .saturating_add(INSTRUCTION_DATA_BYTES_COST as u16 - 1)
        / (INSTRUCTION_DATA_BYTES_COST as u16)
}
```
This ensures partial data pages are billed at least their full compute-unit cost, aligning with the rest of the cost model's rounding convention and avoiding systematic underpricing of pre-fee work, however small.

### Proof of Concept
Given `INSTRUCTION_DATA_BYTES_COST = 4`:
- A transaction with `instruction_data_len() = 3` yields `get_instructions_data_cost = 3/4 = 0` (should be `1`).
- A transaction with `instruction_data_len() = 7` yields `7/4 = 1` (should be `2`).
This can be confirmed directly against the existing unit test that asserts `data_bytes_cost == 1` for a 4-byte-ish instruction payload: [6](#0-5) 

Modify the test payload length to `4k+r` (`0<r<4`) and observe that `data_bytes_cost` does not increase to reflect the extra bytes, confirming the systematic round-down/underpricing.
