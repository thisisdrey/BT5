### Title
Hardcoded first-entry (`[0]`) selection in `objects/info/alternates` parsing lets an injected decoy alternate desynchronize Gitaly's object-pool bookkeeping - (File: `internal/git/objectpool/pool.go`, `internal/git/objectpool/link.go`, `internal/gitaly/service/internalgitaly/scan_pool_metadata.go`)

### Summary
The Kelp report's root cause is a handler that is hardcoded to act on the 0-th element of an attacker-influenceable list (`LidoWithdraw.getWithdrawalRequests[0]`) instead of the specific entry it actually cares about, so an adversary who plants a cheap decoy entry ahead of the real one silently derails the whole flow. Gitaly's object-pool linkage code has the same structural weakness: several places read the repository's `objects/info/alternates` file (which, unlike Gitaly's own `Link()` writer, is not guaranteed to contain exactly one line) and unconditionally trust index `[0]` as "the pool alternate," while Git itself honors *every* line in that file.

### Finding Description
`objects/info/alternates` is a plain, line-oriented file that Git natively supports with multiple entries. Gitaly's low-level reader for it, `stats.ReadAlternatesFile` / `stats.AlternatesInfoForRepository` (`internal/git/stats/repository_info.go:610-668`), makes no attempt to enforce "at most one line" - it simply returns all non-empty, non-comment lines as `ObjectDirectories`.

Three higher-level call sites then take only the first element of that slice as *the* pool link, ignoring any subsequent entries entirely:

- `objectpool.FromRepo`, which resolves which pool a repository belongs to: [1](#0-0) 

- `linkedToRepository`, used by `Link()` to decide whether a repository is already linked to a given pool (and therefore whether to skip re-linking / voting): [2](#0-1) 

- `processPoolMemberFunc`, used by the `ScanPoolMetadata` RPC to discover and record which pool each repository on disk is linked to: [3](#0-2) 

Notably, Gitaly does have a strict, single-alternate-only reader elsewhere - `gitstorage.ReadAlternatesFile`, used by the transaction-manager's partition assigner, explicitly rejects more than one alternate with `ErrMultipleAlternates`: [4](#0-3) 

This shows the codebase is aware that "more than one alternate" is an invariant that must be enforced, yet the object-pool code path (`stats.AlternatesInfoForRepository` consumers) never performs this check and instead defaults to "take index 0," exactly mirroring the Kelp pattern of hardcoding position 0 without validating there is only one legitimate entry.

`Link()` itself always truncates and rewrites the alternates file with exactly one line when it actually performs a link, so a properly-linked repository normally has a single-line file: [5](#0-4) 

However, a repository's on-disk `objects/info/alternates` file can also be populated through paths other than `Link()` - e.g. repository creation/import flows that materialize a full repository tree from client-supplied data (bundle/snapshot import, replication) can bring in a pre-existing `objects/info/alternates` file with more than one line before Gitaly's own bookkeeping ever inspects it. Because `stats.AlternatesInfoForRepository` performs no per-storage-root validation of each entry (unlike `git.altObjectDirs` in `internal/git/dirs.go`, which validates every alternate stays under `storagePrefix`), a two-line file with a decoy first line and the real/valid pool alternate second is not rejected at read time by any of the three call sites above - it's simply misread as "the pool is the decoy."

### Impact Explanation
If a repository ends up with more than one line in `objects/info/alternates` (decoy first, real pool link second):
- `objectpool.FromRepo` (used by the `GetObjectPool` RPC handler and other housekeeping consumers) will resolve the pool from the decoy line. If the decoy doesn't validate as a repository, `FromRepo` fails with `ErrInvalidPoolRepository`, causing the RPC/handler to error out even though the repository is in fact validly linked to a real pool via line 2 - a denial of service of pool-linkage discovery for that repository.
- `linkedToRepository` (called from `Link()`) will conclude the repository is *not* linked to the intended pool (because it only compares against index 0), even though Git will actually search all listed alternate directories. This desynchronizes Gitaly's idempotency/voting logic in `Link()` from the real on-disk/Git-visible state.
- `ScanPoolMetadata`'s `processPoolMemberFunc` will report/record the wrong (decoy) pool as the disk path for that repository, corrupting the pool membership metadata (`poolStore`) used for storage-level housekeeping and cleanup.

This is a DoS/data-corruption of Gitaly's own pool-management bookkeeping (RPC handlers `GetObjectPool`, `ScanPoolMetadata`, and internal `Link()` logic), not an object-read bypass, since Git's own alternates resolution still walks the full list. The severity is comparable in class (unprivileged-triggerable logic desync from a hardcoded index-0 assumption over an attacker-shaped list) but the concrete blast radius here is confined to Gitaly's internal pool bookkeeping/DoS rather than fund loss.

### Likelihood Explanation
Confidence is moderate, not high: I could not, within the available search budget, trace a concrete, currently-reachable RPC path that lets a fully unprivileged user directly plant a two-line `objects/info/alternates` file inside an existing repository's `objects` directory (this would most plausibly require an import/snapshot/bundle-restore code path that writes raw repository files from client-controlled input, or a race between two `Link()`-adjacent operations). The `Link()` function itself always overwrites the file with a single trusted line, so the normal linking flow does not introduce the multi-line condition. The vulnerable pattern (unconditional `[0]` selection, no enforcement of the "single alternate" invariant that exists elsewhere in the codebase) is confirmed and reproducible in isolation, but full end-to-end reachability from an ordinary user's push/fetch/import RPC was not conclusively established.

### Recommendation
- In `stats.AlternatesInfoForRepository` / the three consumers (`objectpool.FromRepo`, `linkedToRepository`, `processPoolMemberFunc`), enforce the same invariant already implemented in `gitstorage.ReadAlternatesFile`: reject (or explicitly and safely handle) alternates files containing more than one entry, rather than silently using `[0]`.
- Validate every entry in `objects/info/alternates` against the storage root (as `git.altObjectDirs` already does) whenever the file may originate from non-`Link()`-controlled sources (imports, snapshots, replication), so a decoy/foreign entry cannot occupy position 0 undetected.
- Audit all repository-materialization code paths (bundle/snapshot import, replication) to ensure they cannot introduce or preserve an attacker-supplied `objects/info/alternates` file verbatim without re-validating/re-normalizing it through the same logic `Link()` uses.

### Proof of Concept
Not independently reproduced end-to-end (see Likelihood Explanation for the gap). The isolated defect is directly demonstrable by placing a two-line `objects/info/alternates` file (`"../../nonexistent/objects\n../../real-pool/objects\n"`) into a repository's `objects/info/alternates` and observing that:
1. `stats.AlternatesInfoForRepository` returns both lines with no error.
2. `objectpool.FromRepo` / `linkedToRepository` / `processPoolMemberFunc` each act only on `ObjectDirectories[0]` (the invalid/decoy entry), producing an error or wrong pool resolution, while `git` itself would still be able to resolve objects via the second, real alternate.

// ReadAlternatesFile reads the alternates file from the given repository. ErrNoAlternate is returned if the
// file doesn't exist or didn't contain an alternate. ErrMultipleAlternates is returned if the
// repository had multiple alternates.
func ReadAlternatesFile(repositoryPath string) (string, error) {
	alternates, err := stats.ReadAlternatesFile(repositoryPath)
	if err != nil {
		if errors.Is(err, fs.ErrNotExist) {
			return "", ErrNoAlternate
		}

		return "", fmt.Errorf("read alternates file: %w", err)
	}

	if len(alternates) == 0 {
		return "", ErrNoAlternate
	} else if len(alternates) > 1 {
		// Repositories shouldn't have more than one alternate given they should only be
		// linked to a single pool at most.
		return "", ErrMultipleAlternates
	}

	return alternates[0], nil
}
