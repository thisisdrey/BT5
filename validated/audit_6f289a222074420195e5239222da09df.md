### Title
Active-Permission Key Can Overwrite Owner Permission via `AccountPermissionUpdateContract` Without Owner Signature - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` never restricts which permission (owner vs. active) may authorize an `AccountPermissionUpdateContract`. Authorization is delegated entirely to the generic multisig operation-bitmap check `checkPermissionOperations` [1](#0-0)  which is invoked via `contract.getPermissionId()` during transaction signing/verification [2](#0-1) . If any Active permission's 32-byte `operations` bitmap has the `AccountPermissionUpdateContract` bit set, a transaction satisfying only that Active permission's threshold — never touching the Owner key — is accepted and lets the actuator overwrite the account's Owner permission, Witness permission and all Active permissions in one call.

### Finding Description
`AccountPermissionUpdateActuator.validate()` checks structural validity of the new `owner`, `witness`, and `actives` permissions (key counts, weights, thresholds, operation-bitmap validity against `getAvailableContractType()`), but it never checks `contract.getPermissionId()` or otherwise requires that the specific transaction be authorized by the *Owner* permission (`permissionId == 0`) [3](#0-2) . `execute()` then unconditionally applies the attacker-controlled `owner`, `witness`, and `actives` permissions to the account via `AccountCapsule.updatePermissions`, replacing the existing Owner permission entirely [4](#0-3)  and [5](#0-4) .

The only gate on *which* key(s) may submit this contract type is the generic per-contract-type operation bit inside whichever permission `contract.getPermissionId()` selects, checked by `checkPermissionOperations` [1](#0-0) , used both when locally signing (`TransactionCapsule.addSign`/`checkPermission`) [2](#0-1)  and by consensus-level signature validation. Nothing in the actuator (or elsewhere) enforces that an `AccountPermissionUpdateContract` must be authorized specifically by the Owner permission (`permissionId == 0`). Consequently, an account owner who has previously delegated an Active permission (e.g., for routine transfers or asset operations) to a co-signer, employee, exchange hot-wallet operator, or third-party service, and whose Active permission's `operations` bitmap happens to include the `AccountPermissionUpdateContract` type bit, exposes their entire account to takeover: the Active-key holder can broadcast a self-authorized `AccountPermissionUpdateContract` that rewrites the Owner permission to keys they control, permanently locking out the original owner.

This mirrors the OctoPrint issue's root cause (CWE-287/CWE-620): a party without the highest-privilege credential can alter the account's own access-control configuration — including revoking/replacing the top-level admin (`Owner`) key — without any requirement to reprove possession of that top-level credential.

### Impact Explanation
Successful exploitation permanently transfers control of the target TRON account (unauthorized account operation / permanent loss of funds control), since Owner permission governs `TransferContract`, `WitnessCreateContract`, future `AccountPermissionUpdateContract` calls, etc. Once the Owner permission is overwritten, the original owner cannot recover the account. This satisfies the "concrete unauthorized account operation / theft or permanent freezing of funds" bar.

### Likelihood Explanation
Exploitation requires that the victim has configured an Active permission with the `AccountPermissionUpdateContract` bit enabled in its `operations` bitmap and delegated signing rights over that permission to a party other than themselves (a realistic multisig/delegation scenario, e.g., co-signers, custodial services, automated bots holding an "active" key for convenience). Given `checkPermission` in the actuator validates the bitmap is well-formed but never disallows setting this bit on an Active permission, and there is no runtime warning to operators, this is a plausible misconfiguration rather than a purely theoretical one, and is entirely reachable by a single signed transaction from any holder of such an Active key — no privileged/witness/protocol-level access needed.

### Recommendation
In `AccountPermissionUpdateActuator.validate()`, require that `AccountPermissionUpdateContract` transactions be authorized only via `permissionId == 0` (the Owner permission), regardless of what the operations bitmap of any Active permission says — i.e., treat permission-management as an implicitly Owner-only operation, similar to how some other high-impact contract types should be restricted. Alternatively/additionally, disallow setting the `AccountPermissionUpdateContract` bit within any non-Owner permission's `operations` field during `checkPermission`, so wallets/tools cannot construct an Active permission capable of self-escalating.

### Proof of Concept
1. Account `X` has Owner permission `{ownerKey}` and an Active permission (id=2) `{coSignerKey}` whose 32-byte `operations` bitmap has bit `AccountPermissionUpdateContract` (from `ContractType`) set to `1` — a configuration the current `checkPermission` logic in `AccountPermissionUpdateActuator` accepts without restriction [6](#0-5) .
2. `coSignerKey` (holder of only the Active permission, never the Owner key) builds an `AccountPermissionUpdateContract` with `owner_address = X`, sets `permission_id = 2` on the transaction, and defines a new `owner` Permission whose keys are entirely controlled by the attacker.
3. `coSignerKey` signs the transaction; `TransactionCapsule.checkPermission`/`checkPermissionOperations` pass because permission id 2's bitmap allows this contract type [7](#0-6) .
4. The transaction is broadcast and accepted by nodes; `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)`, replacing account `X`'s Owner permission with the attacker's key set [5](#0-4) .
5. The original owner of `X` no longer controls the Owner permission and is permanently locked out; the attacker now has full Owner-level control of account `X`.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
