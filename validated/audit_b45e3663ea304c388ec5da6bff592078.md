### Title
Precision-loss / rate-manipulation in TRX Exchange (Bancor-style AMM) via floating-point relay-supply math - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The Balancer report describes an attacker draining one side of a Balancer Boosted Pool to near-zero, exploiting rounding/precision loss in the pool's rate math to mint an inflated share price and extract funds from other liquidity paths. java-tron ships a structurally analogous constant-relay-supply AMM ("TRX Exchange", `ExchangeCreate/Inject/Withdraw/TransactionContract`) whose default calculation path still uses double-precision floating-point math with truncating casts to compute swap outputs, and pool balances can be driven to extreme ratios by the pool's own creator through `ExchangeWithdrawActuator`/`ExchangeInjectActuator`.

### Finding Description
`ExchangeCapsule.transaction()` selects between two calculators depending on the `allowHardenExchangeCalculation` dynamic parameter: [1](#0-0) 

- Legacy (default unless the committee has voted to enable hardening) path is `ExchangeProcessor`, which computes the Bancor relay-supply issuance/redemption using `double` arithmetic (`Maths.pow`) and truncates the result to `long` via a direct cast: [2](#0-1) 
- A hardened `BigDecimal`-based alternative exists (`SafeExchangeProcessor`) but is gated behind `allowHardenExchangeCalculation()`, which is only true if `chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation()` returns true: [3](#0-2) 

The floating-point path (`exchangeToSupply`/`exchangeFromSupply`) computes `1 + quant/newBalance` and raises it to a fractional exponent, then truncates to `long`. When `newBalance` (one side of the pool) is very small relative to `quant`, or when `quant` is very small relative to `newBalance`, the double-precision `pow` result loses precision near 1.0, exactly the same rounding surface that the Balancer exploit abused around its `virtualSupply`.

Reaching this precision-sensitive state is fully attacker-controlled: any account can create its own exchange pool (`ExchangeCreateContract`), then act as `creator` to call `ExchangeWithdrawActuator` to pull one token side down to a near-zero balance. `ExchangeWithdrawActuator.doValidate()` only requires `firstTokenBalance != 0` and `secondTokenBalance != 0` after the operation — it does not prevent driving a balance down to `1`: [4](#0-3) 

Once the pool balance ratio is extreme, any trader (not just the creator) can call `ExchangeTransactionActuator`, whose `execute()`/`validate()` route straight into `exchangeCapsule.transaction()` → `ExchangeProcessor.exchange()` with no additional sanity bound on the resulting price impact beyond the caller-supplied `expected` minimum: [5](#0-4) 

This mirrors the Balancer pattern precisely: (1) attacker-controlled draining of one pool side to a precision-sensitive extreme, (2) small trades that round in the attacker's favor because of floating-point truncation near the extreme ratio, (3) subsequent trades by the attacker (or unwitting counterparties) executed against the now-mispriced pool.

### Impact Explanation
An attacker who creates and self-manages an Exchange pool can manipulate the legacy floating-point calculator to produce out-of-ratio swap outputs, allowing them to extract assets from the pool (their own tokens, or TRX/TRC10 assets deposited via later legitimate trades from other users) beyond what the true constant-relay-supply curve would allow. Because `ExchangeTransactionActuator` is reachable by any signed transaction and moves real TRX/TRC10 balances between `AccountStore` entries via `addAssetAmountV2`/`reduceAssetAmountV2`, a successful exploitation constitutes unauthorized value extraction/theft of funds analogous to the ~$2M Balancer incident, scaled to whatever liquidity is routed through the affected TRX Exchange pool.

### Likelihood Explanation
Likelihood is moderate: the affected legacy math path (`ExchangeProcessor`) is the default and remains active unless the network committee has passed the `allowHardenExchangeCalculation` proposal — I was not able to fully confirm this flag's compiled/effective default in `DynamicPropertiesStore` before running out of tool budget, so whether the hardened path is already enabled network-wide on the target chain is uncertain and should be verified. If the hardened flag is off (the historical default for such newly-added committee-gated protections in java-tron), the vulnerable floating-point path is fully reachable by any unprivileged account that creates its own Exchange pool and by any counterpart who subsequently trades against it — no special privilege beyond broadcasting standard `ExchangeCreateContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract` transactions is required.

### Recommendation
- Confirm and, if necessary, force `allowHardenExchangeCalculation` (and `allowStrictMath`) to be enabled by default so `SafeExchangeProcessor`'s `BigDecimal`-based, fixed-scale math is always used instead of the double/`Math.pow` legacy path in `ExchangeProcessor`.
- Add explicit minimum-liquidity / minimum-balance-ratio floors in `ExchangeWithdrawActuator.doValidate()` and `ExchangeCapsule.transaction()` so a pool side cannot be withdrawn down to values that make the relay-supply calculation precision-sensitive.
- Add a maximum-price-impact-per-trade guard in `ExchangeTransactionActuator` independent of the caller-supplied `expected` value, to bound single-transaction manipulation of the implied exchange rate.

### Proof of Concept
Conceptual reachable path (mirrors the Balancer PoC's drain → mis-priced-swap → profit sequence), not a verified working exploit:
1. Attacker broadcasts `ExchangeCreateContract` to create a TRX/TRC10 pool it fully controls as `creator`.
2. Attacker broadcasts `ExchangeWithdrawContract` (repeatedly) via `ExchangeWithdrawActuator` to reduce one side's `firstTokenBalance`/`secondTokenBalance` to a minimal nonzero value, entering the precision-sensitive region of `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (double `pow` near base 1.0).
3. Attacker (or an unwitting counterparty) broadcasts `ExchangeTransactionContract`, routed through `ExchangeCapsule.transaction()` → `ExchangeProcessor.exchange()`, whose floating-point truncation yields an output quantity that deviates from the true constant-relay-supply ratio.
4. Attacker broadcasts `ExchangeInjectContract`/further `ExchangeTransactionContract`s to restore/rebalance the pool and realize the discrepancy as extracted TRX/TRC10 balance in `AccountStore`. [6](#0-5) [7](#0-6)

package org.tron.core.capsule;

import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.Maths;

@Slf4j(topic = "capsule")
public class ExchangeProcessor implements ExchangeCapsule.Processor {

  private long supply;
  private final boolean useStrictMath;

  public ExchangeProcessor(long supply, boolean useStrictMath) {
    this.supply = supply;
    this.useStrictMath = useStrictMath;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

}

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}
