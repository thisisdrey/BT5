### Title
Missing zero/invalid-address check before relay packet transmission in `SendVia` - (File: `inside.go`)

### Summary
`Interface.SendVia`, which forwards relayed handshake/data packets through a relay hop, calls the UDP transport's `WriteTo` using `via.GetRemote()` without first verifying that the relay hop's remote address is valid (non-zero), unlike the parallel direct-send path `sendNoMetrics`, which explicitly checks `remote.IsValid()` / `hostinfo.GetRemote().IsValid()` before issuing the same `WriteTo` call.

### Finding Description
`sendNoMetrics` is careful to gate every `WriteTo` call behind an `IsValid()` check on the destination address, falling back to relaying only when no valid direct remote exists: [1](#0-0) 

However, when actually sending via a relay, `SendVia` issues the same kind of `WriteTo` call directly against `via.GetRemote()` with no `IsValid()` sanity check at all: [2](#0-1) 

The relay hop (`via`) is selected via `HostMap.QueryVpnAddrsRelayFor`, which only verifies that a `Relay` entry exists and is in the `Established` state for the target IP — it does not verify that the relay hop's own transport-level remote address (`via.GetRemote()`) has actually been populated: [3](#0-2) 

This is structurally the same bug class as the reported issue: an external call (here, a UDP `WriteTo`, analogous to the assembly `call` in `_executeAccountSet`) is executed against a target/address that may not have been properly set, without the sanity check that guards the equivalent code path elsewhere in the same file.

### Impact Explanation
If `via.GetRemote()` returns an unset/zero `netip.AddrPort` (e.g., relay state races such that the relay entry is `Established` before the underlying hostinfo's remote endpoint is populated), the relay packet write is attempted against an invalid destination. Depending on how the underlying OS/UDP layer's `WriteTo` handles a zero-valued `netip.AddrPort`, this can silently no-op, error non-fatally, or in the worst case misroute a packet — all without the caller (`sendNoMetrics`'s relay fallback loop) knowing the send failed, since `SendVia` only logs the error but doesn't return failure status to let the caller try the next relay candidate.

### Likelihood Explanation
Reachability requires no CA-signed certificate and no privileged position: this path is triggered on ordinary outbound traffic to any peer that is only reachable via a relay (a common real-world Nebula deployment pattern behind restrictive NATs/firewalls), whenever the relay's own hostinfo has an established relay state but has not yet finished punching/learning its own remote address.

### Recommendation
Add an explicit `via.GetRemote().IsValid()` check in `SendVia` before calling `f.writers[0].WriteTo(...)`, mirroring the check already present in `sendNoMetrics`, and propagate failure back to the caller (`sendNoMetrics`'s relay loop) so it can try the next relay candidate in `hostinfo.relayState.CopyRelayIps()` instead of silently dropping the packet.

### Proof of Concept
Not independently exploitable via a standalone script within this review; the condition depends on internal timing between relay-state establishment (`Relay.State == Established`) and remote-endpoint learning (`HostInfo.GetRemote()`), which occur asynchronously. This was identified by static code-path comparison between `sendNoMetrics` (which validates) and `SendVia` (which does not), both writing to the same UDP transport.

func (hm *HostMap) QueryVpnAddrsRelayFor(targetIps []netip.Addr, relayHostIp netip.Addr) (*HostInfo, *Relay, error) {
	hm.RLock()
	defer hm.RUnlock()

	// This runs per relayed packet, so check the primary with a single map probe and only consult
	// moreHosts when the primary can't relay for us.
	h, ok := hm.Hosts[relayHostIp]
	if !ok {
		return nil, nil, errors.New("unable to find host")
	}

	for _, targetIp := range targetIps {
		r, ok := h.relayState.QueryRelayForByIp(targetIp)
		if ok && r.State == Established {
			return h, r, nil
		}
	}

	if list, ok := hm.moreHosts[relayHostIp]; ok {
		// list[0] is the primary we already checked
		for _, h := range list[1:] {
			for _, targetIp := range targetIps {
				r, ok := h.relayState.QueryRelayForByIp(targetIp)
				if ok && r.State == Established {
					return h, r, nil
				}
			}
		}
	}

	return nil, nil, errors.New("unable to find host with relay")
}
