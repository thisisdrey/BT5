## Finding

### Title
Exchange bonding-curve pool balance can be driven negative because the legacy (default) processor skips the post-trade solvency check - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()` performs the bonding-curve swap and then only validates that the resulting pool balances are non-negative when `hardenedCalc == true`. Since `ALLOW_HARDEN_EXCHANGE_CALCULATION` defaults to `0` (off) and can only be turned on by a committee proposal, every `ExchangeTransactionContract` submitted by an ordinary account currently runs through the legacy, unchecked path. This mirrors the reported `executeBid()` issue: a state-mutating balance adjustment is performed without verifying the resulting balance stays non-negative, allowing value to be created out of thin air / the pool to become insolvent.

### Finding Description
`ExchangeCapsule.transaction()` computes `newFirstTokenBalance` / `newSecondTokenBalance` from the trade and only guards against a negative result inside an `if (hardenedCalc && ...)` block: [1](#0-0) 

When `hardenedCalc` is `false` (the default, driven by `dynamicStore.allowHardenExchangeCalculation()`/`allowHarden()`), the swap uses the legacy `ExchangeProcessor`, which performs the AMM constant-supply math with plain `double`/`Math.pow` arithmetic instead of the `BigDecimal` arithmetic used by `SafeExchangeProcessor`: [2](#0-1) 

Floating point rounding in this legacy path can yield a `buyTokenQuant` that exceeds the current `buyTokenBalance`, and with the guard disabled, `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` (or the symmetric first-token case) is written back to the pool even if negative: [3](#0-2) 

This is invoked directly from `ExchangeTransactionActuator.execute()`, which any account can trigger by broadcasting an `ExchangeTransactionContract`: [4](#0-3) 

`ExchangeTransactionActuator.doValidate()` only checks that the *caller's own* balance/asset is sufficient for the trade requested; it never checks whether the resulting exchange pool balance remains non-negative: [5](#0-4) 

The default value of the mitigating flag confirms this path is currently active in production configurations that have not enacted the proposal: [6](#0-5) 

### Impact Explanation
If a crafted `sellTokenQuant`/pool-balance combination causes the legacy processor to compute a payout larger than the remaining pool reserve, the pool's `firstTokenBalance`/`secondTokenBalance` (TRX and/or TRC10 asset accounting inside the `ExchangeCapsule`) is set negative and persisted via `Commons.putExchangeCapsule`. Downstream, any account holding a claim on that pool (via `ExchangeInjectActuator`/`ExchangeWithdrawActuator`) can extract tokens/TRX that are no longer backed by the pool's real holdings, i.e., an unbacked balance is created, directly parallel to the "printing cash" impact described in the report.

### Likelihood Explanation
Exploitation requires crafting exchange parameters (extreme sell/buy ratios or repeated small trades against small pool reserves) that push the legacy `double`-based bonding curve math past the exact reserve amount. This is plausible given the codebase's own test suite (`ExchangeProcessorTest`) explicitly demonstrates measurable divergence between the legacy and hardened processors under identical inputs (`testStrictMath`, `Assert.assertNotEquals(anotherTokenQuant, result)`), confirming the legacy math is imprecise by design. Since the hardening flag defaults to off and must be proposed/enacted by the committee, the vulnerable code path is live unless/until that proposal passes. [7](#0-6) 

### Recommendation
Move the non-negative pool-balance invariant check outside the `hardenedCalc` conditional in `ExchangeCapsule.transaction()` so it always applies (mirroring the fix pattern from the report: validate solvency unconditionally after the balance adjustment), regardless of `ALLOW_HARDEN_EXCHANGE_CALCULATION`, or make `SafeExchangeProcessor` the default until the proposal is enacted.

### Proof of Concept
Not independently reproducible from static analysis alone: exploiting this requires computing exact reserve/quantity values that trigger floating-point divergence in `ExchangeProcessor.exchangeFromSupply`. The codebase's own `ExchangeProcessorTest.testStrictMath` (line 272-280) already demonstrates that legacy vs. hardened math diverge for identical inputs, which is the mechanism needed to breach the reserve invariant, but a concrete triggering input pair was not derivable within available tool access.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
