### Title
Command/argument injection into `git` via unsanitized `remote` field in Bazel's git repository fetching tooling - (File: tools/build_defs/repo/git_worker.bzl)

### Summary
`git_repository`/`new_git_repository` (and, via Bzlmod, a registry's `source.json` with `"type": "git_repository"`) accept a `remote` string that Bazel's own shipped Starlark tooling passes verbatim as an argument to the `git` binary, without validating its scheme or rejecting `git`-specific argument/transport-injection payloads (e.g. the `ext::` transport helper). This mirrors the jsii-diff bug class: an attacker-controlled string meant to be a "location specifier" is handed to an external tool that itself interprets embedded syntax as a command to execute.

### Finding Description
`git.bzl` declares `remote` as a plain, unchecked `attr.string` [1](#0-0) . `git_repo()` stores this value verbatim into the `_GitRepoInfo.remote` field [2](#0-1)  and `_update()` passes it straight to `add_origin`, which invokes `git remote add origin <remote>` [3](#0-2) , followed immediately by `fetch(ctx, git_repo)` which runs `git fetch origin ... -- <fetch_ref>` [4](#0-3) .

`git` itself supports remote-helper transport prefixes (for example `ext::<shell-command>`) that cause `git fetch`/`git remote` to spawn arbitrary shell commands using the remainder of the string as the command line — this is a documented feature of git's transport-helper protocol, not something Bazel's wrapper accounts for. Bazel neither restricts `remote` to a benign set of schemes (`https://`, `git://`, `ssh://`) nor sets `GIT_ALLOW_PROTOCOL`/`protocol.*.allow` to disable helper transports before invoking `git`, so any string reaching this code path is executed with full interpretive power of the locally-installed `git`.

Critically, in the Bzlmod flow, `remote` for a `git_repository`-typed module source is populated straight from a registry's `source.json` (as documented: `type: git_repository` carries `remote`, `commit`, `tag`, etc., taken directly from the registry) — this is exactly the kind of "location specifier" field described in the docs. [5](#0-4)  Unlike the `archive` type, which is bound by an `integrity`/`sha256` checksum on the downloaded bytes, the `git_repository` type has **no equivalent authenticity check on `remote` itself** — the `commit` value only pins the tree that would eventually be checked out, but the injection fires during `git remote add`/`git fetch`, before any commit is resolved or verified, so pinning the commit does not stop it.

### Impact Explanation
If a victim consumes a module version whose `source.json` declares `type: git_repository` with a malicious `remote` (e.g. served by a hostile/compromised custom registry configured via `--registry`, or a mirror registry that a transitive dependency's module graph causes to be consulted), `bazel build`/`bazel fetch` will invoke `git`, which executes the attacker-chosen command with the permissions of the Bazel build user. This is arbitrary command execution during repository fetching, i.e. build-time RCE, matching CWE-78/AC:L/PR:N/UI:R just as in the jsii-diff advisory (except the "tool" here is Bazel's git-repo-fetching helper and the interpreter is `git`'s transport-helper mechanism instead of a shell).

### Likelihood Explanation
Reaching this code path requires only that a `git_repository`-typed dependency (native or via a registry's `source.json`) resolve to an attacker-influenced `remote` string — no MITM of an integrity-checked transport is needed, since this field carries no checksum at all, unlike the `archive` type's `integrity`/`sha256`. Any victim configuring or transitively pulling from an untrusted/compromised registry, or using `new_git_repository`/`git_repository` with any dependency-supplied remote string, is exposed. Default flags do not mitigate this because there is no scheme allowlist or `GIT_ALLOW_PROTOCOL` restriction present in `git_worker.bzl`.

### Recommendation
- Validate `remote` against an allowlist of expected schemes (`https://`, `http://`, `git://`, `ssh://`, `file://`) before passing it to `git`, rejecting anything containing `::` transport-helper syntax or leading `-` (which git could otherwise parse as an option).
- Explicitly set `GIT_ALLOW_PROTOCOL`/pass `-c protocol.ext.allow=never` (and disable other non-network helpers) when invoking `git` from `git_worker.bzl`, mirroring the existing sanitization of `GIT_*` environment variables (`_GIT_LOCAL_ENV_VARS`). [6](#0-5) 
- For Bzlmod `git_repository` sources coming from a registry's `source.json`, require and verify some form of authenticity binding on `remote` analogous to the `integrity` field used for archives, so a compromised/hostile registry cannot silently swap in an executable payload.

### Proof of Concept
Using a hostile/custom registry (reachable via `--registry` or as a fallback registry in the module resolution graph), publish a module version whose `source.json` is:
```json
{
  "type": "git_repository",
  "remote": "ext::sh -c 'touch /tmp/pwned; git upload-pack \"$1\"' --",
  "commit": "0000000000000000000000000000000000000000"
}
```
When a victim's `bazel build` resolves a `bazel_dep` on this module version, Bazel's generated `git_repository` invocation calls `add_origin(ctx, git_repo, ctx.attr.remote)` → `git remote add origin ext::sh -c '...' --` followed by `git fetch origin -- <ref>` [7](#0-6) , causing `git` to invoke the embedded shell command (`touch /tmp/pwned`) on the victim's machine during the fetch phase — reproducible as a `src/test/shell/bazel` integration test analogous to `repository_abort_test.sh`, using a local registry serving the malicious `source.json` and asserting the marker file is created.

```text
def _update(ctx, git_repo):
    ctx.delete(git_repo.directory)

    init(ctx, git_repo)
    add_origin(ctx, git_repo, ctx.attr.remote)
    fetch(ctx, git_repo)
    reset(ctx, git_repo)
    clean(ctx, git_repo)

    if git_repo.recursive_init_submodules:
        ctx.report_progress("Updating submodules recursively")
        update_submodules(ctx, git_repo, recursive = True)
    elif git_repo.init_submodules:
        ctx.report_progress("Updating submodules")
        update_submodules(ctx, git_repo)

def init(ctx, git_repo):
    cl = ["git", "init", str(git_repo.directory)]
    st = ctx.execute(cl, environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS)
    if st.return_code != 0:
        _error(ctx.name, cl, st.stderr)

def add_origin(ctx, git_repo, remote):
    _git(ctx, git_repo, "remote", "add", "origin", remote)

def fetch(ctx, git_repo):
    args = ["fetch", "origin"]

    sparse_checkout_patterns_or_file = \
        getattr(ctx.attr, "sparse_checkout_patterns", None) or \
        getattr(ctx.attr, "sparse_checkout_file", None)
    if sparse_checkout_patterns_or_file:
        if _git_sparse_checkout_config(ctx, git_repo):
            # Use filter to disable downloading file contents until we set the `sparse-checkout` patterns.
            args.append("--filter=blob:none")
        else:
            print("WARNING: Sparse checkout is not supported. Doing a full checkout.")
            sparse_checkout_patterns_or_file = None

    args.extend(["--", git_repo.fetch_ref])
    st = _git_maybe_shallow(ctx, git_repo, *args)

    if sparse_checkout_patterns_or_file:
        _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file)

    if st.return_code == 0:
        return
    if ctx.attr.commit:
        # Perhaps uploadpack.allowReachableSHA1InWant or similar is not enabled on the server;
        # fall back to fetching all branches, tags, and history.
        # The semantics of --tags flag of git-fetch have changed in Git 1.9, from 1.9 it means
        # "everything that is already specified and all tags"; before 1.9, it used to mean
        # "ignore what is specified and fetch all tags".
        # The arguments below work correctly for both before 1.9 and after 1.9,
        # as we directly specify the list of references to fetch.
        _report_progress(ctx, git_repo, shallow_failed = True)
        _git(
            ctx,
            git_repo,
            "fetch",
            "origin",
            "--",
            "refs/heads/*:refs/remotes/origin/*",
            "refs/tags/*:refs/tags/*",
        )
    else:
        _error(ctx.name, ["git"] + args, st.stderr)
```
