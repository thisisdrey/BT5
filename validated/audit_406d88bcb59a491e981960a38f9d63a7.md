### Title
Negative rebases break collateral backing and can freeze later withdrawals - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`DepositToken` mints receipt tokens according to the Treasury balance delta at deposit time, but withdrawal accounting remains fixed at the minted `totalSupply` and does not account for later changes in the underlying token's balance. If an accepted collateral is an elastic-supply token and a negative rebase reduces `Treasury`'s balance, early withdrawers can still burn receipt tokens and pull the pre-rebase amount, leaving the Treasury undercollateralized and causing later withdrawals to revert. This is reachable through public `DepositToken.withdraw()` and `Treasury.pull()` calls once such collateral is configured. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`DepositToken.deposit()` deliberately measures the Treasury's received amount with a balance delta, which correctly handles ordinary fee-on-transfer deposits but only captures the balance at that instant. [1](#0-0)  The minted `msdTOKEN` supply is then maintained as ordinary fixed ledger balances rather than as claims whose redemption amount follows the Treasury's current underlying balance. [4](#0-3)  On withdrawal, `_withdraw()` burns `_withdrawn` receipt tokens and instructs Treasury to transfer the same nominal underlying amount, without checking whether the underlying still covers aggregate `totalSupply`. [2](#0-1)  `Treasury.pull()` performs the raw ERC-20 transfer and has no pro-rata redemption logic or rebasing adjustment. [3](#0-2) 

### Impact Explanation
The invariant `DepositToken.totalSupply() == underlying.balanceOf(Treasury)` is assumed but not preserved for elastic-supply collateral; the repository's own invariant test encodes this expectation. [5](#0-4)  After a negative rebase, the aggregate withdrawal claims exceed the Treasury balance, so earlier withdrawals consume more than their post-rebase proportional claim. Later users' unlocked receipt tokens remain valid, but `_burn()` followed by `Treasury.pull()` causes the token transfer to revert when the Treasury is exhausted. [2](#0-1) [3](#0-2)  This produces protocol insolvency and temporary or permanent freezing of residual collateral unless replacement tokens are supplied or the deployment is rescued through governance. [6](#0-5) 

### Likelihood Explanation
The vulnerability requires a negative-rebasing or otherwise balance-reducing collateral to be registered, so it does not affect ordinary fixed-supply ERC-20 collateral. Once configured, no privileged call is needed at exploit time: an unprivileged holder can deposit before a public rebase, wait for the Treasury balance to decrease, and call `withdraw()` before other holders. [7](#0-6) [8](#0-7)  Neither `nonReentrant`, `whenNotPaused`, `whenNotShutdown`, nor the account lock check verifies current Treasury solvency or converts receipt tokens to a pro-rata claim. [8](#0-7) [9](#0-8) 

### Recommendation
Do not register rebasing, elastic-supply, balance-reducing, or otherwise non-unit-of-account tokens as `DepositToken.underlying()` collateral. [10](#0-9)  If such assets must be supported, wrap them in a non-rebasing share token before deposit, or redesign withdrawals to distribute `min(requested, pro-rata Treasury balance)` and update claims rather than performing nominal transfers. [2](#0-1)  Add a solvency assertion or rescue path before withdrawals, and explicitly test negative rebase, positive rebase, fee-on-transfer, and multiple-user withdrawal ordering. [5](#0-4) 

### Proof of Concept
A Foundry PoC can reproduce the issue with a mock rebasing ERC-20 whose `rebase(uint256 factor)` proportionally rewrites every holder balance, including Treasury:

```solidity
// test/foundry/poc/RebaseCollateral.t.sol
function test_negativeRebase_freezesLaterWithdrawals() public {
    MockRebaseToken underlying = new MockRebaseToken();

    // Deploy Pool, FeeProvider, Treasury, and DepositToken as in
    // DepositToken.invariants.t.sol, then register depositToken.
    underlying.mint(alice, 100 ether);
    underlying.mint(bob,   100 ether);

    vm.startPrank(alice);
    underlying.approve(address(depositToken), 100 ether);
    depositToken.deposit(100 ether, alice);
    vm.stopPrank();

    vm.startPrank(bob);
    underlying.approve(address(depositToken), 100 ether);
    depositToken.deposit(100 ether, bob);
    vm.stopPrank();

    assertEq(depositToken.totalSupply(), 200 ether);
    assertEq(underlying.balanceOf(address(treasury)), 200 ether);

    // Treasury now holds only 100 tokens; outstanding claims remain 200.
    underlying.rebaseAllBalances(0.5e18);

    vm.prank(alice);
    depositToken.withdraw(100 ether, alice); // succeeds, drains Treasury

    vm.prank(bob);
    vm.expectRevert(); // ERC20 insufficient-balance transfer revert
    depositToken.withdraw(100 ether, bob);
}
```

The test demonstrates that deposits mint fixed claims, the rebase breaks the tested `totalSupply == Treasury balance` invariant, and the second withdrawal reverts after the first claim consumes the diminished reserve. [1](#0-0) [2](#0-1) [5](#0-4)
