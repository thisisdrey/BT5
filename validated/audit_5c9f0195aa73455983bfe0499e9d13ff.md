Confirmed: nonce is strictly incremented in `submit()` before dispatch, so once a message's nonce is consumed, it can never be replayed/retried on Bridge Hub, even though downstream XCM execution on Asset Hub is a separate, unenforced step. [1](#0-0) 

### Title
Out-of-order/independent `RegisterToken`/`SendToken` Snowbridge V1 messages cause AssetHub-side XCM to abort with no `AssetClaimer`, permanently trapping bridged funds - (File: `bridges/snowbridge/primitives/inbound-queue/src/v1.rs`)

### Summary
Snowbridge's V1 inbound-queue converts independently-nonced Ethereum messages (`RegisterToken`, `SendToken`) into separate XCM programs sent to AssetHub. `SendToken`'s XCM assumes the token is already registered as a foreign asset on AssetHub via `pallet-assets`. If the `SendToken` message for a given token is executed on AssetHub before (or without) the corresponding `RegisterToken` message being processed successfully, the `DepositAsset` instruction fails because the asset id does not yet exist, aborting the program after assets were already brought into the XCM holding register via `ReserveAssetDeposited`. Because the V1 `MessageToXcm::convert_send_token` never sets an `AssetClaimer` hint (unlike the V2 converter), the trapped assets can only be reclaimed by whoever can reconstruct the exact XCM origin used during execution (the descended `UniversalOrigin(GlobalConsensus(Ethereum))` origin) — not by the intended beneficiary. This mirrors the external report's core defect: a cross-chain message assumes state that doesn't exist on the destination side, the transaction fails, and the bridged value becomes permanently locked because the failure/refund path is unreachable by the affected user.

### Finding Description
`Nonce<T>` for a channel is strictly incremented and checked in `submit()` before verification of downstream success; once consumed it can never be replayed. [2](#0-1) 

The V1 `MessageToXcm::convert_send_token` builds an XCM program that performs `ReserveAssetDeposited(asset)` to pull the bridged token into the local holding register, then attempts `DepositAsset` to the beneficiary (or `DepositReserveAsset` onward to a sibling parachain) — with **no `SetHints`/`AssetClaimer` instruction** anywhere in the program. [3](#0-2) 

This differs from the V2 converter, which explicitly sets `AssetClaimer` before executing arbitrary/foreign-asset logic specifically so that trapped funds remain recoverable by a known party: [4](#0-3) 

`RegisterToken` (which performs the `Transact` call to create the foreign asset on AssetHub) is sent as an entirely separate, independently-nonced message from `SendToken`: [5](#0-4) [6](#0-5) 

There is no atomicity or ordering guarantee enforced between these two messages once they leave the Ethereum Gateway and are individually verified/dispatched by relayers — a relayer can legitimately (without being malicious) submit the `SendToken` proof before the `RegisterToken` proof (e.g., differing gas/priority on Ethereum, differing relayer latency, or `RegisterToken` XCM itself failing due to insufficient deposit/fee on AssetHub). When AssetHub processes `SendToken`'s XCM and reaches `DepositAsset`/`DepositReserveAsset` for a still-unregistered `ForeignAssets` id, `pallet-assets` rejects the deposit, aborting the XCM program. The `pallet-message-queue`'s `process_message_payload` treats this as a completed-but-failed execution (`Processed { success: false }`) rather than a retryable error, so it will never be reprocessed. [7](#0-6) 

The V2 test suite explicitly demonstrates this exact failure mode (asset not yet created before `ReserveAssetDeposited`/`DepositAsset` sequencing) resulting in `MessageQueue::Processed { success: false }`, confirming the underlying XCM/asset-registration ordering hazard is real and reachable in this codebase — the V1 path has the same hazard but additionally lacks the `AssetClaimer` mitigation present in V2: [8](#0-7) 

### Impact Explanation
When the `DepositAsset`/`DepositReserveAsset` instruction fails after assets have already entered the holding register via `ReserveAssetDeposited`, the XCM executor traps the remaining holding assets (`AssetTrap`). Recovery via `pallet_xcm::claim_assets` requires the claimant to supply an `origin` matching the trap key, which is derived from the *execution origin at the point of the trap* — here, the `UniversalOrigin(GlobalConsensus(Ethereum))` descended location set by the inbound-queue converter, not the beneficiary's account. Ordinary users have no practical way to construct and authorize this origin, so the bridged tokens are permanently locked with no route to their intended owner. This is a genuine "permanent user-fund lock" impact within the accepted Snowbridge/BridgeHub scope: it requires no malicious relayer, validator, or governance actor — only ordinary asynchronous relaying of two independent, correctly-signed, correctly-proven Ethereum events in a benign but disallowed order.

### Likelihood Explanation
Moderate-to-high. `RegisterToken` and `SendToken` are emitted and relayed as independent events/messages with independent nonce sequences per channel; nothing in the Gateway contract or relayer software enforces that `RegisterToken` for a token is durably finalized on AssetHub before any `SendToken` for the same token is submitted. Network delays, relayer restarts, or even legitimate first-time bridging of a token where a user's transfer races the registration transaction are enough to trigger the ordering hazard. The V1 message converter's structural absence of an `AssetClaimer` (present in V2 but not backported to V1) means the mitigating control is inconsistent across live versions.

### Recommendation
Add a `SetHints { hints: [AssetClaimer { location: <intended beneficiary or bridge sovereign> }] }` instruction to the V1 `convert_send_token`/`convert_send_native_token` XCM builders (mirroring the V2 converter), so that any assets trapped due to unregistered-asset ordering hazards remain claimable by a well-known, reachable account. Additionally, consider making `SendToken` XCM defensively check/register the asset (or fail closed with `ReserveAssetDeposited` never entering holding) rather than relying on prior successful execution of an unrelated, independently-ordered message.

### Proof of Concept
1. Ethereum Gateway emits `RegisterToken(token=X, fee)` as channel nonce N, and shortly after `SendToken(token=X, destination, amount, fee)` as nonce N+1.
2. A relayer submits the `SendToken` proof (nonce N+1) to Bridge Hub via `submit()` before the `RegisterToken` proof (nonce N) has been submitted/finalized on AssetHub (e.g., due to relay latency, or the `RegisterToken` XCM itself stalling on delivery fees).
   - `submit()` only checks that `envelope.nonce == nonce + 1`; nothing blocks accepting nonce N+1 before nonce N's XCM has landed and completed on AssetHub, since nonce is a Bridge-Hub-local, per-channel monotonic counter unrelated to AssetHub-side XCM completion. [1](#0-0) 
3. AssetHub's `MessageQueue` executes `SendToken`'s XCM: `ReserveAssetDeposited(asset X, amount)` succeeds (adds to holding), but the subsequent `DepositAsset`/`DepositReserveAsset` fails because `pallet-assets` has no entry for token X yet. [3](#0-2) 
4. `pallet-message-queue` records `Processed { success: false }` — the message is permanently consumed, never retried. [9](#0-8) 
5. The trapped asset X (amount from step 1) sits in the `AssetTrap` under the Ethereum `UniversalOrigin` execution context. No `AssetClaimer` was set, so the intended beneficiary cannot invoke `claim_assets` (they cannot produce the matching origin). The bridged funds are permanently locked, with the corresponding nonce on the Ethereum Gateway already marked as consumed (no resubmission possible).

			ensure!(!Self::operating_mode().is_halted(), Error::<T>::Halted);

			// submit message to verifier for verification
			T::Verifier::verify(&event.event_log, &event.proof)
				.map_err(|e| Error::<T>::Verification(e))?;

			// Decode event log into an Envelope
			let envelope =
				Envelope::try_from(&event.event_log).map_err(|_| Error::<T>::InvalidEnvelope)?;

			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == envelope.gateway, Error::<T>::InvalidGateway);

			// Retrieve the registered channel for this message
			let channel =
				T::ChannelLookup::lookup(envelope.channel_id).ok_or(Error::<T>::InvalidChannel)?;

			// Verify message nonce
			<Nonce<T>>::try_mutate(envelope.channel_id, |nonce| -> DispatchResult {
				if *nonce == u64::MAX {
					return Err(Error::<T>::MaxNonceReached.into());
				}
				if envelope.nonce != nonce.saturating_add(1) {
					Err(Error::<T>::InvalidNonce.into())
				} else {
					*nonce = nonce.saturating_add(1);
					Ok(())
				}
			})?;

	fn convert_register_token(
		message_id: H256,
		chain_id: u64,
		token: H160,
		fee: u128,
	) -> (Xcm<()>, Balance) {
		let network = Ethereum { chain_id };
		let xcm_fee: Asset = (Location::parent(), fee).into();
		let deposit: Asset = (Location::parent(), CreateAssetDeposit::get()).into();

		let total_amount = fee + CreateAssetDeposit::get();
		let total: Asset = (Location::parent(), total_amount).into();

		let bridge_location = Location::new(2, GlobalConsensus(network));

		let owner = EthereumLocationsConverterFor::<[u8; 32]>::from_chain_id(&chain_id);
		let asset_id = Self::convert_token_address(network, token);
		let create_call_index: [u8; 2] = CreateAssetCall::get();
		let inbound_queue_pallet_index = InboundQueuePalletInstance::get();

		let xcm: Xcm<()> = vec![
			// Teleport required fees.
			ReceiveTeleportedAsset(total.into()),
			// Pay for execution.
			BuyExecution { fees: xcm_fee, weight_limit: Unlimited },
			// Fund the snowbridge sovereign with the required deposit for creation.
			DepositAsset { assets: Definite(deposit.into()), beneficiary: bridge_location.clone() },
			// This `SetAppendix` ensures that `xcm_fee` not spent by `Transact` will be
			// deposited to snowbridge sovereign, instead of being trapped, regardless of
			// `Transact` success or not.
			SetAppendix(Xcm(vec![
				RefundSurplus,
				DepositAsset { assets: AllCounted(1).into(), beneficiary: bridge_location },
			])),
			// Only our inbound-queue pallet is allowed to invoke `UniversalOrigin`.
			DescendOrigin(PalletInstance(inbound_queue_pallet_index).into()),
			// Change origin to the bridge.
			UniversalOrigin(GlobalConsensus(network)),
			// Call create_asset on foreign assets pallet.
			Transact {
				origin_kind: OriginKind::Xcm,
				fallback_max_weight: Some(Weight::from_parts(400_000_000, 8_000)),
				call: (
					create_call_index,
					asset_id,
					MultiAddress::<[u8; 32], ()>::Id(owner),
					MINIMUM_DEPOSIT,
				)
					.encode()
					.into(),
			},
			// Forward message id to Asset Hub
			SetTopic(message_id.into()),
			// Once the program ends here, appendix program will run, which will deposit any
			// leftover fee to snowbridge sovereign.
		]
		.into();

		(xcm, total_amount.into())
	}

	fn convert_send_token(
		message_id: H256,
		chain_id: u64,
		token: H160,
		destination: Destination,
		amount: u128,
		asset_hub_fee: u128,
	) -> (Xcm<()>, Balance) {
		let network = Ethereum { chain_id };
		let asset_hub_fee_asset: Asset = (Location::parent(), asset_hub_fee).into();
		let asset: Asset = (Self::convert_token_address(network, token), amount).into();

		let (dest_para_id, beneficiary, dest_para_fee) = match destination {
			// Final destination is a 32-byte account on AssetHub
			Destination::AccountId32 { id } => {
				(None, Location::new(0, [AccountId32 { network: None, id }]), 0)
			},
			// Final destination is a 32-byte account on a sibling of AssetHub
			Destination::ForeignAccountId32 { para_id, id, fee } => (
				Some(para_id),
				Location::new(0, [AccountId32 { network: None, id }]),
				// Total fee needs to cover execution on AssetHub and Sibling
				fee,
			),
			// Final destination is a 20-byte account on a sibling of AssetHub
			Destination::ForeignAccountId20 { para_id, id, fee } => (
				Some(para_id),
				Location::new(0, [AccountKey20 { network: None, key: id }]),
				// Total fee needs to cover execution on AssetHub and Sibling
				fee,
			),
		};

		let total_fees = asset_hub_fee.saturating_add(dest_para_fee);
		let total_fee_asset: Asset = (Location::parent(), total_fees).into();
		let inbound_queue_pallet_index = InboundQueuePalletInstance::get();

		let mut instructions = vec![
			ReceiveTeleportedAsset(total_fee_asset.into()),
			BuyExecution { fees: asset_hub_fee_asset, weight_limit: Unlimited },
			DescendOrigin(PalletInstance(inbound_queue_pallet_index).into()),
			UniversalOrigin(GlobalConsensus(network)),
			ReserveAssetDeposited(asset.clone().into()),
			ClearOrigin,
		];

		match dest_para_id {
			Some(dest_para_id) => {
				let dest_para_fee_asset: Asset = (Location::parent(), dest_para_fee).into();
				let bridge_location = Location::new(2, GlobalConsensus(network));

				instructions.extend(vec![
					// After program finishes deposit any leftover assets to the snowbridge
					// sovereign.
					SetAppendix(Xcm(vec![DepositAsset {
						assets: Wild(AllCounted(2)),
						beneficiary: bridge_location,
					}])),
					// Perform a deposit reserve to send to destination chain.
					DepositReserveAsset {
						// Send over assets and unspent fees, XCM delivery fee will be charged from
						// here.
						assets: Wild(AllCounted(2)),
						dest: Location::new(1, [Parachain(dest_para_id)]),
						xcm: vec![
							// Buy execution on target.
							BuyExecution { fees: dest_para_fee_asset, weight_limit: Unlimited },
							// Deposit assets to beneficiary.
							DepositAsset { assets: Wild(AllCounted(2)), beneficiary },
							// Forward message id to destination parachain.
							SetTopic(message_id.into()),
						]
						.into(),
					},
				]);
			},
			None => {
				instructions.extend(vec![
					// Deposit both asset and fees to beneficiary so the fees will not get
					// trapped. Another benefit is when fees left more than ED on AssetHub could be
					// used to create the beneficiary account in case it does not exist.
					DepositAsset { assets: Wild(AllCounted(2)), beneficiary },
				]);
			},
		}

		// Forward message id to Asset Hub.
		instructions.push(SetTopic(message_id.into()));

		// The `instructions` to forward to AssetHub, and the `total_fees` to locally burn (since
		// they are teleported within `instructions`).
		(instructions.into(), total_fees.into())
	}
