### Title
Unchecked byte-slice indexing on `git rev-list` walk output during transaction commit can panic and crash the whole Gitaly process - (File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go)

### Summary
`packObjects` is invoked for every WAL-backed repository transaction (i.e., on every push that goes through the transaction manager). Inside one of its `errgroup` goroutines it reads lines from `git-rev-list --objects --missing=print` and blindly indexes the first byte of each scanned line with `objectLine[0]`, without checking that the line is non-empty. This mirrors the reported EVM bug class of missing input-length checks before slice indexing (e.g. `methodID := input[:4]`), except here the resulting panic occurs inside a goroutine spawned via `errgroup.Group.Go`, which is *not* protected by Gitaly's gRPC `panichandler` interceptor — that middleware only wraps the top-level RPC handler goroutine, not arbitrary child goroutines spawned during processing.

### Finding Description
`packObjects` walks new reference tips and quarantined objects via `WalkObjects`, which shells out to `git rev-list --objects --missing=print --stdin` [1](#0-0) . The output is consumed line-by-line with `bufio.NewScanner` and each line is immediately indexed at position 0 without a length check:

```go
scanner := bufio.NewScanner(objectWalkReader)
...
for scanner.Scan() {
    objectLine := scanner.Text()
    if objectLine[0] == '?' {
``` [2](#0-1) 

This code runs inside `group.Go(...)`, one of several goroutines started via `errgroup.WithContext` for `packObjects` [3](#0-2) [4](#0-3) .

Unlike top-level RPC handler goroutines, which are protected by the global `panichandler.UnaryPanicHandler`/`StreamPanicHandler` interceptors installed as the last interceptor in the chain [5](#0-4) [6](#0-5) , a panic raised inside a bare `errgroup.Go` closure is not recovered anywhere in this call path. Gitaly's own style guide explicitly calls out this exact risk: "every new goroutine has the potential to crash the process. Any unrecovered panic can cause the entire process to crash and take out any in-flight requests" and recommends `dontpanic.Go` for goroutines whose panic-safety isn't obvious [7](#0-6) . `packObjects`'s goroutines do not use `dontpanic`, nor does `errgroup` provide panic recovery on its own.

While an empty scan line from `git-rev-list` is not expected under normal operation, the parsing logic makes no defensive check, and if a blank/short line is ever produced by `bufio.Scanner` (e.g., an unexpected trailing empty token, a truncated line at EOF/pipe interruption, or a future/edge-case Git output variance), `objectLine[0]` will panic with an index-out-of-range. Because this happens in an unrecovered background goroutine rather than the RPC's own goroutine, the panic is not caught by the gRPC panic-handler middleware and will crash the entire Gitaly process, not just fail the single request — a categorically worse outcome than the EVM report's "recovered, but free-of-cost DoS" scenario.

### Impact Explanation
A crash of the whole `gitaly` process aborts every in-flight RPC across all repositories served by that process, not just the triggering request. Given `packObjects` runs on the write path for every transaction-managed push, a reliable trigger would constitute a low-cost, repeatable denial-of-service affecting all tenants of the affected storage node.

### Likelihood Explanation
Likelihood is difficult to fully confirm from static analysis alone: triggering an empty line from `git-rev-list --objects --missing=print` output would require an edge case in Git's own output formatting (e.g., interaction with corrupted/crafted quarantine objects, unusual OIDs, or scanner behavior at buffer/EOF boundaries) that could not be verified without dynamic testing. The lack of a defensive length check combined with the absence of panic recovery in this specific goroutine is a concrete code defect regardless of whether a concrete Git-output edge case has been proven to produce the empty line in practice.

### Recommendation
- Add a length/emptiness check before indexing `objectLine[0]`, returning a structured error instead of panicking on malformed/empty lines.
- Wrap the `packObjects` errgroup goroutines (or apply `dontpanic.Try`/`dontpanic.Go`-style recovery inside each `group.Go` closure) so that any unexpected panic is converted into an error result for that goroutine rather than crashing the process, consistent with the guidance already documented in `STYLE.md`.
- Audit other `errgroup.Go`/bare `go func()` call sites in the transaction manager and related packfile/parsing code for the same unprotected-goroutine-panic pattern.

### Proof of Concept
Not independently reproducible from static review alone: it requires demonstrating a way to force `git rev-list --objects --missing=print --stdin` to emit an empty line (or truncated single-character line) into stdout that `bufio.Scanner` surfaces via `scanner.Text()`, which was not verified against a live Git binary in this session. The vulnerability claim rests on the confirmed code fact that `objectLine[0]` is indexed with no length guard in an unrecovered background goroutine [8](#0-7) , and that this goroutine's panic is not covered by the gRPC-level `panichandler` interceptor which only guards the top-level handler goroutine [5](#0-4) .

// WalkObjects walks the object graph starting from heads and writes to the output the objects it
// sees. Objects that are encountered during the walk and exist in the object database are written
// out as `<oid> <path>\n` with the `<path>` being sometimes present if applicable. Objects that
// were encountered during the walk but do not exist in the object database are written out
// as `?<oid>\n`.
func (repo *Repo) WalkObjects(ctx context.Context, heads io.Reader, output io.Writer) error {
	var stderr bytes.Buffer
	if err := repo.ExecAndWait(ctx,
		gitcmd.Command{
			Name: "rev-list",
			Flags: []gitcmd.Option{
				gitcmd.Flag{Name: "--objects"},
				gitcmd.Flag{Name: "--missing=print"},
				gitcmd.Flag{Name: "--stdin"},
			},
		},
		gitcmd.WithStdin(heads),
		gitcmd.WithStdout(output),
		gitcmd.WithStderr(&stderr),
	); err != nil {
		return structerr.New("rev-list: %w", err).WithMetadata("stderr", stderr.String())
	}

	return nil
}

		// Objects that are found are included in the transaction's packfile.

		// Objects that are not found are recorded as the transaction's

		defer objectsToPackWriter.CloseWithError(returnedErr)

		packObjectsStarted := false
		for scanner.Scan() {
			objectLine := scanner.Text()
			if objectLine[0] == '?' {
				// Remove the '?' prefix so we're left with just the object ID.
				transaction.objectDependencies[git.ObjectID(objectLine[1:])] = struct{}{}
				continue
			}

			// haven't yet been launched, launch them.

			}

			return fmt.Errorf("scanning rev-list output: %w", err)
		}

// UnaryPanicHandler creates a new unary server interceptor that handles panics.
func UnaryPanicHandler(logger log.Logger) grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (resp interface{}, err error) {
		defer handleCrash(logger, info.FullMethod, func(grpcMethodName string, r interface{}) {
			err = toPanicError(grpcMethodName, r)
		})

		return handler(ctx, req)
	}
}

// StreamPanicHandler creates a new stream server interceptor that handles panics.
func StreamPanicHandler(logger log.Logger) grpc.StreamServerInterceptor {
	return func(srv interface{}, stream grpc.ServerStream, info *grpc.StreamServerInfo, handler grpc.StreamHandler) (err error) {
		defer handleCrash(logger, info.FullMethod, func(grpcMethodName string, r interface{}) {
			err = toPanicError(grpcMethodName, r)
		})

		return handler(srv, stream)
	}
}
