Audit Report

## Title
`Nfts::transfer` Fails to Clear `ItemAttributesApprovalsOf`, Letting a Former Owner's Delegate Retain Write Access After Ownership Transfer - (File: `substrate/frame/nfts/src/features/transfer.rs`)

## Summary
`Pallet::do_transfer` updates `Account`/`Item.owner` and clears `details.approvals`, `ItemPriceOf`, and `PendingSwapOf`, but never touches `ItemAttributesApprovalsOf` for the item. Because `is_valid_namespace` for `AttributeNamespace::Account(delegate)` validates write access solely against this stale map (and not against the item's current owner), a delegate approved by the previous owner keeps owner-level attribute-write authority after the item is sold or transferred to a new, non-consenting owner.

## Finding Description
`do_transfer` in `substrate/frame/nfts/src/features/transfer.rs` explicitly resets `details.approvals`, `ItemPriceOf`, and `PendingSwapOf` on every ownership change, but contains no call to remove or drain `ItemAttributesApprovalsOf::<T, I>` for the `(collection, item)` key: <cite repo="Lauraivanka/polkadot-sdk--030" path="substrate/frame/nfts/src/features/transfer.rs" start="89-103" end="103" />

`ItemAttributesApprovalsOf` is populated in `do_approve_item_attributes`, which checks `check_origin == details.owner` only at approval time: [1](#0-0) 

Subsequent writes to the `Account(delegate)` namespace are authorized purely via `is_valid_namespace`, which checks `approvals.contains(&origin)` from `ItemAttributesApprovalsOf` without re-verifying that the account approving it is still the current item owner: [2](#0-1) 

The only path that removes an entry from `ItemAttributesApprovalsOf` (besides burning the item) is `do_cancel_item_attributes_approval`, which requires the *current* owner to explicitly name the exact delegate to revoke: [3](#0-2) 

Since `transfer`, `buy_item`, and `do_claim_swap` all route through `do_transfer`, none of these paths purge stale delegate approvals, so a delegate approved by a previous owner retains write access to the `Account(delegate)` namespace on an item now owned by someone else, with no visible signal in the `Transferred` event.

## Impact Explanation
This is a genuine unauthorized-write/origin-integrity bug in a public dispatchable path (`transfer`/`buy_item`/`do_claim_swap` are permissionless, signed-origin extrinsics). It allows a party the previous owner authorized to continue exercising owner-granted write authority (`set_attribute` in the `Account(delegate)` namespace) on an NFT after legitimate transfer of ownership, without the new owner's knowledge or consent. This matches the "runtime bugs that compromise intended behavior" / "unauthorized execution" category, as the NFT ownership-transfer invariant ("transfer grants exclusive control to the new owner") is violated by a residual owner-scoped permission mapping (`ItemAttributesApprovalsOf`) that survives the ownership change.

## Likelihood Explanation
Fully reachable by an ordinary unprivileged user: mint an item, call `approve_item_attributes` for a delegate, set an attribute under `AttributeNamespace::Account(delegate)`, then transfer/sell the item via `transfer`, `buy_item`, or a swap claim. No governance, validator, or privileged role is required, and the sequence works whenever the `Attributes` and `Trading`/`Transfer` pallet features are enabled, which is the case on shipped asset-hub configurations.

## Recommendation
In `do_transfer`, drain `ItemAttributesApprovalsOf::<T, I>::take(&collection, &item)` (or equivalent) whenever ownership changes, mirroring the existing handling of `details.approvals`, `ItemPriceOf`, and `PendingSwapOf`, and unreserve any deposits tied to attributes set under the removed delegate approvals (as `do_cancel_item_attributes_approval` does for `Attribute::<T, I>::drain_prefix`), ensuring all owner-scoped mappings are synchronized atomically with the ownership change.

## Proof of Concept
1. Owner A mints `(collection, item)` and calls `approve_item_attributes(collection, item, delegate)`, populating `ItemAttributesApprovalsOf[(collection, item)] = {delegate}`.
2. `delegate` calls `set_attribute(collection, item, AttributeNamespace::Account(delegate), key, value)`, succeeding via `is_valid_namespace`, reserving a deposit from `delegate`.
3. A transfers the item to B via `Nfts::transfer` (or sells via `buy_item`). `do_transfer` updates `Item.owner` to B and clears `details.approvals`, `ItemPriceOf`, `PendingSwapOf`, but `ItemAttributesApprovalsOf[(collection, item)]` still contains `delegate`.
4. `delegate` calls `set_attribute(collection, item, AttributeNamespace::Account(delegate), key2, value2)`. `is_valid_namespace` returns `true` because `approvals.contains(&origin)` is still satisfied, even though B never approved `delegate` and is the sole current owner.
5. B has no direct visibility into this stale approval and can only remove it via `cancel_item_attributes_approval`, which requires knowing the exact `delegate` account — information not exposed by the transfer flow or its events.
