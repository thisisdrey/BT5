## Verdict: Vulnerability confirmed (with one correction to the question's premise)

**Binding claimed broken:** `debited_balance (1000) == assets_that_left_custody + refund_recredited_by_ft_resolve_withdraw`. Trace shows this equality is indeed broken to `1000 == 1000 + 1000` under a specific (not exactly "huge", but "malformed-but-length-bounded") callback payload.

### Correction to premise
A truly **huge** `ft_on_transfer`/`ft_resolve_transfer` result does **not** reach `Ok(Err(_))`. `promise_result_checked_json::<U128>` calls `env::promise_result_checked(result_idx, max_len)` with `max_len` bounded to `U128::max_json_length_root()` (~44 bytes) [1](#0-0) [2](#0-1) . An oversized result is rejected by the length check and surfaces as `Err(_)` (PromiseError), which routes to the safe `Err(_) => amount.0` branch (full amount treated as "used", no refund) [3](#0-2) . It is a **short but malformed** (non-`U128`-JSON) payload, within the length bound, that lands in `Ok(Err(_deserialize_err)) => 0`.

### Title
Attacker-controlled FT contract forces `Ok(Err(_))` branch in `ft_resolve_withdraw`, re-crediting the withdrawn amount after real transfer succeeds - (File: `contracts/defuse/src/contract/tokens/nep141/withdraw.rs`)

### Summary
Because `token` in `FtWithdraw` is attacker-controlled (any NEP-141 `AccountId` can be used, no allow-list is shown at this call site), the attacker can deploy a malicious FT contract whose `ft_transfer_call` performs a real balance transfer but returns a short, non-`U128`-parseable JSON body. `ft_resolve_withdraw` interprets this as `used = 0` and re-credits the full `amount` back to the attacker's `token_balances`, while the attacker already extracted the real value externally.

### Finding Description
`internal_ft_withdraw` debits `owner.token_balances` by `amount` before scheduling `do_ft_withdraw` → `ft_transfer_call` on the attacker-controlled `token` contract, then chains `ft_resolve_withdraw` [4](#0-3) . `do_ft_withdraw` invokes `ft_transfer_call(receiver_id, amount, memo, msg)` on `token` [5](#0-4) . Since the attacker owns `token`'s code, they can implement `ft_transfer_call` to transfer the real balance to `receiver_id` (themselves) by any means, and directly return a short byte string that is valid length-wise but not deserializable as `U128` (e.g. `"notanumber"`). In `ft_resolve_withdraw`, `promise_result_checked_json::<U128>(0)` succeeds the length check but fails JSON parsing, landing in `Ok(Err(_deserialize_err)) => 0` [3](#0-2) . `refund = amount.0.saturating_sub(0) = amount.0` is then re-deposited to `sender_id` (the attacker, since `owner_id` in a self-`ft_withdraw` is the caller) via `self.deposit` [6](#0-5) . Net result: the internal ledger balance for that `TokenId` returns to its pre-withdraw value while the real transfer already happened, so the internal accounting for that `TokenId` now exceeds actual custody by `amount`.

### Impact Explanation
For the attacker's own maliciously-deployed `TokenId`, the Verifier's internal `token_balances` entry for that id no longer matches real custody — this is precisely the "a batch whose balance changes do not net to zero so the Verifier owes more than it custodies" Critical category. Standing alone (attacker as sole holder of a token they invented), no other party's funds move in this single step; the practical harm materializes if this inflated/duplicated balance is later used inside Defuse (e.g. as the paying leg of a signed swap/`TokenDiff` intent) to extract real assets from a counterparty who is unaware the `TokenId` is undercollateralized, or if other users are induced to hold the same `TokenId`. This is repeatable per withdraw call and across any number of attacker-deployed token contracts.

### Likelihood Explanation
No privileged role is required. Preconditions: deploy an arbitrary FT contract, deposit into Defuse via `ft_on_transfer`, then call `execute_intents`/`ft_withdraw` with `msg` set (so `is_call = true`) and a `token` contract whose `ft_transfer_call` performs the transfer then returns a short malformed body. Fully deterministic and repeatable at negligible cost (attacker only pays gas and controls all contracts involved).

### Recommendation
Do not distinguish "malformed but readable" from "unreadable" results as safely refundable. On `Ok(Err(_deserialize_err))`, treat it the same as `Err(_)` (i.e., `used = amount.0`, no refund) rather than assuming zero usage, since a self-controlled or buggy token contract can always return an ambiguous, non-conforming payload after actually moving funds. Alternatively, only trust `used` amounts from tokens with a verified/allow-listed implementation, or require an explicit “not used” proof rather than defaulting favorably to the sender on parse failure.

### Proof of Concept
`near-workspaces` sandbox test:
1. Deploy a custom FT contract `evil_token` whose `ft_transfer_call` internally moves its own ledger balance to `receiver_id` and returns raw bytes `b"bad_json"` (not valid `U128` JSON, ≤ ~44 bytes) instead of calling the standard NEP-141 `ft_on_transfer`/`ft_resolve_transfer` chain.
2. Attacker calls `evil_token.storage_deposit` + `ft_transfer_call` into `defuse` with `msg = ""` to deposit `1000` (`ft_on_transfer` credits `mt_balance_of(attacker, ft_token_id) == 1000`).
3. Attacker calls `execute_intents` with a signed `FtWithdraw{token: evil_token, receiver_id: attacker, amount: 1000, msg: Some("x")}`.
4. Assert after execution: `mt_balance_of(attacker, ft_token_id) == 1000` (refunded) **and** `evil_token` shows the attacker's external ledger balance increased by `1000` — proving the same `1000` units are simultaneously reflected in Defuse's internal ledger and externally delivered, i.e. `1000 (debited) == 1000 (external) + 1000 (refunded)`.
