### Title
Unvalidated attacker-controlled offset/length in `extractBytesArray`/`extractSigArray` causes uncaught out-of-bounds exception in `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (invoked by any address via a plain `CALL`/message call with attacker-supplied calldata, exactly like the anonymous, feature-complete ABI encoding used in `validatemultisign(address,uint256,bytes,bytes[])`) decodes its `bytes[]` signature array using `extractBytesArray`, which trusts attacker-controlled offset/length words taken directly from calldata and copies them with `Arrays.copyOfRange` without validating them against the real buffer size — the same root-cause class as CVE-2019-19977 (a length/offset value from untrusted input used to size/index a copy without bounds checking). Unlike its sibling `BatchValidateSign`, which wraps the whole decode-and-execute path in a top-level `catch (Throwable t)`, `ValidateMultiSign.execute()` performs the vulnerable array extraction *before* entering its `try` block, so any resulting `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` propagates uncaught out of the precompile.

### Finding Description
`extractBytesArray` reads attacker-controlled 256-bit words straight from calldata and uses them as array index/offset/length with no bounds checking against `words.length` or `data.length`: [1](#0-0) 

`extractBytes` then performs the unguarded copy: [2](#0-1) 

`ValidateMultiSign.execute()` calls this extraction *before* its `try` block that only wraps the permission-weight logic: [3](#0-2) 

By contrast, the sibling precompile `BatchValidateSign` wraps the entire decode+execute path (including the equivalent `extractBytesArray`/`extractSigArray` calls) in a top-level catch-all, explicitly to avoid propagating exceptions from malformed calldata: [4](#0-3) 

The `TIP-854`/`allowTvmOsaka` guard (`isValidAbiEncoding`) only checks overall calldata length is 32-byte aligned and shape-consistent with `(words - H) / I`; it does not validate that individual `bytesOffset`/`bytesLen` values used inside `extractBytesArray` stay within `words.length`/`data.length`: [5](#0-4) 

And critically, this guard is conditional on `VMConfig.allowTvmOsaka()` being active; on chains/paths where that upgrade flag is not yet enabled, or where the older `allowTvmSelfdestructRestriction()`-gated `extractBytesArray` branch is taken, there is no bounds validation at all before the copy: [6](#0-5) 

A caller can craft the `bytes[]` tail so that `words[offset+i+1]` reads past the end of `words` (an `ArrayIndexOutOfBoundsException` on the `DataWord[]` array), or so that `bytesOffset`/`bytesLen` make `extractBytes`'s `offset`/`offset+len` negative or larger than `rawData.length` (`ArrayIndexOutOfBoundsException` / `NegativeArraySizeException` from `Arrays.copyOfRange`). None of this is caught inside `ValidateMultiSign.execute()`, so the exception propagates up through `PrecompiledContract.execute(data)` into `Program.callToPrecompiledAddress`.

### Impact Explanation
An unauthenticated caller can trigger an uncaught runtime exception from within TVM precompiled-contract execution simply by sending a transaction/contract call that invokes the `ValidateMultiSign` precompile with a malformed signature-array offset/length. Because this occurs mid-execution of `Program.callToPrecompiledAddress` rather than through the VM's normal, well-typed `Program.Exception`/`BytecodeExecutionException` hierarchy, it risks bypassing the graceful "revert on bad input" handling that every other code path in this class (see `BatchValidateSign`) was explicitly hardened to guarantee. If this exception is not caught by a generic `Throwable` handler further up the transaction-execution stack, it can abort block/transaction processing non-deterministically depending on activation flags, which for a consensus-critical execution engine can manifest as a node processing halt or crash during block application — matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
High. `ValidateMultiSign` is a public precompile reachable from any signed transaction or contract call (no special privileges required), the offending values are plain calldata words fully controlled by the caller, and the vulnerable code path executes unconditionally before any exception-safety net, in contrast to the explicitly-fixed `BatchValidateSign` sibling that received a full try/catch specifically to contain malformed-calldata exceptions (see the `TIP-854` regression tests guarding `BatchValidateSign`/`ValidateMultiSign` outer-frame containment). The asymmetry between the two precompiles strongly suggests `ValidateMultiSign`'s extraction step was not given the same hardening.

### Recommendation
Move the `extractBytesArray`/`extractSigArray` calls in `ValidateMultiSign.execute()` inside a top-level `try { ... } catch (Throwable t) { return Pair.of(true, DATA_FALSE); }` block (mirroring `BatchValidateSign.execute()`), and/or make `isValidAbiEncoding`-style bounds validation of `bytesOffset`/`bytesLen` against `words.length`/`rawData.length` unconditional (not gated behind `allowTvmOsaka()`/`allowTvmSelfdestructRestriction()`), so malformed calldata always yields a graceful `(true, DATA_FALSE)` result instead of an uncaught exception.

### Proof of Concept
1. Construct calldata for `validatemultisign(address,uint256,bytes,bytes[])` such that the ABI head is well-formed (address, permissionId, `bytes data` offset, and the `bytes[]` array offset word `words[3]`), but the `bytes[]` array's length word `len` and the per-element offset word `words[offset+i+1]` are chosen so that `bytesOffset = words[offset+i+1].intValueSafe() / WORD_SIZE` combined with `bytesLen = words[offset+bytesOffset+1].intValueSafe()` makes `(bytesOffset+offset+2)*WORD_SIZE + bytesLen` exceed `rawData.length`, or makes `offset+bytesOffset+1 >= words.length`.
2. Send this calldata as a `CALL` to the `ValidateMultiSign` precompile address from any account (deployer, contract, or externally-owned account), either directly or via a wrapper smart contract, with `VMConfig.allowTvmOsaka()`/`allowTvmSelfdestructRestriction()` not both enabled (or via the `allowTvmSelfdestructRestriction` branch which still lacks bounds checks on `bytesOffset`/`bytesLen` against `rawData.length`).
3. Observe that `extractBytesArray`/`extractBytes` throws `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` before the `try` block in `ValidateMultiSign.execute()`, propagating out of the precompile call unlike the equivalent `BatchValidateSign` path which is fully guarded.

Note: I could not fully verify, within the available index, exactly how far up the transaction-execution stack (e.g., in `TransactionTrace`/`Runtime`) this specific uncaught exception type is ultimately caught versus allowed to abort processing; confirming the end-to-end consensus impact (transaction revert vs. node-level halt) would require tracing the full call chain in a live/dynamic environment, which is outside what the indexed code excerpts can conclusively show.

    if (offset > words.length - 1) {

    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];

          bytesLen);
    }
    return bytesArray;
  }
