### Title
Cross-StackerDB chunk replay due to signature not binding the target contract - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` — the message that a signer's private key signs to authorize a StackerDB chunk write — commits only to `slot_id`, `slot_version`, and `data_hash`. It never commits to the StackerDB's `QualifiedContractIdentifier` (the "which database" the write is destined for). Because several sibling StackerDB contracts (e.g. the per-message-type `signers-{set}-{msg_id}` contracts used for `BlockResponse`, `StateMachineUpdate`, and `BlockPreCommit`) assign the *same* slot ordering to the *same* signer set, a chunk that is validly signed and broadcast for one message-type database can be replayed verbatim into a different message-type database and will pass all server-side checks. This is the direct analog of the copyparty filekey/dirkey confusion: an authorization token (here, a signature) that is valid in one narrow context (a specific slot in a specific StackerDB) is silently accepted in a different context it was never scoped for.

### Finding Description
`SlotMetadata::auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`SlotMetadata::verify()` recovers the pubkey from that digest and compares its hash160 to the expected slot owner, with no reference to which StackerDB (contract) the chunk claims to belong to: [2](#0-1) 

Both the HTTP-write path (`try_replace_chunk`) and the P2P validation path (`validate_received_chunk`) perform their signer check purely against the per-contract slot owner without folding the contract identifier into the signed material: [3](#0-2) [4](#0-3) 

The HTTP endpoint takes the destination contract straight from the URL path and independently parses the chunk body — the contract never participates in the signature check: [5](#0-4) 

Crucially, sibling StackerDB contracts reuse the exact same signer ordering. `signers-0-1` (BlockResponse), `signers-0-2` (StateMachineUpdate), and `signers-0-3` (BlockPreCommit) are all separate `QualifiedContractIdentifier`s that each delegate to `.signers stackerdb-get-signer-slots-page u0`, producing an identical (signer → slot_id) mapping for a given reward-cycle set: [6](#0-5) [7](#0-6) [8](#0-7) 

The message-type/contract mapping used for these StackerDBs is defined here, confirming multiple sibling databases share a signer set: [9](#0-8) 

Because the signature never binds `slot_id`+`slot_version`+`data_hash` to a specific contract, and slot ownership is identical across sibling contracts, a `StackerDBChunkData` object (slot_id, slot_version, sig, data) that was validly signed and broadcast for `signers-0-1` also passes signature verification unmodified when submitted to `signers-0-2` or `signers-0-3` for the same slot, as long as the target database's stored slot version is behind the replayed one. This equality break — "signed for database A" is silently treated as "valid for database B" — mirrors the copyparty bug's core flaw of an access token not being scoped to the resource it grants access to.

### Impact Explanation
Since StackerDB chunks are broadcast over the p2p network and are, by design, public once relayed (unsolicited `StackerDBPushChunk` and inventory-driven downloads), any peer that observes a legitimately signed chunk for one message-type StackerDB can resubmit those exact bytes — with no signer private key needed — to a different message-type StackerDB (or via the public HTTP `POST /v2/stackerdb/:principal/:contract/chunks` endpoint), causing the node to accept and store/propagate it as if it were content the signer authored for that other message type. This is a form of unauthenticated forged-context propagation onto StackerDB state: an attacker did not need to forge a signature, but they can still get a node to store/relay data under a context (contract/message type) the original signer never authorized, purely by relaying already-public bytes into the wrong "channel." Downstream consumers of that StackerDB (e.g. miner or signer coordination logic which trusts a chunk to be of a well-defined message type based solely on the contract it was fetched from) would receive forged-context data as if it were canonical for that message type.

### Likelihood Explanation
Exploitation requires no privileged access, no node secret, and no other party's private key — only the ability to observe a signed StackerDB chunk that has already propagated on the network (a routine, public event), and to resubmit it (unmodified) to a sibling StackerDB contract whose slot version has not yet caught up. Both preconditions are ordinary in the Nakamoto signer StackerDB deployment where `signers-{set}-1/2/3` contracts co-exist with identical slot layouts.

### Recommendation
Include the target `QualifiedContractIdentifier` (or an equivalent contract/message-type domain separator) in `SlotMetadata::auth_digest()` so that a signature is only valid for the specific StackerDB it was created for. This should be a coordinated protocol change (digest format bump) since it changes what bytes get signed.

### Proof of Concept
1. Observe (via p2p inventory sync or by running an unprivileged node) a validly-signed `StackerDBChunkData { slot_id, slot_version, sig, data }` broadcast for contract `signers-0-1` (BlockResponse) — its signer occupies slot `S`.
2. Confirm, via `.signers` contract state, that the same signer occupies slot `S` in contract `signers-0-2` (StateMachineUpdate) — true by construction, since both contracts read the identical `stackerdb-get-signer-slots-page u0`.
3. Craft an HTTP `POST /v2/stackerdb/<signers-0-2 principal>/<signers-0-2 contract>/chunks` (or an unsolicited P2P `StackerDBPushChunk` naming `signers-0-2`) using the identical `StackerDBChunkData` bytes captured in step 1, provided `slot_version` exceeds `signers-0-2`'s currently stored version for slot `S`.
4. `try_replace_chunk`/`validate_received_chunk` will accept it: the size check passes, `slot_desc.verify(&slot_validation.signer)` succeeds (same signer, same slot id, same digest bytes), and the version-freshness check succeeds against `signers-0-2`'s independently-tracked version counter — storing/propagating data signed for one message type into a different message type's StackerDB.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)

        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
