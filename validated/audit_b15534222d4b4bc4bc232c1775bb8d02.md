### Title
Maker receives zero payment when order fully consumed due to rounding in `matchSingleOrder` "taker == maker" branch - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
In `MarketSellAssetActuator.matchSingleOrder`, when a taker order exactly matches a maker's remaining sell quantity, the maker's payment (`makerBuyTokenQuantityReceive`) is computed via integer division (`MarketUtils.multiplyAndDivide`) without any check that the result is non-zero, unlike the sibling "taker > maker" branch which explicitly guards against a zero result.

### Finding Description
`matchSingleOrder` handles three cases depending on how the taker's desired buy quantity compares to the maker's remaining sell quantity: `taker == maker`, `taker < maker`, and `taker > maker`.

In the `taker == maker` branch:
```java
makerBuyTokenQuantityReceive = MarketUtils
    .multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity,
        this.disableJavaLangMath());
takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain();

long takerSellTokenLeft =
    takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive;
takerOrderCapsule.setSellTokenQuantityRemain(takerSellTokenLeft);
makerOrderCapsule.setSellTokenQuantityRemain(0);
``` [1](#0-0) 

This unconditionally sets the maker's `sellTokenQuantityRemain` to 0 (fully consuming the maker's order) and transfers `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` to the taker via `addTrxOrToken`, while crediting the maker only with `makerBuyTokenQuantityReceive`, a value obtained from integer division that can round down to 0 for small remaining quantities and adverse maker/buy/sell ratios.

By contrast, the `taker > maker` branch, which uses the very same `multiplyAndDivide` calculation for `makerBuyTokenQuantityReceive`, explicitly checks:
```java
if (makerBuyTokenQuantityReceive == 0) {
  // the quantity is too small, return the remain of sellToken to maker
  makerOrderCapsule.setSellTokenQuantityReturn();
  returnSellTokenRemain(makerOrderCapsule);
  return;
}
``` [2](#0-1) 

The comment inline even states an informal (and, given the missing guard in the equal-case branch, incomplete) assumption that this situation "would not happen here" for the maker-buys-fewer case, but no equivalent reasoning or safeguard exists for the `taker == maker` path, where the same rounding-to-zero condition can occur with `makerBuyTokenQuantityReceive == 0`.

### Impact Explanation
When `makerBuyTokenQuantityReceive` rounds to `0` in the `taker == maker` branch, the maker's remaining sell tokens (already deducted from the maker's account balance at order-creation time via `transferBalanceOrToken`) are transferred in full to the taker (`addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, ...)`), while the maker's account is credited with zero tokens in return (`addTrxOrToken(makerOrderCapsule, 0)`), and the maker's order is marked `INACTIVE`/removed from the order book with no recovery path. This is a permanent, unrecoverable loss of value for the maker and an unbacked gain for the taker — the taker effectively receives assets for free — reachable by any account that places a `MarketSellAssetContract` transaction (an ordinary signed transaction, not requiring special privilege).

### Likelihood Explanation
Triggering this requires crafting a taker order whose remaining sell quantity, when converted through the maker's price ratio (`makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity`), rounds down to zero — i.e., the maker's remaining sell quantity is small relative to `makerSellQuantity/makerBuyQuantity`. Since order quantities and remaining balances are attacker/market-participant controlled (via prior partial fills and subsequent order placement), an attacker acting as taker can deliberately construct matching maker orders with small remaining balances and adverse ratios to reliably hit this rounding condition, making exploitation plausible without any privileged access.

### Recommendation
Add the same zero-result guard used in the `taker > maker` branch to the `taker == maker` branch: if `makerBuyTokenQuantityReceive == 0`, return the maker's remaining sell tokens via `returnSellTokenRemain`/`setSellTokenQuantityReturn` instead of consuming the maker's order and transferring the tokens to the taker for free. More generally, consider enforcing a minimum tradable quantity or rounding in the maker's favor to prevent zero-payment settlements.

### Proof of Concept
Exact reproduction requires selecting maker/taker quantities such that `makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity == 0` while `takerBuyTokenQuantityRemain == makerSellRemainQuantity` (entering the `taker == maker` branch) — e.g., a maker order with `makerSellQuantity` much larger than `makerBuyQuantity` and a small `makerSellRemainQuantity` left after prior partial fills, matched by a taker order sized to exactly consume that remainder. Full concrete numeric reproduction was not independently executed in this analysis session (this would require running `MarketUtils.multiplyAndDivide` and the full order-matching flow, which could not be verified here since its implementation body was not retrieved before the tool budget was exhausted); the code-path analysis above is based on direct reading of `matchSingleOrder` and comparison against the guarded sibling branch.
