### Title
Missing receiver address validation in `FreezeBalanceProcessor.validate` can permanently freeze delegated TRX to an unusable address - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java`)

### Summary
This is the java-tron analog of the Aave `claimToTreasury` bug: a fund-moving code path accepts a destination address without validating that it is a well-formed/spendable address. In java-tron, the TVM native "freeze resource / delegate to receiver" flow deducts the caller's TRX balance and delegates the resulting resource (and the underlying frozen TRX) to a `receiverAddress` supplied directly by the smart-contract caller, but the validation routine never checks that this address is well-formed, unlike every sibling actuator that performs the same kind of delegation.

### Finding Description
`FreezeBalanceProcessor.validate()` only compares `receiverAddress` to `ownerAddress` for equality before treating the operation as a delegation: [1](#0-0) 

It never calls `DecodeUtil.addressValid(receiverAddress)`. Every comparable code path that performs the same kind of resource delegation does perform this check, e.g.: [2](#0-1) [3](#0-2) [4](#0-3) 

Because the check is missing, `execute()` proceeds to create/delegate resource to whatever byte array was supplied as `receiverAddress` — including a malformed or all-zero value that no private key can ever control — while still deducting the frozen TRX balance from the caller's account: [5](#0-4) 

This mirrors the Aave bug precisely: a value-transfer/resource-delegation function accepts a destination without confirming it is not a "burn"-equivalent address, so funds routed there become effectively unrecoverable.

### Impact Explanation
If reachable from a TVM-executed transaction (the class is only referenced from `Program.java`, i.e. the VM opcode/native-contract layer, and is otherwise unused by the higher-level actuator dispatch which is guarded by `supportUnfreezeDelay()`), a caller (an unprivileged contract deployer/caller) could freeze TRX and delegate it to a receiver address that fails the format checks enforced everywhere else in the codebase. Because `UnfreezeBalanceActuator` re-validates `receiverAddress` with `DecodeUtil.addressValid` and rebuilds the exact `DelegatedResourceCapsule` key from that receiver, resource/TRX delegated to a malformed/unspendable address could become unreclaimable, resulting in a permanent freeze of the caller's own TRX balance (funds locked but functionally unbacked/unusable), matching the "permanent freezing of funds" impact class.

### Likelihood Explanation
Likelihood depends on whether this old-freeze (v1) native-contract code path remains reachable in the current build (freeze v1 is largely superseded by `FreezeBalanceV2Actuator`/`UnfreezeBalanceV2Processor`, which follow the `supportUnfreezeDelay()` gate). I was not able to conclusively verify, within the available index, the exact TVM opcode/`Program.java` call site that constructs `FreezeBalanceParam` and invokes `FreezeBalanceProcessor`, so exploitability should be confirmed by inspecting `Program.java`'s freeze-related method and `OperationRegistry`/`Op.java` to see whether this legacy path is still exposed to arbitrary contract callers when `supportUnfreezeDelay()` is disabled.

### Recommendation
Add `DecodeUtil.addressValid(receiverAddress)` validation in `FreezeBalanceProcessor.validate()` before allowing delegation, consistent with `DelegateResourceProcessor`, `UnDelegateResourceProcessor`, and the corresponding actuators.

### Proof of Concept
Conceptual PoC (pending confirmation of the exact TVM entry point):
1. Deploy a contract that invokes the legacy TVM "freeze balance" native contract, setting `receiverAddress` to a byte array that is not `ownerAddress` but is otherwise malformed/zero-filled (e.g., all-zero 21-byte value).
2. `FreezeBalanceProcessor.validate()` accepts it because it only checks `FastByteComparisons.isEqual(ownerAddress, receiverAddress)`.
3. `execute()` deducts the frozen TRX from the caller and delegates the resource to the unusable receiver address via `delegateResource(...)`.
4. Later, attempting to reclaim/unfreeze via the standard path (`UnfreezeBalanceActuator`, which enforces `DecodeUtil.addressValid(receiverAddress)` and exact key matching) may be unable to construct or accept the transaction cleanly for this receiver, leaving the frozen TRX permanently locked.

Because I could not fully trace the TVM opcode dispatch to `FreezeBalanceProcessor` within the indexed files, this PoC and the reachability claim should be verified with a full checkout of `Program.java`/`OperationRegistry.java` before treating this as confirmed-exploitable.
