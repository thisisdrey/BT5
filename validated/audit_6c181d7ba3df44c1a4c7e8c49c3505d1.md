### Title
Missing hash verification of fetched `Attachment` content against the requested `content_hash` permanently orphans legitimate BNS attachment instances - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts the `Attachment` payload returned by a peer for a `GetAttachment` request and inserts it into `self.attachments` without ever checking that the received content's hash matches the `content_hash` that was actually requested. Downstream, `AttachmentsBatch::resolve_attachment` is invoked using the hash of the (possibly forged/garbage) content the attacker returned rather than the hash that was requested, so a malicious peer can prevent a targeted, on-chain-committed `AttachmentInstance` from ever being resolved.

### Finding Description
When the downloader fetches attachment content it does so via `AttachmentRequest { content_hash, .. }` built from `attachments_instances` (download.rs:404-478, particularly `content_hash: content_hash.clone()` at line 469). The response is processed in `extend_with_attachments`: [1](#0-0) 

This code decodes the HTTP response into an `Attachment` and inserts it into `self.attachments` (`self.attachments.insert(response.attachment)` at line 548) with **no comparison** between `request.content_hash` (what was asked for) and the hash of the bytes actually returned by the peer.

Later, in `AttachmentsDownloader::run`, the `Done` state drains `context.attachments` and calls `attachment.hash()` — the hash of whatever bytes the peer sent — to look up matching instances and to resolve the batch entry: [2](#0-1) 

Because the hash used for resolution is derived from the (potentially attacker-controlled, mismatched) content rather than the originally requested `content_hash`, a peer that:
1. is selected as one of the victim's outbound sync peers (achievable by any unprivileged remote peer that establishes a normal P2P connection),
2. answers the attachments-inventory request claiming to have the desired page/bit set (so it gets picked as a source in `get_prioritized_attachments_requests`, download.rs:404-478), and
3. answers the subsequent `GetAttachment` request with arbitrary bytes whose hash does not equal the requested `content_hash`,

causes `attachment.hash()` to differ from every key tracked in `attachments_batch.attachments_instances` for that batch. `resolve_attachment` therefore never removes that entry, `has_fully_succeed()` stays false, and the loop at: [3](#0-2) 

re-enqueues the batch for retry, and after `retry_count` exceeds `connection_options.max_attachment_retry_count` the batch is silently dropped. The specific `AttachmentInstance.content_hash` (a legitimately, on-chain-committed BNS zonefile hash) is never resolved at this node.

No other guard intervenes: `check_attachment_instances` (lines 227-286) only classifies instances as known/unknown prior to fetch and does not re-validate fetched content; nothing between `decode_atlas_get_attachment()` and `attachments.insert(...)` performs a `Hash160`/`MerkleHashFunc` equality check against the request's `content_hash`.

### Impact Explanation
A single malicious (or malfunctioning) outbound peer can indefinitely deny resolution of a specific, valid, on-chain-committed BNS zonefile attachment at the victim node by repeatedly serving mismatched content for that hash whenever it is selected as a source. This is a targeted, repeatable availability/correctness failure for Atlas/BNS name resolution — the victim node will never populate its `AtlasDB` with that attachment, so RPC/API consumers relying on the node for that name's zonefile will get no data, even though the data is available elsewhere on the network. This matches the "attachment/BNS mismatch" High-impact category (serving no resolution where canonical on-chain state committed to a resolvable hash).

### Likelihood Explanation
No privileged state is needed: the attacker only needs to (a) run their own peer that establishes an ordinary outbound/inbound P2P connection with the victim (a normal, unprivileged capability) and (b) respond to the victim's `GetAttachmentsInv`/`GetAttachment` HTTP-over-P2P requests with a false inventory bit and garbage content. Reliability-report bookkeeping (`bump_successful_requests`/`bump_failed_requests`) does not distinguish "wrong content" from success since the code treats any successfully decoded response as `succeeded`, so the malicious peer isn't automatically penalized for serving wrong bytes. The attack is cheap (a handful of crafted responses) and repeatable across every retry cycle, up to `max_attachment_retry_count`.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (download.rs:530-558), after decoding the response, compute the hash of `response.attachment` and compare it to `request.content_hash` before inserting into `self.attachments`; if they don't match, treat the peer response as failed (`report.bump_failed_requests()`), and optionally mark the peer as faulty/deregister the event, rather than silently dropping the (correct) request. This keeps the request live so it can be retried against a peer that returns valid content, rather than exhausting the shared batch retry budget on a single tainted content_hash.

### Proof of Concept
Rust test plan in `stackslib/src/net/atlas/tests.rs`:
1. Build an `AttachmentsBatch` tracking one `AttachmentInstance` with a known `content_hash = H1`.
2. Construct an `AttachmentsBatchStateContext` wrapping that batch, and directly call `extend_with_attachments` with a `BatchedRequestsResult` where `succeeded` maps an `AttachmentRequest{content_hash: H1, ..}` to a decoded `GetAttachmentResponse` whose `attachment.content` bytes hash to `H2 != H1`.
3. Assert `context.attachments` now contains the attacker's `Attachment` (proving no validation occurred).
4. Simulate `AttachmentsDownloader::run`'s `Done` handling: call `attachments_batch.resolve_attachment(&attachment.hash())` with the attacker's `H2`, and assert `attachments_batch.has_fully_succeed()` is still `false` (the legitimate `H1` entry remains unresolved).
5. Loop the re-enqueue logic (`bump_retry_count`) until `retry_count > max_attachment_retry_count`, and assert the batch is dropped (not pushed back into `priority_queue`), confirming permanent denial of resolution for `H1`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
