## Title
`WAIT_FOR_TENURE_END_BLOCK_TIMEOUT` constant is declared but never enforced, allowing a stalling peer to indefinitely occupy a tenure download slot - (File: `stackslib/src/net/download/nakamoto/tenure_downloader.rs`)

## Summary
`NakamotoTenureDownloadState::GetTenureStartBlock`/`GetTenureEndBlock` embed a `start_request_time` timestamp, and `WAIT_FOR_TENURE_END_BLOCK_TIMEOUT` is defined at line 52, but a grep across the entire repository shows this constant is referenced exactly once — its own declaration — and is never compared against `start_request_time` anywhere in `try_accept_tenure_start_block`, `try_accept_tenure_end_block`, or any other function in this file or elsewhere in the codebase. `handle_next_download_response` only uses `start_request_time` for a `debug!` log of elapsed milliseconds, not for any expiry decision.

## Finding Description
The state machine stores `start_request_time` in `GetTenureStartBlock(id, start_request_time)` and `GetTenureEndBlock(id, start_request_time)` [1](#0-0) , and defines `WAIT_FOR_TENURE_END_BLOCK_TIMEOUT` [2](#0-1) . However, `try_accept_tenure_start_block` only checks the block ID and signer signature, never any elapsed-time bound [3](#0-2) , and `try_accept_tenure_end_block` similarly only checks state, block ID, signature, and tenure-change linkage, with no time check [4](#0-3) . The only place `start_request_time` is read in the response handler is purely for logging: `get_epoch_time_ms().saturating_sub(*start_request_time)` inside `debug!` calls in `handle_next_download_response` [5](#0-4) . A repo-wide search confirms `WAIT_FOR_TENURE_END_BLOCK_TIMEOUT` is never used in a comparison anywhere in the codebase, so the constant is dead/decorative.

However, this file alone does not implement any timeout-based eviction mechanism at all — timing out a stalled downloader is a concern for whatever driver polls/holds `NakamotoTenureDownloader` instances (e.g., `NakamotoTenureDownloaderSet` or the outer download state machine), not for `tenure_downloader.rs` itself. This file's job is solely to validate and accept blocks once given a response; it never claims to expire requests on its own. Enforcement of `WAIT_FOR_TENURE_END_BLOCK_TIMEOUT` would need to live in the code that drives `send_next_download_request`/`handle_next_download_response`/`is_dead_or_broken`, which is out of scope for this file per the question's own framing, and I could not verify from this file alone whether such enforcement exists or is missing elsewhere (that would require inspecting `download/nakamoto/mod.rs`, `tenure_downloader_set.rs`, or `tenure_downloader_unconfirmed.rs`, which are separate files).

## Impact Explanation
Within the boundaries of this single file, no expiry check fires under any wire-controlled timing behavior — a slow-responding peer is neither rejected nor dropped by `try_accept_tenure_start_block`/`try_accept_tenure_end_block` based on elapsed time. But the actual "does this cause an indefinite stall" question depends on caller-side logic (peer liveness/dead-connection detection via `neighbor_rpc.is_dead_or_broken`, request timeouts at the HTTP/neighbor-RPC layer, or slot-management logic in `NakamotoTenureDownloaderSet`) that is not implemented in `tenure_downloader.rs` and thus cannot be confirmed or refuted as either present or absent from this file's contents alone. The severity claim (High: single-peer indefinite occupation of a confirmed-tenure download slot) requires proof that no other layer in the download pipeline enforces peer liveness/staleness, which is out of the scope of this file review.

## Likelihood Explanation
The attacker (any peer serving tenure-start/end blocks over HTTP) can trivially delay its HTTP response beyond any threshold at negligible cost and fully remotely. Whether this results in real indefinite starvation depends entirely on code outside `tenure_downloader.rs` (e.g., `neighbor_rpc` inflight/dead-connection timeout logic, which this file does call via `neighbor_rpc.is_dead_or_broken` and `neighbor_rpc.has_inflight`) [6](#0-5) . That mechanism is a candidate enforcement point that is out of scope here, so within this file's boundaries I can only confirm the dead constant, not the end-to-end exploitability.

## Recommendation
If `WAIT_FOR_TENURE_END_BLOCK_TIMEOUT` is meant to bound how long a `NakamotoTenureDownloader` instance waits in `GetTenureStartBlock`/`GetTenureEndBlock` before being abandoned, add an explicit check (e.g., in `send_next_download_request` or a new `is_timed_out()` method) comparing `get_epoch_time_ms().saturating_sub(start_request_time)` against `WAIT_FOR_TENURE_END_BLOCK_TIMEOUT`, and have the caller (`NakamotoTenureDownloaderSet`) evict/replace stalled downloaders and mark the offending peer dead via `neighbor_rpc.add_dead`. If timeout enforcement is intentionally delegated to `neighbor_rpc`'s connection-level dead/broken detection, remove the unused constant from this file or document that delegation to avoid the misleading appearance of an unenforced safety mechanism.
