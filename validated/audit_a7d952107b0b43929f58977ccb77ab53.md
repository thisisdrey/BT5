### Title
Contract-controlled `refund_to` lets a malicious cross-contract call burn a caller's attached deposit instead of returning it - ([File: runtime/runtime/src/receipt_manager.rs])

### Summary
The Sherlock report describes a receiver (Lender) that can unilaterally block an inbound token transfer (`repay()`), forcing the transaction to always fail and causing the *other* party's funds to be permanently forfeited. The closest reachable analog in nearcore is the `refund_to` mechanism: any contract that creates an outgoing action receipt via the promise API can redirect that receipt's *deposit refund* to an arbitrary account with `set_refund_to` [1](#0-0) . If that chosen refund destination cannot receive the funds, the refund itself fails and, per protocol, the refunded amount is **burned** rather than returned to the original depositor [2](#0-1) .

### Finding Description
When a receipt fails, its attached deposit is normally returned to `predecessor_id` via a deposit-refund receipt, but a contract can override the destination for its own outgoing receipts using `refund_to` [3](#0-2) . `refund_to` is validated only for account-id well-formedness (`AccountId::validate`), not for existence or reachability [4](#0-3) .

Refund receipts are special-cased in `apply_action_receipt`: they are free and, if the receipt's action fails, the deposit is not retried and is burned into `other_burnt_amount` instead [5](#0-4) . Crucially, refunds are explicitly barred from creating an implicit account, even though a normal Transfer to a non-existent implicit account would succeed and create it: "Implicit account creation is allowed only when the action is the sole action and not a refund" [6](#0-5) , and `check_transfer_to_nonexisting_account` explicitly documents this: "Refunds don't automatically create accounts, because refunds are free and we don't want some type of abuse" [7](#0-6) .

Putting these together: a malicious/faulty contract that is called with an attached deposit (from an honest user, via a cross-contract promise) can call `promise_batch_action_set_refund_to` and point the refund at a **non-existent implicit account id** (e.g., a random 64-hex/`0x…` string it does not control and never intends to fund). If the downstream promise fails (which the malicious contract fully controls, e.g. by making the receiver reject or by attaching insufficient gas), the resulting deposit-refund receipt targets the non-existent account, `check_account_existence`/`check_transfer_to_nonexisting_account` rejects it (refunds cannot create accounts), the refund action itself fails, and the deposit is **burned** rather than credited back to anyone — including the original depositor who never had a say in choosing `refund_to`.

### Impact Explanation
This is a permanent, protocol-level loss of the depositor's attached NEAR balance, triggered entirely by an unprivileged contract's choice of `refund_to`, with no way for the depositor to prevent or recover the funds. This matches "permanent freezing/loss of funds," one of the accepted valid impact categories, and is structurally the same failure pattern as the Cooler bug: the party who does not control the destination of the funds movement (the depositor here, the borrower/owner in Cooler) is harmed because a downstream, adversarial party (the callee contract here, the Lender in Cooler) chose an unreachable/rejecting recipient for that fund movement.

### Likelihood Explanation
Reaching this requires an ordinary user to make a cross-contract call with an attached deposit to a contract that is malicious or compromised; that contract must use the `promise_batch_action_set_refund_to` host function (already implemented and tested, e.g. `test_refund_to` [8](#0-7) ) and must be able to make its own downstream promise fail on demand — both are fully within a contract author's control. No validator, relayer, or privileged role is needed; only ordinary signed transactions and a deployed WASM contract, satisfying the "ordinary client's transaction / deployed contract" scoping.

### Recommendation
When a deposit-refund receipt fails because its `refund_to`/`predecessor_id` target cannot receive the transfer (e.g., non-existent implicit account), do not burn the deposit. Instead, fall back to refunding the immediate `predecessor_id` of the failed receipt (the account that actually attached the deposit), or retry via a `Transfer` action variant that is permitted to create the implicit account for refunds. At minimum, `validate_action_receipt`/`set_refund_to` should reject a `refund_to` account id that does not correspond to an existing account (or is a non-implicit malformed target) at the time the redirect is set, closing the "burn on purpose" griefing vector.

### Proof of Concept
1. User `A` calls `ContractM::relay(target)` with an attached deposit `D` (e.g. 5 NEAR).
2. `ContractM` (malicious), in its execution, creates an outgoing receipt to some far-away receiver `target2` with `attached_deposit = D` via `promise_batch_action_transfer`/`function_call`, then calls `promise_batch_action_set_refund_to(promise_index, "ffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff")` — a syntactically valid but never-created NEAR-implicit account id (this passes `AccountId::validate` per `verifier.rs:602-606`).
3. `ContractM` deliberately makes the downstream receipt fail (e.g., calls a non-existent method on `target2`, or attaches insufficient gas).
4. Runtime generates a deposit-refund receipt (`Receipt::new_balance_refund`) targeting the bogus implicit account id [9](#0-8) .
5. That refund's single `Transfer` action hits `check_account_existence` → `check_transfer_to_nonexisting_account`, which rejects implicit-account creation for refunds [7](#0-6) , so the refund action fails.
6. Per the system-predecessor branch in `apply_action_receipt`, the failed refund's deposit `D` is added to `other_burnt_amount` and permanently destroyed [5](#0-4) .
7. User `A`'s `D` NEAR is gone; `ContractM` incurred no loss and needed no privileges beyond deploying an ordinary contract.

**Uncertainty note:** I could not directly inspect the `promise_batch_action_set_refund_to` host-function implementation body (only its call sites/tests were indexed) to confirm there is no additional existence check performed at the time `refund_to` is set versus only at receipt-validation time; this should be verified by reading `runtime/near-vm-runner/src/logic/logic.rs` and `runtime/runtime/src/verifier.rs` (`validate_action_receipt`, line 615 area) in full before treating this as conclusively exploitable. If a Devin session is desired to confirm and fix this, it would need direct repository access to trace the complete host-function → verifier → runtime call chain and write a reproduction test.

fn check_transfer_to_nonexisting_account(
    config: &RuntimeConfig,
    account_id: &AccountId,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    if implicit_account_creation_eligible
        && account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts)
    {
        // OK. It's implicit account creation.
        // Notes:
        // - Transfer action has to be the only action in the transaction to avoid
        // abuse by hijacking this account with other public keys or contracts.
        // - Refunds don't automatically create accounts, because refunds are free and
        // we don't want some type of abuse.
        // - Account deletion with beneficiary creates a refund, so it'll not create a
        // new account.
        Ok(())
    } else {
        Err(ActionErrorKind::AccountDoesNotExist { account_id: account_id.clone() }.into())
    }
}

// redirect the balance refund using `promise_refund_to`
#[test]
fn test_refund_to() {
    let group = RuntimeGroup::new(4, 4, near_test_contracts::rs_contract());

    let signer_sender = group.signers[0].clone();
    let signer_receiver = group.signers[1].clone();
    let deposit = Balance::from_yoctonear(1000);

    let data = serde_json::json!([
        {
            "batch_create": {
                "account_id": "near_2",
            },
            "id": 0
        },
        {
            "action_function_call": {
                "promise_index": 0,
                "method_name": "non_existing_function",
                "arguments": [],
                "amount": deposit,
                "gas": GAS_2,
            },
            "id": 0
        },
        {
            "set_refund_to": {
                "promise_index": 0,
                "beneficiary_id": "near_3"
            }, "id": 0
        }
    ]);

    let signed_transaction = SignedTransaction::from_actions(
        1,
        signer_sender.get_account_id(),
        signer_receiver.get_account_id(),
        &signer_sender,
        vec![Action::FunctionCall(Box::new(FunctionCallAction {
            method_name: "call_promise".to_string(),
            args: serde_json::to_vec(&data).unwrap(),
            gas: GAS_1,
            deposit,
        }))],
        CryptoHash::default(),
    );

    let handles = RuntimeGroup::start_runtimes(group.clone(), vec![signed_transaction.clone()]);
    for h in handles {
        h.join().unwrap();
    }

    println!("{:?}", group.executed_receipts);

    use near_primitives::transaction::*;
    let [r0] = &*assert_receipts!(group, signed_transaction) else {
        panic!("Incorrect number of produced receipts")
    };

    let receipts = &*assert_receipts!(group, "near_0" => r0 @ "near_1",
        ReceiptEnum::Action(ActionReceipt{actions, ..}) | ReceiptEnum::ActionV2(ActionReceiptV2{actions, ..}),
        {},
        actions,
        a0, Action::FunctionCall(function_call_action), {
            assert_eq!(function_call_action.gas, GAS_1);
            assert_eq!(function_call_action.deposit, deposit);
            assert_eq!(function_call_action.method_name, "call_promise");
        }
    );
    let [r1, refunds @ ..] = &receipts else { panic!("Incorrect number of produced receipts") };
    group.assert_gas_refunds(&refunds[..]);

    let receipts = &*assert_receipts!(group, "near_1" => r1 @ "near_2",
        ReceiptEnum::Action(ActionReceipt{actions, ..}) | ReceiptEnum::ActionV2(ActionReceiptV2{actions, ..}),
        {},
        actions,
        a0, Action::FunctionCall(function_call_action), {
            assert_eq!(function_call_action.gas, GAS_2);
            assert_eq!(function_call_action.deposit, deposit);
            assert_eq!(function_call_action.method_name, "non_existing_function");
        }
    );
    // The redirected deposit refund (to `near_3`) is emitted first; any trailing receipt is the
    // gas refund for executing this receipt.
    let [deposit_refund, refunds @ ..] = &receipts else {
        panic!("Incorrect number of produced receipts")
    };
    group.assert_gas_refunds(&refunds[..]);

    // This is the redirected refund
    assert_refund!(group, deposit_refund @ "near_3");
}
