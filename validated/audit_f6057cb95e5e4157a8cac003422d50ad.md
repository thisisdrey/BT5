### Title
Unbounded attacker-controlled array length in ValidateMultiSign precompile can throw uncaught `OutOfMemoryError`/`NegativeArraySizeException` and crash node execution - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract, reachable from any smart-contract call, decodes an attacker-supplied ABI array length and allocates a Java array sized directly from that untrusted value — without an upper bound — in the legacy (pre-`allowTvmSelfdestructRestriction`) code path. This mirrors the CVE-2017-12186 bug class: a length field taken from untrusted network input is used to size a buffer/array without validation, leading to a crash.

### Finding Description
In `ValidateMultiSign.execute()`, the number of signatures (`len`) is read straight from calldata via `words[offset].intValueSafe()` and only bounds-checked (`sigArraySize > MAX_SIZE`) when `VMConfig.allowTvmSelfdestructRestriction()` is true: [1](#0-0) 

When that fork flag is not active, execution instead falls straight to `extractBytesArray`, which allocates `byte[len][]` with `len` fully attacker-controlled and unchecked: [2](#0-1) 

If `len` is crafted to be very large, `new byte[len][]` can throw `OutOfMemoryError`; if the decoded 32-byte word yields a negative `int` (via `intValueSafe()`'s truncation), `new byte[len][]` throws `NegativeArraySizeException`. Both are thrown *before* the `try { ... } catch (Throwable t)` block that wraps only the later signature-recovery loop: [3](#0-2) 

so neither is caught inside `execute()` itself. This is the same "length taken from attacker input, used to size a buffer/array, without an upper-bound validation" pattern the CVE describes for the X-Resource extension.

### Impact Explanation
An uncaught `OutOfMemoryError`/`NegativeArraySizeException` during TVM execution of a precompiled contract, triggered by a single smart-contract call, can propagate up through contract execution and — depending on how far up the call stack it is ultimately caught — disrupt transaction/block processing on the node executing it, i.e., a node crash/DoS reachable from an unprivileged contract caller. This satisfies the "node crash or halt" impact bar.

### Likelihood Explanation
Exploitability is conditional: the vulnerable branch is only reached when `VMConfig.allowTvmSelfdestructRestriction()` returns `false`. I was not able to verify from the indexed code whether this hard-fork flag is enabled by default on the current mainnet/production configuration; if it has already activated, the safer `extractSigArray` path (with the `MAX_SIZE` guard) is used instead and this issue is not reachable. This uncertainty should be verified against the live chain parameters/hard-fork activation status before treating this as actively exploitable.

### Recommendation
Move the `sigArraySize > MAX_SIZE` bound check outside the `allowTvmSelfdestructRestriction()` gate so it always applies, and add the same upper-bound validation inside `extractBytesArray` (and any other precompile helper that sizes arrays from calldata-derived lengths) regardless of fork status, so an oversized or negative length is rejected before array allocation rather than relying on hard-fork configuration state.

### Proof of Concept
Deploy a contract that performs a `staticcall`/`call` to the `ValidateMultiSign` precompile address with ABI-encoded input where the signature-array length word (`words[3]`) points to an offset whose length word is set to a very large positive value (e.g., `0x7FFFFFFF`) or a value whose top bit is set (interpreted as negative by `intValueSafe()`); when `allowTvmSelfdestructRestriction()` is inactive, this drives `extractBytesArray` to execute `new byte[len][]`, throwing `OutOfMemoryError`/`NegativeArraySizeException` outside any catch block in `execute()`.

    if (offset > words.length - 1) {

    }
