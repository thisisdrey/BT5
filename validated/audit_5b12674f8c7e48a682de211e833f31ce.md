### Title
Unbounded parsing of `pages_indexes` in `/v2/attachments/inv` before enforcing the page-count cap - ([File: stackslib/src/net/api/getattachmentsinv.rs])

### Summary
`RPCGetAttachmentsInvRequestHandler::try_parse_request` in [1](#0-0)  eagerly splits the entire `pages_indexes` query parameter on `,` and inserts every parsed `u32` into a `HashSet` before any bound on the number of entries is applied. The intended cap, `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` (8), is only checked afterwards, inside `try_handle_request` [2](#0-1) . This mirrors the reported bug class: parsing code that "eagerly allocates intermediate arrays/collections before applying size limits" (e.g. `BaggagePropagator.Extract`), enabling a degenerate, delimiter-heavy input to cause disproportionate allocation/parsing work relative to the intended, capped protocol semantics.

### Finding Description
The request handler for the unauthenticated `GET /v2/attachments/inv` endpoint (`security: []` per the OpenAPI spec, confirming no auth is required) reads the `pages_indexes` query argument and, for every comma-delimited token, attempts a `u32` parse and inserts the result into `page_indexes: HashSet<u32>`: [3](#0-2) 

There is no limit on the number of `split(',')` tokens processed at this stage — the loop runs over the entire query string content. Only after this unbounded processing does `try_handle_request` check `page_indexes.len() > MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` (8) and reject the request: [2](#0-1) 

This is the same equality/ordering fault as the report: the "check-then-allocate" invariant is inverted to "allocate-then-check." The protocol's documented invariant — that a client may request at most 8 pages per call, each 8 bits (per `docs/rpc/openapi.yaml` description of `pages_indexes`) — is not enforced during parsing, so the actual per-request parsing/allocation cost is bounded only by the size of the incoming query string/request line rather than by the intended cap of 8.

### Impact Explanation
This is a bounded compute/memory DoS on an unauthenticated read endpoint: an attacker can send a single `GET /v2/attachments/inv?index_block_hash=...&pages_indexes=1,2,3,...,N` request with as many comma-separated numeric tokens as fit within the HTTP request-line/preamble size limits, forcing the node to perform `N` parse operations and `HashSet` insertions before the 8-item cap is ever consulted, all for a single request that is ultimately rejected. This falls into the "High — bounded compute DoS on a read endpoint" category defined in the rules. It does not require any credentials, private keys, or elevated roles, and does not depend purely on traffic volume — a single request with a maliciously crafted query string is sufficient to trigger disproportionate parsing work relative to the intended cap.

### Likelihood Explanation
The endpoint is explicitly unauthenticated (`security: []`), reachable by any remote peer that can issue HTTP RPC requests to a node's RPC port, and the vulnerable code path (`try_parse_request`) is unconditionally invoked for every request to `/v2/attachments/inv` before the handler's real work begins. No preconditions (existing StackerDB config, valid signature, chain state, etc.) are needed — only a syntactically valid query string.

### Recommendation
Enforce the `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` cap (and/or a maximum token count) while iterating the split `pages_indexes` string in `try_parse_request`, aborting/erroring out as soon as the token count exceeds the limit rather than fully parsing and populating the `HashSet` first. Consider also capping the total length of `pages_indexes` accepted before splitting.

### Proof of Concept
1. Send `GET /v2/attachments/inv?index_block_hash=<64 hex chars>&pages_indexes=1,2,3,4,...,<as many entries as fit in the allowed query length>` to a running Stacks node's RPC port (no authentication needed since the route has `security: []`).
2. Observe that `try_parse_request` ( [3](#0-2) ) parses and inserts every comma-separated token into the `HashSet` regardless of count.
3. Only after this full parse does `try_handle_request` reject the request due to exceeding `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` ( [2](#0-1) ), demonstrating that the expensive parse/allocate step is performed unconditionally before the size limit is enforced.
