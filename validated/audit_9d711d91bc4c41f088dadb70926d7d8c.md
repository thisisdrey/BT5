### Title
Attacker permanently/temporarily fills a victim's per-account token list to `MAX_TOKENS_PER_USER` via dust `deposit(..., onBehalfOf)`, DoSing all deposits, borrows, and token receipts - (File: contracts/Pool.sol)

### Summary
The SDL2 bug class is a resource leak causing denial of service: each `GLES_CreateTexture()` call leaks memory that is never reclaimed, so repeated calls exhaust the process. The Metronome analog is the per-account token lists in `Pool`: `depositTokensOfAccount` and `debtTokensOfAccount` are bounded at `MAX_TOKENS_PER_USER = 30` combined, and anyone can add entries to an arbitrary victim's list by dust-depositing collateral `onBehalfOf` the victim. Once the victim's combined list length reaches 30, every subsequent `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` reverts with `UserReachedMaxTokens`, which blocks all new deposits, borrows, and even incoming deposit-token transfers for that account — a resource-exhaustion DoS.

### Finding Description
`Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when the sum of the two per-account sets is `>= 30` (contracts/Pool.sol:143-148). Both `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are gated by it (contracts/Pool.sol:204-220).

The list is populated as a side effect of balance changes, keyed on the *recipient*, not the caller:

- `DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever `balanceOf[account_]` was 0 (contracts/DepositToken.sol:486-488). `_mint` is reached from the public, permissionless `deposit(uint256 amount_, address onBehalfOf_)` (contracts/DepositToken.sol:211-237), where `onBehalfOf_` is fully attacker-controlled.
- `DepositToken._transfer` adds the recipient to the list on first receipt (contracts/DepositToken.sol:518-520), so plain `transfer()` dust also works.
- `DebtToken` minting (via `Pool.mint`/`issue`, and leverage paths) calls `addToDebtTokensOfAccount`, consuming the same shared cap of 30.

Attack:

1. Attacker calls `depositToken_i.deposit(1 wei, victim)` for each registered deposit token (and/or `transfer(victim, dust)`). Each call grows `depositTokensOfAccount[victim]` by 1.
2. If fewer than 30 deposit tokens exist, the attacker can also borrow dust amounts of each synthetic to fill `debtTokensOfAccount[victim]` — `debtToken.issue(amount, to_)` mints debt to an arbitrary `to_` via `Pool.mint`, populating the victim's debt list without their consent.
3. Once the combined count is 30, the victim cannot: `deposit()` any collateral (new or existing token types where their balance is 0 — actually any token not already in their list), `mint`/`issue` any synthetic, receive deposit-token transfers, receive liquidation `seize` proceeds, or use `SmartFarmingManager.leverage`. All these paths funnel into `_mint`/`_transfer`/`issue`, which revert inside `addTo*OfAccount`.

The victim can only recover by pushing entries off the list — transferring each dust balance out so `balanceOf` hits 0 triggers `removeFromDepositTokensOfAccount` (contracts/DepositToken.sol:523-525) — which costs one transaction per token and can be cheaply re-griefed by the attacker after every cleanup, giving sustained liveness denial.

### Impact Explanation
Temporary freezing of funds / liveness DoS matching the report's availability impact (CVSS A:H):

- A victim with no positions is fully locked out of the protocol (cannot deposit or borrow) for as long as the attacker maintains the fill.
- A victim who relies on `deposit(onBehalfOf)` integrations, gateways (`NativeTokenGateway`, `VesperGateway`), or smart-funding flows breaks entirely — `NativeTokenGateway.deposit{value}(pool)` deposits on behalf of `msg.sender`, and SmartFarmingManager leverage mints deposit + debt tokens to the position owner, so leverage/flashRepay into a filled account always reverts.
- Third-party senders cannot transfer deposit tokens to the victim (seizures, OTC, refunds), and liquidators seizing collateral to an account whose list is full will revert — though the liquidator can pick another beneficiary, so the primary victim is the position owner.
- The attacker can sustain the DoS indefinitely at dust cost by re-filling after each removal.

No privileged role, oracle manipulation, or misconfiguration is needed; the attack uses only public entry points on the deployed configuration.

### Likelihood Explanation
- `deposit(amount_, onBehalfOf_)` is permissionless, unpaused-gated only, and imposes no minimum amount (`amount_ == 0` is the only revert), so dust deposits are free aside from gas.
- `transfer`/`transferFrom` on `DepositToken` require `_revertIfLocked(sender_)`, but an attacker with no debt has fully unlocked balance, so dust transfers are unrestricted.
- The check counts deposit + debt tokens together against one constant (30), so fewer than 30 registered deposit tokens does not necessarily protect the victim — debt issuance to `to_` also consumes slots.
- Nothing in `SynthContext`, `ReentrancyGuardTransient`, pause flags, supply caps, or the Operator meta-sender path prevents `onBehalfOf`/recipient poisoning. The only "mitigation" is that the victim can clear entries — which the attacker can immediately re-poison, and which costs the victim O(n) transactions and breaks composability with contracts depositing on their behalf.

### Recommendation
- Require recipient consent before a token is added to `depositTokensOfAccount`: e.g., only add on `deposit` when `onBehalfOf_ == _msgSender()`, or gate `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` calls on an `allowlisted`/"opted-in" flag set by the account.
- Alternatively, treat dust balances below a threshold as not list-worthy, or make `addTo*OfAccount` non-reverting (return bool) and let `depositOf`/`debtOf` iterate over all pool tokens instead of a per-account list.
- At minimum, charge/ burn the first-deposit dust so griefing has a real cost, and document the re-griefing vector.

### Proof of Concept
Hardhat (fork or in-repo fixture) sketch — assumes `pool` has ≥1 `DepositToken` registered per collateral; loop over `pool.getDepositTokens()`:

```ts
it('griefs victim by filling depositTokensOfAccount', async () => {
  const tokens: string[] = await pool.getDepositTokens()

  // 1) attacker dust-deposits on behalf of victim for each deposit token
  for (const addr of tokens) {
    const dt = await ethers.getContractAt('DepositToken', addr)
    const underlying = await ethers.getContractAt('IERC20', await dt.underlying())
    // attacker holds dust of each underlying (e.g. from AMM swaps)
    await underlying.connect(attacker).approve(dt.address, 1)
    await dt.connect(attacker).deposit(1, victim.address)   // victim's balance goes 0 -> 1
  }

  // 2) fill remaining slots via debt issuance to victim, if needed
  //    (attacker borrows with their own collateral, issues to victim)
  while (
    (await pool.getDepositTokensOfAccount(victim.address)).length +
    (await pool.getDebtTokensOfAccount(victim.address)).length <
    (await pool.MAX_TOKENS_PER_USER()).toNumber()
  ) {
    await pool.connect(attacker).mint(synthToken.address, 1, victim.address)
  }

  // 3) any new deposit to victim reverts
  const dt0 = await ethers.getContractAt('DepositToken', tokens[0])
  const und = await ethers.getContractAt('IERC20', await dt0.underlying())
  // victim first removes the dust of token0 to make room, then someone tries
  // to deposit a DIFFERENT collateral on their behalf:
  await dt0.connect(victim).transfer(attacker.address, await dt0.balanceOf(victim.address))
  await und.connect(attacker).approve(dt0.address, 1)
  await expect(dt0.connect(attacker).deposit(1, victim.address))
    .to.be.reverted // works (slot freed) — but re-fill:
  await dt0.connect(attacker).deposit(1, victim.address)

  // victim cannot mint synthetic debt (addToDebtTokensOfAccount reverts)
  await expect(pool.connect(victim).mint(synthToken.address, 1, victim.address))
    .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```

Key steps verifiable against code: `deposit(..., onBehalfOf_)` mints to an arbitrary account (DepositToken.sol:211-237), `_mint`/`_transfer` call `addToDepositTokensOfAccount` on first receipt (DepositToken.sol:486-488, 518-520), and `addTo*OfAccount` reverts once the combined count hits `MAX_TOKENS_PER_USER` (Pool.sol:143-148, 204-220).
