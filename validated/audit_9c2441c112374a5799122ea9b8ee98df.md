### Title
Duplicate-signer weight counting in `ValidateMultiSign` precompile via ECDSA signature malleability - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract, which TVM contracts use to verify multi-signature authorization for an on-chain account/permission, deduplicates signatures by comparing the exact byte-encoding of `(recoveredAddr, sign)` rather than deduplicating by the recovered signer address alone. Because ECDSA signatures are malleable (a second valid `(r, s')` pair with a flipped `v` can be trivially derived from any signature without access to the private key), a single attestor's one signature can be turned into a second, byte-distinct, still-valid signature that recovers to the same address. Both are then counted independently toward `totalWeight`, letting one signer satisfy a multi-key threshold alone.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute`, the loop that accumulates `totalWeight` tracks previously-seen entries in `executedSignList`: [1](#0-0) 

For each supplied signature, `recoverAddrBySign` recovers the signer address, the raw signature bytes are merged with the address into `sign`, and the code only `continue`s (skips adding weight) when **both** the recovered address *and* the exact merged signature bytes were already seen:

```java
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```

If `recoveredAddr` matches a previously-seen entry but the raw signature bytes differ (e.g., a malleated `(r, n-s, flipped v)` signature over the same hash, which recovers to the identical address), the `continue` is skipped and the weight for that signer is added a second time. This is the same bug class as the report: the check verifies exact signature repetition instead of deduplicating by signer identity, so one real signer's authorization can be double- (or multiply-) counted toward the threshold.

By contrast, the consensus-critical transaction-signing path `TransactionCapsule.checkWeight` correctly deduplicates by signer address/base64 key and rejects a repeat signer outright: [2](#0-1) 
This confirms the precompile's weaker exact-byte dedup is the outlier/defective path.

### Impact Explanation
`ValidateMultiSign` is a TVM precompiled contract reachable by any smart contract from a `TriggerSmartContract` transaction submitted by an unprivileged caller. Contracts (e.g., custodial wallets, escrow, or governance contracts on TRON) that rely on this precompile to gate fund transfers or privileged actions behind an M-of-N multisig permission can have their threshold satisfied by a single colluding/compromised key producing two malleated signatures, instead of M independent attestors. This enables unauthorized execution of an operation gated by the multisig check — a concrete unauthorized account operation / theft-of-funds primitive when the calling contract moves value based on the boolean result.

### Likelihood Explanation
Exploitation only requires possession of one valid ECDSA signature (r, s, v) over the target hash from a legitimate key in the permission set; deriving the malleated counterpart `(r, n-s, v')` is pure arithmetic requiring no additional key material. The attacker/contract simply supplies both signatures in the `signatures` array passed to `validatemultisign`. No special privileges or network position are needed — it is reachable from an ordinary `TriggerSmartContract` call.

### Recommendation
Deduplicate `ValidateMultiSign`'s `executedSignList` by recovered signer address only (not by the raw signature bytes), mirroring `TransactionCapsule.checkWeight`'s use of the recovered address/key as the sole dedup key, and reject/skip weight accumulation for any address already counted, regardless of the exact signature bytes presented.

### Proof of Concept
1. Deploy an account/permission with `threshold = 2` and two keys, `key1` and `key2`, each weight 1 (as in `ValidateMultiSignContractTest`). [3](#0-2) 
2. Have only `key1` sign the hash once, obtaining `(r, s, v)`.
3. Compute the malleated counterpart `(r, n-s, v_flipped)` using the secp256k1 curve order `n` — this is valid without `key2`'s participation.
4. Call `validatemultisign(address, permissionId, data, [sig1, sig1_malleated])`.
5. `recoverAddrBySign` recovers `key1`'s address for both entries; since the merged `sign` bytes differ between the two, the `matrixContains(executedSignList, sign)` check fails to detect the duplicate, and `totalWeight` is incremented twice (2 ≥ threshold 2), returning `DataWord.ONE()` despite `key2` never having signed — mirroring the loop shown at: [4](#0-3)
