### Title
`DebtToken.issue()` mints synthetics while the synthetic token is deactivated — the `isActive` safety check applied to `mint()` is missing on the public issuance path - (File: contracts/DebtToken.sol)

### Summary
The fickling bug class is an incomplete deny-list: a safety gate enumerates dangerous operations but misses one entry, so an attacker-controlled input is classified as safe. In Metronome, the analogous gate is the `SyntheticToken.isActive` flag — a governor-controlled kill switch meant to halt minting of a given synth. `DebtToken` defines the `onlyIfSyntheticTokenIsActive` modifier and applies it to `mint()` (`contracts/DebtToken.sol:105-108`, `:338`) but not to `issue()` (`:235-244`) or `flashIssue()` (`:281-292`). The result: while the manager path is blocked once a synth is deactivated, the primary public issuance path keeps minting it — the same "one entry missing from the blocklist" shape.

### Finding Description
`issue()` is the permissionless entry point that locks collateral and mints synthetic tokens to any `to_` address. Its modifiers are `whenNotShutdown`, `nonReentrant`, and `onlyIfSyntheticTokenExists` (`contracts/DebtToken.sol:239-244`) — it only verifies the synth is *registered*, not that it is *active*. Internally it calls `_mint()`, which enforces `onlyIfDebtTokenIsActive`, the debt floor, and `maxTotalSupply` (`:572-601`), and then mints the synthetic token directly at `:268`.

By contrast, `mint()` — the SmartFarmingManager-only sibling — requires both `onlyIfSyntheticTokenExists` and `onlyIfSyntheticTokenIsActive` (`:328-339`). The `isActive` check exists in the codebase precisely to freeze issuance of a synthetic (e.g., when its oracle is being deprecated, the asset is being wound down, or abnormal conditions are detected), but it is absent from the one function any EOA can call.

`flashIssue()` also lacks `onlyIfSyntheticTokenIsActive` (`:290-291`), but it is gated behind `onlyIfSmartFarmingManager`, so the reachable unprivileged surface is `issue()`.

### Impact Explanation
Deactivating a synthetic token is the protocol's per-asset circuit breaker. When it is flipped off, every guarded mint path stops — except `issue()`. An unprivileged attacker (any EOA, directly or via `Operator.execute`) can:

1. Deposit collateral and call `issue(amount, to)` on the deactivated synth's `DebtToken`.
2. Receive freshly minted synthetic tokens that governance intended to halt.
3. Dump them via `Pool.swap` into other synthetics/collateral, or hold them while the position accrues debt.

If the synth was deactivated because of oracle problems or planned wind-down (the realistic reasons to use `isActive`), continued issuance expands the protocol's liability in exactly the asset it tried to quarantine — converting a safety switch into a bypassable control and creating protocol solvency risk. This is the same impact shape as the fickling bypass: a control designed to reject a dangerous operation fails to cover one code path, so the dangerous operation executes.

Caveat I could not fully verify within the available iterations: whether `Pool.swap` and `SyntheticToken.mint` independently check `isActive` would determine whether the minted synth can be immediately swapped. Even if `SyntheticToken.mint` enforces `isActive`, the inconsistency remains a latent footgun; if it does not, the bypass is live.

### Likelihood Explanation
- Requires only that a synthetic token exists and has been deactivated — a state the governor sets precisely when conditions are abnormal.
- Attacker needs only ordinary collateral and a public call to `issue()`; no privileged role, no oracle manipulation, no flash loan required.
- Guarded alternatives (`mint`, and the `whenNotShutdown`/`onlyIfDebtTokenIsActive` checks inside `_mint`) do not block the path because none of them is `onlyIfSyntheticTokenIsActive`.

### Recommendation
Add `onlyIfSyntheticTokenIsActive` to `issue()` (and to `flashIssue()` for consistency) in `contracts/DebtToken.sol`, mirroring `mint()`. Audit all entry points that create new synthetic-token supply to ensure the active flag is enforced uniformly — treat the modifier set as a deny-list that must cover every issuance path.

