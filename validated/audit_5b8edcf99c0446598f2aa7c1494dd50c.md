### Title
HTTP Header Injection into outbound `git clone`/`remote show` requests via unsanitized `HttpAuthorizationHeader` field - ([File: internal/gitaly/service/repository/create_repository_from_url.go])

### Summary
`CreateRepositoryFromURL` and `FindRemoteRootRef` both accept a caller-controlled `HttpAuthorizationHeader` string field and splice it directly into a `http.extraHeader` (or `http.<url>.extraHeader`) Git config value with no validation that it is free of CR/LF control characters, mirroring the "empty headers separated by CR" root cause of the reported Node.js `llhttp` bug class: header/field values are trusted as atomic even though embedded CR/LF can be interpreted as a delimiter, allowing an attacker to inject additional header lines/fields into the outbound HTTP request.

### Finding Description
In `cloneFromURLCommand`, the value taken straight from the RPC request (`req.GetHttpAuthorizationHeader()`) is formatted into an `Authorization:` header and passed as a `git` config pair: [1](#0-0) 
This value flows unchanged from the gRPC request: [2](#0-1) 

The equivalent pattern exists in `findRemoteRootRefCmd`, where `request.GetHttpAuthorizationHeader()` is concatenated into the `http.<remote_url>.extraHeader` config key/value pair without sanitization: [3](#0-2) 

These `ConfigPair` values are transported to the `git` subprocess purely as environment variables (`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`), with no escaping or control-character stripping performed anywhere in that path: [4](#0-3) 

Unlike `Flag`/`ValueFlag`, which do run values through `flagRegex` validation, `ConfigPair` values used via `WithConfigEnv` have no such validation. Compare this to Gitaly's own reference-name validator, which explicitly rejects `\r`/`\n`/control characters for ref names because "someone injected parameters with extra newlines...could cause subsequent values to be ignored": [5](#0-4) 
No analogous check exists for `HttpAuthorizationHeader` in either validation function (`validateCreateRepositoryFromURLRequest` only checks for an empty URL, and `FindRemoteRootRef` only checks for an empty remote URL/repository): [6](#0-5) [7](#0-6) 

Because `http.extraHeader` is passed to libcurl by `git`, an attacker-supplied value containing `\r\n` (or a bare `\r`, per the analogous llhttp behavior) is interpreted as terminating the `Authorization` header and beginning new arbitrary header lines in the outbound HTTP request that Gitaly's `git clone`/`git remote show` issues to the attacker-chosen `Url`/`RemoteUrl`. This is a server-side outbound header-injection primitive reachable from an ordinary user-triggered RPC field (`CreateRepositoryFromURLRequest.http_authorization_header`, `FindRemoteRootRefRequest.http_authorization_header`), not requiring a privileged actor or leaked token — the header content itself is the untrusted input.

### Impact Explanation
Because the `Url`/`RemoteUrl` is also attacker-controlled, and Gitaly performs no CR/LF sanitization of the header value it embeds, an attacker can inject extra HTTP header fields (e.g. overriding `Host`, adding cache-poisoning headers, or splitting into a second smuggled request/response on servers that tolerate lone-CR delimiters) into requests Gitaly makes to arbitrary internal or external HTTP endpoints during `CreateRepositoryFromURL`/`FindRemoteRootRef`. Combined with the fact that these RPCs already function as a controlled SSRF primitive (they let Gitaly issue HTTP requests to attacker-chosen URLs), header injection increases the severity by enabling request smuggling/splitting against downstream proxies or internal services that parse the injected header as legitimate, and by allowing exfiltration or manipulation of headers sent to the attacker's own listener as a way to help fingerprint or manipulate the request in more sophisticated topologies (e.g. cache poisoning of an internal reverse proxy in front of the "remote" host).

### Likelihood Explanation
Both RPCs are reachable via crafted gRPC requests from any client authorized to call `RepositoryService`/`RemoteService` (i.e., ordinary GitLab-authenticated import/mirror flows use these under the hood), and no special privilege beyond normal RPC access is required — the field is a plain proto string with no format constraint enforced server-side. Exploitation only requires supplying a value containing `\r` in the `http_authorization_header` field.

### Recommendation
Reject or strip CR/LF (and other control characters) from `HttpAuthorizationHeader` in both `validateCreateRepositoryFromURLRequest` and `FindRemoteRootRef`'s validation path before it is embedded into the `http.extraHeader` config value, analogous to the control-character rejection already implemented in `ValidateReference`. Alternatively, validate that the header value matches a single `token: value`-shaped line with no embedded CR/LF, consistent with RFC 7230's strict CRLF-only field delimiting.

### Proof of Concept
1. Call `FindRemoteRootRef` (or `CreateRepositoryFromURL`) with:
   - `RemoteUrl`/`Url` pointing to an attacker-controlled or internal HTTP server.
   - `HttpAuthorizationHeader` set to `Bearer x\r\nX-Injected: evil` (or with a bare `\r` per the llhttp-analog delimiter confusion).
2. Gitaly builds the config pair `Authorization: Bearer x\r\nX-Injected: evil` and passes it via `GIT_CONFIG_VALUE_n` to `git remote show`/`git clone`.
3. `git`'s libcurl-based HTTP client sends the value verbatim in the `Authorization:` header; observe on the attacker's listening server that an extra `X-Injected: evil` header (or split request) is received, confirming the header injection.

```go
func (s *server) FindRemoteRootRef(ctx context.Context, in *gitalypb.FindRemoteRootRefRequest) (*gitalypb.FindRemoteRootRefResponse, error) {
	if in.GetRemoteUrl() == "" {
		return nil, structerr.NewInvalidArgument("missing remote URL")
	}
	if err := s.locator.ValidateRepository(ctx, in.GetRepository()); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	ref, err := s.findRemoteRootRef(ctx, in)
	if err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.FindRemoteRootRefResponse{Ref: ref}, nil
```

```go
// ConfigPairsToGitEnvironment converts the given config pairs into a set of environment variables
// that can be injected into a Git executable.
func ConfigPairsToGitEnvironment(configPairs []ConfigPair) []string {
	env := make([]string, 0, len(configPairs)*2+1)

	for i, configPair := range configPairs {
		env = append(env,
			fmt.Sprintf("GIT_CONFIG_KEY_%d=%s", i, configPair.Key),
			fmt.Sprintf("GIT_CONFIG_VALUE_%d=%s", i, configPair.Value),
		)
	}

	return append(env, fmt.Sprintf("GIT_CONFIG_COUNT=%d", len(configPairs)))
}
```
