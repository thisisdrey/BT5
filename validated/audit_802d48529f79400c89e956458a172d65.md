### Title
`LinkRepositoryToObjectPool` allows linking an arbitrary repository to an arbitrary object pool, granting cross-repository object disclosure via git alternates - (File: `internal/gitaly/service/objectpool/link.go`)

### Summary
`LinkRepositoryToObjectPool` accepts two independently-supplied repository references — the `object_pool` (marked `additional_repository`) and the `repository` to link (marked `target_repository`) — and links them without verifying any actual relationship (fork/pool-membership) between the two. This mirrors the reported Web3 bug class: a caller supplies an arbitrary target ID/reference (there, a `tOLPTokenId`; here, an `ObjectPool`) that is never checked for ownership/association with the acting party before a sensitive cross-entity operation (there, `approve`+`participate`; here, writing the pool into the repo's git alternates file) is performed.

### Finding Description
The RPC handler simply validates that `repository` is a well-formed repository and that a pool object can be resolved from `req.GetObjectPool()`, then calls `pool.Link(ctx, repo)`: [1](#0-0) 

`Link` writes the pool's object directory path into the target repository's `objects/info/alternates` file, with no check that the pool being referenced is the pool that this specific repository is supposed to belong to (e.g., its fork-network primary's pool): [2](#0-1) 

The proto definition confirms both fields are caller-controlled, independent identifiers with no cross-validation contract enforced server-side: [3](#0-2) 

Once linked, git treats the pool's object store as transparently available to anyone who can read the linking repository (via `git cat-file`, clone, etc.), because alternates make all objects in the pool directory resolvable from the member repository — this is the intended dedup mechanism, but it becomes a disclosure vector when the pool and the linked repository have no legitimate relationship, exactly as `IERC721(lockDataTarget).approve(...)` in the Solidity report never checked that the caller-controlled `lockDataTarget`/`tOLPTokenId` pair belonged together.

### Impact Explanation
If an actor who is authorized to call `LinkRepositoryToObjectPool` for *some* repository (e.g., a repo they otherwise have write access to) can supply the `object_pool` identifier of a *different*, unrelated (possibly private) repository's pool, all objects contained in that victim pool become readable through the attacker's own repository via git alternates — a cross-repository object disclosure. This is analogous to the reported theft: the victim's "asset" (here, private object contents reachable only through pool membership) becomes accessible to an unauthorized party purely because the linking call trusts a caller-supplied reference without verifying legitimate association.

### Likelihood Explanation
Exploitability depends on whether the calling layer (Gitaly's RPC authorization, normally enforced by Praefect/gitlab-rails token scoping) restricts `object_pool` to pools the caller's repository is actually permitted to join. Within Gitaly itself — the layer in scope here — there is no defense-in-depth check tying the `object_pool` and `repository` fields together; the RPC handler and `Link` function accept any combination that passes basic repository-path validation. If any upstream caller uses this API with attacker-influenced object-pool identifiers, the primitive is directly reachable.

### Recommendation
Add a server-side check in `LinkRepositoryToObjectPool` (or in `objectpool.Link`) that verifies the target repository's expected object pool (e.g., derived from its fork-network origin/primary member metadata) matches the `object_pool` supplied in the request, rather than trusting the two independently-supplied identifiers to be legitimately paired.

### Proof of Concept
1. Attacker has permission to call `LinkRepositoryToObjectPool` for `repository = attacker/repo` (any repo they control).
2. Attacker sets `object_pool` to the pool repository backing `victim/private-repo`'s fork network (a value they can obtain or guess, e.g., via `GetObjectPool` on a repo they can otherwise touch, or through internal path conventions).
3. `s.poolForRequest` resolves the pool and `pool.Link(ctx, repo)` writes the alternates entry into `attacker/repo/objects/info/alternates` pointing at the victim's pool objects directory — see `internal/git/objectpool/link.go:26-66`.
4. Attacker subsequently clones/fetches `attacker/repo`; git transparently resolves any object hash present in the victim pool through the alternates link, disclosing objects that should only be reachable by legitimate pool members.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil

// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

// LinkRepositoryToObjectPoolRequest is a request for the LinkRepositoryToObjectPool RPC.
message LinkRepositoryToObjectPoolRequest {
  // object_pool is the object pool to which the repository shall be linked to.
  ObjectPool object_pool = 1 [(additional_repository)=true];
  // repository is the repository that shall be linked to the object pool.
  Repository repository = 2 [(target_repository)=true];
}
