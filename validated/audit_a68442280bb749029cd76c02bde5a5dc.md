### Title
Object Quarantine Migration Occurs Before Update-Hook Rejection Decision, Persisting Pushed Objects Despite Denied Reference Update - ([File: internal/gitaly/hook/updateref/update_with_hooks.go])

### Summary
In `UpdaterWithHooks.UpdateReference`, the quarantine directory containing newly pushed objects is unconditionally migrated into the repository's main object database as soon as the `pre-receive` hook (the GitLab `/internal/allowed` access check) succeeds, and *before* the `update` hook — the second-stage, per-reference check — has had a chance to run and potentially reject the change.

### Finding Description
The report describes a class of bug where an operation intended to enforce exclusion/rejection of a party has an irreversible side effect that already occurred before the final rejection decision is made, letting the target keep the side effect even though the overall operation is denied.

The Gitaly analog is the object-quarantine migration ordering in `UpdateReference`: [1](#0-0) 

The sequence is:
1. `PreReceiveHook` is run against the quarantined repo (Rails `/internal/allowed` + admin pre-receive custom hooks).
2. If it succeeds, `quarantineDir.Migrate(ctx)` is called immediately, moving all pushed objects into the real object database.
3. Only afterwards is `UpdateHook` invoked, which can still reject the reference update.

This ordering is explicitly confirmed by the design documentation: [2](#0-1) [3](#0-2) 

Because migration happens before the `update` hook runs, any custom `update` hook logic that is meant to block a specific ref update (e.g., per-branch policy enforcement implemented as an `update` hook) cannot prevent the pushed objects from becoming permanent, reachable-by-SHA members of the repository's object store — even though the ref itself is never updated to point at them. The `_redeem`/`ejectUser` pattern in the report ("blocking action has an irreversible side effect that already fired before the block took effect") maps directly onto "objects are migrated (an irreversible action) before the update hook's rejection is evaluated."

### Impact Explanation
An attacker who can push to a repository (an ordinary git user) can smuggle otherwise-blocked objects (commits, blobs, trees) into the main object database of the target repository even when the `update` hook is designed to reject the specific reference update. The objects remain unreachable from any ref, but they persist on disk, are reachable by exact OID, count towards storage, and could later be referenced or leaked (e.g., via a subsequent push of a lightweight tag/ref pointing at the already-present OID, bypassing further object-transfer/validation), and can complicate garbage collection/quota assumptions that rely on "rejected pushes leave no objects behind."

### Likelihood Explanation
This requires only an ordinary authenticated push where the pre-receive checks pass (which they normally do for any authorized pusher) but the update hook (a second, more specific check) rejects the change. This is a very common pattern (e.g., protected-branch enforcement implemented via the `update` hook), so the sequence is reachable through normal usage, not a privileged or MITM scenario.

### Recommendation
Defer `quarantineDir.Migrate(ctx)` until after the `update` hook has approved the change, mirroring how vanilla `git-receive-pack` only merges the quarantine directory once all pre-receive gating has fully completed for that reference. If migrating early is required for hook compatibility (as noted in the code comment about `git-update-ref` needing objects available), an alternative would be to keep the quarantine directory intact until the update hook succeeds, and only merge if the update hook approves; on rejection, discard the quarantine directory entirely as is done in `Migrate`'s cleanup on error.

### Proof of Concept
1. Configure a repository with a custom `update` hook that always rejects a specific ref (this simulates any per-ref policy check, e.g. blocking force-pushes or blocking pushes from a particular user to a protected branch), while `pre-receive` (which only checks general push authorization) accepts the push.
2. Push a new commit to that ref. `PreReceiveHook` succeeds → `quarantineDir.Migrate` runs → objects land in the main object directory.
3. `UpdateHook` runs and rejects → `UpdateReference` returns an error and the ref is never updated.
4. Inspect the repository's object database directly (or via `git cat-file -e <OID>`) and observe that the pushed commit/blob objects exist in the main object store despite the ref update having failed — confirming the objects were not quarantined/discarded on rejection.

Note: I was not able to fully trace `receivePackReferenceUpdates` (used by the alternate `proc-receive` non-atomic path in `internal/gitaly/hook/receivepack/receive_pack.go`) to confirm whether it exhibits the same early-migration-before-rejection pattern, since the tool budget was exhausted before I could locate and read that function's definition. The confirmed finding above is limited to the `UpdaterWithHooks.UpdateReference` path used by most `OperationService` RPCs.
