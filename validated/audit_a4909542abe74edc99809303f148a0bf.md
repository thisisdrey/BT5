### Title
Path traversal / arbitrary file write via unsanitized `tar` extraction in `CreateRepositoryFromSnapshot` — ([File: internal/gitaly/service/repository/create_repository_from_snapshot.go])

### Summary
`CreateRepositoryFromSnapshot` fetches an attacker/caller-supplied archive over HTTP and extracts it directly with the system `tar` binary into a freshly created repository directory, with **no validation of entry names, symlinks, or `../` traversal sequences**. This is the same bug class as the External Report's "admin can point contract addresses/pools to attacker-controlled destinations" — here, an untrusted/attacker-influenced snapshot source can redirect where files land on disk, instead of where a governance role redirects funds.

### Finding Description
The RPC handler `untar()` builds and runs `tar -C <path> -xvf -` directly against the HTTP response body, with the code's own comment acknowledging the danger: [1](#0-0) 

and the call site explicitly documents that the archive content is "trusted *a lot*": [2](#0-1) 

There is no per-entry path validation, no rejection of absolute paths, no symlink-escape check, and no hardlink-escape check — unlike the parallel, hardened implementation used elsewhere in the codebase (`extractTarToDirectory` in `internal/gitaly/service/repository/replicate.go`), which explicitly validates that regular files, symlinks, and hardlinks all resolve within the target directory before writing: [3](#0-2) 

The `CreateRepositoryFromSnapshot` request additionally allows the caller to supply `ResolvedAddress` to pin the DNS resolution of the `HttpUrl`, which shows this RPC is meant to fetch snapshot data from **another Gitaly node acting as an HTTP source, not a fully trusted local process** — meaning the content of the tar stream is effectively coming from a network peer / another storage node, and that content is not authenticated as being a benign Gitaly-generated snapshot: [4](#0-3) 

Because raw system `tar` is invoked, if the archive contains entries with `../../` sequences, absolute paths, or malicious symlinks, `tar` will extract them following its own (permissive) semantics onto disk outside of the intended target repository directory — this is the classic "tar-slip"/path-traversal-in-archive-extraction vulnerability.

### Impact Explanation
If an attacker can control or influence the bytes served from the `HttpUrl` used with `CreateRepositoryFromSnapshot` (e.g., because they control the resolved endpoint, or an intermediate cache/proxy responds instead of the intended Gitaly node, or the source repository's `GetSnapshot` output is otherwise tampered with in transit), the attacker can write or overwrite arbitrary files on the Gitaly host filesystem, escaping the newly created repository directory. This can lead to: overwriting arbitrary files under the storage root (corrupting or replacing other repositories' hooks/config), or writing outside the storage root entirely (system-level file write), which can escalate to remote code execution via custom hook injection or configuration overwrite. This satisfies "concrete storage escape" and "extraction escape" as called out by the analog validation criteria.

### Likelihood Explanation
`CreateRepositoryFromSnapshot` is a first-class, reachable gRPC RPC on `RepositoryService`, and its request carries an unauthenticated (from Gitaly's perspective) HTTP source (`HttpUrl`) plus an optional `ResolvedAddress` used specifically to defeat DNS rebinding — indicating the design already assumes the destination server is not fully trusted network infrastructure. Any caller of this API (which the code comments acknowledge is unsafe against untrusted endpoints) combined with any means of influencing what bytes are returned at that URL results in exploitation; no admin/governance privilege is required beyond the ability to invoke this specific RPC with attacker-influenced parameters, unlike the excluded privileged-admin analog in the original finding.

### Recommendation
Replace the raw `tar` subprocess extraction in `untar()` with the already-hardened, in-repo Go tar extraction logic used by `extractTarToDirectory` (`internal/gitaly/service/repository/replicate.go`), which validates that every regular file, directory, symlink target, and hardlink target resolves within the target directory before writing, and rejects absolute symlinks/traversal outright. Additionally, treat the fetched snapshot as untrusted input regardless of source, and enforce the same size/entry-count and typeflag restrictions used elsewhere in the codebase (e.g., `internal/cli/gitaly/subcmd_recovery_replay.go`'s `extractArchive`, which restricts supported header types).

### Proof of Concept
1. Stand up (or otherwise control the response of) an HTTP endpoint that `CreateRepositoryFromSnapshotRequest.HttpUrl` will be pointed at.
2. Serve a tar stream containing an entry such as `../../../etc/cron.d/evil` or a symlink entry whose target escapes the destination directory (e.g., `Linkname: "../../../../tmp"`, mirrored from the escape test case already present for the hardened code path): [5](#0-4) 
3. Invoke `CreateRepositoryFromSnapshot` with that `HttpUrl`. Because `untar()` shells out to system `tar -xvf -` with no path/symlink validation (unlike the hardened path shown in step 2's test), the crafted entries are extracted following `tar`'s native behavior, writing outside of the intended repository path on the Gitaly host.

// extractTarToDirectory extracts a tar archive to the specified directory using Go's tar package
func (s *server) extractTarToDirectory(ctx context.Context, reader io.Reader, targetDir string) error {
	targetDir = filepath.Clean(targetDir)
	tarReader := tar.NewReader(reader)

	for {
		select {
		case <-ctx.Done():
			return ctx.Err()
		default:
		}

		header, err := tarReader.Next()
		if err == io.EOF {
			break // End of archive
		}
		if err != nil {
			return fmt.Errorf("reading tar header: %w", err)
		}

		targetPath := filepath.Join(targetDir, header.Name)

		if !strings.HasPrefix(targetPath, targetDir+string(os.PathSeparator)) &&
			targetPath != targetDir {
			return fmt.Errorf("invalid file path in tar: %s", header.Name)
		}

		switch header.Typeflag {
		case tar.TypeDir:
			if err := os.MkdirAll(targetPath, os.FileMode(header.Mode)); err != nil {
				return fmt.Errorf("creating directory %s: %w", targetPath, err)
			}

		case tar.TypeReg:
			if err := s.extractFile(ctx, tarReader, targetPath, header); err != nil {
				return fmt.Errorf("extracting file %s: %w", targetPath, err)
			}

		case tar.TypeSymlink:
			if filepath.IsAbs(header.Linkname) {
				return fmt.Errorf("absolute symlink not allowed: %s -> %s", header.Name, header.Linkname)
			}

			// Resolve the relative symlink target from the symlink's parent directory
			// and verify it stays within the extraction boundary, consistent with the
			// hard link validation below.
			resolvedTarget := filepath.Join(filepath.Dir(targetPath), header.Linkname)
			if !strings.HasPrefix(resolvedTarget, targetDir+string(os.PathSeparator)) &&
				resolvedTarget != targetDir {
				return fmt.Errorf("symlink target escapes extraction directory: %s -> %s", header.Name, header.Linkname)
			}
