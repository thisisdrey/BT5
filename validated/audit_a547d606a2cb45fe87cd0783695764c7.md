## Title
Unchecked `reduceAssetAmountV2` return value in `MarketSellAssetActuator::transferBalanceOrToken()` allows silent debit failure - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
The reported ERC20 pattern (`transferFrom` return value ignored, causing accounting desync) has a structural analog in java-tron's `MarketSellAssetActuator`. Java-tron's `AccountCapsule.reduceAssetAmountV2()` returns a `boolean` to signal whether the debit actually succeeded (insufficient balance), and `TransferAssetActuator` correctly checks this return value and aborts the transaction if it fails. `MarketSellAssetActuator.transferBalanceOrToken()`, however, calls the same `reduceAssetAmountV2()` API and discards the boolean result.

### Finding Description
In `TransferAssetActuator.execute()` the pattern for debiting TRC10 tokens is:
```java
if (!ownerAccountCapsule.reduceAssetAmountV2(assetName.toByteArray(), amount, dynamicStore, assetIssueStore)) {
  throw new ContractExeException("reduceAssetAmount failed !");
}
``` [1](#0-0) 

In contrast, `MarketSellAssetActuator.transferBalanceOrToken()` performs the equivalent debit for the "sell" leg of a market order but ignores the returned boolean entirely:
```java
private void transferBalanceOrToken(AccountCapsule accountCapsule) {
  if (Arrays.equals(sellTokenID, "_".getBytes())) {
    accountCapsule.setBalance(subtractExact(accountCapsule.getBalance(), sellTokenQuantity));
  } else {
    accountCapsule
        .reduceAssetAmountV2(sellTokenID, sellTokenQuantity, dynamicStore, assetIssueStore);
  }
}
``` [2](#0-1) 

This is invoked from `execute()` right before an order is created and matched against the order book:
```java
// 1. transfer of balance
transferBalanceOrToken(accountCapsule);

// 2. create and save order
MarketOrderCapsule orderCapsule = createAndSaveOrder(accountCapsule, contract);

// 3. match order
matchOrder(orderCapsule, takerPrice, ret, accountCapsule);
``` [3](#0-2) 

Because the debit result is discarded, if `reduceAssetAmountV2` ever fails to debit (e.g., returns `false` due to insufficient balance or a state inconsistency), the actuator proceeds anyway: it creates a sellable order for the full `sellTokenQuantity` and later matches it against maker orders, crediting the counterparty via `addTrxOrToken`, without the seller's balance ever actually being reduced.

### Impact Explanation
If this debit silently fails, the account can place and have matched a sell order backed by tokens it does not actually give up, letting the counterparty receive real value (TRX or another TRC10 token) while the seller retains its original token balance — an unbacked-balance / theft-of-funds condition consistent with the "unsafe transfer, return value ignored" bug class from the reference report.

### Likelihood Explanation
`MarketSellAssetActuator.validate()` is expected to check sell-token sufficiency before `execute()`, which is the primary reason this path is not trivially triggerable today; exploitability depends on whether any code path/state transition can cause `reduceAssetAmountV2` to return `false` after `validate()` passes (e.g., token map/state divergence between `AssetMap`/`AssetV2Map` under `allowSameTokenName` transitions, or any race/reentrancy in the same block). I was not able to fully verify `reduceAssetAmountV2`'s implementation and `MarketSellAssetActuator.validate()`'s exact balance checks within this session — this needs a full read of `AccountCapsule.reduceAssetAmountV2()` (chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java) and `MarketSellAssetActuator.validate()` to confirm whether such a divergence is currently reachable.

### Recommendation
Check the boolean return value of `reduceAssetAmountV2()` in `MarketSellAssetActuator.transferBalanceOrToken()` and throw a `ContractExeException` (mirroring `TransferAssetActuator`) if the debit fails, aborting order creation/matching rather than silently proceeding.

### Proof of Concept
Not conclusively demonstrated within this session due to incomplete verification of `reduceAssetAmountV2()`'s failure conditions and `MarketSellAssetActuator.validate()`'s pre-checks (tool access ended before these files could be read in full). A concrete PoC would require identifying a state under `allowSameTokenName` toggling, or any other AssetMap/AssetV2Map inconsistency, where `reduceAssetAmountV2` returns `false` after `validate()` has already approved the order — a Devin session with full file access should confirm this before treating the finding as exploitable.
