### Title
Unbounded in-memory buffering of blob content in gitaly-lfs-smudge long-running filter process leads to per-checkout memory exhaustion - (File: cmd/gitaly-lfs-smudge/smudge.go)

### Summary
The `process()` function in `cmd/gitaly-lfs-smudge/smudge.go` accumulates the entire content of a filtered blob into an in-memory `bytes.Buffer` while in `processStateSmudgeContent`, with no size cap, before ever checking whether the blob is a valid LFS pointer via `lfs.DecodeFrom`. A repository owner can mark arbitrarily large non-LFS-pointer blobs with `filter=lfs` in `.gitattributes`, forcing every checkout/archive operation that engages the long-running filter process to buffer the full blob size in RAM inside the `gitaly-lfs-smudge` subprocess.

### Finding Description
`GetArchive` with `IncludeLfsBlobs: true` configures `smudge.DriverTypeProcess` and injects `filter.lfs.process=gitaly-lfs-smudge` into the `git archive` invocation, as seen in `internal/gitaly/service/repository/archive.go`'s `handleArchive`, which builds `smudge.Config{..., DriverType: smudge.DriverTypeProcess}` and passes it via `gitcmd.WithConfig`/`gitcmd.WithEnv` to `repo.Exec`. [1](#0-0)  When git streams a blob through the long-running filter protocol, `process()` reads pktlines in `processStateSmudgeContent` and appends every payload straight into `content bytes.Buffer` with no bound: `if _, err := content.Write(data); err != nil { ... }`, only stopping once a flush packet is received. [2](#0-1)  Only after the full blob has been buffered does `smudgeOneObject` call `lfs.DecodeFrom(from)` to determine whether the content is an actual LFS pointer, and the code's own comment acknowledges this: "Ideally, we could avoid slurping the whole content into memory first... this is impossible in the context of long-running processes" because the server must not respond before receiving all content. [3](#0-2) [4](#0-3)  There is no size limit check on `content` anywhere in this loop, so a large non-pointer blob committed with `filter=lfs` in `.gitattributes` causes the `gitaly-lfs-smudge` subprocess to hold the entire blob in memory.

### Impact Explanation
Each `GetArchive` (or other checkout path using the `DriverTypeProcess` smudge filter) RPC that touches such a blob spawns a `gitaly-lfs-smudge` subprocess whose memory usage grows proportionally to the attacker-controlled blob size, with no cap enforced by Gitaly. Concurrent archive/checkout requests against such a repository can multiply this effect across subprocesses, exhausting host memory/CPU and degrading or crashing the Gitaly node — this matches the "resource exhaustion of a handler" DoS impact class.

### Likelihood Explanation
The precondition set is fully within an unprivileged user's control: they own the repository, can commit a `.gitattributes` with `filter=lfs` and push arbitrarily large blobs that are not valid LFS pointers. Simply calling `GetArchive` with `IncludeLfsBlobs: true` (or any checkout flow using process-mode LFS smudging) against such a repo triggers the vulnerable code path deterministically and repeatably, with no rate limiting or size cap encountered in the reviewed code. However, this is a known and explicitly documented limitation of the git long-running filter-process protocol itself (the code comment states the buffering is required so the server doesn't answer before receiving all content), not a coding oversight unique to Gitaly's logic — a genuine fix would require deviating from or extending the standard protocol semantics (e.g., streaming to a bounded temp file, or enforcing a maximum probe/spool size), which is a design trade-off rather than a simple bug.

### Recommendation
Bound the amount of data buffered in memory: spool blob content that exceeds a reasonable threshold (e.g., a few KB used to detect the LFS pointer signature) to a temporary file on disk instead of an unbounded `bytes.Buffer`, and/or enforce a hard maximum size for the in-memory probe buffer used by `lfs.DecodeFrom`, consistent with the "first 1024 bytes" comment already in the pointer-parsing logic.

### Proof of Concept
1. Create a repository with `.gitattributes` containing `* filter=lfs`.
2. Commit a large (e.g., several-hundred-MB) file that is not a valid LFS pointer (e.g., random binary data).
3. Call `GetArchive` with `IncludeLfsBlobs: true` against a commit including this file.
4. Observe the `gitaly-lfs-smudge` subprocess's RSS grow proportionally to the committed blob size while it buffers content in `process()`'s `content bytes.Buffer` before falling through to `io.NopCloser(contents)` in `smudgeOneObject`. [4](#0-3)
