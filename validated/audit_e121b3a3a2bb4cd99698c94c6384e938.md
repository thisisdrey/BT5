### Title
Integer division truncation in TVM dynamic-energy penalty calculation causes systematic energy fee under-billing - (File: `actuator/src/main/java/org/tron/core/vm/EnergyCost.java`, `actuator/src/main/java/org/tron/core/vm/VM.java`)

### Summary
When `allowDynamicEnergy` is active, every opcode's energy cost is scaled by a per-contract congestion `factor` before it is charged and ultimately paid for (burned/sent to the fee pool) by the calling account. The scaling is done with plain integer division, `energyCost * factor / DYNAMIC_ENERGY_FACTOR_DECIMAL - energyCost`, which floors the result on every single opcode execution. This is the same bug class as the Debita `DebitaV3Aggregator.sol:391` finding: a percentage multiplier applied to a fee/cost via integer division that always rounds down, letting the payer systematically underpay.

### Finding Description
`VM.play` computes the per-opcode dynamic-energy penalty as: [1](#0-0) 

and the CALL-family opcode cost is computed the same way in `EnergyCost.getCalculateCallCost`: [2](#0-1) 

`factor` is `contractStateCapsule.getEnergyFactor() + DYNAMIC_ENERGY_FACTOR_DECIMAL`, set in `Program.updateContextContractFactor`: [3](#0-2) 

For every opcode where `factor > DYNAMIC_ENERGY_FACTOR_DECIMAL`, `energy * factor` is floor-divided by `DYNAMIC_ENERGY_FACTOR_DECIMAL`. Whenever `energy * factor` is not an exact multiple of `DYNAMIC_ENERGY_FACTOR_DECIMAL` (the common case, since `factor` is a dynamically increasing/decreasing value derived from a `pow()`-based decay curve, not a clean multiple), the fractional remainder — up to `(DYNAMIC_ENERGY_FACTOR_DECIMAL-1)/DYNAMIC_ENERGY_FACTOR_DECIMAL` of one energy unit — is silently discarded on every opcode instead of being rounded up or accumulated. Contrast this with `RepositoryImpl.divideCeilExact`/`divideCeil`, which the codebase already uses elsewhere specifically to avoid this class of rounding-down bug for resource accounting: [4](#0-3) 

The dynamic-energy penalty path does not use this ceiling helper, so the truncation is unmitigated.

### Impact Explanation
The dynamic-energy mechanism exists to make heavily-congested/attacked contracts economically costly to call by inflating their effective energy price up to 2x (`factor` up to `DYNAMIC_ENERGY_FACTOR_DECIMAL + DYNAMIC_ENERGY_MAX_FACTOR`). Because the scaling is truncated per opcode rather than per transaction, an attacker who repeatedly invokes a targeted contract can accumulate the rounding loss across many opcodes and many calls within the same congestion cycle, paying less energy (i.e. burning less TRX / contributing less to the transaction fee pool) than the protocol's congestion-pricing formula intends. This directly undermines the anti-spam/anti-DoS economic incentive that `allowDynamicEnergy` is meant to enforce and results in the network under-collecting fees it was designed to charge, mirroring the "borrower pays less than the expected fee" impact of the reference finding.

### Likelihood Explanation
This is reachable by any unprivileged account issuing ordinary `TriggerSmartContract` transactions against a contract whose energy-factor state has been pushed above `DYNAMIC_ENERGY_FACTOR_DECIMAL` (which itself is attacker-triggerable by exceeding `DynamicEnergyThreshold` usage). No special privileges are required — it is purely a function of normal TVM execution and opcode-by-opcode energy accounting, so it will occur deterministically on essentially every call to a "penalized" contract.

### Recommendation
Round the dynamic-energy penalty calculation up (ceiling division) rather than down, or accumulate the fractional remainder across opcodes within a transaction so it isn't discarded, e.g. using the existing `divideCeil`/`divideCeilExact` pattern from `RepositoryImpl`/`ResourceProcessor`, or performing the scaling once per transaction on the aggregate energy usage instead of per opcode.

### Proof of Concept
1. Drive a target contract's cumulative energy usage above `DynamicEnergyThreshold` in a consensus cycle so `ContractStateCapsule.catchUpToCycle` raises `energyFactor`, making `factor = energyFactor + DYNAMIC_ENERGY_FACTOR_DECIMAL > DYNAMIC_ENERGY_FACTOR_DECIMAL`.
2. In the next cycle, repeatedly call the contract with opcodes whose base `energy` values, multiplied by `factor`, are not exact multiples of `DYNAMIC_ENERGY_FACTOR_DECIMAL` (trivially achievable, since opcode energy costs are small fixed constants and `factor` continuously changes via the exponential decay formula in `ContractStateCapsule.catchUpToCycle`).
3. Each such opcode execution in `VM.play` (`actuator/src/main/java/org/tron/core/vm/VM.java:69`) loses up to `(DYNAMIC_ENERGY_FACTOR_DECIMAL-1)` energy-units-worth of fractional penalty per unit, which is never billed to the caller — verifiable by comparing `energyCost * factor` (exact, BigInteger) against the actual `long` truncated result charged via `program.spendEnergyWithPenalty`.

  private long divideCeilExact(BigInteger numerator, BigInteger denominator) {
    BigInteger[] divRem = numerator.divideAndRemainder(denominator);
    long result = divRem[0].longValueExact();
    if (divRem[1].signum() > 0) {
      result = StrictMathWrapper.addExact(result, 1);
