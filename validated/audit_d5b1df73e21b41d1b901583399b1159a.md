### Title
Unbounded array allocation from attacker-controlled length in TVM precompile ABI decoding before size validation - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The Pillow CVE-2021-28675 root cause is that `PsdImageFile` trusted an attacker-supplied layer count and used it to build in-memory structures before validating it against the actual size of the input data, causing a DoS. The analogous pattern in java-tron is in the `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` helper methods used by the `ValidateMultiSign` and `BatchValidateSign` TVM precompiles: they read a `len` value directly from attacker-controlled call data via `DataWord.intValueSafe()` and immediately allocate `new byte[len][]` before any check that `len` is within a sane bound relative to the actual data size.

### Finding Description
`extractBytes32Array` reads a length word and allocates an array sized by it with no bound check at all: [1](#0-0) 

`extractBytesArray` and `extractSigArray` only bound-check the `offset` into the `words` array, not the `len` value used to size the allocation: [2](#0-1) 

`len` comes from `DataWord.intValueSafe()`, which is designed to clamp overflowing values to `Integer.MAX_VALUE` rather than reject them: [3](#0-2) 

In `BatchValidateSign.doExecute`, `extractBytes32Array` is invoked with a length word taken straight from the call-data-derived offset, with no precheck at all: [4](#0-3) 

In `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`, the only length sanity check (`sigArraySize > MAX_SIZE`) is gated behind the `VMConfig.allowTvmSelfdestructRestriction()` hard-fork switch, and even when enabled it is applied only to the signature-array length word, not to `extractBytes32Array`'s address-array length: [5](#0-4) 

Because `len` can be forced to `Integer.MAX_VALUE` (any word occupying >4 bytes or with the sign bit set is clamped by `intValueSafe`), `new byte[len][]` attempts to allocate an array of ~2^31 object references, which triggers an immediate `OutOfMemoryError` — before the subsequent `MAX_SIZE` (5 or 16) check ever runs. This mirrors the Pillow bug class (CWE-233/252): an untrusted "count" field is trusted to build a data structure before it is validated against the actual bounds of the input.

### Impact Explanation
`OutOfMemoryError` is a JVM `Error`, not an `Exception`. If it is not specifically caught by the surrounding TVM execution/energy-metering exception handlers (which typically catch `Exception`/`Throwable` subclasses like `OutOfTimeException`), it can propagate out of the executing thread. Because these precompiles (`ValidateMultiSign` at a fixed precompile address, `BatchValidateSign`) are reachable by any unprivileged account simply by deploying/calling a smart contract that invokes the precompile with crafted call data, this provides a network-reachable trigger for a resource-exhaustion condition on any full node that executes the transaction (including during block validation by all nodes), which can affect node availability/liveness.

### Likelihood Explanation
Reaching this code path requires only a single `TriggerSmartContract` call to the `ValidateMultiSign` or `BatchValidateSign` precompile address with crafted ABI-encoded input — no special privilege, staking, or witness status is needed. The likelihood of successfully forcing the huge-length branch depends on: (1) whether `VMConfig.allowTvmSelfdestructRestriction()` is active on the target network (if inactive, `extractBytesArray`/`extractSigArray` get no length precheck at all), and (2) whether `extractBytes32Array`'s address-array length is checked anywhere else in the call path — I could not fully confirm this in the available index due to truncated call-site context around `Program.java`'s precompile-dispatch and the general TVM exception-handling wrapper, so I cannot be fully certain whether an existing outer catch neutralizes the `Error` before it disrupts more than the single transaction.

### Recommendation
Add an explicit, hard sanity bound on every length value decoded from ABI-encoded precompile input in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` (e.g., reject if `len < 0` or `len > (data.length / WORD_SIZE)` before allocating), independent of the `allowTvmSelfdestructRestriction` feature flag, so that array/collection sizes are always validated against the true size of `data`/`words` before allocation — matching the Pillow fix pattern of checking claimed counts against actual available data before building in-memory structures.

### Proof of Concept
Construct a `TriggerSmartContract` call to the `BatchValidateSign` precompile address (`0x...66` per `PrecompiledContracts` address table) with ABI-encoded input where:
- `words[2]` (address-array offset pointer) points to a word position whose value is set so that `words[offset].intValueSafe()` returns `Integer.MAX_VALUE` (e.g., a 32-byte word with the top bit set or occupying more than 4 significant bytes).
- On networks where `VMConfig.allowTvmSelfdestructRestriction()` is disabled, additionally set the signature-array length word similarly to hit `extractBytesArray`/`extractSigArray` without any precheck.

Submitting this transaction causes `extractBytes32Array`/`extractBytesArray` to execute `new byte[Integer.MAX_VALUE][]`, which throws `OutOfMemoryError` during precompile execution, before the `MAX_SIZE` guard is reached. [1](#0-0)

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
