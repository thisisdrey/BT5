### Title
Unvalidated attacker-controlled offsets in `VerifyTransferProof.execute` allow out-of-bounds array reads/overflow when invoking the `verifyTransferProof` TVM precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The reported libcoap bug class is a stack-based buffer overflow in `get_split_entry`, caused by trusting length/offset fields taken from parsed input without validating them against the buffer's actual bounds before copying data into fixed-size buffers. The `VerifyTransferProof` precompiled contract in java-tron exhibits the same root-cause pattern: it derives `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` directly from attacker-supplied `data` and then uses them, offset by fixed strides, as `System.arraycopy` source indices into that same buffer — with no check that the resulting index ranges stay inside `data.length`.

### Finding Description
`VerifyTransferProof.execute` only validates the *total* length of `data` against a fixed set of allowed sizes `{2080, 2368, 2464, 2752}` [1](#0-0) . It then reads three 32-byte integers directly from caller-controlled `data` as byte offsets:

```
int spendOffset = parseInt(data, 0);
int spendAuthSigOffset = parseInt(data, 32);
int receiveOffset = parseInt(data, 64);
``` [2](#0-1) 

These offsets are fully attacker-controlled (they come from the TVM call data passed to the precompile) and are never bounds-checked against `data.length`. They are subsequently used, with fixed per-record strides, to index into `data` for repeated `System.arraycopy` calls that fill fixed-size destination arrays (`nullifier[i]`, `anchor[i]`, `spendCv[i]`, `rk[i]`, `spendProof[i]`, `spendAuthSig[i]`, `receiveCm[i]`, `receiveCv[i]`, `receiveEpk[i]`, `receiveProof[i]`):

```
int spendCount = parseInt(data, spendOffset);
int spendAuthSigCount = parseInt(data, spendAuthSigOffset);
int receiveCount = parseInt(data, receiveOffset);
...
spendOffset += 32;
for (int i = 0; i < spendCount; i++) {
  System.arraycopy(data, spendOffset + 320 * i, nullifier[i], 0, 32);
  ...
}
``` [3](#0-2) 

While `spendCount`/`receiveCount` are bounded to `[1,2]` after being read [4](#0-3) , the *offsets themselves* (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) used both to read the counts and as the base for the subsequent copy loops are never validated to be within `[0, data.length)`. Since `parseInt`/`data` are plain `byte[]`, a crafted call can set these offsets to arbitrary large or negative values (subject only to `int` parsing of a 32-byte big-endian value truncated via `intValueSafe`/similar helper), causing `System.arraycopy` source ranges to fall outside the actual `data` array — this triggers `ArrayIndexOutOfBoundsException` at best (an exception that is caught by the broad `catch (Throwable any)` at the end of `execute`) or, depending on how the offset arithmetic overflows the `int`, can also read/aliases unintended regions of `data` before failing.

Unlike the `VerifyMintProof`/`VerifyBurnProof` sibling precompiles, which use only fixed literal byte offsets and are therefore memory-safe, `VerifyTransferProof` is unique in this file in deriving copy offsets from attacker data, making it structurally analogous to `get_split_entry`'s trust in an unvalidated length/offset field pulled from input before a fixed-size buffer copy.

### Impact Explanation
This precompile is reachable by any account that can construct and broadcast a `TriggerSmartContract` (or any contract-calling) transaction that invokes the sapling shielded-transfer precompile address inside the TVM, i.e. by any unprivileged transaction sender. Although the exception is presently caught and the call degrades to returning a "false" result rather than crashing the JVM, this is still an availability/robustness defect for a security-critical zk-SNARK verification code path: a well-crafted offset can cause the copy loops to read out-of-range memory (from the perspective of the intended layout) or throw uncontrolled runtime exceptions inside a native-adjacent verification pipeline that also spawns background executor threads (`workersInConstantCall`/`workersInNonConstantCall`) per call — increasing the attack surface for resource exhaustion/exception-driven inconsistency in a code path meant to be a strict cryptographic gate for spending/creating shielded notes.

### Likelihood Explanation
High for reachability: the precompile is invoked purely by supplying attacker-chosen `data` in a normal transaction; no privileged role is required. The lack of bounds checking on `spendOffset`/`spendAuthSigOffset`/`receiveOffset` is unconditional and trivially triggerable by any caller who knows the expected calldata layout (which is public, since it must match the precompile's contract), similar to how `get_split_entry` was exploitable by any file/config supplying an out-of-range split-entry length.

### Recommendation
Validate `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` (and the derived indices `spendOffset + 320*i + …`, `receiveOffset + 288*i + …`, `spendAuthSigOffset + 64*i`) against `data.length` before use, mirroring the length checks already used elsewhere in `PrecompiledContracts` (e.g., `verifyLength` in `RLP.java` or the `data.length != SIZE` checks used by `VerifyMintProof`/`VerifyBurnProof`). Reject the call (return the "false" `Pair`) if any computed offset/length would exceed `data.length`, rather than relying on the outer `catch (Throwable any)` to swallow the resulting `ArrayIndexOutOfBoundsException`.

### Proof of Concept
Craft calldata of exactly one of the allowed sizes (e.g., 2080 bytes) where the first three 32-byte words (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) encode a value close to `Integer.MAX_VALUE` or a value that, after `+= 32` and stride multiplication, exceeds `data.length`. Submitting a `TriggerSmartContract` transaction that calls the `verifyTransferProof` precompile address with this payload drives execution into [5](#0-4) , causing `System.arraycopy` to be invoked with out-of-range indices into `data`, which can be observed as an uncaught-until-outer-catch `ArrayIndexOutOfBoundsException` inside `VerifyTransferProof.execute`.
