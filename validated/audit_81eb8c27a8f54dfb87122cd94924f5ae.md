### Title
`RecurringAirdrop.claim` leaf encoding lacks domain separation, allowing proof replay across deployments - (File: contracts/utils/RecurringAirdrop.sol)

### Summary
`RecurringAirdrop.claim` builds the Merkle leaf as `keccak256(abi.encodePacked(msg.sender, amount_))`. The leaf commits only to the claimant address and amount — it does not bind the proof to the contract address, the chain ID, the distribution token, or a distribution epoch. This is the direct on-chain analog of a hardcoded/default IV: a value that should carry a unique, per-context parameter instead defaults to a fixed, context-free encoding, so the same "ciphertext" (leaf + proof) is valid in every context where the same root exists. Any `RecurringAirdrop` deployment that the governor seeds with the same Merkle root (e.g., the same allocation list distributed on multiple chains, or a redeployed/parallel `MetAirdrop`-style contract over the same token) accepts the same proof again, letting an unprivileged user claim the allocation once per deployment.

### Finding Description
In `RecurringAirdrop.sol:52-66`:

```solidity
bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();
uint256 _claimable = amount_ - claimed[msg.sender];
```

- `claimed[]` is per-contract storage, so it provides replay protection only within one contract instance, not across instances or chains.
- Nothing in the leaf incorporates `address(this)`, `block.chainid`, or a root/epoch nonce. The proof is therefore portable: a `(account, amount, proof)` tuple valid under root R validates on every contract instance holding R.
- `RecurringAirdrop` is explicitly a generic, reusable contract (`MetAirdrop` subclasses it for `MET`/`esMET`, `contracts/MetAirdrop.sol:14-24`), so multiple live instances sharing a root is a realistic configuration — the protocol itself demonstrates the reuse pattern.
- The attacker is an unprivileged EOA listed in the tree (or anyone, since `msg.sender` is the only variable in the leaf — a leaf is self-authenticating for whatever address submits it, so no signature on "behalf of" is needed). They call `claim(amount_, proof_)` on deployment A and again on deployment B; both succeed and each pays `amount_ - claimed[msg.sender]` from its own token balance.

### Impact Explanation
Direct theft of unclaimed yield / protocol funds: a claimant drains an identical allocation from every deployment that shares the root, receiving N× their intended entitlement. The excess paid out on the secondary deployment is taken from tokens reserved for other recipients, so later legitimate claimers find the contract underfunded (permanent loss / theft of unclaimed yield for honest users). No privileged role, oracle manipulation, or flash loan is required — just an ordinary `claim` call repeated per deployment.

### Likelihood Explanation
- `RecurringAirdrop` is designed for recurring, multi-round distributions and `MetAirdrop` shows it is instantiated for real token distributions; recurring drops across L2 deployments are an expected use.
- Sharing a root across deployments is the natural operational choice when the same allocation applies everywhere (it is cheaper to publish one IPFS proofs file).
- The only "mitigation" is operational discipline (never reuse a root); nothing in the code enforces it, analogous to the `parsel` finding where the flaw is only avoided if callers supply their own IV.

### Recommendation
Bind each leaf to the deployment context, e.g.:

```solidity
bytes32 _leaf = keccak256(abi.encodePacked(block.chainid, address(this), msg.sender, amount_));
```

Alternatively include a governor-set `distributionId`/`epoch` in the leaf and bump it on each `updateMerkleRoot`, which also prevents cross-root replay within one contract if `claimed[]` semantics ever change.

### Proof of Concept
Hardhat (foundry-equivalent) sketch:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {RecurringAirdrop} from "contracts/utils/RecurringAirdrop.sol";
import {ERC20Mock} from "contracts/mock/ERC20Mock.sol";

contract AirdropReplayTest is Test {
    RecurringAirdrop airdropA;
    RecurringAirdrop airdropB; // second deployment / second chain instance
    ERC20Mock token;
    address alice = address(0xA11CE);

    function setUp() public {
        token = new ERC20Mock("RWD", "RWD", 18);
        airdropA = new RecurringAirdrop(token);
        airdropB = new RecurringAirdrop(token);
        token.mint(address(airdropA), 1000 ether);
        token.mint(address(airdropB), 1000 ether);
    }

    function test_replayAcrossDeployments() public {
        uint256 amount = 100 ether;

        // Single-leaf tree: root == leaf == keccak256(abi.encodePacked(alice, amount))
        bytes32 leaf = keccak256(abi.encodePacked(alice, amount));
        bytes32[] memory proof = new bytes32[](0);

        // Governor publishes the same root on both instances
        airdropA.updateMerkleRoot(leaf, bytes32("proofs"));
        airdropB.updateMerkleRoot(leaf, bytes32("proofs"));

        // Alice claims her allocation twice with the same proof
        vm.startPrank(alice);
        airdropA.claim(amount, proof);
        airdropB.claim(amount, proof); // replays — no domain separation
        vm.stopPrank();

        assertEq(token.balanceOf(alice), 2 * amount); // 200 ether, intended 100
    }
}
```

The same proof validates on both contracts because `keccak256(abi.encodePacked(msg.sender, amount_))` is identical in both contexts, while `claimed[]` bookkeeping is isolated per contract and cannot detect the cross-instance replay.
