### Title
Dust deposit griefing permanently saturates a victim's per-account token list, blocking all new deposits and borrows — (File: contracts/Pool.sol)

### Summary
The analog of the tiffcrop memory leak (repeated, attacker-triggered resource growth leading to denial of service) is the unbounded-by-victim growth of the per-account token lists in `Pool`. `Pool` enforces `MAX_TOKENS_PER_USER = 30` across `depositTokensOfAccount` + `debtTokensOfAccount` via the `onlyIfAdditionWillNotReachMaxTokens` modifier [1](#0-0) [2](#0-1) . Any EOA can grow a *victim's* list because `DepositToken.deposit(amount_, onBehalfOf_)` mints to an arbitrary `onBehalfOf_`, and `_mint`/`_transfer` unconditionally call `pool.addToDepositTokensOfAccount(account_)` when the recipient's balance goes from 0 to non-zero [3](#0-2) [4](#0-3) .

### Finding Description
1. `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once the combined per-account list reaches 30 entries [5](#0-4) .
2. `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` beneficiary; the attacker supplies the underlying, the victim receives the minted deposit tokens [3](#0-2) .
3. `DepositToken._transfer` also adds the token to the recipient's list, so plain `transfer(to_, 1 wei)` of dust deposit tokens works too — the sender only needs unlocked balance, and the recipient has no way to opt out [6](#0-5) [7](#0-6) .
4. There is no minimum deposit amount, no whitelist, and no consent check. Once the victim's list is full, every subsequent `_mint`/`issue`/`deposit` that would add a *new* token reverts inside `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, so the victim cannot deposit a new collateral type nor open a position in a new synthetic asset.
5. Removal is possible only by the victim actively transferring/withdrawing each dust position (`_transfer`/`_burn` remove the entry at zero balance [8](#0-7) ), but the attacker can re-fill slots in the same block the victim frees them, and each `deposit`/`transfer`/`issue` for the victim keeps reverting while the list is saturated.

### Impact Explanation
Temporary freezing of funds / liveness break: a targeted victim (e.g., a leveraged SmartFarming position or an account about to be liquidated-topped-up) is prevented from adding new collateral or issuing new debt to restore health, and cannot onboard new collateral types at all while saturated. The attacker pays only dust of each underlying; victim remediation (withdrawing dust, paying withdraw fees on 30 slots, racing re-griefing) costs strictly more than the attack. Attack cost scales linearly like the leaked-memory allocations in the CVE — each crafted input permanently consumes a scarce per-account slot.

### Likelihood Explanation
Feasibility depends on the pool listing enough distinct `DepositToken`s to approach 30 combined slots (governor caps the count, but existing Metronome pools list many collaterals plus debt tokens). Debt tokens cannot be pushed onto a victim (issue mints debt to `_msgSender` only [9](#0-8) ), so the attack fills only deposit-token slots — it is most effective on pools with many deposit tokens, or combined with the victim's existing entries. No privileged role, oracle manipulation, or trusted-remote assumption is required; `deposit`/`transfer` are permissionless and `SynthContext`/`nonReentrant`/pause flags do not stop it in normal operation.

### Recommendation
- Enforce a minimum meaningful deposit amount (e.g., reject deposits whose USD value is below `debtFloorInUsd`-style floor) so dust cannot occupy a slot.
- Alternatively, only add tokens to `depositTokensOfAccount` for self-initiated deposits (`onBehalfOf_ == _msgSender()`) or make recipient opt-in.
- Allow anyone to call a `sweepDustToken(account, token)`-style removal for below-threshold balances so victims can cheaply clear forced entries without withdraw fees.

### Proof of Concept
Hardhat sketch (fork or unit env with deployed `Pool`, `DepositToken`s `dt0..dtN`):

```solidity
function test_dustGriefing() public {
    address victim = address(0xV1C);
    IDepositToken[] memory dts = allDepositTokens(pool); // pool's listed deposit tokens
    for (uint i; i < dts.length && pool.getDepositTokensOfAccount(victim).length
         + pool.getDebtTokensOfAccount(victim).length < 30; ++i) {
        IERC20 u = dts[i].underlying();
        deal(address(u), attacker, 1); // 1 wei of underlying
        vm.startPrank(attacker);
        u.approve(address(dts[i]), 1);
        dts[i].deposit(1, victim);     // mints dust to victim, adds to their list
        vm.stopPrank();
    }
    // victim now at 30 slots: any new-token deposit or issue reverts
    vm.prank(victim);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newDepositToken.deposit(1e18, victim); // DepositTokenDoesNotExist path -> revert inside addToDepositTokensOfAccount
    vm.prank(victim);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newDebtToken.issue(1e18, victim);      // _mint -> addToDebtTokensOfAccount reverts
}
```

Setup mirrors `test/Pool.test.ts` 'should revert when reach max tokens' [10](#0-9) , except the entries are pushed onto `victim` by `attacker` via `deposit(1, victim)` instead of the victim minting them.

    ) external override whenNotPaused nonReentrant onlyIfDepositTokenExists returns (uint256 _deposited, uint256 _fee) {
        if (amount_ == 0) revert AmountIsZero();

        IERC20 _underlying = underlying;
        address _msgSender = _msgSender();

        if (_msgSender == _treasury) revert TreasuryCanNotDeposit();

        uint256 _balanceBefore = _underlying.balanceOf(_treasury);
        _underlying.safeTransferFrom(_msgSender, _treasury, amount_);
        amount_ = _underlying.balanceOf(_treasury) - _balanceBefore;

        (_deposited, _fee) = quoteDepositOut(amount_);
        if (_fee > 0) {
            _mint(_pool.feeCollector(), _fee);
        }

        _mint(onBehalfOf_, _deposited);

        emit CollateralDeposited(_msgSender, onBehalfOf_, amount_, _deposited, _fee);
    }
