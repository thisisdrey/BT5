### Title
Node crash via unhandled `IllegalArgumentException` from invalid EC point decompression during transaction/block signature recovery - (File: `crypto/src/main/java/org/tron/common/crypto/ECKey.java`)

### Summary
Signature recovery in `ECKey.recoverPubBytesFromSignature` decompresses an elliptic-curve point derived from attacker-supplied signature `r`/`s`/`v` values via `decompressKey`, which calls BouncyCastle's `CURVE.getCurve().decodePoint(compEnc)`. [1](#0-0) [2](#0-1) 
This decoding throws `IllegalArgumentException` (an unchecked exception) whenever the derived `x` coordinate does not correspond to a valid curve point (roughly half of arbitrary inputs), analogous to the Nimiq bug where `voting_key.uncompress().unwrap()` panics on an invalid compressed key supplied by an untrusted peer.

### Finding Description
`ECKey.signatureToKeyBytes` / `signatureToAddress` are declared to throw only `SignatureException`, but the underlying `recoverPubBytesFromSignature -> decompressKey -> decodePoint` call can throw an unchecked `IllegalArgumentException` instead, which is never declared or expected by callers. [3](#0-2) [4](#0-3) 

This code path is reached from transaction signature validation. `TransactionCapsule.validatePubSignature` only catches `SignatureException | PermissionException | SignatureFormatException`, not `RuntimeException`/`IllegalArgumentException`: [5](#0-4) 

Similarly, `BlockCapsule.validateSignature` (used for witness block-signature checks, and indirectly reachable through the same signature-recovery utility) only catches `SignatureException`: [6](#0-5) 

An attacker can craft a syntactically valid 65-byte transaction signature (any `r`,`s` value passing basic range checks and a `v` byte in `[27,34]`) whose recovered `x` coordinate is not on the secp256k1 curve. This is broadcastable by any unprivileged client through the normal `BroadcastTransaction` path, which flows into `Manager.pushTransaction` → `trx.validateSignature(...)`: [7](#0-6) 
An uncaught `IllegalArgumentException` will propagate out of this call, bypassing the intended `ValidateSignatureException` handling and crashing/aborting the processing thread instead of being rejected as a normal invalid-signature error.

### Impact Explanation
An unauthenticated network participant can craft and broadcast a single transaction with a malformed but well-formed-looking signature to make signature verification throw an unchecked `IllegalArgumentException` instead of the expected `SignatureException`/`ValidateSignatureException`. Because this exception type is not handled anywhere along the `pushTransaction` / block-application signature-verification path, it can abort transaction processing or block validation threads unexpectedly, which is a node crash/halt condition of the same class as the referenced Nimiq advisory (panic on invalid compressed key during untrusted-input processing).

### Likelihood Explanation
High. Roughly half of arbitrary `(r, s, v)` byte combinations will produce an `x` value that BouncyCastle's `decodePoint` rejects as not on curve, so a trivial brute-force/grinding attacker (or even random malformed input) reliably triggers this within a small number of attempts, and the entry point (submitting a transaction with an attached signature) requires no special privileges.

### Recommendation
Wrap the `decodePoint` call in `ECKey.decompressKey` (and the analogous SM2 method) to catch `IllegalArgumentException`/`RuntimeException` from BouncyCastle and translate it into the checked `SignatureException`/return `null` (consistent with the existing `null`-return convention for "could not recover key"), so all callers (`TransactionCapsule.validatePubSignature`, `BlockCapsule.validateSignature`) continue to treat malformed signatures as normal validation failures rather than uncaught runtime exceptions.

### Proof of Concept
1. Construct a `Transaction` with any valid contract (e.g. `TransferContract`).
2. Attach an attacker-controlled 65-byte signature `[r(32) | s(32) | v(1)]` where `v` is in the accepted range but `r` is chosen (via simple iteration) such that `x = r (or r + n)` is not a valid x-coordinate on secp256k1 (i.e., `x^3 + 7 mod p` is not a quadratic residue).
3. Broadcast the transaction via the standard RPC/gRPC `BroadcastTransaction` path, invoking `Manager.pushTransaction` → `TransactionCapsule.validateSignature` → `validatePubSignature` → `ECKey.signatureToAddress` → `recoverPubBytesFromSignature` → `decompressKey`.
4. `CURVE.getCurve().decodePoint` throws `IllegalArgumentException("Invalid point compression")`, which is not caught by `validatePubSignature`'s `catch (SignatureException | PermissionException | SignatureFormatException e)` block, propagating up as an unexpected runtime exception in the transaction-processing thread.

        messageHash.length);
    int header = sig.v;
    // The header byte: 0x1B = first key with even y, 0x1C = first key
    // with odd y,
    //                  0x1D = second key with even y, 0x1E = second key
    // with odd y
    if (header < 27 || header > 34) {
      throw new SignatureException("Header byte out of range: " + header);
    }

      header -= 4;
    }

        messageHash);
    if (key == null) {
      throw new SignatureException("Could not recover public key from " +
          "signature");
    }
    return key;
  }
