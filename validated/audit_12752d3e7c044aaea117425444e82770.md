### Title
Missing bound check on attacker-controlled ABI array-length field enables OOB read / uncontrolled allocation in `BatchValidateSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray`, `extractSigArray`, and `extractBytes32Array` read a "count" word directly from fully attacker-controlled calldata and then iterate over it to index into the `DataWord[] words` buffer, without ever validating that the count fits within the bounds of that buffer. This mirrors the root cause of CVE-2025-21741 (ipheth usbnet): a count/length field taken from an untrusted, fixed-size header is used to drive a loop without limiting it to what the buffer can actually hold.

### Finding Description
`extractBytesArray` and `extractSigArray` only check that the starting `offset` itself is inside `words.length`, not that `offset + len` (the attacker-supplied count) stays within bounds: [1](#0-0) [2](#0-1) 

`extractBytes32Array` has no bound check at all, not even on `offset`: [3](#0-2) 

These helpers are invoked from `BatchValidateSign.doExecute`, where `words[1]`/`words[2]` (offsets) and the "count" words they point to are taken directly from `data`, the raw calldata passed to the precompile by any TVM `CALL`: [4](#0-3) 

The only size guard (`sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE`) is gated behind `VMConfig.allowTvmSelfdestructRestriction()`, and even that guard is only applied to `extractSigArray`'s path — `extractBytes32Array` (used for `addresses`) is never subjected to any pre-allocation size check regardless of that flag. `intValueSafe()` in `DataWord` can return any value up to `Integer.MAX_VALUE` for a fully attacker-chosen 32-byte word: [5](#0-4) 

An attacker can therefore choose an in-bounds `offset` and place an arbitrarily large integer at that word position as the "length" of the byte/signature/address array. `new byte[len][]` will then attempt to allocate a huge object array (e.g. billions of references), and/or the subsequent loop `words[offset + i + 1]` will run past the real end of `words`, throwing `ArrayIndexOutOfBoundsException` — the direct analog of the kernel's DPE OoB read, where a header-declared count is trusted beyond the actual data extent.

### Impact Explanation
Both failure modes are reachable from a single, ordinary signed transaction (a `TriggerSmartContract`/`TriggerConstantContract` call into any contract that in turn calls the `BatchValidateSign` precompile address, or a direct call if callable), i.e. from an unprivileged contract caller/deployer. While the outer `execute()` wraps `doExecute()` in `catch (Throwable t)`, this does not prevent the JVM from first attempting the requested allocation: [6](#0-5) 
A multi-gigabyte array-of-references allocation attempt can trigger heavy GC activity/`OutOfMemoryError` on the node processing the block, degrading or halting block processing for that node (node crash/unresponsiveness), which the task's impact criteria explicitly accept ("node crash or halt"). This is reachable by any account able to submit a smart-contract transaction with enough energy to reach the precompile call.

### Likelihood Explanation
Likelihood depends on the state of `VMConfig.allowTvmSelfdestructRestriction()` (a chain-parameter/proposal-gated flag) and `VMConfig.allowTvmOsaka()`'s `isValidAbiEncoding` gate, both of which only partially or in some code paths (e.g. `extractBytes32Array`) do not constrain the count field against the real buffer size at all. On any deployment/period where these governance flags are not yet enabled (or for the `addresses` extraction path which is unconditionally unguarded), the bug is trivially triggerable with a single crafted calldata blob to the precompile. This makes it Medium-to-High likelihood depending on chain-parameter activation state, which I could not fully confirm was universally enabled given the codebase's feature-flag/proposal-based upgrade model (`ProposalUtil.java`, `DynamicPropertiesStore.java`).

### Recommendation
In `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, validate that the parsed `len` does not exceed the remaining number of elements in `words` (i.e., `offset + len + 1 <= words.length`) before allocating `bytesArray`/`bytes32Array`, mirroring the kernel fix of "limit the number of processed [entries] to the amount that fits into the fixed-size header." Apply the existing `MAX_SIZE` guard unconditionally (not only under `allowTvmSelfdestructRestriction()`), and extend it to cover the `addresses` (`extractBytes32Array`) path as well, independent of feature flags.

### Proof of Concept
1. Craft a `data` payload for `BatchValidateSign` such that `words[1]` (signature array offset) points to a valid in-bounds word, but the word at that offset (the encoded array length) is set to a very large positive 32-bit value (e.g. `0x7FFFFFFF`).
2. Deploy/call a contract that invokes the `BatchValidateSign` precompile address with this payload via `STATICCALL`/`CALL`.
3. Observe that `extractBytesArray`/`extractSigArray` executes `new byte[0x7FFFFFFF][]`, attempting a multi-gigabyte allocation, or that the subsequent loop indexes `words[]` past its real length — both trigger uncontrolled resource consumption or an unhandled bounds violation during transaction execution on the node.

    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
