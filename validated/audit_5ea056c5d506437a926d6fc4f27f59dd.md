### Title
Zero priority floor is indistinguishable from "no floor," letting the scheduler's saturation-drop QoS bypass silently disable itself - ([File: core/src/sigverify.rs])

### Summary
`SchedulerPriorityFloor` is a shared `u64` published by the banking-stage scheduler to sigverify workers so that, once the transaction buffer is saturated, arrivals priced at-or-below the queue-min priority get dropped pre-sigverify to shed load. The value `0` is used both as the "disabled / not saturated" sentinel and as a legitimately computed minimum priority. When the container is saturated and its lowest-priority transaction happens to have priority `0` (which the priority formula can naturally produce), the published floor is `0`, and sigverify's check `if floor > 0 { apply_priority_floor_to_batch(...) }` treats that exactly like "no floor is set," so the drop-on-saturation protection is silently skipped.

### Finding Description
`SchedulerPriorityFloor::clear()` sets the floor to `0` as its "unset" default [1](#0-0) . `update_scheduler_priority_floor` in the scheduler controller republishes the floor from `container.get_min_max_priority()` whenever the container is saturated, defaulting to `0` only when unsaturated or empty — but it does not distinguish a legitimately-computed minimum priority of `0` from the "not saturated" case: both produce the same wire value `0`. [2](#0-1) 

On the consuming side, `run_transaction_task` in sigverify only applies the drop when `floor > 0`:
```rust
if let Some(floor) = state.priority_floor.as_ref() {
    let floor = floor.get();
    if floor > 0 {
        let ((dropped, all_below), priority_floor_time_us) = measure_us!(
            apply_priority_floor_to_batch(&mut batch, floor, &working_bank)
        );
        ...
    }
}
``` [3](#0-2) 

`apply_priority_floor_to_batch` drops packets whose computed priority is `<= floor` [4](#0-3) , and priority itself is `reward * MULTIPLIER / (cost + 1)`, which is `0` whenever the computed reward (base fee reward + prioritization fee reward) is `0` — this is a real, reachable value, not just theoretical, as shown by the existing test `priority_is_zero_when_base_and_priority_fees_are_zero` [5](#0-4) [6](#0-5) .

This is the same bug class as the GMX report: a sentinel meaning "empty/no value" is overloaded onto a value (`0`) that the underlying domain can legitimately produce, so a legitimately-computed data point silently reverts to fallback/disabled behavior instead of being honored.

### Impact Explanation
When the buffer is saturated (i.e., the validator is already under load and relying on this mechanism to shed low-value traffic before spending sigverify/CPU cycles on it) and the current queue-min priority happens to be exactly `0` — trivially achievable by an unprivileged attacker submitting transactions with `compute_unit_price = 0` and no meaningful base-fee reward (e.g. against a bank/cluster with low or zero effective lamports-per-signature reward, or any transaction whose reward rounds to zero) — the published floor collapses to `0`. Sigverify then treats this identically to "priority floor disabled," so it stops dropping at-or-below-floor packets pre-sigverify entirely, even though the scheduler has explicitly signaled saturation. This is a QoS-evasion condition: the exact spam that the floor mechanism is designed to shed under load is instead let through into full signature verification and banking-stage buffering during the exact overload window when the protection is needed, degrading the anti-DoS purpose of the mechanism.

### Likelihood Explanation
Reachable by any unprivileged client sending ordinary transactions (no special privileges, no validator/operator role) via the normal QUIC/TPU ingest path into sigverify. It requires the buffer to already be near saturation and the minimum-priority transaction in the container to be exactly `0`, which is a normal, easily-produced value for the priority formula, not a contrived edge case.

### Recommendation
Do not overload `0` as both "no floor" and "a legitimate zero priority." Use an explicit `Option<u64>` (or `AtomicU64` plus a separate atomic/bit flag, or a sentinel like `u64::MAX` for "unset" since priorities are naturally bounded well below that) in `SchedulerPriorityFloor` so sigverify can distinguish "floor not published/disabled" from "floor is legitimately zero," and always apply the drop check when a floor has actually been published, regardless of its numeric value.

### Proof of Concept
1. Drive the banking-stage transaction container to saturation (e.g., flood with many low-priority transactions until `SaturationState::update` reports saturated), causing `update_scheduler_priority_floor` to compute and publish a floor from `container.get_min_max_priority()`.
2. Ensure the current minimum-priority transaction retained in the container has priority `0` — trivially arranged by submitting `compute_unit_price = 0` transactions (see `priority_is_zero_when_base_and_priority_fees_are_zero` in `core/src/transaction_priority.rs`, confirming priority `0` is a realistic, reachable value).
3. Continue sending additional zero/low-priority packets to the TPU ingest path. In `core/src/sigverify.rs::run_transaction_task`, `state.priority_floor.get()` returns `0`, and the `if floor > 0` guard is false, so `apply_priority_floor_to_batch` is never invoked — the packets bypass the saturation-drop entirely and proceed to full sigverify/forwarding, exactly the behavior the floor mechanism was meant to prevent while the scheduler is saturated.

#[derive(Debug)]
pub struct SchedulerPriorityFloor(AtomicU64);

impl SchedulerPriorityFloor {
    pub fn new() -> Self {
        Self(AtomicU64::new(0))
    }

    pub fn set(&self, floor: u64) {
        self.0.store(floor, Ordering::Relaxed);
    }

    pub fn clear(&self) {
        self.set(0);
    }

    pub fn get(&self) -> u64 {
        self.0.load(Ordering::Relaxed)
    }
}

    /// Update the scheduler priority floor.
    ///
    /// Semantics: when the retained scheduler buffer is nearly full, drop
    /// arrivals that are at-or-below the current queue-min priority, i.e. no
    /// better than what the bounded scheduler candidate set would evict.
    fn update_scheduler_priority_floor(&mut self, num_dropped_on_capacity: usize) {
        let buffer_size = self.container.buffer_size();
        let saturated = self
            .saturation_state
            .update(buffer_size, num_dropped_on_capacity);
        let priority_floor = if saturated {
            self.container
                .get_min_max_priority()
                .map_or(0, |(min, _)| min)
        } else {
            0
        };

        self.saturation_state.publish_floor(priority_floor);
    }

```rust
fn apply_priority_floor_to_batch(
    batch: &mut PacketBatch,
    floor: u64,
    bank: &Bank,
) -> (usize, bool) {
    let mut dropped: usize = 0;
    let mut any_kept = false;
    for mut packet in batch.iter_mut() {
        if packet.meta().discard() {
            continue;
        }
        let Some(data) = packet.data(..) else {
            // Zero-length or otherwise unreadable: leave to downstream
            // stages to reject.
            any_kept = true;
            continue;
        };
        // Unparseable packets are kept and left for downstream rejection.
        match calculate_priority_from_bytes(bank, data) {
            Some(priority) if priority <= floor => {
                packet.meta_mut().set_discard(true);
                dropped = dropped.saturating_add(1);
            }
            _ => any_kept = true,
        }
    }
    (dropped, !any_kept)
}

pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
    let fee_details = solana_fee::calculate_fee_details(
        transaction,
        bank.fee_structure().lamports_per_signature,
        transaction_configuration.priority_fee_lamports,
        bank.fee_features(),
    );
    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    (
        reward
            .saturating_mul(MULTIPLIER)
            .saturating_div(cost.saturating_add(1)),
        cost,
    )
}
