### Title
Missing domain separation between transaction-signature digests and the `ValidateMultiSign` TVM precompile digest enables cross-context signature reuse - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
TRON account permissions use raw, un-prefixed SHA-256 digests for ECDSA signature verification in two independent contexts that share the same on-chain `Permission`/`Key` weight table: (1) ordinary transaction broadcast authorization, and (2) the `ValidateMultiSign` TVM precompile that any smart contract can call to authenticate an arbitrary attacker-supplied 32-byte message against an account's permission. Neither digest includes a type tag or context prefix, so — exactly as in the Meson report — a signature that is valid in one context can, given enough attacker-controlled degrees of freedom, be engineered to also be valid in the other, letting a single signature authorize two unrelated actions under the same key/permission weight.

### Finding Description
An ordinary TRON transaction is signed over `hash = sha256(rawData)` with no domain tag, and its weight is checked with `TransactionCapsule.checkWeight(permission, sigs, hash, ...)`: [1](#0-0) [2](#0-1) 

The `ValidateMultiSign` TVM precompile — reachable from any contract call, i.e. any unprivileged transaction/contract-call sender — builds a *different* digest from fully attacker-supplied inputs (`address`, `permissionId`, and a free 32-byte `data` word taken directly from calldata), with no type prefix either, and checks it against the *same* `Permission` structure via `TransactionCapsule.getWeight`: [3](#0-2) [4](#0-3) 

Both paths ultimately call `SignUtils.signatureToAddress`/`ECKey.recoverPubBytesFromSignature` on a bare 32-byte SHA-256 digest with no "\x19TRON Signed Message" or type-tag prefix distinguishing "this is a transaction" from "this is an arbitrary application message": [5](#0-4) [6](#0-5) 

Because `data` in `ValidateMultiSign` is a fully free 256-bit value chosen by whoever calls the precompile, and a signable transaction's `raw_data` (via `ref_block_bytes`, `ref_block_hash`, `expiration`, `timestamp`, `fee_limit`, and unconstrained smart-contract call `data`/memo fields) also has enormous freedom, an attacker who controls both sides offline (exactly as "Alice" does in the Meson scenario) can search for a transaction encoding `T` and a `ValidateMultiSign` triple `(address, permissionId, data)` such that:

```
sha256(rawData_of_T) == sha256(address || permissionId || data)
```

Once such a collision is found, a single ECDSA signature produced by the account owner for what looks like an innocuous transaction `T` is simultaneously a valid `ValidateMultiSign` authorization for `(address, permissionId, data)` — because both verification paths recover the same signer address and check it against the identical `Permission`/`Key` weight table (`account.getPermissionById(permissionId)`), used at line 1083 of `PrecompiledContracts.java` and identically at line 485 of `TransactionCapsule.java`.

### Impact Explanation
Any TRC-20/TRC-10 vault, bridge, escrow, or DAO contract that relies on `validatemultisign()` to authenticate off-chain-approved actions (a common pattern for multisig-gated withdrawals) trusts that a signature passed to the precompile was created specifically to authorize that message. If an attacker can obtain (via social engineering, or simply by asking the victim to sign a legitimate-looking transaction) a signature that also collides with a `ValidateMultiSign` digest under the victim's account/permission, the attacker can replay that same signature to make an unrelated contract believe the victim approved an arbitrary `data` payload (e.g., a withdrawal authorization), leading to unauthorized account operations and theft of funds — the same class of impact identified in the original Meson report (draining both sides of a transaction using one signature).

### Likelihood Explanation
Exploitation requires the same kind of offline, attacker-controlled birthday-style search described in the original report (~2^60–2^70 hash evaluations, per the auditors' own estimate for the analogous Meson construction). This is expensive but has been demonstrated as tractable for structurally similar untyped-message collisions; the root cause — signing bare, unprefixed SHA-256 digests across two semantically different message spaces that share the same key/weight verification (`getWeight`/`checkWeight`) — is identical to the flagged bug class. No privileged role is needed: the precompile is reachable by any transaction/contract-call sender, and the transaction whose signature is reused can be an ordinary transfer/contract-call the victim signs for unrelated reasons.

### Recommendation
Add an explicit, unambiguous domain-separation prefix to every digest that is fed into `ecrecover`/`SignUtils.signatureToAddress`, distinguishing transaction-signing digests (`TransactionCapsule.sign`/`checkWeight`) from `ValidateMultiSign`/precompile message digests, e.g. `sha256("TRON_TX" || rawData)` vs `sha256("TRON_VALIDATE_MULTISIGN" || address || permissionId || data)`, so that no valid encoding in one message space can ever equal a valid encoding in the other. Long term, document and enforce a single canonical, injective encoding scheme (with type tags) for every message type that can be verified against an account's `Permission` keys, consistent with EIP-712-style typed-data separation.

### Proof of Concept
1. Deploy (or identify) a contract that calls the `ValidateMultiSign` precompile (`address address, uint256 permissionId, bytes32 data, bytes[] signatures`) to gate a sensitive action (e.g., withdrawal), as exercised in `ValidateMultiSignContractTest` (`framework/src/test/java/org/tron/common/runtime/vm/ValidateMultiSignContractTest.java:34-156`).
2. Offline, an attacker who controls the victim's account address and its permission id iterates over many candidate real transactions `T` (varying `ref_block_bytes`, `ref_block_hash`, `expiration`, `timestamp`, `fee_limit`, and/or contract call `data`) computing `sha256(rawData_of_T)`, and in parallel iterates over candidate `data` values for `ValidateMultiSign`, computing `sha256(address || permissionId || data)`, until a collision is found between the two sets (≈2^60–2^70 evaluations, matching the effort estimated in the source report for the structurally identical Meson bug).
3. The attacker convinces the victim (or otherwise obtains the victim's signature) to sign transaction `T` via `TransactionCapsule.sign` (`chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java:589-595`), obtaining signature `sig`.
4. The attacker submits `sig` to the vault/bridge contract's `validatemultisign(address, permissionId, data, [sig])` call; `PrecompiledContracts.ValidateMultiSign.execute` recovers the victim's address from `sig` against `hash = sha256(address||permissionId||data)` (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1062-1098`), which now matches by construction, and the weight check passes, authorizing the attacker-chosen `data` payload using a signature the victim believed only authorized transaction `T`.

  private static byte[] recoverAddrBySign(byte[] sign, byte[] hash) {
    byte[] out = null;
    if (ArrayUtils.isEmpty(sign) || sign.length < 65) {
      return new byte[0];
    }
    try {
      Rsv rsv = Rsv.fromSignature(sign);
      SignatureInterface signature = SignUtils.fromComponents(rsv.getR(), rsv.getS(), rsv.getV(),
          CommonParameter.getInstance().isECKeyCryptoEngine());
      if (signature.validateComponents()) {
        out = SignUtils.signatureToAddress(hash, signature,
            CommonParameter.getInstance().isECKeyCryptoEngine());
      }
    } catch (Throwable any) {
      logger.info("ECRecover error", any.getMessage());
    }
    return out;
  }

  public static byte[] signatureToKeyBytes(byte[] messageHash,
      ECDSASignature sig) throws SignatureException {
    check(messageHash.length == 32, "messageHash argument has length " +
        messageHash.length);
    int header = sig.v;
    // The header byte: 0x1B = first key with even y, 0x1C = first key
    // with odd y,
    //                  0x1D = second key with even y, 0x1E = second key
    // with odd y
    if (header < 27 || header > 34) {
      throw new SignatureException("Header byte out of range: " + header);
    }
    if (header >= 31) {
      header -= 4;
    }
    int recId = header - 27;
    byte[] key = ECKey.recoverPubBytesFromSignature(recId, sig,
        messageHash);
    if (key == null) {
      throw new SignatureException("Could not recover public key from " +
          "signature");
    }
    return key;
  }
