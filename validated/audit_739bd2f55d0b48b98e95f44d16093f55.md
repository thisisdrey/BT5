## Analysis

The Reserve Protocol finding concerns the lack of a two-step confirm process for changing a critical access-control field — `owner` — meaning a single mistaken transaction can lock an account holder out of a contract forever. In java-tron, an analogous single-step, irrevocable change of an account's `owner` signing authority exists in `AccountPermissionUpdateActuator`.

### Title
Single-step, unconfirmed replacement of an account's Owner permission can permanently lock the account - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateContract` lets an account holder replace its `owner` (and `active`/`witness`) `Permission` in a single atomic step. `execute()` immediately overwrites the account's `ownerPermission` via `AccountCapsule.updatePermissions()` with no staged/pending state and no acceptance step by the new key holder(s).

### Finding Description
`AccountPermissionUpdateActuator.execute()` unpacks the `AccountPermissionUpdateContract` and calls `account.updatePermissions(owner, witness, actives)` directly, which replaces the account's `OwnerPermission` field in the same transaction: [1](#0-0) 

The underlying capsule mutation is a direct overwrite of the owner permission, with no staging, no separate acceptance/confirmation step by the new key(s), and no rollback path: [2](#0-1) 

`validate()` only checks structural correctness of the new `Permission` (key format validity via `DecodeUtil.addressValid`, threshold > 0, weight sums, key count limits, permission name length, and operations bitmap for Active permissions) — it never verifies that the new owner keys are reachable/controlled by anyone, nor does it require any acknowledgment transaction from the new key holders before the change takes effect: [3](#0-2) 

Because the `owner` `Permission` type governs which keys can authorize *any* future transaction from the account (including a corrective `AccountPermissionUpdateContract` to fix a mistake), a single erroneous update — e.g., a typo'd key address, an unintended threshold, or accidentally dropping a previously-authorized key — permanently removes the original owner's ability to control the account, exactly mirroring the `_transferOwnership()` one-step risk described in the external report.

### Impact Explanation
If the new `owner` `Permission` set in a single `AccountPermissionUpdateContract` transaction does not include a key the account holder actually controls (e.g., wrong address entered, or insufficient threshold reachable by held keys), the account becomes permanently locked: no valid signature combination can ever satisfy the new owner permission threshold, so no subsequent `AccountPermissionUpdateContract` (or any other transaction requiring owner permission) can be submitted to correct it. This constitutes permanent freezing of the account and all TRX/TRC10/frozen-resource balances associated with it, matching the "permanent freezing of funds" impact criterion.

### Likelihood Explanation
This is directly reachable by any unprivileged transaction broadcaster: it requires only crafting and signing one `AccountPermissionUpdateContract` transaction with the current owner permission, which is a standard, publicly documented operation (also exposed via the `AccountPermissionUpdateServlet` HTTP endpoint and Wallet API): [4](#0-3) 
No malicious actor or privileged role is required — the risk is a user/operator error (fat-fingered address, wrong threshold, dropped key) with no built-in safety net, same class of accidental, high-severity mistake described in the Reserve Protocol report.

### Recommendation
Introduce a two-step confirmation flow for `AccountPermissionUpdateContract` when it changes the `owner` `Permission`: stage the proposed new owner permission and require a subsequent transaction signed under the *proposed* keys (or an explicit timelocked acceptance) before `AccountCapsule.updatePermissions()` commits the change, mirroring `Ownable2Step`-style patterns. At minimum, add stronger pre-commit validation/warnings (e.g., simulate that the current signer's key(s) remain valid under the new threshold, or require an explicit re-confirmation transaction) to reduce the chance of irreversible self-lockout.

### Proof of Concept
1. Alice controls account `A` with a normal `Owner` permission (single key, threshold 1).
2. Alice broadcasts a single `AccountPermissionUpdateContract` transaction, signed with her current owner key, setting a new `owner` `Permission` whose `Key` list contains a mistyped/incorrect (but validly-formatted) address with threshold 1.
3. `AccountPermissionUpdateActuator.validate()` passes because the address passes `DecodeUtil.addressValid` and all structural checks in `checkPermission()`, without checking Alice actually controls the given key.
4. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)`, replacing the owner permission in one step: [5](#0-4) 
5. Alice no longer has any key satisfying the new owner permission threshold; no transaction requiring owner authority (including a corrective `AccountPermissionUpdateContract`) can ever be signed for account `A` again — all balances and resources under `A` are permanently frozen.

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
