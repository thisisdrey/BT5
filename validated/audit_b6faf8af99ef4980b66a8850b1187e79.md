### Title
Unauthenticated `RecvError` packet forces immediate tunnel teardown without checking pending/in-flight state - (File: outside.go)

### Summary
Nebula's `RecvError` message type is processed as an unencrypted, unauthenticated control packet — before any Noise handshake completion check, certificate verification, or AEAD decryption is required. `handleRecvError` uses it to unconditionally tear down an established tunnel via `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, with no check for pending critical operations (in-flight relay establishment, active data transfer, or a concurrently-in-progress re-handshake) that the GMX `emergencyPause` report warns about — an unrestricted "halt" primitive with no pre-condition check on the state it disrupts.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` straight to `f.handleRecvError` before decryption/authentication of the payload is required: [1](#0-0) 

`handleRecvError` gates only on a coarse config policy (`always`/`never`/`private`) and a source-address match against the hostinfo's last known remote — it performs no check on whether the hostinfo has pending relay state, cached outbound packets, or is in the middle of establishing/re-establishing crypto material before calling `closeTunnel`: [2](#0-1) 

The teardown path itself is unconditional — `closeTunnel` deletes the hostinfo and clears lighthouse-learned state with no state machine check: [3](#0-2) 

This mirrors the GMX bug class precisely: a control action (`emergencyPause` / here, `closeTunnel` via `RecvError`) is executed without verifying that no critical, multi-step operation (an active relay handshake, cached-but-undelivered packets, or a fresh re-handshake in progress) is currently relying on that state. In GMX, this stranded deposited funds because the callback that would have completed the operation could no longer succeed; in Nebula, this strands in-flight relay establishment (`Requested`/`PeerRequested` relay states in `relay_manager.go`) and cached packets (`HandshakeHostInfo.packetStore` in `handshake_manager.go`) and forces a full re-handshake, at a time chosen by whoever can trigger the `RecvError` condition.

### Impact Explanation
An attacker (on-path, or one who can send a spoofed/replayed `RecvError` packet matching the current `RemoteIndex` and the victim's last-known-remote address) can force `closeTunnel` + `DeleteHostInfo` at a moment they choose, e.g. mid-handshake completion, mid-relay establishment, or during an active data burst. Because the check performed is only a source-address match (`hr.IsValid() && hr != addr`) and a coarse config toggle, it does not validate that this teardown is safe relative to in-progress protocol steps. This is a remote state-poisoning / denial-of-service vector: it can silently drop an in-flight session and cause packet loss and forced re-handshakes, exactly analogous to the "loss of funds" impact in the GMX report, where a pause action executed without checking pending critical state caused loss of user funds because callbacks could no longer complete correctly.

### Likelihood Explanation
Reachability requires no CA-signed certificate and no completed handshake — `RecvError` is processed prior to any certificate/authentication step, gated only by `f.acceptRecvErrorConfig.ShouldRecvError(addr)`, which defaults to `"always"` (accept from anyone) unless explicitly configured to `"private"` or `"never"`. The remaining barrier is guessing/observing the 32-bit `RemoteIndex` and a matching source address, which is feasible for any on-path observer (packet capture) or in a source-spoofing-capable network position, without ever holding a valid Nebula certificate.

### Recommendation
- Before tearing down via `handleRecvError`, check whether the targeted hostinfo has pending critical operations in flight (e.g., relay states other than `Established`, non-empty cached `packetStore`, or a handshake completion race window) and defer/ignore the teardown, or require additional proof of authenticity (e.g., requiring the packet to be tied to a value only derivable from the current cipher state) before acting.
- Consider rate-limiting/cooldown on `RecvError`-triggered teardown per hostinfo so a single spoofed/observed packet cannot immediately destroy an active tunnel.
- Tighten the default `listen.accept_recv_error` policy away from unconditionally accepting error packets from any source address.

### Proof of Concept
Conceptual PoC (requires an on-path attacker who can observe/spoof the source address matching the victim's active remote, and knows/derives `h.RemoteIndex`):
1. Establish/observe a live Nebula tunnel between hosts A and B; capture the `RemoteIndex` A uses to identify B (visible on any encrypted data packet header, no decryption required).
2. Craft an unencrypted `header.RecvError` packet with that `RemoteIndex`, spoofed to appear to come from B's current UDP address, and send it to A while B is actively transmitting data or during a relay-establishment window.
3. A's `handleRecvError` passes the address check, calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` unconditionally, tearing down the tunnel regardless of any pending relay/data-in-flight state — reproducing the "action taken without checking pending critical state" root cause from the GMX report. func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
