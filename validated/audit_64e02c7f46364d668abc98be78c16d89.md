Audit Report

## Title
`process_delivery_receipt` ignores the `DeliveryReceipt.success` flag and unconditionally pays the relayer reward for failed Ethereum-side message execution - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` containing a `success: bool` field that indicates whether the dispatched command actually executed successfully on the Ethereum Gateway contract, but this field is never checked before paying the relayer reward via `T::RewardPayment::register_reward` and permanently removing the `PendingOrder`. This decouples relayer rewards from actual successful message delivery/execution.

## Finding Description
`submit_delivery_receipt` is a public, unprivileged, signed extrinsic that verifies a genuine Ethereum event log/proof and decodes it into a `DeliveryReceipt` via `T::Verifier::verify` and `DeliveryReceipt::try_from` [4](#0-3) . The `DeliveryReceipt` struct is decoded directly from the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event, which explicitly carries a `success` flag indicating whether command execution on the Gateway succeeded or reverted [5](#0-4) .

`process_delivery_receipt` only validates `receipt.gateway` against `T::GatewayAddress` and checks that a `PendingOrder` exists for `receipt.nonce`; it never reads or enforces `receipt.success` before paying `order.fee` via `T::RewardPayment::register_reward` and calling `<PendingOrders<T>>::remove(nonce)` [2](#0-1) . The `PendingOrder` struct persisted in storage also retains no success/completion semantics — only `nonce`, `block_number`, and `fee` — so there is no way to distinguish a genuinely delivered-and-executed message from one that reverted on Ethereum [1](#0-0) . A codebase-wide search confirms `success` is never referenced anywhere else in the pallet or its tests, meaning no downstream logic compensates for this omission.

This violates the required invariant that message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically — here settlement (reward payment + order removal) proceeds regardless of whether execution succeeded.

## Impact Explanation
This allows unbacked reward payout on BridgeHub for messages that did not execute successfully on Ethereum: relayer rewards are decoupled from delivered value. Any ordinary relayer submitting a genuine, correctly-proven event log for a message whose dispatched command failed on Ethereum (`success = false`, e.g. due to insufficient dispatch gas relative to `GasMeter::maximum_dispatch_gas_used_at_most`, or any legitimate execution-time revert) is unconditionally paid the full `order.fee`, and the order is permanently closed via `PendingOrders::remove`, precluding any reconciliation or retry. This matches the "duplicate settlement or payout" / "theft or unbacked mint or unlock" impact categories.

## Likelihood Explanation
Likelihood is Medium: it requires no privileged actor, malicious peer, or compromised prover — any relayer submitting a genuine, correctly-proven Ethereum event for a message whose execution failed is sufficient to trigger the flawed path. Command execution failures on Ethereum (out-of-gas dispatch, downstream reverts) are a normal, non-exotic operational occurrence in bridge processing, making the precondition realistically reachable and repeatable.

## Recommendation
1. Add `ensure!(receipt.success, Error::<T>::DeliveryFailed)` (or an explicit failure branch) in `process_delivery_receipt` before paying any reward.
2. Separate order resolution from reward payment: only invoke `T::RewardPayment::register_reward` when `receipt.success == true`; on failure, emit a distinct event (e.g., `MessageDeliveryFailed`) and handle fee refund/retry logic explicitly.
3. Persist enough context in `PendingOrder` (e.g., `topic`) to cross-check `receipt.topic` against the original committed message for the given nonce.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrders[nonce] = { nonce, fee, block_number }` with non-zero `fee` [6](#0-5) .
2. The dispatched command reverts on the Ethereum Gateway; the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid proof for this genuine event and calls `submit_delivery_receipt(event)`; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success = false` correctly.
4. `process_delivery_receipt` checks only `receipt.gateway` and `PendingOrders::get(nonce).is_some()`; both pass, `receipt.success` is never read, so `order.fee > 0` triggers `register_reward` and `PendingOrders::remove(nonce)` executes unconditionally.
5. The relayer is paid the full fee for a message that never executed successfully on Ethereum — an unbacked, non-reversible payout with no possibility of reconciliation.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
