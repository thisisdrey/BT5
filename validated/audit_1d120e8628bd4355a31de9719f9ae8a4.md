## Analysis

The in3-server report's core broken invariant is: **a public, unauthenticated request handler accepts an unbounded array of block identifiers and performs proof/signature work proportional to array size, with no per-request cost or cap**, letting a client burn node CPU for free.

The closest local analog is the MMR RPC's `mmr_generateProof` method, which accepts an **unbounded `Vec<BlockNumber>`** and, for every entry, performs an MMR leaf lookup plus a proof-generation walk over the tree — all served for free by any RPC-exposed node, with no size limit and no `DenyUnsafe`/rate gating.

### Title
Unbounded `block_numbers` array in `mmr_generateProof` RPC enables free, unbounded proof-generation work per request - ([File: substrate/client/merkle-mountain-range/rpc/src/lib.rs])

### Summary
The `MmrApiServer::generate_proof` RPC handler forwards a caller-supplied `Vec<BlockNumber>` directly into the runtime API without any length check, and the underlying pallet/MMR logic iterates over every requested block number doing offchain-storage leaf lookups and MMR proof-item computation, all before any of Substrate's normal extrinsic weight/fee accounting applies (this is a JSON-RPC read path, not a signed extrinsic).

### Finding Description
`generate_proof` in the RPC layer takes `block_numbers: Vec<NumberFor<Block>>` unmodified and calls into the runtime API: [1](#0-0) 

That runtime API call reaches `pallet_mmr::Pallet::generate_proof`, which maps *every* requested block number to a leaf index with no cap on the input length: [2](#0-1) 

The leaf indices are then each turned into MMR positions, each position triggers an offchain-storage lookup (`store.get_elem`), and the whole set is run through `gen_proof`, whose cost grows with the number of requested leaves and the MMR depth: [3](#0-2) 

Unlike `state_getKeysPaged`, which explicitly caps its input via `STORAGE_KEYS_PAGED_MAX_COUNT`: [4](#0-3) 

`generate_proof` (and the sibling `read_proof`/`query_storage_at`/`query_storage` handlers that also take unbounded `Vec<StorageKey>`) has no analogous bound and is not gated behind `check_if_safe`/`DenyUnsafe`: [5](#0-4) 

This is the same broken invariant as the in3 report: a single cheap client request (`in3.sign([{blockNumber:i} for i in range(200)])`) can be replaced with a single `mmr_generateProof` call whose `block_numbers` array size is fully attacker-controlled, forcing the node to perform unbounded, unpriced work per call.

### Impact Explanation
MMR/BEEFY proofs are the mechanism used by BEEFY light-client bridging (including Snowbridge's Polkadot→Ethereum state proofs), so nodes that serve this RPC are relied upon by bridge relayers and light clients. An attacker who repeatedly submits `mmr_generateProof` requests with very large `block_numbers` arrays (or many concurrent such requests) can consume disproportionate CPU/IO on any node exposing this RPC, degrading its ability to serve legitimate proof requests and, if the node is also a collator/validator/relayer, its ability to author or relay in time — a public underpriced work-based DoS vector, without needing a malicious validator, collator, relayer, or leaked keys.

### Likelihood Explanation
Likelihood is high for any node with the RPC exposed (a very common deployment configuration for full/archive nodes and bridge-relayer-facing endpoints): the request requires no signature, no fee, and no special privilege — just a JSON-RPC call with an attacker-chosen array length.

### Recommendation
Add an explicit maximum length check on `block_numbers` (and similarly for `verify_proof`/`verify_proof_stateless` leaf counts) in `generate_proof`/`generate_ancestry_proof`, mirroring the `STORAGE_KEYS_PAGED_MAX_COUNT` pattern already used for `state_getKeysPaged`, and consider gating this and other unbounded-array read RPCs (`state_getReadProof`, `state_queryStorageAt`) behind rate limiting or `DenyUnsafe`.

### Proof of Concept
```
# Against any node exposing the default RPC set:
curl -H 'Content-Type: application/json' -d '{
  "id":1, "jsonrpc":"2.0",
  "method":"mmr_generateProof",
  "params": [[1,2,3, ... , N],  N,  null]
}' http://NODE:9944
```
Setting `N` to a very large value (bounded only by MMR leaf count / SCALE decode limits) forces the node to perform `N` offchain-storage lookups and MMR proof computations per call, repeatable indefinitely at no cost to the caller.

	fn generate_proof(
		&self,
		block_numbers: Vec<NumberFor<Block>>,
		best_known_block_number: Option<NumberFor<Block>>,
		at: Option<<Block as BlockT>::Hash>,
	) -> RpcResult<LeavesProof<<Block as BlockT>::Hash>> {
		let mut api = self.client.runtime_api();
		let block_hash = at.unwrap_or_else(||
			// If the block hash is not supplied assume the best block.
			self.client.info().best_hash);

		api.register_extension(OffchainDbExt::new(self.offchain_db.clone()));

		let (leaves, proof) = api
			.generate_proof(block_hash, block_numbers, best_known_block_number)
			.map_err(runtime_error_into_rpc_error)?
			.map_err(mmr_error_into_rpc_error)?;

		Ok(LeavesProof::new(block_hash, leaves, proof))
	}

	pub fn generate_proof(
		&self,
		leaf_indices: Vec<NodeIndex>,
	) -> Result<(Vec<L>, LeafProof<HashOf<T, I>>), Error> {
		let positions = leaf_indices
			.iter()
			.map(|index| mmr_lib::leaf_index_to_pos(*index))
			.collect::<Vec<_>>();
		let store = <Storage<OffchainStorage, T, I, L>>::default();
		let leaves = positions
			.iter()
			.map(|pos| match store.get_elem(*pos) {
				Ok(Some(Node::Data(leaf))) => Ok(leaf),
				e => Err(Error::LeafNotFound.log_debug(e)),
			})
			.collect::<Result<Vec<_>, Error>>()?;

		let leaf_count = self.leaves;
		self.mmr
			.gen_proof(positions)
			.map_err(|e| Error::GenerateProof.log_error(e))
			.map(|p| LeafProof {
				leaf_indices,
				leaf_count,
				items: p.proof_items().iter().map(|x| x.hash()).collect(),
			})
			.map(|p| (leaves, p))
	}
