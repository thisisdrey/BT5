This confirms the Go TLS session resumption cache is not a valid analog to the Zebra vulnerability. Both `loadSession` (client) and `checkForResumption` (server) explicitly re-check all height/time-dependent (context-dependent) properties on every use of the cached session — certificate expiry (`c.config.time().After(session.peerCertificates[0].NotAfter)`), chain validity via `anyValidVerifiedChain` with fresh `CurrentTime`, hostname, TLS version, and cipher suite — precisely the class of checks that Zebra's bug skipped. This is the opposite of the reported flaw: rather than blindly trusting a stale verification result, Go re-validates the context-dependent fields before honoring the cache. [1](#0-0) [2](#0-1) [3](#0-2) 

I did not find any Go stdlib code path (module checksum cache, `go test` result cache, VCS reuse cache, DNS config cache, or TLS session cache) that reuses a prior "verified" result while skipping the height/time/context-dependent checks that made it valid, the way Zebra's mempool verification cache did. The `go.sum`/sumdb cache (`mod_sumdb_cache.txt`) and VCS `-reuse` flag include explicit hash/tag re-validation on each fetch, and the `go test` cache keys on binary hash and cacheable-flag set only, not on any time/height notion. None of these match the reported primitive (accepting a formerly-valid-but-now-invalid unit of work due to skipped contextual re-verification).
