### Title
StackerDB chunk signature omits the contract/StackerDB identity, enabling cross-contract replay of validly-signed chunks - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` computes the digest that a signer signs over as `hash(slot_id, slot_version, data_hash)` only. It does not bind the digest to the specific StackerDB (smart contract) instance the chunk belongs to. Because Nakamoto's `.signers-{0,1}-{message_id}` StackerDB replicas all derive their slot→signer assignment from the *same* underlying list (`stackerdb-get-signer-slots-page`), the same signer occupies the same `slot_id` in every message-type contract for a given signer set/parity, and often across separate reward cycles that reuse the same parity. This means a validly-signed chunk broadcast for one contract can be replayed as-is into a different StackerDB contract (or a stale reward cycle's contract) where the attacker doesn't control the key, and it will pass `SlotMetadata::verify()`/`try_replace_chunk()`.

### Finding Description
The signing/verification logic lives in `libstackerdb/src/libstackerdb.rs`: [1](#0-0) 

`auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash` — no contract identifier, no reward-cycle, no StackerDB-instance binding of any kind. `SlotMetadata::verify()` recovers the public key from this same narrow digest and only compares the recovered `Hash160` against the caller-supplied `principal` address.

The write path, `StackerDBTx::try_replace_chunk()` in `stackslib/src/net/stackerdb/db.rs`, looks up the expected signer for the *target* contract and slot, then calls `slot_desc.verify(&slot_validation.signer)`: [2](#0-1) 

Because `verify()` never checks which contract the signature was originally produced for, any valid `(slot_id, slot_version, sig, data)` tuple observed on the wire for contract A can be resubmitted (via `POST /v2/stackerdb/{contract}/chunks`, see `stackslib/src/net/api/poststackerdbchunk.rs`, or via the p2p `StackerDBPushChunk`/gossip path in `stackslib/src/net/stackerdb/mod.rs::validate_received_chunk`) to contract B, and it will validate as long as:
1. The same signer address owns `slot_id` in contract B (guaranteed within a signer set/parity across all `.signers-{0,1}-{message_id}` contracts, since they all read from the identical `stackerdb-get-signer-slots-page` list defined in `stackslib/src/chainstate/stacks/boot/signers.clar`), and
2. The current stored `slot_version` for that slot in contract B is lower than the replayed `slot_version`. [3](#0-2) [4](#0-3) 

`validate_received_chunk()` performs the identical narrow check for unsolicited/gossiped chunks: [5](#0-4) 

This is precisely the bug class in the external report: the signed hash is missing a binding parameter (there, the executor address; here, the StackerDB/contract context), so a signature that is valid in one context can be replayed in a different, unintended context by anyone who observes it on the wire — StackerDB chunks are gossiped and openly readable, so no privileged access is needed to capture and replay them.

### Impact Explanation
An attacker can inject old, but validly-signed, chunk content into a StackerDB slot belonging to a different contract instance (a different message-type replica for the same signer set, or the same contract in a later reward cycle reusing that parity), as long as the version counter at the target permits it. This lets stale/non-canonical signer state be served as canonical to any peer/consumer reading that slot (nodes, other signers, or miners reading `.signers-*` StackerDBs for block-proposal/response/state-machine data), potentially causing signer state-machine consumers, `stacks-node`'s `StackerDBListener`, or the miner coordinator to load and act on stale, attacker-selected historical data instead of the genuinely latest data — an instance of "serving non-canonical state as canonical" per the impact criteria.

### Likelihood Explanation
Exploitation only requires observing chunk data broadcast over StackerDB (no secret key or privileged role needed), and resubmitting the exact same signed bytes to a different, permissively-writable target slot/contract. The precondition (same signer occupying the same slot_id across sibling contracts) is structurally guaranteed by the current `.signers-{0,1}-{message_id}` design, since every message-type contract for a signer set reads the identical slot list. The remaining gating factor — whether the target slot's stored version is lower than the replayed version — depends on operational timing, making this a realistic but not always-immediately-exploitable condition.

### Recommendation
Bind the signed StackerDB chunk digest to the StackerDB's identity (and ideally the reward cycle) in addition to `slot_id`, `slot_version`, and `data_hash`. Concretely, modify `SlotMetadata::auth_digest()` (and the corresponding `sign`/`verify` call sites) to also hash in the `QualifiedContractIdentifier` of the target StackerDB (already available at all call sites in `try_replace_chunk` and `validate_received_chunk`), so a signature produced for one StackerDB contract cannot be replayed against another.

### Proof of Concept
Conceptual PoC (cannot be executed without live network access, but the code paths are concretely traceable):
1. Observe a validly-signed `StackerDBChunkData` broadcast for contract `.signers-0-1` (e.g., a `BlockProposal` message), signed by signer S occupying `slot_id = 3` with `slot_version = v`.
2. Note that `.signers-0-2` (a different message-type contract for the same signer set) assigns the same `slot_id = 3` to the same signer S (per `stackerdb-get-signer-slots-page u0`), and its current stored version for slot 3 is `< v`.
3. Submit the identical `(slot_id=3, slot_version=v, sig, data)` tuple to `.signers-0-2` via `POST /v2/stackerdb/.signers-0-2/chunks`.
4. `try_replace_chunk()` in `stackslib/src/net/stackerdb/db.rs` looks up the slot 3 signer for `.signers-0-2` (S), calls `slot_desc.verify(&S)`, which succeeds because `auth_digest()` never checked which contract the signature was meant for — the chunk is accepted and overwrites `.signers-0-2`'s slot 3 with data that was never intended for it.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
