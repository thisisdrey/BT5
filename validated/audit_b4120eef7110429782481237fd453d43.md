Confirmed: `TransactionID` is a simple monotonically incrementing `uint64` counter (`r.idSequence++`) that is process-global and shared across all repositories/users on a Gitaly node [1](#0-0) , and `ProcReceiveHook` performs no repository or authorization validation before transmitting the caller-supplied handler into the shared registry [2](#0-1) .

### Title
Cross-Transaction Reference-Update Injection via Unauthenticated `ProcReceiveHook` Callback Re-Entry - (File: internal/gitaly/service/hook/proc_receive.go)

### Summary
The `proc-receive` hook mechanism lets a spawned Git hook process "call back" into the Gitaly gRPC server mid-push, before the write-ahead log (WAL) commits the reference updates, exactly analogous to the external-call re-entrancy pattern in the reported `LPToken.mint()` issue (an external callback fires before the caller's state is finalized). In Gitaly, `ReceivePack` registers a waiter keyed only by a small, sequential, process-wide `storage.TransactionID`, and the `ProcReceiveHook` RPC handler blindly matches on that same integer, with no check that the caller is the actual git-hook subprocess spawned for that specific push, nor even that the caller has access to the target repository.

### Finding Description
When an `OperationService`/`ReceivePack`-style RPC begins a push, it calls `RegisterProcReceiveHook`, which registers a waiter in the shared `ProcReceiveRegistry` under the transaction's `storage.TransactionID` [3](#0-2) . That ID is produced by a simple, unguarded, per-process incrementing counter shared by every repository and every user on the node [1](#0-0) , so any authenticated pusher can trivially infer nearby in-flight transaction IDs from their own recently-observed ID (e.g., by pushing repeatedly and observing sequential allocation, or by racing two pushes).

The `ProcReceiveHook` gRPC handler accepts a stream, builds a `ProcReceiveHandler` purely from client-supplied `EnvironmentVariables` (which encode the `GITALY_HOOKS_PAYLOAD`, including the `TransactionID`) and client-supplied `stdin` (which encodes the reference updates in pkt-line form), and then calls `registry.Transmit`, which looks the handler up **solely by the numeric transaction ID** with no ownership, repository, or token check tying the caller to that specific transaction [2](#0-1) [4](#0-3) . The `TransactionID` and the reference updates (`old-oid new-oid ref-name`) come entirely from the untrusted RPC payload parsed in `NewProcReceiveHandler` [5](#0-4) .

On the other side, `RegisterProcReceiveHook`'s goroutine consumes whatever handler shows up on the channel for its transaction ID and feeds its `ReferenceUpdates()` toward WAL commit via `procReceiveHook`, trusting that the handler legitimately originated from the `git-receive-pack(1)` subprocess it spawned [6](#0-5) . Because there is no cryptographic binding (the hooks payload signing/token used elsewhere for hook auth, e.g. `GITALY_TOKEN`, is not shown to be checked against the specific transaction in `ProcReceiveHook`), a second gRPC caller can independently open a `ProcReceiveHook` stream, guess/observe another concurrent transaction's ID, and race the legitimate hook subprocess to have their crafted reference updates transmitted into that transaction's registry slot first — re-entering another user's in-flight push before its state (WAL commit) is finalized, analogous to how `Attack3`'s `onERC721Received` callback re-entered `addNativeLiquidity` before `LPToken.mint()`'s state was finalized.

This mirrors the reported bug class precisely: an external callback path (git hook subprocess → gRPC RPC) executes mid-transaction and can be triggered/raced independently of the original caller, letting a second actor inject data into shared mutable state (the `ProcReceiveRegistry` map, and ultimately the WAL commit) before the legitimate flow completes.

### Impact Explanation
If exploited, an attacker with ordinary push access could inject arbitrary reference updates (branch/tag creation, deletion, force-updates) into another user's concurrent push transaction, bypassing the normal `pre-receive`/`update` access-check hooks that would otherwise gate such changes (since `proc-receive` bypasses `execute_commands()` entirely as documented) [7](#0-6) . This could corrupt repository state, bypass branch-protection checks that rely on `pre-receive`, or cause a denial-of-service of the victim's push (their real hook process's `Transmit` call fails with "no waiters for id", since the slot may already be consumed) [8](#0-7) .

### Likelihood Explanation
Exploitation requires: (1) authenticated push/RPC access to the Gitaly node (ordinary user, not privileged), (2) ability to guess or observe a nearby `TransactionID` — trivial given it's a small sequential counter shared across the whole process, and (3) winning a race against the legitimate `git-receive-pack` subprocess's own `ProcReceiveHook` call, which is plausible on a busy node with concurrent pushes. No MITM, malicious peer/node, or privileged actor is required — the attacker is simply another ordinary client issuing crafted RPC calls, matching the allowed analog scope.

### Recommendation
Bind the `ProcReceiveHook` RPC to its originating transaction cryptographically or via a per-request secret token (similar to how the reference-transaction hook path is already scoped to a repository via `validateReferenceTransactionHookRequest`) rather than relying on a bare, guessable integer transaction ID for registry lookup [9](#0-8) . At minimum, validate the requesting repository/user against the transaction owner before calling `registry.Transmit`, and randomize `TransactionID` generation instead of using a predictable sequence [1](#0-0) .

### Proof of Concept
1. Attacker (Client A) with push access initiates a push to repo A, observing their allocated `TransactionID` N (via timing/side channel or by having pushed just before/after another user).
2. Attacker crafts a `GITALY_HOOKS_PAYLOAD` environment variable string with `TransactionID = N+1` (the next likely victim transaction) and opens a `ProcReceiveHook` gRPC stream directly (bypassing the actual git subprocess), sending a pkt-line stream declaring malicious `old-oid new-oid ref-name` updates (e.g., overwriting `refs/heads/protected-branch`).
3. If the attacker's `Transmit` call races ahead of the legitimate `git-receive-pack` subprocess handling victim B's push under transaction N+1, `ProcReceiveRegistry.Transmit` matches on `TransactionID` alone and delivers the attacker's handler to victim B's `RegisterProcReceiveHook` goroutine [4](#0-3) .
4. The attacker's forged reference updates are then processed as if they belonged to victim B's legitimate, access-checked push, potentially getting committed to the WAL.

**Uncertainty:** I was unable to fully verify within the index whether `gitcmd.HooksPayloadFromEnv` / hook payload construction embeds a signed/verified token that Gitaly checks against the specific transaction (beyond general RPC auth) before `ProcReceiveHook` proceeds — if such a per-transaction secret check exists elsewhere (e.g., in middleware not surfaced by search), this would mitigate the race. Given index size limits, some related files (e.g., full `hooks_payload.go`, `manager.go` auth wiring) were not completely inspected; a full review in a Devin session would confirm whether such a binding exists.

	ctx := stream.Context()

	firstRequest, err := stream.Recv()
	if err != nil {
		return structerr.NewInternal("receiving first request: %w", err)
	}

		req, err := stream.Recv()
		return req.GetStdin(), err
	})

		return stream.Send(&gitalypb.ProcReceiveHookResponse{Stdout: p})

		return stream.Send(&gitalypb.ProcReceiveHookResponse{Stderr: p})

		return structerr.NewInternal("creating handler: %w", err)

	if err := registry.Transmit(ctx, handler); err != nil {
		return sendProcReceiveHookResponse(stream, 1, fmt.Sprintf("transmitting handler: %s", err))

// Transmit transmits a handler to its waiter.
func (r *ProcReceiveRegistry) Transmit(ctx context.Context, handler ProcReceiveHandler) error {
	r.m.Lock()
	ch, ok := r.waiters[handler.TransactionID()]
	r.m.Unlock()

	if !ok {
		return fmt.Errorf("no waiters for id: %d", handler.TransactionID())
	}

	// It is possible that the RPC (waiter) returned because receive-pack
	// returned an error. In such scenarios, we don't want to block indefinitely.
	select {
	case <-ctx.Done():
		return ctx.Err()
	case ch <- handler:
	}

	return nil
}

func NewProcReceiveHandler(env []string, stdin io.Reader, stdout, stderr io.Writer) (ProcReceiveHandler, <-chan error, error) {
	payload, err := gitcmd.HooksPayloadFromEnv(env)
	if err != nil {
		return nil, nil, fmt.Errorf("extracting hooks payload: %w", err)
	}

	// This hook only works when there is a transaction present.
	if payload.TransactionID == 0 {
		return nil, nil, fmt.Errorf("no transaction found in payload")
	}

	scanner := pktline.NewScanner(stdin)

	// Version and feature negotiation.
	if !scanner.Scan() {
		return nil, nil, fmt.Errorf("expected version negotiation: %w", scanner.Err())
	}

	data, err := pktline.Payload(scanner.Bytes())
	if err != nil {
		return nil, nil, fmt.Errorf("receiving header: %w", err)
	}

	version, features, _ := bytes.Cut(data, []byte{0})
	if !bytes.HasPrefix(version, []byte("version=1")) {
		return nil, nil, fmt.Errorf("unsupported version: %s", data)
	}

	if !scanner.Scan() {
		return nil, nil, fmt.Errorf("expected flush: %w", scanner.Err())
	}

	if !pktline.IsFlush(scanner.Bytes()) {
		return nil, nil, fmt.Errorf("expected pkt flush")
	}

	featureRequests := parseFeatureRequest(features)
	if _, err := pktline.WriteString(stdout, fmt.Sprintf("version=1%s", featureRequests)); err != nil {
		return nil, nil, fmt.Errorf("writing version: %w", err)
	}

	if err := pktline.WriteFlush(stdout); err != nil {
		return nil, nil, fmt.Errorf("flushing version: %w", err)
	}

	var updates []ReferenceUpdate
	for scanner.Scan() {
		line := scanner.Bytes()

		// When all reference updates are transmitted, we expect a flush.
		if pktline.IsFlush(line) {
			break
		}

		data, err := pktline.Payload(line)
		if err != nil {
			return nil, nil, fmt.Errorf("receiving reference update: %w", err)
		}

		update, err := parseRefUpdate(data)
		if err != nil {
			return nil, nil, fmt.Errorf("parse reference update: %w", err)
		}
		updates = append(updates, update)
	}

The `git-receive-pack(1)` executes the proc-receive hook for commands that have a
matching prefix with the multi-valued config variable `receive.procReceiveRefs`.
When the variable is set, the hook executes these commands instead of the internal
`execute_commands()` function. This transfers the responsibility of making
reference updates to the hook. The hook executes once for the receive operation.
The hook takes no arguments, but uses a _pkt-line format_ protocol to communicate
with `git-receive-pack(1)` to read commands and push options, and send results.

In Gitaly, we use this mechanism to intercept updates to references made directly
via Git. This hook allows us to capture any updates to references made and route
them through the write-ahead log's write queue. This ensures that we account for
every reference update and log all reference updates.
