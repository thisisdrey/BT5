### Title
Per-connection (not global) unstaked stream throttling in `throttle_stream`/`StakedStreamLoadEMA` lets a botnet of low-stake IPs multiply unstaked ingress far beyond `MAX_UNSTAKED_TPS` - (File: streamer/src/nonblocking/stream_throttle.rs)

### Summary
`StakedStreamLoadEMA::available_load_capacity_in_throttling_duration` computes a fixed per-connection stream budget for unstaked peers (`max_unstaked_load_in_throttling_window = MAX_UNSTAKED_TPS * STREAM_THROTTLING_INTERVAL_MS / 1000`, i.e. 20 streams/100ms ≈ 200 TPS) instead of dividing a global unstaked budget across all unstaked connections. `throttle_stream` then only sleeps the individual QUIC connection whose own `ConnectionStreamCounter` exceeds that per-connection cap, so the constant `MAX_UNSTAKED_TPS` never actually bounds total unstaked throughput across concurrently admitted connections. An attacker distributing traffic across many source IPs (each individually compliant with per-IP connection-rate limits and per-connection stream limits) can multiply effective unstaked ingress by the number of admitted unstaked connections.

### Finding Description
`StakedStreamLoadEMA::new` (streamer/src/nonblocking/stream_throttle.rs:46-85) computes `max_unstaked_load_in_throttling_window` once at server startup as `MAX_UNSTAKED_TPS * STREAM_THROTTLING_INTERVAL_MS / 1000`, a **constant** independent of how many unstaked connections currently exist. `available_load_capacity_in_throttling_duration` (lines 167-188) returns this same fixed constant for every `ConnectionPeerType::Unstaked` peer, regardless of total unstaked connection count.

Each accepted QUIC connection gets its own `ConnectionStreamCounter` (lines 196-231), and `on_new_stream` in `streamer/src/nonblocking/swqos.rs:497-516` calls `throttle_stream` with `max_streams_per_throttling_interval` = that fixed per-connection value. `throttle_stream` (lines 233-271) only checks/sleeps against the *per-connection* `stream_count`, never against any cross-connection or global counter.

Connection admission for unstaked peers is governed independently by:
- `max_unstaked_connections` (connection-table capacity with LRU pruning in `prune_unstaked_connection_table`/`prune_unstaked_connections_and_add_new_connection`, `streamer/src/nonblocking/swqos.rs:241-299`), and
- `ConnectionRateLimiter` (`streamer/src/nonblocking/connection_rate_limiter.rs:1-51`), a **per-IP** token bucket that only limits connection *creation rate* from a single IP, with no cross-IP aggregation.

There is no mechanism anywhere in this path that sums stream/packet throughput across all unstaked connections and enforces a true system-wide `MAX_UNSTAKED_TPS` ceiling. Consequently, an attacker who spreads connections across N distinct source IPs (each opening 1+ connections while staying under `DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE` and under the per-connection stream cap) can drive up to `N * max_unstaked_load_in_throttling_window` streams per 100ms into the QUIC packet handler, up to the admission ceiling `max_unstaked_connections`. Each stream results in packetization and dispatch into the sigverify/batching pipeline (`total_unstaked_packets_sent_for_batching` counter in `streamer/src/nonblocking/quic.rs:841-846`) before any fee is collected or stake-weighted QoS is applied.

### Impact Explanation
This allows grossly underpriced pre-fee work: sigverify, dedup, and packet-batching CPU cost scales with attacker-controlled connection/IP count rather than with stake or fees paid, since the unstaked throughput ceiling is enforced per-connection instead of globally. This matches the "unprivileged attacker forcing sigverify/dedup/scheduling/buffering work vastly exceeding fees collected" bounty category referenced in the question, degrading leader performance without requiring any stake or elevated privilege.

### Likelihood Explanation
Feasible with only unprivileged network access: an attacker needs a botnet/proxy pool of IPs (no stake, no keys, no validator control) sending QUIC connections to the leader's public TPU port. Each IP independently satisfies `DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE` and the fixed per-connection stream cap; only the aggregate admission limit `max_unstaked_connections` bounds the number of simultaneously exploitable connections, but that limit is sized for connection-table memory, not for aggregate CPU-cost budgeting, so the achievable aggregate stream rate (`N * 20 streams/100ms`) can substantially exceed the intended systemwide 200 TPS unstaked budget for realistic values of `max_unstaked_connections`. This is repeatable every 100ms throttling window indefinitely.

### Recommendation
Enforce `MAX_UNSTAKED_TPS` (or an equivalent configurable ceiling) as a shared/global token bucket across all unstaked connections rather than as a static per-connection allowance — e.g., track an atomic global unstaked stream/packet counter in `StakedStreamLoadEMA` and have `throttle_stream` consult and decrement that shared budget (similar to how `load_in_recent_interval`/EMA already aggregates staked load) instead of relying solely on each connection's independent `ConnectionStreamCounter`.

### Proof of Concept
Integration test plan (in `streamer/src/nonblocking/stream_throttle.rs` or a new integration test under `streamer/tests/`):
1. Construct a `StakedStreamLoadEMA` with `max_unstaked_connections = K` (e.g. 100) via `StakedStreamLoadEMA::new`.
2. Simulate `K` distinct unstaked connections, each with its own `ConnectionStreamCounter`, each independently calling `throttle_stream` in a loop attempting to open streams as fast as allowed.
3. Assert that each connection is permitted `available_load_capacity_in_throttling_duration(ConnectionPeerType::Unstaked, total_stake) == 20` streams per 100ms window (current behavior), and that the **sum** across all `K` connections (`total_unstaked_packets_sent_for_batching` in `StreamerStats`) reaches `K * 20` streams per 100ms window — i.e., `K * 200` TPS — which for `K > 1` already exceeds the documented/intended `MAX_UNSTAKED_TPS = 200` global ceiling.
4. Expected (buggy) result: no code path clamps the summed throughput to 200 TPS; only per-connection counters are checked. A fix should make this aggregate assertion fail against a fixed global bound instead.
