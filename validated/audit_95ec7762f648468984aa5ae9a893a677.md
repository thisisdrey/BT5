### Title
Unbounded array allocation from attacker-controlled length words in TVM precompiled-contract call-data parsing enables memory-exhaustion DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The Pillow advisory describes a bug class where a small, attacker-crafted input carries a length/size field that is trusted without an upper bound, causing the decoder to allocate/consume memory disproportionate to the input size ("decompression bomb"). The analogous pattern in java-tron is in the helper methods used by several TVM precompiled contracts to parse dynamic arrays out of raw call data: `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read a 32-byte "length" word directly from attacker-supplied call data and use it to size a Java array before any bound is enforced against the actual call-data size.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` each read `len = words[offset].intValueSafe()` from caller-supplied `data` and immediately allocate `new byte[len][]` (or iterate `len` times copying from `data`) without first checking that `len` is consistent with the remaining length of `data` or capped to a sane maximum: [1](#0-0) 

`extractBytesArray` does check `offset > words.length - 1`, but that only bounds the *offset*, not the attacker-controlled `len` value used to size the output array; the same is true for `extractBytes32Array` and `extractSigArray`, which perform no such check at all before allocating `new byte[len][]`. Because `data` is the raw call-data byte array supplied in a `CALL`/`STATICCALL` transaction to one of these precompiles, an unprivileged transaction sender can set the length word to an arbitrarily large 32-byte integer, causing the node to attempt a very large heap allocation from a tiny transaction payload — the same "small input, disproportionate memory consumption" shape as the FITS GZIP bomb in Pillow.

This differs from the sibling `ModExp` precompile, which explicitly caps `baseLen`/`expLen`/`modLen` to `UPPER_BOUND` when a feature flag is enabled and calls `MUtil.checkCPUTimeForModExp()`: [2](#0-1) 

showing that other precompiles in this same file *do* defend against length-based resource-exhaustion, while the `extractBytes32Array`/`extractBytesArray`/`extractSigArray` helpers do not apply an equivalent guard before allocation.

### Impact Explanation
A crafted transaction that invokes a precompiled contract relying on these helpers can force allocation of an oversized array from a very small call-data payload. Depending on the magnitude chosen, this can throw an immediate `OutOfMemoryError` (if the array size exceeds the JVM's maximum array length) or, for sizes within the JVM limit but still very large, consume a large fraction of heap in a single call. Since energy/CPU metering for TVM execution is generally charged based on declared call-data length/opcode cost rather than on memory actually touched by these helper routines, an attacker can trigger disproportionate memory pressure relative to the energy paid, risking degraded performance or a node crash for all nodes executing the same transaction (validators and full nodes alike), which matches the "node crash or halt" impact bucket.

### Likelihood Explanation
Reachability requires only a standard signed transaction that performs a `CALL` to the affected precompiled contract address with crafted call data — no special privileges, whitelisting, or SR/witness role is needed, consistent with the "unprivileged transaction broadcaster" reach requirement. The likelihood of exploitation depends on confirming (a) which specific precompile(s) invoke `extractBytesArray`/`extractBytes32Array`/`extractSigArray` at the current call sites, and (b) whether any earlier caller-side validation (e.g., total call-data length checks before dispatch) restricts practical exploitation. I was not able to fully trace all call sites of these three helpers within the available search iterations, so this should be verified directly against the precompile dispatch logic before treating it as fully confirmed.

### Recommendation
Add explicit bounds checks in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` so that the parsed `len` is validated against the remaining size of `data` (similar to `isValidAbiEncoding`/`verifyLength`-style checks already used elsewhere in the codebase, e.g. `RLP.verifyLength`) before any array is allocated, and reject the call (return a failure result) rather than allocating when `len` is inconsistent with the actual call-data size.

### Proof of Concept
1. Identify (via full source access) a precompiled contract that calls `extractBytesArray` or `extractBytes32Array` on its input `data`.
2. Craft a `TriggerSmartContract` transaction whose call data is directed at that precompile's address, with the ABI length word for the relevant array set to a very large value (e.g., `0x7fffffff`) while the actual trailing payload is empty or minimal.
3. Broadcast the transaction; the node executing it invokes `words[offset].intValueSafe()` to obtain the huge length and performs `new byte[len][]`, which either throws `OutOfMemoryError` or forces a large heap allocation disproportionate to the small transaction size. [3](#0-2)

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
