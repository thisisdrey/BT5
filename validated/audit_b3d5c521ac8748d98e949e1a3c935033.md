### Title
Handshake replay protection in `CheckAndComplete` is bypassed whenever the existing tunnel is initiator-side, letting a stale replayed handshake displace a legitimate live tunnel - (File: `handshake_manager.go`)

### Summary
`HandshakeManager.CheckAndComplete` is supposed to reject an incoming handshake for a peer we already have a tunnel with when that incoming handshake is not newer than our current one (anti-replay protection based on the certified `lastHandshakeTime`). The guard is implemented as a single boolean expression that ANDs the freshness check with `!existingHostInfo.ConnectionState.initiator`. Because of that AND, the freshness check is entirely skipped whenever we are the initiator of the existing tunnel, regardless of whether the incoming handshake is actually newer. This mirrors the `CoreRouter.repayBorrowInternal` pattern in the report: a state-mutating block ("take the new handshake" → `unlockedAddHostInfo`) that should only run when a specific condition holds instead runs whenever an unrelated flag (`initiator`) has a particular value, corrupting/replacing legitimate, unrelated state.

### Finding Description
In `handshake_manager.go`:

```go
existingHostInfo, found := hm.mainHostMap.Hosts[hostinfo.vpnAddrs[0]]
if found && existingHostInfo != nil {
    ...
    // Is this a newer handshake?
    if existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime && !existingHostInfo.ConnectionState.initiator {
        return existingHostInfo, ErrExistingHostInfo
    }
    existingHostInfo.logger(hm.l).Info("Taking new handshake")
}
...
hm.mainHostMap.unlockedAddHostInfo(hostinfo, f)
return existingHostInfo, nil
``` [1](#0-0) 

`HostInfo.lastHandshakeTime` is explicitly documented as the anti-replay defense: "This is used to avoid an attack where a handshake packet is replayed after some time" [2](#0-1) . The intended behavior is: if the existing tunnel's handshake is at least as new as the incoming one, keep the existing tunnel and reject the incoming (stale/replayed) one.

The bug is that this freshness check is ANDed with `!existingHostInfo.ConnectionState.initiator`. If the *existing* hostinfo happens to be the one where we were the initiator (`ConnectionState.initiator == true`), the whole condition evaluates to `false` no matter how old/stale the incoming handshake is, so the code falls through to `"Taking new handshake"` and unconditionally calls `unlockedAddHostInfo`, replacing/duplicating the live tunnel's hostinfo. This is functionally identical to the referenced bug: a block that mutates important state ("wipe/replace the current legitimate record") executes without being properly gated on the condition (freshness) that should control it, because an unrelated flag (`initiator`) short-circuits the guard.

### Impact Explanation
An attacker who has captured an old, legitimately-signed handshake stage-1 packet from a real peer (e.g., from an earlier handshake session, before the tunnel we're currently using was established) can replay it at any later time. As long as we are on the initiator side of our current tunnel to that peer, the freshness/replay check is bypassed entirely, and the stale handshake is accepted as "newer," causing:
- Displacement/duplication of the currently active, legitimate hostinfo (indexes, relay state, roaming state) for that peer.
- Potential tunnel disruption/DoS for that peer relationship, since a strictly older, previously-superseded handshake session can be resurrected to overwrite live tunnel state.

This corresponds to "remote state poisoning" per the accepted analog categories — an attacker forces a wrong/older state transition onto a live authenticated hostinfo purely through nonce/replay-window mishandling of the handshake timestamp, without needing any certificate of their own (they only replay pre-captured legitimate bytes).

### Likelihood Explanation
The exact stage-0 payload bytes are checked for byte-for-byte duplication earlier (`bytes.Equal(hostinfo.HandshakePacket[...], testHostInfo.HandshakePacket[...])`, `ErrAlreadySeen` path) [3](#0-2) , but that only catches replays of the *exact current* session's packet. It does **not** catch replay of an *older* legitimate stage-0 packet from a prior session with the same peer (different bytes/timestamp, still a validly signed cert as long as it hasn't expired). Triggering the bug additionally requires that we are currently the initiator side of the tunnel to that peer (`ConnectionState.initiator == true`), which is a common, easily-observable and not attacker-controlled condition, but occurs routinely in normal mesh operation. No special crypto forging is required — only capture-and-replay of a previously-observed genuine UDP packet.

### Recommendation
Decouple the anti-replay freshness check from the `initiator` flag; the freshness comparison should always be enforced regardless of which side initiated the current tunnel:

```diff
-   if existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime && !existingHostInfo.ConnectionState.initiator {
+   if existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime {
        return existingHostInfo, ErrExistingHostInfo
    }
```
If the `initiator` exception is needed for a legitimate simultaneous-handshake tie-break, it must be scoped narrowly (e.g., only when timestamps are exactly equal), never used to bypass the "incoming handshake is older" case entirely.

### Proof of Concept
1. Node `A` and Node `B` complete a handshake at time T0; `A` is the initiator (`A`'s `ConnectionState.initiator == true`), and its `lastHandshakeTime` for `B` is `T0`.
2. An on-path attacker (no CA-signed certificate of their own) captures `B`'s original stage-1 handshake packet sent at `T0` (or any earlier legitimate stage-1 packet from `B` for a still-valid certificate).
3. Time passes; `A` and `B` re-handshake normally (or the tunnel is simply long-lived), so `A`'s current `existingHostInfo.lastHandshakeTime` for `B` is now `T1 > T0`, and `A` is still the initiator side.
4. Attacker replays the captured old stage-1 packet to `A`.
5. In `CheckAndComplete`, `existingHostInfo.lastHandshakeTime (T1) >= hostinfo.lastHandshakeTime (T0)` is true, but `!existingHostInfo.ConnectionState.initiator` is `false` (since `A` is the initiator) — the AND is `false`, so the stale-handshake protection is skipped and `"Taking new handshake"` is logged; the old handshake is accepted, replacing the live tunnel state built at `T1` with a stale one derived from `T0`.
