### Title
Missing slippage/minimum-output protection in `ExchangeWithdrawContract` and `ExchangeInjectContract` allows sandwich-style value extraction on TRC10 Bancor exchanges - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
Unlike `ExchangeTransactionContract`, which carries an explicit `expected` field checked against the computed counter-token amount before execution [1](#0-0) , the `ExchangeInjectContract` and `ExchangeWithdrawContract` messages carry no minimum/maximum bound field at all [2](#0-1) . Both actuators compute the counter-token amount purely from the *current on-chain* pool balances at execution time, with no way for the caller to bound the result.

### Finding Description
`ExchangeWithdrawActuator.doValidate`/`execute` derive `anotherTokenQuant` from `firstTokenBalance`/`secondTokenBalance` read from the `ExchangeCapsule` at validation/execution time, using the ratio of the two token reserves [3](#0-2) . The only sanity checks applied are that the result is positive, within `exchangeBalanceLimit`, and "precise enough" (a hardcoded 0.01% rounding tolerance) — there is no user-supplied `min`/`max` bound to protect the caller from a materially different reserve ratio at execution time [4](#0-3) . `ExchangeInjectActuator` has the same shape: it computes `anotherTokenQuant` from the live reserve ratio with no caller-provided bound [5](#0-4) .

Because block producers order transactions within a block and multiple `ExchangeTransactionContract` trades against the same `exchangeId` can execute before a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` in the same block (there is no atomic bundling or price oracle), an attacker (or even benign but adversarial ordering) can shift the first/second token balance ratio between the time a withdraw/inject transaction is broadcast and the time it is packed into a block and executed. `ExchangeWithdrawActuator` in particular is reachable by the exchange creator only (`account is not creator` check) but that "creator" is still an ordinary, unprivileged account that broadcasts a signed transaction like any user [6](#0-5) ; `ExchangeInjectActuator` has no such restriction and is callable by any account holding the relevant TRC10/TRX balance.

### Impact Explanation
A creator withdrawing liquidity, or any account injecting liquidity, receives/pays a counter-token amount computed from whatever the pool ratio happens to be at the moment their transaction actually executes, not the ratio they observed when they signed the transaction. If the pool has been manipulated (e.g., via preceding `ExchangeTransactionContract` swaps in the same block, which do support an `expected` bound and thus can be crafted to guarantee execution) immediately before the victim's inject/withdraw executes, the victim can receive far less counter-token value than intended on withdraw, or overpay on inject — a direct, unauthorized transfer of value out of the victim's account balance. This is a concrete loss of user funds enforced entirely by actuator logic with no way for the affected party to protect themselves at the protocol level.

### Likelihood Explanation
Exploitation requires only ordinary signed transactions: attacker broadcasts one or more `ExchangeTransactionContract` swaps against the target `exchangeId` to skew the reserve ratio, timed to land in the same block just before the victim's pending `ExchangeInjectContract`/`ExchangeWithdrawContract`. No special privilege, witness/SR role, or protocol vulnerability is needed — it is a standard sandwich pattern enabled purely by the missing bound parameter on these two contract types.

### Recommendation
Add an explicit `expected`-style bound field (e.g. `min_another_token_quant` for withdraw, and `min`/`max_another_token_quant` for inject) to `ExchangeInjectContract` and `ExchangeWithdrawContract` in `exchange_contract.proto`, and enforce it in `ExchangeInjectActuator.doValidate`/`ExchangeWithdrawActuator.doValidate` analogous to the existing check in `ExchangeTransactionActuator.doValidate` (`anotherTokenQuant < tokenExpected`) [1](#0-0) .

### Proof of Concept
1. Exchange pool has reserves `firstTokenBalance`, `secondTokenBalance`.
2. Victim (pool creator) signs and broadcasts an `ExchangeWithdrawContract` for `tokenQuant` of `firstTokenID`, expecting `anotherTokenQuant ≈ secondTokenBalance * tokenQuant / firstTokenBalance` based on the current ratio.
3. Before the victim's transaction is packed, attacker broadcasts one or more `ExchangeTransactionContract` swaps against the same `exchangeId` (each individually satisfying its own `expected` check) that shift the ratio, e.g., pumping `firstTokenBalance` up / `secondTokenBalance` down.
4. When the victim's `ExchangeWithdrawContract` executes in `ExchangeWithdrawActuator.execute`, `anotherTokenQuant` is recomputed from the now-skewed reserves [7](#0-6) , yielding a value far below what the victim expected, with no check to reject the transaction.
5. The victim's `ExchangeWithdrawContract` succeeds anyway, and the value difference accrues to the attacker via their earlier swap(s).
