### Title
Attachment content is stored/resolved by the served hash, not the requested `content_hash`, permanently orphaning legitimate attachments after retry exhaustion - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts and stores any `Attachment` a peer returns for an `AttachmentRequest` without verifying that its hash equals the requested `content_hash`. `AttachmentsDownloader::run` then calls `find_all_attachment_instances` and `resolve_attachment` using `attachment.hash()` (the hash of whatever bytes were served) instead of the originally requested hash, so a malicious response never satisfies the pending `(attachment_index, H1)` entry.

### Finding Description
`extend_with_attachments` blindly inserts whatever the peer decodes as an attachment into `self.attachments`, with no comparison against `request.content_hash`: [1](#0-0) 

Later, in `AttachmentsDownloader::run`, the resolution logic looks up and resolves attachment instances keyed by `attachment.hash()` — the hash of the bytes actually received — rather than the `content_hash` that was originally requested: [2](#0-1) 

Because `AttachmentsBatch::attachments_instances` tracks pending work as `(attachment_index, content_hash)` pairs (see how requests are built from `missing_attachments.iter()` yielding `(attachment_index, content_hash)`), a malicious peer that responds to a request for `content_hash = H1` with unrelated bytes `B2` (whose hash is `H2 != H1`) will cause:
- `find_all_attachment_instances(&H2)` to find nothing relevant to the pending H1 instance,
- `resolve_attachment(&H2)` to fail to clear the H1 entry, since it only matches entries equal to H2.

The H1 entry remains in `attachments_batch.attachments_instances`, so `has_fully_succeed()` returns false, `bump_retry_count()` fires, and the batch is either re-enqueued or, once `retry_count >= max_attachment_retry_count`, silently dropped: [3](#0-2) 

No code path checks `attachment.hash() == request.content_hash` anywhere between response decoding and resolution.

### Impact Explanation
A single unprivileged peer that is selected as a download source (any outbound sync peer) can serve wrong bytes for any requested `content_hash` and cause the corresponding `AttachmentInstance` to be permanently treated as unresolved/absent once retries are exhausted, even though a legitimate attachment for that hash exists and is committed on-chain elsewhere in the network. This matches the "attachment/BNS mismatch" High-severity category — BNS name resolution can serve "no attachment" for a name with a valid, committed attachment. This is repeatable per attachment/content hash and does not require any privileged role, secret, or elevated position — only that the attacker's peer be chosen as one of the response sources for a given `AttachmentRequest`.

### Likelihood Explanation
Preconditions: the attacker must run a normal P2P peer that the victim node treats as an outbound sync peer with a data URL, and that peer's inventory must indicate to the victim that it holds the requested attachment page (this is trivially achievable by the attacker fabricating inventory responses since the same trust model is applied to `GetAttachmentsInvResponse` — no inventory verification is shown here either). Attacker cost is minimal (run a peer, answer one HTTP-like attachment request with arbitrary bytes). The attack is fully remote through the P2P/RPC surface and requires no secrets or privileged roles, and is repeatable against every attachment resolution the attacker chooses to interfere with.

### Recommendation
In `extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed request (`report.bump_failed_requests()`) and optionally flag/deregister the misbehaving peer. Then in `AttachmentsDownloader::run`, continue resolving using the verified `content_hash` (which should now always equal `attachment.hash()`), or explicitly pass the original requested hash through the pipeline for resolution instead of trusting `attachment.hash()` from the response alone.

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/download.rs` test module or a new integration test):
1. Construct an `AttachmentsBatch` with a single tracked instance `(attachment_index=0, content_hash=H1)` for some `contract_id`/`index_block_hash`.
2. Drive `AttachmentsBatchStateMachine` through `Initialized -> DNSLookup -> DownloadingAttachmentsInv` with a mocked peer whose inventory response claims it has the attachment at that index (crafted `GetAttachmentsInvResponse` bytes).
3. Transition to `DownloadingAttachment`; supply a mocked HTTP response for the `AttachmentRequest{content_hash: H1}` containing an `Attachment` whose content actually hashes to `H2` (i.e., wrong bytes `B2`).
4. Call `extend_with_attachments` / `try_proceed` to reach `Done`, then simulate `AttachmentsDownloader::run`'s post-processing loop.
5. Assert that `context.attachments_batch.attachments_instances` still contains the `(0, H1)` entry (i.e., `has_fully_succeed()` is `false`) after processing the malicious response.
6. Repeat step 3-5 `max_attachment_retry_count` times (via `bump_retry_count`), then assert the batch is dropped (matching the `"Atlas: dropping batch ... retries count exceeded"` log path) without `network.atlasdb.find_attachment(&H1)` ever returning `Some`.
