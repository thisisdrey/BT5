### Title
Attached deposit (`CallerDeposit`) is silently dropped and never refunded when the Address-Registrar lookup or NEP-141 `storage_balance_of` cross-contract call fails - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The eth-implicit Wallet Contract's `rlp_execute` entry point is `#[payable]` and records any deposit attached by an external (non-self) predecessor into a `CallerDeposit` so it can be refunded if the user's requested action ultimately fails [1](#0-0) [2](#0-1) . This refund is only implemented in one of the three callback functions that eventually resolve the transaction; the other two intermediate callbacks (`address_check_callback` and `nep_141_storage_balance_callback`) return an error `ExecuteResponse` on a failed intermediate promise without ever using the `caller_deposit` they were passed, so the attached deposit is left stranded in the wallet contract's balance.

### Finding Description
`inner_rlp_execute` computes `caller_deposit` from the attached deposit of an external predecessor [3](#0-2)  and threads it through every callback so it can be returned if the on-chain action fails, as implemented in `rlp_execute_callback`: [4](#0-3) 

However, for `EOABaseTokenTransfer` with an `address_check`, the flow first calls the address registrar and only reaches `rlp_execute_callback` (with its refund logic) if the lookup itself succeeds: [5](#0-4) 

But `address_check_callback` handles a failed registrar lookup by simply returning an error value, dropping `caller_deposit` on the floor: [6](#0-5) 

Similarly, for `ERC20Transfer`, the flow first checks `storage_balance_of` on the target NEP-141 token, and only reaches the refund-capable `rlp_execute_callback` if that check succeeds: [7](#0-6) 

`nep_141_storage_balance_callback` handles a failed `storage_balance_of` call the same broken way — it returns an error `ExecuteResponse` without ever inspecting/using the `caller_deposit` parameter it received: [8](#0-7) 

In both cases `caller_deposit` is a function parameter that is completely unused on the failure branch, in contrast to `rlp_execute_callback`'s `PromiseResult::Failed` arm which explicitly creates a `promise_batch_action_transfer` back to `account_id` for `yocto_near`. This is the direct analog of the audit's root cause ("a function that should forward/refund value along a call chain fails to do so on certain code paths") — here it manifests as a missing balance-refund/forwarding step in intermediate promise callbacks of a payable entry point, rather than a missing `payable` modifier.

### Impact Explanation
Any deposit an ordinary external caller (not the eth-implicit account itself) attaches to `rlp_execute` for a base-token transfer targeting an unregistered eth-implicit address, or for an ERC-20 transfer whose registrar/`storage_balance_of` cross-contract call fails (e.g., the registrar or token contract is temporarily unavailable, runs out of gas, or otherwise returns a promise failure), is permanently retained by the Wallet Contract and never returned to the caller. This is a permanent loss of funds for the caller — the deposit becomes stuck in the wallet contract's balance with no code path to reclaim it, since these are `#[private]` callbacks that cannot be re-invoked by an ordinary account to trigger the refund after the fact.

### Likelihood Explanation
Reachability requires no privileged access: any relayer/predecessor invoking a normal user's signed Ethereum-style transaction through `rlp_execute` with a non-zero attached deposit, where the target is an unregistered eth-implicit account (triggering the registrar lookup) or the ERC-20 transfer path (triggering `storage_balance_of`), can hit this. Both underlying cross-contract calls are external calls to other contracts/accounts (address registrar, NEP-141 token) that can genuinely fail (e.g., insufficient gas allocated, contract busy/panicking, account not existing), which is a normal, non-adversarial occurrence, making this readily triggerable in production without any malicious actor.

### Recommendation
Add the same refund logic present in `rlp_execute_callback`'s `PromiseResult::Failed` branch to the `PromiseResult::Failed` branches of `address_check_callback` and `nep_141_storage_balance_callback`, i.e., when the registrar lookup or `storage_balance_of` call fails, create a `promise_batch_action_transfer` back to `caller_deposit.account_id` for `caller_deposit.yocto_near` before returning the error `ExecuteResponse`. Consider factoring this refund logic into a shared helper to avoid this exact class of "forgot to refund on this failure branch" duplication bug recurring in future callbacks.

### Proof of Concept
1. Deploy the Wallet Contract for an eth-implicit account `alice.eth` and fund it.
2. Have a relayer (any account, not `alice.eth` itself) call `rlp_execute` with `attached_deposit = 1 NEAR`, where the decoded Ethereum transaction is an `EOABaseTokenTransfer` whose `target` is another eth-implicit account (`TargetKind::EthImplicit`), triggering `address_check: Some(address)` in `inner_rlp_execute` [5](#0-4) .
3. Ensure the address-registrar cross-contract call fails (e.g., point `ADDRESS_REGISTRAR_ACCOUNT_ID` at a non-existent or panicking account, or starve the call of gas).
4. Observe that `address_check_callback` is invoked with `PromiseResult::Failed`, and returns `ExecuteResponse { success: false, ... }` without ever transferring back the relayer's attached 1 NEAR [6](#0-5) .
5. Verify on-chain that the wallet contract's balance increased by the attached deposit and no refund receipt was produced to the relayer's account — the deposit is permanently lost to the relayer/caller. The same PoC pattern applies to `nep_141_storage_balance_callback` by causing the `storage_balance_of` call on the target NEP-141 token to fail for an `ERC20Transfer` action.

    pub fn new(context: &ExecutionContext) -> Option<Self> {
