### Title
Unprivileged dust transfers permanently occupy a victim's per-account token slots, bricking new borrows and collateral deposits - (File: contracts/DepositToken.sol)

### Summary
An unauthenticated attacker can exhaust the shared `MAX_TOKENS_PER_USER` (30) per-account slot limit of any victim by pushing dust amounts of `DepositToken`s to them. Once the victim's combined `depositTokensOfAccount + debtTokensOfAccount` reaches 30, every code path that adds a new token entry reverts with `UserReachedMaxTokens`, so the victim cannot open new debt positions or receive/deposit collateral token types not already in their list. This is the on-chain analog of the reported bug class: an unprivileged remote party exhausting a bounded resource (file descriptors → per-account token slots) to deny service to other users.

### Finding Description
`Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= MAX_TOKENS_PER_USER` (30). [1](#0-0) [2](#0-1) 

Any transfer of a `DepositToken` to an account with a zero balance of that token forcibly registers the token in the recipient's list — the recipient never opted in: [3](#0-2) 

The attacker has two cheap vectors to push entries onto the victim's list:

1. `deposit(dust, victim)` — `deposit` mints to an arbitrary `onBehalfOf_` and `_mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the balance goes 0 → >0.
2. `transfer(victim, dust)` / `transferFrom` — `_transfer` adds the entry the same way. [4](#0-3) [5](#0-4) 

Once the victim's list is at the cap:

- `DebtToken.issue` → `_mint` → `pool.addToDebtTokensOfAccount` reverts, blocking any new synthetic debt in a debt-token the victim doesn't already hold (`contracts/DebtToken.sol:598-600`, `contracts/Pool.sol:204-208`).
- `DepositToken.deposit`/`_mint`/`_transfer`/`seize` revert for any collateral token not already in the victim's list, blocking new collateral types and inbound transfers of those tokens.
- Because the check fires inside token internals, it also poisons flows such as `NativeTokenGateway`/`VesperGateway` deposits and `SmartFarmingManager` operations routed to the victim.

Attacker cost is only dust of the underlying for each listed deposit token plus gas; the dust remains the victim's (it is a donation, not a cost sink beyond gas). There is no opt-in, minimum-amount, or allowlist check before slot consumption — `MappedEnumerableSet.add`/`Pool.addToDepositTokensOfAccount` is reached from a fully public, unprivileged entry point.

### Impact Explanation
Liveness/DoS analog: the victim is denied the protocol's core service. In the worst-case deployed configuration (a pool whose `depositTokens` set approaches 30 — `addDepositToken` itself caps at `MAX_TOKENS_PER_USER`), the victim is completely unable to borrow (`issue` always reverts) and cannot accept any new collateral type. In smaller configurations the attack degrades rather than eliminates service: each pushed token consumes one of the victim's 30 slots, shrinking the number of distinct debt/collateral positions they can hold. Existing balances remain withdrawable and debt can be repaid, so this is temporary freezing/griefing of position management rather than theft — matching the "blocks XAPI from carrying out tasks" character of the reference advisory. The victim can free slots by transferring dust back out (one tx per token, at their gas cost), but the attacker can re-fill slots, sustaining the DoS.

### Likelihood Explanation
Requires only an EOA with dust of each underlying collateral; no privileged role, oracle manipulation, or timing assumptions. However, the severity scales with how many deposit tokens the pool lists: with few collaterals the attacker only removes a few slots and the victim retains most of the 30, reducing the issue to a partial restriction. Also note the victim gains free (dust) collateral and can self-recover slots, so the attack is griefing rather than permanent freezing.

### Recommendation
Require recipient consent or a minimum balance before registering a token in the per-account list — e.g., only add to `depositTokensOfAccount` on `deposit`/`_mint` (not on plain `transfer`/`seize`), or allow anyone to call `removeFromDepositTokensOfAccount(account, token)` for tokens with dust balances below a threshold. Alternatively, decouple the slot cap from transfer mechanics by only counting entries above a meaningful balance, or raise/parameterize `MAX_TOKENS_PER_USER` while bounding the iteration cost it was introduced for.

### Proof of Concept
Foundry fork sketch (Hardhat equivalent works identically):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "contracts/Pool.sol";
import {DepositToken} from "contracts/DepositToken.sol";
import {DebtToken} from "contracts/DebtToken.sol";
import {IERC20} from "contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract TokenSlotGriefingTest is Test {
    Pool pool;          // forked Pool proxy
    DebtToken msUsdDebt; // a live DebtToken of the pool
    address[] depositTokens; // pool.getDepositTokens() result
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    function test_fillVictimSlotsBlocksIssue() public {
        // 1. For each listed deposit token, attacker deposits dust on behalf of victim
        for (uint i; i < depositTokens.length; ++i) {
            DepositToken dt = DepositToken(depositTokens[i]);
            IERC20 underlying = dt.underlying();
            deal(address(underlying), attacker, 1);
            vm.startPrank(attacker);
            underlying.approve(address(dt), 1);
            dt.deposit(1, victim); // pushes deposit token into victim's list
            vm.stopPrank();
        }

        // Alternatively / additionally: transfer dust of each deposit token to victim
        // dt.transfer(victim, 1) has the same addToDepositTokensOfAccount effect.

        // 2. Repeat until pool.debtTokensOfAccount(victim).length
        //    + pool.getDepositTokensOfAccount(victim).length == MAX_TOKENS_PER_USER (30).
        //    If the pool has <30 deposit tokens, the attacker can still consume the
        //    remaining slots by depositing dust of every collateral the victim does
        //    not yet hold; once at cap:

        // 3. Victim can no longer issue new debt in a new synthetic
        vm.prank(victim);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        msUsdDebt.issue(1e18, victim);

        // 4. Nor receive/deposit any collateral token type not already in their list
        DepositToken other = DepositToken(depositTokens[0]);
        // (assume victim had none of `other` before attacker's pushes filled the cap)
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        vm.prank(attacker);
        other.transfer(victim, 1);
    }
}
```

Reproduction notes: run against a deployed `Pool` proxy on a fork (deployments exist for mainnet/base/optimism/hemi/swell under `deployments/`); enumerate collaterals via `pool.getDepositTokens()`; assert `pool.getDepositTokensOfAccount(victim).length + pool.getDebtTokensOfAccount(victim).length == 30`, then observe `UserReachedMaxTokens` reverts on `issue` and on any transfer/deposit introducing a new token for the victim.
