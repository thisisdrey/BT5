### Title
Failed `near_withdraw` in `auth_call` permanently burns signer's wNEAR balance with no fund delivered - ([File: contracts/defuse/src/contract/intents/state.rs])

### Summary
`Contract::auth_call` synchronously debits the signer's wNEAR balance via `self.withdraw(...)` in the same receipt that dispatches `ext_wnear::near_withdraw(...).then(do_auth_call)`. Because the withdraw is committed in the original receipt while `near_withdraw`/`do_auth_call` execute in later, independent receipts, a failure of `near_withdraw` causes `do_auth_call`'s `require!(promise_result_checked_void(0).is_ok())` to panic in its own receipt without ever rolling back the already-committed debit from `token_balances`.

### Finding Description
The broken binding: `token_balances[signer_id][wnear] before − token_balances[signer_id][wnear] after == NearToken delivered to contract_id + amount re-credited by any resolver`. This fails whenever `near_withdraw` does not succeed.

Path:
1. `auth_call` calls `self.withdraw(signer_id, [(wnear, N)], Some("withdraw"), false)` synchronously, decrementing the signer's `token_balances` entry for wNEAR. [1](#0-0) 
2. It then schedules `ext_wnear::near_withdraw(N).then(do_auth_call(signer_id, auth_call))` and immediately `.detach()`s the resulting promise chain, returning `Ok(())` from `auth_call` itself. [2](#0-1) 
3. Because the outer call (e.g. `execute_intents`) returns successfully, the state mutation from step 1 is committed in that receipt, independent of what happens to the dispatched promises.
4. `near_withdraw` and `do_auth_call` execute as separate, later receipts. NEAR's `.then()` semantics guarantee the callback (`do_auth_call`) runs regardless of whether the predecessor promise succeeded — it is the callback's job to inspect the result.
5. `do_auth_call` only checks the result via `require!(promise_result_checked_void(0).is_ok(), "near_withdraw failed")` and panics if it failed. [3](#0-2) 
6. This panic reverts only `do_auth_call`'s own receipt (i.e., it correctly prevents the subsequent `ext_auth_callee::...on_auth` promise with the attached deposit from being created — so `contract_id` never receives NEAR). However, it does **nothing** to restore the signer's `token_balances` entry that was already decremented and committed in step 1's receipt.

Root cause: the debit (`self.withdraw`) and the async unwrap (`near_withdraw`) are not atomic across receipt boundaries, and there is no resolver/refund path in `do_auth_call` (unlike patterns that re-credit balances on promise failure elsewhere in the withdraw flows) to restore the balance when `near_withdraw` fails.

Attacker payload: any signer submits `AuthCall { attached_deposit: NearToken::from_yoctonear(N), contract_id: <any_contract>, msg, state_init: None }` with `N > 0` while `token_balances[signer][wnear] >= N`. No special privileges or attacker-controlled contract logic is even required — the trigger is simply a `near_withdraw` failure on the wNEAR contract (e.g., paused, insufficient backing, gas issues), which is outside the signer's control but can be induced/observed opportunistically, or simply occurs due to protocol/contract state at the time.

### Impact Explanation
The signer's wNEAR balance inside the Verifier's `token_balances` ledger is permanently decremented while no NEAR is ever delivered to `contract_id` and no resolver credits it back. This is a fund-loss bug matching the Critical category "a refund or resolver credit that does not match what failed to settle" — the Verifier's committed ledger no longer matches what it actually custodies/delivers (its total liabilities drop by N with no corresponding transfer out), and the individual signer's real funds are permanently lost with no recourse. This is repeatable per signer per `AuthCall` whenever the underlying `near_withdraw` call fails.

### Likelihood Explanation
Preconditions: the signer must hold `token_balances[signer][wnear] >= N` and must submit an `AuthCall` intent with `attached_deposit = N > 0`. The actual trigger — `near_withdraw` failing — is not directly controlled by the attacker in the general case, but is an entirely plausible operational condition (wNEAR contract paused, insufficient reserve, upgrade in progress, gas mis-estimation causing the cross-contract call to fail). Given such conditions arise, exploitation (or accidental loss) is deterministic and requires no special skill — a normal `AuthCall` submission under normal signer permissions suffices, and there's no fix-up path currently in the code to prevent the loss.

### Recommendation
Add a refund/resolver step: `do_auth_call` should re-credit `signer_id`'s wNEAR balance for `attached_deposit` when `promise_result_checked_void(0)` indicates failure, instead of (or before) panicking — mirroring the compensating-refund pattern used elsewhere for failed withdrawals (e.g., NEP-141/171/245 withdraw resolvers). Alternatively, perform the `self.withdraw` decrement only after `near_withdraw` has been confirmed successful (e.g., via a two-phase commit where the balance is held/reserved rather than immediately debited, and released back on failure).

### Proof of Concept
`cargo test` (near-workspaces sandbox) plan:
1. Deploy the Defuse contract and a stub wNEAR contract whose `near_withdraw` can be made to fail (e.g., by pausing it or having it panic unconditionally for a chosen amount).
2. Fund `signer_id` with wNEAR balance `N` in `token_balances` via a normal deposit flow.
3. Record `balance_before = balance_of(signer_id, wnear_token_id)`.
4. Submit a signed `MultiPayload` invoking `AuthCall { attached_deposit: NearToken::from_yoctonear(N), contract_id: attacker_contract, msg: "", state_init: None }` via `execute_intents`.
5. Ensure the stub wNEAR's `near_withdraw` call fails, causing `do_auth_call`'s `require!` to panic.
6. Assert `balance_of(attacker_contract)` (native NEAR) is unchanged (no funds delivered).
7. Assert `balance_of(signer_id, wnear_token_id) == balance_before - N` (bug reproduced: funds is lost) instead of the expected `balance_before` if the ledger were correctly restored — the failing assertion `balance_of(signer_id, wnear_token_id) == balance_before` demonstrates the vulnerability.
