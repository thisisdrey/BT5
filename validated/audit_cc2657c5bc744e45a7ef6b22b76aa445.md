### Title
`write-freq` rate limit for StackerDB writes is enforced only on the pull-sync scheduling path, not on the write-acceptance path (`try_replace_chunk`) - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
The StackerDB smart-contract control interface exposes a `write-freq` parameter that is meant to throttle how often a given slot's chunk may be updated [1](#0-0) , and the DB schema records a `write_time` per slot precisely to support this throttle [2](#0-1) . However, the function that actually authorizes and commits a new chunk version, `try_replace_chunk`, never consults `write_freq`/`write_time` at all — it only checks chunk size, slot existence, signer, staleness, and `max_writes` [3](#0-2) .

### Finding Description
`write_freq` is only read in one place outside of config parsing: `StackerDBSync`'s scheduling logic, which decides whether the *local* node should bother fetching a chunk from remote peers again (`if self.write_freq > 0 && write_ts + self.write_freq > now { ... continue; }`) [4](#0-3) . This is a *pull* optimization, not a *write*-acceptance gate.

The actual write-acceptance/authorization function, `try_replace_chunk`, and the message-validation function used for pushed/gossiped chunks, `validate_received_chunk`, both omit any `write_freq` check by explicit design — the doc comment on `validate_received_chunk` even says: *"NOTE: does not check write frequency, since the caller has different ways of doing this"* [5](#0-4) . But the caller that matters here — the unauthenticated HTTP write endpoint `POST /v2/stackerdb/:principal/:contract/chunks` (`RPCPostStackerDBChunkRequestHandler::try_handle_request`) — calls `tx.try_replace_chunk(...)` directly with no separate `write_freq`/`write_time` check anywhere in that path [6](#0-5) . Likewise `handle_unsolicited_StackerDBPushChunk`, which processes gossiped chunks, calls `validate_received_chunk` (no `write_freq` check) and then relies on the relay path to store it, again with no `write_freq` gate [7](#0-6) .

This is structurally analogous to the referenced Sherlock finding: a resource-limiting invariant (`maxTrainingDeposit`/here `write-freq`) is checked along one code path (deposit-balance check / pull-sync scheduling) but not along the alternate path that actually mutates state (transfer-then-deposit / direct signed HTTP POST or unsolicited push). Any signer who legitimately owns a slot (or any attacker who has captured/forged a valid signature is out of scope, but a legitimate slot owner is in scope) can call the POST chunk RPC as fast as the network/API allows, bumping the Lamport `slot_version` on every call, completely bypassing the smart-contract-stipulated `write-freq` throttle, since only `max_writes` (a version ceiling) and staleness (monotonic version) are enforced — not wall-clock frequency.

### Impact Explanation
This does not by itself provide unauthorized writes (a valid signer signature is still required, keeping this within the "signed chunk write" trust boundary), but it defeats a bandwidth/DoS-shaping control that node operators and the StackerDB-controlling smart contract rely on to bound the network-wide replication cost of a given StackerDB (`write-freq` exists specifically to bound how often the whole network needs to re-fetch/re-broadcast a slot's chunk). A legitimate slot signer (e.g., a signer set member) can flood their own slot with version bumps far faster than `write-freq` intends, forcing every replica in the network to store, hash-verify, and re-gossip an unbounded stream of chunk updates up to `max_writes` versions, exhausting replication bandwidth/storage churn network-wide — this is a bounded-but-amplifiable DoS on StackerDB replication capacity, not a memory-safety or state-integrity bypass.

### Likelihood Explanation
High likelihood for any legitimate holder of a slot signing key (e.g., a registered signer), since it requires no coordination, no race condition, and no cryptographic forgery — simply POSTing a validly-signed chunk with a monotonically incrementing `slot_version` faster than `write_freq` intends. The gap is a straightforward code-path omission (confirmed by the doc comment itself acknowledging write-freq is not checked in `validate_received_chunk`), not a timing-dependent race.

### Recommendation
Enforce `write_freq` (compared against the stored `write_time` for the slot) inside `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs`, in addition to the existing `max_writes`/staleness checks, so that the write-acceptance path itself rejects chunk replacements that arrive before `write_time + write_freq` has elapsed — mirroring the fix pattern from the referenced report ("check the invariant at the point of state mutation, not only at a peripheral decision point").

### Proof of Concept
1. Register/own a StackerDB slot with `write-freq` set to a large value (e.g., 600 seconds) via the controlling contract.
2. Sign chunk version `1` and POST it to `POST /v2/stackerdb/<issuer>/<name>/chunks` — accepted (`try_replace_chunk` passes size/slot/signer/staleness/max-writes checks).
3. Immediately sign chunk version `2` (or up to `max_writes`) with the same key and POST again — `try_replace_chunk` again does not check `write_time`, so it is accepted immediately, well before `write_freq` seconds have elapsed.
4. Repeat rapidly up to `max_writes` — every version bump is accepted, relayed via `StackerDBPushChunk` to peers `stackslib/src/net/api/poststackerdbchunk.rs:315-324`, and each peer re-validates/re-stores it via `validate_received_chunk`/`handle_unsolicited_StackerDBPushChunk`, which likewise never checks `write_freq` [8](#0-7) , demonstrating the throttle is bypassed network-wide.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
