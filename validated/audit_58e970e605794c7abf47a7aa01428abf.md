### Title
Unvalidated `AccountType` in `AccountCreateContract` lets an unprivileged user register a "Contract" account with no backing bytecode - (File: `actuator/src/main/java/org/tron/core/actuator/CreateAccountActuator.java`)

### Summary
`CreateAccountActuator.validate()` never checks the `type` field of `AccountCreateContract`. Any signed transaction from any unprivileged account can create a brand-new address whose `AccountType` is set to `Contract` even though no smart-contract bytecode is ever deployed there and no corresponding `ContractCapsule` is written to `ContractStore`. This mirrors the CVE-2026-4105 root cause: the "class"/type parameter supplied by the caller when registering a new object is not validated, leaving behind an attacker-controlled object of a privileged class that other privileged code paths implicitly trust.

### Finding Description
`CreateAccountActuator.validate()` explicitly comments out the only check that would have validated the contract's `type` field: [1](#0-0) 

and the account is then persisted using whatever `AccountType` the caller supplied, unchecked, in `execute()`: [2](#0-1) 

The capsule constructor faithfully copies `contract.getType()`/`getTypeValue()` into the persisted `Account` proto with no validation that the caller is actually deploying a contract: [3](#0-2) 

The protobuf schema allows the caller to freely choose `AccountType.Contract` for `AccountCreateContract`: [4](#0-3) 

Elsewhere in the codebase, `AccountType.Contract` is treated as a trust signal that the address is a genuine smart contract with an entry in `ContractStore` and version metadata, e.g. in `TransferActuator.validate()`: [5](#0-4) 

Here the code comment "this can not happen" at line 148-150 explicitly assumes an account can never have `AccountType.Contract` without a `ContractStore` entry — an assumption that `CreateAccountActuator`'s missing type validation breaks. Multiple other subsystems (`UnfreezeBalanceActuator`, `FreezeBalanceActuator`, `DelegateResourceActuator`/`DelegateResourceProcessor`, `FreezeBalanceProcessor`, `VMActuator`) also branch on `AccountType.Contract` as an indicator of "this address is a smart contract," so an attacker-fabricated fake-Contract-type account can desynchronize the assumptions those actuators make about resource ownership, delegation eligibility, and self-destruct/beneficiary semantics.

### Impact Explanation
An unprivileged, unauthenticated (from the chain's perspective, any funded) account can:
1. Pre-register any not-yet-existing address as `AccountType.Contract` before the legitimate deployer sends `CreateSmartContract` there, potentially griefing/blocking legitimate deployments or confusing address-based contract detection logic used by downstream actuators.
2. Trigger the "this can not happen" branch in `TransferActuator` (line 148-150), turning a defensive/unreachable assertion into a reachable `ContractValidateException` path — a functional/logic bypass in code that assumed the invariant `AccountType.Contract ⇒ ContractStore.has(address)` always holds.
3. Feed a `Contract`-typed account with no bytecode into other actuators (freeze/unfreeze/delegate resource, EVM-compatibility gating) that gate behavior on `AccountType.Contract`, since those checks trust the type field rather than independently verifying a `ContractCapsule` exists.

This is a medium-severity logic/invariant-violation bug reachable from a single broadcastable transaction (`AccountCreateContract`), analogous to the systemd bug where an unvalidated class parameter leaves behind an attacker-controlled, "privileged-looking" object that other code paths trust.

### Likelihood Explanation
High likelihood of reachability: `AccountCreateContract` is a standard, unprivileged, broadcastable transaction type available to any account with sufficient balance to pay the account-creation fee (`calcFee()` = `getCreateNewAccountFeeInSystemContract()`), requiring no special permission bits beyond the default `Active`/`Owner` multisig operations bitmap. No committee proposal or feature flag gates this behavior — the type-check code is simply commented out, so exploitation requires only constructing the protobuf `AccountCreateContract` with `type = Contract` and broadcasting it.

### Recommendation
Restore and enforce validation of `AccountCreateContract.type` in `CreateAccountActuator.validate()`: reject the transaction unless `type == AccountType.Normal` (or `AssetIssue`, if that is still a legitimately caller-settable type), and/or require that any account marked `Contract` be created exclusively through the `CreateSmartContract` code path where a corresponding `ContractCapsule` is atomically written to `ContractStore`. Additionally, audit and harden all downstream checks (`TransferActuator`, `UnfreezeBalanceActuator`, `FreezeBalanceActuator`, `DelegateResourceActuator`/`Processor`) that currently trust `AccountCapsule.getType() == AccountType.Contract` as a proxy for "has deployed bytecode," and instead verify `ContractStore.get(address) != null` directly wherever that invariant matters.

### Proof of Concept
1. Attacker account `A` (any normal funded account) broadcasts a transaction with contract type `AccountCreateContract`:
   ```
   AccountCreateContract {
     owner_address: A
     account_address: X   // any not-yet-existing address, e.g. a precomputed future contract address
     type: Contract
   }
   ```
2. `CreateAccountActuator.validate()` performs no check on `type` (lines 115-117 are commented out) and passes.
3. `CreateAccountActuator.execute()` persists `AccountCapsule` for `X` with `AccountType.Contract` set, but no entry is written to `ContractStore` for `X`.
4. Any subsequent logic that relies on `AccountType.Contract` implying a real deployed contract (e.g. `TransferActuator.validate()`'s `AllowTvmCompatibleEvm` branch, which explicitly assumes "this can not happen") now observes a `Contract`-typed account with `contractStore.get(X) == null`, breaking the invariant and producing the "impossible" validate-exception path, or otherwise causing inconsistent handling for `X` in any downstream actuator that gates on account type.   public AccountCapsule(final AccountCreateContract contract, long createTime,
      boolean withDefaultPermission, DynamicPropertiesStore dynamicPropertiesStore) {
    if (withDefaultPermission) {
      Permission owner = createDefaultOwnerPermission(contract.getAccountAddress());
      Permission active = createDefaultActivePermission(contract.getAccountAddress(),
          dynamicPropertiesStore);

      this.account = Account.newBuilder()
          .setType(contract.getType())
          .setAddress(contract.getAccountAddress())
          .setTypeValue(contract.getTypeValue())
          .setCreateTime(createTime)
          .setOwnerPermission(owner)
          .addActivePermission(active)
          .build();

          .setType(contract.getType())
          .setAddress(contract.getAccountAddress())
          .setTypeValue(contract.getTypeValue())
          .setCreateTime(createTime)
