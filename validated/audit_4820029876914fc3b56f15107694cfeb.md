## Title
Un-delegate resource-usage transfer is calculated pro-rata against a receiver's *total* delegated pool instead of the specific delegator's actual contribution, causing bandwidth/energy usage misallocation between multiple delegators - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
The `UnDelegateResourceActuator` (and its TVM counterpart `UnDelegateResourceProcessor`) compute how much of a receiver's already-consumed bandwidth/energy usage should be transferred back to an un-delegating owner using a *proportional* formula based on the receiver's aggregate frozen balance from ALL delegators, not the usage actually attributable to that specific owner's delegation.

### Finding Description
When an owner un-delegates resources from a receiver, `transferUsage` is computed as:
```java
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
``` [1](#0-0) 

This same pattern appears in the native-contract path used by TVM `unDelegateResource` opcodes: [2](#0-1) 

`receiverCapsule.getNetUsage()` is the receiver's *total accumulated bandwidth usage*, aggregated across resources acquired from potentially many different delegating owners (`getAllFrozenBalanceForBandwidth()` sums frozen balance from every delegator plus the receiver's own). The formula distributes that single global usage figure proportionally by `unDelegateBalance / totalFrozenBalance`, i.e. exactly the same "distribute an event/attribution-specific quantity by current relative share of a shared pool" pattern flagged in the external report (where entrance fees owed to one specific lender were diluted across all lenders in proportion to their present share of debt).

Concretely: if a receiver gets resource delegated from owner A (large amount) and owner B (small amount), and the receiver's bandwidth usage was driven almost entirely by consumption that happened while only A's delegation existed, a later un-delegation by B will still claw back `netUsage * (B's balance / total balance)` of usage — attributing to B a slice of consumption it never caused, and leaving a mismatched (understated) portion attributed to A. Conversely, whichever owner un-delegates first can capture a disproportionate share of the "usage debt" transfer, and repeated partial delegate/undelegate cycles by multiple owners will not converge to the true owner-level attribution, since there is no per-delegator usage ledger — only the receiver's single aggregate `netUsage`/`energyUsage` counter and total frozen-balance denominator.

### Impact Explanation
This does not directly transfer TRX/asset value between accounts, but it does misallocate bandwidth/energy resource usage credit between multiple delegators to the same receiver. Because `unDelegateIncrease`/`unDelegateIncreaseV2` then feed this mis-derived `transferUsage` into the owner's own resource window calculation (`ResourceProcessor.unDelegateIncrease` / `unDelegateIncreaseV2`), an owner can end up with an understated or overstated "usage window", i.e., an inconsistency between the resource an account is entitled to consume for free (based on its own frozen stake) and what it is actually charged, in scenarios with multiple concurrent delegators un-delegating in different orders/amounts. This can allow an owner to reclaim more free bandwidth/energy capacity than it should have contributed to, at the expense of other co-delegators to the same receiver — a resource-accounting integrity issue reachable purely by unprivileged `UnDelegateResourceContract` transactions or TVM `unDelegateResource` native calls.

### Likelihood Explanation
Trivially reachable: any account can freeze-and-delegate BANDWIDTH/ENERGY to a receiver (`DelegateResourceActuator`/`DelegateResourceProcessor`) and later un-delegate (`UnDelegateResourceActuator`/`UnDelegateResourceProcessor`), and any account can delegate to the same receiver as another party, so the "multiple lenders/delegators to one shared pool" precondition from the analog report is easy to construct with ordinary signed transactions. No special privileges are required.

### Recommendation
Track per-delegator usage attribution explicitly (e.g., record usage debt at delegation/consumption time per `DelegatedResourceCapsule`, similar to a reward-per-share/index model as already used elsewhere in the codebase for witness voting rewards, see `RewardViCalService`/`DelegationStore.accumulateWitnessVi`), rather than deriving `transferUsage` from a proportional split of the receiver's single aggregate usage counter against the total combined frozen balance from all delegators.

### Proof of Concept
1. Owner A delegates a large BANDWIDTH balance to Receiver R; Receiver R consumes a large amount of bandwidth (increasing `netUsage`) while this is the only delegation.
2. Owner B later delegates a small BANDWIDTH balance to the same Receiver R (increasing `getAllFrozenBalanceForBandwidth()`), without R consuming any additional bandwidth attributable to B.
3. Owner B calls `UnDelegateResourceContract` to un-delegate its balance. Per [1](#0-0) 
, `transferUsage` is computed from R's total `netUsage` times `B's balance / total combined frozen balance`, so B receives back a non-zero share of usage it never generated, at A's expense.
4. Repeating this with several delegators un-delegating in different orders demonstrates the split never matches actual per-owner consumption, since no per-delegator usage ledger exists — the same "distribute a specific-attribution quantity across a shared pool by current proportional share" root cause as the referenced entrance-fee bug.
