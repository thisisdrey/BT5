### Title
Lost wNEAR storage_deposit stake on failed `storage_deposit` call in withdraw chain - (File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs)

### Summary
`internal_ft_withdraw` debits both the withdrawn token amount and `storage_deposit` (in wNEAR) from `owner_id` in a single ledger update, but the refund/resolver logic in `ft_resolve_withdraw` only ever re-credits the `token` `amount` on transfer failure and never re-credits the wNEAR `storage_deposit` amount `X` regardless of what happens to the chained `storage_deposit` call. If the `storage_deposit` call to `token` reverts, `X` (already unwrapped into raw NEAR and sent as attached deposit) is refunded by the NEAR runtime to the predecessor of that failed action — i.e. back into the Defuse contract account's raw NEAR balance — with no code path crediting it back to the signer's Multi-Token ledger balance.

### Finding Description
The broken binding: `owner_id`'s wNEAR ledger balance decrease of `X` (via `Nep141TokenId::new(wnear_id)` debit at [1](#0-0)  ) MUST equal either (a) NEAR actually staked as storage for `receiver_id` on `token`, or (b) wNEAR re-credited to `owner_id` via `ft_resolve_withdraw`.

Trace: `internal_ft_withdraw` calls `self.withdraw()` which subtracts both `Nep141TokenId(token)` by `amount` and `Nep141TokenId(wnear_id)` by `X` in the same ledger call [2](#0-1) . It then chains `ext_wnear::near_withdraw` (unwraps `X` wNEAR into raw NEAR held by the Defuse contract) into `do_ft_withdraw` [3](#0-2) . In `do_ft_withdraw`, after checking only that `near_withdraw` itself succeeded via `promise_result_checked_void(0)`, the code builds `p` as `ext_storage_management::ext(withdraw.token).storage_deposit(...)` attaching `X`, then unconditionally extends that same promise with `ext_ft_core::ext_on(p).ft_transfer(_call)(...)` attaching only 1 yoctoNEAR [4](#0-3) . Because `ext_on` schedules the transfer call as a dependent action on the same promise chain, it executes regardless of whether the preceding `storage_deposit` action on `token` succeeded or panicked — NEAR's promise-dependency semantics do not require the parent action to succeed for the dependent action to run. If `token.storage_deposit(receiver_id)` panics (e.g., blocked/blacklisted receiver, insufficient registration logic, or any token-specific revert), the attached `X` NEAR deposit is refunded by the runtime to the predecessor of that failed receipt — the Defuse contract's own account — not credited back to the ledger.

Finally, `ft_resolve_withdraw` only inspects `promise_result_checked_void(0)`/`promise_result_checked_json::<U128>(0)` for the `ft_transfer(_call)` result and refunds only `amount` of `token` back to `sender_id` on failure [5](#0-4) . There is no branch anywhere that inspects the result of the `storage_deposit` sub-call or re-credits wNEAR `X` to `owner_id`. The `require!` guard at [6](#0-5)  only protects against `near_withdraw` failing (i.e., failure to unwrap wNEAR), not against `storage_deposit` failing after the unwrap succeeded.

Attacker/user payload: `FtWithdraw{ token: <any FT whose storage_deposit reverts for receiver_id>, receiver_id, amount, storage_deposit: Some(NearToken::from_near(X)), min_gas: None }` signed via `ft_withdraw`/`execute_intents`.

### Impact Explanation
The signer's own wNEAR balance of `X` is irreversibly deducted from the Verifier's ledger with no corresponding value transferred anywhere the signer can recover (it ends up as unaccounted raw NEAR sitting in the Defuse contract's own account balance, outside the ledger). This matches the Critical category "a refund or resolver credit that does not match what failed to settle" / "user funds permanently frozen": the resolver refund logic explicitly handles only the `token` `amount`, never the `wnear` `storage_deposit` leg. This is repeatable on every `ft_withdraw` call with `storage_deposit` set against any token whose `storage_deposit` implementation can revert for the given `receiver_id` (blacklists, receiver-specific storage policies, or a token deliberately deployed to revert). Each occurrence permanently strands `X` wNEAR per call, scaling with how many such withdrawals a victim/self issues.

### Likelihood Explanation
Preconditions: caller must control (or find) an FT contract whose `storage_deposit` call reverts for the chosen `receiver_id`, must hold wNEAR balance `X` and the token `amount` in the Verifier, and issue a normal signed `ft_withdraw`/`execute_intents` call — no privileged role required, entirely reachable by any unprivileged signer as stated in the audit scope. This is trivially reproducible by deploying a minimal mock FT with a reverting `storage_deposit`, so likelihood/feasibility is high; the only cost is the `X` wNEAR itself and gas.

### Recommendation
In `do_ft_withdraw`, check the result of the `storage_deposit` call before proceeding to `ft_transfer(_call)` (e.g., via a private callback that inspects `promise_result_checked_void` for the `storage_deposit` receipt), and if it failed, abort the transfer and have `ft_resolve_withdraw` (or a new resolver) re-credit `X` wNEAR back to `owner_id` in addition to refunding `token` `amount`. Alternatively, always propagate a wNEAR refund path in `ft_resolve_withdraw` that inspects both the `storage_deposit` and `ft_transfer(_call)` sub-results and re-credits any unconsumed `storage_deposit` NEAR (converted back to wNEAR) to the signer.

impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
