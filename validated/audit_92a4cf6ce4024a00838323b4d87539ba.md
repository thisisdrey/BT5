Audit Report

## Title
ERC20 Asset Transactor credits nominal amount into XCM holding without verifying actual tokens moved, enabling accounting mismatch for fee-on-transfer/deflationary tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` implement XCM's `TransactAsset` trait for ERC20 tokens on `pallet-revive`, calling the contract's `transfer` function and trusting only its boolean return value rather than measuring the actual balance delta. For fee-on-transfer or deflationary ERC20 tokens (a normal, spec-compliant pattern), `transfer` can return `true` while moving fewer tokens than requested, causing the XCM holding register to be credited with an overstated nominal amount that diverges from the real ERC20 balance held by the `TransfersCheckingAccount`.

## Finding Description
In `withdraw_asset_with_surplus`, after calling `IERC20::transferCall { to: checking_address, value: amount }`, the code checks only `is_success` (the decoded boolean) and, if true, unconditionally constructs `Erc20Credit(amount)` into the XCM holding — the full nominal amount, not a measured delta: [1](#0-0) 

The `Erc20Credit` type's own documentation confirms this design choice — that "the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime": [2](#0-1) 

Symmetrically, `deposit_asset_with_surplus` calls `transfer(beneficiary, amount)` from the checking account and treats `Ok(true)` as full success without any `balanceOf` delta check: [3](#0-2) 

Neither function queries `balanceOf` on the checking account or beneficiary before/after the `transfer` call. This is verified as the sole logic path for both directions of ERC20 transacting in production code; there is no reconciliation step anywhere in this file. The existing test-suite guards (`smart_contract_not_erc20_will_error`, `smart_contract_does_not_return_bool_fails`, referenced in the claim) only exercise reverting contracts or contracts that fail to return a bool — none exercise a contract that returns `true` while transferring less than the requested `amount`, so they do not close this gap.

Regarding the `impl_fungibles.rs` extension of this same bug pattern cited in the original claim: that file is gated behind `#![cfg(any(feature = "std", feature = "runtime-benchmarks", test))]`, meaning `mint_into`/`burn_from` there are test/benchmark-only code, not part of the production runtime's `FungiblesAdapter` path used on live chains. This part of the claim should not be treated as a live production vulnerability, but the core `erc20_transactor.rs` logic is unconditional production code and registered in `asset-hub-westend`'s XCM configuration (`cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`), confirming it is a live, reachable path.

## Impact Explanation
This breaks the "conserve value and settle exactly once to the rightful beneficiary and amount" invariant for XCM asset transfers on Asset Hub. The corrupted value is the amount credited into the XCM holding register (`Erc20Credit(amount)`), which can exceed what the `TransfersCheckingAccount` actually received on-chain. Repeated use with a fee-on-transfer/deflationary ERC20 causes the checking account's real balance to progressively fall behind the sum of nominal amounts the runtime believes are backed, which can cause deposit/refund legs of subsequent (potentially unrelated, honest) XCM programs to fail non-deterministically — a fund-lock/DoS condition for that asset class, reachable via a fully public, unprivileged entry point (`pallet_xcm::execute`/`transfer_assets`).

## Likelihood Explanation
Any user can deploy a spec-compliant fee-on-transfer ERC20 contract on `pallet-revive` and reference it in a normal `pallet_xcm::execute` XCM program that triggers `ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus`. No governance, validator collusion, or relayer trust is required — only a standard, non-malicious ERC20 token behavior. This is registered as a live matcher/transactor in `asset-hub-westend`'s runtime XCM configuration, so the path is reachable on a real parachain runtime as included in this repository.

## Recommendation
Before crediting `Erc20Credit(amount)` in `withdraw_asset_with_surplus`, and before treating `deposit_asset_with_surplus` as fully successful, query `balanceOf` on the `TransfersCheckingAccount`/beneficiary immediately before and after the `transfer` call, and use the observed delta — not the requested `amount` — as the value credited/settled. If the delta is less than requested, fail with `XcmError::FailedToTransactAsset` or credit only the measured delta so XCM bookkeeping never diverges from the real on-chain ERC20 balance.

## Proof of Concept
1. Deploy a spec-compliant ERC20 contract on Asset Hub's `pallet-revive` (e.g., modeled after the `MyToken` fixture used in the existing `withdraw_and_deposit_erc20s`-style tests) whose `transfer(to, value)` retains e.g. 2% of `value` as a fee, forwarding only 98% to `to`, while still returning `true`.
2. Submit an XCM program via `pallet_xcm::execute` performing `withdraw_asset` for `erc20_transfer_amount` of this token followed by `deposit_asset` to a beneficiary, exercising `withdraw_asset_with_surplus` then `deposit_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`.
3. Instrument the test to query `balanceOf(checking_account)` before/after step 2's withdraw leg: observe the checking account's real balance increases by only 98% of `amount`, while `Erc20Credit(amount)` records the full nominal `amount` in holding.
4. Repeat the withdraw/deposit cycle across multiple XCM executions and show the checking account's real ERC20 balance progressively diverges from the cumulative nominal amount the runtime believes it holds, eventually causing a `deposit_asset_with_surplus` call to fail for an unrelated honest user's XCM program due to insufficient real balance in the checking account.
