## Title
Heap buffer over-read in `InputZipFile::ProcessCentralDirEntry` extra-field parsing from an attacker-controlled zip/jar archive - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar`'s zip central-directory parser reads attacker-controlled length fields from a `.zip`/`.jar` file (e.g. a `http_archive`/`http_jar` download, or a `srcjar`/dependency jar consumed during a build) and walks the "extra field" chain using length values taken directly from the file, with no check that the declared `extra_field_length` or per-field `data_size` stays within the mapped input file's bounds.

### Finding Description
`InputZipFile::ProcessCentralDirEntry` reads the fixed Central Directory Header fields (compressed/uncompressed size, `file_name_length`, `extra_field_length`, `file_comment_length`) directly from the mmap'ed archive buffer with `get_u4le`/`get_u2le`, without any `EnsureRemaining`-style bounds check against the actual mapped-file length [1](#0-0) . It then walks the extra-field records with a loop driven entirely by attacker-supplied `data_size` values:

```
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
``` [2](#0-1) 

`extra_p` can be advanced past `p` (the intended end-of-extra-field boundary) by a crafted `data_size`, and the loop only terminates on `extra_p != p`, so if `extra_p` overshoots `p` it keeps reading `header_id`/`data_size` values (and dereferencing `get_u8le(extra)` for the ZIP64 case) from memory beyond the declared extra-field region — and potentially beyond the mmap'ed file entirely once several central-directory entries are chained, since `p` (now the cursor for the *next* CDH) is derived from this same unchecked walk. This contrasts with the local-file-header path (`InputZipFile::ProcessLocalFileEntry`), which explicitly calls `EnsureRemaining()` before consuming `file_name_length`/`extra_field_length` bytes [3](#0-2) ; no equivalent check exists for the central-directory path.

This is directly analogous to CVE-2018-7553's root cause: a size/count field taken from crafted, untrusted binary input (PCX raster in `sam2p`; ZIP CDH/extra-field lengths in `ijar`) drives a read/copy loop without validating it against the actual buffer bounds, leading to an out-of-bounds read (and, given `ijar`'s downstream copies of extra-field bytes into freshly allocated output buffers in tools like `singlejar`'s `AppendToDirectoryBuffer`, potential over-read of adjacent heap/mmap memory).

### Impact Explanation
`ijar` (and the related `zipper`/`singlejar` tooling built on the same header classes) processes zip/jar files that originate from external, attacker-influenceable sources: `http_jar`/`http_archive` downloads, third-party dependency jars pulled into a build, or CI-built artifacts from an untrusted branch. A malformed central directory with an inflated extra-field `data_size` causes the parser to read past the intended extra-field/entry boundary. Depending on layout, this can read adjacent mapped memory (information disclosure into internally computed sizes/filenames) or, chained across multiple crafted entries, walk `p` off the end of the mmap'ed region, causing a crash (SIGSEGV) or, in the worst case, an out-of-bounds read whose value influences subsequent size/offset computations used for allocations and copies in downstream consumers (`ProcessFile`, `singlejar`'s CDH-copy in `output_jar.cc`).

### Likelihood Explanation
Reachability is straightforward and requires only a hostile zip/jar file: `ijar` is invoked automatically by Bazel to generate interface jars for every `java_library`-like target, meaning any jar dependency (including ones fetched via `http_jar`/`http_archive`/Maven-style external repositories, or a jar produced by an untrusted CI build on a branch) is parsed by this code with default flags — no opt-in feature or unusual configuration is needed. No checksum/integrity check protects the internal structure of an already-downloaded archive; verifying the archive's own sha256 does not stop the archive itself from being maliciously well-formed-but-crafted at the byte level.

### Recommendation
Add explicit bounds checks in `InputZipFile::ProcessCentralDirEntry`'s extra-field walk (and in the fixed-field reads that precede it) mirroring `EnsureRemaining()` in `ProcessLocalFileEntry`: verify that `extra_field_length` does not exceed the remaining bytes in the mapped file before advancing `p`, and inside the extra-field loop verify `extra_p + 4 <= p` before reading `header_id`/`data_size`, and `extra_p + data_size <= p` before advancing `extra_p`, aborting/erroring out otherwise (as `ExtraField::find` already does for the `singlejar` header classes at `src/tools/singlejar/zip_headers.h:99-115`, which do implement this bound check — `third_party/ijar/zip.cc` lacks the equivalent guard).

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell` reproduction would:
1. Hand-craft a minimal zip file whose single Central Directory Header declares `extra_field_length = N` (small, e.g. 4), but whose first embedded extra-field record declares `data_size` far larger than `N` (e.g. `0xFFFF`), similar to the existing `CreateZipWithMalformedExtraField()` helper already present for `singlejar` header-bounds testing [4](#0-3) , but fed through `ijar`'s `ZipExtractor`/`InputZipFile::ProcessCentralDirEntry` instead of `singlejar`.
2. Place this crafted CDH at the very end of the mmap'ed input file (no trailing padding) so the unchecked `extra_p`/`p` walk reads past the mapped region.
3. Run `ijar`'s extractor (`ZipExtractor::Create` + `ProcessAll`, or `CalculateOutputLength`) on this file and observe a crash or a sanitizer (ASan) report of heap/mmap buffer over-read inside `ProcessCentralDirEntry`, whereas a corresponding well-formed archive is processed cleanly.

*Note: I could not fully trace all downstream consumers of `p`/`extra_p` after the overshoot (e.g., exact behavior when the CDH is not the last entry, or how `MappedInputFile`'s underlying mmap size interacts with the overshoot) within the tool budget available, so the precise memory-safety class (over-read vs. crash-only) should be confirmed with an ASan-instrumented reproduction before filing a fix.*

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
