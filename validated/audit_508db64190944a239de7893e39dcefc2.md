### Title
Single unstaked IP can exhaust the global QUIC connection-slot budget via unfinished handshakes, starving legitimate TPU peers - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`run_server`'s per-IP `ConnectionRateLimiter` and the `overall_connection_rate_limiter` are only ever charged *after* a handshake successfully completes (`register_connection` / `consume_tokens` in `setup_connection`), while the only gate applied to *unverified* in-flight handshakes is a single **global** `ClientConnectionTracker` slot count (`qos.max_concurrent_connections()`). An attacker on one IP can therefore repeatedly open QUIC `Incoming` connections and never finish the handshake, holding global slots for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) each, without ever tripping per-IP rate limiting, and can keep the shared slot pool saturated indefinitely by re-triggering before slots free up.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:331-407`), each accepted `Incoming` is checked against:
1. `overall_connection_rate_limiter.current_tokens() == 0` — a read-only check [1](#0-0) 
2. `rate_limiter.is_allowed(ip)` — also read-only, and explicitly documented to allow first-seen IPs unconditionally [2](#0-1) 
3. `ClientConnectionTracker::new(..., qos.max_concurrent_connections())`, which is the only *mutating*, capacity-bounding check before the handshake, and it is global (not per-IP) [3](#0-2) 

Only after `incoming.accept()` succeeds does `setup_connection` await the handshake with a bounded timeout, and only on `Ok(new_connection)` does it call `rate_limiter.register_connection(&from.ip())` and `overall_connection_rate_limiter.consume_tokens(1)` [4](#0-3) . If the peer never completes (or the peer resets), the `Connecting` future eventually resolves as an error or times out after `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) [5](#0-4) , and neither rate limiter is ever touched — matching the question's premise that `register_connection`/`consume_tokens` are unreachable for abandoned handshakes.

The result: `ConnectionRateLimiter` (per-IP) is completely inert against this pattern (as intended by its own doc comment — it only tracks IPs that have "asserted control" via a completed handshake), and `overall_connection_rate_limiter`'s token bucket is never decremented by aborted attempts either, so it provides no throttling for this pattern despite its stated purpose ("protect against connection attempt bursts with a global rate-limiter"). The single real gate is `ClientConnectionTracker`'s global `open_connections` counter, bounded by `qos.max_concurrent_connections()` (e.g. `max_staked_connections * 5/4` in `SimpleQos`) [6](#0-5) . Because this budget is shared across *all* source IPs, one attacker sending only cheap QUIC Initial packets (never finishing crypto handshake) from a single unstaked IP can occupy up to the entire global slot count for rolling ~2s windows, and by continuously repeating, keep the pool saturated, causing `ClientConnectionTracker::new` to fail for legitimate peers (`refused_connections_too_many_open_connections` counter increments) while `connection_rate_limited_per_ipaddr` for the attacker's IP stays at 0 the whole time.

### Impact Explanation
This is a QoS-evasion / TPU-availability DoS: an unstaked, unprivileged remote client can starve legitimate senders' ability to open TPU QUIC connections by exhausting the shared, IP-agnostic `open_connections`/`outstanding_incoming_connection_attempts` slot budget, without ever being penalized by the per-IP `ConnectionRateLimiter` that is meant to police abusive peers. This matches the "connection/stream/per-IP QoS limits bypassed, starving legitimate senders of TPU capacity" bounty category for `poh/src/poh_service.rs`-adjacent TPU ingress scope.

### Likelihood Explanation
Preconditions are minimal: a reachable TPU QUIC endpoint and the ability to send UDP packets that quinn accepts as `Incoming` (a valid QUIC Initial with matching ALPN). No stake, keys, or special config are required. The attack is fully repeatable and only bounded by the attacker's ability to keep opening/abandoning connections faster than the 2-second handshake timeout releases slots — a cheap, sustainable rate for a single host.

### Recommendation
Add a per-IP cap on *outstanding, unverified* connection attempts (in addition to the existing global `ClientConnectionTracker` cap), e.g., track and bound `outstanding_incoming_connection_attempts` per source IP before `incoming.accept()`. Additionally, make `overall_connection_rate_limiter` actually bound connection *attempts* (consume a token at `incoming.accept()` time, refunding on failure if desired) rather than only successful handshakes, so its doc comment's stated purpose ("protect against connection attempt bursts") is actually enforced.

### Proof of Concept
Integration test plan (extending the pattern used in `tpu-client-next/tests/connection_workers_scheduler_test.rs::test_rate_limiting`):
```rust
#[tokio::test]
async fn test_unfinished_handshake_churn_exhausts_global_slot_budget() {
    // Configure server with a small max_concurrent_connections (via SwQosConfig/SimpleQosConfig)
    // so the attack is feasible in test time, e.g. max_staked_connections small.
    let SpawnTestServerResult { stats, server_address, cancel, .. } =
        setup_quic_server(None, QuicStreamerConfig::default_for_tests(), SwQosConfig::default());

    // Attacker: repeatedly create client endpoints connecting to server_address from the
    // same source IP, calling `.connect()` but never awaiting/completing the handshake
    // (drop the Connecting future immediately), firing faster than
    // QUIC_CONNECTION_HANDSHAKE_TIMEOUT (2s) to keep global slots saturated.
    for _ in 0..N {
        let endpoint = make_bare_client_endpoint(&server_address).await;
        let connecting = endpoint.connect(server_address, "localhost").unwrap();
        drop(connecting); // abandon before handshake completes; never calls register_connection
    }

    // Legitimate peer attempts to connect concurrently and should be refused due to
    // exhausted global open_connections budget, NOT per-IP rate limiting.
    let legit = make_client_endpoint(&server_address, None).await;
    // assert legit connection fails / times out

    assert_eq!(stats.connection_rate_limited_per_ipaddr.load(Ordering::Relaxed), 0);
    assert!(stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed) > 0
        || stats.open_connections.load(Ordering::Relaxed) >= max_concurrent_connections);

    cancel.cancel();
}
```
Expected assertions: `connection_rate_limited_per_ipaddr == 0` throughout the attack, while `refused_connections_too_many_open_connections` rises and legitimate connection attempts fail/time out due to the exhausted global `open_connections` slot pool.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
}
