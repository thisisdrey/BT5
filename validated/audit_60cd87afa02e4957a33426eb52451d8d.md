## Title
Out-of-bounds read / uncaught exception when parsing ABI-encoded array arguments in TVM precompiled contracts - (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
CVE-2014-9844 is an out-of-bounds read in ImageMagick's RLE decoder caused by trusting attacker-supplied length/offset fields inside a crafted file without validating them against the buffer bounds. The analogous pattern exists in java-tron's precompiled-contract ABI decoders `extractBytesArray` and `extractSigArray`, which trust attacker-controlled length and offset words taken directly from TVM call data and index into the `words`/`data` arrays without bounds checking.

### Finding Description
`extractBytesArray` and `extractSigArray` read an attacker-controlled length (`len = words[offset].intValueSafe()`) and then iterate `words[offset + i + 1]` up to `len` times, and compute a further attacker-controlled `bytesOffset` that is used to index both the `words` array and the raw `data` byte array: [1](#0-0) 

Neither loop validates that `offset + i + 1 < words.length` before dereferencing `words[offset + i + 1]`, nor that the computed byte offset/length fed into `extractBytes` (`Arrays.copyOfRange(data, offset, offset + len)`) stays within `data.length`: [2](#0-1) 

Because `words` is the ABI-word array built directly from the precompiled contract's `data` parameter (the calldata of a `CALL`/`STATICCALL` to that precompile address), a caller fully controls both `len` and `bytesOffset`. A crafted `len` larger than `words.length - offset - 1`, or a crafted `bytesOffset` that pushes the computed slice outside `data`, throws an uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` inside the decoder — the same bug class as `ReadRLEImage` trusting an unchecked length/offset from crafted input.

The project's own test suite documents that this failure mode is real and, pre-activation of a mitigating feature flag, is unguarded: "this precompile has no outer catch, so a too-short input raises inside the decoder; that is the documented pre-activation failure mode": [3](#0-2) 

### Impact Explanation
Any account that can broadcast a `TriggerSmartContract` transaction (or any contract that performs a `CALL`/`STATICCALL`) can invoke the affected precompiled contract with a crafted `data` payload whose array-length and offset words are inconsistent with the buffer size. If the resulting runtime exception is not caught somewhere higher in the TVM call-dispatch chain, it propagates out of actuator execution during block application, which can abort transaction/block processing on the node — a denial-of-service (node halt) triggerable by an unprivileged transaction sender, matching the "out-of-bounds read causing a crash/DoS" impact class of CVE-2014-9844.

### Likelihood Explanation
Reachability requires only a signed transaction calling the exposed precompile address with attacker-chosen ABI words — no special privilege, node, or witness status is needed. The existing test explicitly reproduces this exact failure mode, confirming the code path is exercised in practice pre-activation of the mitigating VM config flag.

### Recommendation
Add explicit bounds checks in `extractBytesArray` and `extractSigArray` before dereferencing `words[offset + i + 1]` (verify `offset + i + 1 < words.length`) and before calling `extractBytes`, validate that `offset` and `offset + len` are non-negative and within `data.length`, throwing a caught/handled exception (e.g., returning `Pair.of(false, EMPTY_BYTE_ARRAY)`) instead of letting `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` escape uncaught into block-processing code.

### Proof of Concept
Not independently confirmed end-to-end because the exact call-site/guard conditions in the `ValidateMultiSign`-style precompile's `execute()` method (which invokes `extractSigArray`) and whether TVM's call-dispatch layer wraps precompile execution in a catch-all were not visible in the retrieved code. Conceptually: craft ABI-encoded calldata to the affected precompile where the first array-length word (`len`) exceeds the number of remaining `words`, or where a nested offset word decodes to a value that, after the offset arithmetic, points outside `data`'s length — this drives `extractBytesArray`/`extractSigArray`/`extractBytes` to throw an uncaught runtime exception, matching the documented `testTip854PreActivationNoOp` behavior.     int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }

  private static byte[] extractBytes(byte[] data, int offset, int len) {
    return Arrays.copyOfRange(data, offset, offset + len);
  }
