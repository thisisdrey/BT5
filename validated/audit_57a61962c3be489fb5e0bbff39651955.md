### Title
Legacy (pre-harden) Bancor-formula Exchange precision uses unscaled `double` math causing minimum-trade truncation and pool-drain rounding drift - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeProcessor` computes TRC10 bancor-style exchange amounts using raw `double` arithmetic on relay "virtual supply" values (`1_000_000_000_000_000_000L`) without any explicit fixed-point scaling analogous to ManualVic's unscaled `interestPerSecond`. Just as the reported bug truncates a low interest rate to a granular integer (creating either 0 or hugely skewed rates), `exchangeToSupply`/`exchangeFromSupply` truncate the computed `double` result via `(long)` cast, which for small `quant` relative to large token balances collapses to `0` or introduces large relative deviation from the true bancor price, since the calculation is not resolved in a scaled/BigDecimal domain like the newer `SafeExchangeProcessor`.

### Finding Description
`ExchangeProcessor.exchangeToSupply` and `exchangeFromSupply` compute the relay/output token quantities purely with IEEE-754 `double` operations: [1](#0-0) 

The result is truncated toward zero with a plain `(long)` cast rather than being computed in a scaled fixed-point domain (as ManualVic's raw, unscaled `interestPerSecond` truncates to an integer). This is the exact same bug class described in the report: a value that must represent a very small fraction of a large quantity is computed and truncated without adequate precision, so:
- For low relative trade sizes (`quant` small vs. `balance`), the computed output can round to a value far off from the theoretically correct bancor price, or to zero, exactly like the ManualVic case where `interestPerSecond = 1` for low rates massively overshoots the target APR.
- `double` also has only ~15-17 significant decimal digits, so with `TRX_PRECISION` at 6 decimals and balances that can reach the `getExchangeBalanceLimit()` ceiling, the relative error compounds across repeated calls to `Maths.pow` with exponents `0.0005` / `2000.0`.

Confirming the codebase itself already treats `ExchangeProcessor` as an imprecise/legacy path: a second, "safe" implementation `SafeExchangeProcessor` recomputes the identical formula using `BigDecimal` with 18-digit precision, and it is dispatched only when `hardenedCalc` (i.e. the hard-fork flag) is set: [2](#0-1) [3](#0-2) 

The project's own regression test proves the double-based and BigDecimal-based paths diverge for real trade inputs (`Assert.assertNotEquals(anotherTokenQuant, result)`), i.e. the legacy path is measurably imprecise relative to the "hardened"/fixed-point path: [4](#0-3) 

`ExchangeTransactionActuator.execute` reaches this exact code path from a single signed `ExchangeTransactionContract` transaction broadcast by any account: [5](#0-4) 

### Impact Explanation
Because the amount is not computed in a properly scaled fixed-point representation, unprivileged users invoking `ExchangeTransactionContract` on pools where the harden flag is not yet active for a given network/version can obtain outputs that deviate materially from the correct bancor price for the current pool state, particularly for small trade sizes relative to large pool balances (this is analogous to the report's ~15 bps -> arbitrarily large deviation as trade size shrinks relative to balance). Repeated exploitation of systematically favorable rounding drains value from the exchange pool balances, which are directly redeemable for real TRX/TRC10 assets by other participants — an unbacked-value / fund-drain condition on the shared liquidity pool.

### Likelihood Explanation
Any account holding a minimal balance of a listed token can call `ExchangeTransactionContract` directly through the public transaction broadcast path with no special privilege, and can freely choose transaction size to probe for favorable rounding, making exploitation straightforward to attempt repeatedly at low cost. The severity is limited to networks/chain-configurations where the "harden" flag has not yet been activated, since the fix (`SafeExchangeProcessor`) already exists in the codebase for post-harden execution.

### Recommendation
- Ensure `hardenedCalc`/harden-related flags gating `SafeExchangeProcessor` are activated across all deployed networks, and consider deprecating/removing the double-based `ExchangeProcessor` path entirely rather than keeping it reachable behind a runtime flag.
- For any remaining unscaled-double computations in exchange/reward paths, adopt BigDecimal/BigInteger fixed-point arithmetic with explicit scale (as already done in `SafeExchangeProcessor`) and reject trades whose computed output is inconsistent with expected precision bounds (similar to the "Not precise enough" check already present in `ExchangeWithdrawActuator`).

### Proof of Concept
Concrete exploitation requires knowledge of the exact chain parameters (whether `hardenedCalc`/harden flags are active on the target network) which could not be fully verified in this review; the divergence between `ExchangeProcessor` (double) and `SafeExchangeProcessor` (BigDecimal) demonstrated in the existing unit test `ExchangeProcessorTest.testStrictMath` (asserting `assertNotEquals(anotherTokenQuant, result)` for identical inputs) is direct evidence of the precision defect. Full exploit development (finding trade sizes/pool ratios that maximize rounding-favorable drift on a live/harden-inactive network) requires further investigation with runtime access, which is outside the scope of this static analysis.

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}
