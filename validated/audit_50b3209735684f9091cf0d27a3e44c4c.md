### Title
Postponed action receipts survive `DeleteAccount`/`CreateAccount`, letting stale self-targeted actions (e.g. `DeployContract`) execute against a recreated account - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (`core/store/src/utils/mod.rs:504-575`) purges `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie entries for a deleted account, but never touches `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount` entries keyed by that same `receiver_id`. If the deleted account had a pending self-targeted `ActionReceipt` (e.g. carrying `Action::DeployContract`) waiting on an unmet `input_data_ids` dependency, that fully-serialized `Receipt` (stored via `set_postponed_receipt`, `core/store/src/utils/mod.rs:120-127`) remains in state. Once the account name is recreated and the missing `DataReceipt` eventually arrives, `Runtime::process_receipt` (`runtime/runtime/src/lib.rs:1398-1455`) blindly looks the stale receipt back up by `(receiver_id, receipt_id)` and executes it against whatever account now occupies that id.

### Finding Description
- `set_postponed_receipt` stores the entire `Receipt` (actions included) under `TrieKey::PostponedReceipt{receiver_id, receipt_id}` [1](#0-0) , and `process_action_receipt` writes `PostponedReceiptId`/`PendingDataCount` entries for each missing `input_data_id` [2](#0-1) .
- `action_delete_account` calls `remove_account` to clean up state before nulling the in-memory `Account` [3](#0-2) .
- `remove_account` only removes `Account`, `ContractCode`, access/gas keys, and `ContractData` — it has no code path that scans/removes `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` for the account being deleted [4](#0-3) .
- When the missing `DataReceipt` for the stale postponed receipt later arrives (in the same or a later chunk, potentially long after the account was deleted and recreated), `process_receipt`'s `Data` arm resolves `PostponedReceiptId{receiver_id: X, data_id}` → decrements `PendingDataCount` → on reaching zero, fetches the stored `Receipt` via `get_postponed_receipt(state_update, account_id, receipt_id)` and executes it with `apply_action_receipt` against the account currently living at `X` [5](#0-4) . There is no check that the account is the "same" account that originally created the postponed receipt (no generation/version binding between an `Account` and postponed receipts targeting it).
- Because the stale receipt's `predecessor_id` is `X` itself (a self-call, which is how an account authorizes `DeployContract` on itself), the actor-permission check for `DeployContract` (`actor_id == account_id`) is satisfied purely by account-id string equality, regardless of who currently controls `X` after recreation. This lets an attacker deploy code onto an account the current controller never signed a `DeployContract` for.

### Impact Explanation
This is a scoped authorization-escaping bug: the code that ends up running on the recreated `X` was never authorized by whoever recreated and funded `X`. If exploitable end-to-end, the victim who recreates `X` believing it is a fresh, code-free account and later deposits funds and calls what they believe is a plain account would instead be calling attacker-planted logic that can route the balance to an attacker address. This matches "theft of funds deposited into a re-created account" / authorization escalation across accounts.

### Likelihood Explanation
Exploitability depends on preconditions that meaningfully constrain likelihood:
- The attacker must control `X` and construct a self-targeted `FunctionCall` receipt whose resulting `DeployContract` action is blocked on an unresolved `input_data_id` (e.g. via a cross-contract callback that never completes), then delete `X` via `DeleteAccount` while that postponed receipt is still pending. `action_delete_account`/`check_actor_permissions` does not verify the absence of pending postponed receipts before allowing deletion, so this step is not blocked.
- Crucially, a **victim** must independently choose to (re)create the exact same `AccountId` `X` and fund it, believing it to be fresh. This is a real but non-trivial precondition — it requires the victim to target the specific reused name (e.g. a subaccount name pattern, or an implicit account whose full 64-hex address happens to be reused), which is not a matter of leaked keys or validator/node access, but it is not a generic "any account can be attacked" scenario either.
- I was not able to fully trace `check_actor_permissions`/`check_account_existence` (`runtime/runtime/src/actions.rs`) in this session to confirm there is no additional gate preventing a stale receipt from targeting a recreated account (e.g. a possible check tying the receipt to account existence/version at postponement time). This is the main remaining uncertainty in the analysis, and would need to be confirmed by direct code inspection or by running the integration test below.

### Recommendation
When an account is removed, `remove_account` should also purge all `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` trie entries keyed by that account, or the runtime should reject/refund postponed receipts whose target account was deleted before their dependencies resolved. Alternatively, bind postponed receipts to an account "epoch"/generation counter that is bumped on every `DeleteAccount`+`CreateAccount` cycle, and refuse to execute a postponed receipt whose captured generation no longer matches the current account's generation.

### Proof of Concept
Integration test plan (test-loop, analogous to `test-loop-tests/src/tests/create_delete_account.rs` and `runtime/runtime/src/tests/apply.rs::test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Create account `X` with an access key controlled by "attacker".
2. Submit a `FunctionCall` receipt on `X` that produces a self-targeted `ActionReceipt` on `X` containing `Action::DeployContract(malicious_code)`, gated on an `input_data_id` that is never satisfied in this test until step 4 (simulate via directly constructing the postponed receipt/state entries as done in `insert_postponed_action_receipt`/`action_receipt_awaiting` helpers).
3. Submit `DeleteAccount(X)` from attacker; assert `X` no longer exists (`get_account` returns `None`) while asserting via direct trie reads that `TrieKey::PostponedReceipt{X, receipt_id}` and `TrieKey::PendingDataCount{X, receipt_id}` are still present in the trie.
4. Submit `CreateAccount(X)` from "victim" plus `Transfer(X, deposit)`.
5. Deliver the missing `DataReceipt` for the earlier pending dependency; assert the stored postponed `Receipt` executes and `action_deploy_contract` installs `malicious_code` on the (recreated) `X` — check `X`'s `local_contract_hash`/`storage_usage` changed without any `DeployContract` action ever being submitted by the victim.
6. Victim submits a benign-looking `FunctionCall` (self-authorized) to `X`; assert the malicious injected contract runs and transfers `X`'s balance to an attacker-controlled account, proving fund loss despite the victim never deploying that code.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
