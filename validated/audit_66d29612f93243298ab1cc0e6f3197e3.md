Based on the investigation, I found a plausible analog in the TVM precompiled-contract calldata parsers, but I was unable to fully verify (due to running out of tool iterations) whether the calling `execute()` methods in `BatchValidateSign`/`ValidateMultiSign` wrap this logic in an exception handler that would downgrade the impact to a mere revert rather than a genuine crash/OOM. ### Title
Unbounded attacker-controlled array-length field in TVM precompile calldata decoding causes out-of-bounds array access / uncontrolled allocation - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytesArray` and `PrecompiledContracts.extractSigArray` read a "length" word directly from attacker-supplied TVM calldata (`words[offset].intValueSafe()`) and use it, unbounded, both to size a newly allocated `byte[len][]` array and to drive a loop that indexes further into the same `words` array (`words[offset + i + 1]`) without ever checking `len` against the actual size of `words` (i.e., the actual decoded calldata length) [1](#0-0) . This mirrors the NBNS bug class: an attacker-controlled length field is trusted for both allocation size and copy/index bounds without being validated against the real size of the backing buffer.

### Finding Description
`extractBytesArray(DataWord[] words, int offset, byte[] data)` only guards against `offset` itself being out of range (`offset > words.length - 1`), but the subsequent `len = words[offset].intValueSafe()` is fully attacker-controlled (any 32-byte word placed at that offset in the transaction's contract-call data) and is used unchecked both to allocate `new byte[len][]` and to index `words[offset + i + 1]` / `words[offset + bytesOffset + 1]` in the loop body [2](#0-1) . `extractSigArray` has the identical unbounded-`len` pattern [3](#0-2) . Both helpers are used to decode the input to signature-batch precompiled contracts (`BatchValidateSign`, referenced at [4](#0-3) ), which any smart contract can invoke via a `CALL`/`STATICCALL` opcode to the precompile address — i.e., reachable from an ordinary, unprivileged `TriggerSmartContract` transaction. As with the NBNS `name_len` field being trusted for fixed-size destination buffers, here `len` is trusted for both allocation size and array indexing without any upper bound check relative to `words.length`, so a crafted `len` can either trigger `ArrayIndexOutOfBoundsException` deep in the loop or attempt a huge allocation (`new byte[len][]`) leading to `OutOfMemoryError`.

### Impact Explanation
If the resulting `ArrayIndexOutOfBoundsException`/`OutOfMemoryError` is not caught at a sufficiently high level in the precompile's `execute()` path, it can propagate and crash/halt the node's transaction-execution thread while processing an otherwise ordinary contract call, denying service to that node (and, if triggered deterministically by all nodes executing the same block, potentially a broader halt). This falls into the "node crash or halt" impact category described in the validation rubric.

### Likelihood Explanation
Reaching this code only requires deploying or calling a contract that performs a `CALL` to the `BatchValidateSign`/`ValidateMultiSign` precompile address with crafted calldata containing an oversized length word — something any unprivileged account can do by broadcasting a normal `TriggerSmartContractContract` transaction, making this highly reachable if the bounds issue is real.

### Recommendation
Add an explicit bound check in `extractBytesArray` and `extractSigArray` verifying that `len >= 0` and that `offset + len + 1 <= words.length` before allocating `new byte[len][]`/`new byte[bytesArray.length][]` or entering the loop, mirroring the existing `isValidAbiEncoding` bounds-check helper already present in the same file [5](#0-4) .

### Proof of Concept
Unverified/conceptual: craft a transaction invoking a contract that `CALL`s the `BatchValidateSign` (or `ValidateMultiSign`) precompile with ABI-encoded input where the array-length word at the expected `offset` is set to a very large value (e.g., `0xFFFFFFFF`) while the actual calldata is short. This should cause `extractBytesArray`/`extractSigArray` to either throw `ArrayIndexOutOfBoundsException` when accessing `words[offset + i + 1]` beyond the real array bounds, or throw `OutOfMemoryError` when allocating `new byte[len][]`. I was not able to trace the full `execute()` call chain of `BatchValidateSign`/`ValidateMultiSign` to confirm whether an outer try/catch neutralizes this into a safe revert; this should be verified directly against `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java` before treating this as confirmed exploitable.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
