### Title
Pausable/blacklistable collateral underlying freezes `DepositToken.withdraw` — ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
Metronome's `repay`/`liquidate` paths are insulated from this bug class because they only move internal balances (`SyntheticToken.burn`, `DebtToken._burn`, `DepositToken.seize` → `_transfer` bookkeeping), never the underlying ERC20 [1](#0-0) [2](#0-1) . However, the exit path is not: `_withdraw` ends with `_pool.treasury().pull(to_, _withdrawn)`, which performs a `safeTransfer` of the underlying collateral token [3](#0-2) . If the underlying (e.g., a pausable stablecoin used as collateral) has transfers paused, every withdrawal of that collateral reverts, freezing all depositors' funds until the token is unpaused. There is no alternative withdrawal path — `withdraw`, `withdrawFrom`, and `flashWithdraw` all funnel through the same `_withdraw`.

### Finding Description
- `DepositToken.deposit` pulls underlying into the Treasury via `safeTransferFrom` — reverts while the token is paused, blocking new deposits [4](#0-3) .
- `DepositToken._withdraw` burns `msdTOKEN` and calls `Treasury.pull`, which `safeTransfer`s the underlying to the recipient — reverts while paused, blocking all exits [5](#0-4) .
- The internal `_burn` and fee `_transfer` happen before the external call, so the whole transaction reverts atomically; no accounting corruption, just liveness loss [6](#0-5) .
- Importantly, `Pool.liquidate` still functions during an underlying pause because `depositToken_.seize` only moves `msdTOKEN` share balances internally [7](#0-6) . The original report's primary impact (liquidation/repay DoS → insolvency) therefore does **not** carry over; the residual impact is exit-blocking only.
- Note: for blacklist-style restrictions (e.g., USDC blacklisting of a specific address), `withdraw(amount_, to_)` allows specifying an arbitrary recipient, partially mitigating the single-address case — only a full token-level pause blocks all users [8](#0-7) .

### Impact Explanation
Temporary freezing of user funds: while the underlying collateral token's transfers are paused, no holder of the corresponding `msdTOKEN` can redeem collateral. Interest continues accruing on borrowers, and positions can still be liquidated at the share level, but seized collateral cannot be converted to underlying until the pause lifts. The condition is exogenous (requires the third-party token issuer to pause, analogous to the fee-on-transfer / token-behavior classes in scope), not attacker-triggerable.

### Likelihood Explanation
Low. It requires Metronome governance to have listed a pausable token as collateral (the deployment set includes stablecoin-backed and vault-share collateral) and that token's issuer to activate the pause. When it occurs, the freeze affects 100% of that collateral's depositors simultaneously rather than a single position.

### Recommendation
Add a contingency path that lets users exit their `msdTOKEN` position without an immediate underlying transfer — e.g., burn shares to a claimable balance inside `Treasury` redeemable after unpause, or allow `withdraw` to a "pull-over-time" escrow. Alternatively, restrict collateral listing to non-pausable assets, or accept and document the freeze risk explicitly.

### Proof of Concept
Foundry fork test outline (mainnet fork):
1. Take a deployed `Pool`/`DepositToken` whose `underlying()` is a pausable token (e.g., USDC-backed deposit token).
2. Impersonate the token's `pauser`/`owner` via `vm.prank` and call `pause()` on the underlying (simulates the exogenous trigger).
3. A depositor calls `depositToken.withdraw(amount, user)` → reverts inside `Treasury.pull`'s `safeTransfer` (`Pausable: paused`).
4. Show `pool.liquidate(...)` against an unhealthy account still succeeds (seize is internal), confirming impact is limited to withdrawal freezing.
5. Unpause and repeat withdrawal → succeeds, confirming the freeze is temporary, not permanent loss.
