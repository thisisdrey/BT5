### Title
Account name (username) whitespace is not neutralized on `AccountUpdateContract`, enabling visually-spoofed/duplicate account names - (File: `actuator/src/main/java/org/tron/core/utils/TransactionUtil.java`)

### Summary
`UpdateAccountActuator.validate()` accepts any account name that passes `TransactionUtil.validAccountName()`, but that check only verifies byte length and does not restrict the byte content at all, so a name consisting of, prefixed with, or suffixed by whitespace/control characters is accepted and stored as-is. This mirrors CVE-2025-55127's bug class (improper neutralization of whitespace in a username), letting a name be visually indistinguishable from another account's name while being a different key in storage and indexing.

### Finding Description
`TransactionUtil.validAccountName` delegates to `validBytes`, which only enforces a maximum length and allows empty input; it does not check byte content at all (unlike `validAccountId`/`validAssetName`, which delegate to `validReadableBytes` and reject any byte outside the printable ASCII range `0x21`–`0x7E`, which excludes space `0x20` and all control characters): [1](#0-0) 

`validReadableBytes`, used for account IDs and asset names, explicitly rejects whitespace and unreadable bytes: [2](#0-1) 

`UpdateAccountActuator.validate()` only calls `validAccountName`, then persists the raw bytes into both the account record and the account name index, and rejects re-registration only via an exact byte-for-byte `has()` lookup: [3](#0-2) 

`execute()` writes the untrimmed bytes directly to the account and to the account name index: [4](#0-3) 

No trimming or normalization happens anywhere else in the path (`AccountCapsule.setAccountName` stores the raw `ByteString` bytes verbatim; there is no strip/trim call).

Because the check operates purely on byte length, an attacker can broadcast an `AccountUpdateContract` with an account name such as `"ownerTest "` (trailing space), `" ownerTest"` (leading space), or with embedded/invisible whitespace characters. This name is accepted, stored, and indexed as a distinct key in `AccountIndexStore` even though a legitimate account already holds the visually identical name `"ownerTest"`. UIs/exchanges/wallets that render the raw name will show what looks like the same account name for two different addresses, creating exactly the "virtually indistinguishable... potentially leading to confusion" condition described in CVE-2025-55127, but here reachable directly on-chain by any unprivileged transaction broadcaster via the `AccountUpdateContract` actuator/HTTP-JSON-RPC path into `Wallet`.

### Impact Explanation
This enables account-name spoofing/impersonation: any address holder can claim a name that is visually identical (via leading/trailing/embedded whitespace or unreadable bytes) to an existing, possibly well-known or verified, account name. Downstream consumers (exchanges, explorers, wallets) that trust `account_name` for display or duplicate-detection can be misled into treating the attacker's account as the legitimate one, facilitating phishing, deposit misdirection, or bypass of "name already exists" uniqueness checks that are meant to prevent exactly this kind of collision. This is a concrete unauthorized-impersonation/confusion vector reachable by a single signed transaction from any account holder.

### Likelihood Explanation
High likelihood: no special privileges are required — any account holder can submit an `AccountUpdateContract` (subject only to `allowUpdateAccountName` dynamic property gating re-updates, not content). The whitespace/control-byte bypass requires no unusual tooling; a standard signed transaction with a crafted `account_name` byte string suffices.

### Recommendation
Apply the same content restriction used for `validAccountId`/`validAssetName` (or explicit trimming/whitespace rejection) to `validAccountName` in `TransactionUtil.java`, rejecting or trimming leading/trailing whitespace and disallowing control/whitespace bytes, and re-check the resulting normalized name against `AccountIndexStore` for duplicates before accepting the update in `UpdateAccountActuator`.

### Proof of Concept
1. Build an `AccountUpdateContract` with `owner_address` = attacker's address and `account_name` = `ByteString.copyFromUtf8("ownerTest ")` (visually identical to an existing account named `"ownerTest"`, differing only by a trailing space).
2. Broadcast the signed transaction; `UpdateAccountActuator.validate()` calls `TransactionUtil.validAccountName(accountName)`, which only checks `bytes.length <= 200`, so validation passes.
3. `execute()` stores the name on the attacker's account and inserts it into `AccountIndexStore`, which succeeds because the byte-for-byte key `"ownerTest "` differs from `"ownerTest"`, so the "This name is existed" check in `validate()` does not trigger.
4. Any wallet/explorer that renders `account_name` now displays what appears to be the same name for two different accounts/addresses.

  private static boolean validReadableBytes(byte[] bytes, int maxLength) {
    if (ArrayUtils.isEmpty(bytes) || bytes.length > maxLength) {
      return false;
    }
    // b must be readable
    for (byte b : bytes) {
      if (b < 0x21) {
        return false; // 0x21 = '!'
      }
      if (b > 0x7E) {
        return false; // 0x7E = '~'
      }
    }
    return true;
  }
