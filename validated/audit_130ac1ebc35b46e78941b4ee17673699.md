### Title
`claim_swap` deletes `PendingSwaps` entry even when the underlying transfer fails, permanently freezing the source's reserved funds - (File: substrate/frame/atomic-swap/src/lib.rs)

### Summary
`claim_swap` unconditionally removes the `PendingSwaps` storage entry after invoking `swap.action.claim(...)`, regardless of whether that claim actually succeeded in moving funds. Because the swap action's `claim` implementation swallows any transfer error into a `bool`, a target can trigger (or simply experience) a failed transfer while the pallet still deletes the only on-chain record that would let the source recover the reserved funds via `cancel_swap`.

### Finding Description
In `claim_swap`: [1](#0-0) 

`swap.action.claim(&swap.source, &target)` for the default `BalanceSwapAction` is implemented as: [2](#0-1) 

`repatriate_reserved` is called and only its success/failure is captured as a `bool` (`succeeded`); the `DispatchResult` is discarded. Back in `claim_swap`, regardless of the value of `succeeded`, the code proceeds to unconditionally call `PendingSwaps::<T>::remove(target.clone(), hashed_proof)` and returns `Ok(())`. There is no re-reservation, no error propagation, and no alternate recovery path.

The only other way to release a source's reserved balance is `cancel_swap`, which requires the `PendingSwaps` entry to still exist: [3](#0-2) 

If `claim`'s underlying transfer fails (e.g. `repatriate_reserved` cannot move funds into the target's free balance — insufficient reserved balance due to concurrent slashing/reaping of the source, target-side deposit restrictions, or other `Currency`-implementation-specific failure conditions), the swap record is destroyed anyway. The source's funds remain reserved (i.e., they were never actually transferred or released) but there is no longer any pallet-level record referencing that reservation, so `cancel_swap` can never be called again for it (`Error::NotExist`). Since ordinary users have no direct extrinsic to `unreserve` arbitrary balances outside of pallet-mediated flows, the reserved amount is permanently stuck.

This exactly matches the "ghost accounting" pattern described in the target question: state (`PendingSwaps`) advances/settles even though the underlying resource movement did not atomically succeed, and no rollback of the bookkeeping happens.

### Impact Explanation
This results in permanent, unrecoverable freezing of user funds (the source's reserved balance) whenever the claim action's transfer fails for any reason after the pending swap already exists. This matches the "Required Impacts" criterion of "permanent user-fund or bridge-state lock." It does not, by itself, create a false mint or double-payout, but it is a genuine fund-loss/freeze bug reachable purely through the unprivileged `claim_swap` extrinsic (called by the target, an unprivileged party who could deliberately arrange for the underlying transfer to fail, or simply be unlucky if triggered by unrelated reserve-balance drift on the source's account).

### Likelihood Explanation
Likelihood depends on how easy it is to make `repatriate_reserved` fail while the `PendingSwap` entry still exists and matches. This can happen non-adversarially (e.g., the source's account being reaped/slashed elsewhere between `create_swap` and `claim_swap`, reducing its actual reserved balance below the recorded swap value), and can plausibly also be engineered by a malicious target depending on the concrete `ReservableCurrency`/`fungible` implementation wired into a given runtime's `SwapAction`. Since `SwapAction` is a pluggable trait (`type SwapAction: SwapAction<...>`), runtimes using custom actions with more failure-prone `claim` implementations increase this likelihood further.

### Recommendation
`claim_swap` should only remove the `PendingSwaps` entry (and emit `SwapClaimed { success: true, .. }`) when the underlying `claim` truly succeeded. On failure, either: (a) leave the `PendingSwaps` entry intact so the source can still `cancel_swap` after `end_block`, or (b) propagate the transfer error via `?` and abort the whole extrinsic (reverting nothing, since nothing else was mutated), letting the caller retry. The `SwapAction::claim` trait method should also be changed to return `DispatchResult` instead of `bool` so failures aren't silently discarded.

### Proof of Concept
1. `source` calls `create_swap(target, hashed_proof, BalanceSwapAction::new(value), duration)`, reserving `value` from `source`.
2. Before `target` claims, the actual reserved balance backing this swap becomes insufficient at the `Currency` level for reasons independent of `PendingSwaps` bookkeeping (e.g., a portion of `source`'s reserved balance is consumed/reduced by another mechanism, or the `ReservableCurrency`/`fungible` implementation's `repatriate_reserved` returns `Err` for the given `BalanceStatus::Free` transition into `target`).
3. `target` calls `claim_swap(proof, action)` with the correct proof and matching `action`.
4. `swap.action.claim(...)` returns `false` (transfer failed), but `claim_swap` still executes `PendingSwaps::<T>::remove(...)` and returns `Ok(())`, emitting `SwapClaimed { success: false }`.
5. `source` (or anyone) later calls `cancel_swap(target, hashed_proof)`; it fails with `Error::NotExist` because the entry no longer exists, and `source`'s reserved funds can never be reclaimed through this pallet.

		pub fn cancel_swap(
			origin: OriginFor<T>,
			target: T::AccountId,
			hashed_proof: HashedProof,
		) -> DispatchResult {
			let source = ensure_signed(origin)?;

			let swap = PendingSwaps::<T>::get(&target, hashed_proof).ok_or(Error::<T>::NotExist)?;
			ensure!(swap.source == source, Error::<T>::SourceMismatch);
			ensure!(
				frame_system::Pallet::<T>::block_number() >= swap.end_block,
				Error::<T>::DurationNotPassed,
			);

			swap.action.cancel(&swap.source);
			PendingSwaps::<T>::remove(&target, hashed_proof);

			Self::deposit_event(Event::SwapCancelled { account: target, proof: hashed_proof });

			Ok(())
		}
