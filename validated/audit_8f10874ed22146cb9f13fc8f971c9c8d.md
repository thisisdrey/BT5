### Title
Handshake re-key path skips `verify_secp256k1`, allowing unsigned/mis-signed key takeover of an already-authenticated peer connection - (File: stackslib/src/net/chat.rs)

### Summary
`validate_handshake` only calls `message.verify_secp256k1(&handshake_data.node_public_key)` when `self.connection.get_public_key()` is `None` [1](#0-0) . Once a public key has already been learned for a connection, the `Some(_)` branch performs only an outbound-address consistency check and never re-verifies the message signature against the (old or new) key [2](#0-1) . `update_from_handshake_data` then unconditionally overwrites `self.connection`'s tracked public key with whatever `handshake_data.node_public_key` the wire message contains [3](#0-2) , breaking the invariant that an accepted peer public key must equal the key that actually signed the authenticating message.

### Finding Description
The intended equality is: *the public key stored for a peer connection must always equal the key used to produce a valid `secp256k1` signature over the `Handshake` message that installed it.* This holds only on the very first handshake (`None` branch, chat.rs:1058-1070). On any subsequent `Handshake` for the same connection (`Some(_)` branch, chat.rs:1072-1091), the code performs no signature verification at all — it only checks, and only for outbound connections, that the self-reported `addrbytes`/`port` match the observed socket address. For inbound connections (the case directly reachable by a remote, unprivileged attacker who dials the node's P2P port) there is no check whatsoever in this branch.

`handle_handshake` calls `validate_handshake`, and on `Ok(_)` proceeds to call `update_from_handshake_data`, which reads `handshake_data.node_public_key`, decodes it to a `Secp256k1PublicKey`, and calls `self.connection.set_public_key(Some(pubk))` regardless of whether the message was ever cryptographically tied to that key [4](#0-3) . Thus an attacker who has already completed one valid handshake (trivial: they control their own peer/private key) can send a second `Handshake` whose `node_public_key` is a different, freshly generated valid secp256k1 key, with an arbitrary/garbage `Signature`. `validate_handshake` skips `verify_secp256k1` (Some branch), only checks that the key decodes (chat.rs:1094-1102), that it isn't expired (chat.rs:1104-1111), and that it isn't the local peer's own key (chat.rs:1114-1124) — none of which require the message to be signed by the claimed key. The connection's tracked identity is then silently swapped to a key for which no proof of possession via this message was ever demonstrated.

### Impact Explanation
This is an authentication-bypass in the peer-identity layer: the P2P subsystem's notion of "this connection is authenticated as public key K" can be altered by an unsigned/mis-signed message once the initial handshake has occurred. Any downstream logic that trusts `connection.get_public_key()` as an integrity-checked identity (neighbor-walk reputation/allow-list decisions, StackerDB chunk-push authorization tied to a peer's advertised key, relay/ban bookkeeping) is now trusting an attacker-supplied key that was never proven to be held by the sender of that specific message. This matches the Critical category "auth bypass," since it defeats the authentication guarantee the handshake protocol is supposed to provide for the lifetime of a connection, and it is trivially repeatable per connection.

### Likelihood Explanation
Preconditions: the attacker only needs to be a normal remote peer that can open a TCP connection to the node's P2P port and complete one legitimate handshake (no admin role, no secret, no privileged position) — this is the baseline "unprivileged remote attacker" defined in scope. After the first handshake succeeds, `self.connection.get_public_key()` becomes `Some(_)`, permanently disabling signature verification for all future `Handshake` messages on that connection (for inbound peers, unconditionally). The attacker can then send any number of crafted `Handshake` messages, at zero cost, to swap the tracked key at will.

### Recommendation
In the `Some(_)` branch of `validate_handshake`, still require `message.verify_secp256k1(&handshake_data.node_public_key)` to succeed (proving the sender holds the new key's private key) before allowing a re-key, in addition to (not instead of) the existing address-consistency check for outbound connections. Reject with `net_error::InvalidMessage`/`net_error::InvalidHandshake` when this fails, and leave the previously stored public key intact.

### Proof of Concept
Rust test in `stackslib/src/net/chat.rs` test module:
1. Construct two `ConversationP2P` test peers as in existing handshake tests (see the module's existing `convo_handshake_*` tests for setup pattern of `LocalPeer`, `PeerNetwork`, and `ConversationP2P::new`).
2. Perform a first, correctly-signed `Handshake` (`StacksMessageType::Handshake` with `node_public_key` = `pk1`, signed with `pk1`'s private key) through `handle_handshake`; assert success and that `connection.get_public_key() == Some(pk1)`.
3. Build a second `StacksMessage` with `StacksMessageType::Handshake(HandshakeData { node_public_key: pk2_buf, .. })` where `pk2` is a different freshly generated key, but sign the message with an unrelated/garbage signature (or sign with `pk1`'s key instead of `pk2`, so `verify_secp256k1(&pk2_buf)` would fail if it were called).
4. Call `handle_handshake` (or directly `validate_handshake`) with this second message.
5. Assert: currently the call returns `Ok(_)` and `connection.get_public_key()` becomes `Some(pk2)` — demonstrating the key is swapped without signature verification. The fix should instead cause `validate_handshake` to return `Err(net_error::InvalidMessage)` (mirroring the `None`-branch error path at chat.rs:1064-1070), and `connection.get_public_key()` should remain `Some(pk1)`.
