## Title
Storage-deposit double-counting on same-contract reentry inflates `ContractInfo` counters and permanently under-refunds deposits — ([File: substrate/frame/revive/src/exec.rs])

### Summary
The FairSide bug is a class of "checkpoint accrual asymmetry": one side of a paired accounting operation (tokenize→mint) is never applied, so the other side's later reduction (redeem→burn) operates on a stale/zero baseline and either reverts or produces wrong accounting, permanently locking value. `pallet-revive`'s storage-deposit metering has the same failure mode: on same-contract reentry, a "preview-applied" pending storage diff is written into the persisted `ContractInfo` by the child frame, but the parent's `own_contribution` (the diff that produced that preview) is never consumed/reset. When the parent later finalizes, it re-applies that same diff a second time on top of the now-already-updated `ContractInfo`, permanently inflating `storage_items` / `storage_bytes` / `storage_*_deposit`. Because subsequent refunds are computed pro-rata against these inflated counters (`Diff::update_contract`), all later `clear_storage` refunds under-pay, effectively locking a portion of the depositor's funds in the contract's held deposit.

### Finding Description
`push_frame` in `substrate/frame/revive/src/exec.rs` applies the parent frame's pending storage diff to a cloned `ContractInfo` before creating a nested frame, and persists that clone via `AccountInfo::<T>::insert_contract`, so that child frames can see the parent's pending writes for refund pro-rating: [1](#0-0) 

This "preview-apply" mechanism (introduced to fix contract-issues#213, documented in `prdoc/stable2603/pr_10920.prdoc`) makes the parent's pending diff visible to nested frames but does **not** consume/bank the parent's `own_contribution`: [2](#0-1) 

The documented fix for this exact regression is `prdoc/pr_12267.prdoc`, which describes adding `RawMeter::bank_pending_changes` and `Frame::bank_pending_changes_and_invalidate` so that a parent's pending diff is "banked" (applied once and its `own_contribution` reset) at the cache-invalidation site, preventing the same diff from being re-applied when the parent's `finalize()` runs later: [3](#0-2) 

However, searching the actual pallet code (`substrate/frame/revive/src/exec.rs`, `substrate/frame/revive/src/metering/*.rs`) for the fix's implementation (`bank_pending_changes`, `bank_pending_changes_and_invalidate`) returns no matches — only the older `apply_pending_storage_changes` helper (from PR#10920) exists in `exec.rs`, with no "banking"/consumption step for `own_contribution`. This means the corrupted-value mechanism described in PR#12267 — the parent's `own_contribution` diff surviving in the meter after the preview-applied version is already baked into the persisted `ContractInfo` — is still present in this codebase: for `X` writes `K1` → calls itself (reentry) → writes `K2`, the pre-call write to `K1` is applied to the persisted `ContractInfo` by the child's `insert_contract`, and the parent's `own_contribution` (still holding the `K1` diff) is reapplied a second time when the parent's own `finalize()` runs, inflating `storage_items`, `storage_bytes`, `storage_item_deposit`, `storage_byte_deposit`.

The corrupted value is the persisted `ContractInfo.storage_items` / `storage_bytes` / `storage_item_deposit` / `storage_byte_deposit` fields, which are then used as the denominator for all future refund pro-rating in `Diff::update_contract`: [4](#0-3) 

Because the denominator (`info.storage_bytes` / `info.storage_items`) is inflated relative to the actual bytes/items really held, `ratio = removed / info.storage_bytes` is computed too small, so `clear_storage` refunds less than it should — the difference remains stuck on hold under `HoldReason::StorageDepositReserve` and is not returned to the depositor on ordinary storage clearing. Existing guards do not stop this: `Diff::update_contract`'s `.min(FixedU128::from_u32(1))` clamp only prevents *over*-refund, it does nothing to correct an inflated denominator, and there is no invariant check anywhere that cross-validates `ContractInfo` counters against the actual number of trie keys/bytes held by the contract.

### Impact Explanation
This is a public, permissionless entrypoint issue: any account can deploy a contract that reenters itself (`CallFlags::ALLOW_REENTRY` for PVM, or default `AllowReentry` for non-zero-value EVM calls) and write storage before and after the reentrant call. Every such contract permanently accumulates inflated storage accounting, which under-refunds storage deposits on every future `clear_storage`/`terminate`-adjacent operation, locking a fraction of the depositor's FSD-equivalent (native currency) funds in the contract's `StorageDepositReserve` hold indefinitely (the PR's own severity assessment: refunds only under-charge). This matches the "permanent user-fund…lock" and "runtime bugs that compromise intended behavior" impact categories.

### Likelihood Explanation
High for any contract author who writes to storage, performs a reentrant self-call, and writes to storage again — this is not a rare or adversarial-only pattern; it's a normal contract-development pattern (e.g., pre/post-call bookkeeping). No governance, validator, relayer, or privileged actor is required — this is triggerable by an ordinary contract deployer/caller using only `pallet-revive`'s public `call`/EVM `CALL` entrypoints.

### Recommendation
Implement the fix described in `prdoc/pr_12267.prdoc` in `substrate/frame/revive/src/exec.rs` and `substrate/frame/revive/src/metering/storage.rs`: add `RawMeter::bank_pending_changes(contract, info)` that applies the `Alive` diff to `info` exactly once, records the resulting deposit as a final `Charge`, and resets `own_contribution`; call this via a `Frame::bank_pending_changes_and_invalidate` helper from `pop_frame` whenever the cache-invalidation matcher finds an ancestor frame sharing the popped child's `account_id`, so the parent's `finalize()` never re-applies a diff that has already been persisted into `ContractInfo`.

### Proof of Concept
1. Deploy contract `X` whose call handler: writes key `K1` (35 bytes) to storage; makes a reentrant self-call with `ReentrancyProtection::AllowReentry`; the reentrant frame's `push_frame` preview-applies the pending `K1` diff into a cloned `ContractInfo` and persists it via `insert_contract`.
2. The reentrant call returns; the cache-invalidation matcher marks the parent's cache `Invalidated`.
3. The parent's own `finalize()` (still holding `own_contribution` containing the `K1` diff, since it was never banked/reset) reloads `ContractInfo` from storage (already containing `K1`'s effect) and re-applies the `K1` diff on top → `storage_items`/`storage_bytes`/`storage_*_deposit` double-count `K1`.
4. Later, the contract clears `K1` via `clear_storage`; the refund is computed as `removed_bytes / info.storage_bytes * info.storage_byte_deposit` using the inflated `info.storage_bytes` denominator, producing a refund smaller than the deposit actually charged for `K1` — the residual remains locked under `HoldReason::StorageDepositReserve` and is unrecoverable through normal contract usage (only recoverable via `do_terminate`'s `refund_all`, which requires terminating the whole contract).

```text
title: '[pallet-revive] fix double deposit charge to parent contractinfo'
doc:
- audience: Runtime Dev
  description: |-
    # pallet-revive: fix storage deposit double-count under same-contract reentry

    When a contract writes storage, reenters itself (directly or via an intermediary), and writes storage again, the pre-call write is applied to the contract's persisted `ContractInfo` twice — inflating `storage_items` / `storage_bytes` / `storage_*_deposit`. The corruption is persisted via `insert_contract` and survives across transactions; subsequent `clear_storage` operations under-refund because the inflated counters become the denominator of the pro-rata refund.

    ## What goes wrong

    For `X` writes `K1` → calls itself → writes `K2`:

    1. `push_frame` (`exec.rs:1212-1223`) and the same-contract `cached_info` shortcut (`exec.rs:2150-2160`) clone the parent's `ContractInfo`, preview-apply the parent's pending diff to the clone, and use it as the child's view. The child persists that clone via `insert_contract` on success.
    2. The cache-invalidation matcher (`exec.rs:1616`) then marks the parent's cache `Invalidated`. The parent's next write reloads from storage, which already contains the preview-applied `K1`.
    3. The parent's `finalize()` (`exec.rs:1474-1478`) re-applies its still-pending `own_contribution` (which still contains `K1`) on top of the reloaded info → `K1` counted twice.

    This is a regression from [#10920](https://github.com/paritytech/polkadot-sdk/pull/10920) (commit `1b9ea1c3656`, merged 2026-02-10), which introduced the preview-apply step to make pending writes visible to nested frames for refund pro-rating, but did not consume the parent's `own_contribution`. The existing #10920 regression test (`metering::tests::nested_call_storage_refund` with the `setAndCallClear` fixture) does not catch the case because the parent performs no write after the nested call returns — its cache stays `Invalidated`, the outer pop's `as_contract()` returns `None`, and the diff is never re-applied.

    ## Fix

    Bank the parent's pending diff at the cache-invalidation site so `finalize()` only applies writes recorded afterwards.

    - `RawMeter::bank_pending_changes(contract, info)` (`metering/storage.rs`) — applies the `Alive` diff to `info` once, pushes the resulting deposit as a final `Charge` via the existing `charge_deposit` primitive, and resets `own_contribution`. Two `debug_assert!`s encode invariants: `info.is_some()` whenever the diff is non-empty (otherwise `Diff::update_contract(None)` at `storage.rs:130-134` drops the refund portion and over-charges), and `own_contribution` is `Alive` when banked (on-stack ancestors have not finalized yet, since `finalize` runs at `exec.rs:1474-1478` only at the frame's own pop).
    - `Frame::bank_pending_changes_and_invalidate` (`exec.rs`) — bundles `load → bank → invalidate` so the meter never sees `None` info and the ordering can't be misexpressed. Called from `pop_frame` only when the matcher finds an ancestor with the popped child's `account_id`.

    The `load` covers the case where an earlier same-contract reentry already invalidated the frame, or it accrued a removal-bearing diff via `charge_storage` (which does not reload the cache). Without it, banking would hit the silent `update_contract(None)` refund-drop.

    No behavior change outside same-contract reentry; the matcher returns no ancestor for cross-contract pops, and the bank is a no-op when the pending diff is empty.
```
