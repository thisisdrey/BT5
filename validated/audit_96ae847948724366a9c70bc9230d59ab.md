The `SlotMetadata::auth_digest()` function in `libstackerdb/src/libstackerdb.rs` computes the digest to sign/verify a StackerDB chunk from only `(slot_id, slot_version, data_hash)` — it never binds the signature to the specific StackerDB smart-contract (`QualifiedContractIdentifier`) the chunk belongs to. Let me confirm both write paths (HTTP POST and P2P push) rely on this same under-scoped digest.### Title
Missing contract-id domain separation in StackerDB `SlotMetadata` signature enables cross-contract chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the digest that a StackerDB signer signs (and that verifiers check) from only `(slot_id, slot_version, data_hash)`. It does not include the StackerDB's `QualifiedContractIdentifier`. This is structurally the same class of bug as the reported IPC issue: an identifier/digest used to authenticate and match a message omits a field of context (there, `localNonce`; here, the target contract), so a value that is valid in one context is wrongly accepted as valid in a different context.

### Finding Description
`SlotMetadata::auth_digest()` [1](#0-0)  hashes only the slot id, slot version, and chunk data hash:
```
hasher.update(self.slot_id.to_be_bytes());
hasher.update(self.slot_version.to_be_bytes());
hasher.update(self.data_hash.0);
```
`sign()` and `verify()` both operate on this same digest [2](#0-1) . Nowhere is the target StackerDB's smart contract identifier folded into the signed payload.

Both write paths that accept externally-supplied chunks rely exclusively on this contract-agnostic check:
- The replicated-DB write path `StackerDBTx::try_replace_chunk` looks up `slot_validation.signer` for `(smart_contract, slot_id)` and calls `slot_desc.verify(&slot_validation.signer)` [3](#0-2) . The contract is used only to select *which signer address* to check against — it plays no role in what was actually signed.
- The gossip/sync validation path `PeerNetwork::validate_received_chunk` does the same: it fetches the expected signer for `(smart_contract_id, slot_id)` and calls `slot_metadata.verify(&addr)` [4](#0-3) , again never hashing the contract into the check.

Because the digest is contract-agnostic, a signature that address `X` produced for `(slot_id=5, slot_version=10, data_hash=H)` in StackerDB contract `A` is *also* a valid signature for `(slot_id=5, slot_version=10, data_hash=H)` in any other StackerDB contract `B` where `X` happens to be configured as the signer of slot 5 — which is common in Stacks Nakamoto signer-set contracts, since slot assignment is deterministic from the sorted signer address list and the same signer set (and thus the same relative slot ordering) is frequently reused across different StackerDB contracts (e.g., consecutive reward-cycle `.signers-N-M` contracts, or `.miners`/`.block-proposal`-style DBs). An attacker who merely observes one broadcast chunk (chunks are gossiped over the open p2p network and are also retrievable via the read-only `GET /v2/stackerdb/...` RPC) can resubmit the identical `(slot_id, slot_version, sig, data)` tuple to a *different* contract's slot via the same POST/push mechanisms, as long as the target slot's currently-stored version is lower.

This breaks the intended equality "signature over context C authenticates data only for context C"; instead the digest silently drops the context, so *authenticated-for-A* data is served as *authenticated-for-B*.

### Impact Explanation
This allows an unprivileged remote party to write forged-context data into a StackerDB replica they do not own, without the signer's private key — an unauthorized/forged write to state that then propagates via normal StackerDB gossip (`StackerDBChunkInv`/`StackerDBPushChunk`) to other nodes replicating that contract, exactly the "network-wide propagation of forged data" / "unauthenticated write to StackerDB" category. Even though the attacker cannot fabricate arbitrary bytes (they must replay content some legitimate signer already signed for a different DB), they can make a signer's message appear authoritative in a StackerDB context that signer never intended, corrupting the consuming protocol's view of that DB (e.g. signer coordination/block-proposal messages appearing where they were not meant to be), and effectively let one signer's slot content in DB "A" clobber (Lamport-clock permitting) the same signer's slot in DB "B".

### Likelihood Explanation
Exploitation requires no privileged access: only (1) observing one signed chunk broadcast/served for any StackerDB the target signer participates in, and (2) the target signer having the same slot_id in the destination contract with a lower stored version — both plausible given how Stacks Nakamoto StackerDB slot assignment is deterministic from a signer's sorted address across related contracts. The replay itself is a trivial unmodified resubmission through the existing public POST/push endpoints.

### Recommendation
Bind the signed digest to the specific StackerDB contract by including the `QualifiedContractIdentifier` (and ideally the reward cycle, if slots are cycle-scoped) in `SlotMetadata::auth_digest()`, and propagate that context into `sign()`/`verify()` call sites (`StackerDBChunkData::sign`, `StackerDBChunkData::verify`, `StackerDBTx::try_replace_chunk`, `PeerNetwork::validate_received_chunk`), so a signature can never be judged valid outside the contract it was produced for.

### Proof of Concept
1. Node A and Node B both replicate two different StackerDB contracts, `contract1` and `contract2`, in which signer address `X` is assigned `slot_id = 0` in both (a realistic configuration since slot assignment is derived from sorted signer lists that are frequently shared/duplicated across related contracts).
2. Signer `X` legitimately signs and pushes chunk `(slot_id=0, slot_version=5, data=D)` to `contract1`. This chunk is visible to anyone via `GET /v2/stackerdb/<contract1>/0` or via gossip on the p2p network — no secret is required to obtain it.
3. An attacker (no key required) takes the exact same tuple `(slot_id=0, slot_version=5, sig=S, data=D)` and POSTs it to `contract2`'s chunk-write endpoint (`stackslib/src/net/api/poststackerdbchunk.rs`) or relays it as an unsolicited `StackerDBPushChunk` p2p message.
4. `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-438`) looks up the signer configured for `(contract2, slot 0)` — which is also `X` — computes `slot_desc.verify(&X)` using the contract-agnostic `auth_digest()`, and the signature verifies successfully even though `X` never signed anything for `contract2`.
5. The chunk is accepted into `contract2`'s slot 0 (assuming its currently stored version is `< 5`) and is subsequently gossiped to all of `contract2`'s replicating peers via `StackerDBChunkInv`, propagating the forged-context write network-wide.

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
