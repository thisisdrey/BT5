Audit Report

## Title
Relayer reward paid on failed Ethereum delivery due to unchecked `receipt.success` flag - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`process_delivery_receipt` in the outbound-queue-v2 pallet decodes a `DeliveryReceipt` containing a `success: bool` field sourced from the Ethereum `InboundMessageDispatched` event, but never inspects it before paying the relayer reward and removing the `PendingOrder`. Payout is gated only on `T::GatewayAddress::get() == receipt.gateway` and the existence of a `PendingOrder` for `receipt.nonce`, independent of whether the dispatch actually succeeded on Ethereum.

## Finding Description
`DeliveryReceipt::try_from` decodes the `success` field directly from the `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` event log [1](#0-0) . `submit_delivery_receipt` verifies the beacon/receipt proof, decodes the receipt, and forwards it to `process_delivery_receipt` without ever branching on `success` [2](#0-1) . `process_delivery_receipt` checks only the gateway address and looks up the `PendingOrder` by nonce; if `order.fee > 0` it unconditionally calls `T::RewardPayment::register_reward` and then removes the order and emits `MessageDelivered`, with `receipt.success` never read anywhere in the function body [3](#0-2) . `PendingOrder` itself stores only `nonce`, `fee`, and `block_number` — there is no field to record delivery outcome and no later corrective mechanism [4](#0-3) . This is a genuine gap between decoded state and enforced invariant: settlement (reward payout + order removal) advances on proof validity and nonce match alone, not on execution success.

## Impact Explanation
Any signed account holding a valid Ethereum receipt proof for an `InboundMessageDispatched` event with `success=false` can still collect the full relayer fee attached to the corresponding `PendingOrder`, since the boolean is decoded but discarded. This constitutes payout state advancing without settlement actually succeeding — matching the "public underpriced work" / duplicate-or-unearned-payout impact category for bridge reward funds, allowing repeated draining of the reward pool across nonces for messages whose Ethereum-side dispatch never executed successfully.

## Likelihood Explanation
`submit_delivery_receipt` is callable via `ensure_signed` with no relayer permissioning [5](#0-4) , so any account controlling the outbound message content can craft a command that predictably reverts on the Ethereum side, obtain the genuine `success=false` receipt/event proof, and submit it to collect the reward — a repeatable, unprivileged exploit path requiring no admin, validator, or compromised relayer role.

## Recommendation
Gate reward payment on `receipt.success`. When `success == false`, withhold or reroute the fee (e.g., refund to original sender or hold for retry) instead of paying the relayer, and emit a distinct event (e.g., `MessageDeliveryFailed`) so downstream systems can distinguish failed from successful deliveries. Only call `T::RewardPayment::register_reward` when `receipt.success` is `true`.

## Proof of Concept
1. Send an outbound message so a `PendingOrder{nonce, fee, ..}` is created with `fee > 0` via `do_process_message` [6](#0-5) .
2. Ensure the corresponding Ethereum-side dispatch reverts (e.g., a payload/command valid enough to be included in the message but designed to fail execution), causing the Gateway to emit `InboundMessageDispatched(nonce, topic, success=false, reward_address=attacker)`.
3. Submit `submit_delivery_receipt` with a valid Merkle/receipt proof for that event; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success=false`.
4. `process_delivery_receipt` never checks `receipt.success`; since `order.fee > 0`, `T::RewardPayment::register_reward` fires and the order is removed as if delivery succeeded, as shown at `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:466-475`.
5. Repeat across nonces to extract reward funds for messages that never successfully executed on Ethereum.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
