### Title
`PeerDB::try_insert_peer` stores unauthenticated, self-reported `NeighborKey` from `HandshakeAcceptData`, letting an attacker claim any victim IP:port under their own public key - ([File: stackslib/src/net/db.rs])

### Summary
`PeerDB::try_insert_peer` (stackslib/src/net/db.rs:1452-1488) decides slot occupancy and calls `PeerDB::insert_or_replace_peer` purely from the `Neighbor` struct handed to it, with zero verification that the caller actually proved control of `neighbor.addr.addrbytes:port` over the network connection. This `Neighbor` is built from a remote-controlled `HandshakeAcceptData.handshake` field (`NeighborKey::from_handshake`), which is only self-reported local-peer configuration, not the real socket address. A malicious node operator can therefore squat any third-party IP/port in a victim's peer database bound to the attacker's own public key.

### Finding Description
`PeerDB::try_insert_peer` (stackslib/src/net/db.rs:1452-1488) only checks `PeerDB::has_peer`/`PeerDB::has_peer_at` (keyed by `Hash160(addrbytes,port)`-derived slot) to decide whether to write via `PeerDB::insert_or_replace_peer` (db.rs:1091-1133), which blindly `INSERT OR REPLACE`s `(addrbytes, port, public_key, ...)` from the `Neighbor` argument. Neither function checks that the peer being inserted has cryptographically proven ownership of `addrbytes:port`.

`Neighbor::save`/`save_update` (stackslib/src/net/neighbors/neighbor.rs:50-74) forward directly into `PeerDB::try_insert_peer`/`PeerDB::update_peer` with no additional ownership check.

The reachable exploit path is through the neighbor-walk "handshake with neighbors-of-neighbors" flow:
1. The victim node performs a random walk, dials out (`neighbor_session_begin`) to some address `na.addrbytes:na.port` advertised in a `Neighbors` reply (stackslib/src/net/neighbors/walk.rs:1004-1068) — an address the attacker actually controls (their own reachable node), so the TCP handshake genuinely completes with the attacker.
2. The attacker's node replies to the incoming `Handshake` with a `HandshakeAccept`/`StackerDBHandshakeAccept` whose payload is built by `HandshakeAcceptData::new(network.get_local_peer(), ...)` (stackslib/src/net/chat.rs:1297) — i.e., from the attacker's own `LocalPeer.addrbytes/port`, which is just local node configuration the attacker fully controls (they can set it to any third-party IP such as a victim's real address). The reply is legitimately signed by the attacker's real private key, so `verify_secp256k1`/signature checks pass — the attacker is authenticating as themselves, just lying about their own address field.
3. On the victim side, `handle_neighbor_handshake_accept` → `NeighborWalkDB::add_or_schedule_replace_neighbor` (stackslib/src/net/neighbors/db.rs:368-426) calls `Neighbor::load_and_update` (chat.rs:475-516), which builds `NeighborKey::from_handshake(...)` **from the self-reported `data.handshake.addrbytes/port`**, not from the actual dialed/connected address `na`/`nk`. There is no check anywhere in this path (unlike the direct `handle_handshake_accept` for `cur_neighbor`, which does check `neighbor_from_handshake.addr != self.cur_neighbor.addr` at walk.rs:705) that the reported address matches the address that was actually dialed.
4. `neighbor_from_handshake.save(...)` → `PeerDB::try_insert_peer` then writes `(victim_addrbytes, victim_port) -> attacker_public_key` into the `frontier` table via `PeerDB::insert_or_replace_peer`.

The `pingback_handshakes_try_finish` path (walk.rs:1683-1725) similarly only calls `check_handshake_pubkey_hash` (walk.rs:1664-1680), which verifies the reported public key hashes to the *gossiped* `naddr.public_key_hash` — but that gossiped hash is also attacker-supplied, so it does not constrain `addrbytes`/`port` at all.

`PeerDB`'s existing guards (`has_peer`, `has_peer_at`, `peer_slots`) only enforce slot capacity/dedup by address hash; they never verify a signature or connection-address match against the stored `public_key`. `validate_handshake` (chat.rs:1047-1127) only restricts self-reported `addrbytes`/`port` for *outbound* connections that already have a known public key (chat.rs:1079-1090) — it does not apply to `HandshakeAcceptData` processing at all, and even for `Handshake` it exempts inbound connections entirely.

### Impact Explanation
An unprivileged remote attacker (running their own reachable P2P node) can insert forged `(victim_IP:port -> attacker_pubkey)` records into any peer's `PeerDB` `frontier` table. This is an unauthenticated write to persistent peer-identity state: the victim node will now believe the attacker's public key represents an arbitrary third-party address. This forged frontier entry is then eligible for further gossip (via `Neighbors` responses drawn from `frontier`), propagating the false identity claim network-wide, and can be leveraged to disrupt/eclipse legitimate peers at the squatted address (their real, correctly-signed handshakes would get out-competed/represented incorrectly in the frontier once slots fill or update, and neighbor-walk logic may attempt to treat the attacker as authoritative for that address). This matches the Critical category of "unauthenticated/unauthorized write to state" and "network-wide propagation of forged data."

### Likelihood Explanation
The attacker only needs: (1) their own P2P node, reachable by the victim (attainable by simply gossiping their own address as a "neighbor-of-neighbor" via a `Neighbors` reply, or being a directly-connected/bootstrap-adjacent peer, all in-scope for an unprivileged remote actor), and (2) the ability to reply to a `Handshake` with a `HandshakeAccept` whose embedded `LocalPeer`-derived address field is set to an arbitrary victim address. No secrets, no privileged role, and no race condition are required; the technique is repeatable per targeted address (subject to available `frontier` slots for that address hash) and costs only running a normal, unmodified-protocol peer with attacker-chosen local configuration.

### Recommendation
When processing `HandshakeAcceptData`/`HandshakeData` for peers reached indirectly (neighbor-of-neighbor / pingback walks), do not trust the self-reported `addrbytes`/`port` as the storage key. Either (a) key the stored `Neighbor` by the actual socket address used to establish the TCP connection (as is already done for the direct `cur_neighbor` case in `handle_handshake_accept`, walk.rs:705), overriding/ignoring the self-reported address except for detecting private-IP/NAT cases, or (b) require that any self-reported address substitution be corroborated by multiple independent, non-attacker-controlled peers before being written to `PeerDB`. Additionally, `PeerDB::try_insert_peer`/`insert_or_replace_peer` should treat address fields as untrusted input and never overwrite an existing, distinctly-owned frontier slot for a given `(addrbytes, port)` based solely on unauthenticated self-report.

### Proof of Concept
Rust test plan (in `stackslib/src/net/neighbors/walk.rs` test module, mirroring existing walk tests using `testing_helpers`):
1. Set up victim node `net_1` and attacker node `net_2`, each with its own `PeerDB`/`LocalPeer`.
2. Configure `local_peer_2` (attacker) with `LocalPeer.addrbytes` and `port` set to a third-party "victim" address `V` (e.g. `1.2.3.4:12345`) that neither node actually owns/binds to.
3. Have `net_1` perform a neighbor walk step that reaches `net_2` as a "neighbor-of-neighbor" (`neighbor_handshakes_begin` dialing `net_2`'s real test-harness socket address), and drive `neighbor_handshakes_try_finish`/`handle_neighbor_handshake_accept` to completion using the harness's `convo_send_recv`.
4. Assert that after processing, `PeerDB::get_peer(net_1.peerdb_conn(), network_id, &V.addrbytes, V.port)` returns `Some(neighbor)` where `neighbor.public_key == Secp256k1PublicKey::from_private(&local_peer_2.private_key)` — i.e., the victim address `V` is now bound in `net_1`'s `PeerDB` to the attacker's key, despite `net_1` never having connected to `V` at all.
5. This assertion succeeding (rather than failing/being rejected) demonstrates the break: `PeerDB::insert_or_replace_peer` accepted an address the caller never proved ownership of via a genuine handshake at that address.
