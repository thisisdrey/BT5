Audit Report

## Title
Snowbridge relayer reward claim clears local reward ledger on XCM *send* success, not on destination-chain settlement, causing permanent, unrecoverable loss of claimed rewards - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

## Summary
`pallet-bridge-relayers::claim_rewards_to` finalizes the relayer's `RelayerRewards` entry and emits `Event::RewardPaid` as soon as `PaymentProcedure::pay_reward` returns `Ok(())`. For `BridgeReward::Snowbridge`, `pay_reward` is `PayAccountOnLocation::pay_reward`, which returns `Ok(())` immediately after the `ReserveAssetDeposited`/`DepositAsset` XCM is validated, fee-charged, and handed to the transport layer — not after the deposit actually executes on AssetHub. If the remote `DepositAsset` later fails, the relayer's claim is already irrevocably erased on BridgeHub with no recovery path.

## Finding Description
`do_claim_rewards` in `bridges/modules/relayers/src/lib.rs` uses `RelayerRewards::<T, I>::try_mutate_exists`, taking the reward out of storage, calling `T::PaymentProcedure::pay_reward(...)`, and only rolling back on a *synchronous* `Err` from `pay_reward`. For the Snowbridge reward kind, `PayAccountOnLocation::pay_reward` (`bridges/snowbridge/primitives/core/src/reward.rs`) builds an XCM performing `ReserveAssetDeposited` + `DepositAsset` on AssetHub, and returns `Ok(())` based solely on `validate_send`, `XcmExecutor::charge_fees`, and `XcmSender::deliver` succeeding — none of which say anything about whether `DepositAsset` will succeed when the message executes on AssetHub in a later block. Because the storage removal and `RewardPaid` event are committed atomically with this local `Ok(())`, the protocol asserts the reward is paid and erases the only record that it was owed before the actual settlement occurs. This contrasts with `PayOverXcm` (`polkadot/xcm/xcm-builder/src/pay.rs`, `transfer.rs`) elsewhere in the same repo, which uses a `QueryId`/`check_payment`/`Querier::take_response` mechanism specifically to avoid declaring an XCM payment successful before remote execution is confirmed — `PayAccountOnLocation` has no equivalent mechanism.

## Impact Explanation
This is a permanent, unrecoverable loss of relayer reward funds/state: `RelayerRewards` is cleared and cannot be reclaimed via `claim_rewards_to` (subsequent attempts return `Error::NoRewardForRelayer`), while the underlying asset deposit on AssetHub can independently fail and become trapped, unlinked to the relayer's claim. This matches the "permanent user-fund or bridge-state lock" and "payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" impact criteria.

## Likelihood Explanation
No malicious actor is required. Any relayer submitting a `beneficiary` `AssetHubLocation` that passes local `validate_send`/`charge_fees`/`deliver` but fails at `DepositAsset` execution on AssetHub (e.g., below-ED beneficiary, asset-filter mismatch, mis-versioned `VersionedLocation`) triggers permanent loss of that specific claim, using only the public `claim_rewards_to` extrinsic.

## Recommendation
Do not finalize `RelayerRewards` / emit `RewardPaid` synchronously with local `pay_reward` success for asynchronous cross-chain payment procedures. Adopt a receipt/query-based confirmation pattern analogous to `PayOverXcm`'s `QueryId`/`check_payment`, or keep the reward in a "claim in flight" state that can be restored if remote execution is later observed to fail.

## Proof of Concept
1. Register a Snowbridge reward for `relayer` via `register_reward`.
2. Call `claim_rewards_to` with a `BridgeRewardBeneficiaries::AssetHubLocation(...)` that passes `validate_send`/`charge_fees`/`deliver` on BridgeHub but whose `DepositAsset` execution fails on AssetHub (e.g., a beneficiary account that cannot hold the foreign asset without ED).
3. Observe on BridgeHub: `Event::RewardPaid` emitted, `RelayerRewards::get(relayer, BridgeReward::Snowbridge)` returns `None`.
4. Observe on AssetHub: no successful deposit event; instead an `AssetsTrapped`/failed message-processing event.
5. Re-invoking `claim_rewards_to` returns `Error::NoRewardForRelayer` — the relayer cannot recover the reward.
