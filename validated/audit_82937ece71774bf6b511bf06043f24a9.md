Audit Report

## Title
`snowbridge_pallet_system_frontend::add_tip` irrevocably burns the user's tip asset before remote confirmation, and on remote rejection the burned value is permanently lost, recorded only in `LostTips` with no refund path - ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

## Summary
`Pallet::add_tip` in `snowbridge-pallet-system-frontend` calls `swap_fee_asset_and_burn`, which unconditionally swaps and burns the user's tip asset on the local chain (AssetHub) via `burn_for_teleport` *before* the corresponding remote `add_tip` call on BridgeHub is known to succeed. If the remote `AddTip::add_tip` implementation on `outbound-queue-v2` or `inbound-queue-v2` rejects the tip (`AddTipError::UnknownMessage` or `AddTipError::NonceConsumed`), `system-v2::add_tip` only records the loss in the `LostTips` storage map and emits `TipProcessed { success: false }` — there is no refund or claim mechanism anywhere in the code.

## Finding Description
`add_tip` at [1](#0-0)  executes `swap_fee_asset_and_burn(who, asset)` first, which either swaps-and-burns via `Self::swap_and_burn` or directly calls `burn_for_teleport` [2](#0-1) . This destroys the asset on AssetHub unconditionally, prior to any confirmation that the remote application will succeed. Only afterward is a `Transact` XCM built and sent to BridgeHub's `EthereumSystemV2::add_tip`.

On BridgeHub, `EthereumSystemV2::add_tip` forwards to `InboundQueue::add_tip` or `OutboundQueue::add_tip`, both implementing the `AddTip` trait which can return `AddTipError::UnknownMessage`, `AddTipError::NonceConsumed`, or `AddTipError::AmountZero` [3](#0-2) . `outbound-queue-v2`'s implementation returns `UnknownMessage` when there is no matching `PendingOrder` for the nonce [4](#0-3) . When this error occurs, `system-v2::add_tip` catches it and only mutates `LostTips`, taking no corrective action to return value to the sender [5](#0-4) . The storage doc comment itself concedes there is currently no recovery path: `LostTips` "supports implementing a recovery method in the future" [6](#0-5)  — i.e., no such method currently exists in this pallet or anywhere in the reachable code (`system-frontend`, `system-v2`, `inbound-queue-v2`, `outbound-queue-v2`).

The invariant broken is one-time, atomic settlement: value should only be destroyed/spent once the corresponding downstream effect (tip application to a valid pending order or inbound nonce) is confirmed to succeed. Here, burn happens unconditionally at step 1 regardless of the validity of the caller-supplied `message_id`, which is not validated against the sender's own message ownership or against current nonce state before burning.

## Impact Explanation
This is a permanent user-fund loss triggered entirely by normal, unprivileged extrinsic usage — no malicious relayer, validator, or governance actor is required. Any signed AssetHub account calling `SnowbridgeSystemFrontend::add_tip` with a `MessageId` that does not correspond to a currently pending outbound order (or an unconsumed inbound nonce) irreversibly loses the swapped/burned Ether amount, which is not returned to them; it is merely tallied in `LostTips`. This falls within the "permanent user-fund lock/loss" impact category, as burnt value has no path back to the rightful beneficiary once burned.

## Likelihood Explanation
High and easily reproducible: this requires only a signed, public extrinsic call with attacker-controlled/user-controlled parameters (`message_id`, `asset`), and no privileged access. This is not merely a theoretical race — it is straightforward to hit accidentally (e.g., tipping a nonce that has already been delivered/consumed, or one that was never valid), and is explicitly demonstrated as expected, passing behavior by the existing test `tip_to_invalid_nonce_is_added_to_lost_tips` [7](#0-6) , confirming the loss occurs deterministically and is treated as a "success" case for the pallet's own error-handling logic, rather than guarded against.

## Recommendation
Do not burn/destroy the tip asset on AssetHub until the remote tip application is confirmed. Options include: (1) hold the swapped Ether in escrow (e.g., a `HoldReason`) on AssetHub until a delivery-confirmation XCM from BridgeHub confirms success, releasing/burning only then and refunding the hold on failure; (2) validate nonce/message validity synchronously before burning; or (3) implement the recovery method alluded to in the `LostTips` doc comment — an extrinsic that lets a user reclaim (mint back) the amount tracked in `LostTips` for their account.

## Proof of Concept
1. On AssetHub, a signed user calls `SnowbridgeSystemFrontend::add_tip(origin, MessageId::Outbound(N), asset)` for a nonce `N` with no corresponding `PendingOrder` on BridgeHub (e.g. never created, or already delivered/removed) — reproduced exactly by the existing test `tip_to_invalid_nonce_is_added_to_lost_tips` [8](#0-7) .
2. `swap_fee_asset_and_burn` runs first and unconditionally burns the swapped Ether via `burn_for_teleport` [9](#0-8) .
3. The `Transact` call reaches BridgeHub; `OutboundQueue::add_tip` returns `AddTipError::UnknownMessage` since `PendingOrders` has no entry for `N` [4](#0-3) .
4. `EthereumSystemV2::add_tip` catches the `Err`, increments `LostTips[sender]` by `amount`, and emits `TipProcessed { success: false }` [10](#0-9) , as asserted by the test.
5. The user's burned Ether is never returned — there is no extrinsic anywhere in `system-frontend`, `system-v2`, `inbound-queue-v2`, or `outbound-queue-v2` that consumes `LostTips` to refund the sender, confirming permanent loss of the burned amount for a fully unprivileged, trivially-triggered action.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}

pub fn tip_to_invalid_nonce_is_added_to_lost_tips() {
	fund_on_bh();
	register_assets_on_ah();

	set_up_eth_and_dot_pool();
	let relayer = AssetHubWestendSender::get();

	AssetHubWestend::fund_accounts(vec![(relayer.clone(), INITIAL_FUND)]);

	// A nonce that does not exist.
	let tip_message_id = MessageId::Outbound(22);

	let dot = Location::new(1, Here);
	AssetHubWestend::execute_with(|| {
		type RuntimeOrigin = <AssetHubWestend as Chain>::RuntimeOrigin;

		assert_ok!(<AssetHubWestend as AssetHubWestendPallet>::SnowbridgeSystemFrontend::add_tip(
			RuntimeOrigin::signed(relayer.clone()),

		));

	BridgeHubWestend::execute_with(|| {
		type RuntimeEvent = <BridgeHubWestend as Chain>::RuntimeEvent;

		assert!(relayer_lost_tip > 0);
	});
