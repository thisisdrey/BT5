### Title
Terminal relay peer identity spoofing via unvalidated `RelayFromAddr` in `CreateRelayRequest` - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` authenticates the sender only by virtue of the message arriving over an already-authenticated `HostInfo h` (i.e. the sender has a valid cert-verified tunnel), but it never checks that the attacker-supplied `RelayFromAddr` field in the `NebulaControl` message actually equals (or is contained in) `h.vpnAddrs`. This mirrors the Teller `UpdateCommitment` flaw: authorization is checked against one identity (`msg.sender` / `h`), while the operation is actually keyed off a second, unvalidated identity field (`_commitment.lender` / `RelayFromAddr`) supplied in the same request.

### Finding Description
In `relay_manager.go`, `HandleControlMsg` dispatches `CreateRelayRequest`/`CreateRelayResponse` to `handleCreateRelayRequest`/`handleCreateRelayResponse` after only checking that `RelayFromAddr`/`RelayToAddr` are non-nil: [1](#0-0) 

`handleCreateRelayRequest` then derives `from` directly from the message body: [2](#0-1) 

It checks that `from` is not one of *my own* addresses (`f.myVpnAddrsTable.Contains(from)`), and it checks whether `target` (the terminal endpoint) is me — but it never checks that `from` is contained in `h.vpnAddrs`, i.e. that the claimed relay-origin identity actually belongs to the authenticated peer `h` that sent the packet. When `target` is me, the code proceeds to call `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)`, binding relay state for vpn address `from` to hostinfo `h`: [3](#0-2) 

Because `h` is authenticated (it owns a real handshake-verified tunnel to us) but `from` is an arbitrary, attacker-chosen vpn address taken straight from the packet, a malicious peer can claim to be relaying "from" any victim vpn address it does not own. This is the same root-cause pattern as the reported bug: the authorization check (peer `h` is legitimate) is performed against a different value than the one written into persistent state (`from`), with no equality/ownership check binding the two.

### Impact Explanation
This allows a malicious authenticated peer to register itself, through its own legitimate tunnel `h`, as the relay-origin for an arbitrary victim vpn address, without ever proving control of that address. Downstream, hostmap relay lookups (`HostInfo.relayState.QueryRelayForByIp`) key established relay state by this attacker-controlled `from` value, meaning traffic-relay routing decisions for the victim's address can be poisoned into pointing at the attacker's hostinfo instead of the legitimate one — a remote state-poisoning primitive that can be leveraged to intercept, misroute, or degrade encrypted tunnel traffic that would otherwise be relayed to/from the victim.

### Likelihood Explanation
Reachable by any peer able to open one legitimate, cert-verified tunnel to a node acting as relay terminal/forwarder (`am_relay` or acting as a relay target) — no compromise of another node's certificate or private key is required, only sending a crafted `CreateRelayRequest` Control message over the attacker's own valid session. This fits the "attacker with no CA-signed certificate for the victim" threat model since the attacker uses its own valid cert but forges the `RelayFromAddr` field.

### Recommendation
In `handleCreateRelayRequest` (and correspondingly in `handleCreateRelayResponse`), require that `from` (`RelayFromAddr`/`OldRelayFromAddr`) is contained in `h.vpnAddrs` before calling `AddRelay`/updating relay state for `h`. Reject the message (log and return) if the claimed origin address does not match the authenticated peer's own vpn address set, exactly as `handleHostUpdateNotification` already does for lighthouse updates (`slices.Contains(fromVpnAddrs, detailsVpnAddr)`).

### Proof of Concept
1. Attacker `A` establishes a normal, valid, cert-authenticated Nebula tunnel to victim relay node `R` (`R` has `relay.am_relay: true` or is otherwise a viable relay target for some victim `V`).
2. `A` sends `R` a `NebulaControl` message of type `CreateRelayRequest` with `RelayFromAddr = V` (a vpn address `A` does not own) and `RelayToAddr = R`'s own vpn address.
3. `handleCreateRelayRequest` on `R` sees `target == R` (me) and, finding no existing relay state for `from=V` on hostinfo `h` (which is really `A`'s connection), calls `AddRelay(rm.l, h, f.hostMap, V, &m.InitiatorRelayIndex, TerminalType, Established)` — binding `A`'s hostinfo as the established terminal relay "from" `V`, despite `A` never proving ownership of `V`.
4. `R` sends back a `CreateRelayResponse` treating `A`'s connection as authoritative for relaying on behalf of `V`, which can be used to hijack or disrupt relay-routed traffic intended for `V`. [4](#0-3)

	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {

						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}

				h.relayState.UpdateRelayForByIpState(from, Established)
