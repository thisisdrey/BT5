### Title
Missing timeout check in `VerifyTransferProof` allows indefinite thread block, leading to transaction-processing halt - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.VerifyTransferProof.execute()` (the Sapling shielded-transfer proof-verification precompile) submits its zk-SNARK verification work to a small, static, shared `ExecutorService` and waits on a `CountDownLatch` with a timeout, but — unlike the sibling `BatchValidateSign` precompile in the same file — it never checks the latch's return value before calling the blocking, timeout-less `future.get()` on every submitted task.

### Finding Description
In `BatchValidateSign.doExecute()` the pattern is implemented correctly: [1](#0-0) 
the code explicitly aborts with `Program.Exception.notEnoughTime(...)` when `withNoTimeout` is `false`.

In `VerifyTransferProof.execute()`, the analogous `withNoTimeout` boolean is computed from `countDownLatch.await(getCPUTimeLeftInNanoSecond(), TimeUnit.NANOSECONDS)` but is **never inspected**; execution falls straight through to a loop that calls the blocking `future.get()` (no timeout argument) for every submitted `SaplingCheckSpendTask` / `SaplingCheckOutputTask` / `SaplingCheckBingdingSig` task: [2](#0-1) 

The tasks are submitted to a **static, fixed-size (5-thread), shared** `ExecutorService` per call kind: [3](#0-2) 

Because `ExecutorServiceManager.newFixedThreadPool` backs these with an unbounded work queue, any number of concurrent shielded-transfer verifications from independent transactions/blocks can be queued behind the 5 worker threads. Since `future.get()` has no timeout and the code path bypasses the CPU-time check entirely, the thread that is executing the VM opcode/actuator (which — via `Program.callToPrecompiledAddress` — runs synchronously inside block/transaction application) can block for an unbounded amount of time waiting for a queued or slow/native (`JLibrustzcash`) task to finish.

This mirrors the CVE-2023-54120 bug class: a resource-lifecycle synchronization primitive (`del_timer` vs `del_timer_sync` in the kernel; here, an ignored timeout/latch result before an unbounded `Future.get()`) is not honored, letting execution proceed on a path assuming completion when it isn't guaranteed, producing unbounded blocking on a shared, limited-capacity resource.

### Impact Explanation
Shielded transfer verification runs inside the code path that processes transactions under `Manager`'s `transactionLock`/`synchronized (this)` block during `pushTransaction`/block application: [4](#0-3) 
If a `future.get()` call inside `VerifyTransferProof` blocks indefinitely (worker starvation, a stuck native zk task, or simply queue backlog from a burst of shielded transactions), the thread holding this lock stalls. Since block application and further transaction pushing are serialized behind this lock, this can freeze transaction processing on the node — a denial-of-service / node-halt condition, which is an explicitly accepted impact category.

### Likelihood Explanation
Any unprivileged party can broadcast `ShieldedTransferContract` transactions (or, if the address is reachable via `CALL`/`STATICCALL` from a deployed smart contract through `Program.callToPrecompiledAddress`), and the network already supports concurrent processing of such transactions/blocks. Submitting a burst of these transactions concurrently is sufficient to saturate the fixed 5-worker pool and put the code on the un-checked `future.get()` path; no special privileges, keys, or malicious-peer/witness role are required. This makes exploitation moderately likely for anyone who can broadcast transactions to the network.

### Recommendation
Add the same guard used in `BatchValidateSign`: check `withNoTimeout` immediately after `countDownLatch.await(...)` in `VerifyTransferProof.execute()` and abort (throwing `Program.Exception.notEnoughTime(...)` or similar) instead of calling `future.get()` unconditionally. Additionally, consider using `future.get(timeout, unit)` with a bounded timeout and canceling outstanding futures on timeout, to avoid any code path that can block a transaction-processing thread indefinitely on a shared, size-limited executor.
