Analysis: The reported bug class concerns performance/protocol fee shares being minted using an incorrect simplified formula `fees × totalSupply / totalAsset()` instead of the corrected Lido-style formula `fees × totalSupply / (totalAsset() − fees)`. In this codebase, the analogous protocol fee-share minting occurs in each vault's `accrue` function, where `treasury-lp` shares are minted to `.dao-treasury` based on `reserve-inc` (the fee-reserve portion of accrued interest): [1](#0-0) 

The formula used is:

`treasury-lp = mul-div-down(reserve-inc, total-supply, (total-assets-preview - reserve-inc))` [2](#0-1) 

This is exactly the corrected LIDO-style formula from the report (`shares2mint = fees × totalSupply / (totalAssets − fees)`), where `reserve-inc` plays the role of `fees` and `total-assets-preview` (computed post-accrual, already including the full interest/profit) plays the role of `totalAssets()`, matching the report's `currentNavPerShare`-based `totalAsset()` that already reflects profit: [3](#0-2) 

Since the denominator subtracts the fee amount (`reserve-inc`) rather than using the raw post-profit `total-assets-preview` alone, the vaults here already avoid the exact formula flaw described in H-14. This pattern is identical across all vault contracts (`v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`), so no valid analog of this specific bug class exists in scope.
