Confirmed: `decode_atlas_get_attachment` performs no hash verification, and `extend_with_attachments` in `download.rs` inserts the returned attachment directly with no equality check against `request.content_hash`.

### Title
Attachment download path does not verify `Attachment::hash()` matches requested `content_hash`, allowing a malicious peer to poison the AtlasDB - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When `AttachmentsBatchStateMachine::try_proceed` processes attachment download responses, `AttachmentsBatchStateContext::extend_with_attachments` decodes the peer's `GetAttachmentResponse` and inserts `response.attachment` into `self.attachments` without ever checking that `Hash160::from_data(&attachment.content) == request.content_hash`. This content is later unconditionally persisted via `network.atlasdb.insert_instantiated_attachment(&attachment)` and served back out over `/v2/attachments/<hash>`, and matched with `find_all_attachment_instances(&attachment.hash())`—not the originally requested hash.

### Finding Description
The intended equality is `Hash160::from_data(&attachment.content) == request.content_hash` (the on-chain committed content hash for a resolved BNS/Atlas attachment instance). Tracing the code:

- `AttachmentsBatchStateContext::get_prioritized_attachments_requests` builds an `AttachmentRequest { content_hash, .. }` from the on-chain committed hash [1](#0-0) .
- The response is decoded via `StacksHttpResponse::decode_atlas_get_attachment`, which only performs JSON parsing with zero content validation [2](#0-1) .
- `extend_with_attachments` takes this decoded response and does `self.attachments.insert(response.attachment)` directly, with no check against `request.content_hash` (the request that produced this response is available in scope but never consulted for hash equality) [3](#0-2) .
- In `AttachmentsDownloader::run`, the `Done` state drains `context.attachments` and, for each attachment, calls `attachment.hash()` only to look up *existing* `AttachmentInstance`s bound to that (attacker-supplied) hash, then unconditionally calls `network.atlasdb.insert_instantiated_attachment(&attachment)` [4](#0-3) . Note `attachment.hash()` here is computed from the attacker's own bytes, not compared against the requested `content_hash` used to key the outbound request.

Because any outbound sync peer that is a data source for a page in the peer's inventory can be asked for an attachment, and the response is trusted verbatim, a malicious peer can return `Attachment{content: b"evil"}` in reply to a request keyed on `content_hash = Hash160::from_data(b"real")`. The mismatched content is stored under `atlasdb` bound to whatever attachment instances existed with `attachment_instance.content_hash` matching the real hash—no, more precisely: `insert_instantiated_attachment` stores by the attachment's own re-derived hash (`attachment.hash()`), and `find_all_attachment_instances(&attachment.hash())` looks up instances keyed by the *forged* hash of `b"evil"`, not the originally requested `real` hash — meaning the forged content is stored in the AtlasDB under the wrong key entirely, potentially with zero or unrelated attachment instances resolved to it, while the originally requested legitimate attachment is silently marked as "resolved" (`context.attachments_batch.resolve_attachment(&attachment.hash())` also uses the forged hash, not `request.content_hash`) even though the correct content was never obtained.

Even setting aside the resolve/hash-key confusion, the core defect is that **no code path re-derives `Hash160::from_data(&attachment.content)` and compares it to the `content_hash` that was actually requested** before trusting and storing the response.

### Impact Explanation
A remote unprivileged peer that is included among `sources` for an attachment request (any outbound sync peer this node talks to and that claims to have the attachment in its inventory) can supply arbitrary bytes as attachment content for a hash that does not match. This is persisted into the local `AtlasDB` and later served to any RPC client via `GET /v2/attachments/<hash>`, i.e., "serving non-canonical state as canonical" for BNS/Atlas name-attachment data — matching the High severity category described in the prompt (attachment/BNS mismatch). It is repeatable per attachment batch cycle and requires no privileged role, secret, or write access beyond normal outbound peer connectivity.

### Likelihood Explanation
Preconditions: the victim node must have queued unresolved `AttachmentInstance`s (normal operation for any node processing BNS name operations), and the attacker must be one of the peers listed in the node's outbound sync peer set that responds to attachment inventory/content requests (achievable by any peer the victim dials or that advertises the attachment in its inventory response, since `AttachmentsInventoryRequest`/`GetAttachmentsInvResponse` are similarly self-reported by peers [5](#0-4) ). No secret or privileged role is required; the attacker only needs to run a normal Stacks peer and answer HTTP GETs for attachments and inventories, which is standard unauthenticated behavior.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (stackslib/src/net/atlas/download.rs, around line 547), after decoding the response, recompute `Hash160::from_data(&response.attachment.content)` and compare it to `request.content_hash`. Reject (treat as failed request, bump `report.bump_failed_requests()`) any response whose content hash does not match the requested hash, and only insert into `self.attachments` (and later resolve/store) attachments that pass this check.

### Proof of Concept
Rust test plan (net test, e.g. in `stackslib/src/net/atlas/tests.rs`):
1. Construct an `AttachmentsBatchStateContext` with a pending `AttachmentRequest { content_hash: Hash160::from_data(b"real"), .. }`.
2. Simulate a `BatchedRequestsResult<AttachmentRequest>` where `succeeded` maps that request to `Some(StacksHttpResponse)` whose body deserializes (via `decode_atlas_get_attachment`) to `GetAttachmentResponse { attachment: Attachment { content: b"evil".to_vec() } }`.
3. Call `context.extend_with_attachments(&mut results)` and then drive `AttachmentsDownloader::run`/`try_proceed` to the `Done` state, calling `network.atlasdb.insert_instantiated_attachment(&attachment)`.
4. Assert: `network.atlasdb.find_attachment(&Hash160::from_data(b"real")).unwrap()` is `None` or does not equal `b"real"`, while `network.atlasdb.find_attachment(&Hash160::from_data(b"evil")).unwrap().unwrap().content == b"evil"` — proving forged content unrelated to the requested hash was accepted and stored with no server-side re-hash validation in the download path.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

impl StacksHttpResponse {
    pub fn decode_atlas_get_attachment(self) -> Result<GetAttachmentResponse, NetError> {
        let contents = self.get_http_payload_ok()?;
        let contents_json: serde_json::Value = contents.try_into()?;
        let resp: GetAttachmentResponse = serde_json::from_value(contents_json)
            .map_err(|_e| NetError::DeserializeError("Failed to load from JSON".to_string()))?;
        Ok(resp)
    }
