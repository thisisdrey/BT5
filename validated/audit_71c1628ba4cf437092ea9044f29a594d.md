### Title
Connection freshness timestamp is refreshed on every finished stream regardless of whether it delivered any useful data, letting an unstaked peer evade LRU-based connection eviction - (File: streamer/src/nonblocking/swqos.rs)

### Summary
This is an analog of the reported "reward time updated even when no reward is sent" bug class: a per-actor bookkeeping timestamp that is meant to reflect *productive* activity is instead updated unconditionally on every event, letting the actor keep its state artificially "fresh" and escape a mechanism (there, delayed rewards; here, LRU-based pruning) that depends on that timestamp reflecting real work.

### Finding Description
`SwQos::on_stream_finished` unconditionally stamps the connection's `last_update` timer whenever *any* stream on the connection finishes, with no check on whether the stream actually carried a valid/useful payload: [1](#0-0) 

This `last_update: Arc<AtomicU64>` is stored per-connection in the `ConnectionTable` when the connection is added: [2](#0-1) 

and the unstaked connection table is pruned back to 90% capacity using an LRU-style eviction (`prune_oldest`) whenever it fills up: [3](#0-2) 

Because `on_stream_finished` bumps `last_update` for *every* finished stream — with no distinction between a stream that delivered a legitimate, useful packet and one that was empty, immediately reset, or otherwise a no-op — a connection's "freshness" in the LRU ordering can be manufactured cheaply. `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` allows many concurrent streams per unstaked connection, so a client can open and immediately finish many trivial/empty streams purely to keep re-stamping `last_update`, without doing any of the useful work (sending valid transactions) that the freshness metric is supposed to track.

This mirrors the original Solidity finding precisely: `lastRewardTime`/`last_update` should only be advanced when the associated action actually had effect; instead it is advanced unconditionally, defeating downstream logic that relies on the timestamp being a true signal of recent, meaningful activity.

### Impact Explanation
Under connection-table pressure (the unstaked table pruned to 90% capacity per `prune_unstaked_connection_table`), `prune_oldest` is supposed to evict genuinely idle/stale connections to make room for new legitimate peers. If an unstaked, unprivileged attacker can keep its own connection's `last_update` perpetually fresh via trivial/no-op streams, it can occupy connection-table slots indefinitely and cause the eviction logic to instead prune other, more genuinely active or benign connections, degrading fair QoS admission and effectively evading the intended unstaked-connection churn/pruning policy. This is a QoS-evasion class issue, in scope per the task's validation criteria.

### Likelihood Explanation
Likelihood is medium: this requires no special privilege or stake — only an unstaked QUIC client capable of opening/closing many trivial uni-streams — and the relevant code path (`on_stream_finished`, `prune_oldest`) is on the hot unprivileged ingestion path (streamer QoS). However, exploiting it to meaningfully starve out other peers requires sustained activity and depends on how aggressively `prune_oldest` is invoked relative to attacker throughput, which I was not able to fully verify (I did not confirm the exact call sites in `quic.rs` that invoke `on_stream_finished` for zero-byte/errored streams, nor the full implementation of `prune_oldest`, due to running out of investigation iterations).

### Recommendation
Only refresh `last_update` when a stream actually produced useful work (e.g., successfully delivered and forwarded packet data), mirroring the suggested fix in the original report — move the timestamp update inside the branch that confirms the stream had a real effect, rather than updating it unconditionally in `on_stream_finished`.

    fn prune_unstaked_connection_table(
        &self,
        unstaked_connection_table: &mut ConnectionTable<ConnectionStreamCounter>,
        max_unstaked_connections: usize,
        stats: Arc<StreamerStats>,
    ) {
        if unstaked_connection_table.total_size >= max_unstaked_connections {
            // Prune the connection table down to 90% capacity
            const PRUNE_TABLE_RATIO: f64 = 0.90;
            let max_connections = (PRUNE_TABLE_RATIO * (max_unstaked_connections as f64)) as usize;
            let num_pruned = unstaked_connection_table.prune_oldest(max_connections);
            stats
                .num_evictions_unstaked
                .fetch_add(num_pruned, Ordering::Relaxed);
        }
    }
