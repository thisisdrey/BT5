Audit Report

## Title
Child-bounty curator-fee accumulator is never decremented on `unassign_curator`, permanently locking parent-bounty funds - (File: `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`propose_curator` unconditionally adds the proposed child-bounty fee to the parent bounty's `ChildrenCuratorFees` accumulator whenever the child bounty is in the `Added` state. `unassign_curator` resets a child bounty's status back to `Added` from `CuratorProposed`/`Active`/`PendingPayout` without ever subtracting the fee previously added to `ChildrenCuratorFees`, allowing an unbounded accumulation via repeated propose/unassign cycles that eventually zeroes out and permanently strands the parent curator's fee.

## Finding Description
`ChildrenCuratorFees` is a per-parent-bounty running total intended to represent fees owed to child-bounty curators, subtracted from the parent curator's fee at claim time. The only place this value is decremented is `children_curator_fees()`, invoked once when the parent bounty is claimed, which removes the whole storage item. [1](#0-0) 

`propose_curator` adds `fee` to `ChildrenCuratorFees` any time the child bounty is `Added`: [2](#0-1) 

`unassign_curator` reverts the child bounty's status to `Added` from `CuratorProposed`, `Active`, or `PendingPayout` — including when the proposed curator self-unassigns with zero penalty — but never touches `ChildrenCuratorFees` nor resets `child_bounty.fee`: [3](#0-2) 

Since `Added` is exactly the precondition `propose_curator` requires to add a new fee, an attacker can repeatedly propose and self-unassign, growing `ChildrenCuratorFees` monotonically without any actual payout occurring. Existing guards (`ensure_bounty_active`, `RequireCurator`, `UnexpectedStatus` checks) only gate *who* can call these functions and *when*, but do nothing to prevent double-counting of the same child bounty's fee across multiple propose/unassign cycles.

## Impact Explanation
This matches the "permanent user-fund lock" impact category. `pallet-bounties`'s claim logic computes the parent curator's payable fee as `bounty.fee.saturating_sub(children_curator_fees(bounty_id))` while beneficiary payout is computed independently from `value - fee`. Once the accumulated `ChildrenCuratorFees` exceeds the parent bounty's `fee` (achievable purely through the propose/unassign cycle, with no child bounty ever completing), `saturating_sub` clamps the curator's fee to zero. The gap between the original reserved `fee` and the zeroed-out actual payment is never transferred to anyone and remains stuck in the bounty's pot account after the bounty record is purged on claim.

## Likelihood Explanation
No privileged actor is required. Any account proposed as a child-bounty curator can self-unassign at the `CuratorProposed` stage with no deposit slashed (deposits are only reserved at `accept_curator`, not `propose_curator`), as shown in the `CuratorProposed` match arm of `unassign_curator`. The parent curator (an ordinary assigned account, not privileged treasury/governance) can then freely re-propose. This cycle is cheap, repeatable, and fully driven by public extrinsics with on-chain-observable state (`ChildrenCuratorFees`), making it straightforward to trigger deliberately.

## Recommendation
In `unassign_curator`, before resetting `child_bounty.status` to `Added`, subtract `child_bounty.fee` from `ChildrenCuratorFees::<T>::get(parent_bounty_id)` whenever the previous status was `CuratorProposed`, `Active`, or `PendingPayout` (i.e., whenever a fee had actually been added for that child bounty), and reset `child_bounty.fee` to zero. This ensures the accumulator only ever reflects fees for currently pending/active child-bounty curator assignments.

## Proof of Concept
1. Treasury funds a parent bounty with `value = 100`, `fee = 50`; curator `C` accepted.
2. `C` calls `add_child_bounty(parent, value=10)` → child bounty `child_0` in `Added` state.
3. `C` calls `propose_curator(parent, child_0, X, fee=40)` → `ChildrenCuratorFees[parent] = 40` (per `propose_curator` at lib.rs:389-391).
4. `X` calls `unassign_curator(parent, child_0)` (signed as proposed curator, no penalty per lib.rs:532-547) → `child_0.status = Added`, but `ChildrenCuratorFees[parent]` remains `40`.
5. `C` calls `propose_curator(parent, child_0, Y, fee=40)` again → `ChildrenCuratorFees[parent] = 80`.
6. Repeat steps 4–5 once more → `ChildrenCuratorFees[parent] = 120`, exceeding the parent bounty's `fee = 50`.
7. Parent bounty is claimed: `final_fee = fee.saturating_sub(children_fee) = 50.saturating_sub(120) = 0`. Curator `C` receives `0` fee instead of `50`, and that `50` remains stuck in the bounty's pot account after the bounty record is purged — permanently unrecoverable.
