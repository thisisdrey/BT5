### Title
Missing zero-check on `totalEnergyWeight` in `RepositoryImpl.calculateGlobalEnergyLimit` causes division-by-zero / incorrect energy-limit allocation for TVM contract accounts - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit(AccountCapsule)` computes a frozen-balance-holder's global energy limit by dividing `totalEnergyLimit` by `totalEnergyWeight`. Unlike the sibling implementation in `EnergyProcessor.calculateGlobalEnergyLimit`, this TVM-`Repository` variant relies solely on a Java `assert` statement to guard against `totalEnergyWeight == 0` instead of an actual runtime check. Since JVM assertions are disabled by default in production (`-ea` not set), the guard is a no-op, and the code proceeds to divide by zero whenever `totalEnergyWeight` is 0.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit`: [1](#0-0) 

```
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
  long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
  if (frozeBalance < TRX_PRECISION) {
    return 0;
  }
  long energyWeight = frozeBalance / TRX_PRECISION;
  long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
  long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

  assert totalEnergyWeight > 0;

  if (hardenResourceCalculation()) {
    return BigInteger.valueOf(energyWeight)
        .multiply(BigInteger.valueOf(totalEnergyLimit))
        .divide(BigInteger.valueOf(totalEnergyWeight))
        .longValueExact();
  }
  return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
```

This exactly mirrors the pattern described in the external report: a reward/limit ratio is computed as `X / totalWeight`, and the code assumes `totalWeight` can never be zero on the very first (or an emptied) staking cohort. In the report, the Solidity contract simply never checked for `totalStaked == 0` before dividing; here, the check exists syntactically (`assert`) but is functionally absent in a standard production JVM, which runs with assertions disabled by default. `totalEnergyWeight` is a chain-wide counter incremented only when accounts freeze TRX for energy (`addTotalEnergyWeight`), so it can legitimately be zero — e.g., on a freshly bootstrapped private/test network before any freeze-for-energy operation has occurred, or transiently if all energy-weight is unfrozen.

Contrast this with the properly guarded twin implementation in `EnergyProcessor` used elsewhere in the resource-consumption path: [2](#0-1) 

That method explicitly returns 0 when `totalEnergyWeight <= 0` (guarded by `allowNewReward()`), and its V2 counterpart also has a hard `if (totalEnergyWeight == 0) return 0;` check: [3](#0-2) 

The `RepositoryImpl` copy used by the TVM `Repository`/`ContractState` layer (reachable from any TVM contract execution) lacks this real guard, only carrying the vestigial `assert`.

`calculateGlobalEnergyLimit` in `RepositoryImpl` is exposed through the `Repository` interface and delegated to via `ContractState`: [4](#0-3) 

This is invoked by `VMActuator`/native-contract processors during ordinary contract calls (any user-submitted `TriggerSmartContractContract` transaction that touches energy-usage accounting for a frozen-for-energy account), i.e., reachable by any unprivileged transaction broadcaster.

### Impact Explanation
If `totalEnergyWeight` is 0 at the time `calculateGlobalEnergyLimit` is invoked (hardened-calculation path uses `BigInteger.divide`, non-hardened path performs a native `double` division by zero which yields `Infinity`/`NaN` rather than throwing), the outcome differs by code path:
- Hardened path (`BigInteger.divide(BigInteger.ZERO)`): throws `ArithmeticException`, propagating up through TVM execution and potentially causing an unhandled exception in transaction processing — a node-crash / DoS risk for any transaction that reaches this code with a zero total weight.
- Non-hardened (`double`) path: `totalEnergyLimit / 0.0` yields `Infinity`, and the final cast `(long) (energyWeight * Infinity)` yields `Long.MAX_VALUE`, granting the affected account an effectively unlimited energy budget — enabling free/unmetered contract execution and energy exhaustion of node resources, analogous to the "steal rewards / break accounting" impact in the original report, but manifesting as unmetered resource consumption instead of over-minted rewards.

### Likelihood Explanation
Triggering requires `totalEnergyWeight == 0`, which is a legitimate, reachable chain state on any network (private/test chain at genesis, or theoretically a fully-unfrozen mainnet scenario) before the first freeze-for-energy transaction is committed. Any subsequent TVM contract call that reaches `calculateGlobalEnergyLimit` on such a chain state hits this path deterministically. This is directly analogous to the reported bug class (division by an aggregate that can legitimately be zero, guarded only superficially) but I could not fully confirm from the available index whether `totalEnergyWeight` can realistically reach zero on a live mainnet post-genesis (it depends on historical freeze operations and is unlikely to regress to zero after chain maturity). This uncertainty affects the practical likelihood on TRON mainnet specifically, though the code path itself is unconditionally reachable and unguarded in production builds.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime check mirroring `EnergyProcessor`'s guarded implementations, returning `0` (or otherwise short-circuiting) when `totalEnergyWeight <= 0`, so behavior is consistent and safe regardless of whether JVM assertions are enabled.

### Proof of Concept
Not independently reproducible from static analysis alone; would require constructing a chain state with `totalEnergyWeight == 0` (e.g., genesis of a fresh network before any `FreezeBalanceContract`/`FreezeBalanceV2Contract` for energy is committed) and then invoking a `TriggerSmartContractContract` from an account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION`, causing the TVM's `Repository.calculateGlobalEnergyLimit` to be invoked and hit the unguarded division. This mirrors the PoC pattern in the original report (`epochId 0` staking absent → division by zero / `Infinity` result on `epochId 1`).
