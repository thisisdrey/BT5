### Title
Silent unaccounted packet-batch loss in `EvictingSender::try_send` under concurrent re-queue race - (File: streamer/src/evicting_sender.rs)

### Finding Description
`EvictingSender::try_send` implements the "evict oldest on full" policy for bounded channels feeding both the TPU non-vote banking channel (`BankingTracer::create_channel_non_vote`, `NON_VOTE_CHANNEL_CAPACITY = 16384`) and the shred/vote fetch channels (`ShredFetchStage`, `FetchStage`). [1](#0-0) 

The eviction path is: [2](#0-1) 

When the channel is full, the thread pops the oldest queued item via `self.receiver.try_recv()` (`older`), then attempts to re-queue the new message with `self.sender.try_send(msg)?`. If a concurrent clone of the same `EvictingSender` (multiple producer threads, e.g. per-socket fetch threads or sigverify workers writing into the shared banking channel) fills the freed slot before this thread's re-queue executes, `self.sender.try_send(msg)` fails and the `?` operator returns early with `Err(TrySendError::Full(msg))`. At that point `older` — the item already removed from the channel — is dropped in place (its destructor runs) without ever being returned to the caller or folded into any drop/eviction counter. The function's only visible error carries `msg` (the *new*, still-unsent item), not `older` (the already-evicted, now-lost item).

Callers of this API only account for what is returned in the `Err` variant:
- `TracedSender::send` maps `TrySendError::Full(b)` to `Ok(b.len())` and callers (`sigverify.rs`) add that to `eviction_drops` — this counts the failed-to-enqueue new batch, but never the silently dropped `older` batch. [3](#0-2) [4](#0-3) 
- `ShredFetchStage::modify_packets` similarly only counts `v.len()` from the returned `Full` error, with the fallback branch marked `unreachable!()`, which does not anticipate the double-loss case. [5](#0-4) 

This exact race is acknowledged in the code's own comment ("if multiple senders are used, and another sender is faster than us to send() after we've popped `older`, our try_send() will fail with Full(msg)"), but the comment mischaracterizes the outcome as "we drop the new message" — in fact the *already-popped* `older` message is the one irretrievably lost, and it is never surfaced to any stats/accounting path.

### Impact Explanation
An unprivileged remote client sending a sustained flood of TPU packets (or shreds, for the fetch-stage variant) can saturate the bounded ingress channel to the point where the eviction path is continuously exercised by concurrently-running producer threads (multiple socket/streamer receiver threads all send into the same cloned `EvictingSender`). Under sustained saturation, some fraction of evicted `older` batches are lost with zero accounting anywhere (no `eviction_drops` increment, no `overflow_shreds` increment, no return value to any caller). This breaks the stated invariant that ingress packet loss must be observable/attributable, and lets an attacker mask the true degree of channel saturation from operators' metrics — a real, silent-drop / metrics-integrity bug in the hot ingress path, matching Agave's "denial-of-service masking / observability" bounty category for ingress-buffer accounting flaws. It does not, however, cause unbounded memory growth, a panic, a consensus/verification bypass, or QoS evasion beyond the metrics undercount itself — the channel capacity bound is still respected.

### Likelihood Explanation
The race requires only concurrent calls to `try_send`/`send` on clones of the same `EvictingSender` while the channel is at capacity — no privileged, staked, or config access needed. This condition is trivially reachable during any sustained flood of the TPU non-vote or shred/vote fetch paths, since these channels are fed by multiple producer threads (e.g. multiple socket-serving threads in `ShredFetchStage`/`FetchStage`, or parallel sigverify workers pushing into the shared banking channel). The narrow timing window (a few instructions between `try_recv` and `try_send`) makes each individual occurrence non-deterministic, but under sustained high-throughput flooding by an attacker, the race fires repeatedly, so the aggregate unaccounted loss is practically observable over time even though a single occurrence is probabilistic.

### Recommendation
Change `EvictingSender::try_send` so that when the re-queue of `msg` fails after `older` has already been popped, both messages are accounted for: return or fold `older` into a caller-visible eviction/drop statistic instead of dropping it silently. For example, retry the re-queue with a small bounded loop, or return an enriched error type carrying both `older` and `msg` (or their counts) so callers can update accounting for both, rather than using `?` to short-circuit and discard `older`.

### Proof of Concept
```rust
// streamer/src/evicting_sender.rs (test)
use std::sync::{Arc, Barrier};
use std::thread;
use crossbeam_channel::TrySendError;
use crate::streamer::ChannelSend;
use crate::evicting_sender::EvictingSender;

#[test]
fn concurrent_try_send_loses_evicted_message_unaccounted() {
    const CAP: usize = 8;
    const THREADS: usize = 16;
    let (sender, _receiver) = EvictingSender::<usize>::new_bounded(CAP);

    // Fill channel to capacity first.
    for i in 0..CAP {
        sender.try_send(i).unwrap();
    }

    let barrier = Arc::new(Barrier::new(THREADS));
    let mut handles = Vec::new();
    // total accounted drops observed via TrySendError::Full return values
    let accounted = Arc::new(std::sync::atomic::AtomicUsize::new(0));

    for t in 0..THREADS {
        let sender = sender.clone();
        let barrier = barrier.clone();
        let accounted = accounted.clone();
        handles.push(thread::spawn(move || {
            barrier.wait();
            match sender.try_send(1000 + t) {
                Ok(()) => {}
                Err(TrySendError::Full(_older_or_new)) => {
                    accounted.fetch_add(1, std::sync::atomic::Ordering::Relaxed);
                }
                Err(TrySendError::Disconnected(_)) => unreachable!(),
            }
        }));
    }
    for h in handles { h.join().unwrap(); }

    // EXPECTATION under a correct implementation: every net-removed item across
    // the whole operation (CAP items originally + THREADS inserted - CAP remaining)
    // should be accounted for by `accounted` (or an equivalent counter).
    // Under the current implementation, `accounted` undercounts because some
    // `older` items are dropped inside the `Ok(older) => { self.sender.try_send(msg)?; ... }`
    // branch without ever reaching the `Err(TrySendError::Full(older))` return,
    // and without incrementing any counter.
    let remaining = sender.len();
    let total_inserted_attempts = THREADS; // new items attempted
    let expected_drops = total_inserted_attempts.saturating_sub(CAP.saturating_sub(remaining));
    assert_eq!(
        accounted.load(std::sync::atomic::Ordering::Relaxed),
        expected_drops,
        "accounted drops must equal expected drops -- mismatch indicates an unaccounted/silent loss of an evicted `older` message"
    );
}
```
Expected result: on the current implementation this assertion fails intermittently under concurrency (accounted < expected_drops), demonstrating that some evicted `older` messages are dropped without being reflected in any error return or counter.

    fn try_send(&self, msg: T) -> std::result::Result<(), TrySendError<T>> {
        let Err(e) = self.sender.try_send(msg) else {
            return Ok(());
        };

        match e {
            // Prefer newer messages over older messages.
            TrySendError::Full(msg) => match self.receiver.try_recv() {
                Ok(older) => {
                    // Attempt to requeue the newer message.
                    // NB: if multiple senders are used, and another sender is faster than us to send() after we've popped `older`,
                    // our try_send() will fail with Full(msg), in which case we drop the new message.
                    self.sender.try_send(msg)?;
                    // Propagate the error _with the older message_.
                    Err(TrySendError::Full(older))
                }
                // Unlikely race condition -- it was just indicated that the channel is full.
                // Attempt to requeue the message.
                Err(TryRecvError::Empty) => self.sender.try_send(msg),
                // Unreachable in practice since we maintain a reference to both the sender and receiver.
                Err(TryRecvError::Disconnected) => unreachable!(),
            },
            // Unreachable in practice since we maintain a reference to both the sender and receiver.
            TrySendError::Disconnected(_) => unreachable!(),
        }
    }
