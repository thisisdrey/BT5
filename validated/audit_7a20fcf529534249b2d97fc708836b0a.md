### Title
Unbounded nested-length array indexing in `ValidateMultiSign` / `BatchValidateSign` precompiles leads to uncaught runtime exceptions on attacker-controlled calldata - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray()` and `extractSigArray()` read a nested "array length" word from attacker-controlled calldata and then index further nested words using that length, without ever validating that `offset + len` stays within the bounds of the parsed `DataWord[] words` array. This mirrors CVE-2025-37789's root cause in the Linux kernel openvswitch `set()` action: a nested length/attribute is trusted and used to walk further into a buffer before the buffer's actual size is checked.

### Finding Description
`extractBytesArray` only bounds-checks the *offset* used to read the length field, not the length itself against the number of parsed words: [1](#0-0) 

`extractSigArray` has the identical pattern: [2](#0-1) 

Both are invoked directly from `ValidateMultiSign.execute()` with an offset (`words[3].intValueSafe() / WORD_SIZE`) taken straight from calldata, and — critically — this call happens *before* the method's only `try { } catch (Throwable t)` block, which wraps just the permission-weight logic further down: [3](#0-2) [4](#0-3) 

Because `len = words[offset].intValueSafe()` is fully attacker-controlled:
- A large positive `len` (e.g. close to `Integer.MAX_VALUE`) causes `new byte[len][]` to throw `OutOfMemoryError`, or the subsequent loop `words[offset + i + 1]` to throw `ArrayIndexOutOfBoundsException` once `i` runs past the actual parsed `words.length`.
- A negative-interpreted 32-byte word (top bit set, via `intValueSafe()`) causes `new byte[len][]` to throw `NegativeArraySizeException` immediately.

None of these are `RuntimeException`/`Throwable` caught anywhere in `ValidateMultiSign.execute()` before this point, so the exception propagates uncaught out of the precompiled-contract `execute()` call. `BatchValidateSign.doExecute()` uses the same helper (`extractBytesArray`/`extractSigArray`) with the same unchecked length, but is at least wrapped by an outer `catch (Throwable t)` in `execute()`: [5](#0-4) 
so only the `ValidateMultiSign` path is exposed unguarded.

Both precompiled contracts are reached from ordinary contract execution via the `CALL`/`STATICCALL` opcode dispatch path in the TVM: [6](#0-5) 

### Impact Explanation
Any account that deploys or calls a smart contract can craft calldata to a contract that performs a low-level `CALL` to the `ValidateMultiSign` precompiled contract address with a malformed nested-array offset/length, triggering an uncaught `NegativeArraySizeException`, `ArrayIndexOutOfBoundsException`, or `OutOfMemoryError` inside `PrecompiledContracts.ValidateMultiSign.execute()`. Because this occurs deterministically for every node executing the same transaction (during block application in `Manager`/TVM execution), it can produce inconsistent handling across nodes (some may propagate the error up as an unhandled fault) and is a reachable transaction-processing crash/DoS vector rather than a benign revert.

### Likelihood Explanation
Likelihood is high: triggering the bug requires only crafting normal ABI-style calldata for a broadcastable smart-contract transaction that performs a `CALL` to the `ValidateMultiSign` precompile address — no special privileges, staking, or witness/SR status is required, and the malformed length field is trivial to construct.

### Recommendation
In `extractBytesArray` and `extractSigArray`, validate that `len >= 0` and that `offset + len` (and each derived `bytesOffset`/`bytesLen`) remains within `words.length` and the underlying `data` byte array bounds before allocating arrays or indexing, returning an empty/invalid result instead of throwing. Additionally, wrap the entire body of `ValidateMultiSign.execute()` (not just the permission-check section) in a `catch (Throwable)` block consistent with `BatchValidateSign`, so malformed input degrades to `DATA_FALSE` rather than propagating an uncaught exception.

### Proof of Concept
1. Deploy a helper contract that performs a low-level `call` to the `ValidateMultiSign` precompiled contract address.
2. Construct calldata as 32-byte words: `word0=address`, `word1=permissionId`, `word2=offset_to_data`, `word3=offset_to_sig_array` (e.g. `0xA0`), followed by a data blob, then at the sig-array offset place a length word set to a very large value (e.g. `0x7FFFFFFF`) or a value with the sign bit set (e.g. `0xFFFFFFFF...`).
3. Broadcast the transaction calling this helper contract.
4. `extractBytesArray`/`extractSigArray` in `PrecompiledContracts.java` will attempt `new byte[len][]` or index `words[offset + i + 1]` beyond the parsed word array, throwing an uncaught `NegativeArraySizeException`/`ArrayIndexOutOfBoundsException`/`OutOfMemoryError` from within `ValidateMultiSign.execute()`, since this call site is outside the method's only try/catch guard.
