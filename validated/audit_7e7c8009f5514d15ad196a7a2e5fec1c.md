### Title
Flash-loan sandwich DoS of deposits via `maxTotalSupply` supply-cap inflation - (File: contracts/DepositToken.sol)

### Summary
`DepositToken._mint` reverts with `SurpassMaxDepositSupply` whenever `totalSupply` exceeds the pool-wide `maxTotalSupply` cap. Because `deposit()` and `withdraw()` are both permissionless and have no cooldown, an attacker can flash-loan the underlying, front-run a victim's `deposit()` with a huge deposit that pushes `totalSupply` to the cap, let the victim's transaction revert, and immediately back-run with `withdraw()` to recover funds — repeating this for every depositor. This is the same bug class as the Carapace `leverageRatioCeiling` sandwich: a shared, revert-on-limit check that an attacker can temporarily saturate with borrowed capital.

### Finding Description
`DepositToken.deposit(amount_, onBehalfOf_)` pulls underlying to the treasury, then calls `_mint` (`contracts/DepositToken.sol:211-237`). Inside `_mint`:

```solidity
totalSupply += amount_;
if (totalSupply > maxTotalSupply) revert SurpassMaxDepositSupply();
```
(`contracts/DepositToken.sol:469-489`)

The check is against global `totalSupply`, not per-account, so any account can force it to trip. There is no deposit→withdraw cooldown in the current code (the old BSC build had `lastDepositOf`/`minDepositTime`, which has been removed). `withdraw(amount_, to_)` only requires `_revertIfLocked(_msgSender, amount_)`, which consults `unlockedBalanceOf`; for an attacker with no debt position, `debtPositionOf` returns `_debtInUsd == 0` and the full balance is unlocked (`contracts/DepositToken.sol:383-398, 406-412`). Withdraw is enabled whenever the pool is not in `everythingStopped`, per `docs/emergency-flags.md`, i.e. it is open exactly when deposits are open.

Attack sequence per block:
1. Attacker flash-loans `X` of the underlying (e.g. WETH/msdWETH underlying).
2. Front-run victim: `deposit(X, attacker)` → `totalSupply ≈ maxTotalSupply`.
3. Victim's `deposit(amount, victim)` reverts with `SurpassMaxDepositSupply`.
4. Back-run: `withdraw(mintedAmount, attacker)` → repays flash loan; cost is only depositFee + withdrawFee + flash-loan fee, which can be zero.

### Impact Explanation
Denial of the `deposit()` entry point for all users of a given collateral, sustainable for as long as the attacker can fund the flash loan. Users' deposits are temporarily frozen out of the protocol (liveness break on the deposit invariant). This also griefs flows built on deposits, such as `SmartFarmingManager.leverage`/zaps that call `deposit` internally, causing those transactions to revert too.

### Likelihood Explanation
Likelihood scales with proximity of `totalSupply` to `maxTotalSupply` and the availability of flash liquidity in the underlying. No privileged role, oracle manipulation, or governance misconfiguration is required — only a public deposit/withdraw pair and a supply cap that exists precisely to be approached. Cost is bounded by fees, which are zero when `depositFee`/`withdrawFee` are zero.

### Recommendation
Enforce a cooldown between deposit and withdraw (e.g. record `lastDepositOf[account]` and require `block.timestamp > lastDepositOf[account] + minDepositTime` in `_withdraw`, or simply `block.number + 1`), as the prior `minDepositTime` mechanism did. Alternatively, evaluate the cap check against a value that cannot be round-tripped within one transaction.

### Proof of Concept
```solidity
// Hardhat/Foundry fork sketch — DeployToken wired to a real Pool/Treasury
// Precondition: maxTotalSupply - totalSupply < flashLoanable underlying
uint256 gap = depositToken.maxTotalSupply() - depositToken.totalSupply();

// 1) flash-loan `gap + epsilon` underlying
// 2) frontrun victim
underlying.approve(address(depositToken), type(uint256).max);
depositToken.deposit(gap, attacker);            // totalSupply == maxTotalSupply

// 3) victim tx (would be a separate tx in the same block)
vm.expectRevert(SurpassMaxDepositSupply.selector);
depositToken.deposit(1 ether, victim);          // reverts

// 4) backrun: attacker has no debt -> fully unlocked
depositToken.withdraw(depositToken.balanceOf(attacker), attacker);
// repay flash loan; repeat on next victim
```
I was not able to read the full `_withdraw` body within the iteration budget, but `withdraw()` is confirmed public, guarded only by `_revertIfLocked`, and enabled whenever the pool is not `everythingStopped`, so the round-trip holds.
