### Title
Exchange liquidity is permanently frozen because the creator address of an Exchange (market order pair) can never be reassigned - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java])

### Summary
When any account calls `ExchangeCreateContract` to create a TRX/TRC10 trading pair, the resulting `ExchangeCapsule` permanently binds the deposited liquidity to the `creatorAddress` captured at creation time. There is no actuator, contract type, or code path that lets this creator address be transferred or updated. If the key controlling that address is lost or compromised, the liquidity locked into the exchange can never be injected into or withdrawn by anyone else, since every liquidity-management path strictly checks `creatorAddress` equality.

### Finding Description
`ExchangeCreateActuator.execute()` builds a new `ExchangeCapsule` using the transaction's `ownerAddress` as the immutable creator: [1](#0-0) 

This creator address is stored as `creatorAddress` inside the `Exchange` proto message via the capsule constructor: [2](#0-1) 

`ExchangeCapsule` does expose a `setExchangeAddress(ByteString address)` setter capable of reassigning the creator: [3](#0-2) 

However, this setter is never invoked by any actuator in the codebase — there is no `ExchangeUpdateContract`, `ExchangeTransferContract`, or any other broadcastable transaction type that calls it. It is effectively dead code, confirming the absence of any user-reachable mechanism to change an exchange's creator.

Every operation that manages the deposited liquidity — `ExchangeInjectActuator` and `ExchangeWithdrawActuator` — hard-requires the transaction's `ownerAddress` to equal `exchangeCapsule.getCreatorAddress()`: [4](#0-3) [5](#0-4) 

This mirrors the KintoWallet report's bug class exactly: a critical address role (here, the "exchange owner"/"recoverer of liquidity") is fixed permanently at creation with no update mechanism, so if that address becomes inaccessible (lost key, compromised key, or the address is later frozen/blacklisted by governance), the associated funds have no recovery path.

### Impact Explanation
Any TRX or TRC10 token balance deposited into an `Exchange` (via `ExchangeCreateContract` and later `ExchangeInjectContract`) becomes permanently non-recoverable once the creator's private key is lost or compromised. Trading against the pool via `ExchangeTransactionContract` still works and drains liquidity via the AMM curve, but ordered withdrawal/injection management (rebalancing, exit) is permanently locked to a single, unchangeable address. This is a concrete permanent freezing-of-funds condition reachable purely from a single signed transaction (`ExchangeCreateContract`) broadcast by any unprivileged account.

### Likelihood Explanation
Likelihood is inherent rather than requiring an attacker: any wallet key loss, key rotation failure, key compromise, or address sanctioning/incident affecting the creator account results in the condition. Because `ExchangeCreateContract` can be sent by any account with sufficient balance to pay the creation fee and lock in token balances, this is trivially reachable by any ordinary user, and the risk accumulates naturally over the lifetime of every exchange pair created on-chain.

### Recommendation
Introduce a governed update path (e.g., an `ExchangeUpdateContract`/`ExchangeTransferOwnerContract` actuator) that allows the current `creatorAddress` (or a multisig/owner-permission holder of that account, consistent with `AccountPermissionUpdateActuator`) to reassign the exchange's creator to a new address, using the already-present but currently unused `ExchangeCapsule.setExchangeAddress()` method. Alternatively, allow withdrawal/injection authorization to be satisfied by the account's active/owner multisig permissions rather than a single hardcoded address snapshot.

### Proof of Concept
1. Account `A` broadcasts `ExchangeCreateContract` with `ownerAddress = A`, depositing TRX and a TRC10 token to create exchange `id=1`. `ExchangeCreateActuator.execute()` stores `creatorAddress = A` in both `ExchangeStore`/`ExchangeV2Store` capsules [6](#0-5) .
2. Account `A`'s private key is subsequently lost/compromised.
3. Any attempt to withdraw or inject additional liquidity for exchange `id=1` (`ExchangeWithdrawContract`/`ExchangeInjectContract`) from any other address fails validation with `"account[...] is not creator"` [5](#0-4) .
4. No contract type exists to reassign `creatorAddress` (confirmed absence of `ExchangeUpdateContract`/transfer-owner contract and confirmed `ExchangeCapsule.setExchangeAddress()` has zero callers in the codebase), so the liquidity deposited by `A` remains permanently stuck and unmanageable, aside from being drained via the AMM `transaction()` curve by unrelated traders.
