The strongest reachable DoS surface: dust-transfer griefing of the per-account token list (`MAX_TOKENS_PER_USER = 30`).

### Title
Attacker can permanently block a victim from depositing new collateral or borrowing by dust-filling their account token list to `MAX_TOKENS_PER_USER` - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Every `Pool` tracks a per-account enumerable set of deposit tokens and debt tokens, capped at `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`). `DepositToken._transfer` (and `_mint`) unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever a recipient's balance goes from 0 to >0 (`contracts/DepositToken.sol:517-520`), and `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the combined list length is 30 (`contracts/Pool.sol:143-148, 216-220`). An unprivileged attacker can transfer 1-wei dust of every enabled `DepositToken` to a victim, filling all 30 slots. From then on, any transfer/deposit/mint of a *new* deposit token to the victim reverts, and — critically — any `DebtToken.issue`/`mint` to the victim reverts because `addToDebtTokensOfAccount` enforces the same cap (`contracts/Pool.sol:204-208`).

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's list on first receipt, with no opt-out and no minimum amount — 1 wei suffices to occupy a slot (`contracts/DepositToken.sol:517-520`).
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` both enforce `onlyIfAdditionWillNotReachMaxTokens`, counting debt + deposit tokens together (`contracts/Pool.sol:143-148`).
- The pool can host up to 30 deposit tokens (`ReachedMaxDepositTokens` uses the same constant), so a single attacker can fill the entire victim list alone.
- Consequences once the victim's list is full:
  - `Pool.deposit` of any collateral the victim doesn't already hold reverts (mint → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`), so fresh collateral cannot enter the victim's position.
  - `DebtToken.issue`/`mint` reverts, so the victim cannot borrow any synthetic asset, even against already-deposited collateral.
  - `SmartFarmingManager.leverage` and liquidation paths that mint/seize a *new* token type to the victim also revert.
- Recovery requires the victim to fully transfer out a dusted token (freeing a slot via `removeFromDepositTokensOfAccount`), but the attacker can re-dust in the same or next block at ~1 wei cost, making the DoS effectively permanent for as long as the attacker chooses.

### Impact Explanation
Temporary freezing of funds / liveness denial for a targeted account: the victim's collateral is locked out of any new borrowing, and new collateral cannot be deposited. If the victim's position turns unhealthy while dusted, their ability to add collateral to save it is blocked, indirectly forcing liquidation. No privileged role is needed; DepositToken transfers are permissionless.

### Likelihood Explanation
Cheap and permissionless: requires only dust balances of each enabled deposit token (obtainable by depositing a minimal amount or buying the underlying). The only mitigating factor is that victims can clear slots, but re-dusting is trivially repeatable, including front-running the victim's cleanup.

### Recommendation
Either (a) charge/deposit a meaningful minimum before registering a token in the account list, (b) only register tokens on `deposit`/borrow actions initiated via the `Pool` (where the victim opts in) rather than on raw ERC20 `transfer`, or (c) allow the account owner to purge list entries. Option (b) is the cleanest: track the list in `Pool.deposit`/`DebtToken.issue` instead of inside `DepositToken._transfer`.

### Proof of Concept
```ts
// hardhat fork test sketch
it('griefs victim token list', async () => {
  const attacker = ...; const victim = ...;
  const depositTokens = await pool.getDepositTokens(); // assume ~N enabled
  for (const addr of depositTokens) {
    const dt = await ethers.getContractAt('DepositToken', addr);
    // attacker acquires dust via pool.deposit(underlying, 1) then:
    await dt.connect(attacker).transfer(victim.address, 1);
  }
  // also dust-fill remaining slots using debt-free repeats isn't possible;
  // needs >=30 deposit tokens across pools sharing the cap? cap is per-pool.
  // victim now has 30 entries:
  await expect(pool.connect(victim).deposit(newUnderlying, amount))
    .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
  await expect(debtToken.connect(victim) /* via pool.borrow */)
    .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
});
```
Caveat for a full fork PoC: feasibility depends on the deployed pool having enough enabled `DepositToken`s to reach 30 slots (the per-pool deposit-token cap also equals `MAX_TOKENS_PER_USER`, so at full listing a single attacker can saturate a victim). If the live configuration lists fewer deposit tokens, the attack only partially fills the list and impact is reduced — verify `pool.getDepositTokens().length` on the target chain.
