### Title
Missing zero-address check on `new_authority` in `transfer_to_new_account`/`transfer_to_new_account_pda` permanently locks migrated funds - (File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs)

### Summary
The `transfer_to_new_account` and `transfer_to_new_account_pda` instructions let an account authority migrate their `MarginfiAccount` (including all lending positions/funds) to a brand-new account under an arbitrary `new_authority`. The `new_authority` account is explicitly documented as "completely unchecked" and is never validated to be non-zero. If `new_authority` is `Pubkey::default()` (the zero pubkey), the new account's `authority` field is set to the zero pubkey, and the old account is disabled and its `lending_account` zeroed out, permanently locking the migrated balances since no keypair can ever sign as `Pubkey::default()`.

### Finding Description
Both accounts structs mark `new_authority` as unchecked: [1](#0-0) [2](#0-1) 

The handler passes `ctx.accounts.new_authority.key()` straight into `initialize_migrated_account`, which calls `MarginfiAccount::initialize`, setting `self.authority = authority` with no zero check anywhere in the call chain: [3](#0-2) [4](#0-3) [5](#0-4) 

Immediately afterward, the old account (which held the actual `lending_account` balances) is disabled and zeroed, and the migration is marked irreversible (`migrated_to` is checked to prevent re-migration): [6](#0-5) [7](#0-6) 

Notably, the off-chain `p0-cli` tooling explicitly guards against this exact scenario, confirming the maintainers are aware zero-authority is invalid, but this guard only exists client-side and is not enforced on-chain: [8](#0-7) 

This is a direct analog of the report's "missing zero checks" bug class (e.g. `MapleLoan.setBorrower`/`setLender` allowing `address(0)`): an unprivileged account holder can migrate their own account with a zero `new_authority`, and since the migration copies the `lending_account` (all deposit/borrow positions) into the new account while disabling and zeroing the old one, the funds become permanently inaccessible — no one holds the private key for `Pubkey::default()`.

### Impact Explanation
If a user (or a buggy front end, exactly as described in the report's exploit scenario) submits `transfer_to_new_account` or `transfer_to_new_account_pda` with `new_authority = Pubkey::default()`, the new `MarginfiAccount` — now holding all of the migrated lending positions — becomes permanently uncontrollable, and the old account is simultaneously disabled with its `lending_account` zeroed. This is a permanent lock/freeze of user funds with no recovery path (the `migrated_to`/`AccountAlreadyMigrated` check prevents retrying from the old account), matching the "Impact: High" severity criteria (permanent lock).

### Likelihood Explanation
The instruction is fully permissionless for any account authority to call on their own account, requires no admin/privileged role, and the vulnerable parameter (`new_authority`) is client-supplied with zero on-chain validation. A front-end bug, malformed script, or accidental use of an uninitialized/default pubkey variable — the exact scenario described in the source report — is sufficient to trigger it.

### Recommendation
Add an explicit check in both `transfer_to_new_account` and `transfer_to_new_account_pda` that `ctx.accounts.new_authority.key() != Pubkey::default()`, returning a dedicated error (e.g. `MarginfiError::InvalidAuthority` or similar) before any state mutation occurs.

### Proof of Concept
1. User creates/owns a `MarginfiAccount` with active deposit/borrow positions.
2. User (or a buggy front end) calls `transfer_to_new_account` (or `transfer_to_new_account_pda`), signing as the current `authority`, but supplies `new_authority = Pubkey::default()`.
3. The instruction succeeds: `initialize_migrated_account` sets the new account's `authority` to `Pubkey::default()` and copies over `lending_account` (all balances); `finalize_migrated_old_account` disables the old account and zeroes its `lending_account`, setting `migrated_to` to the new account.
4. No wallet can ever sign as `Pubkey::default()`, so the new account (and the funds it now holds) is permanently locked; the old account cannot be reused because `migrated_to != Pubkey::default()` triggers `AccountAlreadyMigrated` on any retry.

    fn initialize(&mut self, group: Pubkey, authority: Pubkey, current_timestamp: u64) {
        self.authority = authority;
        self.group = group;
        self.emissions_destination_account = Pubkey::default();
        self.migrated_from = Pubkey::default();
        self.last_update = current_timestamp;
        self.migrated_to = Pubkey::default();

        // Seed activity flags so freshly-created accounts aren't immediately eligible for the
        // permissionless close path before the first pulse.

        self.indexer_flags.was_active_60d = 1;
        self.active_orders = 0;
    }
