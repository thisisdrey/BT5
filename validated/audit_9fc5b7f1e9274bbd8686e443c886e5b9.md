### Title
Vault `redeem` updates the `assets` accounting variable only after the external `send-underlying` transfer completes, allowing reentrant calls to observe stale liquidity state - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and identical pattern in `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`)

### Summary
Every Zest v0 vault's `redeem` function follows the exact "external call before state update" pattern flagged in the Notional Sherlock report: it burns shares and sends the underlying asset via `send-underlying` *before* decrementing the internal `assets` accounting variable with `var-set assets`.

### Finding Description
In `redeem`, the sequence is: `(try! (ft-burn? zft amount account))`, `(try! (send-underlying inkind recipient))`, and only afterward `(var-set assets (- current-assets inkind))` [1](#0-0) . All liquidity checks (`get-available-assets`, `current-assets`) are computed from the `assets` and `total-borrowed` data-vars *before* this update [2](#0-1) . This mirrors the M-1 report's root cause exactly: the state mutation that other functions rely on for correctness (`totalBPTHeld`/`totalStrategyTokenGlobal` there, `assets` here) happens strictly after an external interaction (`_unstakeAndExitPool` there, `send-underlying` here) rather than before it. Notably, unlike `deposit`, which explicitly guards with `(asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)` [3](#0-2) , `redeem` has no equivalent reentrancy guard at all [4](#0-3) .

However, I could not locate the definition of `send-underlying` itself within the indexed portion of these files, so I cannot confirm from the available code whether the underlying transfer mechanism (e.g., `stx-transfer?` vs. an `ft-transfer?` to an arbitrary SIP-010 trait implementation) can actually trigger a callback into the vault contract during the transfer. In Clarity, `stx-transfer?` cannot invoke recipient code, and SIP-010 `ft-transfer?` calls also do not grant the receiving principal control flow unless the recipient is itself a contract with a `transfer` post-condition trap — Clarity's execution model does not support arbitrary reentrant callbacks the way EVM `call`/`transfer` does for external contracts implementing hooks. Without the `send-underlying` implementation, I cannot conclusively prove a reachable reentrancy vector purely from Clarity mechanics, unlike the Solidity Aura/Balancer external call in the original report, which explicitly could re-enter via ERC-20 hooks or attacker-controlled pool contracts.

### Impact Explanation
If a reentrancy path were provable (which I cannot confirm from the available code), a stale `assets`/`get-available-assets` read during the window between `send-underlying` and `var-set assets` could allow a second `redeem` (or `borrow`) call to pass the `ERR-INSUFFICIENT-LIQUIDITY` / `ERR-INSUFFICIENT-ASSETS` checks against liquidity that has already been paid out, resulting in double-spending of vault reserves — a direct theft of user funds at rest (Critical impact class). This would require the underlying transfer or a subsequent call to feasibly re-enter `redeem`/`borrow` on the same vault, which is unconfirmed.

### Likelihood Explanation
Low/uncertain. Clarity's contract-call semantics do not provide the same free-form callback surface Solidity does; a recipient contract does not get executed code merely by receiving STX or fungible tokens unless it separately makes a synchronous contract-call back into the vault as part of the same transaction (e.g., the caller being a contract with logic in its `redeem` wrapper, which itself calls back into `redeem` before the first call returns). Since Clarity has no reentrant "hook" analogous to ERC-777/`onERC721Received`, the primary way to reach the vulnerable window would be through the caller being a smart contract that makes a nested call — but standard direct `contract-caller` calls to `redeem` complete synchronously and the vault has no known callback trait invoked during `send-underlying` based on the visible code.

### Recommendation
Regardless of whether a concrete reentrancy path exists today, apply the checks-effects-interactions pattern defensively: move `(var-set assets (- current-assets inkind))` to occur immediately after the burn and before `(try! (send-underlying inkind recipient))` in all six vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`), consistent with how `deposit` already updates `assets` right after `receive-underlying`/`ft-mint?` [5](#0-4) .
