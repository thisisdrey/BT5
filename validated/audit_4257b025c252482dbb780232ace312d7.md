### Title
Cache Key Collision in `GetArchive` via Ambiguous Concatenation of Dynamic-Length Fields - ([File: internal/gitaly/service/repository/archive.go])

### Summary
`createArchiveCacheKey` builds the `git archive` cache key by sequentially hashing three independently variable-length, partially user-controlled strings (`GlProjectPath`, a comma-joined `args` slice, and a comma-joined `pathspecs` slice) with no length-prefixing or unambiguous field separators. This is the same class of defect described in the external report: packing multiple dynamically-sized values without an unambiguous boundary allows different logical inputs to serialize to the same byte sequence, causing a hash/key collision.

### Finding Description
`createArchiveCacheKey` computes the cache key as: [1](#0-0) 

```go
func createArchiveCacheKey(gitLabProjectPath string, args []string, pathspecs []string) string {
	cacheKeyHash := sha256.New()
	cacheKeyHash.Write([]byte(gitLabProjectPath))
	cacheKeyHash.Write([]byte(strings.Join(args, ",")))
	cacheKeyHash.Write([]byte(strings.Join(pathspecs, ",")))
	return hex.EncodeToString(cacheKeyHash.Sum(nil))
}
```

`args` and `pathspecs` are built from request-controlled fields (`commitId`, `path`, `exclude`), where `path`/`exclude` are only validated to not escape the repository root via `storage.ValidateRelativePath`, which does not forbid `,` characters: [2](#0-1) [3](#0-2) 

Because `strings.Join(args, ",")` and `strings.Join(pathspecs, ",")` are hashed with no delimiter between them, and elements can themselves contain `,`, two semantically different `(args, pathspecs)` combinations can serialize to an identical byte stream fed into SHA-256 — e.g. an `args` entry ending in a value followed by a comma boundary can be reconstructed by shifting where an element boundary falls in `pathspecs`, or a path containing an embedded comma can be split across the wrong logical field. This is structurally identical to the reported `abi.encodePacked` ambiguity: multiple dynamically-sized values packed together without length-prefixing (`prefixLen` is exactly the mitigation Gitaly already applies elsewhere for this exact class of bug): [4](#0-3) 

The `internal/cache/keyer.go` comment explicitly documents this exact concatenation-ambiguity risk (`f+oobar` vs `foo+bar`), showing the codebase authors are aware of the bug class, yet `createArchiveCacheKey` does not apply the same protection.

### Impact Explanation
A cache-key collision here means the `s.archiveCache.Fetch` call can return (or store) archive content generated for a different `commitId`/`path`/`exclude` combination than what was actually requested: [5](#0-4) 

Since the cache key does not encode the actual `storage_name`/`relative_path` of the repository (only the client-influenced `GlProjectPath` field of the `Repository` message), a crafted request with paths/excludes containing commas could cause the wrong archive payload — e.g. a broader or different subset of tree contents than authorized for that request — to be served, resulting in unintended content disclosure between differing archive requests that hash to the same key. This is a medium-severity data-confusion issue: it does not directly grant new privileges but corrupts the integrity assumption that the cache key uniquely represents the request.

### Likelihood Explanation
Exploitation requires an attacker to control the `path` and/or `exclude` fields of a `GetArchiveRequest` (an ordinary RPC field reachable by any client authorized to call `GetArchive` for at least one repository) and craft comma-containing relative path names, which are only checked for path-traversal, not for character restrictions. Constructing an actual collision requires careful crafting of path names/commit IDs so the concatenated byte streams match, which is feasible but non-trivial — likelihood is moderate, consistent with the "Medium Risk" severity of the original report.

### Recommendation
Replace the ambiguous comma-joined concatenation with an unambiguous, length-prefixed encoding for each dynamic field before hashing — mirroring the existing `prefixLen` helper in `internal/cache/keyer.go` — e.g. write the byte-length of each field before its content, or hash each field independently and combine the digests, instead of joining variable-length strings with a separator that can itself appear inside the values.

### Proof of Concept
Conceptually: for the same repository/`GlProjectPath` and `args = ["<commitID>"]`, craft two path sets:
- `pathspecs = ["a,b"]` (a single validated relative path containing a literal comma)
- `pathspecs = ["a", "b"]` (two separate exclude entries "a" and "b")

Both serialize to `"a,b"` after `strings.Join(pathspecs, ",")`, and combined with identical `gitLabProjectPath`/`args`, produce the exact same SHA-256 input and therefore the same cache key in `createArchiveCacheKey`, letting a `GetArchive` request for one path/exclude combination be served the cached archive generated for the other.

// prefixLen reduces the risk of collisions due to different combinations of
// concatenated strings producing the same content.
// e.g. f+oobar and foo+bar concatenate to the same thing: foobar
func prefixLen(s string) []byte {
	return []byte(fmt.Sprintf("%08x%s", len(s), s))
}
