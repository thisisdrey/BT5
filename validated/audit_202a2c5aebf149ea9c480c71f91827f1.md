### Title
Position-wide `last-borrow-block` in vault `registry` lets an attacker "dust-borrow" one cheap debt asset to block liquidation of all debt assets in the same position - (`File: mainnet/contracts/market/v0-4-market.clar` / `mainnet/contracts/market/v0-market-vault.clar`)

### Summary
`last-borrow-block` is stored once per position `id` in the vault's `registry` map, not per debt asset. Since `liquidate` compares this single position-level timestamp against `stacks-block-height` regardless of which `debt-ft` is targeted, an attacker with multiple debt assets can dust-borrow the cheapest asset every block to reset `last-borrow-block` and block liquidation of a completely different, far more valuable debt asset on the same position.

### Finding Description
The vault registry stores a single `last-borrow-block` field per position, updated on every `debt-add-scaled` call regardless of `asset-id`: [1](#0-0) 

`liquidate` reads this same position-level field (via `get-liquidation-position`) and enforces the same-block check independent of `debt-ft`/`debt-aid`: [2](#0-1) 

Because the check is `(is-eq last-borrow-block stacks-block-height)` at the position granularity rather than per-`(id, asset)` pair, any `debt-add-scaled` call for *any* asset on the position — including a `u1` (or otherwise economically negligible) borrow of an unrelated, cheap asset — updates `last-borrow-block` to the current block. This means that for a position holding debt in both a cheap asset (e.g., USDC) and an expensive one (e.g., sBTC), the attacker can call `borrow` for `u1` of USDC each block. This resets `last-borrow-block` to the current height, and any attempt in that same block to `liquidate` the sBTC debt-aid on the same borrower fails with `ERR-LIQUIDATION-BORROW-SAME-BLOCK`, even though sBTC debt was never touched.

The comment at line 1428-1430 states the intent is to block flash-loan-based same-block borrow-then-liquidate attacks, but the implementation keys the protection off the whole position rather than the specific debt asset/aid being liquidated, so it also blocks liquidation of debt assets that were not borrowed this block. Repeating this every block (bot-automatable, since `stacks-block-height` advances roughly every block) keeps the position permanently un-liquidatable for its expensive debt asset while the cost to the attacker is just the gas/dust cost of a `u1` borrow of the cheapest tracked asset.

### Impact Explanation
This is protocol insolvency (Critical): a position that should be liquidatable (LTV above `ltv-liq-partial`) can be perpetually shielded from liquidation for its high-value debt asset for the cost of a `u1` borrow of the cheapest asset each block. If the underlying collateral price continues to move against the position (or interest continues to accrue), the protocol accumulates bad debt that can never be seized via `liquidate`, directly threatening solvency of the lending pool that backs zTokens/vault shares.

### Likelihood Explanation
Preconditions are minimal and attacker-controlled: the attacker only needs to already hold debt positions in at least two assets, which is a normal outcome of ordinary borrowing (no privileged role required). The repeated cost is a `u1` (or minimal) borrow of the cheapest supported asset (e.g., stablecoin) executed once per block — cheap, fully automatable, and requires no oracle manipulation, flashloan, or governance action. This is realistically repeatable indefinitely as long as the attacker is willing to pay the trivial per-block dust-borrow cost and transaction fees, making the attack highly feasible for any borrower who anticipates becoming liquidatable.

### Recommendation
Track `last-borrow-block` per `(position id, asset)` pair (mirroring the `debt` map keying) instead of a single position-wide field, and have `liquidate` check the borrow-freshness only for the specific `debt-aid` being liquidated (and/or the specific `coll-aid` involved), not the entire position. Alternatively, track the last-borrow-block per asset within the position struct and derive the same-block check via `(map-get? debt-last-borrow-block {id: id, asset: debt-aid})`.

### Proof of Concept
Clarinet/vitest simnet plan (local fork):
1. Deploy market + vault + two debt-enabled assets (USDC, sBTC) with a price oracle mock allowing controlled prices.
2. Attacker deposits collateral sufficient to borrow both USDC and sBTC; borrow a large amount of sBTC (or manipulate price feed downward for sBTC-collateral-backed debt) so LTV crosses `ltv-liq-partial` for the sBTC debt.
3. In block N: attacker calls `borrow` for `u1` USDC (`debt-add-scaled` with `asset-id = USDC`, `scaled-amount = u1`). Assert registry entry's `last-borrow-block == block-height(N)`.
4. In the same block N: liquidator calls `liquidate(borrower, collateral-ft, sbtc-debt-ft, debt-amount, ...)`. Assert the call reverts with `ERR-LIQUIDATION-BORROW-SAME-BLOCK`, even though sBTC debt was never borrowed this block — demonstrating the whole position (not just USDC debt) is shielded.
5. Advance to block N+1, repeat step 3 (dust-borrow `u1` USDC again) before any liquidation attempt; assert `liquidate` on sBTC debt again reverts with the same error, showing indefinite blocking as long as the attacker keeps dust-borrowing each block.
6. Control test: without the dust-borrow in a given block, confirm `liquidate` on sBTC succeeds (health check passes, LTV above threshold), proving the same-block check — not health/LTV — is what blocks liquidation.
