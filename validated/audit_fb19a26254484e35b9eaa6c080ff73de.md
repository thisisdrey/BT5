### Title
Missing overall timeout on user-controlled HTTP snapshot download enables handler DoS via slow-body response - ([File: internal/gitaly/service/repository/create_repository_from_snapshot.go])

### Summary
`CreateRepositoryFromSnapshot` downloads a repository snapshot from an attacker-influenced URL (`in.GetHttpUrl()`) and streams the HTTP response body directly into `tar` for extraction. The HTTP client used for this request has no overall request timeout — only sub-timeouts for TLS handshake, response headers, and idle-connection reuse — so a slow-responding remote endpoint can keep the request open indefinitely, hanging the RPC handler and its associated goroutine/connection/repository-creation lock, exactly mirroring the reported "missing timeout on downloadS3Data" bug class (unbounded external I/O invoked without an enforced deadline).

### Finding Description
The RPC handler `CreateRepositoryFromSnapshot` calls `s.untar`, which builds an HTTP request from the client-supplied `HttpUrl` field and executes it with a client built from `httpTransport`: [1](#0-0) 

This transport only bounds `DialContext`, `TLSHandshakeTimeout`, `ExpectContinueTimeout`, `ResponseHeaderTimeout`, and `IdleConnTimeout` — none of which bound the time spent reading the response *body*. The actual request/response flow is: [2](#0-1) 

`req` is created via `http.NewRequestWithContext(ctx, ...)`, so the *only* thing that can abort a stalled body read is the incoming gRPC context's deadline — a deadline that is entirely under the caller's control and not enforced anywhere in this code path (no `context.WithTimeout` is applied locally, unlike other network-facing RPCs such as `FetchRemote`, which explicitly does `ctx, cancel = context.WithTimeout(ctx, time.Duration(req.GetTimeout())*time.Second)`): [3](#0-2) 

Because `ResponseHeaderTimeout` fires only once (before headers arrive) and `IdleConnTimeout` only applies to idle pooled connections, an attacker-controlled server pointed to by `HttpUrl` can send response headers immediately and then trickle the body arbitrarily slowly (or stop sending entirely while keeping the TCP connection alive), keeping `client.Do(req)` and the subsequent `cmd.Wait()` on the `tar` process blocked for as long as the RPC's own context permits.

### Impact Explanation
The RPC handler, the repository-creation lock taken by `repoutil.Create`, and the spawned `tar` subprocess are held open for the duration of the stall. Because there is no local upper bound, and no evidence that the gRPC server enforces a hard per-RPC deadline independent of what the caller sets, this can be used to tie up Gitaly worker resources (goroutines, sockets, the in-flight repository-creation slot) far longer than intended, degrading availability for other repository-creation operations targeting the same or other repositories on the node. This matches the report's core concern: unbounded external I/O in a critical path without a defensive timeout, causing indefinite blocking of the operation.

### Likelihood Explanation
`CreateRepositoryFromSnapshot` takes `HttpUrl`, `HttpAuth`, and optionally `ResolvedAddress` directly from the RPC request, i.e., from an ordinary caller with access to the RPC (e.g., via Rails/gitlab-shell import/fork flows that expose repository creation from a URL). No additional privilege beyond invoking this RPC is required to point `HttpUrl` at a server the attacker controls (or a compromised/slow legitimate host) and simply respond slowly.

### Recommendation
Apply a bounded, explicit timeout for the snapshot download independent of the caller-supplied gRPC deadline, e.g. wrap the download in `context.WithTimeout(ctx, someMaxDuration)` before calling `http.NewRequestWithContext`/`client.Do`, and/or set `http.Client.Timeout` on `httpClient`/`newResolvedHTTPClient` to bound total request duration (headers + body). Additionally, consider limiting the size/duration of body reads (e.g., via `io.LimitReader` combined with a deadline-based reader) so that slow-body responses cannot stall the `tar` extraction indefinitely.

### Proof of Concept
1. Stand up an HTTP server that accepts the connection, immediately returns `200 OK` with `Content-Length` unset (chunked), then writes a few bytes and stalls forever without closing the connection or sending more data.
2. Call `CreateRepositoryFromSnapshot` with `HttpUrl` pointing at this server and a repository target, using a gRPC client that does not set an aggressive deadline (or uses the default/long timeout used by internal callers).
3. Observe that the RPC, its `tar` subprocess, and the repository-creation lock remain held for the full duration the malicious server chooses to stall, since `ResponseHeaderTimeout`/`IdleConnTimeout` never trigger (headers were already sent, connection is not idle) and no other timeout is applied.

// than for http.DefaultTransport.

// They define shorter TLS Handshake, and more aggressive connection closing

func (s *server) untar(ctx context.Context, path string, in *gitalypb.CreateRepositoryFromSnapshotRequest) error {
	req, err := http.NewRequestWithContext(ctx, "GET", in.GetHttpUrl(), nil)
	if err != nil {
		return structerr.NewInvalidArgument("Bad HTTP URL: %w", err)
	}

	client := httpClient
	if resolvedAddress := in.GetResolvedAddress(); resolvedAddress != "" {
		client, err = newResolvedHTTPClient(in.GetHttpUrl(), resolvedAddress)
		if err != nil {
			return structerr.NewInvalidArgument("creating resolved HTTP client: %w", err)
		}
	}

	if in.GetHttpAuth() != "" {
		req.Header.Set("Authorization", in.GetHttpAuth())
	}

	rsp, err := client.Do(req)
	if err != nil {
		return structerr.NewInternal("HTTP request failed: %w", err)
	}
	defer rsp.Body.Close()

	if rsp.StatusCode < http.StatusOK || rsp.StatusCode >= http.StatusMultipleChoices {
		return structerr.NewInternal("HTTP server: %s", rsp.Status)
	}

	cmd, err := command.New(ctx, s.logger, []string{"tar", "-C", path, "-xvf", "-"}, command.WithStdin(rsp.Body))
	if err != nil {
		return err
	}

	return cmd.Wait()
}
