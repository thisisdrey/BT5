### Title
Unbounded `DelegatedResourceAccountIndex` growth via `DelegateResourceContract` enables permanent HTTP/gRPC/JSON-RPC DoS of a victim's delegation-index query and can bloat wallet-facing responses without any resource cost limit - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
`DelegateResourceActuator`/`DelegateResourceProcessor` allow any account to delegate as little as 1 TRX of bandwidth or energy to an arbitrary `receiverAddress` chosen by the caller, with no relationship or opt-in required from the receiver. Each such delegation writes a new key under the receiver's `V2_TO_PREFIX` index space in `DelegatedResourceAccountIndexStore`. The receiver's list is not stored as a bounded array but reconstructed on read by `getV2Index()` via an unbounded `prefixQuery` scan over the account's key prefix. A malicious actor can send many cheap `DelegateResourceContract` transactions (1 TRX minimum each) targeting the same victim address with distinct owner addresses, causing the victim's `fromAccounts`/`toAccounts` index list to grow without bound.

### Finding Description
`DelegateResourceActuator.validate()`/`execute()` only requires `delegateBalance >= TRX_PRECISION` (1 TRX) and that `receiverAddress != ownerAddress` and the receiver is not a contract account — there is no cap on how many distinct delegators can target the same receiver, and no opt-in/consent check from the receiver: [1](#0-0) [2](#0-1) 

Each execution calls `delegateResource()`, which persists a new index entry via `DelegatedResourceAccountIndexStore.delegateV2()`: [3](#0-2) 

`delegateV2()` writes one DB record per (from, to) pair under the `V2_FROM_PREFIX`/`V2_TO_PREFIX` key spaces — there is no limit on the number of distinct keys that can accumulate for a single receiver address: [4](#0-3) 

When the index is read (e.g. via the wallet API), `getV2Index()`/`getWithPrefix()` performs an unbounded `prefixQuery` across all keys with that address prefix, sorts them, and materializes the full list into a single `DelegatedResourceAccountIndexCapsule`: [5](#0-4) 

This capsule is exposed directly through the public HTTP endpoint `GetDelegatedResourceAccountIndexV2Servlet`, which calls `wallet.getDelegatedResourceAccountIndexV2(address)` with no pagination or size limit and serializes the entire result to JSON/protobuf for the response: [6](#0-5) 

The same underlying `getDelegatedResourceAccountIndexV2` call is also reachable through the gRPC (`RpcApiService`) and Solidity/PBFT HTTP/gRPC query paths, all of which reuse `Wallet`'s unbounded lookup.

Because an attacker can generate any number of throwaway funded accounts and issue cheap `DelegateResourceContract` transactions (only 1 TRX delegated balance required per transaction, no relation to the receiver needed), the receiver's index list can be inflated arbitrarily (thousands to tens of thousands of entries), analogous to the reported `MFDBase.userLocks` flooding bug where an unbounded per-user array is grown by an unrelated third party via a "stake/delegate on behalf of" style primitive.

### Impact Explanation
Once a victim's `DelegatedResourceAccountIndex` prefix range holds a very large number of entries, every query to `getDelegatedResourceAccountIndexV2` for that address (HTTP `/wallet/getdelegatedresourceaccountindexv2`, `wallet/solidity`, PBFT variants, and gRPC) must scan and sort the full prefix range and serialize the entire result, consuming disproportionate CPU/DB I/O and producing arbitrarily large responses on each request. This can degrade or effectively deny the node's ability to serve that specific wallet query for the targeted address (and place sustained load on the underlying LevelDB/RocksDB prefix scan), which matches the ruleset's accepted impact of "an API the node can no longer serve." It does not directly cause theft or fund freezing since the underlying `DelegatedResourceCapsule` balances remain independently addressable and un-delegatable per pair, but it is a concrete resource-exhaustion/API-availability issue triggered entirely by unprivileged, low-cost transactions.

### Likelihood Explanation
Likelihood is high: delegating resources to an arbitrary receiver requires only a funded account with as little as 1 TRX of frozen V2 balance available for delegation, no cooperation from the victim, and no rate limiting beyond normal bandwidth/energy costs of submitting transactions. An attacker can automate creation of many owner accounts (or reuse the delegatable balance across repeated small delegations) to flood a single receiver's index over time.

### Recommendation
- Add an upper bound on the number of `DelegatedResourceAccountIndex` entries that can be created for a single receiver (and/or owner) in `DelegateResourceActuator.validate()` / `DelegateResourceProcessor.validate()`, rejecting new delegations to (or list growth for) an address once a maximum is reached.
- Alternatively, require the receiver's consent (or restrict unsolicited delegation) or enforce a minimum delegated balance well above 1 TRX to raise the cost of flooding.
- Add pagination/limits to `DelegatedResourceAccountIndexStore.getWithPrefix()` and the corresponding HTTP/gRPC servlets so that queries against attacker-inflated index lists cannot force unbounded scans/serialization in a single request.

### Proof of Concept
1. Create N distinct funded accounts `A_1..A_N`, each freezing at least 1 TRX (`TRX_PRECISION`) worth of bandwidth or energy V2 balance.
2. From each `A_i`, submit a `DelegateResourceContract` transaction with `receiverAddress = Victim`, `resource = BANDWIDTH`, `balance = 1_000_000` (1 TRX), `lock = false`. This passes `DelegateResourceActuator.validate()` (balance ≥ 1 TRX, receiver ≠ owner, receiver exists and is non-contract) and executes successfully, adding one entry to `Victim`'s `V2_TO_PREFIX` index via `delegateV2()`.
3. Repeat for N in the thousands (cost scales linearly and cheaply with N, no cap enforced).
4. Query `http://<node>/wallet/getdelegatedresourceaccountindexv2?address=<Victim>` (or the gRPC/Solidity/PBFT equivalents). `getWithPrefix()` performs a `prefixQuery` over all N entries, sorts them, and returns the full list in a single response — demonstrating the unbounded read amplification and DoS surface caused entirely by the attacker's low-cost `DelegateResourceContract` transactions targeting an unwilling `Victim`.

  private void delegateResource(byte[] ownerAddress, byte[] receiverAddress, boolean isBandwidth,
                                long balance, boolean lock, long lockPeriod) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicPropertiesStore = chainBaseManager.getDynamicPropertiesStore();
    DelegatedResourceStore delegatedResourceStore = chainBaseManager.getDelegatedResourceStore();
    DelegatedResourceAccountIndexStore delegatedResourceAccountIndexStore = chainBaseManager
        .getDelegatedResourceAccountIndexStore();

    // 1. unlock the expired delegate resource
    long now = chainBaseManager.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    delegatedResourceStore.unLockExpireResource(ownerAddress, receiverAddress, now);

    //modify DelegatedResourceStore
    long expireTime = 0;
    if (lock) {
      expireTime = now + lockPeriod * BLOCK_PRODUCED_INTERVAL;
    }
    byte[] key = DelegatedResourceCapsule.createDbKeyV2(ownerAddress, receiverAddress, lock);
    DelegatedResourceCapsule delegatedResourceCapsule = delegatedResourceStore.get(key);
    if (delegatedResourceCapsule == null) {
      delegatedResourceCapsule = new DelegatedResourceCapsule(ByteString.copyFrom(ownerAddress),
          ByteString.copyFrom(receiverAddress));
    }

    if (isBandwidth) {
      delegatedResourceCapsule.addFrozenBalanceForBandwidth(balance, expireTime);
    } else {
      delegatedResourceCapsule.addFrozenBalanceForEnergy(balance, expireTime);
    }
    delegatedResourceStore.put(key, delegatedResourceCapsule);

    //modify DelegatedResourceAccountIndexStore
    delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress,
        dynamicPropertiesStore.getLatestBlockHeaderTimestamp());

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
