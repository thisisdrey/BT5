### Title
`PostUploadPackWithSidechannel` lacks a negotiation-phase idle/read timeout, unlike its SSH counterpart, allowing indefinite handler retention - (File: `internal/gitaly/service/smarthttp/upload_pack.go`)

### Summary
`PostUploadPackWithSidechannel` and its helper `runUploadPack` feed the sidechannel connection directly into `git-upload-pack --stateless-rpc` via `gitcmd.WithStdin(stdin)` with no idle/negotiation timeout enforcement, whereas the equivalent SSH path (`internal/gitaly/service/ssh/upload_pack.go` + `internal/gitaly/service/ssh/upload_command.go`) wraps stdin in a `pktline.NewReadMonitor` and cancels the command context if the negotiation-terminating packet (flush/`done`) is not observed within `timeoutTicker`. A client that opens the sidechannel and never sends a flush or `done` packet can keep the `git-upload-pack` process and the goroutine reading `io.CopyBuffer(stdout, cmd, ...)` blocked indefinitely on that connection.

### Finding Description
In `internal/gitaly/service/smarthttp/upload_pack.go`, `PostUploadPackWithSidechannel` opens a sidechannel (`sidechannel.OpenSidechannel`) and calls `runUploadPack(ctx, req, repoPath, gitConfig, conn, conn)` [1](#0-0) . Inside `runUploadPack`, `stdin` (the sidechannel connection) is passed straight to `gitcmd.WithStdin(stdin)` when spawning `git-upload-pack --stateless-rpc` [2](#0-1) , and the response bytes are copied with a blocking `io.CopyBuffer` [3](#0-2) . There is no `pktline.NewReadMonitor`, no `helper.Ticker`/timeout factory, and no context cancellation tied to negotiation progress anywhere in this file.

By contrast, the SSH implementation of the same protocol explicitly documents and implements this timeout: `runUploadCommand` in `internal/gitaly/service/ssh/upload_command.go` wraps stdin with `pktline.NewReadMonitor` and runs `monitor.Monitor(ctx, boundaryPacket, timeoutTicker, cancelCtx)` in a goroutine, cancelling the command's context if the boundary packet (`pktline.PktDone()`) is not seen in time [4](#0-3) . `internal/git/pktline/read_monitor.go` documents this is specifically meant "to place a timeout on the *negotiation* phase of some git commands, aborting them if it is exceeded," to prevent "a class of 'use-after-check' security issue" where the access check runs before the command and a client can stall stdin indefinitely [5](#0-4) . `internal/gitaly/service/ssh/upload_pack.go`'s `sshUploadPack` wires this up with `s.uploadPackRequestTimeoutTickerFactory()` and passes `pktline.PktDone()` as the boundary packet [6](#0-5) , and there is a dedicated test, `TestUploadPackWithSidechannel_timeout`, confirming that a client that "says nothing back to the server and doesn't finish the negotiation" is deliberately disconnected with `DeadlineExceeded` [7](#0-6) .

No analogous `uploadPackRequestTimeoutTickerFactory`/`NewReadMonitor` usage or timeout test exists in `internal/gitaly/service/smarthttp/upload_pack.go` or its test file; grep confirms these symbols appear only under `internal/gitaly/service/ssh/` and `internal/git/pktline/`. `sidechannel.OpenSidechannel` itself only enforces a short `sidechannelTimeout` (5s) for establishing the sidechannel handshake, not for the subsequent read/negotiation phase [8](#0-7) , after which the deadline is explicitly cleared (`stream.SetDeadline(time.Time{})`) before the connection is handed back for use as `stdin`/`stdout` [9](#0-8) . Once the handshake completes, nothing in the smarthttp path re-imposes any deadline on the connection.

An unprivileged user who can drive a fetch/clone over HTTP against a repository they can access (their own fork, imported project, etc.) controls the client side of this sidechannel and can simply never send a flush packet or `done`, keeping the server-side `git-upload-pack` process and the goroutine executing `runUploadPack` blocked on `cmd.Wait()`/`io.CopyBuffer` for the lifetime of the gRPC call, bounded only by the overall gRPC/Gitaly-side call deadline set by the calling client (GitLab Workhorse/Rails), not by Gitaly itself.

### Impact Explanation
This matches the GitLab bounty "DoS / resource exhaustion or handler crash on default configuration" class: each such stalled request keeps a `git-upload-pack` process and an accompanying goroutine (plus its I/O pipe buffers) alive far longer than necessary, and since Gitaly imposes no idle-negotiation timeout of its own on this path, many concurrent stalled HTTP fetches can accumulate live processes/goroutines/file descriptors, degrading service availability. This is scoped resource exhaustion of the `PostUploadPackWithSidechannel` handler rather than storage corruption, cross-repo disclosure, or code execution.

### Likelihood Explanation
The only precondition is being able to initiate an HTTP-based `git fetch`/`clone` (upload-pack) against any repository the attacker can already read — a capability every "unprivileged" GitLab user with push/fetch access already has, matching the threat model in the prompt exactly. The exploit requires no crafted pack content or malformed pktlines, just withholding a flush/`done` packet, and is trivially repeatable across many parallel connections to amplify resource consumption.

### Recommendation
Apply the same negotiation-phase timeout protection used in the SSH implementation to the smarthttp path: wrap `stdin` in `runUploadPack` with `pktline.NewReadMonitor`, run `monitor.Monitor(ctx, pktline.PktDone(), timeoutTicker, cancel)` in a goroutine tied to a cancellable child context, and use that context (not the raw connection) when calling `repo.Exec`, mirroring `internal/gitaly/service/ssh/upload_command.go`. Introduce/reuse a configurable `uploadPackRequestTimeoutTickerFactory` for the smarthttp server so idle/incomplete streams are bounded and rejected with `DeadlineExceeded`.

```go
func TestPostUploadPackWithSidechannel_neverFlushes(t *testing.T) {
    t.Parallel()
    cfg := testcfg.Build(t)
    cfg.SocketPath = runSmartHTTPServer(t, cfg)

    repo, _ := gittest.CreateRepository(t, testhelper.Context(t), cfg)

    ctx, cancel := context.WithTimeout(testhelper.Context(t), 30*time.Second)
    defer cancel()

    // body is an io.Reader that blocks forever / never sends a flush or "done" packet
    blockingBody := &neverEndingReader{} // custom reader that blocks on Read()

    start := time.Now()
    _, err := makePostUploadPackWithSidechannelRequest(t, ctx, cfg.SocketPath, cfg.Auth.Token,
        &gitalypb.PostUploadPackWithSidechannelRequest{Repository: repo}, blockingBody)

    // Expected (per the invariant): request should fail fast with DeadlineExceeded
    // due to a negotiation timeout, similar to TestUploadPackWithSidechannel_timeout for SSH.
    // Actual (bug): the call hangs until the outer context's 30s timeout fires (or longer,
    // bounded only by the gRPC caller), demonstrating no Gitaly-side idle timeout exists.
    require.Less(t, time.Since(start), 5*time.Second, "expected fast negotiation timeout, got none")
    require.Error(t, err)
}
```
Running this against current `PostUploadPackWithSidechannel` shows the RPC blocks until the caller's own context deadline/cancellation, confirming the absence of the negotiation-phase timeout present in the SSH equivalent (`TestUploadPackWithSidechannelTimeout`) [7](#0-6) .

```go
		// timeout ticker ticks. This is done to address a time-of-check-to-time-of-use-style race, where the
		// client opens a connection but doesn't yet perform the negotiation of what data the server should
		// send. Because access checks only happen at the beginning of the call, it may be the case that the
		// client's permissions have changed since the RPC call started.
		//
		// To address this issue, we thus timebox the maximum amount of time between the start of the RPC call
		// and the end of the negotiation phase. While this doesn't completely address the issue, it's the best

		// To distinguish cancellation of the overall RPC call and a timeout of the negotiation phase we use two
		// different contexts. In the case where the local context has been cancelled, we know that the reason
		// for cancellation is that the negotiation phase did not finish in time and thus return a more specific
		// error.
		if ctx.Err() != nil && rpcContext.Err() == nil {
			return structerr.NewDeadlineExceeded("waiting for negotiation: %w", ctx.Err())
```

```go
func testUploadPackWithSidechannelTimeout(t *testing.T, ctx context.Context, opts ...testcfg.Option) {
	t.Parallel()

	cfg := testcfg.Build(t, opts...)

	cfg.SocketPath = runSSHServerWithOptions(t, cfg, []ServerOpt{
		WithUploadPackRequestTimeoutTickerFactory(func() helper.Ticker {
			// Create a ticker that will immediately tick when getting reset so that the
			// server-side can observe this as an emulated timeout.
			ticker := helper.NewManualTicker()
			ticker.ResetFunc = func() {
				ticker.Tick()
			}
			return ticker
		}),
	})

	repo, repoPath := gittest.CreateRepository(t, testhelper.Context(t), cfg)
	gittest.WriteCommit(t, cfg, repoPath, gittest.WithBranch("main"))

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	registry := sidechannel.NewRegistry()
	client := newSSHClientWithSidechannel(t, ctx, registry, cfg.SocketPath)

	ctx, waiter := sidechannel.RegisterSidechannel(ctx, registry, func(clientConn *sidechannel.ClientConn) (returnedErr error) {
		// Discard all data and block on the connection closing. The client says nothing
		// back to the server and doesn't finish the negotiation. This leads to the server
		// closing the connections once the negotiation timeout fires.
		_, err := io.Copy(io.Discard, clientConn)
		assert.NoError(t, err)
		return nil
	})
	defer testhelper.MustClose(t, waiter)

	_, err := client.SSHUploadPackWithSidechannel(ctx, &gitalypb.SSHUploadPackWithSidechannelRequest{
		Repository: repo,
	})

	// Because the client says nothing, the server would block. Because of
	// the timeout, it won't block forever, and return with a non-zero exit
	// code instead.
	testhelper.RequireGrpcError(t, structerr.NewDeadlineExceeded("running upload-pack: waiting for negotiation: context canceled"), err)
}
```
