### Title
HTTP request/response smuggling via non-RFC-compliant `Content-Length` parsing (`+`-prefixed values accepted) - ([File: stackslib/src/net/http/request.rs])

### Summary
The Stacks node's HTTP preamble parsers for both requests and responses validate the `Content-Length` header using Rust's generic `str::parse::<u32>()`, rather than a strict `1*DIGIT` grammar as required by RFC 7230 §3.3.2. Rust's integer `FromStr` implementation accepts an optional leading `+` sign even for unsigned types, so a header like `Content-Length: +123` is accepted and parsed as `123`. This is the same bug class as GHSA-qppv-j76h-2rpx (Tornado): a length-framing field accepts non-standard characters (`+`) that strict HTTP intermediaries reject or interpret differently, creating a parser-disagreement condition that enables request smuggling when the node sits behind a reverse proxy/load balancer.

### Finding Description
`Content-Length` is parsed in the same permissive way in three places: [1](#0-0) [2](#0-1) [3](#0-2) 

In all three, `value.parse::<u32>()` is used directly on the raw header string. Rust's standard-library integer parsing (`u32::from_str` → `from_str_radix`) explicitly special-cases a leading `+` byte and strips it before parsing the remaining digits, for both signed *and* unsigned integer types. This means `"+123"`, and even `"+0"`, are accepted as valid `Content-Length` values by the Stacks node, even though RFC 7230's `Content-Length` production is `1*DIGIT` and forbids any sign character.

This parsed value is used directly to determine how many bytes constitute the HTTP body/frame: [4](#0-3) 
and to compute `payload_len()` for buffering: [5](#0-4) 

By contrast, the chunk-size parser used for `Transfer-Encoding: chunked` bodies is strict and only accepts hex digits (`0-9a-f`, case-insensitive) plus a well-defined extension syntax — it correctly rejects `+`, `-`, and `_`: [6](#0-5) 

So the vulnerable equality being broken is: "the byte-length the Stacks node believes was framed for this message" vs. "the byte-length any RFC-strict front-end (nginx/haproxy/envoy) believes was framed for the same message," when a `+`-prefixed `Content-Length` is forwarded unmodified by the proxy (many proxies pass through header values verbatim without revalidating the digit grammar) but is rejected/misinterpreted differently by another component in the chain. This is structurally identical to the Tornado advisory's `int()`-based `Content-Length`/chunk-length parsing bug, transplanted onto Rust's permissive `FromStr` for integers.

### Impact Explanation
If a Stacks node's `/v2/...` RPC HTTP endpoint is deployed behind a reverse proxy (a documented and common operational pattern for public API/RPC nodes, and necessary for privileged/auth-token-gated endpoints such as the block-proposal API), a discrepancy between how the proxy and the Stacks node frame the `+`-prefixed `Content-Length` body can desynchronize the TCP stream framing between the two parties. This is the classic precondition for HTTP request smuggling, which can be leveraged to:
- Bypass proxy-level access controls (IP allow-lists, auth headers stripped/added by the proxy) for privileged endpoints by smuggling a second, hidden request that the backend node interprets as a separate, proxy-authorized request.
- Poison the request queue for other clients sharing the proxy connection pool.

This matches the "Critical - ... request smuggling or auth bypass" impact category in the task's rubric, though it is a conditional/environment-dependent issue (requires a reverse-proxy deployment) rather than a standalone remote crash.

### Likelihood Explanation
Exploitability depends entirely on deployment topology: a standalone Stacks node accepting direct TCP connections is not exposed to this issue by itself (no second parser is in the path to disagree with). The issue becomes live only when a reverse proxy or other HTTP intermediary sits in front of the node and forwards headers without revalidating the `Content-Length` grammar strictly (mirroring the original Tornado advisory's caveat that it requires specific proxy behavior, e.g., older haproxy). Given RPC nodes are commonly proxied for TLS/rate-limiting, likelihood is non-negligible but conditional, matching the "Medium" severity of the source advisory.

### Recommendation
Replace `value.parse::<u32>()` for `Content-Length` in `stackslib/src/net/http/request.rs`, `stackslib/src/net/http/response.rs`, and `stackslib/src/net/http/common.rs` with a strict validator that rejects any non-`0-9` byte (e.g., check `value.bytes().all(|b| b.is_ascii_digit())` before calling `parse`), matching RFC 7230's `1*DIGIT` grammar. Apply the same tightening to any other integer header parsing that reuses `str::parse` on attacker-controlled header values.

### Proof of Concept
Send either of the following to a Stacks node RPC endpoint (or exercise `HttpRequestPreamble::consensus_deserialize` / `HttpResponsePreamble::consensus_deserialize` directly in a unit test) and observe the header is accepted rather than rejected:
```
POST /v2/transactions HTTP/1.1
Host: node:20443
Content-Length: +11
Content-Type: application/octet-stream

<11-byte body>
```
`value.parse::<u32>()` returns `Ok(11)` for `"+11"`, so the request is framed with an 11-byte body just as `"11"` would be — despite `+11` being invalid per RFC 7230. A strict-grammar front-end proxy that either rejects this header outright, or that itself reframes based on a stricter interpretation, will disagree with the node about where this request ends, which is the framing-mismatch precondition for smuggling. This can be confirmed directly against `stackslib/src/net/http/tests.rs`-style unit tests (e.g. extending `test_parse_reserved_header`/`test_parse_http_response_preamble_ok` with a `"+123"` case) since existing tests only check `"-1"`, `"asdf"`, and overflow, but never a leading-`+` value: [7](#0-6)

pub fn parse_chunk_size(buf: &[u8]) -> result::Result<Status<(usize, u64)>, Error> {
    const RADIX: u64 = 16;
    let mut bytes = Bytes::new(buf);
    let mut size = 0u64;
    let mut in_chunk_size = true;
    let mut in_ext = false;
    let mut count = 0;
    loop {
        let b = next!(bytes);
        match b {
            b'0'..=b'9' if in_chunk_size => {
                if count > 15 {
                    return Err(Error::ChunkSize);
                }
                count += 1;
                size = size.checked_mul(RADIX).ok_or(Error::ChunkSize)?;
                size = size
                    .checked_add((b - b'0') as u64)
                    .ok_or(Error::ChunkSize)?;
            }
            b'a'..=b'f' if in_chunk_size => {
                if count > 15 {
                    return Err(Error::ChunkSize);
                }
                count += 1;
                size = size.checked_mul(RADIX).ok_or(Error::ChunkSize)?;
                size = size
                    .checked_add((b + 10 - b'a') as u64)
                    .ok_or(Error::ChunkSize)?;
            }
            b'A'..=b'F' if in_chunk_size => {
                if count > 15 {
                    return Err(Error::ChunkSize);
                }
                count += 1;
                size = size.checked_mul(RADIX).ok_or(Error::ChunkSize)?;
                size = size
                    .checked_add((b + 10 - b'A') as u64)
                    .ok_or(Error::ChunkSize)?;
            }
            b'\r' => match next!(bytes) {
                b'\n' => break,
                _ => return Err(Error::ChunkSize),
            },
            // If we weren't in the extension yet, the ";" signals its start
            b';' if !in_ext => {
                in_ext = true;
                in_chunk_size = false;
            }
            // "Linear white space" is ignored between the chunk size and the
            // extension separator token (";") due to the "implied *LWS rule".
            b'\t' | b' ' if !in_ext & !in_chunk_size => {}
            // LWS can follow the chunk size, but no more digits can come
            b'\t' | b' ' if in_chunk_size => in_chunk_size = false,
            // We allow any arbitrary octet once we are in the extension, since
            // they all get ignored anyway. According to the HTTP spec, valid
            // extensions would have a more strict syntax:
            //     (token ["=" (token | quoted-string)])
            // but we gain nothing by rejecting an otherwise valid chunk size.
            _ if in_ext => {}
            // Finally, if we aren't in the extension and we're reading any
            // other octet, the chunk size line is invalid!
            _ => return Err(Error::ChunkSize),
        }
    }
    Ok(Status::Complete((bytes.pos(), size)))
}
