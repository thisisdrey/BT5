### Title
Unvalidated field offsets in `VerifyTransferProof.execute()` allow out-of-bounds array access during shielded-transfer proof parsing - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.VerifyTransferProof.execute(byte[] data)` only validates the *total* length of the precompile input against a fixed set of allowed sizes before parsing variable-length sub-fields at attacker-controlled offsets, mirroring the CVE-2026-31393 pattern of checking an outer/header length but not validating the length actually needed to safely read a nested variable-size payload before indexing into it.

### Finding Description
The method first checks `data.length` against a fixed set `{2080, 2368, 2464, 2752}` [1](#0-0) . It then reads three offset fields directly from attacker-supplied `data` — `spendOffset`, `spendAuthSigOffset`, `receiveOffset` — via `parseInt(data, 0/32/64)` with no bound checking against `data.length` [2](#0-1) . These offsets are subsequently used, after adding 32, to index directly into `data` with `System.arraycopy` calls whose start position is `spendOffset + 320*i + {0,32,64,96,128}` (and similarly for `receiveOffset`/`spendAuthSigOffset`), for up to 2 iterations of `spendCount`/`receiveCount` (validated only against `[1,2]`, not against `data.length`) [3](#0-2) .

Because the fixed-size check only constrains the *total* data length (analogous to the L2CAP `cmd_len` covering just the header), but the actual read positions are derived from `spendOffset`/`receiveOffset`/`spendAuthSigOffset` values that are fully attacker-controlled and unconstrained relative to `data.length`, a crafted `data` blob matching one of the four allowed lengths but with out-of-range offset fields will cause `System.arraycopy` to be invoked with a source position beyond (or with insufficient remaining bytes in) the `data` array — exactly the "length field says X, but the actual buffer segment needed for the field isn't verified before access" defect described in the report.

### Impact Explanation
`System.arraycopy` with an out-of-range `srcPos`/length throws `ArrayIndexOutOfBoundsException`, which is not caught anywhere in `execute()` before its `try` block starts (the offsets are parsed and used for the arraycopy calls, and there is no surrounding try/catch visible around this parsing section) [4](#0-3) . An unhandled exception thrown out of a precompiled contract's `execute()` during TVM execution of a contract call can crash or destabilize transaction execution for any node processing that transaction (including validating full nodes replaying the block), which is a denial-of-service condition reachable by any account able to invoke this precompile via a smart contract call (shielded TRC20 contracts use this precompile for `verifyTransferProof`).

### Likelihood Explanation
Reachable from a single unprivileged, signed TVM contract call that supplies bytes matching one of the four accepted lengths but with crafted offset words — no special privileges, staking power, or SR/witness status required. However, I was not able to fully verify within the available context: (1) whether an encompassing exception handler exists further up the call stack in `PrecompiledContracts`/VM dispatch that would catch `ArrayIndexOutOfBoundsException` and gracefully fail the call instead of propagating further, and (2) the exact reachability path from calldata to this precompile address (I found references only in test files and could not confirm the address mapping/dispatch table entry within the tool budget). Given this uncertainty about whether an outer catch neutralizes the crash, and that I could not conclusively prove an unrecoverable node-level impact (vs. a contained REVERT), I cannot confidently elevate this to a Critical/High finding without further verification of the exception-handling and precompile-dispatch code paths.

### Recommendation
Add explicit bounds validation of `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` (and the derived per-item byte ranges for `spendCount`/`receiveCount` iterations) against `data.length` before any `parseInt`/`parseLong`/`System.arraycopy` call, returning `Pair.of(true, DataWord.ZERO().getData())` on any out-of-range value, consistent with the CVE-2026-31393 fix of validating payload length before subfield access.

### Proof of Concept
Construct a 2080-byte `data` array (matching `SIZE[0]`) where the first 32-byte word (`spendOffset`) is set to a large value (e.g., `data.length - 16`) instead of a valid offset within the buffer; call the `VerifyTransferProof` precompile from a smart contract with this calldata. The subsequent `spendOffset += 32` and `System.arraycopy(data, spendOffset + 320*i + ..., ...)` calls will compute a source index/length exceeding `data.length`, throwing `ArrayIndexOutOfBoundsException` during precompile execution.

*Note: I could not fully confirm within the tool budget whether an outer try/catch in the VM dispatch layer safely contains this exception; this should be verified before treating the impact as a confirmed node crash/halt rather than a contained call failure.*
