### Title
Replay-protection checkpoint (`lastHandshakeTime`) is bypassed when the local side is the initiator, allowing a captured stage-1 handshake to be replayed to poison/replace an established tunnel - (File: `handshake_manager.go`)

### Summary
`HostInfo.lastHandshakeTime` is nebula's monotonic "high-water-mark" analog: it is explicitly documented as existing "to avoid an attack where a handshake packet is replayed after some time" [1](#0-0) . `CheckAndComplete()` is supposed to compare the incoming handshake's timestamp against the existing tunnel's stored value and reject anything that is not newer. Like the reported `highWaterMark` bug, the guard that is meant to enforce "only accept a newer/higher value" is conditioned on an unrelated flag and is silently skipped in a reachable branch, letting a stale/replayed value through and corrupt existing state.

### Finding Description
In `CheckAndComplete`, the "is this a newer handshake" check is:

```go
// Is this a newer handshake?
if existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime && !existingHostInfo.ConnectionState.initiator {
    return existingHostInfo, ErrExistingHostInfo
}
``` [2](#0-1) 

The `>=` comparison is the exact monotonic-checkpoint check (mirrors the recommended `if shareValue > highWaterMark` pattern from the report), but it is gated by `!existingHostInfo.ConnectionState.initiator`. When the *existing* tunnel's local side is the initiator (`ConnectionState.initiator == true`), the entire time-ordering check is skipped, and the code falls straight through to `hm.mainHostMap.unlockedAddHostInfo(hostinfo, f)`, replacing the current, live tunnel with a new one built from the just-arrived handshake — regardless of whether `hostinfo.lastHandshakeTime` is older than what is already recorded.

`lastHandshakeTime` is taken directly from the peer-supplied `Payload.Time` field carried inside the handshake, and is set from `result.HandshakeTime` in `beginHandshake()` [3](#0-2)  and `continueHandshake()` [4](#0-3) . Because a stage-1 packet is a self-contained, previously-captured wire message, an attacker with no certificate of their own can simply record a legitimate stage-1 packet on the wire and replay it later — no CA-signed certificate is required from the attacker, only interception/replay of a packet that a legitimate peer sent at some point in the past.

The certificate-freshness check inside the handshake (`validateCert` → `CAPool.VerifyCertificate`) only verifies that the *embedded* certificate is not expired/blocklisted at replay time [5](#0-4) ; it does nothing to prevent reuse of an old, still-valid handshake message. The `lastHandshakeTime` check was added precisely to close that residual replay window, but the `!existingHostInfo.ConnectionState.initiator` condition reopens it whenever the local node happens to be the initiator side of its currently-established tunnel — exactly the same failure mode described in the report, where the "must only move forward" invariant on a checkpoint value is broken by an extra, unrelated condition guarding the update/reject path.

### Impact Explanation
When the guard is skipped, any old captured stage-1 handshake for a peer can be replayed to a node that currently holds an initiator-side tunnel to that peer. The manager will discard/tear down the existing hostinfo and complete a brand-new handshake in its place ("Taking new handshake" path) [6](#0-5) . This is a remote, unauthenticated (by the attacker) tunnel-state-poisoning / denial-of-service primitive: an attacker who has ever observed a single valid stage-1 packet from a peer can repeatedly force that peer's active session to be torn down and rebuilt at will, without needing any certificate of their own and without needing to break Noise's cryptography. This directly maps to the report's "monotonic checkpoint decreases instead of only increasing" bug class, replacing "charging extra fees" with "accepting a stale handshake and destroying live session state."

### Likelihood Explanation
Exploitability requires only passive capture of one legitimate stage-1 packet between the target and any peer whose certificate has not yet expired, plus the ability to replay UDP packets to the target (standard on-path/off-path UDP spoofing/replay, no CA trust needed). The condition (`local side is initiator of the existing tunnel`) is common in normal operation (whichever side happens to have originated the current handshake). This makes the bug straightforwardly reachable without any privileged position.

### Recommendation
Remove the `!existingHostInfo.ConnectionState.initiator` escape hatch from the freshness check, or restructure the guard so the monotonic ordering is enforced unconditionally:

```go
// Is this a newer handshake? Always enforce the ordering; do not special-case
// based on which side initiated the existing tunnel.
if existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime {
    return existingHostInfo, ErrExistingHostInfo
}
```
If there is a legitimate need to allow a fresh handshake attempt from an initiator-side tunnel, that case should be distinguished by cryptographic freshness (e.g., a nonce/ephemeral binding or a strictly-increasing per-session counter validated against Noise state) rather than by simply disabling the time-based anti-replay comparison.

### Proof of Concept
1. Node `A` establishes a tunnel to peer `B`, with `A` as the Noise initiator (`ConnectionState.initiator == true` on `A`'s existing `HostInfo`).
2. An attacker (no valid certificate required) captures a genuine stage-1 handshake UDP packet that `B` sent to `A` at some earlier point (e.g., during an earlier reconnection attempt, or if `B`'s previous cert is still within validity).
3. Attacker replays this captured stage-1 packet to `A` at any later time while `B`'s certificate embedded in that old packet is still unexpired.
4. `A`'s `HandleIncoming` routes it to `beginHandshake` → `CheckAndComplete`; since `A`'s existing `HostInfo.ConnectionState.initiator == true`, the `lastHandshakeTime` freshness check is bypassed, and `A` replaces its live tunnel to `B` with a new one derived from the replayed handshake, even though `hostinfo.lastHandshakeTime` (from the old packet) is older than the value already recorded.
5. Repeating this at will lets the attacker force repeated session teardown/rebuild on `A`, without ever presenting a certificate signed by the trusted CA.

func (m *Machine) validateCert(payload Payload) error {
	cred := m.getCred(m.myVersion)
	if cred == nil {
		m.failed = true
		return fmt.Errorf("%w: %v", ErrNoCredential, m.myVersion)
	}
	rc, err := cert.Recombine(
		cert.Version(payload.CertVersion),
		payload.Cert,
		m.hs.PeerStatic(),
		cred.Cert.Curve(),
	)
	if err != nil {
		m.failed = true
		return fmt.Errorf("recombine cert: %w", err)
	}

	if !bytes.Equal(rc.PublicKey(), m.hs.PeerStatic()) {
		m.failed = true
		return ErrPublicKeyMismatch
	}

	// Version negotiation, if the peer sent a different version and we have it, switch
	if rc.Version() != m.myVersion {
		if m.getCred(rc.Version()) != nil {
			m.myVersion = rc.Version()
		}
	}

	verified, err := m.verifier(rc)
	if err != nil {
		m.failed = true
		return fmt.Errorf("verify cert: %w", err)
	}

	m.result.RemoteCert = verified
	m.remoteCertSet = true
	return nil
