### Title
Unauthenticated `header.RecvError` packet with spoofed source address and guessed `RemoteIndex` triggers forced tunnel teardown - ([File: outside.go])

### Summary
`Interface.handleRecvError` (implemented in `outside.go`, not in `handshake/errors.go` as the question states) tears down a live tunnel and removes its `HostInfo` purely on receipt of an unauthenticated `header.RecvError` UDP packet whose `RemoteIndex` matches a live session and whose source address matches the hostinfo's current remote. There is no cryptographic proof (MAC/signature) tied to the session key required to accept this control packet.

### Finding Description
The dispatch path is: `readOutsidePackets` sees `h.Type == header.RecvError` and calls `f.handleRecvError(via.UdpAddr, h)` before any decryption or session-state validation [1](#0-0) . Inside `handleRecvError`, after an `acceptRecvErrorConfig.ShouldRecvError(addr)` gate, the code looks up the session purely by `h.RemoteIndex` via `f.hostMap.QueryReverseIndex(h.RemoteIndex)`, then checks only `hr.IsValid() && hr != addr` (i.e., the packet's UDP source address must equal the hostinfo's currently known remote) before calling `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` [2](#0-1) . `closeTunnel` unconditionally deletes the `HostInfo` from the main hostmap (and clears lighthouse state if it was the last tunnel to that vpn addr) [3](#0-2) . None of these steps involve verifying the AEAD/Noise session key, a MAC, or any replay-protected sequence number — the entire "authentication" is (a) an index lookup and (b) a source-IP/port equality check, both of which are attacker-controllable: UDP source addresses are trivially spoofable and `RemoteIndex` is a 32-bit value that, once known or guessed for a specific live session, is sufficient.

The code itself acknowledges the weak nature of this check via the log line `"Someone spoofing recv_errors?"`, confirming the address-equality check is treated as a heuristic, not a security boundary.

### Impact Explanation
A successful spoofed `RecvError` causes an authenticated session between two legitimate nebula nodes to be torn down without either party's cooperation — a remote, unauthenticated denial-of-service against an established tunnel. This matches the "remote state poisoning" / "forced session teardown" DoS impact category: the hostmap and handshake-manager pending state are mutated by unauthenticated network input, forcing a fresh handshake (and thus a fresh nonce/counter space) for reconnection. It does not lead to key/traffic compromise or authentication bypass beyond disruption.

### Likelihood Explanation
Exploitability is gated by two non-trivial preconditions: (1) the attacker must guess/observe a currently valid 32-bit `RemoteIndex` for the targeted tunnel (no rate-limited or entropy-reduced allocation is evident here, so blind brute force is a ~2^31-attempt-average, per-victim problem), and (2) the attacker must spoof the UDP source address/port to exactly match the victim's currently recorded remote endpoint for that hostinfo, which requires already knowing that endpoint (e.g. via traffic observation, a public lighthouse/listener address, or being on-path). Both the sender (`sendRecvErrorConfig`) and receiver (`acceptRecvErrorConfig`) sides have a `ShouldRecvError` gate that can restrict/rate-limit acceptance, but this is a heuristic/config-based mitigation, not cryptographic authentication, and does not eliminate the underlying design gap. Overall this is a real but comparatively low-probability-per-attempt DoS primitive, more practical against small/known-index deployments or in conjunction with traffic observation than as a generic mass-exploitable bug.

### Recommendation
Do not allow `RecvError` (or any control packet) to mutate hostmap/session state based solely on index lookup + source-address equality. Require the packet to include a value only derivable from the current session (e.g., a MAC over the current sending/receiving key, or piggyback the "error" signal onto an already-authenticated encrypted packet type) before invoking `closeTunnel`/`DeleteHostInfo`. At minimum, treat `RecvError` as advisory (e.g., trigger a re-handshake attempt rather than an immediate teardown of the confirmed session) and add strict per-source rate limiting independent of the existing `ShouldRecvError` heuristic.

### Proof of Concept
Unit test in `outside_test.go` (or new test file in package `nebula`):
1. Establish a `HostInfo` in `f.hostMap` with a known `localIndexId`/remote index and a `GetRemote()` value of `victimAddr`.
2. Craft a `header.H` with `Type = header.RecvError`, `RemoteIndex` equal to the victim hostinfo's index, no payload.
3. Call `f.handleRecvError(victimAddr, h)` directly (simulating a spoofed source `victimAddr`, i.e. without possessing any session key material).
4. Assert `f.hostMap.QueryReverseIndex(index)` returns `nil` afterward (tunnel torn down) and that `f.handshakeManager.QueryIndex`/pending state no longer references the hostinfo — demonstrating unauthenticated teardown.
5. Follow with a simulated legitimate re-handshake and inspect the new `ConnectionState` counters to confirm a fresh nonce space, illustrating the reconnection side-effect described in the question.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
