### Title
Unbounded response accumulation in `FindRefsByOID` can exhaust memory/CPU on a single RPC call - (File: internal/gitaly/service/ref/find_refs_by_oid.go)

### Summary
`FindRefsByOID` is a unary (non-streaming) accessor RPC that, unlike its sibling ref-listing RPCs (`ListRefs`, `FindAllTags`, `FindLocalBranches`), accumulates **all** matching reference names into a single in-memory Go slice and returns them in one gRPC response message, with no enforced upper bound when the caller supplies `limit = 0` (the default/unset value).

### Finding Description
`FindRefsByOID` builds its result set as follows: [1](#0-0) 

The `Limit` field is passed straight into `gitpipe.WithCount(int(in.GetLimit()))`, and `ForEachRef` only appends a `--count` flag to `git-for-each-ref` when `cfg.count > 0`: [2](#0-1) 

So when a client omits `Limit` (or sends `0`, which is the proto default for `uint32 limit`), the underlying `git-for-each-ref` process is run with no `--count` limit, and the handler's loop appends every matched ref name into the `refs` slice held entirely in memory before returning a single `FindRefsByOIDResponse`: [3](#0-2) 

This is architecturally different from the other ref-listing RPCs in the same package, which stream results in bounded chunks and support real pagination (`ListRefs` uses a streaming `RefService_ListRefsServer` with a `Chunker`/pagination cursor, and `FindAllTags`/`FindLocalBranches` likewise stream and paginate): [4](#0-3) [5](#0-4) 

Because `FindRefsByOID` is unary and matches refs against `refs/tags/` and `refs/heads/` (or arbitrary caller-supplied patterns) filtered only by `--points-at <oid>`, an ordinary authenticated client can trigger it against a repository containing a very large number of references (e.g., many thousands to millions of branches/tags all pointing at, or peeling to, the same commit) and force Gitaly to buffer the entire unbounded result set in memory and serialize it into a single protobuf message before it can be sent — with no server-side ceiling analogous to `--count`/pagination limits used elsewhere.

### Impact Explanation
A large enough unbounded ref list can cause excessive memory allocation and CPU time within a single RPC handler invocation, and can also produce a response exceeding gRPC's message-size limits, causing the request to fail after having already consumed significant server resources. Because Gitaly serves many repositories/tenants from a single process, sustained or repeated calls of this kind can degrade or exhaust resources for the whole node — a denial-of-service condition directly analogous to the reported "gas exhaustion" bug class, where an unbounded per-call workload consumes all available resources for processing that unit of work.

### Likelihood Explanation
Likelihood is low-to-moderate: the RPC is reachable by any client authorized to call Gitaly RPCs (no special privilege required), and constructing a repository with a very large number of refs pointing at a single object is straightforward for a user who can push/create refs in a repository they control. It requires the attacker to first populate a repository with a large ref count, which takes some effort but is not privileged or exotic.

### Recommendation
Enforce a mandatory, server-side default and maximum on the number of refs returned by `FindRefsByOID` (as is already done via `--count` when a client-supplied limit is present), rather than allowing `count == 0` to mean "unlimited." Consider converting `FindRefsByOID` to a streaming RPC with chunked responses and pagination, consistent with `ListRefs`/`FindAllTags`, to bound both memory usage and per-response message size regardless of client input.

### Proof of Concept
1. Create or use a repository and add a very large number of references (e.g., tens/hundreds of thousands of branches or tags) all pointing at (or peeling to) the same commit `<oid>`.
2. Call `FindRefsByOID` with `Repository=<repo>`, `Oid=<oid>`, and `Limit` unset (`0`).
3. Observe that `ForEachRef` is invoked without `--count`, causing the handler to accumulate all matching ref names in the `refs` slice in `internal/gitaly/service/ref/find_refs_by_oid.go` before returning a single response — measure memory/CPU consumption and response size growth as the number of refs increases, confirming the unbounded-resource-consumption path.

	return func(cfg *forEachRefConfig) {
		cfg.count = count
	}

// context will cause the pipeline to be cancelled, too.

	repo *localrepo.Repo,
	patterns []string,
	opts ...ForEachRefOption,

		// The default format also includes the object type, which requires us to read the
		// referenced commit's object. It would thus be about 2-3x slower to use the
		// default format, and instead we move the burden into the next pipeline step by
		// default.
		format: "%(objectname) %(refname)",
	}
	for _, opt := range opts {
		opt(&cfg)
	}

		defer close(resultChan)

			gitcmd.ValueFlag{Name: "--format", Value: cfg.format},
