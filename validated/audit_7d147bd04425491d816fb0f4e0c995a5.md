### Title
Weight double-counting in `ValidateMultiSign` TVM precompile allows a single signer to satisfy a multi-sig permission threshold with signature malleability - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract, which is reachable by any smart-contract call on-chain (i.e. any unprivileged deployer/caller wiring up on-chain multisig/RWA logic), computes cumulative signer weight for an account `Permission` in a way that is weaker than the canonical signature/weight-checking logic used elsewhere in java-tron (`TransactionCapsule.checkWeight`). It deduplicates signers by exact raw signature bytes instead of by recovered address, so a signer who can produce two distinct byte-level ECDSA signatures over the same message (e.g. via signature malleability) is credited with weight twice.

### Finding Description
`TransactionCapsule.checkWeight` — the reference implementation used to validate ordinary transaction signature weight — deduplicates strictly by recovered *address* and throws `"has signed twice!"` if the same address appears more than once, regardless of the raw signature bytes: [1](#0-0) 

By contrast, `PrecompiledContracts.ValidateMultiSign.execute` (invoked from TVM bytecode via the precompile, e.g. address `0x66`) tracks a list `executedSignList` containing both the recovered address and the merged `(recoveredAddr + signature bytes)` value, and only skips counting weight when it sees the exact same `(recoveredAddr, signature bytes)` pair again: [2](#0-1) 

If the same address `recoveredAddr` reappears with a *different* raw signature encoding (still valid, still recovering to that address — which is possible via ECDSA signature malleability, i.e. submitting both `(r, s)` and `(r, n-s)` with the corresponding recovery id), the code does not `continue`; it merely calls `MUtil.checkCPUTime()` and then falls through to add the key's `weight` to `totalWeight` a second time:
```java
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
```
This means one private key's signature weight can be counted twice (up to `MAX_SIZE = 5` times per call) toward `permission.getThreshold()`, letting a single signer pass a multi-signature permission check that was supposed to require multiple independent, distinct signers — the exact class of "permission access logic" flaw referenced in the Curio incident report (a MakerDAO-style access-control vulnerability that let an attacker bypass intended multi-party authorization).

### Impact Explanation
Any on-chain contract (RWA vaults, custodial multisig wallets, DeFi protocols, etc.) that relies on `ValidateMultiSign` to gate privileged operations (fund release, asset minting, governance actions) based on an account's TRON `Permission` threshold can be tricked into approving an operation using fewer independent signers than the threshold requires. This directly undermines the security guarantee of TRON's native multisig permission system as exposed to smart contracts, potentially enabling unauthorized withdrawal/minting/governance actions analogous to the reported $16M RWA exploit.

### Likelihood Explanation
Exploitability is high in principle, since `ValidateMultiSign` is a public TVM precompile invokable from any deployed contract with attacker-controlled `data`/signature array. The prerequisite is the ability to produce two distinct, valid byte-level ECDSA signature encodings over the same hash that both recover to the same address (classic ECDSA malleability: flipping `s` to `n-s` with adjusted recovery id). Note: I was unable to fully confirm from the available index whether `recoverAddrBySign`/`SignUtils` elsewhere in the codebase enforce canonical low-S signatures at the point signatures are constructed by wallets (which would not prevent an attacker from constructing a malleable variant independently, since malleability is a property of any valid signature, not of the signer's tooling), nor could I retrieve the full implementation of `ByteArray.matrixContains` to confirm its exact comparison semantics. These are noted as open verification items for a deeper review, but the core code-level asymmetry between `checkWeight` (dedup by address) and `ValidateMultiSign` (dedup by exact signature bytes) is confirmed directly in the source shown above.

### Recommendation
In `PrecompiledContracts.ValidateMultiSign.execute`, deduplicate strictly by `recoveredAddr` (mirroring `TransactionCapsule.checkWeight`), rejecting or skipping weight accumulation the moment an address repeats, instead of allowing re-accumulation whenever the raw signature bytes differ. Align this logic with `checkWeight`/`getWeight` used for normal transaction validation so both code paths enforce "each address contributes weight at most once."

### Proof of Concept
1. Deploy a contract account with an `Active` `Permission` requiring `threshold = 2`, with two keys: `keyA` (weight 1) and `keyB` (weight 1) — i.e., normally requires both `keyA` and `keyB` to sign.
2. From `keyA` alone, sign the target hash `hash = sha256(address || permissionId || data)` to get signature `sig1`.
3. Compute the malleable variant `sig2` of the same signature: flip `s -> n-s` and adjust the recovery bit `v`; `sig2` still recovers to `keyA`'s address but has different raw bytes than `sig1`.
4. Call the `ValidateMultiSign` precompile with signature array `[sig1, sig2]`.
5. In `execute`, the first iteration adds `keyA`'s weight (1) to `totalWeight`. The second iteration recognizes `recoveredAddr` (keyA) is already in `executedSignList`, but since `sign` (the merged bytes for `sig2`) differs from the previously stored merged bytes for `sig1`, it does **not** `continue` — it proceeds to add `keyA`'s weight (1) again, making `totalWeight = 2 >= threshold (2)`, returning success — despite `keyB` never having signed.
