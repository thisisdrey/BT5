### Title
Unbounded array allocation in `BatchValidateSign` precompile from attacker-controlled length words - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` precompiled contract (TVM precompile) parses its `calldata` into raw ABI-style length fields and uses those attacker-supplied values directly as Java array sizes before any bound is enforced, when the `allowTvmSelfdestructRestriction` hard-fork flag is not active. This mirrors the CVE-2017-9732 bug class: a length field read straight from untrusted input is used to size a memory allocation without validating it against a sane maximum, enabling remote, unauthenticated memory-exhaustion / denial of service.

### Finding Description
`BatchValidateSign.doExecute` reads the raw words from calldata and computes offsets/lengths that are entirely attacker-controlled: [1](#0-0) 

The `MAX_SIZE` (16) bound check on `sigArraySize`/`addrArraySize` is only performed inside `if (VMConfig.allowTvmSelfdestructRestriction()) { ... }`. When that hard-fork flag is not active (e.g. on a chain/genesis where it has not been enabled), the bound check is skipped entirely, yet `extractBytes32Array` (for `addresses`) is invoked unconditionally regardless of the flag: [2](#0-1) 

`extractBytes32Array` and `extractBytesArray` take `len = words[offset].intValueSafe()` directly from the calldata word and immediately allocate `new byte[len][]`, with no upper bound check on `len` before allocation. Since `intValueSafe()` can return values up to `Integer.MAX_VALUE`, a single crafted `data` blob can force an attempted allocation of a `byte[2147483647][]` reference array (~16 GB of pointers alone, before any of the constituent `byte[]` elements are even populated), or a similarly-sized allocation via `extractBytesArray`'s inner `extractBytes(data, offset, bytesLen)` call which also uses an attacker-controlled `bytesLen`.

This is directly analogous to the `read_packet` flaw in knc: a length value taken from untrusted network/transaction input is used to size a buffer/array before the value is bounds-checked against a safe maximum.

### Impact Explanation
`BatchValidateSign` is invoked from Solidity contracts via the standard precompile-call mechanism, reachable by any unprivileged account that can deploy or call a smart contract (a single signed transaction). A crafted call triggers an immediate, very large heap allocation attempt in the node process executing the transaction. Although the outer `execute()` wraps the call in `catch (Throwable t)` (which would also catch an `OutOfMemoryError`), the JVM has already attempted (and strained) the allocation by the time the error is thrown; repeated or concurrent invocations (the precompile also spins up parallel `Future` tasks on a shared thread pool for the non-constant-call path) can exhaust real heap memory across the node before garbage collection can recover, degrading or crashing the full node — a denial-of-service impact consistent with "node crash or halt."

### Likelihood Explanation
The precompile is reachable by any address via a normal contract call with no special privileges, and the vulnerable path is active precisely on any deployment where `allowTvmSelfdestructRestriction` has not yet been toggled on (a common state for many private/consortium chains or forks that lag mainnet hard-fork activation). No signature or particular privilege is needed to trigger it beyond issuing an ordinary transaction that calls the precompile address.

### Recommendation
Move the `MAX_SIZE` bound check (or an equivalent one) so that it always executes before `extractBytes32Array`/`extractBytesArray` are called, independent of the `allowTvmSelfdestructRestriction` flag. Additionally, `extractBytes32Array`/`extractBytesArray` should themselves validate `len`/`bytesLen` against `MAX_SIZE` (or the remaining `data.length`) before performing any array allocation, so the fix does not depend on a hard-fork toggle.

### Proof of Concept
Construct calldata for `BatchValidateSign(hash, bytes[] signatures, bytes32[] addresses)` where the length word at the `addresses` array offset (word 2 target) is set to `0x7fffffff` instead of a real array length, while running on a chain configuration where `allowTvmSelfdestructRestriction()` is false (default before the corresponding hard fork). Calling this precompile from any contract deployed by an unprivileged account causes `extractBytes32Array` to execute `new byte[2147483647][]`, which forces a multi-gigabyte allocation attempt per invocation. [3](#0-2) 

**Note on verification limits:** I was unable to fully inspect `DataWord.intValueSafe()`'s exact clamping behavior within the tool budget available (only located it in `common/src/main/java/org/tron/common/runtime/vm/DataWord.java` without reading its body), so the precise maximum value it can return should be double-checked; based on its use elsewhere in this codebase as a "safe" int conversion, it is expected to clamp overflowing 256-bit values to `Integer.MAX_VALUE` rather than throwing, which is what makes this allocation-size attack feasible. A Devin session with full file access would be needed to confirm this exact clamping semantic before treating the PoC as final.
