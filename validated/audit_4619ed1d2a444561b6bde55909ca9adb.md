### Title
Attacker can spam `updateBeforeMintOrBurn` to permanently advance `TokenState.timestamp` and burn accrued rewards via index rounding to zero - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenIndex()` advances `TokenState.timestamp` even when the computed `_ratio` (`_tokensAccrued.wadDiv(_totalSupply)`) rounds to zero. Because `updateBeforeMintOrBurn()` is permissionless ("This function also may be called by anyone to update stored indexes"), an attacker can call it every block, keep `_deltaTimestamps` minimal, and — when `speed * 1e18 < totalSupply` — make every index update produce `_ratio == 0` while permanently consuming the elapsed time. Rewards for those periods are lost forever; users' `tokensAccruedOf` never grows.

### Finding Description
In `contracts/RewardsDistributor.sol`, `_calculateTokenIndex` computes:

```solidity
uint256 _tokensAccrued = _deltaTimestamps * _speed;
uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
_newIndex = (_supplyState.index + _ratio).toUint224();
_newTimestamp = block.timestamp.toUint32();
``` [1](#0-0) 

`_updateTokenIndex` then stores `_newTimestamp` whenever `_speed > 0` and `_deltaTimestamps > 0`, even when `_newIndex` equals the old index:

```solidity
if (_newIndex > 0 && _newTimestamp > 0) {
    _supplyState.index = _newIndex;
    _supplyState.timestamp = _newTimestamp;
``` [2](#0-1) 

The entry point `updateBeforeMintOrBurn(IERC20 token_, address account_)` is external and unrestricted — anyone can call it for any tracked token and any account:

```solidity
function updateBeforeMintOrBurn(IERC20 token_, address account_) external override {
    if (tokenStates[token_].index > 0) {
        _updateTokenIndex(token_);
        _updateTokensAccruedOf(token_, account_);
    }
}
``` [3](#0-2) 

`wadDiv` in Metronome's `WadRayMath` returns 0 whenever `numerator * 1e18 < denominator / 2` (half-up rounding). Therefore, if `speed` and `totalSupply` satisfy `2 * speed * 1e18 < totalSupply`, then every call spaced one block (~2 s on Optimism) yields `_tokensAccrued * 1e18 / totalSupply < 1`, i.e. `_ratio == 0`, while `timestamp` is still overwritten with `block.timestamp`. The `_deltaTimestamps * _speed` tokens for those intervals are never added to the index and can never be recovered, since accrual only counts time since the last stored timestamp.

This mirrors the tokemak `AbstractRewarder.rewardPerToken()` finding exactly: division truncation plus a permissionless function that advances the "last updated" marker lets an attacker keep `rewardPerToken`/index increments at zero.

Additionally, `claimRewards` itself calls `_updateTokenIndex`, so even honest user claims keep re-arming the truncation as long as the attacker keeps the elapsed-delta small.

### Impact Explanation
Permanent theft/freezing of unclaimed yield: reward tokens streamed at `tokenSpeeds[token_]` accrue to no one. The emission intended for depositors/debtors during the griefed windows is never reflected in `tokenStates[token_].index`, so `_calculateTokenDelta` returns `_tokensDelta == 0` and `tokensAccruedOf` stays flat while the reward token balance sits undistributed in the contract. Direct impact on the reward-accrual invariant.

### Likelihood Explanation
Requires `tokenSpeeds[token_] * 1e18 * blockDelta < totalSupply / 2`. This is realistic for:
- a low-decimal reward token (e.g. USDC at 6 decimals) with modest speed, and/or
- a DepositToken/DebtToken with large 18-decimal supply.

Example: `totalSupply = 1e27`, `speed = 1e8` (≈ $0.1/s in USDC ≈ $8,640/day), block delta = 2 s → `2e8 * 1e18 = 2e26 < 5e26` ⇒ `_ratio == 0`. The attacker only needs to call the public `updateBeforeMintOrBurn` once per block — gas-cheap on Optimism where Metronome is deployed. Since `updateTokenSpeed` also resets `timestamp` on speed changes, the attacker only needs to sustain the spam while rewards stream; any window where they succeed permanently destroys that window's emission.

Preconditions check: no `onlyPool`/governor modifier on `updateBeforeMintOrBurn`, no pause flag on the distributor path, `nonReentrant` only on `claimRewards`. The bug is in `_updateTokenIndex` itself, so modifiers do not mitigate it.

### Recommendation
Track the division remainder (or accumulate sub-1 index deltas) so truncated rewards roll into the next update instead of being burned. Two viable approaches:

1. Only advance `timestamp` by the amount of time actually "paid for" — e.g. store the remainder `_tokensAccrued * 1e18 % _totalSupply` per token and add it into the next `_ratio` computation:
```solidity
uint256 _scaled = _tokensAccrued * 1e18 + _state.remainder;
_newIndex = _supplyState.index + (_scaled / _totalSupply);
_state.remainder = _scaled % _totalSupply;
```
2. Alternatively, when `_ratio == 0`, do not update `_supplyState.timestamp` at all, so the elapsed time accumulates until the accrual is non-zero. (This delays rather than destroys rewards; option 1 is strictly more accurate.)

### Proof of Concept
Foundry/Hardhat fork sketch against deployed Optimism `RewardsDistributor`:

```solidity
// Setup: rewardToken = USDC-like, token_ = DepositToken with totalSupply = 1e27
// governor sets tokenSpeeds[token] = 1e8

// Attacker loop (once per block, ~2s blocks on Optimism):
for (uint i; i < N; ++i) {
    vm.roll(block.number + 1);
    vm.warp(block.timestamp + 2);
    rewardsDistributor.updateBeforeMintOrBurn(token, address(0xbeef)); // permissionless
    // each call: _deltaTimestamps = 2, _tokensAccrued = 2e8
    // _ratio = 2e8 * 1e18 / 1e27 = 0  -> index unchanged, timestamp advanced
}

// Assert: tokenStates[token].index == INITIAL_INDEX (never increased)
// Assert: elapsed N*2 seconds produced zero accrual -> speed*N*2 tokens burned
// Assert: victim.claimable / tokensAccruedOf[victim] == 0 despite time passing
```

Key assertions:
- `tokenStates[token_].timestamp` equals the latest block timestamp while `index` never moved — proving permanent loss rather than deferral.
- Without the spam (single call after `N*2` seconds), the same window yields a non-zero `_ratio` and non-zero `tokensAccruedOf[victim]`, isolating the attacker's action as the cause.

    function _calculateTokenIndex(
        TokenState memory _supplyState,
        IERC20 token_
    ) private view returns (uint224 _newIndex, uint32 _newTimestamp) {
        uint256 _speed = tokenSpeeds[token_];
        uint256 _deltaTimestamps = block.timestamp - uint256(_supplyState.timestamp);
        if (_deltaTimestamps > 0 && _speed > 0) {
            uint256 _totalSupply = token_.totalSupply();
            uint256 _tokensAccrued = _deltaTimestamps * _speed;
            uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
            _newIndex = (_supplyState.index + _ratio).toUint224();
            _newTimestamp = block.timestamp.toUint32();
        } else if (_deltaTimestamps > 0 && _supplyState.index > 0) {
            _newTimestamp = block.timestamp.toUint32();
        }
    }
```

    function _updateTokenIndex(IERC20 token_) private {
        TokenState storage _supplyState = tokenStates[token_];
        (uint224 _newIndex, uint32 _newTimestamp) = _calculateTokenIndex(_supplyState, token_);
        if (_newIndex > 0 && _newTimestamp > 0) {
            _supplyState.index = _newIndex;
            _supplyState.timestamp = _newTimestamp;
            emit TokenIndexUpdated(_newIndex, _newTimestamp);
        } else if (_newTimestamp > 0) {
            _supplyState.timestamp = _newTimestamp;
            emit TokenIndexUpdated(_supplyState.index, _newTimestamp);
        }
    }
