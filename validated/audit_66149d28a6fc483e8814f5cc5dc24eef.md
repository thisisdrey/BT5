Audit Report

## Title
`SwapFirstAssetTrader::refund_weight` swaps XCM fee refunds through the AMM with `amount_out_min = None`, exposing users to unbounded slippage/sandwiching - (File: `cumulus/primitives/utility/src/lib.rs`)

## Summary
`SwapFirstAssetTrader::refund_weight` unconditionally swaps the unspent portion of the collected XCM execution fee (denominated in `Target`) back into the original fee-payment asset via `SwapCredit::swap_exact_tokens_for_tokens`, passing `None` for `amount_out_min`. This disables the pallet's only slippage guard for that swap, allowing the amount refunded to the fee payer to be reduced by anyone who moves the relevant `pallet_asset_conversion` pool's reserves in the same block.

## Finding Description
In `refund_weight`, the code extracts the refundable portion of `total_fee` and swaps it with:
```rust
SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)
```
at `cumulus/primitives/utility/src/lib.rs:540-544`. This is backed by `pallet_asset_conversion::Pallet::do_swap_exact_credit_tokens_for_tokens` at `substrate/frame/asset-conversion/src/lib.rs:1075-1109`, whose only price-floor check is:
```rust
ensure!(amount_out_min.map_or(true, |a| amount_out >= a), Error::<T>::ProvidedMinimumNotSufficientForSwap);
```
at lines 1093-1096, which is a no-op whenever `amount_out_min` is `None`. Since `refund_weight` always passes `None`, the pallet accepts whatever `amount_out` the AMM curve yields for the pool's current reserves at execution time, with no re-validation afterward. By contrast, `buy_weight` (lines 469-489) uses `swap_tokens_for_exact_tokens`, an exact-output call that inherently bounds the input consumed, so it does not suffer the same unbounded-loss exposure. The asymmetry between `buy_weight`'s bounded swap and `refund_weight`'s unbounded swap is real and verified directly in the current repository code.

## Impact Explanation
Any account can submit ordinary, permissionless `pallet_asset_conversion::swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` extrinsics against the same `Target`/fee-asset pool used by a runtime's configured `SwapFirstAssetTrader`, shifting reserves immediately before an XCM message's fee refund executes. Because the refund leg has no floor, the fee payer receives a reduced refund amount, and the difference is captured by the reserve-manipulating party — a sandwich against an AMM leg the affected user cannot configure a slippage tolerance for, since it fires automatically inside XCM weight accounting rather than as a user-submitted extrinsic. This is value loss/underpricing of a public, automatically-triggered code path, consistent with the "public underpriced work" category of in-scope impacts.

## Likelihood Explanation
Medium-to-high feasibility: the precondition (an XCM message paying fees in a non-`Target` asset via `SwapFirstAssetTrader`, with unused weight to refund) is a normal, frequent code path for any parachain that configures this trader — confirmed as configured in `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/xcm_config.rs`, `asset-hub-westend/src/xcm_config.rs`, `cumulus/parachains/runtimes/testing/penpal/src/xcm_config.rs`, and `substrate/frame/staking-async/runtimes/parachain/src/xcm_config.rs`. No privileged access is required — reserve manipulation only needs ordinary swap extrinsics.

## Recommendation
Do not pass `None` for `amount_out_min` in `refund_weight`. Immediately before the swap, compute an expected output via `QuotePrice::quote_price_exact_tokens_for_tokens` (already used for `quote_weight`), apply a configurable tolerance, and pass `Some(min_expected)` into `SwapCredit::swap_exact_tokens_for_tokens`. On failure to meet the floor, retain the credit in `total_fee` (mirroring the existing `Err` branch) instead of accepting an unbounded-loss trade.

## Proof of Concept
1. Configure a parachain runtime with `SwapFirstAssetTrader<Target, pallet_asset_conversion::Pallet<Runtime>, WeightToFee, ...>` backed by a live `Target`/`OtherAsset` pool.
2. Submit an XCM message paying fees in `OtherAsset` with weight overpaid relative to actual consumption, so `buy_weight` swaps `OtherAsset -> Target` and leaves unused weight for `refund_weight`.
3. Before/around execution of the refund, submit ordinary `swap_exact_tokens_for_tokens` calls on the same pool to shift reserves unfavorably relative to the pending refund direction (`Target -> OtherAsset`).
4. Observe `refund_weight`'s call at `cumulus/primitives/utility/src/lib.rs:540-544` executes and returns less `OtherAsset` than a `quote_weight`-based expectation, since `amount_out_min = None` skips the `ProvidedMinimumNotSufficientForSwap` check in `do_swap_exact_credit_tokens_for_tokens` (`substrate/frame/asset-conversion/src/lib.rs:1093-1096`), confirming the refunded value to the fee payer is reduced with no on-chain floor.
