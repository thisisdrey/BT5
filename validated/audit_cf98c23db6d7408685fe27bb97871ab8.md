Audit Report

## Title
Public `stake()` extrinsic can silently truncate/zero reward accrual in `pallet-asset-rewards` due to undersized `PRECISION_SCALING_FACTOR` with no remainder carry-over - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`reward_per_token()` in `pallet-asset-rewards` computes each update's reward-per-token increment as `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked`, where `PRECISION_SCALING_FACTOR` is a fixed `u16` constant of `4096`. [1](#0-0)  Because `update_pool_rewards` unconditionally advances `last_update_block` to the current block every time it is called regardless of whether the computed increment was nonzero, any truncation to zero in the division is a permanent loss of that time window's reward accrual rather than a deferred one. [2](#0-1) 

## Finding Description
`reward_per_token` performs integer division of `reward_rate_per_block * blocks_elapsed * 4096` by `total_tokens_staked`: [3](#0-2)  and `derive_rewards` divides the per-staker product back down by the same fixed factor. [4](#0-3)  Every call path that touches the pool (`stake`, `unstake`, `harvest_rewards`, `set_pool_reward_rate_per_block`) routes through `update_pool_and_staker_rewards`/`update_pool_rewards`, which sets `new_pool_info.last_update_block = current_block_number()` unconditionally — there is no accumulation of leftover/fractional reward across calls. [5](#0-4)  `stake()` is a public, unprivileged extrinsic that directly inflates `total_tokens_staked`, the divisor in this calculation, with no check anywhere in `create_pool`, `stake`, or `reward_per_token` bounding `total_tokens_staked` relative to `reward_rate_per_block * PRECISION_SCALING_FACTOR`. [6](#0-5)  `set_pool_reward_rate_per_block` only guards against the admin *decreasing* the rate, not against this precision failure mode. [7](#0-6)  The result is a verified, exact-match to the claim: whenever `total_tokens_staked > reward_rate_per_block * blocks_elapsed * 4096`, `reward_per_token_stored` fails to advance for that call, yet `last_update_block` is still advanced, so that window's reward is permanently discarded rather than deferred.

## Impact Explanation
This is a runtime bug compromising the intended reward-distribution behavior of the pallet: legitimate stakers receive less than the reward tokens the pool was funded to distribute via `deposit_reward_tokens`, while the reward tokens remain sitting in the pool's sub-account, only recoverable by the admin through `cleanup_pool` (which additionally requires zero remaining stakers). This is triggerable purely through normal, unprivileged pool participation (`stake`) combined with an admin-chosen `reward_rate_per_block`/asset-decimal combination, and falls under the impact gate's "runtime bugs that compromise intended behavior" / reward-payout correctness category.

## Likelihood Explanation
Feasibility depends on the ratio of `reward_rate_per_block` to `total_tokens_staked`; pools with low per-block rates or high-supply/high-decimal staked assets are naturally close to or past the truncation threshold, and any unprivileged account can push a marginal pool over that threshold simply by calling `stake()` with a sufficiently large amount, with no governance, admin, or collusion required, and it is fully repeatable on every subsequent update while the condition holds.

## Recommendation
Replace the fixed `PRECISION_SCALING_FACTOR: u16 = 4096` with a materially larger, ideally per-pool-configurable or decimal-aware precision multiplier, and modify `reward_per_token`/`update_pool_rewards` to carry over any truncated remainder (e.g., track a running remainder or accumulate un-flushed reward-block credit) instead of discarding it when `last_update_block` is advanced, so reward accrual degrades gracefully rather than being silently and permanently lost per update window.

## Proof of Concept
1. Admin creates a pool with a modest `reward_rate_per_block` (e.g., `100`) for a staked asset with many decimals via `create_pool`.
2. An unprivileged account calls `stake()` with an amount such that `total_tokens_staked > reward_rate_per_block * 4096` for the typical number of blocks between staker interactions.
3. On the next `stake`/`unstake`/`harvest_rewards` call, `update_pool_and_staker_rewards` invokes `reward_per_token()`, which computes `reward_rate_per_block * blocks_elapsed * 4096 / total_tokens_staked == 0`; `update_pool_rewards` then sets `last_update_block` to the current block regardless, discarding that window's reward permanently.
4. Repeating step 3 shows `reward_per_token_stored` and stakers' `derive_rewards` output remain stagnant across multiple update cycles despite `reward_rate_per_block` being nonzero and reward tokens continuing to sit in the pool account, verifiable via a Rust unit test asserting `reward_per_token_stored` before and after several `update_pool_and_staker_rewards` calls under these parameters.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

	fn create_pool(
		creator: &T::AccountId,
		staked_asset_id: T::AssetId,
		reward_asset_id: T::AssetId,
		reward_rate_per_block: T::Balance,
		expiry: DispatchTime<BlockNumberFor<T>>,
		admin: &T::AccountId,
	) -> Result<PoolId, DispatchError> {
		// Ensure the assets exist.
		ensure!(T::Assets::asset_exists(staked_asset_id.clone()), Error::<T>::NonExistentAsset);
		ensure!(T::Assets::asset_exists(reward_asset_id.clone()), Error::<T>::NonExistentAsset);

		// Check the expiry block.
		let now = T::BlockNumberProvider::current_block_number();
		let expiry_block = expiry.evaluate(now);
		ensure!(expiry_block > now, Error::<T>::ExpiryBlockMustBeInTheFuture);

		let pool_id = NextPoolId::<T>::try_mutate(|id| -> Result<PoolId, DispatchError> {
			let current_id = *id;
			*id = id.ensure_add(1)?;
			Ok(current_id)
		})?;

		let footprint = Self::pool_creation_footprint();
		let cost = T::Consideration::new(creator, footprint)?;
		PoolCost::<T>::insert(pool_id, (creator.clone(), cost));

		// Create the pool.
		let pool = PoolInfoFor::<T> {
			staked_asset_id: staked_asset_id.clone(),
			reward_asset_id: reward_asset_id.clone(),
			reward_rate_per_block,
			total_tokens_staked: 0u32.into(),
			reward_per_token_stored: 0u32.into(),
			last_update_block: 0u32.into(),
			expiry_block,
			admin: admin.clone(),
			account: Self::pool_account_id(&pool_id),
		};

		// Insert it into storage.
		Pools::<T>::insert(pool_id, pool);

		// Emit created event.
		Self::deposit_event(Event::PoolCreated {
			creator: creator.clone(),
			pool_id,
			staked_asset_id,
			reward_asset_id,
			reward_rate_per_block,
			expiry_block,
			admin: admin.clone(),
		});

		Ok(pool_id)
	}

	fn set_pool_reward_rate_per_block(
		admin: &T::AccountId,
		pool_id: PoolId,
		new_reward_rate_per_block: T::Balance,
	) -> DispatchResult {
		let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
		ensure!(pool_info.admin == *admin, BadOrigin);
		ensure!(
			new_reward_rate_per_block > pool_info.reward_rate_per_block,
			Error::<T>::RewardRateCut
		);

		// Always start by updating the pool rewards.
		let rewards_per_token = Self::reward_per_token(&pool_info)?;
		let mut pool_info = Self::update_pool_rewards(&pool_info, rewards_per_token)?;

		pool_info.reward_rate_per_block = new_reward_rate_per_block;
		Pools::<T>::insert(pool_id, pool_info);

		Self::deposit_event(Event::PoolRewardRateModified { pool_id, new_reward_rate_per_block });

		Ok(())
	}
