### Title
Postponed receipts are not purged on `DeleteAccount`, allowing a `Transfer` action to be misdelivered to an unrelated account that later reclaims the same name - ([File: runtime/runtime/src/actions.rs])

### Summary
`action_delete_account` (runtime/runtime/src/actions.rs:314-390) removes the `Account` record but never clears any `PostponedReceiptId`, `PendingDataCount`, or `PostponedReceipt` entries that reference the deleted `account_id`. `check_account_existence` (runtime/runtime/src/actions.rs:787-855) only checks `account.is_some()`/`is_none()` at the moment the postponed receipt is finally executed, so once the name is re-registered by anyone, a `Transfer` action from the orphaned postponed receipt is delivered to the new, unrelated account instead of erroring or being refunded.

### Finding Description
When an `ActionReceipt` destined for `acct.near` carries `input_data_ids` that are not yet satisfied, `process_action_receipt` (runtime/runtime/src/lib.rs:1593-1658) stores it as a postponed receipt keyed only by `receiver_id` + `receipt_id`, plus a `PostponedReceiptId` link keyed by `receiver_id` + `data_id`, with no reference to any specific "incarnation" of the account: [1](#0-0) 

If `acct.near` executes `DeleteAccount` before the awaited data arrives, `action_delete_account` removes the `Account` record and returns, but performs no lookup or cleanup of any `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` entries for that account: [2](#0-1) 

Later, when the matching `DataReceipt` finally arrives, `process_receipt`'s `Data` branch looks up the `PostponedReceiptId` purely by `receiver_id`/`data_id`, decrements `PendingDataCount`, and once it hits zero, fetches and executes the stored `ready_receipt` via `apply_action_receipt` — with no check on whether the account is the same one that existed when the receipt was postponed: [3](#0-2) 

Inside that execution, `apply_action`/`check_account_existence` for a `Transfer` action only checks `account.is_none()`; if a new account now exists under that name, no error is raised and the credit proceeds: [4](#0-3) 

Because account identity in state is solely the `AccountId` string (no generation/incarnation tag), this means: original `acct.near` receives an ActionReceipt with a data-blocked `Transfer`; it self-deletes; a third party recreates `acct.near` (e.g. via a permissionless registrar contract) before the data dependency resolves; when the dependency resolves, the deposit is credited into the new owner's `amount` instead of being refunded to the original sender.

### Impact Explanation
This is a fund-misdirection/theft bug: a deposit intended for one logical owner of an account name is credited to a different, unrelated party who merely re-registered the same name after the original owner deleted their account. This maps to the "theft of user funds" bounty category. The loss is bounded by whatever deposit amount is encoded in the pending `Transfer` action.

### Likelihood Explanation
Exploitation requires: (1) a receipt with a data-blocked `Transfer` action targeting an account that later self-deletes while the dependency is still outstanding, and (2) an attacker (or colluding party) re-registering that same account name before the dependency resolves. Account re-registration under NEAR's permissionless registrar/linkdrop-style contracts is achievable by ordinary users, and postponed-receipt state persists indefinitely with no expiry, giving attackers a wide window. The scenario needs a specific sequencing (delete-then-recreate racing the data dependency) rather than being trivially triggerable at will against an arbitrary victim, so it is a real but conditional exploitation path rather than an always-available attack.

### Recommendation
Tie postponed-receipt delivery to account identity: either (a) purge/invalidate all `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` entries for `account_id` inside `action_delete_account`, refunding/erroring those postponed receipts instead of leaving them dangling, or (b) tag accounts with a creation nonce/incarnation id and have `check_account_existence`/`apply_action_receipt` verify the postponed receipt's target incarnation still matches before crediting a `Transfer`.

### Proof of Concept
Runtime/test-loop integration test:
1. Create account `acct.near` with a small balance.
2. Send it an `ActionReceipt` containing a `Transfer(deposit)` action with `input_data_ids = [data_id]` (not yet satisfied) — this becomes a postponed receipt (mirrors `action_receipt_awaiting` pattern used in existing tests, e.g. runtime/runtime/src/tests/apply.rs:5014-5033).
3. In a later receipt, apply `DeleteAccount` on `acct.near` (beneficiary elsewhere), confirming the account is removed while the postponed receipt/PendingDataCount/PostponedReceiptId entries remain in state.
4. Apply a `CreateAccount` receipt re-registering `acct.near` as a fresh, unrelated account with balance 0.
5. Deliver the `DataReceipt` matching `data_id`.
6. Assert: the postponed `Transfer`'s `deposit` is credited into the *new* `acct.near`'s `amount` (not refunded to the original transfer's predecessor), demonstrating misdirected funds.

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}
