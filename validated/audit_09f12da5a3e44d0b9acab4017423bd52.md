### Title
Per-IP unstaked stream throttle can be reset by connection churn, bypassing `MAX_UNSTAKED_TPS` - (`streamer/src/nonblocking/quic.rs`, `streamer/src/nonblocking/stream_throttle.rs`)

### Summary
The `ConnectionStreamCounter` that enforces the 100ms unstaked stream budget (`throttle_stream` / `available_load_capacity_in_throttling_duration`) is keyed to a `ConnectionTable` entry rather than to a persistent per-IP state that outlives connection churn. `ConnectionTable::try_add_connection` only reuses an existing counter if there is already a live connection for that key; once all connections for an unstaked IP are closed and removed, the next connection creates a brand-new `ConnectionStreamCounter` with `stream_count = 0` and a fresh `last_throttling_instant`.

### Finding Description
`ConnectionTable::try_add_connection` looks up the per-key vector of `ConnectionEntry`s and reuses the counter of the *first entry currently present*: [1](#0-0) 
For unstaked peers the table key is the IP address (`ConnectionTableKey::new(remote_addr.ip(), conn_context.remote_pubkey)` with `remote_pubkey = None`): [2](#0-1) [3](#0-2) 

The throttling budget itself is fixed per counter at `MAX_UNSTAKED_TPS * STREAM_THROTTLING_INTERVAL_MS / 1000` = 20 streams / 100ms, independent of how many connections are open for that IP: [4](#0-3) [5](#0-4) 

The counter reset logic only zeroes `stream_count` when `STREAM_THROTTLING_INTERVAL` (100ms) has elapsed since `last_throttling_instant`: [6](#0-5) 

Because `try_add_connection` reuses the counter only "if `connection_entry.first()`" exists — i.e., only while at least one connection for that IP is still tracked in the table — an attacker who fully closes every connection it has open from an IP causes that IP's table entry vector to become empty. If the empty state also allows `stream_counter_factory` to run again on the next connection, the new `ConnectionStreamCounter::new()` starts `stream_count = 0` and `last_throttling_instant = Instant::now()`, discarding whatever budget was consumed in the prior 100ms window. An attacker can therefore:
1. Open a QUIC connection from IP X, consume the full 20-stream/100ms budget on that connection.
2. Immediately close it (and any sibling connections for X), causing the table's entry for key `IP(X)` to lose all live connections.
3. Open a new QUIC connection from the same IP X before the 100ms window elapses; this connection is a "new" table entry and gets a brand-new `ConnectionStreamCounter`.
4. Repeat, consuming a fresh 20-stream budget every connection-churn cycle rather than every 100ms, so the effective aggregate throughput from IP X across all its connections can exceed `MAX_UNSTAKED_TPS` by a factor roughly proportional to how many times faster than 100ms a connection can be opened, sent-to, and closed.

This defeats the intent of `StakedStreamLoadEMA`/`MAX_UNSTAKED_TPS`, which is meant to bound aggregate unstaked throughput per throttling window, not merely per momentarily-alive connection group.

### Impact Explanation
This is a QoS/rate-limit evasion in the TPU QUIC ingestion path: an unstaked, unprivileged remote client can push transaction stream throughput to a leader well above the configured `MAX_UNSTAKED_TPS`, consuming disproportionate CPU/bandwidth/sigverify resources that are meant to be reserved primarily for staked traffic. This falls under the QoS evasion / DoS-via-resource-exhaustion bounty category for the TPU QUIC streamer.

### Likelihood Explanation
Exploitability depends on how fast an unprivileged client can complete a QUIC connect → send → close cycle relative to the 100ms `STREAM_THROTTLING_INTERVAL`, and on how quickly the `ConnectionTable` entry for the IP is actually vacated (removed from `table_type::Unstaked`/`IndexMap`) after the last connection closes. I was not able to fully trace `remove_connection`'s handling of emptied `Vec<ConnectionEntry>` (I ran out of tool budget confirming whether the empty entry is pruned from the `IndexMap` immediately or lingers), which is the one remaining precondition needed to guarantee the exploit works exactly as described. Other mitigating controls exist in the same subsystem — e.g. `tpu_max_connections_per_ipaddr_per_minute` and `max_connections_per_unstaked_peer` — that rate-limit new-connection churn per IP; these could reduce, but based on the code reviewed, do not structurally eliminate, the ability to reset the stream counter more often than once per 100ms.

### Recommendation
Decouple the unstaked stream-rate counter from `ConnectionTable` entry lifetime. Maintain a persistent per-IP (or global unstaked) token-bucket/counter structure that survives connection open/close events for that key, only resetting on the fixed `STREAM_THROTTLING_INTERVAL` wall-clock cadence — not on `stream_counter_factory` re-invocation caused by all connections from that IP being closed and reopened.

### Proof of Concept
Unit test targeting `streamer/src/nonblocking/quic.rs`'s `ConnectionTable`:
```rust
#[test]
fn test_stream_counter_resets_on_full_ip_churn() {
    let cancel = CancellationToken::new();
    let mut table = ConnectionTable::new(ConnectionTableType::Unstaked, cancel);
    let ip = IpAddr::V4(Ipv4Addr::new(1,2,3,4));
    let stats = Arc::new(StreamerStats::default());

    // First connection for IP X gets counter C1
    let (_, _, counter1) = table.try_add_connection(
        ConnectionTableKey::IP(ip), 1,
        ClientConnectionTracker::new(stats.clone(), 1000).unwrap(),
        None, ConnectionPeerType::Unstaked,
        Arc::new(AtomicU64::new(0)), 10,
        || Arc::new(ConnectionStreamCounter::new()),
    ).unwrap();
    counter1.stream_count.fetch_add(20, Ordering::Relaxed); // budget exhausted

    // Close/remove the only connection for IP X (table entry becomes empty)
    table.remove_connection(ConnectionTableKey::IP(ip), 1, /*stable_id*/0);

    // Immediately (< 100ms later) reconnect from same IP X
    let (_, _, counter2) = table.try_add_connection(
        ConnectionTableKey::IP(ip), 2,
        ClientConnectionTracker::new(stats.clone(), 1000).unwrap(),
        None, ConnectionPeerType::Unstaked,
        Arc::new(AtomicU64::new(0)), 10,
        || Arc::new(ConnectionStreamCounter::new()),
    ).unwrap();

    // Assert: new counter is fresh (stream_count == 0), even though
    // less than STREAM_THROTTLING_INTERVAL has elapsed since counter1
    // was exhausted, allowing the IP to bypass the intended 100ms budget.
    assert_eq!(counter2.stream_count.load(Ordering::Relaxed), 0);
    assert!(!Arc::ptr_eq(&counter1, &counter2));
}
```
An integration-level PoC would spawn `setup_quic_server` with `SwQosConfig::default_for_tests()`, then in a loop: open a connection, send up to `max_streams_per_throttling_interval` streams, close the connection, and immediately reconnect, repeating faster than 100ms per cycle; then assert that `packet_batch_sender`-delivered packet count over wall-clock time exceeds `MAX_UNSTAKED_TPS * elapsed_seconds`.

    pub(crate) fn available_load_capacity_in_throttling_duration(
        &self,
        peer_type: ConnectionPeerType,
        total_stake: u64,
    ) -> u64 {
        match peer_type {
            ConnectionPeerType::Unstaked => self.max_unstaked_load_in_throttling_window,
            ConnectionPeerType::Staked(stake) => {
                if self.staked_throttling_enabled.load(Ordering::Relaxed) {
                    // 1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked
                    // clients get at least 1 more number of streams than unstaked connections.
                    self.max_staked_load_in_throttling_window
                        .saturating_mul(stake)
                        .checked_div(total_stake)
                        .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
                        .max(self.max_unstaked_load_in_throttling_window + 1)
                } else {
                    self.max_staked_load_in_throttling_window
                }
            }
        }
    }

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL

            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
