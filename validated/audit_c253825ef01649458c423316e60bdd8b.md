### Title
Postponed cross-contract callback rows and their `PendingDataCount`/`PostponedReceiptId` links survive `DeleteAccountAction` and later execute against the account's recreated instance, letting a deleted account's own stale privileged actions (e.g. `AddKey`) fire against a fresh owner - ([File: runtime/runtime/src/actions.rs], [File: core/store/src/utils/mod.rs])

### Summary
`action_delete_account` gates deletion only on `Account.storage_usage` minus contract code/global-contract overhead, comparing it to `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE`, but that field never includes the bytes of any outstanding `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` rows keyed by the account as receiver. `remove_account` likewise deletes only `Account`, `ContractCode`, access/gas keys and `ContractData`, leaving those postponed-receipt rows untouched in the trie. An attacker can therefore delete their own account while a self-addressed callback (scheduled via `Promise::then`, containing privileged native actions such as `AddKey`) is still parked waiting on attacker-controlled input data, then recreate the same account ID and, at a time of their choosing, feed the awaited `DataReceipt` to trigger execution of the stale receipt against the new account instance.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:314-353`) computes: [1](#0-0) 
using only `account_ref.storage_usage()` minus contract-code bytes. `Account.storage_usage` is maintained solely by actions that touch `Account`/`AccessKey`/`ContractCode`/`ContractData` (e.g. `action_add_key`, `action_deploy_contract`); nothing increments it for `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` rows, which are written directly by `process_action_receipt`/`process_receipt` (`runtime/runtime/src/lib.rs:1589-1658`, `1386-1474`) via `set_postponed_receipt`/`set` without ever touching `Account.storage_usage`.

`remove_account` (`core/store/src/utils/mod.rs:505-575`) removes `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData` only - it never iterates or removes `PostponedReceipt`, `PendingDataCount`, or `PostponedReceiptId` entries for the account: [2](#0-1) 

Exploit flow:
1. Attacker funds account `A` (a top-level name long enough to bypass the registrar restriction - `min_allowed_top_level_account_length` defaults to 32, so any longer top-level name can be created by anyone, confirmed at `core/parameters/res/runtime_configs/parameters.yaml:31` and `runtime/runtime/src/actions.rs:155-181`/`action_create_account`).
2. `A`'s contract schedules a promise to attacker-controlled contract `B` with a `.then()` callback batch on `A` itself containing a privileged native action (e.g. `AddKey` with `FullAccess`). Because the receipt's `predecessor_id` is `A`, `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`) is satisfied for that self-targeted `AddKey`.
3. Since `B`'s result hasn't arrived, `process_action_receipt` stores this callback as a `PostponedReceipt` keyed by `(receiver_id=A, receipt_id)`, plus `PendingDataCount` and `PostponedReceiptId` (`runtime/runtime/src/lib.rs:1608-1655`). These bytes are never reflected in `A.storage_usage`.
4. Attacker submits `DeleteAccountAction` on `A`. The size check only sees the small `Account`/keys footprint (well under 10,000 bytes) and passes; `remove_account` deletes `A`'s account/keys/contract/data but leaves the postponed rows.
5. Attacker (or anyone) issues `CreateAccountAction` to re-register the same account ID `A` — permitted because the name no longer exists and is long enough to not require the registrar.
6. Attacker, controlling `B`, now sends the awaited `DataReceipt` to `A`. `process_receipt`'s `Data` branch (`runtime/runtime/src/lib.rs:1396-1455`) finds the still-present `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` rows (never touched by deletion) and, once the count reaches 0, fetches and executes the stale postponed receipt via `apply_action_receipt`.
7. `apply_action_receipt` calls `get_account(state_update, account_id)` fresh (`runtime/runtime/src/lib.rs:853`), finding the *new* `A`. Each action in the stale receipt runs `check_account_existence`/`check_actor_permissions` against this new account; since the receipt's baked-in `predecessor_id` is still `A`, the self-targeted `AddKey` passes permission checks and installs the attacker's chosen key on the freshly (re)created account — regardless of who or what recreated it.

No existing check stops this: the deletion-size gate and `remove_account` cleanup both key off `Account.storage_usage`/known trie prefixes that exclude postponed-receipt state, and `validate_receipt`/`DeleteActionMustBeFinal` only validate the deleting receipt itself, not any receipts already parked in state for that receiver.

### Impact Explanation
This breaks the "delete means clean slate" invariant for account IDs. If the attacker or any party can predict/control reuse of a particular account ID (e.g. deterministically-named sub-accounts issued by a factory, or simply the attacker recreating their own ID and later transferring/selling it as "clean"), a stale privileged action queued before deletion executes against the new account owner without their consent, matching authorization escalation across accounts. It also demonstrates a metering/cleanup gap: the deletion-size gate can be satisfied while unaccounted state remains permanently resident and independently triggerable by the same attacker who controls the data source, which is a genuine "authorization exactness" violation of the deletion invariant.

### Likelihood Explanation
Fully reachable by an ordinary funded account with no special privileges: it only requires deploying a contract, using standard promise/callback host functions, and submitting ordinary `DeleteAccount`/`CreateAccount` transactions, all timed entirely by the attacker (since the attacker controls contract `B`, the data-receipt trigger is fired at will). The only precondition is registering a top-level name long enough to avoid the registrar restriction, which is a routine, cheap operation. Repeatable at will by the same attacker for demonstration; broader impact against an unwitting party requires that the reused account ID collide with a name a victim later creates for their own purposes.

### Recommendation
`remove_account` should also enumerate and remove `PostponedReceipt`, `PendingDataCount`, and `PostponedReceiptId` entries (and their receipt-owned data dependencies) for the deleted `account_id`, and/or `action_delete_account`'s size gate should include the byte cost of any outstanding postponed-receipt state for the account so deletion of accounts with large pending postponed state is rejected until the state is cleared naturally.

### Proof of Concept
Integration test (e.g. added to `runtime/runtime/src/tests/apply.rs` or `test-loop-tests/src/tests/create_delete_account.rs`, following the pattern of `test_instant_delete_account`/`test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Deploy `rs_contract` to account `A`; call a method that issues a promise batch to `A` itself with `input_data_ids` pointing at data from contract `B`, where the batch contains `AddKey` (attacker key, `FullAccess`) as its only/last action — confirm via state inspection that `TrieKey::PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` rows now exist for `A`.
2. From `A`, submit `DeleteAccountAction`; assert it succeeds (`ActionResult.result.is_ok()`), and directly query the trie to assert the postponed rows from step 1 are still present after `remove_account` runs.
3. Submit `CreateAccountAction` re-creating `A` with a different key.
4. Deliver the `DataReceipt` from `B` that the postponed receipt was waiting on; assert the postponed receipt executes (`PostponedReceipt` row removed) and that the attacker's `AddKey` from step 1 is now present on the recreated `A`'s access keys, without the new creator having authorized it.
5. Assert `Account.storage_usage` at step 2 never reflected the postponed-receipt bytes, confirming the metering gap that let the deletion-size check pass.
