### Title
Unguarded array indexing in `PrecompiledContracts.extractBytes32Array` and pre-Osaka `ValidateMultiSign`/`BatchValidateSign` calldata parsing allows attacker-controlled `ArrayIndexOutOfBoundsException` outside any local catch block - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`extractBytes32Array` indexes the `DataWord[] words` array using an attacker-supplied offset with no bounds check, unlike its sibling helpers `extractBytesArray` and `extractSigArray`, which both guard with `if (offset > words.length - 1) return new byte[0][];`. [1](#0-0) 
Likewise, `ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()` read `words[1]`, `words[2]`, `words[3]` directly from calldata-derived `DataWord[] words` before any length validation when the Osaka/TIP-854 ABI guard (`isValidAbiEncoding`) is not active. [2](#0-1) [3](#0-2) 

### Finding Description
`extractBytes32Array(words, offset)` is called only from `BatchValidateSign.doExecute`, with `offset = words[2].intValueSafe() / WORD_SIZE` — a value fully derived from attacker-controlled calldata passed to the `batchValidateSign` precompile (address `0x9`). [4](#0-3) 
Unlike `extractBytesArray`/`extractSigArray`, it performs no `offset > words.length - 1` check before doing `words[offset].intValueSafe()` and `words[offset + i + 1]`, so a crafted offset can throw `ArrayIndexOutOfBoundsException`. [5](#0-4) 

Separately, `ValidateMultiSign.execute()` reads `words[0]`, `words[1]`, `words[2]`, `words[3]` unconditionally when `VMConfig.allowTvmOsaka()` is false (i.e., the TIP-854 ABI-shape guard `isValidAbiEncoding` is skipped), and the call to `extractBytesArray`/`extractSigArray` at line 1072-1074 sits *before* the method's only local `try { ... } catch (Throwable t)` block (which starts at line 1082 and only wraps the signature-recovery/weight logic). A too-short `rawData` (fewer than 4 words) therefore throws `ArrayIndexOutOfBoundsException` from `words[3]` with no local catch. [6](#0-5) 

This is confirmed by the codebase's own test comments describing this exact pre-activation behavior: "before activation, malformed calldata reaches the legacy decoder... this precompile has no outer catch, so a too-short input raises inside the decoder; that is the documented pre-activation failure mode the TIP explicitly preserves." [7](#0-6) 
The TIP-854 fix (`isValidAbiEncoding` + outer-frame containment) was added specifically to stop this class of exception from escaping into the caller's frame, and the regression test explicitly exercises "malformed calldata" to `ValidateMultiSign`/`BatchValidateSign` to prove the outer VM frame is not corrupted post-activation. [8](#0-7) 

I was not able to fully trace, within the available iterations, how `Program.callToPrecompiledAddress` handles an uncaught `RuntimeException`/`ArrayIndexOutOfBoundsException` thrown out of a `PrecompiledContract.execute()` call in the **pre-Osaka** code path (i.e., whether it is caught at the `CALL` opcode boundary and simply reverts the calling frame, or whether it can escape further). The `AllowTvmOsakaTest`/`OperationsTest` tests only assert correct behavior *after* TIP-854 activation; I could not verify with certainty the outcome for nodes/networks where `allowTvmOsaka` is not yet enabled.

### Impact Explanation
Unlike the FFmpeg C out-of-bounds read (which can leak adjacent process memory into decoded video), Java's array bounds checking converts an OOB access into a thrown `ArrayIndexOutOfBoundsException` — there is no raw memory disclosure. The exploitable consequence in java-tron is therefore not information leakage but an **unhandled exception escaping a precompiled-contract call**, which — if not caught by the VM's opcode dispatch loop — could cause the current transaction's execution to abort in an unexpected way, or (if it propagates further than intended) affect a node processing untrusted contract calls. This is a lower-severity issue than the CVSS 9.1 FFmpeg analog it is modeled on, precisely because Java memory safety prevents true out-of-bounds *reads* of unrelated memory.

### Likelihood Explanation
Any unprivileged account can trigger this by deploying/calling a contract that issues a `CALL` to precompile address `0x9` (`batchValidateSign`) or `0xa` (`validateMultiSign`) with calldata shorter than 4-6 words, or with a crafted length/offset word. On networks where `allowTvmOsaka` (TIP-854) is not yet active, the guard (`isValidAbiEncoding`) is skipped entirely, so the vulnerable code path in `ValidateMultiSign.execute()` is reachable exactly as the test comments describe.

### Recommendation
- Add the same `if (offset > words.length - 1) return new byte[0][];`-style guard to `extractBytes32Array` as already exists in `extractBytesArray`/`extractSigArray`.
- Move the calldata-shape validation (`isValidAbiEncoding` equivalent) so it is unconditional (not gated behind `VMConfig.allowTvmOsaka()`), or ensure the entire `execute()`/`doExecute()` body — including the array-index calls at lines 1057-1077 and 1162-1177 — is wrapped in a single try/catch, matching the containment already added for the post-TIP-854 path.

### Proof of Concept
1. Deploy a contract that performs `staticcall`/`call` to precompile address `0x0000...0009` (`batchValidateSign`) with calldata equal to exactly `5 * 32` bytes (5 words) where word[2] encodes an offset that, once divided by 32, points past the actual word array length (e.g., set word[2] = a large value like `0x2000`).
2. On a chain/config where `VMConfig.allowTvmSelfdestructRestriction()`/`allowTvmOsaka()` guards are not yet active, this reaches `extractBytes32Array(words, words[2].intValueSafe() / WORD_SIZE)`, which indexes `words[offset]` beyond the array bound, throwing `ArrayIndexOutOfBoundsException`.
3. For `validateMultiSign` (address `0x...a`), call with calldata shorter than 128 bytes (fewer than 4 words) while `allowTvmOsaka()` is disabled; `words[3]` in `ValidateMultiSign.execute()` throws outside the method's only local try/catch, matching the documented "no outer catch" pre-activation behavior in `ValidateMultiSignContractTest.testTip854PreActivationNoOp`. [9](#0-8)

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
