### Title
Missing negative-balance guard in default (non-hardened) Bancor exchange calculation allows draining/unbacked-minting of pool reserves - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
`ExchangeCapsule.transaction()` computes the counter-asset amount for a TRC10/TRX AMM-style exchange trade using a Bancor-formula pricing function (`ExchangeProcessor`), which — like the reported `tradingFunction` in the external report — is a floating-point approximation that is not guaranteed to be correctly bounded near the edges of its domain (very small resulting reserve, large `sellTokenQuant` relative to `sellTokenBalance`). The code base itself acknowledges this exact class of bug: it added an explicit sanity check "reserve must not go negative" (`if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) throw ...`) but **only applies this check when `hardenedCalc` (`allowHardenExchangeCalculation`) is true**. In the default/legacy path (`hardenedCalc == false`, using `ExchangeProcessor`'s `double`/`Math.pow`-based Bancor formula), the resulting `newFirstTokenBalance`/`newSecondTokenBalance` are written to storage with **no bound check at all**, exactly mirroring the primitive bug where the boundary term of the invariant is silently treated as zero/undefined and the swap is wrongly accepted.

### Finding Description
`ExchangeCapsule.transaction()` selects between two pricing engines: [1](#0-0) 

- Non-hardened (default) path: `ExchangeProcessor.exchange()` uses `double` arithmetic and `Math.pow` (`exchangeToSupply`/`exchangeFromSupply`) to derive `buyTokenQuant`. [2](#0-1) 
- Hardened path: `SafeExchangeProcessor.INSTANCE` performs the same math with `BigDecimal`, and crucially, `ExchangeCapsule.transaction()` only checks `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) throw new ContractValidateException(...)` — this negative-balance guard is gated on `hardenedCalc`. [3](#0-2) 

`hardenedCalc` is only `true` when the chain parameter `allowHardenExchangeCalculation` is enabled, via `AbstractExchangeActuator.allowHarden()`: [4](#0-3) 

`ExchangeTransactionActuator.doValidate()` only checks that the pre-trade reserves are non-zero (`firstTokenBalance == 0 || secondTokenBalance == 0`) and that `anotherTokenQuant >= tokenExpected`; it never checks that the *post*-trade reserve remains positive, nor that `anotherTokenQuant` is strictly less than the current opposite-side reserve: [5](#0-4) 

`ExchangeTransactionActuator.execute()` then unconditionally credits `anotherTokenQuant` to the trader's account (via `addAssetAmountV2`/TRX balance credit) and persists the exchange's new (possibly negative, in the legacy/default double-math path) balances: [6](#0-5) 

Because the exchange pool holds no separate escrow account — the "reserves" are purely bookkeeping integers in `ExchangeCapsule` derived once at `ExchangeCreateActuator.execute()` by decrementing the creator's account balance/asset balance (no tokens are moved into a pool-owned address): [7](#0-6) 
any trade that produces `buyTokenQuant` computed inconsistently with the actual backing (i.e., exceeding or driving the counter-reserve negative due to floating point edge behavior in `ExchangeProcessor`) results in the trader's account being credited with TRX/TRC10 balance that has no corresponding decrease anywhere else in the system — i.e., unbacked token/TRX minting, directly analogous to "stealing pool reserves" via a wrongly computed invariant at the domain boundary of the pricing function.

### Impact Explanation
An unprivileged account broadcasting a single `ExchangeTransactionContract` transaction (via `TronJsonRpcImpl`/Wallet gRPC and `ExchangeTransactionActuator`) can, in the default (`allowHardenExchangeCalculation == 0`) configuration, cause the legacy floating-point `ExchangeProcessor` Bancor computation to under/overshoot near the boundary of its valid domain without any post-trade reserve sanity check. This can mint TRX or TRC10 token balance into the attacker's account that is not backed by any real decrease in the exchange reserves, i.e., unbacked balance creation / theft, a critical-risk finding matching the class of bug in the external report (wrong invariant computed at input bounds → resources drained/created beyond what is backed).

### Likelihood Explanation
Reaching this code path requires only a signed, unprivileged `ExchangeTransactionContract` transaction against an existing exchange pool — no special privileges are needed. `allowHardenExchangeCalculation` is a chain parameter that must be enabled to get the (partial) safety check; when it is `0` (the historical/legacy default), the vulnerable double/`Math.pow` path with zero bound checking is used for every trade, so likelihood of reachability is high. Actually triggering an exploitable edge case requires crafting `tokenQuant`/reserve ratios that push the Bancor approximation past its safe region (e.g., extremely large `sellTokenQuant` relative to `sellTokenBalance`, or very small reserves), which is feasible for an attacker who controls both the trade parameters and (via prior `ExchangeInject`/`ExchangeWithdraw`) the reserve ratios.

### Recommendation
Apply the same "resulting reserve must not go negative" (and ideally, "must not equal/exceed the opposite reserve") check unconditionally in `ExchangeCapsule.transaction()`, regardless of `hardenedCalc`, i.e., remove the `hardenedCalc &&` gate on the bound check at `ExchangeCapsule.java` lines 160-162. Additionally, in `ExchangeTransactionActuator.doValidate()`, explicitly reject trades where `anotherTokenQuant >= tokenBalance-of-the-side-being-bought`, and consider fully deprecating the unguarded floating-point path in favor of the hardened `BigDecimal`-based `SafeExchangeProcessor` for all trades.

### Proof of Concept
Conceptual (cannot be executed without the running node/test harness, but derivable from code):
1. Create an `Exchange` with `allowHardenExchangeCalculation = 0` (default) via `ExchangeCreateContract`, e.g. `firstTokenBalance = 1_000_000`, `secondTokenBalance = 1_000_000_000_000_000L` (as in `ExchangeProcessorTest`'s existing extreme-ratio test vectors, which already show large asymmetric outputs from `ExchangeProcessor.exchange`).
2. Broadcast an `ExchangeTransactionContract` selling `firstToken` with a `tokenQuant` chosen (per the existing `testStrictMath`/`testHardenedLargeQuant` style test data) such that `Math.pow`-based computation in `ExchangeProcessor.exchangeFromSupply` returns a `buyTokenQuant` that is at or exceeds `secondTokenBalance`.
3. `ExchangeTransactionActuator.doValidate()` does not check `anotherTokenQuant < secondTokenBalance`, so the trade is accepted; `execute()` credits the trader with `anotherTokenQuant` (potentially draining or exceeding the pool's tracked reserve), while `ExchangeCapsule.transaction()`'s only negative-balance guard is skipped because `hardenedCalc` is `false`.       boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
