### Title
Unrecovered per-packet callback in the `recvmmsg` batch-processing loop lets one malformed, pre-authentication UDP datagram crash the reader - ([File: udp/udp_linux.go])

### Summary
`StdConn.ListenOut` (Linux path) reads up to `u.batch` UDP datagrams with a single `recvmmsg` syscall and then iterates over them in a tight `for i := 0; i < n; i++` loop, invoking the caller-supplied `EncReader` callback `r(...)` for every datagram in the batch before returning to read the next batch. [1](#0-0) 

That callback is `f.readOutsidePackets`, which is wired up in `Interface.listenOut` and runs on completely unauthenticated, attacker-controlled bytes: it parses the wire header (`h.Parse(packet)`), and, depending on type, feeds the payload straight into handshake/certificate parsing (`hm.HandleIncoming` → `handshake.Machine.ProcessPacket` → `UnmarshalPayload`/certificate unmarshal) with no cert or CA-pool check yet performed. [2](#0-1) [3](#0-2) 

### Finding Description
This is the structural analog of the C4 finding: the loop at `udp_linux.go:184-192` performs, for every element in an attacker-influenced batch, a call into logic that is *reachable and controllable before any authentication step* (header parsing, handshake message parsing, certificate unmarshalling). Just as the Cudos `Gravity.sol` loop assumed every iteration's external call would succeed and had no isolation/error-handling for a single failing call, this Go loop assumes every iteration's callback will return normally and has no `recover()` to isolate a panic to a single datagram. A single crafted datagram in the middle of a batch that triggers a panic anywhere in the parse chain aborts the in-flight `for` loop, propagates out of `ListenOut`, and — because Go panics that escape a goroutine crash the entire process, not just that goroutine — brings down the whole `nebula` process, not merely the one connection/tunnel that sent the bad packet.

The repository's own `CHANGELOG.md` documents a history of exactly this class of bug being found and fixed reactively ("Fix an IPv6 extension-header length overflow…", "Reject malformed handshakes more reliably, including invalid ed25519 key lengths"), which shows the parse chain reachable from this loop has repeatedly contained input-dependent bugs. Because the loop has no isolation between iterations, any *future* parsing bug of the same shape (a slice out-of-bounds, an unchecked type assertion, a nil dereference on a malformed field) reachable from unauthenticated bytes is no longer a "drop this one packet" bug — it is a full daemon crash for every tunnel served by that process. [1](#0-0) 

I was not able to find any specific currently-exploitable panic in the parse chain during this review (the length checks in `header.Parse`, `parseV4`/`parseV6`, `UnmarshalPayload`, and the ASN.1/protobuf certificate unmarshallers all appear to bounds-check before indexing), so I cannot claim a concrete, already-triggerable crash today. The vulnerability being reported here is the *structural* absence of per-iteration fault isolation in the batch-receive loop, which is a lower-severity, defense-in-depth class of issue rather than a proven, ready-to-exploit crash.

### Impact Explanation
If any parsing/handling code reachable from `readOutsidePackets` (header parsing, handshake message parsing, certificate unmarshalling, or any of the many downstream branches) ever panics on attacker-supplied bytes — as has happened multiple times per the changelog — the panic is not contained to the single malformed datagram. It unwinds out of the `for i := 0; i < n; i++` loop and out of `ListenOut`, crashing the entire `nebula` process and every tunnel it serves, i.e., a remote, unauthenticated denial of service against the whole node rather than a single connection.

### Likelihood Explanation
Likelihood of a *specific* panic today is unproven (I could not find a currently reachable unhandled panic candidate in the time available). However, the general precondition — an unauthenticated attacker can place arbitrary bytes into this exact loop before any cert/CA check — is unconditionally true for every UDP datagram received, and the changelog shows this exact code path (header/extension parsing, handshake certificate handling) has had multiple prior crash-class bugs. So the likelihood of *some* future or latent bug of this shape being catastrophic (whole-process crash instead of one dropped packet) is elevated by the missing isolation.

### Recommendation
Wrap the per-datagram callback invocation inside the `ListenOut` batch loop (and the equivalent single-packet `ListenOut` implementations for the other platforms) in a `defer/recover` that logs and drops the individual malformed datagram instead of letting the panic escape the loop/process. This converts any current or future parsing panic in the unauthenticated pre-handshake path from a whole-node crash into a single dropped packet, matching the "assume calls can fail, isolate failures" mitigation recommended in the referenced report.

### Proof of Concept
Not established. I could not identify a currently reachable, unhandled panic in `header.Parse`, `handshake.UnmarshalPayload`, or the certificate unmarshallers during this review — all paths I inspected have explicit length/bounds checks. Confirming exploitability would require either (a) fuzzing the full `readOutsidePackets` call graph with malformed pre-authentication UDP payloads to find a live panic, or (b) treating this as a hardening recommendation rather than a demonstrated crash today. I flag this uncertainty explicitly rather than fabricate a working PoC.

func (u *StdConn) ListenOut(r EncReader) error {
	var ip netip.Addr
	msgs, buffers, names := u.PrepareRawMessages(u.batch)
	read := u.recvmmsg
	if u.batch == 1 {
		read = u.recvmsg
	}

	for {
		n, err := read(msgs)
		if err != nil {
			if errors.Is(err, unix.EINTR) {
				continue // interrupted by a signal, retry the read
			}
			// net.ErrClosed after Close() is teardown, absorbed by the caller's
			// closed flag like the other platforms; anything else is a real error.
			return err
		}

		for i := 0; i < n; i++ {
			// Its ok to skip the ok check here, the slicing is the only error that can occur and it will panic
			if u.isV4 {
				ip, _ = netip.AddrFromSlice(names[i][4:8])
			} else {
				ip, _ = netip.AddrFromSlice(names[i][8:24])
			}
			r(netip.AddrPortFrom(ip.Unmap(), binary.BigEndian.Uint16(names[i][2:4])), buffers[i][:msgs[i].Len])
		}
	}
}

func (f *Interface) readOutsidePackets(via ViaSender, out []byte, packet []byte, h *header.H, fwPacket *firewall.Packet, lhf *LightHouseHandler, nb []byte, q int, localCache firewall.ConntrackCache) {
	err := h.Parse(packet)
	if err != nil {
		// Hole punch packets are 0 or 1 byte big, so lets ignore printing those errors
		// TODO: record metrics for rx holepunch/punchy packets?
		if len(packet) > 1 {
			f.messageMetrics.RxInvalid(1)
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				f.l.Debug("Error while parsing inbound packet",
					"from", via,
					"error", err,
					"packet", packet,
				)
			}
		}
		return
	}

	if h.Version != header.Version {
		f.messageMetrics.RxInvalid(1)
		if f.l.Enabled(context.Background(), slog.LevelDebug) {
			f.l.Debug("Unexpected header version received", "from", via)
		}
		return
	}

	// Check before processing to see if this is a expected type/subtype
	if !h.IsValidSubType() {
		f.messageMetrics.RxInvalid(1)
		if f.l.Enabled(context.Background(), slog.LevelDebug) {
			f.l.Debug("Unexpected packet received", "from", via)
		}
		return
	}

	if !via.IsRelayed {
		if f.myVpnNetworksTable.Contains(via.UdpAddr.Addr()) {
			f.messageMetrics.RxInvalid(1)
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				f.l.Debug("Refusing to process double encrypted packet", "from", via)
			}
			return
		}
	}

	// don't keep Rx metrics for message type, since you can see those in the tun metrics
	if h.Type != header.Message {
		f.messageMetrics.Rx(h.Type, h.Subtype, 1)
	}

	// Unencrypted packets
	switch h.Type {
	case header.Handshake:
		f.handshakeManager.HandleIncoming(via, packet, h)
		return

	case header.RecvError:
		f.handleRecvError(via.UdpAddr, h)
		return
	}
