## #Vulnerability found

### Title
Wallet contract callback failure paths silently drop `caller_deposit` refund - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR eth-implicit `WalletContract::rlp_execute` entry point tracks an external caller's attached NEAR deposit in a `CallerDeposit` struct specifically so it can be refunded if the downstream cross-contract action fails [1](#0-0) . This refund is correctly performed in the final `rlp_execute_callback` on `PromiseResult::Failed` [2](#0-1) . However, two intermediate callbacks used for multi-step Ethereum-emulated flows — `address_check_callback` (address-registrar lookup for EOA base-token transfers) and `nep_141_storage_balance_callback` (NEP-141 storage check for ERC-20 transfers) — receive the same `caller_deposit` parameter but never use it when their respective cross-contract call fails; they simply return an error response, permanently stranding the caller's attached deposit in the wallet contract.

### Finding Description
`rlp_execute` accepts an attached deposit and, for external (non-self) callers, wraps it in `CallerDeposit::new` so it can later be refunded if the requested action fails to execute [3](#0-2) . Two of the multi-step transaction kinds route `caller_deposit` through intermediate promises before reaching `rlp_execute_callback`:

- `EOABaseTokenTransfer { address_check: Some(_), .. }` calls the address registrar and chains to `address_check_callback` [4](#0-3) .
- `ERC20Transfer` calls `storage_balance_of` on the token contract and chains to `nep_141_storage_balance_callback` [5](#0-4) .

In `address_check_callback`, if the registrar lookup itself fails (`PromiseResult::Failed`), the function returns an error `ExecuteResponse` immediately without ever inspecting or spending `caller_deposit`:
```rust
PromiseResult::Failed => {
    return PromiseOrValue::Value(ExecuteResponse {
        success: false,
        success_value: None,
        error: Some("Call to Address Registrar contract failed".into()),
    });
}
``` [6](#0-5) 

The same pattern exists in `nep_141_storage_balance_callback` for a failed `storage_balance_of` call:
```rust
PromiseResult::Failed => {
    return PromiseOrValue::Value(ExecuteResponse {
        success: false,
        success_value: None,
        error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
    });
}
``` [7](#0-6) 

In both cases the function simply returns without issuing `env::promise_batch_action_transfer` back to `caller_deposit.account_id`, unlike the correct handling in `rlp_execute_callback`'s `Failed` arm [8](#0-7) . Because the wallet contract already received and holds the attached deposit at the time `rlp_execute` was invoked, this deposit is retained by the contract with no code path to return it to the external caller.

This is structurally identical to the reported analog: a promise/action chain fails partway through, a "fallback"/failure-handling callback executes, and that specific failure branch omits the refund of the deposit that was tracked precisely for that purpose.

### Impact Explanation
Any external (non-self) relayer or caller that attaches NEAR to an `rlp_execute` call representing an `EOABaseTokenTransfer` with an address-check step, or an `ERC20Transfer`, permanently loses that attached deposit if the intermediary cross-contract call (`address_registrar.lookup` or `token.storage_balance_of`) fails — e.g., due to the target contract being paused, insufficient gas forwarded, or the registrar/token contract panicking. The funds are not burned by the protocol's normal deposit-refund mechanism (that only applies to the wallet contract's own top-level receipt, not to funds the contract chooses to hold and never returns) and are not recoverable by the caller, constituting a permanent freezing/loss of user funds.

### Likelihood Explanation
This requires an external caller (not the wallet owner) to submit or relay a transaction with a nonzero deposit for one of the two affected transaction kinds, and for the specific intermediate cross-contract call to fail. Registrar/NEP-141 lookups failing due to gas exhaustion, target account/contract issues, or malicious/broken NEP-141 tokens are realistic, non-privileged conditions reachable by ordinary users and relayers, since attaching a deposit and choosing the target contract are both caller-controlled.

### Recommendation
In `address_check_callback` and `nep_141_storage_balance_callback`, on the `PromiseResult::Failed` branch, refund `caller_deposit` exactly as `rlp_execute_callback` does before returning the error `ExecuteResponse`:
```rust
PromiseResult::Failed => {
    if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
        let refund_promise = env::promise_batch_create(&account_id);
        env::promise_batch_action_transfer(refund_promise, NearToken::from_yoctonear(yocto_near.into()));
    }
    return PromiseOrValue::Value(ExecuteResponse { .. });
}
```
Ensure all failure branches throughout the multi-step promise chains consistently honor the `CallerDeposit` refund contract.

### Proof of Concept
1. An external account `caller` (not the wallet owner) calls `wallet_contract.rlp_execute(target, tx_bytes_b64)` with an attached deposit, encoding an Ethereum-emulated `EOABaseTokenTransfer` where `target` is another eth-implicit address requiring an `address_check` (or an `ERC20Transfer`).
2. `inner_rlp_execute` builds `caller_deposit = CallerDeposit::new(&context)` since `predecessor_account_id != current_account_id` [9](#0-8) , and schedules `address_registrar.lookup(...).then(address_check_callback(target, action, caller_deposit))` [10](#0-9) .
3. The `address_registrar.lookup` cross-contract call fails (e.g., registrar contract runs out of gas or panics).
4. `address_check_callback` observes `PromiseResult::Failed` and returns an error response without ever creating a refund promise to `caller_deposit.account_id` [6](#0-5) .
5. The caller's attached NEAR deposit remains in the wallet contract's balance permanently, with no subsequent code path to reclaim it.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
```
