Audit Report

## Title
Curator deposit is permanently locked when refund/payout payment never resolves to `Succeeded` in `pallet-multi-asset-bounties::check_status` - (File: substrate/frame/multi-asset-bounties/src/lib.rs)

## Summary
`check_status` releases the `CuratorDeposit` held via `T::Consideration` only inside the `PaymentState::Succeeded` arm of both the `RefundAttempted` and `PayoutAttempted` branches. Every other resulting payment state (`Pending`, `Failed`, `Attempted`) simply re-enters the same `RefundAttempted`/`PayoutAttempted` status without touching `CuratorDeposit`, and no other extrinsic in the pallet unconditionally releases this deposit, so it can remain locked indefinitely if the payment never reaches `Succeeded`.

## Finding Description
In `check_status`, the `RefundAttempted` branch only calls `CuratorDeposit::<T, I>::take(...)` and `T::Consideration::drop(curator_deposit, curator)` inside the `PaymentState::Succeeded` match arm; the `Pending | Failed | Attempted` arm returns to `BountyStatus::RefundAttempted` unchanged, leaving `CuratorDeposit` untouched [1](#0-0) . The identical pattern exists in the `PayoutAttempted` branch: `CuratorDeposit::<T, I>::take` and `T::Consideration::drop` only occur on `PaymentState::Succeeded`, while `Pending | Failed | Attempted` loop back into `PayoutAttempted` with the deposit intact [2](#0-1) . The only remediation mechanism visible in the pallet is `retry_payment`, which retries the underlying payment attempt but does not itself release the `CuratorDeposit` and depends on the same `Succeeded` transition to ever unlock funds [3](#0-2) . If the configured `T::Paymaster`/`T::Consideration` backend for a given `asset_kind`/beneficiary combination never reports `Succeeded` (e.g. an unsupported asset kind or a beneficiary account state that can never satisfy the payment predicate), `check_status` and `retry_payment` will cycle indefinitely between `Pending`/`Failed`/`Attempted` without ever executing the deposit-release code, and there is no permissionless or governance path in this pallet analogous to `pallet-bounties`'s `reclaim_bounty_funds` to sweep the stranded `CuratorDeposit`.

## Impact Explanation
This is a permanent user-fund lock: the curator's native balance held via `T::Consideration` as `CuratorDeposit` becomes permanently inaccessible with no code path in the pallet to release it once a refund/payout enters a state where the payment backend never resolves to `Succeeded`. This directly matches the "permanent user-fund or bridge-state lock" item in the Polkadot SDK impact gate, and is structurally the same defect class that `pallet-bounties` needed `reclaim_bounty_funds` and the `close_bounty` refund fix for [4](#0-3) [5](#0-4) , and the same class `pallet-multi-asset-bounties` itself already had to patch once for `unassign_curator` leaking the curator deposit [6](#0-5) .

## Likelihood Explanation
No privileged actor, governance action, or compromised relayer/validator is required. Any curator whose bounty enters `RefundAttempted` or `PayoutAttempted` against an asset kind or beneficiary combination that the configured `T::Paymaster` cannot definitively resolve to `Succeeded` will have their deposit stuck, since `check_status`'s only exit path for the deposit is the `Succeeded` arm and `retry_payment` cannot change that outcome if the underlying payment condition is structurally unsatisfiable.

## Recommendation
Add a permissionless or bounded-retry-exhaustion path to release/reclaim `CuratorDeposit` entries independent of the `Succeeded` payment branch — e.g., allow the curator (or `RejectOrigin`) to reclaim the deposit once a bounty has been definitively closed/removed, or once a payment has failed beyond a maximum retry count, mirroring the `reclaim_bounty_funds` pattern added to `pallet-bounties`.

## Proof of Concept
1. Create a multi-asset bounty and assign/accept a curator so `CuratorDeposit` is populated via `T::Consideration`.
2. Call `close_bounty` (or `award_bounty`) to drive the bounty into `RefundAttempted`/`PayoutAttempted`, as shown in `close_bounty` at [7](#0-6) .
3. Configure/observe a paymaster whose `check_payment` never returns `Success` for the chosen `asset_kind`/beneficiary.
4. Repeatedly call `check_status`; observe it always lands in the `Pending | Failed | Attempted` arm shown at [8](#0-7) , and `CuratorDeposit::<T, I>` for that bounty is never `take`n nor dropped, with no other extrinsic available to release it.
