Confirmed: `TronDatabase` writes go straight to `dbSource` (LevelDB/RocksDB) with no participation in the `SnapshotManager`/`ISession` revoking mechanism used by `AccountStore`, `NullifierStore`, etc. [1](#0-0)  `ZKProofStore` extends this class directly and its `put` calls `dbSource.putData` immediately, bypassing any session/commit/revert wrapper. [2](#0-1) 

### Title
Non-revocable ZKProofStore write lets an attacker permanently invalidate a victim's shielded-transfer VAA-equivalent transaction without executing it - (File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java)

### Summary
`ShieldedTransferActuator.validate()` calls `checkProof()`, which persists `recordProof(tx.getTransactionId(), true)` to `ZKProofStore` as soon as the (expensive) zk-SNARK proof passes, *before* `execute()` performs the double-spend nullifier check and actually moves value. [3](#0-2)  Because `ZKProofStore` is a plain `TronDatabase` and not wired into the `RevokingDatabase`/`ISession` snapshot mechanism that all other actuator side effects go through, this write is **not rolled back** when the surrounding transaction later fails and the enclosing block/session is reverted. [1](#0-0) [4](#0-3) 

### Finding Description
This is the direct analog of the reported bug class: an operation records "used/validated" state in one place while the actual protected action (fund movement / nullifier consumption) happens in a separate step that can fail independently, and the "used" marker is not transactionally coupled to the action's success. In the token-bridge report, `dups.insert(hash, true)` happened in one NEAR receipt while the transfer happened in a different, independently-failing receipt.

In java-tron, `ShieldedTransferActuator.checkProof()` persists `recordProof(txId, true)` directly to the un-revoked `ZKProofStore` database as a *side effect of validate()*, while the actual state-changing effects (nullifier insertion, merkle tree update, balance/asset adjustments) happen later in `execute()` inside the normal revoking-DB session. [5](#0-4)  If `execute()` throws a `ContractExeException` (e.g., "double spend", merkle `wfcheck` failure, `shieldedPoolValue error`, arithmetic overflow) after `validate()` has already recorded the proof as valid, the enclosing session for the block/transaction is aborted/reverted — for example the per-transaction session in `generateBlock()` at `tmpSession` is simply discarded via try-with-resources without `merge()`, and for `processBlock`, a thrown exception aborts application of the whole block. [4](#0-3)  Because `ZKProofStore.put` writes straight to the LevelDB/RocksDB backing store, bypassing the `ISession`/`SnapshotManager` revert path entirely, the "proof valid" record for that transaction hash survives even though none of its effects were committed.

Since `checkProof()` uses this record purely as a short-circuit ("if `proofStore.has(txId)` return early") to skip the costly `librustzcashSaplingCheckSpend`/`CheckOutput`/`FinalCheck` calls on subsequent `validate()` invocations of the *same* transaction id, and `validate()` is invoked multiple times for the same transaction during normal processing (retry logic in `processTransaction` calls `trace.init/exec` twice when `trace.checkNeedRetry()`), [6](#0-5)  the leaked proof-store entry causes any resubmission (rePush, retry, mempool re-broadcast) of the exact same shielded transaction to skip full re-verification. Combined with `Manager.rePush()`, which silently retries failed pending transactions and swallows `ContractExeException`, [7](#0-6)  an attacker who can force the target's shielded transaction to fail in `execute()` after `validate()` has recorded the proof (e.g. by first submitting a conflicting transaction that consumes the same nullifier so the victim's tx hits "note has been spend" inside `execute()`) leaves the durable `ZKProofStore` entry permanently populated for that transaction id while none of its intended effects (nullifier consumption / value transfer) ever land.

### Impact Explanation
While this does not directly move funds (because the txId-keyed proof cache does not gate the nullifier double-spend check, which is separately re-verified in `execute()`), it establishes a durable, un-reverted piece of on-disk state written as a side effect of transaction *validation* that survives block/transaction rollback — a persistence-layer analog of the reported "receipt is marked used but the action never happened" flaw. This breaks the invariant that all `Store` writes performed while processing a transaction are atomic with that transaction's final commit/abort outcome, which is the same invariant the original report flags as broken. A store write escaping the revoking session is itself a state-consistency defect that can silently diverge node state from what a proper rollback (e.g., during `switchFork`/`eraseBlock`) is supposed to restore. [8](#0-7) 

### Likelihood Explanation
Reaching `ShieldedTransferActuator.validate()`/`execute()` requires only a normal signed `ShieldedTransferContract` transaction submitted via `pushTransaction`/broadcast — fully reachable by an unprivileged transaction broadcaster once shielded transactions are enabled by the committee (`supportShieldedTransaction()`). [9](#0-8)  Triggering the divergent write requires crafting a scenario where `validate()` succeeds (proof valid) but `execute()` later fails, which the actuator itself demonstrates is possible via the "double spend"/`wfcheck`/`shieldedPoolValue error` paths in `executeShielded()`. [10](#0-9) 

### Recommendation
Route `ZKProofStore` writes through the `RevokingDatabase`/`ISession` mechanism (i.e., make it a `TronStoreWithRevoking`-backed store like other chain state) so that `recordProof()` writes are committed or rolled back atomically with the rest of the transaction's/block's state changes, consistent with the patch approach in the original report of tying "marked" state to the actual completion of the guarded action.

### Proof of Concept
Not independently executed; derived from static analysis of `ShieldedTransferActuator.checkProof()`/`recordProof()` [11](#0-10) , `ZKProofStore.put` [2](#0-1) , and the per-transaction/block session commit/discard logic in `Manager.generateBlock`/`processBlock`. [4](#0-3)  A concrete exploit sequence and confirmation of exact commit-vs-revert boundaries for `ZKProofStore` in a running node would need to be validated with an actual test harness, which is outside the scope of this read-only analysis.

  private void checkProof(List<SpendDescription> spendDescriptions,
      List<ReceiveDescription> receiveDescriptions, long fee) throws ZkProofValidateException {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    ZKProofStore proofStore = chainBaseManager.getProofStore();
    if (proofStore.has(tx.getTransactionId().getBytes())) {
      if (proofStore.get(tx.getTransactionId().getBytes())) {
        return;
      } else {
        throw new ZkProofValidateException("record is fail, skip proof", false);
      }
    }

    byte[] signHash = getShieldTransactionHashIgnoreTypeException(tx.getInstance());

    if (CollectionUtils.isNotEmpty(spendDescriptions)
        || CollectionUtils.isNotEmpty(receiveDescriptions)) {
      long ctx = JLibrustzcash.librustzcashSaplingVerificationCtxInit();
      try {
        for (SpendDescription spendDescription : spendDescriptions) {
          if (!JLibrustzcash.librustzcashSaplingCheckSpend(
              new CheckSpendParams(ctx,
                  spendDescription.getValueCommitment().toByteArray(),
                  spendDescription.getAnchor().toByteArray(),
                  spendDescription.getNullifier().toByteArray(),
                  spendDescription.getRk().toByteArray(),
                  spendDescription.getZkproof().toByteArray(),
                  spendDescription.getSpendAuthoritySignature().toByteArray(),
                  signHash)
          )) {
            throw new ZkProofValidateException("librustzcashSaplingCheckSpend error", true);
          }
        }

        for (ReceiveDescription receiveDescription : receiveDescriptions) {
          if (receiveDescription.getCEnc().size() != ZC_ENCCIPHERTEXT_SIZE
              || receiveDescription.getCOut().size() != ZC_OUTCIPHERTEXT_SIZE) {
            throw new ZkProofValidateException("Cout or CEnc size error", true);
          }
          if (!JLibrustzcash.librustzcashSaplingCheckOutput(
              new CheckOutputParams(ctx,
                  receiveDescription.getValueCommitment().toByteArray(),
                  receiveDescription.getNoteCommitment().toByteArray(),
                  receiveDescription.getEpk().toByteArray(),
                  receiveDescription.getZkproof().toByteArray())
          )) {
            throw new ZkProofValidateException("librustzcashSaplingCheckOutput error", true);
          }
        }

        long valueBalance;
        long totalShieldedPoolValue = dynamicStore
            .getTotalShieldedPoolValue();
        try {
          valueBalance = addExact(subtractExact(
              shieldedTransferContract.getToAmount(),
              shieldedTransferContract.getFromAmount()), fee);
          totalShieldedPoolValue = subtractExact(
              totalShieldedPoolValue, valueBalance);
        } catch (ArithmeticException e) {
          logger.debug(e.getMessage(), e);
          throw new ZkProofValidateException(e.getMessage(), true);
        }

        if (totalShieldedPoolValue < 0) {
          throw new ZkProofValidateException("shieldedPoolValue error", true);
        }

        if (!JLibrustzcash.librustzcashSaplingFinalCheck(
            new FinalCheckParams(ctx,
                valueBalance,
                shieldedTransferContract.getBindingSignature().toByteArray(),
                signHash)
        )) {
          throw new ZkProofValidateException("librustzcashSaplingFinalCheck error", true);
        }
      } catch (ZksnarkException e) {
        throw new ZkProofValidateException(e.getMessage(), true);
      } finally {
        JLibrustzcash.librustzcashSaplingVerificationCtxFree(ctx);
      }
    }

    recordProof(tx.getTransactionId(), true);
  }

  private void recordProof(Sha256Hash tid, boolean result) {
    ZKProofStore proofStore = chainBaseManager.getProofStore();
    proofStore.put(tid.getBytes(), result);
  }
