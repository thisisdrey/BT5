### Title
Unchecked long-overflow in freeze duration arithmetic can produce a corrupted (negative) resource expiration time - ([File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java])

### Summary
The reported CVE-2020-25691 concerns darkhttpd mishandling an attacker-supplied, unbounded date value (a large file modification date), which is never range-checked before being used in date arithmetic, leading to broken error handling and a crash. The closest reachable analog in java-tron is `FreezeBalanceActuator`, where an unprivileged transaction broadcaster fully controls `frozenDuration` inside a `FreezeBalanceContract`, and that value is combined with the current block time using plain (non-overflow-checked) arithmetic to compute the resource `expireTime`.

### Finding Description
`FreezeBalanceActuator.execute()` computes: [1](#0-0) 
using plain `+`/`*`, with no `Math.addExact`/`Math.multiplyExact`-style guard, unlike the equivalent code path in `AssetIssueActuator`, which was explicitly hardened against this exact bug class: [2](#0-1) 

The only guard against an attacker choosing a `frozenDuration` large enough to overflow `now + duration` is the min/max day bound check in `FreezeBalanceActuator.validate()`: [3](#0-2) 
That bound check is itself gated by a flag explicitly commented as being for test use: [4](#0-3) 
`needCheckFrozeTime = CommonParameter.getInstance().getCheckFrozenTime() == 1 //for test`. If this flag is not `1` in a given deployment/configuration, the min/max day bound is skipped entirely and `frozenDuration` is unconstrained, allowing `now + frozenDuration * FROZEN_PERIOD` to overflow `long` and wrap to a negative `expireTime`, which is then persisted via `accountCapsule.setFrozenForBandwidth/setFrozenForEnergy/setFrozenForTronPower`.

A similarly-shaped, unguarded computation exists in the TVM-reachable native contract path `FreezeBalanceProcessor.execute()`: [5](#0-4) 

### Impact Explanation
If `expireTime` overflows to a negative value, subsequent unfreeze logic (`UnfreezeBalanceActuator`, `UnfreezeBalanceV2Processor`) compares `next.getExpireTime() <= now`, which would immediately evaluate `true` for a negative/overflowed timestamp — effectively bypassing the intended freeze lock-up period. This corresponds to the rules' accepted impact of "permanent freezing of funds" or "unbacked balance"/stake-weight corruption (since `addTotalWeight` and voting weight are derived from the frozen balance and its expiration), not merely a crash.

### Likelihood Explanation
Exploitability hinges entirely on whether `CommonParameter.getCheckFrozenTime()` defaults to a value other than `1` in a given node configuration — I was not able to confirm the production default for this flag within the available search budget (the field is described in-code only as "for test"). If the default is `1` in all production configurations, the bound check (`minFrozenTime`/`maxFrozenTime`) is always active and this specific path is not exploitable via `FreezeBalanceActuator`. The TVM-facing `FreezeBalanceProcessor` path could not be fully verified for an equivalent `validate()` bound check within this session — only its `execute()` method (which lacks an overflow guard) was retrieved.

### Recommendation
- Confirm the production default of `CommonParameter.getCheckFrozenTime()`; if it can be `0` in any deployed configuration, either remove the test-only bypass or enforce the min/max day bound unconditionally.
- Add explicit overflow-checked arithmetic (`Math.addExact`/`StrictMathWrapper.addExact`, as already done in `AssetIssueActuator`) around all `now + duration`/`frozenDuration * FROZEN_PERIOD` computations in `FreezeBalanceActuator`, `FreezeBalanceProcessor`, `UnfreezeBalanceV2Actuator.calcUnfreezeExpireTime`, and `UnfreezeBalanceV2Processor.calcUnfreezeExpireTime`.
- Validate `FreezeBalanceProcessor`'s corresponding `validate()` method (not reviewed in this session) for the same bound enforcement as the legacy actuator.

### Proof of Concept
Could not be fully constructed/verified in this session: reproduction requires confirming (a) the deployed value of `CommonParameter.getCheckFrozenTime()`, and (b) whether `FreezeBalanceProcessor`'s TVM-facing validation applies the same day-count bound as `FreezeBalanceActuator.validate()`. Both require reading additional source not retrieved (`FreezeBalanceProcessor`'s `validate()` method and the `CommonParameter` default field definition/config parsing) — I recommend a Devin session with full repository access to pull `CommonParameter.java` (`checkFrozenTime` field default) and the full `FreezeBalanceProcessor.java` to confirm exploitability before treating this as confirmed-high severity.
