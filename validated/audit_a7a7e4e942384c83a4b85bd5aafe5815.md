### Title
Unbounded blocking DNS resolution lets a single malicious peer hang the shared DNS resolver thread, delaying all peers' hostname resolution - (File: stackslib/src/net/dns.rs)

### Summary
`DNSResolver::resolve` performs a **synchronous, blocking** `to_socket_addrs()` call to resolve a hostname supplied by a remote, untrusted peer (via its handshake `data_url`, or via Atlas/StackerDB hint-replica URLs), with no per-lookup execution timeout. This is analogous to CVE-2017-9804: a party supplies a URL/hostname designed to make the validating/resolving component do disproportionate work relative to a normal request, and because resolution runs on a single shared background thread serving *all* peers, one slow-resolving or intentionally-stalling attacker-controlled DNS name can block resolution progress for every other queued lookup.

### Finding Description
`DNSRequest::is_timed_out()` only gates whether a *queued* request is dropped before being handed to `resolve()`; once `resolve()` is invoked it calls the blocking OS resolver API `(req.host.as_str(), req.port).to_socket_addrs()` with no timeout wrapper [1](#0-0) . The resolver's `thread_main` loop dequeues and processes requests one at a time from a single `VecDeque`, so if one hostname resolution blocks (e.g., pointing to a nameserver an attacker controls that intentionally never responds, or a name chain engineered to be maximally slow to resolve), every other request already queued or arriving afterward is starved until the OS resolver call eventually returns/times out at the OS/libc level (which can be tens of seconds to minutes, and is not controlled by this code) [2](#0-1) .

The hostname is attacker-controlled: a remote peer's data URL — set from that peer's own handshake `HandshakeData` — is parsed and, if it is a domain (not a literal IP), queued directly for resolution by the node's shared `DNSClient`/`DNSResolver` pair used across all peer conversations, block downloads, mempool sync, and Atlas attachment fetching [4](#0-3) . The same DNS client/resolver pair also processes Atlas attachment URLs [5](#0-4)  and epoch2x block-downloader URLs [6](#0-5) , all funneling into the same single-threaded resolver.

### Impact Explanation
This breaks the assumption that DNS-lookup capacity is fairly shared/bounded per requester: a single unprivileged remote peer can starve DNS resolution progress for all other peers' hostnames by supplying one pathologically slow-to-resolve `data_url` in its handshake. Because the resolver is single-threaded and processes its queue serially, this is a low-cost way to delay/deny legitimate peer discovery, block download via HTTP relay hints, mempool sync peer resolution, and Atlas attachment fetching that depend on DNS names, for the duration of the stalled call. This matches the "bounded compute DoS on a read endpoint" class, though the actual wall-clock impact is bounded by the OS resolver's own default timeout rather than being unbounded/permanent.

### Likelihood Explanation
Moderate. Exploitation only requires a peer to complete a handshake and advertise a `data_url` with a domain name it controls (or a domain configured to resolve very slowly, e.g., via a non-responsive/black-holed authoritative nameserver). No special privileges or node secrets are required — any p2p peer can supply arbitrary handshake data. Repeated advertisement across reconnects/multiple peer identities could compound the effect, though the single-thread architecture caps how many concurrent stalls exist (only one lookup is ever in-flight in `resolve()` at a time).

### Recommendation
Wrap the blocking resolution call in `DNSResolver::resolve` with an explicit, short timeout (e.g., resolve on a helper thread/task and select against `req.timeout`), so a single slow/malicious hostname cannot block the shared queue beyond the request's own declared deadline. Consider moving resolution off a single serial thread onto a small bounded pool so that one stalled lookup cannot delay unrelated peers' resolutions.

### Proof of Concept
1. Run a Stacks node under test with the DNS resolver enabled.
2. Have an attacker-controlled peer complete a handshake advertising `data_url = "http://slow-attacker-controlled-domain.example:80/"`, where `slow-attacker-controlled-domain.example`'s authoritative nameserver is configured to accept the query but never respond (simulating a hung resolution).
3. Observe `try_resolve_data_url_host` queue this hostname via `dns_client.queue_lookup` [7](#0-6) .
4. Concurrently have legitimate peers advertise valid, quickly-resolving `data_url`s and observe that their DNS resolution stalls behind the queue while the resolver thread is blocked inside `to_socket_addrs()` for the attacker's hostname in `DNSResolver::resolve` [1](#0-0) , confirming serialized blocking with no per-call timeout enforcement.
