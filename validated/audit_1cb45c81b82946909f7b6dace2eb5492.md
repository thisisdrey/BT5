### Title
Permissionless pre-funding of the deterministic TIP-2935 `HistoryBlockHashUtil` address causes permanent freezing of an account's TRX/resources when converted in-place to a system contract - (File: `framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java`)

### Summary
`HistoryBlockHashUtil.deploy()` — invoked once from `ProposalService.process()` when the `ALLOW_TVM_PRAGUE` proposal activates — installs a fixed system contract (code + `ContractCapsule`) at a hardcoded, publicly known address, `HISTORY_STORAGE_ADDRESS`. Any pre-existing `AccountCapsule` at that address is mutated in place: its type is flipped to `Contract` and its delegated-resource fields are cleared, but its balance/asset/frozen state is preserved and the contract is thereafter driven only by the fixed 83-byte `HISTORY_STORAGE_CODE` bytecode, which has no transfer/withdraw entry point. [1](#0-0) 

### Finding Description
Anyone can send TRX (or freeze/delegate resources) to `HISTORY_STORAGE_ADDRESS` before the `ALLOW_TVM_PRAGUE` proposal is applied — the address is deterministic, published in source, and requires no private key to receive funds (comment: "anyone can transfer TRX there to activate it as an EOA"). [2](#0-1) 

When the proposal activates, `deploy()` checks only whether `CodeStore`/`ContractStore` already holds *code* at that address; it does not check whether the `AccountStore` already holds balance/resources there. If an account exists, it is upgraded from `Normal` to `Contract` type and its `code`/`SmartContract` metadata is installed, while the account's TRX balance and other state are explicitly preserved ("mirroring the CREATE2 collision path... preserving balance / asset state"): [3](#0-2) 

The deployed bytecode, `HISTORY_STORAGE_CODE`, is a minimal EIP-2935-style getter/setter for historical block hashes — it exposes no function to withdraw TRX, no `SELFDESTRUCT`, and no owner-controlled rescue path: [4](#0-3) 

The `SmartContract` metadata records `HISTORY_DEPLOYER_ADDRESS` as `originAddress` — an address with no known private key, taken from Ethereum's EIP-2935 keyless deploy sender — so no account can ever administratively act as owner of this contract to recover funds: [5](#0-4) 

This mirrors the root cause of the Meerkat Finance rug pull at the structural level: an in-place "upgrade" of an account/vault's code (there, via `upgradeTo()`; here, via converting an `AccountCapsule` to `AccountType.Contract` and installing new bytecode) that preserves the underlying balance but replaces the controlling logic with code that offers no legitimate path back to the original party, resulting in funds becoming permanently unreachable. The distinguishing detail here is that java-tron performs the equivalent of a proxy-upgrade "in place" against an already-funded account, at the protocol level (`Manager`/`ProposalService` block application), without checking or protecting any pre-existing balance/resource state at that address before doing so.

### Impact Explanation
Any TRX, frozen resources (bandwidth/energy), delegated resources, or TRC10 assets sent to `HISTORY_STORAGE_ADDRESS` prior to `ALLOW_TVM_PRAGUE` activation become permanently inaccessible once the account is converted to `AccountType.Contract` with fixed non-withdrawable bytecode — a concrete case of "permanent freezing of funds," which is an accepted impact category per the validation rules. Because the target address is public (hardcoded in the codebase and documented as EIP-2935-compatible), and activation timing of governance proposals is generally known or predictable in advance, an attacker (or an unwitting user, e.g. tricked via a phishing "deposit to this special address" scheme) can lock TRX there, and it will be permanently unrecoverable after the proposal fires — the resulting contract account has no code path to move funds out.

### Likelihood Explanation
Triggering the precondition (sending TRX/freezing/delegating to a known address) requires only an ordinary, unprivileged TRX transfer or freeze transaction — reachable by any transaction broadcaster with no special permissions. The only requirement is that the sender act before the one-time `ALLOW_TVM_PRAGUE` proposal is approved and applied by the committee; since committee proposals and their approval windows are visible on-chain, an attacker can time the deposit deliberately. This is a Medium-severity design flaw (single trigger point, one-time, requires proposal to activate) rather than a High/Critical uncontrolled asset drain, since there is no attacker-controlled withdrawal — the impact is fund freezing, not theft.

### Recommendation
Before converting the account at `HISTORY_STORAGE_ADDRESS` in `HistoryBlockHashUtil.deploy()`, check if it already holds a non-zero balance, frozen resources, votes, or asset holdings. If so, either (a) skip the in-place conversion entirely (treat it the same as the "foreign code" collision branch and log a warning without installing the system contract at that address), or (b) refund/migrate any pre-existing balance/resources to the account's original state (e.g., transfer balance to the black hole or back to depositors is not feasible without a bijective mapping, so skipping is the safer choice), consistent with how the `CREATE2` collision logic in `Program.createContractImpl` already refuses to reuse addresses with existing contract code. Additionally, document/guard against pre-funding by disallowing normal transfers to addresses that are reserved as pending system-contract activation targets.

### Proof of Concept
1. Before the SR committee approves and the chain applies the `ALLOW_TVM_PRAGUE` proposal, an unprivileged account submits a normal `TransferContract` sending TRX to `HISTORY_STORAGE_ADDRESS` (`410000f90827f1c53a10cb7a02335b175320002935`), creating a `Normal` `AccountCapsule` there with a non-zero balance.
2. The SR committee's proposal setting `ALLOW_TVM_PRAGUE=1` reaches quorum and is applied during maintenance-time block processing via `ProposalService.process()`, which calls `HistoryBlockHashUtil.deploy(manager)`. [6](#0-5) 
3. `deploy()` finds no code/contract at the address (only a funded `AccountCapsule`), so it proceeds to write `CodeCapsule`/`ContractCapsule` and flips the existing account's type to `Contract`, preserving its balance. [7](#0-6) 
4. From this point on, the account at `HISTORY_STORAGE_ADDRESS` only executes the fixed `HISTORY_STORAGE_CODE`, which has no logic to transfer TRX out; the original depositor's funds are permanently stranded, with no owner (the recorded `originAddress` has no known private key) able to recover them.

```java
  public static void deploy(Manager manager) {
    if (manager.getCodeStore().has(HISTORY_STORAGE_ADDRESS)
        || manager.getContractStore().has(HISTORY_STORAGE_ADDRESS)) {
      logger.warn("TIP-2935: foreign state at {}, skipping deploy",
          Hex.toHexString(HISTORY_STORAGE_ADDRESS));
      return;
    }

    manager.getCodeStore().put(HISTORY_STORAGE_ADDRESS,
        new CodeCapsule(HISTORY_STORAGE_CODE));
    manager.getContractStore().put(HISTORY_STORAGE_ADDRESS,
        new ContractCapsule(HISTORY_STORAGE_CONTRACT));

    AccountCapsule account = manager.getAccountStore().get(HISTORY_STORAGE_ADDRESS);
    boolean accountExisting = account != null;
    if (!accountExisting) {
      account = new AccountCapsule(HISTORY_STORAGE_ACCOUNT);
    } else {
      account.updateAccountType(Protocol.AccountType.Contract);
      account.clearDelegatedResource();
    }
    manager.getAccountStore().put(HISTORY_STORAGE_ADDRESS, account);

    // Flip the install marker only after all three store writes succeed; this
    // gates the per-block write() path so a skipped deploy never mutates
    // foreign storage. Any node-local exception above propagates and rolls
    // the marker back together with the partial writes via the revoking session.
    manager.getDynamicPropertiesStore().saveBlockHashHistoryInstalled(1L);

    logger.info("TIP-2935: deployed BlockHashHistory at {} (preExistingAccount={})",
        Hex.toHexString(HISTORY_STORAGE_ADDRESS), accountExisting);
  }
```
