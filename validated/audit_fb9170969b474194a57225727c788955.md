### Title
Unbounded attachment size accepted in `extend_with_attachments` download path bypasses `attachments_max_size` cap - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` (stackslib/src/net/atlas/download.rs:530-558) inserts a remote peer's `GetAttachmentResponse.attachment` into `self.attachments` without ever checking `response.attachment.content.len()` against `AtlasConfig.attachments_max_size`. The downstream persistence call, `AtlasDB::insert_instantiated_attachment` (stackslib/src/net/atlas/db.rs:576-592), likewise performs an unconditional `INSERT OR REPLACE` with no size check, so an oversized blob served by a single malicious/compromised peer is written straight into `AtlasDB`.

### Finding Description
The size-bound enforcement that exists in the codebase, `AtlasDB::should_keep_attachment` (stackslib/src/net/atlas/db.rs:249-266), explicitly checks `attachment.content.len() as u32 > self.atlas_config.attachments_max_size` and logs "will discard posted attachment - attachment too large." Its own log message and the calling context (the `POST /v2/attachments/new` handler) show it is a guard on locally *posted* attachments, not on attachments *pulled from remote peers* via the download state machine.

The download path is: a `content_hash` (`Hash160`, fixed 20 bytes) is committed on-chain via a contract-call transaction and queued as an `AttachmentInstance` (`AtlasDB::queue_attachment_instance`). The `AttachmentsBatchStateMachine` (download.rs:580-661) then issues `GET /v2/attachments/{hash}` requests to peer URLs advertised in the attachment inventory, and when a response decodes successfully via `decode_atlas_get_attachment`, `extend_with_attachments` does:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    ...
}
```
with no length check at all (download.rs:547-549). Because `content_hash` is only a 20-byte digest, it places no bound on the size of the preimage content that hashes to it — an attacker who controls the on-chain commitment (a normal, unprivileged contract-call transaction, e.g. a BNS name update) can choose an arbitrarily large attachment body and simply serve it from a peer they control. The result flows on to `AtlasDB::insert_instantiated_attachment`, which persists `attachment.content` to the `attachments` SQLite table with no size gate whatsoever (db.rs:576-592).

### Impact Explanation
A single unprivileged attacker who (a) can get one contract-call transaction mined (committing an arbitrary `Hash160`) and (b) runs a peer server that answers the resulting `GET /v2/attachments/{hash}` request with an oversized body, causes every downloading node's `AtlasDB` to store a blob of essentially unbounded size, in violation of the configured `attachments_max_size` cap. This is a remote, unauthenticated write of oversized data into node state/disk, repeatable per attachment instance, and matches the Critical category "unauthenticated/unauthorized write to state" and resource-exhaustion impact tied to no meaningful on-chain size commitment.

### Likelihood Explanation
Preconditions are modest: the attacker needs one mined contract-call transaction establishing an `AttachmentInstance` (ordinary user capability, not privileged) and control of a peer/HTTP server that other nodes will query for that hash. No secret, admin role, or protocol-level trust is required — any node running the Atlas downloader will attempt to fetch attachments referenced by on-chain events from whatever peer URL is advertised. The exploit is cheap and repeatable across multiple attachment instances/hashes.

### Recommendation
Enforce `attachments_max_size` in `extend_with_attachments` before inserting into `self.attachments` (reject/drop responses whose `content.len()` exceeds the configured cap, and bump `report.bump_failed_requests()` instead), and additionally add the same length check inside `AtlasDB::insert_instantiated_attachment` (and/or reuse `should_keep_attachment` for downloaded attachments) so persistence itself is guarded regardless of caller.

### Proof of Concept
1. Configure a test `AtlasConfig` with a small `attachments_max_size` (e.g. 1 MB).
2. Queue an `AttachmentInstance` whose `content_hash` is the Hash160 of a deliberately oversized (e.g. 200 MB) byte buffer.
3. Stand up a mock peer HTTP server that responds to `GET /v2/attachments/{hash}` with a `GetAttachmentResponse` wrapping that 200 MB buffer as `Attachment.content`.
4. Drive `AttachmentsBatchStateMachine::try_proceed` through `DownloadingAttachment` so that `extend_with_attachments` (download.rs:530-558) processes the response.
5. Assert that `context.attachments` contains the oversized `Attachment` despite `attachment.content.len() > atlas_config.attachments_max_size`, and/or that a subsequent call to `AtlasDB::insert_instantiated_attachment` succeeds and stores the oversized row, confirming the missing bound check.
