Bazel's `third_party/ijar/zip.cc` implements ZIP/JAR parsing used by ijar/singlejar when processing archives (including third-party jars from external repos), and it has a bounds-check bypass caused exactly by unchecked pointer arithmetic on an attacker-controlled offset field, mirroring the CVE-2025-1866 pattern (pointer manipulation → OOB memory access).

### Title
Out-of-Bounds Read via Unsigned-Underflow Bounds Check in `InputZipFile::EnsureRemaining`/`ProcessNext` when Following an Attacker-Controlled Local-Header Offset - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessNext` computes the location of a ZIP local file header by adding an unvalidated, attacker-controlled 32/64-bit `offset` field taken straight from the Central Directory Header (or its Zip64 extra field) to the base pointer of the mapped input file: `p = zipdata_in_ + in_offset_ + offset;` [1](#0-0) . The subsequent bounds check, `EnsureRemaining`, computes `remaining = input_file_->Length() - in_offset` using unsigned `size_t` arithmetic [2](#0-1) . If the attacker-supplied `offset` pushes `in_offset` (i.e., `p - zipdata_in_`) beyond `input_file_->Length()`, this subtraction underflows to a huge value, so the check `n > remaining` incorrectly passes, and the code proceeds to dereference `p` via `get_u4le(p)` and further field reads — reading memory outside the mmap'd file.

### Finding Description
`ProcessCentralDirEntry` reads `compressed_size`, `uncompressed_size`, `file_name_length`, `extra_field_length`, `attr`, and `offset` directly from attacker-controlled bytes in the Central Directory Header with **no `EnsureRemaining` bounds validation at all** in that function [3](#0-2) , unlike `ProcessLocalFileEntry`, which does call `EnsureRemaining` before each variable-length read [4](#0-3) . If the entry's Zip64 extra field is present, `offset` can be read as a full 64-bit value via `get_u8le(extra)` [5](#0-4) , giving the attacker essentially unconstrained control over the pointer arithmetic that follows.

Back in `ProcessNext`, this offset is added to the mapped-file base pointer without any range check before use:
```
p = zipdata_in_ + in_offset_ + offset;
if (EnsureRemaining(4, "signature") < 0) { return false; }
u4 signature = get_u4le(p);
``` [6](#0-5) 

`EnsureRemaining` is the only guard, and it is defeated by unsigned underflow when `in_offset > input_file_->Length()`:
```
int EnsureRemaining(size_t n, const char *state) {
  size_t in_offset = p - zipdata_in_;
  size_t remaining = input_file_->Length() - in_offset;
  if (n > remaining) { return error(...); }
  return 0;
}
``` [2](#0-1) 

Once this false-negative bounds check passes, `ProcessLocalFileEntry`/`ProcessFile` continue to read/copy data at `p` (e.g. `file_data = p; ... processor->Process(filename, attr, file_data, uncompressed_size_);` in `InputZipFile::ProcessFile`) [7](#0-6) , so out-of-bounds heap/adjacent memory can be copied into the extracted/processed file content (e.g. via `UnzipProcessor::Process`/`write_file` in the `zipper` tool, or into singlejar's output jar). This is the same bug class as CVE-2025-1866: attacker-controlled data drives pointer arithmetic that is not properly restricted within the bounds of the mapped buffer, and the "guard" check itself is subverted by the same unchecked arithmetic.

### Impact Explanation
A maliciously crafted ZIP/JAR file processed by this ijar/zipper/singlejar code path (used when Bazel or a build rule processes a jar — e.g. constructing interface jars, or assembling a deploy jar from third-party dependency jars fetched from an external URL/registry) can cause an out-of-bounds read past the end of the mmap'd input file. Depending on memory layout this can leak adjacent process memory into the extracted output (information disclosure) or cause a crash by touching an unmapped page. This satisfies "write or read outside the ... output base" / untrusted-content-becomes-unconstrained-pointer-arithmetic criteria, going beyond a bare DoS because attacker-controlled bytes directly determine which out-of-bounds memory region gets copied into build outputs.

### Likelihood Explanation
Exploitability requires only supplying a crafted ZIP/JAR — no special privileges, no MITM, and no violation of any declared checksum is required in the reachable case: a victim can reference a jar/zip resource at an attacker-controlled URL/registry with no `sha256`/`integrity` pin set (a common, default-tolerated configuration for `http_jar`/`http_archive` since these attributes are optional), and the jar itself is what gets crafted maliciously; the parser bug then triggers unconditionally on any build step that runs it through ijar/singlejar/zipper.

### Recommendation
- In `EnsureRemaining`, first validate `p >= zipdata_in_ && (size_t)(p - zipdata_in_) <= input_file_->Length()` before computing `remaining`, and fail immediately if `p` is already out of range, avoiding the unsigned subtraction underflow.
- Add the same `EnsureRemaining`-style bounds checks inside `ProcessCentralDirEntry` before every fixed and variable-length read (mirroring what `ProcessLocalFileEntry` already does).
- Explicitly bound-check the `offset` value read from the Central Directory / Zip64 extra field against `input_file_->Length()` before using it in `p = zipdata_in_ + in_offset_ + offset;`.

### Proof of Concept
A `BuildIntegrationTestCase`/shell test (e.g. extending `third_party/ijar/test/zip_test.sh`) that:
1. Crafts a ZIP file with a valid End-Of-Central-Directory record and one Central Directory Header whose `offset` field (or Zip64 `offset` extra-field value) is set to a value larger than the file length (e.g. `Length() + large_delta`).
2. Runs the `zipper`/ijar extraction (`ZipExtractor::Create(...)->ProcessAll()`) against this crafted archive.
3. Observes that `EnsureRemaining` fails to reject the read (due to the underflow) and that `get_u4le(p)`/subsequent reads dereference memory outside the mapped file, either crashing under ASan (`heap-buffer-overflow`/`SEGV`) or producing corrupted/leaked bytes in the extracted output, confirming the bypass of the bounds check identified above.

  u8 compressed, uncompressed;
  u8 offset;

    }

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
