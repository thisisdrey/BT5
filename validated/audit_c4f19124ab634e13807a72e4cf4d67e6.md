### Title
Missing bounds check on ABI array-length offset in `PrecompiledContracts.extractBytes32Array` (`BatchValidateSign` precompile) - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` TVM precompile decodes attacker-controlled ABI-encoded call data using helper functions that read array-length words at attacker-controlled offsets. `extractBytesArray` and `extractSigArray` both guard against an out-of-range offset with `if (offset > words.length - 1) return new byte[0][];`, but the sibling helper `extractBytes32Array`, used to decode the `addresses` array, has no such guard before dereferencing `words[offset]`. [1](#0-0) 

### Finding Description
In `doExecute`, the offset used to index into `words[]` is derived directly from attacker-supplied call data (`words[2].intValueSafe() / WORD_SIZE`), and is passed to `extractBytes32Array` without validating that it is within bounds of the `words` array, unlike the parallel call to `extractSigArray`/`extractBytesArray`, which do perform this check: [2](#0-1) 

This is the same root-cause pattern as the reported TensorFlow bug: a value is read from user-controlled input and used as an array/tensor index without validating that the index actually falls inside the buffer, causing an out-of-bounds access when the value points past the end of the backing array.

### Impact Explanation
Unlike the C++ TensorFlow case (undefined behavior on native memory), in Java this manifests as an `ArrayIndexOutOfBoundsException`. I verified that `execute()` wraps `doExecute()` in a broad `catch (Throwable t)` that returns a benign `(true, zero-bytes)` result: [3](#0-2) 

Because this catch-all is in place, the exception is contained and does not crash the node or corrupt state — it degrades to a "signature check failed" result rather than an actual security-critical fault. I could not identify concrete unauthorized-fund, crash, or node-halt impact stemming specifically from this missing check, since the safety net at the top of `execute()` neutralizes it.

### Likelihood Explanation
Trivial to trigger: any contract caller invoking `BatchValidateSign` with crafted `addresses`-array offset words reaching this code path, but the impact is fully absorbed by the existing exception handler.

### Recommendation
For defense-in-depth and consistency, add the same `offset > words.length - 1` bounds check to `extractBytes32Array` as already exists in `extractBytesArray` and `extractSigArray`, so all three ABI-array decoding helpers behave uniformly and fail closed before any out-of-bounds read is attempted, rather than relying on the outer catch-all.

### Proof of Concept
Craft calldata for `BatchValidateSign` so that the second head word (`words[2]`, i.e. the offset for the `addresses` array) encodes an offset value that, divided by 32, exceeds `words.length - 1`. This causes `extractBytes32Array` to throw `ArrayIndexOutOfBoundsException` at `words[offset].intValueSafe()`; this is currently caught harmlessly by the `execute()` wrapper, so it does not constitute a demonstrated production-impact vulnerability under the strict validation rules — it is reported here as a code-hygiene/defense-in-depth gap rather than a proven exploitable issue.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {

    }

  }
