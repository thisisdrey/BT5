## Analysis

The ApolloX incident stemmed from a signature-verification flaw that let an attacker manufacture large numbers of technically-valid signatures to defeat a threshold/authorization check. Java-tron has a directly analogous flaw in the `ValidateMultiSign` TVM precompiled contract, which any smart contract can call to check whether a set of signatures meets an account's multi-sig `Permission` threshold.

### Title
Duplicate-signature weight inflation in `ValidateMultiSign` precompile allows bypassing multi-sig thresholds - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (`PrecompiledContracts.java`, class `ValidateMultiSign`, `execute()`) is supposed to sum up the weights of *distinct* signers that co-sign a given hash and compare the sum against a `Permission`'s `threshold`. However, its de-duplication logic only rejects a signature if the exact byte-for-byte signature has already been seen — it does not prevent the *same recovered address* from contributing its weight multiple times when presented with multiple, distinct-but-valid signatures over the same hash from the same key. [1](#0-0) 

### Finding Description
In the signature loop:
```java
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  ...
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
``` [2](#0-1) 

`ByteArray.matrixContains` performs exact `Arrays.equals` comparison of raw byte arrays: [3](#0-2) 

ECDSA is not deterministic by default in this codebase's signing path (no RFC 6979 nonce enforcement is visible in `SignUtils`/`ECKey.sign`), so a single private key can be used to produce many different valid `(r, s, v)` signatures over the *same* `hash`. Because the "already seen" check only skips the loop iteration when the exact `sign` bytes match a prior entry (`matrixContains(executedSignList, sign)`), an attacker who controls just **one** key that is a member of a `Permission` can supply several distinct signatures from that same key, each recovering to the same address, and each one still passes through to `totalWeight += weight`. Only the `MUtil.checkCPUTime()` call is invoked as a CPU-time throttle — no weight-dedup guard exists. Compare this to the correct multi-sig weight check `TransactionCapsule.checkWeight()`, which explicitly deduplicates by **address**, not by exact signature bytes, and throws `PermissionException` ("has signed twice!") for a repeat signer: [4](#0-3) 

This shows the intended semantics are per-address dedup, but the TVM precompile diverges from that pattern and instead dedups on the full signature bytes, which is trivially bypassed by re-signing.

Since `signatures.length` is capped at `MAX_SIZE = 5`, an attacker with a single key that has weight ≥ `threshold / 5` (or in general enough repeated weight contributions) can reach `totalWeight >= permission.getThreshold()` using only re-signed copies of their own single valid key, without ever possessing the other required keys.

### Impact Explanation
Any TVM smart contract (e.g., custom multi-sig wallets, vaults, bridges, or vote/approval-gated withdrawal contracts) that relies on `ValidateMultiSign` to enforce an M-of-N signer policy can have that policy bypassed by a holder of just one authorized key (or fewer than M keys), by submitting a `TriggerSmartContract` transaction whose call data supplies several distinct signatures generated from the same private key(s). This directly parallels the ApolloX root cause — generating many valid signatures to defeat a threshold check — and results in unauthorized approval/execution of privileged operations (fund withdrawal, permission changes, etc.) in any DApp built on top of this precompile, i.e., theft of funds/unauthorized account operations.

### Likelihood Explanation
The precompile is reachable by any unprivileged account simply by deploying or calling a contract that invokes `validatemultisign` opcode/precompile with attacker-crafted calldata — no special privilege is required. Producing multiple distinct valid ECDSA signatures over an identical hash using one key is trivial (just re-sign; nonce randomization naturally yields different `r/s` values). The `MAX_SIZE = 5` cap and per-signature energy cost (`1500` per sig) are the only frictions, both negligible compared to the value that could be unlocked in vulnerable downstream contracts.

### Recommendation
Change the de-duplication logic to key on the recovered **address only** (mirroring `TransactionCapsule.checkWeight`), rejecting/skipping the weight addition entirely once an address has already contributed, regardless of whether the exact signature bytes differ:
```java
if (ByteArray.matrixContains(executedAddrList, recoveredAddr)) {
    continue; // never add weight twice for the same address
}
...
totalWeight += weight;
executedAddrList.add(recoveredAddr);
```
Remove the `MUtil.checkCPUTime()`-then-fallthrough branch that currently allows weight accumulation for repeated addresses.

### Proof of Concept
1. Create an account with an Active `Permission` of `threshold = 2`, containing key `K1` (weight 1) and key `K2` (weight 1).
2. Deploy/call a contract (or directly invoke the precompile via a crafted `TriggerSmartContract`) that calls `validatemultisign(address, permissionId, data, sigs)` where `sigs = [sigA, sigB]`, with both `sigA` and `sigB` produced by signing the same derived `hash` twice using only `K1` (two independent `ECKey.sign` calls yield different `r/s` byte encodings but the same recovered address).
3. In `ValidateMultiSign.execute()`: the first signature recovers `K1`'s address, adds weight 1, and is added to `executedSignList`. The second signature also recovers `K1`'s address; `matrixContains(executedSignList, recoveredAddr)` is true, but `matrixContains(executedSignList, sign)` is false (different raw signature bytes), so it falls through and adds weight 1 again.
4. `totalWeight` becomes `2 >= threshold(2)`, so the call returns `DATA_ONE` (success) even though only one of the two required keys (`K1`) actually signed — `K2` never participated. Any downstream contract logic gated on this result executes as if the multi-sig requirement was met.
