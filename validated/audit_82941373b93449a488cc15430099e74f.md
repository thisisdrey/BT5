### Title
Active/Owner permission signatures are not bound to permission content, allowing a pre-collected multi-sig transaction to be executed under a different (weaker) authorization policy than signers approved - (File: `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`)

### Summary
TRON's multi-signature scheme lets a transaction be partially signed by several key-holders over time (via `Wallet.getTransactionApprovedList` / `TransactionUtil.getTransactionSignWeight`) and later broadcast once enough weight is collected. The transaction hash that each signer signs commits only to the numeric `permission_id`, not to the actual `Permission` content (its threshold and key/weight set) that will be used to evaluate their signatures. Because the account's `Owner` permission holder can change the referenced `Active`/`Witness` permission's keys and threshold at any time via `AccountPermissionUpdateContract`, a set of partial signatures collected under one authorization policy can later be evaluated - and satisfy the threshold - under a completely different policy that the original signers never agreed to. This mirrors the reported `ServiceManager` bug class: a signed authorization lacks a binding "upper bound"/snapshot of the mutable parameter (there: bond amount; here: permission threshold/keys) that governs the consequences of using that signature, so an on-chain state change made after signing can silently change what the signature actually authorizes.

### Finding Description
- A transaction's signing hash is `Sha256Hash.hash(raw_data)`, and `raw_data.contract[0].permission_id` is just an integer index into the account's current permission table - the hash never includes the permission's keys/threshold themselves. [1](#0-0) 
- At broadcast/execution time, `validateSignature` looks up the `Permission` object **from the current account state** by `permissionId`, and `checkWeight` sums the weights of the collected signatures against that (possibly-changed) `Permission`: [2](#0-1) 
- `checkWeight` itself has no notion of "the permission that was active when this signature was produced" - it only checks the signature against whatever `Permission` object is passed in: [3](#0-2) 
- The account's `Owner` permission holder (which may itself have a low threshold, e.g. a single key) can unilaterally replace the `Active` permission (keys, weights, threshold) referenced by `permission_id` at any time, without any cooperation from the `Active` permission's key-holders, via `AccountPermissionUpdateActuator.execute` → `account.updatePermissions(...)`: [4](#0-3) 
- The wallet-facing signature-collection APIs (`getTransactionApprovedList`, `getTransactionSignWeight`) explicitly implement a "collect signatures now, broadcast later" workflow, re-deriving `Permission` from current state and checking accumulated weight each time they are called - confirming the intended, reachable pattern in which time elapses between signing and broadcast: [5](#0-4) [6](#0-5) 

Concretely: suppose an `Active` permission requires 3 signers of weight 1 each (threshold 3) to move funds from a shared account. Two of those signers sign a `TransferContract` and the signatures are held pending the third. Before the third signer approves, whoever controls the `Owner` permission (which can have a much lower threshold, even a single key) submits an `AccountPermissionUpdateContract` that replaces the `Active` permission referenced by the same `permission_id` with a new key set/threshold of 2 (or swaps in an entirely different key that the Owner controls). The two previously-collected signatures — signed under the old, stricter policy — are then broadcast and now satisfy the new, weaker policy, and `TransactionCapsule.validateSignature` accepts the transaction and it is executed by `Manager`'s block/transaction application path, moving funds without the third signer's consent.

### Impact Explanation
This allows unauthorized account operations: a multi-signature spending policy can be silently downgraded after signatures are collected but before broadcast, letting a subset of key-holders (in collusion with, or as, the Owner-permission holder) execute a transaction (e.g., a large `TransferContract`, `DelegateResourceContract`, `WitnessUpdateContract`, etc.) that the full original signer set never authorized under the policy they signed against. This is a concrete unauthorized transfer/operation of funds, directly matching the theft-of-funds impact class.

### Likelihood Explanation
Requires the attacker to already control (or collude with the holder of) the `Owner` permission of the target multi-sig account, and to have obtained/retained a partial signature set from other Active-permission signers that was insufficient under the original policy. This is a realistic scenario for custodial/exchange/DAO-style TRON multisig wallets where Owner and Active permission holders differ, and where partial approvals are collected asynchronously (which the wallet APIs explicitly support). It requires no validator/witness/peer compromise and is reachable purely through signed transactions and standard RPC calls (`BroadcastTransaction`, `GetTransactionApprovedList`, `GetTransactionSignWeight`, `AccountPermissionUpdate`).

### Recommendation
Bind the signed hash to a snapshot of the permission content (not just its numeric id), e.g. include a hash/version of the `Permission` (its `keys`, weights and `threshold`) at signing time in the transaction hash, or attach a permission-version/nonce to each `Permission` that is bumped on every `AccountPermissionUpdateContract` and required to match at signature-verification time in `TransactionCapsule.validateSignature`/`checkWeight`. Any mismatch between the permission version referenced by a signature and the account's current permission version should invalidate that signature, forcing re-collection of signatures whenever the account's permission configuration changes.

### Proof of Concept
1. Create account `A` with `Active` permission `P` (id=2): keys `{K1:1, K2:1, K3:1}`, threshold 3. `Owner` permission is a separate single key `KO` held by the account administrator.
2. Build unsigned `TransferContract` moving all of `A`'s balance to attacker-controlled address `R`, with `permission_id=2`.
3. `K1` and `K2` sign the transaction (`TransactionCapsule.addSign` / `sign`), producing 2 signatures; `checkWeight` against `P` gives weight 2 < threshold 3, so it cannot yet be broadcast — confirmed via `getTransactionSignWeight` (`NOT_ENOUGH_PERMISSION`). [7](#0-6) 
4. Using `KO`, submit and confirm an `AccountPermissionUpdateContract` that replaces the id=2 Active permission with a new set `{K1:1, K2:1}`, threshold 2 (`AccountPermissionUpdateActuator.execute` → `account.updatePermissions`). [8](#0-7) 
5. Broadcast the original `TransferContract` (still bearing `permission_id=2` and the two signatures from step 3). `TransactionCapsule.validateSignature` fetches the *new* permission by id, `checkWeight` now returns weight 2 which meets the new threshold 2, and the transfer executes, moving `A`'s full balance to `R` — despite `K3` (part of the originally-agreed 3-of-3 policy) never approving. [2](#0-1)

  public static long checkWeight(Permission permission, List<ByteString> sigs, byte[] hash,
      List<ByteString> approveList)
      throws SignatureException, PermissionException, SignatureFormatException {
    long currentWeight = 0;
    if (sigs.size() > permission.getKeysCount()) {
      throw new PermissionException(
          "Signature count is " + (sigs.size()) + " more than key counts of permission : "
              + permission.getKeysCount());
    }
    HashMap addMap = new HashMap();
    for (ByteString sig : sigs) {
      if (sig.size() < 65) {
        throw new SignatureFormatException(
            "Signature size is " + sig.size());
      }
      String base64 = TransactionCapsule.getBase64FromByteString(sig);
      byte[] address = SignUtils
          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
      if (weight == 0) {
        throw new PermissionException(
            ByteArray.toHexString(hash) + " is signed by " + encode58Check(address)
                + " but it is not contained of permission.");
      }
      if (ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)) {
        base64 = encode58Check(address);
      }
      if (addMap.containsKey(base64)) {
        throw new PermissionException(encode58Check(address) + " has signed twice!");
      }
      addMap.put(base64, weight);
      if (approveList != null) {
        approveList.add(ByteString.copyFrom(address)); //out put approve list.
      }
      currentWeight += weight;
    }
    return currentWeight;
  }

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  @Override
  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule result = (TransactionResultCapsule) object;
    if (Objects.isNull(result)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    long fee = calcFee();
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);

      byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
      AccountCapsule account = accountStore.get(ownerAddress);
      account.updatePermissions(accountPermissionUpdateContract.getOwner(),
          accountPermissionUpdateContract.getWitness(),
          accountPermissionUpdateContract.getActivesList());
      accountStore.put(ownerAddress, account);

      adjustBalance(accountStore, ownerAddress, -fee);
      if (chainBaseManager.getDynamicPropertiesStore().supportBlackHoleOptimization()) {
        chainBaseManager.getDynamicPropertiesStore().burnTrx(fee);
      } else {
        adjustBalance(accountStore, accountStore.getBlackhole(), fee);
      }

      result.setStatus(fee, code.SUCESS);
    } catch (BalanceInsufficientException | InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      result.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }

    return true;
