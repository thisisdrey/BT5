### Title
Out-of-bounds read of a Zip64 extra field when parsing an attacker-supplied jar/zip entry - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`LH`/`CDH::compressed_file_size()`, `uncompressed_file_size()`, and `CDH::local_header_offset()` index into a `Zip64ExtraField`'s `attr_[]` array using a positional index derived from *which* 32-bit fields are `0xFFFFFFFF`, without verifying that the field's declared `payload_size()` actually contains that many 8-byte attributes.

### Finding Description
`ExtraField::find()` only bounds-checks that the extra field's header + declared `payload_size()` fits inside the entry's `extra_fields`/`extra_fields_length()` window [1](#0-0) . It never checks the field's *content* is large enough for the attribute the caller is about to read. `Zip64ExtraField::attr64(index)` simply computes `attr_[index]` with no bounds check against `attr_count()` [2](#0-1) .

Per the ZIP spec, a Zip64 extra field is only required to carry the 64-bit values for the fields that are actually flagged with `0xFFFFFFFF` in the fixed-size header, in a fixed order (uncompressed size, compressed size, offset). Bazel's `compressed_file_size()`, `uncompressed_file_size()`, and `local_header_offset()` compute an `index` purely from which 32-bit fields are flagged as needing extension [3](#0-2) [4](#0-3) [5](#0-4) , but do not verify that the Zip64 field's `payload_size()` (i.e., `attr_count()`) is large enough to actually hold that index. An attacker who crafts a jar/zip with, e.g., `uncompressed_file_size32 == 0xFFFFFFFF` and `compressed_file_size32 == 0xFFFFFFFF` but supplies a Zip64 extra field payload of only 8 bytes (one attribute) can cause `attr64(1)` to read 8 bytes past the end of the declared/validated extra-field bytes — into adjacent file-name/extra-field/comment bytes of the same mmap'd file, or, if the entry is the last thing in the mapped region, past the end of the memory-mapped file entirely (`MappedFile`), an out-of-bounds/uninitialized-relative-to-the-attacker-declared-content read.

This is parsed directly from an externally supplied jar via `InputJar::Open`/`LocateCentralDirectory`, which memory-maps the file and walks central directory headers (`CDH`) with only high-level sanity checks (ECD/CDH signatures, central-directory offset/size bounds) — it performs no validation of per-entry Zip64 extra-field internal consistency [6](#0-5) . `output_jar.cc`'s `WriteEntry`/central-directory-header construction (`OutputJar::WriteEntry`) subsequently reads these fields off the parsed input entry structure when copying metadata into the merged output jar [7](#0-6) .

### Impact Explanation
This is analogous to CVE-2020-1934's class (native code reading uninitialized/out-of-range memory while processing attacker-controlled, non-validated structured input), but here the affected component (singlejar) processes zip/jar files it receives as build inputs — e.g., third-party jars fetched via `http_jar`/`http_archive`/Maven coordinates. Because sha256/integrity only validate the whole downloaded file byte-for-byte, this in no way stops a *legitimately-hashed-but-maliciously-crafted* jar from tripping this bug once it reaches singlejar's zip parsing during a normal build (merging/deploy-jar creation, etc.). The read is out-of-bounds relative to the entry's declared extra-field content and can pull in adjacent heap/mmap bytes (potential information disclosure into the constructed output jar's metadata, e.g., leaking bytes from other parts of the memory-mapped file into `crc32`/size fields written into a generated jar) or crash the tool (SIGSEGV at a page boundary) — a low-severity, read-only info/DoS class matching the CVE-2020-1934 style bug (uninitialized-memory use from untrusted content), not remote code execution.

### Likelihood Explanation
Reaching this requires an attacker to be the maintainer/publisher of a jar dependency (or MITM'd artifact later verified by checksum/lockfile — but the checksum only guards file identity, not internal structural consistency), so it is trivially reachable by anyone who can get a victim to build against a malicious `.jar`/`.zip` via `http_jar`, `http_archive` (type=jar/zip), or similar rules that feed singlejar. No special privileges, network position, or trusted-root-BUILD access is required.

### Recommendation
In `Zip64ExtraField::attr64()` (or at each call site in `LH`/`CDH`), validate `index < attr_count()` before dereferencing `attr_[index]`, and treat a Zip64 extra field with an insufficient `payload_size()` for the flagged 32-bit fields as a corrupt/malformed archive, causing `InputJar`/`ZipExtractor` to reject the file with a diagnostic error rather than silently reading adjacent memory.

### Proof of Concept
Not independently verified/executed — I was not able to trace this all the way into a concrete `output_jar.cc`/`combiners.cc` call path or build a minimal `.jar` reproducing the OOB read within this session's remaining budget. A `zip_headers_test.cc`-style unit test (in the vein of the existing `ZipHeadersTest.LocalHeader`/`Zip64ExtraFieldTest` tests using the `kPoison` sentinel pattern [8](#0-7) [9](#0-8) ) constructing an `LH`/`CDH` with both size fields set to `0xFFFFFFFF` but a Zip64 extra field `payload_size()` of only 8 (single attribute) placed at the very end of the poisoned buffer, then asserting `compressed_file_size()` reads `kPoison`-filled bytes beyond the declared payload, would be the natural reproduction vehicle — this still needs to be written and run to confirm the OOB read is actually observable (vs. compiler/layout artifacts making it always land on valid adjacent memory in practice).

  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
