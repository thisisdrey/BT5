### Title
Consensus-critical `Math.pow()`/legacy `MathWrapper.pow()` produces platform-dependent results in Bancor-formula token exchange and dynamic-energy-factor calculation - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`, `platform/src/main/java/x86|arm/org/tron/common/math/MathWrapper.java`, `chainbase/src/main/java/org/tron/core/capsule/ContractStateCapsule.java`)

### Summary
The externally reported bug class is "a `pow()` implementation whose return value is not guaranteed to be identical across executions/environments, when that `pow()` is used inside a critical financial/accounting formula." java-tron reproduces exactly this bug class natively: `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (the on-chain Bancor-style relay-token pricing formula used by `ExchangeInjectContract`, `ExchangeWithdrawContract` and `ExchangeTransactionContract`) and `ContractStateCapsule.catchUpToCycle` (the TVM dynamic-energy-factor decay/growth formula used on every contract call once dynamic energy is enabled) both call `Maths.pow(a, b, useStrictMath)`, which — depending on the `allowStrictMath`/`disableJavaLangMath` consensus flags — can resolve to the legacy, explicitly non-cross-platform `java.lang.Math.pow()` via `platform/.../MathWrapper.pow()`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Maths.pow(a, b, useStrictMath)` dispatches to `StrictMathWrapper.pow` (which calls `StrictMath.pow`) or to the deprecated `MathWrapper.pow` (which calls `Math.pow` on x86, and on ARM wraps `StrictMath.pow` with a **hand-maintained lookup table of historically observed wrong results**) depending on a governance-controlled boolean. [3](#0-2) [4](#0-3) [5](#0-4) 

The ARM `MathWrapper` static initializer patches ~40 specific `(a, b) → result` triples, each annotated with the mainnet block number where the divergence was observed (e.g. `4137160`, `4065476`, ... `9631452`), all for the exponent `0.0005` used by the exchange formula. [6](#0-5) 

This is direct, concrete evidence that `Math.pow()`/JIT-intrinsic `pow` on this codebase has already caused **real, observed differences in return value between x86 and ARM nodes** for the exact bancor exchange formula reachable by ordinary `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions: [7](#0-6) [8](#0-7) 

Rather than fixing the root cause (as PoolTogether did, by moving to a library version with correct/consistent fixed-point math), java-tron's mitigation is a **finite, hand-curated whitelist of previously-seen bad inputs**, which only protects against inputs that have already caused a fork in the past. Any *new* `(balance, quant)` pair passed to `ExchangeInjectActuator`/`ExchangeWithdrawActuator`/`ExchangeTransactionActuator` that produces a floating-point base value not already present in the ARM `powData` table can still trigger the same class of divergence between x86 and ARM full nodes, because `Math.pow` (used when `useStrictMath=false`, i.e. `allowStrictMath` proposal not yet activated) is explicitly *not* required by the JVM spec to be bit-identical across platforms/JIT implementations — only `StrictMath.pow` carries that guarantee, and `StrictMath` is not the default path on unpatched pre-`allowStrictMath` nodes.

The same `pow()` call is also used, unconditionally on the flag `useStrictMath = dps.allowStrictMath()`, inside `ContractStateCapsule.catchUpToCycle`, which recomputes the network's dynamic-energy-factor every cycle boundary crossing during ordinary smart-contract execution (TVM resource accounting), meaning the identical bug class threatens energy/bandwidth metering consensus as well, not just the exchange module. [9](#0-8) 

### Impact Explanation
If a validator/full-node fleet is heterogeneous (mixed x86/ARM, as java-tron explicitly anticipates by shipping separate `platform/arm` and `platform/x86` `MathWrapper` implementations), an untabulated floating-point divergence in `pow()` produces a different `long` (`(long) issuedSupply` / `(long) exchangeBalance`) on different nodes for the *same* `ExchangeTransactionContract`, or a different `energyFactor` for the *same* block of contract calls. Because these values are written into consensus state (`ExchangeCapsule` balances, `AccountCapsule` asset/TRX balances, `ContractState.energyFactor`), a divergent `pow()` result on even one node causes that node's post-transaction/post-block state root to diverge from the rest of the network — i.e., a **chain split**. This exactly matches the accepted-impact class for this analog (chain split / node no longer agreeing with consensus), and is reachable by any unprivileged user simply broadcasting an `ExchangeTransactionContract` (or any transaction that triggers a smart contract during a dynamic-energy cycle rollover) — no special privilege required.

### Likelihood Explanation
The vulnerability class is not hypothetical for this codebase: the ARM `MathWrapper` static block is a changelog of ~40 real historical consensus incidents traced to specific mainnet block numbers, proving the exact bug (floating point `pow()` inconsistency) has repeatedly occurred in production on the exchange formula. The mitigation approach (an ever-growing hardcoded override table keyed on exact bit patterns of `a`/`b`) is inherently incomplete — it can only cover inputs that have already been observed to break, not any new user-controlled balance/quantity combination that produces an as-yet-untabulated floating point input. As long as any full node runs with `allowStrictMath` proposal not yet activated (`disableJavaLangMath`/legacy path) or runs the non-ARM `MathWrapper.pow` (plain `Math.pow`, no table at all) on hardware/JIT combinations not covered by mainnet history, a fresh divergence is plausible on any newly-crafted exchange transaction quantity.

### Recommendation
- Retire the double/`pow()`-based bancor formula entirely for the exchange and dynamic-energy-factor computations, in favor of deterministic fixed-point/integer arithmetic (e.g., `BigInteger`/`BigDecimal` exponentiation as already done in `SafeExchangeProcessor`), and make that path mandatory (not opt-in via `allowHardenExchangeCalculation`/`allowStrictMath` governance flags) so all nodes, regardless of architecture, compute bit-identical results by construction.
- Remove the legacy `MathWrapper`/`Maths.pow` code paths (`platform/src/main/java/x86|arm/org/tron/common/math/MathWrapper.java`, `common/src/main/java/org/tron/common/math/Maths.java`) once `allowStrictMath`/`disableJavaLangMath` are permanently activated on mainnet, so no code path can still resolve to raw `Math.pow`.
- Apply the same fixed-point replacement to `ContractStateCapsule.catchUpToCycle`'s dynamic-energy-factor `pow()` call, since it is reachable on every TVM call once dynamic energy is enabled and shares the identical `pow()`-consistency risk.

[1](#0-0) 
3. The same `pow()` call, gated only by the `useStrictMath` flag (not eliminated), also drives `ContractStateCapsule.catchUpToCycle`'s energy-factor decay computed on ordinary contract execution. [2](#0-1)

  public boolean catchUpToCycle(
      long newCycle, long threshold, long increaseFactor, long maxFactor,
      boolean useStrictMath, boolean disableMath
  ) {
    long lastCycle = getUpdateCycle();

    // Updated within this cycle
    if (lastCycle == newCycle) {
      return false;
    }

    // Guard judge and uninitialized state
    if (lastCycle > newCycle || lastCycle == 0L) {
      reset(newCycle);
      return true;
    }

    final long precisionFactor = DYNAMIC_ENERGY_FACTOR_DECIMAL;

    // Increase the last cycle
    // fix the threshold = 0 caused incompatible
    if (getEnergyUsage() > threshold) {
      lastCycle += 1;
      double increasePercent = 1 + (double) increaseFactor / precisionFactor;
      this.contractState = ContractState.newBuilder()
          .setUpdateCycle(lastCycle)
          .setEnergyFactor(min(
              maxFactor,
              (long) ((getEnergyFactor() + precisionFactor) * increasePercent) - precisionFactor,
              disableMath))
          .build();
    }

    // No need to decrease
    long cycleCount = newCycle - lastCycle;
    if (cycleCount <= 0) {
      return true;
    }

    // Calc the decrease percent (decrease factor [75% ~ 100%])
    double decreasePercent = pow(
        1 - (double) increaseFactor / DYNAMIC_ENERGY_DECREASE_DIVISION / precisionFactor,
        cycleCount, useStrictMath
    );

    // Decrease to this cycle
    // (If long time no tx and factor is 100%,
    //  we just calc it again and result factor is still 100%.
    //  That means we merge this special case to normal cases)
    this.contractState = ContractState.newBuilder()
        .setUpdateCycle(newCycle)
        .setEnergyFactor(max(
            0,
            (long) ((getEnergyFactor() + precisionFactor) * decreasePercent) - precisionFactor,
            disableMath))
        .build();
