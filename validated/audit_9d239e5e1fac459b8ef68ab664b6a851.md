### Title
Authorization escalation via dangling postponed/data-dependent receipts surviving `DeleteAccount`, later executed against a recreated account of the same name - ([File: runtime/runtime/src/actions.rs])

### Summary
`check_actor_permissions` authorizes privileged actions (`AddKey`, `DeployContract`, `Stake`, `DeleteKey`, `DeleteAccount`, etc.) purely by comparing `actor_id != account_id` as `AccountId` strings, with no concept of "which incarnation" of that account is being addressed. Combined with `remove_account` not purging `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId`/`ReceivedData` trie rows keyed by `receiver_id` when an account is deleted, a self-targeted receipt created by an old incarnation of an account can fire later against a freshly recreated account of the same name and be granted full self-actor privilege.

### Finding Description
`check_actor_permissions` (`runtime/runtime/src/actions.rs:739`) grants privilege for `DeployContract`/`Stake`/`AddKey`/`DeleteKey`/`DeployGlobalContract`/`UseGlobalContract`/`WithdrawFromGasKey`/`DeleteAccount` whenever `actor_id == account_id`: [1](#0-0) 
`actor_id` here is ultimately seeded from `receipt.predecessor_id()`, i.e. it is a bare `AccountId` string baked into the receipt at receipt-creation time — the check has no notion of "account generation" or instance identity; it only checks name equality.

A contract can create a self-targeted `ActionReceipt` (predecessor_id == receiver_id == its own account) carrying privileged actions (e.g. `AddKey`) with `input_data_ids` that are not yet satisfied. Such a receipt is persisted as a **Postponed ActionReceipt** under `TrieKey::PostponedReceipt{receiver_id, receipt_id}`, plus `PendingDataCount` and `PostponedReceiptId` entries, all keyed only by the account-id string (`runtime/runtime/src/lib.rs:1593-1658`, `core/store/src/utils/mod.rs:120-143`): [2](#0-1) 

The account can then be deleted via `DeleteAccount`. `action_delete_account` (`runtime/runtime/src/actions.rs:314`) checks only storage-usage limits and gas-key balances before calling `remove_account`: [3](#0-2) 
`remove_account` (`core/store/src/utils/mod.rs:505`) removes the `Account`, `ContractCode`, access keys/gas-key nonces, and contract data — but **does not** touch `PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, `ReceivedData`, or `PromiseYield*` rows for that account: [4](#0-3) 

Nothing in `action_create_account` (`runtime/runtime/src/actions.rs:167-210`) checks for or purges leftover postponed/pending-data state for the account_id being (re)created: [5](#0-4) 

Consequently, once a new account is created under the same name, the dangling postponed receipt is still addressable: when its outstanding `DataReceipt` finally arrives, `process_receipt`/`process_action_receipt` (`runtime/runtime/src/lib.rs:1367-1474`) will look it up purely by `receiver_id` (the recreated account's name) and execute it via `apply_action_receipt` → `apply_action` → `check_actor_permissions`, which only compares the stale `predecessor_id` string to the current `receiver_id` string and grants privilege on the new account: [6](#0-5) [7](#0-6) 

### Impact Explanation
This lets a privileged action authored by an *old* account instance (e.g. `AddKey` granting a `FullAccess` key to an attacker-chosen public key, or `DeployContract` with attacker-chosen code) execute against a *new, unrelated* account instance that happens to reuse the same `AccountId`, without any authorization from the new owner. This is a direct authorization-escalation-across-accounts bug matching the "authorization escalation across accounts or promises" bounty category, and can lead to theft of funds/control of the recreated account (e.g., attacker adds their own full-access key to a victim's freshly created account of a squatted/reused name).

### Likelihood Explanation
Exploitation requires: (1) an attacker who fully controls an account to author a self-targeted receipt with a data dependency and a privileged action (achievable purely with normal contract calls — no special permissions needed), (2) deleting that account before the data dependency resolves, and (3) a second party creating a new account with the exact same name before the dangling data dependency is satisfied. This is most practically exploitable against namespaces the attacker can also recreate under (e.g., re-registering their own deleted account to weaponize it against their own future self is not useful, but squatting/reuse of short-lived or transient subaccount names, or races where a victim quickly reclaims a freed name, are realistic). The preconditions are non-trivial (requires timing control over data-receipt arrival and someone else recreating the exact name), but all steps are reachable by an ordinary unprivileged account through standard transactions/cross-contract calls; no validator or node privileges are needed.

### Recommendation
- On `DeleteAccount`, purge all outstanding `PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, `ReceivedData`, and `PromiseYield*`/`YieldIdToDataId`/`DataIdToYieldId` trie entries keyed by that `account_id` in `remove_account`, refunding/erroring the associated pending receipts as appropriate (or asserting no such state exists — refusing deletion otherwise).
- Alternatively/additionally, associate postponed/data-dependent receipts with an account-generation identifier (e.g., account creation block height or a monotonic per-account creation counter) so that `check_actor_permissions`/receipt resolution rejects a stale receipt whose recorded generation does not match the current account's generation.

### Proof of Concept
Integration test plan (test-loop / `runtime/runtime/src/tests/apply.rs` style):
1. Create account `victim.parent` with a contract; have it issue a self-call receipt `R` (`predecessor_id = receiver_id = "victim.parent"`) containing `Action::AddKey(attacker_pubkey, FullAccess)`, with one `input_data_id` that is never resolved yet (e.g., call to another contract whose result is delayed). Assert `R` is stored under `TrieKey::PostponedReceipt` for `"victim.parent"`.
2. Submit and apply a `DeleteAccount` receipt for `"victim.parent"` (actor_id == account_id, locked == 0), succeeding. Assert the `Account` row is gone but `TrieKey::PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` for `"victim.parent"` still exist in the trie.
3. Submit and apply a `CreateAccount` + funding for `"victim.parent"` by a legitimate, unrelated actor (new owner, new keys, no `attacker_pubkey`).
4. Deliver the pending `DataReceipt` that satisfies `R`'s `input_data_id`. Assert the postponed receipt fires, `check_actor_permissions` passes (actor_id == account_id string match), and the `AddKey(attacker_pubkey, FullAccess)` is applied to the newly created `"victim.parent"` account — i.e., assert `get_access_key(state_update, "victim.parent", attacker_pubkey)` now returns `FullAccess`, despite the new owner never authorizing it.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }
