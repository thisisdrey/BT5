### Title
Unbounded client-controlled `limit` parameter in paginated HTTP APIs causes excessive memory allocation - (File: `framework/src/main/java/org/tron/core/services/http/GetPaginatedAssetIssueListServlet.java`)

### Summary
Several HTTP servlets that expose paginated on-chain lists (asset issues, exchanges, witnesses, proposals) accept a client-supplied `limit` value and pass it directly, unvalidated, into `Wallet` accessor methods that build a full protobuf list response. Unlike the sibling `GetBlockByLimitNextServlet`, which explicitly caps the requested range to `BLOCK_LIMIT_NUM = 100` before calling into `Wallet`, these paginated-list servlets impose no upper bound on `limit` at the servlet layer.

### Finding Description
`GetPaginatedAssetIssueListServlet.doGet`/`doPost` reads `offset` and `limit` straight from the request (GET query string or POST JSON body) and forwards them unchecked to `wallet.getAssetIssueList(offset, limit)`: [1](#0-0) 

The same unguarded pattern is repeated in the exchange, witness, and proposal paginated endpoints: [2](#0-1) [3](#0-2) [4](#0-3) 

By contrast, the block-range endpoint that also takes attacker-controlled numeric bounds explicitly caps the delta before querying storage: [5](#0-4) 

This is directly analogous to the Tempo bug class: a client-supplied numeric "hint"/"limit" value that is not bounded before being used to drive memory allocation for a response object, allowing a single request to force the node to materialize an arbitrarily large in-memory list/protobuf builder.

I was unable to fully inspect the bodies of `Wallet.getAssetIssueList`, `Wallet.getPaginatedExchangeList`, `Wallet.getPaginatedNowWitnessList`, and `Wallet.getPaginatedProposalList` within the available tool budget, so I cannot confirm with certainty whether any of these methods perform an internal server-side cap on `limit` before allocating the result list/builder. This is a material uncertainty in the finding — the servlet-layer lack of validation is confirmed, but whether the `Wallet` layer independently bounds the value is not verified.

### Impact Explanation
If `limit` is not bounded downstream in `Wallet`, a remote, unauthenticated client (these are read-only GET/POST HTTP endpoints with no signature/permission requirement) can request an extremely large `limit` (e.g., `Long.MAX_VALUE`), causing the node to attempt to build a `AssetIssueList`/`ExchangeList`/`WitnessList`/`ProposalList` protobuf response sized far beyond available heap, resulting in an OutOfMemoryError and node crash — a denial-of-service impacting the full node's ability to serve API/consensus-adjacent functions. This matches the CWE-400 (uncontrolled resource consumption) class of the Tempo advisory (CVE-2026-27878).

### Likelihood Explanation
Likelihood cannot be confirmed as high without verifying the `Wallet` method internals. If those methods clamp `limit` to the actual size of the underlying store (which is bounded on-chain by real proposal/witness/exchange/asset-issue counts, unlike the block store which can be huge), the practical amplification may be limited. Because this uncertainty could not be resolved with the available tools, this finding should be treated as a lead requiring source verification of `Wallet.getAssetIssueList`, `Wallet.getPaginatedExchangeList`, `Wallet.getPaginatedNowWitnessList`, and `Wallet.getPaginatedProposalList` in `framework/src/main/java/org/tron/core/Wallet.java` before being treated as confirmed exploitable.

### Recommendation
Add an explicit maximum-limit check (analogous to `BLOCK_LIMIT_NUM` in `GetBlockByLimitNextServlet`) in each of the four paginated servlets, or ensure the corresponding `Wallet` methods clamp `limit` to a safe maximum before allocating the response builder.

### Proof of Concept
Could not be constructed with certainty because the allocation behavior inside `Wallet.getAssetIssueList`/`getPaginatedExchangeList`/`getPaginatedNowWitnessList`/`getPaginatedProposalList` was not verified within the available investigation budget. A concrete PoC would require confirming those methods lack an internal cap and then issuing e.g. `GET /wallet/getpaginatedassetissuelist?offset=0&limit=9223372036854775807`.
