### Title
Immutable, unvalidated core parameters in `AssetIssueContract` permanently lock an account out of correct TRC10 token issuance - ([File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java])

### Summary
`AssetIssueActuator` permanently binds an account to a single TRC10 asset the first time it successfully issues one, and several critical parameters of that asset (name, `totalSupply`, `precision`, `trxNum`, `num`, `startTime`, `endTime`, frozen-supply schedule) can never be changed afterward. If an issuer submits an `AssetIssueContract` with a mistaken value in any of these unchangeable fields, the account is permanently locked out of ever issuing a corrected token, exactly analogous to the reported `BlueBerryBank.addBank()` issue where incorrect immutable parameters permanently lock a token out of the protocol.

### Finding Description
When a user issues a TRC10 token, `AssetIssueActuator.validate()` only checks that the account has not already issued an asset: [1](#0-0) 

Once `execute()` runs successfully, `accountCapsule.setAssetIssuedName(...)` and `setAssetIssuedID(...)` are set on the account: [2](#0-1) 

There is no actuator or code path that clears `AssetIssuedName`/`AssetIssuedID` or otherwise allows an account to re-issue or delete/replace its token. The only mutation path available afterward is `UpdateAssetActuator`, which is explicitly restricted to `description`, `url`, `new_limit` (`FreeAssetNetLimit`) and `new_public_limit` (`PublicFreeAssetNetLimit`): [3](#0-2) 

Meanwhile, `AssetIssueContract`'s validation logic only checks format/range constraints for the immutable fields (name format, precision range, `totalSupply>0`, `trxNum>0`, `num>0`, start/end time ordering, frozen-supply schedule bounds) but never lets these be corrected later: [4](#0-3) 

If the issuer sends a transaction with a typo in the asset name, a wrong `trxNum`/`num` exchange ratio, an incorrect `precision`, or a badly configured frozen-supply schedule, the transaction still passes validation and is committed on-chain via `execute()`. Because the "one asset per account" rule in `validate()` (line 287-289) is unconditional and there is no way to null out `AssetIssuedName`, that account can never issue another (correct) TRC10 token — the original, flawed one is permanent.

### Impact Explanation
This directly mirrors the reported bug class: unfixable, permanently-locked assets caused by insufficient parameter validation at issuance combined with an irreversible "add once" state transition. An issuer who makes a mistake (or is affected by unlikely external circumstances requiring a parameter change, e.g. wanting to correct `precision`, `trxNum`/`num` pricing, or the frozen supply schedule) permanently loses the ability to correctly issue that TRC10 asset from that account, freezing that account's issuance capability and any funds/fee already spent on the flawed issuance (the `AssetIssueFee` is burned/sent to the blackhole regardless, per `adjustBalance(... , -fee)` in `execute()`). This is a form of permanent freezing of the issuer's capability/funds tied to that specific account, matching the class of "permanent freezing of funds" impact.

### Likelihood Explanation
Likelihood is high because any unprivileged account can trigger this by simply submitting an `AssetIssueContract` transaction with a self-inflicted parameter mistake (no admin/whitelist gating on token issuance, unlike the `addBank()` `onlyOwner` case) — there's no confirmation/two-step process, and the fields at risk (`precision`, `trxNum`, `num`, frozen supply schedule, `totalSupply`, `startTime`/`endTime`) are numerous and easy to misconfigure once and never revisit.

### Recommendation
Add a bounded correction path before the asset window opens: e.g., allow amending immutable-but-erroneous parameters (`precision`, `trxNum`, `num`, frozen-supply list, `totalSupply`) via a dedicated actuator restricted to `startTime` not yet reached, or allow the account's `AssetIssuedName`/`AssetIssuedID` to be cleared/replaced under strict conditions (e.g., zero circulating supply, no exchanges created) so a flawed issuance can be superseded.

### Proof of Concept
1. Account `A` submits `AssetIssueContract` with `name="TOKN"`, `totalSupply=1000`, `trxNum=1`, `num=1000000` (an obviously wrong exchange ratio) and valid `startTime`/`endTime`.
2. `AssetIssueActuator.validate()` passes since it only checks `trxNum>0`/`num>0`, not intended correctness: [5](#0-4) 
3. `execute()` commits the asset and sets `accountCapsule.setAssetIssuedName(...)` permanently: [6](#0-5) 
4. Account `A` attempts to issue a corrected `AssetIssueContract`; `validate()` immediately rejects it with `"An account can only issue one asset"`: [1](#0-0) 
5. Account `A` attempts `UpdateAssetContract` to fix `trxNum`/`num`; the actuator only accepts `description`, `url`, `new_limit`, `new_public_limit`, so the wrong exchange ratio can never be corrected: [7](#0-6)
