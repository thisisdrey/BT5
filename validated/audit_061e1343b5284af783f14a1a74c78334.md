### Title
Double sequential floor-division in `calc-liquidity-rate` causes complete truncation of supplier yield when borrow-rate × utilization is small - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
`calc-liquidity-rate` computes the interest rate paid to liquidity providers by chaining two independent floor-divisions instead of combining the multiplication before dividing once, mirroring the "division before multiplication" precision-loss pattern from the referenced report. Because each stage rounds down independently, the final liquidity rate can be forced to zero even though the underlying borrow rate and utilization are both non-zero, temporarily freezing supplier yield accrual for the affected update cycle.

### Finding Description
`calc-liquidity-rate` in the vault contracts is defined as: [1](#0-0) 

```
(define-private (calc-liquidity-rate (var-borrow-rate uint) (util-pct uint) (reserve-factor-bps uint))
  (let ((util-applied (mul-bps-down var-borrow-rate util-pct))
        (one-minus-rf (- BPS reserve-factor-bps)))
    (mul-bps-down util-applied one-minus-rf)))
```

where `mul-bps-down` is `(/ (* x y) BPS)` with `BPS = u10000`: [2](#0-1) 

The correct, precision-preserving formula for the effective liquidity rate is:
`liquidity_rate = var_borrow_rate * util_pct * one_minus_rf / (BPS * BPS)`

Instead, the code computes `util_applied = floor(var_borrow_rate * util_pct / BPS)` first, and only then multiplies by `one_minus_rf` and divides by `BPS` again. This is exactly the bug class from the external report: a division is performed and its truncated integer result is subsequently used in a further multiplication/division, instead of deferring all division to the very end.

Because `BPS = 10000`, any time `var_borrow_rate * util_pct < 10000` (bps-scaled values, e.g. a borrow rate of 50 bps combined with 100 bps utilization gives a product of `5000`, still `< 10000`), `util_applied` truncates to `0`. The second `mul-bps-down` then always yields `0` regardless of `one_minus_rf`, so the supplier-side `liquidity-rate` used to advance the liquidity index becomes exactly zero for that accrual, even though a real, non-zero borrow rate and utilization exist and interest is genuinely accruing on the debt side.

This value feeds directly into the vault's per-block interest accrual: `next-liquidity-index`/`next` is used inside `accrue` to update `lindex`, which underlies `total-assets`, `total-assets-preview`, share pricing, and the treasury LP mint calculation: [3](#0-2) 

### Impact Explanation
When the truncation condition is hit, LP/depositor share value (via `lindex`) does not increase for that accrual window even though borrowers are simultaneously being charged interest (`index`/`old-debt`/`new-debt` still advance independently via `calc-multiplier-delta` and are unaffected by this bug). This is a temporary freezing of unclaimed yield owed to depositors: the interest that should compound into their redeemable share value is silently dropped for as long as the low-utilization/low-rate condition persists, matching the in-scope "temporary freezing of funds (unclaimed yield)" impact class.

### Likelihood Explanation
The condition is reachable under entirely ordinary, permissionless market conditions — no privileged action or DAO compromise is required. Low utilization combined with a modest borrow rate (both expressed in bps, capped at `BPS = 10000`) is a normal, expected market state (e.g., early after a vault launch, or during periods of low borrowing demand), making the zero-truncation scenario realistically and repeatedly triggerable across every affected vault (`v0-vault-usdc`, `v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-ststxbtc`, `v0-vault-usdh`), since they share the same `calc-liquidity-rate` implementation. [4](#0-3) 

### Recommendation
Combine both scaling operations into a single multiply-then-divide expression to avoid the intermediate rounding step, e.g.:
```
(define-private (calc-liquidity-rate (var-borrow-rate uint) (util-pct uint) (reserve-factor-bps uint))
  (let ((one-minus-rf (- BPS reserve-factor-bps)))
    (/ (* (* var-borrow-rate util-pct) one-minus-rf) (* BPS BPS))))
```
This preserves full precision until the final division, eliminating the zero-truncation window and any smaller-magnitude precision loss in intermediate cases.

### Proof of Concept
With `var-borrow-rate = u50` (0.5%), `util-pct = u100` (1% utilization), `reserve-factor-bps = u1000`:
- Current implementation: `util-applied = floor(50*100/10000) = floor(0.5) = 0`, so `liquidity-rate = floor(0*9000/10000) = 0`.
- Correct implementation: `liquidity-rate = floor(50*100*9000/(10000*10000)) = floor(45000000/100000000) = 0` — in this particular numeric example both are 0, but for slightly larger yet still realistic values such as `var-borrow-rate = u150`, `util-pct = u90`:
  - Current: `util-applied = floor(150*90/10000) = floor(1.35) = 1`; `liquidity-rate = floor(1*9000/10000) = 0`.
  - Correct: `liquidity-rate = floor(150*90*9000/100000000) = floor(121500000/100000000) = 1`.
  
  The current implementation yields `0` while the mathematically correct value is `1`, demonstrating the same "floor-then-scale" truncation defect described in the referenced report, applied here to the vault's supplier interest rate rather than a fee amount.
