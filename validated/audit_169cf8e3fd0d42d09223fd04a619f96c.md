### Title
HookService RPCs are reachable on Gitaly's external, authenticated gRPC socket, letting any client trigger receive-pack hooks outside of an actual push - (File: internal/gitaly/service/hook/pre_receive.go)

### Summary
The reported Forta bug is a "should-be-internal function exposed publicly" access-control gap. The analogous pattern in Gitaly is `HookService` — `PreReceiveHook`, `PostReceiveHook`, `UpdateHook`, `ReferenceTransactionHook`, and `PackObjectsHookWithSidechannel` are gRPC methods that are meant to be invoked only internally by the `gitaly-hooks` helper binary (spawned by `git-receive-pack`/`git-upload-pack` as a child process) over Gitaly's internal socket, but they are registered on, and reachable from, the same external gRPC listener as ordinary user-facing RPCs, with no check that the caller is the trusted internal hook process.

### Finding Description
`PreReceiveHook` [1](#0-0)  and its siblings `PostReceiveHook` [2](#0-1)  only validate that the `Repository` message is well-formed via `validatePreReceiveHookRequest`/`validatePostReceiveHookRequest`, which merely calls `locator.ValidateRepository`. Neither of these entry points verifies that the caller is `gitaly-hooks` acting on behalf of an in-flight push, unlike `SignalPostReceiveReady`, which explicitly checks `backchannel.GetPeerID(ctx)` and rejects calls that don't originate from Praefect's backchannel [3](#0-2) .

The code and tests acknowledge this is intended to be an internal-only surface: a test comment states "In the longer term, we should stop serving HookService on the external socket given it is a service intended only to be used internally by Gitaly for hook callbacks," referencing tracked issue #3746 [4](#0-3) . The server construction code distinguishes "external" vs internal traffic only for middleware wiring (housekeeping/transaction interceptors), not for authorization of which services may be called [5](#0-4) .

Crucially, the `HooksPayload` that carries the acting user's identity (`UserDetails.UserID/Username/Protocol`), the quarantine/object-directory info, and the `InternalSocketToken` is just a base64-encoded JSON blob passed in the `GITALY_HOOKS_PAYLOAD` environment variable/`EnvironmentVariables` field of the RPC request [6](#0-5) . It is not signed or cryptographically bound to an actual authenticated push. Any caller holding a valid Gitaly auth token (the same token required for ordinary RPCs) can construct this payload and the `Repository`/`stdin` fields themselves and invoke `PreReceiveHook`/`PostReceiveHook`/`UpdateHook`/`ReferenceTransactionHook` directly — mirroring the `_register` bug where a function meant to be reached only through a privileged/trusted path (`adminRegister`) was instead callable directly by any actor holding the same generic credentials as normal users.

### Impact Explanation
By calling these hooks directly with an arbitrary `Repository`, attacker-chosen `stdin` (fake old/new OID and ref name), and forged `UserDetails`/`GlId` in the hooks payload, a caller with valid but otherwise limited Gitaly gRPC credentials can:
- Trigger execution of the repository's custom `pre-receive`/`update`/`post-receive` server hooks outside of any real push, with attacker-controlled stdin content (as demonstrated by `TestPrereceive_quarantine`/`TestUpdate_quarantine`/`TestPostReceive_quarantine`, where custom hooks read attacker-controlled ref lines and blob IDs) [7](#0-6) .
- Cause the reference counter tracked by Rails' `/internal/pre_receive`/`/internal/post_receive` endpoints to be incremented/decremented arbitrarily, independent of any real push, since `PreReceiveHook`/`PostReceiveHook` call these Rails endpoints as part of normal processing (see `doc/hooks.md` sequence diagram) [8](#0-7) .
- Potentially spoof the identity used for access-control decisions sent to Rails' `/internal/allowed`, since `UserDetails` in the payload is attacker-supplied and unauthenticated relative to the actual gRPC caller.

This is a DoS/hook-gating-bypass class issue on a handler that should be gated to internal callers only, similar in spirit to the quarantine/hook gating concerns called out in the validation rules.

### Likelihood Explanation
Any client that already holds a valid Gitaly authentication token (which is required to reach any RPC on the external listener, including this one) can reach this surface — no special/admin privilege beyond ordinary token-holder access is required, and the flaw is explicitly acknowledged as unresolved in the codebase (referenced GitLab issue #3746) rather than merely theoretical.

### Recommendation
Restrict `HookService` methods (`PreReceiveHook`, `PostReceiveHook`, `UpdateHook`, `ReferenceTransactionHook`, `PackObjectsHookWithSidechannel`) to Gitaly's internal socket only, and/or add an explicit internal-caller check (mirroring `SignalPostReceiveReady`'s `backchannel.GetPeerID` check, or a dedicated internal-socket-token check) before executing hook logic, so that these RPCs cannot be invoked directly by external gRPC clients holding only ordinary credentials.

### Proof of Concept
Uncertain/not independently verified end-to-end (no ability to execute code in this environment): the code path is inferred from the `HookService` gRPC registration [9](#0-8) , and from the existing test `TestPreReceiveHook_GitlabAPIAccess`, which calls `client.PreReceiveHook(ctx)` through the same external test server socket used for regular RPCs, confirming that the method is reachable without any Praefect-backchannel-style gate [10](#0-9) . A concrete external exploit would require constructing a `PreReceiveHookRequest` with a valid `Repository`, a `GITALY_HOOKS_PAYLOAD`-bearing `EnvironmentVariables` entry (built via `gitcmd.NewHooksPayload(...).Env()`), and attacker-chosen `stdin` — this was not executed against a live server in this analysis.

// HooksPayloadFromEnv extracts the HooksPayload from the given environment
// variables. If no HooksPayload exists, it returns a ErrPayloadNotFound
// error.
func HooksPayloadFromEnv(envs []string) (HooksPayload, error) {
	encoded, ok := lookupEnv(envs, EnvHooksPayload)
	if !ok {
		return HooksPayload{}, ErrPayloadNotFound
	}

	decoded, err := base64.StdEncoding.DecodeString(encoded)
	if err != nil {
		return HooksPayload{}, err
	}

	var jsonPayload jsonHooksPayload
	if err := json.Unmarshal(decoded, &jsonPayload); err != nil {
		return HooksPayload{}, err
	}

	var repo gitalypb.Repository
	err = protojson.Unmarshal([]byte(jsonPayload.Repo), &repo)
	if err != nil {
		return HooksPayload{}, err
	}

	payload := jsonPayload.HooksPayload
	payload.Repo = &repo

	// If no RequestedHooks are passed down to us, then we need to assume
	// that the caller of this hook isn't aware of this field and thus just
	// pretend that he wants to execute all hooks.
	if payload.RequestedHooks == 0 {
		payload.RequestedHooks = AllHooks
	}

	return payload, nil
}
