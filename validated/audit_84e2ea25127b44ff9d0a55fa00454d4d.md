### Title
Dust deposits fill a victim's per-account token list and permanently block their deposits, transfers-in, and collateral top-ups - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER = 30` on the combined `debtTokensOfAccount` + `depositTokensOfAccount` lists, and reverts the whole transaction once the cap is hit. Because `DepositToken.deposit(amount_, onBehalfOf_)` lets any EOA mint deposit-token dust to an arbitrary `onBehalfOf_` address, an unprivileged attacker can fill a victim's list to 30 entries. After that, every path that would add a *new* deposit token to the victim's list — `deposit`, `transfer`/`transferFrom` in, and `seize` — reverts with `UserReachedMaxTokens`, freezing the victim's ability to onboard new collateral. The victim cannot remove the entries (only the token contracts can call `removeFromDepositTokensOfAccount`, and only when the holder's balance hits zero — the attacker controls the dust).

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [1](#0-0) 
- `addToDepositTokensOfAccount` is callable only from a registered deposit token, but `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` beneficiary with no consent [2](#0-1) 
- `_mint` and `_transfer` unconditionally call `pool.addToDepositTokensOfAccount(account_)` on a first-time balance; a revert there reverts the whole deposit/transfer/seize [3](#0-2) 
- Removal only happens inside `_burn`/`_transfer` when the sender's own balance reaches zero [4](#0-3) 
- Debt tokens cannot be pushed onto the victim (non-transferable, minted only to the issuer), so the deposit-token side alone suffices to exhaust the shared 30-slot cap.

Attack: for each registered deposit token `i`, attacker calls `depositToken_i.deposit(dust, victim)` (or deposits to self and `transfer`s dust to `victim`) until `depositTokensOfAccount.length(victim) == 30`. Cost is bounded by dust amounts of at most 30 distinct underlying assets, recoverable later via `withdraw`.

### Impact Explanation
Any subsequent `deposit` of a collateral type the victim doesn't already hold reverts; transfers-in and liquidations where the victim would receive a new token also revert. Critically, a victim whose position turns unhealthy cannot deposit a new collateral type to restore health, enabling liquidation that would otherwise have been prevented — a freeze of the deposit function for the targeted account, meeting the "temporary freezing of funds / griefing" impact class. It also DoS-es `Pool.liquidate`-adjacent flows only where the victim is a recipient, and breaks account abstraction (smart wallets/Operator batches) whose execution depends on deposit success.

### Likelihood Explanation
- Unprivileged EOA only; no governor/keeper/oracle reliance.
- The cap is shared with debt tokens, so the effective attack budget is `30 - existingDebtPositions`, i.e., usually ≤ 30 dust deposits.
- Cost is proportional to the number of deposit tokens registered; on chains with several listed collaterals the attack needs only dust amounts and is partially recoverable by withdrawing the dust afterwards (which also releases the block, so the attacker may keep dust parked).
- No modifier, pause flag, lock check, or reentrancy guard prevents `onBehalfOf_` deposits to a third party.

### Recommendation
- Do not add tokens to `depositTokensOfAccount` for pure `transfer`s / unsolicited `onBehalfOf_` deposits — e.g., only track tokens that are actually usable collateral, or allow permissionless `removeFromDepositTokensOfAccount` initiated by the account itself.
- Alternatively, decouple the account list from transfer success: catch `UserReachedMaxTokens` and skip tracking (position still functions since `depositOf` iterates the list, an untracked token would need an explicit "claim track" call by the owner).
- Or restrict `deposit`'s `onBehalfOf_` to `msg.sender`-owned/whitelisted beneficiaries.

### Proof of Concept
Hardhat sketch (foundry/hardhat project present; run against existing `Pool`/`DepositToken` fixtures like `test/Pool.test.ts`):

```ts
// setup: pool with N registered DepositTokens, victim has <30 tracked tokens
const dust = ethers.utils.parseUnits('0.000001', await underlying.decimals());

// attacker deposits dust of every other collateral type to victim
for (const dt of allDepositTokensExcept(victimHeldTokens)) {
  const underlying = await ethers.getContractAt('ERC20', await dt.underlying());
  await underlying.connect(attacker).approve(dt.address, dust);
  await dt.connect(attacker).deposit(dust, victim.address); // adds entry to victim's list
}
expect(await pool.getDepositTokensOfAccount(victim.address)).length(30);

// victim can no longer deposit a new collateral type
const newDT = depositTokenNotYetHeld;
await underlying.connect(victim).approve(newDT.address, amount);
await expect(newDT.connect(victim).deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim cannot rescue an unhealthy position via a new collateral
// -> liquidatable while deposits are blocked; attacker keeps dust parked indefinitely
```

Note: I did not execute the PoC (no execution environment); the revert path is confirmed by the unconditional `addToDepositTokensOfAccount` call inside `_mint`/`_transfer` and the `onlyIfAdditionWillNotReachMaxTokens` guard shown above.
