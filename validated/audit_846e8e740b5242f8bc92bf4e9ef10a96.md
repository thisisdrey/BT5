### Title
Replay-window check-then-act race in `ConnectionState.Decrypt`/`VerifyRelay` allows duplicate-packet decryption flooding (DoS) - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement anti-replay protection as a two-step "peek, then commit" sequence against the sliding-window `Bits` tracker, but they release the `decryptLock` between the peek (`window.Check`) and the commit (`window.Update`), with the expensive AEAD decryption running in the unprotected gap. This mirrors the reported STPV2 bug class: a shared piece of accounting state (there, `totalRewardsEgress`; here, the replay-window bitmap) is read at one point and only reconciled later, so decisions made in between are based on stale state, letting the same "unit" (a reward claim / a message counter) be processed more than once before the bookkeeping catches up.

### Finding Description
`Decrypt` and `VerifyRelay` both follow this pattern: [1](#0-0) 

The counter is only checked (`window.Check`) and then unlocked, decryption happens outside any lock, and only afterward is the lock re-acquired to actually mark the counter as seen (`window.Update`). The window state consulted by `Check` therefore does not account for any decrypt that is already "in flight" for the same counter, analogous to how the vulnerable `pointsPerShare` calculation didn't account for in-flight `totalRewardsEgress`.

`VerifyRelay` has the identical structure: [2](#0-1) 

Both are reached directly from attacker-controlled network input in `readOutsidePackets`, with no certificate or handshake state required beyond an already-observed ciphertext (e.g. a captured/sniffed packet) - the same packet can be re-injected: [3](#0-2) 

Because nebula runs with multiple RX routines/queues (`routines` config, `q int` parameter threaded through `readOutsidePackets`), duplicate copies of a captured packet delivered concurrently on different queues can each pass `window.Check` before either has called `window.Update`, since the lock is dropped in between. Only one call to `window.Update` will ultimately succeed, but every concurrent duplicate still pays the cost of a full AEAD `DecryptDanger` call before being rejected.

### Impact Explanation
This allows an attacker who can inject UDP traffic toward a node's listening port (no valid certificate needed - they only need to capture or observe one legitimate ciphertext packet, e.g. via network position) to replay-flood that single captured packet across the node's receive queues. Instead of each duplicate being rejected cheaply by the anti-replay bitmap check, a bounded number of duplicates per burst will each incur a full AEAD decryption before being discarded, amplifying CPU cost per replayed byte and providing a remote resource-exhaustion / DoS vector, which the rules classify as in-scope (nonce/replay handling, remote crash/DoS impact).

### Likelihood Explanation
Exploitability requires only capturing one valid ciphertext packet on the wire and being able to inject UDP duplicates concurrently (trivial for any network-adjacent attacker, or even a legitimate peer replaying their own prior traffic) - no CA-signed certificate or handshake participation is needed. The race window is small per-packet, but is trivially amplified by sending many concurrent duplicates and by nebula's multi-routine UDP receive design (`routines > 1`), so it is realistically triggerable, not merely theoretical.

### Recommendation
Hold `decryptLock` for the full duration of the check → decrypt → mark sequence in both `Decrypt` and `VerifyRelay` (or perform an atomic "check-and-reserve" step on the `Bits` window before decrypting, then finalize/roll back after), so that no two goroutines can ever perform a full AEAD decrypt for the same message counter concurrently. This closes the accounting gap analogous to folding `totalRewardsEgress` into the same atomic calculation as `pointsPerShare` in the referenced fix.

### Proof of Concept
1. Establish a tunnel and capture one legitimate data-plane packet (ciphertext + header) sent to a nebula node running with `routines > 1`.
2. Concurrently re-inject N copies of that exact packet on the node's UDP socket from multiple sender threads/sockets so they land on different RX queues near-simultaneously.
3. Because `window.Check` is evaluated without holding the lock across the subsequent `DecryptDanger` call, several of the N duplicates will pass `Check` and enter `DecryptDanger` before any of them calls `window.Update`, each paying full AEAD-decrypt cost even though only one will ultimately be accepted. Repeating this flood amplifies CPU load on the victim node from a single captured packet. [1](#0-0) [2](#0-1)

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
