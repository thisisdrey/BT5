### Title
`write_freq` Rate-Limit Is Never Enforced on StackerDB Chunk Writes, Allowing Unlimited-Rate Slot Overwrites - (File: stackslib/src/net/stackerdb/db.rs)

### Summary
`StackerDBTx::try_replace_chunk`, the single write path used by the unprivileged, unauthenticated `POST /v2/stackerdb/:address/:contract/chunks` RPC endpoint, checks chunk size, slot existence, signer authenticity, staleness, and `max_writes`, but never checks `StackerDBConfig::write_freq` — the minimum wall-clock time between writes to the same slot. The `net_error::TooFrequentSlotWrites` variant exists in the codebase specifically to represent this rejection, but it is never constructed/returned anywhere in the write path, mirroring the reported bug class: a configured limit ("available spins"/here "write frequency") that is defined but never enforced/decremented in the code that actually performs the action.

### Finding Description
`StackerDBConfig` declares `write_freq: u64` as "minimum wall-clock time between writes to the same slot" [1](#0-0) . The database schema records `write_time` for every slot precisely to support this check [2](#0-1) , and `net_error::TooFrequentSlotWrites(deadline)` exists as a dedicated error variant [3](#0-2) .

However, `try_replace_chunk` — the function that actually authorizes and persists a chunk write — only performs these checks, in order: (1) chunk-size cap, (2) slot existence, (3) signature verification, (4) staleness (`slot_version <= stored_version`), and (5) `max_writes` cap. It never compares the current time against `slot_validation.write_time + self.config.write_freq`, and then unconditionally calls `insert_chunk`: [4](#0-3) 

`insert_chunk` stores the new `write_time` unconditionally on every accepted call [5](#0-4) .

This function is invoked directly, and is the *only* validation performed, by the HTTP RPC handler `RPCPostStackerDBChunkRequestHandler::try_handle_request`, which is reachable from any unauthenticated remote peer via `POST /v2/stackerdb/:address/:contract/chunks`: [6](#0-5) 

The error-classification `match` in that handler explicitly enumerates `StaleChunk`, `NoSuchSlot`, `BadSlotSigner`/`VerifyingError`, `StackerDBChunkTooBig`, and `TooManySlotWrites`, but has no arm for `TooFrequentSlotWrites` — consistent with the fact that `try_replace_chunk` can never produce it [7](#0-6) .

By contrast, the *replication/sync* path (used when pulling chunks from peers) does honor `write_freq` when deciding what to fetch, via `make_chunk_request_schedule`, which skips slots written more recently than `write_freq` seconds ago [8](#0-7) , and `StackerDBSync::run` throttles the whole sync round similarly [9](#0-8) . The unsolicited push-chunk handler explicitly documents that it also skips the write-frequency check, on the assumption that bandwidth throttling at the P2P layer substitutes for it: `handle_unsolicited_StackerDBPushChunk` comment states "The write frequency is not checked for this chunk...because the ConversationP2P...will have already bandwidth-throttled the remote peer" [10](#0-9) . That assumption does not hold for the plain HTTP RPC endpoint, which has no equivalent per-message bandwidth throttle tied to `write_freq`, and whose sole gate is `try_replace_chunk`.

The net effect: any legitimate slot owner (someone who possesses a valid signing key for a StackerDB slot, e.g., a registered Stacker/Signer) can call `POST /v2/stackerdb/.../chunks` as fast as they want, bumping `slot_version` on every call, and `try_replace_chunk` will accept every single one so long as `slot_version` increases and stays under `max_writes`. The `write_freq` throttle that application/protocol operators rely on to bound write rate (and thus replication load and storage churn across the whole network, since accepted writes are relayed via `StackerDBPushChunk`) is completely unenforced on the write side.

### Impact Explanation
This does not directly corrupt data (signatures and staleness are still checked), but it breaks the intended write-rate invariant: `write_freq` is advertised by the StackerDB smart contract/config as the write-rate the network is provisioned for, and sync/relay logic elsewhere in the codebase assumes it is honored (e.g., to space out re-fetching and gossip). A slot owner exceeding `write_freq` via the HTTP endpoint can generate excess `StackerDBPushChunk` relay traffic network-wide (each accepted chunk is queued via `node.set_relay_message` and gossiped) [11](#0-10) , causing replication/storage churn beyond the configured budget across all replicas that receive the push. This is a bounded-but-real amplification/DoS-adjacent effect from a single authorized signer, not a full unauthenticated compromise, since it still requires possession of a legitimate slot-owning private key — this differentiates it from the report's "unlimited spins" (no cost at all) but the missing decrement/limit logic is analogous.

### Likelihood Explanation
High likelihood of triggering: any of the legitimately-registered StackerDB slot owners (e.g., signers) can trivially exploit this by scripting repeated `POST /v2/stackerdb/:address/:contract/chunks` calls with incrementing `slot_version`, well within `max_writes`, and observe that `write_freq` is never honored — no special conditions or races are needed.

### Recommendation
Enforce `write_freq` inside `try_replace_chunk` (or a call site immediately before it) by comparing `get_epoch_time_secs()` against `slot_validation.write_time + self.config.write_freq`, returning `net_error::TooFrequentSlotWrites` when the deadline has not elapsed, and add a corresponding `TooFrequentSlotWrites`/`Throttled` arm to the RPC handler's error-classification match in `poststackerdbchunk.rs` so it is surfaced as a proper ack/error code rather than silently permitted.

### Proof of Concept
1. Configure a StackerDB with `write_freq = 120` and `max_writes` large (as in the existing test fixtures, e.g. `stackslib/src/net/stackerdb/tests/db.rs` `test_stackerdb_insert_query_chunks`, which sets `db_config.write_freq = 120`).
2. As the registered slot owner, sign and `POST` chunk version 1 to `/v2/stackerdb/:address/:contract/chunks` — accepted.
3. Immediately (within the same second, well under 120s) sign and `POST` chunk version 2 to the same slot.
4. Observe: the second request is accepted (`ack.accepted == true`), because `try_replace_chunk` only checks staleness (`2 > 1`) and `max_writes`, never `write_freq` — contradicting the configured 120-second minimum write interval. Repeating this in a tight loop lets the owner write at unbounded rate to their slot, each accepted write triggering a `StackerDBPushChunk` relay to the network.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
