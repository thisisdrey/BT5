### Title
Unvalidated attachment content hash allows a malicious peer to permanently deny resolution of legitimate BNS attachments - (File: `stackslib/src/net/atlas/download.rs`)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any bytes a peer returns for a `GET /v2/attachments/{content_hash}` request without checking that `Hash160::from_data(bytes) == content_hash`. Because the state machine later resolves and stores the attachment keyed by the *actual* hash of whatever bytes were returned (not the requested `content_hash`), a malicious peer can serve arbitrary content and cause the legitimate `AttachmentInstance` to never be resolved, while itself being scored as a "successful" and increasingly "reliable" source.

### Finding Description
`extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) decodes the HTTP response via `decode_atlas_get_attachment` (`stackslib/src/net/api/getattachment.rs:159-165`) and inserts the returned `Attachment` into `self.attachments` — with no comparison to `request.content_hash`: [1](#0-0) 

`report.bump_successful_requests()` is also called unconditionally on successful decode, regardless of whether the content matches what was requested: [2](#0-1) 

When the batch finishes, the `Done` branch iterates the collected (unverified) attachments, computes `attachment.hash()` — the hash of the actual (possibly forged) bytes — and uses *that* value both to look up which pending instances it satisfies (`find_all_attachment_instances`) and to mark instances resolved (`resolve_attachment`): [3](#0-2) 

`AtlasDB::insert_instantiated_attachment` similarly stores/updates rows keyed by `attachment.hash()`, i.e., the hash of the actual bytes, not the originally requested `content_hash`: [4](#0-3) 

`AttachmentsBatch::resolve_attachment` removes entries from `attachments_instances` only when the tracked `content_hash` equals the passed hash: [5](#0-4) 

Root cause: the client never asserts `Hash160::from_data(&attachment.content) == request.content_hash` between receiving the HTTP response and inserting/committing it. All downstream keys (`find_attachment`, `find_all_attachment_instances`, `resolve_attachment`, `insert_instantiated_attachment`) are internally self-consistent (all use `attachment.hash()`), but that hash is never checked against the value the batch is actually waiting on (`AttachmentRequest.content_hash`, tracked in `attachments_instances`). A peer that was legitimately selected via `get_prioritized_attachments_requests` (`stackslib/src/net/atlas/download.rs:404-478`) because it advertised the hash in its `GetAttachmentsInvResponse` can therefore answer with unrelated content: the equality `committed_content_hash == stored_attachment_key` the pending instance is waiting for never becomes true, so `resolve_attachment` never removes it from `attachments_instances`.

### Impact Explanation
The pending `AttachmentInstance` for the legitimate `content_hash` is never resolved; it is re-enqueued (`bump_retry_count`) and, since the malicious peer's `ReliabilityReport` score is boosted rather than penalized, it can continue to be selected as the "best" source (`get_most_reliable_source`) on subsequent retries, permanently starving legitimate resolution until `max_attachment_retry_count` is exceeded and the entry is dropped. This denies the node (and any peers pulling attachments from it) the ability to resolve the legitimate BNS zonefile/attachment for that name — an attachment/BNS mismatch/denial condition, matching the listed High-severity category. It is a targeted, repeatable DoS against Atlas/BNS attachment resolution triggerable by any remote peer that is queried for attachments, requiring no privileged role or secret.

### Likelihood Explanation
Precondition: the attacker must run a normal, reachable peer node and respond to `GetAttachmentsInv` claiming to have the attachment (any unprivileged peer can do this), then answer the subsequent `GET /v2/attachments/{hash}` with arbitrary bytes. No handshake privilege, secret, or slot ownership is required beyond standard peer connectivity. Attacker cost is a single crafted HTTP response per attempt, fully repeatable, and self-reinforcing (bumped reliability score increases future selection likelihood).

### Recommendation
In `extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`), after decoding the response, compute `Hash160::from_data(&response.attachment.content)` and compare it to `request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed request (`report.bump_failed_requests()`) and optionally penalize/deregister the offending peer, rather than crediting it as successful.

### Proof of Concept
Rust net test plan (added to `stackslib/src/net/atlas/tests.rs`):
1. Build an `AttachmentsBatchStateContext` with one tracked `AttachmentInstance` whose `content_hash = Hash160::from_data(b"real-content")`.
2. Construct a `BatchedRequestsResult<AttachmentRequest>` where the request's `content_hash` matches the tracked instance, but the mocked `StacksHttpResponse` returns `GetAttachmentResponse { attachment: Attachment::new(b"forged-content".to_vec()) }` (whose true hash differs).
3. Call `context.extend_with_attachments(&mut results)`, then simulate the `Done` branch logic: for the single attachment in `context.attachments`, call `attachments_batch.resolve_attachment(&attachment.hash())`.
4. Assert `attachments_batch.attachments_instances_count() == 1` (unchanged) — proving the original instance was never resolved — and separately assert that `resolve_attachment` was never invoked with the original `content_hash` (`Hash160::from_data(b"real-content")`), confirming the mismatch described in the question.
