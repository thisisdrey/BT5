### Title
Attachment download path stores oversized/unhashed content without enforcing `attachments_max_size` - ([File: stackslib/src/net/atlas/mod.rs])

### Summary
`GetAttachmentResponse`'s custom `Deserialize` impl accepts an arbitrary-length hex string from a peer's `/v2/attachments/{hash}` response and builds an `Attachment` with no size bound. `AttachmentsBatchStateContext::extend_with_attachments` then inserts this attachment into the batch set with no size or hash-equality check, and `AtlasDB::insert_instantiated_attachment` writes it to disk unconditionally, unlike the local push path which enforces `should_keep_attachment`.

### Finding Description
`GetAttachmentResponse::deserialize` (`stackslib/src/net/atlas/mod.rs:69-77`) does:
```rust
let bytes = hex_bytes(&hex_encoded).map_err(de_Error::custom)?;
let attachment = Attachment::new(bytes);
```
with no comparison of `bytes.len()` against `AtlasConfig::attachments_max_size` [1](#0-0) .

The result flows into `AttachmentsBatchStateContext::extend_with_attachments` (`download.rs:530-558`), which, on a successful decode, does only:
```rust
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
```
There is no check here that `response.attachment.hash() == request.content_hash`, nor any size check against `attachments_max_size` [2](#0-1) .

Downstream, `AtlasDB::insert_instantiated_attachment` (`db.rs:576-592`) performs the actual persistence with no size validation at all:
```rust
tx.execute(
    "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
    params![attachment.hash(), attachment.content, now],
)?;
``` [3](#0-2) 

By contrast, `AtlasDB::should_keep_attachment` (`db.rs:249-266`) explicitly enforces the size cap:
```rust
if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
    info!("Atlas: will discard posted attachment - attachment too large");
    return false;
}
``` [4](#0-3) 

This check is only exercised on the locally-submitted transaction/push path (`posttransaction.rs`), not on the remote-download path that calls `insert_instantiated_attachment` directly. So a malicious peer serving `/v2/attachments/{hash}` can return an oversized payload; if the returned bytes happen to hash to the requested `content_hash` (trivially satisfiable since the attacker controls both the served content and picks/knows the hash being requested — e.g. by serving exactly the legitimate content plus attacker doesn't even need a hash collision, they simply need the correct preimage of hash H, which for content the attacker fully controls end-to-end for hashes it advertises via its own attachment instance/inventory), the oversized content is written to the node's `attachments` table unmodified, bypassing the size guard that exists elsewhere in the same module.

### Impact Explanation
A remote, unprivileged peer that is included in `AttachmentRequest.sources` (i.e., advertises the attachment in its inventory) can serve unbounded-size content for an attachment hash and have it persisted into the victim node's `AtlasDB` via `insert_instantiated_attachment`, with no enforcement of `attachments_max_size`. This is a resource/state-integrity issue: the node's Atlas store size guarantee (bounded by `attachments_max_size`) is broken by a single crafted HTTP response from any peer serving the attachment. This matches the "bounded compute/storage DoS" flavor of the High-severity category, since the enforced invariant (`should_keep_attachment`'s size cap) is silently bypassed on the download code path.

### Likelihood Explanation
Precondition: the node must have an outstanding `AttachmentRequest` for a content hash `H` (this happens automatically as part of normal Atlas attachment resolution, e.g., driven by BNS name registrations), and the attacker's peer must be one of the `sources` offering that hash in its inventory — something any peer can advertise for content hashes it controls. No secret, admin role, or privileged access is required; this is reachable purely over the P2P/RPC-served attachment endpoint. The attacker only needs to run a normal peer and answer with a large body when queried.

### Recommendation
Enforce `attachments_max_size` in `GetAttachmentResponse::deserialize` (or immediately after decoding in `extend_with_attachments`), rejecting/truncating hex payloads whose decoded length exceeds the configured maximum, and also verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`. Additionally, call `should_keep_attachment`-equivalent validation (or the size check specifically) inside `insert_instantiated_attachment` itself so all persistence paths share the same invariant, rather than relying on callers to pre-filter.

### Proof of Concept
Rust test in `stackslib::net::atlas::download`:
1. Construct an `AtlasDB` with default `AtlasConfig` (`attachments_max_size = ATTACHMENTS_MAX_SIZE_MIN`).
2. Build a `GetAttachmentResponse` whose `attachment.content` is `ATTACHMENTS_MAX_SIZE_MIN + 1` bytes (or several MB) such that `Hash160::from_data(&content)` equals a chosen outstanding `content_hash` `H` that the downloader is tracking.
3. Feed this response through `AttachmentsBatchStateContext::extend_with_attachments` (or the full `AttachmentsDownloader::run` state machine) as if received from a peer HTTP response body for `/v2/attachments/{H}`.
4. Assert on `AtlasDB::find_attachment(&H)` (or query the `attachments` table directly) that the stored `content.len()` is `<= attachments_max_size`.
5. Expected (buggy) result: the assertion fails — the oversized content is stored, since neither `extend_with_attachments` nor `insert_instantiated_attachment` enforces the size bound that `should_keep_attachment` enforces on the push path.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
