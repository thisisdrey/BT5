### Title
`objectpool.FromRepo` trusts an attacker-controlled `objects/info/alternates` absolute path to identify an unrelated victim repository as the caller's "object pool" - ([File: internal/git/objectpool/pool.go])

### Summary
`objectpool.FromRepo` derives the "pool" identity purely from the content of the calling repository's `objects/info/alternates` file, without verifying that the resolved directory was actually established as a pool relationship for that repo (e.g. via `Link`). It only checks that the resolved path is *some* valid git repository via `locator.ValidateRepository`, not that the caller is an authorized member of that pool. Because `objects/info/alternates` is a plain file that can be injected via the `CreateRepositoryFromSnapshot` untrusted-tar-extraction path, and `stats.AlternatesInfoForRepository` (used here) does not enforce the storage-root/self-repo constraints that `internal/git/dirs.go`'s `altObjectDirs`/`ObjectDirectories` enforce, an attacker can plant an absolute alternates entry that resolves to a victim repository within the same storage.

### Finding Description
`FromRepo` (`internal/git/objectpool/pool.go:123-171`) reads the repo's alternates via `stats.AlternatesInfoForRepository(repoPath)` [1](#0-0) , takes the first absolute object directory, computes `relativePoolObjectDirPath = filepath.Rel(storagePath, absolutePoolObjectDirPath)`, and sets `objectPoolProto.Repository.RelativePath = filepath.Dir(relativePoolObjectDirPath)` [2](#0-1) . It then only checks `locator.ValidateRepository(ctx, objectPoolProto.GetRepository())` — i.e., "is this a syntactically/structurally valid repo path" — before treating that path as the caller's pool [3](#0-2) . There is no check that the target repository was actually linked as a pool for the calling repo (no bidirectional membership check, unlike `partition_assigner.go`'s `getAlternatePartitionID`, which does enforce `ErrAlternatePointsToSelf`/`ErrAlternateHasAlternate`/storage-root validation for WAL partitioning purposes) [4](#0-3) .

Critically, unlike `internal/git/dirs.go`'s `altObjectDirs`, which enforces `storagePrefix` containment when reading alternates for object-directory resolution [5](#0-4) , `stats.AlternatesInfoForRepository`/`ReadAlternatesFile` used by `FromRepo` performs no such validation — it simply returns whatever lines are in the file [6](#0-5) . The existing test suite for `FromRepo` confirms the only rejected case is a *non-existent* path (`ErrInvalidPoolRepository`) — it never tests (nor rejects) an absolute path pointing at another legitimately-existing repository the caller has no relationship with [7](#0-6) .

An attacker-controlled repository can get an arbitrary `objects/info/alternates` file written by using `CreateRepositoryFromSnapshot`, which extracts an attacker-supplied HTTP tar response directly on top of a freshly initialized bare repository with a documented warning that "the received archive is trusted *a lot*" [8](#0-7) . The extraction path validation (`extractTarToDirectory` in `replicate.go`) guards against path traversal/absolute symlinks escaping the *target directory*, but places no restriction on the *contents* written to a legitimate in-bounds file such as `objects/info/alternates`, so an attacker can write an absolute path string (pointing at a victim repo elsewhere in the same storage) into that file.

The reachable sink for this crafted repo is `GetObjectPool` RPC, the only production caller of `objectpool.FromRepo`: `internal/gitaly/service/objectpool/get.go:13-42` calls `s.locator.ValidateRepository(ctx, repository)` on the attacker's own (valid) repo, then calls `objectpool.FromRepo` on it, and returns `objectPoolProto` — including the victim repo's `StorageName`/`RelativePath` — directly in the RPC response [9](#0-8) .

### Impact Explanation
The primary concrete, provable impact is cross-tenant information disclosure: an attacker who owns a repository can, without further authorization, learn the internal relative storage path (and confirm the existence) of an unrelated victim repository by calling `GetObjectPool` on their crafted repository. This corresponds to GitLab's "information disclosure"/"broken access control" bounty classes (disclosure of another user's private repository's internal path/metadata). The broader claim in the question — that this leads to full pool-scoped destructive operations such as object migration against the victim — is not substantiated by the code: other pool-mutating RPCs (`LinkRepositoryToObjectPool`, `FetchIntoObjectPool`, `DeleteObjectPool`, etc.) take the pool repository directly as an explicit, separately-validated RPC field (via `ExtractPool`/`FromProto`, which additionally checks `storage.IsPoolRepository` or temp-dir prefix) rather than through `FromRepo`'s alternates-derived resolution, so this specific `FromRepo` code path does not, by itself, grant write/migrate access to the victim repo.

### Likelihood Explanation
Feasibility depends on two independently-plausible-but-unverified preconditions within this codebase snapshot: (1) that `CreateRepositoryFromSnapshot`'s trusted-tar-extraction is reachable by an unprivileged, non-admin GitLab user for a repository they control (this RPC is documented as untrusted-input-sensitive but its authorization scope wasn't fully confirmed here), and (2) that the target victim repository resides in the same Gitaly storage and its relative path is loosely guessable/enumerable by the attacker (needed to craft the alternates entry, though brute-forcing hashed storage paths is impractical — this substantially limits real-world exploitability). Given these constraints, likelihood is moderate-to-low without further confirmation of RPC authorization scoping for `CreateRepositoryFromSnapshot` and typical `@hashed` path secrecy in target environments.

### Recommendation
`objectpool.FromRepo` should not treat "resolves to a syntactically valid repository" as sufficient proof of pool membership. It should additionally verify a genuine bidirectional pool relationship, e.g. by confirming the resolved directory is marked as a pool repository (`storage.IsPoolRepository`) and/or that the pool's membership records/back-reference include the calling repository, mirroring the stronger checks already present in `getAlternatePartitionID` (self-reference and nested-alternate rejection, storage-root containment) in `internal/gitaly/storage/storagemgr/partition_assigner.go`. Additionally, `stats.AlternatesInfoForRepository`/`ReadAlternatesFile` should validate alternates paths against storage-root containment consistently with `internal/git/dirs.go`'s `altObjectDirs`, and `CreateRepositoryFromSnapshot`/`extractTarToDirectory` should sanitize or reject writes to sensitive metadata files like `objects/info/alternates` (or re-validate/re-write such files, as is done for `config` and `hooks`) rather than trusting raw archive content.

```go
// ReadAlternatesFile returns the repository's alternate object directory paths
// from '<repo>/objects/infop/alternates' and returns them. Returns a wrapped
// fs.ErrNotExist if the file doesn't exist.
func ReadAlternatesFile(repoPath string) ([]string, error) {
	file, err := os.Open(AlternatesFilePath(repoPath))
	if err != nil {
		return nil, fmt.Errorf("open: %w", err)
	}
	defer file.Close()

	var alternatePaths []string
	scanner := bufio.NewScanner(file)
	for scanner.Scan() {
		line := scanner.Bytes()

		switch {
		case len(line) == 0:
			// Empty lines are skipped by Git.
			continue
		case bytes.HasPrefix(line, []byte("#")):
			// Lines starting with a '#' are comments and thus need to be skipped.
			continue
		default:
			alternatePaths = append(alternatePaths, scanner.Text())
		}
	}

	if err := scanner.Err(); err != nil {
		return nil, fmt.Errorf("scanning alternate paths: %w", err)
	}

	return alternatePaths, nil
}
```

```go
func (s *server) GetObjectPool(ctx context.Context, in *gitalypb.GetObjectPoolRequest) (*gitalypb.GetObjectPoolResponse, error) {
	repository := in.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(repository)
	objectPool, err := objectpool.FromRepo(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, repo)
	if err != nil && !errors.Is(err, objectpool.ErrAlternateObjectDirNotExist) {
		s.logger.
			WithError(err).
			WithField("storage", repository.GetStorageName()).
			WithField("relative_path", repository.GetRelativePath()).
			WarnContext(ctx, "alternates file does not point to valid git repository")
	}

	if objectPool == nil {
		return &gitalypb.GetObjectPoolResponse{}, nil
	}

	objectPoolProto := objectPool.ToProto()
	if tx := storage.ExtractTransaction(ctx); tx != nil {
		// The object pool's relative path is pointing to the transaction's snapshot. Return
		// the original relative path in the response.
		objectPoolProto.Repository = tx.OriginalRepository(objectPoolProto.GetRepository())
	}

	return &gitalypb.GetObjectPoolResponse{
		ObjectPool: objectPoolProto,
	}, nil
```
