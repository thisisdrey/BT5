### Title
Signer weight double-counted across approve/reject tallies when `TryFrom<StackerDBChunksEvent>` yields multiple entries for the same slot - (File: `libsigner/src/events.rs`, `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`TryFrom<StackerDBChunksEvent> for SignerEvent<T>` (`libsigner/src/events.rs:568-620`) builds its `messages` vector by iterating `event.modified_slots` and pushing one `(slot_id, pk, message)` tuple per chunk, without any deduplication by `slot_id` or `slot_version`. `StackerDBListener::run` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:372-591`) then processes every tuple sequentially against a single, persistent `BlockStatus` (`self.blocks`), and its two vote-counting guards (`gathered_signatures` for `Accepted`, `responded_signers` for `Rejected`) are asymmetric, letting one slot-owning signer contribute weight to both `total_weight_approved` and `total_weight_rejected` for the same block.

### Finding Description
`TryFrom<StackerDBChunksEvent>` does not enforce "one message per slot, latest version wins": every valid chunk in `event.modified_slots` becomes its own `(slot_id, pk, message)` entry in `messages` [1](#0-0) . If a slot owner signs two chunks at strictly increasing versions (e.g. version N = `BlockResponse::Rejected`, version N+1 = `BlockResponse::Accepted`, for the same `signer_signature_hash`), the StackerDB replica accepts and stores both, since `try_replace_chunk` only requires `slot_version` to strictly increase [2](#0-1) , and both chunks are gathered into a single `StackerDBChunksEvent` batch by `process_stacker_db_chunks`/`process_new_stackerdb_chunks` [3](#0-2) .

In `StackerDBListener::run`, both resulting tuples are processed against the same `BlockStatus` entry keyed by `block_sighash` in `self.blocks` [4](#0-3) . The `Accepted` branch guards weight increments with `!block.gathered_signatures.contains_key(&slot_id)` and then unconditionally does `block.gathered_signatures.insert(...)` and `block.responded_signers.insert(slot_id)` [5](#0-4) . The `Rejected` branch guards its weight increment with `if block.responded_signers.insert(slot_id) { ... }` [6](#0-5) .

Because these are two different sets, processing order matters: if `Rejected` is processed first (populating only `responded_signers`) and `Accepted` second (its guard checks the *different* `gathered_signatures` map, which is still empty), `total_weight_rejected` and `total_weight_approved` are **both** incremented by the same signer's weight for the same block. Since chunk-store ordering follows version ordering (lower version must be stored first), an attacker fully controls this by signing Rejected at the lower version and Accepted at the higher version. This double count is not prevented anywhere else in the code path — the RPC/`try_replace_chunk` version check, the `recover_pk`/signature checks in `TryFrom`, and the `signer_set`/`weight_threshold` checks in the listener all pass normally, because both messages are legitimately signed by the slot owner.

### Impact Explanation
A single unprivileged signer who legitimately owns one StackerDB slot can inflate the miner's local `BlockStatus.total_weight_approved` counter (used to decide when `weight_threshold` has been reached and trigger `cvar.notify_all()` for block signature collection) by their own weight in addition to correctly inflating `total_weight_rejected`. This corrupts the miner's local bookkeeping of how much distinct signer weight has genuinely approved a block, letting the approval threshold be reached with less real distinct signer weight than the protocol requires — i.e., the node can be made to treat a block as having met the accept threshold when it should not have. This affects only the local coordinator's threshold decision (not the wire-format signature set assembled from `gathered_signatures`, which is deduplicated by `slot_id` regardless of ordering), so the severity is bounded to premature/incorrect threshold signaling on the affected miner node rather than a network-wide forged/stored artifact.

### Likelihood Explanation
Preconditions: the attacker must already legitimately own a StackerDB slot in the `.signers-*` contract for the reward cycle in question (a normal, unprivileged signer role) and must be able to push two chunks to the target node in the correct version order within the time window before the node's `StackerDBListener` processes them (either in one batched `StackerDBChunksEvent`, or in two separate ones — the persistent `self.blocks` map means the state survives across polling iterations, so exact batching is not even required). No secret, admin role, or additional privilege is needed; cost is minimal (two signed writes to an owned StackerDB slot) and is repeatable per block/slot.

### Recommendation
Make `BlockStatus` weight tracking symmetric and idempotent per signer regardless of message-type ordering: use a single "already-counted" set per `(slot_id)` (or `HashMap<slot_id, LastVote>`) that governs both the approve and reject weight increments, so a signer's weight is added to at most one bucket total for a given block, and switching between Accept/Reject only updates which bucket holds the weight (decrementing the old bucket, incrementing the new one) rather than allowing both. Additionally, consider having `TryFrom<StackerDBChunksEvent>` retain only the highest-`slot_version` chunk per `slot_id` before building `messages`, to make "one message per slot per event" an explicit invariant for downstream consumers.
