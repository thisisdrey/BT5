### Title
Liquidations of positions with debt below `debtFloorInUsd` permanently revert, leaving bad debt unliquidatable - ([File: contracts/Pool.sol])

### Summary
CVE-2019-9496 is a "missing state validation → crash → denial of service" bug: an out-of-sequence message hits a code path with no state check and kills the process. The Metronome analog is `Pool.liquidate`: two independently reasonable state checks — the `maxLiquidable` repayment cap and the `debtFloorInUsd` minimum-debt floor — are combined without a validation branch for the case where they are mutually exclusive. When a position's debt sits below `debtFloorInUsd`, every possible `amountToRepay_` reverts, permanently disabling liquidation for that position.

### Finding Description
`Pool.liquidate` enforces two checks on `amountToRepay_` against the account's `DebtToken` balance:

1. Close-factor cap: `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` reverts with `AmountGreaterThanMaxLiquidable` (`contracts/Pool.sol:567`). `maxLiquidable` is a governor-set fraction below 1 (e.g. 0.5), so repaying 100% of the debt always fails this check.
2. Debt floor: if `debtFloorInUsd > 0`, the remaining debt after repayment must be either 0 or ≥ `debtFloorInUsd`, otherwise it reverts with `RemainingDebtIsLowerThanTheFloor` (`contracts/Pool.sol:571-579`).

For an account whose total debt value is below `debtFloorInUsd`:
- Any partial repayment leaves `_newDebtInUsd` in `(0, debtFloorInUsd)` → reverts on the floor check.
- A full repayment leaves `_newDebtInUsd == 0` and passes the floor, but `amountToRepay_ / _debtTokenBalance == 1 > maxLiquidable` → reverts on the close-factor check.

All inputs revert: the position can never be liquidated. There is no special-case branch permitting full repayment when the floor would otherwise make partial liquidation impossible — the missing state validation, exactly the CVE's bug class.

Such positions are trivially reachable by an unprivileged user: the attacker deposits collateral and issues synthetic debt just above `debtFloorInUsd` (the floor is enforced at issuance but not maintained afterward), then the position drifts below the floor via interest accrual in `DebtToken.accrueInterest` or collateral price movement (which the attacker can also induce same-transaction via AMM-fed oracle paths if applicable). Once underwater, no liquidator can clear it. Equivalently, a liquidator can partially liquidate a victim down to below the floor, after which the victim's remaining position is permanently unliquidatable.

### Impact Explanation
Permanent liveness failure of `Pool.liquidate` for any account with debt below `debtFloorInUsd`. When such a position is undercollateralized, its bad debt can never be repaid/seized, so the protocol is left holding unbacked synthetic-token obligations — direct protocol insolvency plus permanent freezing of the position (the user's collateral stays locked and the debt can only be exited by the debtor voluntarily repaying). The attacker cost is bounded by their own underwater position's collateral, making cheap griefing/insolvency accumulation feasible.

### Likelihood Explanation
High reachability: `liquidate` is a public, unprivileged entry point; creating a sub-floor debt position requires only a normal deposit + `DebtToken.issue` flow. The trigger (debt crossing below the floor through accrued interest or price drift) requires no privileged action. The only mitigations are governor-set parameters (`debtFloorInUsd == 0` disables the floor check; `maxLiquidable == 1` removes the conflict), so severity depends on deployed configuration — with both set as intended (floor > 0, close factor < 1), the DoS is deterministic.

### Recommendation
In `Pool.liquidate`, special-case the floor: allow full repayment (`amountToRepay_ == _debtTokenBalance`) to bypass `maxLiquidable`, or skip the `debtFloorInUsd` check when the account's total debt is already below the floor. Alternatively, compute the required repayment as `max(minLiquidable, amountToRepay_)` semantics that force full repayment when `remaining < debtFloorInUsd`.

### Proof of Concept
Hardhat fork test sketch:

```ts
// Setup: pool with debtFloorInUsd = $100, maxLiquidable = 0.5e18
await feeProvider.updateProtocolLiquidationFee(0)
await pool.updateDebtFloorInUsd(toUSD('100'))
await pool.updateMaxLiquidable(parseEther('0.5'))

// Attacker deposits collateral and issues debt slightly above the floor ($101)
await metDepositToken.connect(attacker).deposit(collateral, attacker.address)
await msEthDebtToken.connect(attacker).issue(debtJustAboveFloor, attacker.address)

// Collateral price drops (or interest accrues) -> position unhealthy,
// total debt now below floor in USD terms or remaining-debt constraint binds
await masterOracle.updatePrice(met.address, lowerPrice)
const position = await pool.debtPositionOf(attacker.address)
expect(position._isHealthy).false

// Partial liquidation: leaves dust debt below floor -> reverts
const debt = await msEthDebtToken.balanceOf(attacker.address)
await expect(
  pool.connect(liquidator).liquidate(msEth.address, attacker.address, debt.div(4), msdMET.address)
).revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor')

// Full liquidation: exceeds maxLiquidable -> reverts
await expect(
  pool.connect(liquidator).liquidate(msEth.address, attacker.address, debt, msdMET.address)
).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable')

// Position is permanently unliquidatable -> bad debt persists
```
