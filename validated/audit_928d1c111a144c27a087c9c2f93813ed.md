### Title
Missing Is4In6 rejection in unsafeNetworks validation allows ambiguous IPv4-mapped-IPv6 unsafe networks to bypass the same check applied to `networks` - ([File: cert/cert_v2.go])

### Summary
In `certificateV2.validate()`, the loop over `c.details.networks` explicitly rejects IPv4-in-IPv6 (`Is4In6`) addresses, but the parallel loop over `c.details.unsafeNetworks` omits that check. An attacker who controls the DER-encoded `TagDetailsUnsafeNetworks` octet strings passed through `unmarshalDetails` can therefore get an `Is4In6` prefix (e.g. `::ffff:10.0.0.0/104`) accepted into `unsafeNetworks` even though the equivalent value is disallowed for `networks`.

### Finding Description
`unmarshalDetails` reads each network entry as an ASN.1 OCTET STRING bounded to `MaxNetworkLength` (17 bytes) and calls `netip.Prefix.UnmarshalBinary` on it, for both `TagDetailsNetworks` and `TagDetailsUnsafeNetworks` [1](#0-0) . Post-parse validation happens in `certificateV2.validate()`. For `c.details.networks`, the loop checks `IsValid()`, `Addr().IsValid()`, `IsUnspecified()`, `Zone() != ""`, and critically `Addr().Is4In6()` [2](#0-1) . For `c.details.unsafeNetworks`, the loop checks `IsValid()`, `Addr().IsValid()`, `Zone() != ""`, and the IPv4/IPv6 assignment cross-check against `hasV4Networks`/`hasV6Networks`, but it never calls `Is4In6()` [3](#0-2) .

Because `Is4In6()` addresses report `Is6() == true` and `Is4() == false` in Go's `net/netip` semantics, such an address passes the `network.Addr().Is6()` branch of the unsafe-network check as long as the certificate has at least one real IPv6 network assigned (`hasV6Networks == true`) [4](#0-3) . This produces an accepted `unsafeNetworks` entry whose address is simultaneously a valid-looking IPv6 prefix and semantically an IPv4 address range (`::ffff:a.b.c.d`), which is exactly the class of address the sibling `networks` loop treats as invalid/ambiguous and explicitly rejects.

This is reachable purely from certificate content the attacker controls (their own cert's details), through `fromTBSCertificate` -> `validate()` or through `unmarshalCertificateV2` -> `unmarshalDetails` -> `validate()` when the certificate is parsed by a peer, with no privileged access required.

### Impact Explanation
Nebula's firewall/route-trust logic distinguishes IPv4 vs IPv6 address families and uses `UnsafeNetworks()` to permit non-certificate traffic to be routed/allowed through a host (see `firewall.go` usage of unsafe networks). An `Is4In6`-form unsafe network slipping past the same guard that rejects it for regular `networks` creates an inconsistency between how the two lists are validated, which is exactly the "invalid/ambiguous network" condition the question is probing. This is a scoped, real gap in input validation consistency, matching a firewall/network-policy-integrity class bounty issue, though I could not fully confirm within the available tool budget whether downstream firewall matching code (`firewall.go`) actually mishandles `Is4In6` addresses when matching packets (e.g., treating `::ffff:a.b.c.d` differently for IPv4 packets than intended) — that would be required to escalate this from "inconsistent validation" to a confirmed "firewall bypass."

### Likelihood Explanation
This is a certificate content issue, requires no cryptographic bypass — an attacker only needs to embed such a network in the `unsafeNetworks` field of their own certificate details before it is signed by a CA, or, if this code path is also reached on parsing arbitrary untrusted cert bytes before signature verification, on any attacker-supplied bytes. The `MaxNetworkLength` (17-byte) boundary check does not prevent this, since a 17-byte octet string is exactly what a 16-byte IPv6 address plus 1-byte prefix-length encodes, which comfortably fits an `Is4In6` address. It is fully deterministic and repeatable.

### Recommendation
Add the same `Is4In6()` rejection to the `unsafeNetworks` validation loop in `cert/cert_v2.go` `validate()` (lines ~431-451) that already exists for `networks` (line 417-419), so both lists reject IPv4-mapped-IPv6 addresses consistently.

### Proof of Concept
Unit test in `cert/cert_v2_test.go`:
1. Build a non-CA `detailsV2` with `networks = [netip.MustParsePrefix("2001:db8::1/128")]` (to set `hasV6Networks = true`) and `unsafeNetworks = [netip.MustParsePrefix("::ffff:10.0.0.0/104")]` (an `Is4In6` prefix).
2. Marshal via `d.Marshal()`, then round-trip through `unmarshalDetails` and `c.validate()` (or directly call `validate()` on a `certificateV2` built via `fromTBSCertificate`).
3. Assert that `validate()` returns an error (expected fix behavior) — currently it returns `nil`, demonstrating the inconsistency versus the equivalent case for `networks`, where the same prefix in `networks` is correctly rejected with `NewErrInvalidCertificateProperties("4in6 networks are not allowed: %s", network)`.
