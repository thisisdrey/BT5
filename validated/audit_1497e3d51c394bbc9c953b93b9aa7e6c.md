## Title
Protocol fee on `Nep245`/`Imt` transfers is bypassed by splitting a single logical transfer into multiple unit-magnitude `TokenDiff` intents within one signed batch - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` waives the protocol fee for `Nep245`/`Imt` tokens whenever the *local* delta magnitude of a single `TokenDiff` intent is `<= 1`. Because a signer can pack an arbitrary number of `TokenDiff` intents into one signed `DefuseIntents` payload, any transfer of size `N` can be decomposed into `N` separate `TokenDiff` intents each with `delta = -1` on the same `token_id`, each independently qualifying for the zero-fee branch, while producing the exact same net balance change (`-N`) as a single unsplit `delta = -N` intent that would otherwise be fee-liable.

### Finding Description
The broken binding is:
`total_fee_collected(token, net_delta = -N)` should be identical regardless of how the signer chooses to encode that `-N` delta across intents in the same signed batch — i.e. `fee(split into N unit legs) == fee(one -N leg)`.

In code, `token_fee` decides zero-fee eligibility using only the magnitude of the delta *within a single `TokenDiff`'s map entry*, not the net effect across the whole `DefuseIntents.intents` sequence signed by that user: [1](#0-0) 

```
pub fn token_fee(token_id: impl Into<TokenIdType>, amount: u128, fee: Pips) -> Pips {
    match token_id {
        TokenIdType::Nep141 => {}
        TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}
        TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt => return Pips::ZERO,
    }
    fee
}
```

`execute_intent` invokes this per `(token_id, delta)` pair *inside a single `TokenDiff`'s `diff` map* [2](#0-1) , and `DefuseIntents::execute_intent` simply iterates the signer's `Vec<Intent>` executing each one independently with no cross-intent aggregation of amounts for fee purposes [3](#0-2) . `Intent` is an enum that includes `TokenDiff` as one of its variants and multiple `TokenDiff` intents can appear in the same `intents: Vec<Intent>` list inside a single `DefuseIntents` message signed once by the user [4](#0-3) .

**Exploit flow:** the attacker signs one `DefusePayload<DefuseIntents>` whose `intents` field contains `N` `TokenDiff` intents, each with `diff = {mt_token_id: -1}` (map constraint respected since each `TokenDiff`'s map has only one entry for that key). Submitted via `execute_intents`/`simulate_intents`, each intent independently calls `token_fee(Nep245, amount=1, fee)` → `Pips::ZERO`, so `fee_ceil(1) == 0` for every leg. The cumulative balance debit on the signer is `-N`, identical to what a single `TokenDiff{diff:{mt_token_id: -N}}` would produce, but the single-intent version would call `token_fee(Nep245, amount=N>1, fee)` → nonzero `fee`, and collect `fee.fee_ceil(N) > 0` credited to `fee_collector`. No existing guard (`MultiPayload::verify`, nonce checks, `#[private]`) inspects cross-intent amount aggregation for fee-threshold purposes — those guards protect signature/replay integrity, not fee accounting logic.

### Impact Explanation
The protocol under-collects fees on `Nep245`/`Imt`-typed token transfers of arbitrary size for any unprivileged signer, matching the explicitly listed Critical category "protocol fees bypassed or over-collected." This is fully repeatable: any account can apply it to every `Nep245`/`Imt` `token_id` and any transfer magnitude `N`, at the cost of only extra intents inside the same signed payload (no extra signatures, no privileged role needed). It does not move funds out of the Verifier beyond what the signer already authorized, but it starves `fee_collector` of legitimately owed revenue on every such trade route, which is the harm this fee mechanism exists to prevent.

### Likelihood Explanation
Preconditions are minimal: an account holding any `Nep245`/`Imt` balance and the ability to sign a single `DefusePayload` with `N` `TokenDiff` intents (bounded only by gas/payload size, which is out of scope to consider as a blocker). No special role, relayer key, or counterparty cooperation is required for the fee-bypass itself (a counterparty is only needed to balance the overall intent batch to zero-sum, as with any normal trade) — the fee omission occurs independent of whether the batch nets to zero. This is trivially and repeatably exploitable by any user on every negative delta of `Nep245`/`Imt` tokens.

### Recommendation
Compute `token_fee` eligibility from the *aggregate* negative delta per `token_id` per signer across the whole `DefuseIntents.intents` sequence (or reject/merge multiple `TokenDiff` intents touching the same `token_id` within one signed message before fee assessment), rather than from the per-`TokenDiff`-instance delta magnitude, so that `amount > 1` reflects total transfer size regardless of how the signer chooses to split it into intents.

### Proof of Concept
```rust
// crates/num-utils or contracts/defuse/core: property test
#[rstest]
#[case(2)] #[case(10)] #[case(100)] #[case(10000)]
fn fee_bypass_via_unit_split(#[case] n: u128) {
    let fee = Pips::ONE_PERCENT;
    let token_id: TokenId = Nep245TokenId::new("mt.near".parse().unwrap(), "ft1".into()).into();

    // Unsplit: one TokenDiff with delta = -n
    let fee_unsplit = TokenDiff::token_fee(&token_id, n, fee).fee_ceil(n);

    // Split: n TokenDiff intents each with delta = -1
    let fee_split: u128 = (0..n)
        .map(|_| TokenDiff::token_fee(&token_id, 1, fee).fee_ceil(1))
        .sum();

    assert!(fee_unsplit > 0, "unsplit path should charge fee for n>1");
    assert_eq!(fee_split, 0, "split path collects zero fee regardless of n");
    assert_ne!(fee_unsplit, fee_split, "fee bypassed via splitting for n={n}");
}
```
Combined with a `near-workspaces`/sandbox test signing one `DefusePayload<DefuseIntents>` containing `n` `TokenDiff{diff:{mt_token_id: -1}}` intents (balanced by a counterparty leg) versus one `TokenDiff{diff:{mt_token_id: -n}}`, and asserting `fee_collector`'s post-execution balance is `0` in the split case and `> 0` in the unsplit case for the same net signer debit, demonstrates the discrepancy end-to-end via `execute_intents`.
