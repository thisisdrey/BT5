## Title
Permissionless donation via `lending_pool_emissions_deposit` enables classic share-inflation (first-depositor) attack on marginfi Banks - (File: programs/marginfi/src/instructions/marginfi_group/configure_bank.rs)

## Summary
`lending_pool_emissions_deposit` is a permissionless instruction that lets *any* signer transfer tokens directly into a Bank's `liquidity_vault` and have that amount immediately folded into `asset_share_value` for all existing depositors, without minting any new shares. Combined with the fact that a depositor can withdraw down to a near-zero share balance while leaving residual assets in the bank, this reproduces the classic ERC-4626/VotiumStrategy "inflation attack": an attacker can inflate `asset_share_value` right before a victim's deposit, causing the victim's `mintAmount` to round down to (near) zero shares while the attacker (holding the last surviving shares) can later claim the inflated value.

## Finding Description
Bank share accounting is: `asset_amount = shares * asset_share_value`, and deposits compute `get_asset_shares(value) = value / asset_share_value` [1](#0-0) .

`lending_pool_emissions_deposit` transfers `amount` of the bank's own mint from an arbitrary `depositor` account straight into the `liquidity_vault`, then recomputes:
```
total_assets = get_asset_amount(total_asset_shares)
updated_total_assets = total_assets + amount
asset_share_value = updated_total_assets / total_asset_shares
``` [2](#0-1) 

This instruction has **no admin/authority check on the caller** (`depositor` is just a `Signer`, and the only gates are `validate_bank_state`, non-fee-mint check, and `total_asset_shares > 0`) — it is explicitly documented as "Permissionlessly deposit same-mint emissions directly into the bank liquidity vault, increasing depositor value through asset share value" [3](#0-2) .

Because this raises `asset_share_value` for the *whole* pool without minting new shares, it is functionally equivalent to the "donation" step in the VotiumStrategy inflation attack (steps 3–4 in the referenced report), where an attacker inflates the share price so that a subsequent depositor's shares round down to zero.

Attack sketch, using marginfi's real mechanics:
1. Attacker deposits `D` tokens into an otherwise-empty (or low-TVL) Bank via `lending_account_deposit`, getting `D` shares at `asset_share_value = 1` (first-deposit case, confirmed 1:1 minting in tests) [4](#0-3) .
2. Attacker withdraws `D - 1` tokens (burning `D - 1` shares), leaving `1` share and `1` token of principal in the bank (this is standard `withdraw`, which burns shares proportional to `amount / asset_share_value`) [5](#0-4) .
3. Attacker (or anyone) calls `lending_pool_emissions_deposit(Y)`, donating `Y` tokens into the `liquidity_vault`. Since `total_asset_shares = 1`, `asset_share_value` jumps to `1 + Y` [6](#0-5) .
4. Victim deposits `X` tokens (e.g. via `AfEth`-analogous flows, or a JupLend/Kamino wrapped-bank deposit routed through this same bank), and `get_asset_shares(X) = X / (1+Y)`, which floors to `0` if `X <= Y`.
5. Victim's shares are effectively minted as zero, and the attacker (still holding the surviving 1 share, now worth `1+Y+X`) can withdraw the entire pool including the victim's principal.

This mirrors the exact math and consequence from the [M-08] VotiumStrategy report: no minimum-output validation on minted shares, and share price derived from freely-donatable balance rather than a controlled, non-donatable internal counter.

## Impact Explanation
If reachable with unprivileged accounts, this is a direct **theft of victim deposits** and causes the victim's shares to be minted as zero while their principal is absorbed into the attacker-controlled share, i.e. concrete theft/insolvency for that depositor — matching the severity class validated by the original report (Medium, confirmed and mitigated upstream in Asymmetry's codebase).

## Likelihood Explanation
Requires (a) a bank with very low total_asset_shares (attacker can artificially create this state by being first depositor and withdrawing almost all shares) and (b) the emissions-deposit instruction being callable by any signer with tokens — both preconditions are satisfied in-repo based on the code and its own doc comment describing it as "permissionless." However, I was unable to fully confirm within the available iterations whether `lending_pool_emissions_deposit`'s `Accounts` struct enforces any additional privileged constraint (e.g., `has_one = admin` on `depositor`, or a required relationship to the `group`), since the tool call to read the exact `#[derive(Accounts)] pub struct LendingPoolEmissionsDeposit` struct failed at the final iteration. The function body I did retrieve shows no admin check performed inside the handler itself, and the doc comment explicitly states "Permissionlessly," which is strong (but not 100%-certain-from-struct-definition) evidence that any signer can invoke it.

## Recommendation
- Verify (or, if not already present, add) a strict `require!(total_asset_shares >= MINIMUM_SHARES_THRESHOLD)` or a minimum "dead shares" mechanism for a bank's first deposit, similar to UniswapV2, to prevent driving `total_asset_shares` down to a trivially small value.
- Alternatively, require a minimum-output check (`min_shares_out`) on `lending_account_deposit`/wrapped-bank deposit paths so a caller can reject a transaction if the computed shares round to (near) zero due to a manipulated `asset_share_value`.
- Confirm the actual account constraints on `LendingPoolEmissionsDeposit` (I was unable to view the struct definition in this pass) and, if it is indeed unauthenticated to any particular privileged role, consider gating the max single-call inflation ratio, or disallow the deposit when `total_asset_shares` is below a floor.

## Proof of Concept
Conceptual, based on retrieved code paths (not executed):
1. `lending_account_deposit(D)` into fresh Bank → attacker gets `D` shares at `asset_share_value = 1`.
2. `lending_account_withdraw(D-1)` → attacker left with `1` share, bank holds `1` token.
3. `lending_pool_emissions_deposit(Y)` (any signer) → `asset_share_value` becomes `1+Y` per the formula in [6](#0-5) .
4. Victim's `lending_account_deposit(X)` with `X <= Y` → `get_asset_shares(X) = X/(1+Y)` floors to `0` per [7](#0-6) , minting zero shares for the victim while their tokens remain in the vault, now claimable by the attacker's single surviving share.

/// Permissionlessly deposit same-mint emissions directly into the bank liquidity vault,
/// increasing depositor value through asset share value.
pub fn lending_pool_emissions_deposit(
    ctx: Context<LendingPoolEmissionsDeposit>,
    amount: u64,
) -> MarginfiResult {
    if amount == 0 {
        return Ok(());
    }

    let clock = Clock::get()?;
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = ctx.accounts.group.load()?;

    utils::validate_bank_state(&bank, utils::InstructionKind::FailsIfPausedOrReduceState)?;

    // Reject mints with non-zero transfer fees or active transfer hooks.
    let mint_ai = ctx.accounts.mint.to_account_info();
    check!(
        !utils::nonzero_fee(mint_ai.clone(), clock.epoch)?,
        MarginfiError::InvalidTransfer
    );
    check!(
        !utils::has_transfer_hook(mint_ai)?,
        MarginfiError::InvalidTransfer
    );

    let total_asset_shares = I80F48::from(bank.total_asset_shares);
    check!(
        total_asset_shares > I80F48::ZERO,
        MarginfiError::EmissionsUpdateError
    );

    bank.accrue_interest(
        clock.unix_timestamp,
        &group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    transfer_checked(
        CpiContext::new(
            ctx.accounts.token_program.key(),
            TransferChecked {
                from: ctx.accounts.emissions_funding_account.to_account_info(),
                to: ctx.accounts.liquidity_vault.to_account_info(),
                authority: ctx.accounts.depositor.to_account_info(),
                mint: ctx.accounts.mint.to_account_info(),
            },
        ),
        amount,
        ctx.accounts.mint.decimals,
    )?;

    let total_assets = bank.get_asset_amount(total_asset_shares)?;
    let updated_total_assets = total_assets
        .checked_add(I80F48::from_num(amount))
        .ok_or_else(math_error!())?;

    bank.asset_share_value = updated_total_assets
        .checked_div(total_asset_shares)
        .ok_or_else(math_error!())?
        .into();

    bank.update_bank_cache(&group)?;

    msg!(
        "Deposited {} same-bank emissions into liquidity vault",
        amount
    );
```
