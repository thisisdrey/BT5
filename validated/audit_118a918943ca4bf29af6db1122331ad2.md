Audit Report

## Title
Silent payout failure via `debug_assert!` in `claim_child_bounty` permanently locks child-bounty funds - ([File: substrate/frame/child-bounties/src/lib.rs])

## Summary
`pallet-child-bounties::claim_child_bounty` performs two `T::Currency::transfer` calls (curator fee and beneficiary payout) with `AllowDeath`, checking their success only via `debug_assert!`, which is compiled out in release builds. Regardless of transfer outcome, the function unconditionally proceeds to decrement `ParentChildBounties`, remove `ChildBountyDescriptionsV1`, and set `*maybe_child_bounty = None`, permanently deleting the only on-chain reference to the derived `child_bounty_account`.

## Finding Description
In `claim_child_bounty`, the fee transfer to `curator` and payout transfer to `beneficiary` use `T::Currency::transfer(..., AllowDeset)` and are validated only with `debug_assert!(fee_transfer_result.is_ok())` and `debug_assert!(payout_transfer_result.is_ok())`. [1](#0-0) 

In a release build, these `debug_assert!` calls compile to no-ops, so any transfer failure is silently discarded, yet the code unconditionally proceeds to decrement the active-child-bounty counter, remove the description, and null out the storage entry: [2](#0-1) 

There is no minimum-value or ExistentialDeposit enforcement anywhere in this pallet's `add_child_bounty`, `propose_curator`, or `claim_child_bounty` logic beyond `fee < child_bounty.value` in `propose_curator`. [3](#0-2)  Both `curator` and `beneficiary` are attacker-influenced values reachable via the standard `propose_curator` → `accept_curator` → `award_child_bounty` → `claim_child_bounty` flow using only ordinary signed extrinsics, with no privileged or governance action required to trigger the vulnerable path. `Currency::transfer` with `AllowDeath` to an account that does not already exist and would end up below `ExistentialDeposit` returns an error rather than creating a sub-ED account, and that error is exactly what the `debug_assert!` fails to gate on in release builds. Once the storage entry is deleted, `child_bounty_account` — a deterministic derived account — has no remaining dispatchable path that references it, so any balance retained there because a transfer failed is permanently stranded.

## Impact Explanation
This matches the "permanent user-fund lock" impact category: any successful call to `claim_child_bounty` where a fee or payout transfer fails below ED strands the remaining treasury-derived funds in `child_bounty_account` irrecoverably, and is triggerable by ordinary signed accounts (curator/caller), not privileged actors.

## Likelihood Explanation
Triggering requires only a child bounty whose `fee` or `value - fee` remainder is set below the runtime's `ExistentialDeposit`, and a `curator`/`beneficiary` account without a pre-existing balance ≥ ED — both fully controllable by an attacker through the standard `add_child_bounty` → `propose_curator` → `accept_curator` → `award_child_bounty` → `claim_child_bounty` flow. Because `debug_assert!` is compiled out in production/release builds (the deployed configuration for real chains), the bug is live and reachable, not merely a theoretical debug-only issue.

## Recommendation
Replace both `debug_assert!(fee_transfer_result.is_ok())` and `debug_assert!(payout_transfer_result.is_ok())` with proper `?`-propagated error handling (or `ensure!`) inside the `try_mutate_exists` closure so a failed transfer aborts the whole extrinsic and rolls back storage changes atomically with the transfer. Additionally, enforce minimum child-bounty `fee` and payout-remainder values (or use `Preservation::Preserve`/`KeepAlive` semantics with correct error propagation) so transfers to newly specified curator/beneficiary accounts cannot silently fail due to ED requirements.

## Proof of Concept
1. Parent curator creates a parent bounty and calls `add_child_bounty` with `value` slightly above `ExistentialDeposit`.
2. `propose_curator` sets a nonzero `fee` for a zero-balance `curator` account such that `fee` (or `value - fee`) is below `ExistentialDeposit`.
3. `accept_curator` is called by that curator, reserving `curator_deposit`.
4. `award_child_bounty` sets a fresh zero-balance `beneficiary`.
5. After `unlock_at`, anyone calls `claim_child_bounty`. In a release build, `T::Currency::transfer` to `curator` or `beneficiary` fails silently (`debug_assert!` no-op), yet `ChildBounties` and `ChildBountyDescriptionsV1` entries are still removed.
6. The residual balance in `child_bounty_account` is now permanently unreachable, verifiable via a unit test built without `debug-assertions` that asserts nonzero `free_balance(child_bounty_account)` after a successful `claim_child_bounty` call.
