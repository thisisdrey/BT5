**Analysis of the claimed binding:**

The question posits that `PublicKey::to_implicit_account_id()` might produce colliding `AccountId` strings across `Ed25519` and `Secp256k1`/`P256` variants, letting a secp256k1-recovered key (from an ERC-191/TIP-191 signature) satisfy an account id meant for an ed25519 (NEP-413) implicit account.

Tracing `contracts/defuse/core/src/public_key.rs:44-80`, `to_implicit_account_id` produces format-incompatible outputs per variant:

- `Ed25519(pk)` → `hex::encode(pk)`: exactly 64 lowercase hex characters (32-byte key), **no prefix**. [1](#0-0) 

- `Secp256k1(pk)` → `format!("0x{}", hex::encode(&Keccak256::digest(pk)[12..32]))`: `"0x"` + 40 hex chars = 42 chars total. [2](#0-1) 

- `P256(pk)` → `format!("0x{}", hex::encode(&Keccak256::new_with_prefix(b"p256").chain_update(pk).finalize()[12..32]))`: also `"0x"` + 40 hex chars = 42 chars, additionally domain-separated from `Secp256k1` by the `b"p256"` hash prefix. [3](#0-2) 

These two output families are injective/non-colliding for two independent reasons:

1. **Length mismatch**: Ed25519 form is always 64 characters; Secp256k1/P256 form is always 42 characters (`"0x"` + 40 hex digits). A 64-char string can never equal a 42-char string.
2. **Character-set mismatch**: even ignoring length, the Secp256k1/P256 form always starts with the literal characters `0x`, where `x` is not a valid hex digit. `PublicKey::from_implicit_account_id` (the reverse direction, used in `has_public_key`'s implicit fallback and `iter_public_keys`) calls `hex::decode_to_slice(account_id.as_str(), &mut pk)` on a fixed 32-byte buffer — this only succeeds for exactly 64 valid hex characters, so any `"0x..."` string fails to decode and yields `None`. [4](#0-3) 

This is confirmed by the existing unit tests, which show the Ed25519 example resolving to a 64-hex-char id (`423df0a6...`) and the Secp256k1/P256 examples resolving to `0x`-prefixed 40-hex-char ids (`0xbff77166...`, `0x7edf07ede...`). [5](#0-4) 

The `has_public_key` check (`contracts/defuse/src/contract/intents/state.rs:42-50`, and the in-account variants at `contracts/defuse/src/contract/accounts/account/mod.rs:87-90`) relies on exact string equality `account_id == public_key.to_implicit_account_id()`, so given the disjoint length/format between the two derivation families, **no `account_id` string can simultaneously equal both an Ed25519-derived and a Secp256k1/P256-derived implicit id**. The claimed cross-curve collision cannot occur, and thus the NEP-413 vs. ERC-191/TIP-191 envelope domain separation is not undermined via this path. [6](#0-5) [7](#0-6)
