Audit Report

## Title
Validators lose earned era-point rewards for legitimate backing/dispute-vote work performed before being rotated out of the active validator set - (File: polkadot/runtime/parachains/src/reward_points.rs)

## Summary
`RewardValidatorsWithEraPoints::reward_only_active` resolves the validator identity for a `ValidatorIndex` using the historical session's `AccountKeys`, correctly identifying who performed the backing or dispute-voting work, but then filters the resulting reward list against `C::ValidatorSet::validators()` — the validator set active at the time the reward call executes, not the set active during the session in which the work was done. [1](#0-0)  Any validator who legitimately backed an included candidate or cast a valid dispute vote and later leaves the active set (via `chill`, non-re-election, etc.) before this reward call runs has their era points silently and permanently dropped.

## Finding Description
`reward_only_active` fetches `session_info::AccountKeys::<C>::get(&session_index)` to map indices to account IDs for the session in which the activity occurred, which is correct. [2](#0-1)  It then builds `active_set` from `C::ValidatorSet::validators()`, which reflects the *current* session's validator set, and filters rewarded validators against this present-time set before calling `R::reward_by_ids(rewards)`. [3](#0-2) 

For `reward_backing`, `session_index` is `shared::CurrentSessionIndex::<C>::get()`, so the window is small (current session). [4](#0-3)  For `reward_dispute_statement`, invoked from `disputes.rs` after a dispute statement set is imported on-chain, the `session` parameter can refer to a session well in the past relative to when the statement is processed, since dispute statements can be imported later within `dispute_period`/`dispute_post_conclusion_acceptance_period` bounds. [5](#0-4) 

The correct historical active set for `session_index` is already stored on-chain in `Sessions::<T>::get(session_index).active_validator_indices` at session-rotation time [6](#0-5) , but `reward_only_active` does not use it — it only uses the present-time `C::ValidatorSet::validators()`. There is no fallback or deferred crediting mechanism; validators filtered out are simply excluded from `R::reward_by_ids`, so their points for that action are permanently lost.

## Impact Explanation
This is a runtime bug that compromises intended reward/incentive behavior: validators who correctly performed on-chain-verified backing or dispute-vote duties receive reduced or zero era-point compensation purely due to an unrelated, later change in active-set membership, with no attacker or privileged actor involved. This matches the allowed "runtime bugs that compromise intended behavior" impact category.

## Likelihood Explanation
The triggering condition — a validator chilling or not being re-elected between performing the work and the reward call executing — is a routine, unprivileged operational occurrence, not requiring any malicious peer, validator, or governance action. The gap is inherently wider for dispute statements, which by design can be processed across multiple sessions within `dispute_period`/`dispute_post_conclusion_acceptance_period`. [7](#0-6) 

## Recommendation
Filter `reward_only_active` against the active validator set recorded for `session_index` (e.g., `session_info::Sessions::<C>::get(session_index).active_validator_indices`, combined with the already-fetched `AccountKeys`) rather than the current `C::ValidatorSet::validators()`, so rewards are attributed based on the validator's status at the time the work was performed.

## Proof of Concept
1. Validator `V` is active in session `S` and backs a candidate that gets included, or casts a valid dispute statement in session `S`.
2. Before `reward_backing`/`reward_dispute_statement` executes for that action (e.g., dispute statement processed several sessions later), `V` calls `chill` or is not re-elected, removing `V` from `C::ValidatorSet::validators()`.
3. `reward_only_active` resolves `V`'s account correctly via `AccountKeys` for session `S`, but `active_set.contains(v)` fails since `V` is absent from the current set.
4. `V`'s points are excluded from `R::reward_by_ids` and never credited — confirmable via a unit test in `reward_points.rs`/`disputes.rs` asserting `V`'s stash receives no `ErasRewardPoints` increment despite valid backing/dispute participation in session `S`.

	/// Reward validators in session with points, but only if they are in the active set.
	fn reward_only_active(
		session_index: SessionIndex,
		indices: impl IntoIterator<Item = ValidatorIndex>,
		points: u32,
	) {
		let validators = session_info::AccountKeys::<C>::get(&session_index);
		let validators = match validators
			.defensive_proof("account_keys are present for dispute_period sessions")
		{
			Some(validators) => validators,
			None => return,
		};
		// limit rewards to the active validator set
		let active_set: BTreeSet<_> = C::ValidatorSet::validators().into_iter().collect();

		let rewards = indices
			.into_iter()
			.filter_map(|i| validators.get(i.0 as usize).cloned())
			.filter(|v| active_set.contains(v))
			.map(|v| (v, points));

		R::reward_by_ids(rewards);
	}
