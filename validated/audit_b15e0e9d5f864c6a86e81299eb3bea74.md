### Title
Unguarded null-pointer/index exception in `ValidateMultiSign`/`BatchValidateSign` precompiles when TIP-854 guard is inactive - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The TVM precompiled contracts `ValidateMultiSign` and `BatchValidateSign` decode raw call data without adequate length validation before the TIP-854 (`VMConfig.allowTvmOsaka()`) containment guard was introduced. When that guard is not active, malformed/too-short call data reaches the legacy decoder and throws an uncaught `RuntimeException` (documented in the test suite as the "legacy behaviour"), which is not contained inside `Program.callToPrecompiledAddress`.

### Finding Description
`Program.callToPrecompiledAddress` invokes the precompiled contract directly: [1](#0-0) 
The only exception handling present is for `this.result.getException()` after a *normal* failed (`false`) return from `execute()` — it does not wrap the `contract.execute(data)` call itself in a try/catch. If `execute()` throws directly (e.g., an unchecked `RuntimeException`/NPE/`ArrayIndexOutOfBoundsException` from decoding malformed input), that exception propagates unhandled out of the CALL opcode handling and up through the VM/actuator/block-application path.

This exact failure mode is explicitly acknowledged in the test suite. `ValidateMultiSignContractTest.testTip854PreActivationNoOp` documents that pre-activation (`VMConfig.initAllowTvmOsaka(0)`), a too-short input "raises inside the decoder" and there is "no outer catch," calling this "the documented pre-activation failure mode the TIP explicitly preserves": [2](#0-1) 

The remediation for this is `OperationsTest.testTip854OuterFrameContainment`, which shows that only *when* `VMConfig.initAllowTvmOsaka(1)` is active does a call to `ValidateMultiSign`/`BatchValidateSign` with malformed calldata (`inDataSize=0`) get safely converted into "push 0 onto the outer stack" with no propagated exception: [3](#0-2) 

This confirms that the TIP-854 guard is a feature-gated fix for a previously-existing crash bug in the precompile decoders, analogous to the CVE's null-pointer dereference in a kernel-mode path reachable by an unprivileged caller — here the "unprivileged caller" is any account able to submit a transaction/TVM call that reaches the `ValidateMultiSign` (`0x0...1000`)/`BatchValidateSign` precompile addresses via a `CALL`/`STATICCALL` with crafted calldata: [4](#0-3) 

### Impact Explanation
An uncaught `RuntimeException` thrown out of `contract.execute(data)` during transaction execution is not a normal `ContractExeException`/revert — it escapes the expected VM error-handling flow at `Program.callToPrecompiledAddress`. Depending on how far up the stack it is caught (or not), this can abort processing of the entire block being applied in `Manager`, resulting in denial of service for the node processing that transaction. Because any address can be gated behind `VMConfig.allowTvmOsaka()` toggling (a chain parameter/hard-fork switch controlled by SR consensus, not by the individual caller), nodes running with this feature disabled remain exposed to the crash whenever a transaction/contract call reaches these two precompiles with malformed data.

### Likelihood Explanation
Reaching `ValidateMultiSign`/`BatchValidateSign` only requires deploying or calling a contract that issues a `CALL`/`STATICCALL` to the fixed precompile addresses (`0x...1000`/`0x...1001`-style addresses defined in `PrecompiledContracts`) with a short/malformed payload — an operation fully available to any unprivileged transaction broadcaster or contract deployer, requiring no special permission, and inexpensive (bounded by energy limit).

### Recommendation
Wrap the call to `contract.execute(data)` in `Program.callToPrecompiledAddress` in a try/catch that treats any unchecked exception from a precompiled contract as a normal execution failure (push zero / revert), independent of the `VMConfig.allowTvmOsaka()` gate, so the guard behavior added for TIP-854 is not solely feature-flag-dependent. Additionally, harden the legacy decoders in `ValidateMultiSign`/`BatchValidateSign` to validate call-data length before array/field access rather than relying on the outer VM catch alone.

### Proof of Concept
1. Deploy a helper contract whose bytecode issues `STATICCALL`/`CALL` to the `ValidateMultiSign` precompile address (`0x0000...0100` per `validateMultiSignAddr` mapping) with `inDataSize` less than the minimum 5 head words (as done in `OperationsTest.testTip854OuterFrameContainment`, e.g. `inDataSize=0`).
2. Ensure the node has `allowTvmOsaka` disabled (default/pre-activation state).
3. Broadcast a transaction triggering the helper contract to make this call.
4. The decoder inside `ValidateMultiSign.execute()`/`BatchValidateSign.execute()` throws a `RuntimeException` while decoding the malformed input; because `Program.callToPrecompiledAddress` (line 1752) does not catch it, the exception propagates uncaught through transaction execution, matching the pre-activation failure mode explicitly documented in `ValidateMultiSignContractTest.testTip854PreActivationNoOp`.
