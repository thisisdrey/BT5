### Title
Witness-controlled brokerage (fee) ratio can be changed with no timelock, taking effect after a single maintenance cycle - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

### Summary
`UpdateBrokerageContract`, executed by `UpdateBrokerageActuator`, lets any witness unilaterally change the brokerage (reward-split/commission) ratio it charges its voters, with no timelock, no notification mechanism, and no rate-limiting on the magnitude of change between updates.

### Finding Description
Any witness can broadcast an `UpdateBrokerageContract` transaction. It is processed by: [1](#0-0) 

which calls `DelegationStore.setBrokerage(ownerAddress, brokerage)`, an overload that always writes to the special "default" slot keyed by cycle `-1`: [2](#0-1) 

Validation only bounds `brokerage` to `[0, 100]` and checks the witness/account exist; there is no restriction on how large a single change can be, nor any delay before the new value can be locked in for a future cycle: [3](#0-2) 

The actual reward-affecting value is snapshotted forward once per maintenance cycle by `MaintenanceManager.doMaintenance()`, which copies the "default" (cycle -1) brokerage into the next cycle's slot: [4](#0-3) 

and `MortgageService.payReward` reads the brokerage keyed to the *current* cycle to split rewards between the witness (brokerage) and voters: [5](#0-4) 

So a witness can set `brokerage = 100` (taking the entire reward, leaving `0` for delegators) at any time before a maintenance boundary; that value is baked into the *next* cycle's snapshot automatically, with no additional approval, cooldown, or governance step, and no on-chain signal/event that voters are guaranteed to notice before the next maintenance interval elapses.

### Impact Explanation
Delegators who vote for a witness expect the advertised brokerage ratio to persist. Because the change is applied unilaterally by the witness and locked into the very next cycle automatically, voters effectively get, at most, a single maintenance interval (default `MAINTENANCE_TIME_INTERVAL`, ~6 hours per `ProposalUtil.ProposalType`) to react and unvote before their reward split can be maximally skewed in the witness's favor. There is no timelock proportional to typical unstake/unfreeze delays, and no notification/event mechanism forcing awareness. This can result in voters losing expected staking rewards to a witness that abruptly raises its commission to the maximum, which is a direct, unbacked-value/loss-of-funds-for-users type impact (medium severity, since it requires a witness account, is bounded to at most 100% of reward, and can be somewhat mitigated by monitoring/unvoting within one cycle).

### Likelihood Explanation
Likelihood is moderate: any registered witness (a permissioned but common role, not requiring privileged committee/SR consensus) can execute this at will with a normal signed transaction via `wallet/updateBrokerage` HTTP/gRPC/JSON endpoints, at zero fee (`calcFee()` returns `0`), and it requires no other party's cooperation or approval.

### Recommendation
Add a timelock/cooldown to `UpdateBrokerageContract` processing, e.g.:
- Require that a new brokerage value only take effect a fixed number of cycles (e.g., N > 1) after being set, rather than the immediate next cycle, giving voters clear advance notice.
- Cap the maximum delta allowed per update (e.g., ±X percentage points per cycle) instead of allowing 0→100 jumps in one call.
- Emit a clear, queryable pending-change record (already partially possible via `GetBrokerageInfo`) with an explicit "effective cycle" field so wallets/voters can be warned proactively.

### Proof of Concept
1. Witness W is currently at the default brokerage (20%), with voters delegating to it.
2. Shortly before a maintenance cycle boundary, W broadcasts `UpdateBrokerageContract{owner_address: W, brokerage: 100}` via `/wallet/updateBrokerage` (see `UpdateBrokerageServlet`).
3. `UpdateBrokerageActuator.execute` calls `DelegationStore.setBrokerage(W, 100)`, writing to the cycle `-1` slot.
4. At the next `MaintenanceManager.doMaintenance()` call, `delegationStore.setBrokerage(nextCycle, W, delegationStore.getBrokerage(W))` copies `100` into `nextCycle`'s slot.
5. From `nextCycle` onward, `MortgageService.payReward` sends 100% of block/tx-fee rewards to W and 0% to the delegators, who had no time-locked warning beyond the single maintenance interval.

  public void setBrokerage(long cycle, byte[] address, int brokerage) {
    put(buildBrokerageKey(cycle, address), new BytesCapsule(ByteArray.fromInt(brokerage)));
  }

  public int getBrokerage(long cycle, byte[] address) {
    BytesCapsule bytesCapsule = get(buildBrokerageKey(cycle, address));
    if (bytesCapsule == null) {
      return DEFAULT_BROKERAGE;
    } else {
      return ByteArray.toInt(bytesCapsule.getData());
    }
  }

  public void setBrokerage(byte[] address, int brokerage) {
    setBrokerage(-1, address, brokerage);
  }

  public int getBrokerage(byte[] address) {
    return getBrokerage(-1, address);
  }

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
