`x-gitaly-cost` score for `GetArchive` can be gamed via `format=TAR_BZ2` compression to bypass Cloudflare complexity-based rate limiting - ([File: internal/grpc/middleware/costhandler/costhandler.go])

### Summary
The `costhandler` package computes the `x-gitaly-cost` gRPC trailer that Rails/Workhorse forward as the `X-Score` HTTP header to an upstream complexity-based rate limiter (Cloudflare) [1](#0-0) . The score is `static + dynamic`, where `dynamic` is derived only from wire bytes transferred (`InPayloadBytes + OutPayloadBytes`) [2](#0-1) , and `static` is a per-method constant that for `GetArchive` (an `OpAccessor`) is **not** in `staticCostOverrides` and thus falls back to `defaultAccessorCost = 1` [3](#0-2) [4](#0-3) . An ordinary authenticated user can craft a `GetArchiveRequest` with `format=TAR_BZ2` (or `TAR_GZ`) so that Gitaly runs `git archive` piped into `bzip2`/`gzip` server-side, spending disproportionate CPU while streaming back a tiny compressed payload, causing the score to stay near-minimal despite heavy real server cost — the same "cheap-to-manipulate signal, disconnected from true cost" pattern as the reported SynthVault `weight`/`calcReward` mismatch.

### Finding Description
`computeCost` combines a static per-RPC-type weight with a dynamic component computed purely from bytes actually sent/received over the gRPC connection [5](#0-4) , tracked by the `grpcstats.PayloadBytes` stats handler which just sums `stats.InPayload`/`stats.OutPayload` lengths [6](#0-5) . This design assumes payload size is a reasonable proxy for backend resource cost. `GetArchive` breaks that assumption: the handler runs `git archive` and, depending on `format`, pipes the output through `gzip` or `bzip2` compression executed as a Gitaly-side subprocess [7](#0-6) [8](#0-7) . A user fully controls `CommitId`, `Path`, `Exclude`, and `Format` via the `GetArchiveRequest` proto [9](#0-8) , and `GetArchive` is classified as an `Accessor` operation, so it gets `defaultAccessorCost = 1` since it has no entry in `staticCostOverrides` (unlike streaming clone/fetch RPCs, which are explicitly overridden to 10) [10](#0-9) . By requesting a large/incompressible-content-heavy repository archive with `TAR_BZ2`/`TAR_GZ` compression, an attacker forces expensive CPU-bound compression on Gitaly while the actual `OutPayloadBytes` (and thus the dynamic cost term) shrinks proportionally to the achieved compression ratio, or by repeatedly requesting the same archive to exploit the `archiveCache`/`streamcache` cache-hit path where compute cost was already paid once but subsequent hits stream from disk cheaply (further decoupling reported cost from cumulative cluster load). This is directly analogous to the `SynthVault` bug: a value used as an external decision signal (`weight` for reward payout / `x-gitaly-cost` for rate-limit budget) is derived from an easily influenced input (spot price / bytes transferred) rather than the actual resource consumed (locked capital / CPU-seconds), letting the caller cheaply distort the signal in its favor.

### Impact Explanation
Because Rails/Workhorse translate `x-gitaly-cost` directly into the `X-Score` HTTP header consumed by Cloudflare's complexity-based rate limiting [11](#0-10) , an attacker who can keep the reported score artificially low while imposing high CPU cost on Gitaly (via crafted `GetArchive` compression requests) can issue many more such requests than the external rate limiter intends to allow, achieving a CPU-based denial-of-service against the Gitaly node while staying under the complexity budget that the upstream defense is meant to enforce. This undermines the very purpose of the "Signal Export Layer" described in the load-management architecture: the `x-gitaly-cost` signal is supposed to let external rate limiters know the true relative cost of an RPC, but for `GetArchive` (and any other `Accessor` RPC that spawns a costly subprocess with a small final byte count) the signal is decoupled from actual cost.

### Likelihood Explanation
Likelihood is moderate: reaching `GetArchive` requires only a normal authenticated RPC call, well within an ordinary user's capability, and the request fields (`Format`, `CommitId`, `Path`, `Exclude`) are fully attacker-controlled with only path/existence validation [12](#0-11) . The concurrency limiter itself is unaffected (it is method/repo-keyed, not score-based), so this specifically targets the newer, still-evolving cost-signal/rate-limiting layer described in `doc/load-management-architecture.md`, which explicitly acknowledges that "a static score hides variance" [13](#0-12)  — the design already anticipates this class of imprecision but has not addressed the compression-cost mismatch.

### Recommendation
Do not rely solely on wire-transferred bytes for the dynamic cost component of CPU-heavy RPCs. Incorporate actual measured resource usage (e.g., CPU time and wall time of spawned Git/compression subprocesses, obtainable from the `burdenmonitor.RPCEntry`/`CommandStats` already tracked per RPC) into `computeCost`, or add `staticCostOverrides` entries for `GetArchive` proportional to worst-case compression format rather than defaulting to the cheapest `Accessor` tier. Consider also weighting cost by CPU time actually consumed rather than by output size alone, since a decompression/compression ratio is fully attacker-influenced.

### Proof of Concept
1. As an authenticated user, call `RepositoryService.GetArchive` on a repository containing several hundred MB of highly compressible content (e.g., repeated text blobs) with `Format = TAR_BZ2`.
2. Gitaly executes `git archive` piped into `bzip2` server-side [14](#0-13) , consuming significant CPU proportional to input size, but streams back a compressed archive that may be a small fraction of the original size.
3. Observe the `x-gitaly-cost` trailer: `static (defaultAccessorCost=1) + dynamic (ceil(OutPayloadBytes/1MiB))` [15](#0-14) [2](#0-1)  yields a low score disproportionate to the CPU time spent, since only compressed output bytes count toward the dynamic term.
4. Repeat the call rapidly across many/varied commits or paths to sustain CPU load on the Gitaly node while the cumulative `X-Score` reported upstream underrepresents true cost, allowing the attacker to exceed Cloudflare's intended complexity-based rate budget.

// computeCost returns the cost score for a completed RPC. It combines a static
// base cost for the RPC type with a dynamic component from actual bytes
// transferred, read from the RPCEntry in context.
func computeCost(ctx context.Context, fullMethod string) int {
	static := staticCostForMethod(fullMethod)
	dynamic := dynamicCostFromContext(ctx)
	return static + dynamic
}

func staticCostForMethod(fullMethod string) int {
	if cost, ok := staticCostOverrides[fullMethod]; ok {
		return cost
	}

	methodInfo, err := protoregistry.GitalyProtoPreregistered.LookupMethod(fullMethod)
	if err != nil {
		return defaultUnknownCost
	}

	switch methodInfo.Operation {
	case protoregistry.OpAccessor:
		return defaultAccessorCost
	case protoregistry.OpMutator:
		return defaultMutatorCost
	case protoregistry.OpMaintenance:
		return defaultMaintenanceCost
	default:
		return defaultUnknownCost
	}
}

// dynamicCostFromContext computes the dynamic cost contribution from payload
// bytes tracked by the grpcstats.PayloadBytes stats handler.
func dynamicCostFromContext(ctx context.Context) int {
	stats := grpcstats.PayloadBytesStatsFromContext(ctx)
	if stats == nil {
		return 0
	}
	totalBytes := stats.InPayloadBytes + stats.OutPayloadBytes

	return int(math.Ceil(float64(totalBytes) / float64(byteCostDivisor)))
```

func (s *PayloadBytes) HandleRPC(ctx context.Context, rs stats.RPCStats) {
	switch st := rs.(type) {
	case *stats.InPayload:
		bytesStats := ctx.Value(payloadBytesStatsKey{}).(*PayloadBytesStats)
		bytesStats.InPayloadBytes += int64(st.Length)
	case *stats.OutPayload:
		bytesStats := ctx.Value(payloadBytesStatsKey{}).(*PayloadBytesStats)
		bytesStats.OutPayloadBytes += int64(st.Length)
	}
}

func parseArchiveFormat(format gitalypb.GetArchiveRequest_Format) ([]string, string) {
	switch format {
	case gitalypb.GetArchiveRequest_TAR:
		return nil, "tar"
	case gitalypb.GetArchiveRequest_TAR_GZ:
		return []string{"gzip", "-c", "-n"}, "tar"
	case gitalypb.GetArchiveRequest_TAR_BZ2:
		return []string{"bzip2", "-c"}, "tar"
	case gitalypb.GetArchiveRequest_ZIP:
		return nil, "zip"
	}

	return nil, ""
}

### RPC Cost Score (`x-gitaly-cost`)

Gitaly returns a cost score for each RPC as a gRPC response trailer.
Gitaly has the most context about the actual cost of each RPC, making it the right
place to own this value. Rails and Workhorse translate the `x-gitaly-cost`
trailer into an `X-Score` HTTP response header, making the cost signal
available to any upstream rate limiter.

> On GitLab.com, the `X-Score` header feeds Cloudflare's
> [complexity-based rate limiting](https://developers.cloudflare.com/waf/rate-limiting-rules/request-rate/#complexity-based-rate-limiting).
> Self-managed deployments can use the same header with any upstream
> rate limiter or ignore it.
```
