### Title
Exchange Inject/Withdraw computes token amounts from manipulable spot pool ratio with no slippage protection, enabling MEV sandwich extraction - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the counter-party token amount (`anotherTokenQuant`) directly from the exchange's current on-chain balance ratio (`firstTokenBalance`/`secondTokenBalance`) at execution time, with no caller-supplied minimum/maximum bound. Unlike `ExchangeTransactionActuator`, which enforces a `tokenExpected` slippage-protection check, neither Inject nor Withdraw offers any such protection, so an MEV actor can manipulate the pool's spot ratio via a swap immediately before the creator's Inject/Withdraw transaction executes and reverse it afterward, extracting value analogous to the reported spot-price-driven liquidation over-seizure.

### Finding Description
`ExchangeCapsule.transaction()` (the Bancor-style AMM swap logic used by `ExchangeTransactionActuator`) mutates `firstTokenBalance`/`secondTokenBalance` based on constant-product-like math [1](#0-0) . This balance ratio is the exchange's instantaneous "spot price," directly analogous to `sqrtPriceX96` in the report — it is permissionlessly moveable within the same block by any account calling `ExchangeTransactionContract`.

`ExchangeInjectActuator.execute()` computes `anotherTokenQuant` as `floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` (or the symmetric case) purely from the current spot balances, then immediately debits the calling account (the exchange creator) that computed amount of the counterpart token [2](#0-1) . The `doValidate()` path recomputes the same ratio-based amount and only checks balance sufficiency and pool balance limits — there is no caller-provided expected/minimum amount to bound how unfavorable the ratio may be at execution time [3](#0-2) .

`ExchangeWithdrawActuator` has the identical structure: `anotherTokenQuant` is derived from `bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)` (or the symmetric branch) using the current pool balances, and the withdrawn/received amounts are credited based on that spot-derived value [4](#0-3) . Its validate path likewise only checks precision/consistency bounds against the AMM formula itself, not against any user-specified minimum received amount [5](#0-4) .

By contrast, `ExchangeTransactionActuator` explicitly guards against this exact class of manipulation by requiring the resulting `anotherTokenQuant` to be at least the caller's `tokenExpected`, rejecting the transaction otherwise: `if (anotherTokenQuant < tokenExpected) { throw new ContractValidateException("token required must greater than expected"); }` [6](#0-5) . Inject and Withdraw omit this protection entirely.

Both Inject and Withdraw are restricted to the exchange's creator account (`if (!accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress()))`), so the victim of the sandwich is always the specific exchange-creator account, but the attacker performing the sandwiching swap transactions is any unprivileged, permissionless broadcaster [7](#0-6) [8](#0-7) .

### Impact Explanation
An attacker observing a pending `ExchangeInjectContract` or `ExchangeWithdrawContract` from the exchange creator can front-run it with an `ExchangeTransactionContract` swap that skews `firstTokenBalance`/`secondTokenBalance` in the direction that maximizes the counterpart amount the creator must pay in (Inject) or minimizes the counterpart amount the creator receives (Withdraw), then back-run with the inverse swap to restore the ratio and capture the resulting deviation as profit — the same value-transfer mechanism described in the source report, just applied to TRON's on-chain Bancor exchange instead of DexV2 liquidation. This causes the creator to lose value on every Inject/Withdraw operation relative to an unmanipulated ratio, with no cap analogous to `maxLiquidationPenalty`; the loss scales with the size of the operation and the liquidity depth of the pool.

### Likelihood Explanation
Any account can freely submit `ExchangeTransactionContract` transactions against the same `exchangeId`, and transaction ordering within a block is influenced by the block producer/mempool, making the sandwich readily executable by anyone monitoring the mempool for pending Inject/Withdraw transactions from known exchange creators. The absence of any slippage parameter on Inject/Withdraw (contrasted with Transaction, which has one) means there is no way for the creator to protect themselves at the protocol level.

### Recommendation
Add an `expected`/slippage-bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`) and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()`, rejecting the operation if the spot-derived counterpart amount falls outside the caller-specified bound.

### Proof of Concept
1. Exchange creator broadcasts `ExchangeWithdrawContract` withdrawing `tokenQuant` of `firstTokenID`.
2. Attacker sees this in the mempool and broadcasts an `ExchangeTransactionContract` swap that shifts `firstTokenBalance`/`secondTokenBalance` so that `anotherTokenQuant` computed in `ExchangeWithdrawActuator.execute()` (`actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java:77-89`) is minimized for the victim.
3. Block producer includes attacker's swap before the creator's withdraw.
4. Creator's withdraw executes at the skewed ratio, receiving less counterpart token than intended.
5. Attacker submits the inverse swap to restore the ratio, realizing profit equal to the ratio deviation.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
