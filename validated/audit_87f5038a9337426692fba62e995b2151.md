### Title
Client-controlled `GitConfigOptions` can override Gitaly's security-critical Git config defaults, including cross-repository ref-leak protection - (File: `internal/git/gitcmd/command_factory.go`, `internal/git/gitcmd/command_description.go`)

### Summary
`PostReceivePackRequest`, `SSHReceivePackRequest`, `InfoRefsRequest`, and `PostUploadPackWithSidechannelRequest` all expose a `git_config_options` field that an ordinary, unauthenticated-at-the-git-protocol-level pushing/fetching client fully controls [1](#0-0) . Gitaly converts these strings directly into `-c key=value` pairs with no allowlist of safe keys, only generic syntax validation [2](#0-1) [3](#0-2) .

### Finding Description
For `git-receive-pack`, Gitaly hard-codes several config values specifically to prevent security-relevant behavior — most notably `core.alternateRefsCommand = "exit 0 #"`, which is used to **suppress leakage of the object pool's refs during ref advertisement** for pool-linked (fork) repositories, plus fsck and hidden-ref-prefix configuration: [4](#0-3) .

These per-command defaults are combined with the client-supplied config in `combineArgs`: [5](#0-4) 

The order is: (1) process-wide defaults, (2) per-subcommand defaults (including `core.alternateRefsCommand`, fsck config, hidden-ref prefixes), (3) `cc.globals`, which is where `WithConfig(config...)` built from `req.GetGitConfigOptions()` is appended [6](#0-5) , and only last (4) admin-configured `cfg.Git.Config`. Git's `-c` flag semantics mean the **last** occurrence of the same key on the command line wins, so any key set by (2) can be overridden by the client-supplied (3) block. This is confirmed by the existing tests, which show that user-supplied `GitConfigOptions` are able to override built-in behavior such as `receive.unpackLimit`, `receive.MaxInputSize`, and even `uploadpack.hideRefs`/ref visibility controls for upload-pack [7](#0-6) [8](#0-7) .

This is structurally the same bug class as the reported DeFi issue: a value meant to gate a sensitive operation (there: auction pricing parameters; here: `core.alternateRefsCommand`/fsck/hidden-ref config that gates cross-repository ref exposure and object validation) is mutable by the same party whose operation it is supposed to constrain, and is applied *after* the protective default, silently overriding it.

### Impact Explanation
- `core.alternateRefsCommand` is specifically documented as existing to prevent an object pool's refs from being advertised to a pushing client during `receive-pack`'s ref advertisement (this exists to stop cross-repository/fork information disclosure) [9](#0-8) . A pushing client that also supplies `GitConfigOptions=["core.alternateRefsCommand=<real command>"]` (or an equivalent override) could restore visibility into a pool repository's refs/objects that Gitaly deliberately hides for that operation — a cross-repository object/ref disclosure to an unprivileged pushing user.
- Similarly, `receive.fsck.*`/hidden-ref-prefix defaults set for the same command can be relaxed by the client, which weakens object-validation and ref-hiding guarantees during a push.
- Because `GitConfigOptions` is a normal, documented protocol field usable by any client performing a push or fetch, no special privilege is required — this matches the "unprivileged actor" requirement.

### Likelihood Explanation
High for reachability: the field is a first-class part of the smart-HTTP/SSH push and fetch RPCs and is exercised by existing tests demonstrating that client values do override server defaults for at least `receive.unpackLimit`, `receive.MaxInputSize`, and `uploadpack.hideRefs` [10](#0-9) . What I could **not** verify from the index is whether GitLab's Rails layer (outside this repo) or a caller like Praefect strips/validates `git_config_options` before forwarding them to Gitaly, or whether `core.alternateRefsCommand` is realistically overridable to leak useful pool data end-to-end (e.g., whether an attacker-controlled command value could actually be abused as more than a boolean gate). This uncertainty affects the practical severity but not the code-level fact that the override is possible at the Gitaly layer.

### Recommendation
Maintain an explicit allowlist/denylist for `git_config_options` accepted from RPC requests, specifically rejecting or ignoring client-supplied overrides for security-relevant keys that Gitaly sets internally (`core.alternateRefsCommand`, `receive.fsck.*`, `uploadpack.hideRefs`/hidden ref prefixes, `receive.denyCurrentBranch`, etc.), or reorder `combineArgs` so that per-command security defaults are appended **after** (and thus take precedence over) client-supplied `cc.globals` for those specific keys.

### Proof of Concept
1. As an ordinary user with push access, call `PostReceivePack`/`SSHReceivePack` against a repository that belongs to an object pool (fork network).
2. Include `GitConfigOptions` containing a key that collides with one of the command's built-in protective settings, e.g. attempt to override `core.alternateRefsCommand`.
3. Because `combineArgs` appends `cc.globals` (client config) after the command's built-in `opts()` [5](#0-4) , and Git's `-c` uses last-value-wins, the client's value takes effect over Gitaly's intended default, as already demonstrated for other keys in the existing test suite [7](#0-6) .

// ConvertConfigOptions converts `<key>=<value>` config entries into `ConfigPairs`.
func ConvertConfigOptions(options []string) ([]ConfigPair, error) {
	configPairs := make([]ConfigPair, len(options))

	for i, option := range options {
		configPair := strings.SplitN(option, "=", 2)
		if len(configPair) != 2 {
			return nil, fmt.Errorf("cannot convert invalid config key: %q", option)
		}

		configPairs[i] = ConfigPair{Key: configPair[0], Value: configPair[1]}
	}

	return configPairs, nil
}
