### Title
`Wallet.getMarketOrderByAccount` breaks the entire order list when a single order lookup fails - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
`Wallet.getMarketOrderByAccount` iterates over every order ID stored in an account's `MarketAccountOrderCapsule` and looks up each one individually in `MarketOrderStore`. If a single lookup fails with `ItemNotFoundException`, the code converts it into an unchecked `IllegalStateException` inside a `forEach` lambda, which aborts the entire iteration and propagates up through the HTTP/gRPC query path, causing the whole request to fail instead of returning the orders that could be found. This mirrors the reported `BondAggregator.findMarketFor` bug class: a per-item failure inside a loop that is supposed to aggregate/query a list breaks the entire loop/transaction.

### Finding Description
`getMarketOrderByAccount` builds a `MarketOrderList` by iterating `orderIdList` from `MarketAccountOrderCapsule.getOrdersList()` and calling `marketOrderStore.get(orderId.toByteArray())` for each ID: [1](#0-0) 

```java
orderIdList.forEach(
    orderId -> {
      try {
        MarketOrderCapsule orderCapsule = marketOrderStore.get(orderId.toByteArray());
        ...
        marketOrderListBuilder.addOrders(orderCapsule.getInstance());
      } catch (ItemNotFoundException e) {
        logger.warn("orderId = {} not found", orderId);
        throw new IllegalStateException("order not found in store");
      }
    }
);
```

`MarketOrderStore.get(byte[] key)` throws `ItemNotFoundException` whenever the requested key is not present in the underlying revoking DB: [2](#0-1) 

Because the `forEach` lambda re-throws this as an unchecked `IllegalStateException`, Java's `forEach` (which does not support "continue"/skip semantics for a checked-then-unchecked exception) unwinds immediately, discarding the `MarketOrderList.Builder` state built so far and propagating the exception out of `getMarketOrderByAccount`.

This function is reachable directly from unauthenticated/unprivileged HTTP and gRPC query endpoints (no signature or permission required — it only needs an account address):
- `GetMarketOrderByAccountServlet.getResult` calls `wallet.getMarketOrderByAccount(...)` directly and only wraps the call site with generic `Util.processError(e, response)` in `doGet`/`doPost`: [3](#0-2) 
- The same `Wallet` method is exposed on `FullNodeHttpApiService`, `SolidityNodeHttpApiService`, `HttpApiOnPBFTService`, `HttpApiOnSolidityService`, and via gRPC in `RpcApiServiceOnPBFT` / `RpcApiServiceOnSolidity`.

An order can become unreachable from the store while still referenced in the account's order-id list in scenarios such as: matcher/actuator logic removing/consuming a maker order from `MarketOrderStore`/`pairPriceToOrderStore` (see `MarketSellAssetActuator.matchOrder`, which deletes fully-consumed orders) without perfectly synchronized cleanup of `MarketAccountOrderCapsule.getOrdersList()` for every account reference, or any other inconsistency between the account-to-order index and the order store (e.g., under revoking/rollback edge cases). In such cases, the account's stored order-id list contains a stale reference, and the very next legitimate query for that account's market orders throws and returns an error for the *entire* list instead of the valid orders.

### Impact Explanation
This breaks the "list market orders for an account" query feature: any external caller (wallet UI, exchange integration, monitoring tool) querying `getmarketorderbyaccount` for an account that has even one stale/missing order reference gets a hard failure instead of a partial/valid result set. Users lose the ability to view their live market orders — a market feature made silently unusable for affected accounts, analogous to the `findMarketFor` DoS in the referenced report (a legitimate read-only aggregation query becomes unusable due to one bad element).

This is a query-availability issue (denial of a legitimate view of on-chain state) rather than a fund-loss bug; it does not modify orders, balances, or state, so the impact is bounded to breaking node query functionality for the affected account.

### Likelihood Explanation
Reachable by any anonymous API client — the endpoint takes only an address and requires no signature. The precondition (an order-id in `MarketAccountOrderCapsule` that is missing from `MarketOrderStore`) is a data-consistency edge case whose trigger conditions (e.g., partial order consumption/removal logic, chain reorg/rollback interactions with revoking DB) I was not able to fully confirm as reachable in normal operation from this analysis alone — this should be verified against `MarketSellAssetActuator`/`MarketCancelOrderActuator` cleanup logic and revoking-DB rollback semantics to establish a concrete trigger path.

### Recommendation
In `getMarketOrderByAccount`, catch `ItemNotFoundException` per-item and skip the missing order (log and `return`/`continue` within the lambda, or switch to an ordinary `for` loop with `continue`) instead of converting it to an unchecked exception that aborts the whole aggregation. This mirrors the Bond Protocol fix of gracefully handling a single-item failure without breaking the surrounding loop/query.

### Proof of Concept
Conceptual PoC (not fully verified end-to-end due to missing confirmation of a concrete state-inconsistency trigger):
1. Identify or engineer an account whose `MarketAccountOrderCapsule.getOrdersList()` contains an order ID that has already been removed from `MarketOrderStore` (e.g., an order fully matched/consumed and deleted by `MarketSellAssetActuator.matchOrder`, or one that becomes stale following a market order cancellation flow) while the account-order index still lists that reference.
2. Call the HTTP endpoint `GET /wallet/getmarketorderbyaccount?value=<hex_address>` or the gRPC/HTTP-on-Solidity/PBFT equivalent.
3. Observe that `Wallet.getMarketOrderByAccount` throws `IllegalStateException("order not found in store")` from within the `forEach`, which propagates to `Util.processError`, and the client receives an error response instead of the list of the account's still-valid market orders.

```java
  public MarketOrderList getMarketOrderByAccount(ByteString accountAddress) {

    if (accountAddress == null || accountAddress.isEmpty()) {
      return null;
    }

    MarketAccountOrderCapsule marketAccountOrderCapsule;
    try {
      marketAccountOrderCapsule = dbManager.getChainBaseManager()
          .getMarketAccountStore().get(accountAddress.toByteArray());
    } catch (ItemNotFoundException e) {
      return null;
    }

    MarketOrderStore marketOrderStore = dbManager.getChainBaseManager().getMarketOrderStore();

    MarketOrderList.Builder marketOrderListBuilder = MarketOrderList.newBuilder();
    List<ByteString> orderIdList = marketAccountOrderCapsule.getOrdersList();

    orderIdList.forEach(
        orderId -> {
          try {
            MarketOrderCapsule orderCapsule = marketOrderStore.get(orderId.toByteArray());
            // set prev and next, hide these messages in the print
            orderCapsule.setPrev(new byte[0]);
            orderCapsule.setNext(new byte[0]);

            marketOrderListBuilder
                .addOrders(orderCapsule.getInstance());
          } catch (ItemNotFoundException e) {
            logger.warn("orderId = {} not found", orderId);
            throw new IllegalStateException("order not found in store");
          }
        }
    );

    return marketOrderListBuilder.build();
  }
```
