### Title
Object-pool alternates isolation check only validates the first alternate entry, ignoring additional entries Git will still honor - (File: internal/git/objectpool/pool.go)

### Summary
The reported OPCM bug is a "partial verification" class: a check that is supposed to hold across N equivalent components only actually validates a subset (one of four), letting divergent/unvalidated components slip through silently. The closest reachable analog in Gitaly's object-pool/alternates isolation logic is `ObjectPool.FromRepo`, which derives and validates the pool repository from a member repository's `objects/info/alternates` file but only inspects the **first** entry of `AlternatesInfo.ObjectDirectories`, while Git itself (and other lower-level Gitaly code) treats *all* lines in that file as active alternate object directories.

### Finding Description
`FromRepo` in `internal/git/objectpool/pool.go` reads the alternates info for a repository and unconditionally indexes into the first alternate directory to derive and validate the pool: [1](#0-0) 

Unlike the sibling helpers `objectpool.Disconnect` (`internal/git/objectpool/disconnect.go`, lines 69-73) and `gitstorage.ReadAlternatesFile` (`internal/gitaly/storage/gitstorage/alternates.go`, lines 32-38), which both explicitly reject an alternates file containing more than one entry (`errors.New("multiple alternate object directories")` / `ErrMultipleAlternates`), `FromRepo` performs no such length check — it only verifies `!altInfo.Exists || len(altInfo.ObjectDirectories) == 0` before blindly using index `[0]`: [2](#0-1) 

This mirrors the OPCM pattern exactly: three independent call sites (`Disconnect`, `partition_assigner.go`'s `getAlternatePartitionID` via `gitstorage.ReadAlternatesFile`, and the `link.go` linking logic) enforce the "exactly one alternate" invariant, but `FromRepo` — used by the `GetObjectPool` RPC (`internal/gitaly/service/objectpool/get.go`, line 20) and other pool-resolution code — does not. If a member repository's alternates file ever contains multiple lines (e.g., a second line appended after the pool member is legitimately linked, via any code path that writes to `objects/info/alternates` without re-validating single-entry invariants, or via direct disk tampering across replicas/leftover state), `git` (and Git's object lookup machinery) will read objects from *all* listed directories, while `FromRepo`'s security-relevant derivation (`locator.ValidateRepository`) only validates the first path as being a legitimate, permitted pool repository. Any additional, unvalidated alternate directories are silently ignored by this check yet remain fully active for Git's own object resolution.

### Impact Explanation
This is a Medium-risk defense-in-depth gap: it does not itself grant write access, but it breaks the isolation invariant "a repository's usable alternate object directories are limited to the exactly-one that has been explicitly validated via `locator.ValidateRepository`." Because `FromRepo` reports success/derives the pool object solely from the first entry, callers relying on `FromRepo`'s validation (e.g., `GetObjectPool`) can be misled into believing a repository has a single, sanctioned pool link, when in fact Git will additionally consume objects from further, unvalidated alternate paths — undermining the assumption enforced elsewhere in the codebase (`Disconnect`, `ReadAlternatesFile`) that alternates files must contain exactly one entry.

### Likelihood Explanation
Likelihood is limited because the primary interfaces that *write* the alternates file (`objectpool.Link`) enforce single-alternate writes, and RPC-level object-pool creation paths generally reject multi-line alternates (as shown by `TestDisconnectGitAlternatesUnexpectedAlternates`, `internal/gitaly/service/objectpool/alternates_test.go`, lines 74-87, and `partition_assigner_test.go`'s `multiple alternates fail` case). The inconsistency is only exploitable if some other code path or historical/legacy repository state can leave a multi-line alternates file in place before `FromRepo`/`GetObjectPool` is invoked — this exact reachability from an ordinary unprivileged RPC request could not be fully confirmed with available tooling.

### Recommendation
Add the same length check performed in `Disconnect` and `gitstorage.ReadAlternatesFile` to `FromRepo`: reject (return `ErrInvalidPoolRepository` or a new dedicated error) when `len(altInfo.ObjectDirectories) > 1`, instead of unconditionally consuming only `AbsoluteObjectDirectories()[0]`. This makes the "exactly one alternate" invariant consistently enforced across every place that reads a repository's alternates file, rather than in three of four call sites.

### Proof of Concept
Not independently reproducible from the indexed code alone — confirming exploitability requires demonstrating a code path (or crash/restore/replication race) that can leave `objects/info/alternates` with more than one line before `GetObjectPool`/`FromRepo` is called, which was not found within the available search results. Recommend a Devin session with full repository/test access to check write paths (backup restore, replication, partition assignment) for ways a multi-line alternates file could survive to reach `FromRepo`.
