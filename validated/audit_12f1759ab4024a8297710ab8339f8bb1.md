### Title
Quarantine-directory ownership check binds only to `RelativePath`, not to a specific push transaction, allowing cross-request quarantine confusion - ([File: internal/git/localrepo/paths.go])

### Summary
The external report's root cause is that a permissionless, replayable action (`withdraw()`) is authorized using a hash/leaf that omits a domain-binding value (chain ID via EIP-712), so the same data validates in an unintended context. The nearest concrete analog in Gitaly is `Repo.ObjectDirectoryPath()` in `internal/git/localrepo/paths.go`, which authorizes an attacker/client-suppliable `GitObjectDirectory` field against a "quarantine ownership" value, `storage.QuarantineDirectoryPrefix()`, that is derived **only** from the repository's `RelativePath` — with no binding to the specific push/transaction that created the quarantine directory.

### Finding Description
`GitObjectDirectory` and `GitAlternateObjectDirectories` are ordinary fields of the `Repository` protobuf message that accompanies almost every Gitaly RPC. They are populated by GitLab Shell/Rails during object quarantine (see `doc/object_quarantine.md`), but nothing on the Gitaly side cryptographically ties them to a specific request — they are just strings supplied on the wire and accepted from any authenticated caller for any RPC that resolves a repository's object directory.

`ObjectDirectoryPath()` validates such a value in two ways:
1. It must resolve to a relative path inside the repository, or
2. If not, it is accepted anyway when it falls inside the storage's temp directory and starts with a repository-specific prefix: [1](#0-0) 

That prefix is computed as: [2](#0-1) 

The prefix is `"quarantine-" + hex(sha1(RelativePath)[:8]) + "-"` — a deterministic, non-secret value computable by anyone who knows (or can guess/enumerate, since paths are often hashed-storage but well-known project paths map onto them) the target repository's `RelativePath`. It is **not** bound to:
- which specific push/transaction created the quarantine directory,
- which user/session initiated that push,
- a random nonce or transaction ID.

This is directly analogous to the reported bug class: an unprivileged, permissionless-to-replay value (the quarantine "ownership" token) lacks the domain/context separator (here: transaction identity) that should scope it to a single execution context, so the same value validates for *any* quarantine directory ever created for that repository — including ones from other concurrent or still-open transactions.

### Impact Explanation
A repository can have multiple concurrent write RPCs in flight (e.g., two concurrent pushes to the same repository, or a push racing an `OperationService` RPC that also uses `updateref.UpdaterWithHooks` quarantining, per `doc/hooks.md`). Each such write creates its own quarantine directory under the storage's temp dir (see `internal/gitaly/storage/storagemgr/partition/transaction_manager.go`, which creates `txn.quarantineDirectory = filepath.Join(txn.stagingDirectory, "quarantine")`). Because the ownership check only verifies "this path belongs to repo X's family of quarantine directories" rather than "this path belongs to *my* transaction's quarantine directory," a client crafting a request with a `GitObjectDirectory` set to another in-flight quarantine path for the same repository would pass validation as long as the path exists and matches the repo-derived prefix.

Concretely this enables:
- Cross-transaction object visibility/confusion: an RPC (e.g., anything using `repo.ObjectDirectoryPath()`/`repo.Quarantine()`-derived local repos, such as internal read paths that trust `GitObjectDirectory`) could be pointed at another party's not-yet-committed (not-yet-`pre-receive`-approved) quarantined objects for the same repository, exposing objects that should still be invisible/unauthorized (quarantine is specifically designed to hide unapproved objects from the rest of the system until `pre-receive` passes).
- A weakening of the quarantine boundary's intended guarantee that "only the process that owns this exact quarantine instance can reference it," reducing quarantine/hook gating to a per-repository (not per-transaction) boundary.

This maps to the "hook and quarantine gating" and "object-pool and alternates isolation" categories explicitly in scope, is reachable via a crafted RPC field from an ordinary authenticated client during a normal push flow, and does not require a malicious peer/node or leaked token — the prefix is derivable from public repository metadata.

### Likelihood Explanation
Exploitation requires:
1. An attacker capable of issuing Gitaly RPCs against the target repository (a normal, low-privilege capability for any user who can push/write to that repository, or any component forwarding `Repository` messages, e.g., a hook payload constructed with an attacker-influenced object directory) — this is an "ordinary user" surface, not a privileged operator.
2. Racing another write to the same repository so that a second quarantine directory concurrently exists (achievable by any user who can trigger two concurrent pushes, e.g. via GitLab CI parallel jobs or scripted concurrent pushes).
3. Computing the deterministic SHA1-based prefix from the repository's known `RelativePath` (no secret required).

The main mitigating factor is that this requires timing (the other quarantine directory must still exist on disk) and that in most flows `GitObjectDirectory` is set internally by Gitaly/Rails rather than freely chosen by an external client — the extent to which arbitrary RPC callers can freely set this field on requests that reach `ObjectDirectoryPath()` is not fully verified in this codebase (this would require confirming whether any externally-reachable RPC forwards a client-supplied `Repository.GitObjectDirectory` without further pre-authorization by GitLab Shell/Rails). This limitation is worth explicit verification before treating this as fully proven.

### Recommendation
Bind the quarantine "ownership" token to the specific transaction/quarantine instance, not merely to the repository's relative path:
- Include a transaction-specific random component (e.g., the transaction's staging directory name/ID) as part of the value that is verified, rather than relying purely on `sha1(RelativePath)`.
- Alternatively, verify quarantine directory ownership by checking it against the transaction/quarantine directory value recorded server-side for the *current* request/transaction rather than accepting any path that merely matches the repository-derived prefix.
- Treat `GitObjectDirectory`/`GitAlternateObjectDirectories` as a trust boundary: reject values on this field unless they were generated by Gitaly itself for the current request's transaction.

### Proof of Concept
Conceptual PoC (not fully executable without live cluster access to confirm callers can set `GitObjectDirectory` externally):
1. Attacker triggers Push A to repository `R` (RelativePath known), which creates quarantine directory `tempDir/quarantine-<sha1(R)[:8]>-A` and starts `pre-receive`.
2. Concurrently, attacker triggers Push B (or another RPC) to the same repository `R`, crafting the `Repository.GitObjectDirectory` field to point at Push A's quarantine directory instead of its own (`tempDir/quarantine-<sha1(R)[:8]>-A`).
3. Because `QuarantineDirectoryPrefix(repo)` depends only on `R`'s `RelativePath`, `ObjectDirectoryPath()`'s prefix check succeeds for Push B's crafted value even though it references Push A's quarantine directory, not Push B's own.
4. Push B's git process therefore operates against Push A's quarantined (not-yet-approved) objects, breaking the intended per-transaction isolation of the quarantine mechanism. [3](#0-2)

// QuarantineDirectoryPrefix returns a prefix for use in the temporary directory. The prefix is
// based on the relative repository path and will stay stable for any given repository. This allows
// us to verify that a given quarantine object directory indeed belongs to the repository at hand.
// Ideally, this function would directly be located in the quarantine module, but this is not
// possible due to cyclic dependencies.
func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
}
