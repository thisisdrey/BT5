### Title
Unvalidated array-length fields from TVM precompile input allow attacker-controlled memory allocation / denial-of-service in `BatchValidateSign` - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` precompiled contract, and its helper array-extraction functions, take a "length" field directly from attacker-controlled calldata and use it to size a Java array (`new byte[len][]`) before validating that the length is bounded or consistent with the actual size of the input buffer. This mirrors the CVE's root cause: a length/config value parsed straight out of untrusted input is used to drive memory allocation without adequate bounds checking, which can lead to a denial-of-service (excessive/incorrect memory allocation) rather than a buffer over-read (Java arrays can't over-read, but they can still be mis-sized based on attacker data).

### Finding Description
`BatchValidateSign.doExecute` parses the calldata into `DataWord[] words` and computes offsets/lengths purely from data supplied by the caller: [1](#0-0) 

The size check (`sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE`) is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is enabled, and even then it only bounds the signature array — the address array extraction path (`extractBytes32Array`) is unconditionally called with a `len` read straight from calldata: [2](#0-1) 

Similarly, `extractBytesArray` (used when `allowTvmSelfdestructRestriction()` is off) allocates `new byte[len][]` from an attacker-supplied `len` before any bound is enforced: [3](#0-2) 

Crucially, the energy charged for this precompile is computed only from the *physical* length of the submitted calldata (`data.length`), not from the attacker-controlled `len` value embedded inside the words: [4](#0-3) 

This means a caller can submit a small amount of calldata (cheap energy cost) that encodes a huge offset word (e.g., `intValueSafe()` near `Integer.MAX_VALUE`) at the position used as `len`, causing the node to attempt to allocate an enormous `byte[len][]` array while having paid for only a tiny amount of energy. The resulting `OutOfMemoryError`/huge allocation is caught generically in `execute()`: [5](#0-4) 

but the JVM has already attempted the allocation by the time the `Throwable` is caught, which can exhaust heap and destabilize or crash the node process for all other concurrent transaction/block processing (denial of service), analogous to the CAF header CVE where a maliciously crafted length field drives an unchecked/incorrect memory allocation.

Note: I was unable to fully verify the exact bound guarantees of `DataWord.intValueSafe()` (i.e., whether it already clamps to some smaller safe maximum) because the tool budget ran out before I could read its implementation in `common/src/main/java/org/tron/common/runtime/vm/DataWord.java`. This is the key remaining uncertainty for confirming exploitability — if `intValueSafe()` clamps to a small value, the allocation-size risk is mitigated; if it only guards against negative/overflowed longs, then large `int` values (up to `Integer.MAX_VALUE`) are attacker-reachable and the finding stands as described.

### Impact Explanation
If `intValueSafe()` does not sufficiently clamp attacker-controlled lengths, any account able to broadcast a transaction that calls the `BatchValidateSign` precompile address from a smart contract can trigger an oversized array allocation attempt (`new byte[len][]`) for negligible energy cost. Because energy metering (`getEnergyForData`) is decoupled from the actual `len` value used for allocation, an attacker pays far less energy than the resource consumption they cause, and repeated/concurrent such calls can induce memory pressure severe enough to crash or stall node processing — a resource-exhaustion denial-of-service reachable from ordinary TVM contract calls.

### Likelihood Explanation
Likelihood is uncertain pending confirmation of `DataWord.intValueSafe()`'s actual bound. The code path itself is trivially reachable: any contract call/invocation of the `BatchValidateSign` precompile address with attacker-chosen calldata reaches `extractBytesArray`/`extractBytes32Array` without a prior length-sanity check (the `MAX_SIZE` guard is feature-flagged and even then only covers the signature-array branch, not the address-array branch). Given this, if `intValueSafe()` permits large positive `int` values, the likelihood of triggering costly allocations is high and requires no special privileges.

### Recommendation
- Enforce the `MAX_SIZE` (or an equivalent hard cap) bound on both the signature-array length and address-array length unconditionally, not just under `VMConfig.allowTvmSelfdestructRestriction()`.
- Validate that any length value extracted from calldata (`words[offset].intValueSafe()`) is consistent with the actual size of `data` before using it to size arrays, in both `extractBytesArray` and `extractBytes32Array`.
- Make `getEnergyForData` energy cost a function of the actual `len`/array sizes decoded from calldata (or reject calls whose declared lengths are inconsistent with `data.length`), not just the raw byte length of the input.

### Proof of Concept
Conceptually: build a transaction that calls the `BatchValidateSign` precompile address (via a contract's `CALL`/`STATICCALL` to the fixed precompile address) with calldata where:
- Word 0 = arbitrary hash.
- Word 1 = an offset pointing to a word whose decoded `intValueSafe()` value is a very large positive integer (e.g., close to `Integer.MAX_VALUE`), used as `len` in `extractBytesArray`.
- The remaining calldata kept minimal so that `getEnergyForData` charges very little energy.

Since `allowTvmSelfdestructRestriction()` gates the only bound check, and it does not cover the `extractBytesArray`/`extractBytes32Array` `len` itself in all configurations, executing this call attempts `new byte[len][]`, causing an outsized/incorrect memory allocation for minimal energy cost — the analog to the WavPack CAF header CVE's "maliciously crafted [header] file" driving "incorrect memory allocation."

(This PoC's actual exploitability depends on confirming that `DataWord.intValueSafe()` does not itself clamp `len` to a small safe bound — a detail I could not verify within the available tool budget.)

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
