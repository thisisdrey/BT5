Audit Report

## Title
Stale aggregated oracle price is returned indefinitely once fresh submissions expire - ([File: substrate/frame/honzon/oracle/src/default_combine_data.rs])

## Summary
`DefaultCombineData::combine_data` in [1](#0-0)  filters raw submissions by `ExpiresIn` but falls back to `prev_value` with no freshness check on `prev_value` itself whenever fewer than `MinimumCount` fresh values remain. This stale `prev_value` is then written back into `Values` storage in `do_feed_values`, causing the pallet to indefinitely serve an arbitrarily old price to any consumer of `Pallet::get`/`DataProvider::get`.

## Finding Description
`combine_data` retains only submissions within the `ExpiresIn` window, then returns `prev_value` verbatim if the retained count is below `MinimumCount`, without checking `prev_value.timestamp` against `expires_in`: [2](#0-1) . The `prev_value` argument is `Self::values(key)`, the last aggregated value, fetched inside `combined()`: [3](#0-2) . Whatever `combined()` returns (including a stale `prev_value`) is written straight back into `Values<T, I>` in `do_feed_values`: [4](#0-3) . `Pallet::get` and the `DataProvider::get` implementation only surface `.value`, discarding the timestamp, so no downstream caller can detect staleness through this interface: [5](#0-4) [6](#0-5) . The generic `DataProvider` trait itself exposes only the value, never a timestamp: [7](#0-6) . This code is wired into the node runtime with concrete parameters (`MinimumCount=5`, `ExpiresIn=3600`): [8](#0-7) . Note that the module's own doc comment ("Returns prev_value if not enough valid values") confirms this fallback is by design, but the design omits any bound on how stale that fallback can become — there is no re-check of `prev_value`'s age before reuse.

## Impact Explanation
Any pallet built on `DataProvider<OracleKey, OracleValue>`/`pallet_oracle::Pallet::get` to price collateral, redemptions, or liquidations will silently consume an arbitrarily old value once the pool of live/fresh feeders drops below `MinimumCount` — this is a runtime bug that compromises the intended freshness guarantee of the oracle price feed, matching the "runtime bugs that compromise intended behavior" impact class. The severity is entirely contingent on whether/how a specific consuming runtime wires pricing logic to this data provider; in this repository the oracle pallet's own storage and API give no signal of staleness.

## Likelihood Explanation
No privileged action, forged proof, or malicious actor is required to enter the stale state — it is triggered by ordinary reduction in oracle feeder activity (membership churn, feeders going offline) causing the retained fresh-value count to drop below `MinimumCount` within the `ExpiresIn` window. Once triggered, the state self-perpetuates because the stale `prev_value` is fed back as the new `prev_value` on every subsequent call while feeds stay sparse, requiring no further attacker involvement to persist.

## Recommendation
Gate the `prev_value` fallback on its own freshness: only return `prev_value` if `prev_value.timestamp.saturating_add(expires_in) > now`, otherwise return `None`. Additionally, expose the timestamp/staleness through `DataProvider` (or via `DataProviderExtended`, which already carries `TimestampedValueOf`) so downstream consumers can independently reject stale prices instead of relying solely on `pallet-oracle`'s internal `Values` state.

## Proof of Concept
1. Configure `pallet_oracle::DefaultCombineData<T, ConstU32<N>, ConstU64<3600>>` as in the node runtime config at [9](#0-8) .
2. `N` members feed a price at `t = 0`; with `N` fresh values, `combine_data` computes and stores the median in `Values[key]` with `timestamp = 0` via `do_feed_values`.
3. All operators stop feeding (or are removed via `change_members_sorted`, which only clears `RawValues`, not `Values`: [10](#0-9) ). Advance `T::Time` far beyond `expires_in`.
4. Trigger one more `feed_values` call (or any path invoking `combined()`); `values.retain` empties the fresh set, `count < minimum_count`, so `combine_data` returns the untouched `prev_value` from `t = 0`, which is re-inserted into `Values[key]`.
5. Call `Pallet::get(key)` / `DataProvider::get(key)` — it still returns the `t = 0` value with no staleness indication, confirmed by the code paths cited above.

```rust
	fn combine_data(
		_key: &<T as Config<I>>::OracleKey,
		mut values: Vec<TimestampedValueOf<T, I>>,
		prev_value: Option<TimestampedValueOf<T, I>>,
	) -> Option<TimestampedValueOf<T, I>> {
		let expires_in = ExpiresIn::get();
		let now = T::Time::now();

		values.retain(|x| x.timestamp.saturating_add(expires_in) > now);

		let count = values.len() as u32;
		let minimum_count = MinimumCount::get();
		if count < minimum_count || count == 0 {
			return prev_value;
		}

		let mid_index = count / 2;
		// Won't panic as `values` ensured not empty.
		let (_, value, _) =
			values.select_nth_unstable_by(mid_index as usize, |a, b| a.value.cmp(&b.value));
		Some(value.clone())
	}
```

```rust
	fn do_feed_values(who: T::AccountId, values: Vec<(T::OracleKey, T::OracleValue)>) {
		let now = T::Time::now();
		for (key, value) in &values {
			let timestamped = TimestampedValue { value: value.clone(), timestamp: now };
			RawValues::<T, I>::insert(&who, key, timestamped);

			// Update `Values` storage if `combined` yielded result.
			if let Some(combined) = Self::combined(key) {
				<Values<T, I>>::insert(key, combined);
			}

			T::OnNewData::on_new_data(&who, key, value);
		}
		Self::deposit_event(Event::NewFeedData { sender: who, values });
	}
```
