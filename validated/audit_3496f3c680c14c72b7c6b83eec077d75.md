### Title
Attacker can fill a victim's `MAX_TOKENS_PER_USER` slots with forced dust deposits, permanently blocking new collateral/debt positions - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to the OpenQ `nftDepositLimit` grief, `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` enforce a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined size of `debtTokensOfAccount` + `depositTokensOfAccount`. A token is added whenever an account's balance moves from `0`. `DepositToken.deposit(amount_, onBehalfOf_)` lets anyone mint deposit-token shares to an arbitrary `onBehalfOf_` address, and `DepositToken.transfer` lets anyone push dust shares to a victim. An unprivileged attacker can therefore populate a victim's per-account list with tokens the victim never chose, until the cap is hit and every subsequent first-time deposit or first debt issuance reverts with `UserReachedMaxTokens`. ### Finding Description
The counter that is being grieved here is the `MappedEnumerableSet` length checked in `onlyIfAdditionWillNotReachMaxTokens`:

```solidity
if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
    revert UserReachedMaxTokens();
}
``` [5](#0-4) 

Unlike OpenQ, removals do decrement the set (`_burn`/`_transfer` call `removeFromDepositTokensOfAccount` when the balance hits zero). However, the victim's ability to remove an unwanted entry depends on the dust being transferable — `transfer` and `withdraw` both call `_revertIfLocked`, which reverts if `unlockedBalanceOf(victim) < amount`. `unlockedBalanceOf` returns `min(balance, quote(_issuableInUsd / collateralFactor))` whenever the account has debt, so a victim whose position is at (or above) its collateral factor has zero unlocked balance and cannot eject the forced dust without first repaying debt. In that state the attacker can top up the dust cheaply each time the victim frees a slot, keeping the cap saturated — the same "limit reached artificially, refund/cleanup doesn't restore capacity" shape as the reference finding. [6](#0-5) [7](#0-6) 

### Impact Explanation
Temporary freezing of funds / position liveness DoS:

- A victim at the cap cannot deposit a collateral type they don't already hold (`_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`), so they cannot add new collateral to improve health during a liquidation event.
- A victim at the cap cannot open any new debt position, because the first `issue` of a new `DebtToken` adds to `debtTokensOfAccount` under the same modifier.
- If the victim has outstanding debt with no issuable headroom, the forced dust is locked (`unlockedBalanceOf` = 0), so they cannot clear slots by transferring it out; they must repay debt first, which the attack itself may be preventing them from doing economically (e.g., they can't deposit the new collateral they intended to borrow against).

### Likelihood Explanation
Cost scales with the number of registered deposit/debt tokens in the pool. Each forced entry requires the attacker to actually deposit real collateral (`deposit` pulls `underlying` from the attacker into `Treasury`) or to hold shares to transfer. Pools with few deposit-token types leave slots the victim can fill themselves first; the attack is only fully blocking when the attacker can occupy ~30 slots or front-run each of the victim's first-time deposits. It is a griefing attack: the attacker gets no profit and their dust can be recovered by withdrawing their own shares (their own cost is mainly gas and temporary capital). Reachable by any EOA via public `deposit`/`transfer` — no privileged role, oracle manipulation, or bridge message needed. Not gated by `whenNotPaused` differently for the victim, and `SynthContext`/`nonReentrant` do not mitigate it.

### Recommendation
- Gate `deposit(..., onBehalfOf_)` additions so that pushing a *new* token into someone else's list requires the recipient's consent (e.g., only the pool/operator may add to another account's list, or require the recipient to hold a signature/allowance).
- Alternatively, count only tokens whose balance exceeds a minimum "dust floor" toward `MAX_TOKENS_PER_USER`, or allow a forced "sweep" function that lets a user remove below-dust entries from their own list regardless of lock status (transferring the dust back to a burn address or to treasury).
- At minimum, exempt accounts from the cap check when the added token's balance is below a configurable threshold.

### Proof of Concept (Foundry-style sketch)
```solidity
// Assume pool has >= 30 registered DepositTokens d0..d29 and victim already
// has debt such that unlockedBalanceOf(victim) == 0 for small amounts.

function test_fillVictimSlots() public {
    address victim = address(0xBEEF);

    for (uint256 i; i < 30; ++i) {
        DepositToken d = depositTokens[i];
        uint256 dust = 1; // smallest unit; ensure it survives deposit fee
        IERC20(d.underlying()).approve(address(d), dust);
        // mint shares directly to victim -> adds d to victim's list
        d.deposit(dust, victim);
    }

    assertEq(
        pool.getDepositTokensOfAccount(victim).length +
        pool.getDebtTokensOfAccount(victim).length,
        pool.MAX_TOKENS_PER_USER()
    );

    // Victim cannot deposit a collateral type not already in their list
    vm.startPrank(victim);
    DepositToken dNew = depositTokens[30]; // or a fresh one
    IERC20(dNew.underlying()).approve(address(dNew), 1e18);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    dNew.deposit(1e18, victim);

    // Victim cannot eject the dust: transfer/withdraw revert via _revertIfLocked
    // because unlockedBalanceOf(victim) == 0 while debt is at its limit.
    vm.expectRevert(DepositToken.NotEnoughFreeBalance.selector);
    depositTokens[0].transfer(attacker, 1);
    vm.stopPrank();
}
```

Caveat: I did not fully verify `DebtToken`'s add/remove behavior (the grep did not surface the relevant lines in the available output), but the deposit-token path alone is sufficient to saturate the combined cap, and the `debtTokensOfAccount` cap check shares the same modifier. The finding stands on the `DepositToken._mint`/`_transfer` → `Pool.addToDepositTokensOfAccount` path shown above.
