## Analysis Result



### Title
Unprivileged Concurrent Ref-Write Can Abort Repository-Deletion Transactions via Strict "Directory Must Be Empty" Check - (File: internal/gitaly/storage/storagemgr/partition/conflict/fshistory/tree.go)

### Summary
`TransactionManager.verifyFileSystemOperations` conflict-checks every `RemoveDirectoryEntry` operation of a committing transaction (including `DeleteRepository`/`RemoveObjectPool` transactions) against an in-memory `fshistory` tree that strictly forbids removing a directory containing any live entries [1](#0-0) . Any repository collaborator who can push a reference update can race a concurrent `DeleteRepository`/pool-deletion transaction and cause it to fail outright with a `DirectoryNotEmptyError`, mirroring the reported class of bug where a strict "must be empty/zero" invariant can be defeated by an unprivileged party performing a small, otherwise-harmless action against the very resource being torn down.

### Finding Description
`verifyFileSystemOperations` walks each `RemoveDirectoryEntry` operation of a transaction and calls `fsTX.Remove(path)` [2](#0-1) . Internally this hits `applyUpdate`, which rejects the deletion outright if the directory node still has any `directoryEntries` recorded — including entries added by any transaction committed concurrently since the deleting transaction's snapshot — by returning `newDirectoryNotEmptyError(path)` [1](#0-0) .

The dedicated test suite for `DeleteRepository` demonstrates the exploitable race directly: a transaction that pushes a new branch (`refs/heads/branch`) committed concurrently with a `DeleteRepository` transaction causes the deletion to fail with `fshistory.DirectoryNotEmptyError{Path: "…/refs/heads"}` [3](#0-2) , and a second test shows the same effect when a file is written into a directory the deletion needed empty [4](#0-3) . Unlike the analogous pack-refs housekeeping path, which gracefully keeps a directory in place when a concurrent write races it (`directoriesToKeep[relativePath] = struct{}{}`) instead of aborting the whole operation [5](#0-4) , the repository/pool-deletion path has no such tolerance and simply fails the entire transaction.

Because reference pushes and repository deletion (e.g. `RemoveRepository`, `DeleteObjectPool`) are both ordinary, unprivileged RPC operations reachable by any user with write access to the target repository, a user can repeatedly issue trivial ref writes timed against deletion attempts to keep forcing `DirectoryNotEmptyError` aborts, similar in spirit to the reported liquid-staking bug where a strict zero-balance check let an unprivileged token transfer permanently block account closure.

### Impact Explanation
A user with ordinary push access to a repository can indefinitely delay/"grief" administrative deletion of that repository or its object pool by racing tiny reference updates against every deletion attempt, causing repeated transaction aborts. This is a denial-of-service on the repository/pool-removal RPC handler path (`DeleteRepository`/`DeleteObjectPool`) rather than a data-corruption issue, since the underlying conflict-detection design is otherwise sound and intentional for consistency — but it lacks the graceful degrade-and-retry behavior present in the pack-refs housekeeping equivalent.

### Likelihood Explanation
Likelihood is limited: the attacker needs standing write access to the very repository being deleted, and each individual failure is a transient, retryable transaction abort rather than a permanent, unrecoverable state (unlike the on-chain ATA that can never be closed). Exploitation additionally requires tight timing against an operator-driven deletion RPC, and in practice higher layers (e.g., GitLab Rails revoking access before deletion) may reduce the exposed window.

### Recommendation
Bring the `DeleteRepository`/pool-deletion path in line with the pack-refs housekeeping path's tolerant handling: rather than aborting the whole transaction on `DirectoryNotEmptyError` for entries introduced by legitimately-conflicting concurrent writes, either (a) fail with a scoped, targeted conflict error that only rejects the specific conflicting sub-path while still allowing the deletion to make forward progress on retry, or (b) have the deletion path exclusively lock the repository against further reference-transaction admission before deciding on conflict outcomes, as is already partly done via `repoutil.Lock` at the RPC layer [6](#0-5) , ensuring this locking also excludes the transaction-manager-level admission of new writes for the duration of the delete transaction's conflict check.

### Proof of Concept
1. Client A begins a write transaction on repository R and pushes `refs/heads/branch`.
2. Client B concurrently begins a `DeleteRepository` transaction on R (e.g., via `RemoveRepository`/`DeleteObjectPool`).
3. Client A's transaction commits first.
4. Client B's deletion transaction's `verifyFileSystemOperations` attempts to remove `R/refs/heads` and fails with `fshistory.DirectoryNotEmptyError{Path: "R/refs/heads"}`, aborting the entire deletion — reproduced exactly by the existing test case `"deletion fails with concurrent write introducing files in repository"` [3](#0-2) .
5. Client A repeats step 1 for every subsequent deletion attempt from Client B, perpetuating the abort.
