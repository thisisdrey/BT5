### Title
Unbounded Array Allocation from Attacker-Controlled Length in TVM Precompile ABI Decoding - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytesArray` and `PrecompiledContracts.extractBytes32Array` allocate Java arrays whose size is taken directly from calldata-controlled `DataWord` values without any upper-bound validation, mirroring the CVE-2022-41845 bug class in Bento4's `AP4_Array<AP4_ElstEntry>::EnsureCapacity` where an attacker-controlled length field drives unchecked memory allocation.

### Finding Description
Both helper methods read a length word directly from the precompile's input data and use it, unvalidated, to size a new array: [1](#0-0) 

```java
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
  int len = words[offset].intValueSafe();
  byte[][] bytes32Array = new byte[len][];
  ...
}

private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
  ...
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  ...
}
```

`DataWord.intValueSafe()` only clamps values whose byte representation occupies more than 4 bytes (or is negative) to `Integer.MAX_VALUE`; it performs no upper-bound sanity check appropriate to the expected element count of the ABI-encoded dynamic array: [2](#0-1) 

Because `len` can be attacker-supplied up to `Integer.MAX_VALUE`, the subsequent `new byte[len][]` attempts to allocate an array of up to ~2^31 object references (roughly 16 GB of reference slots alone, before any of the inner byte arrays are populated). This is the same bug class as the Bento4 CVE: a length field taken from untrusted input is used to size a container without bounds checking, causing excessive memory consumption (`OutOfMemoryError`) rather than a controlled rejection.

### Impact Explanation
Any account can invoke a TVM precompiled contract that consumes this ABI-decoding path (these `extractBytesArray`/`extractBytes32Array` helpers are used for parsing dynamic `bytes[]`/`bytes32[]` precompile arguments elsewhere in `PrecompiledContracts.java`) by crafting a smart-contract call with a malicious length word. Triggering an `OutOfMemoryError` inside the node's transaction-execution/VM thread can destabilize the JVM heap for the whole node process, potentially crashing or hanging the node (denial of service), which falls within the "node crash or halt" impact category permitted by scope.

### Likelihood Explanation
Reaching this code only requires submitting a normal transaction that calls a TVM precompiled contract with crafted calldata containing an oversized length word in the position read by `words[offset]`. No special privileges, precompiled-contract-specific validation bypass, or SR/witness/peer control is needed — it is reachable by any ordinary contract-calling transaction, matching the "single signed transaction / contract call" bar required by the rules.

### Recommendation
Add an explicit sane upper bound check on `len` before allocation in both `extractBytes32Array` and `extractBytesArray` (e.g., reject/short-circuit if `len` exceeds a reasonable maximum consistent with `data.length`/`words.length`, similar to the bounds check already present via `offset > words.length - 1`), so a crafted length cannot drive multi-gigabyte allocation attempts.

### Proof of Concept
Craft a transaction that calls a precompiled contract address whose input parsing invokes `extractBytes32Array`/`extractBytesArray`, placing at the length-word offset a value such as `0x7fffffff` (2^31-1). This value passes through `intValueSafe()` unchanged (small enough to fit 4 bytes) and is used directly as `len` in `new byte[len][]`, causing the JVM to attempt an allocation of ~2^31 array-reference slots, triggering `OutOfMemoryError` during transaction execution.

*Note: I was unable to trace, within the available tool budget, every concrete precompile entry point (e.g., ecrecover/verifyProof-style precompile) whose input directly calls `extractBytesArray`/`extractBytes32Array` in this snapshot of `PrecompiledContracts.java`, nor confirm whether the resulting `OutOfMemoryError` is caught by an enclosing try/catch elsewhere in the VM dispatcher (which would reduce impact to a per-transaction failure rather than a full node crash). This should be verified with full file access/a Devin session before treating the "node crash" impact as fully confirmed.*
