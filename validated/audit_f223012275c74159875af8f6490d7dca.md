### Title
Missing MIN/MAX validation for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` chain parameters in `ProposalUtil.validator` - ([File: actuator/src/main/java/org/tron/core/utils/ProposalUtil.java])

### Summary
`ProposalUtil.validator`, the single validation gate for every committee-proposed chain parameter change, defines explicit `[MIN, MAX]` bounds for almost all critical fee/limit parameters (`CREATE_ACCOUNT_FEE`, `TRANSACTION_FEE`, `ASSET_ISSUE_FEE`, `UPDATE_ACCOUNT_PERMISSION_FEE`, `MULTI_SIGN_FEE`, `MEMO_FEE`, `DYNAMIC_ENERGY_*`, etc.) but explicitly skips validation for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE`:

```
case ENERGY_FEE:
case EXCHANGE_CREATE_FEE:
  break;
``` [1](#0-0) 

This is exactly the bug class described in the external report: a critical storage variable that is consumed later in transaction validation/execution paths (fee calculations that ordinary, unprivileged transaction senders depend on) can be set to an unbounded value with no MIN/MAX sanity check, unlike every sibling fee parameter in the same switch statement.

### Finding Description
`ENERGY_FEE` is the price-per-unit-of-energy used to compute the TRX cost of every smart-contract call on the network, and it is set through the standard committee proposal pipeline: `ProposalCreateActuator.validateValue` calls `ProposalUtil.validator`, and once approved, `ProposalService.process` writes the value directly into `DynamicPropertiesStore` via `saveEnergyFee`: [2](#0-1) [3](#0-2) 

Every other fee-type `ProposalType` in the same validator has an explicit range check (e.g. `[0, LONG_VALUE]` where `LONG_VALUE = 100_000_000_000_000_000L`): [4](#0-3) 

but `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` fall straight through to `break;` with zero validation, meaning any `long` value (including `Long.MAX_VALUE`, negative values, or 0) is accepted.

`EXCHANGE_CREATE_FEE` is later consumed directly in `ExchangeCreateActuator.calcFee()`/`doValidate()`/`execute()` to determine both the balance check and the amount burned from the caller's account: [5](#0-4) [6](#0-5) 

If this value is set to an extreme value (e.g. near `Long.MAX_VALUE`), any unprivileged account attempting `ExchangeCreateContract` would either always fail (permanent DoS of the exchange-creation feature, mirroring the reported "deposit reverts because amount < relayerFee" pattern) or, if set to a negative value, could allow fee/balance arithmetic to underflow/overflow (`addExact`/`subtractExact` are used defensively here and would throw `ArithmeticException`, but the lack of upstream bounds checking means this class of parameter is the only place in the file relying entirely on incidental downstream exception handling rather than intentional validation). `ENERGY_FEE` similarly feeds the resource/fee accounting used for every contract-invoking transaction network-wide, so an unbounded value has network-wide DoS or economic-distortion potential (energy priced at 0 makes contract execution free; energy priced arbitrarily high makes contract calls unaffordable for ordinary users), all triggered by a single approved parameter change with no sanity ceiling/floor comparable to its sibling parameters.

### Impact Explanation
Once such a proposal is approved and processed, the resulting misconfiguration is reachable by any ordinary, unprivileged transaction sender: every `TriggerSmartContract`/`CreateSmartContract` transaction pays energy at `ENERGY_FEE`, and every `ExchangeCreateContract` transaction pays `EXCHANGE_CREATE_FEE`. Unlike every other bounded fee, there is no defense-in-depth ceiling here, so a single mis-set proposal value can either (a) permanently DoS an entire feature/transaction type for all users until a new proposal clears the required maintenance-cycle voting delay, or (b) enable free/near-free contract execution, which can be abused to exhaust node/validator energy resources without proportional payment — a resource-accounting integrity issue. This matches the Medium severity of the original finding: a legitimate, foreseeable operational mistake (not requiring a malicious committee, simply the same class of oversight the report warns about) causes a broad, difficult-to-quickly-remediate denial of service or economic distortion.

### Likelihood Explanation
Every other fee/parameter in the same switch statement received a bounds check specifically to prevent this scenario, indicating the omission for `ENERGY_FEE`/`EXCHANGE_CREATE_FEE` is an oversight rather than an intentional design choice. Given the number of parameters governed by this same function, an unbounded value being proposed and approved (even inadvertently, exactly as the original report describes "by mistake") is plausible, and its effects are immediate and network-wide once the proposal takes effect at the next maintenance cycle.

### Recommendation
Add explicit `MIN`/`MAX` bounds checks for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` in `ProposalUtil.validator`, consistent with the `[0, LONG_VALUE]` pattern already used for `CREATE_ACCOUNT_FEE`, `ASSET_ISSUE_FEE`, etc., so that neither parameter can be pushed to an economically nonsensical or DoS-inducing value.

### Proof of Concept
1. A committee member submits a `ProposalCreateContract` setting `ProposalType.ENERGY_FEE` (code 11) to `Long.MAX_VALUE` (or `EXCHANGE_CREATE_FEE`, code 12, similarly).
2. `ProposalCreateActuator.validateValue` invokes `ProposalUtil.validator`, which hits `case ENERGY_FEE: case EXCHANGE_CREATE_FEE: break;` and accepts the value unconditionally. [1](#0-0) 
3. Once the proposal passes committee approval and the next maintenance cycle runs, `ProposalService.process` calls `saveEnergyFee`/`saveExchangeCreateFee`, persisting the unbounded value. [7](#0-6) 
4. Any subsequent unprivileged `ExchangeCreateContract` transaction now fails `doValidate()`'s balance checks for virtually any realistic account balance (`accountCapsule.getBalance() < calcFee()`), permanently denying the feature to all users: [5](#0-4) 
5. For `ENERGY_FEE`, all future contract-invoking transactions network-wide are re-priced instantly and unboundedly, since no defensive bound exists to reject the value at proposal-creation time.
