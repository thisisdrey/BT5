### Title
Coarse integer `x-gitaly-cost` scoring undercharges CPU/memory-heavy, low-byte-transfer RPCs, letting attackers bypass upstream rate limiting and exhaust Gitaly resources - (File: internal/grpc/middleware/costhandler/costhandler.go)

### Summary
The external report's root cause is a value with too little granularity (an integer `tokenGasPrice`/gas-fee unit) that cannot proportionally represent the real cost of an operation, causing either wild overcharge or complete undercharge (`0`) depending on the token's real-world value. The analogous defect in gitaly's RPC-handler resource-limiting subsystem is `computeCost()` in `costhandler.go`: it derives the externally-trusted `x-gitaly-cost` trailer from (a) a small hard-coded integer "static" weight per RPC type, and (b) an integer count of *bytes transferred*, while ignoring CPU/memory/object-graph-walk cost. Because the static weights are fixed small integers (0/1/3/5/8/10) chosen from historical averages, and the dynamic term is driven purely by payload bytes, any RPC that does expensive server-side computation but returns/consumes few bytes is scored as cheap (often `1`, sometimes `0`), just like the `tokenGasPrice` truncation letting an operation be priced far below its real cost.

### Finding Description
`x-gitaly-cost` is the signal Gitaly exports to let external, ordinary-user-facing rate limiters (Rails → Workhorse → Cloudflare's complexity-based rate limiting) throttle expensive callers [1](#0-0) . The score is computed entirely inside Gitaly by `computeCost`, which is the sum of a static per-method weight and a dynamic byte-based term: [2](#0-1) 

The static weight is looked up from a hard-coded override table or a coarse per-operation-type default (`accessor=1`, `mutator=5`, `maintenance=3`, `unknown=1`, and even `0` for some RPCs): [3](#0-2) 

The dynamic term is derived solely from `InPayloadBytes + OutPayloadBytes`, divided by a 1 MiB `byteCostDivisor`: [4](#0-3) 

This design assumes that resource cost tracks bytes transferred over the wire. That assumption breaks for any accessor RPC that performs a large, ordinary-user-triggerable server-side computation (revision walk, object enumeration, diff computation, tree traversal, etc.) but returns a small response — for example, requests that filter/limit results, requests that return only counts, or requests over pathological/deep histories that ultimately produce "not found"/empty results. Such calls carry only the fixed integer static weight (as low as `0`–`1`), which is the same order of magnitude of granularity as the `tokenGasPrice` bug: the "price per unit of real resource usage" rounds down to the smallest representable step, permanently undercharging (or zero-charging) the operation regardless of its true cost.

Because the trailer is trusted end-to-end by Rails/Workhorse/Cloudflare as the authoritative complexity signal without independent verification [5](#0-4) , an ordinary authenticated (or even unauthenticated, where routed) user can craft a sequence of accessor RPCs against a repository they can reach (their own project, a fork, or any repo they have read access to) that each individually score `0`–`1` on the external rate limiter's budget while consuming disproportionate CPU/IO/memory on the Gitaly node, defeating the very DoS-mitigation purpose the cost signal exists for. This is distinct from and independent of the internal `ConcurrencyLimiter`/`AdaptiveCalculator`, which is a coarse, unweighted per-RPC-type admission control and does not compensate for the mis-scored external signal.

### Impact Explanation
The cost score is explicitly documented as feeding Cloudflare's complexity-based rate limiting on GitLab.com and any self-managed upstream limiter [6](#0-5) . Systematic undercharging of computationally expensive, low-byte-transfer RPCs allows an ordinary user to issue a high volume of resource-intensive requests while remaining under the externally enforced rate-limiting budget, resulting in a resource-exhaustion / denial-of-service condition on the Gitaly node — the class of impact explicitly in scope ("DoS of a handler" via RPC-handler resource limits).

### Likelihood Explanation
Likelihood is high: any ordinary user with read access to at least one repository can trigger accessor RPCs (e.g., history/tree/diff enumeration APIs) with parameters chosen to maximize server-side work while minimizing response bytes (e.g., limits/filters/short-circuiting revisions), and repeat them at volume. No privileged access, leaked token, or malicious-peer assumption is required — only normal request crafting against reachable RPC fields, matching the "crafted RPC field" reachable path called out in the validation guidance.

### Recommendation
Incorporate an actual resource-usage signal (CPU time and/or object/commit counts walked, not just payload bytes) into the dynamic cost term, and/or raise the floor for computation-heavy accessor RPCs so the static weight cannot understate real cost by orders of magnitude. Consider deriving cost from `BurdenMonitor`/`trace2` per-command CPU and object counts (already collected, see `internal/git/trace2hooks/packobjects_metrics.go` and the `BurdenMonitor` referenced in `doc/load-management-architecture.md`) rather than relying purely on transferred bytes, so that expensive-but-small-response RPCs are not systematically scored near zero.

### Proof of Concept
1. As an ordinary user with read access to a repository, repeatedly call an `OpAccessor` RPC (default static cost `1`, e.g. an RPC not present in `staticCostOverrides`) with request parameters engineered to force a large internal revision/object walk but a small/empty response (e.g., over-restrictive path/limit filters, or revisions that resolve to few/no matches after a deep graph walk).
2. Observe via Gitaly's own Prometheus/BurdenMonitor metrics that CPU time and memory for these calls is high, while the `x-gitaly-cost` trailer returned to the caller — computed by `computeCost` in `internal/grpc/middleware/costhandler/costhandler.go:87-91` — reports the minimal static weight (`1`) plus `dynamicCostFromContext` rounding based on the small payload size (`0` extra, per lines 118-128).
3. Repeat the call in a loop; the aggregate `X-Score` accounted for by Rails/Workhorse/Cloudflare stays low (each call costs `1`), while actual Gitaly CPU/memory usage accumulates well beyond what the reported cost implies, demonstrating the rate-limiting bypass and consequent resource-exhaustion risk.

## Connection to Rails and Workhorse

Gitaly's role in the broader DoS mitigation system is to be the innermost
ring of defense and to communicate two signals outward: node health (for
circuit breaking) and per-RPC cost (for rate limiting).

**What Gitaly provides:**

- `x-gitaly-pressure` gRPC trailer on every response (0.0 = healthy,
  1.0 = saturated) — node health signal
- `x-gitaly-cost` gRPC trailer on every response — per-RPC cost score
- `RESOURCE_EXHAUSTED` gRPC errors when requests are rejected by the
  concurrency limiter or load shedder.

**What Rails does with it:**

- Reads the `x-gitaly-pressure` trailer via a gRPC client interceptor
- Maintains a moving average of pressure per Gitaly storage
- Trips a per-node circuit breaker when sustained pressure is detected
- Translates `x-gitaly-cost` into the `X-Score` HTTP response header for
  upstream consumption

For standard requests, Rails is in the response path:

```plaintext
(upstream rate limiter) <- X-Score header <- Rails <- x-gitaly-cost trailer <- Gitaly
```

For Git operations (clone, fetch, push), Workhorse streams directly
to/from Gitaly — Rails is only in the auth path. Workhorse reads the
`x-gitaly-cost` trailer from the Gitaly response and sets `X-Score` on
the HTTP response to the client:

```plaintext
(upstream rate limiter) <- X-Score header <- Workhorse <- x-gitaly-cost trailer <- Gitaly
                                    |
                           Rails auth response
```

// computeCost returns the cost score for a completed RPC. It combines a static
// base cost for the RPC type with a dynamic component from actual bytes
// transferred, read from the RPCEntry in context.
func computeCost(ctx context.Context, fullMethod string) int {
	static := staticCostForMethod(fullMethod)
	dynamic := dynamicCostFromContext(ctx)
	return static + dynamic
}

// dynamicCostFromContext computes the dynamic cost contribution from payload
// bytes tracked by the grpcstats.PayloadBytes stats handler.
func dynamicCostFromContext(ctx context.Context) int {
	stats := grpcstats.PayloadBytesStatsFromContext(ctx)
	if stats == nil {
		return 0
	}
	totalBytes := stats.InPayloadBytes + stats.OutPayloadBytes

	return int(math.Ceil(float64(totalBytes) / float64(byteCostDivisor)))
}
