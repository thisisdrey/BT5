### Title
Unvalidated `GitObjectDirectory`/`GitAlternateObjectDirectories` RPC fields allow object-directory escape outside the storage root - ([File: internal/git/gitcmd/command_factory.go])

### Summary
Every Gitaly RPC that carries a `gitalypb.Repository` message lets the caller set `git_object_directory` and `git_alternate_object_directories`. These fields are used verbatim by `alternates.Env()` to build the `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables for every Git subprocess Gitaly spawns, without verifying the resulting path stays inside the repository's storage.

### Finding Description
`ExecCommandFactory.newCommand` resolves the repository path via `cf.locator.GetRepoPath(ctx, repo)` (which validates `storage_name`/`relative_path`), but then immediately calls: [1](#0-0) 

`repo.GetGitObjectDirectory()` and `repo.GetGitAlternateObjectDirectories()` are joined with `repoPath` inside `alternates.Env` with no bounds checking: [2](#0-1) 

By contrast, the codebase already contains a dedicated, correct implementation for this exact problem — `Repo.ObjectDirectoryPath()` calls `storage.ValidateRelativePath(storagePath, ...)` and explicitly rejects paths that escape the storage root or don't match the recognized quarantine-directory shape: [3](#0-2) 

The same missing-boundary-check pattern also exists in `GitLabHookManager.customHooksEnv`, which builds the object-directory env vars for custom hooks the same unchecked way: [4](#0-3) 

`ValidateRepository`/`locator.GetRepoPath` (used ubiquitously before every git invocation) only check `storage_name` and `relative_path`: [5](#0-4) 

They never inspect `git_object_directory` or `git_alternate_object_directories`, so nothing in the common request-validation path constrains those two fields, analogous to `redeem()` accepting an arbitrary token address with no allow-list check.

### Impact Explanation
A caller that can set an arbitrary `Repository.git_object_directory` (e.g. `"../../../../tmp/attacker-dir"`) on any RPC that runs a git command against that repository (essentially all repository/blob/ref/commit/operation RPCs) will cause Gitaly to set `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` to a path outside the intended storage root. Depending on the RPC executed (e.g. object-writing operations, `git cat-file`, `unpack-objects`, `receive-pack`), this can be used to read or write loose objects to or from a directory outside the storage root — a storage escape / cross-repository (and potentially cross-storage) object access, and could corrupt or leak files if the escaped directory happens to overlap sensitive host paths.

### Likelihood Explanation
Reachability requires only sending an RPC with a crafted `Repository` message containing an out-of-bounds `git_object_directory`/`git_alternate_object_directories` value; no privileged access, malicious peer, or leaked token beyond ordinary RPC access is needed. In practice these fields are normally populated by GitLab Rails from Gitaly-issued quarantine data, but Gitaly's server-side validation (`ValidateRepository`) does not enforce this trust boundary itself, so any RPC client capable of shaping the `Repository` proto (including through a compromised/malicious upstream component, or any RPC surface where the field is client-influenced) can trigger it.

### Recommendation
Validate `git_object_directory` and `git_alternate_object_directories` the same way `Repo.ObjectDirectoryPath()` already does — via `storage.ValidateRelativePath` against the storage root (and the existing quarantine-prefix check) — inside `alternates.Env`/`newCommand` and inside `customHooksEnv`, rejecting any repository whose object-directory fields resolve outside the storage root before they're used to build the Git environment.

### Proof of Concept
1. Craft a `gitalypb.Repository` with valid `storage_name`/`relative_path` (passes `ValidateRepository`) but set `git_object_directory: "../../../../tmp/evil"`.
2. Send an RPC that executes a git command against that repository (any RPC using `ExecCommandFactory.newCommand`, e.g. a blob/commit read or an operations RPC).
3. Observe that `alternates.Env` (`internal/git/alternates/alternates.go:9-27`) sets `GIT_OBJECT_DIRECTORY=<repoPath>/../../../../tmp/evil`, i.e., a path outside the storage root, with no rejection — unlike the equivalent, validated code path in `Repo.ObjectDirectoryPath()` (`internal/git/localrepo/paths.go:19-83`), demonstrating the missing allow-list/boundary check.

// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

	return env
}

// ObjectDirectoryPath returns the full path of the object directory. The errors returned are gRPC
// errors with relevant error codes and should be passed back to gRPC without further decoration.
func (repo *Repo) ObjectDirectoryPath(ctx context.Context) (string, error) {
	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", err
	}

	objectDirectoryPath := repo.GetGitObjectDirectory()
	if objectDirectoryPath == "" {
		return "", structerr.NewInvalidArgument("object directory path is not set")
	}

	storagePath, err := repo.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return "", fmt.Errorf("get storage by name: %w", err)
	}

	// Ensure the path points somewhere in the storage.
	relativeObjectDirectoryPath, err := storage.ValidateRelativePath(storagePath, filepath.Join(repoPath, objectDirectoryPath))
	if err != nil {
		return "", structerr.NewInvalidArgument("validate relative path: %w", err)
	}
