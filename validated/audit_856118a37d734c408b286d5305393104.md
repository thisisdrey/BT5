### Title
Relay peer authentication bypass via unverified `RelayFromAddr` in CreateRelayRequest — (File: `relay_manager.go`)

### Summary
`handleCreateRelayRequest()` derives the relay-peer's identity directly from an attacker-controlled protobuf field (`m.RelayFromAddr`) inside the `NebulaControl` message, instead of using the cryptographically verified VPN address bound to the certificate of the `HostInfo` (`h`) that actually sent the control message. This mirrors the M-21 root cause pattern: trusting a self-reported/derived address as the authenticated "sender" identity, rather than the address bound to the verified principal that produced the request.

### Finding Description
When a node wants to establish a relay tunnel, `StartRelays()`/`relayManager` code sends a `NebulaControl_CreateRelayRequest` message over an already-established, authenticated Noise tunnel. That control message carries a self-declared `RelayFromAddr` field set by the sender: [1](#0-0) 

On the receiving side, `handleCreateRelayRequest` is invoked with `h`, the `HostInfo` of the peer that authenticated and sent this control packet (its identity/vpnAddrs are certificate-bound and verified by the handshake). However, the function computes `from` purely from the message payload, not from `h.vpnAddrs`: [2](#0-1) 

This `from` value is then used as the key under which relay state is created and later used for routing decisions — both for the terminal case (`AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)`) and, when forwarding, for the target's relay table (`AddRelay(rm.l, peer, f.hostMap, from, nil, ForwardingType, Requested)`): [3](#0-2) [4](#0-3) 

Nowhere in `handleCreateRelayRequest` is `from` checked against `h.vpnAddrs[0]` (the actually-authenticated sender's certificate address) — the code only checks that `from` is not *my own* address: [5](#0-4) 

This is structurally identical to the M-21 bug class: an address that should be bound to the verified initiating principal is instead accepted from an unauthenticated/self-declared field, and used downstream to build routing/trust state (`relayState`, `QueryVpnAddrsRelayFor`) keyed on that unverified value: [6](#0-5) 

### Impact Explanation
A legitimately-authenticated (but malicious) peer `h` can request a relay while claiming `RelayFromAddr` equal to an arbitrary third-party VPN address (e.g. a victim host it has never actually tunneled with). The relay node will then create/overwrite relay state (`relayState.relayForByAddr`, `relayForByIdx`) associating that spoofed address with the attacker's own authenticated tunnel index. This can:
- Poison relay routing state on the relay node and on the forwarding target's `HostInfo`, colliding with or displacing legitimate relay entries the real owner of that VPN address would later try to establish (denial-of-relay-service / state corruption).
- Cause the relay to attribute forwarded relay traffic to a spoofed VPN address in its bookkeeping/logs (`relayFrom` in structured logs), undermining operator trust in relay accounting.
- In `handleCreateRelayResponse`/subsequent lookups keyed by IP (`QueryRelayForByIp(from)`), an attacker-chosen `from` can trigger state-machine transitions (`Requested`→`Established`, etc.) for an address it doesn't own, since none of these paths re-validate `from == h.vpnAddrs[0]`.

This falls under "remote state poisoning," matching the rules' accepted impact categories, since Nebula's relay hostmap/lighthouse trust model is directly manipulated by an unverified sender-claimed address, exactly as in the ZetaChain analog where `emittingContract`/self-declared data was substituted for the verified originator.

### Likelihood Explanation
Any node that can complete a normal handshake with a relay node (i.e., any node holding a CA-signed certificate that can talk to the relay — which satisfies the "no CA-signed certificate" reachability caveat only if an attacker has any valid, even low-privilege, certificate) can trigger this by sending a crafted `CreateRelayRequest` Control message with an arbitrary `RelayFromAddr`. No additional privilege beyond a normal peer handshake is required, and the vulnerable code path (`handleCreateRelayRequest`) is reached on every relay-enabled deployment whenever any peer requests a relay.

### Recommendation
In `handleCreateRelayRequest` (and the analogous response/lookup paths), verify that the claimed `RelayFromAddr`/`from` value equals one of the addresses in the certificate-bound `h.vpnAddrs` of the `HostInfo` that actually delivered the control message, and reject/log the request otherwise instead of trusting the self-declared field.

### Proof of Concept
Conceptual (not executed, since this task is analysis-only):
1. Node `A` establishes a normal, valid Nebula handshake/tunnel with relay node `R` (attacker has a valid certificate, satisfying "authenticated peer" reachability).
2. `A` sends `NebulaControl_CreateRelayRequest` to `R` with `RelayFromAddr` set to victim `V`'s VPN address (not `A`'s own) and `RelayToAddr` set to some target `T`.
3. `R`'s `handleCreateRelayRequest` accepts the request because it only checks `from != myself`, then creates/overwrites relay state keyed on `V`'s address tied to `A`'s tunnel index, per `relay_manager.go:481-487` / `541-552`.
4. If `V` later attempts to legitimately establish a relay through `R`, its request collides with the attacker-seeded state (`QueryRelayForByIp(from)` returns the attacker's poisoned entry), corrupting `V`'s relay session or letting `A` masquerade in relay bookkeeping as `V`. [7](#0-6)
