### Title
`AttachmentsDownloader` stores peer-supplied attachment content without checking `AtlasConfig.attachments_max_size` - (File: `stackslib/src/net/atlas/download.rs`)

### Summary
When a node downloads attachment content from a remote peer via `GET /v2/attachments/<hash>`, the decoded content is inserted into the `AtlasDB` `attachments` BLOB table without ever comparing `attachment.content.len()` against `AtlasConfig.attachments_max_size`. The only place that enforces this bound, `AtlasDB::should_keep_attachment`, is used exclusively for the locally-submitted (`POST /v2/attachments/new`) path, not the peer-download path.

### Finding Description
The equality the operator expects is: stored attachment content size ≤ `attachments_max_size` for every row in the `attachments` table. `AtlasDB::should_keep_attachment` enforces exactly this check by comparing `attachment.content.len() as u32 > self.atlas_config.attachments_max_size` [1](#0-0) , but it is only invoked from `posttransaction.rs`, i.e., the locally-authored attachment path, per the single call-site match found.

The remote-peer download path never calls this check. `AttachmentsBatchStateContext::extend_with_attachments` decodes each successful `GET /v2/attachments/<hash>` HTTP response and unconditionally inserts the decoded `Attachment` into a `HashSet<Attachment>` with no size validation: [2](#0-1) 

`AttachmentsDownloader::run` then drains that set and calls `network.atlasdb.insert_instantiated_attachment(&attachment)` directly, with no size gate before the DB write: [3](#0-2) 

`AtlasDB::insert_instantiated_attachment` performs an unconditioned `INSERT OR REPLACE INTO attachments (hash, content, ...)` with the raw content BLOB, with no length check anywhere in this function: [4](#0-3) 

The same missing check exists in `AttachmentsDownloader::check_attachment_instances`'s "inboxed" branch, which also calls `atlas_db.insert_instantiated_attachment(&attachment)` before invoking `do_if_found`, again without a size comparison: [5](#0-4) 

`RPCGetAttachmentRequestHandler`'s response decoder (`decode_atlas_get_attachment`) simply hex-decodes whatever the peer's JSON response contains into `Attachment.content` with no size cap: [6](#0-5)  and [7](#0-6) 

Because the content hash used to key storage is `Hash160::from_data(&content)` computed from the attacker's own returned bytes (`Attachment::hash`), the attacker fully controls both the stored content and its size; there is no upstream re-check that ties it back to `attachments_max_size` before the write occurs. [8](#0-7) 

### Impact Explanation
A remote peer that a node syncs Atlas attachments with (an outbound sync/data-URL peer, reachable without any node secret or privileged role) can respond to a `GET /v2/attachments/<hash>` request with a body far larger than the operator-configured `attachments_max_size` (minimum floor of 1 MiB, per `ATTACHMENTS_MAX_SIZE_MIN` [9](#0-8) ). That oversized blob gets written unconditionally into the node's SQLite `attachments` table via `insert_instantiated_attachment`. This is repeatable for every distinct attachment instance (content hash) the node has queued for download, allowing an attacker-controlled or malicious peer to inflate the target's Atlas DB storage well beyond the configured bound, one attachment fetch at a time. This matches the "bounded compute DoS on a read endpoint" / storage-exhaustion category — the write path itself has no enforced bound despite the config explicitly documenting one.

### Likelihood Explanation
Preconditions: the target node must have at least one queued/uninstantiated `AttachmentInstance` (created from an on-chain gossiped commitment) whose content is fetched from an outbound peer that is (or can be made to be) the attacker's node, or the attacker's peer must be selected among the reliability-tracked sync peers for a batch. No secrets, RPC auth, or privileged roles are required — the attacker only needs to run a normal P2P peer that the target syncs attachments from and respond to a routine outbound `GET /v2/attachments/<hash>` request with oversized content. This is a low-cost, remotely reachable, and repeatable action.

### Recommendation
Add a size check in the download path before calling `insert_instantiated_attachment`: reject (or discard, marking the instance as unavailable) any downloaded `Attachment` whose `content.len() as u32 > atlas_db.atlas_config.attachments_max_size`, mirroring the existing `should_keep_attachment` logic. Apply this check both in `AttachmentsBatchStateContext::extend_with_attachments` (or immediately before the `insert_instantiated_attachment` call in `AttachmentsDownloader::run`) and in the "inboxed" branch of `check_attachment_instances`.

### Proof of Concept
Rust test plan (`stackslib/src/net/atlas/tests.rs` or a new download test):
1. Configure `AtlasConfig { attachments_max_size: N, .. }` with a small `N` (e.g., 16 bytes) for a fast test.
2. Construct `let oversized = Attachment { content: vec![0u8; (N + 1) as usize] };` and compute `let hash = oversized.hash();`.
3. Build an `AttachmentInstance` with `content_hash = hash` and drive it through `AttachmentsDownloader::check_attachment_instances` using the "inboxed" branch (i.e., first call `atlas_db.insert_uninstantiated_attachment(&oversized)` to simulate the "already inboxed" case reached after a peer download), then invoke `check_queued_attachment_instances`.
4. Assert that after the call, `atlas_db.find_attachment(&hash)` returns `Ok(None)` (i.e., the oversized attachment was rejected) — currently, the assertion `atlas_db.find_attachment(&hash).unwrap().is_some()` succeeds, proving the oversized content was inserted at `stackslib/src/net/atlas/download.rs:259` via `insert_instantiated_attachment` at `stackslib/src/net/atlas/db.rs:576-592`, despite exceeding `attachments_max_size`.

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    }
