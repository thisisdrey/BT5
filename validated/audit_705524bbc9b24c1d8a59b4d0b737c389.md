`accrue` in each vault contract is `define-public` with no `check-caller-auth` gate, so any unprivileged principal can invoke it directly (e.g. `contract-call? .v0-vault-stx accrue`) at will, any number of times per block-time change. This makes the treasury-fee computation inside it a reachable analog to the OCC_Modular APR-combine rounding bug: a repeated weighted-ratio division that rounds down and can be intentionally driven to zero by a user's choice of call cadence, permanently destroying protocol (DAO treasury) yield rather than just shifting it by dust once.

### Title
Reserve-fee (`treasury-lp`) computation in `accrue` rounds down and can be zeroed by user-triggered frequent small accruals - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and the equivalent `v0-vault-*.clar` vaults)

### Summary
Each vault's public, unauthenticated `accrue` function computes the DAO treasury's share of newly accrued interest through two chained floor-divisions. Because the underlying `debt-delta` (interest accrued since `last-update`) grows with elapsed time, a user who calls `accrue` very frequently (small `time-delta` per call) can keep `debt-delta`/`reserve-inc` below the rounding threshold on every single call, so `reserve-inc` and hence `treasury-lp` round down to zero repeatedly, instead of eventually rounding to a nonzero value if interest were left to compound over a longer interval and accrued in one shot.

### Finding Description
`accrue` is `define-public` with no caller-authorization check (unlike `system-borrow`/`system-repay`, which call `check-caller-auth`), so it is reachable directly by any ordinary principal: [1](#0-0) 

Inside `accrue`, the reserve fee owed to the DAO treasury is derived as:
```
old-debt   = mul-div-down(scaled-principal, idx,  INDEX-PRECISION)
new-debt   = mul-div-down(scaled-principal, next, INDEX-PRECISION)
debt-delta = new-debt - old-debt
reserve-inc = mul-div-down(debt-delta, fee-reserve, BPS)
treasury-lp = mul-div-down(reserve-inc, total-supply, total-assets-preview - reserve-inc)
``` [2](#0-1) 

`mul-div-down` truncates (floors) on every call: [3](#0-2) 

The borrow index itself accrues using `round-up=true` (protecting borrower-debt precision in favor of the protocol), while the reserve-fee mint uses `mul-div-down` at every step, i.e. the fee computation is biased against the protocol on every accrual. Because `accrue` recomputes `next-index` from `time-delta = stacks-block-time - last-update` each time it's called, an attacker who calls `accrue()` on every possible block/timestamp change (instead of letting interest accumulate over a longer interval before the next `accrue`) minimizes `debt-delta` per call. If each call's `debt-delta * fee-reserve / BPS` floors to `0`, no `treasury-lp` is ever minted for that slice of interest even though borrowers are still being charged interest (the borrow `index` still advances, since it uses round-up). This is the same rounding-direction/rounding-defeat root cause as the Sherlock M-12 finding: a shared/weighted computation that floors, made worse (driven to zero) by a party who controls the cadence/inputs feeding it, at the expense of the protocol.

This differs from the Sherlock report's specific mechanism (loan-combine weighted APR) but is the same bug class explicitly permitted as an analog: a rounding-down division in interest accrual / treasury LP minting (an in-scope area) that an unprivileged principal can trigger and steer, at protocol expense.

### Impact Explanation
Every time `reserve-inc`/`treasury-lp` rounds to zero instead of its true fractional value, the DAO treasury permanently loses that slice of yield it was entitled to under the reserve-fee parameter — this is a "theft/permanent loss of unclaimed yield" for the protocol treasury, matching the in-scope High impact class (permanent freezing/loss of unclaimed yield). Depositors' `total-assets` accounting still includes the full undiminished interest (since `total-assets` grows through `debt`/`total-borrowed` deltas independent of `treasury-lp`), so the loss is borne specifically by the DAO treasury's expected protocol-fee revenue, accumulating over many small calls.

### Likelihood Explanation
`accrue` requires no permission and no fee to call, is idempotent/harmless to the caller (it simply advances state), and is naturally called as a side effect of borrow/repay, but nothing prevents a user (or bot) from calling it directly and repeatedly with minimal time gaps. Because Stacks block times are coarse but the reserve-fee arithmetic is `BPS`-scaled (1/10000) on top of an already-small `debt-delta` for short intervals, frequent calling is a low-cost, high-likelihood strategy, especially on low-utilization/low-fee-reserve vaults.

### Recommendation
- Accrue and accumulate `reserve-inc` in a persisted "dust" accumulator (carry remainder into the next accrual) rather than resetting the numerator to zero every rounding.
- Alternatively, round the reserve-fee computation up (`mul-div-up`) or track fees in higher-precision fixed-point storage and only mint whole `zft` units when the cumulative remainder exceeds 1 unit, ensuring frequent small calls cannot cause the treasury to permanently lose the fractional fee.
- Consider restricting or rate-limiting unauthenticated `accrue` calls, or making the treasury-fee calculation invariant to call frequency (i.e., mathematically equivalent whether accrued in one call or N calls).

### Proof of Concept
Not independently executed (no terminal/test harness available in this session) — the vulnerability is derived purely from static analysis of the `accrue` function shown above. Conceptually:
1. Attacker computes/observes `fee-reserve` and `BPS=10000` for a given vault.
2. Attacker calls `accrue()` directly (unauthenticated) once per available `stacks-block-time` tick so that each call's `time-delta` is minimal, keeping each `debt-delta` (and hence `reserve-inc = debt-delta * fee-reserve / BPS`) below `1` after flooring.
3. Over many such calls, the aggregate `debt-delta` charged to borrowers (via the round-up borrow index) is unchanged, but the cumulative `treasury-lp` minted to `.dao-treasury` is `0`, whereas a single `accrue()` call spanning the same aggregate time-delta would have minted a non-zero `treasury-lp`.
4. Net effect: DAO treasury permanently loses the fee revenue it would otherwise have earned, extractable/triggerable at will by any unprivileged caller repeatedly invoking `accrue`.
