### Title
Unbounded memory growth in `CheckAttrCmd.Check` via attacker-controlled `.gitattributes` values parsed with unbounded `bufio.Reader.ReadBytes` - (File: internal/git/gitattributes/check_attr.go)

### Summary
`CheckAttrCmd.Check` reads each NUL-delimited field of `git-check-attr -z` output using `c.stdout.ReadBytes('\000')`, which has no size cap and will keep growing its internal buffer until a NUL byte is found. Because attribute values are taken verbatim from a `.gitattributes` file that an unprivileged user can push into their own repository, a single crafted long value forces Gitaly to allocate memory proportional to that value regardless of the RPC request size.

### Finding Description
`git check-attr --stdin -z <names...>` streams `<path> NUL <attribute> NUL <value> NUL` triples on stdout. `CheckAttrCmd.Check` loops calling `c.stdout.ReadBytes('\000')` three times per path to assemble each triple: [1](#0-0) . `bufio.Reader.ReadBytes` has no maximum length; if the delimiter is not found it keeps appending to an internal slice, doubling capacity as needed, until the NUL byte finally appears in the underlying stream (or process EOF/error).

The `<value>` field for a custom attribute is exactly whatever string an author assigns in `.gitattributes`, e.g. `*.md foo=<very long string>` – this is git's normal handling of custom attribute assignment, not filtered or truncated by Gitaly. Because a `.gitattributes` file is ordinary repository content, an unprivileged user who can push to their own repository fully controls the length and content of these values.

`GetFileAttributes` calls `gitattributes.CheckAttr` with attacker-supplied `Attributes` names and then calls `checkAttrCmd.Check(path)` once per entry in the attacker-supplied `Paths` list: [2](#0-1) . Request validation only checks that `Paths`/`Attributes`/`Revision` are non-empty; it does not bound the number of paths, number of attributes, or the size of attribute values that will be echoed back from `.gitattributes`: [3](#0-2) . Similarly, linguist's attribute-based language detection uses the same check-attr codepath and is driven by attacker-controlled paths in the pushed tree: [4](#0-3) [5](#0-4) .

None of the existing safeguards (`storage.ValidateRelativePath`, `git.ValidateRevision`, request field non-emptiness checks) bound the size of `.gitattributes` attribute values or the number of `ReadBytes` calls performed, so a single, moderately sized push containing one huge attribute value assignment is sufficient to make a single `Check()` call allocate an outsized buffer.

### Impact Explanation
Each call to `Check()` can allocate memory proportional to the length of a single attribker-crafted attribute value in `.gitattributes` (e.g., tens/hundreds of MB per value if the pushed blob permits), independent of the size of the incoming RPC request. Combined with a `Paths` list of even modest size, this can be repeated per path, multiplying memory pressure on the Gitaly process and potentially triggering OOM or severe GC pressure, degrading or crashing the service for other tenants on the same node — a resource-exhaustion / DoS impact against an RPC handler.

### Likelihood Explanation
The attacker only needs standard push access to a repository they own (default GitLab capability) to add a `.gitattributes` file with a long custom attribute value, then invoke `GetFileAttributes` (or trigger linguist stats, e.g. via a commit/push that runs language detection) against that revision. No special role, config, or secret is required, and the request itself does not need to be large — the bulk of the payload lives in already-pushed repository content. This makes the issue realistically reachable and repeatable.

### Recommendation
Use a bounded reader, e.g. wrap the read with `io.LimitReader` or use `bufio.Reader.ReadBytes` in a loop with an explicit maximum accumulated size (returning an error such as `structerr.NewResourceExhausted` once a configurable ceiling, e.g. a few KB, is exceeded), for each of the path/attribute/value fields parsed from `git-check-attr -z` output in `CheckAttrCmd.Check`.

### Proof of Concept
```go
func TestCheckAttrCmd_Check_HugeAttributeValue(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg := testcfg.Build(t)

    repoProto, repoPath := gittest.CreateRepository(t, ctx, cfg, gittest.CreateRepositoryConfig{
        SkipCreationViaService: true,
    })
    repo := localrepo.NewTestRepo(t, cfg, repoProto)

    hugeValue := strings.Repeat("A", 200*1024*1024) // 200MB value, no NUL byte
    attrContent := "*.md foo=" + hugeValue

    treeOID := gittest.WriteTree(t, cfg, repoPath, []gittest.TreeEntry{
        {Path: ".gitattributes", Mode: "100644", Content: attrContent},
        {Path: "README.md", Mode: "100644", Content: "hi"},
    })
    commitID := gittest.WriteCommit(t, cfg, repoPath, gittest.WithTree(treeOID))

    checkCmd, finish, err := gitattributes.CheckAttr(ctx, repo, commitID.Revision(), []string{"foo"})
    require.NoError(t, err)
    defer finish()

    // Measure memory before/after; Check() will allocate a >=200MB buffer
    // via bufio.Reader.ReadBytes('\000') to read the single unterminated value field.
    attrs, err := checkCmd.Check("README.md")
    require.NoError(t, err)
    require.Len(t, attrs, 1)
}
```
Repeating this via the `GetFileAttributesRequest{Attributes: ["foo"], Paths: ["README.md", ...]}` RPC against a repository containing the crafted `.gitattributes` reproduces the same unbounded allocation per path at the RPC level.

func (s *server) GetFileAttributes(ctx context.Context, in *gitalypb.GetFileAttributesRequest) (*gitalypb.GetFileAttributesResponse, error) {
	if err := validateGetFileAttributesRequest(ctx, s.locator, in); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(in.GetRepository())

	checkAttrCmd, finishAttr, err := gitattributes.CheckAttr(ctx, repo, git.Revision(in.GetRevision()), in.GetAttributes())
	if err != nil {
		return nil, structerr.New("check attr: %w", err)
	}

	defer finishAttr()

	var attrValues []*gitalypb.GetFileAttributesResponse_AttributeInfo

	for _, path := range in.GetPaths() {
		attrs, err := checkAttrCmd.Check(path)
		if err != nil {
			return nil, structerr.New("check attr: %w", err)
		}

		for _, attr := range attrs {
			attrValues = append(attrValues, &gitalypb.GetFileAttributesResponse_AttributeInfo{Path: path, Attribute: attr.Name, Value: attr.State})
		}
	}

	return &gitalypb.GetFileAttributesResponse{AttributeInfos: attrValues}, nil

func validateGetFileAttributesRequest(ctx context.Context, locator storage.Locator, in *gitalypb.GetFileAttributesRequest) error {
