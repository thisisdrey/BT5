### Title
Newly-initialized reward token grants `balance × INITIAL_INDEX` rewards to existing holders (`accountIndexOf == 0` bypasses the `INITIAL_INDEX` fallback) - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
Metronome's `RewardsDistributor` uses the same global "reward per share" index pattern as the audited `Vault.vy`: a monotonically increasing `tokenStates[token].index` multiplied by the user's balance, minus a per-account snapshot (`accountIndexOf`). The intended fix for the retroactive-accrual bug is the fallback in `_calculateTokenDelta`:

```solidity
// contracts/RewardsDistributor.sol:225-230
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The fallback only fires when `_tokenIndex > INITIAL_INDEX` is *strict*. When a token's reward speed is first enabled, `_updateTokenSpeed` initializes `tokenStates[token_] = {index: INITIAL_INDEX (1e18), timestamp: block.timestamp}` (line 298). In the same block/timestamp, `_calculateTokenIndex` returns `(0,0)` because `_deltaTimestamps == 0`, so the index stays exactly `1e18`. For any account that already holds the DepositToken/DebtToken but never had its index checkpointed (which is guaranteed — all `updateBefore*` hooks skip the body while `tokenStates[token_].index == 0`, line 176/187), `accountIndexOf` is `0`, the fallback does not apply (`1e18 > 1e18` is false), and the delta becomes `balanceOf(account) * 1e18` — i.e., 1 reward token per share, credited instantly for rewards the account never accrued.

### Finding Description
`claimRewards` and `updateBeforeMintOrBurn` are fully permissionless. Attack path:

1. Attacker deposits collateral before rewards are ever enabled for the DepositToken, acquiring a large `balanceOf` with `accountIndexOf == 0` (any holder of the token qualifies; no timing needed for this step).
2. Governor calls `updateTokenSpeed(depositToken, speed)`. `tokenStates` is set to `{index: 1e18, timestamp: block.timestamp}`.
3. In the **same block**, attacker calls `claimRewards([attacker], [depositToken])`. `_updateTokenIndex` no-ops (same timestamp, `_deltaTimestamps == 0`), `_updateTokensAccruedOf` computes `_deltaIndex = 1e18 - 0 = 1e18` and `_tokensDelta = attackerBalance.wadMul(1e18) = attackerBalance`.
4. `_transferRewardIfEnoughTokens` pays out up to the distributor's whole reward-token balance.

The governor's `updateTokenSpeed` transaction is visible in the mempool, so back-running it in the same block (bundle/flashbots, or simply same-block inclusion) is straightforward on mainnet/optimism deployments.

### Impact Explanation
Direct theft of unclaimed yield: the attacker drains reward tokens (e.g., the deployed MET/VSP distributor reserve) equal to `min(msdToken balance, distributor reward balance)`, stealing other users' legitimately accrued rewards. A whale depositor can drain the entire distributor reserve in one transaction.

### Likelihood Explanation
Requires: (a) a DepositToken or DebtToken with existing holders but rewards speed not yet set (the normal state before a new reward program launches — tokens exist long before `updateTokenSpeed` is called), and (b) same-block execution after the governor's `updateTokenSpeed` tx, which is a routine mempool back-run. No privileged role needed by the attacker. The window is narrow per token but repeats for every newly reward-enabled token, and the distribution set-up is done by governance exactly once per token.

### Recommendation
In `_calculateTokenDelta`, treat `accountIndexOf == 0` as `INITIAL_INDEX` whenever the token index is initialized, i.e. change the condition to `_tokenIndex >= INITIAL_INDEX` (or equivalently `if (_accountIndex == 0) _accountIndex = INITIAL_INDEX;`), and/or have `_updateTokenSpeed` iterate impossible-but-safe checkpointing. The clean fix is:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex >= INITIAL_INDEX ? _tokenIndex : INITIAL_INDEX;
}
```

so an uninitialized account snapshot can never produce a nonzero `_deltaIndex` at index initialization time.

### Proof of Concept
Hardhat-style fork/unit PoC against `contracts/RewardsDistributor.sol`:

```solidity
// Setup: pool with msdWETH DepositToken; RewardsDistributor funded with rewardToken
// 1. Alice (attacker) deposits 1000 WETH -> mints 1000 msdWETH
depositToken.deposit(1000 ether, attacker);
// tokenStates[msdWETH].index == 0 -> updateBeforeMintOrBurn is a no-op,
// so accountIndexOf[msdWETH][attacker] remains 0

// 2. Governor enables rewards for msdWETH
vm.prank(governor);
rewardsDistributor.updateTokenSpeed(msdWETH, 1 ether); // index = 1e18, ts = now

// 3. Same block (same timestamp): attacker claims
rewardsDistributor.claimRewards(single(attacker), single(msdWETH));

// _deltaTimestamps == 0 -> index stays 1e18
// accountIndex == 0, tokenIndex == INITIAL_INDEX -> fallback skipped
// _tokensDelta = 1000e18 * wadMul(1e18) = 1000 reward tokens
assertEq(rewardToken.balanceOf(attacker), 1000 ether); // stole reserve
```

Caveat I could not fully verify: if an integrator always calls `updateTokenSpeed` at token-creation time before any user holds a balance, the window never materializes; however, `claimRewards`/`updateBeforeMintOrBurn` being permissionless and `updateTokenSpeed` being callable for already-live tokens (debt tokens for a new incentive, deposit tokens added to an existing distributor via `pool.getRewardsDistributors()`) means existing holders with `accountIndexOf == 0` are the expected case, not an edge case.
