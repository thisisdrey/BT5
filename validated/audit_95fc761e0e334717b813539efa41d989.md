### Title
Zero `totalEnergyWeight`/`totalNetWeight` division relies on a no-op Java `assert` instead of a runtime check, allowing corrupted resource-limit computation - ([File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit` and the equivalent VM-side `RepositoryImpl.calculateGlobalEnergyLimit` compute an account's energy limit by dividing by `totalEnergyWeight`. The only guard against a zero value is either config-gated (`allowNewReward()`) or a bare Java `assert`, which is compiled out and silently skipped unless the JVM is started with `-ea`. This mirrors the Lido report's root cause: a critical denominator used in per-user reward/limit distribution is not defensively checked for zero, only assumed non-zero.

### Finding Description
In `EnergyProcessor.calculateGlobalEnergyLimit`: [1](#0-0) 
```
long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
  return 0;
} else {
  assert totalEnergyWeight > 0;
}
...
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```
The zero-guard only fires when `allowNewReward()` is enabled. When that flag is off (e.g. on networks/timelines where this proposal hasn't been activated, or on a private/side chain deployed from this codebase without activating it), a zero `totalEnergyWeight` falls into the `else` branch, which is a Java `assert` statement. Java `assert` is disabled by default (JVM must be run with `-ea` to enable it), so in a standard production deployment this line is a no-op and execution proceeds into a division of a `double` by zero, yielding `Infinity`. The subsequent cast `(long) (energyWeight * Infinity)` produces `Long.MAX_VALUE`, effectively removing any energy limit for that account.

The identical pattern (with no config gate at all) exists in the VM/TVM-facing `RepositoryImpl.calculateGlobalEnergyLimit`, used from `Program`/`ContractState`/`VMActuator` during contract execution: [2](#0-1) 
```
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
assert totalEnergyWeight > 0;
...
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```
Here there is no config check whatsoever — only the same no-op `assert`.

Note that the "hardened" `V2` variants (`calculateGlobalEnergyLimitV2`) do have a proper explicit `if (totalEnergyWeight == 0) return 0;` check: [3](#0-2) 
confirming the developers are aware zero is a real, reachable state that must be checked — but the older/V1 code paths (still reachable when `supportUnfreezeDelay()` is false) were left relying on the assertion instead of an equivalent guard.

### Impact Explanation
If `totalEnergyWeight` reaches zero while the V1 path is active (`allowNewReward()` off and/or `supportUnfreezeDelay()` off), any account's computed energy limit becomes effectively unbounded (`Long.MAX_VALUE`), letting `useEnergy()` — invoked on every TVM contract call via `EnergyProcessor.useEnergy` — treat the account as having unlimited free energy. This corrupts the network's resource-accounting invariant (frozen TRX ↔ energy backing) analogous to an "unbacked balance," and can be used to execute unlimited free contract calls, degrading node performance/availability (energy metering DoS) without paying for it. It also risks producing corrupted/undefined behavior (NaN/Infinity propagation) in downstream long arithmetic.

### Likelihood Explanation
Reachability depends on `totalEnergyWeight` (sum of frozen-for-energy TRX network-wide) actually being zero, which requires all frozen-for-energy stake to be unfrozen simultaneously — plausible on a private/consortium/test network built from this code, or transiently during specific chain-parameter states, but hard to engineer on TRON mainnet where `allowNewReward` has long been activated (rendering `EnergyProcessor`'s guard effective there). The `RepositoryImpl` copy has no such gate at all, so it is strictly weaker and reachable whenever the V1 (non-`supportUnfreezeDelay`) calculation path is taken. Given the requirement is a chain-wide state (not solely attacker-controlled in a single transaction) and depends on deployment/activation status of `allowNewReward`/`supportUnfreezeDelay`, likelihood is assessed as Medium rather than High.

### Recommendation
Replace the bare `assert totalEnergyWeight > 0;` statements in both `EnergyProcessor.calculateGlobalEnergyLimit` (chainbase) and `RepositoryImpl.calculateGlobalEnergyLimit` (actuator) with an explicit runtime check (`if (totalEnergyWeight <= 0) { return 0; }`), matching the pattern already used in the `V2` variants and in `BandwidthProcessor.calculateGlobalNetLimit`. This removes dependence on JVM assertion flags for a security-relevant invariant.

### Proof of Concept
Not independently reproducible from the index alone: it requires driving `dynamicPropertiesStore.getTotalEnergyWeight()` to `0` while `allowNewReward()` is disabled (for the `EnergyProcessor` path) or unconditionally for `RepositoryImpl` on a network taking the V1 branch, then invoking `useEnergy`/any `TriggerSmartContract` transaction. The existing test `framework/src/test/java/org/tron/core/db/CalculateGlobalLimitHardenTest.java` demonstrates the parity/precision testing around these methods but does not cover the zero-weight/assert-disabled scenario. Full exploitation confirmation would need running the node without `-ea` and forcing `totalEnergyWeight` to zero via the relevant dynamic-property setters, which requires a live/test environment beyond static code inspection.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
