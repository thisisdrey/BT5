### Title
`CreateRepositoryFromSnapshot` performs an unbounded external HTTP fetch/extraction with no size or time cap, allowing resource-exhaustion DoS and SSRF to arbitrary internal endpoints - ([File: internal/gitaly/service/repository/create_repository_from_snapshot.go])

### Summary
The reported issue describes an "unbounded external call" pattern: control is handed to an untrusted party with no cap on the resources that call may consume, letting the caller/attacker force the victim to pay an unpredictable and potentially unbounded cost. The Gitaly analog is `CreateRepositoryFromSnapshot`'s `untar` helper, which issues an HTTP GET to a caller-supplied `HttpUrl`/`ResolvedAddress` and streams the response body directly into `tar -x` with no response-size limit, no read-timeout enforcement beyond TLS/`ResponseHeaderTimeout` (which does not bound body transfer), and no dedicated concurrency/queueing limiter (unlike `GetArchive` or pack-objects, which are covered by caches/limiters described in `doc/backpressure.md`).

### Finding Description
`untar` builds an HTTP request from `in.GetHttpUrl()`, optionally binds it to `in.GetResolvedAddress()`, and streams `rsp.Body` straight into a `tar -C path -xvf -` subprocess: [1](#0-0) 

Key resource-control gaps mirroring the "no gas limit" bug class:
- `httpTransport` sets `DialContext.Timeout`, `TLSHandshakeTimeout`, and `ResponseHeaderTimeout`, but none of these bound how long the response *body* may take to arrive or how large it may be: [2](#0-1) 
- The tar extraction reads `rsp.Body` with no `io.LimitReader` wrapper and no explicit byte cap, so an attacker-controlled server can return an arbitrarily large or drip-fed (slowloris-style) body, keeping the outbound connection and the `tar` subprocess alive indefinitely, bound only by whatever gRPC deadline the *calling* client chooses to set (which, since the caller is often the same untrusted actor supplying the malicious URL, can simply be omitted or set very high).
- Unlike other expensive RPCs in this service (`GetArchive`, `PostUploadPackWithSidechannel`, `PackObjectsHookWithSidechannel`), there is no per-RPC/per-repo concurrency limiter configured by default for `CreateRepositoryFromSnapshot`, and none of the size-based protections documented in `doc/backpressure.md` apply to it: [3](#0-2) 
- The code's own comment acknowledges the endpoint is dangerous if reachable by anything other than a fully trusted source: "the received archive is trusted *a lot*... it should undergo a lot of hardening": [4](#0-3) 
- Because `HttpUrl` is fully attacker-controlled and only `ResolvedAddress` (optional) pins the network destination, an authenticated caller can direct the Gitaly node to issue outbound HTTP requests to arbitrary hosts/ports (including internal-only services), i.e., classic SSRF, while simultaneously forcing unbounded CPU/disk/memory consumption during extraction — the same "uncapped external call cost" failure mode as the reported gas-limit issue, just manifesting as wall-clock/CPU/storage instead of EVM gas.

### Impact Explanation
Any client holding a valid Gitaly auth token (the same token used for ordinary RPCs — there is no additional privilege tier gating this RPC) can:
1. Force the Gitaly node to make outbound HTTP requests to internal-only endpoints (SSRF), potentially reaching metadata services or other internal infrastructure reachable from the Gitaly host.
2. Supply a slow or effectively infinite response body, tying up a `tar` subprocess, an open HTTP connection, and repository-creation machinery indefinitely, since there is no size cap and no dedicated concurrency/queue limiter for this RPC — leading to CPU, disk, and file-descriptor exhaustion (DoS of the RPC handler and potentially the whole node, mirroring how the reported gas-limit bug lets a callee force unpredictable, uncapped resource cost onto the caller).

### Likelihood Explanation
The RPC is reachable with a standard Gitaly auth token — no special/privileged path is required, and the vulnerable `HttpUrl`/`HttpAuth`/`ResolvedAddress` fields are directly attacker-controlled request parameters. Exploitation only requires standing up an HTTP server that returns a large or slow-drip body, which is trivial for any attacker capable of issuing gRPC calls to Gitaly.

### Recommendation
- Wrap `rsp.Body` in an `io.LimitReader` bounded to a sane maximum snapshot size before feeding it into `tar`.
- Enforce an explicit read/idle timeout on the body transfer (e.g., via a context deadline or a stall-detecting reader), independent of the RPC's own deadline.
- Add this RPC to the default `[[concurrency]]` limiter configuration (per-repo/per-RPC) as recommended in `doc/backpressure.md`, so a flood of such requests cannot exhaust node resources.
- Restrict destination hosts/ports for `HttpUrl` (allow-list or require `ResolvedAddress` combined with private-IP blocking) to close the SSRF vector, consistent with the hardening the code comment already flags as outstanding.

### Proof of Concept
1. Stand up an attacker-controlled HTTP server that responds to any GET request by streaming bytes indefinitely (or a multi-terabyte tar stream) without ever closing the connection.
2. As an authenticated Gitaly client, call `CreateRepositoryFromSnapshot` with `HttpUrl` pointing at that server (optionally omitting `ResolvedAddress` to also probe SSRF against internal addresses).
3. Observe the Gitaly node's `tar` subprocess and outbound connection remain active far beyond any expected snapshot-fetch duration, consuming CPU/disk/FDs with no built-in cap, while concurrent requests against the same or other repositories degrade service — reproducing the "uncapped external call cost" DoS described in the analog report.

func (s *server) untar(ctx context.Context, path string, in *gitalypb.CreateRepositoryFromSnapshotRequest) error {
	req, err := http.NewRequestWithContext(ctx, "GET", in.GetHttpUrl(), nil)
	if err != nil {
		return structerr.NewInvalidArgument("Bad HTTP URL: %w", err)
	}

	client := httpClient
	if resolvedAddress := in.GetResolvedAddress(); resolvedAddress != "" {
		client, err = newResolvedHTTPClient(in.GetHttpUrl(), resolvedAddress)
		if err != nil {
			return structerr.NewInvalidArgument("creating resolved HTTP client: %w", err)
		}
	}

	if in.GetHttpAuth() != "" {
		req.Header.Set("Authorization", in.GetHttpAuth())
	}

	rsp, err := client.Do(req)
	if err != nil {
		return structerr.NewInternal("HTTP request failed: %w", err)
	}
	defer rsp.Body.Close()

	if rsp.StatusCode < http.StatusOK || rsp.StatusCode >= http.StatusMultipleChoices {
		return structerr.NewInternal("HTTP server: %s", rsp.Status)
	}

	cmd, err := command.New(ctx, s.logger, []string{"tar", "-C", path, "-xvf", "-"}, command.WithStdin(rsp.Body))
	if err != nil {
		return err
	}

	return cmd.Wait()
}
