### Title
Unbounded per-reference subprocess spawning in non-atomic proc-receive push allows unmetered resource-exhaustion DoS - (File: internal/gitaly/hook/receivepack/receive_pack.go)

### Summary
`gitaly`'s proc-receive push path processes reference updates supplied by the pushing client without any upper bound on their count. When the client requests non-atomic semantics, Gitaly iterates once per reference update and, for **each individual update**, spawns a full `git update-ref` process plus a separate hook-execution round trip (which itself spawns a `gitaly-hooks` subprocess and walks/executes any custom hook files). None of this work is capped, rate-limited, or charged against any per-request budget, so the cost of handling a single `ReceivePack`/`SSHReceivePack` RPC scales linearly with a value the pushing client fully controls — directly analogous to the reported "linear iteration in unmetered execution path" bug class.

### Finding Description
The proc-receive hook handler parses reference updates directly from the client-driven pkt-line stream with no length limit: [1](#0-0) 

These updates are then relayed to `procReceiveHook`, which branches on whether the handler is atomic. In the **non-atomic** branch, Gitaly loops over every single reference update and, for each one, calls `receivePackReferenceUpdates` with a single-element slice: [2](#0-1) 

`receivePackReferenceUpdates` itself spawns a brand-new `git update-ref` process (`updateref.New`/`Start`/`Commit`) and executes the update hook for the reference before committing: [3](#0-2) 

The update hook invocation is not a cheap in-process check — `hookManager.UpdateHook` round-trips through the `gitaly-hooks` binary and the `HookService`, and eventually reaches `newCustomHooksExecutor`, which stats the filesystem for per-project and global custom hook files and executes each one found as a child process, reading all of stdin into memory per invocation: [4](#0-3) 

Because the atomic/non-atomic flag is a proc-receive protocol capability the *pushing client itself* selects, and because the number of reference-update lines a client sends in a single push is unbounded (bounded only by pkt-line/packfile limits, not by any explicit reference-count check), an attacker can push a single request containing a very large number of reference updates (e.g. tens of thousands of lightweight branch creates/deletes pointing at objects already in the repo, requiring no meaningful packfile) and force Gitaly to synchronously spawn tens of thousands of `git update-ref` processes and hook-execution round trips within the handling of one RPC call.

This mirrors the reported bug class precisely: an actor-controlled collection (delegations / reference updates) is iterated without any linear-scaling cost, inside a mechanism (governance hook / receive-pack hook) whose execution cost was assumed to be bounded but in practice grows with attacker-supplied cardinality.

### Impact Explanation
A single crafted push can consume disproportionate CPU, process-table, and file-descriptor resources on the primary Gitaly node handling the push, for the full duration of the RPC. Because receive-pack style hooks run only on the primary node and the RPC holds repository-level locks/transaction state for the whole loop, this can:
- Starve the concurrency-limiting queue (`max_per_repo`/`max_queue_size`) for that repository, and consume worker/goroutine and OS-process capacity that other tenants' RPCs on the same Gitaly node depend on.
- Cause secondary nodes in a Praefect-managed cluster to hang waiting for the primary's vote, per the documented reference-transaction hang scenario, amplifying the blast radius from a single repository to a stalled transaction quorum.
- Produce a self-inflicted denial of service, since the actor pushing does not need any special privilege beyond ordinary write access to a repository.

### Likelihood Explanation
Any user with push access to a repository (or via impersonated/forked repository push, mirror push, or import that goes through `git-receive-pack`) can trigger this by using the proc-receive protocol extension with the non-atomic capability and supplying a large number of reference-update lines. No admin/custom-hook installation or privileged access is required — it only depends on ordinary Git client behavior interacting with an unbounded, unmetered server-side loop.

### Recommendation
Add an explicit cap on the number of reference updates processed per push/`ProcReceiveHandler` invocation (reject or reasonably rate-limit oversized command lists), and/or make the cost of the non-atomic per-reference hook loop proportional to configured concurrency/resource budgets rather than purely to client input. Where feasible, batch the update-hook and `git update-ref` invocations for non-atomic mode instead of spawning one process pair per reference, and enforce the cap at the point where `updates` is parsed in `NewProcReceiveHandler`/`procreceive_handler.go` before any iteration begins.

### Proof of Concept
Conceptually (cannot be executed here, but derivable from the code path):
1. Attacker with push access to a repository initiates `git push` using the proc-receive protocol, advertising non-atomic semantics and a very large `receive.procReceiveRefs` set (or crafts the wire protocol input directly at the `ReceivePack`/`SSHReceivePack` RPC boundary, since the pkt-line reference-update list has no server-side count limit — see `internal/gitaly/hook/procreceive_handler.go` lines 80-98).
2. The push contains N (e.g. 50,000) reference-update lines all pointing old→new object IDs that already exist in the repository (no meaningful packfile payload required), keeping bandwidth/pack cost low while N stays high.
3. `procReceiveHook` (non-atomic branch, `internal/gitaly/hook/receivepack/receive_pack.go` lines 112-138) iterates N times, and for each iteration `receivePackReferenceUpdates` spawns a fresh `git update-ref` process and a full update-hook round trip (lines 200-251), which in turn triggers `newCustomHooksExecutor`'s filesystem walk (`internal/gitaly/hook/custom.go` lines 49-97).
4. The RPC handler blocks synchronously until all N iterations complete, tying up the primary Gitaly node's resources proportionally to N, with no server-side limit rejecting the request beforehand.

func receivePackReferenceUpdates(
	ctx context.Context,
	cfg config.Cfg,
	req gitcmd.ReceivePackRequest,
	repo *localrepo.Repo,
	hookManager hook.Manager,
	updates []hook.ReferenceUpdate,
	stdout, stderr io.Writer,
) (returnedErr error) {
	hooksPayload, err := setupHooksPayloadEnv(ctx, cfg, req, repo, gitcmd.UpdateHook)
	if err != nil {
		return fmt.Errorf("creating hooks payload: %w", err)
	}

	updater, err := updateref.New(ctx, repo, updateref.WithNoDeref())
	if err != nil {
		return fmt.Errorf("spawning ref updater: %w", err)
	}
	defer func() {
		if err := updater.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("cancel ref updater: %w", err)
		}
	}()

	if err := updater.Start(); err != nil {
		return fmt.Errorf("start reference transaction: %w", err)
	}

	for _, update := range updates {
		if err := hookManager.UpdateHook(
			ctx,
			req.GetRepository(),
			update.Ref.String(),
			update.OldOID.String(),
			update.NewOID.String(),
			[]string{hooksPayload},
			stdout, stderr,
		); err != nil {
			return fmt.Errorf("running update hook: %w", err)
		}

		if err := updater.Update(update.Ref, update.NewOID, update.OldOID); err != nil {
			return fmt.Errorf("queueing ref to be updated: %w", err)
		}
	}

	if err := updater.Commit(); err != nil {
		return updateError{error: err}
	}

	return nil
}

func (m *GitLabHookManager) newCustomHooksExecutor(ctx context.Context, repo *gitalypb.Repository, hookName string) (customHooksExecutor, error) {
	repoPath, err := m.locator.GetRepoPath(ctx, repo)
	if err != nil {
		return nil, err
	}

	var hookFiles []string
	projectCustomHookFile := filepath.Join(repoPath, "custom_hooks", hookName)
	if isValidHook(projectCustomHookFile) {
		hookFiles = append(hookFiles, projectCustomHookFile)
	}

	projectCustomHookDir := filepath.Join(repoPath, "custom_hooks", fmt.Sprintf("%s.d", hookName))
	files, err := findHooks(projectCustomHookDir)
	if err != nil {
		return nil, err
	}
	hookFiles = append(hookFiles, files...)

	if m.cfg.Hooks.CustomHooksDir != "" {
		globalCustomHooksDir := filepath.Join(m.cfg.Hooks.CustomHooksDir, fmt.Sprintf("%s.d", hookName))
		files, err = findHooks(globalCustomHooksDir)
		if err != nil {
			return nil, err
		}
		hookFiles = append(hookFiles, files...)
	}

	return func(ctx context.Context, args, env []string, stdin io.Reader, stdout, stderr io.Writer) error {
		var stdinBytes []byte
		if stdin != nil {
			stdinBytes, err = io.ReadAll(stdin)
			if err != nil {
				return err
			}
		}

		for _, hookFile := range hookFiles {
			c, err := command.New(ctx, m.logger, append([]string{hookFile}, args...),
				command.WithDir(repoPath),
				command.WithStdin(bytes.NewReader(stdinBytes)),
				command.WithStdout(stdout),
				command.WithStderr(stderr),
				command.WithEnvironment(env),
				command.WithCommandName("gitaly-hooks", hookName),
			)
			if err != nil {
				return err
			}
