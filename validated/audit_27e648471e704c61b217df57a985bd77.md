### Title
Bazel's `git_repository`/`git_worker.bzl` re-enables Git's `file://` submodule transport (`protocol.file.allow=always`), letting an attacker-controlled repository exfiltrate arbitrary local Git object data via `.gitmodules` — (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository` clones an attacker-influenceable remote and, when submodules are requested, unconditionally runs `git submodule update --init` with `-c protocol.file.allow=always`. That flag is exactly the setting Git upstream restricted (CVE-2022-39253, Git 2.38.1) because a repository's own `.gitmodules` file — fully controlled by whoever publishes the repository, i.e. the attacker — can declare a submodule with an absolute `file://` URL pointing at any local path reachable by the build user. Bazel forces this transport back on for every submodule fetch, in every `git_repository`/`new_git_repository` invocation, defeating the very hardening that Git shipped to stop this class of local data exfiltration.

### Finding Description
`update_submodules()` in `tools/build_defs/repo/git_worker.bzl` builds the submodule-update command with a hardcoded `-c protocol.file.allow=always`: [1](#0-0) 

This is reached from `git_repository`'s implementation whenever `init_submodules`/`recursive_init_submodules` is set: [2](#0-1) 

The `.gitmodules` file that drives which submodule URL and transport is used lives inside the fetched repository content itself, as shown by Bazel's own test fixture (`url = ../pluto`, a repo-controlled relative/absolute URL resolved at submodule-update time): [3](#0-2) 

Because Bazel forces `protocol.file.allow=always`, an attacker who controls only the *contents* of the fetched repository (the exact threat model here — a hostile remote/mirror or a compromised branch a victim's `git_repository` points at) can add or modify `.gitmodules` to declare a submodule with an absolute `url = file:///some/local/path`. When the victim's build runs `bazel fetch`/`bazel build` with `init_submodules`/`recursive_init_submodules = True`, Git will happily perform a **local** clone from that path. Git's local-clone fast path does not selectively transfer only the referenced commit's reachable objects — by default it copies (or hardlinks) the *entire* object database of the source path into the destination, then checks out only the requested gitlink commit. Any object ever written into that local repository's object store (other branches, orphaned commits, blobs from rewritten/deleted history) becomes readable inside the fetched external repository directory, from where ordinary `BUILD` rules (`filegroup`, `genrule`, etc., as already exercised by Bazel's own submodule tests) can read it into build outputs.

This is the direct analog of the ALPINE-CVE-2022-20001 bug class: untrusted content (a git-tracked repository, analogous to `fish`'s auto-invoked `git` prompt) is allowed to steer the trusted tool's ambient behavior (here, which network/local transport `git` uses) in a way the tool's own maintainers deliberately locked down by default, and Bazel has re-opened that hole unconditionally.

### Impact Explanation
This breaks the "write/read stays inside the repository / exec root / output base" invariant: attacker-published repository metadata (`.gitmodules`) can cause Git to read from an arbitrary local filesystem path outside the checkout/exec root and copy that content into the fetched external repository, where it becomes visible to and consumable by the victim's build (and can then be embedded into build outputs, logs, or artifacts — an exfiltration primitive). This is especially potent on shared CI runners where sibling repository checkouts (including private/internal repositories with predictable paths) sit alongside the workspace that fetches the malicious dependency.

### Likelihood Explanation
Any consumer of `git_repository`/`new_git_repository` with `init_submodules` or `recursive_init_submodules` enabled (a common, documented option) is affected. No opt-in beyond that flag is required; `protocol.file.allow=always` is applied unconditionally and is not user-configurable via the rule's attributes. The only requirement on the attacker's side is control of the repository content (its remote or a branch the victim's build points at) — matching the declared unprivileged, remote-content-only attacker model. The main constraint is knowledge of a useful local path/commit hash on the victim's machine, which is often predictable (CI workspace layout, well-known sibling checkouts, or the main repo's own `.git`).

### Recommendation
Remove the blanket `-c protocol.file.allow=always` override from `update_submodules()`, or scope it narrowly to the specific known-safe case referenced by bazelbuild/bazel#17040 (e.g., only when the submodule URL is a relative path resolved against the same already-trusted local `remote`), rather than globally re-enabling `file://` transport for arbitrary absolute submodule URLs declared inside untrusted repository content.

### Proof of Concept
Following the pattern of Bazel's own `src/test/shell/bazel/starlark_git_repository_test.sh` (`test_git_repository_submodules_with_recursive_init_modules`), set up:
1. A "secret" local git repo `SECRET_REPO` (outside the workspace/output base) with a commit containing sensitive data.
2. An attacker-controlled git repo `EVIL_REPO` with a `.gitmodules` entry `url = file://$SECRET_REPO` and a gitlink pointing at (or a fetch that pulls in) objects from `SECRET_REPO`.
3. A `MODULE.bazel` using `git_repository(name="evil", remote=EVIL_REPO, recursive_init_submodules=True, build_file_content=...)` and a genrule reading files from the resulting submodule checkout.
4. Observe that `bazel build` succeeds in materializing content sourced from `SECRET_REPO` inside `@evil//...`, and that the operation fails with `fatal: transport 'file' not allowed` if `-c protocol.file.allow=always` is removed from `_git_maybe_shallow` invocation in `update_submodules()` — confirming that Bazel's override, not Git's own defaults, is what permits the read.

def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
