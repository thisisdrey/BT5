### Title
Unbounded, non-paginated list APIs (`GetAssetIssueList`, `ListExchanges`, `ListWitnesses`, `GetTransactionListFromPending`) allow single-request resource exhaustion - (File: `framework/src/main/java/org/tron/core/services/RpcApiService.java`)

### Summary
Several read-only Wallet/WalletSolidity/WalletExtension RPCs (mirrored by matching HTTP servlets) return the *entire* contents of a store in one response with no limit, cap, offset, or pagination — while a newer paginated variant exists side-by-side for the same data. This is the same bug class as CVE-2024-12778 (aimhubio/aim): the API has no limit on the number of items a single anonymous request can pull back, and the node's request handling is effectively serialized per gRPC/HTTP handler thread pool, so a handful of large unbounded calls can consume excessive CPU/memory and starve legitimate traffic.

### Finding Description
`RpcApiService` exposes both an unbounded and a paginated RPC for the same underlying data:
- `listExchanges` / `getExchangeList()` (unbounded) vs `getPaginatedExchangeList` (bounded, capped at `EXCHANGE_COUNT_LIMIT_MAX`) [1](#0-0) [2](#0-1) 
- `getAssetIssueList` (unbounded, `EmptyMessage`) vs `getPaginatedAssetIssueList` (bounded) [3](#0-2) 
- `listWitnesses` (unbounded) vs `getPaginatedNowWitnessList` (bounded) [4](#0-3) 
- `getTransactionListFromPending` / `getTxListFromPending()`, which serializes the full pending-pool transaction-id set on every call with no size cap [5](#0-4) [6](#0-5) 

All of these are reachable pre-existing service definitions declared in the public proto contract for `Wallet`, `WalletSolidity`, and `WalletExtension`, confirming they are live, unauthenticated, network-facing methods, not internal/test-only helpers [7](#0-6) [8](#0-7) . The corresponding HTTP servlets (`GetPaginatedExchangeListServlet`, `GetPaginatedNowWitnessListServlet`, `GetPaginatedProposalListServlet`) show the project explicitly added pagination-with-limit as a fix pattern for some endpoints [9](#0-8) , but left the original unbounded `List*`/`Get*List` (EmptyMessage) endpoints active and reachable in parallel — exactly mirroring aim's DoS root cause: "lack of a limit on the number of [items] that can be requested per call."

### Impact Explanation
An anonymous client can repeatedly call any of these unbounded list RPCs/HTTP endpoints. As on-chain state (asset issuances, exchange pairs, witnesses, or a flooded pending-transaction pool) grows — which an attacker can itself inflate by issuing TRC10 assets, creating exchange pairs, or broadcasting many valid low-cost transactions into the mempool — every subsequent call forces the node to materialize and JSON/protobuf-serialize the full collection. Because gRPC/HTTP worker threads are a finite, shared pool, a burst of such unbounded requests (or a single request against an already-large store) can exhaust CPU/heap and block the thread pool from servicing legitimate wallet/API/actuator submission traffic, i.e., a full API-availability denial of service, consistent with CVSS 7.5 AV:N/AC:L/PR:N/UI:N/A:H.

### Likelihood Explanation
High. No authentication, no rate limiting beyond the generic `RateLimiterServlet`/gRPC quota (which limits request rate, not response size/work per request), and no per-call item cap exists on these specific unbounded endpoints. An attacker only needs network access to the full node's HTTP/gRPC API, which is the standard exposed interface for wallets and dApps.

### Recommendation
- Deprecate and remove (or internally cap) the unbounded `getAssetIssueList`, `listExchanges`, `listWitnesses`, and `getTransactionListFromPending` code paths, or enforce the same server-side hard cap used by `getPaginatedExchangeList`'s `EXCHANGE_COUNT_LIMIT_MAX` and `getBlocksByLimitNext`'s `BLOCK_LIMIT_NUM` pattern [10](#0-9) .
- Require pagination parameters (offset/limit) with an enforced maximum on all list-returning public endpoints.
- Add response-size/serialization time budgeting or async/streaming responses so a single large response cannot monopolize a worker thread.

### Proof of Concept
1. Attacker issues several TRC10 assets and/or creates exchange pairs over time (cheap relative to the resulting response cost) to grow `AssetIssueStore`/`ExchangeStore`.
2. Attacker sends repeated `GET /wallet/getassetissuelist`, `GET /wallet/listexchanges`, or gRPC `Wallet.ListExchanges`/`Wallet.GetAssetIssueList`/`Wallet.ListWitnesses` calls with no offset/limit parameters.
3. Each call forces the node to enumerate and serialize the entire store on a shared HTTP/gRPC worker thread pool, degrading or blocking availability for other API/wallet clients — directly analogous to the aim CVE-2024-12778 metrics-retrieval DoS.

Note: I was unable to locate the concrete body of `Wallet.getAssetIssueList()` in the indexed sources (only its call sites in `RpcApiService`/proto were found), so the exact store-iteration implementation for that specific method is not independently confirmed here — this is a known indexing limitation, and a Devin session with full repository access could confirm the implementation details of `Wallet.getAssetIssueList()` if deeper verification is required.

  public ExchangeList getPaginatedExchangeList(long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    long latestExchangeNum = chainBaseManager.getDynamicPropertiesStore()
        .getLatestExchangeNum();
    if (latestExchangeNum <= offset) {
      return null;
    }
    limit =
        limit > EXCHANGE_COUNT_LIMIT_MAX ? EXCHANGE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > latestExchangeNum ? latestExchangeNum : end;
