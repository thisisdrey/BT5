### Title
Per-IP QoS controls (ConnectionRateLimiter, ConnectionTable) key on exact `IpAddr` with no IPv6 subnet aggregation, allowing evasion via /64+ address rotation - ([File: streamer/src/nonblocking/connection_rate_limiter.rs], [File: streamer/src/nonblocking/quic.rs])

### Summary
`ConnectionRateLimiter` and `ConnectionTable` both key their per-source accounting on the exact `std::net::IpAddr` of the QUIC peer, with no normalization or aggregation of IPv6 addresses to a routing prefix (e.g. /64). An attacker who owns a routable IPv6 block can rotate the low 64 (or more) bits of the source address on every connection so each connection is treated as a brand-new, never-before-seen IP, receiving the full per-IP allowance every time.

### Finding Description
`ConnectionRateLimiter::register_connection`/`is_allowed` use a `KeyedRateLimiter<IpAddr>` keyed by the literal `IpAddr` extracted from `incoming.remote_address().ip()` in `run_server`/`setup_connection`: [1](#0-0) [2](#0-1) [3](#0-2) 

Similarly, `ConnectionTableKey::IP(IpAddr)` is used verbatim as the map key in the SWQoS/SimpleQos connection tables (`streamer/src/nonblocking/quic.rs` lines 916-928, used by `SwQos::cache_new_connection` in `streamer/src/nonblocking/swqos.rs` lines 209-219 and `SimpleQos::cache_new_connection` in `streamer/src/nonblocking/simple_qos.rs` lines 206-223): [4](#0-3) [5](#0-4) 

Nowhere in the streamer crate is there any canonicalization or masking of IPv6 addresses to a subnet (no `/64` truncation, no `to_canonical`-style prefix normalization was found in `streamer/src/**`). Because `IpAddr` implements `Eq`/`Hash` on the full 128 bits for `Ipv6Addr`, any change to even the lowest bit produces a distinct key in both the `DashMap` inside `KeyedRateLimiter` and the `IndexMap<ConnectionTableKey, _>` inside `ConnectionTable`.

Exploit flow: an attacker who controls a routable IPv6 `/64` (2^64 addresses) opens a QUIC connection from address `ip_1`, consuming up to `DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE` (8, see `streamer/src/quic.rs` line 56) and `DEFAULT_MAX_QUIC_CONNECTIONS_PER_UNSTAKED_PEER` (8, line 41) worth of per-IP allowance. The attacker then opens subsequent connections from `ip_2, ip_3, ..., ip_n`, each differing only in low bits, and because `ConnectionRateLimiter::is_allowed`/`register_connection` and `ConnectionTable::try_add_connection` have never seen these exact addresses before, each is granted a fresh full allowance: [6](#0-5) 

The only aggregate defenses are the global `overall_connection_rate_limiter` (a single shared `TokenBucket`, `MAX_CONNECTION_BURST`/`TOTAL_CONNECTIONS_PER_SECOND`) and the global `max_unstaked_connections`/`max_staked_connections` caps enforced via `prune_unstaked_connection_table`/`prune_oldest` in `streamer/src/nonblocking/swqos.rs`. These bound total connection *count* cluster-wide, but do not restore per-entity fairness: the attacker's rotated identities can consume a disproportionate share of that global cap and evict legitimately-tracked unstaked peers via `prune_oldest`, since the per-IP throttle that is supposed to bound a single entity's share is fully bypassed.

### Impact Explanation
This is a QoS/rate-limit evasion: it does not corrupt state, cause a panic, or bypass sigverify, but it defeats the intended fairness invariant that "per-IP limits enforced per source and cannot be evaded ... by spoofed identity" (in this case, legitimately-owned but numerous identities). Concretely, an attacker with one IPv6 `/64` can drive `N`x the connections/streams of `DEFAULT_MAX_QUIC_CONNECTIONS_PER_UNSTAKED_PEER`/`DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE` toward a leader's TPU, exhausting `max_unstaked_connections` and evicting legitimate unstaked peers through `SwQos::prune_unstaked_connection_table` → `ConnectionTable::prune_oldest`. This falls into the QoS-evasion / resource-exhaustion bounty category rather than consensus safety.

### Likelihood Explanation
Preconditions are modest: the attacker needs only a routable IPv6 `/64` allocation (trivially obtainable from most cloud/VPS/hosting providers today) and no validator/gossip/staked privileges. The TPU QUIC endpoint accepts connections from any remote address that completes the handshake; no additional authentication gates unstaked peers before the rate limiter check. This is fully repeatable and requires no timing races or races against consensus — a script rotating the low bits of the source address per `connect()` call is sufficient.

### Recommendation
Normalize/aggregate IPv6 keys used in `ConnectionRateLimiter` (`streamer/src/nonblocking/connection_rate_limiter.rs`) and `ConnectionTableKey::IP` (`streamer/src/nonblocking/quic.rs`) to a configurable prefix length (e.g. mask to `/64` or `/56`) before hashing, so that all addresses within an attacker-controlled block map to the same rate-limiter/connection-table entry. Apply the same masking consistently in `is_allowed`, `register_connection`, and all `ConnectionTableKey::new` call sites (`swqos.rs`, `simple_qos.rs`).

### Proof of Concept
```rust
// streamer/src/nonblocking/connection_rate_limiter.rs (extend existing test module)
#[tokio::test]
async fn test_ipv6_prefix_rotation_evades_rate_limiter() {
    use std::net::Ipv6Addr;
    let limiter = ConnectionRateLimiter::new(3, 3, 4);
    let base: u128 = 0x2001_0db8_0000_0001_0000_0000_0000_0000; // attacker's /64
    for i in 0..1000u128 {
        let ip = IpAddr::V6(Ipv6Addr::from(base + i)); // rotate low 64 bits
        // each address is "new" -> always allowed at full burst
        assert!(limiter.is_allowed(&ip));
        assert!(limiter.register_connection(&ip));
        assert!(limiter.register_connection(&ip));
        assert!(limiter.register_connection(&ip));
        // 4th connection from the SAME address would be blocked,
        // but attacker never reuses an address, so no throttling ever occurs
    }
    // Total accepted "connections" == 3000, vastly exceeding the intended
    // per-entity cap of 3 (limit_per_minute) for a single attacker with one /64.
}
```
Expected assertion: total accepted registrations scale linearly with the number of distinct low-64-bit values used (`N * limit_per_minute`), demonstrating that the single-IP cap does not bound the attacker's aggregate connection volume, in contrast to the intended per-source limiting behavior verified by the existing `test_connection_rate_limiter` test using single, non-rotating IPv4 addresses.
