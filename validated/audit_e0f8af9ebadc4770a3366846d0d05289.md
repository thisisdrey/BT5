### Title
Legacy Bancor-formula Exchange price calculation uses floating-point `Math.pow`, enabling rounding-based fund extraction from TRX↔TRC10 pools - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The external report describes an attacker abusing a token's internal accounting during repeated transfers to distort the reserve-based price used by an AMM, then draining more value than deposited via a flash loan round-trip. The closest reachable analog in java-tron is the on-chain TRX↔TRC10 "Exchange" (Bancor-relay) market, where the exchange rate is computed from live reserve balances using floating-point `Math.pow`, and where a legacy, non-hardened code path is retained and gated only by a committee-controlled `allowStrictMath`/`allowHardenExchangeCalculation` switch.

### Finding Description
`ExchangeTransactionActuator.execute()` computes the counter-asset amount for a trade by calling `exchangeCapsule.transaction(...)`, which delegates to either `ExchangeProcessor` (legacy) or `SafeExchangeProcessor` (hardened), selected by `dynamicStore.allowHardenExchangeCalculation()`/`allowHarden()`. [1](#0-0) [2](#0-1) 

The legacy `ExchangeProcessor` computes the trade output using `double`-precision `Math.pow` (via `Maths.pow`) against a mutable, ever-changing "virtual supply" state: [3](#0-2) 

This is directly analogous to the vulnerability class in the report: a price/exchange-rate that is derived from mutable reserve state and computed with imprecise arithmetic can be nudged, trade-by-trade, in the attacker's favor. In the PoC, 199 repeated self-transfers manipulated the token contract's internal reserve accounting; in java-tron's Exchange, an attacker can similarly submit a sequence of `ExchangeTransactionContract` trades (each a single signed, unprivileged transaction) against the same `ExchangeCapsule`, exploiting floating-point rounding/precision loss in `exchangeToSupply`/`exchangeFromSupply` to accumulate value asymmetrically from the pool's `firstTokenBalance`/`secondTokenBalance`. The codebase's own presence of a `SafeExchangeProcessor` (BigDecimal-based, deterministic rounding) confirms the double-based path was recognized as imprecise/unsafe enough to warrant a hardened replacement: [4](#0-3) 

However, the hardened path is opt-in, gated behind a committee proposal (`allowHardenExchangeCalculation`), meaning any deployment where that proposal has not been activated still executes trades through the legacy floating-point `ExchangeProcessor`, reachable by any account submitting `ExchangeTransactionContract` transactions: [5](#0-4) 

`ExchangeWithdrawActuator` similarly branches its precision-check logic (`allowHarden`) between `double` and `BigDecimal` remainder computations, showing the same unmitigated legacy math is exercised on withdrawal too: [6](#0-5) 

### Impact Explanation
If the legacy floating-point processor remains active (i.e., the hardening proposal is not enabled on a given network), an attacker could submit a sequence of `ExchangeTransactionContract` transactions crafted to exploit `Math.pow` rounding/precision drift in `exchangeToSupply`/`exchangeFromSupply`, extracting TRX or TRC10 tokens from the exchange pool beyond what a correct constant-formula AMM would allow — a direct theft-of-funds analog to the reported exploit. This would constitute unbacked balance / theft of funds from the on-chain exchange pool.

### Likelihood Explanation
Exploitability is conditional: it requires (a) the target chain to not have activated `allowHardenExchangeCalculation`/`allowStrictMath`, and (b) a sufficiently liquid or structured Exchange pool to make cumulative rounding drift economically meaningful. I could not verify from the available index what the actual default value of these dynamic properties is (the `DynamicPropertiesStore.java` getter/setter definitions were located but their default initialization values were not retrieved within the available tool budget), nor could I confirm empirically (via test execution) that repeated trades produce attacker-favorable drift rather than negligible/self-canceling error. This is a plausible bug-class analog based on code structure, not a confirmed exploitable path.

### Recommendation
- Confirm the default/mainnet-activation state of `allowHardenExchangeCalculation` and `allowStrictMath`; if disabled by default, prioritize activating the hardened, `BigDecimal`-based `SafeExchangeProcessor` path chain-wide.
- Audit `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` for cumulative rounding bias, and add fuzz/property tests simulating many repeated small trades against a single `ExchangeCapsule` to detect balance drift under the legacy path.
- Consider deprecating and eventually removing the legacy double-based `ExchangeProcessor` in favor of `SafeExchangeProcessor` unconditionally.

### Proof of Concept
Not independently reproduced. A conceptual PoC would repeatedly invoke `ExchangeTransactionActuator` (via signed `ExchangeTransactionContract` transactions) against the same `exchangeId` with small `tokenQuant` values while `allowHardenExchangeCalculation == 0`, comparing cumulative `firstTokenBalance`/`secondTokenBalance` drift against the theoretically correct Bancor-formula output to determine if net value can be extracted from the pool, analogous to the existing test harness in `ExchangeTransactionActuatorTest` and `ExchangeProcessorTest`.   private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
