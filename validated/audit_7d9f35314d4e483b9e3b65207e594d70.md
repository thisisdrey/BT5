### Title
JupLend deposit can silently mint zero marginfi shares while the user's underlying assets are transferred out - (File: `programs/marginfi/src/instructions/juplend/deposit.rs`)

### Summary
`juplend_deposit` computes expected fToken shares with a floor-rounding, integer-math formula (`expected_shares_for_deposit_from_rates`), transfers the user's underlying assets into the JupLend vault, and then credits the marginfi account with exactly the number of fTokens minted — with no minimum-shares-out check. When the computed share amount rounds down to `0`, the instruction still succeeds: the user's tokens are moved into the bank's JupLend position, but the user's marginfi balance is credited `0` shares, so they lose the deposited value with nothing to show for it.

### Finding Description
The deposit flow is:
1. `expected_shares_for_deposit_from_rates` computes shares via two floor divisions (`raw = floor(assets*1e12/liquidity_exchange_price)`, then `shares = floor(norm*1e12/token_exchange_price)`). [1](#0-0) 
2. `juplend_deposit` calls this helper to get `expected_shares`, then transfers the user's underlying tokens to the liquidity vault and CPIs into JupLend to deposit them, before crediting the marginfi account with `minted_shares` (required to `== expected_shares`, but there is no check that this value is nonzero): [2](#0-1) 
3. Unit tests in the same codebase explicitly document that tiny deposit amounts floor to `0` shares under realistic exchange-price combinations (e.g., `liquidity_exchange_price=1.1e12, token_exchange_price=1e12` → `assets=1` yields `shares=0`), and the round-trip test even labels this "deposit floors to 0 shares" as expected behavior rather than a rejected case: [3](#0-2) [4](#0-3) 

This is structurally identical to the referenced Popcorn/C4 finding: a rounding-down share-conversion formula that can legitimately return `0` shares for a nonzero deposit, with no guard rejecting that outcome before assets are moved and accounting is finalized.

### Impact Explanation
When `expected_shares`/`minted_shares` is `0`:
- The user's underlying tokens are still transferred out of their wallet and deposited into JupLend via `cpi_transfer_user_to_liquidity_vault` and `cpi_juplend_deposit`.
- `record_deposit_inflow` still records the full `amount` as bank inflow, increasing the value backing the bank's JupLend position.
- `bank_account.deposit_no_repay(I80F48::from_num(0))` credits the depositing user with `0` asset shares.

The net effect: the depositor's assets are absorbed into the bank's position (benefiting the bank's other/eventual shareholders through the exchange-price mechanics) while the depositor's own marginfi account receives no share credit — a real, unauthorized economic loss for an unprivileged user performing a normal deposit. This matches the "concrete theft / unauthorized state change" bar (value transferred without corresponding credit).

### Likelihood Explanation
This requires only a normal, permissionless `juplend_deposit` call with a small enough `amount` relative to the current `liquidity_exchange_price`/`token_exchange_price` ratio — no privileged access or unusual preconditions are needed. The codebase's own tests confirm the zero-share outcome is reachable with realistic (non-degenerate) exchange prices, and treat it as a normal, non-reverting code path rather than an error. The magnitude of loss per occurrence is bounded by the "dust" threshold below which shares floor to zero (which grows as `token_exchange_price` drifts further from `liquidity_exchange_price` over time), consistent with the original finding being assessed as Medium severity rather than Critical.

### Recommendation
Add an explicit check in `juplend_deposit` (and any other integrator-deposit instruction using integer-rounded share math, e.g. Kamino/Drift deposits) that reverts when `expected_shares == 0` (or `minted_shares == 0`) for a nonzero `amount`, mirroring the mitigation recommended in the referenced report: reject deposits that would mint zero shares rather than silently accepting the user's funds with no credit.

### Proof of Concept
Using the project's own documented math (`programs/marginfi/src/instructions/juplend/deposit.rs` tests):
1. Set JupLend state to `liquidity_exchange_price = 1_100_000_000_000`, `token_exchange_price = 1_000_000_000_000`.
2. Call `juplend_deposit(amount = 1)`.
3. `expected_shares_for_deposit_from_rates(1, 1.1e12, 1e12)` returns `0` (per the codebase's own unit test `shares_for_deposit_tiny_amount_can_floor_to_zero`). [3](#0-2) 
4. The instruction proceeds: `cpi_transfer_user_to_liquidity_vault(1)` moves 1 unit of the user's underlying token out of their wallet, `cpi_juplend_deposit` deposits it, `minted_shares == expected_shares == 0` passes the `require_eq!` check, and `bank_account.deposit_no_repay(I80F48::from_num(0))` credits the user 0 asset shares. [5](#0-4) 
5. Result: the user's token balance decreased by 1 unit, but their marginfi account balance for that bank is unchanged (0 shares credited) — funds lost with no accounting benefit to the depositor.

pub fn expected_shares_for_deposit_from_rates(
    assets: u64,
    liquidity_exchange_price: u64,
    token_exchange_price: u64,
) -> Option<u64> {
    let liquidity_ex_price = liquidity_exchange_price as u128;
    let token_ex_price = token_exchange_price as u128;
    if liquidity_ex_price == 0 || token_ex_price == 0 {
        return None;
    }

    let registered_amount_raw = (assets as u128)
        .checked_mul(EXCHANGE_PRICES_PRECISION)?
        .checked_div(liquidity_ex_price)?;

    let registered_amount = registered_amount_raw
        .checked_mul(liquidity_ex_price)?
        .checked_div(EXCHANGE_PRICES_PRECISION)?;

    let shares_u128 = registered_amount
        .checked_mul(EXCHANGE_PRICES_PRECISION)?
        .checked_div(token_ex_price)?;

    shares_u128.try_into().ok()
