### Title
StackerDB chunk signatures omit a contract/domain binding, enabling cross-contract chunk replay - (File: `libstackerdb/src/libstackerdb.rs`, `stackslib/src/net/stackerdb/db.rs`, `stackslib/src/net/stackerdb/mod.rs`)

### Summary
The Beefy report shows that a signed authorization scoped to one context (an order) can be replayed through the router to act on unrelated funds because the router made an arbitrary call to `Permit2` without binding the call to the order it was meant for. The structural analog in this repo is `SlotMetadata`/`StackerDBChunkData` signatures: the signed digest binds only to `(slot_id, slot_version, data_hash)` and never to the StackerDB smart-contract (`QualifiedContractIdentifier`) the chunk is destined for. Because the `.signers-<set>-<message_id>` contracts for a reward cycle all share an *identical* slot→signer layout, a chunk validly signed by signer `S` for slot `k` in one message-type contract also verifies successfully for slot `k` in a sibling message-type contract for the same reward cycle, letting any network observer replay/relay that already-public chunk into the wrong StackerDB.

### Finding Description
`SlotMetadata::auth_digest()` computes the signed digest solely from `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`StackerDBChunkData::verify`/`recover_pk` reuse this same digest with no additional context: [2](#0-1) 

Both the direct-write path (`StackerDBTx::try_replace_chunk`) and the gossip/push validation path (`StackerDBs::validate_received_chunk`) look up the *expected signer* using the target `smart_contract`/`contract_id`, then check the signature only against `(slot_id, slot_version, data_hash)` — the contract identity is used purely to select which signer address to check against, never mixed into what was actually signed: [3](#0-2) [4](#0-3) 

The reward-cycle signer-message contracts are provisioned per message type (`.signers-<set>-0`, `.signers-<set>-1`, ... up to `SIGNER_SLOTS_PER_USER`), and the boot contract explicitly serves the *same* stored slot list to every message-id page for a given signer set: [5](#0-4) 

The test suite confirms this equivalence directly — for every `message_id` in `0..SIGNER_SLOTS_PER_USER`, `stackerdb-get-signer-slots` returns the identical `expected_stackerdb_slots` list (same signer, same slot index) for a given signer set: [6](#0-5) 

Because the same address `S` therefore owns slot `k` in every sibling `.signers-<set>-*` contract, and the chunk's digest never commits to *which* contract it authorizes, a chunk signed by `S` for slot `k` of contract `.signers-1-0` also recovers to `S` and passes `verify(&addr)` for slot `k` of `.signers-1-1`, `.signers-1-2`, etc. StackerDB chunk data is not secret — it is actively broadcast/relayed peer-to-peer (`handle_unsolicited_StackerDBPushChunk`) and servable via the public HTTP `POST /v2/stackerdb/...` endpoint — so any unprivileged network participant can capture a legitimately-signed chunk and resubmit it (via P2P push or the HTTP write endpoint) against a *different* sibling contract/slot, and the node will accept and persist it there as though it were freshly authored for that context.

### Impact Explanation
This breaks the "authenticated-for-context-A" vs "accepted-as-authenticated-for-context-B" equality: a write into a specific signer-message StackerDB slot is supposed to represent that signer's authenticated data for *that particular message type*, but the missing domain separation lets an attacker relay it into an unrelated message-type slot for the same signer, satisfying `BadSigner`/version/size checks. This is an unauthenticated cross-context write of forged/misapplied data into StackerDB state (a different message type's slot than the one actually signed), which can desynchronize or corrupt whatever consumer parses that slot expecting its own message schema, and can also be used to force acceptance of stale/attacker-chosen (but real) chunk bytes as "new" data in a sibling contract whenever version/write-count checks in that other contract still permit it.

### Likelihood Explanation
No privileged access is required: StackerDB chunk data is inherently public (broadcast to all replica peers, and readable/writable subject to signer checks via the public P2P push path and the public HTTP `POST /v2/stackerdb/<contract>/chunks/<slot>` route). All the attacker needs is to observe one legitimately signed chunk from any signer (trivial, since it's gossiped continually) and resend the exact same `(slot_id, slot_version, sig, data)` tuple against a sibling `.signers-<set>-<other_message_id>` contract at the same slot index, which holds the identical signer today by construction of the reward-cycle slot layout.

### Recommendation
Bind the StackerDB chunk/slot signature to the destination contract by including the `QualifiedContractIdentifier` (or a stable digest of it) inside `SlotMetadata::auth_digest()`, so a signature produced for one StackerDB contract cannot be replayed against another. Update `SlotMetadata::sign`/`verify`, `StackerDBChunkData::sign`/`verify`/`recover_pk`, and all callers (`try_replace_chunk`, `validate_received_chunk`, the `poststackerdbchunk` HTTP handler) to pass and check the contract identifier as part of the signed payload, with appropriate versioning/migration for existing chunk data.

### Proof of Concept
1. Reward cycle `N` provisions `SIGNER_SLOTS_PER_USER` sibling contracts `.signers-<N%2>-0` .. `.signers-<N%2>-(k-1)`, each with the identical `(signer_address, slot_id)` layout, per `stackerdb-get-signer-slots-page`/`stackerdb-get-signer-slots` (see `signers.clar` and `signers_tests.rs` above).
2. Signer `S` legitimately signs and pushes/POSTs a chunk `(slot_id=5, slot_version=v, sig, data)` to `.signers-<N%2>-0`; this is broadcast to the network via `handle_unsolicited_StackerDBPushChunk`/gossip and/or fetchable via the public HTTP stackerdb read endpoint.
3. Attacker (any unprivileged peer) captures this `(slot_id, slot_version, sig, data)` tuple and resubmits it — via P2P `StackerDBPushChunkData` with `contract_id = .signers-<N%2>-1` or via `POST /v2/stackerdb/.signers-<N%2>-1/chunks/5` — to a node.
4. The node calls `get_slot_signer(".signers-<N%2>-1", 5)` → returns `S` (same layout), then `slot_metadata.verify(&S)` using `auth_digest()` computed only from `(5, v, data_hash)` → succeeds, since the digest never referenced the contract.
5. The chunk is accepted and stored under `.signers-<N%2>-1` slot 5 even though `S` never signed anything for that contract, demonstrating the cross-contract replay.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

        let digest = self.get_slot_metadata().auth_digest();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(digest.as_bytes(), &self.sig)
            .map_err(|ve| Error::VerifyingError(ve.to_string()))

            ))?;

            return Err(net_error::BadSlotSigner(
                slot_validation.signer,

#[test]
fn signers_db_get_slots() {
    let stacker_1 = TestStacker::from_seed(&[3, 4]);
    let stacker_2 = TestStacker::from_seed(&[5, 6]);

    let (mut peer, test_signers, latest_block_id, _) = prepare_signers_test(
        function_name!(),
        vec![],
        &[stacker_1.clone(), stacker_2.clone()],
        None,
    );

    let private_key = peer.config.private_key.clone();

    let mut expected_signers: Vec<_> =
        [&stacker_1.signer_private_key, &stacker_2.signer_private_key]
            .iter()
            .map(|sk| {
                let pk = Secp256k1PublicKey::from_private(sk);
                let pk_bytes = pk.to_bytes_compressed();
                let signer_addr = StacksAddress::p2pkh(false, &pk);
                let stackerdb_entry = TupleData::from_data(vec![
                    (
                        ClarityName::from_literal("signer"),
                        PrincipalData::from(signer_addr).into(),
                    ),
                    (ClarityName::from_literal("num-slots"), Value::UInt(1)),
                ])
                .unwrap();
                (pk_bytes, stackerdb_entry)
            })
            .collect();

    // should be sorted by the pk bytes
    expected_signers.sort_by_key(|x| x.0.clone());
    let expected_stackerdb_slots = Value::cons_list_unsanitized(
        expected_signers
            .into_iter()
            .map(|(_pk, entry)| Value::from(entry))
            .collect(),
    )
    .unwrap();

    for signer_set in 0..2 {
        for message_id in 0..SIGNER_SLOTS_PER_USER {
            let contract_name =
                ContractName::try_from(format!("signers-{}-{}", &signer_set, &message_id)).unwrap();
            let signers = readonly_call(
                &mut peer,
                &latest_block_id,
                contract_name.clone(),
                ClarityName::from_literal("stackerdb-get-signer-slots"),
                vec![],
            )
            .expect_result_ok()
            .unwrap();

            debug!("Check .{}", contract_name);
            if signer_set == 0 {
                assert_eq!(signers.expect_list().unwrap(), vec![]);
            } else {
                assert_eq!(signers, expected_stackerdb_slots);
            }
        }
    }
