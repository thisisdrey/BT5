### Title
Unchecked attacker-controlled offset used as array index in `ValidateMultiSign` precompile can throw `ArrayIndexOutOfBoundsException` during transaction execution - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.ValidateMultiSign.execute()` parses the raw call data of the precompile into a `DataWord[]` array and then derives an array index directly from an attacker-supplied offset word (`words[3]`) without validating that the resulting index is within the bounds of the parsed array, before it is used both to read a size value and to extract the signature list.

### Finding Description
`ValidateMultiSign.execute(byte[] rawData)` calls `DataWord.parseArray(rawData)` to turn the raw ABI-encoded call data into a `DataWord[] words` array whose length is entirely determined by the length of `rawData` supplied by the caller. [1](#0-0) 

It then computes an index directly from `words[3]` (an offset field controlled by the caller) and uses it to both read a "signature array size" and to call `extractSigArray`/`extractBytesArray`, without any check that `words[3].intValueSafe() / WORD_SIZE` is less than `words.length`: [2](#0-1) 

The only defensive check present, `isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)`, is gated behind `VMConfig.allowTvmOsaka()`, so on chains/paths where that hard fork flag is not yet enabled this validation is skipped entirely, and even where it is enabled it was not possible to confirm from the available code that it fully bounds `words[3]` against the actual parsed word count before this indexing occurs. [3](#0-2) 

This precompile is reachable from any smart contract via a `STATICCALL`/`CALL` to the `ValidateMultiSign` precompiled address, meaning any unprivileged transaction sender who deploys or calls a contract that invokes this precompile with crafted call data controls the value of `words[3]` and therefore the computed array index. This mirrors the CVE-2021-3578 bug class: an unchecked, externally-controlled offset/length value is used directly to index into an array without bounds validation, rather than an unchecked pointer cast, but the same "attacker-controlled index used unchecked to access memory" root cause applies.

### Impact Explanation
If `words[3]` encodes an offset such that `words[3].intValueSafe() / WORD_SIZE >= words.length`, the JVM throws `ArrayIndexOutOfBoundsException` at line 1067, before the `try`/`catch(Throwable t)` block further down in the same method (which only wraps the signature-verification loop, not the array-index computation). If this exception is not caught somewhere further up the precompiled-contract invocation chain in the TVM interpreter, it will propagate uncaught during transaction/block execution, which — because precompile execution happens during consensus-critical block application — could crash or halt the node processing that transaction, or (if only some nodes handle the exception differently) could produce non-deterministic execution outcomes between nodes. I was not able to verify with full certainty whether an outer generic `catch (Exception e)`/`catch (Throwable t)` exists in the TVM's precompiled-contract call path that would convert this into a normal revert; this is a limitation of my analysis given the available tool calls.

### Likelihood Explanation
The precompile is reachable by any contract deployer or caller with a single crafted transaction — no special privileges, SR/witness status, or network position is required, satisfying the "unprivileged transaction broadcaster/contract deployer" reachability requirement. The `words[3]` value is a raw calldata word fully controlled by the transaction sender via the calldata passed into the `CALL` instruction targeting the precompile address.

### Recommendation
Add an explicit bounds check before dereferencing `words[words[3].intValueSafe() / WORD_SIZE]` and before calling `extractSigArray`/`extractBytesArray`, verifying that the computed index is non-negative and strictly less than `words.length`; return `Pair.of(false, EMPTY_BYTE_ARRAY)` (or the existing `DATA_FALSE` failure path) instead of allowing the array access to throw. Ensure the Osaka-only `isValidAbiEncoding` check (or an equivalent) is enforced unconditionally rather than gated behind `VMConfig.allowTvmOsaka()`, and audit the TVM precompiled-contract invocation path to confirm any `RuntimeException` (including `ArrayIndexOutOfBoundsException`) thrown from `execute()` is safely caught and converted into a deterministic contract-call failure rather than propagating and potentially crashing block processing.

### Proof of Concept
1. Deploy or use any smart contract that issues a low-level `staticcall`/`call` to the `ValidateMultiSign` precompiled contract address.
2. Craft `rawData` such that `words[3]` (the 4th 32-byte word) encodes a large offset value (e.g., far beyond the actual length of `rawData`/`words`), while keeping the rest of the ABI-like header parseable by `DataWord.parseArray`.
3. Send this as a normal transaction from an unprivileged account; when `ValidateMultiSign.execute` is invoked, `words[3].intValueSafe() / WORD_SIZE` computes an index at or beyond `words.length`, and the subsequent `words[...]` access at [4](#0-3)  throws `ArrayIndexOutOfBoundsException` outside of the method's own `try/catch(Throwable)` block, propagating to the caller of `execute()`.
4. Observe whether the outer TVM execution path catches this exception gracefully (reverting the transaction) or whether it propagates further, which would need to be confirmed on a running node/testnet to establish full node-crash impact — I could not confirm this last step from the indexed code alone.
