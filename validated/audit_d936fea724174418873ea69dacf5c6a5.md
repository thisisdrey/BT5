### Title
Unbounded Array Allocation in TVM Precompile Signature Extraction Leads to Uncaught OutOfMemoryError - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts extract signature/address arrays from attacker-controlled ABI-encoded call data using a length field that is read directly from the payload and used, unchecked, to allocate a Java array. Because this length is not the same value the energy (gas) cost is computed from, an attacker can submit a small, cheap `TriggerSmartContract` call that encodes an oversized length word, forcing the node to attempt an allocation of up to `Integer.MAX_VALUE` array slots. This is analogous to the CVE-2024-54028 root cause — an untrusted length/count field taken from parsed data is used to size a buffer/array without validating it against the actual bounds of the source buffer, leading to memory corruption/crash on malformed input.

### Finding Description
`extractSigArray` and `extractBytesArray` read a count from the caller-supplied words array and immediately allocate an array of that size: [1](#0-0) [2](#0-1) 

`len` comes from `words[offset].intValueSafe()`, which only clamps overflow into the `int` range — it does not bound the value against the actual number of words present in `rawData`, nor is it validated against any pre-declared size limit before allocation.

Both precompiles that call these helpers only check the derived `sigArraySize`/`addrArraySize` against `MAX_SIZE` under the `VMConfig.allowTvmSelfdestructRestriction()` feature flag, and even then the check happens by reading `words[words[3].intValueSafe() / WORD_SIZE]` which is itself unguarded against `offset` being out of range of `words`: [3](#0-2) [4](#0-3) 

Critically, the `getEnergyForData` methods for these contracts compute cost purely from `data.length` (the physical calldata size), not from the value encoded inside a length word: [5](#0-4) [6](#0-5) 

This means an attacker can submit a small calldata blob (cheap in energy) that still encodes a length field near `Integer.MAX_VALUE` at the offset location referenced by `words[3]`/`words[1]`. The `new byte[len][]` allocation attempt in `extractSigArray`/`extractBytesArray` is executed **before** any exception-tolerant guard in `ValidateMultiSign.execute` (the `try/catch` there only wraps the permission-weight logic starting at line 1082, not the earlier `extractSigArray`/`extractBytesArray` call at lines 1072-1074), so an `OutOfMemoryError` thrown during this allocation propagates unhandled out of the precompile and out of the actuator.

### Impact Explanation
An `OutOfMemoryError` thrown mid-block-application inside `PrecompiledContracts` is not a normal application exception — it can leave the JVM heap in an inconsistent state and is likely to crash the node process or a critical worker thread. Since this precompile is invoked as part of ordinary TVM execution (`CALL`/`STATICCALL` to the `ValidateMultiSign`/`BatchValidateSign` addresses), it is reachable by any account that can broadcast a `TriggerSmartContract` transaction (or by any deployed contract that calls the precompile), making this a low-cost, node-crashing denial-of-service vector.

### Likelihood Explanation
Likelihood is high for any node that processes such a transaction: the attack requires only a single signed transaction invoking the precompiled contract address with a specially crafted calldata word, no special privileges, and negligible energy cost, since energy metering is based on physical calldata length, not the untrusted length field consumed by `extractSigArray`/`extractBytesArray`.

### Recommendation
Validate any length/offset field extracted from the raw calldata against the actual bounds of `words`/`rawData` before allocating, e.g. reject if `len < 0 || len > MAX_SIZE || offset + len + 1 > words.length`, in both `extractSigArray` and `extractBytesArray`, and perform this validation before any array allocation, not just under the `allowTvmSelfdestructRestriction()` feature flag. Additionally, ensure `getEnergyForData` cost scales with the declared length so gas metering cannot be bypassed by a length field disjoint from the actual payload size.

### Proof of Concept
1. Craft a `TriggerSmartContract` transaction whose data calls the `ValidateMultiSign` precompiled contract address.
2. Set `words[3]` such that `words[3].intValueSafe() / WORD_SIZE` points to a word position within the small calldata.
3. At that word position, place a value close to `Integer.MAX_VALUE` (e.g. `0x7fffffff`) as the "signature count".
4. The physical calldata can otherwise be minimal (few words), so `getEnergyForData` charges only for the small `data.length`, while `extractSigArray` executes `new byte[Integer.MAX_VALUE][]` at line 419, an allocation exceeding the JVM heap, producing an unhandled `OutOfMemoryError` (as this code path in `ValidateMultiSign.execute` lines 1072-1074 sits outside the local `try/catch`).

**Uncertainty:** I could not fully trace whether an outer layer (e.g. `Program`/`Runtime` VM call dispatcher) wraps precompile invocation in a catch-all `Throwable`/`Error` handler that would convert this into a normal revert instead of a JVM-level crash; if such a broader safety net exists elsewhere in the runtime call stack, the practical impact would be reduced to a reverted/failed transaction rather than a node crash, though the excessive-allocation attempt and heap pressure would still occur.
