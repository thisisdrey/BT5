### Title
`DeleteAccount` action burns the account balance when `beneficiary_id` does not exist - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` deletes the source account and unconditionally queues a `Transfer` (balance-refund) receipt to whatever `beneficiary_id` the caller supplied, without checking that the beneficiary account exists. Because refund receipts are explicitly barred from implicit account creation, a refund to a non-existent account fails, and a failed refund's deposit is permanently burned rather than restored or diverted. This mirrors the external report's "presence of delegate not enforced" bug class: the protocol allows executing an irreversible action (deleting an account and transferring away its balance) without validating the existence/validity of the fallback recipient (`beneficiary_id` playing the role of the "delegate"/fallback controller), so a bad or unlucky choice permanently destroys funds instead of leaving them recoverable.

### Finding Description
`DeleteAccountAction` only requires `beneficiary_id` to be a syntactically valid `AccountId`; its existence is never checked, either at stateless validation time or at execution time [1](#0-0) .

At execution, `action_delete_account` takes the full account balance and pushes a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)`, then immediately removes the account from state — this happens unconditionally, with no existence check on `beneficiary_id`: [2](#0-1) 

The resulting balance-refund receipt is a normal `ActionReceipt` with a single `Transfer` action and `predecessor_id == "system"` (a refund receipt). When this receipt is later processed, `apply_action` computes `is_refund = true` and `implicit_account_creation_eligible = is_the_only_action && !is_refund`, which evaluates to `false` for any refund: [3](#0-2) 

`check_account_existence` for `Action::Transfer` on a missing account calls `check_transfer_to_nonexisting_account`, which only allows creation when `implicit_account_creation_eligible` is true — for refunds it is always false, so the transfer fails with `AccountDoesNotExist`: [4](#0-3) [5](#0-4) 

Finally, when a receipt whose predecessor is `"system"` (i.e., a refund receipt) fails, its deposit is not re-refunded or held — it is permanently burned: [6](#0-5) 

This is also documented as intended refund semantics: [7](#0-6) 

So the full chain is: user/contract submits `DeleteAccount { beneficiary_id }` → account is deleted and its balance is put into a refund receipt targeting `beneficiary_id` → if `beneficiary_id` does not exist (typo, account never created, or deleted between construction and execution of the action), the refund's `Transfer` fails with `AccountDoesNotExist` → the entire deposit is burned via `other_burnt_amount`. There is no analog of an enforced "delegate"/guardian or existence check that would prevent or recover from this outcome, and no way to reclaim the funds afterward — the original account no longer exists either.

### Impact Explanation
This causes a concrete, irreversible loss of user funds: the account's entire NEAR balance is destroyed (burned) rather than transferred or returned, whenever `beneficiary_id` does not correspond to an existing account at the time the refund receipt executes. Unlike a normal transfer to a non-existent account (which is rejected up front unless it's eligible for implicit creation, protecting the sender's balance), `DeleteAccountAction` performs the destructive step (account removal) unconditionally before the beneficiary is validated, so failure of the beneficiary-side step cannot be rolled back into a fund-safe state — the deposit is simply burned.

### Likelihood Explanation
This is trivially reachable by any account holder or by any contract issuing `DeleteAccount` on behalf of a predecessor (e.g., via cross-contract calls), and requires no privileged access — just specifying (or mistakenly computing/typo-ing) a `beneficiary_id` that does not exist, or one that gets deleted between the meta-transaction/relayer signing time and execution time (in the case of `DelegateAction`-wrapped `DeleteAccount`, where the beneficiary is chosen by the delegator but relayed later). This is a routine, unprivileged action path, not requiring any malicious node/network condition.

### Recommendation
Validate that `beneficiary_id` refers to an existing account before deleting the source account (e.g., reject the action, or require account existence as part of `check_actor_permissions`/`check_account_existence` for `DeleteAccountAction`), or alternatively allow the balance-refund receipt generated by `DeleteAccount` to trigger implicit account creation like other externally-funded transfers, so that a missing beneficiary does not result in permanent token burn.

### Proof of Concept
1. Create account `alice.near` with balance `B`.
2. From `alice.near` (or via a relayed `DelegateAction`), submit `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "ghost.near" })` where `ghost.near` has never been created.
3. `action_delete_account` deletes `alice.near` and queues `Receipt::new_balance_refund("ghost.near", B)` [2](#0-1) .
4. When the refund receipt is processed, `check_account_existence` rejects the `Transfer` because `implicit_account_creation_eligible` is `false` for refunds [3](#0-2) [5](#0-4) .
5. Because the receipt's predecessor is `"system"`, the failed refund's deposit `B` is added to `other_burnt_amount` and permanently destroyed [6](#0-5) .
6. Net effect: `alice.near`'s entire balance `B` is irrecoverably burned; no account (neither `alice.near` nor `ghost.near`) holds the funds.

fn check_transfer_to_nonexisting_account(
    config: &RuntimeConfig,
    account_id: &AccountId,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    if implicit_account_creation_eligible
        && account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts)
    {
        // OK. It's implicit account creation.
        // Notes:
        // - Transfer action has to be the only action in the transaction to avoid
        // abuse by hijacking this account with other public keys or contracts.
        // - Refunds don't automatically create accounts, because refunds are free and
        // we don't want some type of abuse.
        // - Account deletion with beneficiary creates a refund, so it'll not create a
        // new account.
        Ok(())
    } else {
        Err(ActionErrorKind::AccountDoesNotExist { account_id: account_id.clone() }.into())
    }
}
