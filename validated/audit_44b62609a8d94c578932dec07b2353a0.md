Based on my investigation, the closest reachable analog to CVE-2015-8723 (a length field trusted without validating it against the actual buffer bounds, leading to an out-of-bounds/overflow condition) is in the TVM precompiled-contract calldata parsing helpers in `PrecompiledContracts.java`.

### Title
Unvalidated length field in precompiled-contract calldata parsing leads to out-of-bounds array access / uncontrolled allocation - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytes32Array` and `extractBytesArray`, used to decode dynamic array arguments passed to TVM precompiled contracts, read a "length" word directly from attacker-controlled call data and then use it to size an allocation and to index further into the `words` array — without ever checking that the declared length is consistent with the actual number of words available. This mirrors the root cause of CVE-2015-8723: a length value taken from untrusted input is used to drive buffer/array operations without validating it against the real size of the backing buffer.

### Finding Description
`extractBytes32Array` reads `len` from `words[offset]` and then unconditionally allocates `new byte[len][]` and reads `words[offset + i + 1]` for `i` in `[0, len)`, with no check that `offset + len` is within `words.length`: [1](#0-0) 

`extractBytesArray` similarly derives `len`, `bytesOffset`, and `bytesLen` entirely from attacker-supplied `DataWord` values and passes them to `extractBytes`, which does a raw `Arrays.copyOfRange(data, offset, offset + len)` with no bounds validation against `data.length`: [2](#0-1) 

`words[offset].intValueSafe()` can return any 32-bit integer the caller encodes in calldata (including negative values or values far larger than the actual `words` array), so:
- A negative `len` triggers `NegativeArraySizeException` on `new byte[len][]`.
- A very large positive `len` (up to `Integer.MAX_VALUE`) triggers a huge allocation attempt (`OutOfMemoryError`) or, once the loop runs past the real end of `words`, an `ArrayIndexOutOfBoundsException`.

This is functionally the same bug class as the Wireshark CVE: the code trusts a length header embedded in the payload instead of validating it against the true size of the buffer it will be used to traverse.

### Impact Explanation
These helpers back precompiled contracts that accept dynamic array parameters (batch signature/array style precompiles built on this ABI-decoding utility). Any account can invoke a TVM contract that calls such a precompile with crafted calldata, triggering the above exceptions inside the precompile's `execute()` path. Depending on whether the specific precompile caller wraps `execute()` in a broad `catch (Throwable e)` (as some sibling classes in the same file, e.g. `VerifyMintProof`/`VerifyTransferProof`, explicitly do), the failure is either contained to the single transaction (energy consumed, transaction reverted) or — if reached through a call path lacking that broad catch — propagates as an uncaught `Error`/`RuntimeException` out of contract execution, which can disrupt transaction processing for that node.

### Likelihood Explanation
Reachable from a single, unprivileged smart-contract call (deploy or invoke a contract that calls the affected precompile with a malformed dynamic-array argument). No special permissions, staking, or SR/witness role is required — only the ability to broadcast a transaction that triggers TVM execution, which is the same threat model as the CVE (an unprivileged party crafting malformed input that reaches unvalidated length-driven parsing).

### Recommendation
Add explicit bounds checks in `extractBytes32Array`, `extractBytesArray`, `extractSigArray`, and `extractBytes` verifying that `len >= 0` and that `offset + len` (and any computed `bytesOffset`/`bytesLen`) stay within the bounds of `words`/`data` before allocating or copying, returning an empty/failed result instead of throwing when the declared length is inconsistent with the actual buffer size — analogous to the fix in the referenced Wireshark commit, which added a check relating declared length to actual captured length before use.

### Proof of Concept
Deploy a contract that performs a `CALL`/`STATICCALL` into the precompiled contract address whose `execute()` invokes `extractBytesArray`/`extractBytes32Array`, with calldata where the length word at the expected array-length slot is set to `0xFFFFFFFF` (or another value far exceeding the actual number of remaining 32-byte words). This drives `len` to a huge or negative value, causing `NegativeArraySizeException`/`OutOfMemoryError`/`ArrayIndexOutOfBoundsException` inside the precompile.

**Caveat / uncertainty:** I could not fully confirm, within the available search depth, which specific precompiled-contract class (i.e., its `execute()` method) directly invokes `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, nor whether that specific call site wraps the parsing in a `catch (Throwable e)` guard the way `VerifyTransferProof`/`VerifyMintProof` do. If the calling precompile does have such a guard, the practical impact is limited to a failed/reverted transaction rather than a broader node-level fault. I recommend a follow-up review of the exact call sites of these three helper methods in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java` to confirm exception-handling coverage before treating this as a node-crash-capable issue versus a transaction-scoped DoS.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }

  private static byte[] extractBytes(byte[] data, int offset, int len) {
    return Arrays.copyOfRange(data, offset, offset + len);
  }
