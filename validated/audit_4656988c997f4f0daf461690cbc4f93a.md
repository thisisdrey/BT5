### Title
Permissionless `migrate_pool_to_delegate_stake` invokes an un-gated cross-pallet nominator→agent migration that can silently corrupt pool/delegation invariants - ([File: substrate/frame/nomination-pools/src/lib.rs])

### Summary
The external report's core defect is a **strategy migration function that can be triggered outside proper context, without the invariants of the "old" and "new" state being fully validated, leaving the underlying accounting system in an inconsistent state**. The direct local analog is `pallet_nomination_pools::Pallet::migrate_pool_to_delegate_stake`, a permissionless, unauthenticated extrinsic that calls into `pallet_delegated_staking`'s `migrate_nominator_to_agent` → `do_migrate_to_agent` to move a pool's stake from the `TransferStake` adapter model to the `DelegateStake` model.

### Finding Description
`migrate_pool_to_delegate_stake` only checks:
1. That the configured `StakeAdapter` globally uses the `Delegate` strategy, and
2. That the specific pool is still on `Transfer` strategy, [1](#0-0) 

then unconditionally calls `Self::migrate_to_delegate_stake(pool_id)`, which forwards to `T::StakeAdapter::migrate_nominator_to_agent`: [2](#0-1) 

That in turn calls `do_migrate_to_agent` in `pallet-delegated-staking`, which computes `amount_to_transfer` from the pool account's *current reducible free balance* rather than the accounting ledger's expected value, and derives `unclaimed_withdraws` as the delta between that transferred amount and the staking pallet's recorded `stake.total`: [3](#0-2) 

This mirrors exactly the pattern criticized in the external report: a migration operation is exposed as a public/loosely-gated entry point, is executed with `Strategy(oldVersion).migrate(newVersion)`-style trust in an external component's honest bookkeeping, and no invariant is enforced tying "assets actually recorded for this pool" to "assets physically present in the account" at the moment of migration. Just as the report notes governance can trigger `migrate` on a strategy directly, bypassing the vault's oversight, here **any signed account** (not even the pool's depositor or governance) can trigger the migration for **any pool id**, and the amount migrated is derived from the pool bonded account's raw free balance at the instant of the call rather than from a value that is provably reconciled with `BondedPool`/`RewardPools`/`PoolMembers` state. If the pool's bonded account free balance is transiently inflated or deflated relative to its true committed stake (e.g., due to a pending reward sweep, a race with `bond_extra`, `unbond`, or slashing application in the same block), the computed `unclaimed_withdraws` recorded into the `AgentLedger` will not match reality, and the resulting on-chain `AgentLedger::unclaimed_withdrawals` becomes the *permanent, authoritative* value used by all subsequent `withdraw_unbonded`/`migrate_delegation` calls.

Note the code comment itself acknowledges the operation is trusted rather than verified: `// This should never fail but if it does, it indicates bad state and we abort.` at the transfer step, and unclaimed_withdraws is derived via `checked_sub` guarded only against arithmetic underflow — not against being semantically wrong.

### Impact Explanation
Because the migration is irreversible (pool strategy flips from `Transfer` to `Delegate` and cannot be migrated back — enforced by the `AlreadyMigrated` check), any timing-dependent free-balance snapshot error becomes baked into `AgentLedger::unclaimed_withdrawals` for the pool's bonded account. Downstream, `do_release` in `pallet-delegated-staking` treats `unclaimed_withdrawals` as spendable/claimable capital: [4](#0-3) 

An inflated `unclaimed_withdrawals` value would let members over-withdraw funds beyond what the pool's members actually contributed (fund loss to remaining members / pool insolvency); a deflated value would permanently lock legitimate withdrawal claims for pool members, matching the report's "permanent user-fund or bridge-state lock" class of impact. Since the call is `Pays::No` and unauthenticated for `pool_id`, any user can force this migration at a moment of their choosing (e.g., right after front-running a reward payout or bonding operation) rather than the operation being confined to a controlled, atomic, invariant-checked context.

### Likelihood Explanation
Likelihood depends on being able to influence the pool bonded account's free balance relative to its recorded stake at the exact block the permissionless migration call lands — e.g., interleaving `bond_extra_other`, reward payout sweeps, or slashing settlement with a call to `migrate_pool_to_delegate_stake`. This is plausible for an unprivileged actor since the call takes no fee (`Pays::No`) and can target any `pool_id`, and pool bonded accounts routinely hold small floating balances (existential deposit buffers, freshly-collected but not yet distributed rewards) that are not strictly reconciled against `stake.total` at arbitrary block boundaries.

### Recommendation
- Short term: require that `migrate_pool_to_delegate_stake` (and the underlying `do_migrate_to_agent`) compute `unclaimed_withdraws` from a value that is reconciled against pool-level accounting (`BondedPool`/`RewardPools`/sum of member points) rather than the bonded account's raw transient free balance, and reject/queue the migration if a mismatch is detected instead of silently accepting whatever the balance happens to be.
- Long term: treat cross-strategy stake migrations as a high-risk operation class, similar to the report's recommendation to avoid arbitrary "migrate" hooks — require an explicit reconciliation/invariant check step (akin to `do_try_state`) to run and pass before and after `do_migrate_to_agent`, and gate the permissionless call so it cannot execute in the same block as other balance-mutating pool operations for the same pool id.

2. In the same block, issue a transaction that increases the pool bonded account's free balance beyond its recorded `stake.total` (e.g., trigger a reward sweep or an unbonded-but-not-yet-withdrawn balance credit), then immediately call `Pools::migrate_pool_to_delegate_stake(origin, pool_id)` as an arbitrary signed account (not the depositor).
3. Inspect `AgentLedger::<T>::get(&pool_bonded_account).unclaimed_withdrawals` post-migration and compare to the pool's true member-contribution ledger (`PoolMembers`) — a divergence confirms the corrupted value is now permanently recorded and claimable via subsequent `withdraw_unbonded`/`migrate_delegation` calls.

Because I could not execute this scenario against a live test runtime within the available tool budget, the balance-timing precondition (step 2) is asserted from code inspection of `do_migrate_to_agent`'s reliance on `T::Currency::reducible_balance` rather than a reconciled ledger value; a Devin session with test-execution access should confirm exploitability by writing a concrete `#[test]` in `substrate/frame/nomination-pools/test-delegate-stake/src/lib.rs`.

	/// Migrate existing staker account `who` to an `Agent` account.
	fn do_migrate_to_agent(who: &T::AccountId, reward_account: &T::AccountId) -> DispatchResult {
		Self::do_register_agent(who, reward_account);

		// We create a proxy delegator that will keep all the delegation funds until funds are
		// transferred to actual delegator.
		let proxy_delegator = Self::generate_proxy_delegator(Agent::from(who.clone()));

		// Get current stake
		let stake = T::CoreStaking::stake(who)?;

		// release funds from core staking.
		T::CoreStaking::migrate_to_virtual_staker(who)?;

		// transfer just released staked amount plus any free amount.
		let amount_to_transfer =
			T::Currency::reducible_balance(who, Preservation::Expendable, Fortitude::Polite);

		// This should never fail but if it does, it indicates bad state and we abort.
		T::Currency::transfer(
			who,
			&proxy_delegator.clone().get(),
			amount_to_transfer,
			Preservation::Expendable,
		)?;

		T::CoreStaking::set_payee(who, reward_account)?;
		// delegate all transferred funds back to agent.
		Self::do_delegate(proxy_delegator, Agent::from(who.clone()), amount_to_transfer)?;
		// if the transferred/delegated amount was greater than the stake, mark the extra as
		// unclaimed withdrawal.
		let unclaimed_withdraws = amount_to_transfer
			.checked_sub(&stake.total)
			.defensive_ok_or(ArithmeticError::Underflow)?;

		if !unclaimed_withdraws.is_zero() {
			let mut ledger = AgentLedger::<T>::get(who).ok_or(Error::<T>::NotAgent)?;
			ledger.unclaimed_withdrawals = ledger
				.unclaimed_withdrawals
				.checked_add(&unclaimed_withdraws)
				.defensive_ok_or(ArithmeticError::Overflow)?;
			ledger.update(who);
		}

		Ok(())
	}

	/// Release `amount` of delegated funds from `agent` to `delegator`.
	fn do_release(
		who: Agent<T::AccountId>,
		delegator: Delegator<T::AccountId>,
		amount: BalanceOf<T>,
		num_slashing_spans: u32,
	) -> DispatchResult {
		// get inner type
		let agent = who.get();
		let delegator = delegator.get();

		let mut agent_ledger = AgentLedgerOuter::<T>::get(&agent)?;
		let mut delegation = Delegation::<T>::get(&delegator).ok_or(Error::<T>::NotDelegator)?;

		// make sure delegation to be released is sound.
		ensure!(delegation.agent == agent, Error::<T>::NotAgent);
		ensure!(delegation.amount >= amount, Error::<T>::NotEnoughFunds);

		// if we do not already have enough funds to be claimed, try to withdraw some more.
		if agent_ledger.ledger.unclaimed_withdrawals < amount {
			// withdraw account.
			T::CoreStaking::withdraw_unbonded(agent.clone(), num_slashing_spans)
				.map_err(|_| Error::<T>::WithdrawFailed)?;
			// reload agent from storage since withdrawal might have changed the state.
			agent_ledger = agent_ledger.reload()?;
		}

		// if we still do not have enough funds to release, abort.
		ensure!(agent_ledger.ledger.unclaimed_withdrawals >= amount, Error::<T>::NotEnoughFunds);
		agent_ledger.remove_unclaimed_withdraw(amount)?.update();
