Audit Report

## Title
`submit_delivery_receipt` pays relayer reward and settles the order even when the Ethereum delivery event reports failure - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`DeliveryReceipt::try_from` decodes the `success` field from the `InboundMessageDispatched` Ethereum event log, but `Pallet::process_delivery_receipt` never reads this field before paying the relayer reward via `T::RewardPayment::register_reward` and removing the `PendingOrders` entry. This means a message whose dispatch on Ethereum failed is treated identically to a successfully delivered one for settlement purposes.

## Finding Description
`DeliveryReceipt` explicitly carries the on-chain execution outcome decoded from the Ethereum event: [3](#0-2) . The public, permissionless extrinsic `submit_delivery_receipt` requires only a signed origin and a valid proof for a genuine log, then forwards to `process_delivery_receipt`: [4](#0-3) . Inside `process_delivery_receipt`, only the gateway address and existence of a matching `PendingOrder` are checked; `receipt.success` is decoded but never consumed before the reward is registered and the order removed: [5](#0-4) . A repo-wide search confirms `success` is set only at decode time and never read anywhere else in the pallet or crate tree.

## Impact Explanation
This violates the invariant that settlement (payout + queue-marker removal) must only advance after execution actually succeeds. A relayer is paid `order.fee` via `T::RewardPayment::register_reward` for a message whose Ethereum-side command execution failed, and the corresponding `PendingOrders` entry is deleted (finalized) regardless of outcome — this is public underpriced/incorrect work being rewarded and a bridge settlement record being permanently closed on a false/failure signal, matching the "public underpriced work that degrades ... stalls bridge processing" and "duplicate settlement or payout" impact categories.

## Likelihood Explanation
High. No adversarial capability, forged proof, or privileged actor is required — this triggers under the ordinary relaying flow whenever a genuine `InboundMessageDispatched(success=false)` event occurs (e.g., reverted inbound command, insufficient gas), which is a normal, foreseeable operational scenario for a live bridge, not an edge case.

## Recommendation
Check `receipt.success` in `process_delivery_receipt` before calling `T::RewardPayment::register_reward`, e.g., only pay and remove the order when `receipt.success` is true; on failure, emit a distinct event (e.g. `MessageDeliveryFailed`) and decide explicit failure-path semantics for `PendingOrders` (retain for retry, or another resolution) instead of unconditionally rewarding and removing the entry.

## Proof of Concept
1. `do_process_message` enqueues a message and inserts `PendingOrders[nonce] = { nonce, fee > 0, block_number }`: [6](#0-5) .
2. On Ethereum, the Gateway contract's inbound command execution fails, emitting a genuine `InboundMessageDispatched(nonce, topic, success=false, reward_address)` event.
3. Any relayer submits this real event with a valid proof via `submit_delivery_receipt`; `T::Verifier::verify` and `DeliveryReceipt::try_from` succeed, and `process_delivery_receipt` runs.
4. Because `receipt.success` is never checked, `order.fee > 0` triggers `T::RewardPayment::register_reward`, and `PendingOrders::remove(nonce)` deletes the order — the relayer is paid and the record is finalized despite the failed on-chain execution: [7](#0-6) .

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
