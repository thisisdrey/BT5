### Title
Non-Constant-Time Auth-Token Comparison Enables Timing-Based Credential Recovery on Privileged HTTP Endpoints - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
Several `stackslib` HTTP RPC endpoints that are gated by the node's `connection_options.auth_token` compare the client-supplied `authorization` header against the configured secret using a plain, non-constant-time `!=` string comparison instead of a constant-time comparison. This is the same class of bug as the Mautic advisory (CWE-208/CWE-204 Observable Timing Discrepancy): a remote, unauthenticated attacker can measure response-time differences to incrementally recover the secret token byte-by-byte (or at minimum distinguish "correct length/prefix" from "wrong"), and use the recovered token to reach privileged, otherwise-gated functionality.

### Finding Description
The affected handlers all implement the same pattern in `try_parse_request`:

```rust
let Some(password) = &self.auth else {
    return Err(Error::Http(400, "Bad Request.".into()));
};
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
``` [1](#0-0) 

This exact pattern (`auth_header != password`) is present in:
- `stackslib/src/net/api/postblock_proposal.rs` (`/v3/block_proposal`) [1](#0-0) 
- `stackslib/src/net/api/blockreplay.rs` (`/v3/blocks/replay/:block_id`) [2](#0-1) 
- `stackslib/src/net/api/blocksimulate.rs` (`/v3/blocks/simulate/:block_id`) [3](#0-2) 
- `stackslib/src/net/api/postblock_v3.rs` (`/v3/blocks/upload/`, gates `broadcast=1`) [4](#0-3) 
- `stackslib/src/net/api/fastcallreadonly.rs`
- `stackslib/src/net/api/txsimulate.rs`

`String`/`&str` equality in Rust (`PartialEq`) first compares lengths, and if equal, delegates to a byte-slice comparison — this leaks timing information correlated with the length of the matching prefix and, at minimum, whether the guessed length is correct. Over a network, statistical timing analysis (many repeated requests, especially with the network noise, is a real technique documented in the OWASP guide referenced by the Mautic advisory) can be used to recover the secret token character by character, similar to a classic timing side-channel string-comparison attack.

The `auth_token`/`auth_password` is described in the docs as securing:
- the block-proposal validation endpoint used to submit blocks for a signer's validation, and
- `/v2/blocks?broadcast=1` and `/v3/blocks/upload/` broadcast gating. [5](#0-4) 

Successfully brute-forcing this token would let a remote unauthenticated attacker impersonate the signer and:
- POST attacker-controlled blocks to `/v3/block_proposal`, forcing the node to spend CPU/time validating arbitrary blocks (`postblock_proposal.rs` compute path), and
- gate-bypass `/v3/blocks/upload/?broadcast=1`, potentially forcing broadcast of blocks that would otherwise require this secret.

### Impact Explanation
This maps to "bounded compute DoS on a read/validate endpoint" and partial auth bypass of an otherwise-privileged interface (block-proposal validation / block broadcast gate), reachable by any remote, unauthenticated party who can send HTTP requests to the node's RPC port. It does not directly compromise consensus or private keys, but it undermines the security boundary the `auth_token` is meant to provide between the node and its signer, and could be leveraged to trigger repeated, forced block-validation workloads once the token is recovered.

### Likelihood Explanation
Exploitation requires a timing side-channel measurement over the network, which is generally noisy and requires many samples per guessed byte; this makes practical exploitation harder than the trivially-reachable Mautic HTTP login case, but it is a real and previously-demonstrated technique for HMAC/token comparisons (see OWASP reference cited in the report itself). Nodes that expose their RPC/API port publicly (rather than binding to localhost/VPN) are directly exposed. Given `auth_token` defaults to `None` (endpoint disabled) unless configured, exposure is limited to operators who intentionally enable the block-proposal/broadcast endpoints and expose them to untrusted networks — which is the documented, intended miner/signer coordination scenario.

### Recommendation
Replace the direct `!=` string comparison in all affected handlers with a constant-time comparison, e.g. using `subtle::ConstantTimeEq` (already common in Rust ecosystems) or manually comparing SHA-256 digests of the header and secret in constant time. Apply consistently to:
- `stackslib/src/net/api/postblock_proposal.rs`
- `stackslib/src/net/api/blockreplay.rs`
- `stackslib/src/net/api/blocksimulate.rs`
- `stackslib/src/net/api/postblock_v3.rs`
- `stackslib/src/net/api/fastcallreadonly.rs`
- `stackslib/src/net/api/txsimulate.rs`

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. From a remote unauthenticated client, repeatedly POST to `/v3/block_proposal` (or GET `/v3/blocks/replay/<id>`) with an `authorization` header consisting of guessed-prefix strings of increasing length, measuring response latency with high sample counts per candidate byte.
3. Because `auth_header != password` short-circuits on length mismatch and byte-slice comparison, statistically distinguishable timing differences between correct-prefix and incorrect-prefix guesses can be observed over sufficient samples, allowing incremental reconstruction of `auth_token` — analogous to the Mautic timing side-channel (CVE-2025-9824), just applied to a token-equality check instead of a login username check.
