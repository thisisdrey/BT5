## Analysis

The Halborn report describes a case where a two-step operation (`quote` → `create`) had the security check (OTP) applied nowhere along the actual code path that performs the sensitive action, because one endpoint assumed the other had already verified it. The reachable Gitaly analog is the `RefService.UpdateReferences` RPC, which performs raw, force-capable reference writes to a repository while completely bypassing the access-control gate (`pre-receive`/`update`/`post-receive` hooks and Rails' `/internal/allowed` authorization check) that every other reference-mutating path in Gitaly is required to go through.

### Title
Reference writes via `RefService.UpdateReferences` bypass GitLab's pre-receive access-check/hook pipeline - (File: internal/gitaly/service/ref/update_references.go)

### Summary
`UpdateReferences` is a `MUTATOR` RPC that creates, force-updates, or deletes arbitrary references directly through `updateref.New`/`updateref.Updater`, with no call into the hook manager at all.

### Finding Description
Every other reference-mutating write path in Gitaly's `OperationService` (e.g. `UserRebaseConfirmable`, `UserRevert`, `UserMergeBranch`) funnels ref updates through `updateref.UpdaterWithHooks.UpdateReference`, which explicitly invokes `PreReceiveHook` before migrating quarantined objects and committing the update: [1](#0-0) 
The `pre-receive` hook is the mechanism by which GitLab's Rails `/internal/allowed` endpoint decides whether a given ref change is authorized (protected branches, permission level, etc.) — this is documented as the mandatory authorization gate for all repository writes: [2](#0-1) 

In contrast, `RefService.UpdateReferences` validates only the reference name format and object ID hex encoding, then queues and commits the updates directly via `updateref.New(ctx, repo)` — a raw updater with no hook manager involved anywhere in the function: [3](#0-2) [4](#0-3) 

This is structurally identical to the reported bug class: one endpoint (`OperationService` RPCs) enforces the security check (OTP / access-check), while a second reachable endpoint that performs an equivalent sensitive action (`UpdateReferences`) has no such enforcement, because the check was implemented only in the hook-invoking code path and never centrally enforced for all ref-mutating RPCs.

### Impact Explanation
Any caller able to invoke `RefService.UpdateReferences` against a repository can force-create, force-update, or delete any reference (including protected branches/tags) without the change ever passing through GitLab's authorization/hook pipeline, without object quarantine gating, and without generating the `pre-receive`/`update`/`post-receive` events that GitLab relies on for enforcement and auditing/notifications. This can be used to silently overwrite protected branches or forge history in ways that the `OperationService` RPCs would have rejected via the `/internal/allowed` check.

### Likelihood Explanation
Any client presenting valid Gitaly RPC credentials can call this RPC directly with an arbitrary `Repository`, reference name, and object IDs; the request only needs to reference valid, existing object IDs and syntactically valid ref names, which is trivial to satisfy from a normal repository state (e.g., objects introduced by prior pushes).

### Recommendation
Route `RefService.UpdateReferences` through the same `updateref.UpdaterWithHooks` pipeline used by `OperationService` (or otherwise require this RPC to run the `pre-receive`/`update`/`post-receive` hooks and the Rails `/internal/allowed` access check) before committing reference updates, so that raw ref writes cannot be used to bypass GitLab's authorization gate.

### Proof of Concept
1. Establish a `RefService` client with valid Gitaly RPC auth against a target repository.
2. Call `UpdateReferences` with `Repository` set and an `Update` entry setting `reference = refs/heads/<protected-branch>`, `old_object_id` empty (force update), `new_object_id = <attacker-controlled existing commit>`.
3. Observe in `internal/gitaly/service/ref/update_references.go` that the request proceeds straight to `updater.Commit()` with no call to `PreReceiveHook`, `UpdateHook`, or `PostReceiveHook`, and the branch is rewritten without GitLab's `/internal/allowed` check ever being invoked — unlike the equivalent operation via `UserUpdateBranch`/push, which would be rejected if the branch is protected.

- `pre-receive`: The pre-receive hook receives all reference updates as a whole
  via standard input, where each change is represented by one line with the old
  and new object ID as well the name of the reference that is to be updated. At
  this point, all objects required to satisfy the update have already been
  received, but they are still in a separate "quarantine directory" and are
  therefore detached from the main repository. This hook first increments a
  reference counter that tracks how many pushes are active at the same time.
  Afterwards, it posts all changes to Rails' `/internal/allowed` API endpoint so
  that Rails can determine whether the change is allowed or not. Because objects
  still live in a quarantine directory, Gitaly tells Rails where it can find the
  quarantine directory using the repository's alternative object directory
  fields so that any subsequent RPC calls that check the change can access those
  objects. When the access checks succeed, any existing custom pre-receive hooks
  installed by the administrator are executed.
