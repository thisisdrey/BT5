## Title
Unvalidated `value` in `Transact`-derived `CallContract` command lets an unprivileged XCM sender drain the agent contract's Ether on Ethereum - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs`)

### Summary
The Snowbridge V2 outbound-queue XCM converter builds a `Command::CallContract { target, calldata, gas, value }` directly from a user-supplied `ContractCall::V1` embedded in an XCM `Transact` instruction, with `target`, `calldata`, `gas`, and `value` fully attacker-controlled, mirroring the keep-core bug where an arbitrary callback contract/method could be specified by the caller. The converter even declares a dedicated error variant, `XcmConverterError::CallContractValueInsufficient`, signaling that `value` was meant to be checked against the amount of Ether actually deposited/reserved for the agent by the message — but that check is never performed anywhere in `convert()`.

### Finding Description
`XcmConverter::convert()` parses an XCM program and, when it encounters an optional `Transact` instruction, decodes an attacker-supplied `ContractCall::V1 { target, calldata, value, gas }` and pushes it straight into `Command::CallContract`: [1](#0-0) 

This command is later dispatched to the Gateway contract on Ethereum, which executes it via the agent contract acting as a proxy for the origin, including `value` Ether "held by the agent contract": [2](#0-1) 

The only guard in the whole flow is `AllowedAliasOrigin::contains(origin_location)`, which restricts *which chains/locations* may alias an agent, and the ENA/PNA asset-filter matching in `extract_ethereum_native_assets` / `extract_polkadot_native_assets`, which ensures the deposited assets match the `DepositAsset` filter for token unlock/mint commands: [3](#0-2) [4](#0-3) 

None of these paths ever compare the `Transact`-supplied `value` against the amount actually deposited to (or reserved for) the agent in the same message. The converter defines `CallContractValueInsufficient` as an explicit error variant: [5](#0-4) 

but this variant is dead code — it is never constructed or returned anywhere in `convert()`. The in-tree integration test even documents this expectation in a comment without enforcing it in code: [6](#0-5) 

The comment "value should be less than the transfer amount, require validation on BH Exporter" confirms the developers' intent to enforce this constraint on Bridge Hub, but the corresponding logic was never wired into `XcmConverter::convert()`.

### Impact Explanation
Because `value` in the `CallContract` command is not bound to the assets actually reserved/deposited by the same XCM message, any account able to send a `Transact`-bearing XCM into the V2 outbound queue (subject only to the `AllowedAliasOrigin` filter and normal fee payment) can request the agent contract to forward an arbitrary `value` (in Ether) to an arbitrary `target` with arbitrary `calldata`, exceeding what that origin actually transferred/escrowed in the message. Because agent contracts pool Ether from many origins on Ethereum, this can drain funds belonging to other users' agents, i.e., unbacked spend/theft of bridge-held value and unauthorized cross-domain execution — directly matching the bug class in the external report (arbitrary callback destination + unchecked value/method leading to abuse of a shared, funded contract).

### Likelihood Explanation
The `Transact` path is a public, unprivileged feature of the V2 outbound queue intended for ordinary DOT/asset-hub users (see `transact_with_agent_from_asset_hub` test using a normal `signed` origin). The only origin check (`AllowedAliasOrigin`) constrains where the alias can come from, not what `value` can be requested, so any origin permitted to use `Transact` at all can set `value` unconstrained by the actual reserve/deposit amount in the same message. No relayer, validator, governance, or malicious peer is required — a standard user constructing the XCM program on Asset Hub is sufficient.

### Recommendation
In `XcmConverter::convert()`, before pushing `Command::CallContract`, sum the ENA amounts deposited to the resolved agent/beneficiary in the same message and reject (`Err(CallContractValueInsufficient)`) if `value` exceeds that sum, exactly as the dead error variant and the test comment already imply. Alternatively, cap `value` to the running total of `enas`/`pnas` reserved to the beneficiary, and re-verify on the Ethereum Gateway/agent contract side that outgoing value never exceeds funds attributable to the requesting origin.

### Proof of Concept
1. An attacker (regular Asset Hub user, no special privileges) constructs an XCM `InitiateTransfer` to Ethereum with `remote_xcm` containing:
   - `DepositAsset` to the attacker's own agent-derived beneficiary with a *small* or zero deposited ENA amount.
   - `Transact { call: ContractCall::V1 { target: <attacker_address>, calldata: vec![], gas: 40000, value: <large_amount> }.encode() }`
2. `XcmConverter::convert()` decodes the `Transact` payload and unconditionally emits `Command::CallContract { target, calldata, gas, value: <large_amount> }` — see the code path at `convert.rs:294-305` — with no comparison of `value` to any deposited/reserved asset amount.
3. The message is queued and later relayed to the Ethereum Gateway, where the agent contract for the attacker's origin is instructed to send `<large_amount>` Ether to `target`, regardless of whether that Ether was ever deposited by this message. If the agent's pooled balance holds funds belonging to other users' pending operations, the attacker's `Transact` can drain them.
4. This is consistent with the existing test `transact_with_agent_from_asset_hub`, whose only safeguard against over-value is a hand-written comment ("value should be less than the transfer amount, require validation on BH Exporter") that is not backed by any enforced check in `convert.rs`, and with the dead `CallContractValueInsufficient` variant that was clearly intended to perform this validation but is never triggered.

	/// Extract ethereum native assets
	fn extract_ethereum_native_assets(
		&mut self,
		enas: &Assets,
		deposit_assets: &AssetFilter,
		recipient: H160,
	) -> Result<Vec<Command>, XcmConverterError> {
		let mut commands: Vec<Command> = Vec::new();
		for ena in enas.clone().into_inner().into_iter() {
			// Check the the deposit asset filter matches what was reserved.
			if !deposit_assets.matches(&ena) {
				return Err(FilterDoesNotConsumeAllAssets);
			}

			// only fungible asset is allowed
			let (token, amount) = match ena {
				Asset { id: AssetId(inner_location), fun: Fungible(amount) } => {
					match inner_location.unpack() {
						(0, [AccountKey20 { network, key }]) if self.network_matches(network) => {
							Ok((H160(*key), amount))
						},
						// To allow ether
						(0, []) => Ok((H160([0; 20]), amount)),
						_ => Err(AssetResolutionFailed),
					}
				},
				_ => Err(AssetResolutionFailed),
			}?;

			// transfer amount must be greater than 0.
			ensure!(amount > 0, ZeroAssetTransfer);

			commands.push(Command::UnlockNativeToken { token, recipient, amount });
		}
		Ok(commands)
	}
