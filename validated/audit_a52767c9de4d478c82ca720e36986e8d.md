Audit Report

## Title
`pallet-revive` contract termination sweeps all multi-contributor native storage-deposit holds to a single beneficiary instead of refunding each depositor - ([File: substrate/frame/revive/src/deposit_payment.rs])

## Summary
When multiple distinct signed accounts each pay a native-currency storage deposit against the same contract (tracked per-payer in `NativeDepositOf<contract, payer>`), terminating that contract via the permissionless `ISystem.terminate` precompile sends the *entire* combined native hold to a single beneficiary chosen by the terminating caller, via `Deposit::refund_all` in both the native-only and PGAS-backed backends. This breaks value-conservation for the non-terminating depositors, who permanently lose their storage-deposit refund once the contract account is destroyed.

## Finding Description
`Stack::do_terminate` calls `T::Deposit::refund_all(&contract_account, exec_config.funds(origin.account_id()?))?`, routing the refund to the account tied to the terminating call's origin/beneficiary rather than to each original depositor. [2](#0-1)  Both `Deposit` implementations' `refund_all` explicitly bypass the per-contributor `NativeDepositOf` cap that `refund_on_hold` otherwise enforces, pulling the full `HoldReason::StorageDepositReserve` balance held on the contract and transferring it to one destination. [8](#0-7) [9](#0-8)  The per-payer cap (`NativeDepositOf`, populated by `record_native_deposit` on every native-fallback charge) exists specifically to prevent one contributor from claiming another's refund during partial/live refunds, but is silently dropped at the one point where funds irreversibly leave the system. [5](#0-4)  The termination entry point itself, `ISystem.terminate`, is reachable through an ordinary, unauthenticated contract call as shown by the test fixture, which forwards to the system precompile with no access control on either `growStorage` or `terminate`. [1](#0-0) 

## Impact Explanation
Any contract whose storage is funded by more than one signer via the native fallback path allows whoever triggers termination to permanently redirect every other contributor's storage-deposit refund to a beneficiary of their choosing. This is a beneficiary-correctness/value-conservation violation on contract-held value: the wrong account (and thus wrong amount split) receives the settled refund, and the loss is unrecoverable once the contract account is destroyed, matching the "contract-held value must conserve value and settle exactly once to the rightful beneficiary and amount" invariant.

## Likelihood Explanation
The repository's own test, `refund_all_drains_multi_contributor_native_hold`, exercises exactly this scenario using an unrestricted-access fixture contract and confirms ALICE (the terminator/beneficiary chooser) receives both her own and CHARLIE's deposit while CHARLIE receives nothing. [7](#0-6)  No privileged, governance, or off-chain actor is required — only two unprivileged signed accounts and a permissionless contract call, making this readily and repeatably reachable.

## Recommendation
At termination, iterate `NativeDepositOf<contract, _>` and refund each contributor their own recorded share before sweeping only the true residual (excess above tracked contributions) to the beneficiary, or explicitly gate/document this as a contract-author-level risk requiring contracts to fully unwind third-party contributions before allowing termination.

## Proof of Concept
1. Deploy `MultiContributorStorage`. [1](#0-0) 
2. ALICE calls `growStorage()`, accruing a `NativeDepositOf(contract, ALICE)` hold.
3. CHARLIE calls `growStorage()`, accruing a separate `NativeDepositOf(contract, CHARLIE)` hold.
4. ALICE calls `terminate(beneficiary=ALICE)`.
5. As shown in `refund_all_drains_multi_contributor_native_hold`, ALICE's balance increases by at least `alice_entry + charlie_entry`, while CHARLIE never receives his contribution back. [10](#0-9)

	fn refund_on_hold(
		reason: HoldReason,
		from: &T::AccountId,
		dst: Funds<T::AccountId>,
		amount: BalanceOf<T>,
	) -> DispatchResult {
		let to = match &dst {
			Funds::Balance(to) | Funds::TxFee(to) => *to,
		};
		let contribution = NativeDepositOf::<T>::get(from, to);
		let native_requested = amount.min(contribution);

		let native_refunded = if !native_requested.is_zero() {
			<() as Deposit<T>>::refund_on_hold(reason, from, dst, native_requested)?;
			let new_val = contribution.saturating_sub(native_requested);
			if new_val.is_zero() {
				NativeDepositOf::<T>::remove(from, to);
			} else {
				NativeDepositOf::<T>::insert(from, to, new_val);
			}
			native_requested
		} else {
			BalanceOf::<T>::zero()
		};

		let pgas_needed = amount.saturating_sub(native_refunded);
		Self::settle_pgas_refund(reason, from, to, pgas_needed)?;
		Ok(())
	}

	/// Refunds the full native hold to `dst` ignoring the per-contributor cap, then settles the
	/// PGAS hold via [`Self::settle_pgas_refund`] (refunding `RefundPercent` to `dst` and burning
	/// the rest). The native cap only makes sense for partial refunds on a live contract; at
	/// termination there is one recipient and the contract is gone.
	///
	/// Note: callers must run inside a storage layer so partial state rolls back on error.
	fn refund_all(
		from: &T::AccountId,
		dst: Funds<T::AccountId>,
	) -> Result<BalanceOf<T>, DispatchError> {
		let to = match &dst {
			Funds::Balance(to) | Funds::TxFee(to) => *to,
		};
		let native = <() as Deposit<T>>::refund_all(from, dst)?;

		let pgas = Self::pgas_on_hold(reason, from);
		let pgas = Self::settle_pgas_refund(reason, from, to, pgas)?;
		Ok(native.saturating_add(pgas))
	}
