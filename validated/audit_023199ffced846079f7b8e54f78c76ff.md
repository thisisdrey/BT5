### Title
Missing deadline check allows stale-mempool execution of `leverage` and `flashRepay` swaps at outdated slippage bounds - (File: contracts/SmartFarmingManager.sol)

### Summary
`SmartFarmingManager.leverage()` and `SmartFarmingManager.flashRepay()` route user funds through an external AMM `Swapper` (`swapExactInput`) with only a caller-supplied min-amount slippage bound (`depositAmountMin_` / `swapAmountOutMin_`) and no expiration deadline. A transaction that sits pending in the mempool can be mined later at a stale market price, satisfying the old slippage bound while delivering a materially worse outcome to the user — the exact bug class from the AfEth report.

### Finding Description
Both user-facing entry points delegate price-sensitive execution to `ISwapper.swapExactInput`:

- `leverage()` swaps `tokenIn_` → collateral (line 184) and then minted synth → collateral (line 197), checking only `if (_depositAmount < depositAmountMin_) revert LeverageSlippageTooHigh()` at line 198. There is no `block.timestamp` check anywhere in the function (lines 155–211).
- `flashRepay()` swaps withdrawn collateral → synth via `_swap(..., 0)` at line 125 and checks only `if (_swapAmountOut < swapAmountOutMin_) revert FlashRepaySlippageTooHigh()` at line 126. Again, no deadline parameter exists in the signature (lines 98–110).

The internal `_swap()` helper (lines 293–311) forwards `amountOutMin_` to `swapper_.swapExactInput(...)` but also takes no deadline argument, so neither the Swapper call nor the Metronome-level slippage check constrains *when* execution occurs.

By contrast, `Pool.swap()` is not a valid analog: it prices entirely off `masterOracle().quote()` at execution time (Pool.sol:493–497, 513–517), so a delayed transaction simply executes at the then-current oracle price — no stale-slippage harm exists there.

### Impact Explanation
The slippage parameters are calibrated to the market state at signing time. If the tx is delayed and the collateral/synth price moves adversely, `depositAmountMin_`/`swapAmountOutMin_` may still be satisfied on an absolute basis while representing a far worse effective rate than intended — the user silently absorbs the price drift. An unprivileged attacker (e.g., a block builder/MEV bot) can additionally withhold or sandwich the pending tx to profit from the user's now-stale bounds. In `leverage`, the user also ends up with a flash-issued debt position collateralized by a worse-than-expected deposit; in `flashRepay`, less debt is repaid than expected for the same collateral withdrawn. This is direct loss of user funds/value from a public entry point with no privileged involvement.

### Likelihood Explanation
Requires a pending/queued user transaction plus adverse price movement — same conditions as the confirmed AfEth M-06 finding. Likelihood is moderate: on L2s with fast inclusion it is rarer, but mainnet deployments (mainnet deployment artifacts exist in the repo) and builder-controlled ordering make delayed execution and sandwiching realistic. The bug is deterministic once conditions hold; no governance or oracle malfunction is needed.

### Recommendation
Add a user-supplied `deadline_` parameter to both functions and revert when expired, and propagate it (or enforce it) into the `Swapper` call path:

```solidity
function flashRepay(
    ISyntheticToken syntheticToken_,
    IDepositToken depositToken_,
    uint256 withdrawAmount_,
    uint256 swapAmountOutMin_,
    uint256 deadline_
) ... {
    if (block.timestamp > deadline_) revert StaleAction();
    ...
}

function leverage(
    IERC20 tokenIn_,
    IDepositToken depositToken_,
    ISyntheticToken syntheticToken_,
    uint256 amountIn_,
    uint256 leverage_,
    uint256 depositAmountMin_,
    uint256 deadline_
) ... {
    if (block.timestamp > deadline_) revert StaleAction();
    ...
}
```

If the `Swapper` contract supports a deadline argument, pass it through in `_swap()` so the underlying AMM swap also expires.

### Proof of Concept
Hardhat/Foundry fork outline against deployed mainnet contracts:

```solidity
// setup: fork mainnet, resolve pool / smartFarmingManager / depositToken / msUSD
// alice holds vaUSDC-denominated deposit token and has an open debt position

// 1. Alice signs flashRepay with swapAmountOutMin_ quoted at current price
uint256 minOut = pool.quoteSwapOut(msUSD, msETH /* synth */, expected) /* off-chain quote */;
vm.prank(alice);
// tx is broadcast but not mined (simulate delay)
skip(30 minutes);

// 2. Price of collateral drops on the AMM (attacker or market move)
//    e.g., dump collateral into the pool the Swapper routes through
deal(collateral, attacker, 1_000_000e18);
vm.prank(attacker);
swapperLike.swap(collateral, synth, 1_000_000e18); // pushes price down > minOut still satisfied

// 3. Alice's stale tx is included; slippage bound computed pre-drift still passes
vm.prank(alice);
smartFarmingManager.flashRepay(msUSD, depositToken, withdrawAmount, minOutStale);

// assert: repaid amount < fresh-quote amount; difference = user loss absorbed by pool/attacker
assertLt(repaidObserved, repaidAtFreshQuote);
```

The same sequence applies to `leverage()` with a stale `depositAmountMin_`: after delay + adverse price move, the final deposit clears `LeverageSlippageTooHigh` but is worth less than intended, and the position still passes the closing `debtPositionOf` health check since health is measured at oracle prices, not realized swap prices (lines 207–208).
