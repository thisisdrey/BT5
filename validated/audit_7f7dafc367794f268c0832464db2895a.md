## Title
Missing slippage protection in `ExchangeInjectContract`/`ExchangeWithdrawContract` allows sandwich attacks on TRON's native bancor-style Exchange - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeInjectActuator` and `ExchangeWithdrawActuator` — the native TRON Exchange operations analogous to a vault's `deposit()`/`mint()` (inject liquidity) and `redeem()` (withdraw liquidity) — compute the counter-asset amount from the *current* pool ratio at execution time with no minimum-output/maximum-slippage parameter, unlike `ExchangeTransactionActuator` (the swap operation) which already enforces an `expected` field as slippage protection.

### Finding Description
`ExchangeTransactionContract` includes an `expected` field that is checked against the computed `anotherTokenQuant` before executing a swap: [1](#0-0) 

By contrast, `ExchangeInjectContract` and `ExchangeWithdrawContract` carry only `owner_address`, `exchange_id`, `token_id`, and `quant` — no expected/minimum output: [2](#0-1) 

`ExchangeInjectActuator.doValidate()` computes `anotherTokenQuant` purely from the pool balances read at validation/execution time, with no check against any caller-specified bound: [3](#0-2) 

Likewise `ExchangeWithdrawActuator.doValidate()` derives `anotherTokenQuant` from the live pool ratio and only checks for calculation-precision rounding ("Not precise enough"), never a user-supplied minimum: [4](#0-3) 

Because a transaction's execution ordering within a block is determined by the block-producing witness/SR and the exchange pool ratio can be moved by any intervening `ExchangeTransactionContract` (swap) or another Inject/Withdraw from the same mempool window, an attacker (a normal, unprivileged "order placer" broadcasting `exchangetransaction`) can submit a swap immediately before the creator's pending inject/withdraw transaction executes, shifting `firstTokenBalance`/`secondTokenBalance` so the creator's `anotherTokenQuant` is computed against an unfavorable ratio — with no on-chain check to abort. This is the same missing-slippage-protection root cause described in the external report, just materialized on java-tron's native two-sided Exchange rather than an ERC-4626-style vault.

### Impact Explanation
The exchange creator interacting with `ExchangeInjectContract`/`ExchangeWithdrawContract` can receive materially less of the counter-asset than intended when sandwiched, resulting in a real economic loss of funds during a legitimate liquidity operation. This matches the "unexpected losses for users" impact class from the external report, translated into concrete value loss on-chain rather than a purely off-chain slippage concern.

### Likelihood Explanation
Any account can create an Exchange and become its creator (the only actor permitted to call Inject/Withdraw per the `!accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` check), so this affects a broad, unprivileged class of users, not just special roles. The attack itself (front-running with an `ExchangeTransactionContract`) requires no special privilege — it is available to any anonymous transaction broadcaster who can see the pending inject/withdraw transaction and submit a competing swap. This makes exploitation straightforward whenever exchange pools have meaningful liquidity/value.

### Recommendation
Add an optional slippage-protection field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., a `min_expected` counter-asset amount and/or acceptable pool-ratio bounds), and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()` analogous to the existing `expected` check in `ExchangeTransactionActuator`, aborting the operation if the computed counter-asset amount falls outside the caller's specified bound.

### Proof of Concept
1. Creator broadcasts `ExchangeWithdrawContract` expecting `anotherTokenQuant` computed from the current pool ratio (e.g., 1:2).
2. Attacker observes the pending transaction and broadcasts an `ExchangeTransactionContract` swap that shifts the pool ratio unfavorably (e.g., to 1:1.5), which is accepted with higher priority/fee or simply included first in the same block.
3. The withdraw executes against the now-shifted ratio in `ExchangeWithdrawActuator.execute()`, and the creator receives less of the counter-asset than they would have at broadcast time — with no validation check to reject or bound this outcome, since no `expected`/minimum field exists in the contract.
