### Title
Unbounded, Non-Reversible Partition Assignment Registration on Repository-Creating RPCs Leads to KV-Store State Bloat / DoS - ([File: internal/gitaly/storage/storagemgr/partition_assigner.go])

### Summary
Gitaly's `partitionAssigner` records a `(relative_path → partition_id)` mapping in the storage's embedded key-value store *before* the corresponding repository is actually created on disk, and this write is committed directly to the KV store outside of the enclosing transaction's atomic commit/rollback. If the repository creation subsequently fails, is aborted, or the repository is later deleted, the partition-assignment record is never removed. This mirrors the audited "market add" bug class: a registration/state-creating function that writes a critical mapping entry without any corresponding cleanup/reversal path, allowing unmanageable, permanently-orphaned state to accumulate from ordinary, unprivileged repository-creation RPCs (`CreateRepository`, `CreateFork`, `CreateObjectPool`, or an implicit repository creation triggered by a push).

### Finding Description
Every RPC that operates on a repository must first go through `beginTransactionForRepository`, which determines whether the target repository is a "repository-creating" RPC and, if so, sets `AllowPartitionAssignmentWithoutRepository: true`: [1](#0-0) 

This flag is passed down to `StorageManager.Begin`, which calls `partitionAssigner.getPartitionID`: [2](#0-1) 

Inside `getPartitionIDRecursive`, when `isRepositoryCreation` is true, the assigner is explicitly permitted to allocate and persist a partition assignment for a relative path that does not exist yet on disk: [3](#0-2) 

The assignment is written immediately via `partitionAssignmentTable.setPartitionID`, which performs a direct `NewWriteBatch`/`Flush` against the KV store — independent of the surrounding git-data transaction's WAL and commit/rollback semantics: [4](#0-3) [5](#0-4) 

The project's own documentation confirms there is no reconciliation of this mapping: assignments are created before the repository exists and are never deleted, even after the repository itself is deleted: [6](#0-5) 

Because this behavior is reachable via any ordinary repository-creating RPC (`CreateRepository`, `CreateFork`, `CreateObjectPool`, or an implicit repo creation from a push), any authenticated but otherwise unprivileged user who can trigger repeated repository-creation attempts that ultimately fail, are cancelled, or are followed by deletion (a normal and expected client behavior, e.g., retried forks, failed pushes to a new repo, or deliberate create/delete churn) can cause an unbounded number of stale `partition_assignment/<relative_path>` keys to accumulate in the storage's key-value database, permanently consuming partition-ID sequence values and KV-store space with no built-in mechanism to reclaim them.

### Impact Explanation
- **Unmanageable/orphaned state accumulation**: Every failed, aborted, or subsequently-deleted repository creation leaves a permanent partition assignment record, directly paralleling the "No Reversibility" impact described in the source report (accumulation of unmanageable entries with no delete/undo path).
- **Resource exhaustion / DoS of a handler**: Because entries are never removed, an attacker who can cheaply trigger many repository-creation attempts (e.g., pushes to new repository paths that are aborted, or fork/pool creation calls that are cancelled before completion) can grow the KV store's `partition_assignment/` keyspace without bound, degrading the storage engine (Badger DB compaction/iteration cost) over time and consuming partition-ID sequence space, affecting the availability of the Gitaly node for legitimate operations.
- The impact is storage/availability-oriented rather than data-confidentiality, consistent with a resource/DoS class finding rather than a direct data-exposure bug.

### Likelihood Explanation
Likelihood is high: the code path is exercised on the standard/common flow of every repository-creating RPC, requires no special privileges beyond the ability to create (and abandon/delete) repositories — an operation available to ordinary users with push/fork/object-pool-creation access — and the lack of cleanup is explicitly acknowledged as a known, unresolved design gap in the codebase's own documentation and comments (with an open tracking issue referenced directly in the code comments).

### Recommendation
- Make partition-assignment writes participate in the same atomic commit/rollback as the associated repository-creation transaction (e.g., write the assignment as part of the transaction's WAL rather than via a direct, immediate `WriteBatch`), so a failed/aborted creation does not leave a stale assignment behind.
- Add a reconciliation/garbage-collection path that removes `partition_assignment/<relative_path>` entries when the corresponding repository is deleted, or when a partition is confirmed to hold no repositories.
- Rate-limit or bound the number of pending/failed repository-creation attempts per identity to reduce the ability to cheaply grow this state.

### Proof of Concept
1. An unprivileged user repeatedly issues repository-creating RPCs (e.g., `CreateRepository`/`CreateFork`/`CreateObjectPool`) with unique relative paths, but arranges for each attempt to fail after the transaction begins (e.g., by cancelling the client context, or via any RPC-handler-level failure that occurs after `Begin` but before the repository is actually written to disk).
2. Each such attempt calls `partitionAssigner.getPartitionIDRecursive` → `assignPartitionID` → `partitionAssignmentTable.setPartitionID`, which commits a new `partition_assignment/<relative_path>` entry directly to the KV store (see `internal/gitaly/storage/storagemgr/partition_assigner.go` lines 80–91, 266–315), independent of whether the enclosing transaction later succeeds or fails.
3. Because there is no delete path for these entries (confirmed by `doc/transactions.md` lines 69–70), repeating step 1 an arbitrary number of times causes unbounded growth of the KV store's assignment keyspace and consumption of partition IDs, with no cleanup mechanism — demonstrating the storage/DoS impact.

// Begin gets the Partition for the specified repository and starts a transaction. If a
// Partition is not already running, a new one is created and used. The partition tracks
// the number of pending transactions and this counter gets incremented when Begin is invoked.
func (sm *StorageManager) Begin(ctx context.Context, opts storage.TransactionOptions) (_ storage.Transaction, returnedErr error) {
	if opts.RelativePath == "" {
		return nil, fmt.Errorf("target relative path unset")
	}

	relativePath, err := storage.ValidateRelativePath(sm.path, opts.RelativePath)
	if err != nil {
		return nil, structerr.NewInvalidArgument("validate relative path: %w", err)
	}

	partitionID, err := sm.partitionAssigner.getPartitionID(ctx, relativePath, opts.AlternateRelativePath, opts.AllowPartitionAssignmentWithoutRepository)
	if err != nil {
		if errors.Is(err, badger.ErrDBClosed) {
			// The database is closed when PartitionManager is closing. Return a more
			// descriptive error of what happened.
			return nil, ErrPartitionManagerClosed
		}

		return nil, fmt.Errorf("get partition: %w", err)
	}

func (pt *partitionAssignmentTable) setPartitionID(relativePath string, id storage.PartitionID) error {
	wb := pt.db.NewWriteBatch()
	if err := wb.Set(pt.key(relativePath), id.MarshalBinary()); err != nil {
		return fmt.Errorf("set: %w", err)
	}

	if err := wb.Flush(); err != nil {
		return fmt.Errorf("flush: %w", err)
	}

	return nil
}

func (pa *partitionAssigner) assignPartitionID(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID) (storage.PartitionID, error) {
	// Check if the repository has an alternate. If so, it needs to go into the same
	// partition with it.
	ptnID, err := pa.getAlternatePartitionID(ctx, relativePath, recursiveCall, partitionHint)
	if err != nil {
		if !errors.Is(err, gitstorage.ErrNoAlternate) {
			return 0, fmt.Errorf("get alternate partition ID: %w", err)
		}

		ptnID = partitionHint
		if ptnID == invalidPartitionID {
			// The repository has no alternate. Unpooled repositories go into their own partitions.
			// Allocate a new partition ID for this repository.
			ptnID, err = pa.allocatePartitionID()
			if err != nil {
				return 0, fmt.Errorf("acquire partition id: %w", err)
			}
		}
	}

	if err := pa.partitionAssignmentTable.setPartitionID(relativePath, ptnID); err != nil {
		return 0, fmt.Errorf("set partition: %w", err)
	}

	return ptnID, nil
}
