### Title
Unbounded growth of `refs/dangling/*` references in object pools causes escalating cost / DoS of the `FetchIntoObjectPool` RPC handler - (File: internal/git/objectpool/fetch.go)

### Summary
`ObjectPool.FetchFromOrigin` (invoked by the `FetchIntoObjectPool` RPC) creates a `refs/dangling/$OID` reference for every unreferenced object it discovers via `git fsck` after each fetch, but it never removes any of these references. [1](#0-0)  Because force-pushes and rewrites by any pool member routinely orphan objects, and pool fetches are non-pruning by design, this reference set (analogous to the `marketsList` array in the report) grows without bound over the lifetime of the pool, and it is fully re-walked/rewritten on every subsequent housekeeping cycle.

### Finding Description
`rescueDanglingObjects` runs `git fsck --connectivity-only --dangling` and, for every dangling object found, creates a new `refs/dangling/<oid>` reference via `updateref.New` so the object is never pruned: [2](#0-1)  There is no companion mechanism to delete or cap these references — the design explicitly treats every historical dangling object as permanently "kept alive," as documented in `doc/object_pools.md`: [3](#0-2) 

This is the direct analog of the reported bug class: the addition function (`rescueDanglingObjects`) has no corresponding, complete removal function, so the collection (`refs/dangling/*`) can only grow, exactly like `marketsList` growing via `addMarket` with a broken `removeMarket`. Each `FetchIntoObjectPool` call subsequently:
- Performs a non-pruning fetch of `+refs/*:refs/remotes/origin/*` from the origin into the pool [4](#0-3) 
- Re-runs `git fsck --dangling` and iterates all results, creating an update-ref transaction over that (ever-growing) result set [5](#0-4) 
- Triggers `git-pack-refs(1)` and `git-repack(1)` over the pool, both of which must process every accumulated dangling reference [6](#0-5) 

The RPC entry point that triggers this unbounded work is `FetchIntoObjectPool`: [7](#0-6) 

Reachability from an ordinary user: any user with push/force-push access to any member of a fork network (a normal, unprivileged Git operation) can repeatedly create and immediately overwrite/delete branches/tags to generate unreachable objects in that member. GitLab's periodic housekeeping then calls `FetchIntoObjectPool` for the pool, which converts each newly abandoned object into a permanent `refs/dangling/<oid>` reference. Because deletion is architecturally rejected ("there is no point in time where it's safe to delete objects from the object pool" [8](#0-7) ), an attacker with only ordinary push access can drive this reference set arbitrarily large over time with no cap in the codebase.

### Impact Explanation
As the `refs/dangling/*` set grows without bound, every subsequent `FetchIntoObjectPool` invocation becomes progressively more expensive: the `git fsck --dangling` scan, the `update-ref` transaction to (re)create references, `git-pack-refs(1)`, and `git-repack(1)` all scale with the total number of dangling references accumulated since the pool's creation. This is a resource-exhaustion / DoS vector against the housekeeping RPC handler and, transitively, against object-pool member fetches/clones that must connect through the alternate (mitigated only partially via `core.alternateRefsCommand=exit 0 #` [9](#0-8) ). In the worst case this can make `FetchIntoObjectPool` calls exceed RPC time limits, stalling housekeeping for the affected pool indefinitely (the same class of impact as the referenced report's out-of-gas/DoS during market iteration).

### Likelihood Explanation
Likelihood is high for a determined but otherwise unprivileged actor: producing dangling objects only requires ordinary force-push/branch-deletion operations against any repository that is (or later becomes) a member of an object pool (fork network). No special permissions, malicious peers, or leaked credentials are required — this is purely a side effect of normal Git housekeeping repeatedly running against attacker-influenced churn.

### Recommendation
Introduce a bound on the `refs/dangling/*` namespace analogous to bounding `marketsList`:
- Cap the number of dangling references retained (e.g., LRU-evict oldest, or age-based expiry) instead of retaining every dangling object indefinitely.
- Track dangling-reference count/age in `ReferencesInfo` (as is already done for loose/packed refs, see `internal/git/stats/repository_info.go`) and factor it into the housekeeping heuristics so that pack-refs/repack cost is bounded per run.
- Consider a periodic, safe reconciliation that can actually free dangling objects once it can be proven no pool member depends on them (e.g., via generation tracking), rather than relying purely on "keep everything forever."

### Proof of Concept
1. Create an object pool with member repository `R` (standard GitLab fork-network flow).
2. Repeatedly, over time: push a branch to `R`, then force-push over it or delete it, so `git gc`/pool fetch always finds new unreferenced objects.
3. Trigger `FetchIntoObjectPool` (as GitLab's scheduled housekeeping does) after each round.
4. Observe that `refs/dangling/<oid>` references in the pool repository (visible via `git for-each-ref refs/dangling/` inside the pool, as exercised in `TestFetchFromOrigin_dangling` [10](#0-9) ) accumulate monotonically across cycles with no upper bound and are never removed by any code path, causing `git fsck`, `pack-refs`, and `repack` cost inside `FetchIntoObjectPool` to grow linearly with the number of historical push/delete cycles.

	// objects without having to create loads of dangling references. But unfortunately keeping
	// around old refs can lead to D/F conflicts between old references that have since
	// been deleted in the pool and new references that have been added in the pool member we're
	// fetching from. E.g. if we have the old reference `refs/heads/branch` and the pool member
	// has replaced that since with a new reference `refs/heads/branch/conflict` then
	// the fetch would now always fail because of that conflict.
	//
	// Due to the lack of an alternative to resolve that conflict we are thus forced to enable
	// pruning. This isn't too bad given that we know to keep alive the old objects via dangling
	// refs anyway, but I'd sleep easier if we didn't have to do this.
	//
	// Note that we need to perform the pruning separately from the fetch: if the fetch is using
	// `--atomic` and `--prune` together then it still wouldn't be able to recover from the D/F
	// conflict. So we first to a preliminary prune that only prunes refs without fetching
	// objects yet to avoid that scenario.

const danglingObjectNamespace = "refs/dangling/"

// rescueDanglingObjects creates refs for all dangling objects if finds
// with `git fsck`, which converts those objects from "dangling" to
// "not-dangling". This guards against any object ever being deleted from
// a pool repository. This is a defense in depth against accidental use
// of `git prune`, which could remove Git objects that a pool member
// relies on. There is currently no way for us to reliably determine if
// an object is still used anywhere, so the only safe thing to do is to
// assume that every object _is_ used.
func (o *ObjectPool) rescueDanglingObjects(ctx context.Context) (returnedErr error) {
	stderr := &bytes.Buffer{}
	fsck, err := o.Repo.Exec(ctx, gitcmd.Command{
		Name:  "fsck",
		Flags: []gitcmd.Option{gitcmd.Flag{Name: "--connectivity-only"}, gitcmd.Flag{Name: "--dangling"}},
	},
		gitcmd.WithStderr(stderr),
		gitcmd.WithSetupStdout(),
	)
	if err != nil {
		return err
	}

	updater, err := updateref.New(ctx, o.Repo, updateref.WithDisabledTransactions())
	if err != nil {
		return err
	}
	defer func() {
		if err := updater.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("cancel updater: %w", err)
		}
	}()

	if err := updater.Start(); err != nil {
		return fmt.Errorf("start reference transaction: %w", err)
	}

	objectHash, err := o.ObjectHash(ctx)
	if err != nil {
		return fmt.Errorf("detecting object hash: %w", err)
	}

	scanner := bufio.NewScanner(fsck)
	for scanner.Scan() {
		split := strings.SplitN(scanner.Text(), " ", 3)
		if len(split) != 3 {
			continue
		}

		if split[0] != "dangling" {
			continue
		}

		danglingObjectID, err := objectHash.FromHex(split[2])
		if err != nil {
			return fmt.Errorf("parsing object ID %q: %w", split[2], err)
		}

		ref := git.ReferenceName(danglingObjectNamespace + split[2])
		if err := updater.Create(ref, danglingObjectID); err != nil {
			return err
		}
	}

	if err := scanner.Err(); err != nil {
		return err
	}

	if err := fsck.Wait(); err != nil {
		return fmt.Errorf("git fsck: %w, stderr: %q", err, stderr.String())
	}

	return updater.Commit()
}

As a safeguard to not lose any objects by accident, we thus create dangling
references in the object pool after the fetch in `FetchIntoObjectPool`. For each
dangling object, a reference `refs/dangling/$OID` is created which points into
the object. This assures that each object is still referenced.

Having unreachable objects kept alive in this fashion does have its problems:

- For busy repositories, we generate loads of dangling references. While these
  references [cannot be seen by clients](#references), they are seen when
  performing housekeeping tasks on the object pool itself. Fetches into the
  object pool and repacking of references can thus become quite expensive.

func (s *server) FetchIntoObjectPool(ctx context.Context, req *gitalypb.FetchIntoObjectPoolRequest) (*gitalypb.FetchIntoObjectPoolResponse, error) {
	if err := validateFetchIntoObjectPoolRequest(req); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	objectPool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		return nil, structerr.NewInvalidArgument("object pool invalid: %w", err)
	}

	origin := s.localRepoFactory.Build(req.GetOrigin())

	if err := objectPool.FetchFromOrigin(ctx, origin, func(repo *gitalypb.Repository) *localrepo.Repo {
		return s.localRepoFactory.Build(repo)
	}); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}
