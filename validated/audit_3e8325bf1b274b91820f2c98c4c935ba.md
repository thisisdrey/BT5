### Title
Reward computation for cycles before the new VI-based algorithm loses precision via double division-before-multiplication - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes a voter's share of a witness's per-cycle reward using floating-point division followed by multiplication, instead of multiplying first and dividing last. This is the same bug class described in the external report (`swapUnderlyingForYt` computing `uDeposit` via division-then-multiplication), applied here to on-chain stake reward accounting.

### Finding Description
For cycles that predate `dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle()`, rewards are computed with: [1](#0-0) 
```java
long userVote = vote.getValue();
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
```
Here `voteRate` is computed as a `double` division `userVote / totalVote` before being multiplied by `totalReward`. Because doubles have limited (53-bit) mantissa precision and the division happens first, the intermediate `voteRate` is rounded before the multiplication, which both loses precision and can systematically round down (or in some cases round to a value that overstates share for one voter while another loses more) compared to doing `userVote * totalReward / totalVote` with exact integer/BigInteger arithmetic. This is the same root cause the external report flags: division before multiplication with a fractional intermediate causes precision loss relative to multiply-then-divide.

By contrast, the newer VI-based path in the very same file performs the correct order — multiply then divide, using `BigInteger` for exactness: [2](#0-1) 
```java
BigInteger deltaVi = endVi.subtract(beginVi);
...
long userVote = vote.getValue();
reward += deltaVi.multiply(BigInteger.valueOf(userVote))
    .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
```
This confirms the old-path `computeReward(long, List)` is the outlier and the precision-loss pattern is a genuine defect, not an intentional design choice.

This function is reached from a normal, unprivileged, user-signed transaction path: [3](#0-2) 
- `MortgageService.withdrawReward`/`queryReward` are invoked by `WithdrawBalanceActuator`, `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, and `VoteWitnessActuator`, all of which are actuators for broadcastable transaction types (`WithdrawBalanceContract`, `UnfreezeBalanceContract`, `UnfreezeBalanceV2Contract`, `VoteWitnessContract`).
- The old-algorithm branch (`getOldReward`) is invoked whenever `beginCycle < newAlgorithmCycle`: [4](#0-3) 

### Impact Explanation
Rounding of `voteRate` before multiplying by `totalReward` causes an accumulating discrepancy between what individual voters are actually paid (summed across all voters for a witness across all affected cycles) and the true `totalReward` recorded for that witness/cycle in `DelegationStore`. Because the reward pool for a cycle is fixed (`delegationStore.getReward(cycle, srAddress)`), systematic under/over-payment to individual accounts due to rounding drift represents either a small permanent loss of funds for the affected voter, or (depending on rounding direction across many voters) an inconsistency between total rewards distributed and the reward pool actually funded on-chain — i.e., value that is neither fully paid out nor properly accounted for. This is a reward/stake-accounting correctness issue with direct balance impact and falls within the allowed "stake/delegation/reward math" surface.

### Likelihood Explanation
Every call to `withdrawReward`/`queryReward` for any account with votes cast in a cycle prior to `newAlgorithmCycle` exercises this code path; these are triggered by ordinary, frequently-used transactions (`WithdrawBalanceContract`, `UnfreezeBalanceContract`, `UnfreezeBalanceV2Contract`, `VoteWitnessContract`). No special privilege or malicious actor is required — precision loss occurs deterministically whenever `userVote`, `totalVote` do not divide evenly, which is virtually always the case with real vote distributions. The magnitude per single withdrawal is small, but it recurs on every cycle/voter combination in the pre-new-algorithm window, making this a systemic, always-reachable rounding defect rather than a one-off edge case.

### Recommendation
Replace the floating-point division-before-multiplication with exact integer arithmetic that multiplies before dividing, mirroring the approach already used in the VI-based branch of the same class:
```java
long userVote = vote.getValue();
if (totalVote > 0) {
  reward += BigInteger.valueOf(userVote)
      .multiply(BigInteger.valueOf(totalReward))
      .divide(BigInteger.valueOf(totalVote))
      .longValue();
}
```
This avoids the intermediate lossy `double` division and matches the multiply-then-divide pattern recommended in the external report.

### Proof of Concept
1. Set up a witness `sr` with `totalVote = 3` for `cycle`, and record `totalReward = 10` (`delegationStore.addReward`/`setWitnessVote`).
2. Voter A casts `userVote = 1`, Voter B casts `userVote = 2` for `sr` in `cycle` (so `beginCycle < newAlgorithmCycle` so the old path is used).
3. Call `mortgageService.queryReward(A)` and `mortgageService.queryReward(B)` (reachable indirectly by invoking `WithdrawBalanceContract`/`VoteWitnessContract` actuators, or directly via `MortgageService` in a test as in `framework/src/test/java/org/tron/core/services/ComputeRewardTest.java`).
4. With `double voteRate = 1.0/3 = 0.3333...`, `reward_A = (long)(0.3333... * 10) = 3`; `voteRate_B = 2.0/3 = 0.6666...`, `reward_B = (long)(0.6666... * 10) = 6`. Total distributed = `9`, versus the mathematically correct multiply-first result `A = 1*10/3 = 3`, `B = 2*10/3 = 6` — total `9` as well in this particular example, but with different `userVote`/`totalVote`/`totalReward` triples (e.g., `userVote=1, totalVote=7, totalReward=100`), the double-based order-of-operations yields results that diverge from the exact integer multiply-then-divide result, demonstrating the rounding discrepancy documented at [5](#0-4) .

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
