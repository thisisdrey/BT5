Audit Report

## Title
Outbound Queue V2 pays relayer reward and clears `PendingOrders` regardless of on-chain delivery `success` flag - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` that carries a `success: bool` field describing whether the message actually executed successfully on Ethereum, but the field is silently dropped: it is never read or passed into the reward/settlement logic that follows. This allows a relayer to be paid a reward and have the `PendingOrder` settled even when the corresponding Ethereum-side message execution failed.

## Finding Description
`DeliveryReceipt` is decoded from the `InboundMessageDispatched` event log and explicitly carries a `success` flag alongside `nonce`, `topic`, and `reward_address`, via the `TryFrom<&Log>` implementation in `bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs` lines 35-51.

`process_delivery_receipt` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` lines 446-480) verifies the gateway address, resolves the `reward_account`, looks up the `PendingOrder` by `nonce`, and unconditionally pays the reward and removes the pending order — the decoded `receipt.success` value is never consulted anywhere in the function. Existing guards only check `receipt.gateway == T::GatewayAddress::get()` and that the `nonce` maps to a valid `PendingOrder`; neither guard is a substitute for checking whether the on-chain message dispatch actually succeeded.

Any relayer who can produce a valid Merkle/receipt proof for any `InboundMessageDispatched` log — including one where `success = false` (i.e., the message reverted/failed execution on Ethereum) — still gets paid the full relayer fee and the `PendingOrder` is deleted as if delivery succeeded.

## Impact Explanation
This breaks the intended invariant that reward and settlement state must only advance after execution actually succeeds, matching the "duplicate settlement or payout" / "theft or unbacked mint" impact category. A relayer can be paid `order.fee` for messages that failed to execute on Ethereum, and the corresponding `PendingOrder` is irrecoverably removed via `<PendingOrders<T>>::remove(nonce)`, preventing any future re-processing/re-delivery accounting for that nonce. This causes theft of relayer-reward funds and permanently corrupts delivery-accounting state for failed messages.

## Likelihood Explanation
Likelihood is high: `submit_delivery_receipt` is a public, unprivileged extrinsic requiring only `ensure_signed(origin)?`, callable by anyone with a valid proof for a genuine Ethereum log — no malicious relayer/validator/governance collusion is required, just an ordinary failed message execution log (which can occur during normal Ethereum-side failures, e.g., a reverting downstream call). None of the `ensure!` checks in `process_delivery_receipt` reference `success`, so the payout path is reached unconditionally whenever `order.fee > 0`.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: only call `T::RewardPayment::register_reward` and remove/settle the `PendingOrder` when `receipt.success == true`. For `success == false`, either retain the order for retry/refund handling or apply an explicit failure-settlement path that does not release the reward fee to the submitting relayer.

## Proof of Concept
1. A message with `nonce = N` and non-zero `fee` is queued via `do_process_message`, creating `PendingOrders[N]`.
2. The message is relayed to Ethereum but execution fails there (e.g., destination XCM leg reverts), causing Ethereum to emit `InboundMessageDispatched(nonce=N, topic, success=false, reward_address=...)`.
3. Any account submits `submit_delivery_receipt` with a valid proof for that event log.
4. `T::Verifier::verify` succeeds (the log is genuine), `DeliveryReceipt::try_from` decodes `success: false`, but `process_delivery_receipt` never checks it.
5. `order.fee > 0` is true, so `T::RewardPayment::register_reward` pays the full fee to `reward_account`, and `PendingOrders::remove(N)` deletes the order — as if the message had been delivered successfully.
