### Title
Multi-action receipt failure duplicates funds: outgoing promise/transfer receipts are still forwarded while the full deposit is refunded to the sender - (File: `runtime/runtime/src/lib.rs`)

### Summary
`Runtime::apply_action_receipt` executes the actions of a single `ActionReceipt` sequentially, accumulating any outgoing receipts created by earlier, successfully-executed actions (e.g. a `FunctionCall` that calls `Promise::transfer`) into a shared `ActionReceiptResult`. If a *later*, unrelated action in the same receipt fails — or the final storage-staking check fails after all actions already ran — the whole receipt is marked as failed, the account's trie-level state is rolled back, and the *entire* attached deposit of the receipt is refunded to the predecessor. However, the outgoing receipts that were already queued by the earlier successful actions are forwarded regardless of this failure, because the code that ships `result.new_receipts` is not gated on `result.result.is_ok()`. This produces a scenario analogous to the Tokemak M-4 bug: an unrelated "minimum threshold"-style check (here, `check_storage_stake`, structurally identical to Tokemak's `MIN_STAKE_AMOUNT` check) causes the batch to be treated as fully failed, while part of its effects (an outgoing value transfer) has already been irrevocably dispatched — except in nearcore's case this manifests as duplicated funds rather than frozen funds.

### Finding Description
Actions inside one `ActionReceipt` are executed in a loop: [1](#0-0) 

Each iteration calls `self.apply_action(...)`, and on success the resulting `new_result` (including any `new_receipts` produced by that action, e.g. an outgoing `Promise::transfer`/`FunctionCall` receipt created by VM host functions such as `promise_batch_action_transfer`) is merged into the shared `result` via `result.merge(new_result)` *before* the loop checks for an error and `break`s: [2](#0-1) 

Separately, after the whole action loop completes successfully, the runtime performs a final, unrelated check that the receiving account still has enough balance to cover its storage cost (`check_storage_stake`, the structural analog of Tokemak's `MIN_STAKE_AMOUNT` check). If it fails, the whole result is marked `Err`, even though every individual action already succeeded: [3](#0-2) [4](#0-3) 

Once `result.result` is `Err` (from either path above), two things happen:

1. **Full deposit refund** to the predecessor, because `refund_unspent_gas_and_deposits` treats the whole receipt's total deposit as unspent whenever `result.result.is_err()`, regardless of which action failed or how much of the deposit was already consumed by successful actions: [5](#0-4) 

2. **Trie state rollback** of the account, undoing the balance deduction (`deduct_balance`) that backed the already-created outgoing transfer/promise: [6](#0-5) 

3. **Unconditional forwarding of `result.new_receipts`** — the code that turns `result.new_receipts` into outgoing receipts (via `receipt_sink.forward_or_buffer_receipt`) does not check `result.result.is_ok()`; it runs for whatever is in `result.new_receipts` regardless of the final `Err`: [7](#0-6) 

The VM-level deduction that would normally "pay" for an outgoing transfer happens via `deduct_balance` in `result_state`, invoked when the contract appends a `Transfer`/`FunctionCall` promise action: [8](#0-7) 

Because this balance deduction is applied to the in-memory `Account` object that only becomes persisted via `set_account`/trie commit when the containing action_receipt succeeds (line 1024-1034), a subsequent rollback restores the account's balance as if the transfer never happened — while the receipt carrying that transferred value has already been forwarded onward at lines 1139-1184.

### Impact Explanation
This produces token duplication / inflation: the same value is (a) refunded in full to the original sender/predecessor of the receipt (because the overall receipt is marked failed) and (b) simultaneously delivered to the receiver of the already-created outgoing Transfer/FunctionCall promise receipt (because outgoing receipt forwarding is not gated on overall success). This is a direct violation of token-supply invariants and a duplication-of-funds / state-root-divergence class bug reachable purely by an ordinary account deploying/calling a contract that batches a successful value-transferring promise action together with another action engineered to fail the final `LackBalanceForState` check (or any later action in the batch).

### Likelihood Explanation
Reachable from an ordinary, unprivileged transaction/contract call: any account can submit a batch of actions to a receiver, or deploy a contract that (1) creates a promise carrying a `Transfer`/`FunctionCall` action with value, and (2) via a subsequent action in the same receipt (or via causing the account's final storage-stake balance check to fail after successful execution) makes the overall receipt fail. Crafting the storage-staking shortfall deterministically (e.g., depositing exactly enough for the promise but not enough to leave the account above its storage requirement) is straightforward and requires no special privileges, node cooperation, or timing races.

### Recommendation
Gate the forwarding of `result.new_receipts` (and the deposit-refund total) on the final `result.result` being `Ok`. If the overall receipt fails for any reason — whether an individual action error or the trailing `check_storage_stake` check — outgoing receipts already accumulated from earlier, individually-successful actions in the same receipt must be discarded/not sent, consistent with the fact that the corresponding account-side balance deduction is rolled back. Concretely, in `runtime/runtime/src/lib.rs`, drop or replace `result.new_receipts` with an empty set when `result.result` is `Err` before the receipt-ID generation/forwarding loop at lines 1139-1184, mirroring the `state_update.rollback()` semantics already applied at lines 1024-1034.

### Proof of Concept
1. Alice submits a receipt to account `bob` containing two actions in one `ActionReceipt`:
   - Action 0: `FunctionCall` to `bob`'s contract, which internally calls `promise_batch_action_transfer` sending `X` NEAR to `carol` (a plain, cheap-to-store account). This action succeeds and queues an outgoing `Transfer` receipt to `carol`, and merges into `result.new_receipts` at `lib.rs:927`.
   - Action 1: any action (or simply relying on the trailing per-receipt check) engineered so that, after both actions notionally succeed, `bob`'s post-execution balance is insufficient to cover `bob`'s storage usage (`check_storage_stake` at `verifier.rs:47`), producing `LackBalanceForState` at `lib.rs:961-969`.
2. Because `result.result` becomes `Err`, `state_update.rollback()` runs (`lib.rs:1031-1033`), restoring `bob`'s pre-receipt balance in the trie.
3. `refund_unspent_gas_and_deposits` computes `deposit_refund = total_deposit` (the full deposit originally attached to Alice's receipt) since `result.result.is_err()` (`lib.rs:1249`), and issues a refund receipt back to Alice for the full amount.
4. Simultaneously, the `Transfer` receipt to `carol` for `X` NEAR — already present in `result.new_receipts` from the successful Action 0 — is forwarded via `receipt_sink.forward_or_buffer_receipt` at `lib.rs:1173-1179`, unconditionally on `result.result`.
5. Net effect: `carol` receives `X` NEAR, and Alice also gets her full deposit refunded, duplicating `X` NEAR out of thin air with no corresponding debit ever persisted against `bob`'s account.

pub fn check_storage_stake(
    account: &Account,
    account_balance: Balance,
    runtime_config: &RuntimeConfig,
) -> Result<(), StorageStakingError> {
    let billable_storage_bytes = account.storage_usage();
    let required_amount = runtime_config
        .storage_amount_per_byte()
        .checked_mul(u128::from(billable_storage_bytes))
        .ok_or_else(|| {
            format!(
                "Account's billable storage usage {} overflows multiplication",
                billable_storage_bytes
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    let available_amount = account_balance
        .checked_add(account.locked())
        .ok_or_else(|| {
            format!(
                "Account's amount {} and locked {} overflow addition",
                account.amount(),
                account.locked(),
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    if available_amount >= required_amount {
        Ok(())
    } else {
        if is_zero_balance_account(account) {
            return Ok(());
        }
        Err(StorageStakingError::LackBalanceForStorageStaking(
            required_amount.checked_sub(available_amount).unwrap(),
        ))
    }
}
