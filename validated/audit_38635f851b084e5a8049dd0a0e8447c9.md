### Title
DoS via unbounded `DelegatedResourceAccountIndexCapsule` array growth in legacy resource-delegation index - (File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java)

### Summary
When `supportAllowDelegateOptimization()` is disabled, `FreezeBalanceActuator` (and the corresponding `UnfreezeBalanceActuator`) store delegation relationships in a single protobuf-encoded `DelegatedResourceAccountIndexCapsule` per account, appending to its `to_accounts`/`from_accounts` repeated fields with no cap on size, mirroring the `VotingEscrow` `MAX_DELEGATES`-style unbounded-array pattern described in the report.

### Finding Description
In `FreezeBalanceActuator.delegateResource()`, when the "optimized" delegation index is not active, the actuator loads the full `DelegatedResourceAccountIndexCapsule` for both the owner and the receiver, checks `List<ByteString> fromAccountsList/toAccountsList` for containment (an O(n) linear scan), and appends a new entry with `addToAccount`/`addFromAccount`, then serializes and writes the entire capsule back to the KV store: [1](#0-0) 
Because any account can be a `receiverAddress` in a `FreezeBalanceContract`, an unprivileged attacker can create arbitrarily many owner accounts, freeze a small balance, and delegate to a single victim address repeatedly. Each such transaction appends one more entry to the victim's `fromAccountsList`, which is stored as a single protobuf blob — there is no `MAX_DELEGATES`-equivalent limit in this code path, unlike Velodrome's `VotingEscrow` which explicitly caps delegate arrays at 1024.

The removal path in `UnfreezeBalanceActuator` has the same shape: it must read the entire list, materialize it into a `new ArrayList<>(...)`, call `.remove(...)`, and call `setAllToAccounts`/`setAllFromAccounts` (which internally does `clearToAccounts().addAllToAccounts(list)`, i.e., a full rebuild of the repeated field), then re-serialize and persist the whole capsule: [2](#0-1) [3](#0-2) 

Each of these operations (containment scan, list copy, remove, rebuild, protobuf serialize/deserialize) is `O(n)` in the number of delegation relationships recorded against the account, and the cost of a legitimate account's own `FreezeBalance`/`UnfreezeBalance` transaction against that account (or delegated to that account) grows linearly with the number of malicious entries an attacker injected — with no bound. The `calcFee()` for both these actuators returns 0, i.e., there is no bandwidth/energy cost scaled to the size of this index, so the attacker's cost per injected delegation entry is fixed and cheap (the base freeze fee) while the resulting per-operation cost for anyone touching the victim's index grows unbounded.

### Impact Explanation
An attacker can grow a victim's `DelegatedResourceAccountIndexCapsule.from_accounts`/`to_accounts` list without limit by issuing many cheap `FreezeBalanceContract` (with `Resource=BANDWIDTH`/`ENERGY` and `receiver_address` set to the victim) transactions from freshly created accounts, or by growing their own account's list and then this same account later trying to unfreeze/undelegate. This inflates the serialized size of a single DB value and the CPU cost of every subsequent read-modify-write on that account's index performed by `FreezeBalanceActuator`/`UnfreezeBalanceActuator`, without a corresponding increase in the resource fee charged, potentially causing disproportionate CPU/storage cost per block and node processing slowdown for transactions that legitimately touch the victim account's index (analogous to the `VotingEscrow` gas-exhaustion DoS in the reference report, though in java-tron the effect is a mispriced-cost/processing-cost amplification during block application rather than a hard gas-limit revert).

### Likelihood Explanation
Reachable directly via a signed `FreezeBalanceContract` broadcast by any unprivileged account, with no special privileges required, as long as the network still has `supportAllowDelegateOptimization()` disabled for the chain/committee configuration in question. I was not able to verify from the available index whether `supportAllowDelegateOptimization` is enabled by default on current java-tron mainnet or is still active on some deployments (e.g., private/consortium chains built from this codebase); this materially affects real-world reachability of the legacy code path and should be confirmed by inspecting `DynamicPropertiesStore`/`CommitteeConfig` defaults and any committee proposal history, which the index did not conclusively surface.

### Recommendation
- Cap the size of `DelegatedResourceAccountIndexCapsule.to_accounts`/`from_accounts` (e.g., reject new `FreezeBalanceContract`/legacy delegate operations once a per-account limit is reached), mirroring `MAX_DELEGATES`.
- Where the "optimized" per-relationship index (`delegatedResourceAccountIndexStore.delegate`/`delegateV2` with separate keys, as already used by `DelegateResourceActuator`) is available, always prefer it and disable/deprecate the legacy single-blob path entirely rather than gating it behind `supportAllowDelegateOptimization()`.
- Charge resource fees proportional to the size of the account's delegation index for legacy freeze/unfreeze operations touching large indices, or migrate the remaining legacy Stake1.0 delegate index automatically to the V2 per-key scheme.

### Proof of Concept
Not executable in this ask-only investigation; conceptually: an attacker repeatedly submits `FreezeBalanceContract{ownerAddress: freshAccount_i, receiverAddress: victim, resource: BANDWIDTH}` transactions from many distinct freshly funded accounts while `supportAllowDelegateOptimization()` is false, each appending one entry to the victim's `DelegatedResourceAccountIndexCapsule.from_accounts` via [4](#0-3)  at fixed low cost, then measures the CPU time / DB write size incurred by a subsequent `UnfreezeBalanceContract` touching the victim's index at [5](#0-4)  as list size grows unboundedly.

  public void removeFromAccount(ByteString fromAccount) {
    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);
    }
  }

  public List<ByteString> getToAccountsList() {
    return this.delegatedResourceAccountIndex.getToAccountsList();
  }

  public void setAllToAccounts(List<ByteString> toAccounts) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .clearToAccounts()
        .addAllToAccounts(toAccounts)
        .build();
