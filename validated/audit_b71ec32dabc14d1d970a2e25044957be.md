### Title
Out-of-bounds array read via unvalidated attacker-controlled offsets in `VerifyTransferProof.execute` - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The libarchive CVE-2024-48958 bug class is "a length/offset value taken from crafted, untrusted input is used to advance a copy pointer without validating that the resulting position stays within the source buffer, causing out-of-bounds access." The `VerifyTransferProof` precompiled contract (invoked via TVM `STATICCALL`/`CALL` to the shielded-TRC20 verify-transfer precompile address, reachable by any contract deployer/caller) reads `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` directly from the raw contract input `data` and then uses them, combined with attacker-controlled `spendCount`/`receiveCount`, as `System.arraycopy` source offsets without bounds-checking them against `data.length`.

### Finding Description
In `execute(byte[] data)` [1](#0-0) , the method only validates that `data.length` is one of four fixed sizes `{2080, 2368, 2464, 2752}` [2](#0-1) . It then reads three 32-byte-aligned integers directly from attacker-supplied data as byte offsets:

```
int spendOffset = parseInt(data, 0);
int spendAuthSigOffset = parseInt(data, 32);
int receiveOffset = parseInt(data, 64);
``` [3](#0-2) 

These offsets are used, unchecked against `data.length`, to index into `data` for `spendCount`/`receiveCount` and subsequently for the per-item `System.arraycopy` calls that copy `nullifier`, `anchor`, `spendCv`, `rk`, `spendProof`, `spendAuthSig`, `receiveCm`, `receiveCv`, `receiveEpk`, and `receiveProof`:
```
int spendCount = parseInt(data, spendOffset);
...
System.arraycopy(data, spendOffset + 320 * i, nullifier[i], 0, 32);
...
System.arraycopy(data, spendAuthSigOffset + 64 * i, spendAuthSig[i], 0, 64);
...
System.arraycopy(data, receiveOffset + 288 * i, receiveCm[i], 0, 32);
``` [4](#0-3) 

Only `spendCount`/`receiveCount` are range-checked (1-2) and cross-checked against `spendAuthSigCount`; the offsets themselves (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`, which are parsed as full 32-byte big integers truncated by `parseInt`) are never validated to be within `[0, data.length)`, nor is `offset + requiredLength` validated against `data.length`. A caller can therefore choose an offset that is negative, huge, or that lands so close to the end of the 2080–2752-byte input that the arithmetic (`spendOffset + 320*i + 128`, `receiveOffset + 288*i + 96`, etc.) walks past the end of the fixed-size `data` array — directly analogous to the libarchive bug where `src` (the "read cursor") can move beyond the bounds of the underlying buffer because the delta/offset value from crafted input was not validated before being used to index the buffer.

Because Java throws `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` on out-of-bounds `System.arraycopy`/array-allocation rather than allowing raw memory disclosure, the direct memory-safety consequence differs from the native libarchive bug, but the reachable effect is an unhandled runtime exception thrown deep inside the TVM precompile execution path, triggered purely by a `CALL`/`STATICCALL` to the shielded-pool verify-transfer precompile with a maliciously crafted, fixed-length payload.

### Impact Explanation
This precompile is reachable from any contract-calling transaction — an unprivileged transaction sender can call it directly or as part of an arbitrary smart contract's execution. An uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` originating from a precompile invoked deep inside `Program`/VM execution during block application can, depending on how far up the call stack it propagates and whether it is caught only as a generic `Exception`/`Throwable` at a coarse boundary, either (a) cause the current transaction to be marked as an unexpected/uncatalogued failure inconsistent with normal VM revert semantics, or (b) if the exception surfaces during synchronous block application in `Manager` rather than being safely converted into a transaction-level revert, crash or halt node execution for that block — a denial-of-service against every node that processes the transaction. This qualifies under the "node crash or halt" acceptance criterion.

### Likelihood Explanation
The precompile is called via a normal `CALL`/`STATICCALL` opcode from any smart contract, and the entire flaw is triggerable with a single, syntactically valid (length matches one of the 4 allowed sizes) but semantically malicious payload — no special privilege, cryptographic proof validity, or replay of legitimate shielded transaction data is required to reach the array-copy calls (the checks that occur are only on `data.length`, `spendCount`, `receiveAuthSigCount` and `receiveCount`, not on the raw offset fields). This makes the vulnerable path trivially reachable by any anonymous API/transaction submitter.

### Recommendation
Before using `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` (and every subsequent derived index) to access `data`, validate that each offset is non-negative and that `offset + requiredLength <= data.length` for every access performed in the loops (mirroring the bounds-check pattern already used elsewhere in the codebase, e.g. `ByteUtil.parseBytes`/`RLP.verifyLength`). Reject the call (return the "false" `Pair.of(true, DataWord.ZERO().getData())` result) instead of throwing an unchecked exception when any computed offset/length combination would exceed `data.length`.

### Proof of Concept
Craft a `data` payload of exactly one of the accepted fixed lengths (e.g. 2080 bytes for the smallest `spendCount=1, receiveCount=1` case). Set the first 32-byte word (`spendOffset`) to a value such as `data.length - 4` (i.e., a valid-looking small integer far in the array but leaving too little room for the subsequent fixed-size reads), and set the word at that offset (`spendCount`) to `1`. Because `spendOffset + 320*i + 128 + 192` (the `spendProof` copy) will then exceed `data.length`, the `System.arraycopy(data, spendOffset + 320*i + 128, spendProof[i], 0, 192)` call throws `ArrayIndexOutOfBoundsException` when this data is submitted as the input to a `CALL`/`STATICCALL` targeting the `VerifyTransferProof` precompile address from a deployed contract. (Exact confirmation of whether this exception is caught at a coarse `Exception`/`Throwable` boundary higher in `Program`/`Runtime`/`Manager`, or propagates to crash block application, could not be fully verified within available search scope and would need to be confirmed by tracing the full precompile-invocation call chain in a live/checked-out environment.)
