### Title
Integer overflow in ijar's ZIP64 central-directory parsing bypasses bounds checks, causing out-of-bounds heap reads - (File: third_party/ijar/zip.cc)

### Summary
`third_party/ijar/zip.cc`'s `FindZipCentralDirectory` / `MaybeReadZip64CentralDirectory` accept fully attacker-controlled 64-bit `central_dir_size` and `central_dir_offset` values from a crafted ZIP64 End-Of-Central-Directory record, and the bounds check that is supposed to keep the derived central-directory pointer inside the mapped file can be defeated by integer overflow/underflow, matching the CVE-2016-5297 bug class ("error in argument length checking... leading to potential integer overflows or other bounds checking issues").

### Finding Description
`FindZipCentralDirectory` reads the base End-Of-Central-Directory (EOCD) 32-bit `central_dir_size`/`central_dir_offset` fields and, if a ZIP64 locator/record is present, allows `MaybeReadZip64CentralDirectory` to override them with arbitrary 64-bit values read straight off the wire with `get_u8le`, guarded only by an equality check against the 32-bit fields or the sentinel `U4_MAX` (0xFFFFFFFF): [1](#0-0) 

An attacker who crafts a malicious jar simply sets the base EOCD's `central_dir_size`/`central_dir_offset` to `U4_MAX`, which unlocks a completely attacker-chosen 64-bit value for both fields in the ZIP64 EOCD record.

The only sanity check performed before trusting these values is: [2](#0-1) 

This only verifies that `central_dir_offset + central_dir_size` does not exceed the file length; it never verifies that `end_of_central_dir - central_dir_size` (the actual pointer computed for the central directory start) stays at or after the start of the mapped file: [3](#0-2) 

Because `central_dir_size` is a 64-bit attacker-controlled value, an attacker can choose it to be far larger than the actual distance from `end_of_central_dir` back to the buffer start, causing pointer arithmetic to wrap and `central_dir` to point well before (or effectively anywhere relative to) the mmap'd input buffer.

The resulting out-of-bounds pointer is stored and later dereferenced without any additional range check. Reads are nominally protected by `EnsureRemaining`, but that routine itself has the same underflow problem: [4](#0-3) 

`in_offset = p - zipdata_in_` underflows to a huge `size_t` value when `p` (derived from the corrupted `central_dir`) is before `zipdata_in_`, and `remaining = input_file_->Length() - in_offset` underflows a second time back into a huge positive number — so the `n > remaining` guard is defeated and every subsequent read through `ProcessCentralDirEntry`/`ProcessNext` is treated as "safe" even though it is reading arbitrary out-of-bounds heap memory: [5](#0-4) [6](#0-5) 

This is precisely the CVE-2016-5297 pattern: a length/argument value from untrusted input is checked with an insufficient/overflowable comparison, and the downstream bounds-checking primitive (`EnsureRemaining`) that should catch remaining violations is itself vulnerable to the same overflow, so the invariant "reads stay inside the mapped file" is not actually enforced.

### Impact Explanation
ijar is bazel's own C++ tool used to strip jars down to interface jars (invoked automatically for `java_import`/precompiled jar dependencies, including jars fetched from external, attacker-influenced sources such as `http_jar`/`http_archive` with a pinned but attacker-chosen sha256 — the checksum only guarantees the malicious bytes are unmodified, it does nothing to validate that the ZIP structure inside is safe to parse). A crafted ZIP64 central directory causes ijar to compute an out-of-bounds pointer and then read heap memory adjacent to (or far from) the mapped input file as if it were legitimate zip metadata (filenames, sizes, file data). Depending on layout this can crash the build (unreliable, not the primary claim here) or — more importantly — cause bazel's own process heap contents to be parsed and potentially copied into the generated interface jar output, i.e., disclosure of process memory into a build artifact. This is a genuine out-of-bounds read in bazel's own code triggered purely by attacker-supplied archive content, not a sandbox/DoS/mock issue.

### Likelihood Explanation
Any dependency pipeline that runs ijar over an externally-fetched jar (a common, default code path for `java_import`/precompiled Java deps) is affected. The attacker only needs to control the bytes served for a URL that the victim's build declares (and can legitimately compute/publish a matching sha256 for their own malicious content, since the checksum was never meant to validate internal ZIP structural sanity). No special privileges, MITM, or access to the victim's machine/credentials are required — this is a pure malicious-content parsing bug in bazel's own extraction tool.

### Recommendation
In `FindZipCentralDirectory`/`MaybeReadZip64CentralDirectory`, validate that the ZIP64 `central_dir_size`/`central_dir_offset` values are internally consistent with the computed central-directory pointer, explicitly checking `end_of_central_dir - central_dir_size >= bytes` (with unsigned-overflow-safe arithmetic, e.g. compare pointers/lengths without subtracting past the buffer start) before dereferencing, and reject the file otherwise. Additionally, fix `EnsureRemaining` in the same file to detect the case where `p < zipdata_in_` (or the offset computation itself overflows) and fail closed rather than silently underflowing to "plenty of bytes remaining."

### Proof of Concept
A `src/test/shell/bazel` or standalone ijar unit test can construct a minimal ZIP with:
1. A base EOCD record with `central_dir_size = 0xFFFFFFFF` and `central_dir_offset = 0xFFFFFFFF` (ZIP64 sentinels).
2. A ZIP64 EOCD record (and, optionally, locator) immediately preceding it whose `central_dir_size`/`central_dir_offset` fields are set to attacker-chosen 64-bit values engineered so that `central_dir_offset + central_dir_size <= in_length` (passing the existing check at zip.cc:766) while `end_of_central_dir - central_dir_size` underflows to a pointer before the start of the mapped buffer.
3. Feed this file to `devtools_ijar::FindZipCentralDirectory` (or the `ijar` binary end-to-end) and observe (with ASan/heap sanitizers) an out-of-bounds heap read originating from the computed `central_dir` pointer inside `ProcessCentralDirEntry`, confirming the bounds check at zip.cc:766 does not prevent the OOB access.

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
