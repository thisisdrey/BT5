### Title
Local `allowShieldedTransactionApi` restriction is enforced only in Wallet helper/build methods, not in `ShieldedTransferActuator` execution, allowing shielded transactions to bypass a node's disabled-API policy - (File: `actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`)

### Summary
The `allowShieldedTransactionApi` configuration flag is documented and used to let a node operator turn off shielded-transaction support (e.g., because the sapling/librustzcash native library may not be available, or the operator wants to disable the feature). This flag is checked in `Wallet.java` when serving the "build shielded transaction" helper APIs, but the actual on-chain enforcement point — `ShieldedTransferActuator.validate()`/`execute()` — never checks it. Instead it only checks the committee-controlled chain parameters `ALLOW_SAME_TOKEN_NAME` and `supportShieldedTransaction()`.

### Finding Description
Node operators use `allowShieldedTransactionApi=false` to disable the local API surface for shielded transactions, presumably to prevent this node from being used to build/serve shielded transactions (a "presentation-layer" restriction similar in spirit to the MCP `ALLOWED_TOOLS` bypass). However, the flag is never propagated to the actuator that actually validates and executes `ShieldedTransferContract` transactions during block application. As long as the on-chain committee parameters `ALLOW_SAME_TOKEN_NAME` and the shielded-transaction support flag are enabled network-wide (which is the normal production state on public TRON networks), any client can construct a valid `ShieldedTransferContract` transaction offline (using their own zk-SNARK proof generation, not this node's helper API), sign it, and submit it via the node's standard `BroadcastTransaction` gRPC/HTTP path. The actuator's `validate()` method [3](#0-2)  and `execute()` method [4](#0-3)  will accept and process it exactly like on any node without the restriction, because the restriction is only consulted by `Wallet.java`'s build/query helper methods, not by the actuator invoked from `Manager`/transaction execution.

The project's own regression test explicitly asserts this behavior is expected: `shieldedTransferValidationWorksWhenApiDisabled` sets `Args.getInstance().setAllowShieldedTransactionApi(false)` and then confirms `actuator.validate()` still succeeds [5](#0-4) .

### Impact Explanation
This is fundamentally different from the disabled-API HTTP/gRPC enforcement seen in `HttpApiAccessFilter` and `RpcApiAccessInterceptor`, which do correctly block disabled API *servlets/methods* at the request layer [6](#0-5) [7](#0-6) . Those cover named RPC/HTTP endpoints (i.e., they block the "convenience" API surface). But `allowShieldedTransactionApi` was never intended, nor able, to prevent a determined client from submitting a pre-built raw transaction through the normal `broadcastTransaction` path, since transaction execution goes through the actuator, which has no knowledge of this local, per-node config value. Because the flag is purely a local/node-level setting (not a network consensus parameter), and `broadcastTransaction`/block application are unaffected by it, this is best characterized as a documentation/expectation mismatch rather than an actual security boundary bypass — no unauthorized state change, fund theft, or freezing results beyond what any node participating in shielded transactions would normally allow. Node operators who intend `allowShieldedTransactionApi=false` as a way to prevent their node from handling shielded transactions at all should be aware it does not stop shielded transactions from being broadcast and executed by that node.

### Likelihood Explanation
Any unprivileged transaction broadcaster who can build a valid Sapling shielded transaction (using standard client-side zk-SNARK tooling, independent of the target node's helper API) can reach this path by simply calling the node's normal, always-available `BroadcastTransaction` endpoint. No special privilege or node misconfiguration beyond `allowShieldedTransactionApi=false` (with shielded transactions still enabled at the network/consensus level) is required.

### Recommendation
Clarify in documentation that `allowShieldedTransactionApi` only disables the node's own wallet/proof-building convenience endpoints and does not, and cannot, prevent the node from validating/executing pre-built shielded transactions submitted via `broadcastTransaction`, since that is governed by network-wide chain parameters (`ALLOW_SAME_TOKEN_NAME`, `supportShieldedTransaction`) rather than a local flag. If operators need a node to fully refuse handling shielded transactions (e.g. due to legal/compliance reasons), that would require an explicit check added to `ShieldedTransferActuator.validate()` consulting the local `allowShieldedTransactionApi` flag, or handling it at the `disabledApi`/contract-type level in `TransactionCapsule`/`Manager` before actuator dispatch.

### Proof of Concept
1. Configure a fullnode with `node.jsonrpc`/wallet config `allowShieldedTransactionApi = false` while the network's `ALLOW_SAME_TOKEN_NAME` and shielded-transaction-support chain parameters remain enabled (default on public networks).
2. Independently build a valid `ShieldedTransferContract` transaction off-node (using any Sapling-compatible client, not this node's disabled helper API).
3. Sign the transaction and submit it via the node's standard `BroadcastTransaction` gRPC/HTTP call.
4. Observe that the transaction is accepted, validated by `ShieldedTransferActuator.validate()`, and executed by `ShieldedTransferActuator.execute()` exactly as it would be on a node without the restriction — as confirmed directly by the existing unit test `shieldedTransferValidationWorksWhenApiDisabled` [5](#0-4) .
