### Title
Non-constant-time comparison of the `auth_token` HTTP `authorization` header enables remote timing-based credential recovery and auth bypass - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
Six privileged Nakamoto RPC endpoints authenticate incoming requests by comparing the client-supplied `authorization` header against the node's configured `connection_options.auth_token` using Rust's default `!=` string comparison, which is not constant-time. A remote, unauthenticated attacker can exploit the resulting timing side-channel to recover the secret token byte-by-byte and then forge authenticated requests to state-mutating or compute-heavy endpoints.

### Finding Description
The external report flags a plugin storing credentials in a way that lets unauthorized parties view/derive them (CWE-522). The equivalent weakness in this repo is not on-disk plaintext, but leakage of the secret's value through an observable channel — a classic CWE-208 (Observable Timing Discrepancy) — during network comparison of the credential.

Every one of these `try_parse_request` handlers performs the exact same pattern: [1](#0-0) 

```rust
let Some(password) = &self.auth else { ... };
let Some(auth_header) = preamble.headers.get("authorization") else { ... };
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```

The same pattern (identical `auth_header != password` check) is repeated verbatim in: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

`String`/`&str` equality in Rust (`PartialEq` for `str`, implemented via slice `==`) compares byte-by-byte and returns as soon as a mismatch is found, rather than iterating the full length in constant time. Because the comparison happens over the network per-HTTP-request, and this operation is done directly on attacker-supplied bytes vs. the secret, a request whose first N bytes match the real token will take measurably longer to reject than one that mismatches at byte 0. This is a text-book timing side channel on a secret equality check.

I searched the codebase for any constant-time comparison primitive (`subtle::ConstantTimeEq`, `ct_eq`, or a hand-rolled constant-time compare helper) and found none used anywhere for this purpose — confirming that no mitigation exists.

The `auth_token` is described as a "plain-text secret value that must exactly equal" the header in the API docs: [7](#0-6) 

and is documented as securing block-proposal submission, block broadcast, block replay/simulate, transaction simulate, and fast-call-read-only endpoints: [8](#0-7) 

### Impact Explanation
This maps to "auth bypass" under the accepted impact list. If an attacker can recover the `auth_token`, they gain the ability to:
- POST spoofed block proposals to `/v3/block_proposal`, consuming validation resources and potentially influencing miner/signer coordination.
- Force `broadcast=1` publishing of blocks via `/v3/blocks/upload/`.
- Invoke `/v3/blocks/replay/...`, `/v3/blocks/simulate/...`, `/v3/transactions/simulate`, and `/v3/contracts/fast-call-read/...`, all of which perform non-trivial chain-state computation — enabling a bounded compute DoS on a read endpoint once the secret is known, in addition to bypassing the intended access control on privileged operations meant for the coordinated `stacks-signer` only.

### Likelihood Explanation
Exploitation of raw network timing side-channels is noisy and requires many repeated measurements/statistical averaging to overcome jitter, so this is harder to exploit than a functional auth bypass, but it is a well-known, previously-exploited class of vulnerability (byte-at-a-time credential recovery via non-constant-time comparison), it needs no privileges, and it is reachable purely by sending unauthenticated HTTP requests to a normally-exposed RPC surface. Local network or same-datacenter attackers (a realistic threat model for node-to-signer traffic) have substantially reduced jitter, increasing practical feasibility.

### Recommendation
Replace the direct `!=` string comparisons on `auth_header`/`password` in all six handlers with a constant-time comparison (e.g., using the `subtle` crate's `ConstantTimeEq`, or comparing over a fixed-length HMAC/hash of both operands) so that comparison time is independent of where the first mismatching byte occurs. Centralize this check in a single shared helper (e.g. in `stackslib/src/net/httpcore.rs`) to guarantee all current and future auth-gated RPC handlers use the same constant-time logic instead of duplicating the vulnerable pattern.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. From a remote host, repeatedly send POST requests to `/v3/block_proposal` (or any of the other five endpoints) with an `authorization` header guess, measuring response latency for the 401 rejection.
3. Statistically average many requests per guessed byte to distinguish "matched prefix, mismatch at position N" (slightly slower) from "mismatch at position 0" (faster), extending the correctly-guessed prefix one byte at a time until the full token is recovered.
4. Use the recovered token to submit an authenticated block proposal / broadcast request that would otherwise be rejected.
