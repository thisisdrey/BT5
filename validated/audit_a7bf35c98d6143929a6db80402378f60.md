### Title
Rewards accrued in cycle 0 before the first maintenance cycle are permanently unclaimable by voters - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
This is the same bug class as the reported `RewardsDistributor` issue: rewards start accruing for a period before any account-level checkpoint/snapshot exists for that period, so the reward can never be attributed to a holder and is permanently stranded in the contract/store.

### Finding Description
When TRON's vote-based delegation reward model is active (`allowChangeDelegation()`), block and transaction-fee rewards for stand-by/active witnesses are recorded per-cycle via `MortgageService.payReward()`, which calls `delegationStore.addReward(cycle, witnessAddress, value)` using `dynamicPropertiesStore.getCurrentCycleNumber()` as the cycle key. [1](#0-0) 

The per-cycle witness vote total that voters' rewards are computed against, `delegationStore.getWitnessVote(cycle, srAddress)`, is only ever written by `MaintenanceManager.doMaintenance()`, and it is always written for `nextCycle = currentCycleNumber + 1`, never for the cycle that is currently in progress: [2](#0-1) 

Consequently, `getWitnessVote(0, srAddress)` is never explicitly set and falls back to the store's default sentinel value: [3](#0-2) 

`MortgageService.computeReward(long cycle, List<Pair<byte[],Long>> votes)` (the old reward algorithm, used for cycles below `newRewardAlgorithmEffectiveCycle`) explicitly skips any cycle whose recorded vote total equals `DelegationStore.REMARK` (the sentinel for "never set"): [4](#0-3) 

This means every reward that is accrued through `payBlockReward` / `payTransactionFeeReward` during cycle 0 — i.e., from the moment `allowChangeDelegation` is activated until the very first `doMaintenance()` cycle transition — is stored via `delegationStore.addReward(0, srAddress, value)` but can never be attributed to any voter's `computeReward`, because cycle 0's vote total is permanently `REMARK` and can never be retroactively populated (the maintenance loop only ever writes vote totals for the *next* cycle going forward). This is structurally identical to the alchemix `RewardsDistributor` bug: rewards start accruing for a period for which no per-holder/per-cycle snapshot exists at the start of that period, so nobody can ever claim that portion, and it is permanently orphaned in the store (accessible only via `delegationStore.getReward(0, srAddress)`, which is never read back into a claimable pool for voters after cycle 0 has passed). The parallel new-algorithm path (`RewardViCalService`/`accumulateWitnessVi`) similarly forwards a zero Vi delta whenever `voteCount == 0` for a cycle, silently dropping the associated reward amount from the distribution: [5](#0-4) 

### Impact Explanation
Any TRC voter reward attributable to blocks produced in cycle 0 of the vote-delegation reward system is permanently frozen and unclaimable by any voter address, resulting in a real, protocol-level loss of yield that can never be recovered through any user-facing API/actuator flow (`WithdrawRewardContract`, `GetReward`, etc.), matching the "Permanent freezing of unclaimed yield" impact class from the reference report.

### Likelihood Explanation
This triggers deterministically and automatically on every network (mainnet/testnet/private chain) the very first time `allowChangeDelegation` is turned on and blocks are produced before the first `doMaintenance()` cycle boundary is crossed — no attacker action or special privilege is required; it is an unavoidable consequence of the existing reward bookkeeping and cycle-transition logic.

### Recommendation
When `allowChangeDelegation` is first enabled (or at genesis if enabled from network start), explicitly initialize `delegationStore.setWitnessVote(0, witnessAddress, witness.getVoteCount())` (and similarly seed cycle-0 Vi/brokerage state) for every witness before any `payReward` calls can post rewards for cycle 0, so `computeReward`/`accumulateWitnessVi` do not treat cycle 0 as `REMARK`/zero-vote and silently drop the reward.

### Proof of Concept
Conceptual PoC (mirrors the reported alchemix PoC):
1. Deploy/activate `allowChangeDelegation` at network genesis or at a fresh state where `currentCycleNumber == 0` and no `doMaintenance()` has run yet.
2. Produce blocks so that `MortgageService.payBlockReward()` is invoked, causing `delegationStore.addReward(0, srAddress, value)` to accumulate a non-zero reward for cycle 0.
3. Have a user vote for that SR and call `withdrawReward`/`queryReward`.
4. Observe that `computeReward(0, votes)` returns 0 for that user's share of cycle-0 rewards because `getWitnessVote(0, srAddress) == DelegationStore.REMARK`, confirming the cycle-0 portion of `delegationStore.getReward(0, srAddress)` is unreachable and permanently stuck, exactly as `DelegationServiceTest` must manually call `setWitnessVote(0, ...)` to make cycle-0 rewards testable at all: [6](#0-5)

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

    BytesCapsule bytesCapsule = get(buildVoteKey(cycle, address));
    if (bytesCapsule == null) {
      return REMARK;
    } else {
      return ByteArray.toLong(bytesCapsule.getData());

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
