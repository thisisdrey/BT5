### Title
`DynamicPacketToProcessThreshold` permanently latches `max_packets` at 0 with no self-healing, causing unbounded denial of ancestor-hashes repair response processing - ([File: core/src/repair/packet_threshold.rs])

### Summary
`DynamicPacketToProcessThreshold::update` adjusts `max_packets` up or down by 10% using integer arithmetic. Once repeated high-compute-time events drive `max_packets` down through successive `Decrease` calls, integer division eventually rounds the value to `0`. From that point on, the `Increase` branch (`current.saturating_mul(100) / 90`) applied to `current = 0` always evaluates to `0`, so the threshold can never recover. This creates a permanent, one-way latch with no floor/circuit-breaker, matching the audited invariant violation.

### Finding Description
`DynamicPacketToProcessThreshold::update` in [1](#0-0)  only changes `max_packets` when `total_packets >= self.max_packets`, choosing `Decrease` when `compute_time > TIME_THRESHOLD` (1s) or `Increase` otherwise. Both operations are implemented via `PacketThresholdUpdate::calculate` using `saturating_mul`/`saturating_div` integer math: `Decrease` multiplies by 90 and divides by 100, `Increase` multiplies by 100 and divides by 90 [2](#0-1) .

Starting from `DEFAULT_MAX_PACKETS = 1024` [3](#0-2) , repeated `Decrease` events (attacker-induced batches whose processing consistently takes >1s while `total_packets >= max_packets`) shrink the value by ~10% each call. Because the divide truncates, the value eventually reaches `1`, and one more `Decrease` computes `1 * 90 / 100 = 0`, setting `max_packets = 0` permanently.

Once `max_packets == 0`:
- `should_drop(total)` in [4](#0-3)  returns `true` unconditionally, since `total: usize` is always `>= 0`. Every subsequent batch of ancestor-hashes responses is dropped.
- Even if `update` is still invoked afterward, the `Increase` branch computes `0.saturating_mul(100) / 90 = 0`, so the value can never rise back above `0`. There is no minimum floor, no reset timer, and no operator alert anywhere in this file.

`core/src/repair/ancestor_hashes_service.rs` constructs and drives this threshold inside the response-processing loop (confirmed via grep matches for `DynamicPacketToProcessThreshold`/`should_drop` in that file), gating whether incoming ancestor-hashes repair responses on the UDP response socket are processed or discarded. Because the socket receives unauthenticated UDP traffic, a remote unstaked attacker can send arbitrarily crafted/oversized response-shaped packets that are computationally expensive to parse/verify (e.g., large batches forcing `compute_time > 1s`), driving the threshold down over repeated iterations until it latches at `0`. From that point, the node silently drops 100% of ancestor-hashes repair responses forever, with no self-recovery — even after the attacker traffic stops — until the process is restarted.

I could not fully re-derive the exact surrounding loop code of `run_responses_listener` (call ordering of `should_drop`/`update`) within the tool budget available, but the arithmetic defect in `packet_threshold.rs` guarantees the zero-latch regardless of call ordering: either `update` is skipped once `should_drop` is true (common `continue`-on-drop pattern), or `update` is called but the `Increase` formula is a fixed point at `0`. Either way there is no code path that lifts `max_packets` off `0`.

### Impact Explanation
This is a persistent, silent, unbounded-duration denial of ancestor-hashes repair-response processing on the affected node — degrading the node's ability to detect/resolve duplicate-slot and dead-slot situations via ancestor-hashes repair, with no automatic recovery short of a process restart. This matches an availability/DoS-class finding scoped to a non-critical repair subsystem (not consensus-safety-critical, since it only silences a repair side-channel), but it violates the self-healing invariant explicitly targeted by the audit question.

### Likelihood Explanation
Preconditions: an unstaked remote attacker must send enough malformed/oversized UDP traffic to the ancestor-hashes repair response port to force `compute_time > 1s` repeatedly (~60-70 consecutive `Decrease` events, since 1024 × 0.9ⁿ trends to 0 by n≈65-70) while `total_packets >= max_packets` each time. This is a sustained-flood attack requiring no stake, no key material, and no cooperation from other validators — only raw packet volume/complexity — making it feasible for a single unprivileged remote client, though it requires sustained effort over many iterations of the listener loop.

### Recommendation
Enforce a non-zero floor for `max_packets` (e.g., clamp to a `MIN_MAX_PACKETS` constant greater than 0) in both `Decrease` and `Increase` calculations, and/or add a periodic reset-to-default policy independent of the multiplicative feedback so the threshold cannot become a fixed point at 0. Specifically fix the `Increase` calculation in `PacketThresholdUpdate::calculate` (and the assignment in `update`) to ensure `max_packets` is bounded below by a strictly positive minimum.

### Proof of Concept

```rust
// core/src/repair/packet_threshold.rs (add to `mod test`)
use super::DynamicPacketToProcessThreshold;
use std::time::Duration;

#[test]
fn test_max_packets_latches_at_zero_and_never_recovers() {
    let mut threshold = DynamicPacketToProcessThreshold::default();
    let slow = Duration::from_millis(2000); // > TIME_THRESHOLD
    let fast = Duration::from_millis(10);    // <= TIME_THRESHOLD

    // Drive max_packets down to 0 via repeated Decrease events.
    for _ in 0..200 {
        let total = threshold.max_packets_for_test(); // hypothetical accessor, or use should_drop probe
        threshold.update(total.max(1), slow);
        if threshold.max_packets_for_test() == 0 {
            break;
        }
    }
    assert_eq!(threshold.max_packets_for_test(), 0);

    // Simulate attacker traffic stopping entirely: no more high-compute batches,
    // only benign fast batches arrive going forward.
    for _ in 0..1000 {
        threshold.update(0, fast);
    }

    // Invariant violation: threshold never self-heals even with zero attacker traffic.
    assert_eq!(threshold.max_packets_for_test(), 0);
    assert!(threshold.should_drop(0)); // ALL future packets, including 0, are "dropped"
}
```
(Note: `max_packets` is private; a `#[cfg(test)]` accessor or `pub(crate)` getter would need to be added to observe the internal value directly, or the test can be written purely against `should_drop` behavior which is fully observable and sufficient to prove the permanent-drop-everything state.)

```rust
impl PacketThresholdUpdate {
    const PERCENTAGE: usize = 90;

    fn calculate(&self, current: usize) -> usize {
        match *self {
            PacketThresholdUpdate::Increase => {
                current.saturating_mul(100).saturating_div(Self::PERCENTAGE)
            }
            PacketThresholdUpdate::Decrease => {
                current.saturating_mul(Self::PERCENTAGE).saturating_div(100)
            }
        }
    }
}
```
