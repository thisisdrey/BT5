### Title
StackerDB chunk signatures are not bound to a specific contract, enabling cross-replica chunk replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` computes the signed digest for a StackerDB chunk from only `slot_id`, `slot_version`, and `data_hash` — it never includes the target StackerDB's `contract_id`. Because slot ownership (which address owns which `slot_id`) is frequently identical across multiple StackerDB replicas for the same signer set (e.g. `signers-0-0`, `signers-0-1`, … all derive their slot list from the same `signers.clar` per-cycle signer table), a chunk validly signed by a signer for one contract's slot can be replayed verbatim into a different contract's replica at the same `slot_id`, and the storage layer will accept and store/relay it as legitimate for that unrelated replica.

### Finding Description
The signature that authenticates a StackerDB chunk is computed here: [1](#0-0) 

This digest binds only `slot_id`, `slot_version`, and `data_hash` — never the `QualifiedContractIdentifier` of the StackerDB replica the chunk is destined for.

The write path that stores a chunk, `StackerDBTx::try_replace_chunk`, receives `smart_contract` purely to look up the expected signer address and current version for that particular DB, but the actual authenticity check is delegated to `slot_desc.verify(&slot_validation.signer)`, which uses the contract-agnostic digest above: [2](#0-1) 

The same pattern is repeated in the P2P validation path, `PeerNetwork::validate_received_chunk`, which also authenticates purely against `get_slot_signer(smart_contract_id, data.slot_id)` and `slot_metadata.verify(&addr)`, with no binding of the signature to `smart_contract_id`: [3](#0-2) 

And the HTTP write endpoint `RPCPostStackerDBChunkRequestHandler::try_handle_request` simply forwards the caller-supplied `contract_identifier` and `stackerdb_chunk` straight to `try_replace_chunk`: [4](#0-3) 

Crucially, the boot-contract signer sets that back the various `signers-0-{message_id}` / `signers-1-{message_id}` StackerDB replicas for a reward cycle share the *same, deterministically-ordered* slot assignment, since every message-id contract fetches slots from `signers.clar`'s `stackerdb-get-signer-slots-page`: [5](#0-4) 

This means a given signer address is assigned the *same* `slot_id` across every message-id replica for a cycle. Consequently, a signature that a signer legitimately produced for, say, `signers-0-1` (one message lane) recovers to the same address and satisfies `verify()` for the identical `slot_id` in `signers-0-0` (a different message lane), because the signed digest carries no contract binding. The lane/payload-type filtering that exists at the higher `libsigner` event-interpretation layer (`signer_message_payload_matches_lane` in `libsigner/src/events.rs`) is applied only when converting a `StackerDBChunksEvent` into a `SignerEvent`, not at the storage/relay layer — so the chunk is still accepted, stored, and gossiped as canonical data for the wrong replica before any such filtering happens.

This breaks the same class of equality that the referenced bug exploited: an authentication artifact (`chain_hash`/signature) that should be checked against the specific context it targets (`request.chain`/`contract_id`) is instead accepted as valid for any context sharing the other checked fields.

### Impact Explanation
A chunk that was authored for one StackerDB replica can be stored as valid content in a different replica's slot, as long as slot/version constraints happen to align. This is a network-observable acceptance of data into a StackerDB contract that was never actually authorized for that contract, and it will be replicated to other peers via `handle_unsolicited_StackerDBPushChunk` and `StackerDBSync`, serving cross-contract/forged-context data as canonical for that slot. This matches the "High" bar of serving non-canonical state as canonical / network propagation of forged data for a given replica.

### Likelihood Explanation
No forging of a signature is required — only replaying an already-existing, validly-signed chunk (from one lane) into another lane's endpoint. Any registered signer (an otherwise unprivileged network participant relative to any other StackerDB replica) can trigger this by resubmitting a chunk they legitimately authored elsewhere, provided the target slot's version is lower than the replayed chunk's version. This requires no admin role or node secret, and it is a remote, unauthenticated-relative-to-the-target-contract write.

### Recommendation
Include the target StackerDB `contract_id` (or a hash of it) in `SlotMetadata::auth_digest()` so that a chunk's signature is cryptographically bound to the specific replica it is intended for. This requires re-signing on the client side and updating `auth_digest`/`verify`/`sign` in `libstackerdb/src/libstackerdb.rs`, plus corresponding checks in `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs`) and `validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs`).

### Proof of Concept
1. Reward cycle N has boot StackerDB replicas `signers-0-0` (block-response lane) and `signers-0-1` (transaction lane), both populated from the same `signers.clar` slot table, so signer `S` owns `slot_id = 3` in both.
2. Signer `S` legitimately signs and posts chunk `C = (slot_id=3, slot_version=5, sig, data)` to `signers-0-1` via `POST /v2/stackerdb/.../signers-0-1/chunks`, which succeeds (`RPCPostStackerDBChunkRequestHandler` → `try_replace_chunk`).
3. An attacker (or `S` itself) resubmits the exact same `(slot_id, slot_version, sig, data)` tuple to `signers-0-0`'s endpoint instead. `try_replace_chunk` looks up `signers-0-0`'s slot 3 owner (also `S`), calls `slot_desc.verify(&S)`, which succeeds because `auth_digest()` never referenced `signers-0-1` vs `signers-0-0`.
4. Provided `signers-0-0`'s current slot-3 version is `< 5`, the chunk is stored and relayed as legitimate block-response-lane content, even though it was authored and intended for the transaction lane.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
