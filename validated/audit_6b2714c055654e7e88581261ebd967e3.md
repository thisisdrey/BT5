### Title
Unbounded `VotesStore` iteration in `MaintenanceManager.doMaintenance()` causes consensus-critical block-processing DoS - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
`MaintenanceManager.doMaintenance()`, invoked synchronously on every block that crosses a maintenance boundary, calls `countVote(votesStore)`, which does a full linear scan of the entire `VotesStore` [4](#0-3) . `VotesStore` gains one entry per distinct account address that casts a `VoteWitnessContract` (or TVM vote) transaction during the epoch, via `VoteWitnessActuator.countVoteAccount` / `VoteWitnessProcessor`, which is reachable by any unprivileged signed transaction from any funded account [5](#0-4) . There is no cap on the total number of distinct voter addresses across the network/epoch — only the per-transaction number of witnesses voted for is limited. An attacker can create a large number of accounts (cheap on TRON, just enough TRX to activate/freeze small resources) and issue one low-cost vote transaction per account, each of which persists an entry in `VotesStore`.

### Finding Description
This directly mirrors the reported bug class: an unbounded, permissionlessly-growable on-chain set (`activeProtectionIndexes` in the analog / `VotesStore` here) is fully iterated by core protocol logic (`_accurePremiumAndExpireProtection` in the analog / `countVote` here) with no batching or size limit. The critical difference that makes the java-tron instance more severe is that `countVote` runs as mandatory, synchronous, block-processing logic inside `Manager.processBlock` → `consensus.applyBlock` → `DposService.applyBlock` → `MaintenanceManager.applyBlock` → `doMaintenance` [1](#0-0) [2](#0-1) , not gas-metered actuator logic that merely fails one transaction. Every node (witness and full node) must execute this identical unbounded loop deterministically as part of consensus, once per maintenance cycle (default every 6 hours), with no escape hatch and no per-call resource limit — there is no "energy"/gas budget bounding this work the way there is for TVM execution.

### Impact Explanation
If the number of distinct voter addresses is driven large enough that a single maintenance pass takes excessive wall-clock time, all witness nodes stall identically at the same block boundary, since `doMaintenance()` must complete before block application, `pushBlock` return, and subsequent block production/validation can proceed [6](#0-5) . This can halt block production network-wide (a DoS of core chain functionality) rather than merely locking one dApp's funds, and because every node performs the identical scan, it does not create a chain split by itself but does create a synchronized processing stall across the network at the maintenance boundary.

### Likelihood Explanation
Casting a vote only requires TRON Power (frozen balance), and account creation/activation costs are low on TRON; an attacker with access to many keys and modest TRX can generate very large numbers of `VotesStore` entries over time by having many accounts vote once per epoch. Because `votesStore.delete(next.getKey())` clears entries at the end of each maintenance pass [7](#0-6) , the attacker must keep refreshing votes to sustain the effect, but the underlying design constraint — no bound on distinct voter count processed per cycle — remains unmitigated by any validate()-time check.

### Recommendation
Impose a cap on the number of entries processed by `countVote` per maintenance cycle (e.g., batch/paginate the `VotesStore` scan across multiple blocks, or track vote deltas incrementally per witness rather than re-deriving them from a full store scan), and/or bound how fast `VotesStore` can grow per epoch (e.g., limiting distinct new voter accounts processed, or requiring a minimum frozen balance for a vote to be persisted as a new entry rather than a no-op).

### Proof of Concept
1. Fund and activate a large number of distinct accounts with the minimum TRX needed to obtain nonzero TRON Power.
2. For each account, submit a `VoteWitnessContract` transaction voting for any active witness; each such transaction reaches `VoteWitnessActuator.countVoteAccount`, which calls `votesStore.put(ownerAddress, votesCapsule)` for a fresh key per account [8](#0-7) .
3. Repeat across enough accounts before the next maintenance boundary so that `VotesStore` contains a very large number of entries.
4. At the next maintenance boundary, `MaintenanceManager.doMaintenance()` → `countVote(votesStore)` must iterate every entry synchronously as part of `processBlock`/`applyBlock`, extending block-processing latency proportionally to the attacker-inflated store size [4](#0-3) .

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }
