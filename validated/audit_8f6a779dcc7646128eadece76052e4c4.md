### Title
Null Pointer Dereference in `UnDelegateResourceProcessor.execute()` when no unlocked delegated resource exists - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java`)

### Summary
`UnDelegateResourceProcessor.execute()`, the native-contract handler backing the TVM `unDelegateResource` precompile that any contract caller can invoke, fetches the owner-side `DelegatedResourceCapsule` for the "unlocked" key and immediately calls mutator methods on it inside a `switch` without a null check, unlike its sibling classes which guard against the same condition.

### Finding Description
In `execute()`: [1](#0-0) 
```
byte[] key = DelegatedResourceCapsule.createDbKeyV2(ownerAddress, receiverAddress, false);
DelegatedResourceCapsule delegatedResourceCapsule = repo.getDelegatedResource(key);
switch (param.getResourceType()) {
  case BANDWIDTH: {
    delegatedResourceCapsule.addFrozenBalanceForBandwidth(-unDelegateBalance, 0);
```
`repo.getDelegatedResource(key)` can legitimately return `null` when no unlocked delegated-resource record exists for the `(ownerAddress, receiverAddress)` pair (e.g. all delegated balance is still under the "lock" key, or nothing has ever been delegated between the two addresses). The method dereferences the result directly (`.addFrozenBalanceForBandwidth(...)` / `.addFrozenBalanceForEnergy(...)`) with no `null` guard, in contrast to:
- the sibling `DelegateResourceProcessor.delegateResource()`, which explicitly checks `if (delegatedResourceCapsule == null) { delegatedResourceCapsule = new DelegatedResourceCapsule(...); }` before using it: [2](#0-1) 
- the classic (non-TVM) `UnDelegateResourceActuator.execute()`, which first calls `delegatedResourceStore.unLockExpireResource(...)` to guarantee the unlock record is created/migrated before it is read and mutated: [3](#0-2) 

`UnDelegateResourceProcessor.execute()` performs no equivalent `unLockExpireResource` call before reading the "unlock" key, so the guarantee that record exists is not established for this code path.

This mirrors the structure of CVE-2022-49139: a handler assumes a companion object (`conn->link` in the kernel bug, `delegatedResourceCapsule` here) always exists for a given event/request type, but a specific state/type combination (LE link type in the kernel bug; "no unlocked delegation record" here) reaches the dereference without that guarantee, causing a null pointer dereference.

### Impact Explanation
If reachable, this throws an unhandled `NullPointerException` inside TVM contract execution when a smart contract calls the `unDelegateResource` precompile for an owner/receiver pair whose only existing `DelegatedResourceCapsule` is under the "locked" key (or none exists), causing that transaction path to fail with an uncaught runtime exception rather than a graceful `ContractValidateException`. Depending on how this propagates through block application in `Manager`, this ranges from a failed/execution-reverted transaction to a node crash, which the scope rules for this exercise treat as a Medium-severity node-crash class analog.

### Likelihood Explanation
I was unable to fully retrieve the `validate()` method of `UnDelegateResourceProcessor.java` (lines before 91) due to a tool access error, so I cannot confirm with certainty whether `validate()` in this file independently guarantees the unlock-key record exists before `execute()` runs. Given that the sibling `DelegateResourceProcessor` explicitly null-checks the same kind of capsule and the classic actuator explicitly calls `unLockExpireResource()` as a prerequisite (which `execute()` here omits), the missing guard appears to be a genuine inconsistency rather than an intentionally-proven invariant. This uncertainty should be resolved by inspecting the full file, in particular the validate() method, before treating this as fully confirmed.

### Recommendation
Add a null check on `delegatedResourceCapsule` in `UnDelegateResourceProcessor.execute()` (creating a new capsule or throwing a proper `ContractValidateException`/failing the call cleanly), and/or call `unLockExpireResource` prior to reading the unlock key, mirroring the classic `UnDelegateResourceActuator` behavior, to ensure the object referenced by the "unlock" `DelegatedResourceCapsule` key always exists before being mutated.

### Proof of Concept
1. From a TVM contract, call the `unDelegateResource` precompile (which invokes `UnDelegateResourceProcessor.execute()`) for a receiver address that has never received a delegation, or one where all existing delegation is stored only under the locked key (`createDbKeyV2(..., true)`), never migrated to the unlocked key.
2. `repo.getDelegatedResource(key)` for the unlocked key returns `null`.
3. `delegatedResourceCapsule.addFrozenBalanceForBandwidth(...)` throws `NullPointerException` inside the contract-execution path.

Note: due to indexing limits I could not retrieve the `validate()` method body of this file to fully confirm whether it independently blocks this state; a Devin session with full file access is recommended to verify this before treating the finding as fully proven.
