### Title
Permissionless donation to a nomination pool's reward account can brick `join`/`bond_extra`/`unbond`/`claim_payout` for the whole pool, locking members' funds - ([File: substrate/frame/nomination-pools/src/lib.rs])

### Summary
The external report's core broken invariant is: a critical, safety-relevant operation (`executeBid`, health check) performs an unchecked arithmetic/precondition computation over mutable state that an unprivileged third party can perturb via a permissionless, low-cost transfer, causing the operation to revert and blocking the protocol's essential process (liquidation). The local analog is `pallet-nomination-pools`'s reward-accounting math: `RewardPool::current_reward_counter` divides an externally-influenced balance (`RewardPool::current_balance`, which is simply the raw `Balances` balance of a deterministically-derived, publicly-known account) by `bonded_points`, and returns `Error::OverflowRisk` on overflow instead of saturating. Because `current_balance` is fed directly from a plain account balance that *anyone* can top up with an ordinary `balances::transfer_keep_alive`, an attacker can donate funds to a pool's reward account to force this division to overflow, which then makes every pool operation that calls `update_records`/`current_reward_counter`/`do_reward_payout` (`join`, `bond_extra`, `unbond`, `claim_payout`, pool creation flows, etc.) fail with `OverflowRisk`, permanently DoS'ing the pool and locking members' bonded and reward funds inside it.

### Finding Description
`RewardPool::current_balance` reads the *raw* free/reducible balance of the pool's reward account: [1](#0-0) 

The reward account is deterministically derived from the pool id and is fully public/computable by anyone: [2](#0-1) 

Nothing prevents an outside, non-member account from sending an ordinary `Balances::transfer_keep_alive` (or `transfer_allow_death`) directly to this account — no membership, no allowance, no permission is required, exactly like the report's "1 WEI transfer to bidder" primitive.

That balance is then used, together with `bonded_points`, in `current_reward_counter`, which performs a `checked_from_rational(new_pending_rewards, bonded_points)` and treats an overflow as a hard error rather than saturating: [3](#0-2) 

`current_reward_counter` is invoked from `update_records`, which itself is called on essentially every pool-mutating extrinsic (`join`, `bond_extra`, `unbond`) before any other state change is committed, and from `do_reward_payout`, which is invoked whenever a member claims rewards or unbonds: [4](#0-3) [5](#0-4) 

If the numerator (`current_payout_balance`, driven by the attacker-inflated reward-account balance) divided by `bonded_points` exceeds what `FixedU128`/`RewardCounter` can represent (`checked_from_rational` fails when `numerator * 10^18` overflows `u128`), the function returns `Err(Error::<T>::OverflowRisk)`. Because pools with small `bonded_points` (e.g. newly created pools, or pools whose stake has been heavily slashed — a state the pallet explicitly anticipates, see `balance_to_point`'s "pool was totally slashed" branch) require only a comparatively small donated balance to push the ratio past the overflow threshold, this is not a purely theoretical, "billions of DOT" scenario for pools with low bonded points.

This is the direct structural analog of DRV-03: an attacker-influenced value (here, a donated balance instead of a zero/degenerate SVI parameter) flows unchecked into a division used by a safety-critical accounting routine, and the resulting hard failure (`OverflowRisk`/panic-style revert) blocks the "liquidation"-equivalent operations — here, `unbond` and `claim_payout`, which are the *only* ways members can ever get their bonded balance and rewards out of the pool.

### Impact Explanation
Once a pool's reward account is griefed into permanent overflow:
- `join` and `bond_extra` fail (`update_records` errors before any funds move), preventing new stake from ever entering the pool.
- `unbond` and `claim_payout` fail (`do_reward_payout`/`update_records` errors), so existing members cannot withdraw their bonded stake or accrued rewards.
- The pool becomes permanently bricked with member funds locked inside it, with no signed extrinsic path to recover, matching the "permanent user-fund lock" criterion of the impact gate. Depositors' funds (and, transitively, the corresponding nominated stake on the relay/staking side) become unusable, and no privileged/governance actor is required to trigger the condition — only a signed account making an ordinary transfer.

### Likelihood Explanation
The precondition is a single unprivileged `balances::transfer` extrinsic to a publicly-computable account (`generate_reward_account(pool_id)`). No governance, no relayer, no validator, and no leaked key is required — this is exactly the "public underpriced work"/permissionless-griefing shape the impact gate targets. The attack is cheapest against newly-created or heavily slashed pools where `bonded_points` is small relative to the required overflow threshold, which are realistic, naturally occurring pool states (the pallet's own doc comments describe "a pool that has been slashed" as an expected condition).

### Recommendation
- In `RewardPool::current_reward_counter` / `current_balance`, do not let an externally-donated balance directly participate in overflow-sensitive arithmetic. Either:
  - Track only the pool's *known* contributed balance (rewards it itself deposited/received via legitimate accounting), ignoring/quarantining unsolicited transfers, similar to how `pallet-balances`/`pallet-assets` handle unexpected/dust deposits, or
  - Replace `checked_from_rational(...).ok_or(Error::OverflowRisk)` with a saturating computation (`saturating_from_rational`) so that an inflated numerator degrades to a maximal-but-still-valid reward counter instead of hard-failing every subsequent pool operation.
- Add a periodic/`on_idle` sweep (or an explicit privileged/anyone-callable "skim excess" extrinsic) that removes balance in the reward account beyond what accounting expects, before it can affect `current_reward_counter`.
- Add regression tests that directly transfer large balances into a pool's reward account (bypassing `join`) and assert that `join`, `bond_extra`, `unbond`, and `claim_payout` remain functional afterward.

### Proof of Concept
1. Create a nomination pool with the minimum allowed bond (small `bonded_points`), e.g. via `Pools::create`/`Pools::join` with `amount = depositor_min_bond()`.
2. Compute the pool's reward account address off-chain: `generate_reward_account(pool_id)` (`AccountType::Reward` sub-account of `PalletId`).
3. From any unrelated, unprivileged signed account, call `Balances::transfer_keep_alive(reward_account, X)` where `X` is chosen so that `X * 10^18 / bonded_points > u128::MAX` (achievable with a comparatively modest `X` when `bonded_points` is small, e.g. at the pool's minimum bond).
4. Call `Pools::bond_extra` or `Pools::unbond` for the depositor: the call fails with `Error::<T>::OverflowRisk` inside `update_records`/`do_reward_payout`, even though the caller supplied valid inputs.
5. Repeat with `Pools::join` from a different account: it also fails with the same error, confirming the pool is now permanently un-joinable and un-unbondable, with the original depositor's bonded funds and reward account balance stuck.

(Note: exact numeric feasibility of the overflow depends on the runtime's `RewardCounter`/`Balance` types and the pool's live `bonded_points`; this was not executed against a live node/test harness in this session, so the precise donation amount required should be confirmed with a concrete runtime configuration before treating this as fully verified in production parameters.)

	/// Get the current reward counter, based on the given `bonded_points` being the state of the
	/// bonded pool at this time.
	fn current_reward_counter(
		&self,
		id: PoolId,
		bonded_points: BalanceOf<T>,
		commission: Perbill,
	) -> Result<(T::RewardCounter, BalanceOf<T>), Error<T>> {
		let balance = Self::current_balance(id);

		// Calculate the current payout balance. The first 3 values of this calculation added
		// together represent what the balance would be if no payouts were made. The
		// `last_recorded_total_payouts` is then subtracted from this value to cancel out previously
		// recorded payouts, leaving only the remaining payouts that have not been claimed.
		let current_payout_balance = balance
			.saturating_add(self.total_rewards_claimed)
			.saturating_add(self.total_commission_claimed)
			.saturating_sub(self.last_recorded_total_payouts);

		// Split the `current_payout_balance` into claimable rewards and claimable commission
		// according to the current commission rate.
		let new_pending_commission = commission * current_payout_balance;
		let new_pending_rewards = current_payout_balance.saturating_sub(new_pending_commission);

		// * accuracy notes regarding the multiplication in `checked_from_rational`:
		// `current_payout_balance` is a subset of the total_issuance at the very worse.
		// `bonded_points` are similarly, in a non-slashed pool, have the same granularity as
		// balance, and are thus below within the range of total_issuance. In the worse case
		// scenario, for `saturating_from_rational`, we have:
		//
		// dot_total_issuance * 10^18 / `minJoinBond`
		//
		// assuming `MinJoinBond == ED`
		//
		// dot_total_issuance * 10^18 / 10^10 = dot_total_issuance * 10^8
		//
		// which, with the current numbers, is a miniscule fraction of the u128 capacity.
		//
		// Thus, adding two values of type reward counter should be safe for ages in a chain like
		// Polkadot. The important note here is that `reward_pool.last_recorded_reward_counter` only
		// ever accumulates, but its semantics imply that it is less than total_issuance, when
		// represented as `FixedU128`, which means it is less than `total_issuance * 10^18`.
		//
		// * accuracy notes regarding `checked_from_rational` collapsing to zero, meaning that no
		//   reward can be claimed:
		//
		// largest `bonded_points`, such that the reward counter is non-zero, with `FixedU128` will
		// be when the payout is being computed. This essentially means `payout/bonded_points` needs
		// to be more than 1/1^18. Thus, assuming that `bonded_points` will always be less than `10
		// * dot_total_issuance`, if the reward_counter is the smallest possible value, the value of
		//   the
		// reward being calculated is:
		//
		// x / 10^20 = 1/ 10^18
		//
		// x = 100
		//
		// which is basically 10^-8 DOTs. See `smallest_claimable_reward` for an example of this.
		let current_reward_counter =
			T::RewardCounter::checked_from_rational(new_pending_rewards, bonded_points)
				.and_then(|ref r| self.last_recorded_reward_counter.checked_add(r))
				.ok_or(Error::<T>::OverflowRisk)?;

		Ok((current_reward_counter, new_pending_commission))
	}

	fn do_reward_payout(
		member_account: &T::AccountId,
		member: &mut PoolMember<T>,
		bonded_pool: &mut BondedPool<T>,
		reward_pool: &mut RewardPool<T>,
	) -> Result<BalanceOf<T>, DispatchError> {
		debug_assert_eq!(member.pool_id, bonded_pool.id);
		debug_assert_eq!(&mut PoolMembers::<T>::get(member_account).unwrap(), member);

		// a member who has no skin in the game anymore cannot claim any rewards.
		ensure!(!member.active_points().is_zero(), Error::<T>::FullyUnbonding);

			bonded_pool.id,
			bonded_pool.points,

		)?;

		// Determine the pending rewards. In scenarios where commission is 100%, `pending_rewards`
		// will be zero.
