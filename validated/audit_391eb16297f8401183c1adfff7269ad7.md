## Finding [1](#0-0) 

### Title
Missing SSH-signature namespace/domain validation allows cross-context signature reuse in `SSHSigningKey.Verify` - (File: internal/signature/ssh.go)

### Summary
Gitaly implements its own, partial version of the OpenSSH `SSHSIG` signature format (`internal/signature/ssh.go`) instead of relying on a vetted library/CLI (`ssh-keygen -Y verify`) that enforces all protocol invariants. In `Verify`, the "namespace" and "hash algorithm" fields — which exist in the SSHSIG protocol precisely to provide domain separation between different signature use-cases — are taken directly from the attacker-supplied signature blob and copied back into the structure that is cryptographically checked, instead of being validated against the fixed values Gitaly itself uses when creating a signature (`namespace = "git"`, `hashAlgorithm = "sha512"`).

### Finding Description
`SSHSigningKey.CreateSignature` signs a `signedData` struct that always uses the hardcoded constants `magicHeader`, `namespace = "git"`, and `hashAlgorithm = "sha512"`: [2](#0-1) 

However, `SSHSigningKey.Verify` reconstructs the `signedData` to check using values pulled straight from the **caller-supplied** signature (`sshSig.MagicHeader`, `sshSig.Namespace`, `sshSig.HashAlgorithm`), not the constants used at signing time: [3](#0-2) 

Because the field content is attacker-controlled and gets echoed straight back into the exact byte-blob (`ssh.Marshal(signedData)`) that is verified against `sk.PrivateKey.PublicKey()`, the namespace check — the entire purpose of which in the OpenSSH SSHSIG spec is to prevent a signature produced for one context (e.g. file signing, host authentication, or any other consumer of the same SSH key) from being replayed as a valid signature in a different context (here, "this commit was signed by Gitaly's system signing key") — is never enforced. Gitaly's custom implementation is a partial re-implementation of the SSHSIG scheme rather than delegating to the standard, audited primitive that performs this comparison (`ssh-keygen -Y verify -n <namespace>`), exactly mirroring the report's underlying bug class: a hand-rolled signing/verification mechanism omitting a critical protocol/domain-separation field, "more dangerous" than the standard implementation.

### Impact Explanation
This verification result directly drives the `Signer` field returned by the `GetCommitSignatures` RPC — determining whether a commit is reported as `SIGNER_SYSTEM` (i.e., cryptographically signed by Gitaly's own configured signing key) or `SIGNER_USER`: [4](#0-3) 

If Gitaly's configured SSH signing key is ever used to produce any other SSHSIG-format signature under a different namespace (a realistic scenario since SSH keys are frequently reused across systems, and `SigningKeys.PublicKey()` is exposed for verification purposes), an attacker who can push arbitrary commit objects (an ordinary, unprivileged push writes arbitrary bytes into the commit's `gpgsig` header field) can attempt to craft a commit whose `gpgsig` blob embeds a namespace/algorithm string chosen so that the reconstructed `signedData` bytes match one that was legitimately signed for a different purpose, thereby forging the "signed by Gitaly's system key" classification for attacker-chosen commit content. This misleads any downstream trust decision built on this classification (e.g., a "Verified"/"signed by GitLab" indicator).

### Likelihood Explanation
Exploitation requires the attacker to already possess, or be able to obtain, a valid SSHSIG signature produced by the Gitaly signing key for some other namespace/content (cross-protocol signature reuse), which is not always trivial to obtain, so likelihood is moderate rather than high. However, the root cause — omission of the namespace check that the SSHSIG format was specifically designed to require — is unambiguous and unconditionally reachable via the standard `GetCommitSignatures` RPC available to any client with repository access, using only an ordinary crafted commit/push.

### Recommendation
In `SSHSigningKey.Verify`, reject the signature unless `sshSig.Namespace == namespace` ("git"), `sshSig.MagicHeader == magicHeader`, and `sshSig.HashAlgorithm` matches an allow-listed value, before reconstructing `signedData` for cryptographic verification — mirroring the checks performed by `ssh-keygen -Y verify -n git`. More broadly, consider replacing this hand-written partial SSHSIG implementation with calls to the well-tested `ssh-keygen -Y sign/verify` tooling (as the original report recommends using battle-tested EIP-712 libraries instead of a custom implementation).

### Proof of Concept
1. Configure Gitaly with an SSH signing key (`Git.SigningKey`) that is also used elsewhere to produce SSHSIG signatures under a namespace other than `"git"` (e.g., a file-signing use of the same key).
2. Obtain a legitimately produced SSHSIG signature `S` from that other context whose `Hash` field equals `sha512(desiredCommitPayload)` (attacker controls the commit payload to try to match, or brute-forces small variations).
3. Construct a commit object with `desiredCommitPayload` as content and `S` embedded as the `gpgsig` header (any ordinary git push can set the raw signature header).
4. Call `GetCommitSignaturesRequest` for that commit; because `Verify` copies `sshSig.Namespace`/`sshSig.HashAlgorithm` from `S` rather than enforcing `"git"`/`"sha512"`, the reconstructed `signedData` matches what was actually signed and `Verify` returns `nil`, causing the response to report `Signer: SIGNER_SYSTEM` for attacker-chosen commit content.

// Verify method verifies whether a signature has been created by this signing key
func (sk *SSHSigningKey) Verify(signatureText, signedText []byte) error {
	block, rest := pem.Decode(signatureText)
	if block == nil || len(rest) > 0 || block.Type != sshSignatureType {
		return fmt.Errorf("invalid signature text")
	}

	sshSig := &sshSignature{}
	if err := ssh.Unmarshal(block.Bytes, sshSig); err != nil {
		return fmt.Errorf("parse signature text: %w", err)
	}

	signature := &ssh.Signature{}
	if err := ssh.Unmarshal(sshSig.Signature, signature); err != nil {
		return fmt.Errorf("parse signature: %w", err)
	}

	h := sha512.New()
	if _, err := h.Write(signedText); err != nil {
		return fmt.Errorf("failed to create sha for verifying content: %w", err)
	}

	signedData := signedData{
		MagicHeader:   sshSig.MagicHeader,
		Namespace:     sshSig.Namespace,
		HashAlgorithm: sshSig.HashAlgorithm,
		Hash:          h.Sum(nil),
	}

	return sk.PrivateKey.PublicKey().Verify(ssh.Marshal(signedData), signature)
