### Title
Unbounded array allocation from attacker-controlled length words in TVM precompiled-contract input parsers - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts` contains several helper parsers (`extractBytes32Array`, `extractBytesArray`, `extractSigArray`) that read a 32-byte "count" word directly out of attacker-supplied precompiled-contract call data and immediately allocate a Java array of that size — before validating the value against the actual size of the input data. This mirrors the russh bug class described in the advisory: a length-prefixed field is decoded into an owned allocation before the parser checks that the declared length is consistent with the bounded input it was extracted from.

### Finding Description
`extractBytesArray` and its siblings take an attacker-controlled `DataWord[] words` (derived from the calldata passed to a precompiled contract) and do: [1](#0-0) 

```
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
for (int i = 0; i < len; i++) { ... }
```

`len` is read straight from a single 32-byte word supplied in the transaction's contract call data via `DataWord.intValueSafe()` — the only clamp applied is to the range of a signed 32-bit int, not to the actual remaining length of `words`/`data`. The same pattern appears in the sibling helpers: [2](#0-1) [3](#0-2) 

`new byte[len][]` (or `new byte[len][32]`) allocates an owned Java array using the attacker-supplied `len` before any bound check against `words.length` is performed — only after the array is allocated does the per-element loop dereference `words[offset + i + 1]`, at which point a value of `len` larger than the actual `words` array throws `ArrayIndexOutOfBoundsException` (i.e., the same "accept the length prefix, allocate, and only fail later" shape called out in the advisory, where the vulnerable code returns a late/`SshEncoding(Length)`-style error instead of an early bounded rejection). A `len` value near `Integer.MAX_VALUE` (easily encoded as a single 32-byte word in calldata) can force allocation of a multi-gigabyte reference array (each element is an 8-byte object reference on a 64-bit JVM, so `len = 2^31-1` alone requests ~17 GB) purely from a tiny amount of transaction calldata, well before any energy-based cost has been charged for that size.

These parsers are used by the batch/multi-signature validation precompiled contracts (grep confirms `extractBytes*` usage is tied to the `BatchValidateSign`/`ValidateMultiSign` precompile family in this file), which are precompiled contracts directly callable by any TRC20/TVM `CALL` from a `TriggerSmartContract` transaction — i.e., reachable by any unprivileged account, not requiring any special permission. I was not able to fully re-confirm the exact call site inside `BatchValidateSign.execute()`/`ValidateMultiSign.execute()` due to tool-call limits in this session, so the precise energy cost accounting at the call site should be re-verified before treating this as fully proven, but the vulnerable allocation-before-bound pattern in the shared helper functions is directly confirmed.

### Impact Explanation
A crafted `TriggerSmartContract` transaction that calls a precompiled contract using these helpers with a single large length word can force the node's JVM to attempt an enormous array allocation while processing ordinary transaction execution (validate/execute path of an actuator, which every full node must run to apply blocks). This can throw `OutOfMemoryError` inside VM execution; depending on whether that error is caught cleanly at every call frame between the precompile and the top-level block-application code in `Manager`, this can crash or destabilize the node process for all nodes replaying the transaction, which is a shared, deterministic execution path — every validating node would hit the same failure on the same block, giving a credible node-crash/halt scenario rather than a resource-only nuisance.

### Likelihood Explanation
The precompiled contracts in question are reachable via a plain smart-contract call from any account holding minimal TRX/energy — no special role, signature type, or witness/SR privilege is required. Because `len` is attacker-controlled and validated only after the allocation attempt, exploitation requires no more than crafting the calldata word to a large integer value, which is trivial.

### Recommendation
Bound `len` against the remaining `words.length` (and a sane maximum element count derived from `data.length`) before calling `new byte[len][]`/`new byte[len][32]`, mirroring the "borrowed bounded parsing" fix pattern in the advisory (`take_bytes`/`take_name_list`): validate `offset + len` against `words.length` first, and reject with a fast, bounded error before any allocation.

### Proof of Concept
Not independently executed in this session (no runtime/tool access here), but conceptually: submit a `TriggerSmartContract` transaction calling the batch-signature-validation precompile address with a calldata array whose length-declaring word (the word read via `words[offset].intValueSafe()`) is set to a very large value (e.g., close to `Integer.MAX_VALUE`) while the remainder of calldata is short/absent. This drives `extractBytesArray`/`extractBytes32Array`/`extractSigArray` to attempt an array allocation sized by the attacker-chosen `len` before validating it against the actual calldata length.
