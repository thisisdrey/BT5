## Analysis

The kernel bug masks an externally supplied value (`sub_auth[2]`) into `cf_mode` without restricting it to the valid `07777` range before it is used in permission logic. The reachable analog in java-tron is the multisig "operations" bitmap check, where an externally-controlled contract `type` value is used, unmasked/unbounded, as a byte offset into a fixed-size 32-byte bitmap.

### Title
Unvalidated contract type value used as byte-array index in permission operations check causes uncaught crash - ([File: chainbase/src/main/java/org/tron/common/utils/WalletUtil.java])

### Summary
`checkPermissionOperations()` (duplicated in `WalletUtil`, `TransactionUtil`, and inlined in `TransactionCapsule`) reads `contract.getTypeValue()` — the raw, unmasked `int32` value of the transaction's `Contract.type` field — and uses it directly to index into a fixed 32-byte `operations` `ByteString` via `operations.byteAt(contractType / 8)`. Because protobuf3 enum fields preserve arbitrary wire values (even ones outside the declared `ContractType` enum), an attacker fully controls this integer and can drive `contractType / 8` outside `[0, 31]`, triggering an `IndexOutOfBoundsException`. [1](#0-0) [2](#0-1) 

### Finding Description
`Permission.operations` is documented as a 32-byte bitmap ("1 bit 1 contract") with values only defined for the currently known `ContractType` enumerators (max index ~50, well under the theoretical 256-bit capacity): [3](#0-2) 

`checkPermissionOperations` never bounds-checks `contractType` before dividing/moduloing it and indexing the bitmap:
```
int contractType = contract.getTypeValue();
boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
``` [4](#0-3) 

This check is invoked from the core signature-validation path used for every transaction with a non-zero `permission_id` (i.e. any multisig "Active" permission use), both for the broadcast path and for block application:
- `TransactionCapsule.checkPermission` → `TransactionCapsule.validateSignature` → `TransactionCapsule.validatePubSignature`, which only catches `SignatureException | PermissionException | SignatureFormatException` — **not** `RuntimeException`/`IndexOutOfBoundsException`: [5](#0-4) [6](#0-5) 

- `Manager.pushTransaction` calls `trx.validateSignature(...)` directly, with no catch for unchecked exceptions before it propagates: [7](#0-6) 

- `Manager.processTransaction`, invoked for every transaction inside `processBlock` while applying a block, calls the same unguarded signature validation: [8](#0-7) 

`Wallet.getTransactionSignWeight` and `Wallet.getTransactionApprovedList` (HTTP/gRPC query endpoints) invoke the identical unbounded logic directly on attacker-supplied, unsigned/unbroadcast transaction data: [9](#0-8) [10](#0-9) 

The `Contract.type` field is stored internally as a plain `int32` on the wire; protobuf3 preserves unrecognized enum values for retrieval via `getTypeValue()`, so a value like `1000` or a negative number can be embedded in a syntactically valid transaction and survive parsing.

### Impact Explanation
Any account holder can self-configure an "Active" permission with a valid 32-byte `operations` bitmap via `AccountPermissionUpdateContract` (a normal, unprivileged operation): [11](#0-10) 

The attacker can then submit a transaction that (a) sets `permission_id` to that Active permission's id (non-zero) and (b) sets the raw `Contract.type` field to an out-of-range integer (e.g., `>= 256` or negative). When any node validates the transaction's signature — via `broadcastTransaction`, `pushTransaction`, or while applying the transaction inside `processBlock`/`processTransaction` — `checkPermissionOperations` throws an uncaught `IndexOutOfBoundsException`. In the block-application path this is not defensively caught before it can disrupt block processing, which the scan rules classify as a valid "node crash or halt" impact. The same crash is also directly reachable through the unauthenticated HTTP/gRPC `gettransactionsignweight` / `gettransactionapprovedlist` query APIs without even broadcasting the transaction.

### Likelihood Explanation
High. No special privilege, staking, or witness status is required — only a self-owned account with a normal multisig "Active" permission (trivially obtainable by any account), and one crafted raw transaction with an out-of-range `type` field value. The vulnerable code is exercised on every full node during ordinary transaction/block validation.

### Recommendation
Bound-check `contractType` in `checkPermissionOperations` (and its duplicates in `TransactionCapsule`, `WalletUtil`, and `TransactionUtil`) before using it to index the 32-byte `operations` bitmap — e.g., reject/return `false` for any `contractType` outside `[0, operations.size() * 8 - 1]`, mirroring the masking fix in the referenced CVE. Consolidate the duplicated logic into a single validated helper to avoid divergent fixes.

### Proof of Concept
1. Attacker account `A` calls `AccountPermissionUpdateContract` to add itself an "Active" permission with `id = 2` and a valid 32-byte `operations` bitmap.
2. Attacker crafts a `Transaction` whose `raw_data.contract[0]` has:
   - `permission_id = 2`
   - `type` field's raw wire value set to an out-of-range integer (e.g. `1000` or `-1`), while `parameter` holds any `Any`-packed payload.
3. Attacker signs with a key satisfying the Active permission's threshold and submits via `broadcastTransaction` or the `gettransactionsignweight` HTTP/gRPC endpoint.
4. `checkPermissionOperations` computes `operations.byteAt(1000 / 8)` (index 125, out of the 32-byte array), throwing `IndexOutOfBoundsException`, uncaught by `validatePubSignature`/`validateSignature`, propagating into `Manager.pushTransaction`/`processTransaction` or the query-servlet code path.
