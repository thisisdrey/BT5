### Title
Crafted relative path resolving to the storage root can cause `repoutil.Remove` to delete an entire storage - ([File: internal/gitaly/repoutil/remove.go])

### Summary
The Sherlock bug's root cause is that `reclaimContract()` computes a target address (`bulls[contractId]`) from a `contractId` that is fully attacker-controlled (a hash of a fabricated, never-matched order), and then transfers funds to that resolved-but-never-validated target because the only guards checked are `expiry`, `settledContracts`, and `reclaimedContracts` — none of which verify that the target was ever legitimately established. The generalizable bug class is: **an attacker-controlled identifier is resolved into a target used for a sensitive, destructive operation, while the validation logic checks only ancillary state flags and never verifies that the resolved target is the intended, legitimately-created one.**

In Gitaly, the analogous path-resolution primitive is `storage.ValidateRelativePath`, which cleans a caller-supplied `RelativePath` field of a `Repository` message and is used throughout the storage layer (including `repoutil.Remove`) to compute the on-disk target of destructive operations.

### Finding Description
`storage.ValidateRelativePath` is documented to reject paths that escape the storage root, but a relative path that resolves to the storage root itself (e.g. `"subfolder/.."`, or more generally `"<anything>/.."` sequences that cancel out to the root) is explicitly accepted and returned as `"."`, with `nil` error: [1](#0-0) 

This means a `Repository{StorageName: ..., RelativePath: "foo/.."}` (or similar attacker-crafted value) is a "valid" relative path per this function, and it resolves to the storage root directory rather than to any specific repository.

`configLocator.ValidateRepository` only rejects a **completely empty** relative path (`ErrRepositoryPathNotSet`); it does not reject a relative path that cleans to `"."` (the storage root): [2](#0-1) 

Critically, when `ValidateRepository`/`GetRepoPath` is called with `storage.WithSkipRepositoryExistenceCheck()` / `storage.WithRepositoryVerificationSkipped()` — which is exactly how `repoutil.Remove` calls it — the "is this an actual Git directory" check (`storage.ValidateGitDirectory`) is skipped entirely: [3](#0-2) 

`repoutil.remove()` (used by `RemoveRepository`) computes its target path with exactly this skip option: [4](#0-3) 

It then only checks that the resolved `path` exists via `os.Stat` (which the storage root trivially satisfies), locks it, renames it into a temp directory, and removes it: [5](#0-4) 

Because a crafted `RelativePath` such as `"x/.."` cleans to `"."` and passes both `ValidateRelativePath` and the (existence-check-skipped) `ValidateRepository`, the resolved `path` returned by `GetRepoPath` becomes the storage root itself instead of a specific repository directory — directly mirroring the `bulls[contractId] == address(0)` situation, where an insufficiently-validated resolved target (storage root / zero address) is used for a destructive/irreversible operation (deleting a directory tree / transferring funds).

### Impact Explanation
If reachable, this allows an ordinary caller of `RemoveRepository` (or any other RPC that resolves a repository path via `GetRepoPath` with repository-existence verification skipped, and does not separately re-validate that the resolved path is a specific, individual repository) to have Gitaly rename/move the **entire storage root** into a temporary directory and delete it — a catastrophic, storage-wide data-loss event, analogous in severity to "funds transferred to address(0)".

### Likelihood Explanation
Reachability depends on whether upstream authorization/routing (e.g. Praefect's repository-existence lookups, or gRPC-level repository resolution) rejects a `RelativePath` of `"x/.."` before it reaches `repoutil.Remove`, and whether any additional interceptor re-validates that the computed path is a genuine Git directory before the rename/delete occurs. I was not able to fully trace the `RemoveRepository` gRPC handler (`internal/gitaly/service/repository/remove.go`) or Praefect's request-routing/repository-existence checks in the available iterations — this is exactly the "concrete storage escape" / "argument-injection" class the review criteria are targeting, but I could not confirm end-to-end reachability from an *ordinary* user's RPC call without further inspection of the gRPC handler and the Praefect router. This should be verified with direct code access before treating it as a confirmed finding.

### Recommendation
- In `storage.ValidateRelativePath`/`configLocator.ValidateRepository`, explicitly reject a relative path that cleans to `"."` (the storage root) for any repository-scoped operation — a `Repository` message must always resolve to a path strictly inside the storage root, never to the root itself.
- In `repoutil.Remove` (and any other destructive path resolved via `GetRepoPath` with verification skipped), add an explicit check that the resolved relative path is non-trivial (`!= "."`, non-empty) before performing `os.Stat`/rename/delete, mirroring the recommended fix of checking `bulls[contractId] != address(0)` before transferring.

### Proof of Concept
1. As an ordinary Gitaly/Praefect client, call `RemoveRepository` with a `Repository` message such as:
   `{StorageName: "default", RelativePath: "some-existing-dir/.."}`
2. `storage.ValidateRelativePath("<storage_root>", "some-existing-dir/..")` cleans this to `"."` and returns no error (as demonstrated by the existing test case `{"subfolder/..", ".", nil}`) — [1](#0-0) .
3. `repoutil.remove()` calls `locator.GetRepoPath(ctx, repository, storage.WithRepositoryVerificationSkipped())`, which skips the Git-directory validation and returns `path == storagePath` — [4](#0-3) .
4. `os.Stat(path)` succeeds (the storage root always exists), so removal proceeds to lock, rename, and delete the storage root directory — [5](#0-4) .

I could not verify within the available tool budget whether an upstream layer (gRPC service handler, Praefect router) blocks this specific `RelativePath` value before it reaches `repoutil.Remove`; confirming full reachability requires reading `internal/gitaly/service/repository/remove.go` and the Praefect repository-routing code, which I was unable to retrieve in this session.
