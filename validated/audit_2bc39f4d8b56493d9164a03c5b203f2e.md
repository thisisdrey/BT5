## Title
Permanent freeze of an ETH-implicit account via un-resettable `has_in_flight_tx` flag in the wallet contract's relayer-ban path - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` used by every ETH-implicit account gates *all* execution behind a single boolean, `has_in_flight_tx`, which is only cleared inside specific callback methods. One of the paths that is supposed to clear it — the "ban a faulty relayer" batch — bundles `DeleteKey` and the state-clearing `FunctionCall("ban_relayer")` into the **same** receipt. Because NEAR aborts an entire receipt atomically the instant any one of its actions fails, if `DeleteKey` fails, `ban_relayer` never runs, `has_in_flight_tx` is never reset, and it is never cleared again by any other code path. This is the same bug class as the reported presale issue: a precondition (`balance == 0` there, `has_in_flight_tx == false` here) is required for further progress, but the code path that is supposed to satisfy/clear that precondition can itself fail, leaving the system permanently stuck.

### Finding Description
`rlp_execute` refuses to do anything while `has_in_flight_tx` is `true`, and it is the *only* entry point for interacting with an ETH-implicit account's funds: [1](#0-0) 

`has_in_flight_tx` is documented as an invariant that must be `true` exactly while a promise is outstanding, and `false` otherwise: [2](#0-1) 

It is reset to `false` only inside `address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, and `ban_relayer`: [3](#0-2) 

When a relayer misbehaves (`Error::Relayer`) and is itself the account's own signer (i.e. it holds a `FunctionCall`-restricted access key added directly to the wallet, exactly as demonstrated in `wallet_contract_interaction` where the relayer's key is later used to sign `rlp_execute` calls directly for the eth-implicit account), the contract dispatches a *single* receipt containing two batched actions — `DeleteKey` followed by `FunctionCall("ban_relayer")` — via `create_ban_relayer_promise`: [4](#0-3) [5](#0-4) 

`has_in_flight_tx = true` is committed as soon as this promise is returned (this commit happens at the end of the *first* receipt, independent of whether the batched receipt later succeeds). The runtime's receipt-execution model guarantees that if any action within a receipt fails, the whole receipt is aborted and rolled back, with only the failing action's index recorded — later actions in that receipt (here, `ban_relayer`) never execute: [6](#0-5) 

This "stop the loop on first failure" and "failed receipt atomicity → rollback" behavior is explicitly documented: [7](#0-6) 

and is exercised by an existing test showing that when an earlier action in a receipt fails (there, `DeleteKey` on a nonexistent key → `DeleteKeyDoesNotExist`), later actions in that same receipt are simply never run: [8](#0-7) 

So, if the `DeleteKey(pk)` action inside `create_ban_relayer_promise`'s receipt fails for any reason (e.g. that same access key was already removed — by a prior/legitimate `DeleteKey` action the user issued through `rlp_execute` itself, by a previous ban that already ran, or by any other race that removes the key before this delayed self-receipt executes), the paired `ban_relayer` `FunctionCall` never executes and `has_in_flight_tx` is never reset. Since `has_in_flight_tx` was already durably set to `true` by the earlier, successfully-committed `rlp_execute` receipt, and no other code path in the contract clears it, every future `rlp_execute` call — from any relayer, forever — immediately short-circuits with `"transaction already in progress"` without creating any new promise, so the flag can never be cleared again.

### Impact Explanation
Because `rlp_execute` is the sole entry point through which an ETH-implicit account (and any funds/assets it or the wallet contract holds/controls) can act, a permanently-stuck `has_in_flight_tx == true` permanently freezes that account: no transfers, function calls, or key rotations can ever be executed again on it. This satisfies the "permanent freezing of funds" impact category, analogous to (and structurally stronger than) the original presale-delivery bug, since here there is no external retry or alternate recovery path at all.

### Likelihood Explanation
The trigger requires the (documented, supported) workflow where a relayer's access key is added directly on the eth-implicit account and used to sign `rlp_execute` calls (this is the exact flow shown in `test_wallet_contract_interaction`), combined with a `RelayerError` occurring on a transaction signed with that same key at a point where the key has already been removed from the account (e.g., due to key rotation via a legitimate `DeleteKey` action, or an earlier ban already having fired). Given NEAR's asynchronous transaction inclusion (a signed relayer transaction can sit for some time before being included) and the fact this pattern is officially supported/tested, the scenario is realistically reachable without any validator or protocol-level compromise — only ordinary client transactions.

### Recommendation
Do not bundle `DeleteKey` and the state-clearing `ban_relayer` `FunctionCall` into a single all-or-nothing receipt. Either:
- Reset `has_in_flight_tx` unconditionally before/independently of attempting to delete the relayer key (e.g. clear it in the same execution context that dispatches the ban, not only inside `ban_relayer`), or
- Split the ban into two independent receipts/promises so that a `DeleteKeyDoesNotExist` failure on the (possibly already-removed) key cannot prevent the flag reset, or
- Add a permissionless "unstick" path (e.g., a self-callback with a fixed timeout) that can clear `has_in_flight_tx` if the expected callback never lands.

### Proof of Concept
1. Owner creates ETH-implicit account, funds it, and adds a `FunctionCall`-permission access key for `relayer` restricted to `rlp_execute` (as in `test_wallet_contract_interaction`, `runtime/near-wallet-contract/...` / `integration-tests/src/tests/features/wallet_contract.rs:227-304`).
2. `relayer` signs and broadcasts NEAR tx **A**: `rlp_execute` wrapping an Ethereum tx that will hit `Error::Relayer(_)` (e.g. malformed RLP), signed with the wallet's own access key so `env::signer_account_id() == current_account_id` — this tx is queued but not yet included.
3. Before tx **A** is included, the account owner uses their Ethereum key via `rlp_execute` to issue a `near_action::Action::DeleteKey` removing that same relayer access key (legitimate key rotation) — this executes successfully and clears the key from state.
4. Tx **A** is now included and executed: `inner_rlp_execute` returns `Err(Error::Relayer(_))`; since `env::signer_account_id() == current_account_id`, `rlp_execute` dispatches `create_ban_relayer_promise` (`DeleteKey(pk)` + `FunctionCall("ban_relayer")` in one receipt) and sets `has_in_flight_tx = true`.
5. That receipt executes: `DeleteKey(pk)` fails with `DeleteKeyDoesNotExist` (key was already removed in step 3); per receipt atomicity the whole receipt fails and rolls back, so `ban_relayer` never runs and `has_in_flight_tx` stays `true` in committed state.
6. Every subsequent `rlp_execute` call on this account now immediately returns `"transaction already in progress"` (lines 97-105) forever — the account and its funds are permanently frozen.

        alice_account(),
        signers[0].clone(),

            Action::DeployContract(DeployContractAction {
                code: near_test_contracts::rs_contract().to_vec(),
