### Title
Unbounded body read in `process_event` allows single-POST memory-exhaustion DoS against the signer's event listener - (`libsigner/src/events.rs`)

### Summary
`process_event` reads the entire HTTP body of any incoming event POST via `request.as_reader().read_to_string(&mut body)` before any deserialization, with no cap on the number of bytes read. Unlike other parts of the codebase (e.g. `BlockProposalData::consensus_deserialize` using `read_next_at_most(fd, BLOCK_RESPONSE_DATA_MAX_SIZE)`, or the various stackslib RPC handlers checking `preamble.get_content_length()` against `MAX_PAYLOAD_LEN`/`MAX_MESSAGE_LEN`), this signer-side listener has no analogous size check, so a single oversized POST forces the process to allocate memory proportional to the attacker-supplied body.

### Finding Description
`SignerEventReceiver::next_event` routes any POST to a recognized path (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`) into `process_event::<T, E>`, and even unrecognized paths still fall through to `ack_dispatcher` after the handler dispatch logic runs: [1](#0-0) 

Inside `process_event`, the body is read fully into a `String` before any size/content-type validation and before `ack_dispatcher`/`serde_json::from_slice` run: [2](#0-1) 

There is no check of `Content-Length` (or streamed byte count) anywhere in this path, and `tiny_http`'s `Request::as_reader()` will happily continue accepting/allocating bytes for however long the declared body length says. This contrasts with the codec-level guard used elsewhere in the very same file for `BlockProposalData` (`read_next_at_most(fd, BLOCK_RESPONSE_DATA_MAX_SIZE)`, line 183) and with the numerous stackslib RPC handlers (`postblock_proposal.rs`, `postblock.rs`, `poststackerdbchunk.rs`, `posttransaction.rs`, etc.) that all explicitly reject requests whose `Content-Length` exceeds `MAX_PAYLOAD_LEN`/`MAX_MESSAGE_LEN` *before* touching the body. `process_event` has no equivalent gate, so the equality "bytes read == bounded by a MAX_SIZE constant" is broken; the actual bound is unbounded (limited only by available memory).

### Impact Explanation
Any party able to reach the signer's event-receiver HTTP port can send a single POST to a recognized URL (or even an unrecognized one, since the URL routing happens before size limiting) with a very large declared/actual body, causing the signer process to allocate memory equal to the body size in one call to `read_to_string`. Repeating this trivially exhausts memory and crashes or hangs the signer process — an unauthenticated, single-message DoS against the stacks-signer's event-processing thread, which is on the hot path for block validation responses and burn-block/StackerDB event delivery.

### Likelihood Explanation
No authentication, signature check, or size cap exists in this code path — `ack_dispatcher` unconditionally acks with HTTP 200 regardless of body validity, and the body is read to completion first. The attacker needs only network reachability to the signer's event bind address and the ability to send an HTTP POST with a large body; no secret, peer key, or StackerDB slot is required. This is repeatable per-connection.

### Recommendation
In `process_event`, check the request's declared `Content-Length` (via `tiny_http::Request::body_length()`) against a fixed maximum (e.g. reuse `BLOCK_RESPONSE_DATA_MAX_SIZE`/`MAX_PAYLOAD_LEN`-style constant) and reject/close the request before reading the body if it exceeds that bound. Alternatively, wrap `request.as_reader()` with a size-limited reader (e.g. `Read::take(MAX_SIZE)`) so `read_to_string` cannot allocate beyond the cap, mirroring the pattern already used by `BlockProposalData::consensus_deserialize`.

### Proof of Concept
Rust test plan (net-level, using `tiny_http`'s test utilities or a raw `TcpStream` against a bound `SignerEventReceiver`):
1. Bind a `SignerEventReceiver<T>` via `bind()` to get its address.
2. Open a `TcpStream` to that address and send `POST /new_burn_block HTTP/1.1\r\nContent-Length: <N>\r\nContent-Type: application/json\r\n\r\n` followed by `N` bytes of filler (e.g. `N` = several hundred MB, or simulate with a mocked reader for CI-safe testing).
3. Call `next_event()` (which dispatches into `process_event::<T, BurnBlockEvent>`) and observe that the process's memory usage grows to `~N` bytes in `body: String` before `serde_json::from_slice` is ever reached and before any rejection occurs.
4. Assert that no size check rejects the request prior to the full read, i.e. that memory allocation scales linearly with attacker-supplied `Content-Length` with no `MAX_SIZE`-style early return, in contrast to `BlockProposalData::consensus_deserialize`'s `read_next_at_most(fd, BLOCK_RESPONSE_DATA_MAX_SIZE)` guard.

```rust
fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;
```
