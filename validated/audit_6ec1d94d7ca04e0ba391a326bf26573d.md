The POST `/v2/stackerdb/:address/:contract/chunks` endpoint (`RPCPostStackerDBChunkRequestHandler::try_handle_request` in `stackslib/src/net/api/poststackerdbchunk.rs:163-329`) accepts a `StackerDBChunkData` addressed to a specific `contract_identifier`, but the only authorization check performed (`try_replace_chunk` → `SlotMetadata::verify`) validates the signature against `(slot_id, slot_version, data_hash)` — never against the `contract_identifier`/message-type the chunk is destined for. ### Title
StackerDB chunk signatures do not bind to the destination contract, enabling cross-contract chunk replay/frontrunning - (File: stackslib/src/net/stackerdb/db.rs, libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest()` in <cite repo="Kohvert/stacks-core--009" path="libstackerdb/src/libstackerdb.rs" start="159="166" /> commits only to `(slot_id, slot_version, data_hash)` — never to the `QualifiedContractIdentifier` of the StackerDB the chunk is destined for. Because `.signers` assigns the *same* signer address to the *same* `slot_id` across every `signers-{cycle_parity}-{message_id}` StackerDB instance of a signer set (`stackerdb-get-signer-slots-page` reuses one shared slot list per parity), a chunk that a signer validly signs and posts for one message-type contract (e.g. `signers-0-1`, `BlockResponse`) remains a fully valid signature for the identical `slot_id`/`slot_version`/`data_hash` in a sibling contract (e.g. `signers-0-2`, `StateMachineUpdate`).

### Finding Description
`try_replace_chunk` in [1](#0-0)  looks up the expected signer for `(smart_contract, slot_id)` and calls `slot_desc.verify(&slot_validation.signer)`, but this only re-derives the public key from the auth digest of `(slot_id, slot_version, data_hash)`; it never checks that the signature was produced with the destination `smart_contract` in mind. The same gap exists in the p2p ingestion path, `validate_received_chunk` in [2](#0-1) , which likewise verifies only against `get_slot_signer(smart_contract_id, slot_id)` and the chunk's self-contained digest.

An attacker who observes a legitimately-signed chunk being gossiped/POSTed for contract A (e.g. `signers-0-1`) can immediately resubmit the identical `StackerDBChunkData` (unchanged bytes: `slot_id`, `slot_version`, `sig`, `data`) to `/v2/stackerdb/:address/:contract/chunks` for a *different* sibling contract B (e.g. `signers-0-2`) that assigns the same slot to the same signer. Because `RPCPostStackerDBChunkRequestHandler::try_handle_request` ( [3](#0-2) ) passes the chunk straight to `try_replace_chunk` scoped to whatever `contract_identifier` is in the URL, the replay succeeds as an "accepted" write into contract B's replica, occupies that slot/version, and — since acceptance triggers `node.set_relay_message(StacksMessageType::StackerDBPushChunk(...))` (line 316-323) — gets propagated network-wide to peers replicating contract B, exactly as if the signer had legitimately authored data for contract B.

This is the direct analog of the reported "voucher" bug: the cryptographic authorization (the voucher/signature) is not bound to the specific destination/recipient (the target StackerDB contract) it will be redeemed against, so it can be redeemed in the wrong context by a third party before the legitimate write occurs.

### Impact Explanation
This is an unauthenticated write to StackerDB state on a contract the attacker never signed for, and network-wide propagation of that misdirected/forged-context data via the relay path in `poststackerdbchunk.rs`. Because `try_replace_chunk` enforces the stale-chunk/version rule (`slot_desc.slot_version <= slot_validation.version` in [4](#0-3) ), a replayed chunk that claims a given `slot_version` consumes that version number for the wrong contract's slot, causing the real, intended message for that contract/slot/version to be rejected as stale when it later arrives — a direct DoS on that signer's ability to publish to the correct message-type StackerDB (e.g. blocking `BlockResponse` or `StateMachineUpdate` delivery for a round), which can affect signer-set liveness/consensus-adjacent messaging.

### Likelihood Explanation
High. No privileged access or secret key material is required — the attacker only needs to observe one legitimately-broadcast, validly-signed chunk (trivially available: they are gossiped in plaintext over the p2p network and exposed via the same `/v2/stackerdb/.../chunks` HTTP endpoints) and resubmit it verbatim to a sibling contract endpoint before the real destination write occurs. All signer-set boot contracts (`signers-0-0`..`signers-0-{N}` and `signers-1-0`..`signers-1-{N}`) share slot assignments per parity, so this applies broadly whenever a signer participates in more than one message-id lane.

### Recommendation
Bind the destination contract identifier into the signed digest, e.g. include `smart_contract`/`contract_id` bytes in `SlotMetadata::auth_digest()` ( [5](#0-4) ) so a signature is only valid for the specific StackerDB it was produced for, and re-verify this binding in both `try_replace_chunk` and `validate_received_chunk`.

### Proof of Concept
1. Observe a valid `StackerDBChunkData{slot_id: N, slot_version: V, sig, data}` legitimately POSTed/gossiped for contract `signers-0-1` by signer `S`, where `S` also owns slot `N` in `signers-0-2` (true whenever both contracts belong to the same signer-set parity, per shared slot-assignment page).
2. Before signer `S`'s real `signers-0-2` update for slot `N`/version `V` arrives, POST the identical `StackerDBChunkData` bytes to `/v2/stackerdb/<signers-0-2-address>/signers-0-2/chunks`.
3. `try_replace_chunk` looks up `slot_validation.signer` for `signers-0-2` slot `N` (= `S`), calls `slot_desc.verify(&S)` which succeeds (digest only covers slot_id/version/hash), and stores/relays the chunk as accepted for `signers-0-2`.
4. When `S`'s genuine `signers-0-2` chunk for version `V` (or lower) later arrives, it is rejected with `StaleChunk`, denying the legitimate write.
