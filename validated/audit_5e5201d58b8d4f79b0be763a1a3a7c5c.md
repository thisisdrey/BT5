### Title
Spoofable `RelayFromAddr` in `CreateRelayRequest` lets an authenticated peer force relay state onto an arbitrary, unrelated VPN address - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` trusts the `RelayFromAddr` field carried inside the `NebulaControl` payload instead of the cert-authenticated `vpnAddrs` of the sending `HostInfo`. Any peer that has completed a normal handshake (i.e., holds a valid CA-signed cert for its own identity) can send a `CreateRelayRequest` claiming to be relaying "from" any third-party VPN address it does not own, and the receiving node will create relay bookkeeping state and reply as if that third party had initiated the relay.

### Finding Description
When a `Control` packet arrives, `outside.go` dispatches it to `relayManager.HandleControlMsg(hostinfo, out, f)` where `hostinfo` is the caller's cert-verified `HostInfo`. [1](#0-0) 

`HandleControlMsg` only validates that `RelayFromAddr`/`RelayToAddr` are non-nil before dispatching to `handleCreateRelayRequest`; it never checks that `RelayFromAddr` corresponds to the sender's own authenticated `vpnAddrs`: [2](#0-1) 

Inside `handleCreateRelayRequest`, `from` is taken directly from the attacker-controlled protobuf field, not from `h.vpnAddrs` (the cert-verified identity of the sender `h`): [3](#0-2) 

If the receiving node happens to be the `target`, it calls `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` and installs relay state keyed by the spoofed `from` address, then sends a `CreateRelayResponse` back to `h` (the actual attacker), not to the spoofed victim: [4](#0-3) 

The only self-referential check present is `f.myVpnAddrsTable.Contains(from)` — "is the source of the relay me" — which merely prevents the trivial self-relay case, not spoofing of a *third party's* address. [5](#0-4) 

This mirrors the Aave `flashLoan(_receiver, ...)` pattern: the caller supplies an arbitrary target/identity argument (`_receiver` in Aave, `RelayFromAddr` here) and the callee acts on behalf of that argument without confirming the caller is actually authorized to represent it — the callee (here, the relay-target node) has no mechanism to distinguish a legitimately-initiated request from a forged one.

### Impact Explanation
An authenticated but malicious peer can, with a single valid handshake of its own, cause a relay-capable node to fabricate `Relay` entries and hostmap bookkeeping tied to arbitrary victim VPN addresses that never requested a relay. Because `from` is never bound to the sender's own cert identity, an attacker can enumerate many fabricated `from` addresses to inflate the target's relay/hostmap state (state pollution / resource consumption), and any later legitimate `CreateRelayRequest`/response traffic involving those addresses could interact with attacker-seeded state (e.g. `Established`/`Disestablished` transitions keyed on `from`), corrupting the relay state machine for a host that never participated in the exchange.

### Likelihood Explanation
High for any deployment using relays (`relay.use_relays`/`relay.am_relay`): the attack requires only a normal, valid handshake by the attacker to become an authenticated `HostInfo` — no privileged position, malicious lighthouse, or already-established relay is required, satisfying the "reachable by an attacker with no CA-signed certificate beyond their own" analog to the flash-loan report (any caller, not the intended counterpart, can trigger the action).

### Recommendation
Bind `RelayFromAddr` to the sender's cert-authenticated identity: reject the request unless `from` is contained in `h.vpnAddrs` (analogous to `validatePeerCert`'s allow-list checks and the "Host sent invalid update" guard already used in `handleHostUpdateNotification`, which validates that `detailsVpnAddr` is one of `fromVpnAddrs`) [6](#0-5) . Add the equivalent check in `handleCreateRelayRequest` before trusting `from` for `AddRelay`/state transitions.

### Proof of Concept
1. Attacker completes a normal Nebula handshake with its own valid certificate, becoming `HostInfo h` with `h.vpnAddrs = [attackerIp]`.
2. Attacker crafts a `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: victimIp, RelayToAddr: targetIp, InitiatorRelayIndex: N}` and sends it over the header.Control channel to `targetIp` (a relay-capable node the attacker is directly connected to).
3. `targetIp`'s `handleCreateRelayRequest` sees `f.myVpnAddrsTable.Contains(target)==true`, finds no existing relay for `victimIp`, and calls `AddRelay(..., from=victimIp, ..., Established)`, creating relay state for `victimIp` that `victimIp` never requested. [7](#0-6) 
4. `targetIp` replies with `CreateRelayResponse` to the attacker's `h`, completing a relay entry attributed to `victimIp` inside `targetIp`'s hostmap.

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}
