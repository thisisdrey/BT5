### Title
Stale postponed self-receipt (Stake/DeleteKey) survives `DeleteAccount` and executes against a re-created same-named account, bypassing owner consent - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`remove_account` (called from `action_delete_account`) only removes `TrieKey::Account`, `TrieKey::ContractCode`, `TrieKey::AccessKey`/`GasKeyNonce`, and `TrieKey::ContractData` rows, but never touches `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::ReceivedData` rows keyed by the same `account_id`. A postponed self-receipt (receiver = predecessor = the account itself) containing a `Stake` or `DeleteKey` action that is still awaiting a `DataReceipt` when the account is deleted therefore remains in the trie under the same account-id key and later fires against whatever account is subsequently created under that same name.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) deletes the account by calling `remove_account(state_update, account_id)` (`core/store/src/utils/mod.rs:505-575`). That function explicitly enumerates only `Account`, `ContractCode`, access keys/gas-key-nonces, and contract data for removal: [1](#0-0) 
It never removes `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::ReceivedData` entries for that `account_id`, all of which are keyed purely by `receiver_id`/`account_id` string with no account "generation" tag: [2](#0-1) 

The postponement mechanism itself is documented and implemented in `process_action_receipt`: an incoming `ActionReceipt` whose `input_data_ids` are not all satisfied is persisted as a postponed receipt keyed by `(receiver_id, receipt_id)`, with a pending-count row and reverse index keyed by `(receiver_id, data_id)`: [3](#0-2) 
Per the protocol spec, once the last awaited `DataReceipt` for `(receiver_id, data_id)` arrives, the runtime looks up the postponed receipt purely by these string keys and executes it via `apply_receipt`, with no check that the account under `receiver_id` is the same one that existed when the receipt was postponed: [4](#0-3) 

`check_actor_permissions` gates `Stake`/`DeleteKey`/etc. purely on `actor_id == account_id` string equality: [5](#0-4) 
For a self-receipt, `actor_id` is the (unchanged) `predecessor_id`, which equals `account_id` regardless of which "generation" of the account currently occupies that name. So when the stale postponed receipt finally executes against the re-created account, the actor check passes trivially even though the current owner never authorized this action.

Attack flow:
1. Attacker's account `A` deploys a contract and issues a cross-contract promise `A -> B`, chained with `.then(A, [Stake(x)])` (or `[DeleteKey(pk)]`). This creates receipt `R2` to `A` with `input_data_ids = [data_id]`, `predecessor_id = A` (self/SIR).
2. `R2` arrives at `A` before `B`'s reply; it is postponed (`PostponedReceipt{A,R2_id}`, `PendingDataCount{A,R2_id}=1`, `PostponedReceiptId{A,data_id}=R2_id`).
3. Attacker submits a `DeleteAccount` transaction for `A` (self-signed, passes `check_actor_permissions`'s `actor_id==account_id` and zero-`locked` checks). `remove_account` clears `Account`/keys/code/data but leaves the postponed-receipt rows above intact.
4. `A` is re-created later (e.g., attacker as the subaccount's parent re-creates `sub.attacker.near` and hands it to a new owner, who deposits funds and adds fresh keys).
5. `B`'s deferred `DataReceipt` for `data_id` eventually arrives at receiver `A`. The runtime finds the still-present `PostponedReceiptId{A,data_id}`, decrements the still-present `PendingDataCount` to 0, loads `PostponedReceipt{A,R2_id}` and executes it via `apply_action_receipt` against the **new** account state.
6. `check_actor_permissions` passes (`actor_id == account_id` by string equality), and `Stake(x)` mutates the new account's `Account.locked` (and emits a validator-stake proposal) without the new owner's consent. A `DeleteKey` variant would only succeed if the same public key coincidentally exists on the new account, so `Stake` is the practically exploitable variant.

No existing check (`check_account_existence`, `check_actor_permissions`, receipt `validate_receipt`, or the delayed-receipt revalidation mentioned for the gas/compute delayed queue) covers this postponed-on-data path; that revalidation is documented only for the `compute_limit`/storage-proof delayed queue, not for data-postponed action receipts.

### Impact Explanation
This is an authorization-escalation bug: an action (`Stake`) that should require the current, re-created account's own consent (its actor being itself) instead executes based on a stale receipt from a previous, unrelated tenant of the account name, forcibly moving the new owner's `amount` into `locked` and creating a validator proposal — funds are locked/frozen from the new owner's perspective without consent. This matches the "authorization escalation across accounts" and "freezing of user funds" bounty categories.

### Likelihood Explanation
The attacker fully controls every precondition using only their own unprivileged transactions and contract code (creating the self-receipt with pending data dependency, then submitting `DeleteAccount`). The only external dependency is that the account name be re-created and reused by a new owner afterward, which is a normal/expected pattern for subaccounts being sold, reassigned, or reused. The exploit is deterministic and repeatable once the scenario is set up; cost to the attacker is limited to gas and the setup transactions.

### Recommendation
When executing `DeleteAccount`, purge all pending cross-receipt state tied to the account name before/alongside `remove_account`: remove any `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, and `TrieKey::ReceivedData` rows for that `receiver_id`, or alternatively reject `DeleteAccount` while such pending state exists for the account (similar to the existing zero-`locked` precondition in `check_actor_permissions`'s `DeleteAccount` branch).

### Proof of Concept
Unit/integration test plan (e.g., extend `runtime/runtime/src/tests/apply.rs`):
1. Set up account `A` with a `FunctionCall`-based promise chain that produces a postponed action receipt on `A` itself containing `Stake(some_amount)`, awaiting one `input_data_id` from a cross-contract call to `B`.
2. Apply a chunk delivering `R2` (postponed) to `A`; assert `PostponedReceipt{A,...}`/`PendingDataCount{A,...}`/`PostponedReceiptId{A,data_id}` rows exist in the trie.
3. In the same or a later block, apply a `DeleteAccount` transaction from `A` to beneficiary; assert `Account{A}` and `AccessKey{A,*}` rows are gone, but the postponed-receipt-related rows above still exist (demonstrating the gap in `remove_account`).
4. Recreate account `A` (via `CreateAccount` from its parent) with a fresh access key and a deposited balance; assert the new `Account{A}.locked() == 0`.
5. Deliver the `DataReceipt` for `data_id` from `B` to `A`; apply the chunk.
6. Assert (bug reproduction) `Account{A}.locked() > 0` and a validator stake proposal was emitted, even though the new owner of `A` never signed or authorized any `Stake` action — violating the "authorization exactness" invariant.
