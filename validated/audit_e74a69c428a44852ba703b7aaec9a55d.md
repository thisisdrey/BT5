Every variant (`NeighborsData`, `StackerDBChunkInvData`, etc.) is deserialized via `read_next_vec`/`read_next_at_most` style length-prefixed vectors, which read exactly `4 + Σ item_size` bytes — deterministic based on the length prefix embedded in the payload itself, not the preamble's `payload_len`. ### Title
Message-framing desync via mismatched `payload_len` vs. actual bytes consumed by payload deserializer - (File: `stackslib/src/net/connection.rs`)

### Summary
The P2P connection's streaming message parser advances its buffer pointer by the number of bytes the inner `StacksMessageType` deserializer actually consumed (`message_len` from `read_payload`), while the buffering/verification stage only bounds by the attacker-controlled `preamble.payload_len`. No code path asserts these two values are equal, so an attacker can declare a larger `payload_len` than the true serialized size of a valid payload, smuggling arbitrary bytes that get reinterpreted as a fresh, unauthenticated message header on the same connection.

### Finding Description
`ConnectionInbox::consume_payload_known_length` (`stackslib/src/net/connection.rs:799-860`) buffers exactly `preamble.payload_len` bytes (via `buffer_message_bytes`, `connection.rs:766-795`), then calls `protocol.read_payload(preamble, buf_bytes)`. For `StacksP2P` (`stackslib/src/net/codec.rs:1557-1575`), `read_payload` slices `bytes` to `preamble.payload_len`, then parses `(relayers, payload)` via `StacksMessage::deserialize_body`, and returns `cursor.position()` — the *actual* bytes consumed, which can be strictly less than `preamble.payload_len` if the attacker pads the declared length. Back in `connection.rs:818-834`, `next_message_ptr = message_ptr + message_len` uses this actual-consumed value, not `payload_len`, to determine where the next message begins, and the buffer is reset (`self.buf = data.to_vec()`) starting exactly there — i.e., in the middle of the region the attacker declared as this message's payload. No check anywhere compares `message_len` to `preamble.payload_len` and rejects on mismatch.

### Impact Explanation
An attacker who is merely a remote peer able to send bytes on the P2P port can craft one connection message where `preamble.payload_len` overstates the true payload size by N extra attacker-chosen bytes. Those N bytes are silently treated as leading bytes of the "next" message frame, letting the attacker prepend or hide bytes that desynchronize how the receiver interprets subsequent legitimate/attacker traffic on the same TCP stream. This is a framing-integrity defect but its severity depends on whether it can be leveraged into one of the listed severity buckets (forged state, crash, smuggling of an authenticated request, etc.) — I could not confirm from the available code that this alone yields e.g. auth bypass or forged StackerDB writes, since each subsequent "smuggled" pseudo-message must still pass its own preamble/signature checks (`Preamble::consensus_deserialize`, `verify_payload_bytes`) independently.

### Likelihood Explanation
Reaching this code requires only an established, unauthenticated or authenticated P2P connection (reachable by any remote peer) and a single crafted message; no privileged role or secret is needed. The exact severity impact is unconfirmed because I was not able to fully trace what a receiver does with a "smuggled" leftover fragment beyond re-entering the same preamble/payload parsing loop, which re-applies all the same guards (`MAX_MESSAGE_LEN`, preamble length bounds, `verify_payload_bytes` when a `public_key` is set) to the smuggled bytes.

### Recommendation
In `consume_payload_known_length` (`stackslib/src/net/connection.rs`), after `protocol.read_payload` succeeds, assert that `message_len == payload_len` (the value from `protocol.payload_len(preamble)`), and return `net_error::InvalidMessage` if they differ, so leftover bytes within the declared payload span can never be reinterpreted as a new message.

### Proof of Concept
Unable to fully validate real-world exploitable impact within the given time/tool budget — the mismatch (`message_len != payload_len`) is real and unguarded in the code, but I could not confirm a concrete forged-state/crash/smuggling outcome downstream, since re-parsing of the "smuggled" tail still goes through the same authentication and length checks. This finding should be treated as **unconfirmed/needs further investigation** rather than a definitive high/critical vulnerability — recommend a Devin session with full file/test access to write the reproducing Rust test (feeding a `StacksMessage` whose `preamble.payload_len` exceeds the true serialized payload length into `ConnectionInbox::consume_messages`, followed by a second legitimate message, and asserting whether the second message parses correctly or is corrupted/misframed).
