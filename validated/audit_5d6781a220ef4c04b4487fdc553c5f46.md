### Title
`Defuse::new()` / PoA `Contract::new()` initializers are public and unauthenticated, enabling front-run initialization with attacker-controlled roles - ([File: contracts/defuse/src/contract/mod.rs])

### Summary
Multiple `#[init]` constructors in this codebase (`Defuse::new`, `poa/factory::Contract::new`, `poa/token::Contract::new`) are ordinary public `#[near]` methods with no caller restriction, whereas the codebase's own security-sensitive analogs of the same pattern (`w_init`, `gd_init`) are explicitly marked `#[private]` specifically to close this attack vector.

### Finding Description
`Contract::new(config: DefuseConfig)` in `contracts/defuse/src/contract/mod.rs:118-131` sets up `RolesConfig` (`super_admins`, `admins`, `grantees`) via `init_acl`, and is guarded only by `PanicOnDefault` (which prevents re-initialization, not first-caller identity): [1](#0-0) 

Similarly, `poa/factory`'s `Contract::new` at `contracts/poa/factory/src/contract.rs:69-101` and `poa/token`'s `Contract::new` at `contracts/poa/token/src/contract.rs:34-65` are public, unauthenticated `#[init]` methods that set an owner/admin from constructor arguments or `predecessor_account_id`: [2](#0-1) [3](#0-2) 

By contrast, this repository already recognizes and mitigates exactly this class of bug elsewhere: `w_init` in `contracts/wallet/signatures/no-sign/src/contract.rs:28-33` and `gd_init` in `contracts/global-deployer/src/contract.rs:70-74` are marked `#[private]` (restricting the caller to `predecessor_account_id == current_account_id`) with an explicit comment "recommended to call this method in the same receipt right after `UseGlobalContract` action": [4](#0-3) [5](#0-4) 

If code deployment (`DeployContract`/`UseGlobalContract`) and the call to `new()` are ever split across separate transactions for `Defuse`/PoA contracts — the exact scenario the `#[private]` pattern in `w_init`/`gd_init` was designed to prevent — an unprivileged attacker who observes an account with deployed-but-uninitialized code could call `new()` first, supplying themselves as `super_admins`/`admins` in `RolesConfig`, permanently seizing DAO-level control (`Role::DAO`, upgrade rights via `ControllerUpgradable::upgrade` at `contracts/defuse/src/contract/upgrade.rs:11-25`, pause/unpause, etc.) before the legitimate deployer's initialization succeeds (subsequent `new()` calls panic via `PanicOnDefault`).

### Impact Explanation
If reachable, this is Critical: gaining `Role::DAO`/admin over `Defuse` grants control over upgrades and access-controlled operations that gate custody of all tokens held by the intents contract, i.e., authorization is bypassed entirely for the contract's most sensitive functions.

### Likelihood Explanation
Likelihood is low/unconfirmed in this repo. All deployment call sites found (`crates/testing/sandbox/src/extensions/defuse/mod.rs:396-417`, `tests/src/tests/defuse/env/builder.rs:117-153`, `poa/factory::deploy_token` at `contracts/poa/factory/src/contract.rs:126-139`) bundle `DeployContract`/deploy-and-`new()` into a single atomic transaction or single promise action chain, which forecloses any window for an external transaction to be interleaved between deployment and initialization. I could not find a documented or code-enforced production deployment path that decouples code deployment from the `new()` call for `Defuse`, `poa/factory`, or `poa/token` (unlike the wallet/global-deployer flows, which explicitly support and guard against decoupled `UseGlobalContract` + init). Without concrete evidence that these specific contracts are deployed via a global-contract/decoupled path in production, this remains a plausible-but-unconfirmed structural gap rather than a proven exploitable path.

### Recommendation
Mirror the mitigation already used for `w_init`/`gd_init`: mark `Defuse::new`, `poa/factory::Contract::new`, and `poa/token::Contract::new` with `#[private]` (or otherwise enforce `predecessor_account_id() == current_account_id()`/a trusted deployer check) so initialization can only be triggered by the account itself in the same receipt as deployment, closing any front-running window regardless of how deployment tooling evolves.

### Proof of Concept
1. An account has `Defuse` (or PoA factory/token) WASM deployed via `DeployContract`, but `new()` has not yet been called in the same transaction/receipt (e.g., deployment and initialization are split into two transactions by some deployment tool or manual process).
2. An unprivileged attacker submits a transaction calling `new()` on that account with `RolesConfig { super_admins: [attacker], .. }` before the legitimate initializer's transaction lands.
3. `PanicOnDefault` allows only the first successful `new()` call to succeed; the attacker's call succeeds and `init_acl` (`contracts/defuse/src/contract/mod.rs:133-152`) grants the attacker `Role::DAO`/admin.
4. The legitimate deployer's subsequent `new()` call panics ("already initialized"), leaving the attacker in permanent control of the contract's roles/admin, including upgrade rights.

impl Contract {
    /// Initialize a wallet contract on the existing account
    /// with authentication by signature disabled and
    /// add the current account as an extension.
    ///
    /// This method is allowed to be called only by the current
    /// account itself. It's recommended to call this method
    /// in the same receipt right after `UseGlobalContract` action.
    ///
    /// MUST attach at least 1yN for security reasons.
    #[cfg_attr(not(near), allow(dead_code))]
    #[allow(clippy::use_self)]
    #[private]
    #[payable]
    #[init]
    pub fn w_init() -> Self {
        if env::attached_deposit().is_zero() {
            // reject FunctionCall access keys
            Error::InsufficientDeposit.panic();
        }

        let mut s = State::new(NoPublicKey)
            // Add self as the only extension
            .extensions([env::current_account_id()]);

        // Disable signature verification completely,
        // so that accidently removing self from extensions
        // would result into lockout error.
        s.signature_enabled = false;

        Self(s.into())
    }
