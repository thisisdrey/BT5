### Title
Unprivileged attacker can DoS withdrawals and liquidations by stuffing the `feeCollector`'s per-account token set to `MAX_TOKENS_PER_USER` - (File: contracts/Pool.sol)

### Summary
The bug class of CVE-2022-21526 is a remotely-triggerable denial of service. The strongest reachable analog in Metronome is a per-account token-list stuffing attack: `Pool.addToDepositTokensOfAccount()` and `addToDebtTokensOfAccount()` revert with `UserReachedMaxTokens` once an account's combined deposit+debt token count reaches `MAX_TOKENS_PER_USER = 30`. Because fee transfers during `DepositToken.withdraw()` and liquidation `seize()` route through the same `_transfer`/`addToDepositTokensOfAccount` path, an unprivileged attacker can dust-fill the `feeCollector` account's set and make every fee-bearing withdraw and liquidation revert.

### Finding Description
`DepositToken._withdraw()` first transfers the withdraw fee to `pool.feeCollector()` via `_transfer`, and `Pool.liquidate()` seizes a fee portion to the `feeCollector` via `DepositToken.seize()` → `_transfer`. In `_transfer`, whenever the recipient's prior balance of that deposit token is zero, `pool.addToDepositTokensOfAccount(recipient_)` is invoked (`DepositToken.sol:517-520`). That function is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts unconditionally once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`Pool.sol:143-148, 216-220`).

Key attacker primitives, all unprivileged:

- `DepositToken.transfer(to_, amount_)` only checks the *sender's* unlocked balance (`_revertIfLocked(_msgSender, amount_)`, `DepositToken.sol:348-353`), so the attacker can push dust of any deposit token they hold onto any recipient — including the `feeCollector`.
- `DepositToken.deposit(amount_, to_)` mints to an arbitrary `to_`, so dust can be deposited directly to the victim.
- `DebtToken.issue(amount_, onBehalfOf)` mints debt onto `onBehalfOf` against its collateral (test: `msUSDDebt.connect(user2).issue(parseEther('1'), user1.address)`), which triggers `addToDebtTokensOfAccount` — letting the attacker also occupy *debt-token* slots of the victim set, lowering the number of distinct deposit tokens needed.

Attack sequence against `feeCollector`:

1. Attacker deposits dust of N distinct deposit tokens to `feeCollector` (or transfers dust), so `depositTokensOfAccount.length(feeCollector)` grows.
2. Attacker calls `issue(1 wei, feeCollector)` for every debt token, filling `debtTokensOfAccount(feeCollector)` — these only require the feeCollector's (likely zero) collateral to cover dust debt, or alternatively the attacker fills purely with deposit tokens when the pool lists ≥31 collateral types.
3. Once combined length = 30, any fee transfer in a deposit token *not already held* by `feeCollector` reverts in `addToDepositTokensOfAccount` → the whole `withdraw()`/`liquidate()` transaction reverts.

### Impact Explanation
- `DepositToken.withdraw()` / `withdrawFrom()` for any collateral whose deposit token is absent from `feeCollector`'s set permanently reverts while `withdrawFee > 0` — temporary freezing of user collateral.
- `Pool.liquidate()` reverts when seizing a fee in such a token — liquidation DoS allowing bad debt to accrue, a liveness break of the solvency mechanism.
- No modifier stops it: `transfer`/`deposit`/`issue` are public, the revert happens in the callee (`Pool`), and `whenNotShutdown`/`nonReentrant` do not help. The only mitigation is the `feeCollector` (governor-controlled) manually shedding tokens, so funds are frozen until governance intervenes — matching the "temporary freezing of funds" acceptance criterion.

### Likelihood Explanation
Requires the victim account's reachable token universe (deposit tokens + attacker-issuable debt tokens) to exceed 30. On Metronome pools with many registered `DepositToken`s (the production pools on mainnet/Optimism/Base list many collateral types) this is achievable cheaply: dust amounts only, no capital lock-up (transferred dust is recoverable, issued dust debt is trivial). `issue` onto `feeCollector` additionally reduces the required number of deposit tokens. Feasibility must be confirmed per-pool by counting registered deposit/debt tokens on the target deployment.

### Recommendation
- In `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, check membership before enforcing the cap: only revert when the token is not already in the set (currently `onlyIfAdditionWillNotReachMaxTokens` runs before `add`, but the `add` call itself is skipped when balance > 0 — the real fix is making the cap not apply to the `feeCollector`, or allowing it to be bypassed for fee/seize transfers).
- Alternatively, exempt `feeCollector` (and `Treasury`) from `MAX_TOKENS_PER_USER`, or send liquidation/withdraw fees as underlying via `Treasury` instead of deposit-token transfers.
- Consider restricting `DebtToken.issue(amount, onBehalfOf)` so arbitrary accounts cannot push debt-token slots onto victims.

### Proof of Concept
```solidity
// Foundry fork test sketch
function test_FeeCollectorTokenSetStuffingDoS() public {
    address feeCollector = pool.feeCollector();
    address[] memory tokens = pool.getDepositTokens(); // assume >= 30 available incl. debt stuffing

    // 1. Stuff feeCollector's set to MAX_TOKENS_PER_USER (30)
    for (uint256 i; i < 29; i++) {
        IDepositToken dt = IDepositToken(tokens[i]);
        deal(address(dt.underlying()), attacker, 1);
        dt.underlying().approve(address(dt), 1);
        dt.deposit(1, feeCollector); // adds token to feeCollector set
    }
    // fill remaining slots via dust debt issued on behalf of feeCollector
    debtToken.issue(1, feeCollector); // adds debt token slot -> length == 30

    // 2. User holds collateral whose deposit token is NOT in feeCollector's set
    IDepositToken victimDt = IDepositToken(tokens[30]);
    // user deposited earlier; feeCollector holds 0 of victimDt
    vm.prank(user);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    victimDt.withdraw(userBalance, user); // _transfer(account, feeCollector, fee) reverts

    // 3. Liquidations seizing victimDt as fee collateral also revert
    vm.prank(liquidator);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    pool.liquidate(synth, unhealthyAccount, amountToRepay, address(victimDt));
}
```

Note: I verified the revert path `withdraw → _transfer(fee) → addToDepositTokensOfAccount → UserReachedMaxTokens` and the attacker primitives (`transfer`/`deposit` dust, `issue` on behalf) in `contracts/DepositToken.sol` and `contracts/Pool.sol`. What I could not fully confirm in-repo is whether a production pool registers ≥30 receivable token types and the exact `issue` collateralization requirements for dust debt on an empty-collateral account — the PoC should be run against a mainnet/Base fork to confirm slot-count feasibility on the deployed configuration.
