### Title
Delegate can front-run `setAllowance` amount reductions to double-spend the old and new allowance caps - ([File: contracts/TrustedSpender.sol](tare-io__tare-contracts/contracts/TrustedSpender.sol))

### Summary
`TrustedSpender.setAllowance` fully overwrites a `(token, from, to)` route's spending cap in a single storage write, exactly mirroring the classic ERC20 `approve()` race condition described in the external report. Any address registered as a `delegate` for a Safe can observe a pending allowance-reduction transaction in the mempool and front-run it, draining the full old allowance immediately before the reduction lands, then draining the newly-set (lower) allowance right after — spending more than the Safe ever intended to authorize at any single point in time.

### Finding Description
`setAllowance` stores a fresh `Allowance{amount, validUntil}` that completely replaces whatever was previously stored for the route, with no requirement that the caller confirm the currently-observed value (no "compare-and-swap" / expected-old-value parameter, unlike the OpenZeppelin `increaseAllowance`/`decreaseAllowance` mitigation referenced in the report): [1](#0-0) 

`executeTransfer` is callable by any registered `delegate` at any time (subject only to `whenNotPaused`), and decrements the allowance in place: [2](#0-1) 

Because delegates are semi-trusted automation addresses — the entire purpose of the per-route `amount` cap is to bound the damage an operationally-compromised or malicious delegate can inflict — a delegate that observes a Safe's `setAllowance` call reducing its allowance (e.g., in response to detected suspicious activity, an operational policy change, or key-compromise mitigation) can front-run it with `executeTransfer` to drain the full old allowance, then immediately call `executeTransfer` again after the new, lower allowance is applied to drain that as well. This is the same "approve race condition" root cause called out in the ArroToken report, applied to the Safe-account allowance surface instead of a plain ERC20 token.

### Impact Explanation
A delegate can extract USDC (or any ERC20 route) from a Safe in excess of the cap the Safe most recently authorized, defeating the entire security purpose of the allowance-reduction mechanism. This is a direct unauthorized diversion of Safe-held funds triggered by an unprivileged party (the delegate is not a guardian/admin — it is precisely the semi-trusted party the allowance system is designed to constrain).

### Likelihood Explanation
Requires only that (a) the attacker is (or becomes, via compromise) a registered delegate for the target Safe, and (b) the Safe or a guardian ever lowers an existing non-zero allowance for a route that delegate can reach. Given allowances are explicitly designed to be adjustable ("Fully overwrites any existing allowance"), and delegate compromise/rotation is an anticipated operational scenario per the spec, this is a realistic and mempool-observable front-running window.

### Recommendation
Adopt the report's recommended mitigation pattern: add `increaseAllowance`/`decreaseAllowance`-style functions that operate on deltas rather than absolute overwrites, or require `setAllowance` to accept an `expectedCurrentAmount` parameter that reverts if the on-chain value has changed since it was read (compare-and-swap), preventing a delegate from spending both the pre- and post-update allowance.

### Proof of Concept
1. Safe calls `setAllowance(usdc, safe, delegateRecipient, 1000e6, NO_EXPIRY)`.
2. Safe later decides to reduce the cap and submits `setAllowance(usdc, safe, delegateRecipient, 100e6, NO_EXPIRY)`.
3. The registered delegate sees this tx in the mempool and front-runs it with `executeTransfer(usdc, safe, delegateRecipient, 1000e6)`, draining the entire old allowance before the reduction lands.
4. The Safe's `setAllowance(..., 100e6, ...)` is then mined, setting the cap to 100e6.
5. The delegate immediately calls `executeTransfer(usdc, safe, delegateRecipient, 100e6)`, draining the newly-set allowance too.
6. Total extracted: 1100e6, exceeding both the pre- and post-update caps the Safe ever intended to have active simultaneously.

```text
  /// @inheritdoc ITrustedSpender
  function setAllowance(
    address token,
    address from,
    address to,
    uint208 amount,
    uint48 validUntil
  ) external safeOrGuardian(from) {
    require(token != address(0) && from != address(0) && to != address(0), ZeroAddress());
    require(validUntil > block.timestamp, InvalidAllowanceDeadline());

    _allowances[token][from][to] = Allowance({amount: amount, validUntil: validUntil});
    emit AllowanceSet(token, from, to, amount, validUntil);
  }
```

```text
  /// @inheritdoc ITrustedSpender
  function executeTransfer(address token, address from, address to, uint256 amount) external whenNotPaused {
    // Verify sender is a delegate
    require(delegates[from][msg.sender], NotADelegate());

    // Check allowance exists, is sufficient, and has not expired
    Allowance storage allowance = _allowances[token][from][to];
    require(allowance.amount >= amount, InsufficientAllowance());
    require(block.timestamp <= allowance.validUntil, AllowanceExpired());

    // Update allowance if not infinite
    if (allowance.amount != type(uint208).max) {
      allowance.amount -= uint208(amount);
    }

    IERC20(token).safeTransferFrom(from, to, amount);
  }
```
