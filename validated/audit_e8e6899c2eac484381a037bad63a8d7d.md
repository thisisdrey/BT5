Based on my investigation, I found a genuine analog in nebula's `handleRecvError` function that matches the bug class: an unauthenticated action that prematurely tears down/blocks a legitimate flow, exploitable by an attacker who does not need to hold a CA-signed certificate.

### Title
Unauthenticated `RecvError` packet allows any off-path attacker to grief/tear down an established tunnel by spoofing the peer's known UDP source address - (File: `outside.go`)

### Summary
`RecvError` is one of the packet types processed by `readOutsidePackets` before any decryption or certificate verification occurs — it is dispatched straight out of the unauthenticated packet-type switch, alongside `Handshake`. [1](#0-0)  `handleRecvError` then tears down the tunnel identified by `h.RemoteIndex` if the UDP source address on the packet matches the hostinfo's currently known remote, with no cryptographic authentication of the sender at all. [2](#0-1) 

### Finding Description
This mirrors the reported bug class: a state-mutating action ("reveal solution" / here, "declare a receive error and tear down the tunnel") is allowed to execute without validating that the actor is entitled to trigger it, causing legitimate, in-progress communication to be prematurely and irrevocably blocked. In `TriviaChoicePrompt`, the flaw was a missing `reactionDeadline`/state check before an authorized-but-premature action; in nebula, the analogous flaw is a missing *cryptographic authentication* check before a fully unauthenticated, spoofable UDP packet is allowed to terminate a live, already-authenticated session.

Concretely:
- `RecvError` packets are handled in the plaintext branch of `readOutsidePackets`, before `hostinfo.ConnectionState.Decrypt` is ever called. [3](#0-2) 
- `handleRecvError` looks up the hostinfo purely by `h.RemoteIndex` (a 32-bit value that is visible on the wire in every packet for that tunnel) and only checks that the packet's *source UDP address* matches the last known remote address for that hostinfo. [4](#0-3) 
- Because UDP is connectionless and source addresses are trivially forgeable (especially so if the attacker is on-path or shares a NAT/observes traffic, but even blind spoofing is possible depending on network position), an attacker who knows or guesses a peer's public UDP endpoint and a live `RemoteIndex` can forge a `RecvError` packet that causes both `f.closeTunnel(hostinfo)` and `hm.DeleteHostInfo(hostinfo)` to execute — permanently destroying the session state on the receiving side without ever presenting a certificate or completing the handshake. [5](#0-4) 
- This is precisely the "no CA-signed certificate needed" pattern called for by the rules: no handshake, no cert, no decryption key is required to trigger the tunnel teardown; the only gate is a spoofable IP-address match, which does not constitute authentication.

### Impact Explanation
Repeated forged `RecvError` packets let any network-adjacent or address-guessing attacker perform a persistent denial-of-service against specific nebula tunnels, forcing repeated re-handshakes and preventing sustained connectivity between victims — a direct "remote state poisoning"/DoS impact reachable without ever holding a valid certificate, analogous to the griefing in the reported finding where legitimate participants are blocked from completing their intended flow while the attacker incurs no authentication cost.

### Likelihood Explanation
The `CHANGELOG.md` shows this exact class of packet has previously required hardening (`Disable sending recv_error messages when a packet is received outside the allowable counter window`, `Properly handle closetunnel packets`), indicating this attack surface is a recognized, previously-exploited weak point in the protocol's unauthenticated fast paths. [6](#0-5)  The `f.acceptRecvErrorConfig.ShouldRecvError(addr)` gate is a rate/policy limiter, not a cryptographic authentication mechanism, so it reduces frequency but does not close the spoofing vector. [7](#0-6) 

### Recommendation
Require an authenticated/keyed signal (e.g., only honor `RecvError` from a peer once at least one packet has been successfully decrypted with the associated `ConnectionState`, or attach a MAC computed with the tunnel's established keys) rather than only checking an easily spoofed source-address match against `h.RemoteIndex` before calling `f.closeTunnel` and `hm.DeleteHostInfo`.

### Proof of Concept
1. Observe or infer a live tunnel's `RemoteIndex` (visible on the wire in every packet header for that tunnel) and the victim's currently-registered public UDP endpoint (learnable via lighthouse queries, which are also unauthenticated for read purposes).
2. Craft a raw UDP packet with `header.RecvError` type/`RemoteIndex` set, sourced (or spoofed) from that endpoint, per the encoding in `sendRecvError`. [8](#0-7) 
3. Send it to the victim; `handleRecvError` finds the hostinfo by index, sees the source address matches, and calls `f.closeTunnel(hostinfo)` plus `hm.DeleteHostInfo(hostinfo)`, destroying the tunnel with no cryptographic proof of possession of the peer's identity or keys. [9](#0-8)

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
```
