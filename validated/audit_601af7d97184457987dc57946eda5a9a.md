### Title
Vault `assets`/liquidity accounting relies on locally-tracked state instead of actual underlying token balance, allowing donation-based desync of share pricing and liquidity checks - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
Every Zest v0 vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) tracks the underlying-asset amount it holds in a local `assets` variable rather than reading the real-time balance of the underlying token held by the vault contract. `deposit`, `redeem`, `system-borrow`, and `system-repay` all mutate this local `assets` var, and `convert-to-shares-preview`/`convert-to-assets-preview`/`get-available-assets` (share-price and liquidity math) are computed purely from `total-assets` which is derived from `(var-get assets)` plus accrued interest, never from the vault's actual on-chain underlying token balance. This is the same bug class as the Quantstamp report on `parity-issuance`/`parity-staking`, where `total_collateral`/`base_balance` state fields diverged from the real vault ATA balance because they were the source of truth for withdrawal/health checks instead of the real balance.

### Finding Description
Each vault contract exposes a private `ubalance` helper that reads the real fungible-token balance of the vault contract, e.g. in `v0-vault-ststx.clar`:
```
(define-private (ubalance)
  (unwrap-panic (contract-call? .ststx get-balance current-contract)))
```
`local-testing/contracts/vault/vault-ststx.clar:306-308` (mirrored in `mainnet/contracts/vault/v0-vault-ststx.clar`).

However, `ubalance` is never used to validate or reconcile the vault's internal accounting. Instead, `total-assets`/`total-assets-preview` are computed strictly from the local `assets` state variable plus computed interest:
```
(define-private (total-assets)
  (let ((current-assets (var-get assets))
        (debt (total-debt))
        (borrowed (var-get total-borrowed))
        (interest (if (> debt borrowed) (- debt borrowed) u0)))
    (+ current-assets interest)))
```
`local-testing/contracts/vault/vault-ststx.clar:338-343`

`deposit` and `redeem` update `assets` purely via `var-set`, based on the caller-declared `amount`, not the vault's measured balance delta:
```
(try! (receive-underlying amount account))
(try! (ft-mint? zft inkind recipient))
(var-set assets (+ current-assets amount))
```
`local-testing/contracts/vault/vault-sbtc.clar:781-783`

`convert-to-shares-preview`/`convert-to-assets-preview` (share price used for minting/burning zTokens) and `get-available-assets` (the liquidity gate for `redeem` and `system-borrow`) both derive from this same locally-tracked `assets` value, exactly analogous to `deposit_funds.rs`/`withdraw_funds.rs` relying on `total_collateral` and `unstake.rs` relying on `base_balance` in the referenced Solana report rather than the real vault token-account balance.

Because any unprivileged principal can transfer the underlying token directly to the vault contract's address (a normal SIP-010 `transfer` call, no vault-specific permission required), the vault's real underlying balance (`ubalance`) can be pushed arbitrarily out of sync with its internally tracked `assets`/`total-borrowed` state without the vault's own accounting or the `market`/`market-vault` collateral system ever detecting the discrepancy. The vault has zero code path that reads or asserts against `ubalance` to catch this drift.

### Impact Explanation
This lands in the "vault share math and interest accrual" analog area explicitly kept in scope. The direct consequence is a permanent divergence between the vault's tracked `assets` (used for share-price conversion in `convert-to-shares-preview`/`convert-to-assets-preview` and liquidity checks in `get-available-assets`) and the real underlying balance. Donated/dust tokens sent straight to the vault contract are silently absorbed with no accounting trail, meaning they become permanently unreachable/unaccounted-for value inside the vault (the token balance can never be withdrawn via `redeem` because `redeem` pays out based on `total-assets`/share ratio derived from the stale `assets` var, not the true balance) — this is a permanent freezing of those transferred funds, and it also skews the zToken share price for every subsequent depositor/redeemer relative to what the true backing would imply, an accounting drift affecting all vault users' redeemable underlying amounts. This matches the in-scope "temporary/permanent freezing of funds" and "vault share math" impact classes; it does not rely on flashloans, DAO compromise, or oracle manipulation.

### Likelihood Explanation
Triggering the desync requires nothing more than an ordinary principal calling the underlying SIP-010 token's own `transfer` function to send tokens directly to the vault's contract principal — no special authorization, no flashloan, and no privileged role is needed. This can be done at any time by any user, intentionally or accidentally (e.g., a user who mistakes the vault contract address for a deposit target), making the discrepancy easily and repeatedly reproducible across all six vaults (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-usdc`, `v0-vault-usdh`, `v0-vault-ststxbtc`), each sharing the identical `assets`-only accounting pattern.

### Recommendation
Reconcile the vault's `assets` state variable against the real underlying-token balance (`ubalance`) at critical checkpoints — at minimum before computing `convert-to-shares-preview`, `convert-to-assets-preview`, and `get-available-assets`, and ideally on every `deposit`/`redeem`/`system-borrow`/`system-repay` entry. Where excess balance is detected (real balance > tracked `assets`), either sweep it into `assets` in a controlled/permissioned manner or provide an explicit DAO-gated instruction to recover/redistribute it, consistent with the "Use vault ata balance for any checks" fix adopted by the referenced report's client. Treat `ubalance` as the authoritative source of truth for any operation that pays out underlying tokens to users.

### Proof of Concept
1. Attacker (or any user) calls the underlying SIP-010 token contract's `transfer` function directly (e.g. `stSTX transfer <amount> attacker .vault-ststx none`), sending tokens straight to the `v0-vault-ststx` contract principal, bypassing the vault's `deposit` entry point entirely.
2. The vault's real balance as read by `ubalance` increases by `<amount>`, but `(var-get assets)` — used by `total-assets`, `convert-to-shares-preview`/`convert-to-assets-preview`, and `get-available-assets` — is untouched.
3. Subsequent `deposit` and `redeem` calls compute share price entirely from the stale `assets` figure; the donated tokens are never reflected in `total-assets-preview`, so no zToken shares are minted against them and they can never be redeemed out through `redeem`, permanently stranding that value inside the vault contract while simultaneously leaving the vault's own internal ledger inconsistent with its actual token holdings.
