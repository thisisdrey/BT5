### Title
`DebtToken.repay` reverts with an undocumented arithmetic panic on small/edge amounts instead of `BurnAmountExceedsBalance` - (File: contracts/DebtToken.sol)

### Summary
The external report describes a bug class where an edge-case input (a value of 0 or 1) triggers an undocumented low-level exception (`Invalid_argument`) instead of the documented, catchable `Insufficient_key` error. The Metronome analog is in `DebtToken.repay`: for certain gross repay amounts, the half-up rounding in `quoteRepayOut` produces a `_repaid` value that exceeds the debtor's `balanceOf`, and the subtraction `balanceOf(onBehalfOf_) - _repaid` reverts with a raw Solidity `Panic(0x11)` arithmetic-underflow error before execution reaches the documented `BurnAmountExceedsBalance` check inside `_burn`.

### Finding Description
`repay` computes the debt amount to clear via `quoteRepayOut(amount_)`, which uses `wadDiv` with half-up rounding: `_amountToRepay = amount_.wadDiv(HUNDRED_PERCENT + _repayFee)` where `wadDiv(a,b) = (a * WAD + b/2) / b` (`contracts/lib/WadRayMath.sol:39-41`). When `amount_` is small (e.g., 1 wei, or a gross amount computed to exactly cover a dust debt), the half-up term `b/2` can round `_amountToRepay` up so that `_repaid > balanceOf(onBehalfOf_)`.

The code then evaluates the debt-floor check before the balance check:

```solidity
// contracts/DebtToken.sol:442-451
uint256 _debtFloorInUsd = _pool.debtFloorInUsd();
if (_debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = _pool.masterOracle().quoteTokenToUsd(
        address(_syntheticToken),
        balanceOf(onBehalfOf_) - _repaid   // <-- Panic(0x11) here
    );
    ...
}
```

The documented guard `if (_accountBalance < amount_) revert BurnAmountExceedsBalance()` exists only inside `_burn` (`contracts/DebtToken.sol:528-529`), which is reached *after* the underflowing subtraction. So an unprivileged caller passing a gross `amount_` that rounds up past the onBehalf debt gets an undocumented `Panic(0x11)` instead of the expected custom error — exactly the bug class of the advisory (undocumented exception escapes instead of the documented error).

### Impact Explanation
- Any integration, keeper, or batching path (e.g., `Operator.execute` multicall-style flows) that catches or reason about the documented error set of `repay` will see a raw panic instead, aborting the whole batch.
- A payer attempting to repay a counterparty's exact dust debt via a gross amount derived from `quoteRepayIn`/`quoteRepayOut` round-trip can hit a panic rather than a clean revert, breaking repayment UX and off-chain error handling for edge amounts.
- The debt-floor branch is only reached when `debtFloorInUsd > 0` (a deployed configuration on Metronome pools), so this is reachable on the live configuration whenever a repay fee is set.

### Likelihood Explanation
Reachable by any EOA calling `repay(onBehalfOf_, amount_)` with a small or exactly-covering gross amount while `repayFee > 0` and `debtFloorInUsd > 0`. No privileged role needed. Severity is limited because `repayAll` remains available as a workaround, so funds are not permanently frozen; impact is a broken error contract plus revert of the calling transaction.

### Recommendation
Move the balance check ahead of the floor check, or compute `_newDebtInUsd` defensively:

```solidity
uint256 _balance = balanceOf(onBehalfOf_);
if (_balance < _repaid) revert BurnAmountExceedsBalance();
uint256 _newDebtInUsd = _pool.masterOracle().quoteTokenToUsd(
    address(_syntheticToken), _balance - _repaid
);
```

This mirrors the upstream fix: reuse the documented exception (`BurnAmountExceedsBalance`) instead of letting a low-level panic escape.
