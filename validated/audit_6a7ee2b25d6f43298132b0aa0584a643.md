### Title
Floating-point precision loss in the legacy TRC10 Bancor-curve exchange formula allows economically incorrect swap/inject/withdraw amounts - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The default (non-hardened) TRC10 exchange (Bancor-style AMM) pricing path in `ExchangeProcessor` computes swap amounts using IEEE-754 `double` arithmetic and `Math.pow`/`StrictMath.pow`, exactly the same class of defect described in the reference report: a fixed-precision numeric representation is used to compute a ratio-based formula (`quant / newBalance`, raised to a fractional exponent) whose result is extremely sensitive to catastrophic cancellation and rounding when the operands are very large or very small relative to each other. This is reachable by any unprivileged account through `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract`.

### Finding Description
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` implement the constant-formula "bancor" curve entirely in `double`: [1](#0-0) 

`double issuedSupply = -supply * (1.0 - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, useStrictMath))` and the symmetric `exchangeFromSupply` computation both depend on a ratio (`quant/newBalance` or `supplyQuant/supply`) that can be extremely small (analogous to the report's tiny `conf`/`px` values) whenever pool balances are large (up to the configured `balanceLimit`) and the traded `quant` is comparatively small, or vice versa when `quant` approaches the pool balance. In double precision, `1.0 + verySmallRatio` loses the low-order bits of the ratio (machine epsilon ≈ 2.22e-16), and raising that value to a fractional power (`0.0005` or `2000.0`) amplifies the resulting relative error non-linearly — the same "value repeatedly scaled and losing precision" pattern flagged in the report for `pd_store`/`upd_twap`.

This path is selected whenever `allowHarden()` is false (the exchange-hardening feature is a `DynamicPropertiesStore` proposal-gated flag, off by default/until activated) and `dynamicStore.allowStrictMath()` toggles only between `Math.pow` and `StrictMath.pow`, not between float and fixed/BigDecimal arithmetic: [2](#0-1) [3](#0-2) 

The codebase itself contains an already-recognized, disabled-by-default fix, `SafeExchangeProcessor`, which redoes the same math in `BigDecimal` with 18-digit scale specifically to avoid this precision issue: [4](#0-3) 

and the project's own test suite explicitly documents that the legacy `double`-based processor and the hardened `BigDecimal` processor diverge on the same inputs (`Assert.assertNotEquals(anotherTokenQuant, result)`): [5](#0-4) 

confirming that the legacy default path indeed produces materially incorrect results relative to the precise calculation, exactly the "1499 instead of 1000" style discrepancy from the reference report.

### Impact Explanation
Any account can create an exchange pool and drive it into a highly skewed balance ratio (e.g., injecting a very large amount of one token relative to the other, up to `getExchangeBalanceLimit()`), then perform a series of small `ExchangeTransactionContract` trades. Because the resulting `buyTokenQuant`/`anotherTokenQuant` are derived from a `double` computation whose precision degrades under such ratios, an attacker can extract tokens from the pool in excess of (or in amounts inconsistent with) the intended constant-formula curve, effectively creating an economically unbacked balance or draining counter-party liquidity — a concrete "theft of funds"/"unbacked balance" outcome, matching the accepted impact classes.

### Likelihood Explanation
The vulnerable path is the default execution path: `allowHarden()` must be explicitly enabled via a chain proposal to switch to the safe `BigDecimal` processor, and until/unless that proposal is active, every `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawActuator` call from an unprivileged account runs through the imprecise `ExchangeProcessor`. No special privileges beyond creating/using a TRC10 exchange pool are required, and the project's own tests already prove numeric divergence between the legacy and hardened processors on realistic pool sizes, indicating the discrepancy is not merely theoretical.

### Recommendation
Make the `BigDecimal`-based `SafeExchangeProcessor` the default (non-optional) implementation for all TRC10 exchange math, removing the `double`/`Math.pow` code path entirely, or require a fixed minimum precision guard (reject swaps where the computed ratio underflows a safe threshold) before falling back to the legacy processor, consistent with the mitigation adopted for `pd_store`/`upd_twap` in the referenced report (avoid intermediate float scaling that can silently lose precision, or perform the whole computation in a wider fixed-point representation and only round once at the end).

### Proof of Concept
1. Create a TRC10 exchange pool via `ExchangeCreateContract`, then use repeated `ExchangeInjectContract` calls to skew `firstTokenBalance`/`secondTokenBalance` to a large ratio (bounded by `dynamicStore.getExchangeBalanceLimit()`), while `allowHarden()` remains disabled (default).
2. Issue a series of small `ExchangeTransactionContract` swaps (`sellTokenQuant` small relative to `newBalance`) — this hits `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, per `ExchangeCapsule.transaction`: [6](#0-5) 
3. Compare the returned `buyTokenQuant` against the value produced by `SafeExchangeProcessor.INSTANCE.exchange` for the same inputs (as done in `ExchangeProcessorTest.testStrictMath`, which already asserts the two differ): [5](#0-4) 
4. Repeating such skewed, low-ratio trades accumulates a measurable deviation from the exact constant-formula curve, which can be steered to consistently favor the trader executing the sequence, draining the counter-party token reserve beyond what the precise formula would allow.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
