### Title
Unbounded in-memory buffering of `git-pack-objects` stderr in the `PackObjectsHookWithSidechannel` RPC allows memory-exhaustion DoS by any user with fetch access - (File: `internal/gitaly/service/hook/pack_objects.go`)

### Summary
The external-report bug class is a "gas griefing" pattern: a call to an untrusted/external component is protected by a resource limit (`controllerGasLimit`), but the *response data* from that call is copied into memory without any size limit, so a malicious counterpart can force the caller to buffer disproportionate amounts of data. The Gitaly analog is in `runPackObjects()`, which invokes `git-pack-objects` under a per-IP concurrency limiter (`s.packObjectsLimiter.Limit`, in `runPackObjectsLimited`) but captures the subprocess's entire `stderr` stream into an unbounded `bytes.Buffer` regardless of that limit, and later interpolates the full buffer into an error string that is returned to the RPC caller.

### Finding Description
`PackObjectsHookWithSidechannel` is invoked for every `git fetch`/`clone` over SSH or HTTP by any authenticated user with read access to a repository, via `packObjectsHook` in `internal/gitaly/service/hook/pack_objects.go`. The actual `git-pack-objects` subprocess is executed by `runPackObjects`: [1](#0-0) 

While Gitaly does apply a per-remote-IP concurrency limiter around the pack-objects invocation (`runPackObjectsLimited`, which mirrors the "gas limit" concept of bounding the cost of the external call): [2](#0-1) 

...that limiter only bounds *concurrency*, not the *size of data read back from the external process*. The `stderr` of `git-pack-objects` is written into an in-memory `bytes.Buffer` (`stderrBuf`) with no cap, and this buffer is retained until the command finishes, then interpolated wholesale into an error string on failure:
```go
stderrBuf := &bytes.Buffer{}
stderr := io.MultiWriter(sw.Writer(stream.BandStderr), stderrBuf)
...
if err := cmd.Wait(); err != nil {
    return fmt.Errorf("git-pack-objects: stderr: %q err: %w", stderrBuf.String(), err)
}
```
This mirrors exactly the pattern flagged in the report: a call under a resource guard (concurrency/gas limit) whose *return channel* is copied into memory without any independent size limit, unlike `stdout`, which is bounded per write via `pktline.MaxSidebandData` framing through the sideband writer but never truncated in aggregate either — the `stderrBuf` copy has no bound whatsoever.

Because `git pack-objects` writes progress/warning/error diagnostics to stderr proportional to repository traversal work (and can be inflated further with flags such as `--progress`, or by pathological inputs producing many warnings, e.g. corrupt/ambiguous refs, shallow-negotiation edge cases, or huge numbers of "bad object" warnings for crafted requests), a client can cause the server to accumulate large amounts of unbounded, unmetered memory per concurrent request. Every additional concurrent fetch call across many distinct remote IPs multiplies this, since the limiter keys by IP and does not constrain the aggregate memory used by buffered stderr across the fleet of requests.

### Impact Explanation
Any user who can fetch/clone a repository (i.e., an ordinary authenticated Git user, not a privileged instance operator) can trigger this code path repeatedly and from many source IPs to accumulate large, unbounded stderr buffers server-side. This is a resource-exhaustion vector against the Gitaly process handling Git reads, since the concurrency limiter protects CPU-bound pack generation but not the memory consumed capturing diagnostic output, undermining the intended purpose of `PackObjectsHookMaxProc`/concurrency limiting as a DoS mitigation.

### Likelihood Explanation
Reaching this code path requires only ordinary fetch/clone permission on a repository — no admin or hook-installation privilege is needed, since `PackObjectsHookWithSidechannel` is invoked transparently by `git-upload-pack` on every fetch via `uploadpack.packObjectsHook`. Producing meaningfully large stderr output requires some cooperation from repository content/flags, so likelihood is moderate rather than trivially exploitable at scale, but the missing bound is a straightforward, concrete code defect independent of exploit sophistication.

### Recommendation
Wrap `stderrBuf` with a bounded writer (e.g. `io.LimitWriter`/`iotest`-style capped buffer, matching the approach implied by `CustomHookError`'s "Data may be truncated" semantics in `proto/errors.proto`) so that at most a fixed number of bytes (e.g. a few KB) of `git-pack-objects` stderr are retained for logging/error reporting, while the full stream continues to be forwarded to the client over the sideband channel unaffected. Apply the same bound consistently wherever subprocess stderr/stdout is captured into memory for diagnostic purposes.

### Proof of Concept
1. As an ordinary user with read access to a repository, initiate a `git fetch`/`clone` (SSH or HTTP) that exercises the pack-objects hook path (`PackObjectsHookWithSidechannel`).
2. Craft the fetch/negotiation request (e.g., via `--progress`, unusual shallow/deepen parameters, or a repository state producing many `git-pack-objects` warnings) to maximize stderr output from the underlying `git-pack-objects` invocation.
3. Issue many such requests concurrently from distinct source IPs (to bypass the per-IP concurrency limiter in `runPackObjectsLimited`), observing that Gitaly's memory usage grows proportionally to the aggregated, unbounded `stderrBuf` allocations in `runPackObjects` (`internal/gitaly/service/hook/pack_objects.go`), independent of the concurrency guard meant to bound resource usage of the underlying call.
