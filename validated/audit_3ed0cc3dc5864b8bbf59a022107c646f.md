### Title
Unstaked connection floods can exhaust the shared handshake-headroom pool gating all incoming QUIC connections, causing legitimate staked connections to be refused - (File: streamer/src/nonblocking/quic.rs)

### Summary
`ClientConnectionTracker::new` enforces a single global ceiling, `max_concurrent_connections() = (max_staked_connections + max_unstaked_connections) * 5 / 4`, before any peer-type (staked/unstaked) classification occurs, since stake can only be determined after the QUIC/TLS handshake completes. An attacker opening many concurrent unstaked handshake attempts can consume this shared "25%" headroom, causing subsequent `incoming.accept()` calls—including those from legitimate staked peers—to be refused via `refused_connections_too_many_open_connections`.

### Finding Description
In `streamer/src/nonblocking/quic.rs`, the accept loop calls `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())` on every incoming connection attempt, prior to `incoming.accept()` and prior to any determination of whether the connecting peer is staked or unstaked [1](#0-0) . The counter (`stats.open_connections`) is a single global atomic shared by staked and unstaked attempts alike [2](#0-1) . The ceiling itself, `max_concurrent_connections`, is computed as `(max_staked_connections + max_unstaked_connections) * 5 / 4` with the comment "Allow 25% more connections than required to allow for handshake" [3](#0-2)  (an equivalent version exists in `simple_qos.rs` at [4](#0-3) ). Because peer type/stake is unknown at the time this tracker slot is reserved, the 25% margin is not reserved specifically for staked connection setup — it's shared indiscriminately with unstaked/unprivileged attempts.

An unprivileged remote client can open many concurrent QUIC connections to the TPU port. Each connection acquires a `ClientConnectionTracker` slot as soon as it's accepted from the endpoint queue, before `setup_connection` completes the handshake and before `try_add_connection` classifies it into the staked or unstaked `ConnectionTable`. If the attacker can keep enough connections in the pre-classification/handshake phase concurrently (bounded only by per-IP `ConnectionRateLimiter` and the global `overall_connection_rate_limiter` token bucket that gate the *rate* of new attempts, not the *duration* they occupy a tracker slot) [5](#0-4) , they can push `open_connections` to the shared ceiling. Once at the ceiling, `ClientConnectionTracker::new` returns `Err(())` for **any** new connection attempt regardless of the connecting party's eventual stake, triggering `refused_connections_too_many_open_connections` and `incoming.refuse()` [1](#0-0) . This happens strictly before the staked-priority pruning logic in `try_add_connection`/`cache_new_connection` (which only operates on connections that already got past the tracker and completed handshake) ever runs [6](#0-5) .

The existing rate limiters (`ConnectionRateLimiter` per-IP and the `overall_connection_rate_limiter` token bucket) throttle the *arrival rate* of new connection attempts but do not bound how many *concurrently in-flight* (unclassified) connections can occupy tracker slots at once, nor do they distinguish based on eventual peer stake. Slots are only released when the `ClientConnectionTracker` is dropped — i.e., when the connection is closed/finalized (rejected as too-many-per-peer, completed and added to a table, or timed out) — so an attacker who deliberately stalls handshakes or floats many parallel half-open attempts can hold slots for the duration of the connection/handshake timeout window.

### Impact Explanation
Scoped impact is refusal of legitimate staked connection attempts during an attacker-induced handshake flood, i.e., a temporary denial-of-service against the TPU QUIC ingress for staked/legitimate traffic, degrading the leader's ability to admit vote/transaction connections from staked nodes. This maps to the "DoS of TPU ingress / QoS evasion" bounty category rather than any consensus-safety violation, since no invalid block or verification bypass is produced — only admission-control starvation at the connection layer.

### Likelihood Explanation
Preconditions are modest: the attacker needs no stake, only the ability to open many concurrent QUIC connections to the public TPU port from a sufficiently diverse set of source addresses to stay under the per-IP `ConnectionRateLimiter` while collectively exceeding the *shared* 25% global headroom relative to `max_staked_connections + max_unstaked_connections`. The `overall_connection_rate_limiter` bounds burst arrival rate (`MAX_CONNECTION_BURST`/`TOTAL_CONNECTIONS_PER_SECOND`) but does not bound standing concurrency once tokens replenish over time, so a sustained (not necessarily instantaneous) flood can still fill the ceiling. This is feasible and repeatable, though it requires meaningful sustained network resources (many source IPs/connections) rather than a single trivial packet, which somewhat lowers ease of exploitation.

### Recommendation
Reserve headroom capacity specifically for staked-peer handshake overlap by tracking unstaked and staked in-flight (pre-classification) connection attempts separately, e.g., cap unstaked-originated tracker slots at `max_unstaked_connections * 5/4` and staked-eligible slots at `max_staked_connections * 5/4` using two counters instead of one shared `open_connections` value, or defer the global ceiling check until after a lightweight peer-type hint (e.g., via retry/token or address validation) is available so unstaked floods cannot consume staked-reserved headroom.

### Proof of Concept
Integration test plan (extending `streamer/src/nonblocking/quic.rs` test module, similar to `test_client_connection_tracker`):
1. Configure `SwQosConfig` with small `max_staked_connections` and `max_unstaked_connections` (e.g., 4 and 4), yielding `max_concurrent_connections() == 10`.
2. Spawn the QUIC server via `setup_quic_server`.
3. From N attacker client endpoints (unstaked, no client cert matching a staked pubkey), concurrently open connections and stall before completing the handshake (e.g., via a slow/incomplete TLS handshake or by holding many `connecting` futures un-awaited) until `stats.open_connections` reaches `max_concurrent_connections()`.
4. Concurrently, from a legitimate staked client (registered in `StakedNodes`), attempt to connect within `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`.
5. Assert: `stats.refused_connections_too_many_open_connections` increments for the staked attempt, and the staked connection fails/times out — demonstrating that the shared ceiling, not any staked-specific reservation, caused the refusal.

Expected result confirming the bug: the staked client's connection attempt is refused (`refused_connections_too_many_open_connections` incremented) purely because unstaked attempts already saturated the global `open_connections` counter, with no code path exempting or reserving headroom for staked peers at the `ClientConnectionTracker` layer.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
