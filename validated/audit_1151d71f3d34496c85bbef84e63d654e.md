## #Vulnerability found: Active-permission key can hijack an account's Owner permission via `AccountPermissionUpdateContract`

### Title
Active permission can be authorized to execute `AccountPermissionUpdateContract`, allowing a low-trust key to overwrite the account's Owner permission without any Owner-key signature - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateActuator` lets a transaction rewrite an account's Owner permission, Witness permission and all Active permissions in one shot. Which key(s) may authorize this rewrite is determined purely by the transaction's `permission_id` and whatever `Permission` object that id resolves to — there is no requirement inside the actuator that a permission change must itself be authorized by the account's *current* Owner permission. The system explicitly allows `AccountPermissionUpdateContract` to be listed inside an Active permission's `operations` bitmap, so an account can be configured (or a compromised active key can configure it) so that a mere Active-permission signer — normally scoped to day-to-day operations — can rewrite the Owner permission itself, seizing full control of the account. This mirrors the MAS flaw where an already-authenticated but lower-assurance context could perform the most sensitive account-security action (password/email change, deactivation) without re-proving the stronger credential.

### Finding Description
`checkPermission()` in the actuator validates a submitted Active permission's `operations` bitmap only against `dynamicStore.getAvailableContractType()`: [1](#0-0) 

The test `checkAvailableContractTypeCorrespondingToCode` proves that `AccountPermissionUpdateContract` (id 46) *is* part of the set of "available" contract types that may legally be enabled in an Active permission's operations bitmap — only `ClearABIContract` and `UpdateBrokerageContract` are excluded: [2](#0-1) 

(Only the *default* Active permission created for new accounts excludes it, per `ACTIVE_DEFAULT_OPERATIONS`/`checkActiveDefaultOperationsCorrespondingToCode` — but nothing prevents a legitimate `AccountPermissionUpdateContract` transaction from later adding this bit to a custom Active permission.) [3](#0-2) 

Once an Active permission has that bit set, `TransactionCapsule.checkPermission`/`checkPermissionOperations` will accept a signature under that Active permission (via `permission_id` in the contract) as sufficient authorization for an `AccountPermissionUpdateContract`: [4](#0-3) [5](#0-4) 

`execute()` then unconditionally overwrites the Owner permission, Witness permission and Active permissions with whatever the contract specifies, with no additional check that the caller actually satisfied the *current* Owner permission: [6](#0-5) 

The net effect: a key that is only supposed to hold Active (day-to-day, lower-trust) authority can be leveraged to replace the account's Owner permission entirely — removing the legitimate owner's keys and installing attacker-controlled keys — exactly as the CVE describes a session lacking the stronger credential (current password) being able to perform the account's most sensitive security operations.

### Impact Explanation
If an account's Active permission is (or becomes) configured to include `AccountPermissionUpdateContract` in its operations bitmap, whoever controls a key meeting that Active permission's (typically much lower) threshold can submit a single transaction that replaces the account's Owner permission with keys of their choosing. This is a full, permanent account takeover: the legitimate owner can be locked out and the attacker gains total control (transfers, resource management, further permission changes) using only a lesser-privileged key that was never meant to hold Owner-level trust. This satisfies "concrete unauthorized account operation / theft or permanent freezing of funds."

### Likelihood Explanation
Exploitation requires that an Active permission on the target account has the `AccountPermissionUpdateContract` bit enabled in its operations bitmap. This is not the out-of-the-box default (`ACTIVE_DEFAULT_OPERATIONS` excludes it), but it is explicitly permitted by `getAvailableContractType()`/`checkPermission()`, so any account owner (via a normal, validly-signed `AccountPermissionUpdateContract`) or any wallet/dApp tooling that offers "grant this active key full account management" can produce this configuration, intentionally or by mistake. Once set, exploitation by anyone holding a qualifying Active key is a single broadcastable transaction — no special privileges beyond that key are required.

### Recommendation
Disallow `AccountPermissionUpdateContract` (and ideally other identity/permission-defining contract types) from being included in `getAvailableContractType()`'s permitted bitmap for Active permissions, mirroring the exclusion already applied to `ClearABIContract`/`UpdateBrokerageContract`. Additionally, consider requiring that any `AccountPermissionUpdateContract` transaction be authorized specifically via `permission_id == 0` (the account's actual current Owner permission), rather than allowing delegation of this operation through Active-permission operation bitmaps.

### Proof of Concept
1. Account X has Owner permission `{ownerKey}` and an Active permission `{activeKey}` (threshold 1) whose `operations` bitmap has been set (via a normal, validly signed `AccountPermissionUpdateContract` from `ownerKey`) to include bit 46 (`AccountPermissionUpdateContract`) — allowed by `checkPermission()`/`getAvailableContractType()`.
2. Attacker who controls `activeKey` (e.g., a compromised or intentionally lower-trust dApp-facing key) crafts a new `AccountPermissionUpdateContract` for account X, setting `owner_address = X`, `owner = {attackerKey}` (new Owner permission), signs it with `activeKey`, and sets `permission_id` to the Active permission's id.
3. `TransactionCapsule.checkPermission`/`checkPermissionOperations` accept the signature because the Active permission's operations bitmap allows `AccountPermissionUpdateContract`.
4. `AccountPermissionUpdateActuator.execute()` overwrites X's Owner permission with `{attackerKey}`, giving the attacker full control of account X using only the previously lower-trust `activeKey`.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
