### Title
Non-constant-time comparison of the RPC `auth_token` bearer secret enables timing-oracle recovery, bypassing block-proposal/replay/simulate authentication - (File: `stackslib/src/net/api/postblock_proposal.rs`, `stackslib/src/net/api/postblock_v3.rs`, `stackslib/src/net/api/blockreplay.rs`, `stackslib/src/net/api/blocksimulate.rs`, `stackslib/src/net/api/txsimulate.rs`)

### Summary
Several `stackslib` RPC endpoints authenticate privileged/expensive operations by comparing an attacker-supplied `authorization` HTTP header against the node's configured `auth_token` secret using Rust's native string inequality operator (`auth_header != password`). This mirrors the reported `pay` bug class exactly: a fixed shared secret is checked with a non-constant-time equality primitive, on a network-reachable path, creating a timing side channel that could let a remote attacker recover the secret byte-by-byte and unlock write/compute-heavy endpoints gated by that token.

### Finding Description
In `postblock_proposal.rs`, `postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, and `txsimulate.rs`, the `try_parse_request` handlers implement the identical pattern:

```rust
let Some(password) = &self.auth else { ... };
let Some(auth_header) = preamble.headers.get("authorization") else { ... };
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
``` [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

`auth_header != password` compares two `String`/`&str` values with Rust's derived `PartialEq`, which first compares lengths and then performs a byte-wise `memcmp`-style comparison that returns as soon as a mismatching byte is found — the same non-constant-time behavior flagged in the `pay` advisory for `hmac == h1`. The documentation for this configuration explicitly frames it as an exact plain-text secret match: "Plain-text secret value that must exactly equal the node's configured password" [6](#0-5) , and `docs/signing.md` confirms it is a shared secret (`auth_token` / `auth_password`) that must match exactly between the signer and node configs [7](#0-6) .

This is the same equality-fault pattern as the report: a static secret is checked against attacker-controlled bytes using an operator that is not guaranteed constant-time, on a remotely reachable, unauthenticated-until-this-check endpoint.

### Impact Explanation
If exploitable, an attacker who can measure fine-grained response timing to the node's RPC port could statistically recover the `auth_token` byte-by-byte (classic length-extension timing oracle), and then:
- Submit forged/broadcastable blocks via the authenticated branch of `postblock_v3` (`broadcast=1` path) [8](#0-7) .
- Access the block-proposal validation endpoint (`/v3/block_proposal`), which performs expensive validation work per request [9](#0-8) .
- Access block/tx simulation and replay endpoints, enabling bounded compute DoS or information probing on internal validation logic [10](#0-9) [11](#0-10) [12](#0-11) .

This falls in the "High" bucket described by the rules (auth bypass / bounded compute DoS on a read/compute endpoint gated by an auth check).

### Likelihood Explanation
Exploitability is uncertain and likely low in practice for several reasons I could not fully resolve given the available context:
- These endpoints are opt-in — the handler explicitly returns "Bad Request" if no password is configured at all (`self.auth` is `None`), so the endpoints are disabled by default unless an operator sets `auth_token`/miner/signer wiring. I was unable to confirm from available files whether these endpoints are enabled by default on a standard mainnet/follower node, or only enabled in specific miner/signer configurations, or whether the RPC surface is typically firewalled to a private network in production deployments.
- Rust's string/byte-slice equality on modern targets is compiled to vectorized comparisons that are not always a naive early-exit byte loop; the practical exploitability (i.e., a measurable timing signal over a real network, given also network jitter) is much less certain than for the Ruby `String#==` case, which is a well-established one-byte-at-a-time comparison in MRI. This is a code-quality/CWE-208 concern more than a confirmed practical exploit — I was not able to run timing microbenchmarks against this codebase to prove exploitability, unlike the original report's Ruby PoC.
- I was unable to verify from the indexed context whether `connection_options.auth_token` defaults to `None`/disabled for standard node operation, which would gate whether this is remotely reachable "out of the box."

### Recommendation
Replace `auth_header != password` with a constant-time comparison in all affected handlers (`postblock_proposal.rs`, `postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`), e.g. using `subtle::ConstantTimeEq` or an equivalent fixed-time byte comparison that does not short-circuit on length or content mismatch, mirroring the recommended `ActiveSupport::SecurityUtils.secure_compare` fix in the reference advisory. Centralize this check into a single shared helper function (e.g., in `httpcore.rs`) to avoid re-introducing the non-constant-time pattern in future endpoints.

### Proof of Concept
No live network timing PoC could be constructed within this analysis; the following demonstrates the vulnerable pattern in-repo and is analogous to the Ruby microbenchmark in the reference report:

```rust
// stackslib/src/net/api/postblock_v3.rs:104-111
if let Some(password) = &self.auth {
    if let Some(auth_header) = preamble.headers.get("authorization") {
        if auth_header != password {   // <-- non-constant-time '!=' on shared secret
            return Err(Error::Http(401, "Unauthorized".into()));
        }
        authenticated = true;
    }
}
```
An attacker with network access to a node configured with `auth_token` set could send repeated `POST /v3/blocks/broadcast` (or `/v3/block_proposal`, `/v3/blocks/replay/...`, `/v3/blocks/simulate/...`, `/v3/transactions/simulate`) requests with `authorization` header guesses of increasing matched-prefix length and measure response latency, analogous to the microbenchmark methodology in the referenced advisory, to attempt recovery of the `auth_token` value.

endpoint = "0.0.0.0:30000"
