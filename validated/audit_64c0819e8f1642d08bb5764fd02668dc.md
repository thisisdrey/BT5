### Title
Unchecked boolean result of SIP-010 `transfer` calls (`try!` only checks for `err`, not `(ok false)`) can allow non-standard tokens to fake successful deposits/withdrawals - (File: `mainnet/contracts/market/v0-market-vault.clar`)

### Summary
Zest's vault/market contracts move underlying SIP-010 tokens with patterns like `(try! (contract-call? asset transfer ...))`, and in one case return the raw `contract-call?` result without even a `try!`. `try!` in Clarity only short-circuits on an `(err ...)` response - if the SIP-010 `transfer` function returns `(ok false)` (a non-standard but valid `(response bool uint)`), `try!` treats it as success and discards the inner `false`, exactly the "non-standard ERC20 returns `false` instead of reverting" pattern from the referenced report.

### Finding Description
The `receive-tokens` helper in `v0-market-vault.clar` forwards the token's `transfer` response unchecked: [1](#0-0) 
Its counterpart `send-tokens` wraps the call in `try!` but likewise never inspects the boolean payload of a successful `(ok bool)` response: [2](#0-1) 
The same pattern (`try!` around `contract-call? ... transfer ...`, never checking the inner bool) recurs in every vault's `receive-underlying`/`send-underlying` helpers, e.g.: [3](#0-2) [4](#0-3) 
and in the DAO treasury withdraw path: [5](#0-4) 

The SIP-010 fungible-token trait specifies `transfer` returns `(response bool uint)`. A conformant/well-behaved token returns `(err ...)` on failure, which `try!` correctly propagates as an abort. However, nothing in the trait or in Clarity's type system prevents a token implementation from returning `(ok false)` instead of an error on a failed transfer - this is directly analogous to non-standard ERC20 tokens (e.g. `ZRX`-style) that return `false` rather than reverting. Because Zest's code uses `try!`/discards the boolean rather than `(asserts! (is-eq result true) ...)`, such a token would let `receive-tokens`/`receive-underlying` (deposit path) report success even though no tokens actually moved into the vault, and would let `send-tokens`/`send-underlying` (withdrawal path) report success even though the recipient received nothing.

### Impact Explanation
On the deposit side, this causes zTokens/shares to be minted and collateral/debt accounting updated as if real underlying tokens were received, while the vault's actual token balance is unaffected — this understates vault backing relative to minted shares, i.e. protocol insolvency for that vault. On the withdrawal side, `send-tokens`/`send-underlying` would decrement the withdrawing user's shares/debt while the user never receives the underlying asset, i.e. permanent freezing of that user's funds. Both map to the in-scope Critical impact classes (protocol insolvency, permanent freezing of funds).

### Likelihood Explanation
Low. This requires an asset onboarded into the market/vault set (`vault-stx`, `vault-sbtc`, `vault-usdc`, `vault-usdh`, `vault-ststx`, `vault-ststxbtc`, or any market-vault-tracked asset) whose SIP-010 `transfer` implementation is non-standard and returns `(ok false)` instead of erring on failure — mirroring the low likelihood assigned in the original report because few tokens deviate this way, and asset listing itself is a DAO-controlled action (out of scope to attack directly, but the code-level unchecked-boolean weakness is the in-scope root cause being reported here).

### Recommendation
After every `contract-call? <asset> transfer ...`, explicitly assert the inner boolean is `true` (e.g. `(asserts! (try! (contract-call? asset transfer ...)) ERR-TRANSFER-FAILED)`) instead of relying on `try!` alone, in `receive-tokens`/`send-tokens` (`v0-market-vault.clar`), `receive-underlying`/`send-underlying` in every vault contract, and the treasury `withdraw` function.

### Proof of Concept
1. DAO lists an asset whose SIP-010 `transfer` returns `(ok false)` on failure conditions (e.g., insufficient balance, blacklist, paused state) instead of `(err ...)`.
2. A user calls a market/vault entry point that ultimately invokes `receive-tokens`/`receive-underlying` to pull that asset from the user.
3. The token's internal transfer fails and returns `(ok false)`; `try!` unwraps to `false` but the code path does not check it, so the deposit function proceeds to mint shares/credit collateral as though the transfer succeeded.
4. The vault's real token balance never increased, but its liability (minted shares) did — later redemptions by other depositors fail once the shortfall is discovered, demonstrating insolvency/frozen funds.
