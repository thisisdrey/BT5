### Title
Weight-Reuse in `ValidateMultiSign` Precompile Allows a Single Key to Be Counted Multiple Times Toward a Multi‑Sig Threshold - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompile is meant to let a smart contract verify that a set of signatures over some data collectively satisfies an on-chain account `Permission`'s weight threshold — the TVM analogue of the "combined validation context" in the Envoy CVE, where several credential checks are supposed to be aggregated safely. Its de-duplication logic only skips a signature that is byte-for-byte identical to one already processed; if the same signer produces a second syntactically different signature over the same hash that still recovers to the same address, the loop falls through and adds that signer's weight to `totalWeight` again. This lets a caller satisfy a `threshold` that was intended to require multiple independent keys using effectively one key, in violation of the account's declared multi-sig permission (an access-control/authorization bypass reachable from any TVM contract call).

### Finding Description
`ValidateMultiSign.execute()` iterates the supplied signature array, recovers each signer address, and accumulates `Key.getWeight()` into `totalWeight`: [1](#0-0) 

The duplicate-detection only rejects an exact repeat: it checks whether `recoveredAddr` was seen before, and if so, whether the exact `sign` bytes (address+signature merged) were already recorded; if the signature bytes differ (e.g. a different-but-still-valid encoding of a signature from the same key, or a malleable ECDSA signature `(r, n-s)` that recovers to the same address as `(r, s)`), the code does **not** `continue` — it only calls `MUtil.checkCPUTime()` and then proceeds to add that key's weight a second time: [2](#0-1) 

This differs from the consensus-level multisig weight check used for transaction broadcast, `TransactionCapsule.checkWeight`, which explicitly tracks signers by recovered address and throws `PermissionException("... has signed twice!")` if the same address appears more than once: [3](#0-2) 

So the same underlying "shared secret" (a single private key) is allowed to satisfy what should be *distinct* weighted slots in the combined threshold check performed by the precompile — analogous to the CVE-2020-8664 pattern where reusing one credential across multiple validation resources caused a portion of the intended access-control check ("distinct signer required per weight unit") to silently not be enforced, even though the permission's `threshold`/`keysList` (the "static part") is visible and appears correctly configured.

### Impact Explanation
Any smart contract on TRON that uses `ValidateMultiSign` (address `0x0000...09`) to gate an action — e.g., a custodial/vault/escrow contract requiring N-of-M signers before releasing funds, or a governance contract requiring multiple approvers — can have its authorization check defeated by a single signer supplying two distinct valid encodings of a signature (or, where malleable-signature acceptance is not additionally filtered upstream, the `(r, n-s)` malleable counterpart) for the same signing key. This directly produces an authorization bypass: unauthorized execution of an action that was supposed to require independent multi-party approval, which can translate into theft of funds held by such a contract or unauthorized state changes gated by the precompile.

### Likelihood Explanation
The precompile is reachable by any account via a plain `TriggerSmartContract` call from any contract that calls `ValidateMultiSign` — no special privilege is required. Building a second differently-encoded-but-recovering-to-the-same-address signature is a standard ECDSA signature-malleability operation requiring only the original signature (not the private key), making exploitation straightforward for anyone able to obtain one valid signature from the targeted key (e.g., their own key, or a leaked/observed signature). The condition depends on `ValidateMultiSign` actually being relied upon by a deployed contract for security-critical authorization, which is a reasonably common integration pattern for multisig-style dApps on TRON.

### Recommendation
In `ValidateMultiSign.execute()`, track already-counted signers strictly by `recoveredAddr` (not by the full merged `sign` bytes) and skip weight accumulation entirely once an address has been counted once — mirroring the "has signed twice" rejection already implemented in `TransactionCapsule.checkWeight`. Do not allow a second, differently-encoded signature from the same recovered address to add further weight.

### Proof of Concept
1. Deploy a contract that calls the `ValidateMultiSign` precompile with an account whose Active permission is `{threshold: 2, keys: [(A, weight=1), (B, weight=1)]}`.
2. Using only key `A`, produce one valid signature `sig1` over `hash = sha256(address || permissionId || data)`.
3. Derive a second, byte-different signature `sig2` from the same key that still recovers to address `A` (e.g., the ECDSA malleable counterpart `(r, n-s, adjusted-v)` of `sig1`, or any other differently-serialized valid encoding accepted by `recoverAddrBySign`).
4. Call the contract with `signatures = [sig1, sig2]`.
5. In `ValidateMultiSign.execute()`: `sig1` is processed and `A`'s weight (1) is added; for `sig2`, `matrixContains(executedSignList, recoveredAddr)` is true (address `A` seen) but `matrixContains(executedSignList, sign)` is false (different bytes), so the code does not skip — it adds `A`'s weight again, making `totalWeight = 2`, which meets `threshold = 2` even though key `B` never signed.
6. The precompile returns `dataOne()` (success), and the calling contract proceeds as if a genuine 2-of-2 (or N-of-M) authorization occurred, using only a single signer's key — confirming the authorization bypass.
