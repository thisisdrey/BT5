### Title
Unauthenticated `RecvError` packets allow a spoofing attacker to tear down established tunnels without any certificate or key material - (File: outside.go)

### Summary
`RecvError` packets in `readOutsidePackets` are dispatched to `handleRecvError` before any decryption, handshake, or certificate check happens, exactly like the reported `Holdefi` bug where `setHoldefiContract` could be called by anyone before any privileged initialization occurred. `handleRecvError` only performs a comparison against the peer's currently known UDP source address and, in the common case where that address is not yet populated, performs no verification at all before tearing down the tunnel and deleting the host state - the network equivalent of an unrestricted setter that lets any untrusted caller poison privileged state.

### Finding Description
`readOutsidePackets` handles `header.RecvError` in the "Unencrypted packets" branch, calling `f.handleRecvError` directly from the raw UDP payload with no cert/handshake verification of any kind: [1](#0-0) 

`handleRecvError` itself only gates on a config flag (`acceptRecvErrorConfig`) and then looks up the hostinfo by the (attacker-supplied, cleartext, unauthenticated) `RemoteIndex` field from the header: [2](#0-1) 

The only anti-spoofing check present is a comparison between the UDP source address of the incoming packet and `hostinfo.GetRemote()`: [3](#0-2) 

This check is skipped entirely whenever `hr.IsValid()` is false (e.g. before the remote endpoint has been learned/roamed for that hostinfo, or in any state where `GetRemote()` returns a zero value) — in that case `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` execute unconditionally on an attacker-supplied index, with zero cryptographic authentication. Even in the case where `hr` is valid, defeating the check requires only source-UDP-address spoofing (no cert, no key, no CA membership) — a much weaker bar than the "valid-certificate-holder" exclusion in scope, and identical in spirit to the original bug: a state-mutating function (`setHoldefiContract`/`closeTunnel`+`DeleteHostInfo`) that is reachable by anyone because the code trusts caller-supplied identity instead of a cryptographic proof.

### Impact Explanation
An attacker who can observe or guess `RemoteIndex` (visible in the cleartext header of every packet on the wire, including handshake/keepalive traffic) and spoof or reuse a matching source UDP address can force `Holdefi`-style unrestricted teardown of any active nebula tunnel: the local hostinfo is deleted from both the main and pending hostmaps (`closeTunnel` → `hostMap.DeleteHostInfo`, `handshakeManager.DeleteHostInfo`) without any authentication. This is a remote state-poisoning / denial-of-service primitive against established, mutually-authenticated tunnels, achievable purely from the network without holding any CA-signed certificate.

### Likelihood Explanation
Likelihood is limited by the difficulty of learning/guessing the 32-bit `RemoteIndex`, but this value is transmitted in cleartext in every nebula packet header, so any attacker who can observe traffic between two nodes (on-path attacker, misbehaving relay, compromised network segment) trivially obtains it. Combined with the unconditional bypass when `GetRemote()` is not yet populated, or with UDP source spoofing where routing conditions permit it, this is practically exploitable without any privileged access or valid certificate.

### Recommendation
Do not allow `RecvError` to mutate hostinfo/hostmap state based solely on an unauthenticated UDP source-address match. At minimum: (1) never process `RecvError` when `hostinfo.GetRemote()` is invalid/unset, treating that as "deny" rather than "allow"; (2) require some additional proof of liveness/authenticity (e.g., only accept `RecvError` after a matching authenticated packet was recently sent to that same index/address, or bind acceptance to a short freshness window tied to an actual send); (3) consider deprecating the unauthenticated `RecvError` fast-teardown path entirely in favor of the existing authenticated `CloseTunnel` message type for tearing down tunnels.

### Proof of Concept
1. Establish a tunnel between `me` and `them`.
2. Observe (or otherwise learn) `them`'s `RemoteIndex` for the tunnel with `me` via any cleartext nebula packet header.
3. Before `me`'s hostinfo has recorded `them`'s remote UDP endpoint (`GetRemote()` invalid) — e.g., immediately after handshake before any roam — send a raw UDP packet of `header.RecvError` type with that `RemoteIndex` to `me`'s UDP port from an arbitrary source address.
4. `handleRecvError` finds the hostinfo by `RemoteIndex`, skips the address check because `hr.IsValid()` is false, and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)`, silently tearing down the tunnel with no cryptographic proof of identity — comparable to `CollateralsWallet.setHoldefiContract` being callable by anyone to hijack privileged contract state.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}
```
