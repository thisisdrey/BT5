### Title
Unbounded array-size allocation from attacker-controlled `DataWord` length in `PrecompiledContracts` ABI-array extraction helpers - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The Poppler CVE-2019-9959 bug class is: a length field parsed from untrusted input is never validated (not checked for being unreasonably large before use), so the parser directly allocates a heap buffer whose size is fully attacker-controlled, producing an uncontrolled/oversized allocation. `PrecompiledContracts` contains the same pattern: the private helper methods `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` take a length value straight from calldata (`words[offset].intValueSafe()`) and immediately allocate a `byte[][]` of that size with no upper-bound sanity check.

### Finding Description
`extractBytes32Array`, `extractBytesArray` and `extractSigArray` are ABI-array decoding utilities used by TVM precompiled contracts to parse dynamic arrays passed in the `data` payload of a `CALL` to a precompiled-contract address: [1](#0-0) 

In each of these, `len` is derived directly from a 32-byte word in the caller-supplied `data` via `DataWord.intValueSafe()`, and is used immediately to size a `byte[][]` array (`new byte[len][]`) with no explicit maximum-size or bounds validation before the allocation. `intValueSafe()` is designed to keep the returned `int` within Java `int` bounds for large `DataWord` values, but it does **not** limit the value to anything close to a reasonable array size — an attacker can set the length word to a value that decodes to a very large positive `int` (up to `Integer.MAX_VALUE`), causing the JVM to attempt to allocate an array with billions of reference slots in a single call, exactly mirroring `JPXStream::init`'s failure to bound a length before allocating a heap chunk of attacker-controlled size.

The other bound check present (`if (offset > words.length - 1) return new byte[0][];`) only prevents an out-of-range *offset*, it does nothing to validate the *length* value read from that offset, so the core defect — “trust the length field, allocate immediately” — is unmitigated.

### Impact Explanation
Any contract deployer or transaction sender can trigger these helpers by invoking (via a smart contract `CALL`/deployment/transaction) the precompiled contract(s) that use these ABI-array extraction utilities, supplying a crafted length word. The resulting attempted allocation of an oversized `byte[][]` causes the executing thread to throw `OutOfMemoryError` while processing the transaction inside the VM. Because `OutOfMemoryError` is a JVM-level `Error` (not a checked/unchecked `Exception`), depending on how it propagates through the transaction-execution/`Manager.processTransaction` call stack it can leave the JVM heap in an unstable state or terminate node threads outside normal exception handling used for VM reverts, resulting in a node crash / denial of service for a validating/witness node processing the block — a legitimate Medium-severity impact analogous to the referenced CVE's "large heap allocation with attacker-controlled size" primitive.

### Likelihood Explanation
The attack requires only a single crafted transaction/contract call reaching a precompiled contract that uses one of these helpers with attacker-controlled offset/length words in the call data — no special privileges, staking, or trusted role is needed, making the trigger trivially reachable by any unprivileged broadcaster.

### Recommendation
Add an explicit upper bound check on `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` (e.g., reject if `len` exceeds a small sane maximum consistent with the maximum possible number of elements representable by the remaining `data` length, similar to `RLP.verifyLength`'s bounds check against `availableLength`), before performing the `new byte[len][]` allocation, and ensure any resulting `OutOfMemoryError`/`NegativeArraySizeException` in precompiled-contract execution is caught and converted into a normal VM revert rather than escaping the transaction-processing call stack.

### Proof of Concept
1. Deploy or use an existing contract that performs a `CALL`/`STATICCALL` to the precompiled-contract address whose implementation invokes `extractBytesArray`/`extractSigArray`/`extractBytes32Array` (e.g., a batch-signature-validation style precompile that parses a dynamic array argument).
2. Craft the call data so the word at the array-length `offset` decodes (via `DataWord.intValueSafe()`) to a very large positive value (e.g., close to `Integer.MAX_VALUE`).
3. Broadcast the transaction; when the precompiled contract's `execute(byte[] data)` reaches `new byte[len][]`, the JVM attempts an allocation of billions of array slots, throwing `OutOfMemoryError` during transaction execution.

I was not able to retrieve the full body of `DataWord.intValueSafe()` or the exact call sites that invoke `extractBytesArray`/`extractSigArray`/`extractBytes32Array` within my remaining tool budget, so the specific precompiled-contract name(s) that expose this path and the precise clamping behavior of `intValueSafe()` for negative-looking words are not fully confirmed from the index; a Devin session with full repository access would be needed to pin down the exact caller(s) and verify end-to-end exception propagation.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
