#No Vulnerability found for this question.

The premise of the question does not match the actual code path. `validate_receipt` with `ValidateReceiptMode::NewReceipt` performs the exact borsh byte-size check described (`receipt_size > limit_config.max_receipt_size` → `ReceiptSizeExceeded`) and this is invoked **synchronously, immediately after each action executes**, inside `process_action_receipt`'s action loop in `runtime/runtime/src/lib.rs`, before the action's result is merged into the receipt's execution outcome: [1](#0-0) [2](#0-1) 

This means the size check happens during chunk application itself — the same deterministic step that both the chunk producer and every chunk validator execute — not "after the chunk is already produced." A maximal receipt (`max_actions_per_receipt` actions, each a max-size `FunctionCallAction`) would indeed pass the `TotalNumberOfActionsExceeded` count check in `validate_actions_with_mode` but fail size validation: [3](#0-2) 

But that failure surfaces as an `ActionErrorKind::NewReceiptValidationError(ReceiptSizeExceeded)` on the **triggering action/transaction only** — the enclosing chunk is still produced and applied successfully; only the offending transaction's execution outcome becomes a failure. This exact scenario is already covered by an existing test, `test_max_receipt_size`, which asserts this precise failure mode (transaction fails with `ReceiptSizeExceeded`, chunk/runtime continues normally): [4](#0-3) 

There is a known, already-documented edge case (issue #12606, tracked via `ValidateReceiptMode::ExistingReceipt`) where certain receipts can slip past this check by having their size increased *after* the `NewReceipt` validation (e.g., `output_data_receivers` mutated post-check via `promise_return`), but this is a distinct, already-known and intentionally tolerated bug — not a "shard halts because producer is unaware" scenario, since `ExistingReceipt` mode is deliberately lenient to keep the runtime from dying rather than causing consensus divergence: [5](#0-4) 

`receipt_manager.rs`'s `create_action_receipt` does not itself enforce the byte-size bound at construction time, but this is not exploitable: enforcement happens deterministically at the same point (`validate_receipt` call site in `lib.rs`) for every node applying the chunk, so there is no path where a chunk producer "doesn't know" and produces an invalid chunk that a validator later rejects — both compute the same result from the same wasm execution. [6](#0-5) 

No reachable shard-halting or fund-loss impact exists for the exact scenario described; the described "TotalNumberOfActionsExceeded passes but ReceiptSizeExceeded fires only after chunk production" sequence does not occur in this codebase.

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ValidateReceiptMode {
    /// Used for validating new receipts that were just created.
    /// More strict than `OldReceipt` mode, which has to handle older receipts.
    NewReceipt,
    /// Used for validating older receipts that were saved in the state/received. Less strict than
    /// NewReceipt validation. Tolerates some receipts that wouldn't pass new validation. It has to
    /// be less strict because:
    /// 1) Older receipts might have been created before new validation rules.
    /// 2) There is a bug which allows to create receipts that are above the size limit. Runtime has
    ///    to handle them gracefully until the receipt size limit bug is fixed.
    ///    See https://github.com/near/nearcore/issues/12606 for details.
    ExistingReceipt,
}

        };
