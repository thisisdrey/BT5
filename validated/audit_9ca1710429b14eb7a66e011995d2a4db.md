### Title
Attacker can dust-fill a victim's per-account token list to `MAX_TOKENS_PER_USER`, DoSing deposits, borrows, and inbound transfers - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Every `DepositToken` balance change from zero registers the token in the victim's `depositTokensOfAccount` set via `Pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` once the combined `debtTokensOfAccount + depositTokensOfAccount` length reaches `MAX_TOKENS_PER_USER = 30`. An unprivileged attacker can deposit dust of each listed collateral and `transfer()` 1 wei of each `msdToken` to a victim, force-filling the victim's list and causing all subsequent first-time token additions — deposits of new collateral, minting of a new `DebtToken`, `seize` proceeds, or plain inbound `msdToken` transfers — to revert. This is the same bug class as the OpenQ report: an attacker injects unwanted token entries into a victim-dependent accounting structure so that legitimate flows revert. (File: `contracts/DepositToken.sol`, `contracts/Pool.sol`)

### Finding Description
In `DepositToken._transfer` (and equivalently `_mint`), a recipient whose balance transitions from `0` is appended to the per-account set:

```solidity
// contracts/DepositToken.sol
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```

`Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` enforce a hard cap:

```solidity
// contracts/Pool.sol
uint256 public constant MAX_TOKENS_PER_USER = 30;

modifier onlyIfAdditionWillNotReachMaxTokens(address account_) {
    if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
        revert UserReachedMaxTokens();
    }
    _;
}
```

There is no opt-in, whitelist check, or minimum-amount filter on the recipient side: any first-time `transfer`/`deposit`/`seize`/`issue` crediting a token the victim doesn't already hold counts toward the cap. The attacker therefore controls entries in the victim's list simply by sending dust `msdTokens` — `DepositToken.transfer` only checks `_revertIfLocked` on the *sender*, never on the recipient. The same applies to `DebtToken` mints (`addToDebtTokensOfAccount`), so once the list is full the victim cannot mint debt of a synthetic they haven't borrowed before, cannot deposit a collateral type they haven't used, cannot receive a new `msdToken`, and a `Pool.liquidate` whose `seize` would credit a liquidator-position can't be aimed at victim-controlled flows — while the revert is deterministic (`UserReachedMaxTokens`), not a gas issue.

Relevant code: `Pool.addToDepositTokensOfAccount` (`contracts/Pool.sol:216-220`), `onlyIfAdditionWillNotReachMaxTokens` (`contracts/Pool.sol:143-148`), `DepositToken._transfer` (`contracts/DepositToken.sol:498-526`), `DepositToken._mint` (`contracts/DepositToken.sol:469-489`), `DepositToken.seize` (`contracts/DepositToken.sol:343-345`), `DepositToken.transfer` (`contracts/DepositToken.sol:348-354`).

### Impact Explanation
While the victim's list is saturated, every code path that would credit them a *new* token reverts: `deposit` into an unused `DepositToken`, `issue`/`mint` of an unused `DebtToken`, and any inbound `msdToken`/`DebtToken` transfer. Concretely this is a temporary freezing of the account's protocol functionality — the victim cannot open or top-up a position with a different collateral, cannot borrow a different synthetic, and cannot receive transfers of new `msdTokens` (including `seize` credits if the account acts as a liquidation beneficiary via smart-farming flows). Mitigation exists — the victim can transfer the dust `msdTokens` back out, since `DepositToken._transfer` removes the sender's entry when the balance hits zero and dust balances are not locked — but this costs the victim gas and transactions per injected token, and the attacker can re-grief. The attack requires the pool to list enough combined deposit+debt tokens to reach 30 slots (attacker fills `30 − victim's current tokens`); on deployments with fewer listed tokens the attacker can only partially consume capacity, and the victim can be re-targeted after remediation.

### Likelihood Explanation
The attacker is a plain EOA: they deposit a minimum amount of each listed collateral (paying the deposit fee) into their own account and then call `DepositToken.transfer(victim, 1)` for each token — no privileged role, oracle manipulation, or governance action is needed. The cost is bounded by the number of distinct collaterals they must hold dust in plus gas, and no funds are at risk since they can withdraw afterwards. Success depends on the deployed pool having close to 30 distinct deposit/debt tokens, or the victim already holding several. Exploitation is repeatable and front-runnable against any known victim address.

### Recommendation
Make per-account list insertion recipient-driven or revert-proof instead of attacker-driven:

- Do not auto-register tokens on passive receipt. Track collateral membership only via an explicit opt-in (e.g. `deposit`/`issue` mark the token "in use"; passive `transfer`/`seize` credits that aren't registered are excluded from `depositOf`, or a separate `enableCollateral` flag is required for a token to count toward health).
- Alternatively, decouple the list cap from reception: allow `addToDepositTokensOfAccount` to succeed past the cap for accounting/transfer purposes but cap only the number of tokens counted in `depositOf`/`debtPositionOf`, or keep a per-account `uint8` of "collateral-enabled" tokens.
- As a minimal mitigation, skip adding tokens for transfers below a dust threshold, or let `seize` route to a surrogate when the recipient's list is full rather than reverting.

### Proof of Concept
Hardhat-style test (place alongside the existing `UserReachedMaxTokens` cases in `test/Pool.test.ts`); the only change vs. the existing test is that entries are injected by real `DepositToken.transfer` calls from an attacker rather than impersonated calls:

```typescript
it('griefs victim by dust-filling their token list', async function () {
  // given: victim already holds some tokens, attacker deposits dust of every
  // other listed collateral and transfers 1 wei msdToken to victim
  const attacker = alice;
  const victim = bob;
  const max = (await pool.MAX_TOKENS_PER_USER()).toNumber();
  const victimTokens = (await pool.getDepositTokensOfAccount(victim.address)).length
    + (await pool.getDebtTokensOfAccount(victim.address)).length;

  for (const msd of allDepositTokensNotHeldByVictim) {
    const underlying = await msd.underlying();
    // attacker acquires and deposits a tiny amount of underlying
    await underlying.connect(attacker).approve(msd.address, ethers.constants.MaxUint256);
    await msd.connect(attacker).deposit(1, attacker.address);      // mints dust msdToken
    await msd.connect(attacker).transfer(victim.address, 1);       // adds entry to victim's list
    if ((await pool.getDepositTokensOfAccount(victim.address)).length + victimTokens >= max) break;
  }

  expect(
    (await pool.getDepositTokensOfAccount(victim.address)).length
      + (await pool.getDebtTokensOfAccount(victim.address)).length
  ).to.eq(max);

  // victim can no longer deposit a collateral they don't already hold
  await expect(
    someOtherDepositToken.connect(victim).deposit(1000, victim.address)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // victim can no longer mint a synthetic they haven't borrowed before
  await expect(
    someDebtToken.connect(victim).issue(100, victim.address)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // any inbound transfer of a new msdToken to victim reverts
  await expect(
    anotherDepositToken.connect(attacker).transfer(victim.address, 1)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
});
```

Note: I could not verify the number of currently listed deposit/debt tokens on each deployment from the indexed code; if a live pool lists far fewer than 30 tokens, the practical impact on that deployment is limited to consuming part of the victim's headroom rather than fully blocking them.
