### Title
Top-level `CreateAccount` bypasses implicit-account type check, allowing hijack of future NEAR-implicit account IDs - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_create_account` only validates account creation eligibility via `is_top_level()` / `is_sub_account_of()` and a length-vs-`min_allowed_top_level_account_length` check against the registrar; it never inspects `account_id.get_account_type()`. Because a 64-hex-character string (the exact shape of a NEAR-implicit account) has no dots, it is treated as a normal top-level account, and since its length (64) is not below `min_allowed_top_level_account_length` (32 on mainnet), the registrar-only restriction is skipped entirely, letting *any* signer explicitly create that account id and immediately `AddKey` with an attacker-controlled key.

### Finding Description
`action_create_account` (`runtime/runtime/src/actions.rs:167-210`) implements: [1](#0-0) 
This logic never checks `AccountType`; it purely checks dot-structure and, for top-level names, whether `len() < min_allowed_top_level_account_length`. Since a valid NEAR-implicit account id is always exactly 64 lowercase hex characters and contains no dots, it satisfies `is_top_level()` and its length (64) exceeds the typical `min_allowed_top_level_account_length` (32), so the registrar-restriction branch is skipped and the account is created for *any* predecessor.

Separately, `action_implicit_account_creation_transfer` (`runtime/runtime/src/actions.rs:213-244`) is the intended path for creating such accounts — it re-derives the type from the id and, for `NearImplicitAccount`, deterministically sets the access key to the public key encoded by the id itself: [2](#0-1) 
This path guarantees "only the holder of the matching private key can own the account," but it is only reachable via a plain `Transfer` action to a not-yet-existing account. There is no code in `action_create_account` that defers to, or is mutually exclusive with, this implicit-creation invariant — the two account-creation entry points are independent and the explicit-`CreateAccount` path does not defer to `get_account_type()` at all.

An attacker can therefore submit a transaction/receipt with `receiver_id` = a specific 64-hex string (a known or guessed victim implicit-account id) and `actions = [CreateAccount, AddKey(attacker_pubkey)]`, signed by any funded account. Because the length check exempts anyone from the registrar restriction once the name is long enough, this succeeds regardless of the signer's identity, creating the account under the attacker's key before the true key-holder ever transfers funds there.

I was not able to fully verify, within the available search budget, whether an additional pre-execution guard exists in `runtime/runtime/src/action_validation.rs` or `runtime/runtime/src/verifier.rs` that specifically rejects `CreateAccount` actions whose target id has `get_account_type() != AccountType::NamedAccount`. My searches for a function literally named `check_account_existence` in `.rs` sources returned no matches (only documentation references), and I could not read `action_validation.rs` in this session to confirm or rule out an equivalent check under a different name. This is a material verification gap.

### Impact Explanation
If no such guard exists, this is an authorization-escalation / fund-theft primitive matching NEAR's "theft of user funds" bounty category: an attacker can squat a known or predicted implicit-account id, install their own full-access key on it via `AddKey`, and later capture any deposit sent by the legitimate key-holder expecting standard implicit-account creation semantics. The `Transfer`-based implicit-creation invariant ("implicit accounts are only ever created with the key matching the id") would be silently violated for any account id an attacker manages to explicitly `CreateAccount` first.

### Likelihood Explanation
Practical exploitation requires the attacker to know a specific target hex account id in advance (e.g., a publicly displayed deposit address, an id derived from a public key shared out-of-band before the corresponding funding transfer lands on-chain), since blindly squatting the full 64-hex keyspace is computationally infeasible. Given a known target id, the attack costs only the gas/storage-staking deposit for one `CreateAccount`+`AddKey` transaction and is trivially repeatable for any long top-level name. This is gated entirely on whether `action_validation.rs`/`verifier.rs` already rejects such `CreateAccount` targets — which I could not conclusively confirm or refute.

### Recommendation
In `action_create_account` (or in the pre-execution validation of the `CreateAccount` action), explicitly reject `account_id.get_account_type() != AccountType::NamedAccount`, regardless of the top-level length/registrar branch, so that near-implicit and eth-implicit-shaped ids can never be created through the explicit `CreateAccount` path — only via `action_implicit_account_creation_transfer`.

### Proof of Concept
Integration/runtime-test-loop plan:
1. Construct a transaction from an arbitrary funded account (not the registrar) with `receiver_id` set to a syntactically valid 64-hex-char string (a valid `NearImplicitAccount`-typed id) and `actions = [CreateAccount, AddKey(attacker_pubkey)]`.
2. Apply it through the runtime and assert whether the account is created and the attacker's key is installed.
3. Assert expected behavior: `CreateAccount` should be rejected with an `ActionError` for any `account_id` where `get_account_type() != AccountType::NamedAccount`, independent of `is_top_level`/length/registrar checks.
4. Repeat for a 40-hex `0x`-prefixed eth-implicit-shaped id to confirm the same invariant.

Given the unresolved verification gap on `action_validation.rs`/`verifier.rs`, this should be treated as a finding requiring confirmation rather than a fully proven exploit chain.
