### Title
Rounding-to-zero in exact-match branch of market order matching lets a taker drain a maker's remaining inventory for free - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
In `MarketSellAssetActuator.matchSingleOrder`, when the taker's remaining buy amount exactly equals the maker's remaining sell amount ("taker == maker" branch), the payment the maker should receive (`makerBuyTokenQuantityReceive`) is computed via `MarketUtils.multiplyAndDivide`, an integer division that can round down to `0`. Unlike the sibling "taker < maker" and "taker > maker" branches, this branch has no check for a zero result, so the maker's whole remaining order is consumed while the maker receives nothing and the taker pays nothing for that portion of the trade.

### Finding Description
`matchSingleOrder` computes `takerBuyTokenQuantityRemain` via `MarketUtils.multiplyAndDivide` and explicitly guards against a `0` result by returning the sell tokens to the taker [1](#0-0) .

When `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()`, the code enters the "taker == maker" branch and computes `makerBuyTokenQuantityReceive` with the same rounding division, but performs **no zero-check** before consuming the maker's order and crediting the taker: [2](#0-1) 

Compare this to the "taker > maker" branch a few lines later, which computes the identical quantity via the identical `multiplyAndDivide` call and explicitly checks for zero, returning the sell tokens to the maker instead of consuming the order for free: [3](#0-2) 

The underlying division helper truncates toward zero for small numerators: [4](#0-3) 

The code comment at line 469-474 asserts "it would not happen here... for the maker, when sellQuantity < buyQuantity, it will get at least one buyToken even when sellRemain = 1" — but this invariant is about the price ratio `sellQuantity/buyQuantity`, not the value of `makerSellRemainQuantity`. The comment's own worked example ("sellQuantity=200, buyQuantity=100, sellRemain=1... X=199/2") shows the reasoning already concedes fractional/rounding edge cases exist; it only argues the specific "taker > maker" case is safe, and does not extend the argument to the "taker == maker" branch, which lacks any such analysis or protection.

Because `takerBuyTokenQuantityRemain` is guaranteed to be `> 0` at this point (checked at line 406), and this value can equal `makerOrderCapsule.getSellTokenQuantityRemain()` for arbitrary maker order states created by previous partial fills, the "taker == maker" branch is reachable with a maker remaining quantity for which `makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity` rounds down to 0 (e.g., `makerSellRemainQuantity = 1`, `makerBuyQuantity < makerSellQuantity`). In that scenario `makerOrderCapsule.setSellTokenQuantityRemain(0)` is executed unconditionally, marking the maker order fully filled and removing it from the book, while `addTrxOrToken(makerOrderCapsule, 0)` credits the maker with zero payment.

### Impact Explanation
The maker permanently loses the remaining sell-side inventory of their order without receiving the corresponding payment — this is a direct, unauthorized transfer/theft of value from the maker to the taker, reachable by any account placing a `MarketSellAssetContract` transaction (an unprivileged order placer). This matches the Medium-severity impact class of the referenced report (loss/misallocation of counterparty assets due to unguarded rounding-to-zero in trade settlement), though here the effect is direct value theft rather than a permanent lock, since the exchange facility itself isn't disabled.

### Likelihood Explanation
Reaching this state requires crafting maker/taker order price ratios and remaining quantities such that the exact-equality condition (`takerBuyTokenQuantityRemain == makerSellRemainQuantity`) holds while the maker's payout computation rounds to zero. This is achievable by an attacker who fully controls both the maker order (their own prior order, partially filled down to a small remainder) and the taker order parameters (`sellTokenQuantity`, `buyTokenQuantity`) in a single `MarketSellAssetContract` transaction, so it does not require any privileged role, cooperation, or timing — it can be engineered deterministically off-chain and submitted as ordinary transactions.

### Recommendation
Add the same zero-quantity guard used in the "taker > maker" branch to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0` (or, more precisely, if it doesn't meet a minimum settlement threshold), return the maker's remaining sell tokens via `returnSellTokenRemain`/`MarketUtils.returnSellTokenRemain` and mark the order inactive without crediting the taker, instead of unconditionally zeroing `makerOrderCapsule`'s remaining quantity and consuming it for free.

### Proof of Concept
Conceptual reproduction (values are illustrative; exact numbers require solving the integer-rounding constraint against `MarketUtils.multiplyAndDivide`):
1. Attacker A places a maker sell order: sell 200 unit of token X for 100 unit of token Y (price ratio 2:1), which gets partially filled by a normal counter-trade down to `makerSellTokenQuantityRemain = 1`.
2. Attacker (or a colluding/second account) B places a taker sell order such that, per `MarketUtils.multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity, makerBuyQuantity, ...)`, `takerBuyTokenQuantityRemain` computes to exactly `1` — matching the maker's remaining `1`.
3. Execution enters the "taker == maker" branch in `matchSingleOrder` [2](#0-1) ; `makerBuyTokenQuantityReceive = multiplyAndDivide(1, makerBuyQuantity, makerSellQuantity, ...)` rounds down to `0` because `makerBuyQuantity < makerSellQuantity`.
4. `makerOrderCapsule.setSellTokenQuantityRemain(0)` executes, the maker order is marked `INACTIVE` and removed from the book, and `addTrxOrToken(makerOrderCapsule, 0)` credits the maker with zero tokens — while the taker receives `takerBuyTokenQuantityReceive = 1` unit of token X for free (the taker's own sell-side deduction, `takerSellTokenLeft`, is reduced only by the zero `makerBuyTokenQuantityReceive`).

This flow was verified statically against the actuator source; dynamic execution against a running node/testnet would be needed to confirm the exact numeric parameters that satisfy the rounding condition, which is outside the scope of static code review.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
