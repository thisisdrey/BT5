Audit Report

## Title
Cross-chain replay of `hop_submit` promotion-consent signatures due to missing chain/genesis binding in the signed payload - (File: `substrate/client/hop/src/types.rs`)

## Summary
The `hop_submit` signing payload is computed by `submit_signing_payload` as `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || submit_timestamp.to_le_bytes())`, where `HOP_SUBMIT_CONTEXT` is the fixed literal `b"hop-submit-v1:"` shared across every deployment of `sc-hop`. [1](#0-0) [2](#0-1)  Because nothing in these signed bytes identifies the target chain (no genesis hash, spec version, or other chain-binding salt), a `(data, signer, signature, submit_timestamp)` tuple that is valid consent on one HOP-enabled chain is also valid on any other HOP-enabled chain sharing the same `AccountId` scheme and authorization policy.

## Finding Description
`HopRpcServer::submit` in `substrate/client/hop/src/rpc.rs` performs authorization and then signature verification purely against `submit_signing_payload(&hash, submit_timestamp)` and the signer's public key — it never queries or binds the local chain's genesis hash or any other chain-identifying material into the signed bytes. [3](#0-2)  The authorization check `can_account_promote` is evaluated first, gating on account and size only, with no chain-specific binding either. [4](#0-3) 

Once accepted, the tuple `(signer, signature, submit_timestamp)` persists in `HopEntryMeta` and is later carried into the unsigned promotion extrinsic via `HopRuntimeApi::create_promotion_extrinsic`, which itself only documents a timestamp tolerance window as the sole replay mitigation ("otherwise the same `(data, signer, signature)` tuple can be replayed indefinitely from the collator's persisted metadata") — with no mention of cross-chain scope. [5](#0-4)  The `HopEntryMeta` struct's own doc comments confirm the runtime pallet "re-verifies the submit signature using this key when the unsigned promotion extrinsic lands on-chain," with the freshness guarantee described purely in temporal terms ("old `(data, signer, signature)` tuples cannot be replayed indefinitely") — never addressing cross-chain replay. [6](#0-5)  The maintenance task in `promotion.rs` retrieves this exact authorization triple from local storage to build and submit the promotion extrinsic. [7](#0-6) 

Since `AccountId32`/`MultiSigner` key material is chain-agnostic, the same keypair produces the same account on every Substrate chain, so an observed `(data, signer, signature, submit_timestamp)` tuple from chain A's public state can be resubmitted verbatim to chain B's `hop_submit` within the timestamp tolerance window and will pass both the authorization check (if B's policy also authorizes that account) and the signature check (since the payload construction is byte-identical across chains).

## Impact Explanation
This is a forged/mis-bound proof-of-consent acceptance: a signature the user produced to authorize promotion specifically on chain A is accepted as valid consent for storage on chain B, causing B's runtime to store attacker-supplied recipient sets/content and attribute the submission to the victim's account without the victim ever consenting to that chain. This matches the "forged or mis-bound proof or state acceptance" / "unauthorized execution or origin escalation" categories in the impact gate, and can force unwanted permanent on-chain storage state onto a victim account on an unintended chain.

## Likelihood Explanation
No privileged actor is required. Any party observing a promoted HOP entry (public, on-chain data by design) can replay it against a second HOP-enabled chain where the same account happens to be authorized by `can_account_promote` — a realistic configuration for shared allowlists or permissive default policies across a family of parachains. The exploit path uses only the public `hop_submit` RPC.

## Recommendation
Bind `submit_signing_payload` to chain identity — e.g., include the local runtime's genesis hash (and ideally spec version) as part of the hashed payload — and have the runtime-side re-verification in `HopRuntimeApi::create_promotion_extrinsic`'s implementing pallet reject any promotion whose embedded chain-binding material does not match the local chain's genesis hash.

## Proof of Concept
1. Deploy two HOP-enabled chains, A and B, both configuring `can_account_promote` to authorize the same `AccountId`.
2. Submit `hop_submit(data, recipients, signature, signer, submit_timestamp)` on chain A; the entry is later promoted via `HopMaintenanceTask::tick`, exposing `(data, signer, signature, submit_timestamp)` in A's public chain state. [8](#0-7) 
3. Extract that tuple from A's state and call `hop_submit(data, recipients', signature, signer, submit_timestamp)` against chain B within the timestamp tolerance window.
4. Chain B's `submit` verifies the signature successfully because `submit_signing_payload` is identical on both chains (no chain-identifying bytes), and the entry is accepted/promoted on B under the victim's account without B-specific consent. [3](#0-2)

/// Compute the 32-byte payload signed at `hop_submit` time.
///
/// The runtime pallet re-derives this exact byte sequence to verify the
/// signature on-chain, so the construction must remain byte-identical to the
/// pallet's `signing_payload(data, submit_timestamp)`:
/// `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || submit_timestamp.to_le_bytes())`.
pub fn submit_signing_payload(hash: &HopHash, submit_timestamp: u64) -> [u8; 32] {
	let mut buf = [0u8; HOP_SUBMIT_CONTEXT.len() + 32 + 8];
	buf[..HOP_SUBMIT_CONTEXT.len()].copy_from_slice(HOP_SUBMIT_CONTEXT);
	buf[HOP_SUBMIT_CONTEXT.len()..HOP_SUBMIT_CONTEXT.len() + 32].copy_from_slice(hash.as_bytes());
	buf[HOP_SUBMIT_CONTEXT.len() + 32..].copy_from_slice(&submit_timestamp.to_le_bytes());
	blake2_256(&buf)
}

	/// Execute a single maintenance cycle: promote near-expiry entries and clean up expired ones.
	pub fn tick(&self) {
		let current_block = (self.best_block)();

		// Promote near-expiry entries one at a time to bound peak memory.
		if let Some(ref promoter) = self.promoter {
			const PROMOTION_BATCH_SIZE: usize = 10;
			let hashes =
				self.hop_pool
					.get_promotable(current_block, self.buffer_secs, PROMOTION_BATCH_SIZE);
			for hash in hashes {
				// First, ask the runtime whether this hash is already on-chain.
				// If so, the previous attempt (or a third party) already
				// landed it — flag locally and stop touching the chain.
				match promoter.is_promoted_on_chain(hash.as_fixed_bytes()) {
					Ok(true) => {
						self.hop_pool.mark_promoted(&hash);
						tracing::info!(
							target: "hop",
							hash = ?hex::encode(hash),
							"HOP entry already on-chain — flagged locally"
						);
						continue;
					},
					Ok(false) => {},
					Err(e) => {
						// Treat runtime-API failures as "unknown", which means
						// proceed with submission. Worst case we resubmit a
						// duplicate; the on-chain check will catch it next cycle.
						tracing::warn!(
							target: "hop",
							hash = ?hex::encode(hash),
							error = %e,
							"is_promoted_on_chain failed; assuming not on-chain"
						);
					},
				}

				let (data, signer, signature, submit_timestamp) =
					match self.hop_pool.get_with_auth(&hash) {
						Some(t) => t,
						None => continue,
					};
				let size = data.len();
				let result = promoter.promote(data, signer, signature, submit_timestamp);
