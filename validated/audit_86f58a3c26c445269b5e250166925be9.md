### Title
Overpaid storage deposit in `AddressRegistrar::register` is never refunded on success, permanently trapping user funds - (File: runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs)

### Summary
`AddressRegistrar::register`, part of the eth-implicit wallet contract's supporting infrastructure, validates the attached deposit with a `>=` check (`given_deposit < required_deposit` → panic) instead of an exact-match check. When the deposit is sufficient and the address is new (`Entry::Vacant`), the function consumes `given_deposit` in full and returns without refunding the surplus, unlike the `Entry::Occupied` branch, which explicitly refunds the entire deposit back to the caller on failure.

### Finding Description
In `register()`: [1](#0-0) 
computes `required_deposit` from the exact number of storage bytes needed and only panics if `given_deposit < required_deposit`; it never checks `given_deposit == required_deposit`. [2](#0-1) 
On the success path (`Entry::Vacant`) the account id is inserted and `Some(address)` is returned — there is no promise/transfer refunding `given_deposit - required_deposit` back to the caller. By contrast, the failure path (`Entry::Occupied`, address collision) explicitly issues a `promise_batch_action_transfer` refunding the caller's *entire* `given_deposit`. This asymmetry demonstrates the developers were aware refunds are necessary but omitted it for the success path.

This is the same bug class as the external report: a payable/deposit-consuming entry point accepts `msg.value`/`attached_deposit >= required_amount` instead of enforcing an exact amount, so any overpayment is silently absorbed rather than returned to the payer.

### Impact Explanation
Any unprivileged NEAR account (or, in the primary use case, funds routed via the ETH-implicit `wallet-contract`'s RLP-executed `register` call — see `wallet-contract/src/tests/sanity.rs`, `test_caller_refunds`) that attaches more than the exact storage cost to `register` permanently loses the excess: it becomes part of the `AddressRegistrar` contract's balance with no code path to reclaim it. This is a permanent freezing/loss of user funds for anyone who overestimates the storage cost (e.g., a wallet/relayer client that rounds up the byte cost, or retries with a stale `account_id.len()` estimate). Given that this contract is explicitly reachable by an ordinary/unprivileged eth-implicit-account caller and directly handles attached NEAR deposits, it satisfies the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Likelihood is bounded by user/client behavior: it requires the caller (or the wallet client constructing the transaction) to overestimate `required_deposit` when calling `register`. This is plausible for automated tooling that pads the deposit to be safe (a common pattern to avoid `LackBalanceForState`-style failures), similar to how the original Cally report noted a malicious/careless frontend could cause users to overpay. There is no attacker-controlled exploitation needed beyond crafting/relaying an overpaid `register` call; the loss is unconditional whenever `given_deposit > required_deposit` on the success path.

### Recommendation
On the `Entry::Vacant` success path, compute `given_deposit.checked_sub(required_deposit)` and, if positive, issue a `promise_batch_action_transfer` back to `env::predecessor_account_id()` for the surplus, mirroring the refund logic already present in the `Entry::Occupied` branch. Alternatively, require `given_deposit == required_deposit` (rejecting overpayment) as recommended in the original finding, though a refund is more user-friendly and consistent with existing NEAR runtime conventions (e.g., `Receipt::new_balance_refund`).

### Proof of Concept
1. Compute `required_deposit = storage_byte_cost * (20 + account_id.len())` for a fresh, non-eth-implicit `account_id`.
2. Call `AddressRegistrar::register(account_id)` attaching `given_deposit = required_deposit + N` yoctoNEAR (any `N > 0`), e.g. via the wallet-contract's `rlp_execute_from` path as in `test_caller_refunds` ( [3](#0-2) ) or directly as a `FunctionCall` with `deposit = required_deposit + N`.
3. The call succeeds (`given_deposit >= required_deposit`), the mapping is inserted, and `Some(address)` is returned.
4. Query the caller's account balance: it has decreased by `required_deposit + N`, not just `required_deposit`. No refund receipt is ever produced for `N`, and there is no contract method to withdraw it — the `N` yoctoNEAR is permanently stuck in the `AddressRegistrar` contract's balance.

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
