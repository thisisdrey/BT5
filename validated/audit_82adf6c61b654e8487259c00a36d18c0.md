### Title
Front-runnable `initialize()` on Zest vaults lets anyone with minimal underlying-token balance permanently DoS the DAO's vault-initialization proposal - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar` and sibling vaults)

### Summary
Each Zest vault (`v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) exposes a public `initialize` function with no access control other than a one-time-use flag. Anyone holding `MINIMUM-LIQUIDITY` (u1000, scaled by decimals) of the vault's underlying token can call it directly, exactly analogous to the Trader Joe `createRJLaunchEvent()` finding where anyone with 1 wei of the target token could front-run the legitimate creator and permanently block them.

### Finding Description
`initialize` is a `define-public` function guarded only by:
```clarity
(define-public (initialize)
  (begin
    (asserts! (not (var-get initialized)) ERR-ALREADY-INITIALIZED)
    (var-set initialized true)
    (try! (deposit MINIMUM-LIQUIDITY u0 NULL-ADDRESS))
    ...
    (ok true)))
``` [1](#0-0) 

Unlike `set-authorized-contract`, `set-cap-supply/debt`, etc., which call `check-dao-auth` (`(asserts! (is-eq tx-sender .dao-executor) ERR-AUTH)`) [2](#0-1) , `initialize` has **no such check**. It calls the internal `deposit`, which pulls `MINIMUM-LIQUIDITY` from `contract-caller` via `receive-underlying`:
```clarity
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
  (let (... (account contract-caller) ...)
    ...
    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    ...))
``` [3](#0-2) 

The intended flow is that the DAO deployment proposal (e.g. `v0-init.clar` / `proposal-protocol-init.clar`) calls each vault's `initialize` as part of a batched, atomic `execute` transaction that also registers assets, sets caps, and authorizes the market contract — see the equivalent local-testing proposal that performs this exact sequence:
```clarity
(try! (as-contract? ((with-all-assets-unsafe))
  (try! (contract-call? .vault-sbtc initialize))
  (try! (contract-call? .vault-usdh initialize))
  ...))
``` [4](#0-3) 

Because `initialize` is permissionless and callable by anyone holding `MINIMUM-LIQUIDITY` of the underlying token, any ordinary principal can call it directly on a not-yet-initialized vault before the DAO's proposal transaction executes. Since `initialized` is a one-shot boolean with no reset path, the DAO's subsequent `initialize` call inside its batched proposal will revert with `ERR-ALREADY-INITIALIZED`, causing the entire wrapped `try!` chain in the DAO's proposal `execute()` to fail and roll back — including the cap-setting and market-authorization steps for potentially all vaults in that batch, not just the front-run one.

### Impact Explanation
This maps to **temporary freezing of funds**: an unprivileged attacker who merely holds the smallest allowed amount of a vault's underlying token can cause the DAO's atomic vault-bring-up proposal (asset registration, cap configuration, and `market` authorization for all vaults) to permanently fail via `ERR-ALREADY-INITIALIZED`. Until governance detects this and drafts/passes a new proposal that accounts for the already-initialized vault (a process requiring a new DAO vote/deployment), the `market` contract cannot be authorized against the affected vault(s), preventing all users from depositing, borrowing, or using that asset in the lending market — a temporary but governance-cycle-length freeze of protocol functionality and funds routed through that vault.

### Likelihood Explanation
Likelihood is high in the deployment window: any address that acquires `MINIMUM-LIQUIDITY` of the relevant SIP-10 token (a small, often trivial amount, e.g. u1000 base units) can call `initialize` directly with no special privileges, exactly as in the referenced report where 1 wei of `_token` sufficed to call `createRJLaunchEvent()`. The attack requires no flashloan, no DAO compromise, and no oracle manipulation — only observing the pending/expected deployment and racing it, which is a normal frontrunning/mempool-monitoring capability on any public chain.

### Recommendation
Restrict `initialize` on all vault contracts (`v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) to be callable only by `.dao-executor` (or another explicitly authorized deployer/proposal contract), consistent with the `check-dao-auth` pattern already used for `set-authorized-contract`, `set-cap-supply`, `set-cap-debt`, and other administrative entry points in the same files.

### Proof of Concept
1. Vault contract (e.g. `v0-vault-usdc.clar`) is deployed but not yet initialized (`initialized` = false), before the DAO's init proposal transaction is mined.
2. Attacker acquires `MINIMUM-LIQUIDITY` (u1000, scaled) of the vault's `UNDERLYING` token.
3. Attacker calls `(contract-call? .v0-vault-usdc initialize)` directly — no auth check blocks this; `deposit` pulls `MINIMUM-LIQUIDITY` from the attacker via `receive-underlying`, mints shares to `NULL-ADDRESS`, and sets `initialized` to `true`.
4. The DAO's deployment/init proposal (analogous to `local-testing/contracts/proposals/proposal-init-vaults.clar` / `mainnet/contracts/proposals/mainnet/v0-init.clar`) subsequently executes its batched `try!` sequence, which includes `(try! (contract-call? .v0-vault-usdc initialize))`; this call now returns `ERR-ALREADY-INITIALIZED`, causing the entire proposal `execute()` to fail and roll back all steps in that transaction (asset registration, cap-setting, and market authorization for all bundled vaults).
5. The market cannot be authorized on the affected vault(s) until governance passes a new corrective proposal, temporarily freezing that vault's functionality for all legitimate users.
