### Title
Active-permission holders can rewrite an account's Owner permission via `AccountPermissionUpdateContract`, bypassing the Owner multi-sig threshold - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator` never verifies that the permission actually used to *authorize* an `AccountPermissionUpdateContract` transaction is the account's Owner permission (`permission_id == 0`). The generic signature/authorization check (`TransactionCapsule.checkPermission` / `WalletUtil.checkPermissionOperations`) only checks whether the bitmap flag for `AccountPermissionUpdateContract` happens to be set on whatever permission the signer used — including a low-threshold `Active` permission. If that bit is set on any Active permission (a normal, commonly-granted delegation, since `AccountPermissionUpdateContract` is within the globally allowed contract-type range returned by `getAvailableContractType()`), the holder of that Active key can submit a brand-new `AccountPermissionUpdateContract` that completely replaces the account's Owner permission — with keys and threshold of their choosing — without ever satisfying the original Owner multi-sig threshold. This is structurally the same bug class as the Poweradmin advisory: a lower-privilege delegated role (`user_edit_others`/Active permission) is able to reach and overwrite the highest-privilege credential (superuser password/Owner permission) because the enforcement of "who may touch the top tier" is missing at the actuator that actually performs the write.

### Finding Description
- The actual permission/authorization gate for every contract type, including `AccountPermissionUpdateContract`, is generic and bitmap-driven: [1](#0-0)  and [2](#0-1) . It only checks: "is `permission.getType() == Active`" and "is the bit for this `ContractType` set in `operations`" — there is no special-case requiring `permission_id == 0` (Owner) for `AccountPermissionUpdateContract`.
- `AccountPermissionUpdateActuator.validate()` similarly never checks which permission authorized the transaction; it only validates the *shape* of the new permissions being installed (key counts, thresholds, uniqueness, operations bitmap validity) via `checkPermission()`, then unconditionally overwrites the account's Owner/Witness/Active permissions in `execute()`: [3](#0-2) .
- The bitmap validation in `checkPermission()` only rejects bits that are not part of `dynamicStore.getAvailableContractType()`; it does not exclude `AccountPermissionUpdateContract` from ever being grantable to a non-Owner (Active) permission: [4](#0-3) .
- As a result, once an Active permission's `operations` bitmap includes the `AccountPermissionUpdateContract` bit (a routine, commonly-enabled delegation — the default active-permission operations mask is derived from `getActiveDefaultOperations()` and is broad by default: [5](#0-4) ), that low-threshold Active key can single-handedly submit a new `AccountPermissionUpdateContract` that installs an entirely new Owner permission (arbitrary keys/threshold), permanently locking out the original Owner signer(s) and their multi-sig threshold.

This is the direct analog of the Poweradmin flaw: the web/actuator path that actually performs the sensitive write (`updateUser` / `AccountPermissionUpdateActuator.execute()`) trusts a coarse, generically-checked permission (`user_edit_others` / any Active permission with the right bit) to authorize an action that should require the highest tier (superuser / Owner permission), and there is no additional, tier-specific guard comparable to Poweradmin's missing "reject non-superuser editing a superuser" and "require `user_passwd_edit_others`" checks.

### Impact Explanation
Any account that has delegated an Active permission whose `operations` bitmap includes `AccountPermissionUpdateContract` (a very ordinary multi-sig configuration, and the bit is included in the broad default active-operations mask) exposes itself to full account takeover by that Active key holder: the Active key, meeting only its own (typically much lower) threshold, can overwrite the account's Owner permission and Active/Witness permissions with attacker-controlled keys. This is equivalent to an unauthorized account-permission takeover — the original Owner(s) lose all control of the account, its balance, TRC10/TRC20 approvals, staking/voting rights, and (if the account is a witness) block-production credentials, with no requirement to ever meet the Owner threshold. This satisfies the "concrete unauthorized account operation" / permanent loss-of-control bar for high severity.

### Likelihood Explanation
The precondition (an Active permission holding the `AccountPermissionUpdateContract` bit) is common because: (1) it is part of the wide default active-operations bitmask assigned via `createDefaultActivePermission`/`getActiveDefaultOperations`, and (2) account owners frequently configure delegated Active keys for automation/hot-wallet use without realizing this specific bit grants full permission-rewrite capability. No special network condition or malicious-SR/witness assumption is needed — a single signed `AccountPermissionUpdateContract` transaction from a routine Active key is sufficient, exactly mirroring the single-API-request exploit in the Poweradmin report.

### Recommendation
In `AccountPermissionUpdateActuator.validate()`/`execute()` (and in the shared authorization check `TransactionCapsule.checkPermission` / `WalletUtil.checkPermissionOperations`), explicitly require `permission_id == 0` (the account's actual Owner permission) to authorize `AccountPermissionUpdateContract`, regardless of whether an Active permission's `operations` bitmap happens to include that bit. Additionally, exclude `AccountPermissionUpdateContract` from the set of contract types that can legally be enabled in an Active permission's `operations` field during `checkPermission()` validation, mirroring how Poweradmin's fix should mirror the web guard (superuser-only edit, and a dedicated permission for password-equivalent changes) inside the API/actuator path that actually performs the write.

### Proof of Concept
1. Account `A` is created with a standard Owner permission (2-of-2 multisig, e.g., keys `K1`,`K2`, threshold 2) and an Active permission with a single low-weight key `K3` (threshold 1) whose `operations` bitmap includes the bit for `AccountPermissionUpdateContract` (default active operations mask commonly includes this).
2. Attacker who controls only `K3` builds an `AccountPermissionUpdateContract` for `owner_address = A`, setting:
   - `owner` = new Owner permission with a single attacker key `K_evil`, threshold 1
   - `actives` = new Active permission also controlled by `K_evil`
3. Attacker signs the transaction using only `K3` and sets `permission_id = <Active permission id>` on the contract.
4. `TransactionCapsule.checkPermission`/`WalletUtil.checkPermissionOperations` passes because the Active permission's `operations` bitmap has the `AccountPermissionUpdateContract` bit set; `AccountPermissionUpdateActuator.validate()`/`execute()` accept and apply the new Owner permission, per [3](#0-2) .
5. Account `A` is now fully controlled by `K_evil`; the original Owner keys `K1`/`K2` can no longer authorize anything for the account, despite never having approved (or even met the 2-of-2 threshold for) this change.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
