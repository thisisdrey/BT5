## Title
Sandwichable spot-price-based liquidity injection in `ExchangeInjectActuator` allows value extraction from Exchange pool creators — (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The TRC10 `Exchange` (Bancor-style AMM) module lets any account create a token pair and later inject additional liquidity via `ExchangeInjectContract`. Unlike `ExchangeTransactionContract`, which carries an explicit `expected` (minimum-output) field used by `ExchangeTransactionActuator` to bound slippage [1](#0-0) , `ExchangeInjectContract` has no analogous slippage/ratio bound at all [2](#0-1) . The amount of the paired token an injector must (and does) also deposit/withdraw is derived purely from the pool's current spot balances at execution time, exactly the "spot price" pattern flagged in the referenced report.

### Finding Description
`ExchangeInjectActuator.doValidate()`/`execute()` computes the counter-token amount strictly from the current on-chain reserve ratio: [3](#0-2) 

This ratio (`secondTokenBalance * tokenQuant / firstTokenBalance` or vice versa) is the live spot price of the Bancor pool, the same `firstTokenBalance`/`secondTokenBalance` state mutated by `ExchangeTransactionActuator` on every trade [4](#0-3) . Because a single block on java-tron can contain many transactions in a chosen order (the broadcaster picking a low ordering nonce/priority, or any actor able to place a transaction immediately before/after the victim's), an attacker can:
1. Submit an `ExchangeTransactionContract` that heavily skews `firstTokenBalance`/`secondTokenBalance` right before the victim's pending `ExchangeInjectContract` is applied.
2. Let the victim's inject execute — `anotherTokenQuant` is now computed against the manipulated ratio, forcing the victim (the exchange creator, who is the only account allowed to inject per the `is not creator` check [5](#0-4) ) to deposit an unfavorable proportion of the two assets.
3. Submit a second `ExchangeTransactionContract` reversing the initial trade, restoring the pool price and pocketing the extra value the victim's injection effectively donated to the manipulated ratio.

`ExchangeInjectContract` provides no field the victim can use to bound the acceptable ratio/slippage (contrast with `ExchangeTransactionContract.expected`), so there is no way for the injecting party to protect themselves from this manipulation at the protocol level.

### Impact Explanation
An attacker able to control transaction ordering around a victim's `ExchangeInjectContract` (e.g., by paying enough energy/bandwidth priority, or via natural mempool timing) can extract real value from the pool creator's deposit, a concrete transfer of funds achieved purely through spot-price manipulation and no special privilege — the same bug class and impact (fund theft via sandwiching a spot-price-dependent operation) described in the source report for `SponsorVault`.

### Likelihood Explanation
Exploitation requires only two ordinary signed `ExchangeTransactionContract`s (broadcastable by anyone holding the relevant tokens) sandwiching a targeted `ExchangeInjectContract`; both TRC10 exchange transaction types are on the standard actuator/HTTP path (`/wallet/exchangetransaction`, `/wallet/exchangeinject`) reachable by any account, so likelihood is high whenever a creator injects meaningful liquidity into an active, low-liquidity pool.

### Recommendation
Add a slippage/ratio bound to `ExchangeInjectContract` (analogous to `expected` in `ExchangeTransactionContract`), e.g. a min/max accepted `anotherTokenQuant`, and have `ExchangeInjectActuator.doValidate()`/`execute()` reject the injection if the computed counter-token amount falls outside the caller-specified bounds.

### Proof of Concept
1. Exchange pool `P` has reserves `firstTokenBalance = A`, `secondTokenBalance = B`.
2. Creator broadcasts `ExchangeInjectContract{tokenId=first, quant=Q}` expecting to also deposit `~ B*Q/A` of the second token.
3. Attacker front-runs with `ExchangeTransactionContract` selling a large amount of the second token into `P`, driving `secondTokenBalance` down sharply relative to `firstTokenBalance` (per `ExchangeCapsule.transaction` at [6](#0-5) ).
4. Creator's inject executes against the skewed ratio in `ExchangeInjectActuator.execute()` [7](#0-6) , depositing a disproportionately small amount of the (temporarily cheap) second token for the fixed `Q` of the first token.
5. Attacker back-runs with the inverse `ExchangeTransactionContract`, restoring the ratio and withdrawing the surplus value left in the pool by the mis-priced injection.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
