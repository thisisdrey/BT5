## Title
Hardcoded static-gas callback allowance in the ETH-implicit Wallet Contract can permanently freeze `has_in_flight_tx`, permanently locking the account's funds - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

## Summary
The `WalletContract` used to back every ETH-implicit account guards concurrent execution with an in-memory flag `has_in_flight_tx` that is set to `true` before dispatching a promise and is only ever reset to `false` from inside the corresponding callback (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`, `ban_relayer`). Each of those callbacks is scheduled with a small, hardcoded static gas allowance (`RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) rather than a value derived from the actual work the callback may need to perform. This is the NEAR analog of the Solidity report's fixed 2300-gas stipend: a fixed/hardcoded gas budget attached to a downstream call that can be insufficient for legitimate execution, and — because NEAR receipts are atomic and roll back entirely on any failure, including "exceeded prepaid gas" — a callback that runs out of its fixed gas budget never resets `has_in_flight_tx`, permanently disabling further use of the wallet.

## Finding Description
`has_in_flight_tx` is documented as needing to be `true` exactly while a promise from this contract is outstanding, and `false` otherwise [1](#0-0) . It is set in `rlp_execute` before returning a `Promise` [2](#0-1) , and is only cleared inside the private callback functions, e.g. at the very top of `address_check_callback` [3](#0-2) , `nep_141_storage_balance_callback` [4](#0-3) , and `rlp_execute_callback` [5](#0-4) .

Each of these callbacks is dispatched with a fixed, hardcoded static-gas budget rather than a value scaled to worst-case execution needs: [6](#0-5) 

For the general action path, `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas) is the *entire* budget for `rlp_execute_callback` [7](#0-6) ; for the address-check and NEP-141 paths, the callback additionally has to fund constructing further promise batches for the user's parsed action out of `action.gas()` layered on top of the fixed overhead [8](#0-7) .

Because Near receipt execution is atomic — a receipt whose result is `Err` (including running out of prepaid gas) triggers `state_update.rollback()`, discarding *all* state writes performed by that receipt — a callback that exhausts its fixed gas budget while doing legitimate work (e.g. constructing a large `storage_deposit` + `ft_transfer` promise chain, or handling an attacker/relayer-supplied large-argument `FunctionCall` action) never commits its `self.has_in_flight_tx = false` write. This atomicity/rollback behavior is documented generally for receipt execution [9](#0-8) . Since there is no other code path capable of clearing `has_in_flight_tx`, every subsequent `rlp_execute` call is unconditionally rejected with "transaction already in progress" [10](#0-9) , and the account's tests already show that once set, an in-flight rejection is a hard stop with no recovery path [11](#0-10) .

This mirrors the class of the reported bug: a fixed/hardcoded gas allowance attached to a downstream call whose insufficiency (whether from the recipient needing more, or an unlucky/attacker-controlled payload) causes the operation to fail in a way that leaves funds unrecoverable — except here the failure mode is worse, because an ETH-implicit account has no other authorized path to move funds (it "cannot be deleted, nor can a full access key be added" and can "only be used by calling the methods of the Wallet Contract" [12](#0-11) ), so once `has_in_flight_tx` is stuck at `true`, the account's entire balance becomes permanently unreachable by its owner.

## Impact Explanation
An ETH-implicit account can only move funds through `WalletContract::rlp_execute`. If `has_in_flight_tx` becomes permanently stuck at `true` due to a callback receipt failing on its fixed static-gas budget, all future `rlp_execute` calls for that account are rejected forever, and there is no admin/owner override to reset the flag. Because ETH-implicit accounts cannot have a full access key added and cannot be deleted, this results in a permanent freeze of the account's $NEAR (and any NEP-141 tokens reachable only via this contract) balance — a direct NEAR analog of "ETH impossible to withdraw."

## Likelihood Explanation
Triggering this requires a callback (`address_check_callback`, `nep_141_storage_balance_callback`, or `rlp_execute_callback`) to exceed its fixed gas allowance while doing its own bookkeeping/promise-construction work (as opposed to the forwarded `action.gas()` budget for the inner user action). The fixed overheads (5–15 Tgas) are a thin margin relative to NEAR's per-byte costs for constructing `FunctionCall`/promise-batch actions, and `target`, `action` (including arbitrary-length `args`/`method_name`) are attacker/relayer-influenced inputs parsed from the RLP-encoded Ethereum transaction. A relayer (which need not be trusted/honest, per the contract's own threat model) can supply an oversized action payload specifically to blow the fixed overhead budget in the callback's own bookkeeping step, rather than the forwarded action gas.

## Recommendation
- Avoid relying on state mutations inside a receipt whose gas is a small fixed constant when that receipt performs variable/attacker-influenced work; instead, either bound/validate the size of `action`/`args` before scheduling the callback with a fixed budget, or scale the callback's static gas with the size of the data it must process (not just `action.gas()`).
- Consider decoupling the "in-flight" guard from callback completion, e.g., using a timeout/self-healing mechanism (such as a scheduled resume, or a separate low-gas "unlock" method that can be safely called if a callback is provably dropped/failed) so a single out-of-gas callback cannot permanently brick the account.
- Add fuzz/adversarial tests that supply maximal-size `FunctionCall` args/method names through `rlp_execute` to confirm the callback's fixed gas allowance always suffices, or fails safely without leaving `has_in_flight_tx` stuck.

## Proof of Concept
1. Deploy the Wallet Contract as a global contract and create/fund an ETH-implicit account, as in `test_wallet_contract_interaction` [13](#0-12) .
2. Craft an Ethereum-emulated transaction whose parsed `near_action::Action` targets the NEP-141 (or general) path and carries a maximally large `args`/`method_name` payload (bounded only by the max transaction/receipt size), so that reconstructing the outgoing promise batch inside `nep_141_storage_balance_callback`/`rlp_execute_callback` consumes more than `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`RLP_EXECUTE_CALLBACK_GAS` worth of the fixed overhead component alone.
3. Submit via `rlp_execute` with the relayer attaching a total transaction gas large enough to dispatch the callback receipt (satisfying `total_prepaid_gas` checks at creation) but insufficient for the callback's own oversized bookkeeping once it starts executing.
4. Observe the callback receipt fails with an "exceeded prepaid gas" error; per receipt-atomicity semantics the `self.has_in_flight_tx = false` write is rolled back.
5. Any subsequent call to `rlp_execute` on the same account now returns `"Error: transaction already in progress, please try again later."` indefinitely, as demonstrated by the existing `test_simultaneous_transactions` test showing this exact rejection path is reachable and terminal until the flag is cleared [11](#0-10) .

#[tokio::test]
async fn test_simultaneous_transactions() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    let receiver_account = worker.root_account().unwrap();

    let initial_receiver_balance = receiver_account.view_account().await.unwrap().balance;

    let receiver_id = receiver_account.id().as_str().into();
    let action = Action::Transfer { receiver_id, yocto_near: 1 };
    let signed_transaction =
        utils::create_signed_transaction(0, receiver_account.id(), Wei::zero(), action, &wallet_sk);
    let wallet_method_call_1 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));
    let wallet_method_call_2 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));

    let near_transaction = wallet_contract
        .inner
        .as_account()
        .batch(wallet_contract.inner.id())
        .call(wallet_method_call_1)
        .call(wallet_method_call_2)
        .transact()
        .await?;

    let result: ExecuteResponse = near_transaction.json()?;

    // The second transaction in the batch fails and this is returned as the
    // result of the Near transaction. But the first transaction in the batch
    // spawns promises that resolve, so the transfer was will successful.
    assert!(!result.success);
    assert!(result.error.unwrap().contains("transaction already in progress"));

    let final_receiver_balance = receiver_account.view_account().await.unwrap().balance;
    assert_eq!(final_receiver_balance.as_yoctonear() - initial_receiver_balance.as_yoctonear(), 1,);

    Ok(())
}
