### Title
Unvalidated length field in `PrecompiledContracts.extractBytesArray` allows attacker-controlled huge array allocation causing uncaught `OutOfMemoryError` in `ValidateMultiSign` precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract (invoked via `STATICCALL`/`CALL` from any TVM contract) parses attacker-supplied ABI-encoded calldata to build a signature array via `extractBytesArray`. In the legacy code path (`VMConfig.allowTvmSelfdestructRestriction()` disabled), the array length used to allocate a `byte[len][]` is taken directly from the untrusted calldata word with no upper-bound check, and the allocation happens *outside* the surrounding `try { ... } catch (Throwable t)` block that would otherwise absorb such an error.

### Finding Description
`extractBytesArray` reads the length field from raw call data and immediately allocates an array of that size before any validation: [1](#0-0) 

In `ValidateMultiSign.execute`, when the `allowTvmSelfdestructRestriction` proposal is not enabled, `extractBytesArray` is called directly with the attacker-controlled offset/length, and the `MAX_SIZE` bound check on `signatures.length` only happens *after* the array has already been allocated: [2](#0-1) 

Because `words[...].intValueSafe()` can return a value close to `Integer.MAX_VALUE` (attacker fully controls the 32-byte word supplied as call data), `new byte[len][]` can attempt to allocate an object-reference array with ~2^31 entries, immediately throwing `OutOfMemoryError`. Crucially, this call occurs at lines 1072–1074, before the `try { ... } catch (Throwable t)` block that starts at line 1082 in `ValidateMultiSign.execute` (lines 1082-1117). Since the allocation happens outside that guard, the resulting `OutOfMemoryError` is not caught by this method and propagates up the TVM call stack instead of being safely converted into `DATA_FALSE`, unlike other execution errors in this same precompile which are deliberately caught.

### Impact Explanation
Any account can construct a transaction that deploys or calls a contract invoking the `ValidateMultiSign` precompile with a crafted `sigArray` length word. Triggering a multi-gigabyte array allocation attempt can raise `OutOfMemoryError` on the node's JVM heap during transaction/block execution. Depending on JVM memory pressure at the time, this can destabilize or crash the executing full node/SR (denial of service), an integrity/availability impact analogous to the uncontrolled length/overflow-driven memory corruption in the original libXcursor CVE (there: heap buffer overflow from unchecked length fields; here: unchecked length field driving unbounded allocation and an unhandled JVM error).

### Likelihood Explanation
The `ValidateMultiSign` precompile is reachable by any unprivileged contract call — no special permission is required, only a crafted `CALL`/`STATICCALL` to the precompile address with malformed calldata. The vulnerable path exists specifically when `allowTvmSelfdestructRestriction()` is not active (i.e., on chains/proposals where this feature has not been enabled), which is a plausible node configuration state. The trigger requires only constructing one 32-byte word with a large integer value in the length field of the ABI-encoded signature array.

### Recommendation
Validate the parsed array length against `MAX_SIZE` (or another sane bound) in `extractBytesArray`/`extractSigArray` *before* allocating the array, mirroring the check already present for the `allowTvmSelfdestructRestriction()` path. Additionally, wrap the array-extraction call itself inside the existing `try/catch` in `ValidateMultiSign.execute` (or catch `OutOfMemoryError`/`Throwable` around the extraction step) so that malformed length fields cannot escape as unhandled JVM errors.

### Proof of Concept
1. Deploy a contract that performs a `STATICCALL` to the `ValidateMultiSign` precompiled contract address.
2. Encode `rawData` per the contract's expected ABI layout: `words[0]`=address, `words[1]`=permissionId, `words[2]`=data offset/value, `words[3]`=offset pointing to the "signature array" location.
3. At the computed offset (`words[3].intValueSafe() / WORD_SIZE`), place a length word equal to a very large value (e.g., `0x7FFFFFFF`).
4. Ensure the node is running with `allowTvmSelfdestructRestriction()` not yet enabled (older/legacy chain parameter state) so the vulnerable branch at [3](#0-2)  executes `extractBytesArray`.
5. Submit the transaction; `extractBytesArray` attempts `new byte[0x7FFFFFFF][]`, triggering `OutOfMemoryError` outside the method's exception guard, which propagates up through the TVM execution stack.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
