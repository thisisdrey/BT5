## Analysis Result

<title>Stale Signature/Permission Verification Cache Allows Execution of Revoked-Key Transactions Within the Same Block - (File: framework/src/main/java/org/tron/core/db/Manager.java)</title>

### Summary
`Manager.processBlock` performs signature verification for **all** transactions in an incoming block up front, in parallel, via `preValidateTransactionSign`, and caches the result as `isVerified = true` on each `TransactionCapsule`. The block's transactions are then executed sequentially by `processTransaction`, which re-invokes `trx.validateSignature(...)` — but that call is a no-op once `isVerified` is already `true`. If an earlier transaction in the same block (e.g. an `AccountPermissionUpdateContract`) changes an account's permission/key set, a later transaction in the same block signed under the *old* permission set is never re-checked against the *new* state, because its signature was already "verified" and cached before any of the block's transactions executed. This is a check-then-use (TOCTOU) race between signature/permission verification time and actuator-execution time, structurally analogous to CVE-2021-35937.

### Finding Description
In `Manager.processBlock`, when a block is received from the network (`!block.generatedByMyself`), all of its transactions are pre-validated for signature correctness in parallel before any transaction is executed: [1](#0-0) 

`preValidateTransactionSign` calls `trx.validateSignature(...)` for every transaction, which sets `isVerified = true` on the `TransactionCapsule` after checking the signature against the account permission state **as it exists before the block is applied**: [2](#0-1) [3](#0-2) 

Once cached, `validatePubSignature`/`validateSignature` in `TransactionCapsule` short-circuit any further signature/permission checking: [4](#0-3) [5](#0-4) 

The block's transactions are then executed sequentially in `processBlock`'s main loop, calling `processTransaction` for each one: [6](#0-5) 

`processTransaction` calls `trx.validateSignature(...)` again, but since `isVerified` is already `true` from the earlier batch pre-check, this is a no-op and does not re-check against the current account state: [7](#0-6) 

Meanwhile, `AccountPermissionUpdateActuator.execute()` mutates the account's `Permission` (owner/witness/active keys and weights) and persists it to `AccountStore` mid-block, immediately usable by subsequent actuators in the same block: [8](#0-7) 

Notably, the codebase already contains a fix for an analogous stale-verification issue in the fork-switch path — `switchFork` explicitly clears `isVerified` for every transaction before re-applying blocks on diverged state, specifically because "a cached signature-verification result is no longer trustworthy" when permissions may have changed: [9](#0-8) 

No equivalent invalidation exists for the intra-block case handled by `preValidateTransactionSign` + `processBlock`'s main loop: a permission change that takes effect *within* the same block being applied does not invalidate the pre-cached `isVerified` flags of later transactions in that same block.

### Impact Explanation
This allows a transaction signed by a key that is revoked (or has its weight/threshold reduced) by an earlier transaction in the very same block to still execute successfully, because its authorization was cached against the pre-block permission state and never re-validated against the state actually in effect at execution time. Concretely: an account owner detects a compromised active key and submits an `AccountPermissionUpdateContract` to revoke it; if an attacker (or the compromised key holder) races a second transaction signed with the soon-to-be-revoked key into the same block, that transaction is authorized using stale permission data and executes despite the revocation having already taken logical effect earlier in block processing. This is a concrete unauthorized-account-operation / authorization-bypass impact — funds or contract actions can be executed using a key that should no longer have permission.

### Likelihood Explanation
The vulnerable code path (`processBlock` → `preValidateTransactionSign` → sequential `processTransaction`) is core consensus logic executed by every full node for every block relayed from the network, not a privileged-actor-only path. Triggering it requires only that two ordinary transactions from the same account (a permission update and an action using the soon-to-be-superseded key) land in the same block — an outcome achievable by normal mempool timing/racing without any malicious SR/witness behavior, since block producers pack transactions in arrival/priority order rather than semantically re-checking permission dependencies between transactions.

### Recommendation
Invalidate (reset `isVerified` to `false`) for any transaction in a block whose owner address is affected by an `AccountPermissionUpdateContract` executed earlier in the same block, forcing re-validation against the post-update permission state before executing later transactions from that account — mirroring the safeguard already applied in `switchFork`. Alternatively, avoid resolving `isVerified` from a batch pre-check that predates in-block state mutations, and instead re-run full signature/permission validation immediately before each actuator's `execute()` call using the then-current account state.

### Proof of Concept
1. Account `X` has active permission P1 containing key `A` with sufficient weight.
2. Attacker (or the legitimate owner, if key `A` is compromised) crafts TX2: any actuator (e.g. `TransferContract`) from `X`, signed only with key `A`.
3. Owner submits TX1: `AccountPermissionUpdateContract` from `X` revoking key `A` from the active permission set, replacing it with permission P2.
4. Both TX1 and TX2 are relayed to the network and end up in the same block, with TX1 ordered before TX2 (achievable via normal propagation/packing without SR collusion).
5. Node receives the block; `preValidateTransactionSign` verifies TX2's signature against P1 (still in effect pre-block) and sets `isVerified = true` on TX2's capsule.
6. `processBlock`'s sequential loop executes TX1 first via `processTransaction`, which calls `AccountPermissionUpdateActuator.execute()`, replacing P1 with P2 in `AccountStore` per [8](#0-7) .
7. `processTransaction` then executes TX2; `trx.validateSignature(...)` is invoked but short-circuits because `isVerified` is already `true` per [10](#0-9) , so TX2 executes successfully using key `A`, which no longer has authorization under P2.

  private void preValidateTransactionSign(List<TransactionCapsule> txs)
      throws InterruptedException, ValidateSignatureException {
    int transSize = txs.size();
    if (transSize <= 0) {
      return;
    }
    Histogram.Timer requestTimer = Metrics.histogramStartTimer(
        MetricKeys.Histogram.VERIFY_SIGN_LATENCY, MetricLabels.TRX);
    try {
      CountDownLatch countDownLatch = new CountDownLatch(transSize);
      List<Future<Boolean>> futures = new ArrayList<>(transSize);

      for (TransactionCapsule transaction : txs) {
        Future<Boolean> future = validateSignService
            .submit(new ValidateSignTask(transaction, countDownLatch, chainBaseManager));
        futures.add(future);
      }
      countDownLatch.await();

      for (Future<Boolean> future : futures) {
        try {
          future.get();
        } catch (ExecutionException e) {
          throw new ValidateSignatureException(e.getCause().getMessage());
        }
      }

  private static class ValidateSignTask implements Callable<Boolean> {

    private TransactionCapsule trx;
    private CountDownLatch countDownLatch;
    private ChainBaseManager manager;

    ValidateSignTask(TransactionCapsule trx, CountDownLatch countDownLatch,
        ChainBaseManager manager) {
      this.trx = trx;
      this.countDownLatch = countDownLatch;
      this.manager = manager;
    }

    @Override
    public Boolean call() throws ValidateSignatureException {
      try {
        trx.validateSignature(manager.getAccountStore(), manager.getDynamicPropertiesStore());
      } catch (ValidateSignatureException e) {
        throw e;
      } finally {
        countDownLatch.countDown();
      }
      return true;
    }
  }

  public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }

  /**
   * validate signature
   */
  public boolean validateSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore) throws ValidateSignatureException {
    if (!isVerified) {
      //Do not support multi contracts in one transaction
      Transaction.Contract contract = this.getInstance().getRawData().getContract(0);
      if (contract.getType() != ContractType.ShieldedTransferContract) {
        validatePubSignature(accountStore, dynamicPropertiesStore);
      } else {  //ShieldedTransfer
        byte[] owner = getOwnerAddress();
        if (!ArrayUtils.isEmpty(owner)) { //transfer from transparent address
          validatePubSignature(accountStore, dynamicPropertiesStore);
        } else { //transfer from shielded address
          if (this.transaction.getSignatureCount() > 0) {
            throw new ValidateSignatureException("there should be no signatures signed by "
                    + "transparent address when transfer from shielded address");
          }
        }
      }
      isVerified = true;
    }
    return true;
  }
