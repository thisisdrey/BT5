Audit Report

## Title
Relayer reward payout is marked settled after XCM send succeeds, not after execution/deposit succeeds on AssetHub - (File: bridges/snowbridge/primitives/core/src/reward.rs)

## Summary
`PayAccountOnLocation::pay_reward` builds an unpaid, one-way XCM containing `ReserveAssetDeposited` + `DepositAsset` instructions targeting the relayer's `beneficiary` on AssetHub, but only checks local dispatch success (`validate_send`, `charge_fees`, `XcmSender::deliver`) before returning `Ok(())`. `Pallet::do_claim_rewards` treats this `Ok(())` as final settlement, irreversibly removing the `RelayerRewards` entry and emitting `RewardPaid`, even though no confirmation of the remote `DepositAsset` execution on AssetHub is ever obtained.

## Finding Description
The `pay_reward` implementation constructs the XCM program and only validates local, non-remote-outcome signals: [1](#0-0) . `validate_send`, `charge_fees`, and `deliver` confirm only that the message was well-formed, fees were charged locally, and the message was handed to the transport layer — none confirm the `DepositAsset { assets: AllCounted(1).into(), beneficiary }` instruction actually executed successfully on AssetHub.

The caller `Pallet::do_claim_rewards` removes the `RelayerRewards` entry via `maybe_reward.take()` and only reverts the whole closure if `pay_reward` returns `Err`; on `Ok`, it unconditionally emits `Event::RewardPaid` and finalizes the removal: [2](#0-1) . Because the entry is taken before, and only restored on `Err`, a "send succeeded" signal is indistinguishable from "value actually delivered" from the perspective of on-chain bookkeeping.

This contrasts with `PaymentProcedure` for same-chain rewards, which uses an atomic `fungible::Mutate::transfer`, whose `Result` is authoritative within the same transactional storage context — if it fails, `Err` propagates and the reward entry is not removed: [3](#0-2) . `PayAccountOnLocation` has no equivalent remote-execution acknowledgement mechanism (e.g., no `QueryResponse`/receipt), so it cannot offer the same atomicity guarantee, yet `do_claim_rewards` treats both procedures identically.

The `beneficiary: BeneficiaryOf<T, I>` argument of the public extrinsic `claim_rewards_to` is fully attacker/caller-controlled (an arbitrary `VersionedLocation` converted to `Location`), meaning any relayer invoking this call with a malformed or unresolvable location on the AssetHub side (e.g. account not meeting existential deposit, bad junction encoding) triggers this false-success path without any special privilege: [4](#0-3) .

## Impact Explanation
If the beneficiary `Location` fails to resolve to a valid depositable account on AssetHub (bad junction encoding, below-ED account, or execution/barrier rejection of the `DepositAsset` instruction), the reserve-minted asset is trapped (`AssetsTrapped`) instead of credited, while BridgeHub has already deleted the `RelayerRewards` entry and emitted `RewardPaid`. This is a payout-settlement/state-advance violation matching the pivot that "payout state must only advance after ... execution, and settlement succeed atomically" — the relayer's earned reward becomes a permanently locked/lost value with a false "settled" state recorded on-chain, and no automatic recovery path tied back to the claim.

## Likelihood Explanation
No malicious actor or privileged access is required — any relayer calling the public extrinsic `claim_rewards_to` with a `beneficiary` location that AssetHub cannot resolve/deposit into (via ordinary user error, wrong encoding, insufficient existential deposit, or transient AssetHub-side execution failure) hits this false-success path deterministically, since the local checks (`validate_send`, `charge_fees`, `deliver`) never depend on the destination-side outcome.

## Recommendation
Do not remove the `RelayerRewards` entry / emit `RewardPaid` until remote execution is confirmed. Options include using a receipted/paid XCM pattern (e.g. `QueryResponse` acknowledgment from AssetHub) before clearing the reward record, keeping the reward in a "pending" state until a positive execution acknowledgment is received (re-crediting on trap/failure notification), or at minimum validating the beneficiary `Location` more strictly before consuming the local reward record and providing a recovery path for `AssetsTrapped` funds tied to the relayer's claim.

## Proof of Concept
1. Relayer accrues a reward tracked in `RelayerRewards` on BridgeHub.
2. Relayer calls `claim_rewards_to` with a `beneficiary` `Location` that AssetHub's XCM barrier/converter cannot resolve to a valid depositable account.
3. `do_claim_rewards` invokes `PayAccountOnLocation::pay_reward`; `validate_send`, `charge_fees`, and `deliver` all succeed since they check only local dispatch/routing.
4. `pay_reward` returns `Ok(())`; `RelayerRewards` entry is removed and `Event::RewardPaid` is emitted.
5. On AssetHub, `DepositAsset` fails and the reserve-minted asset is trapped (`AssetsTrapped`) instead of credited to the relayer.
6. Result: BridgeHub records the reward as fully paid while the relayer's AssetHub balance is unchanged, with no automatic recovery mechanism.

		fn do_claim_rewards(
			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,
		) -> DispatchResult {
			RelayerRewards::<T, I>::try_mutate_exists(
				&relayer,
				reward_kind,
				|maybe_reward| -> DispatchResult {
					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
					T::PaymentProcedure::pay_reward(
						&relayer,
						reward_kind,
						reward_balance,
						beneficiary.clone(),
					)
					.map_err(|e| {
						tracing::error!(
							target: LOG_TARGET,
							error=?e,
							?relayer,
							?reward_kind,
							?reward_balance,
							?beneficiary,
							"Failed to pay rewards"
						);
						Error::<T, I>::FailedToPayReward
					})?;

					Self::deposit_event(Event::<T, I>::RewardPaid {
						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,
					});
					Ok(())
				},
			)
