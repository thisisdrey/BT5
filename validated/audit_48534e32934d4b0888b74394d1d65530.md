### Title
Unbounded read of Local Header entry size in singlejar's `TransientBytes::ReadEntryContents` can leak adjacent heap/mapped memory into build output - ([File: src/tools/singlejar/transient_bytes.h])

### Summary
`TransientBytes::ReadEntryContents` copies `uncompressed_file_size` bytes starting at `lh->data()` without validating that the size actually fits within the memory-mapped input jar. A crafted dependency jar with an inconsistent/oversized size field can cause the merge step (`Concatenator::Merge`, `Java8DesugarDepsChecker::Merge`) to read past the mapped file and copy adjacent memory bytes into the merged output jar that `singlejar` produces.

### Finding Description
`TransientBytes::ReadEntryContents` in [1](#0-0)  determines the number of bytes to copy from the entry's Central Directory Header (`cdh->uncompressed_file_size()`) or Local Header (`lh->uncompressed_file_size()`) and then unconditionally calls `Append(lh->data(), uncompressed_file_size)`, copying that many bytes starting right after the LH's fixed fields/filename/extra fields [2](#0-1) .

Nowhere in this path is `uncompressed_file_size` checked against the number of bytes actually remaining in the memory-mapped input file. Contrast this with the ijar zip reader (`third_party/ijar/zip.cc`), which explicitly calls `EnsureRemaining()` before consuming compressed/uncompressed payload bytes [3](#0-2) ; singlejar's `InputJar`/`zip_headers.h` machinery has no equivalent bounds check for the `ReadEntryContents` (stored) code path — `InputJar::NextEntry` only validates that the *next Central Directory Header* is mapped [4](#0-3) , not that a given entry's declared uncompressed size is consistent with the mapped extent of the local file data.

This is reachable from ordinary, attacker-controllable inputs: `singlejar` merges the class-file/META-INF entries of every input jar supplied to a `java_library`/`java_binary` build action, including jars fetched as external dependencies (e.g., via `maven_install`/`http_jar`, potentially with a pinned `sha256`). An attacker who publishes a jar whose declared checksum matches but whose ZIP local-header `uncompressed_file_size` (stored, `Z_NO_COMPRESSION`) is larger than the number of bytes actually present in the entry causes `Concatenator::Merge` (used for concatenated resources like `META-INF/services/*`) or the desugar-deps checker to copy trailing bytes beyond the entry — and potentially beyond the mmap'd file — into the merged output. Because the merged bytes land in `TransientBytes`, which is subsequently written to the output jar via `OutputEntry`, any out-of-file-bounds bytes read (uninitialized mmap padding, or adjacent heap memory if a chunk buffer is undersized elsewhere) become part of a build artifact that the victim (and anyone consuming that artifact) can read — the CVE-2018-1052 "read arbitrary bytes of server memory via crafted insert" analog, here manifesting as "read arbitrary bytes of process memory into build output via a crafted archive entry."

### Impact Explanation
If exploitable, this discloses process memory contents (heap data adjacent to the mmap region, or stale mmap padding) into a build artifact, which can then be inspected by anyone with access to the output (CI logs, artifact repositories, or the build machine's other jobs sharing the same builder). This is a confidentiality violation matching the "memory disclosure" bug class of the reference CVE, scoped to the local `singlejar` action rather than a network service.

### Likelihood Explanation
An external, unprivileged attacker only needs to publish one malicious jar as a Maven/HTTP dependency with an internally inconsistent ZIP local header (size field larger than the actual entry payload) while still matching the externally-declared `sha256`/`integrity` — trivial to construct, since the hash simply covers the byte content including the (attacker-chosen) declared size field. No mitm, malicious build proxy, or privileged access is required; the archive itself carries the discrepancy.

### Recommendation
Add explicit bounds validation before `Append(lh->data(), uncompressed_file_size)` in `TransientBytes::ReadEntryContents`/`DecompressEntryContents`, verifying that `lh->data() + uncompressed_file_size` (and the corresponding compressed-size read window) does not exceed the mapped file's end, analogous to `InputZipFile::EnsureRemaining` in `third_party/ijar/zip.cc`. Reject or fail the build with a diagnostic (as `zip.cc` does) rather than silently reading past the entry/file boundary.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style reproduction:
1. Hand-craft a minimal ZIP/JAR whose single stored (`Z_NO_COMPRESSION`) entry's Local Header declares `uncompressed_file_size` (and matching CDH value) larger than the number of bytes physically present between the entry's data offset and EOF (i.e., truncate the actual payload but leave the size fields inflated).
2. Feed this jar as an input to `singlejar --sources crafted.jar --output out.jar` (the same code path `java_library`/`java_binary` build actions invoke, and the same code path a `Concatenator`-merged resource such as `META-INF/services/...` takes via `Merge`).
3. Observe (or instrument, e.g., under ASan/valgrind) that `TransientBytes::ReadEntryContents` copies bytes beyond the mapped file extent into `out.jar`'s corresponding entry, rather than singlejar failing with an "unexpected end of file" diagnostic the way `zip.cc`'s `EnsureRemaining` would produce for the ijar path.

Note: I was not able to fully trace whether the underlying `MappedFile` implementation (`mapped_file_posix.inc`/`mapped_file_windows.inc`) pads the mapping in a way that makes an actual out-of-mapping read crash (SIGBUS) versus silently returning adjacent-page/zero-fill bytes on all platforms; this affects whether the disclosure is "heap-adjacent process memory" or merely "zero/stale page content," and would need to be confirmed by running the PoC under instrumentation before treating this as a confirmed, ship-ready exploit rather than a plausible bounds-check gap.
