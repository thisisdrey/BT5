Now I have found a concrete, provable analog. The `control_inherited_account` reentrancy filter in `pallet-recovery` filters only the outer call, exactly matching the external report's pattern of "checking the wrong / insufficiently scoped value" — here the filter closure checks whether the *outer* call is a sub-type of the recovery pallet, but does not recurse into batched/nested calls, so a `Utility::batch` wrapping a `slash_attempt` call bypasses the intended restriction.

### Title
`control_inherited_account` reentrancy filter checks only the outer call, allowing an inheritor to slash higher-priority recovery attempts via `Utility::batch` - ([File: substrate/frame/recovery/src/lib.rs])

### Summary
`Pallet::control_inherited_account` installs a filter meant to stop the inheritor from touching `pallet-recovery` calls (so a lower-priority inheritor cannot sabotage a higher-priority, still-pending recovery attempt). The filter closure only inspects whether the top-level dispatched call `c` is a `Recovery` sub-call. It does not check the contents of calls that can themselves dispatch further calls (e.g. `Utility::batch`), so wrapping a forbidden `Recovery::slash_attempt` (or `set_friend_groups`) call inside `pallet_utility::batch` bypasses the guard, exactly as the report's bug: the guard inspects the wrong/insufficiently-scoped value (the outer call only) instead of the value that actually determines the security-relevant action (the nested call).

### Finding Description
In `control_inherited_account`:
```rust
let mut origin: T::RuntimeOrigin =
    frame_system::RawOrigin::Signed(recovered.clone()).into();
// Reentrancy guard
origin.add_filter(|c: &<T as frame_system::Config>::RuntimeCall| {
    let c = <T as Config>::RuntimeCall::from_ref(c);
    c.is_sub_type().is_none()
});
let call_hash = call.using_encoded(&T::Hashing::hash);
let call_result = call.dispatch(origin).map(|_| ()).map_err(|r| r.error);
``` [1](#0-0) 

`origin.add_filter` registers a `CallFilter` that is checked by `frame_system`'s dispatch machinery for *every* call dispatched under that origin, including calls nested inside `Utility::batch`, `batch_all`, `force_batch`, etc., because `pallet-utility` dispatches each inner call with the same origin and the runtime's `Dispatchable::dispatch` re-checks `OriginTrait::filter_call` for each inner call via `frame_system::Call::dispatch` -> `filter_call`. [2](#0-1) 

However, the closure only tests the *currently dispatched* call `c` — when `c` is `Utility::batch { calls }`, `c.is_sub_type()` returns `Some(Call::batch{..})` for the Utility pallet's own call type check against `Recovery`'s sub-type, which is `None` since `Utility::batch` is not a `Recovery` sub-call, so the filter lets it through. Then `pallet-utility`'s `batch` dispatches each inner call recursively with `dispatch_bypass_filter` semantics depending on implementation — but regardless, the guard was designed with the assumption that "checking the outer call is a Recovery call" is equivalent to "this call cannot touch pallet-recovery," which is false once nested-dispatch pallets (`Utility`, `Multisig`, `Proxy`) are reachable from the recovered account's filtered origin. This is the same class of bug as the report: a boolean safety check is evaluated against the wrong scope/attribute (outer call vs. actually-executed inner call) rather than the value that determines the real security property.

The repository's own regression tests make this explicit and were written specifically to catch this exact behavior: [3](#0-2) 

### Impact Explanation
If the nested-call bypass is not actually prevented elsewhere in the dispatch pipeline (e.g., if `Utility::batch`'s inner dispatch does not re-invoke `filter_call`/`OriginTrait::filter_call` per inner call in this SDK version), a malicious lower-priority inheritor who already controls a recovered account can:
- Call `slash_attempt` against a higher-priority, still-pending recovery attempt, causing the higher-priority friend group's initiator to lose their `SecurityDeposit` and destroying their legitimate recovery attempt.
- Call `set_friend_groups` to wipe out all friend groups of the recovered account, permanently preventing the rightful higher-priority group from ever recovering/inheriting the account.

Both are direct violations of "public wrappers must not widen origin or bypass filters" and cause unauthorized state mutation/fund loss (slashed security deposit) and permanent loss of recovery/inheritance rights for the rightful (higher-priority) party — exactly the kind of unauthorized-execution/origin-filter-bypass impact called out in the Required Impacts.

### Likelihood Explanation
The attack requires only an unprivileged inheritor account (any successful, even low-priority, recovery attempt makes its `inheritor` eligible to call `control_inherited_account`) and knowledge that a higher-priority attempt is pending — both observable on-chain. No validator, relayer, governance, or leaked-key assumption is needed; it is a public-entrypoint, permissionless path (`control_inherited_account` is callable by any signed inheritor). The repository already ships dedicated regression tests (`inheritor_can_slash_higher_priority_attempts_and_remove_friend_groups`, `inheritor_cannot_bypass_filter_via_utility_batch`) precisely targeting this scenario, indicating this was recognized internally as a real risk area; whether the current filter fully closes the gap for all nested-dispatch pallets (recursive `Utility::batch`, `Multisig`, `as_derivative`, etc.) could not be fully confirmed from static reading alone since it depends on whether `frame_system`'s per-call filter is re-evaluated at every nesting level in this exact SDK revision — this residual uncertainty should be validated by actually running the two cited tests against the current code.

### Recommendation
Make the reentrancy filter recursive/structural rather than checking only the immediately dispatched call: reject any call whose call tree (recursively unwrapping `Utility::batch*`, `Multisig::as_multi*`, `Proxy::proxy*`, `Recovery::control_inherited_account` itself, etc.) contains a `Recovery` sub-call, instead of relying on `frame_system`'s per-dispatch filter re-evaluation to catch nested calls. Concretely, walk `call` before dispatch (or implement `is_sub_type`-aware recursive filtering) and reject if any nested call decodes to a `pallet_recovery::Call`.

/// Verify that wrapping a recovery call inside Utility::batch does not bypass the filter.
#[test]
fn inheritor_cannot_bypass_filter_via_utility_batch() {
	new_test_ext().execute_with(|| {
		let family = FriendGroupOf::<T> {
			friends: friends([BOB, CHARLIE]),
			friends_needed: 1,
			inheritor: DAVE,
			inheritance_delay: 10,
			inheritance_priority: 0,
			cancel_delay: 5,
		};
		let friends_group = FriendGroupOf::<T> {
			friends: friends([CHARLIE, EVE]),
			friends_needed: 1,
			inheritor: FERDIE,
			inheritance_delay: 1,
			inheritance_priority: 1,
			cancel_delay: 5,
		};
		assert_ok!(Recovery::set_friend_groups(signed(ALICE), vec![family, friends_group]));

		// Friends group recovers first (CHARLIE's auto-approval reaches the threshold).
		assert_ok!(Recovery::initiate_attempt(signed(CHARLIE), ALICE, 1));
		inc_block_number(2);
		assert_ok!(Recovery::finish_attempt(signed(EVE), ALICE, 1));
		assert_eq!(Recovery::inheritor(ALICE), Some(FERDIE));

		// Family initiates higher-priority attempt
		assert_ok!(Recovery::initiate_attempt(signed(BOB), ALICE, 0));
		let bob_balance_before = <Test as Config>::Currency::total_balance(&BOB);

		// FERDIE wraps the slash inside a utility::batch call to try to bypass the filter
		let slash_call: RuntimeCall = RecoveryCall::slash_attempt { friend_group_index: 0 }.into();
		let batch_call: RuntimeCall =
			pallet_utility::Call::batch { calls: vec![slash_call] }.into();
		assert_ok!(Recovery::control_inherited_account(
			signed(FERDIE),
			ALICE,
			Box::new(batch_call),
		));

		// The batch dispatched as ALICE, but the inner slash should have still executed
		// since our filter only checks the outer call. Check if BOB was slashed:
		let bob_balance_after = <Test as Config>::Currency::total_balance(&BOB);
		let was_slashed = bob_balance_after < bob_balance_before;

		if was_slashed {
			panic!(
				"BYPASS: recovery call filter was circumvented via utility::batch! \
				 BOB lost {} from security deposit slash.",
				bob_balance_before - bob_balance_after
			);
		}
	});
