This is confirmed by explicit documentation in the code itself: `DeleteObjectPool` performs no member-check before removing the pool, matching the analog pattern precisely — an operation that irreversibly destroys a shared resource without verifying that dependent, in-progress operations (other pool members' repositories) still need it, with no compensating mechanism afterward.

### Title
Object pool can be deleted while members still depend on it, causing irrecoverable corruption with no compensating recovery path - (File: `internal/gitaly/service/objectpool/delete.go`)

### Summary
`ObjectPoolService.DeleteObjectPool` unconditionally removes an object pool repository via `repoutil.Remove` without checking whether any repository is still linked to it as an alternate object store [1](#0-0) . This mirrors the reported bug class: an action that irreversibly consumes/destroys a shared resource before a dependent, multi-step process (here, other repositories relying on the pool's objects via alternates) is guaranteed to be finished, with no built-in mechanism to "replenish" or recover afterward.

### Finding Description
The protobuf documentation for the RPC explicitly acknowledges the danger: "DeleteObjectPool deletes the object pool. There are no safety checks in place, so if any repository is still using this object pool it will become corrupted" and "It is the responsibility of the caller to ensure that it really has no members left, else any existing member will become corrupt" [2](#0-1) . The implementation reflects this: it simply resolves the pool from the request and calls `repoutil.Remove`, with no verification against `LinkRepositoryToObjectPool`/pool membership state before physically removing the pool's object directory [1](#0-0) . Once deleted, any repository whose `objects/info/alternates` still points at the removed pool loses access to objects that were deduplicated into the pool — this is the same "shared object" mechanism documented in `doc/object_pools.md`, which explains that pool members would "miss objects which are only part of the object pool" if the alternate is dropped without first re-materializing shared objects, exactly the safeguard implemented for the legitimate disconnect path in `internal/git/objectpool/disconnect.go` (hard-link objects back into the member, then remove the alternate, then run `git-fsck` to verify) [3](#0-2) . `DeleteObjectPool` bypasses all of that: it does not hard-link objects into any member, does not verify zero members remain, and does not run any consistency check before destroying the pool.

### Impact Explanation
Because the object pool itself has no "receive/replenish" fallback once deleted (its objects and packfiles are gone from disk, and `repoutil.Remove` stages the removal via `os.Rename` into a temp directory before permanent deletion, with no path back for members) [4](#0-3) , any repository still relying on the pool's alternate object directory becomes permanently corrupt: `git-fsck`/read/fetch operations against those repositories will fail with missing-object errors, mirroring the original report's "no way to replenish" characteristic. This can silently corrupt every fork/pool-member repository whose alternates still reference the deleted pool, with no automated recovery — the operator would have to manually re-derive the objects from another remaining full copy, if one exists.

### Likelihood Explanation
The RPC is a plain `MUTATOR` gRPC call requiring only a target repository/object-pool argument that is crafted per-request [5](#0-4) , so any client authorized to call Gitaly's `ObjectPoolService` (e.g., via a misordered or duplicated deletion request, a race between deleting a pool and concurrently forking/linking a new member, or simply a caller that miscalculates whether members remain) can trigger this. There is no server-side guard, so likelihood depends entirely on caller discipline rather than any Gitaly-enforced invariant — the comment in the generated client code makes the risk explicit but doesn't mitigate it.

### Recommendation
Before removing the pool repository in `DeleteObjectPool`, verify there are no remaining members (e.g., via the relational pool-membership tracking already present in `internal/gitaly/storage/relational/state_manager.go`'s `NotifyDeletePool`/pool-member bookkeeping [6](#0-5) ) and refuse to delete (or force an automatic disconnect/hard-link-back step similar to `objectpool.Disconnect`) if any member still references the pool as an alternate.

### Proof of Concept
1. Create an object pool from repository A via `CreateObjectPool`, then link A (and optionally B) to the pool via `LinkRepositoryToObjectPool`, causing objects to be deduplicated into the pool and `objects/info/alternates` in A/B to point at it.
2. Without first calling `DisconnectGitAlternates` on A/B, call `DeleteObjectPool` on the pool [1](#0-0) .
3. Attempt to read/fetch objects from A or B that were deduplicated into the now-deleted pool — the operation fails with missing-object errors, and the repository is permanently corrupt with no automatic recovery path.
