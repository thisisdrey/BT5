### Title
Attacker can fill a victim's per-account token list via forced dust deposits/transfers, blocking new collateral deposits and debt issuance - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
CVE-2018-20358 is a "malformed input reaches an unchecked dereference → crash/DoS" bug class: an attacker-crafted input causes the decoder to fault. The on-chain analog in Metronome is `Pool.onlyIfAdditionWillNotReachMaxTokens`: attacker-controlled inputs (dust `transfer()`s and `deposit(amount_, onBehalfOf_)`) force entries into a victim's `depositTokensOfAccount` enumerable set until it hits `MAX_TOKENS_PER_USER`, after which every code path that would add a new token entry for that account reverts with `UserReachedMaxTokens`. The revert is a persistent denial of service on `DepositToken.deposit`, `DepositToken._transfer`/`seize` (for the victim as recipient), and `DebtToken.issue`/leverage paths for any token type the victim does not already hold.

### Finding Description
`DepositToken._mint` and `DepositToken._transfer` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero (`contracts/DepositToken.sol:486-488` and `contracts/DepositToken.sol:518-520`). That call is guarded by:

```solidity
if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
    revert UserReachedMaxTokens();
}
```
`contracts/Pool.sol:143-148`

Two unprivileged vectors let an attacker add entries to a victim's list:

1. `DepositToken.deposit(amount_, onBehalfOf_)` — `onBehalfOf_` is arbitrary, so the attacker deposits 1 wei of each underlying and mints dust msdTokens directly to the victim (`contracts/DepositToken.sol:211-237`).
2. `DepositToken.transfer(to_, amount_)` — transfers only check the sender's unlocked balance (`_revertIfLocked`), so the attacker dust-transfers each deposit token type to the victim (`contracts/DepositToken.sol:348-354`).

Once `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) >= MAX_TOKENS_PER_USER`:

- `deposit()` of any collateral type the victim does not already hold reverts in `_mint` → `addToDepositTokensOfAccount`.
- Any `transfer`/`transferFrom`/`seize` sending a new token type to the victim reverts — this also makes the victim unable to receive liquidation-seized collateral of a new type, though that is self-choosable by liquidators.
- `DebtToken.issue`/`SmartFarmingManager.leverage` revert for any synth the victim hasn't borrowed before, since `DebtToken` minting calls `addToDebtTokensOfAccount` (`contracts/Pool.sol:204-208`).

The CVE's structure is preserved: a peer-supplied, unchecked input (a forced set insertion) drives a downstream operation (the victim's own legitimate deposit/borrow) into a fault (revert), producing denial of service without any privileged role.

### Impact Explanation
Temporary freezing of funds with a concrete loss path. The critical scenario: the victim's position is approaching liquidation during a price crash. The victim attempts to rescue the position by depositing a collateral type they have never used — the single most common rescue action — and the transaction reverts with `UserReachedMaxTokens`. The position is then liquidated (`Pool.liquidate` at `contracts/Pool.sol:537-596` only requires an unhealthy account and is permissionless), so the griefing converts a recoverable position into a forced liquidation loss, including the liquidator incentive paid out of the victim's collateral. The freeze persists as long as the attacker keeps the list saturated; the victim can only escape by spending gas to zero out each dusted token (each transfer-out removes one slot via `removeFromDepositTokensOfAccount`, `contracts/DepositToken.sol:522-525`), which the attacker can cheaply re-fill — during a crash, this remediation competes directly with the liquidation window.

### Likelihood Explanation
Reachable entirely with unprivileged calls (`deposit`/`transfer`), no privileged actor, oracle manipulation, or malicious bridge required. Two conditions bound feasibility:

- The combined count of distinct registered deposit tokens plus debt-token entries the attacker can force must reach `MAX_TOKENS_PER_USER`. The attacker can force one deposit-token entry per registered collateral and cannot force debt entries on the victim. If `MAX_TOKENS_PER_USER` exceeds the number of registered deposit tokens (plus any debt tokens the victim already holds), the list cannot be saturated and the attack fails — this is the main uncertainty and must be checked against the deployed constant and registry on the target chain.
- Attacker cost is dust-level deposits/transfers of each listed collateral, recoverable afterward.

The attack is most dangerous when combined with volatile conditions where victims urgently need to add new collateral.

### Recommendation
- Make addition to the per-account list opt-in for the beneficiary: only add a deposit token on `deposit()` when `onBehalfOf_ == _msgSender()` (or track an explicit allow-list flag), or skip `addToDepositTokensOfAccount` for balances below a dust threshold so 1-wei transfers cannot occupy a slot.
- Alternatively, treat the recipient-side set insertion failure as non-fatal (wrap in try/catch and skip the accounting entry), since the balance itself is already tracked in `balanceOf` — though this changes `depositOf` semantics for unlisted holdings.
- Bound the griefing asymmetry by requiring a minimum deposit amount in `deposit()` when `onBehalfOf_ != _msgSender()`.

### Proof of Concept
Hardhat (fork or fixture with the deployed pool, e.g. mainnet deployment `deployments/mainnet/Pool.json`):

```typescript
// Assumes: `pool`, several DepositTokens (msdMET, msdUSDC, ...), an unhealthy
// victim `alice`, and attacker `mallory` holding dust of each deposit token.
it('blocks victim from adding new collateral once list is at cap', async () => {
  // 1. Saturate alice's depositTokensOfAccount list via dust transfers
  for (const dt of depositTokens) {
    if ((await dt.balanceOf(alice.address)) == 0) {
      await dt.connect(mallory).transfer(alice.address, 1); // adds entry
    }
  }
  // alt vector: await dt.connect(mallory).deposit(1, alice.address)

  // sanity: list is at MAX_TOKENS_PER_USER
  const len = (await pool.getDepositTokensOfAccount(alice.address)).length
            + (await pool.getDebtTokensOfAccount(alice.address)).length;
  expect(len).to.eq(await pool.MAX_TOKENS_PER_USER());

  // 2. alice's position turns unhealthy (price move)
  await masterOracle.updatePrice(met.address, toUSD('0.60'));

  // 3. alice tries to deposit a collateral type she doesn't hold → reverts
  const newCollateral = someDepositTokenAliceNeverUsed;
  await underlying.connect(alice).approve(newCollateral.address, amount);
  await expect(newCollateral.connect(alice).deposit(amount, alice.address))
    .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // 4. liquidation proceeds against the unrescuable position
  await expect(pool.connect(bob).liquidate(msEth.address, alice.address, amt, msdMET.address))
    .to.emit(pool, 'PositionLiquidated');
});
```

Caveat to verify before execution: confirm the deployed value of `MAX_TOKENS_PER_USER` and the number of registered deposit tokens on the target chain; if the cap exceeds reachable distinct tokens, saturate only up to `registered tokens + victim's existing debt tokens` and the attack applies only to victims already near the cap.
