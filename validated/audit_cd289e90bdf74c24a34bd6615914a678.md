### Title
Missing Sender Validation in `RefTransaction.VoteTransaction` Allows Vote Spoofing for Arbitrary Voter Nodes - ([File: internal/praefect/service/transaction/server.go])

### Summary
The `VoteTransaction` RPC handler on Praefect trusts the client-supplied `node` field in `VoteTransactionRequest` as the identity of the voting Gitaly storage node, without ever verifying that the identity of the actual RPC caller (the backchannel/session that reached Praefect) matches the claimed `node` name. This mirrors the reported `submit_proposal` bug class: an action that should only be performable by an authorized, identified party (the specific Gitaly node casting its own vote) is accepted purely on the basis of an unauthenticated, attacker-controllable request field.

### Finding Description
`VoteTransactionRequest.node` is documented as "the name of the Gitaly node that's voting on a transaction" [1](#0-0) . The Praefect-side handler `Server.VoteTransaction` forwards this field straight into the transaction manager without any check that ties it to the caller's actual identity: [2](#0-1) 

The transaction manager then dispatches to `subtransaction.vote(node, vote)`, whose only validation is that the claimed `node` name exists among the registered voters for that transaction and has not already voted — it never checks who is actually calling: [3](#0-2) 

By contrast, other backchannel-gated RPCs in this codebase, such as `SignalPostReceiveReady`, explicitly verify the caller reached the handler via Praefect's/Gitaly's backchannel using `backchannel.GetPeerID(ctx)` before trusting request content [4](#0-3) . `VoteTransaction` has no equivalent check binding the `node` argument to the connection's authenticated peer/backchannel ID — it is a purely a string supplied by the caller, as demonstrated throughout the test suite where arbitrary `Node` values are sent directly in the request [5](#0-4) .

### Impact Explanation
Any client capable of reaching the `RefTransaction` service on Praefect (which is exposed to be called by each Gitaly node participating in a cluster transaction) can submit a vote under the name of a *different* registered voter node, rather than its own. Because reaching quorum determines whether a reference update is committed or aborted across the whole Gitaly Cluster, an entity able to spoof another node's vote can influence transaction outcomes without actually holding the storage state it claims to represent, undermining the integrity guarantee that "all nodes part of a single transaction perform the same change" [6](#0-5) .

### Likelihood Explanation
The `node` field is a plain proto string with no correlation to the gRPC peer/backchannel session performing the call, and the only validation performed (`subtransaction.vote`) is that the name is one of the pre-registered voters for that transaction ID — not that it matches the actual caller [7](#0-6) . Reaching this code path only requires knowledge of an active `transaction_id` and a legitimate voter name, both of which are visible/derivable by any participant already part of the transaction coordination flow.

### Recommendation
Bind the `node` argument to the authenticated identity of the RPC caller (e.g., the backchannel peer ID or the Gitaly storage identity established at connection/handshake time) and reject `VoteTransaction`/`StopTransaction` calls where the claimed `node` does not match the caller's verified identity, analogous to the backchannel-origin check already used in `SignalPostReceiveReady`.

### Proof of Concept
1. Register a transaction with voters `["primary", "secondary-1", "secondary-2"]` and threshold 3 (as in `TestPraefectWriteSerialization_VoteFailureReleasesLock`) [8](#0-7) .
2. From a single connection (e.g., the one legitimately belonging to `secondary-1`), issue two `VoteTransaction` calls: one with `Node: "secondary-1"` and one with `Node: "primary"`, both with attacker-chosen `reference_updates_hash` values.
3. Observe that both votes are accepted and counted toward quorum, because `Server.VoteTransaction` and `subtransaction.vote` never verify that the caller is actually the node named `"primary"` [2](#0-1) , allowing a single connected node to unilaterally sway or stall the quorum outcome for other nodes it does not control.
