The premise of the question is not supported by the codebase: NEAR does not merge or replay execution results across competing forks. Fork choice is "highest height wins" with no revert/merge step — each fork's chunk application is an independent state transition rooted at the pre-fork common ancestor's state root, and only one branch's results are ever adopted as canonical.Based on my analysis, the attack scenario described does not correspond to a real vulnerability.

### Analysis

The `seen_tx_hashes` dedup at [1](#0-0)  is scoped to a single chunk's transaction list during `apply`, guarding against the *same tx_hash appearing twice within one chunk* producing two conflicting outcomes under the same outcome id. This is a per-chunk concern, and it is not meant to (and does not need to) provide cross-fork dedup, because forks in nearcore never merge.

Each competing chunk on a fork is applied as an independent state transition starting from the shared ancestor's `prev_state_root` (see the `NewChunkData`/`OldChunkData` construction at [2](#0-1)  and the per-shard job scheduling in `apply_chunks_preprocessing` at [3](#0-2) ). Fork choice is "highest height wins," applied atomically via `ChainUpdate::postprocess_block` and `update_head` at [4](#0-3) ; there is no revert/merge step — losing-fork chunk-apply results (chunk extras, trie changes) are simply never referenced by the canonical per-height index and are eventually garbage-collected (`clear_forks_data`). Nothing in `apply_chunk_postprocessing` ( [5](#0-4) ) ever combines or replays a losing fork's `ShardUpdateResult` into the winning fork's chain state.

The only place where results from one applied chunk could be reused across "different" block candidates is the *optimistic block* cache (`apply_chunk_results_cache`), but that mechanism is explicitly scoped to reusing a *speculative* apply of the eventual actual chunk against the eventual actual block fields (same chunk, same prev block) — it is a cache keyed by `CachedShardUpdateKey` that must match exactly, not a mechanism that merges divergent forks (see [6](#0-5)  and cache push/pop at [7](#0-6) ).

Even if the identical signed transaction is included in two competing chunks on two different forks, this is not an attack at all: each fork's `apply` increments the signer's access-key nonce exactly once (since it only sees its own transaction list), and whichever fork is discarded contributes nothing to final state. There's no way for the loser's effect to be "merged" into the winner — that would require an entirely different fork-choice/finalization design than what nearcore implements (a rewrite of `update_head`/GC, not a bug fixable at the tx-hash-dedup layer). The described "double-application across the fork-choice boundary" has no code path in this repository; forks are strictly exclusive alternatives, resolved by height comparison, never merged.

                    self.runtime_adapter.as_ref(),
                    block,
                    new_chunk_result,

  * The optimistic chunk application should produce the exact same result as the real chunk application as long as the optimistic block matches all of the real block’s fields, and the chunks used for optimistic application are exactly the chunks included in the real block (in other words, no chunk producer double-signed, and no chunks were missed).
* **Fallback and safety:** It is possible for the optimistic chunk application to incorrectly predict the actual block produced. Therefore, the original chunk application logic still needs to be executed in that case.
  * To implement cleanly, the optimistic chunk application shall serve only as a cache for the actual chunk application. It should not write any data or do anything else other than acting as a cache. The actual chunk application always happens except it may be skipped if the inputs match exactly.
