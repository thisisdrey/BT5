### Title
Heap-based buffer over-read parsing crafted ZIP/JAR central directory entries - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` and `InputZipFile::ProcessNext`/`EnsureRemaining` in `third_party/ijar/zip.cc` parse ZIP/JAR central-directory and local-file-header fields directly out of a memory-mapped, attacker-suppliable archive with insufficient bounds checking, analogous to the elfutils `read_srclines` heap over-read (ALPINE-CVE-2019-7149), where a crafted length/offset field in binary input drives a read past the mapped buffer.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-controlled bytes with `get_u2le`/`get_u4le`, and none of these primitive readers perform any bounds check — they simply dereference the pointer and advance it: [1](#0-0) 

`ProcessCentralDirEntry` then walks the ZIP64 "extra field" sub-records using an attacker-controlled `data_size` with no check that `extra_p + data_size` stays within the declared `extra_field_length`/mapped-file bounds, and reads 8 bytes via `get_u8le(extra)` unconditionally: [2](#0-1) 

Unlike `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before reading `file_name_`/`extra_field_`, `ProcessCentralDirEntry` performs **no** `EnsureRemaining` calls at all before any of its reads, so a crafted central directory entry near the end of the mapped region can push the cursor past the actual file/mmap boundary. [3](#0-2) 

The one bounds-check helper that does exist, `EnsureRemaining`, is itself vulnerable to unsigned-integer underflow: `in_offset` and `remaining` are computed as unsigned `size_t` subtractions, so if the cursor `p` (derived from an attacker-controlled `offset` field read out of the corrupted/over-read central directory) ends up past `input_file_->Length()`, the subtraction wraps around to a huge value and the check silently passes: [4](#0-3) 

That corrupted `offset` is exactly what feeds the seek in `ProcessNext`: [5](#0-4) 

So the invariant that "container parsing stays within the mapped archive bounds" is broken in two independent ways: (1) unchecked length fields in `ProcessCentralDirEntry` read past the buffer directly, and (2) the one guard that exists (`EnsureRemaining`) can be defeated by integer underflow using an attacker-controlled `offset`/size value, letting subsequent `ProcessFile`/`UncompressFile` reads pull heap memory beyond the archive into the data reported to `ZipExtractorProcessor::Process`.

### Impact Explanation
This code path is used by `ijar` (generating interface jars from `.jar` dependencies) and by `singlejar`, both of which process JAR/ZIP archives that can originate from external, attacker-controlled sources (e.g. `http_jar`/`http_file`-fetched Maven artifacts, or a crafted jar checked into an untrusted CI branch). A checksum on the archive blob (sha256 in `http_jar`/`http_archive`) only verifies the bytes are the ones an attacker chose to serve — it does nothing to stop the parser from misbehaving on a byte-correct-but-structurally-malicious ZIP. The result is a heap-based buffer over-read: at minimum this crashes the build tool (equivalent to the elfutils `eu-nm` segfault demonstrated in the CVE), and at worst it lets adjacent heap bytes be copied into the tool's `Process()` callback and end up embedded in the generated interface jar / merged output jar, i.e., unintended heap-memory disclosure into a build artifact.

### Likelihood Explanation
Any build that consumes a `.jar` from an untrusted origin (dependency mirror, malicious PR branch, compromised registry) through `ijar` or `singlejar` reaches this parser with attacker-fully-controlled bytes; no special privileges beyond serving/publishing the file are required, matching the "hostile origin server" premise.

### Recommendation
Add `EnsureRemaining`-style checks (using a subtraction that first verifies `p >= zipdata_in_` and `p - zipdata_in_ <= input_file_->Length()` before computing `remaining`) to `ProcessCentralDirEntry` before every multi-byte read and before advancing past `file_name_length`/`extra_field_length`/`file_comment_length`; also bound the ZIP64 extra-field walk so `extra_p + data_size` cannot exceed the declared extra-field region, and change `EnsureRemaining`'s arithmetic to avoid unsigned underflow (e.g. compare pointers instead of subtracting into `size_t`).

### Proof of Concept
I could not fully verify a concrete crash/leak reproduction within the available exploration budget — this would need to be confirmed with an ASAN-instrumented build. A reproducible check would follow the existing `third_party/ijar/test/zip_test.sh` / `IjarTests.java` harness pattern: craft a minimal ZIP whose End-Of-Central-Directory and central directory are valid per `FindZipCentralDirectory`'s checks, but whose single CDH entry declares `extra_field_length` large enough that the ZIP64 sub-record's `data_size` walks `extra_p` past the mmap'd file end, or whose `local_header_offset` is set so that the derived `p` in `ProcessNext` exceeds `input_file_->Length()` (triggering the `EnsureRemaining` underflow), then run it through `ijar`/`singlejar` under AddressSanitizer and confirm a `heap-buffer-overflow: READ` report. [6](#0-5)

  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,

    return false;
  }

  // not match the file offset, so always update our pointer.

    return false;
  }

    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}

// Given the data in the zip file, returns the offset of the central directory
// and the number of files contained in it.
bool FindZipCentralDirectory(const u1 *bytes, size_t in_length, u8 *offset,
                             const u1 **central_dir) {
  static const int MAX_COMMENT_LENGTH = 0xffff;
  static const int CENTRAL_DIR_LOCATOR_SIZE = 22;
  // Maximum distance of start of central dir locator from end of file
  static const int MAX_DELTA = MAX_COMMENT_LENGTH + CENTRAL_DIR_LOCATOR_SIZE;
  const u1* last_pos_to_check = in_length < MAX_DELTA
      ? bytes
      : bytes + (in_length - MAX_DELTA);
  const u1* current;
  bool found = false;

  for (current = bytes + in_length - CENTRAL_DIR_LOCATOR_SIZE;
       current >= last_pos_to_check;
       current-- ) {
    const u1* p = current;
    if (get_u4le(p) != EOCD_SIGNATURE) {
      continue;
    }

    p += 16;  // skip to comment length field
    u2 comment_length = get_u2le(p);

    // Does the comment go exactly till the end of the file?
    if (current + comment_length + CENTRAL_DIR_LOCATOR_SIZE
        != bytes + in_length) {
      continue;
    }

    // Hooray, we found it!
    found = true;
    break;
  }

  if (!found) {
    fprintf(stderr, "file is invalid or corrupted (missing end of central "
                    "directory record)\n");
    return false;
  }

  EndOfCentralDirectoryRecord cd;
  const u1* end_of_central_dir = current;
  get_u4le(current);  // central directory locator signature, already checked
  cd.number_of_this_disk = get_u2le(current);
  cd.disk_with_central_dir = get_u2le(current);
  cd.central_dir_entries_on_this_disk = get_u2le(current);
  cd.central_dir_entries = get_u2le(current);
  cd.central_dir_size = get_u4le(current);
  cd.central_dir_offset = get_u4le(current);
  u2 file_comment_length = get_u2le(current);
  current += file_comment_length;  // set current to the end of the central dir

  if (!FindZip64CentralDirectory(bytes, in_length, &end_of_central_dir, &cd)) {
    return false;
  }

  if (cd.number_of_this_disk != 0 || cd.disk_with_central_dir != 0 ||
      cd.central_dir_entries_on_this_disk != cd.central_dir_entries) {
    fprintf(stderr, "multi-disk JAR files are not supported\n");
    return false;
  }

  if (cd.central_dir_offset + cd.central_dir_size > in_length) {
    fprintf(stderr, "central directory offset/size is invalid\n");
    return false;
  }

  // Do not change output values before determining that they are OK.
  *offset = cd.central_dir_offset;
  // Central directory start can then be used to determine the actual
  // starts of the zip file (which can be different in case of a non-zip
  // header like for auto-extractable binaries).
  *central_dir = end_of_central_dir - cd.central_dir_size;
  return true;
}
