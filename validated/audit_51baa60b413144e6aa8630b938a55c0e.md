#### Title
Unbounded tar entry count/depth in `SetCustomHooks` allows CPU/memory DoS via `filepath.WalkDir` double-traversal while holding the hooks lock - ([File: internal/gitaly/repoutil/custom_hooks.go])

#### Summary
`SetCustomHooks` extracts an attacker-supplied tar stream via `ExtractHooks` and then walks the resulting directory tree twice with `newDirectoryVote` (once for the prepared vote, once for the committed vote) while the `custom_hooks` directory is held locked with `safe.NewLockingDirectory`. Neither the RPC handler, `ExtractHooks`, nor `newDirectoryVote` enforce any limit on the number of entries, nesting depth, or extracted size of the tar, so a pathological archive (e.g. millions of tiny files) causes proportionally expensive work under the lock.

#### Finding Description
The call chain is `SetCustomHooksRequest` stream → `server.SetCustomHooks` (`internal/gitaly/service/repository/set_custom_hooks.go:13`) → `repoutil.SetCustomHooks` (`internal/gitaly/repoutil/custom_hooks.go:100`). The handler acquires `hooksLock` [1](#0-0) , then calls `ExtractHooks`, which pipes the raw request stream into a `tar -xf -` subprocess with no size or entry-count restriction [2](#0-1) . After extraction, `newDirectoryVote` recursively walks every extracted file with `filepath.WalkDir`, hashing each path, permission bits, and full file contents — done once against the temp directory (prepared vote) and once against the final repo location (committed vote) [3](#0-2) . All of this — tar extraction, both directory walks, and the rename operations — happens between `hooksLock.Lock()` and `hooksLock.Unlock()` [4](#0-3) . There is no check on entry count, path depth, or total size anywhere in this code, nor in `storage.Locator`/`ValidateRepository` validation performed before this call [5](#0-4) .

#### Impact Explanation
This matches Gitaly's DoS impact class: an attacker with write access to any repository they own can force the Gitaly node to spend excessive CPU/memory/time inside the RPC handler while holding the per-repository custom-hooks lock, blocking any other legitimate `SetCustomHooks`/`RestoreCustomHooks` call on the same repository for the duration. If issued repeatedly/concurrently against many repositories, this can consume significant Gitaly worker/goroutine and disk I/O capacity node-wide. However, this repository's default `[[concurrency]]` limiting (`internal/grpc/middleware/limithandler`) can be, and per GitLab.com production practice generally is, configured per-RPC with `max_per_repo`/`max_queue_size`/`max_queue_wait`, which bounds the number of concurrently in-flight `SetCustomHooks` calls per repository and mitigates (but does not eliminate) the impact — this is an operator-configured mitigation, not a Gitaly code-level limit, so the underlying resource-exhaustion primitive still exists in the handler itself. There is no explicit gRPC message size cap, tar entry-count cap, or extraction-size cap enforced in the code shown.

#### Likelihood Explanation
Any unprivileged user who can push to or otherwise write custom hooks (e.g., via a GitLab feature or internal API surface that ultimately triggers `SetCustomHooksRequest`) on a repository they control can trigger this without any special role, satisfying the stated attacker model. The attack is fully repeatable and requires no race condition or timing — a single pathological tar (e.g., 10^6 small files) is sufficient to multiply CPU/disk work through two full `filepath.WalkDir` traversals of the same tree.

#### Recommendation
Enforce explicit resource bounds before/while extracting custom hooks: cap the maximum tar stream size read by `ExtractHooks`, cap the maximum number of entries and/or maximum path depth extracted (e.g., inspect entries incrementally instead of shelling out to `tar` unconditionally), and consider computing prepared/committed vote hashes without a full second content-hashing walk (e.g., reuse the prepared vote hash or hash directory metadata incrementally as extraction proceeds) to avoid doing double the I/O work under the lock. Additionally, ensure default (non-zero) per-RPC concurrency limits are documented/shipped for `SetCustomHooks`/`RestoreCustomHooks` so a single repository cannot queue unbounded pathological requests.

// newDirectoryVote creates a voting.VoteHash by walking the specified path and
// generating a hash based on file name, permissions, and data.
func newDirectoryVote(basePath string) (*voting.VoteHash, error) {
	voteHash := voting.NewVoteHash()

	if err := filepath.WalkDir(basePath, func(path string, entry fs.DirEntry, err error) error {
		if err != nil {
			return err
		}

		relPath, err := filepath.Rel(basePath, path)
		if err != nil {
			return fmt.Errorf("getting relative path: %w", err)
		}

		// Write file relative path to hash.
		_, _ = voteHash.Write([]byte(relPath))

		info, err := entry.Info()
		if err != nil {
			return fmt.Errorf("getting file info: %w", err)
		}

		// Write file permissions to hash.
		permBytes := make([]byte, 4)
		binary.BigEndian.PutUint32(permBytes, uint32(info.Mode()))
		_, _ = voteHash.Write(permBytes)

		if entry.IsDir() {
			return nil
		}

		file, err := os.Open(path)
		if err != nil {
			return fmt.Errorf("opening file: %w", err)
		}
		defer file.Close()

		// Copy file data to hash.
		if _, err = io.Copy(voteHash, file); err != nil {
			return fmt.Errorf("copying file to hash: %w", err)
		}

		return nil
	}); err != nil {
		return nil, fmt.Errorf("walking directory: %w", err)
	}

	return &voteHash, nil
}
