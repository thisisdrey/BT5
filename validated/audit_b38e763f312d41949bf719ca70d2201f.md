### Title
Missing zero-address validation on `new_authority` in `transfer_to_new_account` / `transfer_to_new_account_pda` permits permanent lock of migrated account funds - (File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs)

### Summary
The bug class from the Celo report — functions accepting an address parameter without checking it is not the zero address, causing permanent loss of control (`_setOwner` in `Proxy.sol`) — has a direct analog in marginfi-v2's account-migration instructions. `transfer_to_new_account` and `transfer_to_new_account_pda` accept a caller-supplied `new_authority` account with no validation that it is not `Pubkey::default()`, and set it as the sole authority of the newly created `MarginfiAccount`, which inherits the old account's entire `lending_account` (deposits/borrows).

### Finding Description
Both instructions take `new_authority` as a completely unchecked account: [1](#0-0) [2](#0-1) 

The handler unconditionally uses `ctx.accounts.new_authority.key()` to initialize the new account's authority field, with no `require_keys_neq!` / zero-address check anywhere in the function: [3](#0-2) [4](#0-3) 

Immediately after, the old account is disabled and its entire `lending_account` state (deposits, borrows) is emptied on the old account and effectively relocated to the new account: [5](#0-4) 

Because Solana has no private key corresponding to `Pubkey::default()` (the system-owned all-zero pubkey), an account whose `authority` field is set to the zero address can never again be controlled by any signer. All subsequent authority-gated actions (`lending_account_withdraw`, `lending_account_borrow`, order placement, emissions-destination updates, another `transfer_to_new_account`, etc.) require `authority: Signer<'info>` matching `marginfi_account.load()?.authority`, which becomes permanently unsatisfiable.

Notably, the off-chain `p0-cli` tooling explicitly guards against this exact mistake client-side: [6](#0-5) 

This confirms the risk is recognized by the team, but the on-chain program itself — which is the actual security boundary and can be called directly by any dApp/integrator/script bypassing the CLI — has no equivalent check.

### Impact Explanation
If `new_authority` is `Pubkey::default()` (whether due to a client bug defaulting an unset parameter, a malicious front-end, or user error), the resulting `MarginfiAccount` and all the deposits/borrow positions migrated into it become permanently unrecoverable by the user: no signer can ever satisfy the `authority` checks gating withdrawals, repayments, order management, or further account migration. This matches the "permanent lock/freeze" impact category, directly analogous to the Celo `Proxy._setOwner` zero-address issue causing "permanent loss of control over the proxy ownership."

Liquidation of an unhealthy position in that state may still proceed permissionlessly (since liquidation doesn't require the account authority's signature), but any surplus collateral, healthy positions, or accrued emissions become permanently locked with no path to recovery for the legitimate owner.

### Likelihood Explanation
Both instructions are unprivileged/user-callable (any `MarginfiAccount` authority can invoke `transfer_to_new_account`/`transfer_to_new_account_pda` on their own account), so the path is fully reachable without any privileged role. The likelihood of an accidental zero address is non-trivial in practice: integrators frequently build automation around such migration flows, and any client-side bug that fails to populate `new_authority` (e.g., an unset variable serialized as default) — the same category the Celo report warns about ("some Ethereum clients may default to sending null parameters if none are specified") — would trigger this irreversibly on-chain, since the program itself performs no defensive check.

### Recommendation
Add an explicit check in both `transfer_to_new_account` and `transfer_to_new_account_pda` (and in `initialize_migrated_account`, for defense-in-depth) that rejects `Pubkey::default()`:

```rust
check!(
    ctx.accounts.new_authority.key() != Pubkey::default(),
    MarginfiError::InvalidAuthority // or a new dedicated error
);
```

This mirrors the recommended fix pattern from the Celo report (require non-zero-address inputs) and prevents irreversible fund lockup from a single malformed instruction argument.

### Proof of Concept
1. User creates and funds a `MarginfiAccount` with deposits/borrows via `lending_account_deposit`/`lending_account_borrow`.
2. User (or an integrator's automation with a bug) calls `transfer_to_new_account` (or `transfer_to_new_account_pda`), signing as the current `authority`, but supplies `new_authority = Pubkey::default()` (system program's null pubkey) as the `new_authority` account.
3. The instruction succeeds: it validates flashloan/receivership/order-execution flags and `migrated_to == Pubkey::default()`, but never checks `new_authority != Pubkey::default()` — see `transfer_to_new_account` at [7](#0-6) .
4. `initialize_migrated_account` sets `new_account.authority = Pubkey::default()` and copies over `old_account.lending_account` (deposits/borrows), while `finalize_migrated_old_account` disables the old account and zeroes its `lending_account`.
5. From this point, any instruction requiring `authority: Signer<'info>` to equal `new_account.authority` (withdraw, repay, borrow, place/cancel order, another transfer) can never be satisfied by any real signer, permanently locking the migrated funds — with no on-chain recovery mechanism, since only a signature from the (nonexistent) zero-address key could unlock them.

```rust
pub fn transfer_to_new_account(ctx: Context<TransferToNewAccount>) -> MarginfiResult {
    // Validate the global fee wallet and claim a nominal fee
    let group = ctx.accounts.group.load()?;
    check_eq!(
        ctx.accounts.global_fee_wallet.key(),
        group.fee_state_cache.global_fee_wallet,
        MarginfiError::InvalidFeeAta
    );
    anchor_lang::system_program::transfer(ctx.accounts.transfer_fee(), ACCOUNT_TRANSFER_FEE)?;

    let mut old_account = ctx.accounts.old_marginfi_account.load_mut()?;

    check!(
        !old_account.get_flag(ACCOUNT_IN_FLASHLOAN),
        MarginfiError::AccountInFlashloan
    );

    check!(
        !old_account.get_flag(ACCOUNT_IN_RECEIVERSHIP),
        MarginfiError::ForbiddenIx
    );

    check!(
        !old_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION),
        MarginfiError::ForbiddenIx
    );

    check!(
        old_account.active_orders == 0,
        MarginfiError::IllegalAction,
        "Close all active orders before transfer"
    );

    // Prevent multiple migrations from the same account
    check_eq!(
        old_account.migrated_to,
        Pubkey::default(),
        MarginfiError::AccountAlreadyMigrated
    );

    let mut new_account = ctx.accounts.new_marginfi_account.load_init()?;
    let current_timestamp = Clock::get()?.unix_timestamp as u64;
    initialize_migrated_account(
        &mut new_account,
        &old_account,
        ctx.accounts.new_authority.key(),
        current_timestamp,
        ctx.accounts.old_marginfi_account.key(),
    );
```
