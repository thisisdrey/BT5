### Title
Attacker fills a victim's per-account token list via dust `DepositToken` transfers/deposits, bricking deposits, issuance, and `seize` payouts (MAX_TOKENS_PER_USER griefing) - ([File: contracts/Pool.sol])

### Summary
Like CVE-2021-22569, where a tiny crafted protobuf payload forces the parser into repeated expensive work, a small amount of dust collateral lets an unprivileged attacker force a victim's account state into a pathological configuration: every subsequent `deposit`, `issue`, `mint`, `leverage`, or `liquidate`-seizure that would add a new token to the victim's (or a liquidator's) per-account `MappedEnumerableSet` reverts with `UserReachedMaxTokens`. The "repeated pauses" analog is a revert inserted into every state-changing path that touches the account's token list.

### Finding Description
`Pool` tracks, per account, which deposit tokens and debt tokens have a non-zero balance in `depositTokensOfAccount` and `debtTokensOfAccount` (`MappedEnumerableSet.AddressSet`). Combined, these lists are capped at `MAX_TOKENS_PER_USER = 30`. [1](#0-0) [2](#0-1) 

The cap is enforced by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30`. [3](#0-2)  Entries are added not only by the account owner: `DepositToken._transfer` adds the token to the *recipient's* list whenever the recipient previously had a zero balance. [4](#0-3)  `DepositToken.deposit(amount_, onBehalfOf_)` similarly mints to `onBehalfOf_` and adds the token to the beneficiary's list via `_mint`. [5](#0-4) [6](#0-5)  `DebtToken._mint` adds debt tokens on first receipt. [7](#0-6) 

An unprivileged attacker who holds dust (1 wei) of each registered `DepositToken` in a pool can push entries into any victim's list by either:

1. Calling `DepositToken.transfer(victim, 1)` for every deposit token the victim doesn't already hold (no lock/health check on plain transfers — `_revertIfLocked` only guards the sender's own locked balance). [8](#0-7) 
2. Calling `DepositToken.deposit(1, victim)` — `deposit` accepts an arbitrary `onBehalfOf_`. [6](#0-5) 

Once the victim's combined count hits 30:

- `deposit` / `NativeTokenGateway.deposit` / `VesperGateway` deposits of a collateral token the victim doesn't hold revert inside `_mint` → `addToDepositTokensOfAccount`. [9](#0-8) 
- `DebtToken.issue` / `mint` (and `SmartFarmingManager.leverage`, which ends in `DebtToken.mint`) for any new synthetic revert, since the debt token can't be added. [10](#0-9) [11](#0-10) 
- `Pool.liquidate` reverts if the liquidator's own list is full, because `depositToken_.seize(account_, liquidator, ...)` performs a `_transfer` to the liquidator — filling a known liquidator bot's list DoSes liquidations of any position that would grant it a new token. [12](#0-11) 

### Impact Explanation
Temporary freezing of funds / liveness break, with a path to direct loss. The critical scenario: a victim's position drifts toward unhealthy and they attempt to deposit a *new* collateral type to restore health. The attacker front-runs with dust transfers/deposits to fill the 30-slot list; the victim's `deposit` reverts with `UserReachedMaxTokens`, and the attacker liquidates the position, collecting the `liquidatorIncentive` bonus. [13](#0-12)  The victim retains the ability to `transfer` dust entries away to free slots (each removal happens on zero balance), so the freeze is temporary and race-dependent, but a determined attacker can re-fill slots again (they still hold dust of other tokens and can re-acquire), and each of the victim's remediation transactions can be front-run. Additionally, stuffing a liquidator's list to 30 makes `liquidate` revert for any seized-token type not already in their set, temporarily blocking liquidations and letting bad debt accrue.

### Likelihood Explanation
Requirements: the pool must have enough registered `DepositToken`s for the attacker (plus the victim's existing entries) to reach the combined cap of 30 — debt tokens are non-transferable (`transfer`/`transferFrom` revert), so the attacker can only push deposit-token entries. [14](#0-13)  In pools with many collateral listings this is cheap: cost is ~30 dust transfers plus acquiring dust of each underlying. No privileged role, oracle manipulation, or governance action is needed; `deposit`'s `whenNotPaused`/`nonReentrant` and the `SynthContext` sender resolution do not stop it. [15](#0-14)  Likelihood is bounded by the victim being able to clear entries and by pools that list few collaterals, where the cap may be unreachable for a fresh victim — but it is fully reachable against any account already holding a meaningful number of positions, or against liquidator bots whose sets are grown over time.

### Recommendation
Decouple "receiving a token" from the per-account accounting limit:

- In `DepositToken._transfer`/`_mint`, do not revert the whole transfer when the recipient's list is full; skip the `addToDepositTokensOfAccount` bookkeeping (track collateral via `balanceOf` directly, or treat the enumerable set as best-effort).
- Alternatively, charge a minimum first-deposit/first-transfer amount (e.g., require `amount_ >= dustThreshold` when `balanceOf[recipient_] == 0`) so griefing a slot costs meaningful capital.
- For liquidation, have `seize` credit the liquidator without adding to `depositTokensOfAccount` (or allow seize to bypass the cap), so liquidations cannot be bricked by dust stuffing.

### Proof of Concept
Hardhat-style sketch (pool with ≥ enough deposit tokens `dT[0..k]`, victim already holding `m` tokens such that `m + k ≥ 30`):

```solidity
// attacker holds 1 wei of each deposit token dT[i]
for (uint i; i < dT.length; ++i) {
    if (dT[i].balanceOf(victim) == 0) {
        dT[i].transfer(victim, 1);           // adds dT[i] to victim's set
        // or: dT[i].deposit(1, victim);
    }
}
// now pool.debtTokensOfAccount+depositTokensOfAccount(victim) == 30

// victim tries to deposit new collateral dNew to avoid liquidation:
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
dNew.connect(victim).deposit(amount, victim);   // reverts inside _mint -> addToDepositTokensOfAccount

// attacker liquidates the now-unhealthy victim
pool.connect(attacker).liquidate(msX, victim, amountToRepay, msdCollateral);
```

Against a liquidator `L`, the same loop on `L` makes `pool.liquidate(...)` revert at `depositToken_.seize(account_, L, _toLiquidator)` whenever the seized token is new to `L`.

        uint256 _senderBalanceBefore = balanceOf[sender_];
        if (_senderBalanceBefore < amount_) revert TransferAmountExceedsBalance();
        uint256 _recipientBalanceBefore = balanceOf[recipient_];

        unchecked {
            balanceOf[sender_] = _senderBalanceBefore - amount_;
            balanceOf[recipient_] += amount_;

        emit Transfer(sender_, recipient_, amount_);

        // Add this token to the deposit tokens list if the recipient is receiving it for the 1st time

            pool.addToDepositTokensOfAccount(recipient_);
        }

        // Remove this token from the deposit tokens list if the sender's balance goes to zero
