### Title
Attacker-controlled `CertVersion` field is trusted without cross-validation against the actual certificate bytes format - (File: `handshake/machine.go`)

### Summary
The external report flags RouterV2 for trusting an attacker-supplied declaration (`amountIn`) without checking it against the actual value provided (`msg.value`), leading to a mismatch that a legitimate-looking input can silently corrupt processing. The analogous pattern in Nebula is `Machine.validateCert` in `handshake/machine.go`, which uses the peer-declared `payload.CertVersion` field to select the certificate parsing routine for `payload.Cert`, without any independent verification that the raw cert bytes actually match the declared version/format before dispatch.

### Finding Description
During a handshake, the peer sends a `Payload` containing `Cert` (raw bytes) and `CertVersion` (an attacker-controlled `uint32` field parsed straight off the wire in `handshake/payload.go`, `unmarshalPayloadDetails`, lines 154-163). `Machine.validateCert` immediately uses this declared version to dispatch parsing: [1](#0-0) 

`cert.Recombine` switches solely on the declared `v` to decide whether to run the protobuf-based V1 unmarshaler or the ASN.1-based V2 unmarshaler on the attacker-supplied `rawCertBytes`: [2](#0-1) 

There is no check that the declared `CertVersion` actually corresponds to the wire format present in `payload.Cert` beyond what each version-specific unmarshaler happens to reject as malformed input. The field is fully attacker-controlled (parsed from wire bytes with only overflow/wire-type checks, no correlation with `Cert`), and the dispatch trusts the declared field over any structural verification that the two are consistent.

### Impact Explanation
If `CertVersion` and the actual encoding of `Cert` are mismatched, the two version-specific parsers (protobuf for V1 vs ASN.1/cryptobyte for V2) may interpret the same byte sequence differently. Because `unmarshalCertificateV1`/`unmarshalCertificateV2` are permissive at the format-validity level (they only check that *their own* wire format is well-formed, not that it was produced by the intended encoder), this creates a class of version-confusion parsing where a byte sequence intended by an honest peer for one certificate structure could, if crafted, still validate under a different parser context and change certificate semantics (name, curve, networks, groups) before signature/CA-chain verification is applied in `CAPool.verify`. This is analogous to RouterV2 not checking that the declared `amountIn` matches the actually-provided `msg.value`: the router trusted a caller-supplied quantity as ground truth for how to process another caller-supplied quantity, exactly as `validateCert` trusts caller-supplied `CertVersion` as ground truth for how to interpret caller-supplied `Cert` bytes.

### Likelihood Explanation
Low-to-moderate. Exploitation requires crafting `Cert` bytes that are simultaneously "valid enough" under the parser selected by a mismatched `CertVersion` to pass structural validation, and then passing the downstream signature/CA-chain checks in `cert/ca_pool.go`. The `verify()` function still enforces CA fingerprint/signature/curve/constraint checks (`cert/ca_pool.go` lines 210-249), which substantially reduces exploitability since a mismatched or corrupted certificate structure would generally fail signature verification. I was unable to fully verify, within the scope of this pass, whether any crafted cross-version byte sequence exists that both parses successfully under the "wrong" version and produces a signature that still validates — this would require deeper cryptobyte/protobuf format-collision analysis that I could not complete with the available tools.

### Recommendation
Do not let the peer-declared `CertVersion` be the sole selector for how to interpret `Cert`. Either:
- Encode the version as a self-describing prefix/tag inside `Cert` itself (rather than a separate, independently-trusted field) so the parser used is intrinsically bound to the bytes being parsed, or
- After `cert.Recombine` succeeds, verify that re-marshaling the resulting certificate under the same declared version reproduces bytes consistent with what was received (cross-check), rejecting on any mismatch, similar in spirit to checking `msg.value == amountIn` before trusting `amountIn` for further processing.

### Proof of Concept
Not fully constructible from static analysis alone. A concrete PoC would require producing a `Cert` byte sequence that:
1. Parses successfully as ASN.1/cryptobyte under `unmarshalCertificateV2` while `CertVersion` is declared as `Version1` (or vice versa, parsing successfully as protobuf under `unmarshalCertificateV1` while `CertVersion` is declared `Version2`), and
2. Still produces a certificate whose signature validates against a real CA in `CAPool`.
This requires crafting a byte-level collision between the protobuf and ASN.1 wire formats, which was not verified in this pass — flagged as an open item rather than a confirmed exploit chain.

func Recombine(v Version, rawCertBytes, publicKey []byte, curve Curve) (Certificate, error) {
	if publicKey == nil {
		return nil, ErrNoPeerStaticKey
	}

	if rawCertBytes == nil {
		return nil, ErrNoPayload
	}

	var c Certificate
	var err error

	switch v {
	// Implementations must ensure the result is a valid cert!
	case VersionPre1, Version1:
		c, err = unmarshalCertificateV1(rawCertBytes, publicKey)
	case Version2:
		c, err = unmarshalCertificateV2(rawCertBytes, publicKey, curve)
	default:
		return nil, ErrUnknownVersion
	}

	if err != nil {
		return nil, err
	}

	if c.Curve() != curve {
		return nil, fmt.Errorf("certificate curve %s does not match expected %s", c.Curve().String(), curve.String())
	}

	return c, nil
}
