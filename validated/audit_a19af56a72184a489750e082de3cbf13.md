### Title
Race condition between `window.Check` and `window.Update` allows a replayed/duplicated UDP packet to bypass the anti-replay window twice - ([File: connection_state.go])

### Summary
`(*ConnectionState).Decrypt` releases `decryptLock` between the anti-replay `window.Check` call and the AEAD `DecryptDanger` call, and re-acquires it only afterward for `window.Update`. If two goroutines (e.g. from different UDP reader queues) invoke `Decrypt` concurrently with the same `messageCounter`, both can pass `Check` before either calls `Update`, letting both goroutines successfully decrypt the same ciphertext and deliver plaintext to the caller — defeating the intended dedup guarantee of the replay window for that duplicate.

### Finding Description
`Decrypt` is structured as three separate critical sections: [1](#0-0) 

1. Lock, call `cs.window.Check(l, messageCounter)`, unlock.
2. Unlocked: call `cs.dKey.DecryptDanger(...)`.
3. Lock, call `cs.window.Update(l, messageCounter)`, unlock.

`Bits.Check` is a pure read that returns true whenever the bit for `i` is not yet set; it does not mark `i` as consumed: [2](#0-1) 

Only `Bits.Update` actually sets the bit (via `updateSlow`'s duplicate check and `set`): [3](#0-2) 

Because marking-as-seen is deferred to step 3, and steps 1–3 are not covered by a single lock, two goroutines that call `Decrypt` with the identical `messageCounter` (i.e., the same UDP datagram replayed/duplicated to the wire, or delivered twice to different reader queues) can both observe `Check == true` in step 1 before either has executed `Update`. Both then proceed to call `DecryptDanger` with the same key, nonce (`messageCounter`), and ciphertext — this succeeds deterministically for both, since it is the *same* authenticated ciphertext, not a distinct plaintext. Only the second `Update` call will correctly detect and reject the duplicate (`ErrAlreadySeen`), but by then the first goroutine has already returned decrypted plaintext to its caller, and the second goroutine also decrypts successfully in step 2 before being rejected in step 3.

The net effect is not a nonce-reuse *oracle producing two different plaintexts* — since the ciphertext is identical, AES-GCM/ChaCha20-Poly1305 decryption is deterministic and produces the same plaintext bytes both times — but it does allow a single wire packet (or a byte-for-byte duplicated/racing copy of it) to be processed twice by the receive pipeline instead of being deduplicated exactly once, which is what the anti-replay window is designed to guarantee.

### Impact Explanation
This is a race-triggered replay-window bypass: a captured or duplicated packet (which an unprivileged attacker can produce simply by re-sending the exact same UDP datagram bytes to multiple queues/paths, or by network-level duplication) can be delivered to the upper layers twice instead of once. This can cause double-processing of a single legitimate frame at the tun/firewall layer, contrary to the documented anti-replay invariant of `Bits`. It does not break confidentiality (no new plaintext is recovered, no key material leaks) and does not on its own bypass authentication, since `DecryptDanger`'s AEAD tag check still gates success. The impact is limited to occasional double delivery/duplicate processing of a single already-authenticated packet under racing conditions, not decryption of forged content or key compromise.

### Likelihood Explanation
Triggering the race requires the exact same `messageCounter` and ciphertext bytes to arrive concurrently on two goroutines calling `Decrypt` for the same `ConnectionState` — this needs either genuine network-level packet duplication (which UDP networks occasionally produce) or an attacker replaying a captured packet at just the right time relative to normal delivery, and further requires the reader-queue scheduling to interleave such that both `Check` calls execute before either `Update`. This is a narrow timing window and does not repeat reliably; it also requires the packet to have been validly encrypted in the first place (attacker cannot forge new ciphertexts without the key).

### Recommendation
Combine the check/decrypt/mark sequence for the same `messageCounter` under a single critical section, or use a per-counter reservation (e.g., a "Check-and-reserve" step that atomically marks the counter as pending before releasing the lock and doing the actual AEAD operation), so that only one goroutine can proceed to `DecryptDanger` for the same `messageCounter` at a time; failed decrypts should then roll back the reservation.

### Proof of Concept
Add a race-mode test in `connection_state_test.go`:
1. Build a real `ConnectionState` with a valid Noise `CipherState` pair (as done in existing tests) and produce one real ciphertext for `messageCounter = N`.
2. Spawn `M` goroutines (M ≥ 2) that all call `cs.Decrypt(logger, N, out, packet, nb)` concurrently with `packet` set to the same valid ciphertext bytes.
3. Run with `go test -race` and assert that only one goroutine's result is a successful decrypt while the rest return `ErrAlreadySeen`.
4. Observe (this is the expected failure under the current code) that under scheduling induced by `runtime.Gosched()` calls inserted between `Check` and `DecryptDanger`, more than one goroutine returns a successful plaintext for the same `messageCounter`, demonstrating the TOCTOU window.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
