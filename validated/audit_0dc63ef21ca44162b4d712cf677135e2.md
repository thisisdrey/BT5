### Title
Unbounded HTTP body read in `process_event` allows single-request memory exhaustion of the signer's event listener - (File: `libsigner/src/events.rs`)

### Finding Description
`process_event<T,E>` reads the entire HTTP request body into a `String` via `request.as_reader().read_to_string(&mut body)` before any parsing, length capping, or signature verification occurs. [1](#0-0)  There is no `Content-Length` cap analogous to `MAX_MESSAGE_LEN` used elsewhere in the node's HTTP body decoding (e.g., `stackslib/src/net/httpcore.rs`), and no bound like `SIGNERS_STACKERDB_CHUNK_SIZE`/`BLOCK_RESPONSE_DATA_MAX_SIZE` is applied prior to the raw byte read. The read happens for every route dispatched through `process_event`, including `/stackerdb_chunks`, `/proposal_response`, and `/new_burn_block`, all reached from `next_event` in `SignerEventReceiver::next_event`. [2](#0-1)  Only after the full body is buffered in memory does `serde_json::from_slice` attempt to parse it into `E`, and only later does deserialization of individual chunk payloads (`T::consensus_deserialize`, `read_next`) or signature recovery (`chunk.recover_pk()`) occur. [3](#0-2)  None of these later checks bound the initial allocation — the damage (unbounded buffer allocation) is done at `read_to_string` regardless of what follows.

### Impact Explanation
A party able to open a TCP connection to the signer's event-listener HTTP port and issue a POST with a large `Content-Length` and matching body can force the process to allocate memory proportional to the attacker-supplied payload size, with no upper bound enforced by this code path, potentially exhausting memory and crashing the signer's `main_loop` thread (and process, depending on OS/allocator behavior). This matches a Critical-class "remote crash/unauthenticated DoS" if — and only if — the listener is reachable by parties other than the specific node(s)/operator configured to be its event source.

### Likelihood Explanation
This finding is contingent on deployment/config facts I could not fully verify from the indexed code: the `SignerEventReceiver`'s `bind()` call uses whatever `SocketAddr` is passed in from the signer's config's `endpoint` setting [4](#0-3) . This is normally intended to be an event-observer endpoint reachable only by the specific stacks-node(s) configured to push events to this signer, not a general public P2P/RPC port. If the operator binds it to a loopback-only or firewalled address (the typical/recommended deployment), this is not remotely exploitable by an unprivileged internet attacker, and the finding would be out of scope per the "config" exclusion and the requirement that the attacker have no privileged role and only reach the node's P2P/RPC port. If, however, an operator exposes this listener on a public interface (which the code does not prevent, and which some deployments may do for convenience), the lack of a body-size cap is a real, low-cost, repeatable DoS vector against that instance.

### Recommendation
Enforce a maximum request-body length before/while reading (e.g., check `Content-Length` header against a constant analogous to `MAX_MESSAGE_LEN`/`SIGNERS_STACKERDB_CHUNK_SIZE`, and use a bounded reader like `Read::take(max_len)` instead of unconditional `read_to_string`) in `process_event`, rejecting oversized requests with an error response before allocating.

### Proof of Concept
A Rust test would bind a `SignerEventReceiver`, open a raw `TcpStream` to it, and send a POST to `/stackerdb_chunks` with a `Content-Length` header far exceeding any expected StackerDB chunk size (e.g., several GB) followed by a matching-size body, then assert that `process_event`/`read_to_string` either causes unbounded allocation (observable via a huge resident memory delta) or that no size check rejects the request prior to allocation — demonstrating the missing cap at `libsigner/src/events.rs:526`.

**Caveat:** I could not confirm within the indexed content whether the default/documented deployment binds this listener to a network-reachable interface reachable by unprivileged remote parties versus loopback/firewalled-only, which is required by the rules to classify this as in-scope Critical vs. out-of-scope config/deployment issue. A Devin session with full repo/docs access would be needed to check `stacks-signer` deployment docs and default config for the `endpoint` field to conclusively resolve remote reachability.

where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
