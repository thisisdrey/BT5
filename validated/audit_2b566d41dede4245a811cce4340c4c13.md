### Title
Missing upper bound on `GetLFSPointersRequest.BlobIds` enables allocation and cat-file processing DoS - ([File: internal/gitaly/service/blob/lfs_pointers.go])

### Summary
`GetLFSPointers` accepts an attacker-controlled `BlobIds` repeated string field and only validates that it is non-empty, with no cap on its length, before allocating a `gitpipe.RevisionResult` slice sized to `len(req.GetBlobIds())` and feeding every entry into the `CatfileInfo`/`CatfileObject` pipeline. A caller with normal repository access can submit a request packed with a very large number of short, garbage blob IDs to force large server-side allocation and a correspondingly large batch of cat-file lookups in a single RPC.

### Finding Description
`validateGetLFSPointersRequest` in [1](#0-0)  only rejects an empty `BlobIds` list; it performs no upper-bound check on `len(req.GetBlobIds())` and no validation that each entry is a well-formed object ID before use.

In `GetLFSPointers`, the handler unconditionally allocates a slice proportional to the attacker-supplied count and forwards every entry — valid or not — into the catfile pipeline: [2](#0-1) 

Each `gitpipe.RevisionResult{OID: git.ObjectID(blobID)}` is passed through `gitpipe.NewRevisionIterator` into `gitpipe.CatfileInfo` and then `gitpipe.CatfileObject`, meaning every attacker-supplied string — including garbage OIDs — drives a `git cat-file --batch-check`/`--batch` round for that entry before the pipeline can determine it isn't a valid LFS pointer. There is no gitaly-side cap analogous to a "max blob ids per request" limit, so the resource cost scales directly and linearly with attacker input.

The `pktLineSplitter` in `internal/git/pktline/pktline.go` referenced in the question operates on pkt-line framed streams used elsewhere (e.g., SSH/HTTP smart protocol, `read_monitor_test.go`) and is not part of the `GetLFSPointers` request path, which is a standard unary/streaming protobuf gRPC call decoded by the gRPC framework, not by `pktline`. The premise that these two are "combined" in a single exploit chain does not hold; they are unrelated code paths.

The practical bound that does exist is gRPC's default maximum receive message size (4 MiB unless explicitly overridden), which was not found to be overridden in [3](#0-2) . This still permits well over a million short string entries in a single 4 MiB request (each proto string field costs only a few bytes of overhead plus the string itself), which is enough to produce a large `make([]gitpipe.RevisionResult, ...)` allocation and a correspondingly large chain of cat-file work for one RPC call, with no additional gitaly-side cap to prevent it.

### Impact Explanation
An authenticated user with ordinary read access to a repository can send a single `GetLFSPointers` request with a very large `BlobIds` list (garbage or real OIDs) to force disproportionate memory allocation and CPU/IO time in the git cat-file pipeline relative to a normal request, degrading the Gitaly node handling that repository's traffic. This matches the "denial of service of an RPC handler" impact class.

### Likelihood Explanation
The precondition is only that the attacker can invoke `GetLFSPointers` against a repository they can access (no special role required), and craft the request payload themselves (or via the GitLab API client), which is fully within an unprivileged GitLab user's capability. The attack is trivially repeatable and requires no race conditions or timing.

### Recommendation
Add an explicit upper bound on `len(req.GetBlobIds())` in `validateGetLFSPointersRequest` (returning `InvalidArgument` when exceeded), consistent with the message-size-driven caps used elsewhere in Gitaly, so that allocation and cat-file pipeline size are bounded by more than gRPC's generic message-size limit alone.

### Proof of Concept
```go
func TestGetLFSPointers_LargeBlobIdsList(t *testing.T) {
    // ... set up server/client and a valid repository ...
    blobIDs := make([]string, 1_000_000)
    for i := range blobIDs {
        blobIDs[i] = "a" // garbage/invalid OID, repeated to stay under the 4MiB gRPC message cap
    }
    stream, err := client.GetLFSPointers(ctx, &gitalypb.GetLFSPointersRequest{
        Repository: repo,
        BlobIds:    blobIDs,
    })
    require.NoError(t, err)
    start := time.Now()
    for {
        _, err := stream.Recv()
        if err == io.EOF {
            break
        }
        require.NoError(t, err)
    }
    t.Logf("processing time for %d blob ids: %s", len(blobIDs), time.Since(start))
    // Expect measurable allocation (len(blobIDs) * sizeof(gitpipe.RevisionResult)) and
    // processing latency growing linearly with len(BlobIds), with no server-side rejection.
}
```

func validateGetLFSPointersRequest(ctx context.Context, locator storage.Locator, req *gitalypb.GetLFSPointersRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetBlobIds()) == 0 {
		return fmt.Errorf("empty BlobIds")
	}

	return nil
}
