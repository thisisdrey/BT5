Audit Report

## Title
Unprotected AMM swap with no slippage floor in Snowbridge tip/fee swap-and-burn path allows attacker-induced fund loss - (File: bridges/snowbridge/pallets/system-frontend/src/lib.rs)

## Summary
`Pallet::swap_and_burn` in the Snowbridge `system-frontend` pallet calls `T::Swap::swap_exact_tokens_for_tokens` with `amount_out_min` hardcoded to `None`, disabling slippage protection entirely regardless of swap size [1](#0-0) . This path is reachable via the public, unprivileged `add_tip` extrinsic, callable by any signed account with an arbitrary asset and amount [2](#0-1) .

## Finding Description
`add_tip` is a public extrinsic requiring only `ensure_signed(origin)`, with no permission check on the caller or the `asset` argument [2](#0-1) . It calls `swap_fee_asset_and_burn`, which for any fee asset other than Ether invokes `swap_and_burn` [3](#0-2) . Inside `swap_and_burn`, `T::Swap::swap_exact_tokens_for_tokens` is called with `amount_out_min` explicitly set to `None`, with the comment "No minimum amount required" [1](#0-0) .

The underlying `pallet_asset_conversion::Swap` trait definition documents that when `amount_out_min` is `Some`, the caller is protected from an insufficient output, implying that `None` means no protection is applied [4](#0-3) . This is confirmed by `do_swap_exact_tokens_for_tokens`'s implementation, which only performs the `amount_out >= amount_out_min` check inside `if let Some(amount_out_min) = amount_out_min` — when `None` is passed, no floor is enforced on the swap output whatsoever. The pool's constant-product pricing formula means a large trade immediately before this call shifts reserves and depresses output for the same input. Since transaction ordering within a block can be influenced by tip/fee-based prioritization or timing of submission, an unprivileged actor can manipulate pool reserves in the same block right before a victim's `add_tip` call executes, causing `ether_gained` to be abnormally low.

`ether_gained` directly determines the amount burned for teleport and the tip/reward amount reported to BridgeHub via `build_add_tip_call` [5](#0-4) . The same unprotected path is also reachable from `register_token` for non-root/non-`Here` origins [6](#0-5) .

## Impact Explanation
A depressed `ether_gained` reduces the tip/reward amount relayed and recorded on BridgeHub, while the value extracted from the tip-payer's asset via the manipulated AMM price is captured by the attacker who moved the pool reserves. This breaks value conservation for the party supplying the tip asset and distorts the reward/payout accounting downstream in the `AddTip`/`RegisterToken` calls dispatched to BridgeHub, falling under underpriced/distorted payout accounting in bridge processing.

## Likelihood Explanation
No privileged role, governance action, or compromised relayer/validator is needed — any unprivileged signed account can call `add_tip` with an arbitrary asset, and an attacker only needs ordinary transaction submission to move the shared AMM pool's reserves ahead of a victim's call in the same block. Because `amount_out_min` is unconditionally `None`, there is no failure mode that would abort the swap regardless of how adverse the realized price is, making the condition always exploitable whenever a shallow-liquidity pool is used for the tip/fee asset.

## Recommendation
Do not hardcode `None` for `amount_out_min` in `swap_and_burn`. Compute an expected minimum output via `QuotePrice::quote_price_exact_tokens_for_tokens` immediately before the swap, apply a bounded tolerance, and pass `Some(min_out)` so that `ProvidedMinimumNotSufficientForSwap` correctly reverts the swap when reserves have been manipulated beyond an acceptable threshold.

## Proof of Concept
1. Attacker observes a pending `add_tip(message_id, asset)` call that will trigger `swap_and_burn(tip_asset -> ether)` on a shallow-liquidity pool.
2. In the same block, attacker submits a large swap of `tip_asset` into the pool via `AssetConversion::swap_exact_tokens_for_tokens`, shifting reserves and depressing the `tip_asset -> ether` price.
3. Victim's `add_tip` executes `swap_and_burn`, which calls `swap_exact_tokens_for_tokens(..., None, ...)` at [1](#0-0)  — no minimum-output check exists, so the swap proceeds and returns a much lower `ether_gained` than expected.
4. Attacker reverses their swap to restore the pool and realize profit from the price differential, while the victim's tip is under-valued and the relayed reward (`ether_gained`) recorded on BridgeHub is correspondingly reduced.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
