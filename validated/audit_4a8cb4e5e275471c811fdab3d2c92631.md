### Title
`x-gitaly-cost` trailer systematically undercounts outbound bytes for unary RPCs, causing under-reported cost/rate-limit-budget scores - ([File: internal/grpc/middleware/costhandler/costhandler.go])

### Summary
The `costhandler` package computes a per-RPC "cost score" (analogous to the Stylus `DataPricer.UpdateModel` demand/cost computation) from a static weight plus a dynamic component derived from bytes transferred, and exports it via the `x-gitaly-cost` gRPC trailer for downstream rate-limit/budget accounting by Rails, Workhorse, and Cloudflare. [1](#0-0)  For `UnaryInterceptor`, the cost is computed and the trailer is set immediately after the wrapped `handler` returns, before gRPC-go actually serializes and writes the response message to the transport. Because the outbound-payload byte count is only recorded by the `grpcstats.PayloadBytes` stats handler when the framework later performs that write, the `OutPayloadBytes` value read by `dynamicCostFromContext` is always `0` (or stale) at the time the trailer is computed for every unary RPC — exactly mirroring the reported bug class where the wrong (too-small) size value is fed into a cost/demand model, producing an artificially low cost.

### Finding Description
`UnaryInterceptor` calls the real handler, then immediately computes the cost and attaches it as a trailer: [2](#0-1) 

`computeCost` combines a static per-method weight with a dynamic component derived from `grpcstats.PayloadBytesStatsFromContext(ctx)`: [3](#0-2) 

The byte counters that back this computation are populated by `PayloadBytes.HandleRPC`, which increments `OutPayloadBytes` only when gRPC-go's stats machinery reports a `stats.OutPayload` event for the response message actually being written to the transport: [4](#0-3) 

For unary RPCs, gRPC-go's server-side unary processing invokes the full interceptor chain to obtain the reply value first, and only *after* the interceptor chain returns does it encode/compress and write that reply to the transport (which is what triggers the `stats.OutPayload` callback and the trailer/status frame that carries our custom `x-gitaly-cost` trailer). Because `UnaryInterceptor` calls `grpc.SetTrailer(...)` synchronously right after `handler(ctx, req)` returns — i.e., before the response payload write and its associated stats callback have occurred — the `OutPayloadBytes` field is always unpopulated (0) at the moment `dynamicCostFromContext` reads it for a unary call. Only `InPayloadBytes` (recorded when the incoming request is deserialized, prior to interceptor invocation) is reliably present. This is a genuine "wrong measurement fed into the cost model" bug: the intended behavior (per `doc/load-management-architecture.md`, "Signal Export Layer... exports two distinct signals per RPC response... a per-RPC cost score for rate limiting") is for the cost to reflect the actual bytes transferred, but the response-side bytes are structurally excluded for the unary path. [5](#0-4) 

### Impact Explanation
This directly parallels the reported bug class: a resource/cost accounting function silently receives an incorrect (too small) input, producing lower-than-intended cost and thus cheaper-than-intended accounted usage. Here, every unary RPC call — including reachable, unprivileged, unauthenticated-adjacent traffic subject to Gitaly's own concurrency/backpressure design (`doc/backpressure.md`) — will have its exported `x-gitaly-cost` trailer under-report the true response size. Since this cost value is explicitly documented as being forwarded by clients (Rails, Workhorse) as the `X-Score` header for Cloudflare-level rate-limiting and admission decisions, systematic undercounting of response bytes for unary calls degrades the accuracy of upstream DoS/abuse mitigation, letting a client's true resource consumption exceed what is charged against its rate-limit budget. This is squarely an "RPC-handler resource limit" degradation in the permitted analog categories.

### Likelihood Explanation
This triggers deterministically on every unary RPC invocation with no special or malicious action required — it is a structural ordering bug in how the interceptor consumes stats populated by an asynchronous/out-of-band gRPC stats callback, not a rare race. Any client issuing ordinary Gitaly requests (an ordinary user's RPC) will exercise this path.

### Recommendation
- Do not compute/emit the cost trailer immediately after the handler returns for unary RPCs. Instead, move the response byte accounting to occur after the actual response payload is known to be finalized (e.g., by measuring the marshaled reply size directly in the interceptor, or by using a stats-handler-based mechanism that fires after `OutPayload` is guaranteed to have been recorded, such as computing the cost from `HandleRPC(*stats.End)` and reporting it out-of-band rather than as a trailer set from within the unary interceptor).
- Alternatively, compute the dynamic cost component directly from `proto.Size(resp)` on the reply object available inside `UnaryInterceptor` rather than relying on the `grpcstats` `OutPayloadBytes` counter for the unary case.
- Add regression tests asserting that `x-gitaly-cost` scales with actual response size for representative unary RPCs with non-trivial payloads (e.g., `RepositoryInfo`, `GetConfig`, `CommitLanguages`) to catch any future ordering regressions.

### Proof of Concept
1. Configure the cost-header interceptor as in production (`internal/gitaly/server/server.go` wiring of `costhandler.UnaryInterceptor` with the `grpcstats.PayloadBytes` stats handler).
2. Issue a unary RPC that returns a sizeable single response message (e.g., `RepositoryService/GetConfig` or `CommitService/CommitLanguages`) against a repository whose response payload is large (tens of KB+).
3. Inspect the returned `x-gitaly-cost` trailer and compare it to a computation using `proto.Size` of the actual response: the trailer's dynamic component will be `0` (i.e., `dynamicCostFromContext` returns a value based only on `InPayloadBytes`, since `OutPayloadBytes` has not yet been recorded when `computeCost` executes), whereas the true response size divided by `byteCostDivisor` (1 MiB) would non-trivially raise the score for sufficiently large responses — demonstrating the systematic undercount described above.

// UnaryInterceptor is a gRPC unary server interceptor that sets the
// x-gitaly-cost trailer after the handler completes.
func UnaryInterceptor(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
	resp, err := handler(ctx, req)

	_ = grpc.SetTrailer(ctx, metadata.Pairs(
		CostHeader, fmt.Sprintf("%d", computeCost(ctx, info.FullMethod)),
	))

	return resp, err
}

// dynamicCostFromContext computes the dynamic cost contribution from payload
// bytes tracked by the grpcstats.PayloadBytes stats handler.
func dynamicCostFromContext(ctx context.Context) int {
	stats := grpcstats.PayloadBytesStatsFromContext(ctx)
	if stats == nil {
		return 0
	}
	totalBytes := stats.InPayloadBytes + stats.OutPayloadBytes

	return int(math.Ceil(float64(totalBytes) / float64(byteCostDivisor)))
}

// HandleRPC implements per-RPC tracing and stats instrumentation.
func (s *PayloadBytes) HandleRPC(ctx context.Context, rs stats.RPCStats) {
	switch st := rs.(type) {
	case *stats.InPayload:
		bytesStats := ctx.Value(payloadBytesStatsKey{}).(*PayloadBytesStats)
		bytesStats.InPayloadBytes += int64(st.Length)
	case *stats.OutPayload:
		bytesStats := ctx.Value(payloadBytesStatsKey{}).(*PayloadBytesStats)
		bytesStats.OutPayloadBytes += int64(st.Length)
	}
}
