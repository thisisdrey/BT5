### Title
Signature over StackerDB chunk metadata omits the contract/database identity, enabling cross-contract chunk replay - (File: `libstackerdb/src/libstackerdb.rs`, `stackslib/src/net/stackerdb/db.rs`)

### Summary
`SlotMetadata::auth_digest()` — the digest a StackerDB writer signs — commits only to `slot_id`, `slot_version`, and `data_hash`. It never includes the target `QualifiedContractIdentifier` (the specific StackerDB instance/contract) that the chunk is destined for. Any node that validates an incoming chunk (`try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs`, or `validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs`) only checks that the signature recovers to the address that owns `slot_id` *in the specific DB being written to* — but because the signed digest carries no contract-scoped context, a signature that was valid (and observed on the wire, since StackerDB chunks are broadcast/pushed and are not secret) for slot `N` in contract `A` is equally valid for slot `N` in any other contract `B` where the same signer address happens to own that slot. [1](#0-0) [2](#0-1) 

### Finding Description
This is the same equality-bypass bug class as the referenced report: the report's flaw was that a check (`stake != address(asset)`) failed to account for two addresses referring to the same underlying token, letting a value be counted/claimed twice in a context the check didn't distinguish. Here, the analogous "equality that should distinguish context but doesn't" is the signature-authenticity check performed by `SlotMetadata::verify()`:

```
fn auth_digest(&self) -> Sha512Trunc256Sum {
    ... hasher.update(self.slot_id...); hasher.update(self.slot_version...); hasher.update(self.data_hash.0);
}
pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
    ... Ok(pubkh == *principal.bytes())
}
``` [3](#0-2) 

Every write path relies solely on this address-recovery equality without folding in the destination contract:

- `StackerDBTx::try_replace_chunk` looks up the slot owner *for the given `smart_contract`* and then calls `slot_desc.verify(&slot_validation.signer)`, but the digest being verified says nothing about which `smart_contract` it was meant for: [4](#0-3) 

- `StackerDBs::validate_received_chunk`, used both for chunks pulled during sync and for unsolicited pushed chunks (`PeerNetwork::handle_unsolicited_StackerDBPushChunk`), performs the identical signer-recovery check with no contract binding either: [5](#0-4) 

- The HTTP write endpoint (`POST /v2/stackerdb/:address/:contract/chunks`) takes the `contract_identifier` purely from the URL and forwards the caller-supplied `StackerDBChunkData` (including its signature) straight into `try_replace_chunk` for that contract, with no re-derivation or contract-specific check on the signature itself: [6](#0-5) 

Because the same signer/slot-owner address is commonly reused across multiple StackerDB contract instances (e.g. successive `signers-0-xxx.clar` / `signers-1-xxx.clar` reward-cycle contracts, both present in the boot contracts, and any application deploying multiple StackerDB instances with overlapping signer sets), an attacker who has observed one valid, previously broadcast `StackerDBChunkData` for contract `A` slot `k` can resubmit the exact same `(slot_id, slot_version, sig, data)` tuple to contract `B`'s HTTP endpoint. If the same address owns slot `k` in `B` and the version/size/write-count checks pass, the node accepts it as authentic for `B` — even though the signer never authorized data for `B`.

### Impact Explanation
This lets an unprivileged network peer cause a node to store, and then gossip/relay via `set_relay_message(StacksMessageType::StackerDBPushChunk(..))`, chunk data into a StackerDB contract that its purported author never signed for that contract. This is a form of unauthorized write / non-canonical data being accepted as canonical for a given StackerDB instance, and it propagates network-wide because accepted pushes are re-broadcast to peers (`handle_unsolicited_StackerDBPushChunk` / relay logic). Depending on what the target contract's data represents (e.g. signer state, block-commit-adjacent metadata), this can poison another instance's replicated state using data that was authorized for a different purpose/context, which matches the "authenticated-for-context-X served as canonical-for-context-Y" bug class described in the rules.

### Likelihood Explanation
Exploitability depends on the existence of at least two live StackerDB contracts (which is normal, not rare — Nakamoto signer StackerDBs already rotate contracts per reward cycle, `signers-0-xxx.clar`/`signers-1-xxx.clar`) where the same signer address is assigned to the same `slot_id` in both. Given deterministic/overlapping signer-set assignment across cycles, this condition is plausible without any secret key or privileged role — the attacker only needs to capture a chunk that was already publicly gossiped (chunks are not confidential) and resend it to a different contract endpoint. No brute force or cryptographic break is required, only a replay across a missing domain-separation boundary.

### Recommendation
Include the `QualifiedContractIdentifier` (and ideally a network/version discriminator) inside `SlotMetadata::auth_digest()` so that a signature is only valid for the specific StackerDB instance it was created for, e.g.:
```rust
fn auth_digest(&self, contract_id: &QualifiedContractIdentifier) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(contract_id.to_string().as_bytes());
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
Thread the contract identifier through `sign`/`verify` call sites in `try_replace_chunk`, `validate_received_chunk`, and the HTTP handler so verification is contract-scoped.

### Proof of Concept
1. Node hosts two StackerDB contracts `A` and `B`, both configuring slot `0` to be owned by address `X` (plausible for successive-reward-cycle signer contracts using the same signer set).
2. Signer `X` legitimately signs and posts `StackerDBChunkData{slot_id:0, slot_version:5, sig, data}` to `POST /v2/stackerdb/.../A/chunks`. The node accepts and gossips it (observable on the wire by any peer).
3. An unprivileged attacker captures this exact `StackerDBChunkData` payload and POSTs it unmodified to `POST /v2/stackerdb/.../B/chunks`.
4. `try_replace_chunk` for contract `B` looks up slot `0`'s owner (`X`), calls `slot_desc.verify(&X)`, which succeeds because `auth_digest()` never included the contract identity — the chunk is accepted into `B`'s slot 0 even though `X` never signed anything for `B`. [7](#0-6)

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
