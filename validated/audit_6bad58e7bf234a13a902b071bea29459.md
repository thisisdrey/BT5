### Title
Protocol fee on NEP-245/Imt `TokenDiff` intents is computed per-intent instead of per-batch, allowing fee-free splitting of large trades - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::execute_intent` computes and collects the protocol fee independently for each signed `TokenDiff` intent, using only that intent's own delta magnitude to decide whether `TokenDiff::token_fee` waives the fee for NEP-245/Imt token ids (`amount <= 1`). An attacker can split one large negative delta of an Imt/Nep245 token into many separate signed `TokenDiff` intents each with `delta == -1`, submitted together in one `MultiPayload` batch, so that every individual fee computation hits the zero-fee branch while the aggregate quantity moved is identical to a single large trade that would have paid `protocol_fee.fee_ceil(total_amount)`.

### Finding Description
The binding that should hold is: `fees_collected[T] == protocol_fee.fee_ceil(sum_of_all_negative_deltas_of_T_in_batch)` for any token `T` appearing across the whole executed `MultiPayload` batch.

What the code actually does: each `TokenDiff` intent is executed in isolation by `execute_intent` (contracts/defuse/core/src/intents/token_diff.rs:41-104). For every `(token_id, delta)` pair inside a *single* `TokenDiff.diff`, if `delta < 0` the fee is `Self::token_fee(token_id, delta.unsigned_abs(), protocol_fee).fee_ceil(amount)` [1](#0-0) . `token_fee` waives the fee entirely for `Nep245`/`Imt` token types whenever `amount <= 1`: [2](#0-1) 

Because each signed `TokenDiff` is its own `DefusePayload` with its own nonce, `execute_signed_intent` processes them one at a time via `intents.execute_intent(...)` (contracts/defuse/core/src/engine/mod.rs:79), and `Engine::execute_signed_intents` simply loops over all payloads in the batch (contracts/defuse/core/src/engine/mod.rs:32-40). There is no aggregation of the total negative delta for the *same* token id across multiple intents/payloads before the `amount > 1` fee-exemption check is applied — the check operates purely on each intent's own local `delta`.

The only batch-level check that exists is `TransferMatcher::finalize` (contracts/defuse/core/src/engine/state/deltas.rs:212-294), which only verifies that the *net* deltas across all accounts in the batch sum to zero per token (custody neutrality) — it does not recompute or verify fees. It is fully satisfied by many small offsetting deltas just as well as by one large delta, so it does not prevent or detect the fee-splitting.

Attacker's exact exploit: attacker (signer S) holds N units of an NEP-245/Imt-classified token id `M` in the Verifier. Instead of signing one `TokenDiff{ diff: {M: -N, X: +Y} }` (which would owe `protocol_fee.fee_ceil(N)` on `M`), S signs N separate `TokenDiff` intents, each `{ diff: {M: -1, X: +y_i} }` with `sum(y_i) = Y`, each with a fresh nonce, and submits them all together (plus one or more matching counterparty intents providing `X: -Y, M: +N`) in a single `execute_intents(signed: Vec<MultiPayload>)` call. For each of the N intents, `amount == 1`, so `token_fee` returns `Pips::ZERO` and `fee_ceil(1) == 0`. Total `fees_collected[M]` across the whole batch is `0`, versus `protocol_fee.fee_ceil(N)` for the equivalent single-intent trade.

### Impact Explanation
This directly bypasses protocol fee collection on the Verifier for any token classified as `TokenIdType::Nep245` or `TokenIdType::Imt` — a category that, per the codebase's own token-id abstractions, is used for fungible-like multi-token balances (not just true 1-of-1 NFTs), so an attacker holding a large quantity of such a token id can trade its entire balance while paying zero fee simply by decomposing the trade into unit-sized legs. This is the "protocol fees bypassed" Critical category explicitly named in the rules. It is fully repeatable: any account, any Imt/Nep245 token id, any batch size N, at will, with no privileged role required — only the cost of constructing and signing N small `TokenDiff` payloads (well within reach of a single transaction with many payloads batched into `execute_intents`).

### Likelihood Explanation
Preconditions are trivial for an unprivileged attacker: own/control a balance of any NEP-245/Imt token id inside the Verifier (deposit is permissionless), sign N `TokenDiff` intents locally (attacker's own keys), and have a counterparty intent (which could be the attacker's own second account, or a cooperating/self-controlled solver account) whose aggregate deltas close the batch per `TransferMatcher::finalize`. No relayer key, DAO role, or upgrade access is needed. The attack scales with N and costs only gas/signing overhead, making it fully practical and repeatable.

### Recommendation
Compute and apply the NEP-245/Imt fee-exemption threshold (`amount > 1`) against the aggregate negative delta of each token id across the entire batch (all `TokenDiff` intents executed within one `execute_signed_intents` call), not per individual intent/payload. This likely requires accumulating per-token negative deltas at the `Engine`/`Deltas` level before applying `TokenDiff::token_fee`, or moving fee accounting out of `TokenDiff::execute_intent` into a batch-finalization step (analogous to `TransferMatcher::finalize`) that sees all intents together.

### Proof of Concept
`cargo test` (near-workspaces sandbox, in `tests/src/tests/defuse/intents/token_diff.rs` style):
1. Deploy an NEP-245 token contract, deposit `N = 10` units of token id `M` (classified `Imt`/`Nep245`) to attacker account `A`, and deposit sufficient `X` to a counterparty `B`. Set `protocol_fee` to a non-zero `Pips` value.
2. Case 1 (baseline): `A` signs one `TokenDiff{ diff: {M: -10, X: +Y} }`; `B` signs a matching `TokenDiff{ diff: {M: +10, X: -Y} }`. Execute via `execute_intents`. Assert `fee_collector` balance of `M` increases by `protocol_fee.fee_ceil(10)` (non-zero).
3. Case 2 (exploit): `A` signs ten separate `TokenDiff{ diff: {M: -1, X: +y_i} }` intents (each own nonce) summing to the same `Y`; `B` signs matching offsetting intent(s) totaling `{M: +10, X: -Y}`. Execute all via one `execute_intents` call. Assert `fee_collector` balance of `M` is unchanged (fee == 0), while `A`'s and `B`'s net token balance changes for `M` and `X` are identical to Case 1.
4. Assertion demonstrating the bypass: `fees_collected_case1[M] > 0 == fees_collected_case2[M]` despite identical net economic trade, proving `Pips::fee_ceil` over the aggregate batch delta is not enforced.
