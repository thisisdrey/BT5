## Title
Integer division truncation in `MarketSellAssetActuator.matchSingleOrder` allows a maker's remaining order to be fully consumed while the maker receives zero payment - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes cross-multiplied quantities with integer division via `MarketUtils.multiplyAndDivide`, which floors the result exactly like the reported Dutch-auction `timePassed / stepSize` bug. In the "taker == maker" branch this floor-to-zero result is *not* checked before being used to both zero-out the maker's remaining balance and to skip debiting the taker's spend, letting an unprivileged order placer drain a maker's TRC10/TRX inventory for free.

### Finding Description
`matchSingleOrder` first computes `takerBuyTokenQuantityRemain` and explicitly guards against it rounding to zero (returns the sell tokens to the taker if so): [1](#0-0) 

When `takerBuyTokenQuantityRemain` exactly equals the maker's remaining sell quantity, execution enters the "taker == maker" branch, which computes `makerBuyTokenQuantityReceive` with the same `multiplyAndDivide` (floor) operation but has **no zero-guard**, unlike the symmetric "taker > maker" branch a few lines below which does check `makerBuyTokenQuantityReceive == 0`: [2](#0-1) [3](#0-2) 

`multiplyAndDivide` performs a straight floor division (`multiplyExact(a,b)/c`), i.e. exactly the `timePassed / stepSize` pattern from the report: whenever `numerator < denominator` the result truncates to `0`: [4](#0-3) 

Because the "taker == maker" branch skips the zero check:
- `takerBuyTokenQuantityReceive` is set to the **entire** `makerOrderCapsule.getSellTokenQuantityRemain()` (taker receives all remaining maker tokens).
- `makerOrderCapsule` is fully zeroed and marked `INACTIVE` (its order is fully consumed).
- `takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive` subtracts `0`, so the taker's own remaining balance is left untouched.
- `addTrxOrToken(makerOrderCapsule, 0)` credits the maker with zero payment.

This is a direct functional analog of the reported bug class: a division whose result silently floors to zero is used downstream without a sanity check, causing an economically incorrect outcome (in this case, free asset extraction instead of a stale price).

### Impact Explanation
An attacker acting only as an ordinary order placer (via `MarketSellAssetActuator`, reachable from any signed `MarketSellAssetContract` transaction) can construct a taker order whose size makes `takerBuyTokenQuantityRemain` land exactly on a small maker remainder such that `makerBuyTokenQuantityReceive` floors to zero. The maker's remaining order is consumed and marked inactive while the maker's account is credited with `0`, and the taker's own balance is not debited for that leg of the match, effectively transferring the maker's TRC10/TRX balance to the taker for free. Because the taker's order can remain `ACTIVE` afterward (since `takerSellTokenLeft` is unchanged), the taker can potentially chain further matches, amplifying the fund loss to makers. This constitutes theft of funds through an on-chain, permissionless transaction, meeting the Medium+ bar (unauthorized value transfer / fund loss).

### Likelihood Explanation
The trigger condition requires the attacker to control the taker order's sell quantity (fully attacker-controlled input) and to know or predict a maker's remaining order state (public on-chain order book state, readable before submission). Any maker order whose sell/buy ratio and remaining quantity satisfy `remain * buyQty < sellQty` is exploitable; this is easy to construct or wait for as maker orders get partially filled down to small remainders, which is a normal, common state in the order book (not a rare edge case).

### Recommendation
Add the same zero-quantity guard used in the "taker > maker" branch to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0`, refuse the match (or return the maker's remaining sell tokens to the maker without crediting/decrementing the taker), consistent with the existing handling at line 466 of `MarketSellAssetActuator.java`.

### Proof of Concept
1. Maker places an order with `sellTokenQuantity = 3`, `buyTokenQuantity = 2` (sell token A for TRX at ratio 3:2), which after prior partial fills has `sellTokenQuantityRemain = 1`.
2. Attacker (taker) submits a `MarketSellAssetContract` selling TRX with `sellTokenQuantity(remaining) = 1`.
3. `matchSingleOrder` computes `takerBuyTokenQuantityRemain = multiplyAndDivide(1, 3, 2) = floor(3/2) = 1`, which equals `makerOrderCapsule.getSellTokenQuantityRemain() = 1`, triggering the "taker == maker" branch.
4. `makerBuyTokenQuantityReceive = multiplyAndDivide(1, 2, 3) = floor(2/3) = 0`.
5. Result: maker's order (`sellTokenQuantityRemain`) is zeroed and marked `INACTIVE`; maker's account is credited `0` TRX; taker receives the maker's 1 unit of token A via `addTrxOrToken(takerOrderCapsule, 1, ...)`, and `takerSellTokenLeft = 1 - 0 = 1` leaves the taker's own order untouched/still active — the taker obtains the maker's asset for free.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
