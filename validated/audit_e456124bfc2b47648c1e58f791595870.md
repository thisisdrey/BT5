### Title
Optional persistence of invalid/expired peer certificates permits stale-trust tunnel abuse - ([File: connection_manager.go])

### Summary
The Pyth/fallback report describes a system where a user can opt to keep relying on a source of truth that is known to be stale/unverified, creating an arbitrage/trust window. Nebula has a structurally analogous choice point: `pki.disconnect_invalid`, which controls whether a tunnel is torn down once the peer's certificate becomes cryptographically invalid (expired, or no longer chains to a trusted CA).

### Finding Description
`connection_manager.go`'s `isInvalidCertificate` re-verifies the cached peer certificate against the current CA pool on every tick. If verification fails for reasons other than blocklisting, the tunnel is destroyed **only if** `cm.intf.disconnectInvalid.Load()` is true: [1](#0-0) 

This is a config-controlled boolean (`pki.disconnect_invalid`) that a node operator sets. When it is `false` (which is an allowed, supported operational mode — the changelog explicitly documents its addition as an opt-in, defaulting to `false`), a tunnel whose remote certificate has expired or whose signing CA is no longer trusted continues to carry live traffic indefinitely: [2](#0-1) 

This mirrors the reported bug class: the system exposes a knob letting a participant "opt out" of enforcing the up-to-date/trusted state (fresh cert validity, akin to Pyth) and instead perpetually rely on a stale, already-invalidated trust state (an expired cert / stale CA membership, akin to the fallback oracle), with no time-bound, deviation check, or forced re-verification cadence beyond the connection manager's periodic sweep. The FSM-like decision (`isInvalidCertificate` → `disconnectInvalid`) is a binary global switch rather than a nuanced expiry/staleness-aware policy, exactly the "rethink the FSM around stale vs trusted" critique in the source report.

Additionally, `isInvalidCertificate` only inspects the *cached* verified certificate state (`hostinfo.GetCert()` + `VerifyCachedCertificate`), and does not appear to re-derive trust from a freshly reloaded CA pool state per-connection beyond what `cm.intf.pki.GetCAPool()` currently holds — so an operator who disables `disconnect_invalid` is fully exposed to using an outdated/revoked trust anchor for the life of the tunnel.

### Impact Explanation
With `pki.disconnect_invalid=false` (an explicitly supported, non-default-forced configuration), a host whose certificate has expired, or whose CA has been removed/rotated out of the trust pool (e.g., due to compromise), keeps an active, encrypted tunnel with full firewall-permitted traffic flow. This is a remote state poisoning / persistent-trust vector: revocation and expiry — the mechanisms Nebula relies on to bound trust — become unenforced for already-established sessions, similar to how the reported bug lets stale price data keep being used past its trust window, enabling arbitrage/exploitation windows.

### Likelihood Explanation
This requires no compromise of a valid-cert holder and no malicious peer/lighthouse cooperation — it's purely a consequence of the operator-facing configuration option being disabled and time elapsing (certificate legitimately expiring or CA rotating away) while a firewall rule or trust boundary decision continues to rely on `isInvalidCertificate`/`VerifyCachedCertificate` being enforced. Because `disconnect_invalid` defaults to `false` per the changelog note, deployments that don't explicitly opt in retain long-lived tunnels on stale trust by default, making this a realistic, not a hypothetical, operating condition.

### Recommendation
- Reconsider defaulting `pki.disconnect_invalid` to `false`; make certificate expiry/CA revocation enforcement mandatory, or at minimum bound the grace period (a "time to update" analog) rather than an unlimited toggle.
- Decouple "certificate expired" from "CA removed/rotated" in `isInvalidCertificate` and enforce disconnection for the latter unconditionally, since a removed CA represents an explicit revocation decision, not routine expiry.
- Add periodic re-verification against a live/reloaded CA pool with a mismatch/staleness threshold, and log/metric the duration a tunnel has been running on invalid trust.

### Proof of Concept
1. Configure two nodes with `pki.disconnect_invalid: false` (or leave at default).
2. Establish a tunnel; then let the responder's certificate expire, or remove/rotate its issuing CA out of the initiator's `pki.ca` trust pool.
3. Observe via `connection_manager.go`'s `isInvalidCertificate` / `Test_NewConnectionManagerTest_DisconnectInvalid`-style test path that the tunnel is retained and traffic continues to flow because `disconnectInvalid` gate returns `false`, confirmed by the existing test asserting `invalid=false` before the disconnect flag flips behavior: [3](#0-2)

// isInvalidCertificate decides if we should destroy a tunnel.
// returns true if pki.disconnect_invalid is true and the certificate is no longer valid.
// Blocklisted certificates will skip the pki.disconnect_invalid check and return true.
func (cm *connectionManager) isInvalidCertificate(now time.Time, hostinfo *HostInfo) bool {
	remoteCert := hostinfo.GetCert()
	if remoteCert == nil {
		return false //don't tear down tunnels for handshakes in progress
	}

	caPool := cm.intf.pki.GetCAPool()
	err := caPool.VerifyCachedCertificate(now, remoteCert)
	if err == nil {
		return false //cert is still valid! yay!
	} else if err == cert.ErrBlockListed { //avoiding errors.Is for speed
		// Block listed certificates should always be disconnected
		hostinfo.logger(cm.l).Info("Remote certificate is blocked, tearing down the tunnel",
			"error", err,
			"fingerprint", remoteCert.Fingerprint,
		)
		return true
	} else if cm.intf.disconnectInvalid.Load() {
		hostinfo.logger(cm.l).Info("Remote certificate is no longer valid, tearing down the tunnel",
			"error", err,
			"fingerprint", remoteCert.Fingerprint,
		)
		return true
	} else {
		//if we reach here, the cert is no longer valid, but we're configured to keep tunnels from now-invalid certs open
		return false
	}
}
