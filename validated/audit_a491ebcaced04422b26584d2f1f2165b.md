### Title
Floating-point precision loss in the Bancor-style `Exchange` swap formula allows an attacker-controlled pool ratio to be exploited for token drain, analogous to Hundred Finance's donation/exchange-rate-inflation attack - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
java-tron's built-in `Exchange` feature (a Bancor-style AMM for TRX/TRC10 pairs, created via `ExchangeCreateContract` and traded via `ExchangeTransactionContract`) computes swap output using double-precision floating point and fractional `Math.pow` exponents. Any unprivileged account can create a pool with an arbitrarily skewed balance ratio and then trade against it. Because the swap math relies on `double` arithmetic truncated to `long`, extreme balance ratios (the on-chain analog of "donating" a large amount to skew the reserve ratio in the Hundred Finance incident) let a trader extract disproportionate amounts from the counter-token side of the pool, mirroring the "inflate the exchange rate, then drain via rounding" bug class.

### Finding Description
The core swap logic lives in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, which model a Bancor bonding curve using `Maths.pow(1.0 + quant/balance, 0.0005, ...)` and `Maths.pow(1.0 + supplyQuant/supply, 2000.0, ...)`, casting the double result to `long`: [1](#0-0) 

This is invoked from `ExchangeCapsule.transaction`, which is reachable by any signed transaction via `ExchangeTransactionActuator`: [2](#0-1) [3](#0-2) 

Pool creation via `ExchangeCreateContract` is open to any account with sufficient balance/assets and only rejects zero token balances — it does not enforce any minimum liquidity or bounded ratio between `first_token_balance` and `second_token_balance`: [4](#0-3) 

Only the pool creator can later `ExchangeInject`/`ExchangeWithdraw` liquidity (both actuators enforce `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`): [5](#0-4) [6](#0-5) 

However `ExchangeTransactionContract` (the swap) has no such restriction — any address can trade against any pool: [7](#0-6) 

A "hardened" alternative calculation path exists (`SafeExchangeProcessor`), but it is only used when the `ALLOW_HARDEN_EXCHANGE_CALCULATION` chain parameter is enabled, which itself requires an SR proposal to activate after fork `VERSION_4_8_2`: [8](#0-7) [9](#0-8) 

Since the parameter defaults to off until an on-chain governance vote enables it, the unsafe double-precision `ExchangeProcessor` path (using `Math.pow` with fractional/large exponents and long-truncation) remains the default execution path for swaps. Because pool creators can freely set an extreme first/second-token ratio (equivalent to "donating" an inflated balance the way the attacker donated 200 WBTC to inflate `hWBTC`'s exchange rate), and any address can then trade against that ratio via `ExchangeTransactionContract`, floating-point rounding at the boundary of the bonding-curve formula produces outputs that do not correctly reflect the intended proportional exchange rate for extreme ratios and tiny trade sizes — allowing repeated small trades to extract disproportionate value from the counter-token reserve.

### Impact Explanation
If exploitable, this allows systematic extraction of TRX/TRC10 value from an `Exchange` pool's reserves beyond what the bonding-curve invariant should allow, i.e., theft of funds held in the pool (which belong to the creator, since only the creator can inject/withdraw liquidity, but any trader interacts with and can drain the reserve through swaps). This falls under "unbacked balance" / "theft of funds" impact categories.

### Likelihood Explanation
Likelihood is High for reachability (any unprivileged account can call `ExchangeCreateContract` and `ExchangeTransactionContract` via HTTP/gRPC `wallet/exchangecreate` and `wallet/exchangetransaction` endpoints), but exact profitability depends on the magnitude of ratio skew and floating-point error accumulation, which requires numeric simulation to confirm precisely how much value can be extracted per trade and how many trades are needed to fully drain a pool. This part is **not verified by execution** in this analysis — I could not run the actual double-precision math to confirm concrete profitable parameters, only that the mechanism (double-precision Bancor curve, truncation to `long`, unrestricted pool ratio, unrestricted trading) structurally mirrors the "inflate ratio via one-sided imbalance, then exploit rounding to drain" bug class from the Hundred Finance report.

### Recommendation
- Make the hardened, integer/BigDecimal-safe exchange calculation (`SafeExchangeProcessor`) the default and mandatory path rather than an opt-in governance parameter, removing dependence on `ALLOW_HARDEN_EXCHANGE_CALCULATION`.
- Enforce a minimum liquidity/ratio bound in `ExchangeCreateActuator` and `ExchangeInjectActuator` to prevent creation of extremely skewed pools.
- Add invariant checks after every swap (e.g., k-invariant or conservation checks) in `ExchangeCapsule.transaction` to reject trades that violate the expected bonding-curve output within precision tolerance, independent of the `hardenedCalc` flag.

### Proof of Concept
Conceptual (not executed/verified numerically):
1. Attacker calls `ExchangeCreateContract` to create a pool with a highly skewed ratio, e.g., a very large `first_token_balance` and a minimal `second_token_balance` (only constrained by the non-zero check in `ExchangeCreateActuator.execute`). [4](#0-3) 
2. Any account (including the attacker) repeatedly submits small `ExchangeTransactionContract` trades against this pool, invoking `ExchangeCapsule.transaction` → `ExchangeProcessor.exchange`. [10](#0-9) 
3. Because the double-precision `Math.pow` computation and truncating cast to `long` do not perfectly preserve the bonding-curve invariant at extreme ratios, repeated small trades can extract more of the counter-token reserve than the true proportional exchange rate would allow, draining pool value analogous to the Hundred Finance donation-then-drain pattern.

Because I do not have execution tools in this environment to run the actual formula and quantify the exact profitable trade parameters, this should be validated with a numeric simulation harness (e.g., extending `framework/src/test/java/org/tron/core/capsule/utils/ExchangeProcessorTest.java`) before treating the magnitude as confirmed.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
