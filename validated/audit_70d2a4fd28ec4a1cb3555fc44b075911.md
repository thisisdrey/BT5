### Title
StackerDB chunk signatures are not bound to the target smart contract, enabling cross-StackerDB replay of validly-signed chunks - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs` computes the signed digest from only `slot_id`, `slot_version`, and `data_hash` — the target smart-contract identifier (`QualifiedContractIdentifier`) of the StackerDB replica is never part of what is signed. Every enforcement point that accepts a chunk (`try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs`, `validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs`, and the unauthenticated HTTP endpoint `RPCPostStackerDBChunkRequestHandler` in `stackslib/src/net/api/poststackerdbchunk.rs`) look up the expected signer for `(smart_contract, slot_id)` and then simply call `SlotMetadata::verify(&signer_addr)`, which recomputes the same contract-agnostic digest. Consequently, a signature that a signer produced for slot `N` in StackerDB contract A is equally valid for slot `N` in any other StackerDB contract B where that same address happens to hold the same `slot_id`.

### Finding Description [1](#0-0) 
`auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`. There is no domain separator or contract identifier folded into the digest before signing: [2](#0-1) 
`verify()` recovers the public key from that same contract-agnostic digest and only checks that the recovered key hash matches the caller-supplied `principal` — it takes no `contract_id` parameter at all.

Every write path funnels through this same equality: [3](#0-2) 
`try_replace_chunk` fetches the `slot_validation.signer` for `(smart_contract, slot_desc.slot_id)` and calls `slot_desc.verify(&slot_validation.signer)` — the contract only enters the lookup of *who* the expected signer is, not the digest that gets verified. [4](#0-3) 
`validate_received_chunk` (used for both `StackerDBSync::validate_downloaded_chunk` and `PeerNetwork::handle_unsolicited_StackerDBPushChunk`) does the identical lookup-then-verify pattern. [5](#0-4) 
The unauthenticated `/v2/stackerdb/:address/:contract/chunks` HTTP handler has no authorization/auth-token check (unlike `postblock_proposal.rs` and `postblock_v3.rs`, which require a password header) and accepts a chunk from any remote peer, relying solely on `try_replace_chunk`'s signature check for authenticity.

Because the signed digest carries no contract binding, the "authenticated-for-contract-A" and "authenticated-for-contract-B" cases are treated as equal whenever the target slot is owned by the same address in both contracts. StackerDB contracts are created afresh per reward cycle for signer message replicas (e.g. `NakamotoSigners::make_signers_db_contract_id(signer_set, reward_cycle, …)`, confirmed used in `libsigner/src/tests/mod.rs` and `stacks-signer/src/client/stackerdb.rs`), and slot allocation is deterministic from the signer set (`StackerDBConfig::signers: Vec<(StacksAddress, u32)>`), so it is common for the same signer address to be assigned the same `slot_id` across consecutive/overlapping signer-set reward cycles or across other differently-purposed StackerDB contracts that reuse the same signer set ordering.

### Impact Explanation
Any observer who has seen one legitimately-signed `StackerDBChunkData` (chunks are broadcast/public, not confidential) can replay it verbatim (unmodified `slot_id`, `slot_version`, `sig`, `data`) against a *different* StackerDB contract, over the public, unauthenticated HTTP POST endpoint or the unsolicited P2P push path, and have it accepted as authentic there — provided the addressed slot in the target contract is owned by the same signer and the version/size/max-writes checks are otherwise satisfied. This is an unauthorized write of forged/misdirected data into a StackerDB replica the signer never intended to write to (`net_error::BadSlotSigner` is bypassed because the recovered address *does* match). Downstream consumers (e.g. `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, which trusts chunk content per `SignerMessage`/`BlockResponse` decoding keyed only by `slot_id`) could then process content that was signed for an unrelated context as if it belonged to the current reward cycle/contract, causing message confusion or stale/misapplied signer state. This satisfies the "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" criteria in-scope.

### Likelihood Explanation
Exploitation requires no privileged access: the attacker only needs (a) a previously observed valid chunk (chunks in StackerDB are not secret — they are actively gossiped/replicated) and (b) knowledge that the same signer address occupies the same `slot_id` in a second StackerDB contract, which is derivable from the public signer set for each reward cycle. No node secret or private key is needed. The POST endpoint has no authentication gate at all, and the P2P unsolicited push path only performs the same contract-agnostic signature check. This makes the attack straightforward to mount remotely against any accessible node once a suitable slot-id collision across two DBs is identified.

### Recommendation
Bind the signed digest to the target StackerDB identity by including the `QualifiedContractIdentifier` (or a stable numeric `stackerdb_id`) in `SlotMetadata::auth_digest()`, and thread that value through `sign()`/`verify()`/`recover_pk()` in `libstackerdb/src/libstackerdb.rs`. Update all call sites (`try_replace_chunk`, `validate_received_chunk`, and the RPC/P2P handlers) to pass the contract identifier into `verify()`. Because this changes the wire-signed digest, it will need a versioned rollout (e.g., a protocol/epoch gate) to avoid breaking existing signers during transition.

### Proof of Concept
1. Identify two StackerDB contracts A and B (e.g., two different reward-cycle `.signers-<set>-<cycle>` contracts) whose signer sets assign the same address `addr` to the same `slot_id = k`.
2. Observe (or request via `GET /v2/stackerdb/.../chunks/k`) a validly signed chunk `{slot_id: k, slot_version: v, sig, data}` that `addr` posted to contract A.
3. Ensure contract B's slot `k` currently has a version `< v` (freshly initialized DBs start at version 0, or wait for a naturally lower version).
4. POST the identical `{slot_id: k, slot_version: v, sig, data}` tuple to `/v2/stackerdb/<addr-of-B-issuer>/<B-contract-name>/chunks` on a target node.
5. `try_replace_chunk` looks up `slot_validation.signer == addr` for contract B, calls `slot_desc.verify(&addr)`, which succeeds because the digest (`slot_id`, `slot_version`, `data_hash`) is identical to the one signed for contract A — the chunk is accepted (`accepted: true`) into contract B even though it was never intended for that replica.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
