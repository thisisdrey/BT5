### Title
Unchecked return value of `addAssetAmountV2` in `TransferAssetActuator.execute` can lead to permanent loss of TRC10 tokens - (File: actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java)

### Summary
`TransferAssetActuator.execute` deducts a TRC10 asset amount from the sender via `reduceAssetAmountV2` and explicitly checks its boolean return value, but the corresponding credit to the receiver via `addAssetAmountV2` is called without checking its return value at all. This mirrors the reported Vyper `AuctionHouse.bid` bug class: a balance-mutating "transfer"-style call whose boolean success indicator is silently discarded, allowing funds to be deducted from one party without being guaranteed to land on the other.

### Finding Description
In `TransferAssetActuator.execute`, the sender-side asset reduction is validated: [1](#0-0) 

But the immediately following receiver-side credit ignores the boolean result entirely: [2](#0-1) 

`addAssetAmountV2`/`reduceAssetAmountV2` are asset-ledger analogs of an ERC20 `transfer` call that returns a boolean success flag (typically `false` on arithmetic overflow, e.g. `LongMath.checkedAdd` failure inside the asset map update). The actuator only guards the debit side (`reduceAssetAmountV2`) with an `if (!...) throw`, exactly like the AuctionHouse code checked nothing at all for the refund `transfer`; here java-tron checks one leg but not the other, so a failure on the credit leg is silently swallowed instead of aborting the transaction.

The same asymmetric/unchecked pattern recurs in the market actuator's token-settlement helpers, which call `addAssetAmountV2` without checking its result when crediting counterparties during order matching and remainder refunds: [3](#0-2) [4](#0-3) 

### Impact Explanation
If the credit-side call fails (e.g., the receiver's existing asset balance plus the transferred amount overflows the internal accounting), the actuator still proceeds to commit the transaction as successful: the sender's balance has already been irreversibly reduced (`reduceAssetAmountV2` succeeded and was committed to `ownerAddress`), while the receiver never gets credited because the failure of `addAssetAmountV2` is not checked or rolled back. This produces an unbacked/burned TRC10 balance — total token supply accounting becomes inconsistent and the transferred value is permanently lost, which matches the High-severity "loss of funds" class from the reported issue.

### Likelihood Explanation
This is directly reachable by any unprivileged account through a standard `TransferAssetContract` broadcast via `TransferAssetActuator`, or through `MarketSellAssetContract` matching/refund logic — both are ordinary, permissionless transaction types processed by the actuator/execute pipeline. No special privileges, malicious validators, or network conditions are required; only a specific arithmetic condition (near-`Long.MAX_VALUE` asset balances) is needed to trigger the silent failure path, which is plausible for widely-held or inflated TRC10 tokens with large total supply.

### Recommendation
Check the boolean return of every asset-crediting call the same way the debit call is checked, and revert/throw `ContractExeException` on failure so the whole transaction (including the already-applied debit) is rolled back:
```java
if (!toAccountCapsule.addAssetAmountV2(assetName.toByteArray(), amount, dynamicStore, assetIssueStore)) {
  throw new ContractExeException("addAssetAmount failed !");
}
```
Apply the same guard to all other unchecked `addAssetAmountV2` call sites (e.g., `MarketSellAssetActuator.addTrxOrToken`, `MarketUtils.returnSellTokenRemain`).

### Proof of Concept
1. Craft/accumulate a receiver account whose TRC10 asset balance for `assetName` is at or near `Long.MAX_VALUE` (achievable given TRC10 total-supply limits are enforced independently per issuance path, or by repeated transfers up to the overflow boundary).
2. Broadcast a `TransferAssetContract` from any sender holding a nonzero balance of that same asset, targeting the near-overflow receiver.
3. In `TransferAssetActuator.execute`, `reduceAssetAmountV2` on the sender succeeds and is persisted (`accountStore.put(ownerAddress, ...)`), but `addAssetAmountV2` on the receiver internally hits an arithmetic overflow and returns `false` (or is a no-op) — a state not checked by the actuator.
4. The transaction still reports `code.SUCESS`, the sender's tokens are gone, and the receiver's balance is unchanged — the transferred asset amount is permanently lost/unbacked.
