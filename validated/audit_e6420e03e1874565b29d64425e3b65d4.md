### Title
insert_instantiated_attachment stores downloaded attachment content without verifying it against the requested content_hash - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When `AttachmentsBatchStateMachine`'s `DownloadingAttachment` step completes, `extend_with_attachments` decodes a peer's `/v2/attachments/{hash}` response and stores the returned `Attachment` in `context.attachments` without ever checking that the content's hash equals the `content_hash` that was actually requested (`AttachmentRequest::content_hash`). In `AttachmentsDownloader::run`, every attachment collected this way is then unconditionally passed to `network.atlasdb.insert_instantiated_attachment(&attachment)` before any equality check against the originally-requested `content_hash` is performed.

### Finding Description
The claimed equality/fault: `Attachment::hash()` (computed from the downloaded bytes) must equal `AttachmentRequest.content_hash` (derived from the on-chain-committed `attachment_instance.content_hash`) before the content is persisted as a validated attachment.

Tracing the code in `stackslib/src/net/atlas/download.rs`:
- `AttachmentsBatchStateContext::extend_with_attachments` (lines 530-558) takes the HTTP response for an `AttachmentRequest`, calls `response.decode_atlas_get_attachment()`, and on success does only:
```
self.attachments.insert(response.attachment);
report.bump_successful_requests();
```
There is no comparison of `response.attachment.hash()` (or `Hash160::from_data(&content)`) against `request.content_hash` anywhere in this function — the `AttachmentRequest` (which carries `content_hash`) is dropped after this point without being consulted for validation.
- In `AttachmentsDownloader::run` (lines 152-169), once the state machine reaches `Done`, every attachment in `context.attachments` is processed:
```rust
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;   // <-- unconditional store
    for attachment_instance in attachments_instances.into_iter() {
        resolved_attachments.push((attachment_instance, attachment.clone()));
    }
    context.attachments_batch.resolve_attachment(&attachment.hash())
}
```
`insert_instantiated_attachment(&attachment)` is called **before and regardless of** whether `find_all_attachment_instances(&attachment.hash())` returned any matching instance. It is keyed only on `attachment.hash()` computed from the peer-supplied bytes themselves, not compared to the batch's requested `content_hash`.

This differs from the `check_attachment_instances` path (lines 227-286), which is used for *already-inboxed* attachments and does perform the lookup by `attachment_instance.content_hash` before insertion — but that is a separate code path (`check_queued_attachment_instances` / `enqueue_initial_attachments`) and does not cover the just-downloaded-from-peer path in `run()`.

Exploit flow: a malicious/unprivileged peer that a node is syncing attachments from can respond to a legitimate `/v2/attachments/{content_hash}` request with **any bytes** (an `Attachment` whose actual content hash differs from the requested `content_hash`). Because `decode_atlas_get_attachment()` only deserializes the response (no hash-equality assertion inside it, as best I could determine from the reachable code), and `extend_with_attachments`/`run()` never compare `attachment.hash()` to the requested `content_hash`, the forged attachment is written into the AtlasDB via `insert_instantiated_attachment` unconditionally, for any peer response.

### Impact Explanation
This would let a remote peer's forged attachment content be durably stored in a victim node's AtlasDB, decoupled from the actual on-chain `content_hash` commitment — i.e., storing non-canonical/forged data as if validated. Downstream consumers keyed by `attachment.hash()` (its own self-hash) rather than by the original `content_hash` would never "pair" with the correct `attachment_instance` (since `find_all_attachment_instances` is keyed by the forged content's own hash, which won't match any real instance's `content_hash`), so the forged blob would sit unpaired in the "instantiated" attachments table but is nonetheless persisted without the authenticity check the question is probing for.

### Likelihood Explanation
I was unable to fully confirm within the available context whether `insert_instantiated_attachment` in `stackslib/src/net/atlas/db.rs` performs an internal recomputation/assertion of `Hash160::from_data(&content) == attachment.hash()` or similar self-consistency check before writing (I could not retrieve its body due to tool-call exhaustion), nor could I confirm the internals of `decode_atlas_get_attachment()` for a hash check against the request. This is a material gap: if `insert_instantiated_attachment` itself enforces `attachment.hash()` self-consistency (i.e., stores under the key derived from the actual content, and pairing against `attachment_instance.content_hash` happens only later at `check_attachment_instances`/`find_attachment` lookup time — which does verify equality against `attachment_instance.content_hash` before invoking `do_if_found`), then no forged pairing (attachment_instance ↔ wrong content) is ever exposed to consumers, even though a self-consistent-but-unsolicited blob gets stored. That would reduce this to low-impact storage bloat rather than an authentication break.

### Recommendation
Add an explicit check in `extend_with_attachments` (or immediately before `insert_instantiated_attachment` in `run()`) asserting `Hash160::from_data(&attachment.content) == request.content_hash` (or equivalently `attachment.hash() == request.content_hash`) before inserting into `self.attachments`/`AtlasDB`; drop and penalize (bump_failed_requests / mark peer faulty) any response that fails this check.

### Proof of Concept

1. Construct an `AttachmentRequest` with a known `content_hash` (e.g., `Hash160::from_data(b"real")`).
2. Craft a `StacksHttpResponse` whose decoded `GetAttachmentResponse.attachment` wraps different bytes, e.g. `Attachment::new(b"forged".to_vec())`, so `Hash160::from_data(b"forged") != content_hash`.
3. Feed this response through `AttachmentsBatchStateContext::extend_with_attachments` and then simulate `AttachmentsDownloader::run`'s `Done` branch.
4. Assert that `atlasdb.insert_instantiated_attachment` is **not** called (or that `find_uninstantiated_attachment`/`find_attachment` for `content_hash` returns `None` afterward) — confirming the hash equality gate is enforced before storage. If the assertion fails (i.e., the forged attachment is found stored under `content_hash` or unconditionally inserted with no gate), the vulnerability is confirmed.
