### Title
Attacker fills victim's `MAX_TOKENS_PER_USER` slot list via dust `deposit(onBehalfOf)` to block collateral top-ups and force liquidation - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The bug class in CVE-2023-49345 is an unprivileged actor pre-creating/controlling a shared, predictable resource so the victim is denied access or shown false state. The on-chain analog lives in `Pool.sol`: per-account `depositTokensOfAccount`/`debtTokensOfAccount` lists are capped at `MAX_TOKENS_PER_USER = 30` (`Pool.sol:79`), and `DepositToken._mint`/`_transfer` unconditionally append the token to the *recipient's* list via `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance goes from 0 to non-zero (`DepositToken.sol:486-488`, `DepositToken.sol:518-520`). `deposit()` accepts an arbitrary `onBehalfOf_` (`DepositToken.sol:211-216`), so anyone can push a dust deposit into a victim's account. Once the combined lists hit 30, `onlyIfAdditionWillNotReachMaxTokens` reverts every `addTo*` call (`Pool.sol:143-148`), which reverts any new `deposit()` mint or first-time `transfer` into the victim — the victim cannot open a new collateral position.

### Finding Description
- `Pool.sol:143-148` — `onlyIfAdditionWillNotReachMaxTokens` reverts with `UserReachedMaxTokens` when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`.
- `DepositToken.sol:211-237` — `deposit(amount_, onBehalfOf_)` pulls `amount_` of underlying from the caller's treasury transfer and mints msdTOKEN to `onBehalfOf_`; there is no opt-in by the beneficiary and no minimum amount.
- `DepositToken.sol:469-489` — `_mint` calls `pool.addToDepositTokensOfAccount(account_)` on first receipt, which enforces the cap.
- `DepositToken.sol:498-526` — `_transfer` does the same for plain `transfer`/`transferFrom` to a fresh recipient, so dust transfers of already-held msdTOKENs work too.
- Removal (`removeFromDepositTokensOfAccount`) only fires when the victim's own balance reaches zero (`DepositToken.sol:460-462`, `523-525`), i.e. the victim must spend gas to withdraw/transfer each dust position.

Attacker path (fully unprivileged, no privileged role):
1. For each registered `DepositToken` in the pool (each backed by a distinct underlying), attacker calls `DepositToken.deposit(dust, victim)` — or first deposits to self, then `transfer(victim, 1 wei)` — until `depositTokensOfAccount(victim).length + debtTokensOfAccount(victim).length == 30`.
2. Victim's next `deposit()` into any collateral they don't already hold reverts in `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`.
3. If the victim's position drifts unhealthy, they cannot add a new collateral type to restore health; `Pool.liquidate` proceeds and the position is seized, including liquidation fees.

### Impact Explanation
Denial of deposits: the victim is blocked from opening positions in any deposit token they don't already hold, which is a liveness break on the deposit path — the exact analog of the CVE's "deny access to the application". Worse, for a victim with existing debt whose health factor deteriorates (price movement or interest accrual via `DebtToken` index), the inability to top up with a new collateral type converts the DoS into forced liquidation: `Pool.liquidate` seizes collateral plus the protocol/liquidator fee split in `DepositToken.seize`. That is direct loss of user funds caused by the grief. Cost to the attacker is only dust amounts of each underlying plus gas; there is no economic penalty, since attacker-paid collateral sits in the victim's account (the "gift" is negligible at dust size).

### Likelihood Explanation
Requires the pool to have enough registered deposit/debt tokens to reach the 30-slot cap (or the victim to already hold some, lowering the attacker's requirement). Each griefed slot costs only a minimal deposit — no minimum deposit amount exists in `deposit()`. The attack is front-runnable/renewable: after the victim clears slots by withdrawing dust (costing them gas per token), the attacker can re-fill them. No modifier stops it: `deposit` is `whenNotPaused`/`nonReentrant`/`onlyIfDepositTokenExists` only, `addToDepositTokensOfAccount` trusts any registered deposit token caller, and SynthContext meta-sender does not change the outcome. Note that if the victim has zero debt, the dust msdTOKENs are fully unlocked and withdrawable, so the pure-grief variant is recoverable with gas cost; the forced-liquidation variant applies when the victim holds debt and health declines before they clear slots.

### Recommendation
- Require beneficiary opt-in for list membership: e.g. only add to `depositTokensOfAccount` when `onBehalfOf_ == _msgSender()` or when the beneficiary has registered/approved the token, or let accounts remove themselves via a `Pool`-level `removeDepositTokenFromMyAccount(token)` escape hatch that burns/forfeits the dust.
- Alternatively, enforce a minimum first-deposit amount per deposit token so filling 30 slots costs meaningful capital, or make the per-account list an unbounded-but-lazy structure (iterate only over tokens with non-trivial balance) so dust can't consume capacity.

### Proof of Concept
Hardhat fork sketch (deployed Base/Optimism pool):

```ts
// Pool + DepositToken on mainnet fork
const pool = await ethers.getContractAt("Pool", POOL_ADDR);
const tokens: DepositToken[] = /* all pool.getDepositTokens() */;

// victim holds debt in msUSD so unlocked-balance math matters later
for (const dt of tokens) {
  if ((await pool.getDepositTokensOfAccount(victim)).length >= 30) break;
  const underlying = await ethers.getContractAt("IERC20", await dt.underlying());
  await underlying.connect(whale).transfer(attacker.address, 10); // dust
  await underlying.connect(attacker).approve(dt.address, 10);
  await dt.connect(attacker).deposit(10, victim.address); // adds token to victim's list
}

expect(await pool.getDepositTokensOfAccount(victim)).length + 
       (await pool.getDebtTokensOfAccount(victim)).length).to.eq(30);

// victim tries to deposit a collateral they don't yet hold
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// victim's health degrades -> liquidator seizes, victim cannot top up
await pool.connect(liquidator).liquidate(synth, victim, repayAmt, depositToken);
```
