### Title
Single-Step, Unverified Owner/Witness/Active Permission Overwrite Can Permanently Lock an Account Out of Its Own Funds - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator`, which executes the `AccountPermissionUpdateContract` (the account-permission/multisig update transaction any account holder can broadcast), overwrites an account's `Owner`, `Witness`, and `Active` permissions in a single atomic step with no confirmation or acceptance step from the new key holders. This mirrors the reported bug class of single-step privileged-role transfers: a mistaken or malicious set of new permission keys/thresholds can be committed irrevocably, permanently freezing the account's ability to authorize any further transaction.

### Finding Description
`execute()` directly calls `AccountCapsule.updatePermissions()` to replace the account's `ownerPermission`, `witnessPermission`, and `activePermission` list as soon as the transaction is validated and applied — there is no two-phase "propose/accept" mechanism, and no requirement that the newly designated key holders co-sign or otherwise prove control of the new keys before the change takes effect: [1](#0-0) 

`validate()` (and the helper `checkPermission()`) only checks structural properties of the new permission — key count, weight positivity/uniqueness, address format validity, and that the sum of weights is not less than the threshold — but never checks that the resulting permission set is actually reachable by any key the caller controls, nor does it require any acknowledgement from the new keys: [2](#0-1) [3](#0-2) 

The actual state mutation is performed in `AccountCapsule.updatePermissions()`, which unconditionally replaces the `ownerPermission` (and witness/active permissions) with the new value supplied in the transaction: [4](#0-3) 

Because the `Owner` permission is the root permission from which all `Active`/`Witness` permissions derive and which is required to authorize further `AccountPermissionUpdateContract` transactions, once it is overwritten with keys the account owner does not actually control (e.g., a mistyped address, a threshold set higher than the reachable weight sum for keys the owner holds, or keys belonging to an unintended/incorrect party), there is no recovery path — the account can never again produce a valid signature for an owner-level operation, including a corrective `AccountPermissionUpdateContract`.

### Impact Explanation
This directly matches the report's exploit scenario ("Alice ... calls the update_admin method with an incorrect address, resulting in the permanent loss of access to the admin role") but applied to any TRON account's core permission model rather than an application-level admin field. Because `Owner`/`Active` permissions gate authorization for asset transfers, resource operations, and further permission updates, an irrecoverable overwrite permanently freezes the account's funds and control — satisfying the "permanent freezing of funds" impact bar. Any account (not just admins) reachable via a normal signed transaction is affected, so the blast radius is any user of the multisig/permission feature.

### Likelihood Explanation
Likelihood is high for accidental self-lockout: any account holder with multisig enabled (`AllowMultiSign`) can trigger this by broadcasting a single `AccountPermissionUpdateContract` transaction with an incorrect address or an unreachable threshold/weight configuration — no attacker collusion is required, and the actuator provides no safety net (no dry-run reachability check, no two-step accept). A malicious insider with temporary access to the owner key could also intentionally lock out other stakeholders in one step.

### Recommendation
Implement a two-step confirmation flow for `AccountPermissionUpdateContract`-style changes to the `Owner` permission: first stage the proposed permission set, then require a transaction signed under the *proposed* new permission (proving reachability/control) before the change is finalized and the old permission is discarded. Short of a full two-step redesign, at minimum add a validation step that simulates whether the caller-supplied keys can practically satisfy the new threshold before committing the overwrite, and/or require an explicit "self-test" signature from at least one new key as a precondition in `AccountPermissionUpdateActuator.validate()`.

### Proof of Concept
1. Enable multisig on account `A` (owner key `K_owner`).
2. `A` broadcasts an `AccountPermissionUpdateContract` (signed with `K_owner`, satisfying the current owner permission) setting the new `Owner` permission to `{ threshold: 2, keys: [ (K_typo, weight 1), (K_owner, weight 1) ] }`, believing `K_typo` is a backup key it controls but is actually a typo'd/unknown address.
3. `AccountPermissionUpdateActuator.validate()` passes: key count > 0, weights > 0, distinct addresses, valid address format, weight sum (2) ≥ threshold (2) — see [5](#0-4) .
4. `execute()` commits the change via `updatePermissions()` — see [4](#0-3) .
5. Account `A` can no longer produce a valid 2-of-2 signature (since it never controlled `K_typo`), so it cannot authorize any further Owner-level transaction, including a corrective permission update — the account's funds and control are permanently frozen.

  private boolean checkPermission(Permission permission) throws ContractValidateException {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (permission.getKeysCount() > dynamicStore.getTotalSignNum()) {
      throw new ContractValidateException("number of keys in permission should not be greater "
          + "than " + dynamicStore.getTotalSignNum());
    }
    if (permission.getKeysCount() == 0) {
      throw new ContractValidateException("key's count should be greater than 0");
    }
    if (permission.getType() == PermissionType.Witness && permission.getKeysCount() != 1) {
      throw new ContractValidateException("Witness permission's key count should be 1");
    }
    if (permission.getThreshold() <= 0) {
      throw new ContractValidateException("permission's threshold should be greater than 0");
    }
    String name = permission.getPermissionName();
    if (!StringUtils.isEmpty(name) && name.length() > 32) {
      throw new ContractValidateException("permission's name is too long");
    }
    //check owner name ?
    if (permission.getParentId() != 0) {
      throw new ContractValidateException("permission's parent should be owner");
    }

    long weightSum = 0;
    List<ByteString> addressList = permission.getKeysList()
        .stream()
        .map(x -> x.getAddress())
        .distinct()
        .collect(toList());
    if (addressList.size() != permission.getKeysList().size()) {
      throw new ContractValidateException(
          "address should be distinct in permission " + permission.getType());
    }
    for (Key key : permission.getKeysList()) {
      if (!DecodeUtil.addressValid(key.getAddress().toByteArray())) {
        throw new ContractValidateException("key is not a validate address");
      }
      if (key.getWeight() <= 0) {
        throw new ContractValidateException("key's weight should be greater than 0");
      }
      try {
        weightSum = addExact(weightSum, key.getWeight());
      } catch (ArithmeticException e) {
        throw new ContractValidateException(e.getMessage());
      }
    }
    if (weightSum < permission.getThreshold()) {
      throw new ContractValidateException(
          "sum of all key's weight should not be less than threshold in permission " + permission
              .getType());
    }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
