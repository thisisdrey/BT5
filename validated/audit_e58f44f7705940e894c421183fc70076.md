### Title
Front-runnable `approve` on `DepositToken` lets a spender pull N+M tokens when the owner reduces allowance - ([contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`DepositToken.approve` (and the identical pattern in `SyntheticToken`) sets `allowance[owner][spender] = amount` directly, with no requirement that the previous allowance be zero. This is the classic ERC20 approve/transferFrom race: if an owner tries to reduce a spender's allowance from N to M by sending a single `approve(M)` transaction, the spender can front-run it with `transferFrom(N)` and then consume the new allowance M, spending N+M total.

### Finding Description
- `approve` calls `_approve(_msgSender(), spender_, amount_)`, which unconditionally overwrites the allowance at `contracts/DepositToken.sol:187-190` and `contracts/DepositToken.sol:432-438`.
- `transferFrom` then lets the spender consume whatever the current allowance is at `contracts/DepositToken.sol:357-376`.
- `increaseAllowance`/`decreaseAllowance` exist (`contracts/DepositToken.sol:195-203`, `255-259`), but nothing forces users to call them; `approve` remains a public, vulnerable entry point.
- Unlike the referenced Surge code, Metronome routes the caller through `SynthContext._msgSender()`/`Operator.execute`, but this does not mitigate the race — an approved spender still sees the pending `approve` transaction in the mempool (or L2 sequencer ordering) and can front-run it with their own `transferFrom`/`execute` call.
- `transferFrom` is `nonReentrant` but the attack is cross-transaction (front-running), not reentrancy, so the guard is irrelevant. `_revertIfLocked` only limits the spender to the victim's *unlocked* balance — for an account with no debt, the entire balance is unlocked (`unlockedBalanceOf` returns `balanceOf` when `_debtInUsd == 0`, lines 383-397).
- The same code shape exists in `contracts/SyntheticToken.sol` (same 6 matches for `approve`/`increaseAllowance`/`decreaseAllowance`), so msTokens are equally affected.

### Impact Explanation
A spender with existing allowance N, upon seeing an owner's `approve(spender, M)` transaction, front-runs it: `transferFrom(owner, attacker, N)` succeeds under the old allowance, then the `approve` lands, granting a fresh M. The spender extracts N+M of the owner's deposit tokens (or synthetic tokens) — up to the victim's full unlocked balance — a direct theft of user funds the owner never authorized.

### Likelihood Explanation
Medium. It requires the victim to lower a non-zero allowance to another non-zero value via `approve` (rather than `decreaseAllowance` or resetting to 0 first), and the spender must monitor the mempool. Deposit tokens are the primary collateral asset, so users commonly approve routers/managers; allowance reductions during routine UX are plausible.

### Recommendation
Follow the report's guidance: deprecate or harden raw `approve`. Common mitigations are (a) revert in `approve` when the existing allowance and new amount are both non-zero (USDT-style), forcing `approve(0)` first, or (b) adopt ERC20Permit-style flows and document that only `increaseAllowance`/`decreaseAllowance` should be used. Apply identically to `DepositToken` and `SyntheticToken`.

### Proof of Concept
Foundry sketch (deployed config; contracts are upgradeable clones created by `Pool`/`PoolRegistry`):

```solidity
// Alice holds msdX and previously approved Bob for N.
// Alice broadcasts approve(Bob, M) to reduce allowance.
// Bob (or a searcher on his behalf) front-runs:
depositToken.transferFrom(alice, bob, N);      // spends old allowance N
// Alice's approve(Bob, M) lands
depositToken.transferFrom(alice, bob, M);      // spends new allowance M
assertEq(depositToken.balanceOf(bob), N + M);  // Bob got N+M, Alice intended M
```

Concrete test outline: fork mainnet, impersonate an msdWBTC/msdWETH holder (or deposit underlying via `DepositToken.deposit`), call `approve(bob, N)`, then in the same test simulate ordering: bob calls `transferFrom(alice, bob, N)`, alice calls `approve(bob, M)`, bob calls `transferFrom(alice, bob, M)`. Both calls succeed because `allowance` was reset rather than decremented, demonstrating the N+M drain. [1](#0-0) [2](#0-1) [3](#0-2)

        address sender_,
        address recipient_,
        uint256 amount_
    ) external override nonReentrant returns (bool) {
        _revertIfLocked(sender_, amount_);

        address _msgSender = _msgSender();
        uint256 _currentAllowance = allowance[sender_][_msgSender];
        if (_currentAllowance != type(uint256).max) {
            if (_currentAllowance < amount_) revert AmountExceedsAllowance();
            unchecked {
                _approve(sender_, _msgSender, _currentAllowance - amount_);
            }
        }

        _transfer(sender_, recipient_, amount_);

        return true;
    }
