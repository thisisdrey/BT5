### Title
Unbounded array allocation from attacker-controlled length field in TVM precompiled-contract ABI decoding helpers can crash the node with `OutOfMemoryError` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Exiv2 advisory describes an integer-overflow/oversized-length bug where a length value taken from untrusted input is used to allocate a huge `std::vector` without being checked against the actual available data, causing an uncaught exception/crash. `PrecompiledContracts.java` contains the same bug-class: helper methods that decode ABI-encoded arrays for precompiled contracts read a 32-byte word as an array length and immediately allocate a Java array of that size, with no bound check against the size of the actual call-data buffer.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` all take an attacker-supplied length word from the precompile's input `data` and allocate arrays sized by that value before any validation against the real amount of data present: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case:
- `len = words[offset].intValueSafe();` — `intValueSafe()` only caps the value at `Integer.MAX_VALUE` when the word doesn't fit in 4 bytes; it performs no check that `len` corresponds to real bytes available in `data`.
- `byte[][] bytesArray = new byte[len][];` is then executed immediately. A single crafted call can set `len` close to `Integer.MAX_VALUE`, causing the JVM to attempt to allocate an array of ~2^31 object references (many GB of heap for the reference array alone, before even filling in the elements).

This mirrors the Exiv2 flaw precisely: a length taken from untrusted, minimally-validated data is used directly to size a large in-memory allocation, and the resulting `OutOfMemoryError` is an unchecked `Error`, not a checked exception, so it is unlikely to be caught by ordinary `catch (Exception e)` handlers used elsewhere in the VM/actuator pipeline.

### Impact Explanation
Any account can trigger this by invoking (via a normal `TriggerSmartContract` transaction, or even a constant/`triggerconstantcontract` API call) a precompiled contract address whose implementation calls one of these helpers, supplying call data where the length word is set to a very large value. The resulting attempt to allocate a huge array can throw `OutOfMemoryError`, which, if not caught along the full call chain up to block/transaction processing in `Manager`, can crash the node process executing the transaction. Because every full node in the network processes the same transaction when applying the block, this could induce a synchronized crash across many/most nodes — a chain halt — rather than affecting a single victim node.

### Likelihood Explanation
Reachable directly from an unprivileged, unauthenticated transaction broadcaster or constant-call API client: the caller only needs to invoke a precompiled contract address with crafted call data (32-byte length word set near `0xFFFFFFFF`/`Integer.MAX_VALUE`). No special permissions, staking, or witness/SR privileges are required. The complexity is low; it only requires a single crafted TVM call.

### Recommendation
Before allocating `new byte[len][]` (or similar) in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against the actual remaining length of `data`/`words` (e.g., reject if `len` would require more bytes than are present, similar to the `verifyLength` checks already used in `RLP.java`). Additionally, cap `len` to a small sane maximum consistent with realistic ABI array sizes for the specific precompiled contract, and ensure any `OutOfMemoryError`/`Throwable` thrown during precompile execution is caught and converted into a normal VM revert rather than propagating up and destabilizing the node.

### Proof of Concept
1. Identify a precompiled contract (reachable via `CALL`/`STATICCALL` from a deployed contract, or directly via `TriggerSmartContract`) whose `execute(byte[] data)` implementation invokes `extractBytes32Array`, `extractBytesArray`, or `extractSigArray` on attacker-controlled `data`.
2. Craft `data` such that the 32-byte word at the expected `offset` decodes (via `DataWord.intValueSafe()`) to a very large value (e.g. `0x7FFFFFFF`).
3. Broadcast a transaction (or issue a `triggerconstantcontract` JSON-RPC/HTTP call) invoking the contract with this crafted call data.
4. The node executing/validating the transaction attempts `new byte[0x7FFFFFFF][]`, which throws `OutOfMemoryError`; observe process instability/crash if this Error is not caught by an enclosing `catch (Throwable ...)` in the actuator/VM execution path.

Note: I was unable to fully trace, within the available tool-call budget, every caller of these three helper methods and confirm whether all call sites are wrapped in a `catch (Throwable ...)` that would fully absorb the `OutOfMemoryError` before it reaches `Manager`'s block-application code. This should be verified by tracing all precompiled-contract implementations that call these helpers and their surrounding exception handling in `Runtime`/`Program`/`TransactionTrace`.
