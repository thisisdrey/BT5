Audit Report

## Title
Griefing via zero-value `stake`/`unstake` permanently advances `last_update_block`, rounding reward-per-token accrual to zero and losing rewards for the accrual period - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards`'s `reward_per_token` computes accrual as `reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked`, and `update_pool_rewards` unconditionally sets `last_update_block = now` regardless of whether the computed increment rounded to zero. Since `stake` and `unstake` are unprivileged, callable every block, and do not enforce `amount > 0`, an attacker can call `stake(pool_id, 0)` every block to keep `rewardable_blocks_elapsed = 1`, maximizing the chance the numerator truncates to zero and permanently erasing that block's reward accrual for all stakers in the pool.

## Finding Description
`reward_per_token` computes `pool_info.reward_per_token_stored.ensure_add(reward_rate_per_block.ensure_mul(rewardable_blocks_elapsed).ensure_mul(PRECISION_SCALING_FACTOR).ensure_div(total_tokens_staked))`, using integer division that truncates toward zero when `reward_rate_per_block * rewardable_blocks_elapsed * 4096 < total_tokens_staked` [1](#0-0) . `PRECISION_SCALING_FACTOR` is fixed at `4096` [2](#0-1) . `update_pool_rewards` then unconditionally advances `last_update_block` to the current block and overwrites `reward_per_token_stored`, irrespective of whether the increment computed was zero [3](#0-2) .

The `stake` extrinsic is callable by any signed account with no `ensure!(amount > 0, ...)` guard; it calls `update_pool_and_staker_rewards` → `reward_per_token` → `update_pool_rewards` on every invocation before adding `amount` (which may be `0`) to storage [4](#0-3) . `unstake` behaves identically and also permits `amount = 0` when the caller acts on their own stake [5](#0-4) . `update_pool_and_staker_rewards` confirms both calls route through the vulnerable reward-per-token computation before any storage mutation [6](#0-5) .

By calling `stake(pool_id, 0)` every block, `rewardable_blocks_elapsed` is forced to `1` on each call, maximizing the likelihood that `reward_rate_per_block * 1 * 4096 < total_tokens_staked` and the increment rounds to `0`, while `last_update_block` is still bumped to the current block — permanently discarding that block's reward accrual for every staker in the pool, since subsequent computations only account for blocks after the (already advanced) `last_update_block`.

## Impact Explanation
This is a public, low-cost griefing vector against a live reward-accounting pallet (`pallet-asset-rewards`) that degrades intended reward payouts to legitimate stakers, matching the "runtime bugs that compromise intended behavior" / underpriced-work-degrading-payouts category. As `total_tokens_staked` grows relative to `reward_rate_per_block`, the window for zero-rounding widens, letting an attacker suppress reward accrual for a pool at minimal transaction-fee cost, with no benefit to the attacker beyond imposing loss on other stakers. Note the underlying reward-asset tokens are not permanently locked (an admin can eventually reclaim unpaid balances via `cleanup_pool`), so the impact is reward-accrual griefing rather than a hard fund lock or theft.

## Likelihood Explanation
No privileged role, governance action, or compromised infrastructure is required — only an ordinary signed account calling the public `stake` (or `unstake`) extrinsic with `amount = 0` every block. This is trivially repeatable on any low-fee chain. Exploitability, however, depends on an admin-chosen pool parameter (`reward_rate_per_block`) being small relative to `total_tokens_staked`; pools with a reward rate sized appropriately for their stake are not exploitable, so real-world likelihood is condition-dependent rather than universal.

## Recommendation
- Reject zero-amount `stake`/`unstake` calls (`ensure!(!amount.is_zero(), ...)`), removing the cheapest griefing trigger.
- Avoid advancing `last_update_block` past the point where the reward-per-token increment would be zero, or track dust/remainder so unrounded reward-time is not silently discarded.
- Consider a higher-precision, always-cumulative reward counter (e.g. `FixedU128`, as used by `pallet-nomination-pools`'s `RewardCounter`) instead of the fixed `PRECISION_SCALING_FACTOR = 4096` integer scaling [7](#0-6) .

## Proof of Concept
1. Admin calls `create_pool` with `reward_rate_per_block = R` and stakers reach `total_tokens_staked = S` such that `R * 4096 < S`.
2. Attacker (any signed account) calls `stake(pool_id, 0)` every subsequent block.
3. Each call triggers `reward_per_token` with `rewardable_blocks_elapsed = 1`; `R * 1 * 4096 / S` truncates to `0` [8](#0-7) .
4. `update_pool_rewards` still advances `last_update_block` to the current block [9](#0-8) , discarding that block's reward permanently for later `harvest_rewards` calls by legitimate stakers.
5. Repeating step 2 indefinitely suppresses reward accrual for the pool as long as `S` stays large relative to `R`, at minimal transaction-fee cost.

		pub fn stake(origin: OriginFor<T>, pool_id: PoolId, amount: T::Balance) -> DispatchResult {

				&FreezeReason::Staked.into(),

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

			Ok(())

		pub fn unstake(
			origin: OriginFor<T>,
			pool_id: PoolId,
			amount: T::Balance,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Check the staker has enough staked tokens.
			ensure!(staker_info.amount >= amount, Error::<T>::NotEnoughTokens);

			// Unfreeze staker assets.
			T::AssetsFreezer::decrease_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_sub_assign(amount)?;
			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_sub_assign(amount)?;

			if staker_info.amount.is_zero() && staker_info.rewards.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			// Emit event.
			Self::deposit_event(Event::Unstaked { caller, staker, pool_id, amount });

			Ok(())
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
