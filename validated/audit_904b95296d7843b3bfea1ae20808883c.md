### Title
Weight double-counting via ECDSA signature malleability in the `ValidateMultiSign` TVM precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract, which any TVM smart contract can invoke to check whether a set of signatures meets an account permission's weight threshold, deduplicates signers incorrectly: it only skips a signature if the *exact same signature bytes* were already processed for an address, not whenever the *same address* has already contributed weight. Because ECDSA signatures are malleable (a signature `(r, s)` and `(r, n-s)` both recover to the same address for the same message hash), a single key holder can submit two different valid signatures over the same hash and have their weight counted twice, potentially satisfying a multi-sig threshold alone.

### Finding Description
`ValidateMultiSign.execute()` iterates over the caller-supplied `signatures` array, recovers the signer address for each, and is supposed to prevent a signer from contributing weight more than once: [1](#0-0) 

The dedup check only calls `continue` (skipping the weight addition) when the *merged* `recoveredAddr + sign` bytes were already seen — i.e. an exact repeat of the same signature:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
``` [2](#0-1) 

If the same address appears again but with a **different** valid signature encoding of the same hash (the malleable `s' = n - s` variant with adjusted recovery id, or any other distinct-but-valid encoding), the inner `matrixContains(executedSignList, sign)` check is false, so the `continue` is skipped and the code falls through to add `weight` again — double-counting the same signer's weight toward `totalWeight`.

By contrast, the equivalent on-chain multi-sig check used for ordinary transactions, `TransactionCapsule.checkWeight`, correctly rejects any second contribution from the same recovered address (post fork `VERSION_4_7_1`, keyed by address rather than raw signature bytes): [3](#0-2) 

This shows the project is aware of, and elsewhere correctly implements, per-address duplicate rejection — but the TVM precompile path was left with the weaker exact-byte-match check.

### Impact Explanation
Any smart contract deployed on TVM that gates a privileged action (fund release, admin operation, ownership change, etc.) on `ValidateMultiSign` returning success relies on the precompile enforcing that each signer contributes weight only once. A single validator/signer who controls one key with non-trivial weight can craft two distinct valid signatures over the same hash (trivial via ECDSA malleability, requiring no additional private key material) and have their weight counted twice. If that doubled weight meets or exceeds the account's `permission.getThreshold()`, the single signer bypasses the intended multi-party quorum, enabling unauthorized execution of whatever action the calling contract gates on this check (e.g., unauthorized transfer/release of custody funds held by a contract-based multisig wallet). This is a fund-theft/unauthorized-operation class impact reachable purely by an unprivileged contract caller supplying calldata to any deployed contract that calls this precompile — no special node or SR privilege required.

### Likelihood Explanation
Exploitation only requires: (1) a contract on-chain that uses the `ValidateMultiSign` precompile (address `0x1000001`) to gate an action, and (2) the attacker controls one signer key in the permission's key set. Producing the malleable counterpart of an ECDSA signature is a simple, well-known, deterministic elliptic-curve computation requiring no brute force. This makes the attack straightforward for any single participant in an on-chain multi-sig scheme built on this precompile — a plausible and commonly-used pattern for TVM DeFi/custody contracts.

### Recommendation
In `ValidateMultiSign.execute()` (and equally in `BatchValidateSign` if the same pattern exists there), deduplicate strictly by `recoveredAddr`, not by the combination of address and raw signature bytes: once an address has contributed weight, any further signature recovering to that same address must be skipped/rejected outright, mirroring the address-keyed dedup already used in `TransactionCapsule.checkWeight`.

### Proof of Concept
1. Deploy/use an account with an `Active` permission containing a key `K` with weight `W >= threshold/2`.
2. Attacker (holder of `K`) computes a valid ECDSA signature `(r, s)` over the required hash, and derives the canonical malleable partner `(r, n-s)` with adjusted recovery id — both recover to the same address `A` for the same `hash`.
3. Attacker calls the `ValidateMultiSign` precompile with `signatures = [(r,s), (r, n-s)]`.
4. First iteration: `executedSignList` is empty, so weight `W` is added; `sign1` and `A` are recorded.
5. Second iteration: `recoveredAddr == A` is found in `executedSignList` (`matrixContains(executedSignList, recoveredAddr)` is true), but `sign2 != sign1` so `matrixContains(executedSignList, sign2)` is false → the `continue` is skipped, and `weight = W` is added again.
6. `totalWeight = 2W`, potentially `>= permission.getThreshold()`, causing the precompile to return success (`DataWord.ONE`) even though only one distinct signer authorized the action. [4](#0-3)
