### Title
Out-of-bounds read via unchecked `Contract.type` value in permission/operations bitmap check - ([File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java])

### Summary
`TransactionCapsule.checkPermissionOperations` (and its duplicate `WalletUtil.checkPermissionOperations` / `TransactionUtil.checkPermissionOperations`) indexes a fixed 32-byte `operations` bitmap using `contract.getTypeValue()` without validating that the value falls in the expected `[0,255]` range. Because `getTypeValue()` returns the *raw* wire-level int32 of the protobuf enum field (not the resolved, range-checked `ContractType` enum), an attacker can submit a transaction whose `Contract.type` field holds an arbitrary out-of-range or negative integer, causing `ByteString.byteAt()` to throw an unhandled `IndexOutOfBoundsException` during signature/permission verification — before any contract-type sanity check is performed.

### Finding Description
The vulnerable computation is: [1](#0-0) 

```java
public static boolean checkPermissionOperations(Permission permission, Contract contract)
    throws PermissionException {
  ByteString operations = permission.getOperations();
  if (operations.size() != 32) {
    throw new PermissionException("operations size must be 32");
  }
  int contractType = contract.getTypeValue();
  boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
  return b;
}
```

`contract.getTypeValue()` is a protobuf accessor that returns the *raw* int32 stored on the wire for the `ContractType type = 1;` enum field, regardless of whether it corresponds to a known enum constant — unlike `getType()`, which would collapse unrecognized values to `UNRECOGNIZED`. Nothing in this code path bounds-checks `contractType` before using it to index a 32-byte array (valid indices `0..31`). Any `contractType` value ≥ 256 or negative causes `operations.byteAt(...)` to throw `IndexOutOfBoundsException`.

This routine is reached from `TransactionCapsule.checkPermission` → `validateSignature` → `validatePubSignature`, which is invoked while verifying an incoming transaction's signature/permission before contract-type-specific actuator validation occurs: [2](#0-1) [3](#0-2) 

The catch block around `validateSignature(...)` in `validatePubSignature` only catches `SignatureException`, `PermissionException`, and `SignatureFormatException` — it does **not** catch `IndexOutOfBoundsException`, so the exception propagates as an uncaught `RuntimeException`: [4](#0-3) 

The same unchecked pattern also exists independently in the query-path duplicate used by `Wallet.getTransactionApprovedList` (reachable via the HTTP/gRPC API without even broadcasting a transaction): [5](#0-4) [6](#0-5) 

Note in `Wallet.getTransactionApprovedList` the call is wrapped in a broad `catch (Exception ex)` clause, so that path degrades gracefully; but the `validatePubSignature`/`checkPermission` path used by normal transaction validation (broadcast and block application) is not.

The precondition — reaching the branch `permissionId != 0` — only requires the target account to have previously set up a multisig **Active** permission via `AccountPermissionUpdateContract` (a normal, unprivileged, self-service operation once `AllowMultiSign` is enabled), and then have any transaction reference that `Permission_id` with a crafted `Contract.type`.

### Impact Explanation
An uncaught `IndexOutOfBoundsException`/`ArrayIndexOutOfBoundsException` thrown deep inside transaction signature/permission validation is a crash primitive: it propagates past the intended exception-handling contract (`ValidateSignatureException`), producing an unexpected `RuntimeException` in the transaction processing pipeline (`Manager.validateTapos`/`Manager.pushTransaction`/block application), and can crash or destabilize a node processing the transaction (broadcast path or, if included in a block, replay/sync path on all full nodes). This matches "node crash or halt" impact class for a High-severity out-of-bounds analog, directly mirroring the amdgpu bug class (missing bounds/type validation leading to out-of-bounds array access).

### Likelihood Explanation
Likelihood is high: the attacker only needs (1) to enable multisig on their own account and set up an Active permission with a non-zero threshold (a standard, unprivileged operation), and (2) craft a raw `Transaction.Contract` protobuf message with an out-of-range `type` field value and a matching `Permission_id`, then broadcast it via the standard `broadcastTransaction` HTTP/gRPC API or p2p transaction relay. No special node/witness/committee privilege is required — this is directly reachable by any anonymous API client / transaction broadcaster.

### Recommendation
Bound-check `contractType` before indexing: reject or treat as `false`/invalid any `contractType` value outside `[0, 255]` in `TransactionCapsule.checkPermissionOperations`, `WalletUtil.checkPermissionOperations`, and `TransactionUtil.checkPermissionOperations`. Additionally, widen the catch clause in `TransactionCapsule.validatePubSignature` to catch generic `RuntimeException` (or explicitly `IndexOutOfBoundsException`) and convert it into a `ValidateSignatureException`/`PermissionException`, ensuring malformed input cannot escape the transaction validation error-handling contract.

### Proof of Concept
1. Attacker account `A` calls `AccountPermissionUpdateContract` to add an `Active` permission with `Permission_id = 2`, a valid operations bitmap, and a low threshold — a normal self-service transaction.
2. Attacker crafts a raw `Transaction` whose single `Contract` has:
   - `Permission_id = 2` (referencing the active permission set up in step 1)
   - `type` field set (at the protobuf wire level) to an out-of-range value, e.g. `10000` (or a negative int32), which protobuf happily deserializes and exposes via `contract.getTypeValue() == 10000`.
3. Attacker signs the transaction with a key present in permission `2`, and broadcasts it via `Wallet.broadcastTransaction` (HTTP `/wallet/broadcasttransaction` or gRPC).
4. During validation, `TransactionCapsule.validateSignature` → `checkPermission` → `checkPermissionOperations` computes `operations.byteAt(10000 / 8)` = `operations.byteAt(1250)`, which throws `IndexOutOfBoundsException` since `operations` is only 32 bytes.
5. This exception is not caught by `validatePubSignature`'s catch clause (`SignatureException | PermissionException | SignatureFormatException`), propagating as an unhandled `RuntimeException` through the node's transaction validation pipeline.
