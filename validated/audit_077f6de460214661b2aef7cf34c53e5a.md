### Title
Non-Atomic Custom Hooks Directory Swap Allows Transient Silent Bypass of pre-receive/update/post-receive Enforcement - ([File: internal/gitaly/repoutil/custom_hooks.go])

### Summary
`SetCustomHooks`/`RestoreCustomHooks` replace a repository's `custom_hooks` directory using two sequential, non-atomic `os.Rename` calls: first renaming the existing directory away, then renaming the new directory into place. Between these two renames there is a window in which the `custom_hooks` directory does not exist on disk at all. Concurrent hook invocations that read the same path directly from disk during this window will observe neither the old nor the new hook set, exactly mirroring the reported cohort-replacement flaw where "delete old, then add new" without any check for concurrent activity produces an inconsistent transient state that other in-flight operations can observe.

### Finding Description
`repoutil.SetCustomHooks` performs the swap as:
1. `os.Rename(repoHooksPath, prevHooksPath)` — removes the live `custom_hooks` directory.
2. `os.Rename(tempHooksPath, repoHooksPath)` — installs the new one. [2](#0-1) 

The `hooksLock` acquired via `safe.NewLockingDirectory(repoPath, CustomHooksDir)` only serializes concurrent *writers* of custom hooks (other `SetCustomHooks`/`RestoreCustomHooks` calls) — it is a lockfile convention that only other calls to this same function respect. [3](#0-2) 

Custom-hook execution, however, does not consult this lock at all. `GitLabHookManager.newCustomHooksExecutor` (invoked from `PreReceiveHook`, `UpdateHook`, `PostReceiveHook` on every push) independently resolves the repository path and globs `custom_hooks/<hookName>` and `custom_hooks/<hookName>.d/*` directly from disk at the moment the RPC executes: [1](#0-0) [4](#0-3) 

Because the reader path takes no lock and the writer path's rename sequence is not atomic (two separate syscalls with a gap), a push whose `pre-receive`/`update`/`post-receive` hook execution happens to land inside that gap will find `custom_hooks` missing, `findHooks` will return no files, and the custom hook step silently no-ops instead of enforcing the administrator-installed policy — analogous to the reported issue where an unguarded delete-then-add sequence produces a state visible to concurrent operations that violates the intended invariant (here: "a hook set must always be enforced," there: "a member cannot be simultaneously absent from both cohorts").

### Impact Explanation
Custom hooks are explicitly documented as the mechanism administrators use to enforce repository-specific policy on `pre-receive`/`update`/`post-receive` (e.g., commit signing, branch protection beyond GitLab's built-in checks). A push racing an in-flight `SetCustomHooks`/`RestoreCustomHooks` RPC on the same repository can transiently bypass that enforcement entirely, with no error surfaced to the operator — this is a hook-bypass condition reachable by an ordinary user's push as long as it coincides with an administrative hook update.

### Likelihood Explanation
`SetCustomHooks`/`RestoreCustomHooks` are relatively infrequent administrative operations, but pushes to an active repository are frequent, so the race window (bounded by two `os.Rename` syscalls plus directory sync when `storage.NeedsSync` is enabled) can realistically be hit under sustained push traffic during a hooks update. No special privilege is needed by the pushing user; only ordinary write access to trigger a hook execution during the window is required.

### Recommendation
Make the hooks-directory swap atomic with respect to readers, e.g. by using a single `os.Rename` from a fully-prepared new directory directly over the old one (relying on `rename(2)`'s atomicity for directory replacement on the same filesystem) instead of a remove-then-install two-step, or by having hook execution resolve the custom hooks directory through the same lock/transaction snapshot used by `SetCustomHooks` so readers never observe an intermediate, hookless state.

### Proof of Concept
1. Repository `R` has a custom `pre-receive` hook installed that rejects pushes containing a forbidden string.
2. Client A calls `RepositoryService.SetCustomHooks` on `R` with a new hooks tarball; the RPC reaches the point after `os.Rename(repoHooksPath, prevHooksPath)` but before `os.Rename(tempHooksPath, repoHooksPath)` completes (as seen in [5](#0-4) ).
3. Concurrently, Client B pushes a commit containing the forbidden string. Gitaly's `pre-receive` hook invokes `newCustomHooksExecutor`, which globs `custom_hooks/pre-receive` and `custom_hooks/pre-receive.d/*` in `R` and finds neither directory present ( [6](#0-5) ), so the custom hook loop executes zero commands and returns success.
4. The push is accepted despite violating the custom hook policy, even though the policy is present both before and after the swap.
