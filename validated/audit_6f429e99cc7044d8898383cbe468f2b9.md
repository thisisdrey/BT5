### Title
Non-constant-time `authorization` header comparison enables remote timing attack against the node's RPC auth token - (File: `stackslib/src/net/api/postblock_v3.rs`, `stackslib/src/net/api/postblock_proposal.rs`, `stackslib/src/net/api/blockreplay.rs`, `stackslib/src/net/api/blocksimulate.rs`, `stackslib/src/net/api/fastcallreadonly.rs`, `stackslib/src/net/api/txsimulate.rs`)

### Summary
Several sensitive RPC endpoints authenticate the caller by comparing the request's `authorization` header directly against the node operator's configured secret (`connection_options.auth_token`) using Rust's standard `!=`/`==` `String` comparison. This is a non-constant-time, early-exit comparison, which is the exact bug class described in the Richie advisory (CWE-208): an attacker who can send many requests and measure response latency can recover the secret token byte-by-byte and forge authentication, bypassing the auth gate for state-changing/administrative RPC endpoints.

### Finding Description
Each of the following handlers implements `try_parse_request` with the identical pattern:

```rust
let Some(password) = &self.auth else { ... };
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
``` [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

`String`'s `PartialEq`/`!=` performs a byte-wise comparison that returns as soon as a mismatch is found (and additionally short-circuits on length). This means the time taken to reject an incorrect `authorization` header value leaks information about how many leading bytes of the guess matched the real secret. The project's own OpenAPI documentation confirms the intended semantics are "must exactly equal" the configured secret [6](#0-5) , i.e., this is deliberately a shared-secret bearer-token check, structurally analogous to an HMAC/signature equality check — the same bug class flagged in the Richie advisory (`==` used for secret verification instead of a constant-time comparison).

The `auth_token` is wired into these handlers centrally in `register_rpc_methods`, confirming this is the node's single configured RPC secret reused across all of them: [7](#0-6)  and [8](#0-7) .

### Impact Explanation
An attacker with network access to the node's RPC port (no privileges, no key material) can mount a remote timing side-channel attack to incrementally recover the `auth_token`. Once recovered, the attacker gains unauthorized write access to security-sensitive endpoints gated by this token, including:
- `/v3/block_proposal` (`postblock_proposal.rs`) — miner block-proposal validation endpoint.
- `/v3/blocks` broadcast mode and `/v3/blocks/replay/*` (`postblock_v3.rs`, `blockreplay.rs`).
- `/v3/contracts/fast-call-read/*` and `/v3/transactions/simulate` (`fastcallreadonly.rs`, `txsimulate.rs`) — potentially heavy read-only execution endpoints.

This maps to "unauthenticated/unauthorized write to state" and auth-bypass impact categories, since successful token recovery converts an unauthenticated remote attacker into an authenticated one for these gated endpoints.

### Likelihood Explanation
Exploitation requires a large number of timing samples (classic remote timing-attack characteristics: network jitter reduces but does not eliminate signal, and statistical averaging over many requests recovers the byte-wise comparison signal), consistent with the CVSS vector in the original advisory (`AC:H`, `S:U`). No privileges or prior secret knowledge are required, and the endpoints are reachable by any network peer that can open an HTTP connection to the RPC surface — the same precondition applies here.

### Recommendation
Replace the direct `String`/`&str` `!=`/`==` comparisons in `postblock_v3.rs`, `postblock_proposal.rs`, `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, and `txsimulate.rs` with a constant-time comparison (e.g., `subtle::ConstantTimeEq`) applied over fixed-length byte buffers (padding/hashing to a fixed length first to also avoid leaking length via early-return-on-length-mismatch behavior).

### Proof of Concept
1. Configure a node with `connection_options.auth_token` set to a secret string.
2. From a remote host, repeatedly POST to `/v3/block_proposal` (or `/v3/transactions/simulate`, etc.) with candidate `authorization` header values that differ from the real secret at increasing byte offsets.
3. Measure response latency for the 401 rejection path at `stackslib/src/net/api/postblock_proposal.rs:1142-1144` for each candidate; because `!=` compares byte-by-byte, guesses matching more leading bytes take measurably longer to fail before returning 401.
4. Iterating this process byte-by-byte over many timing samples per byte position recovers the full `auth_token`, after which the attacker submits requests with the correct `authorization` header and bypasses the auth gate.
