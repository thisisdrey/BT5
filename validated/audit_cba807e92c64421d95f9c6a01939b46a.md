This confirms the exploit path: `harvest_rewards` allows partial unstake via `amount` parameter [1](#0-0) , so `total_tokens_staked` can remain positive after any post-expiry `unstake` call, and `update_pool_rewards` sets `last_update_block` to the raw current block with no cap at `expiry_block` [2](#0-1) . The subsequent `reward_per_token` call skips the underflow only when `total_tokens_staked.is_zero()` [3](#0-2) ; otherwise it computes `last_block_reward_applicable(expiry_block).ensure_sub(last_update_block)`, which underflows once `last_update_block > expiry_block` [4](#0-3) .

Audit Report

## Title
Unbounded `last_update_block` stamping after pool expiry causes permanent arithmetic-underflow lock of staked funds and rewards - (File: substrate/frame/asset-rewards/src/lib.rs)

## Summary
`Pallet::update_pool_rewards` unconditionally sets `PoolInfo::last_update_block` to the current block number with no cap at `expiry_block`, while `reward_per_token` computes elapsed blocks as `last_block_reward_applicable(expiry_block).ensure_sub(last_update_block)`. Once any post-expiry interaction (permitted for any account via `unstake`/`harvest_rewards`) pushes `last_update_block` past `expiry_block` while `total_tokens_staked` remains non-zero, every subsequent pool operation underflows and reverts, permanently freezing staked assets and rewards.

## Finding Description
`update_pool_rewards` at `substrate/frame/asset-rewards/src/lib.rs` L775-784 always writes `new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number()`, with no clamp against `pool_info.expiry_block`. This function is invoked before every pool mutation (`stake`, `unstake`, `harvest_rewards`, `set_pool_reward_rate_per_block`, `set_pool_expiry_block`) via `update_pool_and_staker_rewards`, and directly in reward-rate/expiry setters.

`reward_per_token` (L787-810) short-circuits only when `total_tokens_staked.is_zero()`; otherwise it computes `Self::last_block_reward_applicable(pool_info.expiry_block).ensure_sub(pool_info.last_update_block)`. `last_block_reward_applicable` (L826-833) caps its return value at `expiry_block` once expired, but `update_pool_rewards` applies no equivalent cap when persisting `last_update_block`.

`unstake` (L514-560) permits partial unstaking (`amount` parameter) by any account once `now > pool_info.expiry_block` (`ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin)`, L526), and likewise for `harvest_rewards` (L580). So the first post-expiry `unstake`/`harvest_rewards` call by any account sets `last_update_block` to a value > `expiry_block`, while `total_tokens_staked` can remain > 0 if not fully unstaked. Any subsequent call to `reward_per_token` for that pool then computes `expiry_block.ensure_sub(last_update_block)` with `last_update_block > expiry_block`, which underflows on the unsigned `BlockNumberFor<T>` type and returns `Err`, aborting the extrinsic.

Because `update_pool_rewards` is the only function that writes `last_update_block`, and every pool-mutating call routes through `reward_per_token` first, there is no path to reset the corrupted state once it occurs.

## Impact Explanation
This is a permanent, unprivileged lock of user funds: remaining stakers can never call `unstake` to reclaim frozen staked-asset balances (frozen via `AssetsFreezer`), nor `harvest_rewards` to claim reward-asset balances, since both route through the now-permanently-failing `reward_per_token`. The pool admin cannot recover it either, since `set_pool_reward_rate_per_block` and `set_pool_expiry_block` also call `reward_per_token` first. `cleanup_pool` requires `PoolStakers` to be empty, which becomes unreachable. This matches the "permanent user-fund lock" impact category.

## Likelihood Explanation
No privileged role or malicious behavior is required. A pool naturally reaches `expiry_block` while stakers remain (the intended common case, since `unstake`/`harvest_rewards` are explicitly designed to be callable by anyone post-expiry). Any single ordinary post-expiry `unstake` (partial) or `harvest_rewards` call from any account is sufficient to poison `last_update_block` for all remaining stakers in that pool.

## Recommendation
In `update_pool_rewards`, cap the new `last_update_block` at `expiry_block`, i.e., use `Self::last_block_reward_applicable(pool_info.expiry_block)` instead of the raw `T::BlockNumberProvider::current_block_number()`, so `last_update_block` never exceeds the value used in subsequent `ensure_sub` calls in `reward_per_token`.

## Proof of Concept
1. Create a pool with `expiry_block = E`; stake `amount > 0` before `E` so `total_tokens_staked > 0`.
2. Advance to `now1 > E`. Call `unstake` with a partial amount (or `harvest_rewards`) as any account — succeeds, `last_update_block` becomes `now1 > E`, and `total_tokens_staked` remains `> 0`.
3. Advance to `now2 > now1`. Call `unstake`/`harvest_rewards`/`stake`/`set_pool_reward_rate_per_block`/`set_pool_expiry_block` on the same pool.
4. `reward_per_token` computes `last_block_reward_applicable(E) = E`, then `E.ensure_sub(now1)` where `now1 > E`, causing an underflow error that reverts the call.
5. All further pool operations fail identically forever; remaining staked tokens and unharvested rewards are permanently locked, and `cleanup_pool` can never succeed since `PoolStakers` can never be emptied.
