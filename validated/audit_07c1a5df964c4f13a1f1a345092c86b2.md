### Title
Unbounded growth of per-account `DelegatedResourceAccountIndex` enables resource-exhaustion DoS via unlimited resource-delegation targets - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
Neither `FreezeBalanceActuator` (legacy delegate path) nor `DelegateResourceActuator`/`DelegateResourceProcessor` (v2 delegate path) enforce any limit on how many distinct receiver/sender addresses an account may delegate bandwidth/energy to. Every new distinct counterparty adds one more entry to that account's `DelegatedResourceAccountIndex` (either a growing repeated-field blob in the legacy path, or a growing set of prefixed key/value rows in the v2 path). The full, unbounded index is then read and materialized in memory whenever `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` is queried by any HTTP/gRPC client, without pagination — closely analogous to Mattermost's `getSessions` bug, where an unbounded table can be flooded and then exhausted by reading it back in full.

### Finding Description
Legacy path — `FreezeBalanceActuator.delegateResource()` performs an unbounded read-modify-write on a single key per account: [1](#0-0) 
Each call fetches the entire existing `DelegatedResourceAccountIndexCapsule`, appends the new counterparty via `addToAccount`/`addFromAccount` (which rebuilds the whole protobuf list), and writes the whole blob back: [2](#0-1) 
There is no cap on list size anywhere in `FreezeBalanceActuator.validate()` — only a 1 TRX minimum frozen-balance check exists: [3](#0-2) 

V2 path — `DelegateResourceActuator`/`DelegateResourceProcessor` similarly only checks a 1 TRX minimum and available frozen balance, with no cap on the number of distinct receivers: [4](#0-3) [5](#0-4) 
Each v2 delegate call adds one more prefixed row via `delegate()`: [6](#0-5) 

Read side — `getWithPrefix()` performs a full, unbounded `prefixQuery`, collects every entry into an `ArrayList`, sorts it, and returns it in one response, with no limit/pagination: [7](#0-6) 
This is exposed directly to unauthenticated callers via `Wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2`: [8](#0-7) 
and served over HTTP: [9](#0-8) 
and gRPC: [10](#0-9) 

### Impact Explanation
An attacker can:
1. Fund many distinct addresses with the minimal 1 TRX and repeatedly delegate bandwidth/energy from/to a target account (or their own account), each time to a new distinct address, adding one entry per transaction with no upper bound.
2. In the legacy path, this causes O(n) per-transaction cost during block application (since the whole list is rebuilt/rewritten each time), degrading block processing performance across the network as more nodes apply these transactions (CWE-407-style algorithmic complexity), and grows one on-disk value without bound.
3. In either path, once the index for an account has grown large, any anonymous caller invoking `/wallet/getdelegatedresourceaccountindex(v2)` or the gRPC/JSON-RPC equivalent forces the node to materialize, sort and serialize the full unbounded list in memory for every such request — enabling repeated cheap requests to exhaust node memory/CPU and crash or hang the Full/Solidity/PBFT API service (CWE-400/CWE-770), mirroring the Mattermost `getSessions` exhaustion pattern.

### Likelihood Explanation
Reachable by any account holder with a modest amount of TRX (only 1 TRX minimum per distinct delegation target, refundable after unfreeze/expiry), requiring no special privilege, SR/witness status, or contract deployment. The read path is reachable by any anonymous HTTP/gRPC client with no authentication and no rate limiting beyond the generic `RateLimiterServlet`. Because it is a straightforward transaction-plus-query workflow with no per-account cap enforced in `validate()`, exploitation is mechanically simple and cheap to automate at scale.

### Recommendation
- Enforce a maximum number of distinct delegation counterparties per account (analogous to Mattermost's session limit) in `FreezeBalanceActuator.validate()`, `DelegateResourceActuator.validate()`, and `DelegateResourceProcessor.validate()`, rejecting further delegations once the cap is reached.
- Add pagination/limits to `DelegatedResourceAccountIndexStore.getWithPrefix()` and to the `getDelegatedResourceAccountIndex(V2)` API so a single query cannot force unbounded in-memory materialization.
- Consider converting the legacy full-list read-modify-write append to an incremental (prefixed key) structure across the board to avoid O(n) growth cost per transaction.

### Proof of Concept
1. Create N funded accounts, each freezing/holding at least 1 TRX of bandwidth/energy.
2. From account A, repeatedly submit `DelegateResourceContract` (or legacy `FreezeBalanceContract` with `receiverAddress` set) transactions, each delegating 1 TRX to a new, distinct receiver address, for N in the tens/hundreds of thousands.
3. Observe `DelegatedResourceAccountIndexStore` entries for account A (and each receiver) growing without bound; in the legacy path observe increasing per-transaction latency as N grows (O(n) list rebuild/rewrite).
4. Issue repeated `GET /wallet/getdelegatedresourceaccountindex?value=<A>` (or the gRPC `GetDelegatedResourceAccountIndex` call) requests; observe growing memory allocation, latency, and eventual resource exhaustion/crash of the serving node as the full unbounded list is repeatedly loaded, sorted, and serialized per request.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

  public DelegatedResourceAccountIndex getDelegatedResourceAccountIndex(ByteString address) {
    if (address == null || address.size() != DecodeUtil.ADDRESS_SIZE / 2) {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
    DelegatedResourceAccountIndexCapsule accountIndexCapsule =
        chainBaseManager.getDelegatedResourceAccountIndexStore().getIndex(address.toByteArray());
    if (accountIndexCapsule != null) {
      return accountIndexCapsule.getInstance();
    } else {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
  }
