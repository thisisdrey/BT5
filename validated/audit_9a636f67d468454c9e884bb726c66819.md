### Title
Dust `DepositToken` transfers fill a victim's per-account token list to `MAX_TOKENS_PER_USER`, permanently blocking new deposits, borrows and receipts — (File: contracts/DepositToken.sol)

### Summary
Metronome tracks every `DepositToken`/`DebtToken` an account touches in `MappedEnumerableSet` lists capped at `MAX_TOKENS_PER_USER = 30`. Because `DepositToken.transfer`/`transferFrom` have no minimum amount and `deposit()` has no minimum deposit, an unprivileged attacker can deposit 1 wei of each listed collateral and transfer 1 wei to a victim, filling the victim's `depositTokensOfAccount` list. Once at the cap, `pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens`, which propagates through `DepositToken._transfer`/`_mint`, reverting any `deposit()` of a new collateral to the victim, any `DebtToken.issue()` for a new synthetic (shared 30-slot limit), any `transfer`/`seize` *to* the victim of a token they don't hold, and any smart-farming deposit-on-behalf.

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's pool list whenever the recipient's prior balance was 0 and `amount_ > 0` (no minimum):
  `contracts/DepositToken.sol:517-520` — `if (_recipientBalanceBefore == 0 && amount_ > 0) { pool.addToDepositTokensOfAccount(recipient_); }`
- `transfer`/`transferFrom` are public ERC20 entry points gated only by `_revertIfLocked(sender)` (solvency of the *sender*), with no check on `amount_` or the recipient's list size: `contracts/DepositToken.sol:348-376`.
- `deposit()` only rejects `amount_ == 0`, so the attacker can mint dust balances cheaply: `contracts/DepositToken.sol:211-215`.
- `Pool.addToDepositTokensOfAccount` enforces `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` → revert: `contracts/Pool.sol:143-148, 216-220`; `MAX_TOKENS_PER_USER = 30` at `contracts/Pool.sol:79`.
- The two lists share one budget, so forced deposit-token dust also blocks `DebtToken.issue`→`addToDebtTokensOfAccount` (`contracts/Pool.sol:204-208`), preventing the victim from opening any new borrow position or accepting any new collateral type.

Attack path (public entry points only):
1. For each `DepositToken` registered in the target pool, attacker calls `deposit(1, attacker)` (or any dust amount covering the fee) then `transfer(victim, 1)`.
2. Repeat until `depositTokensOfAccount.length(victim) + debtTokensOfAccount.length(victim) == 30`.
3. Thereafter: `otherToken.deposit(x, victim)` reverts inside `_mint`→`addToDepositTokensOfAccount`; `debtToken.issue()` for a synthetic the victim doesn't yet hold reverts; `msdX.transfer(victim, n)` reverts; `Pool.liquidate` reverts when a liquidation would leave the *liquidator* fine but the code path adds a token to an account already at cap (seize calls `_transfer`, and `_withdraw`'s fee `_transfer` to the feeCollector can also revert if the collector's list is filled — the same attack is applicable to the `feeCollector` address, since it is a plain account whose list is also capped at 30).

Cost: 30 × (dust deposit + transfer) ≈ negligible; the deposit fee is paid in-kind so dust amounts still work when `depositFee == 0`, and even with a fee the attacker only needs `amount_ > 0` received.

### Impact Explanation
The invariant that breaks is liveness of the account-token registry. Concrete effects:
- **Permanent blocking of new collateral/debt slots until the victim actively cleans up**: the victim must discover the dust balances and transfer each one out (balance → 0 triggers `removeFromDepositTokensOfAccount`). Until then they cannot deposit a new collateral type or mint a new synthetic. For a victim that is a contract (e.g., SmartFarmingManager-driven positions, multisigs, the `feeCollector`, or any integrator that holds deposits for users), cleanup may be impossible — no `sweep` of its own `DepositToken` balances exists except governor `sweep` on `TokenHolder` — making the freeze permanent for such accounts.
- **Temporary freezing of funds / denial of accounting**: deposits addressed to the victim (`deposit(amount, onBehalfOf = victim)` from third parties, liquidations paying seized tokens to the victim's address, gateway deposits) revert. `NativeTokenGateway.deposit` and `SmartFarmingManager.leverage` (which call `deposit`/`_mint` on behalf of the user) revert, blocking rescue of an unhealthy position via a new collateral type.

### Likelihood Explanation
- Fully unprivileged: `deposit`, `transfer`, `transferFrom` are public and unprivileged; `SynthContext` sender resolution does not restrict them.
- No modifier stops it: `onlyIfAdditionWillNotReachMaxTokens` is exactly the mechanism that turns dust into a revert; `whenNotPaused`, `nonReentrant`, `onlyIfDepositTokenExists` are satisfied. `deposit` requires only `amount_ != 0`.
- The only mitigation is user action (transfer dust out), which is not possible for contracts that can't call arbitrary functions on `DepositToken`, and the attacker can re-fill slots after cleanup at dust cost.
- Caveat: a victim holding an existing slot can still deposit/withdraw that same token, so this is a liveness/griefing issue rather than direct theft — it fits "temporary freezing of funds" and, for contract-type victims, permanent denial of new deposits.

### Recommendation
- Enforce a minimum economically meaningful amount on `DepositToken._transfer`/`deposit` (e.g., `amount_ >= minTransfer` or a USD floor via `masterOracle.quoteTokenToUsd`), or
- Only call `addToDepositTokensOfAccount` when the received amount exceeds a dust threshold, or
- Make the account list opt-in (register tokens on `deposit`/`issue`, not on inbound `transfer`), so unsolicited dust cannot consume list slots.

### Proof of Concept
Hardhat (against deployed `Pool`/`DepositToken` proxies on a mainnet/Base fork):

```ts
// victim: fresh EOA, attacker: fresh EOA
const pool = await ethers.getContractAt('Pool', POOL_PROXY);
const tokens = await pool.getDepositTokens(); // registered DepositTokens

// 1) attacker seeds dust balances and transfers 1 wei of each token to victim
for (let i = 0; i < 30; i++) {
  const msd = await ethers.getContractAt('DepositToken', tokens[i % tokens.length]);
  const underlying = await ethers.getContractAt('IERC20', await msd.underlying());
  await underlying.connect(attacker).approve(msd.address, 1);
  await msd.connect(attacker).deposit(1, attacker.address);   // mint dust
  await msd.connect(attacker).transfer(victim.address, 1);     // occupies a slot
}
// For pools with fewer than 30 listed collateral tokens, combine with
// debtTokens the victim already holds, or multiple pools are per-pool.

expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30);

// 2) victim cannot deposit a new collateral type
const newMsd = await ethers.getContractAt('DepositToken', tokens[0]);
// remove one dust first to isolate: deposit a token NOT in victim's list
const other = await ethers.getContractAt('DepositToken', OTHER_TOKEN);
await expect(other.deposit(parseEther('1'), victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3) victim cannot open a new borrow (shared 30-slot budget)
const debtToken = await ethers.getContractAt('DebtToken', DEBT_TOKEN);
await expect(debtToken.connect(victim).issue(parseEther('10'), victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 4) inbound transfer/seize of a new token reverts
await expect(newMsd.connect(attacker).transfer(victim.address, 1))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

The revert originates in `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` (`contracts/Pool.sol:143-148`) reached via `DepositToken._transfer`/`_mint` (`contracts/DepositToken.sol:486-488, 517-520`) with only dust amounts — the direct analog of the reported missing-minimum-amount DoS.
