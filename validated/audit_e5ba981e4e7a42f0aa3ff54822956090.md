### Title
Permanent per-channel stall in Snowbridge V1 Inbound Queue when downstream XCM send fails — no bypass, funds/messages permanently blocked - (File: `bridges/snowbridge/pallets/inbound-queue/src/lib.rs`)

### Summary
The `submit` extrinsic in `snowbridge-pallet-inbound-queue` (V1) enforces strictly sequential per-channel nonces and performs nonce validation, fee handling, and the final `send_xcm` dispatch inside a single atomic call. If `send_xcm` fails for any reason on the expected next nonce, the entire extrinsic — including the nonce increment — is rolled back by FRAME's transactional dispatch semantics. Since nonces must be strictly sequential and there is no alternate delivery path or skip/backfill mechanism, that specific message (and every subsequent message on the same channel) can never be delivered until the underlying XCM routing condition resolves itself. This mirrors the reported Across Protocol bug class: a single failing "messenger" makes the canonical path unusable with no bypass, causing a stall.

storage map keyed per `ChannelId`, incremented one at a time.

Later in the same extrinsic, after fee burning, the message is dispatched via XCM: [3](#0-2) 

`send_xcm` wraps the configured `T::XcmSender` (canonical HRMP/XCMP delivery) and maps any `XcmpSendError` (`NotApplicable`, `Unroutable`, `Transport`, `DestinationUnsupported`, `ExceedsMaxMessageSize`, `MissingArgument`, `Fees`) into a hard `Error::<T>::Send`: [4](#0-3) [5](#0-4) 

Because `submit` returns `DispatchResult` and is a normal (non-message-queue) extrinsic, any `Err` return — including the `Send` error from `send_xcm` — causes FRAME to roll back **all** storage mutations performed earlier in the call, including the `Nonce<T>` increment done via `try_mutate` at line 257-267. This is unlike `pallet-message-queue`, which processes each queued message in its own transactional scope and explicitly distinguishes permanent failures (dropped, logged) from transient ones (retried later) without blocking unrelated messages: [6](#0-5) 

The inbound-queue V1 pallet has no such isolation. Because the channel's nonce is strictly sequential and only advances on full extrinsic success, a message whose XCM send permanently fails (e.g. destination's HRMP channel is suspended/congested, `ExceedsMaxMessageSize` due to a payload/config mismatch, or `Unroutable`) can never be superseded. The relayer can resubmit the same event repeatedly, but every resubmission fails identically, and because the nonce never advances, no later message for that channel can ever be accepted either — `InvalidNonce` will reject any higher-numbered event until the stuck one succeeds. There is no `oftMessengers`-style alternate route, no admin-settable bypass, no partial-processing fallback, and no way to skip/backfill the stuck nonce from within this pallet.

### Impact Explanation
This directly matches the "message queues... must only advance after decode, dispatch, execution, and settlement succeed atomically" pivot, but in the wrong direction: because the *entire* pipeline (nonce, fee burn, XCM dispatch) is bundled into one non-isolated atomic unit with strict ordering, a single non-malicious, non-privileged failure condition (transient or persistent XCMP congestion on the destination side) permanently locks the channel. Any teleported assets/messages destined for that parachain through this channel become permanently stuck until governance intervenes (e.g., by fixing routing config or replacing the channel), which satisfies "permanent user-fund or bridge-state lock" and "public underpriced work that... stalls bridge processing" from the impact gate. No malicious peer, relayer, or validator is required — an ordinary XCMP/HRMP congestion event (which can arise from unrelated traffic on the destination parachain, not admin action) is sufficient to trigger the stall.

### Likelihood Explanation
Likelihood is moderate: XCMP/HRMP channel congestion, suspension, or message-size mismatches are realistic, previously-documented operational conditions in Polkadot/Kusama parachains, and any relayer can trigger `submit` freely (permissionless, signed-origin entrypoint, no special privilege required). The strict, un-bypassable sequential nonce check means the very first such failure for a channel is enough to freeze the channel indefinitely — there is no probabilistic recovery, only external/manual intervention.

### Recommendation
Decouple nonce commitment from `send_xcm` delivery success, or route inbound message forwarding through `pallet-message-queue` (as the V2 pallets already do) so that a single message's delivery failure does not block subsequent, independent messages. Alternatively, add an explicit governance/backfill call (analogous to Across's proposed `Arbitrum_SendTokensAdapter` mitigation) that allows skipping or replaying a specific stuck nonce without requiring every subsequent nonce to wait, and emit a permanently-overweight/failed-style event (as `pallet-message-queue` does for `Overweight`/`BadFormat`) so operators are alerted without silently losing funds or indefinitely blocking the channel.

### Proof of Concept
Conceptual reproduction using the existing pallet test harness (`bridges/snowbridge/pallets/inbound-queue/src/test.rs`):
1. Configure a mock `XcmSender` that returns `XcmpSendError::Transport` (or `Unroutable`) for a specific destination `para_id`, simulating a congested/suspended HRMP channel.
2. Call `InboundQueue::submit` with a valid, correctly-proven event for nonce `N+1` on that channel — the call fails with `Error::<T>::Send(SendError::Transport)`, and `Nonce<T>::get(channel_id)` remains at `N` (confirms rollback).
3. Resubmit the same event: it fails identically forever, because the underlying `XcmSender` failure condition never changes as a function of this pallet's own state.
4. Submit a *different*, otherwise-valid event with nonce `N+2` for the same channel: it is rejected with `Error::<T>::InvalidNonce`, proving that the channel is now permanently stalled and no funds/messages can be delivered through it until the routing failure is externally resolved.
