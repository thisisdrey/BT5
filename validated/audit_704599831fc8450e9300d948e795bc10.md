### Title
Wrong-length JSON response from `mt_batch_transfer_call` forces full refund credit while real tokens already left custody - (File: contracts/defuse/src/contract/tokens/nep245/withdraw.rs)

### Summary
`mt_resolve_withdraw` treats any deserialized `Vec<U128>` whose length differs from `amounts.len()` as a total failure (`used = vec![U128(0); amounts.len()]`), refunding the full withdrawn amount back to `sender_id`. A malicious NEP-245 `token` contract can genuinely execute `mt_batch_transfer_call` (moving real custody to `receiver_id`) while intentionally returning a wrong-length success array, causing `mt_resolve_withdraw` to credit `sender_id`'s ledger balance back in full even though the tokens are gone.

### Finding Description
The broken binding: `amount_i debited from sender_id in self.withdraw()` should equal `used_i delivered to receiver_id + refund_i credited back to sender_id`. In `mt_resolve_withdraw` [1](#0-0) , the result of the cross-contract `mt_batch_transfer_call` is parsed via `promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len())`. That helper only uses `amounts.len()` to bound the *maximum byte size* it reads from the promise result [2](#0-1)  — it does not enforce that the deserialized vector actually has that length. If the returned JSON array is shorter than `amounts.len()` (trivially fits under the byte budget), the `Ok(Ok(used)) if used.len() == amounts.len()` guard fails and falls through to `Ok(_) => vec![U128(0); amounts.len()]`, meaning the resolver assumes *zero* tokens were used/kept, regardless of what actually happened on-chain.

`self.withdraw(&owner_id, ...)` already synchronously debits `sender_id`'s internal balance for each `TokenId = Nep245TokenId(token, token_id)` before the promise chain runs [3](#0-2) . `do_mt_withdraw` then calls `mt_batch_transfer_call` on the attacker-supplied `token` contract [4](#0-3) . Since `token` is fully attacker-controlled (attacker may deploy and control their own MT contract), it can perform the real transfer of custody to `receiver_id` and still return a JSON array of the wrong length. `mt_resolve_withdraw` then executes `self.deposit(sender_id, ...)` with `refund = amount - used = amount - 0 = amount` for every token, crediting `sender_id`'s ledger with the entire withdrawn amount [5](#0-4) .

No existing guard prevents this: the `require!(token_ids.len() == amounts.len() && !amounts.is_empty(), ...)` check only validates the *input* arrays, not the callback's returned array [6](#0-5) , and there is no re-check that `used.len()` truly matches after the fallback branch is taken.

### Impact Explanation
`sender_id`'s internal Verifier ledger balance for `TokenId = Nep245TokenId(token, token_id)` is restored to its pre-withdrawal amount even though the corresponding real custody at the external `token` contract has already been transferred to `receiver_id`. This is exactly the "refund or resolver credit that does not match what failed to settle" Critical category: the sum of debits no longer equals delivered assets plus correct refunds. The attacker can repeat this for any amount and any number of token ids in the batch, on a token contract of their own choosing/design, effectively minting an unbacked internal balance for that `TokenId` inside the Verifier. That fraudulently-restored balance can subsequently be used in further intents (transfers, trades via `execute_intents`) to extract genuine value from counterparties who trust the Verifier's internal accounting as being fully collateralized.

### Likelihood Explanation
The attacker only needs to: (1) deploy their own NEP-245 contract implementing `mt_batch_transfer_call` to return a short/mismatched JSON array while still performing the transfer, (2) deposit some balance of a `TokenId` backed by that contract into the Verifier (any amount, since they control minting/registration in their own contract), and (3) call `mt_withdraw` with a `msg` (forcing `is_call = true`) targeting an account they control as `receiver_id`. This uses only unprivileged capabilities explicitly allowed to the attacker (deploying/controlling their own MT contract and receiver, calling `mt_withdraw` on their own balance) and requires no relayer key, DAO role, or victim key. It is fully repeatable per token/account/batch.

### Recommendation
In `mt_resolve_withdraw`, do not conflate "malformed/mismatched-length response" with "all funds successfully refunded." When the parsed `Vec<U128>` length does not match `amounts.len()`, either: (a) treat it as an unrecoverable ambiguous state and do not credit any refund (fail closed toward the Verifier, not toward the sender), or (b) require the promise result to fail loudly (e.g. panic/abort resolving without refunding) so that funds are not credited without proof of a matching-length response, consistent with how the `Err(_) => amounts.clone()` branch already treats unreadable promise results as full success (no refund) rather than assuming failure. At minimum, the wrong-length case should never result in a refund equal to the full `amount` when the call could plausibly have transferred all tokens.

### Proof of Concept
`cargo test` (near-workspaces sandbox) plan:
1. Deploy a malicious NEP-245 contract `evil_mt` whose `mt_batch_transfer_call` performs a real internal transfer of the requested `token_ids`/`amounts` to `receiver_id`, but returns a JSON array `used` with `used.len() == amounts.len() - 1` (or empty) instead of the correct per-token used amounts.
2. Deploy the Defuse Verifier contract; have attacker account `sender_id` deposit a batch of `evil_mt` tokens into the Verifier (crediting `sender_id`'s ledger for `Nep245TokenId(evil_mt, token_id_i)` with `amount_i` for `i = 1..N`).
3. Attacker calls `mt_withdraw(token = evil_mt, receiver_id = attacker_receiver, token_ids, amounts, msg = Some("x"))`.
4. Assert, before the call: `verifier.mt_balance_of(sender_id, token_id_i) == amount_i` for all `i`, and `evil_mt.mt_balance_of(receiver_id, token_id_i) == 0`.
5. After the promise chain resolves, assert both:
   - `evil_mt.mt_balance_of(receiver_id, token_id_i) == amount_i` for all `i` (real tokens delivered), and
   - `verifier.mt_balance_of(sender_id, token_id_i) == amount_i` for all `i` (full refund credited despite delivery) — i.e. `sender_id`'s Verifier-tracked balance was never actually decremented net of the withdrawal, while `receiver_id` independently gained the same amount, proving `debited != delivered + correct_refund`.

pub fn promise_result_checked_json_with_len<T: MaxJsonLength<Args = (usize, ())>>(
    result_idx: u64,
    length: usize,
) -> PromiseJsonResult<T> {
    let max_len = T::max_json_length_root((length, ()));
    let value = env::promise_result_checked(result_idx, max_len)?;
    Ok(serde_json::from_slice::<T>(&value))
}
