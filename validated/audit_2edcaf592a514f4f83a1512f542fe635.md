Audit Report

## Title
`claim_bounty` and `claim_child_bounty` permanently delete bounty records even when `Currency::transfer` payouts fail, permanently locking funds - ([File: substrate/frame/bounties/src/lib.rs], [File: substrate/frame/child-bounties/src/lib.rs])

## Summary
Both `claim_bounty` [1](#0-0)  and `claim_child_bounty` [2](#0-1)  call `T::Currency::transfer(..., AllowDeath)` to pay the curator fee and beneficiary payout, but only guard the result with `debug_assert!`, which is a no-op in release builds. The code then unconditionally clears the bounty storage (`*maybe_bounty = None`) and emits a success event regardless of whether the transfer actually succeeded.

## Finding Description
In `claim_bounty`, `payout` and `final_fee` are derived purely from `balance.saturating_sub(fee)` and `bounty.fee.saturating_sub(children_fee)` with no floor ensuring the amounts clear the Existential Deposit: [3](#0-2)  The transfer results are checked only via `debug_assert!(res.is_ok())`, which is compiled out in `--release` builds used for production runtimes. Execution then proceeds to unconditionally clear the bounty: `*maybe_bounty = None`, remove `BountyDescriptions`, and emit `Event::BountyClaimed` [4](#0-3)  — with no verification that the transfer moved funds.

The identical pattern exists in `claim_child_bounty`: `curator_fee` and `payout` are computed from `child_bounty.fee.min(balance)` and `balance.saturating_sub(curator_fee)`, transfers are made and checked only with `debug_assert!`, and the child bounty state is unconditionally deleted afterward [5](#0-4) .

`Currency::transfer` with `AllowDeath` still enforces the Existential Deposit on the destination account — if the destination does not exist and the transferred amount is below ED, the call returns an `Err` instead of moving funds. Neither `claim_bounty` nor `claim_child_bounty` verifies the destination account pre-exists or that the computed amount exceeds ED before finalizing. Once `*maybe_bounty`/`*maybe_child_bounty` is set to `None`, the `BountyStatus::PendingPayout` state required to re-invoke the claim logic is gone, so there is no permissionless path to retry the payout; the bounty sub-account retains the stranded balance with no ordinary extrinsic path back to the beneficiary/curator.

## Impact Explanation
This breaks the "settle exactly once to the rightful beneficiary and amount" invariant: `BountyClaimed`/`Claimed` events are emitted and bounty records permanently removed even when the beneficiary or curator received zero funds. This matches the "permanent user-fund lock" impact category, reachable via the permissionless `claim_bounty`/`claim_child_bounty` extrinsics (any signed origin can call `claim_bounty`) with no privileged actor, leaked key, or malicious validator/collator involved.

## Likelihood Explanation
The triggering condition — a fresh beneficiary/curator account whose computed payout/fee share falls below the runtime's ED — is an ordinary, non-adversarial occurrence rather than requiring sophisticated attacker coordination; a treasury council merely needs to configure a bounty value/fee split resulting in a small final payout to a not-yet-existing account. The `debug_assert!` guard provides protection only in debug builds and is silently absent in production (`--release`) builds, making this reproducible via a straightforward Rust integration test with a mocked `Currency` implementation or a low-ED test runtime.

## Recommendation
Replace `debug_assert!(res.is_ok())` with proper error propagation (`?` or `ensure!`) for both the fee and payout transfers in `claim_bounty` and `claim_child_bounty`, so a failing transfer aborts the extrinsic and leaves `BountyStatus::PendingPayout` (and the bounty storage entry) intact for retry. Alternatively, explicitly handle the ED-shortfall case (e.g., verify destination account existence or require amounts to clear ED, or use `keep_alive`-aware logic) before finalizing and removing bounty state.

## Proof of Concept
1. Configure a bounty (via `propose_bounty`/`approve_bounty`) such that after subtracting the curator `fee`, the resulting `payout` is smaller than the runtime's `ExistentialDeposit`.
2. Assign a beneficiary `AccountId` that has never existed on-chain (zero balance, no storage entry).
3. Curator calls `award_bounty`; after the payout delay elapses, any signed account calls `claim_bounty`.
4. In `claim_bounty`, `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns an `Err` (e.g. `ExistentialDeposit`/`BelowMinimum`) because `payout` is below ED and the destination account doesn't exist — but in a release build `debug_assert!(res.is_ok())` is compiled out.
5. Execution proceeds to `*maybe_bounty = None`, `BountyDescriptions::remove`, and emits `Event::BountyClaimed { payout, beneficiary, .. }` despite the beneficiary receiving nothing, with the `payout` amount permanently stranded in the bounty sub-account and no further extrinsic path to reclaim it for the beneficiary.
6. The same steps apply analogously to `claim_child_bounty` using a low curator fee / payout split for a freshly generated curator or beneficiary account.

		#[pallet::call_index(6)]
		#[pallet::weight(<T as Config<I>>::WeightInfo::claim_bounty())]
		pub fn claim_bounty(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResult {
			ensure_signed(origin)?; // anyone can trigger claim

			Bounties::<T, I>::try_mutate_exists(bounty_id, |maybe_bounty| -> DispatchResult {
				let bounty = maybe_bounty.take().ok_or(Error::<T, I>::InvalidIndex)?;
				if let BountyStatus::PendingPayout { curator, beneficiary, unlock_at } =
					bounty.status
				{
					ensure!(Self::treasury_block_number() >= unlock_at, Error::<T, I>::Premature);
					let bounty_account = Self::bounty_account_id(bounty_id);
					let balance = T::Currency::free_balance(&bounty_account);
					let fee = bounty.fee.min(balance); // just to be safe
					let payout = balance.saturating_sub(fee);
					let err_amount = T::Currency::unreserve(&curator, bounty.curator_deposit);
					debug_assert!(err_amount.is_zero());

					// Get total child bounties curator fees, and subtract it from the parent
					// curator fee (the fee in present referenced bounty, `self`).
					let children_fee = T::ChildBountyManager::children_curator_fees(bounty_id);
					debug_assert!(children_fee <= fee);

					let final_fee = fee.saturating_sub(children_fee);
					let res =
						T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
					debug_assert!(res.is_ok());
					let res =
						T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
					debug_assert!(res.is_ok());

					*maybe_bounty = None;

					BountyDescriptions::<T, I>::remove(bounty_id);
					T::ChildBountyManager::bounty_removed(bounty_id);

					Self::deposit_event(Event::<T, I>::BountyClaimed {
						index: bounty_id,
						payout,
						beneficiary,
					});
					Ok(())
				} else {
					Err(Error::<T, I>::UnexpectedStatus.into())
				}
			})?;
			Ok(())
		}

		#[pallet::call_index(5)]
		#[pallet::weight(<T as Config>::WeightInfo::claim_child_bounty())]
		pub fn claim_child_bounty(
			origin: OriginFor<T>,
			#[pallet::compact] parent_bounty_id: BountyIndex,
			#[pallet::compact] child_bounty_id: BountyIndex,
		) -> DispatchResult {
			ensure_signed(origin)?;

			// Ensure child-bounty is in expected state.
			ChildBounties::<T>::try_mutate_exists(
				parent_bounty_id,
				child_bounty_id,
				|maybe_child_bounty| -> DispatchResult {
					let child_bounty =
						maybe_child_bounty.as_mut().ok_or(BountiesError::<T>::InvalidIndex)?;

					if let ChildBountyStatus::PendingPayout {
						ref curator,
						ref beneficiary,
						ref unlock_at,
					} = child_bounty.status
					{
						// Ensure block number is elapsed for processing the
						// claim.
						ensure!(
							Self::treasury_block_number() >= *unlock_at,
							BountiesError::<T>::Premature,
						);

						// Make curator fee payment.
						let child_bounty_account =
							Self::child_bounty_account_id(parent_bounty_id, child_bounty_id);
						let balance = T::Currency::free_balance(&child_bounty_account);
						let curator_fee = child_bounty.fee.min(balance);
						let payout = balance.saturating_sub(curator_fee);

						// Unreserve the curator deposit. Should not fail
						// because the deposit is always reserved when curator is
						// assigned.
						let _ = T::Currency::unreserve(curator, child_bounty.curator_deposit);

						// Make payout to child-bounty curator.
						// Should not fail because curator fee is always less than bounty value.
						let fee_transfer_result = T::Currency::transfer(
							&child_bounty_account,
							curator,
							curator_fee,
							AllowDeath,
						);
						debug_assert!(fee_transfer_result.is_ok());

						// Make payout to beneficiary.
						// Should not fail.
						let payout_transfer_result = T::Currency::transfer(
							&child_bounty_account,
							beneficiary,
							payout,
							AllowDeath,
						);
						debug_assert!(payout_transfer_result.is_ok());

						// Trigger the Claimed event.
						Self::deposit_event(Event::<T>::Claimed {
							index: parent_bounty_id,
							child_index: child_bounty_id,
							payout,
							beneficiary: beneficiary.clone(),
						});

						// Update the active child-bounty tracking count.
						ParentChildBounties::<T>::mutate(parent_bounty_id, |count| {
							count.saturating_dec()
						});

						// Remove the child-bounty description.
						ChildBountyDescriptionsV1::<T>::remove(parent_bounty_id, child_bounty_id);

						// Remove the child-bounty instance from the state.
						*maybe_child_bounty = None;

						Ok(())
					} else {
						Err(BountiesError::<T>::UnexpectedStatus.into())
					}
				},
			)
		}
