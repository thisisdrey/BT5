### Title
Truncating double-precision brokerage calculation in `MortgageService.payReward` causes systematic reward misallocation on every block/transaction fee payout - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.payReward()` splits each block reward and transaction-fee reward between a witness's brokerage share and the shared voter reward pool using floating-point multiplication followed by a truncating cast to `long`. This computation is executed on every single block reward payout and on every transaction that pays a fee, exactly analogous to the reported Solidity issue where `feesEarned` is computed via imprecise division on every partial fill instead of once at settlement, causing a systematic rounding bias that compounds over a very large number of operations.

### Finding Description
`payReward` is the sole entry point that splits a reward `value` into a witness brokerage cut and a remainder credited to the cycle's shared voter reward pool: [1](#0-0) 

```java
private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
}
```

`brokerageAmount` is computed as `(double) brokerage / 100 * value` and then truncated toward zero via `(long)` cast. Because this is a `double` calculation (not even an integer floor-division with compensating final settlement, as in the referenced BuyOrderIssuer pattern), the truncation systematically rounds `brokerageAmount` down whenever the exact product is not an integer. The undercounted fraction is *not* lost/burned — it is added into `value`, which flows into the shared voter-reward pool via `delegationStore.addReward(cycle, witnessAddress, value)`.

This function is called from two call sites that are both reachable extremely frequently as part of normal, unprivileged chain activity: [2](#0-1) 

`payBlockReward` runs once per produced block, and `payTransactionFeeReward` runs for every transaction that pays a fee — i.e., triggered directly by any unprivileged transaction broadcaster submitting a fee-paying transaction. `Manager.java` calls both of these during block application:


Unlike the Solidity report's own comparison case (`BuyOrderIssuer`, which cancels out per-fill rounding error by re-adding `remainingPercentageFees + feesEarned` at order close), `payReward` performs the brokerage split once per event with no compensating final reconciliation step across the witness's/voter's lifetime totals — every single block reward and every single transaction fee reward independently accumulates a rounding bias.

### Impact Explanation
Because `payReward` executes on essentially every block and every fee-paying transaction network-wide, the truncation bias compounds continuously and indefinitely. Over the life of the chain, this results in a persistent, protocol-level misallocation of funds between witness brokerage income and the shared voter reward pool — voters systematically receive a bit more than they are entitled to, and witnesses systematically receive a bit less than their configured brokerage percentage implies. This is an unbacked/incorrect balance accounting issue at scale (funds are conserved in aggregate — `value = value - brokerageAmount`, so nothing is created or destroyed — but the recipient split diverges from the protocol-specified brokerage percentage for every SR on every payout, forever). Given the extremely high call frequency (per-block, per-transaction), the aggregate drift over the chain's lifetime is significant even though each individual truncation is tiny.

### Likelihood Explanation
This code path executes deterministically and unconditionally on every block reward and every transaction-fee reward distribution; there's no additional precondition, so the miscalculation happens on effectively 100% of reward payouts. Any brokerage percentage/value combination where `brokerage * value` is not exactly divisible by 100 triggers the truncation, which given `long` values in TRX (sun) units is the overwhelming majority of cases.

### Recommendation
Replace the double-precision brokerage computation with exact integer arithmetic (e.g., `Math.multiplyExact(value, brokerage) / 100` using `long`/`BigInteger`, with an explicit rounding policy), and consider tracking any residual fractional sun in an accumulator per witness/cycle that is reconciled at withdrawal time (similar to how `BuyOrderIssuer` re-adds `remainingPercentageFees + feesEarned` at order close) so that the sum of all payouts exactly matches the intended brokerage split over time, rather than allowing the bias to silently transfer value from brokerage to the voter pool.

### Proof of Concept
Given `brokerage = 33` (33%) and `value = 100` per payout:
- Exact expected brokerage = `100 * 33 / 100 = 33`.
- `brokerageRate = 33.0/100 = 0.33` (already imprecise in binary floating point).
- `brokerageAmount = (long)(0.33 * 100) = (long)(32.99999999999999...) = 32` (or similarly biased for other value/brokerage combinations due to `double` rounding).
- The witness receives `32` instead of `33`; the voter pool receives `68` instead of `67`.
- Repeat over millions of blocks/transactions per witness (payReward is invoked from `payBlockReward`/`payTransactionFeeReward`, called in `Manager.java` during ordinary block application triggered by any transaction broadcaster's fee-paying transactions) — the 1-sun-per-call bias accumulates into a persistent, non-trivial value transfer from witness brokerage income to voter rewards network-wide.
