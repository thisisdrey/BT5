### Title
Precompile delegate-call authorization is opt-in per-implementer, not enforced by the `pallet-revive` precompile framework - (File: `substrate/frame/revive/src/precompiles.rs`, `substrate/frame/revive/src/exec.rs`)

### Summary
`pallet-revive`'s precompile dispatch mirrors the Loihi `assimilators` bug class: a generic lookup (`AllPrecompiles<T>::get`) resolves an address to executable logic and then unconditionally delegates execution to it, without any framework-level check on *how* that logic is being invoked. Rejecting an unsafe invocation mode (a `DELEGATECALL` into the precompile) is left entirely to each individual precompile implementation to remember to add itself, exactly like the original report where "no checks for prior instantiation" let a delegatecall land on an unguarded target.

### Finding Description
When building a call frame, `Stack::new_frame` resolves the callee/delegated-callee address through the shared precompile table: [1](#0-0) 

For a delegate call, if `AllPrecompiles::get(delegated_call.callee)` returns `Some(precompile)`, the framework builds an `ExecutableOrPrecompile::Precompile` and runs it in the *caller's* storage/address/value context — this is standard delegatecall semantics, but it means the precompile's `call()` function executes with `env.caller()` observed from the delegating contract, i.e. it operates on behalf of/against the delegating contract's own state.

The generic `Precompiles<T>` trait implementation (`get`) only matches addresses to code; it performs no distinction between a direct call and a delegate call: [2](#0-1) 

Protection against unsafe delegatecall into a precompile is implemented as an **opt-in convention**: each precompile author must manually call `env.is_delegate_call()` and revert with `PrecompileDelegateDenied` inside their own `call()` body. Some precompiles do this correctly, e.g. `pallet-vesting`'s precompile: [3](#0-2) 

and `pallet-asset-conversion`'s precompile: [4](#0-3) 

There is no shared/derived guard in the `Precompile` trait or in `Precompiles::get`/`Stack::new_frame` that enforces this uniformly for *every* implementer (including out-of-tree precompiles supplied via `Config::Precompiles`, as documented in the pre-compile framework PR). This is analogous to the assimilator bug: the registry lookup (`AllPrecompiles::get`) is trusted implicitly, and the only thing standing between safe and unsafe execution is an ad-hoc check that a specific callee happens to implement — exactly like the assimilator interface's "expected return size" being the only guard against a zero-address delegatecall in the original report.

### Impact Explanation
If any precompile registered through `Config::Precompiles` (or a future built-in precompile) omits the `is_delegate_call()` guard, an attacker-controlled contract can `DELEGATECALL` into that precompile's address. Because delegatecall preserves the caller's storage and address context, the precompile's mutating logic (asset transfers, vesting claims, pool operations, XCM sends, etc., depending on the pallet it wraps) executes as if it were native code of the delegating contract — potentially moving funds, minting/burning balances, or invoking privileged pallet calls under the delegating contract's identity/state rather than the precompile's own. This is unauthorized execution / origin-widening exactly in the spirit of the "Public wrappers ... must not widen origin, bypass filters" pivot, and can lead to theft/misdirection of value if the omitted precompile deals with balances (assets, asset-conversion, vesting all do).

### Likelihood Explanation
The check is missing by default and only present because individual authors added it; it is a structural/pattern gap rather than a per-precompile logic bug. Any newly added precompile (in-tree or from a downstream runtime configuring `Config::Precompiles`) that forgets this one-line guard reintroduces the vulnerability, and there is no compile-time or trait-level mechanism forcing it. I was not able to fully confirm within the available search budget whether every code path of every currently shipped precompile (e.g. all sub-modules of `pallet-assets`' precompile: `permit`, `foreign_assets`, `migration`) applies the guard consistently on all mutating entry points; this remains unverified and should be checked directly in the repository.

### Recommendation
Move the delegatecall authorization decision out of individual precompile bodies and into the shared framework: e.g. have `Precompile` carry a `const DENY_DELEGATE_CALL: bool` (defaulting to `true`) that `Stack::new_frame`/`Precompiles::get` enforces centrally before invoking `call()`, so that a precompile must explicitly opt *in* to allowing delegatecall rather than opt *out* of denying it. Alternatively, add a build-time or benchmarking-time lint that fails compilation for any `Precompile` impl whose `call()` does not reference `is_delegate_call()`.

### Proof of Concept
1. Deploy an attacker contract `Caller` with balance and storage of interest.
2. Have `Caller` issue `DELEGATECALL` to the fixed address of a precompile that lacks the `is_delegate_call()` guard (audit each shipped/downstream precompile for this).
3. The precompile's mutating call (e.g. transfer, claim, mint) executes using `Caller`'s account/storage context as observed via `env.caller()` / underlying pallet calls, allowing the attacker to trigger privileged pallet operations under `Caller`'s identity that were only intended to be reachable via direct call.
4. Compare against `polkadot/xcm/pallet-xcm/precompiles/src/tests.rs::delegatecall_is_rejected`, which demonstrates the expected-safe behavior only for the XCM precompile because that specific implementation added the guard — proving the guard is not systemic. [5](#0-4)

/// The delegatecall guard rejects all calls via delegatecall.
#[test]
fn delegatecall_is_rejected() {
	let balances = vec![(ALICE, 1_000_000_000_000_000u128)];
	new_test_ext_with_balances(balances).execute_with(|| {
		let xcm_precompile_addr = H160::from(
			hex::const_decode_to_array(b"00000000000000000000000000000000000A0000").unwrap(),
		);

		let (init_code, _) = pallet_revive_fixtures::compile_module_with_type(
			"Caller",
			pallet_revive_fixtures::FixtureType::Solc,
		)
		.expect("Caller fixture must be compiled");
		let caller_addr = pallet_revive::Pallet::<Test>::bare_instantiate(
			RuntimeOrigin::signed(ALICE),
			0u32.into(),
			TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::MAX,
				deposit_limit: u128::MAX,
			},
			Code::Upload(init_code),
			vec![],
			None,
			&ExecConfig::new_substrate_tx(),
		)
		.result
		.expect("Caller deployment must succeed")
		.addr;

		let calldata = ICaller::delegateCall {
			callee: alloy::primitives::Address::from(xcm_precompile_addr.0),
			data: IXcm::weighMessageCall { message: Default::default() }.abi_encode().into(),
			gas: u64::MAX,
		}
		.abi_encode();

		let result = pallet_revive::Pallet::<Test>::bare_call(
			RuntimeOrigin::signed(ALICE),
			caller_addr,
			U256::zero(),
			TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::MAX,
				deposit_limit: u128::MAX,
			},
			calldata,
			&ExecConfig::new_substrate_tx(),
		)
		.result
		.expect("outer call must succeed");

		let ret = ICaller::delegateCall::abi_decode_returns(&result.data)
			.expect("return must decode as (bool, bytes)");
		assert!(!ret.success, "DELEGATECALL to XCM precompile must be rejected");
		// PrecompileDelegateDenied is an Error::Error (trap), not an Error::Revert, so the
		// inner call produces no output data. A Solidity-level revert would include
		// ABI-encoded reason bytes.
		assert!(
			ret.output.is_empty(),
			"expected empty output from PrecompileDelegateDenied trap, got {} bytes",
			ret.output.len(),
		);
	});
}
