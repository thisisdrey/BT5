### Title
Unchecked legacy arithmetic in `ExchangeCapsule.transaction()` allows exchange pool token balances to underflow to negative, corrupting on-chain AMM state - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()`, which backs `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`, uses two different arithmetic paths selected by the `AllowHardenExchangeCalculation` proposal flag. The "hardened" path validates that resulting balances cannot go negative, but that validation is only reachable when the flag is enabled by committee proposal. In the default (legacy) path, the pool balances are updated with plain `+`/`-` and no post-condition check, so a computed `buyTokenQuant` (derived from floating-point power calculations in `ExchangeProcessor`) that is even slightly too large can drive a token pool balance negative and it will be silently persisted, exactly analogous to the unchecked subtraction in `isoUSDLoanAndInterest` from the referenced report.

### Finding Description
`ExchangeCapsule.transaction()` computes `buyTokenQuant` via `Processor.exchange()` and then updates pool balances: [1](#0-0) 

When `hardenedCalc` is `false` (the legacy/default path), the new balances are computed with raw `long` arithmetic (`secondTokenBalance - buyTokenQuant` / `firstTokenBalance - buyTokenQuant`) with **no** overflow check and **no** check that the result is non‑negative — the `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0))` guard only runs when `hardenedCalc == true`: [2](#0-1) 

`buyTokenQuant` is produced by `ExchangeProcessor.exchange()`, which relies on double-precision `Math.pow` computations (`exchangeToSupply`/`exchangeFromSupply`), introducing rounding that can, at extreme ratios of balance/quant, return a `buyTokenQuant` that exceeds the actual `buyTokenBalance`: [3](#0-2) 

The `AllowHardenExchangeCalculation` proposal gate defaults to off and must be turned on via committee proposal, meaning any node that has not had the proposal activated runs the unchecked legacy path by default: [4](#0-3) 

Any unprivileged order placer can reach this via `ExchangeTransactionActuator.execute()`/`validate()`, which calls `exchangeCapsule.transaction(...)` with `allowHarden()` as the gate and then persists the (possibly negative) balances back to `ExchangeStore`/`ExchangeV2Store`: [5](#0-4) 

The negative-balance guard test files confirm the hardened path is what enforces the `>= 0` invariant, implying the legacy path lacks it by design: [6](#0-5) 

### Impact Explanation
If a token pool balance in an `ExchangeCapsule` is driven negative, all subsequent `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` calls against that exchange operate on corrupted state. This can permanently break the exchange's internal accounting (a form of unbacked/negative balance analogous to the referenced `isoUSDLoanAndInterest` underflow causing failure to liquidate), potentially permanently freezing further legitimate trading/withdrawal on that exchange or enabling further arithmetic exploitation (e.g., additional trades computing distorted `anotherTokenQuant` off a corrupted negative base), which can facilitate theft of tokens held in the pool.

### Likelihood Explanation
Exploitability requires the default (non-hardened) legacy path to be active, which is the default state prior to committee activation of `AllowHardenExchangeCalculation`, and requires an attacker to find/construct extreme sell/buy quantities or balance ratios where the double-precision `Math.pow`-based `ExchangeProcessor` calculation returns a `buyTokenQuant` exceeding the buy-side pool balance. This is reachable purely through unprivileged, ordinary `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions (no special privileges needed), but requires precise numerical conditions to trigger the underflow, making likelihood dependent on finding such an edge case (exact reproduction was not verified with a concrete number set in this investigation).

### Recommendation
Enforce the non-negative balance and overflow invariant checks (currently only in the `hardenedCalc == true` branch) unconditionally in `ExchangeCapsule.transaction()`, regardless of the `AllowHardenExchangeCalculation` proposal state, or make the hardened calculation path the only path (remove the legacy unchecked branch). At minimum, add the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` check outside the `hardenedCalc` condition so that legacy calculations cannot corrupt the on-chain state even before the proposal is activated.

### Proof of Concept
Not concretely reproduced with exact numeric inputs in this analysis — the root cause was validated by static tracing of `ExchangeCapsule.transaction()` and `ExchangeProcessor.exchange()`. A full PoC would require identifying specific `firstTokenBalance`/`secondTokenBalance`/`sellTokenQuant` values where the double-precision power computation in `ExchangeProcessor` returns a `buyTokenQuant` greater than the true buy-side balance while `AllowHardenExchangeCalculation` is disabled (default), then submitting that as an `ExchangeTransactionContract`/`ExchangeInjectContract` via a signed transaction to drive the stored pool balance negative.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
