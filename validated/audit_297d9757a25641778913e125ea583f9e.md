### Title
Unbounded JSON-RPC filter result queue allows excessive memory allocation via `eth_newFilter`/`eth_newBlockFilter` - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/filters/FilterResult.java`)

### Summary
`LogFilterAndResult` and `BlockFilterAndResult` — the server-side state created by the `eth_newFilter` / `eth_newBlockFilter` JSON-RPC methods — back their result accumulation with a plain, unbounded `LinkedBlockingQueue`. Any unauthenticated JSON-RPC client can create such a filter and simply never call `eth_getFilterChanges`/`eth_uninstallFilter`, causing matching logs or block hashes to accumulate in server memory indefinitely (bounded only by the filter's expiry timer), mirroring the DoH advisory's pattern of buffered data "not released until the end of the connection."

### Finding Description
`FilterResult<T>` defines the shared queue abstraction used by all JSON-RPC filters: [1](#0-0) 

Both concrete implementations instantiate this queue with no capacity bound: [2](#0-1) [3](#0-2) 

`add()` unconditionally appends to the queue (`result.add(...)`) with no size cap, and the accumulated data is only drained (`popAll()`/`drainTo`) when the client actively polls via `eth_getFilterChanges`. The only cleanup mechanism is the expiry timestamp set by `updateExpireTime()` (`TronJsonRpcImpl.EXPIRE_SECONDS`), which is a fixed wall-clock TTL from creation, not tied to actual client activity or queue size. If a filter matches a high-throughput log/block stream (e.g. an `eth_newFilter` with a broad/no address+topic filter) and the client never polls it, matching `LogFilterElement`/block-hash strings keep being pushed into the queue for the full TTL window — directly analogous to the dnsdist DoH bug where the buffer "will not be released until the end of the connection."

### Impact Explanation
A remote, unauthenticated JSON-RPC client can create one or many broad filters and let them run without polling, causing continuous unbounded growth of heap-resident log/block data on the FullNode/SolidityNode/PBFT JSON-RPC service. Multiple concurrent filters compound the effect. This can exhaust node heap memory, leading to `OutOfMemoryError`, GC pressure, and ultimately node crash or denial of service for the JSON-RPC API (and potentially destabilizing the whole node process), which matches the "no impact acceptance criteria" bar of "node crash or halt" / "an API the node can no longer serve."

### Likelihood Explanation
Likelihood is high for triggering excessive queue growth: no authentication or special privilege is required to call `eth_newFilter`, and an attacker fully controls the filter breadth and polling cadence (simply never polling). The only natural limit is the filter's fixed expiry TTL, but during that window under high chain activity (many matching logs/blocks), the queue can still grow substantial before expiry, and an attacker can repeatedly create fresh filters faster than old ones expire to sustain unbounded aggregate memory use.

### Recommendation
Bound `FilterResult`'s internal queue (e.g., cap `LinkedBlockingQueue` capacity or track cumulative size and drop/evict oldest entries or the filter itself once a memory/size threshold is exceeded), and/or reduce `EXPIRE_SECONDS` for filters receiving no `eth_getFilterChanges` polls, and enforce a global maximum on the number of concurrently live filters and their aggregate buffered size, similar to the existing per-connection gRPC/HTTP protections already present elsewhere in the config (`maxConcurrentCallsPerConnection`, `maxMessageSize`).

### Proof of Concept
1. Send a JSON-RPC request `eth_newFilter` with a broad filter (no address/topic restriction) to the node's JSON-RPC HTTP endpoint.
2. Do not call `eth_getFilterChanges` or `eth_uninstallFilter` for the filter's lifetime.
3. Drive chain activity that produces many matching logs/blocks (or simply wait through normal chain operation) — each matching event is unconditionally added to the filter's unbounded `LinkedBlockingQueue`.
4. Repeat step 1 with multiple filters to multiply memory consumption; observe unbounded heap growth in the JSON-RPC filter storage until filter TTL expiry, which can be sustained indefinitely by continuously creating new filters.

public abstract class FilterResult<T> {

  private long expireTimeStamp;

  @Getter
  protected BlockingQueue<T> result;

  public void updateExpireTime() {
    expireTimeStamp = System.currentTimeMillis() + TronJsonRpcImpl.EXPIRE_SECONDS * 1000;
  }

  public boolean isExpire() {
    return expireTimeStamp < System.currentTimeMillis();
  }

  public abstract void add(T t);

  public abstract List<T> popAll();
}
