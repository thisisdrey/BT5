Confirmed: `process_delivery_receipt` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` (lines 445-481) never checks the `receipt.success` field before paying the relayer reward.

### Title
Relayer reward is paid on `submit_delivery_receipt` regardless of the message's actual delivery/execution success on Ethereum - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

### Summary
`DeliveryReceipt` decoded from the Ethereum `InboundMessageDispatched` event carries a `success: bool` field [1](#0-0) , but `Pallet::process_delivery_receipt` never reads or checks it. It always registers the pending order's `fee` as a relayer reward and unconditionally removes the `PendingOrder`, as long as the nonce exists and the gateway matches [2](#0-1) .

### Finding Description
This mirrors the ERC5095 pattern: the ERC5095 report showed the code performing a settlement/payout action (`sellPrincipalToken`, `Safe.transfer`) while skipping the guard condition that should gate it (debiting/verifying the actual owner's balance). Here, the analogous guard that exists in the data model (`receipt.success`) is likewise ignored: the pallet performs the reward settlement (`register_reward`) and order removal unconditionally, without checking whether the message was actually dispatched successfully on the Ethereum side.

`process_delivery_receipt` flow:
1. Verifies gateway address matches [3](#0-2) 
2. Resolves `reward_account` from `receipt.reward_address` [4](#0-3) 
3. Looks up `PendingOrders` by `nonce` [5](#0-4) 
4. Pays `order.fee` as a reward if `> 0` [6](#0-5) 
5. Removes the pending order and emits `MessageDelivered` [7](#0-6) 

At no point is `receipt.success` inspected. Any relayer who can produce a valid Merkle/verifier proof of the `InboundMessageDispatched` event log for a given nonce — even one where the Ethereum-side dispatch reverted (`success: false`, e.g. because gas ran out or the command failed on Ethereum) — will still collect the full relayer fee and have the `PendingOrder` cleared. There is no unprivileged actor assumption violated here: this is triggerable by any signed account that can submit a valid delivery-proof event, which is the pallet's normal, permissionless flow (`submit_delivery_receipt` only requires `ensure_signed`, no special relayer role) [8](#0-7) .

### Impact Explanation
This decouples the reward economics from actual message-delivery correctness. The pallet's own doc comments describe the flow as "Fetch the pending order by nonce of the message, pay reward with fee attached in the order" without qualifying success, but the whole point of carrying `success` in the receipt/event is to distinguish a delivered-and-executed message from a delivered-but-failed one. Because `success` is silently dropped, the reward-payment invariant ("pay only for genuinely completed delivery/execution") is violated, resulting in relayer rewards paid out for messages that failed on the Ethereum side. Repeated over many failed dispatches this drains the reward pool (funded from bridge fees) without the corresponding useful work having been done, and it removes the `PendingOrder` so no retry/re-verification of failure state is possible afterward.

### Likelihood Explanation
High likelihood in terms of triggerability — any relayer submitting a genuine (not forged) event proof for a Command that reverted on Ethereum will hit this path every time, with no special conditions required. The only precondition is that a message dispatch on Ethereum can plausibly fail (out-of-gas, reentrancy guard, bad calldata in a `Command`) while still emitting the `InboundMessageDispatched(success=false)` log, which is exactly how the gateway contract signals failures per the event's presence of a `success` flag.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `receipt.success == true`; when `false`, still remove/settle the `PendingOrder` (or handle it via a distinct failure path/event) but do not pay the relayer fee, or pay a reduced "confirmation only" fee consistent with the documented reward model in `bridges/docs/polkadot-kusama-bridge-overview.md` where compensation is tied to actually delivered work [9](#0-8) .

### Proof of Concept
1. A message with a non-zero `fee` is queued via `do_process_message`, creating `PendingOrders[nonce] = PendingOrder { nonce, fee, block_number }` [10](#0-9) .
2. On Ethereum, the gateway contract attempts to execute the corresponding command and it reverts/fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer (or anyone with the event log + valid proof) calls `submit_delivery_receipt` with this event.
4. `DeliveryReceipt::try_from` decodes `success: false` correctly into the `DeliveryReceipt` struct [11](#0-10) .
5. `process_delivery_receipt` ignores `receipt.success`, pays `order.fee` to `reward_account` via `register_reward`, and removes the order — identical to what would happen for a `success: true` receipt [12](#0-11) .
6. Existing tests only exercise the "always succeeds" path — e.g. `submit_delivery_receipt_succeeds_after_unhalt` asserts the order is settled and reward paid without varying `success` [13](#0-12)  — confirming no test coverage exists distinguishing failed vs. successful delivery for reward gating.

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```

```rust
#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
```
