### Title
CallContract dispatch-gas estimate omits the EIP-150 63/64 buffer that every other Snowbridge command explicitly carries - ([File: bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs])

### Summary
The `ConstantGasMeter::maximum_dispatch_gas_used_at_most` implementation used by the Snowbridge outbound queue explicitly documents that a "healthy buffer... to account for the EIP-150 63/64 rule" must be added on top of the raw gas estimate for every command dispatched to the Ethereum Gateway contract. Every hard-coded command (`SetOperatingMode`, `Upgrade`, `UnlockNativeToken`, `RegisterForeignToken`, `MintForeignToken`) follows this rule with generous fixed constants. `Command::CallContract`, however, returns the user-supplied `gas` value verbatim, with no buffer at all. [1](#0-0) 

### Finding Description
`Command::CallContract` carries a user-controlled `gas: u64` field representing "Maximum gas to forward to target contract" on Ethereum. [2](#0-1) 

This value is fed straight through as the dispatch-gas estimate:

```rust
Command::CallContract { gas: gas_limit, .. } => *gas_limit,
``` [3](#0-2) 

The very same doc comment on `ConstantGasMeter` states that all the constants it returns already bake in a buffer specifically because of "the EIP-150 63/64 rule": [4](#0-3) 

This `maximum_dispatch_gas_used_at_most` value is what's used as `max_dispatch_gas` when the message is committed for delivery to the Ethereum Gateway. [5](#0-4) 

The `OutboundCommandWrapper.gas` field (used identically in the v2 flow via `T::GasMeter::maximum_dispatch_gas_used_at_most`) is what's ABI-encoded and later consumed on the Ethereum side by the Gateway contract to decide how much gas to forward to the target with a low-level call, and to gate whether there is "enough gas" for the dispatch before making that call — exactly the same pattern audited in the Optimism report (`gasleft() >= gas + buffer` followed by forwarding `gasleft()` minus a fixed buffer). [6](#0-5) 

Because the raw user `gas` value is passed through unmodified — unlike every other command, which explicitly reserves margin for the 63/64 rule — any `CallContract` message with a sufficiently large `gas` (per the EIP-150 math in the source report, above ~952,192, scaled to Snowbridge's own buffer thresholds) is exactly the same underestimation bug: the amount of gas that actually reaches the `target` contract via the low-level call on the Ethereum Gateway will be less than the `gas` value the user specified and paid a fee for, because 1/64th of the gas is withheld by the EVM at the call boundary. Since Snowbridge messages, like Optimism withdrawals, are not replayed once dispatched/nonce-consumed (the nonce is incremented unconditionally in `do_process_message` regardless of downstream Ethereum execution outcome) — [7](#0-6)  — a `CallContract` command carrying ether `value` to a target that requires (but doesn't receive) its full specified gas will fail on Ethereum, and the associated value/funds held for that dispatch cannot be redelivered, permanently locking them.

### Impact Explanation
This is a fund-lock / underpriced-work class bug matching the required impact gate: public dispatch of a `CallContract` command with attacker-chosen high gas values causes the fee/gas accounting on the Polkadot side (and, transitively, the amount forwarded on Ethereum) to under-provision gas relative to what was promised/paid for. Because Snowbridge messages are processed and nonced exactly once with no replay, a failed dispatch caused by this gas-accounting gap permanently locks any `value` (ether) associated with the `CallContract` command and wastes the reward/fee paid by the sender, without any way to recover or resubmit.

### Likelihood Explanation
No privileged actor, malicious relayer, or admin action is required — an ordinary user constructing a `CallContract` XCM/message with a gas value near the un-buffered dispatch estimate boundary triggers this deterministically once relayed to Ethereum. The bug is baked into the estimate function itself (`ConstantGasMeter`), which is the default/production `T::GasMeter` implementation, so it applies to every `CallContract` message that reaches this threshold, not merely edge cases requiring adversarial timing.

### Recommendation
Add the same buffer margin used for other commands (or an explicit `gas_limit * 64 / 63` style adjustment) inside `ConstantGasMeter::maximum_dispatch_gas_used_at_most` for `Command::CallContract`, so that the fee charged and the `max_dispatch_gas`/`gas` value propagated to the Ethereum Gateway account for the EIP-150 63/64 rule the same way it is accounted for in every other command variant. This should be paired with verifying that the corresponding Solidity Gateway contract's gas-forwarding check also applies the 64/63 correction (that contract is not present in this repository and could not be verified here).

### Proof of Concept
1. A user submits an XCM that resolves to `Command::CallContract { target, calldata, gas: G, value: V }` with `G` set high enough that `G` is within 1/64th of the dispatch-gas ceiling actually available to the relayer transaction on Ethereum (mirroring the PoC math in the source report: once `G` exceeds roughly the threshold where `G/64` exceeds the fixed buffer used elsewhere).
2. `ConstantGasMeter::maximum_dispatch_gas_used_at_most` returns exactly `G` (no buffer) — [8](#0-7) ; the fee charged to the user and the `gas` encoded in `OutboundCommandWrapper`/`CommittedMessage` reflect only `G`.
3. `do_process_message` increments the channel `Nonce` and commits the message unconditionally, regardless of the eventual Ethereum-side outcome — [7](#0-6) .
4. On Ethereum, the Gateway contract (outside this repo) forwards gas to `target` using a low-level call bounded by `G`; per EIP-150 only 63/64ths of the caller's remaining gas can be forwarded, so the target call receives less than `G`, and can fail even though sufficient total transaction gas was supplied.
5. Because the message's nonce has already advanced and there is no replay mechanism, any `value` attached to the failed `CallContract` command remains permanently stranded, and the sender's fee is spent for a message that could not execute as promised.

/// A meter that assigns a constant amount of gas for the execution of a command
///
/// The gas figures are extracted from this report:
/// > forge test --match-path test/Gateway.t.sol --gas-report
///
/// A healthy buffer is added on top of these figures to account for:
/// * The EIP-150 63/64 rule
/// * Future EVM upgrades that may increase gas cost
pub struct ConstantGasMeter;

impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer.maximum_required_gas
			},
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}
