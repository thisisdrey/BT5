Audit Report

## Title
Integer-division rounding in `calculate_fee` can silently zero-out the Ethereum-side relayer reward for a fully "valid" `PricingParameters` set - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

## Summary
`PricingParameters::validate()` in `bridges/snowbridge/primitives/core/src/pricing.rs` only rejects individually zero-valued fields, but never validates the derived per-message remote fee produced by `Pallet::calculate_fee`. Because `convert_from_ether_decimals` performs a truncating `checked_div` by `10^(ETHER_DECIMALS - Decimals)`, small-but-nonzero, fully "valid" pricing parameters can cause `Fee.remote` to round down to `0`, and this exact behavior is already reproduced by the pallet's own test.

## Finding Description
`PricingParameters::validate()` checks only that `exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, and `multiplier` are individually non-zero: [1](#0-0) . It never simulates or bounds the derived remote fee.

`Pallet::calculate_fee` computes the remote fee via `calculate_remote_fee`, converts to the local currency's fixed-point representation, and then calls `convert_from_ether_decimals`: [2](#0-1) . `convert_from_ether_decimals` performs an integer `checked_div` that truncates toward zero: [3](#0-2) .

`set_pricing_parameters` is the only gate governing this stored value, and it only calls `params.validate()` — it never test-computes `calculate_fee` to confirm the resulting `remote` fee stays non-zero: [4](#0-3) .

Every call to the public `SendMessage::validate` entrypoint — invoked whenever any user routes an XCM message through the Snowbridge exporter — reads the stored `PricingParameters` and calls `calculate_fee` with no additional floor check on the returned fee: [5](#0-4) .

The pallet's own regression test confirms the exact defect end-to-end with a fully "valid" (per `validate()`) parameter set (`fee_per_gas=1`, `rewards.remote=1`, `multiplier=1`, `exchange_rate=1`), producing `fee.remote == 0`, with an explicit comment acknowledging this should be avoided: [6](#0-5) .

## Impact Explanation
`Fee.remote` is meant to reserve the ETH-denominated reward that funds relayer gas reimbursement and incentive for delivering committed messages to Ethereum. Once governance sets a `PricingParameters` value that falls into the truncation range (a value that legitimately passes `validate()`), any unprivileged user can call the public `send`/`validate` path to enqueue and eventually commit messages with `Fee.remote == 0`, meaning zero remote-side compensation is reserved even though `Fee.local` is still charged. This is a public underpriced work condition that can degrade relayer economics and stall Ethereum-side delivery of committed messages, matching the "public underpriced work that degrades block production or stalls bridge processing" impact category.

## Likelihood Explanation
No attacker privilege beyond normal, permissionless message sending is required once the pricing-parameter values fall into the truncation-prone range; this range is plausible for low-decimal-precision `fee_per_gas`/`reward` configurations relative to the `10^(18-Decimals)` scale factor. The exact zero-remote-fee outcome is already reproduced deterministically in the codebase's own test suite with parameters that pass all existing validation, demonstrating this is a reliably reproducible arithmetic property of the current code rather than a hypothetical edge case.

## Recommendation
- Add a post-computation floor check either in `calculate_fee` or by having `PricingParameters::validate()` (called from `set_pricing_parameters`) simulate `calculate_fee` against the expected `gas_used_at_most` range and reject the parameter set if the resulting `remote` fee is `0`.
- Alternatively, replace the truncating `checked_div` in `convert_from_ether_decimals` with a rounding-up division (`div_ceil`) so a non-zero ether-denominated remote fee never converts to `0` in the local currency.

## Proof of Concept
The existing unit test demonstrates the bug directly: [6](#0-5) .

1. Governance calls `set_pricing_parameters` with `fee_per_gas = 1`, `rewards.remote = 1`, `multiplier = 1`, `exchange_rate = 1` — all fields pass `validate()`.
2. Any unprivileged user sends an XCM message routed to the Snowbridge exporter, triggering `OutboundQueue::validate` → `calculate_fee`.
3. `calculate_remote_fee` returns a small positive value that, after `convert_from_ether_decimals`'s integer division, truncates to `0`.
4. The message is accepted and queued with `Fee.remote == 0` — no Ethereum-side relayer reward is reserved, while `Fee.local` is still charged.

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}

fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
