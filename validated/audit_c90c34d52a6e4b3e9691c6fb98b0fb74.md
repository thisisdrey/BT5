### Title
Bad-debt socialization mutates vault interest-accrual state before settling pending interest, causing incorrect reserve/interest accounting - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar`, `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`socialize-debt` in each vault contract mutates `principal-scaled`, `total-borrowed`, `assets`, and `lindex` directly from stale state, without first calling `accrue()`. The market contract then calls `vault-accrue` *after* the write-down has already happened. This is the same ordering defect as the Derby `Vault.rebalance` bug: a state variable that interest/reward math depends on (`principal-scaled`) is updated to reflect the "new period" (post write-down) before the function that computes interest for the "old period" (`accrue`) runs, so the pending interest and treasury reserve for the elapsed period are computed on the wrong principal amount.

### Finding Description
Every other state-mutating vault entrypoint (`deposit`, `redeem`, `transfer`, `system-borrow`, `system-repay`) begins by calling `(try! (accrue))` before reading/mutating `principal-scaled`, `index`, or `lindex`, so pending interest for the elapsed period is always settled against the *pre-mutation* principal: [1](#0-0) 

`socialize-debt`, however, skips this call entirely and immediately reduces `principal-scaled`/`total-borrowed`/`assets` and rewrites `lindex` using values read directly from `var-get`, with no prior `accrue`: [2](#0-1) 

In `market.clar`'s liquidation flow, `socialize-debt-asset` calls `vault-socialize-debt` (which performs the write-down above) and only *afterward* calls `vault-accrue` to "refresh the cache with new indexes post-write-down": [3](#0-2) 

When `accrue()` finally runs, it computes `debt-delta` (interest that accrued since `last-update`) as `new-debt - old-debt` using `scaled-principal` read via `(var-get principal-scaled)`: [4](#0-3) 

But by the time this runs, `principal-scaled` has already been reduced by the socialized (written-off) amount. The interest that accrued on that principal *during the elapsed period before the liquidation*, and the corresponding treasury-lp reserve mint, is therefore computed against the already-shrunk principal instead of the correct pre-write-down principal — exactly mirroring the Derby report's root cause where `settleDeltaAllocation` updated `totalAllocatedTokens` to the new-period value before `storePriceAndRewards` used it to compute rewards for the *previous* period.

### Impact Explanation
This causes systematic under-accrual of interest/treasury reserve for the debt that is about to be written off in every liquidation that triggers bad-debt socialization. Depositors (via `lindex`) and the DAO treasury (via minted `zft` reserve shares) permanently lose the interest that legitimately accrued on that principal for the time between the last accrual and the liquidation, because it is silently dropped rather than credited before the debt is zeroed out. This is a permanent, unrecoverable loss of unclaimed yield to LPs/treasury, which lands in the **High** impact category (permanent freezing/loss of unclaimed yield).

### Likelihood Explanation
This triggers deterministically on every liquidation that results in bad-debt socialization (borrower has no collateral left to cover remaining debt) — a normal, expected code path reachable by any liquidator calling `liquidate`/batch liquidation, not requiring any privileged action or DAO compromise. Any liquidation that occurs after time has passed since the vault's `last-update` (i.e., interest has accrued) will exhibit the miscalculation.

### Recommendation
In `socialize-debt-asset` (and any other caller of the vault's `socialize-debt`), call `vault-accrue` for the asset **before** calling `vault-socialize-debt`, so pending interest and treasury reserve for the elapsed period are settled against the correct (pre-write-down) `principal-scaled`. Equivalently, have the vault's own `socialize-debt` function call `(try! (accrue))` internally at the top, consistent with `deposit`/`redeem`/`system-borrow`/`system-repay`, before performing the write-down.

### Proof of Concept
1. Vault has `principal-scaled = P`, `index = I0`, `last-update = T0`. Time passes to `T1` such that `next-index` at `T1` would be `I1 > I0` (interest has accrued but not yet materialized via `accrue`).
2. A borrower is liquidated with no remaining collateral; `market.clar` invokes `socialize-debt-asset`, which calls `vault-socialize-debt` first: this immediately reduces `principal-scaled` to `P' = P - scaled-amount` and rewrites `lindex` using the *old* `index`/`lindex` (interest for `[T0, T1]` never counted), per `v0-vault-sbtc.clar` lines 942-964.
3. `socialize-debt-asset` then calls `vault-accrue`, which computes `old-debt`/`new-debt` using the *already reduced* `scaled-principal = P'` instead of `P`, per `v0-vault-sbtc.clar` lines 845-852 — understating `debt-delta`, `reserve-inc`, and the treasury-lp mint for the period `[T0, T1]`.
4. Net effect: interest that accrued on the socialized principal between `T0` and `T1` is never credited to `lindex` growth or minted as treasury reserve — it is permanently lost, benefiting no one and shrinking the shares/interest LPs and the DAO treasury should have received.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
