### Title
Deposit-token dust transfer griefing permanently fills a victim's per-account token list, blocking deposits and debt issuance - ([File: contracts/Pool.sol])

### Summary
CVE-2022-3478 is a DoS triggered by a malicious user-controlled upload. The Metronome analog: an unprivileged attacker can push arbitrary "malicious" entries (dust amounts of `DepositToken`s) into a victim's per-account accounting set via `DepositToken.transfer`, permanently DoS-ing the victim's ability to deposit new collateral types or issue new debt tokens once `debtTokensOfAccount + depositTokensOfAccount >= MAX_TOKENS_PER_USER (30)`.

### Finding Description
`Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` are gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens` when the combined per-account list reaches 30 entries [1](#0-0) .

The recipient-side accounting is forced: `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance moves from 0, with no opt-in or minimum amount [2](#0-1) . `transfer` only checks the *sender's* unlocked balance, so any holder can send 1 wei of each deposit token to a victim [3](#0-2) .

Once the victim's list is filled:

- `deposit(amount, victim)` on any deposit token the victim doesn't already hold reverts inside `_mint` → `addToDepositTokensOfAccount` [4](#0-3) .
- `DebtToken.issue` reverts because `_mint` → `pool.addToDebtTokensOfAccount` hits the same shared 30-slot cap, so the victim cannot borrow a synthetic they haven't borrowed before [5](#0-4) .

The attack costs only dust amounts of the underlying collateral for each deposit token the attacker mints and transfers. The victim can still withdraw existing balances, but cannot add new collateral to rescue an unhealthy position in any asset they don't already hold, and cannot open new borrows — a liveness break on core protocol flows for the targeted account.

### Impact Explanation
Temporary freezing of funds / denial of service: the victim is blocked from depositing any new collateral type and from issuing debt in any new synthetic. For an underwater-approaching position, the inability to top up with a different collateral asset can force a liquidation that would otherwise be avoidable. The attacker can re-fill slots cheaply at any time since each dust deposit token permanently occupies a slot while held.

### Likelihood Explanation
Fully unprivileged and cheap: the attacker calls `deposit` once per deposit token (or receives tokens via transfers), then calls `DepositToken.transfer(victim, 1)` for up to 30 distinct tokens. No privileged role, oracle manipulation, or flash loan is required. The only mitigation is that a pool may have fewer than 30 deposit+debt tokens deployed, in which case the attacker can only partially fill the list — partial fills still DoS whatever margin remains. Cost scales with the number of distinct collateral underlyings the attacker must acquire (dust only).

### Recommendation
- Enforce a minimum (e.g., non-dust) amount before calling `addToDepositTokensOfAccount`, or only track tokens added via `deposit`/`seize` rather than permissionless `transfer`.
- Alternatively, apply `MAX_TOKENS_PER_USER` separately to deposit and debt token lists, and exempt `seize`/liquidation paths, so attacker-initiated transfers cannot consume the borrow/deposit capacity of arbitrary accounts.

### Proof of Concept
```solidity
// Foundry fork test sketch (pool with >= 2 deposit tokens: msdA, msdB, ..., msdN)
// Attacker fills victim's depositTokensOfAccount to MAX_TOKENS_PER_USER.

address victim = makeAddr("victim");
address attacker = makeAddr("attacker");

// Victim legitimately holds 1 deposit token + wants to issue debt later
// Attacker loop:
for (uint i; i < depositTokens.length; ++i) {
    DepositToken dt = depositTokens[i];
    IERC20 underlying = dt.underlying();
    deal(address(underlying), attacker, 2);
    vm.startPrank(attacker);
    underlying.approve(address(dt), 2);
    dt.deposit(1, attacker);            // mint 1 wei of msdToken
    dt.transfer(victim, 1);             // forces addToDepositTokensOfAccount(victim)
    vm.stopPrank();
}
// Repeat with enough distinct tokens so that
// depositTokensOfAccount(victim) + debtTokensOfAccount(victim) == 30

// Now victim can no longer deposit into a collateral they don't already hold:
vm.startPrank(victim);
underlying.approve(address(newDepositToken), 100e18);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDepositToken.deposit(100e18, victim);

// And cannot issue debt in a new synthetic:
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDebtToken.issue(1e18, victim);
```

Note: severity is bounded — existing balances remain withdrawable, so this is a temporary functional freeze rather than direct theft; the impact is strongest for users who must diversify collateral or open a new borrow while their position degrades.
