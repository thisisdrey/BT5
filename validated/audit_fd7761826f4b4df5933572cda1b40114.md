### Title
Lack of sanity check on attacker-controlled handshake `Time` field allows permanent denial-of-rehandshake (self-inflicted stale-timestamp DoS) - (File: `handshake_manager.go`)

### Summary
Nebula's handshake payload carries a `Time` field (`handshake/payload.go`), which is unmarshaled into `Result.HandshakeTime` [1](#0-0)  and copied into `HostInfo.lastHandshakeTime` on both the responder path (`beginHandshake`) and the completion path (`continueHandshake`) [2](#0-1) [3](#0-2) . This value is fully attacker-controlled (it is set by the remote peer's `handshake.MarshalPayload` call and only decoded, never sanity-checked, in `processPayload`) [4](#0-3) [5](#0-4) .

### Finding Description
`CheckAndComplete` uses `lastHandshakeTime` as the sole tie-breaker to decide whether a newly-completed handshake is allowed to replace an existing tunnel entry for the same VPN address:

```go
// Is this a newer handshake?
if existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime && !existingHostInfo.ConnectionState.initiator {
    return existingHostInfo, ErrExistingHostInfo
}
``` [6](#0-5) 

This is exactly the same bug class as the referenced `stoptime` report: a value supplied by the counterparty (here, the handshake `Time` field, analogous to `stopTime`) is trusted without any bound check against the local wall clock (`time.Now()`), even though the code comment explicitly states the field's purpose is anti-replay/anti-staleness protection:

```go
// lastHandshakeTime records the time the remote side told us about at the stage when the handshake was completed locally
// ...
// This is used to avoid an attack where a handshake packet is replayed after some time
lastHandshakeTime uint64
``` [7](#0-6) 

There is no `stoptime`-style guard equivalent to `if stopTime <= block.timestamp` — nowhere in `processPayload`, `beginHandshake`, or `continueHandshake` is `payload.Time`/`result.HandshakeTime` validated to be within any reasonable window of `time.Now()`. A remote peer that legitimately possesses a CA-signed certificate (as required by the scope rules) can freely set this field to `math.MaxUint64` on every handshake it initiates. Because `lastHandshakeTime` is compared with `>=`, once an attacker-controlled maximal value is stored for a given `vpnAddr`, no future legitimate handshake from the real peer (whose `Time` is a real, comparatively tiny Unix-nanosecond value) can ever satisfy `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime` being false — the check permanently rejects the genuine peer's handshakes with `ErrExistingHostInfo` ("Handshake too old") for as long as the poisoned `HostInfo` entry survives.

### Impact Explanation
This allows a certificate-holding remote peer to poison a victim's hostmap entry with an unbounded future timestamp, then have all subsequent legitimate re-handshakes from the real peer at that VPN address rejected as "too old" via `handleCheckAndCompleteError`'s `ErrExistingHostInfo` branch [8](#0-7) . This is a remote state-poisoning / persistent tunnel-disruption impact: the legitimate node is effectively locked out of establishing a fresh tunnel to that address until the poisoned `HostInfo` is independently torn down (e.g. by the connection manager's inactivity/invalid-cert logic), which an attacker who can keep resending handshakes can indefinitely prevent.

### Likelihood Explanation
Exploitation only requires the ability to complete one handshake as a legitimately certificate-holding peer (in scope per the rules) and set an arbitrary `Time` value in the handshake payload — no cryptographic bypass is needed since `Time` is unauthenticated payload content only bound by the Noise transcript, not validated against wall-clock bounds. This is straightforward to trigger repeatedly.

### Recommendation
Add a sanity check analogous to the suggested `stopTime <= block.timestamp` fix: reject (or clamp) handshake `Time` values that deviate too far from the local `time.Now()` (e.g., in `processPayload`, when `flags.expectsPayload` is set), for example:
```go
now := uint64(time.Now().UnixNano())
if payload.Time > now+maxClockSkew {
    m.failed = true
    return ErrInvalidHandshakeTime
}
```
This bounds the attacker-controlled field the same way the audit report recommends bounding `stopTime`, preventing a single malicious/skewed peer from permanently starving future legitimate handshakes via `lastHandshakeTime` comparison.

### Proof of Concept
1. Attacker (holding a valid signed cert) initiates a handshake to victim's VPN address, setting `Payload.Time = math.MaxUint64` in `handshake.MarshalPayload` (see field definition) [9](#0-8) .
2. Victim (responder) completes the handshake in `beginHandshake`, storing `hostinfo.lastHandshakeTime = result.HandshakeTime` = `math.MaxUint64` in the main hostmap via `CheckAndComplete` [10](#0-9) .
3. The real, legitimate peer for that VPN address later attempts a genuine re-handshake (e.g., after a restart/roam) with a normal `Time` value (current Unix nanoseconds).
4. In `CheckAndComplete`, `existingHostInfo.lastHandshakeTime (MaxUint64) >= hostinfo.lastHandshakeTime (real time)` is always true, so the genuine handshake is rejected with `ErrExistingHostInfo` ("Handshake too old") [6](#0-5) [8](#0-7) , permanently blocking that peer from re-establishing a tunnel until the poisoned entry is externally evicted.
