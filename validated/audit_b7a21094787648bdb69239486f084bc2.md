Audit Report

## Title
Unconditional tip burn before cross-chain validity check causes permanent user-fund loss in Snowbridge relayer tip top-up flow - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`SnowbridgeSystemFrontend::add_tip` on AssetHub swaps a user-supplied asset for Ether and burns it for teleportation unconditionally via `swap_fee_asset_and_burn`, before it is known whether the target message nonce on BridgeHub is still pending. [1](#0-0)  The teleported value is dispatched via XCM `Transact` to `EthereumSystemV2::add_tip` on BridgeHub, which, if the nonce has already been consumed, swallows the failure into a `LostTips` bookkeeping map while still returning `Ok(())`, and there is no extrinsic to reclaim it. [2](#0-1) 

## Finding Description
`add_tip` burns the tip asset unconditionally by calling `swap_fee_asset_and_burn`, which either swaps the asset for Ether via `T::Swap::swap_exact_tokens_for_tokens` and burns it with `burn_for_teleport`, or burns it directly if it's already Ether — with no reversal mechanism. [3](#0-2) [4](#0-3) 

The burned amount is forwarded via `Transact` to BridgeHub's `EthereumSystemV2::add_tip`. This dispatches to `InboundQueue::add_tip` or `OutboundQueue::add_tip` depending on message direction, and on error, only records the lost amount in `LostTips` and emits `TipProcessed { success: false }`, while the extrinsic itself still returns `Ok(())`. [5](#0-4) 

`LostTips` is explicitly documented as bookkeeping only, "to support implementing a recovery method in the future" — confirming no recovery currently exists. [6](#0-5)  A repo-wide search confirms there is no `claim`/`reclaim`/`recover` extrinsic tied to `LostTips` anywhere in the `bridges/snowbridge` tree — only the mutation site and its tests reference it.

The downstream `AddTip` implementations reject a tip once the nonce is already consumed: `InboundQueue::add_tip` checks `Nonce::<T>::get(nonce)` and errors with `AddTipError::NonceConsumed` if already true. [7](#0-6)  `OutboundQueue::add_tip` errors with `AddTipError::UnknownMessage` if `PendingOrders` no longer contains the nonce (i.e., message already delivered and removed at line 475). [8](#0-7) 

The corrupted invariant: settlement (burn/teleport of user funds on AssetHub) advances irreversibly before dispatch/execution success is confirmed on BridgeHub, violating the required pivot that payout state must only advance after execution and settlement succeed atomically. Because the AH burn and the BH nonce-consumption race across two chains connected only by asynchronous XCM messaging, a normal (non-malicious) relayer processing the message at ordinary speed is sufficient to consume the nonce before the tip's `Transact` message executes on BH.

## Impact Explanation
`add_tip` is a public, unprivileged, signed extrinsic on AssetHub. [9](#0-8)  Ordinary usage (a user tipping a message that a relayer happens to process in parallel) results in permanent, unrecoverable loss of the user's burned funds, since the only trace of the loss is an unclaimable value in `LostTips`. This matches the "permanent user-fund lock" impact class for public underpriced/uncoordinated work in the cross-chain settlement path.

## Likelihood Explanation
High. No adversarial or privileged behavior is required — only the ordinary latency inherent to cross-chain XCM messaging between AssetHub and BridgeHub, combined with a relayer doing its job at normal speed. This race is most likely to occur precisely for near-completion messages, which is exactly when users are incentivized to add tips to hurry them along, making the vulnerable window a routine occurrence rather than an edge case.

## Recommendation
Avoid burning/teleporting the tip on AssetHub until nonce pendency is confirmed on BridgeHub, or make the settlement atomically reversible (e.g., escrow on BH, settle only after confirming nonce liveness). Alternatively, have `EthereumSystemV2::add_tip` propagate the failure as an `Err` instead of masking it via `LostTips` + `Ok(())`, and implement the currently-absent recovery/reclaim extrinsic so amounts recorded in `LostTips` are actually redeemable by the original sender.

## Proof of Concept
1. A message (Inbound nonce `N` or Outbound nonce `N`) is pending with a low relayer fee.
2. User calls `SnowbridgeSystemFrontend::add_tip(message_id, asset)` on AssetHub. [1](#0-0) 
3. `swap_fee_asset_and_burn` immediately swaps and burns the user's asset for Ether with no reversibility. [3](#0-2) 
4. Concurrently, a normal relayer submits `submit_delivery_receipt`/processes the message for nonce `N`, consuming/removing it before the tip's `Transact` message reaches BridgeHub.
5. `EthereumSystemV2::add_tip` executes on BH, `InboundQueue::add_tip`/`OutboundQueue::add_tip` returns `Err(AddTipError::NonceConsumed)`/`Err(AddTipError::UnknownMessage)`. [7](#0-6) 
6. `EthereumSystemV2::add_tip` adds the amount to `LostTips::<T>::get(&sender)`, emits `TipProcessed { success: false }`, and still returns `Ok(())`. [10](#0-9) 
7. The user's already-burned Ether is permanently lost, with no extrinsic in the codebase allowing redemption of the `LostTips` balance.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
