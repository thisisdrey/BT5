### Title
Same-block DeleteKey+AddKey nonce reseed enables replay of already-executed transactions signed under the same public key - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`add_regular_key` (runtime/runtime/src/access_keys.rs:230-255) reseeds a re-added access key's nonce purely from the current `block_height` (`initial_nonce_value`, :46-50), with no regard to the highest nonce previously consumed under that (account_id, public_key) pair. Because a self-directed `DeleteKey`+`AddKey` transaction becomes a *local receipt* executed in the **same block** as the transaction (per `docs/architecture/how/tx_receipts.md:51-53`), an attacker can, within one block, consume a batch of nonces close to the block's upper bound, then reset the key's stored nonce back down to `(block_height-1)*1_000_000` — a value lower than the nonces just consumed — reopening them for replay in a later block.

### Finding Description
- `verify_nonce` (runtime/runtime/src/verifier.rs:211-237) enforces `tx_nonce > current_nonce` (Monotonic mode) and `tx_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (upper bound), where `block_height` is the height of the block currently being applied.
- `initial_nonce_value` (access_keys.rs:46-50) seeds a freshly-added regular key's nonce to `(block_height-1)*1_000_000`, using only the *current* apply-time block height — it never reads or compares against any previously stored/used nonce for that key.
- `action_add_key` → `add_regular_key` (access_keys.rs:149-192, 230-255) writes this reseeded value via `set_access_key` (line 241) unconditionally whenever a public key is re-added after being deleted, even if that exact public key was used moments earlier in the very same block.
- Per `docs/architecture/how/tx_receipts.md:51-53`: "if the sender of the receipt is the same as the receiver, then the receipt will be added to the `local_receipts` queue and executed in the same block." A single self-addressed transaction with actions `[DeleteKey, AddKey]` (same public key) is therefore converted to a receipt and *executed in the same block* as the transaction that created it.
- Exploit flow at block `K`:
  1. Attacker submits a batch of ordinary transactions signed under access key `PK`, with nonces `n_1 < n_2 < ... < n_m` in the natural range `((K-1)*1e6, K*1e6)` — these pass `verify_nonce` and update the stored `access_key.nonce` to `n_m` during transaction processing (phase 1 of block application).
  2. In the same block, attacker submits a self-directed transaction from the same account with actions `[DeleteKey{PK}, AddKey{PK}]`. This becomes a local receipt executed in phase 2 of the same block's apply, calling `add_regular_key` with `apply_state.block_height = K`, which resets `access_key.nonce` to `(K-1)*1_000_000` — below `n_1...n_m`.
  3. In a subsequent block (still within the transaction validity/TTL window), the attacker resubmits the identical, previously-executed transactions `n_1...n_m`. Since `n_i > (K-1)*1_000_000` (the new floor), `verify_nonce` accepts them again, and they are re-executed — a full replay of the batch, not a single transaction.
- No existing check stops this: signature verification succeeds (identical bytes), `chain_validate`/TTL only bounds recency, and duplicate-hash detection (`seen_tx_hashes`, runtime/runtime/src/lib.rs:2031-2042) only dedups within a single chunk, not across blocks. The nonce mechanism is NEAR's sole replay-protection primitive, and it is defeated by the reseed-without-history-check design.

### Impact Explanation
Impact category: **double-spend/replay** and, depending on the replayed actions, **theft or loss of funds / token inflation**. Any value-transferring or state-mutating action (SendMoney, FunctionCall deposits, staking, bridge/lending deposits without contract-side idempotency) signed by the attacker's own key can be executed twice against the same signed bytes. Because the attacker controls the account, they primarily harm themselves unless the replayed action interacts with a third-party contract that treats each successfully-verified transaction as a distinct, non-replayable event (e.g., "claim" logic relying on protocol-level nonce uniqueness rather than its own idempotency guard) — in which case the replay can duplicate credits/mints without doubling the debited resource, i.e., token inflation. This also breaks the invariant "each transaction executes exactly once," a core consensus-safety assumption of the protocol.

### Likelihood Explanation
Preconditions are minimal and attacker-controlled: a funded account with a full-access key, several ordinary prior transactions, and one additional self-addressed `[DeleteKey, AddKey]` transaction, all landing in the same block (which the attacker can engineer by pacing submission close to a chunk-production boundary, since local receipts always execute same-block regardless of producer scheduling). It requires no validator/node privilege, no leaked keys, and is repeatable every time the attacker cycles the key. Cost is only the normal gas fees for the delete/add-key transaction and the resubmitted batch. Because the vulnerable formula (`initial_nonce_value`) was specifically introduced to bound (not eliminate) the nonce-collision window from issue #3779, this same-block edge case appears to have been left unaddressed.

### Recommendation
When re-adding a public key that previously existed on the account (or globally, if key history is tracked), seed the new nonce to `max(initial_nonce_value(block_height), previous_max_nonce_used_by_this_key)` rather than unconditionally overwriting with the block-height-derived floor. At minimum, disallow `AddKey` from lowering the effective nonce floor below any nonce already consumed by that (account_id, public_key) pair within the current block/chunk (e.g., track a per-apply high-water-mark nonce per key and clamp `initial_nonce_value` against it before calling `set_access_key`).

### Proof of Concept
Runtime apply-path integration test (e.g., alongside `runtime/runtime/src/tests/apply.rs`):
1. Create an account with a full-access key `PK` at block height `K0`. Advance to block `K`.
2. In block `K`, submit `m` `SendMoney` transactions signed by `PK` with nonces `n_1 < ... < n_m` in `((K-1)*1_000_000, K*1_000_000)`; assert all succeed and account balance decreases by the sum.
3. In the same block `K`, submit a self-addressed transaction with actions `[DeleteKey{PK}, AddKey{PK, FullAccess}]` signed with a valid higher nonce; assert it is converted to a local receipt and applied in block `K`, and that `get_access_key` afterward shows `nonce == (K-1)*1_000_000`.
4. In block `K+1` (within TTL), resubmit the identical signed transactions from step 2 (same nonces/signatures).
5. Assert: the count of accepted/executed transactions in step 4 equals `m` (i.e., equals the count of previously-consumed nonces `> (K-1)*1_000_000`), not `0`, and that the account balance is debited a second time — demonstrating replay/double execution rather than rejection via `InvalidNonce`.
