Confirmed: when an action within a receipt fails, `apply_action_receipt` breaks the action loop on the first `Err` [1](#0-0)  and the whole receipt rolls back via `state_update.rollback()` on failure [2](#0-1) . This means a batched promise like `Promise::new(current_account_id).delete_key(pk).function_call_weight("ban_relayer", ...)` used in `create_ban_relayer_promise` executes as a single receipt: if `delete_key` fails for any reason, the whole receipt (including the `ban_relayer` call that resets `has_in_flight_tx`) is rolled back and never happens [3](#0-2) . Since `has_in_flight_tx` was already set to `true` in the caller (`rlp_execute`/`address_check_callback`) before returning this promise [4](#0-3) , and no `.then()` callback exists on this ban-relayer promise to reset the flag regardless of outcome, this is a case where the flag could get stuck. However, I could not conclusively verify a concrete, reachable trigger for `delete_key` to fail here (the key being deleted is the signer's own access key, which should normally exist), so I cannot confirm exploitability with certainty from static analysis alone.

Given the scope restrictions (eth-implicit wallet contract is in scope) and the strong structural analogy to the reported bug class — a state flag (`has_in_flight_tx`, analogous to game state) that gates all future calls to the contract, combined with a code path that can leave the flag set without any callback ever running to clear it — I present this as the closest valid analog, while noting the residual uncertainty on the exact failure trigger for `delete_key`.

### Title
Wallet Contract `has_in_flight_tx` can be permanently stuck if the ban-relayer receipt's `delete_key` action fails, locking the ETH-implicit account out of all future transactions - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (deployed on ETH-implicit accounts) uses a boolean flag `has_in_flight_tx` to guard against concurrent `rlp_execute` calls, so only one transaction can be "in flight" at a time [5](#0-4) . Every code path that sets the flag `true` is expected to reach a `#[private]` callback that resets it to `false`, and all normal callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) do reset the flag unconditionally at the top of their body [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) .

However, one of the promises created when a faulty relayer is detected, `create_ban_relayer_promise`, batches `delete_key(pk)` and `function_call_weight("ban_relayer", ...)` into a single receipt rather than chaining them with `.then()` [3](#0-2) . In nearcore's runtime, actions within one receipt execute sequentially and the loop stops at the first action that returns an `Err`, after which the whole receipt is rolled back and no subsequent actions in that receipt run [10](#0-9) [11](#0-10) . If `delete_key` in that batch fails, `ban_relayer` (the only place that would reset `has_in_flight_tx` for that code path) never executes.

### Finding Description
The contract sets `has_in_flight_tx = true` immediately before returning `create_ban_relayer_promise()` from `rlp_execute` and `address_check_callback` [12](#0-11) [13](#0-12) . That promise is a single receipt with two chained actions on the same account (`delete_key` then `function_call_weight("ban_relayer", ...)`), not two separate `.then()`-chained receipts. Per the runtime's action-execution model, if `delete_key(pk)` errors (e.g. `DeleteKeyDoesNotExist` if the key was already removed, was never present, or was consumed/rotated by a race with a concurrent transaction), the receipt's action loop breaks immediately and the entire receipt is rolled back, meaning `function_call_weight` never invokes `ban_relayer` on this same contract. Since `ban_relayer` is the only method in that branch that would flip `has_in_flight_tx` back to `false`, the flag remains permanently `true` in contract state (this mutation to `self` happened in the *prior*, already-committed receipt/method call and is not undone by the failure of the subsequent one).

Once `has_in_flight_tx` is stuck `true`, `rlp_execute`'s very first check unconditionally rejects all future calls with "transaction already in progress" [14](#0-13) , permanently disabling the ETH-implicit account. This mirrors the reported bug class: a state machine (game state / `has_in_flight_tx`) can reach a state that blocks all future user-facing operations because a necessary reset/validation step is bypassed by a specific code path, and there is no external recovery mechanism (no owner, no way to reset the flag, no way to redeploy since ETH-implicit accounts cannot have their contract replaced with an arbitrary one nor obtain a full-access key) — any funds held by or routed through the account become effectively unusable via the intended interface.

### Impact Explanation
If reachable, this permanently locks out the ETH-implicit account from ever executing another Ethereum-style transaction through the Wallet Contract, since `rlp_execute` is the sole entry point and it hard-rejects while `has_in_flight_tx` is `true`. Because ETH-implicit accounts cannot have a full-access key added and cannot have their contract redeployed except through the same locked `rlp_execute` path [15](#0-14) , there is no recovery path — this matches the "permanent freezing of funds" impact bar, since any $NEAR or token balance controlled by that address becomes permanently inaccessible through the protocol-sanctioned interface.

### Likelihood Explanation
Likelihood is uncertain. `delete_key` targets the *signer's own* access key (`env::signer_account_pk()` of the relayer that is being banned) [16](#0-15) , and under ordinary sequential execution that key should still exist at the time this receipt runs (only one transaction is in flight at a time, per the module's own stated invariant). I was not able to confirm from static analysis alone a concrete scenario (e.g., a race where the same key is deleted by an unrelated, concurrently-processed receipt, or where a relayer intentionally submits two overlapping requests with keys that get removed between validation and execution) that would trigger `DeleteKeyDoesNotExist` in this specific batch. This is a genuine gap in verification: the trigger condition is plausible but not proven reachable from an ordinary unprivileged client interaction.

### Recommendation
- Chain `delete_key` and the `ban_relayer` callback with `.then()` instead of batching them into one receipt, so that `ban_relayer` (and thus the `has_in_flight_tx` reset) runs in its own downstream receipt regardless of whether `delete_key` succeeds or fails.
- Alternatively, add a `#[private]` callback that unconditionally resets `has_in_flight_tx` even when the preceding promise fails, mirroring the "always reset" pattern already used by the other three callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`).
- Add an explicit test exercising the failure path of `create_ban_relayer_promise`'s `delete_key` action to confirm whether `has_in_flight_tx` can get stuck, closing the verification gap noted above.

### Proof of Concept
Not independently reproducible from static analysis alone. The theoretical trigger is:
1. A relayer using a `FunctionCall` access key on an ETH-implicit account calls `rlp_execute` with data that causes a "Relayer" error while `env::signer_account_id() == current_account_id` (self-signed / access-key case), causing `create_ban_relayer_promise` to be returned and `has_in_flight_tx` to be set `true` [12](#0-11) .
2. If, at the point this receipt executes, the relayer's access key (`env::signer_account_pk()`) has already been removed from the account (e.g., due to key rotation or an already-completed ban from an overlapping/late-arriving receipt), `delete_key` fails with `DeleteKeyDoesNotExist` [17](#0-16) .
3. Per the action-execution loop, the receipt aborts before running `function_call_weight("ban_relayer", ...)`, so `has_in_flight_tx` is never reset [1](#0-0) .
4. All subsequent calls to `rlp_execute` on this account fail with "transaction already in progress" indefinitely [14](#0-13) .

I was unable to construct or confirm a concrete, deterministic sequence of ordinary-client transactions that forces step 2 to occur; this remains an open question requiring dynamic testing (e.g., in `test-loop-tests` or `integration-tests/src/tests/features/wallet_contract.rs`) rather than static code review.
