### Title
Unvalidated attacker-controlled offsets in shielded-pool precompiled contracts cause out-of-bounds array access - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
CVE-2025-66046 describes libbiosig's MFER parser trusting an attacker-controlled tag/length field and copying data into fixed-size stack buffers without validating that the copy stays within bounds, causing a stack overflow. The closest reachable analog in java-tron is `VerifyTransferProof.execute()` (and its siblings `VerifyMintProof`/`VerifyBurnProof`) in `PrecompiledContracts.java`, which decode attacker-controlled offset/count fields from raw precompile call data and use them directly as `System.arraycopy` source offsets into fixed-size buffers without validating them against `data.length` before use.

### Finding Description
`VerifyTransferProof.execute(byte[] data)` only checks that `data.length` is one of four fixed sizes [1](#0-0) . It then reads three offset fields directly from the untrusted payload: [2](#0-1) 
`spendOffset`, `spendAuthSigOffset`, and `receiveOffset` are fully attacker-controlled 32-bit integers taken from `parseInt(data, 0/32/64)`. These are then used, without any bounds check against `data.length`, both to re-index into `data` for count fields and as the base for further `System.arraycopy` calls copying into fixed-size arrays (`byte[][] nullifier`, `anchor`, `spendCv`, `rk`, `spendProof`, `spendAuthSig`, `receiveCm`, `receiveCv`, `receiveEpk`, `receiveProof`) [3](#0-2) . Only `spendCount`/`receiveCount`/`spendAuthSigCount` bounds (1-2) are validated [4](#0-3) ; the offsets themselves are never checked to be within `[0, data.length]`, so a crafted call can drive `spendOffset + 320*i` (or the analogous receive/spendAuthSig arithmetic) far outside the array, exactly mirroring the MFER bug class where a tag-derived length/offset is trusted to index a fixed buffer without a range check.

The related `VerifyMintProof` and `VerifyBurnProof` methods use fixed offsets (safer) but still perform unguarded `System.arraycopy` reads keyed off attacker-supplied `leafCount`/`value` fields, following the same "trust the header field, copy into fixed buffer" pattern [5](#0-4) .

### Impact Explanation
Because Java performs bounds-checked array access, an out-of-range offset raises `ArrayIndexOutOfBoundsException` rather than true stack memory corruption. If this exception is not caught cleanly by the calling TVM/Program precompile dispatch path, it can propagate as an unexpected runtime exception during block/transaction execution on every full node processing the transaction, rather than being cleanly reverted as an ordinary VM revert — this is a determinism/availability concern reachable by any contract that calls the Sapling shielded precompile address with malformed input. This is a lower-severity analog of the CVE (Java's memory safety prevents RCE), but it still represents an unvalidated-input path that a MFER-style crafted-length attack could exploit to destabilize precompile execution on any node that processes the transaction.

### Likelihood Explanation
Reachability is straightforward: the Sapling precompiled contracts (`VerifyMintProof`, `VerifyTransferProof`, `VerifyBurnProof`) are called via ordinary TVM `CALL`/`STATICCALL` opcodes to the well-known precompile address from any deployed contract, i.e., by any unprivileged contract deployer/caller who can submit a transaction with a crafted `data` payload of the exact size the switch statement expects but with malicious offset fields. No special privileges are required.

### Recommendation
Validate every offset field (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) against `data.length` immediately after `parseInt`, rejecting the call (return `Pair.of(true, DataWord.ZERO().getData())`) if `offset < 0` or `offset + requiredLength > data.length`, mirroring the `verifyLength` bounds check already used in `RLP.java` [6](#0-5) . Apply the same offset validation before every `System.arraycopy` call in `VerifyMintProof`, `VerifyTransferProof`, and `VerifyBurnProof`.

### Proof of Concept
Deploy a contract that performs a `CALL` (or `STATICCALL`) to the Sapling `VerifyTransferProof` precompile address with a payload whose length matches one of the accepted `SIZE` values (2080/2368/2464/2752 bytes) [7](#0-6)  but with the first 32-byte word (`spendOffset`) set to a large or negative value (e.g. `0x7FFFFFFF`). The subsequent `parseInt(data, spendOffset)` and `System.arraycopy(data, spendOffset + 320*i, ...)` calls will attempt to read outside the bounds of `data`, throwing `ArrayIndexOutOfBoundsException` inside precompile execution triggered directly by the submitted transaction.
