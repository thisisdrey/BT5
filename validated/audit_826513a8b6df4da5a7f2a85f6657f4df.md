### Title
`quoteSwapIn`/`quoteLiquidateIn` round the required input down, so the quoted amount produces less than the requested output - (contracts/Pool.sol)

### Summary
Metronome provides reverse-quote view functions that compute the input needed to obtain an exact output: `Pool.quoteSwapIn` (synthetic-to-synthetic swaps) and `Pool.quoteLiquidateIn` (collateral seized for a given repay, used by `quoteLiquidateMax`). Both use `WadRayMath.wadDiv`/`wadMul`, which round half-up — i.e. they can round the required input *down* by up to 0.5 wei per step, and the final oracle `quote` truncates again. Calling `swap`/`liquidate` with the quoted amount then mints/seizes up to a few wei less than the caller requested — the same off-by-one-in-the-wrong-direction class as the Mantra `compute_offer_amount` finding.

### Finding Description
In `Pool.quoteSwapIn` (`contracts/Pool.sol:482-498`):

```solidity
uint256 _swapFee = feeProvider.swapFees(...);
if (_swapFee > 0) {
    amountOut_ = amountOut_.wadDiv(1e18 - _swapFee);   // half-up rounding, can round down
    _fee = amountOut_.wadMul(_swapFee);                // half-up, can round down
}
_amountIn = _poolRegistry.masterOracle().quote(        // truncating conversion
    address(syntheticTokenOut_), address(syntheticTokenIn_), amountOut_
);
```

`wadDiv` computes `(a * WAD + b / 2) / b` (`contracts/lib/WadRayMath.sol:39-41`) — nearest rounding, not ceiling. So for a requested `amountOut_`, the grossed-up amount can be 1 wei short of the true value needed, `wadMul(_swapFee)` can further understate the fee deduction, and `masterOracle().quote` (a plain `amount * priceB / priceA` division in the oracle aggregators) floors the result. The composed `_amountIn` is therefore a lower bound, not an upper bound.

`Pool.swap` (`contracts/Pool.sol:642-671`) then executes the forward path: it burns `amountIn_` and calls `quoteSwapOut` (`contracts/Pool.sol:508-525`), which applies `quote` (floor) and `wadMul(_swapFee)` (half-up on the fee, which can round the *fee* down, leaving net out short). The round-trip `quoteSwapIn → swap` is not guaranteed to yield `amountOut_`; it can return `amountOut_ - 1` (or a few wei less across non-1:1 price pairs and non-18-decimal quote paths).

The identical pattern exists in liquidation: `quoteLiquidateIn` (`contracts/Pool.sol:383-409`) computes `_repayAmountInCollateral = totalToSeize_.wadDiv(1e18 + _totalFees)` and then quotes with floor; `quoteLiquidateMax` (`contracts/Pool.sol:419-440`) feeds `depositToken_.balanceOf(account_)` through it to derive `_maxAmountToRepay`. A liquidator repaying exactly `_maxAmountToRepay` can hit `AmountIsTooHigh` (`_totalSeized > balanceOf`) or, conversely, seize slightly less than the full balance — dust error in the caller's disfavor.

### Impact Explanation
The reverse-quote functions violate the "exact output" invariant: `swap(syntheticTokenIn, syntheticTokenOut, quoteSwapIn(..., X))` can mint `X - ε`. Contracts and integrations that rely on `quoteSwapIn`/`quoteLiquidateIn` to size an exact-out swap or a full-seize liquidation will receive less than requested, or revert on their own slippage/exactness checks — an unexpected-results/unexpected-revert condition identical in kind to the reference finding. Magnitude is limited to dust per call, so it is a correctness/UX bug rather than value extraction; no unprivileged attacker can steal funds with it, but the function returns wrong results to any caller.

### Likelihood Explanation
Occurs whenever `amountOut_ * WAD` is not exactly divisible by `(1e18 - _swapFee)` or the oracle quote truncates — i.e. for most non-round amounts once `swapFee > 0` or prices differ from 1:1. Reachable by any EOA through the public `swap`/`liquidate` entry points (`whenNotShutdown`, `nonReentrant`, `onlyIfSyntheticTokenExists` do not prevent it; `isSwapActive` is enabled in deployed configs).

### Recommendation
Round the reverse quote up instead of down: add a ceiling division for the fee gross-up (`(a * WAD + b - 1) / b` or a `wadDivUp`), round the fee up, and round the oracle conversion up (or add `+ 1` wei when there is a remainder). Paying one extra wei of input guarantees the caller receives the requested `amountOut_`, matching the mitigation accepted in the reference report.

### Proof of Concept
Hardhat (fork or existing fixture in `test/Pool.test.ts`):

```ts
it('quoteSwapIn underestimates amountIn (off-by-one)', async () => {
  // given: swapFee > 0 for the msUSD -> msETH pair
  await feeProvider.updateSwapFee(parseEther('0.003')) // 0.3%

  const amountOut = parseEther('1.234567890123456789') // non-round amount
  const {_amountIn} = await pool.quoteSwapIn(msUSD.address, msETH.address, amountOut)

  // when: user swaps exactly the quoted amountIn
  const balanceBefore = await msETH.balanceOf(user.address)
  await pool.connect(user).swap(msUSD.address, msETH.address, _amountIn)
  const received = (await msETH.balanceOf(user.address)).sub(balanceBefore)

  // then: user receives less than the requested amountOut
  expect(received).to.be.lt(amountOut) // off by >= 1 wei
})
```

Analogous PoC for liquidation: seize `totalToSeize = msdMET.balanceOf(alice)`, compute `quoteLiquidateIn`, then `liquidate` with `_amountToRepay` and observe `_totalSeized` differing from the requested seize amount by dust (or an `AmountIsTooHigh` revert when the division floors the other way).

Relevant code: `quoteSwapIn`/`quoteSwapOut`/`swap`/`quoteLiquidateIn`/`quoteLiquidateMax` in `contracts/Pool.sol:383-440, 482-525, 642-671`; half-up rounding in `contracts/lib/WadRayMath.sol:25-41`.
