### Title
Floating-point precision manipulation in the internal Bancor-style TRC10 exchange price curve allows attacker-controlled rounding drain - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeTransactionActuator`, reachable by any account via a broadcast `ExchangeTransactionContract`, computes the swap output using `ExchangeCapsule.transaction()`, which by default (when `allowHarden`/hardened calculation is not activated) delegates to `ExchangeProcessor`. This class computes the Bancor-like virtual-supply curve using native Java `double` arithmetic (`Math.pow`/`StrictMath.pow` and floating point division) rather than exact integer/BigDecimal math.

### Finding Description
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute the issued/returned quantities via `double issuedSupply = -supply * (1.0 - Math.pow(1.0 + quant/newBalance, 0.0005))` and `balance * (Math.pow(1.0 + supplyQuant/supply, 2000.0) - 1.0)` [1](#0-0) . This code path is selected in `ExchangeCapsule.transaction()` whenever `hardenedCalc` is false, i.e. the legacy/default path used by `ExchangeTransactionActuator.execute()` unless the network has activated `allowHarden()`/strict-math hardening via committee proposal [2](#0-1) [3](#0-2) .

Repo tests confirm the double-based `ExchangeProcessor` and the BigDecimal-based `SafeExchangeProcessor` produce *different, non-equal* results across many realistic input sets (`Assert.assertNotEquals(anotherTokenQuant, result)` for the double vs. strict comparison in `ExchangeProcessorTest.testStrictMath`) [4](#0-3) . This demonstrates the legacy formula's output is not a deterministic, precise function of the reserve ratio — an attacker who can predict/observe how `double` rounding behaves for specific `(sellTokenBalance, buyTokenBalance, sellTokenQuant)` triples can choose trade sizes that yield outputs biased in their favor relative to the "true" reserve-ratio price, extracting value from the pool on every trade while the exchange's stored balances (`firstTokenBalance`/`secondTokenBalance`) are updated using the same biased `buyTokenQuant` [5](#0-4) .

Because TRC10 exchange pools hold real TRX/token reserves and any unprivileged account can submit `ExchangeTransactionContract` transactions repeatedly and cheaply, an attacker can perform many small trades chosen specifically to accumulate rounding-favorable outcomes, progressively draining a pool's reserves — directly analogous to how the Mirror Protocol attacker repeatedly exploited a price-calculation flaw to drain the BTC/ETH/DOT collateral pools before the exchange could be halted or the community could react.

### Impact Explanation
Repeated exploitation drains TRX/TRC10 reserves held in `Exchange`/`ExchangeV2` pools created via `ExchangeCreateActuator`, resulting in direct, permanent loss of funds for liquidity providers/other traders, with no privileged access required — this satisfies the "concrete unauthorized... theft... of funds" bar. Given the amounts that can be locked in these on-chain exchange pools, and that this affects the default (non-hardened) code path, this is a High severity issue.

### Likelihood Explanation
Likelihood is High: the vulnerable code path is the default behavior unless a governance proposal activates the harden/strict-math flags; any account can submit `ExchangeTransactionContract` transactions with attacker-chosen `tokenId`/`quant` at will, with no special privileges, and can iterate transactions cheaply to search for/exploit favorable rounding, similar to how Mirror Protocol's attacker repeatedly interacted with the vulnerable oracle-priced markets.

### Recommendation
Force `SafeExchangeProcessor` (BigDecimal-exact math) as the sole processor for `ExchangeCapsule.transaction()`, removing the legacy `ExchangeProcessor` double-arithmetic path entirely (or making the hardened flag mandatory/always-on rather than proposal-gated), and add a maximum divergence assertion between requested and actual proportional output before committing balance updates in `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator`.

### Proof of Concept
Not independently reproducible from static analysis alone: the repo's own `ExchangeProcessorTest.testStrictMath` table of `(sellBalance, buyBalance, sellQuant)` triples already demonstrates concrete inputs where the legacy double-based `ExchangeProcessor` and the exact `SafeExchangeProcessor` diverge [4](#0-3) . An attacker would enumerate `(firstTokenBalance, secondTokenBalance, tokenQuant)` combinations off-chain (mirroring the on-chain pool state) to find trades where the double-math result exceeds the exact result, then submit `ExchangeTransactionContract` transactions with those parameters via `ExchangeTransactionActuator`, repeating to drain the pool. Full transaction-level PoC requires running the actual Java runtime against a live pool state and could not be executed in this read-only analysis; a background Devin/engineering session with code execution access is needed to construct and verify a concrete end-to-end exploit transaction sequence.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
