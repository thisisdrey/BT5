### Title
Unbounded `paths`/`attributes` lists in `GetFileAttributes` allow CPU/memory exhaustion via `CheckAttr` - (File: internal/gitaly/service/repository/file_attributes.go)

### Summary
`GetFileAttributes` accepts attacker-controlled `paths` and `attributes` lists with no upper bound and invokes `gitattributes.CheckAttrCmd.Check` once per path [1](#0-0) , and `CheckAttr` starts a single long-lived `git check-attr --stdin -z` process for the whole request with a per-answer read loop bounded by `count = len(names)` [2](#0-1) [3](#0-2) . Neither `validateGetFileAttributesRequest` nor `CheckAttr` caps the number of paths or attribute names [4](#0-3) , so a single RPC's cost scales with `len(paths) * len(attributes)`, which is attacker-controlled via the unary request message.

### Finding Description
The RPC handler `GetFileAttributes` validates only that `Repository`, `Revision`, `Paths`, and `Attributes` are non-empty — there is no cap on list length [4](#0-3) . It then loops over every `path` in `in.GetPaths()` and calls `checkAttrCmd.Check(path)` [1](#0-0) . Each `Check` call writes the path to `git check-attr`'s stdin and blocks reading `3 * count` NUL-delimited tokens back, where `count` is the number of requested attribute names [5](#0-4) . Because both `paths` and `attributes` are plain repeated string fields with no server-side limit, and gRPC's default max message size (~4MB, unless configured otherwise — this repo does not appear to override it based on searches) still permits tens of thousands of short strings, the attacker can submit large numbers of both, making the work quadratic in list sizes. This is a generic "many small strings in a request field" resource-amplification issue rather than the git-tree-walk-depth mechanism theorized in the question. I did not find any per-request or per-connection concurrency/CPU-time limiter in this code path that would cap it.

I could not verify with available tools whether the actual cost of `git check-attr --source <revision>` scales specifically with tree depth/width as hypothesized (i.e., that deeply nested `.gitattributes` files make each lookup meaningfully more expensive than a shallow tree) — that claim depends on `git check-attr`'s internal implementation, which is outside this repo. The concretely verifiable issue in this codebase is the missing bound on `len(Paths)` / `len(Attributes)` in the request, not a "quadratic in tree depth" argument-injection issue.

### Impact Explanation
A malicious but unprivileged user who can call `GetFileAttributes` (with a repository they can push to/import) can submit large `paths` and `attributes` lists in a single RPC, forcing the Gitaly node to spawn a `git check-attr` process and perform a correspondingly large amount of stdin/stdout round-tripping and response construction, consuming CPU and memory on the Gitaly node proportional to attacker-chosen input size. This matches a DoS-of-RPC-handler impact class, but is bounded by gRPC's default message-size ceiling and by any existing rate limiting on RPC calls that I was unable to fully verify in this session; the tree-depth-driven quadratic cost portion of the hypothesis is unverified.

### Likelihood Explanation
Reaching this code path requires only being able to call `GetFileAttributes` against a repository the attacker controls (own project, fork, or import) with a valid revision, which is achievable by any authenticated GitLab user with repo access — no special privilege is required. The request itself doesn't need a crafted tree; a large flat `paths`/`attributes` list suffices, making the attack straightforward and repeatable.

### Recommendation
Add explicit upper bounds on `len(in.GetPaths())` and `len(in.GetAttributes())` in `validateGetFileAttributesRequest` (e.g., reject requests with an unreasonably large number of paths/attributes), and consider imposing a maximum total request size or per-request CPU/time budget for the `check-attr` subprocess invocation.

### Proof of Concept
Not provided — the underlying premise that per-invocation cost is quadratic in *tree depth* could not be substantiated from this repository's code (that behavior would need to be verified against `git check-attr` itself), and no PoC demonstrating that specific mechanism could be constructed with confidence from available context. A more limited PoC (large flat path/attribute lists) would only demonstrate a generic unbounded-list issue, not the tree-depth-based scenario described in the question.

func (c CheckAttrCmd) Check(path string) (Attributes, error) {
	if strings.Contains(path, "\000") {
		return nil, fmt.Errorf("path with NUL byte not allowed")
	}

	c.m.Lock()
	defer c.m.Unlock()

	if _, err := c.stdin.WriteString(path + "\000"); err != nil {
		return nil, fmt.Errorf("write path: %w", err)
	}
	if err := c.stdin.Flush(); err != nil {
		return nil, fmt.Errorf("flush: %w", err)
	}

	attrs := Attributes{}
	buf := make([]string, 0, 3)

	// Using git-check-attr(1) with -z will return data in the format:
	// <path> NUL <attribute> NUL <info> NUL ...
	for i := 0; i < c.count; {
		word, err := c.stdout.ReadBytes('\000')
		if err != nil {
			return nil, fmt.Errorf("read line: %w", err)
		}

		buf = append(buf, string(bytes.TrimSuffix(word, []byte{0})))

		if len(buf) < 3 {
			continue // Keep going until we have 3 words
		}

		if buf[0] != path {
			return nil, fmt.Errorf("wrong path name detected, expected %q, got %q", path, buf[0])
		}
		if buf[2] != Unspecified {
			attrs = append(attrs, Attribute{Name: buf[1], State: buf[2]})
		}

		i++
		buf = buf[:0]
	}
