### Title
Unbounded per-address `UsageQueue` map growth in the unified scheduler enables attacker-driven memory exhaustion - (File: unified-scheduler-pool/src/lib.rs)

### Summary
The unified scheduler's `UsageQueueLoaderInner` maintains a `DashMap<Pubkey, UsageQueue>` that gains a new entry for every distinct account address seen across scheduled transactions, and the code itself documents that this map "grows memory usage in unbounded way." [1](#0-0)  This is structurally the same bug class as the Curves `ownedCurvesTokenSubjects` finding: a registry keyed by attacker-influenced addresses that only grows and is never proactively bounded at insertion time, relying entirely on best-effort background pruning.

### Finding Description
`UsageQueueLoaderInner::load` performs `entry(address).or_insert_with(...)` on a `DashMap<Pubkey, UsageQueue>` for every account address referenced by transactions the scheduler processes, unconditionally creating a new entry the first time an address is seen. [2](#0-1)  Any unprivileged user submitting ordinary transactions can reference an unbounded number of distinct, arbitrary account addresses (e.g., transfers/instructions to freshly-generated pubkeys that need not even hold funds) — these addresses do not need to be "real"/funded accounts to be locked and inserted into `usage_queues`, since the map is populated purely from account keys present in transaction messages, not from confirmed account existence. Removal is not immediate or bounded by the insertion path itself: it depends entirely on a separate "cleaner" mechanism (`solScCleaner`, referenced in the same doc comment) and an `is_overgrown` threshold check that only detects the problem after the count already exceeds `max_usage_queue_count`. [3](#0-2)  This mirrors the root cause of the Curves report exactly: a per-key collection that (1) grows on user-controlled input, (2) is not pruned inline when usage ends, and (3) is only cleaned up reactively/periodically rather than being bounded by construction.

### Impact Explanation
If the reactive cleaner cannot keep pace with the rate of new unique addresses introduced by a burst of attacker transactions (each transaction is cheap to construct with many novel addresses, e.g. up to the per-transaction account limit), the `usage_queues` DashMap can grow substantially between cleaner passes, inflating validator memory usage. Because insertion happens synchronously in the scheduling hot path for every transaction, sustained address diversity across a slot (or several) can cause persistent unbounded memory growth until the cleaner intervenes — a concrete unbounded-memory condition on an unprivileged code path, matching the accepted impact categories in scope (unbounded memory).

### Likelihood Explanation
Likelihood is moderate: constructing transactions that reference large numbers of distinct addresses is trivial and requires no privileged role, only fee-paying access, similar to how the Curves attacker only needed to hold arbitrary ERC20-like `curveTokens` to inflate a victim's array. However, unlike the Curves case (which had literally zero mitigation), this path already has a documented, if reactive, cleaning mechanism (`solScCleaner` + `is_overgrown`/`max_usage_queue_count`). I was not able to fully verify from the indexed content the exact trigger cadence/threshold of the cleaner or whether it can be starved or lags behind bursty address-diversity growth enough to cause a practically significant memory spike, so the severity here is bounded by an unverified mitigation rather than being a total absence of defense as in the original report.

### Recommendation
- Enforce an admission-time cap on `usage_queues` size (reject or evict-oldest before insert) rather than relying solely on a periodic reactive cleaner.
- Consider using a weak-reference/refcount-based eviction so entries are removed as soon as no in-flight task references them, rather than depending on the `is_overgrown` count threshold to catch runaway growth after the fact.
- Add explicit backpressure/metrics so operators can detect rapid `usage_queues` growth per slot and correlate it with the cleaner's actual reclamation rate.

### Proof of Concept
Conceptual PoC (not executed): An attacker crafts and submits a continuous stream of otherwise-valid, low-cost transactions where each transaction references many distinct, newly-generated (unfunded) pubkeys as accounts (e.g., as additional readonly/writable account metas alongside a minimal instruction). Each novel pubkey triggers `UsageQueueLoaderInner::load` to insert a new `UsageQueue` entry into the shared `DashMap`. [2](#0-1)  Sustaining this across many transactions/slots faster than `solScCleaner`'s reclamation cadence causes the map's memory footprint to grow, only being caught after crossing `max_usage_queue_count` via `is_overgrown`. [4](#0-3)  I could not execute or benchmark this locally within the scope of this analysis (index access only), so the actual magnitude of achievable memory growth versus the cleaner's effectiveness remains unverified and would need to be confirmed with a running node/benchmark.

/// The primary owner of all [`UsageQueue`]s used for particular [`PooledScheduler`].
///
/// Its `load` method provides `Pubkey`-based multi-thread-friendly `UsageQueue` lookup
/// with automatic population on initial entry misses, fulfilling the Pubkey-UsageQueue 1-to-1
/// mapping responsibility as documented by `UsageQueue`.
///
/// Currently, the simplest implementation. This grows memory usage in unbounded way. Overgrown
/// instance destruction is managed via `solScCleaner`. This struct is here to be put outside
/// `solana-unified-scheduler-logic` for the crate's original intent (separation of concerns from
/// the pure-logic-only crate). Some practical and mundane pruning will be implemented in this type.
#[derive(Debug)]
struct UsageQueueLoaderInner {
    capability: Capability,
    usage_queues: DashMap<Pubkey, UsageQueue>,
}

impl UsageQueueLoaderInner {
    fn new(capability: Capability) -> Self {
        Self {
            capability,
            usage_queues: DashMap::default(),
        }
    }

    fn load(&self, address: Pubkey) -> UsageQueue {
        self.usage_queues
            .entry(address)
            .or_insert_with(|| UsageQueue::new(&self.capability))
            .clone()
    }

    fn count(&self) -> usize {
        self.usage_queues.len()
    }
}

/// Thin wrapper to encapsulate ownership variation of UsageQueueLoaderInner across block
/// verification and production. This is needed to provide a uniform interface for the overgrown
/// check.
#[derive(Debug)]
enum UsageQueueLoader {
    // UsageQueueLoader is owned by this wrapper itself; used by block verification.
    OwnedBySelf {
        usage_queue_loader_inner: UsageQueueLoaderInner,
    },
}

impl UsageQueueLoader {
    fn usage_queue_loader(&self) -> &UsageQueueLoaderInner {
        match self {
            Self::OwnedBySelf {
                usage_queue_loader_inner,
            } => usage_queue_loader_inner,
        }
    }

    fn load(&self, pubkey: Pubkey) -> UsageQueue {
        self.usage_queue_loader().load(pubkey)
    }

    fn is_overgrown(&self, max_usage_queue_count: usize) -> bool {
        if self.usage_queue_loader().count() > max_usage_queue_count {
            return true;
        }

        match self {
            Self::OwnedBySelf {
                usage_queue_loader_inner: _,
            } => false,
        }
    }
}
