### Title
Missing `supportUnfreezeDelay()` governance-gate check in `WithdrawExpireUnfreezeProcessor` allows TVM-triggered unfreeze withdrawal even when the feature is disabled by committee - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java])

### Summary
The direct account-level actuator `WithdrawExpireUnfreezeActuator` gates withdrawal of expired unfrozen TRX behind the dynamic-property check `dynamicStore.supportUnfreezeDelay()`, but the equivalent TVM native-contract path (`WithdrawExpireUnfreezeProcessor`, invoked from the `withdrawExpireUnfreeze` opcode reachable by any smart contract) omits this check entirely. This is analogous to the reported Yolo bug: an outflow-gating guard is enforced on one code path but not on a functionally identical path that an unprivileged caller (here, any contract executing the corresponding TVM opcode) can reach.

### Finding Description
`WithdrawExpireUnfreezeActuator.validate()` (the path used for a plain `WithdrawExpireUnfreezeContract` transaction) explicitly requires the feature to be enabled: [1](#0-0) 

However, the TVM-facing counterpart used when a smart contract invokes the native "withdraw expired unfreeze" functionality via the VM opcode does not perform this check at all: [2](#0-1) 

This processor is invoked directly from `Program.withdrawExpireUnfreeze()`, which any deployed contract can call as part of its bytecode execution, with only `validate()`+`execute()` gating the operation: [3](#0-2) 

`supportUnfreezeDelay()` is backed by the `UNFREEZE_DELAY_DAYS` chain parameter, which is a committee-controlled proposal value (see references in `ProposalUtil.java` and `DynamicPropertiesStore.java`), meaning it is a governance-toggleable gate — the same class of "outflow allowed" switch described in the original report, just enforced inconsistently across two code paths that perform the same state transition (unlocking previously frozen TRX back into spendable balance).

### Impact Explanation
If the committee disables (or has not yet enabled, or later reduces/toggles) `UNFREEZE_DELAY_DAYS`/`supportUnfreezeDelay`, direct `WithdrawExpireUnfreezeContract` transactions are correctly blocked. But any smart contract can still bypass this governance decision by invoking the native `withdrawExpireUnfreeze` opcode, which uses `WithdrawExpireUnfreezeProcessor` and unconditionally releases matured unfrozen balance regardless of the feature flag. This breaks the intended consistency/atomicity of the governance-controlled freeze/unfreeze lifecycle and lets contract-based callers unlock funds that direct account holders are prevented from unlocking — an unauthorized fund-release path.

### Likelihood Explanation
Reachable by any account that deploys or calls a contract exercising the `withdrawExpireUnfreeze` VM operation; no special privilege is required. The only precondition is that the account has entries in `unfrozenV2List` with `unfreezeExpireTime <= now`, a normal state reachable through ordinary `UnfreezeBalanceV2` usage prior to the feature being toggled off. This makes the bypass trivially reachable whenever the flag state diverges between the two code paths.

### Recommendation
Add the same `dynamicStore.supportUnfreezeDelay()` check to `WithdrawExpireUnfreezeProcessor.validate()` that already exists in `WithdrawExpireUnfreezeActuator.validate()`, so the TVM-invoked path and the direct-transaction path enforce identical governance gating.

### Proof of Concept
1. Committee sets `UNFREEZE_DELAY_DAYS` such that `supportUnfreezeDelay()` returns `false` (feature disabled/not yet activated).
2. An account has matured entries in `unfrozenV2List` (expire time already passed) from a prior `UnfreezeBalanceV2` while the feature was enabled, or via any other state-reaching mechanism.
3. Sending a normal `WithdrawExpireUnfreezeContract` transaction fails validation with "Not support WithdrawExpireUnfreeze transaction..." per [1](#0-0) .
4. The same account instead deploys/calls a contract that executes the VM opcode invoking `Program.withdrawExpireUnfreeze()` → `WithdrawExpireUnfreezeProcessor.validate()`/`execute()`. Since this path never checks `supportUnfreezeDelay()`, the withdrawal succeeds and the balance is moved to `accountCapsule`'s spendable balance despite the committee-level restriction, as shown by the unconditional execute flow: [4](#0-3) .

  public long execute(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = ownerCapsule.getInstance().getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze <= 0) {
      return 0;
    }
    ownerCapsule.setInstance(ownerCapsule.getInstance().toBuilder()
        .setBalance(ownerCapsule.getBalance() + totalWithdrawUnfreeze)
        .build());
    List<Protocol.Account.UnFreezeV2> newUnFreezeList = getRemainWithdrawList(unfrozenV2List, now);
    ownerCapsule.clearUnfrozenV2();
    ownerCapsule.addAllUnfrozenV2(newUnFreezeList);
    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);
    return totalWithdrawUnfreeze;
  }
