### Title
Attacker fills a victim's per-account token list to `MAX_TOKENS_PER_USER` via dust deposits/transfers, blocking the victim from receiving new deposit-token types - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` tracks every deposit/debt token an account has ever held a nonzero balance of in `depositTokensOfAccount` / `debtTokensOfAccount` (`MappedEnumerableSet`). Any addition reverts once the combined length reaches `MAX_TOKENS_PER_USER` (30) via `onlyIfAdditionWillNotReachMaxTokens` ( [1](#0-0) ). Because `DepositToken._transfer` and `DepositToken._mint` push the token into the *recipient's* list without the recipient's consent ( [2](#0-1) [3](#0-2) ), and `deposit(amount_, onBehalfOf_)` mints to an arbitrary `onBehalfOf_` ( [4](#0-3) ), an attacker can pollute a victim's list at dust cost — the same bug class as the `@firebase/util` `deepExtend` prototype-pollution issue (attacker-controlled keys polluting a shared/borrowed object) reported in GHSA-fpm5-vv97-jfwg.

### Finding Description
- `DepositToken._mint` and `_transfer` call `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's prior balance was zero.
- `addToDepositTokensOfAccount` enforces `debtTokensOfAccount.length + depositTokensOfAccount.length < 30` and reverts with `UserReachedMaxTokens` otherwise ( [5](#0-4) ).
- The attacker deposits 1 wei of underlying of each listed deposit token with `onBehalfOf_ = victim` (or transfers 1 wei of each `msdToken` they hold). Each dust credit adds that token to the victim's list.
- Once the combined list length hits 30, *every* subsequent first-time mint/transfer/seize of a deposit token to the victim reverts inside `addToDepositTokensOfAccount`, propagating the revert through `deposit`, `transfer`, `transferFrom`, `Pool.seize`/`liquidate` proceeds directed at the victim, and SmartFarmingManager flows.
- Removal is only possible if the victim actively transfers the dust out (balance → 0 triggers `removeFromDepositTokensOfAccount`); with existing debt, locked-balance checks can further constrain cleanup.

### Impact Explanation
Temporary freezing/griefing of the victim's inflows: while the list is saturated, the victim cannot receive any deposit token not already in their list — new-collateral deposits, third-party transfers, liquidation-seize proceeds routed to them, and leverage flows targeting a new collateral all revert. This is a state-pollution DoS (not a gas/unbounded-loop DoS): the invariant broken is that an account can always accept a supported collateral. Existing balances remain withdrawable, so it is temporary freezing rather than permanent loss.

### Likelihood Explanation
Requires only an EOA calling public `deposit`/`transfer` with attacker-chosen beneficiary — no privileged role, oracle manipulation, or governance action. Cost is dust amounts of each enabled deposit token's underlying plus gas (≤30 entries). It is fully attacker-reachable but partially self-curable by the victim, which limits severity.

### Recommendation
Do not auto-register a token in `depositTokensOfAccount` on inbound transfers/mints the recipient didn't initiate, or make registration opt-in/explicit (e.g., only add on `deposit` when `onBehalfOf_ == _msgSender()`, or let accounts remove arbitrary entries). Alternatively, count only positions above a minimum balance, or drop the cap and iterate over protocol-level `depositTokens` with nonzero balances.

### Proof of Concept
```ts
// Hardhat / ethers — victim's list filled via dust deposits
// Setup: pool with N deposit tokens (msdA, msdB, ...) each wrapping an ERC20Mock

it('fills victim deposit token list to MAX and blocks new-token deposits', async () => {
  const max = (await pool.MAX_TOKENS_PER_USER()).toNumber(); // 30
  const depositTokens = await pool.getDepositTokens(); // governor-listed tokens

  // 1) Attacker deposits dust on behalf of victim for each deposit token
  for (let i = 0; i < depositTokens.length && i < max; ++i) {
    const msd = await ethers.getContractAt('DepositToken', depositTokens[i]);
    const underlying = await ethers.getContractAt('ERC20Mock', await msd.underlying());
    await underlying.mint(attacker.address, 1);
    await underlying.connect(attacker).approve(msd.address, 1);
    await msd.connect(attacker).deposit(1, victim.address); // onBehalfOf = victim
  }

  // victim's list is now saturated
  expect((await pool.getDepositTokensOfAccount(victim.address)).length).to.eq(max);

  // 2) Governor lists a NEW deposit token (or victim simply never held some token T)
  //    Any first-time credit of T to victim now reverts:
  await expect(
    newDepositToken.connect(victim).deposit(parseEther('10'), victim.address)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

  //    An unsolicited transfer of T to victim also reverts:
  await expect(
    newDepositToken.connect(attacker).transfer(victim.address, 1)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
});
```

Note: I could not fully verify the deployed deposit-token count per pool or whether any deposit path skips list registration; the attack assumes at least ~30 reachable deposit-token entries across a pool or enough listed tokens to saturate the cap — if a pool lists few deposit tokens, saturation requires combining with the victim's own `debtTokensOfAccount` entries or is infeasible on that deployment.
