### Title
Transaction priority formula lets low-value transactions buy outsized scheduling priority by declaring a minimal compute-budget footprint, evicting legitimately fee-paying transactions - (File: core/src/transaction_priority.rs)

### Summary
The StakeUp `depositTby` bug pays rewards proportional to a value (`amountMinted`) that is disconnected from the actual value/risk contributed, letting an attacker pick an extreme input (a TBY near maturity) to maximize reward-per-unit-of-real-contribution. Agave's transaction-scheduling priority formula has the same structural flaw: priority `P = R / (1 + C)` is computed from **user-declared, unverified** inputs (`compute_unit_limit`, `loaded_accounts_data_size_limit`) rather than from the transaction's real resource consumption. By declaring an artificially tiny compute/data budget while still paying a non-trivial absolute fee via a very high `compute_unit_price`, an unprivileged sender can inflate `P` far beyond what the transaction's real network cost/fee ratio justifies.

### Finding Description
Priority for both the in-scheduler queue and the sig-verify-adjacent forwarding path is computed in `calculate_priority_and_cost` in `core/src/transaction_priority.rs`: [1](#0-0) 

`cost` is derived via `CostModel::calculate_cost_for_executed_transaction` using the **requested** `transaction_configuration.compute_unit_limit` and `loaded_accounts_data_size_limit` — not the transaction's actual/likely resource usage: [2](#0-1) 

`reward` is the fee actually paid (`compute_unit_price * compute_unit_limit` plus base signature fee), computed via `solana_fee::calculate_fee_details`: [3](#0-2) 

The identical estimator is used pre-sanitization in the forwarding stage's `calculate_priority`, which also explicitly notes the estimate "doesn't need to be 100% accurate": [4](#0-3) 

The cost model's `calculate_loaded_accounts_data_size_cost` and `get_estimated_execution_cost` both key off attacker-supplied `ComputeBudgetInstruction` values (`SetComputeUnitLimit`, `SetLoadedAccountsDataSizeLimit`) rather than measured execution: [5](#0-4) 

Default (unset) `loaded_accounts_data_size_limit` is `MAX_LOADED_ACCOUNTS_DATA_SIZE_BYTES`, but a user can explicitly request a tiny value: [6](#0-5) 

Since `programs_execution_cost` is set directly to the *requested* `compute_unit_limit` (as confirmed by the cost-model tests), and `loaded_accounts_data_size_cost` scales off the *requested* size limit, both dominant, attacker-controlled cost terms can be driven to near-zero while `compute_unit_price` (which is unbounded and multiplies into the numerator `reward`) is set arbitrarily high. The denominator `C` collapses toward the small fixed overhead (signature/write-lock cost), while the numerator `R` can still be made non-trivial, producing a priority score wildly disproportionate to the transaction's true fee-per-cost ratio and to any other honest transaction that declares a realistic (larger) compute budget.

This inflated priority is inserted directly into the scheduler's bounded priority queue (`TransactionStateContainer`), which evicts the *lowest*-priority entries once full: [7](#0-6) 

A transaction that declares `compute_unit_limit = 1` will almost certainly fail during execution with `ComputationalBudgetExceeded` (as shown in the cost-adjustment test suite), contributing effectively nothing to the block, yet it can occupy the top of the priority queue and force out real, adequately-provisioned, higher-actual-value transactions: [8](#0-7) 

### Impact Explanation
This is a QoS-evasion / grossly-underpriced-pre-fee-work class issue: the network's transaction-admission and prioritization logic rewards a *declared* commitment rather than a *verified* one, letting any unprivileged sender's packets/transactions leapfrog the queue and evict legitimately-paying users' transactions from banking-stage buffers, degrading fair block-space allocation without commensurate cost to the attacker. Because both the scheduler-side (`transaction_priority.rs`) and pre-execution forwarding-stage estimator (`forwarding_stage.rs`) use the same unverifiable inputs, the exposure spans the full lifecycle from sig-verify/receive through scheduling.

### Likelihood Explanation
Reachable by any unprivileged transaction sender — no special stake, role, or validator/peer privilege required; only standard `ComputeBudgetInstruction` usage (`set_compute_unit_limit`, `set_compute_unit_price`, `set_loaded_accounts_data_size_limit`) available to any client. The comment in `forwarding_stage.rs` itself acknowledges the estimate is deliberately approximate ("doesn't need to be 100% accurate so long as close and consistent"), indicating the tradeoff was accepted but its adversarial-gaming surface via minimal declared budgets does not appear to be fully mitigated.

### Recommendation
Bound the achievable priority inflation, e.g.: enforce a floor on `compute_unit_limit`/`loaded_accounts_data_size_limit` used in the cost denominator (independent of what the transaction declares) so `C` cannot be driven arbitrarily low relative to the true minimum resource commitment a transaction represents; and/or cap effective `compute_unit_price` contribution relative to `compute_unit_limit` to prevent extreme price/limit combinations from producing disproportionate `R/C` ratios. Consider penalizing (lowering priority for) transactions with anomalously small declared budgets combined with anomalously high per-unit prices, and/or requeue/deprioritize transactions that fail execution due to `ComputationalBudgetExceeded` before they can evict other queued transactions.

### Proof of Concept
Conceptual PoC (based on `core/src/transaction_priority.rs` and `cost-model/src/cost_model.rs` logic):
1. Craft transaction A: `set_compute_unit_limit(1)`, `set_loaded_accounts_data_size_limit(1)` (minimum allowed), `set_compute_unit_price(u64::MAX)` — this makes `programs_execution_cost = 1` and `loaded_accounts_data_size_cost` minimal (one page), so `cost` collapses to fixed signature/write-lock overhead, while `reward` (fee) can still be sizable since price is maximal even though limit is 1.
2. Craft transaction B (legitimate): realistic `compute_unit_limit` (e.g., 200,000) with a modest, honest `compute_unit_price`.
3. Compute `calculate_priority_and_cost` for both per `core/src/transaction_priority.rs:32-66` — transaction A's `P = R/(1+C)` can exceed B's despite A contributing negligible real fee/resource value and being near-certain to fail with `ComputationalBudgetExceeded` on execution (per `core/tests/scheduler_cost_adjustment.rs:214-236`).
4. Flood the scheduler with many such transaction-A variants; `TransactionStateContainer::push_ids_into_queue` (`core/src/banking_stage/transaction_scheduler/transaction_state_container.rs:178-201`) will evict lower-priority entries — i.e., legitimate transaction B — once capacity is reached.

```rust
pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
    let fee_details = solana_fee::calculate_fee_details(
        transaction,
        bank.fee_structure().lamports_per_signature,
        transaction_configuration.priority_fee_lamports,
        bank.fee_features(),
    );
    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    (
        reward
            .saturating_mul(MULTIPLIER)
            .saturating_div(cost.saturating_add(1)),
        cost,
    )
```

```rust
fn calculate_priority(
    transaction: &RuntimeTransaction<SanitizedTransactionView<&[u8]>>,
    bank: &Bank,
) -> Option<u64> {
    let transaction_configuration = transaction
        .transaction_configuration(&bank.feature_set)
        .ok()?;

    // Manually estimate fee here since currently interface doesn't allow a on SVM type.
    // Doesn't need to be 100% accurate so long as close and consistent.
    let prioritization_fee = transaction_configuration.priority_fee_lamports;
    let signature_details = transaction.signature_details();
    let signature_fee = signature_details
        .total_signatures()
        .saturating_mul(bank.fee_structure().lamports_per_signature);
    let fee_details = FeeDetails::new(signature_fee, prioritization_fee);

    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    let cost = CostModel::estimate_cost(
        transaction,
        transaction.program_instructions_iter(),
        transaction.num_requested_write_locks(),
        &bank.feature_set,
    );
```

```rust
    fn get_estimated_execution_cost(
        transaction: &impl TransactionMeta,
        feature_set: &FeatureSet,
    ) -> (u64, u64) {
        // if failed to process compute_budget instructions, the transaction will not be executed
        // by `bank`, therefore it should be considered as no execution cost by cost model.
        let (programs_execution_costs, loaded_accounts_data_size_cost) =
            match transaction.transaction_configuration(feature_set) {
                Ok(config) => (
                    u64::from(config.compute_unit_limit),
                    Self::calculate_loaded_accounts_data_size_cost(
                        config.loaded_accounts_data_size_limit,
                        feature_set,
                    ),
                ),
                Err(_) => (0, 0),
            };

        (programs_execution_costs, loaded_accounts_data_size_cost)
    }
```

```rust
    fn push_ids_into_queue(
        &mut self,
        priority_ids: impl Iterator<Item = TransactionPriorityId>,
    ) -> usize {
        for id in priority_ids {
            self.priority_queue.insert(id);
        }

        // The number of items in the `id_to_transaction_state` map is
        // greater than or equal to the number of elements in the queue.
        // To avoid the map going over capacity, we use the length of the
        // map here instead of the queue.
        let num_dropped = self
            .id_to_transaction_state
            .len()
            .saturating_sub(self.capacity);

        for _ in 0..num_dropped {
            let priority_id = self.priority_queue.pop_first().expect("queue is not empty");
            self.remove_state(priority_id.id);
        }

        num_dropped
    }
```
