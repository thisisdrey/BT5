### Title
Liquidation DoS: borrower blocks `Pool.liquidate` by front-running with a dust `DebtToken.repay`, keeping underwater positions alive - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate` enforces `amountToRepay_.wadDiv(debtTokenBalance) <= maxLiquidable` against the debt balance read at execution time, while `amountToRepay_` is fixed calldata. An unprivileged borrower can front-run any liquidation transaction with a dust `repay` (1 wei) so that the liquidator's precomputed `amountToRepay_` exceeds the recalculated cap, forcing a revert on `AmountGreaterThanMaxLiquidable` (or on `RemainingDebtIsLowerThanTheFloor` when `debtFloorInUsd > 0`). This is repeatable for every liquidation attempt, producing a persistent availability failure of the liquidation path — the same bug class as CVE-2022-21531 (an input-triggered, repeatedly reproducible availability/crash condition in a core code path).

### Finding Description
In `Pool.liquidate` (contracts/Pool.sol:537-596):

- The position owner can call `DebtToken.repay(onBehalfOf=account_, amount_)` publicly to reduce `_debtTokenBalance` by an arbitrary dust amount. Repay is `whenNotShutdown` but never paused-gated for the borrower.
- The liquidator's transaction carries a constant `amountToRepay_` (typically `quoteLiquidateMax(...)` computed off-chain).
- At execution, `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` (line 567) reverts with `AmountGreaterThanMaxLiquidable` once the debt shrinks by even 1 wei.
- Alternatively, when `debtFloorInUsd > 0`, a dust repay can push the remaining debt below the floor so `_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd` (lines 571-579) reverts with `RemainingDebtIsLowerThanTheFloor`, unless the liquidator repays the full remaining debt — which `maxLiquidable` may forbid.
- `quoteLiquidateMax` (line 419) returns `_maxAmountToRepay = balance.wadMul(maxLiquidable)` from the same stale balance, so any off-chain-quoted amount is invalidated by the dust repay.

No modifier prevents this: `liquidate` only requires `whenNotShutdown`, `nonReentrant`, and registered token checks; `repay` is permissionless and `whenNotShutdown` only. `SynthContext`, supply caps, and the reentrancy guard do not interfere because the attack is two sequential transactions.

### Impact Explanation
Invariant broken: liquidation liveness/bounds. A borrower whose position turns unhealthy can permanently (or at least persistently) prevent liquidators from liquidating via ordinary EOA transactions, letting the position sink into bad debt. Result is protocol insolvency / permanent freezing of collateral backing the unpaid debt — every liquidation attempt crashes (reverts), mirroring the "frequently repeatable crash" availability impact of the CVE. The attacker's cost is dust synth repayments they already hold from issuance.

### Likelihood Explanation
The attacker is an ordinary borrower (unprivileged EOA); the trigger is a single public `repay` call front-running each observed `liquidate` tx in the mempool. It requires no privileged role, no oracle manipulation, and no special market conditions beyond having an unhealthy position — which the attacker can deliberately create by waiting for price movement or issuing at max LTV. A liquidator could partially bypass by calling `liquidate` from a contract that computes `quoteLiquidateMax` atomically in the same transaction, so the DoS applies to standard bot/EOA liquidation flows rather than all possible callers — this reduces severity to Medium, consistent with the reference CVSS.

### Recommendation
Make `liquidate` robust to intra-block debt changes: cap `amountToRepay_` to `min(amountToRepay_, balance.wadMul(maxLiquidable))` instead of reverting, or accept a `totalToSeize`-style parameter resolved at execution time. For the floor check, permit full repayment when the remaining debt would fall below `debtFloorInUsd` instead of reverting (i.e., clamp `amountToRepay_` to the full balance when `_newDebtInUsd` would be dust). Alternatively, document and support an atomic quote-and-liquidate entry point so liquidation cannot be invalidated by front-running.

### Proof of Concept
Hardhat fork sketch (deployed mainnet Pool, e.g., msUSD/msETH debt + msdMET collateral):

```ts
// 1. Borrower opens position, issues msETH up to near max CF.
await msETHDebt.connect(alice).issue(userMintAmount, alice.address);

// 2. Price drops -> position unhealthy.
await masterOracle.updatePrice(met.address, newMetPrice); // e.g. MET/2

// 3. Liquidator quotes and submits liquidation.
const amountToRepay = await pool.quoteLiquidateMax(msEth.address, alice.address, msdMET.address);
const liquidateTx = await pool.connect(liquidator).populateTransaction.liquidate(
  msEth.address, alice.address, amountToRepay, msdMET.address);

// 4. Attacker (alice) front-runs with dust repay of 1 wei.
await msEthDebt.connect(alice).repay(alice.address, 1);

// 5. Liquidator's tx now reverts: amountToRepay/wadDiv(newDebt) > maxLiquidable.
await expect(
  liquidator.sendTransaction(liquidateTx)
).to.be.revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

// 6. Repeat step 4 for every subsequent attempt -> liquidation path unavailable.
```

This matches the existing test scaffolding in `test/Pool.test.ts` (`describe('liquidate')`, debt-floor cases at lines 408-437) and requires only public entry points (`DebtToken.repay`, `Pool.liquidate`).
