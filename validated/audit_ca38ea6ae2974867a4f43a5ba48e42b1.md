### Title
Attachment download path stores oversized attachments without enforcing `AtlasConfig::attachments_max_size` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes peer HTTP responses via `decode_atlas_get_attachment` and inserts the resulting `Attachment` directly into `self.attachments` with no size check, and `AttachmentsDownloader::run` subsequently calls `AtlasDB::insert_instantiated_attachment` on it, which also performs no size check. This is unlike the transaction-attachment ingestion path (`posttransaction.rs`), which explicitly gates insertion behind `AtlasDB::should_keep_attachment` (checking `content.len() as u32 > attachments_max_size`). A malicious peer serving `GET /v2/attachments/<hash>` can therefore supply a hex-encoded attachment content blob larger than the node's configured `attachments_max_size` and have it silently stored.

### Finding Description
The intended invariant is: every stored attachment's `content.len()` must be `<= AtlasConfig::attachments_max_size`, as enforced by `AtlasDB::should_keep_attachment` [1](#0-0) , which is called from the mempool/contract-call attachment ingestion path before `insert_uninstantiated_attachment` [2](#0-1) .

However, the peer-to-peer Atlas attachment downloader never calls `should_keep_attachment`. `RPCGetAttachmentRequestHandler`'s client-side decode (`decode_atlas_get_attachment`) just JSON-decodes a hex string into an `Attachment` with no bound on length [3](#0-2) . `GetAttachmentResponse`'s `Deserialize` impl similarly just hex-decodes the whole string into `Attachment::new(bytes)` unconditionally [4](#0-3) .

`AttachmentsBatchStateContext::extend_with_attachments` takes these decoded responses and inserts them straight into the in-memory `self.attachments` set with no length check against `attachments_max_size`: `self.attachments.insert(response.attachment);` [5](#0-4) .

Finally, `AttachmentsDownloader::run`, upon reaching the `Done` state, persists every accumulated attachment via `network.atlasdb.insert_instantiated_attachment(&attachment)` [6](#0-5) , and `insert_instantiated_attachment` itself performs no size validation before writing the BLOB into the `attachments` table: [7](#0-6) .

The only bound on the attachment's size on this path is the generic HTTP message-size cap (`MAX_MESSAGE_LEN`, applied to the whole HTTP response body/stream in `httpcore.rs`), not the node-configured `attachments_max_size`. Since `attachments_max_size` is a runtime-configurable value (minimum `1_048_576` bytes but can be set smaller by relative comparisons, and more importantly the enforcement is asymmetric across ingestion paths), any remote peer that is queried for an attachment during the normal Atlas sync flow can return a JSON body containing a hex-encoded blob up to the HTTP layer's cap, and it will be accepted and written to the SQLite `attachments` table's `content` BLOB column, bypassing the `attachments_max_size` bound intended to cap per-attachment storage.

### Impact Explanation
Any Atlas peer that the node queries for an attachment (this happens automatically as part of routine BNS/Atlas attachment syncing whenever the node has an `AttachmentInstance` referencing an unknown hash) can cause the node to store attachment BLOBs whose size is bounded only by the HTTP message cap rather than by the operator-configured `attachments_max_size`. This is a bounded storage-amplification/DoS on a background sync path: each accepted oversized attachment consumes disk space in the AtlasDB beyond the configured budget, and the check meant to bound total disk usage per attachment (`should_keep_attachment`) is bypassed entirely for this ingestion path. This matches "bounded compute/storage DoS via a read/sync endpoint" (High) rather than a crash or forgery — it does not affect canonical chain state, does not forge on-chain data, and is bounded by the outer HTTP length cap, but it defeats an explicit operator-configured resource limit.

### Likelihood Explanation
- The attacker needs only to run a peer that the target node treats as an Atlas sync source (an outbound sync peer with a known data URL) — this is a normal, unprivileged interaction; no secret or privileged role is needed.
- The target node must have at least one `AttachmentInstance` referencing a content hash it doesn't yet have (a common, routine state during BNS/Atlas sync), which triggers `AttachmentsDownloader::run` to request the attachment from peers.
- The attacker crafts an oversized `GetAttachmentResponse` JSON body with hex content whose decoded length exceeds `attachments_max_size` but stays under `MAX_MESSAGE_LEN`.
- This is repeatable per distinct `AttachmentInstance`/content hash the node is trying to resolve, and the attacker can offer many distinct fake attachment instances (bounded by other Atlas queuing limits) to amplify storage usage.

### Recommendation
Add a size check against `AtlasConfig::attachments_max_size` on the attachment-download path, mirroring `should_keep_attachment`:
- In `AttachmentsBatchStateContext::extend_with_attachments` (stackslib/src/net/atlas/download.rs), after `decode_atlas_get_attachment`, reject (treat as failed request) any attachment whose `content.len() as u32 > attachments_max_size`.
- Additionally/defensively, add the same check inside `AtlasDB::insert_instantiated_attachment` (and `insert_uninstantiated_attachment`) so that no code path can bypass the configured maximum, regardless of caller.

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/download.rs` test module or `stackslib/src/net/atlas/tests.rs`):
1. Build an `AtlasConfig` with `attachments_max_size: 1024` (or the enforced minimum) and an `AtlasDB` from it.
2. Construct a `GetAttachmentResponse` whose `attachment.content` is, e.g., 10 MB of bytes (far exceeding `attachments_max_size`), hex-encode it into a fake `StacksHttpResponse` JSON body matching what `decode_atlas_get_attachment` expects.
3. Feed it through `AttachmentsBatchStateContext::extend_with_attachments` via a `BatchedRequestsResult` with `succeeded` containing this response, and observe that `self.attachments` now contains the oversized attachment (no rejection occurs) — assert `context.attachments.iter().next().unwrap().content.len() as u32 > atlas_config.attachments_max_size`.
4. Call `atlas_db.insert_instantiated_attachment(&oversized_attachment)` directly and assert it returns `Ok(())` rather than an error, then `atlas_db.find_attachment(&oversized_attachment.hash())` returns `Some` with the full oversized content — demonstrating the equality `stored content.len() <= attachments_max_size` is violated, in contrast to `AtlasDB::should_keep_attachment` which would return `false` for the same content given the same `contract_id`/config.

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }
