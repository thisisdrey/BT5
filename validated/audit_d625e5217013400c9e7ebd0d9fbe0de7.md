### Title
Griefing via dust `DepositToken` transfers fills victim's token list and permanently blocks their deposits — ([File: contracts/Pool.sol])

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` on the combined length of an account's `depositTokensOfAccount` and `debtTokensOfAccount` lists. `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to non-zero. An unprivileged attacker can deposit dust into the pool's collateral types and transfer 1 wei of each `DepositToken` to a victim, filling the victim's list to the cap. After that, any deposit, transfer-in, or liquidation `seize` that would add a new token to the victim's list reverts with `UserReachedMaxTokens`.

### Finding Description
- `Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are gated by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (contracts/Pool.sol:143-148, 204-220).
- `DepositToken._transfer` adds the token to the recipient's list on any 0→nonzero balance change, with no opt-in or minimum-amount check (contracts/DepositToken.sol:517-520).
- `DepositToken.transfer`/`transferFrom` are public and only check the *sender's* unlocked balance (`_revertIfLocked(sender_, ...)`); the recipient is never consulted (contracts/DepositToken.sol:348-376).
- The attacker only needs a non-zero balance, which `deposit()` provides for any dust `amount_` (contracts/DepositToken.sol:211-237).
- Analogous path on the debt side: `DebtToken` issuance adds to `debtTokensOfAccount` the same way, but debt issuance requires borrowing, so the deposit-token transfer path is the cheapest vector.
- Once the victim is at the cap:
  - `deposit()` into any collateral they don't already hold reverts inside `_mint` → `addToDepositTokensOfAccount` (DepositToken.sol:486-488).
  - Liquidations calling `DepositToken.seize` → `_transfer` revert for the liquidator/victim path when the seized-token recipient is at cap, degrading liquidation liveness (DepositToken.sol:343-345).
- The victim cannot remove entries themselves: entries are only removed when a balance returns to 0 (`removeFromDepositTokensOfAccount` is callable only by the token contract). The victim must transfer out each dust token one-by-one (30 transactions, plus the same griefing can be re-applied).

### Impact Explanation
Liveness violation / temporary freezing of funds: the victim is denied the ability to deposit new collateral types and to receive new deposit tokens (including via `seize` during liquidation). In a pool with ≥30 deposit-token offerings, a single unprivileged EOA can permanently block an arbitrary account's deposits for as long as they keep re-dusting, at a cost bounded by dust deposits in the pool's collateral tokens. Positions that need to add collateral to stay healthy may be pushed to liquidation because topping up with a *new* collateral type reverts.

### Likelihood Explanation
- Requires only unprivileged calls: `DepositToken.deposit` (dust) + `DepositToken.transfer` (1 wei) per token.
- Feasibility depends on the pool listing enough distinct deposit tokens (up to 30 attack entries; fewer needed if victim already holds tokens or has debt tokens).
- The attacker recovers nearly all cost by withdrawing their own dust afterward; only gas is consumed.
- No modifier blocks it: `whenNotPaused`, `nonReentrant`, `SynthContext` sender resolution, and `_revertIfLocked` all pass for the attacker; the cap check correctly reverts but protects the *system*, not the victim.

### Recommendation
Bound griefing by making list membership victim-controlled or free to evict, e.g.:
- Skip adding the recipient in `_transfer` when `amount_` is below a dust threshold, or
- Only track tokens that contribute meaningfully to collateral (e.g., add lazily in `deposit()`/`_mint` rather than on every `_transfer`), or
- Allow `removeFromDepositTokensOfAccount` to be called for tokens with zero balance so the victim can self-clean, or
- Drop the per-account enumerable lists in favor of iterating the global `depositTokens`/`debtTokens` sets.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "../contracts/Pool.sol";
import {DepositToken} from "../contracts/DepositToken.sol";

contract DustGriefTest is Test {
    Pool pool;               // deployed pool
    DepositToken[] dtokens;  // all deposit tokens registered in the pool
    address victim = address(0xV1C);
    address attacker = address(0xA77);

    function test_fillVictimListBlocksDeposits() public {
        uint256 max = pool.MAX_TOKENS_PER_USER(); // 30

        vm.startPrank(attacker);
        for (uint256 i; i < max; ++i) {
            DepositToken dt = dtokens[i];
            IERC20 underlying = dt.underlying();
            deal(address(underlying), attacker, 1);         // dust
            underlying.approve(address(dt), 1);
            dt.deposit(1, attacker);                        // mint dust msdTOKEN
            dt.transfer(victim, 1);                         // fills victim's list
            dt.withdraw(dt.balanceOf(attacker), attacker);  // recover remaining
        }
        vm.stopPrank();

        assertEq(pool.getDepositTokensOfAccount(victim).length, max);

        // Victim can no longer deposit a collateral type they don't already hold
        DepositToken newDt = dtokens[max]; // any not-yet-held token
        IERC20 u = newDt.underlying();
        deal(address(u), victim, 1e18);
        vm.startPrank(victim);
        u.approve(address(newDt), 1e18);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        newDt.deposit(1e18, victim);
        vm.stopPrank();
    }
}
```
