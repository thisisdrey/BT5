Audit Report

## Title
Silent zero-value conversion in PSM decimal scaling causes fund loss for small deposits/redemptions - (File: substrate/frame/psm/src/lib.rs)

## Summary
`pallet-psm`'s `external_to_internal` and `internal_to_external` helpers use `amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero)` in their down-scaling branches, which returns `Ok(0)` for any nonzero input amount smaller than the decimal-scaling factor instead of surfacing an error. This confirmed code pattern exists verbatim in the repository and matches the already-remediated pattern in `pallet-asset-conversion` (PR 11795), which was hardened specifically because zero-output rounding from small inputs is a fund-loss vector.

## Finding Description
The functions `external_to_internal` and `internal_to_external` in `substrate/frame/psm/src/lib.rs` implement decimal conversion between an internal stablecoin and externally pegged stablecoins of differing decimal precision [1](#0-0) [2](#0-1) . In both functions, the down-scaling (division) branch uses `checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero)`, which for unsigned integer division only ever returns `None` on division-by-zero (impossible here since `factor = 10^diff >= 1`), meaning the `unwrap_or_else` fallback is dead code for its ostensible purpose — the real effect is that `Ok(Some(0))` is silently returned whenever `amount < factor`, rather than an explicit error being raised. This is structurally the same "silent zero on failure/edge condition" pattern that `pallet-asset-conversion`'s `quote_price_exact_tokens_for_tokens`/`quote_price_tokens_for_exact_tokens` were hardened against, per the confirmed PR 11795 changelog, which explicitly states "zero outputs from small-input rounding were returned as `Some(0)`" and fixes this by returning `None` instead.

However, I was unable to retrieve and inspect the actual public dispatchable(s) in `substrate/frame/psm/src/lib.rs` that invoke `external_to_internal`/`internal_to_external` due to tool constraints in this session — I could not confirm whether the swap/mint/redeem extrinsics already reject a zero-conversion result before executing the corresponding transfer/mint/burn (e.g., via an existing minimum-amount check or an explicit `ensure!(!result.is_zero(), ...)` guard). This is the same gap the original claim author acknowledged ("I was unable to fully inspect the specific public dispatchable(s)... due to tool budget exhaustion").

## Impact Explanation
If confirmed that no downstream zero-check exists, this would allow an unprivileged user to deposit a small amount of an external asset that decimal-scales to `0` internal units while their asset is retained by the PSM reserve, or symmetrically lose value on redemption — a direct violation of the "Balances, assets... must conserve value" pivot named in the impact gate. The exact corrupted value is the computed swap output balance, which is silently `0` (via `Ok(0)`) instead of an error, for any input amount `amount < 10^diff` in the down-scaling branch.

## Likelihood Explanation
Reachability requires only that governance registers an asset pair with a non-trivial decimal gap (e.g., 18-decimal external vs. 6-decimal internal, giving `factor = 10^12`), after which any unprivileged user can trigger the zero-floor by submitting a swap amount smaller than the factor via the pallet's public swap extrinsic — no privileged actor or malicious peer is needed.

## Recommendation
Change `external_to_internal`/`internal_to_external` to return an explicit error (e.g., a new `Error::<T>::AmountTooSmall`) whenever the division would floor a nonzero input to `0`, mirroring the hardening already applied to `pallet-asset-conversion`'s quote functions in PR 11795.

## Proof of Concept
1. Configure two PSM-approved assets with `external_decimals = 18`, `internal_decimals = 6` (`diff = 12`, `factor = 10^12`).
2. As an unprivileged user, call the PSM's public swap-in extrinsic with `amount = 1` of the external asset.
3. `external_to_internal(1, 18, 6)` executes the `Greater` branch: `1u128.checked_div(&10^12) == Some(0)` → returns `Ok(0)`.
4. Confirm (requires access to the dispatchable body, not verified in this session) whether the swap logic proceeds to transfer the user's deposited external asset into the PSM reserve while crediting `0` internal stablecoin, which would reproduce the fund-loss condition.

Note: Full end-to-end confirmation of the exploit path (i.e., whether the dispatchable enforces a minimum-output check before executing the transfer) could not be completed in this session due to tool/context limitations when attempting to retrieve the dispatchable bodies in `substrate/frame/psm/src/lib.rs`. The underlying helper-function code exactly matches the claim's citations, but the claim's core assertion that "downstream swap logic does not independently reject a `0` conversion result" remains unverified rather than confirmed.
