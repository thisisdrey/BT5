The `gd_transfer_ownership` entrypoint in `contracts/global-deployer/src/contract.rs` is guarded by an explicit ownership check and a one-yoctoNEAR requirement before any state mutation occurs: `if !self.is_owner(&env::predecessor_account_id()) { return Err(Error::Unauthorized); }` [1](#0-0) . There is no two-step/pending-owner mechanism here (unlike some designs) — `new_owner_id` is set directly and atomically only after the caller is verified to be `self.0.owner_id` [2](#0-1) .

Critically, the global-deployer contract has no receiver/callee-invoked transfer-callback flow at all — it only exposes `gd_approve`, `gd_deploy`, and `gd_transfer_ownership`, none of which schedule a cross-contract callback that could let an attacker-controlled callee determine or influence the new owner [3](#0-2) . The premise in the question — "entering through a receiver or callee contract the attacker deployed, invoked during a transfer callback" — does not correspond to any code path in this file; `predecessor_account_id()` is checked synchronously within the same call, so a callee cannot inject itself as caller or manipulate the ownership check via return values, panics, or gas usage.

The existing test suite confirms non-owners are rejected: `bob.gd_transfer_ownership(...).await.assert_err_contains(Error::Unauthorized.to_string())` [4](#0-3) . Both sides of the claimed equality (`the account that can transfer ownership == the current owner at the time of the call`) hold: the check reads `self.0.owner_id` and compares it against `env::predecessor_account_id()` at call time, with no reachable path for a callback-invoked callee to alter this comparison.
