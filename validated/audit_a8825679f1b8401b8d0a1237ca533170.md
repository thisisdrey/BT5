### Title
`use_netrc` sends the user's `.netrc` **default** credential to *any* URL in the `urls` list, including attacker-controlled mirror/fallback URLs - (File: tools/build_defs/repo/utils.bzl)

### Summary
`use_netrc`, used by `get_auth` in the `http_archive`/`git_repository`-style repo-rule helpers, computes an `auth` dict for `ctx.download`. When a requested host is not explicitly listed in the parsed `.netrc`, but the user's `.netrc` contains a `default` entry (the special `""` machine), the login/password from that `default` entry is attached to the URL anyway. This is analogous to the "no validation on a sensitive credential-bearing field" class in the report (there, a privileged `owner` value is accepted unchecked; here, a scope-unbound credential is attached to hosts it was never declared for).

### Finding Description
`parse_netrc` stores the netrc `default` stanza under the special key `""`: [1](#0-0) 

`use_netrc` then extracts the host from each URL and, if the host is not present as an explicit `machine` entry, falls back to the `""` (default) credentials for that URL: [2](#0-1) 

There is no check that the URL's host matches anything the user actually intended to authenticate to — a `default` entry in `.netrc` is unconditionally broadcast to every unmatched host that later shows up in the `urls` list passed to `ctx.download`. `get_auth` (called from `http_archive`/`http_file`/`git_repository` via `http.bzl` and `git.bzl`) wires this straight from `ctx.attr.urls`, `NETRC` env var, or the user's home `.netrc`: [3](#0-2) 

The `urls` attribute of `http_archive`/`http_file` commonly contains multiple mirror URLs (the canonical origin plus fallback mirrors). If any of those URLs, or a redirect target reached during the fetch, points to an attacker-controlled or attacker-served host (e.g., a fallback mirror the attacker manages to have listed, or a maliciously redirected URL), that host — despite never being named in `.netrc` — will still receive the user's `default` netrc login/password, because `use_netrc` treats "no explicit machine entry" the same as "matches default."

### Impact Explanation
This results in credential exfiltration to an attacker-controlled host: a secret the user configured as a netrc "catch-all" (commonly intended for one specific service, e.g. a corporate artifact host) is silently sent in an HTTP `Authorization` header to any URL the build happens to fetch that is not covered by a more specific `machine` stanza, whenever a repository rule's `urls` list includes or is redirected to a hostile server. This matches the "credential exfiltration to an attacker-controlled host" impact class explicitly accepted for this scan.

### Likelihood Explanation
Exploitability depends on the victim having a `default` entry in their `.netrc` (a documented, supported netrc feature) and on an attacker being able to get one of the fetched URLs (mirror list entry, redirect target, or bzlmod-registry-provided URL) to point at a server they control — none of which requires MITM, malicious peer, or local machine access; it only requires the attacker to control content the build fetches (a mirror URL or redirect target), consistent with the "unprivileged, hostile origin server" threat model. This is a design/logic gap rather than a rare edge case, and it reproduces deterministically for any user with a netrc `default` entry.

### Recommendation
Do not treat the netrc `default` machine as authorization to send credentials to arbitrary unmatched hosts implicitly discovered through the `urls` list. At minimum: (1) require explicit opt-in (e.g., an attribute) before applying `default` credentials to a URL, (2) warn or fail loudly when a `default` credential is about to be sent to a host not present as an explicit `machine` entry, and (3) never apply `default` credentials to URLs reached only via redirect (which are not literally in the original `urls` attribute) without the same explicit host allow-listing that other credential helpers (e.g., `CredentialHelperProvider`, `Netrc` API scoping) enforce.

### Proof of Concept
1. Create `~/.netrc`:
```
machine legit.example.com
login alice
password s3cret

default
login alice-default
password s3cret-default
```
2. Define a repo rule (mirroring `test_use_netrc` in `src/test/shell/bazel/starlark_repository_test.sh`) that calls `get_auth(ctx, urls)` with:
```python
urls = [
  "https://legit.example.com/pkg.tar",
  "https://attacker.example.net/pkg-mirror.tar",
]
```
3. Inspect the resulting `auth` dict: `auth["https://attacker.example.net/pkg-mirror.tar"]` is populated with `login = "alice-default"`, `password = "s3cret-default"`, i.e., the default credential is attached to the attacker-controlled host even though `attacker.example.net` never appeared in `.netrc`.
4. This mirrors the existing test harness pattern for `use_netrc`/`get_auth`: [4](#0-3) 

which can be extended with a `default`-only `.netrc` entry and a URL for a host not present in the file, asserting that `auth` still contains credentials for that unrelated URL.

```text
def get_auth(ctx, urls):
    """Utility function to obtain the correct auth dict for a list of urls from .netrc file.

    Support optional netrc and auth_patterns attributes if available.

    Args:
      ctx: The repository context of the repository rule calling this utility
        function.
      urls: the list of urls to read

    Returns:
      the auth dict which can be passed to repository_ctx.download
    """
    if hasattr(ctx.attr, "netrc") and ctx.attr.netrc:
        netrc = read_netrc(ctx, ctx.attr.netrc)
    elif "NETRC" in ctx.os.environ:
        netrc = read_netrc(ctx, ctx.os.environ["NETRC"])
    else:
        netrc = read_user_netrc(ctx)
    auth_patterns = {}
    if hasattr(ctx.attr, "auth_patterns") and ctx.attr.auth_patterns:
        auth_patterns = ctx.attr.auth_patterns
    return use_netrc(netrc, urls, auth_patterns)
```
