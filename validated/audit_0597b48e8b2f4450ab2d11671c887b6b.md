## Analysis

The external report's core broken invariant: a permissionless caller can trigger a payout code path where accounting (`totalProcessed`) advances and a reward event fires even though the underlying transfer did not actually succeed, because the code never inspects the boolean success value returned from the low-level send.

The direct local analog is in Snowbridge's outbound-queue-v2 pallet, `process_delivery_receipt`, which pays the relayer reward without checking the `success` field of the `DeliveryReceipt` it just decoded and verified.

### Title
Relayer reward is paid on Snowbridge Outbound Queue V2 regardless of actual message execution success on Ethereum - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`DeliveryReceipt` carries a `success: bool` field decoded straight from the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event, which reflects whether the outbound message's commands actually executed on the Gateway contract. `Pallet::process_delivery_receipt` verifies the event log/proof and the gateway address, then unconditionally pays `order.fee` to the reward account and clears the pending order — the `success` flag is never read for gating the payment.

### Finding Description
`submit_delivery_receipt` is a permissionless, signed extrinsic [1](#0-0) . It decodes a `DeliveryReceipt` from the Ethereum event log via `DeliveryReceipt::try_from`, which includes a `success` field decoded from the `InboundMessageDispatched` event's `success` topic [2](#0-1) .

`process_delivery_receipt` then only checks `receipt.gateway` against the configured gateway address and looks up the `PendingOrder` by `receipt.nonce`. If `order.fee > 0`, it calls `T::RewardPayment::register_reward` unconditionally and removes the order, without ever branching on `receipt.success`: [3](#0-2) 

This mirrors the `FeeVault.withdraw()` bug exactly: a boolean success indicator produced by an underlying call (`SafeCall.send()` return value / Ethereum `success` topic) is decoded/available but discarded, and settlement state (`totalProcessed` / `PendingOrders` removal + reward payment) advances as if the operation fully succeeded.

### Impact Explanation
The message dispatch on Ethereum can fail for reasons unrelated to relayer misbehavior or a malicious validator — most notably gas griefing of the destination command execution, the same failure class as the `SafeCall.send()` out-of-gas scenario in the original report (the Gateway contract's dispatch of a command can run low on gas and revert/fail while the outer relay transaction that emits `InboundMessageDispatched` still succeeds, setting `success = false`). Because `process_delivery_receipt` ignores this flag, the relayer still collects the full `order.fee` reward even though the bridged message's commands never actually executed. This is a duplicate/incorrect settlement: reward payout state advances without the corresponding message execution actually completing, i.e., a "public underpriced work" and "duplicate settlement or payout" condition against BridgeHub's reward ledger (`T::RewardPayment`), draining reward funds for work that produced no effect on Ethereum.

### Likelihood Explanation
The extrinsic is called by `ensure_signed` — any account can submit it, no elevated privileges or relayer trust assumption is required beyond supplying a valid proof/event log, which is the normal expected workflow [4](#0-3) . `Verifier::verify` only proves the event log was included/committed on Ethereum — it does not, and cannot, force `success` to be `true`; a relayer merely needs a genuine (or self-induced) low-gas execution to emit a `false` success and still collect the reward. This requires no compromised relayer trust model, no governance action, and no node/validator collusion — purely exploiting a missing state check in this pallet's logic.

### Recommendation
Gate reward payment (and/or order lifecycle transition) on `receipt.success`:
```rust
if receipt.success {
    if order.fee > 0 {
        T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
    }
} else {
    // handle failed delivery: e.g. do not reward, optionally allow retry/refund path
}
<PendingOrders<T>>::remove(nonce);
Self::deposit_event(Event::MessageDelivered { nonce, success: receipt.success });
```

### Proof of Concept
1. A relayer submits an outbound message via the normal pipeline; `do_process_message` creates a `PendingOrder { nonce, fee, .. }` [5](#0-4) .
2. On Ethereum, the relayer (or anyone) submits the message to the Gateway with just enough gas to run the outer dispatch loop but insufficient gas for the actual command execution, causing the Gateway to emit `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer calls `submit_delivery_receipt` with a valid proof of that event. `T::Verifier::verify` succeeds (the log genuinely exists and is committed), `DeliveryReceipt::try_from` decodes `success = false`.
4. `process_delivery_receipt` checks `receipt.gateway` and `order.fee > 0`, then unconditionally calls `T::RewardPayment::register_reward(&reward_account, ..., order.fee)` and removes the order — reward is paid in full despite `success == false`.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
