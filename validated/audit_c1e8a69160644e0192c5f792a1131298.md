### Title
Unbounded `estimated_len` in `POST /v2/fees/transaction` causes integer-overflow panic/wrap in `estimate_tx_fee_from_cost_and_length` - (File: stackslib/src/net/api/postfeerate.rs)

### Summary
`RPCPostFeeRateRequestHandler::try_parse_request` accepts an attacker-controlled `estimated_len` field from the JSON request body with no upper bound check, and later `estimate_tx_fee_from_cost_and_length` multiplies this value by `MINIMUM_TX_FEE_RATE_PER_BYTE` using plain `u64` multiplication. An unauthenticated remote caller can set `estimated_len` to a large value (e.g., `u64::MAX`) to trigger an arithmetic overflow.

### Finding Description
The claimed equality — "the `estimated_len` used in fee math is bound by `MAX_PAYLOAD_LEN`/actual payload size" — is false. The handler only checks the HTTP `Content-Length` (`content_len`) against `MAX_PAYLOAD_LEN`: [1](#0-0) . That check bounds the size of the *JSON body*, not the numeric value of the `estimated_len` field inside it. The field itself is parsed as an unconstrained `Option<u64>`: [2](#0-1) , and then combined with the actual payload length via `max`, so a large attacker-supplied number always wins: [3](#0-2) .

This `estimated_len` is stored on the handler and passed straight into `estimate_tx_fee_from_cost_and_length`, where it is multiplied by `MINIMUM_TX_FEE_RATE_PER_BYTE` with no overflow guard: [4](#0-3) . In a debug build this `u64` multiplication panics on overflow (Rust inserts overflow checks in debug profile by default); in a release build (default `overflow-checks = false`), the multiplication silently wraps, producing a garbage `minimum_fee` value that is then returned to the caller as an authoritative fee estimate.

No other guard intervenes: there is no per-field cap on `estimated_len`, the estimator/metric call (`metric.from_cost_and_len`) does not validate the length either, and this endpoint requires no authentication (`security: []` in the OpenAPI spec) and is reachable by any remote peer able to connect to the node's RPC port.

### Impact Explanation
On debug/test builds (commonly used in CI and by some node operators, and definitely by the Rust test harness itself), a single crafted POST panics the thread handling the request, causing a crash/DoS of the public, unauthenticated `/v2/fees/transaction` endpoint. On release builds, the wrapped `minimum_fee` silently corrupts the returned fee estimate, which could mislead wallets/clients relying on this endpoint into submitting underpriced transactions (their real fee floor is bypassed) — a data-integrity issue on a read endpoint. This matches the "bounded compute DoS on a read endpoint" / crash category for a request handler reachable by any unprivileged remote caller, and it is trivially repeatable per request.

### Likelihood Explanation
No privileged role, secret, or special peer state is required — any remote client can send a single small, well-formed JSON POST to `/v2/fees/transaction` with `estimated_len: 18446744073709551615` (or similar) and a minimal valid hex-encoded `TransactionPayload`. Cost estimation must be configured on the node (`rpc_args.get_estimators_ref()` must return `Some`) for the code path to be reached — this is a common node configuration, not a security control. The attack is deterministic and repeatable.

### Recommendation
Bound `estimated_len` to a sane maximum (e.g., `MAX_PAYLOAD_LEN` or a dedicated maximum transaction size constant) in `try_parse_request`, rejecting requests whose `estimated_len` exceeds that bound. Additionally, use checked or saturating arithmetic (`checked_mul`/`saturating_mul`) for `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` in `estimate_tx_fee_from_cost_and_length` so that even if a large value slips through, it degrades gracefully instead of panicking or wrapping.

### Proof of Concept
1. In `stackslib/src/net/api/tests/postfeerate.rs`, add a test that builds a `FeeRateEstimateRequestBody` with `estimated_len: Some(u64::MAX)` and a valid minimal `transaction_payload` (as used in `test_try_parse_request`).
2. Drive it through `TestRPC::setup_with_rpc_args` with real fee/cost estimators configured (as in `test_try_make_response` case 3), then call `try_handle_request` (or run the full RPC round trip).
3. In a debug build assert the call panics (`std::panic::catch_unwind` should show a panic with "attempt to multiply with overflow" at `stackslib/src/net/api/postfeerate.rs:112`).
4. In a release-mode variant, assert instead that `response.estimations[i].fee` is not equal to the wrapped/truncated value that `u64::MAX * MINIMUM_TX_FEE_RATE_PER_BYTE` would produce, demonstrating silent corruption if overflow checks are disabled.
