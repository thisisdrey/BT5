### Title
Unpermissioned state commitment via dust `DepositToken` transfers/deposits lets anyone fill a victim's per-account token list to `MAX_TOKENS_PER_USER`, blocking deposits, borrowing and liquidations - (File: contracts/DepositToken.sol)

### Summary
The Kirby bug class is *missing authorization before committing intermediate state*: chunk data was written to storage before the upload-permission check ran. The Metronome analog is in `DepositToken._transfer`/`_mint` and `deposit(amount_, onBehalfOf_)`: any holder can push an entry into an arbitrary account's `depositTokensOfAccount` set (or `debtTokensOfAccount` count via `addToDepositTokensOfAccount`) without that account's consent. `Pool.addToDepositTokensOfAccount` is guarded only by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once the victim's combined `depositTokensOfAccount + debtTokensOfAccount` length reaches `MAX_TOKENS_PER_USER = 30`. An unprivileged attacker can therefore commit unwanted state to a victim's position bookkeeping and block their future position changes.

### Finding Description
- `DepositToken.transfer`/`transferFrom` only check the *sender's* unlocked balance via `_revertIfLocked` and then call `_transfer`, which calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero (contracts/DepositToken.sol:348-376, 517-520).
- `deposit(amount_, onBehalfOf_)` lets a caller mint deposit tokens to any `onBehalfOf_`, hitting the same `pool.addToDepositTokensOfAccount` path in `_mint` (contracts/DepositToken.sol:211-237, 485-488). The only check on `onBehalfOf_` is non-zero.
- `Pool.addToDepositTokensOfAccount` enforces `debtTokensOfAccount.length + depositTokensOfAccount.length < 30` (contracts/Pool.sol:79, 143-148, 216-220) but performs no consent/permission check on behalf of the recipient — analogous to chunk data being persisted before the permission check.
- The same revert propagates into `DebtToken` issuance paths (`issue` → `_mint` → `addToDebtTokensOfAccount`) and into `DepositToken.seize` during `Pool.liquidate`, since `seize` routes through `_transfer` to the liquidator.

### Impact Explanation
- **Liveness / temporary freezing of funds:** a victim whose list is filled to 30 cannot deposit into any new collateral token, cannot `issue`/`mint` any new synth debt, and cannot receive new deposit tokens — every such call reverts with `UserReachedMaxTokens`. If the victim is unhealthy (`_issuableInUsd == 0`), their `unlockedBalanceOf` is 0 for every token, so they cannot transfer the dust out to free slots; they also cannot add a new collateral to deleverage, and the received dust is permanently locked in their list.
- **Liquidation griefing → bad-debt risk:** `Pool.liquidate` calls `depositToken.seize(account, liquidator, ...)`, i.e. `_transfer` to the liquidator, which calls `addToDepositTokensOfAccount(liquidator)`. An attacker can fill a known liquidator/keeper EOA or contract's list to 30 so that liquidations of the attacker's (or others') underwater positions revert, delaying liquidation until bad debt accrues. The liquidator can clean slots only for tokens where it has unlocked balance.
- Cost to attacker is dust amounts of each whitelisted collateral (or near-zero-cost `transfer` of already-held dust); the check that would have prevented it (recipient consent / opt-in) is never performed.

### Likelihood Explanation
Feasibility depends on the number of whitelisted tokens: the attacker needs enough distinct registered `DepositToken`s (combined with tokens the victim already holds) to reach 30. On pools with many listed collaterals and synths this is reachable; on pools with few tokens it only works against victims already near the cap or against liquidators whose lists the attacker fills. No privileged role, no oracle manipulation, and no special timing is required — plain ERC20 transfers or dust `deposit(..., victim)` calls suffice. Modifiers do not stop it: `transfer` has no `nonReentrant`, `deposit` checks only existence/active flags, and `addToDepositTokensOfAccount` deliberately trusts the token contract caller.

### Recommendation
- Let the recipient opt out: e.g. make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` failure non-fatal in `_transfer`/`_mint` (skip adding instead of reverting), or maintain recipient-side accounting that tolerates unlisted balances.
- Alternatively, add an `allowance`-style opt-in for receiving deposit tokens, or restrict `deposit`'s `onBehalfOf_` so unsolicited deposits cannot create new list entries for third parties.
- For `seize`, consider sending to the liquidator without registering the token in their per-account list, so liquidation cannot be bricked by list exhaustion.

### Proof of Concept
Hardhat (fork against a deployed pool with ≥30 registered deposit tokens, or a local fixture that registers 30 fake deposit tokens):

```ts
// victim starts with an empty token list
expect(await pool.getDepositTokensOfAccount(victim)).to.be.empty

// attacker deposits 1 wei of each registered collateral on behalf of victim
for (const dt of depositTokens /* length >= 30 */) {
  const underlying = await ethers.getContractAt('ERC20', await dt.underlying())
  await underlying.approve(dt.address, 1)
  await dt.deposit(1, victim.address) // mints dust, calls addToDepositTokensOfAccount(victim)
}

expect(await pool.depositTokensOfAccountLength(victim)).to.eq(30)

// victim can no longer deposit into a new collateral or issue new debt
await expect(newDepositToken.deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')
await expect(debtToken.issue(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')

// liquidation griefing: fill a liquidator's list, then seize() reverts
await expect(pool.liquidate(syntheticToken, victimUnderwater, amount, liquidator))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

If the victim has an unhealthy position, `unlockedBalanceOf(victim) == 0` for every deposit token (contracts/DepositToken.sol:383-398), so the dust cannot be transferred out and the slots stay occupied until the position is liquidated or repaid.
