### Title
Attacker can dust-grief a victim's deposit-token list to cap `MAX_DEPOSIT_TOKENS`, causing `ReachedMaxDepositTokens` reverts on victim deposits and inbound transfers - (File: contracts/Pool.sol, contracts/DepositToken.sol)

### Summary
Analogous to the kernel bug (a hard `WARN_ON` on a state that is actually reachable, turning a benign race into a panic/DoS), `Pool.addToDepositTokensOfAccount` hard-reverts with `ReachedMaxDepositTokens` when an account's `MappedEnumerableSet` of deposit tokens is full. An unprivileged attacker can force any victim into that "unexpected" state at will by dust-transferring every whitelisted `DepositToken` to them, so the hard revert becomes attacker-reachable.

### Finding Description
- `DepositToken._transfer` and `DepositToken._mint` call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance transitions from 0 to positive (`contracts/DepositToken.sol:486-488`, `517-520`). There is no opt-out or allowance gating — any holder of a deposit token can push a new entry into any address's per-account list.
- `Pool.addToDepositTokensOfAccount` enforces a per-account cap (`MAX_DEPOSIT_TOKENS_PER_USER`) and reverts `ReachedMaxDepositTokens` once the victim's `MappedEnumerableSet` is full (`contracts/Pool.sol`; error also present in deployed `Pool`/`Pool1`/`Pool2` ABIs). `MappedEnumerableSet._add` appends unconditionally when the value is absent (`contracts/lib/MappedEnumerableSet.sol:22-31`); the cap check lives in the Pool wrapper, not the set.
- Attack path: the attacker obtains a dust amount of each deposit token (by depositing minimal collateral into each market via `Pool.deposit`, or buying them), then calls `DepositToken.transfer(victim, dust)` for each token. Each transfer adds one entry to `depositTokensOfAccount[victim]` until it reaches the cap.
- Once full, any transaction that would add a new entry for the victim reverts: the victim's own `deposit` into a collateral type they don't yet hold, and any transfer/mint of a new deposit token to the victim, all fail inside `addToDepositTokensOfAccount`.

### Impact Explanation
Temporary freezing of funds / liveness break: the victim cannot deposit into any additional collateral market and cannot receive any deposit token they don't already hold until they free a slot (by fully withdrawing or transferring out one of their existing positions, which triggers `removeFromDepositTokensOfAccount` in `DepositToken._transfer`/`_withdraw`). The attacker can also repeatedly re-fill freed slots each time the victim clears one, extending the DoS indefinitely at dust cost, and can front-run a victim's legitimate `deposit` to keep them permanently locked out of new collateral types — e.g., preventing them from adding collateral to avoid liquidation is a real loss vector.

### Likelihood Explanation
The attack requires only unprivileged EOA calls: `deposit` (or acquire) dust of each whitelisted deposit token and N `transfer` calls. Cost is bounded by gas plus negligible dust principal, which the attacker can even recover by burning/repaying their own dust positions afterward. There is no incentive needed beyond griefing; blocking a victim from adding collateral right before liquidation produces concrete profit via the liquidation bonus.

### Recommendation
Replace the hard revert with graceful handling (the same fix pattern as removing the `WARN_ON`): make `addToDepositTokensOfAccount` return a bool and let `_transfer`/`_mint` either skip the accounting entry or revert only for the *sender-initiated* deposit path. Alternatively, require the recipient's explicit opt-in (e.g., only add entries on `deposit`, never on `transfer`), or allow permissionless removal of dust entries via a sweep function so griefed entries are cheap to clear.

### Proof of Concept
```solidity
// Foundry fork-style PoC (hardhat/foundry test harness in repo)
function test_dustGrief_blocksVictimNewCollateral() external {
    // attacker deposits minimal collateral in every whitelisted deposit token market
    for (uint i = 0; i < pool.getDepositTokens().length; i++) {
        IDepositToken dt = pool.getDepositTokens()[i];
        deal(address(dt.underlying()), attacker, 1e6);
        vm.startPrank(attacker);
        dt.underlying().approve(address(pool), 1e6);
        pool.deposit(dt, 1);              // attacker gets dust msdTOKEN
        dt.transfer(victim, 1);           // fills depositTokensOfAccount[victim]
        vm.stopPrank();
    }
    assertEq(pool.getDepositTokensOfAccount(victim).length, MAX);

    // victim now cannot deposit a collateral type they don't already hold
    deal(address(newUnderlying), victim, 1e18);
    vm.startPrank(victim);
    newUnderlying.approve(address(pool), 1e18);
    vm.expectRevert(IPool.ReachedMaxDepositTokens.selector);
    pool.deposit(newDepositToken, 1e18);
    vm.stopPrank();
}
```
