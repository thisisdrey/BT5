### Title
Unprivileged attacker can fill a victim's `depositTokensOfAccount`/`debtTokensOfAccount` lists with dust transfers to permanently block new collateral deposits and force liquidations - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once a user's combined token lists reach `MAX_TOKENS_PER_USER = 30` [1](#0-0) [2](#0-1) . These per-account entries are added automatically whenever a `DepositToken` or `DebtToken` balance goes from `0` to non-zero, including on ordinary `transfer`/`transferFrom` calls [3](#0-2) . Any EOA can therefore dust-transfer 1 wei of every deposit token to a victim and permanently DoS that victim's ability to (a) deposit any collateral type they don't already hold, (b) mint a synthetic they don't already owe, and (c) receive deposit-token transfers — with no privileged role and no way for the victim to preemptively block inbound dust.

### Finding Description
- In `DepositToken._transfer`, a first-time positive balance triggers `pool.addToDepositTokensOfAccount(recipient_)` [3](#0-2) . `_mint` does the same for deposits [4](#0-3) . `DebtToken` mirrors this via `addToDebtTokensOfAccount` on issue/transfer.
- `Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are gated only by `_revertIfSenderIsNotDepositToken`/`_revertIfSenderIsNotDebtToken` (i.e., the token contract itself must call them) plus `onlyIfAdditionWillNotReachMaxTokens` [5](#0-4) . There is no opt-in by the recipient.
- Attack path, entirely unprivileged:
  1. Attacker calls `Pool.deposit` (or `NativeTokenGateway`/`VesperGateway`) to acquire a tiny balance of each of the pool's deposit tokens.
  2. For each deposit token `msdX`, attacker calls `msdX.transfer(victim, 1)`. Each call adds `msdX` to `victim`'s `depositTokensOfAccount` [6](#0-5) .
  3. After 30 (minus existing) distinct entries, every subsequent call that would add a new entry to the victim reverts inside `onlyIfAdditionWillNotReachMaxTokens` [2](#0-1) . Since `_transfer`, `_mint`, and `DebtToken.issue` propagate the revert, the whole transaction fails — there is no way for `deposit`, `transfer`, or `issue` to succeed for a new token.
- Cleanup is asymmetric: the victim can transfer the dust back out to free a slot (`_balanceAfter == 0` → `removeFromDepositTokensOfAccount` [7](#0-6) ), but each freeing tx costs gas, must be done per-token, and the attacker can refill slots in the same or next block. Crucially, a slot only frees if the victim's balance for that token goes fully to zero, which requires finding and spending dust across 30 tokens — while any liquidation or time-critical deposit attempt reverts in the meantime.

### Impact Explanation
Temporary freezing of funds / forced liquidation. The broken invariant is liveness of the deposit/receive path. Concretely:
- A victim with an unhealthy position who needs to deposit a collateral type they do not yet hold cannot do so — `deposit` reverts at `addToDepositTokensOfAccount` — so their position is forcibly liquidated even though they hold sufficient collateral to cure it. The liquidation fee/seize split then transfers value from the victim to liquidators.
- A victim cannot receive any deposit-token transfer of a new type (e.g., OTC settlement, smart-farming unwind proceeds), freezing inbound funds at the sender.
- A victim cannot mint a new synthetic (`DebtToken.issue` → `addToDebtTokensOfAccount` reverts), DoS-ing borrowing for the victim across all synths they don't already hold.

### Likelihood Explanation
Fully unprivileged: the attacker only needs dust amounts of each listed collateral (obtainable via the public `deposit` entry point or gateways) and ~30 cheap ERC20-style transfers. No governor/keeper/oracle cooperation, no oracle manipulation, no flash loan required. Cost scales with the number of listed deposit tokens but each action is a single cheap transfer; sustaining the grief only requires re-topping slots the victim clears. It does not rely on unbounded-loop gas DoS — the revert is an explicit `MAX_TOKENS_PER_USER` check inside a bounded set operation [2](#0-1) .

### Recommendation
- Do not auto-register a token on plain `transfer`/`transferFrom` receipt; only register on `deposit`/`mint` initiated by the account itself (or via `permit`-style opt-in), e.g., move `addToDepositTokensOfAccount` out of `_transfer` and into a `Pool.deposit`-driven path that checks the real depositor via `SynthContext._msgSender()`.
- Alternatively, make `deposit`/`issue` tolerate a full list by first sweeping zero-balance entries, and/or allow the account to `removeFromDepositTokensOfAccount` itself for any token with zero balance so cleanup is a single call.
- Cap only tokens counted toward health/debt calculations rather than the raw balance list.

### Proof of Concept
Hardhat (fork or local) sketch against deployed `Pool`/`DepositToken`:

```ts
// victim has an unhealthy position (or none) — attacker needs no role
const pool = await ethers.getContractAt('Pool', POOL);
const depositTokens: IDepositToken[] = await Promise.all(
  (await pool.getDepositTokens()).map(a => ethers.getContractAt('DepositToken', a))
);

// 1) attacker seeds itself with 1 wei of each deposit token
for (const msd of depositTokens) {
  const underlying = await ethers.getContractAt('IERC20', await msd.underlying());
  await underlying.connect(attacker).approve(pool.address, 1);
  await pool.connect(attacker).deposit(underlying.address, 1); // mints msd to attacker
}

// 2) dust-transfer to victim until list is full
for (const msd of depositTokens) {
  if ((await pool.getDepositTokensOfAccount(victim.address)).length +
      (await pool.getDebtTokensOfAccount(victim.address)).length >= 30) break;
  await msd.connect(attacker).transfer(victim.address, 1);
}

// 3) victim tries to deposit a collateral type it doesn't hold -> reverts
const newToken = depositTokens.find(t => /* not in victim list */);
const underlying = await ethers.getContractAt('IERC20', await newToken.underlying());
await underlying.connect(victim).approve(pool.address, amount);
await expect(
  pool.connect(victim).deposit(underlying.address, amount)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens'); // bubbles from addToDepositTokensOfAccount

// 4) if victim's position is unhealthy, liquidate succeeds while cure is blocked
await pool.connect(liquidator).liquidate(synth, victim.address, amountToRepay, depositTokenToSeize);
```

All calls use public entry points only (`Pool.deposit`, `DepositToken.transfer`, `Pool.liquidate`); the revert path is `DepositToken._mint/_transfer → Pool.addToDepositTokensOfAccount → onlyIfAdditionWillNotReachMaxTokens`. No pause flag, reentrancy guard, or SynthContext check prevents it, since the max-tokens check runs before any of those would matter for the victim's deposit.
