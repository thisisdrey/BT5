### Title
Fake `#[randomness]` Annotation Bypasses On-Chain Validation, Forcing Unnecessary Randomness Aggregation — (`types/src/vm/module_metadata.rs` / `consensus/src/pipeline/pipeline_builder.rs`)

---

### Summary

An unprivileged attacker can publish a Move module where a private/friend entry function carries a `#[randomness]` annotation but makes no randomness API calls. The on-chain metadata validator (`is_valid_unbiasable_function`) only checks that the annotated function is a non-public entry function; it never verifies that the function actually invokes the randomness module. As a result, `rand_txns_check` in the consensus pipeline reads the annotation from on-chain metadata and sets `need_randomness = true`, forcing every block that contains the attacker's transaction to stall at the `wait_for_rand` stage until full randomness aggregation completes. This breaks the invariant that only genuine randomness-consuming transactions trigger aggregation and causes material throughput degradation for all users sharing those blocks.

---

### Finding Description

**Step 1 — Module publish (compiler level)**

`check_and_record_unbiasabale_entry_functions` in `extended_checks.rs` records any function bearing `#[randomness]` into `fun_attributes` without verifying that the function actually calls the randomness module. [1](#0-0) 

`check_unsafe_randomness_usage` only fires an error when a non-public entry function *calls* randomness *without* the attribute — the converse (attribute present, no randomness call) is never checked. [2](#0-1) 

So the following module compiles without error and its metadata records `fake` with a randomness annotation:

```move
module attacker::fake_rand {
    #[randomness]
    entry fun fake() { /* no randomness call */ }
}
```

**Step 2 — On-chain publish validation**

`validate_publish_request` calls `verify_module_metadata_for_module_publishing`, which calls `is_valid_unbiasable_function` for every function whose metadata carries a randomness attribute. [3](#0-2) 

`is_valid_unbiasable_function` accepts the annotation if and only if the function is a non-public entry function — it performs no check on whether the function body actually invokes the randomness module. [4](#0-3) 

The module is published on-chain with the fake annotation intact.

**Step 3 — Transaction submission and `rand_txns_check`**

When a block containing a transaction that calls `attacker::fake_rand::fake` is ordered, `rand_txns_check` iterates over user transactions, fetches the on-chain module, and calls `get_randomness_annotation_for_entry_function`. [5](#0-4) 

`get_randomness_annotation_for_entry_function` looks up the function name in `fun_attributes` and returns the annotation — it has no way to know the annotation is fake. [6](#0-5) 

`need_randomness` is set to `true` and the function returns `Ok(true)`. [7](#0-6) 

**Step 4 — Block stalls at `wait_for_rand`**

`wait_for_rand` awaits `rand_rx` only when `need_randomness == true`, blocking the Execute stage until the consensus-driven randomness aggregation delivers a value. [8](#0-7) 

In `rand_manager`, `AggregationResult::Skip` is sent only when `need_rand == false`; with `need_rand == true` the full share-broadcast and threshold-aggregation protocol runs. [9](#0-8) 

The pipeline README confirms: "execution **cannot** proceed optimistically — it must wait for the randomness value, which blocks the Execute stage and prevents optimistic execution from overlapping with consensus." [10](#0-9) 

---

### Impact Explanation

Every block that contains even one transaction calling the attacker's annotated function is forced through full randomness aggregation before it can execute. This:

- Disables optimistic (Zaptos) execution for those blocks, adding the full randomness aggregation round-trip to their latency.
- Forces the rand manager to run share broadcasting and threshold aggregation for blocks that produce no randomness output, consuming validator CPU and network bandwidth.
- Degrades throughput and increases latency for all users whose transactions land in the same block as the attacker's, without any benefit to the attacker beyond the disruption itself.

The attacker pays only normal gas fees per transaction; the cost is borne by the entire network.

---

### Likelihood Explanation

The attack requires only a standard module publish (no privileged keys, no validator access) followed by repeated entry-function calls. The module compiles with the standard Move toolchain. The missing check is in the on-chain validator, so no bytecode crafting is needed. Any account with sufficient APT for gas can execute this continuously.

---

### Recommendation

`is_valid_unbiasable_function` should be extended to verify that the annotated function's bytecode actually calls into the `0x1::randomness` module (or at minimum that it has a dependency on it). Alternatively, `verify_module_metadata_for_module_publishing` should replicate the call-graph check that `check_unsafe_randomness_usage` performs at compile time, rejecting any module whose metadata claims `#[randomness]` for a function that does not transitively call a `0x1::randomness` function.
