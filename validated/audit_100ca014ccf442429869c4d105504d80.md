### Title
Floating-point rounding in `ExchangeProcessor`'s Bancor-relay math can produce unbacked token amounts / free swaps in TRX↔TRC10 Exchange — ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The reported StableMath bug is a rounding-direction issue in a swap-invariant formula that can let an attacker receive tokens without paying the correct input (or that only degrades at small balances). The closest reachable analog in java-tron is the on-chain **Bancor-relay exchange** (`ExchangeCreate/Inject/Withdraw/TransactionContract`), whose default (non-hardened) calculation path performs the swap math in IEEE-754 `double` precision via `Math.pow`, then truncates to `long`. Just like `_calcOutGivenIn`/`_getTokenBalanceGivenInvariantAndAllOtherBalances`, this arithmetic has no guaranteed, protocol-enforced rounding direction, so an attacker can construct balances/quantities where floating point error rounds in the attacker's favor, extracting value (dust or larger) that is not backed by their deposited input.

### Finding Description
`ExchangeCapsule.transaction()` chooses between two implementations of the `Processor` interface: [1](#0-0) 

When `hardenedCalc` is false (the default, unless the committee has enabled `allowHardenExchangeCalculation` via proposal), it uses `ExchangeProcessor`, which computes the Bancor formula purely with `double` and `Math.pow`, then casts to `long` (truncating, not doing an invariant-derived rounding rule): [2](#0-1) 

This mirrors the Balancer bug exactly: the “invariant” calculation (`exchangeToSupply`) and the “solve-for-balance” calculation (`exchangeFromSupply`) are two independent floating-point operations chained together (an amount is round-tripped through an implied virtual `supply`), and neither is defined to consistently round in the protocol's favor. Floating point `pow`/multiplication/subtraction error compounds across the two steps, so the final truncation `(long) exchangeBalance` can end up either above or below the mathematically "fair" value depending on the specific balances/quantities chosen — precisely the "round up or down according to their values" condition flagged in the external report.

The `SafeExchangeProcessor` variant (only used when `allowHardenExchangeCalculation` is enabled) attempts to fix this by using `BigDecimal` with 18-digit precision and explicit `RoundingMode.DOWN` on the final result: [3](#0-2) 

The existence of this parallel "hardened" implementation strongly indicates java-tron's own maintainers recognized the `double`-based `ExchangeProcessor` math is unsafe/imprecise — but it is gated behind a governance proposal rather than always being enforced, so any chain where the proposal hasn't been activated (or before it is activated) uses the vulnerable path by default.

`ExchangeTransactionActuator.execute()` reaches this code directly from an unprivileged, ordinary `ExchangeTransactionContract` broadcast by any account: [4](#0-3) 
and the same computed `anotherTokenQuant` is what actually credits/debits the account and the exchange pool balances — there is no independent sanity/invariant check ensuring the pool's `k` (or equivalent) never decreases.

### Impact Explanation
If an attacker can find input values (`sellTokenBalance`, `buyTokenBalance`, `sellTokenQuant`) where the `double`/`Math.pow` truncation rounds up in the receiver's favor, the attacker can receive a `anotherTokenQuant` slightly larger than the fair-value amount, extracting real TRX/TRC10 value from the exchange pool that is not backed by an equivalent deposit. Repeated small trades (dust extraction) can compound this into a real drain over many transactions, directly matching "attacker receiving free tokens... via dust accumulation" in the external report. This is a fund-theft/unbacked-balance class issue reachable by any account via a normal transaction (`ExchangeTransactionContract`), no special privileges required.

### Likelihood Explanation
Exploitability requires finding pool balances/quantities where floating-point rounding favors the attacker — the same "high difficulty" characterization given to the original StableMath finding. It's not guaranteed to work for every state, but because `ExchangeProcessor` is the **default** path (hardened math is opt-in via governance proposal), and Exchange contracts/state are fully attacker-controllable inputs (attacker can create their own exchange, inject arbitrary quantities, and choose trade sizes), an attacker has full freedom to search/brute-force for favorable rounding conditions across many self-created exchanges, similar to how the Balancer researchers searched for an exploitable state.

### Recommendation
- Make the `BigDecimal`/rounding-down `SafeExchangeProcessor` path (or an equivalent fixed-point, explicitly-rounded implementation) the default and only implementation for on-chain Exchange math, rather than gating it behind `allowHardenExchangeCalculation`.
- Ensure rounding is always performed against the protocol/pool (i.e., truncate `anotherTokenQuant` down when it benefits the trader, and round remaining pool balances in the pool's favor), consistent with `_calcOutGivenIn`'s "round down overall" mitigation recommended in the original report.
- Add an invariant check (analogous to “outGivenIn must not increase invariant/k in a way that benefits attacker”) before crediting `anotherTokenQuant` in `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator`.
- Remove the deprecated `Maths`/`MathWrapper` double-precision helpers from any monetary calculation path (`ExchangeProcessor.exchangeToSupply/exchangeFromSupply`).

### Proof of Concept
Concrete numeric inputs that trigger favorable floating-point rounding could not be derived analytically without executing `ExchangeProcessor` (this requires numerically searching `Math.pow` truncation behavior similar to the Echidna-based search the auditors used for `StableMath`). Conceptually the PoC pattern is:
1. Attacker creates an `Exchange` (via `ExchangeCreateContract`) with self-chosen `firstTokenBalance`/`secondTokenBalance`.
2. Attacker calls `ExchangeTransactionContract` (routed through `ExchangeCapsule.transaction` → `ExchangeProcessor.exchange`) with a small `sellTokenQuant` chosen (via brute force / binary search over inputs) such that `exchangeToSupply` → `exchangeFromSupply`'s `double` truncation returns a `buyTokenQuant` more favorable to the attacker than the true continuous Bancor formula value.
3. Repeat across many self-created exchanges/trades to accumulate value beyond what was deposited, or drain third-party exchanges that end up in an exploitable balance ratio.

Because the `useStrictMath`/`allowHardenExchangeCalculation` flags mean identical inputs on different node builds (or before/after the hardening proposal is passed) can compute different results, an exact byte-for-byte numeric PoC would need to be run against the live `Math.pow`/`StrictMath.pow` implementations, which is outside what static code review alone can confirm — this is the main unverified aspect of this analog.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
