### Title
Malicious "poison" order at the best price permanently blocks the on-chain DEX matching engine, causing repeated transaction failures (DoS/Censorship) for other traders - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The external report describes an ERC20-token DoS pattern where a token that reverts on transfer to certain addresses can be planted inside a batch operation, causing the whole batch to fail and stranding the fee-payer/relayer while blocking legitimate participants. The closest reachable analog in java-tron is the built-in TRC10/TRX decentralized exchange (`MarketSellAssetContract`), where a single taker transaction matches against a queue of resting maker orders in a loop inside one actuator execution. If matching against any one maker order in that queue throws an exception (e.g., unhandled arithmetic overflow or the "too many matches" guard), the entire actuator execution fails and is rolled back, exactly mirroring the "one bad entry blocks the whole batch" bug class.

### Finding Description
`MarketSellAssetActuator.execute()` performs order matching in a single pass: `matchOrder()` walks the sorted list of resting maker orders at the best price and repeatedly calls `matchSingleOrder()` for each one [1](#0-0) . This is functionally a "batch" of transfers/settlements executed atomically as part of one transaction: for every match, `addTrxOrToken()` credits balances/tokens to both the taker and maker [2](#0-1) .

The `execute()` method only catches a narrow set of checked exceptions: `ItemNotFoundException`, `InvalidProtocolBufferException`, `BalanceInsufficientException`, and `ContractValidateException` [3](#0-2) . However, `matchOrder`/`matchSingleOrder` perform unguarded arithmetic on maker/taker quantities (`multiplyAndDivide`, `subtractExact`, balance/asset addition in `addTrxOrToken`) and enforce a hard match-count ceiling that throws `ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM)` if a single taker order needs to sweep through more than `MAX_MATCH_NUM` (20) resting orders at the best price [4](#0-3) .

Because the maker order list is sorted with the best price first and matching always starts from the head of that list [5](#0-4) , an attacker who fully controls the resting order book for a given token pair can deliberately place ≥`MAX_MATCH_NUM` tiny orders at the best price (or a single order engineered to trigger an unhandled arithmetic exception during settlement). Any subsequent legitimate taker whose sell order is large enough to need matching past the first `MAX_MATCH_NUM` resting orders — or whose match hits the arithmetic edge case — will have their entire `MarketSellAssetContract` transaction throw and fail. Since the actuator's changes are only applied if the whole `execute()` call returns successfully (the surrounding session in `Manager` is rolled back on any exception thrown during transaction processing), none of the taker's other, otherwise-valid matches against the same or other maker orders in that call are ever committed. This is the direct analog of the reported bug class: a single unresolvable operation embedded in a larger batch of transfers (here, order matches) blocks the *entire* batch, the honest party pays the transaction fee/bandwidth and gets nothing, and the malicious party can repeat this cheaply to keep censoring/DoS-ing the market for that token pair.

### Impact Explanation
Traders attempting to sell/buy TRC10 assets or TRX through the on-chain exchange can have their transactions reliably and repeatedly fail whenever an attacker maintains a poisoned order book at the best price for a targeted pair. This is a Medium-severity DoS/Censorship condition consistent with the report's characterization: victims lose transaction fees (bandwidth/energy) for transactions that never execute, and the attacker can deny market access indefinitely at low cost by continuously re-placing cheap "poison" orders. It does not directly cause fund loss or node crash, matching the "Medium" classification of the original report.

### Likelihood Explanation
The `MAX_MATCH_NUM` limit is a fixed constant (20) known to any attacker who can read the code, and placing `>20` small resting orders at the best price for a low-liquidity or newly created TRC10 pair is cheap (each `MarketSellAssetContract` just needs to pay `getMarketSellFee()`), making the "too many matches" DoS path trivially and repeatedly triggerable by any unprivileged account. The arithmetic-overflow-based failure path is less certain — it requires engineering specific quantities to trigger unhandled `ArithmeticException` in `addTrxOrToken`/`multiplyAndDivide`, and I was not able to fully verify all overflow-guard behavior in `AccountCapsule.addAssetAmountV2`/`reduceAssetAmountV2` within the available exploration budget, so that particular sub-case remains unconfirmed.

### Recommendation
Conceptually (no plan requested): matching for a single taker order should either (a) never abort with loss of already-computed matches — i.e., commit partial matches found before hitting the match-count ceiling instead of throwing and discarding the whole execution, or (b) allow the taker to specify a bound and gracefully stop/return the remainder rather than reverting the whole transaction. Additionally, all arithmetic in the matching path should be wrapped with the same exception handling as the rest of `execute()` so that a single bad order cannot produce an unhandled exception that unwinds the whole transaction.

### Proof of Concept
Conceptual PoC (not executed): 
1. Attacker creates 21+ small `MarketSellAssetContract` orders for pair `(tokenA, tokenB)` at the best price, filling the resting order book beyond `MAX_MATCH_NUM = 20` [6](#0-5) .
2. A legitimate user submits a `MarketSellAssetContract` for `(tokenB, tokenA)` large enough that the matching loop must traverse more than 20 resting orders to fill it.
3. `matchOrder` increments `matchOrderCount` past `MAX_MATCH_NUM` and throws `ContractValidateException("Too many matches...")` [4](#0-3) , causing `execute()` to fail and the transaction (and its fee) to be lost, while none of the matches against the first 20 (otherwise fillable) orders are committed [3](#0-2) .
4. Attacker repeats this cheaply for any pair to indefinitely block honest large-order traders.
