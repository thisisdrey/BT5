## Finding: `remote_file_integrity` silently fails open for unmapped `remote_file_urls` entries in `http_archive`

### Title
Missing per-file integrity enforcement in `download_remote_files` lets any unmapped `remote_file_urls` entry be fetched without checksum verification — (File: `tools/build_defs/repo/utils.bzl`)

### Summary
`http_archive` (and any custom repository rule built on the shared `@bazel_tools//tools/build_defs/repo:utils.bzl` helpers) supports overlaying extra files fetched from remote URLs via the `remote_file_urls` / `remote_file_integrity` attribute pair. The utility function `download_remote_files` is supposed to fetch each file in `remote_file_urls` and verify it against the matching entry in `remote_file_integrity`. Instead of requiring a match for every path, it defaults to an **empty integrity string** whenever the corresponding key is absent from the `remote_file_integrity` dict, silently disabling checksum verification for that specific file only, while other files declared in the same rule invocation are checked normally.

### Finding Description
`download_remote_files` iterates over `ctx.attr.remote_file_urls` (a dict of `path -> [urls]`) and issues one `ctx.download()` per path: [1](#0-0) 

The integrity value passed for each download is computed as `ctx.attr.remote_file_integrity.get(path, "")` — i.e., if `path` is not a key in `remote_file_integrity`, the download proceeds with `integrity=""`, which `repository_ctx.download` treats as "no checksum required," per its own documented semantics (a download with no `sha256`/`integrity` is neither checked against a cache by hash nor verified after fetch): [2](#0-1) 

The `http_archive` rule's own documentation implies the two dicts are meant to be a 1:1 mapping ("These relative paths should map to the files (key) in the `remote_file_urls` attribute"), but the code never enforces this — a mismatch is silently accepted: [3](#0-2) 

This is the direct analog of the GMX bug: `remote_file_integrity` is a single checksum-mapping mechanism meant to protect **all** outputs of a multi-output operation (`remote_file_urls` may declare several overlay files, just as the GMX position-close flow may produce either an `outputAmount` or a `secondaryOutputAmount`), but the mechanism only covers entries that happen to have a matching key — any output that falls outside that mapping is delivered to the caller (here: written into the fetched repository) with no verification at all, instead of failing closed.

### Impact Explanation
`remote_file_urls` values are attacker-reachable content: they are ordinary mirror URLs (exactly like `http_archive`'s primary `urls`), and in the bzlmod flow they are populated from a registry's `source.json` `overlay`/`remote_file_urls` fields, which come from whatever index registry is configured — not necessarily BCR. Any of these origin servers is an "outsider [who] publishes or serves content a victim's build consumes." If the `remote_file_integrity` map omits (or is stale/incomplete relative to) one of the `remote_file_urls` keys — through a registry authoring mistake, a lockfile/attrs update that adds a new overlay path without updating the corresponding integrity dict, or any other divergence between the two attributes — the file at that path is silently fetched with no checksum check, letting the hostile origin substitute arbitrary content (e.g. a `BUILD.bazel` or `REPO.bazel` overlay file, which are exactly the kind of files this mechanism is designed to inject) into the repository the build consumes. This breaks the invariant that "integrity is binding" for declared checksums, since the surrounding rule invocation gives every appearance of being checksum-protected while one specific file silently is not.

### Likelihood Explanation
This requires no special access beyond controlling one of the URLs listed for a `remote_file_urls` path whose key is missing from `remote_file_integrity` — a purely data-driven condition (a stale/incomplete attribute pair), not a privileged action. Since neither `http_archive` nor `download_remote_files` validates that the two dict keysets match, and no warning/error is produced when they diverge, this can happen silently through routine maintenance (e.g., a registry or overlay author adding a new file to `remote_file_urls` without threading through the integrity value), making the fail-open behavior easy to trigger unintentionally and straightforward to trigger deliberately by a hostile mirror once such a gap exists.

### Recommendation
In `download_remote_files` (and the analogous `remote_module_file_urls` handling), require every key in `remote_file_urls` to have a corresponding non-empty entry in `remote_file_integrity`, and `fail()` at analysis time if any path is missing — mirroring the existing hard failure used for `remote_module_file_urls`/`remote_module_file_integrity`: [4](#0-3) 

### Proof of Concept
1. Define a custom repository rule (or `http_archive`) with:
   - `remote_file_urls = {"a.txt": ["http://attacker/a.txt"], "b.txt": ["http://good/b.txt"]}`
   - `remote_file_integrity = {"b.txt": "sha256-<good-hash>"}` (no entry for `a.txt`).
2. Run `bazel fetch`/`bazel build` on a target depending on this repo.
3. Observe that `b.txt` is verified against its integrity value while `a.txt` is fetched and written into the repository unconditionally regardless of its content — replacing `a.txt`'s content at the attacker-controlled URL is not detected, unlike a run where `a.txt` also had an integrity entry (which would fail with a checksum mismatch). This can be encoded as a `src/test/shell/bazel/external_integration_test.sh`-style test analogous to the existing `remote_file_urls`/`remote_file_integrity` coverage in that suite, asserting that a build succeeds silently even when the "unmapped" file's content is swapped out from under it.
