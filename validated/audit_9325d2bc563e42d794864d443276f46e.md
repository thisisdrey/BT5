### Title
RewardsDistributor advances `timestamp` without updating `index`, permanently discarding accrued rewards when the index delta rounds to zero - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenIndex` computes the per-token reward increment as `_tokensAccrued.wadDiv(_totalSupply)` (1e18-scaled, half-up rounding). When `_deltaTimestamps * tokenSpeed * 1e18 / totalSupply < 0.5`, the ratio rounds to `0`, the index stays unchanged, but `_updateTokenIndex` still writes `_supplyState.timestamp = block.timestamp`. An unprivileged attacker can call the public `updateBeforeMintOrBurn`/`updateBeforeTransfer` (or trigger them via `DepositToken.transfer`/`DebtToken` transfers) every block to keep advancing the timestamp while the index never moves, so emitted reward tokens are silently never credited to anyone.

### Finding Description
In `contracts/RewardsDistributor.sol:197-212`:

```solidity
uint256 _tokensAccrued = _deltaTimestamps * _speed;
uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
_newIndex = (_supplyState.index + _ratio).toUint224();
_newTimestamp = block.timestamp.toUint32();
```

`wadDiv` is half-up rounding: `(a * 1e18 + b/2) / b` (`contracts/lib/WadRayMath.sol:39-41`). If `_tokensAccrued * 1e18 / _totalSupply < 0.5`, `_ratio = 0`, so `_newIndex == _supplyState.index` but `_newTimestamp` is still set to `block.timestamp`. Then `_updateTokenIndex` (lines 271-282) persists both: since `_newIndex > 0` (initialized to `INITIAL_INDEX`) and `_newTimestamp > 0`, the timestamp is updated while the accrued `_deltaTimestamps * _speed` tokens are discarded forever — they are never added back later.

`updateBeforeMintOrBurn` is explicitly callable by anyone ("This function also may be called by anyone to update stored indexes", line 173) and `updateBeforeTransfer` is invoked on every `DepositToken`/`DebtToken` transfer via the `updateRewardsBeforeMintOrBurn`/`updateRewardsBeforeTransfer` modifiers (`contracts/DepositToken.sol:124-144`). There is no guard on call frequency, and pause flags do not block these external calls.

The invariant that breaks: reward accrual conservation — `sum(rewardToken emitted over time) == sum(tokensAccruedOf) + claimed` is violated; elapsed emission evaporates.

### Impact Explanation
Theft/freezing of unclaimed yield. Reward tokens that should have been distributed per `tokenSpeeds` remain locked in the distributor, unclaimable by any user, while `timestamp` keeps advancing. Even when the ratio doesn't round fully to zero, each update truncates up to `totalSupply / 2e18` reward tokens of emission, so repeated public updates systematically bleed rewards below the configured emission rate (the "rounding eats into rewards" effect, here attacker-accelerated).

### Likelihood Explanation
Condition for full freeze: `_deltaTimestamps * _speed < totalSupply / (2e18)`. With a large deposit/debt token supply (e.g., 1e27 wei ≈ 1B 18-decimal tokens) and a modest emission `speed` (< ~4e7 wei/s on 12s mainnet blocks; < ~2.5e8 wei/s on 2s Optimism/Hemi blocks, where Metronome is deployed), any EOA can keep the delta at one block by calling `updateBeforeMintOrBurn` every block — cheap on L2. Partial reward loss requires no supply/rate extremes at all and occurs naturally on every transfer. No privileged role is needed; `tokenSpeeds` being small is an expected long-tail configuration, not a governance misuse, since speed sanity bounds are not enforced.

### Recommendation
Only persist `timestamp` when the index actually increased: in `_updateTokenIndex`/`_calculateTokenIndex`, skip the timestamp write (or accumulate the sub-unit remainder) when `_ratio == 0`. Alternatively, accumulate elapsed time in a "pending" residual so sub-unit accrual isn't destroyed, and scrutinize downstream effects on `_calculateTokenDelta`'s `INITIAL_INDEX` fallback.
