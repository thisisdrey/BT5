### Title
IPv4-compatible IPv6 addresses (e.g. `::127.0.0.1`) bypass `PeerAddress::is_in_private_range()`, defeating the private-IP/SSRF gate on peer-supplied data URLs - (File: `stacks-common/src/types/net.rs`)

### Summary
`PeerAddress::is_in_private_range()` is the sole gate used throughout `stackslib/src/net/**` to decide whether a remote-supplied network address (from a handshake, neighbor gossip, or a peer's advertised `data_url`) is "private" and therefore should be refused for outbound connections/queries when `private_neighbors` is `false` (the default). For IPv6 it only recognizes `fc00::/7` and the canonical loopback `::1`. It does not recognize the deprecated IPv4-compatible IPv6 form (`::a.b.c.d`, RFC 4291 IPv4-compatible addresses, distinct from the IPv4-mapped `::ffff:a.b.c.d` form it does handle). This is the same bug class as the referenced advisory: a private/loopback address expressed in an alternate IPv6 textual/byte form slips past the hostname/IP validation.

### Finding Description
`is_in_private_range()` in [1](#0-0)  is implemented as:

```
pub fn is_in_private_range(&self) -> bool {
    if self.is_ipv4() {
        ...
    } else {
        // private address (fc00::/7) or localhost (::1)
        self.0[0] >= 0xfc || (self.0[0..15] == [0u8; 15] && self.0[15] == 1)
    }
}
```

`is_ipv4()` only returns `true` for the IPv4-*mapped* prefix `::ffff:0:0/96` [2](#0-1) . A textual/byte address using the IPv4-*compatible* embedding — e.g. `::127.0.0.1`, `::10.0.0.1`, `::192.168.1.1`, `::169.254.169.254` (cloud metadata) — has the same last-4-byte layout as its IPv4 counterpart but a `0x0000` prefix instead of `0x0000...ffff`. Such an address:
- fails `is_ipv4()` (prefix bytes 10-11 are `0x00,0x00`, not `0xff,0xff`), so it is evaluated via the IPv6 branch;
- fails `self.0[0] >= 0xfc` (first byte is `0x00`);
- fails the `::1`-exact check, because bytes 12-15 are `127,0,0,1` (or any other IPv4 octets), not all-zero-then-`1`.

So `is_in_private_range()` returns `false` for `::127.0.0.1`, `::10.0.0.1`, `::192.168.0.1`, `::169.254.169.254`, etc., even though these resolve (via `to_ipaddr()`/`to_socketaddr()`, used everywhere the address is actually dialed) to genuine loopback/private-range/link-local IPv4 sockets. Note also that `PeerAddress::is_loopback()` (`to_socketaddr(0).ip().is_loopback()`, line 216-218) is likewise blind to this form, because Rust's own `Ipv6Addr::is_loopback()` only matches the exact `::1` segment pattern.

This gate is relied on in multiple remote-reachable code paths in the in-scope tree:
- `stackslib/src/net/mempool/mod.rs` `do_mempool_sync` — before issuing an HTTP mempool-sync query to a resolved peer address, it checks `PeerAddress::from_socketaddr(addr).is_in_private_range()` and aborts if private (unless `private_neighbors` is set) [3](#0-2) .
- `stackslib/src/net/p2p.rs` `can_register_peer` — refuses to register/connect to a peer whose `neighbor_key.addrbytes.is_in_private_range()` is true [4](#0-3) .
- `stackslib/src/net/neighbors/walk.rs` `filter_sensible_neighbors` — filters gossiped `NeighborAddress` entries by the same predicate before walking to them [5](#0-4) .

The mempool-sync path is the most directly attacker-triggerable: the target peer's `data_url` (used to build the request URL) and its resolved socket address are attacker-influenced (a malicious/compromised peer's advertised handshake `data_url`, or a domain the attacker controls resolving to an IPv4-compatible IPv6 literal). Because `url::Host::Ipv6` accepts the deprecated IPv4-compatible form and `PeerAddress::from_ip`/`from_socketaddr` faithfully encode it, the private-range check silently fails open, and the victim node's outbound HTTP client (used for mempool queries and block/StackerDB data-URL fetches) is directed to loopback/private/link-local addresses that `private_neighbors=false` was specifically meant to forbid.

### Impact Explanation
This breaks the equality the code intends to enforce ("this socket address is/isn't in a private range") for a specific, legitimately-parseable IPv6 form, letting a remote unauthenticated peer coerce the victim node into issuing outbound HTTP(s) requests toward `127.0.0.1`, RFC1918 ranges, or cloud metadata endpoints (`169.254.169.254`) that are reachable only from the victim node itself — a classic SSRF pivot delivered entirely through P2P protocol fields (handshake `data_url`/DNS-resolved hostnames), requiring no secret key or privileged role, matching CWE-918. It does not directly write chain state, but it can be used to probe/attack internal services from the node's own network position, which fits the "High" bucket (steering a node's outbound requests off its intended target via a defense that fails open).

### Likelihood Explanation
Reachable with a single crafted peer/hostname: the attacker only needs to run (or control DNS for) a node that advertises a `data_url` whose IPv6 literal is written in the IPv4-compatible form. No authentication, no consensus interaction, no volumetric traffic is needed — a single mempool-sync round trip is sufficient to trigger the outbound request.

### Recommendation
Fix `PeerAddress::is_in_private_range()` (and `is_loopback()`/`is_anynet()` if similarly affected) to canonicalize via `to_ipaddr()`/`Ipv6Addr::to_ipv4()`-style detection before classifying: if the IPv6 address embeds an IPv4 address in either the mapped (`::ffff:a.b.c.d`) or the compatible (`::a.b.c.d`) form, apply the IPv4 private-range rules to the embedded octets rather than falling through to the narrow IPv6-only checks. Add explicit unit tests for `::127.0.0.1`, `::10.0.0.1`, `::192.168.0.1`, and `::169.254.169.254`.

### Proof of Concept
```rust
use stacks_common::types::net::PeerAddress;
use std::net::{IpAddr, Ipv6Addr};

// RFC4291 IPv4-compatible embedding of 127.0.0.1 (NOT the ::ffff: mapped form)
let ip: IpAddr = "::127.0.0.1".parse().unwrap();
let pa = PeerAddress::from_ip(&ip);

assert_eq!(pa.is_in_private_range(), false); // BUG: should be true (loopback)
assert_eq!(pa.is_loopback(), false);         // BUG: should be true

// but the address that actually gets dialed is genuinely loopback:
assert!(pa.to_socketaddr(80).ip().to_string().contains("127.0.0.1"));
```
Deliver this as an attacker-controlled `data_url` host (e.g. `http://[::127.0.0.1]:6270/...` or a DNS name resolving to that literal) in a peer handshake; `do_mempool_sync`'s `is_in_private_range()` check at `stackslib/src/net/mempool/mod.rs:488-490` will pass, and the victim will issue an HTTP mempool-sync request to its own loopback interface.
