Audit Report

## Title
`ChildBountiesValuePerParent` is never decremented when a child bounty is closed without payout, permanently under-reporting parent bounty payouts - (File: `substrate/frame/multi-asset-bounties/src/lib.rs`)

## Summary
`calculate_payout` derives the parent bounty's payout by subtracting `ChildBountiesValuePerParent` from the parent's total value, but `remove_bounty`'s child-removal branch (`Some(child_bounty_id) => { ChildBounties::remove(...); ChildBountiesPerParent::mutate(...).saturating_dec(); }`) only decrements the child count and never subtracts the closed child's value from `ChildBountiesValuePerParent`. As a result, closing a child bounty without payout permanently and silently inflates the reserved-value counter, causing the parent bounty's beneficiary to be underpaid by exactly the value of every child bounty ever closed without payout.

## Finding Description
`calculate_payout` at [1](#0-0)  computes the parent payout as `value.saturating_sub(children_value)` where `children_value = ChildBountiesValuePerParent::<T, I>::get(parent_bounty_id)`. This value is only ever cleared in the `None` (full parent removal) branch of `remove_bounty`, while the `Some(child_bounty_id)` branch decrements only `ChildBountiesPerParent`, leaving `ChildBountiesValuePerParent` untouched: [2](#0-1) . Since `remove_bounty` is the sole cleanup routine for child bounty removal — including the close-without-payout path — every child bounty closed before payout leaves its reserved value permanently counted against the parent, with no other code path to reclaim it.

## Impact Explanation
This causes the parent bounty beneficiary to be underpaid on `award_bounty`/claim by the sum of all child-bounty values that were closed without payout, while that same value remains locked in the bounty/treasury source account with no dispatchable path to release it to the intended beneficiary. This matches the "permanent user-fund lock" / "wrong beneficiary amount" impact category for payout-state correctness in scope.

## Likelihood Explanation
Closing a child bounty via `close_child_bounty` before it completes payout is an ordinary, expected curator-level administrative action (also reachable via `RejectOrigin`), not requiring any unusual privilege abuse or attacker-specific setup — every such closure deterministically corrupts the counter for that parent.

## Recommendation
In the `Some(child_bounty_id)` branch of `remove_bounty`, subtract the removed child bounty's `value` from `ChildBountiesValuePerParent::<T, I>` (via checked/saturating subtraction) whenever removal occurs without a completed payout, mirroring the increment performed on child-bounty creation. Add a regression test that closes (rather than claims) a child bounty and asserts `calculate_payout` on the parent subsequently returns the full parent value.

## Proof of Concept
1. Create parent bounty `P` with value `V`; fund it.
2. Add child bounty `C` with value `v`, so `ChildBountiesValuePerParent(P) == v`.
3. Curator calls `close_child_bounty(P, C)` before payout; `remove_bounty(P, Some(C), ..)` decrements `ChildBountiesPerParent(P)` but leaves `ChildBountiesValuePerParent(P) == v`.
4. Award and claim parent bounty `P`: `calculate_payout(P, None, V)` returns `V - v`, though no child ever received `v`.
5. The parent beneficiary receives `V - v` instead of `V`; the remaining `v` is stuck in the bounty account with no call to recover it.

	/// Calculates amount the beneficiary receives during child-/bounty payout.
	fn calculate_payout(
		parent_bounty_id: BountyIndex,
		child_bounty_id: Option<BountyIndex>,
		value: T::Balance,
	) -> T::Balance {
		match child_bounty_id {
			None => {
				// Get total child bounties value, and subtract it from the parent
				// value.
				let children_value = ChildBountiesValuePerParent::<T, I>::get(parent_bounty_id);
				debug_assert!(children_value <= value);
				let payout = value.saturating_sub(children_value);
				payout
			},
			Some(_) => value,
		}
	}
