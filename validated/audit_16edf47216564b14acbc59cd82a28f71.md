### Title
Unbounded Array Allocation in TVM Precompiled Contract Calldata Parsing Enables Remote Denial of Service - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The helper routines `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` read an attacker-controlled element count directly from smart-contract call data and immediately use it to allocate a Java array, with no upper bound check on the count before allocation. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Each of these functions derives `len` from a `DataWord` extracted from the raw calldata via `words[offset].intValueSafe()`, and then performs `new byte[len][]` (or `byte[len][32]`) with no validation that `len` is within any sane bound (such as the actual remaining length of `data`, or a fixed protocol maximum):

```java
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
  int len = words[offset].intValueSafe();
  byte[][] bytes32Array = new byte[len][];
  ...
}

private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  ...
}
``` [4](#0-3) 

This is structurally identical to the GoFiber flash-cookie bug class: an attacker-controlled length field taken from untrusted, deserialized/decoded input is passed directly into an allocation primitive (`make()` in Go / `new T[len]` in Java) with no bounds check against the actual size of the supplied payload. Since `DataWord.intValueSafe()` clamps oversized 256-bit values to `Integer.MAX_VALUE` rather than rejecting them, a crafted 32-byte calldata word (e.g. `0x7fffffff`) causes an attempt to allocate an array with over two billion reference slots, which either throws `OutOfMemoryError`/triggers heavy GC pressure or crashes the JVM process depending on heap configuration — unlike the RLP decoder elsewhere in the codebase, which explicitly guards against this via `verifyLength()` before allocating, these array-extraction helpers have no equivalent guard. [5](#0-4) 

Unlike the length checks visible elsewhere in `PrecompiledContracts.java`, e.g., `VerifyTransferProof.execute()`, which explicitly bounds `spendCount`/`receiveCount` to a small range (`spendCount < 1 || spendCount > 2`) before any array is sized off of it, no such bound exists for `extractBytes32Array`/`extractBytesArray`/`extractSigArray`. [6](#0-5) 

### Impact Explanation
Any account that can broadcast a `TriggerSmartContract` transaction (or interact with a deployed contract that forwards raw calldata to the vulnerable precompiled contract) can supply a malicious length word to force a multi-gigabyte allocation attempt inside the TVM execution path on every full node processing that transaction, matching the Denial-of-Service impact described in the reference advisory (CWE-770/CWE-789, unbounded memory allocation from untrusted input). This can crash or destabilize the node's JVM (`OutOfMemoryError`) and, if reproducible deterministically across all nodes executing the same transaction, could also produce a consensus-relevant halt condition across the network.

### Likelihood Explanation
Reaching these functions requires only an ordinary signed transaction that calls a TVM contract exercising the affected precompiled contract path — no special privileges, staking, or witness/committee role is needed, consistent with the "unauthenticated remote" reachability of the original GoFiber bug. However, I was not able to fully confirm within the available tool iterations which specific precompiled contract(s) invoke `extractBytesArray`/`extractBytes32Array`/`extractSigArray` at their call sites, nor whether an upstream length/energy check (e.g., total calldata size vs. energy cost) indirectly limits `len` before these helpers are reached. This uncertainty should be resolved by inspecting the call sites of these three helper methods and the energy-cost function of whichever precompiled contract(s) use them.

### Recommendation
Add explicit bounds checks in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocation — e.g., validate `len` against the actual number of `DataWord`s available (`words.length - offset - 1`) and/or a fixed protocol maximum, and reject/short-circuit with a failed execution result if `len` exceeds that bound, mirroring the `verifyLength()` guard pattern used in `RLP.java`.

### Proof of Concept
Not independently verified against actual call sites due to reaching the tool-call limit before locating which precompiled contract(s) invoke these helpers; a concrete PoC would require crafting `TriggerSmartContract` calldata that reaches a precompile using `extractBytesArray`/`extractBytes32Array`/`extractSigArray` with a large 32-byte word (e.g., `0x000...7fffffff`) at the length-offset position, then observing the resulting allocation attempt/OOM during TVM execution.
