### Title
`AccountPermissionUpdateActuator` lets a delegated Active-permission signer overwrite the Owner permission with no recovery mechanism - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
The BFX report shows that a lower-tier "admin" role can strip a higher-tier "owner" role and that the only defense (`makeOwnerAdmin()`) is a weak, race-prone patch. Java-tron's account multisig model has the analogous structural weakness: any Active permission whose `operations` bitmap includes bit 46 (`AccountPermissionUpdateContract`) can, with a single signed transaction, completely replace the account's Owner permission (and Active/Witness permissions) - including removing the true owner's key entirely - and unlike BFX there is **no** owner-recovery function at all in java-tron for this case.

### Finding Description
`AccountPermissionUpdateActuator.validate()` determines which signer may submit an `AccountPermissionUpdateContract` purely by checking, via `permissionId`, that the signing permission is of type `Active` and has the corresponding bit set in its `operations` bitmap: [1](#0-0) 

The bit-check itself is: [2](#0-1) 

Once that Active-permission signer's aggregate weight exceeds the Active permission's own threshold, `execute()` unconditionally overwrites the account's Owner permission (`Permission_id` 0), Witness permission, and Active permission list with whatever the transaction specifies - there is no check that the resulting Owner permission still contains the previous owner's key, nor any weight/threshold relationship enforced between the "admin" (Active) permission and the "owner" (Owner) permission being replaced: [3](#0-2) 

`checkPermission()` in the actuator only rejects operation bits that are outside the globally-enabled `dynamicStore.getAvailableContractType()` set - it does not forbid an Active permission from carrying the `AccountPermissionUpdateContract` bit: [4](#0-3) 

The codebase itself acknowledges that this bit is deliberately excluded from the *default* Active permission template (`checkActiveDefaultOperations`), confirming the developers recognized the danger of granting this capability to a non-owner key by default: [5](#0-4) [6](#0-5) 

However, nothing in the actuator or in `AccountCapsule` prevents an owner from later granting (or a compromised/malicious co-signer from being granted) this bit on an Active permission, after which that "admin-tier" key set can unilaterally rewrite the Owner permission to any address set of its choosing - exactly mirroring the BFX pattern where an "admin" role can strip the "owner" role. Unlike BFX's (flawed) `makeOwnerAdmin()` safety valve, java-tron provides **no** built-in mechanism for the original owner to reclaim control once its Owner permission's keys have been replaced by a rogue Active-permission holder, since the immutable, cryptographically-authenticated `owner_address` on the account is distinct from the mutable `Permission` structures that actually gate transaction authorization.

### Impact Explanation
If an account owner (as many multisig setups do) delegates the `AccountPermissionUpdateContract` operation to an Active-tier key (e.g., for operational convenience, exchange hot-wallet management, or DAO-style delegated administration), a compromise or malicious action by that Active key holder allows full, permanent, unrecoverable takeover of the account's Owner permission - and by extension the ability to move all funds, freeze/unfreeze balances, vote, and perform every other Owner-gated operation - with no code path to reinstate the original owner's authority. This constitutes unauthorized account takeover / permanent loss of control over funds, matching the "Accept only concrete unauthorized account operation ... permanent freezing of funds" bar.

### Likelihood Explanation
Requires a single legitimately signed `AccountPermissionUpdateContract` transaction from an Active-permission key that was previously granted the `AccountPermissionUpdateContract` operation bit. This is not the default configuration, so likelihood depends on account owners' delegation choices; however, since java-tron explicitly supports and does not restrict this delegation pattern, and provides no compensating recovery control, any account that does delegate this operation is permanently exposed to this exact class of admin-privilege-escalation/owner-lockout attack, same likelihood profile the original report assigned (Low likelihood, high impact ⇒ Medium severity).

### Recommendation
- In `AccountPermissionUpdateActuator.validate()`/`checkPermission()`, disallow the `AccountPermissionUpdateContract` operation bit from ever being set on non-Owner (`Active`/`Witness`) permissions, or require that any Owner-permission replacement transaction also be co-signed under the current Owner permission threshold (not merely a delegated Active permission).
- Alternatively, add a protocol-level recovery path (analogous to, but stronger than, `makeOwnerAdmin()`) allowing the original Owner-permission key set to reclaim the account's permissions even after a hostile `AccountPermissionUpdateContract` execution, e.g., a time-locked veto window before permission changes involving the Owner permission take effect.

### Proof of Concept
1. Owner account `A` creates default Owner/Active permissions and then issues an `AccountPermissionUpdateContract` granting Active permission id 2 (key `B`) the `AccountPermissionUpdateContract` operation bit (this is possible because `checkPermission()` in [7](#0-6)  only forbids bits outside the globally available contract types, not this specific bit).
2. Key `B` (the "admin") signs a new `AccountPermissionUpdateContract` with `Permission_id = 2`, passing `checkPermission()` in `TransactionCapsule.addSign`/`validatePubSignature` [1](#0-0) , and sets a brand-new Owner permission containing only `B`'s key, removing `A` entirely.
3. `AccountPermissionUpdateActuator.execute()` applies this unconditionally [3](#0-2) , and `A` has no remaining code path to recover Owner control of the account.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
