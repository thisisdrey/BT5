### Title
Per-IP QUIC connection rate limiter tokens are only consumed on handshake success, letting an unstaked attacker churn incomplete handshakes to generate unbounded accept/handshake CPU work for zero fees - (File: streamer/src/nonblocking/quic.rs)

### Summary
The per-IP `ConnectionRateLimiter` and the global `overall_connection_rate_limiter` are checked with a non-mutating "peek" (`is_allowed`/`current_tokens`) before `accept()`, but tokens are only actually debited via `register_connection`/`consume_tokens` after the QUIC handshake fully succeeds inside `setup_connection`. An attacker that repeatedly opens QUIC connections from a single IP (varying ephemeral source ports) and aborts them before the handshake completes never triggers the debiting step, so the limiter's `current_tokens` for that IP is never decremented and the pre-accept checks keep passing forever.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:331-369`), each incoming connection is gated by two non-consuming checks:
- `overall_connection_rate_limiter.current_tokens() == 0` [1](#0-0) 
- `rate_limiter.is_allowed(&incoming.remote_address().ip())` [2](#0-1) 

`ConnectionRateLimiter::is_allowed` only reads `current_tokens` and never mutates the bucket: [3](#0-2) 

The actual token debit only happens in `ConnectionRateLimiter::register_connection`/`TokenBucket::consume_tokens`, and that call is made from `setup_connection` **only after** the QUIC handshake future (`connecting.await`) resolves `Ok(new_connection)`, i.e., only on a fully-completed handshake: [4](#0-3) 

Because `ClientConnectionTracker::new`/`accept()` is invoked (line 371-384) and the handshake begins driving *before* any token is consumed, and the server must process the TLS ClientHello and produce ServerHello/Certificate/CertificateVerify (asymmetric crypto, including a signature with the node's certificate key) as part of driving `connecting`, real CPU work is spent per attempt regardless of whether the handshake ever finishes. An attacker only needs to send an Initial packet and then drop the connection (or simply never send the final handshake flight) to force this work while never causing `register_connection`/`consume_tokens` to run. Consequently:
- `is_allowed()` for that IP keeps returning `true` indefinitely (its backing `current_tokens` was never decremented).
- The `overall_connection_rate_limiter.current_tokens() == 0` check similarly never trips, since its consumption also only happens post-handshake at line 495.

`ClientConnectionTracker::new` (which enforces `max_concurrent_connections`) also does not stop this pattern, because it only bounds *concurrently* open in-flight attempts, and each aborted attempt drops its tracker quickly (freeing a slot for the next attempt), so a fast enough churn rate keeps concurrency low while attempt throughput stays high.

### Impact Explanation
This is a leader CPU-degradation vector matching the "unprivileged attacker can cheaply force sigverify/scheduling/buffering-equivalent work that vastly exceeds fees collected" bounty category described in the audit scope. The QUIC per-IP and global connection rate limiters, whose entire purpose is to bound the rate of connection-handshake work performed by the leader's TPU QUIC endpoint, can be evaded by never completing handshakes, letting a single IP generate an effectively unbounded number of handshake-processing/crypto operations at zero cost (the attacker never pays a fee, and does not even need to complete expensive work on their own side).

### Likelihood Explanation
This requires no stake, no special network position, and no cluster interaction — only a remote, unprivileged client sending QUIC Initial packets to the leader's public TPU QUIC port and aborting/timing out before completing the handshake. It is fully repeatable and can be automated with commodity tooling (varying only local ephemeral ports on one machine/IP), making it straightforward and cheap.

### Recommendation
Consume (or reserve) a per-IP and global rate-limiter token at connection-attempt time (before/at `accept()`), not just at handshake success, and refund the token only if a legitimate reason applies (e.g., true resource exhaustion causing an early server-side refusal unrelated to attacker behavior). Alternatively, additionally rate-limit/track handshake *attempts* per IP (independent of completion) with a token bucket that debits at `incoming.accept()` time in `run_server`, so churn cannot bypass throttling.

### Proof of Concept
Rust integration test plan (extending `streamer/src/nonblocking/quic.rs` test module, using `make_client_endpoint`):
```rust
#[tokio::test]
async fn test_rate_limiter_bypassed_by_incomplete_handshake_churn() {
    // server configured with max_connections_per_ipaddr_per_min = 2
    let (t, _receiver, server_address, cancel) = setup_swqos_quic_server_with(
        QuicStreamerConfig { max_connections_per_ipaddr_per_min: 2, ..Default::default() }
    );

    let mut completed_handshake_attempts = 0;
    for _ in 0..1000 {
        // Open connection but drop before Finished flight completes,
        // e.g. by dropping the endpoint immediately after initiating connect()
        // without awaiting full handshake completion.
        let endpoint = make_partial_client_endpoint(&server_address).await;
        drop(endpoint); // abort before handshake success
        completed_handshake_attempts += 1;
    }

    // Assertion: server's per-IP rate limiter should have blocked further
    // attempts long before 1000 tries, but stats show it never triggers because
    // register_connection() (the only consuming path) was never reached.
    // Expected (buggy) result: stats.connection_rate_limited_per_ipaddr stays 0
    // despite far exceeding max_connections_per_ipaddr_per_min.
    assert_eq!(stats.connection_rate_limited_per_ipaddr.load(Ordering::Relaxed), 0);
    // Desired fix behavior: this count should be > 0 once attempts exceed the configured limit.
}
```
Unit-level assertion on the limiter itself:
```rust
#[test]
fn test_is_allowed_never_trips_without_register_connection() {
    let limiter = ConnectionRateLimiter::new(2, 2, 4);
    let ip = IpAddr::V4(Ipv4Addr::new(10,0,0,1));
    for _ in 0..10_000 {
        assert!(limiter.is_allowed(&ip)); // never mutated -> always true

    }
```

Expected assertion for the fix: `is_allowed`/the pre-accept check must reflect attempt volume, not only completed-handshake volume, so the loop above should eventually return `false`.

```rust
    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }
```
