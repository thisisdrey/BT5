### Title
`text/template` `errRecover` re-panics `runtime.Error` values instead of converting them to a returned error - ([File: src/text/template/exec.go])

### Summary
`Template.Execute` relies on the deferred handler `errRecover` to convert panics raised while walking a template into a returned `error`, so that a bad or unexpected data value supplied to `Execute` does not crash the calling program. However, `errRecover`'s type switch only converts `writeError` and `ExecError` values into a return value; for the `runtime.Error` case it explicitly does `panic(e)` again, i.e. it fails to "catch" that class of error and lets the panic propagate out of `Execute`, mirroring the Sherlock report's core problem (`catch Error(string)` only handling one error shape and letting everything else revert/panic through).

### Finding Description
Untrusted/attacker-influenced data passed as the `data any` argument to `(*Template).Execute` / `ExecuteTemplate` is walked node-by-node by the `state` machine in `src/text/template/exec.go`. Evaluation of pipelines, field/method/index accesses on that data can trigger genuine Go runtime panics (nil pointer dereference, index out of range, interface conversion failure, division by zero, etc.), which the runtime represents as values implementing `runtime.Error`.

The single recovery point guarding this walk is: [1](#0-0) 

```go
func errRecover(errp *error) {
	e := recover()
	if e != nil {
		switch err := e.(type) {
		case runtime.Error:
			panic(e)
		case writeError:
			*errp = err.Err // Strip the wrapper.
		case ExecError:
			*errp = err // Keep the wrapper.
		default:
			panic(e)
		}
	}
}
```

This is functionally identical to the reported Solidity bug: the "catch" clause only handles specific, expected shapes (`writeError`, `ExecError` ≈ `catch Error(string)`), and for the `runtime.Error` shape and any unrecognized value (the `default` branch) it deliberately re-panics instead of converting the failure into the function's normal error-return contract. `Template.Execute`'s doc comment implies callers get an `error` on failure; instead, whenever the underlying cause is a `runtime.Error` (which is exactly the class of error most likely to be triggered by attacker-supplied `data`, e.g. nested nil pointers, out-of-range indices reachable through `{{index .Slice $n}}`, or `{{.X.Y}}` on nil), the panic escapes `Execute` uncaught.

### Impact Explanation
Any Go program/service that executes a `text/template` (or `html/template`, which shares this `exec.go` machinery) against externally influenced data — e.g., an HTTP handler rendering a template with request-derived data — can be crashed by supplying a data shape that causes a runtime panic during evaluation (nil dereference, index out of range, bad interface conversion) rather than getting back a normal `error` from `Execute`. If the caller does not itself wrap the call in a `recover()`, this results in an unhandled panic and process/goroutine crash (denial of service for that request or, absent additional recovery middleware, the whole process). This is a real, reachable behavior in the standard library, not a hypothetical misuse. Severity-wise this would sit in the PUBLIC track as a documented-but-surprising panic-through-error-boundary issue rather than a memory-safety or auth bypass bug.

### Likelihood Explanation
The victim workflow is any server/tool that calls `Execute`/`ExecuteTemplate` with attacker-influenced `data` (a very common pattern: rendering templates with request parameters, user profile fields, etc.). The attacker only needs unauthenticated/ordinary-user-level control over the data values fed into the template pipeline (e.g., causing an index expression to go out of range, or a field access to dereference nil) — no special privileges are required. This matches the ordinary "published/consumed by a normal victim workflow" profile.

### Recommendation
In `errRecover` (src/text/template/exec.go), convert `runtime.Error` panics into a returned error (e.g., wrap in `ExecError`) instead of re-panicking them, so `Execute`/`ExecuteTemplate` consistently returns an `error` for any panic originating from evaluating template data, matching the documented contract. If deliberate re-panic is intended for some other reason, this should be explicitly and clearly documented, and templates that process untrusted data should be advised to wrap `Execute` calls in their own `recover()`.

### Proof of Concept
```go
package template_test

import (
	"strings"
	"testing"
	"text/template"
)

// TestExecutePanicsOnRuntimeError demonstrates that Execute does not
// return an error but instead lets a runtime.Error panic escape,
// when the panic originates from evaluating attacker-supplied data
// (here: an out-of-range index computed from the "attacker" input).
func TestExecutePanicsOnRuntimeError(t *testing.T) {
	tmpl := template.Must(template.New("t").Parse(`{{index .Slice .Index}}`))

	data := struct {
		Slice []int
		Index int
	}{
		Slice: []int{1, 2, 3},
		Index: 99, // attacker-controlled, out of range
	}

	defer func() {
		r := recover()
		if r == nil {
			t.Fatal("expected Execute to panic instead of returning an error (bug), but it did not panic")
		}
		// Confirms the panic is a runtime.Error re-panicked by errRecover,
		// rather than being converted into a returned error as documented.
		t.Logf("Execute panicked instead of returning error: %v", r)
	}()

	var sb strings.Builder
	err := tmpl.Execute(&sb, data)
	if err != nil {
		t.Fatalf("expected panic, but got graceful error instead: %v", err)
	}
}
```
Expected/actual: `tmpl.Execute` panics (caught only by the test's own `defer/recover`) instead of returning a non-nil `error`, confirming `errRecover`'s `case runtime.Error: panic(e)` branch lets this class of failure escape the function's error-return contract — analogous to the Solidity `catch Error(string)` failing to catch non-string reverts.
