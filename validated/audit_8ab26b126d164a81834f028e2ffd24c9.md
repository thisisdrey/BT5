### Title
DIA oracle price path lacks any confidence/outlier validation, unlike the Pyth path - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`resolve-dia` accepts the DIA oracle's raw price with no confidence or deviation check, while `resolve-pyth` explicitly validates a confidence interval via `check-confidence`. This asymmetry means USDH's price (fed through `TYPE-DIA`) is trusted "regardless of its actual value" as long as it is non-zero and passes the timestamp freshness/monotonicity check — precisely the outlier-filtering gap described in the referenced report.

### Finding Description
Price resolution in the market is centralized in `price-resolve`, which dispatches to either `resolve-pyth` or `resolve-dia` depending on the asset's configured oracle `type`: [1](#0-0) 

For Pyth-sourced assets, the raw price is passed through `check-confidence`, which bounds the oracle-reported confidence interval against `max-confidence-ratio` before the price is accepted: [2](#0-1) 

For DIA-sourced assets (used for USDH, per `DIA-USDH` in `v0-1-data.clar`), no equivalent check exists — `resolve-dia` only reformats the timestamp and forwards the value untouched: [3](#0-2) 

The only downstream validation applied to *any* resolved price — Pyth or DIA — is in `price-resolve`: [4](#0-3) [5](#0-4) 

`oracle-price-legal` only rejects a price of exactly `u0`; `oracle-timestamp-fresh` only bounds staleness and enforces timestamp monotonicity. Neither checks the magnitude of a price move, nor cross-validates DIA's reported value against any secondary source or historical bound — this is exactly the pattern flagged in the external report: "the above code outlines how prices are utilised regardless of their actual value (assuming it is always a non-zero value)." The docs (`docs/oracle.md`) confirm this is intentional design ("DIA prices are assumed to be pre-normalized to 8 decimals" with no further sanity check), but it is inconsistent with the protection deliberately built into the Pyth path via `check-confidence`.

### Impact Explanation
USDH price is used through `resolve-dia` in the market's collateral/debt valuation and, ultimately, in health-check/liquidation calculations that gate borrowing and liquidations for ordinary principals. If DIA's on-chain price for USDH is malformed, glitches, or is manipulated by an upstream/malicious update to the DIA oracle (a bug/gap in *this* code's failure to bound or sanity-check it, not a claim about DIA's own correctness), the market will accept and use that value directly for USDH-collateralized borrows and liquidations because `oracle-price-legal`/`oracle-timestamp-fresh` do not catch outlier magnitude. This can let a borrower drain other users' deposited assets against an inflated USDH collateral value (theft of user funds), or cause incorrect liquidations/freezing of otherwise-healthy positions if USDH price is deflated (temporary freezing of funds) — both landing in-scope impact classes.

### Likelihood Explanation
Likelihood is moderate: it requires a genuine outlier/anomaly in the DIA feed (glitch, stale-but-monotonic update, or a compromised upstream that still returns a well-formed, non-zero, monotonically-increasing timestamp), which is exactly the "malfunctioning oracle" scenario the external report is about. The code path is reachable unconditionally by any ordinary principal calling deposit/borrow/liquidate against USDH-backed positions, with no protocol-side circuit breaker beyond the trivial `> 0` and staleness/monotonic-timestamp checks.

### Recommendation
Apply an equivalent bound to the DIA path as is applied to Pyth: e.g., require the reported price to be within some maximum percentage deviation from the last accepted price (or from a secondary reference), and/or require DIA to expose and enforce its own reported deviation/confidence metric analogous to Pyth's `conf` field, gated by `check-confidence`-style logic. At minimum, extend `oracle-price-legal`/`price-resolve` with a bounded deviation check applied uniformly across all oracle types rather than only Pyth.

### Proof of Concept
1. DIA oracle (external, mainnet contract `SP1G48FZ4Y7JY8G2Z0N51QTCYGBQ6F4J43J77BQC0.dia-oracle`) reports an anomalous USDH price (e.g., 10x actual) with a valid, monotonically increasing timestamp.
2. `call-dia` / `resolve-dia` in `v0-4-market.clar` forward the value untransformed: [3](#0-2) 
3. `price-resolve` passes it because `oracle-price-legal` only checks `> 0` and `oracle-timestamp-fresh` only checks staleness/monotonicity: [6](#0-5) 
4. Any ordinary principal supplying/borrowing USDH-denominated collateral or debt then has their position's health computed using the inflated/deflated price, enabling over-borrow (theft) or unjust liquidation (temporary freeze) of counterparty funds.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
