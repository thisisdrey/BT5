Audit Report

## Title
Permissionless `pallet-asset-conversion` pools can be permanently frozen by the asset's own (attacker-controlled) `Freezer` role - ([File: substrate/frame/asset-conversion/src/lib.rs])

## Summary
`pallet-asset-conversion::create_pool`/`add_liquidity` are permissionless, signed-origin calls that accept any `T::AssetKind`, including ordinary `pallet-assets` (trust-backed) assets created via the permissionless `pallet_assets::create` extrinsic, where the creator names themselves `Issuer`/`Admin`/`Freezer` [1](#0-0) . That self-appointed `Freezer` can later call `Assets::freeze(origin, id, who)` on the pool's own vault account, since the dispatchable only checks `origin == d.freezer` with no special-casing of protocol-owned accounts [2](#0-1) , after which transfers of that asset out of the frozen account fail with `Error::Frozen`, permanently trapping any paired liquidity in the pool [3](#0-2) .

## Finding Description
`do_create_pool` computes a deterministic `pool_account` and calls `T::Assets::touch`/`Mutate` on both supplied `AssetKind`s without any inspection of the asset's `Owner`/`Admin`/`Issuer`/`Freezer` fields [4](#0-3) . `create_pool` and `add_liquidity` are both fully permissionless, signed-origin calls [5](#0-4) .

In production Asset Hub runtimes, `pallet_asset_conversion::Config::Assets` is backed by `NativeAndNonPoolAssets`, which wraps the trust-backed `pallet_assets` instance whose `CreateOrigin = AsEnsureOriginWithArg<EnsureSigned<AccountId>>` [6](#0-5)  and `AssetKind = xcm::v5::Location` [7](#0-6) . This confirms that any signed account can create a trust-backed asset and pool it against the native token, exactly as demonstrated in the emulated integration test `set_up_pool_with_wnd_on_ah_westend`, where a user mints/creates an asset and calls `AssetConversion::create_pool` and `add_liquidity` directly [8](#0-7) .

`Assets::freeze` only checks `origin == d.freezer` and does not check whether `who` (the account being frozen) is a special protocol-controlled account like an AMM vault [2](#0-1) . Once frozen, existing unit tests confirm outbound transfers from a frozen account fail with `Error::<Test>::Frozen`, while inbound transfers still succeed [3](#0-2) . `thaw` requires `origin == details.admin` [9](#0-8) , which for a self-created asset is the attacker themselves, so there is no recovery path for the protocol or LPs.

Neither `do_create_pool` nor `do_add_liquidity` validate the team fields of the supplied `AssetKind` before accepting it into a pool, and the `T::Assets: Inspect + Mutate + AccountTouch + Balanced + Refund` trait bound used by the pallet has no "safe asset" concept [10](#0-9) .

## Impact Explanation
Freezing the shared `pool_account` for one leg of a pair blocks all outbound transfers of that asset from the vault, which halts `swap_exact_tokens_for_tokens`, `swap_tokens_for_exact_tokens`, and `remove_liquidity` for that pool, since removal requires moving both legs out of the same account. Any legitimate counter-asset (e.g., native token) paired against the malicious asset becomes permanently locked in the pool together with the frozen asset. This matches the "permanent user-fund lock" impact class in the gate, since it is a direct, unrecoverable value-lock reachable by an ordinary signed account with no governance, admin, or validator involvement, and is reproducible against any live pool that includes an attacker-created trust-backed asset.

## Likelihood Explanation
High. `pallet_assets::create` is permissionless under `AsEnsureOriginWithArg<EnsureSigned<AccountId>>` in production Asset Hub configs, and `create_pool`/`add_liquidity` are permissionless signed extrinsics reachable by any account with ordinary funds to cover deposits/fees. No admin, governance, or validator/collator privilege is needed — the "Freezer" role invoked is self-assigned by the attacker on their own asset, not a protocol-level privilege, so it does not fall under the "privileged governance or admin abuse as the root cause" exclusion. The attack is repeatable against any pool pairing a well-known asset with an attacker-controlled trust-backed asset.

## Recommendation
- Before accepting an `AssetKind` into `create_pool`/`add_liquidity`, verify the asset's `Freezer`/`Admin`/`Owner` fields are not externally controlled (e.g., require `Freezer == None`, `Freezer == pool pallet's account`, or restrict poolable non-native assets to a governance-vetted allow-list).
- Alternatively, expose a `fungibles::roles::Inspect` check (`owner`/`admin`/`issuer`/`freezer`) in `do_create_pool` and reject assets whose freezer/admin is not a trusted/system account.
- Consider adding a "safe asset" filter trait to `pallet-asset-conversion`'s `Config`, analogous to the existing `PoolSetupFee`/sufficiency spam-prevention mechanisms, so runtime integrators can plug in their own asset-trust policy.

## Proof of Concept
1. Attacker calls `Assets::create(origin=attacker, id=X, admin=attacker, min_balance)` (permissionless under `EnsureSigned`), making themselves `Owner`/`Issuer`/`Admin`/`Freezer` of asset `X` [1](#0-0) .
2. Attacker (or anyone) calls `AssetConversion::create_pool(Native, WithId(X))` then `add_liquidity`, as shown reachable in `set_up_pool_with_wnd_on_ah_westend` [11](#0-10) ; other LPs subsequently add real native-token liquidity into the same `pool_account`.
3. Attacker calls `Assets::freeze(origin=attacker, id=X, who=pool_account)`; since `origin == d.freezer` holds, the call succeeds and sets `AccountStatus::Frozen` on the pool's `X` balance [2](#0-1) .
4. Any subsequent `swap_*`/`remove_liquidity` requiring an outbound transfer of `X` from `pool_account` fails with `Error::Frozen`, per the behavior confirmed in `transferring_from_frozen_account_should_not_work` [3](#0-2) , permanently stranding both legs of the pool since only the attacker (as `Admin`) can `thaw`.

			origin: OriginFor<T>,
			id: T::AssetIdParameter,
			admin: AccountIdLookupOf<T>,
			min_balance: T::Balance,
		) -> DispatchResult {

			let owner = T::CreateOrigin::ensure_origin(origin, &id)?;

					owner: owner.clone(),
					issuer: admin.clone(),
					admin: admin.clone(),

					deposit,
					min_balance,
					is_sufficient: false,
					accounts: 0,
					sufficients: 0,
					approvals: 0,
					status: AssetStatus::Live,
				},
			);

			T::AssetIdAllocator::advance().map_err(|_| Error::<T, I>::AssetIdAllocationFailed)?;
			Self::deposit_event(Event::Created {
				asset_id: id,
				creator: owner.clone(),
				owner: admin,
			});

			Ok(())
		}

					AccountStatus::Frozen;
				Ok(())
			})?;

			Self::deposit_event(Event::<T, I>::Frozen { asset_id: id, who });
			Ok(())
		}

		pub(crate) fn do_create_pool(
			creator: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			initial_fee: Option<Permill>,
		) -> Result<T::PoolId, DispatchError> {
			ensure!(asset1 != asset2, Error::<T>::InvalidAssetPair);
			if let Some(fee) = initial_fee {
				ensure!(fee <= T::MaxSwapFee::get(), Error::<T>::FeeTooHigh);
			}

			// prepare pool_id
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;
			ensure!(!Pools::<T>::contains_key(&pool_id), Error::<T>::PoolExists);

			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;

			// pay the setup fee
			let fee =
				Self::withdraw(T::PoolSetupFeeAsset::get(), creator, T::PoolSetupFee::get(), true)?;
			T::PoolSetupFeeTarget::on_unbalanced(fee);

			if T::Assets::should_touch(asset1.clone(), &pool_account) {
				T::Assets::touch(asset1.clone(), &pool_account, creator)?
			};

			if T::Assets::should_touch(asset2.clone(), &pool_account) {
				T::Assets::touch(asset2.clone(), &pool_account, creator)?
			};

			let lp_token = NextPoolAssetId::<T>::get()
				.or(T::PoolAssetId::initial_value())
				.ok_or(Error::<T>::IncorrectPoolAssetId)?;
			let next_lp_token_id = lp_token.increment().ok_or(Error::<T>::IncorrectPoolAssetId)?;
			NextPoolAssetId::<T>::set(Some(next_lp_token_id));

			T::PoolAssets::create(lp_token.clone(), pool_account.clone(), false, 1u32.into())?;
			if T::PoolAssets::should_touch(lp_token.clone(), &pool_account) {
				T::PoolAssets::touch(lp_token.clone(), &pool_account, creator)?
			};
