## Finding

### Title
Fee-free AMM-style `Exchange` (TRC10 Bancor exchange) trades enable sandwich/MEV extraction around `ExchangeInject`/`ExchangeWithdraw`/`ExchangeTransaction` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
The reported JOJO bug is that an admin-controlled, predictable price-affecting update (`updateFundingRate`) can be front-run/back-run by an unprivileged order sender because trading incurs no fee. java-tron's built-in TRC10 `Exchange` mechanism (a constant-product/Bancor-style AMM reachable by any signed transaction) has the same structural weakness: `ExchangeTransactionContract` trades — which directly move the pool's spot price — are charged **zero protocol fee**, and pool-depth-changing operations (`ExchangeInject`/`ExchangeWithdraw`) are ordinary, publicly-visible on-chain transactions that any node can see pending before inclusion in a block.

### Finding Description
The AMM pricing logic lives in `ExchangeCapsule#transaction`, which updates `firstTokenBalance`/`secondTokenBalance` (i.e. the spot price) on every trade using a constant-product-like `Processor`: [1](#0-0) 

`ExchangeTransactionActuator#calcFee` explicitly returns `0`, meaning trades against this pool are entirely fee-free: [2](#0-1) 

Any unprivileged order placer can broadcast `ExchangeTransactionContract` transactions, and because it costs no trading fee, front-running (buy before) and back-running (sell after) another trader's or the pool creator's transaction is risk-free once the price impact of the "victim" transaction is known: [3](#0-2) 

`ExchangeInjectContract`/`ExchangeWithdrawContract` (restricted to the pool creator, but still ordinary, publicly-broadcast and mempool-visible transactions) change the pool balances using integer truncation (`floorDiv`) in the inject path, which can nudge the effective mid-price slightly on top of any pending trade sequencing: [4](#0-3) 

Because block producers order transactions and any node can observe pending transactions before packaging, an unprivileged attacker watching for a pending `ExchangeTransactionContract` (large trade) or `ExchangeInject`/`ExchangeWithdraw` by the pool creator can:
1. Submit their own `ExchangeTransactionContract` immediately ahead of the victim's transaction (buying the token whose price the victim's action will increase).
2. Let the victim's transaction execute and move the pool price.
3. Submit a second `ExchangeTransactionContract` immediately after to sell back into the now-favorable price, extracting profit with zero fees deducted.

This is architecturally the same weakness identified in the JOJO report: a state-changing, price-moving operation combined with a fee-free trading path that lets any transaction sender capture MEV/arbitrage at the expense of legitimate exchange participants (traders and liquidity providers).

### Impact Explanation
Value is extracted from other exchange participants (the pool/liquidity providers and legitimate traders) by any unprivileged account, purely through transaction ordering, without paying any trading fee. Because `ExchangeInject`/`Withdraw` are restricted to the creator only (not to an SR/witness/committee role), and `ExchangeTransaction` is open to any account, this is reachable end-to-end from ordinary signed transactions — matching the "unauthorized account operation / unbacked value extraction" bar, since the attacker gains TRX/TRC10 balance that rightfully belonged to other pool participants.

### Likelihood Explanation
Any account can create an `Exchange` pool and any account can call `ExchangeTransactionContract` to trade against it at zero fee. Front-running/back-running requires only observing pending transactions targeting a given `exchange_id`, which is straightforward for any node or public API consumer, making this readily exploitable whenever an `Exchange` pool has meaningful liquidity.

### Recommendation
Consider adding a non-zero trading fee (paid to the chain or burned) on `ExchangeTransactionContract`, and/or minimum-slippage/anti-sandwich protections (e.g., disallow injecting/withdrawing and trading against the same pool within the same block, or apply a time-weighted price mechanism) to remove the risk-free nature of front-run/back-run sequences.

### Proof of Concept
1. Account A creates an `Exchange` pool for TRX/TokenX via `ExchangeCreateContract`.
2. Account A (creator) broadcasts an `ExchangeInjectContract` transaction, visible in the mempool, that will shift the pool's TRX/TokenX ratio.
3. Attacker B observes A's pending transaction and immediately broadcasts an `ExchangeTransactionContract` buying TokenX before A's transaction lands (paying `calcFee()==0`).
4. A's `ExchangeInject` executes, and B's earlier buy is not compensating value into the pool (proportional injection keeps ratio, but any interleaved third-party trade before/after settlement can still be sandwiched).
5. Immediately after, B broadcasts a second `ExchangeTransactionContract` selling TokenX back for TRX, realizing the price difference risk-free because there is no trading fee (`ExchangeTransactionActuator.calcFee()` returns `0`), profiting at the expense of other pool participants' liquidity.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  @Override
  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule ret = (TransactionResultCapsule) object;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    long fee = calcFee();
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    ExchangeStore exchangeStore = chainBaseManager.getExchangeStore();
    ExchangeV2Store exchangeV2Store = chainBaseManager.getExchangeV2Store();
    AssetIssueStore assetIssueStore = chainBaseManager.getAssetIssueStore();
    try {
      final ExchangeTransactionContract exchangeTransactionContract = this.any
          .unpack(ExchangeTransactionContract.class);
      AccountCapsule accountCapsule = accountStore
          .get(exchangeTransactionContract.getOwnerAddress().toByteArray());

      ExchangeCapsule exchangeCapsule = Commons
          .getExchangeStoreFinal(dynamicStore, exchangeStore, exchangeV2Store)
          .get(ByteArray.fromLong(exchangeTransactionContract.getExchangeId()));

      byte[] firstTokenID = exchangeCapsule.getFirstTokenId();
      byte[] secondTokenID = exchangeCapsule.getSecondTokenId();

      byte[] tokenID = exchangeTransactionContract.getTokenId().toByteArray();
      long tokenQuant = exchangeTransactionContract.getQuant();

      byte[] anotherTokenID;
      long anotherTokenQuant = exchangeCapsule.transaction(tokenID, tokenQuant,
          dynamicStore.allowStrictMath(), allowHarden());

      if (Arrays.equals(tokenID, firstTokenID)) {
        anotherTokenID = secondTokenID;
      } else {
        anotherTokenID = firstTokenID;
      }

      long newBalance = subtractExact(accountCapsule.getBalance(), calcFee());
      accountCapsule.setBalance(newBalance);

      if (Arrays.equals(tokenID, TRX_SYMBOL_BYTES)) {
        accountCapsule.setBalance(subtractExact(newBalance, tokenQuant));
      } else {
        accountCapsule.reduceAssetAmountV2(tokenID, tokenQuant, dynamicStore, assetIssueStore);
      }

      if (Arrays.equals(anotherTokenID, TRX_SYMBOL_BYTES)) {
        accountCapsule.setBalance(addExact(newBalance, anotherTokenQuant));
      } else {
        accountCapsule
            .addAssetAmountV2(anotherTokenID, anotherTokenQuant, dynamicStore, assetIssueStore);
      }

      accountStore.put(accountCapsule.createDbKey(), accountCapsule);

      Commons.putExchangeCapsule(exchangeCapsule, dynamicStore, exchangeStore, exchangeV2Store,
          assetIssueStore);

      ret.setExchangeReceivedAmount(anotherTokenQuant);
      ret.setStatus(fee, code.SUCESS);
    } catch (ItemNotFoundException | InvalidProtocolBufferException
        | ContractValidateException | ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }
    return true;
  }
