### Title
Precision loss from division-before-multiplication in legacy (non-hardened) TVM energy limit calculation - (File: `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`)

### Summary
The energy allocation formula used by `EnergyProcessor.calculateGlobalEnergyLimit` truncates `frozeBalance` via integer division before multiplying by the network-wide energy ratio, exactly matching the "division before multiplication" precision-loss pattern from the referenced report. This code path is active by default (until the `ALLOW_HARDEN_RESOURCE_CALCULATION` chain parameter is turned on via committee proposal), and is reached on every energy-consuming smart-contract call.

### Finding Description
`calculateGlobalEnergyLimit` computes the caller's energy limit as: [1](#0-0) 

```java
if (hardenCalculation()) {
  return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
}
long energyWeight = frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```

`frozeBalance / TRX_PRECISION` is an integer (long) division performed **before** the multiplication by `totalEnergyLimit / totalEnergyWeight`. Any fractional TRX below `TRX_PRECISION` (1,000,000 sun) in `frozeBalance` is discarded immediately, and that lost fraction can never be recovered by the subsequent multiplication — this is the identical bug class described in the external report, where `bareIncrease / PRECISION_FACTOR_YEAR` is computed before multiplying by `poolFee`.

The correct order (multiply first, then divide) is already implemented as the "hardened" replacement `calculateGlobalLimitV1`, gated behind the `hardenCalculation()` flag: [2](#0-1) 

This confirms the maintainers are aware of and have already mitigated the exact same math flaw for `calculateGlobalLimitV1`/`calculateGlobalLimitV2` — but only when the corresponding chain parameter is enabled. The parameter `ALLOW_HARDEN_RESOURCE_CALCULATION` is a governance-controlled dynamic property (referenced across `ProposalUtil`, `DynamicPropertiesStore`, `VMConfig`) which, following the standard java-tron pattern for new chain parameters, defaults to `0` (disabled) until activated by a committee proposal. Until activated, the legacy, imprecise, non-hardened branch above remains live in production.

`calculateGlobalEnergyLimit` is invoked from `useEnergy` and `getAccountLeftEnergyFromFreeze`, which are called on every smart-contract execution to determine how much energy an account may spend without paying TRX fees: [3](#0-2) 

This is directly reachable by any unprivileged account that submits a `TriggerSmartContract` transaction, since the actuator validate/execute path for contract calls consults the account's frozen-for-energy energy limit before charging TRX for energy consumption.

### Impact Explanation
Because `frozeBalance / TRX_PRECISION` truncates before the ratio multiplication, accounts whose frozen balance is not an exact multiple of `TRX_PRECISION` (1 TRX) systematically receive a smaller free-energy allowance than the economically correct proportional share of `totalEnergyLimit`. In the aggregate, across all frozen-for-energy accounts, this causes the sum of allotted "free" energy to diverge (generally undercount, but the divergence is not scaled correctly with `totalEnergyWeight`/`totalEnergyLimit`), meaning free energy accounting used to avoid TRX burn for `energy_fee` is computed off from the intended proportional formula. This is a resource-accounting correctness bug that affects free energy entitlement calculations for every energy-consuming transaction, matching the "math/precision-loss" class of the referenced report, but with a comparatively lower financial blast radius (it affects free energy quota fairness/accuracy rather than direct fund transfer or unbacked-balance minting).

### Likelihood Explanation
This code executes unconditionally for every account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` on every smart-contract-triggering transaction, as long as `ALLOW_HARDEN_RESOURCE_CALCULATION` has not been enabled via governance proposal — which is the default network state absent an explicit committee vote. No special privileges are required to trigger the calculation; any account freezing TRX for energy and calling a contract exercises this path.

### Recommendation
Make the corrected (hardened) computation the default and unconditional implementation rather than gating it behind an opt-in governance flag, i.e., always compute via the multiply-then-divide (BigInteger) formula used in `calculateGlobalLimitV1`/`calculateGlobalLimitV2`, eliminating the truncating `frozeBalance / TRX_PRECISION` step performed before the ratio multiplication.

### Proof of Concept
Given (pre-hardening path):
```
frozeBalance = 1_999_999          // 1.999999 TRX, TRX_PRECISION = 1_000_000
totalEnergyLimit = 3
totalEnergyWeight = 2
```
Legacy (buggy) computation:
```
energyWeight = frozeBalance / TRX_PRECISION = 1_999_999 / 1_000_000 = 1        // truncated
result = (long) (1 * (3.0 / 2)) = 1
```
Correct (hardened) computation:
```
result = (frozeBalance * totalEnergyLimit) / (TRX_PRECISION * totalEnergyWeight)
        = (1_999_999 * 3) / (1_000_000 * 2)
        = 5_999_997 / 2_000_000
        = 2
```
The legacy path yields `1` while the mathematically correct proportional result is `2` — a 50% shortfall in allotted free energy for the affected account, directly reproducing the "division-before-multiplication" precision-loss pattern of the referenced report. This is exercised any time `calculateGlobalEnergyLimit` is called with the hardened flag disabled (default), i.e. on ordinary contract-call transactions.

  protected long calculateGlobalLimitV1(long frozeBalance,
      long totalLimit, long totalWeight) {
    long weight = frozeBalance / TRX_PRECISION;
    return BigInteger.valueOf(weight)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(totalWeight))
        .longValueExact();
  }
