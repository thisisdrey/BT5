## Finding

### Title
Unvalidated archive member name length causes panic in `internal/xcoff.NewArchive` when parsing malicious AIX big-archive files - (File: src/internal/xcoff/ar.go)

### Summary
`xcoff.NewArchive` parses the AIX "big archive" (`<bigaf>`) member header and trusts the attacker-controlled `Arnamlen` text field to size a byte slice without validating that the parsed value is non-negative or sane. A crafted archive with a negative name-length field (e.g. `"-1"`) causes `make([]byte, namlen)` to panic with `makeslice: len out of range`, crashing any process that parses the archive. This is the direct Go analog of CVE-2017-12451: an unvalidated size field taken from an untrusted COFF/XCOFF archive header drives a memory-allocation/read operation without bounds checking.

### Finding Description
Untrusted input enters via `go/importer.ForCompiler(fset, "gccgo", lookup)` [1](#0-0) , which builds a `gccgoimporter.Importer` that is invoked to resolve import paths for gccgo-compiled packages. Resolving a package backed by an AIX big-archive (`.a`) file routes through `aixBigArExportData`, which calls `xcoff.NewArchive(archiveAt)` on the archive reader [2](#0-1) .

Inside `NewArchive`, each member header's name-length field is decoded with `parseDecimalBytes`, which is a thin wrapper over `strconv.ParseInt` (base 10) that accepts negative values, and the result is used directly to allocate a byte slice with no lower-bound check: [3](#0-2) 

If `mhdr.Arnamlen` decodes to a negative number (a 4-byte ASCII field can hold `"-1"` easily), `make([]byte, namlen)` panics. Unlike the C code in the CVE, Go's runtime prevents an actual out-of-bounds memory read, but the trust placed in the unvalidated archive header field is structurally identical: a size/length taken from attacker-supplied archive metadata is used as a raw allocation/read parameter without sanity checking (`namlen >= 0`), producing a crash instead of silent memory corruption.

### Impact Explanation
The result is a reliable, attacker-triggered panic (denial of service) in any Go program that uses `go/importer`/`go/internal/gccgoimporter` to resolve gccgo-compiled package archives supplied by a third party — e.g., a `go vet`/analysis tool or IDE (gopls) processing an untrusted gccgo-compiled dependency. This maps to Go's PUBLIC/regular track as a parser-panic-on-malicious-input bug: it doesn't allow code execution but does allow an unauthenticated/ordinary "malicious archive file" to crash a normal victim workflow (type-checking/importing a package).

### Likelihood Explanation
An attacker able to supply a `.a` archive (e.g., a malicious or corrupted gccgo-compiled library shipped as a dependency, cross-compilation artifact, or vendored archive) that gets loaded by `go/importer.ForCompiler(..., "gccgo", ...)` triggers this without any special privilege — the caller only needs to run a normal import/type-check workflow against attacker-controlled archive data.

### Recommendation
Validate `namlen` (and similarly `size` from `Arsize`, and the file-header offsets) in `internal/xcoff/ar.go`'s `NewArchive` to ensure they are non-negative and within the remaining archive bounds before using them in `make()` or `io.NewSectionReader`, returning a descriptive error instead of allowing a panic.
