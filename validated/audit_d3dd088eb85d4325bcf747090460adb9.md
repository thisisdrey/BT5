Audit Report

## Title
Pallet `multi-asset-bounties` lacks a `reclaim_bounty_funds`-style recovery path, permanently locking stranded value in a bounty's derived account - (File: `substrate/frame/multi-asset-bounties/src/lib.rs`)

## Summary
`pallet-multi-asset-bounties` derives per-bounty and per-child-bounty accounts (`bounty_account`, `child_bounty_account`) that hold escrowed native/asset balances while asynchronous `Paymaster`-driven payments are in flight, and once `check_status` observes a successful refund or payout it calls `remove_bounty` to delete the corresponding storage entry [1](#0-0) . No dispatchable in this pallet exists to sweep any balance left in a derived account after its storage record is deleted, unlike `pallet-bounties`, which added `reclaim_bounty_funds` specifically to fix this defect [2](#0-1) .

## Finding Description
`check_status` transitions `RefundAttempted`/`PayoutAttempted` bounties to a terminal state by calling `Self::remove_bounty(parent_bounty_id, child_bounty_id, metadata)` as soon as the payment status is `Succeeded`, immediately returning `Ok(Pays::No.into())` [3](#0-2) . `remove_bounty` only removes the `Bounties`/`ChildBounties` storage entries (and associated counters), it performs no verification or sweep of the derived account's balance [1](#0-0) . Funding, refund, and payout flows all move funds into/out of these deterministically-derived accounts (`bounty_account`, `child_bounty_account`) via `T::Paymaster::pay`, as seen in `do_process_funding_payment` [4](#0-3) . A search of the crate for a sweep/reclaim dispatchable analogous to `pallet-bounties::reclaim_bounty_funds` returns no matches; the pallet's dispatchables are limited to funding, curator-management, award, close, `check_status`, and `retry_payment` style calls. Once a bounty/child-bounty entry is removed from storage, there is no code path referencing that now-nonexistent index that could redirect any residual or accidentally-sent balance in the deterministic derived account back to a beneficiary or the treasury/funding source.

## Impact Explanation
Any balance left in a bounty's or child-bounty's derived account after its storage entry is removed (via accidental transfer to the deterministically-computable derived address, dust, or a payment that settles for less than the full escrowed amount) becomes permanently unreachable, matching the "permanent user-fund... lock" impact category. This mirrors the exact defect that was fixed in `pallet-bounties` via `reclaim_bounty_funds` [2](#0-1) , and `pallet-multi-asset-bounties` uses the identical derived-account/async-payment architecture without an equivalent fix [5](#0-4) .

## Likelihood Explanation
Triggering this does not require privileged access: any account can compute a bounty's or child-bounty's derived address off-chain and send funds to it, or dust/residual balances can occur naturally from the asynchronous payment lifecycle before `remove_bounty` deletes the tracking entry. This is the same class of trigger that `pallet-bounties`' regression tests (`reclaim_bounty_funds_works_after_accidental_refund`) were written to cover [6](#0-5) .

## Recommendation
Port an equivalent permissionless `reclaim_bounty_funds`-style sweep into `pallet-multi-asset-bounties`, keyed on the deterministic bounty/child-bounty derived account, that works regardless of whether the corresponding storage entry still exists, sweeps both native and configured asset kinds, and respects locks/freezes via `Expendable`-preserving transfer semantics, mirroring the design added in `pallet-bounties` [2](#0-1) .

## Proof of Concept
1. Fund and drive a child-bounty through `FundingAttempted` → `Active` → `RefundAttempted`/`PayoutAttempted` to `Succeeded`, triggering `check_status` to call `remove_bounty` and delete the storage entry [7](#0-6) .
2. Compute the same bounty's derived account (`bounty_account`/`child_bounty_account`) off-chain and send additional native or asset balance to it, or rely on any residual balance left after settlement.
3. Confirm no dispatchable in the pallet references the removed index or the derived account to sweep this balance elsewhere — the pallet's call surface (funding, award, close, `check_status`, `retry_payment`) contains no reclaim/sweep primitive, leaving the value permanently stranded.

	/// Cleanup a child-/bounty from the storage.
	fn remove_bounty(
		parent_bounty_id: BountyIndex,
		child_bounty_id: Option<BountyIndex>,
		metadata: T::Hash,
	) {
		match child_bounty_id {
			None => {
				Bounties::<T, I>::remove(parent_bounty_id);
				ChildBountiesPerParent::<T, I>::remove(parent_bounty_id);
				TotalChildBountiesPerParent::<T, I>::remove(parent_bounty_id);
				ChildBountiesValuePerParent::<T, I>::remove(parent_bounty_id);
			},
			Some(child_bounty_id) => {
				ChildBounties::<T, I>::remove(parent_bounty_id, child_bounty_id);
				ChildBountiesPerParent::<T, I>::mutate(parent_bounty_id, |count| {
					count.saturating_dec()
				});
			},
		}

		T::Preimages::unrequest(&metadata);
	}

	/// Initiates payment from the funding source to the child-/bounty account/location.
	fn do_process_funding_payment(
		parent_bounty_id: BountyIndex,
		child_bounty_id: Option<BountyIndex>,
		asset_kind: T::AssetKind,
		value: T::Balance,
		maybe_payment_status: Option<PaymentState<PaymentIdOf<T, I>>>,
	) -> Result<PaymentState<PaymentIdOf<T, I>>, DispatchError> {
		if let Some(payment_status) = maybe_payment_status {
			ensure!(payment_status.is_pending_or_failed(), Error::<T, I>::UnexpectedStatus);
		}

		let (source, beneficiary) = match child_bounty_id {
			None => (
				Self::funding_source_account(asset_kind.clone())?,
				Self::bounty_account(parent_bounty_id, asset_kind.clone())?,
			),
			Some(child_bounty_id) => (
				Self::bounty_account(parent_bounty_id, asset_kind.clone())?,
				Self::child_bounty_account(parent_bounty_id, child_bounty_id, asset_kind.clone())?,
			),
		};

		let id = <T as Config<I>>::Paymaster::pay(&source, &beneficiary, asset_kind, value)
			.map_err(|_| Error::<T, I>::FundingError)?;

		Self::deposit_event(Event::<T, I>::Paid {
			index: parent_bounty_id,
			child_index: child_bounty_id,
			payment_id: id,
		});

		Ok(PaymentState::Attempted { id })
	}

#[test]
fn reclaim_bounty_funds_works_after_accidental_refund() {
	ExtBuilder::default().build_and_execute(|| {
		Balances::make_free_balance_be(&Treasury::account_id(), 101);

		// Full lifecycle: propose → approve → fund → curator → award → claim
		assert_ok!(Bounties::propose_bounty(RuntimeOrigin::signed(0), 50, b"12345".to_vec()));
		assert_ok!(Bounties::approve_bounty(RuntimeOrigin::root(), 0));
		go_to_block(2);

		let fee = 4;
		Balances::make_free_balance_be(&4, 10);
		assert_ok!(Bounties::propose_curator(RuntimeOrigin::root(), 0, 4, fee));
		assert_ok!(Bounties::accept_curator(RuntimeOrigin::signed(4), 0));
		assert_ok!(Bounties::award_bounty(RuntimeOrigin::signed(4), 0, 3));
		go_to_block(5);
		assert_ok!(Bounties::claim_bounty(RuntimeOrigin::signed(1), 0));

		// Bounty is now fully closed; verify it is gone from storage.
		assert!(pallet_bounties::Bounties::<Test>::get(0).is_none());

		let bounty_account = Bounties::bounty_account_id(0);
		// Account should already be empty after claim.
		assert_eq!(Balances::free_balance(&bounty_account), 0);
