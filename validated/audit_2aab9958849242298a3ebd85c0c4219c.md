### Title
Unbounded `ContractType` value causes uncaught `IndexOutOfBoundsException` in permission-operations bitmask check - ([File: chainbase/src/main/java/org/tron/common/utils/WalletUtil.java])

### Summary
`WalletUtil.checkPermissionOperations` indexes a fixed 32-byte `operations` bitmask using `contract.getTypeValue() / 8` without validating that the resulting index is within `[0,31]`. Because `Tron.proto` is declared `syntax = "proto3"` and `ContractType` is a plain enum field, protobuf preserves any out-of-range int32 value written on the wire for `Transaction.Contract.type` (open enum semantics), so an unprivileged transaction sender can set an arbitrary/huge `type` integer and reach this unchecked array index, producing an uncaught `IndexOutOfBoundsException`.

### Finding Description
`checkPermissionOperations` is:
```java
public static boolean checkPermissionOperations(Permission permission, Contract contract)
    throws PermissionException {
  ByteString operations = permission.getOperations();
  if (operations.size() != 32) {
    throw new PermissionException(...);
  }
  int contractType = contract.getTypeValue();
  boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
  return b;
}
``` [1](#0-0) 

`operations` is always exactly 32 bytes (enforced just above), representing bit-flags for 256 known contract types. `contractType` is taken directly from `contract.getTypeValue()`, the raw integer of the transaction's `type` field, with no range check (no `>= 0 && < 256` guard) before being divided by 8 and used as a `ByteString.byteAt` index.

This mirrors the CVE-2025-38110 bug class: an index/address value taken from attacker-controlled input is used to access a fixed-size internal array/bitmap without validating it against the array's bound (`PHY_MAX_ADDR` in the kernel bug vs. the 32-byte `operations` array here).

Because the proto file uses `proto3` syntax (`protocol/src/main/protos/core/Tron.proto:1`), enum fields are "open": an unrecognized/out-of-range value assigned to `Transaction.Contract.type` on the wire is preserved verbatim and returned by `getTypeValue()`, rather than being clamped or rejected. A transaction built with a raw/manually-crafted protobuf payload (bypassing the client SDK's enum name-based construction) can therefore set `type` to an arbitrary large int32 (e.g. `Integer.MAX_VALUE`), yielding `contractType/8` far outside `[0,31]`.

The same unguarded pattern is duplicated in three reachable call sites:
- `TransactionCapsule.checkPermission` → used by `TransactionCapsule.validateSignature` (transaction signature verification path) and `TransactionCapsule.addSign` [2](#0-1) 
- `Wallet.getTransactionApprovedList` (`/wallet/gettransactionapprovedlist` RPC/HTTP API) [3](#0-2) 
- `TransactionUtil.getTransactionSignWeight` (`/wallet/gettransactionsignweight` RPC/HTTP API) [4](#0-3) 

All three require the contract's `permission_id != 0` to enter the vulnerable branch, which any unprivileged sender can set via `Util.setTransactionPermissionId` on any broadcastable transaction [5](#0-4) .

### Impact Explanation
An `IndexOutOfBoundsException` is a `RuntimeException`, not one of the checked exceptions (`PermissionException`, `SignatureException`, `SignatureFormatException`) declared/caught along these call paths (e.g. `TransactionCapsule.validatePubSignature` only catches those three specific checked exceptions) [6](#0-5) . Depending on which entry point is used:
- The `getTransactionApprovedList` and `getTransactionSignWeight` API handlers wrap the call in a broad `try { ... } catch (Exception ex)` block, so those two specific query endpoints degrade gracefully (return `OTHER_ERROR`) rather than crash — this matches the "HTTP/gRPC/JSON-RPC query paths into Wallet" scope, but the impact there is limited to a caught error response, not a crash.
- `Wallet.broadcastTransaction` also has a final `catch (Exception e)` that would absorb the exception for that single call.

The more serious risk is in `Manager.pushTransaction`/`processTransaction`, which is used both for the caller's own broadcast and, once the malformed transaction is packed into a block (self-mined or received), for block application (`Manager.processTransaction` inside block replay). If an uncaught `RuntimeException` escapes here during block processing (unlike the broadcast path which has a catch-all), it can abort block application, leading to node halt/desync for any node re-validating that block — a chain-availability impact, though I could not fully confirm within the available context whether every call site on the block-application path also wraps this in a catch-all `Exception` handler (tool access ended before this could be verified with certainty).

### Likelihood Explanation
Triggering the bug only requires constructing a raw serialized `Transaction` where `Transaction.Contract.type` is set to an out-of-range integer (a trivial protobuf encoding change) and `permission_id` set to a non-zero value, then submitting it to `/wallet/gettransactionapprovedlist`, `/wallet/gettransactionsignweight`, or via `broadcastTransaction`/`addSign`. No special privileges, keys, or SR/committee status are required — any external API client or transaction broadcaster can attempt it. Likelihood is High for reaching the unchecked index; the severity of the resulting effect (caught vs. uncaught) depends on the exact call path, which is Medium-confidence based on the code reviewed.

### Recommendation
In `WalletUtil.checkPermissionOperations` (and the equivalent inline copy in `TransactionCapsule`), validate `contractType` is within `[0, 255]` (i.e., `contractType/8` within `[0, operations.size()-1]`) before indexing, returning `false`/throwing `PermissionException` for out-of-range values, mirroring the kernel fix's approach of validating the address against `PHY_MAX_ADDR` before use.

### Proof of Concept
1. Build a `Transaction` whose `raw_data.contract[0].type` field is serialized with an out-of-range int32 (e.g. `Integer.MAX_VALUE`) instead of a valid `ContractType` enum value, and set `permission_id` to a non-zero value (e.g. `2`).
2. Submit this transaction to `wallet/gettransactionsignweight` or `wallet/gettransactionapprovedlist`, or attempt `addSign`/`broadcastTransaction`.
3. Observe that `WalletUtil.checkPermissionOperations`/`TransactionCapsule` execute `operations.byteAt(contractType / 8)` with an out-of-range index, throwing `IndexOutOfBoundsException`, exercising the unguarded-index bug class analogous to CVE-2025-38110. [1](#0-0)
