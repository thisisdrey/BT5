### Title
Frontier slot squatting via unverified self-reported address in inbound Handshake - ([File: stackslib/src/net/chat.rs, stackslib/src/net/db.rs])

### Summary
An inbound peer's `Handshake` message carries a self-reported `addrbytes`/`port` in `HandshakeData` that is used directly to build the `Neighbor` record persisted via `PeerDB::try_insert_peer`, without being checked against the actual TCP source address of the connection for inbound sessions. Because `PeerDB::try_insert_peer` (stackslib/src/net/db.rs:1452-1488) only checks slot occupancy for the claimed `(network_id, addrbytes, port)` tuple and never verifies that the reporting connection actually originates from that address, a single attacker keypair can open several inbound connections and each time claim a different, attacker-chosen `addrbytes`/`port`, writing forged `frontier` rows keyed to addresses it doesn't own.

### Finding Description
`PeerDB::try_insert_peer` computes candidate slots purely from `neighbor.addr.network_id`, `neighbor.addr.addrbytes`, and `neighbor.addr.port` (stackslib/src/net/db.rs:1470-1475), and inserts the `Neighbor` (including its `public_key`) into any free slot with `PeerDB::insert_or_replace_peer` (stackslib/src/net/db.rs:1480). The `neighbor.addr` value originates from the `HandshakeData` sent by the remote peer during `Handshake` processing in `stackslib/src/net/chat.rs`. For inbound connections, the address-consistency check in the handshake validation path does not compare the claimed address against the actual TCP peer address of the socket (this exemption is intentional to support NAT'd/publicly-routable-but-different-listen-port nodes announcing their real listen address). This breaks the implicit invariant that every `frontier` row's `(addrbytes, port)` corresponds to an address actually controlled by the holder of the associated `public_key`: an attacker with one valid secp256k1 keypair can open N inbound TCP connections and, on each, send a `Handshake` naming a distinct victim `(addrbytes, port)` pair it does not control, producing N forged `frontier` rows all bound to the attacker's real public key.

### Impact Explanation
Each forged row occupies a `frontier` slot for an address/port bucket that a legitimate peer at that address would otherwise use, crowding it out once all slots in that bucket are filled by attacker-controlled sockets — an unauthenticated write of forged network identity data into `PeerDB`, requiring no packet volume, only a handful of distinct Handshakes over independent TCP sessions. This matches the Critical category "unauthenticated write to state."

### Likelihood Explanation
The attacker needs only one legitimate secp256k1 keypair, the ability to open ordinary inbound TCP connections to the target node's P2P port, and knowledge of the target victim address(es) to squat on — all consistent with an unprivileged remote attacker. No secrets, admin roles, or packet volume are required; cost scales with the number of distinct forged entries desired (one Handshake per forged slot).

### Recommendation
For inbound connections, do not trust the self-reported `addrbytes`/`port` from `HandshakeData` for `frontier`/PeerDB persistence purposes. Either (a) key inbound peer identity/frontier slot allocation off the actual observed TCP source `SocketAddr` rather than the claimed address, or (b) require a verified "pingback" handshake (an outbound connection initiated by the local node back to the claimed address) to succeed before promoting an inbound-claimed address into a durable `frontier` slot, consistent with the existing neighbor-walk pingback pattern used elsewhere in the codebase.

### Proof of Concept
Rust test outline: create a `PeerDB` and a `PeerNetwork`/`ConversationP2P` instance representing a node accepting inbound connections; open several separate inbound `ConversationP2P` sessions from the same attacker keypair; for each session, construct and send a `StacksMessage::Handshake` with `HandshakeData.addrbytes`/`port` set to a distinct victim address not related to the test socket's actual peer address; drive the message through `ConversationP2P`'s handshake handling into `PeerDB::try_insert_peer`; then assert `PeerDB::get_peer(network_id, victim_addrbytes, victim_port)` returns a row whose `public_key` equals the attacker's key for multiple distinct victim addresses that were never the TCP peer address of the corresponding connection.
