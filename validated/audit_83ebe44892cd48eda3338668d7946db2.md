### Title
Unauthenticated `RecvError` packets allow remote tunnel teardown without cryptographic verification - (File: `outside.go`)

### Summary
`handleRecvError` in `outside.go` tears down an active tunnel (`f.closeTunnel(hostinfo)` and `hm.DeleteHostInfo(hostinfo)`) in response to a `header.RecvError` packet that is processed entirely before any decryption or MAC/authentication check, mirroring the reported bug class where a state-changing/closing function (`resolveAuctionWithoutGoverment` → `processDebtClaim`) is reachable without adequate identity/time filtering.

### Finding Description
In `outside.go`, `readOutsidePackets` dispatches unencrypted packet types before any per-packet cryptographic verification: [1](#0-0) 
`header.RecvError` is handled by `f.handleRecvError(via.UdpAddr, h)`, called directly on the raw header with no signature, MAC, or handshake-state check — unlike `header.Message`/`header.Test`/`header.CloseTunnel`, which are only processed after `hostinfo.ConnectionState.Decrypt` succeeds: [2](#0-1) 

`handleRecvError` itself performs only two soft checks: [3](#0-2) 
1. `acceptRecvErrorConfig.ShouldRecvError(addr)` — a config-based accept policy (`always`/`never`/`private`), not a cryptographic filter.
2. `hr.IsValid() && hr != addr` — this only rejects the packet if the hostinfo's `CurrentRemote` is both *set* and *mismatched* from the sender's address. If `hr` is not yet valid (e.g., during roaming or before the remote is pinned), the check is bypassed entirely.

`h.RemoteIndex` (the only "authorization" token used to locate the target `hostinfo` via `QueryReverseIndex`) is transmitted in cleartext in every packet header (see `header.Encode`/`h.Parse` in `header/header.go`), so it is not a secret — any on-path observer or a peer that has exchanged even a single packet with the target can read it. Combined with UDP's unauthenticated source address (which is trivially spoofable at the network layer, similar to how `resolveAuctionWithoutGoverment` accepted zero-value `pool`/`currentAuction.end`), this permits an attacker to close an active tunnel between two legitimate, certificate-verified peers by forging a single `RecvError` packet — the "close active pool at any time" bug-class analog.

This matches the report's pattern precisely: a state-mutating function (`closeTunnel`/`DeleteHostInfo`, analogous to `processDebtClaim`) is reachable via a message type that lacks proper origin/time/identity filtering (`pool`/`currentAuction.end` checks in the original report ↔ `hr.IsValid()` gap and lack of cryptographic authentication here).

### Impact Explanation
An attacker who can either observe traffic (to learn `RemoteIndex`) or spoof the UDP source address of a legitimate peer can force termination of an active, authenticated Nebula tunnel between two hosts. This is a remote state-poisoning / denial-of-service primitive: it does not require possessing a valid certificate or being a lighthouse/relay, and it defeats the mesh's connection stability guarantees, forcing repeated re-handshakes and enabling downgrade/interception windows during forced re-establishment (e.g., races exploited in `TestWrongResponderHandshake`).

### Likelihood Explanation
Reachable pre-authentication over UDP by anyone who can reach the listening port and knows (or can sniff) a valid `RemoteIndex`; no valid certificate is required. The `hr.IsValid()` gap widens the window where the address check is skipped entirely (e.g., early in a tunnel's life or after specific state transitions). Note that Nebula ships an existing e2e regression test, `TestCloseTunnelAuthenticated`, exercising a similar bogus-`CloseTunnel`-packet scenario for the `header.CloseTunnel` path (which *is* protected by decryption) — no equivalent authenticated-teardown test exists for `header.RecvError`, suggesting this path was not hardened to the same standard. [4](#0-3) 

### Recommendation
- Require the `hostinfo.GetRemote()` to be valid before honoring a `RecvError`-triggered teardown, or otherwise fail closed rather than proceeding when `hr.IsValid()` is false.
- Rate-limit and/or require a cryptographic proof (e.g., a MAC keyed by the tunnel's established session keys, or restricting to be decrypted like `CloseTunnel`) before acting on `RecvError` packets that mutate hostmap state.
- Consider moving `RecvError` handling to occur only after verifying the packet correlates with genuinely in-flight traffic (e.g., recent conntrack activity) rather than trusting the bare header.

### Proof of Concept
1. Observe (or otherwise learn) the `RemoteIndex` used between victim peers A and B (visible in cleartext in any exchanged packet header, per `header.H.Parse`).
2. Craft a UDP packet with `header.Encode(..., header.RecvError, 0, victimRemoteIndex, 0)` and send it to A's listening UDP port, spoofing (or simply using, if the check's `hr.IsValid()` gap applies) B's address.
3. On receipt, `readOutsidePackets` routes it to `handleRecvError` without any decryption/authentication (`outside.go:81-84`); if `acceptRecvErrorConfig` allows it and `hr` check is bypassed/matched, `f.closeTunnel(hostinfo)` and `hm.DeleteHostInfo(hostinfo)` execute, tearing down A's active tunnel to B.
4. Repeat as needed to cause A and B's tunnel to constantly re-handshake.

Note: I was unable to inspect the full bodies of `closeTunnel`, `QueryReverseIndex`, and `GetRemote`/`ShouldRecvError` due to tool/iteration limits — their signatures were located but not fully read, so exact edge-case behavior (e.g., whether `CurrentRemote` is unset in additional states beyond initial handshake) could not be fully confirmed. A Devin session with full file access would be needed to verify these details precisely.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
