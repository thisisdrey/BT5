### Title
Out-of-bounds read in ijar's ZIP central-directory parser when processing untrusted archive entries - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` reads central-directory fields (`file_name_length`, `extra_field_length`, and per-record extra-field `header_id`/`data_size`) directly from a memory-mapped ZIP/JAR file with no bounds checking against the mapped file's actual length, unlike its sibling `ProcessLocalFileEntry`, which explicitly guards every read with `EnsureRemaining()`.

### Finding Description
`ProcessCentralDirEntry` advances the cursor `p`/`extra_p` purely based on attacker-controlled length fields taken from the archive itself: [1](#0-0) 

```
p += 16;  // skip to 'compressed size' field
*compressed_size = get_u4le(p);
*uncompressed_size = get_u4le(p);
u2 file_name_length = get_u2le(p);
u2 extra_field_length = get_u2le(p);
...
{
  size_t len = (file_name_length < filename_size) ? file_name_length : (filename_size - 1);
  memcpy(reinterpret_cast<void*>(filename), p, len);
  filename[len] = 0;
}
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
``` [2](#0-1) 

None of `file_name_length`, `extra_field_length`, or `data_size` is validated against the true remaining bytes in the mapped input (`input_file_->Length()`). By contrast, `ProcessLocalFileEntry` calls `EnsureRemaining()` before every variable-length read: [3](#0-2) 

`EnsureRemaining` itself is only invoked in the local-file-entry path, not in the central-directory path: [4](#0-3) 

`ProcessCentralDirEntry` is invoked while iterating the whole central directory, both when actually processing entries and when precomputing output size: [5](#0-4) [6](#0-5) 

If a maliciously crafted (but correctly-checksummed) JAR/ZIP is presented to `ijar` (the interface-jar generator invoked for every `java_library`/`java_import` whose deps are compiled, including jars originating from `http_jar`, `http_archive`-provided jars, or Maven/registry artifacts pinned by `sha256`/`integrity`), a central-directory record whose declared `file_name_length`/`extra_field_length` exceeds the bytes actually remaining before the end of the mmap'd region causes `memcpy` and the extra-field parsing loop to read past the end of the allocated/mapped buffer. This is structurally the same defect class as CVE-2022-23124: a length field taken from attacker-supplied content is trusted without validating it against the real buffer bound before it drives a `memcpy`/pointer read, producing an out-of-bounds read that can disclose adjacent process memory (e.g., into `filename[PATH_MAX]`, which is later used/output) or crash the build. Because the sha256/integrity check only validates that the fetched bytes match what the attacker published — it does not validate the internal structural correctness of the archive — declared checksums do not stop this: an attacker who controls the archive's content is free to craft internally-inconsistent length fields while still matching a pinned digest.

### Impact Explanation
An attacker who can get a victim's build to feed a crafted JAR/ZIP into `ijar` (via any dependency-fetch mechanism that ultimately supplies a jar to `java_library`/`java_import`, e.g. `http_jar`, `http_archive`, or a registry module providing a prebuilt jar) can trigger an out-of-bounds read in the memory-mapped input file. This can leak adjacent process memory into the `filename` buffer/error/interface-jar output or crash the `ijar` process, matching the Medium-severity, network-reachable, no-authentication-required information-disclosure profile of CVE-2022-23124.

### Likelihood Explanation
Any dependency fetch pipeline that results in Bazel invoking `ijar` on a jar (which happens automatically for essentially every Java compilation) reaches this code path. The attacker only needs to control the content served at a URL/registry entry that a victim's build declares (with a self-consistent checksum), which matches the "hostile origin server whose content matches a declared checksum" threat model.

### Recommendation
Add explicit bounds checks in `InputZipFile::ProcessCentralDirEntry` (mirroring `EnsureRemaining()` in `ProcessLocalFileEntry`) before reading/advancing past `file_name_length`, `extra_field_length`, and each extra-field's `data_size`, failing the archive parse instead of reading past the mapped file boundary.

### Proof of Concept
Construct a minimal ZIP where the last Central Directory Header declares `file_name_length` and/or `extra_field_length` values that extend past the actual end of the mapped file (i.e., past the End Of Central Directory record), matching a legitimately-computed `sha256`. Feed this file as the archive input to `ijar` (e.g., via a `java_import`/`http_jar` target). Running `ijar` (or a `BuildIntegrationTestCase`/gtest analogous to `output_jar_simple_test.cc`'s `MalformedExtraField` test, but targeting `third_party/ijar/zip.cc`'s `ProcessCentralDirEntry` instead of `singlejar`'s already-guarded `AppendToDirectoryBuffer`) demonstrates the unguarded `memcpy`/pointer read walking past the mmap'd buffer, in contrast to `ProcessLocalFileEntry`, whose equivalent reads are protected by `EnsureRemaining()`.

  // abort with an error message.  "state" is the name of the field
  // we're about to read, for diagnostics.
  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
  }

      return false;
    }

  return true;
