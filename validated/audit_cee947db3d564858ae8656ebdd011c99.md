### Title
Bancor-style TRC10 exchange withdrawal amount is computed from instantaneous, self-manipulable pool balances, allowing the exchange creator to drain a disproportionate share of pooled tokens - (`actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The `ExchangeWithdrawActuator` (and its sibling `ExchangeInjectActuator`) compute the counter-token amount for a deposit/withdraw purely from the exchange's *current, spot* `firstTokenBalance`/`secondTokenBalance` ratio, exactly like the SPARTAN `getPoolShareWeight` pattern flagged in the referenced report (`uints * baseAmount / totalSupply`, i.e., a value derived from an instantaneously manipulable AMM reserve ratio). Because `ExchangeTransactionActuator` lets any account trade against the pool and change that ratio in the same block/series of self-broadcast transactions, and `ExchangeWithdrawActuator` immediately re-reads the freshly-skewed ratio with no time-delay, TWAP, or snapshot protection, the exchange creator can skew the price with a large self-trade and then withdraw a disproportionate amount of the other token, before reversing the trade.

### Finding Description
`ExchangeCapsule.transaction()` implements a Bancor relay/AMM curve and mutates `firstTokenBalance`/`secondTokenBalance` on every trade: [1](#0-0) 

`ExchangeTransactionActuator.execute` lets *any* account trade tokenID for anotherTokenID against the pool at the current spot ratio - this is a normal, permission-less, single-signed-transaction action: [2](#0-1) 

`ExchangeWithdrawActuator.doValidate`/`execute` compute the amount of the paired token to release using only the *live* pool balances at withdrawal time:
```
anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)...
``` [3](#0-2) [4](#0-3) 

There is no accounting for "shares"/"relay tokens" proportional to what was actually injected — unlike a normal LP model, the withdraw formula is recomputed from the current balance ratio each time, exactly the anti-pattern the report warns about (`uints * baseAmount / totalSupply` being manipulable because `baseAmount` is a live, tradable quantity). The only access control is that withdraw/inject are restricted to the exchange `creatorAddress` (`is not creator` check): [5](#0-4) 
but that creator is not privileged in any special way — anyone can become an exchange creator by broadcasting `ExchangeCreateContract`, satisfying the "unprivileged asset issuer/order placer" reachability requirement.

### Impact Explanation
An ordinary account that creates its own TRC10-TRC10 or TRC10-TRX exchange can:
1. Seed the exchange with some `firstToken`/`secondToken` liquidity via `ExchangeCreateContract`.
2. Execute a large self-trade via `ExchangeTransactionContract` selling `firstToken` into the pool, which (per the Bancor curve in `ExchangeCapsule.transaction`) inflates `firstTokenBalance` and drains `secondTokenBalance`, skewing the `firstTokenBalance/secondTokenBalance` ratio heavily in favor of `firstToken`.
3. Immediately call `ExchangeWithdrawContract` depositing a tiny amount of `secondToken`; because `anotherTokenQuant = firstTokenBalance * secondTokenQuant / secondTokenBalance` is now hugely inflated, the creator extracts a disproportionately large amount of `firstToken` out of the pool for a negligible `secondToken` payment.
4. Reverse the initial trade (sell `secondToken` back for `firstToken`) to restore the pool ratio, keeping the extracted surplus.

This constitutes theft/unbacked extraction of value from any counterparty who had also injected liquidity into the same exchange pool (via `ExchangeInjectContract`, which is open to any account, not just the creator, per `ExchangeInjectActuator.doValidate`), since the withdrawal is not proportional to actual contribution but to the instantaneous, self-manipulable spot ratio. This matches the "unauthorized account operation / theft of funds" bar.

### Likelihood Explanation
Every step (`ExchangeCreateContract`, `ExchangeTransactionContract`, `ExchangeWithdrawContract`, `ExchangeInjectContract`) is a normal, unprivileged, single-signed broadcastable transaction with no special permission requirements beyond owning the exchange (which itself is freely obtainable). No flash loan is even strictly required in this codebase because the attacker directly controls the AMM through their own trades within the exchange they created; the cost is only the bancor slippage/fees paid on the self-trades, similar to the slip-based fee cost described in the original report. This is directly and cheaply exploitable by any account.

### Recommendation
Do not compute inject/withdraw amounts from the instantaneous spot balance ratio. Instead, track an explicit proportional-ownership (LP-share) accounting for each exchange, or require that inject/withdraw pricing use a time-weighted/delayed snapshot of the pool ratio (e.g., ratio as of the start of the block or N blocks prior) so a single-transaction (or same-block) self-trade cannot be used to shift the ratio immediately before a withdrawal. Alternatively, restrict withdrawal amounts to be no more than proportional to the token amounts actually injected by that account, tracked independently of the tradable spot balances.

### Proof of Concept
1. Attacker broadcasts `ExchangeCreateContract` to create Exchange `E` with `firstToken = A`, `secondToken = B`, seeding e.g. `A=1,000,000`, `B=1,000,000` (creator = attacker).
2. Attacker broadcasts `ExchangeTransactionContract` on `E`, selling a very large quantity of `A` (e.g. `900,000`) into the pool. Per `ExchangeCapsule.transaction`, this drives `firstTokenBalance(A)` way up and `secondTokenBalance(B)` way down (Bancor curve), skewing `A/B` ratio strongly upward. (`ExchangeCapsule.java:124-168`)
3. Attacker (still the exchange creator) broadcasts `ExchangeWithdrawContract` with `tokenID = B`, `quant = 1` (a minimal amount of `B`). `ExchangeWithdrawActuator` computes `anotherTokenQuant (A received) = firstTokenBalance(A) * 1 / secondTokenBalance(B)`, which is now very large because `firstTokenBalance(A)` is inflated and `secondTokenBalance(B)` is depleted, releasing a disproportionately large amount of `A` from the pool for essentially free. (`ExchangeWithdrawActuator.java:74-89`, `214-243`)
4. Attacker broadcasts another `ExchangeTransactionContract` selling `B` back into the pool to restore the original `A/B` ratio, paying only Bancor slippage/fee, and keeps the `A` extracted in step 3 as profit.

Note: I was unable to independently confirm whether any other proposal/dynamic-property (e.g., a minimum holding period or later hardening for `Exchange*` actuators) mitigates this in the current codebase version beyond the `allowHarden`/precision checks reviewed (`AbstractExchangeActuator.java`), since those only guard against overflow/precision loss, not price-ratio manipulation. This should be verified against the live `ExchangeCreateActuator` validation logic and any related dynamic parameters before remediation.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
