### Title
Missing slippage control on `ExchangeInjectContract`/`ExchangeWithdrawContract` allows front-run/sandwich extraction from Bancor-style TRC10 exchange pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The `ExchangeTransactionContract` message includes an `expected` field that lets a caller specify the minimum amount of the counter-token they will accept, and `ExchangeTransactionActuator` enforces it during validation. [1](#0-0) [2](#0-1)  By contrast, `ExchangeInjectContract` and `ExchangeWithdrawContract` — which add/remove liquidity to the same Bancor-style pool and likewise compute a counter-token amount from the *current* on-chain pool ratio at execution time — carry no `expected`/minimum-return field and their actuators perform no analogous check, exactly the "lack of slippage control" pattern described in the referenced Kelp DAO `depositAsset` report. [3](#0-2) 

### Finding Description
`ExchangeInjectActuator.execute` computes `anotherTokenQuant` purely from the exchange's live `firstTokenBalance`/`secondTokenBalance` ratio at the moment the transaction is applied on-chain, with no user-supplied floor/ceiling: [4](#0-3) 
The same unconstrained ratio-based computation is repeated in `doValidate`, again with no comparison against any caller-provided expectation — only a "balance must be less than the exchange limit" and balance-sufficiency check are performed. [5](#0-4) 

`ExchangeWithdrawActuator` has the identical structure: `anotherTokenQuant` is derived from the pool ratio at execution time, and the only sanity checks are balance-sufficiency and a fixed-precision "Not precise enough" rounding check — neither of which lets the caller bound the economic result of the trade. [6](#0-5) [7](#0-6) 

The pool ratio (`firstTokenBalance`/`secondTokenBalance`) that both actuators read is the same state mutated by `ExchangeTransactionActuator.execute` via `ExchangeCapsule.transaction`, which uses the Bancor-formula `ExchangeProcessor`/`SafeExchangeProcessor` to move the ratio on every trade. [8](#0-7)  Because block producers order and can insert transactions within a block/epoch, and because any account can broadcast an `ExchangeTransactionContract` that shifts `firstTokenBalance`/`secondTokenBalance` before a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` executes, an attacker can sandwich a victim's inject/withdraw transaction: trade against the pool to skew the ratio, let the victim's inject/withdraw settle at the skewed ratio, then trade back — extracting value from the victim exactly as in the referenced report's oracle-price-manipulation scenario, except here the "oracle" is the on-chain pool state itself, which is even more directly and cheaply manipulable within a single transaction ordering.

### Impact Explanation
A victim injecting or withdrawing liquidity from an `Exchange` receives/gives up a counter-token amount determined solely by the pool ratio at block-inclusion time, with zero user-controlled bound. This is a direct, unauthorized value-transfer vector (theft of funds via sandwich/front-run) reachable by any account that can submit a signed `ExchangeInjectContract` or `ExchangeWithdrawContract` transaction plus a preceding/following `ExchangeTransactionContract` — no privileged role or witness/SR collusion needed. This maps to concrete "theft of funds" impact for exchange/market order handling paths, which is in-scope.

### Likelihood Explanation
Likelihood is high in any exchange pool with realistic liquidity: the attack only requires (a) knowledge of a pending inject/withdraw transaction (visible in the mempool since java-tron transactions are broadcast before block inclusion) and (b) enough of the traded token to move the ratio and reverse the trade, both of which are within reach of an ordinary, unprivileged account. `ExchangeTransactionContract` already had to add an `expected` parameter for this exact reason, confirming the maintainers recognized the risk for the trade path but left the inject/withdraw (liquidity) paths unprotected.

### Recommendation
Add an `expected`/limit field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`), and enforce it in `ExchangeInjectActuator.doValidate`/`ExchangeWithdrawActuator.doValidate` by rejecting the transaction when the computed `anotherTokenQuant` falls outside the caller-specified acceptable bound, exactly as already done at `ExchangeTransactionActuator.java` line 219.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) from the victim in the mempool targeting exchange `X` (first token TRX, second token asset `A`).
2. Attacker broadcasts an `ExchangeTransactionContract` selling a large amount of TRX for `A` against exchange `X`, shifting `firstTokenBalance`/`secondTokenBalance` unfavorably relative to the victim's expected ratio; this is processed by `ExchangeTransactionActuator.execute` → `ExchangeCapsule.transaction` → `ExchangeProcessor.exchange`. [9](#0-8) 
3. The victim's `ExchangeInjectContract` then executes against the now-skewed ratio in `ExchangeInjectActuator.execute`, receiving a worse `anotherTokenQuant` than intended, with no on-chain mechanism to reject the unfavorable rate. [10](#0-9) 
4. Attacker submits a reverse `ExchangeTransactionContract` to restore the ratio and realize profit extracted from the victim's mis-priced injection/withdrawal.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
