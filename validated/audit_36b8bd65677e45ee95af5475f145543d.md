## Analog Vulnerability Found

### Title
Uncontrolled memory allocation from attacker-controlled length field in `BatchValidateSign`/`ValidateMultiSign` precompiles - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The TVM precompiled contracts `BatchValidateSign` (address `0x...9`) and `ValidateMultiSign` (address `0x...a`) decode an ABI-encoded array-length word straight from the smart-contract call data and use it to size a Java array (`new byte[len][]`) before any sanity bound is enforced, mirroring the Exiv2 `DataBuf(subBox.length-sizeof(box))` pattern where a length taken from untrusted input drives an allocation with no upper bound.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read the array-length word directly out of the raw calldata and allocate a Java object array sized by that value with no upper-bound check: [1](#0-0) 

`len = words[offset].intValueSafe()` is fully attacker-controlled: it comes from a 32-byte word embedded in the contract call's `data` parameter, and `intValueSafe()` merely clamps overly large 256-bit values into the `int` range (i.e., it can return values approaching `Integer.MAX_VALUE`), it does not enforce any protocol-defined maximum.

These helpers are invoked from `ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()`: [2](#0-1) [3](#0-2) 

The size bound (`MAX_SIZE`, 5 or 16) is checked **only when `VMConfig.allowTvmSelfdestructRestriction()` is true**; when that hard-fork flag is not active, `extractBytesArray`/`extractBytes32Array` are called with the raw, unbounded length and allocate `new byte[len][]` immediately, with no cap. Even where the flag is active, the guard only limits `sigArraySize`/`addrArraySize` extracted from a *different* embedded word — it does not validate consistency against the physical size of `rawData`/`data`.

Critically, the energy cost charged for these calls is derived purely from the **physical size** of the supplied calldata, not from the value of the embedded length word: [4](#0-3) 

This means an attacker can submit a small, cheap calldata blob (just enough 32-byte words to reach the length field) while setting that embedded length field to a huge value, causing a large/expensive allocation attempt for negligible energy cost — the same "declared length vs. actual/paid-for size" mismatch that underlies CVE-2020-18899.

### Impact Explanation
A crafted TVM contract call to precompile address `0x...9` (`batchValidateSign`) or `0x...a` (`validateMultiSign`) with a manipulated array-length word can force the node to attempt an allocation of an array with billions of elements (`new byte[Integer.MAX_VALUE][]`), which typically throws `OutOfMemoryError` or induces severe GC pressure/heap exhaustion. Since these precompiles are reachable from ordinary contract calls (including constant/view calls used for transaction validation before execution), this can crash or stall a full node processing the transaction/block — a node-crash/DoS impact, reachable by any unprivileged transaction sender or contract deployer.

### Likelihood Explanation
Reachability requires only a normal signed transaction invoking a contract that performs a `CALL`/`STATICCALL` to the precompile address with crafted calldata — no special privileges are needed. The guard bounding array size is conditioned on a hard-fork/proposal flag (`allowTvmSelfdestructRestriction`), so the exposure window and exact exploitability depend on whether that flag is active on the target network; this could not be fully confirmed from the indexed code (default proposal state was not found), so likelihood is assessed as network-configuration-dependent rather than universally guaranteed.

### Recommendation
- Enforce a strict upper bound (matching `MAX_SIZE`) on the decoded array length *before* calling `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, unconditionally (not gated behind `allowTvmSelfdestructRestriction`).
- Validate that the declared length is consistent with the physical size of `data`/`rawData` (as is already partially done via `isValidAbiEncoding`) prior to allocating any array sized by that length.
- Consider charging energy proportional to the declared/decoded length rather than only the raw calldata length, so any legitimate large allocation is economically bounded.

### Proof of Concept
1. Construct ABI-encoded calldata for `batchValidateSign(bytes32,bytes[],address[])` (or `validateMultiSign`) where the header words are valid enough to pass `isValidAbiEncoding`/offset checks, but the length word for the `bytes[]` array (the word pointed to by `words[1]`/`words[3]`) is set to a very large value (e.g., close to `Integer.MAX_VALUE`), while the physical calldata itself is kept short/minimal.
2. Deploy or reuse a simple contract that performs a `CALL` to precompile address `0x...9`/`0x...a` with this crafted calldata, and submit it as a normal `TriggerSmartContract` transaction.
3. On execution, `extractBytesArray`/`extractBytes32Array` executes `new byte[len][]` with the attacker-supplied `len`, causing the node processing the transaction (or replaying/validating the block) to throw `OutOfMemoryError` or hang under GC pressure — for a transaction whose declared energy cost was computed only from the small physical calldata size.
