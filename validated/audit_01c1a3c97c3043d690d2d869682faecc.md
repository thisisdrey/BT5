### Title
Missing authorization check in `LinkRepositoryToObjectPool` allows cross-repository object pool linking - (File: internal/gitaly/service/objectpool/link.go)

### Summary
`LinkRepositoryToObjectPool` accepts any `(repository, object_pool)` pair supplied in the RPC request and links them together without verifying that the target repository is actually a legitimate member of that pool's fork network. Any caller able to invoke this Gitaly RPC — the same trust boundary an ordinary fork/repository-creation flow relies on — can attach their own repository to an arbitrary, pre-existing object pool, deduplicating objects between unrelated repositories.

### Finding Description
`LinkRepositoryToObjectPool` only validates that the `repository` field is a valid repository and that the `object_pool` resolves to a valid pool repository via `poolForRequest`/`objectpool.FromProto`; it never checks that `repository` is actually derived from (or otherwise entitled to be linked to) that specific pool: [1](#0-0) 

The pool lookup helper likewise only checks pool-directory validity, not ownership/ancestry: [2](#0-1) 

The proto documentation itself acknowledges pools have no protective invariants and depend entirely on the caller to use them correctly ("It is the responsibility of the caller to ensure...", "There are no safety checks in place..."): [3](#0-2) 

Once `Link` succeeds, the target repository's `objects/info/alternates` file is rewritten to point at the pool's object directory, meaning every object present in the pool (including private commits/blobs of the pool's real origin repository and any other members) becomes directly readable through the newly-linked repository, e.g. via `CommitService`/`GetObject`-style RPCs, exactly as demonstrated in the existing test that reads a pool-only commit through the linked member repository: [4](#0-3) 

This is analogous to the external report's root cause — a state-mutating operation (`proposeMint`/`proposeBurn`, here `LinkRepositoryToObjectPool`) exposed without any access-control/ownership check tying the caller's target object to the privileged resource it is manipulating (token supply vs. object pool membership).

### Impact Explanation
Successful exploitation causes objects (commits, blobs, trees) belonging to a private or unrelated repository's object pool to become fetchable from an attacker-controlled repository, since the pool becomes a Git alternate object directory for the linked repository. This is a confidentiality breach enabling cross-repository object disclosure, and it can also corrupt pool bookkeeping (pool member counts / disconnection assumptions) since the pool is now linked to a repository outside its intended fork network, undermining the object-pool/alternates isolation guarantees Gitaly is supposed to provide.

### Likelihood Explanation
The RPC has no built-in check tying the `repository` and `object_pool` fields together beyond both being resolvable/valid Gitaly repositories; the actual authorization (that a fork belongs to a given pool) is expected to be enforced entirely by the calling layer (e.g., GitLab Rails). Any client capable of invoking Gitaly RPCs through the normal fork/repository-creation path can supply a pool relative path from a different fork network (pool paths are predictable/guessable object-pool hashed names under `@pools/`), making this reachable without any special privilege beyond normal RPC access.

### Recommendation
Add an authorization/ancestry check inside `LinkRepositoryToObjectPool` (or in the layer that resolves `poolForRequest`) that verifies the target repository's fork network / origin actually corresponds to the pool being linked, rather than trusting the caller-supplied `object_pool` field unconditionally. This state should be tracked and validated server-side (e.g., via the `ObjectPoolStateManager`/pool-membership metadata already present) instead of relying solely on the calling application to pass consistent data.

### Proof of Concept
1. Create object pool `A` from private repository `R1` via `CreateObjectPool`.
2. As an unrelated user, create/own repository `R2` unrelated to `R1`.
3. Call `LinkRepositoryToObjectPool` with `repository = R2` and `object_pool = A` (guessing/knowing `A`'s relative path).
4. Fetch/read objects from `R2` (e.g., via `CommitService.GetCommit` for an OID known only to exist in `R1`/pool `A`); the object resolves successfully because `R2`'s alternates now point at pool `A`'s object directory, as shown by the existing test pattern in `link_test.go` lines 105-156, applied to an attacker-owned repository instead of a legitimate fork.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil
}

// The typical lifetime of an object pool is as follows:
//
// 1. An object pool is created via CreateObjectPool from its primary pool member. Typically this
//    would be the repository that gets forked.
// 2. One or more repositories are linked to the object pool via LinkRepositoryToObjectPool. Each
//    object pool member linked to the repository will have its objects deduplicated when its
//    objects get repacked the next time.
// 3. The object pool is regularly updated via FetchIntoObjectPool. This is typically only done from
//    the primary object pool member.
// 4. Repositories may leave the object pool via DisconnectGitAlternates. There is not much of a
//    reason to do this for any repositories except for the primary object pool member in case it
//    for example becomes private.
// 5. When the object pool does not have any members anymore it gets deleted via DeleteObjectPool.
//    It is the responsibility of the caller to ensure that it really has no members left, else
//    any existing member will become corrupt.
