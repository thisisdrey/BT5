Audit Report

## Title
Unprotected AMM swap in Snowbridge `system-frontend` lets an attacker sandwich `register_token`/`add_tip` and steal the swapped tip/fee value - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`pallet_snowbridge_system_frontend::Pallet::swap_and_burn` invokes `T::Swap::swap_exact_tokens_for_tokens` with `amount_out_min` hard-coded to `None`, and in the live AssetHub Westend runtime `type Swap = AssetConversion` (`pallet_asset_conversion`), a public constant-product AMM. This is reachable from the unprivileged, signed extrinsic `add_tip` and from `register_token` when called by a non-`Here` origin, letting any attacker sandwich the victim's swap and capture nearly all of the swapped value.

## Finding Description
`swap_and_burn` builds a swap path `[tip_asset_location, ether_location]` and calls `T::Swap::swap_exact_tokens_for_tokens(who, swap_path, tip_amount, None, who, true)`, explicitly passing `None` for the minimum-output guard with the comment "No minimum amount required": [1](#0-0) 

This is reached from two call paths that do not require privileged access:
- `add_tip`, callable by any `ensure_signed` account, unconditionally calls `swap_fee_asset_and_burn` → `swap_and_burn` on the caller-supplied `asset`: [2](#0-1) 
- `register_token`, when the resolved `origin_location` is not `Here` (i.e., any non-root XCM origin such as an asset owner acting via `LocalAssetOwner`/`ForeignAssetOwner`), also calls `swap_fee_asset_and_burn` on the caller-supplied `fee_asset`: [3](#0-2) 

`swap_fee_asset_and_burn` routes to `swap_and_burn` whenever the fee/tip asset differs from Ether: [4](#0-3) 

In the production AssetHub Westend runtime, `snowbridge_pallet_system_frontend::Config::Swap` is wired to the real on-chain AMM pallet: `type Swap = AssetConversion;`, confirming the swap operates against genuine, publicly-tradable liquidity pools rather than a mock: [5](#0-4) 

`pallet_asset_conversion::do_swap_exact_tokens_for_tokens` only checks `amount_out >= amount_out_min` when `amount_out_min` is `Some`; passing `None` disables the only built-in slippage guard, so any output amount, however degraded, is accepted: [6](#0-5) 

Because Substrate transactions are visible in the mempool prior to inclusion, and AMM pool reserves move deterministically along public bonding-curve math, an attacker can:
1. Front-run the victim's `add_tip`/`register_token` call with a large trade skewing the relevant pool's price against the tip/fee asset.
2. Let the victim's zero-floor swap execute at the degraded rate inside `swap_and_burn`.
3. Back-run with an opposite trade to restore the pool and capture the extracted value as arbitrage profit.

No existing guard (origin check, fee validation, or pallet-level check) constrains the swap's output; the origin checks in `register_token` (`RegisterTokenOrigin`) and `ensure_signed` in `add_tip` govern *who* may call, not the *economic outcome* of the swap, so they do not mitigate this.

## Impact Explanation
The victim's tip/fee asset is converted into far less Ether than fair value dictates. For `add_tip`, the `ether_gained` amount forwarded to BridgeHub as the relayer reward tip can be driven to near zero, meaning the attacker captures nearly 100% of the intended tip value — a direct theft of value from an ordinary user via manipulation of settlement/payout amount, matching the "theft or unbacked mint" / underpriced-work impact class. For `register_token`, the burned Ether amount that finances the Ethereum-side execution fee can similarly be skimmed to near zero, degrading fee correctness for bridge message processing. The exact corrupted value is `ether_gained` returned from `swap_and_burn`/`swap_fee_asset_and_burn`, which is subsequently burned and forwarded as the on-chain-recorded fee/tip amount despite economic value having been extracted by the attacker.

## Likelihood Explanation
High. `add_tip` is fully permissionless (any signed account) and `register_token`'s fee-payment branch is triggered for any non-root/non-`Here` origin, which in the production runtime includes ordinary asset owners via `LocalAssetOwner`/`ForeignAssetOwner`. No governance, validator, relayer, or key-compromise assumption is needed — only the standard capability to observe the mempool and submit ordering transactions, which is routine MEV/sandwich tooling. The `None` passed for `amount_out_min` is an explicit, unconditional code choice with no fallback protection, and the swap target (`AssetConversion`) is a live, public AMM in the deployed AssetHub Westend runtime.

## Recommendation
1. Do not hard-code `None` for `amount_out_min` in `swap_and_burn`. Derive an acceptable minimum via `AssetConversion::quote_price_exact_tokens_for_tokens` immediately before the swap and apply a bounded tolerance, passing `Some(min_out)`.
2. Alternatively, add an explicit `min_ether_out` parameter to `register_token`/`add_tip` so callers can set their own slippage tolerance, consistent with `pallet_asset_conversion`'s own public dispatchables.
3. Ensure slippage-triggered swap failures roll back the whole extrinsic atomically (already true via `#[transactional]` semantics of `swap_exact_tokens_for_tokens`), so no partial burn/forward occurs on failure.

## Proof of Concept
1. On AssetHub Westend, an attacker observes a pending `EthereumSystemFrontend::add_tip(message_id, asset)` (asset = token X, paired with Ether in an `AssetConversion` pool) in the mempool.
2. Attacker submits, with higher priority, a large `AssetConversion::swap_exact_tokens_for_tokens` trade of X → Ether (or Ether → X) that skews the X/Ether pool reserves so X is temporarily undervalued in Ether terms.
3. The victim's `add_tip` executes next: `swap_and_burn` calls `T::Swap::swap_exact_tokens_for_tokens(..., tip_amount, None, ...)` with no floor, so it executes at the manipulated rate, and `ether_gained` is far below fair value.
4. Attacker submits a back-run trade restoring the pool to its prior state, realizing the value difference as profit.
5. Result: verify via unit test in `bridges/snowbridge/pallets/system-frontend/src/tests.rs` style harness (with a real `AssetConversion`-style AMM instead of the mock `SwapExecutor`) that `ether_gained` returned to `add_tip`/`register_token` is materially smaller than the pre-attack expected quote, demonstrating value extraction with no privileged access.

					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};

				return Ok(0);
			}

					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
