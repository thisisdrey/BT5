## Analysis

The binding claimed by the question is:

```
fee_credited_to_collector(T, Σdelta = -A) == Pips::fee_ceil(A, protocol_fee)
```

i.e. regardless of how a total negative delta of `-A` on token `T` is split across TokenDiff intents in a batch, the fee credited to `fee_collector` for `T` should be the same.

### Tracing the code

`TokenDiff::execute_intent` computes the fee **per intent, per token leg**, not on the aggregate signer/token exposure across the whole batch: [1](#0-0) 

The fee rate itself is: [2](#0-1) 

For `Nep245`/`Imt` token types, `token_fee` returns `Pips::ZERO` whenever `amount <= 1`, regardless of the aggregate exposure of that signer/token pair across the whole `MultiPayload` batch. This check operates purely on the single intent's `amount`, with no aggregation across intents.

The only cross-intent invariant enforced is netting to zero of deposits vs. withdrawals per token via `TransferMatcher::finalize`, which does not track or require any minimum fee — it only requires that the raw balance debits/credits (including whatever fee amounts were separately deposited to `fee_collector`) match up: [3](#0-2) [4](#0-3) 

So an attacker who has a counterparty leg (which can be their own second account, since nothing requires the counterparty to be a distinct beneficial owner) can submit `A` separate `TokenDiff` intents, each `diff = {T: -1}` matched by `A` separate `+1` deposits elsewhere in the batch, instead of one intent with `diff = {T: -A}`. Each of the `A` legs hits `amount == 1`, so `token_fee` returns `Pips::ZERO` for every leg, `fees_collected` stays empty every time, and `internal_add_balance` to `fee_collector` is never called (guarded by `if !fees_collected.is_empty()`), whereas the single, unsplit `-A` intent would have charged `Pips::fee_ceil(A)` and credited `fee_collector` accordingly.

None of the listed guards (`MultiPayload::verify`, nonce/salt checks, `TransferMatcher::finalize`, `checked_*` arithmetic) prevent this, because they are unrelated to fee aggregation — they only ensure signature validity, nonce uniqueness, and that raw balance deltas net to zero across the batch.

This is a genuine, reproducible divergence for `Nep245`/`Imt` token legs (not `Nep141`, where fee applies unconditionally per the `match` in `token_fee`).

### Title
Protocol fee on NEP-245/IMT token_in legs bypassed by splitting a single large delta into unit-sized (`|delta|=1`) `TokenDiff` intents - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` waives the protocol fee for `Nep245`/`Imt` tokens whenever a single intent's `amount <= 1`, and this check is applied per intent rather than per aggregate signer/token exposure across a batch. An unprivileged signer can therefore split one logical `-A` token_in leg into `A` separate `TokenDiff` intents each with `delta = -1` on the same `Nep245TokenId`, driving the total fee credited to `fee_collector` to `0` instead of `Pips::fee_ceil(A)`.

### Finding Description
The broken binding: `fee_credited(T, -A split into A×(-1)) = 0 ≠ Pips::fee_ceil(A, protocol_fee) = fee_credited(T, single -A)`.

Root cause: `TokenDiff::token_fee` (`contracts/defuse/core/src/intents/token_diff.rs:206-216`) short-circuits to `Pips::ZERO` for `Nep245`/`Imt` tokens when `amount <= 1`, and `execute_intent` (`contracts/defuse/core/src/intents/token_diff.rs:59-78`) evaluates this per-intent, per-leg, with no batch-wide aggregation of a signer's exposure on a token. `Deltas`/`TransferMatcher::finalize` (`contracts/defuse/core/src/engine/state/deltas.rs:265-391`) only enforces that deposits and withdrawals net to zero per token across the batch — it has no notion of a minimum required fee, so a batch composed of many unit-sized matched legs balances perfectly with zero fee.

Exploit flow: attacker controls two accounts (or arranges a counterparty), both funded/able to hold the MT balance for `Nep245TokenId(mt_contract, "some_id")`. Instead of signing one `MultiPayload` with `TokenDiff{diff: {T: -A}, ...}` matched by a counterpart `{T: +A, ...}` (which would require `Pips::fee_ceil(A)` extra token_out compensation per `closure_delta`/`supply_delta` to satisfy the matcher along with the fee), the attacker signs `A` intents each `TokenDiff{diff: {T: -1}}` from account 1, matched by `A` intents each `TokenDiff{diff: {T: +1}}` from account 2 (or interleaved in one signer's diff map across sequential nonces), all in one `execute_intents` call. Every leg hits `amount == 1`, so `fee_ceil` is never invoked with a nonzero rate, `fees_collected` stays empty, and `internal_add_balance(fee_collector, fees_collected)` is skipped every time (`token_diff.rs:97-101`).

### Impact Explanation
`fee_collector`'s expected mt balance for token `T` is under-collected by `Pips::fee_ceil(A, protocol_fee)` for every swap the attacker restructures this way, compared to submitting the economically equivalent single intent. This is repeatable indefinitely, for any `Nep245`/`Imt` token and any protocol fee rate, at essentially the cost of more intents (more gas, still one transaction/batch), with no privileged role required. This matches the "protocol fees bypassed" Critical impact category defined in the rules, since value that should flow to `fee_collector` never leaves the swap.

### Likelihood Explanation
Preconditions: only a funded mt token balance for the attacker (or their two self-controlled accounts) and a nonzero `protocol_fee` (e.g. `Pips::ONE_PERCENT`) on `Nep245`/`Imt` tokens — no DAO/role/relayer key needed. Cost to the attacker is purely the extra intents/gas for splitting into `A` unit legs within a single `execute_intents` batch; it is fully repeatable across tokens, accounts, and batches, and there's no need for a counterparty outside the attacker's own control since the attacker can run both sides of the matched deltas.

### Recommendation
Aggregate a signer's net exposure per `TokenId` across the entire intent batch (or at minimum across all `TokenDiff` intents from the same signer in one `MultiPayload`) before evaluating `token_fee`'s `amount > 1` threshold, rather than evaluating it per individual intent/leg. Alternatively, remove the `amount <= 1` fee waiver for `Nep245`/`Imt` and instead gate the waiver on a token-level property (e.g., an explicit "non-fungible" flag/max-supply-1 marker) rather than the transient per-intent `amount`.

### Proof of Concept
`cargo test` in `near-workspaces` sandbox (per existing patterns in `tests/src/tests/defuse/intents/simulate.rs` and `tests/src/tests/defuse/state/fee.rs`):
1. Deploy defuse contract with `protocol_fee = Pips::ONE_PERCENT` and a designated `fee_collector`.
2. Deploy an MT contract, mint/deposit a `Nep245TokenId` balance of `A` (e.g. `A = 1000`) into attacker account `acct1`'s defuse balance, and set up `acct2` (attacker-controlled) able to receive it.
3. **Case 1 (single intent):** Sign and execute one `MultiPayload` containing `TokenDiff{diff: {T: -A, ...}}` from `acct1` matched (via `closure_delta`) by `TokenDiff` from `acct2`. Assert `fee_collector`'s mt balance for `T` after execution equals `Pips::fee_ceil(A, ONE_PERCENT)`.
4. **Case 2 (split):** Sign and execute one `MultiPayload` containing `A` intents `TokenDiff{diff: {T: -1}}` from `acct1`, each matched by a corresponding `TokenDiff{diff: {T: +1}}` from `acct2` (distinct nonces per intent as required). Assert `fee_collector`'s mt balance for `T` after execution is `0`.
5. Assert `Case1_fee_collected != Case2_fee_collected` (`> 0` vs `== 0`), proving the binding `fee(-A split) == fee(-A single)` fails.

        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)

                return Err(InvariantViolated::Overflow);
            }

            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }

    // If returned delta is zero, then overflow happened
    pub fn finalize_into(self, token_id: &TokenId, transfers: &mut Transfers) -> Result<(), i128> {
        // sort deposits and withdrawals in descending order
        let [mut deposits, mut withdrawals] = [self.deposits, self.withdrawals].map(|amounts| {
            let mut amounts: Vec<_> = amounts.into_iter().collect();
            amounts.sort_unstable_by_key(|(_, amount)| Reverse(*amount));
            amounts.into_iter()
        });

        // take first sender and receiver
        let (mut deposit, mut withdraw) = (deposits.next(), withdrawals.next());

        // as long as there is both: sender and receiver
        while let Some(((sender, send), (receiver, receive))) =
            withdraw.as_mut().zip(deposit.as_mut())
        {
            // get min amount and transfer
            let transfer = (*send).min(*receive);
            transfers
                .transfer(sender.clone(), receiver.clone(), token_id.clone(), transfer)
                // no error can happen since we add only one transfer for each
                // combination of (sender, receiver, token_id)
                .unwrap_or_else(|| unreachable!());

            // subtract amount from sender and receiver
            *send = send.saturating_sub(transfer);
            *receive = receive.saturating_sub(transfer);

            if *send == 0 {
                // select next sender
                withdraw = withdrawals.next();
            }
            if *receive == 0 {
                // select next receiver
                deposit = deposits.next();
            }
        }

        // only sender(s) left
        if let Some((_, send)) = withdraw {
            return Err(withdrawals
                .try_fold(send, |total, (_, s)| total.checked_add(s))
                .and_then(|total| i128::try_from(total).ok())
                .and_then(i128::checked_neg)
                .unwrap_or_default());
        }
        // only receiver(s) left
        if let Some((_, receive)) = deposit {
            return Err(deposits
                .try_fold(receive, |total, (_, r)| total.checked_add(r))
                .and_then(|total| i128::try_from(total).ok())
                .unwrap_or_default());
        }

        Ok(())
    }
