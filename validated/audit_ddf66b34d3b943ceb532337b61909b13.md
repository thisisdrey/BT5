### Title
Unprivileged attacker can fill a victim's `MAX_TOKENS_PER_USER` account slots via dust `DepositToken` transfers / `deposit(onBehalfOf)` to block collateral top-ups and new positions - ([File: contracts/Pool.sol])

### Summary
`Pool` maintains a per-account enumerable set of deposit/debt tokens capped at `MAX_TOKENS_PER_USER`. Any address can grow a victim's `depositTokensOfAccount` set without consent — either by `DepositToken.transfer(victim, dust)` or by `DepositToken.deposit(dust, victim)` (`onBehalfOf_`). Once the combined deposit+debt token count reaches the cap, every subsequent `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` reverts with `UserReachedMaxTokens` (`contracts/Pool.sol:143-148`), which makes `deposit()`, `transfer()` into the account, `DebtToken.issue/mint`, `SmartFarmingManager.leverage` (new token types) and liquidation fee/seize flows that would add a new token all revert. This is the Metronome analog of the resource-leak DoS class: a bounded on-chain resource (the victim's token list) is exhausted by an unprivileged caller.

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's pool list whenever the recipient's balance goes from 0 to >0, with no opt-in: `if (_recipientBalanceBefore == 0 && amount_ > 0) pool.addToDepositTokensOfAccount(recipient_)` (`contracts/DepositToken.sol:517-520`). `transfer`/`transferFrom` only check the *sender's* unlocked balance (`_revertIfLocked(sender_)`), so an attacker with no debt can push dust to any victim.
- `DepositToken.deposit(amount_, onBehalfOf_)` has no `onBehalfOf_` authorization; `_mint` performs the same `addToDepositTokensOfAccount` for the beneficiary (`contracts/DepositToken.sol:211-237, 485-488`).
- Removal only happens when the victim's balance for that token returns to 0 (`_transfer` at `contracts/DepositToken.sol:522-525`), and the victim's own `transfer`/`withdraw` are gated by `_revertIfLocked`/`unlockedBalanceOf` (`contracts/DepositToken.sol:348-353, 383-398`). A victim whose position backs debt can have `unlockedBalanceOf == 0` for the dust entries (locked collateral is pro-rata across all listed tokens via `depositOf`), so self-cleaning is not guaranteed while debt exists.
- The cap check is in `onlyIfAdditionWillNotReachMaxTokens` used by both `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` (`contracts/Pool.sol:204-220`); the unit test confirms the revert behavior (`test/Pool.test.ts:1386-1416`).

Attack trace:
1. Attacker deposits a minimal amount into each registered `DepositToken` (cost: only underlying dust, deposit fee if any).
2. For every registered deposit token the victim does not yet hold, attacker calls `msdToken.transfer(victim, 1 wei)` — each call inserts the token into `depositTokensOfAccount[victim]`.
3. When `debtTokensOfAccount + depositTokensOfAccount` for the victim reaches `MAX_TOKENS_PER_USER`, any operation that would register a *new* token reverts: `deposit()` into a collateral type the victim hasn't used, receiving msdTokens, minting a synth type that would create a new `DebtToken` entry, `SmartFarmingManager.leverage`/`flashRepay` paths that deposit new collateral, and even `Pool.liquidate`/`seize` flows that would add a new deposit token to the liquidator/feeCollector account.

### Impact Explanation
This is a liveness/freeze-griefing analog of the reported resource-leak DoS. Concretely:
- A victim approaching liquidation cannot deposit a *new* collateral type to restore health (`deposit` → `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`), so a position that could have been saved is forced into liquidation — indirect loss of funds via seized collateral and liquidation fees.
- A victim with outstanding debt may be unable to remove the injected dust entries (`_revertIfLocked`), making the block persist until debt is repaid — temporary freezing of the deposit/transfer surface.
- Since `debtTokensOfAccount` shares the cap, the victim also cannot open positions in additional synthetic assets.

Note: the attack requires the number of registered deposit tokens (+ victim's debt tokens) to reach `MAX_TOKENS_PER_USER`. The cap's exact value lives in `IPool`/deployment config and the registered-token count is governor-controlled; on deployments where registered deposit tokens ≥ `MAX_TOKENS_PER_USER` minus the victim's existing entries, the attack is fully reachable. I could not confirm the constant's value or per-chain token counts from the indexed sources, so likelihood depends on deployed configuration.

### Likelihood Explanation
Unprivileged EOA only; needs dust amounts of each registered underlying (cheap) and no privileged role, oracle manipulation, or malicious LZ endpoint. Feasibility hinges on deployed `MAX_TOKENS_PER_USER` vs. number of registered `DepositToken`s — if the registry lists fewer tokens than the cap, the attacker can only fill up to that number and the victim is only partially blocked (still a real but narrower DoS on unused token types). The persistence of the block depends on the victim's locked-balance state.

### Recommendation
- Make per-account list insertion opt-in or tolerant: e.g., do not add dust below a minimum threshold, or let `addToDepositTokensOfAccount` silently skip/at-most-warn instead of reverting the whole transaction at the cap (counting collateral `depositOf` could iterate only tokens with balance while treating overflow entries as non-blocking).
- Alternatively, allow anyone to call `removeFromDepositTokensOfAccount` semantics by letting recipients renounce dust balances even when partially locked, or add a `burnDust`/forced-`transfer` escape that ignores `_revertIfLocked` for balances below a floor.
- Restrict `deposit(onBehalfOf_)` additions or add a per-account whitelist of accepted deposit tokens.

### Proof of Concept
Foundry/Hardhat fork sketch (fill slots, then show revert):

```solidity
// pool has D registered DepositTokens; victim already holds k entries
// assume D + victimDebtTokens >= MAX_TOKENS_PER_USER
address[] memory dtokens = pool.getDepositTokens(); // registered
for (uint i; i < dtokens.length; ++i) {
    IDepositToken dt = IDepositToken(dtokens[i]);
    if (dt.balanceOf(victim) > 0) continue;
    // attacker gets 1 wei of msdToken
    underlying(dt.underlying()).approve(address(dt), 1 ether);
    dt.deposit(smallAmount, attacker);
    dt.transfer(victim, 1); // registers token for victim
}
// now: depositTokensOfAccount.length(victim) + debtTokens == MAX_TOKENS_PER_USER

// victim tries to deposit a collateral type not yet in list
vm.startPrank(victim);
underlying.approve(address(newDepositToken), amount);
vm.expectRevert(IPool.UserReachedMaxTokens.selector);
newDepositToken.deposit(amount, victim); // reverts -> cannot add collateral

// victim tries to mint a new synth type -> addToDebtTokensOfAccount reverts too
vm.expectRevert(IPool.UserReachedMaxTokens.selector);
newDebtToken.issue(amount, victim);
```

While the victim's balances are locked by existing debt, `transfer` of the dust entries reverts via `_revertIfLocked`, so the victim cannot clear slots — the block persists until they repay debt or a price move unlocks balance, during which `Pool.liquidate` can seize collateral the victim was prevented from topping up.

Caveat: exact `MAX_TOKENS_PER_USER` value and per-chain registered deposit-token counts were not verifiable from the indexed code; if deployed token counts are far below the cap, impact degrades to a partial rather than complete deposit-block.
