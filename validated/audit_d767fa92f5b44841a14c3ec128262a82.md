### Title
JIT sandwich of `lending_pool_emissions_deposit` lets an attacker steal same-mint emissions from existing depositors - (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`)

### Summary
`lending_pool_emissions_deposit` is a permissionless instruction that transfers tokens directly into a bank's `liquidity_vault` and instantly re-prices `asset_share_value` for *all* existing depositors in that bank, in a single transaction, with no lockup and no entry/exit fee on deposits or withdrawals. This is functionally identical to the root cause described in the Yieldy `LiquidityReserve` JIT/sandwich report: an instantaneous, permissionless value injection into a pooled share price that any account can front-run with a large deposit and back-run with an immediate withdrawal, capturing a disproportionate share of the injected value at (near) zero risk.

### Finding Description
`lending_pool_emissions_deposit` performs the following, atomically: [1](#0-0) 

It transfers `amount` of the bank's underlying mint into `liquidity_vault`, then recomputes:
```
bank.asset_share_value = (total_assets + amount) / total_asset_shares
```
This mirrors the Yieldy bug pattern precisely: a fee/reward event is realized **instantly** and **fully** into the pooled share price rather than being streamed or vested, and there is no barrier (lockup, exit fee, cooldown) preventing a depositor from entering right before and exiting right after the event.

Per `guides/USER/FEES.md`, marginfi deposits and withdrawals are fee-free and have no lockup: [2](#0-1) 

The instruction is explicitly documented and tested as permissionless and share-value-altering: [3](#0-2) [4](#0-3) 

**Attack sequence:**
1. Attacker observes a pending `lending_pool_emissions_deposit(amount)` call for bank X (anyone can submit this, e.g. a rewards program, and its parameters/timing are visible ahead of confirmation).
2. Attacker front-runs it with `lending_account_deposit` of a very large sum into bank X, becoming the overwhelming majority of `total_asset_shares`. Deposits are unweighted by time-in-pool and free.
3. The emissions-deposit transaction executes and bumps `asset_share_value` for the whole bank pro-rata to `total_asset_shares`, crediting the attacker (as the dominant shareholder at that instant) with almost all of the injected value.
4. Attacker immediately back-runs with `lending_account_withdraw`, extracting principal plus the captured share of emissions, with zero withdrawal fee and no cooldown.

This is the on-chain analog of the Yieldy `instantUnstakeReserve()` sandwich: JIT liquidity captures value that was intended for existing, long-term liquidity providers/depositors, contributing nothing of value to the protocol in return (unlike JIT in an AMM swap, where the liquidity is actually used to fill an order).

### Impact Explanation
Existing long-term depositors in a bank have their rightful share of same-mint emissions/rewards diverted to an opportunistic, risk-free JIT depositor. This is an unauthorized value transfer between unprivileged users routed through core accounting state (`asset_share_value`, `total_asset_shares`), diminishing (though not necessarily zeroing) the yield legitimate depositors were meant to receive. Because deposit/withdraw are unbounded in size (subject only to bank deposit limits) and free, the attacker's capture percentage scales with how much capital they can flash into the pool relative to existing depositors, which can be made arbitrarily close to 100% of the emitted amount for banks with modest total deposits.

### Likelihood Explanation
The precondition is simply visibility of a forthcoming (or repeatedly recurring) `lending_pool_emissions_deposit` call, which is a public, permissionless instruction whose calls would appear in the mempool/recent transaction history (marginfi runs on Solana; MEV-style front/back-running within the same or adjacent slots is feasible, especially if the emissions program calls this instruction on a predictable schedule or from a known keeper key). No governance, admin key, or special privilege is required to execute either leg of the attack — only ordinary `lending_account_deposit`/`lending_account_withdraw` calls by an unprivileged account.

### Recommendation
- Stream/vest the emissions injection over time rather than crediting it instantly into `asset_share_value` in a single instruction (e.g., accrue it gradually similar to interest accrual, which is time-weighted).
- Alternatively, snapshot eligible depositor balances prior to the emissions injection (e.g., only accounts that held shares before the triggering block/slot receive the pro-rata benefit), rather than using the live `total_asset_shares` at execution time.
- Consider adding a minimum holding period or a small deposit/withdraw cooldown specifically around emissions-deposit events, or restricting `lending_pool_emissions_deposit` amount/frequency so it cannot be economically front-run at scale.

### Proof of Concept
Conceptual PoC (adapting the existing test harness in `programs/marginfi/tests/misc/emissions_deposit.rs`):
1. Depositor A deposits 40 USDC, Depositor B deposits 60 USDC into `usdc_bank` (baseline, as in the existing test) — this matches the setup in [5](#0-4) .
2. Immediately before the emissions-deposit transaction is confirmed, an attacker account deposits, say, 100,000 USDC into the same bank via `lending_account_deposit` (no fee, no lockup).
3. The pending `lending_pool_emissions_deposit(50 USDC)` call executes, recomputing `asset_share_value` as `(total_assets + 50) / total_asset_shares` per [6](#0-5) ; because the attacker now holds ~99.9% of `total_asset_shares`, they receive ~99.9% of the 50 USDC emission instead of Depositors A and B.
4. Attacker calls `lending_account_withdraw` for their full balance right after, realizing the captured emissions with no fee and no delay, leaving Depositors A and B with only a negligible fraction of the intended reward.

```rust
pub fn lending_pool_emissions_deposit(
    ctx: Context<LendingPoolEmissionsDeposit>,
    amount: u64,
) -> MarginfiResult {
    if amount == 0 {
        return Ok(());
    }

    let clock = Clock::get()?;
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = ctx.accounts.group.load()?;

    utils::validate_bank_state(&bank, utils::InstructionKind::FailsIfPausedOrReduceState)?;

    // Reject mints with non-zero transfer fees or active transfer hooks.
    let mint_ai = ctx.accounts.mint.to_account_info();
    check!(
        !utils::nonzero_fee(mint_ai.clone(), clock.epoch)?,
        MarginfiError::InvalidTransfer
    );
    check!(
        !utils::has_transfer_hook(mint_ai)?,
        MarginfiError::InvalidTransfer
    );

    let total_asset_shares = I80F48::from(bank.total_asset_shares);
    check!(
        total_asset_shares > I80F48::ZERO,
        MarginfiError::EmissionsUpdateError
    );

    bank.accrue_interest(
        clock.unix_timestamp,
        &group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    transfer_checked(
        CpiContext::new(
            ctx.accounts.token_program.key(),
            TransferChecked {
                from: ctx.accounts.emissions_funding_account.to_account_info(),
                to: ctx.accounts.liquidity_vault.to_account_info(),
                authority: ctx.accounts.depositor.to_account_info(),
                mint: ctx.accounts.mint.to_account_info(),
            },
        ),
        amount,
        ctx.accounts.mint.decimals,
    )?;

    let total_assets = bank.get_asset_amount(total_asset_shares)?;
    let updated_total_assets = total_assets
        .checked_add(I80F48::from_num(amount))
        .ok_or_else(math_error!())?;

    bank.asset_share_value = updated_total_assets
        .checked_div(total_asset_shares)
        .ok_or_else(math_error!())?
        .into();
```
