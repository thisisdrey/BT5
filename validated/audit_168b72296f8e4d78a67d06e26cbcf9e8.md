### Title
Unbounded length field in TVM precompiled-contract calldata parsing causes uncontrolled array allocation / crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE-2020-25756 root cause is that Mongoose trusts an attacker-supplied length/offset inside an HTTP header without bounds-checking it against the buffer it is used to index. The same pattern — trusting an attacker-controlled length word to size or index an array without validating it against the real payload size — exists in java-tron's precompiled-contract ABI decoding helpers `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java`.

### Finding Description
`extractBytes32Array` reads a length directly from calldata with no bound check at all: [1](#0-0) 

`extractBytesArray` and `extractSigArray` only guard the initial `offset`, then take an attacker-controlled `len` from `words[offset].intValueSafe()` and immediately allocate `new byte[len][]` before any content is copied: [2](#0-1) 

`intValueSafe()` in `DataWord` does not reject an oversized value — it clamps it to `Integer.MAX_VALUE` instead of throwing or truncating to the real calldata size: [3](#0-2) 

Because `len`/`bytesOffset`/`bytesLen` are never validated against `data.length` before being used to size arrays or as offsets into `extractBytes` (`Arrays.copyOfRange`), a crafted calldata word (e.g., all-`0xFF` word beyond 4 significant bytes) is coerced to `Integer.MAX_VALUE`, causing `new byte[Integer.MAX_VALUE][]` — an out-of-memory allocation — or an `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` further down when `bytesOffset`/`bytesLen` derived from other attacker words are used to slice `data` via `Arrays.copyOfRange` in `extractBytes`: [4](#0-3) 

Notably, elsewhere in the codebase (RLP decoding) the project explicitly anticipates and catches this exact failure mode: [5](#0-4) 
but the precompiled-contract array-extraction helpers have no equivalent `verifyLength`-style check or `OutOfMemoryError` handling.

### Impact Explanation
These helpers are used by precompiled contracts (e.g., the batch signature validation precompile, exercised by `BatchValidateSignContractTest`) that any account can invoke via a normal `TriggerSmartContract`/`CALL` with attacker-chosen calldata — no special privilege is required. An unbounded/huge allocation attempt (`new byte[Integer.MAX_VALUE][]`) can throw an uncaught `OutOfMemoryError` during transaction execution inside the shared JVM that runs block validation, which is a much more severe failure mode than a normal reverted transaction: OOM can destabilize the whole node process (including other concurrently executing transactions or consensus threads), leading to a node crash/DoS. At minimum it is an unhandled runtime exception path in `PrecompiledContract.execute`, differing from the graceful revert behavior the VM is designed to guarantee for malformed input.

### Likelihood Explanation
Reachability is trivial: constructing calldata for the affected precompiled contract with a header word whose value exceeds 4 significant bytes is enough to trigger the clamp-to-`Integer.MAX_VALUE` behavior in `intValueSafe()`, and no authorization beyond broadcasting a normal transaction is needed.

### Recommendation
Add explicit bounds validation in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` (and in `extractBytes`) that rejects `len`/`bytesOffset`/`bytesLen` values whose resulting index or allocation size exceeds `data.length` / `words.length`, mirroring the `verifyLength` pattern already used in `RLP.java`, and fail with a normal VM revert instead of allowing uncontrolled allocation or negative-size array construction.

### Proof of Concept
Craft a call to the precompiled contract that internally calls `extractBytesArray`/`extractSigArray` with calldata where the length word at the expected `offset` is set to `0xFF...FF` (32 bytes of `0xFF`). `intValueSafe()` will report `bytesOccupied() > 4`, returning `Integer.MAX_VALUE` for `len`, and the subsequent `new byte[len][]` allocation attempt will throw `OutOfMemoryError` during precompile execution.

---
Note on confidence: I could not fully confirm within the available search budget (a) the exact precompiled-contract address/dispatch that calls `extractBytesArray`/`extractSigArray` end-to-end, or (b) whether `Runtime`/`Program` execution wraps precompile calls in a catch-all that safely converts `OutOfMemoryError`/`ArrayIndexOutOfBoundsException` into a transaction revert rather than letting it propagate. If such a catch-all exists and reliably absorbs `Error` (not just `Exception`), the practical impact is reduced to a reverted transaction (Medium) rather than a node crash (High/Critical); this would need to be confirmed by reviewing `Program.callToPrecompiledAddress`/`PrecompiledContract` invocation sites in a full session.

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {

    int intValue = intValue();
