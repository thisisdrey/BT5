### Title
Missing Commission Settlement Hook in `set_beneficiary_for_operator` Allows Redirection of Accrued APT Commission to New Beneficiary — (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

---

### Summary

`staking_contract::set_beneficiary_for_operator` and `delegation_pool::set_beneficiary_for_operator` both change the commission-recipient address without first automatically settling accrued but undistributed commission to the old beneficiary. Because the beneficiary lookup is deferred to distribution time, an operator can redirect already-earned commission from the old beneficiary to a new address by calling `set_beneficiary_for_operator` before `distribute` is called.

---

### Finding Description

**Root cause — `staking_contract`**

`distribute_internal` resolves the final commission recipient at distribution time, not at accrual time:

```move
if (recipient == operator) {
    recipient = beneficiary_for_operator(operator);
};
aptos_account::deposit_coins(recipient, coin::extract(&mut coins, amount_to_distribute));
``` [1](#0-0) 

Commission is recorded in `distribution_pool` under the operator's address via `request_commission_internal`. The actual APT transfer to the beneficiary only happens when `distribute` / `distribute_internal` is called later. At that moment, `beneficiary_for_operator(operator)` is re-evaluated live.

`set_beneficiary_for_operator` performs no settlement before overwriting the beneficiary pointer:

```move
public entry fun set_beneficiary_for_operator(
    operator: &signer, new_beneficiary: address
) acquires BeneficiaryForOperator {
    ...
    borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
        new_beneficiary;
    ...
}
``` [2](#0-1) 

The docstring acknowledges the gap but provides no enforcement:

> "To ensures payment to the current beneficiary, one should first call `distribute` before switching the beneficiary." [3](#0-2) 

**Root cause — `delegation_pool`**

`synchronize_delegation_pool` buys commission shares for `beneficiary_for_operator(stake::get_operator(pool_address))` at synchronization time:

```move
buy_in_active_shares(pool, beneficiary_for_operator(stake::get_operator(pool_address)), commission_active);
buy_in_pending_inactive_shares(
    pool,
    beneficiary_for_operator(stake::get_operator(pool_address)),
    commission_pending_inactive
);
``` [4](#0-3) 

`delegation_pool::set_beneficiary_for_operator` also performs no prior synchronization:

```move
public entry fun set_beneficiary_for_operator(
    operator: &signer,
    new_beneficiary: address
) acquires BeneficiaryForOperator {
    ...
    borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
    ...
}
``` [5](#0-4) 

Its docstring similarly warns without enforcing:

> "To ensure payment to the current beneficiary, one should first call `synchronize_delegation_pool` before switching the beneficiary." [6](#0-5) 

---

### Impact Explanation

**`staking_contract` path (concrete theft):**

1. Operator sets beneficiary to Alice via `set_beneficiary_for_operator`.
2. Staking rewards accrue; operator calls `request_commission`, which records commission in `distribution_pool` under the operator's address and moves it to `pending_inactive`.
3. Lockup expires; commission becomes `inactive` (withdrawable).
4. Operator calls `set_beneficiary_for_operator(Bob)` — no settlement occurs.
5. Anyone calls `distribute(staker, operator)`.
6. `distribute_internal` evaluates `beneficiary_for_operator(operator)` → Bob; Alice receives nothing.

Alice's accrued APT commission is permanently redirected to Bob. Alice cannot call `distribute` preemptively because she has no way to know when the operator will change the beneficiary, and even if she did, the operator can front-run her.

**`delegation_pool` path:**

Same pattern: unsynchronized commission shares are credited to the new beneficiary on the next `synchronize_delegation_pool` call, which any user operation triggers automatically.

---

### Likelihood Explanation

- The operator controls `set_beneficiary_for_operator` and can call it at any time.
- The old beneficiary has no on-chain mechanism to prevent or detect the change before distribution.
- `distribute` is a public entry function, but the operator can front-run any protective call by the old beneficiary.
- The scenario is reachable with a single unprivileged-to-the-victim transaction (the operator's `set_beneficiary_for_operator` call).

---

### Recommendation

Add an automatic settlement step inside `set_beneficiary_for_operator` before overwriting the beneficiary pointer. For `staking_contract`, iterate over all staking contracts for the operator and call `distribute_internal` on each. For `delegation_pool`, call `synchronize_delegation_pool` for every pool the operator serves before updating `BeneficiaryForOperator`. This mirrors the pattern already used in `set_operator` (delegation pool) and `switch_operator` (staking contract), both of which settle rewards before the ownership change takes effect. [7](#0-6) [8](#0-7)

### Proof of Concept

**`staking_contract` scenario:**

```
1. setup_staking_contract(staker, operator1, INITIAL_BALANCE, 10)
2. set_beneficiary_for_operator(operator1, alice)          // alice is old beneficiary
3. stake::end_epoch()                                       // rewards accrue
4. request_commission(operator1, staker, operator1)         // commission recorded in distribution_pool
5. stake::fast_forward_to_unlock(pool_address)              // commission becomes inactive
   // At this point alice is owed ~commission APT
6. set_beneficiary_for_operator(operator1, bob)             // NO settlement — alice loses her commission
7. distribute(staker, operator1)
   // distribute_internal: beneficiary_for_operator(operator1) == bob
   // bob receives alice's commission; alice receives 0
assert!(coin::balance<AptosCoin>(alice) == 0)              // alice lost her earned commission
assert!(coin::balance<AptosCoin>(bob)   == expected_commission)
```

The existing test `test_operator_can_set_beneficiary` in `staking_contract.move` (lines 1696–1822) demonstrates the correct flow only when `distribute` is called *before* the switch — it does not test the adversarial ordering where `set_beneficiary_for_operator` is called while commission is already pending distribution.     public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
