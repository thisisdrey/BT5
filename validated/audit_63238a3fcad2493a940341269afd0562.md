### Title
`InstantiateOrigin` permission gate is silently bypassed when a contract nested-instantiates another contract - ([File: substrate/frame/contracts/src/lib.rs], [File: substrate/frame/revive/src/lib.rs])

### Summary
The external report's core broken invariant is: a permission gate meant to restrict who may introduce new trusted/executable code (`Owner`-only facet addition in the Diamond pattern) can effectively be bypassed via an indirect path, exposing users to code that was never meant to be reachable by ordinary actors. The direct local analog is `pallet-contracts`'/`pallet-revive`'s `Config::InstantiateOrigin`, which is documented to gate the top-level `instantiate`/`instantiate_with_code` extrinsics, but is explicitly **not enforced when a contract instantiates another contract** from inside WASM/PVM execution.

### Finding Description
Both `pallet-contracts` and `pallet-revive` expose a `Config::InstantiateOrigin: EnsureOrigin<...>` associated type intended to let a chain restrict *who* may create new contract instances, separately from `UploadOrigin` (who may upload code): [1](#0-0) [2](#0-1) 

The check is performed only at the outer dispatch/`bare_instantiate` entry point: [3](#0-2) [4](#0-3) 

However, the same doc comment on both pallets admits the gap explicitly:
> "This is not enforced when a contract instantiates another contract. The `UploadOrigin` should make sure that no code is deployed that does unwanted instantiations."

The nested-instantiate path — reached from a contract's host-call `seal_instantiate`/`instantiate` syscall (`substrate/frame/contracts/src/wasm/runtime.rs:1069-1120`, `substrate/frame/revive/src/vm/pvm.rs:737-817`) and executed via the exec stack (`ExecStack::run_instantiate` / `Frame::instantiate`, e.g. `substrate/frame/revive/src/exec.rs:1141-1171`) — never re-checks `T::InstantiateOrigin`. It only builds the deployer address, computes the new contract address, and constructs `ContractInfo`: [5](#0-4) 

So if a runtime configures `InstantiateOrigin` to restrict *who may create contract instances* (e.g., only a whitelisted set of accounts, expecting `UploadOrigin` to independently gate what code can exist), any already-signed, non-privileged user can call any contract that internally performs a `CREATE`/`instantiate` using `Code::Existing(code_hash)` (a code hash already on-chain, uploaded earlier under whatever `UploadOrigin` policy applied) and thereby create arbitrarily many new instances of that code — completely bypassing the `InstantiateOrigin` restriction. Unlike the DiamondCutFacet case (which requires the Owner to act), this bypass requires only an ordinary signed call into an already-deployed contract; the root cause is a missing re-check inside the execution stack, not an admin/governance decision.

### Impact Explanation
Any chain that relies on `InstantiateOrigin` (rather than `UploadOrigin` alone) to control who may instantiate contracts — for example to prevent unauthorized deployment of contracts that mint tokens, hold privileged capabilities, or interact with sensitive pallets — loses that guarantee for any code that is reachable transitively through an already-permitted contract call. This is an origin-escalation / filter-bypass condition: a public entry point (any contract call) allows unauthorized execution of a restricted operation (`instantiate`), directly matching the "Public wrappers ... must not widen origin, bypass filters" pivot in the Impact Gate. Depending on how a given runtime uses this knob (e.g., a runtime that permits public uploads/instantiation of "factory" contracts but restricts direct instantiation of a sensitive template), this can let unprivileged users mint unauthorized contract instances that hold or move funds, i.e., unauthorized execution with fund-relevant consequences.

### Likelihood Explanation
The gap is guaranteed to be reachable in any deployment that sets `InstantiateOrigin` to something stricter than `UploadOrigin` (a supported, documented configuration) and has at least one contract on-chain capable of nested instantiation with `Code::Existing`. No malicious node/relayer/validator/admin is required — a normal signed account calling a normal contract triggers it. The bypass is a structural property of the exec stack (confirmed identically in both `pallet-contracts` and `pallet-revive`), not a race condition or timing-dependent bug, so likelihood is high wherever this configuration knob is actually used to enforce security-relevant separation between upload and instantiate rights.

### Recommendation
Enforce (or optionally allow enforcing via a config flag) `T::InstantiateOrigin` at nested-instantiate time as well, or, if that is not architecturally desired (since nested calls don't carry a `RuntimeOrigin`), strengthen and make prominent in the trait documentation that `InstantiateOrigin` provides no isolation for already-uploaded code, and add a compile/integrity-time check or runtime-benchmark warning when `InstantiateOrigin` differs from `UploadOrigin`, since that configuration cannot deliver the isolation its name implies. Alternatively, provide a per-code-hash "instantiate allow-list" enforced inside `ExecStack::run_instantiate` for nested instantiations, independent of the calling origin, so that restricted code truly cannot be instantiated transitively.

### Proof of Concept
1. Configure a test runtime with `UploadOrigin = EnsureSigned` (anyone can upload) and `InstantiateOrigin = EnsureRoot` (or any privileged-only origin), matching the documented supported use case.
2. As a privileged account, upload and instantiate a "factory" contract `F` whose constructor/exported function calls the `instantiate` host function with `Code::Existing(code_hash_of_C)` where `C` is some sensitive contract code (also previously uploaded/instantiated once by the privileged account, establishing `code_hash_of_C` in storage).
3. As an arbitrary unprivileged signed account, call `Contracts::call(origin=signed(attacker), dest=F, ...)`.
4. Observe that `F`'s nested `instantiate(code_hash_of_C, ...)` call succeeds and a brand-new instance of `C` is created, attributed to the attacker-triggered call, even though `RuntimeOrigin::signed(attacker)` would be rejected by `Contracts::instantiate(origin=signed(attacker), code_hash_of_C, ...)` at the dispatchable layer with `BadOrigin` from `T::InstantiateOrigin::ensure_origin`.
5. This demonstrates that `InstantiateOrigin`, the pallet's advertised anti-abuse control (directly analogous to the Diamond's Owner-gated facet-addition control in the external report), is bypassed entirely through an unprivileged, non-admin execution path. [3](#0-2) [5](#0-4)
