### Title
Dust-filling `depositTokensOfAccount` via `deposit(onBehalfOf)` permanently blocks a victim from adding new collateral/debt positions - ([File: contracts/Pool.sol])

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across `debtTokensOfAccount` + `depositTokensOfAccount`, and any mint/transfer that takes a balance from 0 → >0 calls `addToDepositTokensOfAccount`, which reverts once the cap is hit. Because `DepositToken.deposit(amount_, onBehalfOf_)` accepts an arbitrary beneficiary, an unprivileged attacker can cheaply fill a victim's token list with dust deposits and make the victim's subsequent deposits/borrows of new tokens revert — a liveness/DoS analog of CVE-2024-21193.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts with `UserReachedMaxTokens` when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`contracts/Pool.sol:143-148`).
- `DepositToken.deposit(amount_, onBehalfOf_)` is public, `whenNotPaused`, requires only `amount_ > 0` and a non-null beneficiary, pulls `amount_` of underlying from the caller, and mints msdTOKEN to `onBehalfOf_` (`contracts/DepositToken.sol:211-237`).
- `_mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's prior balance was 0 (`contracts/DepositToken.sol:486-488`); the same bookkeeping happens in `_transfer` (`contracts/DepositToken.sol:518-520`) and in `DebtToken._mint` → `addToDebtTokensOfAccount` (`contracts/DebtToken.sol:598-600`), reachable from the public `DebtToken.issue` / `mint`.
- Attack: the attacker calls `depositToken.deposit(1, victim)` (or transfers 1 wei of msdTOKEN) for every deposit token the victim does not already hold, until the combined length hits 30. Each call costs the attacker only dust of the underlying.
- Result: any `deposit`/`issue`/`leverage` that would add a new token to the victim's list reverts inside `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, so the victim cannot onboard new collateral types or open debt in a synthetic they don't already hold.

### Impact Explanation
Temporary freezing of protocol functionality for a targeted user: all new-token deposits and all new-synthetic borrows revert until the victim manually transfers each dust msdTOKEN balance to zero it (paying gas per token, and only possible while the dust is "unlocked"). If the victim has an at-risk position and needs to add a new collateral type to restore health, the block can indirectly force a liquidation. Analogous to the CVE: an availability/DoS condition inflicted on a target through a reachable code path.

### Likelihood Explanation
Requires no privileged role, no oracle manipulation, and no flash loan — just `deposit(1, victim)` calls on the public `DepositToken` entry point (or `transfer` of dust shares). Cost is bounded by the dust value of the pool's whitelisted underlyings plus gas. The cap is a hard constant (30), so feasibility depends on the number of deposit tokens configured in the target pool versus slots the victim already occupies.

### Recommendation
- Count per-account token-list entries only for balances above a dust threshold, or
- Remove the beneficiary parameter's ability to create a new list entry (only credit `depositTokensOfAccount` for `onBehalfOf_ == _msgSender()` or on explicit opt-in), or
- Raise/decouple the cap, or make `addToDepositTokensOfAccount` a no-op instead of a revert when full while keeping health-factor iteration bounded.

### Proof of Concept
Hardhat sketch (pool with N registered deposit tokens):

```ts
// victim has no positions; pool has >= 30 usable token slots
for (const dt of depositTokens) {
  const underlying = await ethers.getContractAt('ERC20', await dt.underlying())
  await underlying.connect(attacker).approve(dt.address, 1)
  await dt.connect(attacker).deposit(1, victim.address) // dust deposit on behalf of victim
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30)

// victim's own deposit into any token they don't already hold reverts:
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// victim's first borrow in a new synthetic also reverts at addToDebtTokensOfAccount:
await expect(
  debtToken.connect(victim).issue(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```
