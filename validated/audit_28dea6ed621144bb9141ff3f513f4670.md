### Title
Dust-transfer stuffing of `depositTokensOfAccount` blocks liquidations, deposits-on-behalf, and transfers via `UserReachedMaxTokens` reverts - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER = 30` (combined deposit + debt tokens) and reverts when the limit is reached [1](#0-0) . Because `DepositToken._transfer` (and `_mint` via `deposit`) unconditionally calls `addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero [2](#0-1) , any EOA can permissionlessly stuff arbitrary entries into a victim's per-account list by depositing dust in each registered collateral and transferring 1 wei to the victim. Once the victim's list is full, any path that would add a new deposit-token entry for that account reverts — including `deposit(amount, onBehalfOf_=victim)`, plain `transfer`/`transferFrom`, and most critically `depositToken_.seize()` inside `Pool.liquidate` when the liquidator or the `feeCollector` is the stuffed account.

### Finding Description
The per-account token list exists so `debtPositionOf`/`depositOf`/`debtOf` can iterate over held positions [3](#0-2) . The cap prevents unbounded iteration (the same resource-consumption class as the libexpat advisory — forcing repeated/prew-bound work), but the revert-on-full behavior is reachable by an unprivileged attacker against *other* accounts:

1. For every registered `DepositToken` T_i the victim does not yet hold, the attacker calls `T_i.deposit(1 wei-equivalent, attacker)` then `T_i.transfer(victim, 1)`. Each transfer appends T_i to `depositTokensOfAccount[victim]` [4](#0-3) .
2. After the combined list hits 30, `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` for any new collateral type.
3. **Liquidation griefing:** `Pool.liquidate` ends with `depositToken_.seize(account_, _msgSender, _toLiquidator)` and, when `fee > 0`, `seize(account_, feeCollector, _fee)` [5](#0-4) . If the liquidator's own list is full and the seized collateral token is not already in it, the seize reverts and the whole liquidation fails. An attacker can front-run any pending liquidation in the mempool with a 1-wei dust transfer of an unused deposit token to the liquidator (or pre-stuff the `feeCollector`), repeat this each block, and keep an underwater position unliquidatable. The attacker can simultaneously stuff the *borrower's* list to prevent third parties (`deposit(..., onBehalfOf_)`, gateways, SmartFarmingManager flows) from adding new collateral types that would restore health.

Nothing in `whenNotShutdown`, `nonReentrant`, `SynthContext._msgSender`, or health checks mitigates this — the revert occurs in the token-list bookkeeping, after all checks pass. `DebtToken` is non-transferable [6](#0-5) , but its list entries can also be consumed on a victim only via `issue`/`mint` on their own behalf, so the practical vector is deposit-token dust.

### Impact Explanation
- **Temporary freezing of liquidation liveness / bad-debt accumulation:** every liquidation attempt whose seized collateral would be a *new* entry for the stuffed account reverts, so an underwater position cannot be liquidated while the stuffing is maintained. Positions deeper underwater accrue bad debt.
- **Temporary freezing of funds for victims:** any deposit-on-behalf, `NativeTokenGateway.deposit`, `VesperGateway`/Operator-mediated deposit, or inbound `transfer`/`transferFrom`/`seize` of a collateral type not already in the victim's list reverts, blocking recapitalization of a position approaching liquidation.
- Cost to the attacker is dust-scale collateral plus gas; no privileged role, oracle manipulation, or governance action is required.

### Likelihood Explanation
Fully unprivileged: depositing and transferring `DepositToken` shares is public, and `_revertIfLocked` only constrains the *sender's* balance [7](#0-6) . The attack scales with the number of registered deposit tokens on the pool (several exist per deployment). Front-running a liquidator additionally requires mempool monitoring on mainnet-style chains; stuffing the `feeCollector` proactively makes every fee-charging liquidation in a new collateral type revert without any timing requirement. The victim can clear entries only by fully zeroing balances (withdraw/transfer), which costs them gas and may be impossible for locked collateral.

### Recommendation
Make list insertion non-reverting for the *recipient*, or bound griefability:
- In `DepositToken._transfer`/`seize`, treat a full recipient list gracefully: either allow `seize` to skip list insertion (the seized tokens still sit in `balanceOf`, only accounting iteration misses them — undesirable) or, preferably, maintain the list differently so a full list does not break token receipt — e.g., cap entries but remove a zero/dust entry, or let `addToDepositTokensOfAccount` no-op on `UserReachedMaxTokens` for `seize`/`transfer` while still enforcing on `deposit`/`issue`.
- Alternatively, adopt an enumerable per-account mapping that tolerates >30 entries and paginate `debtPositionOf` rather than reverting on receipt paths.

### Proof of Concept
Hardhat sketch (deployed pool with ≥30 slots reachable, `msdA`..`msdN` deposit tokens, victim `alice`):

```solidity
// 1) Stuff victim's list
for (uint i; i < depositTokens.length; ++i) {
    DepositToken dt = depositTokens[i];
    dt.deposit(1e6, attacker);            // dust deposit
    dt.transfer(victim, 1);               // adds entry for victim
}
// victim now has 30 combined entries
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
msdNew.deposit(1e18, victim);             // deposit-on-behalf reverts

// 2) Grief a liquidation
// liquidator's list is stuffed the same way (or feeCollector's is pre-stuffed);
// an unhealthy position exists on 'target'
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
pool.liquidate(msUSD, target, repayAmount, msdNotInLiquidatorList);
```

Reproducible on a fork: create an underwater position (issue near max, move oracle price), stuff the would-be liquidator's `depositTokensOfAccount` with 1-wei transfers of each unused collateral, then observe every `liquidate` call revert inside `seize` until the liquidator empties entries — at which point the attacker re-stuffs them in the same block via front-running.
