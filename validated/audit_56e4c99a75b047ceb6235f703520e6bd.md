### Title
Overflow in `TokenTransferMatcher::finalize_into`'s unmatched-delta computation lets fabricated token balances bypass the zero-sum invariant - ([File: contracts/defuse/core/src/engine/state/deltas.rs])

### Summary
`TokenTransferMatcher::finalize_into` computes the residual unmatched deposit/withdrawal amount using `u128` accumulation followed by `i128::try_from(...).ok()`, and on failure falls back to `.unwrap_or_default()` producing `0i128`. `TransferMatcher::finalize` then treats a `0` residual as "no violation" via the short-circuiting `unmatched == 0 || ...` check, so a genuinely non-zero, overflowing residual is silently discarded instead of raising `InvariantViolated::UnmatchedDeltas`. This lets an attacker mint fictitious internal token balance via `TokenDiff` intents with no offsetting withdrawal anywhere in the batch, as long as the aggregated unmatched amount exceeds `i128::MAX`.

### Finding Description
Binding that must hold: `sum(all TokenDiff deposits for token T in batch) == sum(all TokenDiff withdrawals for token T in batch)` (i.e., net internal balance change for T across the whole `MultiPayload` batch is 0). This is enforced by `TransferMatcher::finalize` [1](#0-0) , which is the only invariant check standing between `TokenDiff`'s pure-bookkeeping balance mutation and contract commit.

`TokenDiff::execute_intent` calls `engine.state.internal_apply_deltas(...)`, which for positive deltas invokes `internal_add_balance` directly on the underlying `Contract` state — incrementing `owner.token_balances` with **no check that any real token custody backs it** [2](#0-1) . The only safety net is the deferred `TransferMatcher::finalize()` check that runs once, at the end of the whole batch, and must detect any deposit that isn't matched by a corresponding withdrawal.

In `TokenTransferMatcher::finalize_into`, when only deposits (no withdrawals) remain unmatched:
```
if let Some((_, receive)) = deposit {
    return Err(deposits
        .try_fold(receive, |total, (_, r)| total.checked_add(r))
        .and_then(|total| i128::try_from(total).ok())
        .unwrap_or_default());
}
``` [3](#0-2) 

If the summed residual `total` (a `u128`) exceeds `i128::MAX` (2^127-1), `i128::try_from(total)` returns `None`, and `.unwrap_or_default()` silently yields `0i128`. Back in `finalize`, `unmatched == 0` short-circuits `deltas.apply_delta(...)`, so the unmatched, overflowing deposit is never recorded as a violation [4](#0-3) . The batch is accepted as if perfectly balanced.

Attacker's exact payload: sign a single `MultiPayload` batch with two `TokenDiff` intents (either from the same signer with two nonces, or two attacker-controlled accounts) on an arbitrary `TokenId` T, each with a large positive `diff` entry (e.g., close to `i128::MAX`), with no negative delta on T anywhere in the batch. Since each single `TokenDiff` entry is bounded by `i128`, two such intents summed in `TokenTransferMatcher`'s per-owner/per-token accumulator readily exceed `i128::MAX` while staying within `u128` range, triggering the `try_from` failure without even needing the `checked_add` on `u128` to overflow.

This bypasses the exact protection that the existing `test_unmatched` unit test demonstrates works correctly for *small* unmatched deltas [5](#0-4)  — the protection only fails once the unmatched amount overflows `i128`.

### Impact Explanation
The attacker's account balance for token T is credited internally (via `internal_add_balance`, already committed to state before `finalize()` runs) with an amount that has no corresponding real withdrawal or deposit backing it, and the batch commits successfully instead of panicking/reverting. If T corresponds to a real NEP-141/171/245 token custodied by the Verifier on behalf of other users, the attacker can subsequently call the legitimate `ft_withdraw`/`mt_withdraw` intent to redeem this fabricated balance against real custodied tokens belonging to others — the Verifier now owes more than it custodies. This is a Critical-severity finding: "a batch whose balance changes do not net to zero so the Verifier owes more than it custodies," repeatable per token and per batch by any unprivileged signer using only self-controlled accounts.

### Likelihood Explanation
Preconditions are minimal: the attacker needs no roles, no victim keys, and no special contract state — only the ability to sign two `TokenDiff` intents with large `i128` deltas (values readily representable, no special token amount required) referencing any `TokenId`. No real deposit is required to construct the fabricated credit itself (the overflow-triggering deltas are pure bookkeeping); a real, previously-deposited balance is only needed at the later withdrawal step to realize profit. This is fully attacker-controlled and deterministically reproducible in a unit test with no timing/race dependency.

### Recommendation
Do not use `unwrap_or_default()` to collapse an arithmetic failure into `0` (which is indistinguishable from "no violation"). On `checked_add`/`try_from` failure, `finalize_into` must return a distinguishable overflow signal (e.g., keep returning `Result<(), Option<i128>>` or a dedicated enum) so `TransferMatcher::finalize` unconditionally maps it to `InvariantViolated::Overflow` rather than treating it as a matched (zero) delta.

### Proof of Concept
```rust
// contracts/defuse/core/src/engine/state/deltas.rs (added test)
#[test]
fn test_unmatched_overflow_hidden() {
    let mut deltas = TransferMatcher::default();
    let [a, b]: [AccountId; 2] =
        ["a", "b"].map(|s| format!("{s}.near").parse().unwrap());
    let ft1 = TokenId::from(Nep141TokenId::new("ft1.near".parse::<AccountId>().unwrap()));

    // two unmatched deposits, no withdrawals, summing above i128::MAX
    // each delta individually valid (<= i128::MAX)
    assert!(deltas.add_delta(a.clone(), ft1.clone(), i128::MAX));
    assert!(deltas.add_delta(b.clone(), ft1.clone(), i128::MAX));

    // BUG: finalize() succeeds instead of returning UnmatchedDeltas/Overflow,
    // even though a and b's balances were credited with no backing withdrawal.
    let result = deltas.finalize();
    assert!(result.is_ok(), "expected silent bypass due to overflow bug");
}
```
Expected (buggy) behavior: `finalize()` returns `Ok(Transfers::default())` even though `a` and `b` together received `2*i128::MAX` of `ft1` with zero corresponding withdrawal — proving the invariant `sum(deposits) == sum(withdrawals)` is violated yet unreported. A full `near-workspaces` sandbox reproduction would additionally show `execute_intents` committing two `TokenDiff` intents (from one or two attacker-controlled signers) with large positive deltas on a real NEP-141 `TokenId`, followed by a successful `ft_withdraw` draining tokens deposited by other users, with no panic/revert at the `execute_intents` call.

    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)
                && (unmatched == 0 || deltas.apply_delta(token_id, unmatched).is_none())
            {
                return Err(InvariantViolated::Overflow);
            }
        }
        if !deltas.is_empty() {
            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }
        Ok(transfers)
    }

    fn internal_add_balance(
        &mut self,
        owner_id: AccountId,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
    ) -> Result<()> {
        let owner = self
            .accounts
            .get_or_create(owner_id)
            // we allow locked accounts to accept deposits and incoming deposits
            .as_inner_unchecked_mut();

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }
            owner
                .token_balances
                .add(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        Ok(())
    }
