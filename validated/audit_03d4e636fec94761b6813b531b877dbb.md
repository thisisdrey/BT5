## Title
`MortgageService.computeReward()` divides before multiplying using floating point, causing systemic reward-precision loss - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The "old" (pre-VI-algorithm) voting-reward computation in `MortgageService` computes a voter's share of a super representative's cycle reward by first dividing `userVote` by `totalVote` into a `double`, and only then multiplying by `totalReward`. This is the identical "divide-before-multiply" pattern flagged in the external `FluidLocker::_getUnlockingPercentage()` report, and it produces the same class of systematic rounding/precision loss on every call, reachable from an ordinary `WithdrawBalanceContract` transaction.

### Finding Description
`computeReward(long cycle, List<Pair<byte[], Long>> votes)` performs:
```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
``` [1](#0-0) 

This divides `userVote / totalVote` first (losing fractional precision in a `double`), then multiplies by `totalReward`, instead of computing `userVote * totalReward / totalVote` (multiply first). Mathematically, `(a/b) * c != (a*c)/b` under finite-precision floating point arithmetic — the division-first ordering discards bits of precision before the multiplication can restore them, exactly mirroring the root cause described in the external report ("it divides before multiplying, leading to precision loss").

This routine is used by `computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule)` via `getOldReward()` for every cycle prior to `newRewardAlgorithmEffectiveCycle` (the pre-VI legacy reward era still supported in code): [2](#0-1) 

Both `withdrawReward()` and `queryReward()` call this path, and both are directly reachable by any unprivileged account:
- `withdrawReward()` is invoked from `WithdrawBalanceActuator.execute()`, triggered by broadcasting a standard `WithdrawBalanceContract` transaction. [3](#0-2) 
- `queryReward()` is also invoked in `WithdrawBalanceActuator.validate()` and exposed through `GetRewardServlet`/RPC (HTTP/gRPC query paths). [4](#0-3) 

Notably, elsewhere in the same codebase the correct multiply-then-divide pattern with `BigInteger`/exact arithmetic is used for the newer VI-based reward algorithm and for exchange/market calculations (e.g. `MortgageService.computeReward(long,long,AccountCapsule)` new-algorithm branch, `RewardViCalService`, `ExchangeWithdrawActuator`, `MarketUtils.multiplyAndDivide`), confirming that the legacy `double`-based divide-first computation is the outlier and an unintentional precision bug rather than a designed behavior. [5](#0-4) [6](#0-5) 

### Impact Explanation
Every voter reward computed under the legacy (pre-new-reward-algorithm) cycles is subject to floating-point truncation from dividing before multiplying. This causes voters to systematically receive slightly less reward than they are entitled to (the difference is truncated when the accumulated `double` is cast/added into the `long reward`). Because this occurs on every `withdrawReward`/`queryReward` call across all cycles and all voters for the legacy period, the fund loss accumulates similarly to the cited report's "1 BPS loss ... accumulates" scenario. This is a real, protocol-level fund-accounting error affecting user balances (reward payouts), qualifying as a Medium severity precision/fund-loss issue.

### Likelihood Explanation
The bug triggers on essentially every call into the legacy reward path — any account with votes cast in a cycle prior to `newRewardAlgorithmEffectiveCycle` calling `WithdrawBalanceContract` (a routine, permissionless user transaction) exercises this code. No special preconditions, privileges, or attacker coordination are required; it is a deterministic, always-active precision defect in a widely-used code path (reward withdrawal), matching the "always present, frequently triggered" characterization in the source report.

### Recommendation
Reorder the arithmetic to multiply before dividing, matching the fix already applied for the new VI-based algorithm elsewhere in the same file:
```java
reward += (userVote * totalReward) / totalVote;
```
using `BigInteger` (or a checked multiply) to avoid overflow, consistent with the `deltaVi.multiply(...).divide(...)` pattern already used for the new reward algorithm and with `MarketUtils.multiplyAndDivide`.

### Proof of Concept
Example: `totalVote = 3`, `userVote = 1`, `totalReward = 100`.
- Correct (multiply-first): `(1 * 100) / 3 = 33` (integer truncation of the true 33.33).
- Current buggy (divide-first, double): `voteRate = 1.0/3.0 = 0.3333333333333333`; `voteRate * 100 = 33.33333333333333`; when repeatedly accumulated across many votes/cycles and finally truncated into `long`, the compounding floating-point error causes the cumulative sum to diverge from the exact integer-math result, systematically shorting some voters of dust-level reward on every legacy-cycle withdrawal, exactly as demonstrated by the analogous `_getUnlockingPercentage` discrepancy in the source report.

    long reward = 0;

      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  public void adjustAllowance(AccountStore accountStore, byte[] accountAddress, long amount)
      throws BalanceInsufficientException {
    AccountCapsule account = accountStore.getUnchecked(accountAddress);
    long allowance = account.getAllowance();
    if (amount == 0) {
      return;
    }

    if (amount < 0 && allowance < -amount) {
      throw new BalanceInsufficientException(
          String.format("%s insufficient balance, amount: %d, allowance: %d",
              StringUtil.createReadableString(accountAddress), amount, allowance));
    }
    account.setAllowance(allowance + amount);
    accountStore.put(account.createDbKey(), account);
  }

  private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;
  }

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
