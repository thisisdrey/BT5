### Title
Stale PostponedReceipt survives DeleteAccount and executes privileged self-actions (AddKey/DeployContract) against a re-created account - (File: core/store/src/utils/mod.rs / runtime/runtime/src/actions.rs)

### Finding Description
`remove_account` in `core/store/src/utils/mod.rs` deletes `TrieKey::Account`, `ContractCode`, all `AccessKey`/gas-key entries, and `ContractData` for the account, but never touches `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId`: [1](#0-0) [2](#0-1) 

`action_delete_account` in `runtime/runtime/src/actions.rs` only checks storage-size, gas-key-burn limits, and (via `check_actor_permissions`) that `locked().is_zero()`; there is no check for outstanding postponed receipts before calling `remove_account`: [3](#0-2) [4](#0-3) 

A self-targeting `ActionReceipt` (predecessor_id == receiver_id == A) that has an unmet `input_data_id` is stored as a `PostponedReceipt` keyed only by `receiver_id, receipt_id` — with no link back to a specific account "incarnation": [5](#0-4) 

When the missing `DataReceipt` eventually arrives, `process_receipt` looks the postponed receipt back up purely by `receiver_id`/`receipt_id` and unconditionally re-executes it via `apply_action_receipt`, with no check on whether the account was deleted and recreated in the interim: [6](#0-5) 

Inside `apply_action_receipt`, `actor_id` is (re-)initialized straight from the stale receipt's `predecessor_id` field, which for a self-call equals `account_id`: [7](#0-6) 

`check_actor_permissions` for `AddKey`/`DeployContract`/`DeleteKey`/etc. only checks `actor_id == account_id` (plain string equality), and `check_account_existence` only checks that an account currently exists — neither checks that the account is the *same* account (same lifetime/incarnation) that originally authorized the pending action: [8](#0-7) [9](#0-8) 

Exploit flow: (1) attacker's account A submits a self-call (e.g. `promise_batch_then` on itself) that becomes an `ActionReceipt{predecessor_id: A, receiver_id: A, actions: [AddKey(...)]}` postponed on a missing `input_data_id`; (2) A submits `DeleteAccount` — succeeds because `locked == 0` and there is no check on pending postponed receipts; (3) anyone (or a colluding party) issues `CreateAccount` recreating `A` with a fresh owner key; (4) the attacker (who controls the data producer of the still-outstanding promise) delivers the matching `DataReceipt`, driving `PendingDataCount` to 0 and causing the stale `PostponedReceipt` to execute its `AddKey` action against the newly-recreated account — passing both `check_account_existence` (account now exists) and `check_actor_permissions` (`actor_id == account_id` trivially holds for a self-call) even though the current owner never authorized this key.

### Impact Explanation
This is an authorization escalation across the account-lifecycle boundary: the original account owner (before deletion) can inject an `AddKey` (or `DeployContract`) action into the account namespace after it has been re-created and is controlled by a different owner, without that new owner's consent. This maps to the "authorization escalation across accounts or promises" bounty category, since it lets a party retain covert control (a hidden access key or replaced contract code) over an account that legitimately belongs to someone else post-recreation.

### Likelihood Explanation
The attack requires only ordinary, unprivileged actions available to any funded account: submitting self-targeting promise chains, calling `DeleteAccount` on one's own zero-locked account, and later relaying a `DataReceipt` for a promise the attacker itself set up (since the attacker is the original data producer). The one external dependency is that some third party (or the attacker under an alias, or an automated account-recreation flow) must recreate the exact same `AccountId` before the pending data arrives; this is plausible for sub-accounts (freely recreatable by any account with sub-account creation rights under the parent) and for NEAR/ETH-implicit accounts (recreatable via a simple `Transfer`). The attacker fully controls timing of the final `DataReceipt` delivery, making the attack repeatable and low-cost.

### Recommendation
`remove_account` should additionally scan and remove any `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries keyed by the account being deleted (mirroring how it already cleans up access keys and contract data), or `action_delete_account`/`check_actor_permissions` should reject `DeleteAccount` while the account still has outstanding postponed receipts. Alternatively, bind postponed receipts to an account "incarnation" identifier (e.g., an account creation nonce) and have `apply_action_receipt` verify that the current account's incarnation matches the one recorded at postponement time before allowing privileged actions (`AddKey`, `DeployContract`, `DeleteKey`, etc.) to execute.

### Proof of Concept
Runtime/integration test plan (in `runtime/runtime/src/tests/apply.rs` style, similar to `test_promise_input_size_limit_exceeded_fails_and_cleans_up` and `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Set up account `alice` with `locked = 0`.
2. Feed the runtime a self-targeting `ActionReceipt{predecessor_id: alice, receiver_id: alice, input_data_ids: [data_id], actions: [AddKey(evil_key)]}` with the matching `DataReceipt` for `data_id` withheld — assert it becomes a `PostponedReceipt` via `get_postponed_receipt`.
3. Apply a `DeleteAccount` receipt for `alice` (beneficiary arbitrary) in the same or next chunk — assert it succeeds and `get_account(alice)` returns `None`, while `get_postponed_receipt(alice, receipt_id)` still returns `Some(..)`.
4. Apply a `CreateAccount` receipt recreating `alice` with a new owner's key.
5. Deliver the withheld `DataReceipt{receiver_id: alice, data_id}`.
6. Assert that `alice`'s access-key set now contains `evil_key` (or that code hash changed, for the DeployContract variant), proving the stale postponed receipt executed against the re-created account without the new owner's consent.

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) => (),
    };
    Ok(())
