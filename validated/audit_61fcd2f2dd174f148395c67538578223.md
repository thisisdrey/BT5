### Title
Uncontrolled Resource Consumption via Unvalidated ABI Array-Length Field in `ValidateMultiSign`/`BatchValidateSign` Precompiles - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts decode ABI-encoded `bytes[]`/`address[]` arrays by trusting an attacker-supplied length word embedded inside the call data, without bounding it against the actual size of that data, before using it to size a Java array allocation. This mirrors CVE-2018-5784's root cause: a declared element/entry count taken from untrusted input is used to drive resource allocation/iteration without first validating it against the real amount of data present.

### Finding Description
`extractBytesArray`, `extractSigArray`, and `extractBytes32Array` in `PrecompiledContracts.java` all follow the same unsafe pattern: [1](#0-0) 

```
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
for (int i = 0; i < len; i++) { ... }
```

`words[offset]` is an attacker-controlled 256-bit word taken directly from the transaction's/internal-call's raw ABI-encoded input. `DataWord.intValueSafe()` clamps any out-of-range or overflowing value to `Integer.MAX_VALUE` rather than rejecting it: [2](#0-1) 

Nothing in these helper methods checks `len` against the number of words actually available in `data`/`words` before the `new byte[len][]` allocation executes. In `ValidateMultiSign.execute`, this legacy path is reached whenever `VMConfig.allowTvmSelfdestructRestriction()` is not active for the executing chain — the size guard (`sigArraySize > MAX_SIZE`) is only applied on the flag-enabled branch, while the flag-disabled branch calls `extractBytesArray` unguarded: [3](#0-2) 

The same pattern exists in `BatchValidateSign.doExecute` for both the `signatures`/`addresses` extraction: the `sigArraySize`/`addrArraySize` bound check is likewise gated by the same feature flag before `extractSigArray`/`extractBytesArray`/`extractBytes32Array` are invoked: [4](#0-3) 

The newer `isValidAbiEncoding` guard (added for TIP-854/`allowTvmOsaka`) only checks that the overall data length is congruent with a header+N*item word layout — it never cross-validates the self-declared inner array-length word against the actual number of item slots present, so a crafted call data can declare `len = 0x7fffffff` while the outer data is only a few words long, exactly analogous to the LibTIFF bug where the declared directory-entry count was never checked against the real directory size.

### Impact Explanation
A single TVM `CALL`/`STATICCALL` to the `validateMultiSign` (`0x69`) or `batchValidateSign` (`0x66`) precompile address, issued by any contract deployer or contract caller, can force `new byte[Integer.MAX_VALUE][]` (or a similarly huge array) to be allocated during transaction execution. This triggers immediate memory pressure/`OutOfMemoryError` on every full node that executes or re-validates the transaction/block (during `Manager` block application), which can crash or destabilize node processes and, because it is deterministic across all nodes replaying the same block, can produce a consensus-wide denial of service rather than affecting only a single node.

### Likelihood Explanation
Reachable from any unprivileged account by simply crafting a smart-contract call with hand-built (non-Solidity-ABI-encoder-generated) call data to the precompile address; no special privileges, staking, or witness/committee role are required. It is only exercised on chains/configurations where `VMConfig.allowTvmSelfdestructRestriction()` has not been activated (e.g., freshly bootstrapped or private/consortium java-tron networks, or any deployment prior to that proposal's activation), which is a realistic and common deployment scenario for java-tron-based chains.

### Recommendation
Validate the declared array-length word against the remaining word budget (`words.length - offset - 1`) inside `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` themselves — independent of the `allowTvmSelfdestructRestriction`/`allowTvmOsaka` feature flags — before allocating `new byte[len][]`, rejecting the call (`Pair.of(true, DATA_FALSE)`) when `len` exceeds the bytes actually supplied.

### Proof of Concept
1. Construct raw call data for `validateMultiSign(address,uint256,bytes32,bytes[])` (or `batchValidateSign`) by hand rather than via a standard ABI encoder.
2. Set the head words normally (address, permissionId, hash, offset-to-array).
3. At the array-length slot pointed to by the offset word, place `0x7fffffff` (or any value causing `intValueSafe()` to return `Integer.MAX_VALUE`), while keeping the overall call-data buffer short (just a few words).
4. Deploy a contract that performs `CALL` to precompile address `0x69`/`0x66` with this crafted data, and broadcast a transaction invoking it on a network where `allowTvmSelfdestructRestriction` has not been activated.
5. Observe `extractBytesArray`/`extractSigArray`/`extractBytes32Array` attempting `new byte[0x7fffffff][]`, causing memory exhaustion during transaction execution on every node validating the block.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {

          bytesLen);
    }
    return bytesArray;
  }

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
