### Title
Multi-contract transaction permission bypass — only the first contract's owner/permission is authenticated while all contracts in the raw transaction are processed and fee-charged - ([File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java])

### Summary
`Transaction.raw` in java-tron declares `contract` as a `repeated` field, so a single transaction can legally carry more than one `Contract` entry, each potentially with a different `owner_address`. Signature/permission verification, however, is only ever performed against `contract(0)`, while downstream bookkeeping code (multi-sign fee deduction) iterates over *all* contracts in the list and treats each contract's declared owner as authoritative. This is structurally analogous to CVE-2018-18955: an ID/authorization transformation ("this owner is authorized to act") is applied correctly in one direction (fee accounting assumes every listed owner participated) but is never verified in the other direction (signature/permission checking, which only covers index 0).

### Finding Description
`TransactionCapsule.validateSignature()` explicitly limits itself to the first contract entry and documents this as an assumption rather than an enforced invariant: [1](#0-0) 

`validatePubSignature()` (called from `validateSignature`) resolves the owner and `Permission` strictly from `contract(0)`, checks operation-bit permissions and signature weight only for that one contract: [2](#0-1) 

`Wallet.getTransactionSignWeight` and `Wallet.getTransactionApprovedList` follow the same single-contract permission model: [3](#0-2) 

Meanwhile, `Manager.consumeMultiSignFee()` iterates over **every** contract in `trx.getInstance().getRawData().getContractList()` and debits a fee from each contract's declared owner address, independent of whether that owner's signature/permission was ever checked: [4](#0-3) 

Because actuators are instantiated per `Contract` entry from the same repeated list and executed sequentially during block application, any contract entry beyond index 0 is executed and its owner's balance/state mutated without that owner ever having signed the transaction or having their permission checked — the permission "transformation" (signature-to-authorization) is only enforced for the head of the list, not for the rest of the list that is actually processed.

### Impact Explanation
An attacker who controls a valid, low-privilege account can craft a single transaction whose `contract(0)` is a trivial, self-authorized operation (satisfying signature/permission validation), and append additional `Contract` entries whose `owner_address` is set to an arbitrary victim account. Because only `contract(0)` is authenticated, the additional contracts (e.g. transfers, votes, freezes) can execute as if signed by the victim, resulting in unauthorized account operations, theft of funds, or permanent freezing of a victim's balance — matching the "unauthorized account operation / theft of funds" impact bar.

### Likelihood Explanation
Any unprivileged transaction broadcaster can construct such a transaction using nothing but the JSON-RPC/HTTP/gRPC broadcast API (`Wallet.broadcastTransaction`), since transaction construction is client-side and the `repeated Contract contract` field is not restricted to size 1 in `validatePubSignature`/`validateSignature`. No special privilege, key leakage, or SR/witness compromise is required — only the ability to submit a signed transaction, which is the baseline capability assumed by this analog scan.

### Recommendation
Enforce a single-contract-per-transaction invariant end-to-end: reject any transaction whose `getContractCount() != 1` at signature validation and at broadcast/acceptance time (not just document it in a comment), or, if multi-contract transactions are intended to be supported in the future, validate signature/permission for every contract entry individually (as is already partially done in test utility `TransactionUtils.validTransaction`) before any actuator execution or fee deduction is allowed to reference a given owner address.

### Proof of Concept
1. Build a `Transaction.raw` with two `Contract` entries: `contract[0]` = a self-authorized no-op-like operation from attacker's account `A` (passes `validatePubSignature`); `contract[1]` = `TransferContract`/`VoteWitnessContract`/etc. with `owner_address` set to victim account `B` who never signs.
2. Sign the transaction with `A`'s key only (satisfies `getSignatureCount() > 0` and `validateSignature` since only `contract(0)` is checked).
3. Broadcast via `Wallet.broadcastTransaction`.
4. During block application, `Manager` builds actuators for each contract (including `contract[1]`) and `consumeMultiSignFee` iterates and debits `B`'s account; the actuator for `contract[1]` executes using `B`'s address as owner without `B`'s signature ever being verified.

Note: I was not able to fully trace, within the indexed portion of the codebase, whether an additional consensus-level check (e.g., in `TransactionValidator` or block-acceptance code) enforces `getContractCount() == 1` elsewhere in the pipeline; if such an enforcement exists outside the files reviewed, it would neutralize this analog. A Devin session with full repository access would be needed to confirm whether contract-count is restricted anywhere between broadcast and `Manager` execution.
