Audit Report

## Title
Relayer rewards are settled and cleared on `pay_reward` delivery, not on remote execution, causing permanent, unrecoverable loss of reward funds - ([File: bridges/modules/relayers/src/lib.rs])

## Summary
`do_claim_rewards` in `bridges/modules/relayers/src/lib.rs` removes the relayer's `RelayerRewards` entry and emits `Event::RewardPaid` as soon as `T::PaymentProcedure::pay_reward` returns `Ok(())`, and for the Snowbridge reward kind that success is determined solely by `XcmSender::deliver(ticket)` succeeding in `PayAccountOnLocation::pay_reward` (`bridges/snowbridge/primitives/core/src/reward.rs`), not by confirmation that the remote `ReserveAssetDeposited`/`DepositAsset` sequence actually executes on AssetHub. This decouples ledger settlement from actual custody transfer, so a remote execution failure after successful delivery permanently and irrecoverably clears the relayer's reward record with no on-chain recovery path.

## Finding Description
`do_claim_rewards` takes the reward balance out of `RelayerRewards`, calls `PaymentProcedure::pay_reward`, and on `Ok(())` deposits `RewardPaid` and commits the `try_mutate_exists`, permanently discarding the ledger entry: [1](#0-0) 

For `BridgeReward::Snowbridge`, `pay_reward` is implemented by `PayAccountOnLocation::pay_reward`, which builds an XCM containing `ReserveAssetDeposited`/`DepositAsset` targeting AssetHub, validates it, charges fees, and calls `XcmSender::deliver(ticket)`, returning `Ok(())` immediately once delivery succeeds — with no callback, receipt, or later confirmation that the `ReserveAssetDeposited`/`DepositAsset` instructions actually executed successfully on the destination: [2](#0-1) 

The unit tests for this procedure (`pay_reward_success`, `pay_reward_fails_on_delivery`, `pay_reward_fails_on_charge_fees`) only assert against `validate`/`deliver`/fee-charging outcomes, never against remote execution outcome, confirming the remote-execution-failure path is unverified: [3](#0-2) [4](#0-3) 

Notably, the same codebase already contains an established pattern for handling exactly this class of problem correctly: `PayOverXcm`/`TransferOverXcm` in `polkadot/xcm/xcm-builder`, which is explicitly asynchronous and returns a `QueryId` that callers must later check via `check_payment`/`check_transfer` before treating the payment as settled: [5](#0-4) [6](#0-5)  The Snowbridge reward payment procedure does not use this query/confirmation mechanism, instead treating bare `deliver()` success as final settlement, which is the root cause of the invariant break: ledger-clearing advances before dispatch+execution+settlement all succeed, contrary to the required "advance only after decode, dispatch, execution, and settlement succeed atomically" invariant.

The beneficiary `Location` is supplied by the caller in the permissionless `claim_rewards_to` extrinsic: [7](#0-6)  and is passed through to `PayAccountOnLocation::pay_reward` from the runtime-level dispatch: [8](#0-7)  If remote execution of `ReserveAssetDeposited`/`DepositAsset` fails on AssetHub for any reason (malformed/unsupported beneficiary junction, filtered account, barrier/trust misconfiguration, asset not registered, etc.), the reward is trapped or never minted, while `RelayerRewards` has already been cleared on BridgeHub in the same transaction that only confirmed delivery.

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" and "payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" categories in the Polkadot SDK impact gate: the relayer's earned reward balance is deleted from on-chain storage based only on successful message hand-off, with no mechanism to detect or recover from remote execution failure, resulting in an unrecoverable loss of the exact accounted `reward_balance` value.

## Likelihood Explanation
Reaching this path requires only a signed relayer with an existing registered reward calling the permissionless `claim_rewards_to` extrinsic — no governance, validator collusion, or privileged role is needed. Failure of the destination-side `ReserveAssetDeposited`/`DepositAsset` execution is plausible under ordinary conditions (configuration drift, unsupported/malformed beneficiary junctions, or barrier/asset-registration mismatches between BridgeHub and AssetHub), and the existing test suite explicitly acknowledges it only covers the delivery-failure case, not the remote-execution-failure case, leaving this path unguarded and untested.

## Recommendation
Do not treat `XcmSender::deliver()` success as final settlement for `RelayerRewards`. Either defer clearing the ledger entry until remote execution is confirmed (e.g., adopt the existing `PayOverXcm`/query-id-based confirmation pattern already present in `polkadot/xcm/xcm-builder`), or add a permissionless recovery/retry mechanism that restores the reward balance if remote execution is later proven to have failed instead of unconditionally deleting the ledger entry on mere delivery success.

## Proof of Concept
1. Relayer accrues a `BridgeReward::Snowbridge` reward via `register_reward`.
2. Relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(loc))` with a `loc` that is syntactically valid but will be rejected by AssetHub's XCM executor at `ReserveAssetDeposited`/`DepositAsset` (e.g., unsupported junction combination or asset-registration mismatch).
3. On BridgeHub: `validate_send` and `XcmSender::deliver` succeed → `pay_reward` returns `Ok(())` → `do_claim_rewards` removes the `RelayerRewards` entry and emits `RewardPaid`, per `bridges/modules/relayers/src/lib.rs` lines 263-295 and `bridges/snowbridge/primitives/core/src/reward.rs` lines 127-151.
4. On AssetHub, the XCM fails at `ReserveAssetDeposited`/`DepositAsset`; the reward asset is trapped or never minted.
5. Relayer's `RelayerRewards` entry is already gone (cleared in step 3) and no asset was received on AssetHub — permanent loss with no on-chain reclaim path, matching the currently untested branch noted in `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-westend/tests/tests.rs` lines 787-795 (which only exercises delivery failure, not remote execution failure).

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
