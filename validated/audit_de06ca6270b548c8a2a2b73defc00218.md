### Title
Unbounded growth of the per-account asset map causes ever-increasing bandwidth-consumption cost for every transaction — (File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java)

### Summary
`BandwidthProcessor.updateUsage()` iterates over every entry in an account's TRC10 asset map (`getAssetMap()` / `getAssetMapV2()`) each time bandwidth usage is calculated for that account — i.e., on essentially every transaction the account sends. The number of distinct asset entries an account can accumulate is unbounded: any other account can send the target account a tiny amount of a brand-new TRC10 token, which the receiver's account has no way to reject, and each new token id creates a new map entry that is never removed. This mirrors the reported "unbounded loop over an ever-growing list" bug class (`TrancheVesting.getVestedFraction`), except here the growth is attacker-controllable and the loop runs in the java-tron actuator's resource-accounting path that fires on every transaction from the victim account.

### Finding Description
`updateUsage(AccountCapsule accountCapsule)` in `BandwidthProcessor` performs: [1](#0-0) 
1. If same-token-name is disallowed, it loops over `accountCapsule.getAssetMap()` (`AccountCapsule.java` map of legacy asset names to balances).
2. It always loops over `accountCapsule.getAssetMapV2()` merged with `getAllFreeAssetNetUsageV2()`, and for each entry calls `increase(...)`.

The asset map that is iterated is stored directly in the `Account` protobuf message (`map<string, int64> asset = 6;` / `assetV2 = 56;`), as declared in the protocol: [2](#0-1) 

Any account can receive a `TransferAssetContract` for an arbitrary TRC10 token it never asked for. `TransferAssetActuator.execute()` unconditionally credits the receiver's asset balance via `addAssetAmountV2`, creating a brand-new map entry keyed by token id if one does not already exist: [3](#0-2) [4](#0-3) 

There is no cap on the number of distinct token ids an account can hold (unlike `frozenSupply`, which is capped by `dynamicStore.getMaxFrozenSupplyNumber()`, or vote lists, capped by `MAX_VOTE_NUMBER`, or `unfrozenV2` entries, capped by `UNFREEZE_MAX_TIMES`). Since new TRC10 tokens can be freely issued (`AssetIssueActuator`/`AssetIssueContractV2`) and airdropped in tiny amounts to arbitrary victim accounts by any unprivileged asset issuer, an attacker can grow a victim's `assetV2` map to an arbitrary size. Every subsequent transaction from the victim account that consumes bandwidth calls `updateUsage`, which walks the entire, ever-growing map — an O(n) cost per transaction that grows without bound and is never reclaimed (there is no removal path for zero-balance token entries in the map iterated here).

### Impact Explanation
This is a stored, permanent (non-expiring) unbounded-growth vector reachable by any unprivileged asset issuer/transaction broadcaster: repeatedly issuing new TRC10 assets and sending tiny transfers to a target address inflates that target's `assetV2` map size indefinitely. Because `updateUsage` (and hence this loop) runs during resource/bandwidth accounting for essentially every subsequent transaction sent by the victim, the per-transaction processing cost for the victim's account grows linearly with the number of distinct assets received, with no mechanism to shrink it back down. In the worst case this degrades transaction processing for that account and increases block-processing time proportionally, since block application also invokes bandwidth accounting for every transaction in the block via the same code path. This is a denial-of-service class issue against a specific account/node processing, not merely a "resource-only" annoyance, because it is attacker-triggerable at will and non-reversible by the victim.

### Likelihood Explanation
High from a mechanical standpoint: issuing an asset (`AssetIssueContract`) and transferring 1 unit of it to an arbitrary address are both ordinary, unprivileged, low-cost operations available to any account. No special permission or contract deployment is required. The only friction is the resource/TRX cost of issuing many assets and sending many transfers, which bounds the practical scale but does not prevent the attack — it is a griefing/DoS vector rather than a one-shot exploit.

### Recommendation
Cap the number of distinct TRC10 token types a single account may hold (similar to `MAX_VOTE_NUMBER`, `getMaxFrozenSupplyNumber()`, and `UNFREEZE_MAX_TIMES`), or reject/require opt-in for asset transfers to accounts that have not explicitly allowed a new token registration in their balance map. Alternatively, redesign resource accounting so that per-account bandwidth usage tracking does not need to enumerate the entire asset map on every transaction (e.g., only iterate assets that actually accrued free-net usage in the current cycle rather than the whole map).

### Proof of Concept
1. Attacker issues N distinct TRC10 tokens using `AssetIssueContract` (or `AssetIssueContractV2`), each is a standard, unprivileged transaction.
2. For each token, attacker sends a `TransferAssetContract` with amount `1` to victim address `V`. `TransferAssetActuator.execute()` calls `toAccountCapsule.addAssetAmountV2(...)`, adding a new entry to `V`'s `assetV2` map every time.
3. After doing this N times (e.g., N = 10,000), `V.getAssetMapV2()` has N entries.
4. Any subsequent transaction sent by `V` triggers bandwidth accounting via `BandwidthProcessor.updateUsage(V)`, which iterates all N entries in `getAssetMapV2()` (and merges with `getAllFreeAssetNetUsageV2()`), consuming linearly more CPU per transaction as N grows, with no bound and no cleanup mechanism.

  public boolean addAssetAmountV2(byte[] key, long amount,
      DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    //key is token name
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAsset(nameKey, addExact(currentAmount, amount, disableJavaLangMath))
          .putAssetV2(tokenID, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenIDStr = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenIDStr);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAssetV2(tokenIDStr, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }
    return true;
  }
