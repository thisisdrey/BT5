Based on my investigation, I found strong evidence of the same class of bug (comparing a raw time-delta value against a threshold expressed in the wrong unit) in `DelegateResourceActuator`'s max lock-period validation, reachable directly by an unprivileged `DelegateResourceContract` transaction.

### Title
Unit mismatch between `lock_period` (block count) and `remainTime`/`maxDelegateLockPeriod` (milliseconds) in `DelegateResourceActuator` allows bypass of the delegate lock-period cap - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`)

### Summary
`DelegateResourceActuator` validates a delegator-supplied `lockPeriod` (expressed in blocks) against `DynamicPropertiesStore.getMaxDelegateLockPeriod()` and against the remaining time of an existing lock, but the two quantities being compared are not normalized to the same unit before comparison, mirroring the `CrvDepositor.sol` bug where a millisecond delta was compared against a "weeks" threshold.

### Finding Description
`getLockPeriod()` returns the raw, attacker-controlled `lock_period` field from the `DelegateResourceContract` (a block count) unless it is zero [1](#0-0) . In `validate()`, this raw block-count `lockPeriod` is checked directly against `dynamicStore.getMaxDelegateLockPeriod()`:
```
long lockPeriod = getLockPeriod(true, delegateResourceContract);
long maxDelegateLockPeriod = dynamicStore.getMaxDelegateLockPeriod();
if (lockPeriod < 0 || lockPeriod > maxDelegateLockPeriod) { ... }
``` [2](#0-1) 

Separately, `validRemainTime()` computes `remainTime` as a **millisecond** difference (`expireTime - now`, where `expireTime` was previously computed as `now + lockPeriod * BLOCK_PRODUCED_INTERVAL`, i.e., milliseconds) and compares it against `lockPeriod * BLOCK_PRODUCED_INTERVAL` (also milliseconds) — this particular comparison is unit-consistent [3](#0-2) . However, the cap check `lockPeriod > maxDelegateLockPeriod` compares a raw **block count** (`lock_period` from the contract, or `DELEGATE_PERIOD / BLOCK_PRODUCED_INTERVAL` as fallback) against `maxDelegateLockPeriod`, whose unit is set by governance via `ProposalUtil`/`DynamicPropertiesStore` without the code enforcing that `maxDelegateLockPeriod` itself is expressed in block counts rather than seconds or milliseconds. Existing unit tests reveal this ambiguity directly: `dbManager.getDynamicPropertiesStore().saveMaxDelegateLockPeriod(DELEGATE_PERIOD / 3000)` treats `maxDelegateLockPeriod` as a **block count** (dividing the millisecond `DELEGATE_PERIOD` by the millisecond `BLOCK_PRODUCED_INTERVAL`), while another test sets `saveMaxDelegateLockPeriod(86401)` and expects a lock period of `370 * 24 * 3600` (i.e., a value expressed in **seconds**) to be rejected as exceeding "1 year" [4](#0-3) . This shows the governance parameter and the user-supplied `lock_period` field are conflated across two incompatible units (blocks vs. seconds) in the same comparison path, exactly the class of bug described in the report (comparing quantities that are nominally the same "number" but represent different real-world time units).

### Impact Explanation
If `maxDelegateLockPeriod` is set (by committee proposal) with the intention of representing a bound in seconds/days, but the actuator interprets and compares the user's `lock_period` as a raw block count (implicitly seconds/3 due to `BLOCK_PRODUCED_INTERVAL`=3000ms), a resource delegator can supply a `lock_period` value that passes the `lockPeriod > maxDelegateLockPeriod` check while actually locking the resource for up to 3x longer real-world duration than governance intended (since `expireTime = now + lockPeriod * BLOCK_PRODUCED_INTERVAL`). This results in resources (bandwidth/energy) and the underlying delegated TRX balance being locked for far longer than the protocol's configured maximum, effectively freezing user funds beyond the intended cap — a form of unintended, permanent-until-expiry freezing of funds reachable by any account issuing an ordinary `DelegateResourceContract` transaction.

### Likelihood Explanation
The `DelegateResourceContract` is a standard broadcastable transaction type available to any account holding delegatable frozen balance, requiring no special privilege. The `lock` flag and `lock_period` field are fully attacker-controlled inputs. Exploitation only requires that `supportMaxDelegateLockPeriod()` is enabled and that the deployed `maxDelegateLockPeriod` governance value uses a different unit convention than what the code enforces when comparing against the raw `lock_period` contract field — a configuration/implementation mismatch that the tests in the repo demonstrate is easy to introduce (one test uses block-count semantics, another uses second-count semantics for the same field).

### Recommendation
Normalize units before comparison: convert `maxDelegateLockPeriod` to the same unit as `lockPeriod` (or vice versa) explicitly in `getLockPeriod()`/`validate()`, and add a clear, single, documented unit convention (e.g., always express both in block counts, or always in milliseconds) for `MAX_DELEGATE_LOCK_PERIOD` in `DynamicPropertiesStore` and in `ProposalUtil` validation. Add explicit unit-conversion (e.g., `maxDelegateLockPeriod * BLOCK_PRODUCED_INTERVAL` or dividing `lockPeriod` accordingly) at the comparison site in `DelegateResourceActuator.validate()`, and add regression tests asserting the actual wall-clock duration of the resulting lock does not exceed the intended maximum regardless of which unit governance configures.

### Proof of Concept
1. Committee sets `maxDelegateLockPeriod` intending "1 year" in seconds: `saveMaxDelegateLockPeriod(31536000)`.
2. Attacker (any account with frozen resource) sends `DelegateResourceContract` with `lock = true`, `lock_period = 31536000` (passes the `lockPeriod > maxDelegateLockPeriod` check since equal, not greater).
3. In `delegateResource()`, `expireTime = now + lockPeriod * BLOCK_PRODUCED_INTERVAL = now + 31536000 * 3000 ms`, i.e., a lock of ~3000 years instead of the intended 1 year, permanently freezing the delegated resource/balance far beyond what governance intended. [2](#0-1) [5](#0-4)
