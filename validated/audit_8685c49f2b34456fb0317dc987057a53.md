### Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` Enables Cross-Chain Replay of Signer Capability Offers — (`aptos-move/framework/aptos-framework/sources/account/account.move`)

---

### Summary

`SignerCapabilityOfferProofChallengeV2` is missing the `chain_id` field that its sibling struct `RotationCapabilityOfferProofChallengeV2` explicitly added to prevent cross-chain replay. A valid `offer_signer_capability` signature produced on one Aptos chain (e.g., testnet) is therefore replayable verbatim on any other Aptos chain (e.g., mainnet) at the same sequence number, allowing an attacker to gain unauthorized signer capability over a victim's account and drain all assets.

---

### Finding Description

The Aptos framework defines two proof-challenge structs for delegating account capabilities:

**`RotationCapabilityOfferProofChallengeV2`** — explicitly includes `chain_id`: [1](#0-0) 

The comment on that struct reads:
> "This V2 struct adds the `chain_id` and `source_address` to the challenge message, which **prevents replaying the challenge message**."

**`SignerCapabilityOfferProofChallengeV2`** — `chain_id` is absent: [2](#0-1) 

`offer_signer_capability` constructs the challenge without `chain_id` and passes it directly to `verify_signed_message`: [3](#0-2) 

`verify_signed_message` performs only a BCS-serialized signature check against the supplied message — it adds no chain binding of its own: [4](#0-3) 

Because the BCS-serialized bytes of `SignerCapabilityOfferProofChallengeV2` are identical across all Aptos chains (mainnet, testnet, devnet) for the same `(sequence_number, source_address, recipient_address)` triple, a signature produced on one chain is cryptographically valid on every other chain.

---

### Impact Explanation

Once an attacker replays the signature and `offer_signer_capability` succeeds, the attacker's address is recorded as the authorized recipient in the victim's `signer_capability_offer`. The attacker then calls `create_authorized_signer` to obtain a live `signer` for the victim's account and can:

- Transfer or burn all APT and fungible assets held by the victim.
- Rotate the victim's authentication key, permanently locking them out.
- Perform any on-chain action that requires the victim's signer.

This is a direct theft / unauthorized reassignment of user-controlled on-chain assets, squarely within the Aptos bounty scope.

---

### Likelihood Explanation

The attack requires the attacker to obtain a valid `offer_signer_capability` signature from the victim for the attacker's own address, at a sequence number that also exists on mainnet. Concrete paths:

1. **Phishing via a testnet dApp**: Trick the victim into signing an `offer_signer_capability` transaction on testnet (sequence number 0 for a fresh account). If the victim's mainnet account is also at sequence number 0 (common for new wallets), the signature replays directly.
2. **Compromised off-chain signing service**: Any service that signs `offer_signer_capability` messages off-chain for testnet use leaks replayable signatures.
3. **Social engineering**: Convince the victim that the signature is harmless on testnet.

New accounts start at sequence number 0 on every chain, making the replay window wide for freshly-created wallets.

---

### Recommendation

Add `chain_id` to `SignerCapabilityOfferProofChallengeV2`, mirroring the fix already applied to `RotationCapabilityOfferProofChallengeV2`:

```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    chain_id: u8,          // ADD THIS
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

And update `offer_signer_capability` to populate it:

```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    chain_id: chain_id::get(),   // ADD THIS
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
```

This is the exact pattern already used by `offer_rotation_capability`: [5](#0-4) 

---

### Proof of Concept

1. Alice has a mainnet account at sequence number 0.
2. Attacker (Bob) deploys a testnet dApp and tricks Alice into calling `offer_signer_capability` on testnet, with `recipient_address = Bob`.
3. Alice's testnet account is also at sequence number 0. She signs the `SignerCapabilityOfferProofChallengeV2` struct:
   ```
   { sequence_number: 0, source_address: Alice, recipient_address: Bob }
   ```
4. Bob extracts Alice's signature bytes.
5. Bob submits an `offer_signer_capability` transaction on **mainnet** using Alice's mainnet account as sender, Alice's public key, and the same signature bytes.
6. `verify_signed_message` succeeds — the BCS bytes are identical across chains.
7. Alice's mainnet `signer_capability_offer.for` is now set to Bob.
8. Bob calls `create_authorized_signer(bob_signer, alice_addr)` on mainnet and receives a live signer for Alice's account.
9. Bob drains all of Alice's mainnet APT and fungible assets.

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
