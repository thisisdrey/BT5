### Title
Unauthenticated `RecvError` teardown accepted on spoofable index/address match, allowing remote tunnel state poisoning - ([File: outside.go])

### Summary
Nebula's `header.RecvError` packets are processed on the fully unauthenticated fast path in `readOutsidePackets`, before any decryption or cert-bound verification, and the receiving host is looked up purely by the attacker-supplied 32-bit `h.RemoteIndex` field, gated only by a UDP source-address string match. This mirrors the external report's bug class: an identifier meant to uniquely and authentically pin a specific session/transition (the pre-state root + tx hash in the OVM report; here, `RemoteIndex`) is instead a bare, observable, non-cryptographic value, so a party who never established a valid session can still manipulate state tied to that identifier.

### Finding Description
In `outside.go`, `readOutsidePackets` dispatches `header.RecvError` directly out of the "Unencrypted packets" switch, i.e. before hostinfo/ConnectionState lookup, decryption, or any certificate/PSK check: [1](#0-0) 

`handleRecvError` then resolves state solely from the packet header's `RemoteIndex` and a coarse config gate, then unconditionally tears down the tunnel unless the recorded remote endpoint is both valid and mismatched: [2](#0-1) 

The only "authentication" applied is:
1. `f.acceptRecvErrorConfig.ShouldRecvError(addr)` — a coarse policy (`always`/`never`/`private`) that defaults to accepting from anywhere, per the changelog entry adding this option: [3](#0-2) 
2. A comparison of the UDP source address against `hostinfo.GetRemote()` — this is a plain string/AddrPort compare against a value learned from prior unauthenticated UDP traffic, not a cryptographic proof of possession. If `hr` is not yet valid (e.g., before the peer's underlay address was confirmed), this check is skipped entirely.

The `RemoteIndex` value itself is not a secret: it is transmitted in the clear in the header of every single packet on the wire (`header.H.RemoteIndex`), as seen throughout `outside.go`'s dispatch logic (e.g. `hostinfo = f.hostMap.QueryIndex(h.RemoteIndex)` at [4](#0-3) ) and is explicitly called out elsewhere in the codebase as attacker-influenced/uncontrolled: `hostmap.go`'s deletion path notes "The remote index uses index ids outside our control": [5](#0-4) .

This is structurally the same bug class as the OVM report: a state-mutating operation (fraud-proof finalization / here, tunnel teardown) is keyed by an identifier (`pre-state root + tx hash` / here, `RemoteIndex`) that does not cryptographically and uniquely bind to the specific session it is meant to represent, and that can be replayed/spoofed by a party who was never a validated participant in that session, letting them collapse state that legitimate protocol logic assumed was exclusively theirs to control.

### Impact Explanation
An attacker who can observe one packet on the wire between two Nebula nodes (any passive on-path observer, or even an off-path attacker who can guess/enumerate the endpoint's UDP source port range) learns the victim's `localIndexId` in cleartext. By spoofing the UDP source address of the legitimate remote peer (classic UDP source-address spoofing, feasible on many networks lacking BCP38 egress filtering) and sending a crafted `RecvError` packet carrying that index, the attacker can force `closeTunnel` and `handshakeManager.DeleteHostInfo` on the victim — silently and remotely tearing down an active, otherwise healthy tunnel. This is a remote state-poisoning / denial-of-service primitive against an unauthenticated attacker (no CA-signed certificate required), directly reachable through packet header parsing and index-based hostmap trust with no cryptographic replay/authentication protection on this message type.

### Likelihood Explanation
Likelihood is bounded mainly by the need to either (a) observe traffic to learn the 32-bit index, or (b) spoof the legitimate peer's UDP source address, or both. Both prerequisites are realistic for a network-adjacent or on-path attacker, and UDP source spoofing remains common on networks without strict source-address validation. The project's own changelog shows awareness of `recv_error` abuse (adding `accept_recv_error`/config knobs, and disabling `recv_error` outside the counter window), but the default policy (`recvErrorAlways`) and the address-based (non-cryptographic) check leave the spoofing path open by default.

### Recommendation
Do not process `RecvError` (or any state-mutating control message keyed by `RemoteIndex`) on the fully unauthenticated fast path. Require it to be authenticated/bound to the session it claims to reference — e.g., only accept a `RecvError`/teardown signal if it can be tied to the current, cryptographically-verified `ConnectionState` for the referenced hostinfo (such as a MAC/counter computed under the session's negotiated key), rather than a bare index-plus-source-address comparison. At minimum, tighten the default `accept_recv_error` policy and document that operators on spoofable underlays should disable acceptance, and treat `hostinfo.GetRemote()` invalidity as "deny" rather than "allow through" in `handleRecvError`.

### Proof of Concept
1. Attacker passively observes any packet from Host B to Host A (or otherwise learns Host A's `localIndexId`, e.g. via a captured handshake or data packet header, which is unencrypted).
2. Attacker crafts a UDP packet with header `Type=header.RecvError`, `RemoteIndex=<Host A's localIndexId>`, and spoofs the source address to match Host B's known UDP endpoint (`hostinfo.GetRemote()` on Host A's side), per the packet shape built in `sendRecvError`: [6](#0-5) 
3. Attacker sends this packet to Host A.
4. On Host A, `readOutsidePackets` routes it directly to `handleRecvError` without decryption: [7](#0-6) 
5. `handleRecvError` finds the hostinfo via `QueryReverseIndex(h.RemoteIndex)`, sees the (spoofed) source address matches the recorded remote, and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)`, silently destroying the active tunnel state between A and B: [8](#0-7)

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
