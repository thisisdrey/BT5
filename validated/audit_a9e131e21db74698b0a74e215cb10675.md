### Title
Unsynchronized mutation of shared static TVM `JumpTable` causes a race condition between concurrent contract calls - ([File: actuator/src/main/java/org/tron/core/vm/OperationRegistry.java])

### Summary
`OperationRegistry` keeps two shared, mutable, static `JumpTable` instances — the "transaction" table (`tableMap.get(LATEST_VERSION)`) and the `CONSTANT_CALL_TABLE` — and exposes `prepareAndGetTable(boolean isConstantCall)`, which is invoked on *every* VM execution (`VMActuator.execute`) to re-apply configuration-dependent adjustments (`adjustTable` → `adjustMemOperations`/`adjustVoteWitness`/`adjustSelfdestruct`) directly onto the shared table via `JumpTable.set()`. `JumpTable.set()` mutates a plain (non-volatile, non-`AtomicReferenceArray`) `Operation[256]` array with no locking. [1](#0-0) [2](#0-1) 

### Finding Description
`VMActuator.execute()` calls `OperationRegistry.prepareAndGetTable(isConstantCall)` on the shared table for every contract call (both real transactions and constant/`eth_call`-style calls), then hands the returned table into `VM.play(program, table)`: [3](#0-2) 

`prepareAndGetTable` does not create a per-call copy of the table; it fetches the single shared static instance and mutates it in place:
```
public static JumpTable prepareAndGetTable(boolean isConstantCall) {
  JumpTable table = getTable(isConstantCall);
  adjustTable(table);   // mutates the shared instance via table.set(...)
  return table;
}
``` [4](#0-3) 

`table.set()` simply overwrites an array slot with no synchronization: `table[op.getOpcode()] = op;`. [5](#0-4) 

Any thread reachable by an unprivileged, anonymous client can trigger this path: contract calls submitted as broadcast transactions are executed via `RuntimeImpl.execute` → `VMActuator`, and constant calls (`triggerConstantContract`, JSON-RPC `eth_call`/`eth_estimateGas`, `EstimateEnergyServlet`) execute concurrently on the node's HTTP/gRPC/JSON-RPC request-handling threads, each calling `prepareAndGetTable(true)` against the same `CONSTANT_CALL_TABLE`. [6](#0-5) 

Because multiple contract-invoking requests (constant calls from many simultaneous API clients, or a constant call racing with the single block-application thread executing real transactions) can invoke `adjustTable`/`table.set` on the same table object concurrently, the read (`table.get(op)` inside `VM.play`) and the write (`table.set(...)`) are unsynchronized: one thread can observe a `JumpTable` in a state that mixes operations adjusted under old and new VMConfig values, or (depending on JIT/memory model behavior for plain array writes without a memory barrier) can observe stale values that were not yet published across threads. The energy-cost/action pairs for `MLOAD/MSTORE/MSTORE8`, `VOTEWITNESS`, and `SUICIDE` are all replaced in place by `adjustTable` based on live `VMConfig` flags (which flip at hard-fork boundaries), so a race window exists precisely around configuration changes and every single execution re-touches the shared table.

### Impact Explanation
The impact is scoped to TVM opcode dispatch/energy metering — an in-scope target per the report categories ("TVM opcodes, precompiles and energy metering"). A data race on the shared jump table can cause:
- A contract execution to observe an inconsistent/torn `Operation` for an opcode (mismatched cost function vs. action) during the narrow window while another thread is mid-`adjustTable`, potentially under- or over-charging energy for that opcode in one specific execution.
- Non-deterministic execution results across nodes if the race manifests differently depending on request timing/thread scheduling on different nodes, which is a correctness/consensus concern for a blockchain (nodes must produce identical execution results for the same transaction).

This is a genuine, unsynchronized shared-mutable-state bug analogous to the reported Deis Workflow Manager race condition (CWE-362), reachable purely by ordinary users issuing concurrent contract calls (broadcast transactions and/or constant calls via public APIs) without any special privilege.

### Likelihood Explanation
Likelihood is constrained by two factors that keep it at Medium rather than higher:
1. The race window is narrow — `adjustTable` runs on every call, but most of its component `adjust*` calls are idempotent no-ops unless a `VMConfig` flag actually changed since the last call (this could not be fully confirmed for `adjustMemOperations`/`adjustVoteWitness`/`adjustSelfdestruct`, since their implementations were not located in the available index — see caveat below).
2. Exploitation requires either (a) many concurrent constant-call API requests hitting the node simultaneously, which is plausible since public JSON-RPC/HTTP endpoints for `triggerConstantContract`/`eth_call`/`estimateEnergy` are typically served by a multi-threaded servlet/gRPC pool, or (b) a race between a constant call thread and the single block-application thread, timed around a fork-activation boundary.

Because ordinary unprivileged users can freely and repeatedly invoke constant calls concurrently (no fee, no signature required for constant calls in many deployments), the actor-controlled trigger frequency is high, which raises likelihood above a purely theoretical race.

### Recommendation
- Make `JumpTable`'s backing array access memory-safe under concurrent read/write, e.g. by using `AtomicReferenceArray<Operation>` or `volatile Operation[] table` with copy-on-write semantics for `set()`.
- Avoid re-adjusting the shared table on every call; instead detect a configuration-version change (e.g., versioned/generation counter) and only then perform the adjustment behind a lock, or precompute/cache the adjusted tables per-configuration-version.
- Alternatively, give each call thread a defensively-copied `JumpTable` (or the specific adjusted `Operation` objects) instead of mutating and returning a globally shared instance.

### Proof of Concept
Conceptual PoC (concurrency-timing dependent, cannot be deterministically demonstrated without a live multi-threaded harness):
1. Run two threads: Thread A repeatedly calls `triggerConstantContract` (or `eth_call`) against a contract that uses `MLOAD`/`MSTORE`/`VOTEWITNESS`/`SUICIDE` opcodes, driving `OperationRegistry.prepareAndGetTable(true)` → `adjustTable(CONSTANT_CALL_TABLE)` on every call.
2. Thread B flips relevant `VMConfig` flags (e.g., `allowHigherLimitForMaxCpuTimeOfOneTx`, `allowEnergyAdjustment`, `allowTvmOsaka`, `allowTvmSelfdestructRestriction`) at the same time a hard fork would toggle them, while Thread A's VM execution concurrently reads `table.get(op)` inside `VM.play`.
3. Observe (via energy-cost assertions similar to `OperationRegistryTest`/`VoteWitnessCost3Test`, which already document that mutating the shared table changes cost/action pairs in place) that under concurrent load the energy charged for an opcode in a given execution does not match the flag state that was authoritative for that transaction, demonstrating the shared, unsynchronized mutable table is unsafe for concurrent execution. [7](#0-6) 

**Caveat:** I could not locate the full bodies of `adjustMemOperations`, `adjustVoteWitness`, and `adjustSelfdestruct` within the indexed content (they were referenced but their definitions were not returned by search), so I cannot conclusively state how frequently they actually perform a `table.set()` write versus short-circuiting when nothing changed. This affects the precise likelihood assessment; a Devin session with full repository access would be needed to inspect these methods directly and confirm exact write frequency and whether any incidental synchronization (e.g., `synchronized` blocks) exists that the search did not surface.
