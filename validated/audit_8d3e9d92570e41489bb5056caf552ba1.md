### Title
Possible bypass of "future capacity must not decrease" egroup safety check via `supply-collateral-add` - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`collateral-add` in `v0-4-market.clar` contains a critical guard that blocks adding a new collateral asset type if doing so would move the user into a worse egroup (lower LTV) that reduces borrowing capacity while they carry debt [1](#0-0) . This guard is gated behind `(asserts! (is-eq contract-caller tx-sender) ERR-AUTHORIZATION)` [2](#0-1) , which is designed to block a contract-mediated call from reaching this function directly with attacker-controlled semantics. However, `supply-collateral-add` internally calls `collateral-add` as part of a single top-level user transaction (deposit-then-pledge) [3](#0-2) .

### Finding Description
The report's bug class is "symmetric operation pair where a safety/limiting mechanism is enforced on one path but not on another path that achieves the same state transition." Here, the safety mechanism is the "future capacity must not decrease" egroup check, enforced only inside the standalone `collateral-add` entry point when `is-new-collateral` is true and the user already has debt [4](#0-3) . The composite flow `supply-collateral-add` (deposit underlying → mint ztoken → call `collateral-add`) reaches the exact same state-mutating primitive (`market-vault.collateral-add`, which flips the position mask bit for a new asset) [5](#0-4) . Because `collateral-add`'s "new-collateral" branch is nested inside a `contract-caller`/`tx-sender` re-entry check, if the internal call from `supply-collateral-add` changes `contract-caller` semantics relative to the top-level caller (I could not fully verify this in Clarity's `contract-call?` semantics for this specific pattern within the available time), the capacity check could either be silently skipped or evaluated against stale state, letting a user with debt add a small amount of a new, more-favorable-egroup-triggering collateral type through the composite entry point.

### Impact Explanation
If confirmed, bypassing the "capacity must not decrease" check allows a borrower to force a mask/egroup transition into a state where the position's health check (`is-healthy`) uses a more permissive LTV pairing before the corresponding future-mask validation catches it, potentially permitting new debt to exceed the correct future-egroup LTV limits. This maps to the in-scope **Critical** impact of protocol insolvency (bad debt accrual beyond intended LTV bounds) or theft of user/protocol funds through under-collateralized borrowing.

### Likelihood Explanation
Low-to-moderate confidence. This requires an unprivileged user with an existing debt position to call `supply-collateral-add` for a new asset type they don't currently hold as collateral, and it depends on unverified internal call semantics of `contract-call?`/`contract-caller` propagation between `supply-collateral-add` and `collateral-add` in this codebase.

### Recommendation
Refactor the capacity-preservation check ("future capacity must not decrease") into a shared internal function that is invoked identically by both `collateral-add` and `supply-collateral-add` (and any other path that can add a new collateral-asset bit to the position mask), rather than relying on `contract-caller`/`tx-sender` equality as an implicit single-entry-point gate.

### Proof of Concept
Not fully constructible without confirming Clarity `contract-caller` propagation semantics for nested `contract-call?` invocations in this specific repo version — this would need to be validated with a Devin session that can run the Clarinet test suite in `local-testing/` to confirm whether `supply-collateral-add`'s internal call to `collateral-add` executes with `contract-caller` equal to the original tx-sender (in which case no bug exists) or not.

**Caveat:** I was unable to fully verify this finding due to reaching my tool-call limit before reading `supply-collateral-add`'s full body and confirming Clarity's exact `contract-caller` semantics for this nested-call pattern. This should be treated as a hypothesis requiring further verification, not a confirmed vulnerability. If the internal call preserves `contract-caller` == `tx-sender` correctly (the standard Clarity behavior for `contract-call?` from within the same transaction), the check would trigger properly, and this analog would not hold.
