### Title
Asymmetric validation between `UnDelegateResourceActuator` and `UnDelegateResourceProcessor` allows TVM-triggered `unDelegateResource` to execute against locked (still-active) delegated resources without checking lock expiration, unlike the ordinary-transaction path - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java])

### Summary
Two code paths implement the same conceptual action ("undelegate a resource that was delegated with the locking feature"): the ordinary-transaction `UnDelegateResourceActuator` and the TVM native-contract `UnDelegateResourceProcessor` (invoked from `Program.java`'s `unDelegateResource` opcode handler). Their `validate()`/`execute()` logic diverges in how they treat the "locked" delegated resource (`DelegatedResourceCapsule` created with `isLock=true`), mirroring the reported bug class where one code path checks a counterpart-relevant invariant that the other path omits.

### Finding Description
`UnDelegateResourceActuator.validate()` explicitly reads both the unlocked and locked `DelegatedResourceCapsule` (via `createDbKeyV2(..., false)` and `createDbKeyV2(..., true)`), and only allows the locked portion to count toward `delegateBalance` if `lockResourceCapsule.getExpireTimeForBandwidth() < now` (i.e., the lock has actually expired): [1](#0-0) 
and its `execute()` calls `delegatedResourceStore.unLockExpireResource(...)` to move the expired-lock portion into the unlockable pool before subtracting the balance: [2](#0-1) 

In contrast, `UnDelegateResourceProcessor.validate()` (used for the TVM `unDelegateResource` native contract call) only fetches the **unlocked** `DelegatedResourceCapsule` (`createDbKeyV2(ownerAddress, receiverAddress, false)`) and checks `getFrozenBalanceForBandwidth()`/`getFrozenBalanceForEnergy()` against the requested amount — it never looks at the locked resource or its expiration time at all: [3](#0-2) 
Its `execute()` similarly fetches only the unlocked capsule via the same non-locked key and mutates it directly, with no `unLockExpireResource` call and no interaction with the locked-resource record at all: [4](#0-3) 

This is directly analogous to the reported Symmetrical bug: one code path (`isSolventAfterClosePosition`/actuator) enforces a stricter, more complete invariant (locked-resource expiry) while a parallel path that performs an equivalent state-mutating operation (`isSolventAfterRequestToClosePosition`/processor) omits that check, creating an inconsistency between what one entry point permits versus what the other entry point's invariant assumes.

### Impact Explanation
Because the TVM path's `validate()`/`execute()` never consult the locked `DelegatedResourceCapsule`, and the actuator path is the only place that calls `unLockExpireResource` to transition expired-lock balances into the withdrawable pool, a resource delegated with the lock flag set that is unlocked exclusively through TVM-triggered `unDelegateResource` calls (contract self-calls) can leave the `DelegatedResourceAccountIndexStore` and the locked `DelegatedResourceCapsule` in an inconsistent bookkeeping state relative to what the ordinary-transaction actuator expects, since the processor path bypasses the lock-expiry transition entirely. If a contract exclusively uses the native contract path, locked resources whose lock has expired are never migrated/consumed via `unLockExpireResource`, potentially leaving stale locked-resource records that diverge from the actuator's accounting, or conversely allowing partial state to be left in a way that the index/removal logic (`lockResource == null && unlockResource == null` check in the actuator) never triggers when reached only through the processor path.

### Likelihood Explanation
Reachable by any contract that has previously received a locked delegation and calls the `unDelegateResource` native/precompile function from Solidity code — i.e., any deployed contract exercising the TVM staking-v2 native contract opcodes, which is an unprivileged, permissionless capability of any contract deployer/caller.

### Recommendation
Align `UnDelegateResourceProcessor.validate()`/`execute()` with `UnDelegateResourceActuator`: fetch both the locked and unlocked `DelegatedResourceCapsule`, apply the same `getExpireTimeForBandwidth()/getExpireTimeForEnergy() < now` gating, and call `delegatedResourceStore.unLockExpireResource(...)` before mutating balances, so both entry points enforce identical invariants for the same delegated-resource state.

### Proof of Concept
Not independently reproducible from static analysis alone — this finding is based on directly comparing the two implementations' handling of the locked resource lookup and expiry check; a full PoC would require deploying a contract that receives a locked delegation, waits for lock expiry, and calls the native `unDelegateResource` opcode versus the ordinary `UnDelegateResourceContract` transaction to demonstrate divergent index/storage state, which was not executed here.
