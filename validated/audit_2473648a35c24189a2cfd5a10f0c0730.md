## Analysis

The reported bug class is "hardcoded slippage control [without a user-configurable minimum-received parameter], causing users' funds to be extracted/locked at unfavorable prices when the pool state shifts between quote and execution."

In java-tron's on-chain Bancor-style TRX/TRC10 AMM ("Exchange"), this same bug class is reproducible on `ExchangeWithdrawContract`.

### Contrast with `ExchangeTransactionContract` (correctly protected)

The trade path already includes a user-supplied `expected` field acting as a slippage/minimum-output guard, checked in `ExchangeTransactionActuator`: [1](#0-0) 

### Missing protection on `ExchangeWithdrawContract` (the analog)

`ExchangeWithdrawContract` has no equivalent user-supplied minimum/expected field at all — only `owner_address`, `exchange_id`, `token_id`, and `quant`: [2](#0-1) 

The withdraw actuator computes the counter-asset amount (`anotherTokenQuant`) purely from the *current* on-chain pool ratio at the moment of validation/execution, with no way for the exchange creator to cap the acceptable output or abort if the ratio has moved unfavorably: [3](#0-2) 

The only numeric guard present is a hardcoded 0.01% (`0.0001`) rounding-precision tolerance used to detect a mismatch between the `BigDecimal` HALF_UP estimate and the truncating `BigInteger`/`BigDecimal` division actually applied — it is not a slippage/price-protection mechanism and is not configurable by the caller or operator: [4](#0-3) [5](#0-4) 

`ExchangeWithdrawContract` is only restricted to the exchange's `creatorAddress`, but any unprivileged account can become a creator by broadcasting an `ExchangeCreateContract` transaction, so this path is reachable by any transaction broadcaster: [6](#0-5) 

### Title
Missing user-configurable slippage/minimum-output protection in `ExchangeWithdrawActuator` allows liquidity withdrawals at an attacker-manipulated pool ratio - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawContract`, used to remove liquidity from java-tron's on-chain TRX/TRC10 Bancor-style exchange, carries no `expected`/minimum-output field. Unlike `ExchangeTransactionContract`, which lets the caller bound the trade outcome via `contract.getExpected()`, the withdraw path computes `anotherTokenQuant` strictly from whatever pool ratio (`firstTokenBalance`/`secondTokenBalance`) exists at the moment the transaction executes, with only a hardcoded, non-configurable 0.01% rounding-precision check that has nothing to do with economic slippage.

### Finding Description
`ExchangeCapsule` reserves (`firstTokenBalance`, `secondTokenBalance`) can be changed by any other account submitting `ExchangeTransactionContract` trades against the same `exchange_id` before an `ExchangeWithdrawContract` transaction lands. Because `doValidate()`/`execute()` in `ExchangeWithdrawActuator` only recompute `anotherTokenQuant` off the reserves as read at execution time — with no bound supplied by the withdrawer — a withdraw transaction that was signed expecting a certain pool ratio can be executed against a drastically different, attacker-shifted ratio, transferring far less value than the creator intended. The only slippage-adjacent guard present, the 0.0001 rounding-tolerance check, is a fixed, hardcoded constant unrelated to price protection and cannot be tuned by the creator or operator (mirroring the reported ERC5095 pattern of an inflexible, hardcoded numeric guard standing in for real slippage control).

### Impact Explanation
An exchange creator withdrawing liquidity has no mechanism to guarantee a minimum amount of the counter-asset, unlike traders using `ExchangeTransactionContract`. A single attacker (or bot) monitoring the mempool can submit a large trade that skews the reserve ratio just before the creator's withdraw transaction is packed into the same or an adjacent block, causing the creator to receive substantially less value than intended for the liquidity they remove — a fund-loss condition for an unprivileged, ordinary transaction broadcaster (the exchange creator).

### Likelihood Explanation
Any account can become an exchange creator via `ExchangeCreateContract`, and any account can submit `ExchangeTransactionContract` trades against the pool. No special privilege, SR/witness role, or off-chain trust is required — an attacker only needs to observe pending `ExchangeWithdrawContract` transactions and front-run them with a trade, which is straightforward given java-tron's public mempool/API.

### Recommendation
Add an `expected`/minimum-output field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.getExpected()`), and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` so the withdrawer can specify the minimum acceptable amount of the counter-asset before the transaction is rejected.

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` transaction from a creator withdrawing `tokenID` from `exchange_id`.
2. Attacker broadcasts an `ExchangeTransactionContract` selling a large amount of the counter token into the same pool, shifting `firstTokenBalance`/`secondTokenBalance` sharply, and ensures it is included in the same or immediately preceding block (see reserve mutation in `ExchangeTransactionActuator.execute` at [7](#0-6) ).
3. The pending `ExchangeWithdrawContract` then executes against the skewed reserves in `ExchangeWithdrawActuator.execute` (lines 63-90 above), paying the creator a far smaller `anotherTokenQuant` than intended, with no field available to have rejected the unfavorable outcome.
4. Attacker can optionally reverse their trade in a follow-up transaction to restore the pool ratio and pocket the difference.
