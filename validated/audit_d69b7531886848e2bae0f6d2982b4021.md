### Title
Stale postponed receipts survive `DeleteAccount`/`CreateAccount` and execute privileged self-actions against a recreated account - (`runtime/runtime/src/actions.rs`, `core/store/src/utils/mod.rs`)

### Summary
`remove_account` (invoked from `action_delete_account`) only removes the `Account`, `ContractCode`, access keys, gas keys, and contract data for a deleted account; it never removes `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount` entries keyed to that account. `action_create_account` likewise does not clear any of this state when the same `account_id` is recreated. A self-directed action receipt (`predecessor_id == receiver_id == VICTIM`) that was postponed (waiting on an unresolved `input_data_id`) before the account was deleted therefore survives the deletion and later fires against whatever account now occupies that `account_id`.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` [1](#0-0)  which only clears `Account`, `ContractCode`, access keys/gas-key nonces, and contract data [2](#0-1) . It does not touch `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` trie rows, which are keyed by `(receiver_id, receipt_id)` / `(receiver_id, data_id)` — i.e. by the account_id string, independent of any particular account "incarnation" [3](#0-2) .

When an incoming action receipt has unresolved `input_data_ids`, `process_action_receipt` stores it as a postponed receipt keyed by `receiver_id`/`receipt_id` and records a `PostponedReceiptId` link per missing `data_id` [4](#0-3) . Later, when the missing `Data` receipt arrives, `process_receipt` looks it up purely by `receiver_id`/`data_id` and, once the pending count reaches zero, fetches and executes the stored postponed receipt via `apply_action_receipt` [5](#0-4) . Nothing in this path checks whether the account was deleted and recreated in the meantime.

Inside `apply_action_receipt`, `actor_id` is (re)initialized from `receipt.predecessor_id()` [6](#0-5) , and `check_actor_permissions` only compares `actor_id == account_id` as a string equality for privileged actions such as `AddKey`/`DeployContract`/`DeleteKey` [7](#0-6) . Since the postponed receipt's `predecessor_id` is `VICTIM` itself (a self-directed promise), this check passes trivially regardless of which "generation" of the `VICTIM` account currently exists in state, and `action_create_account` (`runtime/runtime/src/actions.rs:167-210`) never invalidates or purges the previous incarnation's postponed data.

Exploit flow (all steps performed by an ordinary signed-transaction sender who owns `VICTIM`):
1. Attacker (owner of `VICTIM`) deploys a contract and calls it to produce a self-directed promise (`predecessor_id == receiver_id == VICTIM`) with an `AddKey(attacker_public_key)` action, batched behind an unresolved `input_data_id` (e.g. `promise_then` chained on a cross-shard/slow call whose data receipt has not yet arrived). This gets stored as a `PostponedReceipt` under `VICTIM`.
2. Attacker submits a self-`DeleteAccount(VICTIM)` (passes `check_actor_permissions`'s self-actor and zero-stake checks) — this refunds balance and calls `remove_account`, but leaves the `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` rows untouched.
3. `VICTIM` account_id is later recreated (e.g., by a different party who has legitimate reason to (re)create that account id) with a brand-new access key via `CreateAccount`.
4. The pending data dependency finally resolves (attacker can arrange or simply wait for it), causing `process_receipt`'s `Data` branch to fetch and execute the stale postponed receipt.
5. The stale receipt's `AddKey` action runs with `actor_id == account_id == VICTIM` (satisfying `check_actor_permissions`) against the *new* account, granting the attacker's chosen public key full access — without the new owner ever having signed anything.

### Impact Explanation
This is an authorization escalation across account "incarnations": a receipt authorized under the old owner/contract executes privileged actions (`AddKey`, `DeployContract`, `DeleteKey`, etc.) against a subsequently, independently created account sharing the same `account_id`, without any signature or consent from whoever controls the new account. This matches the "authorization escalation across accounts" bounty category and can result in full-access-key theft / account takeover of the recreated account.

### Likelihood Explanation
The prerequisite state (a self-directed postponed receipt with an unresolved dependency, followed by self-`DeleteAccount`) is fully constructible by an ordinary account owner with a deployed wasm contract — no validator, RPC operator, or other privileged access is required. The account-id reuse window (delete → recreate under the same name) is a normal, expected occurrence in NEAR (e.g., sub-accounts, re-registration flows), so the precondition is realistic and repeatable at low cost (gas fees only).

### Recommendation
When deleting an account, also purge any state rooted at that `account_id` that could later be replayed against a different incarnation: iterate and remove `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, and `ReceivedData` trie rows for the account inside `remove_account` (or a dedicated cleanup called from `action_delete_account`), mirroring the existing access-key/gas-key/contract-data removal loops. Alternatively/additionally, tag postponed receipts with a generation counter incremented on `CreateAccount` and reject/drop postponed receipts whose generation doesn't match the current account's generation before executing them.

### Proof of Concept
Runtime integration test (in `runtime/runtime/src/tests/apply.rs` style, following the existing `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code` pattern):
1. Set up `child` account owned by signer A; deploy a contract.
2. Submit a receipt on `child` with `input_data_ids: [pending_data_id]` and `actions: [AddKey(attacker_public_key)]`, `predecessor_id = receiver_id = child` — verify via state that it is stored as a `PostponedReceipt`/`PostponedReceiptId`.
3. Apply a `DeleteAccount(beneficiary)` receipt on `child` (self-actor, zero stake) — assert the account is gone but assert (via direct trie lookup, or via `get_postponed_receipt`) that the `PostponedReceipt` row for `child`/that `receipt_id` still exists.
4. Apply `CreateAccount` on `child` with a different signer B's key (simulating a new, unrelated owner).
5. Deliver the pending `Data` receipt for `pending_data_id` targeting `child`.
6. Assert the postponed `AddKey` receipt executes successfully (`ExecutionStatus::SuccessValue`/`SuccessReceiptId`) and that `attacker_public_key` is now a full-access key on the recreated `child` account (query via `get_access_key`), despite signer B never having authorized it.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
