### Title
Unbounded array allocation via attacker-controlled length fields in precompiled sign-validation contracts causes OutOfMemoryError / node crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE describes a buffer overflow in Shotcut/MLT where an attacker-supplied width/height value (unconnected to the actual data being processed) drives an oversized memory allocation, crashing the process. The direct analog in java-tron is in the `BatchValidateSign` and `ValidateMultiSign` precompiled contracts (TVM addresses `0x9` and `0xa`), where an internal "array length" field is parsed out of attacker-supplied calldata and used directly to size a Java array, while the energy charged for the call is computed from the *physical* calldata length rather than from this internal length field.

### Finding Description
`extractBytesArray`, `extractBytes32Array`, and `extractSigArray` read a length value directly from the ABI-encoded calldata and use it, unchecked, to allocate a Java array: [1](#0-0) 

`len = words[offset].intValueSafe()` is fully attacker-controlled — it need not match the actual size or shape of the surrounding calldata. This value is then used as `new byte[len][]`.

These helpers are invoked from `BatchValidateSign.doExecute` and `ValidateMultiSign.execute`: [2](#0-1) [3](#0-2) 

A bound check (`sigArraySize > MAX_SIZE` / `addrArraySize > MAX_SIZE`) exists, but it is only applied when the feature flag `VMConfig.allowTvmSelfdestructRestriction()` is active — this is a TIP/hard-fork flag toggled by chain governance (`ProposalUtil`/`DynamicPropertiesStore`), not an always-on guard. When that flag is not active, `extractBytesArray`/`extractBytes32Array`/`extractSigArray` are called with the unchecked, attacker-supplied `len`.

Critically, the energy charged for calling these precompiles is computed purely from the *physical byte length* of the supplied calldata: [4](#0-3) [5](#0-4) 

This is entirely decoupled from the internal length word parsed inside `doExecute`/`execute`. An attacker can therefore submit a small, cheap calldata blob (a few hundred bytes, minimal energy) that encodes a huge declared array length (e.g. close to `Integer.MAX_VALUE`) at the position read by `words[offset].intValueSafe()`. The node then attempts `new byte[huge][]`/`new byte[huge]`, which can throw `OutOfMemoryError` well before the (irrelevant) MAX_SIZE check on `signatures.length` is ever reached — exactly the CVE's pattern of an oversized, attacker-supplied dimension driving an unconstrained allocation that is disconnected from the "real" cost/size of the input.

### Impact Explanation
A successful trigger causes an `OutOfMemoryError` inside TVM execution triggered from `callToPrecompiledAddress`: [6](#0-5) 

Depending on how the JVM and surrounding executor threads handle the OOM (especially since `BatchValidateSign` submits work to a shared `ExecutorService` thread pool that is reused across all sign-verification calls on the node), this can degrade or crash the node process, or corrupt the shared worker pool used for every subsequent `BatchValidateSign` invocation, resulting in denial of service for block processing on that node. This is reachable by any unprivileged account that can broadcast a `TriggerSmartContract` transaction calling these fixed precompile addresses — no special permission required.

### Likelihood Explanation
High, if `allowTvmSelfdestructRestriction` is not activated in the target deployment: an attacker only needs to craft standard ABI-encoded calldata with a manipulated header length field. The cost is a single cheap transaction; the resulting allocation attempt is essentially unbounded (up to `Integer.MAX_VALUE` array slots, i.e. ~16GB for `byte[][]` object array overhead alone on 64-bit JVMs). I could not confirm from the available code the on-chain activation status of `allowTvmSelfdestructRestriction` (it is a committee-gated proposal flag), so likelihood is conditional on that proposal not yet being active on the target network.

### Recommendation
Make the length bound check (`MAX_SIZE`) in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` unconditional (not gated behind `allowTvmSelfdestructRestriction`), and/or validate any length word parsed from calldata against the actual physical calldata size before using it to size an array, independent of feature-flag activation state.

### Proof of Concept
1. Craft calldata for `batchvalidatesign(bytes32,bytes[],address[])` (address `0x...9`) where the physical calldata is short (a few hundred bytes, keeping `getEnergyForData` cheap), but the 32-byte word at the offset used for the `bytes[]` length header (read via `words[words[1].intValueSafe() / WORD_SIZE].intValueSafe()`) is set to a very large value (e.g. `0x7FFFFFFF`).
2. Deploy a trivial contract that performs a `STATICCALL`/`CALL` to address `0x9` with this calldata, or invoke it directly as a top-level `TriggerSmartContract`.
3. On a node where `allowTvmSelfdestructRestriction` is not active, `extractBytesArray`/`extractSigArray` will attempt `new byte[0x7FFFFFFF][]`, causing an `OutOfMemoryError` during precompile execution.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

      byte[] hash = words[0].getData();

        int sigArraySize = words[words[1].intValueSafe() / WORD_SIZE].intValueSafe();
        int addrArraySize = words[words[2].intValueSafe() / WORD_SIZE].intValueSafe();
        if (sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE) {
          return Pair.of(true, DATA_FALSE);
        }
      }

          extractSigArray(words, words[1].intValueSafe() / WORD_SIZE, data) :
          extractBytesArray(words, words[1].intValueSafe() / WORD_SIZE, data);

          words, words[2].intValueSafe() / WORD_SIZE);
