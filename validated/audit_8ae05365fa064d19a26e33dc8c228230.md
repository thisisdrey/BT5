### Title
Out-of-bounds array access in permission-operations bitmap check via unvalidated ContractType value - (File: actuator/src/main/java/org/tron/core/utils/TransactionUtil.java)

### Summary
`TransactionUtil.checkPermissionOperations()` computes `contractType / 8` from `contract.getTypeValue()` and uses it directly to index into the 32-byte `operations` `ByteString` via `operations.byteAt(...)`, without validating that `contractType` falls within the legal `ContractType` enum range (0-59). This mirrors the FreeRDP CVE-2020-11095 pattern of indexing a fixed-size array with an unchecked, attacker-influenced type/order field.

### Finding Description
`Contract.getTypeValue()` returns the raw protobuf enum field value as an `int32`, independent of whether it matches a declared `ContractType` constant (unlike `getType()`, which maps unknown values to `UNRECOGNIZED`). Because a transaction's `Contract.type` field is fully attacker-controlled, `getTypeValue()` can be an arbitrarily large (or negative, depending on wire encoding) integer. `checkPermissionOperations` then computes:
```java
int contractType = contract.getTypeValue();
boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
``` [2](#0-1) 
The `operations` `ByteString` is fixed at 32 bytes (checked by `operations.size() != 32`), so any `contractType` value where `contractType / 8 >= 32` or negative will cause `byteAt()` to throw `IndexOutOfBoundsException`, an unhandled runtime exception at this call site.

### Impact Explanation
This method is invoked from `TransactionUtil.getTransactionSignWeight()` [3](#0-2) , which is reachable via the multi-signature weight-check gRPC/HTTP API (`GetTransactionSignWeight`), a query path that any unauthenticated API client can invoke by submitting a crafted transaction with a permission_id != 0 and an out-of-range contract type value. An uncaught `IndexOutOfBoundsException` here is only caught generically as `Exception ex` in the surrounding try/catch [4](#0-3) , so within this specific method the impact is contained to an error response rather than a crash. However, the same unguarded arithmetic pattern also exists in `AccountPermissionUpdateActuator`/tests operating on this bitmap by contract-type ordinal, indicating a broader latent risk if `checkPermissionOperations`-style logic is invoked elsewhere without an equivalent surrounding catch-all (e.g., in actuator validate/execute paths during block application, which could cause a node crash/halt on a broadcast transaction).

### Likelihood Explanation
High: constructing a `Transaction.Contract` with a spoofed out-of-range `type` field is trivial for any transaction sender, and does not require special privileges beyond crafting the protobuf transaction manually rather than through SDK helpers that always set valid enum values.

### Recommendation
Validate `contractType` against the valid enum range (`0 <= contractType/8 < operations.size()`) before indexing, returning `false`/throwing a `PermissionException` for out-of-range values, mirroring proper bounds checking rather than relying on downstream catch blocks.

### Proof of Concept
Construct a `Transaction` whose `raw_data.contract[0].type` field is manually set (via raw protobuf bytes, bypassing the enum) to a value such as `1000` (well beyond the declared `ContractType` range up to 59), with `permission_id` set to a non-zero active permission id on an account that owns such a permission. Submitting this transaction to the `GetTransactionSignWeight` API triggers `checkPermissionOperations`, computing `1000/8 = 125`, which exceeds the 32-byte `operations` array and throws `IndexOutOfBoundsException` inside `getTransactionSignWeight`.
