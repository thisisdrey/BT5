### Title
Missing slippage/minimum-output protection in `ExchangeInjectContract` and `ExchangeWithdrawContract` - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeTransactionActuator` explicitly protects users from unfavorable pricing by requiring an `expected` (minimum-output) field that is validated against the pool ratio at execution time [1](#0-0) . `ExchangeInjectActuator` and `ExchangeWithdrawActuator`, however, compute the counter-asset amount (`anotherTokenQuant`) purely from the exchange pool's current `firstTokenBalance`/`secondTokenBalance` ratio at block-application time, with no caller-supplied bound to protect against that ratio having moved since the transaction was signed and broadcast.

### Finding Description
`ExchangeInjectContract` and `ExchangeWithdrawContract` only carry `owner_address`, `exchange_id`, `token_id`, and `quant` — no `expected`/minimum field, unlike `ExchangeTransactionContract` which added `expected` for exactly this purpose [2](#0-1) .

In `ExchangeInjectActuator.doValidate()`/`execute()`, `anotherTokenQuant` is derived from the live pool ratio (`firstTokenBalance`/`secondTokenBalance`) read from the `ExchangeCapsule` at the moment the transaction is validated/executed in the block, not at signing time [3](#0-2) . There is no check comparing `anotherTokenQuant` to any minimum or maximum the caller specified — the only checks are that it is `> 0` and within the exchange balance limit [4](#0-3) .

Similarly, `ExchangeWithdrawActuator` computes `anotherTokenQuant` from the live pool ratio with only a rounding-precision check ("Not precise enough"), not a slippage/minimum bound supplied by the caller [5](#0-4) .

Because any account can broadcast an `ExchangeTransactionContract` trade against the same exchange pool (this is exactly the same mutable-state class of dependency called out in the report — a value derived from state that can be moved by another actor's transaction before the target transaction is applied), an attacker can shift the pool ratio between the time the exchange creator signs their `ExchangeInject`/`ExchangeWithdraw` transaction and the time it is applied in `Manager`'s block-application path, causing the creator to inject or withdraw at a ratio worse than intended, with no on-chain enforcement of a minimum acceptable counter-asset amount.

### Impact Explanation
The exchange creator (an ordinary, unprivileged account that becomes "creator" merely by issuing `ExchangeCreateContract`) can have the counter-asset amount for an inject/withdraw operation manipulated below their expectation by any other unprivileged account trading against the same pool beforehand, causing an unbacked loss of value for the creator with no protective parameter to prevent it — matching the "theft/permanent loss of funds due to unbounded state-dependent computation" impact class from the rules.

### Likelihood Explanation
Any account can call `ExchangeTransactionContract` against the same pool without restriction; sequencing transactions in the same or an adjacent block to move the ratio unfavorably before a known/pending `ExchangeInject`/`ExchangeWithdraw` transaction is fully within the capability of an ordinary transaction broadcaster, requiring no special privilege.

### Recommendation
Add an `expected`/minimum (and optionally maximum) counter-asset amount field to `ExchangeInjectContract` and `ExchangeWithdrawContract`, mirroring the existing `expected` field and check already present in `ExchangeTransactionActuator` [1](#0-0) , and validate the computed `anotherTokenQuant` against it in both `ExchangeInjectActuator` and `ExchangeWithdrawActuator` before executing the balance changes.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` transaction (or `ExchangeWithdrawContract`) from the exchange creator in the mempool.
2. Attacker broadcasts an `ExchangeTransactionContract` trade against the same `exchange_id` designed to shift `firstTokenBalance`/`secondTokenBalance` unfavorably, and ensures it is applied before the creator's transaction (e.g., same block ordering, or fee/priority manipulation).
3. When the creator's `ExchangeInjectContract`/`ExchangeWithdrawContract` is applied, `anotherTokenQuant` is recomputed from the now-shifted ratio in `ExchangeInjectActuator.execute()`/`ExchangeWithdrawActuator.execute()` [6](#0-5) , giving the creator a worse counter-asset amount than intended, with no on-chain check to reject the trade.
