## Finding Validated

I traced the code path and confirmed the described defect exists exactly as specified.

### Title
`do_ft_withdraw`'s `near_withdraw`-failure panic permanently burns `storage_deposit` while `ft_resolve_withdraw` only refunds `amount` - (File: `contracts/defuse/src/contract/tokens/nep141/withdraw.rs`)

### Summary
When `FtWithdraw.storage_deposit` is set and the chained `near_withdraw` call on `wnear_id` fails, `do_ft_withdraw`'s `require!(promise_result_checked_void(0).is_ok(), "near_withdraw failed")` panics, producing a failed promise for the whole chain. `ft_resolve_withdraw` then observes only a single failed promise result and refunds `amount`, but has no way to know about or refund `storage_deposit`, which was already burned from `token_balances`/`total_supplies` synchronously in `withdraw()`.

### Finding Description
The broken binding: `debited (amount + storage_deposit)` == `delivered (0)` + `recredited (amount only)`, i.e. `storage_deposit` vanishes from both sides.

- `internal_ft_withdraw` synchronously debits `withdraw.amount` (of `withdraw.token`) **and** `storage_deposit.as_yoctonear()` (of `wnear_id`) via `self.withdraw(...)`, which calls `owner.token_balances.sub(...)` and `total_supplies.sub(...)` — an irreversible burn committed in the same receipt as `execute_intents`: [1](#0-0) [2](#0-1) 
- The promise chain is `near_withdraw().then(do_ft_withdraw(..)).then(ft_resolve_withdraw(..))`: [3](#0-2) 
- `do_ft_withdraw` panics via `require!` if the `near_withdraw` promise failed, **before** ever scheduling `ft_transfer`/`ft_transfer_call`: [4](#0-3) 
- Because `do_ft_withdraw` panics instead of returning a `Promise`, the receipt it represents completes as Failed, so `ft_resolve_withdraw`'s `promise_result_checked_void(0)` (for `is_call == false`, i.e. `msg: None`) reads a failed result, sets `used = 0`, and refunds only `amount`: [5](#0-4) 

`storage_deposit` is never referenced anywhere in `ft_resolve_withdraw`, so there is no code path that can recredit it once `near_withdraw` fails. Meanwhile the real wNEAR NEP-141 tokens backing that `storage_deposit` were never actually unwrapped (since `near_withdraw` itself failed) and remain custodied by the Defuse contract's account on the real `wnear` contract, orphaned from any user's ledger balance — an unrecoverable loss from the signer's perspective, and `total_supplies` no longer matches actual custody, violating conservation.

No existing guard prevents this: `withdraw()` only checks the owner's own `token_balances`, not whether Defuse's actual on-chain wNEAR reserve is sufficient to cover the promised `near_withdraw`; `require!` in `do_ft_withdraw` has no compensating recovery logic.

The attacker's own signed batch (a single `MultiPayload` with an initial `FtWithdraw` unwrapping most of Defuse's real wNEAR reserve via `native_withdraw`/`FtWithdraw` without `storage_deposit`, followed by their `FtWithdraw{storage_deposit: Some(_), msg: None}`) can deterministically cause the second `near_withdraw` receipt (both directed at the same `wnear_id` receiver, in creation order) to fail due to insufficient real wNEAR balance on Defuse's account, triggering the panic described.

### Impact Explanation
The `storage_deposit` NEAR amount debited from the caller's internal wNEAR balance is permanently and irrecoverably lost — burned from `total_supplies`/`token_balances` with no refund path, while the corresponding real wNEAR tokens remain stuck, unindexed, in Defuse's custody. This matches the Critical category "user funds permanently frozen" and "a refund or resolver credit that does not match what failed to settle." The loss lands on whoever signs the `FtWithdraw{storage_deposit}` intent when the `near_withdraw` leg fails — repeatable per attempt/account for any `storage_deposit` amount, and independently reachable by any user hitting a `near_withdraw` failure (not exclusively attacker-induced).

### Likelihood Explanation
Requires only unprivileged access: sign and submit a `MultiPayload` batch containing (a) sufficient existing internal wNEAR balance to withdraw most of Defuse's real wNEAR reserve in one leg, and (b) a second `FtWithdraw{storage_deposit: Some(_), msg: None}` in the same batch, relying on receipt-ordering to the same `wnear_id` receiver. No DAO role, relayer key, or victim key needed — fully attacker/self-controlled and reproducible in a sandbox.

### Recommendation
Track `storage_deposit` amount inside `ft_resolve_withdraw`'s callback state (or pass it through) and, upon `near_withdraw`/`do_ft_withdraw` failure, refund `storage_deposit` back to the owner's wNEAR balance symmetrically to how `amount` is refunded. Alternatively, restructure so that `do_ft_withdraw`'s `require!` failure returns a value/`Result` instead of panicking, allowing the outer resolver to see and refund both debited legs distinctly.
