### Title
Legacy (non-hardened) `ExchangeCapsule.transaction` path allows a single trade to drive pool token balances negative, socializing the loss onto all other exchange participants - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeCapsule.transaction()` computes AMM-style trade outputs via a Bancor bonding-curve formula and only validates that the resulting pool balances remain non-negative when the `hardenedCalc` flag is true. When the chain parameter `allowHardenExchangeCalculation` is disabled, this check is skipped entirely, so the legacy floating-point math path can silently push one side of the pool negative, corrupting the shared collateral that backs every other holder's exchange balance.

### Finding Description
`ExchangeCapsule.transaction()` uses `ExchangeProcessor` (floating point `double`/`Math.pow` Bancor relay math) to compute `buyTokenQuant` for a trade against a two-token pool that is jointly funded by the exchange creator and any subsequent `ExchangeInjectActuator` callers. [1](#0-0) 

The post-trade sanity check that the new balances are not negative is gated behind `hardenedCalc`: [2](#0-1) 

Whether `hardenedCalc` is `true` is controlled purely by the chain-wide dynamic property `allowHardenExchangeCalculation`, exposed through `AbstractExchangeActuator.allowHarden()`: [3](#0-2) 

`ExchangeTransactionActuator` (reachable by any unprivileged, signed `ExchangeTransactionContract` transaction) calls `exchangeCapsule.transaction(...)` in both `validate()` and `execute()` using this same flag, and if the flag is off, applies neither `addExact`/`subtractExact` overflow protection nor the negative-balance guard: [4](#0-3) [5](#0-4) 

`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` rely on `double` precision and `Math.pow`, which can introduce rounding/precision drift especially for extreme ratios of `quant`/`newBalance`: [6](#0-5) 

Because in the legacy (non-hardened) path there is no verification that `buyTokenQuant` does not exceed the actual `buyTokenBalance` in the pool, a trade whose computed `buyTokenQuant` (due to floating-point error) exceeds the real balance will drive the corresponding `newFirstTokenBalance`/`newSecondTokenBalance` negative and persist that corrupted state to the store via `Commons.putExchangeCapsule`. This is directly analogous to the FlatMoney bug class: the pool's balances are a shared resource contributed by multiple parties (creator via `ExchangeCreateActuator`, and any injector via `ExchangeInjectActuator`), and an accounting flaw in a single trade's settlement can consume value that belongs to other participants, instead of that shortfall being isolated to the trader who caused it or rejected outright.

### Impact Explanation
A corrupted, negative (or effectively negative once represented as an underflowed value after subsequent operations) token balance in a shared `Exchange`/`ExchangeV2` pool means the collateral backing every other participant's claim against that pool (their proportional right to withdraw or trade against `firstTokenBalance`/`secondTokenBalance`) is destroyed or misallocated. Subsequent legitimate `ExchangeWithdrawActuator` or `ExchangeTransactionActuator` calls by unrelated accounts will operate against corrupted state, causing them to receive incorrect amounts or fail — the loss caused by one trader's transaction is socialized onto all other holders of that exchange pool, matching the "losses of some eat into the margins/funds of others" bug class from the reference report. This is an unbacked-balance / loss-of-funds class issue reachable by any account submitting a normal, signed `ExchangeTransactionContract`.

### Likelihood Explanation
Exploitability depends on whether `allowHardenExchangeCalculation` is disabled for the target chain/network at the time of the transaction — this is a governance-controlled dynamic property (via `ProposalUtil`/`Wallet`), not a caller-supplied parameter, so the caller cannot toggle it themselves. On chains/period where it is disabled (e.g., prior to the corresponding proposal being activated, which the presence of `SafeExchangeProcessor` and the explicit hardening feature strongly suggests was the historical/default state), any account can construct trade quantities designed to maximize floating-point drift in the Bancor formula and attempt to extract more than the pool's true balance in a single `ExchangeTransactionContract`.

### Recommendation
Remove the `hardenedCalc` gate around the balance-sufficiency check in `ExchangeCapsule.transaction()` so that `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` is always validated and rejected regardless of the `allowHardenExchangeCalculation` setting, and prefer deterministic fixed-point arithmetic (as already implemented in `SafeExchangeProcessor`) unconditionally rather than only when the proposal is active.

### Proof of Concept
1. Deploy/operate on a network state where `DynamicPropertiesStore.allowHardenExchangeCalculation()` returns `false` (legacy path).
2. Create an exchange pool with token balances near precision-sensitive ratios via `ExchangeCreateActuator`/`ExchangeInjectActuator`.
3. Submit an `ExchangeTransactionContract` with a `quant`/`expected` chosen so that `ExchangeProcessor.exchange()`'s floating point computation of `buyTokenQuant` (lines 17-39 of `ExchangeProcessor.java`) rounds up beyond the true `buyTokenBalance`.
4. Because `ExchangeTransactionActuator.doValidate()`/`execute()` call `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` with `allowHarden()==false`, the negative-balance check at `ExchangeCapsule.java:160` is skipped, and the resulting negative/corrupted balance is persisted via `Commons.putExchangeCapsule`.
5. Any subsequent trader or the exchange creator attempting to trade/withdraw against this pool will observe balances inconsistent with the tokens actually deposited, demonstrating the loss has been transferred from the exploiting trade onto other pool participants.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
