### Title
Active-permission signers can rewrite Owner permission via `AccountPermissionUpdateContract`, bypassing the Owner/Active privilege hierarchy - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The Discord bot bug lets a moderator with a single limited permission bit act against targets who should be protected by role hierarchy, because the hierarchy check that should compare the *actor's* rank to the target is missing and only the bot's own rank is effectively enforced. java-tron has an analogous two-layer-authorization gap in its multi-sig permission model: `AccountPermissionUpdateActuator.checkPermission()` validates the `operations` bitmap of an `Active` permission against `DynamicPropertiesStore.getAvailableContractType()`, which — unlike `ACTIVE_DEFAULT_OPERATIONS` — does **not** exclude `AccountPermissionUpdateContract` (type 46). This allows an `Active` permission (a lower-tier, lower-threshold key set) to be granted rights over the very operation that rewrites the account's `Owner` permission, letting a holder of a narrow, low-weight Active key seize full Owner-level control of the account.

### Finding Description
`checkPermission()` in `AccountPermissionUpdateActuator.java` validates each bit of an `Active` permission's `operations` field against `dynamicStore.getAvailableContractType()`: [1](#0-0) 

The stored `AVAILABLE_CONTRACT_TYPE` bitmap includes `AccountPermissionUpdateContract` (type 46) as a valid bit — confirmed by the test that reconstructs it and excludes only `UNRECOGNIZED` and `UpdateBrokerageContract`: [2](#0-1) 

In contrast, `ACTIVE_DEFAULT_OPERATIONS` — used only when auto-generating a default Active permission — explicitly excludes `AccountPermissionUpdateContract`: [3](#0-2) 

This shows the intent was that `Active` permissions should not normally be able to invoke `AccountPermissionUpdateContract`, yet `checkPermission()` enforces against the wrong bitmap (`AVAILABLE_CONTRACT_TYPE` instead of `ACTIVE_DEFAULT_OPERATIONS`), so nothing prevents an `Active` permission from having bit 46 set.

Once such an `Active` permission exists, signature/permission verification for a transaction only checks that the signer's weight under that specific permission meets its own threshold — it never compares the permission tier being used against the operation's required tier: [4](#0-3) [5](#0-4) 

Finally, `AccountPermissionUpdateActuator.execute()` blindly applies whatever `Owner`/`Witness`/`Active` permissions are in the contract to the target account, with no additional check that the transaction's signing permission tier ("rank") is authorized to modify `Owner`: [6](#0-5) 

This is directly analogous to the Discord bug class: a lower-ranked authority (Active permission, meant only for scoped operations) is allowed — due to a missing/incorrect tier check — to perform an operation (`AccountPermissionUpdateContract`) that should be reserved for the higher-ranked authority (Owner permission), completely overriding the intended hierarchy.

### Impact Explanation
Any account owner who (knowingly or via a maliciously crafted dApp/wallet prompt) creates or edits an `Active` permission whose `operations` bitmap includes bit 46 grants that Active key set the power to fully rewrite the account's `Owner` permission with an arbitrary low threshold, using only the Active permission's own (typically much weaker) weight/threshold. This results in a concrete unauthorized account takeover: the attacker can lock out the legitimate owner, drain TRX/TRC10/TRC20 balances, redirect votes/frozen resources, and permanently control the account — i.e., theft and permanent loss of control of funds.

### Likelihood Explanation
Exploitation requires the target account to already have an `Active` permission with bit 46 set in its operations. This can happen if an owner is tricked (e.g. by a malicious signing request from a dApp/exchange integration) into signing an `AccountPermissionUpdateContract` that defines such an Active permission, since `checkPermission()` will accept it without complaint (unlike the stricter `ACTIVE_DEFAULT_OPERATIONS` mask). This is a realistic supply-chain/social-engineering vector similar to how the Discord bug required only that the bot outrank the target and the moderator hold one permission bit — no additional protections exist once the permission is set.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, explicitly forbid `AccountPermissionUpdateContract` (and any other Owner-tier-only contract types) from being settable in an `Active` permission's `operations` bitmap — i.e., validate against `ACTIVE_DEFAULT_OPERATIONS` (or an explicit denylist) rather than `AVAILABLE_CONTRACT_TYPE`. Additionally, consider adding a defense-in-depth check in `execute()`/`validateSignature()` that rejects `AccountPermissionUpdateContract` transactions signed under any `permissionId != 0` (i.e., require Owner-level signing to modify permissions at all).

### Proof of Concept
1. Owner account `A` (Owner permission: key `O`, threshold 1) is induced to sign an `AccountPermissionUpdateContract` (permissionId=0, using Owner key `O`) that defines an `Active` permission (id=2, threshold=1, one key `K`, weight=1) whose `operations` bitmap has bit 46 (`AccountPermissionUpdateContract`) set. `AccountPermissionUpdateActuator.validate()`'s `checkPermission()` accepts this because bit 46 is present in `AVAILABLE_CONTRACT_TYPE`. `execute()` stores this Active permission on `A`.
2. Attacker, holding only private key `K`, crafts a new `AccountPermissionUpdateContract` for account `A` (permissionId=2) that sets `Owner` permission to a key fully controlled by the attacker with threshold 1, and signs it with `K`.
3. `TransactionCapsule.validateSignature()` → `checkPermission(2, activePermission, contract)` → `checkPermissionOperations` returns true (bit 46 set); `checkWeight` returns weight 1 ≥ threshold 1 → transaction accepted for broadcast.
4. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)`, overwriting `A`'s Owner permission with the attacker's key.
5. Attacker now solely controls account `A`'s Owner permission and can drain all balances/resources, permanently locking out the original owner.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
