### Title
Meta-transaction (`DelegateAction`) relayer funds can be redirected to the malicious sender via the deposit-refund `predecessor_id` routing - (File: `runtime/runtime/src/actions.rs`)

### Summary
In NEAR's meta-transaction flow (NEP-366), a relayer submits a `DelegateAction`/`DelegateV2` on behalf of a `sender_id` and prepays all gas and attached deposits for the inner actions. If an inner action fails on the receiver's shard, the standard protocol rule sends the deposit refund to the **predecessor** of the failed receipt — but `apply_delegate_action` sets that predecessor to `sender_id` (the untrusted delegator), not to the relayer who actually paid the deposit. This lets a malicious `sender_id` craft a delegate action with a large attached deposit to an inner action that is guaranteed to fail, and collect the refund itself, at the relayer's expense — mirroring the code-423n4 Rubicon pattern where a permissioned-but-untrusted actor (`strategist`) used an unchecked address parameter (`_stratUtil`/refund target) to redirect funds that were not theirs.

### Finding Description
`apply_delegate_action` builds the inner receipt with `predecessor_id: sender_id.clone()` while the relayer only supplies gas/deposit as `signer_id`/fee payer: [2](#0-1) 

The accompanying code comment explicitly states the consequence: [3](#0-2) 

The refund path itself (`refund_unspent_gas_and_deposits`) always sends the deposit refund to `receipt.balance_refund_receiver()`, which defaults to `predecessor_id()` when `refund_to` is unset: [4](#0-3) [5](#0-4) 

This is also independently documented in the architecture docs as a known caveat of the meta-transaction design: [6](#0-5) 

### Impact Explanation
An ordinary, unprivileged account (the `sender_id`/delegator in a meta-transaction) can cause a relayer to pay a deposit that is refunded back to the delegator instead of the relayer whenever the delegated inner action predictably fails (e.g., calling a non-existent method, or a receiver contract enforcing a condition the delegator knows will fail). This is a concrete theft of funds from the relayer, reachable purely through the standard `Action::Delegate`/`Action::DelegateV2` transaction path available to any signer — no special/privileged role is required on the attacker's side, only an unwary relayer that accepts the meta-transaction and forwards it. It is directly analogous to the reported bug class: an unprivileged/semi-trusted actor exploiting unchecked routing of a refund/beneficiary to redirect funds that belong to someone else.

### Likelihood Explanation
This does not require any protocol bug beyond what is documented; it is a design consequence of always routing balance refunds to `predecessor_id`, which for delegate actions is fixed to the delegator rather than the fee-paying relayer. Because the mechanic is already documented (`docs/architecture/how/meta-tx.md`) as something "relayer implementations must be aware of," it is a known, currently-unmitigated-at-protocol-level footgun rather than a novel discovery, and any relayer service that naively forwards meta-transactions without simulating them first is exposed. Likelihood is Medium: it requires a relayer that does not pre-validate/simulate delegate actions before paying for them.

### Recommendation
Since this behavior is called out as "by design" in the current codebase and mitigated only by advising relayers to validate delegate actions before submission, no protocol code change is strictly required; however, protocol designers should consider either (a) making `refund_to` default to the relayer (fee payer) rather than the delegator for `Delegate`/`DelegateV2` inner-action deposit refunds, or (b) providing an explicit "refund to signer" option relayers can opt into on `DelegateAction`, and clearly surfacing simulation-based validation as a mandatory relayer requirement, consistent with the C4 recommendation of not letting an untrusted party who does not own the funds control where they are redirected on failure.

### Proof of Concept
1. Malicious account `alice` (delegator) crafts a `DelegateAction` with `receiver_id = "bob"` and one inner `FunctionCall` action carrying a large `deposit` and calling a method on `bob` guaranteed to fail (e.g., a non-existent method, mirroring `test_transfer_64len_hex`-style tests already in the codebase but engineered to fail).
2. `alice` gets a relayer to wrap this in a transaction (`Action::Delegate`), where the relayer is `signer_id`/fee payer and prepays the attached deposit and gas, per `apply_delegate_action`. [7](#0-6) 
3. The relayer submits the transaction; the inner receipt to `bob` is created with `predecessor_id = alice`.
4. Because the call to `bob` fails as designed, `refund_unspent_gas_and_deposits` issues a balance-refund receipt to `receipt.balance_refund_receiver()`, which resolves to `alice` (the `predecessor_id`), not the relayer who actually funded the deposit. [4](#0-3) 
5. `alice` receives back the deposit that the relayer paid for, net theft of relayer funds equal to the attached deposit.

```rust
pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }

    // Generate a new receipt from DelegateAction.
    let new_receipt = Receipt::V0(ReceiptV0 {
        predecessor_id: sender_id.clone(),
        receiver_id: delegate_action.receiver_id().clone(),
        receipt_id: CryptoHash::default(),

        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: action_receipt.signer_id().clone(),
            signer_public_key: action_receipt.signer_public_key().clone(),
            gas_price: action_receipt.gas_price(),
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: delegate_action.get_actions(),
        }),
    });

    // Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas.
    // If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction.
    // Gas is refunded to the signer, this is Relayer.
    // Some contracts refund the deposit. Usually they refund the deposit to the predecessor and this is sender_id/Sender from DelegateAction.
    // Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit.
```

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
