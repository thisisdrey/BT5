## Title
Maker order can lose entire remaining balance for free due to integer-truncation-to-zero in `MarketSellAssetActuator.matchSingleOrder` "exact match" branch - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes the amount a maker receives from a fill using integer multiply-then-divide (`MarketUtils.multiplyAndDivide`). Two of the three branches explicitly guard against the division truncating to `0` (returning tokens to the order owner instead of silently zeroing them out), but the "taker == maker" (exact match) branch does not. This lets an attacker construct or select a fill that exactly matches a maker's remaining sell quantity while the reward computation rounds down to `0`, so the maker's whole remaining sell-token balance is consumed (set to `0`) while the maker receives nothing in return.

### Finding Description
In `matchSingleOrder`, `takerBuyTokenQuantityRemain` is computed and, if it equals `0`, the code protects the taker by returning their sell tokens: [1](#0-0) 

When `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` (the "taker == maker" exact-match case), `makerBuyTokenQuantityReceive` is computed via the same truncating division but with **no zero-check**, and the maker's remaining balance is immediately zeroed regardless of the result: [2](#0-1) 

Contrast this with the "taker > maker" branch, which uses the exact same `multiplyAndDivide` call but explicitly checks for a zero result and returns the sell tokens back to the maker instead of consuming them for nothing: [3](#0-2) 

The truncating helper itself performs plain integer division with no minimum-output enforcement: [4](#0-3) 

If a maker order has a price ratio where `sellTokenQuantity >> buyTokenQuantity` (e.g. sell 1,000,000 of token A for 1 of token B) and its remaining sell quantity `R` satisfies `R * buyTokenQuantity < sellTokenQuantity`, then any taker fill that lands exactly on `R` (an attacker can engineer this, since the taker's own `sellTokenQuantity`/`buyTokenQuantity` are fully attacker-controlled and the maker order's remaining quantity is publicly readable from the order-book stores) produces `makerBuyTokenQuantityReceive == 0`, yet `makerOrderCapsule.setSellTokenQuantityRemain(0)` still executes, permanently zeroing the maker's remaining sell-side balance with no compensation.

### Impact Explanation
This is a concrete unbacked-value / theft path reachable purely by broadcasting `MarketSellAssetContract` transactions (an unprivileged order-placer action). A maker who places (or has an existing) large-ratio order can have their entire remaining sell-token balance permanently taken by an attacker's taker order for zero payment, while the taker's tokens are unaffected (their own zero-fill case is protected). This satisfies "concrete unauthorized... theft or permanent freezing of funds" — funds are transferred out of the maker's order with no corresponding value returned.

### Likelihood Explanation
Reachable from a single transaction pair: one `MarketSellAssetContract` transaction to create/maintain the maker order (or use of any existing on-chain maker order with a skewed price ratio) and a second `MarketSellAssetContract` transaction from the attacker crafted to exactly match the maker's remaining quantity. All required state (order book prices/remaining quantities) is queryable via the public market stores. No special privileges, and the developer's own defensive pattern in the sibling branch shows the fix was known but not applied consistently.

### Recommendation
In the "taker == maker" branch of `matchSingleOrder`, add the same guard used in the "taker > maker" branch: if `makerBuyTokenQuantityReceive == 0`, return the maker's remaining sell tokens via `returnSellTokenRemain`/`setSellTokenQuantityReturn` instead of consuming them, before proceeding to zero out `makerOrderCapsule`'s remaining quantity.

### Proof of Concept
1. Attacker/maker places order O1: sell 1,000,000 of token A, buy 1 of token B (`MarketSellAssetContract`). This enters the order book via `createAndSaveOrder`/matching logic.
2. Through prior partial fills (or directly, if O1 is untouched and a first partial fill brings `sellTokenQuantityRemain` down to some `R` where `R * 1 < 1,000,000`, e.g. `R = 999,999`), O1's remaining sell quantity becomes `R`.
3. Attacker submits a second order O2 (`MarketSellAssetContract`) selling token B for token A, choosing `sellTokenQuantity`/`buyTokenQuantity` such that in `matchSingleOrder`, `takerBuyTokenQuantityRemain = multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity, makerBuyQuantity)` exactly equals `R` (attacker fully controls the inputs and can query O1's live state to compute this).
4. Execution enters the `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` branch: `makerBuyTokenQuantityReceive = multiplyAndDivide(R, 1, 1_000_000) = 0`, `makerOrderCapsule.setSellTokenQuantityRemain(0)` executes unconditionally, and `takerBuyTokenQuantityReceive = R` is credited to the attacker via `addTrxOrToken`.
5. Result: attacker receives `R` tokens of A for free; O1's owner's remaining `R` tokens of A are gone with `0` tokens of B credited back.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
