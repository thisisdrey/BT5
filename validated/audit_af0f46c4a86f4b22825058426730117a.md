### Title
Unbounded array allocation from attacker-controlled length in TVM precompiled contract signature/array extraction helpers - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` read a length value directly out of caller-supplied calldata (`words[offset].intValueSafe()`) and immediately allocate a two-dimensional array (`new byte[len][]`) sized by that untrusted value, with no upper bound check on `len` itself before allocation. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Each of these three helpers only guards against `offset` being past the end of the `words` array, not against `len` (the claimed element count) being arbitrarily large:
```
private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];   // <-- allocation size fully attacker-controlled
  ...
}
``` [4](#0-3) 

`len` comes from `words[offset].intValueSafe()`, i.e. a raw 32-byte word taken from the calldata passed to the precompiled-contract call (`data`/`words` are derived from the TVM `CALL` input to these precompiles, per the surrounding class which implements Sapling/signature-verification/multi-sig precompiled contracts, e.g. `BatchValidateSign`/`ValidateMultiSign`, exercised in `BatchValidateSignContractTest` and `ValidateMultiSignContractTest`). Because `intValueSafe()` only caps the value to fit in a Java `int` (i.e., it can still return values close to `Integer.MAX_VALUE`) rather than validating it against the actual size of `words`/`data`, a single crafted call can request an array of hundreds of millions or billions of `byte[]` references. This is directly analogous to the CVE-2018-12698 pattern: an attacker-controlled length feeds an `XNEWVEC`/`new T[len]`-style allocation without a sanity bound, causing uncontrolled memory consumption (OOM) before any subsequent bounds-checking code (which would otherwise reject the malformed input) ever runs.

Because this is a bare array-of-references allocation (`new byte[len][]`), even before any inner `byte[]` payloads are populated, the JVM must allocate `len` reference slots (8 bytes each on a 64-bit JVM, or 4 with compressed oops) contiguously, which can itself trigger `OutOfMemoryError` or heavy GC pressure well before the subsequent loop would throw an `ArrayIndexOutOfBoundsException` for the malformed structure.

### Impact Explanation
An `OutOfMemoryError` thrown inside precompiled-contract execution during TVM opcode processing can crash or destabilize the executing full node / SR node process, since `OutOfMemoryError` is not consistently guaranteed to be cleanly caught and converted into a reverted transaction in all call paths of the VM interpreter (the codebase does have an explicit `OutOfMemoryException` wrapper used for TVM `new` opcode OOMs, as seen in `EnergyWhenAssertStyleTest.outOfMemTest`, but that is for the interpreter's own memory-limited allocations, not necessarily for this unrelated precompiled-contract array-length parsing path). A crashed or unstable node from a single low-cost transaction is a node-crash/halt class issue, matching the validation criteria (node crash or halt). [5](#0-4) 

### Likelihood Explanation
Reachability requires only that an unprivileged account submit or trigger a smart-contract call that invokes one of the precompiled contracts using `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (e.g. `BatchValidateSign`) with crafted calldata containing a huge length word in the position read as `len`. This requires no special privilege beyond deploying/calling a contract or invoking the precompile address directly via a transaction, which any broadcaster can do.

### Recommendation
Add an explicit upper bound check on `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocating the array — validating that `len` is non-negative and consistent with the actual size of the supplied `data`/`words` (e.g., `len <= (words.length - offset - 1)` or a similarly derived maximum based on `data.length`), rejecting the call (returning an empty/failure result) rather than performing the allocation when the claimed count cannot possibly be backed by the actual input size.

### Proof of Concept
Note: I was unable to fully trace the exact call sites and energy-charging order for `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (e.g., whether `getEnergyForData` for the specific precompiled contract charges energy proportional to `len` *before* this allocation happens) within the available tool budget, so the exploitability of this as an unmitigated OOM (versus one that is already bounded by an adequate pre-allocation energy check) is not fully confirmed. A concrete PoC would need to: (1) identify which precompiled-contract address dispatches to one of these three helper methods (candidates: `BatchValidateSign`/`ValidateMultiSign` per `BatchValidateSignContractTest.java` and `ValidateMultiSignContractTest.java`), (2) confirm the corresponding `getEnergyForData` does not already bound `len` against `feeLimit`/energy prior to calling the helper, and (3) craft a `TriggerSmartContract` call to that precompiled address with a data word at the expected `offset` set to a very large value (e.g. `0x7fffffff`) to trigger the oversized `new byte[len][]` allocation. Given the incomplete verification of the energy-gating order, this should be treated as a **candidate** finding requiring confirmation of the call path and energy accounting before being treated as fully validated.
