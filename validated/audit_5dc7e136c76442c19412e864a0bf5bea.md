## Title
Runtime recomputes prepaid exec/send fees from the *current* `RuntimeConfig` at refund time instead of the config that was active when the gas was purchased, causing incorrect gas refunds across a protocol upgrade — (File: `runtime/runtime/src/lib.rs`)

## Summary
This is the same bug class as the SYMM-IO finding: a fee-dependent amount is paid using a config value at time T1, but the refund of that amount is recomputed using the config value read live at time T2. If the config changed between T1 and T2, the refund no longer matches what was actually charged.

## Finding Description
When a transaction is converted into a receipt, `calculate_tx_cost` (`runtime/runtime/src/config.rs:417-500`) computes `gas_remaining` — the Gas amount to be purchased for prepaid function-call gas plus `total_prepaid_send_fees`/`total_prepaid_exec_fees` plus the wrapping receipt's exec fee — using the `RuntimeConfig` in effect at the *signer shard's current block* (`config.rs:470-477`). This Gas amount is converted to a Balance at `receipt_gas_price` and permanently deducted from the signer's account. Only the resulting Gas quantities and the receipt's `gas_price` are attached to the outgoing `ActionReceipt`; the fee-table values used to derive `prepaid_exec_gas` are **not stored** anywhere in the receipt.

Later, when this receipt is actually executed by `apply_action_receipt`, `refund_unspent_gas_and_deposits` (`runtime/runtime/src/lib.rs:1230-1365`) **recomputes** `prepaid_gas`/`prepaid_exec_gas` from scratch: [1](#0-0) 

using `config: &RuntimeConfig`, which is `apply_state.config` for the chunk currently being applied — i.e., the config for the protocol version active *at execution time*, not the config that was active when the fee was originally charged at conversion time: [2](#0-1) 

If a receipt sits in the delayed-receipts queue (congestion control can hold receipts for many blocks) or crosses shards and its execution happens after an epoch boundary where the protocol version — and therefore per-action `Fee` values in `RuntimeFeesConfig.action_fees` — changed, then `prepaid_exec_gas` recomputed at refund time will differ from the Gas amount that was actually purchased at conversion time. `gross_gas_refund = prepaid_gas + prepaid_exec_gas − gas_burnt/gas_used` will consequently be wrong: [3](#0-2) 

This exactly mirrors the reported bug: `LibQuote.getTradingFee` was called both at charge time and refund time reading the *live* `symbol.tradingFee`, so a fee change between the two calls produced a wrong refund. Here, `total_prepaid_exec_fees`/`total_prepaid_send_fees` are called both at charge time (`config.rs:417-477`) and at refund time (`lib.rs:1242-1248`) against the *live* `RuntimeConfig`, rather than against a value fixed/stored at charge time.

## Impact Explanation
- If per-action exec/send fees **increase** between conversion and execution, the refund computation treats the receipt as having purchased more gas than it actually did, producing an **over-refund** — new tokens effectively refunded that were never taken from the signer's balance, i.e. inflation / minting beyond what accounting invariants expect.
- If fees **decrease**, the refund computation under-counts the originally purchased gas, producing an **under-refund** — permanent loss of user funds (the difference is silently burned/retained rather than refunded).

Both outcomes violate the invariants documented for this refund path (`docs/RuntimeSpec/Refunds.md:42`, `protocol-model/spec/economics.md:96` — "Refund penalty ≤ refund" and burn/refund balancing), which assume the refund is computed consistently with the amount purchased.

## Likelihood Explanation
This requires no malicious actor — only:
1. A user submits an ordinary transaction whose receipt execution completes after a protocol-version-driven `RuntimeConfig` fee change (e.g., any `NN.yaml` diff altering `action_receipt_creation`, `action_create_account`, `action_function_call`, etc., such as the `AccountCostIncrease`/PV 85 fee changes noted in `core/parameters/res/runtime_configs/85.yaml`), and
2. The receipt is still in flight (delayed queue, cross-shard buffering, or congestion-throttled admission) when the epoch boundary crosses.

Because chunk/receipt processing spans multiple blocks and epochs under congestion, and protocol upgrades are a normal, expected, recurring event (not an attacker action), this is reachable through completely ordinary transaction flow. However, I was not able to fully verify from the indexed source how large a fee-table delta typically is between adjacent protocol versions, nor precisely bound how long a receipt can realistically remain queued across an epoch boundary in current mainnet operating conditions — that would require deeper investigation of the congestion-control code and empirical epoch-transition receipt backlog behavior, which is outside what I could confirm with the available index.

## Recommendation
Store the originally-purchased `prepaid_gas`/`prepaid_exec_gas` (or the resulting Balance amount) inside the `ActionReceipt` (or a receipt-associated side record) at the time the transaction is converted, and use that stored value in `refund_unspent_gas_and_deposits` instead of recomputing it from the possibly-different `RuntimeConfig` active at execution time. This mirrors the SYMM-IO fix of storing the fee actually paid rather than recomputing it from the live parameter at refund time.

## Proof of Concept
Conceptual sequence (I could not execute this against a live test harness given the available tools):
1. At block/epoch E (protocol version P1), Alice submits a `FunctionCall` transaction with a cross-shard receiver. `calculate_tx_cost` computes `prepaid_exec_gas` using P1's `action_fees` and deducts the corresponding balance from Alice's account (`runtime/runtime/src/config.rs:417-489`).
2. Due to congestion control, the resulting receipt is buffered/delayed rather than executed immediately (see `protocol-model/spec/runtime-execution.md:151-156`, "Delayed receipts").
3. Before the receipt is dequeued and applied, the network votes in protocol version P2 at an epoch boundary, and P2's `runtime_configs/*.yaml` diff changes one or more `ActionCosts` fee values used by `total_prepaid_exec_fees`.
4. The receipt is finally applied in a P2 chunk. `apply_action_receipt` calls `refund_unspent_gas_and_deposits` with `apply_state.config` = P2's config (`runtime/runtime/src/lib.rs:1006-1016`), recomputing `prepaid_exec_gas` with P2 fee values instead of the P1 values that were actually charged (`runtime/runtime/src/lib.rs:1241-1262`).
5. `gross_gas_refund` and the resulting `gas_balance_refund` sent back to Alice (`runtime/runtime/src/lib.rs:1346-1362`) diverge from the amount actually purchased, over- or under-refunding depending on the direction of the fee change.
