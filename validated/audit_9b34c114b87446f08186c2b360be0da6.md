## Why the Deadlock Is Real

The partitioner pre-computes cross-shard dependencies from static write hints on `AnalyzedTransaction`. If transaction T1 on Shard A has a write hint for key K, the partitioner registers K as a dependency for T2 on Shard B. Shard B initializes a `RemoteStateValue::waiting()` for K and blocks on `get_value()` when T2 reads it.

If T1 aborts (Move abort, out-of-gas, etc.):
- `on_transaction_committed` is called with T1's output (an empty or gas-only write set).
- `send_remote_update_for_success` iterates the write set — K is absent — so no `RemoteTxnWriteMsg` is sent.
- No abort notification path exists (`on_transaction_aborted` is absent from the trait).
- Shard B's thread waits forever on the `Condvar`.
- `rayon::scope` in `execute_transactions_with_dependencies` never completes.
- `execute_block` never returns, `send_execution_result` is never called, and the coordinator blocks waiting for results.

The `messages.rs` `Option<WriteOp>` field with its "None if aborted" comment proves the design intended an abort-notification path that was never implemented. [7](#0-6)

## Verdict

### Title
Cross-shard dependency never resolved on transaction abort — permanent executor deadlock — (`aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_client.rs`)

### Summary
`CrossShardCommitSender` implements `TransactionCommitHook` but only handles the success path. When a producing transaction aborts, no `RemoteTxnWriteMsg` is ever sent to the dependent shard. The dependent shard's thread blocks indefinitely on `RemoteStateValue::get_value()` with no timeout, deadlocking the entire block execution for any block containing such a cross-shard dependency.

### Finding Description
`TransactionCommitHook` exposes only `on_transaction_committed`; there is no `on_transaction_aborted`. [1](#0-0) 

`CrossShardCommitSender::on_transaction_committed` calls `send_remote_update_for_success`, which iterates `txn_output.write_set()`. An aborted transaction's write set does not contain the cross-shard key, so no message is dispatched. [3](#0-2) 

`CrossShardStateView::get_state_value` calls `RemoteStateValue::get_value()`, which spins on a `Condvar` with no timeout or cancellation path. [4](#0-3) 

The `RemoteTxnWrite::write_op` field is `Option<WriteOp>` with an explicit comment "None if the transaction is aborted," confirming the design intended an abort-notification path that was never wired up. [6](#0-5) 

### Impact Explanation
Any block routed through the sharded block executor that contains a cross-shard dependency where the producing transaction aborts will deadlock permanently. The `rayon::scope` in `execute_transactions_with_dependencies` never exits, `send_execution_result` is never called, and the coordinator hangs. This constitutes a material chain availability failure for all blocks containing such dependencies. [7](#0-6) 

### Likelihood Explanation
Any unprivileged user can submit a transaction that aborts (Move `abort`, out-of-gas, failed assertion). If the partitioner assigns that transaction to a shard with a dependent cross-shard edge — which is determined by static write hints — the deadlock is triggered. The attacker does not need privileged keys or validator access; a normal user transaction suffices.

### Recommendation
1. Add `fn on_transaction_aborted(&self, txn_idx: TxnIndex)` to `TransactionCommitHook`.
2. Implement it in `CrossShardCommitSender` to send `RemoteTxnWriteMsg` with `write_op: None` for every registered dependent edge of the aborted transaction.
3. In `CrossShardCommitReceiver::start`, handle the `None` write op by calling `set_value(None)` on the `RemoteStateValue`, unblocking the waiting thread.
4. Add a timeout to `RemoteStateValue::get_value()` as a defense-in-depth measure.
