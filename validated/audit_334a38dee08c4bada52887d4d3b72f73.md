### Title
Missing Slippage/Minimum-Output Protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` Enables Front-Running of Exchange Liquidity Operations - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java] / [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the counter-token amount (`anotherTokenQuant`) proportionally from the *current* `firstTokenBalance`/`secondTokenBalance` of the Bancor-style `Exchange` pair at execution time, exactly like the `_optimizeAmounts`/`_quote` pattern in the referenced report. Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced against `tokenExpected` in `ExchangeTransactionActuator.doValidate`, neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` expose any caller-supplied bound on the computed `anotherTokenQuant`. This makes both operations fully exposed to reserve manipulation performed via an ordinary, unprivileged `ExchangeTransactionContract` trade executed immediately before/after the inject/withdraw transaction.

### Finding Description
`ExchangeInjectActuator.execute`/`doValidate` derives `anotherTokenQuant` purely from the spot ratio of `firstTokenBalance`/`secondTokenBalance` read from the `ExchangeCapsule` at execution time: [1](#0-0) 

The `ExchangeInjectContract` protobuf message carries only `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no field allowing the caller to bound `anotherTokenQuant` (e.g. a `maxAnotherTokenQuant`): [2](#0-1) 

The same pattern applies to `ExchangeWithdrawActuator`, which computes `anotherTokenQuant` from the live pool ratio with only an internal rounding-precision check ("Not precise enough"), not a caller-supplied minimum bound: [3](#0-2) [4](#0-3) 

By contrast, `ExchangeTransactionActuator` — the trade path — does provide and enforce a slippage bound via `expected`: [5](#0-4) 

Because any account can freely call `ExchangeTransactionContract` to move `firstTokenBalance`/`secondTokenBalance` in either direction (subject only to `ExchangeBalanceLimit` and its own asset holdings), an attacker can transiently skew the pool ratio immediately before the creator's `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction is packed into the same block, causing the injected/withdrawn `anotherTokenQuant` to be computed against a manipulated ratio, and then reverse the skewing trade afterward. This is the direct analog of the report's `_optimizeAmounts`/`_quote` issue: a ratio-only slippage check with no protection against the underlying reserves being manipulated between quote time and execution time.

### Impact Explanation
An attacker who sandwiches the exchange creator's inject/withdraw transaction can force liquidity to be added/removed at a price that deviates from the creator's intended price, extracting value equal to the mispricing when the attacker closes out the sandwich trade. Because Tron transactions within the same block execute in a deterministic, attacker-controllable order relative to a pending transaction the attacker can observe (mempool/broadcast visibility), this constitutes a concrete value-extraction / theft-of-funds vector reachable by any unprivileged account issuing ordinary `ExchangeTransactionContract` and `ExchangeInjectContract`/`ExchangeWithdrawContract` transactions — no special privilege beyond being the exchange creator (for the injection side) or any trader (for the manipulation side) is required, and exchange creation itself is open to any account.

### Likelihood Explanation
Likelihood is limited by the precondition that `ExchangeInjectContract`/`ExchangeWithdrawContract` may only be sent by the exchange's `creatorAddress`: [6](#0-5) 
so the attacker cannot arbitrarily target any account, only accounts that are exchange creators actively managing liquidity. However, since exchange creation is permissionless and injection/withdrawal transactions are broadcast to the public mempool before confirmation, an attacker monitoring pending transactions can reliably front-run/back-run them with ordinary trade transactions, making exploitation practical whenever a creator performs one of these operations.

### Recommendation
Add caller-supplied bounds to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., `anotherTokenExpected`/min-max fields) analogous to the `expected` field already used in `ExchangeTransactionContract`, and enforce them in `ExchangeInjectActuator.doValidate`/`ExchangeWithdrawActuator.doValidate` before mutating balances, so that manipulated-ratio injections/withdrawals revert instead of executing at an attacker-controlled price.

### Proof of Concept
1. Exchange creator `C` holds an Exchange pair (TRX/TokenA) and broadcasts `ExchangeInjectContract{token_id=TRX, quant=Q}` intending to add liquidity at the current fair ratio.
2. Attacker `A` observes `C`'s pending transaction and broadcasts `ExchangeTransactionContract{token_id=TokenA, quant=X}` ordered immediately before it, skewing `firstTokenBalance`/`secondTokenBalance` (per `ExchangeCapsule.transaction`, `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java` lines 124-169).
3. `ExchangeInjectActuator.execute` computes `anotherTokenQuant` from the now-skewed balances (lines 71-83 of `ExchangeInjectActuator.java`), causing `C` to inject liquidity that "bakes in" the skewed ratio.
4. `A` broadcasts a second `ExchangeTransactionContract` reversing the initial trade; because the pool now holds `C`'s freshly injected liquidity at the skewed ratio, `A`'s reverse trade experiences reduced slippage compared to the initial skew, letting `A` extract value equal to the mispricing introduced in step 2, funded by `C`'s injected liquidity.
