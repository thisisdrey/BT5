### Title
Predictable, non-secret quarantine-directory prefix lets a caller-supplied `GitObjectDirectory` field impersonate another repository's in-flight quarantine — (File: `internal/git/localrepo/paths.go`)

### Summary
The bug class in the report is trusting a caller-supplied identity field (`sender`) instead of verifying real provenance. In Gitaly, the analogous trust failure is in how a repository's object-quarantine directory is "authenticated": ownership of a quarantine directory is decided purely by whether the caller-supplied `Repository.GitObjectDirectory` path has a prefix that is a deterministic, unsalted `SHA1` of the repository's own (attacker-controlled) `RelativePath` field — not by any capability, token, or randomness tied to the actual push/session that created the quarantine.

### Finding Description
`storage.QuarantineDirectoryPrefix` computes the "proof of ownership" for a quarantine directory as: [1](#0-0) 

This prefix is only a hash of the repository's `RelativePath` — a value that is itself part of the request and, for many repositories, is publicly knowable (project paths) or otherwise not secret. It contains no random nonce and no binding to the specific push/session/quarantine instance that created the directory.

`Repo.ObjectDirectoryPath` uses this prefix as the sole check that a supplied `GitObjectDirectory` "belongs" to the repository when the path isn't a normal in-repo path or a transaction-quarantine directory: [2](#0-1) 

Because the check is `strings.HasPrefix(absoluteObjectDirectoryPath, expectedQuarantinePrefix)` and `expectedQuarantinePrefix` is fully derivable by anyone who knows (or can compute) the target repository's relative path, an attacker who can issue a request specifying `Repository{RelativePath: <victim path>, GitObjectDirectory: "<storage>/tmp/quarantine-<sha1(victimRelPath)>-<guessed-suffix>"}` passes this "ownership" check even though they never legitimately created that quarantine.

This is compounded by `internal/gitaly/storage/storagemgr/middleware.go`, which treats the mere *presence* of a non-empty `GitObjectDirectory`/`GitAlternateObjectDirectories` field as proof the request is a trusted loop-back from Rails' access-check flow, and — for any accessor RPC — skips normal transactional snapshot handling and instead restores an attacker/Rails-supplied relative path directly from a header: [3](#0-2) [4](#0-3) 

The code's own comments acknowledge this heuristic is not a real trust boundary: *"This property is violated in tests which manually configure the object directory... This allows for circumventing the transaction management..."* (see comment block at lines 271–281 of `middleware.go`).

The legitimate use of the quarantine-directory naming scheme is documented in `doc/object_quarantine.md`, describing how Rails round-trips the object-directory information back to Gitaly without any additional secret: [5](#0-4) 

### Impact Explanation
An attacker who can reach Gitaly with a request carrying a `Repository` message with attacker-chosen `RelativePath` and `GitObjectDirectory` fields (the same class of caller as in the pre-receive/access-check loop-back path, i.e. an ordinary pushing user whose requests are proxied through this mechanism) can attempt to read another repository's in-flight quarantine directory — objects that a different push is staging but that have not yet passed `pre-receive` and been merged into the main object store. Because the "ownership" check is a predictable hash rather than a secret token, this is a quarantine/storage-path isolation bypass rather than a genuine authorization boundary: it allows disclosure of not-yet-accepted objects across repositories/pushes and, more generally, undermines the guarantee (stated in `doc/object_quarantine.md`) that quarantine directories are scoped to the repository that created them.

### Likelihood Explanation
Exploitation requires: (1) knowledge of the victim repository's relative path (frequently derivable — project paths for public/known projects, or hashed storage paths that are still deterministic and can be recomputed if the project ID/path is known), and (2) a race window while the victim's quarantine directory exists on disk during their `pre-receive`/access-check cycle, plus guessing/enumerating the random `tempdir` suffix component of the quarantine directory name (the prefix is fixed, but the full directory name includes a random suffix from `tempdir.NewWithPrefix`). This materially reduces — but does not eliminate — the attack surface, since only the prefix is predictable and the full path still needs the random suffix, which is not verified against a secret either but must be independently discovered (e.g., via directory listing under storage's temp dir if permissions allow, or via information leaks). Likelihood is therefore moderate: the security-relevant flaw (using a non-secret, attacker-computable value as an ownership check) is definite and reachable, but full exploitation depends on additional information leakage of the random suffix.

### Recommendation
Do not rely on a deterministic hash of the repository's relative path as an ownership proof for quarantine directories. Instead:
- Bind the quarantine ownership check to something unpredictable and issued only to the legitimate requester, e.g. a per-request random token embedded in the quarantine directory name and verified against server-side state instead of purely a hash of a caller-supplied field.
- In `internal/gitaly/storage/storagemgr/middleware.go`, do not treat "an accessor RPC has `GitObjectDirectory` set" as sufficient signal that the request is a legitimate Rails loop-back; tie this trust to an authenticated, request-scoped identifier (e.g. validated against the active transaction/partition state) rather than to the mere presence of a field the caller fully controls.
- Ensure `Repo.ObjectDirectoryPath` in `internal/git/localrepo/paths.go` cannot accept a caller-controlled `GitObjectDirectory`/`RelativePath` combination unless the quarantine directory is verifiably tied to the actual transaction/partition currently associated with the request context, closing the analog of the "sender == address(this)" self-authorization flaw.

### Proof of Concept
Conceptual PoC (concrete directory listing/suffix discovery not verified against a live deployment):
1. Attacker learns/derives victim repository's relative path `R_v` (e.g., known project path).
2. Attacker computes `prefix = "quarantine-" + hex(sha1(R_v)[:8]) + "-"` exactly as `storage.QuarantineDirectoryPrefix` does.
3. During a window where the victim is pushing (their `pre-receive` quarantine directory exists under the storage's temp dir with a name `prefix + <random-suffix>`), the attacker issues a Gitaly accessor RPC (e.g. `GetObjectDirectorySize`, or any RPC reachable via the Rails access-check loop-back path) with:
   - `Repository.RelativePath = R_v`
   - `Repository.GitObjectDirectory = "<tempdir-relative-path>/" + prefix + <guessed-or-leaked-suffix>`
4. `Repo.ObjectDirectoryPath` (`internal/git/localrepo/paths.go:53-75`) accepts the path because it matches `expectedQuarantinePrefix`, exposing the victim's staged, not-yet-committed objects to the attacker before the push has been vetted.

**Uncertainty note:** I could not confirm from the indexed code the exact mechanism generating the random suffix (`tempdir.NewWithPrefix`) or how easily it can be discovered/enumerated in this deployment, nor whether external RPC callers can set arbitrary absolute-looking `GitObjectDirectory` values that resolve into the shared storage temp directory in practice (this depends on `ValidateRelativePath` bounds-checking against `storagePath`, confirmed at `internal/git/localrepo/paths.go:38`). A full assessment of exploitability would require live testing (e.g., via a Devin session with repo access) rather than static index review alone.

```go
func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
}
```

```go
func restoreSnapshotRelativePath(ctx context.Context, methodInfo protoregistry.MethodInfo, req proto.Message) (proto.Message, error) {
	// Rails sends RPCs from its access checks with quarantine applied. The quarantine paths are relative to the
	// snapshot repository of the original transaction. While the relative path of the request is the original relative
	// path of the repository before snapshotting, Rails sends the snapshot repository's path in a header. For the
	// quarantine paths to apply correctly, we must thus rewrite the request to point to the snapshot repository here.
	snapshotRelativePath := metadata.GetValue(ctx, MetadataKeySnapshotRelativePath)
	if snapshotRelativePath == "" {
		return nil, ErrQuarantineWithoutSnapshotRelativePath
	}

	rewrittenReq, targetRepo, err := rewritableRequest(methodInfo, req)
	if err != nil {
		return nil, fmt.Errorf("rewritable request: %w", err)
	}

	targetRepo.RelativePath = snapshotRelativePath

	return rewrittenReq, nil
}
```
