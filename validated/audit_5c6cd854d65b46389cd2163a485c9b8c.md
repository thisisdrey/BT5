### Title
Race condition in `ConnectionState.VerifyRelay` allows a duplicate relay packet with the same `messageCounter` to bypass the anti-replay window under concurrent UDP delivery - (File: connection_state.go)

### Summary
`VerifyRelay` (and the twin `Decrypt` path) checks the anti-replay window with `window.Check`, then performs the expensive AEAD verification via `DecryptDanger`, and only afterward marks the counter as seen with `window.Update`, with each of the two window operations taking and releasing `decryptLock` independently rather than as one atomic critical section. If two UDP packets carrying the same `h.MessageCounter` and the same valid AEAD tag arrive close enough in time to be processed by concurrent reader goroutines, both can pass `window.Check` before either calls `window.Update`, letting both packets pass verification and be forwarded via `handleOutsideRelayPacket`.

### Finding Description
`readOutsidePackets` dispatches relay packets (`header.Message`/`header.MessageRelay`) by looking up the hostinfo via `f.hostMap.QueryRelayIndex(h.RemoteIndex)` and calling `hostinfo.ConnectionState.VerifyRelay(f.l, h.MessageCounter, packet, nb)` [1](#0-0) . Nebula's UDP receive path runs multiple reader routines (one per configured `routines`), so two packets landing on different queues can invoke `VerifyRelay` on the same `ConnectionState` concurrently.

Inside `VerifyRelay`:
```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
if !result { return ErrAlreadySeen }

... cs.dKey.DecryptDanger(...) ...

cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)
cs.decryptLock.Unlock()
if !result { return ErrAlreadySeen }
``` [2](#0-1) 

`Check` and `Update` are each individually lock-protected, but the check-then-act sequence spans the unlocked `DecryptDanger` call, so it is not atomic. `Bits.Check` only inspects whether the bit for `i` is already set and returns true if not [3](#0-2) , while the actual "mark as seen" side effect happens only in `Bits.Update`/`updateSlow` [4](#0-3) . Two goroutines racing with the identical `messageCounter` can both observe `Check` returning true before either has called `Update`, so both proceed to `DecryptDanger` and (since the tag is valid — replay of a previously-seen, attacker-observed relay packet, not forgery) both succeed and are forwarded.

This requires the attacker to already possess a previously observed, validly-tagged relay frame (e.g., by capturing their own or a routed peer's relayed traffic, or via a permitted MITM/observation of UDP traffic reaching the relay endpoint) and to resend two copies of it nearly simultaneously to the victim's relay socket. No cryptographic material needs to be forged; this is purely a replay-window race, and the existing "atomic" `Check`+`Update` design intends to prevent exactly this.

### Impact Explanation
This is a real, exploitable TOCTOU race in the anti-replay logic that is unique to `VerifyRelay`/`Decrypt`'s split-lock design (note `Decrypt` for direct data-plane traffic has the identical pattern [5](#0-4) ). The scoped impact is a duplicate relay frame processed twice and forwarded via `handleOutsideRelayPacket`, i.e., the anti-replay invariant ("replayed packets are dropped") is violated for a narrow race window. This maps to a traffic-replay / duplicate-processing impact rather than authentication bypass or decryption/forgery, since the attacker cannot produce a *new* valid message — only cause a *previously valid* one to be delivered twice through the relay path, briefly duplicating relay-forwarded traffic.

### Likelihood Explanation
Preconditions: (1) attacker must already have a validly-tagged relay packet to replay (requires legitimate ability to observe/capture such a packet — e.g., their own relayed session, or on-path observation of UDP traffic), and (2) attacker must send two near-simultaneous copies that land on different reader goroutines within the tiny window between the unlock after `Check` and the relock for `Update` (bounded by one `DecryptDanger` AEAD call, i.e., microseconds). This is a narrow, timing-sensitive race but is deterministically reproducible in a unit test that directly drives two goroutines through `VerifyRelay`/`Decrypt` with a controlled/injected delay, confirming the logical flaw independent of real network timing.

### Recommendation
Make the check-decrypt-update sequence atomic with respect to a given `messageCounter`: either hold `decryptLock` across the whole `Check` → `DecryptDanger` → `Update` sequence (accepting the serialization cost per `ConnectionState`), or use a single locked "reserve" operation that atomically checks-and-marks the counter as in-flight before decryption, then finalizes/rolls back after decryption completes, so no other goroutine can pass `Check` for the same counter while the first request is still processing.

### Proof of Concept
Add a concurrency unit test in `connection_state_test.go`:
1. Build a `ConnectionState` with a real cipher (as done in existing tests) and produce one valid relay frame (`payload`, `messageCounter`) via `EncryptDanger`/equivalent, matching what `VerifyRelay` expects.
2. Optionally inject an artificial delay inside a test-only wrapper around `DecryptDanger` (or rely on natural race-window scheduling under `-race`/`GOMAXPROCS>1` with many repeated trials) to widen the check-decrypt-update gap.
3. Launch two goroutines that call `cs.VerifyRelay(l, messageCounter, packet, nb)` concurrently with identical `messageCounter` and `packet`.
4. Assert that across repeated trials at least one run yields both goroutines returning `nil` (i.e., both succeed) instead of exactly one `nil` and one `ErrAlreadySeen`, demonstrating the replay-window race; run under `go test -race -count=N` to confirm no data race panics mask the logical duplicate-acceptance bug.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}

// updateSlow handles jumps, in-window backfill, dupes, and out-of-window.
func (b *Bits) updateSlow(l *slog.Logger, i uint64) bool {
	// If i is a jump, adjust the window, record lost, update current, and return true
	if i > b.current {
		end := i
		if end > b.current+b.length {
			end = b.current + b.length
		}
		count := end - b.current
		startPos := (b.current + 1) & b.lengthMask

		var lost int64
		if b.current >= b.length {
			// Steady state: every cleared slot is past warmup, so any unset
			// bit we evict is a lost packet from the previous cycle.
			wasSet := b.clearRange(startPos, count)
			lost = int64(count) - int64(wasSet)
		} else {
			// Warmup (the very first window). Some cleared slots represent
			// packets <= length where eviction is not "lost" in the usual
			// sense. This branch is taken at most once per connection so we
			// don't bother optimizing it.
			for n := b.current + 1; n <= end; n++ {
				if !b.get(n) && n > b.length {
					lost++
				}
			}
			b.clearRange(startPos, count)
		}

		// Anything past the new window can never be backfilled, so it's lost.
		if i > b.current+b.length {
			lost += int64(i - b.current - b.length)
		}
		b.lostCounter.Inc(lost)

		b.set(i)
		b.current = i
		return true
	}

	// If i is within the current window but below the current counter, check to see if it's a duplicate
	if b.strictlyWithinWindow(i) {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if b.current == i || w&mask != 0 {
			if l.Enabled(context.Background(), slog.LevelDebug) {
				l.Debug("Receive window",
					"accepted", false,
					"currentCounter", b.current,
					"incomingCounter", i,
					"reason", "duplicate",
				)
			}
			b.dupeCounter.Inc(1)
			return false
		}

		b.bits[word] = w | mask
		return true
	}

	// In all other cases, fail and don't change current.
	b.outOfWindowCounter.Inc(1)
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("Receive window",
			"accepted", false,
			"currentCounter", b.current,
			"incomingCounter", i,
			"reason", "nonsense",
		)
	}
	return false
}
