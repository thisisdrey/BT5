## Finding: Unbounded array allocation from attacker-controlled length word in TVM precompile input parsers [1](#0-0) 

### Title
Memory Allocation with Excessive Size Value in TVM Precompile ABI Decoding (`extractBytes32Array`/`extractBytesArray`/`extractSigArray`) - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The static helpers `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` allocate Java arrays whose length (`len`) is taken directly and unbounded from a single 32-byte word of attacker-supplied calldata, before any validation that the array size is consistent with the actual size of the input payload. ### Finding Description
Each helper reads `len` via `words[offset].intValueSafe()` — a value derived purely from the caller-supplied calldata — and immediately allocates `new byte[len][]` (an array of `len` object references) with no upper bound check and no validation that `data`/`words` actually contains `len` further entries:
```java
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];   // unbounded allocation
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();   // OOB access if len is bogus
    }
    return bytes32Array;
}
```
These helpers are used by precompiled contracts such as `BatchValidateSign`/`ValidateMultiSign` (confirmed by the `signatures`/`addresses`/`cnt` array patterns in `BatchValidateSignContractTest.java` and `ValidateMultiSignContractTest.java`) that are reachable by any account through a `TriggerSmartContractContract` calling the corresponding precompiled address, or through a `CALL` from any deployed contract — i.e. by any unprivileged transaction broadcaster. Because `intValueSafe()` clamps very large `DataWord` values (e.g., a crafted word close to `2^256-1`) to `Integer.MAX_VALUE` rather than rejecting them, an attacker can supply a tiny calldata payload (just the header words) that encodes an enormous declared array length, triggering `new byte[Integer.MAX_VALUE][]` — an allocation of roughly 16+ GB of reference slots — before the loop even attempts to read out-of-bounds data.

### Impact Explanation
Attempting to allocate an array of `Integer.MAX_VALUE` references throws an immediate `OutOfMemoryError` (or induces massive GC pressure) inside the JVM executing the TVM. Because TVM execution happens inline in block/transaction validation, this can crash or hang the executing FullNode/SR node processing the transaction, causing denial of service — matching the CWE-789 "Memory Allocation with Excessive Size Value" bug class from the report (excessive allocation triggered by a small, low-privilege request).

### Likelihood Explanation
Reachability requires only a normal signed transaction invoking the target precompiled contract (directly or via a deployed contract's `CALL`) with crafted calldata — no special privilege beyond an account able to broadcast a transaction. The precise conditions under which the declared `len` word is fully attacker-controlled and unconstrained by the energy-cost formula for the specific precompile (e.g., `BatchValidateSign`'s `getEnergyForData`) could not be fully re-derived from the available context in this session — it is possible the energy cost formula for the concrete precompile scales with the same declared count and gates the allocation via the fee limit before the array is created. This caveat should be verified against the full `getEnergyForData` and `execute()` implementation of the precompile(s) that call these helpers before treating this as a proven, low-cost DoS.

### Recommendation
Before allocating `bytes32Array`/`bytesArray`, validate `len` against a sane upper bound (derived from `words.length` and the type-specific fixed size of each array element) and reject with a `false`/empty result if `len` is inconsistent with the actual calldata length, mirroring the defensive pattern already used elsewhere in the codebase (e.g., `ContractEventParser.subBytes` explicitly rejects oversized ABI lengths). Ensure the corresponding `getEnergyForData` method charges energy proportional to the *declared* array length (not just the raw byte length of `data`) so that any legitimate large allocation is already gated by the transaction's `feeLimit`.

### Proof of Concept
Craft a `TriggerSmartContractContract` transaction (or a contract that internally `CALL`s) targeting the `BatchValidateSign`/`ValidateMultiSign` precompiled address, with the header word at the `offset` consumed by `extractBytesArray`/`extractSigArray`/`extractBytes32Array` set to a very large value (e.g., `0xFFFFFFFF...FFFF`), while keeping the rest of the calldata minimal. On execution, `words[offset].intValueSafe()` clamps to `Integer.MAX_VALUE`, and `new byte[Integer.MAX_VALUE][]` is attempted, which throws `OutOfMemoryError` in the executing node's JVM.

**Uncertainty note:** I was unable to fully view the beginning of the `BatchValidateSign`/`ValidateMultiSign` `execute()` method and their `getEnergyForData` implementations within the available tool budget to confirm whether the energy charge already scales with the declared array length (which would gate this attack behind a proportional fee) or is decoupled from it (which would make the exploit "free" relative to allocation size, exactly matching the CVE's bug class). This should be verified with a full read of `PrecompiledContracts.java` around the `BatchValidateSign`/`ValidateMultiSign` classes before treating the severity as confirmed.
