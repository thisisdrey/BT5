### Title
Fee-bypass via unit-amount `TokenDiff` splitting for Nep245/Imt legs - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` exempts `Nep245`/`Imt` legs from fees only when `amount == 1`, and this threshold is evaluated per individual signed `TokenDiff` intent (in `execute_intent`) and per raw `(token_id, delta)` entry (in `closure_deltas`/`supply_delta`), never on an aggregated net position across a batch. An attacker who controls both sides of a trade can therefore split one large Nep245/Imt-side transfer into N unit-amount (`|delta| == 1`) legs across N separate signed `TokenDiff` intents executed in a single `MultiPayload`, so every leg hits the `amount > 1` exemption in `token_fee` and pays `Pips::ZERO`, while the aggregate value moved can be arbitrarily large.

### Finding Description
The binding that should hold is: `fee_owed_on_logical_trade(token_id, total_amount_moved) == Σ fee_owed_per_signed_intent(token_id, per_intent_amount)`. The code never enforces this equality — it only computes the right-hand side, per-intent: [1](#0-0) 

For each `(token_id, delta)` pair inside a single `TokenDiff`, `Self::token_fee(token_id, amount, protocol_fee)` is invoked with `amount = delta.unsigned_abs()` of *that intent only*: [2](#0-1) 

The `TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}` guard means any Nep245/Imt leg with `amount == 1` returns `Pips::ZERO` instead of the configured `fee`. Because this check is applied independently for every `TokenDiff` intent processed by `execute_intents` (and identically inside `closure_deltas`/`supply_delta`, which evaluate `token_fee` on each raw pre-aggregation delta before folding by `TokenId`), there is no code path that sums per-token amounts across intents in the same batch before applying the threshold.

An attacker who controls (or colludes on) both legs of a trade can therefore sign N matching pairs of `TokenDiff` intents, each moving exactly 1 unit of the Nep245/Imt asset against some Nep141 amount, and bundle all 2N intents into one `MultiPayload` passed to `execute_intents`. Each of the N Nep245/Imt-side deltas individually satisfies `amount == 1`, so `token_fee` returns `Pips::ZERO` for every one of them, and `fees_collected` accumulates nothing for that token across the whole batch, regardless of how large N (and thus the total value moved) is. Existing guards (`MultiPayload::verify`, nonce/lock checks, `TransferMatcher`/balance netting) only ensure signature validity and that the batch nets to zero economically between counterparties — none of them re-evaluate or aggregate fee liability across intents.

### Impact Explanation
This lets an attacker move an arbitrarily large notional value through Nep245/Imt legs while paying zero protocol fee, by decomposing a fee-liable trade into many fee-exempt unit legs inside a single atomically-executed batch. This directly matches the "protocol fees bypassed" Critical category: the fee collector receives less than the protocol's fee schedule implies it should for the given total value transferred. The blast radius covers any Nep245 (multi-token) or Imt asset traded through `TokenDiff`, and is repeatable for every batch and every pair of colluding/self-controlled accounts.

### Likelihood Explanation
Preconditions are met by any unprivileged actor: the attacker needs no special role, only two accounts they control (or a willing counterparty), the ability to sign `TokenDiff` intents, and an underlying Nep245/Imt asset with balances granular enough to split into unit amounts. The only cost is the added transaction size/gas from including N intents in one `MultiPayload`, which scales linearly and is not prohibitive for moderate N. No additional privileges, roles, or races are required, making it fully feasible and repeatable at will.

### Recommendation
Aggregate the Nep245/Imt amount per `TokenId` across all `TokenDiff` intents within the same `MultiPayload`/execution batch before applying the `amount > 1` exemption check in `token_fee`, rather than evaluating the threshold on each intent's raw per-intent delta. Alternatively, remove or tighten the `amount <= 1` exemption for Nep245/Imt so it cannot be trivially satisfied by splitting a larger logical trade into unit-sized intents (e.g., only exempt when the underlying token's total supply for that `token_id` is itself 1, akin to true NFTs).

        match token_id {
