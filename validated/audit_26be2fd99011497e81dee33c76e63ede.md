## Analysis: ModExp precompile length fields lack CPU/memory bounds before the Osaka fork

### Title
Unbounded `ModExp` (0x05) precompile input-length fields allow single-transaction memory-exhaustion DoS - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.ModExp.execute()` derives `baseLen`, `expLen`, and `modLen` directly from three attacker-controlled 32-byte words in the call data and only rejects oversized values when `VMConfig.allowTvmOsaka()` is active. Before that fork is activated network-wide, an unprivileged contract caller can set any of these lengths up to `Integer.MAX_VALUE` and force allocation of correspondingly huge byte arrays for the BASE/EXPONENT/MODULUS operands, independent of the CPU-time throttle that was added only for the narrow degenerate case `baseLen==0 && modLen==0`.

### Finding Description
The ModExp energy/gas calculation and the actual computation both read length fields with no real upper bound outside the Osaka fork gate: [1](#0-0) 

Only when `VMConfig.allowTvmOsaka()` is enabled is there a hard `UPPER_BOUND` (1024 bytes) check on `baseLen`/`expLen`/`modLen`: [2](#0-1) 

The only CPU-time guard that exists independent of the Osaka fork, `MUtil.checkCPUTimeForModExp()`, is gated behind a *different, older* fork (`VERSION_4_8_1_1`) and — critically — only fires for the specific degenerate case `baseLen == 0 && modLen == 0 && expLen > UPPER_BOUND`: [3](#0-2) [4](#0-3) 

This means any combination where `baseLen` or `modLen` is non-zero — or where the exponent length itself is the huge value while base/mod are small but non-zero — is not covered by either the `UPPER_BOUND` rejection (pre-Osaka) or the `checkCPUTimeForModExp` guard. The code then proceeds to build `BigInteger` operands sized by these attacker-supplied lengths: [5](#0-4) 

The docstring itself states calldata is "assumed to be infinitely right-padded with zero bytes," confirming that `parseBytes`/`parseArg` allocate arrays sized to the declared length field regardless of how much real data was supplied, and zero-fill the remainder — i.e., an attacker only needs to submit a small transaction payload with a length header claiming megabytes/gigabytes of data to force a correspondingly large allocation.

The energy-cost formula used pre-Osaka (`getMultComplexity` / `getAdjustedExponentLength`) charges energy that scales with these same lengths, but energy accounting happens independently of, and does not prevent, the JVM from attempting the underlying array allocation and `BigInteger.modPow` computation — a caller with a modest `feeLimit` can still cause the node to attempt an outsized allocation before the energy limit check can abort execution, since the array allocation itself happens inside `execute()` prior to any additional bound check.

This precompile is directly reachable from an ordinary `TriggerSmartContract`/`CALL` executed by any unprivileged account through `Program.callToPrecompiledAddress`, which forwards call data straight to `contract.execute(data)`: [6](#0-5) 

### Impact Explanation
A malicious but otherwise unprivileged contract deployer/caller can trigger an `OutOfMemoryError`/large allocation inside every full node and witness node that executes the transaction (since TVM execution is deterministic and replicated), potentially crashing or severely stalling block processing — a full-node/consensus-wide denial of service from a single broadcast transaction. This matches the "hang or frequently repeatable crash (complete DOS)" class described in the CVE hint, mapped onto the TVM precompile/energy-metering surface explicitly in scope.

### Likelihood Explanation
Exploitability depends on the `VMConfig.allowTvmOsaka()` fork not yet being activated on the target network (the `UPPER_BOUND` check is the only network-wide bound and is fork-gated). Given the test suite treats Osaka as a forward-looking/optional fork (`VMConfig.initAllowTvmOsaka(1)` is explicitly toggled on in tests, implying it is off by default), most currently running java-tron networks that have not activated Osaka remain exposed. No special privilege is needed beyond the ability to submit a `TriggerSmartContract` transaction that reaches address `0x...05`.

### Recommendation
- Enforce the `UPPER_BOUND` (or an equivalent sane cap, e.g. 1024 bytes as used by the Osaka path) on `baseLen`, `expLen`, and `modLen` unconditionally in `ModExp.execute()` and `getEnergyForData()`, not only when `allowTvmOsaka()` is enabled.
- Generalize `MUtil.checkCPUTimeForModExp()` (or a new allocation-size guard) to trigger whenever any of `baseLen`, `expLen`, `modLen` exceeds a safe bound, not only the `baseLen==0 && modLen==0` degenerate case.
- Validate lengths against actual available energy/fee before allocating operand byte arrays, so the allocation itself cannot occur ahead of energy-limit enforcement.

### Proof of Concept
Construct calldata for the `0x05` (MODEXP) precompile with:
- `baseLen = 32` (32-byte word, offset 0)
- `expLen = <very large value, e.g. 0x7FFFFFFF>` (offset 32)
- `modLen = 32` (offset 64)
- followed by a short/base/modulus payload

Because `baseLen != 0` and `modLen != 0`, the `checkCPUTimeForModExp()` guard at [3](#0-2)  never fires, and (absent the Osaka fork) the `UPPER_BOUND` check at [7](#0-6)  is skipped. Execution proceeds to `parseArg(data, ..., expLen)`, attempting to allocate/zero-fill a `~2GB` byte array for the exponent inside `execute()`, which can be submitted via a normal `TriggerSmartContract` call from any account with enough TRX to cover the base call fee.

**Note on verification limits:** I was not able to inspect the exact body of the shared `parseBytes`/`addSafely` helper methods or `DataWord.intValueSafe()` in this pass (tool budget exhausted), so the precise allocation mechanics (e.g., whether an intermediate bound already exists inside `parseBytes` itself) could not be fully confirmed from source; the conclusion above is based on the docstring's explicit "infinitely right-padded with zero bytes" semantics and the absence of any other length check outside the Osaka-gated `UPPER_BOUND`. A Devin session with full repo access should verify `ByteUtil`/`parseBytes`/`DataWord.intValueSafe()` implementations directly before treating this as fully confirmed.
