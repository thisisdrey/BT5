### Title
Uninitialized reward index at `INITIAL_INDEX` credits existing holders a full balance-sized reward - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` treats an account as initialized only when the token index is strictly greater than `INITIAL_INDEX`, so a user who already holds a `DepositToken` or `DebtToken` when its reward speed is first enabled keeps `accountIndexOf == 0` while the token index is exactly `1e18`. [1](#0-0)  The first call to `claimRewards`, `updateBeforeMintOrBurn`, or `updateBeforeTransfer` then computes `_deltaIndex = INITIAL_INDEX - 0`, accruing `balanceOf(account) * 1` reward units that were never earned. [2](#0-1) 

### Finding Description
When rewards are enabled for an already-existing token, `_updateTokenSpeed` initializes `tokenStates[token_]` to `{index: INITIAL_INDEX, timestamp: block.timestamp}` but does not iterate existing holders or set their per-account indexes. [3](#0-2)  `_calculateTokenDelta` only substitutes `INITIAL_INDEX` for an uninitialized account if `_tokenIndex > INITIAL_INDEX`; at the boundary case `_tokenIndex == INITIAL_INDEX`, `accountIndexOf` remains zero. [1](#0-0)  Because deposits, withdrawals, transfers, mints, burns, and permissionless `claimRewards` all route into `_updateTokensAccruedOf`, the erroneous delta is committed to `tokensAccruedOf` on the first touch. [4](#0-3) [5](#0-4) [6](#0-5) 

### Impact Explanation
This breaks reward-accrual conservation: pre-existing balances are credited as if they had been earning since index `0`, although the reward stream starts at `INITIAL_INDEX`. [7](#0-6) [8](#0-7)  Each affected holder receives a one-time unearned accrual approximately equal to their tracked token balance, and `claimRewards` pays it whenever the distributor has enough reward-token balance. [9](#0-8) [10](#0-9)  On a funded distributor this can drain the reward pool or steal rewards that should belong to later legitimate earners; on an underfunded one it permanently records inflated `tokensAccruedOf` entitlements that are paid first once funding arrives. [11](#0-10) 

### Likelihood Explanation
The trigger is a normal configuration transition—setting a non-zero speed for a token with existing holders—rather than an admin mistake or malicious oracle. [12](#0-11)  The attacker only needs to hold the deposit/debt token before activation, or receive one by ordinary deposit, and then call the public `claimRewards(account_, tokens_)` path. [13](#0-12) [14](#0-13)  No health check, pause flag, reentrancy guard, or sender authorization prevents the claim because `claimRewards` pays `account_` regardless of `msg.sender` and `_transferRewardIfEnoughTokens` only checks distributor balance. [4](#0-3) [10](#0-9) 

### Recommendation
Change the fallback condition to initialize never-seen accounts at the current token index whenever `accountIndexOf == 0` and the token state exists, e.g. set `_accountIndex = _tokenIndex` or use `>= INITIAL_INDEX` instead of `> INITIAL_INDEX`. [1](#0-0)  Additionally, consider explicitly initializing accounts when a token is added or provide a migration that sets existing holders’ `accountIndexOf` to `INITIAL_INDEX` before nonzero speed activation. [3](#0-2) 

### Proof of Concept
A Foundry/Hardhat fork test can reproduce it by deploying the pool stack, adding and registering a `DepositToken`, depositing so `alice` has a nonzero balance before rewards start, registering/funding a `RewardsDistributor`, then enabling speed and claiming. [15](#0-14) [16](#0-15) 

```solidity
// invariant: rewards speed is activated after Alice already holds msdTOKEN
depositToken.deposit(100e18, alice);             // Alice balance = 100e18 before rewards
pool.addRewardsDistributor(distributor);         // governor/ops action
rewardToken.mint(address(distributor), 1_000e18);

vm.prank(governor);
distributor.updateTokenSpeed(IERC20(address(depositToken)), 1e18); // index == INITIAL_INDEX

IERC20[] memory toks = new IERC20[](1);
toks[0] = IERC20(address(depositToken));
distributor.claimRewards(alice, toks);           // permissionless; pays alice

assertEq(rewardToken.balanceOf(alice), 100e18);  // unearned balance-sized payout
assertEq(distributor.tokensAccruedOf(alice), 0);
```

The same sequence through `depositToken.transfer(...)` or a second deposit also writes the inflated accrual because `_mint`/`_transfer` invoke the distributor before changing balances. [17](#0-16)

    function _calculateTokenDelta(
        TokenState memory _tokenState,
        IERC20 token_,
        address account_
    ) private view returns (uint256 _tokenIndex, uint256 _tokensDelta) {
        _tokenIndex = _tokenState.index;
        uint256 _accountIndex = accountIndexOf[token_][account_];

        if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
            _accountIndex = INITIAL_INDEX;
        }

        uint256 _deltaIndex = _tokenIndex - _accountIndex;
        _tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
    }

        IERC20 token_,
        uint256 newSpeed_
    ) private onlyIfDistributorExists onlyIfTokenExists(address(token_)) {
        uint256 _currentSpeed = tokenSpeeds[token_];
        if (_currentSpeed > 0) {
            _updateTokenIndex(token_);
        } else if (newSpeed_ > 0) {
            // Add token to the list
            if (tokenStates[token_].index == 0) {
                if (tokens.length == MAX_REWARD_TOKENS) revert ReachedMaxRewardTokens();
                tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp.toUint32()});
                tokens.push(token_);
            } else {
                // Update timestamp to ensure extra interest is not accrued during the prior period
                tokenStates[token_].timestamp = block.timestamp.toUint32();
            }
        }

        if (_currentSpeed != newSpeed_) {
            tokenSpeeds[token_] = newSpeed_;
            emit TokenSpeedUpdated(token_, _currentSpeed, newSpeed_);
        }
    }
