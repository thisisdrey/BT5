## Analog Found

### Title
`handle_unsolicited_StackerDBPushChunk` advertises an accepted StackerDB chunk inventory before the chunk is actually persisted, biasing served inventory vs. committed state - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
The H‑3 bug class is: a derived/reported value is computed from an *intermediate* state of an atomic two-step operation (remove-then-add) and is then propagated/used as if it reflected the *final* state, biasing downstream accounting. The same shape exists in `PeerNetwork::handle_unsolicited_StackerDBPushChunk`: it validates an incoming pushed chunk, then **patches and immediately sends** a `StackerDBChunkInv` reply that advertises the new (higher) `slot_version` as accepted — before the chunk is ever written to the StackerDB. The actual durable write happens later, asynchronously, in the relayer.

### Finding Description
In `stackslib/src/net/stackerdb/mod.rs`, `handle_unsolicited_StackerDBPushChunk`: [1](#0-0) 

1. It calls `make_StackerDBChunksInv_or_Nack` to snapshot the *current* on-disk slot versions into `data.slot_versions`. [2](#0-1) 
2. It runs `validate_received_chunk`, which checks size, signer, version-freshness and max-writes against that snapshot — but never writes anything to the database. [3](#0-2) 
3. On success, it *patches* the in-memory `data.slot_versions[slot_id]` to the pushed chunk's `slot_version` — pretending the chunk is already stored — and immediately signs and sends this patched `StackerDBChunkInv` back to the peer: [4](#0-3) [5](#0-4) 
4. The function then returns `(false, true)`, meaning the *actual* storage happens later and separately, in the relayer's `process_stacker_db_chunks`, which performs its own independent, authoritative freshness re-check via `StackerDBTx::try_replace_chunk`: [6](#0-5) [7](#0-6) 

Between step 3 (reply sent, claiming acceptance) and the relayer's eventual `try_replace_chunk` call, the two operations are not atomic: any concurrent write to the same slot (from another peer's push, an HTTP upload, or a sync download) can cause `try_replace_chunk` to return `StaleChunk`, which the relayer silently drops (only logs a debug message and `continue`s, never correcting the earlier reply): [8](#0-7) 

The result: the `StackerDBChunkInv` this node just sent — the message peers use to decide what to fetch/skip during StackerDB sync — can advertise a slot version that the node's replica never actually stores. This is structurally the same bug as H‑3: an intermediate value (the “we’re about to accept this” version) is computed before the atomic operation (durable persist) completes, and is served as if it already reflected the final, canonical state.

### Impact Explanation
This breaks the equality between *served/advertised* StackerDB inventory and *actually committed* StackerDB inventory. Peers running `StackerDBSync` rely on `StackerDBChunkInvData.slot_versions` to decide whether a given replica already has a chunk (skip re-fetch/re-push) — see `StackerDBSync::add_pushed_chunk`, which treats received inventories as authoritative for resync decisions: [9](#0-8) 
If this node's advertised version is higher than what it actually holds, other replicas can under-replicate that chunk (believing it is already propagated here), producing a network-wide availability gap for that StackerDB slot — this matches "serving non-canonical state as canonical" (High).

### Likelihood Explanation
This requires no privileged access: any connected, unauthenticated-or-authenticated p2p peer can trigger it simply by pushing a valid, signed `StackerDBPushChunk` for any monitored contract while a second write to the same slot races in from a different code path (concurrent push, HTTP upload, or sync download) — all of which are normal, remotely-triggerable, unprivileged operations. The existing project changelog entry (`changelog.d/stackerdb-uploaded-chunk-event-loss.fixed`) shows the maintainers already found and fixed one race in this general area (HTTP-upload/relay-echo ordering), which corroborates that this deferred-store/optimistic-reply pattern is a real, previously-manifested source of races in this exact code path. [10](#0-9) 

### Recommendation
Do not patch and send the `StackerDBChunkInv` reply optimistically before the chunk is durably stored. Either perform the `try_replace_chunk` write synchronously (within the same lock/transaction) before constructing the reply, or defer sending the inventory reply until the relayer has confirmed the chunk was actually persisted, only then reflecting the *actual* stored version rather than the *intended* one.

### Proof of Concept
1. Node A replicates StackerDB `SC` and currently stores slot 0 at version 4.
2. Peer B sends `StackerDBPushChunk{slot_id:0, slot_version:5}` (validly signed) to A.
3. A's `handle_unsolicited_StackerDBPushChunk` runs `validate_received_chunk` (passes: 5 ≥ 4), patches `data.slot_versions[0] = 5`, and immediately replies to B with `StackerDBChunkInv{slot_versions: [..,5,..]}` — before writing anything to disk (`stackslib/src/net/stackerdb/mod.rs:794-815,858-870`).
4. Before the relayer processes the buffered push, Peer C's push of `slot_version:6` for the same slot races in and is committed first via a separate call path.
5. The relayer now processes B's original push via `process_stacker_db_chunks` → `try_replace_chunk`, which sees `slot_validation.version = 6 ≥ 5` and returns `StaleChunk`; the chunk is silently dropped (`stackslib/src/net/relay.rs:2412-2424`, `stackslib/src/net/stackerdb/db.rs:424-429`).
6. Node A's real DB never stores version 5 for that push, yet A had already told B (and A's own gossip-driven sync state) that it accepted/holds a chunk at version 5 for that slot — an inventory reply that does not correspond to any committed chunk A ever actually held at that instant, i.e., mismatched/non-canonical data served to the network.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
