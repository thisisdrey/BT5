### Title
CPU-exhaustion DoS via cheap forged-signature shred flood defeating sigverify LRU cache and dedup - ([File: turbine/src/sigverify_shreds.rs])

### Summary
An unstaked, unprivileged remote attacker can send UDP packets shaped as valid shreds (correct format, size, slot, index, parent offset, fec-set fields, and shred-version) for slots whose leaders are publicly known from the leader schedule, with a corrupted/forged signature. Because signature verification cost (`Signature::verify`) is paid per distinct `(signature, pubkey, merkle_root)` tuple and the shred fetch stage has no per-source authentication or rate limiting, an attacker can force the sigverify thread pool into performing a real ed25519 verification for every forged packet at effectively zero attacker cost.

### Finding Description
Shreds are received on TVU UDP sockets via `ShredFetchStage::packet_modifier` in `core/src/shred_fetch_stage.rs`, using `streamer::receiver(..., is_staked_service=false, ...)`, meaning packets are accepted from any IP without a staked/authenticated-sender check [1](#0-0) . Before sigverify, `ShredFilterContext::should_discard_shred` only performs cheap structural sanity checks (shred version, slot bounds, index bounds, parent offset, fec-set/erasure-config alignment) — none of which validate the signature [2](#0-1) .

Packets that pass this filter reach `run_shred_sigverify` → `verify_packets` → `verify_shreds` → `verify_shred_cpu` in `turbine/src/sigverify_shreds.rs` and `ledger/src/sigverify_shreds.rs`. The dedup step keys on the raw shred wire bytes via `Deduper`, so a single flipped signature byte produces a distinct dedup key and is never filtered as a duplicate [3](#0-2) . `verify_shred_cpu` looks up an LRU cache keyed by `(Signature, Pubkey, merkle_root)`; a forged signature always produces a cache miss, forcing the actual `key.0.verify(key.1.as_ref(), key.2.as_ref())` ed25519 computation on every single distinct forged packet, with no cost bound or fee attached to shred processing [4](#0-3) .

`get_slot_leaders` resolves each shred's slot to its known leader pubkey from the (public) `LeaderScheduleCache`, so the attacker can pick any near-future slot with a known, real leader identity to make `slot_leaders.get(&slot)` succeed and reach the real crypto check rather than being discarded early [5](#0-4) . Because `SIGVERIFY_SHRED_BATCH_SIZE` (1024 batches) and `num_sigverify_threads` bound only per-iteration throughput of the rayon thread pool, not the arrival rate, a sustained flood of cheaply-crafted, uniquely-forged-signature packets exceeding the pool's ed25519-verify throughput causes CPU saturation on the `solSvrfyShredNN` threads and backlog growth in the shred-fetch → sigverify channel (`fetch_receiver`/`SHRED_FETCH_CHANNEL_SIZE`), starving legitimate turbine shred processing.

### Impact Explanation
This is a CPU-exhaustion resource-consumption bug in the shred sigverify thread pool: the attacker pays essentially nothing (no lamports, no stake, no fee — shreds are feeless), while the validator must perform one full ed25519 verification per forged packet since neither the content-hash deduper nor the signature-keyed LRU cache can catch distinct-signature forgeries. This matches the "grossly underpriced pre-fee work" / CPU-DoS bounty category, causing degraded or delayed shred propagation/ingestion (turbine) on the targeted validator, potentially delaying block replay/voting for that node.

### Likelihood Explanation
Feasible and repeatable by a single unprivileged remote host: no gossip/stake/config privilege is required, the TVU shred fetch socket accepts unauthenticated UDP traffic (`is_staked_service=false`), and the leader schedule (mapping slot → leader pubkey) is public. Constructing a well-formed-looking shred packet with a valid slot/index/fec header (to survive `should_discard_shred`) and a random/flipped signature is inexpensive; varying either the signature bytes or the merkle-root field for each packet guarantees a fresh cache-miss key, so the attack scales linearly with attacker bandwidth up to the sigverify thread pool's aggregate ed25519 throughput.

### Recommendation
Add a cost/authentication gate ahead of the expensive `Signature::verify` call for shred ingestion, e.g.: rate-limit or apply per-source-IP/connection quotas on the TVU shred UDP sockets (similar to existing staked-service QoS used elsewhere in streamer), and/or introduce a lightweight pre-check (e.g., requiring the shred merkle root or FEC layout to be consistent with recently-seen legitimate broadcasts from the actual turbine retransmit parent) before falling back to full ed25519 verification, so that arbitrary-source packets bearing a known leader's slot cannot cheaply force full crypto work at unlimited rate.

```rust
fn get_slot_leaders<'a>(
    self_pubkey: &'a Pubkey,
    batches: &'a mut [PacketBatch],
    leader_schedule_cache: &'a LeaderScheduleCache,
    bank: &'a Bank,
) -> impl Iterator<Item = (Slot, Option<Pubkey>)> + 'a {
    batches
        .iter_mut()
        .flat_map(|batch| batch.iter_mut())
        .filter(|packet| !packet.meta().discard())
        .filter_map(move |mut packet| {
            let shred = shred::layout::get_shred(packet.as_ref());
            let slot = shred.and_then(shred::layout::get_slot)?;
            let leader = leader_schedule_cache
                .slot_leader_at(slot, Some(bank))
                .map(|leader| leader.id)
                .filter(|leader| leader != self_pubkey);
            if leader.is_none() {
                packet.meta_mut().set_discard(true);
            }
            Some((slot, leader))
        })
}
```
