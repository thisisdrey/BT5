### Title
Unauthenticated UDP source flagged as `FROM_STAKED_NODE` on the TPU-vote socket, spoofing the trust signal that gates forwarding/QoS decisions - (File: `streamer/src/streamer.rs`, `core/src/fetch_stage.rs`)

### Summary
This is the closest reachable analog to the Holograph `isOwner`/`onlyOwner` bug: two different ingestion paths populate the same trust flag (`FROM_STAKED_NODE`) with different guarantees, and downstream code cannot tell which path produced it. The QUIC path derives this flag from a cryptographically verified TLS client certificate (`get_remote_pubkey`), while the plain-UDP path derives it purely from which socket the packet happened to arrive on, with no per-packet identity check at all.

### Finding Description
In `streamer/src/streamer.rs`, `recv_loop` unconditionally stamps every packet received on a socket with the caller-supplied `is_staked_service` bool: [1](#0-0) 

This is wired up in `FetchStage::new_multi_socket`, where the TPU-vote UDP sockets are registered with `is_staked_service = true`, with the comment "only staked connections should be voting": [2](#0-1) 

Contrast this with the QUIC ingestion path in `streamer/src/nonblocking/quic.rs`, where `FROM_STAKED_NODE` is derived from `ConnectionPeerType`, itself established via a TLS-certificate-verified pubkey (`get_remote_pubkey` in `tls-utils/src/tls_certificates.rs`): [3](#0-2) [4](#0-3) 

So on the QUIC path, `FROM_STAKED_NODE` reflects a cryptographic identity check. On the UDP TPU-vote path, it reflects nothing but "which port did this UDP datagram land on" — UDP has no built-in sender authentication, and the source IP in `Meta::addr` (set in `recvmmsg.rs`) is trivially spoofable. Any packet arriving on that socket, from anyone, is marked `FROM_STAKED_NODE = true`, exactly the same 1-bit flag that the QUIC path only sets after verifying a signed TLS identity.

Downstream consumers treat this flag as an actual trust signal without distinguishing which ingestion path produced it:
- `ForwardingStage::initial_packet_meta_filter` only allows packets missing `discard`/`forwarded` and requiring `is_from_staked_node()` to be buffered/forwarded: [5](#0-4) 
- The banking-stage's TPU→Pack scheduler-bindings translation copies the flag straight into `TpuToPackMessage.flags` used by the external pack process for scheduling decisions: [6](#0-5) [7](#0-6) 

This mirrors the Holograph pattern precisely: one code path (`ERC721H`'s fallback / QUIC) appends a cryptographically-tied identity marker; the other code path (direct implementation calls / plain UDP `recv_loop`) does not, yet both paths funnel into shared logic (`isOwner` / `initial_packet_meta_filter`, `tpu_message_flags::FROM_STAKED_NODE`) that cannot tell the difference and treats the unauthenticated value as trustworthy.

### Impact Explanation
An unstaked, unprivileged attacker can send raw UDP packets to the TPU-vote socket and have them unconditionally tagged `FROM_STAKED_NODE`. Anything gated on that bit — the forwarding stage's staked-only ingress filter, and scheduling/QoS metadata forwarded to the external pack process via `scheduler-bindings` — will treat attacker-controlled, unstaked traffic as if it originated from a verified, staked validator. This can be used to get spam/garbage packets past the "staked-only" admission filter (`initial_packet_meta_filter`) that is specifically meant to keep unstaked traffic out of the forwarding/vote-priority pipeline, degrading the intended QoS guarantee that only stake-weighted senders get this treatment. It does not, from what could be verified, bypass Ed25519 signature verification itself (the transaction/vote content still must carry a valid signature to be processed as a real vote/transaction), so the primary impact is QoS/trust-flag spoofing rather than a full transaction-forgery bypass.

### Likelihood Explanation
High reachability: this is UDP, so no connection setup or stake is required — any host on the network that can reach the TPU-vote port can trigger this by construction, and the flag is set unconditionally per the code shown. The only variable determining actual severity is exactly which downstream behaviors key off `is_from_staked_node()`/`FROM_STAKED_NODE`; the `forwarding_stage` filter and the `tpu_to_pack` flag propagation were directly confirmed. Whether this flag also feeds into fee-priority or scheduling weight decisions inside the external `scheduler-bindings` consumer (which is out of scope per SECURITY.md as an external process) could not be fully confirmed.

### Recommendation
Do not set `FROM_STAKED_NODE` based solely on socket/port binding for UDP ingestion. Either (a) drop the per-packet `FROM_STAKED_NODE` semantics for the plain-UDP TPU-vote listener and rely only on cryptographic/stake verification performed later in the pipeline (e.g., BLS/vote signature + stake lookup), or (b) clearly separate the "socket-level trust hint" from the "verified-identity" flag so that `initial_packet_meta_filter` and any scheduler-bindings consumer only honor a flag that was derived from an authenticated channel (QUIC/TLS), never from `recv_loop`'s `is_staked_service` parameter alone.

### Proof of Concept
1. Identify a validator's TPU-vote UDP socket address (this is discoverable via gossip contact info, as with any TPU service).
2. From an unstaked machine, send arbitrary UDP datagrams directly to that port (no handshake, no stake, no valid client certificate required, since this is plain UDP not QUIC).
3. In `recv_loop` (`streamer/src/streamer.rs:216-217`), every packet received on this socket gets `p.meta_mut().set_from_staked_node(true)` unconditionally, because the socket was registered with `is_staked_service = true` in `FetchStage::new_multi_socket` (`core/src/fetch_stage.rs:196`).
4. This packet now satisfies `initial_packet_meta_filter` in `forwarding_stage.rs:768-770` (assuming it is not otherwise discarded), and its `FROM_STAKED_NODE` bit is propagated into `TpuToPackMessage.flags` via `flags_from_meta` (`core/src/banking_stage/tpu_to_pack.rs:182-184`), causing an attacker-originated, unstaked packet to carry the same trust flag reserved for QUIC connections whose identity was validated via TLS client certificates.

fn flags_from_meta(flags: PacketFlags) -> u8 {
    let mut tpu_message_flags = 0;

    if flags.contains(PacketFlags::SIMPLE_VOTE_TX) {
        tpu_message_flags |= tpu_message_flags::IS_SIMPLE_VOTE;
    }
    if flags.contains(PacketFlags::FORWARDED) {
        tpu_message_flags |= tpu_message_flags::FORWARDED;
    }
    if flags.contains(PacketFlags::FROM_STAKED_NODE) {
        tpu_message_flags |= tpu_message_flags::FROM_STAKED_NODE;
    }

    tpu_message_flags
}
