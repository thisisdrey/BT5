### Title
Fee evasion on `Nep245`/`Imt` transfers via unit-delta leg-splitting in `TokenDiff::execute_intent` - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` waives protocol fees for `Nep245`/`Imt` legs whenever the per-leg `|delta| <= 1`, and `TokenDiff::execute_intent` computes the fee independently for each `(token_id, delta)` pair in the diff without aggregating repeated transfers of the same token across multiple `TokenDiff` intents or multiple legs. An attacker who controls two accounts can move an arbitrarily large quantity of the same `Nep245`/`Imt` asset by encoding it as many unit (`|delta| == 1`) legs across multiple `TokenDiff` intents (or `TokenId`s) inside one or more signed `MultiPayload`s, paying zero protocol fee on the aggregate transfer that would otherwise be fee-liable if expressed as a single delta with `amount > 1`.

### Finding Description
The binding that should hold is: `sum_over_legs(fee_ceil(protocol_fee, |delta_leg|)) == fee_ceil(protocol_fee, |sum_of_deltas_for_same_net_transfer|)` for economically equivalent transfers of the same asset between the same counterparties. This is broken because `TokenDiff::token_fee` decides fee liability purely from the `amount` value passed for a *single* leg: [1](#0-0) 

and `TokenDiff::execute_intent` computes and collects fee per `(token_id, delta)` pair independently, once per `TokenDiff` intent, with no cross-intent or cross-leg aggregation of the same `token_id`: [2](#0-1) 

Because `TokenDeltas` (`Amounts<BTreeMap<TokenId, i128>>`) only allows one entry per `TokenId` inside a single `TokenDiff`, the split has to happen either (a) across multiple `Intent::TokenDiff` entries inside the same `DefuseIntents.intents` vector (one signature, one nonce, many intents; see `DefuseIntents::execute_intent` iterating `self.intents`), or (b) across multiple signed `MultiPayload`s passed together to `execute_intents`/`simulate_intents`: [3](#0-2) [4](#0-3) 

Exploit flow: attacker controls account A and account B, both pre-funded with balances of the same `Nep245`/`Imt` `token_id` inside the Verifier. Attacker signs a batch containing N `TokenDiff` intents from A, each `diff = {token_id: -1, ...}`, matched by N `TokenDiff` intents from B, each `diff = {token_id: +1, ...}` (netted to zero by the `TransferMatcher`/`Deltas::finalize` invariant check, so the batch still balances). For every one of the N legs, `token_fee` sees `amount == 1`, hits the `TokenIdType::Nep245 | TokenIdType::Imt` arm without `amount > 1`, and returns `Pips::ZERO`, so `fees_collected` for that `token_id` stays `0` for the whole batch, while the aggregate quantity actually transferred from A to B is `N`. Had the same aggregate transfer been expressed as one `TokenDiff` with `delta = -N` (`amount = N > 1`), `token_fee` would return the real `protocol_fee`, and `fee_ceil` would charge a nonzero fee to the `fee_collector`.

No existing guard prevents this: `MultiPayload::verify` and nonce checks only ensure each intent is authentically signed and not replayed; they do not constrain how a signer chooses to decompose a diff. `TransferMatcher::finalize` only enforces that the batch nets to zero (no unauthorized fund creation), not that fee accounting is aggregated per token across legs/intents.

### Impact Explanation
The protocol's `fee_collector` receives less than the fee binding requires for `Nep245`/`Imt` transfers whose aggregate value the two colluding attacker-controlled accounts choose to move in unit-sized legs, which falls under "protocol fees bypassed or over-collected" (Critical). No third party's funds are stolen and no balance invariant is violated (the batch still nets to zero) — the loss is confined to the protocol's fee revenue on `Nep245`/`Imt` swaps. This is repeatable indefinitely across any `Nep245`/`Imt` token_id and any two attacker-controlled accounts, bounded only by per-transaction gas/log limits (out of scope to consider as a blocker per the rules, since the finding itself is fee bypass, not DoS).

### Likelihood Explanation
Preconditions are simple and match the stated attacker profile: two attacker-controlled accounts, each holding a Verifier balance of the same `Nep245`/`Imt` `token_id` (obtainable via ordinary deposit), and the ability to sign `MultiPayload`s and call `execute_intents`/`simulate_intents`, all of which are available to any unprivileged user. No relayer key, DAO role, or victim key is needed. The only cost to the attacker is the marginal gas of issuing N small intents/legs instead of one, which is linear and easily affordable for realistic batch sizes.

### Recommendation
Aggregate the effective transferred amount per `token_id` (and ideally per counterparty pair) across all legs of a batch — e.g. compute fee liability from the net absolute delta accumulated across all `TokenDiff` intents executed within the same `execute_intents`/`simulate_intents` call for a given `token_id`, rather than per individual leg's raw `amount`. Alternatively, remove or shrink the `amount > 1` fee-exemption threshold for `Nep245`/`Imt` so genuinely fungible-like MT transfers cannot be trivially decomposed into fee-free unit legs, or track cumulative moved amount per `(signer_id, token_id)` within the batch before applying the exemption.

### Proof of Concept
`cargo test` plan (in `contracts/defuse/core/src/intents/token_diff.rs` tests or an integration test under `tests/src/tests/defuse/intents/token_diff.rs` using the sandbox harness):
1. Set `protocol_fee = Pips::ONE_PERCENT` (nonzero).
2. Build one `MultiPayload` batch with N=100 `Intent::TokenDiff` from account A, each `diff = {nep245_token_id: -1}`, and N=100 matching `Intent::TokenDiff` from account B, each `diff = {nep245_token_id: +1}` (both accounts pre-funded with `Nep245` balance ≥ N under that `token_id`).
3. Execute via `execute_intents`/simulated via `Engine::execute_signed_intents`, and assert `fees_collected` for `nep245_token_id` equals `0`.
4. In a second run, submit a single `TokenDiff` from A with `diff = {nep245_token_id: -100}` matched by B's `diff = {nep245_token_id: +100}`, and assert `fees_collected` for `nep245_token_id` equals `Pips::ONE_PERCENT.fee_ceil(100)` (nonzero).
5. Assert the two `fees_collected` values differ (`0 != nonzero`) despite identical aggregate quantity (`100`) moved between the same two accounts, proving the binding `sum_over_legs(fee_ceil(...)) == fee_ceil(aggregate)` is violated.
