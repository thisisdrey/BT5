### Title
Out-of-bounds slice reads in reftable ref-block parsing due to unchecked attacker-controlled length/offset fields - (File: internal/git/reftable/reftable.go)

### Summary
This is a genuine analog of the reported bug class ("attacker-controlled size/offset values consumed directly by a memory-copy/slice operation without bounds validation"), but the impact in Go is constrained to a crash (index-out-of-range panic / DoS), not memory corruption or RCE, because Go slice accesses are bounds-checked at runtime.

### Finding Description
`Table.getRefsFromBlock` in [1](#0-0)  parses length-prefixed fields (`prefixLength`, `suffixLength`, `hashSize`, symref `size`) read via `getVarInt` directly from the raw reftable byte buffer `src`, and then immediately slices `src` using these attacker-influenced values with no validation that `idx+suffixLength`, `idx+hashSize`, or `idx+size` stay within `len(src)` or within the current block boundaries: [2](#0-1) [3](#0-2) [4](#0-3) 

`getVarInt` itself only checks that `start <= blockEnd` while iterating the continuation bits, and does not bound the *decoded value* it returns — the returned `prefixLength`/`suffixLength`/`size` values are used as raw slice lengths with no upper bound check against the remaining buffer: [5](#0-4) 

Additionally, `refname := prefix[:prefixLength]` in [6](#0-5)  slices the previous reference name string using an attacker-controlled `prefixLength` with no check that `prefixLength <= len(prefix)`.

`parseRefBlock` similarly computes `RestartStart` from an on-disk `RestartCount` field without validating it against the block size, which can produce a huge or negative-wrapping (`uint`) `RestartStart`/loop bound before calling `getRefsFromBlock`: [7](#0-6) 

This is directly analogous to the reported Firedancer flaw: an untrusted, structurally-parsed size field is trusted and fed straight into a raw buffer copy/read (`fd_memcpy(ctx->_txns, src, sz-...)` there vs. `src[idx:idx+suffixLength]` / `src[idx:idx+hashSize]` / `prefix[:prefixLength]` here) without validating it stays within the source buffer.

### Impact Explanation
Because Go performs runtime bounds checking on slice/string indexing, an out-of-range index here does not corrupt memory or enable RCE (unlike the C/`fd_memcpy` case) — it triggers a runtime panic. If this parsing path runs in the main Gitaly server goroutine handling ref reads (e.g. servicing `ListRefs`/ref resolution against a reftable-backed repository) without panic recovery isolating just that RPC, a maliciously crafted `.ref` reftable file could crash the whole `gitaly` process, denying service to all other repositories/RPCs handled by that process — a legitimate DoS of a handler per the validation criteria. This is reachable wherever reftable files are read that could originate from or be influenced by an untrusted party, e.g., through repository import/fork of a repository containing a crafted `reftable/` directory, or replication of a manipulated table file.

### Likelihood Explanation
Exploitability requires the ability to place a corrupted/crafted reftable file into a repository's `reftable/` storage that Gitaly subsequently parses (e.g., via unpacking an imported repository or a replicated fork). I could not fully verify from the indexed code which specific RPC(s)/import path directly write attacker-supplied bytes into a `.ref` table file (this would need to be confirmed against `ReadTablesList`/table-loading call sites and any repository-import/backup-restore code paths not fully covered by the indexed portion of the codebase). Given this uncertainty, likelihood is assessed as moderate rather than confirmed.

### Recommendation
- In `getVarInt`, bound the decoded value itself (not just the traversal index) against the remaining block/buffer size before returning it.
- In `getRefsFromBlock`, after decoding `prefixLength`/`suffixLength`/`hashSize`/`size`, explicitly validate `idx+length <= len(src)` (and `<= b.RestartStart`/`b.FullBlockSize` as appropriate) and that `prefixLength <= len(prefix)` before slicing; return a parse error instead of panicking.
- In `parseRefBlock`, validate `RestartCount` and the derived `RestartStart` against the actual block size before use.
- Wrap reftable parsing entry points with panic recovery so a malformed table can only fail the specific request/repository instead of crashing the whole Gitaly process.

### Proof of Concept
Not independently reproduced against a running Gitaly instance; the analysis is based on static code review of the parsing logic. A conceptual PoC would craft a `.ref` reftable file whose ref-block encodes a `suffixLength` (or symref `size`) varint value large enough that `idx+length` exceeds `len(src)`, then have Gitaly call `Table.GetReferences()` on a repository containing that file, which would trigger a Go runtime `panic: runtime error: slice bounds out of range` inside `getRefsFromBlock`.

func (t *Table) getVarInt(src []byte, start uint, blockEnd uint) (uint, uint, error) {
	var val uint

	val = uint(src[start]) & 0x7f

	for (uint(src[start]) & 0x80) > 0 {
		start++
		if start > blockEnd {
			return 0, 0, fmt.Errorf("exceeded block length")
		}

		val = ((val + 1) << 7) | (uint(src[start]) & 0x7f)
	}

	return start + 1, val, nil
}

func (t *Table) parseRefBlock(src []byte, headerOffset, blockStart, blockEnd uint) ([]git.Reference, error) {
	currentBS := t.extractBlockLen(src, blockStart+headerOffset)

	fullBlockSize := t.blockSize
	if fullBlockSize == 0 {
		fullBlockSize = currentBS
	} else if currentBS < fullBlockSize && currentBS < (blockEnd-blockStart) && src[blockStart+currentBS] != 0 {
		fullBlockSize = currentBS
	}

	b := &block{
		BlockStart:    blockStart + headerOffset,
		FullBlockSize: fullBlockSize,
	}

	if err := binary.Read(bytes.NewBuffer(src[blockStart+currentBS-2:]), binary.BigEndian, &b.RestartCount); err != nil {
		return nil, fmt.Errorf("reading restart count: %w", err)
	}

	b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)

	return t.getRefsFromBlock(src, b)
