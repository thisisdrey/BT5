### Title
Heap OOB read in ijar's ZIP central-directory parser via unchecked length fields — (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar reads the ZIP central-directory-header length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) and the ZIP64 extra-field `data_size` directly from attacker-controlled archive bytes and advances the read cursor `p`/`extra_p` by those values with **no bounds check against the mapped input buffer**, unlike the local-file-header path which is protected by `EnsureRemaining()`. A malicious but sha256-pinned jar/zip dependency can therefore drive the parser to read past the end of the mmap'd file.

### Finding Description
`ProcessCentralDirEntry` (`third_party/ijar/zip.cc:493-545`) does: [1](#0-0) 
```
p += 16;  // skip to 'compressed size' field
*compressed_size = get_u4le(p);
*uncompressed_size = get_u4le(p);
u2 file_name_length = get_u2le(p);
u2 extra_field_length = get_u2le(p);
u2 file_comment_length = get_u2le(p);
...
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
```
and then walks the extra-field chain: [2](#0-1) 
```
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  if (header_id == ZIP64_EXTRA_FIELD_TAG) {
    if (*uncompressed_size == U4_MAX) { *uncompressed_size = get_u8le(extra); }
    if (*compressed_size == U4_MAX) { *compressed_size = get_u8le(extra); }
    if (*offset == U4_MAX) { *offset = get_u8le(extra); }
  }
}
```
None of `file_name_length`, `extra_field_length`, `file_comment_length`, or `data_size` are validated against the amount of data actually remaining in the mmap'd file before use. Compare this to the sibling function `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before every variable-length read: [3](#0-2) 
```
file_name_length_ = get_u2le(p);
extra_field_length_ = get_u2le(p);
if (EnsureRemaining(file_name_length_, "file_name") < 0) { return -1; }
file_name_ = p;
p += file_name_length_;
if (EnsureRemaining(extra_field_length_, "extra_field") < 0) { return -1; }
```
`ProcessCentralDirEntry` has no equivalent `EnsureRemaining` calls at all — confirmed by `EnsureRemaining` occurring only in the local-file-entry and file-data paths of this file. `FindZipCentralDirectory` only validates that the *aggregate* `central_dir_offset + central_dir_size <= in_length` [4](#0-3) , it does not validate that each entry's individually-declared variable-length fields are internally consistent with that budget. A single malicious central-directory record with `file_name_length = extra_field_length = file_comment_length = 0xFFFF` moves `p`/`central_dir_current_` up to ~200KB past its true position, which, once inflated across the record and combined with the `extra_p` walk on attacker-chosen `data_size`, drives `get_u2le`/`get_u4le`/`get_u8le`/`memcpy` reads past the end of the `mmap`'d region backing `zipdata_in_` (see `InputZipFile::Open()`, which builds `p`/`central_dir_` directly off the mapped buffer) [5](#0-4) .

This class of bug — trusting internal offset/length fields inside an already-integrity-checked blob without validating them against the buffer's true extent — is the direct analog of the TensorFlow `BoostedTreesSparseCalculateBestFeatureSplit` bug, where `stats_summary_indices` values were used to index a buffer without being checked against the declared shape.

### Impact Explanation
ijar (the interface-jar stripper) is invoked by Bazel's Java rules on jar inputs, including jars supplied as external dependencies (e.g. via `java_import`, `aar_import`, or jars fetched with `http_archive`/`http_jar` and pinned with `sha256`/`integrity`). The `sha256` pin only guarantees that the downloaded bytes match a specific attacker-chosen blob — it says nothing about whether the internal ZIP central-directory length fields are self-consistent. An attacker who controls the artifact hosted at the pinned URL (or a compromised mirror serving that exact pinned content) can therefore ship a jar whose central directory entries have deliberately oversized `file_name_length`/`extra_field_length`/`data_size` fields, causing the native ijar process to read out of bounds of its mmap'd input buffer (CWE-125, heap/mmap OOB read), typically manifesting as a worker/action crash and in some cases reading adjacent process memory into size fields that flow into further parsing.

### Likelihood Explanation
Reaching this code path only requires supplying a crafted ZIP/JAR as a build dependency — something fully within the described unprivileged-attacker capability (publishing content that a victim's build fetches and pins by checksum). No special build configuration is required; ijar runs by default whenever Bazel needs an interface jar from a precompiled jar dependency.

### Recommendation
Add `EnsureRemaining()` (or an equivalent bounds check against `input_file_->Length()`/the mapped buffer extent) before every variable-length read in `InputZipFile::ProcessCentralDirEntry`, exactly as already done in `ProcessLocalFileEntry`:
- before advancing `p` by `file_name_length`, `extra_field_length`, and `file_comment_length`,
- before advancing `extra_p` by `data_size` and before the fixed 8-byte `get_u8le` reads in the ZIP64 extra-field branch, verifying `data_size >= 8 * count` and that `extra_p` does not exceed `p`'s pre-declared extra-field boundary or the overall file length.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` reproduction would:
1. Hand-craft a minimal ZIP file whose single central-directory record declares `file_name_length = extra_field_length = file_comment_length = 0xFFFF` (well beyond the actual small file size), with a valid EOCD record so `FindZipCentralDirectory` succeeds.
2. Register it as a `java_import`/`http_jar` dependency with a `sha256` matching this crafted file (simulating the pinned-but-malicious-origin scenario).
3. Run a Bazel build that requires an ijar interface jar for this dependency (e.g., depending on it from a `java_library`).
4. Observe the `ijar` action crash (SIGSEGV) or, under ASan, an explicit heap-buffer-overflow/`SEGV on unknown address` report originating in `InputZipFile::ProcessCentralDirEntry`, confirming the OOB read is reached through the normal `sha256`-checked dependency-fetch path.
