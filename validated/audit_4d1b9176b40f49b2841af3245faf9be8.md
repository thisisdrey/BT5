### Title
Unbounded slippage in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` due to missing minimum/maximum ratio protection - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` only carry a single `quant` for one side of a bancor-style exchange pair; the counterpart amount (`anotherTokenQuant`) is derived on-chain, at execution time, from the *current* `firstTokenBalance`/`secondTokenBalance` ratio. Unlike `ExchangeTransactionContract`, which has an `expected` field checked in `ExchangeTransactionActuator` to bound slippage, neither Inject nor Withdraw contracts have any caller-supplied bound on `anotherTokenQuant`. This is the same bug class as the reported `DealManager::initiatePrincipalPayout` issue: an amount is signed off-chain based on an observed ratio, but is reconstructed on-chain from live state that can shift before the transaction executes, silently producing a far worse outcome than the signer intended.

### Finding Description
In `ExchangeInjectActuator.execute()`/`doValidate()`, the account calling inject computes, off-chain, how much of the counterpart token they're willing to deposit based on the exchange's balances at signing time. On-chain, the actual amount deposited/withdrawn is recomputed from whatever `firstTokenBalance`/`secondTokenBalance` happen to be at execution time: [1](#0-0) 

The validate step re-derives the same ratio-dependent `anotherTokenQuant` and only checks that the signer has enough balance for whatever value comes out — there is no check that it matches (within tolerance) a value the signer expected: [2](#0-1) 

`ExchangeWithdrawActuator` has the same pattern: `anotherTokenQuant` is derived from live balances in both `execute()` and `doValidate()`, with only a fixed 0.0001 relative "precision" check (comparing the actuator's own double vs BigDecimal computation, not a caller-supplied bound), so it does not protect against balances moving between signing and inclusion: [3](#0-2) [4](#0-3) 

By contrast, `ExchangeTransactionActuator` — which performs the analogous "buy/sell" operation on the same exchange — explicitly guards against this by requiring the caller to supply `tokenExpected` and reverting if the computed output is less than expected: [5](#0-4) 

This shows the codebase's own pattern for correctly guarding a ratio-derived, precomputed-off-chain value was not applied to Inject/Withdraw.

### Impact Explanation
Any account that is the creator of an `Exchange` object (created via `ExchangeCreateContract`, not privileged in any way — reachable by any ordinary account) who submits an `ExchangeInjectContract` or `ExchangeWithdrawContract` transaction is exposed to a sandwich/front-run: another party can submit `ExchangeTransactionContract` trades against the same exchange pair before the Inject/Withdraw transaction is packed into a block, shifting `firstTokenBalance`/`secondTokenBalance`. Because `anotherTokenQuant` is recomputed against the *post-trade* ratio with no user-supplied bound, the creator can be forced to inject/withdraw a proportionally much larger or smaller amount of the counterpart asset than intended when signing, resulting in an unfavorable, unbounded value transfer relative to what they authorized — directly matching the "unbounded slippage" bug class of the referenced report (more value moved than the signer intended, without any recourse to revert).

### Likelihood Explanation
Medium: any account can create an exchange and be its creator, and any other account can freely trade against the exchange via `ExchangeTransactionActuator` (no special permission required) to manipulate the ratio just before the Inject/Withdraw transaction lands, similar to standard AMM sandwich attacks. This mirrors the original report's own assessment that likelihood is limited by the number of steps required, but here the manipulating party does not need to be the same privileged actor (unlike the original DealManager scenario, which required the originator itself to perform all steps) — an unrelated third party can trigger the ratio shift, making this arguably easier to trigger than the original finding.

### Recommendation
Add a caller-supplied bound (e.g., `expectedAnotherTokenQuant` with min/max) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validate logic the same way `tokenExpected` is enforced in `ExchangeTransactionActuator`, reverting the transaction if the on-chain-computed `anotherTokenQuant` falls outside the caller's tolerance.

### Proof of Concept
1. Account A creates an exchange with `firstTokenBalance = 1000`, `secondTokenBalance = 1000` (1:1 ratio) and is set as `creatorAddress`.
2. A signs an `ExchangeInjectContract` with `tokenId = firstToken`, `quant = 100`, expecting `anotherTokenQuant ≈ 100` (based on the 1:1 ratio at signing time).
3. Before A's transaction is included, account B (unprivileged, unrelated) submits an `ExchangeTransactionContract` that heavily skews the ratio, e.g. buying most of `secondToken`, making `secondTokenBalance = 100`, `firstTokenBalance = 10000` — see the live ratio dependency in `ExchangeInjectActuator.execute()` at [6](#0-5) .
4. A's inject transaction now executes with `anotherTokenQuant = secondTokenBalance * quant / firstTokenBalance = 100*100/10000 = 1`, drastically different from the ~100 A expected when signing, and there is no check to prevent or revert this deviation — A's deposit is accepted at a ratio A never agreed to.
