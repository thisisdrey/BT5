### Title
Unprotected `ExchangeInjectContract` liquidity injection can be sandwiched via `ExchangeTransactionContract` trades to steal value from injectors - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` computes the paired-token amount required for a liquidity injection strictly from the exchange pool's *live* `firstTokenBalance`/`secondTokenBalance` ratio at execution time, with no user-supplied slippage/expected-amount bound and no minimum-price protection. [1](#0-0)  By contrast, `ExchangeTransactionContract` (the trade instruction) carries an explicit `expected` field that lets a trader bound their execution price. [2](#0-1)  Because `ExchangeInjectContract` has no such field, and any account (not just the exchange creator) can invoke `ExchangeInjectActuator`, an attacker can front-run a victim's inject transaction with an `ExchangeTransactionContract` trade that skews the pool ratio to an extreme, forcing the victim to inject tokens at a manipulated ratio, then back-run by reversing the trade to capture the victim's injected value as profit — the same "sandwich around a reserve-scaling liquidity operation" pattern described in the source report against Hyperdrive's `addLiquidity`.

### Finding Description
The TRON on-chain bonding-curve exchange (`ExchangeCapsule`) models a two-token pool via a Bancor-style CRR bonding curve with fixed exponents (0.0005 / 2000), independent of the real reserve sizes. [3](#0-2)  `ExchangeTransactionActuator` lets any account trade against this curve, driving `firstTokenBalance`/`secondTokenBalance` toward an arbitrarily skewed ratio (bounded only by an upper `balanceLimit`, not by any minimum-balance/anti-skew invariant). [4](#0-3) 

`ExchangeInjectActuator.execute` then computes the second token amount to charge the injector as a pure proportional function of whatever the *current* balances are:
```
anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)
``` [5](#0-4) 
This is exactly analogous to the Hyperdrive `addLiquidity()` flaw: an operation that "kicks off" or scales the current `(z,y)`-like reserve point can be executed right after an attacker has pushed the pool into an extreme, low-liquidity-imbalance state, so a legitimate injector unwittingly transacts at a manipulated instantaneous ratio instead of a fair one. Unlike `ExchangeTransactionContract`, which carries an `expected` (slippage-bound) field checked in `doValidate()`, [6](#0-5)  `ExchangeInjectContract` has no equivalent bound field at all — only `owner_address`, `exchange_id`, `token_id`, `quant`. [7](#0-6)  `ExchangeInjectActuator.doValidate()` never checks the resulting price/ratio against any user-provided limit; it only checks balance sufficiency and the exchange balance cap. [8](#0-7) 

Additionally, unlike `ExchangeWithdrawActuator`, which restricts the caller to `exchangeCapsule.getCreatorAddress()`, [9](#0-8)  `ExchangeInjectActuator` has no creator-only restriction, so any unprivileged account can be the sandwiched victim (as an injector) while any other unprivileged account can be the attacker (trader).

### Impact Explanation
An attacker can:
1. Front-run a pending `ExchangeInjectContract` by submitting an `ExchangeTransactionContract` that sells a large amount of one token into the pool, skewing `firstTokenBalance`/`secondTokenBalance` far from the pool's "fair" ratio (bounded only by the configurable `balanceLimit`, not a minimum-reserve invariant).
2. The victim's `ExchangeInjectContract` executes against this skewed ratio, so `anotherTokenQuant` is computed unfavorably to the victim, forcing them to inject value at an off-market rate. Because the injection maintains whatever (attacker-skewed) ratio is live, value can be extracted from the victim's contribution when the attacker reverses the trade.
3. The attacker back-runs by reversing the trade, restoring the ratio and pocketing the difference, extracting real backing tokens from the pool at the victim's expense.

This results in direct, unauthorized value extraction from another unprivileged account's on-chain transaction (theft of funds), matching the medium/high severity threshold, since it is reachable purely by ordinary signed `ExchangeTransactionContract`/`ExchangeInjectContract` transactions with no special privilege required.

### Likelihood Explanation
Both `ExchangeTransactionContract` and `ExchangeInjectContract` are broadcastable by any account holding the relevant tokens/TRX; there is no creator-only gate on inject (unlike withdraw). An attacker capable of ordering transactions within the same block (front-run/back-run), which is a standard MEV-style capability on TRON given block producers control transaction ordering, can reliably execute this sandwich whenever a victim's inject transaction is visible in the mempool. The lack of any slippage-bound field on `ExchangeInjectContract` means the victim has no on-chain mechanism to protect themselves.

### Recommendation
Add an `expected`/slippage-bound field to `ExchangeInjectContract` (mirroring `ExchangeTransactionContract.expected`) so injectors can specify the maximum/minimum acceptable `anotherTokenQuant`, and reject the injection in `ExchangeInjectActuator.doValidate()`/`execute()` if the computed value falls outside that bound. Additionally, consider adding a minimum-reserve-ratio invariant enforced in `ExchangeTransactionActuator.doValidate()` to prevent a single trade from skewing `firstTokenBalance`/`secondTokenBalance` to an extreme ratio in one transaction.

### Proof of Concept
Conceptual PoC using existing exchange contracts (verified against `ExchangeInjectActuatorTest.java`/`ExchangeCapsuleTest.java` test harness patterns):
1. Create an exchange with balanced reserves, e.g. `firstTokenBalance = secondTokenBalance = 100_000_000L`, via `ExchangeCreateContract`.
2. Attacker submits `ExchangeTransactionContract` selling a large quantity of `firstToken`, driving `secondTokenBalance` down sharply per `ExchangeCapsule.transaction()`. [10](#0-9) 
3. Victim submits `ExchangeInjectContract` for `firstToken` with `quant = X`; `anotherTokenQuant` is computed from the now-skewed ratio via `floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)`, charging the victim a disadvantageous amount of `secondToken`. [5](#0-4) 
4. Attacker submits a reversing `ExchangeTransactionContract` (buying back `firstToken`), restoring the ratio and realizing a net profit funded by the victim's injected `secondToken`.

Because I could not execute the java-tron test harness directly in this environment, this PoC path is derived from reading the actuator/capsule logic and existing unit tests (`ExchangeInjectActuatorTest.java`, `ExchangeCapsuleTest.java`); a background engineering session with repository access should implement and run the concrete numeric scenario to confirm exact profit figures.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
