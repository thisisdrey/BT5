### Title
Inconsistent overflow handling between `doValidate()` and `execute()` in `ExchangeInjectActuator` causes legitimately-validated exchange injections to fail non-deterministically - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator` computes the same "another token quantity" ratio twice using two different arithmetic strategies: `doValidate()` uses lossless `BigInteger` multiplication/division, while `execute()` uses primitive `multiplyExact`/`floorDiv` on `long`. Because `BigInteger` cannot overflow but `long` primitives can, a transaction can pass `doValidate()` and then throw `ArithmeticException` inside `execute()` for the exact same inputs, mirroring the root cause of the Sherlock M-3 finding: intermediate multiplication before division overflowing even though the final quotient is well within range.

### Finding Description
In `doValidate()`, the ratio is computed safely: [1](#0-0) 
using `BigInteger.multiply().divide()`, which never overflows regardless of the magnitude of `firstTokenBalance`, `secondTokenBalance`, or `tokenQuant`.

However, `execute()` recomputes the identical ratio using raw `long` arithmetic: [2](#0-1) 
`multiplyExact(secondTokenBalance, tokenQuant)` (or the symmetric branch) computes the full product `secondTokenBalance * tokenQuant` **before** dividing by `firstTokenBalance`. If that intermediate product exceeds `Long.MAX_VALUE` (~9.22e18) — which can legitimately happen even when the final quotient `anotherTokenQuant` is small — `multiplyExact` throws `ArithmeticException`, which is caught and converted into `ContractExeException`, failing the transaction.

This differs from the pattern in `MarketUtils.multiplyAndDivide()` (used by `MarketSellAssetActuator`) and `MarketComparator.comparePrice()`, both of which explicitly catch the `ArithmeticException` from the primitive path and **fall back to `BigInteger`** computation: [3](#0-2) 
`ExchangeInjectActuator.execute()` has no such fallback — it lets the `ArithmeticException` propagate and fail the whole transaction, even though `doValidate()` already proved the operation is mathematically valid via `BigInteger`.

### Impact Explanation
This is a functional inconsistency/DoS bug, not silent value corruption (unlike the original Sherlock report, which involved silent overflow wraparound in floating-point-free integer math producing wrong values). Here the failure mode is: a transaction that correctly passes on-chain validation (`validate()` succeeds) can still deterministically fail at `execute()` for the same state and inputs, because `execute()`'s primitive-overflow guard has no `BigInteger` fallback (unlike its sibling `MarketUtils.multiplyAndDivide`). This wastes the sender's bandwidth/fee for a transaction that was supposed to succeed, and represents a reachable, deterministic execution failure in a normal `ExchangeInjectContract` broadcast by any account, triggered purely by large (but valid, within `ExchangeBalanceLimit`) pool balances and inject quantities — no privileged access required.

### Likelihood Explanation
Reachable by any account broadcasting a signed `ExchangeInjectContract` transaction against an `Exchange`/`ExchangeV2` pool whose `secondTokenBalance` (or `firstTokenBalance`) multiplied by the injected `tokenQuant` exceeds `Long.MAX_VALUE`. Given TRX/TRC10 balances and exchange limits can be large (bounded only by `DynamicPropertiesStore#getExchangeBalanceLimit`, whose exact configured value I could not fully verify due to index truncation), and `tokenQuant` is attacker/user controlled up to their asset balance, this condition is plausible for high-balance pools, making this a realistic Medium-likelihood scenario rather than a purely theoretical one.

### Recommendation
Make `execute()`'s ratio computation consistent with `doValidate()`: catch `ArithmeticException` from the `multiplyExact`/`floorDiv` primitive path in `execute()` and fall back to the same `BigInteger` computation used in `doValidate()` (mirroring `MarketUtils.multiplyAndDivide`'s pattern), ensuring that any transaction that passes validation is guaranteed to also succeed in execution.

### Proof of Concept
Not independently reproducible from static analysis alone (no runtime environment available). Conceptually:
1. Create an exchange pool where `firstTokenBalance` is small and `secondTokenBalance` is close to `Long.MAX_VALUE / small_tokenQuant` such that `secondTokenBalance * tokenQuant` for a chosen `tokenQuant` exceeds `Long.MAX_VALUE`, but `secondTokenBalance * tokenQuant / firstTokenBalance` (the true quotient) is small and valid.
2. `doValidate()` succeeds because it uses `BigInteger`.
3. `execute()` calls `multiplyExact(secondTokenBalance, tokenQuant)`, which throws `ArithmeticException`, converted to `ContractExeException`, failing the otherwise-valid transaction.

Note: I was unable to confirm the exact configured/default value of `ExchangeBalanceLimit` due to index size limits truncating `DynamicPropertiesStore.java`; a Devin session with full repository access would be needed to confirm concrete numeric feasibility bounds and to write an executable JUnit PoC (similar to the existing `ExchangeTransactionActuatorTest#hardenedExecuteOverflowThrowsArithmeticException` test in the codebase, which already demonstrates the analogous overflow-throw behavior for `ExchangeTransactionActuator`).
