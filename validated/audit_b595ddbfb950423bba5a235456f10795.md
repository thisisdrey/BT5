### Title
Oversized attachment content accepted and stored without enforcing `attachments_max_size` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
A malicious peer answering a `/v2/attachments/{hash}` request can return a `GetAttachmentResponse` whose hex-decoded `Attachment.content` is arbitrarily large (bounded only by the chunked-transfer/`MAX_MESSAGE_LEN` limits in `stacks-common`), and this content is passed straight to `AtlasDB::insert_instantiated_attachment` with no check against `AtlasConfig.attachments_max_size`. This lets a peer force storage of attachments far larger than the configured cap intended for BNS zonefiles.

### Finding Description
`StacksHttpResponse::decode_atlas_get_attachment` simply extracts the HTTP payload, converts it to JSON, and deserializes it into `GetAttachmentResponse` with no size validation: `let contents_json: serde_json::Value = contents.try_into()?; let resp: GetAttachmentResponse = serde_json::from_value(contents_json)...` [1](#0-0) .

This decoded response is consumed in `AttachmentsBatchStateContext::extend_with_attachments`, which stores `response.attachment` directly into the `attachments: HashSet<Attachment>` context with no length check: `if let Ok(response) = response.decode_atlas_get_attachment() { self.attachments.insert(response.attachment); ... }` [2](#0-1) .

When the state machine reaches `Done`, every attachment in this set is unconditionally handed to `AtlasDB::insert_instantiated_attachment` before any size comparison against `attachments_max_size` occurs: 
```
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;
    ...
}
``` [3](#0-2) .

The only bound on the attachment size at this point in the code path I could verify is whatever `MAX_MESSAGE_LEN`/chunked-transfer-decoding imposes on the HTTP body overall — there is no explicit `attachment.content.len() <= atlas_config.attachments_max_size` guard anywhere between the hex-decode (`Attachment::new(bytes)`) and the `insert_instantiated_attachment` call in this file. The same absence of a size guard applies to the `check_attachment_instances` path, which also calls `atlas_db.insert_instantiated_attachment(&attachment)` for attachments pulled from the "uninstantiated"/inboxed table [4](#0-3) .

### Impact Explanation
A remote peer that legitimately serves attachment-inventory/data (no privileged role required) can respond to attachment fetch requests with content much larger than the operator's configured `attachments_max_size`, and that oversized blob gets persisted into the node's `AtlasDB` SQLite store. This is attachment-storage bloat/exhaustion that is not tied to any consensus-committed size bound, matching the "attachment/BNS mismatch"-adjacent High-impact category described in the prompt (oversized data accepted where a size bound was expected to apply).

### Likelihood Explanation
The attacker only needs to run/serve as an outbound sync peer (or be selected as a data URL peer during Atlas sync) and answer a `/v2/attachments/{hash}` GET with a large hex payload — no secret, no signature, no admin privilege is needed. This is repeatable per attachment instance the node is trying to resolve, and the request path (`AttachmentsBatchStateMachine::DownloadingAttachment` → `extend_with_attachments`) is a normal part of Atlas sync reachable by any peer providing a data URL.

### Recommendation
Enforce `attachment.content.len() <= atlas_config.attachments_max_size` immediately after decoding the response in `decode_atlas_get_attachment`/`extend_with_attachments`, rejecting (and penalizing the peer's reliability report) any attachment exceeding the configured maximum before it is added to `context.attachments` or passed to `insert_instantiated_attachment`.

### Proof of Concept
In `stackslib/src/net/atlas/download.rs` tests, construct a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains a `StacksHttpResponse` with a JSON body `{"attachment": {"content": "<hex string longer than attachments_max_size>"}}`. Call `AttachmentsBatchStateContext::extend_with_attachments` on it, then drive the state machine to `Done` and call `AttachmentsDownloader::run`. Assert that `network.atlasdb.insert_instantiated_attachment` is invoked (or that `find_attachment` after the run returns content) with `content.len() > atlas_config.attachments_max_size`, demonstrating no size gate exists before storage.
