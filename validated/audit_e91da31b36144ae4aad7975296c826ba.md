Found it. `handleRecvError` in `outside.go` tears down an active tunnel based on an entirely **unauthenticated, unencrypted** `header.RecvError` packet — no CA-signed certificate, no decryption, no handshake required.

### Title
Unauthenticated `RecvError` packet allows any attacker to remotely tear down established tunnels - (File: `outside.go`)

### Summary
`header.RecvError` packets are processed before any decryption/authentication step in `readOutsidePackets`, and `handleRecvError` uses them to call `f.closeTunnel(hostinfo)` on a live, fully-established tunnel. The only mitigations are a source-address match check and an opt-in rate/allow config (`acceptRecvErrorConfig.ShouldRecvError`), neither of which authenticates the sender as the legitimate certificate holder for that index. This mirrors the reported bug class: a state-mutating operation with no real access control, callable repeatedly by an unauthenticated party, that degrades or denies a resource/service other users depend on (there, ETH needed for LZ messaging; here, the peer's live tunnel needed for messaging).

### Finding Description
In `outside.go`, `RecvError` is dispatched straight out of the unencrypted-header switch, before any `hostinfo`/`ConnectionState` decryption gate: [1](#0-0) 

`handleRecvError` resolves the packet's `RemoteIndex` to a hostinfo via `QueryReverseIndex`, and if the claimed source UDP address happens to match the currently recorded remote for that tunnel, it unconditionally tears the tunnel down: [2](#0-1) 

There is no cryptographic proof that the sender is the actual certificate-holding peer on the other end of that tunnel — `RecvError` carries no MAC, no message counter validated against the session, and is processed with zero decryption. An attacker who can spoof/guess the victim's current UDP source address (already known to any observer of the traffic, e.g. through NAT/relay visibility, or via off-path spoofing since this is UDP) and the 32-bit `RemoteIndex` can force `closeTunnel` + `DeleteHostInfo` on a live session. Unlike `CloseTunnel`, which the changelog explicitly hardened to require the encrypted/authenticated path ("Properly handle `closetunnel` packets"), `RecvError` remains an intentionally-unauthenticated fast path, and the CHANGELOG documents a prior race here ("Rare race condition when tearing down a tunnel due to `recv_error`") confirming this is a known-sensitive, remotely-triggerable teardown primitive.

### Impact Explanation
Repeatedly sending spoofed `RecvError` packets lets an unauthenticated remote attacker force continuous tunnel teardown/re-handshake cycles between two legitimate, properly-certified peers, denying them stable connectivity — directly analogous to the original report's "attacker can call `withdraw()` in every block to make the system unusable." This is a remote state-poisoning / DoS primitive reachable without holding a CA-signed certificate, matching the accepted "remote state poisoning" impact class.

### Likelihood Explanation
The only barrier is knowing/guessing the victim's `RemoteIndex` (32-bit, but observable by an on-path attacker or a lighthouse-adjacent observer) and current UDP endpoint, and the `acceptRecvErrorConfig` allow-list being permissive (default behavior depends on config, but the code path itself performs no cryptographic authentication regardless). No certificate or handshake completion is required to reach `handleRecvError`.

### Recommendation
Do not act on `RecvError` (or any unencrypted control message) to tear down established tunnels based solely on address matching. Require the sender to prove possession of the session's cryptographic state before honoring teardown — e.g., authenticate `RecvError` with the AEAD session keys (similar to how `CloseTunnel` was hardened per the changelog entry "Properly handle `closetunnel` packets"), or require an out-of-band signed confirmation before deleting hostinfo/closing the tunnel.

### Proof of Concept
1. Observe/derive a victim tunnel's `RemoteIndex` and current UDP endpoint (e.g., from network vantage point or address reuse).
2. Craft an unencrypted `header.RecvError` packet with that `RemoteIndex`, sourced (or spoofed) from the victim's recorded peer address.
3. Send it to the victim's UDP listener; `readOutsidePackets` routes it directly to `f.handleRecvError` with no decryption.
4. `handleRecvError` matches the address and calls `f.closeTunnel(hostinfo)` plus `hm.DeleteHostInfo(hostinfo)`, tearing down the legitimate tunnel.
5. Repeat continuously to prevent the tunnel from ever staying established, denying service between the two legitimate peers. [3](#0-2) [2](#0-1) [4](#0-3)

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
