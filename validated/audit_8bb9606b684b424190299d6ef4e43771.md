### Title
DeleteKey+AddKey nonce reseed to `(block_height-1)*1e6` enables intra-block/next-block replay of an already-executed transaction - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`add_regular_key` (and `add_gas_key`) unconditionally reseed a re-created access key's nonce to `initial_nonce_value(block_height) = (block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, without regard to what nonce that same public key had already reached earlier in the same block/chunk. If a FullAccess key is used to execute one or more transactions in block height `H` (nonces `(H-1)*1e6+1`, `(H-1)*1e6+2`, ...) and is then deleted and re-added with the same public key in the same chunk, the new key's nonce is reset to `(H-1)*1e6`, which is strictly less than the nonces already consumed.

### Finding Description
`initial_nonce_value` at [1](#0-0)  computes the reseed value purely from `block_height`, with no reference to the access key's prior nonce. `add_regular_key` applies this value unconditionally whenever a key with the same public key is re-created via `AddKey`: [2](#0-1) . `action_delete_key`/`delete_regular_key` fully removes the access key from the trie state, discarding its previously advanced nonce: [3](#0-2)  and [4](#0-3) .

Nonce verification (`verify_nonce`) only enforces `tx_nonce > current_nonce` (Monotonic mode) against the *currently stored* access key nonce, plus an upper bound of `block_height * 1e6`: [5](#0-4) . There is no independent transaction-hash-based replay cache in the runtime — replay protection is nonce-based plus a block-hash "freshness"/validity-period check (`check_transaction_validity_period`), which only bounds *how old* the referenced block hash may be, not whether a specific tx was previously executed: [6](#0-5) . The `docs/architecture/how/tx_routing.md` note about mempool-level "duplicate" dropping applies to unconfirmed pool eviction, not to state-based execution guarantees.

This is a **known, documented limitation**: the code comment explicitly says "Set default nonce for newly created access key to avoid transaction hash collision" (referencing near/nearcore#3779) — the reseed exists to prevent *hash collisions between historically re-used pubkeys*, not to preserve monotonic ordering against nonces already consumed by that key earlier in the same block. A related integration test acknowledges the underlying issue directly: `test_delete_key_last` in `integration-tests/src/tests/standard_cases/mod.rs` contains a `TODO(#6724)` comment stating "This is a wrong error, the transaction actually succeeds... Normally, retries are handled by nonces, but we forget the nonce when we delete a key!" [7](#0-6) 

However, the exploit as posed requires the DeleteKey+AddKey to occur in the **same chunk/apply call** as the prior transactions against that key, at the **same block height H**, and for the previously-consumed nonces to be `> (H-1)*1e6` — which is only true if the key had already processed at least one transaction in that exact block. Under normal operating conditions (block height growing roughly one at a time, ~1-2s per block), a single block's nonce budget of `1e6` is never exhausted by legitimate use, so this can occur at *any* block height, not only "after years of operation" — the "seed-vs-bound collision" framing in the question (implying it only manifests once chain height is very large) is not accurate: the collision is deterministic and height-independent, occurring any time DeleteKey+AddKey happens in the same block as a prior transaction from that same key.

### Impact Explanation
This is a genuine double-spend / transaction-replay primitive: an attacker's own transaction (e.g., a `Transfer` action) can be re-executed after being invalidated via key deletion+recreation, in a subsequent block, moving funds twice from the same signed transaction. This matches the "double-spend/replay" bounty category from the rules. The impact is scoped to funds controlled by the attacker's own account being replayed to a chosen receiver — it does not directly enable stealing funds from other users' accounts, only value duplication for the attacker's own outgoing transfer (which is still a protocol-level integrity violation: a receiver could be paid twice for one transfer, or a transaction burning attacker balance could be replayed to double the burn against network invariants, or more critically, an attacker could double-spend a payment to an exchange/merchant that trusts on-chain finality).

### Likelihood Explanation
Preconditions are fully attacker-controlled and require no privileged access: fund an account, use a FullAccess key, sign multiple transactions with sequential nonces, then submit a `DeleteKey`+`AddKey` (same pubkey) pair, all targeted to land in the same chunk/block height. The attacker needs only to submit ordinary transactions to a public RPC endpoint. It requires precise timing to get all actions (prior txs + delete + re-add) included in one chunk before resubmitting the earlier transaction — feasible for a determined attacker who controls transaction submission timing and can retry across blocks (this is exactly the scenario already flagged internally via #6724). Cost is minimal (only gas fees).

### Recommendation
When re-adding an access key for a public key that previously had a higher nonce, the runtime should not reduce the effective nonce below the highest nonce that key has ever reached. Options: (1) track a per-account/per-pubkey monotonic "nonce floor" that persists across delete/re-add cycles within the retention window, rather than deriving the reseed purely from `block_height`; (2) reseed using `max((block_height-1)*1e6, previous_nonce)` where `previous_nonce` is read from the just-deleted key before removal; or (3) address the long-standing `#6724` TODO directly by preserving the nonce across delete-then-recreate rather than resetting it to a height-derived constant.

### Proof of Concept
Unit test in `runtime/runtime/src/tests/apply.rs`:
1. Set up account with FullAccess key at fixed `block_height = H` in `ApplyState`.
2. In one `apply()` call, include: `tx1` (nonce `(H-1)*1e6+1`, e.g. Transfer to account B), `tx2` (nonce `(H-1)*1e6+2`), `DeleteKey(pubkey)`, `AddKey(pubkey, FullAccess)` — assert all four succeed and the new stored `AccessKey.nonce == (H-1)*1e6`.
3. In a second `apply()` call at `block_height = H+1` (or same `H` if chunk boundary allows), resubmit `tx1` (same signed bytes, nonce `(H-1)*1e6+1`) against the recreated key.
4. Assert: `verify_nonce`/tx execution succeeds (no `InvalidNonce` error), and account B's balance reflects the transfer amount being credited a second time — demonstrating double-spend. Compare against expected invariant: total value transferred out of the signer account should equal exactly one transfer amount, but observed value equals two.

}

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}

/// Computes, for each transaction in `chunk`, whether it is still within its
/// validity period relative to `prev_block_header`.
pub fn compute_transaction_validity(
    chain_store: &ChainStoreAdapter,

    prev_block_header: &BlockHeader,

) -> Vec<bool> {

        .to_transactions()

        })
        .collect()
}
