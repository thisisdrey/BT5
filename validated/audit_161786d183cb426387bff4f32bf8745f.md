## Title
Replay-window check/commit split allows same-nonce packet to be decrypted twice under concurrent processing - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement the anti-replay defense as three separate, non-atomic steps: lock → `window.Check()` → unlock, then AEAD decrypt (unlocked), then lock → `window.Update()` → unlock. This mirrors the pattern in the referenced report: a value is validated ("checked"), a state-changing operation is performed in between while the lock is dropped, and only afterward is the "commit" (`Update`) applied. If nebula's inbound packet path can invoke `Decrypt`/`VerifyRelay` for the same `hostinfo`/`ConnectionState` concurrently (multiple UDP reader routines feeding `readOutsidePackets`), an attacker who replays a captured packet can race the original processing: both the original and the replayed copy can pass `window.Check()` (since neither has yet called `Update()`), and both will then successfully decrypt, because it's the literal same ciphertext/nonce.

### Finding Description
`Decrypt`: [1](#0-0) 

`VerifyRelay`: [2](#0-1) 

Both functions take `decryptLock`, call `window.Check()`, release the lock, perform the (comparatively slow) AEAD decrypt operation unlocked, then reacquire the lock and call `window.Update()`. This check→(unlocked work)→commit structure is the same root-cause pattern as the reported issue: state used for a security decision is read, mutated only at the very end, and a second, concurrently-processed message can observe the pre-commit state and be allowed through. The CHANGELOG entries for this exact release line ("Lock replay window updates so concurrent readers can't corrupt it. (#1802)", "Advance the replay window on relayed packets... (#1751)", "Fix a race in relay state handling. (#1753)") confirm this window/relay path has already been a source of replay-window races, and a dedicated e2e regression test exists for the *relay* replay case: [3](#0-2) 

However, that test and the CHANGELOG fixes address forwarding-relay re-transmission and internal bitmap corruption — they do not close the fundamental TOCTOU gap between `Check` and `Update` for a *terminal* endpoint's own `Decrypt`/`VerifyRelay` call when two goroutines race on the same counter before either commits.

### Impact Explanation
If exploitable, an attacker capturing one legitimate encrypted packet could get it processed twice on the receiver (double delivery to the tun device, or double-processing of a relayed Control/Message frame), defeating the anti-replay guarantee the `Bits` window is supposed to provide. This is a concrete traffic-replay/state-poisoning impact class explicitly in scope.

### Likelihood Explanation
This requires two threads to race in the narrow gap between `window.Check()` returning and the corresponding `window.Update()` call for the *same* message counter on the *same* `ConnectionState`, which requires either genuinely concurrent UDP packet delivery for the same tunnel (I could not fully confirm from the available index whether `Interface`'s outside read path (`readOutsidePackets`) is invoked from multiple concurrent goroutines per hostinfo/queue, or a single per-queue goroutine serializes decrypts for a given peer) or an attacker able to trigger overlapping delivery (e.g., via relay forwarding paths that call `Decrypt`/`VerifyRelay` from different code paths). I was not able to verify this concurrency model within the available tool budget/index, so likelihood is uncertain and should be verified against `interface.go`'s reader-goroutine setup before treating this as confirmed-exploitable.

### Recommendation
Hold `decryptLock` for the full check-decrypt-update sequence (or otherwise make the check+commit atomic with respect to the decrypt step), so that no second caller can observe a not-yet-committed window state for the same counter. Alternatively, perform a provisional/tentative `Update` (reserve the slot) before decrypting, and roll it back on decrypt failure, so a concurrent duplicate is rejected at `Check` time rather than only detected after both have decrypted.

### Proof of Concept
Conceptual PoC (pending confirmation of concurrent invocation):
1. Establish a tunnel and let the attacker capture one legitimate ciphertext packet with counter `N`, destined to a victim receiver.
2. Simultaneously (or with the receiver processing delayed, e.g. by scheduling pressure) deliver two copies of the packet with counter `N` to the receiver's UDP socket such that both are picked up by concurrent processing before either has completed its `Update(N)` call.
3. If the receiver's `Decrypt`/`VerifyRelay` invocations are not otherwise serialized per-`ConnectionState`, both `window.Check(N)` calls return `true` (neither has committed yet), both successfully `DecryptDanger` the identical ciphertext, and the packet is delivered/forwarded twice. [4](#0-3)

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
