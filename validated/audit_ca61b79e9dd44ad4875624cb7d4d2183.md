### Title
`AccountLocks::try_lock_transaction_batch` validates all transactions against pre-batch state before locking any, allowing intra-batch write/write and write/read conflicts to both return `Ok` - (File: `accounts-db/src/account_locks.rs`)

### Summary
`try_lock_transaction_batch` performs its validation pass and its locking pass as two fully separate loops over the batch, and the validation pass only checks each transaction's account set against `self`'s state as it existed *before the batch started* — it never sees the locks that earlier transactions in the same batch will take. The subsequent locking pass unconditionally applies `lock_accounts` for every transaction marked `Ok`, with no re-check, so two conflicting transactions in the same batch can both be marked `Ok` and both have their write locks incremented on the same account.

### Finding Description
`try_lock_transaction_batch` first iterates the batch and, for every transaction still marked `Ok`, calls `self.can_lock_accounts(keys.clone())` [1](#0-0)  . `can_lock_accounts` takes `&self` and is purely a read-only check against `write_locks`/`readonly_locks` [2](#0-1)  — it does not mutate `self`, so nothing learned while validating transaction *i* is visible when validating transaction *i+1* in the same call.

Only after the entire batch has been validated does the second pass run `self.lock_accounts(keys)` for every transaction that is still `Ok` [3](#0-2)  . `lock_accounts` unconditionally increments the write/read counters with no conflict re-check [4](#0-3)  `can_write_lock`/`can_read_lock` are only consulted in the first pass, never in the second [5](#0-4)  .

Concretely: if a batch contains transaction A writing account `X` and transaction B also writing account `X`, and `X` is not already locked from a prior, already-completed batch, then in the validation pass both A and B see `can_write_lock(X) == true` (since `self.write_locks` has not yet been touched for `X`) and both remain `Ok`. In the locking pass, `lock_write(X)` is called twice, incrementing `write_locks[X]` from 0 to 2, and both transactions are returned as `Ok(())` from `try_lock_transaction_batch`. This directly violates the invariant that account locks prevent conflicting transactions from executing concurrently, since callers treat an `Ok` result as "safe to dispatch for execution."

I was not able to fully trace, within the available tool budget, whether every call site of `Accounts::lock_accounts` (in `accounts-db/src/accounts.rs`) pre-filters batches so that no two transactions in a single call ever reference the same writable/readable account (e.g., via scheduler-side conflict partitioning). If such external filtering exists and is airtight for every caller, this bug would be unreachable in practice; if any caller can pass a raw, unfiltered batch of sanitized-but-conflicting transactions (as an unprivileged submitter fully controls transaction content and account references, only bounded by sanitization, not by inter-transaction account overlap), the bug is directly reachable and produces the described double-lock outcome. This uncertainty is called out because I could not inspect `accounts-db/src/accounts.rs` call sites for `try_lock_transaction_batch`/`lock_accounts` before running out of iterations.

### Impact Explanation
If reachable with attacker-controlled batches, this breaks the core account-locking invariant that Agave's execution pipeline depends on for safe parallel transaction execution: two transactions that both write (or write/read) the same account could be dispatched for concurrent execution, causing data races on account state, non-deterministic execution results, and potential consensus-breaking divergence between validators (different threads executing the conflicting transactions in different relative orders). This falls under "invalid recorded block / verification bypass" category in scope, since it directly corrupts the safety guarantee that account locks are supposed to enforce.

### Likelihood Explanation
Exploitability hinges entirely on whether any code path allows an attacker to get sanitized transactions with overlapping writable accounts into a single `try_lock_transaction_batch` call. The `account_locks.rs` code itself has no defense against this scenario — the bug is unconditional and would trigger any time such a batch is submitted. I could not confirm from the available context whether upstream callers guarantee non-overlapping batches, so likelihood is uncertain and depends on further verification of `accounts-db/src/accounts.rs` and scheduler call sites.

### Recommendation
Merge the validate and lock phases into a single sequential pass: for each transaction in the batch, atomically check `can_lock_accounts` against the *current* `self` state and, if it passes, immediately call `lock_accounts` before moving to the next transaction, so that intra-batch conflicts are detected using up-to-date lock state (restoring the original check-and-lock-per-transaction semantics rather than validate-all-then-lock-all).

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (test module)
#[test]
fn test_try_lock_transaction_batch_detects_intra_batch_conflict() {
    let mut locks = AccountLocks::default();
    let x = Pubkey::new_unique();

    // Two transactions in the SAME batch both write account `x`.
    let tx_a_keys = vec![(&x, true)];
    let tx_b_keys = vec![(&x, true)];

    let batch: Vec<TransactionResult<_>> = vec![
        Ok(tx_a_keys.into_iter()),
        Ok(tx_b_keys.into_iter()),
    ];

    let results = locks.try_lock_transaction_batch(batch);

    // Invariant: at most one of two conflicting writers in the same batch
    // may succeed.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert!(
        ok_count <= 1,
        "both conflicting writers were locked Ok: write_locks[x] = {:?}",
        locks.is_locked_write(&x)
    );
}
```
Expected: with the current implementation, both results are `Ok(())` and `write_locks[x]` ends up with an internal count of 2, failing the `ok_count <= 1` assertion — demonstrating the double-lock. A property/fuzz variant would generate random batches of `(Pubkey, bool)` account-lock sets with intentional overlaps and assert, for every pair of `Ok` results in the batch, that their read/write account sets are conflict-free (no write/write or write/read intersection).

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    fn lock_accounts<'a>(&mut self, keys: impl Iterator<Item = (&'a Pubkey, bool)>) {
        for (key, writable) in keys {
            if writable {
                self.lock_write(key);
            } else {
                self.lock_readonly(key);
            }
        }
    }

    fn can_read_lock(&self, key: &Pubkey) -> bool {
        // If the key is not write-locked, it can be read-locked
        !self.is_locked_write(key)
    }

    fn can_write_lock(&self, key: &Pubkey) -> bool {
        // If the key is not read-locked or write-locked, it can be write-locked
