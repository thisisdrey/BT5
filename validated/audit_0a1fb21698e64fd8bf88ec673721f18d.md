### Title
Sandwich-attack MEV extraction on `ExchangeInjectContract` liquidity provision due to missing slippage/minimum-output protection - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
TRON's on-chain Bancor-style AMM ("Exchange"/`ExchangeV2Store`) lets any account inject liquidity into a token pair pool via a broadcastable `ExchangeInjectContract` transaction, analogous to `addLiquidity` in the Vader report. Unlike the paired swap operation (`ExchangeTransactionContract`), which carries a user-supplied `expected` minimum-output field enforced during validation, the inject contract carries no minimum/expected counterpart-token amount, so a liquidity provider has no on-chain way to bound how much of the paired asset they will be charged.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` [1](#0-0) . In contrast, `ExchangeTransactionContract` (the swap operation) additionally carries an `expected` field [2](#0-1) , which is validated against the pool-computed output before a swap is allowed to execute: `anotherTokenQuant < tokenExpected` throws `ContractValidateException` [3](#0-2) .

`ExchangeInjectActuator`, however, computes the paired-token amount required from the injector purely from the pool's *current* reserve ratio at validation/execution time, with no user-imposed bound: `anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)` [4](#0-3) , and the same ratio-based computation is repeated in `execute()` against on-chain state at block-application time [5](#0-4) . There is no check anywhere in `doValidate()` bounding `anotherTokenQuant` to a caller-specified maximum, only a lower bound of `> 0` and a global `balanceLimit` cap [6](#0-5) .

A witness (block producer) ordering transactions within its own block, or any account able to get its own `ExchangeTransactionContract` swap included immediately before a victim's `ExchangeInjectContract` in the same block, can shift the pool ratio (`firstTokenBalance`/`secondTokenBalance`) right before the victim's inject executes. Because the victim's signed transaction only fixes `token_id`/`quant` and has no `expected`/max bound on `anotherTokenQuant`, the victim is forced to deposit an unfavorable, attacker-manipulated ratio of the paired asset — donating value to the manipulated pool state, which the attacker then recovers by reversing the swap afterward (classic sandwich pattern), extracting the injected value as MEV. This is the same root cause identified in the referenced Vader `addLiquidity` finding: the paired asset amount for a liquidity deposit is derived from spot reserves at execution time with no slippage protection.

### Impact Explanation
An attacker (or block-producing witness with ordering power) can extract value from any account that submits `ExchangeInjectContract` transactions to `ExchangeV2Store` pools, resulting in an unauthorized transfer of value from the victim's deposited assets into the attacker's/manipulator's control — a concrete theft-of-funds impact via unbacked/unfavorable pool state exploitation. This satisfies "unauthorized account operation / theft of funds" reachable purely through signed transactions (`ExchangeInjectContract` + `ExchangeTransactionContract`), with no privileged role required beyond controlling transaction ordering (which any account attempting front-running within mempool/witness block assembly, or a colluding/self-witness, can influence).

### Likelihood Explanation
Medium likelihood: exploitation requires either (a) collusion with, or control by, a block-producing witness able to order transactions within a single block, since java-tron blocks are produced by a fixed super-representative rather than an open mempool auction like Ethereum, or (b) favorable mempool positioning across adjacent blocks combined with pool illiquidity. This mirrors the original finding's judged medium-risk determination, and the underlying design flaw (ratio-derived paired-token amount without a slippage bound) is unconditionally present for every `ExchangeInjectContract` transaction regardless of attacker capability.

### Recommendation
Add a `expected`-style field to `ExchangeInjectContract` (analogous to `ExchangeTransactionContract.expected`) allowing the caller to specify a maximum acceptable `anotherTokenQuant`, and enforce it in `ExchangeInjectActuator.doValidate()` right after `anotherTokenQuant` is computed, rejecting the transaction if the required paired-token amount exceeds the caller's specified bound — mirroring the existing check at `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java:219-221`.

### Proof of Concept
1. Victim broadcasts `ExchangeInjectContract` intending to inject `quant` of `token_id` into `exchange_id`, expecting the current pool ratio to determine `anotherTokenQuant` as computed in `ExchangeInjectActuator.doValidate()` [7](#0-6) .
2. Before the victim's transaction is applied, an attacker/witness includes an `ExchangeTransactionContract` swap that shifts `firstTokenBalance`/`secondTokenBalance` unfavorably for the upcoming injection (no protection exists against this ordering since inject has no `expected` bound, unlike the swap contract which does [8](#0-7) ).
3. The victim's `ExchangeInjectContract` executes against the manipulated reserves, recomputing `anotherTokenQuant` from the skewed ratio in `execute()` [5](#0-4) , causing the victim to deposit more of the valuable asset than intended.
4. The attacker reverses their initial swap with a second `ExchangeTransactionContract`, restoring the ratio and extracting the value donated by the victim's unfavorable injection, completing the sandwich.
