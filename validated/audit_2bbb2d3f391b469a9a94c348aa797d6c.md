### Title
Operator.execute delegates the caller's identity to arbitrary contracts — a malicious contract invoked in the batch can act as the victim across all SynthContext contracts - (File: contracts/Operator.sol)

### Summary
`Operator.execute` stores the caller's address in a transient slot and `SynthContext._msgSender()` treats any call made while that slot is set as authenticated by that caller. Because `execute` performs arbitrary calls to arbitrary targets, any contract invoked inside the batch inherits the victim's identity and can freely act as the victim in `Pool`, `DepositToken`, `DebtToken`, and `SyntheticToken`. This is the direct analog of the reported bug: an "authority" (the resolved `msg.sender`) is allowed to be a program account, and the invoked program can abuse that authority.

### Finding Description
`Operator.execute` sets `MSG_SENDER_STORAGE = msg.sender`, then calls `functionCallWithValue` on each attacker-influenced `target` supplied in `calls_` [1](#0-0) . `SynthContext._msgSender()` returns `getActualMsgSender()` whenever `msg.sender == operator`, with no restriction on which contract is being called or what code runs while the slot is populated [2](#0-1) .

Concretely, when a user batches calls via `Operator.execute` and any `Call.target` is an attacker-controlled contract (a malicious token, router, airdrop, or a compromised/upgradeable dependency), that contract can call any Synth protocol contract during the same transaction and be seen as the victim. For example it can call `SyntheticToken.transfer(attacker, victimBalance)` or `DepositToken.transfer(attacker, ...)`, since those functions debit `_msgSender()` — which resolves to the victim — and the malicious callee chooses `to`.

The `nonReentrant` guard on `execute` only protects the `Operator` contract itself [3](#0-2) ; `ReentrancyGuardTransient` on `Pool`/`DepositToken` is per-contract and does not fire on fresh entry. The `setMsgSender` modifier clears the slot only after all calls complete, so every nested call inside the batch runs under the victim identity.

### Impact Explanation
Direct theft of user funds: any ERC-20-style token using `SynthContext` (synthetic tokens, deposit tokens) can be transferred out of the victim's account; the attacker contract can also burn/repay or otherwise mutate the victim's positions (e.g., `DebtToken.repay`, `Pool.liquidate`-adjacent flows) under the victim identity.

### Likelihood Explanation
`Operator` exists precisely so users batch arbitrary calls, so arbitrary external code executing under the user's identity is the normal mode of operation — no privileged role, oracle manipulation, or admin action is required. Exploitation requires the victim's batch to include a call to attacker-controlled code (malicious token/router in the batch), which is realistic given multicall usage patterns and the fact that `execute` places no restriction on `target`.

### Recommendation
Restrict `execute` to calls against an allowlist of protocol targets, or require each `Call` to carry the user's explicit authorization (e.g., signed intent per call). At minimum, do not keep the ambient `MSG_SENDER` authority active while calling arbitrary external contracts — scope the trusted sender to calls into known protocol contracts only, or have `SynthContext._msgSender()` reject the delegation when the immediate caller is not an expected protocol contract.

### Proof of Concept
Hardhat sketch:

```solidity
contract Evil {
    function pwn(IDepositToken dt, address to) external {
        // Called via Operator.execute while MSG_SENDER = victim
        dt.transfer(to, dt.balanceOf(_victim())); // _victim resolved via dt._msgSender()
    }
}

// test
IOperator.Call[] memory calls = new IOperator.Call[](1);
calls[0] = IOperator.Call({
    target: address(evil),
    value: 0,
    callData: abi.encodeCall(Evil.pwn, (depositToken, attacker))
});
vm.prank(victim);
operator.execute(calls); // victim batch contains evil call

assertEq(depositToken.balanceOf(victim), 0);
assertGt(depositToken.balanceOf(attacker), 0);
```

Steps: deploy `Evil`, have `victim` hold deposit tokens, call `Operator.execute` from `victim` with a batch containing `Evil.pwn`. Inside `pwn`, `DepositToken.transfer` resolves `_msgSender()` → `Operator.getActualMsgSender()` → `victim`, so the transfer debits `victim` without any signature or allowance.

    function _msgSender() internal view virtual override returns (address) {
        IPoolRegistry _poolRegistry = poolRegistry();
        if (address(_poolRegistry) != address(0)) {
            IOperator _operator = _poolRegistry.operator();
            if (msg.sender == address(_operator)) {
                return _operator.getActualMsgSender();
            }
        }

        return msg.sender;
    }
