Found a concrete, reachable division-by-zero / unguarded-float-division analog in `RepositoryImpl.calculateGlobalEnergyLimit`, which is invoked from TVM opcodes that check delegatable/spendable energy for *every* contract call.

### Title
Division by Zero / Silent-Infinity Energy Limit in `RepositoryImpl.calculateGlobalEnergyLimit` when `totalEnergyWeight` is 0 - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit(AccountCapsule)` divides by `totalEnergyWeight` with only a Java `assert` as a guard. Java assertions are disabled by default in production JVMs (no `-ea` flag), so if `totalEnergyWeight` is `0`, the assert is a no-op and the code proceeds to divide by zero.

### Finding Description [1](#0-0) 

```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
  long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
  if (frozeBalance < TRX_PRECISION) {
    return 0;
  }
  long energyWeight = frozeBalance / TRX_PRECISION;
  long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
  long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

  assert totalEnergyWeight > 0;

  if (hardenResourceCalculation()) {
    return BigInteger.valueOf(energyWeight)
        .multiply(BigInteger.valueOf(totalEnergyLimit))
        .divide(BigInteger.valueOf(totalEnergyWeight))
        .longValueExact();
  }
  return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
```
Unlike the sibling method `EnergyProcessor.calculateGlobalEnergyLimit`, this `RepositoryImpl` copy has **no** explicit `if (totalEnergyWeight <= 0) return 0;` check at all — the only guard is the disabled `assert`. There are two divergent failure modes once `totalEnergyWeight == 0`:
- Hardened path (`hardenResourceCalculation()` true, i.e. `ALLOW_HARDEN_RESOURCE_CALCULATION` proposal enabled): `BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException`, confirmed by the repo's own test [2](#0-1) , which asserts an `ArithmeticException` is thrown for `totalEnergyWeight = 1` overflow (a related but distinct case) — an uncaught `ArithmeticException` propagating from inside VM resource accounting can abort contract execution paths that don't expect it.
- Legacy path (`hardenResourceCalculation()` false, the default since `ALLOW_HARDEN_RESOURCE_CALCULATION` defaults to `0`) [3](#0-2) : `(double) totalEnergyLimit / 0` does **not** throw in Java — it evaluates to `Double.POSITIVE_INFINITY`. `energyWeight * Infinity` cast back to `long` yields `Long.MAX_VALUE`, i.e. the caller is granted an effectively unlimited energy budget.

`totalEnergyWeight` is the network-wide sum of all frozen-for-energy stake, tracked via `DynamicPropertiesStore` and adjusted on freeze/unfreeze of energy resources. The `EnergyProcessor` variant of this same computation guards this with `if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) return 0;` else falls to the same unguarded `assert` [4](#0-3) , which itself only fully protects the zero case when the `ALLOW_NEW_REWARD` proposal (#67) is active; `RepositoryImpl`'s copy has no such conditional check whatsoever.

### Impact Explanation
If `totalEnergyWeight` reaches zero (e.g. private/consortium chain in early bootstrap before any energy is frozen, chain state corruption, or a future refactor of freeze/unfreeze accounting that decrements the counter to 0), then:
- In the legacy (non-hardened) mode, any account with `frozenBalanceForEnergy >= TRX_PRECISION` obtains `Long.MAX_VALUE` of usable energy — an unbacked/unlimited resource grant that lets a caller execute unlimited free TVM computation, i.e. an "unbacked balance" style resource-accounting break reachable from ordinary contract calls that consult `RepositoryImpl.calculateGlobalEnergyLimit`.
- In the hardened mode, the uncaught `ArithmeticException` can propagate out of VM repository code during transaction processing, which is a `node crash / DoS`-class outcome if not caught by the calling actuator.

### Likelihood Explanation
Requires `totalEnergyWeight == 0`, which is unlikely on a long-running mainnet with existing frozen stake, but is realistically reachable on newly bootstrapped or private/consortium java-tron networks before any `FreezeBalance(V2)` for energy has occurred, and the guard that exists in the sibling `EnergyProcessor` implementation (gated behind `allowNewReward()`) is entirely absent here, making this strictly weaker than the parallel code path. Given the divergence between the two near-duplicate implementations of the same formula, this looks like an unintentional gap rather than a deliberately accepted risk.

### Recommendation
Add an explicit, unconditional guard before the division in `RepositoryImpl.calculateGlobalEnergyLimit` (and align it with `EnergyProcessor`'s implementation), e.g.:
```java
if (totalEnergyWeight <= 0) {
  return 0;
}
```
placed before the `assert` and before both the BigInteger and double division branches, so behavior is deterministic in production builds (where `assert` is compiled out) regardless of `allowNewReward()`/`hardenResourceCalculation()` state.

### Proof of Concept
1. Deploy/operate a java-tron network (or reach a state) where `DynamicPropertiesStore.getTotalEnergyWeight()` returns `0` (e.g., fresh private chain before any `FreezeBalanceV2Contract` for `ENERGY` is broadcast, so `totalEnergyWeight` was never incremented from its default).
2. Freeze `>= TRX_PRECISION` (1,000,000 sun) of balance for energy on an account so `frozeBalance >= TRX_PRECISION`.
3. Trigger a smart contract call from that account; the runtime path invokes `RepositoryImpl.calculateGlobalEnergyLimit` for resource accounting.
4. With `ALLOW_HARDEN_RESOURCE_CALCULATION` unset (default `0`), observe the returned energy limit is `Long.MAX_VALUE` (via `(double) totalEnergyLimit / 0 == Infinity` cast to `long`), granting unlimited energy despite `totalEnergyLimit`/`totalEnergyWeight` being finite — confirmable by unit-testing `calculateGlobalEnergyLimit` directly with `saveTotalEnergyWeight(0)` as done in the existing test harness pattern [5](#0-4) .
5. With `ALLOW_HARDEN_RESOURCE_CALCULATION` set to `1`, the same call throws `ArithmeticException` from `BigInteger.divide(BigInteger.ZERO)`, propagating out of VM repository logic.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
