### Title
Unhealthy accounts can evade pending liquidations by front-running with `transfer_to_new_account` - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The `transfer_to_new_account` / `transfer_to_new_account_pda` instructions let an account authority move an entire `lending_account` (all collateral and liability positions) to a brand-new `MarginfiAccount` under a new authority, while disabling the old account. This instruction performs no health/liquidatability check on the source account, so an under-collateralized borrower can front-run a pending liquidation transaction (which targets the old account's pubkey) by migrating their position out from under it, causing the liquidation to fail — directly analogous to the UMA "sponsors can delay liquidations via position transfer" bug class.

### Finding Description
`transfer_to_new_account` only validates: the protocol is not paused, the old account is not frozen, the signer is authorized, the account is not in flashloan/receivership/order-execution, that it has no active orders, and that it has not already been migrated. [1](#0-0) 

Critically, there is no check that the account is healthy, nor any check against `check_pre_liquidation_condition_and_get_account_health` or any risk-engine health validation — unlike `start_liquidation`, which explicitly requires the account to be eligible (unhealthy) and unlike deposits/borrows which trigger `check_account_init_health`. The account state (all balances/shares) is copied verbatim to the new account and the old account is zeroed and flagged `ACCOUNT_DISABLED`: [2](#0-1) 

Liquidations in marginfi are triggered against a specific account pubkey, either via the direct permissionless `lending_account_liquidate` instruction (which loads `liquidatee_marginfi_account` by key) or via the receivership `start_liquidation`/`end_liquidation` flow keyed to a `liquidation_record` tied to a specific `marginfi_account`. [3](#0-2) [4](#0-3) 

Because `transfer_to_new_account` requires only the account authority's signature (no cooldown, no delay, no health gate), a sponsor who sees a liquidation transaction targeting their under-collateralized account in the mempool can submit `transfer_to_new_account` first. This zeroes out and disables the targeted account before the liquidator's transaction lands, causing the pending liquidation (`lending_account_liquidate` or `start_liquidation`) to fail — since the account either has no positions left to liquidate or is now `ACCOUNT_DISABLED`. The debt and collateral simply move, unchanged, to a fresh account under an address the same authority still controls (or an entirely new authority they designate), which the protocol and liquidators must then re-discover and re-target from scratch. This is functionally identical to the UMA "position transfer to escape liquidation" bug: the transfer instruction is not delayed or gated in any way analogous to slow withdrawal requests.

### Impact Explanation
Repeated use of this technique lets an insolvent or near-insolvent borrower indefinitely delay liquidation by hopping their position to new accounts each time a liquidation attempt is imminent, keeping bad debt un-liquidated on-chain for extended periods. This directly threatens protocol solvency: interest keeps accruing on the liability while collateral value may continue falling, increasing the eventual bad debt that must be socialized via the insurance fund/bankruptcy mechanism (`lending_pool_handle_bankruptcy`). This is a concrete insolvency/bad-debt risk rather than a theoretical one, since liquidation is the only automated backstop against under-collateralization in marginfi's accounting model.

### Likelihood Explanation
The transfer instruction is fully permissionless to the account authority, costs only a small flat SOL fee, and requires no special conditions beyond the account not being frozen, in flashloan/receivership, or having open orders — none of which apply to a normal under-collateralized (but not yet in receivership) account. A borrower or a bot watching the mempool for liquidation transactions targeting their account can reliably front-run with this transfer, making the attack straightforward and repeatable at low cost.

### Recommendation
Gate `transfer_to_new_account`/`transfer_to_new_account_pda` behind a health check (reject if the account is currently liquidatable, i.e., maintenance health < 0), or introduce a time-delay/cooldown on transfers analogous to the delay applied to slow withdrawal requests, so that a pending liquidation cannot be trivially evaded by migrating the position moments before execution. Alternatively, require that a liquidation-eligible account cannot transfer at all until it is fully healthy or has passed through liquidation/bankruptcy.

### Proof of Concept
1. Attacker deposits collateral and borrows against it via a normal `MarginfiAccount` A, then price moves against them so that A becomes unhealthy (maintenance health < 0), making it eligible for `lending_account_liquidate` / `start_liquidation`.
2. A liquidator observes this and submits a `lending_account_liquidate` (or `start_liquidation`) transaction targeting account A.
3. Before that transaction lands, the attacker submits `transfer_to_new_account` (self-signed, only their own authorization required) with `old_marginfi_account = A`, moving the full `lending_account` (collateral + liability shares) to fresh account B and setting `A.account_flags |= ACCOUNT_DISABLED`, `A.lending_account = zeroed`. [5](#0-4) 
4. The liquidator's transaction against A now fails (no positions/health issue to act on, or account disabled).
5. Repeat steps 1–4 with account B as needed, indefinitely delaying liquidation while risk to the protocol accumulates.

```rust
fn initialize_migrated_account(
    new_account: &mut MarginfiAccount,
    old_account: &MarginfiAccount,
    new_authority: Pubkey,
    current_timestamp: u64,
    old_account_key: Pubkey,
) {
    new_account.initialize(old_account.group, new_authority, current_timestamp);
    new_account.lending_account = old_account.lending_account;
    new_account.emissions_destination_account = old_account.emissions_destination_account;
    new_account.account_flags = old_account.account_flags;
    new_account.migrated_from = old_account_key;
    new_account.indexer_flags = old_account.indexer_flags;
    new_account.sync_indexer_flags();
}

fn finalize_migrated_old_account(
    old_account: &mut MarginfiAccount,
    new_account_key: Pubkey,
    current_timestamp: u64,
) {
    old_account.migrated_to = new_account_key;
    old_account.last_update = current_timestamp;
    old_account.lending_account = LendingAccount::zeroed();
    old_account.set_flag(ACCOUNT_DISABLED, true);
    old_account.sync_indexer_flags();
}
```

```rust
pub fn transfer_to_new_account(ctx: Context<TransferToNewAccount>) -> MarginfiResult {
    // Validate the global fee wallet and claim a nominal fee
    let group = ctx.accounts.group.load()?;
    check_eq!(
        ctx.accounts.global_fee_wallet.key(),
        group.fee_state_cache.global_fee_wallet,
        MarginfiError::InvalidFeeAta
    );
    anchor_lang::system_program::transfer(ctx.accounts.transfer_fee(), ACCOUNT_TRANSFER_FEE)?;

    let mut old_account = ctx.accounts.old_marginfi_account.load_mut()?;

    check!(
        !old_account.get_flag(ACCOUNT_IN_FLASHLOAN),
        MarginfiError::AccountInFlashloan
    );

    check!(
        !old_account.get_flag(ACCOUNT_IN_RECEIVERSHIP),
        MarginfiError::ForbiddenIx
    );

    check!(
        !old_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION),
        MarginfiError::ForbiddenIx
    );

    check!(
        old_account.active_orders == 0,
        MarginfiError::IllegalAction,
        "Close all active orders before transfer"
    );

    // Prevent multiple migrations from the same account
    check_eq!(
        old_account.migrated_to,
        Pubkey::default(),
        MarginfiError::AccountAlreadyMigrated
    );

    let mut new_account = ctx.accounts.new_marginfi_account.load_init()?;
    let current_timestamp = Clock::get()?.unix_timestamp as u64;
    initialize_migrated_account(
        &mut new_account,
        &old_account,
        ctx.accounts.new_authority.key(),
        current_timestamp,
        ctx.accounts.old_marginfi_account.key(),
    );

    finalize_migrated_old_account(
        &mut old_account,
        ctx.accounts.new_marginfi_account.key(),
        current_timestamp,
    );
```

```rust
pub fn lending_account_liquidate<'info>(
    mut ctx: Context<'info, LendingAccountLiquidate<'info>>,
    asset_amount: u64,
    liquidatee_accounts: u8,
    liquidator_accounts: u8,
) -> MarginfiResult {
    check!(asset_amount > 0, MarginfiError::ZeroLiquidationAmount);

    check!(
        ctx.accounts.asset_bank.key() != ctx.accounts.liab_bank.key(),
        MarginfiError::SameAssetAndLiabilityBanks
    );

    // Liquidators must repay debts in allowed asset types. A SOL debt can be repaid in any asset. A
    // Staked Collateral debt must be repaid in SOL or staked collateral. A Default asset debt can
    // be repaid in any Default asset or SOL.
    {
        let asset_bank = ctx.accounts.asset_bank.load()?;
        let liab_bank = ctx.accounts.liab_bank.load()?;
        validate_bank_asset_tags(&asset_bank, &liab_bank)?;
        validate_bank_state(&asset_bank, InstructionKind::FailsInPausedState)?;
        validate_bank_state(&liab_bank, InstructionKind::FailsInPausedState)?;

        // Sanity check user/liquidator accounts will not contain positions with mismatching tags
        // after liquidation.
        // * Note: user will be repaid in liab_bank
        let user_acc = ctx.accounts.liquidatee_marginfi_account.load()?;
        validate_asset_tags(&liab_bank, &user_acc)?;
        // * Note: Liquidator repays liab bank, and is paid in asset_bank.
        let liquidator_acc = ctx.accounts.liquidator_marginfi_account.load()?;
        validate_asset_tags(&liab_bank, &liquidator_acc)?;
        validate_asset_tags(&asset_bank, &liquidator_acc)?;

        liquidatee_marginfi_account: liquidatee_marginfi_account_loader,
        group: marginfi_group_loader,
        ..
    } = ctx.accounts;

    let mut liquidator_marginfi_account = liquidator_marginfi_account_loader.load_mut()?;
    let mut liquidatee_marginfi_account = liquidatee_marginfi_account_loader.load_mut()?;
```
