### Title
Exchange creator can be sandwiched during `ExchangeWithdrawContract` due to missing minimum-output protection - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeWithdrawActuator` computes the counterpart token amount (`anotherTokenQuant`) to return to the exchange creator purely from the *current* bancor-style pool balances at execution time, with no user-supplied minimum-acceptable-output parameter to bound slippage, unlike its sibling `ExchangeTransactionActuator`, which does carry an `expected` field for exactly this purpose.

### Finding Description
`ExchangeWithdrawContract` is defined with only `owner_address`, `exchange_id`, `token_id`, `quant` [1](#0-0)  — there is no minimum/expected amount field. Compare this to `ExchangeTransactionContract`, which explicitly adds an `expected` field used to bound the trade's output [2](#0-1) .

In `ExchangeWithdrawActuator.execute()`, the amount of the "another token" returned to the withdrawing exchange creator is derived on-the-fly from the exchange's current `firstTokenBalance`/`secondTokenBalance` (the bancor-curve reserves) at the moment the transaction executes: [3](#0-2) 

`doValidate()` only checks that `anotherTokenQuant` is non-zero, non-negative, and within a fixed 0.01% precision-rounding tolerance band relative to `tokenQuant` — it never checks against a value chosen by the caller: [4](#0-3) 

Because the reserves (`firstTokenBalance`/`secondTokenBalance`) can be moved arbitrarily within a single block by any account issuing `ExchangeTransactionContract` trades against the same `exchange_id` (via `ExchangeCapsule.transaction(...)`, seen in `ExchangeTransactionActuator.execute()` [5](#0-4) ), an attacker who observes a pending `ExchangeWithdrawContract` transaction in the mempool can front-run it with a large trade that skews the reserve ratio, causing the victim's withdrawal to compute a much smaller `anotherTokenQuant` than the victim expected, and then reverse the trade afterward to capture the difference — a classic sandwich attack. This mirrors the reported DODO `sellShares()` bug class: a liquidity-withdrawal-style operation whose "price" is computed at execution time with no caller-supplied minimum-output bound.

### Impact Explanation
Any account that is the creator of a TRON Exchange (created via `ExchangeCreateContract`, permissionless for any account holding the required TRX/asset) is exposed to this risk whenever it calls `ExchangeWithdrawContract`. Because withdrawal amounts scale with the pool's balances at execution time and the only ownership check is that the caller is the exchange creator [6](#0-5) , this is reachable by any unprivileged broadcaster who happens to control an exchange, and any other unprivileged broadcaster can be the attacker executing the sandwiching trades via ordinary `ExchangeTransactionContract` transactions. The result is a direct, quantifiable loss of asset/TRX value to the withdrawing account — a concrete unauthorized value transfer/theft of funds via price manipulation, matching the severity class of the original report.

### Likelihood Explanation
Exploitation only requires: (1) observing a pending `ExchangeWithdrawContract` transaction (transactions are visible in the mempool before block inclusion), and (2) submitting `ExchangeTransactionContract` transactions before and after it with higher energy/bandwidth priority or in the same block window. No special privilege, contract deployment, or non-broadcastable capability is needed — this is reachable purely through the standard signed-transaction broadcast path (`ExchangeWithdrawActuator`/`ExchangeTransactionActuator`), making likelihood non-trivial for any active exchange.

### Recommendation
Add a caller-supplied minimum-acceptable-output field (analogous to `expected` in `ExchangeTransactionContract`) to `ExchangeWithdrawContract`, and enforce `anotherTokenQuant >= expectedMin` in `ExchangeWithdrawActuator.doValidate()`, so a withdrawing creator can bound their acceptable slippage exactly as trade-callers already can.

### Proof of Concept
1. Alice owns/creates an Exchange with reserves `firstTokenBalance = A`, `secondTokenBalance = B`.
2. Alice broadcasts `ExchangeWithdrawContract{exchangeId, tokenId=first, quant=Q}` expecting `anotherTokenQuant ≈ B*Q/A`.
3. Attacker sees this in the mempool and front-runs with `ExchangeTransactionContract` trades that shift the ratio `B/A` unfavorably (e.g., dumping `firstToken` into the pool to inflate `A` relative to `B`), computed via `ExchangeCapsule.transaction(...)` [5](#0-4) .
4. Alice's withdrawal executes against the skewed reserves in `ExchangeWithdrawActuator.execute()` [7](#0-6) , yielding a much smaller `anotherTokenQuant` than the pre-attack ratio implied, with no field available to her to reject this outcome.
5. Attacker reverses the trade afterward, pocketing the value difference extracted from Alice's withdrawal.
