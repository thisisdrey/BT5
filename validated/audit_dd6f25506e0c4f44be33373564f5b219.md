## Finding: Snowbridge outbound-queue-v2 pays relayer rewards and closes delivery orders regardless of Ethereum-side dispatch outcome

### Title
Delivery-receipt reward payout ignores `DeliveryReceipt.success`, closing `PendingOrder`s and rewarding relayers even when the bridged message failed on Ethereum - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`process_delivery_receipt` decodes a `DeliveryReceipt` (which carries an explicit `success: bool` field decoded straight from Ethereum's `InboundMessageDispatched` event) but never inspects that field before paying the relayer reward and permanently removing the `PendingOrder`. This mirrors the external report's root cause: a field/interface meant to gate a critical follow-up action exists in the data model but is never actually enforced, so the "success path" runs unconditionally even when the underlying operation failed.

### Finding Description
The delivery-receipt flow is:
1. `submit_delivery_receipt` verifies the Ethereum proof/event log via `T::Verifier::verify` and decodes it into a `DeliveryReceipt`. [1](#0-0) 
2. `DeliveryReceipt` is decoded from the `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` Solidity event, which explicitly carries a `success` flag describing whether the dispatched command on Ethereum executed successfully. [2](#0-1) 
3. `process_delivery_receipt` checks only the gateway address and the pending-nonce existence, then unconditionally pays the reward (`register_reward`) and removes the `PendingOrder`: [3](#0-2) 

The `success` field is decoded into the `DeliveryReceipt` struct but is never read anywhere in `process_delivery_receipt` (or elsewhere in the pallet) — it is dead data. There is no branch that skips reward, retries, requeues, or refunds when `success == false`.

This is structurally the same defect class as the GMX report: a piece of state/interface that is supposed to gate whether a settlement action is "really" complete (GMX: callback confirming withdrawal finished; Snowbridge: `success` flag confirming the message actually dispatched correctly on Ethereum) is present in the data model but not wired into the logic that finalizes settlement.

### Impact Explanation
- Reward is paid and the pending order is deleted from `PendingOrders` even for messages whose Ethereum-side execution failed (`success == false`). This is a "duplicate settlement or payout" / "message queues ... must only advance after ... execution ... success" violation called out explicitly in the Polkadot SDK Pivots.
- Once `PendingOrders::remove(nonce)` runs, there is no other on-chain mechanism in this pallet to retry, resubmit, or reconcile the failed command — the bridging operation that failed on Ethereum (e.g., a token unlock/mint/arbitrary command dispatched through the Gateway) is permanently marked as delivered from the parachain's bookkeeping perspective, with no corrective path, which can leave assets or state inconsistent between chains ("permanent... bridge-state lock").
- Because any signed account can call `submit_delivery_receipt` with a valid Ethereum proof (no privileged actor required — this is the intended, permissionless relayer flow), an entirely honest relayer submitting a legitimately failed-execution receipt still collects the full reward while the underlying bridge operation silently fails to complete, and the protocol has no way to detect or resolve that mismatch.

### Likelihood Explanation
This does not require a malicious relayer, validator, or governance actor — it only requires that the Gateway on Ethereum legitimately reports `success: false` for a dispatched command (e.g., an out-of-gas or reverted secondary command execution), which is an expected, non-adversarial occurrence in a cross-chain message-passing system. Any relayer who submits the resulting valid proof triggers the flawed unconditional payout/removal path.

### Recommendation
Check `receipt.success` in `process_delivery_receipt` before finalizing settlement:
- On `success == true`: proceed as today (pay reward, remove order).
- On `success == false`: do not silently close the order as fully settled. At minimum, emit a distinct event (e.g., `MessageDeliveryFailed`) and consider whether reward should still be paid for relaying, but the pending order/settlement bookkeeping should reflect that the underlying command did not succeed, and any recovery/retry mechanism should be engaged rather than treating it identically to success.

### Proof of Concept
1. Attacker/relayer (unprivileged, honest) relays a message to Ethereum; the Gateway dispatches the enclosed command but the command's execution reverts internally, so the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
2. Relayer builds an `EventProof` for this log and calls `submit_delivery_receipt`. [1](#0-0) 
3. `DeliveryReceipt::try_from` decodes `success: false` into the receipt struct. [4](#0-3) 
4. `process_delivery_receipt` ignores `receipt.success`, pays `order.fee` to the reward account, and removes `PendingOrders[nonce]`, emitting `MessageDelivered { nonce }` as if the operation fully succeeded. [5](#0-4) 
5. Existing tests (`submit_delivery_receipt_succeeds_after_unhalt`, `invalid_nonce_for_delivery_receipt_fails`) only assert on gateway/nonce/halted checks; none construct a `success: false` receipt to verify differing behavior, confirming the code path is untested for this case. [6](#0-5)

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}

// After governance resumes the bridge, legitimate delivery receipts flow through again:
// the order is paid out and removed from storage.
#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
}
