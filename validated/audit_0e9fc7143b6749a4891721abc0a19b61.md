## Analysis

The strongest applicable analog in this codebase is in Gitaly's concurrency-limiting middleware (the RPC-handler resource-limit gate), which contains the same "protective parameter set/left at 0 → protection is entirely disabled" pattern as the Beedle borrower-fee bug.

### Title
Concurrency limiter silently disables *all* per-RPC protection (including queue bounding) when the configured limit is 0 - ([File: internal/limiter/concurrency_limiter.go])

### Summary
`ConcurrencyLimiter.Limit` treats a configured limit of `<= 0` as "unlimited" and bypasses the entire limiting/queueing mechanism, executing the wrapped RPC handler function directly with no bound whatsoever. Because Gitaly's config schema allows (and even defaults to) `max_concurrency`/`max_per_repo` of `0` while still accepting a non-zero `max_queue_size`/`max_queue_wait`, an operator (or the default zero-value config) can end up with an RPC entry that looks protected but provides zero actual protection — mirroring the Beedle case where a protection parameter set to `0` silently strips out the entire safety mechanism instead of just one component of it.

### Finding Description
`ConcurrencyLimiter.Limit` starts with: [1](#0-0) 

If `c.currentLimit() <= 0`, the function immediately calls `f()` and returns — completely skipping acquisition of the per-key concurrency semaphore and the queue-token semaphore. This means when the configured `MaxConcurrency`/`MaxPerRepo` is `0`, not only is concurrency unlimited, but `MaxQueueSize` and `MaxQueueWait` (the safeguards meant to bound in-flight queue memory growth) never even come into play, because `getConcurrencyLimit` — where the queue semaphore is constructed — is never reached: [2](#0-1) 

The config validation explicitly allows `MaxConcurrency`/`MaxPerRepo` of `0` (`GreaterOrEqual(0)`), while requiring `MaxQueueSize` to be `> 0`: [3](#0-2) 

`ConcurrencyLimits.Concurrency()` returns `0` whenever neither `MaxConcurrency` nor `MaxPerRepo` is set: [4](#0-3) 

and `WithConcurrencyLimiters` feeds this value straight into the `AdaptiveLimit`'s `Initial` setting used as `currentLimit()`: [5](#0-4) 

So an operator who configures only `max_queue_size`/`max_queue_wait` for an RPC (a completely plausible, valid configuration per the docs) — intending to bound queued requests while relying on the default concurrency behavior — unintentionally leaves the RPC entirely unprotected: no concurrency cap, no queue cap, no queue-wait timeout. This exactly parallels the Beedle report's core defect: a legitimate, allowed "0" setting for one safety knob (`borrowerFee` / `MaxConcurrency`) causes the *whole* protection mechanism (fee-based economic disincentive / concurrency+queue limiting) to collapse to a no-op rather than degrading gracefully to just "no concurrency cap but the queue bound still applies."

This is directly reachable by ordinary users: any Git operation (clone/fetch/push) that maps to an RPC configured this way, or to an RPC relying on the default zero-value concurrency config, can be sent in unbounded parallel volume by any client, exhausting Gitaly's goroutines, file descriptors, and I/O — a DoS of the RPC handler resource-limiting subsystem itself, which is the explicit purpose of this file (`doc/backpressure.md`): [6](#0-5) 

### Impact Explanation
An operator who believes an RPC is bounded (because they set `max_queue_size`/`max_queue_wait`) actually gets zero protection if `max_per_repo`/`max_concurrency` is left at its zero default. Any client (internal service, gitlab-shell, workhorse, or a user with repository access) can then issue unbounded concurrent calls to that RPC for a given repository, exhausting Gitaly node resources (goroutines, memory, disk I/O) and degrading or blocking service for all other legitimate operations on that node — a full denial-of-service of the resource-limiting mechanism that Gitaly relies on as "primary backpressure."

### Likelihood Explanation
Likelihood is moderate-to-high: this requires no privileged access, no leaked token, and no malicious peer — only a configuration that is explicitly valid per `ConcurrencyLimits.Validate()` (zero `MaxConcurrency`/`MaxPerRepo` with a set `MaxQueueSize`) or simply relying on defaults where these fields aren't configured. Given the example config in `config.toml.example` only shows `max_per_repo`/`max_queue_wait`/`max_queue_size` together as an example but does not warn that omitting `max_per_repo` nullifies the other two settings, this is a realistic operator footgun. [7](#0-6) 

### Recommendation
Decouple the "unlimited concurrency" short-circuit from the queueing mechanism: when `currentLimit() <= 0` but `maxQueueLength > 0` (or `maxQueueWait > 0`), still enforce the queue-based bounds rather than bypassing the limiter entirely. Alternatively, treat `MaxConcurrency <= 0` combined with a configured `MaxQueueSize` as a configuration error during `Validate()`, forcing operators to be explicit about "fully unlimited" (omit all fields) versus "queue-bounded but concurrency-unbounded" (which arguably should not be permitted as an option since it defeats the purpose of `MaxQueueSize`).

### Proof of Concept
1. Configure Gitaly with:
```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_queue_size = 5
max_queue_wait = "10s"
```
(no `max_per_repo`/`max_concurrency` set — a valid config per `Validate()`).
2. `WithConcurrencyLimiters` computes `Initial: concurrency.Concurrency()` = `0` since neither field is set.
3. `ConcurrencyLimiter.Limit` for this RPC evaluates `c.currentLimit() <= 0` as true on every call and executes `f()` directly, never touching the queue/`max_queue_size` logic at all.
4. An attacker sends an arbitrarily large number of concurrent `PostUploadPackWithSidechannel` (clone/fetch) requests against the same repository; none are queued or rejected, exhausting Gitaly resources and blocking legitimate clone/fetch operations for other users on that node.

```go
// getConcurrencyLimit retrieves the concurrency limit for the given key. If no such limiter exists
// it will be lazily constructed.
func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}
```

```go
	}
	return c.MaxPerRepo
```

```markdown
# Request limiting in Gitaly

In the GitLab ecosystem, Gitaly is the service that is at the bottom of the
stack for Git data access. This means that when there is a surge of
requests to retrieve or change a piece of Git data, the I/O happens in Gitaly.
This can lead to Gitaly being overwhelmed due to system resource exhaustion
because all Git access goes through Gitaly.

If there is a surge of traffic beyond what Gitaly can handle, Gitaly should
be able to push back on the client calling. Gitaly shouldn't subserviently agree
to process more than it can handle.
```
