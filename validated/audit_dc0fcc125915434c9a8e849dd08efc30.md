### Title
Unbounded reference updates per `UpdateReferences` RPC stream enable resource-exhaustion DoS - (File: internal/gitaly/service/ref/update_references.go)

### Summary
The external report's bug class is "unbounded, attacker-controlled repeated fields processed in a loop with no upper bound, causing DoS/resource exhaustion." In Gitaly, the `UpdateReferences` RPC accepts a client-streamed sequence of messages, each carrying an unbounded `repeated Update updates` field, and the server queues every single update into a long-lived `git update-ref --stdin` process with no cap on the total number of updates or stream messages before a single `Commit()` call.

### Finding Description
`RefService.UpdateReferences` is implemented in [1](#0-0) : after validating the repository once, it starts a `git update-ref --stdin` process via `updateref.New`/`Start()` and then loops forever over incoming stream messages.

For every message, it iterates `request.GetUpdates()` — a `repeated Update` field defined without any size limit in the proto ( [2](#0-1) ) — validating each reference name/OID and calling `updater.Update(...)` for each one, then reads the next stream message and repeats until `io.EOF`: [3](#0-2) .

Each `Update()` call writes directly into the `git-update-ref` subprocess's stdin pipe (`u.write(...)` via `fmt.Fprintf(u.cmd, ...)`), and no queuing limit or count check exists in `internal/git/updateref/updateref.go` (`Update`, `write`) either: [4](#0-3) [5](#0-4) . All queued commands accumulate as pending state inside the single long-running `update-ref` process until `Commit()` finally sends the `commit` command: [6](#0-5) .

There is no maximum on:
- the number of `Update` messages per gRPC stream call, or
- the number of `updates` entries per message, or
- the total accumulated updates before commit.

An authenticated client with repository-mutation access to this `MUTATOR` RPC (reachable the same way any ordinary Gitaly client/GitLab Rails caller can invoke ref-update RPCs) can send an arbitrarily large number of stream messages, each with an arbitrarily large `updates` array, causing Gitaly to: hold open a `git update-ref` process for the duration; keep growing memory/pipe buffers for every queued command; and, when it reaches `Commit()`, force `git-update-ref` to lock and process an enormous number of references atomically in one transaction. This directly mirrors the reported smart-contract analog where unbounded `tokenIds`/`collectors` arrays, processed without an upper bound, blow up gas/resource cost per call and can prevent the operation from ever completing successfully.

### Impact Explanation
A crafted `UpdateReferences` call with a very large number of ref updates can cause excessive CPU/memory/lock time on the Gitaly node while `git-update-ref` processes/locks all references, and can starve other requests to the same repository (reference locks are typically per-repository or per-reftable). Because there is no limit, a single client-controlled call can degrade or deny service for legitimate operations against the targeted repository, which is a DoS impact analogous to the reported gas-exhaustion/DoS concern in the smart-contract audit.

### Likelihood Explanation
Any authenticated caller permitted to invoke repository-mutating RPCs (the normal path for pushes/ref updates from GitLab Rails or direct gRPC clients with repo access) can trigger this without any special privilege — they only need to construct a stream with a large number of `Update` entries, which is a straightforward, unprivileged, crafted-RPC-field scenario as required by the validation rules.

### Recommendation
Introduce explicit upper bounds in `UpdateReferences`:
- Reject requests/streams whose cumulative number of `updates` exceeds a configured maximum (return `structerr.NewInvalidArgument` similar to the existing empty-updates check at [7](#0-6) ).
- Optionally bound total accumulated payload size/queued command count in `updateref.Updater` itself, so the underlying `git-update-ref` transaction cannot grow unbounded regardless of caller.
- Ensure the limit is enforced incrementally (per received message) rather than only after buffering everything, to avoid the resource cost being paid before rejection.

### Proof of Concept
1. Open a `RefService.UpdateReferences` gRPC stream against a repository the attacker has mutate access to.
2. Send an initial message with a valid `repository` and a very large `updates` array (e.g., hundreds of thousands of no-op or benign create/delete entries referencing distinct ref names).
3. Continue sending additional stream messages with further large `updates` arrays before closing the stream (EOF).
4. Observe that the server accepts and queues all entries into the `git-update-ref --stdin` process (per `internal/gitaly/service/ref/update_references.go` lines 47-97 and `internal/git/updateref/updateref.go` lines 384-396) with no rejection, consuming server memory/CPU and holding the process/lock open until `Commit()` — which for a sufficiently large payload will take excessive time or resources on the Gitaly node, degrading service for that repository.

func (s *server) UpdateReferences(server gitalypb.RefService_UpdateReferencesServer) error {
	ctx := server.Context()

	request, err := server.Recv()
	if err != nil {
		return fmt.Errorf("receiving initial request: %w", err)
	}

	if err := s.locator.ValidateRepository(ctx, request.GetRepository()); err != nil {
		return err
	}
	repo := s.localRepoFactory.Build(request.GetRepository())

	objectHash, err := repo.ObjectHash(ctx)
	if err != nil {
		return fmt.Errorf("detecting object hash: %w", err)
	}

	// Unset the repository so that we can more easily verify inside of the loop that all incoming requests
	// ain't got a repository set anymore.
	request.Repository = nil

	updater, err := updateref.New(ctx, repo)
	if err != nil {
		return fmt.Errorf("creating updater: %w", err)
	}

	if err := updater.Start(); err != nil {
		return fmt.Errorf("starting updater: %w", err)
	}

// Update commands the reference to be updated to point at the object ID specified in newOID. If
// newOID is the zero OID, then the branch will be deleted. If oldOID is a non-empty string, then
// the reference will only be updated if its current value matches the old value. If the old value
// is the zero OID, then the branch must not exist.
//
// A reference transaction must be started before calling Update.
func (u *Updater) Update(reference git.ReferenceName, newOID, oldOID git.ObjectID) error {
	if err := u.expectState(stateStarted); err != nil {
		return err
	}

	return u.write("update %s\x00%s\x00%s\x00", reference.String(), newOID, oldOID)
}

// Commit applies the commands specified in other calls to the Updater. Commit finishes the
// reference transaction and another one must be started before further changes can be staged.
func (u *Updater) Commit() error {
	// Commit can be called without preparing the transactions.
	if err := u.checkState(statePrepared); err != nil {
		if err := u.expectState(stateStarted); err != nil {
			return err
		}
	}

	u.state = stateIdle

	if err := u.setState("commit"); err != nil {
		return err
	}

	return nil
}
