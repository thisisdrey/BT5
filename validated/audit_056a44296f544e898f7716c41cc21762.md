### Title
Attacker can drain backing value by executing oracle-priced swaps at two different prices in the same transaction - ([File: contracts/Pool.sol])

### Summary
`Pool.swap` burns `syntheticTokenIn_` and mints `syntheticTokenOut_` at whatever price `masterOracle().quote()` returns at the moment of the call, with no same-block/same-transaction price consistency check. Metronome's deployed configuration uses pull oracles (Pyth on mainnet, RedStone-style pull provider on Hemi) whose price updates are permissionless — anyone can call `pyth.updatePriceFeeds` / `pullPriceProvider.updatePrice`, and the E2E tests themselves batch such updates inside `Operator.execute` (`test/E2E.mainnet.next.test.ts:948-960`, `test/E2E.hemi.pullOracle.test.ts:152-159`). A pull oracle can legitimately hold several signed updates with different prices inside its staleness window, so an attacker can push price A, act, push price B, and act again — all in one transaction.

### Finding Description
`swap()` in `contracts/Pool.sol:642-671` performs no slippage protection beyond the optional `swapFees` and quotes atomically via `quoteSwapOut` (`contracts/Pool.sol:508-525`), which calls `masterOracle().quote(syntheticTokenIn_, syntheticTokenOut_, amountIn_)`. There is no mechanism pinning one price per block/tx. The attacker contract (or `Operator.execute` batch) does:

1. Call the pull oracle's permissionless update with the signed update giving the lower price for `syntheticTokenOut_` (e.g., msETH cheap vs msUSD).
2. `pool.swap(msUSD, msETH, amountIn)` — receives more msETH than fair value.
3. Update the oracle again with a signed update giving the higher msETH price.
4. `pool.swap(msETH, msUSD, amountOut)` — receives more msUSD than originally burned.

Both swaps merely burn and mint synthetics; the excess minted synths are claims on the same collateral pool, diluting all other synth/debt holders and LPs. The same primitive applies to `DebtToken.issue`/`repay` and `DepositToken.deposit`/`withdraw` valuations via `Pool.debtPositionOf`, and to `SmartFarmingManager.leverage` quotes, but `swap` is the cleanest surface since it directly mints unbacked value twice at inconsistent prices. No modifier stops this: `swap` is `whenNotShutdown nonReentrant` only, and `SynthContext._msgSender`/Operator paths preserve an attacker-controlled caller.

### Impact Explanation
Each round-trip mints more synthetic value than it burns, i.e., creates synths not backed by any deposit — protocol insolvency borne by LPs and other synth holders. Profit is bounded by the price gap between two valid oracle updates minus `swapFees` twice; since the fee path is conditional (`if (_swapFee > 0)` at `contracts/Pool.sol:488,521`), pairs with zero or low configured fee, or volatile assets where the inter-update gap exceeds the fee, are exploitable. Repeating across blocks compounds the drain.

### Likelihood Explanation
Requires a swap-active pool (`isSwapActive`) with a synth pair priced by a pull oracle that accepts multiple signed updates in one block — the deployed mainnet/Base/Optimism/Hemi configuration. The attacker needs capital in `syntheticTokenIn_` (obtainable via `DebtToken.issue` against their own collateral or flash-acquired synths) and signed oracle updates, both unprivileged. Profitability per iteration is modest because of swap fees, matching the medium severity of the original Flat Money finding.

### Recommendation
Pin oracle prices per block/transaction — e.g., cache `price`/`block.number` in `MasterOracle` or `PoolRegistry` on first read and reuse it for all subsequent reads in the same block, or record `block.number` of the last accepted oracle update and revert any `swap`/`issue`/`liquidate` when the oracle was updated earlier in the same block by a different caller than the current transaction initiator. At minimum, enforce a non-zero `swapFee` and slippage bounds (`amountOutMin`) on `swap`.

### Proof of Concept
Foundry fork sketch (mainnet pool where Pyth is the pull oracle):

```solidity
function test_sameTxTwoPrices() public {
    // attacker holds msUSD (issued against own collateral)
    bytes[] memory lowUpdate  = pyth.getUpdateData(msETHFeed, t1); // lower msETH price
    bytes[] memory highUpdate = pyth.getUpdateData(msETHFeed, t2); // higher msETH price, t2 > t1

    uint256 msUsdBefore = msUSD.balanceOf(attacker);

    vm.startPrank(attacker);
    pyth.updatePriceFeeds{value: fee}(lowUpdate);          // push low msETH price
    (uint256 msEthOut,) = pool.swap(msUSD, msETH, msUsdBefore); // buy msETH cheap

    pyth.updatePriceFeeds{value: fee}(highUpdate);         // push high msETH price
    (uint256 msUsdOut,) = pool.swap(msETH, msUSD, msEthOut);    // sell msETH dear
    vm.stopPrank();

    assertGt(msUsdOut, msUsdBefore); // unbacked msUSD minted; holders diluted
}
```

For a Hardhat repro, reuse the `Operator.execute` batching pattern from `test/E2E.mainnet.next.test.ts:948-960` to sequence `updatePriceFeeds → swap → updatePriceFeeds → swap` in a single transaction.
