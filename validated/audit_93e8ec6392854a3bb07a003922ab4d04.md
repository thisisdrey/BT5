### Title
Unauthenticated Backup Service with Unbounded State Scan Causes Validator I/O Exhaustion via SSRF or Misconfigured Binding - (File: storage/backup/backup-service/src/handlers/mod.rs)

### Summary

The Aptos node embeds an HTTP backup service (`aptos-backup-service`) that exposes multiple unauthenticated GET endpoints on port 6186. The `GET /state_snapshot/<version>` endpoint hardcodes `usize::MAX` as the iteration limit, unconditionally scanning the entire AptosDB state (hundreds of millions of entries on mainnet) per request. The `GET /transactions/<start>/<num>` and `GET /state_snapshot_chunk/<version>/<start>/<limit>` endpoints accept attacker-controlled `usize` parameters with no server-side cap. The service has no authentication, no rate limiting, and no concurrency control. Production deployment configs (Helm charts, Pangu fixtures) bind the service to `0.0.0.0:6186`, making it directly reachable. Even when bound to `127.0.0.1:6186` (the code default), it is reachable via SSRF from any co-located web application.

### Finding Description

**Root cause — hardcoded unbounded scan in `state_snapshot` handler:** [1](#0-0) 

The handler calls `bh.get_state_item_iter(version, 0, usize::MAX)`. There is no per-request limit, no concurrency semaphore, and no authentication gate anywhere in the handler chain.

**Root cause — attacker-controlled `num_transactions` with no cap:** [2](#0-1) 

`num_transactions` is parsed directly from the URL as a `usize` and forwarded to `bh.get_transaction_iter(start_version, num_transactions)` with no upper-bound check.

**Root cause — attacker-controlled `limit` in `state_snapshot_chunk` with no cap:** [3](#0-2) 

**No authentication anywhere in the service:** [4](#0-3) 

`start_backup_service` calls `warp::serve(routes).bind(address)` with no middleware for authentication, rate limiting, or IP allowlisting.

**Default binding is localhost, but production configs expose `0.0.0.0:6186`:** [5](#0-4) 

Default is `127.0.0.1:6186`. However, the Helm chart base configs and Pangu fixtures override this: [6](#0-5) [7](#0-6) 

The Helm fullnode base config similarly sets `0.0.0.0:6186`. These are the configs used for actual node deployments.

**The backup service is started unconditionally on every node:** [8](#0-7) 

**Contrast with AdminService, which enforces authentication on mainnet:** [9](#0-8) [10](#0-9) 

The `AdminService` explicitly rejects unauthenticated requests on mainnet. The backup service has no equivalent guard.

**Exploit path:**

1. Attacker identifies a validator or fullnode with `backup_service_address: "0.0.0.0:6186"` (Helm/Pangu deployment), or finds an SSRF in a co-located web application to reach `127.0.0.1:6186`.
2. Attacker sends repeated `GET /state_snapshot/<latest_committed_version>` requests.
3. Each request causes the node to iterate the entire state KV store (hundreds of millions of entries on mainnet) via `get_state_item_iter(version, 0, usize::MAX)`, spawning a blocking thread per request via `tokio::task::spawn_blocking`.
4. Concurrent requests saturate the blocking thread pool, exhaust RocksDB I/O bandwidth, and starve the consensus/execution path of I/O resources.
5. The validator falls behind on block production, risks being jailed or slashed.

### Impact Explanation

A single `GET /state_snapshot/<version>` request on a mainnet node triggers a full scan of the state database with no bound. Multiple concurrent requests (the service has no concurrency limit) can saturate the node's I/O and CPU, causing validator slowdown or crash. This maps to the allowed impact: "validator slowdown … reachable from unprivileged repository entrypoints with concrete mainnet impact." The `transactions` and `state_snapshot_chunk` endpoints additionally accept attacker-controlled `usize` parameters that can be set to `usize::MAX` (18446744073709551615), causing the iterator to attempt to walk the entire ledger history.

### Likelihood Explanation

- Nodes deployed via the official Helm charts or Pangu fixtures have `backup_service_address: "0.0.0.0:6186"`, making the service directly reachable without SSRF.
- Even with the default `127.0.0.1:6186`, any SSRF in a co-located service (monitoring dashboard, indexer, etc.) reaches the backup service.
- No authentication, no rate limiting, no concurrency control — a single HTTP GET is sufficient to trigger the unbounded scan.

### Recommendation

1. **Add authentication** to the backup service, mirroring the `AdminService` pattern (passcode SHA-256 or mTLS).
2. **Remove the hardcoded `usize::MAX`** in the `state_snapshot` handler; require the caller to supply an explicit chunk size and enforce a server-side maximum.
3. **Add a server-side cap** on `num_transactions` and `limit` parameters (e.g., `min(caller_limit, MAX_BACKUP_CHUNK_SIZE)`).
4. **Add a concurrency semaphore** to limit simultaneous backup requests.
5. **Change the default binding** back to `127.0.0.1:6186` in all deployment configs and document that exposing it on `0.0.0.0` requires explicit operator intent and network-level controls.

### Proof of Concept

```bash
# Assuming backup service is reachable (0.0.0.0:6186 or via SSRF to 127.0.0.1:6186)
# Get the latest committed version from the db_state endpoint (no auth required):
LATEST_VERSION=$(curl -s http://<node_ip>:6186/db_state | python3 -c \
  "import sys,bcs; d=bcs.deserialize(sys.stdin.buffer.read(), ...); print(d.committed_version)")

# Trigger unbounded full-state scan (usize::MAX hardcoded server-side):
# Each request spawns a blocking thread scanning hundreds of millions of state entries
for i in $(seq 1 20); do
  curl -s "http://<node_ip>:6186/state_snapshot/$LATEST_VERSION" > /dev/null &
done

# Or trigger unbounded transaction scan with attacker-controlled num_transactions:
curl -s "http://<node_ip>:6186/transactions/0/18446744073709551615" > /dev/null
```

Twenty concurrent requests to `/state_snapshot/<version>` will saturate the node's RocksDB I/O and blocking thread pool, causing the validator to stall on consensus duties.

pub fn start_backup_service(
    address: SocketAddr,
    db: Arc<AptosDB>,
    num_runtime_threads: Option<usize>,
) -> Runtime {
    let backup_handler = db.get_backup_handler();
    let routes = get_routes(backup_handler);

    let runtime = aptos_runtimes::spawn_named_runtime("backup".into(), num_runtime_threads);

    // Ensure that we actually bind to the socket first before spawning the
    // server tasks. This helps in tests to prevent races where a client attempts
    // to make a request before the server task is actually listening on the
    // socket.
    //
    // Note: we need to enter the runtime context first to actually bind, since
    //       tokio TcpListener can only be bound inside a tokio context.
    let _guard = runtime.enter();
    let server = warp::serve(routes).bind(address);
    runtime.handle().spawn(server);
    info!("Backup service spawned.");
    runtime
}
