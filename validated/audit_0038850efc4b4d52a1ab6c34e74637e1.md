### Title
Revoking all StackerDB signer authorizations via the smart contract does not invalidate previously-authorized signers' write permits - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` deliberately skips applying a new signer configuration to the local StackerDB replica whenever the newly-fetched signer list is empty. This means that when a StackerDB-controlling smart contract legitimately revokes all previously-authorized signers (e.g. to deauthorize a signer set, akin to revoking a permit), the node's persisted per-slot signer authorization (used to authenticate every future chunk write) is never cleared. Any peer that possessed a previously-valid signer key can continue signing and pushing chunks that the node will accept as authentic, exactly mirroring the reported bug class: "no way to invalidate previously issued permits."

### Finding Description
`StackerDBConfig::from_smart_contract` reads the authorized `(signer, num_slots)` list straight from the controlling contract via `stackerdb-get-signer-slots` [1](#0-0) . This is the mechanism by which the contract "issues" or revokes StackerDB write permits per signer/slot.

When the node periodically calls `create_or_reconfigure_stackerdbs` to reload this authorization set from chain state, it only actually rewrites the local per-slot signer bindings when the new config differs *and* is non-empty: [2](#0-1) 

If the contract's new signer list becomes empty (a legitimate way for a contract to revoke/deauthorize all current signers), the `!new_config.signers.is_empty()` guard is false, so `reconfigure_stackerdb` is never called. Crucially, the in-memory `stacker_db_configs` map is still updated with the new (empty) config at the end of the loop (`new_stackerdb_configs.insert(...)`) regardless of whether the DB replica was actually reconfigured, creating a divergence between the "high-level" advertised config and the actual persisted per-slot authorization table.

The persisted per-slot authorization comes from the `chunks` table's `signer` column, populated at `create_stackerdb` time and only updated by `reconfigure_stackerdb` [3](#0-2) . Both the p2p chunk-validation path and the write path authenticate against this persisted signer, not against the live `stacker_db_configs`:

- P2P received-chunk validation calls `self.stackerdbs.get_slot_signer(...)` and then `slot_metadata.verify(&addr)` against that stored signer [4](#0-3) .
- `get_slot_signer` reads directly from the `chunks` table [5](#0-4) .

Because `reconfigure_stackerdb` was skipped when the new signer list was empty, this stored `signer` value is never cleared, so the network-facing chunk-validation and write paths keep authenticating chunks signed by the old, now-revoked, private key.

### Impact Explanation
This allows an unauthenticated/unauthorized write to persist in a distributed, replicated state store (StackerDB) after the smart-contract-level authorization has been revoked. A previously-authorized peer's signature — which should now be treated as unauthorized/"revoked" — continues to be accepted by `validate_received_chunk` (used both for `StackerDBGetChunkData` pull sync and for the unsolicited `StackerDBPushChunk` p2p message path) and propagated across the network, effectively allowing forged/stale-permission data to be written to StackerDB and gossiped node-wide. This matches the "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" Critical impact categories.

### Likelihood Explanation
The path is fully remote and requires only possession of a signer key that was valid at *some* point before the contract emptied its signer list — no privileged access to any other party's key or to the node is required. The triggering condition (contract legitimately transitioning its authorized signer set to empty) is a realistic operational action (e.g., pausing/decommissioning a signer set), and the guard exists explicitly in the reconfiguration code (with a comment referencing bug #5142) to protect against clobbering valid configs on transient failures — but this same protection also silently blocks legitimate full-revocation reconfigurations.

### Recommendation
Distinguish between "failed to load config" (which should indeed fall back to `noop()`/preserve prior state) and "successfully loaded an intentionally-empty signer list from the contract." Only the former should suppress `reconfigure_stackerdb`; the latter must always propagate to the persisted slot-signer table so that revoked signers are immediately wiped, analogous to adding an explicit nonce/version-based revocation mechanism as recommended in the referenced report.

### Proof of Concept
1. Deploy/observe a StackerDB-controlling contract with `stackerdb-get-signer-slots` initially returning a non-empty signer list including `signer_A`.
2. `signer_A` signs and pushes valid chunks; the node stores them with `chunks.signer = signer_A` (via `create_stackerdb`).
3. The contract owner calls into the contract to change `stackerdb-get-signer-slots` to return an empty list (revoking all signers).
4. Node runs `refresh_stacker_db_configs` → `create_or_reconfigure_stackerdbs`; because `new_config.signers.is_empty()`, the `reconfigure_stackerdb` call is skipped (see the boolean guard in `stackerdb/mod.rs` lines 414-428), leaving `chunks.signer` unchanged as `signer_A`.
5. `signer_A` (now supposedly revoked) signs and pushes/gossips a new chunk with an incremented version. `validate_received_chunk`/`get_slot_signer` still returns `signer_A`, `slot_metadata.verify` succeeds, and the chunk is accepted and relayed network-wide — despite the contract's intent to revoke `signer_A`'s permission entirely.

        slot_id: u32,
    ) -> Result<Option<StacksAddress>, net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
