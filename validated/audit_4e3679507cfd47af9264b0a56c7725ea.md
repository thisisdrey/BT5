### Title
Peer-controlled `remoteIndexId` allows silent hijack of `HostMap.RemoteIndexes` mapping - (File: `hostmap_manager.go` / `hostmap.go`)

### Summary
The report's bug class is "multiple/ambiguous state entries keyed by an attacker-influenced value, allowing manipulation of history/state lookups." The closest reachable analog in Nebula is `HostMap.RemoteIndexes`, a map keyed by `remoteIndexId` — a 32-bit value that is *supplied by the remote peer* during the handshake (`result.RemoteIndex` in `handshake_manager.go`) rather than generated and deduplicated locally the way `localIndexId` is (via `generateIndex` + collision-checking in `allocateIndex`/`CheckAndComplete`). Because nothing prevents a peer from choosing (or a malicious peer from replaying/colluding to reach) a `remoteIndexId` that collides with an already-registered entry for a different host, the code path that adds a new `HostInfo` to the main hostmap only *logs* the collision and then overwrites the map entry.

### Finding Description
`HandshakeManager.CheckAndComplete` and `HandshakeManager.Complete` both look up `hm.mainHostMap.RemoteIndexes[hostinfo.remoteIndexId]` before insertion: [1](#0-0) [2](#0-1) 

In both cases, if an existing entry is found for a *different* `vpnAddrs`/hostinfo, the code does nothing but log `"New host shadows existing host remoteIndex"` and proceeds to call `unlockedAddHostInfo`, which unconditionally overwrites the map slot: [3](#0-2) 

Unlike `localIndexId` — which is generated locally via `generateIndex` and explicitly checked for uniqueness across both the pending (`hm.indexes`) and main (`hm.mainHostMap.Indexes`) maps in `allocateIndex`/`CheckAndComplete` (returning `ErrLocalIndexCollision` on conflict) — `remoteIndexId` is accepted verbatim from the peer's handshake message and is never deduplicated; the collision path is treated as an expected, tolerable event ("this can happen since we can't control the remote ID"). This means `HostMap.RemoteIndexes` — one of the hostmap's core lookup structures — can hold at most one authoritative entry per `remoteIndexId`, yet the value space is chosen by an untrusted third party, giving a "one written key can point to different peers over time" property analogous to the reported one-to-many `fromBlock` ambiguity: a lookup by that key does not reliably identify a unique, correct peer/session state.

### Impact Explanation
`RemoteIndexes` is consulted via `HostMap.QueryReverseIndex`, used elsewhere in the hostmap/relay bookkeeping flows (`outside.go`) to resolve a peer's self-reported index back to a `HostInfo`. If an attacker completes (or replays) a handshake advertising a `remoteIndexId` that matches an index already used by a legitimate, unrelated peer's session, the newer hostinfo silently supersedes the mapping for that key. Any code path relying on `RemoteIndexes`/`QueryReverseIndex` to resolve state for the original session can now be pointed at the attacker's `HostInfo` instead, which is a remote state-poisoning primitive directly analogous to the reported "shadow past state from queries" impact — here it shadows a live peer/session-state entry keyed by an attacker-chosen index rather than a block-number-keyed history record. It does not require the attacker to possess a CA-signed certificate different from a normal peer's; it only requires ordinary handshake participation with a chosen 32-bit RemoteIndex value.

### Likelihood Explanation
Likelihood is moderate: `generateIndex` selects indexes pseudo-randomly, so a chance collision across the full uint32 space is unlikely, but the attacker fully controls the value they advertise as their own local index in the handshake, and no local uniqueness constraint is enforced on `remoteIndexId` before it is written into `RemoteIndexes`. Repeated handshake attempts (or targeted guessing after observing another session's traffic pattern/index disclosure, e.g., via `renderHostmap`/debug output or packet header inspection since indexes are sent in cleartext handshake/message headers) make deliberate collision practical without needing any cryptographic break.

### Recommendation
Treat `RemoteIndexes` insertion with the same rigor as `localIndexId`: when a collision is detected in `CheckAndComplete`/`Complete` against a *different* `vpnAddrs`, do not silently overwrite the mapping. Only replace the old `RemoteIndexes` entry once it is provably obsolete (e.g., the old entry's hostinfo has been independently verified as stale/removed), and ensure any consumer of `QueryReverseIndex` re-validates the returned `HostInfo` against the calling context (certificate/vpn address) rather than trusting the index-based lookup alone, mirroring the recommended fix pattern from the original report (never let a newly observed key silently displace the authoritative record for a distinct entity).

### Proof of Concept
Conceptual PoC (not executable without lab access to the repo/build):
1. Peer A completes a legitimate handshake with Node N, receiving `localIndexId = X` on N's side and registering `N.RemoteIndexes[X] = HostInfo_A`.
2. Attacker B initiates (or replays) a handshake with N, crafting/choosing (via the handshake machine's `IndexAllocator`-equivalent local index selection on B's side, which N cannot see or constrain) a self-reported index equal to `X`.
3. N's `HandshakeManager.CheckAndComplete` sees `existingRemoteIndex.vpnAddrs[0] != hostinfo.vpnAddrs[0]`, logs the shadow warning, and calls `unlockedAddHostInfo`, which sets `N.RemoteIndexes[X] = HostInfo_B`, discarding the pointer to `HostInfo_A`.
4. Any subsequent logic that resolves state via `QueryReverseIndex(X)` on N now returns `HostInfo_B` instead of `HostInfo_A`, silently swapping session-state resolution for that index. [4](#0-3) [5](#0-4) [6](#0-5)

func (hm *HostMap) QueryReverseIndex(index uint32) *HostInfo {
	hm.RLock()
	if h, ok := hm.RemoteIndexes[index]; ok {
		hm.RUnlock()
		return h
	} else {
		hm.RUnlock()
		return nil
	}
}

// unlockedAddHostInfo assumes you have a write-lock and will add a hostinfo object to the hostmap Indexes and RemoteIndexes maps.
// If an entry exists for the Hosts table (vpnIp -> hostinfo) then the provided hostinfo will be made primary
func (hm *HostMap) unlockedAddHostInfo(hostinfo *HostInfo, f *Interface) {
	if f.dnsServer != nil {
		remoteCert := hostinfo.ConnectionState.peerCert
		f.dnsServer.Add(remoteCert.Certificate.Name()+".", hostinfo.vpnAddrs)
	}
	for _, addr := range hostinfo.vpnAddrs {
		hm.unlockedInnerAddHostInfo(addr, hostinfo, f)
	}

	hm.Indexes[hostinfo.localIndexId] = hostinfo
	hm.RemoteIndexes[hostinfo.remoteIndexId] = hostinfo
