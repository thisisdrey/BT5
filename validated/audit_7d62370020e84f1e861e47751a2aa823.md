### Title
`auth_call` permanently burns wNEAR balance when `near_withdraw`/`do_auth_call` fails - ([File: contracts/defuse/src/contract/intents/state.rs])

### Summary
`Contract::auth_call` synchronously debits `auth_call.attached_deposit` of wNEAR from the signer's `token_balances` via `self.withdraw(...)` *before* scheduling the `near_withdraw` promise and the `do_auth_call` callback. If `near_withdraw` fails (e.g. wNEAR contract paused, insufficient contract-side liquidity, or gas exhaustion), `do_auth_call` panics on `require!(promise_result_checked_void(0).is_ok(), "near_withdraw failed")`, and unlike every other withdraw path in the contract (`ft_resolve_withdraw`, `resolve_deposit_internal`), there is no resolver that re-credits the signer. The debited wNEAR balance is permanently frozen inside the Verifier with no corresponding NEAR ever forwarded to `on_auth`.

### Finding Description
Binding claimed: `debited(signer_id.token_balances[wNEAR]) == attached_deposit forwarded to on_auth`. 

Trace:
1. `Contract::auth_call` (state.rs) calls `self.withdraw(signer_id, [(wnear_token_id, deposit)], ..)`, which synchronously runs `Contract::withdraw` (contracts/defuse/src/contract/tokens/mod.rs) performing `owner.token_balances.sub(token_id, amount)` and `total_supplies.sub(...)`. This state change is committed as part of the current receipt's execution and is **not** contingent on any later promise outcome. [1](#0-0) [2](#0-1) 
2. It then schedules `ext_wnear::near_withdraw(...)` followed by `.then(Self::ext(current_account_id).do_auth_call(signer_id, auth_call))`. [3](#0-2) 
3. `do_auth_call` only checks `promise_result_checked_void(0).is_ok()` via `require!`; on failure it panics, aborting the promise chain, but there is no `*_resolve_*` callback anywhere to re-credit the signer's balance. [4](#0-3) 

Contrast with `internal_ft_withdraw` (nep141 withdraw.rs), which uses the identical `withdraw → near_withdraw → do_ft_withdraw` pattern but always additionally chains `ft_resolve_withdraw`, which computes `used`/`refund` from the *final* promise result and calls `self.deposit(sender_id, [(token, refund)], ...)` to restore any amount that failed to transfer. [5](#0-4)  `auth_call`'s flow has no equivalent resolver — `do_auth_call`'s `require!` is a dead end: on failure it simply panics without any refund path, freezing the previously-debited balance forever.

Attacker payload: sign `AuthCall { contract_id: <any_contract>, attached_deposit: NearToken::from_yoctonear(N), msg }` while holding `>= N` wNEAR balance in the Verifier, then trigger a condition under which `near_withdraw` fails (wNEAR contract paused by its own admin, wNEAR contract lacking sufficient NEAR reserves, or gas/receipt failure). Since `auth_call` itself is only reachable via signed intents (an intent authorizes it), and NEAR promise-chain failures are entirely feasible without any privileged actor (the wNEAR contract being paused, out of gas, or its own resource limits are external triggers, not requiring a Role holder in *this* contract), the attacker's own funds become permanently locked. This is a "signer's own funds frozen" case matching the Critical category "user funds permanently frozen".

### Impact Explanation
The signer's wNEAR balance recorded in the Verifier's `token_balances` is debited unconditionally and irreversibly whenever the promise chain fails after the synchronous `withdraw()` call, with no compensating credit anywhere in the codebase. This is not attacker-vs-victim value extraction (the attacker only harms themselves in the simplest exploit), but it does violate the equality invariant (`amount debited == amount actually forwarded to on_auth`), and any account (not just the attacker's) that calls `auth_call` with `attached_deposit > 0` under a failing `near_withdraw` condition would suffer permanent, unrecoverable loss of Verifier-custodied wNEAR — with no way to reclaim it since the balance record is gone and no NEAR was released to compensate. This matches "user funds permanently frozen" (Critical).

### Likelihood Explanation
The trigger condition (`near_withdraw` failing) is outside the attacker's unilateral control in the general case (requires wNEAR contract to be paused or insufficient reserves), but is externally observable/triggerable in principle (e.g., during any period the deployed wNEAR contract is paused, upgraded, or receipt gas runs out under specific network congestion). No privileged role, DAO action, or victim key is required — only ordinary use of `auth_call` by any signer holding wNEAR balance. However, because the failure condition depends on the wNEAR token contract's own state (outside this repo's control) rather than something the attacker can deterministically force from `intents--024`, reliable weaponization against a third party (rather than self-loss) is limited; it is more of a structural resiliency gap.

### Recommendation
Add a resolver callback analogous to `ft_resolve_withdraw` for the `auth_call` flow: chain a `#[private]` `resolve_auth_call` after `do_auth_call`'s dependent promise (or restructure so `do_auth_call` re-credits the signer via `self.deposit(...)` before panicking, rather than using a bare `require!` that aborts without refund) when `near_withdraw` fails.

        token_amounts: impl IntoIterator<Item = (TokenId, u128)>,

        force: bool,

        let owner = self

            .accounts
            .get_mut(owner_id)
            .ok_or_else(|| DefuseError::AccountNotFound(owner_id.to_owned()))?
            .get_mut_maybe_forced(force)
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;

        let mut burn_event = MtBurnEvent {
            owner_id: Cow::Owned(owner_id.to_owned()),
            authorized_id: None,
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into).map(Into::into),
        };

        for (token_id, amount) in token_amounts {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            burn_event.token_ids.to_mut().push(token_id.to_string());
            burn_event.amounts.to_mut().push(amount);

            owner
                .token_balances
                .sub(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;

            self.storage
                .state
                .total_supplies
                .sub(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

#[near]
impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
}
