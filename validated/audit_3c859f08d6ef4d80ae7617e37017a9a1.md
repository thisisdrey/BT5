### Title
`submit_delivery_receipt` pays and consumes the relayer reward for a nonce without checking `DeliveryReceipt.success`, letting the reward be claimed regardless of whether Ethereum message dispatch actually succeeded - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`Pallet::process_delivery_receipt` in the Snowbridge outbound-queue-v2 pallet pays out the relayer reward and permanently removes the `PendingOrders` entry for a nonce purely on the basis of a verified Ethereum log proof containing `nonce`, `gateway`, and `reward_address` - but it never inspects `DeliveryReceipt.success`, even though that field is decoded from the same event and is explicitly named/intended to represent delivery status. [1](#0-0) 

### Finding Description
The relevant flow:

1. `submit_delivery_receipt` verifies the Ethereum proof (Merkle/beacon proof of the `InboundMessageDispatched` event log) and decodes it into a `DeliveryReceipt { gateway, nonce, topic, success, reward_address }`. [2](#0-1) 

2. `process_delivery_receipt` then:
   - checks `gateway` matches the configured address,
   - resolves the `reward_account`,
   - fetches the `PendingOrders` entry by `nonce`,
   - if `order.fee > 0`, unconditionally calls `T::RewardPayment::register_reward(...)`,
   - unconditionally removes the pending order. [3](#0-2) 

The `success: bool` field decoded straight from the Solidity event (`event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)`) is never read in `process_delivery_receipt`. This is the exact bug-class analog to the C4 report's core defect: a value that should gate settlement (there, `tokensBought != 0`; here, `receipt.success`) is decoded/available but the settlement logic performs the payout and permanently consumes/clears the accounting state (there: repay credit using an attacker-satisfied nonzero check; here: pay + remove `PendingOrders`) without actually verifying the semantic condition the value was meant to encode. Both cases result in "settlement proceeds on an unverified/insufficiently-verified success signal."

Because the Ethereum log itself is attested by a real proof (so an arbitrary attacker cannot fabricate an arbitrary `success` value out of thin air), the severity here is lower than the original Solidity bug, but the underlying invariant violation is structurally identical: **the code never binds settlement to the correctness/success semantics of the delivery it is being paid for.** Any relayer who is aware that a dispatched message failed on the Ethereum/gateway side (e.g. Ethereum-side execution reverted for the OutboundMessage's commands, causing `success = false` in the emitted receipt) can still submit that same failing receipt and be paid the full `order.fee`, and the order is deleted so no other/duplicate handling, retry, or refund/slashing path can ever act on it again.

Existing guards that do NOT stop this:
- `T::Verifier::verify` only proves the log is authentic and included in a valid Ethereum block - it says nothing about whether the encoded `success` is `true`.
- `ensure!(T::GatewayAddress::get() == receipt.gateway, ...)` only checks origin authenticity, not delivery outcome.
- `PendingOrders::get(nonce)` only checks the order exists; it has no separate "already failed"/"needs retry" state machine gated on `success`.

### Impact Explanation
This falls under the "duplicate settlement or payout" / "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" pivot. A relayer reward is unconditionally paid and the pending order permanently removed regardless of whether Ethereum-side execution of the OutboundMessage actually succeeded. This can: (a) drain the BridgeHub-side relayer reward pot for messages that never executed correctly on Ethereum, and (b) permanently destroy the only on-chain state (`PendingOrders`) that could otherwise be used to detect/retry/react to a failed delivery, since the entry is removed unconditionally in the same call that pays the reward.

### Likelihood Explanation
Likelihood is moderate: the attacker does not need to forge any proof - they only need to be an ordinary permissionless relayer who submits `submit_delivery_receipt` for a message whose real-world Ethereum-side dispatch legitimately returned `success = false` (e.g., because gas metering, message content, or downstream contract logic caused the dispatched commands to revert on Ethereum). This is within reach of any relayer monitoring the bridge, requires no malicious node/validator/governance action, and the extrinsic is a public, permissionless, signed call (`ensure_signed(origin)?`) available to anyone.

### Recommendation
Have `process_delivery_receipt` branch on `receipt.success`:
- On `success == true`: pay `order.fee` to `reward_account` and remove the `PendingOrders` entry as today.
- On `success == false`: do not register the relayer reward for successful delivery of a failed execution (or route it into a different, smaller "relaying attempt fee" path if relayers must still be compensated for on-chain gas spent relaying), and only remove/finalize the `PendingOrders` entry in a way that reflects the true delivery state, so downstream logic (retries, slashing, accounting) can observe execution failure. At minimum, emit a distinct event (e.g. `MessageDeliveryFailed`) so success/failure is observable and reconciled, and audit any other consumer of `DeliveryReceipt` to ensure `success` is checked consistently everywhere it's relevant.

### Proof of Concept
1. A message with nonce `N` and `fee = F` is queued via `do_process_message`, creating `PendingOrders[N] = { nonce: N, fee: F, block_number }`.
2. The message is relayed to Ethereum but its dispatched commands revert on execution (e.g., insufficient gas, reentrancy guard, or a malformed/adversarial command payload accepted at ABI-encoding time but rejected at execution time), so the Ethereum Gateway emits `InboundMessageDispatched(nonce=N, topic, success=false, reward_address=R)`.
3. A relayer captures this real, valid event log and its receipt/execution proof (no forgery needed - it is a genuine event) and calls `submit_delivery_receipt(event)`.
4. `T::Verifier::verify` succeeds (proof is valid); `DeliveryReceipt::try_from` decodes `success = false` correctly, but `process_delivery_receipt` at [4](#0-3)  never inspects `success`; it pays `F` to `reward_account` and deletes `PendingOrders[N]`.
5. Result: the relayer is fully rewarded for a message whose Ethereum-side delivery/execution failed, and the pending-order record that would have let anyone detect/react to the failure is now gone - final, unconditional payout occurring on a condition (proof validity) that is weaker than what should gate settlement (proof validity AND `success == true`).

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
