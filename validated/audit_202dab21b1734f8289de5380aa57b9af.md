### Title
Bazel silently executes an attacker-planted `bash`/`patch` executable placed in a fetched (untrusted) repository directory when applying patches on Windows - (File: `tools/build_defs/repo/utils.bzl`, `src/main/native/windows/util.cc`)

### Summary
`tools/build_defs/repo/utils.bzl`'s patch-application helper resolves the shell used to run the patch tool as the bare name `"bash"` (or `"powershell.exe"`) unless `BAZEL_SH`/`BAZEL_POWERSHELL` is set, and runs it with `working_directory` defaulting to the repository root — i.e., the directory that was just populated with attacker-supplied, checksum-pinned archive/VCS content [1](#0-0) [2](#0-1) . On Windows, the process-creation layer (`bazel::windows::WaitableProcess::Create`) only converts an executable argument into a fully-qualified path if it already contains a path separator; a bare name like `"bash"` is left unresolved and passed with `lpApplicationName == nullptr`, while `lpCurrentDirectory` is set to the (attacker-controlled) working directory [3](#0-2) [4](#0-3) . With `lpApplicationName == nullptr`, `CreateProcessW`'s own module-search algorithm applies, which checks the *current directory* before `PATH` — the exact "uncontrolled search path element" class described in CVE-2023-29012 (`doskey.exe` picked up from an untrusted CWD by `git.exe`).

### Finding Description
`_apply_patches` (the shared implementation backing `patch()` used by `http_archive`, `git_repository`, and other Starlark repository rules) computes:

```
bash_exe = ctx.os.environ["BAZEL_SH"] if "BAZEL_SH" in ctx.os.environ else "bash"
...
st = ctx.execute([bash_exe, "-c", command], working_directory = patch_directory or "")
``` [1](#0-0) [5](#0-4) 

`patch_directory` defaults to `None`/`""` when the rule does not set it, which `repository_ctx.execute` treats as the repository's own directory — the same directory the archive/VCS checkout was just extracted into [6](#0-5) . This non-native code path is taken whenever `patch_tool` is explicitly set or `patch_args` contains anything other than `-p<N>`, a supported and common configuration for consumers of third-party patches.

On Windows, `repository_ctx.execute` ultimately reaches `bazel::windows::WaitableProcess::Create`, which:
1. Calls `AsExecutablePathForCreateProcess(argv0, ...)` to try to fully-qualify the executable. For a bare name with **no path separator** (e.g. `"bash"`), the function does nothing to resolve it against `PATH` and returns an **empty `extended_path`**, keeping `quoted_path` as the untouched bare word [3](#0-2) .
2. Calls `CreateProcessW` with `lpApplicationName = extended_path.empty() ? nullptr : ...` (so `nullptr` here) and `lpCurrentDirectory = cwd` (the attacker-populated repo/patch directory) [4](#0-3) .

When `lpApplicationName` is `NULL`, `CreateProcessW` performs its own module search, and per Microsoft documentation that search checks the directory from which the application loaded, then **the current directory of the calling process** (which is set here to `lpCurrentDirectory`), before falling back to `System32`, the Windows directory, and `PATH`. This mirrors exactly the "uncontrolled search path element" defect in Git for Windows (CVE-2023-29012), where an attacker-controlled current working directory shadowed a trusted binary (`doskey.exe`) resolved without an explicit full path.

### Impact Explanation
A malicious/compromised upstream archive or VCS ref (matching the sha256/integrity the victim has pinned, or fetched via an unpinned reference such as `git_repository` without a fixed commit or `new_git_repository`) can ship a file named `bash.exe` (or `bash.com`/`bash.bat`/`bash.cmd`, or `powershell.exe` for the PowerShell branch) at the repository root. When the victim's `http_archive`/`git_repository` invocation applies patches with a non-default `patch_tool`/`patch_args` (a normal, supported configuration), Bazel on Windows will execute the attacker's planted binary instead of the real MSYS/Git bash or system PowerShell, achieving arbitrary code execution in the context of the Bazel repository-fetch phase — with no additional privileges required from the attacker beyond controlling content the build already trusts enough to fetch and patch. The pinned integrity check (sha256/commit) does not prevent this because it validates that the fetched bytes match what the attacker legitimately published; it does not inspect the *contents* of the archive for planted binaries.

### Likelihood Explanation
Requires: (a) Windows host, (b) a repository rule invocation using this Starlark patch-utility code path with `patch_tool` set or non-`-p` `patch_args` (common for teams relying on GNU patch fallback for fuzzy/binary patches), and (c) no `BAZEL_SH`/`BAZEL_POWERSHELL` override pointing to an absolute path (the common default). Given `bash_exe`/`powershell_exe` default to bare names and `patch_directory` defaults to the repo root, the precondition is essentially "attacker controls the archive/repo content and the build uses a non-default patch tool" — a plausible but not universal configuration.

### Recommendation
- In `tools/build_defs/repo/utils.bzl`, resolve `bash_exe`/`powershell_exe` to an absolute path (e.g., via a dedicated PATH search rooted outside the fetched repository, mirroring `blaze::Which`) before invoking `ctx.execute`, rather than passing bare names.
- In `AsExecutablePathForCreateProcess` (`src/main/native/windows/util.cc`), fully resolve bare (separator-less) executable names to an absolute path using a controlled search (excluding the child's working directory) before calling `CreateProcessW`, instead of leaving `lpApplicationName` `NULL` and delegating to the OS's CWD-inclusive search order.

### Proof of Concept
Not fully reproducible from the available static analysis alone: confirming end-to-end exploitability requires validating on Windows that `repository_ctx.execute()`'s Java-to-native plumbing indeed calls `bazel::windows::WaitableProcess::Create` with the unresolved `bash`/`powershell.exe` argv0 and the repository directory as `lpCurrentDirectory` for the `patch_tool`/`patch_cmds_win` code paths (I traced the Starlark call site and the native `CreateProcessW` invocation but could not, within the available tool budget, trace the intermediate Java `Subprocess`/JNI layer connecting `ctx.execute` to `process.cc` in this index). A concrete `src/test/shell/bazel` proof would: create an `http_archive` whose tarball contains a top-level `bash.exe` (a trivial marker-writing stub), reference it with `patches=["//:some.patch"]` and `patch_tool="patch"`, run `bazel fetch`/`bazel build` on Windows, and assert the marker file produced by the attacker's `bash.exe` exists rather than output from the genuine MSYS bash/patch tool.

wstring AsExecutablePathForCreateProcess(wstring path, wstring* quoted_path,
                                         wstring* extended_path) {
  if (path.empty()) {
    return MakeErrorMessage(WSTR(__FILE__), __LINE__,
                            L"AsExecutablePathForCreateProcess", path,
                            L"path should not be empty");
  }
  if (IsSeparator(path[0])) {
    return MakeErrorMessage(WSTR(__FILE__), __LINE__,
                            L"AsExecutablePathForCreateProcess", path,
                            L"path is absolute without a drive letter");
  }
  if (HasSeparator(path) && !HasDriveSpecifierPrefix(path.c_str())) {
    wstring cwd;
    DWORD err;
    if (!GetCwd(&cwd, &err)) {
      return MakeErrorMessage(WSTR(__FILE__), __LINE__,
                              L"AsExecutablePathForCreateProcess", path, err);
    }
    path = cwd + L"\\" + path;
  }
  wstring error = AsShortPath(path, quoted_path);
  if (error.empty()) {
    // Quote the path in case it's something like "c:\foo\app name.exe".
    // Do this unconditionally, there's no harm in quoting. Quotes are not
    // allowed inside paths so we don't need to escape quotes.
    QuotePath(*quoted_path, quoted_path);
    extended_path->clear();
    return L"";
  }
