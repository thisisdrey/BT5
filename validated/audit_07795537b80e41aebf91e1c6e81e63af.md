### Title
Claimed amounts persist across merkle-root updates, so a user whose new-epoch leaf equals or falls below their already-claimed total can never claim the new rewards - (File: contracts/utils/RecurringAirdrop.sol)

### Summary
`RecurringAirdrop.claim` identifies a user's entitlement solely by the leaf `(msg.sender, amount_)` and enforces payout via a cumulative, epoch-independent `claimed[msg.sender]` counter. When the governor rotates `merkleRoot` for a new distribution epoch, `claimed[]` is never namespaced by root or epoch. If a subsequent tree legitimately grants a user an `amount_` that is `<= claimed[msg.sender]` — most naturally when leaves encode per-epoch (non-cumulative) allocations, e.g., a fixed periodic reward identical to a previous one — `amount_ - claimed[msg.sender]` underflows or yields 0 and `claim` reverts. The user permanently loses that epoch's rewards even though they hold a valid Merkle proof. This is the same bug class as the OpenQ report: a claim identifier that fails to distinguish two distinct legitimate claims, causing a later valid claim to be treated as already-satisfied.

### Finding Description
The contract is explicitly designed for *recurring* airdrops via `updateMerkleRoot`, yet claim state is a single monotonically-increasing `claimed` mapping keyed only by `address`: [1](#0-0) 

- Line 55: `_leaf = keccak256(abi.encodePacked(msg.sender, amount_))` — the leaf contains no epoch/root identifier, so the same `(account, amount)` pair in two different epochs produces identical leaves.
- Line 58: `uint256 _claimable = amount_ - claimed[msg.sender]` — if the new epoch's leaf amount is `<= claimed`, this either reverts on underflow (epoch amount < claimed) or hits `NothingToClaim` (equal). Either way the claim is impossible.
- `claimed` is never reset or scoped to `merkleRoot` when `updateMerkleRoot` rotates the tree (lines 81-90), so collision across epochs is guaranteed whenever two distributions give a user overlapping totals.

Nothing enforces that the operator publishes cumulative totals per account, and nothing prevents the natural scenario of equal per-epoch allocations (a fixed stipend, repeated identical reward amounts, or a corrected/reduced allocation). The deployed `MetAirdrop` (deployments/mainnet/MetAirdrop.json at `0x265714B10B9309a8A7A505DBFA6Cb6c39b842309`) inherits this exact `claim` logic and locks rewards into `esMET` via `_transferReward`, so the frozen amount is permanently locked/undistributed MET.

### Impact Explanation
Permanent freezing/theft of unclaimed yield: a user holding a valid Merkle proof for a new epoch cannot receive their rewards because `claimed[]` from prior epochs absorbs the new entitlement. In the worst case (`amount_` decreases), the subtraction underflows and the claim path is bricked; if the allocation is later raised back, only the excess over historical `claimed` is payable, so the skipped epoch's rewards are lost forever — they remain stuck in the contract until governance sweeps them.

### Likelihood Explanation
This requires no attacker action beyond normal use: it triggers whenever a recurring distribution's leaf amount for an account is not strictly greater than that account's lifetime `claimed` total. Repeated identical rewards (a common pattern for periodic airdrops) hit it deterministically on the second epoch if leaves encode per-epoch amounts. The `nonReentrant` guard, `Governable` checks, and merkle proof verification do nothing to prevent it — the revert happens after a fully valid proof.

### Recommendation
Namespace claims per distribution epoch: e.g., `mapping(bytes32 merkleRoot => mapping(address => uint256)) claimed` or `mapping(bytes32 root => mapping(bytes32 leaf => bool))` for per-epoch leaf claims, or include an epoch/index component in the leaf and track `claimed[account][epoch]`. Alternatively, strictly enforce and document cumulative leaf semantics and have `updateMerkleRoot` snapshot/validate monotonicity — though per-epoch namespacing is the robust fix, analogous to adding a `depositId` discriminator to OpenQ's `claimId`.

### Proof of Concept
Foundry test demonstrating that a user with a valid proof for an equal second-epoch allocation can never claim it. Assumes a simple toy merkle setup; in practice generate roots with `merkletreejs` in a Hardhat test against the deployed `MetAirdrop` ABI:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {RecurringAirdrop} from "contracts/utils/RecurringAirdrop.sol";
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract MockMET is ERC20("MET", "MET") {
    constructor() { _mint(msg.sender, 1_000_000e18); }
}

contract RecurringAirdropClaimCollisionTest is Test {
    RecurringAirdrop airdrop;
    MockMET met;
    address alice = address(0xA11CE);
    address governor;

    function setUp() public {
        met = new MockMET();
        airdrop = new RecurringAirdrop(met);
        governor = airdrop.governor();
        met.transfer(address(airdrop), 500_000e18);
    }

    // Single-leaf trees: root == leaf (proof = empty array)
    function testSecondEpochSameAmountUnclaimable() public {
        bytes32[] memory emptyProof = new bytes32[](0);

        // Epoch 1: alice allocated 100 MET (leaf = keccak(alice, 100e18))
        bytes32 leaf1 = keccak256(abi.encodePacked(alice, uint256(100e18)));
        vm.prank(governor);
        airdrop.updateMerkleRoot(leaf1, bytes32("ipfs1"));

        vm.prank(alice);
        airdrop.claim(100e18, emptyProof);
        assertEq(met.balanceOf(alice), 100e18);
        assertEq(airdrop.claimed(alice), 100e18);

        // Epoch 2: alice is again allocated 100 MET for this epoch.
        // The leaf is IDENTICAL because leaf = (account, amount) with no epoch id.
        bytes32 leaf2 = keccak256(abi.encodePacked(alice, uint256(100e18)));
        vm.prank(governor);
        airdrop.updateMerkleRoot(leaf2, bytes32("ipfs2"));

        // Alice has a valid proof for the new root, but:
        vm.prank(alice);
        vm.expectRevert(NothingToClaim.selector); // 100e18 - 100e18 == 0
        airdrop.claim(100e18, emptyProof);

        // If epoch 2 instead encodes a lower amount (e.g. correction to 50),
        // the subtraction underflows and reverts the same way:
        bytes32 leaf3 = keccak256(abi.encodePacked(alice, uint256(50e18)));
        vm.prank(governor);
        airdrop.updateMerkleRoot(leaf3, bytes32("ipfs3"));
        vm.prank(alice);
        vm.expectRevert(); // underflow: 50e18 - 100e18
        airdrop.claim(50e18, emptyProof);

        // Second epoch's 100 MET (and the 50 MET) are permanently stuck
        // in the airdrop contract despite alice holding valid proofs.
    }
}
```

The same flow applies to `MetAirdrop` on mainnet (`claim` → `_transferReward` → `esMET.lockFor`), where the unclaimable rewards remain locked in the contract indefinitely.

```text
    function claim(uint256 amount_, bytes32[] calldata proof_) external nonReentrant {
        if (merkleRoot == bytes32(0)) revert NothingToClaim();

        bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
        if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();

        uint256 _claimable = amount_ - claimed[msg.sender];
        if (_claimable == 0) revert NothingToClaim();

        claimed[msg.sender] += _claimable;

        _transferReward(msg.sender, _claimable);

        emit RewardClaimed(msg.sender, _claimable);
    }
```
