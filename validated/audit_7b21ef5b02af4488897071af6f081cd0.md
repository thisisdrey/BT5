### Title
Deleting an account with a pending `PromiseYield` leaves `PromiseYieldReceipt`/`PromiseYieldStatus`/`PromiseYieldTimeout` state behind, letting the timeout later replay the old owner's action list against a re-created account - (`core/store/src/utils/mod.rs::remove_account`)

### Summary
`remove_account` only purges `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` entries, and `action_delete_account` never checks for outstanding promise-yield state before calling it. If an account self-destructs while it has a pending `PromiseYield` receipt, the `PromiseYieldReceipt`, its `PromiseYieldStatus`, and the queued `PromiseYieldTimeout` entry all survive the deletion. When the same account name is later re-created and the timeout eventually fires, `resolve_promise_yield_timeouts` finds the stale receipt still present and synthesizes a `PromiseResume` that executes the old owner's action list against the new account with `predecessor_id == receiver_id == account_id`.

### Finding Description
An unprivileged account (`victim.near`) deploys a contract and, via a `FunctionCall` action, invokes the `promise_yield_create` host function. On successful execution this writes a `TrieKey::PromiseYieldReceipt` once the yield is processed locally (`runtime/runtime/src/lib.rs:1495-1499`, `set_promise_yield_receipt`) and enqueues a `TrieKey::PromiseYieldTimeout` entry with `expires_at = block_height + yield_timeout_length_in_blocks` (`runtime/runtime/src/function_call.rs:160-169`).

The same account can then submit a `DeleteAccountAction`. `action_delete_account` (`runtime/runtime/src/actions.rs:314-391`) only checks storage-usage size and gas-key burn limits before calling `remove_account`; it performs no check for outstanding promise-yield state. `remove_account` (`core/store/src/utils/mod.rs:505-575`) removes only `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData` - it never touches `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, or the `TrieKey::PromiseYieldTimeout` queue entry, which are separate trie key prefixes not covered by any of `remove_account`'s iteration passes.

Once the account name is free, anyone able to satisfy the normal account-creation rules (top-level via registrar, or sub-account of their own predecessor) can issue `CreateAccountAction` to re-create `victim.near`. When the block height reaches the original `expires_at`, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3104`) walks the still-intact timeout queue, checks `state_update.contains_key(&TrieKey::PromiseYieldReceipt{receiver_id: queue_entry.account_id, data_id})` (`lib.rs:3047-3051`) - which is still true because the receipt was never removed - and synthesizes a `PromiseResume` receipt destined for the (now re-created) account (`lib.rs:3059-3097`).

When that `PromiseResume` is processed, `lib.rs:1500-1562` retrieves the leftover `get_promise_yield_receipt`, removes it, writes `ReceivedData`, and executes `apply_action_receipt` on the original yielded receipt. That receipt carries the action list crafted by the *old* account owner before deletion, and it runs with `predecessor_id == receiver_id == account_id` (self-call trust context), i.e. as if the *new* account owner authorized it. Because the pending PromiseYield/timeout state was never invalidated across the delete/recreate boundary, no signature, nonce, or access-key check from the new owner is ever consulted for these actions.

### Impact Explanation
This is an authorization-escalation bug: the old (deleted) account owner can pre-plant an arbitrary action list (e.g., `AddKey` with a full-access key, `Transfer`, or `FunctionCall`) that executes against whoever later re-creates the same account name, with the full self-call trust level, entirely bypassing the new owner's actual access keys/authorization. This falls under authorization escalation across accounts/promises in the bounty scope.

### Likelihood Explanation
Preconditions are all attacker-reachable with ordinary transactions: deploy a wasm contract, call `promise_yield_create` from it, then submit `DeleteAccountAction` from the same account (a normal, permitted action sequence with no validation against pending yields). The only external dependency is that some party re-creates the exact same account name before the yield timeout fires - straightforward for sub-accounts of the attacker's own namespace, and possible for others if the name is reused. Cost to the attacker is just the price of a `FunctionCall` (yield creation) plus a `DeleteAccountAction`; it is fully repeatable per account name.

### Recommendation
Either (a) have `remove_account` also purge any `PromiseYieldReceipt`, `PromiseYieldStatus`, and enumerate/clear associated `PromiseYieldTimeout` queue entries for the account being deleted, or (b) have `action_delete_account` reject deletion (similar to the existing staking/large-state checks) while the account still has outstanding promise-yield receipts pending resolution.

### Proof of Concept
Integration/test-loop test:
1. Deploy a test contract on account `victim.near` exposing a method that calls `promise_yield_create` with an action batch (e.g., `AddKey` for an attacker-controlled public key).
2. Submit a tx invoking that method, then submit `DeleteAccountAction` for `victim.near` in a following block (before the yield timeout).
3. Submit `CreateAccountAction` (from another account, e.g., "bob.near" creating "sub.bob.near", or from the same attacker recreating a top-level name it owns) to re-create `victim.near`.
4. Advance blocks past `yield_timeout_length_in_blocks` (as in `test-loop-tests/src/tests/yield_timeouts.rs`).
5. Assert that: `TrieKey::PromiseYieldReceipt`/`PromiseYieldStatus` still existed in state right after step 2 (proving `remove_account` didn't clean them - directly testable via unit test on `remove_account` in `core/store/src/utils/mod.rs`); and after step 4, the planted action (e.g., new `AccessKey` for the attacker's public key) is present on the re-created `victim.near` account, despite the new owner never signing or authorizing it.
