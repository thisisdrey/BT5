### Title
`receive-tokens` in `market-vault.clar` ignores the SIP-010 `transfer` boolean, allowing collateral to be credited even if the asset transfer semantically fails - ([File: mainnet/contracts/market/v0-market-vault.clar])

### Summary
`receive-tokens` returns the raw `(response bool uint)` from a SIP-010 `transfer` call, and its only caller, `collateral-add`, wraps it in `try!` but never inspects the inner boolean payload. [1](#0-0) [2](#0-1) 

### Finding Description
`receive-tokens` is implemented as a direct passthrough of the trait call:
```
(define-private (receive-tokens (asset <ft-trait>) (amount uint) (account principal))
  (contract-call? asset transfer amount account current-contract none))
``` [1](#0-0) 

In `collateral-add`, the ledger update (`add-user-collateral`/`insert updated-entry`) and the token pull are ordered so that `try!` only guards against an explicit `err` response; it does not verify that the wrapped `ok` value is `true`:
```
(try! (receive-tokens ft amount account))
(insert updated-entry)
``` [3](#0-2) 

This is the same bug class as the reported Swivel finding: an external call's return value is used only to gate on failure, while the actual success/failure boolean encoded in a successful `(ok bool)` response is discarded. If any registered collateral asset's `transfer` implementation can return `(ok false)` (a semantically-failed but ABI-successful transfer) rather than throwing an error, `receive-tokens` would let `try!` pass through, and the vault would record collateral (`add-user-collateral`) for a user who supplied zero real tokens. `market.clar`'s `collateral-add` entry point calls this internal function only after validating the `ft` argument against the DAO asset registry via `get-asset`, so the check is scoped to whichever tokens the DAO has registered as collateral — but it does not, and cannot, guarantee that every current or future registered SIP-010 implementation strictly reverts on failure instead of returning `(ok false)`.

### Impact Explanation
If reachable, this would let an ordinary principal register non-existent collateral in the protocol's own accounting (`market-vault` collateral map), directly enabling under-collateralized borrowing and protocol insolvency — a Critical-class impact (theft of funds at rest / insolvency) rather than a benign edge case.

### Likelihood Explanation
Likelihood is low in the current deployment: all supported assets (wSTX, sBTC, USDC, USDH, stSTX, stSTXbtc) are pre-vetted SIP-010 tokens that are expected to revert rather than return `(ok false)` on failed transfers, so exploiting this today would require a non-standard token implementation — which falls close to the excluded "third-party token" bug class. The finding is best framed as a defensive-coding gap in Zest's own contract rather than a currently demonstrable exploit against a specific registered asset, since I could not verify (within available context) that any currently-registered token actually returns `(ok false)` instead of erroring.

### Recommendation
Explicitly assert the inner boolean of the SIP-010 response in `receive-tokens` (and the mirrored `send-tokens`, plus the analogous `receive-underlying`/`send-underlying` helpers in the vault contracts) instead of relying solely on `try!`, e.g. `(asserts! (try! (contract-call? asset transfer amount account current-contract none)) ERR-TRANSFER-FAILED)`, so that a semantically-failed transfer cannot be recorded as a successful deposit.

### Proof of Concept
Not independently constructible from the indexed contract set alone, because it requires a registered SIP-010 asset whose `transfer` function returns `(ok false)` on failure instead of erroring; none of the currently indexed token wrappers were confirmed to exhibit that behavior. The conceptual PoC is: deploy/register (or have the DAO register) a token that returns `(ok false)` under some condition (e.g., insufficient balance) → call `collateral-add` with that condition → `receive-tokens`'s `try!` succeeds despite no tokens moving → `add-user-collateral`/`insert` still credits the user with phantom collateral.
