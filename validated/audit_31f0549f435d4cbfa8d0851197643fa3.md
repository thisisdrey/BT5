### Title
Non-constant-time HTTP `authorization` header comparison enables remote timing attack to recover the node's `auth_token` - ([File: stackslib/src/net/api/postblock_v3.rs], [File: stackslib/src/net/api/postblock_proposal.rs], [File: stackslib/src/net/api/blockreplay.rs], [File: stackslib/src/net/api/txsimulate.rs], [File: stackslib/src/net/api/blocksimulate.rs], [File: stackslib/src/net/api/fastcallreadonly.rs])

### Summary
Several `stackslib` RPC request handlers authenticate privileged endpoints by comparing the client-supplied `authorization` HTTP header directly against the configured `auth_token` using Rust's built-in `String`/`&str` `PartialEq` (`auth_header != password` / `auth_header == password`). This is the same bug class as CVE-2015-20110/GHSA-4gpm-r23h-gprw: the comparison short-circuits on the first differing byte, so response timing leaks how many leading bytes of the guess were correct, letting a remote, unauthenticated attacker recover the secret token byte-by-byte instead of needing to brute-force it as a whole.

### Finding Description
The `auth_token` (`connection_options.auth_token`) is the single shared secret that gates several sensitive RPC endpoints, as documented in [1](#0-0) . It is checked in multiple handlers, all using ordinary string equality on attacker-controlled input:

- `/v3/blocks` broadcast endpoint (`postblock_v3.rs`): [2](#0-1) 
- `/v3/block_proposal` endpoint used for signer↔node coordination (`postblock_proposal.rs`) — same `auth_header != password`/`==` pattern (grep-confirmed, 3 matches in file), gating a compute-intensive block-validation endpoint.
- `/v3/blocks/replay/:block_id` (`blockreplay.rs`): [3](#0-2) 
- `/v3/transactions/simulate` (`txsimulate.rs`): [4](#0-3) 
- block simulation (`blocksimulate.rs`) and fast read-only call (`fastcallreadonly.rs`) — same header/`password` comparison pattern (grep-confirmed).

In every case the comparison is a plain Rust `!=`/`==` on `String`/`&str`, which is implemented via a length check followed by a byte-wise `memcmp`-style comparison that returns as soon as a mismatch is found. There is no constant-time comparison utility anywhere in the repository (searched for `constant_time`, `ct_eq`, `subtle::` — no matches), confirming this is the actual comparison path used for the shared secret, in contrast to how public-key signature recovery (e.g. `libstackerdb/src/libstackerdb.rs` `SlotMetadata::verify`) is used for StackerDB/consensus data, which does not rely on comparing two secrets.

Because HTTP header comparison happens early in request parsing (`try_parse_request`), on the hot path before expensive body parsing, an attacker measuring response latency over many requests can statistically detect at which byte position the comparison diverged, and thus recover `auth_token` character-by-character rather than needing `O(charset^len)` guesses.

### Impact Explanation
Recovering `auth_token` allows a remote, unauthenticated attacker to fully impersonate the trusted `stacks-signer` / operator and:
- Submit broadcast blocks via `/v3/blocks?broadcast=1` (`postblock_v3.rs`), bypassing the intended "must be an authenticated operator" gate documented in `stackslib/src/config/mod.rs`.
- Access the `/v3/block_proposal` endpoint, which triggers real, expensive block validation (`postblock_proposal.rs`'s `fault_injection_validation_stall`/validation pipeline), giving an attacker a route to unauthenticated compute-intensive operations that was meant to be gated by a shared secret.
- Access `/v3/blocks/replay`, `/v3/transactions/simulate`, block simulation, and fast-read-only-call endpoints intended to be operator-only.

This maps to the rules' "auth bypass" impact category, since successful token recovery is a full authentication bypass for these operator-only endpoints, not merely a resource-consumption issue.

### Likelihood Explanation
Exploitation requires many timing-based network round trips per byte of the token and is sensitive to network jitter, but it is a well-established practical attack class (this is literally the referenced CVE's exact bug). It requires no privileges, no node secret, and no special network position — only the ability to send repeated HTTP requests to the node's RPC interface, which is explicitly reachable by design (these are RPC handlers, some of which — like block-broadcast/proposal — are meant to be reachable from a remote signer). The main mitigating factor is that this requires a low-noise network path and many samples/averaging to reliably distinguish sub-millisecond timing differences remotely, which raises practical difficulty but does not eliminate the vulnerability.

### Recommendation
Replace all `auth_header != password` / `auth_header == password` comparisons for `auth_token` in `postblock_v3.rs`, `postblock_proposal.rs`, `blockreplay.rs`, `txsimulate.rs`, `blocksimulate.rs`, and `fastcallreadonly.rs` with a constant-time comparison (e.g., the `subtle` crate's `ConstantTimeEq`, or an HMAC-based comparison) that does not short-circuit based on byte position, and ensure both sides are equal-length (e.g., hash both values first) to avoid leaking length information as well.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. Send repeated `POST /v3/blocks?broadcast=1` (or `/v3/block_proposal`, `/v3/transactions/simulate`, `/v3/blocks/replay/:id`) requests with an `authorization` header guess, incrementally trying each byte position 0-255 while keeping prior confirmed-correct bytes fixed.
3. Measure response latency for each guess at each position; the guess causing the comparison to proceed one byte further (higher latency due to comparing more bytes before mismatching) reveals the correct byte.
4. Repeat until the full token is recovered, then use it to authenticate to the otherwise-gated endpoints.

Note: I was unable to fully view the exact surrounding code of the auth check in `postblock_proposal.rs`, `blocksimulate.rs`, and `fastcallreadonly.rs` beyond confirming (via grep) that each contains the same `auth_header`/`password` comparison pattern as `postblock_v3.rs`/`blockreplay.rs`/`txsimulate.rs`; a full session with file access would let a background agent verify the exact line numbers and apply the fix consistently across all six files.
