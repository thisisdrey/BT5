### Title
Hardcoded per-command gas limits in Snowbridge's `ConstantGasMeter` can cause outbound messages to run out of gas on Ethereum, permanently losing bridged commands and funds - ([File: bridges/snowbridge/primitives/outbound-queue/src/v1/message.rs])

### Summary
Snowbridge's outbound queue prices and later executes messages sent from Polkadot to Ethereum using a fixed, hardcoded gas figure per `Command` variant, taken from a single "worst case" gas report rather than computed from the actual payload of each message. Because several commands carry variable-length or caller-controlled data (e.g. `RegisterForeignToken`, `AgentExecute::TransferToken`, `MintForeignToken`, `UnlockNativeToken`, `Upgrade`), the real gas required on the Ethereum Gateway contract can exceed the hardcoded constant, causing the message to run out of gas and revert on execution while the corresponding nonce/commitment on the Substrate side has already advanced - resulting in a permanently lost cross-chain command, mirroring the external report's "hardcoded gas for cross-chain message" bug class.

### Finding Description
`GasMeter::maximum_dispatch_gas_used_at_most` is implemented by `ConstantGasMeter`, which returns a fixed constant per `Command` regardless of the actual message content: [1](#0-0) 

Note in particular:
- `AgentExecuteCommand::TransferToken { .. } => 200_000` - a flat gas budget for calling `IERC20.transferFrom` on an arbitrary ERC-20 contract, whose actual gas cost is entirely determined by the token contract's own logic (fee-on-transfer tokens, rebasing tokens, hooks, etc. can exceed 200_000).
- `Command::RegisterForeignToken { .. } => 1_200_000` - a flat budget regardless of the token metadata (name/symbol length, decimals) being registered.
- `Command::MintForeignToken { .. } => 100_000` and `Command::UnlockNativeToken { .. } => 200_000` - same pattern.
- `Command::Upgrade` at least partially compensates by adding `initializer.maximum_required_gas`, but that value is caller-supplied and not otherwise verified against actual bytecode execution cost.

This constant is used, unmodified, both to price the message (`calculate_fee`) and to set the amount of gas forwarded to the Gateway contract on Ethereum: [2](#0-1) 

`validate()` computes `gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command)` purely from the `Command` discriminant/fields listed above, never inspecting or bounding execution cost of the destination contract logic that will actually run on Ethereum. The message is then enqueued and, once committed and relayed, executed with that fixed gas ceiling on the Ethereum side by the Gateway contract (outside this repo, but the gas ceiling itself originates here and is transmitted as part of the message).

Once a message is delivered into the queue and its commitment/merkle-root/nonce advances (`do_process_message`, `commit`), there is no mechanism in this repo to increase the gas afterward or to retry with a larger budget if the fixed constant proves insufficient for a particular token/contract instance. This is the same underlying flaw as the reported issue: a hardcoded gas figure that does not adapt to variable per-message execution cost (e.g., token-specific `transferFrom` logic, or metadata length in registration), risking permanent loss of the cross-chain operation for specific tokens/messages, exactly as previously happened in production - documented by the historical fix: [3](#0-2) 

which raised `TransferToken`'s gas limit from 100_000 to 200_000 after LDO token transfers required 140_000 gas, i.e., the previous hardcoded constant was already empirically proven insufficient for at least one real-world ERC-20 token. This confirms the vulnerability class is not theoretical: it has already manifested once for `TransferToken`, and the same structural flaw remains for every other `Command` variant that carries caller/token-controlled payload (`RegisterForeignToken`, `MintForeignToken`, `UnlockNativeToken`).

### Impact Explanation
If the fixed gas budget for a given command undershoots the actual Ethereum execution cost (e.g., a new ERC-20 token with more expensive `transferFrom`/`mint` hooks, or metadata triggering more expensive registration logic than assumed), the corresponding cross-chain operation (token transfer, token registration, native token unlock) fails on Ethereum after the corresponding nonce has already been consumed and committed on the Substrate side. Because delivery/commitment is one-directional and not automatically retried with higher gas, the operation is effectively lost: users lose access to bridged funds or a governance-driven token registration/mint silently fails, matching the report's "loss of cross-chain deployments" impact for specific tokens/routes. This is a Medium-Medium class issue similar to the seed report: no direct fund theft, but potential permanent lock/loss of value or dropped state transitions for particular messages, which qualifies under "permanent user-fund or bridge-state lock" in the impact gate.

### Likelihood Explanation
Likelihood is Medium: it requires a specific combination of token/contract behavior (e.g., a token whose `transferFrom` legitimately costs more than 200_000 gas, or similarly for mint/unlock/registration flows) to trigger, which is plausible given ERC-20 diversity and has already occurred once in production for `TransferToken` prior to the 100k→200k gas bump. It does not require a malicious actor, admin, or validator - simply routing a normal, unprivileged cross-chain transfer/registration involving a token whose gas cost profile diverges from the constant assumption is sufficient.

### Recommendation
Replace (or supplement) the fixed per-`Command` gas constants in `ConstantGasMeter` with a mechanism that:
1. Accounts for `baseGas`/`intrinsicGas` separately from `executionGas`, as recommended in the seed report.
2. For commands whose Ethereum-side cost depends on caller-controlled or token-controlled logic (`TransferToken`, `MintForeignToken`, `UnlockNativeToken`, `RegisterForeignToken`), allow a caller-specified (and fee-charged) gas limit bounded by a sane maximum, similar to how `Command::CallContract` already accepts an explicit `gas` parameter and `Upgrade` already adds `initializer.maximum_required_gas`.
3. Add governance/monitoring tooling to periodically re-benchmark and update the hardcoded constants (as was done ad hoc via PR #7947/#8259), or better, move to a dynamic estimation strategy so that per-token/per-message gas needs are reflected in both the fee charged and the gas forwarded, preventing silent execution failure and permanent message loss.

### Proof of Concept
1. Register (via `RegisterForeignToken`) or otherwise onboard an ERC-20 token whose `transferFrom` implementation costs more than 200_000 gas net of the 21,000 base transaction cost already folded into `MAXIMUM_BASE_GAS` (e.g., a token with non-trivial before/after-transfer hooks, similar to LDO prior to the gas-limit bump documented in `pr_7947.prdoc`).
2. Initiate an `AgentExecute::TransferToken` (or `MintForeignToken`/`UnlockNativeToken`) command through the normal user-facing cross-chain transfer flow.
3. `Pallet::validate` in `send_message_impl.rs` computes the fee using the fixed 200_000/100_000 gas constant from `ConstantGasMeter`, accepts the message, and it is committed/relayed to Ethereum.
4. On Ethereum, the Gateway contract executes the command with the fixed gas ceiling; because the token's actual `transferFrom` execution exceeds the budget, the call runs out of gas and reverts.
5. The Substrate-side nonce/commitment has already advanced (message consumed from the queue and merklized), but the corresponding Ethereum-side effect never took place, and there is no retry-with-higher-gas path in this codebase - the message/command is permanently lost, reproducing the `TransferToken` incident that necessitated the historical 100_000→200_000 gas bump.

pub struct ConstantGasMeter;

impl GasMeter for ConstantGasMeter {
	// The base transaction cost, which includes:
	// 21_000 transaction cost, roughly worst case 64_000 for calldata, and 100_000
	// for message verification
	const MAXIMUM_BASE_GAS: u64 = 185_000;

	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::AgentExecute { command, .. } => match command {
				// Execute IERC20.transferFrom
				//
				// Worst-case assumptions are important:
				// * No gas refund for clearing storage slot of source account in ERC20 contract
				// * Assume dest account in ERC20 contract does not yet have a storage slot
				// * ERC20.transferFrom possibly does other business logic besides updating balances
				AgentExecuteCommand::TransferToken { .. } => 200_000,
			},
			Command::Upgrade { initializer, .. } => {
				let initializer_max_gas = match *initializer {
					Some(Initializer { maximum_required_gas, .. }) => maximum_required_gas,
					None => 0,
				};
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer_max_gas
			},
			Command::SetTokenTransferFees { .. } => 60_000,
			Command::SetPricingParameters { .. } => 60_000,
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
		}
	}
}
