### Title
Relayer reward paid in full and unconditionally regardless of Ethereum execution success or actual gas used, with no sender refund - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

### Summary
`Pallet::process_delivery_receipt` in the Snowbridge V2 outbound queue pays the full pre-committed `PendingOrder.fee` to the relayer's `reward_account` as soon as a `DeliveryReceipt` is verified, without inspecting the `success` field of the underlying `InboundMessageDispatched` Ethereum event, and without any mechanism to refund unused portion of the fee (which was originally computed from a worst-case gas bound) back to the sender. [1](#0-0) 

### Finding Description
The fee attached to each outbound message (`order.fee`) is set once at enqueue time in `do_process_message`, taken directly from the `Message.fee` field supplied by the sender/XCM exporter — itself derived from a worst-case gas estimate via `GasMeter::maximum_dispatch_gas_used_at_most`. [2](#0-1) 

When a relayer later calls `submit_delivery_receipt`, the event log is verified cryptographically and decoded into a `DeliveryReceipt`, which explicitly carries a `success: bool` field decoded from the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event. [3](#0-2) 

However, `process_delivery_receipt` never reads or checks `receipt.success`. It only checks the gateway address, looks up the `PendingOrder` by nonce, and if `order.fee > 0` unconditionally calls `T::RewardPayment::register_reward` for the *entire* fee, then removes the order: [4](#0-3) 

This reproduces the exact broken invariant from the Wormhole report:
1. The sender pays a fee sized for a worst-case gas/execution scenario at enqueue time, with no visibility into actual downstream cost.
2. There is no code path anywhere in this pallet (or `AddTip`) that computes actual gas/execution cost on the target chain and refunds the difference to the sender; the entire quoted `fee` is transferred to whichever address claims the receipt.
3. Because `success` is decoded but discarded, a relayer is rewarded the full quoted fee even for a delivery that ultimately failed on Ethereum (only cryptographic verification of the log is checked, not the semantic outcome it reports) — an even stronger version of the "relayer earns more than it spent" incentive misalignment described in the external report, since here the relayer can be rewarded even without a successful message execution.
4. `PendingOrders::remove(nonce)` is called after payout in every case, so there is no distinct settlement path for failed vs. successful delivery, and no state exists to trigger a sender-side refund once `success == false` is observed.

Existing guards do not stop this: `T::Verifier::verify` only checks that the log is authentic and was emitted by the real gateway (cryptographic/proof validity), it says nothing about the semantic content (`success`) of the event; `InvalidPendingNonce`/`InvalidGateway` checks are unrelated to fee correctness; and no `WeightToFee`/gas-usage reconciliation step exists post-receipt.

### Impact Explanation
This directly matches the required impact classes: it is a runtime bug that compromises intended behavior (fee is supposed to correspond to delivery cost, but is decoupled from actual outcome) and results in duplicate/mis-scoped settlement of value — paying out bridge relayer rewards without validating the value-conservation condition (`success == true` and cost == fee). Funds (the quoted fee) are settled to the relayer even in scenarios where message execution failed or cost less than quoted, permanently overcharging the message sender with no recourse, exactly as impact (1) and (2) in the original report describe, but exacerbated because it doesn't require any relayer misbehavior beyond simply calling `submit_delivery_receipt` — it's the pallet's normal, only code path.

### Likelihood Explanation
High: `submit_delivery_receipt` is a permissionless, public extrinsic (`ensure_signed(origin)?` is the only origin check) that any address holding a valid Ethereum log proof can call. No governance, privileged, or malicious-peer assumption is required — any legitimate relayer following the intended flow will unconditionally receive the full fee once verification of the log succeeds, regardless of the `success` outcome carried in that same log. This is a systemic property of the shipped code, not a rare edge case. [5](#0-4) 

### Recommendation
- Check `receipt.success` in `process_delivery_receipt`; only pay the full `order.fee` reward when `success == true`.
- On `success == false` (or partial-execution outcomes), either withhold/reduce the relayer reward and route the unused fee back to the original message sender/origin, or track actual gas consumed (if surfaced via a future event extension) and refund the delta to the sender similar to Wormhole's `targetChainRefundPerUnitGasUnused` fix.
- Ensure the state transition (`PendingOrders::remove`) is only treated as "settled" after the reward/refund split has been correctly computed and dispatched, so failed deliveries do not silently over-reward relayers at sender expense.

### Proof of Concept
1. A sender submits a Snowbridge V2 message via `send_message_impl::SendMessage::deliver`, paying `Message.fee` computed from `GasMeter::maximum_dispatch_gas_used_at_most` (a worst-case gas bound). [6](#0-5) 
2. The message is enqueued as a `PendingOrder` with the full quoted `fee`. [2](#0-1) 
3. On Ethereum, the gateway contract emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)` (e.g., because the receiving contract call reverted, but the outer transaction still logs the event as part of the outbound-queue-acknowledgment mechanism).
4. A relayer submits this same log via `submit_delivery_receipt`; `T::Verifier::verify` succeeds because the log is authentically from the gateway.
5. `process_delivery_receipt` never inspects `success`; it pays out `order.fee` in full to `reward_account` and removes the pending order. [7](#0-6) 
6. Result: the sender has paid full worst-case fee for a message that failed on the target chain (or consumed much less gas than quoted), and there is no code path in this pallet that returns any portion of that fee to them — the exact overcharge/no-refund condition described in the external Wormhole report, reproduced natively in Snowbridge's reward settlement logic.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
