### Title
Fee-on-transfer / deflationary NEP-141 and NEP-245 tokens allow crediting more internal balance than actually custodied - (File: `contracts/defuse/src/contract/tokens/nep141/deposit.rs`)

### Summary
`ft_on_transfer`/`mt_on_transfer` credit the internal ledger with exactly the `amount`/`amounts` value reported by the calling token contract, without ever checking that this amount actually landed in Defuse's own token balance. For a token whose contract deducts a transfer fee (or rebases) before crediting the receiver, the amount argument passed to the receiver hook can be larger than what Defuse actually received, breaking the custody invariant that a user's credited internal balance must be backed 1:1 by tokens actually held by the contract.

### Finding Description
On deposit, the contract trusts the caller-supplied `amount`: [1](#0-0) 

`self.deposit(receiver_id, [(token_id, amount.0)], ...)` credits `amount.0` verbatim — this value is fully controlled by the predecessor token contract (`env::predecessor_account_id()`), which becomes the `TokenId` for future accounting. Nothing in this path calls `ft_balance_of`/verifies the contract's actual balance delta for that token before crediting. The identical pattern exists for multi-token deposits: [2](#0-1) 

The symmetric withdrawal path has the same blind spot in the other direction: `ft_resolve_withdraw`/`mt_resolve_withdraw` only look at whether the outgoing `ft_transfer`/`ft_transfer_call` promise *succeeded*, not at how many tokens the receiver actually got: [3](#0-2) 

For a plain (non-call) `ft_transfer`, NEP-141 returns an empty success value regardless of whether the token contract silently deducted a fee en route, so `used = amount.0` is assumed and no shortfall is ever tracked or refunded.

Because Defuse accepts and auto-registers a `TokenId` for *any* NEP-141/NEP-245 contract that calls `ft_on_transfer`/`mt_on_transfer` on it (no allowlist gate on the receiver hooks), an attacker can point Defuse at a token contract they control (or any already-listed fee-on-transfer/rebasing token) and exploit the mismatch:

- Deposit path: `amount` reported to `ft_on_transfer` (the pre-fee gross amount, as required by the NEP-141 `ft_transfer_call` semantics — the sender specifies the amount debited from itself) is credited in full to the depositor's internal balance, while the contract's real token holdings only increase by `amount - fee`.
- This breaks the invariant `sum(credited internal balances for TokenId T) == actual balance of T held by Defuse`, which is the custody binding equivalent to "balance change versus the amount authorised/credited."

### Impact Explanation
The attacker's own internal balance for token `T` becomes over-credited relative to the tokens Defuse actually possesses for `T`. The attacker can withdraw (or use in `execute_intents` transfers/swaps against counterparties) more of `T` — or a proportional share of other pooled assets it's exchanged for — than they ever actually delivered to the contract. Because balances of the same `TokenId` are pooled across all Defuse users, this insolvency surfaces as later, legitimate holders of the same token being unable to fully withdraw their credited balance (funds effectively frozen/short), while the attacker walked away with tokens credited without matching backing. This matches the "Critical: tokens... credited... without valid authorisation" / "funds permanently frozen" impact classes.

### Likelihood Explanation
Exploitability requires the attacker to control (or find) a NEP-141/NEP-245 contract that applies a transfer fee/rebase and to get it accepted as a `TokenId` in Defuse — which requires no privileged action, since any contract calling `ft_on_transfer`/`mt_on_transfer` is auto-onboarded as a distinct `TokenId` keyed by `predecessor_account_id`. The attacker fully controls both the malicious token contract and the deposit/withdraw calls, making this a purely unprivileged, self-serviceable attack path.

### Recommendation
For NEP-141/NEP-245 deposits, verify the contract's actual balance delta for the token (e.g., snapshot `ft_balance_of(current_account_id)` before/after, or require standard-compliant tokens only via an explicit allowlist/registration step) before crediting the internal ledger, rather than trusting the `amount` argument supplied by the calling token contract. Symmetrically, on withdraw, confirm the receiver's actual balance increase (or restrict withdrawals to tokens known to conform strictly to non-fee-on-transfer NEP-141/NEP-245 semantics) instead of inferring full delivery purely from promise success.

### Proof of Concept
1. Attacker deploys `feetoken.near`, a NEP-141 contract that on `ft_transfer_call(receiver, amount, memo, msg)` debits `amount` from sender but forwards only `amount * 99 / 100` to the receiver (a 1% fee), while still invoking `ft_on_transfer(sender_id, amount, msg)` with the full pre-fee `amount` (this is a valid, spec-compliant NEP-141 implementation choice, since NEP-141 does not mandate the receiver-hook amount equal the actual balance delta).
2. Attacker calls `feetoken.near::ft_transfer_call(intents.near, 100_000, ..., "")`. Defuse's `ft_on_transfer` (`contracts/defuse/src/contract/tokens/nep141/deposit.rs:19-43`) credits the attacker's internal `Nep141(feetoken.near)` balance with `100_000`, while Defuse's real `feetoken.near` balance only increased by `99_000`.
3. Attacker signs and executes an `FtWithdraw` intent for `100_000` of `feetoken.near` to any receiver (or trades it via `Transfer`/other intents against real counterparties). Defuse's own token holdings for `feetoken.near` are only `99_000`, so either this withdrawal succeeds by consuming reserves meant for other depositors of the same token (later depositors' withdrawals of `feetoken.near` then fail/underflow), or, if pooled with a legitimate counterpart token via a swap intent, the attacker extracts value backed by tokens that were never actually deposited.

    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        require!(amount.0 > 0, "zero amount");

        let token_id = TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()));

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {
            DepositMessage::new(sender_id.clone())
        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());
