I need to check how `DebtToken.issue` adds tokens to an account's list and whether a victim can be pushed to the cap.### Title
Dust-transfer griefing fills `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, permanently bricking a victim's ability to deposit or borrow - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`DepositToken._transfer` unconditionally registers the recipient in the pool's per-account set `depositTokensOfAccount` on first receipt of any deposit token. `Pool.addToDepositTokensOfAccount` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` across deposit + debt tokens and reverts with `UserReachedMaxTokens` once reached. An unprivileged attacker can dust-transfer every registered deposit token to a victim, filling the set to the cap, after which the victim cannot deposit any new collateral type, receive any new deposit token, or take on new debt.

### Finding Description
Two code paths combine to create the vulnerability:

1. `DepositToken._transfer` (contracts/DepositToken.sol:498-526) calls `pool.addToDepositTokensOfAccount(recipient_)` whenever `_recipientBalanceBefore == 0 && amount_ > 0`, with no consent or opt-out from the recipient. Transfers are permissionless, so any holder of an `msdTOKEN` can add it to an arbitrary account's set for the cost of a 1-wei dust transfer.

2. `Pool.addToDepositTokensOfAccount` (contracts/Pool.sol:216-220) is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` (contracts/Pool.sol:143-148). The cap counts entries added *to* the victim, not entries the victim chose.

Attack sequence:

1. Attacker acquires dust amounts of each deposit token registered in the pool (by depositing the underlying themselves, or buying `msdTOKEN`s).
2. For each deposit token `msd_i`, attacker calls `msd_i.transfer(victim, 1)`. Each first-receipt call pushes `msd_i` into `depositTokensOfAccount[victim]` via `Pool.addToDepositTokensOfAccount`.
3. Once the combined set reaches 30 entries, any subsequent `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` call for the victim reverts with `UserReachedMaxTokens`.

Consequences for the victim while the state persists:

- `DepositToken._mint` (contracts/DepositToken.sol:486-488) calls `pool.addToDepositTokensOfAccount(account_)` on a first-time deposit. The whole mint reverts, so the victim **cannot deposit any collateral type they do not already hold** — they cannot add collateral to improve health in a new asset.
- `DebtToken` issuance likewise calls `pool.addToDebtTokensOfAccount`, which is gated by the same modifier, so the victim **cannot borrow any synthetic they do not already owe**.
- Any third party attempting to `transfer` a deposit token the victim does not yet hold reverts, breaking integrations (zaps, leverage unwinds, reward payouts in msTokens).
- On a pool with ≥30 registered deposit/debt tokens the account is fully saturated; on smaller pools the attacker consumes the entire remaining headroom (e.g., a pool with 8 deposit tokens leaves the victim permanently capped at whatever the attacker pushed).

The victim can free slots only by transferring a full balance out (`_transfer` calls `removeFromDepositTokensOfAccount` when the sender's balance hits zero, line 523-525), but the attacker can refill the slot immediately, so the griefing is persistent at negligible cost.

### Impact Explanation
Temporary freezing of funds / liveness denial against a targeted account: the victim cannot open new collateral positions or new debt while saturated, and inbound token transfers of new types revert. If the victim's existing collateral is delisted (`toggleIsActive`) or its collateral factor is cut, the victim cannot migrate to a different collateral type and may be forced into liquidation while unable to add collateral. The attack requires no privileged role, no price manipulation, and no victim cooperation — only dust amounts of each pool deposit token.

### Likelihood Explanation
Medium-low. The attack is cheap (dust transfers, bounded by the pool's registered token count) and fully permissionless. Limitations: the victim keeps the ability to withdraw and repay existing positions, the damage is griefing rather than direct theft, and profit for the attacker is indirect (e.g., forcing a liquidation the attacker then executes, or blocking a competing leveraged position in `SmartFarmingManager`). Pools with few registered deposit tokens reduce but do not eliminate the impact, since debt tokens share the same 30-slot budget.

### Recommendation
- Make the per-account list opt-in: do not add to `depositTokensOfAccount`/`debtTokensOfAccount` on plain `transfer`/`transferFrom`; only register on `deposit`/`mint`-initiated actions, or iterate collateral a different way (e.g., over the pool's global `depositTokens` set bounded by `MAX_DEPOSIT_TOKENS`).
- Alternatively, exempt unsolicited inbound transfers from `UserReachedMaxTokens` by skipping the `add` when the recipient is at cap (the token still credits but isn't tracked — though this changes `depositOf`/health semantics and must be evaluated).
- At minimum, allow the account owner to remove entries via a dedicated `removeFromDepositTokensOfAccount` owner-callable path rather than requiring a full balance transfer.

### Proof of Concept
Foundry-style PoC (assumes a deployed `Pool` with registered deposit tokens `msd[]` and a `victim` holding one deposit token):

```solidity
function test_FillVictimTokenSet() public {
    uint256 MAX = pool.MAX_TOKENS_PER_USER(); // 30

    // Attacker holds dust of each deposit token (obtained by depositing minimal underlying)
    for (uint256 i; i < msd.length && i < MAX; ++i) {
        uint256 before = IDepositToken(msd[i]).balanceOf(victim);
        if (before == 0) {
            IDepositToken(msd[i]).transfer(victim, 1); // adds to depositTokensOfAccount[victim]
        }
    }

    uint256 total = pool.getDepositTokensOfAccount(victim).length
                  + pool.getDebtTokensOfAccount(victim).length;
    assertEq(total, MAX); // victim's set saturated

    // Victim can no longer deposit a collateral type it doesn't already hold
    vm.startPrank(victim);
    underlying.approve(address(newDepositToken), type(uint256).max);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newDepositToken.deposit(1e18, victim);

    // And cannot borrow any new synthetic
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newDebtToken.issue(1e18, victim);
    vm.stopPrank();
}
```
