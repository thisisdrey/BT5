### Title
Unbounded array allocation from attacker-controlled length word in TVM precompiled-contract input decoding causes node OutOfMemoryError DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`node-tar`'s flaw is that a small compressed input can cause the parser to allocate/write an unbounded amount of data because no hard cap exists on the declared size before it is used to drive allocation/decompression. `PrecompiledContracts` in java-tron has the same root-cause shape: several ABI-array decoding helpers read an attacker-controlled 32-byte "length" word from precompiled-contract call data and immediately use it, via `DataWord.intValueSafe()`, to size a Java array — with no check that the declared length is consistent with the actual size of the supplied `data` buffer before the allocation happens.

### Finding Description
`extractBytesArray`, `extractSigArray`, and `extractBytes32Array` decode dynamic arrays passed to certain precompiled contracts (e.g. batch/multi-signature validation precompiles reachable from TVM `CALL`/`STATICCALL` to the corresponding precompile addresses): [1](#0-0) 

`len` is obtained from `words[offset].intValueSafe()`, and `DataWord.intValueSafe()` clamps overflow/negative values to `Integer.MAX_VALUE` rather than rejecting them: [2](#0-1) 

Because `len` is used directly to size `new byte[len][]` (an object array, ~8 bytes per reference on a 64-bit JVM) *before* any bounds check against the true length of `data`, a caller can supply a calldata word encoding a value close to `Integer.MAX_VALUE` (e.g. `0x7FFFFFFF`). This causes the JVM to attempt to allocate an array requiring tens of gigabytes of heap (or hit the JVM's max-array-size limit), throwing an `OutOfMemoryError`/`Error` rather than a normal, catchable VM exception such as the `Exception`-based `Program.Exception` hierarchy used elsewhere in TVM execution. Unlike `RLP.calcLength`/`verifyLength` in `framework/src/main/java/org/tron/core/capsule/utils/RLP.java`, which validates declared lengths against the available payload before allocating (`verifyLength(length, msgData.length - pos - lengthOfLength)`), no equivalent check exists in these `PrecompiledContracts` helpers. [3](#0-2) 

### Impact Explanation
An `Error` (not an `Exception`) escaping mid-execution of a transaction inside the TVM can propagate past the actuator's normal try/catch handling designed for `ContractExeException`/`Program.Exception`, potentially destabilizing the executing thread and, under memory pressure, the whole node process (denial of service against the validating/witness node). Any unprivileged account can trigger this by broadcasting a single ordinary contract-call transaction that targets the relevant precompiled address with crafted calldata — no special privilege, large payload, or SR/witness compromise is required, matching the "small input, disproportionate resource consumption" pattern of the `node-tar` advisory.

### Likelihood Explanation
Triggering this requires only building a transaction whose calldata to the affected precompile encodes an inflated length word; this is easy to construct and costs only the energy for a small calldata payload/precompile invocation. The unusual clamp-to-`Integer.MAX_VALUE` semantics of `intValueSafe()` (rather than throwing/rejecting on out-of-range values) makes this reachable through ordinary contract-call handling, not just fuzzing of internal APIs.

### Recommendation
In `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, validate `len` against the actual bounds of the supplied `data`/`words` array (similar to `RLP.verifyLength`) before allocating any array, and reject the call (return `false`/revert) instead of allocating when the declared count is inconsistent with the available data. Consider also capping `intValueSafe()` consumers that feed array sizes to a sane maximum tied to real calldata size limits.

### Proof of Concept
1. Construct a transaction invoking one of the precompiles that uses `extractBytesArray`/`extractSigArray` (batch/multi-signature validation precompile), with calldata where the array-length word at the expected `offset` is set to `0x000000000000000000000000000000000000000000000000000000007FFFFFFF` (a value with `bytesOccupied() <= 4` so it's not clamped by the overflow branch, but still huge).
2. Broadcast the transaction to a full node for execution/validation.
3. During execution, `extractBytesArray`/`extractSigArray` calls `new byte[len][]` with `len ≈ 2^31-1`, which the JVM must attempt to satisfy as an ~17GB (or larger, given per-object overhead) allocation, throwing `OutOfMemoryError`/`Error` mid-TVM-execution — an unhandled `Error` that can destabilize the node process, from a single small, cheap transaction.

  /**
   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()
   */
  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }
