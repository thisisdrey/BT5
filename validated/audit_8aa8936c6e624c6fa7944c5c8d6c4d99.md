### Title
Flat per-signature precompile verification cost is decoupled from actual verified-message size, letting attackers get expensive CPU work performed for a fixed, unscaled CU charge - (File: cost-model/src/block_cost_limits.rs)

### Summary
The Perennial `H-6` report's root cause is a fee/compensation mechanism that charges a **fixed** unit price for work whose real cost is driven by a variable, attacker-controlled dimension (L1 calldata bytes), so the flat charge can diverge arbitrarily from the true cost of the work performed. Agave's cost model has the same structural pattern for ed25519/secp256k1/secp256r1 precompile signature verification: the CU charge is a flat per-signature constant, while the actual CPU work performed by every validator (leader during banking-stage execution, and every other node during replay) scales with the verified message length, which the submitter fully controls.

### Finding Description
`cost-model/src/block_cost_limits.rs` defines the compute-unit cost of signature verification as flat, size-independent constants derived from an assumed cluster-average `COMPUTE_UNIT_TO_US_RATIO`: [1](#0-0) 

These constants are consumed by `CostModel::get_signature_cost`, which multiplies the *count* of signatures per precompile type by the flat per-signature cost, with no dependency on the size of the data actually verified: [2](#0-1) 

However, the actual verification work performed by the ed25519 precompile (`agave_precompiles::ed25519::verify`) hashes/verifies over a `message` slice whose length (`message_data_size`) is attacker-controlled and can be as large as `u16::MAX` bytes (per-signature), taken either from the same instruction or from another instruction's data referenced via `message_instruction_index`: [3](#0-2) [4](#0-3) 

The project's own benchmarks explicitly confirm the cost scales with message length (32 bytes vs 32KB vs ~64KB), which the flat `ED25519_VERIFY_STRICT_COST` (30 * 80 = 2400 CU) never reflects: [5](#0-4) 

This same flat-cost, size-independent charge is used not merely for local accounting but to gate/allocate the scarce resource in question (compute-unit block limits, per-account write-lock throttling, and — critically — the priority/QoS formula that decides whose transactions get processed first and whose get dropped under load): [6](#0-5) 

This is used directly to compute the priority-floor that `SigVerifyStage` uses to *drop packets before doing any signature verification at all* when the scheduler is saturated: [7](#0-6) 

### Impact Explanation
This mirrors the Perennial finding precisely: a flat, size-independent charge for work whose real cost is driven by a size/complexity parameter the submitter controls. In Agave, this means:
- An attacker can construct many transactions carrying ed25519/secp256k1/secp256r1 precompile instructions with maximal `message_data_size` (referencing another instruction's larger data blob within the same packet-sized transaction), forcing every validator that processes/replays the block to perform disproportionately expensive hashing/verification work relative to the CU price/priority the transaction pays.
- Because the flat cost also feeds the priority-floor/QoS mechanism (`calculate_priority_and_cost` in `core/src/transaction_priority.rs`, consumed by `SchedulerController::update_scheduler_priority_floor` and `SigVerifyStage::apply_priority_floor_to_batch`), the cost model under-reports the true resource consumption of such transactions, letting them appear cheap enough to avoid being dropped/pre-verify-filtered under saturation while actually imposing outsized CPU cost — a QoS-evasion vector, and in the aggregate a grossly underpriced-work condition analogous to the H-6 keeper compensation mismatch.
- Unlike Perennial's keeper (a privileged operator role), any unprivileged transaction submitter can trigger this by simply constructing an oversized-message precompile instruction; no special role or permission is required.

### Likelihood Explanation
The mismatch is structural and permanent (the constants in `block_cost_limits.rs` are static, historically-calibrated averages, not derived per-transaction from `message_data_size`), so — exactly as the escalation debate in H-6 argued about the impossibility of a single fixed buffer tracking a variable ratio — no constant can correctly price a workload whose true cost varies with an attacker-chosen size parameter. Triggering it requires only crafting a standard, permissionless transaction with a large-message precompile instruction referencing another instruction's data; this is always exploitable, not conditional on external market conditions (unlike the original L1/L2 gas-price ratio dependency), making it arguably easier to trigger reliably than the original finding.

### Recommendation
Scale `SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, and `SECP256R1_VERIFY_COST` (and the corresponding `get_signature_cost` computation) by the actual `message_data_size` referenced by each signature, rather than a flat per-signature constant, mirroring how `data_bytes_cost`/`INSTRUCTION_DATA_BYTES_COST` scales with instruction data length elsewhere in the same cost model. Feed the size-aware cost into both the CU/block-limit accounting and the `calculate_priority_and_cost` formula used for scheduling and the sigverify priority floor.

### Proof of Concept
Not independently executed; based on static analysis of `cost-model/src/block_cost_limits.rs`, `cost-model/src/cost_model.rs::get_signature_cost`, `precompiles/src/ed25519.rs::verify`, and the project's own `precompiles/benches/ed25519_instructions.rs` benchmarks demonstrating that verification cost grows with `message_data_size` (32B → 32KB → ~64KB) while the CU charge (`ED25519_VERIFY_STRICT_COST`) remains a fixed 2400 CU per signature regardless of message length. I could not fully verify the maximum realistically achievable `message_data_size` within a single wire-format transaction (bounded by overall packet/transaction size limits, e.g. `PACKET_DATA_SIZE`, and by the tx-v1 feature referenced in `core/src/sigverify.rs`) within the available iterations — this would need to be confirmed with a live benchmark/PoC transaction to quantify the exact CU-cost-to-real-CPU-time ratio achievable in practice.

fn get_data_slice<'a>(
    data: &'a [u8],
    instruction_datas: &'a [&[u8]],
    instruction_index: u16,
    offset_start: u16,
    size: usize,
) -> Result<&'a [u8], PrecompileError> {
    let instruction = if instruction_index == u16::MAX {
        data
    } else {
        let signature_index = instruction_index as usize;
        if signature_index >= instruction_datas.len() {
            return Err(PrecompileError::InvalidDataOffsets);
        }
        instruction_datas[signature_index]
    };

    let start = offset_start as usize;
    let end = start.saturating_add(size);
    if end > instruction.len() {
        return Err(PrecompileError::InvalidDataOffsets);
    }

    Ok(&instruction[start..end])
}

/// Calculate priority and cost for a transaction:
///
/// Cost is calculated through the `CostModel`,
/// and priority is calculated through a formula here that attempts to sell
/// blockspace to the highest bidder.
///
/// The priority is calculated as:
/// P = R / (1 + C)
/// where P is the priority, R is the reward,
/// and C is the cost towards block-limits.
///
/// Current minimum costs are on the order of several hundred,
/// so the denominator is effectively C, and the +1 is simply
/// to avoid any division by zero due to a bug - these costs
/// are calculated by the cost-model and are not direct
/// from user input. They should never be zero.
/// Any difference in the prioritization is negligible for
/// the current transaction costs.
pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
    let fee_details = solana_fee::calculate_fee_details(
        transaction,
        bank.fee_structure().lamports_per_signature,
        transaction_configuration.priority_fee_lamports,
        bank.fee_features(),
    );
    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    (
        reward
            .saturating_mul(MULTIPLIER)
            .saturating_div(cost.saturating_add(1)),
        cost,
    )
}
