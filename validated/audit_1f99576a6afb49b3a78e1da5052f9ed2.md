## Analysis

The reported bug is a classic **unbounded per-item loop** pattern: a user-controlled collection (`activeProposals`) drives a loop where each iteration performs expensive external calls, and the cost is entirely borne by the calling (unprivileged) user with no batching/limit. The Gitaly analog is the **non-atomic reference-update path of the `proc-receive` hook handler**, where the number of loop iterations is directly controlled by an ordinary user's `git push` (via the reference updates it sends), and each iteration spawns a brand-new subprocess.

### Title
Unbounded per-reference-update subprocess spawning in non-atomic proc-receive handling causes push-driven resource exhaustion - (File: internal/gitaly/hook/receivepack/receive_pack.go)

### Summary
When a client pushes with the `proc-receive` protocol and the handler is non-atomic, Gitaly iterates over every reference update the pusher supplied and, for **each one individually**, spawns a fresh `git-update-ref` process and runs the `update` hook (itself potentially spawning custom-hook subprocesses). An ordinary user can control the number of reference updates in a single push, so this per-update process-spawn cost scales linearly (unbounded) with attacker-chosen input, unlike the atomic path which batches all updates into one `updateref` invocation.

### Finding Description
`procReceiveHook` branches on `handler.Atomic()`: [1](#0-0) 

In the non-atomic branch, the code loops over `handler.ReferenceUpdates()` — a slice built directly from the pkt-line reference-update lines the client streamed in during proc-receive negotiation (see `parseRefUpdate`/`updates` construction in `internal/gitaly/hook/procreceive_handler.go`) — and calls `receivePackReferenceUpdates` once **per single update**: [2](#0-1) 

Each call to `receivePackReferenceUpdates` independently:
1. Spawns a new `updateref.New(ctx, repo, ...)` process (i.e., forks/execs `git-update-ref`), and
2. Invokes `hookManager.UpdateHook(...)`, which runs the `update` custom-hook executor for every single reference: [3](#0-2) 

There is no limit on the number of reference updates a push may contain via this path, so the cost (process forks, hook executor spawns, `HooksPayload` construction, transaction bookkeeping) is proportional to the number of refs the pusher includes — entirely attacker/user controlled, and it all runs synchronously on the single primary Gitaly node handling the push (see `doc/hooks.md`, describing receive-pack hooks as only running on the primary).

### Impact Explanation
A pusher can craft a single push containing a very large number of small/no-op reference updates (e.g., many branch/tag creations or fast-forward updates) processed non-atomically, forcing the primary Gitaly node to spawn one `git-update-ref` process and one (or more, if custom hooks are installed) hook-executor process per update, sequentially and synchronously. This consumes CPU, process table slots, and file descriptors disproportionate to the actual work being done, and — because receive-pack style hooks execute only on the primary — can stall that node's processing of the push (and potentially delay/hang other Gitaly nodes waiting on the corresponding transaction to reach quorum, per `doc/hooks.md`'s discussion of the primary/secondary hang scenario). This is a resource-exhaustion / DoS vector against the RPC handler triggered purely by an ordinary user's push content, no special privileges required.

### Likelihood Explanation
The non-atomic path is a normal, documented mode of proc-receive processing (`doc/hooks.md`, "receive_pack.go"), not privileged or admin-only functionality. Any client authorized to push can shape their push to hit this per-update loop and increase the number of individual reference updates, making the exploitation path straightforward and reachable via a normal write operation.

### Recommendation
Cap the number of reference updates processed per non-atomic proc-receive invocation (mirroring limits already used elsewhere, e.g. pagination/`limit` fields on other RPCs such as `FindRefsByOIDRequest.limit`), or batch multiple updates into fewer `updateref` sessions instead of spawning one subprocess (plus hook invocation) per reference. Alternatively, apply Gitaly's existing concurrency/backpressure mechanisms (`doc/backpressure.md`) to bound the cost of a single push based on the number of ref updates it contains, and reject/require chunked processing of excessively large pushes before entering the per-update hook/subprocess loop.

### Proof of Concept
1. As an authorized user, initiate a push using the `proc-receive` protocol (Git ≥ 2.29 client with `receive.procReceiveRefs` configured, or trigger the corresponding Gitaly RPC path directly).
2. Include a very large number (e.g., tens of thousands) of small reference updates (e.g., creating many lightweight branches) in the single push, with the server-side proc-receive handler operating in non-atomic mode (`handler.Atomic() == false`).
3. Observe that Gitaly's `procReceiveHook` (`internal/gitaly/hook/receivepack/receive_pack.go`) iterates the full list, and `receivePackReferenceUpdates` is invoked once per update, each spawning a new `git-update-ref` process and running the `update` hook — measure CPU/process-count growth on the primary Gitaly node proportional to the number of refs supplied, with no limit enforced by Gitaly on that count. 	logger log.Logger,
	cfg config.Cfg,
	req gitcmd.ReceivePackRequest,
	repo *localrepo.Repo,
	hookManager hook.Manager,
	tx storage.Transaction,

) (returnedErr error) {
	var acceptedUpdates []hook.ReferenceUpdate
	rejectedUpdates := make(map[git.ReferenceName]string)

	defer func() {
		if err := handler.Close(returnedErr); err != nil && returnedErr == nil {
			returnedErr = err
		}
	}()

	if handler.Atomic() {
		// Atomic reference updates are all or nothing. If this fails for any reason, return an error.
		err := receivePackReferenceUpdates(
			ctx, cfg, req, repo, hookManager, handler.ReferenceUpdates(), handler, handler,
		)
		if err != nil {
			return fmt.Errorf("updating references atomically: %w", err)
		}

		// There is no need to track rejected reference updates because we fail early if any updates
		// are not successful.
		acceptedUpdates = handler.ReferenceUpdates()

		// Non-atomic reference updates are performed one at a time. Errors due to an update hook

// receivePackReferenceUpdates is intended for use with receive-pack RPC handlers when executing the
// proc-receive hook. In addition to atomically updating references in bulk, it also manually
// invokes the update hook for each reference since the proc-receive hook disables the normal
// automatic execution of the update hook. Errors result in reference updates not being committed.
// If the error is due to update hook failure, a CustomHookError is returned to provide context
// regarding why the update hook failed.
func receivePackReferenceUpdates(
	ctx context.Context,
	cfg config.Cfg,
	req gitcmd.ReceivePackRequest,
	repo *localrepo.Repo,
	hookManager hook.Manager,
	updates []hook.ReferenceUpdate,
	stdout, stderr io.Writer,
) (returnedErr error) {
	hooksPayload, err := setupHooksPayloadEnv(ctx, cfg, req, repo, gitcmd.UpdateHook)
	if err != nil {
		return fmt.Errorf("creating hooks payload: %w", err)
	}

	updater, err := updateref.New(ctx, repo, updateref.WithNoDeref())
	if err != nil {
		return fmt.Errorf("spawning ref updater: %w", err)
	}
	defer func() {
		if err := updater.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("cancel ref updater: %w", err)
		}
	}()

	if err := updater.Start(); err != nil {
		return fmt.Errorf("start reference transaction: %w", err)
	}

	for _, update := range updates {
		if err := hookManager.UpdateHook(
			ctx,
			req.GetRepository(),
			update.Ref.String(),
			update.OldOID.String(),
			update.NewOID.String(),
			[]string{hooksPayload},
			stdout, stderr,
		); err != nil {
			return fmt.Errorf("running update hook: %w", err)
		}

		if err := updater.Update(update.Ref, update.NewOID, update.OldOID); err != nil {
			return fmt.Errorf("queueing ref to be updated: %w", err)
		}
	}

	if err := updater.Commit(); err != nil {
		return updateError{error: err}
	}

	return nil
}
