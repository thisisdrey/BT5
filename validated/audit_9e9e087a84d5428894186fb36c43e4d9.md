### Title
Attachment content hash is never verified against the requested `content_hash` before being persisted via `insert_instantiated_attachment` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any peer-supplied `Attachment` body from a `GetAttachment` HTTP response and inserts it into `context.attachments` without checking that its bytes hash to the `content_hash` that was actually requested (`AttachmentRequest.content_hash`). In the `Done` branch of `AttachmentsDownloader::run`, every attachment drained from that set is unconditionally persisted via `network.atlasdb.insert_instantiated_attachment(&attachment)`, regardless of whether `find_all_attachment_instances(&attachment.hash())` returned any matching rows.

### Finding Description
The equality the Atlas subsystem is supposed to preserve is: every attachment stored in the `attachments` table must correspond to a `content_hash` recorded by a confirmed on-chain contract-call operation (an `AttachmentInstance`), i.e. `stored_attachment_hash == some_confirmed_name_operation.content_hash`.

The code path that breaks this:
1. In `AttachmentsBatchStateContext::get_prioritized_attachments_requests` (lines 404-478), the node builds `AttachmentRequest { content_hash, sources, ... }` for a `content_hash` it legitimately learned from a confirmed `AttachmentInstance`, and sends it to a peer whose advertised inventory bit for that hash was set to 1 (`extend_with_inventories`, lines 490-528). Any remote peer can be selected as a source here simply by being one of `network.get_outbound_sync_peers()` and answering the inventory request with a `1` bit for the position corresponding to the requested hash - this requires no privilege, secret, or slot ownership.
2. When the attacker peer responds to the follow-on `GetAttachment` request, `extend_with_attachments` (lines 530-558) does:
   ```rust
   if let Ok(response) = response.decode_atlas_get_attachment() {
       self.attachments.insert(response.attachment);
       report.bump_successful_requests();
   }
   ```
   There is **no check** that `response.attachment.hash() == request.content_hash`. The attacker can therefore return arbitrary bytes unrelated to any on-chain commitment, and they are accepted as long as the HTTP response decodes.
3. In `AttachmentsDownloader::run`, the `Done` branch (lines 153-169):
   ```rust
   for attachment in context.attachments.drain() {
       let attachments_instances = network
           .atlasdb
           .find_all_attachment_instances(&attachment.hash())?;
       network
           .atlasdb
           .insert_instantiated_attachment(&attachment)?;
       for attachment_instance in attachments_instances.into_iter() {
           resolved_attachments.push((attachment_instance, attachment.clone()));
       }
       context.attachments_batch.resolve_attachment(&attachment.hash())
   }
   ```
   `find_all_attachment_instances(&attachment.hash())` is queried using the hash of the *actual bytes received*, not the hash that was originally requested. For a fabricated attachment, this lookup legitimately returns an empty vector - yet `insert_instantiated_attachment(&attachment)` is called unconditionally right after, with no `if !attachments_instances.is_empty()` guard. This persists the fabricated content into the `attachments`/instantiated-attachments table even though zero `attachment_instances` rows reference its hash.

No handshake/signature check, no `MAX_MESSAGE_LEN`/`MAX_PAYLOAD_LEN`-style guard, and no per-content-hash equality check exist along this path to prevent this - the only gate is the generic HTTP decode succeeding.

### Impact Explanation
An unprivileged remote peer that is (or can get itself selected as) an outbound sync source for a victim node can, upon receiving a legitimate `GetAttachment` request for some known `content_hash`, respond with fabricated/arbitrary bytes instead of the real attachment. The victim node will permanently store this fabricated data in its local Atlas SQLite `attachments` table via `insert_instantiated_attachment`, with zero matching rows in `attachment_instances` for that hash. This is a High-severity "attachment/BNS mismatch" condition: content is served/stored as if instantiated/canonical Atlas data, but it is not tied to any confirmed on-chain commitment. It is repeatable per download cycle/content-hash the node solicits, and can be used to pollute the node's Atlas storage with unbounded amounts of data disconnected from chain state.

### Likelihood Explanation
Preconditions are all attacker-controllable without privilege: be an outbound sync peer with an advertised data URL (`network.get_outbound_sync_peers()` / `get_data_url`), answer the `GetAttachmentsInv` request with a `1` bit for a page/position the victim is polling, and then answer the follow-up `GetAttachment` request with arbitrary bytes. No RPC secret, no slot key, no admin role is needed - this is exactly the unprivileged remote P2P/RPC interaction the threat model covers. The state machine reaching `Done` with `context.peers` non-empty and `context.attachments` populated occurs naturally as part of normal Atlas batch processing.

### Recommendation
In `extend_with_attachments` (or immediately in the `Done` branch of `run`), verify `response.attachment.hash() == request.content_hash` before inserting into `context.attachments`; discard/penalize (bump_failed_requests, mark peer faulty) on mismatch. Additionally, in the `Done` branch, only call `insert_instantiated_attachment` when `!attachments_instances.is_empty()` (i.e., there is at least one `AttachmentInstance` row referencing that hash), mirroring the guard already used elsewhere (`check_attachment_instances`), to avoid persisting attachments with no matching on-chain commitment.

### Proof of Concept
Rust test plan in `stackslib::net::atlas::download` tests:
1. Construct an `AttachmentsBatchStateContext` with one peer URL in `peers` and a fabricated `AttachmentRequest` for some `content_hash` `H` (not backed by any `AttachmentInstance` in the test `AtlasDB`).
2. Simulate `extend_with_attachments` being fed a `BatchedRequestsResult` whose `succeeded` map contains a `StacksHttpResponse` decoding to `GetAttachmentResponse { attachment: Attachment::new(b"evil bytes") }`, where `Attachment::new(b"evil bytes").hash() != H`.
3. Drive the state machine to `AttachmentsBatchStateMachine::Done(context)` with `context.attachments` containing this fabricated `Attachment`.
4. Call `AttachmentsDownloader::run` (or directly execute the `Done` branch logic) against a fresh `AtlasDB`.
5. Assert: `atlasdb.find_all_attachment_instances(&fabricated_attachment.hash())` returns `Ok(vec![])` (zero matching instances), yet `atlasdb.find_attachment(&fabricated_attachment.hash())` returns `Ok(Some(_))` after `run` completes - proving unauthenticated data was persisted without any corresponding on-chain commitment.     pub fn get_prioritized_attachments_requests(&self) -> BinaryHeap<AttachmentRequest> {
        let mut queue = BinaryHeap::new();
        let mut enqueued = HashSet::new();
        for ((contract_id, pages, _), peers_responses) in self.inventories.iter() {
            let missing_attachments = match self
                .attachments_batch
                .attachments_instances
                .get(contract_id)
            {
                None => continue,
                Some(missing_attachments) => missing_attachments,
            };
            // Note: we're getting missing_attachments (attachment_id: content_hash)
            for (attachment_index, content_hash) in missing_attachments.iter() {
                let page_index = attachment_index / AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;
                // Since there's a limit in the number of pages that a node can request,
                // we can potentially have multiple inventory request at once.
                if !pages.contains(&page_index) {
                    continue;
                }

                if enqueued.contains(content_hash) {
                    debug!("Atlas: {} already enqueued", content_hash);
                    continue;
                }

                let mut sources = HashMap::new();
                let position_in_page =
                    attachment_index % AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;

                for (peer_url, response) in peers_responses.iter() {
                    // Considering the response, look for the page with the index
                    // we're looking for.
                    let search_page = response.pages.iter().find(|page| page.index == page_index);

                    let has_attachment = search_page
                        .and_then(|search_page| {
                            search_page.inventory.get(position_in_page as usize)
                        })
                        .map(|result| *result == 1)
                        .unwrap_or(false);

                    if !has_attachment {
                        debug!(
                            "Atlas: peer does not have attachment ({}, {}) in its inventory {:?}",
                            page_index, position_in_page, response.pages
                        );
                        continue;
                    }

                    let report = self
                        .peers
                        .get(peer_url)
                        .expect("Atlas: unable to retrieve reliability report for peer");
                    sources.insert(peer_url.clone(), report.clone());
                }

                if sources.is_empty() {
                    warn!("Atlas: could not find a peer including attachment in its inventory");
                    continue;
                }

                // Success, we found at least one inventory including the attachment we're looking for.
                let request = AttachmentRequest {
                    sources,
                    content_hash: content_hash.clone(),
                    stacks_block_height: self.attachments_batch.stacks_block_height,
                    canonical_stacks_tip_height: self.attachments_batch.canonical_stacks_tip_height,
                };
                enqueued.insert(content_hash);
                queue.push(request);
            }
        }
        queue
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
