### Title
Path-traversal bypass in ijar `zipper` extraction via prefix-only directory-boundary check - (File: `third_party/ijar/zip_main.cc`)

### Summary
`third_party/ijar/zip_main.cc`'s `UnzipProcessor::Process` guards zip-entry extraction against path traversal with a raw string-prefix comparison of normalized paths, the same insufficient pattern described in the external report (`String.prototype.startsWith(baseDir)` analog). Because the comparison does not verify a directory-separator boundary, an attacker-crafted zip/jar archive with an entry name such as `../<output_root_basename>_evil/pwned` can escape the intended extraction directory whenever a sibling directory shares the `output_root` string as a prefix.

### Finding Description
The extraction guard is: [1](#0-0) 

```cpp
char path[PATH_MAX];
if (!concat_path(path, sizeof(path), output_root_, output_file_name)) {
  abort();
}
std::string normalized_root = normalize_path(output_root_);
std::string normalized = normalize_path(path);
if (normalized.compare(0, normalized_root.size(), normalized_root) != 0) {
  fprintf(stderr,
          "paths in the zip may not end up outside of the output "
          "directory: %s vs "
          "%s\n",
          path, normalized.c_str());
  abort();
}
```

`normalized.compare(0, normalized_root.size(), normalized_root)` is a pure string-prefix test on the normalized path, not a path-boundary test. There is no check that the character following the `normalized_root` prefix in `normalized` is a path separator (or that the strings are equal). This is structurally identical to the vulnerable `full.startsWith(base)` pattern in the report. Existing shell test `test_no_path_traversal` in `third_party/ijar/test/zip_test.sh` shows the maintainers were already aware of a traversal issue and added this check, but the fix itself did not close the sibling-prefix gap. [2](#0-1) 

`normalize_path` simply builds a `blaze_util::Path` and returns its printable form; it performs no separator-aware containment logic itself: [3](#0-2) 

Concrete bypass: if `output_root_` normalizes to `/tmp/out` (no trailing separator) and a malicious zip contains an entry whose relative path is `../out_evil/pwned`, then after `concat_path`+normalization the resulting path is `/tmp/out_evil/pwned`. `normalized.compare(0, strlen("/tmp/out"), "/tmp/out")` returns `0` (equal) because `"/tmp/out_evil/pwned"` literally begins with the character sequence `"/tmp/out"`, even though `/tmp/out_evil` is a sibling directory of `/tmp/out`, not a descendant. The guard silently passes and the file is written to `/tmp/out_evil/pwned`, i.e. outside `output_root_`.

### Impact Explanation
`zip_main.cc`'s `extract()` / `UnzipProcessor` is the extraction engine behind Bazel's `zipper` tool (`tools/zip/BUILD.tools`), used to unpack zip/jar archives whose contents are not necessarily produced by trusted, root-repo-controlled logic (e.g., archives fetched or built from external, attacker-influenced sources). A crafted archive can place files outside the intended extraction directory, leading to arbitrary file write/overwrite outside the sandboxed output directory the caller expects — a concrete CWE-22 escape of the declared extraction root, matching the report's impact class (unauthorized read/write outside a base directory due to a string-prefix boundary bug).

### Likelihood Explanation
Exploitation requires only that (a) the attacker can supply the contents of a zip/jar archive that gets fed into this `zipper`/ijar extraction path, and (b) a sibling directory name sharing the `output_root_` string prefix exists (or can be forced, since the attacker also controls the crafted entry name that creates the sibling, i.e. the entry name itself is `../<root_basename>_suffix/...`, so the "sibling" is created by the same operation — no pre-existing filesystem state is required beyond the parent of `output_root_` being writable, which it is by construction). This makes the bypass reliably attacker-triggerable purely from archive content, with no reliance on a race condition, matching a Medium/AC:H-style bar (attacker needs to control the archive being extracted, but no additional privilege).

### Recommendation
Replace the prefix compare with a separator-aware boundary check, e.g.:
```cpp
if (normalized != normalized_root &&
    normalized.compare(0, normalized_root.size() + 1, normalized_root + "/") != 0) {
  // reject
}
```
ensuring `normalized_root` is canonicalized with a trailing separator (or explicitly checking `normalized[normalized_root.size()] == '/'`) before treating the prefix match as containment, mirroring the fix pattern in the external report (`full !== base && !full.startsWith(base + sep)`).

### Proof of Concept
1. Choose/derive `output_root_` = `/tmp/zipout` (as computed via `concat_path(output_root, ..., cwd, exdir)` in `extract()`, `third_party/ijar/zip_main.cc:172-182`).
2. Craft a zip archive containing a single entry named `../zipout_evil/pwned.txt` (relative to the extraction root).
3. Run the `zipper x <archive> -d zipout` (or equivalent `extract()` invocation) from `/tmp`.
4. Observe that `concat_path` + `normalize_path` produce `/tmp/zipout_evil/pwned.txt`; the boundary check at `third_party/ijar/zip_main.cc:136` passes because `"/tmp/zipout_evil/pwned.txt".compare(0, 12, "/tmp/zipout")` matches, and the file is written outside `/tmp/zipout`.
5. A JUnit/`src/test/shell` regression test analogous to the existing `test_no_path_traversal` in `third_party/ijar/test/zip_test.sh` (lines 277-283) should be added with an archive entry `../<basename(output_root)>_evil/pwned` and assert the file does **not** land outside the extraction directory (current code will fail this assertion).
