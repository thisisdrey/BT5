### Title
Missing size validation before storing gossiped attachment content allows storage exhaustion via oversized attachments - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AtlasConfig.attachments_max_size` is defined as a configuration bound (default floor `ATTACHMENTS_MAX_SIZE_MIN = 1_048_576`) intended to cap the size of any individual `Attachment.content` accepted by the node [1](#0-0) . `GetAttachmentResponse` deserializes attacker-controlled hex-encoded bytes directly into an `Attachment{content: Vec<u8>}` with no length check at deserialization time [2](#0-1) , and the response-processing path that ultimately stores these attachments does not appear to enforce `attachments_max_size` against `content.len()` before accepting the attachment.

### Finding Description
`Attachment` is a plain wrapper around `Vec<u8>` with no size bound enforced in its constructor [3](#0-2) . The `GetAttachmentResponse` deserializer decodes arbitrary hex payload from the wire directly into `Attachment::new(bytes)` with no size validation [2](#0-1) . Only the hash of the content is checked for correctness against the expected `content_hash` via `Attachment::hash()` (`Hash160::from_data`) [4](#0-3) , not its length. `AtlasConfig.attachments_max_size` exists precisely to bound attachment content size, with `AtlasConfig::validate()` only checking that the *configured* value is not too small — it does not enforce the bound at runtime on incoming attachment content [5](#0-4) .

I was not able to fully confirm within the available tool budget whether `AttachmentsBatchStateContext::extend_with_attachments` (download.rs:530-558, per the question) or the DB insertion routine `insert_uninstantiated_attachment` in `db.rs` perform a runtime check of `content.len() <= attachments_max_size` before storing the attachment. I found matches for `attachments_max_size` in `db.rs` and `download.rs` were not conclusively read line-by-line in my final pass, so I cannot state with certainty whether this specific check is present or absent in those exact functions.

### Impact Explanation
Uncertain / not fully verified. If confirmed absent, an attacker could gossip oversized attachment content for a legitimate queued `content_hash`, and repeated over many distinct content hashes this could exhaust attachment storage in `AtlasDB`, bounded loosely by `max_uninstantiated_attachments` (default `MAX_UNINSTANTIATED_ATTACHMENTS_MIN = 50_000`) rather than by actual on-chain commitment size [6](#0-5) .
