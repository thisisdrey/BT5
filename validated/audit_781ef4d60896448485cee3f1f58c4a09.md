Based on my research, I found a concrete analog in the `ValidateMultiSign` TVM precompiled contract, which is directly reachable by any transaction that triggers a smart contract calling precompile address `0x66`.

### Title
Unbounded array allocation from attacker-controlled length word in `ValidateMultiSign` precompile causes node OOM/crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Redis cjson bug class is "a crafted length/size field drives unchecked heap allocation, causing memory corruption/crash." java-tron's `ValidateMultiSign` precompiled contract parses a signature-array length directly from calldata and, on the legacy (pre-`allowTvmSelfdestructRestriction`) code path, uses that value to allocate a Java array with no upper bound before any signature data is validated.

### Finding Description
`ValidateMultiSign.execute` parses the calldata into 32-byte words and reads the signature-array length from an attacker-controlled word: [1](#0-0) 

When `VMConfig.allowTvmSelfdestructRestriction()` is disabled (i.e. the corresponding hard-fork proposal has not been activated on that chain), the code calls `extractBytesArray` directly, without the `sigArraySize > MAX_SIZE` guard that exists on the newer branch: [2](#0-1) 

`extractBytesArray` (and its sibling `extractSigArray`/`extractBytes32Array`) then allocates a Java object array sized directly from `words[offset].intValueSafe()` before doing any bounds validation against the actual calldata size: [3](#0-2) 

`intValueSafe()` returns any value up to `Integer.MAX_VALUE` as long as the word occupies ≤4 bytes — it does not check that the value is sane relative to the surrounding data: [4](#0-3) 

Because the length word is just one 32-byte word of the calldata, an attacker can submit a very small transaction (a handful of ABI words) while setting the length field to a huge value (e.g. `0x7FFFFFFF`), forcing `new byte[len][]` (or `new byte[len]` in `extractBytes32Array`) to be allocated with billions of elements — before the loop that would otherwise throw `ArrayIndexOutOfBoundsException` on the mismatched calldata ever executes. `getEnergyForData` only charges energy proportional to the actual (small) calldata length, so the attack is essentially free in energy terms while the allocation attempt is unbounded: [5](#0-4) 

### Impact Explanation
An uncontrolled, attacker-sized heap allocation inside a precompile executed during ordinary transaction validation/execution can throw `OutOfMemoryError`, crashing the JVM process on every full node and witness node that processes the transaction (it is part of consensus, so all nodes execute it identically). This maps to the accepted impact class "node crash or halt, chain split" since a network-wide simultaneous crash across nodes at the same block height can also cause a chain halt.

### Likelihood Explanation
Reaching this code requires only: (1) a deployed contract that calls precompile address `0x66` (`ValidateMultiSign`), or a directly crafted `TriggerSmartContract`/static call to it, and (2) the target chain not having activated the `allowTvmSelfdestructRestriction` hard-fork proposal (this is a `ForkBlockVersionEnum`-gated feature in `DynamicPropertiesStore`/`ConfigLoader`, meaning any chain/testnet/private java-tron network that has not enabled this specific proposal remains exposed). Any unprivileged transaction broadcaster can construct the calldata; no special privileges or existing account permission are required to trigger the vulnerable code path itself (the permission check happens only after the array is already allocated).

### Recommendation
- Validate the parsed array length against a sane upper bound (e.g. `MAX_SIZE` or a value consistent with the remaining calldata length) in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` themselves, unconditionally, rather than only in the newer `allowTvmSelfdestructRestriction` branch.
- Cross-check that `len * itemSize` does not exceed `data.length - offset` before allocating, similar to the `isValidAbiEncoding` check already used elsewhere in this file.
- Apply the same length-vs-remaining-data validation pattern that was already applied to `ContractEventParser.subBytes` (see `subBytes` bounds check) to these precompile helper methods: [6](#0-5) 

### Proof of Concept
1. Craft calldata for `ValidateMultiSign` (precompile `0x66`) with the standard 5-word ABI header (`address`, `permissionId`, `data` offset, `sigArray` offset, `sigArray` also referencing `data`).
2. At the `sigArray` offset word, set the encoded length to `0x000000000000000000000000000000000000000000000000000000007FFFFFFF` (or any value close to `Integer.MAX_VALUE`) instead of a length matching the actual number of appended signature words.
3. Send a `TriggerSmartContract` transaction (or a constant call) whose contract invokes this precompile with the crafted calldata, on a network where `allowTvmSelfdestructRestriction` is not active.
4. `extractBytesArray`/`extractSigArray` executes `new byte[len][]` with `len` ≈ 2^31−1 before validating any remaining data length, attempting a multi-gigabyte allocation and triggering `OutOfMemoryError` on every node processing the transaction.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {

  protected static byte[] subBytes(byte[] src, int start, int length) {
    if (ArrayUtils.isEmpty(src)) {
      throw new OutputLengthException("source data is empty");
    }
    if (start < 0 || start >= src.length || length < 0 || length > src.length - start) {
      throw new OutputLengthException(
          "data start:" + start + ", length:" + length + ", src.length:" + src.length);
    }
    byte[] dst = new byte[length];
    System.arraycopy(src, start, dst, 0, length);
    return dst;
