The `account_locks` field is guarded by a single `Mutex<AccountLocks>` and `try_lock_transaction_batch` performs the entire check-then-lock sequence (`can_lock_accounts` loop followed by `lock_accounts` loop) synchronously within one call while the caller holds this mutex for the whole batch. [1](#0-0) [2](#0-1) 

There is no window where `can_lock_accounts` can observe a stale key set that `lock_accounts` then mutates differently, because both operations occur on the same `&mut self` within a single, non-reentrant function call — no other thread can acquire the mutex or mutate `write_locks`/`readonly_locks` between the check and the mutate phases. Within a single transaction's own key list, duplicates are already rejected before locks are ever attempted by `validate_account_locks`/`has_duplicates`, which is called prior to lock attempts. [3](#0-2)  Across different transactions in the same batch, `can_lock_accounts` for a later transaction correctly observes locks already applied by `lock_accounts` for earlier transactions in the same `try_lock_transaction_batch` call, since the two loops run strictly sequentially per-transaction and the per-transaction check/lock pair for entry N happens after locks for entries < N are already applied in the check phase's iteration order — actually, re-reading the code: the check phase (`can_lock_accounts`) runs for *all* transactions in the batch *before* any locks are applied (first `for_each` loop), and only afterward does the `lock_accounts` mutation loop run for all passing transactions in the second `map` loop. [4](#0-3) 

This means `can_lock_accounts` for transaction B does NOT see the effect of transaction A's `lock_accounts` in the same batch if A comes before B, because the check loop runs to completion before any `lock_accounts` call executes. If transaction A and transaction B in the same batch write to the same account key, `can_lock_accounts` will independently evaluate both against the *pre-batch* lock state (since neither has mutated `write_locks`/`readonly_locks` yet during the check phase) and both will pass the check, then both will be locked in the mutation phase — resulting in a write-lock count of 2 for the same key from two transactions in the same batch, which are then treated as independently "locked" and eligible for concurrent execution scheduling, violating the write-exclusivity invariant.

This matches the exact code-level flaw described in the question: `can_lock_accounts` (check) runs against a state that has not yet been updated by `lock_accounts` calls for earlier transactions in the same batch, allowing two transactions with an overlapping writable key within a single batch to both be granted locks.

### Title
Same-batch write-lock double-grant due to check-then-lock phase separation in `try_lock_transaction_batch` - ([File: accounts-db/src/account_locks.rs])

### Summary
`AccountLocks::try_lock_transaction_batch` first runs `can_lock_accounts` for every transaction in the batch against the pre-batch lock state, and only afterward applies `lock_accounts` for all transactions that passed. Two transactions in the same batch that write to the same account key both pass the check phase (since neither has mutated lock state yet) and are then both granted write locks in the mutation phase, producing two concurrently-held write locks on the same key.

### Finding Description
`try_lock_transaction_batch` at [2](#0-1)  is structured as two separate passes over `validated_batch_keys`:
1. A `for_each` loop calls `self.can_lock_accounts(keys.clone())` for every transaction in the batch and marks failures, but does not mutate `write_locks`/`readonly_locks`.
2. Only after that full loop completes does the second pass call `self.lock_accounts(keys)` for every transaction that passed the check.

Because `can_lock_accounts` [5](#0-4)  only consults `self.write_locks` / `self.readonly_locks` as they exist prior to the batch (via `can_write_lock`/`can_read_lock`, which are pure read checks against current state), two distinct transactions within the same batch that both write to pubkey `P` will each independently see `P` as unlocked during the check phase, since neither transaction's `lock_accounts` call has executed yet. Both entries therefore pass `can_lock_accounts`, and the subsequent mutation phase increments `write_locks[P]` to `2`, meaning both transactions are reported as "locked" via `Ok(())` results and can be scheduled/executed as if they hold exclusive access to `P`.

An attacker only needs to submit a normal transaction batch (e.g., via QUIC to the TPU) containing two sanitized transactions that each write to the same account — no duplicate keys within a single transaction are required (which `validate_account_locks`/`has_duplicates` would catch), only overlap *across* transactions in the batch, which is not checked by this code path at all.

### Impact Explanation
This breaks the fundamental account-locking invariant that transactions writing to the same account cannot execute concurrently. Two transactions that both believe they hold an exclusive write lock on the same account could be picked up by different execution threads/units concurrently, leading to a race condition on account state, an incorrect balance/state result, or a bank hash mismatch relative to what deterministic single-threaded replay would produce. This falls into the "invalid recorded block" / "state inconsistency" bounty category for Agave.

### Likelihood Explanation
This requires no privilege beyond submitting a normal transaction batch with two independent transactions that both write the same account — a trivially constructible input for any client submitting transactions to the TPU. It does not require duplicate keys within one transaction (already blocked by `validate_account_locks`), malformed transactions, or any special timing/race — the flaw is deterministic based on the two-pass structure of `try_lock_transaction_batch` itself.

### Recommendation
Restructure `try_lock_transaction_batch` to interleave the check and lock steps per-transaction (check then immediately lock before moving to the next transaction), so that later transactions in the same batch see locks already applied by earlier transactions in the same batch, exactly mirroring how batches are processed elsewhere in the runtime (e.g., `Bank::lock_accounts`-style per-transaction check+lock). Alternatively, pre-aggregate write/read intents across the whole batch before the check phase and reject any batch where two transactions conflict on the same key, rather than only checking against pre-batch state.

/// Validate account locks before locking.
pub fn validate_account_locks(
    account_keys: AccountKeys,
    tx_account_lock_limit: usize,
) -> TransactionResult<()> {
    if account_keys.len() > tx_account_lock_limit {
        Err(TransactionError::TooManyAccountLocks)
    } else if has_duplicates(account_keys) {
        Err(TransactionError::AccountLoadedTwice)
    } else {
        Ok(())
    }
}

thread_local! {
    static HAS_DUPLICATES_SET: RefCell<AHashSet<Pubkey>> = RefCell::new(AHashSet::with_capacity(MAX_TX_ACCOUNT_LOCKS));
}

/// Check for duplicate account keys.
fn has_duplicates(account_keys: AccountKeys) -> bool {
    // Benchmarking has shown that for sets of 32 or more keys, it is faster to
    // use a HashSet to check for duplicates.
    // For smaller sets a brute-force O(n^2) check seems to be faster.
    const USE_ACCOUNT_LOCK_SET_SIZE: usize = 32;
    if account_keys.len() >= USE_ACCOUNT_LOCK_SET_SIZE {
        HAS_DUPLICATES_SET.with_borrow_mut(|set| {
            let has_duplicates = account_keys.iter().any(|key| !set.insert(*key));
            set.clear();
            has_duplicates
        })
    } else {
        for (idx, key) in account_keys.iter().enumerate() {
            for jdx in idx + 1..account_keys.len() {
                if key == &account_keys[jdx] {
                    return true;
                }
            }
        }
        false
    }
}
