Audit Report

## Title
Donated tokens sent to the DAP general staker/incentive pot are snapshotted into `ErasValidatorReward`/`ErasValidatorIncentiveBudget` as if they were legitimate inflation, silently distorting era reward accounting - (File: `substrate/frame/staking-async/src/reward.rs`)

## Summary
`EraRewardManager::snapshot_era_rewards` computes the amount moved into an era's reward pot by reading the entire `reducible_balance` of the general DAP pot accounts (`general_staker_pot`, `general_incentive_pot`), rather than a value tracked independently of the account's live balance. Since these pot accounts are ordinary derived `AccountId`s reachable via a plain `Balances::transfer_keep_alive`, anyone can inflate the balance that gets swept into `EraRewardAllocation` and subsequently recorded as `ErasValidatorReward`/`ErasValidatorIncentiveBudget`, distorting the DAP-governed reward curve without any minting.

## Finding Description
`EraRewardManager::snapshot_era_rewards` reads `T::Currency::reducible_balance(&general_staker_pot, Preservation::Preserve, Fortitude::Polite)` and `reducible_balance(&general_incentive_pot, ...)` and transfers that entire amount into freshly-created era pots, returning it as `EraRewardAllocation { staker_rewards, validator_incentive }`. [1](#0-0)  There is no independent accumulator of "how much DAP actually dripped this era" that is reconciled against the live balance before the snapshot — the account balance itself is the sole input to the calculation. [2](#0-1) 

`pallet-dap` mints and drips issuance into these general pots via `mint_and_distribute`/`drip_issuance`, but the pot accounts (`general_staker_pot`, `general_incentive_pot`, derived via `T::RewardPots::pot_account(RewardPot::General(...))`) are ordinary accounts with no incoming-transfer restriction — they are not frozen, held, or access-controlled. [3](#0-2)  Any unprivileged, funded account can compute the deterministic pot address off-chain and call `Balances::transfer_keep_alive` (or any transfer) to that address, inflating the balance that will be swept at the next era boundary.

## Impact Explanation
This is a genuine runtime logic flaw: the era-reward snapshot conflates "DAP-issued inflation currently sitting in the pot" with "total balance of the pot," so any donation is folded into `ErasValidatorReward`/`ErasValidatorIncentiveBudget` and subsequently paid out to validators/nominators via `payout_stakers`, distorting the DAP-governed reward curve (e.g. the 85/15 or 65/20/15 splits) without requiring any new minting. This matches the "runtime bug that compromises intended behavior" impact class in the gate, since it breaks the invariant that per-era payouts correspond exactly to governance-approved DAP budget rather than an attacker-influenced value. [4](#0-3) 

## Likelihood Explanation
No special privilege is required: the pot account IDs are deterministically derived and computable off-chain, and ordinary `Currency::transfer` calls into them are unrestricted. The snapshot runs unconditionally every era, so any balance sitting in the general pot — donated or dripped — is swept and committed on-chain without further attacker action. [5](#0-4) 

## Recommendation
Track the amount actually dripped into each general pot with an accumulator independent of the account's live balance (incremented by DAP drips, decremented by the snapshot), and have `snapshot_era_rewards` move only the tracked delta instead of `reducible_balance`. Any balance beyond the tracked delta should be treated as unexpected/extra and excluded from `ErasValidatorReward`/`ErasValidatorIncentiveBudget` accounting (e.g., returned, burned, or diverted to a separate bucket).

## Proof of Concept
1. Compute the deterministic account for `RewardPot::General(RewardKind::StakerRewards)` via `T::RewardPots::pot_account`.
2. From any unprivileged, funded account, call `Balances::transfer_keep_alive(general_staker_pot, X)` before the next era rotation.
3. At era-end, `EraRewardManager::snapshot_era_rewards` reads `reducible_balance(&general_staker_pot, ...)`, which now includes `X`, and transfers it (minus ED) into the era-specific pot as `staker_rewards`. [6](#0-5) 
4. `ErasValidatorReward` for that era is inflated by `X` above the DAP-governance-intended amount, and `payout_stakers` distributes the inflated amount to validators/nominators.

	/// Snapshots the general reward pots into era-specific pots.
	///
	/// DAP drips inflation continuously into the general pots. At era boundary,
	/// this transfers the accumulated balances (minus ED) into era pots.
	pub(crate) fn snapshot_era_rewards(era: EraIndex) -> EraRewardAllocation<BalanceOf<T>> {
		let staker_era_pot = Self::create(era, RewardKind::StakerRewards);
		let incentive_era_pot = Self::create(era, RewardKind::ValidatorSelfStake);

		let general_staker_pot =
			T::RewardPots::pot_account(RewardPot::General(RewardKind::StakerRewards));
		let general_incentive_pot =
			T::RewardPots::pot_account(RewardPot::General(RewardKind::ValidatorSelfStake));

		// Leave ED in the general pots to keep them alive.
		let staker_balance = T::Currency::reducible_balance(
			&general_staker_pot,
			Preservation::Preserve,
			Fortitude::Polite,
		);
		let incentive_balance = T::Currency::reducible_balance(
			&general_incentive_pot,
			Preservation::Preserve,
			Fortitude::Polite,
		);

		let actual_staker = if !staker_balance.is_zero() {
			match T::Currency::transfer(
				&general_staker_pot,
				&staker_era_pot,
				staker_balance,
				Preservation::Preserve,
			) {
				Ok(_) => staker_balance,
				Err(e) => {
					log!(error, "Era {:?}: staker reward transfer failed: {:?}", era, e);
					defensive!("Failed to transfer staker rewards to era pot");
					Zero::zero()
				},
			}
		} else {
			Zero::zero()
		};
