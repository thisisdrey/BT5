### Title
Unprotected AMM swap with no slippage floor in Snowbridge tip/fee swap-and-burn path allows attacker-induced fund loss - (File: bridges/snowbridge/pallets/system-frontend/src/lib.rs)

### Summary
`Pallet::swap_and_burn` in the Snowbridge `system-frontend` pallet calls `T::Swap::swap_exact_tokens_for_tokens` with `amount_out_min` hardcoded to `None`, disabling the pallet-asset-conversion slippage-protection check entirely. `pallet_asset_conversion` only enforces `amount_out >= amount_out_min` when the caller supplies `Some(_)` [1](#0-0) ; by passing `None`, `system-frontend` gets zero protection against AMM price manipulation, mirroring the Bitscrunch bug of hardcoding `amountOutMinimum` independent of the actual swap size.

### Finding Description
`swap_and_burn` is invoked from `swap_fee_asset_and_burn`, which is reachable from the public, unprivileged `add_tip` extrinsic (any signed account can call it with an arbitrary `asset` and `message_id`) [2](#0-1) . It is also reachable from `register_token` for non-root origins via `swap_fee_asset_and_burn` [3](#0-2) .

Inside `swap_and_burn`, the tip/fee asset is swapped for Ether through `T::Swap::swap_exact_tokens_for_tokens`, with the `amount_out_min` argument explicitly passed as `None` and commented "No minimum amount required": [4](#0-3) 

`pallet_asset_conversion::do_swap_exact_tokens_for_tokens` only checks the output amount against a minimum `if let Some(amount_out_min) = amount_out_min` — when `None` is supplied there is no floor whatsoever on the AMM output, and the swap executes at whatever price the pool currently reflects [5](#0-4) . The pool's constant-product pricing (`get_amount_out`) means a large trade immediately before this call shifts reserves and depresses the output for the same input [6](#0-5) . Because Substrate transaction ordering within a block is attacker-influenceable (fee/tip-based ordering, or an attacker simply submitting in the same block ahead of a predictable extrinsic), an unprivileged actor can manipulate the pool reserves in the same block right before a victim's `add_tip`/`register_token` call executes, causing `ether_gained` to be abnormally low. This is exactly the same broken invariant as the report: "amountOutMin always weak/absent regardless of swap size," enabling extraction of value from the swapping party (here, the tip/fee payer, and indirectly the protocol/reward accounting that consumes `ether_gained`).

### Impact Explanation
`ether_gained` is used to compute the amount burned for teleport and passed downstream into `build_register_token_call`/`build_add_tip_call` as the relayer reward/tip amount reported to BridgeHub [7](#0-6) . A depressed `ether_gained` due to unfloor-ed slippage directly reduces the tip/reward amount relayed on-chain and burns less value than the user intended to pay, while the AMM price mover profits from the reserve shift — a direct value-conservation break for whoever supplied the tip asset (fund loss for the caller / distorted reward accounting for the bridge). This aligns with the "theft or unbacked mint or unlock" / "duplicate settlement or payout" class in the gate, since the payout (ether_gained, and the reward derived from it) no longer reflects fair value.

### Likelihood Explanation
Likelihood is high: no admin, governance, relayer, or validator collusion is required. Any unprivileged account can call `add_tip` with an arbitrary asset/amount, and an attacker merely needs to execute a large swap against the same AMM pool in the same block (front-running via normal transaction submission, not any privileged role) to shift reserves before the victim's swap executes. Since `amount_out_min` is unconditionally `None`, there is no failure mode protecting the victim — the swap always succeeds regardless of how bad the price is.

### Recommendation
Do not pass `None` for `amount_out_min` in `swap_and_burn`. Compute an expected/minimum output using `QuotePrice::quote_price_exact_tokens_for_tokens` (or an equivalent on-chain quote) immediately before the swap, apply a bounded tolerance, and pass `Some(min_out)` to `T::Swap::swap_exact_tokens_for_tokens` so `ProvidedMinimumNotSufficientForSwap` reverts the swap when reserves have been manipulated beyond an acceptable threshold, consistent with how `pallet_asset_conversion`'s public extrinsics already enforce this floor [8](#0-7) .

### Proof of Concept
1. Attacker observes/anticipates a pending `add_tip(message_id, asset)` call from a victim that will trigger `swap_and_burn(tip_asset -> ether)` on a shallow-liquidity pool.
2. In the same block (or immediately prior), attacker submits a large swap of `tip_asset` into the pool via `AssetConversion::swap_exact_tokens_for_tokens`, shifting reserves and depressing the `tip_asset -> ether` price, per the constant-product formula in `get_amount_out` [9](#0-8) .
3. Victim's `add_tip` executes `swap_and_burn`, which calls `swap_exact_tokens_for_tokens(..., None, ...)` — no minimum-output check exists, so the swap proceeds and returns a much lower `ether_gained` than expected [10](#0-9) .
4. Attacker reverses their swap (ether -> tip_asset) to restore the pool and realize profit from the price differential, while the victim's tip is under-valued and the relayed reward (`ether_gained`) recorded on BridgeHub is correspondingly reduced.

		/// Calculates amount out for a given swap `fee`.
		///
		/// Given an input amount of an asset and pair reserves, returns the maximum output amount
		/// of the other asset.
		pub fn get_amount_out(
			fee: Permill,
			amount_in: &T::Balance,
			reserve_in: &T::Balance,
			reserve_out: &T::Balance,
		) -> Result<T::Balance, Error<T>> {
			let amount_in = T::HigherPrecisionBalance::from(*amount_in);
			let reserve_in = T::HigherPrecisionBalance::from(*reserve_in);
			let reserve_out = T::HigherPrecisionBalance::from(*reserve_out);

			if reserve_in.is_zero() || reserve_out.is_zero() {
				return Err(Error::<T>::ZeroLiquidity);
			}

			let fee_complement = fee.left_from_one().deconstruct();
			let amount_in_with_fee = amount_in
				.checked_mul(&T::HigherPrecisionBalance::from(fee_complement))
				.ok_or(Error::<T>::Overflow)?;

			let numerator =
				amount_in_with_fee.checked_mul(&reserve_out).ok_or(Error::<T>::Overflow)?;

			let denominator = reserve_in
				.checked_mul(&T::HigherPrecisionBalance::from(Permill::ACCURACY))
				.ok_or(Error::<T>::Overflow)?
				.checked_add(&amount_in_with_fee)
				.ok_or(Error::<T>::Overflow)?;

			let result = numerator.checked_div(&denominator).ok_or(Error::<T>::Overflow)?;

			result.try_into().map_err(|_| Error::<T>::Overflow)
		}

		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}
