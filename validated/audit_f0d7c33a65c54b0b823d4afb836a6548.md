### Title
Missing bulk complexity metering for `VariantFieldInstantiation` and `StructVariantInstantiation` tables in `check_module_complexity` — (`third_party/move/move-binary-format/src/check_complexity.rs`)

### Summary
`check_module_complexity` bulk-meters `FieldInstantiation` and `StructDefInstantiation` tables but omits equivalent bulk metering for the `VariantFieldInstantiation` and `StructVariantInstantiation` tables. An attacker can publish a module with up to 65535 `VariantFieldInstantiation` entries carrying complex type-parameter signatures that are never referenced by any bytecode instruction. These entries are invisible to the complexity budget, allowing the module to pass `check_module_complexity` with a true complexity far exceeding the budget. The accepted module then forces the bytecode verifier to iterate all entries in an unmetered path, causing disproportionate validator CPU work per publish transaction.

### Finding Description
`check_module_complexity` (line 401) calls `meter_field_instantiations()` for the `FieldInstantiation` table (line 411) but has no corresponding call for the `VariantFieldInstantiation` table. The single-entry method `meter_variant_field_instantiation` exists (line 180) and is correctly wired into `meter_code` for bytecode-referenced entries (line 285), but no bulk sweep of the table is performed. The same omission applies to `StructVariantInstantiation` — `meter_struct_variant_instantiation` exists (line 139) but there is no `meter_struct_variant_instantiations()` bulk call in `check_module_complexity`.

Because `meter_signature` charges on every call (line 99), the design intent is that N entries referencing the same signature cost N × signature_cost. For `VariantFieldInstantiation`, only bytecode-referenced entries are charged; the rest cost 0.

### Impact Explanation
A module with 65535 `VariantFieldInstantiation` entries each referencing a 50-node type-parameter signature has an uncounted complexity of ~26.2M against a budget of ~5.24M. The module is accepted by `check_module_complexity` and proceeds to the bytecode verifier, which calls `verify_variant_field_instantiations_contextless` (line 779) — an unmetered loop over all entries. This allows an unprivileged user to force disproportionate CPU work on every validator during module publish, constituting a validator slowdown / material availability risk.

### Likelihood Explanation
Exploitable by any account that can submit a package publish transaction. No privileged access, governance, or validator control is required. The `VariantFieldInstantiation` table is a standard part of the Move binary format for modules with enum/variant types. Constructing a crafted `CompiledModule` with a large table is straightforward using the Move binary format API.

### Recommendation
Add a `meter_variant_field_instantiations()` bulk function mirroring `meter_field_instantiations()` (lines 197–207), and a `meter_struct_variant_instantiations()` bulk function mirroring `meter_struct_def_instantiations()` (lines 155–165). Call both from `check_module_complexity` alongside the existing bulk calls (lines 408–411).
