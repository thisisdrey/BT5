### Title
`redeem()` in `pallet-psm` bypasses the decimals-drift guard applied to `mint()`, allowing stale/mismatched decimal ratios to under- or over-pay redemptions - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
`pallet-psm::mint()` and `pallet-psm::redeem()` both convert between an "internal" stablecoin (pUSD) and an "external" asset using a decimals ratio, exactly the kind of share↔asset conversion described in the seed report (AuraVault confusing rewardPool shares with AuraVault assets). `mint()` derives its conversion decimals through a guarded helper that verifies the live asset metadata still matches the registration snapshot, while `redeem()` reads the snapshotted decimals directly, skipping that guard entirely. This asymmetry means the two entry points use different amounts of trust in the decimals values, breaking the invariant that the "ratio of internal to external units is authoritative and validated" for both mint and redeem paths.

### Finding Description
In `mint()`, the decimals used for `external_to_internal` / `internal_to_external` conversions are obtained via: [1](#0-0) 

`ensure_decimals_match` is the "Runtime drift guard" described in the accompanying prdoc, returning `DecimalsMismatch` if live asset metadata diverges from the `AssetDecimals`/`StableDecimals` snapshot taken at registration — this halts the asset until governance intervenes.

In `redeem()`, however, the decimals are pulled directly from the stored snapshot without going through that guard: [2](#0-1) 

The rest of `redeem()` uses these unguarded decimals to compute `external_out` via `internal_to_external`, and to compute `effective_internal_net` via `external_to_internal`, then burns `effective_internal_net` and transfers `external_out` from the PSM reserve to the caller: [3](#0-2) 

Since `redeem()` never calls `ensure_decimals_match`, any live-metadata drift that would cause `mint()` to halt with `DecimalsMismatch` is silently ignored on the redeem path. The pallet's own documented design intends the drift guard to protect *both* mint and redeem ("`mint`/`redeem` return `DecimalsMismatch` if live metadata diverges... that asset halts until governance intervenes" — per the prdoc), so this is a real deviation from intended behavior rather than a documented asymmetry. [4](#0-3) 

### Impact Explanation
This falls under "runtime bugs that compromise intended behavior" and "theft or unbacked mint/unlock" for the underpriced/overpriced path: if the live decimals metadata of `external_asset` changes after registration (a scenario the drift guard was explicitly built to catch), `redeem()` still computes `external_out`/`effective_internal_net` from the stale snapshot instead of failing safely. Depending on the direction of drift, users redeeming through the unguarded path can either receive more external asset than their burned internal asset is worth (draining the PSM reserve, i.e. unbacked value extraction) or receive less (fund loss for users), while `mint()` for the same asset would simply halt. This directly parallels the seed vulnerability's core defect: an entrypoint using an unguarded/incorrect ratio for a value that should be validated before conversion.

### Likelihood Explanation
No privileged actor is required to trigger the bug — any signed user can call `redeem()` at any time. Likelihood of the underlying trigger condition (external asset metadata drift after registration) depends on external factors, but the coded asymmetry between `mint()` and `redeem()` is a permanent, always-present logic gap that a background agent or auditor can trivially verify by diffing the two dispatchables; it needs no malicious peer, relayer, validator, or governance abuse to exist as a defect in the code as written.

### Recommendation
Apply the same `ensure_decimals_match` guard in `redeem()` that is used in `mint()`, deriving `ext_decimals`/`internal_decimals` through the guarded helper instead of reading `external.decimals` and `info.internal_decimals` directly, so both entrypoints halt symmetrically on `DecimalsMismatch` when live metadata diverges from the registered snapshot.

### Proof of Concept
1. Register a PSM pair with `internal_decimals = 18` and `external.decimals` snapshotted as `6` in `AssetDecimals`.
2. Externally (e.g., via a foreign-asset registry update outside PSM's control) the live decimals metadata for the external asset changes to `18`.
3. Call `mint()` for this pair: `ensure_decimals_match` detects the live-vs-snapshot mismatch and returns `Error::DecimalsMismatch`, halting the asset as designed. [5](#0-4) 
4. Call `redeem()` for the same pair with a valid `internal_amount`: it never calls `ensure_decimals_match`, so it proceeds using the stale snapshot decimals (`6`) instead of the current live decimals (`18`), producing an `external_out` computed with the wrong power-of-ten scale. [6](#0-5) 
5. The PSM reserve pays out (or the user's burn is under/over-counted by) a 10^12-scale factor error, resulting in either reserve drainage or a user redeeming far less than entitled — while the identical asset is simultaneously halted for minting.
