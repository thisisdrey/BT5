### Title
Phantom overflow in ParticipateAssetIssueActuator causes legitimate token-purchase transactions to revert unexpectedly - (File: actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java)

### Summary
`ParticipateAssetIssueActuator` computes the exchange amount for buying a TRC10 token as `cost * num / trxNum` using `long` arithmetic, multiplying before dividing. Because `num` and `trxNum` are attacker-(issuer)-controlled `int32` values with no practical upper bound, and `cost` is attacker-(buyer)-controlled up to their own TRX balance, the intermediate product `cost * num` can overflow `long` even when the true mathematical result of `cost * num / trxNum` is small and perfectly valid.

### Finding Description
In both `validate()` and `execute()`, the exchange rate is applied as:
```java
long exchangeAmount = multiplyExact(cost, assetIssueCapsule.getNum());
exchangeAmount = floorDiv(exchangeAmount, assetIssueCapsule.getTrxNum());
``` [3](#0-2) [4](#0-3) 

`num` and `trxNum` are set by the asset issuer at asset-creation time via `AssetIssueContract`, whose only validation is `trxNum > 0` and `num > 0`, with no upper limit [1](#0-0) . Both fields are declared `int32` in the protobuf definition [2](#0-1) , so an issuer can set, e.g., `num = 2_000_000_000` and `trxNum = 2_000_000_000` (an economically valid ~1:1 exchange rate). Any buyer attempting to participate with a moderately large `amount` (`cost`) — well within their real TRX balance and far below `Long.MAX_VALUE` — will trigger `cost * num` to exceed `Long.MAX_VALUE`, causing `multiplyExact` to throw `ArithmeticException` even though `cost * num / trxNum` (the actual intended result) is small and entirely valid.

This is precisely the "phantom overflow" pattern described in the referenced report: an intermediate multiplication in a multiply-then-divide sequence overflows even though the final, mathematically correct result would fit comfortably in the target width.

The test suite already demonstrates awareness of *unconditional* overflow (very large `cost` values causing `multiplyExact` to throw) as expected/acceptable behavior [5](#0-4) , but that test uses an extreme `num` value chosen to overflow regardless of `trxNum`; it does not cover the case where `num`/`trxNum` are both large but proportionate (yielding a small, valid true ratio), which is the actual phantom-overflow scenario.

### Impact Explanation
Any TRC10 asset issuer can configure `num`/`trxNum` (fully under issuer control, unbounded) such that the exchange calculation phantom-overflows for any buyer trying to purchase with a realistic amount of TRX. This causes `ParticipateAssetIssueContract` transactions to unexpectedly and permanently revert (`ArithmeticException` → `ContractValidateException`/`ContractExeException`), denying legitimate participation in that asset's crowdsale entirely — a functional denial-of-service on a core, broadcastable contract type reachable by any unprivileged account. Since the token sale window is time-bounded (`start_time`/`end_time`), buyers may be permanently unable to participate for the token's entire sale, and the issuer's ability to raise funds via the sale is broken with no way for an ordinary participant to route around it.

### Likelihood Explanation
High: the issuer sets `num`/`trxNum` at asset-creation time and only needs `num, trxNum > 0`; no economic or size cap prevents choosing large values. Any single participant transaction with a realistic `amount` can then trigger the overflow — no special privileges, coordination, or unusual network conditions are required, only a single signed `ParticipateAssetIssueContract` and a single signed `AssetIssueContract` (which can even be issued by an attacker specifically to target other users' purchase attempts, or arise unintentionally from a well-meaning issuer picking large precision-adjusted values).

### Recommendation
Compute `exchangeAmount = cost * num / trxNum` using `BigInteger` (or another wide-intermediate technique such as Uniswap's `FullMath`) instead of raw `long multiplyExact`/`floorDiv`, mirroring the pattern already used elsewhere in the codebase for other multiply-then-divide computations (e.g., `RepositoryImpl.usageToBalance`, `ResourceProcessor.calculateGlobalLimitV2`, `ExchangeInjectActuator`/`ExchangeWithdrawActuator`) [6](#0-5) [7](#0-6) . This avoids overflowing the intermediate product while still truncating only at the final division, matching the mathematically correct result and eliminating unintended reverts.

### Proof of Concept
1. Issuer creates a `AssetIssueContract` with `num = 2_000_000_000`, `trxNum = 2_000_000_000` (both pass `validate()` since they are `> 0` and within `int32`).
2. A participant broadcasts a `ParticipateAssetIssueContract` with `amount` (i.e., `cost`) = e.g. `10_000_000_000` sun (10,000 TRX, a realistic amount).
3. In `validate()`/`execute()`, `multiplyExact(cost, num)` computes `10_000_000_000 * 2_000_000_000 = 2 * 10^19`, which exceeds `Long.MAX_VALUE` (~9.22 * 10^18) and throws `ArithmeticException`, even though the true value `cost * num / trxNum = 10_000_000_000` is a perfectly valid, in-range result.
4. The transaction fails with "No enough balance"/`ContractValidateException`-style overflow error (per the existing overflow test pattern) [8](#0-7) , denying a legitimate purchase.
