### Title
Unauthenticated block upload triggers network-wide relay via `set_relay_message` regardless of `broadcast=Some(false)` - (File: stackslib/src/net/api/postblock_v3.rs)

### Summary
The `broadcast && !authenticated` gate at line 120 only blocks requests that explicitly request `broadcast=1` without auth, but the accept-and-relay logic in `try_handle_request` (lines 197-202) sets a relay message purely based on `data_resp.accepted`, not on `self.broadcast`. This means an unauthenticated POST (`broadcast=0`, no secret) that successfully parses and is accepted for local storage will still be gossiped to the rest of the network.

### Finding Description
`try_parse_request` computes `authenticated` from the `authorization` header and `broadcast` from the query string, and only rejects the request outright when `broadcast=1` and `!authenticated` [1](#0-0) . When `broadcast=0` (the default, no query param at all), the handler proceeds without ever requiring `authenticated`, decodes the block, and sets `self.broadcast = Some(false)` [2](#0-1) .

In `try_handle_request`, `self.broadcast.unwrap_or(false)` is passed into `Relayer::process_new_nakamoto_block_ext` as an internal flag [3](#0-2) . Separately, and unconditionally on `self.broadcast`, if the returned `accepted` result is true, the handler calls `node.set_relay_message(StacksMessageType::NakamotoBlocks(...))` [4](#0-3) . This relay-message queuing is gated only on acceptance of the block by chainstate — not on `self.broadcast` or `authenticated` at all.

Thus the equality claimed in the question ("relay set == authenticated set") does not hold in this file: a `broadcast=0`, unauthenticated, well-formed, chainstate-acceptable block still results in `node.set_relay_message(...)` being invoked, which queues the block for propagation to the node's peers just as if it had been submitted with `broadcast=1` and a valid secret.

### Impact Explanation
This allows an attacker with no RPC secret to get their own submitted Nakamoto block relayed to the rest of the network — i.e., unauthenticated write causing network-wide propagation of data that bypassed the authenticated-broadcast gate. Whether this is a genuine security-relevant issue depends on whether `process_new_nakamoto_block_ext`'s block-acceptance path already performs full consensus/signature validation before returning `accepted=true` — if so, the "forged" nature of the relayed block is limited to blocks that are already valid Nakamoto blocks (i.e., not junk), which would reduce the severity substantially, since any relayed block still must pass full validation before being treated as canonical elsewhere. This part of the analysis (whether `process_new_nakamoto_block_ext`'s accept path validates signatures/consensus before returning "accepted") could not be confirmed within this iteration, since the body of `Relayer::process_new_nakamoto_block_ext` in `stackslib/src/net/relay.rs` and `StacksNodeState::set_relay_message` in `stackslib/src/net/mod.rs` were not retrieved before the tool budget ran out.

### Likelihood Explanation
Preconditions: attacker needs only network/RPC connectivity to the `/v3/blocks/upload/` endpoint — no secret, no privileged role, no query parameter required (default `broadcast=false`). Attacker cost is a single well-formed POST with a block body that chainstate will accept for local storage. This is repeatable per accepted block.

### Recommendation
Gate the `node.set_relay_message(...)` call in `try_handle_request` on `self.broadcast == Some(true)` in addition to `data_resp.accepted`, so that unauthenticated (`broadcast=false`) submissions are only stored locally and never queued for relay to peers, matching the documented intent that non-broadcast POSTs are accepted-but-not-relayed.

### Proof of Concept
Rust test plan (net test in `stackslib/src/net/api/tests/postblock_v3.rs` or equivalent):
1. Construct an `RPCPostBlockRequestHandler::new(Some("secret".into()))`.
2. Build an HTTP POST to `/v3/blocks/upload/` with no `authorization` header and no `broadcast` query param, body = valid consensus-serialized `NakamotoBlock` bytes that chainstate will accept.
3. Call `try_parse_request` — assert it succeeds and `self.broadcast == Some(false)`.
4. Call `try_handle_request` with a `StacksNodeState` wired to accept the block (`process_new_nakamoto_block_ext` returns accepted=true).
5. Assert on the mock/stub for `node.set_relay_message` (or inspect the network relay-message queue after the call) — the bug is confirmed if `set_relay_message` was invoked despite `self.broadcast == Some(false)` and no `authorization` header was ever supplied.

Note: I was unable to fully verify within the available iterations whether `Relayer::process_new_nakamoto_block_ext`'s own internal `broadcast` flag independently gates any network announcement (which could make the `set_relay_message` call redundant-but-harmless, or could itself be the primary/sole relay path controlled correctly by `self.broadcast`). Confirming the full downstream effect of `set_relay_message` (i.e., does it actually push the block onto the P2P broadcast queue, or is it just a diagnostic/local hint) requires reading `stackslib/src/net/mod.rs` (`set_relay_message`) and `stackslib/src/net/relay.rs` (`process_new_nakamoto_block_ext`) in full, which was not completed.
