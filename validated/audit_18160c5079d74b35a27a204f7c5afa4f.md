### Title
Dust-transfer griefing fills `MAX_TOKENS_PER_USER` account lists, causing every deposit/seize/liquidation transfer to revert — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary

CVE-2020-8623 is a remotely-triggered crash: a crafted input forces a state in which the target's request handling fails unconditionally (liveness/DoS bug class, not gas exhaustion). The Metronome analog lives in the per-account token lists. `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens()` once an account holds `MAX_TOKENS_PER_USER` (30) entries in `depositTokensOfAccount` + `debtTokensOfAccount` (`Pool.sol:79,143-148`). These functions are invoked internally by `DepositToken` whenever a balance goes from 0 to non-zero — including on plain `transfer`, `deposit`, and `seize` — and by `DebtToken` on `issue`/`mint`. An unprivileged attacker can deliberately push a victim's or the fee collector's list to the cap with dust `DepositToken.transfer`s of each registered collateral type, after which every code path that would create a new token entry for that account reverts.

### Finding Description

Two concrete crash surfaces:

1. `Pool.sol:143-148` — `onlyIfAdditionWillNotReachMaxTokens` checks `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` and reverts. Since deposit tokens are transferable ERC20 shares, an attacker calls `DepositToken.transfer(victim, 1 wei)` for each of the pool's deposit tokens the victim does not yet hold (the pool itself can register at most 30, `Pool.sol:703`), filling the list.
2. Consequences:
   - **Victim deposit blocked**: `DepositToken.deposit`/`transfer` into the victim reverts in `addToDepositTokensOfAccount`, so a victim whose position is drifting toward liquidation cannot add a *new* collateral type to rescue it — the crafted input turned a routine recovery call into a guaranteed revert.
   - **Fee-collector seize blocked — all fee-bearing liquidations revert**: `Pool.liquidate` ends with `depositToken_.seize(account_, _poolRegistry.feeCollector(), _fee)` (`Pool.sol:591-593`). `seize` performs a balance 0→>0 update for the fee collector, which calls back into `addToDepositTokensOfAccount`. If an attacker dusts `feeCollector` so its combined list reaches 30, every `liquidate` that produces `_fee > 0` reverts, blocking liquidation of unhealthy positions protocol-wide.

No privileged action is required: both attacks use only public token transfers. Reentrancy guards, `SynthContext`, pause flags, and supply caps do not intercept them; the check in `onlyIfAdditionWillNotReachMaxTokens` is precisely what gets weaponized.

### Impact Explanation

- Victim accounts are temporarily frozen out of collateral top-ups and new debt positions; if the position goes unhealthy while blocked, it is liquidated — direct loss of the liquidation incentive portion of collateral.
- Dusting `feeCollector` converts `Pool.liquidate` into an unconditional revert for all liquidations with a non-zero protocol fee. Underwater positions cannot be closed, causing protocol insolvency/bad-debt accumulation and temporary freezing of seized collateral flows until governance rotates the fee collector or the list is drained.

### Likelihood Explanation

Attack cost is bounded: the pool supports at most `MAX_TOKENS_PER_USER` deposit tokens, so filling the fee collector's list requires at most 30 dust transfers (fewer for a victim already holding some tokens). No flash loan, oracle manipulation, or privileged role is needed. Mitigating factor: an affected EOA victim can remove entries by transferring a dust balance out, and governance can rotate `feeCollector`; the impact is therefore temporary-freezing / forced-liquidation rather than permanent loss, matching a High-confidence Medium/High DoS.

### Recommendation

- Do not apply `onlyIfAdditionWillNotReachMaxTokens` on paths that credit third parties (`seize` to `feeCollector`, incoming `transfer`), or raise/de-scope the cap for protocol-owned recipients.
- Make `seize` to `feeCollector` and `liquidate`'s fee leg resilient: e.g., route fees through a dedicated accounting bucket instead of a balance that mutates the recipient's token list, or let `addToDepositTokensOfAccount` silently skip for protocol addresses.
- Alternatively, revert-free "force-add" for the fee collector plus a keeper-callable cleanup that consolidates its list.

### Proof of Concept

Foundry/Hardhat fork sketch (deterministic):

```solidity
// Setup: pool has deposit tokens dt1..dtN registered; victim holds a position.
// Attacker (EOA) fills victim's list:
for (uint i; i < pool.getDepositTokens().length; ++i) {
    IDepositToken dt = IDepositToken(pool.getDepositTokens()[i]);
    if (dt.balanceOf(victim) == 0) {
        dt.transfer(victim, 1); // attacker first mints dust via own deposit
    }
}
// Assert list is full:
assertGe(
    pool.getDepositTokensOfAccount(victim).length +
    pool.getDebtTokensOfAccount(victim).length,
    pool.MAX_TOKENS_PER_USER()
);
// 1) Victim can no longer deposit a NEW collateral type:
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDepositToken.deposit(amount);

// 2) Fee-collector variant — brick liquidations:
//    repeat dust loop with victim = poolRegistry.feeCollector()
vm.prank(liquidator);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
pool.liquidate(msSynthetic, unhealthyAccount, repayAmount, depositToken);
// reverts inside depositToken_.seize(account_, feeCollector, _fee)
// at Pool.sol:592
```

Reproduction steps: fork a deployed pool (e.g., mainnet `Pool1`), deposit dust of each collateral into attacker-controlled deposit tokens, transfer 1 wei of each to `feeCollector` (or a victim), then call `liquidate` on any position yielding `_fee > 0`, or `deposit` a fresh collateral as the victim — both revert with `UserReachedMaxTokens`, demonstrating the crafted-input crash of the protocol's liquidation and deposit paths.
