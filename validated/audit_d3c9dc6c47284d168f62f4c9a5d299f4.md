### Title
ETH-implicit Wallet Contract lets a self-signed `AddKey`/`DeleteKey` action be routed to an arbitrary named account instead of the signer's own account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
`WalletContract::rlp_execute` is a public entry point that decodes a Secp256k1-signed Ethereum-style transaction into a NEAR action and forwards it as a `Promise` to an attacker-supplied `target: AccountId` parameter. For `AddKey`/`DeleteKey` calldata, the code documents (and the type name `SelfNearNativeAction` implies) that the receiver "should be equal to the current account," but this restriction is only enforced for the `EthImplicit` target case — not for `TargetKind::OtherNearAccount`, which is the normal case for any existing named account. As a result, the signer of the wallet's own private key can direct an `AddKeyAction`/`DeleteKeyAction` at any other existing named account.

### Finding Description
`rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:89-128`) calls `internal::parse_rlp_tx_to_action`, which decodes ADD_KEY/DELETE_KEY calldata into `ParsableTransactionKind::SelfNearNativeAction` without any receiver check [1](#0-0) , unlike `FUNCTION_CALL_SELECTOR`/`TRANSFER_SELECTOR` which explicitly assert `target.as_str() == receiver_id.as_str()` [2](#0-1) .

In `parse_rlp_tx_to_action`, the `SelfNearNativeAction` branch only special-cases `TargetKind::EthImplicit` (converting the action into a harmless zero-value transfer); for every other target kind (`CurrentAccount` or `OtherNearAccount`) the original `AddKey`/`DeleteKey` action passes through unchanged as `TransactionKind::NearNativeAction`: [3](#0-2) 

`validate_tx_relayer_data` only requires that the signed transaction's `to` field equal `account_id_to_address(target)` for the `OtherNearAccount` case — it never requires `target == current_account_id` for self-only actions: [4](#0-3) 

Finally, `action_to_promise` unconditionally sends the resulting action (including `AddKey`/`DeleteKey`) to the attacker/user-controlled `target`, never substituting `current_account_id`: [5](#0-4) 

Because `tx.to` and `target` are both chosen and signed by the wallet-account owner themselves (not by an untrusted relayer — the relayer only forwards bytes; the owner's Secp256k1 signature is what authorizes the action per `validate_tx_relayer_data`'s `tx.address == context.current_address` check), the account owner can trivially compute `to = account_id_to_address("alice.near")`, sign an Ethereum transaction with `data` = ADD_KEY_SELECTOR calldata, and call `rlp_execute(target = "alice.near", tx_bytes)`. The runtime-level `action_add_key`/`action_delete_key` handlers perform no actor/predecessor authorization check against the receiving account (confirmed in `runtime/runtime/src/access_keys.rs:149-192` and `:52-91` — they operate purely on whatever `account_id` the receipt was routed to), so the resulting `AddKeyAction`/`DeleteKeyAction` receipt executes successfully against `alice.near` if that account exists.

This lets any eth-implicit wallet holder add a full-access key to (or delete a key from) any other existing named NEAR account, without that account's consent — a complete authorization bypass across accounts, directly analogous to the reported bug class where a "critical function" (`AddKey`/`DeleteKey`, intended to be self-restricted like `rescue`/`blacklist` were intended to be owner-restricted) lacks the access-control check its design assumes.

### Impact Explanation
This is a theft/authorization-escalation-across-accounts vulnerability: an attacker controlling any eth-implicit wallet account can add a full-access key to an arbitrary victim named account and drain its funds, or delete the victim's existing keys to lock them out — a direct path to fund theft and account takeover across unrelated accounts, satisfying the "concrete theft" / "authorization escalation across accounts" acceptance criteria.

### Likelihood Explanation
High. Exploitation requires no special privileges: any holder of an eth-implicit account (created simply by transferring $NEAR to a `0x...` account id) can construct the RLP transaction locally, compute `to = keccak256("victim.near")[12:32]`, sign it with their own key, and submit it via `rlp_execute` — no relayer collusion, no guessing/preimage work, and no dependence on any privileged component.

### Recommendation
Enforce that `AddKey`/`DeleteKey` (`ParsableTransactionKind::SelfNearNativeAction`) can only ever be routed to `current_account_id`, regardless of `target_kind`. Concretely, in `parse_rlp_tx_to_action`'s `SelfNearNativeAction` branch, reject (or force to a no-op) any case where `target != context.current_account_id`, mirroring the explicit receiver-equality check already used for `FUNCTION_CALL_SELECTOR`/`TRANSFER_SELECTOR`, and/or have `action_to_promise` always target `current_account_id` for `AddKey`/`DeleteKey` actions rather than the caller-supplied `target`.

### Proof of Concept
1. Attacker owns eth-implicit account `X` (address `0xAAAA...`), created via a $NEAR transfer, running the deployed wallet contract.
2. Attacker picks victim `target = "alice.near"` (any existing named account) and computes `to = account_id_to_address("alice.near")` = last 20 bytes of `keccak256("alice.near")`.
3. Attacker builds an RLP-encoded Secp256k1-signed Ethereum transaction from address `0xAAAA...` with `to = <that hash>`, `data = ADD_KEY_SELECTOR || abi_encode(pubkey=<attacker's ed25519 key>, is_full_access=true, ...)`, and the correct nonce.
4. Attacker (or any relayer, even themselves) calls `X.rlp_execute(target="alice.near", tx_bytes_b64=<signed tx>)`.
5. `validate_tx_relayer_data` passes (`tx.address==current_address`, `to==account_id_to_address(target)`); `parse_tx_data` returns `Action::AddKey{...}` as `SelfNearNativeAction`; since `target_kind = OtherNearAccount("alice.near")` (not `EthImplicit`), the action passes through unmodified as `TransactionKind::NearNativeAction`.
6. `action_to_promise("alice.near", AddKeyAction{...})` creates `Promise::new("alice.near").add_access_key(...)`, which the runtime executes with no cross-account authorization check, granting the attacker's key full access to `alice.near`.

fn action_to_promise(target: AccountId, action: near_action::Action) -> Result<Promise, Error> {
    match action {
        near_action::Action::FunctionCall(action) => Ok(Promise::new(target).function_call(
            action.method_name,
            action.args,
            action.deposit,
            action.gas,
        )),
        near_action::Action::Transfer(action) => Ok(Promise::new(target).transfer(action.deposit)),
        near_action::Action::AddKey(action) => match action.access_key.permission {
            near_action::AccessKeyPermission::FullAccess => {
                Err(Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey)))
            }
            near_action::AccessKeyPermission::FunctionCall(access) => Ok(Promise::new(target)
                .add_access_key_allowance_with_nonce(
                    action.public_key,
                    access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
                    access.receiver_id,
                    access.method_names.join(","),
                    action.access_key.nonce,
                )),
        },
        near_action::Action::DeleteKey(action) => {
            Ok(Promise::new(target).delete_key(action.public_key))
        }
    }
