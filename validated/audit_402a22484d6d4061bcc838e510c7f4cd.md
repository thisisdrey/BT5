## Title
Unbounded interest-delta vs. treasury-LP subtraction can permanently brick vault deposit/redeem accrual - ([File: mainnet/contracts/vault/v0-vault-stx.clar], and identical logic in the other `v0-vault-*.clar` contracts)

### Summary
The reported LPDA issue is a Solidity-checked-math underflow: a linear decay (`startPrice - dropPerSecond*timeElapsed`) that a bad, unvalidated parameter combination can push negative, permanently reverting every future call and bricking the contract. In Zest's vaults, `calc-treasury-lp-preview` performs an analogous unguarded subtraction, `(- ta-preview reserve-inc)`, where `reserve-inc` is a fee-cut of freshly-projected interest and `ta-preview` is the vault's currently tracked assets. Clarity aborts (rather than wrapping) on unsigned underflow, so if `reserve-inc` ever exceeds `ta-preview`, every subsequent call into this code path reverts, with no way to recover the relationship going forward.

### Finding Description
`calc-treasury-lp-preview` computes the treasury's share-mint amount from newly accrued interest: [1](#0-0) 

```
(define-private (calc-treasury-lp-preview)
  (let ((scaled-principal (var-get principal-scaled))
        (idx (var-get index))
        (next (next-index))
        (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
        (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
        (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
        (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
        (ta-preview (total-assets-preview)))
    (if (> reserve-inc u0)
        (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))
        u0)))
```

`debt-delta` is the interest that would accrue between the last stored `index` and the `next-index` projected from `stacks-block-time - last-update` — i.e., it grows with elapsed dormancy time and the current variable interest rate, both of which are unbounded and outside admin control on a per-call basis (rate is driven purely by utilization via `interpolate-rate`, and `time-delta` grows every second the vault goes untouched): [2](#0-1) 

`reserve-inc` is only guarded against being `u0`; it is never checked against `ta-preview` before the subtraction `(- ta-preview reserve-inc)` executes. `ta-preview` is `total-assets-preview`, i.e. the vault's currently tracked assets plus interest accrued *since inception up to now* — a much smaller quantity than the compounding delta that can build up over a long dormant period combined with a sustained high utilization rate: [3](#0-2) 

Because Clarity has no unchecked/wrapping arithmetic, `(- ta-preview reserve-inc)` throws a runtime error whenever `reserve-inc > ta-preview`, exactly mirroring the Solidity checked-math revert in `LPDA.getPrice`. Once the projected interest delta for the elapsed period is large enough (long time since `last-update` at a high borrow rate) relative to `ta-preview`, this function reverts — and since `time-delta` and the compounded rate only grow further with each additional second of inactivity, the imbalance cannot self-correct; it gets worse, not better, exactly like the LPDA drop continuing to widen the underflow window as time passes.

### Impact Explanation
If `calc-treasury-lp-preview` reverts, any public entry point (deposit/redeem/borrow/repay previews and the corresponding treasury-LP-minting logic that shares this computation) that depends on it will abort. This can permanently freeze deposit/redeem flows for the affected vault, i.e., temporary-to-permanent freezing of user funds and unclaimed treasury/LP yield in that vault, matching the in-scope "temporary freezing of funds" / "permanent freezing of unclaimed yield" impact classes. It also affects `vault share math and interest accrual`, one of the explicitly in-scope areas.

### Likelihood Explanation
Reaching this state requires (a) a vault going a long period without any accrual-triggering transaction (deposit/redeem/borrow/repay) while (b) utilization/interest rate stays high, so that the projected `debt-delta` for that dormant window grows large relative to the vault's `ta-preview`. Neither condition requires privileged access or DAO misconfiguration — it can occur under ordinary market conditions (e.g., a low-liquidity, high-utilization vault that simply isn't interacted with for an extended stretch). This is a plausible, unprivileged-reachable scenario, though it needs a combination of dormancy and rate conditions to actually trigger the underflow, so likelihood is moderate rather than trivial to hit on every call.

### Recommendation
Guard the subtraction the same way the codebase already guards `debt-delta` and other similar computations elsewhere (e.g. `(if (> ta-preview reserve-inc) (- ta-preview reserve-inc) u0)`, with an additional fallback such as skipping the treasury-LP mint or capping `reserve-inc` at `ta-preview` when it would otherwise exceed it), and ensure any code path that forces an accrual after long dormancy cannot itself be bricked by having `reserve-inc` computed proportionally/capped rather than as an unconditional multiplicative fee on an unbounded compounding delta.

### Proof of Concept
Conceptual reproduction (mirrors the LPDA PoC structure):
1. Deploy `v0-vault-stx`, have a borrower take out a large loan so `principal-scaled`/`total-borrowed` are large relative to `assets`, driving utilization (and thus `interest-rate`) high.
2. Do not call any vault function (no deposit/redeem/borrow/repay) for a long period so `last-update` stays stale while `stacks-block-time` advances — `time-delta` in `next-index` grows large.
3. Call any function that triggers `calc-treasury-lp-preview` (a deposit/redeem preview or the accrual-linked mint flow). `debt-delta = new-debt - old-debt` reflects the entire dormant period's compounding interest, and `reserve-inc = debt-delta * fee-reserve / BPS` can exceed `ta-preview = total-assets-preview`.
4. The subtraction `(- ta-preview reserve-inc)` aborts, reverting the call — and every subsequent call suffers the same or worse imbalance since `time-delta` and thus `debt-delta` only grow further, permanently freezing that entry point for the vault.

Note: I was unable to fully confirm, within the remaining exploration budget, whether `calc-treasury-lp-preview`'s abort actually propagates to block all of `deposit`/`redeem`/`borrow` (as opposed to being used only in a read-only preview endpoint that callers could simply avoid), because the call sites of `calc-treasury-lp-preview` versus the "live" `calc-treasury-lp` mint function were not retrieved before the tool budget ran out. Confirm this call-graph and the exact numeric thresholds (fee-reserve bps, `SECONDS-PER-YEAR-BPS`, `INDEX-PRECISION`) needed to trigger the underflow before treating this as fully validated.
