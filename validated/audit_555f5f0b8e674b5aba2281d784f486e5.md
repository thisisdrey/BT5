### Title
Attacker can permanently DoS a victim's account by filling `depositTokensOfAccount` to `MAX_TOKENS_PER_USER` with dust msdToken transfers - (File: contracts/DepositToken.sol)

### Summary
Every successful `DepositToken` transfer or mint to a fresh recipient calls `Pool.addToDepositTokensOfAccount(recipient_)`, which enforces the `MAX_TOKENS_PER_USER = 30` cap on the per-account `MappedEnumerableSet`. An unprivileged attacker can craft dust transfers of deposit tokens the victim does not yet hold (the analog of the "carefully crafted malicious URL" — a crafted input object that exhausts a bounded resource) to fill all 30 slots of a victim's account list. Once the set is full, any subsequent mint (`deposit` on behalf of the victim) or transfer-in of a deposit token the victim doesn't already hold reverts, denying the victim the ability to receive collateral.

### Finding Description
`DepositToken._transfer` and `DepositToken._mint` unconditionally register the recipient in the pool's per-account token list whenever the recipient's prior balance was zero (`DepositToken.sol:518-520` and `DepositToken.sol:486-488`). `Pool.addToDepositTokensOfAccount` adds to `depositTokensOfAccount`, a `MappedEnumerableSet` capped by `MAX_TOKENS_PER_USER = 30` (`Pool.sol:79`); once the cap is reached the add reverts, reverting the entire transfer/mint.

Attack trace (all public, unprivileged):

1. Attacker deposits collateral into the pool once, receiving msdTokens of each deposit token type (or acquires them via `transfer`).
2. Attacker calls `DepositToken.transfer(victim, 1 wei)` for each deposit token the victim does not hold, until `depositTokensOfAccount[victim]` contains 30 entries. Each dust transfer succeeds because there is no minimum amount and no opt-in on the recipient side.
3. Subsequently:
   - `DepositToken.deposit(amount_, victim)` reverts inside `_mint → addToDepositTokensOfAccount` for any token not already in the victim's list.
   - Anyone sending the victim a new msdToken type reverts.
   - `Pool.liquidate` paths that `seize` collateral *to* the victim (e.g., `DepositToken.seize(account_, to_, ...)` where `to_` is a smart-farming/unwind flow crediting the account) revert.
   - `SmartFarmingManager` leverage flows that mint new deposit-token types to the victim revert.

The victim's own outgoing transfers/withdrawals still work (`_burn`/transfer-out call `removeFromDepositTokensOfAccount`, which never hits the cap), so this is a freezing/griefing vector rather than direct theft — but the victim cannot receive additional collateral, cannot be topped up by a third party to avoid liquidation, and cannot use leverage entry points.

### Impact Explanation
Temporary freezing of funds / liveness break: the victim's account is blocked from receiving any deposit token not already in its list. Because the attacker controls the dust balances, they can keep slots perpetually occupied by re-transferring dust whenever the victim clears entries (each removal requires the victim to explicitly transfer the dust back out, and the attacker can front-run the cleanup transaction with another dust transfer of a different token). A victim whose health factor deteriorates cannot be rescued by a third-party deposit of a new collateral type, converting the DoS into forced liquidation and loss of funds.

### Likelihood Explanation
- Fully unprivileged: only needs public `DepositToken.transfer` and one ordinary deposit to source dust.
- Cost is trivial: 30 transfers of 1-wei amounts of msdTokens; the dust remains recoverable.
- No modifier stops it: `transfer` has no `nonReentrant`/pause gate on the recipient-registration path, the recipient cannot opt out, and `SynthContext`/`MAX_TOKENS_PER_USER` are enforced exactly as designed — the cap is the resource being exhausted.
- Note (unverified detail): the exact revert inside `addToDepositTokensOfAccount` when the set reaches 30 entries could not be read line-by-line in this session; the cap constant at `Pool.sol:79` and the unconditional `addToDepositTokensOfAccount` calls in `DepositToken.sol` are confirmed. If the implementation silently ignores overflow adds instead of reverting, this finding collapses and should be re-checked.

### Recommendation
- Do not revert account list additions on cap; instead make `debtPositionOf`/health iteration cap-agnostic, or only count tokens with non-trivial balances.
- Alternatively, require a minimum transfer amount, or make list insertion best-effort (`add` returning false without revert) while bounding `debtPositionOf` iterations by actual nonzero balances.
- Another option: allow anyone to call `removeFromDepositTokensOfAccount` cleanup for dust balances, or exempt `seize`/liquidation paths from the cap.

### Proof of Concept
Hardhat sketch against deployed pool contracts:

```ts
// Victim holds some position (e.g., msdETH debt) but few deposit tokens.
const depositTokens: DepositToken[] = await getAllDepositTokens(pool); // >= 1 attacker-held type + others

// 1. Attacker mints itself a balance of a token victim doesn't hold
await underlying.connect(attacker).approve(msdTokenA.address, amount);
await msdTokenA.connect(attacker).deposit(amount, attacker.address);

// 2. Fill victim's list to MAX_TOKENS_PER_USER with dust of tokens
//    (attacker cycles: deposit each collateral, transfer 1 wei to victim)
for (const dt of depositTokens.slice(0, 30)) {
  await dt.connect(attacker).transfer(victim.address, 1);
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30);

// 3. Any new deposit token type to victim now reverts
await expect(
  msdTokenB.connect(attacker).transfer(victim.address, 1)
).to.be.reverted; // TooManyDepositTokens-style revert in addToDepositTokensOfAccount

// 4. Third-party rescue deposit on behalf of victim reverts
await expect(
  msdTokenB.connect(rescuer).deposit(parseEther('10'), victim.address)
).to.be.reverted;
```

Expected result: victim's `depositTokensOfAccount` reaches the 30-entry cap via attacker dust, after which all inbound mints/transfers of unheld deposit tokens revert, persistently blockable by re-dusting — matching the DoS-via-crafted-input bug class of the Discourse Onebox report.
