### Title
Forged `relay_hints` in StackerDB chunk push allow targeted broadcast-suppression of a victim peer - (File: `stackslib/src/net/p2p.rs`)

### Summary
`PeerNetwork::sample_broadcast_peers` blindly trusts the `relay_hints` field carried inside an incoming `StacksMessage` (e.g. a `StackerDBPushChunk`) to decide which already-connected peers should be excluded from re-broadcast. Because `relay_hints` is attacker-supplied data with no cryptographic binding to the actual relay path, an attacker who owns a valid StackerDB slot can forge a `RelayData` entry naming a victim peer's `public_key_hash`, causing the network to skip sending the chunk to that victim even though the victim never actually relayed it.

### Finding Description
In `sample_broadcast_peers` (`stackslib/src/net/p2p.rs:1495-1580`), the function builds a `relay_pubkhs` set directly from the `relay_hints` slice passed in [1](#0-0) , and then removes any currently-connected peer whose public key hash is in that set from both `outbound_dist` and `inbound_dist`, with the comment "don't send a message to anyone who sent this message to us" [2](#0-1) .

The equality the code assumes — "peer named in relay_hints" == "peer that actually relayed this message to us" — is never verified. `relay_hints` is simply data embedded in the `StacksMessage` payload/relay-hint list, populated by whoever constructs the message (in this case, a StackerDB slot owner constructing a `StackerDBPushChunkData` push). Since a legitimate slot owner can produce a validly signed chunk, they control the `relay_hints` list attached to their gossip of that chunk. Nothing in `handle_unsolicited_stacks_message` / `handle_unsolicited_StackerDBPushChunk` (`stackslib/src/net/unsolicited.rs:539-577`) cross-checks the `relay_hints` entries against the actual conversation/relay history recorded by the local peer (e.g. against `self.peers` inbound/outbound identities that were truly observed forwarding this specific chunk). The only checks performed on the incoming push are chunk-signature/slot-ownership validation (in `handle_unsolicited_StackerDBPushChunk`), not relay-hint authenticity.

Consequently, when this chunk is subsequently rebroadcast via `NetworkRequest::Broadcast` → `sample_broadcast_peers`, any victim peer V whose `public_key_hash` was forged into the `relay_hints` list is silently dropped from both `outbound_dist` and `inbound_dist`, and thus excluded from `outbound_sample`/`inbound_sample`/the final coalesced neighbor list, even though V never received or relayed the chunk. This lets colluding attackers who hold any StackerDB slot suppress delivery of a specific StackerDB chunk to a specific victim peer, without the victim ever seeing the message via this path.

### Impact Explanation
The attacker does not forge chunk *contents* (chunk signature/slot ownership checks remain intact), but they *do* forge routing metadata that determines who receives a legitimate broadcast. This is a targeted propagation/availability degradation against a specific victim peer — an unauthenticated write to broadcast routing decisions — matching "steering a node off the tip via false inventory"-class High severity (propagation suppression rather than volumetric DoS). It is repeatable per chunk/message and can be applied to selectively starve a targeted node of StackerDB updates (signer messages, config data, etc.) as long as the attacker keeps constructing pushes with forged `relay_hints` naming that victim.

### Likelihood Explanation
Preconditions are modest: the attacker needs to legitimately own any StackerDB slot (a normal, unprivileged capability for participants such as signers) to produce a validly signed `StackerDBPushChunk`. No secret, RPC credential, or other peer's key is required — the attacker only needs to know the victim's public-key hash (routinely observable, e.g., via neighbor/handshake gossip) to place it in `relay_hints`. The P2P port is remotely reachable by design. This can be repeated for every chunk write, making sustained suppression against a chosen victim feasible at low cost.

### Recommendation
Do not use unauthenticated `relay_hints` as authoritative for broadcast suppression. Either (a) only exclude peers from `outbound_dist`/`inbound_dist` if the local node's own `RelayerStats`/`relay_pubkhs` tracking independently recorded receiving this exact payload's ID from that peer (compare against a locally-maintained "who actually sent me this" map keyed by message hash/id, not attacker-supplied hints), or (b) treat `relay_hints` purely as a hint for logging/telemetry and never let it alone drive exclusion from the broadcast peer sample.

### Proof of Concept
Add a unit test in `stackslib/src/net/p2p.rs`'s test module (alongside existing `sample_broadcast_peers` tests referenced in `stackslib/src/net/tests/relay/epoch2x.rs`):
1. Construct a `PeerNetwork` test harness with at least two authenticated connected peer convos: attacker peer A and victim peer V, neither of which has actually sent the target chunk to the local node.
2. Build a `StackerDBPushChunkData` (or any `RelayPayload`) as the broadcast payload.
3. Construct `relay_hints: Vec<RelayData>` containing a single `RelayData` whose `peer.public_key_hash` equals `Hash160::from_node_public_key(V's real pubkey)`, while V's convo was never the actual sender.
4. Call `network.sample_broadcast_peers(&relay_hints, &payload)`.
5. Assert that V's `NeighborKey` is absent from the returned `Vec<NeighborKey>` (proving wrongful exclusion), while V never relayed anything — demonstrating the forged-hint suppression at `stackslib/src/net/p2p.rs:1534` (`relay_pubkhs.contains(&pubkey_hash)`). [3](#0-2)
