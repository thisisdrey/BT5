### Title
Unbounded array allocation from attacker-controlled length in `BatchValidateSign` precompile leads to memory exhaustion - (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` precompiled contract (and its helper functions `extractBytesArray`/`extractBytes32Array`) allocate Java arrays sized directly from an attacker-controlled 32-byte word taken from the transaction's call data, with no upper bound enforced unless a specific hard-fork feature flag is active. This mirrors the reported bug class: allocating a buffer using an untrusted "size hint" without capping it, which can force the JVM to attempt a multi-gigabyte allocation and trigger memory exhaustion.

### Finding Description
`BatchValidateSign.doExecute` parses the call data into `DataWord[] words` and only bounds the signature/address array sizes (`MAX_SIZE = 16`) when `VMConfig.allowTvmSelfdestructRestriction()` is enabled: [1](#0-0) 

When that flag is not active (its default/pre-activation state, controlled by a committee proposal, i.e. any chain that has not yet passed this specific hard fork), `signatures` is built via `extractBytesArray` and `addresses` via `extractBytes32Array` with **no size check at all**: [2](#0-1) 

Both helpers compute `len` straight from an attacker-supplied `DataWord` via `intValueSafe()` (which returns up to `Integer.MAX_VALUE`) and immediately allocate an array of that size:
```java
int len = words[offset].intValueSafe();
byte[][] bytes32Array = new byte[len][];
```
There is no `serde`-style cap (e.g. 4096) analogous to the report's recommendation — the array is sized directly by untrusted input before any validation of the actual data length or of `cnt` against `MAX_SIZE`, which only happens afterwards at line 1179.

### Impact Explanation
An attacker can craft calldata for a `TriggerSmartContract` transaction that calls address `0x66` (BatchValidateSign) with a length word set to a huge value (up to `Integer.MAX_VALUE`). This causes an attempt to allocate an array of object references sized proportionally to that value (e.g. `new byte[Integer.MAX_VALUE][]` requests on the order of 16+ GB of reference-array memory), which will throw `OutOfMemoryError`. While `execute()` catches `Throwable`, the allocation attempt itself stresses the JVM heap and can trigger full GC pauses or cascading `OutOfMemoryError`s in unrelated threads, degrading or crashing the node processing blocks/transactions — a memory-exhaustion denial-of-service reachable from a single unauthenticated/unprivileged transaction.

### Likelihood Explanation
Reachable via any node that has not yet activated `allowTvmSelfdestructRestriction` (a committee-gated feature, off by default until enabled) — any transaction broadcaster can call the precompile at address `0x66` with a `TriggerSmartContract`, without needing any privilege, asset, or special account state. The energy cost model (`getEnergyForData`) is based on `data.length`, not on the value encoded inside the data, so a small, cheap calldata payload can encode an arbitrarily large `len` value.

### Recommendation
Apply the same `MAX_SIZE` bound check (or an equivalent low ceiling) to `sigArraySize`/`addrArraySize` unconditionally, before calling `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, regardless of the `allowTvmSelfdestructRestriction` flag. More generally, `extractBytesArray` and `extractBytes32Array` should validate `len` against a sane upper bound (and against the actual remaining `data`/`words` length) before allocating, mirroring `serde`'s `cautious()` pattern of capping size hints rather than trusting them directly.

### Proof of Concept
1. Craft a `TriggerSmartContract` transaction whose call data targets precompile address `0x66` (`BatchValidateSign`).
2. Encode the ABI header so `words[1]` (signature array offset) or `words[2]` (address array offset) point to a word position where the length is set to a very large value, e.g. `0x7FFFFFFF`.
3. Submit the transaction on a network/chain where `allowTvmSelfdestructRestriction` has not been activated by proposal.
4. On execution, `extractBytesArray`/`extractBytes32Array` compute `len = words[offset].intValueSafe()` and execute `new byte[len][]`, forcing the JVM to attempt a huge allocation, causing `OutOfMemoryError` / severe GC pressure on the node processing the transaction.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();

      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }

          bytesLen);
    }
    return bytesArray;
  }
