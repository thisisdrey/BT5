### Title
Stale slippage check in `ExchangeTransactionActuator` allows trade to settle below user's `expected` minimum - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
`ExchangeTransactionActuator` (java-tron's bancor-style AMM trade contract) enforces the caller's minimum-received guarantee (`tokenExpected`) only inside `validate()`, using a value computed from a snapshot of the exchange pool. The value that actually gets credited to the user's account is computed independently inside `execute()`, from a freshly re-read `ExchangeCapsule`, and is never re-checked against `tokenExpected` before crediting the account. This is the same "check the amount now, transfer a possibly different amount later" pattern as the Slingshot finding.

### Finding Description
In `validate()` the actuator loads the exchange, computes the anticipated output, and rejects the transaction if it is below the user-specified `tokenExpected`: [1](#0-0) 

In `execute()`, the actuator re-fetches the `ExchangeCapsule` from the store and calls `exchangeCapsule.transaction(...)` a second, independent time to determine `anotherTokenQuant`, which is what is actually credited to the account — with no comparison to `tokenExpected` at this point: [2](#0-1) 

`ExchangeCapsule.transaction()` derives its output purely from the pool's *current* `firstTokenBalance`/`secondTokenBalance` at the moment it is invoked, and also mutates those balances as a side effect of the call: [3](#0-2) 

Because the guarantee (`tokenExpected`) is validated against one evaluation of the AMM curve but the funds actually transferred are computed from a second, later evaluation of the same curve, any change to the pool's balances between the `validate()` pass and the `execute()` pass for this transaction (or the fact that the check is not re-asserted at the only place where funds are actually moved) reproduces exactly the Slingshot root cause: "premature" checking of the minimum-output condition, structurally separated from the point where the asset is actually delivered to the user, instead of `finalOutputAmount ≥ finalAmountMin` being validated as the very last step before crediting the account.

### Impact Explanation
If the value the actuator credits in `execute()` is lower than the `tokenExpected` the user validated against, the user's trade settles for less than the pool price they explicitly protected against — the exact "receives less than the guaranteed minimum" outcome flagged as Medium severity in the original Slingshot report. In an AMM, any output-guarantee check that is not re-verified atomically with the balance mutation defeats the entire purpose of a slippage-protection parameter and can result in users losing funds relative to their accepted minimum.

### Likelihood Explanation
The actuator is reachable by any account via a signed `ExchangeTransactionContract` broadcast to `ExchangeTransactionActuator`; no special privilege is required. The likelihood of the two evaluations actually diverging in production depends on java-tron's actuator invocation model (whether `validate()` and `execute()` for a single transaction are guaranteed to run back-to-back on the exact same `ExchangeCapsule` instance with no intervening state mutation) — I was not able to fully confirm this sequencing within the tool budget available, so this should be treated as requiring further verification of the transaction-processing pipeline (`ActuatorFactory`/`Manager` invocation order) before being treated as fully proven.

### Recommendation
Re-derive and re-assert `anotherTokenQuant >= tokenExpected` inside `execute()`, immediately before/at the point the balances are mutated and persisted, rather than relying solely on the separate check performed in `validate()`. This mirrors the Slingshot fix of comparing actual balance deltas against the minimum at the moment of transfer rather than pre-transfer.

### Proof of Concept
1. User submits `ExchangeTransactionContract` with `tokenId`, `quant`, and `expected` (minimum acceptable `anotherTokenQuant`).
2. `validate()` computes `anotherTokenQuant` from the exchange pool state at validation time and confirms it is `>= expected`.
3. `execute()` independently re-reads the `ExchangeCapsule` and re-invokes `exchangeCapsule.transaction(...)`, producing a new `anotherTokenQuant` used to actually credit the account, without re-checking it against `expected`.
4. If pool state differs between these two evaluations, the amount credited to the user can be lower than the `expected` value they approved, matching the Slingshot "checked-then-transferred-less" bug class.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
