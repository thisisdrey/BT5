### Title
Unauthenticated `recv_error` teardown lets an off-path attacker repeatedly abort tunnels and extend reconnection downtime - (File: `outside.go`)

### Summary
`handleRecvError` in `outside.go` tears down an active or pending tunnel based solely on a plaintext, unencrypted `RecvError` packet whose only "authentication" is a comparison against the locally learned remote `UdpAddr` — and that check is skipped entirely whenever the hostinfo hasn't yet learned a remote address. Combined with `sendRecvErrorConfig`/`acceptRecvErrorConfig` defaulting to `always`, an attacker who can guess/observe a peer's session index (carried unencrypted as `h.RemoteIndex` in every packet header) and spoof a UDP source can force repeated tunnel teardowns, extending the amount of time a victim spends re-handshaking instead of exchanging traffic — analogous to the reported griefer resetting a trust/cooldown timer with a cheap, low-cost message to keep a victim stuck in a degraded state.

### Finding Description
`RecvError` is handled entirely outside the encrypted/authenticated packet path in `readOutsidePackets`: [1](#0-0) 

`handleRecvError` looks the hostinfo up purely by the (plaintext, guessable/observable) `RemoteIndex`, and only rejects the packet if the hostinfo already has a **learned, valid** remote address that doesn't match the packet's source: [2](#0-1) 

Key points:
- `hr.IsValid()` is false for any hostinfo that hasn't yet had a remote learned (e.g. a pending/just-created responder hostinfo, or one where `SetRemote` hasn't fired yet, or after certain roams/relay-only paths) — in that state, an attacker's spoofed `RecvError` from *any* source address is accepted unconditionally.
- Even when `hr.IsValid()` is true, the check is a bare address comparison with no cryptographic binding (no nonce, no MAC, no proof of session possession) — an attacker able to spoof UDP source `addr` to match the victim's already-known remote simply passes the check.
- On acceptance, `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` unconditionally destroy the tunnel state, exactly analogous to how the reported bug's `_updateUserFeesOnDeposit()` unconditionally resets `lastActionTimestamp` on any inbound transfer regardless of how trivial/illegitimate the contribution is.
- The `RemoteIndex` needed to target a specific tunnel is not secret: it is echoed in cleartext in every packet's header (`header.H.RemoteIndex`), so any passive observer on the path (or anyone who receives punch/lighthouse traffic) can harvest it.
- By default `listen.send_recv_error`/`listen.accept_recv_error` are `always` (per `CHANGELOG.md` #670 and current defaults), so this path is live out of the box.

This mirrors the reported bug class: a cheap, unauthenticated action (sending a 1-message, header-only `RecvError` packet — no CA-signed certificate required, no handshake completed) causes a disproportionate, repeatable reset of connection state (tunnel teardown + forced re-handshake), which a griefer can keep re-triggering to indefinitely prolong the victim's "not yet reconnected" window, just as the original bug let a griefer indefinitely prolong the "high withdrawal fee" window by repeatedly resetting `lastActionTimestamp` with negligible-value transfers.

### Impact Explanation
An attacker with no valid Nebula certificate and no completed handshake can force victims into a persistent disconnect/reconnect loop:
- Each spoofed `RecvError` destroys the main hostinfo (`closeTunnel`) and any pending handshake state (`handshakeManager.DeleteHostInfo`), forcing a full re-handshake.
- Repeating this before the new handshake completes (or immediately after) keeps the victim tunnel perpetually torn down, denying overlay connectivity — a remote, unauthenticated availability/state-poisoning impact against the mesh, without ever needing a signed certificate.

### Likelihood Explanation
- Requires only: (1) the ability to send spoofed UDP packets toward the victim's listen port (common on the open internet/most NAT setups since Nebula runs over UDP), and (2) knowledge of the victim's session `RemoteIndex`, which travels unencrypted in every packet the attacker can passively observe (e.g., by being on path, or by capturing lighthouse/punch traffic).
- No cryptographic material, cert, or CA trust of any kind is needed — this is explicitly allowed by design (`recv_error` predates and bypasses the AEAD/cert path), and defaults (`always`) make it broadly reachable.

### Recommendation
Do not let an unauthenticated, unencrypted control packet unilaterally destroy tunnel/handshake state:
- Require the `RecvError` path to only act when the hostinfo already has a learned, valid remote (never treat "no remote learned yet" as an implicit trust bypass), and prefer failing closed (ignore) rather than open in that case.
- Bind acceptance to something the sender must have proven possession of (e.g., only accept `recv_error` correlated with a currently in-flight message the local side actually sent, or require it be authenticated/MAC'd like other post-handshake messages) rather than a bare index + address compare.
- Consider rate-limiting/backoff on `recv_error`-triggered teardowns per remote index/address to blunt repeated griefing even if the trust model is left as-is.

### Proof of Concept
1. Establish (or begin establishing) a tunnel between `victim` and `peer`; observe `peer`'s traffic (or lighthouse punch notifications) to learn `peer`'s `localIndexId` (sent in cleartext as `RemoteIndex` in every header the peer emits).
2. Craft a `header.RecvError` packet with that `RemoteIndex` (see `sendRecvError` for wire format: `header.Encode(..., header.RecvError, 0, index, 0)`), and send it from a spoofed UDP source matching `victim`'s currently-known/learned remote address for that hostinfo (or send it before `victim` has learned a remote address at all, in which case any source works).
3. On `victim`, `handleRecvError` (`outside.go:541`) accepts the packet, calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, destroying the tunnel/handshake state.
4. Repeat step 2–3 whenever `victim` attempts to re-handshake with `peer`, keeping the pair permanently disconnected without ever presenting a certificate or completing a handshake. [2](#0-1) [3](#0-2)

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
