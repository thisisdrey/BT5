### Title
Remote-triggerable deletion of the only viable relay path while it is merely transiently unusable (not permanently dead), permanently freezing the data-plane tunnel — ([File: inside.go])

### Summary
`sendNoMetrics` in `inside.go` unconditionally deletes a hostinfo's relay-candidate entry the moment `QueryVpnAddrsRelayFor` returns *any* error, even though that error is also returned for relays that are only *temporarily* unusable (e.g. `Requested` or `Disestablished`, not yet `Established`). This mirrors the Ajna `moveLiquidity` bug class: a state entry is unconditionally removed based on a check that does not actually confirm the underlying resource is permanently gone/exhausted, causing a currently-recoverable, partial condition to become a permanent freeze of the resource (here: the ability to transmit at all).

### Finding Description
`f.hostMap.QueryVpnAddrsRelayFor` only returns success when a relay entry exists **and is in the `Established` state**: [1](#0-0) 

Any other condition — the relay host not found, no relay-for-IP entry, or the relay-for-IP entry existing but sitting in `Requested`, `PeerRequested`, or `Disestablished` state — causes `QueryVpnAddrsRelayFor` to return the generic `"unable to find host with relay"` error. That error is indistinguishable, at the call site, from "this relay is genuinely gone."

In `sendNoMetrics`, when attempting to relay an outbound packet because no direct remote path is known, the code loops over the hostinfo's list of candidate relay IPs and, on the *first* error from `QueryVpnAddrsRelayFor`, unconditionally deletes that relay from the hostinfo's relay list: [2](#0-1) 

This is functionally identical to the Ajna finding: a partial/transient condition (relay temporarily `Disestablished` while it re-establishes, or `Requested` while a `CreateRelayRequest` is in flight) is treated the same as a terminal failure, and the tracking entry is unconditionally removed via `hostinfo.relayState.DeleteRelay(relayIP)`: [3](#0-2) 

If this was the only relay candidate for the hostinfo (a very common single-relay topology), the hostinfo's relay list becomes empty. Unlike the hostinfo-level state machine (`relayForByIp`), the `relays []netip.Addr` ordered list consumed here has no automatic re-population path outside a fresh handshake/lighthouse relay list injection — the deletion happens on the **live data-plane send path**, not during handshake setup, so there is no natural retry that re-adds the relay. The e2e regression test `TestRelayHandshakeOverDisestablishedEntry` explicitly documents this exact failure mode ("its first transmit deletes its only relay and the tunnel is born transmit-dead: them can receive but every send is silently dropped") for a related code path in the responder's relay-request handling, confirming the fragility of the "delete-on-not-Established" pattern is a known-risky area of this codebase: [4](#0-3) 

However, that guarded test only covers the `handleCreateRelayRequest`/`handleCreateRelayResponse` control-message path (which correctly transitions `Disestablished → Established` rather than deleting). The `sendNoMetrics` data-plane path in `inside.go:414-429` has no equivalent safeguard: it deletes on *any* non-`Established` state, including `Requested`/`Disestablished`, not just on a genuine "host missing" condition.

### Impact Explanation
A remote peer (or even natural network conditions with no attacker required) can cause the relay's state to sit briefly in `Requested` or `Disestablished` (e.g., right after `CloseTunnel`+re-handshake, or while a `CreateRelayRequest`/`CreateRelayResponse` round-trip is outstanding). Any locally queued outbound packet during that window causes `DeleteRelay` to permanently discard the node's only relay path, silently dropping all subsequent outbound traffic to that peer with no user-visible error and no automatic recovery — effectively a permanent (until manual reconfiguration/restart) denial of communication for the affected tunnel, analogous to "frozen funds" in the original finding: a resource is left permanently stranded because the removal was gated on the wrong condition (any query failure) rather than confirming the relay path is truly and permanently unusable.

### Likelihood Explanation
No attacker-controlled certificate or privileged access is required. The state window (`Requested`/`Disestablished`) is reached during ordinary relay establishment/re-establishment races that already occur in normal single-relay deployments (as demonstrated by the very similar `TestRelayHandshakeOverDisestablishedEntry` scenario), and any queued packet arriving during that window triggers the deletion. Given `sendNoMetrics` is on the hot outbound path, the race window is regularly hit whenever a relay bounces or is renegotiating, making this readily reachable rather than a rare edge case.

### Recommendation
Do not delete the relay candidate on a generic "not found" error from `QueryVpnAddrsRelayFor`. Distinguish between:
- the relay host truly being absent from the hostmap (safe to prune), and
- the relay-for-IP entry existing but being in `Requested`/`PeerRequested`/`Disestablished` (transient — must be retried/re-requested, not deleted).

`QueryVpnAddrsRelayFor` should return enough information (or a distinct error) to let `sendNoMetrics` only call `DeleteRelay` when the relay truly no longer exists, and otherwise leave the relay entry intact (optionally triggering a `CreateRelayRequest` retry, as `StartRelays` already does for the `Disestablished`/`Requested` cases) so a transient state does not permanently strand the tunnel.

### Proof of Concept
1. Set up `me` (uses relay), `relay`, and `them` (uses relay), matching the topology in `TestRelayHandshakeOverDisestablishedEntry` / `TestReestablishRelays`.
2. Establish a working relayed tunnel `me <-> relay <-> them`.
3. Force `them`'s relay-for-IP entry for `me` into `Disestablished` or `Requested` (e.g. close and quickly re-handshake the tunnel through the relay, as in the existing e2e test, or simply race a `CreateRelayRequest` retransmit window).
4. While the relay is in that transient state, have `them` (or `me`) enqueue an outbound tun packet destined through the relay — this hits `sendNoMetrics`'s relay fallback branch.
5. Observe `QueryVpnAddrsRelayFor` returning an error (state != `Established`) and `hostinfo.relayState.DeleteRelay(relayIP)` being called, removing the only relay candidate.
6. Confirm that subsequent outbound packets to that peer are now silently dropped indefinitely (no relay candidates remain, and no automatic mechanism re-adds one), reproducing the "transmit-dead" condition the codebase's own test comment describes for the sibling code path.

func (hm *HostMap) QueryVpnAddrsRelayFor(targetIps []netip.Addr, relayHostIp netip.Addr) (*HostInfo, *Relay, error) {
	hm.RLock()
	defer hm.RUnlock()

	// This runs per relayed packet, so check the primary with a single map probe and only consult
	// moreHosts when the primary can't relay for us.
	h, ok := hm.Hosts[relayHostIp]
	if !ok {
		return nil, nil, errors.New("unable to find host")
	}

	for _, targetIp := range targetIps {
		r, ok := h.relayState.QueryRelayForByIp(targetIp)
		if ok && r.State == Established {
			return h, r, nil
		}
	}

	if list, ok := hm.moreHosts[relayHostIp]; ok {
		// list[0] is the primary we already checked
		for _, h := range list[1:] {
			for _, targetIp := range targetIps {
				r, ok := h.relayState.QueryRelayForByIp(targetIp)
				if ok && r.State == Established {
					return h, r, nil
				}
			}
		}
	}

	return nil, nil, errors.New("unable to find host with relay")
