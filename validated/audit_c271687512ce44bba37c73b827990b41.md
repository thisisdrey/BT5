## Title
Snowbridge `PayAccountOnLocation::pay_reward` marks relayer rewards as claimed based on local XCM delivery success, not remote settlement, causing permanent loss of reward funds - ([File: bridges/snowbridge/primitives/core/src/reward.rs])

### Summary
The GroupBuy bug pattern is: a low-level `call` is treated as "successful" and downstream state (balances, allowances) is permanently updated, without verifying that the recipient actually received/processed the funds. The local analog is `PayAccountOnLocation::pay_reward` in `bridges/snowbridge/primitives/core/src/reward.rs`, used by `pallet_bridge_relayers::do_claim_rewards` on BridgeHub Westend. This procedure returns `Ok(())` as soon as the XCM message describing the reward mint/deposit is handed off to the local `XcmSender` (`XcmSender::deliver`) — it does not, and cannot, know whether the remote chain (AssetHub) actually executes `DepositAsset` successfully for the beneficiary. Yet the caller (`do_claim_rewards`) irrevocably deletes the relayer's pending reward record and emits `RewardPaid` the moment `pay_reward` returns `Ok`.

### Finding Description
`pay_reward` builds an `UnpaidExecution` XCM containing `DescendOrigin`, `UniversalOrigin`, `ReserveAssetDeposited`, and `DepositAsset`, then does: [1](#0-0) 

```rust
let (ticket, fee) =
    validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

Ok(())
```

`deliver` only confirms that the message was accepted by the local transport (HRMP channel) for the destination — it is not a receipt that the message was executed, nor that `DepositAsset` succeeded on AssetHub. It is fire-and-forget: since the XCM uses `UnpaidExecution`, there is no fee-based execution guarantee on the remote side, and any remote execution failure (e.g. beneficiary account doesn't exist/is filtered, asset trust/registration issue, insufficient weight) produces no failure signal back to BridgeHub.

The caller, `Pallet::do_claim_rewards`, treats the `Ok(())` return from `pay_reward` as final settlement: [2](#0-1) 

```rust
fn do_claim_rewards(...) -> DispatchResult {
    RelayerRewards::<T, I>::try_mutate_exists(
        &relayer,
        reward_kind,
        |maybe_reward| -> DispatchResult {
            let reward_balance =
                maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
            T::PaymentProcedure::pay_reward(...)
                .map_err(|e| { ...; Error::<T, I>::FailedToPayReward })?;

            Self::deposit_event(Event::<T, I>::RewardPaid { ... });
            Ok(())
        },
    )
}
```

Because `maybe_reward.take()` already removed the storage entry, and the closure returns `Ok(())` whenever `pay_reward` returns `Ok`, the `try_mutate_exists` commits the removal permanently. There is no callback, receipt-tracking, or retry path if the remote `DepositAsset` instruction actually fails after being delivered — this exactly mirrors GroupBuy's flaw of asserting success from a call whose actual effect on the recipient was never verified.

### Impact Explanation
If the remote XCM execution on AssetHub fails after delivery (e.g. beneficiary location is malformed/unsupported, `ReserveAssetDeposited`/`DepositAsset` errors, or weight/barrier rejects the message on the remote side), the relayer's reward is permanently and unrecoverably lost: the `RelayerRewards` entry has already been deleted on BridgeHub and `RewardPaid` was emitted, so `claim_rewards_to` will subsequently fail with `NoRewardForRelayer` for any retry. This is a direct "loss of funds" scenario for the relayer, consistent with the High-severity classification of the original GroupBuy finding, and falls within the "permanent user-fund lock" / "duplicate settlement" impact category described for this scan (funds effectively burned/unbacked because BridgeHub's local ledger already discharged its obligation while AssetHub never delivered the corresponding value).

### Likelihood Explanation
This does not require a malicious actor — it can be triggered by an ordinary relayer calling the public, unprivileged `claim_rewards_to` extrinsic with a syntactically valid but remote-execution-incompatible `AssetHubLocation` beneficiary, or simply by transient/legitimate remote-side conditions (e.g. AssetHub temporarily rejecting the `DepositAsset` due to congestion, filters, or an unregistered/untrusted reserve asset configuration). The existing tests already demonstrate paths where `claim_rewards_to` fails at the local send step (`FailedToPayReward`), but do not cover — and the code path does not defend against — the remote-side silent failure after successful local delivery.

### Recommendation
Do not treat local `XcmSender::deliver` success as final settlement. Options:
- Use a paid/query-based XCM execution with `ReportError`/`QueryResponse` (similar to `PayOverXcm`'s query-id + `check_payment` pattern) so settlement is confirmed asynchronously before the reward record is purged, or
- Keep the reward record in a "pending" state after successful delivery and only fully clear it upon a confirmed remote success signal, with a re-claimable/retry path if no confirmation arrives within a timeout.

### Proof of Concept
1. A relayer accrues a `BridgeReward::Snowbridge` reward via `register_reward`.
2. Relayer calls `claim_rewards_to(BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(some_location))`.
3. `BridgeRewardPayer::pay_reward` invokes `PayAccountOnLocation::pay_reward`, which succeeds at `validate_send`, `charge_fees`, and `deliver` (all local operations) and returns `Ok(())`.
4. `do_claim_rewards` deletes the `RelayerRewards` entry and emits `RewardPaid`.
5. On AssetHub, the `DepositAsset { assets: AllCounted(1).into(), beneficiary }` instruction fails to execute (e.g., due to an unregistered reserve asset trust relationship for the given `EthereumNetwork`/location, or a filtered beneficiary) — no value is ever credited to the relayer.
6. Relayer calls `claim_rewards_to` again for the same reward and receives `Error::<T, I>::NoRewardForRelayer` (`bridges/modules/relayers/src/lib.rs`), confirming the reward is permanently lost with no recourse, matching the analogous unchecked-call assumption in the GroupBuy report. 	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
