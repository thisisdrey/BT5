## Title
`pallet_dap::mint_and_distribute` can silently discard non-zero issuance and panic via `debug_assert!` when all per-recipient shares round to zero - (File: `substrate/frame/dap/src/lib.rs`)

## Summary
`Pallet::mint_and_distribute` [1](#0-0)  computes a non-zero `issuance` value from `T::IssuanceCurve::issue`, then splits it per-recipient with `Perbill::mul_floor`, which always rounds down [2](#0-1) . When `issuance` is small relative to the number/granularity of configured shares, every recipient's floor-rounded cut can independently be zero even though the aggregate `issuance` is non-zero, causing `total_minted` to remain zero while the event still fires and a `debug_assert!` asserts the opposite is impossible [3](#0-2) .

## Finding Description
`drip_issuance`, invoked every block via `on_initialize`, calls `mint_and_distribute(elapsed)` unconditionally once cadence/ceiling checks pass [4](#0-3) . Inside, `issuance = T::IssuanceCurve::issue(total_issuance, elapsed)` is computed and checked only for exact zero [5](#0-4) . The subsequent per-recipient loop computes `perbill.mul_floor(issuance)` for each of `T::BudgetRecipients::recipients()` and only mints amounts that are non-zero, with an explicit comment acknowledging "Rounding dust from `Perbill::mul_floor` is not minted" [6](#0-5) . There is no code path that aggregates rounding dust, routes it to a fallback recipient, or defers it to the next drip. The function nonetheless asserts `!total_minted.is_zero()` whenever `issuance` was non-zero [7](#0-6) , an invariant the arithmetic in the loop does not actually guarantee — with several small `Perbill` shares and a sufficiently small `issuance`, every individual `mul_floor` result can floor to zero simultaneously while their sum (as fractions) is exactly `Perbill::one()`.

## Impact Explanation
Two consequences follow directly, both matching allowed impact categories: (1) In release builds, minted issuance silently diverges from the value reported in `Event::IssuanceMinted`/actually intended by the issuance curve — the aggregate issuance for that drip is permanently lost rather than distributed, a runtime accounting bug that compromises intended economic behavior. (2) In debug-assertion-enabled builds (common for testnets/dev chains/CI), the `debug_assert!` panics inside `on_initialize`, aborting block production deterministically until the underlying state (e.g., total issuance, elapsed time) changes — an implementation bug that can bring down a Substrate-based chain without requiring machine access.

## Likelihood Explanation
No attacker action or privileged operation is required beyond the pallet's own intended one-time operational configuration (`set_budget_allocation` with more than one recipient carrying modest percentage shares, which is the pallet's documented use case). From that point, whether the bug triggers depends purely on ordinary, non-adversarial runtime state: `total_issuance`, elapsed time since last drip, and the configured `IssuanceCurve` output — all of which are smallest early in a chain's life or with short drip cadences, making the degenerate all-zero-shares condition reachable during normal, unprivileged block production.

## Recommendation
Replace the `debug_assert!` with explicit handled logic: when `total_minted` is zero but `issuance` is non-zero, either mint the leftover `issuance` (or its rounding remainder) to a designated fallback recipient (e.g., the DAP buffer account), or accumulate the undistributed remainder into state so it is included in the next drip's issuance computation, ensuring eventual minting rather than silent loss or a panic.

## Proof of Concept
Using the existing test harness in `substrate/frame/dap/src/tests/drip.rs` [8](#0-7) : configure `BudgetAllocation` with several small-percentage recipients (e.g., 5 recipients at 20% each, summing exactly to `Perbill::one()`), then drip with an `elapsed` value tuned so `TestIssuanceCurve` returns a small `issuance` (e.g., 4) such that `Perbill::from_percent(20).mul_floor(4) == 0` for every recipient. The resulting `IssuanceMinted { total_minted: 0, .. }` event fires despite `issuance = 4`, and the `debug_assert!` at `substrate/frame/dap/src/lib.rs:457-460` panics in debug-assertions builds, aborting the `on_initialize` hook.
