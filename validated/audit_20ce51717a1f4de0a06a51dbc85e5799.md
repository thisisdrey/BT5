### Title
Unbounded per-filter result queue growth in JSON-RPC log filters enables broadcaster/attacker-triggered memory exhaustion - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java`)

### Summary
The external report describes a memory-leak-class bug in Privoxy where a client-supplied filtering feature ("client tags") is processed without adequate bounds and causes unbounded memory growth leading to a crash. The analogous reachable feature in java-tron is the JSON-RPC event/log filter subsystem (`eth_newFilter`-style filters) exposed by `TronJsonRpcImpl`, where an anonymous JSON-RPC client can register filters whose match results are appended to a per-filter, uncapped `LinkedBlockingQueue` for the lifetime of the filter.

### Finding Description
`TronJsonRpcImpl` maintains filter maps (`eventFilter2ResultFull`, `eventFilter2ResultSolidity`) keyed by filter id, each entry being a `LogFilterAndResult` [1](#0-0) . Each `LogFilterAndResult` stores matched results in an unbounded `LinkedBlockingQueue` (`result = new LinkedBlockingQueue<>();`), with no size cap on `add()` [2](#0-1) .

For every new block, `handleLogsFilter` iterates all active filters and, for each one whose block range/bloom matches, computes `LogMatch.matchBlock(...)` and appends every matched `LogFilterElement` to that filter's result queue via `processLogFilterEntry`, with no bound on how many elements accumulate before the client calls `eth_getFilterChanges`/`eth_uninstallFilter` [3](#0-2) . The only cap present, `maxLogFilterNum`, limits how many distinct filters can exist, not how much data a single long-lived, broadly-scoped filter (e.g., matching all contracts/topics across its full block range) can accumulate in its result queue before it expires [4](#0-3) . The shared `logElementCache` used for deduplication is itself capped at 300,000 entries with a 5-minute TTL, but that cache only avoids duplicate `LogFilterElement` object allocation — it does not limit how many elements a given filter's own queue can retain, and each queue element is still referenced from the filter's `result` list for the full life of the filter [5](#0-4) .

An unprivileged, unauthenticated JSON-RPC caller can therefore open filters and simply never poll them, causing the queues to accumulate log data for every subsequent matching block until the filter's `EXPIRE_SECONDS` (5 minutes) elapses, and can repeat this by re-issuing `eth_newFilter` calls before expiry, up to `maxLogFilterNum` concurrent filters, each with an unbounded per-block growth rate driven purely by chain activity, not by any client-imposed cap.

### Impact Explanation
Sustained accumulation of unbounded per-filter result queues, driven by repeated public JSON-RPC calls, can exhaust heap memory on a full node/solidity node/PBFT node exposing the JSON-RPC service, leading to garbage-collection pressure, OutOfMemoryError, and ultimately node crash or the node becoming unable to serve any further API requests — this matches the "node crash or halt" / "API the node can no longer serve" impact criteria for this class of finding.

### Likelihood Explanation
The JSON-RPC log-filter endpoints are part of the standard public API surface (`TronJsonRpcImpl`/`TronJsonRpc`) reachable by any anonymous API client without requiring a signed transaction, a witness role, or special privileges. The only friction is the `maxLogFilterNum` cap on the number of concurrently open filters and the 5-minute filter TTL, both of which an attacker can work around by opening filters near-continuously and by choosing broad, high-match-rate filter criteria to maximize per-filter queue growth.

### Recommendation
Cap the size of each filter's result queue (e.g., reject/drop new `add()` calls or evict oldest results once a configurable per-filter maximum is reached, mirroring `maxLogFilterNum`), and/or bound total aggregate memory used by all pending filter results. Consider also shortening default `EXPIRE_SECONDS` for filters with no recent `eth_getFilterChanges` poll, and emitting metrics/alerts when a filter's queue depth crosses a threshold.

### Proof of Concept
1. As an anonymous JSON-RPC client, repeatedly call `eth_newFilter` with a broad filter (wide `fromBlock`/`toBlock`, no address/topic restriction) up to `maxLogFilterNum` times, without ever calling `eth_getFilterChanges` or `eth_uninstallFilter`.
2. As the chain continues producing blocks with events, `handleLogsFilter` → `processLogFilterEntry` appends every matching `LogFilterElement` into each filter's `LinkedBlockingQueue` result [5](#0-4) .
3. Repeat step 1 just before each filter's 5-minute expiry to keep the maximum number of filters alive indefinitely.
4. Over time, heap usage grows unbounded with chain throughput and filter count, exhausting node memory and crashing or hanging the JSON-RPC-serving node.

Note: I was unable to fully verify (due to tool-call limits) whether an additional enforcement check on `maxLogFilterNum` or a hard cap on filter-queue size exists inside the `eth_newFilter`-equivalent method body of `TronJsonRpcImpl`, since I could not view that specific method's full source before the session ended. This should be confirmed against the live source before treating this as fully validated.

  private void processLogFilterEntry(
      Map.Entry<String, LogFilterAndResult> entry,
      Map<String, LogFilterAndResult> eventFilterMap,
      LogsFilterCapsule logsFilterCapsule) {
    LogFilterAndResult logFilterAndResult = entry.getValue();
    if (logFilterAndResult.isExpire()) {
      eventFilterMap.remove(entry.getKey());
      return;
    }

    long blockNumber = logsFilterCapsule.getBlockNumber();
    long fromBlock = logFilterAndResult.getLogFilterWrapper().getFromBlock();
    long toBlock = logFilterAndResult.getLogFilterWrapper().getToBlock();
    if (!(fromBlock <= blockNumber && blockNumber <= toBlock)) {
      return;
    }

    if (logsFilterCapsule.getBloom() != null && !logFilterAndResult.getLogFilterWrapper()
        .getLogFilter().matchBloom(logsFilterCapsule.getBloom())) {
      return;
    }

    LogFilter logFilter = logFilterAndResult.getLogFilterWrapper().getLogFilter();
    List<LogFilterElement> elements =
        LogMatch.matchBlock(logFilter, blockNumber, logsFilterCapsule.getBlockHash(),
            logsFilterCapsule.getTxInfoList(), logsFilterCapsule.isRemoved());

    List<LogFilterElement> localResults = new ArrayList<>(elements.size());
    for (LogFilterElement element : elements) {
      LogFilterElement cachedElement;
      try {
        // compare with hashcode() first, then with equals(). If not exist, put it.
        cachedElement = logElementCache.get(element, () -> element);
      } catch (ExecutionException e) {
        logger.error("Getting/loading LogFilterElement from cache fails", e); // never happen
        cachedElement = element;
      }
      localResults.add(cachedElement);
    }
    logFilterAndResult.getResult().addAll(localResults);
