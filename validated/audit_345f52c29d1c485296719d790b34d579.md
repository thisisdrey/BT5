Based on the evidence, the premise of this question is factually incorrect about how `current_protocol_version` is determined during chunk application.

### Analysis

The `EnforcePerReceiptStorageProofLimit` gate in `apply_action_receipt` checks `apply_state.current_protocol_version`, not a node's local binary version: [1](#0-0) 

This `apply_state.current_protocol_version` is populated from the **epoch's canonical protocol version** — a consensus-agreed value stored in `EpochInfo` and looked up via `epoch_manager.get_epoch_protocol_version(&epoch_id)` — not from the chunk producer's or validator's own binary `PROTOCOL_VERSION`: [2](#0-1) [3](#0-2) 

The epoch's protocol version is computed deterministically by all nodes from the same stake-weighted vote tally, two epochs in advance, and is fixed for the entire epoch: [4](#0-3) 

Every honest node — whether producing or validating a chunk — reads the exact same `epoch_id → protocol_version` mapping for a given chunk, so a chunk producer and a chunk validator can never apply the same receipt under different `current_protocol_version` values within a correctly functioning network. The test `slow_test_epoch_multi_protocol_version_change_epoch_overlap` explicitly asserts this invariant — protocol version never changes mid-epoch and never jumps by more than one version at a time: [5](#0-4) 

If a node's own binary lags behind the network-voted epoch protocol version, `check_protocol_version` deliberately panics rather than let it produce/apply chunks with a stale gate value, which prevents exactly the kind of silent producer/validator mismatch hypothesized: [6](#0-5) 

The referenced test `test_per_receipt_storage_proof_size_limit` demonstrates the feature's behavior at `feature_version - 1` vs `PROTOCOL_VERSION` purely as a **unit-test harness technique** to compare pre/post-fix behavior in isolation — it does not simulate two different nodes disagreeing on which protocol version to use for the same live chunk, since `apply_state.current_protocol_version` in production is always sourced from the single epoch-level value, identical for every node: [7](#0-6) 

There is no attacker-controlled input (receipt contents, timing, or size) that can cause the epoch's protocol version to be computed differently by different honest nodes applying the same chunk. The scenario described — an unprivileged sender causing a producer/validator protocol-version mismatch on this feature gate purely by timing a transaction — has no code path in this codebase; it would require either a bug in epoch-manager's deterministic protocol-version computation (an epoch-manager/consensus-layer issue explicitly out of scope) or a byzantine/misconfigured node running mismatched binaries (also out of scope).
