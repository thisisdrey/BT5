### Title
Stale YieldIdToDataId/DataIdToYieldId and PromiseYieldReceipt/PromiseYieldStatus mappings survive DeleteAccountAction, allowing a recreated account to resume/execute a promise yield receipt from its previous incarnation - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` (called from `action_delete_account`) only removes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie entries for a deleted account, but never removes `TrieKey::YieldIdToDataId`, `TrieKey::DataIdToYieldId`, `TrieKey::PromiseYieldReceipt`, or `TrieKey::PromiseYieldStatus`. Because these keys are namespaced only by `account_id` (not by any account-generation/nonce value), a stale `yield_id -> data_id` mapping and its associated parked yield receipt persist in state across a delete-then-recreate cycle of the same account name, so `submit_promise_resume_data_with_yield_id`/`submit_promise_resume_data` can resolve and resume the pre-deletion receipt against the post-recreation account.

### Finding Description
`promise_yield_create_with_id` writes bidirectional mappings via `set_yield_id_mapping` [1](#0-0)  plus a `PromiseYieldReceipt`/`PromiseYieldStatus` entry [2](#0-1) . When the account is subsequently deleted via `DeleteAccountAction`, `action_delete_account` calls `remove_account` [3](#0-2) , which only clears `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData` [4](#0-3) . It never calls `remove_yield_id_mappings`, `remove_promise_yield_receipt`, or `remove_promise_yield_status`, so those entries remain keyed by the (reusable) `account_id`.

If the account is recreated under the same name and a contract on it later calls `promise_yield_resume_with_yield_id` with the same `yield_id`, `submit_promise_resume_data_with_yield_id` resolves the stale `data_id` via `get_data_id_for_yield_id` [5](#0-4) , and `submit_promise_resume_data` finds the still-present `PromiseYieldReceipt`/`PromiseYieldStatus` for that `data_id` and happily submits a resume [6](#0-5) . When the resulting `PromiseResume` receipt is processed, the runtime looks up `get_promise_yield_receipt` purely by `account_id`/`data_id` and, if found, removes it and executes it via `apply_action_receipt` — the receipt being executed is the one originally created before deletion, with actions/method calls fixed at that earlier time [7](#0-6) . Only if the yield was created via `yield_create_with_id` and the `yield_id -> data_id` mapping is later exercised through the normal completion path is `remove_yield_id_mappings` invoked [8](#0-7)  — there is no equivalent cleanup triggered by account deletion.

No existing check enforces that a `yield_id`/`data_id`/receipt belongs to the "current" incarnation of an account; the trie key design has no notion of account generation, so nothing distinguishes a pre-deletion mapping from a post-recreation one.

### Impact Explanation
This breaks the intended authorization/data-dependency exactness of the yield/resume mechanism: a resumed receipt tied to the account's *previous* incarnation (with actions and arguments fixed by the old contract/owner) can be delivered and executed against the *new* incarnation of the account, whose current owner/contract never created or approved that pending continuation. Depending on what the stale receipt's actions do (e.g., a `FunctionCall` continuation designed to move funds or grant access based on trusted yield data), this can result in unintended execution of unauthorized logic against the recreated account — a scoped authorization-escalation-across-promises issue. It is also a straightforward state-hygiene defect (orphaned trie entries that never get cleaned by `remove_account`), independent of whether a concrete fund-loss scenario is constructed.

### Likelihood Explanation
Requires: (1) `ProtocolFeature::YieldWithId` active, (2) the account owner using `promise_yield_create_with_id`, (3) the account being deleted before the yield's timeout (`yield_timeout_length_in_blocks`) expires — since `PromiseYieldTimeout` will eventually fire and clean up the receipt/status/mappings regardless of account existence — and (4) the account being recreated and a `promise_yield_resume_with_yield_id` call with the same `yield_id` occurring within that window. For the same actor reusing their own account name this is fully attacker-controlled and trivially reproducible; for it to affect a different party's newly (re)created account, it additionally depends on that party's `yield_id` colliding with the stale one (plausible if applications use low-entropy/sequential yield IDs, but not guaranteed). The underlying missing-cleanup bug itself is deterministically reproducible regardless of that collision likelihood.

### Recommendation
In `remove_account` (or in `action_delete_account` before/after calling it), also iterate and remove any `TrieKey::YieldIdToDataId`, `TrieKey::DataIdToYieldId`, `TrieKey::PromiseYieldReceipt`, and `TrieKey::PromiseYieldStatus` entries scoped to the deleted `account_id`, mirroring the cleanup already done for access keys and contract data. Alternatively/additionally, incorporate an account-generation counter into these trie keys (or invalidate them explicitly on `DeleteAccountAction`) so that a resumed yield can never resolve to a receipt created under a different account incarnation.

### Proof of Concept
1. Unit test in `core/store/src/utils/mod.rs` tests: call `set_yield_id_mapping(state_update, &A, Y, D)`, then call `remove_account(state_update, &A)`, then assert `get_data_id_for_yield_id(state_update, &A, Y)` — expected `None` per the invariant, but actual result is `Some(D)`, proving the mapping is not cleared.
2. Extend to a runtime-level integration test (similar to `integration-tests/src/tests/runtime/test_yield_resume.rs`): (a) deploy a contract on account A, call `yield_create_with_id` with a chosen `yield_id` Y and a callback that performs an observable/sensitive action; (b) delete account A within the timeout window; (c) recreate A with a different (or same) contract; (d) from the new contract, call `promise_yield_resume_with_yield_id(Y, payload)` and assert it returns success (`1`) and that the *old* callback executes against the new account, demonstrating cross-incarnation execution of an unauthorized continuation.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

    fn create_promise_yield_receipt_with_id(
        &mut self,
        receiver_id: AccountId,
        user_yield_id: YieldId,
    ) -> Result<Option<(ReceiptIndex, CryptoHash)>, VMLogicError> {
        // Check for duplicate yield_id in trie. TrieUpdate also reflects writes from earlier
        // calls within the same function call, so this also catches in-transaction duplicates.
        if has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)
            .map_err(wrap_storage_error)?
        {
            return Ok(None);
        }

        let input_data_id = self.generate_data_id();

        // Store bidirectional yield_id <-> data_id mappings
        set_yield_id_mapping(&mut self.trie_update, &receiver_id, user_yield_id, input_data_id);

        let receipt_index =
            self.receipt_manager.create_promise_yield_receipt(input_data_id, receiver_id.clone());

        set_promise_yield_status(
            &mut self.trie_update,
            &receiver_id,
            input_data_id,
            PromiseYieldStatus::Yielded,
        );

        Ok(Some((receipt_index, input_data_id)))
    }

    fn submit_promise_resume_data(
        &mut self,
        data_id: CryptoHash,
        data: Vec<u8>,
    ) -> Result<bool, VMLogicError> {
        let has_yield_receipt_in_state =
            has_promise_yield_receipt(self.trie_update, self.account_id.clone(), data_id)
                .map_err(wrap_storage_error)?;
        let has_yield_status_in_state =
            has_promise_yield_status(self.trie_update, &self.account_id, data_id)
                .map_err(wrap_storage_error)?;

        if has_yield_receipt_in_state || has_yield_status_in_state {
            self.receipt_manager.create_promise_resume_receipt(data_id, data);
            set_promise_yield_status(
                &mut self.trie_update,
                &self.account_id,
                data_id,
                PromiseYieldStatus::ResumeInitiated,
            );
            return Ok(true);
        }

        Ok(false)
    }
