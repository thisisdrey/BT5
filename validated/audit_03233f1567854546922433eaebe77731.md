### Title
Unchecked 256-bit wraparound in `DataWord.mul()`/`add()` lets `VOTEWITNESS` bypass memory-limit and energy checks - ([File: actuator/src/main/java/org/tron/core/vm/EnergyCost.java])

### Summary
`EnergyCost.getVoteWitnessCost()` / `getVoteWitnessCost2()` compute the memory needed for the `VOTEWITNESS` TVM opcode by multiplying a caller-controlled 256-bit `DataWord` array length by `wordSize` (32) using `DataWord.mul()`, then adding an offset with `DataWord.add()`. Both operations silently wrap modulo 2^256 instead of detecting overflow. This is a fixed-width-arithmetic “sign/overflow miscalculation” analogous to CVE-2017-16995, where `check_alu_op` mis-tracked value bounds after an arithmetic operation, letting the verifier accept operations whose real runtime value diverged from what was checked. Here, an attacker-chosen stack length causes the *computed* memory-size check to wrap to a small number while the *real* offset/length values used by the rest of the opcode pipeline remain large, defeating the `checkMemorySize`/`MEM_LIMIT` guard and the energy metering that is supposed to gate memory growth.

### Finding Description
`getVoteWitnessCost` and `getVoteWitnessCost2` pop the witness/amount array offsets and lengths straight off the EVM/TVM stack as `DataWord` (unsigned 256-bit) values and do: [1](#0-0) 

`DataWord.mul()`/`add()` operate mod 2^256 with no overflow signal — this mirrors the DataWord test suite's own `testMulOverflow`/`testAddModOverflow` cases showing silent wraparound is expected/normal behavior for these primitives: [2](#0-1) 

Because `amountArrayLength.mul(wordSize)` and `.add(wordSize)` can wrap, an attacker can choose a length such that `length*32 (+32)` overflows back to a tiny value. `memNeeded()` then returns a small `BigInteger`, `checkMemorySize()` (which compares against `MEM_LIMIT`) passes, and `calcMemEnergy` charges energy for a small memory region: [3](#0-2) 

The project's own regression test proves this is a genuine, previously-unfixed defect: it shows `cost2`'s `DataWord.mul()` wraps a huge length around undetected, whereas the newer `cost3` (using `BigInteger`, gated behind `VMConfig.allowTvmOsaka()`) throws `Program.OutOfMemoryException` for the same input: [4](#0-3) [5](#0-4) 

Critically, `cost3` **self-dispatches back to `cost2`'s vulnerable arithmetic whenever `VMConfig.allowTvmOsaka()` is not active** — i.e., the wraparound bug is only masked when the Osaka hard-fork feature switch is turned on for a given chain/node: [6](#0-5) 

This means any java-tron network (private chain, or the public chain prior to Osaka activation) still runs the unguarded `getVoteWitnessCost2` path reachable from `Op.VOTEWITNESS`, wired into the jump table used for every contract call: [7](#0-6) 

The root cause class matches the CVE precisely: a fixed-width arithmetic operation (multiply/add on a 256-bit word) is trusted by a bounds-checking/"verifier" routine (`checkMemorySize`/energy metering) without accounting for wraparound, so the check's conclusion ("this memory access is small and affordable") diverges from the real, attacker-supplied value that downstream code will act on.

### Impact Explanation
If a malicious contract can drive `getVoteWitnessCost2` to under-report the real memory footprint of a `VOTEWITNESS` call (by choosing a length whose `*32(+32)` wraps to a small `DataWord`), it bypasses:
1. The `MEM_LIMIT` guard (`checkMemorySize`) meant to reject unreasonably large memory requests and stop node-side over-allocation.
2. The energy/bandwidth accounting meant to charge the caller proportionally to actual memory usage, letting the caller allocate memory for free or far under cost.

Depending on how the subsequent memory extension in `Memory.extend`/`Program` uses the real (unwrapped) offset and length values versus the wrapped `BigInteger` that passed the check, this class of bug typically manifests as uncharged/uncontrolled memory growth or a crash from unexpected memory-size mismatch, i.e., a resource-metering bypass with potential for node instability. This satisfies the "unbacked" resource-accounting / node-crash category called out in scope.

### Likelihood Explanation
The `VOTEWITNESS` opcode is reachable by any account that deploys or calls a contract containing this opcode in the TVM — no special privilege is required, matching the "unprivileged contract deployer/caller" threat actor in scope. The vulnerable code path (`getVoteWitnessCost`/`getVoteWitnessCost2`) is the default path unless `VMConfig.allowTvmOsaka()` is enabled, so any deployment that has not activated the Osaka feature is exposed. Crafting the exact stack values to trigger the wrap is a simple integer computation (choose `length` such that `length*32(+32) mod 2^256` is small), requiring no race conditions or special timing.

### Recommendation
- Make the `BigInteger`-based, overflow-safe computation in `getVoteWitnessCost3` (currently only used when `allowTvmOsaka()` is true) unconditional for the memory-size/length arithmetic in `getVoteWitnessCost`/`getVoteWitnessCost2`, rather than gating the fix behind an unrelated hard-fork switch.
- Audit all other opcode/energy-cost helpers in `EnergyCost.java` that multiply/add `DataWord` values directly (any use of `DataWord.mul()`/`add()` on stack-controlled lengths) for the same wraparound pattern, and replace with `BigInteger` arithmetic before comparing against `MEM_LIMIT`.
- Add an explicit overflow check inside `DataWord.mul()`/`add()` (or a dedicated “checked” variant) for use in security-sensitive size calculations, so wraparound cannot silently defeat downstream bounds checks.

### Proof of Concept
1. Deploy a contract whose bytecode invokes `VOTEWITNESS` with a witness-array length or amount-array length `L` on the stack chosen such that `L * 32 + 32 mod 2^256` is small (e.g., `L = (2^256 - 32) / 32`, or any `L` derived by solving `L*32+32 ≡ small (mod 2^256)`).
2. Call this contract on a java-tron node/network where `VMConfig.allowTvmOsaka()` is not enabled (the default/legacy path), as validated directly by `VoteWitnessCost3Test.testLargeArrayLengthOverflow`/`testCost3FallsBackToCost2WhenOsakaOff`, which reproduce the wraparound and show `cost2` fails to raise `Program.OutOfMemoryException` for the same crafted length that `cost3` correctly rejects: [4](#0-3) 
3. Observe that `getVoteWitnessCost2` returns a low energy cost and does not throw the memory-overflow exception, whereas the real intended memory footprint associated with the true (unwrapped) `L` is enormous — demonstrating the check/charge is bypassed via the arithmetic wraparound, the exact class of defect described in CVE-2017-16995 (incorrect arithmetic tracking defeating a safety verifier).

*Note: I was unable to fully trace, within the available tool budget, the exact downstream code that performs the actual `VOTEWITNESS` memory read/write using the offset/length values (i.e., `VoteWitnessProcessor`/native contract execution path) to confirm whether the mismatch directly causes an OOM crash versus merely an energy-undercharge. This should be verified by a follow-up review of `org.tron.core.vm.nativecontract.VoteWitnessProcessor` and the corresponding `Program` memory-extension call sites for `Op.VOTEWITNESS`.*

  private static long calcMemEnergy(long oldMemSize, BigInteger newMemSize,
                             long copySize, int op) {
    long energyCost = 0;

    checkMemorySize(op, newMemSize);

    // memory SUN consume calc
    long memoryUsage = (newMemSize.longValueExact() + 31) / 32 * 32;
    if (memoryUsage > oldMemSize) {
      long memWords = (memoryUsage / 32);
      long memWordsOld = (oldMemSize / 32);
      long memEnergy = (MEMORY * memWords + memWords * memWords / 512)
          - (MEMORY * memWordsOld + memWordsOld * memWordsOld / 512);
      energyCost += memEnergy;
    }

    if (copySize > 0) {
      long copyEnergy = COPY_ENERGY * ((copySize + 31) / 32);
      energyCost += copyEnergy;
    }
    return energyCost;
  }

  private static void checkMemorySize(int op, BigInteger newMemSize) {
    if (newMemSize.compareTo(MEM_LIMIT) > 0) {
      throw Program.Exception.memoryOverflow(op);
    }
  }

  private static BigInteger memNeeded(DataWord offset, DataWord size) {
    return size.isZero() ? BigInteger.ZERO : offset.value().add(size.value());
  }

        EnergyCost.getVoteWitnessCost2(mockProgram(zero, new DataWord(1), zero, huge, 0));
