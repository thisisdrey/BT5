### Title
Attacker-controlled precompile instruction byte inflates declared signature count, causing cost-model overcharge and CostTracker/block-cost budget exhaustion disproportionate to real work - (File: `runtime-transaction/src/signature_details.rs`)

### Summary
`get_num_signatures_in_instruction` blindly trusts the first byte of a secp256k1/ed25519/secp256r1 precompile instruction's data as the "number of signatures," without any cross-check against the instruction's actual payload length or real signature verification. This value is baked into `signature_details()` at transaction sanitization time and later multiplied by `SECP256K1_VERIFY_COST`/`ED25519_VERIFY_STRICT_COST`/`SECP256R1_VERIFY_COST` in `CostModel::get_signature_cost`, feeding directly into `CostTracker::try_add`, so an attacker pays for one real signature but can debit the block/account cost budget as if hundreds of expensive signature verifications occurred.

### Finding Description
`get_num_signatures_in_instruction` reads only `instruction.data.first()` as the declared signature count with no validation: [1](#0-0) 

This is invoked from `PrecompileSignatureDetailsBuilder::process_instruction`, once per matching precompile instruction (not deduplicated per instruction, only the program-id classification is cached): [2](#0-1) 

It is computed at sanitization time in `RuntimeTransaction::try_from` via `InstructionMeta::try_new`, and stored as static `TransactionSignatureDetails` in the transaction's cached meta, long before the precompile's real `verify()` (which checks `data.len()` against `count * SIGNATURE_OFFSETS_SERIALIZED_SIZE`) is ever executed: [3](#0-2) [4](#0-3) 

Real verification only happens later, inside instruction execution, via `InvokeContext::process_precompile`, i.e. as a normal (possibly failing) instruction — not as a pre-execution sanitization gate: [5](#0-4) 

The declared (unverified) count is what `CostModel::get_signature_cost` uses to compute `signature_cost`, multiplying attacker-controlled values by the per-signature cost constants: [6](#0-5) [7](#0-6) 

Crucially, the post-execution "cost adjustment" logic (`sub_transaction_execution_cost`) only corrects `programs_execution_cost` (the CU meter), never `signature_cost`, and `calculate_cost_for_executed_transaction` recomputes `signature_cost` from the same cached, unverified `signature_details()`: [8](#0-7) [9](#0-8) 

Since precompile execution failures (e.g. `InvalidInstructionDataSize` when the declared count doesn't match the actual data) surface as ordinary `InstructionError`s inside a still-committed transaction (as demonstrated by the cost-adjustment test suite, where failing instructions still get committed and costed, only CU-meter is trued up, not signature cost): [10](#0-9) [11](#0-10) 

...the full attacker-declared signature cost is permanently applied via `check_block_cost_limits`/`try_add_processed_transaction_costs` → `CostTracker::try_add`, which enforces both `MAX_BLOCK_UNITS` and per-account (`account_cost`) limits: [12](#0-11) [13](#0-12) [14](#0-13) 

An attacker crafts a transaction with one real signature (fee payer) and many minimal precompile instructions (e.g. `program_id = secp256k1_program::ID`, `accounts = []`, `data = [255]`), each just a few bytes. Each such instruction adds `255 * SECP256K1_VERIFY_COST` (`255 * 223 * 30 ≈ 1.7M CU`) to the declared signature cost, while the real work performed at execution is a length check that fails almost instantly (`verify()` returns `InvalidInstructionDataSize` before any real `libsecp256k1` operation). Packing ~14 such instructions (trivially fits in the 1232-byte packet limit) yields ~24M CU of declared cost — enough to hit `MAX_WRITABLE_ACCOUNT_UNITS` (24,000,000) on the fee-payer/writable account, or a large chunk of `MAX_BLOCK_UNITS` (60,000,000) — for the price of a single base transaction fee.

### Impact Explanation
This is a fee/cost mismatch ("grossly underpriced pre-fee work" in reverse: real work is negligible but charged as if expensive) that lets an unstaked, unprivileged sender exhaust the per-account (`WouldExceedAccountMaxLimit`) or per-block (`WouldExceedBlockMaxLimit`) cost budget cheaply. This causes `CostTracker::try_add` to reject/evict other legitimate transactions competing for the same writable accounts or block budget, matching the "costliest-account/block-cost budget exhaustion" impact scoped in the question. It does not require staking, validator control, or any privileged access — only crafting and sending a transaction batch to the leader's TPU.

### Likelihood Explanation
High feasibility: the attacker only needs to control instruction data bytes of a standard transaction referencing the secp256k1/ed25519/secp256r1 program IDs, which any client can construct. No signature verification bypass is needed since the declared count feeds the cost model regardless of whether the precompile's real `verify()` later succeeds or fails — and per the cost-adjustment tests, failing instructions still result in a committed, costed transaction. This is fully repeatable per-slot with new blockhashes/nonces and requires no cooperation from other peers.

### Recommendation
Do not let the cost model trust an unverified declared signature count from raw instruction bytes. Options:
1. Cap the per-instruction declared signature count used for costing to a value consistent with the instruction's actual data length (mirror the same `expected_data_size` bound each precompile's `verify()` enforces), rather than accepting the raw `data[0]` byte unconditionally.
2. After a precompile instruction fails verification (`InstructionError` from `process_precompile`), true up `signature_cost` down to the real number of signatures actually verified (extending the existing post-execution cost-adjustment mechanism, currently limited to `programs_execution_cost`, to also cover `signature_cost`).
3. Alternatively, validate declared precompile signature counts against instruction data length during sanitization (in `PrecompileSignatureDetailsBuilder`/`InstructionMeta::try_new`), rejecting outright transactions whose declared count cannot possibly be satisfied by the instruction's actual byte length.

```rust
use solana_sdk_ids::secp256k1_program;
use solana_svm_transaction::instruction::SVMInstruction;
use solana_runtime_transaction::signature_details::get_precompile_signature_details;

#[test]
fn test_inflated_precompile_signature_cost_vs_real_work() {
    // A single-byte instruction declaring 255 "signatures" with no actual
    // signature-offset payload -- verify() would fail instantly on this,
    // performing zero real cryptographic work.
    let program_ids = [secp256k1_program::ID];
    let instruction = SVMInstruction {
        program_id_index: 0,
        accounts: &[],
        data: &[255u8], // declared count = 255
    };

    let details = get_precompile_signature_details(
        std::iter::once((&program_ids[0], instruction)),
    );
    assert_eq!(details.num_secp256k1_instruction_signatures, 255);

    // Feed into cost model constants directly (mirrors CostModel::get_signature_cost).
    use solana_cost_model::block_cost_limits::SECP256K1_VERIFY_COST;
    let declared_cost = details.num_secp256k1_instruction_signatures * SECP256K1_VERIFY_COST;
    // ~1.7M CU declared cost for an instruction whose real verify() work
    // is a single length check that fails immediately (no real crypto).
    assert!(declared_cost > 1_000_000);
}
```

```rust
pub fn verify(
    data: &[u8],
    instruction_datas: &[&[u8]],
    _feature_set: &FeatureSet,
) -> Result<(), PrecompileError> {
    if data.is_empty() {
        return Err(PrecompileError::InvalidInstructionDataSize);
    }
    let count = data[0] as usize;
    if count == 0 && data.len() > 1 {
        // count is zero but the instruction data indicates that is probably not
        // correct, fail the instruction to catch probable invalid secp256k1
        // instruction construction.
        return Err(PrecompileError::InvalidInstructionDataSize);
    }
    let expected_data_size = count
        .saturating_mul(SIGNATURE_OFFSETS_SERIALIZED_SIZE)
        .saturating_add(1);
    if data.len() < expected_data_size {
        return Err(PrecompileError::InvalidInstructionDataSize);
    }
```

```rust
    pub fn try_add(
        &mut self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<UpdatedCosts, CostTrackerError> {
        let cost = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // Check each account against account_cost_limit and apply the cost in
        // the same lookup. On failure, undo the applied prefix.
        let mut updated_costliest_account_cost = 0;
        for (index, account_key) in tx_cost.writable_accounts().enumerate() {
            let new_account_cost = match self.cost_by_writable_accounts.entry(*account_key) {
                Entry::Occupied(mut entry) => {
                    let new_account_cost = entry.get().saturating_add(cost);
                    if new_account_cost > self.limits.account_cost {
                        None
                    } else {
                        *entry.get_mut() = new_account_cost;
                        Some(new_account_cost)
                    }
                }
                Entry::Vacant(entry) => {
                    // `cost <= limits.account_cost` was checked above, so an
                    // account without chained cost always fits
                    entry.insert(cost);
                    Some(cost)
                }
            };
            let Some(new_account_cost) = new_account_cost else {
                // the first `index` accounts were applied before this failure
                self.roll_back_applied_costs(tx_cost, cost, index);
                return Err(CostTrackerError::WouldExceedAccountMaxLimit);
            };
            updated_costliest_account_cost = updated_costliest_account_cost.max(new_account_cost);
        }

        // every check passed: publish the block-level state
        self.allocated_accounts_data_size = allocated_accounts_data_size;
        self.transaction_count += 1;
        self.transaction_signature_count += tx_cost.num_transaction_signatures();
        self.secp256k1_instruction_signature_count +=
            tx_cost.num_secp256k1_instruction_signatures();
        self.ed25519_instruction_signature_count += tx_cost.num_ed25519_instruction_signatures();
        self.secp256r1_instruction_signature_count +=
            tx_cost.num_secp256r1_instruction_signatures();
        self.block_cost.fetch_add(cost);

        Ok(UpdatedCosts {
            updated_block_cost: self.block_cost(),
            updated_costliest_account_cost,
        })
    }
```

```rust
fn check_block_cost_limits<Tx: TransactionWithMeta>(
    bank: &Bank,
    tx_costs: &[Option<TransactionCost<'_, Tx>>],
) -> TransactionResult<()> {
    let mut cost_tracker = bank.write_cost_tracker().unwrap();
    for tx_cost in tx_costs.iter().flatten() {

            .map_err(TransactionError::from)?;
    }
```
