### Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` enables cross-chain replay to grant unauthorized signer capability — (`aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
`SignerCapabilityOfferProofChallengeV2` does not bind the signed challenge to a specific chain. A valid Ed25519 signature produced on testnet (or devnet) can be replayed on mainnet if the source account shares the same sequence number, granting the attacker-controlled `recipient_address` a `SignerCapability` over the victim's account.

### Finding Description
`RotationCapabilityOfferProofChallengeV2` was explicitly upgraded to include `chain_id` to prevent cross-chain replay:

```move
// line 147-153
/// This V2 struct adds the `chain_id` and `source_address` to the challenge message,
/// which prevents replaying the challenge message.
struct RotationCapabilityOfferProofChallengeV2 has drop {
    chain_id: u8,
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
``` [2](#0-1) 

The parallel struct for signer capability delegation was never given the same fix:

```move
// line 155-159
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
``` [3](#0-2) 

The BCS-serialized bytes of this struct are identical across all Aptos networks for any account that shares the same `sequence_number`, `source_address`, and `recipient_address`. The Ed25519 signature verification in `offer_signer_capability` → `verify_signed_message` → `signature_verify_strict_t` → `signature_verify_strict_internal` operates purely on those bytes with no chain-binding domain separator.

### Impact Explanation
A `SignerCapability` allows its holder to produce a `signer` for the delegating account and execute arbitrary Move calls on its behalf — including transferring APT, fungible assets, and any other resource the account controls. Cross-chain replay of a single testnet signature is sufficient to permanently set `signer_capability_offer.for` in `Account[A]` on mainnet to the attacker's address B. [4](#0-3) 

### Likelihood Explanation
The precondition is that the victim's account exists on both networks with the same sequence number at the time of the replay. This is realistic for newly created accounts (sequence number 0 or low values) and for accounts that are active on testnet but have not yet advanced their mainnet sequence number past the captured value. The attacker only needs to observe a single `offer_signer_capability` transaction on any non-mainnet network.

### Recommendation
Add `chain_id: u8` to `SignerCapabilityOfferProofChallengeV2`, populated via `chain_id::get()`, mirroring the fix already applied to `RotationCapabilityOfferProofChallengeV2`. All callers constructing this struct must be updated to include the chain ID.

### Proof of Concept
1. On a testnet harness, create account A (sequence number 0). Sign `SignerCapabilityOfferProofChallengeV2 { sequence_number: 0, source_address: A, recipient_address: B }` with A's Ed25519 key.
2. On a mainnet-parameter harness, create account A with the same key and sequence number 0.
3. Submit `offer_signer_capability(sig, 0, pubkey, B)` from account A using the testnet-produced signature.
4. Assert that `Account[A].signer_capability_offer.for == Some(B)` — the offer is accepted despite the signature being produced on a different chain, demonstrating the cross-chain replay.
