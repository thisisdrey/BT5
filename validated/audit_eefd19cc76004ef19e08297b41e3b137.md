## Analysis

The external report describes a flashloan attack that exploited a "price protection mechanism" to manipulate reserves and drain funds via a decentralized-exchange-style pool. The closest reachable analog in this java-tron repo is the built-in Bancor-relay TRC10/TRX Exchange feature (`ExchangeCreateContract` / `ExchangeInjectContract` / `ExchangeTransactionContract` / `ExchangeWithdrawContract`), which any account can invoke via a signed transaction or gRPC/HTTP API (`Wallet.exchangeCreate/Inject/Transaction/Withdraw`). [1](#0-0) 

The reserve-balance update after a trade only rejects a negative resulting balance **when hardened math is enabled**: [2](#0-1) 

`ALLOW_HARDEN_EXCHANGE_CALCULATION` defaults to `0` and can only be flipped on by a super-representative committee proposal: [3](#0-2) [4](#0-3) 

In the default (non-hardened) mode, the buy amount is computed purely with double-precision floating point via `Math.pow`, in `ExchangeProcessor` (the legacy, non-hardened processor): [5](#0-4) 

`ExchangeTransactionActuator.doValidate()` only enforces a lower-bound slippage check (`anotherTokenQuant < tokenExpected`) and an upper-bound check on the *sold* token's new balance against `exchangeBalanceLimit` — it never verifies that the *bought* token's balance stays non-negative before execution: [6](#0-5) 

`execute()` then unconditionally credits the attacker with `anotherTokenQuant` and persists the (potentially negative) pool balances: [7](#0-6) 

Because the double-precision `pow(1 + supplyQuant/supply, 2000.0)` computation in `exchangeFromSupply` can overflow to `Double.POSITIVE_INFINITY` (or produce a grossly inflated result) for extreme sell/supply ratios permitted by `exchangeBalanceLimit`, `(long) exchangeBalance` can exceed the actual `buyTokenBalance` held in the pool. In default mode this is never rejected, so `newSecondTokenBalance`/`newFirstTokenBalance` becomes negative while the caller's account is credited real TRX/TRC10 balance — an unbacked-balance mint directly analogous to the reserve-manipulation "price protection" bypass described in the Caterpillar Coin report.

### Title
Non-hardened Bancor exchange math allows pool reserves to go negative while crediting the trader, minting unbacked balance - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
`ExchangeCapsule.transaction()` only guards against negative resulting pool balances when `allowHardenExchangeCalculation` (chain parameter `ALLOW_HARDEN_EXCHANGE_CALCULATION`, default `0`) is enabled. In the default path, the legacy `ExchangeProcessor` computes the counter-token amount using floating-point `Math.pow` with an exponent of `2000.0`, which can return a result larger than the actual reserve for extreme sell-quantity/reserve ratios permitted by `exchangeBalanceLimit`. `ExchangeTransactionActuator` never independently checks that the computed `anotherTokenQuant` is ≤ the pool's counter-token balance, so the trade executes, the trader's account is credited the inflated amount, and the pool's persisted balance goes negative.

### Finding Description
- `ExchangeTransactionActuator.doValidate()` validates only a lower bound (`anotherTokenQuant < tokenExpected`, the "slippage protection") and an upper bound on the balance of the *sold* token, never on the *bought* token: [6](#0-5) 
- `ExchangeCapsule.transaction()` computes `buyTokenQuant` via `ExchangeProcessor.exchange()` (double math) or `SafeExchangeProcessor` (BigDecimal, hardened) depending on `hardenedCalc`, and only checks for a negative resulting balance in the hardened branch: [8](#0-7) 
- `ExchangeProcessor.exchangeFromSupply()` raises `1 + supplyQuant/supply` to the power `2000.0` using plain double `Math.pow`/`StrictMath.pow` (selected only for cross-platform consistency, not overflow safety): [9](#0-8) 
- `ALLOW_HARDEN_EXCHANGE_CALCULATION` is off by default on any chain until a super-representative committee explicitly enacts it post-fork 4.8.2: [3](#0-2) [4](#0-3) 
- `ExchangeTransactionActuator.execute()` then credits the caller with the (possibly reserve-exceeding) `anotherTokenQuant` and persists the exchange pool with negative reserves unchallenged: [10](#0-9) 

This mirrors the reported bug class: a DEX-style "price protection" (slippage/expected-amount) check that is insufficient to prevent reserve manipulation because it does not bound the trade against actual liquidity, letting an attacker mint value that is not backed by pool reserves.

### Impact Explanation
An attacker who creates or trades against an `Exchange` pool on a chain that has not enacted `ALLOW_HARDEN_EXCHANGE_CALCULATION` can, through a single `ExchangeTransactionContract` broadcast, extract more TRX/TRC10 tokens than the pool actually holds, driving one side of the reserve negative while the account balance/asset ledger is credited real, spendable value. This is an unbacked-balance/theft-of-funds condition, directly reachable by any unprivileged transaction broadcaster with no special permission.

### Likelihood Explanation
Exploitation requires finding sell-quantity/reserve ratios where the double-precision `pow(x, 2000.0)` computation departs materially from the true Bancor curve (e.g. near overflow to `Infinity`, or accumulated rounding at extreme skew), which is deterministic and can be searched for offline by the attacker before sending the transaction. Since `ALLOW_HARDEN_EXCHANGE_CALCULATION` defaults to disabled, every exchange pool on the network is exposed unless the SR committee has explicitly turned on hardened math, making this reachable "out of the box."

### Recommendation
Add the same non-negative reserve check unconditionally (not gated behind `hardenedCalc`) in `ExchangeCapsule.transaction()`, and additionally validate in `ExchangeTransactionActuator.doValidate()`/`execute()` that `anotherTokenQuant` never exceeds the current counter-token balance regardless of the `allowHardenExchangeCalculation` flag, so the legacy double-precision path can never authorize a trade the pool cannot honor.

### Proof of Concept
1. Create (or use an existing) `Exchange` pool with a small counter-token reserve relative to `exchangeBalanceLimit`, e.g. via `ExchangeCreateContract`.
2. On a chain where `ALLOW_HARDEN_EXCHANGE_CALCULATION` is `0` (default), broadcast an `ExchangeTransactionContract` selling an amount chosen so that `supplyQuant/supply` inside `ExchangeProcessor.exchangeFromSupply()` drives `pow(base, 2000.0)` to a value whose resulting `exchangeBalance` exceeds the pool's actual counter-token balance (this is the same class of test scaffolding already present in `hardenedExecuteOverflowThrowsArithmeticException`/`hardenedAddExactOverflowThrows`, but run with hardened mode left at its default `0`, so no `ArithmeticException`/negative-balance guard fires): [11](#0-10) 
3. Observe `ExchangeTransactionActuator.execute()` credits the full computed `anotherTokenQuant` to the attacker's account while `Commons.putExchangeCapsule` persists the exchange with a negative counter-token balance, since the negative-balance guard in `ExchangeCapsule.transaction()` is skipped for `hardenedCalc == false`. [2](#0-1)

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

    pool.setBalance(Long.MAX_VALUE - 5L, 10_000_000L);
    dbManager.getExchangeV2Store().put(pool.createDbKey(), pool);

    String tokenId = "_";

        OWNER_ADDRESS_SECOND, exchangeId, tokenId, quant, 1));
