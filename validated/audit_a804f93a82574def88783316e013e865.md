### Title
Unvalidated user-controlled array length in `PrecompiledContracts` ABI-array extraction leads to out-of-bounds array access / uncontrolled allocation - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` take a length value directly from attacker-controlled calldata (via a `DataWord.intValueSafe()` call) and use it, unchecked, both to size a newly allocated array and as a loop bound for indexing into the `words` array that was derived from the same calldata buffer.

### Finding Description
In `extractBytes32Array`: [1](#0-0) 
`len` is read straight from `words[offset].intValueSafe()` with no upper-bound check against `words.length`, and no check that `offset + len + 1` stays within the `words` array. The subsequent loop reads `words[offset + i + 1]` for `i` up to `len - 1`, which can run past the end of the actual `words` array derived from the calldata.

The same unchecked pattern repeats in `extractBytesArray`: [2](#0-1) 
and in `extractSigArray`: [3](#0-2) 

Both allocate `new byte[len][]` where `len` is an attacker-supplied integer with no upper bound validation, and then read `words[offset + i + 1]` in a loop whose extent is controlled entirely by the same attacker-supplied `len`, independent of the actual size of the calldata-derived `words` array. This is structurally analogous to the curl globbing flaw (CVE-2016-8620): an integer taken from untrusted input is used both to size a buffer and to drive out-of-bounds indexing without validating it against the real bounds of the source data.

These extraction helpers are used by the `ValidateMultiSign` and `BatchValidateSign` precompiled contracts (`validateMultiSignAddr` / `batchValidateSignAddr`), which any smart contract can invoke via a `CALL`/`STATICCALL` opcode when `VMConfig.allowTvmSolidity059()` is enabled: [4](#0-3) 

Because these precompiled addresses are reachable from any signed transaction that deploys or calls a contract performing the corresponding `CALL`, an unprivileged transaction broadcaster fully controls the calldata bytes that become the `words` array and the `len` fields extracted from it.

### Impact Explanation
If `len` is crafted to be large (bounded only by `intValueSafe()`'s clamping) but the actual calldata buffer is short, the loop will attempt to read indices beyond the `words` array bounds, causing an uncaught `ArrayIndexOutOfBoundsException`, or a very large `len` can trigger excessive array allocation (`OutOfMemoryError`). Depending on where in the TVM call stack these exceptions propagate and whether they are caught generically as reverts vs. escaping to node-level processing, this can range from a single-transaction revert (low impact) up to a node crash/DoS if the exception is not fully contained during block application. I was not able to fully trace, within the remaining investigation budget, whether the outer `Program`/`Runtime` call path wraps `PrecompiledContract.execute()`/`getEnergyForData()` calls with a catch-all `Throwable` handler that would fully contain this to a revert. This is the key point of remaining uncertainty.

### Likelihood Explanation
High: The precompiled contracts are reachable via a plain `CALL` from any TVM contract, requiring no special privileges, only that `allowTvmSolidity059()` is active (a normal, typically-enabled chain parameter). Crafting calldata with mismatched declared array length vs actual data length is straightforward for any transaction sender or contract deployer.

### Recommendation
Add explicit bounds validation before using any length value extracted from calldata in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`: verify `len >= 0` and that `offset + len + 1 <= words.length` (and, for `extractBytesArray`/`extractSigArray`, that computed `bytesOffset`/`bytesLen` values also stay within `data.length`) before allocating arrays or performing `System.arraycopy`/array indexing. Reject the call (return false/failure) rather than throwing when the declared count exceeds the actual buffer bounds.

### Proof of Concept
Construct a transaction that calls a contract which in turn issues a `CALL` (or `STATICCALL`) to the `ValidateMultiSign`/`BatchValidateSign` precompiled address (`...1006`/similar) with calldata whose signature-count or array-length word (the word read via `words[offset].intValueSafe()`) is set to a large value (e.g., `0xFFFFFFFF` truncated to a large positive int) while the actual calldata is only a few words long. This causes `extractSigArray`/`extractBytesArray` to iterate past the real `words` array bounds, throwing an `ArrayIndexOutOfBoundsException`, or to attempt to allocate an oversized `byte[len][]`, throwing `OutOfMemoryError`. A confirmed PoC requires tracing the exact call-site wrapping in `Program`/`VM` execution, which was not fully completed here.
