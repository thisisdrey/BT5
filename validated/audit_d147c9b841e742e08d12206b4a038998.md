**Rationale:**

The premise that `forward_distribution_next_shard` uniquely bypasses `validate_receipt` while the first-hop receipt from `initiate_distribution` is checked is incorrect. `validate_receipt` contains an explicit, unconditional exemption for this receipt kind that applies identically regardless of which code path or which `ValidateReceiptMode` invokes it:

```rust
VersionedReceiptEnum::GlobalContractDistribution(_) => Ok(()), // Distribution receipt can't be issued without a valid contract
``` [1](#0-0) 

This branch is reached both when `apply_action_receipt`'s actions loop calls `validate_receipt(..., NewReceipt)` on the first-hop distribution receipt produced by `initiate_distribution` [2](#0-1)  and (if it were called at all) when `process_incoming_receipts`/`process_delayed_receipts` validate `ExistingReceipt` mode [3](#0-2) . So there is no differential treatment between the first hop and subsequent hops — size/action validation for `ReceiptSizeExceeded` is deliberately skipped for every `GlobalContractDistributionReceipt`, everywhere, by design, not selectively bypassed by `forward_distribution_next_shard`.

Separately, even setting aside the uniform exemption, `forward_distribution_next_shard`'s per-hop growth is bounded to appending a single `ShardId` to `already_delivered_shards` [4](#0-3) , which adds only a few bytes per shard (bounded by the shard count), not an unbounded or attacker-controlled growth vector — the receipt's size is dominated by the contract code, which is already bounded/priced at deploy time via `action_deploy_global_contract`'s storage-cost charge [5](#0-4) . There is no evidence this produces divergent acceptance between chunk producer and chunk validator (the state transition is deterministic and identical on all nodes), nor any concrete loss/freezing of funds, consensus divergence, or shard-halting condition.
