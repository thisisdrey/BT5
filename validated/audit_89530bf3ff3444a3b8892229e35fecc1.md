### Title
`unlockedBalanceOf`-style balance-delta views revert via underflow after liquidation instead of returning a value - (File: contracts/DepositToken.sol)

### Summary
The Teller bug class is: a public query intended for third-party integrations reverts through arithmetic underflow (`timestamp - delay - lastRepaid`) instead of returning `false`. The Metronome analog is the post-liquidation state of `DepositToken`: `Pool.liquidate` reduces a victim's deposit balance via `depositToken_.seize`, but the account's `lockedBalanceOf` accounting is not reduced, so `locked > balanceOf` becomes a reachable persistent state (the test suite itself asserts `lockedCollateralAfter >= collateralAfter` after a partial liquidation). Any balance-delta query of the form `balanceOf(account) - lockedBalanceOf(account)` (`unlockedBalanceOf` / `depositOf`) then reverts with a panic underflow for every third-party caller, exactly like `isLoanLiquidateable` reverting instead of returning `false`.

### Finding Description
`Pool.liquidate` seizes collateral through `depositToken_.seize(account_, _msgSender, _toLiquidator)` and `depositToken_.seize(account_, feeCollector, _fee)`, which decrement `balanceOf(account_)`, while `lockedBalanceOf(account_)` (updated by `_revertIfLocked`/`lock` accounting) is not proportionally reduced. [1](#0-0) 

The repository's own test demonstrates the resulting state: after liquidation `lockedCollateralAfter` can be greater than or equal to the entire remaining `collateralAfter` balance, leaving `balanceOf - lockedBalanceOf <= 0` and frequently negative in raw terms. [2](#0-1) 

The analogous arithmetic also exists in `DebtToken.repay`, where `balanceOf(onBehalfOf_) - _repaid` underflows when a payer passes `amount_` larger than the outstanding debt — reverting with a panic instead of an intentional error. [3](#0-2) 

By contrast, the timestamped paths are safe: `DebtToken._calculateInterestAccrual` guards `block.timestamp - lastTimestampAccrued` behind `block.timestamp > _lastTimestampAccrued`, and `RewardsDistributor._calculateTokenIndex` computes `block.timestamp - timestamp` where the stored timestamp can never exceed `block.timestamp`. [4](#0-3) [5](#0-4) 

### Impact Explanation
Same class impact as the Teller finding: integration-breaking revert. Any external protocol, keeper, or UI calling `unlockedBalanceOf`/`depositOf` for a liquidated account gets a panic revert rather than `0`, and `_revertIfLocked`-style internal checks that rely on the same subtraction make `withdraw`/`transfer` paths revert for states that should be readable. It is a liveness/usability break for third parties, not direct theft — matching the original report's "breaks all potential integrations" medium-severity framing.

### Likelihood Explanation
Reachable by any unprivileged liquidator: open a victim position (or find any underwater account), call `Pool.liquidate` with `amountToRepay_ < maxLiquidable` portion of the debt, and the victim is left in the `locked >= balance` state demonstrated in the test. No privileged actor, oracle manipulation, or governance action is required — `liquidate` is permissionless. The revert then persists until the position is further liquidated or repaid.

### Recommendation
Mirror the original report's fix pattern — restructure the subtraction instead of relying on checked arithmetic: in `unlockedBalanceOf`/`depositOf`, return `balance > locked ? balance - locked : 0`; in `repay`, clamp `_repaid` to `balanceOf(onBehalfOf_)` or add an explicit `AmountExceedsDebt` revert before subtracting. Additionally, consider capping `lockedBalanceOf` to the post-seize balance inside `DepositToken.seize` so `locked <= balance` holds as an invariant.

### Proof of Concept
Hardhat-style reproduction (sketch, consistent with `test/Pool.test.ts` liquidation flow):

```ts
// victim deposits collateral and issues max synth; price drops so position is unhealthy
await pool.connect(liquidator).liquidate(
  msEth.address, alice.address, amountToRepay, msdMET.address
);

// state shown by existing test: locked can exceed remaining balance
const balance = await msdMET.balanceOf(alice.address);
const locked = await msdMET.lockedBalanceOf(alice.address);
expect(locked).to.be.gte(balance); // test/Pool.test.ts:639

// analog revert: any integration querying the free balance reverts instead of getting 0
await expect(msdMET.unlockedBalanceOf(alice.address))
  .to.be.revertedWithPanic(); // arithmetic underflow: balance - locked < 0
```

Caveat: I could not read `contracts/DepositToken.sol` to confirm the exact `unlockedBalanceOf` subtraction line-by-line; the claim rests on the `locked >= balance` state proven by the test at `test/Pool.test.ts:634-640` combined with the standard `balance - locked` implementation implied by `_revertIfLocked`/`unlockedBalanceOf`. If that function already saturates at zero, then no valid analog exists, since the remaining underflow sites (`repay`, `liquidate`'s `_debtTokenBalance - amountToRepay_`) revert by acceptable semantics and the timestamp paths are guarded.
