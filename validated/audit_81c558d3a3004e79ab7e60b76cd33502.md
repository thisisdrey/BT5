### Title
Adaptive concurrency limiter uses point-sampled, non-time-integrated "load-weighted" observations instead of a true time-weighted average, allowing sustained inter-sample load to evade backpressure - (File: `internal/loadmonitor/monitor.go`, `internal/limiter/condition_cpu.go`, `internal/limiter/adaptive_calculator.go`)

### Summary
Gitaly's adaptive concurrency-limiting backpressure (used to protect all Git RPC handlers, including `PostUploadPackWithSidechannel`, `PostReceivePack`, and other push/fetch/clone paths) derives its "how loaded is the system" signal from two independently fixed-interval samplers whose output is treated as a step function rather than a true time-weighted measure, mirroring the TWAP report's root cause: the resulting "average load" is really an observation-weighted signal that ignores how long pressure actually persisted between observations. An unprivileged client that paces resource-intensive Git operations to land in the gaps between samples can sustain real backend resource pressure while never tripping (or while under-counting) the corresponding backoff signal, keeping the adaptive concurrency limit inflated and defeating the DoS protection the mechanism is meant to provide.

### Finding Description
Two layers compound the issue:

1. **`LoadMonitor` point-sampling**: `DefaultMonitor` polls cgroup stats only once per `PollInterval` (default `10s`) [1](#0-0) , and its main loop simply resets the ticker and polls at that fixed cadence [2](#0-1) . `poll()` stores only the two endpoints — `previousStats` and `currentStats` — of the interval [3](#0-2) ; nothing in between is captured.

   The CPU-throttling `Condition` then computes throttled duration strictly as the delta between these two snapshots divided by the elapsed interval: `throttledDuration/pollInterval.Seconds() > threshold` [4](#0-3) . This treats a brief, intense throttling spike that starts and fully resolves inside the 10-second window as identical to "no throttling," so long as the spike doesn't straddle the sampled boundary values enough to cross the 50% threshold at those two fixed instants.

2. **`AdaptiveCalculator` step-function calibration**: Independently, the calculator recalibrates every `CalibrationInterval` (default `30s`) using a fixed ticker [5](#0-4) . Within a calibration window, it keeps only the *most recent* `BackoffEvent` (last-observation-wins, not time-integrated) via `setLastBackoffEvent`, and unconditionally resets it to `nil` after each tick regardless of how much of the 30-second window was actually under pressure [6](#0-5) [7](#0-6) . `calibrateLimits` then makes a single binary decision per limit — additive `+1` if `backoffEvent == nil`, or multiplicative `× BackoffFactor` if any event occurred — with no accounting for event count, duration, or recency within the window [8](#0-7) .

Just as the PRICE.sol "TWAP" only records a fixed number of price observations without weighting by the time elapsed between them (allowing manipulation by controlling when/if `beat()` is called), Gitaly's load signal only records discrete stats at fixed polling/calibration boundaries without weighting by how long the underlying pressure condition actually persisted. A client that understands (or empirically discovers) the default 10s poll / 30s calibration cadence can synchronize bursts of expensive Git operations (large pack generation, deep history diffs, etc.) to occur and dissipate between poll boundaries, so the two-point delta used by conditions like `newCPUThrottlingCondition` never crosses the threshold, and/or so that isolated backoff events are diluted by intervening `nil` resets before the next calibration tick, letting the additive-increase branch keep raising `AdaptiveLimit` even while aggregate load is high.

### Impact Explanation
This directly weakens `ConcurrencyLimiter`/`AdaptiveCalculator`, which is Gitaly's primary backpressure mechanism protecting Git RPC handlers from resource exhaustion (per `doc/backpressure.md` and `doc/load-management-architecture.md`) [9](#0-8) . An ordinary, unprivileged client driving normal push/fetch/clone RPCs can pace load to keep the adaptive per-repository/per-RPC concurrency limit at or near `Max` while imposing sustained CPU/memory pressure between samples, degrading availability for other tenants on the same Gitaly node — a DoS of the RPC-handler resource-limiting mechanism itself.

### Likelihood Explanation
The default intervals (`defaultPollInterval = 10s`, `DefaultCalibrateFrequency = 30s`) are fixed and documented/configurable constants, not secret, so an attacker can time bursts accordingly with modest experimentation against a target node's observed behavior. No credentials beyond ordinary repository access (clone/fetch/push) are required, and the mechanism runs identically for every RPC subject to `[[concurrency]]` limiting.

### Recommendation
- Compute load/pressure using a genuinely time-integrated (or continuously-weighted) measure across the calibration window rather than two-point deltas at fixed poll boundaries — e.g., accumulate throttled-time and event duration continuously, weighting each sub-interval by its own elapsed time, similar to how PSI `avg10/avg60/avg300` already work internally in cgroups.
- In `AdaptiveCalculator.calibrateLimits`, aggregate all backoff events observed during a calibration window (count, cumulative duration, severity) instead of retaining only the last event before reset, so brief-but-real pressure isn't diluted or missed.
- Consider variable/jittered polling and calibration intervals to prevent clients from reliably synchronizing bursts to sampling gaps.

### Proof of Concept
1. Configure Gitaly with default `LoadMonitor.PollInterval` (10s) and `AdaptiveCalculator.CalibrationInterval` (30s) and an adaptive `[[concurrency]]` limit on a fetch/clone RPC.
2. As an ordinary client, repeatedly issue expensive Git operations (e.g., large `git-upload-pack` invocations causing CPU throttling) in short bursts timed to complete and recover within a single 10-second poll window, with idle gaps aligned to just before each `pollTicker` fire (`internal/loadmonitor/monitor.go:220,231`).
3. Observe via `gitaly_concurrency_limiting_current_limit` and `gitaly_pressure` metrics that the CPU-throttling condition (`internal/limiter/condition_cpu.go:38`) rarely or never fires because the two sampled endpoints don't reflect the intervening spike, and that `AdaptiveCalculator` continues its additive-increase path (`internal/limiter/adaptive_calculator.go:261-270`), keeping the concurrency limit at `Max` despite sustained real CPU pressure on the node.

func (m *DefaultMonitor) poll() error {
	// Record the time right before polling
	now := time.Now()

	// Poll the cgroups stats
	cgroupStats, err := m.cgroupManager.Stats()
	if err != nil {
		return fmt.Errorf("polling cgroup stats failed: %w", err)
	}

	// There is no need to lock access to the state here because poll is called
	// synchronously before notify
	if m.state.lastPoll.IsZero() {
		// This is the first poll, set the previous state to the current state.
		m.state.previousStats.CGroup = cgroupStats
	} else {
		m.state.previousStats = m.state.currentStats
		m.state.lastPollInterval = now.Sub(m.state.lastPoll)
	}

	m.state.currentStats.CGroup = cgroupStats
	m.state.currentStats.pollTime = now
	m.state.lastPoll = now
	return nil
}

func (c *AdaptiveCalculator) waitForEvents(ctx context.Context) {
	for {
		select {
		case <-ctx.Done():
			return

		case e := <-c.eventCh:
			c.setLastBackoffEvent(&BackoffEvent{
				ConditionName: e.ConditionName,
				Reason:        e.Description,
				ShouldBackoff: true,
				CurrentStats:  e.CurrentStats,
				PreviousStats: e.PreviousStats,
			})
		}
	}
