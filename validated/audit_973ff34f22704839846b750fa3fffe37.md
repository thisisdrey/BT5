Based on my investigation, I found a concrete analog in the `near-wallet-contract` (the ETH-implicit account Wallet Contract), which is the in-scope "eth-implicit wallet contract" component.

### Title
Attached deposit permanently locked in Wallet Contract when `rlp_execute` fails before reaching `rlp_execute_callback` - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The Wallet Contract's `rlp_execute` entry point is `#[payable]`, accepting an attached deposit from an external caller (relayer), tracked via `CallerDeposit` so it can be refunded if the downstream cross-contract call fails. However, the refund of `caller_deposit` is only performed inside `rlp_execute_callback` on `PromiseResult::Failed` [1](#0-0) . Several other failure branches that occur *before* `rlp_execute_callback` is reached return an `ExecuteResponse`/error directly without ever creating a refund promise for the tracked `caller_deposit`, permanently trapping the caller's attached NEAR in the wallet contract's balance.

### Finding Description
`CallerDeposit::new` captures the predecessor's attached deposit whenever the caller is not the wallet contract itself [2](#0-1) . This is passed through async callback chains (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`) so that if the outer cross-contract promise fails, the caller gets refunded [3](#0-2) .

The refund logic exists in exactly one place — `rlp_execute_callback`, on `PromiseResult::Failed` [1](#0-0) . But `address_check_callback` has multiple early-return paths that discard `caller_deposit` without refunding it:
- When the address-registrar cross-contract call itself fails (`PromiseResult::Failed`) [4](#0-3) .
- When the registrar response cannot be deserialized [5](#0-4) .
- When the target address is found registered to a named account and the calling signer is not the wallet contract itself, resulting in `"Invalid target..."` error [6](#0-5) .

Similarly `nep_141_storage_balance_callback` discards `caller_deposit` without refunding when the `storage_balance_of` call fails or its response can't be parsed [7](#0-6) .

In all of these cases, the function returns `PromiseOrValue::Value(ExecuteResponse{...})`, which means the method call completes *successfully* from the runtime's perspective (`rlp_execute` doesn't panic/fail) — this is intentional so the contract can persist state changes such as banning a dishonest relayer [8](#0-7) . Because the receipt succeeds, near's protocol-level deposit-refund mechanism does not trigger (deposit refunds only occur when a receipt's execution fails) [9](#0-8) , and the wallet contract itself never issues a compensating transfer back to the depositor for these code paths. The attached NEAR balance stays with the wallet contract's account with no function ever created to sweep or reclaim it (no "withdraw" method exists in this contract, mirroring the reported `UpliftOnlyExample` bug class where funds land in a contract with no path back out).

### Impact Explanation
Any relayer or third-party caller that attaches a deposit to `rlp_execute` (e.g., for an ERC-20/base-token transfer targeting another eth-implicit account, which triggers the address-registrar check path, or a NEP-141 transfer requiring the storage-balance check path) risks having that deposit permanently stuck in the target eth-implicit account if the registrar call or storage-balance call fails, or if the target resolves to an already-registered named account. This is a direct, protocol-adjacent loss of funds for legitimate callers using the standard eth-implicit-account wallet flow described in NEP-518, with no recovery mechanism.

### Likelihood Explanation
This requires attaching a non-zero deposit to `rlp_execute` while targeting a flow that spawns `address_check_callback` or `nep_141_storage_balance_callback` (ERC-20 transfers to unregistered eth-implicit targets, or NEP-141 transfers needing storage registration) and having the downstream call fail (e.g., registrar unreachable, malformed response, or already-registered target). These are realistic operational conditions for relayers routinely serving ETH-implicit-account users, not a contrived edge case, making the likelihood moderate-to-high in production usage of the Wallet Contract.

### Recommendation
In `address_check_callback` and `nep_141_storage_balance_callback`, propagate/refund the `caller_deposit` on every early-return branch that does not eventually route through `rlp_execute_callback`'s existing refund logic — i.e., add the same `promise_batch_create` + `promise_batch_action_transfer` refund pattern used in `rlp_execute_callback` [10](#0-9)  to the failure/error branches at lines 141-148, 149-158, 168-173, and 203-220 of `lib.rs`.

### Proof of Concept
Not independently executed (index-only analysis); the code path is directly traceable:
1. Relayer calls `rlp_execute` with a non-zero attached deposit, targeting another eth-implicit account address that is not itself, producing `TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer{address_check: Some(addr), ..})` — this defers the fee-refund and instead calls the address registrar, spawning `address_check_callback` with `caller_deposit = Some(...)` [11](#0-10) .
2. If the registrar cross-contract call fails or returns unparsable data, `address_check_callback` returns `ExecuteResponse{success:false,...}` directly at lines 141-158 without refunding `caller_deposit`.
3. The wallet contract's account balance now permanently retains the attached deposit; no method in `WalletContract` exists to reclaim it.
