Audit Report

## Title
XCM `ERC20Transactor` credits full requested amount into `AssetsInHolding` without verifying actual tokens received by the checking account, allowing fee-on-transfer/non-standard ERC20 tokens to drain the shared checking account - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` calls an arbitrary ERC20 contract's `transfer(checking_address, amount)` and, based solely on the boolean success return of the call, unconditionally constructs `Erc20Credit(amount)` and inserts it into the XCM holding register, without ever reading `balanceOf(checking_address)` to confirm the shared checking account actually received `amount`. [1](#0-0)  `deposit_asset_with_surplus` symmetrically transfers the same recorded `amount` out of the same shared `TransfersCheckingAccount` on later deposits. [2](#0-1) 

## Finding Description
`ERC20Transactor` is wired into `asset-hub-westend`'s `AssetTransactors` tuple, used alongside `FungibleTransactor`, `FungiblesTransactor`, etc., with a dedicated shared `ERC20TransfersCheckingAccount` (a `PalletId`-derived account) and `assets_common::ERC20Matcher` as its `Matcher`. [3](#0-2)  `pallet_revive::Config` on this runtime has `AllowEVMBytecode` enabled, meaning arbitrary Solidity/EVM contracts (including custom, non-standard ERC20 implementations) can be deployed by any signed account via `UploadOrigin`/`InstantiateOrigin` set to `EnsureSigned`. [4](#0-3) 

In `withdraw_asset_with_surplus`, the code encodes and dispatches `IERC20::transferCall { to: checking_address, value: amount }`, and only checks (a) whether the call reverted and (b) whether the ABI-decoded boolean return is `true`; if so, it credits `Erc20Credit(amount)` — the requested amount, not any measured delta — into `AssetsInHolding`. [5](#0-4)  There is no `balanceOf` read before/after the call anywhere in this function. A fee-on-transfer, rebasing, or deflationary ERC20 contract can legally return `true` from `transfer` while delivering less than `amount` to `checking_address`, and this code path does not detect that.

Symmetrically, `deposit_asset_with_surplus` transfers `amount` from the shared `TransfersCheckingAccount` to the beneficiary using the same trust-the-boolean-return pattern, again without any verification of the beneficiary's real balance delta. [6](#0-5)  Because the checking account is shared across all XCM programs using this transactor for a given token, an inflated `Erc20Credit` recorded from one (attacker-controlled, fee-on-transfer) withdrawal is indistinguishable in the XCM holding register from a legitimately fully-funded credit, and later deposits will draw down real balance in the shared account that may have been contributed by unrelated transfers.

## Impact Explanation
This breaks the invariant that XCM-recorded holding amounts must reflect actually-custodied value; the on-chain ERC20 balance of the shared `TransfersCheckingAccount` can diverge from the `AssetsInHolding` register's `Erc20Credit` amount. Consequences allowed by the repository's impact gate include unbacked/duplicate settlement (the holding register claims more was received than the checking account actually holds) and permanent fund lock (subsequent `deposit_asset_with_surplus` calls reverting due to insufficient real balance in the shared account), both of which fall under "theft or unbacked mint or unlock, duplicate settlement or payout, permanent user-fund ... lock."

## Likelihood Explanation
No privileged actor is required: `pallet_revive` on `asset-hub-westend` permits any `EnsureSigned` account to upload/instantiate arbitrary EVM bytecode including custom fee-on-transfer ERC20 contracts, and any user can then route that token through `pallet-xcm::execute` or a reserve transfer to hit `withdraw_asset_with_surplus`/`deposit_asset_with_surplus`. The only existing guard — checking the boolean `transfer` return value — is satisfied by a fee-on-transfer token while still under-delivering the recorded amount, so the guard does not block this path. This requires the attacker's custom token to be `matches_fungibles`-recognized by `assets_common::ERC20Matcher`; the exact permission model of that matcher (whether it accepts arbitrary contract addresses directly encoded in a `Location`/`AssetId`, or requires prior registration) could not be fully confirmed from the files inspected — this is the one open point that could not be fully verified.

## Recommendation
In `withdraw_asset_with_surplus`, read `balanceOf(checking_address)` before and after the `transfer` call and construct `Erc20Credit` from the actual observed delta rather than the requested `amount`. Symmetrically, in `deposit_asset_with_surplus`, verify the beneficiary's balance delta matches the intended transfer, and return any shortfall back into `AssetsInHolding` (trapped assets) instead of assuming full-amount success purely from the boolean return value.

## Proof of Concept
1. Deploy an ERC20 contract on `pallet-revive` (permitted since `AllowEVMBytecode: ConstBool<true>` and `UploadOrigin`/`InstantiateOrigin: EnsureSigned`) whose `transfer` implementation burns e.g. 5% of `value` from the recipient's credited balance while still returning `true`.
2. Ensure the contract's address is recognized by `assets_common::ERC20Matcher` as used by `ERC20Transactor` in `AssetTransactors`.
3. Execute an XCM program performing `WithdrawAsset` for `amount` of this token; `withdraw_asset_with_surplus` calls `transfer(checking_address, amount)`, gets `true`, and constructs `Erc20Credit(amount)` even though `checking_address`'s real balance only increased by `amount * 0.95`. [7](#0-6) 
4. Repeat alongside unrelated legitimate transfers of the same token sharing `ERC20TransfersCheckingAccount`; observe cumulative real balance falling behind the sum of recorded `Erc20Credit` amounts, causing later `deposit_asset_with_surplus` transfers to fail or to be paid from balance contributed by other users.
