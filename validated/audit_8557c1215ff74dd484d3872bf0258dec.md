### Title
Griefing via dust deposits fills victim's deposit-token list to `MAX_TOKENS_PER_USER`, blocking further deposits and transfers - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The MySQL CVE is a low-privileged availability (hang/crash DoS) bug; the Metronome analog is an unprivileged liveness attack against a victim's collateral accounting. `DepositToken.deposit(amount_, onBehalfOf_)` lets any EOA mint deposit tokens to an arbitrary `onBehalfOf_` address. Every first-time mint (or transfer into an account with zero balance) calls `pool.addToDepositTokensOfAccount(account_)`, which enforces the per-account cap `MAX_TOKENS_PER_USER` defined in `Pool.sol`. An attacker can dust-deposit (or dust-transfer) every enabled deposit token to a victim until the victim's list hits the cap; after that, any operation that would add a new token to the victim's list reverts — `deposit(..., victim)`, `transfer(..., victim)`, `seize(from, victim, ...)` during liquidation — until the victim manually clears entries.

### Finding Description
- `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` and only rejects `address(0)` and the Treasury; there is no opt-in for receiving a new token type [1](#0-0) 
- `_mint` adds the token to the recipient's pool-level list whenever their prior balance is zero [2](#0-1) 
- `_transfer` does the same on plain transfers, so an attacker who already holds deposit tokens can also push new entries via `transfer(victim, dust)` — `transfer` only checks the *sender's* unlocked balance, never the recipient's list capacity [3](#0-2) 
- `addToDepositTokensOfAccount` in `contracts/Pool.sol` reverts once `depositTokensOfAccount[victim].length == MAX_TOKENS_PER_USER` (the constant and its enforcement live in `Pool.sol`/`PoolStorage.sol`, which contain the `MAX_TOKENS_PER_USER` matches). Removal only happens when a balance returns to zero [4](#0-3) 

Attack path (all unprivileged):
1. Attacker deposits/obtains dust amounts of deposit tokens.
2. For each enabled `DepositToken` `d_i`, attacker calls `d_i.transfer(victim, 1)` (or `d_i.deposit(1, victim)` with underlying dust) until `depositTokensOfAccount(victim).length == MAX_TOKENS_PER_USER`.
3. Any subsequent `deposit`, `transfer`, `seize`, or liquidation crediting the victim with a *new* token type reverts.

### Impact Explanation
Temporary freezing of funds / forced liveness degradation: the victim cannot receive deposits, LP-collateral transfers, or liquidation proceeds in any token not already in their list. Critically, `DepositToken.seize` is used by `Pool.liquidate` — a liquidator who has never held a given deposit token can be blocked from receiving seized collateral for it, which can make liquidations of that victim revert depending on the liquidator's token list, harming the protocol's bad-debt resolution path. Recovery requires the victim to send full-balance transfers to zero out list entries one at a time (each removal costs a transfer and is re-griefable by the attacker at dust cost).

### Likelihood Explanation
- Fully unprivileged: needs only an EOA, dust amounts of underlying/deposit tokens, and public `deposit`/`transfer` entry points.
- Cost is bounded by `MAX_TOKENS_PER_USER` transactions of minimal value; on L2s (Optimism, Base, Hemi, Swell deployments exist) this is cheap.
- Modifiers do not stop it: `deposit` has `whenNotPaused`/`nonReentrant`/`onlyIfDepositTokenExists` only; `transfer` has no cap check on the recipient side; `SynthContext._msgSender` checks don't restrict `onBehalfOf_`.
- The victim cannot prevent being listed — receiving a token is permissionless by design.

### Recommendation
- Require opt-in for new token entries: either restrict `deposit(onBehalfOf_)` so `onBehalfOf_ == _msgSender()` unless the caller is whitelisted, or maintain a per-account "accepted collateral" opt-in flag checked in `addToDepositTokensOfAccount`.
- Alternatively, charge a minimum first-deposit amount (e.g., a USD floor via `masterOracle`) so dust-listing is uneconomical, or track "has ever held" separately from the capped list so receiving additional tokens doesn't consume list slots.

### Proof of Concept
Hardhat fork sketch (mainnet fork, using deployed pool and deposit tokens):

```ts
import { ethers } from 'hardhat';

it('fills victim deposit-token list and DoSes deposits', async () => {
  const pool = await ethers.getContractAt('Pool', POOL);
  const victim = (await ethers.getSigners())[1];
  const attacker = (await ethers.getSigners())[2];

  // Enumerate registered deposit tokens
  const dTokens: string[] = await pool.getDepositTokens(); // or iterate pool.depositTokenList()

  const cap = await pool.MAX_TOKENS_PER_USER();

  for (let i = 0; i < cap; i++) {
    const dt = await ethers.getContractAt('DepositToken', dTokens[i % dTokens.length]);
    const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
    // acquire dust underlying (whale impersonation / swap), approve, dust-deposit on behalf of victim
    await underlying.connect(attacker).approve(dt.address, 1);
    await dt.connect(attacker).deposit(1, victim.address);
  }

  expect((await pool.depositTokensOfAccount(victim.address)).length).to.eq(cap);

  // Victim tries to deposit a collateral type not in their list -> reverts
  const dtNew = await ethers.getContractAt('DepositToken', dTokens[0]); // any token victim doesn't hold after clearing, or a newly added collateral
  const underlyingNew = await ethers.getContractAt('IERC20', await dtNew.underlying());
  await underlyingNew.connect(victim).approve(dtNew.address, ethers.utils.parseUnits('1', 18));
  await expect(dtNew.connect(victim).deposit(ethers.utils.parseUnits('1', 18), victim.address))
    .to.be.reverted; // MaxLimitReached from pool.addToDepositTokensOfAccount

  // Liquidator receiving a new token via seize also reverts
  // ... construct underwater victim position, liquidator with full token list, liquidate() reverts at seize
});
```

Note on verification: I confirmed the deposit/transfer/seize hooks and the permissionless `onBehalfOf_` path in `DepositToken.sol`, and that `MAX_TOKENS_PER_USER`/`addToDepositTokensOfAccount`/`removeFromDepositTokensOfAccount` exist in `contracts/Pool.sol` and `contracts/storage/PoolStorage.sol` (9 grep matches), but I could not open `Pool.sol` to quote the exact revert line before the iteration limit — the PoC's revert assertion should be checked against that function's concrete error name. If `addToDepositTokensOfAccount` does not actually enforce the cap, this finding is invalid; that check is the load-bearing assumption.
