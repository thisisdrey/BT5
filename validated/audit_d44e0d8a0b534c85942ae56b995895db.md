### Title
Unauthenticated `RecvError` packet spoofing enables remote tunnel-teardown DoS via uncontrolled `RemoteIndexes` binding - (File: outside.go, handshake_manager.go, hostmap.go)

### Summary
`RecvError` packets are processed by `readOutsidePackets` before any certificate/handshake authentication and are resolved to a `HostInfo` purely via the plaintext `h.RemoteIndex` field against the `HostMap.RemoteIndexes` map. That map is explicitly documented as holding values "outside our control" and can be silently overwritten/shadowed by any peer that completes its own handshake with a colliding self-chosen index, and the packet itself carries no cryptographic proof binding it to the session it claims to terminate.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` straight to `f.handleRecvError(via.UdpAddr, h)` before any tunnel/cert state is consulted: [1](#0-0) 

`handleRecvError` resolves the target tunnel solely from `h.RemoteIndex` via `QueryReverseIndex`, which reads the `RemoteIndexes` map: [2](#0-1) [3](#0-2) 

The `RemoteIndexes` map key (`remoteIndexId`) is the *peer's own* self-chosen local index — a value Nebula does not control or verify for global uniqueness. This is called out directly in the hostmap/handshake code: [4](#0-3) [5](#0-4) [6](#0-5) 

This is structurally the same bug class as the CID `mint()`/`add()` finding: a caller-supplied/attacker-influenceable identifier (`_cidNFTID` there, `RemoteIndex`/`remoteIndexId` here) is used to select which victim's state an action applies to, without the system verifying that the identifier still belongs to the flow the actor believes it does. In CID, an attacker mints ahead of the victim to make the victim's `add()` land on the attacker's token. In Nebula, any unauthenticated party can (a) observe `RemoteIndex` values in cleartext packet headers exchanged with a victim, or (b) deliberately complete its own handshake choosing a local index that collides with (and per the log message "shadows") an already-established victim tunnel's `remoteIndexId` — then send a bare, unauthenticated `RecvError` packet that `handleRecvError` uses to tear down whatever `HostInfo` currently occupies that index slot.

The only check standing between "attacker knows/collides an index" and "tunnel torn down" is:
```
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr { ... return }
f.closeTunnel(hostinfo)
```
This is a soft address-equality check on data that is itself attacker-controlled at the UDP layer (spoofable, and the comparison is skipped entirely if `hr` is not yet valid, e.g., for relay-established or not-yet-roamed hostinfos).

### Impact Explanation
Impact is remote, unauthenticated denial-of-service / remote state poisoning: a party with no CA-signed certificate can force closure of another peer's established Nebula tunnel by sending a single small `RecvError` packet, exploiting an index value it did not need to be cryptographically authorized to use. This is analogous in class (though lower severity than the CID theft bug) to the "attacker exploits an uncontrolled, reused, or collidable identifier to hijack/disrupt another party's in-flight or established state" pattern from the source report. It fits the allowed "firewall bypass / remote state poisoning / remote crash impact" categories because it disrupts an authenticated tunnel's availability using pre-authentication packet handling.

### Likelihood Explanation
Moderate-to-low but non-trivial: the attacker must either (1) be positioned to observe cleartext headers of the victim's Nebula traffic (on-path, or via a colluding relay/lighthouse-adjacent vantage point) to learn a valid `RemoteIndex`, or (2) deliberately engineer an index collision by repeatedly initiating handshakes and picking indices that collide with a known-active tunnel — the collision code path explicitly acknowledges this is possible and only logs it ("New host shadows existing host remoteIndex"). Combined with UDP source-address spoofing (feasible on networks without egress filtering) to satisfy the `hr != addr` check, or exploiting the case where `hr` is not yet valid, this is achievable without holding a certificate from the network's CA.

### Recommendation
- Do not use the peer-chosen `remoteIndexId`/`RemoteIndex` as sole authorization for terminating a tunnel; require `RecvError` handling to also validate against session-specific state that is not attacker-choosable (e.g., only accept `RecvError` for indexes we ourselves allocated as `localIndexId`, mirroring how `Indexes`/`QueryIndex` already guarantees uniqueness, or require an authenticated/counter-bound proof).
- Reject/ignore collisions in `RemoteIndexes` instead of silently shadowing the existing entry (the current "just log" behavior should escalate to refusing to link the new hostinfo to that index).
- Tighten `handleRecvError` so that a `hr` that is not yet `IsValid()` cannot bypass the address-binding check.

### Proof of Concept
1. Attacker (no valid Nebula certificate) passively observes or brute-forces the `RemoteIndex` used between victim host A and its established peer B (values are cleartext in every packet header, and the responder-chosen index is also visible during the handshake exchange).
2. Attacker sends a crafted UDP packet to A with `header.Type = RecvError` and `h.RemoteIndex` set to the observed/colliding value, spoofing the source address to match B's known UDP endpoint (or timing it for a state where `hr.IsValid()` is false).
3. `readOutsidePackets` routes this directly to `handleRecvError` without any certificate or handshake check.
4. `QueryReverseIndex` resolves the victim's live `HostInfo` for B, the address check passes (or is skipped), and `f.closeTunnel(hostinfo)` tears down A's tunnel to B.

Note: I was not able to fully verify, within the available tool budget, the exact conditions under which `HostInfo.GetRemote()` returns an "invalid" `AddrPort` (e.g., for relay-only or pre-roam hostinfos), which would determine whether the address-spoofing step is even necessary. This should be confirmed against `hostmap.go`'s `GetRemote`/`SetRemote` implementation before relying on this PoC for exploitation without spoofing.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
```

```go
func (hm *HostMap) QueryReverseIndex(index uint32) *HostInfo {
	hm.RLock()
	if h, ok := hm.RemoteIndexes[index]; ok {
		hm.RUnlock()
		return h
	} else {
		hm.RUnlock()
		return nil
	}
}
```
