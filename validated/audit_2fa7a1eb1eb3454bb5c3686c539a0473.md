### Title
Unbounded array allocation from attacker-controlled length field in `PrecompiledContracts.extractBytesArray` / `extractSigArray` (legacy code path) - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` (address `0x9`) and `ValidateMultiSign` (address `0xa`) TVM precompiled contracts decode ABI-encoded `bytes[]` parameters by reading a length word directly from attacker-supplied call data and immediately allocating a Java array of that size, with the size-capping check (`MAX_SIZE`) only enforced on the newer, feature-gated code path.

### Finding Description
`ValidateMultiSign.execute` and `BatchValidateSign.doExecute` parse the raw call data into `DataWord[] words` and then extract the signature array via a ternary that is keyed off `VMConfig.allowTvmSelfdestructRestriction()`: [1](#0-0) 

When that flag is enabled, `sigArraySize` is checked against `MAX_SIZE` **before** the array is materialized: [2](#0-1) 

But when the flag is disabled, execution falls through to the legacy helper `extractBytesArray`, which has no such guard: [3](#0-2) 

`len` comes straight from `words[offset].intValueSafe()` — a 32-byte word fully controlled by the transaction/contract-call sender — and is used to allocate `new byte[len][]` with no upper bound check, exactly analogous to `ReadDDSInfo` in ImageMagick trusting an attacker-supplied size field to drive an allocation/loop before validating it (CVE-2017-1000476). The same unguarded pattern exists in `extractBytes32Array`, used for the `address[]` argument of `BatchValidateSign`: [4](#0-3) 

This precompile is only reachable when `VMConfig.allowTvmSolidity059()` gates the address routing: [5](#0-4) 

### Impact Explanation
If `allowTvmSelfdestructRestriction` is not active (e.g. the corresponding hard fork has not yet activated on a given network, or on any private/test/forked chain that has not enabled it), any account can deploy a contract that `CALL`s address `0x9` or `0xa` with a crafted length word (up to `Integer.MAX_VALUE`-range), causing the node to attempt a huge array allocation (`new byte[len][]`) during transaction execution/energy metering. This can throw `OutOfMemoryError` or cause severe GC pressure across the whole node process, which is not a per-transaction energy-limited cost — a classic CPU/memory exhaustion DoS, matching CVE-2017-1000476's bug class.

### Likelihood Explanation
Exploitability depends entirely on whether `VMConfig.allowTvmSelfdestructRestriction()` is active on the target network. I was not able to determine from the available index whether this fork flag is unconditionally activated (hard-coded true) on current mainnet or still conditionally gated by block height/committee proposal — the file `chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java` and `VMConfig.java` reference it as a switchable fork parameter, suggesting it can, in principle, be inactive on some deployments (new private chains, forks that haven't replayed the activation block, or misconfigured genesis). If inactive, the path is trivially reachable by any unprivileged contract deployer/caller via a single `CALL` instruction, with no special privileges required.

### Recommendation
Move the `MAX_SIZE` bound check to run unconditionally, before calling either `extractBytesArray`/`extractBytes32Array` or `extractSigArray`, regardless of the `allowTvmSelfdestructRestriction()` flag value, so the length read from attacker-controlled call data can never drive an oversized allocation. Alternatively, add a length sanity check inside `extractBytesArray`/`extractBytes32Array`/`extractSigArray` themselves (e.g., reject `len < 0 || len > MAX_SIZE` or a small absolute cap) before allocating the array.

### Proof of Concept
1. On a network/config where `allowTvmSelfdestructRestriction` is disabled, deploy a trivial contract.
2. From that contract, issue a `CALL` to precompile address `0x000...9` (BatchValidateSign) or `0x000...a` (ValidateMultiSign) with ABI-encoded call data whose `bytes[]` length-word offset (`words[1]` / `words[3]`) is set to a very large positive 32-bit value (e.g. `0x7FFFFFFF`), while keeping the remainder of the payload short.
3. `doExecute`/`execute` calls `extractBytesArray(words, offset, data)`, which reads that length and executes `new byte[len][]`, attempting to allocate hundreds of millions of array-reference slots, exhausting node memory before any subsequent bounds/`MAX_SIZE` check can reject it.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {

    for (int i = 0; i < len; i++) {

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
