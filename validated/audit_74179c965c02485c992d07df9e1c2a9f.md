### Title
Remote panic on `/status` in `SignerEventReceiver::next_event` via early connection close - ([File: libsigner/src/events.rs])

### Summary
In `SignerEventReceiver::next_event`, the `/status` branch calls `request.respond(HttpResponse::from_string("OK")).expect("response failed")` with no error handling, unlike every other response path in the same function (`ack_dispatcher`, `process_event`) which log-and-continue on write errors. Any unauthenticated remote client that connects to the signer's event-receiver port, sends `GET /status ...`, and closes the socket before the response write completes will make `tiny_http`'s write fail, triggering the `.expect()` panic and killing the event-receiver thread.

### Finding Description
`next_event` (`libsigner/src/events.rs:413-459`) accepts requests via `http_server.recv()` and dispatches by URL. For `/status`:
```rust
if request.url() == "/status" {
    request
    .respond(HttpResponse::from_string("OK"))
    .expect("response failed");
    return Ok(SignerEvent::StatusCheck);
}
``` [1](#0-0) 

Every other reply path in this file tolerates a write/IO failure instead of panicking: `ack_dispatcher` does `if let Err(e) = request.respond(...) { error!(...) }` [2](#0-1) , and `process_event` also routes through `ack_dispatcher`. The `/status` branch is the sole exception with an unguarded `.expect()`.

`tiny_http::Request::respond` performs a blocking write of the HTTP response to the underlying `TcpStream`. If the peer has already closed/reset the connection (e.g., immediately after sending the request line), the write returns `io::Error` (broken pipe / connection reset), which `respond()` propagates as `Err`. The unguarded `.expect("response failed")` converts that IO error into a panic inside the event-receiver's request-handling closure, which unwinds through `next_event` and the `main_loop`/receiver thread. There is no `catch_unwind` around this call path found in `libsigner/src/runloop.rs` or `events.rs`'s `main_loop`, so the panic terminates the dedicated event-receiver thread.

No authentication or secret gates the `/status` endpoint — `next_event` reaches the `/status` branch before any auth/method checks, so this is reachable by an unprivileged remote party who can merely open a TCP connection to the signer's listening endpoint (the sample configs show this endpoint can be bound to `0.0.0.0`, i.e., non-loopback, e.g. `sample/conf/signer/mainnet-signer-conf.toml:39`) [3](#0-2) .

### Impact Explanation
A single crafted request (`GET /status HTTP/1.1\r\n\r\n` followed by an immediate socket close before the response is fully written) panics and kills the signer's event-receiver thread. Once that thread dies, the signer stops receiving all future node events (block proposals, StackerDB chunks, burn blocks) via this observer, effectively disabling the signer's participation until the process is restarted. This is a remotely triggerable, unauthenticated denial-of-service from a single message, matching the "Critical - remote crash/unauthenticated DoS from few messages" category, scoped specifically to the signer's event-receiver thread (not the whole node process, since Rust thread panics do not abort the process by default and no `panic = "abort"` setting was found in the workspace).

### Likelihood Explanation
No special preconditions are required beyond network reachability to the signer's event-receiver port, which per the sample configuration files is explicitly supported to bind on `0.0.0.0` (all interfaces) — the docs even warn about exposing this endpoint to an "external node" being risky. The `/status` branch is reached before any method/auth check, so no secret, StackerDB slot ownership, or peer identity is needed — purely an unprivileged TCP client. The attack is trivially repeatable (each connect+early-close attempt has a chance to race the response write; on typical local/adjacent networks this is highly reliable) and costs a single short-lived TCP connection.

### Recommendation
Handle the `Result` from `request.respond(...)` in the `/status` branch the same way `ack_dispatcher` does elsewhere in the file — log the error via `error!` (or `warn!`) instead of `.expect()`, so a client that disconnects early cannot panic the event-receiver thread. Optionally route `/status` through `ack_dispatcher`-style handling for consistency.

### Proof of Concept
Add a test in `libsigner/src/events.rs`'s `tests` module (or `libsigner/src/tests/mod.rs`, alongside `test_status_endpoint`) that:
1. Binds a `SignerEventReceiver` on a test port and spawns the receiver's `main_loop` in a thread (as `test_status_endpoint` at `libsigner/src/tests/mod.rs:199-230` already does for the happy path).
2. Opens a raw `TcpStream` to the endpoint, writes `"GET /status HTTP/1.1\r\n\r\n"`, and immediately calls `stream.shutdown(Shutdown::Both)` / drops the socket without reading the response.
3. Joins the receiver thread and asserts it panicked (e.g., wrap the receiver thread spawn with `std::thread::Builder::spawn` and check `JoinHandle::join().is_err()`), demonstrating the panic at `libsigner/src/events.rs:426` (`.expect("response failed")`). [1](#0-0) [2](#0-1)
