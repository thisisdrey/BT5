### Title
Dust-transfer griefing fills `depositTokensOfAccount`/`debtTokensOfAccount` to `MAX_TOKENS_PER_USER`, DoSing victim deposits, borrowing and collateral top-ups - (File: contracts/Pool.sol, contracts/DepositToken.sol)

### Summary
`Pool` tracks every deposit/debt token a user holds in two enumerable sets capped at `MAX_TOKENS_PER_USER = 30` combined. Every `DepositToken._transfer` and `DepositToken._mint` adds the token to the recipient's set and reverts with `UserReachedMaxTokens` once the cap is hit. Because `DepositToken.transfer`/`transferFrom` are public and permissionless, an attacker can push dust amounts of many different deposit tokens to a victim, filling all 30 slots and making every subsequent `deposit()` (which calls `_mint` → `pool.addToDepositTokensOfAccount`) and every `issue()`/`leverage()` (which adds a `DebtToken` to the shared count) revert — an availability/DoS analog of the InnoDB hang/crash class in CVE-2026-35237.

### Finding Description
`Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30` [1](#0-0) . `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero [2](#0-1) , and `transfer` only checks the sender's unlocked balance [3](#0-2) . The pool supports up to 30 deposit tokens, so an attacker holding dust of each can saturate a victim's list at near-zero cost (1 wei per token). Critically, `deposit()` mints via `_mint`, which hits the same revert [4](#0-3) , so the victim cannot add *any new collateral type* — including in the same transaction they intended to use to restore health before liquidation. Debt issuance is also blocked because the same combined counter is checked for debt tokens [5](#0-4) . The victim's only remediation is to transfer each dust token fully out (so `removeFromDepositTokensOfAccount` fires), but the attacker can front-run or re-dust repeatedly since the dust tokens remain freely transferable.

### Impact Explanation
Temporary freezing of funds and forced-liquidation exposure. While the cap is saturated, all of the victim's calls to `DepositToken.deposit` for a collateral they do not already hold revert, and `DebtToken.issue`/`SmartFarmingManager.leverage` revert when they would add a new debt token. A victim whose position is approaching unhealthy cannot top up with a new collateral type and can be liquidated, losing collateral plus the liquidation fee — damage directly caused by the attacker grief. This mirrors the source CVE's availability-only impact (denial of service of a core function) on Metronome's own code.

### Likelihood Explanation
The attack needs only unprivileged EOAs and ordinary ERC-20 transfers of whitelisted deposit tokens; no privileged role, oracle manipulation, or flash loan is required. Cost is bounded by acquiring 1 wei–scale balances of each listed `DepositToken` (minted by depositing dust of each underlying). The attack is repeatable: every time the victim clears a slot, the attacker can refill it. It does require the pool to list enough distinct deposit tokens to approach the cap and a victim holding fewer than 30 tracked tokens, but on deployments with several collaterals this is cheap and reliable.

### Recommendation
Do not add a token to `depositTokensOfAccount`/`debtTokensOfAccount` on plain `transfer`/`transferFrom` for unsolicited dust, or decouple the accounting set from transferability — e.g., only track tokens that were added through `deposit`/`issue`/`seize`, or make `addToDepositTokensOfAccount` non-reverting (drop/ignore additions beyond the cap while still allowing positions in untracked tokens to be valued via a fallback). Alternatively, raise/replace the hard cap with a design that does not give third parties the ability to write entries into a victim's set.

### Proof of Concept
```solidity
// Hardhat fork test sketch
// Setup: pool has N deposit tokens listed (msdA, msdB, ...).

// 1) Attacker deposits dust into each DepositToken to mint itself 1+ wei.
for (token of depositTokens) {
    underlying.approve(token, DUST);
    token.deposit(DUST, attacker);          // attacker gets >0 msd balance
}

// 2) Victim currently tracks K tokens. Attacker fills the remaining
//    30 - K slots with 1-wei transfers.
for (i = 0; i < 30 - K; i++) {
    depositTokens[i].connect(attacker).transfer(victim, 1);
}
// depositTokensOfAccount(victim) + debtTokensOfAccount(victim) == 30

// 3) Victim tries to deposit a collateral it doesn't hold yet (e.g.
//    to rescue an unhealthy position) — reverts.
await expect(
    newDepositToken.connect(victim).deposit(amount, victim)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// 4) Victim tries to issue a new debt token — also reverts via
//    DebtToken._mint -> pool.addToDebtTokensOfAccount.
await expect(
    newDebtToken.connect(victim).issue(amount, victim)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// 5) Attacker front-runs any cleanup transfer to re-dust the freed slot,
//    keeping the victim's deposit/borrow path DoS'd while liquidate()
//    proceeds against them.
```
