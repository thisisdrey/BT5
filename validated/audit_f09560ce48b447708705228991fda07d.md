## Title
HTTP request `Transfer-Encoding: chunked` header is silently ignored, causing chunked request bodies to desync the connection and enable request smuggling - (File: `stackslib/src/net/http/request.rs`)

### Summary
`HttpRequestPreamble::consensus_deserialize` never inspects the `Transfer-Encoding` header. Every request's body length is taken exclusively from `Content-Length` (defaulting to `0` when absent), while any `Transfer-Encoding: chunked` header is stored as an ordinary, unconsumed header string. When a client sends a chunk-encoded body without (or with a mismatched) `Content-Length`, the node's connection state machine treats the body as zero-length and leaves the un-decoded chunked bytes sitting in the read buffer, where they are subsequently re-parsed as the start of a brand-new HTTP request on the same connection. This is the same underlying bug class as CVE-2010-2227 (Tomcat mishandling of an invalid `Transfer-Encoding` header corrupting buffer state) — here it desyncs the Stacks node's own request/response framing rather than a shared buffer pool, but the fault-line is identical: the declared byte length of the body does not equal the bytes actually present, and the excess bytes are misattributed to the next message.

### Finding Description
`HttpRequestPreamble::consensus_deserialize` explicitly special-cases only `host`, `content-type`, `content-length`, `connection`, and `set-cookie` headers; any other header (including `transfer-encoding`) falls through to the generic `headers` map and is never used to influence parsing: [1](#0-0) 

`HttpReservedHeader::is_reserved` likewise does not recognize `transfer-encoding`, confirming it is never treated as a framing-relevant header for requests: [2](#0-1) 

The request body length used everywhere downstream is `get_content_length()`, which silently returns `0` if no `Content-Length` header was sent — regardless of any `Transfer-Encoding` header: [3](#0-2) 

`StacksHttp::payload_len` for a `Request` preamble unconditionally reports this (possibly zero) content length as the known payload size: [4](#0-3) 

`ConnectionInbox::consume_payload_known_length` then hands the *entire remaining buffer* to `protocol.read_payload`, trusting that the protocol will only consume `payload_len` bytes and advance `message_ptr` by exactly `message_len`: [5](#0-4) 

`StacksHttp::read_payload` for requests slices only `buf[0..len]` (where `len == get_content_length()`) and returns `message_len = len`: [6](#0-5) 

Combining these: if a client sends `Transfer-Encoding: chunked` and omits (or lies about) `Content-Length`, `len` is `0`, so `read_payload` parses the request with an empty body and reports `message_len = 0`. Back in `consume_payload_known_length`, `next_message_ptr = message_ptr + 0`, so the buffer is *not* advanced past the actual chunked body bytes the client sent — those bytes remain in `self.buf` and become the input to the next call to `read_preamble`/`consensus_deserialize`, i.e., they are parsed as an entirely new HTTP request on the same connection.

This breaks the equality "declared body length == bytes actually consumed for that message." An attacker can place a second, fully-formed HTTP request inside what looks (to any front-end component that *does* honor `Transfer-Encoding`, e.g. a reverse proxy fronting the RPC/API port) like the body of the first request. The proxy and the Stacks node disagree on where request #1 ends and request #2 begins — the textbook TE.CL request-smuggling primitive.

### Impact Explanation
This is a request-smuggling / auth-bypass primitive reachable by any unauthenticated remote client that can reach the node's HTTP RPC interface. In deployments where the Stacks node sits behind a reverse proxy or load balancer that applies access control, rate limiting, or routing based on parsed request boundaries, an attacker can smuggle a request past those controls by hiding it inside a chunk-encoded body of an allowed request — the proxy sees one request; the node processes two. This matches the "Critical — request smuggling or auth bypass" category in scope.

### Likelihood Explanation
Any remote, unauthenticated peer that can open an HTTP connection to a node's RPC endpoint can trigger this by simply adding a `Transfer-Encoding: chunked` header (with no/short `Content-Length`) and appending a smuggled request after the chunked body — no cryptographic material, node secret, or privileged role is required.

### Recommendation
Explicitly reject (400) any HTTP request preamble that contains a `Transfer-Encoding` header, and/or reject requests with `Transfer-Encoding: chunked` and no correctly-terminating body consumption, mirroring the check already done for HTTP *responses* in `HttpResponsePreamble::consensus_deserialize` (which does understand `transfer-encoding` and rejects the conflicting/ambiguous case): [7](#0-6) 
The same "transfer-encoding" detection and hard-fail-on-conflict logic used for responses should be applied to `HttpRequestPreamble::consensus_deserialize`.

### Proof of Concept
```
POST /v2/transactions HTTP/1.1
Host: node:20443
Transfer-Encoding: chunked
Connection: keep-alive

5
hello
0

GET /v2/info HTTP/1.1
Host: node:20443
Connection: keep-alive

```
- `content_length` is `None` (no `Content-Length` header sent) → `get_content_length()` returns `0`.
- The node parses the `POST /v2/transactions` request with an empty body and reports `message_len = 0`.
- The buffer position is not advanced past `"5\r\nhello\r\n0\r\n\r\n"`, so the node's next parse pass reads `GET /v2/info HTTP/1.1...` out of what a chunk-aware intermediary would consider the *body* of the first request — demonstrating the desync.
