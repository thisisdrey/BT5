### Title
Global Deployer's `gd_post_deploy` callback commits deployment state without checking the deploy promise's success - (File: `contracts/global-deployer/src/contract.rs`)

### Summary
`Contract::deploy()` chains `deploy_global_contract_by_account_id(code)` with a `.then()` callback `gd_post_deploy`, but `post_deploy()` never inspects the outcome of the preceding promise before committing `code_hash` state and consuming the approval. This is the exact analog of the `create2` return-value bug: the code assumes the deployment action succeeded instead of verifying it, so a reverted/failed deployment is recorded as a successful one.

### Finding Description
`Contract::deploy()` builds a single promise batch (transfer + `deploy_global_contract_by_account_id`) and attaches a callback via `.then()`/`gd_post_deploy`: [1](#0-0) 

The callback `post_deploy` is invoked unconditionally once the deploy attempt's receipt resolves, but it does not call `env::promise_result(...)` or otherwise validate that `deploy_global_contract_by_account_id` actually succeeded: [2](#0-1) 

Instead, `post_deploy` unconditionally:
- sets `self.0.code_hash = code_hash`,
- emits `GdEvent::Deploy`,
- resets `approved_hash` back to `DEFAULT_HASH` (burning the approval),
- computes a refund from `env::account_balance()` deltas.

If the preceding deploy action fails for any reason (e.g. gas exhaustion mid-batch, storage/byte-cost edge cases, protocol-level rejection of the WASM payload, or any other revert of `deploy_global_contract_by_account_id`), NEAR still executes the `.then()` callback — callbacks always run regardless of the parent receipt's outcome — but `gd_post_deploy` has no logic to detect the failure. This mirrors the reported bug class: checking only that a call "returned" (the promise resolved) rather than validating that the underlying deployment actually produced the expected on-chain artifact (bytecode present at `result`, vs. here, code actually deployed to `current_account_id`).

### Impact Explanation
Because the approval is a single-use, owner-gated permission (`gd_approve`/`gd_approved_hash`), an unprivileged caller invoking the permissionless `gd_deploy` can trigger a scenario where:
- `approved_hash` is consumed/reset to zero even though the code was never actually deployed,
- `code_hash` is updated to reflect a hash for code that does not exist on-chain,
- refund accounting is computed against a false premise of "deploy succeeded."

This breaks the binding between the contract's recorded `code_hash` state and the actual deployed bytecode. Any downstream logic or off-chain tooling trusting `gd_code_hash()` (e.g. via `contracts/global-deployer/README.md`'s deployment attestations, or dependent controller/escrow instances relying on `GlobalContractId::AccountId` resolution) can be misled, and the owner's approval mechanism is silently invalidated without an actual upgrade taking place — requiring a fresh owner approval to recover, i.e. state desync/DoS on the deployment workflow with no valid authorization actually having been granted.

### Likelihood Explanation
`gd_deploy` is explicitly permissionless — "anyone can deploy as long as SHA-256 hash of the code matches currently approved one" — so any unprivileged actor can invoke it. Triggering the deploy sub-action to fail while the outer receipt/callback still resolves is a purely mechanical scenario (e.g., insufficient attached gas/deposit tuning, hitting `deploy_global_contract_by_account_id` protocol-level failure conditions) fully controllable by the caller who supplies both the WASM payload and the attached deposit/gas in the same call.

### Recommendation
In `gd_post_deploy`/`post_deploy`, explicitly check the promise result of the deploy action (e.g. via `env::promise_result(0)` or an analogous SDK API for verifying the prior batched action succeeded) before committing `code_hash`, emitting `GdEvent::Deploy`, or resetting `approved_hash`. If the deploy failed, the callback should panic/revert without mutating approval state, so that the approval remains valid for a retry.

### Proof of Concept
1. Owner calls `gd_approve(old_hash, new_hash)` to approve `new_hash`.
2. An unprivileged caller calls `gd_deploy(code)` where `sha256(code) == new_hash`, but crafts the call (gas/deposit) such that the batched `transfer` + `deploy_global_contract_by_account_id(code)` receipt fails on-chain (e.g., insufficient gas forwarded to complete the deploy action, or a protocol-level rejection).
3. NEAR still executes the attached `.then()` callback `gd_post_deploy`, since callback execution is unconditional.
4. `post_deploy` runs to completion: sets `code_hash = new_hash` even though no code was deployed, emits a `Deploy` event, and resets `approved_hash` to `DEFAULT_HASH`, consuming the owner's one-time approval for nothing.
5. Contract state now claims `gd_code_hash() == new_hash` while the account's actual global contract code is unchanged/absent, and the owner must re-approve to retry deployment — see `Contract::deploy`/`post_deploy` at [3](#0-2) .

        fn deploy(&self, code: Vec<u8>) -> Result<Promise> {
            let code_hash = Sha256::digest(&code).into();

            if !self.is_approved(&code_hash) {
                return Err(Error::InvalidCodeHash);
            }

            let initial_balance = env::account_balance().saturating_sub(env::attached_deposit());

            Ok(Self::ext_on(
                Promise::new(env::current_account_id())
                    // 0. In case a receipt fails, re-direct the refund to the same
                    // account which was specified as `refund_to` for current receipt.
                    .refund_to(env::refund_to_account_id())
                    // 1. Transfer attached deposit to ourselves, so that it doesn't
                    // affect our balance while in-flight. We could have attached
                    // it to `gd_post_deploy()` below, but this balance is needed
                    // for `deploy_global_contract_by_account_id` to succeed, so
                    // we add a separate transfer action before.
                    .transfer(env::attached_deposit())
                    // 2. Deploy the global contract by our account_id
                    .deploy_global_contract_by_account_id(code),
            )
            .with_static_gas(Self::GD_POST_DEPLOY_MIN_GAS)
            .with_unused_gas_weight(1)
            // 3. Call post-deploy callback **in the same receipt**
            .gd_post_deploy(code_hash.into(), initial_balance, env::attached_deposit()))
        }

        fn post_deploy(
            &mut self,
            code_hash: [u8; 32],
            initial_balance: NearToken,
            deploy_deposit: NearToken,
        ) -> Result<()> {
            // check that approved hash hasn't changed while in-flight
            if !self.is_approved(&code_hash) {
                return Err(Error::InvalidCodeHash);
            }

            self.0.code_hash = code_hash;
            GdEvent::Deploy { code_hash }.emit();

            // remove just-used approval
            self.approve(State::DEFAULT_HASH, ApprovalReason::Deploy(code_hash));

            let refund = env::account_balance()
                .saturating_sub(initial_balance)
                .min(deploy_deposit);
            if !refund.is_zero() {
                // refund the rest to `refund_to` forwarded here by `gd_deploy()`
                Promise::new(env::refund_to_account_id())
                    .transfer(refund)
                    .detach();
            }

            Ok(())
        }
