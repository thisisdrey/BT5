### Title
Instruction-data byte cost truncation systematically undercounts transaction cost, enabling QoS evasion of block cost limits - ([File: cost-model/src/cost_model.rs])

### Summary
The Anchor-style report describes LBPair's `SwapHelper.getAmounts` applying a fee formula on the wrong base amount, causing systematic under-collection of fees that compounds with repeated/multi-step operations. The equivalent bug class in agave — a resource-pricing calculation that always rounds in the "cheaper for the user" direction and compounds across many small units of work — exists in the cost model's instruction-data byte accounting used to gate block cost limits.

### Finding Description
`CostModel::get_instructions_data_cost` computes the compute-unit cost attributed to instruction data bytes using integer (floor) division: [1](#0-0) 

against the constant: [2](#0-1) 

`INSTRUCTION_DATA_BYTES_COST` is itself the floor of `140/COMPUTE_UNIT_TO_US_RATIO` (=`140/30`≈4.67, truncated to `4`) at compile time, and then `instruction_data_len / 4` truncates again per transaction. This means any transaction whose total instruction data length is not a multiple of 4 loses up to 3 bytes worth of cost accounting entirely (a full "free" allowance), and in the worst case (instruction data length < 4 bytes) the entire instruction payload is priced at **zero** CU cost, despite still consuming block-production bandwidth, serialization, and I/O.

This computed `data_bytes_cost` directly feeds `TransactionCost::sum()`: [3](#0-2) 

which is what `CostTracker::try_add` uses to enforce `MAX_BLOCK_UNITS` / `MAX_WRITABLE_ACCOUNT_UNITS` limits during banking-stage block production: [4](#0-3) 

Because the rounding is always downward (never rounded up like `calculate_loaded_accounts_data_size_cost`'s page accounting, which explicitly adds `page_size - 1` before dividing — see `calculate_pages_for_bytes`), any unprivileged user submitting many transactions whose instruction data length modulo 4 is nonzero systematically under-reports the true data cost of the block. This is directly analogous to the LBPair bug: a per-unit fee/cost computation whose rounding direction favors the caller, which compounds as more units (transactions, in this case) are packed into the same block.

### Impact Explanation
An attacker splitting a data-heavy workload into many small transactions (each crafted so `instruction_data_len % 4 != 0`, or trivially `< 4` bytes) causes the cost tracker to under-account the true data-carrying cost of the block relative to what `INSTRUCTION_DATA_BYTES_COST` intends to charge. Since `try_add` is the sole gate for `WouldExceedMaxBlockCostLimit`/`WouldExceedMaxAccountCostLimit` during banking-stage packing (used from `core/src/banking_stage/consumer.rs` via `try_add_processed_transaction_costs`), this allows more instruction-data bytes to be packed into a block than the block-cost model's intended `INSTRUCTION_DATA_BYTES_COST` rate permits, a QoS evasion of the cost-based block-production throttle. This is a resource-accounting undercharge reachable by any unprivileged transaction submitter, matching the "grossly underpriced pre-fee work" class called out in scope, though — like the original Medium-severity LBPair finding — the per-transaction magnitude is small (at most 3 CU per transaction, i.e., ≤0.75 bytes-equivalent), so the aggregate effect on block-production timing is limited and bounded by the number of transactions fit per block.

### Likelihood Explanation
The condition is trivially and deterministically reachable by any user: crafting instruction data whose length is not divisible by 4 (or is very short) requires no special privileges, only a normal transaction submission. No feature gate or validator-role bypass is required, and the erroneous rounding is unconditional in `get_instructions_data_cost`.

### Recommendation
Change `get_instructions_data_cost` to round up (ceiling) the same way `calculate_pages_for_bytes` does for loaded-accounts-data-size cost, e.g. `(instruction_data_len + INSTRUCTION_DATA_BYTES_COST - 1) / INSTRUCTION_DATA_BYTES_COST`, so instruction data is never charged less compute-unit cost than intended, consistent with how the other cost components in `TransactionCost` are computed conservatively.

### Proof of Concept
1. Construct a transaction whose combined instruction data length is, e.g., 3 bytes (or any value not a multiple of `INSTRUCTION_DATA_BYTES_COST = 4`).
2. Call `CostModel::calculate_cost` on it and observe `data_bytes_cost == 0` via `get_instructions_data_cost` (`3 / 4 == 0` in integer division): [1](#0-0) 
3. Submit N such transactions in a block; each contributes 0 CU for its instruction-data footprint to `CostTracker::block_cost`, allowing more raw instruction-data bytes to be admitted than `MAX_BLOCK_UNITS`/`INSTRUCTION_DATA_BYTES_COST` was designed to permit, while `try_add` still accepts them as fitting under the limit: [4](#0-3)

    pub fn try_add(
        &mut self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<UpdatedCosts, CostTrackerError> {
        let cost = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
