### Title
Unauthenticated peer-reported Stacks tip height permanently poisons `/v2/health` via unbounded `max`-based update - (File: `stackslib/src/net/mod.rs`)

### Summary
The Apollo Oracle report describes how a single compromised price source can skew a supposedly robust "median-of-many" computation because the aggregation logic has no bound checking on individual inputs. The analogous defect in this repo is `PeerNetwork`'s `highest_stacks_neighbor` tracker: instead of aggregating multiple neighbors' claims into a robust statistic, the node simply keeps a running, unbounded `max()` over whatever Stacks tip height any single remote neighbor last reported. One malicious/compromised peer can set this value once to an arbitrarily large number and permanently dominate the field, since only a strictly-greater comparison is performed and there is no sanity bound relative to the node's own burnchain-derived expectations.

### Finding Description
`StacksNodeState::update_highest_stacks_neighbor` updates `PeerNetwork::highest_stacks_neighbor`, a field documented as "Address and height of the neighbor that reported the highest Stacks block height via RPC responses": [1](#0-0) 

The update logic performs only:
```
if new_height > current_height { network.highest_stacks_neighbor = Some((*new_address, new_height)); }
```
There is no upper bound derived from the local burnchain view, no requirement that multiple independent neighbors corroborate the value, and no decay/expiration of a previously-accepted extreme value. This mirrors the oracle bug's root cause: a single untrusted input can set (or in this case, permanently "win") an aggregate value because the aggregation function (`max` here, `median` there) is not robust against one adversarial input when there is no cross-checking of multiple sources.

The field is defined on `PeerNetwork`: [2](#0-1) 

and is exercised/verified in the test suite as the value surfaced by the node's own health reporting (`max_stacks_height_of_neighbors`), confirming it is populated purely from what a peer claims about itself over an RPC/handshake exchange and then served back out: [3](#0-2) 

Because `new_height` originates from an untrusted remote peer's self-reported chain-tip height and the update rule is a strict, unconditional `max`, a single hostile peer can set this value to `u64::MAX` (or any implausibly large number) in one interaction. From that point on, no legitimate peer can ever exceed it, so the field is poisoned indefinitely (until process restart), analogous to Eve permanently steering the "median" oracle price to an attacker-chosen value by exploiting the lack of bound-checking in the aggregation.

### Impact Explanation
This does not directly corrupt consensus-critical chain state or allow unauthorized writes to StackerDB/chain data, so it does not rise to "Critical." However, it does cause the node to durably serve non-canonical/false data (a fabricated "highest known neighbor height") as if it were a legitimate, corroborated network observation via the node's health/monitoring surface (`/v2/health`, `max_stacks_height_of_neighbors`) — this is an instance of "serving non-canonical state as canonical," which the rules classify as High impact. Operators or automation relying on this metric to detect whether their node is behind the network tip can be misled into believing they are perpetually far behind (or conversely masking real staleness, if the false huge value suppresses alerting logic based on a delta from height).

### Likelihood Explanation
Likelihood is high for triggering the poisoning itself: any remote peer that completes a handshake/RPC exchange with the node can supply a `new_height` value, and the code path applies no plausibility check against the local burnchain-derived height before accepting it. No authentication beyond ordinary peer conversation is required, and no special privilege, key, or signer role is needed — this satisfies the rule that only unprivileged, remote analogs are in scope.

### Recommendation
Bound-check incoming neighbor-reported heights against the node's own burnchain-derived expected range (e.g., reject or clamp values more than some small margin above the locally observed burn/Stacks tip), require corroboration from more than one independent neighbor before accepting a height as the new "highest," and/or apply decay/expiration so a stale or adversarial extreme value does not persist indefinitely. This mirrors the oracle report's long-term recommendation: don't let a single untrusted input control an aggregate that downstream consumers treat as ground truth.

### Proof of Concept
1. Run a Stacks node with the vulnerable build.
2. As a remote peer, complete a normal p2p handshake/RPC conversation with the target node.
3. In the RPC response/handshake data path that feeds `update_highest_stacks_neighbor` (`stackslib/src/net/rpc.rs`), report a Stacks tip height of `u64::MAX` (or any absurdly large but syntactically valid height).
4. Because the check is only `new_height > current_height`, `PeerNetwork::highest_stacks_neighbor` is immediately overwritten to `(attacker_addr, u64::MAX)`.
5. Query the node's `/v2/health` endpoint; observe `max_stacks_height_of_neighbors` permanently reflects the attacker-supplied value, and no subsequent honest peer (whose real height is far lower) can ever overwrite it.

    pub fn update_highest_stacks_neighbor(
        &mut self,
        new_address: &SocketAddr,
        new_height: Option<u64>,
    ) {
        self.with_node_state(|network, _, _, _, _| {
            if let Some(new_height) = new_height {
                let current_height = network
                    .highest_stacks_neighbor
                    .as_ref()
                    .map(|(_addr, height)| *height)
                    .unwrap_or(0);

                if new_height > current_height {
                    network.highest_stacks_neighbor = Some((*new_address, new_height));
                }
            }
        });
    }
