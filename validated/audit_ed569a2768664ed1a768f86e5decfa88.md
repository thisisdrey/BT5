### Title
`ReceivePack` (SSH and smarthttp) has no negotiation/idle timeout, allowing a client to hold the handler open indefinitely - ([File: internal/gitaly/service/ssh/receive_pack.go], [File: internal/gitaly/service/smarthttp/receive_pack.go])

### Summary
`sshReceivePack` and `postReceivePack` read the client's pktline stream directly via `stream.Recv()` and feed it to `git-receive-pack` without any request-scoped timeout ticker. Unlike `SSHUploadPackWithSidechannel` and `SSHUploadArchive`, which explicitly wrap their negotiation phase with `uploadPackRequestTimeoutTickerFactory` / `uploadArchiveRequestTimeoutTickerFactory` to bound waiting for client input, `ReceivePack` has no equivalent `receivePackRequestTimeoutTickerFactory`, so a client that never sends a flush packet and never closes the gRPC stream can keep the handler (and the spawned `git-receive-pack` process) blocked indefinitely.

### Finding Description
In `internal/gitaly/service/ssh/receive_pack.go`, `sshReceivePack` builds `stdin` from `streamio.NewReader` wrapping `stream.Recv()` [1](#0-0) , then spawns `git-receive-pack` with that pipe as stdin and calls `cmd.Wait()` [2](#0-1) . `cmd.Wait()` blocks until the process exits; `git-receive-pack` itself blocks reading its stdin until it sees a full command list terminated with a flush packet. If the attacker sends nothing further and never calls `CloseSend()`, `stream.Recv()` blocks forever, the `io.Copy(pw, stdin)` goroutine never reaches EOF, `git-receive-pack` never sees EOF/flush, and `cmd.Wait()` never returns.

The identical pattern exists in `internal/gitaly/service/smarthttp/receive_pack.go`'s `postReceivePack`, where `stdin` is again `stream.Recv()`-backed and fed straight to `git-receive-pack --stateless-rpc` with no timeout [3](#0-2) .

By contrast, `sshUploadPack` explicitly builds a `timeoutTicker := s.uploadPackRequestTimeoutTickerFactory()` and passes it into `runUploadCommand` specifically to "mitigate use-after-check attacks" where the negotiation never completes [4](#0-3) . The `server` struct carries `uploadPackRequestTimeoutTickerFactory` and `uploadArchiveRequestTimeoutTickerFactory` fields, each backed by `deps.Cfg.Timeout.UploadPackNegotiation` / `UploadArchiveNegotiation` config, but there is no analogous `receivePackRequestTimeoutTickerFactory` field or config value [5](#0-4) . Tests (`TestUploadPackWithSidechannel_timeout`, `TestFailedUploadArchiveRequestDueToTimeout`) explicitly assert that stalled negotiation streams for upload-pack/upload-archive are torn down via `context canceled` after the ticker fires [6](#0-5) [7](#0-6) ; no equivalent test or mechanism exists for `ReceivePack`.

The existing `TestReceivePack_client` "command without flush" test case only demonstrates that the handler correctly errors out when the client sends data and then closes the stream (`stream.CloseSend()`), which triggers EOF and lets `git-receive-pack` fail with "remote end hung up unexpectedly" [8](#0-7) . It does not cover the case where the client keeps the stream open without ever sending EOF or a flush — in that scenario there is nothing in the code that bounds the wait, since gRPC itself imposes no default idle deadline and the RPC context has no timeout applied by the handler.

### Impact Explanation
An unprivileged user who can push to a repository they own (or via fork/import flows that route through `ReceivePack`) can open a `SSHReceivePack` or `PostReceivePack` stream, send the initial `Repository`/`GlId` request, and then simply never send a flush packet and never close the stream. This holds a goroutine, a `git-receive-pack` subprocess, an `os.Pipe()`, and a transaction/vote slot open for as long as the attacker chooses (bounded only by TCP/gRPC connection liveness, not by any Gitaly-enforced timeout). Repeating this concurrently across many connections can exhaust worker goroutines, file descriptors, and process table slots, degrading or denying service to other users — matching the "DoS / resource exhaustion" bounty class.

### Likelihood Explanation
This is trivially reachable by any user capable of a `git push` (SSH or HTTP) to a repository they can write to, requiring no special role, secret, or non-default configuration — the SSH/smarthttp `ReceivePack` handlers are on the standard push code path. The attack is deterministic and repeatable: opening N such stalled streams ties up N handler instances indefinitely with no time-based recovery specific to receive-pack, unlike the already-mitigated upload-pack/upload-archive negotiation paths.

### Recommendation
Introduce a `receivePackRequestTimeoutTickerFactory` (backed by a new `Timeout.ReceivePackNegotiation` config value, analogous to `UploadPackNegotiation`/`UploadArchiveNegotiation`) and use it to bound the time the handler waits for the client to complete sending the command list/pack (e.g., wrap the read loop or apply a `context.WithTimeout`/ticker-driven cancellation similar to `runUploadCommand`'s timeout handling), ensuring an idle or incomplete `ReceivePack` stream is canceled and the subprocess killed after a bounded interval, in both the SSH (`sshReceivePack`) and smarthttp (`postReceivePack`) code paths.

### Proof of Concept
Extend `TestReceivePack_client` in `internal/gitaly/service/ssh/receive_pack_test.go` with a case that never sends a flush and never calls `stream.CloseSend()`:
```go
{
    desc: "stalled stream never completes",
    writeRequest: func(t *testing.T, stdin io.Writer) {
        // send nothing further; do not write flush, do not close stream
    },
},
```
Then, instead of calling `stream.CloseSend()`, leave the stream open and assert (with `require.Eventually`/a bounded `select` with a short test timeout) that the RPC returns within some deadline. Under current code, `cmd.Wait()` in `sshReceivePack` [9](#0-8)  never returns and the test would hang/timeout, demonstrating the unbounded block, whereas the equivalent `TestUploadPackWithSidechannel_timeout` test [6](#0-5)  shows the expected bounded behavior via `structerr.NewDeadlineExceeded`.

func testUploadPackWithSidechannelTimeout(t *testing.T, ctx context.Context, opts ...testcfg.Option) {
	t.Parallel()

	cfg := testcfg.Build(t, opts...)

	cfg.SocketPath = runSSHServerWithOptions(t, cfg, []ServerOpt{
		WithUploadPackRequestTimeoutTickerFactory(func() helper.Ticker {
			// Create a ticker that will immediately tick when getting reset so that the
			// server-side can observe this as an emulated timeout.
			ticker := helper.NewManualTicker()
			ticker.ResetFunc = func() {
				ticker.Tick()
			}
			return ticker
		}),
	})

	repo, repoPath := gittest.CreateRepository(t, testhelper.Context(t), cfg)
	gittest.WriteCommit(t, cfg, repoPath, gittest.WithBranch("main"))

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	registry := sidechannel.NewRegistry()
	client := newSSHClientWithSidechannel(t, ctx, registry, cfg.SocketPath)

	ctx, waiter := sidechannel.RegisterSidechannel(ctx, registry, func(clientConn *sidechannel.ClientConn) (returnedErr error) {
		// Discard all data and block on the connection closing. The client says nothing
		// back to the server and doesn't finish the negotiation. This leads to the server
		// closing the connections once the negotiation timeout fires.
		_, err := io.Copy(io.Discard, clientConn)
		assert.NoError(t, err)
		return nil
	})
	defer testhelper.MustClose(t, waiter)

	_, err := client.SSHUploadPackWithSidechannel(ctx, &gitalypb.SSHUploadPackWithSidechannelRequest{
		Repository: repo,
	})

	// Because the client says nothing, the server would block. Because of
	// the timeout, it won't block forever, and return with a non-zero exit
	// code instead.
	testhelper.RequireGrpcError(t, structerr.NewDeadlineExceeded("running upload-pack: waiting for negotiation: context canceled"), err)
}

func TestFailedUploadArchiveRequestDueToTimeout(t *testing.T) {
	t.Parallel()

	cfg := testcfg.Build(t)

	// Use a ticker channel so that we can observe that the ticker is being created. The channel
	// is unbuffered on purpose so that we can assert that it is getting created exactly at the
	// time we expect it to be.
	tickerCh := make(chan *helper.ManualTicker)

	cfg.SocketPath = runSSHServerWithOptions(t, cfg, []ServerOpt{
		WithArchiveRequestTimeoutTickerFactory(func() helper.Ticker {
			// Create a ticker that will immediately tick when getting reset so that the
			// server-side can observe this as an emulated timeout.
			ticker := helper.NewManualTicker()
			ticker.ResetFunc = func() {
				ticker.Tick()
			}
			tickerCh <- ticker
			return ticker
		}),
	})

	ctx := testhelper.Context(t)
	repo, _ := gittest.CreateRepository(t, ctx, cfg)

	client := newSSHClient(t, cfg.SocketPath)

	stream, err := client.SSHUploadArchive(ctx)
	require.NoError(t, err)

	// The first request is not limited by timeout, but also not under attacker control
	require.NoError(t, stream.Send(&gitalypb.SSHUploadArchiveRequest{Repository: repo}))

	// We should now see that the ticker limiting the request is being created. We don't need to
	// use the ticker, but this statement is only there in order to verify that the ticker is
	// indeed getting created at the expected point in time.
	<-tickerCh

	// Because the client says nothing, the server would block. Because of
	// the timeout, it won't block forever, and return with a non-zero exit
	// code instead.
	requireFailedSSHStream(t, structerr.NewDeadlineExceeded("running upload-archive: waiting for negotiation: context canceled"), func() (int32, error) {
		resp, err := stream.Recv()
		if err != nil {
			return 0, err
		}

		var code int32
		if status := resp.GetExitStatus(); status != nil {
			code = status.GetValue()
		}

		return code, nil
	})
}
