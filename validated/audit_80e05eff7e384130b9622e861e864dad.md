### Title
Protocol fees bypassed on Nep245/Imt token diffs by splitting an amount-A transfer into A unit-delta (|delta|==1) legs - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Finding Description
The binding that should hold is: for any signer settling a net negative delta of `A` on a `Nep245`/`Imt` token in a batch, `fees_collected[token] == Pips::fee_ceil(A, protocol_fee)`. Instead, `TokenDiff::token_fee` computes the fee **per intent, per token, using that single intent's own `|delta|`**, not the signer's aggregate negative delta across the batch: [1](#0-0) 

Because `TokenIdType::Nep245 | TokenIdType::Imt` returns `Pips::ZERO` whenever `amount <= 1`, a signer can take a legitimate `Nep245` transfer of amount `A` and represent it as `A` separate `TokenDiff` intents, each with `delta == -1` on the same `token_id` (each intent individually valid: `execute_intent` only rejects `delta == 0`, not duplicate tokens across intents): [2](#0-1) 

Each of the `A` legs computes `fee = Self::token_fee(token_id, 1, protocol_fee).fee_ceil(1) = Pips::ZERO.fee_ceil(1) = 0`, so `fees_collected` for that token accumulates to `0` across the whole batch, while a single equivalent `TokenDiff` with `delta == -A` (`A > 1`) would have charged `fee = Pips::fee_ceil(A) > 0` for `protocol_fee > 0`.

To actually settle value (not just mutate the signer's own balance), the batch needs counterparty legs of matching positive delta so `TransferMatcher::finalize` nets deltas to zero per token across the whole `MultiPayload` (`contracts/defuse/core/src/engine/state/deltas.rs`, `TransferMatcher::finalize`/`TokenTransferMatcher::finalize_into`) — an unprivileged attacker can supply these counterparty legs themselves, e.g. from a second account they control, also as unit legs (each leg individually pays no fee since `amount<=1` on the counterparty's positive-delta legs too, and fees are only taken from negative deltas anyway). None of `MultiPayload::verify`, nonce checks, `Lock`, or `TransferMatcher::finalize`'s invariant check inspect or block per-token fee granularity — they only ensure the *balance* deltas net to zero, not that the *fee* matches `Pips::fee_ceil` of the aggregate negative delta.

### Impact Explanation
The `fee_collector` account is under-credited: for a transfer of `A` units of a `Nep245`/`Imt` token, the protocol collects `0` fee instead of `Pips::fee_ceil(A, protocol_fee)`. This directly matches the enumerated Critical category "protocol fees bypassed." It is fully repeatable — for every `Nep245`/`Imt` token and any amount `A`, the attacker splits into `A` unit legs across any number of signed intents in one `MultiPayload`, at no additional cost beyond constructing/signing `A` small intents instead of one. It applies to any signer using `Nep245`/`Imt` tokens (multi-token / semi-fungible balances), which are not restricted to atomic (amount=1) semantics — they routinely represent divisible balances (e.g., LP shares, wrapped balances) greater than 1, so the "do not fee NFTs/MTs with `|delta| <= 1`" exemption (intended for atomic NFT-like transfers) is trivially circumvented for fungible-like MT balances by decomposing any transfer into unit legs.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: hold balance `A` of some `Nep245`/`Imt` token in Defuse, and have `protocol_fee (Pips) > 0` configured (a normal deployment setting, not attacker-controlled but a standard precondition). The attacker only needs to sign `A` (or fewer, batched with a counterparty account they also control) `TokenDiff` intents instead of one, and submit them together in a single `MultiPayload` to `execute_intents`. This requires no privileged role, no relayer key, and no counterpart's cooperation beyond controlling a second account of their own. It is trivially repeatable across all Nep245/Imt tokens and arbitrary amounts.

### Recommendation
Compute the fee based on the **signer's aggregate negative delta per token across the whole processed batch** (or at minimum across a signer's session/execution context), not on each individual intent's per-call `|delta|`. Alternatively, remove or tighten the `amount <= 1` fee exemption for `Nep245`/`Imt` so it only applies to intrinsically non-fungible/atomic token ids (e.g., check token semantics rather than the numeric amount of a single intent leg), or track a running per-signer, per-token negative-delta accumulator in `Engine`/`Deltas` state and charge `Pips::fee_ceil` on the accumulated total when finalizing the batch.

    // Finalizes all transfers, or returns unmatched deltas.
    // If unmatched deltas overflow, then Err(None) is returned.
    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)
                && (unmatched == 0 || deltas.apply_delta(token_id, unmatched).is_none())
            {
                return Err(InvariantViolated::Overflow);
            }
        }
        if !deltas.is_empty() {
            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }
        Ok(transfers)
    }
}
