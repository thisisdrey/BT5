### Title
receive_pack: no per-request idle/negotiation timeout enforced on the client-controlled stdin stream, allowing a stalled push to hold a `git receive-pack` process open indefinitely - (File: internal/gitaly/service/smarthttp/receive_pack.go)

### Summary
`PostReceivePack` reads client-supplied stdin data via `streamio.NewReader` and feeds it directly into `git receive-pack --stateless-rpc`, then blocks on `cmd.Wait()` with no application-level idle/negotiation timeout. Unlike `git-upload-pack`, which Gitaly explicitly protects with `pktline.ReadMonitor`/`uploadPackRequestTimeoutTickerFactory` to bound the negotiation phase, `receive-pack` has no equivalent mechanism in `internal/gitaly/service/smarthttp/receive_pack.go` or `internal/gitaly/service/ssh/receive_pack.go`.

### Finding Description
`postReceivePack` wires the gRPC stream directly to the stdin of a spawned `git receive-pack --stateless-rpc` process: `stdin := streamio.NewReader(...)`, passed via `gitcmd.WithStdin(stdin)`, and the handler then calls `cmd.Wait()` [1](#0-0) . If the client never sends a flush-pkt or does not close/finish the pack negotiation (i.e., "a stream that never sends flush"), `git receive-pack` blocks on its own stdin read and `cmd.Wait()` in Gitaly blocks correspondingly, with no context deadline or ticker bounding this wait.

Gitaly does have exactly this kind of protection for `upload-pack`: `internal/git/pktline/read_monitor.go` implements `ReadMonitor.Monitor`, explicitly documented as mitigating "a class of 'use-after-check' security issue" where "the user has control of stdin for the git command, and if they can delay input for an arbitrarily long time, they can gain access days or weeks after the access check has completed" [2](#0-1) . This is wired into `internal/gitaly/service/ssh/upload_pack.go`, which calls `s.runUploadCommand(ctx, ..., timeoutTicker, pktline.PktDone(), ...)` specifically to bound the negotiation phase and there is a dedicated test, `TestUploadPackWithSidechannel_timeout`, verifying that a stalled negotiation is aborted with `DeadlineExceeded` [3](#0-2) [4](#0-3) .

No equivalent `ReadMonitor`/timeout-ticker exists for `receive-pack` in either the smarthttp (`internal/gitaly/service/smarthttp/receive_pack.go`) or SSH (`internal/gitaly/service/ssh/receive_pack.go`) implementations. The SSH variant does address a *different* problem — preventing `cmd.Wait()` from hanging when the underlying git process crashes before stdin reaches EOF, via an explicit `os.Pipe()` and goroutine [5](#0-4)  — but this only protects against the process dying early; it does not bound how long a client may withhold input from a live, waiting `git receive-pack` process.

The only broader protections that exist are: gRPC keepalive settings (`grpc.KeepaliveParams{Time: 5*time.Minute}` with `EnforcementPolicy{MinTime: 10s}`) which detect dead TCP connections, not idle-but-alive application streams [6](#0-5) ; and the `[[concurrency]]` queueing limiter (`max_queue_wait`, `max_queue_size`), which only bounds time spent *waiting to enter* an RPC handler, not time spent *inside* an already-admitted, in-progress handler [7](#0-6) . Neither mechanism time-bounds an already-admitted `PostReceivePack`/`SSHReceivePack` stream that is stalled waiting on client input.

### Impact Explanation
An attacker who can push to a repository they own can open a `PostReceivePack`/`SSHReceivePack` stream, send the initial repository/GlId message, then stall — never completing the pack transfer or sending a flush packet. This holds open a live `git receive-pack` subprocess, an associated file descriptor/pipe, and a Gitaly gRPC handler goroutine for an unbounded duration (bounded in practice only by the 5-minute gRPC keepalive ping interval and TCP-level liveness, not by an idle-input timeout). By repeating this with multiple concurrent connections, an attacker can accumulate many stalled `git receive-pack` processes and open handlers, consuming process table slots, memory, and file descriptors on the Gitaly node — a resource-exhaustion DoS vector matching the "DoS / resource exhaustion" GitLab bounty impact class, and consistent with the deliberate `ReadMonitor` mitigation that was applied to `upload-pack` for the same class of concern but is missing for `receive-pack`.

### Likelihood Explanation
This requires only push access to a repository the attacker controls (fork/own project), no special role, and is trivially reproducible: send the first `PostReceivePackRequest`/`SSHReceivePackRequest` and then simply stop sending `Data`/`Stdin` frames without closing the stream. No malformed pack or crafted pktline content is even necessary — a client that is merely slow/silent is sufficient, since there's no dedicated code path in `receive_pack.go` distinguishing "slow legitimate client" from "attacker holding a handler open." Concurrency-limit configuration (`[[concurrency]] rpc = ".../PostReceivePack"`) can mitigate impact if an operator has configured `max_per_repo`/`max_queue_size`/`max_queue_wait`, but this is non-default configuration; by default there's no limit on `PostReceivePack`/`SSHReceivePack`, and even with limits configured, they bound queuing time, not the already-admitted handler's stall time.

### Recommendation
Add negotiation/idle-input timeout protection to `postReceivePack` (`internal/gitaly/service/smarthttp/receive_pack.go`) and `sshReceivePack` (`internal/gitaly/service/ssh/receive_pack.go`) analogous to what `upload-pack` already has via `pktline.ReadMonitor`/`uploadPackRequestTimeoutTickerFactory`: wrap the client-supplied stdin reader with a monitor that watches for a terminal pktline (e.g., the flush packet indicating end of ref-update commands) within a bounded time, and cancel the command's context (thereby killing the `git receive-pack` subprocess and unblocking `cmd.Wait()`) if the timeout elapses. This should be configurable similarly to the existing upload-pack negotiation timeout and should be applied by default.

```go
		WithUploadPackRequestTimeoutTickerFactory(func() helper.Ticker {

			ticker := helper.NewManualTicker()

				ticker.Tick()
			}
			return ticker
		}),
	})

	repo, repoPath := gittest.CreateRepository(t, testhelper.Context(t), cfg)
	gittest.WriteCommit(t, cfg, repoPath, gittest.WithBranch("main"))

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	registry := sidechannel.NewRegistry()
	client := newSSHClientWithSidechannel(t, ctx, registry, cfg.SocketPath)

	ctx, waiter := sidechannel.RegisterSidechannel(ctx, registry, func(clientConn *sidechannel.ClientConn) (returnedErr error) {
		// Discard all data and block on the connection closing. The client says nothing
		// back to the server and doesn't finish the negotiation. This leads to the server
		// closing the connections once the negotiation timeout fires.
		_, err := io.Copy(io.Discard, clientConn)
		assert.NoError(t, err)
		return nil
	})
	defer testhelper.MustClose(t, waiter)

	_, err := client.SSHUploadPackWithSidechannel(ctx, &gitalypb.SSHUploadPackWithSidechannelRequest{
		Repository: repo,
	})

	// Because the client says nothing, the server would block. Because of
	// the timeout, it won't block forever, and return with a non-zero exit
	// code instead.
	testhelper.RequireGrpcError(t, structerr.NewDeadlineExceeded("running upload-pack: waiting for negotiation: context canceled"), err)
```

```go
// acquire tries to acquire the semaphore. It may fail if the admission queue is full or if the max
// queue-time ticker ticks before acquiring a concurrency token.
func (sem *keyedConcurrencyLimiter) acquire(ctx context.Context, limitingKey string) (returnedErr error) {
	if sem.queueTokens != nil {
		// Try to acquire the queueing token. The queueing token is used to control how many
		// callers may wait for the concurrency token at the same time. If there are no more
		// queueing tokens then this indicates that the queue is full and we thus return an
		// error immediately.
		if err := sem.queueTokens.TryAcquire(); err != nil {
			return err
		}
		// We have acquired a queueing token, so we need to release it if acquiring
		// the concurrency token fails. If we succeed to acquire the concurrency
		// token though then we retain the queueing token until the caller signals
		// that the concurrency-limited function has finished. As a consequence the
		// queue token is returned together with the concurrency token.
		//
		// A simpler model would be to just have `maxQueueLength` many queueing
		// tokens. But this would add concurrency-limiting when acquiring the queue
		// token itself, which is not what we want to do. Instead, we want to admit
		// as many callers into the queue as the queue length permits plus the
		// number of available concurrency tokens allows.
		defer func() {
			if returnedErr != nil {
				sem.queueTokens.Release()
			}
		}()
	}

	// We are queued now, so let's tell the monitor. Furthermore, even though we're still
	// holding the queueing token when this function exits successfully we also tell the monitor
	// that we have exited the queue. It is only an implementation detail anyway that we hold on
	// to the token, so the monitor shouldn't care about that.
	sem.monitor.Queued(ctx, limitingKey, sem.queueLength())
	defer sem.monitor.Dequeued(ctx)

	if sem.maxQueueWait != 0 {
		if sem.setWaitTimeoutContext != nil {
			ctx = sem.setWaitTimeoutContext()
		} else {
			var cancel context.CancelFunc
			ctx, cancel = context.WithTimeout(ctx, sem.maxQueueWait)
			defer cancel()
		}
	}

	// Try to acquire the concurrency token now that we're in the queue.
	return sem.concurrencyTokens.Acquire(ctx)
}
```
