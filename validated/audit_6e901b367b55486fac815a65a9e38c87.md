### Title
Shielded Transaction Spending/Viewing Keys Accepted via HTTP GET Query Strings - ([File: framework/src/main/java/org/tron/core/services/http/GetExpandedSpendingKeyServlet.java])

### Summary
Multiple full-node HTTP wallet endpoints for the shielded (Sapling) transaction API accept the equivalent of usernames/passwords for this CVE class — full spending keys, sub-keys, and viewing keys — as unencrypted `GET` query-string parameters, in addition to supporting `POST`. This is the exact bug class described in GHSA-gcvm-c75m-h4p4 (CWE-598, GET with sensitive query strings), but arguably more severe because the exposed secrets are cryptographic key material rather than a login credential.

### Finding Description
Several servlets registered in `FullNodeHttpApiService` implement `doGet` handlers that read highly sensitive shielded-key material straight out of `request.getParameter(...)`:

- `GetExpandedSpendingKeyServlet.doGet` reads the full raw spending key (`sk`) from the `value` query parameter and returns the expanded spending key (`ask`, `nsk`, `ovk`): [1](#0-0) 

- `GetAkFromAskServlet.doGet` reads the spend-authorizing key (`ask`) from the `value` query parameter: [2](#0-1) 

- `GetNkFromNskServlet.doGet` reads the nullifier-deriving key (`nsk`) from the `value` query parameter: [3](#0-2) 

- `ScanNoteByOvkServlet.doGet` (and its Solidity/PBFT-fronting counterparts `ScanNoteByOvkOnSolidityServlet`, `ScanNoteByOvkOnPBFTServlet`) reads the outgoing viewing key (`ovk`) from the `ovk` query parameter: [4](#0-3) 

- `ScanShieldedTRC20NotesByOvkServlet.doGet` likewise reads `ovk` from the query string for TRC20 shielded note scanning: [5](#0-4) 

- `GetZenPaymentAddressServlet.doGet` reads the incoming viewing key (`ivk`) from the query string: [6](#0-5) 

The shared servlet dispatch in `RateLimiterServlet.service` does not distinguish "sensitive" GET requests for special handling (no redaction, no forced-POST enforcement) — it merely routes to `doGet`/`doPost` uniformly: [7](#0-6) 

All of these servlets are wired into the standard, unauthenticated Full Node HTTP API surface via `FullNodeHttpApiService`, which any anonymous API client with network access to the node's HTTP port can reach: [8](#0-7) 

Because these are `GET` requests, the full URL — including the raw spending key, `ask`, `nsk`, or `ovk` — is exposed through the same channels the OpenMeetings advisory warns about: web server/proxy access logs, browser history, `Referer` headers sent to third parties when the API is fronted by a browser-based tool, and any intermediary caches or CDNs sitting between the client and node.

### Impact Explanation
Unlike the original OpenMeetings finding (username/password), the equivalent secrets here are cryptographic keys that directly gate shielded-pool fund custody and privacy:
- Disclosure of a raw spending key (`sk`, via `GetExpandedSpendingKeyServlet`) or its `ask`/`nsk` components gives an attacker full spend authority and nullifier-derivation capability over the corresponding shielded funds, enabling theft.
- Disclosure of an `ovk` or `ivk` lets an attacker decrypt outgoing/incoming shielded notes, defeating the privacy guarantee of the shielded pool for that account (a confidentiality break analogous in class to CVE-2026-34020's `C:H` impact).

This satisfies the "Validate" bar for concrete impact: key disclosure and potential theft of shielded funds, not merely a low-severity/no-impact finding.

### Likelihood Explanation
Exploitation requires no special privilege — any client capable of issuing an HTTP GET to the node's wallet API (or any operator/tool that logs URLs, or any reverse proxy/CDN in front of the API) can capture these secrets. Because wallet client tooling built against this API (e.g., `WalletClient` test utilities show interactive password/key handling patterns) may plausibly use the GET variants for convenience, and because these endpoints exist specifically as GET alternatives to the POST-based equivalents, sensitive key material is likely to appear in access logs in real deployments that expose these endpoints (e.g., third-party wallet backends or SDKs built on the full-node HTTP API).

### Recommendation
- Remove or disable the `doGet` handlers for all endpoints that take spending keys, `ask`, `nsk`, `ovk`, or `ivk` as input (`GetExpandedSpendingKeyServlet`, `GetAkFromAskServlet`, `GetNkFromNskServlet`, `ScanNoteByOvkServlet`/`ScanNoteByOvkOnSolidityServlet`/`ScanNoteByOvkOnPBFTServlet`, `ScanShieldedTRC20NotesByOvkServlet`, `GetZenPaymentAddressServlet`), forcing clients to use `POST` with a request body.
- If GET support must remain for backward compatibility, reject GET requests that include these sensitive parameters (return `405`/`400`), matching the fix pattern the advisory describes for OpenMeetings' login endpoint.
- Audit all shielded-key HTTP endpoints for the same pattern (any handler that reads `ask`, `nsk`, `ovk`, `ivk`, `sk`, or `value` meant to hold key material from `request.getParameter`) and apply the same POST-only restriction.
- Add documentation/config guidance that these endpoints must not be exposed behind logging proxies/CDNs, and consider disabling them entirely by default on public-facing full nodes.

### Proof of Concept
Against a full node with the HTTP API enabled on the default port, an attacker who can observe access logs, `Referer` headers, or browser history (e.g., via a shared/reverse proxy, or a wallet web UI built on this API) captures a request such as:
```
GET /wallet/getexpandedspendingkey?value=<raw_spending_key_hex> HTTP/1.1
Host: node:8090
```
The raw spending key is now present in plaintext in any log or history retaining that URL, from which the attacker can derive `ask`/`nsk`/`ovk` and gain spend authority over the associated shielded funds — mirroring the exact CWE-598 exposure pattern from GHSA-gcvm-c75m-h4p4, applied here to cryptographic secrets instead of a login password.
