### Title
Attached deposit stranded on `Error::User` early-return in `inner_rlp_execute` - ([File: internal.rs](runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs))

### Summary
`inner_rlp_execute` computes `caller_deposit` from the attached deposit before parsing the RLP transaction, but on the `Err(err @ Error::User(_))` branch it only increments the nonce and returns the error without ever creating a refund promise for `caller_deposit`. Since the caller's attached deposit is transferred into the wallet contract's account balance as part of NEAR's normal function-call-action processing (the wasm call itself does not panic — it returns `Ok`/`ExecuteResponse{success:false,...}` normally), the deposit is never returned and is permanently retained by the wallet contract.

### Finding Description
In `WalletContract::rlp_execute` (`lib.rs`), `inner_rlp_execute` is called with `env::attached_deposit()` already captured in the `ExecutionContext`, and `CallerDeposit::new(&context)` is computed immediately afterward: [1](#0-0) . `CallerDeposit::new` only returns `Some` when `predecessor_account_id != current_account_id` and `attached_deposit > 0` [2](#0-1) .

The result of `parse_rlp_tx_to_action` is then matched. When `parse_tx_data`'s `FUNCTION_CALL_SELECTOR` or `TRANSFER_SELECTOR` branches detect `yocto_near >= MAX_YOCTO_NEAR`, they return `Error::User(UserError::ExcessYoctoNear)` [3](#0-2) [4](#0-3) . Back in `inner_rlp_execute`, this is caught by the `Err(err @ Error::User(_))` arm, which only bumps the nonce and returns the error — `caller_deposit` is silently dropped without creating any transfer/refund promise: [5](#0-4) .

Back in `rlp_execute`, any `Err(e)` that is not a `Relayer` error banned condition simply converts to `PromiseOrValue::Value(e.into())` [6](#0-5)  — i.e., the wasm call returns normally (no panic, no scheduled promise transferring funds back). Because the call does not panic, NEAR's automatic deposit-refund-on-panic mechanism does not trigger, and the attached deposit — already credited to the wallet contract account as part of the FunctionCall action's deposit — remains in the contract permanently.

This is in clear contrast to the intended, correct handling in `rlp_execute_callback`, which refunds `caller_deposit` explicitly whenever the downstream cross-contract promise fails: [7](#0-6) . The existing regression test `test_caller_refunds` only exercises the promise-failure refund path (`rlp_execute_callback`), not the early `Error::User` return path in `inner_rlp_execute` [8](#0-7) , so this gap is untested.

### Impact Explanation
Permanent freezing/loss of user funds: any external, unprivileged caller who attaches a non-zero deposit to `rlp_execute` while supplying an Ethereum-encoded transaction with `yocto_near >= MAX_YOCTO_NEAR` (1,000,000) in a `FUNCTION_CALL_SELECTOR`/`TRANSFER_SELECTOR` payload will have their attached deposit stuck in the target wallet-contract account with no promise ever created to return it. This matches the NEAR bounty "permanent freezing of funds" category, scoped to whatever deposit the attacker/relayer chooses to attach on a single call.

### Likelihood Explanation
- Preconditions are trivial to satisfy for any unprivileged caller: relay a `rlp_execute` call to any deployed wallet-contract (eth-implicit) account, from a different `predecessor_account_id`, with `attached_deposit > 0`.
- Crafting `yocto_near >= MAX_YOCTO_NEAR` in the ABI-encoded action just requires setting that ABI field; no special signing rights beyond a valid signature for the wallet's private key over the RLP payload are needed to trigger this error (the check happens after RLP parsing/signature validation, on the decoded action field).
- Fully repeatable — deterministic, no race conditions or network-timing dependence, single transaction.
- Cost to attacker: only the deposit they choose to attach and gas fees; the "attacker" loses their own deposit, but this could also be exploited/observed as a griefing vector against a relayer that attaches deposit on behalf of a user, or accidentally lost by a legitimate but not attentive external caller/relayer.

### Recommendation
In the `Err(err @ Error::User(_))` arm of `inner_rlp_execute` (and similarly for other early `Err` returns that occur after `caller_deposit` is computed), create a refund promise back to `caller_deposit.account_id` for `caller_deposit.yocto_near` before returning the error, mirroring the refund logic already implemented in `rlp_execute_callback`. Alternatively, restructure so `CallerDeposit::new` is computed only once parsing has succeeded, and centralize refund creation so every `Error::User`/early-return path is required to route through a helper that always issues the refund when `caller_deposit.is_some()`.

### Proof of Concept
Integration test (extending `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/user_error.rs` style, using the `sanity.rs` `rlp_execute_from` helper with non-zero `deposit_amount`):
1. Build a `TRANSFER_SELECTOR` (or `FUNCTION_CALL_SELECTOR`) Ethereum transaction with the ABI-encoded `yocto_near` field set to `MAX_YOCTO_NEAR` (1_000_000), targeting a valid `receiver_id`.
2. Call `wallet_contract.rlp_execute_from(&caller, target, &signed_tx, deposit_amount)` with `deposit_amount = NearToken::from_near(3)` from an account distinct from the wallet contract (`predecessor != current_account_id`).
3. Assert `result.error == Some(Error::User(UserError::ExcessYoctoNear).to_string())` and `result.success == false`.
4. Assert the caller's balance decreased by approximately `deposit_amount` (no refund), and the wallet contract's balance increased correspondingly — i.e., `post_tx_caller_balance` is not restored, unlike in `test_caller_refunds`'s first case where a promise failure triggers a refund via `rlp_execute_callback`.
5. Expected (buggy) result: deposit is retained by the wallet contract permanently; a fixed implementation should instead schedule a refund promise and restore the caller's balance (minus gas costs), matching the behavior already asserted for the promise-failure path in `test_caller_refunds` [9](#0-8) .

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
