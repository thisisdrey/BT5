### Title
Unbounded Witness Registration Enables Denial-of-Service via O(n) Maintenance-Cycle Loops - ([File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java])

### Summary
`WitnessCreateActuator` lets any account register as a witness with no protocol-enforced cap on the total number of witnesses. `MaintenanceManager.doMaintenance()` — invoked from every block that crosses a maintenance boundary — repeatedly iterates the *entire* `WitnessStore` (via `consensusDelegate.getAllWitnesses()`), and `WitnessStore.getWitnessStandby()` additionally performs an `O(n log n)` sort over all witnesses. As the witness set grows without bound, these operations grow linearly (or worse) with attacker-controlled input, mirroring the reported `_approvedBorrowers`-style DoS: an unbounded, externally-growable collection that is walked inside a critical, frequently-invoked code path.

### Finding Description
`WitnessCreateActuator.validate()`/`.execute()` only checks:
- the address is valid,
- the address is not already a witness,
- the account balance covers `getAccountUpgradeCost()` (a fixed dynamic-property fee). [1](#0-0) 

There is no maximum-witness-count check anywhere in this actuator, unlike other list-growing operations in the codebase that are explicitly capped (e.g. `MAX_VOTE_NUMBER` in `VoteWitnessProcessor.validate` [2](#0-1) , or the `UNFREEZE_MAX_TIMES` cap in `UnfreezeBalanceV2Processor.validate` [3](#0-2) ). This means the `WitnessStore` collection (keyed by unique account address) can be grown arbitrarily by any sufficiently-funded broadcaster simply by repeating `WitnessCreateContract` transactions from different owned addresses.

That unbounded store is then walked multiple times per maintenance cycle inside `MaintenanceManager.doMaintenance()`, which is called from `applyBlock()` — i.e., directly from block application in the consensus/Manager flow: [4](#0-3) 

Inside `doMaintenance()`, `consensusDelegate.getAllWitnesses()` (a full DB scan producing a `List<WitnessCapsule>` of every registered witness) is invoked up to three separate times per cycle: [5](#0-4) 

`WitnessStore.getAllWitnesses()` itself streams the whole underlying store: [6](#0-5) , and `getWitnessStandby()`/`sortWitnesses()` sorts the complete witness list on every call: [7](#0-6) .

### Impact Explanation
Because the maintenance cycle executes as part of ordinary block application (every witness registered performs get/put operations against `WitnessStore`/`AccountStore`, and the maintenance sweep processes the full store on a fixed schedule regardless of how many entries exist), an attacker who funds enough addresses to pay the fixed `AccountUpgradeCost` per witness can inflate the witness set to a size that makes each maintenance cycle (and any full-store sort/iteration triggered from it) prohibitively slow. Because this code runs synchronously inside block application, a sufficiently bloated witness set can stall block production/maintenance processing across the network — a chain-wide halt/DoS rather than a localized failure, which meets the "node crash or halt" bar for impact.

### Likelihood Explanation
The registration path (`WitnessCreateContract`) is reachable by any unprivileged, signed transaction from a funded account — no special permission is required beyond paying the fixed upgrade fee. The only friction is economic cost per witness (a fixed TRX amount), not a hard protocol limit, so a well-funded attacker (or a coordinated set of low-cost throwaway addresses if the fee is ever lowered by governance, or amortized via flash capital) can grow the store over time. This is a realistic, if capital-intensive, griefing vector rather than a trivial free attack, which is why it is assessed as Medium rather than High/Critical.

### Recommendation
Add an explicit maximum-witness-count check in `WitnessCreateActuator.validate()` (analogous to `MAX_VOTE_NUMBER` / `UNFREEZE_MAX_TIMES`), rejecting new `WitnessCreateContract` transactions once `witnessStore` size reaches a governance-configurable ceiling. Additionally, consider caching/memoizing `getAllWitnesses()` results within a single maintenance cycle instead of re-querying the full store multiple times, and avoid re-sorting the complete witness list on every `getWitnessStandby()` call if it can be avoided.

### Proof of Concept
1. Fund N distinct addresses, each with `≥ AccountUpgradeCost` TRX (the current default upgrade cost, e.g. 9999 TRX, defines the per-witness cost).
2. From each address, broadcast a `WitnessCreateContract` transaction; `WitnessCreateActuator.validate()`/`execute()` accepts it unconditionally (no cap check) as long as the balance and address-uniqueness checks pass — see `actuator/src/main/java/org/tron/core/actuator/WitnessCreateActuator.java` lines 98–106.
3. Repeat until `WitnessStore` contains a very large number of entries.
4. Observe that each subsequent maintenance cycle (`MaintenanceManager.doMaintenance()`, called from `applyBlock()`) takes proportionally longer due to repeated full-store iterations (`consensusDelegate.getAllWitnesses()`) and sort operations (`WitnessStore.sortWitnesses`), degrading block-application throughput network-wide.

        //pbft sr msg
        pbftManager.srPrePrepare(blockCapsule, currentWitness,

    //pbft block msg
    if (blockNum == 1) {
      nextMaintenanceTime = consensusDelegate.getNextMaintenanceTime();
    }

  public List<WitnessCapsule> getWitnessStandby(boolean isSortOpt) {
    List<WitnessCapsule> ret;
    List<WitnessCapsule> all = getAllWitnesses();
    sortWitnesses(all, isSortOpt);
    if (all.size() > Parameter.ChainConstant.WITNESS_STANDBY_LENGTH) {
      ret = new ArrayList<>(all.subList(0, Parameter.ChainConstant.WITNESS_STANDBY_LENGTH));
    } else {
      ret = new ArrayList<>(all);
    }
    // trim voteCount = 0
    ret.removeIf(w -> w.getVoteCount() < 1);
    return ret;
  }

  public static void sortWitnesses(List<WitnessCapsule> witnesses, boolean isSortOpt) {
    witnesses.sort(Comparator.comparingLong(WitnessCapsule::getVoteCount).reversed()
        .thenComparing(isSortOpt
            ? Comparator.comparing(WitnessCapsule::createReadableString).reversed()
            : Comparator.comparingInt((WitnessCapsule w) -> w.getAddress().hashCode()).reversed()));
  }
