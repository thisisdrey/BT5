### Title
Self-destined tun packets bypass firewall via `immediatelyForwardToSelf` path - ([File: inside.go])

### Summary
On BSD-family builds (darwin, dragonfly, freebsd, netbsd, openbsd), `consumeInsidePacket` detects packets whose destination is one of the node's own VPN addresses and writes them straight to `f.readers[q]` (the `Device.Write`/`UserDevice.Write` path) without ever calling `f.firewall.Drop`. Every other outbound/inbound packet path calls `Firewall.Drop` before reaching the tun write, but this self-to-self shortcut does not.

### Finding Description
`consumeInsidePacket` in `inside.go` first checks whether the packet's destination matches an address the node itself owns: [1](#0-0) 
When `f.myVpnAddrsTable.Contains(fwPacket.RemoteAddr)` is true and the build-time constant `immediatelyForwardToSelf` is `true` (set for darwin/dragonfly/freebsd/netbsd/openbsd in `inside_bsd.go`), the packet is written directly to `f.readers[q].Write(packet)` — which for a `UserDevice` calls `UserDevice.Write` at `overlay/user.go:64` — and the function returns immediately, never reaching the `f.firewall.Drop(...)` call that gates every other packet at line 74 of the same file. [2](#0-1) [3](#0-2) 
By contrast, the normal outbound path performs the firewall check before any write: `dropReason := f.firewall.Drop(*fwPacket, false, hostinfo, ...)` and only calls `f.sendNoMetrics(...)` (not a tun write) on success, or `rejectInside` on failure. [4](#0-3) 
The comment states this branch exists because, on Darwin-based/FreeBSD hosts, the OS itself routes self-to-self VPN traffic through the tun device rather than loopback, so Nebula must simulate that. However, this simulated forwarding is unconditional on packet content — it does not apply the outbound firewall ruleset the way the "normal" data path does, so an attacker-crafted inner packet destined at the node's own VPN address will be written to the tun device even if the firewall's outbound rules would otherwise deny it. Since the `overlay.UserDevice` type is available on all platforms (used by user-space netstack integrations like `service/service.go`) but only invoked in this bypass path when `immediatelyForwardToSelf` is true (BSD-only build tags), the concrete exploitability is limited to those OS builds; on generic builds the constant is `false` and packets simply drop at that branch.

### Impact Explanation
On the affected platforms, any application on the local host capable of sending packets into the outbound side of the tun device (this is the "attacker-authored inner packet reaching the tun write path" scenario named in the question) can craft an inner IP packet destined at its own Nebula address; that packet is looped back into the tun device without any firewall evaluation. This is a firewall bypass matching the "Firewall bypass injecting attacker packets directly into the host's network stack" impact category, because packets that the configured `firewall.outbound`/`firewall.inbound` rules would deny are still delivered onto the tun interface and into the host's network stack.

### Likelihood Explanation
This requires no CA certificate, no host/root privileges, and no configuration control — only the ability to send a packet on the local outbound path whose destination equals one of the node's own VPN addresses, and running on darwin/dragonfly/freebsd/netbsd/openbsd where `immediatelyForwardToSelf` is `true`. This is a fully local (non-network) condition that is deterministic and repeatable every time such a self-destined packet is emitted.

### Recommendation
Route self-destined packets through the same `f.firewall.Drop` evaluation used for all other outbound traffic before writing to `f.readers[q]` in the `immediatelyForwardToSelf` branch of `consumeInsidePacket` in `inside.go`, so the firewall invariant holds uniformly regardless of destination.

### Proof of Concept
Integration test plan (Go, in the `nebula` package, exercising `Interface.consumeInsidePacket` directly, forcing `immediatelyForwardToSelf = true` via build tag or test-only override):
1. Construct an `Interface` with a deny-all outbound firewall rule set (or simply no matching outbound rule) and a `UserDevice`/reader that records what is written.
2. Craft an inner IP packet whose destination address equals the node's own configured VPN address (found via `f.myVpnAddrsTable`).
3. Call `f.consumeInsidePacket(packet, ...)`.
4. Assert that `f.firewall.Drop` was never invoked (e.g., via a mock/counter) and that the packet nonetheless appears on `f.readers[q]` (i.e., is written to the tun device), demonstrating the bypass. A correct fix should make the write occur only after a `Drop` call returns `nil`, or the reader should record no write for a packet that the configured rules would deny.
