Based on my investigation, I found a strong analog in Bazel's own native ZIP-parsing code.

### Title
Out-of-bounds read when parsing central directory "extra field" records in ijar's zip reader - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar` (`third_party/ijar/zip.cc`) is Bazel's native tool for stripping/creating interface jars, and it parses ZIP central-directory records directly from an mmap'd, attacker-influenced `.jar`/`.zip` file. Unlike `InputZipFile::ProcessLocalFileEntry`, which calls `EnsureRemaining()` before consuming length-prefixed fields [1](#0-0) , the central-directory "extra field" walker in `InputZipFile::ProcessCentralDirEntry` has no such bound check.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` straight out of attacker-controlled bytes, then walks the extra-field region with a raw `while (extra_p != p)` loop: [2](#0-1) 

Inside that loop, `header_id` and `data_size` are read via `get_u2le` (advancing the cursor by 4 bytes) and then `extra_p += data_size;` with **no check that `data_size` doesn't overrun the `extra_field_length` region, let alone the mmap'd file itself**. If `data_size` is crafted so that `extra_p` jumps past `p` without ever landing exactly on it, the loop condition `extra_p != p` never becomes false, and the code keeps calling `get_u2le`/`get_u8le` past the end of the extra-field buffer — and potentially past the end of the entire mapped file — which is a classic length-prefixed-field out-of-bounds read, structurally identical to the LibRaw `get_huffman_diff()` bug class (reading a size field and then indexing/advancing without validating it against the buffer's real bounds).

By contrast, every other length-prefixed read in this file (`ProcessLocalFileEntry`, `SkipFile`) is guarded by `EnsureRemaining()` [3](#0-2) , confirming this is a missing check specific to the central-directory extra-field parser.

### Impact Explanation
`ijar` runs as part of normal Bazel Java/Android builds on `.jar` files that can originate from external dependencies fetched via `http_jar`/`http_archive`/Bzlmod registries. A hostile origin server can publish a jar whose bytes are known to the attacker (so the declared `sha256`/`integrity` matches, i.e., the checksum does not stop this — it only pins to attacker-chosen bytes) but which contains a malformed ZIP central directory extra field. When Bazel's `ijar` binary processes it, this triggers an out-of-bounds read (crash / potential info leak from adjacent memory) in a native binary that runs during the build, with attacker-controlled archive bytes as the only input needed.

### Likelihood Explanation
Moderate. It requires only that a dependency the build already downloads and passes to `ijar` (interface-jar generation for `java_library`) be attacker-controlled at the byte level — exactly the "hostile origin server/mirror serving content a victim's build consumes" scenario the prompt permits, since the checksum only certifies "this is the byte-for-byte file the attacker published," not that it is well-formed.

### Recommendation
Add a bound check in the `ProcessCentralDirEntry` extra-field loop analogous to `EnsureRemaining()`: validate that `extra_p + 4 + data_size <= p` (the previously-computed end of the extra field region) before dereferencing `header_id`/`data_size`, and bail out with an error rather than continuing the loop if the check fails. Also bound-check `file_name_length`, `extra_field_length`, and `file_comment_length` against the file's actual remaining length before advancing `p` by them, mirroring `EnsureRemaining()` usage elsewhere in the file.

### Proof of Concept
A `BuildIntegrationTestCase`/native fuzz-style unit test can construct a minimal ZIP file with one central directory entry whose `extra_field_length` is small (e.g., 4) but whose embedded `data_size` field (the second `u2` inside the extra field) is set to a large value (e.g., `0xFFFF`), causing `extra_p` to jump past the legitimate `extra_field_length` boundary. Feeding this file to `ZipExtractor::ProcessAll()` (as `zip_main.cc`'s unzip tool does) demonstrates reads continuing past the intended extra-field region; running under AddressSanitizer over the mmap'd file shows a heap/mmap out-of-bounds read once the loop walks past the actual central directory bytes.   // Check that at least n bytes remain in the input file, otherwise
  // abort with an error message.  "state" is the name of the field
  // we're about to read, for diagnostics.
  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
  }

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
