Audit Report

## Title
Unbounded, XCM‑controlled `gas` on `Command::CallContract` breaks the fixed‑gas invariant enforced for every other Snowbridge V2 outbound command - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs`)

## Summary
`ConstantGasMeter::maximum_dispatch_gas_used_at_most` returns a fixed, protocol-defined gas constant for every `Command` variant except `Command::CallContract`, for which it returns the caller-supplied `gas` field unmodified. [1](#0-0)  This `gas` value originates directly from an XCM `Transact` instruction decoded via `ContractCall::decode_all` with no bound check, and is pushed straight into `Command::CallContract` by `XcmConverter::convert`. [2](#0-1) 

## Finding Description
The `Command::CallContract` variant carries an attacker-controlled `gas: u64` field. [3](#0-2)  It is constructed in `XcmConverter::convert` directly from a decoded `Transact` instruction (`ContractCall::V1 { target, calldata, gas, value }`) without any cap or validation against the fee paid. [2](#0-1)  The fee is extracted independently in `extract_remote_fee`, which only checks that the fee asset is Ether held at `Here` and that the withdrawn amount covers the `PayFees` amount — it has no relationship to the `gas` value requested for `CallContract`. [4](#0-3) 

Downstream, `ConstantGasMeter` enforces fixed constants for `SetOperatingMode`, `Upgrade`, `UnlockNativeToken`, `RegisterForeignToken`, and `MintForeignToken`, but passes through the raw `gas_limit` for `CallContract` unchecked. [1](#0-0)  This value becomes `OutboundCommandWrapper.gas` / `CommandWrapper.gas`, which is hashed into `MessageLeaves` and committed as the dispatch gas limit that the Ethereum `Gateway` contract will honor when executing the command. [5](#0-4) 

I confirmed there is no other validation layer that would catch this: `Pallet::validate` in the outbound-queue-v2 pallet's `SendMessage` implementation only checks that the encoded message payload size is under `MaxMessagePayloadSize`; it performs no check relating `gas` to `fee`. [6](#0-5)  The `EthereumBlobExporter::validate` path (which invokes `XcmConverter::convert` and then `OutboundQueue::validate`) likewise adds no gas-fee linkage check. [7](#0-6) 

The only gating mechanism on this path is the `AllowedAliasOrigin` filter applied to the `AliasOrigin` instruction. [8](#0-7)  I was unable to locate the concrete production runtime configuration binding `AllowedAliasOrigin` (e.g., in Asset Hub / Bridge Hub runtime config) within the indexed codebase to determine exactly how permissive it is in production; this is a gap in my verification, though the vulnerable code path itself is unconditional once an origin passes that filter.

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" impact category: the committed `CommandWrapper.gas` field can be inflated by an XCM submitter to an arbitrarily large value (up to `u64::MAX`) while paying only the minimal fee validated by `extract_remote_fee`, since fee and gas are computed independently with no cross-check. [4](#0-3)  This can result in underpriced execution burden pushed onto relayers/Gateway, or a message whose gas requirement is impractical to execute, stalling nonce-sequential delivery of subsequent outbound messages. [9](#0-8) 

## Likelihood Explanation
The vulnerable code path is reachable via any XCM `Transact` instruction decodable as `ContractCall::V1`, gated only by the `AllowedAliasOrigin::contains` check on the `AliasOrigin` instruction. [10](#0-9)  The asymmetry is clearly visible in the single `match` block in `ConstantGasMeter::maximum_dispatch_gas_used_at_most`, where every other branch returns a hardcoded constant and only `CallContract` returns the raw field. [1](#0-0)  Exact severity depends on how restrictive `AllowedAliasOrigin` is configured in the live runtime, which I could not fully confirm in the indexed sources.

## Recommendation
Bound the `gas` value accepted for `Command::CallContract` to a fixed protocol maximum (consistent with the constants used for other commands), and/or require `fee_amount` (from `PayFees`/`WithdrawAsset`) to scale with the requested `gas` before it is accepted into the message in `XcmConverter::convert` or checked in `Pallet::validate`.

## Proof of Concept
1. Construct a V2 XCM: `WithdrawAsset`/`PayFees` with a minimal Ether fee, `AliasOrigin` (satisfying `AllowedAliasOrigin`), `DepositAsset`, and a `Transact` instruction whose call bytes decode via `ContractCall::decode_all` to `ContractCall::V1 { target, calldata, gas: u64::MAX, value }`.
2. Submit through `EthereumBlobExporter::validate` → `XcmConverter::convert`, which pushes `Command::CallContract { gas: u64::MAX, .. }` with no bound check. [2](#0-1) 
3. `Pallet::process` computes `T::GasMeter::maximum_dispatch_gas_used_at_most(&command)`, returning `u64::MAX` for the `CallContract` command, which is hashed into `MessageLeaves` and queued for relay/execution on Ethereum despite the minimal fee paid. [5](#0-4)

impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer.maximum_required_gas
			},
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}

			_ => Err(AssetResolutionFailed),
		}?;

			match_expression!(self.next()?, PayFees { asset: fee }, fee).ok_or(InvalidFeeAsset)?;

			_ => Err(AssetResolutionFailed),
