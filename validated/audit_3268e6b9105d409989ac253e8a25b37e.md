### Title
Unbounded token amount calculation in `ExchangeInjectActuator` allows unexpected loss of funds due to pool-ratio front-running - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectContract` lets an exchange creator inject liquidity by specifying only the quantity of one token (`quant`); the amount of the paired token that is also debited from the creator (`anotherTokenQuant`) is computed on-the-fly from the exchange's current token-balance ratio. There is no user-supplied maximum/expected bound on `anotherTokenQuant`, so if the pool ratio shifts (via other users' `ExchangeTransactionContract` trades) between when the creator signs/broadcasts the transaction and when it is actually validated/executed on-chain, the creator can be charged a materially different (larger) amount of the second token than they intended — exactly the "fee/cost depends on other users' activity with no max-fee guard" bug class described in the report.

### Finding Description
In `doValidate()`, `anotherTokenQuant` is derived from the live pool state: [1](#0-0) 

and it is recomputed again in `execute()` using whatever balances exist at the moment the transaction is actually applied in the block: [2](#0-1) 

Unlike `ExchangeTransactionActuator`, which protects the caller with a `tokenExpected` slippage floor that is enforced in validation: [3](#0-2) 

`ExchangeInjectContract`/`ExchangeInjectActuator` provides no analogous `expected`/`maxAnotherTokenQuant` field or check anywhere in `doValidate()` or `execute()`. Between the time the creator forms and signs the transaction (based on the pool ratio they observed) and the time it is included and executed by a block producer, any number of `ExchangeTransactionContract` trades from unrelated, unprivileged users can shift `firstTokenBalance`/`secondTokenBalance`, changing the effective price used to compute `anotherTokenQuant`. Because the debit of `anotherTokenQuant` from the creator's balance is unconditional and unbounded, the creator's transaction can execute successfully while consuming far more of the second token than anticipated.

### Impact Explanation
The exchange creator (the only account authorized to call this actuator, per the creator-address check) can have significantly more of a TRC10 asset or TRX debited from their account balance than intended, purely due to price movement caused by other unprivileged users' trades executed in the same or an intervening block. This is a direct, quantifiable loss of user funds triggered by a single broadcastable transaction combined with unrelated market activity from other order placers, matching the report's Medium/Medium classification.

### Likelihood Explanation
Any user can trigger `ExchangeTransactionContract` trades on a given exchange pair to move its ratio; an exchange creator broadcasting an injection has no built-in way to bound their exposure, and normal network latency/block-packing order is enough for the ratio to have moved by the time the inject transaction executes. This makes the condition reachable without any privileged access — a plain signed transaction plus ordinary trading activity from other market participants.

### Recommendation
Add an `expected`/`max_another_token_quant` field to `ExchangeInjectContract`, and in `ExchangeInjectActuator.doValidate()`/`execute()` reject the transaction if the computed `anotherTokenQuant` exceeds the caller-specified maximum, mirroring the slippage protection (`tokenExpected`) already implemented in `ExchangeTransactionActuator`.

### Proof of Concept
1. Exchange creator observes pool ratio `firstTokenBalance : secondTokenBalance` and signs an `ExchangeInjectContract` for `quant` of `firstToken`, expecting to also pay `anotherTokenQuant` of `secondToken` based on the observed ratio.
2. Before the creator's transaction is packed into a block, other users submit `ExchangeTransactionContract` trades on the same `exchangeId` that shift the balance ratio significantly (e.g., heavily buying `secondToken`).
3. When the creator's `ExchangeInjectContract` is validated/executed (`ExchangeInjectActuator.doValidate`/`execute`, lines 215-227 and 71-83), `anotherTokenQuant` is recalculated using the new, shifted ratio, resulting in a much larger debit of `secondToken` than the creator anticipated.
4. The transaction succeeds because there is no `expected`/max bound check, and the creator's account is debited the unexpectedly large `anotherTokenQuant`, with no recourse.
