Audit Report

## Title
Zero-slippage AMM swap in `snowbridge-pallet-system-frontend` allows sandwich attack that drains user tip/fee assets and underfunds Ethereum-side execution - (File: bridges/snowbridge/pallets/system-frontend/src/lib.rs)

## Summary
`Pallet::swap_and_burn` calls `T::Swap::swap_exact_tokens_for_tokens` with `amount_out_min` hardcoded to `None`, disabling slippage protection on the AMM trade that converts a user-supplied fee/tip asset into Ether before burning it for teleport to Ethereum. This is reachable from the permissionless `register_token` (non-Root origin) and `add_tip` extrinsics, allowing any unprivileged actor to sandwich the swap and drain nearly all of the victim's value while the resulting deflated `ether_gained` is forwarded as the authoritative fee/tip amount to BridgeHub.

## Finding Description
`swap_and_burn` explicitly passes `None` for the minimum-output parameter with the comment `// No minimum amount required`: [1](#0-0) 

This function is invoked from `swap_fee_asset_and_burn` whenever the supplied fee/tip asset differs from Ether: [2](#0-1) 

`swap_fee_asset_and_burn` is called by both permissionless extrinsics: `register_token` (open to any origin whose `asset_id` is nested within it, non-`Root` locations pay via swap) and `add_tip` (open to any `ensure_signed` account): [3](#0-2) [4](#0-3) 

The resulting `ether_gained`, whose value is not bounded by any minimum, is forwarded verbatim as the `amount` field in the `EthereumSystemCall::RegisterToken` and `EthereumSystemCall::AddTip` calls dispatched to BridgeHub: [5](#0-4) 

Elsewhere in the codebase, `pallet_asset_conversion`'s own extrinsic path enforces a real minimum via `ProvidedMinimumNotSufficientForSwap`, and the `Swap` trait signature itself supports an `amount_out_min: Option<Balance>` guard designed for this exact purpose — confirming that `system-frontend` is deliberately bypassing an available protection mechanism rather than lacking the capability to use one.

## Impact Explanation
Because the swap output is unconstrained, an attacker who sandwiches the trade against the public `pallet_asset_conversion` pool can extract nearly all of the value of the victim's tip/fee asset. The deflated `ether_gained` is then: (1) burned via `burn_for_teleport` — permanently destroying the user's originally supplied asset value — and (2) recorded as the authoritative fee/tip `amount` sent to BridgeHub's `EthereumSystem::register_token`/`add_tip`. This breaks the bridge-reward conservation-of-value invariant (the relayer reward tip for a `message_id`, or the execution fee for token registration, no longer reflects the value the user actually paid), directly causing user fund loss with no compensating benefit and potential underfunding of Ethereum-side execution.

## Likelihood Explanation
Exploitation requires only observing a pending `register_token`/`add_tip` transaction in the pool and executing a standard front-run/back-run (sandwich) pair against the relevant `pallet_asset_conversion` pool within the same block window — no privileged role, validator collusion, or off-chain infrastructure access is needed. This is a well-known, repeatable MEV technique bounded only by pool liquidity depth and attacker capital.

## Recommendation
Add a real `amount_out_min` parameter (or derive a conservative bound via `pallet_asset_conversion::quote_price_exact_tokens_for_tokens` with an acceptable tolerance) to `register_token`/`add_tip`, and pass it into `T::Swap::swap_exact_tokens_for_tokens` in `swap_and_burn` instead of `None`, so the swap fails and the extrinsic reverts if pool price moves beyond an acceptable slippage bound.

## Proof of Concept
1. Attacker observes a pending `add_tip(message_id, asset)` call in the transaction pool, where `asset` targets a `tip_asset → ether` pool in `pallet_asset_conversion`.
2. Attacker front-runs with a large `tip_asset → ether` trade on the same pool, skewing the price.
3. Victim's `add_tip` executes `swap_and_burn`, which calls `T::Swap::swap_exact_tokens_for_tokens(..., None, ...)` at `bridges/snowbridge/pallets/system-frontend/src/lib.rs:301-308` — the trade succeeds despite `ether_gained` being far below fair value.
4. Attacker back-runs with the reverse `ether → tip_asset` trade, restoring price and capturing the difference as profit.
5. The deflated `ether_gained` is burned and forwarded as the `amount` in `EthereumSystemCall::AddTip`, so the relayer reward recorded for `message_id` is far lower than the value the user paid.
