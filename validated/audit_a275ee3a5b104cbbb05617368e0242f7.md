### Title
Unbounded array allocation from attacker-controlled length word in precompile array extraction - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` read a 32-byte "length" word directly from calldata via `DataWord.intValueSafe()` and immediately allocate a `byte[len][...]` array with that value, without validating it against the actual size of the supplied calldata. This mirrors the reported Go `archive/zip` bug class: a crafted header falsely declaring a large item count causes an allocation/loop to run before the real data is validated, producing a panic/OOM rather than a controlled error.

### Finding Description [1](#0-0) 
`extractBytes32Array` computes `len = words[offset].intValueSafe()` and immediately does `new byte[len][]` with no upper bound check tying `len` to the actual `words`/`data` length. [2](#0-1) 
`extractBytesArray` similarly derives `len` from calldata and allocates `byte[len][]` before any per-element offset/length is checked against the real `data.length`. [3](#0-2) 
`extractSigArray` follows the identical pattern for signature arrays.

Because `len` is fully attacker-controlled (it is simply a 32-byte word from the precompile's `data` argument, safely down-cast to `int` via `intValueSafe()`), a caller can set it to an arbitrarily large positive `int` (up to `Integer.MAX_VALUE`) while supplying only a small amount of actual calldata. The allocation `new byte[len][]` happens before any bound is enforced against the true payload size — the same root-cause pattern as the CVE: trusting a declared count/length field to size a data structure ahead of validating that the underlying buffer actually contains that much data.

### Impact Explanation
A very large `len` triggers a multi-array allocation of up to billions of elements/objects, which can throw `OutOfMemoryError` or consume excessive heap/CPU, potentially destabilizing or crashing the executing node process for any transaction that invokes the affected precompile with crafted calldata. This is reachable from any unprivileged contract call routed through the TVM to this precompile (no special privilege required — a plain contract-call/transaction is sufficient).

### Likelihood Explanation
Reachability requires knowing/using whichever precompiled contract address dispatches to the class(es) containing these extraction helpers; I could not confirm within the available context exactly which precompile(s) invoke `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, nor whether the calling `execute()` wraps the allocation in a broad `catch (Throwable)` (which would downgrade impact to a caught/logged failure rather than a crash, as is done for `VerifyMintProof`/`VerifyTransferProof` elsewhere in the same file). Given this uncertainty, likelihood is Medium — the primitive (attacker-controlled unbounded allocation length) is confirmed, but full exploit-to-crash reachability was not fully confirmed with the tools available in this session.

### Recommendation
Before allocating `byte[len][...]` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against the maximum number of elements the actual `words`/`data` array could possibly contain (e.g., `len <= (words.length - offset - 1)` or an equivalent bound derived from `data.length`), rejecting the call with a normal execution failure instead of allocating first and discovering the mismatch later.

### Proof of Concept
1. Craft calldata for the affected precompile where the length word at `offset` (consumed by `extractBytes32Array`/`extractBytesArray`/`extractSigArray`) is set to a very large value (e.g., `0x7fffffff`), while the remainder of `data`/`words` is minimal.
2. Submit a transaction/contract call that invokes this precompile with the crafted calldata.
3. Observe the precompile attempt `new byte[len][...]`, driving excessive memory allocation and potential `OutOfMemoryError`/node instability, analogous to the crafted-archive-header panic in the referenced CVE.

    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
