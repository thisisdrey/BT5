This confirms the key finding. The Gitaly documentation itself explicitly states that partition assignments are **never invalidated on repository deletion**, which is the direct structural analog to the Solidity `_isContract()` bug: an identity/isolation-boundary determination is made once from transient on-disk state (`ValidateGitDirectory`) and then permanently cached under a stable "address" (the `relativePath`), even though the underlying "contract" (repository) can be destroyed and recreated at that same address with entirely different content/ownership. ### Title
Stale/Never-Invalidated Partition Assignment Allows a Recreated Repository to Inherit a Prior (Possibly Pool-Linked) Partition Identity - (File: `internal/gitaly/storage/storagemgr/partition_assigner.go`)

### Summary
`getPartitionIDRecursive` determines a repository's isolation-boundary ("partition") identity by checking, exactly once, whether the on-disk path is a valid Git directory (`storage.ValidateGitDirectory`), and then permanently persists that determination as a `(relativePath, partitionID)` mapping in `partitionAssignmentTable`. This assignment is **never removed when the repository is deleted** — the project's own documentation calls this out as a known, crude limitation. Consequently, a relative path's partition identity, once established (e.g., because the original repository was an object pool member with alternates, per `getAlternatePartitionID`), persists indefinitely and is silently reapplied to whatever repository is later created at that same relative path, without ever re-running the validation/alternates check that produced the original assignment.

### Finding Description
The relevant control flow is:

1. `getPartitionIDRecursive` first looks up `relativePath` in `partitionAssignmentTable`. If an entry exists, it is returned immediately with **no re-validation whatsoever** [3](#0-2) .
2. Only on the very first access (cache miss) does the code call `storage.ValidateGitDirectory` to confirm the path is a real Git directory, and `getAlternatePartitionID`/`gitstorage.ReadAlternatesFile` to determine whether this repository is linked to (or should be co-located with) an object pool [4](#0-3) [5](#0-4) .
3. Once written via `setPartitionID`, this mapping in the embedded key-value store is permanent. There is no code path that deletes a `partition_assignment/<relativePath>` entry when the corresponding repository is removed (via `RemoveRepository`/`repoutil.Remove`, or via WAL `DeleteRepository`) [6](#0-5) [7](#0-6) .
4. The project's own architecture documentation explicitly acknowledges this: *"The assignment handling is fairly crude at the moment. The assignments are created before the repository is even created, and assignments are not deleted even if the repository is deleted."* [1](#0-0) 
5. Confirmed by the transaction-manager test suite: `"create repository again after deletion"` and `"writes concurrent with repository deletion fail"` steps explicitly exercise delete-then-recreate at the identical relative path and validate WAL/LSN state, but never assert on partition-assignment invalidation — the assignment table is orthogonal and untouched by these flows [8](#0-7) .

This is structurally identical to the `Blocklist._isContract` bug: an existence/identity check on a mutable, attacker-controllable on-disk location (`extcodesize(addr)` ≅ `ValidateGitDirectory(path)`) is performed once and its result is cached against a stable "address" (`addr` ≅ `relativePath`). The underlying object can then be destroyed (`selfdestruct` ≅ `RemoveRepository`/`DeleteRepository`) and recreated at the same address (`CREATE2` with fixed salt ≅ creating a new repository at the identical `RelativePath`, which is entirely attacker/caller-controlled in most repository-creation RPCs), silently inheriting the old identity/trust decision instead of being freshly evaluated.

### Impact Explanation
Partitions are Gitaly's transactional and WAL isolation boundary — "Transactions always operate against a single partition, never across them," and pool members are deliberately co-located with their object pool's partition specifically so that fork/pool cross-object visibility is transactionally safe [9](#0-8) . If a relative path was once assigned into a shared pool partition (because the original repository at that path had an alternates file, or was passed as an "additional repository" for a fork/pool creation) and is later deleted and recreated as an unrelated, independent repository, the new repository is silently placed into the old, unrelated partition rather than being assigned its own. This blurs the partitioning/isolation guarantees the WAL and conflict-detection logic rely on, and it means a repository's partition membership — and thus its exposure to another partition's WAL/transactions/data — is determined by history at that path rather than its current, actual state. Because `RelativePath` values are attacker/caller-influenced across ordinary repository lifecycle RPCs (`CreateRepository`, `CreateFork`, `RemoveRepository`), this allows a caller who controls the create/delete/recreate sequence at a given path to force a new repository into a stale partition assignment it was never validated against.

### Likelihood Explanation
Reaching this requires only ordinary, unprivileged repository lifecycle operations exposed via standard Gitaly RPCs: create a repository (optionally with an alternate/pool relationship) at a relative path, delete it, then create a new repository at the identical relative path. No malicious peer, leaked token, or privileged access is required — this is achievable by any client capable of issuing normal repository management RPCs against a given relative path.

### Recommendation
Delete (or invalidate/re-validate) the `partition_assignment/<relativePath>` entry whenever a repository is removed (in `repoutil.Remove` and in the WAL's `DeleteRepository` commit path), so that partition assignment is re-derived — including re-running `ValidateGitDirectory` and the alternates/object-pool check — the next time a repository is created at that relative path, rather than trusting a stale cached mapping.

### Proof of Concept
1. Create repository A at relative path `R` as a member of object pool `P` (so `R` gets assigned into `P`'s partition via `getAlternatePartitionID`) [10](#0-9) .
2. Call `RemoveRepository` on `R` (deletes the on-disk directory and repository key, but never touches `partitionAssignmentTable`) [6](#0-5) .
3. Create a brand-new, unrelated repository at the same relative path `R` (no alternates, unrelated content).
4. Observe via `StorageManager.GetAssignedPartitionID(R)` that the new repository is still assigned to pool `P`'s partition ID, identical to step 1, without `ValidateGitDirectory`/`getAlternatePartitionID` ever being re-run against the new repository's actual state [11](#0-10) .

```markdown
### Partitioning

Gitaly divides the data it stores into partitions. Each partition is essentially its own mini-database. They have their own write-ahead log, and store one or more repositories and their associated key-value entries. Transactions always operate against a single partition, never across them. Transactional guarantees only apply within a partition, and transactions are not ordered between different partitions.

Before a transaction can be started against a repository, Gitaly needs to determine which partition the repository belongs to. This is by looking up the repository's partition assignment from the embedded key-value store mapping. The mapping stores the assigned partition ID of each relative path in the form of `(relative_path, partition_id)`. If a mapping already exists, a transaction is started against the assigned partition. If there's no existing mapping yet, the relative path will automatically be assigned into a partition.

Gitaly automatically assigns repositories to partitions when they are first accessed:

- Object pools and all repositories connected to the object pool are placed in the same partition. Repositories that are about to be connected to an object pool, such as newly created forks, are also placed in the same partition with the object pool they are about to be connected.
  - Assigning pools and their connected repositories into the same partition ensures transactions can guarantee consistency between them. If pools were in different partitions, transaction ordering could cause issues, for example updating a reference in a fork before the objects are written into the pool.
- Repositories that are not connected (nor about to be connected) to an object pool are placed in their own partitions.
```

```go
func (pa *partitionAssigner) getPartitionIDRecursive(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID, isRepositoryCreation bool) (storage.PartitionID, error) {
	// Check first whether the repository is already assigned into a partition. If so, just return the assignment.
	ptnID, err := pa.partitionAssignmentTable.getPartitionID(relativePath)
	if err != nil {
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			return 0, fmt.Errorf("get partition: %w", err)
		}

		// Repository wasn't yet assigned into a partition. This is the slow path. Requests attempting
		// to get or assign a partition ID concurrently are serialized.

		releaseLock, err := pa.acquireRepositoryLock(ctx, relativePath)
		if err != nil {
			return 0, fmt.Errorf("acquire repository lock: %w", err)
		}

		defer releaseLock()

		// With the repository locked, check first whether someone else assigned it into a partition
		// while we weren't holding the lock between the first failed attempt getting the assignment
		// and locking the repository.
		ptnID, err = pa.partitionAssignmentTable.getPartitionID(relativePath)
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			if err != nil {
				return 0, fmt.Errorf("recheck partition: %w", err)
			}

			// Some other goroutine assigned a partition between the failed attempt and locking the
			// repository.
			return ptnID, nil
		}

		// With the repository under lock, verify it is a Git directory before we assign it into a partition.
		// It's okay if the repository doesn't yet exist as this transaction may be about to create it.
		if err := storage.ValidateGitDirectory(filepath.Join(pa.storagePath, relativePath)); err != nil {
			if errors.Is(err, fs.ErrNotExist) {
				if !isRepositoryCreation {
					return 0, relativePathNotFoundError(relativePath)
				}

				// Repository creations are allowed to target non-existing repositories. They create the partition
				// where the repository is to be created.
			} else {
				return 0, fmt.Errorf("validate git directory: %w", err)
			}
		}

		ptnID, err = pa.assignPartitionID(ctx, relativePath, recursiveCall, partitionHint)
		if err != nil {
			return 0, fmt.Errorf("assign partition ID: %w", err)
		}
	}

	return ptnID, nil
}
```

```go
func (pa *partitionAssigner) assignPartitionID(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID) (storage.PartitionID, error) {
	// Check if the repository has an alternate. If so, it needs to go into the same
	// partition with it.
	ptnID, err := pa.getAlternatePartitionID(ctx, relativePath, recursiveCall, partitionHint)
	if err != nil {
		if !errors.Is(err, gitstorage.ErrNoAlternate) {
			return 0, fmt.Errorf("get alternate partition ID: %w", err)
		}

		ptnID = partitionHint
		if ptnID == invalidPartitionID {
			// The repository has no alternate. Unpooled repositories go into their own partitions.
			// Allocate a new partition ID for this repository.
			ptnID, err = pa.allocatePartitionID()
			if err != nil {
				return 0, fmt.Errorf("acquire partition id: %w", err)
			}
		}
	}

	if err := pa.partitionAssignmentTable.setPartitionID(relativePath, ptnID); err != nil {
		return 0, fmt.Errorf("set partition: %w", err)
	}

	return ptnID, nil
}
```

```go
func (pa *partitionAssigner) getAlternatePartitionID(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID) (storage.PartitionID, error) {
	alternate, err := gitstorage.ReadAlternatesFile(filepath.Join(pa.storagePath, relativePath))
	if err != nil {
		return 0, fmt.Errorf("read alternates file: %w", err)
	}

	if recursiveCall {
		// recursive being true indicates we've arrived here through another repository's alternate.
		// Repositories in Gitaly should only have a single alternate that points to the repository's
		// pool. Chains of alternates are unexpected and could go arbitrarily long, so fail the operation.
		return 0, storage.ErrAlternateHasAlternate
	}

	// The relative path should point somewhere within the same storage.
	alternateRelativePath, err := storage.ValidateRelativePath(
		pa.storagePath,
		// Take the relative path to the repository, not 'repository/objects'.
		filepath.Dir(
			// The path in alternates file points to the object directory of the alternate
			// repository. The path is relative to the repository's own object directory.
			filepath.Join(relativePath, "objects", alternate),
		),
	)
	if err != nil {
		return 0, fmt.Errorf("validate relative path: %w", err)
	}

	if alternateRelativePath == relativePath {
		// The alternate must not point to the repository itself. Not only is it non-sensical
		// but it would also cause a dead lock as the repository is locked during this call
		// already.
		return 0, storage.ErrAlternatePointsToSelf
	}

	// Recursively get the alternate's partition ID or assign it one. This time
	// we set recursive to true to fail the operation if the alternate itself has an
	// alternate configured.
	ptnID, err := pa.getPartitionIDRecursive(ctx, alternateRelativePath, true, partitionHint, false)
	if err != nil {
		return 0, fmt.Errorf("get partition ID: %w", err)
	}

	return ptnID, nil
```
