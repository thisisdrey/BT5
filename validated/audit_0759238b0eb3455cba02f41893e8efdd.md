### Title
Witness Vi snapshot for the reward cycle is taken before all rewards for that same cycle are credited, permanently excluding late-credited rewards from voter payout - ([File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java])

### Summary
In `MaintenanceManager.doMaintenance()`, the "global" per-cycle reward accumulator (`DelegationStore.accumulateWitnessVi`) is snapshotted for the *current* cycle number before all reward-crediting operations for that same cycle have finished executing. Any reward credited to the `reward` bucket for that cycle *after* the Vi snapshot is taken (but still tagged with the same, not-yet-incremented cycle number) is written to `DelegationStore`'s reward store but is never reflected in any witness Vi value, because Vi for that cycle is only ever computed once. This is structurally the same class of bug as the reported issue: a "global" aggregate (Vi, analogous to the global position accumulator in the Perennial report) is finalized using a snapshot of state that races with "local" per-entity updates (per-cycle reward crediting, analogous to local position settlement) for the same period, causing a desync between the two and unrecoverable loss for some claimants (voters relying on the new reward algorithm).

### Finding Description
`MaintenanceManager.doMaintenance()` executes, in order:
1. If `useNewRewardAlgorithm()`, snapshot Vi for every witness for `curCycle = dynamicPropertiesStore.getCurrentCycleNumber()`: [1](#0-0) 
2. Count votes and, if there are newly counted votes, run `incentiveManager.reward(newWitnessAddressList)` — which pays out rewards (through `MortgageService.payReward`) using the *same* `curCycle` number, since the cycle has not been incremented yet: [2](#0-1) 
3. Only afterward is the cycle number incremented and next-cycle brokerage/vote snapshots are written: [3](#0-2) 

`MortgageService.payReward` credits reward into `delegationStore.addReward(cycle, witnessAddress, value)` keyed by whatever `dynamicPropertiesStore.getCurrentCycleNumber()` returns at call time: [4](#0-3) 

`DelegationStore.accumulateWitnessVi(cycle, address, voteCount)` reads `getReward(cycle, address)` **once** to compute the Vi delta for that cycle, and this call happens only from step 1 of `doMaintenance`: [5](#0-4) 

Voter reward computation (`VoteRewardUtil.computeReward` / `queryReward`) is entirely driven by the difference between two Vi checkpoints (`endVi - beginVi`) for the account's vote cycle range: [6](#0-5) 

Because Vi for `curCycle` is computed and persisted once at step 1, any reward subsequently written into the same `curCycle` reward bucket at step 2 (`incentiveManager.reward`) will never be picked up by a later Vi computation — the next Vi accumulation runs for `curCycle+1` using `getReward(curCycle+1, ...)`, not `curCycle`. The reward amount silently exists in the `DelegationStore` reward bucket for `curCycle` but is permanently unreachable through the Vi-based delegator payout path, i.e. the delegator vote-share of that reward becomes irrecoverably lost/frozen, while the brokerage portion (paid directly via `adjustAllowance`) is unaffected.

This mirrors the reported root cause precisely: a global/aggregate state finalization step races ahead of per-entity updates meant to occur within the same accounting period, and once the global snapshot is taken, later same-period updates diverge permanently from what the aggregate reflects.

### Impact Explanation
Delegator (voter) reward derived from the standby-witness/incentive payout awarded during `doMaintenance()` for the current cycle can be permanently excluded from any voter's claimable reward, since it is never incorporated into any Vi checkpoint. This constitutes a permanent loss of funds for voting accounts, while the underlying value remains recorded (but effectively orphaned) in `DelegationStore`. Because this occurs every maintenance cycle in which `incentiveManager.reward()` performs a payout keyed to `curCycle` after the Vi snapshot, this is not a one-off edge case but a structural, recurring issue for any market/network running with `useNewRewardAlgorithm()` enabled and non-empty `newWitnessAddressList` on that cycle transition.

### Likelihood Explanation
This does not require an attacker or unusual conditions — it happens automatically inside normal `doMaintenance()` execution whenever both `useNewRewardAlgorithm()` is enabled and vote counts (and thus `incentiveManager.reward()`) are non-empty at maintenance time, which is the normal, expected steady-state operation of the DPoS consensus/reward cycle. This makes the ordering bug reachable purely through ordinary chain progression, without any additional attacker involvement.

Note: I was unable to fully inspect `IncentiveManager.reward()`'s internal implementation before running out of tool iterations, so I cannot conclusively confirm the exact reward amounts/paths it credits through `MortgageService.payReward` versus other sinks (e.g., whether it always calls `payReward` with `curCycle`, or credits some rewards differently). The finding above is based on the confirmed call ordering in `MaintenanceManager.doMaintenance()` and the confirmed single-shot nature of `accumulateWitnessVi`/`getReward` usage, but full verification of `IncentiveManager.reward()`'s behavior would require further investigation of that file.

### Recommendation
Move the Vi accumulation snapshot (`delegationStore.accumulateWitnessVi(curCycle, ...)`) to occur strictly after all reward-crediting operations for `curCycle` have completed (including `incentiveManager.reward(...)`), and only then increment the cycle number. Alternatively, defer `incentiveManager.reward()`'s payout for the just-closed cycle to be tagged with the cycle number *before* the Vi snapshot is taken, ensuring the global (Vi) and local (per-cycle reward bucket) accounting always observe a consistent, fully-settled state for a given cycle before the aggregate is finalized.

### Proof of Concept
Conceptual trace based on confirmed code paths:
1. `useNewRewardAlgorithm()` is true; `curCycle = N`.
2. `doMaintenance()` calls `delegationStore.accumulateWitnessVi(N, witness, voteCount)` for every witness, freezing Vi(N) based on `reward(N, witness)` accumulated so far from in-cycle block/tx-fee rewards.
3. `doMaintenance()` continues, and non-empty `countWitness` triggers `incentiveManager.reward(newWitnessAddressList)`, which (via `MortgageService.payReward`) calls `delegationStore.addReward(N, witnessAddress, value)` — still cycle `N` since increment hasn't happened yet.
4. `doMaintenance()` finally increments `currentCycleNumber` to `N+1`.
5. Any voter computing reward across a range including cycle `N` uses `Vi(N-1)` and `Vi(N)` — but `Vi(N)` was computed in step 2, *before* the extra reward from step 3 was added to `reward(N, witness)`. That reward amount is never included in any Vi(N) or Vi(N+1) computation, and is effectively lost from the delegator payout pool permanently.

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
