### Title
Unbounded per-filter result queue growth in JSON-RPC `eth_newFilter`/`eth_newBlockFilter` allows unauthenticated memory-exhaustion DoS - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/filters/FilterResult.java])

### Summary
The Mattermost CVE-2023-5330 root cause is that the OpenGraph cache had a bound on the number of cache entries but no bound on the *size* each cached entry could grow to, letting an attacker inflate memory via crafted requests until the server became unavailable. java-tron's JSON-RPC filter subsystem exhibits the same bug class: `eth_newFilter`/`eth_newBlockFilter` are capped in *count* (`maxLogFilterNum`, `maxBlockFilterNum`), but each individual filter's result buffer (`FilterResult.result`, a `BlockingQueue`) has no capacity bound and accumulates every matching log/block for up to 5 minutes without the caller ever having to drain it.

### Finding Description
`TronJsonRpcImpl.newFilter()`/`newBlockFilter()` are reachable by any anonymous JSON-RPC HTTP client (`eth_newFilter`, `eth_newBlockFilter`) and are capped only by the *number* of live filters: [1](#0-0) [2](#0-1) 

Each created filter is backed by a `LogFilterAndResult`/`BlockFilterAndResult`, both extending `FilterResult<T>`, whose `result` field is an unbounded `LinkedBlockingQueue`: [3](#0-2) [4](#0-3) 

`add(T t)` unconditionally appends new matching elements with no size cap, and `isExpire()`/`updateExpireTime()` only track a 5-minute (`EXPIRE_SECONDS = 300`) TTL that resets on every poll — but nothing prevents the queue itself from growing arbitrarily large *before* the TTL elapses or before the caller ever polls: [5](#0-4) 

Because a filter's queue is populated passively as new blocks/logs are produced on-chain (independent of whether the client ever calls `eth_getFilterChanges`), an attacker only needs to: (1) create one or a few filters via `eth_newFilter` with broad match criteria (e.g., no address/topic filter, matching every log), and (2) never poll or uninstall them. Over the 5-minute window (renewed indefinitely as long as the attacker keeps creating fresh filters before the old ones expire, since the node can hold up to `maxLogFilterNum`=20000 / `maxBlockFilterNum`=50000 concurrent filters by default), each filter's internal queue accumulates every matching `LogFilterElement`/block hash with no per-filter or aggregate byte-size limit — unlike the count-based `maximumSize` bounds used elsewhere in the codebase's Guava caches (e.g. `CacheStrategies`, `GlobalRateLimiter`, `logElementCache`).

### Impact Explanation
An unauthenticated JSON-RPC client can drive unbounded heap growth on the FullNode/SolidityNode JSON-RPC service by opening many broad-match filters and letting them accumulate log/block events without draining. Since this queue growth is uncapped in size (only capped in filter *count*, and even that limit is generous by default — 20,000 log filters, 50,000 block filters), sustained on-chain activity (or an attacker triggering many events via cheap self-triggered contract calls) can exhaust node memory, causing OOM crashes or GC-driven service degradation, matching the "node crash or halt" / "API the node can no longer serve" impact bar.

### Likelihood Explanation
The JSON-RPC HTTP interface is commonly enabled on public/RPC-serving FullNodes and requires no authentication or on-chain balance to call `eth_newFilter`. Triggering large volumes of matching logs is straightforward for an attacker (broad topic/address criteria, or self-generated events over time), and no operator action is required to make the queue overflow — the code path is entirely passive from the attacker's perspective once filters are created.

### Recommendation
Bound each `FilterResult`'s queue with a maximum element count (and optionally evict/replace with an "overflow" indicator once exceeded, similar to how `logElementCache`/`blockHashCache` are size-capped), or drop/expire filters proactively once their queue exceeds a configured threshold rather than only bounding filter count.

### Proof of Concept
1. Enable JSON-RPC HTTP (`vm.jsonrpc.httpFullNodeEnable = true`, default port 8545).
2. As an anonymous client, call `eth_newFilter` with an empty/broad filter (no address, no topics) to match all logs.
3. Do not call `eth_getFilterChanges`/`eth_uninstallFilter`.
4. Let normal chain activity (or attacker-driven contract event spam) run for the ~5-minute filter TTL; observe the corresponding `LogFilterAndResult.result` queue growing without bound, proportional to on-chain log volume, with no cap enforced by `FilterResult.add()`.
5. Repeat filter creation up to `maxLogFilterNum` (20,000 by default) concurrently to multiply memory pressure across many unbounded queues simultaneously.

package org.tron.core.services.jsonrpc.filters;

import java.util.List;
import java.util.concurrent.BlockingQueue;
import lombok.Getter;
import org.tron.core.services.jsonrpc.TronJsonRpcImpl;

public abstract class FilterResult<T> {

  private long expireTimeStamp;

  @Getter
  protected BlockingQueue<T> result;

  public void updateExpireTime() {
    expireTimeStamp = System.currentTimeMillis() + TronJsonRpcImpl.EXPIRE_SECONDS * 1000;
  }

  public boolean isExpire() {
    return expireTimeStamp < System.currentTimeMillis();
  }

  public abstract void add(T t);

  public abstract List<T> popAll();
}
