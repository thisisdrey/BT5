### Title
Anti-replay window `Check`/`Update` race in `ConnectionState.Decrypt` allows nonce reuse and replay of data-plane packets - (File: `connection_state.go`)

### Summary
This is the concurrency analog of the C4 finding: a value is read, validated, and then acted upon while assuming it hasn't changed — but the "check" and the "commit" are split across two separate lock acquisitions with unprotected work in between, letting two concurrent operations both pass the check before either commits. In VTVL, `balanceOf()` was read once and trusted for later use even though the underlying balance state could change. In Nebula, `cs.window.Check()` validates a message counter against the replay window and releases `decryptLock` before the packet is actually decrypted; `cs.window.Update()` — the operation that actually records the counter as consumed — only happens afterward, under a second, independent lock acquisition.

### Finding Description
`ConnectionState.Decrypt` in `connection_state.go` performs replay protection in three separate critical sections instead of one atomic operation: [1](#0-0) 

```
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)   // (1) validate
cs.decryptLock.Unlock()
...
out, err = cs.dKey.DecryptDanger(...)          // (2) act — outside the lock
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)   // (3) commit
cs.decryptLock.Unlock()
```

`Check` only *reads* the sliding-window bitmap (`bits.go`, `Check`) — it does not mark the counter as seen. Marking only happens in `Update`, which flips the bit for that counter position: [2](#0-1) 

Because `decryptLock` is released between steps (1) and (3), two goroutines that call `Decrypt` concurrently with the **same `messageCounter`** can both execute `Check()` and both observe "not yet seen," since neither has called `Update()` yet. Both then proceed to call `DecryptDanger` and, if it succeeds for both, both would then call `Update()` — the second `Update()` call would return `false` (duplicate), but decryption and any side effects on the first goroutine's success path (e.g., delivering the plaintext to the tun device, firewall processing, conntrack insertion) have already occurred once already, and it's the parallel duplicate execution of `DecryptDanger` and downstream processing that constitutes the race — not a single logical delivery.

Concurrent invocation is realistic: Nebula supports multiple parallel UDP listener routines that each independently read packets and call into the same `Interface`/`HostInfo`/`ConnectionState`: [3](#0-2) 

An attacker who captures one valid encrypted data packet (this requires no CA-signed certificate — merely observing/capturing UDP traffic between two hosts, or being a relay) can duplicate it and send both copies at once, or send it to the two different listener sockets in quick succession, so that both are read by different goroutines and race inside `Decrypt` before the window bit is set.

### Impact Explanation
Splitting the "checked" state from the "committed" state — just as the audited contract checked `balanceOf()` once but relied on it staying true through `withdraw()` — creates a window where the safety invariant (each nonce/counter is used at most once) can be violated under concurrency. This undermines the AEAD nonce-uniqueness guarantee the replay window exists to enforce and can cause a legitimately delivered packet to be processed twice by the host's downstream logic (tun write, firewall/conntrack state), which is a state-consistency and duplicate-delivery issue in the data path — the kind of remote state-poisoning concern the bug class targets when the "checked" resource is not the same as the "used" resource by the time the action commits.

### Likelihood Explanation
Exploitability depends on timing: the attacker must get a duplicate encrypted packet processed by two different reader goroutines within the small window between `Check()` and `Update()`. Nebula's multi-routine UDP listener design makes this plausible, and no cryptographic material or valid certificate is required — only capture/replay of one legitimate ciphertext, matching the "no CA-signed certificate" reachability constraint via the nonce/replay-handling class.

### Recommendation
Perform the check-and-mark as a single atomic operation under one lock acquisition (i.e., merge `Check` and `Update` into one locked call, or hold `decryptLock` across the entire check-decrypt-update sequence, or use a compare-and-set style API on `Bits` that reserves the slot before decryption and rolls it back only on decryption failure) so no other goroutine can observe an "unused" counter that is concurrently being consumed.

### Proof of Concept
Conceptual PoC (not executed, based on code reading):
1. Establish a Nebula tunnel between hosts A and B normally.
2. Attacker (on-path or relay) captures one legitimate encrypted data packet `P` (header + ciphertext) sent from B to A, containing a specific `messageCounter`.
3. Attacker sends two copies of `P` to A's underlay socket(s) at (near-)the same instant, ideally targeting the separate `listenOut(i)` reader goroutines A runs (`interface.go` lines 309-326).
4. Both goroutines call `ConnectionState.Decrypt` for the same `messageCounter`. Because `decryptLock` is released between `window.Check` and `window.Update` (`connection_state.go` lines 61-82), both goroutines can pass `Check` before either calls `Update`, causing `DecryptDanger` to run twice concurrently for the same nonce/counter and duplicate downstream processing of the packet, defeating the intended once-only replay guarantee.

```go
func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
```

```go
func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
```
