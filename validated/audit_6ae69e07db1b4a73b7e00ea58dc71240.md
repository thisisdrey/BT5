Audit Report

## Title
Reward payout on delivery receipt ignores dispatch `success` flag, causing incorrect settlement regardless of actual message execution outcome - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` containing a `success: bool` field sourced from the Ethereum `InboundMessageDispatched` event, but never checks this field before crediting the relayer reward and removing the `PendingOrder`. Any relayer who submits a validly-proven receipt for a message whose dispatch on Ethereum failed will still be paid the full fee, and the order will be settled as if delivery succeeded.

## Finding Description
The `DeliveryReceipt` type explicitly carries a `success` flag decoded straight from the on-chain event log [3](#0-2) . The extrinsic `submit_delivery_receipt` verifies the Merkle/Beefy proof of the log and constructs the `DeliveryReceipt`, then calls `process_delivery_receipt` [4](#0-3) . Inside `process_delivery_receipt`, the only checks performed are on the gateway address and existence of a `PendingOrders` entry for the nonce; the `receipt.success` field is read only to derive nothing — it is fetched into the struct but never branched on [1](#0-0) . If `order.fee > 0`, `T::RewardPayment::register_reward` is called unconditionally, and the order is removed and `MessageDelivered` is emitted regardless of whether the dispatch on Ethereum actually succeeded. The module-level documentation itself states the intended flow is "verified and executed" before reward payment [5](#0-4) , confirming this is a deviation from intended behavior rather than an ambiguous design choice.

## Impact Explanation
This causes payout of relayer rewards for messages that were not successfully executed on the destination (Ethereum) side, which is a duplicate/incorrect settlement of bridge relayer rewards independent of actual execution outcome — the `PendingOrder` state advances (is removed, reward paid) without settlement of the underlying message actually succeeding, violating the intended invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." This is a runtime bug compromising intended reward-payout behavior in bridge processing, matching the impact gate.

## Likelihood Explanation
Any unprivileged relayer submitting a genuine, validly-proven `InboundMessageDispatched` event where the emitted `success` field is `false` (e.g., due to insufficient gas budget, application-level command revert, or any legitimate Ethereum-side execution failure) triggers this bug through the ordinary, public, signed `submit_delivery_receipt` extrinsic [4](#0-3) . No collusion, forged proof, or privileged access is required — the flag is legitimately produced by real failed dispatches, and the pallet simply fails to consult it in the payout path.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: on `true`, keep the current reward-and-removal behavior; on `false`, still remove the `PendingOrder` to avoid a permanently stuck slot, but skip `register_reward` (or route to a distinct failure/refund flow) and emit a distinct event (e.g., `MessageDispatchFailed`) instead of `MessageDelivered`, so relayers are not compensated for failed destination-side dispatches.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating a `PendingOrders[nonce]` entry with `fee > 0` [6](#0-5) .
2. The message is relayed to Ethereum but the destination-side command execution fails (e.g. insufficient gas or an application-level revert), causing the Gateway contract to emit `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer calls `submit_delivery_receipt` with a valid Beefy/Merkle proof of this real event log; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success = false` correctly [3](#0-2) .
4. `process_delivery_receipt` ignores `success`, sees `order.fee > 0`, calls `T::RewardPayment::register_reward` to pay the relayer, removes the `PendingOrder`, and emits `MessageDelivered` — despite the dispatch having failed [7](#0-6) .
