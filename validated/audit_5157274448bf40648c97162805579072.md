This confirms the vulnerability. The RPC handler `try_handle_request` in `getattachment.rs` returns whatever attachment is stored under the requested hash key when serving legitimately [1](#0-0) , but nothing prevents a malicious peer from returning an arbitrary `GetAttachmentResponse{attachment: Attachment{content: ...}}` with any content on the wire — the decode function only does JSON parsing with no hash check [2](#0-1) . The client-side code in `extend_with_attachments` inserts `response.attachment` into the `attachments` HashSet with no comparison to `request.content_hash` at all [3](#0-2) . Then in `AttachmentsDownloader::run`, the `Done` handler stores the attacker-controlled attachment under its own self-computed hash via `insert_instantiated_attachment`, looks up `find_all_attachment_instances` and resolves the batch using `attachment.hash()` — never the originally requested `content_hash` [4](#0-3) .

### Title
Attachment gossip response is stored/resolved without verifying it matches the requested content_hash - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When the Atlas subsystem fetches an attachment for a pending `AttachmentInstance` via `GET /v2/attachments/<content_hash>`, the response body is decoded and accepted without ever checking that the returned `Attachment::hash()` equals the requested `content_hash`. A malicious peer serving this endpoint can return arbitrary bytes with an unrelated hash, which get permanently written into `AtlasDB` and resolve a *different* attachment entry than the one legitimately requested, leaving the truly-committed content unresolved.

### Finding Description
The broken equality is: `Attachment::hash()` of the served bytes must equal `AttachmentRequest.content_hash` (which itself equals the on-chain committed `AttachmentInstance.content_hash`), but this equality is never checked anywhere in the code path.

Trace:
1. `AttachmentsBatchStateContext::get_prioritized_attachments_requests` builds an `AttachmentRequest { content_hash: H1, ... }` for a missing attachment tied to a processed block [5](#0-4) .
2. The request is dispatched to a remote peer's `/v2/attachments/H1` endpoint; the peer's HTTP handler is `RPCGetAttachmentRequestHandler`, but a malicious peer under attacker control doesn't have to run this legitimate handler at all — it just needs to return a well-formed 200 JSON response shaped like `GetAttachmentResponse`.
3. `StacksHttpResponse::decode_atlas_get_attachment` merely JSON-parses the body into `GetAttachmentResponse { attachment }` with no hash validation [2](#0-1) .
4. `AttachmentsBatchStateContext::extend_with_attachments` inserts `response.attachment` into `self.attachments` (a `HashSet<Attachment>`) with no comparison against `request.content_hash` [6](#0-5) .
5. `AttachmentsDownloader::run`'s `Done` branch iterates `context.attachments`, computes `attachment.hash()` (call it H2, attacker-controlled), looks up `find_all_attachment_instances(&attachment.hash())`, calls `insert_instantiated_attachment(&attachment)` to persist it, and calls `context.attachments_batch.resolve_attachment(&attachment.hash())` — resolving by H2, not by the original H1 that was requested [4](#0-3) .

Since H2 != H1, the batch entry for H1 (the real, on-chain-committed content hash) is never marked resolved. It remains in the `AttachmentsBatch` and is retried until `max_attachment_retry_count` is exhausted, after which the batch is dropped [7](#0-6) . Meanwhile attacker-chosen bytes are permanently persisted in `AtlasDB` under hash H2, an identifier that no on-chain name operation ever referenced.

No existing guard catches this: there is no length/hash cap on the JSON attachment content beyond generic decode, and no equality check exists in `extend_with_attachments` or in the `Done` resolution logic.

### Impact Explanation
- A remote unprivileged peer serving the Atlas HTTP endpoint (or claiming to) can prevent a legitimately committed BNS zonefile/attachment (identified by content_hash H1) from ever resolving on the victim node, since its `AttachmentsBatch` entry is never marked resolved and is eventually dropped after retries are exhausted. This is a "serving non-canonical state as canonical" / "attachment/BNS mismatch" class issue matching the High severity bucket.
- The attacker's arbitrary bytes are written into `AtlasDB.attachments` under a self-chosen hash (`insert_instantiated_attachment`), polluting local storage, though they are not tied to any instance since no `AttachmentInstance` references H2 (`find_all_attachment_instances` for H2 will typically be empty), so no consumer treats it as valid content for a name. The primary and confirmed impact is denial of resolution for the legitimate committed attachment.
- This is repeatable per content_hash request, on every retry, from any peer selected as an outbound sync peer serving the attachments endpoint.

### Likelihood Explanation
- Precondition: the node must have a pending unresolved `AttachmentInstance` (e.g., BNS zonefile hash) from a processed block, and must select a malicious/attacker-run peer as one of its outbound sync peers for attachment inventory/serving purposes — attainable since Atlas peer selection is based on the normal outbound peer set with no additional trust requirement [8](#0-7) .
- Attacker cost is minimal: run/control a P2P node with an HTTP server, respond to `/v2/attachments/<hash>` with a fabricated JSON body. No secrets or privileged role needed.
- Fully remotely reachable via the public RPC/data URL that peers exchange.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after decoding the response, compare `response.attachment.hash()` to `request.content_hash`; if they differ, treat it as a failed request (`report.bump_failed_requests()` and skip insertion) rather than inserting into `self.attachments`. Additionally/alternatively, in `AttachmentsDownloader::run`'s `Done` handling, resolve using the originally requested hash and verify it matches `attachment.hash()` before calling `insert_instantiated_attachment` and `resolve_attachment`.

### Proof of Concept
Rust unit test in `stackslib::net::atlas::tests` (or `download.rs` test module):
1. Construct an `AttachmentsBatchStateContext` with an `AttachmentsBatch` tracking `AttachmentInstance` with `content_hash = H1`.
2. Build a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains an `AttachmentRequest{content_hash: H1, ...}` paired with a `Some(StacksHttpResponse)` whose body decodes (via `decode_atlas_get_attachment`) to `GetAttachmentResponse{attachment: Attachment{content: b"evil".to_vec()}}`, whose `hash()` is H2 != H1.
3. Call `context.extend_with_attachments(&mut results)` and then simulate the `Done` branch logic (`insert_instantiated_attachment`, `resolve_attachment(&attachment.hash())`) against an in-memory `AtlasDB`.
4. Assert: `atlasdb.find_attachment(&H1).unwrap().is_none()` (the real committed hash never resolved) and `atlasdb.find_attachment(&H2).unwrap().is_some()` (attacker bytes stored under unrelated hash) — demonstrating the mismatch is never rejected.

    pub fn get_prioritized_attachments_requests(&self) -> BinaryHeap<AttachmentRequest> {
        let mut queue = BinaryHeap::new();
        let mut enqueued = HashSet::new();
        for ((contract_id, pages, _), peers_responses) in self.inventories.iter() {
            let missing_attachments = match self
                .attachments_batch
                .attachments_instances
                .get(contract_id)
            {
                None => continue,
                Some(missing_attachments) => missing_attachments,
            };
            // Note: we're getting missing_attachments (attachment_id: content_hash)
            for (attachment_index, content_hash) in missing_attachments.iter() {
                let page_index = attachment_index / AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;
                // Since there's a limit in the number of pages that a node can request,
                // we can potentially have multiple inventory request at once.
                if !pages.contains(&page_index) {
                    continue;
                }

                if enqueued.contains(content_hash) {
                    debug!("Atlas: {} already enqueued", content_hash);
                    continue;
                }

                let mut sources = HashMap::new();
                let position_in_page =
                    attachment_index % AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;

                for (peer_url, response) in peers_responses.iter() {
                    // Considering the response, look for the page with the index
                    // we're looking for.
                    let search_page = response.pages.iter().find(|page| page.index == page_index);

                    let has_attachment = search_page
                        .and_then(|search_page| {
                            search_page.inventory.get(position_in_page as usize)
                        })
                        .map(|result| *result == 1)
                        .unwrap_or(false);

                    if !has_attachment {
                        debug!(
                            "Atlas: peer does not have attachment ({}, {}) in its inventory {:?}",
                            page_index, position_in_page, response.pages
                        );
                        continue;
                    }

                    let report = self
                        .peers
                        .get(peer_url)
                        .expect("Atlas: unable to retrieve reliability report for peer");
                    sources.insert(peer_url.clone(), report.clone());
                }

                if sources.is_empty() {
                    warn!("Atlas: could not find a peer including attachment in its inventory");
                    continue;
                }

                // Success, we found at least one inventory including the attachment we're looking for.
                let request = AttachmentRequest {
                    sources,
                    content_hash: content_hash.clone(),
                    stacks_block_height: self.attachments_batch.stacks_block_height,
                    canonical_stacks_tip_height: self.attachments_batch.canonical_stacks_tip_height,
                };
                enqueued.insert(content_hash);
                queue.push(request);
            }
        }
        queue
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
