Confirmed: `ExchangeInjectContract` and `ExchangeWithdrawContract` have no `expected`/minimum-amount field, unlike `ExchangeTransactionContract` which explicitly carries `expected` for slippage protection. [1](#0-0) 

### Title
Missing slippage control (no minimum-received check) in ExchangeInjectActuator and ExchangeWithdrawActuator enables sandwich extraction of TRC10 bancor-exchange liquidity - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
The `ExchangeInjectContract` and `ExchangeWithdrawContract` (java-tron's built-in bancor-style TRC10 exchange, distinct from smart-contract DEXes) carry no minimum-output / minimum-ratio parameter, unlike `ExchangeTransactionContract` which has an explicit `expected` field used for slippage protection. [1](#0-0)  Because the exchange's `firstTokenBalance`/`secondTokenBalance` ratio can be freely and atomically moved by anyone submitting an `ExchangeTransactionContract` trade against the same pool, a pending Inject or Withdraw transaction from the exchange creator has no way to bound the price it will execute at.

### Finding Description
`ExchangeInjectActuator.execute` computes the paired "another token" amount purely from the pool's current balances at execution time, with no lower/upper bound supplied by the caller: [2](#0-1)  Its validator (`doValidate`) likewise only checks balance-limit and balance-sufficiency constraints, never a caller-supplied minimum/maximum for `anotherTokenQuant`: [3](#0-2) 

`ExchangeWithdrawActuator` has the identical pattern: `anotherTokenQuant` is derived from the live pool ratio in both `execute` and `doValidate`, with no minimum threshold parameter in the contract to reject an unfavorable ratio: [4](#0-3) [5](#0-4) 

In contrast, `ExchangeTransactionActuator` deliberately added an `expected` minimum-received check to prevent exactly this class of value extraction: [6](#0-5)  This shows the protocol authors recognized the slippage risk for trades but omitted the identical protection for liquidity inject/withdraw operations.

Both Inject and Withdraw are restricted to the exchange's creator address, but that restriction only prevents a random address from directly calling inject/withdraw on someone else's pool — it does not prevent any unprivileged account from broadcasting an `ExchangeTransactionContract` (open to any account holding the relevant token) that shifts `firstTokenBalance`/`secondTokenBalance` immediately before the creator's pending Inject/Withdraw transaction is packed into a block. [7](#0-6) 

### Impact Explanation
An attacker (any unprivileged, unpermissioned account) observing a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` in the mempool can front-run it with an `ExchangeTransactionContract` trade that skews the pool ratio, causing the creator's inject to deposit an unfavorable/mismatched pair (locking in value at a bad ratio) or causing the creator's withdraw to redeem a materially smaller amount of the paired token than expected — a direct, unauthorized transfer of value from the exchange creator to the attacker's advantage, without any on-chain mechanism for the creator to bound or reject the unfavorable execution.

### Likelihood Explanation
Any account can submit an `ExchangeTransactionContract` against a public exchange pool at will and cheaply, and transaction ordering within a block is influenced by fee/broadcast timing rather than any protection mechanism here; the creator has no parameter to defend against this, making the attack straightforward to execute whenever a sizeable Inject/Withdraw is expected or observed pending.

### Recommendation
Add a caller-supplied slippage-bound field (e.g., `expected`/`min_another_token_quant` for `ExchangeInjectContract`, and `expected`/`min_another_token_quant` for `ExchangeWithdrawContract`), and validate it in `ExchangeInjectActuator.doValidate`/`ExchangeWithdrawActuator.doValidate` the same way `tokenExpected` is validated in `ExchangeTransactionActuator`, rejecting the transaction if the computed `anotherTokenQuant` is worse than the caller's specified bound.

### Proof of Concept
1. Exchange creator broadcasts `ExchangeWithdrawContract` intending to withdraw `tokenQuant` of `firstTokenID`, expecting `anotherTokenQuant` of `secondTokenID` based on the current pool ratio observed in the mempool/latest block.
2. Before this transaction is included, an attacker broadcasts an `ExchangeTransactionContract` selling a large amount of `secondTokenID` into the same pool, shifting `firstTokenBalance`/`secondTokenBalance` sharply (this call is open to any account and only requires holding/owning `secondTokenID`, per `ExchangeTransactionActuator.doValidate`) — see the transaction-based ratio update in `ExchangeCapsule.transaction`: [8](#0-7) 
3. The creator's withdraw is then processed using the now-skewed balances in `ExchangeWithdrawActuator.execute`, redeeming a much smaller `anotherTokenQuant` than originally expected, with no validation step able to reject this because no minimum/expected field exists in `ExchangeWithdrawContract`. [9](#0-8) 
4. The attacker can optionally reverse their trade afterward, extracting the value transferred from the creator's withdraw at the attacker's chosen ratio — a classic sandwich, mirroring the missing-slippage-control root cause described in the Ajna/Uniswap report but reachable here via `ExchangeTransactionContract` + `ExchangeWithdrawContract`/`ExchangeInjectContract`.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
