Audit Report

## Title
Permanent, unprivileged-triggerable loss of staking rewards via unconditional "claimed" marking before payout success - (File: `substrate/frame/staking/src/pallet/impls.rs`, also `substrate/frame/staking-async/src/pallet/impls.rs`)

## Summary
In `payout_stakers`/`do_payout_stakers`, `EraInfo::<T>::set_rewards_as_claimed` (legacy `pallet-staking`) and `Eras::<T>::set_rewards_as_claimed` (`staking-async`) irreversibly mark an era/page as claimed before any individual payout is attempted, and the subsequent per-staker payout functions can silently fail and return `None`/drop funds with no error propagated to the caller. Since `payout_stakers` is a permissionless, publicly callable extrinsic, any account whose configured `RewardDestination::Account` target cannot receive funds permanently and silently forfeits its share of that era/page's reward, while the call itself still returns `Ok`.

## Finding Description
The claimed-state flag is set unconditionally prior to payout execution in both pallets: [1](#0-0) [2](#0-1) 

The code's own comment confirms the deliberate design intent that "no errors allowed" after this point, meaning individual payout failures cannot abort the extrinsic or roll back the claimed flag: [3](#0-2) 

Per-staker payouts return `Option`, and any `None` result is simply skipped without any error surfaced to the caller: [4](#0-3) 

`make_payout` resolves the caller-chosen `RewardDestination`. For `RewardDestination::Account`, it calls `asset::mint_creating` (not `mint_into_existing` as the original claim stated) — I want to flag this discrepancy from the original submission for accuracy. `mint_creating` uses `Precision::BestEffort` and `unwrap_or_default()`, meaning if the deposit cannot succeed (e.g., destination account doesn't exist and reward amount is below the Existential Deposit), the resulting imbalance is silently zero — funds are effectively dropped rather than transferred, with no error: [5](#0-4) [6](#0-5) 

In `staking-async`, the transfer-based payout path (`make_payout_from_provider`) transfers from an era reward pot to the caller-controlled `payout_account` using `Preservation::Expendable`; if the transfer fails (e.g., destination cannot be created because the amount is below ED), the error is logged and dropped with no propagation to the dispatch result: [7](#0-6) 

Since `set_rewards_as_claimed`/`is_rewards_claimed` gate future calls with `Error::<T>::AlreadyClaimed`, once the flag is set for an `(era, stash, page)` tuple, there is no code path to retry or recover the lost payout for that page.

## Impact Explanation
This matches the "permanent user-fund lock" pattern in the impact gate: a stash's reward for a specific `(era, page)` is irrecoverably and silently lost if its `RewardDestination::Account` target cannot receive the deposit/transfer (e.g., account doesn't exist and the reward is below ED). The claimed flag is committed atomically with no dependency on payout success, so there is no way to re-trigger payment for that page once `payout_stakers` has been called — unlike `pallet-treasury`, which supports payment-state tracking and retries. The dispatch reports `Ok`, masking the loss from both the caller and the affected staker.

## Likelihood Explanation
`payout_stakers`/`payout_stakers_by_page` are permissionless extrinsics callable by anyone on behalf of any validator/era/page, so no privileged access is required. The triggering condition — a nominator/validator's configured payee account not being funded to at least the Existential Deposit at the time of payout — is a realistic, easily-reachable state that can occur naturally (unfunded new account) or be induced/exploited by a third party who calls the payout before the payee corrects their account state.

## Recommendation
Do not commit `set_rewards_as_claimed` until each beneficiary's payout has been confirmed to succeed, or introduce a per-stash/per-page payment-state tracking mechanism (similar to `pallet-treasury`'s `PaymentState`) that allows retries for failed payout legs. At minimum, emit a distinguishable failure event per failed beneficiary (rather than silently omitting `Rewarded`) and consider only marking the specific stash's portion as claimed when the deposit/transfer actually succeeds, keeping the remainder retryable.

## Proof of Concept
1. A nominator `N` calls `set_payee(RewardDestination::Account(X))`, where `X` is an account that has never held a balance (below Existential Deposit).
2. Era `E` completes with `N` holding nonzero exposure in validator `V`'s page `P`.
3. Any account calls `payout_stakers(V, E)` or `payout_stakers_by_page(V, E, P)`.
4. `EraInfo::<T>::set_rewards_as_claimed(E, &V, P)` (or `Eras::<T>::set_rewards_as_claimed`) executes unconditionally, before any transfer/mint is attempted.
5. `make_payout(&N, reward)` resolves `dest_account = X` and calls `asset::mint_creating::<T>(&X, reward)`; if `reward < ED`, `Precision::BestEffort` deposit fails and `unwrap_or_default()` yields a zero imbalance — no funds move to `X`.
6. The extrinsic returns `Ok(...)`. Any subsequent call to `payout_stakers`/`payout_stakers_by_page` for `(V, E, P)` returns `Error::<T>::AlreadyClaimed`, permanently precluding retry for `N`'s lost reward.

	fn make_payout_from_provider(
		era: EraIndex,
		stash: &T::AccountId,

		if amount.is_zero() {
			return None;
		}

		let dest = match Self::payee(Stash(stash.clone())) {
			Some(d) => d,
			None => {
				Self::deposit_event(Event::<T>::Unexpected(UnexpectedKind::MissingPayee {
					era,
					stash: stash.clone(),
				}));
				return None;
			},
		};

		let staker_rewards_pot =
			T::RewardPots::pot_account(RewardPot::Era(era, RewardKind::StakerRewards));

			&staker_rewards_pot,
			&payout_account,
			amount,
			Preservation::Expendable,
		) {
			log!(
				error,
				"Failed to transfer reward from pot for era {:?}, stash {:?}: {:?}",
				era,
				stash,
				e
			);
			return None;
