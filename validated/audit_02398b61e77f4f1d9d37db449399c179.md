Given the review, the strongest reachable analog of the "assumed peg / proxy-value diverges from real value, undermining a safety limit" bug class in this Gitaly snapshot is the `x-gitaly-cost` cost-scoring mechanism, which explicitly (by its own design documentation) treats a declared/static value as equivalent to real resource consumption even though the two can diverge arbitrarily.

### Title
RPC cost score assumes payload bytes are a 1:1 proxy for actual backend cost, letting expensive requests report as cheap - ([File: internal/grpc/middleware/costhandler/costhandler.go])

### Summary
The `x-gitaly-cost` gRPC trailer is Gitaly's sole signal for external rate limiting (translated by Rails/Workhorse into the `X-Score` HTTP header consumed by Cloudflare's complexity-based rate limiter). The score is computed as a fixed per-RPC "static" weight plus a dynamic term derived only from the number of payload bytes transferred, divided by 1 MiB [1](#0-0) . This assumes payload byte count is an adequate 1:1 proxy for actual computational/IO cost of the RPC, in the same way the audited report assumed WETH price was an adequate 1:1 proxy for stETH price.

### Finding Description
`computeCost` combines `staticCostForMethod` (a hardcoded table of per-RPC weights, or a default based on whether the RPC is classified accessor/mutator/maintenance) with `dynamicCostFromContext`, which is purely `bytes / 1MiB` [2](#0-1) [3](#0-2) . The project's own architecture document acknowledges this proxy is imprecise: "A static score hides variance (e.g. `PostUploadPackWithSidechannel` is the same cost whether it serves 1 MB or 10 GB), but dynamic cost (bytes transferred, object count) is only known after the RPC completes." [4](#0-3)  Yet the field left as override weights (`staticCostOverrides`) are hardcoded per full-method-name, and the dynamic term never accounts for CPU-bound work (e.g., revision walks, diff/rename detection, deltification, tree traversal) that is decoupled from the number of output/input bytes [5](#0-4) . An ordinary authenticated client can pick request parameters (revision ranges, path filters, pagination, or crafted diff/blame/commit-walk arguments) that maximize server-side CPU/IO work while minimizing the response payload size, causing `dynamicCostFromContext` to report near-zero additional cost even though the RPC handler consumes disproportionate CPU/memory. Because the static weight per RPC is fixed regardless of the actual arguments (e.g., `CommitDiff`/`RawDiff`/`ListCommits` always score the same static 6–8 regardless of the revision range or rename-detection cost) [6](#0-5) , the "declared" cost that Gitaly hands to the upstream rate limiter diverges from real resource consumption in the same way the audited protocol assumed `stETH` tracked `WETH` 1:1 for computing a swap's `minOutAmount`.

### Impact Explanation
The `x-gitaly-cost` trailer is the load-management design's outward signal specifically meant to let Cloudflare/Rails/Workhorse throttle expensive clients before they reach the innermost defense layer [7](#0-6) . If the cost score systematically underestimates true cost for specific RPC/argument combinations, an attacker can issue many "cheap-scored but actually expensive" requests that evade the upstream complexity-based rate limiter, sustaining elevated CPU/memory pressure on the Gitaly node. This undermines the very purpose of the mitigation chain and can contribute to a DoS of the affected RPC handler(s) and, at scale, the node (feeding into `LoadShedder`/circuit-breaker only after the fact, once pressure is already elevated) [8](#0-7) .

### Likelihood Explanation
Any authenticated caller of the gRPC API (a normal, unprivileged Gitaly client through Workhorse/Rails) can choose RPC parameters; no privileged access, leaked token, or MITM is required. The gap is baked into the always-fixed `staticCostOverrides` table and the byte-only dynamic term, so it is deterministically exploitable for any RPC whose real cost is not proportional to transferred bytes (e.g., deep history walks, expensive diff computations, filters over large object graphs).

### Recommendation
Do not treat transferred bytes as a proxy for computational cost. Incorporate actual measured resource usage (CPU time and/or `BurdenTracker`/cgroup measurements already collected for the pressure signal) into the per-RPC cost calculation, or at minimum scale the static weight by request-shape signals that correlate with real work (e.g., number of commits walked, diff computations performed, objects touched) rather than a fixed per-method constant. Where the true cost can only be known after completion, reconcile it in a follow-up signal as the design doc itself suggests, and ensure the reconciliation is actually wired into the exported score rather than left as a documented gap.

### Proof of Concept
1. Issue a `CommitDiff`/`RawDiff`/`ListCommits` request against a repository with a very large history/revision range but constrain the response to keep transferred bytes minimal (e.g., request a diff between two commits that are computationally expensive to compare — heavy rename detection — but whose actual diff output is tiny, or request `ListCommits` with a broad revision range but a `PaginationParams` limit of 1).
2. Observe that `computeCost` returns `staticCostOverrides["/gitaly.DiffService/CommitDiff"] (=8)` plus a `dynamicCostFromContext` near 0 (since `OutPayloadBytes`/1MiB rounds to ~0) [6](#0-5) [1](#0-0) , while the actual Gitaly-side CPU time for the handler is orders of magnitude higher than a "cheap" accessor RPC.
3. Repeat the request at high volume; because the exported `x-gitaly-cost`/`X-Score` stays low, the upstream Cloudflare/Rails rate limiter under-throttles the traffic, allowing sustained resource exhaustion on the Gitaly node.

func computeCost(ctx context.Context, fullMethod string) int {
	static := staticCostForMethod(fullMethod)
	dynamic := dynamicCostFromContext(ctx)
	return static + dynamic
}

// staticCostForMethod returns the static cost weight for the given full method
// name. It first checks per-RPC overrides, then falls back to a default based
// on the method's operation type from the proto registry.
func staticCostForMethod(fullMethod string) int {
	if cost, ok := staticCostOverrides[fullMethod]; ok {
		return cost
	}

	methodInfo, err := protoregistry.GitalyProtoPreregistered.LookupMethod(fullMethod)
	if err != nil {
		return defaultUnknownCost
	}

	switch methodInfo.Operation {
	case protoregistry.OpAccessor:
		return defaultAccessorCost
	case protoregistry.OpMutator:
		return defaultMutatorCost
	case protoregistry.OpMaintenance:
		return defaultMaintenanceCost
	default:
		return defaultUnknownCost
	}
}

## Connection to Rails and Workhorse

Gitaly's role in the broader DoS mitigation system is to be the innermost
ring of defense and to communicate two signals outward: node health (for
circuit breaking) and per-RPC cost (for rate limiting).

**What Gitaly provides:**

- `x-gitaly-pressure` gRPC trailer on every response (0.0 = healthy,
  1.0 = saturated) — node health signal
- `x-gitaly-cost` gRPC trailer on every response — per-RPC cost score
- `RESOURCE_EXHAUSTED` gRPC errors when requests are rejected by the
  concurrency limiter or load shedder.

**What Rails does with it:**

- Reads the `x-gitaly-pressure` trailer via a gRPC client interceptor
- Maintains a moving average of pressure per Gitaly storage
- Trips a per-node circuit breaker when sustained pressure is detected
- Translates `x-gitaly-cost` into the `X-Score` HTTP response header for
  upstream consumption

For standard requests, Rails is in the response path:

```plaintext
(upstream rate limiter) <- X-Score header <- Rails <- x-gitaly-cost trailer <- Gitaly
```

For Git operations (clone, fetch, push), Workhorse streams directly
to/from Gitaly — Rails is only in the auth path. Workhorse reads the
`x-gitaly-cost` trailer from the Gitaly response and sets `X-Score` on
the HTTP response to the client:

```plaintext
(upstream rate limiter) <- X-Score header <- Workhorse <- x-gitaly-cost trailer <- Gitaly
                                    |
                           Rails auth response
```
