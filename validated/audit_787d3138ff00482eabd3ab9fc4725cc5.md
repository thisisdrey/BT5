### Title
Newline injection into git-rev-list `--stdin` via `--glob=` pseudo-revision bypasses `ValidateRevision` whitespace check - ([File: internal/git/revision.go])

### Summary
`git.ValidateRevision` with `AllowPseudoRevision()` returns `nil` immediately when a revision has a prefix like `--glob=`, `--branches=`, or `--tags=`, without ever reaching the later whitespace/newline check that applies to normal revisions. Revisions accepted by RPCs such as `ListCommits` and `ListBlobs` are passed to `git-rev-list`/`git-log` not as an argv-per-line list but joined by `\n` and fed via `--stdin`, so an attacker-controlled newline inside a `--glob=` value becomes a new, independent line of stdin input that Git will interpret as its own revision/pseudo-option.

### Finding Description
`ValidateRevision` in [1](#0-0)  checks pseudo-revision prefixes (`--glob=`, `--branches=`, `--tags=`) via `bytes.HasPrefix` and returns `nil` as soon as a prefix matches, before the subsequent checks for leading dash, NUL bytes, and — critically — whitespace/newlines at [2](#0-1)  are ever executed. This means a value like `--glob=refs/heads/*\n--upload-pack=/tmp/evil` is treated as fully valid.

This validation is invoked directly by RPC handlers such as `verifyListCommitsRequest` and `verifyListBlobsRequest`, which validate each element of `request.GetRevisions()` with `git.AllowPseudoRevision()` and otherwise accept the string verbatim: [3](#0-2) [4](#0-3) . The same validation is also referenced by `gitcmd.commandDescriptions["rev-list"].validatePositionalArgs` at [5](#0-4) .

The accepted revisions are subsequently not passed as a single argv token to `git-rev-list`. Instead, `gitpipe.Revlist` runs `git-rev-list --stdin` (or `git-log --stdin` for follow mode) and joins all revisions with `\n` before writing them to the child process's stdin: [6](#0-5) [7](#0-6) . Because Git's `--stdin` reader treats each line as an independent revision/option, an embedded `\n` inside a `--glob=` value effectively injects a brand-new line that Git parses as a separate token — bypassing the intended "single safe positional" invariant.

While `--upload-pack=...` is not a recognized option for `git-rev-list`'s stdin parser (that flag belongs to `fetch-pack`/`upload-pack` invocations, not `rev-list`), the underlying flaw is general: any option that `git-rev-list --stdin` legitimately accepts (e.g. another `--glob=`, `--exclude=`, `--all`, `-- <path>` separator, or a completely different ref pattern) can be smuggled in via the embedded newline, letting the attacker inject an arbitrary extra rev-list argument/pseudo-revision that was never validated as its own list entry. This breaks the "single token, no reinterpretation" invariant even though it does not itself amount to full shell/argv command injection (there is no shell involved and `exec.Command` still sees `--stdin` reading from a pipe, not the OS argv).

### Impact Explanation
The impact is confined to the `git-rev-list --stdin` argument-parsing context: an attacker can inject an arbitrary extra `--stdin`-recognized rev-list argument/pseudo-revision after their intended `--glob=`/`--branches=`/`--tags=` entry, potentially causing `git-rev-list` to traverse or exclude refs the caller did not intend, or to abuse other stdin-accepted rev-list options. This is not remote code execution (no shell interpretation, and `--upload-pack` is not a rev-list stdin keyword), so it does not map to a critical RCE bounty class, but it is a genuine argument-injection weakening of the "safe single positional" invariant that the codebase's comments and design explicitly intend to guarantee.

### Likelihood Explanation
Any unprivileged GitLab user who can call `ListCommits` or `ListBlobs` (available on any repository they can read) can supply a crafted `Revisions` field containing an embedded `\n` inside an allowed pseudo-revision prefix, since gRPC string fields freely accept newlines and neither handler strips them before calling `ValidateRevision`. No special role, secret, or non-default configuration is required — this is reachable via a normal RPC call.

### Recommendation
In `ValidateRevision` (`internal/git/revision.go`), move the pseudo-revision prefix checks so that they also enforce absence of NUL and whitespace/control characters in the remainder of the value (e.g., validate `bytes.ContainsAny(revision, " \t\n\r")` and NUL before/alongside the `HasPrefix` short-circuits, similar to how `AllowPathScopedRevision` still runs the whitespace check on the ref portion). Alternately, explicitly reject any pseudo-revision value containing `\n`, `\r`, NUL, or other characters that could be interpreted as a line separator by `--stdin` consumers.

### Proof of Concept
```go
package git

import "testing"

func TestValidateRevision_GlobAllowsNewlineInjection(t *testing.T) {
	revision := []byte("--glob=refs/heads/*\n--exclude=refs/heads/main")
	if err := ValidateRevision(revision, AllowPseudoRevision()); err != nil {
		t.Fatalf("expected acceptance (demonstrating the bug), got error: %v", err)
	}
	// BUG: a single `--glob=...` token containing an embedded newline is accepted,
	// even though gitpipe.Revlist joins revisions with "\n" and feeds them to
	// `git-rev-list --stdin`, causing the newline to be treated as a stdin line
	// separator and the suffix as an independent rev-list argument.
}
```
RPC-level PoC: call `ListCommits` with `Revisions: ["--glob=refs/heads/*\n--exclude=refs/heads/main"]`; `verifyListCommitsRequest` accepts it [8](#0-7) , and `gitpipe.Revlist` writes it verbatim (with the embedded newline) to `git-rev-list --stdin`'s stdin stream [9](#0-8) , resulting in `--exclude=refs/heads/main` being parsed by Git as a second, independent rev-list argument.
