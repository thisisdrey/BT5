### Title
Permanent Lockup of TRX Sent via CALL-with-value to Precompiled Contract Addresses in `Program.callToPrecompiledAddress` - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
The reported issue describes a Solidity contract (`CurveStableOracle.sol`) that accepts ETH via a `receive()` fallback but has no withdraw mechanism, permanently locking any TRX/ETH sent to it. The equivalent root cause in java-tron is that the TVM allows a `CALL` opcode with non-zero value to be routed to a **precompiled contract address** (e.g. `0x...01`–`0x...0a`, or the FreezeV2/vote query addresses `0x...1000001`–`0x...1000015`), and the endowment is unconditionally transferred into that address's on-chain balance — even though no actuator, opcode, or precompile logic can ever spend a precompiled address's balance back out.

### Finding Description
When a `CALL`/`CALLCODE` targets an address recognized by `PrecompiledContracts.getContractForAddress`, execution is routed through `Program.callToPrecompiledAddress` instead of `callToAddress`: [1](#0-0) 

Inside `callToPrecompiledAddress`, if the message carries a non-zero endowment, the value is moved from the caller into the *precompiled address's account balance* before the precompile logic even runs, entirely independent of whether the precompile's `execute()` does anything with TRX: [2](#0-1) 

None of the registered precompiled contracts (`ECRecover`, `Sha256`, `Identity`, `ModExp`, `BN128*`, `BatchValidateSign`, `ValidateMultiSign`, the FreezeV2 query precompiles, vote-count precompiles, etc.) implement any logic to move balance back out of their own address — they are pure computation/query functions returning a `Pair<Boolean, byte[]>`: [3](#0-2) [4](#0-3) 

These fixed addresses (`0x01`…`0x0a`, `0x1000001`…`0x1000015`, etc.) have no corresponding private key, are never deployed with code, and are not reachable as a `senderAddress`/`contextAddress` in any subsequent `callToAddress`/`callToPrecompiledAddress` invocation that could move funds out (there is no code at that account for the VM to execute in a "from" role, and no actuator lets an arbitrary account claim/withdraw balance sitting at a fixed precompile address). Consequently, any TRX endowed to these addresses via `CALL` is permanently and irrecoverably locked in that address's balance, functionally identical to the "receive() but no withdraw" pattern in the reported issue.

This is distinct from — and not prevented by — the direct `TransferContract` protection (`ForbidTransferToContract`), which only blocks transfers to accounts of `AccountType.Contract`: [5](#0-4) 

Precompile addresses are not registered as deployed `AccountType.Contract` accounts in `AccountStore` — they're recognized purely by the hard-coded address matching in `PrecompiledContracts.getContractForAddress`. Any account (auto-)created at such an address by `createAccountIfNotExist`/`MUtil.transfer` inside the VM would default to `AccountType.Normal`, so the `ForbidTransferToContract` safeguard would not necessarily even apply here — but the more directly reachable vector is any smart contract, or the TVM `CALL` opcode itself, sending value to these fixed addresses, since `callToPrecompiledAddress` performs the transfer unconditionally whenever `endowment > 0`.

### Impact Explanation
Any attacker-deployed contract (or even a benign contract with a bug) that does `target.call.value(x)(data)` against one of the fixed precompiled addresses will have `x` TRX permanently removed from circulation in a way that is not covered by the black-hole/burn accounting (`DynamicPropertiesStore.burnTrx`), i.e., it becomes an unbacked/unaccounted-for balance sitting at an address nobody controls and no code can ever spend from. This is a genuine, irreversible loss-of-funds bug class reachable by any unprivileged account issuing an ordinary `TriggerSmartContract` transaction that in turn performs a value-bearing `CALL` to a precompile address — no special privileges are required.

### Likelihood Explanation
Likelihood is moderate: it requires a user or contract to deliberately or accidentally send value to a precompiled address via the low-level `CALL` opcode (e.g. `addr.call.value(x)(data)`), which is unusual but fully permitted since neither `callToPrecompiledAddress` nor any of the precompile `execute()` implementations reject non-zero `msg.value`. Given TRON's widespread use of custom low-level calls (delegatecall proxies, multi-sig relayers, etc.), and given that some of the precompile addresses (e.g. `0x1`–`0xa`) are commonly used as targets for hash/signature helper calls, accidental value-forwarding is plausible, and can also be triggered intentionally by a malicious contract to permanently lock a victim's funds.

### Recommendation
In `Program.callToPrecompiledAddress`, reject calls to any address returned by `PrecompiledContracts.getContractForAddress` when `msg.getEndowment().value() > 0` (similar to how EVM implementations generally treat precompiles as non-payable), refunding the energy and pushing zero/reverting the call, rather than silently transferring TRX into an address that can never be spent from again.

### Proof of Concept
1. Deploy a trivial contract `Locker` with a function:
   `function drain() public payable { address(0x9).call.value(msg.value)(""); }` (address `0x...09` = `BatchValidateSign` precompile, always enabled once `allowTvmSolidity059` is active).
2. Call `drain()` with a positive TRX value via `TriggerSmartContract`.
3. Trace execution: `OperationActions.exeCall` detects the target as a precompile (`PrecompiledContracts.getContractForAddress` returns non-null) and calls `Program.callToPrecompiledAddress`, which executes `MUtil.transfer(deposit, senderAddress, contextAddress, endowment)` — moving TRX into account `0x...09`'s balance.
4. Query `AccountStore.get(0x...09)` post-execution: the balance now holds the transferred TRX.
5. Observe that there exists no actuator, contract, or key that can ever transfer this balance back out (no code is deployed there, and no private key exists for that address), demonstrating permanent fund lockup.
