### Title
`uint32` reward timestamp cast permanently freezes deposits, withdrawals, transfers, and reward claims after `uint32.max` - (contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor` stores reward checkpoints as `uint32` and casts `block.timestamp` with `SafeCast.toUint32()`. Once chain time exceeds `type(uint32).max` on 2106-02-07, every update of an initialized reward token reverts.

### Finding Description
`TokenState.timestamp` is a `uint32`. [1](#0-0)  `_calculateTokenIndex()` calls `block.timestamp.toUint32()` whenever a tracked token has a positive stored index and time has advanced. [2](#0-1)  `SafeCast` reverts instead of truncating when the value does not fit. [3](#0-2) 

The public `updateBeforeMintOrBurn()` and `updateBeforeTransfer()` entry points invoke that calculation for every initialized token. [4](#0-3)  Deposit-token mints and burns call the first hook for every distributor registered by the pool. [5](#0-4)  Deposit-token transfers call the second hook for every registered distributor. [6](#0-5) 

The issue also affects reward claiming because `claimRewards()` calls `_updateTokenIndex()` before paying accrued balances. [7](#0-6) 

### Impact Explanation
For any reward-configured `DepositToken`, `_mint()` and `_burn()` execute `updateRewardsBeforeMintOrBurn`; consequently, `deposit()` and `withdraw()` revert after the `uint32` boundary. [8](#0-7)  `_transfer()` executes `updateRewardsBeforeTransfer`, so users also cannot move unlocked deposit shares. [9](#0-8) 

This can permanently freeze the underlying collateral represented by affected deposit tokens and permanently freeze unclaimed reward balances while the affected distributor remains registered. No attacker privilege is required; the condition is triggered by normal public calls after `block.timestamp > type(uint32).max`.

### Likelihood Explanation
The condition is deterministic but can only occur after Unix timestamp `4,294,967,295`. It additionally requires the affected token to have been initialized in the distributor, which occurs when its token state is created with `INITIAL_INDEX` during speed activation. [10](#0-9)  Once initialized, the revert occurs even if the current speed is zero because the fallback branch still casts the timestamp. [11](#0-10) 

### Recommendation
Store `TokenState.timestamp` as `uint64` or `uint256`, or retain `uint32` only for a deliberately modular epoch scheme that handles wraparound explicitly. The index calculation should use a `uint256` current timestamp and convert it only after proving the selected storage representation cannot make user-facing token operations revert.

### Proof of Concept
The following Hardhat test can be added to the existing `RewardsDistributor` fixture in `test/RewardDistributor.test.ts`, where `pool.getRewardsDistributors` already returns the deployed distributor and `pool.doesDepositTokenExist` returns true: [12](#0-11) 

```ts
it('reverts reward updates after uint32 timestamp overflow', async function () {
  // Initializes tokenStates[msdTOKEN1] with INITIAL_INDEX and current uint32 timestamp.
  await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, 1)

  // Last timestamp that still fits in uint32.
  await time.increaseTo(2 ** 32 - 1)
  await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, alice.address)

  // First timestamp that exceeds uint32.
  await time.increaseTo(2 ** 32)

  await expect(
    rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, alice.address)
  ).to.be.revertedWith("SafeCast: value doesn't fit in 32 bits")

  await expect(
    rewardDistributor.claimRewards(alice.address, [msdTOKEN1.address])
  ).to.be.revertedWith("SafeCast: value doesn't fit in 32 bits")
})
```

For a configured production pool, the same revert propagates through `DepositToken.withdraw()` because withdrawal burns the position through `_burn()` and therefore enters the distributor hook before releasing collateral. [13](#0-12)
