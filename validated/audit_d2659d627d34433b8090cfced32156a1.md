### Title
Front-running of deterministic object-pool paths blocks legitimate pool creation and repository management - ([File: internal/gitaly/storage/repository_path.go])

### Summary
The Story Protocol report describes an attacker front-running an owner's transaction by pre-registering a resource (a derivative) at a location the legitimate owner intended to control, causing a lock that permanently denies the owner's follow-up management action. The closest reachable analog in Gitaly is the deterministic, low-entropy derivation of on-disk object-pool paths from sequential repository IDs, combined with `repoutil.Create`'s "create-if-absent" semantics — an unprivileged actor able to trigger repository/pool creation for a *known or guessable future* repository ID can pre-occupy that path before the legitimate owner's `CreateObjectPool` call lands, permanently blocking pool creation for that repository.

### Finding Description
`storage.DerivePoolPath` computes the on-disk path of an object pool purely from the repository's integer ID: [1](#0-0) 

```go
func DerivePoolPath(repositoryID int64) string {
	return deriveDiskPath(praefectPoolPathPrefix, repositoryID)
}
```

and `deriveDiskPath` hashes only the string form of that ID with SHA-256, keeping the numeric ID itself in the resulting path (`@cluster/pools/<hash-prefix>/<repositoryID>`): [2](#0-1) 

Because repository IDs are sequential and predictable, the future pool path for a soon-to-be-created repository is fully computable in advance by any client that can enumerate or predict IDs (e.g. by observing the last assigned ID via other repository-creation RPCs).

The actual creation path shared by object-pool and ordinary repository creation, `repoutil.Create`, only guards against *concurrent* creation via a lock — it does not prevent an attacker from creating *any* content at a path first, as long as the path did not previously exist: [3](#0-2) 

The critical section explicitly documents intent to detect races ("it could have happened that a concurrent RPC call created it") but only fails the *later* actor — regardless of whether that later actor is the legitimate owner or the attacker. If an attacker submits a `CreateRepository`/repository-creation request targeting the pre-computed pool path before the legitimate `CreateObjectPool` call is issued for that repository ID, the real `CreateObjectPool` RPC will hit `os.Stat(targetPath)` returning "already exists" and fail with `AlreadyExists`, per the same logic verified by tests: [4](#0-3) 

This mirrors the reported bug class: the attacker does not need any privilege on the target repository, does not need to compromise Gitaly, and does not race a lock in the traditional narrow sense — they win a naming race against a deterministic, guessable path, permanently occupying the resource the legitimate owner needs, causing a persistent denial of object-pool functionality (deduplication) for that repository.

### Impact Explanation
If successful, this locks out the legitimate repository/fork owner from ever creating an object pool for that repository ID at the expected path, since Gitaly's `CreateObjectPool` (via `repoutil.Create`) treats path pre-existence as a hard, non-recoverable failure. This disrupts fork/object-pool deduplication for that repository indefinitely — a persistent, low-cost DoS of a core storage-management feature, without requiring any compromise of credentials or elevated privilege, matching the required "concrete storage escape ... DoS of a handler" impact bar.

### Likelihood Explanation
Exploitability hinges on the attacker being able to (a) predict or observe the numerically sequential repository ID assigned to the target repository/fork before the object pool is created for it, and (b) issue an ordinary repository-creation RPC targeting the computed `@cluster/pools/...` relative path ahead of the legitimate `CreateObjectPool` call. Whether an unprivileged, unauthenticated-for-that-repo client can direct arbitrary relative paths of this form through the standard repository-creation RPC (bypassing the pool-specific validation in `internal/gitaly/service/objectpool/util.go`) could not be fully confirmed in this pass — the file contents for `internal/gitaly/service/objectpool/create.go`, `util.go`, and `internal/gitaly/service/repository/create_repository.go` were not retrievable in this investigation (tool errors prevented reading them), so the exact authorization/validation boundary on the relative-path parameter for ordinary `CreateRepository` calls, and whether it is scoped away from the `@cluster/pools/...` namespace, remains unverified.

### Recommendation
- Do not derive object-pool (or any security-relevant) storage paths solely from low-entropy, externally-observable identifiers such as sequential repository IDs; incorporate a per-repository secret/random component.
- Reject/validate that ordinary repository-creation RPCs cannot target paths inside the `@cluster/pools/...` or `@pools/...` namespaces reserved for object pools, closing off the path-squatting vector even if IDs are guessed.
- Consider a grace/reservation window (already partially achieved via the storage lock in `repoutil.Lock`) that binds a specific caller/transaction identity to a not-yet-existing repository ID before the ID becomes guessable externally, analogous to the `disabled`-flag mitigation adopted upstream in the referenced Story Protocol fix.

### Proof of Concept
Conceptual PoC (concrete confirmation blocked by unavailable file contents for the RPC handlers noted above):
1. Attacker observes/predicts that the next `repositoryID` to be allocated for a target fork/project is `N` (IDs are sequential, e.g. `storage.DeriveReplicaPath`/`DerivePoolPath` tests show ID `1`, `2` map to specific fixed hash-prefixed paths).
2. Attacker computes `poolPath = DerivePoolPath(N)` = `@cluster/pools/<hash prefix>/N`.
3. Attacker issues an ordinary repository-creation RPC (if unrestricted, as could not be fully verified) targeting `poolPath` before the legitimate owner's flow creates repository `N` and calls `CreateObjectPool`.
4. When the legitimate owner's `CreateObjectPool` reaches `repoutil.Create`'s critical section, `os.Stat(targetPath)` finds the attacker's pre-existing directory and returns `AlreadyExists`, permanently blocking object-pool creation for repository `N`.

func deriveDiskPath(prefixDir string, repositoryID int64) string {
	hasher := sha256.New()
	// String representation of the ID is used to make it easier to derive the replica paths with
	// external tools. The error is ignored as the hash.Hash interface is documented to never return
	// an error.
	hasher.Write([]byte(strconv.FormatInt(repositoryID, 10)))
	hash := hasher.Sum(nil)
	return filepath.Join(prefixDir, fmt.Sprintf("%x/%x/%d", hash[0:1], hash[1:2], repositoryID))
}
