## Title
Stale-signature/permission cache in `Manager.processBlock` allows a revoked signer's transaction to execute after mid-block permission changes - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
The GitLab report describes stale authorization state (TODO items pointing at confidential notes) not being invalidated when the underlying permission/membership changes, letting a party who should have lost access still act on outdated authorization. The java-tron analog is the transaction-level signature-verification cache (`TransactionCapsule.isVerified`), which is populated once (either at broadcast time via `pushTransaction`, or in bulk via `preValidateTransactionSign` when a block is received) and is never re-checked once set to `true`, even though a transaction that runs *earlier* in the same block can mutate the very account permission that a *later* transaction's signature validity depends on.

### Finding Description
Signature/permission checks are cached on the `TransactionCapsule` object: [1](#0-0) 

`validateSignature`/`validatePubSignature` only perform the actual permission/weight check `if (!isVerified)`; once `isVerified` is `true` they short-circuit and return `true` unconditionally.

When a block is received from a peer, `processBlock` first runs a **parallel, batched** signature pre-check over all transactions in the block against the account state as it exists *before any transaction in the block has executed*, then loops sequentially and calls `processTransaction` (which itself only re-checks the signature `if (!isVerified)`): [2](#0-1) [3](#0-2) 

Because `preValidateTransactionSign` sets `isVerified=true` on every transaction against the pre-block account/permission state, and the subsequent sequential `processTransaction` call trusts that cached flag instead of re-deriving permission validity from the state as of *its own turn* in the block, a permission-revoking transaction (`AccountPermissionUpdateActuator`, which mutates `AccountCapsule` permissions directly in `AccountStore`) that appears earlier in the block does not retroactively invalidate the cached `isVerified=true` on a later transaction in the same block signed under the now-revoked key/threshold.

The actuator that produces the underlying permission change re-writes permissions unconditionally on execution: [4](#0-3) 

The codebase does contain partial mitigations for related staleness scenarios: `getVerifyTxs` re-verifies transactions whose owner address is in `ownerAddressSet` (multi-sign accounts with a pending permission update) rather than trusting a matching signature blindly, and `switchFork` clears `isVerified` on the transactions of the branch being switched to: [5](#0-4) 

However, these mitigations target the *cross-block* fork-switch and *own-node-mempool-to-block* paths, not the **intra-block, peer-supplied-block** path through `preValidateTransactionSign` → `processBlock`'s sequential `processTransaction` loop, where the batched pre-check happens once against pre-execution state and is never redone per-transaction as the sequential execution mutates account permissions.

### Impact Explanation
If exploitable, an attacker (or an SR building/relaying a block) could order two transactions from the same account within one block: (1) an `AccountPermissionUpdateContract` that revokes a key/lowers its weight below threshold, and (2) a transaction signed with the now-revoked key/insufficient weight. Because the second transaction's signature was already marked `isVerified=true` during the batched, pre-block-state pass, its permission is never re-checked against the account's actual (already-updated) permission set at the moment it executes, allowing an unauthorized signer to move funds/execute an actuator after their authority was revoked within the same block — an unauthorized account operation / theft-of-funds class outcome.

### Likelihood Explanation
This requires control over transaction ordering within a single block (an SR producing the block, or an attacker able to get both transactions accepted and ordered as desired), and depends on the exact call sequence in `preValidateTransactionSign`/`processBlock` versus `AccountPermissionUpdateActuator.execute`. The parallel `ValidateSignTask` referenced by `preValidateTransactionSign` could not be fully inspected in this session (its implementation body was not returned by search), so I could not conclusively confirm whether it reads a live, per-transaction-updated account snapshot or a single upfront snapshot — this is a meaningful open uncertainty that should be verified against the actual `ValidateSignTask`/`RepositoryImpl` sequencing before treating this as confirmed exploitable.

### Recommendation
Ensure that `isVerified` is invalidated (or that permission checks are unconditionally re-run) whenever an account's `Owner`/`Active`/`Witness` permission is modified by a preceding transaction in the same block, not only across fork-switches or mempool re-push. Concretely, `AccountPermissionUpdateActuator.execute` (or `processTransaction`) should force re-validation (`trxCap.setVerified(false)`) for any transaction later in the block queue whose owner address matches an account whose permissions were just modified, mirroring the `ownerAddressSet` mechanism already used in `getVerifyTxs`/`rePush`, but applied to the sequential intra-block `processBlock` execution path as well.

### Proof of Concept
Could not construct a concrete, verified PoC within this session because the exact code of `ValidateSignTask` (and thus whether the parallel pre-check reads a shared, mutating `AccountStore` versus an immutable snapshot) was not retrieved. A full PoC would require: (1) confirming `ValidateSignTask`'s account-lookup source, (2) crafting a block with an `AccountPermissionUpdateContract` transaction followed by a transaction signed by the removed/downweighted key from the same owner, and (3) observing whether `processTransaction` executes the second transaction successfully despite the revoked permission — this should be validated with the full source before treating this finding as conclusively proven.

      //Do not support multi contracts in one transaction
      Transaction.Contract contract = this.getInstance().getRawData().getContract(0);
      if (contract.getType() != ContractType.ShieldedTransferContract) {
        validatePubSignature(accountStore, dynamicPropertiesStore);
      } else {  //ShieldedTransfer
        byte[] owner = getOwnerAddress();
        if (!ArrayUtils.isEmpty(owner)) { //transfer from transparent address
          validatePubSignature(accountStore, dynamicPropertiesStore);
        } else { //transfer from shielded address
          if (this.transaction.getSignatureCount() > 0) {
            throw new ValidateSignatureException("there should be no signatures signed by "
                    + "transparent address when transfer from shielded address");
          }
        }
      }
      isVerified = true;
    }

  public List<TransactionCapsule> getVerifyTxs(BlockCapsule block) {

    if (pendingTransactions.size() == 0) {
      return block.getTransactions();
    }

    List<TransactionCapsule> txs = new ArrayList<>();
    Map<String, TransactionCapsule> txMap = new HashMap<>();
    Set<String> multiAddresses = new HashSet<>(ownerAddressSet);

    pendingTransactions.forEach(capsule -> {
      String txId = Hex.toHexString(capsule.getTransactionId().getBytes());
      if (isMultiSignTransaction(capsule.getInstance())) {
        String address = Hex.toHexString(capsule.getOwnerAddress());
        multiAddresses.add(address);
      } else {
        txMap.put(txId, capsule);
      }
    });

    block.getTransactions().forEach(capsule -> {
      String address = Hex.toHexString(capsule.getOwnerAddress());
      String txId = Hex.toHexString(capsule.getTransactionId().getBytes());
      if (multiAddresses.contains(address) || !isSameSig(capsule, txMap.get(txId))) {
        txs.add(capsule);
      } else {
        capsule.setVerified(true);
      }
    });

    return txs;
  }
