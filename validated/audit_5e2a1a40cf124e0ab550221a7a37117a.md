### Title
Reachable assertion / uncaught RuntimeException in `BandwidthProcessor.useAssetAccountNet` on mismatched contract-type/payload causes DoS - (File: `chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java`)

### Summary
The CVE describes a UPF crash caused by a reachable assertion when the type-tagged field (F-TEID) of a message doesn't actually match the declared/expected value (address family), and this mismatch is not validated before a hard assertion fires. The analogous pattern in java-tron is a place where a transaction's declared `Contract.ContractType` is trusted to imply the shape of its `Any` payload, and unpacking that payload on a mismatch is escalated into an *unchecked* `RuntimeException` that is not declared/caught by the surrounding bandwidth-consumption and transaction-processing call chain.

### Finding Description
`BandwidthProcessor.useAssetAccountNet` is reached for any transaction whose top-level `Contract.getType() == TransferAssetContract`: [1](#0-0) 

It attempts `contract.getParameter().unpack(TransferAssetContract.class)` and, on any exception (including `InvalidProtocolBufferException` from a genuinely mismatched/malformed payload), re-wraps it as `new RuntimeException(ex.getMessage())` and throws it. Unlike the rest of the codebase's contract-handling paths (e.g. actuators' `validate()` methods, which uniformly catch `InvalidProtocolBufferException` and convert it to the *checked* `ContractValidateException`), this method converts the failure into an unchecked exception.

`consume()` in the same class, which calls `useAssetAccountNet`, is declared to throw only `ContractValidateException`, `AccountResourceInsufficientException`, `TooBigTransactionResultException`, `TooBigTransactionException` — it does not declare or handle `RuntimeException`: [2](#0-1) 

`BandwidthProcessor.consume` is invoked as part of bandwidth accounting during transaction validation/execution (`Manager.consumeBandwidth`), which itself sits ahead of/inside the transaction-processing pipeline used both for locally-broadcast transactions and for transactions embedded in blocks being applied (`Manager.processBlock` → `processTransaction`). None of the surrounding call sites list `RuntimeException` in their `catch`/`throws` clauses (see the exhaustive checked-exception catch lists in `Manager.applyBlock`/`switchFork`/`processBlock`): [3](#0-2) [4](#0-3) 

Because the unchecked `RuntimeException` is not part of the declared exception contract of `consume()`, it can propagate past code paths that were only written/tested against the checked exceptions, unlike `ContractValidateException` which is uniformly expected and handled (e.g. in `TronNetDelegate.pushTransaction`): [5](#0-4) 

An attacker only needs to craft a single transaction where `Contract.getType()` is set to `TransferAssetContract` but the `Any` payload is *not* actually a valid `TransferAssetContract` (or is empty/garbage bytes) — a mismatch conceptually identical to the CVE's "declared address family doesn't match the actual F-TEID content."

### Impact Explanation
If the `RuntimeException` from `useAssetAccountNet` reaches a call frame that only catches the enumerated checked transaction-processing exceptions (rather than a blanket `catch (Throwable)`), it will propagate uncaught through that thread. Depending on which thread reaches this code path (e.g. a background transaction-processing/repush thread rather than one of the frames that happens to wrap `applyBlock` in `catch (Throwable throwable)`), this can terminate that thread ungracefully, corrupt in-flight processing state, or in the worst case destabilize block application — a denial-of-service condition analogous to the reachable-assertion crash in the CVE. Even where an outer `catch (Throwable)`/`catch (Exception)` ultimately absorbs it (as in `Wallet.broadcastTransaction`'s final generic catch), the deviation from the codebase's own convention (wrap in `ContractValidateException`) shows this code path was not exercised/tested for malformed-type-vs-payload mismatches, which is exactly the bug class described in the CVE.

### Likelihood Explanation
Reaching this code requires only crafting and broadcasting a single transaction (via the standard broadcast API) with `ContractType.TransferAssetContract` and a non-conforming `Any` payload — trivially producible by any unprivileged client with no special permissions, similar to the CVE's requirement of a single malformed PFCP message from an unprivileged UE/session-establishing entity.

### Recommendation
In `BandwidthProcessor.useAssetAccountNet`, replace the `throw new RuntimeException(ex.getMessage())` with a checked `ContractValidateException` (consistent with how actuators handle `InvalidProtocolBufferException` elsewhere in the codebase), and audit all other `Any.unpack(...)` call sites in resource-processing / consensus-critical paths (outside of actuator `validate()`) for the same unchecked-exception escalation pattern.

### Proof of Concept
1. Construct a `Transaction` whose `raw.contract[0].type = TransferAssetContract` but whose `parameter` (the packed `Any`) is set to a different/incompatible protobuf message (or arbitrary bytes) so that `Any.unpack(TransferAssetContract.class)` throws `InvalidProtocolBufferException`.
2. Sign and broadcast the transaction through the standard HTTP/gRPC broadcast endpoint so it enters `Manager`'s bandwidth-consumption path where `Contract.getType() == TransferAssetContract` routes into `BandwidthProcessor.useAssetAccountNet`.
3. Observe that the unpack failure is converted to an unchecked `RuntimeException` in `chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java` lines 296-298, which is not declared by `consume()`'s throws clause and is not part of the checked-exception set handled by callers such as `TronNetDelegate.pushTransaction`; verify (via targeted unit test or logging) which thread ultimately fails to catch it and terminates/aborts processing.

Note: I was not able to fully trace every call frame between `Manager.consumeBandwidth` and all its callers (some Manager.java method bodies were not retrievable within the available tool budget), so the exact thread/frame where this `RuntimeException` would go fully uncaught (versus being absorbed by a generic `catch (Throwable)`/`catch (Exception)`) could not be conclusively confirmed. A Devin session with full file access would be needed to pinpoint the precise uncaught-crash path or confirm it is always absorbed (in which case this finding would be downgraded).
