### Title
Per-IP QUIC connection rate limiter is trivially bypassed by rotating IPv6 addresses, allowing unstaked attackers to monopolize the shared unstaked connection pool - ([File: streamer/src/nonblocking/connection_rate_limiter.rs])

### Summary
`ConnectionRateLimiter` keys its `TokenBucket` per exact `IpAddr` with no subnet/prefix aggregation, so a single attacker who controls a routed IPv6 prefix (e.g. a `/64`, trivially and cheaply obtainable from any residential/cloud IPv6 allocation) can generate effectively unlimited distinct source addresses. Each fresh address gets its own untouched rate-limit bucket in both `is_allowed`/`register_connection` (per-IP) and the `SwQos` per-peer connection table keyed by `(ip, pubkey)`, letting the attacker capture a disproportionate share of the shared `max_unstaked_connections` pool and evict legitimate single-address senders via LRU pruning.

### Finding Description
In `setup_connection` (`streamer/src/nonblocking/quic.rs:359,483`), before a connection is admitted the server checks `rate_limiter.is_allowed(&incoming.remote_address().ip())` and later `rate_limiter.register_connection(&from.ip())`. `ConnectionRateLimiter` (`streamer/src/nonblocking/connection_rate_limiter.rs:7-50`) wraps a `KeyedRateLimiter<IpAddr>` whose bucket key is the literal `IpAddr` value — there is no normalization to an IPv6 `/56`/`/64` prefix anywhere in `streamer` or `net-utils` (confirmed by absence of any subnet/prefix/`to_canonical` handling in `net-utils/src/token_bucket.rs` or `streamer/src`). The same applies to the per-peer connection cap in `SwQos::cache_new_connection` (`streamer/src/nonblocking/swqos.rs:205-218`), which uses `ConnectionTableKey::new(remote_addr.ip(), conn_context.remote_pubkey)` — again the full literal IP.

Because IPv6 address space allocation is per-prefix (a single customer typically gets a `/64` or larger, i.e. billions of addresses) and QUIC's handshake still completes address-ownership validation for *each* individual address the attacker actually controls (this is not IP spoofing — the attacker legitimately owns/routes the whole prefix), the attacker can open connections from a new address for every handshake. Each new address is unseen by `ConnectionRateLimiter`, so `is_allowed`/`register_connection` returns `true` (`connection_rate_limiter.rs:34-40,42-50`) regardless of how many prior connections the attacker's prefix has made. The same rotation defeats `max_connections_per_unstaked_peer` (default 8, `streamer/src/quic.rs:41`) in `SwQos::try_add_connection` (`streamer/src/nonblocking/swqos.rs:415-438`), since that cap is also keyed by the literal source IP.

The only remaining backstops are the global `overall_connection_rate_limiter` (burst 1000 / 2500 conns/sec, `streamer/src/nonblocking/quic.rs:277-281`) and the aggregate `max_unstaked_connections` cap (default 2000, `streamer/src/quic.rs:48`) enforced in `SwQos::prune_unstaked_connection_table`/`prune_unstaked_connections_and_add_new_connection` (`streamer/src/nonblocking/swqos.rs:241-290`). These do bound total memory/connection growth, so the total accepted unstaked connections stay bounded by `DEFAULT_MAX_UNSTAKED_CONNECTIONS` — but that cap is a shared, oldest-first-pruned pool. Because per-IP/per-peer fairness controls are bypassed, a rotating attacker can occupy the entire 2000-slot unstaked table (respecting only the 2500/sec global admission rate and QUIC handshake cost), continuously evicting older entries (`prune_oldest`) including legitimate single-address senders, well beyond what the 8-connections-per-IP-per-minute design intends.

### Impact Explanation
This is a QoS-evasion finding: the intended fairness invariant ("cap total connections per-peer/ip", stated in the `run_server` comment at `streamer/src/nonblocking/quic.rs:339-340`) is defeated for any attacker with a routed IPv6 prefix, letting them starve legitimate unstaked senders out of the shared unstaked connection table by continuous LRU eviction. It does not cause unbounded memory growth or a crash — the hard cap `DEFAULT_MAX_UNSTAKED_CONNECTIONS` (2000) still holds — but it converts a designed "few connections per source" fairness policy into "whoever churns fastest wins the whole pool," a QoS-capture impact.

### Likelihood Explanation
Feasible for any unprivileged, unstaked remote attacker with a public TPU endpoint and no more than an ordinary routed IPv6 prefix (no spoofing, no privileged access, no stake required). The attack only requires completing genuine QUIC handshakes from many addresses within the attacker's own prefix, which is inexpensive and fully repeatable indefinitely, bounded only by the global `TOTAL_CONNECTIONS_PER_SECOND` (2500/s) admission ceiling.

### Recommendation
Aggregate IPv6 rate-limiting/connection-table keys to a fixed prefix length (e.g. `/64` or `/56`, matching typical single-customer allocation) instead of the full 128-bit address, both in `ConnectionRateLimiter` (`connection_rate_limiter.rs`) and in `ConnectionTableKey` used by `SwQos` (`swqos.rs`), so that address churn within an attacker-controlled prefix no longer resets the rate-limit bucket or per-peer connection cap.

### Proof of Concept
Rust unit/fuzz test plan in `streamer/src/nonblocking/connection_rate_limiter.rs`:
```rust
#[test]
fn test_ipv6_prefix_rotation_evades_per_ip_limit() {
    let limiter = ConnectionRateLimiter::new(8, 8, 4); // default-like config
    let mut allowed_count = 0;
    // Simulate attacker rotating addresses within a single owned /64 prefix
    let base: u128 = 0x2001_0db8_0000_0001_0000_0000_0000_0000;
    for i in 0..1000u128 {
        let ip = IpAddr::V6(Ipv6Addr::from(base + i)); // same /64, distinct full address
        if limiter.register_connection(&ip) {
            allowed_count += 1;
        }
    }
    // Expected (buggy) behavior: nearly all 1000 rotated addresses are admitted,
    // because each gets a fresh TokenBucket entry — demonstrating the per-/64
    // fairness limit (intended ~8/min) is bypassed.
    assert!(allowed_count > 900, "per-IP limiter should have throttled a single /64 prefix, got {allowed_count}");
}
```
A companion integration test in `streamer/src/nonblocking/quic.rs`'s test module would spawn a server with `SwQosConfig::default()` and drive `N` rotated-IPv6 `Connecting` handshakes to show that `open_unstaked_connections`/`num_evictions_unstaked` climbs and evicts a control connection from a single fixed IPv4/IPv6 address that would otherwise remain within its 8-connections-per-minute budget, confirming the fairness bypass while the aggregate `DEFAULT_MAX_UNSTAKED_CONNECTIONS` cap itself remains intact.
