### Title
Silent `long` truncation in `MarketUtils.multiplyAndDivide` BigInteger fallback can corrupt on-chain exchange order fill quantities - (File: `chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java`)

### Summary
The Seaport bug truncates a fraction's numerator/denominator to a smaller integer type when the "safe" multiply/cross-multiply path overflows, silently producing wrong (often 0) values that let an attacker refill/oversell an order. Java-tron's on-chain order matching engine (`MarketSellAssetActuator`) has the same structural weakness: its core price-ratio arithmetic helper `MarketUtils.multiplyAndDivide` falls back to `BigInteger` math on overflow, but converts the final `BigInteger` result back to `long` with `.longValue()` instead of `.longValueExact()`, silently truncating any result that exceeds the 64-bit range instead of reverting.

### Finding Description
`MarketUtils.multiplyAndDivide` is used by `MarketSellAssetActuator.matchSingleOrder` to compute how much of the counter-asset a taker/maker receives, based on cross-multiplying user-supplied order quantities: [1](#0-0) 

```java
public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
  try {
    long tmp = multiplyExact(a, b, disableMath);
    return floorDiv(tmp, c, disableMath);
  } catch (ArithmeticException ex) {
    // do nothing here, because we will use BigInteger to compute again
  }

  BigInteger aBig = BigInteger.valueOf(a);
  BigInteger bBig = BigInteger.valueOf(b);
  BigInteger cBig = BigInteger.valueOf(c);

  return aBig.multiply(bBig).divide(cBig).longValue();
}
```

When `a * b` overflows `long`, the code deliberately switches to `BigInteger` arithmetic "to compute again," but the final line calls `.longValue()`. `BigInteger.longValue()` does not check range — if the true mathematical quotient exceeds `Long.MAX_VALUE`/`Long.MIN_VALUE`, it silently returns the low 64 bits of the value (an arbitrary wrapped/truncated number), exactly the same class of bug as Seaport's `uint120(...)` truncation of an out-of-range fraction.

This helper is invoked in `matchSingleOrder` with three fully user-controlled `int64` quantities taken directly from broadcastable `MarketSellAssetContract` orders stored on-chain (`sellTokenQuantity`, `buyTokenQuantity`, `sellTokenQuantityRemain`): [2](#0-1) [3](#0-2) [4](#0-3) 

`buyTokenQuantity` (the declared price denominator of a maker order) is not required to be backed by any balance — only the `sellTokenQuantity` side is escrowed/checked against the account's real asset/TRX balance. An attacker acting as a maker can therefore freely choose an extreme price ratio (e.g. very large `sellTokenQuantity` with a very small `buyTokenQuantity`, or vice versa), and as a taker choose an extreme `sellTokenQuantityRemain`, to force the `a*b` cross product to overflow `long` and drive the `BigInteger` quotient itself past `Long.MAX_VALUE`, so `.longValue()` silently wraps to an attacker-chosen small/zero/negative-looking value.

### Impact Explanation
A corrupted `takerBuyTokenQuantityRemain`/`makerBuyTokenQuantityReceive` computed this way feeds directly into `matchSingleOrder`'s branch logic that updates `sellTokenQuantityRemain` on both maker and taker `MarketOrderCapsule`s and calls `addTrxOrToken`/`addAssetAmountV2` to credit balances: [5](#0-4) 

A silently truncated/wrapped quantity can: (a) desynchronize the remaining-quantity bookkeeping of an order so it never reaches zero (order can be matched again and again at the same stale price, mirroring the Seaport "continue filling and draining more tokens for the same consideration" exploit), or (b) directly mint/credit an attacker-chosen wrapped `long` value of TRX/TRC10 tokens via `addTrxOrToken`, i.e. an unbacked balance increase. Either outcome is a direct theft-of-funds / unbacked-balance vulnerability reachable by any account that can broadcast a `MarketSellAssetContract` transaction, satisfying the "unauthorized account operation / theft or permanent freezing of funds / unbacked balance" bar.

### Likelihood Explanation
Reaching the vulnerable path requires only broadcasting ordinary `MarketSellAssetContract` transactions — no privileged role, no consensus assumptions, and no dependency on other actors behaving maliciously. The attacker fully controls all three multiplicands (`sellTokenQuantity`, `buyTokenQuantity` on the maker side; `sellTokenQuantityRemain` on the taker side) across two orders they create themselves, so crafting values whose cross-product/quotient exceeds `Long.MAX_VALUE` is a straightforward arithmetic exercise, not a probabilistic or race-dependent condition.

### Recommendation
Replace `.longValue()` with `.longValueExact()` in the `BigInteger` fallback path of `MarketUtils.multiplyAndDivide`, and let the resulting `ArithmeticException` propagate as an order-validation failure (reject the trade) instead of silently wrapping. Additionally, add explicit range/sanity checks on `sellTokenQuantity`/`buyTokenQuantity` at order-creation time (`MarketSellAssetActuator` validate) so that no combination of maker/taker order quantities can produce a cross-product whose true quotient exceeds `Long.MAX_VALUE`.

### Proof of Concept
Conceptual reproduction, based on `MarketUtils.multiplyAndDivide` and `matchSingleOrder`:
1. Attacker creates maker order O1 selling `A` tokens with `sellTokenQuantity = S1` (bounded only by real balance) and `buyTokenQuantity = B1` set to an extremely small value (e.g. `1`), giving an extreme price ratio; `buyTokenQuantity` requires no balance backing.
2. Attacker (or colluding second account) creates a taker order with `sellTokenQuantityRemain = S2` chosen such that `S2 * S1` (the `a*b` cross product in `multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity, makerBuyQuantity, ...)`) overflows `long`, forcing the `BigInteger` fallback, and such that the true quotient `(S2 * S1) / B1` exceeds `Long.MAX_VALUE`.
3. `multiplyAndDivide` returns `aBig.multiply(bBig).divide(cBig).longValue()`, silently truncating the astronomically large true quotient to an arbitrary wrapped `long` (potentially `0`, negative, or a small positive number) instead of throwing.
4. This corrupted value is used in `matchSingleOrder` to update `sellTokenQuantityRemain` and to credit `addTrxOrToken`/`addAssetAmountV2`, letting the attacker either re-trigger matching on an order that should be exhausted or receive a token/TRX credit inconsistent with the real trade, without full arithmetic-level tracing of the exact numeric constants (which would require live BigInteger experimentation against on-chain balance limits) this could not be fully confirmed with a concrete numeric example within the scope of this review.
