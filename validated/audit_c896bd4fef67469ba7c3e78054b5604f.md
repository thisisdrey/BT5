### Title
Unsigned integer underflow in reftable block parsing leads to out-of-bounds slice indexing / DoS - (File: internal/git/reftable/reftable.go)

### Summary
`Table.parseRefBlock` computes the restart-table offset of a reftable ref block directly from an on-disk `RestartCount` field without validating it against the actual size of the block, mirroring the `QuailFinance.sol` bug class where an index/bound is derived from an expected count instead of the real data length. Because the arithmetic is performed on the unsigned `uint` type, a `RestartCount` that is inconsistent with the block's real size causes the subtraction to underflow and wrap to a huge value, which is then used as a loop bound to index into the in-memory `src` byte slice in `getRefsFromBlock`, producing an out-of-bounds slice access.

### Finding Description
`parseRefBlock` reads `RestartCount` straight from file bytes: [1](#0-0) 

`b.RestartStart` is computed as `blockStart + currentBS - 2 - 3*uint(b.RestartCount)`. All operands are `uint`. If `3*RestartCount + 2 > currentBS` (e.g., a corrupted or maliciously-crafted `RestartCount` larger than what the block actually contains), the subtraction underflows and `RestartStart` becomes an enormous value close to `math.MaxUint`.

This value is then used unchecked as the loop bound in `getRefsFromBlock`: [2](#0-1) 

The loop condition `idx < b.RestartStart` will now never terminate at the real end of the block; subsequent reads such as `src[idx]`, `src[idx:idx+suffixLength]`, and hash-size slicing (`src[idx : idx+uint(hashSize)]`) will run past the bounds of the `src` byte slice that was read once via `io.ReadAll(t.src)` in `GetReferences`: [3](#0-2) 

This is structurally identical to the reported Solidity bug class: an index/bound (`winnerIndex` there, `RestartStart` here) is derived from a count value (`numParticipants` / `RestartCount`) that is not cross-checked against the actual size of the collection being indexed (`participants.length` / the real block bytes), so the derived bound can exceed the real data and trigger out-of-range access.

`GetReferences()` (and thus `parseRefBlock`/`getRefsFromBlock`) is invoked when reading references out of a `reftable` file, with call sites in the ref-listing service path and backup code, so it is reachable whenever Gitaly reads references from a repository that uses the reftable backend.

### Impact Explanation
An out-of-range slice index in Go triggers a runtime panic. If this panic occurs inside an RPC-serving goroutine without being converted into a graceful gRPC error, it can crash or abort the handling goroutine, denying service for the RPC (and depending on panic-recovery middleware, potentially the whole `gitaly` process) whenever reference data is parsed from a corrupted or adversarially crafted `.ref` reftable file. This constitutes a DoS impact on a request handler.

### Likelihood Explanation
Exploitability depends on how the corrupted/malicious reftable file gets onto disk. Ordinary reference writes are produced by Git itself, which should not by itself produce a `RestartCount` inconsistent with a block's actual size; I could not confirm within this analysis a concrete unprivileged path (e.g., an untrusted repository import, fork, or replication step) that lets an external actor supply raw, attacker-controlled reftable bytes that Gitaly would parse without prior validation by Git. This makes the likelihood uncertain, and I was not able to fully trace all producers of reftable files (e.g., inter-node replication, backup/restore, or pool imports) within the available context.

### Recommendation
Validate `RestartCount` against the actual block size before using it to compute `RestartStart`: ensure `3*uint(b.RestartCount) + 2 <= currentBS` and reject/return an error otherwise, rather than performing unchecked unsigned subtraction. Additionally, bound-check every derived index/offset (`idx`, `RestartStart`, etc.) against `len(src)` before slicing, instead of trusting length/count fields embedded in the file.

### Proof of Concept
Not independently verified by execution; the underflow condition is analytically derivable from the code path shown above: crafting/corrupting a reftable ref block so that its trailing 2-byte `RestartCount` value satisfies `3*RestartCount + 2 > currentBS` (the block's own encoded length) will cause `b.RestartStart` in `parseRefBlock` to underflow, and the subsequent loop in `getRefsFromBlock` to index past the end of the in-memory `src` slice, panicking during `Table.GetReferences()`.
