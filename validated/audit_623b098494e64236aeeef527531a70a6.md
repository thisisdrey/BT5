Based on my analysis, I found a concrete local analog of the reported bug class: a checks-effects-interactions violation in the bridge messages pallet's inbound lane, where the delivered-message state is persisted to storage *after* the external dispatch call rather than before it.

### Title
Inbound bridge lane persists delivered-nonce/relayer state after external message dispatch, enabling nonce-replay via dispatch reentrancy - (File: `bridges/modules/messages/src/inbound_lane.rs`)

### Summary
`InboundLane::receive_message` checks the expected nonce against locally-loaded lane data, then calls the pluggable `Dispatch::dispatch` hook, and only *afterwards* persists the updated relayer/nonce bookkeeping to storage via `self.storage.set_data(data)`. This mirrors exactly the reported anti-pattern ("nonce incremented after external call, not before") — the effect (recording that nonce `N` was delivered) is applied after the interaction (dispatch), not before it. [1](#0-0) 

### Finding Description
In `receive_message`, the nonce check reads a **local** copy of `InboundLaneData` fetched at function entry (`let mut data = self.storage.data();`), verifies `Some(nonce) == data.last_delivered_nonce().checked_add(1)`, then calls `Dispatch::dispatch(...)`, and only afterward mutates the local `data.relayers` and calls `self.storage.set_data(data)` to persist it. [2](#0-1) [3](#0-2) 

`Dispatch` is the generic, pallet-supplied `T::MessageDispatch` hook. For XCM-based lanes (`pallet-xcm-bridge-hub`), `dispatch()` forwards the payload to `T::BlobDispatcher::dispatch_blob`, which in turn calls `send_xcm` to route the message onward. [4](#0-3) 

The message-processing infrastructure in the codebase explicitly anticipates that dispatch of a message can be recursive/reentrant — `pallet-message-queue`'s `service_page_item` persists `Pages`/`BookStateFor` to storage *before* invoking `process_message_payload`, specifically commented as protection "for the case that `process_message_payload` is recursive," and reloads state afterward to observe any nested changes. [5](#0-4) 

`InboundLane::receive_message` does not follow this same defensive pattern: it defers the storage write until *after* dispatch completes, leaving the not-yet-committed `last_delivered_nonce` invisible to any nested/reentrant invocation of `receive_messages_proof` that occurs as a side effect of dispatch (e.g. via an XCM `Transact` instruction executed synchronously inside the dispatched payload, as XCM messages are processed synchronously through `XcmExecutor::execute` when routed through `ProcessXcmMessage`). [6](#0-5) 

This is precisely the class of bug in the external report: the authorization check (nonce/signature validity) happens correctly up front, but the state that prevents *replay* of that same authorization is written only after the external call returns — during which the external call can loop back and re-trigger the same code path while the old, pre-update state is still visible in storage.

### Impact Explanation
If any configured `MessageDispatch` implementation can, directly or transitively, cause re-entry into `receive_messages_proof` for the same lane before the outer call's `self.storage.set_data(data)` executes, the same message nonce could be accepted and dispatched twice (or an out-of-order/duplicate `ReceptionResult::Dispatched` could be recorded), leading to duplicate settlement of whatever action the message performs (e.g. duplicate asset transfer/mint on the receiving side, double relayer reward accounting) — directly matching the "duplicate settlement or payout" and "message queues... must only advance after decode, dispatch, execution, and settlement succeed atomically" impact categories.

### Likelihood Explanation
Likelihood is bounded by whether any deployed `T::MessageDispatch` for a bridge-messages lane can synchronously re-enter `receive_messages_proof`. The only production dispatcher found in this repository (`pallet-xcm-bridge-hub`'s `MessageDispatch::dispatch`) forwards to `send_xcm`, which enqueues the message for later/asynchronous delivery rather than executing it synchronously in the current call stack — this specific configuration does not appear directly reachable today. The vulnerability is therefore a structural checks-effects-interactions ordering flaw that is exploitable only if a `MessageDispatch` implementation performs synchronous, potentially attacker-influenced execution before the pallet persists delivery state — a precondition on pluggable runtime configuration rather than a currently-exercised path in the audited dispatcher.

### Recommendation
Move the `self.storage.set_data(data)` call (recording the incremented `last_delivered_nonce`/relayer bookkeeping) to occur *before* invoking `Dispatch::dispatch`, mirroring the pattern already used in `pallet-message-queue::service_page_item`, which persists `Pages`/`BookStateFor` prior to calling the message processor specifically to guard against reentrant/recursive dispatch. This ensures any nested re-entry into `receive_messages_proof` observes the updated nonce and is rejected by the `InvalidNonce` check.

### Proof of Concept
1. Configure a bridge-messages lane with a `MessageDispatch::dispatch` implementation whose downstream processing can synchronously re-invoke `pallet_bridge_messages::Pallet::receive_messages_proof` for the same lane (e.g. a `Transact`-carrying XCM payload executed synchronously against a runtime that permits the bridge's sovereign/relayer origin to call `receive_messages_proof`).
2. Submit a proof containing message with `nonce = N + 1` (valid next nonce).
3. `receive_message` loads `data` (with `last_delivered_nonce = N`), passes the nonce check, and calls `Dispatch::dispatch`.
4. Inside `dispatch`, the crafted payload triggers a nested call to `receive_messages_proof` with a proof for the *same* nonce `N + 1` again.
5. Because `self.storage.set_data(data)` from step 3's original call has not yet executed, on-chain storage still shows `last_delivered_nonce = N`, so the nested call's nonce check passes again, and the message is dispatched a second time.
6. Whatever side effect the message performs (asset unlock, mint, XCM execution) is settled twice for a single relayed proof.

	pub fn receive_message<Dispatch: MessageDispatch<LaneId = S::LaneId>>(
		&mut self,
		relayer_at_bridged_chain: &S::Relayer,
		nonce: MessageNonce,
		message_data: DispatchMessageData<Dispatch::DispatchPayload>,
	) -> ReceptionResult<Dispatch::DispatchLevelResult> {
		let mut data = self.storage.data();
		if Some(nonce) != data.last_delivered_nonce().checked_add(1) {
			return ReceptionResult::InvalidNonce;
		}

		// if there are more unrewarded relayer entries than we may accept, reject this message
		if data.relayers.len() as MessageNonce >= self.storage.max_unrewarded_relayer_entries() {
			return ReceptionResult::TooManyUnrewardedRelayers;
		}

		// if there are more unconfirmed messages than we may accept, reject this message
		let unconfirmed_messages_count = nonce.saturating_sub(data.last_confirmed_nonce);
		if unconfirmed_messages_count > self.storage.max_unconfirmed_messages() {
			return ReceptionResult::TooManyUnconfirmedMessages;
		}

		// then, dispatch message
		let dispatch_result = Dispatch::dispatch(DispatchMessage {
			key: MessageKey { lane_id: self.storage.id(), nonce },
			data: message_data,
		});

		// now let's update inbound lane storage
		match data.relayers.back_mut() {
			Some(entry) if entry.relayer == *relayer_at_bridged_chain => {
				entry.messages.note_dispatched_message();
			},
			_ => {
				data.relayers.push_back(UnrewardedRelayer {
					relayer: relayer_at_bridged_chain.clone(),
					messages: DeliveredMessages::new(nonce),
				});
			},
		};
		self.storage.set_data(data);

		ReceptionResult::Dispatched(dispatch_result)
	}

	fn dispatch(
		message: DispatchMessage<Self::DispatchPayload, Self::LaneId>,
	) -> MessageDispatchResult<Self::DispatchLevelResult> {
		let payload = match message.data.payload {
			Ok(payload) => payload,
			Err(e) => {
				tracing::error!(
					target: LOG_TARGET,
					error=?e,
					lane_id=?message.key.lane_id,
					message_nonce=?message.key.nonce,
					"dispatch - payload error"
				);
				return MessageDispatchResult {
					unspent_weight: Weight::zero(),
					dispatch_level_result: XcmBlobMessageDispatchResult::InvalidPayload,
				};
			},
		};
		let dispatch_level_result = match T::BlobDispatcher::dispatch_blob(payload) {
			Ok(_) => {
				tracing::debug!(
					target: LOG_TARGET,
					lane_id=?message.key.lane_id,
					message_nonce=?message.key.nonce,
					"dispatch - `DispatchBlob::dispatch_blob` was ok"
				);
				XcmBlobMessageDispatchResult::Dispatched
			},
			Err(e) => {
				tracing::error!(
					target: LOG_TARGET,
					error=?e,
					lane_id=?message.key.lane_id,
					message_nonce=?message.key.nonce,
					"dispatch - `DispatchBlob::dispatch_blob` failed"
				);
				XcmBlobMessageDispatchResult::NotDispatched(Some(e))
			},
		};
		MessageDispatchResult { unspent_weight: Weight::zero(), dispatch_level_result }
	}
