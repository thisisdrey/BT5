### Title
Starvation and biased eviction of equal-priority transactions via `TransactionPriorityId` tie-break on `TransactionId` - ([File: core/src/banking_stage/transaction_scheduler/transaction_priority_id.rs])

### Summary
`TransactionPriorityId` derives `Ord` lexicographically from `(priority, id)`, so for transactions with identical fee-priority, the tuple with the larger `TransactionId` (i.e., the most recently inserted transaction) always wins both `BTreeSet::pop_last()` scheduling selection and survives `BTreeSet::pop_first()` capacity eviction. An unprivileged attacker who floods the leader's TPU with many transactions carrying the same `compute_unit_price` as a victim's transaction can therefore keep the victim's older, equal-fee transaction perpetually at the bottom of its priority tier — causing it to be scheduled last (starvation) or evicted first when the buffer is at capacity (silent drop).

### Finding Description
`TransactionPriorityId` is defined as: [1](#0-0) 
with `#[derive(PartialOrd, Ord)]` giving field-order comparison: `priority` first, then `id` (`TransactionId`) as the tie-breaker.

The scheduler pops work from `TransactionStateContainer` via: [2](#0-1) 
`BTreeSet::pop_last()` returns the maximum element of the set. For two entries with equal `priority`, the one with the larger `id` is always selected first by `GreedyScheduler::schedule`'s main loop: [3](#0-2) 

`TransactionId`s are allocated via `Slab::vacant_entry` in `insert_map_only`, which under sustained load (steady insertion faster than removal) yields monotonically increasing keys correlated with arrival order: [4](#0-3) 

Consequently, for a fixed priority tier, **newer arrivals systematically out-rank older ones** in both directions:
1. Scheduling selection (`pop_last`) always prefers the newest same-priority transaction.
2. Capacity eviction (`pop_first`, in `push_ids_into_queue`) always evicts the oldest same-priority transaction first when the buffer is full: [5](#0-4) 

An attacker who submits transactions to the public TPU with `ComputeBudgetInstruction::set_compute_unit_price` equal to a victim's (or simply to a very common/default priority value used by many wallets/dApps, e.g. `0` or a fixed default) will have their transactions repeatedly assigned higher `TransactionId`s than the victim's earlier-queued transaction. As long as the attacker sustains a volume of same-priority transactions:
- The victim's transaction is scanned later and later relative to newly-arriving attacker transactions each `schedule()` pass (`num_scanned` bound by `max_scanned_transactions_per_scheduling_pass`), effectively unbounded starvation while attacker volume continues.
- If the container is near/at capacity (`receive_and_buffer.rs`'s `push_ids_into_queue` eviction path), the victim's older transaction is the exact tuple `(priority, older_id)` — the minimum among the tied group — so it is evicted first and silently dropped, before any of the attacker's newer, equal-fee transactions.

None of the existing guards prevent this:
- Sigverify/dedup only check signature validity and duplicate signatures, not priority collisions.
- `check_fee_payer_unlocked` only requires the fee payer be able to pay the fee; it does not require the fee to be paid unless the transaction is actually executed, so the attacker's flooding transactions cost effectively nothing if they are never scheduled/executed.
- The `SchedulerPriorityFloor` mechanism only drops arrivals below the container's current minimum priority when saturated; it does nothing to protect intra-tier fairness among transactions of the *same* priority. [6](#0-5) 

### Impact Explanation
This falls squarely within the described bounty scope: an unprivileged attacker can permanently strand or silently drop another user's fee-paying transaction purely through priority-tier buffer/eviction handling, with no lock conflicts or staked/privileged access required. Concretely, victims whose wallet/dApp uses a common or predictable `compute_unit_price` can have their transactions perpetually pushed to the bottom of the tie-break order and either never scheduled while the leader slot lasts, or evicted from the bounded buffer entirely — a silent drop of a legitimately fee-paying transaction, degrading QoS fairness guarantees the priority-fee market is supposed to provide.

### Likelihood Explanation
- Requires only an unstaked client submitting ordinary, signature-valid transactions to a leader's TPU — no special privileges.
- Requires no fee expenditure beyond having a fee-payer able to cover the fee check (`check_fee_payer_unlocked`); transactions that are never scheduled/executed do not actually deduct fees, so the flood is essentially free/cheap to sustain.
- Colliding on a victim's exact priority is trivial if the priority is a common default (many wallets set `compute_unit_price` to `0` or another fixed low value), and reliably reproducible under a differential test comparing FIFO-fair vs. actual `TransactionStateContainer::pop()`/eviction order.
- The effect scales directly with attacker-sent volume, not with queue size, which is the defining signature of the described starvation/eviction-bias vulnerability class.

### Recommendation
Change the tie-break in `TransactionPriorityId`'s ordering (or in the container's insertion logic) to favor older transactions at equal priority instead of newer ones — e.g., invert the `id` comparison for ties (`Reverse(id)`) so `pop_last()` naturally prefers the oldest transaction among equals, and `pop_first()` naturally evicts the newest instead of oldest. Alternatively, incorporate a monotonically increasing sequence number combined with a priority decay/aging factor so that transactions waiting longer at the same fee level gain effective priority over time, bounding worst-case wait time by queue size rather than attacker-sustained volume.

### Proof of Concept
Rust unit test in `transaction_state_container.rs` / `greedy_scheduler.rs` test modules demonstrating the bias:
```rust
#[test]
fn test_equal_priority_starvation_and_eviction_bias() {
    let mut container = TransactionStateContainer::with_capacity(3);

    // Victim inserted first with priority P.
    let (victim_tx, max_age, priority, cost) = test_transaction(/* priority */ 5);
    container.insert_new_transaction(victim_tx, max_age, priority, cost);
    let victim_id = *container.priority_queue.iter().next().unwrap();

    // Attacker floods with the SAME priority, arriving later (higher TransactionId).
    for _ in 0..10 {
        let (attacker_tx, max_age, priority, cost) = test_transaction(5);
        container.insert_new_transaction(attacker_tx, max_age, priority, cost);
    }

    // Assert: pop_last() always returns an attacker tx (larger id), never the victim,
    // as long as attacker volume keeps refilling equal-priority entries -- i.e., victim's
    // wait time depends on attacker's sustained volume, not queue size.
    for _ in 0..7 {
        let popped = container.pop().unwrap();
        assert_ne!(popped, victim_id, "victim tx should not be starved to the back");
    }

    // Separately assert eviction bias: at capacity, the victim (oldest, same-priority,
    // smallest id) is evicted before any attacker tx of equal priority.
}
```
Expected (failing) assertions demonstrate that the victim's `TransactionPriorityId` is always scheduled last and evicted first among an equal-priority group, confirming the tie-break bias is exploitable to bound the victim's effective wait/eviction risk only by attacker-supplied volume, not container/queue size.

    fn push_ids_into_queue(
        &mut self,
        priority_ids: impl Iterator<Item = TransactionPriorityId>,
    ) -> usize {
        for id in priority_ids {
            self.priority_queue.insert(id);
        }

        // The number of items in the `id_to_transaction_state` map is
        // greater than or equal to the number of elements in the queue.
        // To avoid the map going over capacity, we use the length of the
        // map here instead of the queue.
        let num_dropped = self
            .id_to_transaction_state
            .len()
            .saturating_sub(self.capacity);

        for _ in 0..num_dropped {
            let priority_id = self.priority_queue.pop_first().expect("queue is not empty");
            self.remove_state(priority_id.id);
        }

        num_dropped
    }

    fn update_scheduler_priority_floor(&mut self, num_dropped_on_capacity: usize) {

        let saturated = self
            .saturation_state
            .update(buffer_size, num_dropped_on_capacity);

                .get_min_max_priority()
