### Title
Out-of-bounds heap read parsing crafted ZIP central directory entries in ijar - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses attacker-controlled central directory records of a JAR/ZIP file (`file_name_length`, `extra_field_length`, `file_comment_length`, and nested extra-field `data_size`) and advances a raw pointer `p`/`extra_p` through the mmap'd input buffer using these fields, with no bounds check against the actual mapped file length, unlike the sibling function `ProcessLocalFileEntry` which calls `EnsureRemaining()` before every pointer advance/memcpy. This mirrors the class of bug in CVE-2017-12456, where `read_symbol_stabs_debugging_info` trusted attacker-supplied length fields in a crafted binary and read past the allocated buffer.

### Finding Description
`ProcessCentralDirEntry` reads the compressed/uncompressed size, `file_name_length`, `extra_field_length`, `file_comment_length`, `attr`, and `offset` fields directly from the mmap'd file, then:
- `memcpy(filename, p, len)` where `len` is derived from `file_name_length` [1](#0-0) 
- advances `p += file_name_length` and `p += extra_field_length`, then walks a nested extra-field loop using an attacker-controlled `data_size` with no upper bound check [2](#0-1) 

None of these operations call `EnsureRemaining()`, the helper that exists specifically to bound-check reads against `input_file_->Length()`: [3](#0-2) . Contrast this with `ProcessLocalFileEntry`, which does call `EnsureRemaining()` before every length-based advance: [4](#0-3) .

The only aggregate check performed before entering the per-entry loop is in `FindZipCentralDirectory`, which verifies that `cd.central_dir_offset + cd.central_dir_size <= in_length` [5](#0-4) . This bounds the *declared* central directory region as a whole but does not validate that any individual entry's declared `file_name_length`/`extra_field_length`/`file_comment_length` stays within that declared `central_dir_size`, nor within the mmap'd file. A crafted jar with a central directory entry whose length fields are inflated beyond the remaining bytes causes `p`/`extra_p` to walk past the mapped region, and the `memcpy` and `get_u2le`/`get_u4le`/`get_u8le` reads in the extra-field loop then read out-of-bounds heap memory adjacent to the mmap'd buffer.

This function is invoked both from `InputZipFile::ProcessNext` (used when actually extracting/stripping the jar) [6](#0-5)  and from `InputZipFile::CalculateOutputLength`, which is called on every jar ijar processes to size the output buffer [7](#0-6) .

### Impact Explanation
`ijar` is a production binary invoked by Bazel's Java rules to strip method bodies from a jar into an interface jar, exposed to Starlark via `java_common.run_ijar(jar=...)` (documented in `docs/versions/*/rules/lib/toplevel/java_common.mdx`, "Runs ijar on a jar..."). The `jar` argument can be a prebuilt/imported jar originating from an external dependency (e.g., a `java_import` target whose jar was fetched from an untrusted URL/registry and only integrity-checked as an opaque byte blob). Because the sha256/integrity check only verifies the whole-file hash and not the internal structural invariants of the ZIP format, an attacker who controls the served jar content (while still matching a legitimate-looking or otherwise-permitted archive) can craft central directory records with out-of-range length fields that ijar will trust unconditionally, producing an out-of-bounds heap read in the Bazel-run native tool process. Depending on heap layout this can crash the build (worker/build failure) or copy adjacent heap bytes into the `filename` buffer that is subsequently used in output ("Accept"/further processing), risking information disclosure or corrupted output jar structure.

### Likelihood Explanation
Any repository or Java rule that runs `ijar`/`run_ijar` on a jar sourced from a dependency URL, registry module, or other externally-fetched artifact reaches this code path automatically as part of normal Java compilation/import (interface jar generation), requiring no unusual build configuration or flags — only that the input jar's central directory records contain oversized `file_name_length`/`extra_field_length`/`file_comment_length`/extra-field `data_size` values, which is trivial for a hostile origin server to construct while still matching a required content hash if the attacker also controls the initial version served before pinning, or via any mirror/URL rotation scenario.

### Recommendation
Add bounds checks in `InputZipFile::ProcessCentralDirEntry` (and its extra-field parsing loop) analogous to `EnsureRemaining()` used in `ProcessLocalFileEntry`: validate that `p + file_name_length`, `p + extra_field_length`, and each extra-field's `data_size` remain within `zipdata_in_ + input_file_->Length()` (and within the declared `central_dir_size`) before dereferencing or memcpy'ing, returning an error instead of continuing to parse on overflow.

### Proof of Concept
Construct a minimal ZIP/JAR whose End-Of-Central-Directory declares a small `central_dir_size`/`central_dir_offset` that passes the `FindZipCentralDirectory` aggregate check, but whose single Central Directory Header entry declares `file_name_length` (and/or `extra_field_length`) large enough that `p`/`extra_p` walks past the actual mmap'd file end (similar in structure to the existing `CreateZipWithMalformedExtraField` test helper in `output_jar_simple_test.cc`, but targeting `InputZipFile::ProcessCentralDirEntry`/`CalculateOutputLength` in `zip.cc` rather than `output_jar.cc`'s already-guarded extra-field copy path [8](#0-7) ). Run `ijar` (or `java_common.run_ijar`) on this crafted jar; a new JUnit/BuildIntegrationTestCase invoking `ijar` on such a file under ASan would demonstrate the heap-buffer-overflow read reported at the `memcpy`/`get_u2le` calls in `ProcessCentralDirEntry`.

bool InputZipFile::ProcessNext() {
  // Process the next entry in the central directory. Also make sure that the
  // content pointer is in sync.
  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }
  u4 signature = get_u4le(p);
  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}

u8 InputZipFile::CalculateOutputLength() {
  const u1* current = central_dir_;

  u8 compressed_size = 0;
  u8 uncompressed_size = 0;
  u8 skipped_compressed_size = 0;
  u4 attr;
  u8 offset;
  char filename[PATH_MAX];

  while (true) {
    u8 file_compressed, file_uncompressed;
    if (!ProcessCentralDirEntry(current,
                                &file_compressed, &file_uncompressed,
                                filename, PATH_MAX, &attr, &offset)) {
      break;
    }

    if (processor->Accept(filename, attr)) {
      compressed_size += (u8) file_compressed;
      uncompressed_size += (u8) file_uncompressed;
    } else {
      skipped_compressed_size += file_compressed;
    }
  }

  // The worst case is when the output is simply the input uncompressed. The
  // metadata in the zip file will stay the same, so the file will grow by the
  // difference between the compressed and uncompressed sizes.
  return (u8) input_file_->Length() - skipped_compressed_size
      + (uncompressed_size - compressed_size);
}

  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);

  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
