### Title
Unsafe floating-point Bancor pricing math is the default TRC10 Exchange calculation path, enabling systematic value extraction from Exchange pools - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
Moonwell's root cause was a pricing formula that silently used an imprecise/incomplete calculation (ratio without the required multiplication) instead of a materially "safe" one, and this bad value was reachable by any caller (a liquidation bot) with no sanity gate stopping it. java-tron's TRC10 Exchange subsystem has an analogous structural pattern: token pricing for `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` is computed by a `Processor` interface that has two implementations - a `double`-based `ExchangeProcessor` (imprecise floating point Bancor curve math) and a `BigDecimal`-based `SafeExchangeProcessor`. Which one actually executes on-chain is selected by the `allowHarden()` / `allowHardenExchangeCalculation()` dynamic-property flag, not by any per-transaction validation of the resulting price. Any unprivileged account holding TRX/TRC10 balances can call these actuators directly.

### Finding Description
`ExchangeCapsule.transaction()` selects the pricing engine purely based on a global feature flag: [1](#0-0) 

When the flag is not enabled, `ExchangeProcessor` computes the bonding-curve relay/output amounts using native `double` arithmetic and floating-point `pow`: [2](#0-1) 

Only the alternate, hardened path (`SafeExchangeProcessor`) performs the equivalent computation with `BigDecimal` at fixed scale/rounding: [3](#0-2) 

Crucially, there is no independent sanity check performed on the resulting `anotherTokenQuant` before it is applied to account balances and exchange reserves in `ExchangeTransactionActuator.execute()` - the actuator trusts whatever the selected `Processor` returns and immediately credits/debits accounts: [4](#0-3) 

This mirrors the Moonwell defect structurally: the "correct" (safe/complete) computation exists in the codebase (`SafeExchangeProcessor`, analogous to the correctly-composed `cbETH/ETH * ETH/USD`), but the code path actually exercised for a live transaction depends on a switch that defaults to the unsafe/incomplete computation (`ExchangeProcessor`, analogous to the deployed `cbETH/ETH`-only feed), and nothing in the transaction-processing pipeline independently verifies the output price/quantity before it is used to move real value between accounts. The `allowHarden()` flag is a chain-wide committee-governed parameter (`ProposalUtil`/`DynamicPropertiesStore`), so any TRC10 Exchange pair created and used while that hardening parameter has not been activated by governance is, by construction, priced with the imprecise `double`/`Math.pow` formula.

Floating-point `pow`/division on `double` is not exact and does not round consistently at scale; repeated calls with carefully chosen `sellTokenQuant` values against small or freshly-adjusted `firstTokenBalance`/`secondTokenBalance` pairs (via `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, which also branch on the same flag for their integer-only paths) can accumulate rounding bias in the caller's favor across many transactions, extracting real TRX/TRC10 value from the pool's other liquidity providers - functionally the same "wrong number gets trusted and immediately acted on" failure mode as the rekt report, just triggered by floating-point drift instead of a missing multiplicand.

### Impact Explanation
If exploited, an attacker can drain real TRX/TRC10 balances from an Exchange pool's other token side by repeatedly executing `ExchangeTransactionContract` calls that are individually valid but collectively biased by floating-point rounding error, resulting in unauthorized transfer of value out of the pool and into the attacker's account - a concrete unauthorized account operation / theft of funds as required by the validation criteria. This is reachable from a single signed transaction by any account, with no privileged role required.

### Likelihood Explanation
Likelihood depends on whether `allowHardenExchangeCalculation` is active on a given network/pool. Where it is not (the code's structural default absent governance action), every `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` call against that pair uses the `double`-based `ExchangeProcessor`. Actually engineering profitable drift requires precise control of trade sizes relative to reserve balances and many iterations, so this is not a one-shot four-minute drain like Moonwell, but it is a continuously reachable, unprivileged, and repeatable path with no on-chain guard preventing it.

### Recommendation
- Make `SafeExchangeProcessor` (BigDecimal, fixed rounding) the sole/default pricing engine for all Exchange actuators, removing the `double`/`Math.pow` code path entirely rather than gating it behind an optional governance flag.
- Add an explicit sanity/invariant check inside `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` that verifies the constant-product/bonding-curve invariant holds (within a strict tolerance) after each trade, rejecting the transaction if the computed price deviates unexpectedly, rather than trusting the `Processor` output unconditionally.
- Audit `ExchangeInjectActuator`'s non-hardened path (`floorDiv(multiplyExact(...))` on primitive `long`) for the same category of precision/rounding issues relative to its `BigInteger`-based validation counterpart.

### Proof of Concept
1. Attacker (unprivileged account) creates or locates a TRC10 Exchange pair on a network segment where `allowHardenExchangeCalculation` has not been enabled by committee proposal.
2. Attacker repeatedly submits `ExchangeTransactionContract` transactions with `tokenQuant` values chosen to bias the `double`-based `exchangeToSupply`/`exchangeFromSupply` rounding in `ExchangeProcessor.exchange()` in their favor.
3. Each transaction is individually accepted by `ExchangeTransactionActuator.doValidate()`/`execute()` since it only checks `anotherTokenQuant >= tokenExpected`, not overall pool-value conservation.
4. Over many iterations, the attacker's account accumulates more of the counter-token than the constant-product invariant should allow, at the expense of the pool/other liquidity holders — direct value extraction with no privileged access required.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
