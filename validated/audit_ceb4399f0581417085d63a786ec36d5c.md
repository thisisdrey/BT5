## Title
Unbounded growth of `RemoteList.badRemotes` causes linear/quadratic-cost re-scans on every handshake retry, enabling a remote CPU-exhaustion DoS - (File: `remote_list.go`)

### Summary
This maps the "iteration through the whole storage array" bug class from the audited contract (unbounded `userLocks`/`userEarnings` arrays walked on every `withdraw()`) to nebula's `RemoteList.badRemotes` slice, which is appended to by `BlockRemote()` and linearly scanned by `unlockedIsBad()` on every subsequent call and rebuild, with no maximum size enforced.

### Finding Description
`RemoteList.BlockRemote` appends the offending UDP address to `r.badRemotes` after checking `unlockedIsBad`, which performs a full `slices.Contains` linear scan of the entire slice: [1](#0-0) 

`unlockedIsBad` itself is the O(n) scan used both here and (per its doc comment) during dedupe/collect on rebuild: [2](#0-1) 

There is no cap on the size of `badRemotes` anywhere in `remote_list.go` — it only shrinks to `nil` when a handshake with that peer fully completes (`RefreshFromHandshake`) or is manually reset (`ResetBlockedRemotes`): [3](#0-2) 

An attacker who does not hold a valid CA-signed certificate can still send spoofed UDP handshake-stage traffic from many different source `netip.AddrPort` values while a legitimate handshake to a given vpnAddr is pending. Each such "wrong host responded" event triggers `BlockRemote` (as exercised by `TestHandshakeWrongResponderPacketStore`, which shows `evil`'s address being tracked as blocked in `pendingHI.RemoteAddrs`/`badRemotes` while the real handshake to `them` is still outstanding): [4](#0-3) 

Because the pending-handshake window is retried repeatedly by `HandshakeManager.handleOutbound` (`OutboundHandshakeTimer` retry loop, up to `hm.config.retries` attempts, each iterating `hostinfo.remotes.ForEach`/rebuild): [5](#0-4) [6](#0-5) 

an attacker can keep the handshake pending (e.g. by never letting the real peer's response land first, or by racing it) while flooding spoofed "wrong responder" packets from many distinct source addresses, each one growing `badRemotes` by one entry and making every subsequent `unlockedIsBad` check (called on every new blocked-address attempt and on every `Rebuild`/`unlockedCollect` pass triggered by the retry loop) proportionally more expensive. This is structurally identical to the audited contract iterating the full `userLocks[onBehalfOf]` array on every `withdraw()` — an attacker-growable, unbounded array that is repeatedly walked in full on a hot path.

### Impact Explanation
Sustained spoofed traffic against one or more pending handshakes can drive `badRemotes` to a large size, making the per-packet/per-retry linear scans in `BlockRemote`/`unlockedIsBad` (and the rebuild/dedupe pass that also has to account for blocked entries) increasingly expensive. Since this runs on the handshake hot path under the `HandshakeHostInfo` lock, it can degrade legitimate handshake throughput and CPU usage for the process handling that host's pending handshakes — a remote, unauthenticated CPU-exhaustion / DoS vector against a specific victim vpnAddr's handshake state.

### Likelihood Explanation
Reachability does not require a CA-signed certificate: it only requires the ability to send UDP packets that reach the responder while a legitimate handshake to the target vpnAddr is outstanding, using spoofed source `netip.AddrPort` values to defeat the `unlockedIsBad` de-dup check (each new spoofed address is a new distinct entry). This is a plausible but not fully proven-in-full-detail DoS: I could not, within the tool budget, confirm the exact cost of `unlockedCollect`'s treatment of `badRemotes` during `Rebuild`, nor measure a concrete growth ceiling/rate limit elsewhere in the handshake path (e.g., whether `AllowUnknownVpnAddr`/`AllowAll` remote allow-lists or per-source rate limiting already bound this in practice). This uncertainty should be verified before treating this as a confirmed, high-severity finding.

### Recommendation
Bound `RemoteList.badRemotes` to a fixed maximum size (mirroring `MaxRemotes` used elsewhere in this file), evicting oldest entries once the cap is reached, and/or replace the linear `slices.Contains` scan in `unlockedIsBad` with a set-based lookup so blocking cost does not scale with the number of previously-seen bad remotes.

### Proof of Concept
1. Initiate a handshake from host A to host B for vpnAddr V (A has no established tunnel yet, handshake is pending in `HandshakeManager.indexes`).
2. From an attacker-controlled position (no valid CA-signed certificate needed), send repeated forged handshake-stage-2 style UDP replies to A, each from a distinct spoofed source `netip.AddrPort`, that complete the noise exchange but resolve to the "wrong host" (a cert that doesn't match the vpnAddr A is trying to reach) — analogous to the `evil` party flow in `TestHandshakeWrongResponderPacketStore`.
3. Each such event calls `RemoteList.BlockRemote` with a new address, growing `badRemotes` by one entry per attempt (as long as the real peer's completion doesn't arrive to trigger `RefreshFromHandshake`/clear the list).
4. Repeat at high rate/many distinct spoofed addresses while keeping the real handshake from completing (e.g., by racing or dropping the real reply at a lower layer); observe increasing CPU cost in `unlockedIsBad`/rebuild calls tied to the size of `badRemotes`, and correspondingly increased handshake-processing latency for host A.

// BlockRemote locks and records the address as bad, it will be excluded from the deduplicated address list
func (r *RemoteList) BlockRemote(bad ViaSender) {
	if bad.IsRelayed {
		return
	}

	r.Lock()
	defer r.Unlock()

	// Check if we already blocked this addr
	if r.unlockedIsBad(bad.UdpAddr) {
		return
	}

	// We copy here because we are taking something else's memory and we can't trust everything
	r.badRemotes = append(r.badRemotes, bad.UdpAddr)

	// Mark the next interaction must recollect/dedupe
	r.shouldRebuild = true
}

// RefreshFromHandshake locks and updates the RemoteList to account for data learned upon a completed handshake
func (r *RemoteList) RefreshFromHandshake(vpnAddrs []netip.Addr) {
	r.Lock()
	r.badRemotes = nil
	r.vpnAddrs = make([]netip.Addr, len(vpnAddrs))
	copy(r.vpnAddrs, vpnAddrs)
	r.Unlock()
}

// ResetBlockedRemotes locks and clears the blocked remotes list
func (r *RemoteList) ResetBlockedRemotes() {
	r.Lock()
	r.badRemotes = nil
	r.Unlock()
}

func (hm *HandshakeManager) handleOutbound(vpnIp netip.Addr, lighthouseTriggered bool) {
	hh := hm.queryVpnIp(vpnIp)
	if hh == nil {
		return
	}
	hh.Lock()
	defer hh.Unlock()

	hostinfo := hh.hostinfo
	// If we are out of time, clean up
	if hh.counter >= hm.config.retries {
		fields := []any{
			"udpAddrs", hh.hostinfo.remotes.CopyAddrs(hm.mainHostMap.GetPreferredRanges()),
			"initiatorIndex", hh.hostinfo.localIndexId,
			"durationNs", time.Since(hh.startTime).Nanoseconds(),
		}
		// hh.machine can be nil here if buildStage0Packet never succeeded
		// (e.g., no certificate available). In that case there's no useful
		// handshake metadata to log.
		if hh.machine != nil {
			fields = append(fields, "handshake", m{
				"stage": uint64(hh.machine.MessageIndex()),
				"style": header.SubTypeName(header.Handshake, hh.machine.Subtype()),
			})
		}
		hh.hostinfo.logger(hm.l).Info("Handshake timed out", fields...)
		hm.metricTimedOut.Inc(1)
		hm.DeleteHostInfo(hostinfo)
		return
	}

	// Increment the counter to increase our delay, linear backoff
	hh.counter++

	// Check if we have a handshake packet to transmit yet
	if !hh.ready {
		if !hm.buildStage0Packet(hh) {
			hm.OutboundHandshakeTimer.Add(vpnIp, hm.config.tryInterval*time.Duration(hh.counter))
			return
		}
	}
