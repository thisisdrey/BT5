### Title
Unbounded array allocation in TVM signature-batch precompiles causes memory-exhaustion DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`ValidateMultiSign` and `BatchValidateSign` decode an attacker-controlled length field from smart-contract call data and use it directly to size a Java array (`new byte[len][]`) before any bound is enforced, mirroring the FFmpeg `che_configure` pattern of allocating memory from an untrusted size field (CVE-2016-9561).

### Finding Description
`extractBytesArray` and `extractSigArray` in `PrecompiledContracts.java` read `len` from `words[offset].intValueSafe()` and immediately allocate `new byte[len][]` before validating `len` against any sane maximum: [1](#0-0) 

The `MAX_SIZE` guard that is supposed to bound this length is only applied when the `allowTvmSelfdestructRestriction` chain parameter is active. When that parameter is not activated (its default is `0`, i.e. off, until a super-representative proposal enables it), `ValidateMultiSign.execute` calls `extractBytesArray` with the raw, unchecked length directly: [2](#0-1) [3](#0-2) 

The same pattern occurs in `BatchValidateSign.doExecute`, which also calls `extractBytes32Array`/`extractBytesArray` guarded by the same feature flag: [4](#0-3) 

`extractBytesArray`/`extractSigArray` compute `len` from a single 32-byte word treated as an `int` via `intValueSafe()`, with no upper bound check before the array allocation: [5](#0-4) 

Because `DataWord` values are fully attacker-controlled call-data words, a contract call can set this offset word to a large value (e.g., close to `Integer.MAX_VALUE`), causing the node to attempt `new byte[large][]`, which throws `OutOfMemoryError` or otherwise forces a huge, wasted allocation during transaction/contract execution.

### Impact Explanation
An unauthenticated party who can deploy a contract or call an existing contract that reaches `validatemultisign`/`batchvalidatesign` (precompiled addresses `0x9`/`0xa`) can trigger a large, attacker-sized array allocation during EVM execution on chains/networks where `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` has not yet been activated. This can raise `OutOfMemoryError` inside the node process, potentially crashing or destabilizing the node (denial of service), consistent with the CVE-2016-9561 bug class (huge memory allocation from an unchecked, attacker-supplied size field).

### Likelihood Explanation
Reachability requires only a normal contract call from any account (no special privileges) into the `ValidateMultiSign`/`BatchValidateSign` precompiled contracts, and requires that `allowTvmSelfdestructRestriction` is not enabled on the target network. Because the guard is a chain-parameter/committee-activated flag rather than an unconditional bound check baked into `extractBytesArray`, any network or historical block range predating that proposal's activation is exposed. Where the flag is already active (e.g., current mainnet after the corresponding hard fork), the `MAX_SIZE` check executes before the allocation and the analog is not exploitable — this reduces but does not eliminate risk on chains/testnets/private forks where the proposal hasn't been passed.

### Recommendation
Move the length/size sanity check (e.g., cap `len` to `MAX_SIZE` or another small bound, and reject negative/absurdly large values) unconditionally inside `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` themselves, rather than only in the caller and only when `allowTvmSelfdestructRestriction` is enabled. This ensures the fix applies regardless of chain-parameter activation state.

### Proof of Concept
1. Deploy or call a contract that issues a `CALL` (or use the precompile directly via low-level call) to address `0x...9` (`ValidateMultiSign`) or `0x...a` (`BatchValidateSign`) on a java-tron network/testnet where `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` has not been activated (`getAllowTvmSelfdestructRestriction() == 0`).
2. Encode call data such that the dynamic-array offset word (e.g., the 4th word for `ValidateMultiSign`, pointing at the `bytes[]` length slot) resolves to a length word containing a very large positive integer (e.g., `0x7fffffff`).
3. Submit the transaction; `extractBytesArray`/`extractSigArray` will execute `new byte[0x7fffffff][]`, causing the node's execution thread to throw `OutOfMemoryError` or consume excessive heap, potentially destabilizing the node process.

Note: I was unable to fully confirm the exact bounds of `DataWord.intValueSafe()` (e.g., whether it clamps to `Integer.MAX_VALUE` or some smaller safe value) due to the index not returning the full method body for that call; a background agent with full file access should verify this before finalizing severity, as it directly affects how large an allocation an attacker can trigger.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();

    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,

    }

  }

  public long getAllowTvmSelfdestructRestriction() {
    return Optional.ofNullable(getUnchecked(ALLOW_TVM_SELFDESTRUCT_RESTRICTION))
        .map(BytesCapsule::getData)
        .map(ByteArray::toLong)
        .orElse(0L);
  }

  public void saveAllowTvmSelfdestructRestriction(long value) {
    this.put(ALLOW_TVM_SELFDESTRUCT_RESTRICTION, new BytesCapsule(ByteArray.fromLong(value)));
  }

  public boolean allowTvmSelfdestructRestriction() {
    return getAllowTvmSelfdestructRestriction() == 1L;
  }
