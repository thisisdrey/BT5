### Title
Unauthenticated DNS Resolution Poisons `static_host_map` Address Trust - (File: `remote_list.go`)

### Summary
Nebula's `static_host_map` hostname entries are periodically re-resolved via the OS default DNS resolver with no authentication, DNSSEC validation, or pinning of the result. Whatever addresses the resolver returns are blindly written into the `RemoteList` cache that Nebula uses to decide where to attempt handshakes for that VPN identity. Like the reported bug — where an externally-sourced, unauthenticated document is imported and trusted verbatim — Nebula imports unauthenticated DNS answers and trusts them to update its internal host/address trust state.

### Finding Description
`NewHostnameResults` in [1](#0-0)  spawns a background goroutine that calls `net.DefaultResolver.LookupNetIP` on a timer and stores whatever IP/port set comes back, with no signature, DNSSEC, or certificate-based verification of the response: [2](#0-1) 

When the resolved set differs from the previous one, the change is accepted unconditionally and `onUpdate()` fires: [3](#0-2) 

That `onUpdate` callback is wired up in `addStaticRemotes`, which marks the entry `shouldRebuild` and feeds the DNS-resolved addresses directly into the `RemoteList` used to source handshake attempts for that VPN address: [4](#0-3) 

This static-host DNS refresh path is loaded for every `static_host_map` entry containing a hostname on config load/reload via `loadStaticMap`: [5](#0-4) 

The `RemoteList` (the same "hostmap/address trust" store queried by the handshake manager to pick a destination `ip:port` for outbound handshake attempts) is thus poisoned purely by controlling DNS answers — no Nebula CA-signed certificate is required to influence which underlay address Nebula will try to reach for a given VPN peer.

### Impact Explanation
An attacker capable of spoofing/poisoning DNS responses for a hostname configured in `static_host_map` (classic off-path DNS cache poisoning or on-path DNS response injection, neither of which requires holding a Nebula CA-signed certificate) can redirect the victim's outbound handshake attempts to an address of the attacker's choosing. This is remote state poisoning of the address-trust subsystem: it can be used to blackhole/deny connectivity to the legitimate lighthouse/peer, or to lure handshake-initiation traffic (including the attacker-observable underlay endpoint and handshake packets) toward an attacker-controlled host. While the Noise handshake's certificate verification against the CA pool still prevents a full session establishment with an unauthenticated peer, the address-selection trust boundary itself is compromised with no verification analogous to the reported "anyone can edit, and the app blindly imports it" pattern.

### Likelihood Explanation
Any hostname entries in `static_host_map` are refreshed on a timer using plain, unauthenticated DNS lookups by default (`net.DefaultResolver.LookupNetIP`), with no DNSSEC enforcement, TLS, or certificate check on the result. Any attacker with common DNS-spoofing capability (off-path cache poisoning, rogue/compromised resolver, or on-path injection) can trigger this without possessing any Nebula credential, making the precondition realistically reachable for deployments using hostnames (rather than raw IPs) in `static_host_map`.

### Recommendation
- Prefer requiring raw IPs in `static_host_map` for security-sensitive deployments, and document the trust implications of DNS-based entries.
- Validate DNS responses with DNSSEC where possible, or require the resolved address to still pass through the same certificate/CA validation before being trusted as authoritative for handshake initiation.
- Consider rate-limiting/logging address changes learned via DNS and requiring out-of-band confirmation (e.g., alerting) before large-scale bulk redirection, and ensure a single DNS response cannot silently displace all previously known-good addresses for a host.

### Proof of Concept
1. Configure a `static_host_map` entry using a hostname (not a literal IP).
2. As a network attacker, spoof/poison the DNS response for that hostname to point to an attacker-controlled `ip:port`.
3. Observe `NewHostnameResults`'s background goroutine in [6](#0-5)  accept the spoofed answer and call `onUpdate`, which via `addStaticRemotes` in [4](#0-3)  writes the attacker's address into the `RemoteList` for that VPN identity, causing subsequent handshake attempts to target the attacker-controlled endpoint.

func (lh *LightHouse) loadStaticMap(c *config.C, staticList map[netip.Addr]struct{}) error {
	d, err := getStaticMapCadence(c)
	if err != nil {
		return err
	}

	network, err := getStaticMapNetwork(c)
	if err != nil {
		return err
	}

	lookupTimeout, err := getStaticMapLookupTimeout(c)
	if err != nil {
		return err
	}

	shm := c.GetMap("static_host_map", map[string]any{})
	i := 0

	for k, v := range shm {
		vpnAddr, err := netip.ParseAddr(fmt.Sprintf("%v", k))
		if err != nil {
			return util.NewContextualError("Unable to parse static_host_map entry", m{"host": k, "entry": i + 1}, err)
		}

		if !lh.myVpnNetworksTable.Contains(vpnAddr) {
			lh.l.Warn("static_host_map key is not within our networks, layer 3 network traffic to this host will not work",
				"vpnAddr", vpnAddr,
				"networks", lh.myVpnNetworks,
				"entry", i+1,
			)
		}

		vals, ok := v.([]any)
		if !ok {
			vals = []any{v}
		}
		remoteAddrs := []string{}
		for _, v := range vals {
			remoteAddrs = append(remoteAddrs, fmt.Sprintf("%v", v))
		}

		err = lh.addStaticRemotes(i, d, network, lookupTimeout, vpnAddr, remoteAddrs, staticList)
		if err != nil {
			return err
		}
		i++
	}
