### Title
Information Disclosure via Overly Broad Exception Handling in Trigger/Estimate HTTP Servlets - (File: `framework/src/main/java/org/tron/core/services/http/TriggerConstantContractServlet.java`)

### Summary
Multiple HTTP/gRPC/JSON-RPC entry points that an unauthenticated client can call directly (no signed transaction required) catch a broad `Exception` and echo the raw exception class name and message back into the JSON response sent to the caller. This mirrors the CVE-2021-25958 bug class: a generic `try/catch` used for error handling leaks internal implementation details (exception class names, underlying library/DB exception messages) that aid attacker recon, rather than returning a generic, sanitized error.

### Finding Description
In `TriggerConstantContractServlet.doPost` and `TriggerSmartContractServlet.doPost`, after a `ContractValidateException` is handled specifically, any other `Exception` is caught and its class name plus message are concatenated directly into the gRPC `Return.message` field, which is serialized straight back to the HTTP caller: [1](#0-0) 

The same pattern exists in `EstimateEnergyServlet.doPost`: [2](#0-1) 

And in the gRPC path `RpcApiService.callContract` (backing `WalletApi#triggerContract` / `triggerConstantContract`), which any unauthenticated gRPC client can invoke: [3](#0-2) 

And in `Wallet.getTransactionApprovedList`, reachable via the `GetTransactionApprovedList` API without any signature or authentication: [4](#0-3) 

None of these call sites sanitize the exception before surfacing it. Because the input to these endpoints (arbitrary ABI-encoded call data, function selectors, parameters) is fully attacker-controlled, an attacker can deliberately trigger internal exceptions (e.g., `NullPointerException`, `ArrayIndexOutOfBoundsException`, decode/parse failures from the ABI or VM layers, `RuntimeException`s thrown deep in `Runtime`/VM execution) whose `getClass()`/`getMessage()` values reveal internal class names, package structure, and sometimes state details that are not meant to be exposed, exactly as in the OFBiz issue where the try/catch leaked sensitive table info.

### Impact Explanation
This is an information-disclosure issue: it does not itself cause fund loss or a crash, but it exposes internal implementation/class details of the actuator/TVM stack to any anonymous API caller across `wallet/triggerconstantcontract`, `wallet/triggersmartcontract`, `wallet/estimateenergy`, and the gRPC `TriggerContract`/`TriggerConstantContract`/`GetTransactionApprovedList` calls. This recon information can materially assist an attacker in crafting further exploits against the node (e.g., pinpointing which internal exception type/class is thrown for a given malformed input, revealing code paths not documented in the public API).

### Likelihood Explanation
High likelihood of triggering: these endpoints are part of the public, unauthenticated Wallet HTTP/gRPC API and accept fully attacker-controlled ABI/function-selector/parameter data, so a wide range of malformed inputs can be crafted to force various internal exceptions to surface through the generic `catch (Exception e)` branches.

### Recommendation
Replace the generic `e.getClass() + " : " + e.getMessage()` (and bare `e.getMessage()`) responses in `TriggerConstantContractServlet`, `TriggerSmartContractServlet`, `EstimateEnergyServlet`, `RpcApiService.callContract`, and `Wallet.getTransactionApprovedList` with a fixed, generic error code/message for the catch-all branch, logging the full exception (class + message + stack) only server-side (as is already done via `logger.warn(...)`), never in the client-visible payload.

### Proof of Concept
1. Send a POST to `/wallet/triggerconstantcontract` (or `/wallet/triggersmartcontract`, `/wallet/estimateenergy`) with a syntactically valid JSON body but with `function_selector`/`parameter` fields crafted to cause an internal exception during `Util.parseMethod` or downstream VM execution (e.g., malformed ABI parameter causing an unchecked `RuntimeException` inside the ABI decoding/VM layer) rather than a `ContractValidateException`.
2. Observe the HTTP 200 response body contains `"message"` populated with `e.getClass() + " : " + e.getMessage()` — e.g., exposing something like `java.lang.ArrayIndexOutOfBoundsException: ...` or an internal store/decoder class name and message — via the code path shown at `TriggerConstantContractServlet.java:73-80`.
3. Repeat with varied malformed inputs to enumerate internal exception types/messages for recon purposes.
