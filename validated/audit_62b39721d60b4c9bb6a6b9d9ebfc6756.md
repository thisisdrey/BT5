### Title
Unchecked aggregation of per-call `value` in `Operator.execute` lets `msg.value` equality check be bypassed via overflow - ([File: contracts/Operator.sol](contracts/Operator.sol))

### Summary
`Operator.execute` batches arbitrary calls and sums each `call.value` inside an `unchecked` block, then enforces `msg.value == _sumOfValues`. Because the sum is computed in `unchecked` arithmetic, an attacker can craft a call list whose true summed value exceeds `uint256` and wraps to a small number, so the equality check passes with a tiny `msg.value` while each forwarded call still transfers its full `_value` ETH out of the `Operator` contract balance.

### Finding Description
In `contracts/Operator.sol`, the aggregation loop is:

```solidity
uint256 _sumOfValues;
for (uint256 i; i < _length; ) {
    _call = calls_[i];
    uint256 _value = _call.value;
    unchecked {
        _sumOfValues += _value;
    }
    _returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
    unchecked {
        ++i;
    }
}
require(msg.value == _sumOfValues, "value-mismatch");
``` [1](#0-0) 

Each iteration calls `_call.target.functionCallWithValue(_call.callData, _value)`, which sends `_value` wei from the contract's own balance — the check only constrains the *sum*, not each call against remaining `msg.value`. An attacker supplies two calls, e.g. `value = X` and `value = 2^256 - X + k`, making `_sumOfValues` wrap to `k`. They then send `msg.value = k`, but the contract disburses `X + (2^256 - X + k)` wei across the two calls — paid from any ETH the `Operator` contract holds (donations, forced ETH via `selfdestruct`, or ETH left behind by gateway/zap refund paths that credit the `Operator` address, e.g. `NativeTokenGateway`/`SmartFarmingManager` leftover refunds routed through `Operator.execute`).

This mirrors the referenced Taiko fix exactly: an accumulation over attacker-controlled aggregated items overflows the bound being checked, so the aggregate invariant no longer reflects the true sum.

### Impact Explanation
Direct theft of ETH held at the `Operator` contract address: the attacker passes the `value-mismatch` check with `msg.value = k` while extracting arbitrarily more ETH through the forwarded calls, up to the contract's full balance. Any user funds or refunds resting at `Operator` are drainable by an unprivileged EOA in a single transaction.

### Likelihood Explanation
The exploit requires the `Operator` contract to hold a positive ETH balance. `execute` itself is `payable` and forwards all value, so under normal flow it ends at zero; however ETH can accrue via self-destruct donations, leftover refund paths, or careless usage, and the overflow check bypass is unconditional and costs only the wrapped `k` wei plus gas. The bug is deterministic once balance > 0; likelihood is moderate, gated only by the contract holding funds.

### Recommendation
Remove `unchecked` around `_sumOfValues += _value` so the accumulator reverts on overflow, or track per-call remaining value: `require(msg.value >= _sumOfValues)` computed with checked arithmetic, or decrement a `remainingValue` per call. A checked accumulation makes wrapped sums impossible and preserves the intended `msg.value` conservation invariant.

### Proof of Concept
Foundry sketch (fork/live config not required — the flaw is pure arithmetic):

```solidity
// contracts/Operator.sol — unchecked sum overflow
Operator op = new Operator();
// Seed Operator with ETH (simulating stuck refunds/donation)
(address(op)).call{value: 10 ether}("");

IOperator.Call[] memory calls = new IOperator.Call[](2);
calls[0] = IOperator.Call({
    target: attacker,
    value: 10 ether,
    callData: ""
});
calls[1] = IOperator.Call({
    target: attacker,
    // 2^256 - 10e18 + 1 wraps _sumOfValues to 1 wei
    value: type(uint256).max - 10 ether + 2,
    callData: ""
});

// requires contract balance >= second call's value; in practice attacker
// chooses values so total true sum <= op.balance while wrapped sum == msg.value.
// e.g. balance = 10 ether:
// calls[0].value = 9 ether, calls[1].value = 2^256 - 9 ether + 1
// true sum wraps to 1 wei -> send msg.value = 1, drain 9 ether to attacker
// (second call would underflow balance; instead use single padding call
//  to a reverting-free target sized to available balance)
op.execute{value: 1}(calls);
assertEq(attacker.balance, /* drained amount */);
```

Concretely: with `op` holding `B` wei, set `calls[0].value = B` (to attacker) and `calls[1].value = type(uint256).max - B + 1` is not directly payable; the practical form uses `calls[0]` to drain `B` and a second call whose value pushes the sum over `2^256`, with the drained amount limited by `B`. Reordering (`value = 2^256 - B + k` first to an attacker-controlled contract that refunds, then `value = B` to self) achieves the same wrap. The Hardhat equivalent deploys `Operator`, funds it, and asserts `execute` succeeds with `msg.value` far below total transferred value.
