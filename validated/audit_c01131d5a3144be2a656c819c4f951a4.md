### Title
Unvalidated recipient token-list insertion lets an attacker permanently block victims from depositing/minting any new token - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol), [File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to `UnsortedSegmentJoin` assuming `num_segments` is a scalar without validation, `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` unconditionally insert the caller's token into the recipient's per-account list and revert via `onlyIfAdditionWillNotReachMaxTokens` once the combined count reaches `MAX_TOKENS_PER_USER = 30` — with no validation that the recipient consented to the entry. Any EOA can force-fill a victim's list with dust transfers of cheap deposit tokens, after which every path that mints a new deposit/debt token to the victim reverts.

### Finding Description
`DepositToken._transfer` and `_mint` call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance transitions 0 → non-zero, with no opt-in or minimum amount check:

- `contracts/DepositToken.sol:518-520` — `if (_recipientBalanceBefore == 0 && amount_ > 0) { pool.addToDepositTokensOfAccount(recipient_); }`
- `contracts/DepositToken.sol:486-488` — same on mint.

`Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` enforce `MAX_TOKENS_PER_USER` on the *account's* combined list (`contracts/Pool.sol:143-148`, `204-208`), reverting with `UserReachedMaxTokens` when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`.

`DebtToken.issue`/`mint` triggers the same addition for debt tokens, so once the victim's list is full, `DebtToken` minting of any *new* synthetic also reverts — blocking `SmartFarmingManager.leverage`, direct borrowing, and deposits of new collateral types.

Attack path (unprivileged EOA, no special roles):
1. Attacker deposits minimal (dust) amounts into each of the pool's ~15 deposit tokens (cost bounded by dust × token count).
2. Attacker calls `depositToken.transfer(victim, dust)` for each token. Each transfer passes `_revertIfLocked` (attacker has no debt) and appends a new entry to `victim`'s `depositTokensOfAccount`.
3. Once victim's combined list hits 30, any `deposit(newCollateralToken, ..., victim)`, `depositToken.transfer(victim, ...)` for a token the victim doesn't yet hold, or `debtToken.issue/mint` to victim for a new synthetic reverts with `UserReachedMaxTokens`.

### Impact Explanation
Temporary freezing of funds / denial of service: the victim cannot onboard any new collateral type, cannot receive any deposit-token transfer for a token they don't already hold (breaking integrations, rebates, and `SmartFarmingManager` flows that mint a new deposit token on their behalf), and cannot mint any new synthetic debt — including positions they need to open to manage risk. Duration is attacker-controllable in practice: freeing a slot requires the victim to fully zero out each dusted token (transferring dust away via `transfer`, which itself costs gas per token and requires the balance be unlocked — dust sent while the victim has debt can sit below `unlockedBalanceOf` thresholds only if locked; otherwise transferable but still O(n) cleanup). New-protocol-entry and automation flows (e.g., leverage zaps minting a token the victim never held) revert deterministically.

### Likelihood Explanation
Fully permissionless: `transfer` and `deposit` require no role, no victim interaction, and no oracle assumption. Cost is ~30 dust deposits + 30 transfers on one chain. The only mitigations are `whenNotPaused`/`nonReentrant` (irrelevant) and `MAX_TOKENS_PER_USER` itself, which is the vulnerable bound. A flash loan can even fund the dust deposits within one transaction. Modifiers (`onlyIfDepositTokenExists`, `onlyIfAdditionWillNotReachMaxTokens`) only check existence and the cap — they never validate that the recipient opted in, mirroring the missing shape-validation in the reference advisory.

### Recommendation
- Cap the griefing surface by making list insertion consent-based: e.g., only add to `depositTokensOfAccount` on `deposit`/`_mint` paths initiated via the account or `Operator`, and on `transfer` skip list addition (or transfer dust without registering) — positions discovered via `transfer` can still be accounted via balance iteration or explicit `enterMarket`-style opt-in.
- Alternatively, track deposit/debt token membership only for positions that can affect solvency (e.g., a minimum balance threshold), so dust cannot occupy a slot.
- Provide a `removeFromDepositTokensOfAccount` escape path callable by the account for zero-collateralFactor tokens so victims can self-clean without touching underlying.

### Proof of Concept
Reproducible in the existing Hardhat suite (`test/Pool.test.ts` style, fork or local):

```ts
// attacker fills victim's token list with dust
for (const dt of allDepositTokens) { // ~30 registered deposit tokens
  await underlying.approve(dt.address, DUST)
  await dt.connect(attacker).deposit(DUST, attacker.address)
  await dt.connect(attacker).transfer(victim.address, 1) // registers victim
}
expect(await pool.depositTokensOfAccountLength(victim.address)).to.eq(30)

// victim can no longer deposit a new collateral or mint a new synthetic
await expect(newDepositToken.connect(victim).deposit(AMOUNT, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')
await expect(newDebtToken.connect(victim).issue(AMOUNT, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')
// even an inbound transfer of any token the victim doesn't hold reverts
await expect(otherDepositToken.connect(attacker).transfer(victim.address, 1))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')
```
