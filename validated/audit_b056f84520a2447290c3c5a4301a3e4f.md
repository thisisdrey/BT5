### Title
Unchecked division by `totalEnergyWeight`/`totalNetWeight` in resource-limit calculations can throw `ArithmeticException` when hardened math is enabled - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()` relies on a Java `assert` (disabled by default in production JVMs) to guard against `totalEnergyWeight == 0`, then unconditionally performs a `BigInteger` division by `totalEnergyWeight` when the hardened resource-calculation path is active. This mirrors the reported `TokenDistribution.sol` bug class: a divisor derived from network/global state is used without a real runtime check, only a comment/assert-level "guard" that is not actually enforced, creating a division-by-zero condition instead of the underflow described in the original report.

### Finding Description
`calculateGlobalEnergyLimit()` computes: [1](#0-0) 

The only protection against `totalEnergyWeight == 0` is a Java `assert` statement, which is compiled out and not enforced at runtime unless the JVM is started with `-ea`. If the hardened calculation path (`VMConfig.allowHardenResourceCalculation()`) is enabled and `totalEnergyWeight` is `0`, the code proceeds to:
```java
BigInteger.valueOf(energyWeight).multiply(...).divide(BigInteger.valueOf(totalEnergyWeight)).longValueExact();
```
`BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException`. This is directly analogous to the reported Solidity bug: a "necessary check" is documented/implied (via assert/comment) but not actually enforced with a `require`-equivalent, allowing a zero divisor to reach the division operator.

By contrast, other resource-limit calculation methods in the same codebase area (`BandwidthProcessor.calculateGlobalNetLimit`, `calculateGlobalNetLimitV2`, `EnergyProcessor.calculateGlobalEnergyLimit`, `calculateGlobalEnergyLimitV2`) explicitly check `totalNetWeight == 0` / `totalEnergyWeight == 0` and `return 0` before dividing: [2](#0-1) [3](#0-2) 

This shows the codebase's intended pattern is an explicit zero-check, but `RepositoryImpl.calculateGlobalEnergyLimit()` (used by the TVM/native-contract energy path) omits that explicit check and substitutes an `assert`.

This method is exercised via the `Repository` interface used inside TVM execution / native contract processors (e.g., `ContractState`/`VMActuator` energy-limit computations), i.e. it is reachable from ordinary smart-contract transaction execution paths, not just privileged code: [4](#0-3) 

I was not able to fully trace, within the remaining tool budget, the exact conditions under which `dynamicPropertiesStore.getTotalEnergyWeight()` could reach `0` on a live/mainnet chain (it is the sum of frozen-for-energy balances network-wide, which is normally never zero once any account has frozen for energy). This is the key uncertainty: while the code path is unsafe in principle, whether an attacker can realistically drive `totalEnergyWeight` to exactly `0` on a running chain (as opposed to only in test/private-network scenarios) is unconfirmed.

### Impact Explanation
If `totalEnergyWeight` reaches `0` while `VMConfig.allowHardenResourceCalculation()` is enabled, any call path that invokes `RepositoryImpl.calculateGlobalEnergyLimit()` during transaction/contract execution would throw an uncaught `ArithmeticException`. Depending on where this exception propagates (inside VM execution vs. block application), this could cause a node to fail to process a valid block/transaction consistently, i.e. a potential node crash/halt or consensus-affecting exception during block application — matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
Likelihood is currently assessed as low-to-uncertain because:
- The vulnerable branch only activates when `allowHardenResourceCalculation()` is true (a chain-parameter-gated feature).
- `totalEnergyWeight == 0` requires the entire network's energy-frozen weight to be zero, which is an unusual, likely testnet/private-chain-only condition rather than something a single unprivileged transaction can trigger on mainnet.
- No stack trace / crash was directly observed; this is inferred from static code analysis of the guard-vs-check discrepancy.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit()` with an explicit runtime check consistent with the pattern already used in `EnergyProcessor`/`BandwidthProcessor` (e.g., `if (totalEnergyWeight <= 0) { return 0; }`) before performing the `BigInteger` division, so that a zero (or negative) divisor can never reach the arithmetic operation regardless of JVM assertion settings.

### Proof of Concept
Not independently verified end-to-end due to tool-call limits. The reasoning is based on static code inspection:
1. Set/observe `dynamicPropertiesStore.getTotalEnergyWeight() == 0` (e.g., in a test/private network where no account has frozen for energy).
2. Enable `VMConfig.allowHardenResourceCalculation()`.
3. Trigger a TVM call path that invokes `RepositoryImpl.calculateGlobalEnergyLimit(accountCapsule)` for an account whose `getAllFrozenBalanceForEnergy() >= TRX_PRECISION`.
4. Observe `BigInteger.divide(BigInteger.ZERO)` throwing `ArithmeticException`, as already demonstrated for the analogous `usageToBalance` method in the existing test `testUsageToBalanceOverflowDetectedWithHardening` (which shows the `ArithmeticException` behavior of the hardened BigInteger division path): [5](#0-4)

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

      assert totalEnergyWeight > 0;

      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
