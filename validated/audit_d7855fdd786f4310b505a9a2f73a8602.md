### Title
Unbounded body buffering via `read_to_string` in `SignerEventReceiver::process_event` with no `MAX_MESSAGE_LEN` cap - (File: libsigner/src/events.rs)

### Summary
`process_event` reads the full HTTP body of an incoming signer-event request into a `String` without ever comparing the declared/actual body size against `MAX_MESSAGE_LEN` (or any other constant cap), unlike sibling code in `libsigner/src/http.rs` and the node-side RPC handlers, which explicitly bound body/chunk decoding to `MAX_MESSAGE_LEN`. This lets a remote sender who can reach the signer's event-receiver bind address send an oversized body and force the receiver thread to allocate memory proportional to the attacker-chosen body size.

### Finding Description
`libsigner/src/events.rs` contains the only `read_to_string` call in the file, used to slurp the request body for POST endpoints such as `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, and `/new_block`. Searching the codebase for `MAX_MESSAGE_LEN` shows it is referenced extensively in `libsigner/src/http.rs` (bounding `HttpChunkedTransferReader` decoding) and in numerous `stackslib/src/net/*` RPC handlers, but `libsigner/src/events.rs` does not appear at all in that reference list. This means the body-buffering step in `process_event` has no equivalent guard: there is no check of `Content-Length` against `MAX_MESSAGE_LEN`, and no bounded/`take()`-wrapped reader is used before calling `read_to_string`, so the buffer size is dictated entirely by what the remote peer sends, not by a fixed constant as the BOUNDS invariant requires.

### Impact Explanation
A single oversized POST to any of the event-receiver's endpoints can drive the signer's event-receiver thread to allocate memory proportional to the attacker-supplied body, exhausting process memory and crashing or hanging the signer with a single request. This matches the Critical category ("remote crash/unauthenticated DoS from few messages"), since the endpoint requires no authentication/secret and is reachable by any party able to connect to the signer's event port.

### Likelihood Explanation
No privileged role, secret, or valid peer/slot key is needed — the attacker only needs network reachability to the signer's bound event-receiver address and the ability to issue one HTTP POST with a large body/Content-Length. This is fully attacker-controlled and repeatable per connection at negligible attacker cost, since building/sending the body only requires local storage of the payload (which can also be sent as a slow drip after promising a large Content-Length), while the receiver eagerly buffers whatever amount the sender chooses.

### Recommendation
Wrap the body reader in `process_event` with a bounded reader (`Read::take(MAX_MESSAGE_LEN as u64)`), and/or reject requests up front where the `Content-Length` header exceeds `MAX_MESSAGE_LEN`, mirroring the pattern already used in `decode_http_body` in `libsigner/src/http.rs` and the node's RPC handlers.

### Proof of Concept
Rust test plan: start a `SignerEventReceiver` bound to a local port; open a TCP connection and send `POST /stackerdb_chunks HTTP/1.1\r\nContent-Length: <N>\r\n\r\n` with `N` far larger than `MAX_MESSAGE_LEN` (e.g., 10x), followed by that many actual body bytes (streamed slowly to simulate a trickle); assert that either (a) the connection is closed/request rejected once buffered bytes exceed `MAX_MESSAGE_LEN`, or (b) memory usage of the receiver thread grows unbounded and matches `N` rather than being capped — the current code exhibits (b), confirming the missing cap in `process_event`'s `read_to_string` call. /// Decode an HTTP body, given the headers.
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
