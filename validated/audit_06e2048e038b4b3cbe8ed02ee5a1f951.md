Found: `Manager.pushTransaction` calls `trx.validateSignature(...)` before the `ContractSizeNotEqualToOneException` contract-count check that only exists later in `processTransaction`.

### Title
Unhandled `IndexOutOfBoundsException` on empty-contract-list transaction in `Manager.pushTransaction` — potential DoS analog to CVE-2017-12803 - ([File: framework/src/main/java/org/tron/core/db/Manager.java])

### Summary
CVE-2017-12803 is a crash caused by an unvalidated structural precondition being asserted deep in a parser (`Node_ValidatePtr`) instead of being checked before use, so a crafted file trips an `assert`/fault. The analog class of bug in java-tron is a broadcastable transaction that reaches deep into the pending-transaction / signature-validation path with a structural precondition (raw contract list must be non-empty) left unchecked, letting an internal method index into an empty list.

### Finding Description
`Manager.pushTransaction` (the entry point used by `Wallet.broadcastTransaction` and by `TronNetDelegate.pushTransaction` for the P2P transaction relay path) enqueues the transaction and immediately calls: [1](#0-0) 
```
if (!trx.validateSignature(chainBaseManager.getAccountStore(),
    chainBaseManager.getDynamicPropertiesStore())) {
```
`validateSignature` internally does `contract = transaction.getRawData().getContractList().get(0)` without any check that the contract list is non-empty: [2](#0-1) 

By contrast, `validatePubSignature` (used elsewhere) does check `getContractCount() <= 0` first, and `processTransaction` (called later, inside `pushTransaction`) explicitly throws `ContractSizeNotEqualToOneException` when the contract-list size isn’t exactly 1: [3](#0-2) 

However, this size check occurs **after** `trx.validateSignature(...)` is already invoked directly inside `pushTransaction` (line 905), which routes to `TransactionCapsule.validateSignature` (the static method, not `validatePubSignature`) and unconditionally does `.getContractList().get(0)`. If `Wallet.broadcastTransaction` is bypassed for the check at `contractCount == 0` (it currently checks `getContractCount() == 0` before calling `pushTransaction`, mitigating this specific path — see `Wallet.java:571-574`), but the P2P relay path in `TronNetDelegate.pushTransaction` → `dbManager.pushTransaction(trx)` has no equivalent pre-check of `getContractCount()`; it relies entirely on `Manager.pushTransaction` internals. Since `Manager.pushTransaction` calls `trx.validateSignature(...)` (the boolean instance method) at line 905 before the `getRawData().getContractList().size() != 1` guard (which only exists inside `processTransaction`, invoked later at line 934), a transaction with an **empty** contract list reaching this path via P2P relay would throw an unchecked `IndexOutOfBoundsException` from `.get(0)` inside `TransactionCapsule.validateSignature`.

### Impact Explanation
An uncaught `IndexOutOfBoundsException` propagating from `Manager.pushTransaction` is not one of the checked exceptions declared/caught by callers (`ValidateSignatureException`, `ContractValidateException`, etc.), so it surfaces as an unchecked `RuntimeException`. Depending on the calling thread (e.g., the P2P message-handling thread pool in `TransactionsMsgHandler`), this can abort transaction processing for that thread, and if uncaught further up the stack, could destabilize the P2P message-handling loop — a denial-of-service condition analogous to the `assert`-triggered crash in mkclean/mkvalidator, though scoped to a single thread rather than the whole process given java-tron's general practice of catching broad exceptions at higher levels.

### Likelihood Explanation
Moderate/uncertain. I could not fully confirm within the available index whether `TransactionsMsgHandler` (the P2P entry point that ultimately calls `TronNetDelegate.pushTransaction`) validates `getContractCount() >= 1` before invoking `dbManager.pushTransaction`. I did find a check in `TransactionsMsgHandler.check` (`framework/src/main/java/org/tron/core/net/messagehandler/TransactionsMsgHandler.java:143-146`) that rejects transactions with `getContractCount() < 1` for the P2P relay path — this appears to close the gap for P2P-originated transactions, but I was not able to fully verify that every other broadcastable entry point (e.g., internal re-push, `rePush`, or other legacy call sites of `Manager.pushTransaction`) enforces the same precondition before reaching `validateSignature`.

### Recommendation
Add an explicit `getRawData().getContractCount() >= 1` (or `== 1`) guard at the very start of `Manager.pushTransaction`, before calling `trx.validateSignature(...)`, mirroring the check already present in `TransactionCapsule.validatePubSignature` and in `processTransaction`. This removes the reliance on every caller (P2P handler, RPC broadcast, internal re-push) independently enforcing the precondition, and ensures the guard is applied uniformly regardless of entry point.

### Proof of Concept
Not independently verified end-to-end (would require confirming whether a bypass path exists that calls `Manager.pushTransaction` without first checking contract count). Conceptually: construct a `Transaction` whose `raw.contract` list is empty, sign it with an arbitrary key so it satisfies signature-count > 0 checks elsewhere, and submit it through any code path that calls `Manager.pushTransaction` without a prior `getContractCount()` check; this should throw `IndexOutOfBoundsException` from `TransactionCapsule.getOwner`/`validateSignature`'s `.getContractList().get(0)` call.
