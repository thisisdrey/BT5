### Title
Check-then-Update replay window race lets a duplicated/replayed data or relay packet be decrypted and delivered twice before the anti-replay bitmap is committed - (File: `connection_state.go`)

### Summary
The Telcoin bug is a checkpoint-lookup ambiguity: two state-mutating operations (stake, exit) land in the same block, and the "state at block N" query resolves to the wrong (stale) checkpoint because the check-and-record step is not atomic with the value that gets trusted, letting an attacker fabricate a large "as-of" value cheaply. Nebula's data-plane replay defense has the analogous non-atomicity: the "is this counter new" check and the "commit this counter as seen" update are two separate critical sections with decryption sandwiched in between, so two concurrent deliveries of the same message counter can both pass the check before either commits the update.

### Finding Description
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` both perform the anti-replay validation in three discrete steps instead of one atomic operation: [1](#0-0) 

1. Lock, call `cs.window.Check(l, messageCounter)`, unlock.
2. Perform AEAD decryption (`DecryptDanger`) with the lock released.
3. Lock again, call `cs.window.Update(l, messageCounter)`, unlock.

`Check` only inspects the bitmap; it does not mark the counter as seen. `Update` is what actually commits the bit into the `Bits` sliding window: [2](#0-1) [3](#0-2) 

Because the lock is released between `Check` and the eventual `Update`, if the same encrypted packet (same `h.MessageCounter`) is delivered to the Interface twice at roughly the same time — e.g. via UDP retransmission/duplication at the network layer, or intentionally re-injected by an on-path attacker who can observe/replay ciphertext without possessing a certificate — both deliveries can call `Check` and both observe "not yet seen," both proceed to decrypt successfully (decryption itself doesn't consult the window and will succeed identically for both copies since it's the same ciphertext/nonce), and only afterward do they race to call `Update`. This mirrors `readOutsidePackets`, which routes to `Decrypt`/`VerifyRelay` per received UDP datagram: [4](#0-3) 

and the relay verification path, which has the identical Check-decrypt-Update pattern with a separate lock per call: [5](#0-4) 

Just as the Telcoin `getAtBlock` bug arises because "checkpoint recorded" and "checkpoint queried" are not the same atomic step, here "counter checked" and "counter committed" are not the same atomic step, and a second reader can slip through the gap.

### Impact Explanation
A successful race causes the same on-the-wire message counter to be decrypted and delivered to the tun device or forwarded through a relay twice, defeating the purpose of `ReplayWindow`/`Bits` as documented in the CHANGELOG fix that hardened the relay path against exactly this class of issue ("Advance the replay window on relayed packets so a relay drops replayed frames instead of re-forwarding them" and "Lock replay window updates so concurrent readers can't corrupt it"): [6](#0-5) 

Those fixes addressed data-structure corruption and missing advancement on the relay-forwarding path, but did not make the Check→Decrypt→Update sequence itself atomic. The residual race allows: duplicate delivery of a single application payload to the overlay device (double-injection), or on a `ForwardingType` relay, a second forwarded copy of an already-forwarded relay frame — i.e., traffic replay in the sense the anti-replay window exists specifically to prevent.

### Likelihood Explanation
Exploitability depends on the ability to deliver two copies of the same ciphertext to the interface's UDP listener(s) within the small window between `Check` returning and `Update` executing (which spans one AEAD decrypt operation). This is plausible under `listen.routines`/`tun.routines` > 1 configurations where multiple reader goroutines call `readOutsidePackets`/`Decrypt` concurrently, or simply by an attacker duplicating a captured UDP datagram at the network layer (UDP has no delivery-uniqueness guarantee) so the kernel or NIC/queue delivers it to Nebula twice in quick succession. No valid certificate or session key is required to inject duplicate raw UDP frames toward the listening socket; the attacker only needs to observe/capture a legitimate ciphertext frame in transit.

### Recommendation
Make the replay-window check-and-commit atomic with respect to the specific message counter: hold `decryptLock` for the full Check→Decrypt→Update sequence (or use a single "reserve" primitive that atomically marks the counter as claimed before decryption starts and rolls it back on decryption failure), rather than releasing the lock between `Check` and `Update` in both `ConnectionState.Decrypt` and `ConnectionState.VerifyRelay`.

### Proof of Concept
1. Establish a tunnel (directly or through a `ForwardingType` relay) so a `ConnectionState` with an active `window *Bits` exists.
2. Capture one legitimate data-plane or relay message-type UDP frame with counter `N` (as done in `TestRelayReplayProtection`, which captures `relayFrame` via `myControl.GetFromUDP(true)`).
3. Instead of a single re-injection (as that test performs), inject two copies of the identical frame back-to-back from two goroutines/sockets so that both `readOutsidePackets` invocations race into `Decrypt`/`VerifyRelay` for the same `messageCounter` before either has called `window.Update`.
4. Observe whether both copies pass `window.Check` (returns `true` for both) and both successfully complete `DecryptDanger`/relay-signature verification, resulting in the payload being written to `f.readers[q]` twice (data path) or forwarded twice via `f.SendVia` (relay path), rather than the second copy being rejected with `ErrAlreadySeen` as intended.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
