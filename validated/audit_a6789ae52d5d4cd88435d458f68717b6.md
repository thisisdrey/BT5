Based on the code review, the resharding split logic in `retain_multi_range_recursive` (`core/store/src/trie/ops/resharding.rs`) and `squash_node` (`core/store/src/trie/ops/squash.rs`) is implemented as a single generic algorithm shared by both the memtrie and disk-storage code paths, via the `GenericTrieUpdateRetain`/`GenericTrieUpdateSquash` traits over the `GenericUpdatedTrieNode` abstraction. `Trie::retain_split_shard` (`core/store/src/trie/mod.rs:1746`) simply dispatches to `retain_split_shard_with_memtrie` or `retain_split_shard_with_trie_storage` depending on whether memtries are loaded, but both call into the exact same `retain_multi_range_recursive`/`squash_node` logic operating on the same logical (hash-independent) node structure. [1](#0-0) [2](#0-1) 

When the split boundary falls inside an extension node, the algorithm does not attempt to split the extension's nibble string directly. Instead, `retain_decision` is evaluated on the *full accumulated key path* at entry to each recursive call, and for an `Extension` node it descends into the child using `child_key = key_nibbles + extension_nibbles` (the full path after the extension), re-evaluating `retain_decision` for the child using that extended key. This means the decision of whether to retain/discard/descend is always made against the complete key, never against a partial nibble sequence, so a boundary landing mid-extension is handled correctly and identically regardless of whether the source is a memtrie or on-disk representation. Post-processing via `squash_node` (which restructures branches with 0/1 children and merges adjacent extensions, `core/store/src/trie/ops/squash.rs:29-106`) is likewise representation-agnostic. There's an existing unit test (`05201000 = 0025 # split extension node into branch in the middle`) explicitly covering mid-extension splits. [3](#0-2) 

Additionally, `core/store/src/trie/split.rs` contains `big_random_trie_inner`, a fuzz-style test that explicitly checks that `find_trie_split` produces identical results between the memtrie path and a `recorded_trie` built purely from a `PartialStorage` proof, i.e., cross-representation consistency is already tested. [4](#0-3) 

The "referencing account deleted while others still reference the code" detail (alluding to `GLOBAL_CONTRACT_CODE`/`GLOBAL_CONTRACT_NONCE` refcounted global contract code) is orthogonal to the split algorithm: these columns are copied identically to both children via `get_interval_for_copy_to_both_children`, independent of the boundary account, so account deletion timing cannot desynchronize the split outcome. [5](#0-4) 

No code path was found where an unprivileged account's storage layout (however shaped) can cause `process_memtrie_resharding_storage_update` (`chain/chain/src/resharding/manager.rs:162-295`) to compute a memtrie-derived child root that diverges from a disk-derived one — both call the same `retain_split_shard` → same generic algorithm, and the resulting root hash is a pure function of the resulting canonical trie content, not of the underlying representation. [6](#0-5)
