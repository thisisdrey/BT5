### Title
Unprivileged dust transfers permanently fill a victim's per-account token list, DoS-ing deposits, borrows, and collateral receipt - ([File: contracts/Pool.sol])

### Summary
The reference bug (CVE-2023-3618) is a buffer overflow in `Fax3Encode`: a crafted input forces a write past a bounded buffer and crashes the process — a denial-of-service caused by exhausting a hard bound with attacker-controlled data. The Metronome analog is the fixed-size accounting bound `MAX_TOKENS_PER_USER` in `Pool.sol`: an unprivileged attacker can force entries into any victim's `depositTokensOfAccount` set via dust `DepositToken.transfer()` calls, overflowing the bound so that every subsequent state transition that would add a new token to the victim's list reverts with `UserReachedMaxTokens`, blocking the victim from receiving new collateral types or opening any new debt position.

### Finding Description
`Pool` tracks two per-account sets, `debtTokensOfAccount` and `depositTokensOfAccount`, whose combined length may not exceed `MAX_TOKENS_PER_USER = 30` [1](#0-0) .

Both `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are called from the token contracts, not from the user: `DepositToken._transfer` and `_mint` invoke `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was previously zero [2](#0-1) , and `DebtToken._mint` does the same for debt [3](#0-2) .

Because `DepositToken.transfer`/`transferFrom` are public and permissionless (only gated by `_revertIfLocked` on the *sender*, and the sender needs no collateral or debt), an attacker can mint a dust balance of each `DepositToken` in the pool and transfer 1 wei of each to a chosen victim. Each dust transfer pushes a new entry into the victim's `depositTokensOfAccount`. Once `debt + deposit` entries reach 30, the `onlyIfAdditionWillNotReachMaxTokens` modifier reverts on every future addition — and since the revert happens inside `_transfer`/`_mint`, the entire transaction reverts.

### Impact Explanation
Once the victim's list is full:

- `DepositToken.transfer`/`transferFrom`/`deposit(..., onBehalfOf_=victim)` of any deposit token the victim doesn't already hold reverts — the victim cannot receive collateral top-ups, liquidation proceeds are unaffected, but anyone paying the victim in a new collateral is blocked.
- `DebtToken.issue` reverts for any synthetic the victim doesn't already owe (`_mint` → `addToDebtTokensOfAccount` → `UserReachedMaxTokens`), so the victim cannot open new borrow positions at all. Since the combined cap is shared, filling the list with ~30 deposit-token dust entries leaves zero slots for debt tokens.
- Critically, `SmartFarmingManager` holds all leveraged users' deposit/debt tokens under its own account. Dust-filling the manager's 30 slots makes `SmartFarmingManager.leverage`/`mint`/`flashIssue`-driven flows revert whenever a new token type would be added — freezing the protocol's leverage feature for all users of that manager until governance removes/re-adds tokens.

The victim can recover by transferring the dust out (each zeroed balance triggers `removeFromDepositTokensOfAccount`), so this is a temporary rather than permanent freeze of account functionality — but it is a forced revert of all state-changing paths that touch a new token, which is the same failure shape as the reference crash: attacker-supplied input pushes a fixed bound past its limit and the operation dies. Cost to the attacker is negligible (dust of each collateral, plus gas); no privileged role, oracle manipulation, or governance action is required.

### Likelihood Explanation
- Reachable from a pure EOA: attacker calls `DepositToken.deposit` (or receives tokens) once per collateral, then `transfer(victim, 1)` for each of up to 30 deposit tokens. No modifier stops this — `transfer` only checks the sender's own unlocked balance [4](#0-3) .
- The number of deposit tokens per pool is itself capped at 30 (`addDepositToken` [5](#0-4) ), so a pool with many listed collaterals gives the attacker enough distinct tokens to saturate the cap.
- Impact is bounded: no theft, no insolvency, and the victim can shed dust to restore functionality. This maps to the Medium/DoS severity of the reference report rather than a fund-loss critical.

### Recommendation
- Do not revert the transfer when the recipient's list is full; instead, allow balance accrual while skipping the list insertion and excluding un-listed tokens from `depositOf`/`debtOf` accounting — or make insertion failure non-fatal via `try/catch`.
- Alternatively, track "counted" tokens per account with an explicit opt-in (e.g., recipient must toggle a token as collateral before it contributes to issuable limit), so unsolicited dust cannot consume slots.
- If the current model is kept, at minimum exclude zero-or-dust balances from counting, or raise/uncouple the shared deposit+debt cap so debt issuance can't be blocked by inbound collateral dust.

### Proof of Concept
Hardhat fork test sketch (assume a deployed `Pool` with ≥ a few `DepositToken`s listed):

```ts
it("griefs victim's token list via dust transfers", async () => {
  const depositTokens: DepositToken[] = await getAllDepositTokens(pool); // pool.getDepositTokens()
  const attacker = await getSigner();
  const victim = victimAddress;

  // Attacker deposits 1 wei of each underlying and transfers dust deposit tokens
  for (const dt of depositTokens.slice(0, 30)) {
    const underlying = await ethers.getContractAt("IERC20", await dt.underlying());
    await deal(underlying, attacker.address, 1);          // hardhat deal/impersonated whale
    await underlying.approve(dt.address, 1);
    await dt.deposit(1, attacker.address);                // mints ~1 wei msdToken
    await dt.transfer(victim, 1);                         // adds dt to victim's list
  }

  const combined =
    (await pool.getDepositTokensOfAccount(victim)).length +
    (await pool.getDebtTokensOfAccount(victim)).length;
  expect(combined).to.eq(await pool.MAX_TOKENS_PER_USER()); // 30

  // 1) Victim can no longer open any new debt position
  await expect(
    debtToken.connect(victimSigner).issue(parseEther("1"), victim)
  ).to.revertedWithCustomError(pool, "UserReachedMaxTokens");

  // 2) Victim cannot receive a deposit token type they don't already hold
  const newDt = await deployNewDepositToken(pool);        // governor adds it
  await expect(
    newDt.transfer(victim, 1)                              // attacker has balance
  ).to.revertedWithCustomError(pool, "UserReachedMaxTokens");

  // 3) deposit() on behalf of the victim reverts for un-held tokens
  await expect(
    newDt.deposit(100, victim)
  ).to.revertedWithCustomError(pool, "UserReachedMaxTokens");
});
```

Caveat: I verified the modifier, the add-on-first-balance hooks, and the cap logic in `Pool.sol`/`DepositToken.sol`/`DebtToken.sol`, but the PoC above is a sketch rather than an executed fork run; the exact number of listed deposit tokens on each chain and whether any deployment config (e.g., `isActive` flags) further constrains the dust-mint step should be confirmed on a fork.
