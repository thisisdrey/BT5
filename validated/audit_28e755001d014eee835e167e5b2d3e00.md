## Analog Found

### Title
Active (non-owner) Permission Key Can Rewrite Owner Permission via `AccountPermissionUpdateContract`, Causing Irreversible Account Takeover - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The phpMyFAQ bug lets a session with only a CSRF token change a password without re-verifying the current one, causing account takeover. The analogous java-tron flaw is that `AccountPermissionUpdateContract`—the transaction type that rewrites an account's `owner`, `witness`, and `active` permissions (the on-chain equivalent of account credentials)—is signature-checked generically like any other contract type. If an account's `active` permission has the `AccountPermissionUpdateContract` bit set in its operations bitmap, a signer holding only that lower-privileged active key (not the true owner key) can broadcast an `AccountPermissionUpdateContract` transaction and unconditionally overwrite the account's `owner` permission with attacker-controlled keys, with no additional "owner-level" re-verification step.

### Finding Description
`TransactionCapsule.validatePubSignature` resolves the signing permission purely from `contract.getPermissionId()` and validates weight against that permission via `checkWeight`/`checkPermission`, using `WalletUtil.checkPermissionOperations` to confirm only that the permission's operations bitmap contains the bit for the contract's `ContractType`: [1](#0-0) . The generic per-contract-type check `checkPermissionOperations` treats `AccountPermissionUpdateContract` the same as any low-risk contract type (e.g. a transfer): [2](#0-1) .

Crucially, `AccountPermissionUpdateActuator.checkPermission` validates an active permission's `operations` bitmap only against `dynamicStore.getAvailableContractType()`, and `AccountPermissionUpdateContract` **is** a member of that "available" set (unlike the "default active operations" set, which explicitly excludes it): [3](#0-2) . This is proven by the test suite itself, which shows `AccountPermissionUpdateContract` is excluded from `ACTIVE_DEFAULT_OPERATIONS` but present in `AVAILABLE_CONTRACT_TYPE`: [4](#0-3) . So while it isn't granted by default, nothing prevents an owner (or an active key that was itself granted broad/unrestricted operations) from enabling this bit for an active permission, or an attacker exploiting a mis-provisioned active key that has it enabled.

Once any active permission's threshold is satisfied and its operations bitmap contains the `AccountPermissionUpdateContract` bit, `AccountPermissionUpdateActuator.execute()` performs an unconditional, unauthenticated-at-owner-level overwrite of `owner`, `witness`, and `active` permissions taken directly from the attacker-supplied contract fields, with no check that the transaction was actually signed under the `owner` permission (`permissionId == 0`): [5](#0-4) .

### Impact Explanation
An account whose active permission (intended for routine, lower-trust operations) is provisioned with the `AccountPermissionUpdateContract` operation bit enabled can be permanently and irreversibly taken over by whoever controls that active key/threshold: they can set an entirely new `owner` permission (their own keys) and drop the original owner's keys from all permission groups, exactly mirroring the CVE's "irreversible account takeover and victim lockout" impact, but on-chain and unrecoverable (no password reset path exists for TRON accounts).

### Likelihood Explanation
Exploitation requires that the target account's active permission has the `AccountPermissionUpdateContract` bit set, which is not the default configuration, but the validation logic explicitly allows and does not reject it (`getAvailableContractType()` includes it, only `getActiveDefaultOperations()` excludes it by default), so it can arise from legitimate custom permission setups (e.g., multisig treasury/DAO/exchange wallets configured for flexible active permissions), from tooling that copies the "available" bitmap instead of the "default" one, or from an owner intentionally delegating broad active permissions without realizing this specific bit grants full account seizure capability.

### Recommendation
Explicitly forbid `AccountPermissionUpdateContract` (and ideally any of `owner`/`witness` update) from being settable in a non-owner (`Active`) permission's operations bitmap inside `AccountPermissionUpdateActuator.checkPermission`, and/or require `contract.getPermissionId() == 0` (owner permission) whenever the transaction's contract type is `AccountPermissionUpdateContract`, enforced centrally in `TransactionCapsule.checkPermission`/`validateSignature`.

### Proof of Concept
1. Owner account `A` creates a custom active permission with a key `K` (weight meets threshold) and sets `operations` bitmap bit for `AccountPermissionUpdateContract` (allowed because `AccountPermissionUpdateActuator.checkPermission` only checks against `getAvailableContractType()`, which contains this bit).
2. Holder of key `K` crafts an `AccountPermissionUpdateContract` with `ownerAddress = A`, a new `owner` `Permission` containing only attacker's key, signs it with `K` using `permissionId` pointing at the compromised active permission.
3. `validatePubSignature` resolves permission via `account.getPermissionById(permissionId)`, confirms the bit is set via `checkPermissionOperations`, and the threshold is met by `K`'s weight — signature check passes.
4. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)`, replacing `A`'s owner permission with the attacker's key, permanently locking out the legitimate owner.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
