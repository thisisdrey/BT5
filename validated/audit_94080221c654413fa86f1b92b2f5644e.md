### Title
Missing balance-underflow check in default (non-hardened) TRC10 Exchange transaction path allows pool balance corruption via floating-point rounding - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
TRON's built-in Bancor-style TRC10 `Exchange` (`ExchangeCreateActuator`, `ExchangeTransactionActuator`) computes swap outputs with a legacy double-precision floating-point implementation (`ExchangeProcessor`) whose result is only guarded against producing a negative pool balance when the `allowHardenExchangeCalculation` proposal is active. In the default/legacy path this guard is skipped entirely, and `ExchangeTransactionActuator.calcFee()` always returns `0`, so an attacker can freely and repeatedly submit exchange-transaction contracts against the same pool to accumulate floating-point rounding drift, in the same way the Yearn attacker exploited a disabled fee plus a repeatable deposit/withdraw primitive to siphon value out of a shared pool over many iterations.

### Finding Description
`ExchangeCapsule.transaction()` selects between two `Processor` implementations depending on `dynamicStore.allowHardenExchangeCalculation()`: [1](#0-0) 

The negative-balance sanity check is conditioned on `hardenedCalc`:
```
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException(...)
}
``` [2](#0-1) 

In the default (legacy, non-hardened) path, `ExchangeProcessor` performs the Bancor relay-token math entirely in `double` and truncates the result to `long` via a straight cast (`(long) issuedSupply`, `(long) exchangeBalance`), with no bounds or sanity check on the resulting pool balances: [3](#0-2) 

`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` and persists the new pool balances unconditionally when it does not throw: [4](#0-3) 

Critically, `ExchangeTransactionActuator.calcFee()` always returns `0`, meaning there is no protocol-level cost (beyond bandwidth/energy) to repeatedly executing exchange transactions against the same pool: [5](#0-4) 

`allowHardenExchangeCalculation` is a committee-controlled dynamic parameter (`AbstractExchangeActuator.allowHarden()`), meaning the negative-balance / overflow protection is off unless explicitly enabled by governance: [6](#0-5) 

This mirrors the structural root cause in the Yearn incident: a protective mechanism (withdrawal fee in Yearn; balance-underflow check here) was disabled/not-yet-enabled, and a cheap, freely-repeatable operation (Curve/vault deposit-withdraw cycles in Yearn; zero-fee TRC10 exchange transactions here) was used to accumulate value extracted through accounting/precision drift in a shared liquidity pool.

### Impact Explanation
If an attacker can drive the floating-point Bancor calculation to a boundary where the computed relay/output quantity exceeds what the pool can back (via repeated round-trip trades exploiting `double` precision loss at large token-balance magnitudes, since balances can be created up to `getExchangeBalanceLimit()`, historically 1e15, near the edge of `double`'s 2^53 exact-integer precision), the resulting `ExchangeCapsule` balances can be persisted without correction in the default path. Because token amounts are simultaneously credited to/debited from real user `AccountCapsule` asset balances in the same `execute()` call, an under-detected negative or corrupted pool balance state can let subsequent trades extract more tokens than the pool actually holds — a form of unbacked-balance/fund-theft against liquidity providers of the pool, analogous to the value siphoned from Yearn's shared vault.

### Likelihood Explanation
The attack path is reachable by any account with a signed `ExchangeTransactionContract` (no special privilege required) and costs nothing extra per exchange call (`calcFee()==0`), so an attacker can iterate cheaply. However, exploitation requires precise conditions (large pool balances near double-precision limits, and specific sell/buy amounts to force truncation to push balances negative) that were not verified end-to-end in this review — reaching an actually negative/corrupted balance requires further numeric analysis or a PoC harness against `ExchangeProcessor`/`ExchangeCapsule.transaction()` with the default (`hardenedCalc=false`) parameters, since the added `SafeExchangeProcessor`/hardened check strongly suggests the java-tron team already identified rounding/overflow issues in the legacy formula and gated the fix behind governance rather than making it default.

### Recommendation
- Enforce the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` (and any overflow) check unconditionally in `ExchangeCapsule.transaction()`, not only when `hardenedCalc` is true.
- Consider making `allowHardenExchangeCalculation` (and `SafeExchangeProcessor`) the default/mandatory computation path, deprecating the legacy floating-point `ExchangeProcessor`.
- Re-evaluate whether `ExchangeTransactionActuator.calcFee()` should remain `0`, since a zero-fee, freely-repeatable swap primitive removes an economic disincentive against precision-drift arbitrage.

### Proof of Concept
Not independently reproduced. A full PoC would require: (1) creating an `ExchangeCreateContract` with `allowHardenExchangeCalculation` left at its default (disabled) value and token balances near `getExchangeBalanceLimit()`, (2) submitting a sequence of `ExchangeTransactionContract` calls alternating buy/sell direction to accumulate `double`-precision truncation error in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, and (3) demonstrating that `exchange.getFirstTokenBalance()`/`getSecondTokenBalance()` can be driven negative or below the sum of real token backing without the actuator rejecting the transaction, since the `hardenedCalc && (...)` check is bypassed in the default path. This was not executed against a live/test node in this review; the finding rests on the static code-path analysis above [2](#0-1) [3](#0-2) .

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
