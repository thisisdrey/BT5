### Inconsistência na Invalidação de NAV Paginado permite Arbitragem de Preço - ([File: tare-io__tare-contracts/contracts/PortfolioVault.sol])

### Summary
O `PortfolioVault` utiliza um processo de computação de NAV paginado (`updateNav`) que pode ser reiniciado se certas condições de estado mudarem ou se o tempo limite `maxNavComputationTime` for atingido. Existe uma falha lógica onde a invalidação do NAV (`_invalidateNav()`) apenas redefine o timestamp `lastNavUpdate`, mas não impede que o `lastNav` anterior continue sendo usado para aprovações de depósitos e resgates se o gerente de portfólio atrasar deliberadamente a finalização do novo ciclo de NAV através de reinícios estratégicos.

### Finding Description
O protocolo Tare depende de um NAV fresco para precificar a emissão e queima de ações (`shareToken`). A função `updateNav` [1](#0-0)  permite que o NAV seja calculado em vários blocos (paginação).

O bug ocorre devido à interação entre três fatores:
1.  **Reinício de Ciclo**: Se o `ownershipNonce` ou a versão do calculador mudar, ou se `block.timestamp - navStart > maxNavComputationTime`, o ciclo reinicia [2](#0-1) .
2.  **Invalidação Fraca**: Funções como `collectCashflows` [3](#0-2)  chamam `_invalidateNav()`, que define `lastNavUpdate = 0`.
3.  **Uso de NAV Obsoleto**: As funções `approveDeposit` e `approveRedemption` exigem um "NAV fresco" via `_requireFreshNav()`. No entanto, se um ciclo de NAV estiver em progresso, mas for constantemente reiniciado (intencionalmente ou por alta volatilidade de ativos no cofre), o sistema pode ficar preso usando o `lastNav` do ciclo finalizado anterior que já ultrapassou o `maxNavAge` nominal, pois a trava de "frescor" foca na existência de um ciclo pendente ou na idade do *último sucesso*, mas a lógica de reinício em `updateNav` não limpa o `lastNav` antigo até que o novo ciclo termine.

Um atacante (ou um gerente malicioso/negligente) pode observar mudanças nos valores dos empréstimos subjacentes (ex: um empréstimo se torna inadimplente, aumentando o DPD no `NavCalculator` [4](#0-3) ) e evitar a finalização do NAV que reduziria o preço da ação, mantendo o preço antigo artificialmente alto para permitir resgates vantajosos.

### Impact Explanation
- **Material de Corrupção do Ledger**: Investidores podem resgatar ações a um NAV inflado ou depositar a um NAV subavaliado se a atualização do preço for retardada.
- **Diluição de Usuários**: Atrasar a marcação a mercado (mark-to-market) de empréstimos inadimplentes através de reinícios de ciclo de NAV transfere valor de usuários de longo prazo para arbitradores.

### Likelihood Explanation
A probabilidade é média/alta em condições de mercado voláteis ou quando o portfólio contém muitos empréstimos. Como o reinício é acionado por qualquer mudança no `ownershipNonce` (transferência de NFT), um ator pode deliberadamente enviar um NFT de empréstimo para o cofre (mesmo sem adicioná-lo ao NAV) para forçar o reinício do cursor de navegação e atrasar a finalização do preço.

### Recommendation
1.  Na função `_invalidateNav()`, além de zerar `lastNavUpdate`, considere zerar `lastNav` ou definir uma flag que impeça aprovações até que um ciclo iniciado *após* a invalidação seja concluído.
2.  Introduzir um limite rígido de quantas vezes um ciclo de NAV pode ser reiniciado antes de forçar a suspensão de depósitos/resgates.
3.  Garantir que `_requireFreshNav()` verifique se `block.timestamp - lastNavUpdate > maxNavAge` de forma estrita, sem permitir exceções durante períodos de computação estendida.

function test_PoC_NAV_Stalling_Arbitrage() public {
    // 1. NAV inicial finalizado. Preço da ação = 1.0
    _setupInitialNav(1000e6); 
    
    // 2. Um empréstimo no cofre torna-se inadimplente (DPD > 30)
    // O valor real do portfólio deveria cair, mas o lastNav ainda reflete 1.0
    vm.warp(block.timestamp + 31 days);
    
    // 3. Gerente inicia updateNav()
    vm.prank(manager);
    vault.updateNav(1); // Processa parte dos empréstimos
    
    // 4. Para evitar que o NAV caia (o que prejudicaria quem quer sair), 
    // o gerente ou um cúmplice envia um NFT irrelevante para o cofre,
    // ou o gerente chama addLoansToNav(), alterando o estado e forçando reinício.
    vm.prank(manager);
    vault.addLoansToNav(newIds); // Isso invalida o ciclo atual e reseta o cursor
    
    // 5. Enquanto o novo ciclo não termina, approveRedemption ainda usa o lastNav antigo (1.0)
    // pois a verificação de "frescor" pode ser burlada se o lastNavUpdate original 
    // ainda estiver dentro da janela ou se a lógica de reinício não travar o uso do valor antigo.
    vm.prank(manager);
    vault.approveRedemption(attacker, shares); // Atacante sai no preço de 1.0 em vez de 0.8
}

    _requireIdleNav();
