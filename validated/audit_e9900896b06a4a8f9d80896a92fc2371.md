### Title
Buffer Over-Read in ZIP Central Directory Parsing via Crafted Archive Entry Length Fields - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in the `ijar`/interface-jar zip reader parses each central-directory entry of an attacker-supplied `.jar`/`.zip` archive and advances its cursor by attacker-controlled 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) without ever checking that the resulting pointer stays within the bounds of the memory-mapped input file. This mirrors the CVE-2017-11577 bug class: a font/format parser trusting length fields from untrusted input and reading past the end of the mapped buffer.

### Finding Description
`FindZipCentralDirectory` validates only that the *aggregate* central directory region fits inside the file (`cd.central_dir_offset + cd.central_dir_size > in_length` check) [1](#0-0) . It never re-validates that any individual entry's declared name/extra/comment lengths keep the cursor inside that region or inside the mmap'd file.

`ProcessCentralDirEntry` then reads these lengths directly from attacker-controlled bytes and blindly advances the cursor: [2](#0-1) 
The `memcpy` into the fixed-size `filename` buffer is bounded on the *write* side (`len = min(file_name_length, filename_size-1)`), but the **read** source `p` can already point past the mapped buffer, so the copy reads out-of-bounds heap/mmap memory [3](#0-2) .

The subsequent extra-field walk is even less constrained: `extra_p` is advanced by an attacker-supplied `data_size` with only a loop-termination check against `p` (itself possibly already out of bounds), and on a `ZIP64_EXTRA_FIELD_TAG` it performs additional `get_u8le` reads from `extra` without any remaining-length check: [4](#0-3) 

This is in stark contrast to the local-file-header path, `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before consuming `file_name_length`/`extra_field_length` bytes [5](#0-4) . No equivalent bounds check (`EnsureRemaining`, or comparison against `zipdata_in_ + input_file_->Length()`) exists in `ProcessCentralDirEntry`.

### Impact Explanation
An attacker who controls the bytes of a `.jar`/`.zip`/`.aar` artifact consumed by Bazel's `ijar` (used to build interface jars for `java_library`/`java_import` and similar rules) can craft a central directory entry with an oversized `file_name_length`, `extra_field_length`, or nested extra-field `data_size` to push the read cursor past the end of the mmap'd input file. This causes:
- An out-of-bounds read that can crash the build process (SIGSEGV) when it crosses an unmapped page, and
- Potential leakage of adjacent process memory into the truncated `filename` buffer (up to `PATH_MAX-1` bytes) or into computed offsets used later in file processing, which is written into build artifacts/output paths — a memory-disclosure primitive analogous to the FontForge `getsid` over-read.

### Likelihood Explanation
Any dependency fetched via `http_archive`/`http_jar`/`http_file` and unpacked/interface-jarred by Bazel is untrusted content from a hostile origin; there is no sha256/integrity check that inspects internal zip structure (checksums only validate the whole downloaded blob, not that every field is well-formed once passed through this parser). The parser processes every central directory record in the file automatically, so any single malformed entry anywhere in a large dependency archive triggers the bug without additional attacker capability or timing requirements — likelihood is high once such an archive is built with by a project.

### Recommendation
Add the same `EnsureRemaining()`-style bounds checks used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry` (and to the extra-field walk) before advancing `p`/`extra_p`, validating each `file_name_length`, `extra_field_length`, `file_comment_length`, and nested extra-field `data_size` against the remaining bytes in the mapped buffer, aborting parsing with an error rather than reading out of bounds.

### Proof of Concept
Construct a minimal valid ZIP end-of-central-directory record where a single central directory entry declares `file_name_length = 0xFFFF` (or a similarly oversized `extra_field_length`) while the actual bytes in the file after that header are far shorter than declared, causing `p += file_name_length` in `ProcessCentralDirEntry` to point past `zipdata_in_ + input_file_->Length()`; feed it to `ZipExtractor::Create`/`ProcessAll` (as invoked by `ijar` when generating an interface jar) and observe an out-of-bounds `memcpy` read / crash, reproducible in a `third_party/ijar/zip_test.cc`-style unit test that opens this crafted archive and calls `ProcessAll()`.
