## Finding

### Title
`process_delivery_receipt` settles relayer reward and closes the pending order without checking the on-chain `success` flag of the delivery - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
The Snowbridge outbound queue V2 decodes a `DeliveryReceipt` from the `InboundMessageDispatched` Ethereum event, which carries an explicit `success: bool` field describing whether the message actually executed successfully on the Gateway contract. `Pallet::process_delivery_receipt` never inspects this field before releasing the relayer reward and permanently deleting the `PendingOrder`. This mirrors the external report's root cause: a validity/status signal exists in the data but the on-chain logic fails to gate acceptance on it, so an outcome that should be treated as "not completed" is instead accepted and settled as final.

### Finding Description
`DeliveryReceipt` is decoded straight from the verified Ethereum log: [1](#0-0) 

`process_delivery_receipt` uses only `receipt.gateway`, `receipt.nonce`, and `receipt.reward_address` to pay the reward and clear the order — `receipt.success` is decoded but discarded: [2](#0-1) 

Once `<PendingOrders<T>>::remove(nonce)` executes, there is no other storage record of the message's delivery state — no retry, no refund path, and `MessageDelivered` is emitted unconditionally regardless of whether the commands (e.g. asset unlocks/mints/transacts encoded in the original `OutboundMessage`) actually executed on Ethereum: [3](#0-2) 

The pallet's own doc-comment for the extrinsic flow only describes "verify the message ... fetch the pending order ... pay reward ... remove the order," with no mention of gating on delivery success: [4](#0-3) 

This breaks the pivot requirement that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — settlement (reward payment + order removal) proceeds even when the encoded `success` bit says execution failed on the Ethereum side.

### Impact Explanation
Assets/commands corresponding to an `OutboundMessage` are queued and committed on the BridgeHub side when the message is first accepted (nonce assigned, `PendingOrder` created) — see `process_outbound_message`: [5](#0-4) 
If the corresponding Ethereum-side execution reverts or otherwise fails (`success == false`), the relayer is still fully paid (`order.fee`) and the `PendingOrder` is deleted, permanently closing the book on that nonce. There is no compensating mechanism to retry delivery or refund/unlock the originating assets on the source chain once the order is gone, which is a form of "permanent user-fund or bridge-state lock" / bridge-reward mis-settlement as defined in the impact gate (payout state advances without confirmed successful settlement).

### Likelihood Explanation
Any relayer can trigger this path unprivileged by simply submitting a real, verifiably-proven `EventProof` for a delivery that the Gateway contract itself reports as failed (`success = false`), which is a legitimate, achievable on-chain event (out-of-gas execution, revert in a downstream command, etc.) — no malicious peer, validator, governance, or leaked key is required. The relayer only needs to wait for such a naturally occurring failed delivery and submit the honestly-provided proof to be rewarded as if the message fully succeeded.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`:
- If `true`, proceed exactly as today (pay reward, remove `PendingOrder`, emit `MessageDelivered`).
- If `false`, do not pay the relayer's fee for the failed portion (or reward only a base "attempt" fee if intended), and either keep the order in a distinct failed/retryable state or emit a `MessageDeliveryFailed` event and trigger any refund/unlock path for the affected assets, rather than silently discarding the order as delivered.

### Proof of Concept
1. A message is queued via `process_outbound_message`, creating `PendingOrders[nonce] = { fee, block_number }` and locking/burning the corresponding assets on BridgeHub/AssetHub side per the `OutboundMessage` commands.
2. The Gateway contract on Ethereum attempts to execute the message but a downstream command reverts, so the contract emits `InboundMessageDispatched(nonce, topic, success = false, reward_address)`.
3. A relayer builds a valid `EventProof` for this real, verifiable log (the log genuinely exists on-chain with `success = false`) and calls `submit_delivery_receipt`.
4. `T::Verifier::verify` succeeds (the proof is legitimate), `DeliveryReceipt::try_from` decodes `success = false` correctly, but `process_delivery_receipt` (lines 445-480 above) never reads `receipt.success`; it pays `order.fee` to the reward account and removes `PendingOrders[nonce]`, emitting `MessageDelivered`.
5. The assets associated with the failed command are never recovered, yet the bridge treats the nonce as fully and successfully settled — confirmed by the existing test suite, which only ever constructs receipts with `success: true` and never exercises the `false` branch, e.g. [6](#0-5) , showing no code path differentiates on this field.

**Note on confidence:** I was unable to fully confirm from the indexed code whether Snowbridge's design intentionally treats relayer reward as "payment for delivery attempt" independent of downstream execution outcome (which would make this a documented design choice rather than a bug) — the doc comments and code give no indication of intentional disregard, and the `success` field appears only to be decoded and otherwise unused across the reachable pallet code I could inspect. Confirming original design intent would require checking Snowbridge's off-repo specification/audit history, which is outside available tools.

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```

```rust
#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
}
```
