### Title
Missing content-hash verification of downloaded attachment data allows a malicious peer to poison the Atlas attachment cache and stall content resolution - (File: stackslib/src/net/atlas/download.rs)

### Summary
When `AttachmentsBatchStateContext::extend_with_attachments` processes a successful HTTP response for an `AttachmentRequest`, it inserts the peer-supplied `Attachment` into `self.attachments` without checking that `Hash160::from_data(attachment.content)` equals the requested `AttachmentRequest.content_hash`. Any peer chosen as a source can therefore return arbitrary bytes and have them accepted, stored under their own (attacker-computed) hash, while the legitimately committed `content_hash` is never resolved.

### Finding Description
`AttachmentRequest::sources` is populated in `AttachmentsBatchStateContext::get_prioritized_attachments_requests` [1](#0-0) , and the response is consumed in `extend_with_attachments`:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
``` [2](#0-1) 

`decode_atlas_get_attachment` (in `stackslib/src/net/api/getattachment.rs`) merely deserializes the JSON body into a `GetAttachmentResponse { attachment }` with no hash check against the request that was sent: [3](#0-2) 

Crucially, `extend_with_attachments` never references `request.content_hash` at all when validating `response.attachment` — the association between the request that was sent and the attachment that is stored is dropped entirely at this point. Once in `context.attachments` (a `HashSet<Attachment>`, keyed by content, not by the originally requested hash), the `Done` branch of `AttachmentsDownloader::run` processes each attachment using `attachment.hash()` (i.e., the hash of the *received* bytes, not the requested `content_hash`):
```
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;
    ...
    context.attachments_batch.resolve_attachment(&attachment.hash())
}
``` [4](#0-3) 

A remote peer included in `AttachmentRequest.sources` for a given `content_hash` can respond to `GET /v2/attachments/<content_hash>` with a JSON body containing arbitrary bytes `b` such that `Hash160::from_data(b) != content_hash`. The state machine accepts this response uncritically, computes `attachment.hash()` from the attacker's bytes, inserts it into `atlasdb` under that wrong hash, calls `find_all_attachment_instances(&attachment.hash())` (which will typically find nothing, since no legitimate on-chain instance references the attacker's bogus hash), and calls `resolve_attachment(&attachment.hash())` on the batch — which does not match the tracked `content_hash` in `attachments_batch.attachments_instances`. The legitimately requested `content_hash` is therefore never resolved (remains "missing"), the batch keeps getting retried/re-enqueued until `max_attachment_retry_count` is exceeded and dropped, and the attacker's row occupies a slot in `atlasdb`'s uninstantiated/instantiated attachment tables, contributing to eviction/slot pressure (`evict_expired_uninstantiated_attachments`, `evict_expired_unresolved_attachment_instances`).

### Impact Explanation
Any peer offering itself as a Atlas attachment-data source can, per response, cause the node to store attacker-controlled content under an attacker-chosen hash, and prevent the correct, on-chain-committed attachment content from ever being fetched/resolved by that node (since the state machine "gives up" on the content_hash after retries are exhausted). This matches the "attachment/BNS mismatch" and "serving non-canonical state as canonical" High-severity categories: the node's Atlas database can end up permanently missing the canonical attachment for a given BNS name/zonefile hash while holding garbage data under an unrelated hash, and legitimate RPC callers of `GET /v2/attachments/<content_hash>` for the real hash will continue to 404 indefinitely for that node.

### Likelihood Explanation
The attacker only needs to be a normal outbound-reachable peer with an advertised Atlas attachment inventory bit set for the page/index in question, so that it's picked as a `source` in `get_prioritized_attachments_requests`; no secret, signature, or privileged role is required. Attaching an attachment payload matching the fake inventory bit and returning arbitrary JSON is trivial and repeatable on every retry cycle for any content_hash the attacker wants to block.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (or in `decode_atlas_get_attachment`), verify `Hash160::from_data(&response.attachment.content) == request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed request (bump `report.bump_failed_requests()` and optionally mark peer as faulty) instead of accepting the payload.

### Proof of Concept
Add a unit test in `stackslib/src/net/atlas/tests.rs` (or a new test module) that:
1. Constructs an `AttachmentsBatchStateContext` with an `AttachmentRequest { content_hash: H, sources, .. }`.
2. Mocks a `BatchedRequestsResult` whose `succeeded` map contains that request paired with a `StacksHttpResponse` whose JSON body is `GetAttachmentResponse { attachment: Attachment { content: b"attacker bytes" } }` where `Hash160::from_data(b"attacker bytes") != H`.
3. Calls `context.extend_with_attachments(&mut results)` and then drives `AttachmentsDownloader::run`'s `Done` branch logic (or directly replicate the `attachments.drain()` loop) to assert:
   - `network.atlasdb.find_attachment(&H)` is still `None` (content_hash never resolved),
   - `network.atlasdb` gains a row for `Hash160::from_data(b"attacker bytes")` via `insert_instantiated_attachment`,
   - `context.attachments_batch.resolve_attachment(&H)` was never effectively called (the batch instance for `H` remains unresolved), confirming the mismatch causes indefinite non-resolution of `H` while attacker data is stored.
