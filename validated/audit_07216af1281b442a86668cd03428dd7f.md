## Finding

### Title
Unvalidated attacker-controlled array-length allocation in `ValidateMultiSign` precompile can trigger `NegativeArraySizeException`/`OutOfMemoryError` during decode - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The reported `postgres-protocol` bug is a classic "decode a length field taken directly from untrusted input, then use it unchecked for allocation/copy" pattern (CWE-20/CWE-248) that panics the client. The closest reachable analog in java-tron is the `ValidateMultiSign` precompiled contract, which is reachable from any TVM `CALL`/`STATICCALL` to address `0x66` with attacker-controlled calldata (any account can deploy a contract that invokes this precompile, or call it directly if permitted). It decodes a signature-array length straight from calldata via `DataWord.intValueSafe()` and immediately allocates `new byte[len][]` without validating the value unless a specific feature flag is active.

### Finding Description
`ValidateMultiSign.execute()` [1](#0-0)  parses the raw calldata into `DataWord[]` and computes the signature array via `extractBytesArray`/`extractSigArray` [2](#0-1) . Inside `extractBytesArray`, `len` comes directly from `words[offset].intValueSafe()` — a value fully controlled by the calldata — and is used unchecked to allocate `new byte[len][]`: [3](#0-2) 

The only bound on `len` (`sigArraySize > MAX_SIZE` check) is gated behind `VMConfig.allowTvmSelfdestructRestriction()` [4](#0-3) ; when that feature flag is not active, `extractBytesArray` is invoked with a raw, unvalidated length. Unlike its sibling `BatchValidateSign`, which wraps `doExecute` in a top-level `try { } catch (Throwable t)` [5](#0-4) , `ValidateMultiSign.execute()` has no such wrapper around the parsing/extraction step — the only inner `try/catch` starts after the signature array has already been built [6](#0-5) .

A crafted `len` value can therefore cause:
- `NegativeArraySizeException` if the decoded 256-bit word maps to a negative `int`, or
- `OutOfMemoryError` if `len` is large (up to `Integer.MAX_VALUE`), since `new byte[len][]` allocates an object-reference array proportional to `len`.

`Program.callToPrecompiledAddress` calls `contract.execute(data)` with no surrounding try/catch [7](#0-6) , so any uncaught exception/error propagates up the VM call stack until it reaches `VMActuator`'s outer `catch (Throwable e)` [8](#0-7) .

### Impact Explanation
`VMActuator`'s top-level `catch (Throwable e)` does absorb the exception and fails the transaction gracefully rather than crashing the JVM outright in the common case (`NegativeArraySizeException`). However, the `OutOfMemoryError` path is riskier: forcing the JVM to attempt a multi-gigabyte array allocation can trigger heap exhaustion and long GC pauses that affect concurrently executing transactions/threads on the node, degrading availability for all users even though the specific throwing thread's error is technically caught. This is a resource-exhaustion/DoS class issue analogous to the hstore panic, though — unlike the postgres-protocol case where the panic directly kills the client connection — java-tron's top-level exception handling substantially mitigates (but does not eliminate) the worst-case impact for the `NegativeArraySizeException` variant.

### Likelihood Explanation
Reachable from a single crafted transaction: any account can call/deploy a contract that issues a `CALL` to the `ValidateMultiSign` precompile address with attacker-chosen calldata, no special privilege required. The lack of the `MAX_SIZE` bound outside the `allowTvmSelfdestructRestriction()` flag, and the missing outer `try/catch` present in `BatchValidateSign`, both indicate this path was not hardened to the same degree as its sibling precompile.

### Recommendation
Add an outer `try { ... } catch (Throwable t) { return Pair.of(true, DATA_FALSE); }` around the parsing/extraction logic in `ValidateMultiSign.execute()`, mirroring `BatchValidateSign.execute()`. Additionally, validate the decoded `len` in `extractBytesArray`/`extractSigArray` (bounds-check against `MAX_SIZE` and non-negativity) unconditionally, not only when `allowTvmSelfdestructRestriction()` is enabled.

### Proof of Concept
Craft calldata for `ValidateMultiSign` (address `0x66`) where the fourth head word points to an array-length word set to a very large value (e.g., `0x7FFFFFFF`) or a value whose `intValueSafe()` result is negative, and issue a `CALL` opcode to that address from a deployed contract with `allowTvmSelfdestructRestriction()` not yet activated on the target network. This drives execution into `extractBytesArray`'s `new byte[len][]` with the unchecked length, producing `NegativeArraySizeException`/`OutOfMemoryError` inside `execute()`.

**Uncertainty / limitation:** I was unable to fully verify, given tool budget, whether `VMConfig.allowTvmSelfdestructRestriction()` is enabled by default on current mainnet/production configuration (which would make the `MAX_SIZE` guard always active and significantly reduce real-world exploitability), and I could not exhaustively trace all callers/consensus-critical paths that might re-execute this precompile outside the top-level `VMActuator` catch (e.g., during block replay). If `allowTvmSelfdestructRestriction()` is already active by default, exploitability of this specific analog is much lower.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }
