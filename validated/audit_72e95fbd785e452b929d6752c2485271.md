## Title
Integer division rounding-down in `MarketSellAssetActuator.matchSingleOrder` (taker == maker branch) lets a taker receive maker's full sell tokens while paying zero — analogous to JIT-minting free-token bug (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

## Summary
`MarketSellAssetActuator` implements TRON's on-chain order-book market (`MarketSellAssetContract`), matched via `matchOrder`/`matchSingleOrder`. When a taker order exactly consumes a maker order's remaining sell quantity, the payment the taker must give to the maker is computed via `MarketUtils.multiplyAndDivide`, an integer (floor) division. Unlike the sibling "taker > maker" branch, this specific branch omits the zero-result guard, so a specially crafted maker/taker order pair can cause the computed payment to round down to zero while the taker still receives the maker's full token amount — the same root cause as the reported JIT-minting bug (`buyerPayment = (fillAmount * price) / 10000` rounding to 0 while tokens are still minted).

## Finding Description
In `matchSingleOrder` (`actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java:402-499`), the "taker == maker" branch computes: [1](#0-0) 

```java
if (takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()) {
  makerBuyTokenQuantityReceive = MarketUtils
      .multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...);
  takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain();

  long takerSellTokenLeft =
      takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive;
  takerOrderCapsule.setSellTokenQuantityRemain(takerSellTokenLeft);
  makerOrderCapsule.setSellTokenQuantityRemain(0);
  ...
}
```

`multiplyAndDivide` performs `(makerSellRemainQuantity * makerBuyQuantity) / makerSellQuantity`, a floored integer division. If `makerSellQuantity` is large relative to `makerBuyQuantity` (i.e., a maker order with a very low unit price) and `makerSellRemainQuantity` is small (e.g. an almost-fully-filled maker order with a tiny remainder), this product can round down to `0`.

Compare this to the symmetric "taker > maker" branch a few lines below, which explicitly guards against this exact rounding-to-zero condition: [2](#0-1) 

```java
makerBuyTokenQuantityReceive = MarketUtils
    .multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...);

MarketUtils.updateOrderState(makerOrderCapsule, State.INACTIVE, marketAccountStore);
if (makerBuyTokenQuantityReceive == 0) {
  // the quantity is too small, return the remain of sellToken to maker
  // it would not happen here ...
  makerOrderCapsule.setSellTokenQuantityReturn();
  returnSellTokenRemain(makerOrderCapsule);
  return;
} else {
  ...
}
```

The "taker == maker" branch has **no equivalent `== 0` check**. If `makerBuyTokenQuantityReceive` rounds to zero there:
- `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` is still the maker's full non-zero remaining sell amount — the taker is credited this full amount via `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule)` ( [3](#0-2) ).
- `makerBuyTokenQuantityReceive = 0` is added to the maker's account, i.e., the maker gets nothing for giving up its full remaining sell balance.
- `takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - 0`, so the taker's own remaining "amount owed" is essentially unchanged — the taker's sell-side balance is not actually debited for this fill.

This mirrors the reported bug exactly: the buyer/taker side of a trade receives tokens while its corresponding payment amount computation rounds down to zero due to integer division, letting it capture the counterparty's locked assets for free.

## Impact Explanation
A maker can deliberately construct an order with an extreme price ratio (`makerSellQuantity` orders of magnitude larger than `makerBuyQuantity`) and, through partial fills, reduce `makerSellTokenQuantityRemain` to a small residual value that exactly matches the taker's computed `takerBuyTokenQuantityRemain`. When such a trade executes, the taker (which could be the same actor operating both sides, or any user who discovers/triggers this residual state) receives the maker's remaining sell-token balance for free, without paying the corresponding buy-token amount. Because `MAX_MATCH_NUM` (20) allows multiple maker orders to be consumed within a single `MarketSellAssetContract` transaction ( [4](#0-3) ), this could be chained across several maker orders to drain locked asset balances, directly causing unbacked token accounting / theft of funds from order-book participants — a Medium/High severity accounting bug.

## Likelihood Explanation
Exploitation requires an attacker to control (or be) the maker order and engineer the exact residual quantities so the "taker == maker" equality condition is hit with a rounding-to-zero maker price ratio. This is achievable by anyone placing sell/buy orders through `MarketSellAssetActuator` (a fully permissionless, unprivileged actuator reachable by any signed `MarketSellAssetContract` transaction), and does not require any special privilege, making it a realistically reachable, if somewhat orchestration-dependent, attack.

## Recommendation
Add the same zero-quantity guard used in the "taker > maker" branch to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0`, reject/return the maker's remaining sell tokens instead of proceeding to credit the taker with the maker's full sell-token remainder. Alternatively, enforce a minimum fillable quantity/price-ratio check before allowing order matching to proceed.

## Proof of Concept
1. Maker places a `MarketSellAssetContract` order selling token A for token B with `sellTokenQuantity = makerSellQuantity` (very large) and `buyTokenQuantity = makerBuyQuantity = 1` (minimal), producing a near-zero effective price.
2. Through prior partial fills (or direct order construction), reduce the maker order's `sellTokenQuantityRemain` to a small value `R` such that `R * makerBuyQuantity / makerSellQuantity == 0` (guaranteed whenever `R * makerBuyQuantity < makerSellQuantity`).
3. A taker places an order such that the computed `takerBuyTokenQuantityRemain` (via `MarketUtils.multiplyAndDivide`) exactly equals `R`, triggering the "taker == maker" branch in `matchSingleOrder`.
4. `makerBuyTokenQuantityReceive` evaluates to `0`; the taker is credited `R` units of token A (maker's full residual sell balance) via `addTrxOrToken`, while the maker receives `0` units of token B and the taker's own remaining sell-token balance is left effectively undebited.
5. Repeat against additional maker orders (up to `MAX_MATCH_NUM` per transaction, or across multiple transactions) to accumulate free tokens from multiple counterparties.

Note: I was unable to inspect the exact body of `MarketUtils.multiplyAndDivide` (only its call sites were retrieved) to confirm whether it uses plain floor division or `BigInteger`/`disableJavaLangMath`-based math in all code paths; this should be verified against the actual implementation before treating the PoC as fully confirmed, though the floor-division intent is evident from the surrounding comments and the explicit `== 0` guard present in the neighboring branch.
