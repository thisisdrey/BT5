### Title
FetchIntoObjectPool accepts arbitrary Origin repository without verifying pool membership, allowing shared object-pool poisoning - (File: internal/gitaly/service/objectpool/fetch_into_object_pool.go)

### Summary
`FetchIntoObjectPool` fetches objects/refs from an attacker-influenceable `Origin` repository into a shared `ObjectPool` repository that may be linked (via `objects/info/alternates`) to many other repositories/forks. The only validation performed, `validateFetchIntoObjectPoolRequest`, checks that origin and pool share the same storage — it never checks that `Origin` is the pool's designated/authoritative member.

### Finding Description
`validateFetchIntoObjectPoolRequest` performs two checks: that `Origin` and `ObjectPool` are non-nil, and that they are on the same storage: [1](#0-0) 

The handler then builds the origin directly from the request field and fetches from it into the pool without checking whether `Origin` is actually a member of `ObjectPool`, or whether the pool was ever linked/seeded from that repository: [2](#0-1) 

The underlying `FetchFromOrigin` operation similarly just performs `git fetch` from whatever `origin` path it is given into the pool, with no ownership check: [3](#0-2) 

This is structurally analogous to the reported bug class: a value that establishes a trust/authority relationship (the asset's aggregator; here, the pool's authoritative origin) can be repeatedly re-supplied on each call with a different, attacker-controlled value, and the system accepts it without checking it against the previously established value or membership relationship. Object pools are explicitly documented as a shared resource linked to multiple repositories via alternates, so any content fetched into the pool is visible to (and trusted by) every linked member: [4](#0-3) 

### Impact Explanation
Because the object pool's objects are shared across all linked members via alternates, an attacker who can invoke `FetchIntoObjectPool` (or cause it to be invoked, e.g. as an owner of some repository on the same storage as a target pool) with an `Origin` they control but that is *not* a legitimate pool member can inject arbitrary refs/objects into the shared pool under the `refs/remotes/origin/*` namespace. This can pollute or corrupt the pool's ref namespace and object set for every repository dependent on that pool, and creates a cross-repository object-injection primitive, undermining the pool's integrity guarantees documented in `doc/object_pools.md`.

### Likelihood Explanation
`FetchIntoObjectPool` is a `MUTATOR` RPC reachable given only storage-name and repository path knowledge for both `Origin` and `ObjectPool`; the request-level validation only enforces same-storage, not membership. Any caller capable of triggering this RPC with an arbitrary origin (e.g., through automation like a repository import/fork/replication flow that passes user-influenceable repository identifiers) can exploit this without additional privileges beyond what's needed to name two repository objects on the same storage.

### Recommendation
In `validateFetchIntoObjectPoolRequest` (or in the handler before calling `FetchFromOrigin`), verify that `Origin` is a recognized member of `ObjectPool` — e.g., by confirming the origin's `objects/info/alternates` already points at the pool (as enforced for `LinkRepositoryToObjectPool`'s no-clobber checks), or by consulting pool membership metadata, before permitting the fetch to proceed. Reject the request with `InvalidArgument`/`PermissionDenied` if `Origin` is not an established member of `ObjectPool`.

### Proof of Concept
1. Attacker controls (or can specify) a repository `Origin = attacker-repo` and knows/derives the relative path of a victim `ObjectPool` on the same storage (pools follow a predictable/derivable disk layout).
2. Attacker calls `ObjectPoolService.FetchIntoObjectPool` with `{ Origin: attacker-repo, ObjectPool: victim-pool }`.
3. `validateFetchIntoObjectPoolRequest` only checks storage equality and passes.
4. `FetchFromOrigin` executes `git fetch attacker-repo-path '+refs/*:refs/remotes/origin/*'` directly into `victim-pool`, importing attacker-controlled refs/objects into the shared pool, visible to every repository linked to that pool via alternates.

func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
}

# Object Pools

When creating forks of a repository, most of the objects for forked repository
and the repository it forked from are shared. Storing those shared objects
multiple times is a waste of disk space and also of CPU time, given that those
shared objects would have to be repacked for both repositories. To fix this
waste of resources, we use object pools, which are essentially a repository
which holds the shared objects of both repositories.

The sharing of objects for a given repository and its object pool is done via
alternate object directories which Gitaly sets up when linking a repository to
an object pool by writing the `objects/info/alternates` file.

## Lifetime of Object Pools

The lifetime of object pools is maintained via the
[ObjectPoolService](../proto/objectpool.proto), which provides various RPCs to
create and delete object pools as well as to add members to or remove members
from the pool.
