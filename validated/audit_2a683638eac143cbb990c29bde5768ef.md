### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` causes escalating per-transaction cost and potential DoS - (File: `chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java`)

### Summary
The legacy (non-optimized) delegated-resource accounting path in `FreezeBalanceActuator`/`UnfreezeBalanceActuator` stores every distinct delegation counterparty address inside a single `DelegatedResourceAccountIndexCapsule` record, in an unbounded `toAccountsList`/`fromAccountsList`. Every freeze or unfreeze transaction that touches this account must fully deserialize, linearly scan (`.contains()`), possibly copy, mutate, and reserialize this list. Because there is no cap on list size, a single account can grow this list arbitrarily large across many low-cost transactions, making every subsequent freeze/unfreeze operation on that account increasingly expensive to execute — the same class of bug as the reported `_unstake` `for`-loop DoS: an unbounded on-chain array iterated/mutated on every state-changing call, with no way to "skip" or reset it cheaply.

### Finding Description
When `dynamicStore.supportAllowDelegateOptimization()` is false (the pre-optimization path, still present and reachable in code), `FreezeBalanceActuator.delegateResource()` maintains index records like this: [1](#0-0) 

```
List<ByteString> toAccountsList = ownerIndexCapsule.getToAccountsList();
if (!toAccountsList.contains(ByteString.copyFrom(receiverAddress))) {
  ownerIndexCapsule.addToAccount(ByteString.copyFrom(receiverAddress));
}
```
The `.contains()` check and every `addToAccount` operate over the full list, which is stored as part of a single protobuf-backed capsule (`DelegatedResourceAccountIndexCapsule`) under one DB key. [2](#0-1) 

`addToAccount`/`addFromAccount` never enforce a maximum size, and `removeToAccount`/`removeFromAccount` copy the entire list into a new `ArrayList`, remove the entry, and rebuild the protobuf object — an O(n) operation triggered on every unfreeze: [3](#0-2) 

Because a delegator can create delegations to an unbounded number of distinct receiver addresses (each just a small `FreezeBalanceContract` with a `receiverAddress`), nothing in `validate()` bounds the number of unique counterparties. Each new counterparty permanently grows the single `DelegatedResourceAccountIndexCapsule` record for that owner (and correspondingly for each receiver's `fromAccountsList`). Every future freeze/unfreeze transaction touching that owner (or receiver) address must then load, scan, and rewrite this ever-growing list — the per-transaction execution cost grows roughly linearly (or, when combined with repeated adds/removes across many receivers, effectively worse) with the number of historical counterparties, while the on-chain fee for `FreezeBalanceContract`/`UnfreezeBalanceContract` delegation calls remains fixed/bandwidth-only (`calcFee()` returns 0 in the delegation branch).

### Impact Explanation
This mirrors the reported vulnerability class: an unbounded array stored under a single key, iterated and mutated on every subsequent state-changing operation, with no mechanism to bound or reset it. Consequences:
- Any account that has delegated resources to (or received delegations from) very many distinct counterparties becomes progressively more expensive, in real CPU/IO cost, to process on every subsequent freeze/unfreeze transaction — without a proportional increase in the resource/bandwidth fee charged, since fee accounting is based on transaction size, not on the size of an internal store record that must be deserialized and rewritten.
- Because delegation is a normal user-triggered operation (`FreezeBalanceContract` with `receiverAddress`) reachable by any account holder, an attacker can deliberately grow their own account's index record to a very large size, then use it to make ordinary future freeze/unfreeze operations on that same account artificially slow for full nodes / SRs validating the block, and can equally target another account by delegating resources *to* it from many freshly-created sender addresses, growing that victim's `fromAccountsList` without the victim's consent.
- This is a real-cost/DoS issue on legacy (`!supportAllowDelegateOptimization`) accounts and any account carrying pre-optimization index records; it does not directly cause fund theft, but it can degrade node performance/processing time for transactions touching the affected account, which is the exact impact class ("high gas cost" / DoS) called out in the report.

### Likelihood Explanation
Likelihood is moderate: the vulnerable branch is only exercised when `supportAllowDelegateOptimization` is disabled, and once enabled network-wide the new `delegate`/`unDelegate` keyed-by-pair storage avoids the unbounded list. However, (a) accounts that accumulated large `toAccountsList`/`fromAccountsList` records prior to the optimization being enabled retain these bloated records permanently since there is no migration/cap enforcement path shown other than lazy `convert()` on next use, and (b) the vulnerable code remains present and reachable for any deployment/testnet or historical chain state where the flag is off, or for any future regression that re-enables/uses the legacy path. An attacker needs only ordinary `FreezeBalanceContract` transactions with many distinct receiver addresses — fully within an unprivileged transaction broadcaster's capability.

### Recommendation
- Cap the number of distinct entries permitted in `toAccountsList`/`fromAccountsList` (similar to the `UNFREEZE_MAX_TIMES` cap already used for `unfrozenV2List`), rejecting further delegations to new distinct counterparties beyond the cap in `validate()`.
- Avoid storing an unbounded array under a single capsule/key; prefer a per-pair keyed store (as already done for the `supportAllowDelegateOptimization` path) universally, and provide an eager/forced migration (rather than lazy `convert()`) for any legacy records so that no account can retain an oversized `toAccountsList`/`fromAccountsList`.
- When removing an entry, avoid full-list copy/rebuild costs by using a data structure/backing store that supports O(1) or O(log n) removal instead of `ArrayList.remove` on a rebuilt protobuf list.

### Proof of Concept
1. Ensure `supportAllowDelegateOptimization` is disabled (default/historical state) via `DynamicPropertiesStore`.
2. From `OWNER_ADDRESS`, repeatedly submit `FreezeBalanceContract` transactions each with a `receiverAddress` set to a freshly generated address (as done in `FreezeBalanceActuatorTest.testMultiFreezeDelegatedBalanceForBandwidth`, which already demonstrates appending up to `RECEIVE_COUNT` (100) distinct receivers into `ownerIndexCapsule.getToAccountsList()`Increasing this to tens of thousands is limited only by account balance, not by any protocol-level cap): [4](#0-3) 
3. Observe that `ownerIndexCapsule.getToAccountsList().size()` grows without bound as more distinct receivers are used.
4. Subsequent `FreezeBalanceActuator`/`UnfreezeBalanceActuator` calls for `OWNER_ADDRESS` must deserialize, linearly scan (`contains`), and (for unfreeze) copy/rebuild this list — demonstrating the same growing per-call cost pattern described in the external report's `_unstake` for-loop DoS.
