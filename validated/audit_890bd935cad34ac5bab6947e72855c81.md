### Title
Buffer over-read parsing malformed Zip64 extra fields in central directory - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's zip reader parses the extra-field records that follow each central directory header without bounds-checking the declared per-record `data_size` against the remaining extra-field bytes, and reads 8-byte Zip64 values (`get_u8le`) from a Zip64 extra field without verifying it actually contains 8+ bytes of payload.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-controlled bytes in the central directory of a jar/zip file, with no validation that these lengths, combined with the current read offset, stay within the mapped input buffer [1](#0-0) .

It then walks the extra-field region using an unchecked loop:
```
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  if (header_id == ZIP64_EXTRA_FIELD_TAG) {
    if (*uncompressed_size == U4_MAX) *uncompressed_size = get_u8le(extra);
    ...
``` [2](#0-1) 

Two independent over-read conditions exist here:
1. The loop condition `extra_p != p` does not guarantee at least 4 bytes remain before calling `get_u2le(extra_p)` twice — if `extra_field_length` is not an exact multiple of `4 + data_size`, the last iteration can read past the end of the extra-field region (and potentially past the mapped file/buffer) before the loop terminates.
2. When `header_id == ZIP64_EXTRA_FIELD_TAG`, the code unconditionally calls `get_u8le(extra)` (reading 8 bytes) even though the declared `data_size` for that record could be less than 8 — the format allows partial Zip64 fields, and a malicious file can declare a header with `data_size < 8`, causing `get_u8le` to read beyond the intended record (and potentially beyond the whole extra-field/central-directory buffer) into adjacent memory.

By contrast, the local-header path (`ProcessLocalFileEntry`) does call `EnsureRemaining()` before reading variable-length fields [3](#0-2) , and the singlejar zip-header parsing utilities include explicit bounds checks such as `ExtraField::find` verifying `byte_ptr(start) + extra_field->size() > byte_ptr(end)` before dereferencing [4](#0-3) . `ProcessCentralDirEntry`, however, has no equivalent containment check for the extra-field walk, and no `EnsureRemaining` call is made before or during this loop.

### Impact Explanation
ijar is invoked by Bazel to build interface jars from arbitrary input jars supplied as build dependencies (e.g., a jar downloaded via `http_jar`/`http_archive`/a Maven-style rule). A jar whose bytes match a pinned `sha256`/`integrity` value can still be crafted by a malicious publisher to contain a malformed central-directory extra field, since checksum verification only guarantees byte-for-byte integrity, not that the content is well-formed. When such a jar is processed, `ProcessCentralDirEntry` performs an out-of-bounds read of process memory adjacent to the mapped input file. Depending on heap/mmap layout this can crash the ijar subprocess (denial of the specific build action) or leak adjacent memory bytes into the derived output artifact (e.g., through miscomputed sizes/offsets used later in `CalculateOutputLength` and entry copying), which is a data-disclosure concern analogous to the reported Mesa buffer over-read.

### Likelihood Explanation
Exploitability requires only crafting an unusual (but not necessarily "invalid" per the on-disk bytes a naive tool would accept) zip central directory with a Zip64 extra field whose declared payload is truncated, or with a extra-field-length value not evenly divisible into legitimate 4+`data_size` records. This does not require any privileged access — the attacker only needs to control the contents of a jar file that ends up as a build input (e.g., published as a project dependency archive). This makes the likelihood moderate: it is straightforward to construct such a file, but it requires the target to actually invoke ijar on that specific archive (i.e., use it as a `java_import`/similar dependency), which narrows applicability somewhat.

### Recommendation
Add explicit bounds checks in `ProcessCentralDirEntry`'s extra-field loop, mirroring the containment checks already used in `src/tools/singlejar/zip_headers.h`'s `ExtraField::find`:
- Before reading `header_id`/`data_size`, verify at least 4 bytes remain between `extra_p` and `p` (the end of the extra-field region).
- After computing `data_size`, verify `extra_p + data_size <= p` before advancing `extra_p` or dereferencing `extra`.
- Before calling `get_u8le(extra)` on the Zip64 tag, verify `data_size >= 8` (and, for consistency with the spec, that enough qualifying attributes are present) before reading each 8-byte value.
- On any violation, treat the file as malformed and return an error via `error(...)` rather than continuing to read, consistent with how `EnsureRemaining` is used in `ProcessLocalFileEntry`.

### Proof of Concept
A JUnit/`googletest`-style reproduction (analogous to the existing `CreateZipWithMalformedExtraField` helper already present in `src/tools/singlejar/output_jar_simple_test.cc` for the sibling singlejar zip parser [5](#0-4) ) would:
1. Build a minimal zip byte buffer containing one central directory header whose `extra_field_length` declares a Zip64 extra field (`header_id = 0x0001`) but with `data_size` set to, e.g., `2` (less than the 8 bytes `get_u8le` will read), and set the corresponding 32-bit size field to `U4_MAX` so the Zip64 branch is taken.
2. Feed this buffer as an `InputZipFile` to `ijar`'s `CalculateOutputLength()`/interface-jar generation path, which calls `ProcessCentralDirEntry` in a loop [6](#0-5) .
3. Run this under AddressSanitizer to confirm the heap-buffer-overflow (read) is triggered inside `get_u8le(extra)` at `third_party/ijar/zip.cc:533-539`.

Note: I was not able to find an existing automated test exercising `ProcessCentralDirEntry` with a malformed Zip64 extra field in the indexed portion of the repository; a new test would need to be authored following the pattern in `output_jar_simple_test.cc`.
