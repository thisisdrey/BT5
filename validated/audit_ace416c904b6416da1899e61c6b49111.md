### Title
Global chain-processing mutex held while blocking on a background reward-index computation causes node-wide hang - ([File: chainbase/src/main/java/org/tron/core/service/RewardViCalService.java])

### Summary
`allowOldRewardOpt`, when enabled by chain configuration, routes vote-reward computation through `RewardViCalService.getNewRewardAlgorithmReward()`, which blocks the calling thread on a `CountDownLatch.await()` until a background one-time indexing pass (`startRewardCal()`) completes. [1](#0-0) [2](#0-1) 

### Finding Description
`MortgageService.computeReward()` is invoked by `WithdrawBalanceActuator`, `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, and `VoteWitnessActuator` during actuator `execute()`. When `dynamicPropertiesStore.allowOldRewardOpt()` is true, `getOldReward()` delegates to `rewardViCalService.getNewRewardAlgorithmReward()`. If the one-time historical VI (value-index) computation has not finished (`isDone()` false), the calling thread blocks on `lock.await()` with no timeout until the background scheduled task (`es`) finishes `startRewardCal()` (an O(cycles × witnesses) iteration over the witness/delegation stores) and calls `clearUp(true)` → `lock.countDown()`. [3](#0-2) [4](#0-3) 

Critically, actuators run under `Manager`'s transaction/block processing lock: `pushTransaction()` executes `processTransaction()` inside `synchronized (transactionLock) { synchronized (this) { ... } }`, and block application (`pushBlock`/`processBlock`) similarly executes transactions under `synchronized (this)` on `Manager`. [5](#0-4) [6](#0-5) 

This mirrors the CVE-2021-47192 bug class exactly: a globally-serializing lock (there, SCSI `state_mutex`; here, `Manager`'s object monitor / `transactionLock`) is held while the code path blocks waiting on a separate subsystem to make forward progress. Any single unprivileged user broadcasting a `WithdrawBalanceContract`, `UnfreezeBalanceContract`, `UnfreezeBalanceV2Contract`, or `VoteWitnessContract` transaction can trigger this call path — no special privilege is required, since these are ordinary user-facing contract types processed by the actuator/validate-execute pipeline reachable from any signed transaction broadcast.

### Impact Explanation
While the calling thread is parked in `lock.await()`, it holds `Manager`'s global synchronization lock, blocking all subsequent transaction pushes and block application on that node until the background computation finishes. Since `startRewardCal()` iterates over every witness for every cycle since genesis (`LongStream.range(1, newRewardCalStartCycle)`), on a long-lived chain this can be a large, unbounded amount of work, and there is no timeout on the `await()`. During the block period after `allowOldRewardOpt` is enabled (before `isDone()` becomes true), any node whose first triggering transaction lands can effectively halt from processing new transactions/blocks — an availability impact (node halt) that is one of the accepted validate outcomes.

### Likelihood Explanation
Reachability requires only that `allowOldRewardOpt` be enabled via committee proposal (a normal on-chain config toggle, not attacker-controlled per se) and the first vote-reward-computing transaction to arrive before the background indexing completes. Once enabled, any of several commonly-used contract types (withdraw, unfreeze, unfreeze v2, vote) trigger the code path, so the race window is easily hit under normal chain operation, not requiring an adversarial actor to construct anything unusual — this is a config-gated but broadly reachable hang rather than a targeted exploit, so confidence in exact severity depends on how `allowOldRewardOpt` is activated in practice (governance-controlled), which I could not further verify from the indexed files.

### Recommendation
Move the `lock.await()` wait (or the entire reward lookup fallback) outside of any lock/monitor held by `Manager`, or bound the wait with a timeout and fail gracefully (e.g., fall back to the old cycle-by-cycle computation) rather than blocking indefinitely while holding a chain-wide serialization lock. Alternatively, ensure `RewardViCalService`'s indexing completes (synchronously, at startup, before enabling `allowOldRewardOpt`) so runtime actuator calls never need to await it.

### Proof of Concept
1. Deploy/run a node where the `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` dynamic property and `allowOldRewardOpt` become active while `RewardViCalService`'s background `es` task has not yet completed `startRewardCal()` (large chain history increases this window).
2. Have any unprivileged account broadcast a `WithdrawBalanceContract`, `UnfreezeBalanceContract`, `UnfreezeBalanceV2Contract`, or `VoteWitnessContract` transaction that reaches `MortgageService.computeReward()` with `beginCycle < newAlgorithmCycle`.
3. The transaction thread enters `Manager.pushTransaction()`'s `synchronized (transactionLock) { synchronized (this) {...} }` block, calls into the actuator, and blocks on `RewardViCalService.lock.await()`.
4. All other transaction/block processing on the node stalls until the background `startRewardCal()` finishes, evidencing the node-wide hang. [7](#0-6)

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
