### Title
TRC10 token balance overflow in `transferAllToken` (SELFDESTRUCT beneficiary transfer) bypasses overflow-safe accounting used everywhere else - (File: `actuator/src/main/java/org/tron/core/vm/utils/MUtil.java`)

### Summary
The Sherlock report flags that Surge's `Pool.sol` mints ERC20 shares in several places without updating `totalSupply`, breaking the ERC20 invariant that the sum of balances must equal `totalSupply`. The closest reachable analog in java-tron is `MUtil.transferAllToken()`, which moves *all* TRC10 token balances from a self-destructing contract to its beneficiary using raw, unchecked `long` addition instead of the overflow-checked accounting (`addExact`) that every other token-balance mutation path in the codebase uses.

### Finding Description
Every other TRC10 balance-mutating code path funnels through overflow-checked arithmetic:
- `AccountCapsule.addAssetAmountV2()` uses `addExact(currentAmount, amount, disableJavaLangMath)` [1](#0-0) 
- `RepositoryImpl.addTokenBalance()` (used by the `transferToken` VM opcode) also routes through `addAssetAmountV2` [2](#0-1) 
- `MUtil.transferToken()` calls `deposit.addTokenBalance(...)` for both sides of the transfer [3](#0-2) 

However, `MUtil.transferAllToken()` — invoked from `SELFDESTRUCT` handling in `Program.java` to sweep all of a contract's TRC10 balances to the specified beneficiary address — bypasses this and does the addition directly with the plain `+` operator, with no `addExact`/overflow check and no interaction with any `totalSupply` bookkeeping: [4](#0-3) 

Because `AssetIssueActuator.validate()` only requires `totalSupply > 0` and enforces no upper bound [5](#0-4) , any unprivileged asset issuer can create a TRC10 token with `totalSupply` close to `Long.MAX_VALUE`. An attacker who controls both the self-destructing contract's asset balance and the beneficiary account's asset balance for that same token can arrange for the unchecked `getOrDefault(tokenId, 0L) + amount` sum to exceed `Long.MAX_VALUE`, silently wrapping to a negative/garbage value. This breaks the implicit conservation invariant that all TRC10 transfer paths otherwise enforce (sum of balances == asset `totalSupply`), producing a corrupted/incoherent balance for the beneficiary account — the same class of impact called out in the report ("incorrect token balances and incoherence").

### Impact Explanation
A corrupted (wrapped) TRC10 balance breaks per-account accounting consistency for that asset and could produce a token balance value that no longer reflects real backing, undermining the “unbacked balance” property this scan is meant to catch. Because the mutation happens through `putAccountValue` directly (no validation of the resulting value), the corrupted number is persisted to state without any sanity check.

### Likelihood Explanation
Reaching this path requires: (1) issuing a TRC10 asset with a very large `totalSupply` (unprivileged, one signed `AssetIssueContract` transaction), (2) deploying a contract and accumulating large token balances on both the self-destructing contract and the beneficiary account for that asset, and (3) triggering `SELFDESTRUCT` with the crafted beneficiary. This is achievable purely through ordinary signed transactions/contract deployment without any special privilege, but requires precise setup (very large balances summing past `Long.MAX_VALUE`), making it a real but non-trivial-to-execute scenario.

### Recommendation
Route `transferAllToken()` through the same overflow-checked helper (`addTokenBalance`/`addAssetAmountV2` with `addExact`) used by `transferToken()` and other balance-mutating actuators, so that any overflow throws `ArithmeticException` and reverts the transaction instead of silently corrupting state.

### Proof of Concept
1. Issue TRC10 asset `X` with `totalSupply` set near `Long.MAX_VALUE` (allowed since `AssetIssueActuator.validate()` has no upper bound check).
2. Deploy contract `C` and, through normal token transfers, accumulate a large balance of `X` on `C` and separately on target beneficiary address `B` such that `balance(C, X) + balance(B, X) > Long.MAX_VALUE`.
3. From `C`, execute `SELFDESTRUCT` with `B` as beneficiary, triggering `Program`'s call into `MUtil.transferAllToken(deposit, C, B)`.
4. `toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount)` overflows silently, leaving `B`'s stored balance for `X` at an incorrect (wrapped) value that no longer matches the asset's real supply, unlike every other transfer path that would instead throw on overflow.

  public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }
