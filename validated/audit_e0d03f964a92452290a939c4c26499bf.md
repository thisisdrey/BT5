### Title
Users can acquire collateral positions in a deactivated (delisted) asset via `transfer`/`transferFrom`, bypassing the `isActive` deposit restriction - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
Metronome's `DepositToken` gates new deposits behind `isActive` (`onlyIfDepositTokenIsActive` on `_mint`), the equivalent of JOJO's `isDepositAllowed` check. However, the ERC-20 paths `transfer`, `transferFrom`, and the pool-called `seize` all route through `_transfer`, which credits the recipient's collateral balance and registers the token in `Pool.depositTokensOfAccount` without checking `isActive`. A holder of a deactivated deposit token can therefore "deposit" the disallowed collateral into arbitrary fresh accounts, which then count it toward borrowing power.

### Finding Description

- `deposit()` mints via `_mint`, which is protected by `onlyIfDepositTokenIsActive` — deactivating the token blocks new deposits:
  `DepositToken._mint` — [1](#0-0) 
  `DepositToken.deposit` — [2](#0-1) 

- But `transfer`/`transferFrom` only check the sender's unlocked balance and call `_transfer`, which adds the token to the recipient's per-account collateral list — no `isActive` check anywhere on this path: [3](#0-2) [4](#0-3) 

- `Pool.depositOf` iterates `depositTokensOfAccount` and counts every balance toward `_issuableLimitInUsd` regardless of the token's `isActive` flag: [5](#0-4) 

- `addToDepositTokensOfAccount` only verifies the caller is a registered deposit token, not that it is active: [6](#0-5) 

Concretely: governor calls `DepositToken.toggleIsActive()` to wind down a risky collateral. An attacker holding `msdTOKEN` calls `DepositToken.transfer(victim_or_sybil_account, amount)`. The recipient's `depositTokensOfAccount` gains the token, `debtPositionOf` counts it toward `_issuableLimitInUsd`, and the recipient can mint synthetics (`DebtToken.issue`/`mint`) against a collateral the protocol explicitly disabled — the exact invariant the JOJO issue describes ("disallowed tokens can still be deposited").

### Impact Explanation
Deactivating a deposit token is the protocol's lever to stop new exposure to a collateral (e.g., oracle deprecation, asset risk). The bypass lets any unprivileged user create brand-new collateralized positions backed by the disabled asset on fresh accounts and mint synthetic debt against them. If the asset was disabled because its pricing/oracle is being retired or it is considered risky, this re-opens exactly the exposure governance intended to close, potentially leading to protocol insolvency when the collateral is later removed or devalued. Note `removeDepositToken` requires `totalSupply == 0`, so disabling plus transfer-spreading also indefinitely blocks full delisting while holders refuse to withdraw — a liveness/governance-execution concern.

### Likelihood Explanation
Requires only that the attacker holds the deactivated `msdTOKEN` (acquired before deactivation or received from another holder) and calls a public `transfer`. No privileged roles, no oracle manipulation, no flash loans needed. The condition (`isActive == false` while supply > 0) is a routine governance state during collateral wind-downs.

### Recommendation
Add the `isActive` check to the crediting side of `_transfer`/`seize` — e.g., revert if `!isActive` when the recipient's balance transitions from zero — or gate `addToDepositTokensOfAccount`/`depositOf` to ignore inactive tokens when computing `_issuableLimitInUsd`. At minimum, inactive collateral should not increase an account's issuable debt limit.

### Proof of Concept
Hardhat sketch (extends `test/DepositToken.test.ts` fixtures):

```ts
// given: alice deposited MET while active
await metDepositToken.connect(governor).toggleIsActive() // deactivate collateral

// deposit is blocked
await expect(
  metDepositToken.connect(alice).deposit(parseEther('1'), alice.address)
).revertedWithCustomError(metDepositToken, 'DepositTokenIsInactive')

// but transfer bypasses the check
await metDepositToken.connect(alice).transfer(bob.address, depositedAmount)
expect(await metDepositToken.balanceOf(bob.address)).eq(depositedAmount)

// bob's deposit list now includes the inactive token and it counts toward issuable limit
expect(await pool.getDepositTokensOfAccount(bob.address)).contains(metDepositToken.address)
const [, , , issuableLimit] = await pool.debtPositionOf(bob.address)
expect(issuableLimit).gt(0) // bob can now mint synthetics against disabled collateral
```

The key assertion is that `debtPositionOf(bob)` credits the inactive collateral toward `_issuableLimitInUsd`, enabling `DebtToken.mint`/`issue` on a collateral that `deposit()` itself refuses to accept — a reproducible fork test against the deployed configuration.
