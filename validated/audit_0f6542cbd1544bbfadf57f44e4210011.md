### Title
Lighthouse trusts a construction-time snapshot of the local VPN network table that is never refreshed when the PKI certificate state changes - (File: `lighthouse.go`)

### Summary
`LightHouse` is built once with a *copy* of the current certificate's VPN network list (`cs.myVpnNetworks` / `cs.myVpnNetworksTable`), taken from the `PKI`'s `CertState` at construction time. `PKI.reloadCerts` (in `pki.go`) can later swap in a new `CertState` — including one with an expanded set of VPN networks (adding a v2 cert alongside an existing v1 cert is explicitly permitted: "adding certs is fine, actually") — by atomically storing it (`p.cs.Store(newState)`). Unlike every other piece of reloadable lighthouse state (`remoteAllowList`, `localAllowList`, `staticList`, `lighthouses`, `advertiseAddrs`, `relaysForMe`, `calculatedRemotes`, all `atomic.Pointer`), `myVpnNetworks`/`myVpnNetworksTable` are plain, non-atomic fields set only in `NewLightHouseFromConfig` and never re-derived from `PKI.getCertState()` afterward. This mirrors the RabbitHole bug class: a subordinate component (`LightHouse`) caches an address/state reference from a controlling component (`PKI`) at init time, and the controller's authoritative state can move on without the subordinate being told.

### Finding Description
`LightHouse.myVpnNetworksTable` is used as a security boundary check — it is the table consulted to make sure a host does not claim, as its own underlay/remote address, an address that falls inside the local node's VPN network range (see the "Make sure we won't add ips in our vpn network" filtering behavior exercised in `lighthouse_test.go`). [1](#0-0) 

This table is populated once, from the `CertState` handed in at construction: [2](#0-1) 

Meanwhile, `PKI.reloadCerts` can install a new `CertState` — including a superset of VPN networks when a v2 cert is added on top of an existing v1 cert — purely through an atomic store, with no mechanism shown to propagate the new network set back into the already-constructed `LightHouse`: [3](#0-2) [4](#0-3) 

Everything else in `LightHouse` that must reflect config/cert reloads uses `atomic.Pointer` fields explicitly so `reload()` can swap them safely at runtime: [5](#0-4) 

`myVpnNetworks`/`myVpnNetworksTable` conspicuously do not follow this pattern, strongly suggesting they are treated as immutable after construction even though the certificate (and thus the authoritative VPN network set) can be reloaded via SIGHUP without a process restart.

### Impact Explanation
If an admin performs a cert reload (SIGHUP) that adds VPN network coverage (e.g., rolling out a v2 certificate with additional/expanded networks alongside an existing v1 cert), the lighthouse's underlay-address sanity filter keeps using the stale, narrower network table. Any address that falls inside the newly-added VPN network range — which should be rejected as "an underlay address can't be inside our own VPN space" — would no longer be filtered out by the stale table. A remote peer could then supply, and have the lighthouse (or `HandshakeManager`, which also filters on `f.myVpnNetworksTable`/`f.myVpnAddrsTable`) accept, an underlay address which the current certificate policy is supposed to have excluded. This is a hostmap/lighthouse address-trust weakening: state used to validate/scrub remote address data becomes silently inconsistent with the live certificate authority state, without any error being surfaced to the operator, directly analogous to `QuestFactory` caching the old `rabbitholeReceiptContract` address while `Quest` moved on.

### Likelihood Explanation
Requires an admin-driven cert/config reload that changes the VPN network set (a supported, documented operation — SIGHUP reload of `pki.cert`/`pki.ca` is a core reload feature per `pki.go` and `CHANGELOG.md`). No attacker action is needed to create the mismatch; a remote, unauthenticated peer only needs to send handshake/lighthouse traffic afterward to exploit the stale boundary — reachable purely over the wire, no CA-signed certificate required to trigger the mismatch window.

### Recommendation
Make `myVpnNetworks`/`myVpnNetworksTable` `atomic.Pointer` fields on `LightHouse`, updated inside `lh.reload()` (and any equivalent path in `HandshakeManager`/`Interface`) by re-reading `f.pki.getCertState()` each time certs are reloaded, exactly the same way `remoteAllowList`/`staticList`/etc. are refreshed. All consumers of `myVpnNetworksTable` should load the current pointer rather than relying on a value captured at construction.

### Proof of Concept
1. Start nebula with a v1 cert whose `Networks()` is `10.0.0.0/24`.
2. `NewLightHouseFromConfig` captures `myVpnNetworksTable` = table containing `10.0.0.0/24` only.
3. Reload config with `pki.cert` containing an additional v2 cert whose networks include `10.1.0.0/24` (allowed per the "adding certs is fine" branch in `PKI.reloadCerts`). `PKI.cs` now atomically points to a `CertState` whose combined `myVpnNetworksTable` includes both `10.0.0.0/24` and `10.1.0.0/24`.
4. `LightHouse.myVpnNetworksTable` still only contains `10.0.0.0/24` (never refreshed).
5. A remote peer advertises an underlay address inside `10.1.0.0/24`. The lighthouse's "don't accept addresses inside our own VPN network" filter — which should now reject `10.1.0.0/24` — fails to do so because it is checking against the stale table, allowing the address to be recorded/distributed as if it were a legitimate external underlay address.

*Note: I was unable to fully inspect the body of `LightHouse.reload()` before running out of tool iterations to conclusively rule out an in-place refresh of these two fields; the finding rests on (a) the fields' non-atomic type in contrast to every other reloadable field in the struct, and (b) no call site found that re-derives them from `pki.getCertState()` after construction. This should be verified directly against `lighthouse.go`'s `reload` function before treating this as fully confirmed.*

func NewLightHouseFromConfig(ctx context.Context, l *slog.Logger, c *config.C, cs *CertState, pc udp.Conn, p *Punchy) (*LightHouse, error) {
	amLighthouse := c.GetBool("lighthouse.am_lighthouse", false)
	nebulaPort := uint32(c.GetInt("listen.port", 0))
	if amLighthouse && nebulaPort == 0 {
		return nil, util.NewContextualError("lighthouse.am_lighthouse enabled on node but no port number is set in config", nil, nil)
	}

	// If port is dynamic, discover it
	if nebulaPort == 0 && pc != nil {
		uPort, err := pc.LocalAddr()
		if err != nil {
			return nil, util.NewContextualError("Failed to get listening port", nil, err)
		}
		nebulaPort = uint32(uPort.Port())
	}

	h := LightHouse{
		ctx:                ctx,
		amLighthouse:       amLighthouse,
		myVpnNetworks:      cs.myVpnNetworks,
		myVpnNetworksTable: cs.myVpnNetworksTable,
		addrMap:            make(map[netip.Addr]*RemoteList),
		nebulaPort:         nebulaPort,
		punchy:             p,
		updateTrigger:      make(chan struct{}, 1),
		queryChan:          make(chan netip.Addr, c.GetUint32("handshakes.query_buffer", 64)),
		l:                  l,
	}
