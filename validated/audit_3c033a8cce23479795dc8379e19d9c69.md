### Title
Dust transfers fill a victim's per-account token list, blocking new deposits and collateral top-ups - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`DepositToken._transfer()` unconditionally registers the recipient in the pool's per-account `depositTokensOfAccount` set whenever they receive a token for the first time. `Pool.addToDepositTokensOfAccount` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` across `debtTokensOfAccount + depositTokensOfAccount` and reverts with `UserReachedMaxTokens()` once full. Because `transfer()`/`transferFrom()` only validate the *sender's* unlocked balance (`_revertIfLocked`) and never check whether the recipient's list has capacity, any unprivileged user can push dust amounts of many deposit tokens to a victim, permanently occupying list slots and causing all subsequent operations that add a new token for that account to revert.

### Finding Description
Relevant code paths:

- `DepositToken.transfer()` checks only the sender: `_revertIfLocked(_msgSender, amount_)`, then `_transfer(_msgSender, to_, amount_)` [1](#0-0) ; `transferFrom()` likewise only checks `sender_` [2](#0-1) .
- `_transfer` credits the recipient and, on first receipt, calls `pool.addToDepositTokensOfAccount(recipient_)` [3](#0-2) . A revert there rolls back the whole transfer — the recipient is never asked and never consented.
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts `UserReachedMaxTokens()` at `>= 30` combined entries [4](#0-3) [5](#0-4) .
- The same modifier protects `addToDebtTokensOfAccount` [6](#0-5) , so issuance of a *new* synthetic debt for the victim also reverts once the combined list is full.
- `_mint` in `DepositToken` performs the same registration on deposit [7](#0-6) , so `deposit()` into a collateral the victim doesn't already hold also reverts.

Attack: the attacker acquires dust balances of up to 30 distinct deposit tokens (the protocol itself caps the pool at 30 deposit tokens via `ReachedMaxDepositTokens` [8](#0-7) ) and calls `transfer(victim, dust)` on each. No consent, allowance, or recipient-side check exists to refuse. From then on, every call that would add a new token to the victim's account reverts: `deposit()` of any new collateral type, `transfer`/`transferFrom`/`seize` of any deposit token the victim doesn't already hold, and `DebtToken` issuance of any new synthetic.

### Impact Explanation
Temporary freezing / liveness loss with a path to direct loss:

1. The victim cannot deposit a *new* collateral type — `deposit()` reverts inside `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`. If the victim's position is drifting toward `debtPositionOf()._isHealthy == false`, the attacker can preemptively fill the list so that the only collateral the victim can top up is one already in their list; if they hold none liquid, `liquidate()` proceeds and their collateral is seized — a concrete loss enabled by the griefing.
2. The victim cannot receive any deposit token they don't already hold (transfers revert), cannot receive liquidation-seized tokens, and cannot issue new synthetic debt — all third-party-initiated credits to that account fail.
3. Recovery is possible but costly and not atomic: the victim must manually transfer out each dust token so `removeFromDepositTokensOfAccount` frees a slot [9](#0-8)  — up to 30 transactions, during which the attacker can re-fill freed slots. The freeze persists as long as the attacker is willing to re-grief.

No privileged role is needed: only public `transfer()` calls on production `DepositToken`s, so the modifier set (`_revertIfLocked`, `nonReentrant`, `whenNotShutdown`, SynthContext `_msgSender`) does not stop it — none inspects recipient list capacity.

### Likelihood Explanation
Requires the attacker to hold at least a dust amount of each deposit token type used. In pools with few registered deposit tokens this is cheap; filling all 30 slots requires sourcing dust across up to 30 collaterals (some may need a `deposit()` call each). Attack cost is bounded and repeatable; the victim cannot prevent it and cleanup is non-atomic (attacker can re-dust freed slots). Likelihood is moderate: it needs a pool with several deposit tokens and a victim worth targeting (e.g., a large position approaching liquidation).

### Recommendation
Do not gate unrequested incoming transfers on a hard per-account cap, or make registration non-reverting:
- In `DepositToken._transfer` / `_mint`, tolerate a full list (skip `addToDepositTokensOfAccount` or wrap in try/catch) so credits never revert — the list is only used by `depositOf`/`debtOf` views and liquidations; alternatively track collateral accounting without a capped enumerable set.
- If the cap must stay, revert only when the *sender/initiator* is the account being expanded (deposit/mint paths), not on passive receipt in `transfer`/`transferFrom`/`seize`, mirroring the fix pattern of validating the recipient side rather than punishing them.

### Proof of Concept
Reproducible in the existing Foundry/Hardhat setup (e.g., `test/DepositToken.test.ts` / `test/foundry/` harness):

```solidity
// Setup: pool with >= 2 deposit tokens (e.g. msdWETH, msdWBTC); attacker deposits dust
// in every registered deposit token to acquire transferable balances.

// 1) Attacker pushes victim's list to the cap (30 combined entries).
for (uint i; i < depositTokens.length; ++i) {
    IDepositToken dt = IDepositToken(depositTokens[i]);
    vm.prank(attacker);
    dt.transfer(victim, 1); // victim's _recipientBalanceBefore == 0 -> registers in list
}
// Victim now has debtTokensOfAccount.length + depositTokensOfAccount.length == 30

// 2) Victim tries to deposit a collateral type not already in their list.
vm.startPrank(victim);
underlying.approve(address(msdNEW), amount);
vm.expectRevert(IPool.UserReachedMaxTokens.selector);
msdNEW.deposit(amount, victim);

// 3) Any third-party transfer of a token victim doesn't hold also reverts.
vm.prank(attacker);
vm.expectRevert(IPool.UserReachedMaxTokens.selector);
msdNEW.transfer(victim, 1);

// 4) Consequence: while list is saturated, victim cannot top up new collateral;
//    if position becomes unhealthy, liquidate() succeeds against them and seize()
//    to the liquidator only works if the liquidator's own list has capacity —
//    attacker can grief liquidation targets pre-emptively.
```

Note: I could not exhaustively confirm within this iteration whether any production deployment actually registers ≥30 deposit tokens (the pool-level cap allows up to 30 [10](#0-9) ), but the code path is identical regardless of count — a smaller registered set just means fewer slots the attacker must fill before all *new* tokens are blocked.
