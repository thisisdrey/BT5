### Title
Out-of-bounds heap read when parsing a hostile ZIP64 extra field in `singlejar`'s `CDH`/`LH` size accessors - (File: `src/tools/singlejar/zip_headers.h`)

### Summary

### Finding Description
`singlejar` (used by Bazel to merge/pack jars for `java_binary`/`java_library`/deploy-jar actions) parses ZIP central-directory (`CDH`) and local-file (`LH`) headers directly from an `mmap`'d input jar with no application-level integrity check beyond the raw bytes matching whatever the build fetched (e.g. a third-party `.jar` obtained via `http_jar`/`http_file`/Maven coordinates). This is structurally analogous to CVE-2017-6300, where a fixed/derived-size field ("version field") in an attacker-controlled binary blob (a TNEF stream) was trusted without validating it against the actual payload extent, leading to an out-of-bounds access.

In `src/tools/singlejar/zip_headers.h`, `ExtraField::find()` bounds-checks only that `sizeof(ExtraField) + payload_size()` fits within `[start, end)`: [1](#0-0) 

`Zip64ExtraField::attr_count()` is derived from that same, attacker-controlled `payload_size()`: [2](#0-1) 

But `CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, and `CDH::local_header_offset()` compute the *index* into `attr_[]` from unrelated 32-bit sentinel fields (`compressed_file_size32_`, `uncompressed_file_size32_`) rather than from `attr_count()`: [3](#0-2) [4](#0-3) 

Because `attr64(index)` performs a raw `le64toh(attr_[index])` read with no bound check against `attr_count()`: [5](#0-4) 

an attacker who crafts a CDH entry with `compressed_file_size32_ == 0xFFFFFFFF` and/or `uncompressed_file_size32_ == 0xFFFFFFFF`, but attaches a Zip64 extra field whose declared `payload_size` is smaller than required (e.g. `0` or `8` instead of `24`), causes `attr64()` to read 8-byte quantities past the extra-field's validated payload region — an out-of-bounds read into whatever heap/mmap memory follows. `ExtraField::find()` only validated the *declared* payload size, not the size actually needed by the caller's index computation, so the "invariant that a checked field extent bounds every subsequent access" is broken exactly like the TNEF version-field overflow: a size/version-like descriptor is trusted for indexing without confirming its declared length matches what the parser will actually dereference.

The parsed (bogus) 64-bit size value then propagates into archive-processing logic (`InputJar`/`CDH` consumers in `output_jar.cc`/`combiners.cc`) that uses it to determine how many bytes of file data to copy/read from the mmap'd input, which can drive further out-of-bounds reads or corrupt output when merging jars.

### Impact Explanation
A malicious or compromised third-party jar dependency (fetched by URL, from a hostile mirror, or a malicious registry entry) can crash the `singlejar` build action with an out-of-bounds heap read (info leak / crash), and the corrupted size value derived from that read can affect how much data is copied during jar merging, producing incorrect/oversized reads from the mapped file region. This occurs purely from parsing content the build already trusts to consume once it has been fetched — no MITM or peer access to the build host is required. `sha256`/`integrity` pinning on the download only verifies the byte-for-byte content is what was hashed; it does nothing to prevent this parsing bug because the malicious structural inconsistency is baked into the file itself and is exactly what gets hashed and "verified".

### Likelihood Explanation
Any Bazel `java_*` target that depends on a third-party `.jar` (via `http_jar`, `http_file`, `http_archive`, or a Maven/registry ruleset) will run this parsing path during the deploy-jar/packaging build action. An attacker able to publish or serve a jar to a project's dependency list (compromised package, malicious mirror, malicious branch that a CI job builds) can trigger this by crafting a single central-directory entry with an inconsistent Zip64 extra-field size — no special privileges or timing needed. Constructing the crafted CDH bytes is straightforward given the header layout is a simple flat C++ struct.

### Recommendation
In `Zip64ExtraField`/`CDH`/`LH`, validate that `attr_count()` is large enough for the requested index before calling `attr64(index)` (i.e., check `index < attr_count()` in `CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, and `CDH::local_header_offset()`, and in the equivalent `LH` accessors), returning an explicit parse error instead of reading past the declared payload when the extra field is undersized relative to the sentinels that reference it.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/tools/singlejar` unit test (in the style of the existing `output_jar_simple_test.cc::CreateZipWithMalformedExtraField` helper) can construct a `CDH` with:
- `compressed_file_size32_ = 0xFFFFFFFF`
- `uncompressed_file_size32_ = 0xFFFFFFFF`
- a Zip64 extra field (`tag = 1`) with `payload_size = 8` (only one 8-byte attribute present, when two are required per spec/order)

and then call `cdh->compressed_file_size()`, which computes `attr_no = zfield_has_ext64(uncompressed_file_size32())` (i.e. `1`) and calls `z64->attr64(1)`, reading 8 bytes beyond the field's validated 8-byte payload — verifiable under ASan as a heap-buffer-overflow read. I was not able to fully trace every downstream consumer of this value (e.g., exact copy loops in `output_jar.cc`/`combiners.cc`) within the available search budget; a background Devin session with full repository access would be needed to confirm the exact secondary impact (corrupted copy length vs. pure OOB read) and to write the full JUnit/C++ regression test.

  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
