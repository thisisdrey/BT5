### Title
Unprivileged attacker can fill a victim's per-account token list with dust deposits, DoS-ing collateral top-ups and new borrowing until liquidation (`Pool.sol` / `DepositToken.sol`)

### Summary
`Pool` tracks per-account holdings in two `MappedEnumerableSet`s (`depositTokensOfAccount`, `debtTokensOfAccount`) capped at `MAX_TOKENS_PER_USER = 30`. Entries are added inside `DepositToken._mint`/`_transfer` (which call `pool.addToDepositTokensOfAccount`) and `DebtToken._mint` (which calls `pool.addToDebtTokensOfAccount`). `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once the combined count hits 30 [1](#0-0) . Because `deposit(amount_, onBehalfOf_)` lets anyone mint msdTOKEN to an arbitrary `onBehalfOf_` address, an attacker can force-add a deposit-token entry to any victim's list for nothing more than a dust amount of underlying [2](#0-1) . Once the victim's list is full, every path that adds a *new* token entry to their account reverts.

### Finding Description
The bug class mapped from CVE-2020-2770 is "authenticated-but-low-skill DoS via a state-writing code path" — here the reachable analog is griefing of the per-account token registry.

Attack flow (all calls permissionless, attacker = EOA):

1. For each listed `DepositToken` `d_i` that the victim does not yet hold, attacker calls `d_i.deposit(1 wei-equivalent dust, victim)`. This pulls `amount_` of underlying from the attacker to the treasury and `_mint`s dust msdTOKEN to the victim, which calls `pool.addToDepositTokensOfAccount(victim)` [3](#0-2) . (Alternatively the attacker can `d_i.transfer(victim, dust)` from their own balance [4](#0-3) .)
2. Once `depositTokensOfAccount.length(victim) + debtTokensOfAccount.length(victim) >= 30`, any subsequent call that would add a *new* token to the victim's lists reverts:
   - `DepositToken.deposit(x, victim)` for any collateral type the victim doesn't already hold — reverts inside `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens` [5](#0-4) .
   - `DebtToken.issue(...)` from the victim for any synthetic they haven't borrowed before — reverts inside `_mint` → `addToDebtTokensOfAccount` [6](#0-5) .
   - `DepositToken.transfer`/`transferFrom`/`seize` *to* the victim for a new token — reverts, so third parties (and `SmartFarmingManager` flows that mint/deposit on the victim's behalf) also fail.

There is no flag, modifier, or check that prevents a third party from writing to a victim's list: `deposit` only requires `whenNotPaused`, `nonReentrant`, `onlyIfDepositTokenExists`, a nonzero amount, and nonzero beneficiary. Neither pause, `SynthContext`, `MAX_TOKENS_PER_USER` itself, nor any health check distinguishes "the account owner deposited" from "an attacker deposited dust on their behalf."

### Impact Explanation
Temporary denial of service of a victim's position management, repeatable indefinitely:

- A victim whose position is trending toward liquidation **cannot add collateral of a new type** to restore health (`deposit` reverts), and cannot open new borrows. They can be pushed into liquidation while the only remediation that would have saved them — topping up a different, cheaper collateral — is blocked. That converts a liveness DoS into a realized loss via forced liquidation (liquidation fee + unfavorable seize) — i.e., temporary freezing of funds with consequential loss, matching the "temporary freezing of funds" impact class.
- Recovery requires the victim to notice and `transfer` the dust msdTOKENs out (each transfer removes an entry when their balance hits zero [7](#0-6) ), but the attacker can cheaply re-fill the list, turning remediation into an ongoing gas-cost race.

### Likelihood Explanation
- Fully unprivileged: only needs small amounts of listed underlyings and gas. No governor/keeper/oracle cooperation required.
- Cost scales with the number of listed deposit tokens the victim doesn't already hold (bounded by the pool's own `ReachedMaxDepositTokens` cap, also `MAX_TOKENS_PER_USER`); on pools with many collaterals the attack reaches the cap on deposit tokens alone.
- Not blocked by any deployed modifier: `deposit` is `whenNotPaused nonReentrant onlyIfDepositTokenExists` only; `addToDepositTokensOfAccount` is externally callable by any registered `DepositToken` for any `account_`.
- Caveats lowering severity: it doesn't freeze existing balances (withdraw/repay of already-held tokens still work), and it cannot push *debt* tokens onto the victim (debt tokens are non-transferable and mint only to the borrower/SmartFarmingManager), so blocking `issue` requires the victim to not already hold that debt token.

### Recommendation
- Decouple "receive" from "accounting": don't revert in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` when the cap is hit — e.g., return `false` and let `debtOf`/`depositOf` iterate differently, or track membership in a bounded way that can't be externally filled.
- Alternatively, only add a deposit-token entry on behalf of `_msgSender()` (remove third-party beneficiary minting to the list, or require `onBehalfOf_ == _msgSender()` / `recipient_ == sender_` for list insertion), and document that received-dust balances are still priced via balance checks rather than list membership.
- At minimum, emit events and keep removal paths (transfer-out) cheap so victims can self-recover.

### Proof of Concept
Hardhat sketch against deployed-style contracts (mainnet fork), assuming at least 2 listed deposit tokens (`msdA`, `msdB`):

```ts
// attacker holds dust of underlyingA and underlyingB
const victim = bob.address
const count = await pool.MAX_TOKENS_PER_USER() // 30

// 1) Fill victim's deposit-token list to the cap
for (const d of allListedDepositTokens) {
  if ((await d.balanceOf(victim)).isZero()) {
    await underlyingOf[d].approve(d.address, DUST)
    await d.deposit(DUST, victim) // mints dust msdTOKEN to victim, list++
  }
}
expect(
  (await pool.getDepositTokensOfAccount(victim)).length +
  (await pool.getDebtTokensOfAccount(victim)).length
).to.eq(count)

// 2) Victim tries to deposit a collateral type they don't hold yet
const newDep = someDepositTokenVictimDoesntHold
await underlyingNew.mint(victim, amount)
await underlyingNew.connect(bob).approve(newDep.address, amount)
await expect(newDep.connect(bob).deposit(amount, victim))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 3) Victim tries to issue a new synthetic (new debt token entry)
await expect(newDebtToken.connect(bob).issue(issueAmount, victim))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 4) While blocked, victim's unhealthy position can be liquidated normally
await expect(pool.liquidate(victim, msynth, repayAmt, victimDepositToken))
  .to.emit(pool, 'PositionLiquidated') // succeeds; victim couldn't add collateral to avoid it
```

All steps use only public entry points (`DepositToken.deposit`, `transfer`, `DebtToken.issue`, `Pool.liquidate`) by an unprivileged account; no privileged roles or manipulated oracle data are required.
