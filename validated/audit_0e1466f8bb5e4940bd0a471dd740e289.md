Audit Report

## Title
Permanent Fund Lock in `pallet-asset-rewards` from Uncapped `last_update_block` After Pool Expiry - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`update_pool_rewards()` unconditionally sets `PoolInfo.last_update_block` to the current block number instead of capping it at `expiry_block`, unlike `reward_per_token()`'s accrual window which is correctly capped via `last_block_reward_applicable`. Once any staker calls `unstake` on their own account after `expiry_block` (permitted regardless of expiry), the persisted `last_update_block` exceeds `expiry_block`, causing every subsequent `reward_per_token()` call to underflow in `ensure_sub` and revert.

## Finding Description
`reward_per_token()` computes rewardable blocks as `last_block_reward_applicable(pool_info.expiry_block).ensure_sub(pool_info.last_update_block)` ( [2](#0-1) ), where `last_block_reward_applicable` returns `min(now, expiry_block)` ( [3](#0-2) ). But `update_pool_rewards()` persists `last_update_block = T::BlockNumberProvider::current_block_number()` unconditionally, without capping to `expiry_block` ( [1](#0-0) ).

`unstake` explicitly permits the staker to act on their own account regardless of expiry (`ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin)`, [4](#0-3) ) and always calls `update_pool_and_staker_rewards` → `update_pool_rewards` before persisting via `Pools::<T>::insert(pool_id, pool_info)` ( [5](#0-4) ). `update_pool_and_staker_rewards` itself routes through the uncapped `update_pool_rewards` ( [7](#0-6) ).

Once a call after expiry sets `last_update_block > expiry_block`, any future `reward_per_token()` invocation computes `expiry_block.ensure_sub(last_update_block)`, which underflows on the unsigned `BlockNumberFor<T>` type and returns `Err`. This affects `stake`, `unstake`, `harvest_rewards`, `set_pool_reward_rate_per_block`, and `set_pool_expiry_block` — all of which call `reward_per_token()` first. `set_pool_expiry_block` itself calls `reward_per_token(&pool_info)` on the already-corrupted state before applying a new expiry ( [6](#0-5) ), so it also fails, leaving no admin remediation path.

## Impact Explanation
Once triggered, `total_tokens_staked` can never be reduced via `unstake` for remaining stakers, and `harvest_rewards` permanently fails, since both call `reward_per_token()`. `cleanup_pool`-style recovery requires no remaining stakers, which cannot be reached once other stakers are locked out. Staked asset balances and unclaimed reward-asset balances held in the pool's sub-account (derived in `pool_account_id`, [8](#0-7) ) become permanently unreachable, matching the "permanent user-fund or bridge-state lock" impact category.

## Likelihood Explanation
No privileged actor or special conditions are required. Any staker can call `unstake` on their own position after `expiry_block` has passed while other stakers remain in the pool — this is explicitly permitted by the `caller == staker` bypass in the expiry check — and this ordinary action alone corrupts the shared `PoolInfo.last_update_block` for all remaining stakers. Any pool that outlives its `expiry_block` while holding more than one staker is exposed via routine usage.

## Recommendation
In `update_pool_rewards()`, set `new_pool_info.last_update_block = Self::last_block_reward_applicable(pool_info.expiry_block)` instead of the raw current block number, mirroring the cap already applied in `reward_per_token()`. This keeps `last_update_block` bounded by `expiry_block`, eliminating the underflow in subsequent `ensure_sub` calls.

## Proof of Concept
1. Create a pool with `expiry_block = 25` and two stakers, `staker1` and `staker2`, both staking non-zero amounts before expiry.
2. Advance the block number past `expiry_block` (e.g., block 30) without calling `set_pool_expiry_block`.
3. `staker1` calls `unstake(pool_id, amount, None)` for their own stake (`caller == staker` bypasses the expiry check at [4](#0-3) ); this persists `pool_info.last_update_block = 30` while `expiry_block` remains `25`.
4. `staker2`, who still has staked tokens, calls `unstake` or `harvest_rewards`. `reward_per_token()` computes `last_block_reward_applicable(25).ensure_sub(30)` = `25 - 30`, which underflows and returns `Err`, causing the call to fail.
5. The pool admin attempts `set_pool_expiry_block` to fix the pool; this also fails because it first calls `reward_per_token(&pool_info)` on the stale, corrupted `pool_info`.
6. `staker2`'s stake and any pending rewards are now permanently locked in the pool's sub-account, with no available extrinsic path to recover them.
