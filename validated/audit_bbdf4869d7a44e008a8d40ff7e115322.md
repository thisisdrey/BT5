### Title
Exchange trades silently and indefinitely skipped from block packing when `ALLOW_HARDEN_EXCHANGE_CALCULATION` is not enacted, freezing Exchange pool liquidity - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
`Manager.generateBlock()` silently drops every pending `ExchangeTransactionContract` from block packing whenever the chain parameter `ALLOW_HARDEN_EXCHANGE_CALCULATION` has not yet been enacted by committee proposal, via the `isExchangeTransaction()` gate. This mirrors the Perennial M-11 pattern where transactions of a specific class are perpetually held back pending an external state transition, preventing time-sensitive operations (there: liquidations; here: exits/trades against Exchange pools) from ever confirming.

### Finding Description
In `generateBlock()`, every transaction pulled from `pendingTransactions`/`rePushTransactions` is checked with `isExchangeTransaction()` before being packed: [1](#0-0) 

`isExchangeTransaction()` returns `true` (meaning "skip this transaction") for any `ExchangeTransactionContract` unless `allowHardenExchangeCalculation()` is enabled: [2](#0-1) 

`allowHardenExchangeCalculation()` is a dynamic property backed by the `ALLOW_HARDEN_EXCHANGE_CALCULATION` committee proposal parameter, which is gated behind fork `VERSION_4_8_2` and requires an explicit governance proposal/vote to become `1`: [3](#0-2) [4](#0-3) 

Separately, there is a `rejectExchangeTransaction()` helper that throws a hard `ContractValidateException("ExchangeTransactionContract is rejected")` once a *different* fork (`VERSION_4_8_0_1`) has passed: [5](#0-4) 

Because the "hard reject" fork (`VERSION_4_8_0_1`) and the "re-enable via hardened math" fork (`VERSION_4_8_2`, `ALLOW_HARDEN_EXCHANGE_CALCULATION`) are two independent, sequentially-activated governance switches, there is a window (and, if the committee never approves `ALLOW_HARDEN_EXCHANGE_CALCULATION`, an indefinite window) in which:
- transactions are not rejected at admission/validation time (so an ordinary account can freely submit `ExchangeTransactionContract`), but
- `generateBlock()` unconditionally and silently `continue`s past them every time a block is produced, on every super representative, because the skip condition is derived from global chain state (`allowHardenExchangeCalculation()`), not from any per-transaction or per-witness decision.

This is structurally identical to the Perennial M-11 bug class: a class of transactions is blocked from ever being committed pending an external state transition (there: a new oracle version request; here: a committee-approved hard-fork flag), with no fallback path for the blocked transactions to be processed by any means available to the ordinary caller.

### Impact Explanation
Balances that have already been deposited into an `Exchange`/`ExchangeV2` pool via `ExchangeCreateContract` can only be exited or traded through `ExchangeTransactionContract`. If that contract type is perpetually skipped from block packing (because `ALLOW_HARDEN_EXCHANGE_CALCULATION` has not been enacted, which is its default state until a witness/committee vote), pool participants have no way to trade against or withdraw their share of Exchange liquidity — an ordinary, unprivileged asset holder's funds locked in the exchange pool become effectively frozen for as long as this flag remains unenacted, with no error surfaced to explain why their transaction never confirms (it simply expires after the transaction's `expiration` window, over and over).

### Likelihood Explanation
Any account with existing Exchange pool participation is affected purely by submitting an ordinary, well-formed `ExchangeTransactionContract` — no special privilege or malicious actor is required. The condition is entirely a function of chain-wide governance state (`ALLOW_HARDEN_EXCHANGE_CALCULATION`), so the behavior is deterministic and reproducible by every honest witness once that flag is unset, which is the default/starting condition for any chain instance until the community explicitly votes it in.

### Recommendation
Do not silently `continue` past `ExchangeTransactionContract` transactions in `generateBlock()` while leaving them valid at admission. Either:
1. Reject `ExchangeTransactionContract` at validation/admission time consistently with `rejectExchangeTransaction()` so senders get immediate, explicit feedback instead of silent exclusion from blocks, or
2. Route unhardened exchange transactions through the legacy (non-strict-math) execution path instead of dropping them, so they are still processed and can confirm.
In either case, ensure the fork/parameter gating between `VERSION_4_8_0_1` (hard reject) and `ALLOW_HARDEN_EXCHANGE_CALCULATION` (`VERSION_4_8_2`, hardened re-enable) has no gap window where a transaction type is neither rejected nor processed.

### Proof of Concept
1. Deploy/operate a chain where `ALLOW_HARDEN_EXCHANGE_CALCULATION` has not been enacted (default state) and fork `VERSION_4_8_0_1` has not yet triggered `rejectExchangeTransaction()` rejection at admission (or is bypassed/not yet active in the relevant code path).
2. An unprivileged account with existing `Exchange`/`ExchangeV2` balances broadcasts a valid `ExchangeTransactionContract`.
3. The transaction is accepted into `pendingTransactions` (not rejected at validation).
4. Every witness's `generateBlock()` call reaches the loop at [1](#0-0)  and calls `isExchangeTransaction()`, which returns `true` per [2](#0-1) , causing `continue` — the transaction is never packed into any block.
5. The transaction eventually expires unconfirmed; the sender cannot trade against or withdraw pool liquidity through any other transaction type, repeating indefinitely for any resubmission while the flag remains disabled.

Note: I was unable to fully trace every call site of `rejectExchangeTransaction()` (only a reflective invocation is visible in test code) to confirm whether admission-time rejection is universally wired in for all transaction entry points (P2P broadcast vs. local API), so the exact width of the "silently skipped but not rejected" window could not be fully verified from the indexed code alone.

  private boolean isExchangeTransaction(Transaction transaction) {
    if (getDynamicPropertiesStore().allowHardenExchangeCalculation()) {
      return false;
    }
    Contract contract = transaction.getRawData().getContract(0);
    switch (contract.getType()) {
      case ExchangeTransactionContract: {
        return true;
      }
      default:
        return false;
    }
  }
