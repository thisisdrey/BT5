I found a solid analog. The `Banlist<T>::ban()` function in `net-utils/src/banlist.rs` exhibits exactly the same bug class as the reported `AssetLock.sol` issue: it unconditionally overwrites the existing expiration timestamp with a newly-computed one instead of taking the `max()` of the two, allowing a concurrent race to silently shorten an active ban.### Title
Concurrent bans on the same peer can silently shorten an active ban's expiration due to unconditional overwrite instead of monotonic-max update - (File: `net-utils/src/banlist.rs`)

### Summary
`net-utils/src/banlist.rs`'s `Banlist::ban()` computes a new expiration instant and unconditionally `insert()`s it into the map, overwriting whatever expiration was previously stored for that key — with no comparison against the existing value. This is the same bug class as the reported `AssetLock.sol` issue: a "renew/extend" operation that should only ever move a time-bound value forward can instead move it backward, because the code takes the *new* value unconditionally instead of `max(existing, new)`.

### Finding Description
`Banlist<T>::ban()` is implemented as: [1](#0-0) 

```rust
pub fn ban(&self, id: T, timeout: Duration) -> bool {
    debug_assert!(!timeout.is_zero());
    debug_assert!(Instant::now().checked_add(timeout).is_some());
    let Some(expires_at) = Instant::now().checked_add(timeout) else {
        return false;
    };
    let prev = self.banned.write().unwrap().insert(id, expires_at);
    debug_assert!(prev < Some(expires_at));
    prev.is_some()
}
```

Each call computes `expires_at = Instant::now() + timeout` *before* acquiring the write lock, then blindly overwrites the map entry. There is only a `debug_assert!(prev < Some(expires_at))` — compiled out in release builds — guarding the invariant that a new ban should never regress an existing one.

This `Banlist<Pubkey>` is wrapped by `SimpleQosBanlist` and shared across multiple independent, concurrently-invoked banning call-sites that ban the *same identity* for unrelated reasons: [2](#0-1) 
- `bls-sigverify/src/bls_cert_sigverify.rs` bans a pubkey on certificate verification failure.
- `bls-sigverify/src/bls_vote_sigverify.rs` bans a pubkey on invalid vote verification. [3](#0-2) [4](#0-3) 

Both of these run inside parallel sig-verify worker pools (`thread_pool.install(...)` / `rayon` par-iterators), so two threads can race to ban the same offending pubkey concurrently, each independently computing `expires_at` from `Instant::now()` before contending for the write lock. Whichever thread's `insert()` executes *last* wins, regardless of which one computed the later (correct, extended) expiration. If the thread that computed the earlier `expires_at` (e.g., from an earlier-arriving invalid vote) is scheduled to write *after* the thread with the later `expires_at` (from an invalid certificate arriving slightly afterward), the final stored value is the smaller one — silently truncating what should have been the longer, most-recent ban.

This directly mirrors the reported bug: a value meant to only monotonically increase (lock end time / ban expiration) is instead overwritten unconditionally by whatever call happens to write last, with no `max()` comparison enforced at runtime.

### Impact Explanation
The banlist exists to protect the leader/validator (via `SimpleQos` in the QUIC streamer, and the BLS cert/vote sigverify pipelines) from misbehaving or malicious peers by temporarily denying them service. A silently truncated ban duration allows a malicious/misbehaving validator identity to be re-admitted to the connection table and resume sending invalid votes/certificates or consuming QUIC connection/stream resources sooner than the banning logic intended — i.e., QoS/anti-abuse evasion. Because the guard against this is only a `debug_assert!`, release (production) validator builds have no runtime protection against the race, so the truncation happens silently with no logged inconsistency.

### Likelihood Explanation
This requires no privileged role — any adversarial peer/validator identity that triggers ban-worthy behavior across two different sig-verify banning paths in close succession (e.g., sending an invalid vote and an invalid certificate nearly simultaneously) can create the race window, since both `bls_cert_sigverify` and `bls_vote_sigverify` verification run in parallel thread pools and both call `banlist.ban()` for the same pubkey. The race is a matter of thread-scheduling timing rather than a rare or hard-to-trigger condition, and an attacker who controls when/how quickly they emit multiple kinds of invalid messages has some influence over triggering it repeatedly.

### Recommendation
Change `Banlist::ban()` to only ever extend (never shorten) an existing ban, e.g.:
```rust
pub fn ban(&self, id: T, timeout: Duration) -> bool {
    let Some(expires_at) = Instant::now().checked_add(timeout) else {
        return false;
    };
    let mut banned = self.banned.write().unwrap();
    let prev = banned.get(&id).copied();
    let new_expiry = prev.map_or(expires_at, |p| p.max(expires_at));
    banned.insert(id, new_expiry);
    prev.is_some()
}
```
This guarantees the stored expiration is always `max(existing, new)`, eliminating the ordering-dependent truncation, and removes reliance on a release-mode-disabled `debug_assert!` for a correctness property.

### Proof of Concept
1. Thread A (from `bls_vote_sigverify`) detects an invalid vote from pubkey `P` at time `t0` and calls `banlist.ban(P, BAN_TIMEOUT)`, computing `expires_at_A = t0 + BAN_TIMEOUT`, but is preempted before acquiring the write lock.
2. Thread B (from `bls_cert_sigverify`), running concurrently, detects an invalid certificate from the same pubkey `P` slightly later at `t1 > t0` and calls `banlist.ban(P, BAN_TIMEOUT)`, computing `expires_at_B = t1 + BAN_TIMEOUT > expires_at_A`, and successfully inserts `expires_at_B` first.
3. Thread A resumes, acquires the write lock, and overwrites the map with `expires_at_A < expires_at_B`.
4. The banlist now reports `P` as banned only until `expires_at_A`, silently truncating the ban that should have lasted until `expires_at_B`. `P` can reconnect and resume misbehaving before the intended (longer) ban window elapses.

Note: I was not able to fully confirm from the index whether `bls_cert_sigverify` and `bls_vote_sigverify` share the exact same `SimpleQosBanlist` instance at runtime (vs. separate instances) in the current wiring code — the grep results show both modules reference `BAN_TIMEOUT`/`banlist.ban` but I could not trace the full construction/wiring path within the tool budget. If they use separate `Banlist` instances, the race would instead need two threads within the same verification path (e.g., two invalid votes for the same pubkey processed in the same parallel batch), which is still plausible given `rayon` parallel iteration over vote batches. A Devin session with full repo access could confirm the exact sharing topology.
