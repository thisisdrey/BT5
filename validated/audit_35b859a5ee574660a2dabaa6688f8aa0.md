### Title
Non-constant-time auth-token comparison enables timing side-channel token recovery on privileged RPC endpoints - (File: stackslib/src/net/api/postblock_proposal.rs)

### Summary
Every HTTP RPC handler that gates access with `connection_options.auth_token` compares the client-supplied `authorization` header to the configured secret using Rust's built-in `!=` operator on `String`/`&str`. This comparison is not constant-time: it returns as soon as it finds a length mismatch or the first differing byte, so equal-vs-unequal decisions leak timing information proportional to the length of the correct-prefix match, exactly the bug class described in the NocoDB advisory (CWE-208/CWE-307), but here applied to a shared-secret RPC auth token instead of an email-lookup branch.

### Finding Description
The same pattern is repeated verbatim across at least six privileged RPC handlers in `stackslib/src/net/api/`:

- `postblock_proposal.rs` (`/v3/block_proposal`): [1](#0-0) 
- `postblock_v3.rs` (`/v3/blocks`, `broadcast=1` gate): [2](#0-1) 
- `blocksimulate.rs` (`/v3/blocks/simulate/:block_id`): [3](#0-2) 
- `txsimulate.rs` (`/v3/transactions/simulate`): [4](#0-3) 
- `blockreplay.rs` and `fastcallreadonly.rs` contain the identical `auth_header` comparison pattern as confirmed by grep matches.

In every case the check is:
```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```
`String`'s `PartialEq` (used by `!=`) is implemented via slice comparison, which in the standard library short-circuits on the first mismatched byte (and immediately on length mismatch). Because the comparison happens synchronously on the calling thread before any expensive JSON/body parsing, the elapsed wall-clock time for a request with a candidate token that matches the true secret for `k` bytes is measurably larger (extra per-byte comparison work, and cache/branch effects) than one that fails on byte 0. A remote, unauthenticated attacker who can send repeated `POST` requests and measure response latency can incrementally recover `auth_token` character-by-character — the same statistical technique used for the NocoDB sign-in timing bug, adapted from "does this email exist" to "is this candidate byte correct."

Unlike the NocoDB email-enumeration case (low-impact PII leak), the secret guarded here, `connection_options.auth_token`, gates write/administrative-grade operations: submitting block proposals for validation (`/v3/block_proposal`), forcing self-broadcast of blocks (`/v2/blocks?broadcast=1` via `postblock_v3.rs`), and other simulate/replay endpoints. This token is explicitly documented as the shared secret between a `stacks-signer` and its node: [5](#0-4) 

### Impact Explanation
Recovering `auth_token` via a timing side-channel gives a remote, unauthenticated attacker full access to the node's signer-only RPC surface, most notably the ability to submit crafted `NakamotoBlockProposal`s to `/v3/block_proposal` and to force `/v2/blocks?broadcast=1`. This is an authentication-bypass primitive: once the secret is recovered, standard equality is satisfied and every subsequent gated request is treated as authenticated. This matches the "auth bypass" / "unauthenticated write to state" Critical impact category defined in scope.

### Likelihood Explanation
Exploitation requires only the ability to send repeated unauthenticated HTTP requests to the node's RPC port, no special network position or existing credentials are needed, matching the report's own precondition ("only the ability to send unauthenticated sign-in requests"). Extracting a small-alphabet secret one byte at a time via timing is a well-established technique; however, practical extraction over commodity networks generally requires many repeated samples per byte to overcome jitter, which is a bounded-but-nontrivial effort. This is why the finding is rated Medium/timing-class rather than a trivially exploitable bypass, consistent with the original advisory's Medium severity for the same bug class.

### Recommendation
Replace the direct `!=` string comparisons in `postblock_proposal.rs`, `postblock_v3.rs`, `blocksimulate.rs`, `txsimulate.rs`, `blockreplay.rs`, and `fastcallreadonly.rs` with a constant-time comparison (e.g., `subtle::ConstantTimeEq`, or a manual XOR-accumulate over fixed-length byte buffers) applied to the raw bytes of `auth_header` and `password`. Ensure the comparison time does not depend on where the first mismatching byte occurs and that both operands are treated as fixed length (e.g., hash both sides with a keyed MAC and compare digests) to also eliminate leakage from the length check.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"` exposing `/v3/block_proposal`.
2. From a remote unauthenticated client, repeatedly send `POST /v3/block_proposal` with the `authorization` header set to candidate strings that share an increasing correct prefix with the real token (e.g., `"a"`, `"ab"`, `"ac"`, ...), each followed immediately by wrong trailing bytes, and measure round-trip latency for many samples per candidate.
3. Statistically, candidates whose prefix matches more bytes of the true secret take marginally longer to reject (extra comparison work in `auth_header != password` before returning `401`) than those that diverge at the first byte.
4. Iterating this per-byte oracle over the keyspace of possible characters recovers `auth_token` without ever needing to know it in advance, after which the attacker can freely submit authenticated block proposals: `stackslib/src/net/api/postblock_proposal.rs:1139-1144`.
