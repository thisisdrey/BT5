Audit Report

## Title
Underpriced remote-fee rounding to zero in Snowbridge `pallet-outbound-queue::calculate_fee` allows fee-free message export - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

## Summary
`calculate_fee` in `bridges/snowbridge/pallets/outbound-queue/src/lib.rs` converts a remote (Ethereum-side) fee from wei-scale Ether to native-currency decimals via `convert_from_ether_decimals`, and this final integer division can truncate a non-zero intermediate value to `0` even when `exchange_rate`, `fee_per_gas`, `reward`, and `multiplier` are all valid and non-zero. [1](#0-0) [2](#0-1)  The pallet's own test confirms this exact zero-rounding outcome for realistic parameters and explicitly labels it invalid, and neither `calculate_fee`, `send_message_impl::validate`, nor `do_process_message` contains any guard rejecting or flooring a zero `remote` fee before the message is queued and eventually committed. [3](#0-2) 

## Finding Description
`calculate_fee` computes `RemoteFeeAdjusted` by multiplying the wei-scale fee by `multiplier`, dividing by `exchange_rate`, and then calling `convert_from_ether_decimals`, which divides by `10^(18 - T::Decimals)` (e.g., `10^8` for a 10-decimal chain). [4](#0-3)  If the intermediate value after the exchange-rate division is smaller than this denominator, integer division floors the result to `0`, as demonstrated by `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero`. [3](#0-2) 

`calculate_fee` is invoked from `SendMessage::validate` in `send_message_impl.rs`, which computes `gas_used_at_most` from the message command and the current public `PricingParameters`, then returns `(ticket, fee)` to the caller (the XCM exporter). [5](#0-4)  Critically, `validate` and `deliver` in this pallet never withdraw or charge the returned `Fee` themselves — there is no `withdraw`/`imbalance`-handling code in `send_message_impl.rs`; the only fee-related API exposed by this pallet is `SendMessageFeeProvider::local_fee`. [6](#0-5)  `deliver` unconditionally enqueues the message via `T::MessageQueue::enqueue_message`, and once dequeued, `do_process_message` unconditionally appends the message to `Messages`/`MessageLeaves` regardless of what fee was computed. [7](#0-6) [8](#0-7) 

I was unable to locate, within the available index, the actual code that withdraws/charges the `Fee` value from the caller's account (e.g., the `EthereumBlobExporter` in `bridges/snowbridge/primitives/outbound-queue/` or callers in `snowbridge-pallet-system`/asset-hub XCM router) to confirm precisely how and whether this fee is deducted before or independent of `validate`/`deliver`. This is a gap in my verification: the actual value-transfer/charging step that the claim's "fee-free message export" impact depends on lives outside `pallet-outbound-queue` itself, and I could not confirm from the indexed files whether that external charging logic has its own minimum-fee floor or additional guards that would prevent free export even if `calculate_fee` returns zero.

## Impact Explanation
If confirmed end-to-end, this matches "public underpriced work that degrades block production or stalls bridge processing" — a zero remote fee for realistic pricing parameters would let an unprivileged submitter get a message committed into the outbound Merkle root without covering the Ethereum-side relayer compensation, undermining the anti-spam/relayer-incentive design documented in the pallet's own module docs. [9](#0-8)  However, this impact hinges entirely on confirming that the fee-charging mechanism (outside this pallet) has no independent floor/guard — which the reporter also acknowledges is unconfirmed ("A background agent should trace `send_message_impl.rs` to confirm whether a zero `remote` fee is deducted/enforced anywhere before `do_process_message` commits the message").

## Likelihood Explanation
`PricingParameters` are public storage, readable and computable by any user, so triggering the zero-rounding condition itself requires no special privilege and is directly demonstrated by the pallet's existing test with realistic values (`exchange_rate = 1/1`, `fee_per_gas = 1`, `reward = 1`). [3](#0-2)  However, likelihood of actual "fee-free" exploitation cannot be fully assessed without confirming the external charging path.

## Recommendation
Add an explicit floor/guard in `calculate_fee` so that a computed `remote` fee of `0` is either rejected (return an error from `validate`) or replaced with a configured minimum, e.g., after `convert_from_ether_decimals`, `ensure!(fee.remote >= T::MinimumRemoteFee::get(), Error::<T>::FeeTooLow)`. This should be done regardless of where the actual withdrawal happens, since `calculate_fee` is the single source of truth for the remote fee quoted to callers.

## Proof of Concept
The existing regression test in the repo reproduces the rounding defect at the calculation layer directly: [3](#0-2)  With `exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards.remote = 1`, `multiplier = 1`, `gas_used = 250000`, `calculate_fee` returns `fee.remote == 0` while `fee.local == 698000000`. Full end-to-end exploitability (confirming no external fee floor exists in the XCM exporter or fee-charging caller) could not be verified from the indexed files and would require further investigation of `bridges/snowbridge/primitives/outbound-queue/src/v1/converter/` and the asset-hub/system-pallet callers of `SendMessage::validate`.

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}
