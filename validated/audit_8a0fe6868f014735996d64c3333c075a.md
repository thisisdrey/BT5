### Title
PSM `redeem` lets minters swap out for a different, better-quality external asset, draining a shared reserve backed by other collateral depositors - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
`pallet-psm` implements a Maker-style Peg Stability Module where a single internal stablecoin is backed by multiple approved external ("collateral") assets, all held in one shared reserve account per PSM instance. Minting with external asset A and redeeming for external asset B are fully decoupled operations on the fungible `internal_asset` — nothing binds a unit of internal asset to the external asset that was deposited to create it. This reproduces exactly the bug-class from the external report: the pooled debt token's value floor becomes that of its weakest collateral, and depositors of a high-quality asset can have their asset drained by holders who minted with a low-quality/depegging asset and then redeemed for the good one.

### Finding Description
Each PSM instance is keyed by `internal_asset` and has one reserve account, `psm_account(internal_asset)`, derived in [1](#0-0) . This single account holds the balances of *all* approved external assets for that PSM (`ExternalAssets` is a `(internal_asset, external_asset)` double map, see [2](#0-1) ).

`mint` accepts any approved `external_asset`, transfers it into the shared `psm_account`, and mints fungible `internal_asset` to the caller, tracking debt only in a `(internal, external)` keyed counter `PsmDebt`: [3](#0-2) 

`redeem` lets the caller pick *any* approved `external_asset` for the *same* `internal_asset`, independent of what they (or anyone) minted with, and pulls that asset out of the same shared `psm_account`: [4](#0-3) [5](#0-4) 

Because `internal_asset` is a single fungible token, there is no metadata tying a specific unit to the external asset used to mint it — exactly the "fungibility vs. redemption-source binding" tradeoff the external report calls out for `BitcornOFT`/`SwapFacility`. Any holder of `internal_asset`, no matter how they acquired it (even by minting against a soon-to-depeg asset A), can call `redeem` targeting a different, higher-quality external asset B, as long as: (1) B is approved, (2) B's per-asset debt counter (`PsmDebt<T>`) covers the requested amount, and (3) B's live on-chain reserve balance covers it (`get_reserve`, [6](#0-5) ). Both of these gates are satisfiable purely by other, unrelated users' prior minting activity against B — nothing requires the redeemer's own internal-asset balance to originate from B.

The `AssetCeilingWeight`/`max_asset_debt` mechanism ( [7](#0-6) ) only bounds how much new debt can be *minted* per external asset; it places no limit on how much of another external's already-minted debt can be redeemed by holders who never contributed that collateral. The only real check is `current_debt >= effective_internal_net` on the target external's own debt counter (line 849), which any set of `internal_asset` holders can exhaust regardless of which asset they originally deposited.

### Impact Explanation
If external asset A depegs, is exploited, or its issuer freezes/blacklists it, holders of `internal_asset` (including those who never touched A) can race to `redeem` against the healthier external asset B before B's PSM debt/reserve is exhausted. This:
- Socializes A's loss onto B's depositors: legitimate B-minters are left unable to redeem B (their intended collateral), and instead are forced into the impaired `internal_asset`/A exposure.
- Produces a bank-run dynamic identical to the reported issue: "the value of the pooled token is only as strong as its weakest collateral link," and unprivileged, non-malicious holders of the fungible debt token can extract value disproportionately by choosing the strongest remaining backing asset.
- No governance/admin misbehavior, malicious validator, or off-chain actor is required — this is pure public-entrypoint behavior of `mint`/`redeem`, matching the "theft or unbacked mint" / "duplicate settlement" spirit of in-scope impacts: value that should stay proportionally distributed across all collateral depositors is instead extractable preferentially by whichever depositor moves first to redeem the best remaining asset.

### Likelihood Explanation
High under multi-external-asset PSM configurations (the pallet's documented, supported use case — `add_external_asset` explicitly supports "one or more approved external stablecoins" per instance). No privileged action, front-running of block production, or malicious infrastructure is needed: any signed account can call `mint` then `redeem` with a different `external_asset` parameter in the same or a later transaction, and the race condition emerges naturally whenever one approved external asset is perceived as riskier than another (e.g. impending depeg news, exploit disclosure). The existing guards — per-asset `PsmDebt` and `ExternalAssets` circuit breaker (`CircuitBreakerLevel`) — are reactive (must be manually paused by admins after the fact) and do not intrinsically prevent the drain before it happens.

### Recommendation
Either (a) bind redemption to the same external asset that was deposited (losing full fungibility across collateral types, similar to the external report's rejected "metadata" option), or (b) enforce a per-asset redemption cap tied to that asset's own realized reserve inflow rather than allowing any internal-asset holder unrestricted access to any other external's reserve, or (c) implement the "redemption priority queue" / pro-rata basket redemption the original report's response also proposes, so that in a partial-depeg scenario redemptions are distributed proportionally across all remaining collateral rather than allowing a first-mover to fully drain the healthiest asset.

### Proof of Concept
1. Admin creates a PSM for `internal_asset = STABLE` and approves two externals: `USDC` (external A) and `USDT` (external B), both with normal fees/weights.
2. User1 (legitimate) mints 1,000,000 `STABLE` by depositing 1,000,000 `USDT` via `mint(STABLE, USDT, 1_000_000, max_fee)` — `PsmDebt(STABLE, USDT) = 1_000_000`, `psm_account` holds 1,000,000 USDT.
3. USDC's issuer is compromised / USDC depegs to near zero, but the PSM admin has not yet called `set_asset_status` to disable USDC.
4. Attacker mints 1,000,000 `STABLE` by depositing 1,000,000 (soon-worthless) `USDC` via `mint(STABLE, USDC, 1_000_000, max_fee)` — `PsmDebt(STABLE, USDC) = 1_000_000`.
5. Attacker immediately calls `redeem(STABLE, USDT, 1_000_000, max_fee)`, burning their `STABLE` and pulling out User1's 1,000,000 `USDT` from the shared `psm_account`, satisfying both the `PsmDebt(STABLE, USDT) >= effective_internal_net` check and the `get_reserve` check purely because User1 had deposited USDT earlier — attacker never held USDT.
6. Result: attacker walks away with real USDT collateral obtained from depositing worthless USDC; User1, who deposited good collateral, can no longer redeem USDT from this PSM — the PSM's remaining reserve is now the depegged USDC, and `internal_asset` in circulation is now under-collateralized. This mirrors the external report's PoC (`test_clear_vault_collateral_with_other_swapfacility`) exactly, transplanted to `pallet-psm`'s `mint`/`redeem`.

		pub fn psm_account(internal_asset: &T::AssetId) -> T::AccountId {
			let entropy = (<PalletId as TypeId>::TYPE_ID, T::PalletId::get(), internal_asset)
				.using_encoded(sp_io::hashing::blake2_256);
			T::AccountId::decode(&mut TrailingZeroInput::new(entropy.as_ref()))
				.expect("All byte sequences are valid `AccountId`s; qed")
		}
