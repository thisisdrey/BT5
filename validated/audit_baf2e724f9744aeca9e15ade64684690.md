### Title
Off-by-one boundary in `RewardsDistributor._calculateTokenDelta` grants `INITIAL_INDEX`-scaled rewards to un-indexed accounts when token index equals `INITIAL_INDEX` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
The reference bug (CVE-2018-20194) is a buffer underflow caused by mishandling a boundary condition (`G_max <= G`) while limiting a gain value — the limit branch fails at the equality edge. The Metronome analog is in `RewardsDistributor._calculateTokenDelta`, which clamps a missing `accountIndexOf` to `INITIAL_INDEX` only when the token index is *strictly greater* than `INITIAL_INDEX` (`_tokenIndex > INITIAL_INDEX`). When `_tokenIndex == INITIAL_INDEX` exactly, the fallback is skipped and `_deltaIndex = INITIAL_INDEX - 0 = 1e18`, crediting the account `balanceOf(account) * 1e18` (wad-scaled, i.e., its full balance) in reward tokens — a spurious accrual of unclaimed yield.

### Finding Description
`RewardsDistributor` tracks a Compound-style reward index per tracked `DepositToken`/`DebtToken`. A token's index is initialized to `INITIAL_INDEX = 1e18` the first time the governor enables a non-zero speed (`_updateTokenSpeed`, contracts/RewardsDistributor.sol:296-299). The per-account accrual is:

```solidity
// contracts/RewardsDistributor.sol:222-230
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The `_accountIndex == 0` fallback exists because accounts that held a balance *before* the token was added to the distributor have no stored index (`updateBeforeMintOrBurn`/`updateBeforeTransfer` early-return when `tokenStates[token_].index == 0`). The fallback uses `>` instead of `>=`: when the supply index is still exactly `INITIAL_INDEX`, `_accountIndex` remains `0` and `_deltaIndex` becomes `1e18` instead of `0`, so `_tokensDelta = balance.wadMul(1e18) = balance`.

Reachable windows where `tokenStates[token_].index == INITIAL_INDEX` while un-indexed accounts hold balances:

- The same block/timestamp in which `updateTokenSpeed`/`updateTokenSpeeds` initializes the token — `_calculateTokenIndex` returns no index update when `_deltaTimestamps == 0`, so `index` stays `INITIAL_INDEX` for every transaction at that timestamp.
- Speed set `> 0` and later set back to `0` before a timestamp boundary elapsed — index never advances past `INITIAL_INDEX`, and the window stays open indefinitely while speed is `0`.
- `syncTokenSpeed` (keeper) writes a `0` speed during a gap in `periodFinish` after the token was initialized — same effect.

An unprivileged account that deposited before reward tracking began (and was never touched by `updateBeforeTransfer`/`updateBeforeMintOrBurn` after index init — e.g., it simply holds, since these hooks only fire on the account's own mint/burn/transfer) calls `claimRewards(account, [token])` during the window: `_updateTokensAccruedOf` credits `tokensAccruedOf[account] += balance`, and `_transferRewardIfEnoughTokens` pays out `min(accrued, distributor balance)` (contracts/RewardsDistributor.sol:248-255). `accountIndexOf` is then permanently set to `INITIAL_INDEX`, so the bug also hard-codes a wrong baseline for that account.

### Impact Explanation
Direct theft of unclaimed yield: the attacker is paid reward tokens proportional to their deposit/debt-token balance without any time having accrued. Since payout is bounded only by the distributor's `rewardToken` balance, a large deposit holder (or a flash-funded position via `deposit` before the window) can drain the entire rewards reserve, denying all other users their accrued rewards. The corrupted `accountIndexOf = 1e18` baseline also permanently distorts that account's future accrual (it skips the delta between `INITIAL_INDEX` and the current index once the index advances).

### Likelihood Explanation
Likelihood is moderate and configuration-dependent:

- Triggering requires a claim while `index == INITIAL_INDEX`, which is a narrow timing window (same timestamp as `updateTokenSpeed`, or a period where speed is `0` after init). On L2s/Base, governor config transactions can be front-run or sandwiched by watching the mempool, and a holder can pre-position a large deposit before rewards are ever enabled — a very plausible rollout scenario for this contract (it is explicitly a "temporary fix" retrofitted onto existing deposit tokens, so accounts holding balances without an `accountIndexOf` are the norm at init time, not the exception).
- No privileged role is needed for the claim itself; `claimRewards` is permissionless (`claimRewards(address[] , IERC20[])` is `public`). The governor only performs a routine, legitimate speed update — the flaw is the equality edge in the fallback, not a malicious parameter choice.
- Impact per trigger is bounded by the distributor's balance, but the reserve is funded precisely to pay out rewards, so the drain is real value.

### Recommendation
Change the strict comparison to inclusive and/or normalize the stored index:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

Equivalently, treat `accountIndexOf == 0` as `INITIAL_INDEX` unconditionally (`if (_accountIndex == 0) _accountIndex = INITIAL_INDEX;` is safe whenever `tokenStates.index > 0`, since the index is monotonically non-decreasing from `INITIAL_INDEX`). Also consider initializing `accountIndexOf` to `INITIAL_INDEX` on first touch in `_updateTokensAccruedOf` so the invariant is stored rather than inferred.

### Proof of Concept
Hardhat-style reproduction sketch (fork/standalone against deployed-style contracts):

```ts
// 1. Setup: alice deposits collateral BEFORE rewards are configured.
await met.approve(msdMET.address, DEPOSIT)
await msdMET.deposit(DEPOSIT, alice.address)
// RewardsDistributor exists but msdMET is not yet tracked (index == 0),
// so deposit's updateBeforeMintOrBurn early-returns → accountIndexOf[alice] == 0.

// 2. Fund the distributor.
await rewardToken.mint(rewardsDistributor.address, REWARD_RESERVE)

// 3. Governor enables speed in block N (index := INITIAL_INDEX = 1e18).
await rewardsDistributor.connect(governor).updateTokenSpeed(msdMET.address, SPEED)

// 4. Same block (or before the index advances): alice claims.
//    _calculateTokenIndex returns deltaTimestamps == 0 → index stays 1e18.
//    _calculateTokenDelta: accountIndex 0, tokenIndex == INITIAL_INDEX,
//    fallback skipped (1e18 > 1e18 is false) → deltaIndex = 1e18,
//    tokensDelta = DEPOSIT.wadMul(1e18) = DEPOSIT.
await rewardsDistributor.claimRewards(alice.address, [msdMET.address])

// 5. Assert: alice received min(DEPOSIT, REWARD_RESERVE) reward tokens
//    despite zero accrual time.
expect(await rewardToken.balanceOf(alice.address)).to.be.closeTo(
  BigNumber.from(DEPOSIT).min(REWARD_RESERVE), 1
)
```

To run the same-block variant deterministically, use `evm_setAutomine(false)` / `network.provider.send('evm_setNextBlockTimestamp', ...)` so `updateTokenSpeed` and `claimRewards` share a timestamp, or set speed `>0`, then back to `0` within one timestamp, then claim — the index remains `INITIAL_INDEX` in both cases.
