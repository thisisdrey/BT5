## Finding: Unbounded swap output used as relayer reward amount without slippage protection in Snowbridge `add_tip`

### Title
Unslippage-protected swap in `snowbridge-pallet-system-frontend::add_tip` lets an attacker inflate relayer reward registration relative to actual value pledged - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

### Summary
The core broken invariant in the Sherlock report is: a user-supplied "price" feeds directly into a settlement/PnL calculation without being bound to the collateral actually pledged, letting the settlement extract far more value than was backed. The closest local analog is in `snowbridge-pallet-system-frontend::add_tip` / `swap_and_burn` [1](#0-0) , where the "price" that determines the payout (the swap's exchange rate) is not bound by any minimum-output/slippage check before the resulting `ether_gained` value is forwarded as the exact relayer reward amount on BridgeHub.

### Finding Description
`add_tip` takes a signed user, swaps the user-supplied `asset` for Ether via `T::Swap::swap_exact_tokens_for_tokens`, then forwards the resulting `ether_gained` amount as the tip/reward amount to `EthereumSystem::AddTip` on BridgeHub: [2](#0-1) 

Note the call to `swap_exact_tokens_for_tokens` passes `None` for the minimum-amount-out parameter:
```
let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
    who.clone(),
    swap_path,
    tip_amount,
    None, // No minimum amount required
    who,
    true,
)?;
```
There is no cap, sanity check, or minimum-received enforcement on `ether_gained` relative to `tip_amount`. This value then becomes the exact `amount` field forwarded via XCM `Transact` to `EthereumSystem::add_tip` on BridgeHub: [3](#0-2) 

On BridgeHub, `system-v2::add_tip` simply calls into `InboundQueue::add_tip`/`OutboundQueue::add_tip`, which unconditionally records `amount` into the `Tips` storage map with no further validation against the underlying pool liquidity or exchange-rate sanity: [4](#0-3) 

When the tipped message is later processed, the full recorded tip is paid out as a relayer reward: [5](#0-4) 

This mirrors the reported bug-class exactly: a user-controlled "price" (here, the AMM exchange rate realized by the swap) directly determines a settlement value (the relayer reward) with no bound tying it to the actual collateral/value pledged (`tip_amount`) or to a fair market rate. In a thinly-liquidated or attacker-controlled pool (e.g., an attacker-created/attacker-dominated pool pair, or one manipulated within the same block via a sandwich/flash-swap-style sequence using `pallet_asset_conversion`), the attacker can cause `swap_exact_tokens_for_tokens` to report an inflated `ether_gained` for a comparatively small `tip_amount`, which is then burned (`burn_for_teleport`) for a modest real cost while the corresponding relayer reward registered on BridgeHub is proportionally huge.

### Impact Explanation
The relayer reward registered via `pallet_bridge_relayers::Event::RewardRegistered` is eventually claimable value (paid out through `BridgeRewardPayer::pay_reward` to a real beneficiary account) [6](#0-5) . If an attacker can register themselves (or a colluding relayer) as the reward beneficiary for a manipulated tip, they can extract funds disproportionate to what they actually paid/burned, i.e., theft of bridge-controlled/backing value — the same "large gain at settlement from a manipulated price with insufficient backing collateral" pattern as the external report.

### Likelihood Explanation
This requires only unprivileged, signed-origin access to `add_tip` and control of (or influence over) the swap pool used for the tip asset → Ether pair — no validator, relayer, governance, or leaked-key assumption is needed, satisfying the "public underpriced work / unauthorized value extraction" impact gate. The likelihood depends on the existence of a thin/attacker-influenced liquidity pool for the chosen tip asset, which is plausible for newly listed or low-liquidity assets under `pallet_asset_conversion`.

### Recommendation
Enforce a `min_amount_out` (or equivalent slippage/oracle-bound check) in `swap_and_burn` rather than passing `None`, and/or cap the forwarded tip/reward `amount` to a sane multiple of `tip_amount` based on a trusted price reference, so the reward registered on BridgeHub can never exceed what is proportionally backed by the value actually withdrawn and burned from the user.

### Proof of Concept
1. Attacker creates or manipulates a low-liquidity `pallet_asset_conversion` pool for `(tip_asset, Ether)`.
2. Attacker calls `system_frontend::add_tip(message_id, Asset{ tip_asset, small_amount })`.
3. `swap_and_burn` calls `swap_exact_tokens_for_tokens(..., small_amount, None, ...)` against the manipulated pool, returning an inflated `ether_gained` because there is no `min_amount_out` protection.
4. `ether_gained` is burned via `burn_for_teleport` (a comparatively small real cost) but forwarded as the exact reward `amount` in `EthereumSystemCall::AddTip` to BridgeHub.
5. `InboundQueue::add_tip` records the inflated amount unconditionally in `Tips` [4](#0-3) .
6. When the associated message is processed, the inflated tip is paid out in full as a relayer reward [5](#0-4) , disproportionate to the value the attacker actually contributed.

			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}

	impl<T: Config> AddTip for Pallet<T> {
		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			// If the nonce is already processed, return an error
			ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
			// Otherwise add the tip.
			Tips::<T>::mutate(nonce, |tip| {
				*tip = Some(tip.unwrap_or_default().saturating_add(amount));
			});
			return Ok(());
		}
