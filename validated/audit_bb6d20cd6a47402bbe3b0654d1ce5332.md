### Title
Heap buffer over-read when parsing a crafted ZIP central directory entry in ijar's `ProcessCentralDirEntry` - (`third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the ZIP central directory of a jar file that ijar/singlejar process (e.g. third-party jars fetched via `http_jar`/`http_archive`/`maven_install` and consumed as build inputs). Unlike its sibling `ProcessLocalFileEntry`, which validates remaining bytes with `EnsureRemaining()` before every read, `ProcessCentralDirEntry` performs no such validation at all before dereferencing `p`.

### Finding Description
`InputZipFile::ProcessLocalFileEntry` is careful to bound-check every read against the size of the mmap'd input file: [1](#0-0) 

By contrast, `ProcessCentralDirEntry` reads the signature, skips 16 bytes, then reads `compressed_size`, `uncompressed_size`, `file_name_length`, `extra_field_length`, `file_comment_length`, `attr`, and `offset` directly off `p` with **no `EnsureRemaining()` calls whatsoever**: [2](#0-1) 

It then `memcpy`s `file_name_length` bytes from `p` into a fixed `filename[PATH_MAX]` buffer, advances `p` by `file_name_length`, and walks an extra-field list purely based on attacker-controlled `header_id`/`data_size` fields, again with no check that `extra_p`/`p` stay inside the mapped file: [3](#0-2) 

Because `file_name_length`, `extra_field_length`, and `file_comment_length` are attacker-controlled 16-bit values taken straight from the crafted central directory record, and the `while (extra_p != p)` loop advances `extra_p` by an attacker-controlled `data_size` with no termination guarantee if `extra_p` overshoots `p`, a jar file crafted with an oversized/misaligned central-directory record causes reads past the end of the `mmap`'d region — the byte-for-byte analog of the ImageMagick MAP decoder's unchecked `p[...]` read that triggered the reported heap-buffer-overflow.

### Impact Explanation
This is a CWE-125 heap/mmap buffer over-read reachable purely from the bytes of a ZIP/jar file that ijar (interface-jar generator) or singlejar process as ordinary build inputs — jars that can originate from an untrusted third-party dependency (e.g. a Maven artifact fetched by `http_jar`/`maven_install`, or a jar living in a repository archive) i.e., content published by an unprivileged, attacker-controlled origin that a victim's build consumes. The over-read data is copied into the `filename` buffer that is subsequently propagated into the tool's output (the generated interface jar's directory entries) or into diagnostic `errmsg` strings, giving the class of impact matching the referenced CVE (heap-buffer over-read / potential memory disclosure), not merely a crash.

### Likelihood Explanation
Any repository rule or dependency-fetch path (`http_jar`, `http_archive` producing `.jar` inputs, Maven/`rules_jvm_external`) that hands a jar to ijar/singlejar during normal Bazel Java builds routes attacker-supplied bytes straight into this unguarded parser. No special privileges, sandbox escape, or credential access are required — only that the victim's build consumes a jar whose bytes were chosen by the attacker (e.g., a malicious release artifact or a compromised/typosquatted Maven coordinate). A sha256/integrity pin on the download stops *substitution* of a different file but does not stop this bug, because the vulnerability triggers on the pinned bytes themselves being adversarially crafted.

### Recommendation
Add the same `EnsureRemaining()` bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry` before every field read (fixed header, filename, and each extra-field record), and bound the `while (extra_p != p)` extra-field loop by an explicit `extra_p < p_end` check derived from `EnsureRemaining(extra_field_length, ...)`, rejecting the entry with an error instead of reading past the mapped file when the declared lengths exceed the remaining bytes.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style reproduction:
1. Hand-construct a minimal ZIP file whose End-Of-Central-Directory record points to a Central Directory Header (`CENTRAL_FILE_HEADER_SIGNATURE`) placed at the very end of the mapped file, with `file_name_length`/`extra_field_length`/`file_comment_length` fields set to values (e.g. `0xFFFF`) that extend past the actual file length.
2. Run `ijar` (or singlejar) against this crafted jar, e.g. via the existing ijar integration test harness that already exercises `InputZipFile::ProcessCentralDirEntry` on attacker-supplied archives.
3. Observe (under AddressSanitizer) a heap-buffer-overflow READ originating in `ProcessCentralDirEntry`'s `memcpy`/`get_u2le` calls at `third_party/ijar/zip.cc:508-536`, analogous to the ASan trace in the ImageMagick MAP-decoder report.

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
