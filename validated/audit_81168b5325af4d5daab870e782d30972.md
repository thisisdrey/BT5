### Title
Git commit pinning integrity bypass via ambiguous ref/hash resolution in `git_repository`'s fallback fetch - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`/`new_git_repository` (and `git_override` in Bzlmod, which shares this Starlark plumbing) let users pin an external dependency to an exact commit via the `commit` attribute, which is meant to act like a checksum: only content reachable at that exact hash should be checked out. When the attacker-controlled (or attacker-served) git remote does not support fetching an arbitrary object by SHA (`uploadpack.allowReachableSHA1InWant` disabled, which is common and the default on many hosting setups), Bazel's fallback path fetches *all* branches and tags and then runs `git reset --hard <commit>` on the literal hex string, with no post-checkout verification that the resulting `HEAD` actually equals the pinned `commit`.

### Finding Description
In `git_repo()`, when `ctx.attr.commit` is set, both `reset_ref` and `fetch_ref` are simply the raw hex string the user supplied: [1](#0-0) .

`fetch()` first tries `git fetch origin -- <commit>` directly. If that fails (server doesn't support fetching arbitrary SHAs), Bazel falls back to fetching every branch and every tag from the remote: [2](#0-1) .

After this fallback, `reset()` runs `git reset --hard <commit>` where `<commit>` is still the raw, unqualified hex string: [3](#0-2) .

Because the fallback just fetched `refs/heads/*` into `refs/remotes/origin/*`, an attacker who controls the remote (a hostile/malicious mirror, a compromised upstream, or an untrusted fork referenced by `remote =` in `git_repository`/`git_override`) can create a branch whose name is the exact same 40-character hex string as the commit the victim has pinned. Git's revision disambiguation logic can resolve an unqualified name that matches both a ref and an object id in favor of the ref in this scenario (the underlying bug class from CVE-2022-4205/GitLab), so `git reset --hard <hex>` checks out the attacker's branch tip instead of the object with that hash — silently substituting different tree content while looking like the correct pinned commit.

Crucially, after the reset Bazel never re-verifies the outcome. `_update()` just calls `reset()` then records whatever `HEAD` ends up being via `_get_head_commit()`: [4](#0-3) [5](#0-4) .

The repository-rule implementation then treats `commit`-pinned rules as reproducible without comparing the recorded/actual commit hash back to `ctx.attr.commit`: [6](#0-5) . There is no code path anywhere in `git.bzl`/`git_worker.bzl` that asserts `git_.commit == ctx.attr.commit` (confirmed via repo-wide search for such a check, which found none). This means the `commit` attribute — the mechanism users rely on for integrity/pinning, analogous to a checksum — is not actually binding: the checkout can silently diverge from the declared hash whenever the fallback path is taken and the attacker plants a same-named branch.

### Impact Explanation
An attacker who controls (or has push access to, or can MITM/serve as) the git remote referenced by an unprivileged victim's `git_repository`/`new_git_repository`/`git_override(commit=...)` can supply completely different source content than what the pinned commit hash represents, while Bazel proceeds as if the pin was honored. This is a build-time supply-chain integrity bypass: the victim's build silently consumes attacker-chosen files, which then get compiled/executed as part of the build, defeating the entire purpose of commit pinning.

### Likelihood Explanation
Exploitability requires two realistic conditions that align with common real-world configuration: (1) the target git server does not enable `uploadpack.allowReachableSHA1InWant` (the default posture for many git servers/mirrors, forcing the fallback path), and (2) the attacker can create/control a branch under that remote (true for a hostile mirror, a compromised or attacker-run fork used as `remote =`, or any dependency source not fully trusted). No access to the victim's machine, credentials, or output base is required — only the ability to serve/host content at the declared remote URL, matching the "hostile origin server" scenario in the rules.

### Recommendation
After `reset()`/`_get_head_commit()`, when `ctx.attr.commit` is non-empty, compare the resolved `HEAD` commit hash against `ctx.attr.commit` (case-insensitively) and `fail()` the repository rule if they don't match exactly. Additionally, prefer fully-qualified refspecs when resetting to a bare hex commit (e.g., disambiguate explicitly via `git rev-parse --verify <commit>^{commit}` scoped away from ref namespaces, or reset using `refs/<sha>` forms that cannot collide with `refs/heads/*`/`refs/remotes/*`) so that a same-named branch cannot shadow the intended object.

### Proof of Concept
1. Stand up a git server (attacker-controlled) with `receive.denyCurrentBranch=updateInstead` and `uploadpack.allowReachableSHA1InWant=false` (default on many servers), simulating a hostile/malicious mirror that a victim's `git_repository(remote = "https://attacker/repo.git", commit = "<TARGET_SHA>")` points to.
2. On that server, create branch `refs/heads/<TARGET_SHA>` (the exact 40-hex string of the commit the victim pins) pointing to a different, attacker-chosen commit whose tree contains malicious `BUILD`/source content, while also ensuring the real object `<TARGET_SHA>` is still reachable (e.g., part of history) so it's fetched too.
3. Run `bazel build` referencing this `git_repository`. The initial `git fetch origin -- <TARGET_SHA>` fails (SHA fetch disabled), triggering the fallback `git fetch origin -- refs/heads/*:refs/remotes/origin/* refs/tags/*:refs/tags/*` in `fetch()` (`tools/build_defs/repo/git_worker.bzl:181-202`), which pulls in `refs/remotes/origin/<TARGET_SHA>`.
4. `reset()` executes `git reset --hard <TARGET_SHA>` (`tools/build_defs/repo/git_worker.bzl:204-205`). Verify via `git rev-parse HEAD` inside the checkout that HEAD is NOT `<TARGET_SHA>`'s tree/content but instead the attacker branch's commit — while Bazel records success and (per `git.bzl:297-298`) marks the rule `reproducible = True` with no failure raised, demonstrating the pinned-commit integrity guarantee is bypassed.
5. Wrap this in a `src/test/shell/bazel` integration test (local git server fixture) asserting that build output originates from the intended pinned commit content and fails/differs when the malicious same-named branch is present, proving the missing post-checkout verification.
