### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign`/`BatchValidateSign` precompiles causes node OOM DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The TVM precompiled contracts `ValidateMultiSign` and `BatchValidateSign` decode a signature/address count directly from attacker-supplied call data and use it to allocate `byte[len][]` arrays before any bound is enforced, unless the `allowTvmSelfdestructRestriction` fork feature happens to be active on that code path. This mirrors the `tf.ragged.constant` bug class: an integer size parameter taken from untrusted input is used to size a memory allocation with no validation, letting an attacker force an out-of-memory condition.

### Finding Description
`extractBytesArray`, `extractBytes32Array`, and `extractSigArray` all read a `len` value straight from the caller-supplied `DataWord[]` (i.e., from the raw TVM call data) and immediately allocate an array of that size: [1](#0-0) [2](#0-1) [3](#0-2) 

`intValueSafe()` only clamps the value into the `int` range — it performs no upper-bound sanity check relative to the actual call-data length. `ValidateMultiSign.execute()` only checks `sigArraySize > MAX_SIZE` (16) *before* allocation when the `allowTvmSelfdestructRestriction` fork feature is enabled; the `else` branch calls `extractBytesArray` with the raw, unchecked `len`: [4](#0-3) 

The length check `signatures.length == 0 || signatures.length > MAX_SIZE` at line 1076 happens **after** the array has already been allocated inside `extractBytesArray`/`extractSigArray`, so it cannot prevent the allocation itself — only reject the result afterward.

`BatchValidateSign.doExecute()` has the identical pattern for signatures, and additionally calls `extractBytes32Array` for addresses with **no size guard applied to that specific call at all**, only checking `addrArraySize > MAX_SIZE` when the fork flag is active, before invoking the very same unguarded `extractBytes32Array`: [5](#0-4) 

Both precompiles are ordinary TVM precompiled contracts reachable via a standard `CALL`/`STATICCALL` from any smart contract, i.e. from any unprivileged contract deployer or caller who can craft a transaction invoking these precompile addresses with malicious call data (e.g., setting the length word to a large value such as `0x7FFFFFFF`).

### Impact Explanation
An attacker can craft TVM call data to these precompiles so that the decoded `len` is enormous (up to `Integer.MAX_VALUE`), forcing the JVM to attempt to allocate a multi-gigabyte `byte[len][]` object array. This throws `OutOfMemoryError` or otherwise exhausts node heap during transaction execution/validation, which every full node and witness/SR node must perform when processing or re-validating the block containing this transaction. This can crash or hang node processes handling the transaction, matching the accepted "node crash or halt" impact category.

### Likelihood Explanation
The precompiles are reachable by any account through a plain contract call; no special privilege, staking, or witness role is required — only enough energy/fee to invoke the precompile call. The vulnerable code path is taken whenever the `allowTvmSelfdestructRestriction` fork feature is not exercised for that particular call branch, i.e., the `extractBytesArray`/`extractBytes32Array` calls are always reachable with attacker-controlled `len` for at least the address array in `BatchValidateSign`, and for the signature array whenever the feature-gated branch is not taken. Likelihood is high because triggering it only requires deploying/calling a trivial contract with crafted call data.

### Recommendation
Add an explicit upper bound check on `len` (and on offsets) inside `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` themselves — independent of the `allowTvmSelfdestructRestriction` fork flag — before performing `new byte[len][]`, e.g., bound `len` by `MAX_SIZE` (16) or by the maximum number of words that could fit in `data.length`. Do not rely on post-allocation checks (`signatures.length > MAX_SIZE`) to catch oversized allocations, since the damage (OOM) occurs during allocation itself.

### Proof of Concept
Construct call data for the `ValidateMultiSign` precompile (address `0x0...66`) where the ABI-encoded array-length word pointed to by `words[3]/WORD_SIZE` is set to a very large value (e.g., `0x7FFFFFFF`), while `allowTvmSelfdestructRestriction` is not yet enforced on that call branch (or by targeting `BatchValidateSign`'s address-array length word at `words[2]/WORD_SIZE`, which has no size guard regardless of the fork flag). Deploy a minimal contract that performs a `STATICCALL`/`CALL` to the precompile address with this crafted data and trigger it from any account; `extractBytesArray`/`extractBytes32Array` will attempt `new byte[0x7FFFFFFF][]`, causing an immediate `OutOfMemoryError` in the node processing the transaction.
