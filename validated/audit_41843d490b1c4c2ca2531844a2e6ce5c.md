### Title
Unbounded write-starvation of `ThreadAwareAccountLocks` when read locks on a hot account are spread across ≥2 worker threads - ([File: scheduling-utils/src/thread_aware_account_locks.rs])

### Summary
`ThreadAwareAccountLocks::schedulable_threads::<WRITE>` returns `ThreadSet::none()` for a write whenever an account's outstanding read locks span more than one thread, since `only_one_contained()` is `None` for any set with >1 bit. Because `select_thread` load-balances new locks across whichever threads currently have the least in-flight work, an attacker who continuously floods independent, non-conflicting read-only transactions on a single popular account can keep that account's read locks spread across ≥2 threads indefinitely, permanently blocking any write transaction on that account regardless of the fee it pays.

### Finding Description
`schedulable_threads::<WRITE>` implements the write-schedulability rule: [1](#0-0) 
When only read locks exist on an account and they are held on more than one thread, `read_locks.thread_set.only_one_contained()` returns `None`, so the function falls back to `ThreadSet::none()` — i.e. no thread is currently write-schedulable for that account. This is fed into `accounts_schedulable_threads`, which ANDs this into the overall schedulable set: [2](#0-1) 
and ultimately into `try_lock_accounts`, which returns `Err(TryLockError::MultipleConflicts)` in that case (`accounts_schedulable_threads` returning `None`) or, if schedulable threads intersect to empty after allowed-thread filtering, `Err(TryLockError::ThreadNotAllowed)`. [3](#0-2) 

The `GreedyScheduler` calls this via `try_schedule_transaction`, and on either error it just re-queues the transaction id into `self.unschedulables` for the next scheduling pass rather than dropping it — so the failure recurs every pass as long as the lock condition persists: [4](#0-3) [5](#0-4) 

Critically, when a new read-only lock on an account with no existing lock is being scheduled, the thread that receives it is picked by `select_thread`, which chooses whichever thread currently has the fewest in-flight CUs/transactions (pure load balancing, no notion of "keep reads on one thread"): [6](#0-5) 
This means an attacker submitting many independent read-only transactions naming the same account will, by design, have them spread across multiple worker threads (the exact opposite of what would be needed to keep `only_one_contained()` returning `Some`). Read locks are only released when a worker finishes its batch and the scheduler processes `try_receive_completed` → `complete_batch` → `unlock_accounts`: [7](#0-6) 
so as long as the attacker keeps a steady supply of new read-only transactions on the target account ready to replace ones that finish, at least two threads can be kept holding read locks on that account continuously, with no fee-based override — the writer's priority fee has zero effect on this specific lock-conflict check.

### Impact Explanation
A victim's write transaction on a shared/popular account (e.g. a busy AMM pool, an oracle, a popular program's global state account) can be perpetually re-queued as `UnschedulableConflicts` and never scheduled into any worker thread, no matter how high a priority fee it pays, as long as the attacker sustains rolling read-only transactions spread across ≥2 banking threads. This is a liveness/availability violation of the invariant "account locks prevent conflicts" combined with unbounded write starvation — an unprivileged attacker paying only cheap read-only tx fees can deny service to fee-paying writers on a specific account indefinitely.

### Likelihood Explanation
Feasibility requires only that the attacker be able to submit many valid, distinct, non-conflicting read-only transactions naming the victim account (e.g. `getAccountInfo`-style transfers/instructions where the account is read-only) using different fee payers, and keep a continuous stream so that the lock coverage across threads never collapses to a single thread. Given `select_thread`'s load-balancing behavior actively spreads new read locks across underutilized threads, this condition arises naturally under moderate flooding without any special validator/leader control — it is purely a client-side flood of cheap transactions against the TPU.

### Recommendation
Change the write-schedulability policy for read-locked accounts so that a pending write is not permanently blocked by a spread of read locks: e.g., track a "preferred"/"chain" thread for read locks (similar to how `write_lock_account` requires reads to already be single-threaded before permitting a write), or add an aging/priority-based override that forces new read locks for an account with a pending write onto the account's already-locked thread set (shrinking the read thread-set toward a single thread over time), or bound the maximum number of distinct threads an account's read locks may span concurrently.

### Proof of Concept

```rust
#[test]
fn test_write_starved_by_multi_thread_reads() {
    let pk = Pubkey::new_unique();
    let mut locks = ThreadAwareAccountLocks::new(TEST_NUM_THREADS);

    // Simulate attacker: keep at least 2 threads holding read locks on `pk`.
    locks.read_lock_account(&pk, 0);
    locks.read_lock_account(&pk, 1);

    // Victim's write transaction can never be scheduled while reads span >1 thread.
    for _ in 0..1000 {
        assert_eq!(
            locks.try_lock_accounts(
                [&pk].into_iter(),
                std::iter::empty(),
                TEST_ANY_THREADS,
                test_thread_selector
            ),
            Err(TryLockError::MultipleConflicts)
        );

        // Attacker "refreshes" reads: unlock one read and immediately re-lock on
        // a different thread, keeping the thread_set spanning >1 thread forever.
        locks.read_unlock_account(&pk, 0);
        locks.read_lock_account(&pk, 2);
        std::mem::swap(&mut 0, &mut 0); // placeholder to illustrate rotation
    }
    // Writer never succeeds despite reads individually completing/rotating.
}
```
Expected assertion: `try_lock_accounts` for the write on `pk` returns `Err(TryLockError::MultipleConflicts)` on every iteration, demonstrating unbounded starvation as long as ≥2 threads hold reads on the account.

```rust
    fn schedulable_threads<const WRITE: bool>(&self, account: &Pubkey) -> ThreadSet {
```

```rust
fn try_schedule_transaction<Tx: TransactionWithMeta>(
    transaction_state: &mut TransactionState<Tx>,
    account_locks: &mut ThreadAwareAccountLocks,
    schedulable_threads: ThreadSet,
    thread_selector: impl Fn(ThreadSet) -> ThreadId,
) -> Result<TransactionSchedulingInfo<Tx>, TransactionSchedulingError> {
    // Schedule the transaction if it can be.
    let transaction = transaction_state.transaction();
    let account_keys = transaction.account_keys();
    let write_account_locks = account_keys
        .iter()
        .enumerate()
        .filter_map(|(index, key)| transaction.is_writable(index).then_some(key));
    let read_account_locks = account_keys
        .iter()
        .enumerate()
        .filter_map(|(index, key)| (!transaction.is_writable(index)).then_some(key));

    let thread_id = match account_locks.try_lock_accounts(
        write_account_locks,
        read_account_locks,
        schedulable_threads,
        thread_selector,
    ) {
        Ok(thread_id) => thread_id,
        Err(TryLockError::MultipleConflicts) => {
            return Err(TransactionSchedulingError::UnschedulableConflicts);
        }
        Err(TryLockError::ThreadNotAllowed) => {
            return Err(TransactionSchedulingError::UnschedulableThread);
        }
    };
```

```rust
pub fn select_thread<Tx>(
    thread_set: ThreadSet,
    batch_cus_per_thread: &[u64],
    in_flight_cus_per_thread: &[u64],
    batches_per_thread: &[Vec<Tx>],
    in_flight_per_thread: &[usize],
) -> ThreadId {
    thread_set
        .contained_threads_iter()
        .map(|thread_id| {
            (
                thread_id,
                batch_cus_per_thread[thread_id] + in_flight_cus_per_thread[thread_id],
                batches_per_thread[thread_id].len() + in_flight_per_thread[thread_id],
            )
        })
        .min_by(|a, b| a.1.cmp(&b.1).then_with(|| a.2.cmp(&b.2)))
        .map(|(thread_id, _, _)| thread_id)
        .unwrap()
}
```
