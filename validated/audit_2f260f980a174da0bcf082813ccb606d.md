### Title
Single poisoned maker order can abort the entire batch match in `MarketSellAssetActuator`, reverting fills for unrelated makers - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator` is java-tron's on-chain TRC10 order book, structurally analogous to the `OrderBook.sol` reviewed in the external report: a single transaction's `execute()` atomically settles the taker against up to `MAX_MATCH_NUM` different maker orders in one loop [1](#0-0) . Just as `OrderBook.collectFees()` bundled two independent transfers (DAO + host) into one all-or-nothing call, `matchOrder`/`matchSingleOrder` bundles many independent maker settlements into one all-or-nothing call. If crediting any single maker's account throws (e.g., a `long` overflow via `addAssetAmountV2`/`addExact`), the whole loop — and thus the whole transaction, including the fills that had already succeeded against other, unrelated makers in the same batch — fails and is reverted.

### Finding Description
`matchOrder` iterates over the maker order book at the best price and calls `matchSingleOrder` repeatedly until the taker's remaining sell quantity is exhausted or `MAX_MATCH_NUM` is reached [2](#0-1) . Each call to `matchSingleOrder` credits both the taker and a distinct maker via `addTrxOrToken`, which in the token case delegates to `AccountCapsule.addAssetAmountV2` [3](#0-2) .

`addAssetAmountV2` uses `addExact`, which throws `ArithmeticException` on overflow [4](#0-3) . The top-level `execute()` catch clause only handles `ItemNotFoundException`, `InvalidProtocolBufferException`, `BalanceInsufficientException`, and `ContractValidateException` — it does **not** catch `ArithmeticException` [5](#0-4) . This mirrors the `ParticipateAssetIssueActuator` and `TransferAssetActuator` behaviors, where the same overflow condition is exercised and documented in tests as producing a `long overflow` failure that aborts the whole action [6](#0-5) .

Because a single account's asset balance for a given TRC10 token is attacker-controlled (an attacker can grow their own balance close to `Long.MAX_VALUE` by legitimately trading/transferring, or place a resting maker order under such an account), placing that "poisoned" maker order into the order book for a given trading pair means: any future taker order that matches into this maker (as one of up to `MAX_MATCH_NUM` matches in the same `matchOrder` batch) will trigger the overflow when the code attempts to credit the poisoned maker, causing the entire transaction — including fills against the other, legitimate makers matched earlier in the same loop — to fail and roll back. This is the direct analog of the audited `collectFees` bug: one bad "recipient" (the poisoned maker account) blocks atomic settlement intended for multiple independent parties (the other makers and the taker) in the same operation.

### Impact Explanation
This is a Medium-severity liveness/funds-lockout issue analogous to the reported one: it does not itself steal funds, but it lets an attacker deny order-matching for legitimate market participants sharing a price level with the poisoned account, by making certain sell/buy order combinations permanently un-matchable against a specific price bucket in the order book (until/unless that maker order is manually removed, e.g., by `MarketCancelOrderActuator`). Because up to `MAX_MATCH_NUM` (20) unrelated makers can be batched together with the poisoned one, the blast radius of a single poisoned recipient extends to many otherwise-unaffected counterparties per transaction, exactly matching the "atomic delivery to multiple recipients" bug class from the report.

### Likelihood Explanation
Reaching an account balance near `Long.MAX_VALUE` for a specific TRC10 token requires either the token's total supply to be very large or the attacker to accumulate assets over many legitimate transfers, so this is not trivial to engineer but is fully within reach of an unprivileged user issuing ordinary `MarketSellAssetContract`/`TransferAssetContract` transactions — no privileged role, oracle, or off-chain assumption is needed. Because `AbstractActuator`/`AccountCapsule` treat TRC10 balances as plain `long` fields with `addExact` overflow checks rather than clamped/rejecting logic at the market layer, the condition is deterministically reproducible once the target account's balance is positioned near the overflow boundary for the specific token used in the trade.

### Recommendation
In `matchOrder`/`matchSingleOrder`, isolate the failure of crediting a single maker so it cannot revert fills against other, unrelated makers in the same batch — e.g., validate/guard the credit operation with an explicit overflow check before committing to the match, skip or fail only the poisoned maker's leg (similar to how the Clober fix parametrized `collectFee` to a single recipient with independent counters), and ensure `execute()`'s catch clause set is complete for all exceptions the match path can throw (currently `ArithmeticException` is not among the caught types [5](#0-4) ), so failures are converted into a clean transaction failure rather than leaving ambiguous partial-state exposure across a multi-maker batch.

### Proof of Concept
1. Attacker account `M` accumulates TRC10 token `T` balance close to `Long.MAX_VALUE` (via ordinary transfers/participation, `TransferAssetActuator`/`ParticipateAssetIssueActuator`).
2. Attacker places a resting sell order via `MarketSellAssetContract` selling some other token `S` for `T`, using account `M`, at a price that lands in a shared price bucket alongside several other legitimate makers' orders for the same pair.
3. A taker (any user) submits a `MarketSellAssetContract` selling `T` for `S`, whose taker price matches the shared bucket; `matchOrder` walks the maker list and batches the legitimate makers together with `M` (up to `MAX_MATCH_NUM`) in the loop at [7](#0-6) .
4. When `matchSingleOrder` reaches `M`'s order and calls `addTrxOrToken` → `addAssetAmountV2` → `addExact`, the overflow throws `ArithmeticException`, uncaught by `execute()`'s catch list [8](#0-7) , aborting the entire transaction and rolling back fills already computed for the other, legitimate makers matched earlier in the same call.

Note: I was unable to fully trace, within this session, how the top-level block-application/transaction-processing pipeline in `Manager`/`TransactionUtil` ultimately handles an uncaught `RuntimeException` (`ArithmeticException`) escaping `execute()` — i.e., whether it is caught generically higher up and only fails the single transaction (matching the `TransferAssetActuatorTest`/`ParticipateAssetIssueActuatorTest` overflow tests' expected behavior), or whether it could have a broader effect on block processing. This affects only the precise blast-radius characterization (transaction-level failure vs. something more severe) and does not change the core finding that legitimate, unrelated maker fills are reverted alongside the poisoned one.

  private void matchOrder(MarketOrderCapsule takerCapsule, MarketPrice takerPrice,
      TransactionResultCapsule ret, AccountCapsule takerAccountCapsule)
      throws ItemNotFoundException, ContractValidateException {

    byte[] makerSellTokenID = buyTokenID;
    byte[] makerBuyTokenID = sellTokenID;
    byte[] makerPair = MarketUtils.createPairKey(makerSellTokenID, makerBuyTokenID);

    // makerPair not exists
    long makerPriceNumber = pairToPriceStore.getPriceNum(makerPair);
    if (makerPriceNumber == 0) {
      return;
    }
    long remainCount = makerPriceNumber;

    // get maker price list
    List<byte[]> priceKeysList = pairPriceToOrderStore
        .getPriceKeysList(MarketUtils.getPairPriceHeadKey(makerSellTokenID, makerBuyTokenID),
            (long) (MAX_MATCH_NUM + 1), makerPriceNumber, true);

    int matchOrderCount = 0;
    // match different price
    while (takerCapsule.getSellTokenQuantityRemain() != 0) {
      // get lowest ordersList
      MarketPrice makerPrice = hasMatch(priceKeysList, takerPrice);
      if (makerPrice == null) {
        return;
      }

      byte[] pairPriceKey = priceKeysList.get(0);

      // if not exists
      MarketOrderIdListCapsule orderIdListCapsule = pairPriceToOrderStore.get(pairPriceKey);

      // match different orders which have the same price
      while (takerCapsule.getSellTokenQuantityRemain() != 0
          && !orderIdListCapsule.isOrderEmpty()) {
        byte[] orderId = orderIdListCapsule.getHead();
        MarketOrderCapsule makerOrderCapsule = orderStore.get(orderId);

        matchSingleOrder(takerCapsule, makerOrderCapsule, ret, takerAccountCapsule);

        // remove order
        if (makerOrderCapsule.getSellTokenQuantityRemain() == 0) {
          // remove from market order list
          orderIdListCapsule.removeOrder(makerOrderCapsule, orderStore,
              pairPriceKey, pairPriceToOrderStore);
        }

        matchOrderCount++;
        if (matchOrderCount > MAX_MATCH_NUM) {
          throw new ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM);
        }
      }

  public boolean addAssetAmountV2(byte[] key, long amount,
      DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    //key is token name
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAsset(nameKey, addExact(currentAmount, amount, disableJavaLangMath))
          .putAssetV2(tokenID, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenIDStr = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenIDStr);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAssetV2(tokenIDStr, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }
    return true;
  }
