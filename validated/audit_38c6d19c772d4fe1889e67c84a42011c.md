Found the local analog: `pallet-nomination-pools`'s `withdraw_unbonded` extrinsic computes `balance_to_unbond` from pool bookkeeping, uses it to actually withdraw funds via the stake adapter, but then emits its accounting event using the pre-computed (potentially stale/optimistic) `balance_to_unbond` rather than any actual-amount-returned value — mirroring the BunniHub pattern of "compute expected amount → perform the real value-moving operation → use the stale pre-operation amount for the externally-visible effect (event/hooklet/check)."

### Title
`Withdrawn` event and pool bookkeeping in `pallet-nomination-pools::withdraw_unbonded` use pre-transfer `balance_to_unbond` instead of the amount actually released - (File: `substrate/frame/nomination-pools/src/lib.rs`)

### Summary
In `Pallet::withdraw_unbonded` [1](#0-0) , `balance_to_unbond` is computed from the sub-pool dissolution math and then clamped by `T::StakeAdapter::transferable_balance(...)` [2](#0-1) . This value is passed into `T::StakeAdapter::member_withdraw(...)` [3](#0-2) , whose return value (`Ok(())`) is discarded — the call does not surface how much was actually released. The pallet then emits `Event::Withdrawn { balance: balance_to_unbond, ... }` using the same pre-call quantity [4](#0-3) , exactly analogous to `BunniHubLogic.deposit` invoking the hooklet/slippage check with the stale `amount0`/`amount1` instead of the post-adjustment reserve values.

### Finding Description
The staking adapter abstraction (`adapter.rs`, `delegated-staking` pallet) explicitly documents that funds "actually released" from a hold/delegation can differ from the amount requested — see `fungible::hold::Mutate::release`, which states "the amount actually unreserved and returned... may be smaller than the amount passed" [5](#0-4) , and `delegated_staking::do_release`, which calls `T::Currency::release(..., Precision::BestEffort)` and only *defensively asserts* (non-fatal in production) that `released == amount` [6](#0-5) . Despite this, `withdraw_unbonded` in `pallet-nomination-pools` never captures or uses any actually-released value from `member_withdraw`; it simply reuses the `balance_to_unbond` figure that was computed *before* the stake-side withdrawal executed. The `SubPoolsStorage` dissolution (`era_pool.dissolve(*unlocked_points)`) that derives `balance_to_unbond` also happens before the real transfer, so if the stake adapter's actual movement diverges (e.g., due to `BestEffort` precision, existential-deposit dust, or partial release when a delegation is not fully claimed), the pool's emitted `Withdrawn` event and downstream consumers relying on it (indexers, `TotalValueLocked` trackers, off-chain accounting) will record a value that does not match what left the bonded/delegated stash.

### Impact Explanation
If `member_withdraw` performs a best-effort release that transfers less than `balance_to_unbond` (rather than erroring), the pool's internal points bookkeeping (`sub_pools`, `member.total_points()`) has already been permanently reduced to reflect a withdrawal that never actually happened in full. This can permanently strand member funds (they lose their claim/points on the unbonded amount without receiving the corresponding balance) or produce inconsistent `TotalValueLocked`/reward accounting across the pool — the same "wrong beneficiary/amount, fund loss or lock" class called out in the Impact Gate. It does not require a malicious relayer, validator, or governance actor; only an unprivileged member calling the permissionless/self-service `withdraw_unbonded` extrinsic under the right ledger state (partial release scenario already anticipated by the delegated-staking `defensive_assert`).

### Likelihood Explanation
Medium: the codebase itself anticipates and documents that the release can be a `BestEffort` partial operation (`defensive_assert!(released == amount, ...)` is only a defensive log, not an abort) [6](#0-5) , meaning the divergence path is a recognized, reachable condition rather than a purely theoretical one, but it typically requires an unusual ledger state (e.g., partially-claimed delegation, dust-level rounding, or ED-driven clamping) to actually manifest a mismatch large enough to matter.

### Recommendation
Change the stake adapter's `member_withdraw` to return the actually-withdrawn amount (as `fungible::hold::Mutate::release` already does), propagate that value up through `withdraw_unbonded`, and use it — not the pre-computed `balance_to_unbond` — for the `Event::Withdrawn` emission and for reconciling `sub_pools`/`member` state, so pool accounting never diverges from what was truly transferred out of the bonded stash.

### Proof of Concept
Conceptual PoC (cannot be fully executed without a live delegated-staking harness given index-only access):
1. Member `A` bonds via `DelegateStake` strategy; a slash occurs and reduces `unclaimed_withdrawals`/delegation such that a subsequent `member_withdraw` for the computed `balance_to_unbond` can only be honored on a `BestEffort` basis for less than requested (mirroring the `defensive_assert` scenario in `delegated-staking::do_release`).
2. `A` calls `Pools::withdraw_unbonded(A, A, num_slashing_spans)`.
3. `balance_to_unbond` is computed and `sub_pools`/`member.points` are reduced by the full amount [2](#0-1) .
4. `T::StakeAdapter::member_withdraw` internally releases less than `balance_to_unbond` (best effort), but the call still returns `Ok(())`, so the pallet proceeds.
5. `Event::Withdrawn { balance: balance_to_unbond, .. }` is emitted reporting the full requested amount even though `A`'s actual free-balance increase is smaller — an observable discrepancy between recorded and real settlement, matching the BunniHub stale-`amount` pattern.

This confirms the structural analog is real and locally provable; a full economic-loss demonstration would require instrumenting the `DelegateStake` test harness (`test-delegate-stake`) to force the best-effort branch, which is beyond what static/index inspection can execute here.
