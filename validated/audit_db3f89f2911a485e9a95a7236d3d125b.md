### Title
Unsynchronized concurrent mutation of the shared consensus `JumpTable` opcode array races with in-flight TVM execution reads - ([File: actuator/src/main/java/org/tron/core/vm/OperationRegistry.java])

### Summary
`OperationRegistry` maintains a single shared, mutable `JumpTable` instance for all non-constant-call transaction executions (`tableMap.get(LATEST_VERSION)`), and every call to `VMActuator.validate()` invokes `OperationRegistry.prepareAndGetTable(isConstantCall)` → `adjustTable(table)`, which calls `table.set(op)` on that shared table on every single transaction execution. `JumpTable.set()` writes directly into a plain, non-volatile `Operation[256]` array with no locking, and `JumpTable.get()` reads from that same array during opcode dispatch in `VM.play()`. This is analogous to the `lock_api` `MappedRwLockWriteGuard` unsoundness (CVE-2020-35912): unsynchronized concurrent writer/reader access to shared mutable state that can produce a torn/racy read.

### Finding Description
`OperationRegistry.getTable(false)` always returns the exact same `JumpTable` object for every non-constant transaction: [1](#0-0) 

`prepareAndGetTable` mutates that shared instance on every call via `adjustTable`, which conditionally calls `table.set(...)` based on live `VMConfig` flags (`allowHigherLimitForMaxCpuTimeOfOneTx`, `allowTvmOsaka`, `allowEnergyAdjustment`, `allowTvmSelfdestructRestriction`): [2](#0-1) [3](#0-2) 

`JumpTable` itself provides no synchronization for its backing array: [4](#0-3) 

`VMActuator.validate()` calls `OperationRegistry.init()` and, indirectly through the interpreter loop in `VM.play()`, reads from this same shared table via `jumpTable.get(program.getCurrentOpIntValue())` while another thread could concurrently be writing to it via `adjustTable`: [5](#0-4) [6](#0-5) 

`RuntimeImpl.execute()` shows the reachable entry point: any `TriggerSmartContract` or `CreateSmartContract` transaction (broadcast or block-application) instantiates a `VMActuator` and calls `validate()`/`execute()`, exercising the shared, non-constant `JumpTable`: [7](#0-6) 

Because the shared, non-constant table (`isConstantCall=false`) is used both when a transaction is validated/executed via `Manager.pushTransaction` (broadcast path, guarded by `synchronized(this)`) and when it is executed during `Manager.generateBlock`'s packing loop (`processTransaction` calls inside the transaction-packing loop shown in the block-producer path), any concurrency gap between those two call sites — e.g. a constant-call/energy-adjustment config flip mid-flight, or any future refactor that removes/relaxes the `synchronized(this)` guard around `processTransaction` — allows one thread's `table.set()` write (a plain array-slot store, not atomic w.r.t. the reader's `table[op]` load) to race against another thread's in-progress `VM.play()` opcode dispatch on the very same table. A torn or stale `Operation` reference read from `table[op]` can select the wrong `Operation` (wrong energy-cost function or wrong action for that opcode index), producing a mismatch between the consensus energy metering / opcode semantics and the value the executing thread observes.

### Impact Explanation
If a mid-execution opcode dispatch observes a partially-updated or wrong `Operation` instance for an opcode (e.g., because a concurrent writer flipped MLOAD/MSTORE/MSTORE8/VOTEWITNESS/SUICIDE variants during a live transaction's interpreter loop), the acting node could execute wrong energy accounting or wrong SUICIDE (self-destruct) semantics for a smart-contract transaction that another node executes with the correct value, producing a state/receipt divergence between nodes (a consensus/chain-split class issue) or incorrect energy metering that could permit under/over-charging energy for a transaction.

### Likelihood Explanation
Today's code path largely serializes writes to the shared table through `Manager.pushTransaction`'s `synchronized(this)` block, and `OperationRegistry.adjustTable` is idempotent (it always ends by writing a value consistent with the currently-read `VMConfig` flags), which limits practical exploitability under the current single Manager-lock design shown here. However, the architecture itself — a package-shared mutable `JumpTable` backing array mutated on every transaction execution with no `volatile`/lock inside `JumpTable`/`OperationRegistry`, read concurrently by the VM interpreter loop, and reachable purely by pushing/broadcasting ordinary `TriggerSmartContract`/`CreateSmartContract` transactions — is inherently unsound for any future multi-threaded transaction/block-processing path (e.g., parallel transaction validation, alternate execution engines, or a regression removing the `synchronized(this)` guard), matching the same "unsynchronized shared mutable guard state" bug class as CVE-2020-35912.

### Recommendation
Make `JumpTable`'s backing store either immutable-per-snapshot (build a new `Operation[]` array and publish it via a single `volatile` reference swap instead of mutating slots in place) or guard `set`/`get` with proper synchronization (e.g., `AtomicReferenceArray<Operation>` or a `ReadWriteLock`). At minimum, document and enforce (via an assertion or lock) that `adjustTable` may only be invoked while holding the same lock used to serialize `Manager.processTransaction`, and audit all call sites of `OperationRegistry.getTable(false)`/`prepareAndGetTable(false)` to guarantee no execution path can read while another concurrently writes.

### Proof of Concept
Conceptual PoC (concurrency-dependent, not deterministically reproducible without code changes):
1. Thread A begins executing a `TriggerSmartContract` transaction whose bytecode loops on `MLOAD`/`SUICIDE`, entering `VM.play()` and repeatedly calling `jumpTable.get(op)` on the shared table from `OperationRegistry.getTable(false)`.
2. Concurrently, Thread B (e.g., a different transaction, or a maintenance/config-reload path) calls `OperationRegistry.prepareAndGetTable(false)`, which invokes `adjustTable` and mutates `table.set(...)` for `MLOAD`/`SUICIDE` slots based on a flipped `VMConfig` flag (`allowHigherLimitForMaxCpuTimeOfOneTx`/`allowTvmSelfdestructRestriction`).
3. Thread A's in-flight `VM.play()` loop can observe the updated `Operation` for a subsequent opcode fetch mid-transaction, executing with a different opcode cost/action definition than was used to validate energy limits at the start of the transaction, producing a computation that another node (which did not race the write at the same instant) would not reproduce.   public static void adjustMemOperations(JumpTable table) {
    boolean adjusted = VMConfig.allowHigherLimitForMaxCpuTimeOfOneTx();
    table.set(adjusted ? ADJUSTED_MLOAD : DEFAULT_MLOAD);
    table.set(adjusted ? ADJUSTED_MSTORE : DEFAULT_MSTORE);
    table.set(adjusted ? ADJUSTED_MSTORE8 : DEFAULT_MSTORE8);
  }

  public static void adjustVoteWitness(JumpTable table) {
    if (VMConfig.allowTvmOsaka()) {
      table.set(OSAKA_VOTEWITNESS);
    } else if (VMConfig.allowEnergyAdjustment()) {
      table.set(ADJUSTED_VOTEWITNESS);
    } else {
      table.set(DEFAULT_VOTEWITNESS);
    }
  }

  public static void adjustSelfdestruct(JumpTable table) {
    if (VMConfig.allowTvmSelfdestructRestriction()) {
      table.set(RESTRICTED_SUICIDE);
    } else if (VMConfig.allowEnergyAdjustment()) {
      table.set(ADJUSTED_SUICIDE);
    } else {
      table.set(DEFAULT_SUICIDE);
    }
  }
