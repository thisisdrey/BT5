### Title
Shielded (zk-SNARK) private key material transmitted as GET query parameters in Full Node HTTP API - (File: framework/src/main/java/org/tron/core/services/http/)

### Summary
Multiple HTTP servlets exposed by the java-tron Full Node accept raw shielded-transaction key material — spend authorizing keys (`ask`), spend/nullifier keys (`nsk`), outgoing/incoming viewing keys (`ovk`/`ivk`), and viewing/authorizing keys (`ak`/`nk`) — as `doGet` query-string parameters, in addition to a POST body option. This mirrors the reported bug class (CWE-598): secret material handed to the server as part of a URL is exposed to browser history, web/proxy access logs, and the `Referer` header, exactly as with the JWT-in-URL issue in Filebrowser.

### Finding Description
Servlets such as `GetAkFromAskServlet`, `GetExpandedSpendingKeyServlet`, `GetNkFromNskServlet`, `GetIncomingViewingKeyServlet`, `GetZenPaymentAddressServlet`, `ScanAndMarkNoteByIvkServlet`, `ScanNoteByOvkServlet`, and `ScanShieldedTRC20NotesByOvkServlet` implement a `doGet(HttpServletRequest, HttpServletResponse)` handler that reads sensitive values directly via `request.getParameter(...)`: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

The values passed here (`ask`, `nsk`, `ovk`, `ivk`, `ak`, `nk`) are the raw private cryptographic material used to derive spend authority and viewing capability over shielded (zk-SNARK / Sapling) TRC-20 balances, as defined in the protobuf messages: [6](#0-5) 

Because these are accepted as GET query-string parameters (not just via the POST-body path), any client that constructs the GET request — including through browser address bars, embedded links, or automated tooling that logs full request URLs — will leak this key material into:
- Full Node HTTP access logs
- Any reverse proxy / load balancer / CDN request logs sitting in front of the node's HTTP API
- Browser history if the request is triggered/tested via a browser
- The `Referer` header of any subsequent cross-origin request made from the same page

This is the exact bug class in the report: secrets should never be transmitted in the URL because URLs are pervasively logged, regardless of TLS.

### Impact Explanation
Disclosure of `ask`/`nsk` allows full reconstruction of Sapling spending authority for the corresponding shielded address, letting an attacker who obtains node/proxy logs spend the victim's shielded TRC-20 funds. Disclosure of `ovk`/`ivk` allows decrypting the victim's shielded transaction history (confidentiality loss over supposedly private balances/transfers) via the same scan endpoints (`ScanNoteByOvkServlet`, `ScanAndMarkNoteByIvkServlet`, `ScanShieldedTRC20NotesByOvkServlet`). This is a Medium/theft-relevant confidentiality-plus-unauthorized-spend risk consistent with the CVSS profile of the analog report (network/log exposure leading to account compromise), scoped strictly to the shielded-transaction subsystem rather than the whole node.

### Likelihood Explanation
Exploitation does not require the attacker to compromise TLS; it only requires access to any log or history store that records full request URLs on the path between client and Full Node (operator access logs, reverse proxies, browser history/extensions, shared machines). Given that wallets/SDKs interacting with java-tron's shielded APIs may choose the simpler GET form (these servlets explicitly support it) instead of POST, real-world usage of the vulnerable code path is plausible. This matches the "AC:L / PR:H(analogous—key holder)/ UI:N" reasoning in the original advisory, since anyone with the ability to observe such logs — not just the key owner — benefits from the exposure.

### Recommendation
Remove or deprecate the `doGet` handlers on all shielded-key servlets that accept `ask`, `nsk`, `ovk`, `ivk`, `ak`, `nk`, `d` as query parameters (`GetAkFromAskServlet`, `GetExpandedSpendingKeyServlet`, `GetNkFromNskServlet`, `GetIncomingViewingKeyServlet`, `GetZenPaymentAddressServlet`, `ScanAndMarkNoteByIvkServlet`, `ScanNoteByOvkServlet`, `ScanShieldedTRC20NotesByOvkServlet`, and any sibling shielded-scan servlets found via the same pattern), forcing clients to use the POST-body path (`PostParams.getPostParams`) exclusively for any endpoint that transmits private key material. Additionally, document that these endpoints should only ever be called against `localhost`/loopback-bound HTTP servers, never through a public-facing reverse proxy, and ensure access logging for the HTTP API can be configured to exclude request query strings.

### Proof of Concept
```
GET /wallet/getexpandedspendingkey?value=<ASK_NSK_OVK_HEX>&visible=true HTTP/1.1
Host: fullnode.example:8090
```
The `value` parameter here is the raw shielded spending key `ask` concatenated with `nsk`/`ovk` derivation input, processed by `GetExpandedSpendingKeyServlet.doGet` [1](#0-0) . Any intermediary or log aggregator that records the request line captures the full spending key, enabling later unauthorized spends from the corresponding shielded address.
