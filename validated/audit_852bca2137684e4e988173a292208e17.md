### Title
Dust-transfer griefing fills a victim's per-account token list (`MAX_TOKENS_PER_USER`), permanently blocking them from depositing/borrowing new asset types while their balance is locked - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` tracks every `DepositToken` and `DebtToken` an account has ever touched in two `MappedEnumerableSet` lists, capped at `MAX_TOKENS_PER_USER = 30` combined (`Pool.sol:79`, `Pool.sol:143-148`). `DepositToken._transfer` and `_mint` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to >0 (`DepositToken.sol:486-488`, `DepositToken.sol:517-520`), and that add reverts with `UserReachedMaxTokens` once the cap is hit (`Pool.sol:216-220`). Because `DepositToken` is a freely transferable ERC-20, any EOA can push dust amounts of every deposit token in the pool to a victim, filling their list and causing any subsequent receipt of a *new* token type to revert.

### Finding Description
- `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` enforce `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER → revert` (`Pool.sol:143-148`, `204-220`).
- `DepositToken.transfer`/`transferFrom` only require the *sender's* unlocked balance (`DepositToken.sol:348-376`); the recipient cannot refuse.
- The pool itself can register at most 30 deposit tokens (`addDepositToken` enforces `ReachedMaxDepositTokens`, `Pool.sol:703`), so an attacker can deposit 1 wei of each collateral (or acquire dust) and `transfer` it to the victim until the victim's list holds 30 entries.
- Once the list is full, any operation that would add a new token to the victim's list reverts inside the state-changing call:
  - `DepositToken.deposit(amount, onBehalfOf = victim)` reverts in `_mint → addToDepositTokensOfAccount`, so the victim cannot onboard a new collateral type — including via smart-contract wallets or integrations depositing on their behalf.
  - `DebtToken.issue` of a synth the victim has never borrowed reverts identically via `addToDebtTokensOfAccount`, blocking new borrows.
  - `Pool.liquidate` reverts when `depositToken_.seize`/`syntheticToken` flows would add a new token to the feeCollector/liquidator... more importantly, a liquidator or `feeCollector` whose list is full causes `liquidate` to revert for the corresponding collateral (`Pool.sol:589-593` → `DepositToken._transfer` → add).
- Escape is asymmetric: the victim can only free a slot by zeroing a balance via `transfer` or `withdraw`, both gated by `_revertIfLocked`/`unlockedBalanceOf` (`DepositToken.sol:180-182`, `383-398`). A victim with debt has most/all balance locked, so they cannot remove the attacker's dust entries — the DoS persists for the lifetime of the debt.

### Impact Explanation
Unprivileged attacker permanently (for the duration of the victim's debt) blocks the victim from depositing new collateral types or issuing new debt tokens, and can degrade `liquidate` for collaterals the liquidator/feeCollector doesn't yet hold. A victim approaching liquidation cannot rescue the position with a new collateral type, converting a liveness DoS into forced liquidation losses. This mirrors CVE-2022-21628's unauthenticated, low-complexity, partial availability impact.

### Likelihood Explanation
Cost is bounded: deposit minimum amounts of up to 30 pool collateral types and dust-transfer them. No privileged role, oracle manipulation, or flash-loan-sized capital is required. Success depends only on the victim's combined list not already being at 30, and the griefing being strongest against accounts with locked balances.

### Recommendation
- Do not let unsolicited ERC-20 `transfer`/`transferFrom` populate `depositTokensOfAccount`; only add on `deposit`/`seize`, or track collateral membership lazily.
- Alternatively, allow `removeFromDepositTokensOfAccount` to also trigger on reducing a *locked* dust balance, or let users zero-out dust positions regardless of lock status.
- Consider making `addTo*` non-reverting at the cap for `seize`/fee paths so liquidations and withdrawals cannot be blocked.

### Proof of Concept
Hardhat sketch (against deployed pool on a fork):

```ts
// attacker deposits 1 wei of each of the pool's deposit tokens
for (const dt of depositTokens) {
  await underlying(dt).approve(dt.address, 1);
  await dt.deposit(1, attacker.address);        // attacker gets msdX
  await dt.connect(attacker).transfer(victim.address, 1); // victim list += 1
}
// victim list now == MAX_TOKENS_PER_USER

// victim (or anyone) tries to deposit a collateral type the victim hasn't used
await expect(newDepositToken.deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim with debt cannot clear dust: unlockedBalanceOf(victim) == 0
await expect(dt.connect(victim).transfer(attacker.address, 1))
  .to.be.revertedWithCustomError(dt, 'NotEnoughFreeBalance');

// new synth issuance to victim also reverts
await expect(newDebtToken.issue(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

**Uncertainty noted:** I verified the gating logic in `Pool.sol` and `DepositToken.sol`, but did not confirm `DebtToken.issue`'s exact `addToDebtTokensOfAccount` call site line numbers or the deployed count of deposit tokens per pool; the attack's reach (how many of the 30 slots an attacker can fill) equals the number of deposit tokens actually registered on each live pool.
