### Title
Native STX sent directly to a vault contract's principal is permanently unrecoverable and unaccounted for - (File: mainnet/contracts/vault/v0-vault-stx.clar and sibling vault contracts)

### Summary
`wstx.clar` is a thin wrapper whose `get-balance` simply returns `stx-get-balance` of the queried principal and whose `transfer` simply calls `stx-transfer?`. [3](#0-2)  Because of this, "wSTX balance" of any vault contract (e.g. `v0-vault-stx`) is literally the contract's native STX balance, reachable directly through a plain `stx-transfer?` call from any unprivileged principal to the vault's contract address — no special `receive`/deposit call is required, unlike an ERC20 token.

### Finding Description
The vault's internal accounting variable `assets` is only mutated inside explicit protocol entry points: `deposit` (increments it by the deposited amount), `redeem` (decrements it), `flashloan`, and `socialize-debt`. [4](#0-3)  Share price and asset accounting (`total-assets`, `total-assets-preview`, `convert-to-shares-preview`, `convert-to-assets-preview`) are computed strictly from this `assets` variable plus computed interest — never from the raw contract balance (`ubalance`). [1](#0-0)  `ubalance` (raw balance via `.wstx get-balance`) is only used as a liquidity ceiling check inside `flashloan`. [2](#0-1) 

Since `wstx` is not a real SIP-010 token backed by its own ledger but a direct proxy to native STX (`stx-transfer?`/`stx-get-balance`), any ordinary principal can send raw STX directly to the vault contract's on-chain address using a standard STX transfer, entirely bypassing `deposit`. This STX becomes part of the vault's real balance (and thus `ubalance`), but is never reflected in the `assets` variable that governs `total-assets-preview`, share minting/redemption math, or `get-available-assets`/`utilization`. There is no vault function that lets anyone reconcile the raw balance with `assets`, nor any sweep/rescue function analogous to `dao-treasury.withdraw` (which only handles funds routed through it deliberately via `check-dao-auth`, and even then only for FT-trait tokens/wSTX it explicitly manages, not stray STX in arbitrary vault contracts). [5](#0-4)  As a result, this STX is permanently locked in the vault contract: it does not increase share value for depositors (since `assets` doesn't grow), it doesn't mint shares for the sender, and no DAO or user-facing function exists to extract it. This is directly analogous to the `Comet`/`Bulker` bug report's core issue — a contract accepts value through a channel that requires no special call, but has no corresponding withdrawal/sweep path — except here the loss is total and immediate rather than merely a fallback path failing to be exercised.

### Impact Explanation
This results in **permanent freezing/loss of user funds**: any STX (native) accidentally or intentionally sent directly to any of the vault contracts (`v0-vault-stx`, and by the same wSTX-proxy pattern any future STX-underlying vault) becomes permanently stuck, benefiting nobody and unrecoverable by the sender, the DAO, or the protocol. This falls squarely under the Critical impact bucket: "permanent freezing of funds."

### Likelihood Explanation
Likelihood is high in practice because sending STX to a contract's principal is trivial and requires no protocol-specific tooling — any wallet UI mistake (e.g. treating the vault's contract identifier like a normal address) or third-party integration bug would trigger it. It requires no privileged access and no cooperation from the protocol.

### Recommendation
Add a permissioned sweep function (callable only by DAO/authorized governance, similar to `dao-treasury.withdraw`) on each vault contract that can move any raw STX balance exceeding the tracked `assets` value to a recovery address, or reconcile it into `assets`/`total-supply` via an explicit "donate"/"skim" function. Alternatively, document/enforce that vault contracts must never be treated as valid STX transfer targets, and add front-end/tooling safeguards, though a contract-level sweep is the more robust fix.

### Proof of Concept
1. Deploy/observe `v0-vault-stx` at its contract principal `SP....v0-vault-stx`.
2. From any unprivileged wallet, call `(stx-transfer? u1000000 tx-sender 'SP....v0-vault-stx)` directly — a standard STX transfer, not `.v0-vault-stx deposit`.
3. Observe: `(contract-call? .wstx get-balance 'SP....v0-vault-stx)` now reflects the increased raw balance (since it is just `stx-get-balance`), but `(var-get assets)` inside the vault is unchanged, and `total-assets-preview`/`convert-to-shares-preview` do not account for it.
4. No depositor received extra shares, no `assets` value increased, and there is no vault or DAO function that can withdraw this raw STX back out — it is permanently stuck.
