## Title
Missing bounds validation of untrusted central-directory length fields in `InputZipFile::ProcessCentralDirEntry` causes out-of-bounds reads - (File: `third_party/ijar/zip.cc`)

### Summary
`third_party/ijar/zip.cc`'s `InputZipFile::ProcessCentralDirEntry` parses ZIP Central Directory Header (CDH) records and advances its cursor `p` by attacker-controlled 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) without ever validating that these lengths stay within the bounds of the memory-mapped input file. This mirrors the CVE-2023-53194 bug class exactly: a length field taken from untrusted, on-disk structured data is trusted to bound a subsequent read/copy without checking it against the actual remaining buffer size.

### Finding Description
`InputZipFile::ProcessLocalFileEntry` calls `EnsureRemaining()` before every advance of `p` (e.g. [1](#0-0) ), but the sibling function `ProcessCentralDirEntry`, which parses the *central directory* entries that the whole extraction loop (`ProcessNext` → `ProcessAll`) iterates over, has no equivalent check: [2](#0-1) 

`file_name_length`, `extra_field_length`, and `file_comment_length` are read directly from the untrusted CDH bytes and used to:
1. `memcpy` `file_name_length` bytes from `p` into a caller-provided fixed buffer (bounded only by `filename_size`, not by how much data actually remains in the mapped file) — [3](#0-2) .
2. Advance `p` by `file_name_length` and then by `extra_field_length`, and iterate an inner `while (extra_p != p)` loop that calls `get_u2le`/`get_u8le` on `extra_p` with **no check that `extra_p` plus the 4-byte tag/size header, or the declared `data_size`, remain inside the extra-field region or the mapped file at all** — [4](#0-3) .
3. Advance `p` again by `file_comment_length` with no bound check — [5](#0-4) .

The only bound check present anywhere in this path is in `FindZipCentralDirectory`, which validates that `central_dir_offset + central_dir_size <= in_length` for the *aggregate* central directory [6](#0-5) . It never validates that any individual entry's declared lengths keep the parser within `central_dir_size`, nor within the memory-mapped file `in_length` itself. A crafted CDH entry with, e.g., `extra_field_length = 0xFFFF` near the end of the mapped region can push `extra_p`/`p` past the end of the `mmap`'d input file, and the inner loop's `get_u2le(extra_p)` calls then read from unmapped memory — the same "trust the on-disk length field, don't check it against remaining buffer size" defect as the NTFS `indx_get_root` bug that CVE-2023-53194 fixed.

`InputZipFile`/`ZipExtractor` is the general-purpose ZIP central-directory reader shared by ijar (used to build interface jars from `.jar` inputs, including third-party jars fetched as external dependencies) and by `PartialZipExtractor` in `src/main/cpp/archive_utils.cc`.

### Impact Explanation
A malicious `.jar`/`.zip` file — e.g., a third-party dependency artifact whose bytes an attacker controls (the attacker publishes the artifact and its accompanying checksum, so sha256/integrity verification of the downloaded bytes passes, but the checksum does not validate internal structural well-formedness) — can trigger an out-of-bounds read past the memory-mapped file when ijar processes it. Depending on adjacent memory contents this can crash the build process (denial of service for that action) or leak adjacent heap/mmap memory bytes into a copied filename buffer, which is a memory-safety violation reachable directly from attacker-supplied archive bytes.

### Likelihood Explanation
Any build that runs `ijar` over an externally-supplied jar (a very common code path for Java/Android dependencies fetched via `http_jar`, `http_archive`, or Maven-style rules) will invoke this parser on attacker-influenced bytes. No special privileges beyond publishing/serving the artifact are required; the existing sha256/integrity check on download does not protect against structurally malformed ZIP central directory records, since the check happens on raw bytes only.

### Recommendation
Add an `EnsureRemaining`-style bound check in `ProcessCentralDirEntry` before reading and advancing past `file_name_length`, `extra_field_length`, and `file_comment_length`, verifying `p` (and `extra_p` plus each extra-field's 4-byte header/`data_size`) never exceeds `central_dir_ + central_dir_size` (and never exceeds the underlying mmap length). Reject the file with an error instead of continuing to parse when the check fails, matching the pattern already used in `ProcessLocalFileEntry`/`EnsureRemaining`.

### Proof of Concept
A JUnit/`googletest` proof would construct a minimal ZIP file whose single CDH entry declares `extra_field_length = 0xFFFF` (or `file_name_length`/`file_comment_length` similarly oversized) while the actual central directory / mapped file is only a few bytes larger than the CDH header, then invoke `ZipExtractor::Create(...)->ProcessAll()` (as exercised by `third_party/ijar/zip_main.cc`'s `extract()` or `PartialZipExtractor::UnzipUntil`) and observe a crash/ASan out-of-bounds-read report when `get_u2le(extra_p)`/`get_u8le(extra)` read past the end of the mapped input file, analogous to the existing `zip_headers_test.cc` test harness style already present in the repo ( [7](#0-6) ).
