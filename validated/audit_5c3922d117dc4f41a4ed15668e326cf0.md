### Title
Unbounded block / permanent `loading_entries` leak via concurrent program-account closure racing `ProgramCache::extract` cooperative loading - ([File: program-runtime/src/loaded_programs.rs])

### Summary
`ProgramCache::extract` registers a program as a *cooperative loading task* by inserting `(slot, ThreadId)` into `loading_entries: Mutex<HashMap<Pubkey,(Slot, ThreadId)>>`, and the winning thread is expected to always call `finish_cooperative_loading_task` afterward to remove the entry and `notify()` waiters. If the account backing the program is closed between `extract()` releasing the cache lock and the subsequent `load_program_with_pubkey` call, `load_program_with_pubkey` returns `None` and `replenish_program_cache` panics via `.expect("called load_program_with_pubkey() with nonexistent account")` before `finish_cooperative_loading_task` is ever invoked, permanently leaking the `Pubkey` entry in `loading_entries` and blocking any transaction batch that needs that same program.

### Finding Description
`ProgramCache::extract` at [1](#0-0)  registers the calling thread as the sole loader for a given `program_id` by inserting into `loading_entries` only when the `Entry` is `Vacant`. This makes the registration/removal protocol strictly asymmetric: only `finish_cooperative_loading_task` removes the key [2](#0-1) .

Between the `extract()` call and the actual account load, the global cache lock is dropped: [3](#0-2) 

`load_program_with_pubkey` re-reads current account state via `callbacks.get_account_shared_data(pubkey)`, and returns `None` if the account no longer exists [4](#0-3) [5](#0-4) . The caller unconditionally unwraps this with `.expect(...)`: [6](#0-5) 

This exact panic is explicitly reproduced by the existing test: [7](#0-6) 

Because the panic unwinds the worker thread's call stack *before* `finish_cooperative_loading_task` executes, the `(Slot, ThreadId)` entry for that `Pubkey` in `loading_entries` is never removed and `loading_task_waiter.notify()` is never called for that key. Any other transaction batch (on any thread) that subsequently calls `extract()` for the same `program_id` finds the map entry `Occupied`, is not selected as a new cooperative loader, remains in `search_for`, and falls into `task_waiter.wait(task_cookie)` in `replenish_program_cache` [8](#0-7) . Since nothing will ever call `finish_cooperative_loading_task` for that specific key again, any batch requiring it is stuck retrying `extract()`/`wait()` forever (bounded only by unrelated `notify()` broadcasts from other keys' completions, which cause a spin rather than true progress).

Root cause: `extract()`/`finish_cooperative_loading_task()` assume `load_program_with_pubkey` always succeeds once a program has been selected as `cooperative_loading_task`, but the account can be closed concurrently by the actual owner/authority (which the attacker controls for their own deployed program) between the two calls, since the global cache read-lock is deliberately dropped to avoid holding it during the (potentially slow) load.

### Impact Explanation
Concrete impact:
1. **Permanent entry leak in `loading_entries`**: each successful race leaves one `Pubkey` entry stuck forever inside the global, validator-wide `ProgramCache`. An attacker can repeat this with a fresh program deployment each time (permissionless), causing unbounded growth of `loading_entries` over the life of the validator process — an unbounded-memory condition in shared validator state.
2. **Worker-thread panic**: the panic occurs in a transaction-processing worker thread executing `replenish_program_cache`/`load_and_execute_sanitized_transactions`. Depending on how that thread's join/`catch_unwind` boundary is structured, this either kills that worker permanently (reducing available processing concurrency) or propagates further up and aborts the validator process.
3. **Stalled batches for the specific program_id**: any transaction (including unrelated fee-paying users') that references the exact `program_id` whose entry was leaked will loop indefinitely between `extract()` and `task_waiter.wait()`, never completing, since no thread will ever again become responsible for loading that key.

This corresponds to the Agave bounty categories of node panic and unbounded resource growth in the validator's shared program cache.

### Likelihood Explanation
The attacker needs only unprivileged, permissionless capabilities:
- Deploy an upgradeable BPF program under their own authority (no special privileges needed).
- Submit transactions invoking that program to force it to be uncached and trigger the cooperative `extract()` path.
- Concurrently submit a "close program" transaction (using their own upgrade authority) timed via QUIC packet ordering/timing so the account closure lands after `extract()` releases the read lock but before `load_program_with_pubkey` reads the account.

The race window exists on every cooperative load because the code intentionally drops the cache lock before loading; there is no retry/backoff, no re-check of account existence before the `.expect()`, and no cleanup path for the leaked `loading_entries` key. This is deterministic to reproduce in a unit test (as the codebase's own `#[should_panic]` test at `svm/src/transaction_processor.rs:1855` shows the panic is trivially triggerable by a missing account), and only requires normal timing control over one's own transactions, which is within the stated "unprivileged attacker with QUIC control" threat model.

### Recommendation
- In `replenish_program_cache`, do not `.expect()` on `load_program_with_pubkey`'s `None` result. Instead, when the account has disappeared, still call `finish_cooperative_loading_task` (e.g., with a tombstone/`InvalidAccountData`/closed entry) so the `loading_entries` slot is always released regardless of load outcome.
- Guard the removal of `loading_entries` with a `Drop` guard (RAII) established immediately when the entry is inserted in `extract()`, so that any panic during the load automatically triggers `finish_cooperative_loading_task`-equivalent cleanup and `notify()`, preventing permanent leaks/stalls even under unexpected panics.
- Consider re-validating account existence transactionally as part of loading, not with an `.expect()`, since account closure is legitimately possible.

```rust
// svm/src/transaction_processor.rs (extension of existing test)
#[test]
fn test_cooperative_loading_leak_on_missing_account_race() {
    use std::sync::{Arc, Barrier};
    use std::thread;

    let mock_bank = MockBankCallback::default();
    let fork_graph = Arc::new(RwLock::new(TestForkGraph {}));
    let batch_processor = Arc::new(TransactionBatchProcessor::new(
        0, 0, Arc::downgrade(&fork_graph), None,
    ));
    let key = Pubkey::new_unique();
    // NOTE: account intentionally absent to simulate a close-account race
    // landing before load_program_with_pubkey reads it.

    let env = batch_processor.program_runtime_environment_for_epoch(0);
    let account_loader = (&mock_bank).into();

    // Thread A: becomes cooperative loader, then panics inside replenish_program_cache
    // because the account no longer exists (simulating the race).
    let bp = Arc::clone(&batch_processor);
    let handle = thread::spawn(move || {
        let mut batch = ProgramCacheForTxBatch::new(bp.slot);
        let _ = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
            bp.replenish_program_cache(
                &account_loader,
                vec![ProgramToLoad {
                    program_id: &key,
                    loader: ProgramCacheEntryOwner::LoaderV3,
                    match_criteria: ProgramCacheMatchCriteria::NoCriteria,
                    last_modification_slot: 0,
                }],
                &env,
                &mut batch,
                &mut ExecuteTimings::default(),
                true,
                true,
            );
        }));
    });
    handle.join().unwrap();

    // Assert: `loading_entries` for `key` should be empty after the panic
    // recovers, but currently remains permanently populated because
    // finish_cooperative_loading_task() was never called.
    let cache = batch_processor.global_program_cache.read().unwrap();
    match &cache.index {
        IndexImplementation::V1 { loading_entries, .. } => {
            assert!(
                loading_entries.lock().unwrap().get(&key).is_none(),
                "BUG: loading_entries leaked an entry for {key} after a panic \
                 in the cooperative loading task, causing future extract() calls \
                 for this program to block forever"
            );
        }
    }
}
```
Expected (buggy) result: the assertion fails — `loading_entries` still contains the leaked `key`, confirming that any future call to `extract()` for `key` will never obtain a new `cooperative_loading_task` and will spin/block forever in `replenish_program_cache`'s `task_waiter.wait()` loop.

```rust
    pub fn finish_cooperative_loading_task(
        &mut self,
        program_runtime_environment: &ProgramRuntimeEnvironment,
        current_slot: Slot,
        key: Pubkey,
        last_modification_slot: Slot,
        loaded_program: Arc<ProgramCacheEntry>,
    ) -> bool {
        match &mut self.index {
            IndexImplementation::V1 {
                loading_entries, ..
            } => {
                let loading_thread = loading_entries.get_mut().unwrap().remove(&key);
                debug_assert_eq!(loading_thread, Some((current_slot, thread::current().id())));
                // Check that it will be visible to our own fork once inserted
                if loaded_program.deployment_slot > self.latest_root_slot
                    && !matches!(
                        self.fork_graph
                            .as_ref()
                            .unwrap()
                            .upgrade()
                            .unwrap()
                            .read()
                            .unwrap()
                            .relationship(loaded_program.deployment_slot, current_slot),
                        BlockRelation::Equal | BlockRelation::Ancestor
                    )
                {
                    self.stats.lost_insertions.fetch_add(1, Ordering::Relaxed);
                }
                let was_occupied = self.assign_program(
                    program_runtime_environment,
                    key,
                    last_modification_slot,
                    loaded_program,
                );
                self.loading_task_waiter.notify();
                was_occupied
            }
        }
    }
```
