### Title
`VesperGateway.deposit` assumes the full `amount_` of a fee-on-transfer underlying is received and reverts / mis-approves inside `vToken_.deposit` — (contracts/VesperGateway.sol)

### Summary
`VesperGateway.deposit` pulls `amount_` of the vToken's underlying asset from the caller, then approves and calls `vToken_.deposit(amount_)` with the *nominal* amount instead of the *actual received* amount. For any whitelisted vToken whose underlying charges a transfer fee, the gateway receives less than `amount_`, and `vToken_.deposit(amount_)` fails on `transferFrom` (insufficient gateway balance) — so the deposit path always reverts. This is the same bug class as the referenced Malt finding (`_bond()` reverting because it assumes the full amount arrived), and it stands in contrast to `DepositToken.deposit` and `SmartFarmingManager._safeTransferFrom`, which correctly measure the balance delta.

### Finding Description
In `VesperGateway.deposit` (contracts/VesperGateway.sol:44-65):

```solidity
// contracts/VesperGateway.sol:50-57
IERC20 _underlying = IERC20(vToken_.token());
_underlying.safeTransferFrom(_msgSender, address(this), amount_);

_underlying.safeApprove(address(vToken_), 0);
_underlying.safeApprove(address(vToken_), amount_);
uint256 _balanceBefore = vToken_.balanceOf(address(this));
vToken_.deposit(amount_);
```

`_underlying.safeTransferFrom(_msgSender, address(this), amount_)` credits the gateway with `amount_ - fee` for a fee-on-transfer token, but the code then approves `vToken_` for `amount_` and calls `vToken_.deposit(amount_)`. Vesper's `VPool.deposit` performs `transferFrom(gateway, pool, amount_)` for the full `amount_`, which exceeds the gateway's actual balance and reverts.

By comparison, the protocol's own code demonstrates the correct pattern:
- `DepositToken.deposit` measures the treasury balance delta and rewrites `amount_` accordingly (contracts/DepositToken.sol:225-227).
- `SmartFarmingManager._safeTransferFrom` returns the actual transferred amount (contracts/SmartFarmingManager.sol:257-261).
- `VesperGateway.withdraw` itself measures `_underlying` by balance delta (contracts/VesperGateway.sol:87-89) — only the deposit side forgets to.

`vToken_` is an attacker/user-chosen argument gated only by `pool_.depositTokenOf(vToken_)` returning an active `DepositToken` (i.e., a whitelisted collateral), and `pool_` must pass `isPoolRegistered`. If any whitelisted vToken's underlying is (or becomes, e.g., USDT/USDC-style fee switches) fee-on-transfer, this entry point is permanently unusable.

### Impact Explanation
Every call to `VesperGateway.deposit` for a fee-on-transfer underlying reverts inside `vToken_.deposit`, permanently denying that deposit route for the affected collateral. Users cannot lose principal in the gateway itself (the revert restores the pulled funds), so the direct impact is liveness/DoS of a public deposit path rather than theft — the same impact profile as the original Malt finding, where `_bond()` reverted in `_balanceCheck`.

### Likelihood Explanation
Likelihood is conditional on a whitelisted collateral whose `token()` charges a transfer fee. Deployed Metronome pools use Vesper vTokens over standard assets (WETH, USDC, WBTC, etc.), none of which currently take a fee, so on today's configuration the path does not revert — but the code is structurally unsafe and the fix pattern already exists elsewhere in the same codebase. Any future whitelisting of (or fee activation on) such a token silently bricks the gateway path. No privileged action, oracle manipulation, or governance involvement is needed to trigger the revert once such a collateral exists.

### Recommendation
Measure the actual amount received before depositing into the vToken, mirroring `DepositToken.deposit`:

```solidity
uint256 _underlyingBefore = _underlying.balanceOf(address(this));
_underlying.safeTransferFrom(_msgSender, address(this), amount_);
amount_ = _underlying.balanceOf(address(this)) - _underlyingBefore;
```

Then approve `vToken_` for the measured `amount_` before calling `vToken_.deposit(amount_)`.

### Proof of Concept
A Hardhat test in the style of the existing fee-on-transfer test in `test/DepositToken.test.ts` (which uses `ERC20Mock.updateFee`, contracts/mock/ERC20Mock.sol:73-83):

```ts
it('reverts depositing a fee-on-transfer underlying through VesperGateway', async () => {
  // underlying of a whitelisted vToken (mocked VPool) charges 10% transfer fee
  await underlying.updateFee(parseEther('0.1'))

  const amount = parseEther('100')
  await underlying.mint(alice.address, amount)
  await underlying.connect(alice).approve(vesperGateway.address, amount)

  // gateway receives only 90, then vToken.deposit(100) pulls more than balance -> revert
  await expect(
    vesperGateway.connect(alice).deposit(pool.address, vToken.address, amount)
  ).to.be.reverted // ERC20: transfer amount exceeds balance (inside VPool.deposit)
})
```

The revert occurs inside `vToken_.deposit(amount_)` at contracts/VesperGateway.sol:57 because the gateway's actual balance is `amount_ - fee` after the pull at line 51.

Note on acceptance criteria: this is a reachable, unprivileged DoS of a public deposit entry point identical in mechanism to the source finding; it does not by itself cause theft or insolvency on the currently deployed collateral set. If a stricter impact bar (funds already lost/frozen) is required rather than "function reverts for fee-on-transfer tokens," this analog does not meet it.
