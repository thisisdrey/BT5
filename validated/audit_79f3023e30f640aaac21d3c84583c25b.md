## Title
Precompiled contract array-length parsing without full bounds validation causes unguarded `ArrayIndexOutOfBoundsException` from attacker-controlled TVM call data - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

## Summary
The Mini-XML CVE is a stack-buffer-overflow class bug: an untrusted, malformed length/structure field drives an unbounded array read in a low-level parser (`mxml_string_getc`). The closest reachable analog in java-tron is `PrecompiledContracts.extractSigArray` / `extractBytesArray` / `extractBytes32Array`, which decode an attacker-supplied length word from TVM call data and then index into the `DataWord[] words` array using that length without validating that the derived index stays within `words.length`.

## Finding Description
`extractSigArray` and `extractBytesArray` only bounds-check the initial `offset` argument, not the loop bound derived from attacker data: [1](#0-0) [2](#0-1) 

In both methods, `len` is read directly from `words[offset].intValueSafe()` — a 256-bit word fully controlled by the caller's ABI-encoded call data to the `BatchValidateSign` / `ValidateMultiSign` precompiled contracts. The subsequent loop `for (int i = 0; i < len; i++) { ... words[offset + i + 1] ... }` never checks `offset + i + 1 < words.length`. A caller can set `len` to an arbitrarily large value (e.g. `Integer.MAX_VALUE` or any value larger than the actual `words` array size) while supplying a `words` array that is short, forcing `words[offset + i + 1]` to throw `ArrayIndexOutOfBoundsException`.

This mirrors the CVE-2021-42860 bug class: a length/count field taken from untrusted input is used to drive array access without validating it against the actual buffer size, causing out-of-bounds access instead of the intended bounds-checked parse. Compare this to the properly bounds-checked analogs elsewhere in the same file and codebase — `RLP.verifyLength` [3](#0-2) , `ContractEventParser.subBytes` [4](#0-3) , and `ByteUtil.parseBytes` [5](#0-4)  — all of which explicitly validate the requested length/offset against the actual array/buffer length before copying. `extractSigArray`/`extractBytesArray` lack this equivalent check on the loop bound.

## Impact Explanation
An unhandled `ArrayIndexOutOfBoundsException` thrown from inside precompiled-contract execution during TVM opcode dispatch is a `RuntimeException`, not one of the checked exceptions (`ContractExeException`/`ContractValidateException`) that the transaction/block-application pipeline is generally designed to catch. If this exception is not caught by an enclosing handler in the TVM's per-opcode/CALL dispatch path, it can propagate out of transaction execution during block application, potentially aborting block processing on a node (Medium/High DoS impact) rather than being confined to a graceful revert of the single contract call. I was not able to fully confirm, within the available search iterations, whether the outer `CALL`/precompiled-contract dispatch code in `Program.java` wraps this call in a catch-all `Throwable`/`RuntimeException` handler (as is done explicitly and defensively in several other precompiled contracts in the same file, e.g. `VerifyMintProof`, `VerifyBurnProof`, `recoverAddrBySign`, which wrap their logic in `catch (Throwable any)`). `extractSigArray`/`extractBytesArray` themselves are called directly with no such wrapping visible in the excerpt, in contrast to those other precompiles.

## Likelihood Explanation
Reaching this code only requires an unprivileged contract caller to invoke the `BatchValidateSign` or `ValidateMultiSign` precompiled contract with crafted ABI-encoded call data (a broadcastable smart-contract call), setting the length word at the expected offset to a value larger than the actual data/word array. This is trivially reachable by any account able to submit a `TriggerSmartContract` transaction.

## Recommendation
Add an explicit bounds check on the derived loop index in `extractSigArray` and `extractBytesArray` (and `extractBytes32Array`), e.g. validate `offset + len + 1 <= words.length` (and similarly validate `bytesOffset`-derived indices) before use, returning an empty array or throwing a handled exception otherwise — consistent with the bounds checks already used in `RLP.verifyLength`, `ContractEventParser.subBytes`, and `ByteUtil.parseBytes`. Additionally, confirm (or add) a catch-all exception boundary around precompiled contract `execute()` invocation in the TVM CALL dispatch path so any residual parsing bug degrades to a call revert rather than escaping transaction execution.

## Proof of Concept
1. Deploy or call an existing contract that invokes the `BatchValidateSign` (or `ValidateMultiSign`) precompiled contract via a `CALL`/`STATICCALL` opcode, supplying ABI-encoded `data` such that:
   - the `DataWord` at the expected `offset` (the "length" word) decodes via `intValueSafe()` to a large value, e.g. larger than the number of actual 32-byte words present in `data`.
2. Submit this as a normal `TriggerSmartContractContract` transaction from any account with enough energy to reach the precompile call.
3. During precompiled contract execution, `words[offset + i + 1]` in `extractSigArray`/`extractBytesArray` is accessed with `i` approaching the attacker-supplied `len`, exceeding `words.length`, throwing `ArrayIndexOutOfBoundsException`.
4. Observe whether this exception is caught and converted into a reverted call (expected, lower severity) or propagates further up the execution/block-application stack (higher severity, DoS).

*Note: I could not fully verify, within available search iterations, the exact exception-handling boundary around this call site in `Program.java`'s CALL/precompiled dispatch logic, so the ultimate severity (contained revert vs. node-impacting crash) is not fully confirmed from the code I was able to inspect.*
