### Title
Permissionless Exchange (Bancor-style) pool creation lets any account set an attacker-controlled price for arbitrary TRC10/TRX pairs with no whitelist - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java])

### Summary
`ExchangeCreateActuator` lets any signed account create a bancor-formula liquidity pool (`ExchangeCreateContract`) for an arbitrary pair of TRC10 tokens (or TRX), fully choosing both initial reserves and thus the implied exchange rate, with no whitelist or governance check on either the tokens or the price ratio, mirroring the report's core concern about permissionless, unvetted price-setting mechanisms that other users may unknowingly trust.

### Finding Description
`ExchangeCreateActuator.doValidate()` only checks that the tokens differ, that balances are positive and under `exchangeBalanceLimit`, and that the creator actually has the funds; it performs no assessment of the token pair's legitimacy or of whether the chosen reserve ratio reflects a fair market price: [1](#0-0) 
Because anyone can also freely mint a new TRC10 asset via `AssetIssueContract` before creating the pool, a malicious actor fully controls both sides of the pair and can set the initial `firstTokenBalance`/`secondTokenBalance` to any ratio they like when calling `ExchangeCreateActuator.execute`: [2](#0-1) 
Once created, the pool's price is derived purely from these attacker-chosen reserves via the bancor relay formula in `ExchangeProcessor`/`SafeExchangeProcessor`, and any other account can trade against it through `ExchangeTransactionActuator` or add proportional liquidity through `ExchangeInjectActuator` without any signal that the pool's price was set adversarially: [3](#0-2) [4](#0-3) 
This is directly analogous to the reported Curve StableSwap-NG issue: a permissionless "pool factory" primitive (here TRON's native Exchange, there Curve pools) allows a single unprivileged transaction to fix a price-determining mechanism (reserve ratio / oracle) that other users, wallets, aggregators, or naive integrators may later trust and interact with, without any whitelist gate over who may define that price source.

### Impact Explanation
Unlike a constant-product AMM whose price is only meaningful once liquidity is contributed by multiple parties, TRON's Exchange lets the creator single-handedly fix the *initial* implied price of an arbitrary token pair. Any later trader or LP who is unaware the pool was seeded adversarially (e.g., trusting the on-chain existence of an "official-looking" TRC10/TRX exchange, or interacting programmatically via `ExchangeTransactionContract`/`ExchangeInjectContract`) can permanently lose value: swaps at the skewed rate transfer real TRX/asset value to the malicious pool creator, and injectors are forced to deposit in the same skewed ratio, locking in the loss. This matches the report's "Curve LPs will lose value" scenario, but for TRON's native DEX-like primitive.

### Likelihood Explanation
Every step is reachable by a normal unprivileged account with a single signed transaction: issuing a TRC10 asset (`AssetIssueContract`), creating the pool (`ExchangeCreateContract`), and then either trading (`ExchangeTransactionContract`) or waiting for other users/bots to interact with the pool. No special privileges, governance approval, or malicious-SR/witness/peer behavior is required, satisfying the in-scope "asset issuer"/"order placer" personas.

### Recommendation
Introduce a whitelist/governance-gated allowlist for which TRC10 token pairs (or which accounts) may create `ExchangeCreateContract` pools, or require that initial reserve ratios be validated against an independent reference price before the pool is exposed to public trading/injection, consistent with the original report's recommendation for Curve.

### Proof of Concept
1. Attacker issues a new TRC10 token `FAKE` via `AssetIssueContract`.
2. Attacker calls `ExchangeCreateContract` with `firstTokenId = "_"` (TRX), `firstTokenBalance = 1 TRX`, `secondTokenId = FAKE`, `secondTokenBalance = 1,000,000 FAKE` — see `ExchangeCreateActuator.execute` at [2](#0-1) , which accepts this with no ratio/whitelist check.
3. A victim (unaware of the skew) calls `ExchangeTransactionContract` to sell TRX into the pool, or `ExchangeInjectContract` to add liquidity proportionally to the already-skewed ratio, both processed via the bancor formula in `ExchangeCapsule.transaction` at [3](#0-2) , permanently losing value to the attacker-controlled pool.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
