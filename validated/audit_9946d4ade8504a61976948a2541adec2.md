Looking at the `revoke` function carefully:

The vulnerability is real. Here is the analysis:

---

### Title
Cross-Root Unauthorized Delegate Revocation via Missing Root Binding Check — (`aptos-move/framework/aptos-stdlib/sources/capability.move`)

### Summary

The `revoke` function destroys a target's `CapDelegateState<Feature>` using only `move_from`, then attempts to clean up `self.root`'s delegates list. It never asserts that `self.root` equals the `root` stored inside the victim's `CapDelegateState`. Any holder of `Cap<Feature>` rooted at Y can therefore permanently destroy the `CapDelegateState` of a delegate that was authorized by a completely different root X, while leaving a stale, unremovable entry in X's `CapState.delegates`.

### Finding Description

In `revoke`:

```move
public fun revoke<Feature>(self: Cap<Feature>, _feature_witness: &Feature, from: address)
acquires CapState, CapDelegateState
{
    if (!exists<CapDelegateState<Feature>>(from)) return;
    let CapDelegateState { root: _root } = move_from<CapDelegateState<Feature>>(from);   // (1)
    remove_element(&mut borrow_global_mut<CapState<Feature>>(self.root).delegates, &from); // (2)
}
``` [1](#0-0) 

At **(1)**, `_root` — the root that originally delegated to `from` — is extracted and immediately discarded. There is no `assert!(self.root == _root, ...)` guard. At **(2)**, the cleanup targets `self.root`'s delegates list, not `_root`'s. When `self.root != _root`:

- `move_from<CapDelegateState<Feature>>(from)` permanently destroys victim's delegate state.
- `remove_element` on `self.root`'s list is a no-op (victim was never in Y's list).
- X's `CapState.delegates` retains a stale entry for `from`.

The stale entry is **permanently unremovable**: a subsequent call to `revoke` by X returns early at line 174 because `CapDelegateState` no longer exists at `from`, so the `remove_element` on X's list is never reached. [2](#0-1) 

`delegate` uses `add_element` which is idempotent (skips duplicates), so X re-delegating to `from` would create a new `CapDelegateState` but would not double-insert into the delegates list — the stale entry silently becomes the live entry. This masks the corruption but does not eliminate it. [3](#0-2) 

### Impact Explanation

- **Unauthorized state transition**: An attacker holding any valid `Cap<Feature>` (rooted at Y) can unilaterally destroy the `CapDelegateState` of a delegate authorized by a different root X, without X's consent and without holding X's capability.
- **Permanent access denial**: The victim delegate immediately loses the ability to call `acquire<Feature>`, since `validate_acquire` requires both `CapDelegateState` to exist and the address to appear in the root's delegates list.
- **Persistent state corruption**: X's `CapState.delegates` vector is left with a stale entry that X cannot remove through any public API path, corrupting X's authorization bookkeeping indefinitely. [4](#0-3) 

### Likelihood Explanation

The attacker must supply `_feature_witness: &Feature`, which is a reference to the phantom witness type owned by the module defining `Feature`. This confines the exploit to callers operating within that module's context. However, any module that (a) permits multiple roots for the same `Feature` type and (b) exposes a path for cap holders to call `revoke` is fully vulnerable. The `revoke` function is `public`, so any such module is one transaction away from exploitation by any address that legitimately holds a `Cap<Feature>`.

### Recommendation

After `move_from`, assert that the revocation is authorized by the correct root:

```move
let CapDelegateState { root } = move_from<CapDelegateState<Feature>>(from);
assert!(root == self.root, error::invalid_argument(EDELEGATE));
remove_element(&mut borrow_global_mut<CapState<Feature>>(self.root).delegates, &from);
```

This ensures only the root that originally delegated to `from` can revoke that delegation, preserving the invariant that `CapDelegateState.root` and the corresponding `CapState.delegates` entry are always managed by the same authority.

### Proof of Concept

```move
#[test(aptos_framework = @aptos_std, x = @0xA, y = @0xB, victim = @0xC)]
fun test_cross_root_revoke(x: &signer, y: &signer, victim: &signer) {
    // Both X and Y create independent capability roots for the same Feature
    capability::create<Feature>(x, &Feature{});
    capability::create<Feature>(y, &Feature{});

    // X delegates to victim
    let cap_x = capability::acquire<Feature>(x, &Feature{});
    capability::delegate(cap_x, &Feature{}, victim);

    // Confirm victim is a valid delegate of X
    let cap_victim = capability::acquire<Feature>(victim, &Feature{});
    assert!(capability::root_addr(cap_victim, &Feature{}) == @0xA, 0);

    // Attacker (Y) calls revoke(from = victim) using Y's cap
    let cap_y = capability::acquire<Feature>(y, &Feature{});
    capability::revoke(cap_y, &Feature{}, @0xC);

    // victim's CapDelegateState is now destroyed — acquire will abort
    // X's delegates list still contains @0xC (stale, unremovable)
    // assert: exists<CapDelegateState<Feature>>(@0xC) == false
    // assert: spec_delegates<Feature>(@0xA) still contains @0xC
}
```
