### Title
Unhardened bancor-style TRC10 Exchange trade path allows draining pool reserves below zero via floating-point imprecision - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
The external report describes Uniswap spot-price manipulation through reserve changes that break downstream logic relying on an instantaneous AMM price. The closest reachable analog in java-tron is the built-in TRC10 **Exchange** module, a bancor-formula AMM (`ExchangeCreateActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator`/`ExchangeTransactionActuator`). Trade output is computed from the *instantaneous* pool reserves stored in `ExchangeCapsule`, and — critically — the non-hardened (legacy/default) calculation path performs **no post-trade solvency check**, unlike the hardened path. This lets a single `ExchangeTransactionContract` broadcast, using floating-point precision loss in the bancor formula, extract more of a token than the pool actually holds.

### Finding Description
`ExchangeCapsule.transaction()` dispatches to either `ExchangeProcessor` (legacy, double/`Math.pow` based) or `SafeExchangeProcessor` (BigDecimal-based, hardened) depending on `hardenedCalc`: [1](#0-0) 

The resulting balances are only checked for non-negativity **when `hardenedCalc` is true**: [2](#0-1) 

`hardenedCalc` is driven by `allowHarden()`, which reads a dynamic-properties flag (`allowHardenExchangeCalculation`) that must be explicitly enabled by a committee proposal: [3](#0-2) 

When this flag is not enabled (the historically default state), trades run through the legacy `ExchangeProcessor`, whose math is entirely double-precision floating point, including `Math.pow(base, 2000.0)`: [4](#0-3) 

Because no invariant re-check exists on this path, if the floating-point computation for `exchangeFromSupply` yields an output (`buyTokenQuant`) that is larger than the actual `buyTokenBalance` in the pool (plausible near precision boundaries with a large exponent like 2000 and no clamping), `ExchangeCapsule.transaction()` will happily set a **negative** `newFirstTokenBalance`/`newSecondTokenBalance` and persist it.

`ExchangeTransactionActuator.execute()` then unconditionally credits the caller with this computed `anotherTokenQuant`, without ever validating it against the actual reserve balance before mutation: [5](#0-4) 

`doValidate()` only checks `anotherTokenQuant < tokenExpected` (a slippage-style check controlled by the attacker's own `expected` parameter) — it does not verify `anotherTokenQuant <= currentBuyTokenBalance`: [6](#0-5) 

This is directly analogous to the reported bug class: a price computed from mutable, single-transaction-manipulable state (here, floating-point reserve math rather than flash-loaned reserves) is trusted without a sanity/invariant check, and that untrusted value is used to move real value (asset/TRX balances) between accounts.

### Impact Explanation
An attacker who can trigger this floating-point overshoot in `ExchangeProcessor.exchangeFromSupply`/`exchangeToSupply` can receive more of the counter-token than the pool's `firstTokenBalance`/`secondTokenBalance` actually contains. This:
- Creates an unbacked/negative on-chain reserve balance in `Exchange`/`ExchangeV2` protobuf state.
- Effectively steals value from the pool (and thus from other participants/liquidity, e.g. subsequent `ExchangeWithdrawActuator` callers who can no longer withdraw their proportional share since the reserve accounting is corrupted).
- Is reachable by any unprivileged account via a single signed `ExchangeTransactionContract`, satisfying the “unauthorized account operation / theft / permanent freezing of funds” bar.

### Likelihood Explanation
Likelihood depends on whether specific `(firstTokenBalance, secondTokenBalance, sellTokenQuant)` triples exist where `Math.pow` (double precision) overshoots enough to exceed the real counter-balance, and on whether `allowHardenExchangeCalculation` is active on the network being assessed. The existence of a parallel, explicitly “hardened” `SafeExchangeProcessor` plus test cases in `ExchangeProcessorTest`/`ExchangeCapsuleTest` demonstrating divergence between legacy and hardened results (`testStrictMath`, `testTransactionLegacyVsHardenedProcessorSelection`) confirms the floating-point path is known to be numerically imprecise; whether the imprecision can be pushed far enough to flip a balance negative for realistic reserve magnitudes was not confirmed from static review alone and would require numerical exploration/fuzzing of the formula across the full `long` input domain.

### Recommendation
- Make the post-trade non-negativity/solvency invariant unconditional in `ExchangeCapsule.transaction()`, not gated behind `hardenedCalc`.
- Require `ExchangeTransactionActuator.doValidate()`/`execute()` to explicitly assert `anotherTokenQuant <= currentBuyTokenBalance` before mutating and crediting balances, independent of the caller-supplied `expected` value.
- Consider deprecating the legacy double-based `ExchangeProcessor` entirely in favor of the `SafeExchangeProcessor` (BigDecimal) path by default, rather than opt-in via a dynamic property.

### Proof of Concept
Exact numeric inputs that trigger a negative-balance overshoot in the legacy `ExchangeProcessor` were not derived within this review (would require targeted numerical search over `(sellTokenBalance, buyTokenBalance, sellTokenQuant)` near precision boundaries of `Math.pow(x, 2000.0)`). The reachable call chain is:
1. Attacker (or anyone) creates/joins an existing TRC10 `Exchange` pool.
2. Attacker crafts `ExchangeTransactionContract{tokenId, quant, expected=1}` such that `ExchangeProcessor.exchange()` (invoked from `ExchangeCapsule.transaction()` with `hardenedCalc=false`) returns `anotherTokenQuant` greater than the pool's actual counter-token balance.
3. `ExchangeTransactionActuator.execute()` credits the attacker with `anotherTokenQuant` and persists the (now negative) `ExchangeCapsule` balance via `Commons.putExchangeCapsule`, with no invariant check blocking it (only reachable in the `hardenedCalc == false` branch, since the check at `ExchangeCapsule.java:160` is gated by `hardenedCalc`).

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
