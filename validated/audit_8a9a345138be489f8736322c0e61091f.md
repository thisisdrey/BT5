### Title
VotePacketReceiver never checks `PacketFlags::DISCARD`, letting sigverify-failed vote packets reach VoteStorage as "passed_sigverify_count" - ([File: core/src/banking_stage/vote_packet_receiver.rs])

### Summary
`VotePacketReceiver::buffer_packet_batch` iterates every packet in a `BankingPacketBatch` and calls `SanitizedTransactionView::try_new_sanitized` without ever checking `packet.meta().discard()`, unlike every other consumer of post-sigverify `PacketBatch`es in the codebase. Because `SigVerifyWorkerPool::run_transaction_task` only skips forwarding a batch when *all* packets in it fail verification (`num_valid_packets == 0`), a batch containing at least one genuinely valid packet is forwarded in full - including packets whose signatures failed `perf::sigverify::verify_packet` and were only marked `discard=true`, not removed.

### Finding Description
`SigVerifyWorkerPool::run_transaction_task` (`core/src/sigverify.rs:326-344`) runs `sigverify::ed25519_verify_serial`, which per-packet calls `perf::sigverify::verify_packet` and marks failing packets with `packet.meta_mut().set_discard(true)` (`perf/src/sigverify.rs:108-133`). It then computes `num_valid_packets = sigverify::count_valid_packets(...)` and only aborts sending the *entire batch* when that count is zero: [1](#0-0) 
If even one packet in the batch is valid, the whole `PacketBatch` (containing both valid and discard-marked invalid packets) is wrapped into a `BankingPacketBatch` and sent on `banking_stage_sender`, which for the TPU-vote path feeds `VotePacketReceiver`'s channel.

`VotePacketReceiver::buffer_packet_batch` then processes every packet in that batch with no `meta().discard()` filter at all: [2](#0-1) 
Contrast this with every other consumer of post-sigverify `PacketBatch`es in the codebase, which explicitly filter on the discard flag: `forwarding_stage.rs`'s `initial_packet_meta_filter` (`!meta.discard() && ...`), `sigverify.rs`'s `apply_priority_floor_to_batch` (`if packet.meta().discard() { continue; }`), and the sigverify stage's own tests/benches (`.filter(|packet| !packet.meta().discard())`). [3](#0-2) [4](#0-3) 

Because `VotePacketReceiver` skips this check, any packet in a mixed-validity batch that structurally parses (sanitizes) as a transaction is unconditionally counted as buffered/valid: `update_receive_stats` derives `passed_sigverify_count` purely from `errors + num_buffered_packets + filtered_account_key_count`, with no reference to `meta().discard()` whatsoever: [5](#0-4) 
The packet is then handed to `vote_storage.insert_packet(vote_source, packet)`. `VoteStorage`'s own authorization check only validates that the *signer field marked in the transaction message* matches the epoch's authorized voter pubkey (`tx.message.is_signer(i) && key == authorized_voter`) — it never re-executes ed25519 signature verification itself, relying entirely on the upstream sigverify stage having already discarded bad signatures: [6](#0-5) 

Exploit flow: an unstaked attacker sends a UDP/QUIC burst to the leader's TPU-vote port containing two packets in the same OS-level receive batch: (1) any trivially self-signed, genuinely valid transaction (to make `num_valid_packets >= 1` for the batch), and (2) a forged "vote" packet referencing a real, known authorized-voter pubkey as signer but carrying an invalid/garbage signature. Sigverify marks packet (2) `discard=true` but still forwards the whole batch because of packet (1). `VotePacketReceiver` ignores the discard flag, parses packet (2) successfully (parsing only requires structural sanitization, not signature validity), and buffers it into `VoteStorage`, incrementing `passed_sigverify_count` for a packet that never passed `ed25519_verify_serial`/`verify_packet`.

### Impact Explanation
This is a signature-verification bypass allowing an unsigned/forged vote-shaped transaction to enter `VoteStorage` and downstream vote processing/scheduling metrics as if it had passed sigverify, violating the invariant "no path marks a packet verified without checking it." Depending on what further validation `VoteWorker`/`Consumer` performs before executing (bank execution ultimately re-verifies signatures at the runtime level for actual state changes), the primary concrete impact is a verification-bypass at the ingress/metrics/buffering layer of banking stage — packets that should be classified `failed_sigverify_count` are instead classified `passed_sigverify_count` and queued for processing, corrupting scheduling decisions and consuming buffer capacity that a discard check would have avoided. This matches Agave's "verification bypass" bounty category.

### Likelihood Explanation
Fully reachable by an unstaked remote client sending arbitrary UDP/QUIC packets to a leader's public TPU-vote port; no staked/leader/gossip control is required. The only precondition is getting two packets (one valid, one forged) coalesced into the same `PacketBatch` at the FetchStage/QUIC ingestion boundary, which is a normal outcome of batched socket receives (`recv_mmsg`/QUIC stream batching) under a fast burst from a single sender. This is deterministic and repeatable.

### Recommendation
Add an explicit `if packet.meta().discard() { continue; }` (or equivalent filter) at the top of `VotePacketReceiver::buffer_packet_batch`'s per-packet loop in `core/src/banking_stage/vote_packet_receiver.rs`, mirroring the discard checks already present in `forwarding_stage.rs` and `sigverify.rs`. Additionally, consider making `run_transaction_task`'s early-return decision (and the `passed_sigverify_count`/`failed_sigverify_count` accounting) reflect per-packet discard state consistently across all consumers of `BankingPacketBatch`.
