### Title
Held (non-immediately-retryable) transactions bypass priority-queue eviction, allowing `push_ids_into_queue`/`flush_held_transactions` to attempt eviction from an empty queue while the map is full, panicking or unfairly evicting fresh high-priority transactions - ([File: core/src/banking_stage/transaction_scheduler/transaction_state_container.rs])

### Summary
`TransactionStateContainer` enforces capacity by comparing `id_to_transaction_state.len()` (the map, which includes held transactions) against `capacity`, but only evicts from `priority_queue`, which never contains held transactions. [1](#0-0)  Because `hold_transaction` pushes into `held_transactions` without adding to `priority_queue`, an attacker who reliably drives their transactions into the "held" (`immediately_retryable=false`) path can fill the map to capacity with entries that are invisible to the eviction logic, so a subsequent `push_ids_into_queue` call (from either newly received transactions or `flush_held_transactions` itself) can be forced to pop from an empty `priority_queue`. [2](#0-1) 

### Finding Description
The container maintains two independent structures: `priority_queue: BTreeSet<TransactionPriorityId>` (used for scheduling/eviction) and `id_to_transaction_state: Slab<TransactionState<Tx>>` (the map, sized `capacity + EXTRA_CAPACITY`). [3](#0-2)  `hold_transaction` is documented as "Hold the transaction until the next flush (next slot)" and simply appends the id to a `Vec` (`held_transactions`), leaving the map entry intact but not touching `priority_queue`: [4](#0-3) [5](#0-4) 

`push_ids_into_queue` computes `num_dropped` from `id_to_transaction_state.len().saturating_sub(self.capacity)` (i.e., using the map size, which includes held+queued+pending entries), then evicts that many entries by calling `self.priority_queue.pop_first().expect("queue is not empty")` — i.e. it assumes there are always at least `num_dropped` entries physically present in the queue to satisfy the "map size minus capacity" deficit: [1](#0-0) 

This invariant silently depends on held transactions never becoming a large fraction of the map while the queue is comparatively empty. Reachable attacker path: a remote unstaked client submits transactions via the TPU that reach `receive_and_buffer.rs`, get inserted with `insert_map_only` + `push_ids_into_queue`, and are scheduled/consumed by `ConsumeWorker`. If a worker's batch commit hits the `all_or_nothing`/`remaining_batch_error` cancellation path in `Consumer::execute_and_commit_transactions_locked`, the transaction at `failed_index` (the one that actually caused the cost-limit failure) is marked `immediately_retryable: false` by `cancel_processed_transactions_for_retry`, while other canceled transactions in the same batch get `immediately_retryable: true`: [6](#0-5) 

That result flows back through `SchedulingCommon::try_receive_completed`, which calls `container.retry_transaction(id, transaction, immediately_retryable)`, routing `immediately_retryable=false` transactions to `hold_transaction` instead of `push_ids_into_queue`: [7](#0-6) [8](#0-7) 

An attacker who repeatedly engineers batches so their transaction is the one that trips the per-batch/per-account cost limit (deterministic: the attacker fully controls the compute-unit cost and can size transactions to be "the straw that breaks the cost limit" in a batch) causes many of their own transactions to accumulate in `held_transactions` across scheduling passes, each still occupying a slot in `id_to_transaction_state`. Because `flush_held_transactions` only runs once per slot boundary (called from the controller, not on every insertion), held count can grow across multiple insert/schedule cycles within a slot while `priority_queue` remains comparatively small. When the map nears `capacity + EXTRA_CAPACITY`, the `assert!` in `get_vacant_map_entry` still permits insertion of a new/legitimate transaction (since it only checks map length against slab capacity), but the following `push_ids_into_queue` call computes a `num_dropped` based on total map length that can exceed the number of entries actually present in `priority_queue` (because a large chunk of the map is held, not queued). This causes `pop_first().expect("queue is not empty")` to panic once the queue is exhausted before satisfying `num_dropped`, or — before that extreme is reached — causes freshly-inserted, possibly high-priority transactions sharing the same push batch to be evicted alongside/instead of the stale held transactions, since held transactions are structurally exempt from this eviction path.

### Impact Explanation
This matches "QoS evasion" / fairness violation and, in the worst case (queue empty at eviction time while map deficit > 0), an `expect` panic causing a node crash/DoS — a concrete node-panic condition reachable by an unstaked remote attacker via ordinary transaction submission and no privileged access, satisfying the requirement for a real reachable defect rather than best-practice cleanup. Short of the panic, the effect is throughput degradation/unfair eviction of legitimate high-priority transactions, which is explicitly the scoped, bounded impact called out in the question (not an invalid block on its own).

### Likelihood Explanation
Preconditions: attacker must be able to reliably become the `failed_index` transaction in a cost-limit-exceeding batch, which requires knowledge of current cost-tracker state and batch composition timing — feasible for a sophisticated but still unstaked/unprivileged attacker sending crafted, high-compute-unit transactions to a leader's TPU, but requires careful timing/tuning (batch size is `TARGET_NUM_TRANSACTIONS_PER_BATCH = 64`) and repeated attempts across slots to accumulate enough held entries relative to `capacity` (buffer capacity is large, e.g., configured via `TOTAL_BUFFERED_PACKETS`), making it non-trivial but not requiring any staked/privileged capability. Repeatability is bounded by the once-per-slot `flush_held_transactions` call and cost-tracker reset each slot, which somewhat limits accumulation speed but does not eliminate the structural mismatch between map-based capacity accounting and queue-based eviction.

### Recommendation
Account for `held_transactions.len()` when computing `num_dropped` in `push_ids_into_queue` (i.e., base the eviction target on `priority_queue.len()` headroom, or eagerly evict from `held_transactions` too when the map is over capacity), and replace the `expect("queue is not empty")` with either a bounded loop that also drains `held_transactions` or a graceful degrade (drop excess held entries) instead of panicking. Ensure `flush_held_transactions` (or an equivalent periodic budget check) enforces that `held_transactions.len() + priority_queue.len() <= capacity` independent of scheduling cadence.

### Proof of Concept
Add a unit test in `transaction_state_container.rs`'s test module:
```rust
#[test]
fn test_held_transactions_starve_queue_capacity() {
    let capacity = 4;
    let mut container = TransactionStateContainer::with_capacity(capacity);

    // Fill container to capacity via normal inserts (all queued).
    push_to_container(&mut container, capacity); // helper already used elsewhere in this file

    // Pop all of them out of the priority_queue and mark them held,
    // simulating repeated cost-limit-exceeded batches with immediately_retryable=false.
    let mut held = Vec::new();
    while let Some(pid) = container.pop() {
        held.push(pid);
    }
    for pid in held {
        container.hold_transaction(pid);
    }
    // Invariant check: map is at capacity, but priority_queue is now empty.
    assert_eq!(container.buffer_size(), capacity);
    assert_eq!(container.queue_size(), 0);

    // Insert one new, fresh high-priority transaction -- this should not panic,
    // and eviction should never attempt to pop from an empty priority_queue
    // while the map has been artificially inflated by held-but-invisible entries.
    let (transaction, max_age, priority, cost) = test_transaction(u64::MAX);
    // insert_new_transaction internally calls insert_map_only + push_ids_into_queue,
    // reproducing the get_vacant_map_entry assert + pop_first().expect(...) panic path.
    let dropped = container.insert_new_transaction(transaction, max_age, priority, cost);

    // Expected (fixed) behavior: either the held transaction is displaced to make room,
    // or the new high-priority transaction is accepted without panicking and without
    // evicting itself; system-wide, eviction should never remove a higher-priority
    // entry while lower-priority held entries remain un-evicted.
    assert!(!dropped, "freshly inserted highest-priority transaction should not be dropped");
}
```
Expected current (buggy) behavior: this test panics inside `push_ids_into_queue` at `self.priority_queue.pop_first().expect("queue is not empty")`, or, if `capacity` is tuned so `num_dropped` accounting drops the fresh transaction instead of the held stale ones, `dropped` is asserted `true` incorrectly. A fuzz/invariant harness can generalize this by interleaving `hold_transaction`, `flush_held_transactions`, and `push_ids_into_queue(std::iter::once(...))` calls with randomized priorities and asserting that after every eviction, the removed entries are always the globally lowest-priority entries across held+queued state, not merely lowest within the current `priority_queue`.

    fn push_ids_into_queue(
        &mut self,
        priority_ids: impl Iterator<Item = TransactionPriorityId>,
    ) -> usize {
        for id in priority_ids {
            self.priority_queue.insert(id);
        }

        // The number of items in the `id_to_transaction_state` map is
        // greater than or equal to the number of elements in the queue.
        // To avoid the map going over capacity, we use the length of the
        // map here instead of the queue.
        let num_dropped = self
            .id_to_transaction_state
            .len()
            .saturating_sub(self.capacity);

        for _ in 0..num_dropped {
            let priority_id = self.priority_queue.pop_first().expect("queue is not empty");
            self.remove_state(priority_id.id);
        }

        num_dropped
    }

    fn cancel_processed_transactions_for_retry<Tx: TransactionWithMeta>(
        transactions: &[Tx],
        processing_results: &mut [TransactionProcessingResult],
        processed_counts: &mut ProcessedTransactionCounts,
        error_counters: &mut TransactionErrorMetrics,
        retryable_transaction_indexes: &mut Vec<RetryableIndex>,
        failed_index: usize,
        transaction_error: &TransactionError,
        start_index: usize,
    ) {
        for (index, (tx, processing_result)) in transactions
            .iter()
            .zip(processing_results.iter_mut())
            .enumerate()
            .skip(start_index)
        {
            if processing_result.was_processed() {
                Self::decrement_processed_counts(tx, processing_result, processed_counts);
                let retry_error = if index == failed_index {
                    transaction_error.clone()
                } else {
                    TransactionError::CommitCancelled
                };
                Self::accumulate_post_execution_transaction_error(
                    processing_result,
                    &retry_error,
                    error_counters,
                );
                *processing_result = Err(retry_error);
                retryable_transaction_indexes.push(RetryableIndex {
                    index,
                    // The cost-limit failure should be held until a later retry opportunity.
                    // Transactions canceled behind it did not fail cost are immediately retryable..
                    immediately_retryable: index != failed_index,
                });
            }
        }
    }
