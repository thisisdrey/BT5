### Title
StackerDB chunk signature does not bind the smart-contract identifier, enabling cross-database replay of validly-signed chunks - ([File: stackslib/src/net/stackerdb/db.rs], [File: libstackerdb/src/libstackerdb.rs])

### Summary
The `SlotMetadata` signature that authenticates a StackerDB chunk commits only to `(slot_id, slot_version, data_hash)` and never to the target smart contract (`QualifiedContractIdentifier`) the chunk is being written to. This is the same class of bug as the reported issue: the signed payload is under-specified (it omits a "denomination"/context field), so a value that is valid in one context can be misinterpreted as valid in another.

### Finding Description
`SlotMetadata::auth_digest` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

This digest is what gets signed (`SlotMetadata::sign`) and what gets checked (`SlotMetadata::verify`), which recovers a pubkey hash and compares it to the expected principal: [2](#0-1) 

The contract binding is enforced only indirectly: the caller (`try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs`) looks up the expected signer *for that specific contract and slot* via `get_slot_validation`, then calls `slot_desc.verify(&slot_validation.signer)`: [3](#0-2) 

Because the signature itself never encodes which contract it was made for, if the same signer address `A` is registered as the owner of `slot_id = S` in two different StackerDB contracts (e.g., two different reward-cycle `.signers-N-M` instances, or any two StackerDB replicas that happen to allocate the same slot index to the same address — which is the normal, expected case across reward cycles with overlapping signer sets, since slot indices are assigned deterministically from list position), then a chunk `(slot_id, slot_version, sig, data)` that was validly signed and accepted into contract X can be replayed byte-for-byte into contract Y, as long as Y also expects a chunk with the same `slot_id`/`slot_version` from `A` at some point. The same equality check (`verify(&addr)`) will pass in both places because it never distinguishes *which* StackerDB the signature was meant for.

`validate_received_chunk` (used both for chunks pulled during sync and for unsolicited pushed chunks) exhibits the identical gap — it fetches the expected signer scoped to `smart_contract_id`, but the signature check performed via `slot_metadata.verify(&addr)` still only checks the contract-agnostic digest: [4](#0-3) 

The unit tests confirm the digest's exact coverage — mutating `slot_id`, `slot_version`, or `data_hash` breaks verification, but there is no equivalent test or code path covering the contract/database identity, because that context is never part of what's signed: [5](#0-4) 

### Impact Explanation
An unprivileged network peer that has observed a validly-signed chunk broadcast on one StackerDB instance (e.g., `.signers-1-1`) can relay/replay that exact chunk into a different StackerDB instance (e.g., `.signers-2-1`) that happens to assign the same `slot_id` to the same signer address, whenever the receiving contract is waiting for a chunk at a version equal to or below the replayed one. This is an unauthenticated/unauthorized write of forged-in-context data: the receiving node will accept and store/propagate a chunk that was never actually produced or intended for that database, purely because the signature format collapses two distinct authorization contexts into one equality check. This matches the "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" impact class.

### Likelihood Explanation
Slot allocation for signer/miner StackerDB contracts is deterministic from ordered lists (e.g., reward-set index), so it is common — not a rare coincidence — for the same signer address to hold the same `slot_id` across adjacent reward-cycle contracts or across the miners/signers contracts sharing index-based slot layouts. Any relaying peer that has already legitimately received the chunk (which is by design broadcast/gossip data, not secret) can attempt the replay without needing any private key. The main constraint is that `slot_version` and `expected_versions`/staleness checks at the destination must line up, which is plausible on a freshly (re)configured or lagging replica.

### Recommendation
Include the target `smart_contract_id` (or a stable numeric database ID) as part of the signed digest in `SlotMetadata::auth_digest`, e.g. `hash(smart_contract_id || slot_id || slot_version || data_hash)`, and thread the contract identifier through `sign`/`verify` call sites (`StackerDBChunkData::sign/verify`, `try_replace_chunk`, `validate_received_chunk`). This mirrors the report's fix of adding the missing "denomination" field to the leaf so a value can't be validly reinterpreted outside its intended context.

### Proof of Concept
1. Signer `A` is slot owner of `slot_id = 3` in `.signers-1-1` and also slot owner of `slot_id = 3` in `.signers-2-1` (common due to deterministic index-based slot assignment across reward cycles with overlapping signer sets).
2. `A` legitimately signs and pushes chunk `C = (slot_id=3, slot_version=5, data=D)` to `.signers-1-1`; `sig` is computed only over `(3, 5, hash(D))` per `SlotMetadata::auth_digest`.
3. An observing peer captures this `StackerDBChunkData`/`StackerDBPushChunkData` message from the network.
4. The peer resends the identical `(slot_id=3, slot_version, sig, data=D)` payload, addressed to `.signers-2-1`, to a node still expecting version ≤5 for slot 3 from `A`.
5. `try_replace_chunk`/`validate_received_chunk` for `.signers-2-1` fetches `A` as the expected signer for slot 3 in that contract and calls `slot_desc.verify(&A)`, which succeeds because the digest never referenced the contract — the forged-context chunk is accepted and stored/relayed as if it were legitimately produced for `.signers-2-1`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
