Confirmed: no constant-time comparison utility (`subtle` crate or similar) exists anywhere in the codebase, and all six privileged RPC handlers use the identical vulnerable pattern `auth_header != password`.### Title
Non-constant-time comparison of the privileged `authorization` bearer token enables remote timing side-channel to brute-force `connection_options.auth_token` - (File: stackslib/src/net/api/postblock_v3.rs)

### Summary
Six privileged Stacks-node RPC endpoints gate access behind a single shared secret (`connection_options.auth_token`) that is checked with a plain Rust `String` inequality comparison (`auth_header != password`) rather than a constant-time comparison. Because this comparison short-circuits on the first mismatching byte, an unauthenticated remote attacker can use response-time measurements to recover the secret byte-by-byte, ultimately forging the `authorization` header and unlocking write/administrative capability that is otherwise gated on possession of the token — conceptually the same "guessable/derivable credential accepted at a public endpoint" failure class as the reported Vercel Workflow issue (predictable webhook token accepted as a credential).

### Finding Description
`connection_options.auth_token` is a single pre-shared string that authenticates privileged HTTP RPC requests. It is checked identically in six handlers, all in `stackslib/src/net/api/**`:

- `postblock_v3.rs` (`/v2/blocks?broadcast=1`) [1](#0-0) 
- `postblock_proposal.rs` (`/v3/block_proposal`) [2](#0-1) 
- `blockreplay.rs` (`/v3/blocks/replay/:id`) [3](#0-2) 
- `blocksimulate.rs` (`/v3/blocks/simulate/:id`) [4](#0-3) 
- `fastcallreadonly.rs` (`/v3/contracts/fast-call-read/...`) [5](#0-4) 
- `txsimulate.rs` (`/v3/transactions/simulate`) [6](#0-5) 

Each performs:
```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```
`String`/`str` equality in Rust compares byte-by-byte and returns as soon as a mismatch is found (it does not process the whole buffer in constant time). This is the classic precondition for a remote timing side-channel against a shared secret. A search of the whole repository confirms there is no constant-time comparison utility (`subtle` crate or hand-rolled constant-time compare) used anywhere for `auth_token`, and this exact vulnerable pattern (`auth_header != password`) is repeated in all 6 files with no additional mitigation such as HMAC-based comparison, `subtle::ConstantTimeEq`, or a minimum-delay/rate-limited retry policy in front of the check.

This is directly analogous to the reported bug class: instead of a webhook accepting a *predictable, user-chosen* token as a durable credential, this codebase accepts a *fixed shared secret* but validates it in a way that leaks enough information (via timing) to let a remote, unauthenticated attacker reconstruct the credential — breaking the same equality invariant ("attacker-supplied value == stored secret") the advisory is about, just via a side-channel instead of predictable value guessing.

### Impact Explanation
`auth_token` gates non-trivial capabilities:
- `/v3/block_proposal` and `/v3/blocks/replay`, `/v3/blocks/simulate`, `/v3/transactions/simulate`, and fast-call-read-only trigger chainstate validation/simulation compute on attacker-supplied block/transaction data [7](#0-6) .
- `/v2/blocks?broadcast=1` authenticates the requester to force broadcast of a submitted block onto the network [8](#0-7) .
- The signer/miner documentation explicitly states this token "secures the communication channel between this node and a connected `stacks-signer` instance" and is required for the miner–signer block-proposal workflow, i.e. its compromise undermines the intended coordination trust boundary [9](#0-8) .

If an attacker recovers the token via timing analysis, they gain unauthenticated write access to (or forced broadcast through) endpoints that are supposed to require operator-level trust — an auth-bypass outcome, matching the Critical/High impact buckets in scope ("unauthenticated/unauthorized write to state," "auth bypass").

### Likelihood Explanation
This is a genuine root-cause defect (non-constant-time secret comparison, confirmed with no mitigating constant-time logic anywhere in the codebase), but real-world exploitability depends on network jitter versus the signal from a single-byte-early-return in a `memcmp`-style comparison. Over the public Internet this typically requires substantial statistical averaging (many thousands of requests) to extract a usable timing signal per byte, and there is no visible rate limiting on these specific handlers to slow such probing (confirmed no `429`/rate-limit logic in the relevant files). This raises likelihood somewhat but the practical difficulty of a network-based timing attack (as opposed to same-host/low-latency conditions) keeps it below a trivial/"obvious" severity; it is a well-established technique (e.g., against API keys/HMAC checks) but non-trivial to mount reliably.

### Recommendation
Replace the direct `!=` string comparisons in all six handlers with a constant-time comparison (e.g., using the `subtle` crate's `ConstantTimeEq`, or by first hashing both sides with a keyed MAC and comparing digests in constant time). Apply this uniformly across `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `postblock_proposal.rs`, `postblock_v3.rs`, and `txsimulate.rs`, ideally by factoring the check into one shared helper in `stackslib/src/net/httpcore.rs` or `stackslib/src/net/api/mod.rs` to avoid future drift. Additionally consider adding a minimum-delay/backoff on repeated `401` responses for these endpoints to blunt any residual signal.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "S3CR3T-TOKEN"` and expose `/v3/block_proposal` (or any of the other five endpoints).
2. From a remote unauthenticated client, repeatedly send POST requests with an `authorization` header value that is correct for an increasing number of leading bytes (e.g., start with `"A"`, then `"S"`, then `"S3"`, …), each time timing the round-trip to the `if auth_header != password` check inside `try_parse_request` (e.g., `postblock_v3.rs` lines 104–111 [1](#0-0) ).
3. Because the comparison exits at the first mismatching byte, headers whose prefix matches more of the real secret take measurably (if noisy) longer to reject than those that mismatch immediately; averaging many samples per candidate byte allows incrementally recovering `auth_token` character-by-character without ever needing to see the node's configuration file.
4. Once `auth_token` is fully recovered, the attacker can submit an `authorization: <token>` header on any of the six protected endpoints to obtain the unauthenticated capabilities described above (e.g., force `/v2/blocks?broadcast=1` to accept/broadcast attacker blocks).
