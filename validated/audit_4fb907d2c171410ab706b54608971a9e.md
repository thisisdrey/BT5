### Title
HTTP request framing ignores `Transfer-Encoding`, enabling CL/TE request smuggling against the Stacks RPC server - (File: stackslib/src/net/http/request.rs)

### Summary
`HttpRequestPreamble::consensus_deserialize` frames every incoming HTTP request purely by the `Content-Length` header and never inspects or rejects a `Transfer-Encoding` header. This is the same bug class as GHSA-hw6f-rjfj-j7j7 (eventlet request smuggling via improper trailer/framing handling): a request-line/headers parser that lets `Content-Length` and `Transfer-Encoding` disagree, or silently ignores `Transfer-Encoding`, creates a CL/TE desync opportunity against anything in front of the node (a reverse proxy, load balancer, or another Stacks node acting as a relay) that honors `Transfer-Encoding` per RFC 7230.

### Finding Description
`HttpRequestPreamble::consensus_deserialize` explicitly parses and validates `host`, `content-type`, `content-length`, `connection`, and `set-cookie` headers, but any `transfer-encoding` header falls through to the generic headers map with no special handling: [1](#0-0) 

Unlike the response parser, which explicitly rejects the combination of `Content-Length` and chunked `Transfer-Encoding` as an error: [2](#0-1) 

the request parser has no equivalent equality check. Framing for requests is then derived solely from `Content-Length`: [3](#0-2) 

If an attacker sends a request with both `Content-Length: N` and `Transfer-Encoding: chunked` to a party that sits in front of the Stacks node (a reverse proxy/load balancer that is TE-aware, or any HTTP intermediary that prioritizes `Transfer-Encoding` per spec), that intermediary may forward only the chunk-decoded body, while the Stacks node — which never looks at `Transfer-Encoding` at all — will instead read exactly `Content-Length` bytes as the body from the raw (still chunk-encoded) stream. Any leftover bytes (the chunk terminator, or attacker-crafted bytes appended after it) are left in the connection buffer and get parsed by the node as the start of the *next* pipelined HTTP request. This breaks the equality "bytes of the intended request == bytes the node consumes for that request," letting an attacker's trailing bytes be interpreted as a new request on a shared connection — the definition of HTTP request smuggling.

### Impact Explanation
This is a request-smuggling / desync primitive on the node's public JSON-RPC HTTP surface. Depending on deployment topology (e.g., a load balancer or CDN terminating/multiplexing client connections in front of the Stacks RPC endpoint), this can let an attacker's smuggled request be attributed to or interleaved with another client's connection, potentially bypassing IP-based/proxy-enforced access controls on sensitive RPC endpoints, poisoning any caching layer in front of the node, or hijacking pipelined responses meant for another user of the shared backend connection. This matches the "request smuggling or auth bypass" Critical-tier impact category in scope.

### Likelihood Explanation
The request is fully remote and unauthenticated — a single crafted HTTP request with conflicting `Content-Length`/`Transfer-Encoding` headers is sufficient to trigger the desync; no signer, admin, or node-secret access is needed. Actual exploitability depends on the presence and behavior of an intermediary between the client and the Stacks node (common in production deployments using reverse proxies/load balancers in front of RPC nodes), which is why this is rated as a request-smuggling primitive rather than a guaranteed direct compromise from the node alone.

### Recommendation
In `HttpRequestPreamble::consensus_deserialize` (`stackslib/src/net/http/request.rs`), explicitly detect a `Transfer-Encoding` header the same way `HttpResponsePreamble::consensus_deserialize` does, and reject the request (e.g., with `CodecError::DeserializeError`) if `Transfer-Encoding` is present at all, or specifically if it is present together with `Content-Length`. This closes the CL/TE ambiguity at the parser boundary, matching the eventlet patch's approach of refusing to allow ambiguous framing metadata to pass through unexamined.

### Proof of Concept
Send the following over a raw TCP connection to a proxy/gateway placed in front of a Stacks RPC node that honors `Transfer-Encoding` (per RFC 7230 §3.3.3, TE takes precedence over CL):
```
POST /v2/transactions HTTP/1.1
Host: victim-node:20443
Content-Type: application/octet-stream
Content-Length: 6
Transfer-Encoding: chunked

0

GET /v2/admin-only-or-victim-path HTTP/1.1
Host: victim-node:20443
...
```
A TE-aware front end forwards only the zero-length chunk body (empty request), while the Stacks node — which ignores `Transfer-Encoding` and reads exactly `Content-Length: 6` bytes ("0\r\n\r\n") as the body per `read_payload` at `stackslib/src/net/httpcore.rs:1716-1730` — leaves the smuggled `GET /v2/admin-only-or-victim-path ...` bytes in the stream to be parsed as an independent, subsequent request on the same connection.
