Based on the evidence gathered, the strongest local analog to the `BaseVaultAdaptor.calculateShare` bug (a hard-coded decimals/conversion assumption without a live consistency check) is in `pallet-psm`'s `mint`/`redeem` pair, where the decimals-drift guard is present in one path but missing in the other.

### Title
`redeem` skips the live-decimals drift check that `mint` enforces, allowing conversion at a stale decimals ratio — ([File: substrate/frame/psm/src/lib.rs])

### Summary
`pallet-psm` normalizes external-asset amounts to internal (pUSD) units using a decimals snapshot taken at registration (`AssetDecimals`/`StableDecimals`), and is documented to guard against "runtime drift": if live asset metadata decimals diverge from the registration snapshot, `mint`/`redeem` should return `DecimalsMismatch` and halt that asset until governance intervenes. [1](#0-0) 
In the actual implementation, `mint` explicitly calls `Self::ensure_decimals_match` before doing any conversion: [2](#0-1) 
but `redeem` never calls this guard — it reads the decimals straight out of the stored snapshot (`external.decimals`, `info.internal_decimals`) and proceeds directly to conversion: [3](#0-2) 

### Finding Description
The bug class in the external report is: a share/amount conversion function assumes a fixed decimals relationship instead of validating it against the live, protocol-reported precision, so if that precision actually differs (or later changes), the conversion silently produces the wrong number of shares/tokens.

`pallet-psm` mirrors this exact failure mode asymmetrically between its two conversion entry points:
- `mint` calls `Self::ensure_decimals_match(&info, &internal_asset, &external_asset, &external)` at [4](#0-3)  to confirm the live `T::Fungibles::decimals(...)` for both assets still equal the values snapshotted at `register_external_asset`/`create_psm` time, only then calling `external_to_internal`/`internal_to_external`.
- `redeem` instead does:
```
let ext_decimals = external.decimals;
let internal_decimals = info.internal_decimals;
``` [5](#0-4) 
and feeds these directly into `internal_to_external`/`external_to_internal` [6](#0-5) 
without ever calling the drift-detection helper. `ExternalAssets` and `Psm` only store the snapshot values (`external.decimals`, `info.internal_decimals`) — they are never refreshed automatically [7](#0-6) , so once the live decimals of either the internal or an approved external asset diverge from what was snapshotted, `mint` correctly halts with `DecimalsMismatch`, but `redeem` keeps computing `external_out`/`effective_internal_net` using the now-incorrect (stale) scaling factor from `pow10(diff)`.

### Impact Explanation
If the true decimals of an approved external asset (or the internal asset) drift after PSM registration — a legitimate, unprivileged-observable state since asset metadata is a property of the underlying asset pallet, not the PSM's own admin, and the prdoc explicitly anticipates such drift as a normal operational hazard requiring a halt — `redeem` will continue applying the stale `pow10` scale factor. This corrupts the exact value the vault-adaptor bug corrupted: the computed `share`/`amount` conversion. Depending on the direction of drift, this either lets any redeeming user extract more external collateral from the reserve than their burned internal amount is actually worth (fund loss from the PSM reserve, i.e., theft of other users'/protocol collateral), or it forces under-payment while `PsmDebt` bookkeeping is decremented by the wrong `effective_internal_net`, breaking the pallet's own documented value-conservation invariant between `mint` and `redeem` for mixed-decimal assets. This is exactly the "value must conserve and settle exactly once to the rightful beneficiary and amount" pivot called out for staking/treasury/asset-accounting paths.

### Likelihood Explanation
The trigger condition (decimals metadata drift for an already-approved external asset) is plausible without any malicious PSM governance action: it can occur through normal reconfiguration of the underlying asset (e.g., a metadata correction on `pallet-assets`, or `T::Fungibles::decimals` returning a different value for a foreign/derivative asset whose backing metadata is not controlled by the PSM admin at all). The public `redeem` extrinsic is callable by any signed account, so any user can trigger the vulnerable path once drift exists — no privileged actor, relayer, or validator collusion is required. The severity is bounded only by the drift's decimal-order-of-magnitude and can be large (a difference of even one decimal place multiplies/divides amounts by 10).

I could not fully verify the internals of `ensure_decimals_match` itself within the available inspection budget, but its call site pattern (present only in `mint`, absent in `redeem`) is directly confirmed from the code shown above.

### Recommendation
Call `Self::ensure_decimals_match(&info, &internal_asset, &external_asset, &external)` at the start of `redeem` exactly as `mint` does, before deriving `ext_decimals`/`internal_decimals`, so that a drifted asset halts symmetrically on both mint and redeem paths until governance re-registers/updates the snapshot.

### Proof of Concept
1. Register an external asset `X` with live decimals = 6, causing `ExternalAssets` to snapshot `external.decimals = 6` and `Psm::internal_decimals = 6`.
2. Have the asset's own metadata authority (independent of PSM admin) change `X`'s live decimals to 18 via the underlying assets pallet (a normal operation outside PSM's control).
3. Call `mint` with asset `X` — `ensure_decimals_match` detects the live/snapshot mismatch and returns `Error::DecimalsMismatch`, correctly halting.
4. Call `redeem` with asset `X` — no such check runs; `internal_to_external` uses the stale snapshot decimals (6) to compute `external_out`, producing an output amount off by `10^12` relative to what the now-18-decimal `X` actually represents, while `PsmDebt`/reserve accounting is updated using this wrong figure, draining or misallocating the PSM's `X` reserve.

		pub(crate) fn external_to_internal(
			amount: BalanceOf<T>,
			ext_decimals: u8,
			internal_decimals: u8,
		) -> Result<BalanceOf<T>, Error<T>> {
			use core::cmp::Ordering::*;
			match ext_decimals.cmp(&internal_decimals) {
				Equal => Ok(amount),
				Less => {
					let diff = (internal_decimals - ext_decimals) as u32;
					let factor = Self::pow10(diff)?;
					amount.checked_mul(&factor).ok_or(Error::<T>::ConversionOverflow)
				},
				Greater => {
					let diff = (ext_decimals - internal_decimals) as u32;
					let factor = Self::pow10(diff)?;
					Ok(amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero))
				},
			}
		}
