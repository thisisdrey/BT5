### Title
Unauthenticated collateral-slot dusting can block position recovery - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces a shared limit of 30 debt-token and deposit-token positions per account. Because anyone can mint a positive `DepositToken` balance to an arbitrary recipient, an attacker can occupy the victim’s final available slot with dust. Once the combined per-account lists reach `MAX_TOKENS_PER_USER`, every operation that would add another deposit token reverts. For an unhealthy account, the dusted position may also be completely locked, preventing the victim from clearing the slot before liquidation.

### Finding Description
`Pool.addToDepositTokensOfAccount` rejects additions when the sum of the account’s debt-token and deposit-token lists is at least 30. [1](#0-0) [2](#0-1) 

`DepositToken.deposit` accepts an arbitrary `onBehalfOf_` address and mints the resulting deposit-token balance to that address. [3](#0-2) [4](#0-3) 

During `_mint`, the first positive balance invokes `pool.addToDepositTokensOfAccount(account_)`; if the account is already at the cap, the whole deposit reverts. [5](#0-4) 

The same insertion happens on an ERC20-style transfer when the recipient previously had zero balance, so the attacker can alternatively transfer dust to occupy a slot without paying deposit fees. [6](#0-5) 

For an unhealthy account, `unlockedBalanceOf` returns zero because `debtPositionOf` reports no remaining issuable capacity. [7](#0-6)  Both `transfer` and `withdraw` require the requested amount to be unlocked, so the victim cannot remove even the dusted collateral position while unhealthy. [8](#0-7) [9](#0-8) 

### Impact Explanation
An attacker can front-run a victim’s attempt to add a new collateral type and permanently occupy the last account slot. If the victim’s position is unhealthy and the attack fills the final slot, the victim cannot transfer or withdraw the dusted token to clear it. The victim remains able to increase an already-listed collateral type, but any rescue strategy requiring a new collateral type is unavailable.

This can preserve an otherwise recoverable position for liquidation. A liquidator can then repay the allowed portion of the victim’s debt and seize collateral through `Pool.liquidate`, including the liquidator incentive. [10](#0-9)  The result is attacker-facilitated loss of collateral and temporary freezing of the victim’s ability to onboard collateral while the slot remains occupied.

### Likelihood Explanation
The attack requires the victim to have 29 combined debt-token and deposit-token entries and requires an additional whitelisted deposit token that the victim does not already hold. The attacker must obtain a positive, transferable amount of that token, but only one minimal unit is needed because list insertion depends on a transition from zero to positive balance, not value.

The conditions are feasible in pools close to the 30-token limit. No privileged role, oracle failure, malicious bridge endpoint, or compromised contract is required. `deposit` is public, `onBehalfOf_` is attacker-controlled, and `Pool.liquidate` is publicly callable once the victim is unhealthy. [11](#0-10) [12](#0-11) 

### Recommendation
Prevent unsolicited collateral from consuming a victim’s limited account slots. Suitable mitigations include:

- Remove the per-account token cap or replace it with bounded accounting.
- Track deposit collateral only after an explicit account opt-in.
- Allow an account to remove a zero-value or dust position even while unhealthy.
- Exclude positions below a configured USD or token threshold from `depositTokensOfAccount`.
- Allow liquidation proceeds or repayments to remove the attacker-donated position without requiring it to be unlocked.

// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {IDepositToken} from "../../contracts/interfaces/IDepositToken.sol";
import {IPool} from "../../contracts/interfaces/IPool.sol";
import {IERC20} from "../../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract DepositSlotDustingTest is Test {
    IPool internal pool;
    IDepositToken internal existingCollateral;
    IDepositToken internal newCollateral;

    address internal victim;
    address internal attacker;

    function testDustBlocksNewCollateral() public {
        // Arrange a victim with 29 combined debt/deposit-token entries
        // and an unhealthy position in a forked deployment fixture.
        assertEq(
            pool.getDebtTokensOfAccount(victim).length +
                pool.getDepositTokensOfAccount(victim).length,
            29
        );
        assertFalse(pool.debtPositionOf(victim));

        IERC20 underlying = newCollateral.underlying();
        deal(address(underlying), attacker, 1 ether);

        vm.startPrank(attacker);
        underlying.approve(address(newCollateral), 1 ether);

        // Any amount that mints a positive DepositToken balance is enough.
        // deposit(..., victim) is equivalent to transferring a dust balance.
        (uint256 deposited,) = newCollateral.deposit(1, victim);
        assertGt(deposited, 0);
        vm.stopPrank();

        assertEq(
            pool.getDebtTokensOfAccount(victim).length +
                pool.getDepositTokensOfAccount(victim).length,
            30
        );

        // The victim cannot clear the dusted slot while unhealthy because the
        // entire dust balance is treated as locked collateral.
        vm.prank(victim);
        vm.expectRevert(bytes4(keccak256("NotEnoughFreeBalance()")));
        newCollateral.transfer(attacker, deposited);

        // A subsequent deposit of any whitelisted DepositToken not already in
        // the victim's list reverts while registering the recipient position.
        vm.prank(attacker);
        vm.expectRevert(bytes4(keccak256("UserReachedMaxTokens()")));
        newCollateral.deposit(1, victim);
    }
}
