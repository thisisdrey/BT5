### Title
`ExchangeWithdrawContract` withdraws TRC10 exchange (Bancor pool) liquidity with no slippage/minimum-output protection - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeWithdrawContract`/`ExchangeWithdrawActuator` lets an exchange creator withdraw one side of a TRC10 Bancor-style liquidity pool and computes the paired ("another") token amount purely from the pool ratio at execution time, with **no caller-supplied minimum-output field**. In contrast, its sibling `ExchangeTransactionContract`/`ExchangeTransactionActuator` explicitly added an `expected` field and a `token required must greater than expected` check for exactly this purpose. Because pool ratios can be shifted by any other account between transaction broadcast and execution (via `ExchangeInjectContract` or `ExchangeTransactionContract`), the withdraw executes at an unprotected, front-runnable price.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` [1](#0-0) . Compare this to `ExchangeTransactionContract`, which additionally carries an `expected` field used as a slippage bound [2](#0-1) .

In `ExchangeTransactionActuator.doValidate()`, the actuator computes the counter-amount via `exchangeCapsule.transaction(...)` and explicitly rejects the trade if the result is below the caller's `tokenExpected`: [3](#0-2) 

`ExchangeWithdrawActuator`, however, computes `anotherTokenQuant` from the *current* pool balances with no equivalent bound supplied by the caller: [4](#0-3) 

Its `doValidate()` only checks internal consistency (rounding "precision" checks and that balances are sufficient), never a caller-specified minimum acceptable amount of the paired token: [5](#0-4) 

Because the pool ratio (`firstTokenBalance`/`secondTokenBalance`) is shared, mutable state that any account can move by broadcasting `ExchangeInjectContract` (add liquidity) or `ExchangeTransactionContract` (trade) transactions before the withdraw transaction is packed into a block, a third party can shift the ratio between the time the withdraw transaction is signed/broadcast and the time it is executed. The withdraw actuator will then execute against the manipulated ratio and hand the creator whatever `anotherTokenQuant` results, with no way for the withdraw transaction to abort if that amount is worse than expected.

### Impact Explanation
This is the same class of bug as the external report: a withdraw operation that converts a share of a liquidity/exchange pool into a paired asset with no slippage protection, unlike the protocol's own analogous exchange-trade actuator which does provide one. An account waiting to withdraw can have the value of its own withdrawal degraded by front-running trades/injections from any other network participant, resulting in the withdrawing account receiving fewer paired tokens than the pool state implied when it signed the transaction. This is a concrete asset-value loss for the withdrawing account, reachable purely through ordinary signed transactions (`ExchangeInject`, `ExchangeTransaction`, `ExchangeWithdraw`) with no special privilege required — matching the medium-severity "bad slippage control" class from the source report.

### Likelihood Explanation
Any account can create an exchange (via `ExchangeCreateContract`) and later withdraw from it; any other account can call `ExchangeInjectContract`/`ExchangeTransactionContract` on the same exchange to shift the pool ratio. Since block-packing order is not guaranteed to match broadcast order, and the actuator applies the pool ratio at execution time rather than at signing time, exploitation only requires ordinary transaction submission with no elevated privileges — a straightforward front-running/sandwich pattern.

### Recommendation
Add a caller-supplied minimum-output field (analogous to `expected` in `ExchangeTransactionContract`) to `ExchangeWithdrawContract`, and validate in `ExchangeWithdrawActuator.doValidate()`/`execute()` that the computed `anotherTokenQuant` is not less than that minimum, mirroring the check already present in `ExchangeTransactionActuator` at [3](#0-2) .

### Proof of Concept
1. Account A creates a TRC10 exchange pool with tokens X/Y via `ExchangeCreateContract`.
2. Account A signs and broadcasts `ExchangeWithdrawContract` to withdraw some of token X (expecting a certain amount of token Y based on the current ratio), per `ExchangeWithdrawActuator.execute()` [6](#0-5) .
3. Before A's transaction is packed, Account B (unprivileged) broadcasts `ExchangeInjectContract` or `ExchangeTransactionContract` transactions against the same `exchange_id` to skew the X:Y ratio.
4. If B's transaction lands first in the same or an earlier block, A's withdraw executes against the skewed ratio and A receives a worse `anotherTokenQuant` of token Y than intended — with no `ExchangeWithdrawContract` field available to bound or reject this outcome, unlike the `expected` field guard present in `ExchangeTransactionActuator`.

Note: I was unable to run this scenario in a live network/test harness (no execution environment available); the finding is based on static comparison of the two actuator implementations and their protobuf contracts, which clearly shows the missing slippage-bound field/check in `ExchangeWithdrawContract`/`ExchangeWithdrawActuator` relative to `ExchangeTransactionContract`/`ExchangeTransactionActuator`.
