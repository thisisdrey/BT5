### Title
Legacy `ExchangeProcessor` silently overflows `Math.pow` computations, allowing incorrect (unbacked) token amounts in Bancor-style exchange trades - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The default (non-hardened) `ExchangeProcessor` used by `ExchangeCapsule.transaction()` computes exchange amounts with `double`-precision `Math.pow` calls that can silently overflow to `Infinity`/`NaN` or lose precision, then casts the result directly to `long`. This mirrors the reported `FixedPointMath.pow` bug class: an unchecked power computation that "silently overflows and yields wrong results," propagating an incorrect value into downstream balance accounting. Unlike the hardened `SafeExchangeProcessor`, the legacy path performs no overflow detection.

### Finding Description
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute: [1](#0-0) 

```
double issuedSupply = -supply * (1.0 - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, ...));
...
double exchangeBalance = balance * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, ...) - 1.0);
```

`Maths.pow` delegates to `StrictMath.pow`/`Math.pow` on raw `double` values, with no overflow or NaN check: [2](#0-1) 

For `exchangeFromSupply`, the exponent is a fixed `2000.0`. Because a `double` can only represent values up to ~1.8e308 (i.e. `2^1024`), any base `b` with `b^2000` exceeding that bound overflows silently to `Double.POSITIVE_INFINITY`. Since `2^2000` vastly exceeds `2^1024`, a base approaching `2.0` (i.e. `supplyQuant` approaching `supply`, meaning the caller withdraws a large fraction of the relay-token supply) causes `Math.pow` to return `Infinity`. `(long) Double.POSITIVE_INFINITY` in Java evaluates to `Long.MAX_VALUE`, so `exchangeBalance` becomes `balance * (Infinity - 1)` → `Infinity` → cast to `Long.MAX_VALUE`, an amount wildly disconnected from the actual exchange reserves.

This value flows back into `ExchangeCapsule.transaction`, which — in the **non-hardened** path — updates balances with plain `long` arithmetic (`secondTokenBalance - buyTokenQuant`) and performs **no non-negativity check**, unlike the hardened path which explicitly guards against this: [3](#0-2) 

The choice between the vulnerable legacy processor and the safe one is gated by the `allowHardenExchangeCalculation` dynamic parameter, checked in `AbstractExchangeActuator.allowHarden()`: [4](#0-3) 

and threaded through `ExchangeTransactionActuator.execute`/`doValidate`, which any unprivileged account can trigger by broadcasting an `ExchangeTransactionContract`: [5](#0-4) [6](#0-5) 

The project's own test suite acknowledges the risk difference between the hardened and legacy processors, explicitly demonstrating that the hardened path throws `ArithmeticException` on overflow while the legacy path does not guard against it: [7](#0-6) 

### Impact Explanation
If `allowHardenExchangeCalculation` is not enabled on a given network (it is an opt-in dynamic parameter set via proposal, not enabled by default), any account can place an `ExchangeTransactionContract` trade sized so that `supplyQuant/supply` approaches 1 (i.e., trading a large fraction of the relay-token supply back out). The `Math.pow(base, 2000.0)` call overflows to `Infinity`, the cast to `long` yields `Long.MAX_VALUE` (or another grossly wrong figure well beyond the actual pool reserves), and this amount is credited to the attacker's account balance/asset while the exchange's internal token balances are decremented via unchecked `long` subtraction (which can wrap negative or leave an inconsistent state). This allows unauthorized creation of unbacked TRX/TRC10 balance out of the exchange pool — a direct theft-of-funds / unbacked-balance condition reachable from a single signed transaction by an anonymous order placer.

### Likelihood Explanation
The vulnerable path (`ExchangeProcessor`, not `SafeExchangeProcessor`) is the default unless the `AllowHardenExchangeCalculation` proposal parameter has been activated on the chain. Reaching the overflow only requires an account able to place a valid `ExchangeTransactionContract` against an exchange pair with a sufficiently large relay-supply ratio — no special privileges, SR/witness status, or contract deployment are required, only a signed transaction meeting the (fairly loose) validate() checks in `ExchangeTransactionActuator`. This is analogous in kind to the original `FixedPointMath.pow` finding: a numeric-overflow bug reachable through ordinary user-facing operations.

### Recommendation
1. Make `SafeExchangeProcessor` (BigDecimal-based, with `StrictMathWrapper.addExact/subtractExact` and explicit non-negative balance checks) the mandatory/default computation path for all `Exchange*Actuator`s, rather than gating it behind an opt-in dynamic parameter.
2. In the legacy `ExchangeProcessor`, validate the `Math.pow` result for `Infinity`/`NaN` before casting to `long`, and reject the transaction (throw `ArithmeticException`/`ContractValidateException`) instead of silently truncating.
3. Enforce non-negative balance invariants in `ExchangeCapsule.transaction` regardless of `hardenedCalc`, so an under/overflowed quantity cannot corrupt the pool's `firstTokenBalance`/`secondTokenBalance`.

### Proof of Concept
1. Create an exchange pool with a small relay `supply` and modest reserves (as in `ExchangeCapsule.transaction`, `supply = 1_000_000_000_000_000_000L` initially, but a live pool can have a much smaller effective `supply` after prior trades reduce it).
2. As an unprivileged account, submit an `ExchangeTransactionContract` selling a token amount `sellTokenQuant` such that the resulting `relay` value (`supplyQuant`) fed into `exchangeFromSupply` satisfies `supplyQuant / supply` ≈ 1 (i.e., withdrawing close to the entire relay supply in one trade).
3. Inside `exchangeFromSupply`, `base = 1 + supplyQuant/supply` ≈ `2.0`; `Maths.pow(base, 2000.0, ...)` overflows the `double` range and returns `Infinity`.
4. `exchangeBalance = balance * (Infinity - 1.0)` = `Infinity`; `(long) Infinity` = `Long.MAX_VALUE`.
5. `ExchangeTransactionActuator.execute` credits the attacker with `anotherTokenQuant = Long.MAX_VALUE` (or another wildly incorrect figure) via `addAssetAmountV2`/`setBalance`, while `ExchangeCapsule.setBalance` decrements the pool's `secondTokenBalance` by the same bogus amount using unchecked `long` subtraction — producing an unbacked balance / exchange pool corruption, without the hardened non-negativity check that exists only when `allowHardenExchangeCalculation` is enabled (confirmed by `SafeExchangeProcessor.INSTANCE.exchange(Long.MAX_VALUE, 1_000_000L, 1L)` throwing `ArithmeticException` in `ExchangeProcessorTest.testHardenedOverflowDetection`, versus no such guard in the default `ExchangeProcessor`).

```java
  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
```

```java
  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
```
