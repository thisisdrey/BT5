### Title
Out-of-bounds array read (unchecked attacker-controlled offsets) in `PrecompiledContracts.extractBytesArray` / `extractSigArray` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The UPX report describes a heap-buffer-overflow in `PackTmt::pack()` caused by trusting an attacker-controlled length/offset field taken from a crafted input file without validating it against the actual buffer bounds before it is used to index/copy memory. The closest reachable analog in java-tron is the dynamic-array decoding helpers used by TVM precompiled contracts, `extractBytesArray` and `extractSigArray`, which decode ABI-style offset/length words taken directly from EVM calldata (fully attacker-controlled) and use them to index into the `words[]` array and to compute slice bounds for `Arrays.copyOfRange` without validating the derived index/length against the array size on every iteration. [1](#0-0) [2](#0-1) 

### Finding Description
`extractBytesArray(DataWord[] words, int offset, byte[] data)` only bounds-checks the initial `offset` argument (`offset > words.length - 1`) before the loop begins:

```java
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen);
    }
    return bytesArray;
}
``` [1](#0-0) 

`len` is fully attacker-controlled (derived from `DataWord.intValueSafe()`, which can be as large as `Integer.MAX_VALUE`) and is not validated against the actual size of `words[]` (which is derived from the caller-supplied calldata length). Once the loop starts, every iteration indexes `words[offset + i + 1]` with no re-validation, so a crafted `len`/`offset` combination causes the loop to read past the end of `words[]`, throwing an `ArrayIndexOutOfBoundsException`. The companion helper `extractSigArray` has the identical pattern, and `extractBytes` performs `Arrays.copyOfRange(data, offset, offset + len)` with an offset/length pair computed from these same unchecked values, which can also throw `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` for crafted inputs. [2](#0-1) 

This mirrors the UPX root cause structurally: a length header taken from untrusted input is trusted to drive further indexing/copies without validating it against the real bounds of the underlying buffer on every access, not just once at entry.

### Impact Explanation
`words[]` is built from the raw calldata bytes passed to whatever precompiled contract calls these helpers (this decoding pattern implements Solidity ABI dynamic `bytes[]`/signature-array decoding for precompiles such as batch-signature-validation contracts). Because the calldata originates from an ordinary contract call (any unprivileged account or contract can invoke a precompiled address with crafted input via a `CALL`/`STATICCALL`), an attacker can trigger an uncaught `ArrayIndexOutOfBoundsException` during precompiled-contract execution. Java's memory safety prevents true heap corruption (unlike the C/C++ UPX case), so the concrete effect is a runtime exception surfacing during TVM opcode execution, which is a reachable robustness/DoS condition on the execution path rather than a heap-overflow-style write. I was not able to fully trace whether this exception is caught generically at the `Program`/`Runtime` execution layer (turning it into a normal reverted transaction) or can propagate further; this should be verified before treating this as more than a per-transaction-scoped exception.

### Likelihood Explanation
Reaching this code only requires constructing a transaction/contract call whose calldata targets a precompiled contract that uses `extractBytesArray`/`extractSigArray`, with crafted dynamic-array length/offset words — no special privileges are required, since this is invocable by any transaction broadcaster or contract deployer that can trigger a `CALL` to the precompiled address.

### Recommendation
Add explicit per-iteration bounds checks in `extractBytesArray` and `extractSigArray` (verify `offset + i + 1 < words.length` and that computed `bytesOffset`/`bytesLen` stay within `data.length`) before indexing, matching the length-validation pattern already used elsewhere in the codebase (e.g. `RLP.verifyLength`) so malformed calldata is rejected deterministically instead of relying on an uncaught `ArrayIndexOutOfBoundsException`.

### Proof of Concept
Not independently executed; conceptually: invoke the precompiled contract that uses `extractBytesArray`/`extractSigArray` (a batch-signature-validation-style precompile) with calldata whose first-array-length word is set to a large value (e.g. `0xFFFFFFFF`) while the actual calldata buffer contains far fewer 32-byte words — the loop in `extractBytesArray`/`extractSigArray` will then index `words[offset + i + 1]` beyond `words.length`, throwing `ArrayIndexOutOfBoundsException` during precompile execution.

**Note on confidence:** I could not locate, within the indexed portion of the codebase, the exact precompiled contract class that invokes `extractBytesArray`/`extractSigArray`, nor confirm definitively whether the resulting exception is caught at a higher layer (e.g., `Program`/`Runtime`) and safely converted into a reverted transaction. Given the file-size/indexing limits noted in the system instructions, a full trace of the exception-handling path around `PrecompiledContract.execute()` and its callers would require a live Devin session with full repository access to confirm actual node-level impact versus a benign per-transaction revert.
