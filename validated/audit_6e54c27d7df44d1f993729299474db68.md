### Title
Vault `deposit`/`redeem`/`borrow`/`repay`/`flashloan` entry points do not check the `initialized` flag, allowing front-running of the seed deposit - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and sibling vault contracts)

### Summary
Each Zest vault contract (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) tracks an `initialized` data-var that is only ever read inside the `initialize` function itself, mirroring the "inconsistently checking initialization" pattern described in the Audius report (`_requireIsInitialized` used in some functions but not others).

### Finding Description
Each vault defines: [1](#0-0) 

and its only guard is inside `initialize`: [2](#0-1) 

`initialize` performs the anti-inflation "seed" deposit of `MINIMUM-LIQUIDITY` to `NULL-ADDRESS` before the vault is supposed to accept real user activity. The publicly-callable `deposit` function (present in every vault, e.g. `v0-vault-usdc.clar`) does not reference `(var-get initialized)` anywhere in the contract outside of `initialize` — no other public entry point (`deposit`, `redeem`, `borrow`, `repay`, `accrue`, `flashloan`) asserts that the vault has been initialized before proceeding. This is exactly the class of bug in the referenced report: the check exists but is not applied consistently across all externally reachable functions of a contract that has an explicit initialization step.

Because Clarity contract deployment and the subsequent `initialize` call are two separate transactions (not atomic like a constructor), there is a window after deployment and before the deployer's `initialize` transaction confirms during which an ordinary principal can call `deposit` directly. At that point `total-supply` is `0`, so the caller becomes the true first depositor instead of the protocol-controlled `MINIMUM-LIQUIDITY` seed deposit that `initialize` is designed to lock in first. This defeats the purpose of the seed-deposit anti-inflation-attack pattern typically used in share-based vaults, since the attacker — not the protocol — now owns the initial share/asset ratio.

### Impact Explanation
If an attacker can seize the first-depositor position, they can attempt a share-price manipulation ("vault inflation") attack against subsequent depositors' shares/collateral accounting, leading to theft of user funds at rest for later depositors whose minted shares round down due to a manipulated exchange rate. This lands on the Critical impact category (direct theft of user funds at rest).

### Likelihood Explanation
Likelihood depends on there being an observable, front-runnable gap between contract deployment and the deployer's `initialize` transaction being confirmed on-chain — something that cannot be verified from the contract source alone, and is a deployment-process, not purely code, consideration. I could not confirm from the available files whether `deposit` truly omits the check (I found the `initialized` var referenced only inside `initialize` in the sections I was able to inspect, but did not get to read the full body of `deposit`/`redeem`/`borrow` in the remaining iterations to positively rule out an implicit ordering guard, e.g. via `total-supply` or reentrancy locks that might incidentally block pre-initialization deposits).

### Recommendation
Add an explicit `(asserts! (var-get initialized) ERR-NOT-INITIALIZED)` check to every externally reachable public function in the vault contracts (`deposit`, `redeem`, `borrow`, `repay`, `accrue`, `flashloan`), or ensure deployment tooling calls `initialize` atomically with contract deployment so no window exists for pre-initialization calls.

### Proof of Concept
1. Deployer deploys `v0-vault-usdc.clar` (or any sibling vault).
2. Before the deployer's `initialize` transaction is mined/confirmed, attacker calls `deposit` directly, becoming the first depositor with `total-supply == 0`.
3. Deployer's later `initialize` call still succeeds (it only checks `not initialized`, not `total-supply == 0`), but the protocol-controlled `MINIMUM-LIQUIDITY` seed no longer establishes the initial exchange rate — the attacker's deposit does.
4. Attacker then attempts standard share-price manipulation against subsequent depositors.

Note: step 3/4's exact exploitability could not be fully confirmed within the remaining investigation budget — this should be validated by reading the complete `deposit`, `convert-to-shares-preview`, and `redeem` logic (not fully retrieved in this session) to confirm no independent `total-supply == 0` guard exists elsewhere.
