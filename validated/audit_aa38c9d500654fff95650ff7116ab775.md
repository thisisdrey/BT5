### Title
Local conntrack cache bypasses ruleset re-validation and authoritative eviction on stale entries - (File: `firewall.go`, function `inConns`)

### Summary
Nebula's per-goroutine `firewall.ConntrackCache` ("localCache") mirrors the same bug class as the reported precompile-staleness issue: a security decision that should always be re-derived from the current authoritative state is instead served from a locally cached "already checked" flag that can outlive the validity window of the underlying state it was derived from.

### Finding Description
`Firewall.Drop` first consults `f.inConns(fp, h, caPool, localCache)` [1](#0-0) . Inside `inConns`, if the flow tuple is already present in the caller-supplied `localCache`, the function returns `true` immediately — allowing the packet — without touching the authoritative `Conntrack` map, without purging expired entries via `TimerWheel.Purge()`, and without re-checking `c.rulesVersion` against the firewall's current `rulesVersion`: [2](#0-1) 

The authoritative path that runs when there is *no* local-cache hit does perform the up-to-date validation: it purges expired conntrack entries, and if the entry's `rulesVersion` differs from the live `f.rulesVersion` (i.e., firewall rules were reloaded), it re-validates the flow against the current rule table and evicts it if it no longer matches: [3](#0-2) .

This `localCache` is not scoped to a single packet or a single authoritative check — it is a long-lived, per-reader-goroutine map obtained once per `ConntrackCacheTicker` tick window and reused across every packet processed by that goroutine during that window: `ctCache.Get()` is fetched once in `listenOut`/`listenIn` and passed into every subsequent `readOutsidePackets`/`consumeInsidePacket` call until the ticker advances: [4](#0-3) [5](#0-4) . The ticker only resets the map when its internal tick counter changes, controlled by a configurable duration: [6](#0-5) .

This is structurally analogous to the reported bug: the precompile-based equity check is only authoritative "once per block" and every subsequent transaction in that block trusts the stale read instead of the latest state, letting a security check that should always be freshly evaluated be bypassed for the remainder of the window. Here, once a flow tuple is recorded in `localCache`, every later packet for that tuple during the remainder of the cache-tick window skips the authoritative re-validation entirely — including the ruleset-reload re-check and the timer-wheel-driven expiry/eviction — even if, in the interim, the conntrack entry was deleted, expired, or invalidated by a firewall rule reload.

### Impact Explanation
If firewall rules are reloaded (config reload changes `f.rulesVersion` via `AddFirewallRulesFromConfig`/rule table rebuild) or a conntrack entry is otherwise invalidated during the active local-cache window, packets belonging to that stale-but-cached flow continue to be allowed through the firewall without the mandated re-authorization against the current ruleset, until the cache ticker rolls over. This is a firewall-bypass condition: traffic that should be dropped under the newly active policy is instead forwarded, undermining the security guarantee that `Drop` is supposed to enforce on every packet.

### Likelihood Explanation
Likelihood is medium: it requires (a) an established flow that is present in the local cache, and (b) a rule reload or conntrack-state change occurring within the same cache-tick window (`conntrackCacheTimeout`). Rule reloads are a normal operational event (SIGHUP/config reload) and the cache window is a coarse, time-based batching mechanism rather than a per-packet-consistent check, so the race window is realistic under normal operational conditions rather than requiring an unusual attacker-controlled trigger.

### Recommendation
Do not let `localCache` hits bypass the `rulesVersion` re-validation. At minimum, store the `rulesVersion` (or a monotonic generation counter) alongside the cached tuple in `localCache` and compare it against the live `f.rulesVersion` before returning `true`; on mismatch, fall through to the authoritative `Conntrack` check. Alternatively, invalidate/clear the local cache synchronously whenever the firewall ruleset is reloaded, rather than relying solely on the independent time-based ticker.

### Proof of Concept
1. Establish a flow F that is allowed by rule R and gets recorded into both the authoritative `Conntrack.Conns` map and, on the next packet for F within the current tick, into the reader goroutine's `localCache` (`firewall.go:505-510`, `573-575`).
2. Trigger a firewall rule reload that removes/narrows rule R (e.g., via config reload invoking rule re-application, which bumps `f.rulesVersion`).
3. Continue sending packets for flow F within the same `conntrackCacheTimeout` window. Because `localCache[fp]` still has the stale entry, `inConns` returns `true` immediately at `firewall.go:505-510`, never reaching the `rulesVersion` comparison at `firewall.go:527-560` that would otherwise drop the now-disallowed flow.
4. Traffic for flow F continues to pass until the `ConntrackCacheTicker` advances and the local cache is reset (`firewall/cache.go:52-67`), demonstrating a window in which the firewall bypasses its own updated policy.

			}
			break
		}

// Get checks if the cache ticker has moved to the next version before returning
// the map. If it has moved, we reset the map.
func (c *ConntrackCacheTicker) Get() ConntrackCache {
	if c == nil {
		return nil
	}
	if tick := c.cacheTick.Load(); tick != c.cacheV {
		c.cacheV = tick
		if ll := len(c.cache); ll > 0 {
			if c.l.Enabled(context.Background(), slog.LevelDebug) {
				c.l.Debug("resetting conntrack cache", "len", ll)
			}
			c.cache = make(ConntrackCache, ll)
		}
	}

	return c.cache
}
