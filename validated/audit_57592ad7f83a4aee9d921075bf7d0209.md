### Title
Unbounded attachment size accepted on P2P download path bypasses `attachments_max_size` cap - (File: `stackslib/src/net/atlas/download.rs`, `stackslib/src/net/atlas/db.rs`)

### Summary
`AttachmentsDownloader::run()` inserts every attachment returned by a peer for a `GetAttachment` request directly via `AtlasDB::insert_instantiated_attachment`, without ever invoking `AtlasDB::should_keep_attachment`, which is the only place that checks `attachment.content.len() as u32 > self.atlas_config.attachments_max_size`. Any peer selected as a download source can therefore return content far larger than the configured `attachments_max_size` and have it persisted to the node's local Atlas database.

### Finding Description
When the node needs an attachment, `AttachmentsBatchStateMachine` issues an `AttachmentRequest` to a chosen peer. When the peer replies, `AttachmentsBatchStateContext::extend_with_attachments` decodes the body and inserts the raw `Attachment` into `self.attachments` with no size check: [1](#0-0) 

In `AttachmentsDownloader::run()`, once the state machine reaches `Done`, every attachment collected from `context.attachments` is passed straight to `AtlasDB::insert_instantiated_attachment`: [2](#0-1) 

At no point on this path is `should_keep_attachment` — the function that enforces `attachments_max_size` — called. Grepping the whole repo for `should_keep_attachment` and `insert_instantiated_attachment` shows the size-checking function is defined in `stackslib/src/net/atlas/db.rs` but its only caller outside tests is on the local RPC transaction-posting path (`posttransaction.rs`), not the P2P attachment-download path. The `check_attachment_instances` helper (used for the initial batch and queued-instance resolution) also calls `insert_instantiated_attachment` directly for previously-inboxed attachments without any size gate: [3](#0-2) 

Because the attacker is a legitimate outbound-sync peer the victim selected as an attachment source (no special privilege needed — any peer that a node is data-syncing with can be picked), the attacker fully controls the HTTP response body for `GetAttachment`, bounded only by the node's general HTTP body-size limit, which is independent of and typically much larger than `attachments_max_size`.

### Impact Explanation
A single malicious peer can cause the victim node to write attachment blobs to its SQLite-backed Atlas DB (`instantiated_attachments`/related tables) that exceed the operator-configured `attachments_max_size`, defeating the purpose of that cap. This is repeatable per attachment request/response cycle and amplifies local storage consumption per accepted attachment, up to the node's HTTP payload ceiling instead of the intended, much smaller `attachments_max_size` ceiling. This matches the "storage exhaustion / unauthenticated write to state" pattern called out as Critical in the prompt, since it is an unauthenticated write of attacker-controlled size to persistent node state via a single P2P/RPC exchange.

### Likelihood Explanation
Preconditions: the victim node must be actively resolving an Atlas attachment (a routine, frequent operation for a syncing node) and must pick the attacker as one of its outbound sync peers/data sources for that request — something any connected peer offering the relevant attachment in its inventory can arrange by advertising a positive inventory bit. No secrets, keys, or privileged roles are required; the attacker only needs to run a normal peer and respond to a `GetAttachment` request the victim itself initiated. The attack is cheap (one oversized HTTP response) and repeatable across multiple attachment hashes/batches.

### Recommendation
Invoke `AtlasDB::should_keep_attachment` (or an equivalent length check against `AtlasConfig::attachments_max_size`) before calling `insert_instantiated_attachment` in both `AttachmentsDownloader::run()` (the `Done` branch handling `context.attachments`) and in `check_attachment_instances`'s "inboxed attachment" branch. Reject/drop oversized attachments and penalize the offending peer's reliability report instead of persisting the data.

### Proof of Concept
Rust test plan (net-level):
1. Construct an `AtlasDB` with `AtlasConfig::attachments_max_size` set to a small value (e.g., 1 MB).
2. Build an `Attachment { content: vec![0u8; 10_000_000], .. }` (content exceeds the cap).
3. Call `atlas_db.should_keep_attachment(&contract_id, &attachment)` (or the equivalent size-check API) and assert it returns `false`.
4. Simulate the download path by directly invoking `atlas_db.insert_instantiated_attachment(&attachment)` (mirroring the call in `AttachmentsDownloader::run()`'s `Done` branch) and assert the call succeeds and a subsequent `atlas_db.find_attachment(&attachment.hash())` returns `Some(attachment)` with `content.len() == 10_000_000`, proving the oversized blob was persisted despite the cap.
5. (End-to-end variant) Stand up two `TestPeer`s, have the victim issue a real `GetAttachment` request that the attacker peer answers with a 10 MB body, and assert via `AttachmentsDownloader::run()` that the oversized attachment ends up stored in the victim's Atlas DB.
