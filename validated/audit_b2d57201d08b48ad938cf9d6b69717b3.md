### Title
Unauthorized cross-repository object pool linking allows arbitrary object disclosure via `LinkRepositoryToObjectPool` - (File: internal/gitaly/service/objectpool/link.go)

### Summary
`LinkRepositoryToObjectPool` lets the caller name *any* object pool by storage name and relative path and attach it as an alternate object directory to a repository the caller controls, with no verification that the caller (or the target repository) has any prior relationship, membership record, or authorization concerning that pool.

### Finding Description
The RPC handler `LinkRepositoryToObjectPool` [1](#0-0)  only validates that the `repository` field is a syntactically valid repository via `s.locator.ValidateRepository`, then resolves the `object_pool` field through `s.poolForRequest(ctx, req)` [2](#0-1) , which simply loads whatever pool repository is named in the request — there is no check that the object pool "belongs" to, was created from, or was ever intended to be shared with the calling repository. The proto definition confirms both fields are attacker-controllable identifiers (storage + relative path) rather than opaque, pre-authorized handles [3](#0-2) .

`pool.Link()` then writes the pool's object directory path into the target repository's `objects/info/alternates` file [4](#0-3) . Once linked, Git treats all objects in the pool as part of the target repository's object database. Because alternates make all objects in the pool directly readable through the linking repository (via `git-cat-file`, `TreeEntry`, `GetBlob`, clone/fetch, etc.), any ordinary user who can reach this RPC for a repository they control (e.g., through their own project/fork) and who can discover or guess a private pool's storage name and relative path can pull that pool's objects into their own repository and read them — including commits/blobs originating from repositories they were never granted access to. Gitaly explicitly acknowledges elsewhere that alternates/pool isolation is safety-critical and fragile: `DeleteObjectPool`'s documentation states "There are no safety checks in place, so if any repository is still using this object pool it will become corrupted" [5](#0-4) , showing the design assumes pool membership is trustworthy and pre-vetted by the caller — an assumption `LinkRepositoryToObjectPool` does not enforce itself.

### Impact Explanation
This mirrors the `withdrawInterest()` pattern: a caller can perform a sensitive state-changing action (linking to/disconnecting from a resource) targeting an entity (the object pool and its true members) it does not own or control, with no consent check from the affected party. Consequences:
- **Object disclosure**: A user can link their own repository to an unrelated, potentially private object pool and read its objects, bypassing per-repository access control.
- **Corruption/DoS of unrelated pool members**: If `DeleteObjectPool` or repacking/pruning is later invoked by the legitimate pool owner under the (violated) assumption that only known members are linked, unexpected linked repositories can be corrupted, per the documented lack of safety checks.

This is a real access-control gap in the isolation boundary between repositories sharing an object pool, matching the "object-pool and alternates isolation" bug class.

### Likelihood Explanation
Exploitation requires only an authenticated, ordinary Gitaly caller (any user/service able to invoke RPCs for a repository they legitimately own, as in any GitLab project owner) and knowledge or a guessable/enumerable relative path of a target object pool (pool paths are typically derived deterministically from a hashed repository ID / fork lineage, which may be inferable). No privileged token beyond ordinary repository access is required, and the routing/authorization model does not gate pool membership beyond basic path validation.

### Recommendation
Enforce an ownership/membership authorization check before linking: verify that the `object_pool` is one that was created from (or is already associated with) the `repository`'s fork network/partition, e.g., by checking the object pool state store (`ObjectPoolStateManager`) for an expected relationship, or by requiring the caller to also prove control of the pool's origin repository, before writing the alternates file. Additionally, consider recording and validating pool membership centrally (as `NotifyLinkRepository`/`NotifyUnlinkRepository` in `internal/gitaly/storage/relational/state_manager.go` already does for bookkeeping) and using that record to reject links that don't match the expected fork-network partitioning invariant described in the transactions documentation.

### Proof of Concept
1. As User A, create/own repository `R_A` in project A's storage.
2. Determine or guess the storage name and relative path of an existing object pool `P_B` that was created for a different, private project B's fork network (pool relative paths follow a predictable derivation scheme within a storage).
3. Call `LinkRepositoryToObjectPool` with `repository = R_A` and `object_pool = P_B`.
4. Observe that `R_A`'s `objects/info/alternates` now references `P_B`'s object directory [6](#0-5) .
5. Fetch/clone `R_A`; all of `P_B`'s objects (including private objects from project B and its forks) become retrievable through `R_A`, even though User A has no access grant to project B.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}
