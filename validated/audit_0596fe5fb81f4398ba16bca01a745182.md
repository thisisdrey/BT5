## Finding

### Title
Remote unauthenticated panic in `SignerEventReceiver::next_event` via `.expect()` on failed HTTP response write - (File: `libsigner/src/events.rs`)

### Summary
The Prysm fix (`bcb4155`) hardens an event-stream handler so that a connection error while replying to a peer returns an error instead of panicking the process. The `libsigner` `SignerEventReceiver`, which listens for HTTP events posted by the Stacks node, has the same bug class: several response paths call `.expect(...)` on a fallible I/O write to the client socket, so if the remote peer half-closes or resets the connection at the wrong moment, the receiver thread panics instead of returning an `EventError`.

### Finding Description
`SignerEventReceiver::next_event` handles the `/status` endpoint by writing a response directly and unwrapping the result: [1](#0-0) 

```rust
if request.url() == "/status" {
    request
    .respond(HttpResponse::from_string("OK"))
    .expect("response failed");
    return Ok(SignerEvent::StatusCheck);
}
```

`request.respond()` performs a network write to the client's TCP socket via `tiny_http`. If the client (the connecting peer) closes/resets the connection between accepting the request and the server writing the reply — a completely normal, remotely-triggerable TCP condition — this call returns `Err`, and `.expect("response failed")` panics the thread running `main_loop()`. [2](#0-1) 

`main_loop()` runs in a dedicated thread and repeatedly calls `next_event()`; there is no `catch_unwind` around it, so a panic inside `next_event()` terminates that thread outright, silently killing the signer's event-ingestion pipeline (no more StackerDB chunk events, burn-block events, or block-proposal responses will ever be received again on that signer instance).

This is directly analogous to the referenced Prysm commit: a connection-level error (peer disconnecting mid-response) that should be handled gracefully instead reaches an `.expect()`/`unwrap()`-style panic path.

Unlike the sibling helper `ack_dispatcher`, which correctly logs-and-continues on write failure: [3](#0-2) 

```rust
fn ack_dispatcher(request: HttpRequest) {
    if let Err(e) = request.respond(HttpResponse::empty(200u16)) {
        error!("Failed to respond to request: {:?}", &e);
    };
}
```

the `/status` branch does not follow this pattern and instead panics.

### Impact Explanation
Any TCP client that can reach the signer's event-receiver bind address (this is the endpoint the Stacks node is configured to POST events to; depending on deployment it can be reachable beyond localhost) can trigger this by connecting, issuing `GET /status`, and closing the socket before the server finishes writing its response. This crashes the event-receiver thread, permanently stopping that signer from receiving further StackerDB/burn-block/block-validation events until the process is restarted — an unauthenticated remote DoS requiring only a single malformed/interrupted request, matching the "Critical: remote crash/unauthenticated DoS from few messages" bar.

### Likelihood Explanation
High. No authentication or signature check gates the `/status` path, and triggering a mid-write connection reset from a client is trivial (e.g., closing the socket immediately after sending the request, or using `SO_LINGER` with a zero timeout to force a `RST`). No special timing beyond a single connection attempt is required.

### Recommendation
Change the `/status` handler (and audit any other `.expect()`/`.unwrap()` calls on `request.respond(...)` in `libsigner/src/events.rs`) to handle the `Result` gracefully, mirroring `ack_dispatcher`'s pattern — log the error and return a recoverable `EventError` (or simply continue the loop) instead of panicking the receiver thread.

### Proof of Concept
1. Start a signer with `SignerEventReceiver` bound to a reachable address/port.
2. From an external host, open a raw TCP connection to that port and send:
   ```
   GET /status HTTP/1.1\r\nHost: x\r\nConnection: close\r\n\r\n
   ```
3. Immediately after sending, close/reset the socket (e.g., set `SO_LINGER(0)` then close) before the server's response bytes are flushed.
4. Observe the event-receiver thread panic at the `.expect("response failed")` call, ending the `main_loop()` thread and halting all further event delivery to the signer.

```rust
    /// Main loop for the receiver.
    /// Typically, this is started in a separate thread.
    fn main_loop(&mut self) {
        loop {
            if self.is_stopped() {
                info!("Event receiver stopped");
                break;
            }
            let next_event = match self.next_event() {
                Ok(event) => event,
                Err(EventError::UnrecognizedEvent(..)) => {
                    // got an event that we don't care about (not a problem)
                    continue;
                }
                Err(EventError::Terminated) => {
                    // we're done
                    info!("Caught termination signal");
                    break;
                }
                Err(e) => {
                    warn!("Failed to receive next event: {:?}", &e);
                    continue;
                }
            };
            if !self.forward_event(next_event) {
                info!("Failed to forward event");
                break;
            }
        }
        info!("Event receiver main loop exit");
    }
```
