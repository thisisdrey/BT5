### Title
Meta-transaction `SignedDelegateAction`/`VersionedSignedDelegateAction` signatures omit any chain/network identifier, enabling cross-chain replay of the same signed delegate action - (File: `core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`)

### Summary
The reported bug class is: a signature scheme's `messageHash` omits `chainId`, so a signed message valid on one chain can be replayed on another chain sharing the same signer/account model. In nearcore, the NEP-366/NEP-461 meta-transaction signing scheme (`DelegateAction`/`DelegateActionV2` signed via `get_nep461_hash()` and verified by `SignedDelegateAction::verify()` / `VersionedSignedDelegateAction::verify()`) has the exact same gap: the signed payload contains no chain identifier and no `block_hash` binding, unlike ordinary `Transaction`s, which nearcore explicitly relies on `block_hash` for replay protection across chains/forks.

### Finding Description
A regular NEAR `Transaction` includes a `block_hash` field that ties the signature to a specific chain/fork; the JSON-RPC layer explicitly rejects transactions built on an unrelated fork/chain (`test_replay_protection` in `chain/jsonrpc/jsonrpc-tests/tests/rpc_transactions.rs`), and this is documented as a core replay-protection mechanism (`docs/architecture/how/tx_routing.md`).

In contrast, `DelegateAction` (the payload a user signs off-chain for meta transactions, NEP-366) is defined with only: [1](#0-0) 
and the hash that gets signed is produced purely from a `SignableMessage` wrapper (`discriminant` + the message itself), with no chain/genesis/block binding at all: [2](#0-1) 

`SignedDelegateAction::verify()` and `VersionedSignedDelegateAction::verify()` both simply recompute this chain-agnostic hash and check the signature: [3](#0-2) [4](#0-3) 

Neither the `discriminant` (which only encodes the NEP number and on/off-chain flag, see `MessageDiscriminant`/`SignableMessageType` in `signable_message.rs`) nor the `DelegateAction`/`DelegateActionV2` fields (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`) contain any value that is unique to a specific NEAR chain instance (no genesis hash, no `chain_id`, no `block_hash`). The only binding to "freshness" is `max_block_height`, a plain integer with no chain context, and `nonce`, which is scoped only to `(sender_id, public_key)` — not to a chain.

By design, `SignedDelegateAction` is meant to be transmitted off-chain to a relayer (see `docs/architecture/how/meta-tx.md`), and the *outer* transaction that wraps it is separately signed by the relayer with a valid `block_hash` for whatever chain it targets — that outer signature check does not, and cannot, validate that the inner `DelegateAction` was intended for that particular chain. `apply_delegate_action` in `runtime/runtime/src/actions.rs` only checks the inner signature validity, `max_block_height` expiry, sender/receiver matching, and nonce ordering — never anything chain-specific: [5](#0-4) 

nearcore's own tooling demonstrates that two distinct NEAR chains can legitimately share identical account/access-key/nonce state: `tools/mirror` explicitly forks a "target chain" from a "source chain"'s state (`view-state dump-state`), and its README states plainly that ordinary transactions *cannot* be replayed cross-chain only because of the `block_hash` field, which is why the mirror tool must remap every account's private key to produce new signatures: [6](#0-5) 

That `block_hash`-based protection that `tools/mirror` relies on for ordinary transactions simply does not exist for the inner `DelegateAction` signature. Any two NEAR-protocol-compatible networks that share (even momentarily, e.g., right after a state fork/mirror, or through independent chains where a user reuses the same account id/key/nonce sequence) the same `(sender_id, public_key, nonce)` tuple will accept the identical `SignedDelegateAction` bytes as valid, because the signed hash is chain-agnostic.

### Impact Explanation
An intercepted (or intentionally dual-submitted) `SignedDelegateAction` can be relayed and executed on a second NEAR-protocol chain that shares the signer's access-key nonce state (e.g., a state-forked/mirrored chain, or any deployment sharing account/key/nonce state with the original). This causes the same signed meta-transaction — a token transfer, an `AddKey`/`DeleteKey`, a function call moving funds, etc. — to execute twice with only a single user authorization, which is a double-spend/replay of value and a form of unauthorized cross-chain execution of a user's signed intent. This matches the "double-spend/replay" and "authorization escalation across ... promises" impact categories.

### Likelihood Explanation
Exploitation requires two chains that share meta-transaction signer state at some point (nonce for `(sender_id, public_key)` still valid/equal). This is a scenario nearcore itself deliberately creates and documents (`tools/mirror`, state-forked test/shadow networks), and can also occur incidentally whenever the same account id and key are used with fresh/matching nonces across independently operated NEAR-protocol chains. The attack itself requires no privileged position: any party who obtains the off-chain `SignedDelegateAction` bytes (which NEP-366 explicitly has travel off-chain to a relayer before being included on-chain) and access to a relayer on the second chain can replay it.

### Recommendation
Include a chain-binding value in the NEP-461 signable payload for `DelegateAction`/`DelegateActionV2` — e.g., mix in the genesis hash / chain id (analogous to `GenesisId` used in the network protocol, see `chain/network/src/network_protocol/network.proto`) or the same `block_hash` binding used by ordinary `Transaction`s — so that `get_nep461_hash()` commits to the specific chain the delegate action is intended for, preventing the same signature from validating on more than one chain.

### Proof of Concept
1. Alice has an account `alice.near`/access key that exists with nonce `N` on Chain A and, due to a state fork/mirror (as with `tools/mirror`) or independent chain with identical account/key/nonce setup, also on Chain B.
2. Alice signs a `DelegateAction { sender_id: alice, receiver_id: bob, actions: [Transfer(X)], nonce: N+1, max_block_height: H, public_key: pk }` off-chain per NEP-366, producing `SignedDelegateAction` via `get_nep461_hash()` (`core/primitives/src/action/delegate.rs`).
3. A relayer submits it wrapped in a fresh outer `SignedTransaction` (with a valid `block_hash` for Chain A) to Chain A — `apply_delegate_action` validates `signed_delegate_action.verify()`, `max_block_height`, and `nonce`, and executes the transfer, bumping Alice's nonce there.
4. Before Chain B's state diverges (nonce for `pk` still `N`), an attacker (or the same relayer) wraps the identical `SignedDelegateAction` bytes in a new outer `SignedTransaction` valid for Chain B (its own valid `block_hash`) and submits it there. `signed_delegate_action.verify()` succeeds identically since the hash never referenced any chain identifier, and `nonce: N+1 > N` passes the nonce check on Chain B too — the transfer executes a second time, on a second chain, from a single user signature.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }
