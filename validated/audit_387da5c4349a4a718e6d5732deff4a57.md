Audit Report

## Title
Insufficient reward-rate precision in `pallet-asset-rewards` truncates and permanently loses staker rewards for low-decimal reward tokens - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards` scales `reward_per_token` calculations by a fixed, hard-coded `u16` `PRECISION_SCALING_FACTOR` of `4096` [1](#0-0) . Because this scaling factor is not chosen relative to the reward token's decimals or the pool's staked-token magnitude, integer division in `reward_per_token()` can truncate to zero whenever `reward_rate_per_block * rewardable_blocks_elapsed * 4096 < total_tokens_staked` [2](#0-1) , and since `update_pool_rewards` unconditionally advances `last_update_block` to the current block and overwrites `reward_per_token_stored` with the (possibly truncated) value [3](#0-2) , any reward owed for that already-elapsed interval is permanently lost rather than merely delayed.

## Finding Description
`reward_per_token()` computes the incremental reward-per-token value using `pool_info.reward_rate_per_block.ensure_mul(rewardable_blocks_elapsed.into())?.ensure_mul(PRECISION_SCALING_FACTOR.into())?.ensure_div(pool_info.total_tokens_staked)?` [2](#0-1) , and `derive_rewards()` later divides back out by the same fixed `PRECISION_SCALING_FACTOR` when computing a staker's owed amount [4](#0-3) . Neither `create_pool` [5](#0-4)  nor `set_pool_reward_rate_per_block` [6](#0-5)  validates that the configured `reward_rate_per_block` is large enough relative to plausible `total_tokens_staked` (which is only known/grows after users stake, post-creation) to survive this division.

Because `update_pool_rewards` writes `reward_per_token_stored = reward_per_token` and advances `last_update_block` to "now" every time it is invoked (via `stake`, `unstake`, or `harvest_rewards`), the `rewardable_blocks_elapsed` window used in the next computation always resets to zero from that point forward — there is no fractional/remainder carry mechanism. This differs materially from `pallet-nomination-pools`, which deliberately uses a `FixedPointNumber`-based `RewardCounter` (documented to be robust to this class of precision loss, e.g. `FixedU128`) specifically to avoid truncation [7](#0-6) .

This creates two related exploit paths, both reachable via public extrinsics with no special privilege required:
1. **Configuration-driven truncation**: A pool combining a large-magnitude staked asset (e.g., 18-decimal token, large stake) with a modest `reward_rate_per_block` for a low-decimal reward asset causes the division to floor to 0 on ordinary reward-accrual calls.
2. **Griefing via forced flush**: Any unprivileged staker can call the public `harvest_rewards` extrinsic with high frequency (e.g., every block), forcing `rewardable_blocks_elapsed` to stay small on each call. If `reward_rate_per_block * elapsed * 4096 < total_tokens_staked` for that small `elapsed`, each call truncates the earned increment to zero and irrecoverably discards it via `update_pool_rewards`'s stateless overwrite — degrading rewards for the entire pool, not just the caller, since `reward_per_token_stored` is a shared value.

## Impact Explanation
This matches the "runtime bug that compromises intended behavior" and "permanent user-fund lock" impact categories: reward-asset tokens deposited into the pool's account by the pool creator/admin are accounted for via `reward_rate_per_block`, but the truncation described above means the pallet's internal accounting (`reward_per_token_stored`, `staker_info.rewards`) can never register the owed amount for the affected interval. The tokens remain in the pool account balance but are effectively unclaimable by their intended beneficiaries because the ledger permanently under-counts them, with no privileged actor or malicious node/validator/relayer behavior required — ordinary public extrinsic calls (`stake`, `unstake`, `harvest_rewards`) by unprivileged users are sufficient to trigger and lock in the loss.

## Likelihood Explanation
Likelihood is high for any pool whose staked-asset magnitude is large relative to `reward_rate_per_block * PRECISION_SCALING_FACTOR` — a realistic, non-malicious configuration for popular high-decimal staked tokens paired with modest reward-token emission rates. It requires no compromised keys, no governance abuse, and no off-repo trust assumptions: normal user staking/harvesting behavior (or a single user repeatedly calling the public `harvest_rewards` extrinsic) is sufficient to trigger and permanently lock in the truncation, and the flaw exists in the pallet's own fixed-point design rather than any admin misconfiguration.

## Recommendation
Replace the fixed `u16` `PRECISION_SCALING_FACTOR = 4096` with a much larger, fixed-point-safe precision accumulator (e.g., a `FixedU128`/`u128`-based reward counter analogous to `pallet-nomination-pools`'s `RewardCounter`), and/or add validation at `create_pool`/`set_pool_reward_rate_per_block` time and on each `reward_per_token` update to detect/reject configurations where the division would systematically floor to zero, or accumulate remainders across calls instead of discarding them on each `update_pool_rewards` overwrite.

## Proof of Concept
1. Create a pool via `create_pool` with a staked asset of 18 decimals and `reward_rate_per_block = 1` (raw units), relying on the fixed `PRECISION_SCALING_FACTOR = 4096` [1](#0-0) .
2. Stake tokens via the public `stake` extrinsic such that `total_tokens_staked` reaches `10^18`.
3. Call the public `harvest_rewards` extrinsic repeatedly (e.g., every block). Each call computes `reward_per_token()` as `1 * elapsed * 4096 / 10^18` per [2](#0-1) , which truncates to `0` for any small `elapsed`; `update_pool_rewards` then persists this unchanged value and advances `last_update_block` [3](#0-2) , discarding the fractional reward for that interval.
4. Observe `staker_info.rewards` (via `derive_rewards`, [4](#0-3) ) remains `0` indefinitely while the reward-asset balance sits unclaimed in the pool account, confirming the permanent fund-lock impact.

	fn create_pool(
		creator: &T::AccountId,
		staked_asset_id: T::AssetId,
		reward_asset_id: T::AssetId,
		reward_rate_per_block: T::Balance,
		expiry: DispatchTime<BlockNumberFor<T>>,
		admin: &T::AccountId,
	) -> Result<PoolId, DispatchError> {
		// Ensure the assets exist.
		ensure!(T::Assets::asset_exists(staked_asset_id.clone()), Error::<T>::NonExistentAsset);
		ensure!(T::Assets::asset_exists(reward_asset_id.clone()), Error::<T>::NonExistentAsset);

		// Check the expiry block.
		let now = T::BlockNumberProvider::current_block_number();
		let expiry_block = expiry.evaluate(now);
		ensure!(expiry_block > now, Error::<T>::ExpiryBlockMustBeInTheFuture);

		let pool_id = NextPoolId::<T>::try_mutate(|id| -> Result<PoolId, DispatchError> {
			let current_id = *id;
			*id = id.ensure_add(1)?;
			Ok(current_id)
		})?;

		let footprint = Self::pool_creation_footprint();
		let cost = T::Consideration::new(creator, footprint)?;
		PoolCost::<T>::insert(pool_id, (creator.clone(), cost));

		// Create the pool.
		let pool = PoolInfoFor::<T> {
			staked_asset_id: staked_asset_id.clone(),
			reward_asset_id: reward_asset_id.clone(),
			reward_rate_per_block,
			total_tokens_staked: 0u32.into(),
			reward_per_token_stored: 0u32.into(),
			last_update_block: 0u32.into(),
			expiry_block,
			admin: admin.clone(),
			account: Self::pool_account_id(&pool_id),
		};

		// Insert it into storage.
		Pools::<T>::insert(pool_id, pool);

		// Emit created event.
		Self::deposit_event(Event::PoolCreated {
			creator: creator.clone(),
			pool_id,
			staked_asset_id,
			reward_asset_id,
			reward_rate_per_block,
			expiry_block,
			admin: admin.clone(),
		});

		Ok(pool_id)
	}

	fn set_pool_reward_rate_per_block(
		admin: &T::AccountId,
		pool_id: PoolId,
		new_reward_rate_per_block: T::Balance,
	) -> DispatchResult {
		let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
		ensure!(pool_info.admin == *admin, BadOrigin);
		ensure!(
			new_reward_rate_per_block > pool_info.reward_rate_per_block,
			Error::<T>::RewardRateCut
		);

		// Always start by updating the pool rewards.
		let rewards_per_token = Self::reward_per_token(&pool_info)?;
		let mut pool_info = Self::update_pool_rewards(&pool_info, rewards_per_token)?;

		pool_info.reward_rate_per_block = new_reward_rate_per_block;
		Pools::<T>::insert(pool_id, pool_info);

		Self::deposit_event(Event::PoolRewardRateModified { pool_id, new_reward_rate_per_block });

		Ok(())
	}
