### Title
Unprivileged attacker can fill a victim's per-account token list (`MAX_TOKENS_PER_USER`) via dust `DepositToken` transfers, DoS-ing deposits, borrows and self-rescue - ([File: contracts/Pool.sol](contracts/Pool.sol), [File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`Pool` enforces a hard cap of 30 entries across `debtTokensOfAccount` + `depositTokensOfAccount` per account. `DepositToken._transfer` adds a token to the *recipient's* list without any opt-in whenever their prior balance was zero. An unprivileged attacker can deposit dust of every collateral type, then `transfer` 1 wei of each deposit token to a victim, permanently occupying list slots and making any call that adds a new token to the victim's list revert with `UserReachedMaxTokens`. This is the availability/DoS analog of the CVE (hang/crash → complete denial of service): the protocol liveness guarantee for the targeted account is broken by an unprivileged caller.

### Finding Description
- `Pool.addToDebtTokensOfAccount` / `addToDepositTokensOfAccount` are gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` (`MAX_TOKENS_PER_USER = 30`). [1](#0-0) [2](#0-1) 
- `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's balance was 0 and `amount_ > 0` — there is no recipient consent, allowlist, or minimum-amount check. [3](#0-2) 
- `transfer` only checks the *sender's* unlocked balance, so the attacker can freely push dust to any address. [4](#0-3) 
- The same mechanism exists on mint: `_mint` calls `addToDepositTokensOfAccount` for first-time recipients, so a victim whose list is full cannot `deposit` into a new collateral (the `_mint` reverts), cannot `issue`/`leverage` a new synth (the debt-token add reverts), and cannot receive a different collateral deposit token that would be needed to restore health before liquidation. [5](#0-4) 

### Impact Explanation
Availability loss for the targeted account: any operation that would add a new deposit or debt token reverts, so the victim is blocked from opening new debt positions and — critically — from depositing a *new* collateral type to rescue an unhealthy position before `Pool.liquidate`. Combined with a price move, this can force liquidation that the victim could otherwise have prevented (indirect loss of collateral via the liquidation incentive). The DoS persists until the victim withdraws the dusted collateral (burns to zero to trigger `removeFromDepositTokensOfAccount`), which costs gas per token and requires the dusted deposit tokens to actually be withdrawable — note `_withdraw` is `whenNotShutdown` only, so withdrawal itself is available, bounding this to temporary freezing/griefing rather than permanent loss.

### Likelihood Explanation
Cheap to execute: the attacker deposits a minimal amount of each listed underlying (dust), then calls `transfer(victim, 1)` for each deposit token. Each transfer is a normal ERC20 call with no privileged role, no pause dependency, and no reentrancy/`SynthContext` restriction (`transfer` only checks sender's `unlockedBalanceOf`). The number of registered deposit tokens per pool is small, so filling a victim who already holds a few tokens is trivial. Main limitation: impact is bounded — the victim can clear slots by fully withdrawing dusted tokens, so this is a temporary DoS / forced-liquidation grief rather than theft.

### Recommendation
- Require recipient-side consent or a minimum threshold before registering a token in `depositTokensOfAccount` (e.g., only add on `deposit`, not on `transfer`, or ignore amounts below a floor).
- Alternatively, remove the shared cap or track `MAX_TOKENS_PER_USER` separately for deposits vs. debts, and skip `add`/`remove` bookkeeping for seized/liquidation flows where possible.
- At minimum, document that users can recover by withdrawing the dusted collateral.

### Proof of Concept
Foundry-style fork test sketch:

```solidity
// victim has an open position using a few tokens
// attacker:
for (uint i; i < depositTokens.length; ++i) {
    underlying[i].approve(address(depositToken[i]), 1);
    depositToken[i].deposit(1, attacker);      // or deposit enough for 1 wei msdToken
    depositToken[i].transfer(victim, 1);       // adds token to victim's list, no consent
}
// repeat/compose until debtTokensOfAccount.length(victim)
//   + depositTokensOfAccount.length(victim) == 30

// then:
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
depositTokenNew.deposit(amount, victim);       // _mint -> addToDepositTokensOfAccount reverts

vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
debtTokenNew.issue(amount, victim);            // addToDebtTokensOfAccount reverts

// victim with unhealthy position cannot deposit a new collateral to deleverage;
// pool.liquidate succeeds against them (position stays liquidatable).
```

Note: I could not verify the full `liquidate` body beyond line 560 or confirm the deployed count of deposit tokens per pool; the PoC assumes enough distinct deposit tokens exist in a pool to fill the remaining slots (the cap check sums both lists). If the victim can always withdraw dust to clear slots cheaply, severity is bounded to temporary DoS consistent with a Medium finding.
