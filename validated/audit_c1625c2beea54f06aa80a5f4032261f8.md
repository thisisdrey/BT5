### Title
Denial of service via dust transfers filling `depositTokensOfAccount` to `MAX_TOKENS_PER_USER` — ([File: contracts/Pool.sol](contracts/Pool.sol) / [contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The Discourse report's bug class is an unprivileged user injecting arbitrarily large data through a public route, exhausting a bounded resource. The Metronome analog is the per-account token-list resource: every first-time receipt of a `DepositToken` (via `deposit`/`_mint`, `transfer`, `transferFrom`, `seize`, or fee crediting) calls `Pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` once the combined count of deposit and debt tokens reaches `MAX_TOKENS_PER_USER = 30`. Any EOA can force-push dust deposit-token balances to an arbitrary victim (including the protocol `feeCollector`), permanently consuming slots in the victim's list and causing all future first-time token additions for that account to revert.

### Finding Description
- `DepositToken._transfer` adds the token to the *recipient's* list when their balance was zero (`contracts/DepositToken.sol:518-520`), and the same happens in `_mint` (`contracts/DepositToken.sol:486-488`).
- `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, reverting once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`contracts/Pool.sol:143-148`, `204-208`).
- `transfer`/`transferFrom` are permissionless and the recipient is attacker-chosen (`contracts/DepositToken.sol:348-376`). There is no opt-in, no minimum amount, and no way for the recipient to refuse.

Attack paths:
1. **Victim griefing**: attacker deposits dust into every listed deposit token, then `transfer`s 1 wei of each to the victim until the victim's combined list hits 30. Afterwards the victim cannot `deposit` a collateral type they don't already hold, cannot receive any new deposit token, and cannot mint a new synth debt type (`DebtToken.issue` → `addToDebtTokensOfAccount` hits the same cap) — all revert `UserReachedMaxTokens`. If the victim's collateral is fully locked (`unlockedBalanceOf == 0`, e.g., position at max LTV or underwater), they cannot even transfer the dust out to free slots, so the block persists until their position health improves.
2. **FeeCollector amplification**: `_withdraw` pays the withdraw fee by `_transfer(account, feeCollector, fee)` (`contracts/DepositToken.sol:545-548`) and `deposit` mints the fee to `feeCollector` (`contracts/DepositToken.sol:230-233`). Filling the feeCollector's list makes every deposit/withdrawal of any token not yet in its list revert, a pool-wide DoS on fee-bearing flows, recoverable only by governance sweeping the collector.

### Impact Explanation
Temporary freezing of funds / liveness break: a targeted account is barred from adding any new collateral or debt position, and if its balance is fully locked it cannot self-recover. In the feeCollector variant, deposits and withdrawals across the entire pool revert for untouched tokens, freezing user funds until the feeCollector's list is reduced (requires a privileged sweep). No funds are stolen, matching a Medium-severity DoS analogous to the reference report.

### Likelihood Explanation
Requires the pool to have enough registered deposit + debt tokens for the attacker to push the victim to the 30-entry cap (the attacker cannot create new entries beyond the governor-listed tokens, since debt tokens are not freely transferable). Cost is only dust deposits plus gas for ≤30 transfers, reachable via `Operator.execute` batching. Effectiveness is conditional on the deployed pool's token count — pools with few collateral types leave the victim with slack, so the attack fully lands only where the listed token count approaches/exceeds 30 or where the victim already occupies many slots.

### Recommendation
- Make list additions non-reverting at capacity: silently skip `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` when the account is at the cap, since the lists are only used for `debtOf`/`depositOf` accounting — alternatively iterate over the pool's global `depositTokens`/`debtTokens` sets.
- Or gate additions: only add tokens for which the account deposited itself (track a flag set in `deposit`/`issue` rather than in `_transfer`), so unsolicited dust transfers cannot consume slots.
- At minimum, exclude `feeCollector` from list accounting.

### Proof of Concept
Hardhat/fork sketch:

```ts
// setup: pool with >=30 listed deposit tokens (depositToken[i])
const victim = bob.address
// attacker deposits 1 wei underlying in each token, then dusts the victim
for (const dt of depositTokens) {
  await underlying[i].approve(dt.address, 1)
  await dt.deposit(1, attacker.address)            // attacker gets dust
  await dt.transfer(victim, 1)                     // victim list += 1
}
// victim's combined depositTokensOfAccount + debtTokensOfAccount == 30
// any new first-time addition reverts:
await expect(
  newDepositToken.deposit(parseEther('1'), victim) // _mint -> addToDepositTokensOfAccount
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// feeCollector variant:
for (const dt of depositTokens) await dt.transfer(feeCollector, 1)
await expect(
  depositTokenNotYetInList.withdraw(amount, alice.address) // fee _transfer to feeCollector
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Note: a full reproduction requires a deployed pool whose registered deposit+debt token count lets the attacker drive a target to the 30-entry cap; on pools with few listed tokens the attack only consumes part of the victim's allowance and the DoS is partial.
