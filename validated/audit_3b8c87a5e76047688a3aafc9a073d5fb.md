Audit Report

## Title
`pallet-dap::drip_issuance` permanently drops inflation past `MaxElapsedPerDrip` because `LastIssuanceTimestamp` advances to `now` instead of `last + max_elapsed` - (File: substrate/frame/dap/src/lib.rs)

## Summary
`drip_issuance` clamps `elapsed` to `MaxElapsedPerDrip` before minting via `IssuanceCurve::issue(total_issuance, elapsed)`, but unconditionally sets `LastIssuanceTimestamp` to the uncapped `now` rather than to `last + max_elapsed`. The un-minted remainder of elapsed time beyond the ceiling is neither minted immediately nor deferred to a future drip — it is silently and permanently lost.

## Finding Description
In `drip_issuance`, `elapsed = now - last` is computed, then clamped to `max_elapsed` if it exceeds the ceiling (emitting `ElapsedClamped`), and `mint_and_distribute(elapsed)` mints/distributes issuance based on the clamped value only. [3](#0-2)  Immediately before minting, `LastIssuanceTimestamp::<T>::put(now)` sets the tracked timestamp to the full, uncapped `now`, not to `last.saturating_add(max_elapsed)`. [4](#0-3)  Consequently, the window `[last + max_elapsed, now]` is never accounted for on this or any subsequent drip, because the next drip's `elapsed` calculation starts from the already-advanced `now`. `mint_and_distribute` mints strictly based on the passed-in `elapsed` and distributes to budget recipients (buffer, staking reward pot, etc.) proportionally, so the lost window directly reduces recipients' payouts with no recovery mechanism. [2](#0-1)  `on_initialize` is the only caller of this logic, so this executes automatically on every block without any attacker or privileged action once a gap between drips exceeds `MaxElapsedPerDrip`.

## Impact Explanation
This is a runtime bug that compromises intended issuance/payout behavior: budget recipients (staking rewards, treasury/buffer, validator incentive pots) permanently receive less inflation than the `IssuanceCurve` intends whenever the gap between drips exceeds `MaxElapsedPerDrip`, e.g., due to chain downtime, throttled block production, or a low `MaxElapsedPerDrip` configuration. Because `LastIssuanceTimestamp` jumps past the un-minted window instead of stopping at the boundary of what was actually minted, the shortfall cannot be recovered automatically; only a manual, one-off governance migration (as done for the V1→V2 path) can catch it up.

## Likelihood Explanation
No adversarial action is needed — any real-world block-production stall or outage exceeding `MaxElapsedPerDrip` triggers this on the very next `on_initialize` call. The pallet's own test `elapsed_ceiling_is_applied` demonstrates the exact loss (1000 minted instead of 2000 for a 20-minute gap against a 10-minute ceiling) and the authors' own PR doc for `pr_11809` confirms they identified and fixed this precise defect for the migration seeding path but left the general recurring drip path unfixed.

## Recommendation
When `elapsed` is clamped to `max_elapsed`, advance `LastIssuanceTimestamp` by `last.saturating_add(max_elapsed)` instead of the full `now`, preserving the un-minted remainder as outstanding elapsed time to be credited (subject to the ceiling again) on the next drip — mirroring the catch-up semantics already implemented in `MigrateV1ToV2`.

## Proof of Concept
Using `substrate/frame/dap/src/tests/drip.rs`'s existing test infrastructure: configure `MaxElapsedPerDrip = 600_000` ms and advance mock time by `1_200_000` ms before calling `drip_issuance`, as `elapsed_ceiling_is_applied` does — this mints only 1000 units instead of the 2000 units a full 20-minute accrual would produce, and `ElapsedClamped` fires. [5](#0-4)  Advancing time again and calling `drip_issuance` a second time confirms the missing 10 minutes of accrual from the first call is never minted, because `LastIssuanceTimestamp` was already set to the full `now` in the first call.
