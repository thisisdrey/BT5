### Title
Priority computed from self-declared, unaffordability-unchecked compute-unit-price lets attacker packets always evade the `SchedulerPriorityFloor` while consuming full sigverify CPU - (File: core/src/sigverify.rs, core/src/transaction_priority.rs)

### Summary
`apply_priority_floor_to_batch` drops packets only when `calculate_priority_from_bytes` returns `Some(priority) if priority <= floor`; any packet that either fails to parse (returns `None`) or reports a priority above the floor is unconditionally kept and passed on to the expensive `ed25519_verify_serial` step. Because the priority is computed purely from the `ComputeBudgetInstruction::set_compute_unit_price` value embedded in the (fully self-controlled) transaction bytes — with no check that the declared fee payer can actually afford it — an attacker can trivially set an arbitrarily large `compute_unit_price` (or send otherwise-unparseable bytes) to guarantee `priority > floor` (or `None`) on every packet, defeating the floor's load-shedding purpose entirely.

### Finding Description
`SigVerifyWorkerPool::run_transaction_task` calls `apply_priority_floor_to_batch` before `sigverify::ed25519_verify_serial` when a non-zero floor is published [1](#0-0) . The floor check itself only discards a packet when its computed priority is `<= floor`; unparseable packets and any priority strictly greater than the floor are left in the batch ("any_kept = true") and therefore always proceed to full signature verification [2](#0-1) .

The priority value is produced by `calculate_priority_from_bytes`, which parses the raw packet bytes into a `SanitizedTransactionView`/`RuntimeTransaction`, extracts the `TransactionConfiguration` (which includes `priority_fee_lamports`, itself derived from the attacker-supplied `ComputeBudgetInstruction::set_compute_unit_price` value), and computes `reward / (1 + cost)` [3](#0-2) [4](#0-3) . Nothing in this path checks the fee payer's account balance or ability to actually pay the declared price — it is a pure function of the packet bytes themselves. Since `compute_unit_price` is an arbitrary `u64` chosen by the packet's author, and the packet only needs to be well-formed/sanitizable (not properly funded or ultimately executable), an attacker can set `compute_unit_price = u64::MAX` (or similarly outsized) on every flooded packet to guarantee `priority` exceeds whatever floor the scheduler has published, or can send bytes that fail to parse (e.g., truncated/garbage `[u8; 32]`, as shown by the existing test `priority_from_bytes_returns_none_for_garbage`), which also returns `None` and is unconditionally kept per the explicit "leave to downstream stages to reject" comment.

In both cases the packet reaches `sigverify::ed25519_verify_serial`, doing the full expensive per-packet cryptographic work regardless of whether the packet's real priority/fee would have been at or below the floor, and regardless of whether the transaction could ever be admitted or executed (insufficient funds is only checked much later in banking stage/SVM). This defeats the stated purpose of the floor: "when saturated, the scheduler publishes the queue-min transaction's priority and workers drop at-or-below-floor arrivals here, ahead of signature verification" [5](#0-4) .

### Impact Explanation
An unstaked remote attacker opening a TPU QUIC/UDP connection can flood packets with an artificially inflated (or unparseable) declared priority so the pre-sigverify load-shedding floor never triggers on their traffic, forcing every worker to do full `ed25519_verify_serial` on every attacker packet even under sustained flood and high floor conditions. This degrades ingress throughput for legitimate, actually-fundable transactions — a denial-of-service against sigverify worker CPU capacity, consistent with the QoS-evasion / grossly-underpriced-pre-fee-work category in scope.

### Likelihood Explanation
Fully attacker-controlled and requires no special privileges: the attacker only needs to craft a valid-enough `VersionedTransaction` (satisfying `sanitize_config()`/`RuntimeTransaction::try_new`) with a huge `set_compute_unit_price` instruction and any signer/dummy account as fee payer — no funds are required to achieve a high computed priority. It is also trivially repeatable at line rate since crafting such packets costs the attacker nothing extra. The condition requires `floor > 0`, i.e., the scheduler queue is already saturated/under load — exactly the condition where the floor mechanism is supposed to provide protection, making the bypass most damaging when it matters most.

### Recommendation
Do not rely solely on self-declared priority for the floor gate. Options: (1) bound the maximum `compute_unit_price`/priority credited for the floor comparison against some sanity ceiling or require it be consistent with recently-observed real-market caps; (2) perform a cheap, bounded fee-payer existence/balance sufficiency check (not full lock/execution) before granting "above floor" status, so priority cannot be claimed without at least plausible ability to pay; (3) treat `None` (unparseable) packets from `calculate_priority_from_bytes` as equivalent to zero priority (drop them at the floor) rather than unconditionally keeping them, since they will be rejected downstream anyway and currently get a free pass on the floor.

fn apply_priority_floor_to_batch(
    batch: &mut PacketBatch,
    floor: u64,
    bank: &Bank,
) -> (usize, bool) {
    let mut dropped: usize = 0;
    let mut any_kept = false;
    for mut packet in batch.iter_mut() {
        if packet.meta().discard() {
            continue;
        }
        let Some(data) = packet.data(..) else {
            // Zero-length or otherwise unreadable: leave to downstream
            // stages to reject.
            any_kept = true;
            continue;
        };
        // Unparseable packets are kept and left for downstream rejection.
        match calculate_priority_from_bytes(bank, data) {
            Some(priority) if priority <= floor => {
                packet.meta_mut().set_discard(true);
                dropped = dropped.saturating_add(1);
            }
            _ => any_kept = true,
        }
    }
    (dropped, !any_kept)

pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
    let fee_details = solana_fee::calculate_fee_details(
        transaction,
        bank.fee_structure().lamports_per_signature,
        transaction_configuration.priority_fee_lamports,
        bank.fee_features(),
    );
    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    (
        reward
            .saturating_mul(MULTIPLIER)
            .saturating_div(cost.saturating_add(1)),
        cost,
    )
}

pub(crate) fn calculate_priority_from_bytes(bank: &Bank, data: &[u8]) -> Option<u64> {
    let view = SanitizedTransactionView::try_new_sanitized(data, &sanitize_config()).ok()?;
    let runtime_tx = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    )
    .ok()?;
    let transaction_configuration = runtime_tx
        .transaction_configuration(&bank.feature_set)
        .ok()?;
    let (priority, _cost) =
        calculate_priority_and_cost(bank, &runtime_tx, &transaction_configuration);

    Some(priority)
}
