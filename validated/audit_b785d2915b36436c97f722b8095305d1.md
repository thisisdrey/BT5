### Title
Unreleased `EntryBytesBudget` reservation permanently burns leader block-space capacity on record failure - (File: `runtime/src/bank/entry_bytes_budget.rs`)

### Summary
`EntryBytesBudget` only exposes a `reserve()` method that atomically bumps a monotonically increasing `consumed` counter against a fixed `slot_limit`; there is no corresponding release/refund method anywhere in the type. [1](#0-0)  `Consumer::execute_and_commit_transactions_locked` reserves bytes for a batch of *processed* transactions before attempting to record them into PoH, but if the subsequent `record_transactions` call fails, the code rolls back the cost-tracker state and marks transactions retryable — yet it never releases the entry-bytes it already reserved. [2](#0-1) 

### Finding Description
The flow is:
1. `entry_bytes` is computed as the serialized size of all transactions that were actually processed in the batch. [3](#0-2) 
2. `bank.entry_bytes_budget().reserve(entry_bytes)` atomically adds this to the `consumed` counter, subject to `slot_limit`, and cannot be undone. [4](#0-3) 
3. If the reservation succeeds, `record_transactions` is invoked to actually write the entry into PoH. [5](#0-4) 
4. If recording fails for any reason, `remove_added_transaction_costs` is called to roll back the cost tracker, and the transactions are marked retryable — but the `entry_bytes_budget` consumption is never rolled back. [6](#0-5) 

This mirrors the RToken bug class exactly: a scarce, per-period resource limit (`allVestAt` in RToken; `entry_bytes_consumed` here) is advanced/consumed based on a user-influenced quantity (issuance amount / transaction batch size), and the "cancel"/failure path (RToken's `cancel`; banking stage's record failure + retry) refunds the other tracked state (deposited tokens / cost tracker) but leaves the byte-budget counter un-refunded. Because there is no `release`/`unreserve` API at all in `EntryBytesBudget`, this is not merely a missed call on one path — the type structurally cannot be decremented once bytes are reserved.

### Impact Explanation
`entry_bytes_budget` gates how many bytes of transaction data the leader may still pack into entries for the remainder of the current slot (`slot_limit` per `SlotParams::max_entry_bytes_per_slot`, e.g. 10–20 MiB). [7](#0-6) [8](#0-7)  Any batch whose bytes are reserved but whose recording subsequently fails permanently reduces the remaining capacity for the rest of that leader slot without ever contributing a recorded entry. Repeated occurrence within a slot can exhaust the entire `slot_limit`, causing the leader to reject/blocks entry-recording for legitimate transactions for the remainder of its slot (`EntryBytesReserveError::ExceedsSlotLimit` → `PohRecorderError::MaxHeightReached`), effectively reducing realized block space/throughput.

### Likelihood Explanation
This is bounded in scope compared to the original RToken finding (RToken's `allVestAt` accumulates indefinitely across blocks; here `entry_bytes_consumed` resets every slot since a fresh `EntryBytesBudget` is constructed for each new bank). [9](#0-8)  The griefing window is therefore limited to a single leader slot rather than "a very long time." Triggering the failure path repeatedly and predictably (rather than via natural end-of-slot `MaxHeightReached` races) would require further investigation into how often `record_transactions` fails for reasons other than the slot simply ending, which could not be fully verified within the scope of this exploration (the `transaction_recorder.rs`/`poh_recorder.rs` failure paths were not read due to iteration limits). This uncertainty lowers confidence that an unprivileged user can reliably and repeatedly hit this path at will versus it only occurring incidentally near slot boundaries (which would have limited additional impact beyond the natural end of leader duties).

### Recommendation
Add a `release`/`unreserve` method to `EntryBytesBudget` that subtracts the previously reserved amount from `consumed`, and call it in `Consumer::execute_and_commit_transactions_locked` whenever `record_transactions` fails after a successful reservation, symmetric to how `remove_added_transaction_costs` already rolls back the cost tracker on the same failure path.

### Proof of Concept
Not independently reproduced; based on static code-path analysis of `EntryBytesBudget::reserve` (no release counterpart exists in the type) and `Consumer::execute_and_commit_transactions_locked`, which rolls back cost-tracker state on `record_transactions` failure but omits any entry-bytes rollback. [4](#0-3) [6](#0-5)  Full verification of how frequently/reliably `record_transactions` can be made to fail post-reservation by an unprivileged actor was not completed due to tool-iteration limits; a Devin session with repository access could trace `TransactionRecorder::record_transactions` and `PohRecorderError` variants to confirm exploitability and construct a runnable test.

#[derive(Debug)]
pub struct EntryBytesBudget {
    consumed: AtomicU64,
    slot_limit: u64,
}

impl EntryBytesBudget {
    pub const fn new(slot_limit: u64) -> Self {
        Self {
            consumed: AtomicU64::new(0),
            slot_limit,
        }
    }

    pub const fn slot_limit(&self) -> u64 {
        self.slot_limit
    }

    pub fn reserve(&self, bytes: u64) -> std::result::Result<(), EntryBytesReserveError> {
        loop {
            let current = self.consumed.load(Ordering::Acquire);
            let next = current.saturating_add(bytes);
            if next > self.slot_limit {
                return Err(EntryBytesReserveError::ExceedsSlotLimit);
            }

            if self
                .consumed
                .compare_exchange(current, next, Ordering::AcqRel, Ordering::Acquire)
                .is_ok()
            {
                return Ok(());
            }
        }
    }
}
