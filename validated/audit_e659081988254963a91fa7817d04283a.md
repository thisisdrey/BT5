### Title
Fixed-interval `/proc` polling in `BurdenMonitor` allows attackers to evade load-shedding resource accounting by bursting short-lived Git subprocesses between polls - (File: internal/burdenmonitor/poller.go)

### Summary
The bug class in the external report is that a value used to make a security/economic decision (the TWAP price) is derived from a sampling window that can shrink to a single observation point, letting an attacker who controls exactly that narrow window inject an unrepresentative value that the consumer trusts as if it were an averaged/stable measurement. The same "narrow, attacker-timeable observation window feeding a trust decision" pattern exists in Gitaly's `BurdenMonitor`, which snapshots per-process CPU/memory usage from `/proc/[pid]` on a fixed `2s` ticker and only accounts for processes that are still alive at the instant of the poll [1](#0-0) .

### Finding Description
`BurdenMonitor` is the data-collection component that the load shedder and resource-limiting/DoS-protection layer rely on to decide which in-flight RPC/process is "costly" and should be throttled or cancelled [2](#0-1) . Its poll loop wakes up every `defaultPollInterval` (2 seconds) and reads `/proc/<pid>/stat` and `/proc/<pid>/status` for every command currently tracked in each `RPCEntry.Commands` map [3](#0-2) [4](#0-3) .

Because the poll is a single instantaneous snapshot on a fixed interval, a Git subprocess that starts and finishes strictly *within* one polling interval is registered and completed without ever being observed by `pollEntryCommands`, so its CPU/memory usage is only accounted for via `MarkCommandCompleted`'s "final consumption" bookkeeping rather than being visible as an in-flight, high-cost sample used to rank/select victims in real time. This is explicitly acknowledged as a known limitation in Gitaly's own architecture documentation: "Short-lived commands may complete before `/proc` is ever polled. This is acceptable as the commands that cause resource contention are mostly the long-running ones." [5](#0-4) 

This is directly analogous to the TWAP finding: just as an attacker can pump a price and hold it for exactly one observation block so the oracle's window captures only the manipulated single sample, an attacker driving an ordinary Gitaly RPC (e.g. any RPC that lets them influence spawned Git subprocess behavior, or repeated RPC invocations that spawn many cheap/short commands in bursts) can time bursts of resource-intensive but short-lived commands to complete inside the ~2s gap between ticks. The load shedder's `EntriesSortedBy(CPU)`/`SnipeTopN()` decision path, which depends on `BurdenMonitor`'s live snapshot, never sees these commands as "currently expensive," so it cannot select them for cancellation, defeating the very purpose of the load-shedding defense against resource exhaustion [6](#0-5) .

### Impact Explanation
The `BurdenMonitor`/Load Shedder pair exists specifically to protect Gitaly from being overwhelmed and to identify and cancel the RPCs actually causing resource pressure during a DDoS-style incident [7](#0-6) . If an attacker (an ordinary, unprivileged client capable of issuing repeated RPCs that spawn Git subprocesses) can structure their load as many short, CPU/memory-intensive bursts each shorter than the poll interval, the highest-cost-ranking mechanism used to snipe the actual offenders will not "see" them, so:
- The load shedder cannot correctly identify and cancel the attacker's requests when critical thresholds are hit, undermining the RPC-handler resource-limiting/DoS mitigation described in `doc/load-management-architecture.md`.
- Prometheus metrics and canonical log lines fed by `BurdenMonitor` under-report the attacker's actual resource consumption, which can also blind on-call responders during an incident.

### Likelihood Explanation
Any authenticated Gitaly client can trigger arbitrary Git subprocess execution via normal RPCs (clones, fetches, `pack-objects`, etc.), and the poll interval (2s) is a fixed, publicly documented value, making the timing window predictable and simple to exploit without any special access. The documentation itself flags this exact scenario as an accepted tradeoff rather than a hardened guarantee, indicating the gap is real and not an edge case.

### Recommendation
Do not rely solely on point-in-time `/proc` snapshots taken at a fixed interval for cost/priority decisions. Track cumulative CPU/memory consumption continuously (e.g., accumulate deltas each time a command is observed, and also account for the delta of *any* command's total lifetime consumption—not just the last sample—when it completes, so bursts entirely between two polls are reflected in the entry's aggregate). Consider shortening the polling interval adaptively under high load, or hooking into `wait4`/`getrusage`-style exit statistics so short-lived process resource usage is always captured on completion regardless of poll timing, similar to how the Uniswap-style TWAP fix recommends deriving values from cumulative counters rather than instantaneous window samples.

### Proof of Concept
1. Configure `BurdenMonitor` with the default 2-second poll interval, as done via `StartPoller` [8](#0-7) .
2. Issue repeated RPCs that each spawn a short, resource-intensive Git subprocess (e.g., many `git cat-file`/`git rev-list` invocations chained back-to-back) such that each individual process starts and exits within well under 2 seconds, but the aggregate rate of such processes drives sustained high CPU/memory usage on the node.
3. Because `pollEntryCommands` only reads `/proc/<pid>` for PIDs present in `entry.Commands` at the instant the ticker fires [4](#0-3) , most of these short commands complete and are removed before ever being sampled, so `EntriesSortedBy(CPU)` under-ranks this RPC entry relative to its true resource cost, and `SnipeTopN()` fails to select it for cancellation even while the node is under critical pressure.

```go
func (bm *BurdenMonitor) pollLoop(ctx context.Context, interval time.Duration) {
	ticker := time.NewTicker(interval)
	defer ticker.Stop()
	logTicker := time.NewTicker(defaultLogInterval)
	defer logTicker.Stop()

	for {
		ticker.Reset(interval)
		select {
		case <-ctx.Done():
			return
		case <-ticker.C:
			bm.pollAllEntries()
		case <-logTicker.C:
			bm.logStats()
		}
	}
}
```

```go
func (bm *BurdenMonitor) pollEntryCommands(entry *RPCEntry) {
	entry.mu.Lock()
	defer entry.mu.Unlock()

	for pid, cmd := range entry.Commands {
		stats, err := readProcessStats(pid)
		if err != nil {
			bm.logger.WithFields(log.Fields{
				"pid":   pid,
				"error": err,
			}).DebugContext(entry.Context, "failed to read process stats")
			continue
		}

		cmd.UserTime = stats.UserTime
		cmd.SystemTime = stats.SystemTime
		cmd.WallTime = time.Since(cmd.StartTime)
		cmd.AnonRSS = stats.AnonRSS
	}
}
```

```markdown
### BurdenMonitor

This component would figure out which RPC/process is causing stress.

- Tracks all in-flight RPCs via gRPC interceptors: registers on entry,
  deregisters on exit
- Tracks spawned commands via the Git command factory
- Polls per-process stats from `/proc/[pid]/stat` and `/proc/[pid]/status`
  every x seconds using a single ticker and a bounded worker pool. This is
  primarily useful for long-running commands (large clones). Short-lived
  commands may complete before `/proc` is ever polled. This is acceptable as
  the commands that cause resource contention are mostly the long-running ones.
  A single ticker seems to be sufficient: benchmarks on a production node show ~250ms to
  read `/proc` for 209 concurrent Git processes. At the observed peak of ~1170
  processes during a DDoS incident, sequential polling extrapolates to ~1.4s —
  within the 2s interval but with thin margin. A bounded worker pool should parallelise the reads to stay well within the interval at peak load.
- Maintains ordered lists of running requests sorted by CPU time, memory,
  and duration
- Also addresses the need for periodic logging of long-running command
  resource consumption
  ([#7097](https://gitlab.com/gitlab-org/gitaly/-/work_items/7097)) -
  the BurdenMonitor already has the data, it just needs to emit periodic
  log entries for the top-N consumers
```

```markdown
### Load Shedder

The concurrency rate limiter reduces the flow of incoming requests when resources are
constrained, while load shedder controls in-flight requests. When resource pressure exceeds critical thresholds despite admission control, the load shedder identifies the
highest-cost running requests and cancels them to free resources
immediately.

- Subscribes to LoadMonitor notifications with critical thresholds (e.g.,
  OOM events, sustained extreme CPU throttle)
- When triggered, queries BurdenMonitor for the highest-cost running
  requests
- Cancels specific request contexts to recover capacity
```
