### Title
Unhardened Bancor-formula exchange math (`ExchangeProcessor`) permits unbacked-balance draining / permanent trading DoS when `allowHardenExchangeCalculation` is not enabled - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The TRC10 `Exchange` (Bancor-style AMM) computes trade output using floating-point `Math.pow` with fixed exponents (`0.0005` and `2000.0`), exactly the same class of bug as the reported `vrgdac.xToY`/`yToX` precision blow-up: a fixed-point/floating-point power computation that degrades or becomes undefined as pool state drifts away from initial assumptions, and whose result is trusted without bounds-checking unless a hardening flag is enabled.

### Finding Description
`ExchangeProcessor.exchangeToSupply` and `exchangeFromSupply` implement the Bancor "relay-token" curve using raw `double` math: [1](#0-0) 

`ExchangeCapsule.transaction()` calls this processor and only guards against a corrupted (negative) resulting balance when `hardenedCalc` is true: [2](#0-1) 

`hardenedCalc` is derived from `allowHardenExchangeCalculation()`, a chain parameter gated behind an `AbstractExchangeActuator.allowHarden()` check that is itself governed by a committee proposal (`ProposalUtil`, `ProposalService`): [3](#0-2) 

`ExchangeTransactionActuator.execute`/`doValidate` pass `dynamicStore.allowStrictMath()` and `allowHarden()` straight into `exchangeCapsule.transaction(...)`, and only catch `ArithmeticException`, not silent numeric corruption from `double` overflow/`NaN`/`Infinity`: [4](#0-3) 

As in the reported `vrgdac` issue, this is a case where a power-law pricing formula is evaluated on values that can legitimately grow far from the parameters' intended operating range (pool balances drift heavily from their initial ratio, or the relative trade size becomes large as the pool is used over time). At extreme ratios, `1.0 + quant/newBalance` raised to `2000.0` can reach `Double.POSITIVE_INFINITY`, and casting that to `long` yields `Long.MAX_VALUE`; feeding this into `balance * (powResult - 1.0)` and truncating back to `long` produces an arbitrary/overflowed `long` value that is not sanity-checked unless hardening is enabled. The project's own `SafeExchangeProcessor` (BigDecimal-based) and the `hardenedCalc` negative-balance check in `ExchangeCapsule.transaction()` were clearly added specifically to address this precision/overflow class of bug, confirming it is a real, previously-identified root cause in this codebase — but the fix is opt-in via governance and the legacy path remains reachable for any exchange until the proposal is passed.

### Impact Explanation
If a legacy (non-hardened) exchange pool is pushed into an extreme balance ratio (achievable by an unprivileged trader repeatedly executing `ExchangeTransactionContract`/`ExchangeInjectContract`, both broadcastable by anyone), the floating-point Bancor computation can silently overflow to `Infinity`/`NaN` and be truncated into an untrusted `long`. Without the `hardenedCalc` negative-balance guard, this value is written directly into the exchange's on-chain balances and paid out to the trader's account (`accountCapsule.addAssetAmountV2` / `setBalance`), allowing the attacker to receive assets not backed by the pool (unbacked balance / theft) or corrupt the pool's balances so severely that further trading permanently reverts (mirroring the reported `buyToken` "always reverts after N days" scenario), effectively freezing the pool's trading function while the corrupted balances remain unresolved.

### Likelihood Explanation
The path is reachable by any account that can create/inject into an `Exchange` and issue `ExchangeTransactionContract` transactions — no special privilege required. It requires driving the pool into an extreme state, which is more effort than the original C4 report's simple time-based trigger, and only manifests when the network-wide `allowHardenExchangeCalculation` parameter has not yet been enabled by committee proposal. Given the mitigation (`SafeExchangeProcessor`, `hardenedCalc` checks) already exists in-code but is proposal-gated, likelihood depends on current mainnet proposal state, which cannot be verified from the repository alone.

### Recommendation
- Make the hardened, `BigDecimal`-based exchange calculation (`SafeExchangeProcessor`) and the negative-balance check in `ExchangeCapsule.transaction()` mandatory (not conditional on a governance flag), or ensure the corresponding proposal is enabled by default for all networks.
- Add explicit bounds/finite checks (`Double.isFinite`) on the results of `Math.pow` in `ExchangeProcessor` before they are used to mutate balances, rejecting the transaction rather than truncating overflowed doubles into `long`.
- Add regression tests that drive exchange pools to extreme balance ratios (as done in `ExchangeProcessorTest.testHardenedLargeQuant`) against the *unhardened* path to confirm no unbacked balance or state corruption can occur even when hardening is disabled.

### Proof of Concept
Not independently executable from the indexed code (no local build/test harness available in this session), but the existing test `ExchangeProcessorTest.testStrictMath` demonstrates that hardened and unhardened processors already diverge in output for the same inputs: [5](#0-4) 
and `testHardenedLargeQuant`/`testSafeProcessorNoOvershootForTypicalInputs` show the hardened path was specifically built to bound results that the legacy `double`-based `ExchangeProcessor` does not bound: [6](#0-5) 
Reproducing the overflow concretely (choosing `sellTokenBalance`, `buyTokenBalance`, and `sellTokenQuant` such that `1 + quant/newBalance` raised to the `2000` exponent overflows `double`) would require running `ExchangeProcessor.exchange` directly in a Java test harness, which is outside the scope of this read-only analysis.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  public void testHardenedLargeQuant() {

    long buyBalance = 1_000_000_000_000L;
    long sellQuant = 1_000_000_000_000L; // 100% of sell balance

    long result = SafeExchangeProcessor.INSTANCE.exchange(sellBalance, buyBalance, sellQuant);

    Assert.assertTrue("Result must be less than buy balance", result < buyBalance);

  @Test
  public void testSafeProcessorNoOvershootForTypicalInputs() {
    // Verify across realistic inputs that hardened result never exceeds buy reserve.
    long[][] data = {
        {100_000_000L, 100_000_000L, 1_000_000L},
        {1_000_000_000L, 1_000_000_000L, 100_000L},
        {1L, 10_140_000_000_000L, 2_897_000_000_000L},
        {903L, 737L, 50L},
    };
    for (long[] row : data) {
      long result = SafeExchangeProcessor.INSTANCE.exchange(row[0], row[1], row[2]);
      Assert.assertTrue("Result must be non-negative", result >= 0);
      Assert.assertTrue("Result must not exceed buy reserve, got " + result + " > " + row[1],
          result <= row[1]);
    }
  }
