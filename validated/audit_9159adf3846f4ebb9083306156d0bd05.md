## Title
Unhardened Bancor-style exchange math in `ExchangeProcessor` can produce financially-inconsistent (unbacked) results via floating-point edge cases when the hardened path is not enabled - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The ImageMagick advisory describes undefined behavior caused by unvalidated arithmetic (values escaping the expected range and division producing indeterminate results) that is reachable through attacker-supplied input. The closest reachable analog in java-tron is the default (non-hardened) TRC10 exchange pricing engine, `ExchangeProcessor`, used by `ExchangeCapsule.transaction()` [1](#0-0) , which performs `double`-based division and `Math.pow` operations without overflow/NaN/Infinity checks, and silently narrows the result with `(long)` casts [2](#0-1) . This path is directly reachable by any account through `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`.

### Finding Description
`ExchangeProcessor.exchangeToSupply()` and `exchangeFromSupply()` compute:
```
double issuedSupply = -supply * (1.0 - Math.pow(1.0 + (double) quant / newBalance, 0.0005));
...
double exchangeBalance = balance * (Math.pow(1.0 + (double) supplyQuant / supply, 2000.0) - 1.0);
``` [2](#0-1) 

Neither `exchangeToSupply` nor `exchangeFromSupply` validates that `newBalance` or the running `supply` variable stay within safe bounds before dividing, nor do they check the result of `Math.pow` for `Infinity`/`NaN` before the final `(long)` cast. This exactly mirrors the ImageMagick bug class: math operations (division, and here also `pow`) performed on values that can legitimately fall outside the type's safe range, producing undefined/out-of-range results that are then silently truncated into the target type.

The engineering team has already recognized this class of problem: a `SafeExchangeProcessor` exists that uses `BigDecimal`, `StrictMathWrapper.addExact/subtractExact`, and an explicit post-condition check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) [3](#0-2) , and `ExchangeCapsule.transaction()` only performs this bounds check `if (hardenedCalc && ...)` [4](#0-3)  — i.e., the safety check is skipped entirely unless `allowHarden()` is enabled. The unit tests explicitly document that the un-hardened `ExchangeProcessor` and the hardened `SafeExchangeProcessor` can produce **different results** for identical inputs (`testStrictMath`) [5](#0-4) , and that the hardened processor throws `ArithmeticException` on cases (e.g., overflow, division producing an arithmetic error) that the un-hardened processor does not guard against at all [6](#0-5) .

### Impact Explanation
When `allowHarden()` is false (i.e., before the corresponding committee proposal activates the hardened math on the network), any account executing `ExchangeTransactionContract` against `ExchangeProcessor` is exposed to floating-point edge cases (extreme quant/balance ratios bounded only by `dynamicStore.getExchangeBalanceLimit()`) that can drive `Math.pow` results toward `Infinity`/very large magnitudes, then get silently cast to `long`. Because the corresponding balance mutation in `ExchangeCapsule.transaction()` for the non-hardened path performs plain `+`/`-` with no negative-balance guard (`newFirstTokenBalance = firstTokenBalance + sellTokenQuant`, `newSecondTokenBalance = secondTokenBalance - buyTokenQuant`, checked only `if (hardenedCalc ...)`) [7](#0-6) , this can push the exchange's internal balances to negative or otherwise inconsistent state, letting a user receive tokens the exchange pool does not actually back — an unbacked-balance/fund-theft class impact directly reachable from a single signed transaction.

### Likelihood Explanation
This requires the network to still be operating with `allowHarden()` disabled (the default/legacy behavior) and requires an attacker to construct an exchange pair with a deliberately small counter-token reserve (achievable since anyone can create their own TRC10 asset and its paired exchange), then submit a single `ExchangeTransactionContract`/`ExchangeInjectContract` with `tokenQuant` near the configured `exchangeBalanceLimit`. This is entirely achievable by an unprivileged asset issuer/order placer with no special permissions — only bounded by the `getExchangeBalanceLimit()` governance parameter, which was not verified in this pass to be low enough to fully neutralize the ratio.

### Recommendation
- Make the hardened (`SafeExchangeProcessor`) path the unconditional default rather than gating it behind `allowHarden()`, or force its activation as part of a mandatory hard fork rather than an optional committee proposal.
- Add explicit `Double.isInfinite`/`Double.isNaN` checks after every `Math.pow`/division in `ExchangeProcessor` and reject the transaction instead of silently truncating via `(long)` cast.
- Enforce the same "resulting balance must be ≥ 0" invariant unconditionally in `ExchangeCapsule.transaction()`, not only when `hardenedCalc` is true.

### Proof of Concept
Not independently verified end-to-end in this pass — this analysis is based on static code review of `ExchangeProcessor`, `ExchangeCapsule.transaction()`, `SafeExchangeProcessor`, and the `ExchangeTransactionActuator`/`ExchangeWithdrawActuator`/`ExchangeInjectActuator` validation paths. I was not able to confirm within the available iterations (a) the concrete default value of `dynamicStore.getExchangeBalanceLimit()` (which bounds the achievable quant/balance ratio and therefore the practical exploitability of the floating-point edge case), or (b) whether `allowHarden()` is already active by default/hard-forked in this snapshot of the codebase (its activation mechanism is a `ProposalUtil`-controlled dynamic parameter). Because I could not confirm these two facts, I cannot state with certainty that this analog is currently exploitable on a live, properly configured network — it is a legitimate code-level analog to the reported bug class (unchecked arithmetic on attacker-influenced values, silently truncated across type boundaries), but confirming a concrete unauthorized-fund-theft PoC would require checking the live/deployed value of `getExchangeBalanceLimit()` and the activation status of `allowHarden()`, which are runtime/governance-controlled and not fully determinable from static code alone.

    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;

          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

      throw new ContractValidateException("Exchange balance must be >=0 after transaction");

        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
