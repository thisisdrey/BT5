### Title
Unbounded Recursive Tree Walk in `GetTreeEntries` Causes Stack-Overflow DoS via Attacker-Crafted Deeply-Nested Tree Objects - (File: internal/git/localrepo/tree.go)

### Summary
The `TreeEntry.walk` function in `internal/git/localrepo/tree.go` recurses once per nesting level of a Git tree object without any depth limit. Because Git tree nesting depth is fully attacker-controlled (any client can construct arbitrarily deep tree chains via plumbing commands and push them to a repository Gitaly hosts), an ordinary user can trigger unbounded native call-stack recursion in a widely used RPC (`GetTreeEntries` with `Recursive=true`), leading to goroutine stack exhaustion and a crash/DoS of the serving `gitaly` process.

### Finding Description
`ReadTree` with `WithRecursive()` populates a `TreeEntry` tree structure via `populate()`, which itself is implemented iteratively using a `treeStack` to avoid recursion [1](#0-0) . However, once this nested `TreeEntry` structure is built, `sendTreeEntriesUnified` (backing the `GetTreeEntries` RPC) calls `tree.Walk(...)` to flatten it into response entries [2](#0-1) .

`Walk` delegates to the internal `walk` method, which is a genuine self-recursive function — one Go call-stack frame is consumed per level of tree nesting, with no bound on depth:

```go
func (t *TreeEntry) walk(dirPath string, callback func(path string, entry *TreeEntry) error) error {
	nextDirPath := filepath.Join(dirPath, t.Path)
	if err := callback(dirPath, t); err != nil {
		return err
	}
	for _, entry := range t.Entries {
		if err := entry.walk(nextDirPath, callback); err != nil {
			return err
		}
	}
	return nil
}
``` [3](#0-2) 

Unlike the bounded flat-path computation, which explicitly limits recursion depth (`defaultFlatTreeRecursion`, verified in tests as capped at 10 levels) [4](#0-3) , the full recursive `Recursive=true` code path in `GetTreeEntries` has no equivalent guard.

A tree's nesting depth is not restricted by Git itself: an attacker can locally build a chain of thousands (or hundreds of thousands) of single-child tree objects using ordinary plumbing commands (`git mktree`, `git hash-object -t tree`, or `fast-import`) and push the resulting objects to any repository they have write access to via `git-receive-pack`, since Gitaly's default connectivity checks do not restrict tree-nesting depth. When any client subsequently calls `GetTreeEntries` with `Recursive=true` against a revision containing such a tree, the server-side `walk` recursion depth matches the crafted nesting depth, exhausting the goroutine's stack and crashing the `gitaly` process (or the specific worker) servicing that RPC — analogous to the reported `_getRootNodeAndCompress` recursion-based stack-overflow DoS, but reached through a crafted Git object graph rather than crafted linked-list nodes.

### Impact Explanation
A successful exploitation causes a stack-overflow crash of the Gitaly process handling the RPC. Because `gitaly` processes typically serve many repositories/connections per node, a crash can disrupt service availability for other tenants co-located on that Gitaly node, constituting a denial-of-service condition triggerable by any user with push access to a single repository followed by a routine, unprivileged `GetTreeEntries` recursive call (used e.g. by GitLab's repository browser/API "get all files" features).

### Likelihood Explanation
Likelihood is moderate-to-high: creating a deeply nested tree object graph requires only standard Git plumbing tooling available to any client, no special repository permissions beyond ordinary push access, and no server-side validation currently rejects such structures. The vulnerable code path (`Recursive=true`) is a commonly used, ordinary feature of the `GetTreeEntries` RPC, not a privileged or maintenance-only API.

### Recommendation
Convert `TreeEntry.walk` to an iterative, explicit-stack traversal (mirroring the existing pattern already used in `populate()`'s `treeStack`), removing native call-stack recursion. Additionally, consider enforcing a maximum tree-nesting depth (mirroring the bounded `defaultFlatTreeRecursion` approach) for the fully recursive `GetTreeEntries` path, and/or bound resource usage (CPU/stack/time) per RPC handler so a single crafted request cannot destabilize the whole process.

### Proof of Concept
1. Using ordinary Git plumbing (or `git fast-import`), construct a chain of N single-entry tree objects `T0 → T1 → T2 → … → TN` (each tree containing exactly one sub-tree entry pointing to the next), with N in the tens/hundreds of thousands.
2. Attach `TN` as the root tree of a commit, and push this commit/branch to a Gitaly-hosted repository via normal `git push` (an ordinary write-access operation, no special hooks or unusual object types involved).
3. Invoke the `GetTreeEntries` RPC (`gitalypb.CommitServiceClient.GetTreeEntries`) against that commit with `Recursive: true`.
4. Server-side, `sendTreeEntriesUnified` builds the nested `TreeEntry` structure via `ReadTree(..., WithRecursive())` and then calls `tree.Walk(...)`, which recurses N times through `TreeEntry.walk`, exhausting the goroutine stack and crashing/aborting the Gitaly worker handling the request.

// populate scans through the output of ls-tree -r, and constructs a TreeEntry
// object.
func (t *TreeEntry) populate(
	ctx context.Context,
	repo *Repo,
) error {
	if t.OID == "" {
		return errors.New("oid is empty")
	}

	t.Entries = nil

	entries, err := repo.listEntries(
		ctx,
		git.Revision(t.OID),
		"",
		true,
	)
	if err != nil {
		return err
	}

	stack := treeStack{t}

	// The output of ls-tree -r is the following:
	// a1
	// dir1/file2
	// dir2/file3
	// f2
	// f3
	// Whenever we see a tree, push it onto the stack since we will need to
	// start adding to that tree's entries.
	// When we encounter an entry that has a lower depth than the previous
	// entry, we know that we need to pop the tree entry off to get back to the
	// parent tree.
	for _, entry := range entries {
		if levelsToPop := len(stack) - depthByPath(entry.Path); levelsToPop > 0 {
			for i := 0; i < levelsToPop; i++ {
				stack.pop()
			}
		}

		entry.Path = filepath.Base(entry.Path)
		stack.peek().Entries = append(
			stack.peek().Entries,
			entry,
		)

		if entry.Type == Tree {
			stack.push(entry)
		}
	}

	if err != nil {
		return fmt.Errorf("listing entries: %w", err)
	}

	return nil
}

func (t *TreeEntry) walk(dirPath string, callback func(path string, entry *TreeEntry) error) error {
	nextDirPath := filepath.Join(dirPath, t.Path)
	if err := callback(dirPath, t); err != nil {
		return err
	}

	for _, entry := range t.Entries {
		if err := entry.walk(nextDirPath, callback); err != nil {
			return err
		}
	}

	return nil
}

// Walk will walk the whole tree structure and call callback on every entry of
// the tree in a depth-first like fashion.
func (t *TreeEntry) Walk(callback func(path string, entry *TreeEntry) error) error {
	for _, e := range t.Entries {
		if err := e.walk(t.Path, callback); err != nil {
			return err
		}
	}

	return nil
}
