## Analysis

The reported bug class is: a protective invariant check for a voting-power/balance quantity is applied in one code path but inconsistently (or not at all) in a sibling code path that computes conceptually the same value, causing divergent voting-power accounting depending on entry point.

In java-tron, witness voting power ("TRON Power") used to cap the number of votes an account may cast is computed in three separate places, and the guard that decides between the "new" (`getAllTronPower()`) and "old" (`getTronPower()`) power calculation is inconsistent between them:

- `VoteWitnessActuator.validate()` (the regular on-chain `VoteWitnessContract` transaction path) gates the choice **only** on `supportAllowNewResourceModel()`: [1](#0-0) 

- `VoteWitnessProcessor.execute()` (the TVM native-contract `vote()` path, reachable by any smart contract via the `vote` precompile) gates the same choice on **both** `supportUnfreezeDelay()` **and** `supportAllowNewResourceModel()`: [2](#0-1) 

- `PrecompiledContracts.TotalVoteCount` (the read-only `totalVoteCount()` precompile query, reachable by any TVM caller) also gates on **both** flags, matching the processor rather than the actuator: [3](#0-2) 

Because `supportAllowNewResourceModel()` and `supportUnfreezeDelay()` are independent hard-fork proposal switches (each toggled by a separate `DynamicPropertiesStore` flag) [4](#0-3) , there can exist a window where `supportAllowNewResourceModel()` is `true` while `supportUnfreezeDelay()` is `false`. In that window:
- `VoteWitnessActuator` (plain transaction) uses `getAllTronPower()` as the vote ceiling.
- `VoteWitnessProcessor`/`TotalVoteCount` (TVM contract calls) use the narrower `getTronPower()` as the ceiling.

This is a direct analog of the reported inconsistency pattern: the same conceptual quantity (voting power used to gate an operation) is computed with a different, more permissive formula in one reachable code path (regular vote transaction) than in the parallel path (TVM vote/queries), so votes accepted through one entry point may not be validated the same way when read back through the other — an accounting inconsistency in SR election weight that is directly analogous in kind and root cause (inconsistent flash-loan-style protective condition across sibling balance/voting functions) to the reported Velodrome finding, though the original finding was similarly rated only Medium impact for the same reason (governance/tally divergence, not direct fund theft).

I could not fully verify from the index whether the two flags (`supportAllowNewResourceModel`, `supportUnfreezeDelay`) are always activated together in the same hard-fork proposal in production (which would make the divergence window practically unreachable) — the `DynamicPropertiesStore.java` proposal-activation logic for both flags was not fully retrievable via the tools available in this session. That is the key uncertainty for confirming actual exploitability/likelihood, and would need direct inspection of the proposal-activation code (`ProposalUtil`/`ForkController`) to confirm whether these two switches can genuinely diverge on any activated network.

### Title
Inconsistent TRON Power calculation guard between `VoteWitnessActuator` and `VoteWitnessProcessor`/`TotalVoteCount` - (File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java)

### Summary
The condition used to decide whether an account's voting-power ceiling should be computed via `getAllTronPower()` (new resource model, broader) or `getTronPower()` (legacy, narrower) differs between the plain-transaction vote path and the TVM/precompile vote path.

### Finding Description
`VoteWitnessActuator.validate()` selects `getAllTronPower()` solely based on `dynamicStore.supportAllowNewResourceModel()` [1](#0-0) , whereas the semantically equivalent gate in `VoteWitnessProcessor.execute()` (invoked when a smart contract calls the `vote()` native/precompiled operation) additionally requires `supportUnfreezeDelay()` to be true [2](#0-1) , matching the `TotalVoteCount` read-only precompile [3](#0-2) . If the two hard-fork switches are not enabled atomically, the vote ceiling enforced for a directly broadcast `VoteWitnessContract` transaction can differ from the ceiling enforced for the same account when voting or querying voting power via a TVM contract call.

### Impact Explanation
This is a governance/vote-accounting inconsistency, not direct fund theft: an account could be validated to cast votes against a broader "TRON Power" figure through one entry point while the read-side (`totalVoteCount`) or contract-vote entry point enforces a narrower figure, distorting SR election weight relative to actual resource holdings during the mismatch window.

### Likelihood Explanation
Requires the two independent hard-fork proposals (`ALLOW_NEW_RESOURCE_MODEL` and unfreeze-delay support) to be in a mismatched activation state on the live chain; whether that window is currently reachable on mainnet could not be confirmed with the tools available in this session.

### Recommendation
Make the tron-power selection guard identical across `VoteWitnessActuator`, `VoteWitnessProcessor`, and `PrecompiledContracts.TotalVoteCount` (i.e., all three should check the same combination of `supportAllowNewResourceModel()`/`supportUnfreezeDelay()`), consistent with the report's recommendation to keep such checks consistent across all related methods or remove the divergent check if no longer needed.

### Proof of Concept
Not independently reproduced; this analog is derived from static comparison of the three code paths cited above. A concrete PoC would require constructing a chain state where `supportAllowNewResourceModel()==true` and `supportUnfreezeDelay()==false` (or vice versa) and comparing vote validation results between a `VoteWitnessContract` transaction and an equivalent TVM `vote()` contract call for the same account.
