Mutable `UpdateSettingContract`/`UpdateEnergyLimitContract` Allow a Contract Owner to Rewrite Energy-Cost Allocation After Callers Have Already Broadcast Transactions - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateSettingContractActuator.java`, `actuator/src/main/java/org/tron/core/actuator/UpdateEnergyLimitContractActuator.java`)

### Summary
`UpdateSettingContractActuator` lets a deployed contract's `origin_address` change `consume_user_resource_percent` (0–100) at any time, with no time-lock, no cooldown, and no restriction on how often it can be called before every `TriggerSmartContract` transaction. [1](#0-0)  `UpdateEnergyLimitContractActuator` similarly lets the same owner change `origin_energy_limit` at any time. [2](#0-1)  Both values are read live, at the moment a caller's `TriggerSmartContract` is executed, to split energy cost between the contract owner and the caller.

### Finding Description
When an unprivileged user calls `TriggerSmartContract`, the energy cost split between them and the contract owner is computed from the contract's *current* `consume_user_resource_percent` and `origin_energy_limit` fields, fetched fresh from `ContractStore` at execution time in `VMActuator.getTotalEnergyLimitWithFixRatio` / `getTotalEnergyLimitWithFloatRatio`. [3](#0-2)  The same live value is read again at billing time in `TransactionTrace.pay()` to decide how much of the total energy usage is billed to the origin vs. the caller. [4](#0-3)  `ReceiptCapsule.payEnergyBill` then splits and burns the caller's/origin's frozen-energy or TRX balance according to that same percent. [5](#0-4) 

Neither actuator's `validate()` imposes a freeze period, a minimum interval between updates, or any notice mechanism — the owner can submit `UpdateSettingContract` (changing `consume_user_resource_percent` up to 100) or `UpdateEnergyLimitContract` (reducing `origin_energy_limit` to a minimal positive value) in the very same block as, or immediately before, a victim's already-broadcast `TriggerSmartContract` transaction is packed. This is structurally the same bug class as the reported `HarTokenSale.setWhitelistReserve()` issue: an allocation-determining parameter that other unprivileged parties rely on can be rewritten unilaterally and instantly by a single privileged party, with no consent, no time-lock, and no snapshot, directly before those parties' pending economic commitments are executed.

Unlike the token-sale case, the "commitment" here is a broadcast-but-unmined transaction (fee limit / expected cost) rather than a multi-day deposit window, but the mechanism and impact category are directly analogous: the contract owner can flip `consume_user_resource_percent` to 100 (or slash `origin_energy_limit` to near zero) between the time a caller signs/broadcasts a transaction with a given `fee_limit` and the time it executes, forcing the caller to pay energy fees they never intended and did not consent to, or causing their carefully calculated `fee_limit` to be insufficient and the transaction to fail (burning TRX for a reverted/out-of-energy execution).

### Impact Explanation
A malicious or economically incentivized contract owner can:
1. Watch the mempool for a pending `TriggerSmartContract` transaction with a `fee_limit` set on the assumption of the currently-published `consume_user_resource_percent`/`origin_energy_limit`.
2. Broadcast an `UpdateSettingContract` (percent → 100) or `UpdateEnergyLimitContract` (limit → very small) transaction with higher priority/energy to land in the same or an earlier block.
3. Cause the victim's transaction to consume far more of the victim's own frozen energy/TRX than expected (fee/allocation griefing), or to run out of energy and fail while the caller is still billed for consumed resources — an economic outcome the caller never agreed to, changed unilaterally and without warning by a party who does not have to compensate them.

This directly mirrors the report's "no consent mechanism or warning period" and "funds locked/committed under one set of rules, then rules change" pattern, but the funds at risk here are the caller's frozen/staked energy resources and TRX fees rather than sale deposits.

### Likelihood Explanation
Likelihood is significant for any actively-used dApp: `UpdateSettingContract`/`UpdateEnergyLimitContract` are ordinary, cheaply-broadcastable transactions requiring only that the sender be the contract's `origin_address` (checked in `validate()`), and no proposal/committee/timelock gate exists beyond a hard-fork feature flag (`ReceiptCapsule.checkForEnergyLimit`) for the energy-limit variant. [6](#0-5)  Any contract owner (a normal, unprivileged account from the chain's perspective) can exploit this against their own contract's callers at will, repeatedly, since there is no rate-limit as demonstrated by the existing `twiceUpdateSettingContract`/`twiceUpdateEnergyLimitContract` tests showing back-to-back updates succeed. [7](#0-6) [8](#0-7) 

### Recommendation
- Introduce a minimum interval (e.g., one maintenance cycle or a fixed number of blocks) between successive `UpdateSettingContract`/`UpdateEnergyLimitContract` calls for the same contract, analogous to freezing `whitelistReserve` after the sale opens.
- Alternatively, apply changes only from the *next* cycle/block onward (similar to how `UpdateBrokerageContract` changes only take effect for the next reward cycle via `DelegationStore`/`MaintenanceManager.doMaintenance`) rather than immediately for in-flight transactions. [9](#0-8) 
- Emit an event/track a "pending change" state so wallets and callers can detect an imminent parameter change and adjust `fee_limit` or defer submission.

### Proof of Concept
1. Deploy a contract `C` with `origin_address = A`, `consume_user_resource_percent = 0` (owner pays all energy) and `origin_energy_limit` set high.
2. User `B` observes these settings, computes an expected energy cost, and broadcasts `TriggerSmartContract(contract=C)` with a `fee_limit` sized only to cover `B`'s expected share (0%, since owner pays 100%).
3. Before `B`'s transaction is packed into a block, `A` broadcasts `UpdateSettingContract(contract=C, consume_user_resource_percent=100)`, landing in an earlier or the same block via `UpdateSettingContractActuator.execute` which writes the new percent directly to `ContractStore` with no delay. [10](#0-9) 
4. `B`'s `TriggerSmartContract` now executes with `consumeUserResourcePercent = 100`; `VMActuator.getTotalEnergyLimitWithFixRatio` and `TransactionTrace.pay()`/`ReceiptCapsule.payEnergyBill` bill 100% of the energy usage to `B` instead of `A`, causing `B`'s transaction to run out of energy (using the previously undersized `fee_limit`) or to burn far more TRX than `B` intended — with no recourse, since the change was unilateral and instantaneous. [11](#0-10)

  public void payEnergyBill(DynamicPropertiesStore dynamicPropertiesStore,
      AccountStore accountStore, ForkController forkController, AccountCapsule origin,
      AccountCapsule caller,
      long percent, long originEnergyLimit, EnergyProcessor energyProcessor, long now)
      throws BalanceInsufficientException {

    // Reset origin energy usage here! Because after stake 2.0, this field are reused for
    // recording pre-merge frozen energy for origin account. If total energy usage is zero, this
    // field will be a dirty record.
    this.setOriginEnergyUsage(0);

    if (receipt.getEnergyUsageTotal() <= 0) {
      return;
    }

    if (Objects.isNull(origin) && dynamicPropertiesStore.getAllowTvmConstantinople() == 1) {
      payEnergyBill(dynamicPropertiesStore, accountStore, forkController, caller,
          receipt.getEnergyUsageTotal(), receipt.getResult(), energyProcessor, now);
      return;
    }
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();

    if ((!Objects.isNull(origin)) && caller.getAddress().equals(origin.getAddress())) {
      payEnergyBill(dynamicPropertiesStore, accountStore, forkController, caller,
          receipt.getEnergyUsageTotal(), receipt.getResult(), energyProcessor, now);
    } else {
      long originUsage = multiplyExact(receipt.getEnergyUsageTotal(), percent, disableJavaLangMath)
          / 100;
      originUsage = getOriginUsage(dynamicPropertiesStore, origin, originEnergyLimit,
          energyProcessor,
          originUsage);

      long callerUsage = receipt.getEnergyUsageTotal() - originUsage;
      energyProcessor.useEnergy(origin, originUsage, now);
      this.setOriginEnergyUsage(originUsage);
      payEnergyBill(dynamicPropertiesStore, accountStore, forkController,
          caller, callerUsage, receipt.getResult(), energyProcessor, now);
    }
