### Title
Protocol fees on NEP-245/IMT "token_in" legs are silently bypassed by decomposing a fungible transfer into unit-delta `TokenDiff` intents - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` returns `Pips::ZERO` for any `TokenIdType::Nep245`/`TokenIdType::Imt` token whose per-intent `|delta| <= 1`, an exemption meant for NFT-like/non-fungible semantics. Because NEP-245 is a generic Multi Token standard that can represent finely-divisible fungible sub-tokens, an attacker can transfer/swap an arbitrarily large fungible NEP-245-denominated balance while paying zero protocol fee by splitting it into many `TokenDiff` intents, each moving exactly `delta = ±1` of that token, batched in a single `execute_intents` call.

### Finding Description
The broken binding is: **fee collected on a `token_in` leg of amount `A`** should equal **`protocol_fee.fee_ceil(A)`** regardless of how `A` is partitioned across intents in one transaction. In `TokenDiff::execute_intent`, for each `(token_id, delta)` pair the fee is computed independently per-intent: [1](#0-0) 

and `token_fee` unconditionally zeroes the fee whenever `amount <= 1` for `Nep245`/`Imt`: [2](#0-1) 

`DefuseIntents.intents` is a `Vec<Intent>` executed sequentially inside one signed `MultiPayload`, and each `TokenDiff` in that vector is evaluated independently with no cross-intent amount aggregation for fee purposes: [3](#0-2) 

An attacker (using two accounts they fully control, or in cooperation with a willing counterparty) can therefore submit one `execute_intents([...])` call containing `N` `TokenDiff` intents, each with `diff = {nep245_token: -1}` on the "in" side (paired against whatever they receive), instead of one `TokenDiff` with `diff = {nep245_token: -N}`. Each individual intent hits the `amount > 1` guard with `amount == 1`, so `token_fee` returns `Pips::ZERO` on every single one, while an equivalent single intent moving the aggregate amount `N` (or any `Nep141` transfer of the same size) would pay `protocol_fee.fee_ceil(N) > 0`. The `TransferMatcher`/`finalize` invariant check only verifies that total deltas net to zero across the whole batch — it does not recompute or enforce fee correctness — so this path is not caught by any existing guard (`MultiPayload::verify`, nonce checks, or invariant balancing all pass normally).

### Impact Explanation
This directly bypasses "protocol fees bypassed" (explicitly a Critical category): the `fee_collector` receives `0` instead of the fee owed on the aggregate transferred amount of any NEP-245 (or IMT) token whose sub-token is used to represent a fungible/divisible asset. It is fully repeatable — cost scales only with the number of intents batched into one call (bounded by gas, which the attacker controls by choosing `N`), and applies to any Nep245/Imt-typed asset with real fungible value. The victim is the protocol/fee_collector, who under-collects on economically meaningful token movements that the "NFT-like, unit-delta cannot be meaningfully arbitraged" assumption incorrectly exempts.

### Likelihood Explanation
No privileged role, relayer key, or victim key is needed — the attacker only needs a NEP-245 (or IMT) balance in the Verifier and the ability to sign `DefuseIntents` with multiple `TokenDiff` entries in one `MultiPayload`, or two of their own accounts trading with each other. The only cost is transaction gas for `N` intents packed into one `execute_intents` call, which is cheap relative to the fee saved for any sizeable transfer. This is straightforward and requires no race conditions or third-party cooperation.

### Recommendation
Do not key the fee exemption purely on the type discriminant (`Nep171`/`Nep245`/`Imt`) plus an unbounded per-intent amount check. Either (a) remove the blanket `amount <= 1` fee exemption for `Nep245`/`Imt` and only exempt token types that are provably non-fungible (e.g., `Nep171`, and `Nep245`/`Imt` sub-token ids that are registered/flagged as NFT-class at the protocol level), or (b) aggregate the amount per `(signer, token_id)` across all `TokenDiff` intents within a single execute_intents call (and ideally across the whole transaction) before evaluating the `amount > 1` fee-exemption threshold, so an attacker cannot reset the "amount" counter to 1 by splitting a transfer into many intents.

### Proof of Concept
```rust
// contracts/defuse/core/src/intents/token_diff.rs (unit test), or tests/src/tests/defuse/intents/token_diff.rs (sandbox)
#[test]
fn fee_bypass_via_unit_delta_batching() {
    let token = TokenId::from(Nep245TokenId::new("mt.near".parse().unwrap(), "ft-wrapped".to_string()));
    let fee = Pips::ONE_PERCENT; // nonzero protocol fee

    // Single TokenDiff moving N=1_000_000 units in one intent: fee > 0
    let fee_single = TokenDiff::token_fee(&token, 1_000_000, fee).fee_ceil(1_000_000);
    assert!(fee_single > 0);

    // N=1_000_000 TokenDiff intents each moving delta = -1: each returns ZERO fee
    let mut total_fee_batched: u128 = 0;
    for _ in 0..1_000_000u64 {
        total_fee_batched += TokenDiff::token_fee(&token, 1, fee).fee_ceil(1);
    }
    assert_eq!(total_fee_batched, 0);
    assert_ne!(total_fee_batched, fee_single); // binding broken: same aggregate transfer, different fee outcome
}
```
A sandbox-level `near-workspaces` version would deposit a fungible NEP-245 balance for `user1`, sign one `MultiPayload` containing `N` `TokenDiff` intents each `{nep245_token: -1}` paired against a colluding `user2` account with matching `{nep245_token: +1}` legs, call `execute_intents`, and assert the `fee_collector`'s `mt_balance_of(nep245_token)` is `0`, while a control test using a single `TokenDiff{nep245_token: -N}` (or an equivalent `Nep141` diff) results in `fee_collector` balance `> 0`.
