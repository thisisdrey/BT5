This confirms the analog: `AccountIndexStore` maps `accountName -> address` and is written to in `UpdateAccountActuator.execute()` at [1](#0-0) , but the old name entry is never deleted when an account's name is changed. `AccountIndexStore.put()` only adds the new name key [2](#0-1) , and `validate()` rejects any new name that collides with an existing entry in `AccountIndexStore` [3](#0-2) . The test `UpdateAccountActuatorTest.twiceUpdateAccountSuccess` demonstrates this: every "third Update" and subsequent renames are followed by a manual `dbManager.getAccountIndexStore().delete(accountTest.getBytes())` [4](#0-3) , indicating the production code path leaves the stale name mapping behind and it will keep failing `has(accountName)` for anyone else forever.

### Title
Old account name entries are never cleared in `AccountIndexStore`, permanently blocking name reuse - (File: actuator/src/main/java/org/tron/core/actuator/UpdateAccountActuator.java)

### Summary
`AccountUpdateContract` lets any account owner rename their account (once `AllowUpdateAccountName` is enabled, or once if it is not). `UpdateAccountActuator.execute()` writes the new name into `AccountIndexStore` via `accountIndexStore.put(account)`, but never removes the mapping for the account's *previous* name. Because `AccountIndexStore` is a simple `name -> address` KV store with no reverse cleanup, the old name key remains present indefinitely.

### Finding Description
`validate()` uses `chainBaseManager.getAccountIndexStore().has(accountName)` as the uniqueness check for account names [3](#0-2) . `execute()` sets the account's new name and calls `accountIndexStore.put(account)`, which stores `accountName -> address` [1](#0-0) [2](#0-1) . There is no corresponding `accountIndexStore.delete(oldName)` call anywhere in this actuator (or in `AccountIndexStore` itself, which exposes no delete/remove logic for stale keys). This mirrors the `D3MakerFreeSlot.setNewTokenAndReplace()` bug class exactly: an identifier ("slot"/name) that is claimed via a `has()`/uniqueness check is never released when the owning entity moves on to a new identifier, so the old identifier becomes permanently unusable by anyone (including a legitimate later owner who might want that name, or the original account itself if `AllowUpdateAccountName` allowed it to revert).

### Impact Explanation
Once account A renames from `nameX` to `nameY`, `nameX` remains permanently marked as taken in `AccountIndexStore`. Any other account B that later tries to set/update its name to `nameX` will be rejected by the `has(accountName)` check in `validate()`, even though no live account currently holds that name. This is a permanent freezing of a namespace resource: legitimate account names become permanently unusable, and this can be triggered by any unprivileged account owner simply by renaming twice (broadcasting two `AccountUpdateContract` transactions), which is fully within reach of a normal transaction broadcaster.

### Likelihood Explanation
High likelihood of occurrence — it requires no special privileges, only that `AllowUpdateAccountName` be enabled (already default-on-chain behavior once activated) and that the same address calls `AccountUpdateContract` twice with two different names, or that one account updates its name away from a name another account wants later. The test suite already manually works around this exact defect by explicitly deleting the stale `AccountIndexStore` entry after tests (`dbManager.getAccountIndexStore().delete(accountTest.getBytes())` / `.delete(ACCOUNT_NAME.getBytes())`) [5](#0-4) [6](#0-5) , confirming production code does not do this cleanup itself.

### Recommendation
In `UpdateAccountActuator.execute()`, before writing the new name to `AccountIndexStore`, delete the entry for the account's previous name if it is non-empty and differs from the new name:
```java
byte[] oldName = account.getAccountName().toByteArray();
account.setAccountName(accountUpdateContract.getAccountName().toByteArray());
chainBaseManager.getAccountStore().put(ownerAddress, account);
if (oldName.length > 0 && !Arrays.equals(oldName, accountUpdateContract.getAccountName().toByteArray())) {
  chainBaseManager.getAccountIndexStore().delete(oldName);
}
chainBaseManager.getAccountIndexStore().put(account);
```

### Proof of Concept
1. Account A calls `AccountUpdateContract` with `accountName = "alice"`. `AccountIndexStore` now has `"alice" -> A`.
2. With `AllowUpdateAccountName` enabled, account A calls `AccountUpdateContract` again with `accountName = "alice2"`. `AccountIndexStore` now has `"alice" -> A` (stale, never deleted) and `"alice2" -> A`.
3. Account B (a different, unrelated address) attempts to call `AccountUpdateContract` with `accountName = "alice"`. `validate()` finds `accountIndexStore.has("alice") == true` and throws `ContractValidateException("This name is existed")`, permanently blocking B (or anyone else) from ever using the name "alice" again, even though no account currently holds it.
