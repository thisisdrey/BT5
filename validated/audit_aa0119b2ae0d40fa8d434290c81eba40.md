### Title
Dust-transfer griefing fills a victim's `depositTokensOfAccount` list, causing subsequent legitimate deposit/transfer/seize operations to revert - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`DepositToken._transfer` and `DepositToken._mint` unconditionally register the recipient in the pool's per-account deposit-token list whenever they receive the token for the first time (`_recipientBalanceBefore == 0 && amount_ > 0`). There is no opt-out and no minimum amount: a permissionless ERC-20 `transfer`/`transferFrom` of 1 wei of `msdTOKEN` inserts the token into the recipient's `depositTokensOfAccount` set via `pool.addToDepositTokensOfAccount(recipient_)`. [1](#0-0)  The same registration happens on mint via `deposit`. [2](#0-1) 

This is the direct analog of CVE-2025-70123: an attacker-crafted first "message" (a dust transfer, analogous to the malformed Association Setup Request) is accepted without sufficient validation of its effect on per-account state, placing the victim's position in an inconsistent/blocked state such that a later valid operation (a deposit, a liquidation `seize`, or a transfer of a new collateral type) reverts — a cascading liveness failure.

### Finding Description
- `DepositToken._transfer` runs `pool.addToDepositTokensOfAccount(recipient_)` for any first-time receipt of any amount, including attacker-sent dust. [1](#0-0) 
- `_mint` (reached via `deposit(amount_, onBehalfOf_)`, which allows depositing on behalf of an arbitrary `onBehalfOf_` address) does the same, so an attacker can also register tokens on a victim via `deposit` with `onBehalfOf_ = victim` without the victim's consent. [2](#0-1) 
- The account's deposit-token set is backed by `MappedEnumerableSet` and the Pool enforces a `MAX_TOKENS_PER_USER`-style bound (matches in `contracts/Pool.sol` and `contracts/lib/MappedEnumerableSet.sol`). Once the victim's set is at capacity, any path that would insert a new token — `deposit` to a new `DepositToken`, a `transfer`, or `seize(from, victim, amount)` of a token the victim doesn't already hold — reverts inside `addToDepositTokensOfAccount` and rolls back the entire transaction.
- Removal only happens when the sender's own balance reaches zero, so the victim cannot free the slots themselves except by transferring the dust away one token at a time; meanwhile any attempt to receive a new collateral type fails.

### Impact Explanation
Temporary freezing of funds and liveness disruption of liquidation:
- A victim at the cap cannot deposit into a newly onboarded collateral `DepositToken` (revert in `_mint` → `addToDepositTokensOfAccount`), blocking their ability to add collateral — including when they are near liquidation and need to top up.
- `Pool.liquidate` calls `DepositToken.seize`, which routes through `_transfer`; if the liquidator passes a `depositToken_` the victim doesn't hold, or the protocol tries to credit a seized token to an account (liquidator) whose list is full, the seize reverts, blocking the liquidation pathway and leaving bad-debt positions unclosable.
- The victim must spend gas sweeping dust tokens out before recovering, and the attacker can re-fill slots cheaply. No privileged role, no oracle manipulation, no governance action is required — only an EOA calling public `transfer`/`transferFrom`/`deposit`.

### Likelihood Explanation
Fully permissionless and cheap: the attacker needs only one wei of each registered `msdTOKEN` deposit token (obtainable by depositing minimum amounts or receiving dust), then calls `transfer(victim, 1)` or `deposit(1, victim)` across tokens until the victim's list hits the cap. No modifiers block it: `transfer`/`transferFrom` are public with only `_revertIfLocked` on the sender side (attacker's own unlocked balance), and `deposit` accepts any `onBehalfOf_`. It only pays off when the victim wants to onboard a new collateral type or during liquidation, so impact is conditional but repeatable.

### Recommendation
Make the per-account deposit-token list opt-in or lazily managed rather than unconditionally appended on every first receipt:
- Only register a token in `depositTokensOfAccount` for a threshold amount (e.g., ignore receipts below a dust floor), or
- Let `debtPositionOf`/collateral accounting derive tokens from a registry of the account's nonzero balances instead of a capped enumerable set, or
- Allow recipients to deregister tokens without zeroing the balance, and/or make `addToDepositTokensOfAccount` non-reverting (return bool) so a full list degrades gracefully rather than bricking `deposit`/`seize`.
- At minimum, exempt `seize` (liquidation path) from the cap so liquidations can't be blocked by a full recipient list.

### Proof of Concept
Note: I could not fully read `Pool.sol`'s `addToDepositTokensOfAccount`/`MAX_TOKENS_PER_USER` enforcement within the available iterations, so the cap value and exact revert condition are inferred from the set-registration pattern and the prompt's bug-class map; the unconditional insertion in `DepositToken` is confirmed by direct file reads.

Hardhat fork sketch:

```ts
// Fork at deployed state where pool has N deposit tokens registered.
// attacker holds >=1 wei of each msdTOKEN i.

const victim = bob.address;
for (const dt of depositTokens) {
  // fill victim's depositTokensOfAccount list
  await dt.connect(attacker).transfer(victim, 1);
}
// victim list is now at MAX_TOKENS_PER_USER

// 1) victim cannot onboard the new collateral type:
await expect(
  newDepositToken.connect(attacker).transfer(victim, 1)
).to.be.reverted; // reverts inside pool.addToDepositTokensOfAccount

// 2) liquidation DoS: victim has an unhealthy position; seize of a token
// the liquidator-to list is full for reverts
await expect(
  pool.connect(liquidator).liquidate(syntheticToken, victim, maxUint, newDepositToken)
).to.be.reverted; // DepositToken.seize -> _transfer -> addToDepositTokensOfAccount reverts

// 3) even a plain transfer of any token the victim doesn't hold fails:
await expect(
  dt.connect(alice).transfer(victim, amount)
).to.be.reverted;
```

The invariant broken is liveness: an accepted state mutation (dust registration) by an unprivileged party causes subsequent valid operations (`deposit`, `seize`, `transfer`) to deterministically revert for the victim.
