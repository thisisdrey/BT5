### Title
Unprivileged attacker can DoS all deposits, withdrawals, and liquidations by filling the fee collector's per-account token list to `MAX_TOKENS_PER_USER` - (File: contracts/Pool.sol)

### Summary
`Pool.addToDepositTokensOfAccount` reverts once an account holds 30 distinct deposit/debt tokens (`MAX_TOKENS_PER_USER`). Any account's list can be filled by an attacker because `DepositToken.deposit(amount_, onBehalfOf_)` mints to an arbitrary beneficiary and `DepositToken._transfer` adds the token to an arbitrary recipient. If the targeted account is the pool's `feeCollector`, then every fee-bearing `deposit`, `withdraw`, and liquidation `seize` permanently reverts with `UserReachedMaxTokens`, causing a protocol-wide availability failure (the analog of the MySQL Optimizer "complete DOS" in CVE-2025-30682).

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [1](#0-0) [2](#0-1) 
- `DepositToken._mint` and `_transfer` call `pool.addToDepositTokensOfAccount(account_)`/`(recipient_)` whenever the balance goes from 0 to >0 — with no consent check on the receiver [3](#0-2) [4](#0-3) 
- `DepositToken.deposit(amount_, onBehalfOf_)` is permissionless and lets the caller mint the receipt token to any `onBehalfOf_` address [5](#0-4) 
- `deposit` mints the deposit fee directly to `pool.feeCollector()` inside `_mint`, and `withdraw`/`seize` transfer fees to `feeCollector`/`to_` via `_transfer` — both paths internally call `addToDepositTokensOfAccount` when the feeCollector's balance of that token was 0 [6](#0-5) [7](#0-6) 

Attack: the attacker acquires 1 wei (post-fee) of each of the pool's deposit tokens and either calls `deposit(dust, feeCollector)` or `transfer(feeCollector, dust)` for ~30 distinct deposit tokens (or fewer if the feeCollector already holds some). Once the combined list reaches 30, every subsequent `deposit`/`withdraw`/`liquidate` that tries to mint/transfer a *new* token type to the feeCollector (i.e., any fee-bearing operation on a collateral the feeCollector has not yet touched) reverts. The feeCollector (a fee-collection address, not a user wallet) has no incentive or easy mechanism to zero out 30 dust balances, so the freeze is effectively permanent.

### Impact Explanation
Complete availability DoS of the pool: all fee-charged collateral deposits, withdrawals, and liquidations revert for every user. Blocked liquidations additionally allow underwater positions to accrue bad debt (insolvency risk). The attacker is an unprivileged EOA spending only dust amounts of underlying collateral. This mirrors CVE-2025-30682's class: a low-privileged network attacker causing a complete denial of service.

### Likelihood Explanation
High. Only ~30 cheap calls are needed; dust deposits of each enabled collateral are sufficient since `deposit` accepts arbitrary `onBehalfOf_`. Nothing stops it: no pause flag, cap, or modifier prevents adding entries to another account's list. The attack can also be aimed at individual victims (e.g., filling a user's list so they cannot deposit a *new* collateral type to rescue a position heading toward liquidation).

### Recommendation
- Remove the `MAX_TOKENS_PER_USER` revert for protocol-internal accounts such as `feeCollector`, or exempt first-time mints to the feeCollector.
- Alternatively, charge fees in underlying (Treasury pull) rather than minting deposit tokens to the feeCollector, or batch-sweep so the feeCollector's receipt-token balance never creates new list entries.
- Consider letting accounts opt out / making the list add non-reverting (ignore additions beyond the cap and compute positions differently).

### Proof of Concept
Foundry-style fork test sketch (Hardhat equivalent works):

```solidity
// pool, depositTokens[i], feeCollector from deployed Metronome pool on fork
address feeCollector = pool.feeCollector();
uint256 needed = 30
    - pool.getDepositTokensOfAccount(feeCollector).length
    - pool.getDebtTokensOfAccount(feeCollector).length;

for (uint256 i; i < needed; ++i) {
    IERC20 underlying = depositTokens[i].underlying();
    deal(address(underlying), attacker, dust);
    underlying.approve(address(depositTokens[i]), dust);
    // mints msdToken directly to feeCollector, adding it to its list
    depositTokens[i].deposit(dust, feeCollector);
}

assertEq(
    pool.getDepositTokensOfAccount(feeCollector).length
        + pool.getDebtTokensOfAccount(feeCollector).length,
    30
);

// Now any fee-bearing deposit of a collateral NOT already in the list reverts
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
depositTokens[newIdx].deposit(amount, alice); // _mint(feeCollector, fee) -> addToDepositTokensOfAccount reverts
// Same for withdraw (fee _transfer to feeCollector) and liquidate (seize fee split)
```

Assumptions/uncertainties: requires `depositFee > 0`/`withdrawFee > 0` on the deployed FeeProvider for the fee-mint path (with 0 fees, the attacker must fill the list via dust `transfer`s to the victim, which still DoSes that user's new deposits/issues but not feeCollector mints); the total number of enabled deposit tokens in the pool must be large enough to reach 30 combined entries (per-pool collateral + synth count on deployed chains should be checked).
