### Title
Dust-transfer griefing fills a victim's `depositTokensOfAccount` set up to `MAX_TOKENS_PER_USER`, permanently blocking deposits and transfers to that account - (File: contracts/Pool.sol)

### Summary
`DepositToken._transfer()` and `DepositToken._mint()` automatically call `Pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance of that deposit token was previously zero. `Pool` enforces `MAX_TOKENS_PER_USER` across `depositTokensOfAccount` + `debtTokensOfAccount` and reverts with `UserReachedMaxTokens` once the combined set size reaches the cap. Because entries are added on the *recipient's* set, any unprivileged user can permissionlessly grow a victim's tracked-token list by depositing dust amounts of each registered collateral and transferring the resulting msd tokens to the victim — an on-chain analog of the CVE's "memory leak → DoS" class: forced resource accumulation inside a bounded structure that then makes subsequent operations fail.

### Finding Description
- `DepositToken.deposit(amount_, onBehalfOf_)` → `_mint(onBehalfOf_, ...)` → `if (balanceBefore == 0 && amount > 0) pool.addToDepositTokensOfAccount(account_)` (`DepositToken.sol:486-488`).
- `DepositToken._transfer(sender_, recipient_, amount_)` → `if (_recipientBalanceBefore == 0 && amount_ > 0) pool.addToDepositTokensOfAccount(recipient_)` (`DepositToken.sol:518-520`).
- `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once `depositTokensOfAccount[account].length() + debtTokensOfAccount[account].length() >= MAX_TOKENS_PER_USER` (griefing surface confirmed by `UserReachedMaxTokens` revert in `test/Pool.test.ts:1491-1520`).

Attack steps (unprivileged EOA):
1. For each registered `DepositToken` in the pool, call `deposit(1 wei worth, attacker)` then `transfer(victim, dust)`. Each transfer inserts that deposit token into `depositTokensOfAccount[victim]`.
2. Optionally mint dust amounts of each synthetic via `DebtToken.issue` on the attacker's own position and have the victim's debt set reached — the cap counts the union of both sets, so deposits alone are usually enough.
3. Once the victim's combined set length equals `MAX_TOKENS_PER_USER`, every subsequent `deposit(x, victim)`, `transfer(victim, y)` for a *new* collateral type, and any `_mint`/`seize` that would add a new entry reverts with `UserReachedMaxTokens`.

Unlike a true memory leak, entries are removable (the victim can burn/transfer the dust out), so this is griefing that forces the victim to spend gas to clean their set before they can onboard new collateral — but until then, liveness of any path that adds a new tracked token to the victim is broken.

### Impact Explanation
Temporary freezing of funds / liveness denial: the victim cannot receive any new collateral type (direct deposits `onBehalfOf_` them, inbound transfers, SmartFarmingManager leverage that mints a new deposit token, or liquidation `seize` flows that would mint/seize a new token to them). If the victim holds a levered position whose health is degrading, they are prevented from topping up with a different collateral type while the set is saturated, making their position forcibly liquidatable. The attacker only pays dust deposits + transfer gas; the victim must burn each dust position individually (and each burn triggers reward-distributor callbacks, costing them gas) to recover.

### Likelihood Explanation
No privilege required: `deposit`, `transfer`, and `DebtToken.issue` are all public, and the set insertion happens on the recipient's storage, not the sender's. The only prerequisites are that the victim's combined tracked-token count be close enough to `MAX_TOKENS_PER_USER` that the attacker can bridge the gap with the pool's registered collateral types. On pools with several deposit tokens and a modest cap this is feasible; the attack also naturally triggers whenever a victim already uses most slots and receives dust of the remaining types.

### Recommendation
Only add a deposit token to `depositTokensOfAccount` when the credited amount exceeds a meaningful threshold (e.g. a per-token dust floor), or add entries on explicit opt-in (e.g. only via `deposit`/`_mint` initiated for the account, not via inbound `transfer`/`seize`). Alternatively, make `addToDepositTokensOfAccount` non-reverting on cap overflow and have `debtPositionOf`/`depositOf` skip untracked tokens, so a saturated set degrades gracefully instead of bricking transfers to the account.

### Proof of Concept
Hardhat sketch (mirroring `test/Pool.test.ts` setup):

```ts
// victim starts with N tracked tokens; MAX_TOKENS_PER_USER = M
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber()
// attacker fills remaining slots with dust of each deposit token
for (const dt of depositTokens) {           // each registered DepositToken
  await underlying.connect(attacker).approve(dt.address, 1)
  await dt.connect(attacker).deposit(1, attacker.address)   // dust
  await dt.connect(attacker).transfer(victim.address, 1)    // adds dt to victim's set
}
// now victim's combined set length == max
// any new-token flow to victim reverts:
await expect(
  someOtherDepositToken.connect(bob).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
await expect(
  newDepositToken.connect(bob).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
// victim's own set reaches cap even though they never opted in
expect((await pool.getDepositTokensOfAccount(victim.address)).length).to.eq(max)
```

Note: this assumes the number of registered deposit tokens plus the victim's existing tracked tokens can reach `MAX_TOKENS_PER_USER`; I could not verify the deployed cap value or the count of registered collaterals on a live fork within this iteration, so the exact feasibility threshold remains unconfirmed.
