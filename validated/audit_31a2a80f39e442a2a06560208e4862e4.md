## Analysis Result

### Title
Missing non-negative clamp on `RepositoryImpl.addTotalNetWeight/addTotalEnergyWeight/addTotalTronPowerWeight` allows the global resource-weight aggregates to diverge and go negative - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
The Backd `StakerVault` bug class is: a global aggregate (`_poolTotalStaked` / `strategiesTotalStaked`) is maintained by two separate code paths that are not kept mutually consistent, so decrementing the aggregate through one path can push it below zero because the invariant enforced by the other path was bypassed. Java-tron has a structurally identical pattern in its global resource-weight accounting: `TotalNetWeight`, `TotalEnergyWeight`, and `TotalTronPowerWeight` are shared aggregate counters that are mutated from two independent implementations — the legacy actuator layer (`DynamicPropertiesStore`) and the TVM native-contract layer (`RepositoryImpl`) — and only one of them enforces a non-negative floor.

### Finding Description
`DynamicPropertiesStore.addTotalNetWeight/addTotalEnergyWeight/addTotalTronPowerWeight`, used by the legacy `FreezeBalanceActuator`/`UnfreezeBalanceActuator` path, clamps the result to zero whenever `allowNewReward()` is active: [1](#0-0) 

However, `RepositoryImpl.addTotalNetWeight/addTotalEnergyWeight/addTotalTronPowerWeight`, used by the TVM native-contract path (`FreezeBalanceV2Processor`, `UnfreezeBalanceV2Processor`, `CancelAllUnfreezeV2Processor`), performs a plain `+=` with **no clamp at all**: [2](#0-1) 

Both code paths write to the exact same persisted keys (`TOTAL_NET_WEIGHT`, `TOTAL_ENERGY_WEIGHT`, `TOTAL_TRON_POWER_WEIGHT`) and are reachable by an unprivileged actor:
- The legacy path is reached by a plain `FreezeBalanceContract`/`UnfreezeBalanceContract` transaction.
- The TVM native path is reached by any account calling a smart contract that invokes the `freezeBalanceV2`/`unfreezeBalanceV2`/`delegateResource`/`cancelAllUnfreezeV2` native opcodes, e.g.: [3](#0-2) [4](#0-3) 

This is directly analogous to the StakerVault report's root cause: an aggregate value (`_poolTotalStaked`/`strategiesTotalStaked` there, `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight` here) is maintained across two distinct code paths whose invariants are not synchronized — one enforces a safety floor, the other does not — so a decrement issued via the unprotected path can drive the shared counter negative even though the "sibling" implementation was designed to prevent exactly that.

### Impact Explanation
`TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight` are used network-wide as the denominator/participant in bandwidth and energy allocation ratio calculations (e.g. `DelegateResourceProcessor.validate`): [5](#0-4) 
If this global weight becomes negative or otherwise inconsistent with the sum of per-account frozen weights, the bandwidth/energy limit computed for every account on the chain is corrupted, which can translate into accounts obtaining more free bandwidth/energy than their frozen TRX actually backs (unbacked resource), or all such computations reverting/misbehaving — a chain-wide resource-accounting integrity issue.

### Likelihood Explanation
Reaching the TVM native path requires nothing more than an unprivileged account calling a deployed contract that performs `freezeBalanceV2`/`unfreezeBalanceV2`/`delegateResource`/`cancelAllUnfreezeV2`, all of which are ordinary user-triggerable opcodes. Divergence between the legacy actuator path (clamped) and native path (unclamped) only manifests once `allowNewReward()` is enabled and the totals would otherwise need clamping — a state that can be reached through ordinary freeze/unfreeze usage patterns without any privileged role, matching the "fairly low but non-privileged, mistake- or race-triggerable" likelihood the original C4 judge assigned to the analogous Backd finding.

### Recommendation
Move the same non-negative clamp logic used in `DynamicPropertiesStore.addTotalNetWeight/addTotalEnergyWeight/addTotalTronPowerWeight` into `RepositoryImpl`'s equivalents (or centralize both implementations into one shared helper) so both the legacy actuator path and the TVM native-contract path enforce the identical invariant when decrementing the shared aggregate counters.

### Proof of Concept
1. Enable `allowNewReward` (already a supported/production dynamic parameter).
2. Freeze/delegate/unfreeze TRX for bandwidth/energy through the legacy `FreezeBalanceContract`/`UnfreezeBalanceContract` transactions until the clamped total is near zero.
3. From a deployed smart contract, invoke the TVM native `unfreezeBalanceV2`/`cancelAllUnfreezeV2` opcodes to decrement the same global counter via `RepositoryImpl.addTotalNetWeight`/`addTotalEnergyWeight` — which has no floor — driving `TotalNetWeight`/`TotalEnergyWeight` negative, unlike the equivalent legacy-path call which would have clamped to zero.
