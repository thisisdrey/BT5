## Analysis Result

### Title
Unbounded iteration over all registered Witnesses in `MaintenanceManager.doMaintenance()` can DoS block processing/consensus - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
`MaintenanceManager.doMaintenance()` is the java-tron analog of the reported `updatePeriod()`/`distributeAll()` pattern: a periodically-triggered, protocol-critical routine that unconditionally iterates over the *entire* set of a permissionlessly-growable entity (gauges in the report, witnesses here) instead of a bounded subset. Because witness registration has no cap on the total count, an attacker can grow `WitnessStore` without limit and inflate the cost of every future maintenance cycle, which runs synchronously inside block application on every full node.

### Finding Description
Any account with sufficient balance can register as a witness via `WitnessCreateActuator`. The only uniqueness check is that the *same* address cannot register twice; there is no global cap on the total number of witnesses that can exist: [1](#0-0) 

Every maintenance cycle (`doMaintenance()`, invoked automatically from `MaintenanceManager.applyBlock()` which is called from block application in `Manager.processBlock()` via `consensus.applyBlock(block)`), the code performs several unconditional, unbounded loops over **all** witnesses returned by `consensusDelegate.getAllWitnesses()`: [2](#0-1) [3](#0-2) [4](#0-3) 

`WitnessStore.getAllWitnesses()` itself simply streams the entire underlying store with no size limit: [5](#0-4) 

This is applied inside `Manager.processBlock`, which is executed synchronously for every incoming/produced block: [6](#0-5) 

Unlike EVM contract execution (which is bounded by energy/gas metering), this native Java code path has no per-block resource ceiling — it will simply run as long as it takes to iterate the full `WitnessStore`, `WitnessStore` writes (`saveWitness`), and `DelegationStore` updates for every witness, for every account that ever registered. Note that only a bounded subset (`WITNESS_STANDBY_LENGTH` = 127) receives standby rewards via `payStandbyWitness()`/`WitnessStore.getWitnessStandby()`, and only `MAX_ACTIVE_WITNESS_NUM` (27) witnesses are "active" — but `doMaintenance()`'s loops over `getAllWitnesses()` are not bounded by either of these constants.

### Impact Explanation
Since witness registration is permissionless and only gated by a one-time TRX fee (`AccountUpgradeCost`, historically 9999 TRX) with **no upper bound on total registrations**, an attacker with sufficient capital (or, over time, smaller amounts spread across many funded accounts) can inflate `WitnessStore` to an arbitrarily large size. Each subsequent maintenance cycle — which occurs automatically and cannot be skipped, since `MaintenanceManager.applyBlock()`/`doMaintenance()` runs unconditionally as part of block application for every full node — must then iterate, read, and re-write the entire witness set multiple times (vote accumulation, reward calc, brokerage/vote persistence). If the number of witnesses grows large enough that this processing exceeds acceptable block-production/verification time, it degrades or halts block production and validation across the network, directly mirroring the reported `updatePeriod()` DoS on weekly emission distribution: a core, unavoidable, and unbounded per-cycle operation reachable by any funded account.

### Likelihood Explanation
Witness creation requires no special privilege beyond holding/paying the registration fee, matching the "asset issuer" class of unprivileged actor referenced in scope. The attack is purely economic (registration fee × number of witnesses) and does not require compromising any SR/committee role, cooperation from other validators, or network-level attacks — it is a straightforward repeated broadcast of `WitnessCreateContract` transactions from many funded addresses.

### Recommendation
Bound the maintenance-cycle iteration to the actively-relevant subset of witnesses (e.g., the standby/active list already used for reward payout, capped by `WITNESS_STANDBY_LENGTH`/`MAX_ACTIVE_WITNESS_NUM`) rather than `getAllWitnesses()`, or impose/enforce a hard cap on total witness registrations, or process witness updates incrementally/paginated across multiple maintenance cycles to bound per-block work.

### Proof of Concept
1. Fund a large number of distinct accounts, each with at least `AccountUpgradeCost` TRX.
2. From each account, submit a `WitnessCreateContract` transaction (`WitnessCreateActuator.validate()`/`execute()` impose no cap on total witness count, only per-address uniqueness).
3. Repeat until `WitnessStore` contains a very large number of entries.
4. At the next maintenance boundary, `Manager.processBlock()` triggers `consensus.applyBlock(block)` → `MaintenanceManager.doMaintenance()`, which iterates `consensusDelegate.getAllWitnesses()` multiple times (lines 98-101, 108-109, 157-161 of `MaintenanceManager.java`), performing DB reads/writes proportional to the inflated witness count for every node processing that block, degrading or stalling block processing network-wide.
