### Title
Unconditional relayer fee refund paid before address-registrar validation completes allows repeated draining of Wallet Contract funds - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
In `inner_rlp_execute`, the relayer fee (`tx_fee`) for an `EOABaseTokenTransfer` is sent to the predecessor (relayer) unconditionally as soon as the transaction is parsed, before the asynchronous `address_registrar.lookup` call (resolved later in `address_check_callback`) confirms whether the relayer legitimately targeted an unregistered eth-implicit account. Because the nonce is also not incremented on this code path until the callback resolves, and the callback does not — and cannot — cancel the already-dispatched fee-refund promise, a relayer can repeatedly submit the very same signed transaction targeting an address that is actually registered to a named NEAR account and collect the fee refund every time, even though `address_check_callback` will detect the faulty targeting.

### Finding Description
`parse_rlp_tx_to_action` (`internal.rs`, lines 107-122) computes `TargetKind::EthImplicit(address)` whenever the relayer sets `target` to the eth-implicit-account form of `tx.to`, which `validate_tx_relayer_data` (`internal.rs` lines 318-368) accepts as long as `to == address` and `target` textually matches `0x<hex(address)><suffix>` — it performs **no check** that the address is actually unregistered. That validation is deliberately deferred to an async call to the `eth-address-registrar` contract, resolved later in `address_check_callback` (`lib.rs` lines 133-192).

However, in `inner_rlp_execute` (`lib.rs` lines 330-410), for `EOABaseTokenTransfer { fee, .. }` (matching both `address_check: Some(_)` and `address_check: None`), the code:
```rust
if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
    let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
    env::promise_batch_action_transfer(refund_promise, *fee);
}
``` [1](#0-0) 
This promise is created **before** the `address_registrar.lookup` call is even dispatched (that happens further down, only for the `address_check: Some(address)` branch) [2](#0-1) . The refund is an independent receipt, not chained after or contingent on the registrar lookup's outcome, so it will execute regardless of what `address_check_callback` later determines.

When `address_check_callback` later runs and finds `maybe_account_id.is_some()` (i.e., the address is in fact registered to a named account, meaning the relayer's chosen `target` was invalid/faulty), it either bans the relayer (only if `env::signer_account_id() == current_account_id`, i.e. only when the relayer used a wallet-granted access key) or simply returns a failure `ExecuteResponse` with no further consequence for an external relayer using its own account as predecessor:
```rust
} else {
    return PromiseOrValue::Value(ExecuteResponse {
        success: false, success_value: None,
        error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
    });
}
``` [3](#0-2) 
Critically, the nonce is **not incremented** on this code path in `inner_rlp_execute` (it is explicitly skipped for `address_check: Some(_)`) [4](#0-3) , and `address_check_callback` only increments the nonce in the `None` branch [5](#0-4) . So when the registrar returns `Some` and no ban occurs (external relayer, no access key), the nonce stays unchanged and the exact same signed Ethereum transaction can be resubmitted via `rlp_execute` indefinitely — each resubmission re-triggers the unconditional fee-refund transfer in `inner_rlp_execute` before the registrar check runs again.

### Impact Explanation
This is a value-conservation break: the Wallet Contract pays out `tx_fee` from its own balance to a relayer for a transaction that is ultimately rejected as invalid (faulty targeting of a registered account), and it can do so repeatedly for the same signed transaction because the nonce is never consumed on this path when the caller has no access key to revoke. This constitutes direct theft of user funds from the wallet contract by an unprivileged relayer, matching the NEAR bounty "theft of user funds" category.

### Likelihood Explanation
The precondition is that the attacker acts as a relayer for a wallet-owner-signed Ethereum transaction whose `to` address is registered in `eth-address-registrar` to a named NEAR account (this is a normal, expected registrar-usage scenario, not a rare edge case). The attacker needs no access key, no validator/node privilege, and no social engineering beyond obtaining/relaying a legitimately signed transaction (the same signed bytes an honest relayer would also carry). The attack is fully repeatable — bounded only by the wallet's balance and gas costs of resubmission, each of which costs the attacker only ordinary transaction gas fees while netting `tx_fee` each round trip.

### Recommendation
Do not dispatch the relayer fee-refund promise until after the address-registrar check (when `address_check: Some`) confirms the target was legitimately unregistered. Move the fee-refund promise creation into the `None` branch of `address_check_callback` (where the nonce is also incremented), rather than unconditionally in `inner_rlp_execute` for all `EOABaseTokenTransfer`/`ERC20Transfer` cases with `address_check: Some(_)`.

### Proof of Concept
Integration test (extends `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/relayer.rs`):
1. Deploy `eth-address-registrar` and a target NEP-141 (or any) contract account; `register` it so its address maps to a named `AccountId`.
2. Sign an Ethereum base-token-transfer transaction (`crypto::sign_transaction`) from the wallet's key with `to = registered_address`, `max_fee_per_gas`/`gas_limit` set so `tx_fee > 0`.
3. Call `wallet_contract.rlp_execute(target = "0x<hex(registered_address)><suffix>", signed_tx)` from a relayer account that is **not** using a wallet-granted access key (plain external predecessor).
4. Assert:
   - The call resolves with `success = false` and error `"Invalid target: target is address corresponding to existing named account_id"`.
   - Despite the failure, the relayer's account balance increased by `tx_fee` (asserting the bug).
   - `get_nonce()` is unchanged from before the call.
5. Resubmit the identical `rlp_execute` call again with the same `target`/`signed_tx`; assert the relayer again receives `tx_fee`, demonstrating unbounded repeatable drain — this should fail (assert refusal / no further payment) once fixed.
