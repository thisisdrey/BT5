Audit Report

## Title
Validator self-stake incentive payout can silently fail and be permanently lost due to budget/pot funding mismatch - (File: `substrate/frame/staking-async/src/pallet/impls.rs`, `substrate/frame/staking-async/src/reward.rs`)

## Summary
`snapshot_era_rewards` funds the era-specific validator-incentive pot by sweeping whatever balance happens to sit in the *general* incentive pot at the era boundary, with no relationship to the sum of per-validator incentive entitlements that will later be computed page-by-page in `payout_stakers_alive_staked`. Because payouts are claimed independently across many permissionless calls draining a single shared, finite era pot, a shortfall causes `transfer_validator_incentive` to fail after `Eras::<T>::set_rewards_as_claimed` has already been recorded, permanently forfeiting the validator's incentive with no retry path.

## Finding Description
`EraRewardManager::snapshot_era_rewards` transfers the entire reducible balance of `general_incentive_pot` into the era pot at era rotation, independent of any computed total entitlement for that era: [1](#0-0) 

`payout_stakers_alive_staked` marks the page as claimed *before* computing and transferring the incentive: [2](#0-1) 

It then computes the per-page incentive and immediately calls `transfer_validator_incentive`, without any upfront check that the era pot holds enough to cover the sum of all validators'/pages' entitlements for that era: [3](#0-2) 

Inside `transfer_validator_incentive`, a failed transfer only logs a warning and emits `ValidatorIncentiveTransferFailed`; it does not propagate an error back to the caller and does not roll back the `set_rewards_as_claimed` flag already set earlier: [4](#0-3) 

There is no reconciliation step anywhere between the amount swept into the era pot (a snapshot of whatever accumulated via continuous drip-minting) and the total that will later be claimed by validators from that same pot across multiple independent, permissionless calls. This is confirmed by the existing test that deliberately empties the pot and demonstrates the exact `Err` path being hit: [5](#0-4) 

In production builds (without `debug_assertions`), the `defensive!` macro does not panic — it merely logs — so the same code path silently drops the incentive while the claim remains marked as settled.

## Impact Explanation
This matches the "permanent user-fund lock" / "duplicate settlement or payout" impact category: the validator's entitlement is marked as claimed (`set_rewards_as_claimed`) while the actual liquid transfer of the self-stake incentive silently fails and is never retried, resulting in a permanent loss of the promised incentive amount for that validator/era/page with no on-chain remediation. The corrupted value is the validator's per-page incentive amount computed by `calculate_validator_incentive_for_page`, which becomes unrecoverable once `transfer_validator_incentive` fails after the claim flag is already set.

## Likelihood Explanation
The vulnerability is reachable by any unprivileged caller invoking the public `payout_stakers_alive_staked` extrinsic — no malicious validator, governance, or privileged action is required. Because the era incentive pot is funded once via an unrelated balance snapshot and drawn down by uncoordinated, independent per-validator/per-page calls, any shortfall between snapshot timing (dependent on DAP drip minting schedule) and the sum of computed entitlements results in later claimants' transfers failing. The existing `defensive_panic_on_transfer_failure` test in the repository demonstrates this exact scenario is triggerable and handled (rather than prevented) by the code, confirming feasibility.

## Recommendation
Reconcile the era incentive pot's actual funded balance against the total computed entitlement for the era before allowing any individual payout to proceed — e.g., precompute the full per-era total incentive and either pro-rate it to the actual pot balance or fail the entire era's payout atomically if insufficient. Additionally, do not set `Eras::<T>::set_rewards_as_claimed` until the transfer has been confirmed successful, or revert the claimed flag if `transfer_validator_incentive` fails, so validators can retry once the pot is corrected.

## Proof of Concept
The existing unit test `defensive_panic_on_transfer_failure` reproduces the scenario: after setting up an incentive budget and rewarding an era, the era's incentive pot is deliberately drained to a near-zero balance, then `make_all_reward_payment` is called, triggering the `Err` branch in `transfer_validator_incentive` (panicking under `debug_assertions`, but under production builds merely logging a warning and emitting `ValidatorIncentiveTransferFailed` while the claim remains permanently marked as settled). 	/// Transfer validator incentive from era pot to the validator's payout account.
	///
	/// This is a direct liquid transfer. Future PRs may introduce vesting via a trait.
	fn transfer_validator_incentive(era: EraIndex, stash: &T::AccountId, amount: BalanceOf<T>) {
		let Some(dest) = Self::payee(Stash(stash.clone())) else {
			Self::deposit_event(Event::<T>::Unexpected(UnexpectedKind::MissingPayee {
				era,
				stash: stash.clone(),
			}));
			return;
		};
		let Some(payout_account) = Self::payout_account_for_dest(stash, &dest) else {
			// Destination is `None`; intentional opt-out.
			return;
		};

		let incentive_pot = T::RewardPots::pot_account(crate::RewardPot::Era(
			era,
			crate::RewardKind::ValidatorSelfStake,
		));

		match T::Currency::transfer(
			&incentive_pot,
			&payout_account,
			amount,
			Preservation::Expendable,
		) {
			Ok(_) => {
				Self::deposit_event(Event::<T>::ValidatorIncentivePaid {
					era,
					validator_stash: stash.clone(),
					dest,
					amount,
				});
			},
			Err(e) => {
				log!(warn, "Failed to transfer liquid incentive: {:?}", e);
				Self::deposit_event(Event::<T>::Unexpected(
					UnexpectedKind::ValidatorIncentiveTransferFailed { era },
				));
				defensive!("Validator incentive liquid transfer failed");
			},
		}
	}

#[test]
#[should_panic(expected = "Validator incentive liquid transfer failed")]
fn defensive_panic_on_transfer_failure() {
	ExtBuilder::default().build_and_execute(|| {
		let alice = 11; // validator

		// GIVEN: incentive enabled, validator has weight.
		setup_incentive_with_budget(45, 5);
		Session::roll_until_active_era(2);
		Eras::<Test>::reward_active_era(vec![(alice, 1), (21, 1)]);
		Session::roll_until_active_era(3);

		// WHEN: drain the incentive pot so transfer fails.
		let pot = <Test as Config>::RewardPots::pot_account(RewardPot::Era(
			2,
			RewardKind::ValidatorSelfStake,
		));
		let pot_balance = Balances::free_balance(&pot);
		if pot_balance > 0 {
			// Transfer everything out to account 999 to empty the pot.
			let _ = <Balances as frame_support::traits::fungible::Mutate<_>>::transfer(
				&pot,
				&999,
				pot_balance,
				frame_support::traits::tokens::Preservation::Expendable,
			);
		}

		// THEN: payout panics on defensive.
		make_all_reward_payment(2);
	});
}
