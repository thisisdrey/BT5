Based on my research, I found a strong structural analog to the reported bug class in Gitaly's Praefect router.

### Title
Stale `DefaultReplicationFactor` config value causes panic (slice out-of-range) when a virtual storage loses nodes - ([File: internal/praefect/router_per_repository.go])

### Summary
The Revert Finance bug centers on an admin-controlled numeric config value (`collateralFactor`) that is valid at the time it's set but becomes inconsistent with the system's actual state after an admin removes the underlying resource (a token), leading to an unguarded arithmetic operation (division by zero) that DoSes core protocol functions (liquidations). The Gitaly analog is `PerRepositoryRouter.assignRepositoryToNodes` in Praefect, which uses an admin-set `DefaultReplicationFactor` value together with the *live* set of connected secondary nodes to slice a node list. If the configured/connected node set for a virtual storage shrinks (a node is removed from cluster config, or fails to dial at startup) while the stale `DefaultReplicationFactor` remains at its previously-valid value, the resulting slice index can exceed the length of the available nodes, causing a runtime panic in the RPC routing path used for every repository-creation request.

### Finding Description
`PerRepositoryRouter.assignRepositoryToNodes` computes the replication factor from a config snapshot taken at Praefect startup: [1](#0-0) 

In the default branch (used whenever `replicationFactor != 1` and no additional repository metadata is supplied), it builds `secondaryNodes` from the *live* connection map `r.conns[virtualStorage]` and then slices it using the replication factor taken from config: [2](#0-1) 

Specifically:
```
secondaryNodes = secondaryNodes[:replicationFactor-1]
```
This assumes `len(secondaryNodes) >= replicationFactor-1`. `secondaryNodes` reflects the number of nodes Praefect actually has connections for in `r.conns[virtualStorage]`, which is populated once at startup by `DialNodes` against the configured `Nodes` list for that virtual storage. `replicationFactor` comes from `r.defaultReplicationFactors[virtualStorage]`, which is derived from the config's `VirtualStorage.DefaultReplicationFactor` field: [3](#0-2) 

The field's doc comment states the intended invariant explicitly ("a valid value is inclusive between 1 and the number of configured storages in the virtual storage"), but this is a documentation constraint, not necessarily an enforced runtime invariant tied to the *current* connected node count. If an administrator removes a Gitaly node from a virtual storage's `Nodes` list (a normal, expected admin action — analogous to removing a token from the Revert protocol's collateral list) but leaves `DefaultReplicationFactor` unchanged at a value that was valid for the larger node set, the number of nodes available at `assignRepositoryToNodes` runtime becomes smaller than `replicationFactor - 1`, and the slice expression panics with "slice bounds out of range."

This mirrors the Revert bug precisely: an admin-managed numeric parameter (`collateralFactor` / `DefaultReplicationFactor`) is set once, is valid at that time, but there is no re-validation tying it to the current live set of managed resources (accepted collateral tokens / connected storage nodes). When the resource set shrinks through a normal, expected admin operation, the stale parameter causes an unguarded computation (division by zero / slice index out of range) to break a core code path (liquidation / repository routing).

### Impact Explanation
A panic in `assignRepositoryToNodes` occurs inside the gRPC request-routing hot path (`StreamDirector`) for any RPC that creates a repository with `per_repository` failover election strategy enabled and a reduced replication factor configured. Unless the panic is recovered by a top-level gRPC panic-recovery interceptor (turning it into an `Internal` error per request) rather than crashing the whole process, this results in a denial of service for repository-creation RPCs against the affected virtual storage — a core Praefect routing function, similar in severity to the DoS of liquidations in the original report. Even if recovered per-request, it becomes a persistent, unrecoverable error state for every repository-creation call until an administrator corrects the mismatched config and restarts Praefect.

### Likelihood Explanation
This requires an administrator to legitimately remove/reduce nodes in a virtual storage's config without correspondingly lowering `DefaultReplicationFactor`, and requires `per_repository` failover election strategy in use with `DefaultReplicationFactor > 1`. This is a plausible operational scenario (cluster node decommissioning) but requires the config-reload/restart step to introduce the mismatch, so likelihood is moderate rather than trivially triggerable by an unprivileged actor. I was unable to confirm within the available tool budget whether `Cfg.Validate()` (in `internal/praefect/config/config.go`) enforces `DefaultReplicationFactor <= len(Nodes)` at config parse time for every reload, which is the deciding factor for whether this is exploitable via ordinary admin config changes or already fully guarded. This should be verified directly in `internal/praefect/config/config.go`'s validation logic before treating this as confirmed-exploitable.

### Recommendation
- Re-validate `DefaultReplicationFactor` against the currently configured (or currently connected) node count for each virtual storage at config load and, ideally, at Praefect startup after dialing nodes, clamping or rejecting the config if `DefaultReplicationFactor > len(Nodes)`.
- In `assignRepositoryToNodes`, defensively clamp the slice bound: `min(replicationFactor-1, len(secondaryNodes))` instead of trusting the config-derived value unconditionally.
- Add a regression test that starts a virtual storage with N nodes and `DefaultReplicationFactor == N`, then simulates node removal (via config reload/restart) with fewer live connections, asserting no panic occurs.

### Proof of Concept
1. Configure a virtual storage with 4 Gitaly nodes and `praefect['failover_election_strategy'] = 'per_repository'` and `default_replication_factor = 4` for that virtual storage.
2. Remove two nodes from the virtual storage's `Nodes` list in `praefect.config.toml` (leaving 2 nodes) without adjusting `default_replication_factor`, then restart/reconfigure Praefect.
3. Issue a `CreateRepository`-class RPC that is routed via `PerRepositoryRouter.assignRepositoryToNodes` (the "default" branch, `replicationFactor != 1`, no `additionalRepoMetadata`).
4. `secondaryNodes` will have length `1` (2 nodes minus the picked primary), while `replicationFactor-1 == 3`, causing `secondaryNodes[:3]` to panic with "slice bounds out of range." [4](#0-3)
