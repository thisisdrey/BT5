### Title
Unbounded byte-array allocation from attacker-controlled length in `EXTCODECOPY`/`CALLDATACOPY` can cause OOM - (File: `actuator/src/main/java/org/tron/core/vm/OperationActions.java`)

### Summary
`extCodeCopyAction` and `ProgramInvokeImpl#getDataCopy`/`ProgramInvokeMockImpl#getDataCopy` allocate a `byte[]` sized directly from a length value popped off the EVM stack (via `DataWord.intValueSafe()`), before any check against the actual source data length. [1](#0-0)  The clamping of the copy size (`sizeToBeCopied`) happens only for the `System.arraycopy` source range, not for the destination allocation size itself, so `new byte[lengthData]` is executed with the full attacker-supplied length. [2](#0-1) 

### Finding Description
`DataWord.intValueSafe()` returns `Integer.MAX_VALUE` (≈2.1 GB) whenever the underlying 256-bit stack value occupies more than 4 bytes or decodes negative, rather than reverting. [2](#0-1)  In `extCodeCopyAction`, `lengthData` is read this way and immediately used as the allocation size for `codeCopy` — `byte[] codeCopy = new byte[lengthData];` — before the actual bytes to copy are clamped to `fullCode.length`. [3](#0-2)  The same pattern exists in `ProgramInvokeImpl.getDataCopy` (`CALLDATACOPY`) and its mock counterpart, where `byte[] data = new byte[length];` is allocated from the raw stack-derived `length` prior to clamping against `msgData.length`. [4](#0-3)  This mirrors the libtiff bug class: a size value derived from attacker-controlled input is used for allocation before validation against the real available data size, enabling a crafted-but-small input to trigger a disproportionately large allocation.

### Impact Explanation
A contract call that pushes a very large `length` operand (e.g. all-`0xFF` stack word, or any value exceeding 4 bytes) to `EXTCODECOPY`/`CODECOPY`/`CALLDATACOPY` can force the VM to allocate up to ~2 GB per invocation. Repeated within a transaction (e.g., looped calls or nested `CALL`s to different contract addresses invoking `EXTCODECOPY`), this can drive JVM heap pressure high enough to trigger `OutOfMemoryError`, potentially crashing or stalling the node process that executes the transaction — a denial-of-service impacting block production/validation, which the report rules classify as a valid analog (node crash/halt).

### Likelihood Explanation
This code path is reachable by any unprivileged party who can deploy or invoke a smart contract containing the `EXTCODECOPY`, `CODECOPY`, or `CALLDATACOPY` opcode with a crafted large length argument — no special privileges required, matching the "contract deployer" reachability criterion. However, I could not fully confirm from the available index whether energy/gas metering (`EnergyCost.EXT_CODE_COPY` and associated memory-expansion cost calculation in `EnergyCost.java`) is computed and charged **before** `extCodeCopyAction`/`getDataCopy` executes the allocation, which would bound the practical size an attacker can reach (gas limits would make a 2 GB allocation prohibitively expensive per call, though repeated smaller allocations near typical gas/memory limits could still be probed). I was not able to retrieve the full `EnergyCost.java` opcode-dispatch/memory-cost logic or the `OperationRegistry`/`Op.java` dispatch order within the available search results to verify whether allocation precedes or follows the energy charge. This is a meaningful gap: if energy is charged strictly before allocation (as is standard in most EVM-derived clients including go-ethereum-style implementations), the practical exploitability of a single call is limited to the memory-expansion cost paid by the caller, reducing this to a low-severity/self-limiting issue rather than a true unauthenticated OOM.

Given the uncertainty above, I cannot assert with full confidence that this OOM is remotely triggerable without matching energy cost — this would need explicit verification of `EnergyCost.java`'s memory-expansion charge relative to the allocation call site in `OperationActions.extCodeCopyAction` and `ProgramInvokeImpl.getDataCopy`, which requires a full read of `EnergyCost.java` and `OperationRegistry.java` (not fully available in this session).    * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }
