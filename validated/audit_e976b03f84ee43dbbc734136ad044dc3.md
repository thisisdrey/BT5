## Analog Found

### Title
Meta-transaction relayers can be drained of attached deposits because deposit refunds on failed inner actions go to the `DelegateAction` sender, not the relayer who paid them - (File: runtime/runtime/src/actions.rs)

### Summary
NEP-366 meta-transactions let a "relayer" submit a `SignedDelegateAction` on behalf of an untrusted `sender_id`, paying all gas and attached-deposit costs for the actions the sender specifies against an arbitrary receiver. This mirrors the Connext report's scenario: an "operator" (the relayer) executes an action whose control flow it does not own, on a receiver it does not control, while its own funds are exposed. In nearcore, if the receiver-side execution fails, the protocol's generic refund rule sends the deposit back to the receipt's `predecessor_id` — which for delegate-action receipts is the (potentially malicious) `sender_id`, not the relayer who actually funded the deposit.

### Finding Description
When a relayer wraps and submits a `SignedDelegateAction`, `apply_delegate_action` builds a new inner receipt with `predecessor_id: sender_id.clone()` (the delegate-action's `sender_id`, e.g. "Alice") while the relayer bears all the gas and deposit costs: [1](#0-0) 

This is explicitly acknowledged in the code comment: *"Relayer prepaid all fees and all things required by actions: attached deposits and attached gas... If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction... Relayer should verify DelegateAction before submitting it."* [2](#0-1) 

On the receiver shard, if the inner action receipt execution fails, `refund_unspent_gas_and_deposits` generates a deposit refund receipt sent to `receipt.balance_refund_receiver()`: [3](#0-2) [4](#0-3) 

`balance_refund_receiver()` resolves to `refund_to` if set, otherwise falls back to `predecessor_id()` — i.e., the delegate action's `sender_id`, not the relayer: [5](#0-4) 

The protocol documentation confirms this is a known, unresolved trust gap: *"what if the transaction fails execution on Bob's shard? At this point, the predecessor is `Alice` and therefore she receives the token balance refunded, not the relayer... there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail."* [6](#0-5) 

This is structurally the same bug class as the external report: an operator (relayer/Relayer A) funds an action whose execution path it does not fully control (xReceive / arbitrary DelegateAction receiver), and an implicit-identity attribution rule (`tx.origin` in Solidity, `predecessor_id`-based refund routing in nearcore) lets the untrusted party capture funds that were actually paid by the operator.

### Impact Explanation
A dishonest `sender_id` (or a `sender_id` colluding with a malicious/reverting receiver contract) can construct a `DelegateAction` with a large attached deposit targeting a receiver/method engineered to fail (e.g., a non-existent method, a contract that conditionally panics, or an account that will not exist by execution time). Once a relayer submits and pays for this meta-transaction, the deposit is refunded to the sender rather than the relayer, resulting in concrete theft of the relayer's NEAR tokens with no on-chain recourse.

### Likelihood Explanation
This requires only that a relayer accept and submit a `SignedDelegateAction` without perfectly predicting execution outcome on a foreign receiver shard/contract — exactly the trust assumption flagged in the project's own architecture docs as an open, accepted risk for relayer implementations, with no protocol-level mitigation (comparable to the original report's "Acknowledged" resolution).

### Recommendation
Route deposit refunds for delegate-action-spawned receipts to the relayer (the outer transaction's `signer_id`/original fee payer) instead of `predecessor_id`, or require the relayer to explicitly set `refund_to` when constructing meta-transaction receipts, consistent with how gas refunds already go to the relayer (`action_receipt.signer_id()`) rather than the predecessor: [7](#0-6) 
At minimum, this risk should be prominently documented for relayer operators as a required pre-execution simulation step, similar to the recommendation in the original report to isolate untrusted execution from funds at risk.

### Proof of Concept
1. Alice (`sender_id`) crafts a `DelegateAction` targeting `receiver_id = "bob"` with `actions = [Transfer{ deposit: 1000 NEAR }]`, where `bob`'s contract is designed/known to make the receipt fail (e.g., a `FunctionCall` to a nonexistent method, or `bob` deletes/never creates its account before execution).
2. Alice signs the `SignedDelegateAction` and sends it off-chain to Relayer R.
3. R wraps it in a transaction it signs and submits, per `apply_delegate_action`, paying the attached 1000 NEAR deposit plus gas costs: [8](#0-7) 
4. The new receipt has `predecessor_id = "alice"`, `receiver_id = "bob"`.
5. Execution on `bob`'s shard fails as engineered.
6. `refund_unspent_gas_and_deposits` issues the 1000 NEAR deposit refund to `receipt.balance_refund_receiver()` = `"alice"`: [3](#0-2) [4](#0-3) 
7. Alice receives the 1000 NEAR that Relayer R actually paid, and R has no on-chain recovery mechanism.

    pub fn refund_to(&self) -> &Option<AccountId> {
        match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseResume(_)
            | ReceiptEnum::GlobalContractDistribution(_) => &None,
            ReceiptEnum::ActionV2(action_receipt_v2)
            | ReceiptEnum::PromiseYieldV2(action_receipt_v2) => &action_receipt_v2.refund_to,
        }
    }

    pub fn balance_refund_receiver(&self) -> &AccountId {
        self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
    }
