### Title
Anti-replay window Check/Update race allows duplicate decryption and replay acceptance - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay check into two separately-locked operations — `window.Check()` before decryption and `window.Update()` after — with the lock released across the expensive AEAD decrypt call in between. This mirrors the reported bug class: a security-critical decision (accept/reject based on current state) is made without accounting for another in-flight operation racing to update that same state, producing an incorrect / stale result.

### Finding Description
`Decrypt` takes `decryptLock`, calls `cs.window.Check(l, messageCounter)`, and releases the lock before calling `cs.dKey.DecryptDanger(...)`. Only after decryption succeeds does it re-acquire the lock and call `cs.window.Update(l, messageCounter)` to actually mark the counter as seen. [1](#0-0) 

`VerifyRelay` has the identical pattern for relay frames. [2](#0-1) 

Between the `Check` and the subsequent `Update`, the replay-window bitmap (`Bits`) does not yet reflect the in-flight packet — analogous to the escrow's `tvl()` not reflecting the in-flight bridge amount during the same block. If two copies of the same ciphertext (a captured/replayed packet) are processed concurrently, both can pass `Check` before either calls `Update`, because the lock is not held across the full check-decrypt-mark sequence.

This is directly reachable in production: nebula spins up `f.routines` independent UDP-reading goroutines, each invoking `readOutsidePackets` → `Decrypt`/`VerifyRelay` on the shared `ConnectionState` for a given peer. [3](#0-2) 
An attacker capturing one legitimate encrypted packet and re-injecting it (a classic on-path/network replay, requiring no valid certificate) can race two copies against the multi-queue UDP listeners so that both are processed by different reader goroutines nearly simultaneously.

Notably, the CHANGELOG shows the project has already fixed similar issues in this exact area for *relayed* traffic and for the `Bits` internals directly ("Advance the replay window on relayed packets…", "Lock replay window updates so concurrent readers can't corrupt it"), which corroborates that concurrent access to replay-window state is a known-sensitive area of this codebase, but the split Check/Update window in `Decrypt`/`VerifyRelay` itself is not covered by those fixes. [4](#0-3) 

### Impact Explanation
A successful race lets an attacker who has observed a single legitimate ciphertext (e.g., an on-path attacker, or an attacker capable of duplicating UDP traffic to the target) get the same encrypted payload decrypted and delivered twice into the TUN device, defeating the protocol's anti-replay guarantee. This can be leveraged to duplicate application-layer traffic, and — depending on the payload — this class of duplicate-delivery bug can enable downstream replay-dependent attacks. It undermines a core Noise/data-plane security invariant (each counter is processed exactly once), classified as Medium/High depending on what protocols run over the tunnel.

### Likelihood Explanation
Likelihood is High-ish but requires precise timing: the attacker must get two copies of the same captured packet to land on different listener goroutines within the narrow window between `Check` returning and `Update` committing (i.e., during the AEAD `DecryptDanger` call). With multiple queues (`f.routines`) actively reading in parallel and no synchronization preventing simultaneous dispatch to the shared `ConnectionState`, an attacker controlling packet injection timing (e.g., sending both duplicates back-to-back over UDP, exploiting NIC/socket load balancing across queues) has a realistic chance of winning the race repeatedly given enough attempts.

### Recommendation
Hold `decryptLock` for the entire check-decrypt-mark sequence (or use a single atomic "claim" operation on the bitmap that reserves the slot before decryption and rolls back on decrypt failure) so no two goroutines can simultaneously pass `Check` for the same counter. Concretely, merge `Check` and `Update` into one lock scope that also encompasses `DecryptDanger`, or perform an atomic "test-and-set" of the window bit before decrypting, releasing/undoing the bit only if `DecryptDanger` fails.

### Proof of Concept
1. Establish a nebula tunnel between two hosts with `f.routines > 1` (multi-queue UDP reader enabled).
2. Capture one legitimate `header.Message` UDP packet sent from peer A to peer B (any application data packet with the same `MessageCounter`).
3. From an attacker position with the ability to send UDP packets to peer B, replay the exact captured packet twice in rapid succession, timed/spread so the two OS-level receives are dispatched to two different `listenOut` reader goroutines (e.g., via socket `SO_REUSEPORT`/queue hashing behavior, or simply flooding at high rate given multiple listener goroutines contending on the socket).
4. Observe (via a debug counter or TUN capture) that both invocations pass `cs.window.Check()` (both return "not yet seen") before either commits `cs.window.Update()`, resulting in the same packet being decrypted and delivered to the TUN device twice — confirming replay-window bypass. func (f *Interface) listenOut(i int) {
	var li udp.Conn
	if i > 0 {
		li = f.writers[i]
	} else {
		li = f.outside
	}

	ctCache := firewall.NewConntrackCacheTicker(f.ctx, f.l, f.conntrackCacheTimeout)
	lhh := f.lightHouse.NewRequestHandler()
	plaintext := make([]byte, udp.MTU)
	h := &header.H{}
	fwPacket := &firewall.Packet{}
	nb := make([]byte, 12, 12)

	err := li.ListenOut(func(fromUdpAddr netip.AddrPort, payload []byte) {
		f.readOutsidePackets(ViaSender{UdpAddr: fromUdpAddr}, plaintext[:0], payload, h, fwPacket, lhh, nb, i, ctCache.Get())
	})

	// An error after teardown began is shutdown noise, the closed flag covers resources
	// Close releases itself and the cancelled ctx covers ones torn down by their owners
	// reacting to it, like the user device pipes
	if err != nil && !f.closed.Load() && f.ctx.Err() == nil {
		f.l.Error("Error while reading inbound packet, closing", "error", err)
		f.onFatal(err)
	}

	f.l.Debug("underlay reader is done", "reader", i)
}
