### Title
`FetchIntoObjectPool` fetches from an arbitrary caller-supplied `origin` repository into an object pool without verifying the origin is actually a member of that pool, enabling cross-repository object injection/disclosure - ([File: internal/gitaly/service/objectpool/fetch_into_object_pool.go])

### Summary
`FetchIntoObjectPool` treats its `origin` and `object_pool` fields as independent, uncorrelated repository identifiers. The handler only checks that the two share a storage name; it never verifies that `origin` is actually a genuine pool member (i.e., that the pool's alternates were derived from that origin, or that any prior `LinkRepositoryToObjectPool` relationship exists). Any caller who can invoke this RPC can therefore fetch the full ref/object graph of any repository they name as `origin` into a pool they can name as `object_pool`, permanently merging those objects into a de-duplication store that is shared, via `objects/info/alternates`, with every other member of that pool.

### Finding Description
The RPC's request validation is limited to a storage-name equality check: [1](#0-0) 

The handler itself simply builds a `localrepo.Repo` for whatever `origin` was supplied and fetches it into the pool with no membership check: [2](#0-1) 

The proto documents `origin` as merely "the repository to fetch changes from" and `object_pool` as "the repository to fetch changes into", with no membership relationship enforced in either the message or the service definition: [3](#0-2) 

Design documentation confirms the RPC is *intended* to be run "only ... with the original object pool member from which the pool has been seeded," but this is a convention, not an enforced invariant in the code path itself: [4](#0-3) 

The underlying fetch performs a full `+refs/*:refs/remotes/origin/*` refspec pull straight from the supplied origin's on-disk path into the pool's object store, with no filtering tied to pool membership: [5](#0-4) 

This mirrors the analog bug class: the smart-contract flaw let a caller supply an arbitrary `_receiver` (a discriminator field) that was never cross-validated against the `_depositId`'s true owner, letting a value computed from the caller's own record be applied to unrelated victim storage. Here, `origin` is the analogous unauthenticated discriminator: it is never cross-validated against the `object_pool` target's actual membership set, so objects from any repository the caller names get merged into a shared store used by unrelated pool members.

### Impact Explanation
Because pool members share objects via alternates, any objects introduced into the pool from an unauthorized/unrelated `origin` become reachable by every other pool member (e.g., every fork of the seeding project) via `git cat-file`, `git log`, or clone of the pool member — a cross-repository/cross-project object disclosure that escapes the normal repository access boundary. This is a concrete cross-repository object access primitive: private commits/blobs from `origin` end up permanently retained in a pool object store shared across potentially many other repositories, and cannot be trivially removed afterward (pool deletion affects all members).

### Likelihood Explanation
`FetchIntoObjectPool` is a MUTATOR RPC reachable by any caller with sufficient access to name both an `origin` repository and a `object_pool` target repository (both are ordinary repository fields subject to normal per-repository authorization, but there is no requirement that the two be related). Since object pools are typically associated with a project the caller controls (e.g. their own fork chain), and `origin` merely needs to be some other repository the caller can read, this is reachable through ordinary API-level requests without needing to be a privileged Gitaly operator, a leaked token holder, or a malicious peer.

### Recommendation
Before performing the fetch, `FetchIntoObjectPool` should verify that `origin` is an actual member of `object_pool` — e.g., by checking that `origin`'s `objects/info/alternates` resolves to the target pool's object directory (the same check `Link`/`linkedToRepository` already performs elsewhere), and reject the request otherwise.

### Proof of Concept
1. Attacker creates (or already has fetch access to) object pool `P` associated with their own project, and separately has read access to an unrelated repository `R` they do not own and that is not a member of `P` (e.g. via any legitimately readable project).
2. Attacker calls `FetchIntoObjectPool` with `origin = R`, `object_pool = P`.
3. `validateFetchIntoObjectPoolRequest` only checks `R.StorageName == P.Repository.StorageName`, which is easily satisfied.
4. `objectPool.FetchFromOrigin` executes `git fetch <R path> +refs/*:refs/remotes/origin/*` directly into `P`'s object store, importing all of `R`'s objects into `P` regardless of whether `R` was ever linked to `P`.
5. Any other repository already linked to `P` (via `LinkRepositoryToObjectPool`) can now read `R`'s objects through the shared alternates, disclosing content across repository boundaries.

```go
func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
}
```

```text
message FetchIntoObjectPoolRequest {
  // origin is the repository to fetch changes from.
  Repository origin = 1 [(additional_repository)=true];
  // object_pool is the repository to fetch changes into.

  // Repack had the intent to control whether FetchIntoObjectPool would perform housekeeping tasks
  // in the pool repository or not. This flag wasn't ever honored though and is thus doing nothing.

  reserved "repack";
```
