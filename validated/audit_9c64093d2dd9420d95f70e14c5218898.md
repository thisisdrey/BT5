Confirmed: storage deposits from `bare_call` are charged (held) from the **origin account of the call** (`charge_deposit` → `T::Deposit::charge_and_hold(..., origin, contract, amount)`) [1](#0-0)  and refunded back to that same origin only when storage is later cleared/shrunk [2](#0-1) . In `deposit_asset_with_surplus`, the `bare_call` origin is the **shared `TransfersCheckingAccount`**, not the XCM message's fee payer [3](#0-2) , so this shared account (not the calling user) bears the storage-deposit cost of any first-time `balanceOf`/allowance slot the destination address causes the ERC20 contract to allocate. `ERC20Matcher` accepts any `AccountKey20`-shaped location as a valid "ERC20" asset id with no verification that the contract implements a real ERC20 [4](#0-3) , and the fixtures explicitly acknowledge non-standard/attacker contracts (`MyTokenFake.sol`) are expected inputs to this transactor [5](#0-4) , exactly the "modified/non-standard ERC20" bug-class from the external report.

### Title
Public ERC20 XCM deposit path drains the shared `ERC20TransfersCheckingAccount` via unrefundable per-recipient storage deposits — ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::deposit_asset_with_surplus` executes the on-chain `transfer` call for every incoming ERC20-over-XCM deposit using `TransfersCheckingAccount` as the transaction origin. Because storage-deposit accounting in `pallet-revive` charges the *call origin*, every first-time transfer to a brand-new beneficiary address (which the attacker fully controls) causes a new storage slot inside the target contract to be paid for out of the shared checking account, up to `ERC20TransferStorageDepositLimit` per call. This deposit stays held against the checking account indefinitely (refund only occurs if that storage is later cleared, which nothing in this flow does), letting any unprivileged user drain the checking account by executing many low-value deposits to fresh addresses.

### Finding Description
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` implement `TransactAsset` for XCM messages whose asset is matched by `ERC20Matcher` [4](#0-3) . `ERC20Matcher` matches *any* location of the shape `(0, [AccountKey20 { .. }])` — it performs no check that the referenced address is a real, well-formed ERC20 token, only that the location structure fits [6](#0-5) . Any user can therefore deploy an arbitrary `pallet-revive` contract at any address (including one whose `transfer`/`balanceOf` behave however the attacker wants, as demonstrated by the test fixture `MyTokenFake.sol` [5](#0-4) ) and immediately use it as a first-class XCM fungible asset.

For the deposit leg, the transactor calls `pallet_revive::Pallet::<T>::bare_call` with `OriginFor::<T>::signed(TransfersCheckingAccount::get())` as the origin, targeting the arbitrary contract with an `IERC20::transferCall` to the beneficiary chosen by the attacker [7](#0-6) . `pallet-revive`'s storage metering charges/holds storage deposits from the *call origin* (`ReservingExt::charge` → `Pallet::<T>::charge_deposit(HoldReason::StorageDepositReserve, origin, contract, amount, ...)`) [2](#0-1) , and this hold is only released when that same storage is subsequently freed [8](#0-7) . Because `TransfersCheckingAccount` is the origin of every `deposit_asset_with_surplus` call, every time a beneficiary address receives an ERC20-over-XCM deposit for the first time — creating a new balance-mapping storage slot in the target contract — the storage deposit for that slot is charged to and held from the shared checking account, capped only by `ERC20TransferStorageDepositLimit` (10,200,000,000 units) per call [9](#0-8) .

An attacker who deploys their own ERC20-like contract can then send repeated `withdraw_asset`/`deposit_asset` XCM programs, each choosing a brand-new `AccountKey20` beneficiary, to force the checking account to pay a fresh storage deposit hold every time — since nothing in this flow ever clears that storage or refunds the checking account, the held balance never comes back. This mirrors the report's "modified standard contract, missing invariant enforcement" pattern: a standard-ERC20-integration adapter was built assuming well-behaved, bounded-storage tokens, but instead trusts an arbitrary, attacker-supplied contract shape while making a *shared, protocol-funded* account pay per-recipient state-growth costs with no accounting limit across calls and no path to reclaim the funds.

### Impact Explanation
This is public, underpriced work performed by an unprivileged actor against a shared protocol account (`py/revch`), degrading/eventually halting all ERC20-over-XCM processing on the chain once the checking account's balance is exhausted (subsequent `bare_call`s from it will fail liquidity checks in `ReservingExt::check_limit`, per [10](#0-9) , which mirrors `pallet-revive`'s analogous check). This falls under "public underpriced work that degrades block production or stalls bridge/asset processing" and effectively "permanent... bridge/asset-transfer-state lock" once the account can no longer front deposits, matching the accepted impact categories.

### Likelihood Explanation
High. No privileged action, malicious peer, validator, or governance actor is required — only an ordinary account able to deploy a `pallet-revive` contract and send local/XCM-executed `withdraw_asset`/`deposit_asset` instructions, which is a normal, public capability on Asset Hub. The cost to the attacker is bounded by their own fees/gas; the cost inflicted on the checking account scales with the number of distinct new beneficiary addresses they choose, which they fully control.

### Recommendation
- Do not use a shared, protocol-owned account as the storage-deposit-paying origin for contract calls triggered by arbitrary/user-supplied XCM messages; instead, require the deposit to be paid from assets already carried in the XCM holding register (i.e., attribute the storage cost to the message's own fee/asset payer), or cap total outstanding, un-refunded deposit exposure per checking account with a hard ceiling and reap/alerting when approached.
- Track and reclaim/refund storage deposits paid by `TransfersCheckingAccount` as part of the transactor's own accounting rather than relying on incidental later clears.
- Consider requiring an allow-list or additional validation (e.g., verifying bytecode/interface conformance, or requiring governance registration) before a contract address can be treated as an `ERC20Matcher`-recognized XCM asset, consistent with how `TrustBackedAssets`/`ForeignAssets` require explicit registration rather than accepting any address.

### Proof of Concept
1. Attacker deploys a minimal contract at address `C` whose `transfer(address,uint256)` always returns `true` and requires no meaningful `balanceOf` bookkeeping (structurally like `MyTokenFake.sol` [5](#0-4) ).
2. Attacker executes an XCM program via `PolkadotXcm::execute` (as in `withdraw_and_deposit_erc20s` test) that:
   - `withdraw_asset` for `(AccountKey20(C), amount)` from their own account (self-controlled contract logic lets this always "succeed"),
   - `deposit_asset` to a freshly generated `AccountKey20` beneficiary address never seen before by contract `C`.
3. `deposit_asset_with_surplus` runs `IERC20::transferCall` on `C` with origin `TransfersCheckingAccount`, causing `C` to allocate a new storage slot for the new beneficiary; `pallet-revive` charges/holds the corresponding storage deposit from `TransfersCheckingAccount` [3](#0-2) .
4. Repeat step 2 with a new beneficiary address each time; each iteration consumes a fresh, unrefunded slice of `TransfersCheckingAccount`'s balance (bounded per call by `ERC20TransferStorageDepositLimit`), eventually exhausting it and breaking ERC20-over-XCM processing chain-wide.

	/// Refund a deposit.
	///
	/// `dst` is usually the transaction origin and `from` a contract or
	/// the pallets own account.
	fn refund_deposit(
		hold_reason: HoldReason,
		from: &T::AccountId,
		dst: deposit_payment::Funds<T::AccountId>,
		amount: BalanceOf<T>,
	) -> Result<(), DispatchError> {
		if amount.is_zero() {
			return Ok(());
		}

		let to = match &dst {
			deposit_payment::Funds::Balance(to) | deposit_payment::Funds::TxFee(to) => *to,
		};
		let result = T::Deposit::refund_on_hold(hold_reason, from, dst, amount);

		result.defensive_map_err(|err| {
			let available = T::Deposit::total_on_hold(hold_reason, from);
			if available < amount {
				// The storage deposit accounting got out of sync with the balance: This would be a
				// straight up bug in this pallet.
				log::error!(
					target: LOG_TARGET,
					"Failed to refund storage deposit {amount:?} from contract {from:?} to origin {to:?}. Not enough deposit: {available:?}. This is a bug.",
				);
				Error::<T>::StorageRefundNotEnoughFunds.into()
			} else {
				// There are some locks preventing the refund. This could be the case if the
				// contract participates in government. The consequence is that if a contract votes
				// with its storage deposit it would no longer be possible to remove storage without first
				// reducing the lock.
				log::warn!(
					target: LOG_TARGET,
					"Failed to refund storage deposit {amount:?} from contract {from:?} to origin {to:?}: {err:?}. First remove locks (staking, governance) from the contracts account.",
				);
				Error::<T>::StorageRefundLocked.into()
			}
		})
	}

impl<T: Config> Ext<T> for ReservingExt {
	fn check_limit(
		origin: &T::AccountId,
		limit: Option<BalanceOf<T>>,
		min_leftover: BalanceOf<T>,
	) -> Result<BalanceOf<T>, DispatchError> {
		// We are sending the `min_leftover` and the `min_balance` from the origin
		// account as part of a contract call. Hence origin needs to have those left over
		// as free balance after accounting for all deposits.
		let max = T::Currency::reducible_balance(origin, Preservation::Preserve, Polite)
			.saturating_sub(min_leftover)
			.saturating_sub(Pallet::<T>::min_balance());
		let default = max.min(T::DefaultDepositLimit::get());
		let limit = limit.unwrap_or(default);
		ensure!(
			limit <= max &&
				matches!(T::Currency::can_withdraw(origin, limit), WithdrawConsequence::Success),
			<Error<T>>::StorageDepositNotEnoughFunds,
		);
		Ok(limit)
	}
