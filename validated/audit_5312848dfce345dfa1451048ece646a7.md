### Title
StackerDB chunk signatures are not bound to the target contract, enabling cross-instance chunk replay by any third party - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the value that a signer's private key signs to authorize a StackerDB chunk write, but the digest only commits to `(slot_id, slot_version, data_hash)`. It never includes the target smart-contract identifier (i.e., which StackerDB instance the chunk is destined for). Because slot-to-signer assignments are frequently identical across sibling StackerDB contracts (e.g. the `signer-<set>-1` and `signer-<set>-2` "lane" contracts that share the same underlying signer ordering), any unprivileged network peer that has observed one validly-signed chunk can replay it — unmodified, without the signer's key — into a *different* StackerDB contract where the same signer address happens to own the same `slot_id`. This is the same root-cause class as the `reportUnauthorizedSigning` bug: a message/proof that is valid in one context is not bound to that context, so it can be redirected/reused ("front-run") by a party who never produced it.

### Finding Description
`SlotMetadata::sign`/`verify` compute the authenticated digest as: [1](#0-0) 

This digest is bound only to `slot_id`, `slot_version`, and `data_hash`. It carries no reference to the StackerDB smart-contract identifier the chunk is meant for. `StackerDBChunkData::get_slot_metadata()`/`verify()` simply forward to this same digest: [2](#0-1) 

On the storage side, `try_replace_chunk` looks up the *slot's* recorded signer for the *given* `smart_contract` and checks the signature and version monotonicity, but nothing in the signed material itself ties the chunk to that particular contract: [3](#0-2) 

The unsolicited push-chunk path (`validate_received_chunk`/`handle_unsolicited_StackerDBPushChunk`) performs the same checks — signer-address lookup for the local slot, signature verification, staleness — and none of them reference anything that ties the specific bytes to the contract they were originally produced for: [4](#0-3) 

Slot-to-signer assignment is derived by ordinal position from the reward-set signer list, and multiple sibling StackerDB contracts (distinguished only by a message-id suffix, e.g. `signer-<parity>-1` vs `signer-<parity>-2`) are built from the same ordered signer set, so the same signer address commonly owns the identical `slot_id` in more than one contract. `libsigner`'s consumption layer even documents that lane separation is enforced only at the application-parsing layer, by payload-type byte — not by the StackerDB authentication layer itself: [5](#0-4) 

Because the chunk-write authentication in `libstackerdb`/`stackslib/src/net/stackerdb` never incorporates the destination contract identifier, an attacker who captures a validly-signed `StackerDBChunkData` broadcast for contract A can re-broadcast the identical bytes as an unsolicited `StackerDBPushChunk` targeting contract B, provided (a) the same signer address owns the same `slot_id` in B, and (b) the replayed `slot_version` exceeds B's currently-stored version for that slot (trivially true for a slot B hasn't seen writes for yet, or for any slot lagging behind). The store layer will accept and persist this write, and it will subsequently be relayed to other peers replicating contract B — all without the attacker possessing any private key.

### Impact Explanation
This breaks the authenticated-vs-stored equality: a chunk cryptographically authorized for one StackerDB instance is accepted and durably stored/relayed as valid content for a different instance. This is an unauthenticated write to state (the attacker did not sign this specific write for this specific contract) and results in network-wide propagation of forged/misattributed data, since accepted chunks are gossiped to other replicating peers via the StackerDB sync protocol. Depending on which contracts collide (e.g. a `BlockResponse` message replayed into a `StateMachineUpdate` lane, or vice versa), this can corrupt a signer's or miner's view of another peer's most recent message for that lane before the real owner writes anything there.

### Likelihood Explanation
No secret key or privileged role is required — only observation of one legitimately-signed chunk on the wire (chunks are gossiped in plaintext over StackerDB sync/push) and knowledge of the target contract/slot layout, both of which are public. The main constraint is finding a target slot where the replayed version is not yet stale, which is readily satisfiable for infrequently-written lanes or immediately following any contract (re)configuration.

### Recommendation
Include a domain separator that binds the signed digest to the specific StackerDB contract instance (e.g. hash in the `QualifiedContractIdentifier`, or a contract-specific nonce/epoch) inside `SlotMetadata::auth_digest()`, so that a chunk signature is only valid for the exact contract it was produced for. Reject any chunk at the `try_replace_chunk`/`validate_received_chunk` layer whose signature does not also attest to the target `smart_contract_id`.

### Proof of Concept
1. Signer `X` owns `slot_id = 5` in both `signer-0-1` (block-response lane) and `signer-0-2` (state-machine-update lane), which is common since both lanes are derived from the same ordered signer set.
2. `X` legitimately signs and pushes a `StackerDBChunkData{slot_id:5, slot_version:7, data:D}` to `signer-0-1`; an attacker observes this chunk on the p2p wire.
3. Attacker constructs a `StackerDBPushChunkData{contract_id: signer-0-2, chunk_data: StackerDBChunkData{slot_id:5, slot_version:7, sig:<same sig>, data:D}}` and sends it to a victim node as an unsolicited push.
4. `handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk` looks up the slot-5 signer for `signer-0-2` (which is also `X`), calls `slot_metadata.verify(&addr)`, which succeeds because `auth_digest()` never referenced the contract — the chunk is accepted, stored, and re-gossiped for `signer-0-2`, even though `X` never authorized this content for that contract/lane.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn get_slot_metadata(&self) -> SlotMetadata {
        SlotMetadata {
            slot_id: self.slot_id,
            slot_version: self.slot_version,
            data_hash: self.data_hash(),
            signature: self.sig.clone(),
        }
    }

    /// Sign this given chunk data message with the given private key.
    /// Sets self.signature to the signature.
    /// Fails if the underlying signing library fails.
    pub fn sign(&mut self, privk: &StacksPrivateKey) -> Result<(), Error> {
        let mut md = self.get_slot_metadata();
        md.sign(privk)?;
        self.sig = md.signature;
        Ok(())
    }

    pub fn recover_pk(&self) -> Result<StacksPublicKey, Error> {
        let digest = self.get_slot_metadata().auth_digest();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(digest.as_bytes(), &self.sig)
            .map_err(|ve| Error::VerifyingError(ve.to_string()))
    }

    /// Verify that this chunk was signed by the given
    /// public key hash (`addr`).  Only fails if the underlying signing library fails.
    pub fn verify(&self, addr: &StacksAddress) -> Result<bool, Error> {
        let md = self.get_slot_metadata();
        md.verify(addr)
