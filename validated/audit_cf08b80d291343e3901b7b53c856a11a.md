## Title
Unbounded `GetAssetIssueList` / `ListExchanges` / `ListWitnesses` query endpoints allow unauthenticated resource-exhaustion DoS - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
The Liferay advisory describes a GraphQL endpoint that does not cap the number of objects a query can return, letting an unauthenticated client force the server to serialize and transmit unbounded result sets, exhausting resources. java-tron has a structurally identical class of endpoints: `GetAssetIssueList`, `ListExchanges`, and `ListWitnesses`, exposed over both gRPC and HTTP, which return the *entire* current set of asset issues, exchanges, or witnesses with no limit/pagination and no maximum-size clamp, unlike their own "paginated" siblings.

### Finding Description
`Wallet.getAssetIssueList()`, `getExchangeList()`, and `getWitnessList()` are invoked directly by unauthenticated RPC/HTTP handlers with no offset/limit parameter at all: [1](#0-0) [2](#0-1) [3](#0-2) 

These same RPCs are declared in the public proto surface (`ListWitnesses`, `GetAssetIssueList`) and reachable from any anonymous full-node client: [4](#0-3) 

By contrast, the project's own "paginated" variants of the same data — `getPaginatedProposalList` and `getPaginatedExchangeList` — explicitly clamp the caller-supplied `limit` to a fixed maximum (`PROPOSAL_COUNT_LIMIT_MAX`, `EXCHANGE_COUNT_LIMIT_MAX`) before building the response: [5](#0-4) 

This demonstrates the project is aware that unbounded list construction is a resource risk for exactly this class of store-backed list query, and mitigates it for the paginated endpoints — but the un-paginated `GetAssetIssueList` / `ListExchanges` / `ListWitnesses` endpoints have no such control, no offset/limit parameter, and no upper bound on the number of protobuf objects appended to the response builder. Both `AssetIssueContract` creation and `ExchangeCreateContract` creation are ordinary, unprivileged, fee-paying transaction types available to any funded account (an "asset issuer" / "order placer" per the in-scope actor list), so the underlying data set these queries serialize is attacker-growable over time by simply broadcasting more issue/exchange-creation transactions, then repeatedly calling the unbounded list RPC.

### Impact Explanation
Each call to `GetAssetIssueList`, `ListExchanges`, or `ListWitnesses` forces the node to iterate the full store, construct full protobuf message objects for every entry, and serialize/transmit the entire result on a single request — with cost scaling linearly (or worse, given JSON printing on the HTTP path) with the total number of assets/exchanges/witnesses ever created on the chain. An attacker who inflates that data set (by issuing many tokens or creating many exchange pairs, both are permissionless operations) and then floods this endpoint can drive sustained CPU, memory, and bandwidth consumption on any full/solidity node serving these RPC/HTTP APIs, degrading or halting the node's ability to serve other API clients — matching the CWE-400 resource-exhaustion / "API the node can no longer serve" impact class of the advisory.

### Likelihood Explanation
High. No authentication, no special privilege, and no rate/size limiting beyond the generic per-request `RateLimiterServlet` (which throttles request frequency, not response size) are required; a single crafted transaction sequence to grow the underlying data set followed by repeated calls to the existing public endpoint is sufficient.

### Recommendation
Enforce a maximum object count (mirroring `PROPOSAL_COUNT_LIMIT_MAX`/`EXCHANGE_COUNT_LIMIT_MAX`) or require pagination for `getAssetIssueList()`, `getExchangeList()`, and `getWitnessList()` in `Wallet.java`, and reject or truncate unbounded requests at the `RpcApiService`/HTTP servlet layer, consistent with how `getPaginatedProposalList`/`getPaginatedExchangeList` already clamp caller-supplied limits.

### Proof of Concept
1. As any funded account, broadcast repeated `AssetIssueContract` (or `ExchangeCreateContract`) transactions to substantially grow the asset-issue/exchange store over time.
2. Repeatedly invoke the unauthenticated gRPC `GetAssetIssueList`/`ListExchanges`/`ListWitnesses` (or HTTP `/wallet/getassetissuelist`, `/wallet/listexchanges`, `/wallet/listwitnesses`) endpoints.
3. Observe that each call returns the complete, ever-growing data set with no offset/limit control, unlike the sibling paginated endpoints, consuming disproportionate CPU/memory/bandwidth per request and degrading node responsiveness for other API clients.

**Uncertainty note:** I could not directly locate the exact HTTP servlet source for `GetAssetIssueListServlet`/`ListExchangesServlet`/`ListWitnessesServlet` (only their gRPC handlers in `RpcApiService.java` were retrieved by search), so the HTTP-path request/response construction details are inferred from the analogous paginated HTTP servlets shown above rather than directly confirmed; a Devin session with full repository access could verify these HTTP servlet files if further confirmation is needed.

  public ProposalList getPaginatedProposalList(long offset, long limit) {

    if (limit < 0 || offset < 0) {
      return null;
    }

    long latestProposalNum = chainBaseManager.getDynamicPropertiesStore()
        .getLatestProposalNum();
    if (latestProposalNum <= offset) {
      return null;
    }
    limit =
        limit > PROPOSAL_COUNT_LIMIT_MAX ? PROPOSAL_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > latestProposalNum ? latestProposalNum : end;
    ProposalList.Builder builder = ProposalList.newBuilder();

    ImmutableList<Long> rangeList = ContiguousSet
        .create(Range.openClosed(offset, end), DiscreteDomain.longs())
        .asList();
    rangeList.stream().map(ProposalCapsule::calculateDbKey).map(key -> {
      try {
        return chainBaseManager.getProposalStore().get(key);
      } catch (Exception ex) {
        return null;
      }
    }).filter(Objects::nonNull)
        .forEach(proposalCapsule -> builder
            .addProposals(proposalCapsule.getInstance()));
    return builder.build();
  }

  public ExchangeList getPaginatedExchangeList(long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    long latestExchangeNum = chainBaseManager.getDynamicPropertiesStore()
        .getLatestExchangeNum();
    if (latestExchangeNum <= offset) {
      return null;
    }
    limit =
        limit > EXCHANGE_COUNT_LIMIT_MAX ? EXCHANGE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
