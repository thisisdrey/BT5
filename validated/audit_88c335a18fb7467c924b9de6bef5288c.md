### Title
`Pool.swap` executes at the oracle price read at inclusion time with no user-specified minimum output - ([File: contracts/Pool.sol](contracts/Pool.sol#L642))

### Summary
`Pool.swap` burns the caller's `syntheticTokenIn_` and mints `syntheticTokenOut_` at whatever `masterOracle().quote()` returns when the transaction is mined. The function signature takes only `amountIn_` — there is no `amountOutMin_` parameter — so a user who quotes a trade and submits it cannot bound the exchange rate applied at execution. This is the same bug class as the reported Splits Swapper issue: an oracle-priced trade where a delayed/relayed execution or an oracle update landing between submission and inclusion makes the trader pay more (or receive less) than they saw at signing time, with no way to revert.

### Finding Description
In `contracts/Pool.sol`, `swap` resolves the output amount inside the same call that commits the burn:

- `syntheticTokenIn_.burn(_msgSender, amountIn_)` executes first, then `(_amountOut, _fee) = quoteSwapOut(...)` is computed and `syntheticTokenOut_.mint(_msgSender, _amountOut)` is called.
- `quoteSwapOut` delegates entirely to `_poolRegistry.masterOracle().quote(syntheticTokenIn_, syntheticTokenOut_, amountIn_)` (lines 508–525) and subtracts the swap fee.
- `IPool.swap` (contracts/interfaces/IPool.sol:100–104) confirms the deployed interface has no slippage parameter.
- By contrast, the protocol does treat slippage as a real risk elsewhere: `SmartFarmingManager` reverts with `LeverageSlippageTooHigh`/`FlashRepaySlippageTooHigh`, and `CrossChainDispatcher` exposes `swapAmountOutMin`/`newAmountOutMin_` on its swap-retry path — but `Pool.swap` itself offers no equivalent guard.

Attack path (unprivileged, allowed by the rules):

1. Victim reads `quoteSwapOut(msUSD, msETH, X)` off-chain, e.g. expecting `Y` msETH, and broadcasts `pool.swap(msUSD, msETH, X)` with a low gas price.
2. While the victim tx is pending, the oracle price used for the pair moves. Two realistic movers, neither requiring privileged roles:
   - Pull-oracle push: the deployed `MasterOracle` can be backed by a Pyth/pull price provider (see `test/E2E.mainnet.test.ts` usage of `pyth.updatePriceFeeds`). `IPyth.updatePriceFeeds` is permissionless — any EOA holding signed price update data can land a fresh (worse for the victim) price in the block immediately before the victim's `swap` executes. This is same-transaction/adjacent-transaction manipulation of the *read*, not incorrect oracle data.
   - Natural drift: a new Chainlink round or a moved TWAP observation lands before the pending tx is mined (the exact scenario in the source report).
3. The victim's `swap` executes at the moved price and mints strictly less `syntheticTokenOut_` than quoted at signing. Because there is no `amountOutMin_`, the transaction cannot revert; the user is forced to accept the worse fill.

The burned input is gone at step 660 before the quote is even computed (line 662), so the user has no atomic opportunity to back out. `nonReentrant`, `whenNotShutdown`, and `isSwapActive` do not constrain the price at which the trade settles.

### Impact Explanation
Direct loss of user funds: the user receives materially less of `syntheticTokenOut_` than the rate they agreed to at signing, up to arbitrarily bad rates if the oracle price moves enough between broadcast and inclusion. On low-liquidity or thin oracle configurations the delta can be large; the user has zero on-chain recourse.

### Likelihood Explanation
Moderate. It requires the victim's tx to be pending across an oracle update (low gas price, congestion, or a sequencer/relayer delay) or an MEV actor to front-run the swap with a permissionless pull-oracle price push. Synth swaps are exactly the flow where users rely on quoted rates, and the fix pattern (min-out parameter) is standard and already used by the protocol's own swapper integrations (`ISwapper.swapExactInput` takes `amountOutMin_`).

### Recommendation
Add a `amountOutMin_` parameter to `swap` (and a matching `maxAmountIn_` variant if an exact-out swap is added):

```solidity
function swap(
    ISyntheticToken syntheticTokenIn_,
    ISyntheticToken syntheticTokenOut_,
    uint256 amountIn_,
    uint256 amountOutMin_
) ... {
    ...
    (_amountOut, _fee) = quoteSwapOut(syntheticTokenIn_, syntheticTokenOut_, amountIn_);
    if (_amountOut < amountOutMin_) revert SlippageTooHigh();
    ...
}
```

Compute the quote before burning, or keep the burn but rely on the revert to roll it back. Update `IPool.swap` accordingly and let callers pass `quoteSwapOut(...) * (1 - slippage)` from the UI.

### Proof of Concept
Foundry mainnet-fork sketch using the deployed Pool (`0x574a32f1047C631653D9283d36e73cF9BA67B940` per `test/foundry/poc/TBY.t.sol`) and the Pyth pull oracle pattern from `test/E2E.mainnet.test.ts`:

```solidity
function test_swap_no_slippage_protection() public {
    // Setup: victim holds msUSD (via deal/issue path), swap is active.
    uint256 amountIn = 10_000e18;

    // 1. Victim quotes at signing time
    (uint256 quotedOut, ) = pool.quoteSwapOut(msUSD, msETH, amountIn);

    // 2. Between broadcast and inclusion the oracle moves against the victim.
    //    Permissionless path: attacker lands a fresh Pyth update in the same block:
    //    pyth.updatePriceFeeds{value: fee}(updateData); // signed data, worse msETH price
    //    (or a new Chainlink round / TWAP tick lands while the tx pends.)

    // 3. Victim's tx executes — no way to revert at the stale rate
    uint256 balBefore = msETH.balanceOf(victim);
    vm.prank(victim);
    pool.swap(msUSD, msETH, amountIn); // cannot pass amountOutMin_
    uint256 received = msETH.balanceOf(victim) - balBefore;

    // 4. Victim received strictly less than quoted; burn already committed.
    assertLt(received, quotedOut);
}
```

The PoC demonstrates that (a) `IPool.swap` exposes no slippage bound, (b) the input burn precedes the oracle read at line 660 vs. 662 of `contracts/Pool.sol`, and (c) a permissionless pull-oracle price push or a pending-tx oracle drift results in a strictly worse fill that cannot be rejected on-chain. I was unable to verify within the index which oracle provider backs each deployed `MasterOracle` token feed on a given chain (the contract is external to this repo), so the fork test should use `updateTokenOracle` configuration to confirm a pull/TWAP-backed pair rather than assuming one.
