Based on my investigation, I found a concrete analog of the "wrong address used for a security-relevant action" bug class in `relay_manager.go`.

### Title
Relay manager trusts attacker-supplied `RelayFromAddr` instead of the authenticated sender's vpn address when creating relay state - (File: relay_manager.go)

### Summary
Just as `BBLeverage.sellCollateral` used the unverified `from` parameter as the repay identity instead of the already-verified `address(this)`, Nebula's `handleCreateRelayRequest` in `relay_manager.go` uses the attacker-controlled `RelayFromAddr` field from an unauthenticated protobuf control message as the identity key for relay state, instead of cross-checking it against `h.vpnAddrs[0]` — the identity that was actually verified via the certificate/handshake for the authenticated `HostInfo h` the control message arrived over.

### Finding Description
`handleCreateRelayRequest` receives `h *HostInfo` (the peer whose authenticated tunnel the `NebulaControl` message arrived over) and `m *NebulaControl`, which carries `RelayFromAddr`/`RelayToAddr` as plain, attacker-supplied fields [1](#0-0) . The function only checks that `from` is not one of *my own* addresses [2](#0-1) ; it never checks that `from == h.vpnAddrs[0]` (the sender's actual, certificate-verified vpn address).

When `target` is one of my own addresses (I am asked to be the terminal relay endpoint), the code installs new relay state keyed by the attacker-chosen `from` directly on the authenticated hostinfo `h`: [3](#0-2) 
This calls `AddRelay`, which inserts `relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)` keyed by the caller-supplied `vpnIp` (here, `from`) [4](#0-3) .

Likewise, in the middle-man branch, `peer.relayState.QueryRelayForByIp(from)` / `AddRelay(..., from, ...)` again key relay-routing state by the unauthenticated `from` value supplied by the sender `h`, rather than validating it against `h`'s verified identity [5](#0-4) .

This mirrors the Tapioca root cause precisely: a function has an already-authenticated/verified identity available (`h`, verified via CA-signed cert during handshake — see `validatePeerCert` at `handshake_manager.go:995-1039`) but instead performs a security-relevant lookup/state-mutation using a different, attacker-supplied address parameter (`from`) that is never checked for equality against the verified one.

### Impact Explanation
Any node with an established, authenticated tunnel to a relay-capable peer can claim, via `RelayFromAddr`, to be relaying "from" an arbitrary victim vpn address it does not own (no CA-signed certificate for that address is required — it is simply a protobuf field). The receiving node (either the terminal target or a middle-man relay) will install `TerminalType`/`ForwardingType` relay routing state associating that victim's vpn address with the attacker's authenticated `HostInfo`. Any other peer that subsequently looks up "how do I reach victim via this relay" through `HostMap.QueryVpnAddrsRelayFor` will be routed to the attacker's tunnel instead of the real victim, enabling relay-routing redirection/hijack of relay-forwarded traffic streams intended for the victim (remote state poisoning of hostmap/relay address trust).

### Likelihood Explanation
Requires only a standard, already-authenticated Nebula tunnel to a peer that is relay-capable (`am_relay` or acting as a terminal target) — no certificate for the spoofed victim address is needed, satisfying the "no CA-signed certificate" reachability constraint. Sending a `CreateRelayRequest` with a forged `RelayFromAddr` is a single, low-cost protobuf message.

### Recommendation
In `handleCreateRelayRequest` (and symmetrically in `handleCreateRelayResponse`), validate that `from` (as the claimed identity of whoever's traffic will terminate/route through this relay) actually corresponds to the peer that sent the message — i.e. reject/ignore the request unless `from` can be independently corroborated (e.g., only trust `RelayFromAddr` when it equals `h.vpnAddrs[0]` in the client-request-to-terminal case, or otherwise route/keys relay state off the authenticated `HostInfo` identity rather than the raw wire field).

### Proof of Concept
1. Attacker `E` establishes a normal, legitimate authenticated tunnel to relay/terminal node `T` (standard handshake, valid cert for `E`'s own address).
2. `E` sends `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: <victim V's vpn addr>, RelayToAddr: <T's own vpn addr>, InitiatorRelayIndex: idx}` over that tunnel.
3. In `handleCreateRelayRequest`, `f.myVpnAddrsTable.Contains(target)` is true (T is being targeted), and since `from` (V's address) is not T's own address, T proceeds to `AddRelay(rm.l, h, f.hostMap, from=V, &m.InitiatorRelayIndex, TerminalType, Established)`, associating `h` (E's authenticated HostInfo) with vpn address `V` in `h.relayState` [3](#0-2) .
4. T replies with `CreateRelayResponse` completing the relay.
5. Any other node that later asks T (via `QueryVpnAddrsRelayFor`) to relay traffic to `V` will be directed into `E`'s tunnel instead of the legitimate `V`'s tunnel, since T's relay map now (incorrectly) associates `V`'s address with `E`.
