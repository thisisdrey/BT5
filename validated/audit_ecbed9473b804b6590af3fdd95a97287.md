### Title
Repeated small UnDelegateResource operations let an account launder consumed NetUsage/EnergyUsage via floor-rounded proportional transfer, bypassing the bandwidth/energy cap tied to frozen balance - (File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java)

### Summary
The Ulysses "balancing" bug works because a proportional redistribution formula (liquidity vs. weight) is recomputed on every add/remove action, and repeating tiny add/remove cycles lets an attacker walk the system to a state that violates the intended per-destination cap. java-tron's resource-delegation system has a structurally similar proportional-redistribution formula: when un-delegating BANDWIDTH/ENERGY, the usage that "follows" the balance back to the owner is computed as `receiverUsage * (unDelegateBalance / receiverAllFrozenBalance)`, truncated to a `long`.

### Finding Description
In `UnDelegateResourceActuator.execute()` (and the mirrored TVM path `UnDelegateResourceProcessor.execute()`), when a resource owner reclaims delegated BANDWIDTH/ENERGY from a receiver, the amount of "usage" transferred back from the receiver to the owner is: [1](#0-0) 

```
long unDelegateMaxUsage = (unDelegateBalance / TRX_PRECISION) * (totalNetLimit / totalNetWeight);
transferUsage = receiverCapsule.getNetUsage() * ((unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth());
transferUsage = min(unDelegateMaxUsage, transferUsage);
```
followed by `receiverCapsule.setNetUsage(receiverCapsule.getNetUsage() - transferUsage)` and (per the test assertions) `ownerCapsule.setNetUsage(ownerCapsule.getNetUsage() + transferUsage)` [2](#0-1) .

This is the same class of proportional-redistribution logic that drives the Ulysses AMM bandwidth exploit: a value (`transferUsage`) is computed as `floor(usage * fraction)` where `fraction = unDelegateBalance / totalFrozenBalance`. Because the result is truncated toward zero on every partial operation, **splitting a single large un-delegation into N small un-delegations systematically loses usage in the rounding step N times instead of once**, exactly mirroring how the Ulysses report's repeated add/remove cycles let `diff` (the imbalance) leak value at every step due to redistribution being recomputed from scratch each time.

Concretely: a user delegates BANDWIDTH to a receiver they control (a sacrificial/self-owned account), lets the receiver consume its resource allowance (accumulating `NetUsage`), then un-delegates the balance back to the owner in many tiny increments instead of one lump sum. On each small increment, `transferUsage = floor(receiverUsage * tinyBalance / totalFrozenBalance)` rounds down to a smaller value (frequently to 0 when `tinyBalance` is small relative to `totalFrozenBalance`), so the receiver's `NetUsage` is decremented by less than its true proportional share, and the owner's netUsage credited is correspondingly reduced too. Repeating this "balancing" sequence — delegate a chunk, consume, undelegate in slivers — allows usage accounting to drift away from the balance-based cap enforced by `BandwidthProcessor.calculateGlobalNetLimit`/`calculateGlobalNetLimitV2` [3](#0-2) , letting the attacker retain more usable (unconsumed) bandwidth/energy capacity than their frozen TRX legitimately backs — the same "bypass a max limit by repeatedly redistributing a bounded resource" pattern described in the report, just applied to TRON's resource-delegation bandwidth/energy accounting rather than a Balancer-style LP pool.

### Impact Explanation
Bandwidth and Energy are TRX-backed resources: `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` cap how much data/computation an account can consume for free based on its frozen (or delegated) balance [4](#0-3) . If repeated small delegate/undelegate cycles let usage accounting be systematically under-decremented from the receiver (or under-incremented on the owner), an account can effectively use more bandwidth/energy than its frozen balance entitles it to, forcing the network to serve free transactions/contract calls beyond the intended TRX-to-resource ratio. This is a resource-accounting integrity issue affecting the fairness/economics of the shared `TotalNetLimit`/`TotalEnergyCurrentLimit` pools, potentially degrading service for legitimate users once repeated at scale.

### Likelihood Explanation
`DelegateResourceContract`/`UnDelegateResourceContract` are ordinary signed transactions any account can broadcast, and the delegate/undelegate pair can trivially be split into arbitrarily many small-value transactions to maximize truncation drift, requiring no special privilege — only paying the normal transaction bandwidth/energy fee for each call (a cost, but potentially small relative to the resource gained if repeated with high `receiverUsage`/`unDelegateBalance` ratios chosen adversarially).

### Recommendation
Avoid recomputing the proportional `transferUsage` independently for every partial un-delegation using floor/`long`-truncated division. Instead:
1. Track the exact usage-to-balance ratio at delegation time and use a monotonic/exact accounting method (e.g., accumulate remainders across partial un-delegations, or use fixed-point arithmetic with carried remainders) so that summing several partial un-delegations yields the same `transferUsage` as a single full un-delegation.
2. Alternatively, disallow reliance on repeated small operations by charging a minimum un-delegation granularity or by settling usage transfer strictly at final/full un-delegation rather than per-partial-call.

### Proof of Concept
Not independently executed (no runtime access); this is a structural code-level analysis. Suggested reproduction outline for a Devin agent with test-harness access:
1. Freeze TRX for BANDWIDTH on account A, delegate a large balance to account B (self-controlled).
2. Have B consume some bandwidth (increase `NetUsage`).
3. Instead of un-delegating the full balance from A in one call, issue many `UnDelegateResourceContract` transactions each un-delegating a tiny fraction of the balance.
4. Compare the sum of `transferUsage` moved back to A across the many small calls vs. the `transferUsage` that a single full un-delegation would have produced (as validated in `framework/src/test/java/org/tron/common/runtime/vm/FreezeV2Test.java`) [5](#0-4) .
5. Confirm the sum is smaller (drift), meaning B's `NetUsage` remains inflated relative to its now-reduced frozen balance, and/or A's post-un-delegation available bandwidth exceeds what a single-step un-delegation would allow.

  public long calculateGlobalNetLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForBandwidth();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalNetLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long totalNetLimit = chainBaseManager.getDynamicPropertiesStore().getTotalNetLimit();
    long totalNetWeight = chainBaseManager.getDynamicPropertiesStore().getTotalNetWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalNetWeight <= 0) {
      return 0;
    }
    if (totalNetWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalNetLimit, totalNetWeight);
    }
    long netWeight = frozeBalance / TRX_PRECISION;
    return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
  }
