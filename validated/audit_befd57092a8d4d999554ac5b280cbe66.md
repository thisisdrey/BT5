This confirms `BridgeRewardPayer` (used by `pallet_bridge_relayers::Config<BridgeRelayersInstance>` in `bridge-hub-westend`) routes `BridgeReward::Snowbridge` payouts through `PayAccountOnLocation::pay_reward`, which is fire-and-forget via `XcmSender::deliver` with `UnpaidExecution` — no query-based confirmation mechanism, unlike `PayOverXcm`/`TransferOverXcm` which use `ReportError`+`QueryResponse` and `check_payment`/`check_transfer` for exactly this reason. Audit Report

## Title
Snowbridge `PayAccountOnLocation::pay_reward` marks relayer rewards as claimed based on local XCM delivery success, not remote settlement, causing permanent loss of reward funds - ([File: bridges/snowbridge/primitives/core/src/reward.rs])

## Summary
`PayAccountOnLocation::pay_reward` returns `Ok(())` once the reward-minting XCM (containing `ReserveAssetDeposited`/`DepositAsset`) is merely accepted by the local `XcmSender::deliver`, without any confirmation that the remote `DepositAsset` executed successfully on AssetHub. `pallet_bridge_relayers::do_claim_rewards` treats this `Ok` as final settlement and permanently deletes the `RelayerRewards` entry and emits `RewardPaid`, so any remote-side execution failure results in irrecoverable loss of the relayer's reward.

## Finding Description
`pay_reward` in `bridges/snowbridge/primitives/core/src/reward.rs` builds an `Xcm` with `UnpaidExecution`, `DescendOrigin`, `UniversalOrigin`, `ReserveAssetDeposited`, and `DepositAsset`, then calls `validate_send`, `XcmExecutor::charge_fees`, and `XcmSender::deliver`, returning `Ok(())` immediately after delivery succeeds [1](#0-0) . `deliver` only guarantees local transport acceptance (e.g. into the HRMP channel); it provides no receipt of remote execution. Since the message uses `UnpaidExecution`, there is no fee-backed remote execution guarantee, and any remote failure (unregistered/untrusted reserve asset, filtered beneficiary, insufficient weight) produces no signal back to BridgeHub.

The caller, `Pallet::do_claim_rewards` in `bridges/modules/relayers/src/lib.rs`, takes the reward out of storage via `maybe_reward.take()` before calling `pay_reward`, and if `pay_reward` returns `Ok`, the closure returns `Ok(())`, which commits the removal via `try_mutate_exists` and emits `Event::RewardPaid` [2](#0-1) . There is no callback, receipt tracking, or retry mechanism tied to actual remote settlement.

This contrasts directly with the codebase's own `PayOverXcm`/`TransferOverXcmHelper` pattern, which is explicitly designed for asynchronous XCM payments: it appends a `SetAppendix` with `ReportError(QueryResponseInfo{...})` so the destination reports back execution status via `QueryResponse`, and exposes `check_payment`/`check_transfer` to confirm settlement before a caller (e.g. `pallet_salary::check_payment`) finalizes state [3](#0-2) [4](#0-3) . `PayAccountOnLocation` implements no equivalent query/receipt mechanism, so the invariant "state only advances after execution and settlement succeed" is violated.

This is wired into production BridgeHub Westend config: `BridgeRewardPayer::pay_reward` for `BridgeReward::Snowbridge` calls exactly this `PayAccountOnLocation::pay_reward` and is registered as `pallet_bridge_relayers::Config<BridgeRelayersInstance>::PaymentProcedure` on the `Runtime` [5](#0-4) .

## Impact Explanation
This falls under "duplicate settlement or payout" / "permanent user-fund lock" in the accepted impact gate: BridgeHub's local ledger irrevocably discharges its reward obligation (deletes `RelayerRewards`, emits `RewardPaid`) while AssetHub may never actually deliver value to the beneficiary if the remote `DepositAsset` fails. The relayer has no recourse — a subsequent `claim_rewards_to` call for the same reward fails with `Error::<T, I>::NoRewardForRelayer` since the storage entry is already gone.

## Likelihood Explanation
No privileged access or malicious actor is required. Any relayer calling the public `claim_rewards_to` extrinsic with `BridgeRewardBeneficiaries::AssetHubLocation(...)` is exposed to this if the remote AssetHub-side execution of the reward-mint XCM fails for any reason (unregistered/untrusted Ethereum-network reserve-asset trust configuration, filtered/malformed beneficiary, or transient congestion/weight issues) — none of which are attacker-controlled but all of which are realistic operational conditions given that `UnpaidExecution` provides no remote fee/weight guarantee.

## Recommendation
Replace the fire-and-forget delivery with an asynchronous, receipt-confirmed settlement pattern analogous to `PayOverXcm`: append a `ReportError`/`QueryResponse`-based appendix to the reward XCM, and only permanently clear `RelayerRewards` after `check_payment`-style confirmation of remote success. Alternatively, keep the reward in a "pending" state after delivery and provide a re-claim/retry path if no success confirmation is received within a timeout window, so a remote execution failure does not silently and permanently destroy the relayer's entitlement.

## Proof of Concept
1. Relayer accrues a `BridgeReward::Snowbridge` entry via `register_reward`.
2. Relayer calls `claim_rewards_to(BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(loc))`.
3. `BridgeRewardPayer::pay_reward` dispatches to `PayAccountOnLocation::pay_reward`, which succeeds through `validate_send`, `charge_fees`, and `deliver` — all purely local checks — and returns `Ok(())`.
4. `do_claim_rewards` deletes the `RelayerRewards` entry for this relayer/reward and emits `RewardPaid`.
5. On AssetHub, `DepositAsset { assets: AllCounted(1).into(), beneficiary }` fails (e.g., unregistered reserve trust for the `EthereumNetwork` asset, or a filtered/incompatible beneficiary) — no funds are credited.
6. Relayer calls `claim_rewards_to` again for the same reward and receives `Error::<T, I>::NoRewardForRelayer`, confirming permanent, unrecoverable loss of the reward with no remote-settlement verification ever having occurred, as demonstrated by the existing unit tests in `reward.rs` which only assert on local-step outcomes (`pay_reward_success`, `pay_reward_fails_on_xcm_validate_xcm`, `pay_reward_fails_on_charge_fees`, `pay_reward_fails_on_delivery`) and never model remote execution at all [6](#0-5) .

			let mut status = Status::<T, I>::get().ok_or(Error::<T, I>::NotStarted)?;

				Attempted { id, registered, amount } => (id, registered, amount),
				_ => return Err(Error::<T, I>::NoClaim.into()),
			};
			match T::Paymaster::check_payment(id) {

					// Payment failed: we reset back to the status prior to payment.
					if let Some(amount) = registered {

						claimant.status = ClaimState::Registered(amount);

						// been paid.
						status.total_unregistered_paid.saturating_reduce(amount);
					}
				},
				PaymentStatus::Success => claimant.status = ClaimState::Nothing,
				_ => return Err(Error::<T, I>::Inconclusive.into()),
