### Title
Fixed-window per-connection stream throttle allows ~2x burst amplification at window boundary - (File: streamer/src/nonblocking/stream_throttle.rs)

### Summary
The QUIC stream-throttling mechanism used by `SwQos` (the stake-weighted QoS controller) resets its per-connection stream counter only when the elapsed time since the last reset exceeds a fixed 100ms window, rather than aligning consumption to a monotonic period boundary or using a continuously-draining accounting scheme. This is the same class of bug as the PoolTogether "observation overwritten within the same period" issue: a value meant to bound activity for a period is not finalized/reset until the window fully elapses, so an attacker can concentrate activity at both ends of consecutive windows to get roughly double the intended budget in a short span of wall-clock time.

### Finding Description
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements the throttle window: [1](#0-0) 

It only zeroes `stream_count` when `Instant::now() - last_throttling_instant > STREAM_THROTTLING_INTERVAL` (100ms, `STREAM_THROTTLING_INTERVAL_MS`), and returns the (possibly stale) `last_throttling_instant` otherwise: [2](#0-1) 

`throttle_stream` then compares the still-accumulating `stream_count` to the per-peer budget `max_streams_per_throttling_interval` and sleeps only if the budget is exceeded, otherwise the stream is admitted immediately: [3](#0-2) 

`SwQos::on_new_stream` invokes this exact throttling path per opened stream, using `StakedStreamLoadEMA::available_load_capacity_in_throttling_duration` to compute the per-connection allotment for the window: [4](#0-3) 

Because the window is not aligned to any absolute boundary and is instead reset lazily on next access after the interval has elapsed, a connection can:
1. Open its full quota of streams (`max_streams_per_throttling_interval`) just before the 100ms window naturally expires.
2. Immediately after the window resets (next stream open call), open another full quota.

This yields roughly `2 * max_streams_per_throttling_interval` admitted streams (i.e., transactions entering the QUIC → SigVerify → banking-stage pipeline) within a very short real-time span, rather than the intended `max_streams_per_throttling_interval` per 100ms. This is directly analogous to the referenced report: a quantity is supposed to be capped/finalized per discrete period, but the implementation only "closes" the period lazily and allows the tracked state to be manipulated/exploited right at the boundary.

### Impact Explanation
This allows an unprivileged (or staked) QUIC client to exceed the leader's configured stake-weighted stream/transaction admission rate for its connection by close to 2x in bursts, which is a QoS evasion: it weakens the validator's designed protection against connections overwhelming SigVerify/banking-stage capacity, and if repeated by many connections near-simultaneously it amplifies aggregate load beyond what the throttling design intends to permit.

### Likelihood Explanation
The path is reachable by any TPU/QUIC client that can open streams on a connection (unprivileged from the protocol's perspective — no special validator/operator role required), and only requires timing stream opens relative to a 100ms wall-clock window, which is easily controllable by a client. The `SwQos` throttling path is the standard stake-weighted QoS implementation used in the TPU QUIC server.

### Recommendation
Replace the lazy, elapsed-time-triggered reset in `ConnectionStreamCounter::reset_throttling_params_if_needed` with a scheme that accounts for consumption relative to fixed, monotonically advancing period boundaries (e.g., align windows to `base_time + n * STREAM_THROTTLING_INTERVAL` similar to how `TokenBucket` continuously accrues/consumes tokens), or switch `SwQos` to use the same continuous `TokenBucket` accounting already used by `SimpleQos`'s stream counter, which does not have a hard reset boundary and therefore does not allow doubling at window edges.

### Proof of Concept
1. Establish a QUIC connection to the TPU that is routed through `SwQos` (staked connection), where `max_streams_per_throttling_interval` = N (from `StakedStreamLoadEMA::available_load_capacity_in_throttling_duration`).
2. At local time `t0`, just before `last_throttling_instant + 100ms` elapses, open N streams — all admitted without sleeping since `stream_count < N`.
3. Wait a few milliseconds until `Instant::now() - last_throttling_instant > 100ms` (natural window expiry).
4. Open N more streams immediately: `reset_throttling_params_if_needed` resets `stream_count` to 0 and `last_throttling_instant` to now, so all N are again admitted without throttling.
5. Net effect: `2N` streams admitted within a window much shorter than 100ms, doubling the intended per-connection throughput versus the configured `max_streams_per_throttling_interval` for that peer/stake weight.

    /// Reset the counter and last throttling instant and
    /// return last_throttling_instant regardless it is reset or not.
    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
