### Title
Optimistic StackerDB inventory update before chunk is actually stored — advertised inventory can diverge from real replica state (`File: stackslib/src/net/stackerdb/mod.rs`)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches the outbound `StackerDBChunkInvData` (the inventory it will send back to the pushing peer, and which is also used by other peers' sync logic) to claim the new chunk version *before* that chunk has actually been committed to the local StackerDB replica. Storage only happens later, asynchronously, when the chunk is forwarded to the relayer. This mirrors the reported bug class: two code paths track a single piece of state with different sources of truth — one path (the inventory response) treats the *requested/pushed* version as accepted, while the other path (the actual DB write via `try_replace_chunk`) is the true source of truth, and the two are not synchronized before the tracking value is used.

### Finding Description
`validate_received_chunk` (stackslib/src/net/stackerdb/mod.rs:649-718) performs only *validation* — signature, size, staleness, and write-count checks — and does not write anything to the database. It's called from `handle_unsolicited_StackerDBPushChunk` (stackslib/src/net/stackerdb/mod.rs:742-861): [1](#0-0) 

After validation succeeds, the code directly mutates the reply-inventory object to declare the new version as accepted: [2](#0-1) 

The comment "patch inventory -- we'll accept this chunk" makes explicit that this is an optimistic update: the function is only forwarding the chunk (`return Ok((x, true))`) to the relayer for real processing/storage — the actual persistence of the chunk via `StackerDBTx::try_replace_chunk` (stackslib/src/net/stackerdb/db.rs:400-438), which re-validates signer identity and version ordering, happens in a separate, later step outside this function's control.

This creates exactly the "two sources of truth" pattern from the analog report: the inventory reply that this node hands back to its peer (and that peer's downstream sync-scheduling decisions, e.g. `make_chunk_request_schedule` in stackslib/src/net/stackerdb/sync.rs:308-407, which prioritizes chunks by rarest/newest based on received `StackerDBChunkInvData`) is updated based on the *pushed* version, while the *actual* stored version is whatever `try_replace_chunk` ultimately commits (which can differ or fail, e.g. `StaleChunk`, `TooManySlotWrites`, `BadSlotSigner`, or simply not having been processed yet due to relayer queueing/backpressure).

### Impact Explanation
If the optimistic inventory patch is delivered to peers before (or in place of) an actual successful write, this node is asserting it possesses chunk data it does not yet have (or may never obtain, if the deferred write fails or the message is dropped). Downstream StackerDB sync neighbors use this inventory to decide priority and to skip re-fetching/re-pushing that slot version (`request.slot_version < *remote_version` checks in `make_chunk_request_schedule`), which can result in the affected chunk version never actually propagating through the network from this node, i.e., false inventory being propagated and consumed as canonical for sync-scheduling purposes. This matches the High-impact category "serving non-canonical state as canonical / steering a node off the tip via false inventory," since the false advertised version can cause other replicas to believe the data is already replicated by this node.

### Likelihood Explanation
Any peer that this node has an active P2P conversation with can trigger this path by sending an unsolicited `StackerDBPushChunk` with a validly-signed chunk (satisfying `validate_received_chunk`). No special privilege is required beyond an ordinary connected peer relationship — this is the standard StackerDB chunk-push gossip flow. The race window (patch inventory now, store later via relayer) exists on every such push, making the discrepancy reachable, though its practical severity depends on relayer processing succeeding shortly after in the common case; it is exploitable specifically when the deferred store fails or is delayed/dropped (buffering limits, `StaleChunk`, concurrent writes, disconnects before the relay step completes).

### Recommendation
Only patch/report the slot version in the outbound `StackerDBChunkInvData` after the chunk has been durably stored via `StackerDBTx::try_replace_chunk` succeeds, rather than immediately after signature/size validation. Alternatively, defer sending any acknowledgment/inventory update until the relayer confirms successful storage, ensuring the advertised inventory reflects only actually-committed StackerDB state.

### Proof of Concept
Conceptual PoC (mirrors `test_handle_unsolicited_stackerdb_push_chunk_future_view_validation` in stackslib/src/net/tests/relay/nakamoto.rs:1162-1304, extended to demonstrate the gap):
1. Set up a StackerDB with a signer-owned slot.
2. Send a validly-signed `StackerDBPushChunk` for slot 0, version 1.
3. Immediately inspect the returned `StackerDBChunkInvData` from `handle_unsolicited_StackerDBPushChunk` — it will show slot 0 at version 1.
4. Before the relayer processes/stores the chunk (e.g., by dropping the message post-validation, or inducing a `TooManySlotWrites`/concurrent write race in `try_replace_chunk`), query the actual on-disk slot version via `stackerdbs.get_slot_version(...)` — it will still show version 0 (or the prior version), proving the advertised inventory was ahead of the real, durably stored state.
