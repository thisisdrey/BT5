### Title
Unbounded array-length read in `PrecompiledContracts.extractBytes32Array()` causes attacker-controlled buffer over-read / crash in the `BatchValidateSign` precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The Alpine `tcpdump` CVE-2018-14881 is a buffer over-read caused by `bgp_capabilities_print()` trusting an attacker-supplied length field (BGP capability length) without validating it against the remaining buffer size before reading. The same bug class — trusting a length/offset word taken from untrusted input to index into an array without bounds checking — exists in java-tron's TVM precompile input parser `extractBytes32Array()`, which is reachable by any account that calls the `BatchValidateSign` precompiled contract at address `0x9` with crafted calldata.

### Finding Description
`PrecompiledContracts.extractBytes32Array()` reads a length word directly out of the caller-supplied `words` array and then loops that many times, indexing further into `words` with no bounds check: [1](#0-0) 

```java
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
  int len = words[offset].intValueSafe();
  byte[][] bytes32Array = new byte[len][];
  for (int i = 0; i < len; i++) {
    bytes32Array[i] = words[offset + i + 1].getData();
  }
  return bytes32Array;
}
```

This is unlike its sibling helpers `extractBytesArray()` and `extractSigArray()` in the same file, which explicitly guard `offset > words.length - 1` before indexing: [2](#0-1) 

`extractBytes32Array` is called from `BatchValidateSign.doExecute()` to build the `addresses` array using an `offset` computed entirely from attacker-controlled calldata (`words[2].intValueSafe() / WORD_SIZE`): [3](#0-2) 

```java
DataWord[] words = DataWord.parseArray(data);
byte[] hash = words[0].getData();
...
byte[][] addresses = extractBytes32Array(
    words, words[2].intValueSafe() / WORD_SIZE);
```

`words` (the parsed `DataWord[]`) is sized to the actual calldata length, so an attacker who controls `data` (the raw call payload to precompile address `0x9`) fully controls:
- `offset` (via `words[2]`), which can point at or past the end of `words`, and
- `len` (via `words[offset]`), which is read from wherever `offset` points, and can be an arbitrarily large 32-bit value (`intValueSafe()`), causing:
  - `ArrayIndexOutOfBoundsException` when `words[offset]` or `words[offset + i + 1]` is out of range (buffer over-read analog of the BGP parser bug), or
  - Attempted allocation of `new byte[len][]` with a huge `len`, causing `NegativeArraySizeException` or `OutOfMemoryError`.

Under `VMConfig.allowTvmSelfdestructRestriction()`, there's a size check on `sigArraySize`/`addrArraySize` before calling `extractBytesArray`/`extractSigArray`, but this check does not bound `extractBytes32Array`'s own out-of-range `offset` read — the check reads `words[words[2].intValueSafe() / WORD_SIZE]` itself with the same unchecked offset, so if the offset is unbounded, the exception/crash happens even before reaching the size-limit check.

### Impact Explanation
Any unprivileged account can construct a transaction that triggers a `TVM` call to the `BatchValidateSign` precompile (address `0x9`) with a malformed `data` payload where `words[2]` decodes to an out-of-range offset or a huge length. This throws an unchecked `ArrayIndexOutOfBoundsException`, `NegativeArraySizeException`, or triggers massive allocation (`OutOfMemoryError`) inside VM execution. Depending on how exceptions from precompile execution propagate through `Program`/`VMActuator` execution (uncaught runtime exceptions vs. the `Throwable` catch used in `BatchValidateSign.execute()` — note this wraps `doExecute()` in try/catch for `Throwable`, which does catch `Error` types like `OutOfMemoryError` too, mitigating some cases). This reduces the severity from full node crash to a potential resource-exhaustion / repeated GC-pressure / possible node instability issue when many such contract calls are broadcast, since `new byte[len][]` with a large `len` can force large transient allocations before the size check subsequently rejects the count.

### Likelihood Explanation
High likelihood of triggering the code path: `BatchValidateSign` is a public, gated-only-by-`VMConfig.allowTvmSolidity059()` precompile reachable from any deployed smart contract via a `STATICCALL`/`CALL` to address `0x9`, requiring no special permission, no signature, and no privileged account — only a valid TVM contract invocation with attacker-chosen calldata.

### Recommendation
Add the same `offset > words.length - 1` bounds guard used in `extractBytesArray` and `extractSigArray` to `extractBytes32Array`, and additionally clamp/validate `len` (e.g., cap it at `MAX_SIZE` before allocating `new byte[len][]`) and validate `offset + len` does not exceed `words.length` before the loop executes, mirroring `verifyLength`-style checks used elsewhere in RLP decoding (`framework/src/main/java/org/tron/core/capsule/utils/RLP.java`).

### Proof of Concept
1. Deploy a trivial contract that calls precompile address `0x0000...0009` (BatchValidateSign) via `staticcall`/`call`, passing raw crafted `data`.
2. Craft `data` such that:
   - `words[0]` = arbitrary hash (32 bytes),
   - `words[1]` = signature-array offset word (small valid value),
   - `words[2]` = a value that, divided by `WORD_SIZE`, yields an `offset` ≥ `words.length` (e.g., set `words[2]` to a large 32-byte integer).
3. Broadcast the transaction calling this contract. `extractBytes32Array(words, offset)` executes `words[offset].intValueSafe()` with `offset` out of bounds, throwing `ArrayIndexOutOfBoundsException` (or, if `offset` is in range but the word at that location decodes to a very large `len`, `new byte[len][]` attempts an oversized allocation).
4. Because `doExecute()` is wrapped only at the top level (`execute()` catches `Throwable`), most exceptions are absorbed into a `DATA_FALSE` result today — this reduces the practical impact to unnecessary large transient allocations for large-but-not-huge `len` values (since `OutOfMemoryError` is also caught), rather than a full crash. The primary confirmed defect is the missing bounds check itself, mirroring the CVE's root cause (untrusted length field used without bounds validation) — full crash/DoS impact could not be conclusively confirmed with certainty from static analysis alone given the surrounding `Throwable` catch; further dynamic testing would be needed to determine whether extremely large `len` (e.g., `Integer.MAX_VALUE`) can still cause an unrecoverable `OutOfMemoryError` that destabilizes the JVM before being caught.
