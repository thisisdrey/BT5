### Title
Cost model's account-data-allocation accounting only inspects top-level system-program instructions, letting CPI-driven account growth evade the per-block allocation budget - ([File: cost-model/src/cost_model.rs])

### Summary
The Sherlock finding shows Illuminate charging its protocol fee based on the *declared* order amount while ignoring the *actual* balance delta ("premium") realized after execution, letting users route value through a path the fee calculator doesn't see. The analogous pattern in Agave is `CostModel::calculate_allocated_accounts_data_size` in [1](#0-0) , which determines the accounts-data-size cost charged against the network-wide `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` budget by statically inspecting only the transaction's **top-level** instructions and only when the instruction's `program_id` equals the System Program id.

### Finding Description
`calculate_account_data_size_on_instruction` explicitly gates on the top-level `program_id`: [2](#0-1) 

and `calculate_allocated_accounts_data_size` sums allocation size only from instructions matched this way, iterating `transaction.program_instructions_iter()` (top-level compiled instructions), never inner/CPI instructions: [1](#0-0) 

This value is fed into `TransactionCost.allocated_accounts_data_size` at cost-calculation time [3](#0-2)  and is what `CostTracker::add_transaction_cost` accumulates into the block-wide `allocated_accounts_data_size` counter used for QoS/block-inclusion throttling: [4](#0-3) . That counter is checked against `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100,000,000 bytes per block) defined in [5](#0-4) .

If a user's transaction invokes a custom (BPF) program which itself performs a CPI into the System Program's `CreateAccount`/`Allocate`/`AllocateWithSeed` (as exercised by the test programs in `programs/sbf/rust/realloc_invoke/src/lib.rs`, e.g. `INVOKE_REALLOC_TO_THEN_LOCAL_REALLOC_EXTEND`) [6](#0-5) , the actual account-data growth still occurs and is enforced per-transaction at runtime, but the **cost-model estimate used for block-level accounting is zero for that allocation**, because the top-level instruction's `program_id` is the caller's custom program, not `system_program::id()`. This is exactly the "declared amount vs. realized balance/side-effect" mismatch from the Illuminate report: the fee/cost is computed from the visible, declared instruction, while the actual resource consumption occurs through an indirect path (CPI) that the pricing logic never inspects.

### Impact Explanation
Because block-level accounts-data-size accounting undercounts CPI-driven allocations, transactions that grow account data primarily through CPI to the System Program are charged less against `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` than transactions that do the identical allocation via a top-level System Program instruction. This is a QoS-evasion / underpriced-work condition: the block-inclusion cost accounting can be systematically bypassed, allowing more real account-data growth to be packed into a block than the cost model's throttle intends, without a matching bump in the tracked cost. This matches the accepted category "QoS evasion, or grossly underpriced pre-fee work" for this scan.

### Likelihood Explanation
Reachable by any unprivileged user: deploying a trivial BPF program that CPIs into the System Program to create/allocate large accounts, and calling it from a transaction, requires no special privilege. The `realloc_invoke` test program in the repository already demonstrates this exact CPI-allocation pattern, showing the code path is exercised and reachable in normal transaction processing (not a mocked-only or theoretical scenario).

### Recommendation
Extend the cost-model's account-data-allocation accounting to also account for accounts data growth caused indirectly via CPI, not just top-level System Program instructions — e.g. by using post-execution actual data-size deltas (already tracked at runtime for the per-transaction cap) to adjust/true-up the block-level `allocated_accounts_data_size` counter after execution, analogous to how `calculate_cost_for_executed_transaction` already trues up CU and loaded-accounts-data-size costs using actual execution values [7](#0-6) .

### Proof of Concept
1. Deploy a program with the behavior shown in `programs/sbf/rust/realloc_invoke/src/lib.rs`'s `INVOKE_REALLOC_TO_THEN_LOCAL_REALLOC_EXTEND`/`INVOKE_REALLOC_TO` handlers [6](#0-5) , which CPIs into the System Program (or performs an account resize reachable via System Program CPI) to grow account data.
2. Submit a transaction invoking this program (top-level instruction targets the custom program, not `system_program::id()`).
3. Observe that `CostModel::calculate_allocated_accounts_data_size` returns `SystemProgramAccountAllocation::None` for the top-level instruction (since `program_id != system_program::id()` at [8](#0-7) ), so `tx_cost.allocated_accounts_data_size()` is 0, and `CostTracker::add_transaction_cost` [4](#0-3)  adds nothing to the block's `allocated_accounts_data_size`, even though the account's actual data size has grown by the CPI-requested amount.
4. Repeating this across many transactions in a block allows real account-data growth to exceed what `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` [5](#0-4)  is meant to bound, without the cost model ever reflecting the true cost.

    /// eventually, potentially determine account data size of all writable accounts
    /// at the moment, calculate account data size of account creation
    fn calculate_allocated_accounts_data_size<'a>(
        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
        feature_set: &FeatureSet,
    ) -> u64 {
        let mut tx_attempted_allocation_size = Saturating(0u64);
        for (program_id, instruction) in instructions {
            match Self::calculate_account_data_size_on_instruction(
                program_id,
                instruction,
                feature_set,
            ) {
                SystemProgramAccountAllocation::Failed => {
                    // If any system program instructions can be statically
                    // determined to fail, no allocations will actually be
                    // persisted by the transaction. So return 0 here so that no
                    // account allocation budget is used for this failed
                    // transaction.
                    return 0;
                }
                SystemProgramAccountAllocation::None => continue,
                SystemProgramAccountAllocation::Some(ix_attempted_allocation_size) => {
                    tx_attempted_allocation_size += ix_attempted_allocation_size;
                }
            }
        }

        // The runtime prevents transactions from allocating too much account
        // data so clamp the attempted allocation size to the max amount.
        //
        // Note that if there are any custom bpf instructions in the transaction
        // it's tricky to know whether a newly allocated account will be freed
        // or not during an intermediate instruction in the transaction so we
        // shouldn't assume that a large sum of allocations will necessarily
        // lead to transaction failure.
        (MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION as u64)
            .min(tx_attempted_allocation_size.0)
    }

        self.transaction_count += 1;
