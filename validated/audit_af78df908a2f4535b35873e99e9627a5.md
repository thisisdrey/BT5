### Title
Unbounded `DelegatedResourceAccountIndexStore.getIndex`/`getV2Index` prefix scan allows API-reachable resource-exhaustion DoS via mass small-amount delegations - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`DelegatedResourceAccountIndexStore.getIndex` and `getV2Index` build a full account's delegation index by loading and sorting **every** matching DB entry under a `from`/`to` address prefix into memory with no size cap, similar in class to the `DepositQueue.remove` unbounded-iteration bug in the referenced report. Because any signed account can call `DelegateResourceContract`/`DelegateResourceContractV2` cheaply and repeatedly to create a large number of distinct delegation relationships to (or from) a single address, an attacker can inflate the prefix range for that address to an arbitrary size, and any subsequent query resolving that address's delegation index becomes increasingly expensive, unlike the bounded, capped operations elsewhere in the freeze/vote code (e.g. `UnfreezeBalanceV2ActuatorTest` shows a hard cap of ~32 pending unfreeze entries, and `MarketSellAssetActuator.matchOrder` is capped by `MAX_MATCH_NUM`).

### Finding Description
`getWithPrefix` (used by both `getIndex` and `getV2Index`) performs: [1](#0-0) 

For every call it executes `this.prefixQuery(key)` twice (once for the "from" side, once for the "to" side) and materializes **all** matching entries into an `ArrayList`, then sorts the full list by timestamp, with no upper bound on the number of entries scanned, sorted, or returned — unlike other list operations in the codebase that are explicitly capped (e.g. `MAX_MATCH_NUM` in market order matching, or the ~32-item cap on `UnfreezeV2` entries enforced in `UnfreezeBalanceV2Actuator`).

The number of entries under a given address's prefix is attacker-controlled and unbounded: each new call to `DelegateResourceActuator`/`DelegateResourceContractV2` from a unique `(owner, receiver)` pair adds one more `from`/`to` key under both endpoints' prefixes: [2](#0-1) 

There is no maximum-delegatee-count validation on the delegate actuators before writing new index entries, so a single low-value account can create thousands of unique delegation relationships targeting one victim address at minimal cost (only requiring `freezeBalance`/`freezeBalanceV2` with dust amounts), continually growing that victim's prefix range in `DelegatedResourceAccountIndexStore`.

### Impact Explanation
Any subsequent resolution of that address's delegation index (a read path, but one whose cost grows with attacker-controlled state) becomes progressively more expensive to compute — an unbounded prefix scan, in-memory list construction, and sort. If the number of index entries for an address grows large enough (analogous to the "few thousand" queue-size threshold in the referenced DepositQueue bug), a single call resolving that index can consume excessive CPU/memory on the node process. Since this can be triggered from query paths that serve external API clients, an attacker can degrade or deny that portion of node service (an API the node can no longer serve promptly), which is a resource-exhaustion/availability impact consistent with the "no vulnerability found" boundary only if it cannot be confirmed as concretely reachable and unbounded — I was not able to confirm within the available search results that `getIndex`/`getV2Index` (as opposed to the newer `convert`+`delegate` prefix-based model, which is the default in current forks) are still reachable from a live HTTP/gRPC handler in this specific codebase snapshot; that mapping requires further verification in `Wallet.java`'s delegated-resource-index query methods, which the search did not conclusively surface.

### Likelihood Explanation
Creating many unique delegation relationships is cheap (bounded only by TRX available to freeze in small increments and standard transaction fees), and no per-account cap on the number of distinct delegatees/delegators exists in the actuator validation logic reviewed. However, exploitability depends on whether the legacy (`FROM_PREFIX`/`TO_PREFIX`) code path — gated behind `!dynamicPropertiesStore.supportAllowDelegateOptimization()` — is still active on mainnet, since the "optimization" path (`delegate`/`unDelegate` with V2 prefixes) still uses `getWithPrefix` for `getV2Index`, meaning the same unbounded-scan structure persists regardless of optimization flag.

### Recommendation
- Enforce a maximum count of unique delegate relationships per account (analogous to the `MAX_MATCH_NUM` cap in market order matching or the frozen-supply-count cap in `AssetIssueActuator`), rejecting new `DelegateResourceContract`/`DelegateResourceContractV2` transactions once an address exceeds the limit.
- Bound `prefixQuery` result sizes in `getWithPrefix` with a hard limit and/or paginate results instead of loading and sorting the entire prefix range in one call.
- Consider replacing the linked/prefix-scan index structure with a data structure supporting constant- or logarithmic-time insert/remove/lookup, as recommended for the original `DepositQueue` bug.

### Proof of Concept
Conceptual (not verified end-to-end against a live API handler due to inability to confirm the exact HTTP/gRPC handler wiring in this snapshot):
1. Attacker controls or funds many small accounts, each freezing a minimal amount and delegating it to a single victim receiver address via `DelegateResourceContract`, each with a distinct owner address — this creates one `TO_PREFIX`/`FROM_PREFIX` (or V2 equivalent) entry per delegation without any cap.
2. Repeat until the victim address accumulates a very large number of index entries (thousands+).
3. Trigger any code path that calls `DelegatedResourceAccountIndexStore.getIndex`/`getV2Index` for the victim address (e.g. an account-index query), causing `getWithPrefix` to scan, materialize, and sort the entire unbounded entry set in a single call, consuming disproportionate CPU/memory relative to normal usage.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
