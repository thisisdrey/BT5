**Reasoning:**

`ShardLayoutV3::recent_split()` only needs to expose the single most recent parent→children mapping because `ShardId` allocation in `ShardLayoutV3::derive_impl` is strictly monotonically increasing and shard ids are never reused: [1](#0-0) 

Specifically, `max_shard_id` is computed from the *currently active* `shard_ids` list (which excludes retired parents), and every new split allocates `max_shard_id + 1` and `max_shard_id + 2` as the new children. Since `max_shard_id` only grows monotonically across successive derivations (each split's new children become the new max), no split can ever produce a child `shard_id` that collides with any previously-used `shard_id` — whether that prior id belonged to a still-active shard or a retired parent from an older split. The `shards_split_map` itself is also cumulative across the full history (`pub(crate) shards_split_map: ShardssplitMapV3` doc at lines 111-113), so parent ids from all past splits remain permanently reserved and are never reassigned. [2](#0-1) 

Because `ShardUId` for V3 always uses a fixed `version = 3` combined with a `shard_id` drawn from this strictly-increasing, never-reused allocation scheme, the union of `parent_shard`/`left_child_shard`/`right_child_shard` `ShardUId`s across any two (or more) chained `from_shard_layout` calls can never contain a duplicate `(version, shard_id)` pair — the invariant the question asks about is guaranteed structurally by the id-allocation logic in `derive_impl`, independent of scheduling/timing of resharding events across epochs. `recent_split()` returning only the latest split is therefore sufficient and safe for `from_shard_layout`'s purpose of deducing a single split event at a time: [3](#0-2) 

There is no reachable attacker-controlled path (account creation timing, transaction submission, etc.) that can influence `max_shard_id` computation or force id reuse — this is purely a function of the deterministic, monotonic split-history data structure maintained by validators/epoch-manager during layout derivation, not by end-user transactions. No unprivileged-client-triggerable state-root divergence or shard-halt exists via this mechanism.
