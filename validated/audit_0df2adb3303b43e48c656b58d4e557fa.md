## Title
Self-trading via `MarketSellAssetActuator` causes lost/duplicated account state due to a stale `AccountCapsule` fetch analogous to the wXTZ double-balance bug - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The wXTZ report describes a class of bug where a token holder's account is fetched into an in-memory object, mutated for one side of a transfer, but a second, independently-fetched (and therefore stale) copy of the *same* underlying account is used to compute the other side of the transfer. Because the stale copy doesn't reflect the first mutation, the two writes race and the net effect is that value is duplicated or lost. `MarketSellAssetActuator`, reachable directly from an unprivileged `MarketSellAssetContract` transaction (an "order placer"), contains this exact pattern when a user's sell order matches against their own resting order in the order book (self-trade), which `validate()` never forbids.

### Finding Description
In `execute()` (`actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java:99-162`), the taker's account is fetched once: [1](#0-0) 

That single `accountCapsule` object is mutated in memory (fee, sell-side balance reduction, buy-side balance addition for matched fills) throughout `transferBalanceOrToken`, `createAndSaveOrder`, and `matchOrder`, and is only persisted to `accountStore` at the very end of `execute()`: [2](#0-1) 

However, inside `matchSingleOrder`, the maker side of the trade is credited through a *different* overload of `addTrxOrToken` that independently re-fetches the maker's account from `accountStore` and immediately writes it back: [3](#0-2) 

If the taker's order matches a resting maker order placed earlier by the **same address** (a self-trade), then during this single `execute()` call:
1. `accountCapsule` (taker) already holds an in-memory balance/asset state that has been debited for the sell and is not yet flushed to `accountStore`.
2. `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` calls `accountStore.get(orderCapsule.getOwnerAddress())`, which — since the taker's writes haven't been committed yet — returns a **stale** copy of the same account (pre-dating the in-memory taker mutations), applies the maker credit to that stale copy, and immediately `put()`s it back to the store.
3. At the end of `execute()`, `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` overwrites the store again with the taker's in-memory object, which itself doesn't know about the maker-side credit applied in step 2.

This is structurally identical to the wXTZ bug: two independent, stale reads of the same underlying account object are mutated separately and their writes race, so one side's update is silently discarded while the other's is kept — causing either lost or duplicated asset/TRX balance for the same user, depending on write order and the accumulation of unrelated mutations already staged in `accountCapsule`.

Nowhere in `validate()` (lines 165-281) or in `matchOrder`/`matchSingleOrder` is there a check that the maker order's owner differs from the taker (`contract.getOwnerAddress()`); other actuators in the same codebase (`TransferActuator`, `TransferAssetActuator`, `ParticipateAssetIssueActuator`, `DelegateResourceActuator`, `UnDelegateResourceActuator`) all explicitly reject a same-address counterparty (e.g. `"Cannot transfer TRX to yourself."`, `"receiverAddress must not be the same as ownerAddress"`), confirming that self-interaction was recognized elsewhere as a hazard but was missed for the market/exchange order-matching path.

### Impact Explanation
Depending on the exact sequencing of mutations vs. the final `put`, this can result in:
- Loss of the maker-side credit (the user's matched buy-side proceeds silently disappear), or
- Duplication/inflation of account balance or TRC10 asset balance if the taker's final write does not encompass the maker credit and the maker's earlier `put` is not fully overwritten (e.g., differing fields on the same key, or interleaving with other in-flight modifications in a block with multiple such transactions).
Either outcome directly violates system invariants: it can create unbacked TRX/TRC10 balance out of nothing (inflation, "free money" for the attacker) or destroy funds. This matches the "unbacked balance"/"theft of funds" impact bar required by the rules.

### Likelihood Explanation
This is trivially reachable by any account: place a sell order (`MarketSellAssetContract`) for pair A→B, then place another sell order for pair B→A at a matching price, from the **same address**. `validate()` never checks that the maker owner differs from the taker owner, and the order book (`pairPriceToOrderStore`/`orderStore`) does not filter by address in `matchOrder`. No special privileges, front-running, or attacker infrastructure are required — a single account and two ordinary transactions suffice.

### Recommendation
**Short term:** In `matchSingleOrder`/`addTrxOrToken`, detect when `makerOrderCapsule.getOwnerAddress()` equals the taker's `contract.getOwnerAddress()` and, in that case, apply the maker-side credit to the *same* in-memory `takerAccountCapsule` object already held by `execute()` instead of re-fetching a fresh `AccountCapsule` from `accountStore`. Alternatively, disallow self-matching entirely by skipping/rejecting maker orders whose owner equals the taker's owner address, consistent with the yourself-checks already present in `TransferActuator`, `TransferAssetActuator`, and the delegate-resource actuators.

**Long term:** Add invariant-based tests (as urged in the original report) that specifically construct self-trade scenarios across all actuators that read/write `AccountCapsule` more than once per execution, verifying that no combination of same-address parameters can result in net balance creation or loss.

### Proof of Concept
1. Enable market transactions (`supportAllowMarketTransaction`).
2. From address `X`, submit `MarketSellAssetContract` selling `100 TokenA` for `100 TokenB` (creates a resting order on the A→B book).
3. From the same address `X`, submit `MarketSellAssetContract` selling `100 TokenB` for `100 TokenA` matching the resting order at the same price.
4. In `execute()` for the second transaction, `matchOrder`→`matchSingleOrder` is invoked with `makerOrderCapsule.getOwnerAddress() == takerAccountCapsule` address `X`. The maker-side `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` fetches a stale copy of `X`'s account (pre-dating the fee/sell debit already staged in the in-memory `accountCapsule`), credits it, and writes it to `accountStore` immediately.
5. `execute()` finishes and overwrites `accountStore` again with the taker's `accountCapsule`, which does not include the maker credit written in step 4 — net result: the credit from step 4 is lost (or, depending on field overlap and ordering across the whole block, can instead be duplicated) rather than reflecting a balanced self-trade with no net asset change.

*Note: I was not able to fully trace `AccountStore.get()`'s caching semantics (whether it always deserializes a fresh object per call or shares a cache) within the available index; this would need to be confirmed in a full checkout to pin down the exact final numeric outcome (loss vs. duplication) of the race, though the structural bug — two independently-fetched, non-aliased copies of the same account being mutated and written back separately within one execute() call, with no self-trade guard — is confirmed from the source shown above.*
