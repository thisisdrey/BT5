### Title
Unauthenticated RecvError packets let an attacker tear down victim tunnels by guessing/observing the numeric `RemoteIndex`, without any binding to tunnel content or certificate - (File: outside.go)

### Summary
Nebula identifies an established tunnel (`HostInfo`) purely by a 32-bit numeric index (`remoteIndexId`/`localIndexId`) that is never bound to the tunnel's cryptographic content. The unauthenticated, unencrypted `RecvError` packet type is processed by looking up a hostinfo solely from that attacker-supplied index via `QueryReverseIndex`, mirroring the reported bug class where an entity is identified by a content-independent numeric ID rather than something tied to its actual data/identity.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` packets before any cryptographic authentication: [1](#0-0) 

The handler resolves the target tunnel purely by the numeric `h.RemoteIndex` field carried in the plaintext header, using the `RemoteIndexes` map, which is populated with indexes that are explicitly documented as "outside our control": [2](#0-1) 

```go
hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
...
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    f.l.Info("Someone spoofing recv_errors?", ...)
    return
}
f.closeTunnel(hostinfo)
f.handshakeManager.DeleteHostInfo(hostinfo)
```

The only check that ties this action back to the "real" tunnel is a comparison of the UDP source address against the hostinfo's last known remote endpoint (`hr != addr`). Nothing about the RecvError message is authenticated by the Noise session keys or by certificate — index-and-source-address is the entire trust model, exactly as publication IDs (an opaque, content-independent counter) were the entire trust model in the reported Lens finding. The hostmap code itself acknowledges the index namespace is attacker-influenced and only logs rather than rejects the resulting ambiguity: [3](#0-2) [4](#0-3) 

Because `remoteIndexId` is a bare 32-bit value with no content binding, and `RemoteIndexes` is populated unconditionally on `unlockedAddHostInfo` regardless of whether an existing distinct peer already owns that value, an attacker who can observe or guess a peer's live `RemoteIndex` (e.g., via passive on-path observation, or a spoofed/forged path where UDP source-address anti-spoofing is weak) can trigger `closeTunnel` + `DeleteHostInfo` on that hostinfo, with only a same-endpoint check standing between the attacker and remote state poisoning of an arbitrary established tunnel.

### Impact Explanation
An attacker able to spoof the UDP source address for the victim's peer endpoint (or observe the index value on path) can force termination of an active, fully-authenticated tunnel between two legitimate parties by sending a single unauthenticated `RecvError` packet carrying the guessed/observed index — a remote state-poisoning / denial-of-service impact on the mesh, achieved purely through content-independent numeric-index confusion, analogous to how a content-independent publication ID let an attacker's `act()` call land on the wrong publication after a reorg.

### Likelihood Explanation
Exploitation requires either (a) an on-path or traffic-observing position to learn the exact 32-bit `RemoteIndex` and current remote `UdpAddr`, or (b) the ability to spoof the source IP:port that already matches the target's current remote endpoint. Both preconditions are non-trivial but plausible for on-path/adjacent-network attackers (the report's own precedent — chain reorgs / index reuse — argues that "unlikely but not negligible" content-independent identifier confusion is exactly the class of issue meant to be flagged here). No certificate or successful handshake is required to send the `RecvError` packet itself.

### Recommendation
Do not resolve or act on hostinfo state based solely on an unauthenticated numeric index. At minimum:
- Require `RecvError` handling to additionally verify some value derived from the current session (e.g., a MAC over the index using the current tunnel's derived key, or require the packet to be delivered only over an already-authenticated channel) rather than relying on index + source-address alone.
- When storing `RemoteIndexes`, avoid silently allowing an index to be shadowed/reused across different peer identities without stronger anti-collision handling than a log line.

### Proof of Concept
1. Establish tunnels `A<->Victim` and note `Victim`'s `remoteIndexId` value assigned to `A` (observable on-path, e.g., via traffic capture or a compromised relay position, since it is sent in plaintext handshake payloads: `p.InitiatorIndex`/`p.ResponderIndex`, see [5](#0-4) ).
2. Attacker crafts a plaintext `header.RecvError` packet with `RemoteIndex` set to the observed index, and sends it from a UDP source address spoofed/matching `A`'s current remote endpoint as seen by `Victim`.
3. `Victim`'s `handleRecvError` ( [2](#0-1) ) finds the hostinfo via `QueryReverseIndex`, the address check passes (source matches `hr`), and `closeTunnel`/`DeleteHostInfo` are invoked — tearing down the legitimate `A<->Victim` tunnel without any cryptographic proof of authorization, purely from a content-independent numeric identifier.

	}
