Audit Report

## Title
`ERC20Transactor` credits/debits nominal `amount` instead of verified ERC20 balance delta, allowing fee-on-transfer or transfer-hook tokens to desynchronize the shared checking account - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`withdraw_asset_with_surplus` and `deposit_asset_with_surplus` mint/spend XCM holding credit equal to the nominal `amount` decoded from the XCM `Asset`, verifying only that `IERC20::transfer` returned `true` via `abi_decode_returns_validate`, never comparing `balanceOf(ERC20TransfersCheckingAccount)` before and after the call. Because `ERC20TransfersCheckingAccount` is a single shared account for all ERC20 assets matched by `assets_common::ERC20Matcher`, a fee-on-transfer, rebasing, or transfer-hook ERC20 that delivers less than `amount` to the checking account causes the XCM holding ledger to be overstated relative to the checking account's real token balance.

## Finding Description
In `withdraw_asset_with_surplus`, the code calls `IERC20::transferCall { to: checking_address, value: amount }` and, upon a successful (`true`) return value, unconditionally credits `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — the nominal `amount`, not any measured delta. [1](#0-0) 

Symmetrically, `deposit_asset_with_surplus` transfers the same nominal `amount` from `TransfersCheckingAccount` to the beneficiary and treats a `true` return as full success, again with no balance verification. [2](#0-1) 

There is no call to `balanceOf` anywhere in the file, and no other guard reconciles the credited/debited holding amount with the checking account's actual ERC20 balance. This is wired into Asset Hub Westend's `AssetTransactors` via `ERC20Transactor`, using the single shared `ERC20TransfersCheckingAccount` (`PalletId(*b"py/revch")`) for every ERC20 asset matched by `assets_common::ERC20Matcher`. [3](#0-2) 

Any ERC20 contract whose `transfer` does not move exactly `amount` tokens (fee-on-transfer, deflationary burn, rebasing, or arbitrary transfer hooks) — while still returning `true` — causes the transactor to credit/debit the nominal amount regardless of the real balance change, silently desynchronizing the shared checking account's real balance from the sum of nominal credits issued across all users of that asset class.

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" / fund-lock impact category: once the checking account's real balance for a given ERC20 falls behind the cumulative nominal credits, later `deposit_asset_with_surplus` calls for unrelated users of the same asset can revert with `"ERC20 contract transfer failed"` due to insufficient real balance, or in other orderings allow one user's shortfall to be paid out of other users' funds held in the same shared account. The root cause is a genuine logic flaw in `ERC20Transactor` (missing balance-delta verification), not a privileged-actor or off-chain-infra issue.

## Likelihood Explanation
Reachable by any unprivileged user: deploying a non-standard ERC20 via `pallet-revive` and registering it as an `AccountKey20` XCM asset location is unprivileged, and executing withdraw/deposit sequences through `pallet_xcm::execute`/`send` is a normal, permissionless XCM operation, as demonstrated by the existing negative-path tests for non-conformant ERC20 behavior in the test suite. [4](#0-3) 
No special privilege, governance action, or off-chain trust assumption is required beyond deploying a contract with non-1:1 transfer semantics.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `IERC20::balanceOf` on the checking account (and/or beneficiary) immediately before and after the `transfer` call, and use the observed balance delta — not the nominal `amount` — both for the `AssetsInHolding` credit/debit and as the success condition, rejecting the operation (or crediting only the actual delta) when it diverges from `amount`.

## Proof of Concept
1. Deploy a `pallet-revive` ERC20 contract whose `transfer(to, amount)` deducts a fee (e.g., 1%) before crediting `to`, but still returns `true`.
2. Register the contract address as an XCM asset location matched by `assets_common::ERC20Matcher`.
3. Execute `withdraw_asset` (1000 units) + `deposit_asset` to beneficiary B via `pallet_xcm::execute`: only 990 real tokens land in `ERC20TransfersCheckingAccount`, yet holding is credited 1000, and the deposit instructs 1000 out of the checking account.
4. Repeat across multiple users of the same fee-on-transfer asset until the checking account's real balance is insufficient to honor the sum of inflated nominal credits, causing `deposit_asset_with_surplus` to fail with `"ERC20 contract transfer failed"` for users unrelated to the deficient token, or to pay out of other users' balances.
