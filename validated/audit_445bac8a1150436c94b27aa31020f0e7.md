### Title
Non-atomic replay-window check-then-act in `ConnectionState.Decrypt`/`VerifyRelay` allows duplicate-packet processing under concurrent readers - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay guard into two separately-locked critical sections: `window.Check()` runs and releases `decryptLock`, then the (comparatively expensive) AEAD decryption runs unguarded, and only afterward is `decryptLock` re-acquired to call `window.Update()`. Because state confirmation (`Update`) happens only *after* an external, unlocked operation (`DecryptDanger`) rather than atomically with the check, the same encrypted packet delivered to two socket-reader routines concurrently can pass `Check()` twice before either calls `Update()`, producing double authenticated delivery of one packet — the same "state update happens only once/late, after an externally-observable operation that can be triggered multiple times before the guard finalizes" bug class described in the H-05 report, where `sponsor()`'s `totalSponsored` update happened only after the reentrant `mint()` callback.

### Finding Description
`Decrypt` (`connection_state.go:61-82`) and `VerifyRelay` (`connection_state.go:85-108`) both follow this pattern:
```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
if !result { return nil, ErrAlreadySeen }

out, err = cs.dKey.DecryptDanger(...)   // unlocked, expensive AEAD op
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)  // guard is only finalized here
cs.decryptLock.Unlock()
``` [1](#0-0) [2](#0-1) 

`Bits.Check` only reads the window state; it does not reserve or mark the counter as consumed [3](#0-2) . Only `Bits.Update` mutates the bitmap to record the counter as seen [4](#0-3) . Between the `Check` and the later `Update`, the mutex is released, so the anti-replay guard is not atomic across the whole operation — exactly analogous to the reported pattern where `totalSponsored`/the `Sponsored` event (the guard/state) was updated only after a reentrant call, letting the operation be repeated before the state caught up.

Nebula's interface is designed to run `f.routines` independent reader goroutines pulling from the same UDP socket when the platform supports multiple readers (`SupportsMultipleReaders`), each calling `readOutsidePackets` → `ConnectionState.Decrypt`/`VerifyRelay` concurrently for whatever hostinfo the packet resolves to [5](#0-4) [6](#0-5) . `readOutsidePackets` resolves the `hostinfo` by remote index and immediately calls `Decrypt`/`VerifyRelay` on its shared `ConnectionState` with no per-hostinfo serialization lock around the whole check-decrypt-update sequence [7](#0-6) . An off-path attacker who can capture one legitimate ciphertext packet on the wire (no CA-signed certificate needed — this is exactly the "attacker with no CA-signed certificate" threat model) can duplicate that UDP datagram onto the wire multiple times in quick succession; if multiple copies land on different reader routines before the first `Update()` call commits, more than one copy will pass `Check()`, be independently AEAD-decrypted (which will succeed since the ciphertext/nonce is valid and hasn't been "used" from the window's perspective yet), and be delivered to the tun device or forwarded (in the relay case) — defeating the very anti-replay/duplicate-suppression guarantee the mechanism exists to provide. The project's own CHANGELOG documents that this exact class of bug (replay window races) has bitten this code before: "Lock replay window updates so concurrent readers can't corrupt it" and "Advance the replay window on relayed packets so a relay drops replayed frames instead of re-forwarding them" [8](#0-7) ; those fixes addressed *internal corruption* and *missing advancement*, but did not make the overall Check→Decrypt→Update sequence atomic, leaving this TOCTOU window.

### Impact Explanation
Successful exploitation causes duplicate delivery/forwarding of an already-authenticated packet, i.e. a concrete traffic-replay bypass of the anti-replay protection that `ReplayWindow`/`Bits` is meant to enforce. For `handleOutsideRelayPacket`, a duplicated relay frame that races through `VerifyRelay` on two routines could be forwarded twice toward the relay target, directly reproducing the "relay re-forwards replayed frames" impact that a prior CVE-like fix (#1751) specifically targeted for the sequential path — but the same effect can still be achieved via the unlocked concurrent window here. For direct tunnels, duplicate delivery of tun-bound application data can cause application-level duplication/side effects and undermines the confidentiality/integrity guarantee that each ciphertext+counter is processed exactly once.

### Likelihood Explanation
Requires `f.routines > 1` (multi-reader mode, common on Linux with `SO_REUSEPORT`-style multi-queue socket support) and an attacker able to inject/duplicate a captured ciphertext packet onto the wire close in time so it lands on two different reader goroutines before the first `Update()` commits. This is a narrow timing window but is a standard, well known TOCTOU race; a sustained flood of duplicate copies of a captured packet increases the odds of hitting the race, especially under load when `DecryptDanger` takes measurably longer, widening the window between `Check` and `Update`.

### Recommendation
Make the replay-window check and its confirmation atomic with respect to a given message counter: hold `decryptLock` (or a per-counter reservation) across the entire Check→Decrypt→Update sequence, or restructure `Bits` to offer a single "reserve-if-not-seen" operation that marks the counter as claimed before decryption begins and rolls back only on genuine decrypt failure, so a duplicate arriving concurrently is rejected at the `Check`/reserve step rather than being allowed to race to `Update`.

### Proof of Concept
1. Configure nebula with `routines: 2+` on a platform where `SupportsMultipleReaders()`/`SupportsMultiqueue()` returns true (e.g. Linux with `SO_REUSEPORT` listener), establishing a tunnel between two peers.
2. As an on-path/off-path attacker who observes one legitimate encrypted UDP application packet (`header.Message`/`MessageNone`) addressed to the victim, capture it and rapidly re-inject two (or more) copies of the exact same datagram to the victim's listening UDP port(s) in immediate succession.
3. If the copies are picked up by two different reader goroutines (`f.listenOut(i)`) before the first `ConnectionState.Update()` call completes, both goroutines call `cs.window.Check()` [9](#0-8)  and both observe "not yet seen," both successfully call `dKey.DecryptDanger` [10](#0-9) , and both proceed to deliver the plaintext via `handleOutsideMessagePacket`/tun write — observably duplicating the packet at the tun interface, confirming the anti-replay guarantee was bypassed.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}

func (f *Interface) listenOut(i int) {
	var li udp.Conn
	if i > 0 {
		li = f.writers[i]
	} else {
		li = f.outside
	}

	ctCache := firewall.NewConntrackCacheTicker(f.ctx, f.l, f.conntrackCacheTimeout)
	lhh := f.lightHouse.NewRequestHandler()
	plaintext := make([]byte, udp.MTU)
	h := &header.H{}
	fwPacket := &firewall.Packet{}
	nb := make([]byte, 12, 12)

	err := li.ListenOut(func(fromUdpAddr netip.AddrPort, payload []byte) {
		f.readOutsidePackets(ViaSender{UdpAddr: fromUdpAddr}, plaintext[:0], payload, h, fwPacket, lhh, nb, i, ctCache.Get())
	})

	// An error after teardown began is shutdown noise, the closed flag covers resources
	// Close releases itself and the cancelled ctx covers ones torn down by their owners
	// reacting to it, like the user device pipes
	if err != nil && !f.closed.Load() && f.ctx.Err() == nil {
		f.l.Error("Error while reading inbound packet, closing", "error", err)
		f.onFatal(err)
	}

	f.l.Debug("underlay reader is done", "reader", i)
}
