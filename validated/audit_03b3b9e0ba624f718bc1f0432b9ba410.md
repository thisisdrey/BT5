## Title
Silent Failure of `reduceAssetAmountV2` Ignored in Exchange/Market Actuators Can Corrupt Token Accounting Without Reverting - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`, `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`AccountCapsule.reduceAssetAmountV2` returns `false` instead of throwing when the account's asset balance is insufficient [1](#0-0) . Several actuators that handle exchange/market TRC-10 token movement — `ExchangeInjectActuator`, `ExchangeCreateActuator`, and `MarketSellAssetActuator` — call this method and completely ignore its boolean return value, unlike `TransferAssetActuator` and `ParticipateAssetIssueActuator`, which explicitly check it and throw `ContractExeException` on failure. This mirrors the reported Solidity pattern of a non-reverting token transfer/burn whose failure is silently swallowed, letting the surrounding state-mutating logic (exchange pool balances, order books) proceed as if the debit succeeded.

### Finding Description
`AccountCapsule.reduceAssetAmountV2` decrements a TRC-10 asset balance only if the current balance is sufficient; otherwise it returns `false` and leaves the account state untouched: [1](#0-0) 

`TransferAssetActuator.execute` correctly treats this return as authoritative and aborts the whole contract execution via a thrown exception if it fails: [2](#0-1) 

`ParticipateAssetIssueActuator.execute` does the same: [3](#0-2) 

However, `ExchangeInjectActuator.execute` calls `reduceAssetAmountV2` for both `tokenID` and `anotherTokenID` without checking the return value, while it has *already* mutated the `exchangeCapsule` pool balances (`exchangeCapsule.setBalance(...)`) before the reduction is attempted: [4](#0-3) 

`ExchangeCreateActuator.execute` exhibits the identical pattern — mutating exchange pool state and persisting the new `ExchangeCapsule` while the corresponding `reduceAssetAmountV2` calls for `firstTokenID`/`secondTokenID` are unchecked: [5](#0-4) 

`MarketSellAssetActuator.transferBalanceOrToken` (invoked from `execute` before order creation and matching) also ignores the boolean result: [6](#0-5) 

In every one of these call sites, if `reduceAssetAmountV2` returns `false` (insufficient asset balance), execution does not throw, does not roll back, and does not fail the transaction — it simply continues, meaning the exchange/market pool bookkeeping (which was already advanced) diverges from the account's real token holdings.

### Impact Explanation
If reachable with an insufficient asset balance at the exact point of the `reduceAssetAmountV2` call (e.g., due to a state transition between `validate()` and `execute()`, or a validation gap that does not perfectly mirror the execute-time computation), the actuator would record an exchange pool credit / order fulfillment for tokens the account never actually gave up. This creates an accounting mismatch between the on-chain `ExchangeCapsule`/`MarketOrderCapsule` bookkeeping and actual `AccountCapsule` asset balances — a form of unbacked balance in the exchange/market subsystem, since counterparties (or the pool) receive tokens whose corresponding debit silently failed.

### Likelihood Explanation
This is a real code-quality gap versus the sibling actuators (`TransferAssetActuator`, `ParticipateAssetIssueActuator`) that explicitly guard against exactly this failure mode, indicating the developers are aware of the return-value contract. However, I could not confirm within the available tool budget whether `ExchangeInjectActuator.doValidate()`, `ExchangeCreateActuator.doValidate()`, and `MarketSellAssetActuator.validate()` already perform an equivalent sufficiency check (e.g., via `assetBalanceEnoughV2`) before `execute()` runs, which would make the unchecked call effectively unreachable with a failing balance in the normal transaction-processing flow. I was unable to retrieve the `doValidate()` bodies of these actuators in the final iteration due to tool call errors, so this is reported with that caveat: the discrepancy in error-handling style versus `TransferAssetActuator`/`ParticipateAssetIssueActuator` is confirmed, but full exploitability (i.e., that `validate()` does not already close this gap) is **not confirmed**.

### Recommendation
Check the boolean return value of every `reduceAssetAmountV2`/`addAssetAmountV2` call in `ExchangeInjectActuator`, `ExchangeCreateActuator`, and `MarketSellAssetActuator`, and throw `ContractExeException` on `false`, consistent with the pattern already used in `TransferAssetActuator` and `ParticipateAssetIssueActuator`. Additionally, audit `doValidate()`/`validate()` in these actuators to confirm asset-sufficiency is checked prior to `execute()`, and add explicit pre-execution sufficiency checks if missing.

### Proof of Concept
Not independently reproduced — a Devin session with full codebase/test access is recommended to construct a validate()/execute() sequencing test (analogous to `AccountCapsuleTest.sameTokenNameCloseAssertAmountV2test` at [7](#0-6) , which demonstrates `reduceAssetAmountV2` returning `false` on insufficient balance) that drives `ExchangeInjectActuator`/`ExchangeCreateActuator`/`MarketSellAssetActuator` into the unchecked-failure branch and observes the resulting exchange-pool/account-balance divergence.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }
