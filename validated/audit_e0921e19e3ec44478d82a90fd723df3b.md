Audit Report

## Title
Referendum "support" quorum can be gamed via live, attacker-shrinkable issuance denominator (NIS deactivation) instead of a snapshot - (File: substrate/frame/conviction-voting/src/types.rs)

## Summary
`Tally::support()` computes support as `self.support / Total::get()` on every evaluation rather than against a value fixed when the referendum entered its deciding period. `Total::get()` is bound in runtime configs to `TotalIssuanceOf`/`ActiveIssuanceOf`, both of which are live, externally movable values — `ActiveIssuanceOf` specifically can be shrunk by any unprivileged account via `pallet-nis`'s permissionless `place_bid` extrinsic, which deactivates issuance. This allows the reported support ratio to increase without any additional aye votes, since the same numerator is divided by a smaller denominator.

## Finding Description
`Tally::support` is defined as: [1](#0-0) 

`Total` is bound in production runtime configs to `TotalIssuanceOf<Balances, ...>` (relay/node runtime) or `ActiveIssuanceOf<Balances, ...>` (Asset Hub Westend governance, staking-async RC governance) — both are live currency-issuance trackers, not referendum-scoped snapshots. `pallet_referenda::Pallet::is_passing` recomputes `tally.support(id)` fresh on every service invocation (scheduler alarm or permissionless `nudge_referendum`) and compares it against the track's `min_support` curve to decide whether to enter/continue Confirmation and ultimately schedule enactment. Because the denominator is live and externally reducible (via `pallet-nis`'s permissionless issuance-deactivating extrinsic, when NIS and conviction-voting/referenda share the same runtime and `ActiveIssuanceOf` binding), the referendum's computed support fraction can be manipulated upward purely by shrinking the denominator, independent of the actual numerator (aye-weighted votes). No snapshot of the denominator is taken when the deciding period begins, so this manipulation is possible at any point in the referendum's lifecycle, not just at proposal creation — the same structural flaw as the cited SALT quorum bug (recomputing quorum from a live, externally-controllable value instead of a value fixed at a discrete checkpoint).

## Impact Explanation
This is a runtime bug that compromises the intended behavior of the governance quorum/support mechanism: it allows a referendum to be moved into Confirmation and ultimately scheduled for enactment — potentially dispatching calls under elevated origins per track (Root, Treasurer, WhitelistedCaller, etc.) — based on an inflated support percentage rather than genuine voter turnout. This aligns with the "runtime bugs that compromise intended behavior" and "forged/mis-bound... state acceptance" impact classes for the Polkadot SDK program, since the quorum/support check accepts a corrupted intermediate value (the live `Total::get()` denominator) as if it were fixed and trustworthy.

## Likelihood Explanation
The attack requires only an ordinary, unprivileged token holder capable of casting conviction votes and (where NIS is present with `ActiveIssuanceOf`-bound `MaxTurnout`) submitting `place_bid`, plus triggering/waiting for the next referendum service call, which is itself permissionless (`nudge_referendum`). No validator, collator, relayer, or privileged governance action is required — this is consistent with the "unprivileged external attacker using public extrinsics" requirement. The magnitude of achievable manipulation is bounded by how much issuance an attacker can practically deactivate relative to total issuance, and the exact reversibility/cost profile of NIS bids was not fully verified in this pass, but the underlying invariant violation — a public support/quorum computation reading a live, externally movable denominator rather than one fixed at the start of the deciding period — is present in the code as described.

## Recommendation
Snapshot the `MaxTurnout` (issuance) value used as the support denominator once, when a referendum's `DecidingStatus` begins, and store it in `ReferendumStatus` for use throughout the deciding/confirming lifecycle, instead of calling `Total::get()` live in `Tally::support()` on every `is_passing` evaluation. This removes any single actor's issuance-affecting extrinsic (NIS bids, burns, mints, etc.) from being able to shift a referendum's quorum requirement mid-flight.

## Proof of Concept
1. Attacker casts an "aye" `pallet_conviction_voting::vote` on an ongoing referendum on a track whose live `tally.support()/Total::get()` ratio is just below the track's current `min_support` curve threshold.
2. On a runtime where `pallet_conviction_voting::Config::MaxTurnout = ActiveIssuanceOf<Balances, ...>` and `pallet-nis` is deployed, attacker calls `pallet_nis::Pallet::place_bid`, which deactivates a chunk of currency issuance, reducing `ActiveIssuance` and thus `Total::get()`.
3. On the next scheduler alarm or permissionless `nudge_referendum` call, `Referenda::is_passing` recomputes `tally.support(track_id) = Perbill::from_rational(self.support, Total::get())` with the now-smaller denominator, yielding a higher support percentage with no new aye votes.
4. If this crosses `track.min_support.threshold(elapsed_fraction)`, the referendum enters/continues Confirmation earlier than organic turnout warrants (`substrate/frame/referenda/src/lib.rs`, `is_passing`/service logic), potentially leading to premature `Approved` state and scheduled enactment.
