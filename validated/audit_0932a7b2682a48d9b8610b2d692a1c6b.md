### Title
Anti-replay window Check-then-Update race allows duplicate/replayed data and relay packets to bypass replay protection - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` in `connection_state.go` validate an incoming message counter against the sliding-window replay tracker (`Bits`) in two separate locked critical sections, with the expensive/attacker-controlled AEAD decrypt operation performed *outside* the lock, in between the check and the commit. This mirrors the structural root cause in the Beanstalk `FarmFacet` report: a security-relevant piece of shared state (`s.isFarm` / here, the replay window `Bits.current`/bitmap) is read, control is handed off to an operation that can be raced by another concurrently-processed attacker-controlled packet, and only afterward is the state updated — creating a window where the check performed by one packet is stale by the time the corresponding update runs.

### Finding Description
`Bits.Check` (read-only test) and `Bits.Update` (commit) are two independent operations, each individually protected by `cs.decryptLock`, but `Decrypt`/`VerifyRelay` release the lock between them to perform `DecryptDanger`: [1](#0-0) [2](#0-1) 

Nebula processes inbound UDP packets on the outside listener path in `outside.go`'s `readOutsidePackets`, which looks up the `HostInfo` purely by the wire-visible `RemoteIndex` in the cleartext header — no certificate or credential of the sender is required to reach this code path, only knowledge of a valid `RemoteIndex` (observable on the wire) and a captured/replayed ciphertext: [3](#0-2) 

nebula supports multiple concurrent UDP reader/listener goroutines (configurable via `listen.routines`/interface `routines`), each independently invoking `readOutsidePackets` → `ConnectionState.Decrypt`/`VerifyRelay` for the same `HostInfo`/`ConnectionState`: [4](#0-3) 

Because `Check` and `Update` are not part of one atomic critical section, two threads racing on the same captured/replayed packet (same `messageCounter`) can both pass `Check` (window not yet marked), both proceed to decrypt successfully (the ciphertext is validly authenticated — it's a genuine, previously-sent packet being replayed by a network observer), and only then serialize on `Update`, with the second call's `!result` check happening too late to prevent the first `Decrypt`/`VerifyRelay` from already having returned the plaintext / accepted the relay frame to the caller. The `Bits` sliding window itself is explicitly designed as the sole anti-replay mechanism (see `bits.go`, `Check`/`updateSlow`) and assumes callers serialize check-then-commit atomically; splitting the lock defeats that invariant under concurrency: [5](#0-4) [6](#0-5) 

The `e2e/tunnels_test.go` `TestRelayReplayProtection` test explicitly documents that a prior bug ("handleOutsideRelayPacket authenticated the frame but never advanced the replay window") allowed every replay to be re-forwarded, confirming that replay-window bypasses in this exact code path are a recognized, previously-exploited bug class in this codebase: [7](#0-6) 

### Impact Explanation
An attacker who can passively observe/capture a single legitimate encrypted data or relay packet (no CA-signed certificate or handshake participation required) can re-inject it concurrently against a target running with multiple listener routines. Because the check-then-decrypt-then-update sequence is not atomic, the replayed packet can be accepted a second time, defeating the anti-replay guarantee that the Noise/AEAD nonce-window is supposed to provide. Depending on payload semantics this can cause duplicate processing of tunnel traffic, duplicate forwarding of relay frames (state poisoning/traffic duplication), or be leveraged as a building block for further replay-based abuse. This is a genuine violation of the "nonce/replay handling" guarantee explicitly called out as in-scope.

### Likelihood Explanation
Exploitability requires (a) the ability to capture a legitimate ciphertext packet exchanged between two nebula nodes (feasible for any network-position attacker without a valid certificate, since UDP transport is unauthenticated) and (b) a target configured with more than one UDP listener/reader routine so packets can be processed concurrently. Multi-routine listening is a supported, documented configuration option, making this more than a theoretical race — the same class of bug (window not enforced atomically around forwarding) was previously found and fixed for the relay path per the regression test, indicating this is a recurring pattern rather than a one-off.

### Recommendation
Make the check-and-commit sequence atomic: hold `decryptLock` for the entire duration of `Check` → `DecryptDanger`/AEAD verify → `Update`, or perform an optimistic `Update` first (reserving the slot) and roll back only on decrypt failure, so no other goroutine can observe a "not yet seen" state for the same counter while a decrypt is in flight. Apply the same fix to both `Decrypt` and `VerifyRelay` in `connection_state.go`.

### Proof of Concept
Conceptual PoC (Go, not exploit code, describing the race):
1. Configure a nebula node with `listen.routines` > 1.
2. Capture one legitimate encrypted UDP packet destined for that node (e.g., via network tap) — this requires no certificate ownership by the attacker.
3. Re-inject the exact same captured packet twice, once to each of two listener sockets/goroutines, as close together in time as possible.
4. If both goroutines execute `cs.window.Check(...)` before either executes `cs.window.Update(...)` (achievable due to the unlocked `DecryptDanger` gap), both `Decrypt`/`VerifyRelay` calls return success for the same `messageCounter`, and the packet is processed/forwarded twice — demonstrating the anti-replay window failed to reject the duplicate.

This mirrors the e2e regression test pattern already present in the repo (`TestRelayReplayProtection`), which specifically validates that replayed relay frames are rejected exactly once by the window; the race window identified here shows the check/update split can still be defeated under true concurrency even though the sequential (single-goroutine) case is covered by that test.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

// updateSlow handles jumps, in-window backfill, dupes, and out-of-window.
func (b *Bits) updateSlow(l *slog.Logger, i uint64) bool {
	// If i is a jump, adjust the window, record lost, update current, and return true
	if i > b.current {
		end := i
		if end > b.current+b.length {
			end = b.current + b.length
		}
		count := end - b.current
		startPos := (b.current + 1) & b.lengthMask

		var lost int64
		if b.current >= b.length {
			// Steady state: every cleared slot is past warmup, so any unset
			// bit we evict is a lost packet from the previous cycle.
			wasSet := b.clearRange(startPos, count)
			lost = int64(count) - int64(wasSet)
		} else {
			// Warmup (the very first window). Some cleared slots represent
			// packets <= length where eviction is not "lost" in the usual
			// sense. This branch is taken at most once per connection so we
			// don't bother optimizing it.
			for n := b.current + 1; n <= end; n++ {
				if !b.get(n) && n > b.length {
					lost++
				}
			}
			b.clearRange(startPos, count)
		}

		// Anything past the new window can never be backfilled, so it's lost.
		if i > b.current+b.length {
			lost += int64(i - b.current - b.length)
		}
		b.lostCounter.Inc(lost)

		b.set(i)
		b.current = i
		return true
	}
