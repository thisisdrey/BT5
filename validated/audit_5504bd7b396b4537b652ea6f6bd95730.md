### Title
Out-of-bounds read parsing Central Directory Header fields in ijar's zip reader - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` decodes each Central Directory Header (CDH) of a JAR/ZIP file without validating that the attacker-controlled `file_name_length`, `extra_field_length`, and `file_comment_length` fields stay within the bounds of the memory-mapped input buffer, unlike its sibling `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before every variable-length field read.

### Finding Description
`ProcessLocalFileEntry` bounds-checks every read of attacker-controlled data with `EnsureRemaining(n, state)` [1](#0-0) , which compares the requested length against `input_file_->Length() - (p - zipdata_in_)` and aborts on overrun [2](#0-1) .

`ProcessCentralDirEntry`, however, performs none of these checks. It reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from the mapped buffer and then advances the cursor and `memcpy`s from it without ever confirming these values fit inside the mapped file: [3](#0-2) 

It then walks the "extra field" region using a 2-byte, attacker-controlled `data_size` to advance `extra_p`, with only a `while (extra_p != p)` loop guard — if `data_size` values don't sum exactly to `extra_field_length`, `extra_p` can overshoot `p` and the loop keeps dereferencing memory indefinitely past the intended region: [4](#0-3) 

The only prior validation is a global check in `FindZipCentralDirectory` that `cd.central_dir_offset + cd.central_dir_size <= in_length` [5](#0-4) . This bounds the *aggregate* central directory region against the file length, but does nothing to stop a single malformed entry's length fields from pointing the cursor past the end of the mmap'd file — `get_u4le`/`get_u2le`/`memcpy` in `common.h` perform raw, unchecked pointer arithmetic and dereferences [6](#0-5) .

`ProcessCentralDirEntry` is reached both from `InputZipFile::ProcessNext` (used whenever ijar/singlejar open and process a `.jar`/`.zip` file, e.g., to build interface jars for Java compilation) [7](#0-6)  and from `CalculateOutputLength`, which loops over every CDH in the file [8](#0-7) . Any jar consumed by Bazel's Java toolchain during a build (e.g., a `java_import`/`http_jar` target whose byte content is attacker-controlled) is decoded by this code path.

### Impact Explanation
A crafted JAR/ZIP with an inflated `file_name_length`, `extra_field_length`, or `file_comment_length` in a Central Directory Header entry, or a malformed extra-field `data_size` chain, causes the parser to read memory beyond the memory-mapped file. Depending on layout this can (a) crash the `ijar`/`singlejar` process (denial of build), or (b) copy adjacent-heap/mapped bytes into the `filename` buffer that is later used and potentially surfaced (information disclosure of process memory), analogous to the FFmpeg `cavs_idct8_add_c` out-of-bounds read while decoding attacker-supplied stream data.

### Likelihood Explanation
Reachability is high: any build target consuming an externally sourced jar (declared via `http_jar`/`http_archive`/`java_import`) will have this code path invoked on the artifact's exact bytes during interface-jar generation. Content-integrity checks like `sha256`/`integrity` on the *download* do not stop this, because the malicious bytes are the pinned artifact itself — the vulnerability is in how ijar decodes the (legitimately fetched, hash-verified) archive content, not in a fetch-time substitution.

### Recommendation
Add `EnsureRemaining()`-style bounds validation in `ProcessCentralDirEntry` before reading/advancing past `file_name_length`, `extra_field_length`, and `file_comment_length`, mirroring `ProcessLocalFileEntry`. Additionally bound the extra-field parsing loop so that `extra_p + data_size` can never exceed `p`/`extra_field_length`, converting the `while (extra_p != p)` loop to a monotonic bounded loop (`while (extra_p < p)`) with an explicit remaining-length check per iteration.

### Proof of Concept
A `BuildIntegrationTestCase`/shell test (in the spirit of `src/test/shell/bazel/external_integration_test.sh`) can:
1. Hand-craft a ZIP file with a valid End-Of-Central-Directory record and a single Central Directory Header entry whose `file_name_length` (or `extra_field_length`) field is set to a value that would place the read past the end of the physical file bytes (e.g., `0xFFFF` while the file itself is only a few hundred bytes long), while `central_dir_offset + central_dir_size` is kept consistent with `in_length` so `FindZipCentralDirectory`'s aggregate check passes.
2. Feed this file to `ijar`/`singlejar` (or via a Bazel `java_import`/`http_jar` target pointing at this artifact with a correct `sha256`).
3. Observe a crash (ASan: heap-buffer-overflow / SEGV) or leaked out-of-bounds bytes in the resulting error message or filename metadata, confirming the OOB read is reachable purely by build-time jar processing of attacker-controlled bytes.

Note: I was not able to fully trace every downstream consumer of `ProcessCentralDirEntry`'s output within this session (e.g., exact call sites in `singlejar`'s use of the shared `zip_headers.h`/`CDH` classes) — a Devin session with full repository access would be needed to construct and run the exact PoC binary/test and confirm crash behavior under ASan.

  // abort with an error message.  "state" is the name of the field
  // we're about to read, for diagnostics.
  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
  }

bool InputZipFile::ProcessNext() {
  // Process the next entry in the central directory. Also make sure that the
  // content pointer is in sync.
  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }
  u4 signature = get_u4le(p);
  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}

inline u1 get_u1(const u1 *&p) {
    return *p++;

inline u2 get_u2be(const u1 *&p) {
    u4 x = (p[0] << 8) | p[1];
    p += 2;
    return x;
}

inline u2 get_u2le(const u1 *&p) {
    u4 x = (p[1] << 8) | p[0];
    p += 2;
    return x;
}

inline u4 get_u4be(const u1 *&p) {
    u4 x = (p[0] << 24) | (p[1] << 16) | (p[2] << 8) | p[3];
    p += 4;
    return x;
}

inline u4 get_u4le(const u1 *&p) {

inline u8 get_u8le(const u1 *&p) {
  u4 lo = get_u4le(p);
  u4 hi = get_u4le(p);
