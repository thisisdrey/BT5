### Title
Protocol fee on NEP-245/IMT token swaps can be fully bypassed by splitting a `TokenDiff` swap into unit-amount (`delta == 1`) deltas - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::token_fee` returns `Pips::ZERO` for any NEP-245 or IMT token delta whose absolute amount is `<= 1`, unconditionally skipping the protocol fee, regardless of how much total volume the signer moves in the swap. Because a single signed `DefuseIntents` payload can contain an arbitrary number of `TokenDiff` intents, an attacker can decompose an arbitrarily large NEP-245/IMT swap into many `delta == 1` legs, each individually exempt from the fee, extracting the full swap volume while paying zero protocol fee.

### Finding Description
`TokenDiff::execute_intent` computes the fee to collect on every negative (token-in) delta via `Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)`: [1](#0-0) 

`token_fee` implements the exemption: [2](#0-1) 

For `TokenIdType::Nep171` the fee is always zero (intended for true 1-of-1 NFTs). For `TokenIdType::Nep245` and `TokenIdType::Imt`, the fee is zero whenever `amount <= 1` (since `delta != 0` is enforced upstream, this is exactly `amount == 1`), and is only the configured `protocol_fee` when `amount > 1`.

NEP-245 in this protocol is not restricted to true NFTs — it is used broadly to represent divisible, fungible-like balances (as seen in the escrow-swap README example `nep245:intents.near:nep141:usdt.tether-token.near`, wrapping a NEP-141 fungible token). The same `Intent::TokenDiff` type can appear multiple times inside one `DefuseIntents.intents` list, all executed under a single signature/nonce: [3](#0-2) [4](#0-3) 

Because each `TokenDiff` intent is evaluated independently for fee purposes, a signer can put `N` separate `TokenDiff` intents into one `DefuseIntents` payload, each transferring exactly `1` unit of the NEP-245/IMT token in and the corresponding counter-token out, and each will be exempted from the fee by the `amount <= 1` branch. Aggregated, this lets the signer move `N` units of value through the fee-bearing swap mechanism while the ledger records `fees_collected == 0` for the entire operation — breaking the invariant that `fees owed == fees collected` for the actual swapped volume.

### Impact Explanation
This is a concrete, unprivileged, attacker-profitable fee bypass: any signer can avoid the protocol fee entirely on trades denominated in NEP-245/IMT tokens (which in this protocol commonly wrap fungible assets), simply by expressing their swap as many unit-sized `TokenDiff` legs in a single signed payload instead of one large delta. This matches the "fees bypassed" Critical-impact category, since the fee collector never receives the fee it is entitled to for the actual economic size of the trade.

### Likelihood Explanation
Likelihood is high: no special privileges, no counterparty cooperation beyond a normal solver/counterparty fill, and no reliance on protocol misconfiguration are required — only that a NEP-245/IMT token with `protocol_fee > 0` is used, which is the default configurable state of the fee mechanism. The only cost to the attacker is constructing `N` intents in one payload/transaction, which is straightforward and cheap relative to the fee saved for high-value swaps.

### Recommendation
Compute and apply the fee based on the aggregate NEP-245/IMT delta actually swapped by the signer across the whole batch/settlement (or remove the `amount <= 1` fee exemption for NEP-245/IMT token types that represent divisible/fungible balances), rather than per-intent-leg amount. Alternatively, restrict the "no fee for `amount <= 1`" exemption to token ids that are provably non-fungible (e.g., only `Nep171`), and always apply the configured fee proportionally for `Nep245`/`Imt` deltas regardless of size.

### Proof of Concept
1. Protocol fee `protocol_fee = P > 0` is configured, and a NEP-245 token `T` (e.g. wrapping a fungible NEP-141 asset) with counter-token `C` has a two-sided market.
2. Attacker (or attacker + a cooperating/matched counterparty via `TokenDiff` closure) wants to swap a large amount `Q` of `T` for `C`.
3. Instead of submitting one `TokenDiff` intent with `diff = {T: -Q, C: +out}`, the attacker signs a single `DefuseIntents` payload containing `Q` separate `TokenDiff` intents, each with `diff = {T: -1, C: +delta_i}` (summing to the same total `out`).
4. In `TokenDiff::execute_intent`, for every leg `amount = 1`, so `TokenDiff::token_fee` returns `Pips::ZERO` at contracts/defuse/core/src/intents/token_diff.rs:211-213, and `fee_ceil(1) == 0`; `fees_collected` stays empty for the entire batch.
5. The full amount `Q` of `T` is swapped for `C` with zero fee ever added to `fees_collected`/`fee_collector`, whereas a single non-split `TokenDiff` of the same size would have paid `fee_ceil(Q) > 0`.
