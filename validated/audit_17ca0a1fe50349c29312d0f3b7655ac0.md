### Title
Dust deposits fill a victim's `MAX_TOKENS_PER_USER` slot list, blocking them from depositing new collateral or issuing new debt — (File: contracts/Pool.sol)

### Summary
CVE-2020-7040 is a predictable shared-resource squatting bug: storeBackup used a fixed `/tmp/storeBackup.lock` pathname, so any local user could pre-create it and block all other users until an admin manually removed it. The Metronome analog is the per-account `depositTokensOfAccount` / `debtTokensOfAccount` sets capped at `MAX_TOKENS_PER_USER = 30` in `Pool`. Any unprivileged attacker can squat a victim's slots by pushing dust positions into the victim's account, after which `onlyIfAdditionWillNotReachMaxTokens` reverts `UserReachedMaxTokens` on every operation that would add a new token type — blocking the victim until they manually clean out the dust (the on-chain equivalent of deleting the lockfile). [1](#0-0) [2](#0-1) 

### Finding Description
`Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` are guarded by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`. [3](#0-2) 

An attacker reaches this from public entry points without the victim's cooperation:

1. **Dust deposit on behalf of victim** — `DepositToken.deposit(amount_, beneficiary_)` accepts an arbitrary beneficiary (the test suite itself deposits to `bob` from `alice`). `_mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance goes 0 → >0, with no minimum amount and no consent check. [4](#0-3) [5](#0-4) 
2. **Dust transfer** — `DepositToken._transfer` also calls `pool.addToDepositTokensOfAccount(recipient_)` on a first-time balance. The attacker can transfer 1 wei of each `msdTOKEN` they hold (unlocked balance only restricts the *sender*). [6](#0-5) 

With ~30 listed deposit/debt tokens in a deployed pool (the cap is also the per-pool deposit token limit, `ReachedMaxDepositTokens`), the attacker fills all victim slots for the cost of dust collateral. [7](#0-6) 

Once full, the victim cannot:
- Deposit into any collateral token they don't already hold (`addToDepositTokensOfAccount` reverts inside `_mint`).
- Transfer in or receive any new `msdTOKEN`.
- Issue any synthetic they don't already owe (`DebtToken` similarly registers on 0 → >0 via `addToDebtTokensOfAccount`).
- Be onboarded into new markets added later — the slot is permanently occupied until manually freed.

There is no reentrancy guard, pause flag, health check, or `SynthContext` check that stops this; the only mitigation (`onlyIfAdditionWillNotReachMaxTokens`) is itself the vulnerability's blocking mechanism. [2](#0-1) 

### Impact Explanation
Like the lockfile, the attacker squatting a slot doesn't steal funds directly but performs targeted liveness denial: a victim (e.g., a SmartFarming user mid-leverage, a liquidation-avoiding borrower needing to add a new collateral type, or any user depositing on a schedule/front-run in the same block) is blocked from opening positions in new token types until they pay gas to withdraw/transfer out up to 30 dust positions one by one. A leveraged victim racing to add collateral before liquidation can be force-liquidated during the cleanup window — converting the DoS into loss of the victim's collateral. Funds are recoverable, so this is temporary freezing / blocked-protocol-operation rather than permanent loss.

### Likelihood Explanation
- Attacker needs only dust amounts of listed underlyings (or the deposit tokens themselves) and gas — fully unprivileged, no privileged role, oracle manipulation, or malicious infrastructure.
- Repeatable and cheap to re-apply: the attacker can front-run any cleanup the moment a slot frees.
- Requires the pool to list enough tokens for dust-filling to matter; on pools with many listed deposit/debt tokens the attack is most potent.
- The victim can always self-recover by withdrawing the dust (`withdraw` is open to balance holders and only gated by `whenNotShutdown`/`_revertIfLocked` on the caller's own position), which caps severity at temporary freeze / griefing rather than permanent loss. [8](#0-7) 

### Recommendation
- Only count a token toward `MAX_TOKENS_PER_USER` when the account opted in, or enforce a minimum balance (e.g., value ≥ `debtFloorInUsd`-scaled dust threshold) before registering in `depositTokensOfAccount`/`debtTokensOfAccount`.
- Alternatively let `addToDepositTokensOfAccount` skip (not revert) when called for a beneficiary whose slots are full, and revert only in the user-facing path — though this changes accounting semantics and needs care.
- Simplest robust fix: require `beneficiary_ == _msgSender()` (or an explicit opt-in allowance) in `DepositToken.deposit`, and make `transfer`/`transferFrom` for msdTokens pull-based or consent-based, so an attacker cannot force-register tokens on a victim.

### Proof of Concept
Reproducible in the existing Hardhat suite (pattern after `test/Pool.test.ts` "should revert when reach max tokens"):

```ts
// Fork/integration context: pool with N listed deposit tokens, victim with 0 balances.
// attacker approves underlying and calls, for each listed deposit token i:
//   await depositToken[i].connect(attacker).deposit(1n, victim.address);
// each call mints 1 wei msdTOKEN to victim -> pool.addToDepositTokensOfAccount(victim)
// After 30 registrations:
//   await depositTokenX.connect(victim).deposit(amount, victim.address)
//   -> _mint -> addToDepositTokensOfAccount -> UserReachedMaxTokens (revert)
//   await debtTokenY.connect(victim).issue(amount, victim.address)
//   -> addToDebtTokensOfAccount -> UserReachedMaxTokens (revert)
// Victim must loop withdraw(1 wei)/transfer dust for each token to regain access.
```

The revert path is already exercised by the existing unit test at `test/Pool.test.ts:1386` and `:1491` ("should revert when reach max tokens"); the attack adds only the missing observation that account registration is permissionless via `deposit(amount, beneficiary)` and `transfer`.

**Uncertainty:** I verified the deposit-side vector (`_mint`/`_transfer` → `addToDepositTokensOfAccount` with no beneficiary consent). I did not fully trace whether `DebtToken.issue` allows `onBehalfOf` for arbitrary accounts — most implementations restrict it to self or `onlyIfSmartFarmingManager`, so the deposit-token vector is the primary path and sufficient on its own. Whether a deployed pool actually lists ~30 tokens affects practical potency.
