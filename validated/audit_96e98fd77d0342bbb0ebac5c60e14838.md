### Title
Malformed-length `mt_batch_transfer_call` result in `mt_resolve_withdraw` triggers full refund even when tokens were actually delivered - ([File: contracts/defuse/src/contract/tokens/nep245/withdraw.rs])

### Summary
`mt_resolve_withdraw` treats any syntactically-valid but wrong-length JSON array returned by `mt_batch_transfer_call` as "zero tokens used," refunding the full withdrawn `amounts` back to `sender_id` regardless of what the external MT contract actually transferred to `receiver_id`. An attacker who deploys the `token` contract referenced in their own `MtWithdraw` can return a wrong-length array while still delivering the tokens to `receiver_id`, causing the Verifier to both refund the full amount internally and let the real transfer complete externally.

### Finding Description
The broken binding is: `debited(amounts) == delivered(to receiver_id) + refunded(to sender_id)`.

In `mt_resolve_withdraw` [1](#0-0) :

```rust
let mut used = if is_call {
    match promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len()) {
        Ok(Ok(used)) if used.len() == amounts.len() => used,
        Ok(_) => vec![U128(0); amounts.len()],
        Err(_) => amounts.clone(),
    }
} ...
```

When the promise succeeds and returns `Ok(Ok(used))` but `used.len() != amounts.len()`, the match falls through to `Ok(_) => vec![U128(0); amounts.len()]`, i.e. the resolver assumes **nothing** was transferred, even though the call genuinely succeeded and the callee could have already moved value to `receiver_id`. `used` is then fed into `self.deposit(sender_id, ...)` which computes `refund = amount - used = amount` for every token, crediting the sender's Verifier balance with the entire withdrawn amount [2](#0-1) .

Exploit path:
1. Attacker deploys their own MT contract `EvilMT` and uses it as `token` in a self-authorized `mt_withdraw`/`MtWithdraw` intent, setting `receiver_id` to an account they control, `msg` to `Some(...)` (forcing `is_call = true`), and `amounts = N`.
2. The Verifier debits `N` from the attacker's own Defuse balance via `self.withdraw` in `internal_mt_withdraw` [3](#0-2) , then calls `do_mt_withdraw` which invokes `EvilMT.mt_batch_transfer_call(receiver_id, token_ids, amounts, None, memo, msg)` [4](#0-3) .
3. `EvilMT`'s implementation actually credits `receiver_id` with the real transferred balance (a genuine on-chain transfer of the Verifier's held balance on `EvilMT`), but returns a JSON array whose length does not equal `amounts.len()` (e.g. an empty array or one with extra/missing elements) — still valid JSON, still `Ok`.
4. `mt_resolve_withdraw` sees `Ok(Ok(used))` with `used.len() != amounts.len()`, falls into the `Ok(_)` branch, and refunds the **full** `N` back into the attacker's Verifier balance.
5. Net result: the attacker now holds `N` again in the Verifier's internal ledger for `Nep245TokenId::new(EvilMT, token_id)`, AND the same `N` was already delivered to their `receiver_id` account on `EvilMT`. The Verifier's custodied real balance on `EvilMT` dropped by `N`, but its internal ledger still shows it owes `N` — the batch does not net to zero, and the Verifier now owes more than it custodies for that token.

The existing guard (`used.len() == amounts.len()`) is meant to detect malformed responses, but the fallback for the "successful but malformed" case incorrectly assumes zero delivery instead of full delivery, which is the opposite of what a length-mismatched-but-successful call typically means for an attacker-controlled callee that fully drains funds while returning bad data. This differs from the `Err(_) => amounts.clone()` branch, which correctly avoids refunding on read-failure (per the NEP-141/NEP-245 known gas-limitation issue) — the `Ok(_)` branch does not have equivalent protection for a call that both succeeds and truly transfers tokens.

### Impact Explanation
The attacker can duplicate the value of any token type keyed by `Nep245TokenId(token, token_id)` where `token` is a contract they control: value is simultaneously credited back into the Verifier's internal balance for `sender_id` and delivered externally to `receiver_id`. This is a violation of the settlement invariant (`debited == delivered + refunded`) and matches the Critical category "a batch whose balance changes do not net to zero so the Verifier owes more than it custodies." This is repeatable per withdraw call and per attacker-controlled token, letting the attacker mint unlimited internal Verifier balance for a token type they define, which could subsequently be used in intents/swaps against genuine counterparties' assets.

### Likelihood Explanation
The attacker needs only to: deploy their own MT contract, deposit into the Verifier under that token type (to establish a starting balance/backing), and issue a self-authorized `mt_withdraw`/`MtWithdraw` with `msg` set (forcing the `is_call` path). No privileged role, relayer key, or victim key is required — this is entirely self-serviceable and cheap (gas only), and repeatable at will.

### Recommendation
In `mt_resolve_withdraw`, do not assume zero-usage when the promise succeeds but the returned array length is wrong. Treat a length mismatch the same as a deserialization/read failure (i.e. assume full usage, `used = amounts.clone()`, refund nothing) rather than assuming zero usage, since a successful-but-malformed response from a callee should be treated conservatively against the Verifier, not against the sender who might have actually paid out. Apply the analogous fix to `mt_resolve_transfer` in `contracts/defuse/src/contract/tokens/nep245/resolver.rs` and `resolve_deposit_internal` in `contracts/defuse/src/contract/tokens/mod.rs`, which use similar length-check-then-fallback patterns.

### Proof of Concept
`cargo test` plan (near-workspaces sandbox):
1. Deploy a mock/malicious MT contract `EvilMT` whose `mt_batch_transfer_call` implementation: (a) actually credits `receiver_id`'s balance on `EvilMT` for the full transferred amount, and (b) returns a manually crafted JSON array of the wrong length (e.g., `[]` or `[U128(0), U128(0)]` when 1 element is expected).
2. Have attacker deposit `N` of `Nep245TokenId::new(EvilMT, token_id)` into the Verifier (establishing Verifier's real balance on `EvilMT` and attacker's internal Verifier balance = `N`).
3. Call `mt_withdraw` (or sign an `MtWithdraw` intent via `execute_intents`) with `token = EvilMT`, `receiver_id = attacker2` (attacker-controlled), `amounts = [N]`, `msg = Some("...")`.
4. Assert: Verifier's internal balance for attacker on `Nep245TokenId(EvilMT, token_id)` == `N` (full refund credited).
5. Assert: `EvilMT`'s real balance for `attacker2` == `N` (tokens actually delivered).
6. Assert `N (refund) + N (delivered) > N (originally debited)`, demonstrating the settlement invariant `debited == delivered + refunded` is violated and the Verifier now owes more than it custodies for this token.
