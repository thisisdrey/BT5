### Title
Griefing attack perpetually blocks OpMaintenance RPCs (e.g. `OptimizeRepository`, `RewriteHistory`) via cheap repeated write RPCs - (File: `internal/grpc/middleware/housekeeping/middleware.go`)

### Summary
An ordinary user with write access to a repository can keep the repository's housekeeping `active` flag continuously set by issuing a steady stream of cheap mutator RPCs (e.g. `WriteRef`). Because every mutator RPC that lands while the flag is `false` immediately re-triggers an asynchronous housekeeping run and flips the flag back to `true`, a legitimate, explicit maintenance RPC (`OpMaintenance`, such as `OptimizeRepositoryRequest` or `CleanupService_RewriteHistory`) issued against that repo can be perpetually rejected with `AlreadyExists`, denying maintenance for as long as the attacker keeps pushing. This mirrors the `MochiVault` griefing pattern: a cheap, repeatable, unprivileged action (`deposit`/`WriteRef`) resets a timer/flag (`lastDeposit`/`repoActivity.active`) that gates a legitimate action (`withdraw`/`OptimizeRepository`).

### Finding Description
`Middleware.repoActivity` tracks, per `repoKey{storage, relativePath}`, an `active` flag and a `writeCount` [1](#0-0) .

For every `OpMutator` RPC, `scheduleHousekeeping` is invoked after the handler runs [2](#0-1) . Inside `scheduleHousekeeping`, the write counter is incremented while holding `m.mu`; if the repo is already `active`, the call simply returns (writes are still counted), but as soon as `active` is `false` and the RPC-interval threshold has been exceeded, the middleware synchronously marks the repo `active` and launches an asynchronous goroutine running `OptimizeRepository` [3](#0-2) .

Separately, `OpMaintenance` RPCs check `isActive(key)` under the same mutex and immediately fail with `AlreadyExists` if a housekeeping run is in progress for that repo [4](#0-3) .

Because `writeCountAtLastRun[op]` is set to the current `writeCount` the moment a run is *scheduled* (not when it finishes) [5](#0-4) [6](#0-5) , an attacker who keeps `writeCount` climbing past the interval threshold on every mutator RPC guarantees that the very next mutator RPC delivered after the current run's `markHousekeepingInactive` [7](#0-6)  will immediately re-arm `active = true` again before a concurrent, legitimate `OpMaintenance` call can win the race for the (very short) inactive window. Since `RPCInterval` defaults to as low as 10-20 write RPCs [8](#0-7) , a small, cheap write (analogous to Mochi's "tiny deposit") is all that's needed to repeatedly re-trigger housekeeping and keep the flag pinned to `active`.

### Impact Explanation
While `active` is kept pinned, all explicit `OpMaintenance` RPCs for the targeted repository — including `OptimizeRepository` and `CleanupService_RewriteHistory` (a `forceHousekeepingRPC`) [9](#0-8)  — are rejected with `AlreadyExists`. An attacker with only ordinary push/write access to a single repository can therefore indefinitely deny operator- or automation-initiated maintenance for that repository, preventing pack/GC/commit-graph maintenance and letting loose objects, temp files, and repository size grow unbounded (a resource-exhaustion / DoS vector on the Gitaly node), without needing any elevated privilege.

### Likelihood Explanation
Reachable purely from an ordinary user's repeated mutator RPCs (e.g. any RPC classified `OpMutator` in the protoregistry, such as `WriteRef`); no privileged actor, malicious peer, MITM, or leaked token is required. Exploitability scales with how cheaply the attacker can issue mutator RPCs and how quickly `writeCount` exceeds the (default 10-20) `RPCInterval`, so it is straightforward on any environment with low per-request overhead, and can be amplified by concurrent request bursts to close the small inactive race window.

### Recommendation
Decouple the "housekeeping run in progress" gate used to reject `OpMaintenance` RPCs from the write-triggered scheduling counter, e.g., only block explicit maintenance RPCs while an operation they'd actually conflict with is running, and rate-limit or debounce how quickly write-triggered housekeeping can be re-armed after finishing (e.g. require a minimum idle interval since the last run, not just a raw write count, before scheduling the next one).

### Proof of Concept
1. As an ordinary user with push access, repeatedly call a cheap `OpMutator` RPC (e.g. `WriteRef`) against a target repository in a tight loop, at a rate exceeding the configured `RPCInterval` (default 10-20 writes) [8](#0-7) .
2. Each burst of writes causes `scheduleHousekeeping` to relaunch `OptimizeRepository` in the background as soon as the previous run finishes and `active` is reset [3](#0-2) .
3. Concurrently issue an `OptimizeRepositoryRequest` (or `RewriteHistory`) against the same repository; observe repeated `AlreadyExists: housekeeping already executing for repository` errors [10](#0-9)  for as long as the write flood continues, confirming maintenance can be perpetually griefed by an unprivileged writer.

func (m *Middleware) markHousekeepingInactive(key repoKey) {
	m.mu.Lock()
	defer m.mu.Unlock()

	a, ok := m.repoActivity[key]
	if !ok {
		a = newActivity()
		m.repoActivity[key] = a
	}

	a.active = false
}

// pendingOperations returns operations that have exceeded their RPC interval thresholds.
func (m *Middleware) pendingOperations(a *activity, force bool) []config.OperationType {
	var pending []config.OperationType

	for _, op := range allOperations {
		thresholds := m.getThresholds(op)
		lastRun := a.writeCountAtLastRun[op]
		writesSinceLastRun := a.writeCount - lastRun

		if force || writesSinceLastRun > thresholds.RPCInterval {
			pending = append(pending, op)
		}
	}

	return pending
}

func (m *Middleware) scheduleHousekeeping(ctx context.Context, repo *gitalypb.Repository, force bool) {
	m.mu.Lock()
	defer m.mu.Unlock()

	key := m.getRepoKey(repo)

	a, ok := m.repoActivity[key]
	if !ok {
		a = newActivity()
		m.repoActivity[key] = a
	}
	a.writeCount++

	if a.active {
		return
	}

	pendingOps := m.pendingOperations(a, force)
	if len(pendingOps) == 0 {
		return
	}

	m.logger.WithFields(log.Fields{
		"forced":     force,
		"operations": pendingOps,
	}).InfoContext(ctx, "beginning scheduled housekeeping")

	// Mark that these operations are running at the current write count
	for _, op := range pendingOps {
		a.writeCountAtLastRun[op] = a.writeCount
	}

	m.markHousekeepingActive(key)

	m.wg.Add(1)
	go func() {
		// We need to call OptimizeRepository with a child context that's disowned from the parent's
		// cancellation signals we're executing it asynchronously. Providing the existing `ctx` would
		// cause it to fail, since `ctx` would be cancelled when this request completes. We still want
		// to be able to abort the worker when the middleware shuts down though, so we propagate
		// cancellation from the middleware's shutdown context.
		housekeepingCtx, housekeepingCancel := context.WithCancel(context.WithoutCancel(ctx))
		stopShutdownPropagation := context.AfterFunc(m.shutdownCtx, housekeepingCancel)

		defer func() {
			stopShutdownPropagation()
			m.markHousekeepingInactive(key)
			m.logger.InfoContext(housekeepingCtx, "ended scheduled housekeeping")
			housekeepingCancel()
			m.wg.Done()
		}()

		localRepo := m.localRepoFactory.Build(repo)
		if err := m.manager.OptimizeRepository(housekeepingCtx, localRepo,
			manager.WithOptimizationStrategyConstructor(
				func(info stats.RepositoryInfo) housekeeping.OptimizationStrategy {
					return housekeeping.NewSelectiveOptimizationStrategy(info, pendingOps)
				},
			),
			manager.WithMVCCGarbageCollection(),
		); err != nil {
			m.logger.WithError(err).ErrorContext(housekeepingCtx, "failed scheduled housekeeping")
		}
	}()
}
