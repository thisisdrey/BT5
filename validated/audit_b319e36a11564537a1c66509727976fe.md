## Title
Unauthenticated `TransferToGasKeyAction` lets any account grief a victim's gas-key balance, blocking `DeleteKey`/`DeleteAccount` (donation-style DOS) - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
The original Noya finding is a "donation attack": an unprivileged caller directly transfers tokens to a contract's own balance, inflating a value (`baseToken.balanceOf(address(this))`) that a public function treats as internal accounting, corrupting a comparison used to gate withdrawals and DOSing legitimate users.

A structurally equivalent pattern exists in nearcore's gas-key subsystem. `action_transfer_to_gas_key` (`runtime/runtime/src/access_keys.rs:257-288`) lets *any* receipt's action fund an *existing* gas key on the receiver account, without verifying that the predecessor/signer is the account owner. That deposited balance later gates whether the key (or the whole account) can be deleted, via the hard-coded `GasKeyInfo::MAX_BALANCE_TO_BURN` check in `delete_gas_key` (`runtime/runtime/src/access_keys.rs:93-111`). An attacker can therefore "donate" tokens into a victim's gas key to push its balance above the burn threshold, causing `ActionErrorKind::GasKeyBalanceTooHigh` and blocking `DeleteKey`/`DeleteAccount` on that key.

### Finding Description
`TransferToGasKeyAction` is a normal action (usable both in a signed transaction and via the `promise_batch_action_transfer_to_gas_key` host function, `runtime/near-vm-runner/src/logic/logic.rs:3197-3245`) that funds a gas key's balance: [1](#0-0) 

Note that `action_transfer_to_gas_key` only checks that the target public key exists and is a gas key on `account_id` — it performs no check that `account_id` (the receipt's receiver) is the predecessor/signer that funded the deposit. The deposit is paid from whoever sends the receipt (exactly like a `TransferAction`, whose funds also come from the sender of the receipt). This means an attacker can address a receipt at the victim's account and fund the victim's gas key against their will.

That balance is later checked in `delete_gas_key`, which is invoked both from `DeleteKey` (`action_delete_key`, `runtime/runtime/src/access_keys.rs:52-91`) and, per the protocol-model spec, from full account deletion which "sums all gas-key balances against the same threshold" (`runtime/runtime/src/actions.rs:389`): [2](#0-1) 

If `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN`, the delete action fails with `GasKeyBalanceTooHigh` instead of proceeding, so the key cannot be deleted (and, per the spec citation, account deletion is blocked the same way) while the balance remains above the threshold:


This mirrors the Noya bug's mechanics precisely: an externally-controllable balance value (gas-key balance, analogous to `baseToken.balanceOf(address(this))`) is compared against a fixed threshold inside logic that gates an operation the victim wants to perform (deleting a key/account, analogous to `retrieveTokensForWithdraw`), and the attacker can inflate that balance cheaply via a normal, permissionless transfer-style action.

### Impact Explanation
An attacker can grief any account that has an active gas key by sending it a small extra deposit via `TransferToGasKeyAction`, pushing the gas key's balance above `MAX_BALANCE_TO_BURN`. This blocks the victim's `DeleteKey` action for that specific key and, according to the account-deletion invariant which sums all gas-key balances against the same cap, can also block deleting the whole account while any gas key retains an inflated balance. This is a denial-of-service on key/account lifecycle management triggered entirely by an unprivileged third party's transaction, at a cost bounded by the (small, ≤1 NEAR class) `MAX_BALANCE_TO_BURN` threshold.

Note for completeness: `WithdrawFromGasKeyAction` exists specifically to let an account draw funds back out of a gas key balance, which — if restricted to the account's own signer — would let the victim self-remediate (withdraw enough to drop below the threshold, then delete). I was not able to fully confirm within the available context whether `WithdrawFromGasKeyAction` requires signer-is-receiver, so I cannot rule out that this griefing is fully recoverable by the victim with one extra transaction rather than a truly permanent freeze.

### Likelihood Explanation
The attack requires only a single, cheap, unprivileged transaction (or a cross-contract call using the host function) targeting any account with a known gas-key public key (gas-key public keys, like regular access keys, are visible on-chain via `ViewAccessKey`/`ViewGasKeyNonces` queries). No special permissions, races, or validator behavior are needed, making this trivially and repeatedly triggerable.

### Recommendation
- Restrict `action_transfer_to_gas_key` to only allow depositing into a gas key on the same account (`sir`, i.e., predecessor_id == account_id), consistent with the restriction already documented for `WithdrawFromGasKeyAction`, unless the intent is to allow this deliberately as a "sponsor a gas key" pattern for others.
- If open funding by others is intended, reconsider gating `delete_gas_key`/account deletion on an absolute `MAX_BALANCE_TO_BURN` threshold that is influenced by third-party deposits — e.g., allow the burn amount to be capped/truncated rather than blocking deletion outright, or require the account owner to explicitly acknowledge/burn any surplus balance as part of the delete flow.
- Add integration tests exercising `TransferToGasKeyAction` from a predecessor different from the target account to confirm whether this is an intended capability, and if so, ensure `DeleteKey`/`DeleteAccount` cannot be permanently blocked by third-party funding.

### Proof of Concept
1. Victim account `alice.near` creates and funds a gas key normally (`AddKey` with `AccessKey::gas_key_full_access`, then `TransferToGasKeyAction` to fund it modestly), as in `test_gas_key_transaction` (`test-loop-tests/src/tests/gas_keys.rs:83-176`).
2. Attacker `mallory.near`, with no relationship to `alice.near`, submits a transaction/receipt to `alice.near` containing `Action::TransferToGasKey(TransferToGasKeyAction { public_key: <alice's gas key>, deposit: <MAX_BALANCE_TO_BURN + 1 yoctoNEAR-equivalent> })`. This succeeds because `action_transfer_to_gas_key` does not check the predecessor: [3](#0-2) 
3. Alice subsequently submits `Action::DeleteKey` (or an account-deletion transaction) for that gas key. `delete_gas_key` now observes `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN` and returns `ActionErrorKind::GasKeyBalanceTooHigh`, aborting the deletion: [4](#0-3)

```rust
pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
```
