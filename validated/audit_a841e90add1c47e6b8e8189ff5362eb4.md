### Title
Node advertises an unstored StackerDB chunk version as its own inventory before the chunk is actually committed - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches its outgoing `StackerDBChunkInv` reply to claim it now holds a pushed chunk's `slot_version` *before* that chunk has actually been written to the local `StackerDBs` store. This mirrors the sDaiStrategy bug class: an accounting/state value (`totalActiveDeposits` there, the advertised slot version here) is optimistically updated on receipt of unvalidated-for-storage input, without confirming the corresponding effect (deposit into the pool / chunk commit to disk) actually occurred, breaking the equality between "advertised state" and "stored state."

### Finding Description
On receipt of an unsolicited `StackerDBPushChunk`, `handle_unsolicited_StackerDBPushChunk` builds a reply inventory via `make_StackerDBChunksInv_or_Nack`, runs `validate_received_chunk` (signature, size, version, max-writes checks only — the docstring explicitly notes it "does not check write frequency"), and then patches the in-memory inventory copy: [1](#0-0) 

immediately followed by sending this patched `StackerDBChunkInv` back to the sender as if the chunk were already durably stored: [2](#0-1) 

The actual commit to the on-disk `StackerDBs` replica only happens later, out-of-band, via `Relayer::process_pushed_stacker_db_chunks` → `process_stacker_db_chunks` → `StackerDBTx::try_replace_chunk`, which can independently fail (e.g. `StaleChunk` on a race with a concurrently-processed chunk for the same slot, or `NoSuchSlot`/`BadSlotSigner` if the StackerDB config/slot ownership was reconfigured in the intervening window): [3](#0-2) [4](#0-3) 

Because the inventory reply is sent *before* this commit step runs (and completely independently of whether it later succeeds), the node can tell a peer "I have slot X at version V" while its local StackerDB store still holds an older (or no) version. Any peer relying on that `StackerDBChunkInv` — for rarest-first fetch scheduling or push-target selection in `StackerDBSync` — will treat the sender as an authoritative source for a chunk version it does not actually possess, exactly the "served non-canonical/mismatched state as canonical" pattern (advertised chunk inventory vs. actually committed data).

### Impact Explanation
This breaks the invariant that `StackerDBChunkInv` accurately reflects the node's committed StackerDB slot versions, which the report's rules classify as High impact ("steering a node off the tip via false inventory" / serving non-canonical state as canonical). Concretely, a peer that trusts the advertised version may stop trying to obtain/relay that chunk from elsewhere (believing it is now redundantly available here), while the true committed copy at the affected node remains stale — degrading replication reliability for StackerDB contracts, including signer-message StackerDBs used for block pre-commits (an existing changelog entry, `changelog.d/stackerdb-uploaded-chunk-event-loss.fixed`, documents a related "chunk stored but not announced" defect class in this exact subsystem, underscoring that these accounting/announcement races have caused real problems here before).

### Likelihood Explanation
Likelihood is high for a remote, unauthenticated (with respect to slot ownership — anyone can push an unsolicited chunk with a valid slot signature, since the write is application-controlled, not consensus/reconsensus-gated) attacker to trigger the race window: it merely requires sending two chunks (or a chunk racing another peer's concurrent chunk for the same slot) close in time so that `try_replace_chunk` for one of them returns `StaleChunk`/`NoSuchSlot`/`BadSlotSigner` after the optimistic inventory reply for it was already sent. No privileged capability, node secret, or high traffic volume is required — a small, deliberately-timed pair of unsolicited pushes suffices.

### Recommendation
Do not patch and send the advertised `StackerDBChunkInv` slot version until the chunk has actually been durably committed via `try_replace_chunk` (or an equivalent synchronous verification step). If synchronous storage isn't feasible in `handle_unsolicited_StackerDBPushChunk`, defer sending the inventory reply until after `process_stacker_db_chunks` confirms success for that specific slot/version, or only patch the in-memory `slot_versions` used for the reply from the authoritative store state after the write completes.

### Proof of Concept
1. Attacker connects to node N and identifies a StackerDB slot it controls the private key for.
2. Attacker crafts two valid, signed chunks for slot S with distinct but close-together higher-than-current versions (V1 then V2), and sends them from two connections/relayers in quick succession as `StackerDBPushChunk`.
3. `handle_unsolicited_StackerDBPushChunk` runs `validate_received_chunk` for the V1 push, patches and replies with inventory claiming slot S is at V1 (line 807/863 in `stackslib/src/net/stackerdb/mod.rs`).
4. Before V1's `try_replace_chunk` actually runs in `process_stacker_db_chunks`, the V2 push is processed and committed first (or vice versa) causing V1's later `try_replace_chunk` call to fail with `Error::StaleChunk` and get silently dropped: [5](#0-4) .
5. Node N has already told the peer (in step 3) that it holds slot S at V1, but its actual store never contains V1 — the peer's inventory-driven sync/fetch logic is left with false state about N's replica contents.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
