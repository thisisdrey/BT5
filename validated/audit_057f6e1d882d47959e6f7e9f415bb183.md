## Title
Stuck Treasury XCM payouts: `PayOverXcm`/`TransferOverXcmHelper::check_transfer` reports `Pending` forever when the remote query never resolves, permanently locking the spend as unclaimable and unrecoverable - ([File: polkadot/xcm/xcm-builder/src/pay.rs] and [File: polkadot/xcm/xcm-builder/src/transfer.rs])

## Summary
`pallet-treasury`'s cross-chain payout path (`PayOverXcm`/`PayAccountId32OnChainOverXcm`) tracks a spend's state entirely via a `pallet-xcm` query created in `do_new_query`, which is only ever resolved by `OnResponse::on_response` matching the exact `responder`/`maybe_match_querier` <cite repo="ThankGodontt/polkadot-sdk--024" path="polkadot/xcm/pallet-xcm/src/lib.rs" start="3435-3455" /><cite repo="ThankGodontt/polkadot-sdk--024" path="polkadot/xcm/pallet-xcm/src/lib.rs" start="4086-4104" />. `TransferOverXcmHelper::check_transfer` and `PayOverXcmWithHelper::check_payment` map `Querier::take_response`'s `Pending` variant to `TransferStatus::InProgress`/`PaymentStatus::InProgress` with no timeout enforcement anywhere in the code [1](#0-0) [2](#0-1) . In `pallet-treasury`, once a spend transitions to `PaymentState::Attempted { id }` via `payout`, `check_status` calls `T::Paymaster::check_payment(payment_id)`, and if it returns `Status::InProgress`, `check_status` just returns `Error::Inconclusive`, leaving the spend permanently in the `Attempted` state with no other exit [3](#0-2) .

## Finding Description
When a treasury spend is paid out through `PayOverXcm`, `TransferOverXcmHelper::send_remote_transfer_xcm` calls `Querier::new_query(asset_location, Timeout::get(), from_location.interior)`, which inserts `Queries::<T>::insert(id, QueryStatus::Pending { responder, maybe_match_querier, maybe_notify, timeout })` [4](#0-3) [5](#0-4) . The only code path that can transition this entry out of `Pending` is `OnResponse::on_response`, which requires the incoming response's origin to exactly equal the stored `responder` (and, if set, `maybe_match_querier`) [6](#0-5) . If the remote chain never sends a response, sends one from a mismatched origin, or a version conversion fails, the pallet emits `InvalidResponder`/`InvalidResponderVersion` and explicitly leaves the query `Pending` for a possible future response [7](#0-6) .

Crucially, `take_response` reads `QueryStatus::Pending { timeout, .. }` and returns `QueryResponseStatus::Pending { timeout }` regardless of whether the stored `timeout` block has already passed — the `timeout` value is only carried through informationally, never compared against the current block number or used to auto-resolve the query [8](#0-7) . I searched `pallet-xcm/src/lib.rs` for `on_initialize`/`on_idle`/`expire_query` hooks that could sweep expired queries and found none — the pallet has no `Hooks` implementation that inspects `timeout`.

`TransferOverXcmHelper::check_transfer` maps `Pending { .. }` unconditionally to `TransferStatus::InProgress`, and `PayOverXcmWithHelper::check_payment` passes this straight through as `PaymentStatus::InProgress` [1](#0-0) [2](#0-1) .

On the consumer side, `pallet-treasury::payout` sets `spend.status = PaymentState::Attempted { id }` [9](#0-8) . `check_status` handles the `Attempted` case by calling `T::Paymaster::check_payment(payment_id)`; on `Status::InProgress` it simply returns `Error::<T, I>::Inconclusive` without touching `spend.status` or `spend.expire_at` [10](#0-9) . Notably, the `now > spend.expire_at` expiry-sweep branch at the top of `check_status` explicitly excludes spends in the `Attempted` state (`!matches!(spend.status, State::Attempted { .. })`), so even after `spend.expire_at` passes, an `Attempted` spend is never auto-removed [11](#0-10) . Additionally, `void_spend` only permits voiding spends whose status is `PaymentState::Pending | PaymentState::Failed`, explicitly excluding `Attempted`, so there is no governance/root escape hatch either [12](#0-11) . The `payout_extends_expiry` and `payout_retry_works` tests confirm the only recovery path is via `check_status` observing `Status::Failure` or `Status::Success`/`Unknown` — a permanently `InProgress` payment id has no test coverage or handling path [13](#0-12) .

Taken together: an approved and attempted treasury spend whose XCM query never resolves (dropped `ReportError`, remote weight/barrier failure, version mismatch) results in a permanent `PaymentState::Attempted` record that can never be marked `Failed` (to permit retry) nor removed/refunded to the pot, and cannot be voided by any origin including root, because `void_spend` and the expiry-sweep in `check_status` both explicitly exclude the `Attempted` state.

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" class in the impact gate: any runtime that wires `pallet-treasury` (or another `Pay`-consumer) to `PayOverXcm`/`PayAccountId32OnChainOverXcm` risks having earmarked treasury funds permanently locked in an unresolvable `Attempted` spend record — neither delivered to the beneficiary nor returned to the pot, with no governance override available (`void_spend` cannot act on `Attempted` spends).

## Likelihood Explanation
No malicious actor is required — ordinary cross-chain unreliability suffices: a version mismatch causing `InvalidResponderVersion`, the destination chain failing to execute the `ReportError` appendix (e.g., due to insufficient remote weight or a `Barrier` rejection), or the response message simply being dropped by network/channel congestion. Since the `Timeout` parameter passed into `Querier::new_query` is never enforced by any hook or extrinsic in `pallet-xcm`, and `pallet-treasury::check_status`/`void_spend` explicitly exclude `Attempted` spends from any escape path, this can realistically occur over the operational life of any chain using `PayOverXcm`-based treasury spends.

## Recommendation
- Add a mechanism in `pallet-xcm` (e.g., a permissionless `expire_query` extrinsic or a scheduled sweep) that transitions a `QueryStatus::Pending` entry whose `timeout` has elapsed into a terminal state.
- Have `TransferOverXcmHelperT::check_transfer`/`PayOverXcmWithHelper::check_payment` surface this expired state as a definite `Failure` instead of indefinite `InProgress`.
- In `pallet-treasury`, allow `check_status`/`void_spend` (or a new dedicated call) to act on `Attempted` spends whose payment id has passed a reasonable deadline, so funds can be returned to the pot or the payout retried instead of being stuck forever.

## Proof of Concept
1. Configure a runtime with `pallet-treasury::Config::Paymaster = PayAccountId32OnChainOverXcm<...>` targeting a remote chain with `Timeout::get() = T`.
2. Approve a spend and call `payout`; this sets `spend.status = PaymentState::Attempted { id }` and creates a `pallet-xcm` query via `Querier::new_query(..., T, ...)`, inserting `QueryStatus::Pending { ..., timeout: T }`.
3. Simulate the remote chain dropping the `ReportError` appendix (e.g., insufficient remote weight) or responding from a mismatched origin so `on_response` emits `InvalidResponder`/`InvalidResponderVersion` and the query stays `Pending`.
4. Advance the chain far past block `T` and `spend.expire_at`. Call `Treasury::check_status(index)` — it calls `check_payment(id)`, which reflects `Querier::take_response` still returning `Pending`, so `check_status` returns `Error::Inconclusive` every time.
5. Call `Treasury::void_spend(index)` with root — it fails with `Error::AlreadyAttempted` because `spend.status` is `Attempted`, not `Pending`/`Failed`.
6. The spend record and its earmarked funds remain permanently stuck with no code path in this repository to force resolution.

		pub fn check_status(origin: OriginFor<T>, index: SpendIndex) -> DispatchResultWithPostInfo {
			use PaymentState as State;
			use PaymentStatus as Status;

			ensure_signed(origin)?;
			let mut spend = Spends::<T, I>::get(index).ok_or(Error::<T, I>::InvalidIndex)?;
			let now = T::BlockNumberProvider::current_block_number();

			if now > spend.expire_at && !matches!(spend.status, State::Attempted { .. }) {
				// spend has expired and no further status update is expected.
				Spends::<T, I>::remove(index);
				Self::deposit_event(Event::<T, I>::SpendProcessed { index });
				return Ok(Pays::No.into());
			}

			let payment_id = match spend.status {
				State::Attempted { id } => id,
				_ => return Err(Error::<T, I>::NotAttempted.into()),
			};

			match T::Paymaster::check_payment(payment_id) {
				Status::Failure => {
					spend.status = PaymentState::Failed;
					Spends::<T, I>::insert(index, spend);
					Self::deposit_event(Event::<T, I>::PaymentFailed { index, payment_id });
				},
				Status::Success | Status::Unknown => {
					Spends::<T, I>::remove(index);
					Self::deposit_event(Event::<T, I>::SpendProcessed { index });
					return Ok(Pays::No.into());
				},
				Status::InProgress => return Err(Error::<T, I>::Inconclusive.into()),
			}
			return Ok(Pays::Yes.into());
		}

#[test]
fn payout_extends_expiry() {
	ExtBuilder::default().build().execute_with(|| {
		assert_eq!(<Test as Config>::PayoutPeriod::get(), 5);

		System::set_block_number(1);
		assert_ok!(Treasury::spend(RuntimeOrigin::signed(10), Box::new(1), 2, Box::new(6), None));
		// Fail a payout at block 4
		System::set_block_number(4);
		assert_ok!(Treasury::payout(RuntimeOrigin::signed(1), 0));
		assert_eq!(paid(6, 1), 2);
		let payment_id = get_payment_id(0).expect("no payment attempt");
		// spend payment is failed
		set_status(payment_id, PaymentStatus::Failure);
		unpay(6, 1, 2);

		// check status to set the correct state
		assert_ok!(Treasury::check_status(RuntimeOrigin::signed(1), 0));
		System::assert_last_event(Event::<Test, _>::PaymentFailed { index: 0, payment_id }.into());

		// Retrying at after the initial expiry date but before the new one succeeds
		System::set_block_number(7);

		// the payout can be retried now
		assert_ok!(Treasury::payout(RuntimeOrigin::signed(1), 0));
		assert_eq!(paid(6, 1), 2);
	});
