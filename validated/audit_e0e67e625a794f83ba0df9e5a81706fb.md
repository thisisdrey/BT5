### Title
Unbounded array allocation from attacker-controlled length field in TVM precompiled-contract ABI decoding - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
Several private helper methods in `PrecompiledContracts.java` that decode ABI-encoded dynamic arrays for precompiled contracts (reachable from any TVM `CALL`/`STATICCALL` to a precompile address) allocate arrays sized directly by a length word taken from the caller-supplied `data`, with no upper bound check before allocation, mirroring the "buffer sized by an untrusted length field before validating it against actual available data" bug class described in the `bep/imagemeta` PNG/WebP advisory.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read a count/length value directly from the call data words via `words[offset].intValueSafe()` and immediately allocate an array of that size, before any check that the remaining `data`/`words` actually contain that many elements: [1](#0-0) [2](#0-1) [3](#0-2) 

`intValueSafe()` can return up to `Integer.MAX_VALUE` for an attacker-chosen 32-byte word, so `len` in `extractBytesArray`/`extractSigArray`/`extractBytes32Array` can be set to any value up to ~2^31-1 by simply crafting the calldata passed to a precompile that uses these helpers (e.g. multi-signature validation precompiles that decode arrays of signatures/bytes from ABI-encoded input). The subsequent `new byte[len][]` allocation attempts to allocate a reference array proportional to `len` (8 bytes per reference on typical JVMs, i.e. up to ~16GB for `len` near `Integer.MAX_VALUE`) before any bounds check against the actual size of `data`/`words`, and before any element is populated. This is the same root cause as the `bep/imagemeta` advisory: a length header/field controls buffer size independent of the amount of data actually present, permitting attacker-driven large allocations.

### Impact Explanation
A malicious contract deployer or caller can invoke a precompile that uses these helpers with a crafted `len` value to force a large memory allocation on the node executing the transaction, well before the loop (which would normally fail with `ArrayIndexOutOfBoundsException` from `words[offset + i + 1]`) has a chance to bound the length against actual data size. Because Java arrays are eagerly allocated, a sufficiently large `len` can trigger `OutOfMemoryError` on the executing full node/SR, degrading or crashing the JVM process handling transaction execution — a node availability impact, consistent with `VA:H` in the referenced CVSS vector.

### Likelihood Explanation
The path is reachable by any unprivileged account able to submit a `TriggerSmartContract` transaction (or make a `CALL`/`STATICCALL`) that targets one of the affected precompiled-contract addresses which route through `extractBytesArray`/`extractBytes32Array`/`extractSigArray`. No special privileges are required beyond the ability to submit an ordinary transaction with crafted calldata, and no upstream length validation (e.g., versus `data.length`) precedes the allocation.

### Recommendation
Before allocating `bytes32Array`/`bytesArray`, bound `len` against a sane maximum (e.g., derived from `data.length / WORD_SIZE` or `words.length - offset - 1`) and reject the call (return `Pair.of(true, DataWord.ZERO().getData())`) if the declared count exceeds what the input can actually supply, mirroring the approach already used for `offset > words.length - 1` in `extractBytesArray`/`extractSigArray`.

### Proof of Concept
Craft calldata for a precompiled contract that internally calls `extractBytesArray(words, offset, data)` (or the sibling helpers) such that `words[offset]` encodes a very large 32-byte integer (e.g., `0x7FFFFFFF`), while `data`/`words` otherwise remains minimal. The precompile's `execute(byte[] data)` will invoke `int len = words[offset].intValueSafe();` followed by `byte[][] bytesArray = new byte[len][];`, forcing the JVM to attempt a multi-gigabyte allocation before any bounds validation occurs.

Note: The exact precompiled contract(s) that call these three helper methods could not be conclusively enumerated within the indexed context (index size limits may have excluded some call sites); a full audit of all callers of `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` in `PrecompiledContracts.java` is recommended to confirm all reachable entry points.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
