### Title
Unbounded attacker-controlled length words in TVM precompile array extraction can trigger OOM/crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The external CVE describes an integer/size-underflow in a file parser where an attacker-controlled `plen` field is used to size a buffer without validating it against the actual available data, leading to memory corruption. The equivalent bug-class in java-tron is present in the helper functions that decode ABI-encoded array arguments passed to TVM precompiled contracts: `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` in `PrecompiledContracts.java` read a length/count word directly from attacker-supplied call data and use it to allocate arrays and index into the call-data buffer with no upper-bound validation.

### Finding Description
`extractBytesArray` and `extractSigArray` read `len` from `words[offset].intValueSafe()` — a 256-bit word taken directly from the precompile call data supplied by the calling smart contract — and immediately use it to allocate `new byte[len][]` and then loop `for (int i = 0; i < len; i++)` indexing further into `words[]` and `data[]`: [1](#0-0) [2](#0-1) 

Similarly, `extractBytes32Array` performs the same unchecked pattern: [3](#0-2) 

None of these three helpers validate `len` against the remaining length of `words`/`data` before allocating the array or before computing `bytesOffset`/`bytesLen` from further words and slicing `data` via `extractBytes` (`Arrays.copyOfRange(data, offset, offset + len)`): [4](#0-3) 

Only the `offset > words.length - 1` guard exists for the *first* index, not for `len` itself or the subsequent per-element `bytesOffset`/`bytesLen` values, which are themselves attacker-controlled words. A caller can supply a very large `len` (up to `intValueSafe`'s clamp, e.g. `Integer.MAX_VALUE`) causing an oversized `new byte[len][]` allocation (`OutOfMemoryError`), or supply `bytesOffset`/`bytesLen` values that push `extractBytes`'s `Arrays.copyOfRange` calls out of bounds, throwing unchecked `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`/`IllegalArgumentException` deep inside precompile execution. This mirrors the CVE root cause: a length field taken from untrusted input is used directly to size/copy a buffer without bounds validation against the real data size.

### Impact Explanation
If these array-allocation/slicing exceptions are not fully contained by the VM's exception handling around precompiled-contract execution, they can propagate as unhandled `Error`/`RuntimeException` during transaction execution, causing a node to crash or halt block processing — a denial-of-service condition reachable by any account that deploys or calls a contract invoking the affected precompiled contract (e.g., the multi-signature validation precompile that uses `extractSigArray`/`extractBytesArray`). This falls into the "node crash or halt" impact category required by the validation rules.

### Likelihood Explanation
Reaching this code only requires a signed transaction that calls the TVM precompiled contract(s) using these helpers with crafted call data — no special privileges are needed, matching the "unprivileged contract deployer/caller" threat model. However, I was not able to confirm from the indexed code whether the caller of `extractBytesArray`/`extractSigArray` wraps the whole precompile `execute()` invocation in a broad `catch (Throwable)` at a higher layer (e.g., in `VMActuator` or `Program`) that would downgrade a thrown exception into a normal contract-execution failure rather than a node crash; my searches for exception handling in `VMActuator.java` returned no matches, but this could be due to search/indexing limits. This uncertainty affects whether the ultimate impact is a genuine node crash versus merely a failed/reverted transaction.

### Recommendation
Add explicit bounds checks in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` verifying that `len` (and per-element `bytesOffset`/`bytesLen`) are within the bounds of `words.length` and `data.length` before allocating arrays or performing `Arrays.copyOfRange`, returning a "false"/failure result instead of throwing when the encoding is malformed — consistent with the existing `isValidAbiEncoding` helper already defined in the same file. Confirm (and if absent, add) that any exception from precompile execution is caught at the VM invocation boundary and converted into a normal (non-fatal) transaction failure.

### Proof of Concept
1. Deploy or call a contract that invokes the precompiled contract at the address backed by `ValidateMultiSign`/similar (which uses `extractSigArray`/`extractBytesArray`).
2. Craft the call data so the length word feeding `extractBytesArray`/`extractSigArray` (`words[offset]`) is an extremely large value (e.g., `0x7FFFFFFF`) or so that a per-element `bytesOffset`/`bytesLen` word points far outside `data`'s actual length.
3. Submit the transaction; `new byte[len][]` in `extractBytesArray`/`extractSigArray`/`extractBytes32Array` triggers `OutOfMemoryError`, or `extractBytes`'s `Arrays.copyOfRange` triggers an out-of-bounds exception, verifiable by exact file/method: [1](#0-0)  and [4](#0-3) .
