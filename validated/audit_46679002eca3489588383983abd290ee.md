### Title
Market order cancellation is gated behind the same `AllowMarketTransaction` switch as order creation, letting users' locked TRX/tokens become permanently unwithdrawable - (File: actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java)

### Summary
`MarketSellAssetActuator` lets any account create a sell order that removes the seller's TRX or TRC10 balance from their spendable account and holds it in the on-chain order book instead. The only way to get that value back if the order is not fully matched is `MarketCancelOrderActuator`, which returns the remaining `sellTokenQuantity` to the owner. Both actuators require the dynamic parameter `AllowMarketTransaction` to be enabled, but this parameter is controlled by chain-wide committee proposal, not by the individual user who placed the order.

### Finding Description
`MarketSellAssetActuator.execute()` deducts `sellTokenQuantity` from the caller's balance/asset map via `transferBalanceOrToken()` and persists a `MarketOrderCapsule` in `orderStore`/`marketAccountStore` for any unmatched remainder: [1](#0-0) 

Its `validate()` only allows this operation when the feature flag is on: [2](#0-1) 

The only mechanism for the order owner to reclaim the deposited (locked) funds is `MarketCancelOrderActuator`, whose `execute()` calls `MarketUtils.returnSellTokenRemain(...)` to give back the remaining sell quantity: [3](#0-2) 

However, `MarketCancelOrderActuator.validate()` imposes the exact same chain-wide precondition as order creation: [4](#0-3) 

`AllowMarketTransaction` (`supportAllowMarketTransaction()`) is a dynamic property set through committee governance (`ProposalUtil`/`DynamicPropertiesStore`), i.e., toggled by a chain-level proposal and not tied to any individual user's transaction. If this flag is switched off after a user has an active, partially or fully unmatched sell order sitting in the order book (their funds already deducted from their spendable balance), that user's `MarketCancelOrderContract` will now fail validation with `"Not support Market Transaction, need to be opened by the committee"`, exactly mirroring the deposit/withdraw asymmetry in the referenced report: funds can go in via one path but the only exit path shares a precondition that can independently become false, with no per-user way to force it. There is no separate exemption in `MarketCancelOrderActuator` to allow existing order holders to exit their position while new order creation remains disabled.

### Impact Explanation
Any account that had an active sell order at the moment the market-transaction feature is disabled has its TRX or TRC10 tokens permanently frozen inside `MarketOrderStore`/`MarketAccountStore` with no actuator path to release them until/unless the committee re-enables the flag. Because `MarketSellAssetActuator` and `MarketCancelOrderActuator` are reachable from ordinary signed transactions (`MarketSellAssetContract`, `MarketCancelOrderContract`), this is a real theft-adjacent freezing-of-funds condition affecting normal order placers, not privileged actors — matching the class of bug in the reference report (irreversible lock of user-deposited assets due to insufficiently scoped access/availability checks).

### Likelihood Explanation
Triggering the sequence only requires: (1) a user submitting a normal `MarketSellAssetContract` while the market is enabled, leaving an order partially/fully unfilled in the book, and (2) the market-transaction dynamic parameter later being turned off through ordinary, non-malicious committee governance (e.g., to pause the market for maintenance, or due to any future proposal disabling it) — this is a standard governance action already wired through `ProposalUtil`, not an attacker-controlled or malicious act. Because both order creation and order cancellation are gated by the identical flag, this asymmetric lock is a deterministic and easily reachable consequence of routine parameter changes, not a rare edge case.

### Recommendation
Decouple `MarketCancelOrderActuator.validate()` from the `AllowMarketTransaction` gate (or add an explicit exemption) so that users can always cancel/exit pre-existing orders and recover their locked balance/tokens regardless of whether new order creation is currently permitted. At minimum, cancellation should remain available whenever a valid, active order exists for the caller, independent of the global market-enable switch.

### Proof of Concept
1. Committee enables `AllowMarketTransaction` (normal state).
2. User A submits `MarketSellAssetContract` (sellTokenId = "_", sellTokenQuantity = X) via `MarketSellAssetActuator`; `transferBalanceOrToken()` deducts X TRX from A's balance and creates an active `MarketOrderCapsule` (see [1](#0-0) ). Suppose it's not immediately matched, so the order remains active in the order book.
3. Committee (through ordinary governance, not malice) disables `AllowMarketTransaction`.
4. User A submits `MarketCancelOrderContract` for that order; `MarketCancelOrderActuator.validate()` immediately throws `"Not support Market Transaction, need to be opened by the committee"` before reaching the ownership/order checks (see [4](#0-3) ), so User A cannot retrieve the X TRX already deducted in step 2.
5. The X TRX remains locked in the order book indefinitely, with no other actuator path to reclaim it while the flag stays disabled.
