### Title
Path Traversal via Unvalidated Tar Extraction in `CreateRepositoryFromSnapshot` - (File: internal/gitaly/service/repository/create_repository_from_snapshot.go)

### Summary
`CreateRepositoryFromSnapshot` extracts an attacker/caller-supplied tar archive (fetched over HTTP from a caller-controlled URL) directly into a freshly created repository directory using the system `tar` binary with no path/entry validation. Unlike the RPC's own hardened counterpart, `extractTarToDirectory` used by `ReplicateRepository`'s snapshot flow, the `untar` helper here performs no checks for path traversal (`../` sequences), absolute paths, or malicious symlink/hardlink targets. This mirrors the "manipulatable external input drives an unguarded write/accounting operation" root cause from the TermMax report: here the untrusted tar stream (an externally-controlled value) is trusted to determine where files are written on disk, rather than an internally-validated extraction routine.

### Finding Description
`CreateRepositoryFromSnapshot` is a `RepositoryService` RPC that takes an `HttpUrl` (and optional `HttpAuth`/`ResolvedAddress`) field supplied entirely by the caller [1](#0-0) . The handler creates a new bare repository and then calls `s.untar` to fetch the archive and extract it directly on top of the repository path [2](#0-1) .

The extraction itself execs the system `tar` binary with `-C path -xvf -`, streaming the HTTP response body straight into it, with zero validation of the archive's entry names or link targets [3](#0-2) . The code even self-documents this as unhardened: *"the received archive is trusted a lot... it should undergo a lot of hardening"* [4](#0-3) .

Contrast this with the already-hardened extraction path used for `ReplicateRepository`'s internal snapshot transfer (`extractSnapshot`/`extractTarToDirectory`), which explicitly:
- Joins entry names with the target dir and requires the result stay prefixed by `targetDir` [5](#0-4) .
- Rejects absolute symlinks and validates that relative symlink/hardlink targets resolve within the extraction boundary [6](#0-5) .

`CreateRepositoryFromSnapshot`'s `untar` has none of these protections. Because raw GNU `tar` honors absolute path entries and permits `../`-relative entries and arbitrary symlink/hardlink targets, a caller who controls (or can redirect/spoof) the HTTP endpoint referenced by `HttpUrl` can craft a tar archive that writes files anywhere the Gitaly process has permissions to write — escaping the newly created repository's storage path entirely.

### Impact Explanation
A malicious or compromised `HttpUrl` response can place arbitrary files at attacker-chosen absolute paths or paths outside the intended repository directory (e.g., via `../../../` entries or symlink/hardlink tricks), which can be used to overwrite Gitaly configuration, cross into other repositories' storage areas, or plant executable content (e.g., custom hooks or scripts) outside the sandboxed repository tree. This is a concrete storage/extraction escape consistent with a High-impact classification, comparable in class to the reward-report's "attacker controls a value that is trusted without internal validation, leading to unauthorized asset placement/theft."

### Likelihood Explanation
The RPC directly exposes `HttpUrl`, `HttpAuth`, and `ResolvedAddress` as caller-supplied fields with no restriction on the target other than DNS-rebinding protection via `ResolvedAddress` [7](#0-6) . Any caller with access to invoke this RPC (e.g., during repository import/migration flows) fully controls the archive content fetched and extracted, and the code comment confirms this was a known, unaddressed gap ("should undergo a lot of hardening"). No authentication of archive content or path sanitization occurs before extraction, making exploitation straightforward given RPC access.

### Recommendation
Replace the raw `tar -C path -xvf -` subprocess invocation in `untar` with Go's `archive/tar` package and apply the same validation already implemented in `extractTarToDirectory` (path-prefix checks against the target directory, rejection of absolute symlinks, and resolution/validation of relative symlink and hardlink targets before writing). Alternatively, route `CreateRepositoryFromSnapshot` through the existing hardened `extractTarToDirectory` helper instead of maintaining a second, unguarded extraction implementation.

### Proof of Concept
1. Stand up an HTTP server that serves a tar archive containing an entry with a traversal path, e.g., `../../../../tmp/evil` or an absolute path `/tmp/evil`, or a symlink entry pointing outside the target directory followed by a regular file entry using that symlink name.
2. Invoke `CreateRepositoryFromSnapshot` with `HttpUrl` pointing at that server.
3. Observe that `tar -C <repoPath> -xvf -` writes the `evil` file outside `<repoPath>`, demonstrating the extraction escape — analogous to the `TestExtractTarToDirectory_SymlinkValidation` test cases that verify the *hardened* extractor rejects exactly this class of input [8](#0-7) , which the `untar` path in `create_repository_from_snapshot.go` does not perform at all.
