### Title
Unbounded pre-check `Vec<u8>` allocation for `server_version`/`miner_diagnostic_data` inside `BlockProposalData::consensus_deserialize` allows bounded memory-allocation DoS - (File: libsigner/src/events.rs)

### Summary
`BlockProposalData::consensus_deserialize` first bounds the outer envelope to `BLOCK_RESPONSE_DATA_MAX_SIZE` (2MB) via `read_next_at_most`, then re-parses that buffer with an `inner_reader` and calls generic `read_next::<Vec<u8>, _>` for `server_version` and `miner_diagnostic_data` with no independent per-field cap. The generic `Vec<u8>` codec reads a `u32` length prefix and allocates a buffer of that declared size *before* attempting `read_exact`/verifying the reader actually has that many bytes remaining, so a crafted length prefix inside the 2MB inner buffer can trigger an allocation request far larger than the bytes actually available, failing only after the allocation attempt.

### Finding Description
The outer `read_next_at_most(fd, BLOCK_RESPONSE_DATA_MAX_SIZE)` call caps the number of bytes read off the wire for `inner_bytes` to 2MB, but it does not, and cannot, cap the *value* of a length prefix embedded inside those 2MB of already-read bytes. Once `inner_bytes` is materialized, `consensus_deserialize` wraps it in `inner_reader` and calls `read_next` for `server_version: Vec<u8>` and later `miner_diagnostic_data`. The `Vec<u8>` `StacksMessageCodec` implementation deserializes a `u32` length field and then allocates a buffer of that declared length (`vec![0u8; len]` or equivalent) prior to calling `read_exact`, which is the point where a mismatch between declared length and actual remaining bytes in `inner_reader` would be detected. This means the equality "declared length for the sub-field == bytes actually remaining in `inner_reader`" is checked only *after* the allocation has already been requested, not before it.

An attacker only needs to send a single crafted `BlockProposal`/`BlockResponse` StackerDB chunk (reachable through the unauthenticated `/stackerdb_chunks` miner-lane ingestion path) containing `inner_bytes` a few bytes long, where the first four bytes (the `server_version` length prefix) encode a value close to `u32::MAX` (bounded practically by u32, i.e. up to ~4GB). The outer size check passes because `inner_bytes` itself is small and within the 2MB cap; the inner length prefix is unconstrained by that outer cap.

### Impact Explanation
Each malformed message can force the receiving node to attempt a multi-gigabyte heap allocation (up to ~4GB, bounded by `u32::MAX`) for a single unauthenticated chunk write, which is a bounded compute/memory-allocation DoS on message ingestion — matching the "bounded compute DoS on a read endpoint" High-impact category. It is repeatable per message and does not require any privileged role, secret, or valid signer/StackerDB slot ownership beyond what's needed to post to the relevant StackerDB slot/chunk endpoint.

### Likelihood Explanation
The attacker needs only network reachability to the node's StackerDB chunk ingestion path and the ability to submit a chunk that decodes as a `BlockProposal`/`BlockResponse` containing a `BlockProposalData` — no signer key, RPC secret, or admin role is required to trigger parsing of the bytes up to the point of the vulnerable allocation. The cost is a single small message (a few bytes) versus a large allocation attempt on the target, making this cheap and repeatable.

### Recommendation
Enforce a per-field cap when decoding `server_version` and `miner_diagnostic_data` inside `inner_reader` — use `read_next_at_most` with a small, sane maximum (e.g., a few hundred bytes for `server_version`) instead of the unbounded generic `read_next`, and validate the declared length against `inner_reader`'s remaining length before allocating any buffer.

### Proof of Concept
```rust
// libsigner/src/events.rs (test module)
#[test]
fn test_block_proposal_data_oversized_inner_length_prefix() {
    // Craft inner_bytes: 4-byte length prefix for server_version claiming
    // a huge length, but with only a handful of bytes actually following.
    let mut inner_bytes = Vec::new();
    inner_bytes.extend_from_slice(&(u32::MAX - 1).to_be_bytes()); // bogus server_version length
    inner_bytes.extend_from_slice(&[0u8; 4]); // a few trailing bytes, far short of declared length

    // Wrap as the outer envelope BlockProposalData::consensus_deserialize expects:
    // [len-prefix for inner_bytes][inner_bytes...]
    let mut wire = Vec::new();
    wire.extend_from_slice(&(inner_bytes.len() as u32).to_be_bytes());
    wire.extend_from_slice(&inner_bytes);

    let mut fd = &wire[..];
    // Expect: either an allocation of ~4GB is attempted before the
    // read_exact/EOF error surfaces (observable via allocator instrumentation
    // or process RSS spike), or (if guarded) an immediate length-mismatch
    // error with no attempted allocation.
    let result = BlockProposalData::consensus_deserialize(&mut fd);
    assert!(result.is_err(), "expected decode failure on truncated inner_bytes");
    // Instrument with a custom global allocator or `cap_alloc` to assert
    // that no single allocation request >  a few KB occurred prior to error.
}
```
