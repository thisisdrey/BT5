### Title
Unvalidated attacker-controlled array length in `extractBytesArray()` can throw `NegativeArraySizeException`/`OutOfMemoryError` from precompiled-contract input parsing - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The reported iccDEV bug class is a heap-buffer-overflow in `IccTagXml()` caused by trusting an attacker/file-controlled length/size value when allocating and copying into a buffer. The closest reachable analog in java-tron is in `PrecompiledContracts.extractBytesArray()` / `extractBytes32Array()`, which allocate `byte[][]` arrays sized directly from an attacker-controlled 256-bit word (`words[offset].intValueSafe()`) taken from calldata passed to a precompiled contract, without validating that the resulting length is sane relative to the remaining input size.

### Finding Description
`extractBytesArray(DataWord[] words, int offset, byte[] data)` reads `len = words[offset].intValueSafe()` directly from the ABI-decoded precompile input and then does `new byte[len][]`, iterating to compute `bytesOffset`/`bytesLen` and calling `extractBytes(data, ..., bytesLen)` for each entry: [1](#0-0) 

`extractBytes32Array` similarly trusts `len` without any upper bound check before allocating an array whose length is directly attacker-supplied: [2](#0-1) 

Because `intValueSafe()` can return any 32-bit value the caller encodes in the calldata word, a contract invoking the corresponding precompile (e.g., a batch-signature-validation-style precompile that decodes dynamic byte arrays) can supply a very large `len`, causing:
- A `NegativeArraySizeException` if the decoded value is negative, or
- An extremely large allocation attempt (`new byte[len][]`) leading to `OutOfMemoryError`, or
- Subsequent out-of-bounds reads inside `extractBytes` once the loop dereferences `words[offset + i + 1]` beyond the actual `words` array length.

This mirrors the iccDEV root cause pattern: an untrusted length field is used to size/index a buffer without validating it against the actual available data size before the copy/allocation happens.

### Impact Explanation
An uncaught `OutOfMemoryError`/`NegativeArraySizeException` thrown while executing a smart-contract-triggered precompiled contract call, if not fully caught by the surrounding TVM exception handling, can crash or destabilize the node processing the transaction (denial of service for the block-processing/JVM thread), which is more severe than a simple revert because `OutOfMemoryError` is an `Error`, not an `Exception`, and is not guaranteed to be caught by typical `catch (Exception e)` blocks in the TVM call path.

### Likelihood Explanation
Reachable by any unprivileged account that can deploy or call a contract invoking the affected precompiled contract address with crafted calldata; no special privileges are required, matching the "unprivileged transaction broadcaster / contract deployer" reachability requirement.

### Recommendation
Validate `len` in `extractBytesArray`/`extractBytes32Array` against a sane upper bound derived from `data.length` and the remaining `words` array length before allocating, and treat any inconsistency as an invalid precompile call (return failure) rather than let an allocation/array exception propagate. Ensure `Program`'s precompiled-contract invocation path uses a broad `catch (Throwable)` (not just `Exception`) to prevent `Error` types from escaping the TVM execution sandbox.

### Proof of Concept
I could not confirm from the indexed context which specific precompiled contract(s) call `extractBytesArray`/`extractBytes32Array`, nor whether `Program.java`'s precompiled-contract execution path wraps calls in a `catch (Throwable)` versus a narrower `catch (Exception)` — the relevant call site match in `Program.java` did not return enough surrounding context to verify the exception-handling scope. This is a limitation of the current index; confirming full reachability and exception-handling coverage would require inspecting the complete `Program.java` call site and the callers of these two helper methods in a live checkout (e.g., via a Devin session) before treating this as a confirmed, PoC-verified vulnerability rather than a plausible analog.

    if (offset > words.length - 1) {

    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
