### Title
Unauthenticated HTTP API leaks internal exception class names and messages (including DB/RocksDB internals) via `Util.printErrorMsg` / `Util.processError` - (File: framework/src/main/java/org/tron/core/services/http/Util.java)

### Summary
Across dozens of full-node HTTP servlets (`GetAccountServlet`, `GetAccountByIdServlet`, `GetTransactionByIdServlet`, `GetTransactionInfoByIdServlet`, `GetAccountResourceServlet`, `GetAccountNetServlet`, `GetAssetIssueByIdServlet`, `GetBlockByIdServlet`, `GetContractServlet`, and many more), any exception raised while parsing a malformed request parameter or while executing the underlying store/query is caught and serialized verbatim into the client-visible JSON response via `Util.processError` → `Util.printErrorMsg`, which builds the response body as `e.getClass() + " : " + e.getMessage()`.

### Finding Description
`Util.printErrorMsg` at [1](#0-0)  constructs the API error payload directly from the raw Java exception's class name and message, with no allow-list or sanitization. `Util.processError` at [2](#0-1)  is the generic catch-all handler wired into essentially every read-only wallet HTTP endpoint, e.g. `GetAccountServlet.doGet/doPost` [3](#0-2) , `GetTransactionByIdServlet.doGet/doPost` [4](#0-3) , `GetAccountByIdServlet` [5](#0-4) , `GetAccountResourceServlet` [6](#0-5) , and roughly 40 other servlets per the codebase grep.

Any exception in the call chain surfaces unfiltered: malformed hex/base58 addresses raise `DecoderException`/`NumberFormatException`; and if the store layer itself fails (e.g., `RocksDbDataSourceImpl.getData`/`putData` wraps a `RocksDBException` into `new RuntimeException(dataBaseName, e)` [7](#0-6) ), that `RuntimeException`'s message (the internal database/column-family name) and class name are echoed straight back to any unauthenticated caller. This is structurally the same bug class as the parse-server advisory: a client-controlled malformed query parameter triggers a lower-layer/database exception whose internal details (class name, message, DB name) are relayed unsanitized in the API response instead of being reduced to a generic error and only logged server-side.

Note also `Util.getMessage()`-based JSON-RPC error paths largely already sanitize (e.g. `TronJsonRpcImpl.call`/`estimateGas` replace quotes and wrap in `JsonRpcInternalException`, see [8](#0-7) ), and `JsonRpcServlet` returns a generic "Internal error" on `RuntimeException` [9](#0-8) ; but the classic HTTP wallet API (`Util.processError`) has no equivalent generic-message fallback — it always emits the exception's class and message.

### Impact Explanation
This is an information-disclosure issue (CWE-209), matching Medium severity of the referenced advisory: it can reveal internal implementation details (Java exception class names, RocksDB store/column-family names, stack-trace-derived messages) to any anonymous API caller. While this by itself is not a fund-theft or RCE primitive, it aids reconnaissance (fingerprinting internal store layout, library versions, error conditions) for further attacks and violates the expectation that internal server errors are not exposed to unauthenticated clients, consistent with the advisory's "leaks database internals" classification.

### Likelihood Explanation
High likelihood of triggering: the affected servlets are reachable by any unauthenticated HTTP client with no permission checks (`wallet/getaccount`, `wallet/gettransactionbyid`, `wallet/getaccountbyid`, etc.), and simple malformed inputs (invalid hex length, invalid base58 checksum, oversized address, null pointers from malformed JSON parameter merging) reliably trigger the catch-all `Util.processError` path.

### Recommendation
Change `Util.printErrorMsg`/`Util.processError` to return a generic, non-parameterized message (e.g., `"An internal error occurred"`) to the client for unexpected/internal exceptions, while logging the full exception (class, message, stack trace) server-side only. Preserve specific, safe validation messages (e.g., explicit "invalid address" style checks already added in some servlets) but stop echoing `e.getClass()` and raw `e.getMessage()` for exceptions originating from lower layers such as store/database wrappers (`RuntimeException(dataBaseName, e)` from `RocksDbDataSourceImpl`).

### Proof of Concept
1. Send `GET /wallet/getaccount?address=zz` (or any malformed hex/base58 string) to a java-tron full node HTTP API.
2. `Util.getAddress`/`decodeFromBase58Check` or `ByteArray.fromHexString` throws a `DecoderException`/`NumberFormatException`.
3. `GetAccountServlet.doGet` catches it and calls `Util.processError(e, response)` [10](#0-9) .
4. The HTTP response body becomes `{"Error":"class java.lang.NumberFormatException : <raw message>"}`, exposing the exception's fully-qualified class name and internal message to the anonymous caller — analogous to the parse-server advisory's leak of internal error details for a malformed query.
