### Title
`queryDelegatableResource()` precompile and `calcCanDelegatedMaxSize` API return non-zero when resource delegation is unsupported/paused - ([File: actuator/src/main/java/org/tron/core/vm/utils/FreezeV2Util.java])

### Summary
The TVM precompile query `queryDelegatableResource()` (exposed on-chain to any deployed contract) and the corresponding gRPC/HTTP query `Wallet.calcCanDelegatedBandWidthMaxSize` / `calcCanDelegatedEnergyMaxSize` compute and return a positive "max delegatable balance" using only `VMConfig.allowTvmFreezeV2()` as a gate, while the actual state-changing path (`DelegateResourceActuator.validate()` / `DelegateResourceProcessor.validate()`) additionally requires `dynamicStore.supportDR()` and `dynamicStore.supportUnfreezeDelay()` to be enabled, throwing `"No support for resource delegate"` / `"Not support Delegate resource transaction, need to be opened by the committee"` otherwise. This mirrors the reported `maxFlashLoan()` bug class: a caller-facing "how much can I do" query omits a governance-controlled pause/support check that the real execution path enforces, so the query can report resource as delegatable when any attempt to actually delegate it will revert.

### Finding Description
`FreezeV2Util.queryDelegatableResource()` only checks `VMConfig.allowTvmFreezeV2()`: [1](#0-0) 

The same pattern exists in `Wallet.calcCanDelegatedBandWidthMaxSize` / `calcCanDelegatedEnergyMaxSize`, which compute a max size directly from frozen/usage balances with no support-flag check at all: [2](#0-1) 

In contrast, the actual `DelegateResourceActuator.validate()` gates the whole operation on `dynamicStore.supportDR()` and `dynamicStore.supportUnfreezeDelay()`: [3](#0-2) 

and `DelegateResourceProcessor.validate()` (used by the TVM native `delegateResource` opcode) gates on `dynamicStore.supportDR()`: [4](#0-3) 

Because the query functions never check `supportDR()`/`supportUnfreezeDelay()`, if the committee has not (or has no longer) enabled resource delegation, both the on-chain precompile and the off-chain API will still report a non-zero delegatable amount, while any transaction or contract call attempting to actually delegate that amount will revert with `"No support for resource delegate"`.

### Impact Explanation
This is a query/execution consistency bug, not a direct fund-theft or freezing vector: the reported "max delegatable size" can mislead any smart contract or off-chain client (an "unprivileged... API client" per scope) that uses `queryDelegatableResource` or `GetCanDelegatedMaxSize` to size a subsequent `DelegateResourceContract` transaction or a `delegateResource` TVM call, causing that downstream operation to unexpectedly revert. Unlike the original flash-loan report where the mis-reported max value could cause a third-party protocol to select a wrong lending source, here the impact is limited to failed/wasted transactions (reverted delegate calls) rather than a concrete unauthorized transfer, theft, or fund freeze.

### Likelihood Explanation
Reachable by any account or smart contract at any time via the `delegateResource`-related TVM precompile or the `GetCanDelegatedMaxSize` gRPC/HTTP API — no privileged role required. However, it only manifests when `supportDR()`/`supportUnfreezeDelay()` is disabled at the network level (a specific governance state), which is not the default/expected long-term state of a mature chain, so real-world likelihood is low.

### Recommendation
Add the same `dynamicStore.supportDR()` (and, where relevant, `supportUnfreezeDelay()`) checks used in `DelegateResourceActuator.validate()` / `DelegateResourceProcessor.validate()` to `FreezeV2Util.queryDelegatableResource()` and to `Wallet.calcCanDelegatedBandWidthMaxSize` / `calcCanDelegatedEnergyMaxSize`, returning `0` when delegation is unsupported, to keep the query results consistent with actual executability.

### Proof of Concept
1. Committee disables `supportDR` (or it has never been enabled on a given network/testnet).
2. A user or contract with sufficient `FrozenV2BalanceForBandwidth`/`FrozenV2BalanceForEnergy` calls the `queryDelegatableResource` TVM precompile, or the client calls `GetCanDelegatedMaxSize` — both return a positive available amount.
3. The same caller then submits a `DelegateResourceContract` transaction or invokes the `delegateResource` TVM opcode using that reported amount.
4. The operation reverts with `"No support for resource delegate"` from `DelegateResourceActuator.validate()` / `DelegateResourceProcessor.validate()`, contradicting the previously reported non-zero delegatable amount. [5](#0-4)

  public long calcCanDelegatedBandWidthMaxSize(
          ByteString ownerAddress) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    AccountCapsule ownerCapsule = accountStore.get(ownerAddress.toByteArray());
    if (ownerCapsule == null) {
      return 0L;
    }

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    processor.updateUsage(ownerCapsule);

    long accountNetUsage = ownerCapsule.getNetUsage();
    accountNetUsage += TransactionUtil.estimateConsumeBandWidthSize(dynamicStore,
            ownerCapsule.getFrozenV2BalanceForBandwidth());

    long netUsage = (long) (accountNetUsage * TRX_PRECISION * ((double)
            (dynamicStore.getTotalNetWeight()) / dynamicStore.getTotalNetLimit()));

    long v2NetUsage = getV2NetUsage(ownerCapsule, netUsage, dynamicStore.disableJavaLangMath());

    long maxSize = ownerCapsule.getFrozenV2BalanceForBandwidth() - v2NetUsage;
    return max(0, maxSize, dynamicStore.disableJavaLangMath());
  }

  public long calcCanDelegatedEnergyMaxSize(ByteString ownerAddress) {

  }
