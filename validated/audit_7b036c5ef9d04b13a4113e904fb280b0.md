The signer set for `reward_cycle % 2` is shared across **all three** message-type contracts (`signers-{0,1}-1` for `BlockResponse`, `signers-{0,1}-2` for `StateMachineUpdate`, `signers-{0,1}-3` for `BlockPreCommit`), all deriving their slot→signer mapping from the same `stackerdb-get-signer-slots-page` call in `.signers` [1](#0-0) . So for a given cycle-parity, the same `slot_id → StacksAddress` mapping is reused identically across the `BlockResponse`, `StateMachineUpdate`, and `BlockPreCommit` StackerDB instances [2](#0-1) , and the same contract names get reused every other reward cycle since the name only depends on `reward_cycle % 2` [3](#0-2) . The chunk signature digest itself never binds to the contract/StackerDB identity:### Title
Cross-StackerDB chunk replay: `SlotMetadata` signature omits the StackerDB contract ID, allowing a validly-signed chunk from one signer StackerDB to be replayed into another that shares the same signer set - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` (and therefore every `StackerDBChunkData` signature) only commits to `slot_id`, `slot_version`, and `data_hash` — it never includes the StackerDB's `QualifiedContractIdentifier`. Because the Nakamoto signer-set slot layout (`slot_id → StacksAddress`) is identical across the three per-message-type StackerDB contracts for a given cycle parity (`BlockResponse`, `StateMachineUpdate`, `BlockPreCommit`, all `signers-{0,1}-{msg_id}`), and is also re-used verbatim every other reward cycle (contract name only depends on `reward_cycle % 2`), a signature valid for one contract instance is *also* valid for a different, unrelated contract instance. This is the direct network-layer analog of the "chain ID missing from signed offer" bug class: the signed payload lacks the domain/context binding needed to prevent cross-context replay.

### Finding Description
The digest that gets signed is computed here: [4](#0-3) 

Note it hashes only `slot_id`, `slot_version`, and `data_hash` — no contract/DB identifier is mixed in. Verification is likewise contract-agnostic (only checks that the recovered pubkey hash matches the passed-in `principal`): [5](#0-4) 

The actual per-DB "authorization" comes entirely from an out-of-band lookup — `get_slot_signer(smart_contract_id, slot_id)` — done by the *caller* before invoking `verify()`: [6](#0-5) 

`validate_received_chunk()` (used both for chunks pulled via sync and for unsolicited `StackerDBPushChunk` gossip) checks: chunk size, expected-version array bounds, `slot_metadata.verify(&addr)` where `addr` comes from *that* contract's slot table, and version/write-count bounds. Nowhere is the contract ID cryptographically bound to the signature itself [7](#0-6) .

Now consider the deployment topology of the boot contracts. All signer-related StackerDBs for a given reward-cycle parity derive their `slot_id → signer address` mapping from the *same* underlying `.signers` state via `stackerdb-get-signer-slots-page`: [1](#0-0) 

and this identical page is consumed by every message-type contract for that cycle parity (`signers-0-1`, `signers-0-2`, `signers-0-3` all call `stackerdb-get-signer-slots-page u0`): [8](#0-7) 

The three message types (`BlockResponse=1`, `StateMachineUpdate=2`, `BlockPreCommit=3`) each map to their own `QualifiedContractIdentifier` built from `(cycle_parity, message_id)`: [2](#0-1) [9](#0-8) 

So for a fixed cycle parity, the same `(slot_id, StacksAddress)` mapping is installed identically across all three DBs. A signer's private key producing a valid `(slot_id, slot_version, data)` signature for, e.g., the `StateMachineUpdate` StackerDB (message_id=2) produces a signature that is **also cryptographically valid** for the same `slot_id`/`slot_version`/`data` in the `BlockPreCommit` StackerDB (message_id=3) or `BlockResponse` StackerDB (message_id=1), because `verify()` never checks which contract the chunk is destined for. Additionally, because `make_signers_db_name` only depends on `reward_cycle % 2`, the exact same contract name (and therefore identical `QualifiedContractIdentifier`) is reused every other reward cycle, meaning a chunk signed in cycle N can be replayed unmodified into the "same-named" contract in cycle N+2 if the signer's slot assignment happens to repeat.

Any unprivileged network peer that observes a legitimately signed chunk broadcast (via `StackerDBPushChunk` gossip or via HTTP GET of chunks) can re-POST those exact bytes (`slot_id`, `slot_version`, `sig`, `data`) to a *different* StackerDB replica's `POST /v2/stackerdb/:contract/chunks` endpoint. Since the byte-for-byte signature still recovers to the address that server believes owns that slot in that DB, the write is accepted as authentic — even though the original signer never intended or authorized that data to appear in that other DB/message-type context.

### Impact Explanation
This breaks the "authenticated vs. stored" equality for a specific StackerDB instance: data attributable to one signer message-type/round is injected into another logically distinct StackerDB (e.g., a `StateMachineUpdate` payload replayed into the `BlockPreCommit` slot, or a stale `BlockPreCommit`/`BlockResponse` chunk from a prior matching-parity cycle replayed into the current cycle's DB) purely by an unprivileged relayer replaying observed gossip — no private key needed by the attacker. Downstream consumers of these StackerDBs (e.g. `StackerDBListener`, `stacks-signer` monitors) parse chunks per contract and per message type and may misinterpret cross-context data as an authentic message of the wrong type/round from that signer, corrupting signer state-machine views or `BlockPreCommit`/`BlockResponse` interpretation. This matches the "network-wide propagation of forged data" / unauthorized-write class of impact, since the chunk is accepted as authentic in a context the signer never authorized.

### Likelihood Explanation
Likelihood is bounded by two preconditions that are guaranteed by design rather than incidental: (1) the slot-to-signer mapping is intentionally shared verbatim across the three message-type contracts for a cycle parity via `stackerdb-get-signer-slots-page`, and (2) contract names cycle with period 2 by `make_signers_db_name`. No attacker private key or admin role is required — only passive observation of gossiped/broadcast chunks (which are public, unencrypted p2p/HTTP traffic) and a single unauthenticated POST/relay to the target StackerDB's ports. This is a remote, unprivileged, low-cost action.

### Recommendation
Bind the smart contract identifier (and ideally chain/network ID) into the signed digest in `SlotMetadata::auth_digest()`, e.g. hash `smart_contract_id` (or a fixed message-type+reward-cycle-parity tag) alongside `slot_id`, `slot_version`, and `data_hash`, and update `verify()`/`sign()` call sites (`StackerDBChunkData`, `try_replace_chunk`, `validate_received_chunk`) to pass and check this context. This is a wire/data-format change requiring coordinated signer and node upgrades.

### Proof of Concept
1. Signer `S` is assigned slot 3 in both `signers-0-2` (`StateMachineUpdate`) and `signers-0-3` (`BlockPreCommit`) for reward cycle N (even parity), per the shared `stackerdb-get-signer-slots-page` mapping.
2. `S` legitimately signs and POSTs a `StateMachineUpdate` chunk `(slot_id=3, slot_version=7, data=D)` to `signers-0-2`; this chunk gets gossiped via `StackerDBPushChunk` to other nodes.
3. Attacker `A` (any unprivileged peer) observes this chunk on the wire and re-POSTs the identical `(slot_id=3, slot_version=7, sig, data=D)` tuple to a node's `signers-0-3` (`BlockPreCommit`) StackerDB endpoint.
4. The server calls `get_slot_signer(signers-0-3, 3)` → returns `S`'s address (same mapping), then `slot_metadata.verify(&S_addr)` succeeds because `auth_digest()` never included the contract ID — the forged-context chunk is accepted and stored/replicated as if `S` had authored a `BlockPreCommit` message.
