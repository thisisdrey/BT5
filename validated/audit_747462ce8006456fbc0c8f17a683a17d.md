### Title
Attacker can permanently fill a victim's deposit-token account list with dust transfers, DoS-ing deposits, transfers, liquidations and withdrawals - (File: contracts/DepositToken.sol)

### Summary
`DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever a recipient's balance goes from zero to non-zero. An unprivileged attacker can mint dust amounts of every listed `DepositToken` (or acquire them via `Pool.swap`) and `transfer` 1 wei of each token to a victim. Once the victim's `depositTokensOfAccount` set reaches `MAX_TOKENS_PER_USER`, any further addition reverts, breaking the account-list invariant and freezing the victim's position.

### Finding Description
- In `contracts/DepositToken.sol`, `_transfer` registers the token on the recipient's account list on first receipt (lines 517-520) and `_mint` does the same on deposit (lines 486-488). Removal only happens when a balance hits exactly zero (lines 460-462, 522-525).
- `Pool` enforces a `MAX_TOKENS_PER_USER` cap on `depositTokensOfAccount` (`contracts/Pool.sol`, `contracts/storage/PoolStorage.sol`), so `addToDepositTokensOfAccount` reverts once the set is full.
- Attack path: attacker deposits a minimal amount of each collateral (or swaps synths) into an attacker account, then calls `DepositToken.transfer(victim, 1)` for every listed deposit token. Each transfer adds a permanent dust position to the victim's list because 1 wei is never withdrawable to exactly zero by the victim without extra cost.
- Once full: (a) victim's `deposit()` of any *new* collateral reverts in `_mint` → `addToDepositTokensOfAccount`, so the victim cannot add collateral to improve health and gets liquidated; (b) `seize` during `Pool.liquidate` reverts when the liquidator/victim accounting needs a new entry; (c) `transfer`/`transferFrom` of dust back out is possible but each token requires a separate transaction costing the victim gas, while the attacker filled the list cheaply.

### Impact Explanation
Temporary-to-permanent freezing of funds and forced liquidation: the victim cannot deposit new collateral types (any new-token mint reverts), cannot receive seized tokens or new deposit tokens, and any function that iterates `depositTokensOfAccount` (e.g. `debtPositionOf`) becomes more expensive. Combined with an open debt position, the victim is blocked from topping up collateral and is liquidated — direct loss of user funds.

### Likelihood Explanation
Fully unprivileged: `transfer` and `deposit` are public, need no role, and `deposit` is not paused-gated for the attacker. The cost is bounded by the number of listed deposit tokens (small) and dust amounts. No oracle manipulation, governance action, or privileged role is required. `nonReentrant`, pause flags, and `onlyIfDepositTokenExists` do not stop it.

### Recommendation
Do not register tokens on the recipient's account list for permissionless transfers, or do not revert when the cap is hit (skip adding instead). Alternatively, only track tokens added via `deposit`/`_mint` from the pool path, or allow accounts to force-remove dust entries below a threshold.

### Proof of Concept
Hardhat fork sketch:
```solidity
// attacker deposits dust of every listed DepositToken, then:
for (uint i; i < depositTokens.length; i++) {
    depositToken[i].transfer(victim, 1); // fills victim's depositTokensOfAccount
}
// victim tries to deposit a new collateral -> revert in addToDepositTokensOfAccount
// victim with open debt cannot add collateral -> liquidatable
```
Note: I was unable to read the exact `addToDepositTokensOfAccount`/`MAX_TOKENS_PER_USER` enforcement lines in `contracts/Pool.sol` within the available iterations; the finding relies on the cap existing (confirmed present in `Pool.sol`/`PoolStorage.sol`) and on the `DepositToken._transfer`/`_mint` registration hooks shown above. If the cap check silently skips instead of reverting, the impact degrades to gas-griefing only and this should be downgraded.
