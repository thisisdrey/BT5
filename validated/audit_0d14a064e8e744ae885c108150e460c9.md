### Title
Transient `MSG_SENDER` leaks to arbitrary call depth — any contract regaining control during `Operator.execute` can act as the user ([File: contracts/Operator.sol](contracts/Operator.sol) / [File: contracts/utils/SynthContext.sol](contracts/utils/SynthContext.sol))

### Summary
`Operator.execute` stores the user's EOA in transient slot `MSG_SENDER_STORAGE` for the **entire duration** of the transaction (`setMsgSender` modifier, `Operator.sol` lines 20–24). `SynthContext._msgSender()` returns that stored address to any caller whenever `msg.sender == operator`, regardless of call depth (`SynthContext.sol` lines 14–24). This is the on-chain analogue of the OpenClaw bug: authentication is inferred from "the request arrived through the trusted channel" (loopback peer / Operator contract) rather than authenticating the actual originating call. Any contract that gains execution control inside a user's `execute` batch — e.g., an ERC-777/ERC-677 `tokensReceived` hook, a flash-loan callback, or a router/token call — can then invoke protocol functions and will be treated as the victim.

### Finding Description
The call chain: `EOA → Operator.execute → (call to attacker-reachable contract) → DepositToken.withdraw(amount, attacker)`. At step 3, `msg.sender == Operator`, so `SynthContext._msgSender()` returns the victim EOA. `_withdraw` then burns the victim's unlocked `msdToken` balance and calls `pool.treasury().pull(attacker, withdrawn)` (`DepositToken.sol` lines 406–411, 536–553).

Controls that do **not** stop it:
- `nonReentrant` on `execute` only blocks re-entry into `Operator`, not into `Pool`/`DepositToken`.
- `_withdraw`'s `nonReentrant` is a per-contract transient slot on `DepositToken`; there is no prior `DepositToken` frame, so it does not fire.
- `_revertIfLocked` only limits the amount to the victim's unlocked balance (`DepositToken.sol` line 409) — the unlocked portion is still fully stealable.
- `getActualMsgSender` does not verify the caller is part of a call the user intended; it just reads the slot.

### Impact Explanation
Direct theft of user funds: any user executing a batch through `Operator` that hands control to attacker code loses all unlocked collateral (via `withdraw`/`transfer`), can have debt manipulated, rewards claimed, etc. — everything reachable through `_msgSender()`.

### Likelihood Explanation
Requires the user's `execute` batch to pass control to attacker code. This is realistic because `Operator` exists precisely to compose arbitrary calls (swap routers, token approvals, flash loans); ERC-777-style receive hooks or a compromised/malicious target contract included in the batch suffice. Front-end-composed multicalls routinely include token contracts with callbacks.

### Recommendation
Bind the transient sender to the current `Operator` call frame only: e.g., have `Operator` set `MSG_SENDER` immediately around each `functionCallWithValue` (clearing it after each inner call), or require downstream contracts to accept an explicit `onBehalfOf`/signed-intent parameter instead of trusting `msg.sender == operator` at arbitrary depth.

### Proof of Concept
```solidity
// Attacker deploys Hook.sol with tokensReceived():
function tokensReceived(...) external {
    // During victim's Operator.execute batch; MSG_SENDER slot == victim
    uint256 amt = depositToken.unlockedBalanceOf(victim);
    depositToken.withdraw(amt, attacker); // _msgSender() resolves to victim
}

// Victim tx (e.g. UI-composed batch including an ERC-777 send to attacker):
operator.execute([Call({target: erc777, value: 0,
    callData: abi.encodeCall(IERC777.send, (attacker, 1, ""))})]);
// Result: treasury.pull(attacker, withdrawn) — victim's collateral stolen.
```
