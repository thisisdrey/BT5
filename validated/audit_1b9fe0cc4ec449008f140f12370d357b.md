### Title
Storage-proof soft-limit ordering (`process_local_receipts` before `process_delayed_receipts`) allows an unprivileged attacker to indefinitely starve a shard's delayed-receipt queue - (`runtime/runtime/src/lib.rs`, `core/parameters/src/config.rs`)

### Summary
`main_storage_proof_size_soft_limit` is enforced via a single shared `Trie` proof recorder for the whole chunk `apply()` call, and `process_receipts` runs `process_local_receipts` before `process_delayed_receipts` and `process_incoming_receipts` [1](#0-0) . An attacker can submit, in every chunk, a self-targeting (`signer_id == receiver_id`) `FunctionCall` local receipt that reads many of its own pre-populated storage keys and pushes the shared proof budget to the soft limit before the delayed queue is ever touched, causing `process_delayed_receipts` to break on its very first iteration [2](#0-1)  and defer the entire backlog (including an unrelated victim receipt) to the next chunk.

### Finding Description
`process_local_receipts` checks `processing_state.state_update.trie.check_proof_size_limit_exceed()` only *before* each receipt, not after, and pushes overflow receipts to the delayed queue [3](#0-2) . Because the check is pre-receipt, a single local receipt is always allowed to execute and can itself push the recorded storage proof up to (or slightly past) `main_storage_proof_size_soft_limit` (default 4 MB) as long as it stays under the separate, larger `per_receipt_storage_proof_size_limit` hard cap enforced in `apply_action_receipt` [4](#0-3) .

`process_receipts` then calls `process_delayed_receipts`, whose loop immediately checks `trie.check_proof_size_limit_exceed()` before popping anything, breaking out with zero receipts processed if the local phase already exhausted the budget [2](#0-1) . The same shared-trie-recorder budget is consumed by `process_incoming_receipts` as well. Since the proof recorder is fresh only once per `apply()` call (i.e., per chunk), an attacker who repeats this pattern — submit one self-call each chunk that reads enough of its own previously-inflated account storage to approach the 4 MB soft limit — can prevent *any* delayed receipt (not just a targeted victim's) from being dequeued for as long as they keep submitting such transactions. `CongestionInfo`/`CongestionControl`, which is the system's only automatic backpressure mechanism against this kind of shard monopolization, tracks delayed/buffered receipt **gas and byte** totals, not storage-proof size [5](#0-4) , so it does not detect or throttle this specific attack pattern: a single small victim receipt (e.g., a transfer) contributes negligible gas/bytes to `delayed_receipts_gas`, so `congestion_level` stays well under `reject_tx_congestion_threshold` and the attacker's local self-calls keep being admitted at the normal `process_tx_limit`.

This is a known engineering trade-off acknowledged in the docs ("receipts which perform a lot of trie removals might be limited more than theoretically applicable" and "the total size of storage proof could reach 8 MB") [6](#0-5) , but the specific mechanism of *local* receipts (from an unprivileged attacker's own account) monopolizing the entire per-chunk proof budget ahead of the delayed and incoming queues, indefinitely and renewably, does not appear to be checked against by congestion control.

### Impact Explanation
While the attack is sustained, no delayed receipt on the shard can make progress — this includes any victim's queued receipt carrying an attached transfer or callback. This is a liveness/DoS impact: temporary but renewable freezing of funds/state transitions for arbitrary unrelated users on the shard, entirely at the discretion of a single unprivileged attacker who only needs to keep paying for one cheap `FunctionCall` per chunk. It does not cause state-root divergence or theft, but it is a scoped liveness violation matching a DoS/liveness bounty category rather than a permanent-freeze category, since stopping the attacker's transactions restores normal processing on the next chunk.

### Likelihood Explanation
Preconditions: the attacker needs (1) a funded account, (2) a deployed contract with pre-populated storage large/deep enough that a bounded-gas `storage_read`/`storage_has_key` loop generates close to 4 MB of trie proof, and (3) the ability to get one transaction per chunk included (ordinary RPC submission, no special access). Populating storage is a one-time setup cost (storage staking); the recurring cost per chunk is just the gas fee for one `FunctionCall`. The feasibility of hitting ~4 MB of *proof* with a comparatively low, bounded *gas* cost depends on the gas-cost-vs-proof-size asymmetry inherent to trie-node touch accounting, which is exactly the asymmetry this limit was designed to bound and which the docs concede is only approximately estimated. This makes the attack plausible and repeatable but its exact cost-efficiency (gas spent per MB of proof) was not independently benchmarked here and would need to be measured/confirmed with a concrete PoC.

### Recommendation
Account for cumulative storage-proof usage in `CongestionInfo`/`CongestionControl` (or a similar per-account/per-shard throttle) so that an account whose own local receipts repeatedly saturate the proof-size soft limit is rate-limited independent of gas/byte-based congestion, and/or change the check ordering so `process_delayed_receipts`/`process_incoming_receipts` are guaranteed a minimum share of the per-chunk proof budget regardless of how much `process_local_receipts` consumed, analogous to the `allowed_shard_outgoing_gas` "provably impossible deadlock" guarantee already used elsewhere in congestion control [7](#0-6) .

### Proof of Concept
Integration/apply-loop test plan (extending the existing `test_main_storage_proof_size_soft_limit` pattern [8](#0-7)  and `storage_proof_size_limit.rs` test-loop harness [9](#0-8) ):
1. Deploy an attacker contract with a large/deep own-account storage footprint (many keys).
2. Enqueue one victim delayed receipt (e.g., a `Transfer` to a third account) into the shard's delayed queue.
3. For N chunks, include one attacker `FunctionCall` local receipt (signer==receiver==attacker) per chunk that reads enough of its own storage to push `state_update.trie.check_proof_size_limit_exceed()` to true.
4. Assert that after N chunks (N configurable, e.g. 20+) the victim's delayed receipt is still present in the delayed queue (`apply_result.delayed_receipts_count` unchanged / still contains the victim receipt), demonstrating no bound on deferral as long as the attacker sustains the pattern, versus the baseline where a delayed receipt with no competing local traffic drains within 1–2 chunks (as shown by chunks C/D in `storage_proof_size_limit.rs`).
5. Stop the attacker's local receipts and assert the victim's receipt is finally processed on the very next chunk, confirming the freeze is attacker-controlled rather than a permanent unrecoverable state.

    pub fn shard_accepts_transactions(&self) -> ShardAcceptsTransactions {
        let incoming_congestion = self.incoming_congestion();
        let outgoing_congestion = self.outgoing_congestion();
        let memory_congestion = self.memory_congestion();
        let missed_chunks_congestion = self.missed_chunks_congestion();

        let congestion_level = incoming_congestion
            .max(outgoing_congestion)
            .max(memory_congestion)
            .max(missed_chunks_congestion);

        // Convert to NotNan here, if not possible, the max above is already meaningless.
        let congestion_level =
            NotNan::new(congestion_level).unwrap_or_else(|_| NotNan::new(1.0).unwrap());
        if *congestion_level < self.config.reject_tx_congestion_threshold {
            return ShardAcceptsTransactions::Yes;
        }

        let reason = if missed_chunks_congestion >= *congestion_level {
            RejectTransactionReason::MissedChunks { missed_chunks: self.missed_chunks_count }
        } else if incoming_congestion >= *congestion_level {
            RejectTransactionReason::IncomingCongestion { congestion_level }
        } else if outgoing_congestion >= *congestion_level {
            RejectTransactionReason::OutgoingCongestion { congestion_level }
        } else {
            RejectTransactionReason::MemoryCongestion { congestion_level }
        };
        ShardAcceptsTransactions::No(reason)
    }

* `main_storage_proof_size_soft_limit - 4 MB`
  * This is a limit on the total size of storage proof generated by receipts in one chunk. Once receipts generate more storage proof than this limit, the chunk producer stops processing receipts and moves the rest to the delayed queue.
  * It's a soft limit, which means that the total size of storage proof could reach 8 MB (3.99MB + one receipt which generates 4MB of storage proof)
  * Due to implementation details it's hard to find the exact amount of storage proof generated by a receipt, so an upper bound estimation is used instead. This upper bound assumes that every removal generates additional 2000 bytes of storage proof, so receipts which perform a lot of trie removals might be limited more than theoretically applicable.
