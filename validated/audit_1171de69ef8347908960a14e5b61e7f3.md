### Title
Uninitialized/out-of-bounds heap read in `Zip64ExtraField::attr64()` via truncated Zip64 extra field in singlejar - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`singlejar` merges input jars supplied to a Bazel build (e.g. `deploy_jar`, `java_binary` output, third-party jars on the classpath). Parsing of the Central Directory Header (`CDH`) and Local Header (`LH`) 64-bit size/offset fields trusts a Zip64 extra-field record's *declared header* without validating that its *payload* actually contains the number of 8-byte attributes the caller is about to read.

### Finding Description
`ExtraField::find()` in `src/tools/singlejar/zip_headers.h:99-115` only verifies that the extra field's own declared `size()` (`4 + payload_size()`) fits within `extra_fields()`/`extra_fields_length()`. It never checks that `payload_size()` is large enough for the specific attribute index that will later be read.

`Zip64ExtraField::attr64(int index)` (`zip_headers.h:160`) blindly does `le64toh(attr_[index])` with no bound against `attr_count()`.

Callers such as `CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, `CDH::local_header_offset()`, and the equivalent `LH` methods (`zip_headers.h:406-437`, `482-493`) decide *which* index to read purely from the 32-bit field being `0xFFFFFFFF` (`ziph::zfield_has_ext64`), e.g.: [1](#0-0) 

If an attacker crafts a Zip64 extra field whose header declares `payload_size() == 0` (or smaller than needed) — i.e. a truncated Zip64 record, analogous to the truncated ASCONF address parameter in the kernel bug — but sets the corresponding 32-bit `compressed_file_size32`/`uncompressed_file_size32`/`local_header_offset32` field to `0xFFFFFFFF`, `zip64_extra_field()` still returns a non-null pointer (because the 4-byte header itself fits within the declared, bounds-checked extra-field region), and `attr64(0)`/`attr64(1)`/`attr64(2)` then reads 8-24 bytes past the actual payload boundary — into whatever bytes follow in the mapped/heap buffer (adjacent extra fields, comment field, next CDH entry, or uninitialized/adjacent heap memory). [2](#0-1) [3](#0-2) 

This is the exact class of bug in the report: a length/flag field is checked to be internally consistent ("chunk holds a valid header"), but the code trusts a fixed downstream read size that the checked length does not actually guarantee, producing a read of uninitialized/adjacent memory driven entirely by attacker-controlled length fields.

### Impact Explanation
`output_jar.cc` (singlejar's jar-merging tool) invokes these size/offset accessors while processing every input jar supplied to a `java_binary`/`java_library`/`deploy_jar` build action, including third-party or externally-fetched jars. A malicious jar with a crafted, truncated Zip64 extra field causes singlejar to read adjacent/uninitialized memory as if it were a 64-bit size or file offset. Depending on where that value flows (e.g. used as `local_header_offset` to locate the next header, or as a size used to bound subsequent memory copies), this can propagate uninitialized memory content into the output jar (information disclosure) or destabilize header-chain parsing (`LocateCentralDirectory`/`NextEntry` in `input_jar.cc`/`input_jar.h`) leading to further out-of-bounds reads/crashes during the build.

### Likelihood Explanation
Reaching this path only requires supplying a jar file with a hand-crafted CDH/LH Zip64 extra field to the build (e.g. a maven/third-party jar dependency, or any jar consumed as `srcs`/`deps`/`runtime_deps` merged with singlejar). No credentials, MITM, or trusted-repo Starlark access are required — an unprivileged attacker distributing a jar artifact is sufficient. The check that is expected to gate this (`ExtraField::find`'s bounds check) is present but insufficient, since it validates the extra-field envelope, not the payload size needed by each specific attribute reader.

### Recommendation
In `Zip64ExtraField::attr64()`, validate `index < attr_count()` before reading, and make every caller (`CDH`/`LH`/`ECD64`, etc.) treat a `zip64_extra_field()` whose `attr_count()` is insufficient for the requested attribute the same as `zip64_extra_field() == nullptr` (i.e., surface a corrupt-archive error rather than reading past the payload), mirroring `sctp_walk_params()`-style bounding used elsewhere.

### Proof of Concept
A `BuildIntegrationTestCase`/`zip_headers_test.cc`-style unit test can construct a `CDH` (or `LH`) with:
- `compressed_file_size32(0xFFFFFFFF)` (or `uncompressed_file_size32`/`local_header_offset32`),
- an extra-fields buffer containing a `Zip64ExtraField` with `payload_size(0)` (i.e., only the 4-byte tag/length header, no attribute bytes),

then call `cdh->compressed_file_size()` and observe that `attr64(index)` reads 8 bytes beyond the declared payload (verifiable with a poisoned/guard buffer as already done in `zip_headers_test.cc:135-227`, extending the existing `CentralDirectoryHeader` test with a short Zip64 payload and an MSAN/ASAN build to detect the uninitialized/out-of-bounds read). class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
  bool is(uint16_t tag) const { return htole16(tag_) == tag; }
  bool is_zip64() const { return is(1); }
  bool is_unix_time() const { return is(0x5455); }
  void signature(uint16_t tag) { tag_ = le16toh(tag); }

  uint16_t payload_size() const { return le16toh(payload_size_); }
  void payload_size(uint16_t v) { payload_size_ = htole16(v); }

  uint16_t size() const { return sizeof(ExtraField) + payload_size(); }

  const ExtraField* next() const {
    return reinterpret_cast<const ExtraField*>(ziph::byte_ptr(this) + size());
  }

} attr_packed;

class Zip64ExtraField : public ExtraField {
 public:
  static const Zip64ExtraField* find(const uint8_t* start, const uint8_t* end) {
    return reinterpret_cast<const Zip64ExtraField*>(
        ExtraField::find(1, start, end));
  }

  bool is() const { return is_zip64(); }
  void signature() { ExtraField::signature(1); }

  // The value of i-th attribute
  uint64_t attr64(int index) const { return le64toh(attr_[index]); }
  void attr64(int index, uint64_t v) { attr_[index] = htole64(v); }

  // Attribute count
  int attr_count() const { return payload_size() / sizeof(attr_[0]); }
  void attr_count(int n) { payload_size(n * sizeof(attr_[0])); }

  // Space needed for this field to accommodate n_attr attributes
  static uint16_t space_needed(int n_attrs) {
    return n_attrs > 0 ? sizeof(Zip64ExtraField) + n_attrs * sizeof(uint64_t)
                       : 0;
  }

 private:
  uint64_t attr_[];
} attr_packed;
