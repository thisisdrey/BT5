## Title
Legacy floating-point Bancor-relay math in `ExchangeProcessor` allows rounding-based value extraction from TRC10 Exchange pools - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The Balancer report describes an AMM whose invariant math diverged from actual token accounting (a compatibility/precision defect between the pool's internal bookkeeping and real token amounts), letting an attacker repeatedly interact with the pool to drain it. The closest reachable analog in java-tron is its native Bancor-style TRC10↔TRX/TRC10 liquidity pool ("Exchange" feature), whose default swap math (`ExchangeProcessor`) is implemented with IEEE‑754 `double` arithmetic rather than exact integer/BigDecimal math, and is directly reachable by any unprivileged account via `ExchangeTransactionContract`.

### Finding Description
`ExchangeCapsule.transaction()` selects a `Processor` to compute the AMM swap output, defaulting to the legacy `ExchangeProcessor` unless the "hardened" chain parameter is enabled: [1](#0-0) 

The legacy `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute the Bancor relay-token conversion using `double` and `Math.pow`, then truncate to `long`: [2](#0-1) 

This is invoked directly from an unprivileged, signed `ExchangeTransactionContract` via `ExchangeTransactionActuator.execute()`, which trusts the returned `anotherTokenQuant` to credit/debit the caller's TRX/TRC10 balances and update the pool's persisted `firstTokenBalance`/`secondTokenBalance`: [3](#0-2) 

Because the math is floating-point, repeated small swaps (in either direction) accumulate rounding error between the value the pool *believes* it holds (its stored `firstTokenBalance`/`secondTokenBalance`) and what should hold under an exact invariant — conceptually the same class of defect as Balancer's cached-vs-actual-balance mismatch that let an attacker structure a sequence of trades to extract value beyond what the true invariant allows. The project's own tests acknowledge this by adding a `SafeExchangeProcessor` (`BigDecimal`-based) and a "hardened" flag, and by asserting that legacy vs. hardened results diverge: [4](#0-3) 

The hardened path is opt-in via a dynamic-property/committee proposal (`allowHardenExchangeCalculation`), so on any deployment where this parameter has not been activated (the historical default), the exploitable legacy `double`-based math remains the active code path for every `ExchangeTransactionContract`.

### Impact Explanation
An attacker who repeatedly submits `ExchangeTransactionContract` swaps (permitted to any account, no special privilege required) can exploit the accumulated floating-point rounding of `exchangeToSupply`/`exchangeFromSupply` to obtain more of one token than the true bonding-curve invariant should yield, at the expense of other liquidity providers/traders in the same pool — a direct value-extraction/drain scenario on TRC10/TRX liquidity locked in the Exchange, analogous to the reported Balancer fund loss.

### Likelihood Explanation
Reachable by a single unprivileged, signed transaction type (`ExchangeTransactionContract`) with no special permissions, and requires only repeated calls with attacker-chosen `token_id`/`quant`, bounded by the `Not precise enough`/balance-limit checks that exist for Inject/Withdraw but not for the swap math itself. Exploitability depends on the magnitude of accumulated floating-point error being economically significant relative to gas/fee costs and pool size, and on the hardened flag not being enabled — both plausible on any node/testnet/private chain that has not activated `allowHardenExchangeCalculation`.

### Recommendation
Make `SafeExchangeProcessor` (BigDecimal-based) the default and only implementation used by `ExchangeCapsule.transaction()`, removing the legacy `ExchangeProcessor` double-based code path entirely, or force-enable `allowHardenExchangeCalculation` protocol-wide rather than leaving it as an optional committee proposal.

### Proof of Concept
1. Create an Exchange pool via `ExchangeCreateContract` with TRX and a TRC10 token.
2. Repeatedly submit `ExchangeTransactionContract` swaps alternating direction with small `quant` values, using `expected` set to the actuator's own pre-computed anotherTokenQuant so validation always passes.
3. Observe that the sequence of `double`-based `exchangeToSupply`/`exchangeFromSupply` conversions in `ExchangeProcessor` yields cumulative token output exceeding what the exact-math `SafeExchangeProcessor` would produce for the same swap sequence, as demonstrated by the differing results asserted in `ExchangeProcessorTest.testStrictMath` (`assertNotEquals(anotherTokenQuant, result)`), confirming the divergence exists in-repo between legacy and hardened math.

**Uncertainty note:** I could not fully verify from the indexed code whether `allowHardenExchangeCalculation` is enabled by default at genesis/mainnet or only via committee proposal (`ProposalUtil`/`ProposalService` reference it), nor did I find a concrete numeric example proving the rounding drift is large enough to be economically exploitable versus fees. Confirming default activation state and the real-world magnitude of the floating-point drift would require running the actual swap sequence against a live/test chain configuration, which is out of scope for this read-only analysis.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
