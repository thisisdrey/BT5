### Title
Unbounded array-length allocation in `PrecompiledContracts.BatchValidateSign`'s legacy (pre-`allowTvmSelfdestructRestriction`) path enables memory-amplification DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `batchValidateSign` TVM precompile decodes an attacker-supplied ABI-encoded array of addresses via `extractBytes32Array`, which allocates a Java array sized by a length value taken directly from calldata, with no upper bound check when the `allowTvmSelfdestructRestriction` hard fork switch is off (the legacy behavior). This mirrors the Cap'n Proto CVE-2015-2312 bug class: a small message can declare a huge element count, forcing the receiver to allocate/iterate proportional to the *declared* size rather than the actual (small) input size.

### Finding Description
`extractBytes32Array` reads the element count straight from the calldata word and allocates an array of that size before any validation: [1](#0-0) 

This is invoked from `BatchValidateSign.doExecute` to build the `addresses` array: [2](#0-1) 

The size guard (`sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE`) that bounds the declared array length is only applied when `VMConfig.allowTvmSelfdestructRestriction()` is true: [3](#0-2) 

When that flag is off, `extractBytesArray`/`extractSigArray` (used for signatures) at least bound-check the `offset` against `words.length`, but `extractBytes32Array` (used for addresses) has no such check at all — neither on `offset` nor on `len` before the `new byte[len][]` allocation. Because `len` comes from `words[offset].intValueSafe()`, an attacker can craft an ABI header word claiming an address-array length near `Integer.MAX_VALUE` while keeping the actual submitted calldata tiny, since `getEnergyForData` charges energy based only on `data.length`, not on the claimed array length: [4](#0-3) 

This decouples the cost charged to the caller from the resource consumption imposed on the node — exactly the amplification pattern in the Cap'n Proto advisory referenced in the report.

Note: I was not able to fully verify the exact clamping behavior of `DataWord.intValueSafe()` (whether it always returns a value ≤ `Integer.MAX_VALUE` or can itself throw/clamp) because the method's implementation was not located within the indexed portion of `DataWord.java`; the search only found `intValueSafe` usages in `PrecompiledContracts.java`, `OperationActions.java`, `Program.java`, `EnergyCost.java`, and `ProgramInvokeImpl.java`, but not its definition. Confirming the exact numeric range `len` can take requires reading the full `DataWord.java` source, which a Devin session with full file access could do.

### Impact Explanation
If `len` can reach values in the hundreds of millions to `Integer.MAX_VALUE` (2^31-1), `new byte[len][]` allocates an object-reference array of that size (4–8 bytes per reference plus array header), i.e. up to ~16 GB just for the reference array before any element is populated — likely triggering an immediate `OutOfMemoryError` in the node JVM. Since this runs inside contract execution triggered by any `TriggerSmartContract` transaction (fully permissionless, deployable/callable by any account), a single crafted transaction could crash or destabilize full nodes/SRs processing it, which is a node-crash/availability impact under the report's acceptance criteria.

### Likelihood Explanation
Reachability is straightforward for any account: deploy or call a contract that performs a `CALL`/`STATICCALL` to the `BatchValidateSign` precompile address with crafted calldata (this is exactly what `BatchValidateSignContractTest` in the test suite exercises via `AbiUtil`/`TvmTestUtils` calldata construction, confirming the precompile is reachable via ordinary TVM `CALL` semantics): [5](#0-4) 
Likelihood depends on whether `allowTvmSelfdestructRestriction` (a hard-fork-gated `VMConfig` flag) is already activated on mainnet — if it is enabled network-wide, the `MAX_SIZE` guard is always applied and this path is not reachable; if any network (including older/forked networks or misconfigured private chains) still runs with that flag disabled, the unguarded legacy path remains live. I could not confirm the current mainnet activation status of `allowTvmSelfdestructRestriction` from the indexed files.

### Recommendation
Add the same `MAX_SIZE` bound check unconditionally (not gated behind `allowTvmSelfdestructRestriction`) before calling `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, and additionally harden `extractBytes32Array` itself to validate `len` against both `MAX_SIZE` and the available `words.length` before allocating, mirroring the `offset > words.length - 1` guard already present in `extractBytesArray`/`extractSigArray`.

### Proof of Concept
Conceptual (cannot be fully executed without runtime access to confirm `intValueSafe` clamping and the current value of `allowTvmSelfdestructRestriction` on target network):
1. Deploy any contract capable of issuing a `STATICCALL`/`CALL` to the `BatchValidateSign` precompile address, or call it directly if reachable from an EOA-triggered contract.
2. Construct calldata matching the ABI header words (`hash`, sig-array offset word, addr-array offset word) such that the word at the addr-array offset encodes a very large length (e.g., close to `0x7fffffff`), while keeping the rest of the calldata minimal/absent — analogous to the parameter construction in `BatchValidateSignContractTest.validateMultiSign`: [6](#0-5) 
3. Submit via `TriggerSmartContract` on a network/configuration where `allowTvmSelfdestructRestriction` is not yet activated, so the `MAX_SIZE` guard at lines 1165-1171 is skipped and `extractBytes32Array` is invoked directly with the attacker-controlled `len`.
4. Observe large/failed allocation (`OutOfMemoryError`) or excessive GC pressure in the node processing the transaction.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();

  }
