### Title
Atlas attachment downloader accepts and stores peer-returned content without verifying it hashes to the requested `content_hash` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When the Atlas subsystem fetches an `Attachment` from a remote peer in response to an `AttachmentRequest`, the returned bytes are inserted into the local `AtlasDB` and cached as validated content without ever comparing `Attachment::hash()` against the `content_hash` that was actually requested. A malicious, unauthenticated peer serving `/v2/attachments/<content_hash>` can return arbitrary content, which the requesting node will unconditionally accept, hash on its own terms, and persist into `attachments` (marked `was_instantiated = 1`).

### Finding Description
`AttachmentRequest` carries the expected `content_hash` [1](#0-0) . `AttachmentsBatchStateContext::extend_with_attachments` receives the HTTP response for that request and inserts `response.attachment` into `self.attachments: HashSet<Attachment>` with **no comparison of `response.attachment.hash()` to `request.content_hash`** — it only checks that the response decodes at all: [2](#0-1) .

Later, in `AttachmentsDownloader::run`, once the state machine reaches `Done`, every attachment collected in `context.attachments` is committed to the database via `insert_instantiated_attachment`, keyed by the hash the node computes *from the bytes it received* — again without ever checking that hash against the original request's `content_hash`: [3](#0-2) .

`insert_instantiated_attachment` writes the content straight into the `attachments` table as `was_instantiated = 1` and flips `is_available = 1` on any `attachment_instances` row whose `content_hash` matches the *self-computed* hash of the delivered bytes: [4](#0-3) . There is also no size bound enforced against `AtlasConfig::attachments_max_size` at this ingestion point [5](#0-4) , so a peer can return an oversized blob decoded straight from hex in the JSON response [6](#0-5) , consuming memory/DB storage.

This breaks the intended equality: "content served under a `content_hash` request must hash to that `content_hash`." The self-consistency check (data actually equals `Hash160::from_data(&content)`) is present, but the authorization/identity check (returned data corresponds to the *requested* hash) is absent. Any content whose hash the node computes gets written to disk as an "instantiated," trusted attachment and gets paired with whatever `attachment_instances` happen to reference that hash — including instances created later by different, unrelated on-chain events, since the DB write is a global side effect keyed only by hash, not tied to the specific request context.

### Impact Explanation
This matches the "attachment/BNS mismatch" impact class explicitly called out as acceptable High severity: a node's Atlas cache/BNS zonefile data can be poisoned by any of the (fully untrusted, unauthenticated) peers it queries for attachments, since the download path never validates the peer-supplied content against the specific hash it asked for before persisting it as validated, "instantiated" data. Combined with the missing size cap at ingestion, an adversarial or misbehaving replica can also inflate local storage/memory with oversized attachment blobs on every retry cycle.

### Likelihood Explanation
Any remote node the requester queries via the standard `/v2/attachments/<hash>` GET endpoint can trigger this — no authentication, no special privilege, and no need to guess or precompute a hash preimage that's meaningful beyond "some other `attachment_instances` row happens to reference the same hash," which is a low bar for content the peer already knows the node is asking about (the peer literally receives the requested `content_hash` in the URL and can trivially engineer bytes/side effects that reuse an already-known hash, e.g. re-serve `Attachment::empty()` for a genuinely non-empty hash to poison the uninstantiated/instantiated bookkeeping, or return oversized data every retry).

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, before inserting into `self.attachments`, verify `response.attachment.hash() == request.content_hash`; drop/penalize (via `report.bump_failed_requests()`) any response that fails this check instead of accepting it. Also enforce `attachment.content.len() <= atlas_config.attachments_max_size` at this same ingestion point before it ever reaches `insert_instantiated_attachment`.

### Proof of Concept
1. Node A has an `AttachmentInstance` with `content_hash = H1` pending resolution, and issues `GET /v2/attachments/H1` to peer B (a normal, unauthenticated Atlas peer).
2. Malicious peer B, instead of returning content that hashes to `H1`, returns arbitrary bytes `C2` (e.g. the empty attachment, or bytes matching some other known/soon-to-be-created attachment's hash `H2`).
3. `extend_with_attachments` decodes the response and inserts `Attachment::new(C2)` into `context.attachments` with no check against `H1` (`stackslib/src/net/atlas/download.rs:547-548`).
4. `AttachmentsDownloader::run`'s `Done` branch computes `attachment.hash()` (which is `H2`, not `H1`), calls `insert_instantiated_attachment`, and pairs/resolves any `attachment_instances` rows matching `H2` — silently persisting B's chosen content as validated Atlas/BNS data while A's original request for `H1` is left unresolved and eventually times out/retries, all while B's unrelated `C2` payload is now trusted local state.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
