### Title
Unsynchronized `GetPaginatedNowWitnessList` API read races with lock-held `MaintenanceManager.doMaintenance()` mutation of `VotesStore`/`WitnessStore` - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getPaginatedNowWitnessList()` is reachable directly from an unauthenticated HTTP/gRPC API call (`GetPaginatedNowWitnessListServlet` / `RpcApiService`) and reads `WitnessStore.getAllWitnesses()` and iterates `VotesStore` via `countVote()` without acquiring the `Manager`'s block-application lock. Meanwhile, `MaintenanceManager.doMaintenance()` — invoked from `Manager.pushBlock()` inside `synchronized (this)` — mutates the very same `VotesStore` (deleting entries) and `WitnessStore` (rewriting vote counts) during block application. This is structurally the same bug class as CVE-2026-74561: a store/list that is walked by an unlocked, externally-reachable code path while a locked, serialized code path concurrently mutates and removes entries from that same collection.

### Finding Description
`Wallet.getPaginatedNowWitnessList()` at [1](#0-0)  fetches the full witness list and then computes vote deltas by iterating `VotesStore` via `countVote(votesStore)`, all without taking any lock on `Manager`. The `countVote` implementation reads `votesStore.iterator()` and reads each `VotesCapsule`'s old/new votes [2](#0-1) .

Concurrently, block application runs inside `synchronized (this)` in `Manager.pushBlock()` [3](#0-2) , which eventually invokes `MaintenanceManager.doMaintenance()` (via `MaintenanceManager.applyBlock()`). `doMaintenance()` calls `countVote(votesStore)` and then **deletes every entry from `votesStore`** as part of its own count pass [4](#0-3) , and rewrites `WitnessCapsule` vote counts via `consensusDelegate.saveWitness(...)` for every witness affected by votes in that epoch [5](#0-4) .

Because the API-facing `getPaginatedNowWitnessList()` path takes no synchronization on the `Manager` object (or any store-level lock) while performing its multi-step read-then-mutate-in-memory sequence (read `witnessCapsuleList`, read+accumulate `votesStore` entries, apply deltas), a concurrently running block-application thread holding the `Manager` monitor can simultaneously be deleting `VotesStore` entries and rewriting `WitnessCapsule` records that the servlet thread is in the middle of reading and mutating (`witnessCapsule.setVoteCount(...)` at [6](#0-5) ). The developers' own comment acknowledges this exact class of race ("the race condition of VoteStores deleted but Witness vote counts not updated") [7](#0-6) , and the existing mitigation only covers the specific "maintenance in progress" flag window, not the general unlocked concurrent-store-mutation race — the underlying `VotesStore`/`WitnessStore` iteration itself is still performed with zero synchronization against the `Manager`'s block-processing lock, exactly analogous to `nh_rt_cache_flush()` walking `nh->f6i_list` without `nh->lock` while the locked IPv6 route path mutates and frees `fib6_info` entries.

### Impact Explanation
Since Java has garbage collection, this cannot produce a raw use-after-free/RCE like the kernel bug; the concrete impact is:
- **API a node can no longer serve**: concurrent read/iterate on a `LevelDbDataSourceImpl`/`RocksDbDataSourceImpl`-backed store while another thread deletes/rewrites entries in the same window can surface as store iterator exceptions or inconsistent/corrupted response construction, which the servlet only wraps in generic `Util.processError`, but under a maintenance-epoch boundary crossing this can throw unexpected runtime exceptions that are not one of the checked types handled gracefully, potentially destabilizing the request-handling thread pool under sustained abuse (an unprivileged remote caller can simply spam this endpoint around every maintenance-cycle boundary, a fully predictable window since maintenance times are public/deterministic on-chain data).
- Data returned to callers (vote counts, active witness set) can be transiently inconsistent (stale or double-counted) because the count map is built from a store that a competing block-application thread is actively clearing/rewriting — this does not by itself move funds, but it does provide out-of-spec query results for the query API path called out as in-scope ("HTTP/gRPC/JSON-RPC query paths into Wallet").

Given the honest assessment: this is a real, in-scope, unlocked-concurrent-collection race analogous to the kernel bug's structure, but the demonstrable concrete impact in java-tron is bounded to request-thread failures/inconsistent query responses rather than memory corruption, RCE, or fund theft. I could not find a path from this specific race to unauthorized balance mutation, so per the strict "Validate" criteria (unauthorized account operation, theft/freezing of funds, unbacked balance, node crash/halt, chain split, key disclosure, RCE, or unservable API) the only qualifying outcome here is the "API the node can no longer serve" / node instability angle, and it is comparatively weaker/less certain than the original kernel UAF.

### Likelihood Explanation
The maintenance window is fully deterministic and publicly computable (`getNextMaintenanceTime()`), and the HTTP/gRPC endpoint requires no authentication, no fee, and no special privilege — any external caller can time repeated requests to land exactly during `doMaintenance()` execution. However, triggering an observable failure (rather than simply a slightly stale response) requires winning a narrow timing race against the votes-store clearing loop, so real-world reliability of a crash/DoS outcome is uncertain without further empirical testing that I could not perform here.

### Recommendation
Synchronize `Wallet.getPaginatedNowWitnessList()` (and its `countVote` helper) on the same lock used by `Manager.pushBlock()`/`applyBlock()` before reading `WitnessStore`/`VotesStore`, or take a consistent point-in-time snapshot (e.g., via the revoking/snapshot mechanism already used elsewhere in `chainbase`) rather than iterating the live mutable stores directly. At minimum, widen the existing maintenance-flag check to cover the entire duration of the read+aggregate sequence, not just an initial flag check, to close the TOCTOU race.

### Proof of Concept
1. Node is running normally; note the publicly-readable `getNextMaintenanceTime()` value from `DynamicPropertiesStore`.
2. An external client repeatedly calls `GET /wallet/getpaginatednowwitnesslist` (`GetPaginatedNowWitnessListServlet`) in a tight loop timed to straddle the computed maintenance-time boundary.
3. Concurrently, the node's block-application thread reaches `MaintenanceManager.doMaintenance()` for the block that crosses `nextMaintenanceTime`, which begins deleting `VotesStore` entries and rewriting `WitnessCapsule` vote counts.
4. Because `getPaginatedNowWitnessList()`/`countVote()` hold no lock, the request thread's iteration over `votesStore` and its read/write of `witnessCapsuleList` entries interleaves with the maintenance thread's concurrent deletes/writes to the same underlying LevelDB/RocksDB-backed stores, producing inconsistent vote totals in the API response or an unexpected iterator/runtime exception in the servlet thread.

Note: I was unable to fully verify runtime behavior (e.g., whether the underlying `TronStoreWithRevoking` iterator throws under concurrent mutation or silently returns stale data) without executing the code; this assessment is based on static analysis of the described data flow.

```java
  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
```

```java
  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
```
