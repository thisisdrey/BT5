## Finding: `TrieKey::PromiseYieldReceipt` / `PromiseYieldTimeout` survive `remove_account` — enables account-name-reuse authorization escalation

### Title
Stale PromiseYield receipts/timeouts survive `DeleteAccount` and re-execute self-privileged batched actions against a re-created account of the same name - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`remove_account` only removes `TrieKey::Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` entries; it never touches `TrieKey::PromiseYieldReceipt`, `PromiseYieldStatus`, or the `PromiseYieldTimeout` queue. [1](#0-0)  If an account self-creates a `PromiseYield` receipt and then batches additional privileged actions (e.g. `AddKey` with full access) onto the same promise index before deleting itself, that pending receipt (keyed only by `receiver_id + data_id`) remains in state after `DeleteAccount`, and its `PromiseYieldTimeout` queue entry (keyed by index, not scoped to account existence) still fires at `expires_at` regardless of account deletion. [2](#0-1) 

### Finding Description
`set_promise_yield_receipt`/`remove_promise_yield_receipt` operate on `TrieKey::PromiseYieldReceipt{receiver_id, data_id}`. [3](#0-2)  This key is only removed when a `PromiseResume` receipt is actually processed for that `(receiver_id, data_id)` pair. [4](#0-3)  `remove_account` never queries or deletes this key space, nor `PromiseYieldStatus`, nor pending `PromiseYieldTimeout` entries. [1](#0-0) 

A contract calling `promise_yield_create` (predecessor_id == receiver_id == the caller's own account, since it targets itself) receives a promise index tied to a `ReceiptIndex` that already has one `FunctionCall` action appended. [5](#0-4)  Because this is a regular batched-action promise index, the contract can append additional actions to the same receipt via standard host functions such as `promise_batch_action_add_key_with_full_access`, which simply calls `append_action_add_key_with_full_access` on the same `receipt_index`. [6](#0-5)  The resulting stored receipt therefore has `actions = [FunctionCall, AddKey(FullAccess, attacker_pubkey)]`, `predecessor_id == receiver_id == A`, and is parked as `ReceiptEnum::PromiseYieldV2` in `TrieKey::PromiseYieldReceipt`. [7](#0-6) 

Later, either an explicit resume, or — critically — the automatic timeout mechanism, delivers a `PromiseResume` to `receiver_id = A`. [8](#0-7)  `process_receipt`'s `PromiseResume` arm looks up `get_promise_yield_receipt(state_update, account_id, data_receipt.data_id)` using only `account_id` (the *current* occupant of that name) and `data_id`; if found, it executes the parked receipt via `apply_action_receipt` — including the batched `AddKey(FullAccess)` action — with `predecessor_id == receiver_id == A`, satisfying the same-actor "administrative actions... only if sender=receiver" rule regardless of who currently owns account `A`. [9](#0-8) 

This is exploitable specifically because account names can be freed and re-registered by an unrelated party: `CreateAccount` only requires the new id be a sub-account of `predecessor_id` (or created by the registrar for top-level ids), with no dependency on prior occupant history. [10](#0-9)  Many real registrars (e.g. `near`) permit third parties to create arbitrary sub-accounts on behalf of end users (linkdrop-style registration flows), so an attacker can deliberately "squat" a desirable name, install a booby-trapped yield, delete the account to reclaim its balance, and wait for the name to be re-registered by a victim.

### Impact Explanation
If a victim later registers the exact same account name before the yield's timeout has fired, and the attacker's pending yield resumes (via explicit resume trigger or automatic timeout), the attacker's chosen full-access public key is silently added to the victim's brand-new account — full authorization escalation/account takeover, matching the "authorization escalation across accounts" bounty category. This is a direct consequence of `remove_account`'s failure to purge `PromiseYieldReceipt`/`PromiseYieldStatus`/`PromiseYieldTimeout` state.

### Likelihood Explanation
The practical likelihood is constrained by a narrow timing window: the `PromiseYieldTimeout` entry fires unconditionally at `expires_at = creation_height + yield_timeout_length_in_blocks`, and once it fires the stale receipt is consumed and removed even if the account doesn't exist at that time (the action simply fails with `AccountDoesNotExist` and produces no lasting state). Thus the attack only succeeds if a victim re-registers the *exact* deleted account name within the (relatively short) yield timeout window — a narrow, low-probability coincidence for an attacker who does not control when/if a specific name gets re-claimed. This significantly limits real-world exploitability against an arbitrary unsuspecting victim, though it remains a genuine confirmed logic flaw (stale privileged receipt surviving account deletion) rather than a purely theoretical one. I was not able to confirm the exact numeric default of `yield_timeout_length_in_blocks` from the parameter files within the available iterations, which affects how tight this window actually is.

### Recommendation
`remove_account` in `core/store/src/utils/mod.rs` should also enumerate and remove any `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, and pending `TrieKey::PromiseYieldTimeout` entries associated with the account being deleted (or, more robustly, `process_receipt`'s `PromiseResume` handling and `resolve_promise_yield_timeouts` should additionally verify that the parked receipt's `predecessor_id`/creation context still corresponds to a live, unchanged account generation before executing its actions).

### Proof of Concept
Integration/test-loop plan:
1. Deploy a test contract to account `A` that, in one function call, invokes `promise_yield_create` to get `promise_idx`, then calls `promise_batch_action_add_key_with_full_access(promise_idx, attacker_pubkey, nonce)`.
2. Submit `DeleteAccount(A)` before the yield is resumed or times out.
3. Submit `CreateAccount` to re-create `A` as a sub-account (simulating a different owner re-registering the freed name), asserting it succeeds with a fresh `Account` and no access keys.
4. Advance blocks to the yield's `expires_at` height (or submit an equivalent trigger) so `resolve_promise_yield_timeouts` fires a `PromiseResume` for the same `data_id`.
5. Assert that after this resume executes, `attacker_pubkey` now has a `FullAccess` `AccessKey` on the re-created account `A` — demonstrating the new owner's account was compromised without any signature from the new owner.

pub fn set_promise_yield_receipt(state_update: &mut TrieUpdate, receipt: &Receipt) {
    match receipt.versioned_receipt() {
        VersionedReceiptEnum::PromiseYield(action_receipt) => {
            assert!(action_receipt.input_data_ids().len() == 1);
            let key = TrieKey::PromiseYieldReceipt {
                receiver_id: receipt.receiver_id().clone(),
                data_id: action_receipt.input_data_ids()[0],
            };
            set(state_update, key, receipt);
        }
        _ => unreachable!("Expected PromiseYield receipt"),
    }
}

pub fn remove_promise_yield_receipt(
    state_update: &mut TrieUpdate,
    receiver_id: &AccountId,
    data_id: CryptoHash,
) {
    state_update.remove(TrieKey::PromiseYieldReceipt { receiver_id: receiver_id.clone(), data_id });
}

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
