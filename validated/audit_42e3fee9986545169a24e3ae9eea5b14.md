### Title
`do_native_withdraw`, `do_storage_deposit`, `do_auth_call` never re-credit signer's wNEAR balance when the second (post-`near_withdraw`) promise fails - ([File: contracts/defuse/src/contract/tokens/nep141/native.rs], [File: contracts/defuse/src/contract/tokens/nep141/storage_deposit.rs], [File: contracts/defuse/src/contract/intents/auth_call.rs])

### Summary
`do_native_withdraw`, `do_storage_deposit`, and `do_auth_call` each start with `require!(promise_result_checked_void(0).is_ok(), "near_withdraw failed")` to confirm `near_withdraw` succeeded, then schedule a *second* promise (`transfer`, `storage_deposit`, or `on_auth`) with no further `.then()` resolver attached to check that second promise's outcome. Unlike `internal_ft_withdraw`, which always chains a `ft_resolve_withdraw` callback that refunds via `self.deposit` on failure, none of these three paths ever re-credits the signer's internal `Nep141TokenId(wnear_id)` balance if the second promise fails.

### Finding Description
The broken binding is: `value_debited(signer, wnear) == value_delivered_or_recredited(signer)`.

For `native_withdraw` / `storage_deposit` / `auth_call` (with non-zero `attached_deposit`), `contracts/defuse/src/contract/intents/state.rs` (lines 212-337) immediately calls `self.withdraw(...)`, which synchronously does `internal_sub_balance` (`contracts/defuse/src/contract/tokens/mod.rs:76-128`), debiting the signer's wNEAR balance and emitting a burn event. It then schedules `near_withdraw` → `.then(do_native_withdraw/do_storage_deposit/do_auth_call)`.

Each of these `#[private]` callbacks: [1](#0-0) [2](#0-1) [3](#0-2) 

only checks `promise_result_checked_void(0)` — the *first* promise's (`near_withdraw`) result — then schedules the second promise (`Promise::new(receiver_id).transfer(...)`, `ext_storage_management::storage_deposit`, or `ext_auth_callee::on_auth`) and returns it directly with no further `.then(...)` callback. Compare with `internal_ft_withdraw` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs:53-107`), which always appends `.then(Self::ext(...).ft_resolve_withdraw(...))` after `do_ft_withdraw`'s promise chain, regardless of whether a `storage_deposit` leg is present, so the transfer/transfer_call result is checked and refunded via `FungibleTokenWithdrawResolver::ft_resolve_withdraw` on failure.

Because near receipts/promises are asynchronous and the internal balance was already permanently decremented before the second promise resolves, if that second promise fails (e.g., `transfer` to a non-existent named account for `native_withdraw`, a reverting `storage_deposit` call for `storage_deposit`, or a reverting `on_auth` callee for `auth_call`), the debited wNEAR is never restored to the signer and never actually delivered anywhere the signer can recover it (raw NEAR failing back lands in the contract's own account, not the signer's Verifier balance).

An attacker/signer's own `NativeWithdraw`/`StorageDeposit`/`AuthCall` intent (part of a signed `MultiPayload`) specifies `receiver_id`/`contract_id`/`msg` themselves, so a griefer able to influence the state of a shared target contract (e.g., an `storage_deposit` target that already has the account registered and panics, or an `on_auth` callee whose behavior depends on external, attacker-manipulable state) can force the second promise to fail for a legitimate signer's already-signed intent, permanently freezing that signer's debited wNEAR with no recredit path.

### Impact Explanation
Signer's wNEAR balance is unconditionally burned from Verifier accounting on downstream-promise failure with no compensating refund event or resolver, for all three of `native_withdraw`, `storage_deposit`, and `auth_call`. This matches the "refund or resolver credit that does not match what failed to settle" / "user funds permanently frozen" Critical categories: the Verifier's internal ledger permanently loses value that was never delivered to the intended recipient and never returned to the signer, while `internal_ft_withdraw`'s `ft_resolve_withdraw` demonstrates the correct pattern exists elsewhere in the same codebase. This is repeatable per intent/account and applies to any account performing a native withdraw, storage deposit, or auth call whose second-leg promise fails.

### Likelihood Explanation
Triggering requires only causing the *second* promise (post-`near_withdraw`) to fail — e.g., a non-existent/misconfigured `receiver_id` for `native_withdraw`, an already-registered account or panicking `storage_deposit` callee for `storage_deposit`, or a reverting `on_auth` implementation for `auth_call`. All of these are realistically achievable with attacker-deployed or attacker-influenced target contracts, or simple misconfiguration, at negligible cost (a single withdraw intent + gas). No privileged role, relayer key, or DAO/role holder is needed.

### Recommendation
Attach a `.then()` resolver callback (analogous to `ft_resolve_withdraw`) to the second promise in `native_withdraw`, `storage_deposit`, and `auth_call` (`contracts/defuse/src/contract/intents/state.rs`, `contracts/defuse/src/contract/tokens/nep141/native.rs`, `contracts/defuse/src/contract/tokens/nep141/storage_deposit.rs`, `contracts/defuse/src/contract/intents/auth_call.rs`) that checks the second promise's `PromiseResult` and calls `internal_add_balance`/`self.deposit` to re-credit the signer's wNEAR balance on failure, mirroring `FungibleTokenWithdrawResolver::ft_resolve_withdraw`.

        if !auth_call.attached_deposit.is_zero() {
            require!(
                promise_result_checked_void(0).is_ok(),
                "near_withdraw failed",
            );
        }

        let min_gas = auth_call.min_gas();
        let mut p = Promise::new(auth_call.contract_id);

        if let Some(state_init) = auth_call.state_init {

        }

        ext_auth_callee::ext_on(p)
            .with_attached_deposit(auth_call.attached_deposit)
            .with_static_gas(min_gas)
            .on_auth(signer_id, auth_call.msg)
    }

impl Contract {
    pub(crate) fn internal_ft_withdraw(
        &mut self,
        owner_id: AccountId,
        withdraw: FtWithdraw,
        force: bool,
    ) -> Result<PromiseOrValue<U128>> {
        self.withdraw(
            &owner_id,
            iter::once((
                Nep141TokenId::new(withdraw.token.clone()).into(),
                withdraw.amount,
            ))
            .chain(withdraw.storage_deposit.map(|amount| {
                (
                    Nep141TokenId::new(self.wnear_id().into_owned()).into(),
                    amount.as_yoctonear(),
                )
            })),
            Some("withdraw"),
            force,
        )?;

        let is_call = withdraw.is_call();
        Ok(if let Some(storage_deposit) = withdraw.storage_deposit {
            ext_wnear::ext(self.wnear_id.clone())
                .with_attached_deposit(NearToken::from_yoctonear(1))
                .with_static_gas(NEAR_WITHDRAW_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .near_withdraw(U128(storage_deposit.as_yoctonear()))
                .then(
                    // schedule storage_deposit() only after near_withdraw() returns
                    Self::ext(env::current_account_id())
                        .with_static_gas(
                            Self::DO_FT_WITHDRAW_GAS
                                .checked_add(withdraw.min_gas())
                                .ok_or(DefuseError::GasOverflow)
                                .unwrap_or_else(|err| err.panic()),
                        )
                        .do_ft_withdraw(withdraw.clone()),
                )
        } else {
            Self::do_ft_withdraw(withdraw.clone())
        }
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(Self::FT_RESOLVE_WITHDRAW_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .ft_resolve_withdraw(withdraw.token, owner_id, withdraw.amount.into(), is_call),
        )
        .into())
    }
}

    pub(crate) fn withdraw(
        &mut self,
        owner_id: &AccountIdRef,
        token_amounts: impl IntoIterator<Item = (TokenId, u128)>,
        memo: Option<impl Into<String>>,
        force: bool,
    ) -> Result<()> {
        let owner = self
            .storage
            .accounts
            .get_mut(owner_id)
            .ok_or_else(|| DefuseError::AccountNotFound(owner_id.to_owned()))?
            .get_mut_maybe_forced(force)
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;

        let mut burn_event = MtBurnEvent {
            owner_id: Cow::Owned(owner_id.to_owned()),
            authorized_id: None,
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into).map(Into::into),
        };

        for (token_id, amount) in token_amounts {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            burn_event.token_ids.to_mut().push(token_id.to_string());
            burn_event.amounts.to_mut().push(amount);

            owner
                .token_balances
                .sub(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;

            self.storage
                .state
                .total_supplies
                .sub(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        // Schedule to emit `mt_burn` events only in the end of tx
        // to avoid confusion when `mt_burn` occurs before relevant
        // `mt_transfer` arrives. This can happen due to postponed
        // delta-matching during intents execution.
        if !burn_event.amounts.is_empty() {
            self.runtime.postponed_burns.mt_burn(burn_event);
        }

        Ok(())
    }
