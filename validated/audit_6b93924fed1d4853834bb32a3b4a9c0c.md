### Title
Slowloris-style HTTP request starvation permanently exhausts the FullNode/Solidity/PBFT Wallet HTTP API connection pool - (File: `framework/src/main/java/org/tron/common/application/HttpService.java`)

### Summary
`HttpService`, the base class for every Jetty-backed Wallet HTTP endpoint (`FullNodeHttpService`, `SolidityNodeHttpService`, `FullNodeJsonRpcHttpService`, PBFT variants), starts a plain Jetty `Server` with only a connection-count cap and a body-size cap. It never configures a Jetty `HttpConfiguration`/`minRequestDataRate` or any absolute per-request completion timeout, so — exactly like the Node.js report — the only defense against a stalled request is Jetty's idle timeout, which resets on every single byte received. An attacker who trickles bytes (headers or body) slower than the idle timeout, but never finishes the request, can hold a connection open indefinitely.

### Finding Description
`HttpService.initServer()` does: [1](#0-0) 

This creates `new Server(this.port)`, which internally builds a default `ServerConnector` with Jetty's default per-byte idle timeout and no `HttpConfiguration.setMinRequestDataRate(...)` or explicit total-request timeout. The only mitigations wired in are:
- `ConnectionLimit` bounding the *number* of concurrent TCP connections (`maxHttpConnectNumber`), and
- `SizeLimitHandler` bounding request *body size* (`maxRequestSize`), enforced only once bytes are dispatched.

Neither of these detects or terminates a connection that is technically "active" (never idle) but progressing at an attacker-controlled trickle rate through headers or body — the same gap Node.js's `server.timeout`/`headersTimeout` had before `requestTimeout` was introduced in the referenced CVE-2020-8251 fix. `SizeLimitHandlerTest` and `JettyServerTest` in the repo confirm the only server hardening present is size-limit and connection-limit based, not rate/time based: [2](#0-1) 

Because `ConnectionLimit` is a hard cap (`maxHttpConnectNumber`) rather than a per-IP or time-bounded limit, an attacker who opens that many connections and trickles each one just above the idle-timeout threshold occupies every slot permanently. Every legitimate unprivileged client trying to reach `Wallet` HTTP endpoints (broadcast, deploy, asset issue, order placement, balance/account queries) or `TronJsonRpcImpl`/`JsonRpcServlet` over the same Jetty stack is denied service once the cap is saturated, since new connections are refused at the `ConnectionLimit` bean while the malicious ones never complete or close.

### Impact Explanation
This matches the CWE-400 report's core mechanism: unfinished HTTP/1.1 requests (never-completing headers or bodies) exhaust the server's finite connection capacity, denying service to legitimate broadcasters, contract callers, and JSON-RPC clients — i.e., "an API the node can no longer serve," one of the accepted impact categories. Full/Solidity/PBFT nodes that rely on this HTTP path for transaction submission or chain queries become unreachable for as long as the attacker maintains the slow connections, and the attack is trivially renewable (reopen once the attacker's sockets are eventually reaped).

### Likelihood Explanation
Reachable by any anonymous network client with no signature, permission, or on-chain resource required — a raw TCP client that speaks partial HTTP/1.1 syntax to the node's exposed HTTP ports (`fullNodePort`, `solidityPort`, `pBFTPort`, JSON-RPC ports) is sufficient. The number of sockets needed equals `maxHttpConnectNumber` (or the OS file-descriptor limit if unset), which is a modest, well-known/configurable value, making the attack cheap and repeatable, similar in complexity to the original Node.js Slowloris-class report.

### Recommendation
Configure Jetty's `HttpConfiguration` with `setMinRequestDataRate(...)` (and/or `setIdleTimeout` tuned tighter) on the connector created in `HttpService.initServer()`, so requests must progress at a minimum byte rate rather than merely avoid full idleness. Additionally consider an absolute maximum time-to-complete-request-headers/body independent of idle resets, and/or per-remote-IP connection limits layered on top of the global `ConnectionLimit`, mirroring the Node.js `requestTimeout` fix referenced in the report.

### Proof of Concept
Using the same technique as the Node.js PoC, adapted to any java-tron HTTP endpoint (e.g. FullNode HTTP port 8090):
```javascript
const { createConnection } = require('net')
const client = createConnection({ port: 8090 }, () => {
  client.write('POST /wallet/broadcasttransaction HTTP/1.1\r\n')
  client.write('Content-Type: application/json\r\n')
  client.write('Content-Length: 1000000\r\n')
  client.write('\r\n')
  let i = 0
  const interval = setInterval(() => {
    client.write('a')   // one byte, well under Jetty's idle-timeout window
    if (++i === 1000000) clearInterval(interval)
  }, 20000)
})
```
Repeating this in parallel up to `maxHttpConnectNumber` sockets saturates `ConnectionLimit` (`framework/src/main/java/org/tron/common/application/HttpService.java:83`), after which the Wallet HTTP/JSON-RPC API refuses all further connections until the attacker chooses to release them. [3](#0-2)

    this.apiServer = new Server(this.port);
    int maxHttpConnectNumber = Args.getInstance().getMaxHttpConnectNumber();
    if (maxHttpConnectNumber > 0) {
      this.apiServer.addBean(new ConnectionLimit(maxHttpConnectNumber, this.apiServer));
    }

  }

  protected ServletContextHandler initContextHandler() {
    ServletContextHandler context = new ServletContextHandler(ServletContextHandler.SESSIONS);
    context.setContextPath(this.contextPath);
    SizeLimitHandler sizeLimitHandler = new SizeLimitHandler(this.maxRequestSize, -1);
    sizeLimitHandler.setHandler(context);
    this.apiServer.setHandler(sizeLimitHandler);
    return context;
  }
