### Title
Object pool `Link()` only validates the first `alternates` entry, allowing extra unauthorized alternate object directories to persist undetected - ([File: internal/git/objectpool/link.go])

### Summary
`objectpool.Link()` determines whether a repository is already linked to its object pool by calling `linkedToRepository()`, which reads the repository's `objects/info/alternates` file and compares only `altInfo.ObjectDirectories[0]` against the expected pool path [1](#0-0) . If this single-entry check matches, `Link()` treats the repository as already linked, casts a synchronization vote, and returns without ever writing to or otherwise inspecting the `alternates` file [2](#0-1) . Any additional lines present in the `alternates` file are never read, validated, or rejected. This mirrors the reported bug class: an invariant guard (here, "is this repository correctly and *only* linked to its designated object pool") is enforced by checking only a subset of the state (the first list entry / an implicit "count of one"), rather than performing a full comparison of the entire list, letting an attacker-controlled entry silently persist and be treated as safe.

### Finding Description
The `alternates` mechanism is the isolation boundary between a repository and the object stores it may read from — this is explicitly the isolation model documented for object pools [3](#0-2) . Elsewhere in the same package, `Disconnect()` explicitly guards against multiple alternate entries and treats more than one as an invalid/dangerous state, failing loudly: `len(altInfo.ObjectDirectories) > 1` results in an error [4](#0-3) . `Link()`'s `linkedToRepository()` has no equivalent safeguard: it reads `altInfo.ObjectDirectories` but only ever inspects index `0` [5](#0-4) .

If a repository's `objects/info/alternates` file (e.g., seeded through a repository import/bundle, or through any prior operation that can place file content into the repository directory) contains the expected pool-relative path as its first line and an additional, attacker-chosen path as a subsequent line, then:
1. `linkedToRepository()` returns `true` because line 0 matches.
2. `Link()` short-circuits, casts only a "repository linked" vote, and never rewrites, canonicalizes, or truncates the `alternates` file.
3. The second (malicious) alternate directory entry remains active and is honored by Git for every subsequent object lookup in that repository, indefinitely.

This is functionally identical to the reported bug: a security-relevant list (Safe modules / Gitaly alternates) is checked only partially (first module count and identity vs. full array), so an attacker can smuggle in an extra, unauthorized entry that grants persistent unauthorized access.

### Impact Explanation
An `alternates` entry that is not restricted to the intended object pool directory grants the repository (and thus any RPC that reads objects for it, e.g., `CommitService`, `BlobService`) read access to loose objects and packfiles at an arbitrary path, which the attacker can leverage for cross-repository/cross-tenant object disclosure (reading objects — including potentially sensitive blob content — from other repositories or arbitrary paths that Git can resolve as an object directory). Because the check in `linkedToRepository()` never re-validates or corrects existing extra entries once the first line matches, this represents a durable backdoor: it survives repeated calls to `LinkRepositoryToObjectPool`, and there is no equivalent of `checkAfterExecution`-style enforcement performed anywhere else in the linking path to catch it.

### Likelihood Explanation
Exploitation requires the attacker to control the initial contents of the `alternates` file for a repository before/at the time `Link()`/`linkedToRepository()` is invoked (e.g., via repository import/bundle restoration or replication of a pre-crafted repository, since object-pool linking is triggered as part of fork-related workflows). This requires knowledge of the predictable, deterministic relative pool path computed by `getRelativeObjectPath()` [6](#0-5)  so the first line matches exactly, which is derivable since pool paths are constructed deterministically from repository/pool relative paths. This is a plausible but non-trivial attack chain (dependent on how repository content reaches disk, e.g. through import/replication), rather than a fully unauthenticated one-shot RPC exploit.

### Recommendation
`linkedToRepository()` (and `Link()`) should validate the *entire* `ObjectDirectories` list, not just index `0`:
- Reject (or fail closed) if `len(altInfo.ObjectDirectories) != 1`, mirroring the safeguard already present in `Disconnect()` [4](#0-3) .
- Only treat the repository as "already linked" if the single entry exactly equals the expected relative pool path; any other content (extra lines, unexpected entries) should cause the RPC to fail loudly rather than silently accepting the existing file as-is.
- Consider having `Link()` always rewrite the `alternates` file to the canonical single expected value (via the existing `safe.NewLockingFileWriter` + transactional commit path) rather than skipping the write whenever a partial match is found.

### Proof of Concept
1. Prepare a repository (e.g., via repository import/bundle restore, or by any means that lets attacker-influenced content land in the repository directory) whose `objects/info/alternates` file contains two lines:
   ```
   ../../@pools/xx/yy/<pool-id>.git/objects
   /some/other/repository/objects
   ```
   where the first line is the exact value `getRelativeObjectPath()` would compute for the legitimate pool [6](#0-5) .
2. Trigger `LinkRepositoryToObjectPool` (or any code path invoking `objectpool.Link()`) for that repository/pool pair.
3. Observe that `linkedToRepository()` returns `true` from line-0 comparison [7](#0-6) , so `Link()` only casts a "repository linked" vote and returns without inspecting or correcting the file [8](#0-7) .
4. Confirm the second, malicious alternate entry remains in place and that objects from `/some/other/repository/objects` are now readable through the victim repository (e.g., via `git cat-file` or the Gitaly `CommitService`/`BlobService` against the victim repository).

**Note on scope:** exact reachability details (which higher-level RPC or import path can deposit an attacker-controlled multi-line `alternates` file before `Link()` executes) were not exhaustively traced within the available index; a Devin session with full repository/file access is recommended to confirm the precise external trigger path (e.g., project import, fork-related pool linking) end-to-end.

```go
func getRelativeObjectPath(ctx context.Context, pool, repo *localrepo.Repo) (string, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return "", fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", fmt.Errorf("getting repository path: %w", err)
	}

	relPath, err := filepath.Rel(filepath.Join(repoPath, "objects"), poolPath)
	if err != nil {
		return "", err
	}

	return filepath.Join(relPath, "objects"), nil
}
```

```markdown
# Object Pools

When creating forks of a repository, most of the objects for forked repository
and the repository it forked from are shared. Storing those shared objects
multiple times is a waste of disk space and also of CPU time, given that those
shared objects would have to be repacked for both repositories. To fix this
waste of resources, we use object pools, which are essentially a repository
which holds the shared objects of both repositories.

The sharing of objects for a given repository and its object pool is done via
alternate object directories which Gitaly sets up when linking a repository to
an object pool by writing the `objects/info/alternates` file.
```
