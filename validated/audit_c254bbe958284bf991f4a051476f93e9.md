### Title
Downloaded attachment content is inserted into AtlasDB with no size or hash equality check against the requested `content_hash` - (File: stackslib/src/net/atlas/mod.rs, stackslib/src/net/atlas/download.rs, stackslib/src/net/atlas/db.rs)

### Summary
`GetAttachmentResponse::deserialize` decodes an attacker-controlled hex string from a `GetAttachment` HTTP response into a `Vec<u8>` via `hex_bytes(&hex_encoded)` and wraps it in `Attachment::new(bytes)` with no length bound and no comparison to the requested content hash. The resulting `Attachment` flows through `extend_with_attachments`/`AttachmentsBatchStateMachine` into `AtlasDB::insert_instantiated_attachment`, which stores it unconditionally, unlike the mempool-attachment path which enforces `should_keep_attachment` (contract allow-list + `attachments_max_size`) before insertion.

### Finding Description
`GetAttachmentResponse::deserialize` (stackslib/src/net/atlas/mod.rs:69-77) does:
```rust
let bytes = hex_bytes(&hex_encoded).map_err(de_Error::custom)?;
let attachment = Attachment::new(bytes);
```
No check against `AtlasConfig::attachments_max_size` and no comparison of `attachment.hash()` to the `content_hash` that was actually requested for this batch item.

This response is consumed by `AttachmentsBatchStateContext::extend_with_attachments` (stackslib/src/net/atlas/download.rs:530-559), which does `self.attachments.insert(response.attachment)` for every successfully-decoded response with no validation. Later, in `AttachmentsBatchStateMachine`'s `Done` branch (stackslib/src/net/atlas/download.rs:149-169), every attachment in `context.attachments` is unconditionally passed to `network.atlasdb.insert_instantiated_attachment(&attachment)` (stackslib/src/net/atlas/db.rs:576-591), which performs a raw `INSERT OR REPLACE INTO attachments (hash, content, ...)` with no size guard.

Contrast this with `AtlasDB::should_keep_attachment` (stackslib/src/net/atlas/db.rs:249-266), which does enforce `attachment.content.len() as u32 > self.atlas_config.attachments_max_size` — but that gate is only used on the locally-submitted mempool-attachment path (`posttransaction.rs`), not on attachments fetched from a remote peer via `GetAttachment`.

The only place hashes are checked is `attachment.hash()` being used as a lookup/resolve key (e.g., `context.attachments_batch.resolve_attachment(&attachment.hash())`), which is a self-referential hash of the attacker's own bytes, not a comparison against the `content_hash` that was actually requested from the batch (`AttachmentInstance::content_hash`). So a peer can return content unrelated to what was requested, or grossly oversized content, and it still gets inserted into `AtlasDB` as an "instantiated" attachment as long as decoding succeeds.

### Impact Explanation
A remote, unprivileged peer serving `GetAttachment` responses (or any HTTP relay position for that RPC call during attachment sync) can cause a node's `AtlasDB` to store arbitrarily large, no-canonical-commitment-matching blobs under the `attachments` table, bypassing the `attachments_max_size` cap that is meant to bound storage. This is attachment/BNS-data storage that no on-chain name commit corresponds to, matching the "High — attachment/BNS mismatch" impact category. It is repeatable per attachment-batch download from any peer the node queries for attachments.

### Likelihood Explanation
The only precondition is that the victim node performs Atlas attachment sync and queries the attacker's node (or a node under attacker's control, or a MITM-able HTTP path) for a `GetAttachment` response as part of resolving a batch of `AttachmentInstance`s recorded from chain state. No secret, no privileged role, and no special peer relationship beyond being a normal reachable Atlas peer is required. The attacker fully controls the JSON body of the HTTP response.

### Recommendation
In `GetAttachmentResponse::deserialize` or immediately after decoding in `extend_with_attachments`/`AttachmentsBatchStateMachine`, reject/drop attachments whose `attachment.content.len()` exceeds `AtlasConfig::attachments_max_size`, and verify `attachment.hash() == requested_content_hash` for the specific `AttachmentRequest` before calling `insert_instantiated_attachment`. Apply the same `should_keep_attachment`-style gate used for locally-posted attachments to attachments received from peers.

### Proof of Concept
Rust net test: construct a fake `GetAttachment` JSON response body whose hex payload decodes to a `Vec<u8>` larger than `AtlasConfig::attachments_max_size` (e.g., `atlas_config.attachments_max_size + 1` bytes), feed it through `StacksHttpResponse::decode_atlas_get_attachment` / `GetAttachmentResponse::deserialize`, then run it through `AttachmentsBatchStateContext::extend_with_attachments` and `AttachmentsBatchStateMachine`'s completion path into `AtlasDB::insert_instantiated_attachment`. Assert that `atlas_db.find_attachment(&oversized_attachment.hash())` returns `Some` afterward (i.e., no rejection occurred), and separately assert that `oversized_attachment.hash() != requested_content_hash` for a crafted mismatched-content case, showing storage occurs despite the hash mismatch.     pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
}

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }
