### Title
Unsynchronized map iteration in `ConcurrencyLimiter`'s adaptive-resize hook causes concurrent map read/write crash - (File: internal/limiter/concurrency_limiter.go)

### Summary
`NewConcurrencyLimiter()` registers an `AfterUpdate` hook on the shared `AdaptiveLimit` that iterates over `ConcurrencyLimiter.limitsByKey` to resize each keyed semaphore whenever the adaptive limit changes. This iteration happens without holding `ConcurrencyLimiter.m`, the very mutex that guards all other reads/writes of `limitsByKey` (`getConcurrencyLimit`/`putConcurrencyLimit`). Ordinary user RPC traffic (e.g. `PostUploadPackWithSidechannel`, `PackObjectsHookWithSidechannel`) concurrently mutates that map while the background `AdaptiveCalculator` goroutine periodically calls `AdaptiveLimit.Update()`, which invokes the unsynchronized hook. This is the direct structural analog of the Fenix `killGauge()` bug: a bookkeeping structure (`weightsPerEpoch`/`totalWeightsPerEpoch` there, `limitsByKey` here) is updated in one code path under one discipline (mutex-protected map ops in `getConcurrencyLimit`/`putConcurrencyLimit`) while a second code path (the resize hook, analogous to `distribute()`'s use of stale weight data) touches the same structure under a different discipline, producing an inconsistent/corrupted view of the accounting state — here manifesting as a Go runtime "concurrent map read and map write" fatal crash instead of a numeric misallocation.

### Finding Description
`internal/limiter/concurrency_limiter.go`:
- `ConcurrencyLimiter.limitsByKey` is a `map[string]*keyedConcurrencyLimiter` guarded by `ConcurrencyLimiter.m sync.RWMutex`. [1](#0-0) 
- `getConcurrencyLimit()` and `putConcurrencyLimit()` correctly lock `c.m` before reading/writing/deleting entries in `limitsByKey`. [2](#0-1) 
- However, in `NewConcurrencyLimiter()`, the hook registered via `limit.AfterUpdate(...)` ranges directly over `limiter.limitsByKey` with no lock at all: [3](#0-2) 
- `AdaptiveLimit.Update()` invokes all registered hooks synchronously while holding only the `AdaptiveLimit`'s own internal mutex — not `ConcurrencyLimiter.m`: [4](#0-3) 
- `Update()` is called periodically by the background `AdaptiveCalculator.calibrateLimits()` goroutine (default every 30s, or on backoff events), completely independent of and concurrent with in-flight RPCs: [5](#0-4) 
- `limitsByKey` is populated/evicted on every RPC subject to a keyed, adaptive concurrency limit — reachable by ordinary/unauthenticated clients, e.g. via the pack-objects concurrency limiter keyed by RemoteIP/Repository/User, or per-RPC-per-repository limits: [6](#0-5) [7](#0-6) 

Because Go maps are not safe for concurrent read/write, if the calibration goroutine's hook iterates `limitsByKey` (a read) at the same moment an RPC goroutine inserts a new key on cache-miss or deletes a key whose refcount reaches zero in `putConcurrencyLimit()` (a write), the Go runtime detects the race and calls `fatal error: concurrent map read and map write`, which is unrecoverable and terminates the entire `gitaly` process.

### Impact Explanation
This is a full-process denial of service reachable by any client capable of generating concurrent traffic against RPCs guarded by an adaptive, keyed concurrency limiter (this feature is documented and configurable, e.g., `[[concurrency]] adaptive = true` or the built-in pack-objects limiter). No privileged access, malicious peer, or token leak is required — normal, high-concurrency fetch/clone/push traffic from ordinary users is sufficient to trigger key churn in `limitsByKey` at the same time the adaptive calculator recalibrates the limit (which happens automatically and periodically once any adaptive limit is configured). A crash of the Gitaly process affects all repositories and all users served by that node, making this a high-severity, unprivileged DoS of an RPC-handler resource-limiting subsystem — squarely within the accepted category "DoS of a handler" via resource-limit bookkeeping corruption, directly analogous to how `killGauge()`'s inconsistent bookkeeping corrupted the Voter's emission distribution.

### Likelihood Explanation
Likelihood is high whenever adaptive concurrency limiting is enabled (it is a first-class configuration option and increasingly the default direction per `doc/load-management-architecture.md`), since:
1. `limitsByKey` entries churn continuously under real traffic — every unique key gets inserted on first request and deleted when its refcount returns to zero.
2. `AdaptiveCalculator` runs an unconditional background timer (`DefaultCalibrateFrequency = 30s`) that calls `Update()` → hook → unguarded map iteration, regardless of whether any RPC calls are actually resizing.
3. Any RPC traffic pattern generating multiple distinct limiting keys (distinct repositories, distinct remote IPs/users for pack-objects) increases the chance of a concurrent insert/delete colliding with a calibration tick.

The bug is not timing-sensitive to exploit deliberately — it is a genuine data race that will eventually be caught by Go's race detector or crash in production under sustained load, similar to how the emission accounting bug in Fenix manifests deterministically once a gauge is killed with an in-flight distribution.

### Recommendation
Have the `AfterUpdate` resize hook acquire `ConcurrencyLimiter.m` (a read lock is sufficient, since it doesn't add/remove keys, only mutates `*keyedConcurrencyLimiter` fields reached via pointers already in the map) before iterating `limitsByKey`:

```go
limit.AfterUpdate(func(val int) {
    limiter.m.RLock()
    defer limiter.m.RUnlock()
    for _, keyedLimiter := range limiter.limitsByKey {
        if keyedLimiter.queueTokens != nil {
            if semaphore, ok := keyedLimiter.queueTokens.(*resizableSemaphore); ok {
                semaphore.Resize(uint(val + limiter.maxQueueLength))
            }
        }
        if semaphore, ok := keyedLimiter.concurrencyTokens.(*resizableSemaphore); ok {
            semaphore.Resize(uint(val))
        }
    }
})
```
Additionally, run the race detector (`go test -race`) against `internal/limiter` with concurrent `Limit()` calls interleaved with `AdaptiveLimit.Update()` to add regression coverage, mirroring how the Fenix fix required auditing `killGauge()` against Minter's emission-calculation assumptions.

### Proof of Concept
Conceptual reproduction (requires `go test -race`):
1. Configure an adaptive concurrency limit (`concurrency.Adaptive = true`) for an RPC such as `PostUploadPackWithSidechannel`, and start `AdaptiveCalculator` with a short calibration interval.
2. Drive many concurrent RPCs against distinct `limitingKey`s (e.g., distinct repositories) so that `getConcurrencyLimit`/`putConcurrencyLimit` continuously insert/delete entries in `limitsByKey`.
3. Concurrently, let the `AdaptiveCalculator`'s timer fire (or call `AdaptiveLimit.Update()` directly), invoking the registered hook which ranges over `limitsByKey` without `c.m` held.
4. Under `-race`, Go reports a data race on the map; under normal `go build` conditions with sufficient concurrency, the runtime can hit `fatal error: concurrent map read and map write`, crashing the process. This can be confirmed by inspecting `internal/limiter/concurrency_limiter.go` lines 171-184 (unguarded iteration) versus lines 245-292 (guarded map access), and `internal/limiter/adaptive_limit.go` lines 66-77 (hook invocation) alongside `internal/limiter/adaptive_calculator.go` lines 248-289 (periodic, independent trigger).

func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}

// putConcurrencyLimit drops the reference to the concurrency limit identified by the given key.
// This must only ever be called after `getConcurrencyLimit()` for the same key. If the reference
// count of the concurrency limit drops to zero then it will be destroyed.
func (c *ConcurrencyLimiter) putConcurrencyLimit(limitingKey string) {
	c.m.Lock()
	defer c.m.Unlock()

	ref := c.limitsByKey[limitingKey]
	if ref == nil {
		panic("semaphore should be in the map")
	}

	if ref.refcount <= 0 {
		panic(fmt.Sprintf("bad semaphore ref refcount %d", ref.refcount))
	}

	ref.refcount--
	if ref.refcount == 0 {
		delete(c.limitsByKey, limitingKey)
	}
}

// Update adjusts the current limit value and executes all registered update hooks.
func (l *AdaptiveLimit) Update(val int) {
	l.Lock()
	defer l.Unlock()

	if val != l.current {
		l.current = val
		for _, hook := range l.updateHooks {
			hook(val)
		}
	}
}

// UnaryInterceptor returns a Unary Interceptor
func (c *LimiterMiddleware) UnaryInterceptor() grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
		lockKey := c.getLockKey(ctx)
		if lockKey == "" {
			return handler(ctx, req)
		}

		// Check if request is authenticated
		limiter := c.methodLimiters[info.FullMethod]
		unauthLimiter, ok := c.methodLimitersUnauthenticated[info.FullMethod]
		if !auth.IsAuthenticated(ctx) && ok {
			limiter = unauthLimiter
		}

		if limiter == nil {
			// No concurrency limiting
			return handler(ctx, req)
		}

		return limiter.Limit(ctx, lockKey, func() (interface{}, error) {
			return handler(ctx, req)
		})
	}
}
