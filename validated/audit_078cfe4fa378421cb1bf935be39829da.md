### Title
Peer-inventory ack claims chunk storage before it is actually written, letting a node advertise data it may never persist - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches and sends a `StackerDBChunkInv` acknowledgment claiming the new slot version is now stored *before* the chunk has actually been written to the StackerDB. The real write only happens later, in the relayer's `process_stacker_db_chunks` (`stackslib/src/net/relay.rs`), via `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs`). This breaks the equality between "served inventory" and "actually stored chunk."

### Finding Description
In `handle_unsolicited_StackerDBPushChunk`: [1](#0-0) 
the function calls `validate_received_chunk` (signature + version + size checks only, no DB write), then directly mutates the outgoing `StackerDBChunkInv` payload's `slot_versions` entry to the new version: [2](#0-1) 
It then wakes the sync state machine and, further down, signs and sends this inventory reply to the remote peer: [3](#0-2) 
The function returns `(false, true)`, meaning "forward to relayer" — i.e., the actual persistence via `try_replace_chunk` happens asynchronously afterward in `Relayer::process_stacker_db_chunks`: [4](#0-3) 
`try_replace_chunk` re-validates chunk size, slot signer, staleness, and max-writes against the current DB state: [5](#0-4) 
Because the inventory ack in `handle_unsolicited_StackerDBPushChunk` is generated and sent *before* this second, independent validation/write occurs, there is a window where the local node has told a peer "I have version N of slot S" while the DB transaction to actually store it hasn't run yet (or could still fail, e.g. if a concurrent write from another origin bumps `slot_validation.version` past N first, causing `StaleChunk`, or another race causes `try_replace_chunk` to error and `continue` without storing). In that failure branch, the chunk is dropped silently and never stored, yet the inventory acknowledgment already told the peer that version N was received.

### Impact Explanation
Downstream peers using inventory data (via `StackerDBChunksInv`) to decide what to fetch/rebroadcast may believe a slot is at version N and skip re-requesting it, while the local replica never actually committed that version. This can cause a legitimately fresher chunk to be dropped from the mesh's effective state, a "served vs. stored" mismatch that maps to the "non-canonical state served as canonical" impact category. However, in the common single-writer-per-slot path there is typically only one push at a time, so an attacker's ability to force a losing race deterministically is limited to a narrow concurrency window (e.g., simultaneous chunk pushes/syncs racing on the same slot), not a guaranteed reproducible corruption.

### Likelihood Explanation
Triggering the race requires an attacker (or two independent legitimate senders) to submit two different chunk versions for the same slot in close succession so the second `try_replace_chunk` call observes a stale `slot_validation.version` after the ack for the first has already been sent, or for the relayer path to otherwise fail post-ack. This is a narrow, timing-dependent condition, not a simple, deterministic single-request exploit, so likelihood is low-to-moderate and largely benign in effect (self-healing once the sync state machine retries).

### Recommendation
Move the inventory-version patch (line 807) to occur only after `try_replace_chunk` has succeeded in the relayer, or restructure so the ack sent back to the peer reflects a version the node has confirmed committed to disk, not merely validated in isolation from the store step.

### Proof of Concept
Not independently reproducible from static analysis alone: a full PoC would require driving a race between two chunk-push events on the same slot (e.g. via `handle_unsolicited_StackerDBPushChunk` invoked twice from different event IDs with different valid versions) such that the second's `try_replace_chunk` call in `process_stacker_db_chunks` observes a version conflict, while the earlier-sent `StackerDBChunkInv` ack already advertised its slot version as current. This dynamic timing behavior could not be exercised through static code reading alone within the available tooling.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
