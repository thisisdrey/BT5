### Title
`get_chunks` omits the chunk-size validation present in `get_latest_chunks`, and `run_http_request` buffers unbounded HTTP responses before any size check runs - ([File: libsigner/src/session.rs])

### Summary
`StackerDBSession::get_chunks` (session.rs:200-227) pushes the raw `body_bytes` returned by `rpc_request` into `payloads` with no size check, unlike `get_latest_chunks` (session.rs:230-262) which discards any body exceeding `SIGNERS_STACKERDB_CHUNK_SIZE`/`STACKERDB_MAX_CHUNK_SIZE`. Both paths, however, already read the entire HTTP response into memory via `run_http_request`'s `sock.read_to_end(&mut buf)` (http.rs:249-251) before either check can run, so the size validation in `get_latest_chunks` cannot actually bound memory usage - it only filters the value after the unbounded allocation has already happened.

### Finding Description
The claimed equality — "bytes accepted as a chunk == bytes within the validated `STACKERDB_MAX_CHUNK_SIZE` bound" — is broken in two related ways, but the root cause is in `run_http_request`, not the presence/absence of the post-hoc check in `get_chunks` vs `get_latest_chunks`:

1. `run_http_request` (libsigner/src/http.rs:221-262) calls `sock.read_to_end(&mut buf)` with no cap on `buf`'s size, prior to any header parsing or body-size validation. A malicious or MITM'd server response of arbitrary size will be fully buffered in memory regardless of which downstream function (`get_chunks` or `get_latest_chunks`) called it.
2. `get_chunks` (session.rs:200-227) never checks `body_bytes.len()` at all, so an oversized payload is stored in `payloads` and can flow onward (e.g., via `get_chunk` → `get_latest::<T>::consensus_deserialize`, session.rs:56-95) with no bound. `get_latest_chunks` at least filters after the fact (session.rs:243-247), converting an oversized body to `None`, but this occurs only after the full buffer has already been allocated and copied by `run_http_request`/`decode_http_body`.

So even the "protected" path (`get_latest_chunks`) does not defend against the unbounded-allocation aspect of the finding; it only prevents an oversized chunk from being handed to a caller/deserializer. The unbounded allocation itself is not defended against on either path.

### Impact Explanation
`StackerDBSession` is client-side code used by the signer binary (`stacks-signer`) to fetch StackerDB chunks from a Stacks node over plaintext TCP/HTTP. A malicious node operator whose RPC endpoint the signer is configured to query (or a MITM on that plaintext connection) can respond to a `GET` chunk request with an HTTP body far larger than `STACKERDB_MAX_CHUNK_SIZE`. This forces the signer process to allocate memory proportional to the attacker-chosen response size in `run_http_request`, independent of the `get_chunks`/`get_latest_chunks` distinction. Repeated requests (the signer polls StackerDB continuously) allow repeated unbounded allocations, which can degrade or crash the signer process (memory-exhaustion DoS) — this matches the Critical "remote crash/unauthenticated DoS from few messages" category only insofar as the signer's operator has configured it to talk to (or is MITM'd talking to) that specific host; it is not a P2P/RPC-server-side vulnerability reachable by an arbitrary unprivileged network peer against a listening node.

### Likelihood Explanation
This requires the signer to be configured to query a specific node host (`StackerDBSession::host`) that is attacker-controlled, or an active MITM on that specific plaintext TCP connection (the code indeed uses plain `TcpStream::connect` with no TLS, per session.rs:129). This is a real precondition narrower than "any unprivileged remote party who can connect to a node's P2P or RPC port," since it is the signer acting as a client reaching out to a node the operator chose, not an attacker reaching into a listening service. It is not a volumetric/bandwidth-flood scenario — one crafted oversized HTTP body per request triggers the allocation — but it does depend on the signer's own configuration pointing at, or being intercepted en route to, a malicious/compromised host.

### Recommendation
Bound the response size in `run_http_request` before or during `read_to_end` (e.g., use a length-limited reader, honor `Content-Length` against a max, or read in a loop with a running cap and abort once exceeded), rather than relying on post-hoc `len()` checks in `get_chunks`/`get_latest_chunks`. Additionally, add the missing size check to `get_chunks` for defense-in-depth/consistency with `get_latest_chunks`.

### Proof of Concept
Rust test: spin up a `TcpListener`, accept a connection, respond with `HTTP/1.1 200 OK\r\nContent-Length: <N>\r\n\r\n` followed by `N` bytes where `N >> STACKERDB_MAX_CHUNK_SIZE` (e.g., hundreds of MB), call `StackerDBSession::get_chunks(&[(0,0)])` against that listener, and observe/assert that `run_http_request`'s `buf` grows to `N` bytes (e.g., via process RSS measurement or by using a very large `N` to demonstrate practical memory pressure) — while `get_latest_chunks` under the same conditions returns `None` for the oversized chunk, it too has already fully buffered the oversized body in `run_http_request`, showing the allocation is not prevented by either function's per-item size check.
