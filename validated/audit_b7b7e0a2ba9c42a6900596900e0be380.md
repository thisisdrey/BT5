Audit Report

## Title
Stranded funds in closed child-bounty accounts have no reclaim path - (File: `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`pallet-child-bounties` derives a per-child-bounty sub-account via `child_bounty_account_id` that holds the child bounty's escrowed value during its lifecycle, but unlike `pallet-bounties` (which was fixed via `reclaim_bounty_funds` in `substrate/frame/bounties/src/lib.rs` L1048-1090, per `prdoc/pr_11045.prdoc`), no dispatchable in `pallet-child-bounties` exists to sweep residual balance from that account once the corresponding `ChildBounties` storage entry is removed via `close_child_bounty`/`claim_child_bounty`. Any tokens sent to a child bounty's derived account after closure are permanently stranded with no recovery path.

## Finding Description
`pallet-child-bounties` exposes the lifecycle calls `add_child_bounty`, `propose_curator`, `accept_curator`, `award_child_bounty`, `claim_child_bounty`, `unassign_curator`, and `close_child_bounty` [1](#0-0) , which mirror the same lifecycle pattern used by `pallet-bounties`. `claim_child_bounty` and `award_child_bounty` mutate/remove the `ChildBounties` entry via `try_mutate_exists` [2](#0-1) , and once the entry is gone the derived sub-account (`child_bounty_account_id`) is no longer referenced by any call in the pallet — a grep across the file confirms the only matches for `child_bounty_account_id` are in the fund-transfer logic, tests, and migration, not in any permissionless sweep function. `pallet-bounties`, by contrast, had this exact defect and fixed it with `reclaim_bounty_funds`, gated on `!Bounties::<T, I>::contains_key(bounty_id)` [3](#0-2) , which force-transfers all remaining native/asset balance from `Self::bounty_account_id(bounty_id)` to the treasury [4](#0-3) . The `reclaim_bounty_funds_works_after_accidental_refund` test demonstrates the exact precondition (accidental transfer to a closed bounty account) that this fix addresses [5](#0-4) . `pallet-child-bounties` has no analogous `!ChildBounties::<T>::contains_key(...)`-gated sweep extrinsic.

## Impact Explanation
Funds sent to a closed child bounty's derived account (accidental transfers, dust, delayed settlement) become permanently unrecoverable — no call in the pallet references the account once its storage key is removed. This matches the "permanent user-fund lock" impact class.

## Likelihood Explanation
Reaching the precondition requires only ordinary, unprivileged actions: complete a child bounty's lifecycle (`claim_child_bounty` or `close_child_bounty`) and then transfer funds to the deterministically-derivable `child_bounty_account_id`. No privileged access or governance action is needed to create the stranded state, though recovering the funds is impossible for anyone, including governance, since no extrinsic references the closed account.

## Recommendation
Add a permissionless `reclaim_child_bounty_funds` extrinsic to `pallet-child-bounties`, gated on `!ChildBounties::<T>::contains_key(parent_bounty_id, child_bounty_id)`, that transfers residual native/asset balance from `Self::child_bounty_account_id(parent_bounty_id, child_bounty_id)` back to the parent bounty account or treasury, mirroring `pallet-bounties::reclaim_bounty_funds`.

## Proof of Concept
1. Create a parent bounty and add a child bounty via `add_child_bounty`, funding it from the parent bounty account.
2. Progress the child bounty through `propose_curator` → `accept_curator` → `award_child_bounty` → `claim_child_bounty`, which removes the `ChildBounties` entry for `(parent_bounty_id, child_bounty_id)`.
3. Transfer native tokens directly to `ChildBounties::child_bounty_account_id(parent_bounty_id, child_bounty_id)`.
4. Observe no extant call in `pallet-child-bounties` references this account any longer, reproducing the scenario covered for `pallet-bounties` by `reclaim_bounty_funds_works_after_accidental_refund`, but without an equivalent fix present for child bounties.

#[test]
fn reclaim_bounty_funds_works_after_accidental_refund() {
	ExtBuilder::default().build_and_execute(|| {
		Balances::make_free_balance_be(&Treasury::account_id(), 101);

		// Full lifecycle: propose → approve → fund → curator → award → claim
		assert_ok!(Bounties::propose_bounty(RuntimeOrigin::signed(0), 50, b"12345".to_vec()));
		assert_ok!(Bounties::approve_bounty(RuntimeOrigin::root(), 0));
		go_to_block(2);

		let fee = 4;
		Balances::make_free_balance_be(&4, 10);
		assert_ok!(Bounties::propose_curator(RuntimeOrigin::root(), 0, 4, fee));
		assert_ok!(Bounties::accept_curator(RuntimeOrigin::signed(4), 0));
		assert_ok!(Bounties::award_bounty(RuntimeOrigin::signed(4), 0, 3));
		go_to_block(5);
		assert_ok!(Bounties::claim_bounty(RuntimeOrigin::signed(1), 0));

		// Bounty is now fully closed; verify it is gone from storage.
		assert!(pallet_bounties::Bounties::<Test>::get(0).is_none());

		let bounty_account = Bounties::bounty_account_id(0);
		// Account should already be empty after claim.
		assert_eq!(Balances::free_balance(&bounty_account), 0);

		// Simulate someone accidentally sending funds to the closed bounty account.
		Balances::make_free_balance_be(&bounty_account, 25);
		assert_eq!(Balances::free_balance(&bounty_account), 25);

		let treasury_before = Treasury::pot();

		// Dust the account.
		assert_ok!(Bounties::reclaim_bounty_funds(RuntimeOrigin::signed(99), 0));
		assert_eq!(last_event(), BountiesEvent::BountyFundsReclaimed { bounty_id: 0 },);

		assert_eq!(Balances::free_balance(&bounty_account), 0);
		assert!(Treasury::pot() > treasury_before);
	});
}
