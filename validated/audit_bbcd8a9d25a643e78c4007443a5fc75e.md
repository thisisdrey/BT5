### Title
Stale-storage cache poisoning race in `CachingConsistentStoragesGetter` from concurrent write notification and read-through population - ([File: internal/praefect/datastore/storage_provider.go])

### Summary
`CachingConsistentStoragesGetter` caches the set of "up to date" storages for a repository, keyed by `relativePath`, and invalidates entries only reactively via Postgres `NOTIFY` payloads delivered to `Notified()`. There is no locking between the invalidation path (`Notified`) and the read-through population path (`GetConsistentStorages` miss → DB query → `cache.Add`). This mirrors the fee-vault bug class: a value fetched from the true source-of-truth (the DB) can become stale by the time it is written into the cache, because an intervening state-changing event (a write notification) races the read used to populate the cache, and the "escape" logic (cache-hit skip) then serves the wrong, unrefreshed value for an indefinite period.

### Finding Description
The cache is populated like this in `GetConsistentStorages`: [1](#0-0) 

and invalidated like this in `Notified`, which is called asynchronously off of Postgres `LISTEN/NOTIFY` when a write updates the set of up-to-date storages for a `relativePath`: [2](#0-1) 

The `syncer.await` mechanism only serializes concurrent *populate* attempts for the same key against each other; it provides no ordering guarantee with respect to `Notified()`: [3](#0-2) 

This produces the following race, structurally identical to the fee-vault's "escape condition uses a stale rate" bug:

1. A read RPC misses the cache for `relativePath` and calls `c.csg.GetConsistentStorages(ctx, ...)`, reading the pre-write set of consistent storages from Postgres.
2. Concurrently, an ordinary user pushes to the same repository. The write completes on the DB side and Postgres emits a `NOTIFY` reflecting the new (post-write) consistent-storages state for `relativePath`.
3. Praefect's listener delivers this notification to `Notified()`, which calls `cache.replicaInfoCache.Remove(relativePath)` — but the entry does not exist yet (it hasn't been added).
4. The reader from step 1 now executes `cache.replicaInfoCache.Add(relativePath, cachedReplicaInfo{...})`, inserting the **stale** pre-write result *after* the invalidation for the write it raced against.

Because no further write happens to trigger another `NOTIFY`/`Remove` for that `relativePath`, this stale entry remains a permanent cache hit (`c.cacheAccessTotal...hit`) for all subsequent reads until the repository is written again. This is directly analogous to the fee-vault issuing a stale `b_rate` because an intervening default (state change) landed inside the "escape window" of the cache's staleness check.

### Impact Explanation
`GetConsistentStorages` is used by Praefect's read-distribution logic to decide which physical storage node is authoritative/up to date for serving a request on behalf of a virtual storage. If the cache is poisoned with a stale, pre-write "up to date storages" set:
- Reads can be routed to a node that is not actually up to date, silently serving stale repository data to clients (accessor RPCs going through Praefect), which is a consistency violation caused entirely by an ordinary user's push racing an ordinary concurrent read — no privileged access required.
- Because the poisoned entry survives indefinitely (until a further write on that same `relativePath` triggers another notification), the incorrect routing decision persists, rather than self-healing.

This does not directly cause data loss but does cause the same class of harm as the referenced report: consumption of authoritative state that is inconsistent with the true source of truth due to a race around a "skip-refresh" cache path, leading to incorrect behavior that is silent and durable.

### Likelihood Explanation
The race window is narrow (between the DB SELECT in `csg.GetConsistentStorages` and the subsequent `cache.Add`), but it is triggerable by any ordinary user simply by pushing to a repository at the same moment another client happens to read it — a common occurrence on busy repositories under Gitaly Cluster/Praefect. No special privileges, malicious peers, or MITM are required; it's purely a timing race between two otherwise-legitimate operations (push + concurrent read), consistent with the "ordinary user's push" reachability criterion.

### Recommendation
Close the window by either:
- Recording a monotonically increasing generation/version alongside each notification and only allowing `Add` to insert an entry if it is not older than the last known invalidation generation for that key (compare-and-swap style versioning), or
- Re-checking for a pending/received invalidation for the key immediately after populating and before/after `Add` (i.e., treat `Notified` and `Add` as needing to be serialized per key using the existing `syncer`, so a notification arriving during a populate is applied after the populate completes rather than being effectively lost), or
- Adding a short TTL to cache entries so a lost invalidation cannot pin a stale entry indefinitely.

### Proof of Concept
1. Start Praefect with `CachingConsistentStoragesGetter` enabled (`Connected()` called) for a virtual storage `vs` and repository at `relativePath`.
2. Goroutine A: call `GetConsistentStorages(ctx, "vs", relativePath)`; pause execution (e.g. via a test hook / `-race` timing) right after `c.csg.GetConsistentStorages` returns the pre-write result but before `cache.replicaInfoCache.Add` executes.
3. Goroutine B: perform a write to the repository that changes its "up to date storages" set, causing the DB to emit a `NOTIFY`; deliver this to `c.Notified(...)` synchronously — this calls `cache.replicaInfoCache.Remove(relativePath)` on an as-yet-absent key (no-op).
4. Resume Goroutine A: `cache.replicaInfoCache.Add(relativePath, staleInfo)` inserts the pre-write result.
5. Subsequent calls to `GetConsistentStorages(ctx, "vs", relativePath)` return the stale `staleInfo` as cache hits indefinitely (see hit counter in `cacheAccessTotal`), demonstrating the same pattern the tests in `storage_provider_test.go` exercise for the "hit" path but here with content pre-dating a completed write. // Notified handles notifications by invalidating cache entries of updated repositories.
func (c *CachingConsistentStoragesGetter) Notified(n glsql.Notification) {
	var changes []notificationEntry
	if err := json.NewDecoder(strings.NewReader(n.Payload)).Decode(&changes); err != nil {
		c.disableCaching() // as we can't update cache properly we should disable it
		c.callbackLogger.WithError(err).WithField("channel", n.Channel).Error("received payload can't be processed, cache disabled")
		return
	}

	for _, entry := range changes {
		cache, found := c.caches[entry.VirtualStorage]
		if !found {
			c.callbackLogger.WithError(errNotExistingVirtualStorage).WithField("virtual_storage", entry.VirtualStorage).Error("cache not found")
			continue
		}

		for _, relativePath := range entry.RelativePaths {
			cache.replicaInfoCache.Remove(relativePath)
		}
	}
}

// await acquires lock for provided key and returns a callback to invoke once the key could be released.
// If key is already acquired the call will be blocked until callback for that key won't be called.
func (sc *syncer) await(key string) func() {
	sc.mtx.Lock()

	if cond, found := sc.inflight[key]; found {
		sc.mtx.Unlock()

		<-cond // the key is acquired, wait until it is released

		return func() {}
	}

	defer sc.mtx.Unlock()

	cond := make(chan struct{})
	sc.inflight[key] = cond

	return func() {
		sc.mtx.Lock()
		defer sc.mtx.Unlock()

		delete(sc.inflight, key)

		close(cond)
	}
}
