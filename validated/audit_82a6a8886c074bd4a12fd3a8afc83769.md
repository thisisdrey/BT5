### Title
Unbounded contract-type index into fixed 32-byte permission `operations` bitmap causes uncaught `ArrayIndexOutOfBoundsException` during transaction signature validation - (File: `chainbase/src/main/java/org/tron/common/utils/WalletUtil.java`)

### Summary
`WalletUtil.checkPermissionOperations` (duplicated in `actuator/src/main/java/org/tron/core/utils/TransactionUtil.java`) uses the raw, unvalidated `contract.getTypeValue()` as a bit index into a fixed 32-byte (256-bit) `operations` `ByteString` without checking that the value is in range `[0,255]` (or non-negative). This mirrors the CVE-2025-38568 bug class: a boundary value accepted by upstream validation (or, here, no boundary validation at all) is used directly as an index into a fixed-size buffer.

### Finding Description
`checkPermissionOperations` computes:
```java
int contractType = contract.getTypeValue();
boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
``` [1](#0-0) 

`operations` is enforced to be exactly 32 bytes just above this line, but `contractType` (`contract.getTypeValue()`) is never range-checked. In protobuf3, a singular (non-repeated) enum field preserves out-of-range values as the raw underlying int — `getType()` would return `UNRECOGNIZED` but `getTypeValue()` still returns the attacker-supplied integer (which can be negative or far larger than the ~50 known `ContractType` values). A transaction's `Contract.type` field is exactly such a field, and an unprivileged transaction broadcaster fully controls the raw serialized transaction bytes, including this enum's wire value.

If `contractType` is, e.g., `100000`, `contractType / 8` is far beyond the 32-byte `operations` buffer, and `ByteString.byteAt` throws an unchecked `IndexOutOfBoundsException`. If `contractType` is negative (also representable in the wire format), the division/modulo can also produce out-of-range or negative indices.

This check is reached on the transaction signature-validation path whenever `permissionId != 0` (i.e., any multi-sig/active-permission transaction), via:
- `TransactionCapsule.checkPermission` → `checkPermissionOperations` [2](#0-1) 
- called from `TransactionCapsule.validateSignature(Transaction, ...)` (static overload) [3](#0-2) 
- called from `validatePubSignature`, whose try/catch only handles `SignatureException | PermissionException | SignatureFormatException` — **not** the unchecked `IndexOutOfBoundsException** that `checkPermissionOperations` can throw [4](#0-3) 

Identical unguarded logic exists in `actuator/src/main/java/org/tron/core/utils/TransactionUtil.java`: [5](#0-4) 

Some call sites do wrap the whole operation with a broad `catch (Exception ex)` (e.g. `Wallet.getTransactionSignWeight`, `Wallet.getTransactionApprovedList`), which would absorb the exception there. [6](#0-5) [7](#0-6) 

However, the core signature-validation path (`validatePubSignature`/`validateSignature`) does **not** catch generic `RuntimeException`, so an unchecked exception thrown here during normal transaction broadcast/pushTransaction/block-application flows is not guaranteed to be caught before it reaches block-processing code in `Manager`. I was unable to fully trace every downstream caller of `TransactionCapsule.validateSignature`/`validatePubSignature` inside `Manager.java` (e.g., in the block-application/`pushTransaction`/`ValidateSignTask` code paths) within the available context to confirm whether a broader catch-all exists there that would downgrade this to a rejected transaction rather than a crashed thread or halted node — this needs verification with a full read of `Manager.java`'s transaction-processing and block-application methods.

### Impact Explanation
If the unchecked exception is not caught somewhere up the call stack (which is uncertain per the note above), an attacker could:
- Cause an uncontrolled exception during transaction signature validation for a broadcast transaction, potentially disrupting the node's transaction-processing pipeline (a resource/availability issue), or
- In the worst case, if the exception surfaces uncaught inside block application in `Manager`, it could crash the validation thread or halt processing of transactions, which would be a High severity finding per the given rules ("node crash or halt").

Because I could not fully confirm the innermost call chain into `Manager.java`'s block-application code in the remaining context, the severity should be treated as **potential High** pending confirmation, but at minimum this is a Medium-severity input-validation bug: an unprivileged transaction broadcaster can trigger an unhandled runtime exception in core permission-checking logic by supplying an out-of-range `Contract.type` value together with a non-zero `permissionId`.

### Likelihood Explanation
Trivial to trigger: crafting a raw transaction with an out-of-range `type` value for the `Contract` message is a simple protobuf-encoding manipulation, requiring no special privileges, valid signature weight, or account state — the vulnerable code path is reached before/during permission and signature checking whenever `permissionId != 0`.

### Recommendation
Add explicit bounds validation of `contractType` before using it as a bit index, e.g.:
```java
int contractType = contract.getTypeValue();
if (contractType < 0 || contractType >= 256) {
  throw new PermissionException("invalid contract type: " + contractType);
}
```
in both `WalletUtil.checkPermissionOperations` and `TransactionUtil.checkPermissionOperations`, and ensure this exception type is caught alongside `PermissionException` wherever `checkPermissionOperations` is invoked (particularly in `TransactionCapsule.checkPermission`/`validatePubSignature`).

### Proof of Concept
1. Construct a raw `Transaction` where `raw_data.contract[0].type` is serialized with an out-of-range varint value (e.g., `100000`) for the enum field, and `permission_id` set to a nonzero value (e.g., `2`) that resolves to an `Active` permission with a 32-byte `operations` field on the sender's account.
2. Broadcast the transaction to a java-tron node.
3. During signature verification, `TransactionCapsule.checkPermission` → `WalletUtil.checkPermissionOperations` computes `contractType / 8 = 12500`, and `operations.byteAt(12500)` throws `IndexOutOfBoundsException`, which is not caught by the surrounding `catch (SignatureException | PermissionException | SignatureFormatException)` block in `validatePubSignature`.       }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {

          isVerified = false;
          throw new ValidateSignatureException("sig error");

        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());

        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
