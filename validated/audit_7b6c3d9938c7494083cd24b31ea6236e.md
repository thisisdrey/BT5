### Title
Off-Path Tunnel Teardown via Spoofed `RecvError` Packet Lacking Cryptographic Sender Authentication - (File: outside.go)

### Summary
Nebula's `RecvError` control message is processed before any handshake/certificate verification, and the only "authorization" check performed before acting on it is a plaintext-IP/port comparison against the hostinfo's currently known remote endpoint. This mirrors the H-01 report's root cause: a security-relevant decision (tearing down/re-establishing a session) is driven by an attacker-influenced, unauthenticated value (the source `UdpAddr` and the `RemoteIndex` in the cleartext header) instead of being bound to something the other, legitimate party actually agreed to cryptographically (a verified certificate/handshake state).

### Finding Description
`RecvError` packets are dispatched straight out of `readOutsidePackets` before any certificate or handshake state is required: [1](#0-0) 

`handleRecvError` then looks up the hostinfo purely by the attacker-controlled `h.RemoteIndex` field (which travels in the cleartext packet header, and is visible to any observer, on- or off-path, since headers are unencrypted for every data-plane packet), and the only additional check is that the sender's UDP source `addr` equals the last known remote `UdpAddr` recorded for that hostinfo: [2](#0-1) 

Because UDP has no source-address authentication, this check is a plaintext, spoofable network-layer comparison — not a cryptographic proof that the sender possesses the peer's certificate/private key. Nothing in `handleRecvError` verifies a MAC, requires the Noise session state, or checks the peer certificate before calling `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`.

This is the same bug class as H-01: a party accepts and acts on an unauthenticated parameter (there, the oracle address chosen unilaterally by the borrower; here, the "I am experiencing an error, tear down the tunnel" signal keyed only by a spoofable IP/port and an index value carried in cleartext) without validating that the counterparty legitimately produced it via the trust anchor (a verified certificate/handshake), enabling the attacker to force a security-relevant state transition that the honest party never agreed to.

### Impact Explanation
An attacker who can spoof UDP packets with the victim tunnel's known 4-tuple (source IP/port of the legitimate remote peer, as recorded in `hostinfo.GetRemote()`), and who can obtain/guess the 32-bit `RemoteIndex` (observable in cleartext on any packet exchanged between the two peers, e.g. by an on-path/adjacent-network attacker, or brute-forceable off-path since it is only a 32-bit value with no rate limiting on this path), can force `closeTunnel` and deletion of the pending hostmap entry on a victim node with zero cryptographic material and no CA-signed certificate. Repeated over time this causes tunnel teardown / denial of service and unnecessary re-handshake churn — a remote state poisoning / remote DoS impact, matching the "Impact Explanation" criteria required for a valid finding (concrete remote state poisoning / remote crash-equivalent DoS impact).

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to either be on-path (able to observe the cleartext `RemoteIndex` and thus not need to guess it, while spoofing source IP/port is trivial on UDP) or off-path with the ability to guess/brute-force a 32-bit index while spoofing the peer's address — non-trivial but feasible for a motivated network-adjacent attacker, and the changelog itself notes this exact attack surface was already partially hardened (disabling `recv_error` outside the valid counter window, adding `accept_recv_error`/`send_recv_error` config knobs), confirming maintainers recognize `RecvError` handling as an authentication-weak surface.

### Recommendation
- Do not act on `RecvError` (or any other pre-handshake/unauthenticated control message) based solely on a plaintext source-address match; require it to be delivered inside the authenticated/encrypted channel (i.e., only accept `RecvError`-equivalent signals once wrapped in a MAC-protected message tied to the current Noise session keys), or
- If a lightweight unauthenticated fast-path must be kept for performance, bind acceptance to a nonce/challenge that was itself established during the authenticated handshake, and rate-limit/throttle `handleRecvError` per source and per index to blunt brute-force guessing of `RemoteIndex`.
- Consider defaulting `listen.accept_recv_error` to `private` or `never` rather than `always`, since the current default trusts unauthenticated `RecvError` packets from any address.

### Proof of Concept
1. Attacker observes (on-path) or brute-forces (off-path, 32-bit space) the `RemoteIndex` value used between victim node A and its peer B (visible in the cleartext header of any packet A/B already exchange).
2. Attacker crafts a UDP packet with `header.Type = RecvError`, `RemoteIndex` set to the observed/guessed value, and spoofs the source IP:port to match B's currently known address as stored in A's `hostinfo.GetRemote()` (also learnable via observation).
3. Attacker sends this single spoofed packet to A.
4. A's `readOutsidePackets` routes it straight to `handleRecvError` (outside.go:541-575) without any certificate or handshake validation.
5. Since `f.acceptRecvErrorConfig.ShouldRecvError(addr)` is `always` by default and `hr == addr` (spoofed to match), A calls `f.closeTunnel(hostinfo)` and deletes the pending hostinfo, tearing down the legitimate tunnel between A and B — achieved entirely by an attacker holding no CA-signed certificate.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
