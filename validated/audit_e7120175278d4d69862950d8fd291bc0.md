### Title
`LinkRepositoryToObjectPool` allows linking any repository to any object pool without verifying membership relationship - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
The `LinkRepositoryToObjectPool` RPC handler links an arbitrary `repository` to an arbitrary `object_pool` with no validation that the two are actually related (i.e., that the pool was derived from that repository, or that the repository is a legitimate fork/member candidate of that pool). This mirrors the `Vault.sponsor()` bug class: a state-mutating entrypoint accepts attacker-controlled target/parameter combinations and performs a forced, unauthorized linkage that changes another repository's object-resolution state.

### Finding Description
`LinkRepositoryToObjectPool` only validates that the `repository` field is a well-formed/existing repository, and that the `object_pool` resolves to a valid pool directory: [1](#0-0) 

`poolForRequest`/`ExtractPool` merely resolve the pool from the request and check `objectpool.ErrInvalidPoolDir` / `ErrInvalidPoolRepository`: [2](#0-1) 

Neither function checks that `repository` was the `origin` used to create the `object_pool` (as done in `CreateObjectPool`, which records only `origin` → `poolRepo`): [3](#0-2) 

The actual linking logic in `objectpool.Link` unconditionally writes the pool's path into the target repository's `objects/info/alternates` file whenever the two aren't already linked, and only rejects the write if the repo is already linked to a *different* pool — it never asks whether this pairing is expected: [4](#0-3) [5](#0-4) 

This is directly analogous to the `sponsor()` finding: a caller supplies two independently-controlled identifiers (there, `receiver`/amount; here, `repository`/`object_pool`) and the callee performs a forced, irreversible state mutation (there, forced delegation to sponsorship address; here, forced alternates linkage) without checking that the target has any established relationship or consent to be paired with the caller-supplied counterpart. As documented, Gitaly's design assumes callers of `ObjectPoolService` will only ever link a repository to the pool it was itself forked from, but this invariant is not enforced in code — it is left entirely to the caller (normally GitLab Rails) to be well-behaved: [6](#0-5) 

### Impact Explanation
Any caller able to invoke `ObjectPoolService.LinkRepositoryToObjectPool` for a given storage (i.e., an authenticated Gitaly RPC client — which per the object-pool design should only ever be Rails acting on a user's own fork relationship, but here nothing in Gitaly itself enforces that restriction) can:
- Force-link a victim's repository to an arbitrary/attacker-controlled object pool, silently changing its object resolution search path and removing its existing bitmap (`removeMemberBitmaps`), degrading performance/introducing a warning-suppression side effect the victim never requested.
- Force a repository into a pool relationship that was never established via `CreateObjectPool`'s `origin`↔pool linkage, breaking the documented invariant that pool membership only exists between a pool and repositories that were legitimately cloned from it. This can lead to `DisconnectGitAlternates`/housekeeping and `FetchIntoObjectPool` operating on an inconsistent membership graph, and pool deletion later corrupting a repository that was never legitimately part of that pool's lineage (per the "no safety checks" warning documented for `DeleteObjectPool`).
- This is a cross-repository object/alternates isolation violation analogous to the External Report's forced state manipulation of another party's delegation — here it is forced manipulation of another repository's object-pool membership/alternates state, achievable from an ordinary unprivileged RPC input rather than a privileged actor.

### Likelihood Explanation
Reachable directly via a single unprivileged `LinkRepositoryToObjectPool` gRPC call with attacker-chosen `repository` and `object_pool` fields — no special repository state or prior write access is required beyond being able to name any two repositories/pool paths on the same storage. The only gating today is disk-level path validation (`ValidateRepository`, `ErrInvalidPoolDir`), not a relationship/ownership check, so exploitation requires no race conditions or additional preconditions.

### Recommendation
Enforce and persist the pool-membership invariant established at `CreateObjectPool` time (record which `origin` repository a pool was created from, e.g., alongside `migrationStateManager.RecordKeyCreation`), and have `LinkRepositoryToObjectPool` (and `FetchIntoObjectPool`) verify that the `repository`/`origin` being linked/fetched is a recognized, authorized member of the target `object_pool` before mutating alternates — rejecting the request otherwise, rather than relying solely on the caller (Rails) to only ever request legitimate pairings.

### Proof of Concept
Not independently verifiable from the indexed code alone (no test harness in the index exercises cross-tenant pool linking); however, the absence of any origin/membership check is directly visible in the cited handler and helper code — `internal/gitaly/service/objectpool/link.go` lines 10-19 and `internal/gitaly/service/objectpool/util.go` lines 24-49 perform no such check before `objectpool.Link` (internal/git/objectpool/link.go lines 28-83) writes the alternates file. Due to index size limits, related authorization middleware (if any exists outside this package) may not be fully indexed; a full review would benefit from a live Devin session with complete repository access to confirm whether any upstream gRPC interceptor enforces repository/pool relationship checks before reaching this handler.

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil

func (s *server) CreateObjectPool(ctx context.Context, in *gitalypb.CreateObjectPoolRequest) (*gitalypb.CreateObjectPoolResponse, error) {
	if in.GetOrigin() == nil {
		return nil, errMissingOriginRepository
	}

	poolRepo := in.GetObjectPool().GetRepository()
	if poolRepo == nil {
		return nil, errMissingPool
	}

	if !storage.IsPoolRepository(poolRepo) {
		return nil, errInvalidPoolDir
	}

	// repoutil.Create creates the repositories in a temporary directory. This means the repository is not created in the location
	// expected by the transaction manager. This makes sense without transactions, but with transactions, there's no real point in
	// doing so given a failed transaction's state is anyway removed. Creating the repository in a temporary directory is problematic
	// as the reference transaction hook is invoked for the repository from unexpected location, causing the transaction to fail to
	// associate the reference updates with the repository.
	//
	// Run the repository creation without the transaction in the context. The transactions reads the created repository's state from
	// the disk when committing it, so it's not necessary to capture the updates from the reference-transaction hook. This avoids the
	// problem for now, and later with transactions enabled by default we can stop creating repositories in unexpected locations.
	ctxWithoutTransaction := storage.ContextWithTransactionID(ctx, 0)
	if err := repoutil.Create(ctxWithoutTransaction, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.repositoryCounter, poolRepo, func(poolRepo *gitalypb.Repository) error {
		if _, err := objectpool.Create(
			ctxWithoutTransaction,
			s.logger,
			s.locator,
			s.gitCmdFactory,
			s.catfileCache,
			s.txManager,
			s.housekeepingManager,
			&gitalypb.ObjectPool{
				Repository: poolRepo,
			},
			s.localRepoFactory.Build(in.GetOrigin()),
		); err != nil {
			return err
		}

		return nil
	}, repoutil.WithSkipInit()); err != nil {
		return nil, structerr.New("creating object pool: %w", err)
	}

func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

	if err := transaction.CommitLockedFile(ctx, txManager, alternatesWriter); err != nil {
		return fmt.Errorf("committing alternates: %w", err)
	}

	if tx := storage.ExtractTransaction(ctx); tx != nil {
		alternatesRelativePath, err := filepath.Rel(tx.FS().Root(), altPath)
		if err != nil {
			return fmt.Errorf("rel alternates file: %w", err)
		}

		if err := tx.FS().RecordFile(alternatesRelativePath); err != nil {
			return fmt.Errorf("record alternates file")
		}
	}

	return removeMemberBitmaps(ctx, pool, repo)

// linkedToRepository tests if a repository is linked to an object pool
func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
}

```markdown
## Lifetime of Object Pools

The lifetime of object pools is maintained via the
[ObjectPoolService](../proto/objectpool.proto), which provides various RPCs to
create and delete object pools as well as to add members to or remove members
from the pool.

An object pool is typically created from an existing repository by doing a
[`--local`](https://git-scm.com/docs/git-clone#Documentation/git-clone.txt---local)
clone of the repository, which bypasses the normal transport mechanisms and
instead simply performs a copy of the references and objects.

Afterwards, any repositories which shall be a member of the pool needs to be
linked to it. Linking most importantly involves setting up the "alternates" file
of the pool member, but it also includes deleting all bitmaps for packs of the
member. This is required by Git because it can only ever use a single bitmap.
While it's not an error to have multiple bitmaps, Git will print a
[user-visible warning](https://gitlab.com/gitlab-org/gitaly/-/issues/1728) on clone or fetch
if there are. See [`git-multi-pack-index(1)`](https://git-scm.com/docs/multi-pack-index#_future_work)
for an explanation of this limitation.

Removing a member from an object pool is slightly more involved, as members of
an object pool members will miss objects which are only part of the object pool.
It is thus not as simple as removing `objects/info/alternates`, as that would
leave behind a corrupt repository. Instead, Gitaly hard-links all objects which
are part of the object pool into the dissociating member first and removes the
alternate afterwards. In order to check whether the operation succeeded, Gitaly
now runs `git-fsck(1)` to check for missing objects. If there are none, the
dissociation has succeeded. Otherwise, it will fail and re-add the alternates
file.
```
