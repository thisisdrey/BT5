The nearcore codebase's caching layers relevant to this bug class — the compiled-contract `AnyCache`/`LruWeightedCache` in `runtime/near-vm-runner/src/cache.rs` and the trie shard cache `TrieCacheInner` in `core/store/src/trie/trie_storage.rs` — are both weight-bounded LRU caches with explicit overflow protections and extensive regression tests covering exactly this bug class (unbounded growth / weight-tracking drift).

Specifically:
- `LruWeightedCache::MAX_WEIGHT` is capped at `u64::MAX / 2 - 1` specifically to prevent the transient `current_weight + weight` sum from overflowing during `insert`, and an oversized entry is rejected/evicted rather than accepted unbounded. [1](#0-0) 
- Regression tests explicitly guard against weight-tracking drift when `lru::LruCache` silently evicts entries due to item-capacity limits, which is the same class of bug (stale weight accounting causing caches to grow unbounded or evict incorrectly). [2](#0-1) 
- The on-disk `FilesystemContractRuntimeCache` enforces a size-bounded LRU eviction policy on `put`, unlinking victims to keep disk usage bounded. [3](#0-2) 
- The trie shard cache (`TrieCacheInner`) enforces a hard `total_size_limit` on every `put`, evicting via a deletions queue then LRU until the size constraint holds, and rejects caching values above `TRIE_LIMIT_CACHED_VALUE_SIZE` (e.g. contract code) to avoid unbounded growth from large values. [4](#0-3) [5](#0-4) 

None of these caches have a reachable path from an ordinary transaction or deployed contract that could cause unbounded growth, arithmetic overflow, or a crash — the size/weight limits are enforced on every insert path, with dedicated tests (`lru_weighted_cache_*`, `trie_cache_tests::test_size_limit`, `test_small_memory_limit`) covering exactly the drift/overflow scenarios that the Lighthouse `OverflowLRUCache` bug involved. This does not map to a reachable theft-of-funds, freezing, double-spend, authorization-escalation, state-root divergence, or shard-halting issue as required by the validation criteria.

    fn lru_weighted_cache_item_capacity_eviction_tracks_weight() {
        // Regression test: when lru::LruCache silently evicts an entry due to
        // item_capacity, the evicted entry's weight must be subtracted from
        // current_weight. Otherwise the tracked weight drifts upward and
        // triggers spurious weight-based evictions.
        let item_capacity = NonZeroUsize::new(2).unwrap();
        let max_weight = 25;
        let mut cache = LruWeightedCache::<&str, u32>::new(item_capacity, max_weight);

        cache.put("a", 10, 1);
        cache.put("b", 10, 2);
        // At this point: items={a,b}, current_weight should be 20.

        // Inserting "c" causes lru::LruCache to silently evict "a" (the LRU).
        // Total actual weight is now 20 (b=10 + c=10) which fits in max_weight=25.
        cache.put("c", 10, 3);

        // "b" should still be in the cache because total weight (20) <= max_weight (25).
        assert!(
            cache.contains(&"b"),
            "item 'b' was spuriously evicted due to inflated current_weight"
        );
        assert!(cache.contains(&"c"), "item 'c' should be in cache");
        assert!(!cache.contains(&"a"), "item 'a' should have been evicted by item_capacity");
    }
