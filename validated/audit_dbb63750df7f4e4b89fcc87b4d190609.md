### Title
`Certificate.Verify` silently ignores `VerifyOptions.CertificatePolicies` when using the platform verifier - (File: src/crypto/x509/verify.go, root_darwin.go, root_windows.go)

### Summary
`VerifyOptions.CertificatePolicies` is documented to restrict which certificate policy OIDs are acceptable during verification [1](#0-0) , and the pure-Go verifier correctly enforces this via `policiesValid` in `Certificate.Verify` [2](#0-1) . However, on Windows, macOS, and iOS, when `opts.Roots` is nil (i.e., the system root pool is used), `Certificate.Verify` delegates entirely to `c.systemVerify(&opts)` [3](#0-2) , and neither `root_windows.go` nor `root_darwin.go` reference `opts.CertificatePolicies`, `requireExplicitPolicy`, or `policiesValid` anywhere. This mirrors the CVE-2023-0466 bug class: an API is documented to enable/enforce a policy constraint but the actual code path silently fails to apply it under certain conditions.

### Finding Description
Attacker input: a leaf certificate presented during TLS verification (or any `Certificate.Verify` call) whose issuing CA chain contains a `certificatePolicies` extension asserting an OID that a policy-constrained caller did not intend to accept. Entry point: `(*Certificate).Verify(opts VerifyOptions)` [4](#0-3) . On Windows/macOS/iOS with `opts.Roots == nil`, execution is redirected to `c.systemVerify(&opts)` before the Go policy-tree logic (`policiesValid`) ever runs [5](#0-4) . `systemVerify` on Darwin (`root_darwin.go`) builds a `SecPolicyCreateSSL` policy and checks key usage and hostname, but never inspects or forwards `opts.CertificatePolicies` [6](#0-5) . The Windows equivalent (`verifyChain`/`checkChainSSLServerPolicy` in `root_windows.go`) similarly only checks trust status, hostname (SSL policy), and key usage — never `CertificatePolicies` [7](#0-6) [8](#0-7) . Thus the failed check is the caller-supplied `CertificatePolicies` acceptance constraint, and the sink is chain-acceptance success returned from `Verify` despite the certificate asserting a disallowed/unexpected policy OID.

### Impact Explanation
An application that sets `VerifyOptions.CertificatePolicies` to restrict trust to certificates issued under a specific CA policy (e.g., an EV policy, a specific enterprise PKI policy OID) to gate authentication or trust decisions will have that restriction silently bypassed for any user or connection using the system root pool on Windows/macOS/iOS, but correctly enforced on Linux/BSD (pure-Go verifier). This is an authentication/authorization bypass: a certificate that does not meet the caller's declared policy — but is otherwise trusted by the OS — will be accepted where the developer expected rejection. Under Go's security triage this would be a PUBLIC/vulnerability-track candidate only if this behavior diverges from documented/intended semantics; the doc comment for `CertificatePolicies` makes no exception for the platform verifier, so the current behavior is inconsistent with its own documentation.

### Likelihood Explanation
This affects any Go program that (a) runs on Windows, macOS, or iOS, (b) uses `Certificate.Verify` with `opts.Roots == nil` (i.e., relying on system trust, the common/default configuration), and (c) sets `CertificatePolicies` to constrain acceptable policy OIDs — a documented, supported, non-test feature added for RFC 5280 policy validation. The attacker need only present a certificate, chaining to a trusted (OS-trusted) root, that lacks the caller's required policy OID; no special privileges are needed beyond obtaining any certificate trusted by the platform (e.g., from any CA in the OS trust store).

### Recommendation
In `(*Certificate).Verify`, after receiving chains from `systemVerify` on Windows/macOS/iOS, additionally run `policiesValid` (and related `requireExplicitPolicy`/`inhibitPolicyMapping`/`inhibitAnyPolicy` checks) against the returned chain before accepting it, or explicitly document that `CertificatePolicies` is ignored by the platform verifier and reject/error if a caller sets `CertificatePolicies` while using the system root pool, forcing use of the pure-Go verifier for policy-constrained verification.

```go
package x509

import "testing"

// This test demonstrates that on darwin/windows, CertificatePolicies is not
// enforced by the platform verifier path, unlike the pure-Go verifier.
func TestPlatformVerifierIgnoresCertificatePolicies(t *testing.T) {
	// Build (or load) a chain where the leaf/intermediate assert only
	// testOID1, but the caller requires testOID3 with requireExplicitPolicy
	// semantics equivalent to CertificatePolicies enforcement.
	testOID3 := mustNewOIDFromInts([]uint64{1, 2, 840, 113554, 4, 1, 72585, 2, 3})

	leaf := loadTestCertFromFile(t, "testdata/policy_leaf.pem")           // asserts oid1/oid2 only
	// opts.Roots left nil to force systemVerify on darwin/windows.
	_, err := leaf.Verify(VerifyOptions{
		CertificatePolicies: []OID{testOID3},
	})

	// Expected (per documented semantics): verification should fail because
	// the chain does not support testOID3.
	// Actual (bug): on darwin/windows with system roots, systemVerify
	// succeeds because CertificatePolicies is never checked, so err == nil.
	if err == nil {
		t.Fatal("expected policy validation failure due to CertificatePolicies mismatch, but Verify succeeded — CertificatePolicies was ignored by the platform verifier")
	}
}
```
Note: this PoC requires the test certificate's issuer to be present in the OS trust store to actually exercise the `systemVerify` path (as done in `TestPlatformVerifier`, which requires manual trust store setup) [9](#0-8) ; it is included to demonstrate the code path and expected assertion, not as a fully self-contained CI test.

```go
func (c *Certificate) systemVerify(opts *VerifyOptions) (chains [][]*Certificate, err error) {
	certs := macos.CFArrayCreateMutable()
	defer macos.ReleaseCFArray(certs)
	leaf, err := macos.SecCertificateCreateWithData(c.Raw)
	if err != nil {
		return nil, errors.New("invalid leaf certificate")
	}
	macos.CFArrayAppendValue(certs, leaf)
	if opts.Intermediates != nil {
		for _, lc := range opts.Intermediates.lazyCerts {
			c, err := lc.getCert()
			if err != nil {
				return nil, err
			}
			sc, err := macos.SecCertificateCreateWithData(c.Raw)
			if err != nil {
				return nil, err
			}
			macos.CFArrayAppendValue(certs, sc)
		}
	}

	policies := macos.CFArrayCreateMutable()
	defer macos.ReleaseCFArray(policies)
	sslPolicy, err := macos.SecPolicyCreateSSL(opts.DNSName)
	if err != nil {
		return nil, err
	}
	macos.CFArrayAppendValue(policies, sslPolicy)

	trustObj, err := macos.SecTrustCreateWithCertificates(certs, policies)
	if err != nil {
		return nil, err
	}
	defer macos.CFRelease(trustObj)

	if !opts.CurrentTime.IsZero() {
		dateRef := macos.TimeToCFDateRef(opts.CurrentTime)
		defer macos.CFRelease(dateRef)
		if err := macos.SecTrustSetVerifyDate(trustObj, dateRef); err != nil {
			return nil, err
		}
	}

	// TODO(roland): we may want to allow passing in SCTs via VerifyOptions and
	// set them via SecTrustSetSignedCertificateTimestamps, since Apple will
	// always enforce its SCT requirements, and there are still _some_ people
	// using TLS or OCSP for that.

	if ret, err := macos.SecTrustEvaluateWithError(trustObj); err != nil {
		switch ret {
		case macos.ErrSecCertificateExpired:
			return nil, CertificateInvalidError{c, Expired, err.Error()}
		case macos.ErrSecHostNameMismatch:
			return nil, HostnameError{c, opts.DNSName}
		case macos.ErrSecNotTrusted:
			return nil, UnknownAuthorityError{Cert: c}
		default:
			return nil, fmt.Errorf("x509: %s", err)
		}
	}

	chain := [][]*Certificate{{}}
	chainRef, err := macos.SecTrustCopyCertificateChain(trustObj)
	if err != nil {
		return nil, err
	}
	defer macos.CFRelease(chainRef)
	for i := 0; i < macos.CFArrayGetCount(chainRef); i++ {
		certRef := macos.CFArrayGetValueAtIndex(chainRef, i)
		cert, err := exportCertificate(certRef)
		if err != nil {
			return nil, err
		}
		chain[0] = append(chain[0], cert)
	}
	if len(chain[0]) == 0 {
		// This should _never_ happen, but to be safe
		return nil, errors.New("x509: macos certificate verification internal error")
	}

	if opts.DNSName != "" {
		// If we have a DNS name, apply our own name verification
		if err := chain[0][0].VerifyHostname(opts.DNSName); err != nil {
			return nil, err
		}
	}

	keyUsages := opts.KeyUsages
	if len(keyUsages) == 0 {
		keyUsages = []ExtKeyUsage{ExtKeyUsageServerAuth}
	}

	// If any key usage is acceptable then we're done.
	for _, usage := range keyUsages {
		if usage == ExtKeyUsageAny {
			return chain, nil
		}
	}

	if !checkChainForKeyUsage(chain[0], keyUsages) {
		return nil, CertificateInvalidError{c, IncompatibleUsage, ""}
	}

	return chain, nil
}
```

```go
// checkChainSSLServerPolicy checks that the certificate chain in chainCtx is valid for
// use as a certificate chain for a SSL/TLS server.
func checkChainSSLServerPolicy(c *Certificate, chainCtx *syscall.CertChainContext, opts *VerifyOptions) error {
	servernamep, err := syscall.UTF16PtrFromString(strings.TrimSuffix(opts.DNSName, "."))
	if err != nil {
		return err
	}
	sslPara := &syscall.SSLExtraCertChainPolicyPara{
		AuthType:   syscall.AUTHTYPE_SERVER,
		ServerName: servernamep,
	}
	sslPara.Size = uint32(unsafe.Sizeof(*sslPara))

	para := &syscall.CertChainPolicyPara{
		ExtraPolicyPara: (syscall.Pointer)(unsafe.Pointer(sslPara)),
	}
	para.Size = uint32(unsafe.Sizeof(*para))

	status := syscall.CertChainPolicyStatus{}
	err = syscall.CertVerifyCertificateChainPolicy(syscall.CERT_CHAIN_POLICY_SSL, chainCtx, para, &status)
	if err != nil {
		return err
	}

	// TODO(mkrautz): use the lChainIndex and lElementIndex fields
	// of the CertChainPolicyStatus to provide proper context, instead
	// using c.
	if status.Error != 0 {
		switch status.Error {
		case syscall.CERT_E_EXPIRED:
			return CertificateInvalidError{c, Expired, ""}
		case syscall.CERT_E_CN_NO_MATCH:
			return HostnameError{c, opts.DNSName}
		case syscall.CERT_E_UNTRUSTEDROOT:
			return UnknownAuthorityError{c, nil, nil}
		default:
			return UnknownAuthorityError{c, nil, nil}
		}
	}

	return nil
}
```

```go
func verifyChain(c *Certificate, chainCtx *syscall.CertChainContext, opts *VerifyOptions) (chain []*Certificate, err error) {
	err = checkChainTrustStatus(c, chainCtx)
	if err != nil {
		return nil, err
	}

	if opts != nil && len(opts.DNSName) > 0 {
		err = checkChainSSLServerPolicy(c, chainCtx, opts)
		if err != nil {
			return nil, err
		}
	}

	chain, err = extractSimpleChain(chainCtx.Chains, int(chainCtx.ChainCount))
	if err != nil {
		return nil, err
	}
	if len(chain) == 0 {
		return nil, errors.New("x509: internal error: system verifier returned an empty chain")
	}

	// Mitigate CVE-2020-0601, where the Windows system verifier might be
	// tricked into using custom curve parameters for a trusted root, by
	// double-checking all ECDSA signatures. If the system was tricked into
	// using spoofed parameters, the signature will be invalid for the correct
	// ones we parsed. (We don't support custom curves ourselves.)
	for i, parent := range chain[1:] {
		if parent.PublicKeyAlgorithm != ECDSA {
			continue
		}
		if err := parent.CheckSignature(chain[i].SignatureAlgorithm,
			chain[i].RawTBSCertificate, chain[i].Signature); err != nil {
			return nil, err
		}
	}
	return chain, nil
}
```
