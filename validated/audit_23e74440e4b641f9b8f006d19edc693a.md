### Title
Unvalidated User-Supplied Remote URL Enables SSRF via `FindRemoteRepository` RPC - (File: internal/gitaly/service/remote/find_remote_repository.go)

### Summary
The `FindRemoteRepository` RPC accepts a user-controlled `remote` string and passes it directly to `git-ls-remote(1)` with no scheme validation, no destination allowlist, and no DNS-rebinding protection, unlike its sibling RPCs (`FetchRemote`, `CreateRepositoryFromURL`, `UpdateRemoteMirror`, `FindRemoteRootRef`) which at least support the `resolved_address`/`curloptResolve` mitigation. This mirrors the reported bug class: absence of a whitelist/allowlist for destination and no restriction on which "mailbox"/transport target can be reached, letting a caller direct outbound git network traffic at arbitrary internal or external hosts.

### Finding Description
`FindRemoteRepository` only checks that `req.GetRemote()` is non-empty before using it verbatim as the target of `git ls-remote`: [1](#0-0) 

Compare this to `FetchRemote`/`CreateRepositoryFromURL`/`UpdateRemoteMirror`/`FindRemoteRootRef`, which all funnel the user-supplied URL through `gitcmd.GetURLAndResolveConfig`, a function whose explicit purpose is "to avoid DNS rebinding" by binding the URL's hostname to a resolved IP via `http.curloptResolve` or literal replacement for `ssh://`/scp-like/`git://` URLs: [2](#0-1) [3](#0-2) 

`FindRemoteRepository` has no equivalent field (`proto/remote.proto` `FindRemoteRepositoryRequest` exposes no `resolved_address`) and no scheme/host allowlist at all — the string is passed straight into the git command args: [4](#0-3) 

Because `git-ls-remote` will honor whatever transport scheme is embedded in the string (`http://`, `https://`, `ssh://`, `git://`, or file/local paths), and there is no whitelist restricting destination domains/schemes as recommended in the analog report, any authenticated Gitaly client (e.g. GitLab Rails backend acting on unprivileged user input such as import URLs) can direct the Gitaly node to make outbound connections to attacker-chosen hosts, including internal-only services (metadata endpoints, internal admin panels) or to probe internal network topology by observing timing/error differences.

### Impact Explanation
This is a Server-Side Request Forgery primitive: Gitaly (a backend service with network access potentially including internal-only endpoints) can be coerced into issuing outbound git-protocol/HTTP requests to arbitrary attacker-supplied targets, since the `remote` argument is neither restricted to an allowlist of domains, nor is DNS-rebinding otherwise mitigated for this particular RPC (unlike the other four remote-URL-accepting RPCs). This can be used for internal network reconnaissance, and depending on the transport parsed by git could also touch local file paths.

### Likelihood Explanation
Likelihood is high: `FindRemoteRepository` is reachable by any caller invoking the gRPC-level `RemoteService` (typically GitLab Rails on behalf of a user performing a repository-existence/import check), requires only a syntactically valid `remote` string, and the only validation performed is a non-empty check.

### Recommendation
- Add the same `resolved_address` field and `gitcmd.GetURLAndResolveConfig` handling used by `FetchRemote`, `CreateRepositoryFromURL`, `UpdateRemoteMirror`, and `FindRemoteRootRef` to `FindRemoteRepository`/`FindRemoteRepositoryRequest`, so DNS-rebinding protection is consistently applied.
- Restrict accepted URL schemes to an explicit allowlist (e.g., `http`, `https`, `git`, `ssh`) before invoking `git ls-remote`, rejecting anything else outright.
- Consider requiring callers to pre-validate destination domains against an application-level allowlist before the RPC is ever issued, consistent with the "whitelisting mechanism" recommendation in the analog report.

### Proof of Concept
1. Call `RemoteService.FindRemoteRepository` with `remote = "http://169.254.169.254/latest/meta-data/"` (or any internal-only host/port). [5](#0-4) 
2. Gitaly executes `git ls-remote http://169.254.169.254/latest/meta-data/ HEAD` unmodified, with no allowlist check and no `resolved_address` mitigation applied, causing Gitaly to originate a request to the attacker-chosen target.
3. Observe response/timing differences in the resulting `Exists`/error to confirm reachability of internal hosts distinct from the intended remote-repository universe.

func (s *server) FindRemoteRepository(ctx context.Context, req *gitalypb.FindRemoteRepositoryRequest) (*gitalypb.FindRemoteRepositoryResponse, error) {
	if req.GetRemote() == "" {
		return nil, structerr.NewInvalidArgument("empty remote can't be checked.")
	}

	var output bytes.Buffer
	cmd, err := s.gitCmdFactory.NewWithoutRepo(ctx,
		gitcmd.Command{
			Name: "ls-remote",
			Args: []string{
				req.GetRemote(),
				"HEAD",
			},
		},
		gitcmd.WithStdout(&output),
	)
	if err != nil {
		return nil, structerr.NewInternal("error executing git command: %w", err)
	}

	if err := cmd.Wait(); err != nil {
		return &gitalypb.FindRemoteRepositoryResponse{Exists: false}, nil
	}

func buildCommandOpts(ctx context.Context, opts *localrepo.FetchOpts, req *gitalypb.FetchRemoteRequest) error {
	remoteURL := req.GetRemoteParams().GetUrl()
	var config []gitcmd.ConfigPair

	for _, refspec := range getRefspecs(req.GetRemoteParams().GetMirrorRefmaps()) {
		config = append(config, gitcmd.ConfigPair{
			Key: "remote.inmemory.fetch", Value: refspec,
		})
	}

	if resolvedAddress := req.GetRemoteParams().GetResolvedAddress(); resolvedAddress != "" {
		modifiedURL, resolveConfig, err := gitcmd.GetURLAndResolveConfig(remoteURL, resolvedAddress)
		if err != nil {
			return fmt.Errorf("couldn't get curloptResolve config: %w", err)
		}

		remoteURL = modifiedURL
		config = append(config, resolveConfig...)
	}

	config = append(config, gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL})
