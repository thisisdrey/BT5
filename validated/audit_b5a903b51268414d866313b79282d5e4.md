## Title
Partial Path Traversal in ijar `zipper` Extraction via Insufficient Prefix Check — (File: third_party/ijar/zip_main.cc)

### Summary
The `zipper` tool's ZIP extraction routine `UnzipProcessor::Process` in `third_party/ijar/zip_main.cc` guards against path traversal using a raw string-prefix comparison (`normalized.compare(0, normalized_root.size(), normalized_root)`) rather than checking for a proper path-segment boundary after the root. This is structurally identical to the AWS SDK `TransferManager.downloadDirectory`/`leavesRoot` bug: a destination-directory prefix check without a trailing separator allows sibling directories whose name shares the same prefix (e.g. `output_root_ = "/tmp/foo"` vs. an entry that normalizes to `/tmp/foo-bar/evil`) to pass validation.

### Finding Description
`UnzipProcessor::Process` builds the output path by concatenating `output_root_` with the (possibly attacker-controlled) ZIP entry name, then normalizes both and compares: [1](#0-0) 

The check `normalized.compare(0, normalized_root.size(), normalized_root) != 0` only verifies that `normalized` textually starts with the bytes of `normalized_root` — it does not verify that the next character (if any) is a path separator. This is exactly the "insufficient guard" root cause described in the AWS advisory: `"/usr/outnot".startsWith("/usr/out")` returns true even though `outnot` is a sibling, not a descendant, of `out`. Here, if `output_root_` resolves to `/tmp/extract` and a crafted entry name (via `..` segments and a suitably named sibling, e.g. `../extract-evil/payload`) normalizes to `/tmp/extract-evil/payload`, the prefix comparison against `/tmp/extract` succeeds because `/tmp/extract-evil` textually starts with `/tmp/extract`, even though it is a different, sibling directory.

This is confined to the C++ `zipper`/ijar extraction path (`extract()` / `UnzipProcessor::Process`), which is a general-purpose, attacker-facing ZIP extraction routine within the same repository as the checked-out `third_party/ijar` sources.

### Impact Explanation
If this extraction path is invoked against a ZIP archive whose entry names are not otherwise fully sanitized (i.e., an entry can encode `..` segments), an attacker who controls the archive contents can cause files to be written into a directory adjacent to (sharing a prefix with) the intended output root, escaping the intended containment boundary — matching the AWS advisory's "one level up, name-prefix-matching sibling directory" impact.

### Likelihood Explanation
Exploitability depends on whether entry names reaching this code can actually contain `..` segments after normalization and whether a same-repo test (`third_party/ijar/test/zip_test.sh`) already covers the general path-traversal case. Indeed, the repo's own test suite includes `test_no_path_traversal`, which exercises a `path_traversal_zip.jar` payload against exactly this code path: [2](#0-1) 

That existing test only validates the simple `..`-escape case (writing outside the root entirely), not the partial/sibling-prefix bypass class described in the AWS advisory (writing into `output_root_ + "-suffix"`). I could not verify with the tools available whether `normalize_path`/`AsPrintablePath` (in `blaze_util::Path`) already canonicalizes such that a `..`-crafted entry can actually reach a sibling directory name, and I was unable to locate a Java-side `StripPrefixedPath`/`ZipDecompressor`/`TarFunction` in this index to compare against (these classes named in the prompt's "surface" list were not found via search, which may be an index-coverage limitation rather than their absence from the codebase).

### Recommendation
Change the containment check in `UnzipProcessor::Process` to require a trailing path separator (or exact equality) after the root prefix, e.g.:
```cpp
if (normalized.compare(0, normalized_root.size(), normalized_root) != 0 ||
    (normalized.size() > normalized_root.size() &&
     normalized[normalized_root.size()] != '/')) {
  // reject
}
```
This mirrors the AWS SDK's actual fix pattern (ensuring the parent path is separator-terminated before the `startsWith` check).

### Proof of Concept
I could not construct or run a verifying JUnit/shell-based reproduction within this session (no filesystem/terminal access, and the extraction logic's exact interaction with `blaze_util::Path` normalization was not fully traceable via the indexed search tools). A concrete PoC would need to:
1. Craft a ZIP with an entry name such as `../extract-evil/payload` where `zipper x archive.zip -d extract` is invoked with cwd/exdir resolving to `.../extract`.
2. Verify whether `normalize_path` collapses the `..` such that `normalized` becomes `.../extract-evil/payload`, and confirm the existing prefix check at lines 134–143 fails to reject it.
3. Extend `third_party/ijar/test/zip_test.sh`'s `test_no_path_traversal` with this sibling-directory payload to assert the file is not written outside `output_root_`.

**Given the inability to confirm end-to-end that attacker-controlled entry names can actually produce a sibling-prefix-matching normalized path (rather than being caught earlier by `..`-rejection elsewhere, which I could not fully rule out from the visible code), this finding should be treated as a plausible but unverified analog rather than a confirmed exploitable vulnerability.**
