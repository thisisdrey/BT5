### Title
`init_global_fee_state` is permissionless and lets an attacker front-run deployment to seize `global_fee_admin` - (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
`init_global_fee_state` initializes the single, program-wide `FeeState` PDA (seeded only by `FEE_STATE_SEED`, with no group-specific component) and sets `global_fee_admin` and `global_fee_wallet` to caller-supplied `Pubkey` arguments, with no signer/authorization check restricting who may call it or what values they may pass. [1](#0-0)  The `InitFeeState` accounts struct only requires an arbitrary `payer: Signer`, and the PDA is `init`-constrained on that seed alone, so whoever's transaction lands first "wins" the account. [2](#0-1)  This is the direct analog of the reported `RadiantOFT.setMinter()` bug: a one-time, deploy-time bootstrap function with no on-chain restriction and no enforced deployment ordering, allowing anyone to become the privileged role before the legitimate deployer does.

### Finding Description
The instruction is documented in `lib.rs` as "(Runs once per program)"—i.e., a deploy-time bootstrap, exactly like `RadiantOFT.setMinter()`—but nothing enforces that only the legitimate deployer calls it, or that it is called atomically with deployment. [3](#0-2)  The `admin_key` and `fee_wallet` parameters are fully attacker-controlled, and the PDA address is deterministic and publicly known (`[FEE_STATE_SEED]`), so any party monitoring the mempool/program upgrade can race to submit `init_global_fee_state` with their own keys before the project's own setup transaction executes. [4](#0-3)  Because Solana's `init` account constraint fails on a second call to the same PDA, once an attacker's transaction lands first, the legitimate admin can never re-initialize it—mirroring the report's finding that `setMinter()` "can be called only once" but with no guarantee the deployer calls it first.

Once `global_fee_admin` is attacker-controlled, `edit_global_fee_state` (which is gated only by `global_fee_admin`) is fully exploitable, per the documented access matrix. [5](#0-4)  The `FeeState` struct's `global_fee_admin` field is described as able to "modify fees, pause the protocol, etc," and `pause_delegate_admin` (settable by `global_fee_admin`) can panic-pause the entire protocol. [6](#0-5)  The panic-pause capability blocks deposit/borrow/withdraw/repay, liquidations, order flows, and permissionless fee/bad-debt operations protocol-wide. [7](#0-6) 

### Impact Explanation
An attacker who front-runs `init_global_fee_state` gains permanent, unrecoverable control of the single program-wide `global_fee_admin` role (the PDA cannot be reinitialized). This lets them: (1) redirect `global_fee_wallet` so all protocol/program fees route to an attacker-controlled address (unauthorized value diversion), and (2) repeatedly panic-pause the entire protocol, freezing deposits, withdrawals, borrows, repays, liquidations, and order execution across every group on the deployment—an unauthorized state change and a protocol-wide freeze/DoS. This satisfies the "unauthorized state change" and "permanent lock/freeze" impact categories.

### Likelihood Explanation
Exploitation requires only submitting a transaction calling `init_global_fee_state` with attacker-chosen `admin_key`/`fee_wallet` before the project's own setup transaction executes, targeting the deterministic PDA `[FEE_STATE_SEED]`. On any public deployment, program IDs and instruction discriminators are visible immediately once the program is deployed/upgraded, and initialization is normally done as a separate follow-up transaction, not atomically with the program deploy—so there is a real window for a race. This is a standard, well-known Solana "instruction front-running / unprotected initializer" pattern, requiring no privileged keys, matching the baseline "no-privilege attacker" model.

### Recommendation
Restrict `init_global_fee_state` (and `init_global_fee_state_v2`) so that `payer`/caller must equal a hard-coded or program-upgrade-authority-derived address (e.g., check against the program's `BPFLoaderUpgradeable` upgrade authority via the `program_data` account, as is already done elsewhere for admin-only bootstrap paths), or bundle initialization atomically into the deployment transaction itself so no window for front-running exists. Alternatively, require the instruction to be invoked in the same transaction as program deployment/upgrade instructions, or add a signer check against a fixed deployer pubkey compiled into the program.

### Proof of Concept
1. Attacker monitors the target cluster for the marginfi program's deployment/upgrade transaction (program ID is public once deployed).
2. Before the project team submits their own `init_global_fee_state` transaction, the attacker derives the same PDA `[FEE_STATE_SEED]` (deterministic, no secret involved) and submits `init_global_fee_state(admin_key = attacker_pubkey, fee_wallet = attacker_pubkey, ...)` with themselves as `payer`.
3. Because `InitFeeState` requires only an arbitrary signer as payer and no admin check, the attacker's transaction succeeds and creates the `FeeState` PDA with `global_fee_admin = attacker_pubkey`.
4. The legitimate team's subsequent `init_global_fee_state` call fails (`init` constraint: account already in use).
5. Attacker now calls `edit_global_fee_state` (gated only by `global_fee_admin`) to redirect `global_fee_wallet` to themselves and/or repeatedly invoke `panic_pause` to freeze the entire protocol, as shown by the documented capabilities of `global_fee_admin`. [5](#0-4)

```rust
// Runs once per program to init the global fee state.
use anchor_lang::prelude::*;
use marginfi_type_crate::{
    constants::FEE_STATE_SEED,
    types::{FeeState, WrappedI80F48},
};

#[allow(unused_variables)]
pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}
```
