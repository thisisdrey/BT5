Audit Report

## Title
Permanent, unclaimable fund lock in Snowbridge V1 inbound `SendToken`/`SendNativeToken` XCM when `DepositAsset` to `beneficiary` fails - ([File: bridges/snowbridge/primitives/inbound-queue/src/v1.rs])

## Summary
Snowbridge V1's `MessageToXcm::convert_send_token` and `convert_send_native_token` construct XCM programs that clear or never set the execution origin (via `ClearOrigin` and absence of `SetHints`/`asset_claimer`) before the terminal `DepositAsset { beneficiary }` instruction. If that deposit fails for any realistic reason (frozen beneficiary account, de-registered asset, ED shortfall), the XCM executor traps the assets under the unreachable BridgeHub sibling-parachain origin, permanently locking the bridged value with no claim path from AssetHub.

## Finding Description
`convert_send_token`'s direct-AssetHub branch executes `ReserveAssetDeposited` then `ClearOrigin` before finally issuing `DepositAsset { assets: Wild(AllCounted(2)), beneficiary }` [1](#0-0) [2](#0-1) . `convert_send_native_token` similarly issues `WithdrawAsset` followed directly by `DepositAsset { .., beneficiary }` with no claimer set at any point [3](#0-2) .

Neither function ever emits `SetHints { hints: [AssetClaimer { .. }] }` or `AliasOrigin`, unlike the V2 converter which was specifically patched to pin a claimer reachable by a signed AssetHub extrinsic (`prdoc/stable2603-3/pr_11919.prdoc`). When the terminal `DepositAsset` fails — e.g., the beneficiary's `ForeignAssets` account is frozen, the asset id was de-registered, or ED/consumer-reference constraints block account creation — the executor's `post_process` trap-drop logic resolves the claimer in priority order: explicit `asset_claimer`, then `context.origin`, then `self.original_origin`. Since V1 clears/never sets the first two, the fallback is `original_origin`, i.e. the BridgeHub sibling-parachain `Location` under which the whole message was executed on AssetHub — not an account-derived location.

`pallet_xcm::claim_assets` computes the trap-lookup hash from `(origin, assets)` where `origin` is derived from `T::ExecuteXcmOrigin::ensure_origin(origin)` for a signed extrinsic, which always yields an `AccountId32`-based location via `SignedToAccountId32`. No signed AssetHub account can present a `Parachain(BridgeHub)` origin, so the trap can never be matched and claimed.

## Impact Explanation
Any failure of the final `DepositAsset` in the V1 `SendToken`/`SendNativeToken` inbound flow permanently locks the corresponding bridged asset and fee value under an origin architecturally unreachable from AssetHub signed extrinsics. This matches the "permanent user-fund or bridge-state lock" impact category in the accepted impact gate, since the root cause is a code defect in the message-to-XCM converter, not privileged-actor misuse.

## Likelihood Explanation
Deposit failures are realistic and not attacker-privileged: a frozen/blocked `ForeignAssets` account, a de-registered asset, or ED/consumer-reference shortfalls for the specific beneficiary are conditions that can arise naturally or be engineered by an unprivileged actor controlling the destination account state, exactly mirroring the reported CCTP/Wormhole failure mode. Snowbridge V1 remains a live production message path, and the V2 fix (claimer pinning) was never backported to V1's converter, so this gap is currently live.

## Recommendation
Add an explicit `SetHints { hints: [AssetClaimer { location }] }` (or `AliasOrigin`) in the V1 `convert_send_token` and `convert_send_native_token` XCM programs, anchored to a location reachable by a normal signed AssetHub extrinsic (mirroring the V2 fix's `network: Some(LocalNetwork::get())` pinning), so that any `DepositAsset` failure traps funds under a claimable location rather than the unreachable BridgeHub sibling-parachain origin.

## Proof of Concept
1. An Ethereum user sends a `SendToken`/`SendNativeToken` message with `Destination::AccountId32 { id }` targeting an AssetHub account.
2. Before the message is relayed/processed, the target `ForeignAssets` account for that beneficiary becomes unable to receive the deposit (frozen, de-registered asset, or ED shortfall).
3. `EthereumInboundQueue::process_message` converts and executes the resulting XCM on AssetHub; `DepositAsset { assets: Wild(AllCounted(2)), beneficiary }` fails; the executor's trap logic falls back to `original_origin = Location::new(1, [Parachain(BridgeHub)])`.
4. No AssetHub signed account can reproduce that origin via `pallet_xcm::claim_assets` (which always derives an `AccountId32` location), so the `AssetsTrapped` event remains permanently unclaimed and the bridged value is lost.
