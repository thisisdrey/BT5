Confirmed: when an action receipt's execution result is `Err` (e.g. an out-of-gas panic inside a callback function), `state_update.rollback()` discards **all** state changes made during that receipt, including any writes the WASM guest made before the panic [1](#0-0) . This is exactly the mechanism that makes the wallet-contract griefing path exploitable: `self.has_in_flight_tx = false` is written as the very first line of every callback, but if the *rest* of that same callback function later panics (e.g. from an out-of-gas condition while deserializing a huge/malformed JSON payload returned by an untrusted contract), the entire receipt fails and the flag reset is rolled back along with everything else.

### Title
Griefing via malicious NEP-141/registrar target permanently bricks the ETH-implicit Wallet Contract, freezing its funds - (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract (NEP-518) that NEAR deploys on every ETH-implicit account guards against re-entrant/out-of-order execution with a single boolean flag, `has_in_flight_tx`, which is set to `true` before any promise is scheduled and is only ever reset to `false` at the very start of the corresponding callback [2](#0-1) . When the wallet emulates an ERC-20 transfer, it calls an arbitrary, attacker-influenceable NEP-141 token contract's `storage_balance_of` and deserializes the JSON response inside `nep_141_storage_balance_callback`, under a hard-coded, small static gas budget (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS` plus the user-specified action gas) [3](#0-2) [4](#0-3) . The same pattern applies to `address_check_callback`, which deserializes the address registrar's response.

### Finding Description
`rlp_execute` refuses to start a new transaction whenever `has_in_flight_tx == true`, and there is no other public method to clear it [5](#0-4) . `has_in_flight_tx` is only cleared inside `address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, and `ban_relayer`, and in every case the flag is reset as the *first statement* of the function [6](#0-5) [7](#0-6) [8](#0-7) .

nearcore's runtime rolls back **all** trie writes performed during a receipt whenever the receipt execution fails (e.g. the contract host aborts the call with `HostError`/gas exhaustion): `Err(_) => state_update.rollback()` [1](#0-0) . A failed function call is not partially committed — the whole write set, including the `has_in_flight_tx = false` write made before the failure, is discarded.

This is structurally the same bug class as the reported Sense issue: an attacker-supplied/attacker-influenceable external component (the "adapter"/target token contract, here a NEP-141 token or the address registrar) is invoked mid-flow, and its response can be crafted to break the invariant-tracking logic that a subsequent, unprivileged, funds-controlling step depends on. Here, a token contract that the ETH-implicit account owner is tricked (or chooses) to interact with can return an oversized or gas-expensive `storage_balance_of`/registrar `lookup` response. `serde_json::from_slice` deserialization of that payload happens inside the callback under the small static callback gas budget; if it exhausts gas, the callback function call fails, and the entire receipt (including the `has_in_flight_tx = false` reset) is rolled back by `state_update.rollback()`. Because `rlp_execute` is now permanently blocked (`has_in_flight_tx` stays `true` forever, and there is no reset path since ETH-implicit accounts cannot hold a full access key and cannot be deleted) [9](#0-8) , the account is permanently bricked.

### Impact Explanation
Because ETH-implicit accounts can *only* be operated through `rlp_execute` on the Wallet Contract (they cannot have a full-access key added nor be deleted), permanently setting `has_in_flight_tx = true` makes the account's entire $NEAR balance and any NEP-141/other tokens it holds permanently inaccessible — a concrete, permanent freezing of user funds with no recovery path, matching the reported bug class's "block withdrawal altogether" impact.

### Likelihood Explanation
Any unprivileged party can trigger this: the account owner (or a colluding/malicious token issuer whose contract the owner is induced to interact with via an ERC-20 style emulated transfer) only needs to make `target`/`token_id` resolve to a contract that returns an oversized/expensive-to-parse JSON body from `storage_balance_of` (or the registrar's `lookup`). No special privileges, validator collusion, or protocol-level actions are required — only a single `rlp_execute` call with gas parameters low enough (or a response large enough) that the callback's static gas allotment is exhausted during JSON deserialization.

### Recommendation
Do not rely on "reset flag as first statement, then possibly panic" for a persisted invariant. Instead, clear `has_in_flight_tx` in a way that is committed even if the rest of the callback logic fails — e.g., wrap the response-processing logic in a `#[private]` callback that first commits the flag reset via a cheap, dedicated action/receipt, or budget enough gas headroom and defensively cap/validate the size of untrusted cross-contract responses before deserializing them (e.g. reject payloads over a fixed byte length before calling `serde_json::from_slice`), so that gas exhaustion during parsing cannot occur. Alternatively, track "in-flight" state using a mechanism that is not lost on receipt failure (e.g. a time-based/nonce-based liveness check that lets a stuck flag self-heal after a bounded number of blocks).

### Proof of Concept
1. Deploy a malicious "NEP-141-like" contract `evil.token` whose `storage_balance_of` method returns a very large JSON array/string (sized so that parsing it costs more gas than `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` provides once combined with the attacker-chosen small `action.gas()`).
2. From the ETH-implicit wallet, sign and relay an Ethereum-style transaction that emulates an ERC-20 transfer with `target = evil.token`, using a `gas_limit` just large enough to pass `validate_tx_relayer_data`'s `InsufficientGas` check but small enough that `NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())` is insufficient for the callback's deserialization step [10](#0-9) .
3. `rlp_execute` sets `has_in_flight_tx = true` and schedules the promise chain: `storage_balance_of` → `nep_141_storage_balance_callback`.
4. `nep_141_storage_balance_callback` executes, sets `self.has_in_flight_tx = false` in-memory, then runs out of gas while deserializing `evil.token`'s oversized response via `serde_json::from_slice`.
5. The receipt fails; nearcore's `Runtime::apply_action_receipt` calls `state_update.rollback()`, discarding the `has_in_flight_tx = false` write along with everything else in that receipt.
6. `has_in_flight_tx` remains `true` in committed state forever. Every subsequent `rlp_execute` call to this account now immediately returns the "transaction already in progress" error, and since ETH-implicit accounts have no full-access key and cannot be deleted, the account and its entire balance are permanently frozen.
