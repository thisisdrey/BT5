Audit Report

## Title
Missing bound check between per-call slash `amount` and `AgentLedger.pending_slash` allows over-slashing of delegators - (`substrate/frame/delegated-staking/src/lib.rs`)

## Summary
`Pallet::do_slash` only validates the requested `amount` against `pending_slash > 0` (existence check) and `delegation.amount >= amount` (the delegator's own balance), but never checks that `amount <= agent_ledger.ledger.pending_slash`. This allows an agent to call `delegator_slash` with a per-call `amount` — or with a cumulative sum across multiple delegator calls — that exceeds the agent's actual `pending_slash`, since `remove_slash` uses a saturating subtraction rather than a checked one.

## Finding Description
`do_slash` in `substrate/frame/delegated-staking/src/lib.rs` checks only:
1. `agent_ledger.ledger.pending_slash > Zero::zero()` at [1](#0-0) 
2. `delegation.amount >= amount` at [2](#0-1) 

Neither check bounds `amount` by the agent's actual `pending_slash`. The slash is then applied unconditionally: `T::Currency::slash(...)` followed by `agent_ledger.remove_slash(actual_slash).save()` at [3](#0-2) .

`remove_slash` performs a **saturating**, not checked, subtraction of `pending_slash` and `total_delegated`: [4](#0-3) . If `amount` exceeds `pending_slash`, `pending_slash` simply clamps to zero (with only a `defensive_saturating_sub`, which is a no-op assertion in release builds) rather than the call failing.

I confirmed the calling path from nomination-pools: `DelegateStake::member_slash` forwards the caller-supplied `amount` directly to `Delegation::delegator_slash` at [5](#0-4) , and `delegator_slash` forwards straight into `do_slash` at [6](#0-5) . I was not able to fully trace, within the available tool budget, the nomination-pools `lib.rs` internal logic that computes the per-member `amount` passed into `member_slash` to determine whether nomination-pools itself enforces that the sum of amounts distributed across members is capped at the pool's `pending_slash` before calling into `delegated-staking`. This is a gap in my verification: if nomination-pools' internal slashing algorithm (`do_apply_slash` or similar) already computes per-member amounts that are provably bounded by the pool's total pending slash before ever calling `member_slash`, then the *pools* consumer path would not be exploitable even though the low-level `do_slash` primitive lacks the check. However, `delegator_slash` is a `pub` interface (`DelegationInterface::delegator_slash`) reachable by **any account registered as an `Agent`**, not just via the nomination-pools pallet — `register_agent` is open to any signed account with no privilege requirement, as shown in [7](#0-6) . This means the vulnerable path is directly reachable without going through nomination-pools' internal bookkeeping at all — an agent can call `delegator_slash` with an arbitrary `amount` for its own delegators, and the missing bound is a real gap in `delegated-staking` regardless of how any particular consumer pallet chooses to derive `amount`.

The module's own documentation states the intended invariant — "Staking pallet ensures the pending slash never exceeds staked amount ... it is the agent's responsibility to apply slashes for each delegator, one at a time" at [8](#0-7)  — but this invariant is enforced only on the *production* side (`on_slash` accruing into `pending_slash`) at [9](#0-8) , and is not enforced on the *consumption* side (`do_slash`).

## Impact Explanation
An agent account (any signed account can register as one) can invoke `delegator_slash` against its own delegators with an `amount` that is not validated against the agent's actual `pending_slash`. Because the check is only `pending_slash > 0` (not `amount <= pending_slash`), and `remove_slash` silently saturates instead of erroring, delegator funds held under `HoldReason::StakingDelegation` can be slashed for more than the agent's true `pending_slash`, with the excess moved to `T::OnSlash`/reporter via `T::Currency::slash` and `credit.split(...)` at [10](#0-9) . This is unbacked destruction/reallocation of delegator-held value, breaking the "conserve value and settle exactly once" invariant for staking value.

## Likelihood Explanation
`register_agent` requires only a signed origin — no governance or root privilege — as shown at [7](#0-6) . Once any slash has posted a nonzero `pending_slash` for that agent (a normal event from `CoreStaking::on_slash`), the agent can call `delegator_slash` against each of its own delegators with attacker-chosen `amount` values, each individually passing the two existing (insufficient) checks. This requires only ordinary agent-level control (e.g., a pool operator role), not any privileged or governance capability, making the bug realistically reachable by an unprivileged actor.

## Recommendation
Add an explicit bound check in `do_slash` before executing the slash:
```rust
ensure!(agent_ledger.ledger.pending_slash >= amount, Error::<T>::NotEnoughFunds /* or dedicated error */);
```
Additionally, change `AgentLedgerOuter::remove_slash` to use a checked subtraction (returning an error/`DispatchResult`) instead of `defensive_saturating_sub`, so any residual drift between the sum of applied per-call slashes and the agent's `pending_slash` is caught rather than silently absorbed.

## Proof of Concept
1. Agent `A` registers via `register_agent` (open, unprivileged) and receives delegations of `100` each from delegators `D1` and `D2`.
2. `CoreStaking` reports a slash on `A`, causing `on_slash` to set `AgentLedger(A).pending_slash = 50` via `pending_slash.saturating_accrue(slashed_total)`.
3. Agent `A` calls `delegator_slash(A, D1, 100, None)`. The checks `pending_slash (50) > 0` and `delegation(D1).amount (100) >= 100` both pass — nothing bounds `amount` (`100`) by `pending_slash` (`50`). `T::Currency::slash` removes `100` from `D1`, and `remove_slash(100)` saturates `pending_slash` to `0` and `total_delegated` decreases by `100`, silently losing `50` of unaccounted-for slashing beyond what was actually posted.
4. `D1` has lost `50` more than the chain's own slashing mechanism ever decided to slash from `A`'s stake, with the excess routed to `T::OnSlash`/reporter — a reproducible unit test asserting `AgentLedger(A).pending_slash == 0` and `D1` balance reduced by `100` (versus the intended `50`) after step 3 would confirm the over-slash.
