### Title
Unauthenticated `page_index` u32 overflow in `get_attachments_available_at_page_index` via `/v2/attachments/inv` - ([File: stackslib/src/net/api/getattachmentsinv.rs])

### Summary
The `/v2/attachments/inv` handler accepts arbitrary `u32` values for `pages_indexes` and passes each one, unbounded, into `AtlasDB::get_attachments_available_at_page_index`. Neither `try_parse_request` nor `try_handle_request` validates that `page_index` is within any sane bound (they only cap the *count* of requested pages to `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`), so a value like `u32::MAX` reaches the arithmetic that derives byte/row ranges from `page_index * AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE`.

### Finding Description
In `stackslib/src/net/api/getattachmentsinv.rs`, `try_parse_request` parses each comma-separated entry of `pages_indexes` with `entry.parse::<u32>()` [1](#0-0)  with no upper-bound check on the value itself. `try_handle_request` only bounds the *number* of page indexes (`page_indexes.len() > MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`) [2](#0-1) , and then forwards each raw `u32` value directly into `network.get_atlasdb().get_attachments_available_at_page_index(*page_index, &index_block_hash)` [3](#0-2) . The handler's own comment confirms the page/byte-range derivation is done from `page_index` combined with a fixed page size constant [4](#0-3) , meaning `page_index` is multiplied by `AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE` to compute a range bound inside `AtlasDB`.

I was not able to retrieve the exact body of `get_attachments_available_at_page_index` in `stackslib/src/net/atlas/db.rs` within the available tool budget (only surrounding, unrelated lines were returned) to confirm the precise arithmetic operation (checked/wrapping/saturating vs. plain `*`/`+`) or whether an explicit bounds check exists before the multiplication. This is a material gap: without seeing that function body directly, I cannot confirm whether Rust's default overflow-checked arithmetic panics on `page_index = u32::MAX`, whether the code uses `checked_mul`/`saturating_mul`, or whether an early bounds check already rejects out-of-range page indices before any arithmetic occurs.

### Impact Explanation
If unchecked/plain multiplication is used, this would be a remote, unauthenticated, single-GET-request crash of the node's RPC-serving thread when overflow checks are enabled (debug/test builds, or any release build compiled with `overflow-checks = true`), matching the Critical "remote crash/unauthenticated DoS from few messages" category. If wrapping arithmetic is used, the impact is likely limited to serving incorrect/empty attachment inventory bits rather than memory-unsafety, since SQLite bounds are still validated by the query engine. The severity is contingent on the unverified arithmetic in `AtlasDB::get_attachments_available_at_page_index`.

### Likelihood Explanation
The RPC endpoint requires no authentication, no privileged role, and no state precondition beyond a syntactically valid 64-hex `index_block_hash`; the attacker only needs to send one `GET /v2/attachments/inv?index_block_hash=<hex>&pages_indexes=4294967295` request, well within `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`. Reachability is confirmed at the handler layer; the only unresolved question is whether the downstream `AtlasDB` function itself already guards against overflow.

### Recommendation
Add an explicit upper bound check in `try_parse_request` or `try_handle_request` in `stackslib/src/net/api/getattachmentsinv.rs` that rejects any `page_index` whose `page_index.checked_mul(AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE)` would overflow (or simply cap `page_index` to a maximum sane value, e.g., derived from the maximum possible attachment count), returning `HttpBadRequest` instead of forwarding the value to `AtlasDB`. Additionally, verify/replace any raw `*`/`+` arithmetic in `AtlasDB::get_attachments_available_at_page_index` (`stackslib/src/net/atlas/db.rs`) with `checked_mul`/`checked_add`, returning a `db_error` on overflow rather than panicking or silently wrapping.

### Proof of Concept
Add a test in `stackslib/src/net/api/tests/getattachmentsinv.rs` that constructs a real `AtlasDB` (as existing tests in that file do), builds a `StacksHttpRequest::new_getattachmentsinv` with `pages_indexes = {u32::MAX}` and a valid `index_block_hash`, and drives it through `RPCGetAttachmentsInvRequestHandler::try_handle_request`. Assert that the call returns a controlled `HttpBadRequest`/`HttpNotFound` response rather than panicking; run this test under `cargo test` (debug/overflow-checked build) to detect a panic at the multiplication/addition site inside `AtlasDB::get_attachments_available_at_page_index` in `stackslib/src/net/atlas/db.rs`.

Note: due to index/tool limits, I could not directly inspect the body of `get_attachments_available_at_page_index` to confirm the exact overflow-triggering statement or whether a guard already exists; a Devin session with full file access would be needed to pinpoint the exact line and confirm exploitability before treating this as fully verified.
