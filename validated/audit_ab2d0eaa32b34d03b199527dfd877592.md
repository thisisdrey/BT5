### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign`/`BatchValidateSign` TVM precompiles enables memory-exhaustion DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` precompiled contracts, reachable from any smart contract via a `staticcall`/`call` to their precompile addresses, read an attacker-supplied "array length" word directly out of the call data and use it to size a `byte[][]` before any bound check is performed, when the `allowTvmSelfdestructRestriction` chain parameter is not active.

### Finding Description
`ValidateMultiSign.execute` and `BatchValidateSign.doExecute` decide which helper to call based on `VMConfig.allowTvmSelfdestructRestriction()`: [1](#0-0) 

When the flag is `true`, the code first reads `sigArraySize`/`addrArraySize` from `words[...]` and rejects it if it exceeds `MAX_SIZE` (5 for `ValidateMultiSign`, 16 for `BatchValidateSign`) before calling `extractSigArray`/`extractBytes32Array`.

However, when the flag is `false`, the bound check is skipped entirely and `extractBytesArray` / `extractBytes32Array` are invoked directly on the untrusted length: [2](#0-1) 

Both helpers do `int len = words[offset].intValueSafe(); byte[][] bytesArray = new byte[len][];` with **no upper bound whatsoever** on `len` before allocation — `len` is a raw 256-bit word from the calldata truncated to an `int`, so a caller can set it to `Integer.MAX_VALUE` (or any large positive value). Only *after* the array has already been allocated does the code check `signatures.length > MAX_SIZE` (`ValidateMultiSign`, line ~1076) or `cnt > MAX_SIZE` (`BatchValidateSign`, line ~1179) — too late, since the massive allocation (and potential `OutOfMemoryError`) has already occurred: [3](#0-2) 

This mirrors the Bitcoin Core INV-message bug class: a single attacker-controlled input field dictates the size of memory allocated by the node *before* the value is validated or bounded, letting an unprivileged party force large allocations cheaply.

### Impact Explanation
`new byte[len][]` for a large `len` (e.g. ~2^31-1) attempts to allocate an object-reference array many gigabytes in size on 64-bit JVMs. This can throw `OutOfMemoryError` inside the TVM execution path. Depending on where the OOM is thrown and how the surrounding executor/thread pool and JVM heap react, this can destabilize or crash the node process (all full nodes/witnesses that execute the transaction, i.e. every node on the network), which is a denial-of-service against chain liveness — consistent with the "node crash or halt" acceptance criterion.

### Likelihood Explanation
The precompiles are reachable by any account through a plain contract call with attacker-chosen calldata — no special privilege is required, matching the "unprivileged contract deployer/caller" scope. The vulnerable code path is only active when `VMConfig.allowTvmSelfdestructRestriction()` returns `false`, i.e., on any chain/network where the corresponding TIP/hard-fork chain parameter has not yet been activated (this is a proposal-gated flag per `DynamicPropertiesStore`/`ProposalUtil`). On such networks (e.g., private/test networks or a mainnet prior to that proposal's activation), the vulnerable branch is live and directly reachable by an ordinary transaction. I could not verify from the indexed code alone whether this proposal is already permanently activated and forced-true on TRON mainnet today; this needs to be confirmed against the live chain parameter state.

### Recommendation
Move the `sigArraySize`/`addrArraySize` (and the `len` bound check inside `extractBytesArray`/`extractBytes32Array`) validation to occur unconditionally, before any array allocation, regardless of `allowTvmSelfdestructRestriction`. Specifically, clamp/reject `len` against `MAX_SIZE` (or another sane hard cap) inside `extractBytesArray`/`extractBytes32Array` themselves, so the fix does not depend on caller code correctly ordering checks per feature flag.

### Proof of Concept
1. Craft calldata for `BatchValidateSign` (or `ValidateMultiSign`) where the word at the offset used as the "signature/address array length" (`words[1]`/`words[2]` for `BatchValidateSign`, `words[3]` for `ValidateMultiSign`) encodes a large positive integer such as `0x7FFFFFFF`.
2. Deploy/call a contract that invokes the precompile address for `batchvalidatesign`/`validatemultisign` with this calldata, on a network/chain state where `allowTvmSelfdestructRestriction` is not enabled.
3. Observe that `extractBytesArray`/`extractBytes32Array` executes `new byte[len][]` before any size validation, causing a very large heap allocation attempt / `OutOfMemoryError` during transaction execution on every node that processes the transaction.
