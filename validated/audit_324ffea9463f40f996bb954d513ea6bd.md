### Title
Unbounded blocking `/heartbeat` request permanently starves the single-threaded monitoring server - (File: stacks-signer/src/monitoring/server.rs)

### Summary
`MonitoringServer::heartbeat()` issues a blocking HTTP GET to the configured `stacks_node_origin` using a `reqwest::blocking::Client` created with no timeout. Because `main_loop()` processes requests synchronously on a single thread, a single unauthenticated `GET /heartbeat` request will hang forever (or for as long as the node is unreachable/slow), preventing any other client — including legitimate Prometheus scrapers — from getting a response from `/metrics`, `/info`, or `/`.

### Finding Description
The equality claimed is: "time bound on one `/heartbeat` request == a fixed timeout." This does not hold: the client is constructed with `reqwest::blocking::Client::new()` at [1](#0-0)  with no `.timeout(...)` builder call, so the default reqwest blocking client has no request timeout configured. `heartbeat()` then performs a fully synchronous `self.stacks_node_client.get(url).send()` at [2](#0-1)  which blocks the calling thread until the OS TCP stack gives up or the peer responds.

`main_loop()` is a single-threaded, sequential accept-and-handle loop: it calls `self.http_server.recv()` to get one request, dispatches synchronously, and only then loops back to receive the next request [3](#0-2) . The `/heartbeat` branch calls `self.heartbeat()` directly inline before responding [4](#0-3) . There is no worker pool, no per-request thread spawn, and no timeout guard anywhere in this file.

Any remote party that can reach the metrics port (which is explicitly a monitoring/scraping endpoint, not gated by any secret or auth check in this file) can send `GET /heartbeat`. If `stacks_node_origin` is unreachable, firewalled to a black hole, or simply slow, the outbound `send()` call blocks indefinitely (bounded only by OS-level TCP timeouts, which can be many minutes), and the entire monitoring server — including `/metrics` needed for alerting and `/info` — becomes unresponsive to all other callers for that duration.

### Impact Explanation
A single unauthenticated `GET /heartbeat` request can deny service to the monitoring endpoint for every other caller, matching the Critical "remote crash/unauthenticated DoS from few messages" category. This is a self-inflicted DoS on the signer operator's own observability plane: Prometheus scraping and health checks (`/metrics`, `/info`) silently stop working, which can mask signer misbehavior/downtime from operators. It is repeatable on every reconnect of the underlying node or whenever an attacker (or transient network condition) can keep the outbound connection to `stacks_node_origin` pending.

### Likelihood Explanation
The metrics port must be reachable by the attacker and `stacks_node_origin` must be unreachable/slow at the time of the request — a condition that can occur naturally (node restart, network partition, node under load) or that a network-adjacent attacker could induce by targeting the node's RPC port. No secret, authentication, or privileged role is required to hit `/heartbeat`; it costs the attacker a single TCP connection and one HTTP GET.

### Recommendation
Configure a bounded timeout on the `reqwest::blocking::Client` (e.g., `Client::builder().timeout(Duration::from_secs(N)).build()`) used for the heartbeat/node RPC calls, and/or handle each incoming monitoring request on its own thread (or move `heartbeat()`'s outbound call off the accept loop) so a stalled node connection cannot starve unrelated endpoints.

### Proof of Concept
Rust test: bind a `TcpListener` on a local port that accepts connections but never writes a response (simulating an unreachable/slow node). Construct a `MonitoringServer` with `stacks_node_origin` pointing at that listener. From one thread, send `GET /heartbeat` to the monitoring server (this call will block inside `heartbeat()`'s `send()`). From a second thread, concurrently send `GET /metrics` to the same server and assert it does not return within a bounded test deadline (e.g. 5 seconds) — demonstrating that the single-threaded `main_loop` is starved by the pending `/heartbeat` request, confirming the unbounded blocking fault at [2](#0-1) .

    pub fn main_loop(&mut self) -> Result<(), MonitoringError> {
        info!("{}: Starting Prometheus metrics server", self);
        loop {
            if let Err(err) = self.refresh_metrics() {
                error!("Monitoring: Error refreshing metrics: {:?}", err);
            }
            let request = match self.http_server.recv() {
                Ok(request) => request,
                Err(err) => {
                    error!("Monitoring: Error receiving request: {:?}", err);
                    return Err(MonitoringError::Terminated);
                }
            };

            debug!("{}: received request {}", self, request.url());

            if request.url() == "/metrics" {
                let response = HttpResponse::from_string(gather_metrics_string());
                request.respond(response).expect("Failed to send response");
                continue;
            }

            if request.url() == "/info" {
                request
                    .respond(HttpResponse::from_string(self.get_info_response()))
                    .expect("Failed to respond to request");
                continue;
            }

            // return 200 OK for "/"
            if request.url() == "/" {
                request
                    .respond(HttpResponse::from_string("OK"))
                    .expect("Failed to respond to request");
                continue;
            }

            // Run heartbeat check to test connection to the node
            if request.url() == "/heartbeat" {
                let (msg, status) = if self.heartbeat() {
                    ("OK", 200)
                } else {
                    ("Failed", 500)
                };
                request
                    .respond(HttpResponse::from_string(msg).with_status_code(status))
                    .expect("Failed to respond to request");
                continue;
            }

            // unknown request, return 404
            request
                .respond(HttpResponse::from_string("Not Found").with_status_code(404))
                .expect("Failed to respond to request");
        }
    }
