### Title
`Loans.disburse` reverts entirely and permanently strands investor principal if the borrower address cannot receive USDC (blacklist/incompatible receiver) - (File: `contracts/Loans.sol`)

### Summary
The C4 report shows that a single push-based native-asset transfer (`transferEth`) to a contract that cannot accept the payment reverts the entire calling function, causing loss of entitlements for the receiver. Tare's `Loans.disburse` has the same push-transfer root cause but for USDC: it performs a single unconditional `currency.safeTransfer(borrowers[loanId], netDisbursedAmount)` at the end of the function, and if that transfer fails (e.g., USDC blacklists the borrower, or the borrower address is otherwise incapable of receiving), the whole `disburse` call reverts, permanently blocking the loan from ever transitioning out of `FullyFunded`.

### Finding Description
`Loans._disburse` writes the ledger entries for the origination fee and cash movement and then performs the actual token transfer: [1](#0-0) 

This is invoked from the external `disburse` entrypoint, which is the only state transition from `FullyFunded` to `Active`: [2](#0-1) 

If `currency.safeTransfer(borrowers[loanId], ...)` reverts — which happens for USDC if the borrower address is blacklisted, or the borrower is later blacklisted between `create` and `disburse` — the entire `disburse` transaction reverts (ledger entries and status transition roll back together). This is functionally identical to the C4 finding's `transferEth`/`_burn` pattern: a single push-payment call embedded in a state-transition function that has no fallback path when the recipient cannot receive.

The recovery path is `updateBorrower`, which requires the new borrower to already be registered in the servicer's address book. This is itself an audit-documented "code smell" in this repository's own `pashov-ai-audit-report`: [3](#0-2) 

### Impact Explanation
Once `fund()` succeeds, the investor's full principal has already been pulled into the loan's `ACC_CASH` (`InvestorPrincipalPayable == UnfundedCommitment`). If `disburse` cannot complete because the borrower cannot receive USDC:
- The loan is permanently stuck at `FullyFunded` — it cannot reach `Active`, cannot originate interest/fee terms, and the originator cannot re-attempt disbursement to any other address without an out-of-band `updateBorrower` call from the servicer.
- Investor principal sits idle in `ACC_CASH` with no on-chain investor-initiated exit: `investorWithdraw` only distributes `ACC_INVESTOR_INTEREST_PAID`/`ACC_INVESTOR_PRINCIPAL_REPAID` balances, which are never populated pre-disbursement, so the investor has no unilateral recovery route.
- If the servicer is unavailable or unwilling to call `updateBorrower`, the funds are effectively locked — matching the allowed-impact class "Permanent or practically unrecoverable lock of USDC ... caused by an unprivileged path" (the borrower's own address falling out of USDC's good graces is not something the investor or originator controls).

### Likelihood Explanation
USDC blacklisting is a real, externally-triggerable condition (not attacker-crafted malicious contract code as with the ETH-receive case, but functionally equivalent: an address that legitimately cannot receive the token). Any loan whose `borrowers[loanId]` address becomes blacklisted between `create()`/`fund()` and `disburse()` — or was already blacklisted and slipped through address-book validation — hits this path deterministically. No attacker action is required to trigger it, and it is reachable purely through normal operational timing.

### Recommendation
Do not let a failed borrower payout revert the entire `disburse` ledger update. Options:
- Split ledger settlement from token movement: finalize the ledger entries/status transition unconditionally, and route the actual USDC transfer through a pull-based escrow (e.g., credit an internal claimable balance for the borrower) so a blacklisted/incompatible borrower does not block loan disbursement.
- Alternatively, wrap the `safeTransfer` in a try/catch (or use a low-level call and check success) and, on failure, escrow the funds to a claimable mapping keyed by `borrowers[loanId]`, emitting an event so the servicer can redirect the payout via `updateBorrower` without leaving investor capital in limbo.
- At minimum, provide an unprivileged (or investor-triggerable) fallback that reclaims the parked `ACC_CASH` back to the investor if disbursement cannot be completed within a bounded time, so the funds aren't solely dependent on servicer responsiveness.

### Proof of Concept
1. Deploy `Loans` with a mock USDC token that supports an address blacklist (mirroring real USDC `isBlacklisted` semantics).
2. Originator calls `create(borrower, investor, servicer, originator, principal, timestamp)`.
3. Investor calls `fund(loanId, principal, timestamp, ref)` — USDC moves from investor into the contract's `ACC_CASH`; loan status becomes `FullyFunded`.
4. Blacklist `borrower` on the mock USDC token.
5. Originator calls `disburse(loanId, netDisbursedAmount, ...)`.
6. Observe: `currency.safeTransfer(borrowers[loanId], ...)` at [4](#0-3) 
reverts, causing the entire `disburse` call (including the ledger entries and status transition) to revert.
7. Loan remains `FullyFunded` indefinitely; investor's principal remains parked in `ACC_CASH` with no on-chain investor-initiated withdrawal path until the servicer calls `updateBorrower` to re-point `borrowers[loanId]`.
