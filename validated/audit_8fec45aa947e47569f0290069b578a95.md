## Analysis

The CVG bug class is: **two different code paths compute the same conceptual quantity via different orders of division/multiplication**, so an aggregate/tracked total silently diverges (by rounding) from what individual per-user calculations yield, letting a participant harvest the accumulated rounding "dust" through repeated small operations.

The strongest analog reachable from a single signed transaction in java-tron is in the **TRC10/TRX resource delegation "usage transfer" logic** used by `DelegateResourceContract`/`UnDelegateResourceContract` (both the Wallet/actuator path and the TVM native-contract path). When bandwidth/energy is un-delegated, the amount of "usage" (netUsage/energyUsage) that must move from receiver back to owner is computed independently on each side using floating‑point, non‑matching formulas, rather than one canonical formula applied consistently — exactly the divergent-formula pattern in the report.

### Title
Inconsistent floating-point usage-transfer formulas in resource delegation allow bandwidth/energy accounting drift (potential unbacked resource) - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java)

### Summary
`UnDelegateResourceActuator`/`UnDelegateResourceProcessor` (and their `DelegateResource` counterparts) compute the amount of consumed bandwidth/energy ("usage") that must be transferred between accounts using two independently derived `double`-based formulas that are supposed to represent the same proportional share of a global resource pool, but are not order-of-operations equivalent to how the pool's totals (`TotalNetWeight`/`TotalEnergyWeight`) are tracked.

### Finding Description
In `UnDelegateResourceProcessor.execute` the receiver-side "how much usage should move" value is computed two different ways and the minimum is taken: [1](#0-0) 

```java
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * dynamicStore.getTotalNetLimit() / repo.getTotalNetWeight());
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
transferUsage = min(unDelegateMaxUsage, transferUsage, VMConfig.disableJavaLangMath());
```

`unDelegateMaxUsage` is derived from the *global* weight/limit ratio (mirrors `calculateGlobalNetLimitV2`), while `transferUsage` is derived from the *account-local* usage/frozen-balance ratio. These are two structurally different formulas meant to bound the same quantity, both truncated via `(long)` cast on `double` arithmetic, with no shared canonical computation. The same pattern repeats for energy and in the classic actuator path: [2](#0-1) 

The owner side then simply adds whatever `transferUsage` value was derived to its own usage counter via `unDelegateIncrease`, without re-deriving or cross-checking it against the receiver's actual consumed usage: [3](#0-2) 

Because `min(unDelegateMaxUsage, transferUsage)` mixes two independently-rounded double computations, the value transferred is not guaranteed to equal the value actually deducted from the receiver's tracked usage nor to correctly reconstruct the owner's proportional share, particularly at small/edge balances where `(long)` truncation of `double` division dominates. This mirrors the CVG root cause: the "total" (global weight/limit ratio bound) and the "individual" (per-account proportional formula) are computed via non-identical formulas that can diverge by rounding.

Notably, java-tron's own test suite documents an almost identical bug class being found and partially hardened elsewhere in the same resource subsystem — proving this exact rounding-divergence pattern is a known, real issue class in this codebase: [4](#0-3) 

This test explicitly shows that the legacy "floor-then-multiply" formula and a "multiply-then-floor" formula give different results (25 vs 37) for the same conceptual quantity — the same class of bug as CVG's `ysTotalAmount1` vs `ysTotalAmount2`. A `BigInteger`-based "hardened" path (`calculateGlobalLimitV2`, `unDelegateIncreaseV2`'s hardened branch) was introduced to fix this for some call sites, gated by the `AllowHardenResourceCalculation` proposal parameter, but the `unDelegateMaxUsage`/`transferUsage` computation inside `UnDelegateResourceProcessor.execute` and `UnDelegateResourceActuator.execute` was **not** migrated to the hardened/BigInteger path and still relies on raw, unguarded `double` arithmetic with two divergent formulas.

### Impact Explanation
If the two divergent formulas allow `transferUsage` to differ from the amount actually needed to keep the receiver's and owner's tracked usage in balance with the true global bandwidth/energy pool, repeated delegate/undelegate cycles by a user (analogous to Alice repeatedly locking small amounts in the CVG report) could accumulate a persistent discrepancy in tracked usage, i.e., an account paying less for bandwidth/energy consumption than it is entitled to, or vice versa — a form of resource accounting drift that is the TRON equivalent of "unbacked balance" (excess free bandwidth/energy not backed by frozen TRX weight, or lost accounted capacity for a legitimate delegator).

### Likelihood Explanation
The `DelegateResourceContract`/`UnDelegateResourceContract` are ordinary, unprivileged, broadcastable transactions and TVM native contract operations reachable by any account (delegator/delegatee), requiring only that the attacker be the delegator/receiver of the resource — no special privilege needed, similar to "Alice is the only YS locker" needing only ordinary transaction rights.

### Recommendation
Unify `unDelegateMaxUsage` and `transferUsage` computation to use a single canonical, `BigInteger`-based formula (as already done for `calculateGlobalLimitV2` and the hardened branch of `unDelegateIncreaseV2`), and extend `AllowHardenResourceCalculation` (or make it unconditional) to cover the usage-transfer calculations in `UnDelegateResourceProcessor.execute` and `UnDelegateResourceActuator.execute` / `DelegateResourceActuator` validate logic, eliminating the two-different-formula divergence.

### Proof of Concept
A concrete PoC requires constructing account states where `unDelegateBalance`, `getAllFrozenBalanceForBandwidth()`, `TotalNetLimit`, and `TotalNetWeight` combine so that `(double) unDelegateBalance / TRX_PRECISION * TotalNetLimit / TotalNetWeight` and `receiverCapsule.getNetUsage() * ((double) unDelegateBalance / receiverCapsule.getAllFrozenBalanceForBandwidth())` truncate to different integer values under repeated small delegate/undelegate operations, similar to the CVG PoC's chosen `lockDuration=64, amount=15, ysPercentage=10` parameters that maximize the rounding gap; this requires deeper numeric fuzzing against `UnDelegateResourceProcessor` to confirm an exploitable persistent drift, which is beyond what can be confirmed via static code review alone.

    long remainOwnerWindowSize = owner.getWindowSize(resourceCode);
    long remainReceiverWindowSize = receiver.getWindowSize(resourceCode);
    remainOwnerWindowSize = remainOwnerWindowSize < 0 ? 0 : remainOwnerWindowSize;
    remainReceiverWindowSize = remainReceiverWindowSize < 0 ? 0 : remainReceiverWindowSize;

    long newOwnerUsage = ownerUsage + transferUsage;
    // mean ownerUsage == 0 and transferUsage == 0
