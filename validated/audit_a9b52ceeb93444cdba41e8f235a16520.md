### Title
Unbounded growth of a victim's `DelegatedResourceAccountIndexCapsule` list via unprivileged, low-cost delegate transactions - ([File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java])

### Summary
The OpenQ finding is a class of bug where an unprivileged party can pollute a *victim-owned*, list-type piece of state with attacker-controlled, low-value entries because no size limit is enforced, degrading or blocking future legitimate use of that state. The closest reachable analog in java-tron is `FreezeBalanceActuator`'s legacy (non-optimized) delegation path, which appends to a receiver's `DelegatedResourceAccountIndexCapsule.fromAccountsList`/`toAccountsList` with no cap on size, and the entry can be created by *any* other account, not the victim.

### Finding Description
When `DynamicPropertiesStore.supportAllowDelegateOptimization()` is `false` (the legacy resource-delegation model), `FreezeBalanceActuator.delegateResource()` unconditionally mutates the *receiver's* `DelegatedResourceAccountIndexCapsule`: [1](#0-0) 

Specifically, for every call it does a linear `contains()` check and then `addFromAccount`, with **no upper bound** on the list length: [2](#0-1) 

The `DelegatedResourceAccountIndexCapsule` itself exposes unbounded add operations with no size validation anywhere in the class: [3](#0-2) 

Because `receiverAddress` is fully attacker-chosen and only a minimal frozen amount is required to trigger delegation, an attacker can create a large number of throwaway accounts, freeze the minimum amount from each with delegation enabled, and target the same victim address repeatedly. Each such transaction appends one more entry to the *victim's* `fromAccountsList` in `DelegatedResourceAccountIndexStore`, entirely without the victim's consent or any participation, mirroring the OpenQ pattern where an attacker griefs a shared/victim-owned bounded structure by filling it with dust entries from unrelated addresses.

Unlike the OpenQ bug (which has an explicit `TOKEN_ADDRESS_LIMIT`), java-tron enforces **no limit at all** on this particular list, which is arguably worse: the structure can grow without bound as long as attackers are willing to pay the minimal freeze cost per entry.

### Impact Explanation
As the victim's `fromAccountsList` grows large:
- Every subsequent delegate/undelegate/unfreeze operation touching that account performs an `O(n)` `contains()` scan and a full list-rebuild (`removeFromAccount`) over an attacker-inflated list, as seen in the `UnfreezeBalanceActuator`/`DelegateResourceActuator` flows that read and rewrite `DelegatedResourceAccountIndexCapsule`.
- The capsule is fully deserialized/reserialized on every read/write of the account's delegation index (`DelegatedResourceAccountIndexStore.get`/`put`), so CPU and memory cost of processing any transaction touching that account scales with the attacker-inflated list size.
- Public API endpoints that return this data (e.g. `GetDelegatedResourceAccountIndexServlet` / `getDelegatedResourceAccountIndex`) will serialize and return arbitrarily large protobuf lists back over HTTP/gRPC, which can be used to degrade full-node/API responsiveness for that account.

This is reachable from a single signed `FreezeBalanceContract` transaction issued by any unprivileged account against any chosen receiver address, and can be repeated cheaply to keep growing the victim's list, resulting in a resource-exhaustion style denial of service against normal delegation/unfreeze operations for the targeted account and against API consumers querying it.

### Likelihood Explanation
Likelihood is moderate-to-high in networks/configurations where `supportAllowDelegateOptimization` is not yet enabled (legacy delegation still active), since the only cost to the attacker is the minimum freeze amount and standard transaction fees, and the receiver address is fully attacker-controlled with no whitelist or consent check on the receiving side.

### Recommendation
Enforce a maximum size on `DelegatedResourceAccountIndexCapsule.fromAccountsList`/`toAccountsList` (similar in spirit to `MAX_ACTIVE_ORDER_NUM` used in `MarketSellAssetActuator`) and validate it in `FreezeBalanceActuator.validate()`/`delegateResource()` before appending new entries, or migrate fully to the optimized (`V2`) delegation index model which avoids storing an unbounded list per account.

### Proof of Concept
1. Attacker creates `N` throwaway accounts (minimal TRX needed to freeze the minimum bandwidth/energy amount, e.g. 1 TRX).
2. From each throwaway account, attacker sends a `FreezeBalanceContract` with `receiver_address` set to the victim's address and `resource` delegated (legacy model, `supportAllowDelegateOptimization() == false`).
3. Each transaction triggers `FreezeBalanceActuator.delegateResource()`, which appends the attacker address to the victim's `DelegatedResourceAccountIndexCapsule.fromAccountsList` with no cap.
4. Repeating this for large `N` inflates the victim's index capsule; subsequent `UnfreezeBalanceActuator`/`DelegateResourceActuator` calls on the victim, and public queries via `GetDelegatedResourceAccountIndexServlet`, become increasingly expensive, degrading service for the victim and API consumers.
