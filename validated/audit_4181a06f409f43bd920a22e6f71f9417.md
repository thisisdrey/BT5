### Title
Dust deposit/transfer fills `MAX_TOKENS_PER_USER` account list, DoSing victim's deposits, mints, and integrations — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The per-account token lists (`depositTokensOfAccount`, `debtTokensOfAccount`) are capped at `MAX_TOKENS_PER_USER = 30` and the cap is enforced inside `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`, which revert with `UserReachedMaxTokens` when the combined length reaches 30 [1](#0-0) . An attacker can force entries into a victim's list with unilateral calls — `deposit(amount_, onBehalfOf_)` credits any address [2](#0-1)  and `transfer`/`transferFrom` of unlocked dust adds the token to the recipient's list [3](#0-2) . Once the victim's list is full, every code path that adds a token on a `0 → nonzero` balance transition reverts: first-time deposits, first-time `issue`, `seize` into the victim, and leverage callbacks. This mirrors the CVE bug class: an attacker-controlled quota-exceeded error path bricks subsequent state transitions (liveness / freezing).

### Finding Description
- `DepositToken._mint` pushes the token into the recipient's account list on first receipt via `pool.addToDepositTokensOfAccount(account_)` [4](#0-3) .
- `DepositToken._transfer` does the same for any recipient [5](#0-4) , and `transfer`/`transferFrom`/`seize` all route through it [6](#0-5) .
- `DebtToken._mint` pushes debt tokens via `pool.addToDebtTokensOfAccount(account_)` [7](#0-6) .
- Both Pool entry points are permissionless (callable by any registered deposit/debt token, i.e., indirectly by anyone) and share a single 30-slot budget across deposit + debt tokens [8](#0-7) .
- Attack (unprivileged EOA): for each of N distinct `DepositToken`s registered in the pool, the attacker either (a) calls `depositToken.transfer(victim, dust)` after depositing dust themselves, or (b) calls `depositToken.deposit(dustUnderlying, victim)` — both add the token to `victim`'s list with no consent. Repeating across deposit tokens fills the list to 30.
- Consequence: victim's `deposit` into any not-yet-held collateral reverts (the whole tx rolls back after `_mint` → `addToDepositTokensOfAccount` reverts); `issue`/`flashIssue` of any not-yet-held synthetic reverts via `DebtToken._mint`; `seize`/`transfer` *to* the victim reverts. Because the revert propagates through the whole transaction, there is no partial-state escape.

### Impact Explanation
Temporary freezing of funds / liveness failure. An EOA victim can recover by transferring dust entries out (`transfer` removes the sender's entry when balance hits 0 [9](#0-8) ), but a *contract* victim that has no function to move msdTOKENs — e.g., a vault, multisig-without-arbitrary-calls, or an integration contract holding collateral via `onBehalfOf_` — cannot clear its own list and is permanently bricked: no new deposits, no new debt issuance, and any protocol action requiring a new token entry (including liquidation seizes crediting it) reverts. This satisfies the "permanent freezing of funds / liveness" acceptance bar for contract victims and "temporary freezing" for EOAs.

### Likelihood Explanation
Fully attacker-reachable: requires only public `deposit`/`transfer` calls plus dust of each underlying; no privileged roles, no oracle manipulation, no governance. Cost is bounded by ~30 dust deposits across registered collateral types. The only mitigation is that `DebtToken` is non-transferable [10](#0-9) , so debt-list slots can't be force-filled — but deposit slots alone suffice to exhaust the shared 30-entry budget since the check sums both lists [11](#0-10) .

### Recommendation
Make list addition non-reverting for unsolicited balance changes: (a) skip the `add` revert inside `addTo*TokensOfAccount` when the cap is reached and instead revert the caller selectively, or (b) require `recipient_` opt-in for transfers (`transferFrom`-only receivership), or (c) revert the cap check only for the *account initiating* the action (`_msgSender() == account_`) so that receiving dust as a third party cannot exhaust the quota.

### Proof of Concept
Hardhat sketch (fork or unit):

```ts
// pool has >=30 registered DepositTokens: dt[0..29]
for (let i = 0; i < 30; i++) {
  // attacker deposits dust and transfers 1 wei of msdToken to victim
  await underlying[i].approve(dt[i].address, 1);
  await dt[i].deposit(1, attacker.address);
  await dt[i].transfer(victim.address, 1); // adds dt[i] to victim's list
}
// victim's list is now full:
await expect(dt[0].deposit(1e6, victim.address))      // new collateral? already in list — ok
await expect(newDt.deposit(1e6, victim.address))       // any new deposit token → UserReachedMaxTokens
await expect(debtTokenX.connect(victim).issue(1e18, victim.address)) // first issue → UserReachedMaxTokens
// victim EOA recovers via dt[i].transfer(dustOut); contract victim without transfer fn is permanently bricked
```
