### Title
Use of Uninitialized Field After Failed Protobuf Parse Causes NullPointerException in `ExchangeCapsule` — Reachable via `GetExchangeById` API (JSON-RPC/HTTP/gRPC) — (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeCapsule(byte[] data)` parses a stored `Exchange` protobuf message and, on `InvalidProtocolBufferException`, only logs the error and leaves the `exchange` field uninitialized (`null`) instead of throwing [1](#0-0) . `ExchangeStore.get(byte[] key)` unconditionally constructs an `ExchangeCapsule` from whatever bytes are found (or even from a null/empty value if the underlying `revokingDB.get` doesn't throw), and returns it to the caller without checking whether the internal `exchange` field parsed successfully [2](#0-1) . `Wallet.getExchangeById` treats a non-null `ExchangeCapsule` as valid and immediately calls `getInstance()` [3](#0-2) , which simply returns the (possibly null) `exchange` field [4](#0-3) . This is the same bug class as CVE-2024-32878: a parse routine leaves a variable in an uninitialized/null state on malformed input, and a caller later dereferences it without validation, producing a crash.

### Finding Description
This pattern — catching `InvalidProtocolBufferException` in a capsule constructor and only logging, leaving the wrapped protobuf object `null` — is repeated across many capsule classes (`AbiCapsule`, `AccountCapsule`, `AssetIssueCapsule`, `ContractCapsule`, `ContractStateCapsule`, `MarketOrderCapsule`, `MarketAccountOrderCapsule`, `MarketPriceCapsule`, `ProposalCapsule`, `IncrementalMerkleTreeCapsule`, `IncrementalMerkleVoucherCapsule`, `PedersenHashCapsule`, `ReceiveDescriptionCapsule`), in contrast to `TransactionCapsule`, which correctly throws `BadItemException` on parse failure [5](#0-4) .

`ExchangeStore` is the clearest example reachable from an unprivileged API request: its `get()` override never validates that the capsule actually contains valid data before returning it to callers [2](#0-1) . Once such a capsule reaches `Wallet.getExchangeById`, the non-null check on the `ExchangeCapsule` object is insufficient — it doesn't check whether `getInstance()` returns null before returning it through the gRPC/HTTP/PBFT/Solidity query paths (`GetExchangeByIdServlet`, `RpcApiService.getExchangeById`, PBFT and Solidity variants) [6](#0-5) [7](#0-6) . Downstream, `getInstance()` result is serialized (e.g. via `JsonFormat.printToString` or protobuf response marshaling), which dereferences fields on a null `Exchange` object.

### Impact Explanation
If an `ExchangeCapsule`'s internal `exchange` field is null (e.g., data corruption, a partial/incompatible write, or any code path that stores non-well-formed bytes under an exchange key), any subsequent read via `GetExchangeById` (HTTP `/wallet/getexchangebyid`, `/walletsolidity/getexchangebyid`, `/walletpbft/getexchangebyid`, and the gRPC `GetExchangeById` RPC) throws an unhandled `NullPointerException` while serializing the response. Because there is no null-check between `ExchangeStore.get()` and consumption of `getInstance()`, this satisfies the "API the node can no longer serve" criterion — repeated invalid access would degrade or crash the query-handling path for that endpoint, and the same defensive gap (silently swallowing parse failures instead of surfacing them) exists across numerous other capsules used in actuator validate/execute paths (`ContractCapsule`, `ProposalCapsule`, `MarketOrderCapsule`), amplifying the risk that a single malformed record silently propagates as `null` deep into contract execution logic rather than failing fast.

### Likelihood Explanation
Likelihood is limited by the fact that, under normal operation, every byte array stored via `ExchangeStore.put()` (and analogous stores) is generated internally via protobuf builders and should always parse successfully — so the failure path is not directly triggerable by a single crafted transaction in the current codebase as I was able to verify. I could not find a concrete external write primitive that lets an unprivileged transaction/API caller inject non-well-formed bytes directly into the `exchange` (or similar) DB column, which is necessary to fully weaponize this into remote, on-demand crashes.

### Recommendation
Change `ExchangeCapsule(byte[] data)` (and the equivalent constructors in `AbiCapsule`, `AccountCapsule`, `AssetIssueCapsule`, `ContractCapsule`, `ContractStateCapsule`, `MarketOrderCapsule`, `MarketAccountOrderCapsule`, `MarketPriceCapsule`, `ProposalCapsule`, `IncrementalMerkleTreeCapsule`, `IncrementalMerkleVoucherCapsule`, `PedersenHashCapsule`, `ReceiveDescriptionCapsule`) to throw a checked exception (e.g. `BadItemException`) on `InvalidProtocolBufferException`, matching `TransactionCapsule`'s behavior, and have callers (`ExchangeStore.get`, `Wallet.getExchangeById`, etc.) propagate/handle that exception instead of returning an object whose `getInstance()` can be null.

### Proof of Concept
Not independently verifiable in this repo without confirmation of a write path that injects malformed bytes into the `ExchangeStore` (or sibling stores) reachable by an unprivileged caller — I was unable to locate one within the scope investigated. The reachable, provable defect is the missing null/validity check between deserialization failure and consumption, demonstrated at: [1](#0-0) [2](#0-1) [3](#0-2)
