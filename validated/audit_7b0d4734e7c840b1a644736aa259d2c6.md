### Title
Unsynchronized shared `AccountStateCallBack.trie` mutation between block generation and block application causes a `TrieImpl` race condition - (File: framework/src/main/java/org/tron/core/db/accountstate/callback/AccountStateCallBack.java)

### Summary
The reported go-ethereum fix addressed a race condition where a `ZktrieTracer` instance's internal state was mutated by more than one execution path without synchronization, corrupting trie state or crashing the node. java-tron has a structurally identical pattern: the singleton Spring bean `AccountStateCallBack` holds one mutable `TrieImpl trie` field that is written to from two independent, unsynchronized code paths in `Manager` — self block production (`generateBlock`) and network block application (`pushBlock`/`processBlock`) — allowing concurrent, unguarded mutation of the same trie's internal node tree.

### Finding Description
`AccountStateCallBack` is a Spring singleton (`@Component`) with an instance field `trie` of type `TrieImpl` [1](#0-0) . Its lifecycle methods (`preExecute`, `preExeTrans`, `exeTransFinish`, `deleteAccount`, `executePushFinish`, `executeGenerateFinish`) directly call `trie.put(...)`, `trie.delete(...)`, and `trie.getRootHash()` on this shared instance [2](#0-1) [3](#0-2) .

`TrieImpl` itself performs unsynchronized, non-atomic mutation of its internal `Node` tree (`children[]`, `dirty`, `hash` fields) on `insert`/`delete`/`encode`, and even dispatches sub-tree hashing to a shared static `ExecutorService` [4](#0-3) [5](#0-4) . None of these operations are guarded by locks — they assume single-threaded, sequential access to one `TrieImpl` instance.

The `accountStateCallBack` singleton is invoked from two independent call sites in `Manager`:
- `pushBlock()` (network/self block application), which is wrapped in `synchronized (this)` [6](#0-5) , subsequently invoking `processBlock()` which drives `accountStateCallBack.preExecute/preExeTrans/exeTransFinish/executePushFinish` sequentially for every transaction in the block [7](#0-6) .
- `generateBlock()` (local block production, run from the witness/miner loop on a separate thread), which calls `accountStateCallBack.preExecute(blockCapsule)` and then `preExeTrans()`/`exeTransFinish()` per packed transaction — but this method is **not** wrapped in `synchronized (this)` [8](#0-7) [9](#0-8) .

Because `pushBlock()`'s lock is only acquired on the `pushBlock` code path and `generateBlock()` has no equivalent guard, a witness node that is producing its own block via `generateBlock()` while concurrently receiving and applying a peer's block via `pushBlock()`/`processBlock()` on another thread can call into `accountStateCallBack` from two threads at once, both mutating the same `trie` instance's node graph without synchronization.

### Impact Explanation
Concurrent unsynchronized mutation of the shared `TrieImpl` node tree can:
- Corrupt in-memory `Node` state (`children[]`, `dirty`, `hash`), causing internal assertion failures (`assert getType() == NodeType.BranchNode`) or `ClassCastException`/`NullPointerException` during trie traversal/encoding, crashing the witness or block-processing thread (node crash / DoS).
- Produce an incorrect computed `accountStateRoot`, which is compared against the block header's declared root in `executePushFinish()`; a mismatch throws `BadBlockException` [10](#0-9) , causing legitimate blocks to be rejected and potentially halting block application for nodes with `allowAccountStateRoot` enabled.

This falls into the permitted "block application in Manager" analog category. This feature is gated behind the `allowAccountStateRoot` dynamic property (checked via `chainBaseManager.getDynamicPropertiesStore().allowAccountStateRoot()`), so exploitability depends on whether that flag is enabled on the target network/node — I could not verify its default/mainnet status from the available code.

### Likelihood Explanation
Likelihood is timing-dependent rather than trivially/always reachable: it requires (a) `allowAccountStateRoot` to be active, and (b) the witness's own `generateBlock()` execution to overlap in time with a `pushBlock()` call from block reception. Since witness block production and P2P block reception are driven by separate threads in normal node operation, and only `pushBlock()` — not `generateBlock()` — takes the `synchronized (this)` lock on `Manager`, this overlap is plausible during normal network operation without any attacker action beyond broadcasting a competing block at the right moment, but is not guaranteed on every block.

### Recommendation
Serialize access to `accountStateCallBack` across `generateBlock()` and `pushBlock()`/`processBlock()`, e.g., by having `generateBlock()` acquire the same lock object (`synchronized (this)` or a dedicated lock) used by `pushBlock()`, or by making the `AccountStateCallBack.trie` field access itself thread-safe (e.g., guarding all its lifecycle methods with an internal lock). Additionally, audit `TrieImpl` to ensure a single instance is never accessed concurrently from multiple threads.

### Proof of Concept
I could not construct a runnable, deterministic PoC without execution/environment access — the race requires precise thread interleaving between the witness's block-production thread (`generateBlock`, unsynchronized) and the network block-application thread (`pushBlock`, synchronized on a different guard scope), both invoking the shared `accountStateCallBack` singleton. This is a structural/code-level finding based on the absence of common locking between the two call paths; confirming actual triggerability under production thread scheduling would require a running multi-threaded testnet or unit test harness with `allowAccountStateRoot` enabled, which is outside the scope of static code review here.

  public void put(byte[] key, byte[] value) {
    TrieKey k = TrieKey.fromNormal(key);
    if (root == null) {
      if (value != null && value.length > 0) {
        root = new Node(k, value);
      }
    } else {
      if (value == null || value.length == 0) {
        root = delete(root, k);
      } else {
        root = insert(root, k, value);
      }
    }
  }

  private Node insert(Node n, TrieKey k, Object nodeOrValue) {
    NodeType type = n.getType();
    if (type == NodeType.BranchNode) {
      if (k.isEmpty()) {
        return n.branchNodeSetValue((byte[]) nodeOrValue);
      }
      Node childNode = n.branchNodeGetChild(k.getHex(0));
      if (childNode != null) {
        return n.branchNodeSetChild(k.getHex(0), insert(childNode, k.shift(1), nodeOrValue));
      } else {
        TrieKey childKey = k.shift(1);
        Node newChildNode;
        if (!childKey.isEmpty()) {
          newChildNode = new Node(childKey, nodeOrValue);
        } else {
          newChildNode = nodeOrValue instanceof Node
              ? (Node) nodeOrValue : new Node(childKey, nodeOrValue);
        }
        return n.branchNodeSetChild(k.getHex(0), newChildNode);
      }
    } else {
      TrieKey currentNodeKey = n.kvNodeGetKey();
      TrieKey commonPrefix = k.getCommonPrefix(currentNodeKey);
      // NOTE: equals(k) MUST precede isEmpty(). They overlap only when both k and
      // currentNodeKey are empty (duplicate put on a fully-split KV leaf); in that
      // case the correct behavior is an in-place value update, not conversion to
      // a BranchNode. Swapping the order corrupts the trie structure. See #6608.
      if (commonPrefix.equals(k)) {
        return n.kvNodeSetValueOrNode(nodeOrValue);
      } else if (commonPrefix.isEmpty()) {
        Node newBranchNode = new Node();
        insert(newBranchNode, currentNodeKey, n.kvNodeGetValueOrNode());
        insert(newBranchNode, k, nodeOrValue);
        n.dispose();
        return newBranchNode;
      } else if (commonPrefix.equals(currentNodeKey)) {
        insert(n.kvNodeGetChildNode(), k.shift(commonPrefix.getLength()), nodeOrValue);
        return n.invalidate();
      } else {
        Node newBranchNode = new Node();
        Node newKvNode = new Node(commonPrefix, newBranchNode);
        // TODO can be optimized
        insert(newKvNode, currentNodeKey, n.kvNodeGetValueOrNode());
        insert(newKvNode, k, nodeOrValue);
        n.dispose();
        return newKvNode;
      }
    }
  }
