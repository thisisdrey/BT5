## Title
Witness reward-per-vote (VI) accumulation permanently drops block/tx-fee rewards earned while a witness's per-cycle vote count is zero - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`, `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
java-tron's post-`allowChangeDelegation` witness reward model is a fork of the same "reward-per-token accumulator" pattern the Sherlock report describes for `VirtualStakingRewards`: rewards are minted into a per-cycle bucket and then converted into a cumulative per-vote index (`Vi`) that voters later diff to compute their share. Exactly like the reported issue - where rewards accrued while `totalSupply == 0` (no stakers yet) are silently dropped because the accumulator is only advanced when there is at least one participant - java-tron's `accumulateWitnessVi` skips the delta-Vi accumulation whenever a witness's vote count for that cycle is `0`, even though real reward value was already credited to that witness/cycle via `addReward`. That reward amount is never folded into `Vi` and can never be attributed to any voter, in any future cycle.

### Finding Description
Every block, `Manager.payReward()` credits the producing witness with a block reward and (if enabled) a transaction-fee-pool reward: [1](#0-0) 

These calls flow into `MortgageService.payReward()`, which stores the value keyed by `(cycle, witnessAddress)`: [2](#0-1) 

which ultimately persists into `DelegationStore.addReward(cycle, address, value)`: [3](#0-2) 

At every maintenance cycle (invoked from block application through `MaintenanceManager.doMaintenance()`, itself called from `MaintenanceManager.applyBlock()` during consensus block application), the accumulated per-cycle reward for every witness is folded into a cumulative reward-per-vote index `Vi`: [4](#0-3) 

The actual accumulation logic is: [5](#0-4) 

The bug: `voteCount` passed in is `witness.getVoteCount()` at maintenance time - the witness's *current* total vote count for that cycle. If a witness accrued a nonzero `reward` for the cycle (it produced blocks and/or received tx-fee-pool share) but its vote count for that cycle is `0` (e.g. a newly-added witness that has not yet received any votes, or a witness whose voters have withdrawn/cleared all votes for that cycle), the branch `if (reward == 0 || voteCount == 0)` is taken and the function *only forwards the previous `Vi`* - the delta corresponding to that cycle's reward is never computed or added anywhere.

This is precisely the reported bug-class: the `notifyRewardAmount`-style "period accrues from time X but the reward accumulator is not advanced until a participant exists (Y), so the accrued value between X and Y is unrecoverable" is mirrored here as "reward money accrues for cycle C into `delegationStore.reward(C, witness)`, but because `voteCount(C, witness) == 0`, the delta is never merged into `Vi`, so no past, present or future voter diff (`endVi - beginVi`, used identically in `MortgageService.computeReward` and `VoteRewardUtil.computeReward`) can ever recover it." [6](#0-5) [7](#0-6) 

Both consumers of `Vi` only ever look at `endVi - beginVi`; there is no other path that re-attributes a "skipped" cycle's reward once vote count becomes nonzero again later. The raw reward value written by `addReward(cycle, witnessAddress, value)` for that specific zero-vote cycle is orphaned in the `delegation` store forever - it is read only inside `accumulateWitnessVi`/`getReward`, and once that function chooses the "forward previous Vi" branch, that reward number is never consulted again.

### Impact Explanation
Whenever an active, block-producing witness has zero recorded votes in a given maintenance cycle, all TRX reward value that would have been distributable to voters for that cycle (block reward share and, if `supportTransactionFeePool` is enabled, tx-fee-pool share) is permanently unattributable - none of the witness's voters can ever claim it via `withdrawReward`/`queryReward`, and there is no compensating mechanism (unlike the naive "next `notifyRewardAmount` absorbs it" workaround discussed in the report, java-tron has no equivalent fallback at all: the value is not re-added to any subsequent cycle's bucket). This is a permanent freezing/loss of protocol-level reward funds that legitimately belongs to future voters of that witness, satisfying the "permanent freezing of funds" impact bar. It requires no attacker privilege - it happens naturally whenever a witness is freshly elected/added, or when all its voters clear their votes for exactly one cycle while the witness still produces blocks.

### Likelihood Explanation
This condition is reachable purely through ordinary, unprivileged protocol operation: any account can call the vote/unvote actuators (or the TVM `VoteWitnessContract`/`clearVote` native contracts) to move votes such that a witness's vote count for the *current* cycle transiently becomes `0` while it still produces blocks and earns block/tx-fee rewards (which happen automatically once per block regardless of vote count, see `Manager.payReward`). It is also guaranteed to occur for every witness's very first active cycle before any voter's vote registers in `delegationStore.setWitnessVote` for that specific cycle. `MaintenanceManager.doMaintenance()` runs automatically at every maintenance boundary as part of ordinary block application (`Manager.processBlock` → `consensus.applyBlock` → `MaintenanceManager.applyBlock` → `doMaintenance`), so the vulnerable code path executes unconditionally on livenet whenever `useNewRewardAlgorithm()` is enabled - no special transaction or malicious actor is required.

### Recommendation
Do not silently "forward" `Vi` when `voteCount == 0` but `reward > 0`. Options:
- Carry the un-attributable reward forward into the next cycle's `reward` bucket for that witness (`addReward(cycle+1, address, reward)`) instead of discarding it, so it is redistributed once vote count becomes nonzero again, analogous to rolling unallocated Synthetix rewards into the next `notifyRewardAmount` period.
- Alternatively, attribute the reward to the brokerage/self-vote allowance for that witness (similar to how `MortgageService.payReward` already routes brokerage) rather than dropping it when there is no votable base.

### Proof of Concept
1. A witness `W` is newly added to `WitnessStore` (or all voters call `clearVote`/withdraw votes on `W`) such that `witness.getVoteCount() == 0` for the upcoming cycle `C`.
2. `W` produces a block in cycle `C`; `Manager.payReward()` → `MortgageService.payBlockReward()` → `delegationStore.addReward(C, W, value)` records a nonzero reward for `(C, W)`.
3. At the next maintenance boundary, `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(C, W, 0)` (`voteCount == 0`), which takes the `voteCount == 0` branch and only forwards the prior `Vi(C-1, W)` to `Vi(C, W)` — the delta for `reward(C, W)` is never applied.
4. Any voter who later votes for `W` and withdraws via `MortgageService.withdrawReward`/`VoteRewardUtil.withdrawReward` computes reward strictly from `Vi(endCycle-1) - Vi(beginCycle-1)`; since `Vi` never reflects `reward(C, W)`, that reward is permanently unclaimable by anyone, while the raw value remains stranded in the `delegation` store keyed by `(C, W, "reward")`, never read again.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);

      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
