### Title
`ProxyOFT.sendFrom` silently truncates an over-length destination address instead of reverting, minting bridged tokens to a wrong address - (File: contracts/dependencies/@layerzerolabs/solidity-examples/contracts-upgradeable/token/oft/OFTCoreUpgradeable.sol)

### Summary
Analogous to the ENS `hexToAddress()` truncation bug, Metronome's OFT bridging path accepts a `bytes` destination address of arbitrary length and silently truncates it to 20 bytes on the receiving chain instead of validating the length. `OFTCoreUpgradeable._send` forwards the raw `_toAddress` bytes into the LayerZero payload, and `_sendAck` decodes it via `BytesLib.toAddress(_bytes, 0)`, which only requires `length >= 20` and returns the first 20 bytes via `div(mload(...), 0x1000000000000000000000000)` — discarding trailing bytes without any check. [1](#0-0) [2](#0-1) 

### Finding Description
`ProxyOFT` exposes the inherited `sendFrom(address,uint16,bytes,uint256,address,address,bytes)` entry point where `_toAddress` is an unrestricted `bytes calldata`. [3](#0-2)  On the source chain, `_debitFrom` burns the sender's `SyntheticToken` without ever inspecting `_toAddress` (it is commented out in the signature). [4](#0-3)  On the destination chain, the delivered payload is decoded and `toAddressBytes.toAddress(0)` extracts only the leading 20 bytes; `_creditTo` then mints to that truncated address. [5](#0-4)  A user who supplies a 32-byte `bytes32`-encoded address (e.g., `abi.encode(addr)`, a common pattern since the interface accepts "any size" per the natspec) will have tokens minted to `address(uint160(bytes32>>96))` semantics — i.e., the wrong recipient — with no revert and no way to recover.

### Impact Explanation
Tokens are burned on the source chain and minted on the destination chain to an address the sender does not control (e.g., `address(0)`-adjacent or an arbitrary EOA when a padded 32-byte value is supplied). This is permanent loss of user funds caused by silent truncation rather than reverting on malformed input — the same failure mode and recommended fix (strict length check, revert instead of truncate) as the ENS finding, which the judge upheld as Medium.

### Likelihood Explanation
Like the ENS report, exploitation requires the user to supply an invalid-length address; it is not directly attacker-weaponizable against third parties. However, the interface explicitly permits arbitrary-length `_toAddress`, the "user friendly" overloads encode exactly 20 bytes while the raw overload does not warn, and bridge UIs/integrators frequently pass `bytes32` values — making the mistake realistic. Funds are unrecoverable once minted to the truncated address since `retryOFTReceived`/recovery paths only apply to `PT_SEND_AND_CALL`, which `ProxyOFT` disables. [6](#0-5) 

### Recommendation
In `ProxyOFT._debitFrom` (or an overridden `_send`), enforce `_toAddress.length == 20` for EVM destinations and revert otherwise, so malformed addresses fail on the source chain before tokens are burned. Alternatively, override `_sendAck`/`toAddress` usage to require exact length rather than truncating.

### Proof of Concept
```solidity
// Source chain: user holds msUSD synthetic token and calls the raw sendFrom
// with a 32-byte abi.encode'd destination address instead of 20 bytes.
bytes memory badTo = abi.encode(bob); // 32 bytes: 12 zero pad + 20-byte addr

proxyOFT.sendFrom{value: fee}(
    alice,
    DST_CHAIN_ID,
    badTo,            // length 32, accepted without revert
    1000e18,
    payable(alice),
    address(0),
    adapterParams
);
// alice's 1000 msUSD burned on source chain.

// Destination chain: lzReceive -> _nonblockingLzReceive -> _sendAck
// toAddressBytes.toAddress(0) reads the FIRST 20 bytes of `badTo`,
// i.e. 0x000000000000000000000000XXXXXXXX (upper bytes of the padded word),
// NOT bob. syntheticToken.mint(truncatedAddr, 1000e18) succeeds.
// Result: tokens minted to an unintended/uncontrolled address; alice's funds lost.
```
Foundry fork PoC: deploy `ProxyOFT` + `SyntheticToken` on a fork, call `sendFrom` with a 32-byte `_toAddress`, then deliver the constructed `PT_SEND` payload through `lzReceive` and assert `syntheticToken.balanceOf(truncatedAddress) == amount` while `balanceOf(intended) == 0`.

        address _from,
        uint16 _dstChainId,
        bytes memory _toAddress,
        uint _amount,

        bytes memory _adapterParams
    ) internal virtual {

        bytes memory lzPayload = abi.encode(PT_SEND, _toAddress, amount);
        _lzSend(_dstChainId, lzPayload, _refundAddress, _zroPaymentAddress, _adapterParams, msg.value);

        emit SendToChain(_dstChainId, _from, _toAddress, amount);
    }

    function _sendAck(uint16 _srcChainId, bytes memory, uint64, bytes memory _payload) internal virtual {
        (, bytes memory toAddressBytes, uint amount) = abi.decode(_payload, (uint16, bytes, uint));

        address to = toAddressBytes.toAddress(0);

        amount = _creditTo(_srcChainId, to, amount);
        emit ReceiveFromChain(_srcChainId, to, amount);
    }
