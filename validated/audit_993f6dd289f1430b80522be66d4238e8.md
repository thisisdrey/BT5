### Title
Reward Dilution via Deposit/Withdraw Sandwich on `lending_pool_emissions_deposit` - ([File: programs/marginfi/src/instructions/marginfi_group/configure_bank.rs])

### Summary
`lending_pool_emissions_deposit` computes the bank's new `asset_share_value` by dividing the funded emissions `amount` (plus existing assets) by the bank's *current* `total_asset_shares` at the moment the instruction executes. Because this instruction is permissionless and callable by anyone, and because ordinary `lending_account_deposit`/`lending_account_withdraw` can mint/burn shares at zero net cost within the same transaction/slot, an attacker can sandwich any emissions-deposit call with a large temporary deposit and withdrawal to dilute the share-value increase attributed to existing depositors and capture a proportional slice of the emissions for themselves — the exact bug class described in the Beedle `Staking.sol` report (reward computed as `delta / currentTotalSupply`, sandwichable with a large temporary stake).

### Finding Description
The vulnerable computation is in `lending_pool_emissions_deposit`: [1](#0-0) 

```
let total_asset_shares = I80F48::from(bank.total_asset_shares);
...
let total_assets = bank.get_asset_amount(total_asset_shares)?;
let updated_total_assets = total_assets.checked_add(I80F48::from_num(amount))?;
bank.asset_share_value = updated_total_assets.checked_div(total_asset_shares)?.into();
```

This mirrors Beedle's `rewardPerToken += (balanceDelta) / totalStaked` pattern: the value added (`amount`) is divided by whatever `total_asset_shares` happens to be at that exact instant, and the result is baked permanently into `asset_share_value`, which is used by every subsequent deposit/withdraw calculation: [2](#0-1) 

Ordinary deposits/withdrawals mint/burn shares at the *current* `asset_share_value`, which is unaffected by the size of the deposit/withdrawal itself: [3](#0-2) 

Mathematically, if an attacker deposits `X` immediately before an emissions deposit of `E` (with pre-existing assets `A0`, shares `S0`) and withdraws immediately after:
- Baseline (no attack): existing depositors' shares become worth `A0 + E`.
- With the sandwich: existing depositors' shares become worth `A0 + A0·E/(A0+X)`, i.e., they receive `E·A0/(A0+X)` instead of `E`.
- The attacker withdraws `X + X·E/(A0+X)`, i.e., a costless profit of `X·E/(A0+X)`.

This is enabled because:
1. `lending_pool_emissions_deposit` is explicitly documented as **permissionless** ("(permissionless) — deposit same-bank emissions directly into the liquidity vault, raising `asset_share_value`"), so anyone (including the attacker or an MEV searcher observing a pending legitimate emissions-funding transaction) can trigger/observe it and race to sandwich it. [4](#0-3) 
2. `total_asset_shares` can be inflated/deflated at will via ordinary, uncapped `lending_account_deposit`/`lending_account_withdraw` calls with no minimum holding period, cooldown, or same-block/flashloan protection on the withdraw path shown. [5](#0-4) 

By contrast, the normal interest-accrual path (`accrue_interest`) is *not* vulnerable to this class of attack because it multiplies `asset_share_value` by an APR/time-derived rate factor rather than dividing an absolute externally-supplied amount by the instantaneous share count — the share-count cancels out of the accrual formula. [6](#0-5) 

### Impact Explanation
This allows an unprivileged attacker to steal a portion of any emissions/rewards deposit intended for genuine long-term depositors, at zero net capital cost (ignoring transaction fees), by front-running/sandwiching the emissions-deposit call. The magnitude of the theft scales with `X/(A0+X)` — an attacker who can temporarily deposit an amount comparable to or larger than the bank's total assets can capture a majority of any given emissions deposit. This is a direct unauthorized transfer of value from existing depositors to the attacker (concrete theft), not merely a theoretical griefing vector.

### Likelihood Explanation
Likelihood is bounded by two factors: (1) the attacker needs enough capital to temporarily inflate `total_asset_shares` (which can be sourced via flashloan-like large temporary deposits, since marginfi deposits are not otherwise restricted in size for a permissionless bank), and (2) the attacker needs visibility into or the ability to trigger the `lending_pool_emissions_deposit` call. Since the instruction is permissionless, the attacker does not need to wait for an admin — they only need someone (protocol, admin, or another user) to fund emissions, which they can then sandwich. On Solana, same-slot sandwiching of a target transaction is harder than on typical EVM mempools, which somewhat reduces — but does not eliminate — practical exploitability; validators/leader-adjacent actors or bundling infrastructure could still achieve this reliably.

### Recommendation
Change `lending_pool_emissions_deposit` to not use the instantaneous `total_asset_shares`/`total_assets` snapshot taken in the same instruction as the deposit. Options:
- Require a minimum settlement delay: snapshot `total_asset_shares` from *before* the current slot/transaction (e.g., cached from the last `accrue_interest` call) rather than reading it live at deposit time.
- Rate-limit or time-lock large deposit/withdraw pairs (as recommended in the original report) so a single transaction/slot cannot mint and burn a large share position around a sensitive state-mutating call.
- Alternatively, redesign emissions deposit to accrue linearly over time (similar to how interest accrual works, immune to instantaneous share manipulation) rather than as an instantaneous lump-sum division by current shares.

### Proof of Concept
Given bank state `total_assets = A0`, `total_shares = S0`, `asset_share_value = A0/S0`:

1. Attacker calls `lending_account_deposit(X)` on the target bank in the same or immediately preceding transaction, minting `s = X·S0/A0` shares at unchanged `asset_share_value`.
2. Anyone (admin, protocol, or the attacker) calls `lending_pool_emissions_deposit(E)`:
   - `total_assets' = A0 + X + E`
   - `total_shares' = S0 + s`
   - `asset_share_value' = (A0+X+E)/(S0+s) = (A0/S0)·(A0+X+E)/(A0+X)`
3. Attacker immediately calls `lending_account_withdraw` for all `s` shares, receiving `s·asset_share_value' = X·(A0+X+E)/(A0+X) = X + X·E/(A0+X)`.
4. Attacker's net gain: `X·E/(A0+X)` tokens, with zero net principal risk (assuming the deposit/withdraw round-trip has no other fee).
5. Existing depositors (holding `S0` shares) now have their `E`-worth emissions diluted to `A0·E/(A0+X)`, a shortfall of exactly `X·E/(A0+X)` — matching the attacker's gain, confirming a direct value transfer.

Note: I was unable to run this against the actual test harness (e.g., `programs/marginfi/tests/misc/emissions_deposit.rs`) to empirically confirm the exact numeric outcome including rounding effects from `I80F48` fixed-point math and any dust/rounding protections; the derivation above is based on the documented/read formulas in `configure_bank.rs`, `bank.rs`, and `deposit.rs`. A Devin session with terminal access would be needed to write and execute a concrete Rust/Anchor test reproducing this end-to-end and to check for any additional guards (e.g., minimum deposit intervals) not visible in the indexed snippets.
