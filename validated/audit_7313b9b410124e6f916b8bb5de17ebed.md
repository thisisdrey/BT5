## Title
Unauthenticated `RecvError` packet allows remote tunnel teardown without any credential check - (File: outside.go)

## Summary
Nebula's `handleRecvError` accepts a completely unencrypted, unauthenticated control packet type (`header.RecvError`) and uses it to unilaterally tear down an established tunnel's `HostInfo` from the main hostmap and the handshake manager, based only on a plaintext `RemoteIndex` field and a source-address comparison — no certificate, no AEAD/decryption, no nonce/replay protection. This mirrors the DebtDAO `close()` bug class: a state-destroying operation ("close the position"/"close the tunnel") is reachable without validating that the caller is entitled to perform it.

## Finding Description
`readOutsidePackets` dispatches `header.RecvError` before any decryption or peer authentication occurs: [1](#0-0) 

`handleRecvError` then looks up the hostinfo purely by the attacker-supplied `RemoteIndex` and only checks that the packet's source `netip.AddrPort` matches the hostinfo's currently known remote address, before calling `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`: [2](#0-1) 

The `RemoteIndex` used to look up the target hostinfo (`QueryReverseIndex`) is not a secret: it is present in cleartext in the header of every packet sent over the tunnel, so any attacker who can observe a single packet between the two peers (or who previously communicated with either peer) learns it. The only remaining "check" preventing a stranger from spoofing this packet is comparing the packet's UDP source `addr` to `hostinfo.GetRemote()`, i.e. spoofing the peer's known UDP source IP:port — trivial for an on-path attacker or attacker on a shared/spoofable network segment, and this packet type carries no cryptographic proof of origin at all (unlike `header.Message`/`header.Test`/`header.CloseTunnel`, which require successful AEAD decryption with the session key derived from a certificate-authenticated handshake before being processed, see the `case header.CloseTunnel:` branch that only runs after `hostinfo.ConnectionState.Decrypt` succeeds at [3](#0-2) ).

This is analogous to the reported bug: in DebtDAO, `close()` destroyed the credit's accounting state (`_close`) without verifying that the `id` referenced a real/valid position; here, `handleRecvError` destroys the tunnel's session state (hostmap entry, handshake-manager entry, and eventually lighthouse cache via `DeleteVpnAddrs`) without verifying that the packet was authored by an entity holding the negotiated session keys or a valid CA-signed certificate — only an easily-spoofed address match gates a destructive state transition.

## Impact Explanation
An attacker who can either (a) observe one packet of an existing tunnel (to learn `RemoteIndex`) and spoof the victim peer's UDP source `IP:port`, or (b) is on-path between the two peers, can force any live tunnel to be torn down at will and repeatedly, without possessing any CA-signed certificate or session key. Effects:
- Remote unauthenticated tunnel teardown / persistent denial of service against arbitrary Nebula tunnels.
- Forces expensive rehandshakes, and combined with repeated spoofed `RecvError` packets, can prevent a tunnel from ever staying up (a poor-man's remote kill switch).
- The teardown clears lighthouse-learned state as well when it's the last hostinfo (`f.lightHouse.DeleteVpnAddrs`), amplifying disruption of the mesh's routing state.

This does not permit traffic decryption or forgery, but it is a concrete unauthenticated remote state-poisoning / DoS primitive matching the "remote crash/state poisoning" acceptance bar.

## Likelihood Explanation
- `RemoteIndex` is transmitted in cleartext on every packet (see `header.H` field usage throughout `outside.go`), so it is trivially learned by anyone who can see even one packet of the target tunnel.
- The only gate is a UDP source-address match against the last known/roamed remote — UDP source spoofing is well known to be feasible for on-path/off-path attackers in many network topologies (no TCP-style handshake to prevent it), and Nebula's own roaming logic already accepts new source addresses opportunistically.
- Whether this is exploitable in a given deployment depends on `f.acceptRecvErrorConfig` (`listen.accept_recv_error`), which is configurable (`recvErrorAlways`/`recvErrorNever`/`recvErrorPrivate`) — see the config surface in `interface.go` (grep confirms `acceptRecvErrorConfig` wiring there, though the exact default value could not be verified from the indexed content). If the default or a common configuration is `recvErrorAlways` or `recvErrorPrivate` for a public-facing listener, exploitation is remotely feasible without any credentials.

## Recommendation
- Do not act on `RecvError` from source addresses/paths that cannot be authenticated; at minimum require some replay-resistant proof (e.g., only accept `RecvError` correlated with an actual recent outbound packet that could have triggered it, or require it to be sent from the exact 4-tuple *and* rate-limit/cross-check with recent traffic timestamps).
- Consider requiring `RecvError` to include or be preceded by material that only the legitimate peer could produce (e.g., authenticate it with the session key once one exists, rather than accepting it in the clear pre-decryption).
- At minimum, ensure `acceptRecvErrorConfig` defaults to the most conservative option and clearly document the spoofing risk in the config docs, since this fully bypasses handshake/cert verification, unlike `CloseTunnel`, which is authenticated via AEAD decryption.

## Proof of Concept
1. Establish (or passively observe) a Nebula tunnel between hosts A and B; capture one packet to learn A's `RemoteIndex` as seen by B (present in cleartext header) and A's currently active UDP `IP:port` as known to B.
2. From a vantage point able to spoof UDP source address `A_ip:A_port` (on-path attacker, or a network permitting source spoofing), send B a single-byte-header `header.RecvError` packet with `RemoteIndex` set to the learned value and no payload/encryption.
3. `readOutsidePackets` routes this directly to `handleRecvError` before any decryption/authentication (outside.go:81-83).
4. `handleRecvError` finds the hostinfo via `QueryReverseIndex`, sees the spoofed source address matches the recorded remote, and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)` (outside.go:557-574), tearing down B's tunnel to A with no proof the sender ever held a valid Nebula certificate or session key.
5. Repeating this at will produces a persistent, unauthenticated remote denial of service against the tunnel.

*(Note: I could not fully verify the compiled default value of `acceptRecvErrorConfig`/`listen.accept_recv_error` from the available index — `interface.go` shows the enum and wiring but the exact default assignment line was not captured in my search results. This should be confirmed directly in `interface.go` before finalizing severity/likelihood.)*

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
