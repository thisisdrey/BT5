### Title
Attacker-controlled `relay_hints` in `broadcast_message` allows a single forged message to suppress re-broadcast to every connected neighbor - (File: stackslib/src/net/p2p.rs)

### Summary
`PeerNetwork::broadcast_message` decides whether to forward a message to a given neighbor solely by checking if that neighbor's `Hash160` public-key hash appears anywhere in the `relay_hints: Vec<RelayData>` list, with no cryptographic proof that the listed peer actually relayed the message. Since `relay_hints` is populated from the `relayers` field of the incoming wire message (a field the originating/relaying sender fully controls), a malicious peer can pad it with the public-key hashes of every neighbor this node is connected to, causing `do_relay` to be `false` for all of them and silently dropping propagation while the message is still accepted/stored locally.

### Finding Description
In `broadcast_message` (stackslib/src/net/p2p.rs:1267-1293), for every candidate neighbor the code computes `pubkey_hash = Hash160::from_node_public_key(pubkey)` and sets `do_relay = false` if that hash matches **any** entry in `relay_hints`: [1](#0-0) 

This `relay_hints` vector is not independently verified by this node — it is threaded straight through from the received `StacksMessage`'s own relayer chain (`RelayData` entries carrying a `NeighborAddress` with `public_key_hash`), which is attacker-supplied data from the wire. Each `RelayData` entry records only a hash and sequence metadata, not a signature proving the named peer actually forwarded the message. A remote peer originating (or re-relaying) a message can therefore include, in the initial `relayers` list, the `public_key_hash` values of every peer it can enumerate as connected to the victim node (neighbor pubkeys are discoverable via handshakes/gossip), regardless of whether those peers ever touched the message.

Because the equality the check relies on is "neighbor pubkey_hash is in `relay_hints`" and this list is attacker-forged rather than a true record of the actual relay path, the number of neighbors actually forwarded to collapses to zero even though none of them legitimately relayed the message. The message itself is still processed/stored locally by this node (accepted into the relay pipeline before `broadcast_message` runs), so the attacker succeeds in getting the payload accepted while blackholing further propagation from this node.

### Impact Explanation
A single crafted message can cause a targeted node to stop forwarding that message to its entire neighbor set, degrading block/transaction propagation across the network path through that node — this matches the "High: steering propagation / degrading network-wide block/tx propagation" category. It does not corrupt local state or crash the node, but it silently defeats gossip-based dissemination, which can be repeated for every new block/tx broadcast the attacker wants suppressed at that node, and can be combined across multiple victim nodes to reduce global propagation efficiency.

### Likelihood Explanation
Any unprivileged remote peer that can open a P2P connection and complete the handshake can send a normal application message with a forged `relayers` list; no secret, signing key, or privileged role is needed beyond what's needed to be a normal gossip peer. The main constraint is the wire-level cap on relayer-chain length (`MAX_RELAYERS_LEN`), which bounds how many distinct pubkey hashes can be stuffed into one message's relay chain, so the attacker may need this cap to be at least as large as the target's outbound peer count to fully blackhole it in one shot; even with a smaller cap, it still suppresses forwarding to that many neighbors per message, repeatable on every new message.

### Recommendation
Do not trust the wire-supplied `relay_hints`/`relayers` list as authoritative proof of "who already relayed this." Instead, derive the relay-suppression set from information this node can independently verify — e.g., only suppress relay back to the *direct* peer socket that delivered this specific message to this node (which is already known from the connection/event_id), and/or require each `RelayData` hop to be signed by the claimed relayer's key so the chain can be cryptographically validated before being trusted for relay suppression.

### Proof of Concept
Add a test in `stackslib/src/net/p2p.rs` (or `net/tests/relay/epoch2x.rs`) that:
1. Spins up a `PeerNetwork` with N authenticated neighbor conversations (mocked `ConversationP2P` with known public keys).
2. Constructs a `relay_hints: Vec<RelayData>` containing the real `public_key_hash` of every one of the N neighbors, without any of them having actually relayed the message (attacker forges this list as the "original sender").
3. Calls `network.broadcast_message(neighbor_keys, relay_hints, message_payload)`.
4. Asserts that `add_relay_handle` / `sign_and_forward` was invoked zero times (i.e., no relay handles were queued) — demonstrating that all N legitimate neighbors were skipped via `do_relay = false` (stackslib/src/net/p2p.rs:1275-1293), even though none of them are actually in the true relay path.
