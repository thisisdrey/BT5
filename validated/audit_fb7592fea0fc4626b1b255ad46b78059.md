### Title
Lack of Slippage Protection in `ExchangeWithdrawContract` (Bancor-style Pool Withdrawal) Allows Users to Receive Fewer Tokens Than Expected - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator` lets a bancor-exchange creator withdraw liquidity by specifying only the `token_id` and `quant` of one side of the pool; the amount of the *other* token returned (`anotherTokenQuant`) is computed on-the-fly from the current pool ratio at execution time, with no user-supplied minimum-output bound. This mirrors the PoolTogether `PrizeVault.withdraw`/`redeem` finding: the exchange rate used at execution can differ from the rate observed when the transaction was signed/broadcast, and the creator has no way to bound the loss.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected` (minimum-output) field: [1](#0-0) 

By contrast, `ExchangeTransactionContract` (the trade/swap contract) explicitly carries an `expected` field that is enforced in `doValidate()`: [2](#0-1) [3](#0-2) 

`ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` directly from the pool's current `firstTokenBalance`/`secondTokenBalance` ratio at the moment the transaction executes, using whatever state the pool is in at that block: [4](#0-3) 

`doValidate()` similarly recomputes `anotherTokenQuant` from the current pool balances and only checks a fixed-precision rounding tolerance ("Not precise enough") — it never compares the computed output against any user-specified minimum: [5](#0-4) 

Because the bancor pool balances (`firstTokenBalance`, `secondTokenBalance`) are mutable and can be moved by any other user's `ExchangeTransactionContract` (swap) or `ExchangeInjectContract` transaction included in the same block or in blocks preceding execution, the ratio used to compute `anotherTokenQuant` for a pending `ExchangeWithdrawContract` transaction can shift between the time the owner signs/broadcasts it and the time it is actually executed by the actuator — exactly the "loss while transaction is pending" scenario described in the PoolTogether report, just replacing "yield vault loss" with "pool ratio shifted by a preceding swap."

The owner (exchange creator) who broadcasts a withdrawal has no field to express "I want at least X of the other token," so they cannot protect themselves — the transaction will always succeed at whatever ratio is current at execution time, silently returning less value than anticipated.

### Impact Explanation
An exchange creator withdrawing liquidity via `ExchangeWithdrawContract` can receive materially less of the paired token than they expected if the pool ratio shifts (due to a preceding swap/inject transaction) between signing and execution — a direct, unbacked-expectation loss of value for the withdrawer, analogous to the Medium-severity PoolTogether finding. This is a genuine value-extraction/loss-of-funds issue reachable by any account holding exchange-creator privileges for a bancor pool, through a normal signed transaction with no special privileges required beyond being the pool creator.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an active bancor exchange pair with reasonable trading volume/pool imbalance risk, and (b) a withdrawal transaction sitting in the mempool or being executed after other swap transactions shift the ratio. This is a normal, expected operational condition on any actively traded pool rather than a contrived attack — any user (or the withdrawer's own delayed transaction) trading against the pool before the withdrawal executes triggers the condition. No malicious SR/witness/node behavior is required; it is purely a consequence of ordinary transaction ordering and pool state changes at execution time versus signing time.

### Recommendation
Add a slippage-protection field (e.g., `expected_another_token_quant` or `min_another_token_quant`) to `ExchangeWithdrawContract`, mirroring the existing `expected` field in `ExchangeTransactionContract`, and enforce it in `ExchangeWithdrawActuator.doValidate()` by rejecting the transaction if the computed `anotherTokenQuant` is less than the user-specified minimum — consistent with how `ExchangeTransactionActuator` already guards against unfavorable execution-time rates.

### Proof of Concept
1. Exchange pool P has `firstTokenBalance = 100000`, `secondTokenBalance = 200000` (2:1 ratio).
2. Creator Alice signs an `ExchangeWithdrawContract` to withdraw `quant = 1000` of the first token, expecting `anotherTokenQuant ≈ 2000` of the second token based on the current ratio.
3. Before Alice's transaction is included, another user Bob executes an `ExchangeTransactionContract` swap that shifts the pool to `firstTokenBalance = 100000`, `secondTokenBalance = 150000` (ratio dropped to 1.5:1).
4. Alice's withdrawal then executes against the new ratio: `anotherTokenQuant = 150000 * 1000 / 100000 = 1500`, i.e., 25% less than she expected, with no way for her transaction to have specified a minimum acceptable amount and reverted instead — see the unconditional computation in `execute()`: [6](#0-5)
