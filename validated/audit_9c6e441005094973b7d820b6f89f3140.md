Unauthenticated `/shutdown` route in `SignerEventReceiver::next_event` allows any remote TCP client to permanently halt the signer's event stream - ([File: libsigner/src/events.rs])

### Summary
`SignerEventReceiver::next_event` handles a `/shutdown` HTTP POST route by unconditionally setting `stop_signal` to `true` and returning `EventError::Terminated`, with no check of a secret, token, or source address. Any TCP client that can reach the signer's event-receiver port can send this exact request and permanently stop the signer's `main_loop`, without ever going through `get_stop_signaler()`.

### Finding Description
The intended invariant is that only the local node process (via `RunningSigner::stop()` / `SignerStopSignaler::send()`, which connects to `self.local_addr` and issues `POST /shutdown`) should be able to halt the event receiver. In practice, `next_event` implements this "stop" capability as a bare, unauthenticated HTTP route match: [1](#0-0) 

There is no shared secret, HMAC, or origin/IP allow-list check comparing the requester to the node dispatcher — the branch is reached purely by matching `request.url() == "/shutdown"` and `request.method() == Post` inside `next_event`: [2](#0-1) 

The legitimate stop path (`SignerStopSignaler::send`) constructs the exact same unauthenticated wire bytes that any attacker could replay: [3](#0-2) 

Once `stop_signal` is set, `is_stopped()` returns true and `main_loop` (in `EventReceiver::main_loop`, `libsigner/src/events.rs`) exits on its next iteration, and `next_event` itself immediately errors with `EventError::Terminated`, breaking the receiver's `main_loop`. No other guard (no `MAX_MESSAGE_LEN` check, no auth-gate, no signature check) sits in front of this branch — the `/status`, `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, and `/new_block` routes have their own payload-specific validation, but `/shutdown` has none at all, by design, since it's meant to only be invoked locally by the same process.

The signer's own documentation acknowledges this exposure risk generically ("exercise caution if you are communicating with an external node... this could potentially expose sensitive data or functionalities to security risks if additional proper security checks are not integrated"), confirming the gap is known but unmitigated at the code level: [4](#0-3) 

### Impact Explanation
Any remote party who can open a TCP connection to the signer's bound event-receiver address/port (the `endpoint` configured in `GlobalConfig`, bound via `Signer::spawn` / `SignerEventReceiver::bind`) can send a single `POST /shutdown` request and permanently stop that signer's event ingestion loop. This is a single-message, remotely-triggerable, unauthenticated denial of service against a signer node — matching the "Critical - remote crash/unauthenticated DoS from few messages" category. The attack is trivially repeatable and requires no special role, secret, or prior state.

### Likelihood Explanation
No preconditions beyond network reachability to the signer's event-receiver TCP port are required. The attacker does not need the node's RPC secret, StackerDB slot ownership, or any peer/key material — a bare TCP connection and a hand-crafted HTTP request suffice. The only mitigating factor is that the signer event-receiver endpoint is typically intended to be bound to a local/private interface reachable only by the associated Stacks node; whether it is reachable by a remote unprivileged attacker depends entirely on the operator's network/firewall configuration of `endpoint`, which is not enforced or restricted by the code itself.

### Recommendation
Require the `/shutdown` (and ideally all) requests to `SignerEventReceiver::next_event` to be authenticated, e.g., by requiring a shared secret/token known only to the node and signer (compared in constant time), or by binding the event-receiver socket to loopback only and rejecting connections from non-loopback source addresses at accept time, rather than relying purely on network topology/firewalling.
