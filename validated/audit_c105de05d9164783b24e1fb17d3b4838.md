### Title
Unbounded growth of `DelegatedResourceAccountIndex` from/to lists reachable via `DelegateResourceContract`, causing unbounded work in every `getDelegatedResourceAccountIndexV2` query - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
Any account holder can freeze a minimal amount of TRX and issue an unlimited number of `DelegateResourceContract` transactions to distinct, unique receiver addresses. Each such delegation appends an entry to the `to`/`from` account index for the delegator/delegatee via `DelegatedResourceAccountIndexStore.delegateV2()`, with no cap on how many unique counterpart addresses a single account can accumulate — unlike other resource-list structures in the codebase (e.g. `UNFREEZE_MAX_TIMES = 32` for `UnfreezeBalanceV2`, `MAX_VOTE_NUMBER` for votes, `MAX_FROZEN_SUPPLY_NUMBER` for asset issuance), which all explicitly bound list growth before allowing writes.

### Finding Description
`DelegateResourceProcessor.execute()` / `DelegateResourceActuator` calls into `delegateResource()` (`actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java:146-191`), which unconditionally writes new index entries keyed by `V2_FROM_PREFIX`/`V2_TO_PREFIX` + address pairs via `repo.updateDelegatedResourceAccountIndex(...)`. There is no limit check anywhere in `validate()` on the number of distinct receiver addresses an owner can delegate to, nor on the number of distinct delegators an account can receive from.

Each such delegate operation only requires `frozenBalance >= 1 TRX` (`FreezeBalanceProcessor.validate`, `actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java:30-36`), so an attacker with modest capital can freeze a small amount and split it into large numbers of 1-TRX delegations to many unique, attacker-controlled receiver addresses, each creating a new row under the `V2_FROM_PREFIX`/`V2_TO_PREFIX` key space in `DelegatedResourceAccountIndexStore`.

The unbounded list is fully materialized on every read: `DelegatedResourceAccountIndexStore.getWithPrefix()` (`chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java:118-138`) performs an unbounded `prefixQuery`, collects **all** matching capsules into a list, sorts them by timestamp, and maps them into the response — with no pagination or size cap. This method backs `getV2Index()`, which is exposed through `Wallet.getDelegatedResourceAccountIndexV2` and served via the gRPC (`RpcApiService`), HTTP (`GetDelegatedResourceAccountIndexV2Servlet`), and solidity/PBFT node query paths (confirmed via multiple call sites in `RpcApiService.java`, `HttpApiOnPBFTService.java`, `HttpApiOnSolidityService.java`).

This mirrors the OpenQ `TOKEN_ADDRESS_LIMIT`-declared-but-unenforced pattern: java-tron has demonstrated the pattern of bounding similar per-account lists (frozen supply count, vote count, unfreeze count) precisely to avoid unbounded iteration, but the delegate-resource index has no analogous bound.

### Impact Explanation
An attacker can grow a single account's delegated-resource index to an arbitrarily large size at low cost (1 TRX per unique counterpart address, refundable via unfreeze/undelegate later). Subsequent `getDelegatedResourceAccountIndexV2` queries against that account force the node to execute an unbounded `prefixQuery` + full in-memory sort + full list materialization for every request, which can degrade or exhaust node resources (CPU/memory) servicing that single anonymous API request repeatedly, denying the JSON-RPC/gRPC/HTTP query service for that endpoint (matches the allowed "API the node can no longer serve" outcome).

### Likelihood Explanation
Likelihood is moderate: the attack is fully executable by an unprivileged account using only standard `DelegateResourceContract` transactions and requires no special privileges, but the cost scales linearly with the number of index entries created (1 TRX minimum per entry, transaction fees per delegation), so building a very large list requires many transactions/blocks. It is nonetheless straightforward and repeatable, and once the list is large the amplification per query is persistent until entries are removed.

### Recommendation
Introduce and enforce a maximum count on the number of distinct entries a `DelegatedResourceAccountIndex` (`to`/`from`) can hold per account, checked in `DelegateResourceActuator`/`DelegateResourceProcessor.validate()` before allowing a new delegation to a not-yet-seen counterpart address (analogous to `UNFREEZE_MAX_TIMES` in `UnfreezeBalanceV2Actuator`). Additionally, add pagination/limit parameters to `DelegatedResourceAccountIndexStore.getWithPrefix()`/`getV2Index()` and the corresponding `Wallet` and API methods so that queries against pathologically large indexes cannot force unbounded server-side work in a single request.

### Proof of Concept
1. Attacker freezes minimal TRX (`FreezeBalanceV2Contract`, ≥1 TRX) for BANDWIDTH/ENERGY.
2. Attacker repeatedly submits `DelegateResourceContract` transactions delegating 1 TRX each to N distinct, attacker-controlled receiver addresses (`actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java:117-191`), each call appending a new entry via `DelegatedResourceAccountIndexStore.delegateV2()` with no upper bound check.
3. After building up N (e.g., tens of thousands of) entries, any client calls `getDelegatedResourceAccountIndexV2` (gRPC/HTTP) for the attacker's address.
4. The node executes `getWithPrefix()` (`chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java:118-138`), performing an unbounded prefix scan, list construction, and sort over all N entries on every single request, consuming disproportionate CPU/memory relative to the cost of triggering the underlying state growth.
