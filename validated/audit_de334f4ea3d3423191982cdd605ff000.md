### Title
Unbounded Witness Registration Enables Unbounded Growth of the Witness List Used in Every Maintenance Cycle and Public API Query - ([File: actuator/src/main/java/org/tron/core/actuator/WitnessCreateActuator.java])

### Summary
`WitnessCreateActuator.validate()` never checks how many witnesses already exist before allowing a new one to be registered. Any account that pays the fixed `AccountUpgradeCost` fee can create a witness, so the total number of `WitnessCapsule` entries stored in `WitnessStore` (and thus returned by `getAllWitnesses()`) is unbounded — exactly the same class of bug as the reported "tranches" issue: a list that is pushed to by an ordinary, permissionless actuator with no upper-bound check, and later relied upon as if it were small.

### Finding Description
`WitnessCreateActuator.validate()` only checks address validity, URL format, account existence, whether the address is already a witness, and balance sufficiency — there is no limit on the total number of witnesses: [1](#0-0) 

`createWitness()` unconditionally pushes a new `WitnessCapsule` into `WitnessStore` for every successful call: [2](#0-1) 

`WitnessStore.getAllWitnesses()` loads **every** witness ever registered (not just the active/standby set) into an in-memory list: [3](#0-2) 

This unbounded list is then repeatedly iterated and sorted in performance-critical, per-block/per-maintenance-cycle code paths:
- `MaintenanceManager.doMaintenance()` iterates `consensusDelegate.getAllWitnesses()` multiple times every maintenance cycle (Vi accumulation, building `newWitnessAddressList`, brokerage/vote bookkeeping): [4](#0-3) [5](#0-4) 

- `WitnessStore.getWitnessStandby()` sorts the full witness list (`O(n log n)`) on every call: [6](#0-5) 

- The public, unauthenticated APIs `getWitnessList()` and `getPaginatedNowWitnessList()` in `Wallet` also load and sort the **entire** witness set on every request, even though the caller only wants a small page: [7](#0-6) 

These are exposed via HTTP/gRPC (`ListWitnesses`/`getwitnesslist`) to any anonymous client, so both the write path (unbounded registration) and the read path (unbounded full-list materialization/sort) are reachable without special privilege.

Unlike `FrozenSupply` in `AssetIssueContract`, which is explicitly bounded by `getMaxFrozenSupplyNumber()`: [8](#0-7) 

and unlike votes, which are capped by `MAX_VOTE_NUMBER`: [9](#0-8) 

the witness list has no analogous cap in `WitnessCreateActuator`, `WitnessStore`, or `DynamicPropertiesStore`.

### Impact Explanation
Because the number of registered witnesses can grow without bound, every maintenance cycle (which runs on a fixed periodic schedule for every full node in the network) does `O(n)` or worse work over the full witness set, and every call to `getWitnessList()` / `getPaginatedNowWitnessList()` (unauthenticated HTTP/gRPC/JSON-RPC endpoints) forces the node to materialize and sort the entire witness set in memory. An attacker who repeatedly funds and submits `WitnessCreateContract` transactions can inflate this list arbitrarily, degrading maintenance-cycle performance for the whole network and turning a normally cheap, paginated API query into an increasingly expensive full-scan/sort operation on every node that serves it — a resource-exhaustion / node-degradation vector consistent with "API the node can no longer serve" and consensus-critical processing slowdown.

### Likelihood Explanation
Reaching this is trivial for any account: `WitnessCreateActuator` is reachable by a single signed `WitnessCreateContract` transaction from an ordinary account, gated only by holding `AccountUpgradeCost` TRX (a fixed, non-scaling cost) and a distinct address per witness. There is no cool-down, no global cap check, and no growth-rate limiting logic anywhere in the validate/execute path or in `DynamicPropertiesStore`.

### Recommendation
Add an explicit cap on the total number of witnesses (e.g., a `MAX_WITNESS_NUMBER` dynamic parameter, analogous to `MAX_FROZEN_SUPPLY_NUMBER`) checked in `WitnessCreateActuator.validate()` before allowing `witnessStore.put(...)`, for example:
```java
if (witnessStore.getAllWitnesses().size() >= dynamicStore.getMaxWitnessNumber()) {
    throw new ContractValidateException("Witness number exceeds the maximum limit");
}
```
Additionally, avoid materializing/sorting the full witness list on read paths that only need a bounded page (`getWitnessList`, `getPaginatedNowWitnessList`), and consider making the registration cost scale with the current witness count to further discourage list inflation.

### Proof of Concept
Not independently executable within this analysis (no test harness access), but the exploit path is straightforward and directly mirrors the reference POC pattern: repeatedly submit `WitnessCreateContract` transactions from N distinct funded accounts (each holding `AccountUpgradeCost`), each of which passes `WitnessCreateActuator.validate()` unconditionally and calls `witnessStore.put(...)`, growing `WitnessStore` without bound; then observe the linear/superlinear increase in the time taken by `MaintenanceManager.doMaintenance()` and by `Wallet.getWitnessList()` / `getPaginatedNowWitnessList()` as N grows, as shown by the code paths cited above.

  public WitnessList getPaginatedNowWitnessList(long offset, long limit) throws
      MaintenanceUnavailableException {
    if (limit <= 0 || offset < 0) {
      return null;
    }
    if (limit > WITNESS_COUNT_LIMIT_MAX) {
      limit = WITNESS_COUNT_LIMIT_MAX;
    }

    /*
      In the maintenance period, the VoteStores will be cleared.
      To avoid the race condition of VoteStores deleted but Witness vote counts not updated,
      return retry error.
      Only apply to requests that rely on the latest block,
      which means the normal fullnode requests with HEAD cursor.
    */
    boolean isMaintenance = chainBaseManager.getDynamicPropertiesStore().getStateFlag() == 1;
    if (isMaintenance && !Args.getInstance().isSolidityNode() && getCursor() == Cursor.HEAD) {
      String message =
          "Service temporarily unavailable during maintenance period. Please try again later.";
      throw new MaintenanceUnavailableException(message);
    }
    // It contains the final vote count at the end of the last epoch.
    List<WitnessCapsule> witnessCapsuleList = chainBaseManager.getWitnessStore().getAllWitnesses();
    if (offset >= witnessCapsuleList.size()) {
      return null;
    }

    VotesStore votesStore = chainBaseManager.getVotesStore();
    // Count the vote changes for each witness in the current epoch, it is maybe negative.
    Map<ByteString, Long> countWitness = countVote(votesStore);

    // Iterate through the witness list to apply vote changes and calculate the real-time vote count
    witnessCapsuleList.forEach(witnessCapsule -> {
      long voteCount = countWitness.getOrDefault(witnessCapsule.getAddress(), 0L);
      witnessCapsule.setVoteCount(witnessCapsule.getVoteCount() + voteCount);
    });

    // Use the same sorting logic as in the Maintenance period
    WitnessStore.sortWitnesses(witnessCapsuleList,
        chainBaseManager.getDynamicPropertiesStore().allowWitnessSortOptimization());

    List<WitnessCapsule> sortedWitnessList = witnessCapsuleList.stream()
        .skip(offset)
        .limit(limit)
        .collect(Collectors.toList());

    WitnessList.Builder builder = WitnessList.newBuilder();
    sortedWitnessList.forEach(witnessCapsule ->
        builder.addWitnesses(witnessCapsule.getInstance()));

    return builder.build();
  }
