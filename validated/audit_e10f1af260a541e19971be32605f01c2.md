## Cross-StackerDB Chunk Replay (Missing Domain Separation in Signature) - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
The signature that authenticates a StackerDB chunk write (`SlotMetadata::auth_digest`) commits only to `(slot_id, slot_version, data_hash)` and never to the target StackerDB smart-contract identifier. Because many distinct StackerDB contracts (e.g. the `signers-0-1`, `signers-0-2`, …, `signers-0-N` message-type contracts for the same signer set) assign the *same signer address to the same `slot_id`*, a signature that a signer legitimately produced for one contract's slot is also valid for another contract's identically-indexed slot. Any unprivileged network relay can capture such a chunk off the wire and replay it into the sibling contract, since each contract tracks its own independent Lamport version counter.

### Finding Description
`SlotMetadata::auth_digest` at [1](#0-0)  computes the signed digest as `SHA512/256(slot_id || slot_version || data_hash)`. There is no smart-contract identifier, chain id, or any other domain separator baked into what is signed. `SlotMetadata::verify` at [2](#0-1)  recovers the pubkey from that same digest and checks it against the expected principal — again with no notion of which contract the write targets.

Every enforcement path that accepts a chunk write resolves the "expected signer" independently per contract but then calls this contract-oblivious `verify()`:
- Local RPC write path: `StackerDBTx::try_replace_chunk` looks up `slot_validation.signer` for `(smart_contract, slot_id)` and calls `slot_desc.verify(&slot_validation.signer)` [3](#0-2) .
- P2P gossip/relay path: `StackerDBs::validate_received_chunk` looks up `get_slot_signer(smart_contract_id, data.slot_id)` and again calls `slot_metadata.verify(&addr)` with the same contract-independent digest [4](#0-3) .

Crucially, the same underlying slot assignment is shared across many sibling contracts for the same signer set. The boot contract `signers.clar` stores exactly one slot list per signer-set parity (`stackerdb-signer-slots-0` / `-1`) and every `signers-{set}-{message_id}` contract for `message_id` in `0..SIGNER_SLOTS_PER_USER` reads that *same* list via `stackerdb-get-signer-slots-page` [5](#0-4) . This is confirmed by the test that iterates `message_id in 0..SIGNER_SLOTS_PER_USER` and asserts every `signers-{set}-{message_id}` contract returns the identical slot list [6](#0-5) . Consequently, a given signer address occupies the same `slot_id` in every one of these sibling contracts, and each contract maintains its own independent per-slot version counter (`create_stackerdb`/`get_slot_validation` are keyed per `(stackerdb_id, slot_id)`) [7](#0-6) .

An unprivileged attacker who merely observes a legitimately-signed chunk that signer `S` posted to slot `k` in contract `signers-0-1` can resubmit that exact `(slot_id, slot_version, sig, data)` tuple to contract `signers-0-2` (a different message-type StackerDB used by the same signer set) via the public `POST /v2/stackerdb/{address}/{contract}/chunks` endpoint [8](#0-7) . Because `signers-0-2`'s slot `k` has an independent (and typically lower) stored version, the replayed write passes all checks — chunk size, `expected_version`, `verify()`, `max_writes` — in `try_replace_chunk` [9](#0-8)  and is accepted as if signer `S` had authored that content for that contract/message type.

Once stored, this forged-context chunk is also propagated network-wide: any peer receiving a `StackerDBChunkInv`/push for `signers-0-2` will independently run `validate_received_chunk`, which performs the identical contract-oblivious signature check, and will accept and further relay it [10](#0-9) .

### Impact Explanation
This is a direct analog of the reported EIP-712 replay bug class: the signature lacks a domain separator that binds it to the specific "verifying contract" (here, the specific StackerDB smart contract), so a message authorized for context A is accepted as valid for context B. Concretely this allows an unauthenticated network participant to:
- Write attacker-selected but signer-authenticated data into a StackerDB slot that the true signer never intended for that contract/message type (unauthorized write to state), and
- Have that forged-context chunk propagate network-wide via the normal StackerDB sync/relay path, since remote validation performs the same contract-oblivious check.

This matches the "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" impact tiers.

### Likelihood Explanation
Exploitation requires only passively observing one legitimately-signed chunk on the wire (e.g. any signer-to-signer StackerDB message, which are routinely broadcast) and re-POSTing it to a sibling contract's public HTTP endpoint or injecting it via `StackerDBPushChunk` gossip — no private key, no privileged role, and no complex timing is required. The precondition (same signer occupying the same `slot_id` across sibling `signers-{set}-{message_id}` contracts) is guaranteed by the current boot contract implementation, not merely probable.

### Recommendation
Bind the signed digest to the destination StackerDB context: include the `QualifiedContractIdentifier` (and ideally a chain/network identifier) inside `SlotMetadata::auth_digest` in `libstackerdb/src/libstackerdb.rs`, and thread the contract id into `sign()`/`verify()` call sites in `stackslib/src/net/stackerdb/db.rs` and `stackslib/src/net/stackerdb/mod.rs`. This is a wire-format/signature-scheme change and needs coordinated versioning across `libstackerdb`, `stacks-signer`, and all StackerDB consumers.

### Proof of Concept
1. Signer `S` signs and posts chunk `(slot_id=5, slot_version=3, data=D)` to `signers-0-1`; it is accepted (`try_replace_chunk` succeeds).
2. Attacker (no keys needed) observes this chunk over the network (e.g. via `StackerDBChunkInv`/`StackerDBGetChunk` or the public HTTP GET chunk endpoint).
3. Attacker POSTs the identical `(slot_id=5, slot_version=1, sig, D)` (or any version above `signers-0-2`'s current stored version but still using the captured signature/digest, since `slot_version` is part of the signed digest — the attacker simply needs `signers-0-2` slot 5's stored version to be below the captured `slot_version`) to `signers-0-2` via `POST /v2/stackerdb/{S}/signers-0-2/chunks`.
4. Because `signers-0-2` assigns the same slot 5 to `S` (per `stackerdb-get-signer-slots-page`) and its independent version counter starts lower, `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` accepts the write: chunk-size OK, `slot_desc.verify(&slot_validation.signer)` succeeds (same digest, same signer), version check passes against `signers-0-2`'s own counter.
5. The forged-context chunk is now canonical in `signers-0-2` and propagates to peers via the normal `validate_received_chunk`/push-relay path in `stackslib/src/net/stackerdb/mod.rs`.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
