### Title
Denial of service via unmetered `estimateEnergy` binary-search re-execution of arbitrary TVM code — (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
The `estimateEnergy` API path (reachable via gRPC `estimateEnergy`, HTTP `EstimateEnergyServlet`, and JSON-RPC `eth_estimateGas`) lets **any anonymous client** repeatedly force the node to fully re-execute arbitrary TVM bytecode via a fee/energy binary search, with no cost or quota debited from the caller, analogous to the neutron bug where an unauthenticated/low-privileged query created resources "unconstrained by the user's quota," enabling DoS.

### Finding Description
`Wallet.estimateEnergy` runs a binary search over `feeLimit` values from `0` up to `dps.getMaxFeeLimit()`, each iteration invoking `cleanContextAndTriggerConstantContract` → `callConstantContract` → `VMActuator.execute`, which fully executes the target contract's bytecode as a constant call: [1](#0-0) [2](#0-1) 

Each of these constant-call executions is subject only to a CPU-time deadline (`getMaxCpuTimeOfOneTx`/`constantCallTimeoutMs`), not to the caller's actual account energy/bandwidth balance — `callConstantContract` never debits the caller and does not require a signed, broadcast transaction: [3](#0-2) 

Because the search additionally retries on `Program.OutOfTimeException` up to `estimateEnergyMaxRetry` (default 3) times per step, and the binary search itself runs `O(log2(maxFeeLimit/energyFee))` steps, a single client request to `estimateEnergy`/`eth_estimateGas` can trigger many dozens of full-length TVM executions of an attacker-supplied (or attacker-deployed) contract that is deliberately crafted to consume close to the CPU-time limit on every call (e.g., near-infinite loop bounded only by energy limit). This differs from a normal `triggerconstantcontract` call, which executes the code only once per request.

The entry points are unauthenticated and reachable without any signed transaction: [4](#0-3) [5](#0-4) [6](#0-5) 

This is analogous to CVE-2023-3637's root cause: a query-type request that creates node-side resource consumption not gated by the requester's quota/authorization, permitting repeated cheap requests to amplify into heavy backend work — here CPU-bound VM executions instead of neutron's unconstrained security-group DB rows.

### Impact Explanation
Repeated calls from a single unauthenticated client (no TRX fee, no signed transaction, no energy ownership required) can force the full node to spend large amounts of CPU executing attacker-controlled bytecode multiple times per request (multiplied by binary-search steps and retries). At scale this can degrade or exhaust node CPU resources used for serving RPC/HTTP/JSON-RPC clients, an "API the node can no longer serve" condition consistent with the required impact bar.

### Likelihood Explanation
The `estimateEnergy`/`eth_estimateGas` endpoints are commonly exposed to the public in wallet/dApp tooling deployments. Triggering the amplification requires only: (1) a deployed contract with a CPU/energy-heavy view/pure function (trivial and cheap for the attacker to deploy once), and (2) repeated unauthenticated calls to `estimateEnergy`/`eth_estimateGas`. No special privileges, signatures, or balance are needed by the caller of the estimate endpoint itself. This is somewhat mitigated by `RateLimiterServlet` on the HTTP path and by `estimateEnergyMaxRetry`/CPU-time clamps, but the gRPC `estimateEnergy` service does not appear to use the same HTTP rate limiter, and even bounded per-request amplification (log2 binary-search steps × retries) multiplies attacker cost advantage versus a single `triggerconstantcontract` call.

### Recommendation
- Cap the number of full VM executions per `estimateEnergy` request more aggressively (e.g., reduce binary-search precision/step count or use a fixed small set of probe points) and enforce a strict wall-clock/CPU budget for the *entire* `estimateEnergy` call, not just per sub-execution.
- Apply consistent rate limiting (IP-based / global QPS) to the gRPC `estimateEnergy` endpoint identical to what protects the HTTP servlet.
- Consider requiring `feeLimit`/energy pre-checks against the caller-supplied `owner_address`'s actual resources before allowing repeated re-execution, or charging a small non-refundable cost for constant-call/estimate requests to remove the free amplification factor.

### Proof of Concept
1. Deploy a trivial contract with a `view`/`pure` function whose execution time scales with an input parameter (e.g., a bounded loop that nearly reaches the max CPU-time/energy limit for constant calls).
2. Call `/wallet/estimateenergy` (or gRPC `estimateEnergy`, or JSON-RPC `eth_estimateGas`) targeting that function repeatedly and concurrently from many connections, without ever broadcasting a signed transaction or paying TRX fees.
3. Each request causes the node to execute the function body up to `log2(maxFeeLimit/energyFee) + estimateEnergyMaxRetry` times inside `Wallet.estimateEnergy`'s binary search, multiplying CPU cost per client request; observe the full node's RPC/HTTP serving latency degrade under concurrent load.

Note: I could not fully verify at what QPS/thread-pool level the gRPC `estimateEnergy` service is protected (if at all) versus the HTTP servlet's `RateLimiterServlet`, so the exact exploitability threshold under default configuration is uncertain and would need runtime confirmation.
