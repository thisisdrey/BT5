### Title
Unguarded raw-calldata word indexing in `ValidateMultiSign` precompile causes uncaught exception on malformed input - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
Any account can deploy a contract and issue a `CALL`/`STATICCALL` to the built-in precompiled contract at address `0x0a` (`ValidateMultiSign`). The precompile's `execute()` method parses fixed offsets out of the raw calldata (`words[0]`, `words[1]`, `words[2]`, and later `words[3]`) before any length/shape validation is performed, unless a specific hardfork guard is active.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute(byte[] rawData)` calls `DataWord.parseArray(rawData)` and immediately indexes `words[0]`, `words[1]`, `words[2]` to build `address`, `permissionId`, and `data` [1](#0-0) . The only defensive check, `isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)`, is gated behind `VMConfig.allowTvmOsaka()` [2](#0-1) . When that flag is not active, calldata shorter than the 3 required head words reaches the unguarded array indexing directly, and the only `try/catch` in the method wraps solely the later permission/weight logic, not the initial parsing [3](#0-2) .

Critically, unlike its sibling `BatchValidateSign`, which wraps its entire `doExecute()` call in a top-level `catch (Throwable t)` [4](#0-3) , `ValidateMultiSign.execute()` has **no such outer catch**. The exception raised by the malformed-input decoder therefore propagates directly out of `contract.execute(data)` in `Program.callToPrecompiledAddress` [5](#0-4) , which itself has no surrounding try/catch, and further up through `OperationActions.exeCall` [6](#0-5) .

This is confirmed directly by the project's own regression tests, which document the pre-fix ("TIP-854") behavior as: *"Pre-activation: decoder may throw — this is the existing behaviour... this precompile has no outer catch, so a too-short input raises inside the decoder; that is the documented pre-activation failure mode the TIP explicitly preserves."* [7](#0-6) . This is the exact bug-class match to CVE-2015-5316: a message/input handler that assumes a specific structural precondition (well-formed ABI-shaped calldata / a completed request-response handshake) and dereferences/indexes into that structure without validating it first, resulting in an unhandled runtime fault.

### Impact Explanation
If an uncaught `ArrayIndexOutOfBoundsException`/`RuntimeException` from `ValidateMultiSign.execute()` is not fully absorbed by higher-level transaction-processing exception handling, it could propagate into block/transaction application, potentially halting or crashing node processing of that transaction/block (denial of service). I was not able to fully trace, within the available tool budget, whether `VM.java`'s opcode-stepping loop or `Runtime`/`TransactionTrace` ultimately catches this generic exception and safely converts it into a reverted/failed transaction (the standard, expected fail-safe behavior for EVM-derived execution engines) rather than letting it escalate to a node-level crash. This is the key uncertainty in this finding — confirming whether it is contained at the transaction level (low/no impact) or escapes further (node crash/halt, matching the CVE's DoS impact) requires additional tracing of `VM.play()`/`Runtime.execute()` exception handling that I could not complete.

### Likelihood Explanation
Trivially reachable: any address can deploy a minimal contract that issues a `CALL` or `STATICCALL` to address `0x0a` with calldata shorter than 3 words (96 bytes) or otherwise malformed relative to the expected ABI shape, with no special privilege, signature scheme, or SR/witness/peer role required — matching the "unprivileged transaction broadcaster / contract deployer" reachability bar.

### Recommendation
Apply the same defensive posture already used for `BatchValidateSign` to `ValidateMultiSign`: validate/guard the calldata shape (or wrap the entire `execute()` body, including the initial `DataWord.parseArray`/indexing, in a `try/catch (Throwable)`) unconditionally, rather than only when `VMConfig.allowTvmOsaka()` is active. Confirm and, if necessary, harden the top-level exception handling in `VM.java`/`Runtime` around precompiled-contract calls so that no precompile can throw an exception that escapes transaction-level containment.

### Proof of Concept
1. Deploy any contract containing a low-level `call(gas, 0x0a, 0, in, insize, out, outsize)` (Solidity `address(0x0a).call(...)`), reachable by any unprivileged account.
2. Invoke it with `insize` set to fewer than 96 bytes (3 words) of calldata (e.g., empty/zero-length payload) while the network has not activated the TIP-854/`allowTvmOsaka` hardfork guard.
3. `PrecompiledContracts.ValidateMultiSign.execute()` calls `DataWord.parseArray(rawData)` and indexes `words[0]`/`words[1]`/`words[2]`, throwing an unguarded exception, matching the behavior explicitly documented in `ValidateMultiSignContractTest.testTip854PreActivationNoOp` [8](#0-7) .

**Note on confidence:** This finding is based on confirmed source-level evidence (no outer catch in `ValidateMultiSign.execute()`, and test comments explicitly describing the pre-activation throw as real, documented behavior), but I could not verify within the available budget whether the resulting exception is ultimately absorbed safely by the broader transaction-execution pipeline (which would reduce this to a per-transaction revert, not a node crash) or escalates to a genuine node-level fault. I recommend a Devin session trace `VM.play()` → `Runtime.execute()` → `TransactionTrace`/`Manager` exception handling paths to confirm actual blast radius before treating this as confirmed Medium/High severity.
