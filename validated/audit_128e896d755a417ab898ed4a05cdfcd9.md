### Title
DebtToken deactivation does not stop new debt issuance — `issue` is missing the `onlyIfDebtTokenIsActive` check applied to all other mint paths - ([File: contracts/DebtToken.sol])

### Summary
The referenced bug class is a sanity check that enumerates valid variants but fails to cover a newly added one, so an attacker can route through the uncovered variant. In Metronome, `DebtToken` enforces an `onlyIfDebtTokenIsActive` gate on the newer mint paths `flashIssue` and `mint`, but the original public entry point `issue` was never given that modifier. As a result, deactivating a `DebtToken` (the intended kill-switch for halting new borrowing against that synthetic asset) does not actually stop issuance — any user can keep minting synth via `issue`.

### Finding Description
In `contracts/DebtToken.sol`, the three issuance entry points are guarded inconsistently:

- `flashIssue(to_, amount_)` — gated by `onlyIfSmartFarmingManager`, `whenNotShutdown`, `nonReentrant`, `onlyIfSyntheticTokenExists`, **and `onlyIfDebtTokenIsActive`** (lines 281-293).
- `mint(to_, amount_)` — gated by `onlyIfSmartFarmingManager`, `whenNotShutdown`, `nonReentrant`, `onlyIfSyntheticTokenExists`, **and `onlyIfSyntheticTokenIsActive`** (lines 328-339).
- `issue(amount_, to_)` — gated only by `whenNotShutdown`, `nonReentrant`, `onlyIfSyntheticTokenExists` (lines 235-244). There is **no** `onlyIfDebtTokenIsActive` check.

`issue` is an external, unprivileged function: any EOA calls it directly with an arbitrary `amount_`. It accrues interest, reads `pool.debtPositionOf(_msgSender)` for the issuable limit, checks `amount_ <= quoteUsdToToken(syntheticToken, issuableInUsd)`, then mints debt shares via `_mint` and mints the synthetic token to `to_` (lines 246-268).

The deactivation flag (`isActive` on the debt token, toggled by the governor) exists precisely to halt new debt on that instrument — e.g., when a collateral's oracle is degraded, a synth is being sunset, or bad debt is accumulating. The newer privileged paths correctly respect it; the legacy public path does not. The analog holds: the validity check was applied to the new variants (`flashIssue`, `mint`) but not to the pre-existing variant (`issue`), breaking the "deactivated ⇒ no new issuance" invariant.

Caveat: the `SyntheticToken._mint` internal check `onlyIfSyntheticTokenIsActive` still applies, so this only bypasses *debt-token-level* deactivation, not synthetic-token-level deactivation. If governance uses the debt-token flag independently (which the existence of `onlyIfDebtTokenIsActive` on `flashIssue` implies is intended), the bypass is real.

### Impact Explanation
Direct, unprivileged bypass of a security control. When a `DebtToken` is deactivated — the expected response to a distressed collateral, malfunctioning oracle feed, or an emergency where new borrowing must stop — any attacker can continue calling `issue` to mint new synthetic debt. If deactivation was triggered because collateral pricing or a deposit token is compromised, continued issuance mints synths against degraded collateral and can create bad debt / protocol insolvency, or dilute the synth at the expense of other holders. Even in the benign case, it defeats the protocol's own emergency-halt semantics for a specific token without requiring any privileged role.

### Likelihood Explanation
Likelihood of the *condition* (a deactivated debt token) depends on governance action, but the *bypass* itself is fully unprivileged and deterministic: `issue` requires only an open collateral position with issuable capacity, which any attacker can set up beforehand with a cheap deposit. No flash loan, oracle manipulation, or privileged access is needed — just a pre-existing deposit and a call to `issue` after deactivation.

### Recommendation
Add `onlyIfDebtTokenIsActive` (and consider `onlyIfSyntheticTokenIsActive` for defense-in-depth) to `DebtToken.issue` so that the deactivation flag uniformly covers all issuance variants, mirroring how `flashIssue` is gated. More generally, consolidate the issuance preconditions into a single shared modifier/internal check so future variants cannot be added without inheriting the full invariant set.

### Proof of Concept
Hardhat-style PoC (assumes standard pool/debtToken/syntheticToken fixtures):

```ts
// Setup: user deposits collateral in a DepositToken, giving issuable capacity.
await depositToken.connect(alice).deposit(collateralAmount, alice.address);

// Governor deactivates the debt token to halt new issuance.
await debtToken.connect(governor).toggleIsActive(); // isActive = false

// Sanity: privileged paths are now blocked.
await expect(
  debtToken.connect(sfm).flashIssue(alice.address, mintAmount)
).to.be.reverted; // DebtTokenIsNotActive
await expect(
  debtToken.connect(sfm).mint(alice.address, mintAmount)
).to.be.reverted; // DebtTokenIsNotActive

// BUG: the public path still succeeds.
await debtToken.connect(alice).issue(mintAmount, alice.address);
expect(await syntheticToken.balanceOf(alice.address)).to.eq(mintAmount); // issuance bypassed
```

**Uncertainty note:** I was unable to fully verify the exact revert name/behavior of `onlyIfDebtTokenIsActive` or confirm whether `issue` is additionally re-checked inside `Pool` (e.g., a pool-level `issue` wrapper), because the final grep results returned only match counts, not contents. If `Pool` re-validates the active flag on every `issue` call path, the finding's reachability would need re-evaluation.
