### Title
`write_freq` StackerDB config value is validated and stored but never enforced as a write-rate gate - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
`StackerDBConfig.write_freq` is documented as "the minimum wall-clock time between writes to the same slot," is parsed from the controlling smart contract with strict bounds checking, and the `net_error::TooFrequentSlotWrites` variant exists specifically to report a violation of this bound. However, no code path that actually admits a write into a StackerDB slot (`StackerDBTx::try_replace_chunk`) ever constructs or checks against `TooFrequentSlotWrites`, so the "minimum write interval" invariant is never enforced at the point where writes are accepted, only consulted opportunistically by the pull-based sync scheduler's fetch-throttling heuristic.

### Finding Description
`StackerDBConfig` defines `write_freq` with the doc comment "minimum wall-clock time between writes to the same slot" [1](#0-0) . The contract-config loader in `config.rs` validates that `write-freq` is present and within `u64::MAX`, treating it as a meaningful, enforced protocol parameter [2](#0-1) . The corresponding error type `net_error::TooFrequentSlotWrites(deadline)` is defined and has a `Display` implementation [3](#0-2) , and it is referenced only in `stackslib/src/net/mod.rs` — nowhere else in the codebase is it ever constructed or returned (confirmed via full-repo search).

The single authoritative write path, `StackerDBTx::try_replace_chunk`, checks: chunk size cap, slot existence, signer correctness, staleness (version), and `max_writes` — but never `write_freq` or slot write timestamps [4](#0-3) . This function is the exact code invoked by the unauthenticated-but-signed HTTP write RPC (`RPCPostStackerDBChunkRequestHandler::try_handle_request`) that any remote peer with a slot-owning key can call [5](#0-4) .

The read-side validator `validate_received_chunk`, used for both pulled and gossip-pushed chunks, explicitly documents that it "does not check write frequency, since the caller has different ways of doing this" [6](#0-5) . The only place `write_freq` is actually consulted is `StackerDBSync`'s pull-scheduling logic, which uses it purely to decide whether to *bother fetching* a chunk from a peer, skipping the chunk if it was "written too frequently" locally — this is a scheduling optimization, not a security gate on writes [7](#0-6) . Because the sync fetch skip only suppresses redundant downloads (and only from the puller's perspective of its own last-write timestamp), it does not stop a slot owner from posting writes to the HTTP endpoint faster than `write_freq`, nor does it stop such over-frequent chunks from being relayed once accepted via `try_replace_chunk` and gossiped via `process_uploaded_stackerdb_chunks`/`process_stacker_db_chunks` [8](#0-7) .

This is the direct analog of the reported "unused mapping" pattern: a security-relevant piece of state (`write_freq` / the `deprecated`-mapping equivalent) is read in one place but the logic that should act on it (rejecting/gating writes, i.e., "unfinished contract logic") is missing at the actual enforcement point, leaving the protocol's documented invariant unimplemented.

### Impact Explanation
Any legitimate StackerDB slot owner (someone holding the private key for a configured slot — e.g., a signer's `.signers-*` StackerDB slot) can write to their slot as fast as the network and `max_writes`/`max_neighbors` cap allow, completely ignoring the contract-specified `write_freq` throttle. Since `write_freq` is a network-wide bandwidth/DoS-shaping parameter meant to bound how much a single slot can push into the P2P network (each write triggers a broadcast in `process_stacker_db_chunks`/`process_uploaded_stackerdb_chunks`), its absence at the enforcement point allows a bounded-compute/bandwidth amplification against the whole StackerDB gossip network by a party who only needs to control one already-authorized signing key (not an admin, not the node's own key). This falls into the "bounded compute DoS on a read endpoint"/write-amplification class rather than a full unauthenticated compromise, since the actor must already be an authorized slot signer — but it defeats an explicit rate-limit control that operators rely on to bound propagation volume from any single participant.

### Likelihood Explanation
High likelihood of the *bug* (missing enforcement) being real: it is directly demonstrated by reading `try_replace_chunk` (no `write_freq`/timestamp check present) and by the dead `TooFrequentSlotWrites` variant that is never constructed anywhere in the codebase. Exploitability requires only being an authorized signer for at least one StackerDB slot (a role many signer-set participants already hold in production, e.g., every `.signers-*` and `.miners` participant), and does not require the node's own key or any admin privilege — just posting chunks via the standard `/v2/stackerdb/.../chunks` RPC faster than the configured `write_freq`.

### Recommendation
Enforce `write_freq` at the actual write-acceptance point in `StackerDBTx::try_replace_chunk` (or immediately before it, using `get_slot_write_timestamps`/`get_slot_validation`), returning `net_error::TooFrequentSlotWrites` when a chunk for a slot is submitted before `write_time + write_freq` has elapsed, and surface this via a new `StackerDBErrorCodes` case (analogous to `TooManySlotWrites`) in the HTTP POST handler so remote posts are also rejected rather than silently accepted and rebroadcast.

### Proof of Concept
1. Configure/observe a live StackerDB contract with `write-freq > 0` (any `.signers-*` contract deployment where the operator intends slot writes to be rate-limited).
2. As the holder of one slot's private key, sign and POST successive `StackerDBChunkData` payloads with monotonically increasing `slot_version` to `POST /v2/stackerdb/<addr>/<contract>/chunks` back-to-back, faster than the configured `write_freq` interval.
3. Observe that `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` accepts every version-incrementing, correctly-signed, non-oversized write regardless of timing (no `TooFrequentSlotWrites` is ever returned), and each accepted write is broadcast to the P2P network via `Relayer::process_uploaded_stackerdb_chunks`, confirming the `write_freq` throttle is never enforced end-to-end.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }

    pub fn process_uploaded_stackerdb_chunks(
        &mut self,
        rc_consensus_hash: &ConsensusHash,
        uploaded_chunks: Vec<StackerDBPushChunkData>,
        event_observer: Option<&dyn StackerDBEventDispatcher>,
    ) {
        let mut all_events: HashMap<QualifiedContractIdentifier, Vec<StackerDBChunkData>> =
            HashMap::new();
        for chunk in uploaded_chunks.into_iter() {
            // Always forward the event to ensure the local signer receives it.
            if event_observer.is_some() {
                if let Some(events) = all_events.get_mut(&chunk.contract_id) {
                    events.push(chunk.chunk_data.clone());
                } else {
                    all_events.insert(chunk.contract_id.clone(), vec![chunk.chunk_data.clone()]);
                }
            }

            if chunk.rc_consensus_hash != *rc_consensus_hash {
                debug!("Not rebroadcasting stale uploaded StackerDB chunk";
                           "stackerdb_contract_id" => %chunk.contract_id,
                           "slot_id" => chunk.chunk_data.slot_id,
                           "slot_version" => chunk.chunk_data.slot_version,
                           "chunk.rc_consensus_hash" => %chunk.rc_consensus_hash,
                           "network.rc_consensus_hash" => %rc_consensus_hash);
                continue;
            }

            debug!("Got uploaded StackerDB chunk"; "stackerdb_contract_id" => %chunk.contract_id, "slot_id" => chunk.chunk_data.slot_id, "slot_version" => chunk.chunk_data.slot_version);

            let msg = StacksMessageType::StackerDBPushChunk(chunk);
            if let Err(e) = self.p2p.broadcast_message(vec![], msg) {
                warn!("Failed to broadcast StackerDB chunk: {e:?}");
            }
        }
        if let Some(observer) = event_observer {
            for (contract_id, new_chunks) in all_events.into_iter() {
                observer.new_stackerdb_chunks(contract_id, new_chunks);
            }
        }
    }
