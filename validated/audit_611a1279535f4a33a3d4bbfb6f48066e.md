### Title
Stuck `has_in_flight_tx` reentrancy guard permanently freezes the eth-implicit Wallet Contract when the unlocking callback runs out of gas - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The eth-implicit Wallet Contract implements a mutex-style reentrancy guard (`has_in_flight_tx`) to serialize `rlp_execute` calls while a cross-contract promise chain is outstanding. The guard is set to `true` synchronously and only ever reset to `false` inside a `#[private]` callback (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`) that runs in a *separate, dependent receipt* after the user-chosen target contract has been called. Because a failing receipt is fully rolled back in nearcore's runtime, if that unlocking callback itself fails (most plausibly by running out of its small, fixed static gas budget while processing/forwarding an oversized return value from the target contract), the `has_in_flight_tx = false` write is discarded while the earlier `has_in_flight_tx = true` write (from the initiating receipt) remains committed. There is no other entry point capable of resetting the flag, so the wallet is permanently locked out of `rlp_execute` from then on.

### Finding Description
`WalletContract::rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:89-128`) guards against concurrent execution: [1](#0-0) 

The invariant documented on the struct is that `has_in_flight_tx` must be `true` whenever a mutable method returns a promise and `false` otherwise: [2](#0-1) 

The flag is only cleared inside the `#[private]` callbacks that are scheduled to run *after* the promise chain (which invokes the user-chosen `target` contract) resolves, e.g. the generic/catch-all action path: [3](#0-2) 

and the callback itself: [4](#0-3) 

Crucially, in this generic (catch-all) path the callback is attached with a fixed, non-scaled static gas amount, `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas), regardless of how large the return value produced by the (attacker- or third-party-controlled) `target` contract's promise result may be: [5](#0-4) 

`rlp_execute_callback` copies the entire `PromiseResult::Successful(value)` into the returned `ExecuteResponse`, which `near-sdk` then serializes as the method's return value — work whose cost scales with the size of `value`, not with the fixed gas budget allocated to the callback.

Per nearcore's runtime spec, a receipt whose action result is `Err` (including a gas-exhaustion panic) is fully rolled back, discarding *all* state writes made in that receipt, while previously committed receipts are untouched: [6](#0-5) 

Consequently: the initiating receipt (running `rlp_execute`) commits `has_in_flight_tx = true`. If the subsequent callback receipt (running `rlp_execute_callback`) fails — e.g. because processing/copying a large return value from the target contract exceeds the fixed 5 Tgas budget — its attempted write of `has_in_flight_tx = false` is rolled back, but the earlier `true` write is not undone (it lives in a different, already-committed receipt). No other method in the contract (only the private callbacks and `ban_relayer`, which is only reachable from within `rlp_execute`'s own successful/erroring flow) can reset the flag. From this point, every future call to `rlp_execute` is rejected at the guard check: [7](#0-6) 

### Impact Explanation
This constitutes permanent freezing of funds: the eth-implicit Wallet Contract account becomes permanently unable to execute any Ethereum-emulated transaction (transfers, ERC-20 emulation, function calls, or key management) once the guard is stuck, since `rlp_execute` is the sole mutable entry point and it is unconditionally blocked by the stuck flag. Any $NEAR or token balances held by that account become inaccessible to their owner going forward, with no recovery path in the contract itself (no admin reset, no timeout/expiry logic for `has_in_flight_tx`).

### Likelihood Explanation
The likelihood is that any real-world usage of the wallet's generic function-call path (calling into contracts other than the specifically-optimized ERC-20/EOA-emulation paths) attaches only a fixed 5 Tgas static budget for the unlocking callback (`RLP_EXECUTE_CALLBACK_GAS`), independent of the response size of the target contract. Any target that returns a return value large enough to exceed that budget when copied/serialized (well within protocol-allowed receipt/return-value sizes) will trigger the stuck state. This can occur unintentionally (a legitimate but "chatty" contract call) or be deliberately triggered by any contract the wallet owner or a relayer causes to be invoked as `target`, without requiring any special privilege — an ordinary signed transaction routed through `rlp_execute` is sufficient.

### Recommendation
- Do not gate `has_in_flight_tx` reset behind the success of a downstream FunctionCall action whose gas usage depends on untrusted/attacker-influenced data size; instead reset the flag (or make its clearing independent of the forwarded call's gas cost) using an unconditional, minimal-gas final step, or bound/cap the amount of data copied back from `target`'s promise result.
- Scale the static gas attached to `rlp_execute_callback` (and the other unlock callbacks) to account for the maximum possible promise-result size, not a small fixed constant, in every action path — not just the ERC-20/address-check paths that already do `.saturating_add(action.gas())`.
- Add a recovery mechanism (e.g., a way to force-clear `has_in_flight_tx` after receipts are provably no longer pending, or a protocol-level timeout) so a single failed callback cannot permanently brick the account.

### Proof of Concept
1. Deploy an eth-implicit Wallet Contract for address `A` and fund it with $NEAR.
2. Have the owner (or any relayer) sign/submit an RLP transaction via `rlp_execute` whose `to`/`target` points at a contract `T` that, on the invoked method, returns a large successful return value (sized close to the maximum receipt/return-value limit allowed by the protocol) — this is a legitimate action the owner intended to perform, going through the catch-all branch that attaches only `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas) to `rlp_execute_callback`.
3. `rlp_execute` commits `has_in_flight_tx = true` and schedules `action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:466-471`).
4. When `T`'s call resolves, `rlp_execute_callback` receives the large `PromiseResult::Successful(value)` and attempts to copy it into `ExecuteResponse.success_value` and return it; with only 5 Tgas allocated this exceeds the budget and the callback FunctionCall action fails with a gas-exhaustion error.
5. Per `apply_action_receipt`'s failure semantics, this callback receipt is rolled back entirely, so the `self.has_in_flight_tx = false` write never persists; the previously committed `true` from step 3 remains.
6. Any subsequent call to `rlp_execute` on this account now immediately returns `"Error: transaction already in progress, please try again later."` forever, since no code path exists to clear `has_in_flight_tx` outside of a successful callback — permanently freezing the account's funds. This can be observed against the existing test harness's `test_simultaneous_transactions` guard logic (`runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs:121-169`), which confirms the guard's blocking behavior, by instead crafting the second (or triggering) `target` response to exceed the callback's gas budget rather than issuing a second concurrent call.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
