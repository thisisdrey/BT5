## Analog Found: Integer-Division Rounding Lets a Maker's Remaining Tokens Be Taken for Zero Payment in the On-Chain Order Book

### Title
Zero-payment token transfer via integer-division rounding in `MarketSellAssetActuator.matchSingleOrder` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
TRON's on-chain order-book exchange (`MarketSellAssetContract`/`MarketSellAssetActuator`) settles trades atomically using integer arithmetic (`MarketUtils.multiplyAndDivide`). In the "taker > maker" branch, the code computes `makerBuyTokenQuantityReceive` via integer division and consumes the maker's *entire* remaining sell balance (marks the maker order `INACTIVE`) regardless of whether that computed payment rounds down to zero. The code even contains a comment acknowledging the assumption that this "would not happen," but the assumption is not defensively enforced, so an attacker-controlled taker order can, in specific residual-quantity/price combinations, drain a maker's remaining asset balance while paying zero (or near-zero) TRX/TRC10 tokens — directly analogous to the MakerDAO incident where collateral was auctioned off for $0 due to an unenforced price floor.

### Finding Description
In `matchSingleOrder` ( [1](#0-0) ), when the taker's desired buy quantity exceeds the maker's remaining sell quantity, the code computes:

```
makerBuyTokenQuantityReceive = MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)
MarketUtils.updateOrderState(makerOrderCapsule, State.INACTIVE, marketAccountStore);
if (makerBuyTokenQuantityReceive == 0) {
  // the quantity is too small, return the remain of sellToken to maker
  // it would not happen here
  // for the maker, when sellQuantity < buyQuantity, it will get at least one buyToken
  // even when sellRemain = 1.
``` [1](#0-0) 

This is contrasted with the earlier branch at line 406, where the actuator explicitly checks `if (takerBuyTokenQuantityRemain == 0)` and safely returns the taker's tokens instead of consuming them for free: [2](#0-1) 

The maker-side branch's zero-payment guard depends entirely on an informal invariant ("maker's sellQuantity < buyQuantity") that is asserted only in a comment, not validated anywhere in `validate()` of either `MarketSellAssetActuator` or of the maker's own original order creation. Order prices are set arbitrarily by users (any positive `sellTokenQuantity`/`buyTokenQuantity`, see the validate checks at [3](#0-2) ), so a maker order where `sellQuantity >= buyQuantity` (i.e., the maker is selling more units than it wants back) combined with a small residual (`makerSellRemainQuantity`) can drive `multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity)` to round down to 0, while `makerSellRemainQuantity` itself is still nonzero and gets fully consumed since the order is unconditionally marked `INACTIVE`.

An attacker can deliberately engineer this: place (or find) a resting maker order with the vulnerable price ratio, then submit a taker `MarketSellAssetContract` sized so the residual match against that maker order rounds the maker's payout to zero, extracting the maker's remaining asset balance for free.

### Impact Explanation
This allows unauthorized asset theft: a victim's resting order (asset balance already escrowed into the market subsystem via `transferBalanceOrToken`) can be fully drained by a taker who pays 0 (or negligible) TRX/TRC10 tokens in return, resulting in a concrete unbacked-value transfer / loss of funds for the maker — matching the "unauthorized account operation / theft of funds" bar in the validation rules.

### Likelihood Explanation
Reachable by any unprivileged account via a signed `MarketSellAssetContract` transaction (broadcastable once `supportAllowMarketTransaction` is enabled, see [4](#0-3) ). No special privilege is needed — only crafting order quantities to trigger integer-division rounding, which is a common and well-understood class of AMM/order-book rounding exploit. Exploitability depends on finding/creating a maker order with the specific unfavorable price ratio and residual size, which is feasible since a single account can act as both maker and taker (or collude across two accounts) to engineer the exact rounding condition.

### Recommendation
Add an explicit zero-payment guard in the "taker > maker" branch mirroring the taker-side guard: if `makerBuyTokenQuantityReceive == 0`, do not mark the maker order `INACTIVE` and do not consume `makerSellRemainQuantity`; instead treat it as an unmatchable/too-small residual and skip settlement for that maker order, or return the maker's un-paid-for remaining tokens rather than the trade completing at zero cost. The "would not happen" comment-based invariant should be replaced with a runtime check, since the invariant is not enforced by order-validation logic.

### Proof of Concept
Not directly executable without repo access to build/run tests; conceptually:
1. Account A creates a `MarketSellAssetContract` maker order selling `sellQuantity = 100` of asset X for `buyQuantity = 99` TRX (ratio close to/at parity or unfavorable), and it partially fills, leaving `makerSellRemainQuantity` small (e.g., `1`).
2. Attacker B submits a taker `MarketSellAssetContract` selling TRX to buy asset X such that in `matchSingleOrder`'s "taker > maker" branch, `multiplyAndDivide(1, 99, 100, ...)` computes to `0` due to integer truncation.
3. `makerOrderCapsule` is unconditionally set to `State.INACTIVE` and its `sellTokenQuantityRemain` (1 unit of X) is transferred to B, while `makerBuyTokenQuantityReceive == 0` means B pays A nothing for that residual unit.
4. This can be scaled/repeated across many orders to drain meaningful value at zero cost, analogous to the MakerDAO $0 liquidation auction. [1](#0-0)
