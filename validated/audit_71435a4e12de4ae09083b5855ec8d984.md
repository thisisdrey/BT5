### Title
Floating-point brokerage/vote-reward rate computation causes systematic reward miscalculation - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
The Neptune Mutual finding concerns a fee-rate computation that always deviates from the intended, configured value due to imprecise arithmetic and period accounting. java-tron has an analogous pattern in its Super Representative (SR) reward/brokerage distribution logic: it converts an integer basis-points-style rate into a `double`, multiplies it against the reward amount, and truncates the result with a `(long)` cast — the same class of "incorrect rate → incorrect fee/amount charged or paid" defect, but applied to on-chain block/vote reward accounting instead of an insurance policy fee.

### Finding Description
`MortgageService.payReward` computes the brokerage the witness keeps from a block/transaction-fee reward using floating-point division and multiplication, then truncates to `long`: [2](#0-1) 

```java
private void payReward(byte[] witnessAddress, long value) {
  long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
  int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
  double brokerageRate = (double) brokerage / 100;
  long brokerageAmount = (long) (brokerageRate * value);
  value -= brokerageAmount;
  delegationStore.addReward(cycle, witnessAddress, value);
  adjustAllowance(witnessAddress, brokerageAmount);
}
```

Similarly, the pre-VI ("old") per-voter reward algorithm distributes a witness's total cycle reward among its voters using a `double` vote-share ratio, then accumulates the truncated result into a `long`: [3](#0-2) 

```java
private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
  ...
  double voteRate = (double) userVote / totalVote;
  reward += voteRate * totalReward;
  ...
}
```

This function is reached whenever an account withdraws its accumulated staking reward via `WithdrawBalanceActuator`, which is a normal, unprivileged, signed `WithdrawBalanceContract` transaction that calls `mortgageService.withdrawReward(ownerAddress)` → `computeReward(...)`. It is also reached from `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, and `VoteWitnessActuator`, all of which invoke reward withdrawal/settlement as a side effect before mutating stake.

As with the Neptune Mutual bug, the computed "rate" (brokerage % or vote-share %) is not applied with exact fixed-point arithmetic. `double` cannot exactly represent most fractional percentages, and the truncating `(long)` cast discards the remainder each time instead of consistently rounding or carrying the remainder forward. Over many voters and many cycles this produces a persistent discrepancy between:
- the sum of rewards actually paid out to individual voters (`Σ computeReward(cycle, votes)` across all voters of a witness), and
- the total reward pool recorded for that witness/cycle in `DelegationStore.addReward` (which itself is set with the exact residual `value - brokerageAmount`, i.e., is internally consistent but the *voter-level* share calculation, done independently per withdrawal, is where the floating-point drift accumulates).

### Impact Explanation
Because `computeReward` truncates the fractional share (`voteRate * totalReward`) toward zero on every voter’s withdrawal independently, and there is no compensating remainder-redistribution step, the aggregate amount actually claimable by all voters of a witness across a cycle is not guaranteed to equal the reward pool recorded for that witness/cycle. Depending on rounding direction and ordering of withdrawals, this can either:
- permanently strand small amounts of reward that no voter can ever claim (locked/unspendable value), or
- in adversarial sequencing (e.g., a voter who structures many small votes/withdrawals to repeatedly benefit from truncation-in-their-favor), skew the effective payout ratio away from the intended vote-weighted formula.

This is the "incorrect fee/rate" bug class from the report, manifested as reward-accounting drift rather than a large single-transaction fund drain — it is a Medium-severity accounting integrity issue rather than defended-against theft, since no single call moves more than the already-computed `deltaVi`-scaled amount and callers cannot withdraw more than `computeReward` returns.

### Likelihood Explanation
`computeReward(long, List<Pair<byte[], Long>>)` (the "old algorithm" path) only executes for cycles prior to `dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle()`, per `MortgageService.computeReward(long,long,AccountCapsule)` (`chainbase/src/main/java/org/tron/core/service/MortgageService.java:199-230`), so on a chain where the new VI-based algorithm has been active from genesis or for a long time, this path is dormant/historical. It is nonetheless reachable and was clearly exercised historically (tests reference `ComputeRewardTest`), so on any deployment (or a fork/testnet) where the new algorithm's effective cycle is set high or unset, every voter's `WithdrawBalanceContract`, `UnfreezeBalance(V2)Contract`, and `VoteWitnessContract` transaction triggers this floating-point computation, making it trivially and repeatedly reachable by any unprivileged account.

### Recommendation
Replace the `double`-based percentage/ratio arithmetic in `MortgageService.payReward` and the old-algorithm `computeReward(long, List<Pair<byte[], Long>>)` with integer/`BigInteger` fixed-point math consistent with the newer VI-based algorithm (`computeReward(long beginCycle, long endCycle, AccountCapsule)` already uses `BigInteger` deltaVi scaling, at `chainbase/src/main/java/org/tron/core/service/MortgageService.java:215-227`). Track and carry forward rounding remainders per witness/cycle so the sum of amounts claimable by all voters exactly equals the recorded reward pool, eliminating systematic drift equivalent to the reported "incorrect fee rate" defect.

### Proof of Concept
Not directly demonstrable without executing a multi-cycle simulation in the existing test harness (`framework/src/test/java/org/tron/core/services/ComputeRewardTest.java`, `framework/src/test/java/org/tron/common/runtime/vm/VoteTest.java`), but the defect can be shown by: (1) forcing `getNewRewardAlgorithmEffectiveCycle()` to a value greater than the test cycle so the old algorithm path in `computeReward(long, List<Pair<byte[],Long>>)` is used, (2) setting up a witness with a reward pool `totalReward` and multiple voters whose `userVote/totalVote` fractions are not exact binary fractions (e.g., `1/3`), and (3) asserting that `Σ` of each voter's `WithdrawBalanceActuator`-triggered payout does not equal `totalReward` due to per-voter `(long)` truncation of the `double` vote-share multiplication in `MortgageService.java:184-186`.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
