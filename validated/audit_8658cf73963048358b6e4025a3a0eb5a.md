Audit Report

## Title
`fungible::Mutate::transfer` and `fungibles::Mutate::transfer` credit the destination with the full requested amount while discarding the actually-decreased amount from `decrease_balance`, breaking value conservation - ([File: substrate/frame/support/src/traits/tokens/fungible/regular.rs])

## Summary
The default `Mutate::transfer` implementation withdraws from `source` via `decrease_balance(source, amount, BestEffort, preservation, Polite)` but discards its `Result<Balance, _>` return value (the actual amount removed), then unconditionally calls `increase_balance(dest, amount, BestEffort)` with the original requested `amount` and returns `Ok(amount)`. [1](#0-0)  Because `decrease_balance` legitimately returns less than `amount` under `Precision::BestEffort` when the account's reducible balance is smaller than requested, this creates a case where `dest` gains more than `source` loses, i.e. value is created rather than conserved.

## Finding Description
`Unbalanced::decrease_balance` caps the actually-removed amount at `reducible_balance(who, preservation, force)` under `BestEffort` and returns the true amount removed via `old_balance.saturating_sub(new_balance)`: [2](#0-1)  `Mutate::transfer` ignores this return value (`Self::decrease_balance(source, amount, BestEffort, preservation, Polite)?;`) and deposits the *requested* `amount` into `dest`, then returns `Ok(amount)`: [3](#0-2)  The identical pattern exists in `fungibles::Mutate::transfer`. [4](#0-3) 

The pre-check `can_withdraw(source, amount).into_result(...)` does not reliably prevent the shortfall for the production `pallet-balances` implementation of `Inspect::can_withdraw`. That implementation hardcodes `Self::reducible_balance(who, Expendable, Polite)` internally regardless of the `preservation` value the caller ultimately passes to `transfer`: [5](#0-4)  Meanwhile `decrease_balance` (called later inside `transfer`) computes `reducible_balance(who, preservation, force)` using the *actual* `preservation` argument passed to `transfer`, e.g. `Preservation::Preserve` or `Protect`, which enforces stronger ED-protection and yields a smaller reducible amount than the `Expendable` value used by `can_withdraw`'s internal gate: [6](#0-5)  This mismatch between the pre-flight check (always `Expendable`-based) and the actual withdrawal cap (based on the real `preservation`) means `can_withdraw` can approve a transfer that `decrease_balance`'s `BestEffort` clamp subsequently only partially executes — and that shortfall is silently absorbed because the return value is discarded and `dest` is still credited the full nominal `amount`.

Note: the original claim's PoC used `Preservation::Expendable` as the triggering preservation; for the real `pallet_balances` implementation this specific case does not diverge, because `can_withdraw`'s internal check and `decrease_balance`'s cap both resolve to the same `reducible_balance(Expendable, Polite)` formula. The actual divergence requires `Preservation::Preserve` (or `Protect`), where `can_withdraw`'s gate (hardcoded to `Expendable`) is looser than the cap actually applied inside `decrease_balance`. The underlying code defect described (discarding `decrease_balance`'s actual returned amount, crediting `dest` with the nominal `amount`, returning `Ok(amount)` unconditionally) is present and verified by direct code inspection.

## Impact Explanation
Any pallet that calls the default `fungible::Mutate::transfer` / `fungibles::Mutate::transfer` with `Preservation::Preserve` or `Protect` on an account whose balance minus `amount` would fall below the existential deposit can trigger a shortfall: `source` loses only the amount capped by `reducible_balance(who, preservation, Polite)`, while `dest` is credited the full requested `amount`. This breaks the pairwise value-conservation invariant between source and destination accounts (`balance(dest)_after - balance(dest)_before` can exceed `balance(source)_before - balance(source)_after`), i.e., value is created rather than moved. This matches the "balances ... must conserve value" pivot criterion for unbacked credit creation.

## Likelihood Explanation
This is a structural defect in the widely-shared FRAME `fungible`/`fungibles` trait default implementations used throughout the runtime stack (nomination pools, treasury, asset-conversion, bridging sovereign accounts, etc.), triggerable whenever a caller invokes `transfer` with `Preservation::Preserve`/`Protect` on an account near the existential deposit. It does not require privileged access — any code path (including unprivileged extrinsics that internally call `transfer` with `Preserve`/`Protect`) on an account near ED can hit this. Exploitability depends on which `Preservation` value the calling pallet chooses, which the external attacker may or may not directly control depending on the specific call site.

## Recommendation
In `fungible::Mutate::transfer` and `fungibles::Mutate::transfer`, bind the actual value returned by `decrease_balance` and use that value (not the caller-supplied `amount`) for the subsequent `increase_balance(dest, ...)` call, and return the actual transferred value instead of the requested `amount`. Additionally, align `Inspect::can_withdraw`'s internal reducible-balance check with the `preservation` value actually used downstream by `decrease_balance`, or remove reliance on `can_withdraw` as a sufficient pre-check for `transfer`'s correctness.

## Proof of Concept
1. Using `pallet-balances`' `fungible::Mutate` implementation, set up `source` with `free = ED + amount - 1` and no freezes/holds/consumer references blocking provider decrement.
2. Call `<T as fungible::Mutate<AccountId>>::transfer(&source, &dest, amount, Preservation::Preserve)`.
3. `can_withdraw(source, amount)` succeeds because its internal gate uses `reducible_balance(source, Expendable, Polite)`, which — since the account can drop its provider ref — permits withdrawing the full `amount` (potentially dusting to zero).
4. `decrease_balance(source, amount, BestEffort, Preserve, Polite)` computes `reducible_balance(source, Preserve, Polite)`, which enforces `untouchable = max(untouchable, ED)`, capping the actual withdrawal at `amount - 1` (or less), and returns that lesser value — which `transfer` discards.
5. `increase_balance(dest, amount, BestEffort)` credits `dest` the full nominal `amount`; `transfer` returns `Ok(amount)`.
6. Assert `balance(dest)_after - balance(dest)_before == amount` while `balance(source)_before - balance(source)_after < amount`, confirming unbacked value creation.

	fn reducible_balance(
		who: &T::AccountId,
		preservation: Preservation,
		force: Fortitude,
	) -> Self::Balance {
		let a = Self::account(who);
		let mut untouchable = Zero::zero();
		if force == Polite {
			// Frozen balance applies to total. Anything on hold therefore gets discounted from the
			// limit given by the freezes.
			untouchable = a.frozen.saturating_sub(a.reserved);
		}
		// If we want to keep our provider ref..
		if preservation == Preserve
			// ..or we don't want the account to die and our provider ref is needed for it to live..
			|| preservation == Protect && !a.free.is_zero() &&
				frame_system::Pallet::<T>::providers(who) == 1
			// ..or we don't care about the account dying but our provider ref is required..
			|| preservation == Expendable && !a.free.is_zero() &&
				!frame_system::Pallet::<T>::can_dec_provider(who)
		{
			// ..then the ED needed..
			untouchable = untouchable.max(T::ExistentialDeposit::get());
		}
		// Liquid balance is what is neither on hold nor frozen/required for provider.
		a.free.saturating_sub(untouchable)
	}

	fn can_withdraw(
		who: &T::AccountId,
		amount: Self::Balance,
	) -> WithdrawConsequence<Self::Balance> {
		if amount.is_zero() {
			return WithdrawConsequence::Success;
		}

		if TotalIssuance::<T, I>::get().checked_sub(&amount).is_none() {
			return WithdrawConsequence::Underflow;
		}

		let account = Self::account(who);
		let new_free_balance = match account.free.checked_sub(&amount) {
			Some(x) => x,
			None => return WithdrawConsequence::BalanceLow,
		};

		let liquid = Self::reducible_balance(who, Expendable, Polite);
		if amount > liquid {
			return WithdrawConsequence::Frozen;
		}

		// Provider restriction - total account balance cannot be reduced to zero if it cannot
		// sustain the loss of a provider reference.
		// NOTE: This assumes that the pallet is a provider (which is true). Is this ever changes,
		// then this will need to adapt accordingly.
		let ed = T::ExistentialDeposit::get();
		let success = if new_free_balance < ed {
			if frame_system::Pallet::<T>::can_dec_provider(who) {
				WithdrawConsequence::ReducedToZero(new_free_balance)
			} else {
				return WithdrawConsequence::WouldDie;
			}
		} else {
			WithdrawConsequence::Success
		};

		let new_total_balance = new_free_balance.saturating_add(account.reserved);

		// Eventual free funds must be no less than the frozen balance.
		if new_total_balance < account.frozen {
			return WithdrawConsequence::Frozen;
		}

		success
	}
