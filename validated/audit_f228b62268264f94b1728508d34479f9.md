### Title
NullPointerException in `UnDelegateResourceActuator.execute()` when only a locked delegation exists — ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
`UnDelegateResourceActuator.validate()` accepts a transaction if *either* the unlocked (`unlockResourceCapsule`) or the locked (`lockResourceCapsule`) `DelegatedResourceCapsule` exists and has sufficient balance. `execute()`, however, unconditionally fetches the unlock-key resource and dereferences it without a null check, causing a NullPointerException when only a locked delegation record exists.

### Finding Description
In `validate()`: [1](#0-0) 
the check only requires `unlockResourceCapsule == null && lockResourceCapsule == null` to fail — i.e. if the caller only ever performed a **locked** delegation (`DelegateResourceContract` with `lock=true`, which creates only the lock-key `DelegatedResourceCapsule`, never the unlock-key one) and never an unlocked delegation, `unlockResourceCapsule` is `null` but `lockResourceCapsule` is not, so validation passes as long as the locked balance (checked when `lockResourceCapsule.getExpireTimeForBandwidth()/getExpireTimeForEnergy() < now`, i.e. the lock has expired) covers `unDelegateBalance`: [2](#0-1) 

In `execute()`, the actuator fetches the unlock-key resource unconditionally: [3](#0-2) 
and then dereferences it without checking for `null` in both the BANDWIDTH and ENERGY branches: [4](#0-3) 
Specifically `unlockResource.addFrozenBalanceForBandwidth(...)` (line 137) or `unlockResource.addFrozenBalanceForEnergy(...)` (line 152) throws an NPE when `unlockResource` is `null`, which happens exactly in the case validate() permits (locked-only delegation, no unlocked delegation ever created for the pair).

This mirrors the CWE-476/CWE-400 class of the VTK advisory: a return value from a lookup (`delegatedResourceStore.get(unlockKey)`, analogous to `xmlDocGetRootElement`) is dereferenced without verifying it is non-null, even though the validation logic explicitly anticipates that this value can be absent.

### Impact Explanation
An uncaught `NullPointerException` inside `execute()` propagates as a `RuntimeException` out of the actuator loop in `RuntimeImpl`/`TransactionTrace.exec()` and up through `Manager.processTransaction()`. This method is invoked both for locally broadcast transactions (`pushTransaction`) and, more critically, for every transaction inside `Manager.processBlock()` when applying blocks received from the network: [5](#0-4) 
If a node processing an incoming block hits this NPE while re-applying a transaction (which any node syncing/verifying the chain must do deterministically), the exception is not one of the checked exception types the `processBlock` caller expects to gracefully skip; it can abort block application, causing that node to fail to advance past the block (denial of service / potential liveness impact for nodes reprocessing the same transaction stream). Since the crash condition depends only on account/resource state that any user can set up with normal transactions, this is reachable by an unprivileged transaction broadcaster.

### Likelihood Explanation
Reaching the vulnerable state requires only standard user-facing contracts:
1. Broadcast a `DelegateResourceContract` with `lock=true` to a receiver (creates only the "locked" `DelegatedResourceCapsule`, no "unlocked" one).
2. Wait until the lock period expires (`getExpireTimeForBandwidth`/`getExpireTimeForEnergy` < now).
3. Broadcast an `UnDelegateResourceContract` for that owner/receiver/resource pair with `unDelegateBalance` ≤ the locked amount, and never having performed a normal (non-locked) delegation to that receiver for that resource.

This is a straightforward, unprivileged sequence of two standard transaction types — no special permissions, no witness/SR compromise, no p2p manipulation required.

### Recommendation
In `UnDelegateResourceActuator.execute()`, mirror the null-safety already used for `lockResource`/`receiverCapsule` elsewhere in the method: check `unlockResource != null` before calling `addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy`, and when it is null, skip that update (only operate on `lockResource` in that scenario), keeping validate()/execute() logic consistent. Add or extend unit/regression tests covering the "locked-only, unlocked-resource-absent" unDelegate path for both BANDWIDTH and ENERGY resources.

### Proof of Concept
1. Account A calls `DelegateResourceContract` to account B with `lock=true` for BANDWIDTH, amount `X`. This creates only `DelegatedResourceCapsule` at `createDbKeyV2(A,B,true)`; no capsule exists at `createDbKeyV2(A,B,false)`.
2. Wait (or manipulate `dynamicStore.getLatestBlockHeaderTimestamp()` in test harness) until `lockResourceCapsule.getExpireTimeForBandwidth() < now`.
3. Account A submits `UnDelegateResourceContract` to B for BANDWIDTH with `unDelegateBalance <= X`.
4. `validate()` succeeds because `lockResourceCapsule != null` and `delegateBalance >= unDelegateBalance`.
5. `execute()` runs `DelegatedResourceCapsule unlockResource = delegatedResourceStore.get(unlockKey);` which returns `null` (no such key exists), then reaches `unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0);` at line 137, throwing `NullPointerException`.

Note: I was unable to fully trace whether every call path from `Manager.processBlock()` to its outer callers has a catch-all that prevents a full node crash/halt versus merely rejecting the block; this would need to be confirmed by examining the block-application call chain (`pushBlock`, sync service) in more depth, which was not fully covered within the available search budget.
