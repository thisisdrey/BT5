`success` is decoded into `DeliveryReceipt` but never referenced anywhere outside `delivery_receipt.rs` — confirming `process_delivery_receipt` truly ignores it before rewarding and clearing the order.

Audit Report

## Title
`process_delivery_receipt` pays the full relayer reward without checking the Ethereum-side `success` flag - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`DeliveryReceipt::success` is decoded directly from the Ethereum `InboundMessageDispatched` event log and indicates whether the inbound dispatch actually succeeded on the gateway contract. `process_delivery_receipt` never inspects this field before paying out `order.fee` and clearing `PendingOrders`, so a relayer is fully rewarded even for a delivery event that Ethereum reported as failed.

## Finding Description
`DeliveryReceipt` carries an explicit `success: bool` decoded from the `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` event log via `TryFrom<&Log>` [1](#0-0) , and this field is populated straight from the decoded event without any subsequent validation [2](#0-1) .

The public, unprivileged extrinsic `submit_delivery_receipt` only requires `ensure_signed`, verifies the merkle/header proof via `T::Verifier::verify`, decodes the `DeliveryReceipt`, and forwards it unchecked to `process_delivery_receipt` [3](#0-2) .

`process_delivery_receipt` checks only `receipt.gateway` against `T::GatewayAddress` and whether `order.fee > 0`, then unconditionally calls `T::RewardPayment::register_reward` and removes the pending order — `receipt.success` is never read or enforced anywhere in this function or elsewhere in the pallet [4](#0-3) . A grep across the Snowbridge tree confirms `success` is referenced only at its point of decode in `delivery_receipt.rs` and nowhere in the reward/settlement path.

This is a genuine missing invariant check: the data model explicitly distinguishes successful vs. failed dispatch, but the payout/settlement logic treats both outcomes identically.

## Impact Explanation
Any properly proven `InboundMessageDispatched` log — including ones where `success == false` — results in `T::RewardPayment::register_reward` crediting the full `order.fee` to the relayer/reward account and `PendingOrders::<T>::remove(nonce)` permanently deleting the order record, foreclosing retry or alternate handling for that nonce. This decouples relayer reward from actual successful bridge delivery, constituting an underpriced/incorrect-payout condition against the relayer reward pot as covered by the "duplicate settlement or payout" and "public underpriced work" categories of the impact gate.

## Likelihood Explanation
The path is reachable by any unprivileged, signed account via `submit_delivery_receipt` with only a valid Ethereum event-log proof; no governance, admin, or privileged role is required, and the relayer does not need to influence the `success` value of the log they submit — they only need one legitimate log (successful or failed) to exist and prove it. This makes the issue trivially and repeatably triggerable in the normal course of relayer operation.

## Recommendation
Add an explicit `ensure!(receipt.success, Error::<T>::MessageDeliveryFailed)` guard in `process_delivery_receipt` before calling `T::RewardPayment::register_reward` and removing the order, and define an explicit non-reward code path (e.g., retry-preserving cleanup or a distinct failure event) for `success == false` receipts instead of treating them identically to successful ones.

## Proof of Concept
1. `do_process_message` enqueues a message, inserting a `PendingOrder { nonce, fee, .. }` with `fee > 0` [5](#0-4) .
2. On Ethereum, the corresponding inbound dispatch fails and the gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid proof for this log and calls `submit_delivery_receipt`; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success: false` without error.
4. `process_delivery_receipt` checks only `receipt.gateway` and `order.fee > 0`, then unconditionally rewards the relayer and removes the order via `T::RewardPayment::register_reward` and `PendingOrders::<T>::remove(nonce)` — the relayer is fully paid despite Ethereum reporting delivery failure [6](#0-5) .

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
