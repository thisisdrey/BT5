### Title
Missing reward settlement before mutating frozen/delegated stake in `DelegateResourceActuator`/`DelegateResourceProcessor` causes incorrect vote-reward accounting - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`)

### Summary
The external report's root cause is that a state-changing side effect of an action (AURA minting) was not reflected in the accounting structure (`tokensIn`) that other logic relies on to compute an account's true value, causing incorrect enforcement (unfair liquidation). The closest reachable analog in java-tron is in the stake/delegation/reward-accounting path: every actuator/native-contract that changes an account's votable stake composition settles (snapshots) the account's pending vote reward first via `mortgageService.withdrawReward()` / `VoteRewardUtil.withdrawReward()` — except `DelegateResourceActuator`/`DelegateResourceProcessor`, which mutate the frozen/delegated balances that back an account's tron power without first settling the reward.

### Finding Description
Every other actuator that changes the frozen balance / voting-power composition of an account calls the reward settlement routine before mutating balances:

- `UnfreezeBalanceActuator.execute()`: `mortgageService.withdrawReward(ownerAddress);` before any balance change. [1](#0-0) 

- `UnfreezeBalanceV2Actuator.execute()`: same pattern. [2](#0-1) 

- `VoteWitnessActuator.countVoteAccount()`: `mortgageService.withdrawReward(ownerAddress);` before clearing/resetting votes. [3](#0-2) 

- The TVM-native counterparts follow the same rule: `VoteWitnessProcessor.execute()` and `WithdrawRewardProcessor.execute()` call `VoteRewardUtil.withdrawReward(...)` before touching votes/allowance, and `Program.withdrawRewardAndCancelVote()` does the same before clearing votes on SUICIDE. [4](#0-3) [5](#0-4) 

In contrast, `DelegateResourceActuator.execute()` directly mutates `ownerCapsule`'s frozen/delegated V2 balances (`addDelegatedFrozenV2BalanceForBandwidth`, `addFrozenBalanceForBandwidthV2`, and the ENERGY equivalents) with no preceding call to `mortgageService.withdrawReward(ownerAddress)`: [6](#0-5) 

The same omission exists in the TVM native-contract path reachable from a `DELEGATERESOURCE` opcode call, `DelegateResourceProcessor.execute()`, which performs the identical balance mutations without settling the reward first: [7](#0-6) 

The reward computation (`MortgageService.withdrawReward` / `VoteRewardUtil.withdrawReward`, and `computeReward`) is driven by the account's current vote list and the account's frozen/tron-power at the time of settlement: [8](#0-7) [9](#0-8) 

Because `DelegateResourceActuator`/`DelegateResourceProcessor` do not snapshot the reward before shifting a chunk of an account's frozen balance into `DelegatedFrozenV2`, any later reward-settlement call (via `WithdrawBalanceActuator`, `VoteWitnessActuator`, TVM `WITHDRAWREWARD`, etc.) will compute the account's reward for the whole cycle using the account's *post-delegation* stake state, even though part of the cycle the account actually held (and voted with) the un-delegated, larger stake. This mirrors the Aura issue precisely: a side effect of a broadcastable action (delegation) changes the account's underlying value/weight without being reflected in the bookkeeping (`beginCycle`/`endCycle`/account-vote-snapshot) that a separate piece of logic relies on to compute correct value/reward.

### Impact Explanation
Reward accounting inconsistency directly affects fund balances (`allowance`, ultimately convertible via `WithdrawBalanceContract`/`WITHDRAWREWARD` to spendable TRX `balance`). If the settlement is computed against a stake state that does not match the state that actually earned rewards during part of the cycle, this can either credit an account more reward than it earned (an unbacked-balance/inflation issue) or less than it earned (permanent loss of legitimately earned funds), both of which the rules explicitly recognize as impactful ("unbacked balance" / "permanent freezing of funds").

### Likelihood Explanation
`DelegateResourceContract` is a standard, unprivileged broadcastable transaction type usable by any account holding frozen V2 balance, and `DelegateResourceProcessor` is reachable via the TVM `DELEGATERESOURCE` opcode from any deployed contract call — both requiring only a single signed transaction with no special permissions. Any account that (a) has votes cast, (b) delegates a portion of its resource mid-cycle, and (c) later triggers a reward settlement (withdraw, vote, or via TVM) will exercise this inconsistent path, making it trivially and repeatably reachable.

### Recommendation
Add a call to `mortgageService.withdrawReward(ownerAddress)` (actuator path) and `VoteRewardUtil.withdrawReward(ownerAddress, repo)` (native-contract path) at the start of `DelegateResourceActuator.execute()` and `DelegateResourceProcessor.execute()`, mirroring the pattern already used in `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `VoteWitnessActuator`, and their TVM equivalents, so that the reward is snapshotted against the pre-delegation stake before the frozen/delegated balances are mutated.

### Proof of Concept
1. Account `A` freezes stake and votes for witness `W` in cycle `N`. `beginCycle`/`endCycle` for `A` are recorded via `delegationStore` based on the current vote list and stake. [8](#0-7) 
2. Mid-cycle `N`, `A` broadcasts a `DelegateResourceContract` that moves a large portion of `A`'s `FrozenV2BalanceForBandwidth`/`Energy` into `DelegatedFrozenV2Balance...` — `DelegateResourceActuator.execute()` performs this mutation without calling `withdrawReward` first. [6](#0-5) 
3. At the end of cycle `N` (or when `A` later calls `WithdrawBalanceContract`/`WITHDRAWREWARD`), `MortgageService.withdrawReward`/`VoteRewardUtil.withdrawReward` computes the reward for cycle `N` using `A`'s vote list/account snapshot, which was never re-snapshotted at the point of delegation — so the computed reward for that cycle does not correctly reflect the stake `A` actually held while accruing votes/power for part of the cycle, resulting in an allowance amount inconsistent with `A`'s actual contribution. [10](#0-9)

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }

  public static void withdrawReward(byte[] address, Repository repository) {
    if (!VMConfig.allowTvmVote()) {
      return;
    }
    AccountCapsule accountCapsule = repository.getAccount(address);
    long beginCycle = repository.getBeginCycle(address);
    long endCycle = repository.getEndCycle(address);
    long currentCycle = repository.getDynamicPropertiesStore().getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account, repository);
        adjustAllowance(address, reward, repository);
        reward = 0;
      }
      beginCycle += 1;
    }
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      repository.updateBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule, repository);
      adjustAllowance(address, reward, repository);
    }
    repository.updateBeginCycle(address, endCycle);
    repository.updateEndCycle(address, endCycle + 1);
    repository.updateAccountVote(address, endCycle, accountCapsule);
  }
