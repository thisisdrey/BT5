### Title
Active permission holders can be granted the AccountPermissionUpdateContract operation bit, allowing a non-owner delegated key to fully overwrite Owner/Witness/Active permissions and hijack account control - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator.checkPermission()` validates the 32-byte operations bitmap of an `Active` permission only against the chain's global `getAvailableContractType()` whitelist; it never excludes contract type `AccountPermissionUpdateContract` (id 46) from that bitmap. Combined with the generic signature/permission-check path (`TransactionCapsule.checkPermission` / `WalletUtil.checkPermissionOperations`), which authorizes execution of *any* contract type solely by testing the corresponding bit in the signer's `Permission.operations`, a delegated `Active` key that is (mistakenly or maliciously) granted the `AccountPermissionUpdateContract` bit can itself broadcast an `AccountPermissionUpdateContract` transaction and unconditionally overwrite the account's Owner, Witness and all Active permissions — even though it only ever held a lower-tier, restricted permission.

### Finding Description
`AccountPermissionUpdateActuator.checkPermission()` enforces generic bit-validity of the operations field but places no special restriction on contract type 46 (`AccountPermissionUpdateContract`) being included: [1](#0-0) 

Execution then unconditionally overwrites the account's Owner/Witness/Active permission set from the contract payload, with no re-check that the acting permission (identified by `permissionId`) has appropriate seniority relative to what it is changing: [2](#0-1) 

Authorization to broadcast the `AccountPermissionUpdateContract` (like any contract) is enforced purely by testing the operations bitmap bit for the contract type against the permission chosen via `contract.getPermissionId()` — it does not require `permissionId == 0` (Owner) or compare permission "rank": [3](#0-2) [4](#0-3) 

The same permission model is used to accept/reject the transaction at the signature-validation stage: [5](#0-4) 

Because nothing in `checkPermission()` prevents the `AccountPermissionUpdateContract` bit from being set on a non-Owner `Active` permission, and because the actuator execution path treats any successfully-authorized signer as fully entitled to replace the account's entire permission structure, a lower-weight `Active` key effectively inherits Owner-equivalent capability the moment that single bit is set — collapsing the intended privilege boundary between "Owner" (id 0, full control) and "Active" (id ≥2, intended to be restricted to specific operations) permission tiers. This is the same bug class as CVE-2021-35624: a component (MySQL's privilege-checking logic / here, java-tron's permission-operations bitmap check) fails to correctly gate a sensitive administrative operation (GRANT/permission-modification-equivalent) behind the correct privilege tier, letting an already-authenticated but lower-privileged principal perform unauthorized modification of critical account data.

### Impact Explanation
An account owner who delegates an `Active` permission (e.g., to an exchange hot-wallet co-signer, a dApp relayer, or a multisig participant) with the `AccountPermissionUpdateContract` bit enabled — whether by oversight, social engineering, or a compromised/malicious co-signer intentionally requesting that scope — grants that delegated key the ability to single-handedly overwrite Owner, Witness and all Active permissions of the account via `AccountPermissionUpdateActuator.execute()`. This allows the delegate to lock out the legitimate owner, install its own keys as sole Owner, and subsequently gain unrestricted control over the account's TRX/TRC10/TRC20 balances and voting/staking rights. This is a concrete unauthorized account-takeover / permanent loss-of-control scenario reachable purely with a signed transaction from a party that was never intended to hold administrative privilege over the account's permission structure.

### Likelihood Explanation
Exploitation requires only that some `Active` permission on the target account currently has the `AccountPermissionUpdateContract` operation bit set — a state reachable by any account owner configuring multisig/delegation without realizing the implication (the codebase's own default-permission helper deliberately excludes bit 46 from defaults, as shown by `checkActiveDefaultOperations`-style tests, indicating the danger is implicitly known but not enforced), or by a malicious co-owner requesting overly broad scope during permission setup. Once such a permission exists, exploitation is a single signed `AccountPermissionUpdateContract` transaction from any key holding sufficient weight in that (deliberately limited-scope) `Active` permission — no additional privilege or code path is required.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, explicitly reject any `Active` (non-Owner) permission whose `operations` bitmap has the `AccountPermissionUpdateContract` bit set, and/or enforce in `TransactionCapsule.checkPermission` / `WalletUtil.checkPermissionOperations` that `AccountPermissionUpdateContract` transactions may only be authorized via `permissionId == 0` (Owner permission), never via a delegated `Active` permission.

### Proof of Concept
1. Account `A` (Owner key `K_owner`) creates an `Active` permission with `id = 2`, a low threshold, key `K_delegate` with sufficient weight, and an `operations` bitmap where bit 46 (`AccountPermissionUpdateContract`) is set alongside whatever legitimate operations were intended (e.g., `TransferContract`). This is accepted by `AccountPermissionUpdateActuator.checkPermission()` since no check forbids bit 46 in an Active permission's operations.
2. Attacker in possession of `K_delegate` constructs a new `AccountPermissionUpdateContract` transaction for account `A`, setting `permission_id = 2` in the outer `Contract`, and supplying a new Owner permission whose sole key is attacker-controlled.
3. Signature/permission verification (`TransactionCapsule.validateSignature` → `checkPermission` → `checkPermissionOperations`) succeeds because permission 2 is `Active` type and its operations bitmap authorizes contract type 46, and `K_delegate`'s weight meets permission 2's threshold.
4. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)` unconditionally, replacing `A`'s Owner permission with the attacker's key.
5. Attacker now solely controls account `A`'s Owner permission and all funds/resources associated with it.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
