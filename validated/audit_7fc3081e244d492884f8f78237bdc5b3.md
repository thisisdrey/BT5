### Title
Unauthenticated peer-reported slot versions can poison `expected_versions` and permanently block acceptance of genuine StackerDB chunk updates - ([File: stackslib/src/net/stackerdb/sync.rs])

### Summary
`StackerDBSync` treats the `slot_versions` vector reported by a remote peer in a `StackerDBChunkInvData` message as if it were the canonical, authenticated version of a slot. This value is a bare, self-reported `u32` per slot with no per-slot signature tying it to the real slot owner's signed chunk (only the P2P message envelope is authenticated, i.e. "this peer said this", not "this version genuinely exists"). This unauthenticated value is folded into `expected_versions`, which then gates whether subsequently downloaded or pushed chunks — including correctly-signed ones from the real slot owner — are accepted or rejected as "stale". This is analogous to the reported bug: an ephemeral, externally-observable quantity (peer-claimed inventory / DAO balance) is used as ground truth for a validation check instead of the authoritative, tracked/committed state (the real signed slot version), letting an attacker desynchronize the check from reality.

### Finding Description
`StackerDBChunkInvData` carries a plain integer vector of claimed slot versions with no per-slot authentication: [1](#0-0) 

When a node receives pushed-chunk inventory updates from neighbors, it stores these peer-reported vectors directly into `self.chunk_invs` without validating that the claimed version numbers correspond to any real, signed chunk: [2](#0-1) 

The sync state machine then derives `expected_versions` — the value later used to gate acceptance of chunks — by taking the max of these peer-reported vectors across all known neighbors: [3](#0-2) 

`validate_received_chunk` (shared by both the download path and the unsolicited-push path) rejects any chunk whose `slot_version` is less than the corresponding entry in `expected_versions`, treating it as stale: [4](#0-3) 

Because `expected_versions` here is sourced from unauthenticated peer self-reports (rather than from the locally verified, signed `SlotMetadata` stored via `StackerDBTx::try_replace_chunk`, which does correctly check the real slot owner's signature — see `stackslib/src/net/stackerdb/db.rs:411-429`), a single malicious or Sybil neighbor can announce an artificially high slot_version for any slot (even one it does not own) that the local node is replicating. Once merged into `expected_versions`, this poisons the freshness gate for that slot: subsequent genuine, correctly-signed chunks from the true slot owner, whose real (much lower) version numbers cannot immediately exceed the forged value, are rejected outright by `validate_received_chunk` before any actual DB/signature check on the slot owner's real version is performed. The true DB-level check in `try_replace_chunk` (`slot_desc.slot_version <= slot_validation.version`) is never reached for these attacker-poisoned slots because `validate_received_chunk` rejects the chunk earlier based on the forged `expected_versions` entry.

This exactly parallels the report's bug class: validation relies on a value (`daoBalance` / here, peer-claimed inventory) that is not the authoritative running/committed value, and can be pushed out of sync with reality by an external, unprivileged party, breaking the intended equality between "claimed/observed state" and "actual signed/committed state".

### Impact Explanation
This allows any single unprivileged StackerDB neighbor (no signing key, no admin role) to durably stall replication of a specific slot on a victim node by announcing a bogus high version number. The victim node will refuse all further genuine updates to that slot until the real owner's version counter catches up to (or exceeds) the forged value — which may never happen, since real version growth is bounded by `write_freq`/`max_writes` policy. This matches the "steering a node off the tip via false inventory" High-impact category: the node is kept on stale, non-canonical (or entirely absent) data for that StackerDB slot while believing (per its inflated `expected_versions`) that legitimate updates are stale forgeries.

### Likelihood Explanation
Likelihood is high: the attack requires only running an ordinary StackerDB-replicating peer and sending a `StackerDBPushChunk`/`StackerDBChunkInv` reply with a forged `slot_versions` entry — no signature over individual slot versions is required, no privileged role, and no computational cost beyond one small message.

### Recommendation
Do not let unauthenticated, peer-reported `slot_versions` values gate acceptance of otherwise-valid signed chunks as if they were canonical. Either:
- Only use locally-verified, signed slot metadata (as already computed via `StackerDBs::get_slot_versions`/`get_slot_validation`) as the freshness baseline for accepting a chunk, and use peer-reported inventories only to *prioritize downloads*, never to *reject* an otherwise validly signed, higher-version-than-locally-known chunk; or
- Track the authenticated maximum version per slot ever proven via a validly verified `SlotMetadata` signature, and only raise `expected_versions` for a slot once such a signed proof has actually been observed/downloaded, rather than trusting a bare integer claim from any single peer.

### Proof of Concept
1. Attacker peer `M` connects to victim node `V`, which replicates StackerDB contract `C` with a slot owned by honest signer `S` currently at version `1`.
2. `M` sends `V` a `StackerDBPushChunk` (or replies to `V`'s `StackerDBGetChunkInv`) with a `StackerDBChunkInvData.slot_versions` entry claiming version `1000` for `S`'s slot — no signature over this integer is required beyond the P2P message envelope signed by `M`'s own key.
3. `V` stores this in `self.chunk_invs` via `add_pushed_chunk`/`getchunksinv_try_finish`, and `recalculate_chunk_request_schedule` sets `self.expected_versions[slot] = 1000` (`max` over all peers, including `M`).
4. Honest signer `S` later legitimately writes and pushes/serves a correctly-signed chunk at version `2` (the true next version).
5. `V`'s `validate_received_chunk` compares `data.slot_version (2) < expected_versions[slot] (1000)` and rejects the chunk as stale, even though it is validly signed by the true slot owner — `V` never applies `S`'s real update, remaining stuck on stale/absent data for that slot indefinitely.

    /// Recalculate the download schedule based on chunkinvs received on push
    pub fn recalculate_chunk_request_schedule(
        &mut self,
        network: &PeerNetwork,
    ) -> Result<(), net_error> {
        // figure out the new expected versions
        let mut expected_versions = vec![0u32; self.num_slots];
        for (_, chunk_inv) in self.chunk_invs.iter() {
            for (slot_version, expected_version) in chunk_inv
                .slot_versions
                .iter()
                .zip(expected_versions.iter_mut())
            {
                *expected_version = (*slot_version).max(*expected_version);
            }
        }

        let priorities =
            self.make_chunk_request_schedule(network, Some(expected_versions.clone()))?;

        self.chunk_fetch_priorities = priorities;
        self.expected_versions = expected_versions;
        Ok(())
    }
