### Title
No Slippage/Minimum-Amount Control on `ExchangeInjectContract` (Bancor-style Pool Deposit) - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
The `ExchangeInjectContract` handler, `ExchangeInjectActuator`, lets any account deposit liquidity into a TRC10 Bancor-style exchange pair by specifying only the quantity of one token (`tokenQuant`). The counterpart amount (`anotherTokenQuant`) is derived on-chain from the *current* pool ratio at execution time and is force-debited from the depositor with no user-supplied bound. Unlike `ExchangeTransactionContract` (the swap operation), which carries an `expected` field enforced in `ExchangeTransactionActuator.doValidate()`, the inject (deposit) and withdraw contracts have no analogous minimum/maximum guard.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, `quant` — there is no `expected`/`min_another_token` field: [1](#0-0) 

In `ExchangeInjectActuator.execute`, the counterpart quantity is computed purely from the pool balances read at execution time, then both amounts are unconditionally deducted from the depositor's account: [2](#0-1) 

The validate path (`doValidate`) recomputes the same ratio-based amount and only checks that it is `> 0` and within the global `balanceLimit` — there is no check that it matches what the user intended when they built the transaction: [3](#0-2) 

Contrast this with `ExchangeTransactionContract`/`ExchangeTransactionActuator`, which explicitly supports slippage protection via the `expected` field and rejects the transaction if the computed output is below it: [4](#0-3) 

Because the pool ratio (`firstTokenBalance` / `secondTokenBalance`) can be changed by any other account's `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` transaction that gets ordered before the victim's deposit in the same block (SR block producers control ordering, and any account can submit a preceding transaction), the counterpart amount charged to the depositor can be manipulated. An attacker can sandwich a victim's `ExchangeInjectContract`: swap to shift the ratio unfavorably right before the victim's inject executes, forcing the victim to contribute a disproportionately large amount of the second token for the same `tokenQuant`, then swap back afterward to restore the ratio and extract the excess value, all within blocks the attacker (or a colluding SR) controls the ordering of.

### Impact Explanation
A depositor into any TRC10 exchange pair can be forced to pay materially more of the counterpart token than the ratio they observed when constructing the transaction, with the excess captured by whoever manipulates ordering (a front-runner or colluding block producer). This is a direct, unauthorized value-extraction / theft-of-funds vector against liquidity providers, reachable by any account holding a TRC10 token used in an exchange pair — no special privilege required.

### Likelihood Explanation
Exchange pairs and their reserves/prices are fully public on-chain state (`ExchangeStore`/`ExchangeV2Store`), so any observer can compute the exact ratio needed to profitably sandwich a pending inject. The attack only requires submitting ordinary `ExchangeTransactionContract`/`ExchangeInjectContract` transactions around the victim's transaction, something well within reach of a normal transaction broadcaster or a witness with block-ordering control (mempool visibility is sufficient; no SR malice needed for an unprivileged bracketed transaction attack in the same or adjacent block).

### Recommendation
Add an `expected`/bound field to `ExchangeInjectContract` (and analogously `ExchangeWithdrawContract`), mirroring the `expected` field already present on `ExchangeTransactionContract`, and enforce it in `ExchangeInjectActuator.doValidate`/`execute` (e.g., reject if the required `anotherTokenQuant` exceeds a user-specified maximum, or falls outside a user-specified tolerance band).

### Proof of Concept
1. Attacker observes pending `ExchangeInjectContract` from victim: inject `tokenQuant` of token A into exchange `E` (first/second balances `F0`, `S0`).
2. Attacker submits `ExchangeTransactionContract` selling a large amount of token A into `E` first, shifting the ratio so `S/F` increases.
3. Victim's inject executes: `anotherTokenQuant = floorDiv(S1 * tokenQuant, F1)` per `ExchangeInjectActuator.execute` (lines 71-83) is now larger than what the victim expected based on `S0/F0`, and this full amount is deducted from the victim's account.
4. Attacker submits a second `ExchangeTransactionContract` reversing the initial swap, restoring the ratio and pocketing the extra value the victim was forced to contribute — all with no validation error raised, since `doValidate` only checks `anotherTokenQuant > 0` and the global `balanceLimit`.
