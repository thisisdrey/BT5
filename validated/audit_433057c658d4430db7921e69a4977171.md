## Analysis

The Velodrome bug is fundamentally about a user-facing entry point that (1) commits an irreversible action (burning WEVE) and (2) forwards a user-supplied value intended to pay for a downstream operation, with **no mechanism to guarantee that the payment actually covers what's needed or that the payment is contingent on the downstream operation succeeding**. When the value is insufficient, the irreversible action still happens but the paid-for service is not delivered.

The strongest reachable analog in this nearcore codebase is in the **eth-implicit wallet contract** (`runtime/near-wallet-contract`), specifically its relayer-fee mechanism for emulated Ethereum base-token/ERC-20 transfers.

### Title
Wallet Contract pays the relayer fee unconditionally before the underlying action's outcome is known - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`inner_rlp_execute` computes a relayer "fee" from the user-signed Ethereum transaction (`max_fee_per_gas * gas_limit`, see `internal.rs`) and immediately dispatches it as an **independent, fire-and-forget** `Promise` transfer to the relayer, *before* the actual emulated action (the transfer/ERC-20 call the user intended) has been attempted. If that action later fails, only the caller's `attached_deposit` is refunded in `rlp_execute_callback` — the fee already paid to the relayer is never reclaimed.

### Finding Description
In `inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:367-385`), once a transaction is parsed as `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero `fee`, the contract eagerly creates a **separate** promise batch and sends the fee to the relayer: [1](#0-0) 

This fee-transfer promise is not chained to (`.then(...)`) the promise that performs the actual requested action; it is submitted independently in the same batch of scheduled work. The actual action (e.g., `ft_transfer`, a NEAR transfer, or the registrar-check/storage-deposit flow for ERC-20) is scheduled separately and its result is only inspected later in `rlp_execute_callback`: [2](#0-1) 

On failure of that action, the callback only refunds `caller_deposit` (the NEAR attached directly to the `rlp_execute` call by the caller) — it has no way to claw back the fee that was already sent to the relayer via the independent promise created earlier in `inner_rlp_execute`.

The fee amount itself is derived purely from user/relayer-supplied Ethereum-transaction fields with no cap tied to whether the downstream action can or will succeed: [3](#0-2) 

This mirrors the Velodrome bug class exactly: a value meant to compensate for/gate a specific downstream operation is deducted from the account's balance unconditionally, while the operation it is supposed to correspond to can independently fail (e.g., NEP-141 `ft_transfer` failing due to insufficient token balance, receiver panics, insufficient prepaid gas for the storage-deposit/registrar sub-calls, or an intentionally malformed relayer-submitted action), leaving the wallet owner's funds spent with no corresponding service rendered.

### Impact Explanation
Since the fee promise is dispatched unconditionally and separately from the action promise, any relayer (or an attacker acting as relayer, since `rlp_execute` can be called by anyone per the contract's design of "any relayer can safely serve" per the code comment) can submit transactions engineered to fail on the emulated-action leg (e.g., undersized callback gas causing `Exceeded the prepaid gas` — cf. `test_insufficient_gas` in `sanity.rs`) while still collecting the fee every time, since only the `caller_deposit` — not the fee — is refunded on failure. This constitutes a permanent, repeatable loss of funds from the wallet's balance without executing the user's intended transfer, and, because `nonce` is still incremented for user-caused failures, the wallet owner cannot even trivially retry without incurring the fee loss again.

### Likelihood Explanation
The wallet contract is intentionally designed to let "any relayer" submit `rlp_execute` calls on behalf of an eth-implicit account without prior on-boarding, specifically to enable this fee-based compensation flow (per the in-code comment). This makes an untrusted, permissionless relayer path — with a user-signed but relayer-submitted transaction — the normal operating mode, increasing the realistic likelihood that fee payment and action failure can be decoupled either by an adversarial relayer or simply by routine execution failures (e.g., gas underestimation for the ERC-20 storage-deposit/registrar sub-calls, or token-side reverts).

### Recommendation
Chain the relayer-fee transfer to the same promise (or a `.then()` callback) that carries the emulated action's outcome, so that the fee is only paid out if the underlying action succeeds — analogous to using `estimateFees()`-style gating in the original report, i.e., only commit the payment once the downstream operation's success is confirmed. Alternatively, include the fee amount in the `CallerDeposit`/refund accounting so that `rlp_execute_callback`/`address_check_callback`/`nep_141_storage_balance_callback` can refund the fee together with the caller's deposit when the action fails.

### Proof of Concept
1. Deploy the wallet contract for an eth-implicit account and fund it with NEAR.
2. Have the account owner sign an Ethereum ERC-20-transfer transaction (`ERC20_TRANSFER_SELECTOR`) with a non-zero `max_fee_per_gas * gas_limit` (i.e., non-zero `fee`) targeting a NEP-141 token contract, intending to send tokens to a receiver.
3. Submit this via `rlp_execute` as a relayer, but engineer or allow the downstream `ft_transfer`/`storage_deposit` promise chain to fail (e.g., the wallet has insufficient token balance in the token contract, or the callback gas is insufficient — see `test_insufficient_gas` pattern in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs:34-79`).
4. Observe: the relayer still receives the `fee` transfer created in `inner_rlp_execute` (`lib.rs:381-384`), while `rlp_execute_callback` (`lib.rs:296-311`) only refunds `caller_deposit`, not the fee — the wallet owner's fee payment is permanently lost despite the transfer never happening.
