### Title
Intra-batch write/write lock conflicts are not detected by `try_lock_transaction_batch`, allowing two same-account writers to both lock successfully - (File: accounts-db/src/account_locks.rs)

### Summary
`AccountLocks::try_lock_transaction_batch` performs a two-pass algorithm: it first calls `can_lock_accounts` for every transaction in the batch against the *pre-batch* lock state, and only afterwards applies `lock_accounts` for every transaction that passed. Because the check pass never incrementally updates `write_locks`/`readonly_locks` as each transaction in the same batch is validated, two conflicting transactions submitted together in one batch both pass the conflict check and both get locked, violating the accounts-lock invariant.

### Finding Description
`try_lock_transaction_batch` [1](#0-0)  is implemented as:

1. A `for_each` loop that calls `self.can_lock_accounts(keys.clone())` for every transaction's keys and mutates the transaction's own result to `Err` on conflict — but it never calls `lock_write`/`lock_readonly` inside this loop.
2. A second, separate pass (`into_iter().map(...)`) that calls `self.lock_accounts(keys)` for every transaction whose result is still `Ok`.

`can_lock_accounts` [2](#0-1)  only consults the current `write_locks`/`readonly_locks` maps via `can_write_lock`/`can_read_lock` [3](#0-2) . Since the first pass never writes to those maps for entries earlier in the same batch, a transaction B that write-locks the same account as transaction A (processed earlier in the same `for_each` iteration) sees an unmodified `self` state and also passes the check — both A and B get `Ok(())` from `try_lock_transaction_batch`, and the subsequent `lock_accounts` pass locks the account for both, incrementing `write_locks[key]` to 2 with no error surfaced.

This is reachable by an unprivileged attacker: `SigVerifyStage` verifies signatures on incoming QUIC-delivered packets/batches, and `banking_stage` groups verified transactions into a single packet batch and calls `try_lock_transaction_batch` on the whole batch at once, so any attacker that sends two transactions writing the same account together in one packet batch triggers this path without needing any special privilege, stake, or config. Sigverify and QoS/dedup upstream only check signature validity and account-limit/duplicate-account-within-a-single-transaction (`validate_account_locks`/`has_duplicates`) [4](#0-3) ; none of them detect or prevent cross-transaction write/write conflicts within a batch — that is the explicit job of `try_lock_transaction_batch`, which fails to do it correctly.

### Impact Explanation
Both conflicting transactions being reported as successfully locked means the batch-execution scheduler downstream may treat them as safe to execute concurrently (or execute in an order not reflected in locking semantics), risking data races on the same account's state during execution and potential production of a PoH-recorded entry whose ordering/state does not correspond to a valid sequential execution — this is an "invalid recorded block" / core-consensus-safety class impact.

### Likelihood Explanation
The precondition is trivial and fully attacker-controlled: submit two transactions writing the same account in the same QUIC-delivered packet batch to a leader's TPU. No stake, special timing, or validator cooperation is required — it depends solely on how `banking_stage` batches transactions from a `SigVerifyStage` output before calling `try_lock_transaction_batch`. This is deterministic (not a true race window over wall-clock time) — it's a logic bug in the two-pass check vs. lock separation, so it is repeatable on every invocation with such input.

### Recommendation
Merge the check-and-lock into a single atomic pass per transaction: for each transaction in the batch, call `can_lock_accounts` and, if `Ok`, immediately call `lock_accounts` before moving to the next transaction in the same batch. This ensures each subsequent transaction's conflict check sees the locks acquired by earlier transactions in the same batch.

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (test)
#[test]
fn test_try_lock_transaction_batch_intra_batch_ww_conflict() {
    let mut locks = AccountLocks::default();
    let shared_key = Pubkey::new_unique();

    // Two transactions in the SAME batch, both write-locking `shared_key`.
    let tx_a_keys = vec![(&shared_key, true)];
    let tx_b_keys = vec![(&shared_key, true)];

    let batch = vec![
        Ok(tx_a_keys.into_iter()),
        Ok(tx_b_keys.into_iter()),
    ];

    let results = locks.try_lock_transaction_batch(batch);

    // EXPECTED (correct behavior): one Ok, one Err(AccountInUse).
    // ACTUAL (bug): both entries are Ok(()), demonstrating the missed
    // intra-batch write/write conflict.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert_eq!(
        ok_count, 1,
        "both conflicting writers were locked simultaneously: {:?}",
        results
    );
}
```
Running this test against the current implementation fails the assertion (`ok_count == 2`), confirming both write-conflicting transactions in the same batch are incorrectly granted locks.

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

        !self.is_locked_write(key)
    }

    fn can_write_lock(&self, key: &Pubkey) -> bool {

pub fn validate_account_locks(
    account_keys: AccountKeys,
    tx_account_lock_limit: usize,
) -> TransactionResult<()> {
    if account_keys.len() > tx_account_lock_limit {
        Err(TransactionError::TooManyAccountLocks)
    } else if has_duplicates(account_keys) {
        Err(TransactionError::AccountLoadedTwice)
    } else {
        Ok(())
    }
}

thread_local! {
    static HAS_DUPLICATES_SET: RefCell<AHashSet<Pubkey>> = RefCell::new(AHashSet::with_capacity(MAX_TX_ACCOUNT_LOCKS));
}

/// Check for duplicate account keys.
fn has_duplicates(account_keys: AccountKeys) -> bool {
    // Benchmarking has shown that for sets of 32 or more keys, it is faster to
    // use a HashSet to check for duplicates.
    // For smaller sets a brute-force O(n^2) check seems to be faster.
    const USE_ACCOUNT_LOCK_SET_SIZE: usize = 32;
    if account_keys.len() >= USE_ACCOUNT_LOCK_SET_SIZE {
        HAS_DUPLICATES_SET.with_borrow_mut(|set| {
            let has_duplicates = account_keys.iter().any(|key| !set.insert(*key));
            set.clear();
            has_duplicates
        })
    } else {
        for (idx, key) in account_keys.iter().enumerate() {
            for jdx in idx + 1..account_keys.len() {
                if key == &account_keys[jdx] {
                    return true;
                }
            }
        }
        false
    }
}
