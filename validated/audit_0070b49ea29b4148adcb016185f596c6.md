## Finding: Unsynchronized concurrent mutation of `ownerAddressSet` between block generation and transaction push/block application paths

### Title
Data race on `Manager.ownerAddressSet` (plain `HashSet`) between unsynchronized block-generation and synchronized transaction-push/block-application paths can corrupt internal state and crash/hang the node - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
The reported CVE-2022-28796 is a use-after-free caused by a race condition on a shared `transaction_t` object accessed without proper locking discipline in the Linux kernel's journal code. The closest reachable analog in java-tron is a genuine, unguarded data race on the `Manager.ownerAddressSet` field, a plain (non-thread-safe) `HashSet<String>` that is read and mutated from multiple threads with inconsistent locking: some call sites hold the `Manager` monitor (`synchronized (this)`), while the block-production path does not hold it at all.

### Finding Description
`Manager.ownerAddressSet` is declared as a plain `HashSet<String>`: [1](#0-0) 

It is written to inside `processTransaction()` whenever a multi-sign transaction (`AccountPermissionUpdateContract`) is processed: [2](#0-1) 

`processTransaction()` is invoked from two different concurrency contexts:
1. `pushTransaction()`, which acquires the `Manager` instance monitor via `synchronized (this)` before calling `processTransaction()`: [3](#0-2) 

2. `generateBlock()`, the block-production loop, which calls `processTransaction()` directly with **no `synchronized` block around it and no `synchronized` modifier on the method itself**: [4](#0-3) [5](#0-4) 

Additionally, `pushBlock()` clears and rebuilds `ownerAddressSet` under `synchronized (this)`: [6](#0-5) 

and `generateBlock()` also *reads* `ownerAddressSet` (`.contains(ownerAddress)`) while iterating pending transactions, again with no lock held: [7](#0-6) 

Because `pushTransaction()` (triggered by any unprivileged, remote, signed transaction broadcast, e.g., through `TransactionsMsgHandler`'s worker pool) mutates/adds to `ownerAddressSet` under the `Manager` monitor while `generateBlock()` (running on the block-production thread, invoked once per block-production slot on every witness node) concurrently reads and writes the very same `HashSet` **without** taking that monitor, the two threads can race on the set's internal bucket array. `java.util.HashSet`/`HashMap` are explicitly not thread-safe for concurrent structural modification (add/resize) concurrent with iteration or other adds; this can corrupt the bucket linked list, leading either to lost entries, infinite loops during resize/iteration (classic pre-Java 8 HashMap infinite-loop failure mode, sometimes reproducible even on modern JVMs under a data race), or a `ConcurrentModificationException`/`NullPointerException`.

This mirrors the CVE's bug class: a shared mutable object accessed from multiple execution contexts with inconsistent/absent synchronization, leading to memory-state corruption and a crash.

### Impact Explanation
A crash or infinite hang inside `generateBlock()` (the routine that every witness must call periodically to produce blocks) stalls block production on that witness. Because `ownerAddressSet` gating also affects whether a multi-sign transaction's cached signature-verification flag (`trx.setVerified(false)`) is honored, corruption of this set could also cause an already-verified-but-stale transaction to be incorrectly treated as verified/unverified, i.e., a signature-permission bypass or improper re-validation skip for multi-sign (`AccountPermissionUpdateContract`) transactions. At minimum this is a node availability issue (DoS on a witness's block production) reachable purely by unprivileged transaction submission; at worst it can affect the integrity of multi-sign permission validation.

### Likelihood Explanation
Any account holder can trigger the write path by broadcasting an `AccountPermissionUpdateContract` transaction (a normal, permissionless multi-sign contract type) which any full node accepts via `pushTransaction()`. The race window opens naturally whenever such a transaction arrives concurrently with a witness's local `generateBlock()` call — a condition that occurs continuously in normal network operation, since witnesses are producing blocks on a schedule while simultaneously receiving broadcast transactions on the `trxHandlePool` executor. No special privilege (SR/witness malice) is required — only that the target node happens to be an active witness, which is the normal, honest role of many java-tron nodes.

### Recommendation
Ensure all reads and writes of `ownerAddressSet` go through the same lock discipline as the rest of pending-transaction/block state — either wrap the `generateBlock()` accesses of `ownerAddressSet` (both the read at line 1736 and any indirect write via `processTransaction()`) in `synchronized (this)`, or replace `ownerAddressSet` with a `Collections.synchronizedSet(...)`/`ConcurrentHashMap`-backed set consistently used everywhere, matching how `poppedTransactions` is already made thread-safe via `Collections.synchronizedList(...)`.

### Proof of Concept
1. Run a java-tron witness node.
2. Continuously broadcast a stream of valid `AccountPermissionUpdateContract` transactions from different accounts to the node (each triggers `pushTransaction()` → `processTransaction()` → write to `ownerAddressSet`).
3. Simultaneously, since the witness is scheduled to call `generateBlock()` on every production slot, `generateBlock()` will be concurrently reading/writing `ownerAddressSet` without holding the `Manager` monitor.
4. Under sustained load, observe either a `ConcurrentModificationException`/`NullPointerException` thrown out of `generateBlock()` (failing block production for that slot) or, in rarer timing windows, a hang inside `HashSet` resize logic, both of which degrade or halt the witness's block production.
