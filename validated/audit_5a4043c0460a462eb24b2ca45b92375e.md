### Title
Truncating integer division in `convert_from_ether_decimals` underprices Snowbridge outbound-queue fees, allowing free/cheap spam of Ethereum-bound messages - (File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs)

### Summary
`Pallet::<T>::calculate_fee` in `bridges/snowbridge/pallets/outbound-queue/src/lib.rs` computes the remote (Ethereum-side) portion of a message's delivery fee in 18-decimal (ether/WAD) fixed-point precision and then downscales it to the local chain's token precision (10 decimals for DOT, 12 for KSM) using plain integer division in `convert_from_ether_decimals`. Because the division truncates rather than rounds, any WAD-scaled fee value smaller than the divisor (`10^(18 - Decimals)`, e.g. `1e8` for a 10-decimal chain) collapses to `0`. This is the same root-cause pattern as the external report: math correct at 18 dp becomes wrong/degenerate once results are naively rescaled to a lower-dp token without precise rounding, and the small-value regime silently loses all resolution.

### Finding Description
`calculate_fee` computes the remote fee entirely in ether/WAD units: [1](#0-0) 

The final downscale step is: [2](#0-1) 

`convert_from_ether_decimals` computes `denom = 10^(18 - T::Decimals)` and does `value.checked_div(denom)`, a floor division with no rounding-up/ceiling and no minimum-fee floor. `T::Decimals` is constrained only to be `10` or `12` via `integrity_test`: [3](#0-2) 

so `denom` is `1e8` (10-decimal chains) or `1e6` (12-decimal chains). Any pre-division `value` (the WAD-scaled, exchange-rate-and-multiplier-adjusted remote fee) below that threshold is silently rounded down to `0`, exactly mirroring the reported bug class: a computation performed correctly at 18-dp precision produces an incorrect/degenerate result once rescaled to a lower-dp unit through simple (non-precise) arithmetic.

This fee is exactly the value charged to the sender in `SendMessage::validate` (`fee = Self::calculate_fee(...)`), which callers (e.g. the XCM exporter charging for bridge delivery) use to withdraw payment from the user before enqueueing the message: [4](#0-3) 

The fee is a function of governance-set `PricingParameters` (`exchange_rate`, `fee_per_gas`, `rewards.remote`, `multiplier`) which can legitimately be small numbers depending on live market rates — there is no code path that clamps the final local fee to a nonzero minimum before this division, and no `preciseMul`/ceiling-style rounding is applied anywhere in `calculate_fee`.

### Impact Explanation
If the computed remote-fee-in-local-currency value falls under the fixed decimal-scaling threshold (`1e8`/`1e6` in ether-WAD terms — i.e. roughly less than `1e-10` DOT worth of remote fee before scaling, which is plausible at low ETH/DOT exchange rates or low `fee_per_gas`/`reward` settings), `convert_from_ether_decimals` returns `0` for the remote fee component. The message is still accepted and queued for relayers to process and pay gas for on Ethereum, but the sender pays no compensation for that remote cost. This is the "public underpriced work that degrades block production or stalls bridge processing" impact category: an unprivileged user can submit (spam) Ethereum-bound commands that cost real relayer gas but are charged zero remote fee, degrading relayer incentives and potentially stalling/congesting the bridge outbound pipeline, without needing any malicious peer, relayer, or governance actor.

### Likelihood Explanation
Likelihood depends on `PricingParameters` values set by governance (`exchange_rate`, `fee_per_gas`, `multiplier`, `rewards.remote`) staying above the implicit precision floor. Because these are periodically updated market-driven parameters (documented as manually updated "every few weeks"), there is a realistic window where combinations of low gas price and low reward could put the computed local fee near or under the decimal-scaling threshold, especially for the 12-decimal (higher precision, larger `denom`... actually smaller `denom`, so 10-decimal chains are more exposed) case. No test in the repo asserts the local converted fee is bounded away from zero; the truncation is unconditional integer division with no minimum-fee safeguard.

### Recommendation
- Use ceiling/rounding-aware scaling instead of `checked_div` truncation in `convert_from_ether_decimals`, e.g. round up (`checked_div` plus remainder-based increment) so any non-zero remote cost never rounds down to a zero local fee.
- Enforce a protocol-level minimum non-zero fee (or reject/queue-refuse messages whose computed fee rounds to zero) so spam cannot bypass remote-cost compensation.
- Consider validating in `PricingParameters::validate` (or at `set_pricing_parameters` time) that the configured parameters cannot produce a zero-rounding fee for the configured `T::Decimals`.

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {

		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };
