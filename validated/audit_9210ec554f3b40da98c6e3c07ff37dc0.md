### Title
Node's `StackerDBChunkInv` reply advertises a chunk version as committed before it is actually stored - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` mutates the local `StackerDBChunkInvData` reply's `slot_versions` entry to reflect a just-received chunk's `slot_version` *before* that chunk has actually been written to the local `StackerDBs` replica. The chunk is only durably persisted later, out-of-band, when the message is forwarded to the relayer and processed by `Relayer::process_stacker_db_chunks`, which performs the actual `tx.try_replace_chunk` call. [1](#0-0) [2](#0-1) 

### Finding Description
On receipt of an unsolicited `StackerDBPushChunk`, the peer network builds a `StackerDBChunkInv` (or `Nack`) reply via `make_StackerDBChunksInv_or_Nack`, which reflects the *current* on-disk slot versions. Before sending that reply, the handler runs `validate_received_chunk` (signature, size, freshness, write-count checks) and, if it passes, directly patches the in-memory `data.slot_versions[slot_id]` to the pushed chunk's `slot_version`, then immediately signs and sends this patched inventory back to the peer as if the chunk were already stored. [3](#0-2) [4](#0-3) 

The actual write only happens afterward, when the return value `(false, true)` tells the caller to forward the raw message to the relayer, which independently re-derives sync results and calls `tx.try_replace_chunk` (in `Relayer::process_stacker_db_chunks`) - a call that can still fail for reasons this earlier gate does not fully re-check at that exact moment (e.g. `StaleChunk` if another chunk for the same slot was stored concurrently in between, or any other `try_replace_chunk` failure), in which case the chunk is silently dropped with only a log message. [2](#0-1) [5](#0-4) 

This creates a window where the node's outgoing `StackerDBChunkInv` claims a slot version that is not actually present in its own `StackerDBs` store — breaking the "served vs committed" invariant: the inventory a node advertises to its peers is supposed to accurately reflect the versions it can actually serve on a subsequent `StackerDBGetChunkData` request.

### Impact Explanation
A remote, unprivileged peer can exploit this without owning any StackerDB slot key: it only needs to *relay* a chunk it observed elsewhere (chunks are gossiped in plaintext with a valid signature attached, so no private key is required to replay one) as an unsolicited `StackerDBPushChunk` to a victim node, timed to race against another legitimate write to the same slot. The victim will optimistically report the new version in its `StackerDBChunkInv` reply while the concurrent `try_replace_chunk` in the relayer path can lose the race and drop the chunk (`StaleChunk`/other error) without correcting the previously-sent inventory claim. Downstream peers that trust this inventory (used to schedule `StackerDBGetChunkData` requests and to decide who to query next, per the download-scheduling logic described in the StackerDB module docs) may skip re-requesting that slot version from the victim under the false belief it is already replicated there, and if the victim is also treated as an authoritative source, this steers other replicas away from actually obtaining the latest committed chunk — a form of serving state that does not match what is actually committed. [6](#0-5) 

### Likelihood Explanation
The race requires two writes to the same slot arriving close together (one via unsolicited push, one via normal sync) — plausible in a live gossip network, and the attacker fully controls when it sends the replayed chunk to the victim, giving it control over timing on its side. No secret key or privileged role is needed since only a previously-observed valid signature is replayed. [7](#0-6) 

### Recommendation
Only patch/send the advertised `slot_versions` entry (or send the `StackerDBChunkInv` reply at all) *after* confirming the chunk was actually and successfully persisted (i.e., move the inventory patch to occur after a successful `try_replace_chunk`, or re-read the true on-disk version right before replying instead of optimistically setting it from the unverified-as-stored chunk).

### Proof of Concept
1. Attacker observes any validly-signed `StackerDBChunkData` for slot `S` version `V` gossiped on the network (no private key needed to replay it).
2. Attacker sends this as an unsolicited `StackerDBPushChunk` to victim node `N` for contract `C`.
3. Concurrently, another peer's legitimate sync also delivers a conflicting/racing write for slot `S` to `N` via the normal sync path.
4. `N`'s `handle_unsolicited_StackerDBPushChunk` validates the attacker's chunk against currently-known versions, patches its `StackerDBChunkInv` reply to advertise version `V` for slot `S`, and sends this reply back immediately. [8](#0-7) 
5. The actual storage attempt for the attacker's chunk, performed later via `Relayer::process_stacker_db_chunks` → `tx.try_replace_chunk`, loses the race (e.g., `StaleChunk`) and is silently dropped, so `N`'s on-disk state never actually reaches version `V`. [9](#0-8) 
6. `N` has now advertised inventory (version `V`) that diverges from its committed state, potentially causing peers to skip re-fetching the real latest chunk from `N`.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
