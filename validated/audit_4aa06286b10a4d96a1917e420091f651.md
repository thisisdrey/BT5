### Title
Unvalidated attachment content lets a malicious peer permanently fill the `attachments` table with unbounded, un-evictable rows - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` stores whatever `Attachment` payload a peer returns for a `GetAttachment` request without checking that the returned content's hash matches the `content_hash` that was actually requested. `AttachmentsDownloader::run` then unconditionally calls `AtlasDB::insert_instantiated_attachment` on every such attachment, persisting it as `was_instantiated=1`, which is never subject to `evict_expired_uninstantiated_attachments` or the `max_uninstantiated_attachments` cap (both only target `was_instantiated=0` rows).

### Finding Description
The equality that should hold is: every row in `attachments` with `was_instantiated=1` corresponds to content whose hash matches a `content_hash` referenced by an on-chain `AttachmentInstance`. This is broken because:

1. In `stackslib/src/net/atlas/download.rs`, `extend_with_attachments` (lines 530-558) decodes the peer's HTTP response via `response.decode_atlas_get_attachment()` and does `self.attachments.insert(response.attachment)` — with no check that `response.attachment.hash() == request.content_hash` [1](#0-0) . The server side (`stackslib/src/net/api/getattachment.rs`) trusts the client's requested hash to look up its own DB and returns whatever `Attachment` JSON it wants attached to that response; a malicious peer can simply serve its own fabricated `GetAttachmentResponse { attachment }` with arbitrary content, independent of the path's `attachment_hash` query key [2](#0-1) .
2. In `AttachmentsDownloader::run`'s `Done` branch, for every attachment drained from the batch, the code calls `network.atlasdb.find_all_attachment_instances(&attachment.hash())` and then unconditionally calls `network.atlasdb.insert_instantiated_attachment(&attachment)` — the insert is not gated on `attachments_instances` being non-empty [3](#0-2) .
3. `insert_instantiated_attachment` writes the row with `was_instantiated=1` unconditionally [4](#0-3) .
4. `evict_expired_uninstantiated_attachments` and `evict_k_oldest_uninstantiated_attachments` (and the `max_uninstantiated_attachments` cap enforced in `insert_uninstantiated_attachment`) all filter/act only on `was_instantiated = 0` [5](#0-4) [6](#0-5) . There is no cap or expiry for `was_instantiated=1` rows.
5. Because `context.attachments_batch.resolve_attachment(&attachment.hash())` is keyed on the fabricated hash (not the originally requested `content_hash`), the real, legitimately tracked `content_hash` is never marked resolved, so `has_fully_succeed()` stays false and the batch is re-queued for retry (`bump_retry_count`) up to `max_attachment_retry_count` times [7](#0-6) , giving the attacker multiple additional chances to serve new distinct fabricated payloads per real on-chain attachment instance.

### Impact Explanation
A single malicious peer that is selected as an outbound sync source and claims (via its inventory response) to have content for tracked `content_hash` values can return arbitrary payloads (up to `attachments_max_size`, default `1_048_576` bytes) that get permanently written into the node's `attachments` table as "instantiated," bypassing the intended requirement that persisted attachment content be tied to an on-chain-committed `AttachmentInstance.content_hash`. Because these rows are marked `was_instantiated=1`, none of the existing eviction/cap logic ever removes them, so disk usage grows without bound as long as new (legitimate) `AttachmentInstance`s continue to be tracked and the attacker is chosen as a download source, and is repeatable across retries of the same batch. This matches the "attachment/BNS mismatch" High-impact category: state (attachment content) is persisted and served as if validated/committed, when it was never actually linked to the corresponding on-chain commitment.

### Likelihood Explanation
Requires the attacker to run a normal, remotely reachable peer that the victim node includes among `network.get_outbound_sync_peers()` and that responds to `/v2/attachments/inv` claiming availability and then to `/v2/attachments/<hash>` GET requests — no privileged role, secret, or authentication is needed, this is a standard Atlas peer interaction any P2P peer can perform. It does require at least one legitimate on-chain `AttachmentInstance` to exist so the downloader has something to fetch, but the number of fabricated rows the attacker can inject is not bounded by that count due to the retry re-queuing behavior described above.

### Recommendation
In `extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`, and treat a mismatch as a failed request (bump `report.bump_failed_requests()`) rather than a success. Additionally, in `AttachmentsDownloader::run`'s `Done` handling, only call `insert_instantiated_attachment` when `find_all_attachment_instances` returns a non-empty result (i.e., only persist content that is actually referenced by a tracked `AttachmentInstance`), and consider adding a cap/expiry policy for `was_instantiated=1` rows as a defense-in-depth measure.

### Proof of Concept
Rust test plan (extending `stackslib/src/net/atlas/tests.rs` and `download.rs` test infra):
1. Construct an `AttachmentsBatch` from a real `AttachmentInstance` with `content_hash = H` (as in existing tests like `test_downloader_context_attachment_requests`).
2. Simulate a malicious peer's inventory response claiming it has content for `H`, then simulate its `GetAttachmentResponse` for the resulting `AttachmentRequest` containing an `Attachment` whose `content` hashes to `H' != H` (e.g., use `new_attachment_from("evil_payload")`).
3. Call `AttachmentsBatchStateContext::extend_with_attachments` with this crafted result and assert `self.attachments` now contains the attachment keyed by `H'` even though it was requested under `H`.
4. Drive this through `AttachmentsDownloader::run`'s `Done` path (or call `atlasdb.find_all_attachment_instances(&H')` then `atlasdb.insert_instantiated_attachment`) and assert:
   - `atlasdb.find_all_attachment_instances(&H')` returns empty (no `AttachmentInstance` references `H'`), yet
   - a row with `hash = H'`, `was_instantiated = 1` exists in the `attachments` table after the call.
5. Call `atlasdb.evict_expired_uninstantiated_attachments()` after advancing time past `uninstantiated_attachments_expire_after` and assert the fabricated row with `was_instantiated=1` is **not** deleted, demonstrating the permanent, unbounded, un-evictable storage growth.

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",

        Ok(())
