### Title
Callback failure in the eth-implicit Wallet Contract permanently locks `has_in_flight_tx`, freezing the account forever - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the eth-implicit wallet contract used to let ETH-style addresses transact on NEAR) guards against concurrent execution with a `has_in_flight_tx` boolean that is reset to `false` as the very first statement of its promise callbacks (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`). Because NEAR rolls back *all* state changes of a receipt when that receipt's execution fails (the exact "child call fails, parent revert" pattern described in the TRST-H-2 report), any failure of these callback receipts — e.g. running out of the small fixed `RLP_EXECUTE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budgets — reverts the `has_in_flight_tx = false` write along with everything else. Since `rlp_execute` unconditionally rejects any new transaction while `has_in_flight_tx` is `true`, and there is no other method that can reset the flag, the wallet becomes permanently unusable, freezing all funds held by that account.

### Finding Description
`WalletContract::rlp_execute` refuses to process a new transaction whenever `self.has_in_flight_tx` is `true`: [1](#0-0) 

The flag is only ever cleared inside the private callbacks that resolve a previously-dispatched promise, each of which sets it `false` as the first statement and then, in some branches, sets it `true` again before returning a new promise: [2](#0-1) [3](#0-2) [4](#0-3) 

These callbacks are executed with small, fixed static gas budgets: [5](#0-4) 

NEAR's action-execution model guarantees that a receipt whose execution fails is *fully* rolled back — none of its state writes persist, including ones made before the failure point: [6](#0-5) [7](#0-6) 

This is precisely the bug class in the report: the "parent" logically-correct bookkeeping (`has_in_flight_tx = false`) is committed only if the whole receipt — including a "child" step (parsing a cross-contract response, or a nested cross-contract call) — also succeeds. If the child step exhausts the callback's fixed gas budget or otherwise fails (e.g. `serde_json::from_slice` on an oversized `storage_balance_of`/registrar response, or `GasExceeded` while copying a large `PromiseResult::Successful` payload out of the register), the whole callback receipt fails and `has_in_flight_tx` reverts to (and remains) `true`. Because `rlp_execute` is the sole public entry point and unconditionally short-circuits when the flag is `true`, and no other method resets it, the account is permanently locked out of `rlp_execute` — the *only* way this contract can move funds — for the rest of its existence.

### Impact Explanation
This results in permanent freezing of funds: every NEAR/ERC-20 balance controlled by that eth-implicit wallet becomes unspendable via the contract's only mutation entry point (`rlp_execute`). Unlike a normal failed transaction (which is retryable), this state persists indefinitely because the guard flag itself is corrupted and there is no recovery method in the contract's public API.

### Likelihood Explanation
The trigger does not require a malicious validator, node, or operator — it only requires an ordinary signer/relayer to submit an RLP transaction whose `target` is a normal (not necessarily malicious) contract that returns a response large enough, or whose downstream call chain is expensive enough, to exceed the fixed 5 TGas callback budgets (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`). Because `target`, `method_name`, and `args` are attacker/user-chosen fields inside the signed Ethereum transaction, an ordinary unprivileged user (or a relayer acting on their behalf) can reliably construct such a call.

### Recommendation
Ensure `has_in_flight_tx` cannot be left permanently stuck. Options include: resetting the flag from a location whose write is guaranteed to persist even if the rest of the callback logic fails (e.g. wrap the "sensitive" logic in a way that cannot abort after the flag write, or perform the flag reset with a receipt structure that is guaranteed not to fail), add a resettable admin/self-unlock method (e.g., allow the account owner to force-reset `has_in_flight_tx` after a timeout using the current block height/timestamp), or size the callback static gas budgets to account for worst-case (max_length_returned_data-sized) responses so `GasExceeded` cannot realistically occur inside the callback itself.

### Proof of Concept
1. Deploy the wallet contract for an eth-implicit account `W`.
2. Sign an Ethereum transaction (via `W`'s private key) whose `target` is any NEP-141-style contract (or the address registrar) that can be made to return a JSON payload sized close to the network's `max_length_returned_data` limit (e.g. a `storage_balance_of`/lookup implementation that echoes back attacker-supplied padding) for the ERC20/`address_check` transfer path.
3. Submit this via `rlp_execute`; `inner_rlp_execute` dispatches the two-hop promise chain through `nep_141_storage_balance_callback` (or `address_check_callback`), whose static gas is fixed at `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:37-41`).
4. When the callback tries to read/deserialize the oversized `PromiseResult::Successful` payload, it exceeds its small fixed gas allotment and fails with `GasExceeded`.
5. Per NEAR's receipt-atomicity guarantee, the entire callback receipt (including the initial `self.has_in_flight_tx = false;` write at `lib.rs:202`/`lib.rs:140`) is rolled back, leaving `has_in_flight_tx == true` in persisted state.
6. Any subsequent call to `rlp_execute` on `W` now immediately returns `"Error: transaction already in progress, please try again later."` forever, since no method resets the flag — `W`'s funds are permanently frozen.

    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

                    Ok(p) => p,

            }
        };
        self.has_in_flight_tx = true;

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
