### Title
Replay-window race in `ConnectionState.Decrypt`/`VerifyRelay` lets a duplicated packet slip past the anti-replay guard before it is marked seen - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement anti-replay protection with a manual check-then-set pattern around a shared `Bits` window, guarded by `decryptLock`. The lock is released between the "check" step and the "set" step, and the expensive AEAD decrypt runs *outside* the lock. This mirrors the external report's root cause: a guard whose "entered" state can be reset/bypassed because the code path that is supposed to make the guard atomic (check window → do the protected work → mark window) is split into two separately-locked critical sections instead of one, letting a second, concurrently-processed copy of the same message observe the pre-update guard state.

### Finding Description
`Decrypt` performs:
1. Lock, `window.Check(messageCounter)`, unlock.
2. `dKey.DecryptDanger(...)` (AEAD decrypt, no lock held).
3. Lock, `window.Update(messageCounter)`, unlock. [1](#0-0) 

`VerifyRelay` (used for relay-forwarded frames) has the identical structure: [2](#0-1) 

Nebula processes inbound UDP packets on multiple concurrent reader goroutines/queues (`readOutsidePackets` is invoked per queue index `q`), and `Decrypt` is reached directly from that hot path once header parsing has picked out a `hostinfo`: [3](#0-2) 

An attacker who has captured (or is on-path for) one legitimate ciphertext packet does not need a certificate of their own — they only need to replay the exact same bytes. If two copies of the same captured packet are delivered to the two lock-released windows (e.g. by arriving on different reader queues at nearly the same time, which an off-path attacker can influence by flooding duplicates), both goroutines can pass `window.Check()` before either has called `window.Update()`, because the lock is dropped between the two calls. This is the direct analog of the reported bug class: a security guard ("has this counter been seen") that is supposed to be set atomically with the check is instead reset/left-open across a re-entrant window, letting a second call through when it should have been rejected.

### Impact Explanation
The CHANGELOG for this codebase already records that this exact area has needed hardening more than once ("Advance the replay window on relayed packets...", "Lock replay window updates so concurrent readers can't corrupt it"), showing the replay-window plumbing is a recognized hot spot for subtle races: [4](#0-3) 

With the current split-lock pattern, a duplicated packet can be AEAD-decrypted twice concurrently before the second copy is finally rejected by `Update`. While the caller in `outside.go` does discard the second copy's plaintext once `Update` reports `ErrAlreadySeen`, the check-then-act gap is exactly the kind of TOCTOU that anti-replay code must not have, and it weakens the guarantee that "once `Check` returns true the counter is immediately consumed" — the same property the external report flags as broken by `setXvsStore`/`setVenusInfo` being re-callable.

### Likelihood Explanation
Triggering the race requires only capturing/duplicating a single ciphertext packet and re-injecting it so two goroutines reach `Decrypt`/`VerifyRelay` for the same `ConnectionState` concurrently — no valid CA-signed certificate or completed handshake of the attacker's own is required, only knowledge of one legitimate packet's bytes (on-path capture or a lighthouse-visible relay frame, as already exercised in `TestRelayReplayProtection`). Likelihood is moderate: it depends on winning a narrow timing window across reader queues, which is easier under load/multi-queue configurations.

### Recommendation
Hold `decryptLock` for the entire check → decrypt → update sequence in both `Decrypt` and `VerifyRelay`, so the replay-window guard is atomic with respect to the AEAD verification it protects, instead of being split into two independently-lockable steps.

### Proof of Concept
1. Establish a tunnel and capture one legitimate data-plane ciphertext packet (`packet`, with `messageCounter = N`) addressed to a `hostinfo`.
2. Re-inject two copies of `packet` so they are dispatched to two different UDP reader queues/goroutines at nearly the same time (e.g., via `readOutsidePackets` on different `q` values).
3. Both goroutines call `hostinfo.ConnectionState.Decrypt` and both execute `window.Check(l, N)` before either calls `window.Update(l, N)`, because the lock is released after `Check` — both proceed to run the costly `DecryptDanger` AEAD operation concurrently on the same counter, and only the loser is caught by the second, `Update`-time check. func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
