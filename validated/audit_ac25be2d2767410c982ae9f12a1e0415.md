### Title
Malicious peer serving hash-mismatched `Attachment` bytes is scored as a successful, reliable source, letting it keep being selected via `get_most_reliable_source` while the legitimate `AttachmentInstance` never resolves - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` classifies an `AttachmentRequest` response as successful purely based on whether the HTTP body could be decoded, never checking that `Hash160::from_data(attachment.content) == request.content_hash`. A peer that always serves well-formed but content-hash-mismatched bytes is rewarded with `bump_successful_requests()` on every round, so `get_most_reliable_source` keeps preferring it, while the real `AttachmentInstance` is never resolved because it is only matched/resolved downstream by `attachment.hash()`.

### Finding Description
In `extend_with_attachments` [1](#0-0) , for each completed `AttachmentRequest`, the code does:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
```
There is no comparison of `Hash160::from_data(&response.attachment.content)` against `request.content_hash` at this point - decode success alone drives `bump_successful_requests()`.

The actual hash-based validation happens much later and out-of-band: in `AttachmentsDownloader::run`, once the sub-state-machine reaches `Done`, attachments are drained and matched to pending instances by `attachment.hash()` via `atlasdb.find_all_attachment_instances(&attachment.hash())` [2](#0-1) . If a lying peer's `attachment.content` hashes to something other than the requested `content_hash`, `find_all_attachment_instances` will simply find no (or the wrong) matching instances, and `context.attachments_batch.resolve_attachment(&attachment.hash())` never marks the originally-requested `content_hash` as resolved. The batch is therefore still incomplete and gets retried:
```
if !context.attachments_batch.has_fully_succeed() {
    context.attachments_batch.bump_retry_count();
    ...
}
``` [3](#0-2) 

Meanwhile, the reliability report for the lying peer's URL was already bumped as successful in `extend_with_attachments`, and this same `ReliabilityReport` object is what feeds `AttachmentRequest`'s ordering and `get_most_reliable_source`:
```
pub fn get_most_reliable_source(&self) -> (&UrlString, &ReliabilityReport) {
    self.sources.iter().max_by_key(|(_, v)| v.score()).expect(...)
}
``` [4](#0-3) 
and this is also what `Requestable::get_url` uses to pick which peer to actually query for the content on the next attempt [5](#0-4) .

Because the score keeps rising for the lying peer (its "requests" always decode successfully) while an honest peer that might simply be slower/less used has a lower or equal score, the lying peer remains the max-scoring source and continues to be picked by `get_most_reliable_source` on every retry, up to `max_attachment_retry_count`, without any honest fallback occurring.

### Impact Explanation
This denies resolution of a legitimately committed `AttachmentInstance`/BNS attachment: the node will keep re-querying the same lying peer for the same `content_hash`, the batch keeps failing `has_fully_succeed()`, and once `retry_count >= max_attachment_retry_count` the batch is simply dropped [6](#0-5) , permanently blocking resolution of that attachment even though an honest peer may have had the correct data all along. This matches the "attachment/BNS mismatch" / denial-of-resolution High-impact category from the rules.

### Likelihood Explanation
The attacker only needs to be a normal outbound-reachable peer serving the `/v2/attachments/{hash}` endpoint with attacker-controlled content bytes (no privileged role, no secret) - a trivial and repeatable action requiring no special timing or state beyond being included in `network.get_outbound_sync_peers()`/`get_data_url`. Since the check is purely "did decode succeed" and not "did content match hash," the attack succeeds every time.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, additionally verify `Hash160::from_data(&response.attachment.content) == request.content_hash` before calling `report.bump_successful_requests()` and before inserting into `self.attachments`; on mismatch, call `report.bump_failed_requests()` (or a dedicated "served bad content" penalty) instead, so a hash-mismatching peer is deprioritized rather than rewarded.

### Proof of Concept
Rust test plan (net test, e.g. in `stackslib/src/net/atlas/tests.rs`):
1. Build an `AttachmentsBatchStateContext` with one `AttachmentInstance`/`content_hash` and two peer URLs: `peer_lying` and `peer_honest`.
2. Simulate `BatchedRequestsState::Done` results where `peer_lying` always returns a decodable `GetAttachmentResponse` whose `attachment.content` hashes to something other than `content_hash`, and `peer_honest` is unavailable/slow (e.g., returns `None`/decode failure) for the first N rounds.
3. Call `extend_with_attachments` repeatedly (simulating retries) and inspect `context.peers.get("peer_lying").score()` vs `context.peers.get("peer_honest").score()`.
4. Assert that `peer_lying`'s score is higher than or equal to `peer_honest`'s after each round (proving it's never penalized for serving wrong-hash content), and that `get_most_reliable_source` on an `AttachmentRequest` built with both sources still returns `peer_lying`'s URL up through `max_attachment_retry_count` retries, while `attachments_batch.has_fully_succeed()` remains `false`, confirming the batch is eventually dropped at line `stackslib/src/net/atlas/download.rs:199-204` without ever trying `peer_honest`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
