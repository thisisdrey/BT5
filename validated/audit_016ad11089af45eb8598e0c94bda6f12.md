### Title
Permission check for multi-sig `Active` operations is bound to the declared `Contract.type` field rather than the actual unpacked contract message, enabling type-confusion permission bypass - ([File: chainbase/src/main/java/org/tron/core/utils/TransactionUtil.java])

### Summary
The n8n bug allowed a permission check to be evaluated against an unresolved/wrong value (the raw expression) instead of the resolved credential type actually used at execution, letting an attacker bypass an ownership check. In java-tron, the multi-sign `Active` permission bit-check, `checkPermissionOperations`, is evaluated using `contract.getTypeValue()` — the *declared* `ContractType` enum on the outer `Transaction.Contract` envelope — while the actuator that actually executes the operation determines behavior from the *inner* `Any` parameter payload via `any.is(XXXContract.class)`/`any.unpack(...)`. These are two different pieces of transaction data that are supposed to always agree, but the permission gate trusts only the declared enum tag.

### Finding Description
`checkPermissionOperations` is defined identically in two places and used on the signature/permission-verification path: [1](#0-0) [2](#0-1) 

It is invoked from `TransactionCapsule.checkPermission`/`validateSignature`/`addSign` (the actual consensus-critical multisig gate used before a transaction's signature weight is accepted): [3](#0-2) 

and from the RPC-facing `getTransactionSignWeight`/`getTransactionApprovedList` flows: [4](#0-3) [5](#0-4) 

The bit index used for the permission check is `contract.getTypeValue()` — this is the enum tag on `Transaction.Contract`, set independently by the client/attacker when constructing the raw transaction, not derived from the actual `Any` bytes. Meanwhile, actuator selection for real execution is performed by `ActuatorFactory`/`ActuatorCreator`, which *also* keys off the same declared `contract.getType()` to pick the actuator class, but each actuator's `validate()` cross-checks the `Any` payload against the expected message class (e.g. `this.any.is(TransferContract.class)`), throwing a "contract type error" if they disagree: [6](#0-5) [7](#0-6) 

The only place that structurally reconciles the declared `ContractType` with the actual `Any` payload bytes is `validContractProto`, which unpacks using the class registered for the declared type and re-serializes to compare bytes: [8](#0-7) 

I was not able to fully verify, within the remaining tool budget, (a) whether `validContractProto` is unconditionally invoked on every transaction path before `checkPermissionOperations`/actuator execution (it appears tied to P2P block/transaction ingestion, e.g. `TransactionMessage`/`BlockMessage`, rather than the local broadcast/actuator-validate path), and (b) whether protobuf's `Any.is()`/`unpack()` type-URL matching combined with `getOwner(contract)`'s reflection-based owner-field extraction (which also switches on `contract.getType()`) could be made to disagree with the actuator's own re-derivation of the owner/operation semantics for some contract type pair. Because I could not conclusively trace a concrete transaction that produces divergent behavior between the declared `ContractType` and the actuator-selected/validated logic under `validContractProto`'s bytes-compare guard, I cannot assert with confidence that funds/permission bypass is currently reachable in this exact form.

### Impact Explanation
If such a divergence were confirmed reachable (i.e., a signer holding an `Active` permission whose `operations` bitmap authorizes only a benign contract type, such as `TransferContract`, could get a differently-typed operation such as `AccountPermissionUpdateContract` or a witness/committee-affecting contract executed), this would let a partially-privileged co-signer perform unauthorized account operations — a direct analog of the n8n credential-authorization bypass (CWE-863: Incorrect Authorization).

### Likelihood Explanation
Low-to-unconfirmed. The `validContractProto` bytes-comparison and each actuator's own `any.is(ExpectedContract.class)` check appear to form two independent guards that would need to be simultaneously bypassed or bypassed on divergent code paths (e.g., the local wallet/RPC broadcast path vs. the P2P ingestion path) for exploitation, and I could not confirm within this session that `checkPermissionOperations`'s bit-check ever runs on a contract whose declared `ContractType` and actual `Any` payload have been allowed to diverge past both guards.

### Recommendation
Ensure `checkPermissionOperations` (and any account-address extraction such as `TransactionCapsule.getOwner`) always evaluates against the actual, fully-parsed inner `Any` contract message type — not the attacker-controlled outer `Transaction.Contract.type` enum tag — and that `validContractProto`'s type/payload consistency check is unconditionally enforced on every code path that leads to permission verification or actuator execution (local broadcast, RPC creation, and P2P ingestion alike), not only the P2P block-validation path.

### Proof of Concept
Not established. A conclusive PoC would require constructing a `Transaction.Contract` where the declared `ContractType` differs from the actual `google.protobuf.Any` payload type, and demonstrating that it reaches `checkPermissionOperations`/execution without being rejected by `validContractProto` or the actuator's own `any.is(...)` check — this was not verified within the available tool budget.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

  public static void validContractProto(Transaction.Contract contract)
      throws InvalidProtocolBufferException, P2pException {
    Any contractParameter = contract.getParameter();
    Class clazz = TransactionFactory.getContract(contract.getType());
    if (clazz == null) {
      throw new P2pException(PROTOBUF_ERROR, PROTOBUF_ERROR.getDesc());
    }
    com.google.protobuf.Message src = contractParameter.unpack(clazz);
    com.google.protobuf.Message contractMessage = parse(clazz,
        Message.getCodedInputStream(src.toByteArray()));

    Message.compareBytes(src.toByteArray(), contractMessage.toByteArray());
  }
