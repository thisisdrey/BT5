Audit Report

## Title
XCM `ERC20Transactor` credits/debits the exact requested amount based solely on an ERC20 contract's boolean `transfer` return value, without verifying the real balance delta of the checking/beneficiary account - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in `ERC20Transactor` decide how much value to credit into (or trust as deposited from) the XCM `AssetsInHolding` register purely from the boolean return of the underlying ERC20 `transfer` call, never from an observed `balanceOf` delta on the checking account or beneficiary. Because the `ERC20Matcher` used to select which contract to call accepts any `AccountKey20`-keyed location as an asset id with no on-chain registry or permissioning, an unprivileged attacker can supply an arbitrary (self-deployed) or any real fee-on-transfer/deflationary ERC20 contract and cause the XCM holding register's accounted amount to diverge from what actually moved in the ERC20 contract.

## Finding Description
`withdraw_asset_with_surplus` calls `IERC20::transferCall` to move `amount` from the withdrawing account to the checking account, and on a decoded `true` return unconditionally constructs `AssetsInHolding::new_from_fungible_credit(..., Box::new(Erc20Credit(amount)))` — crediting the *requested* `amount`, not any measured balance change: [1](#0-0) 

Symmetrically, `deposit_asset_with_surplus` calls `transfer` from the checking account to the beneficiary and, on `Ok(true)`, returns `Ok(surplus)` — treating the XCM deposit as fully successful for `amount` without checking the beneficiary's real ERC20 balance increase: [2](#0-1) 

The `Erc20Credit` type's own documentation confirms this is a deliberate design choice to skip runtime-level balance enforcement, relying entirely on the external contract: [3](#0-2) 

Critically, which contract gets called is not gated by any asset registry. `ERC20Matcher` matches on `IsLocalAccountKey20`/`AccountKey20ToH160`, converting *any* `AccountKey20` location junction directly into the `H160` contract address that gets called: [4](#0-3)  This transactor is wired into the live `AssetTransactors` tuple on Asset Hub: [5](#0-4) 

This means an attacker can deploy an arbitrary `pallet-revive` contract implementing `IERC20` that returns `true` on `transfer` while moving less than `value` (fee-on-transfer/deflationary semantics), or reference an already-deployed real-world token with such semantics, and route an XCM program's `WithdrawAsset`/`DepositAsset` through it with no permissioned check preventing this.

## Impact Explanation
The XCM holding register (`AssetsInHolding`) is the shared accounting abstraction the XCM executor uses for all subsequent instructions in a program, including `ExchangeAsset` against `pallet-asset-conversion` pools, further `DepositAsset`/`InitiateTransfer` instructions, etc. Since the `Erc20Credit` inserted by `withdraw_asset_with_surplus` reflects the *requested* amount rather than the amount that actually reached the checking account, any subsequent instruction that consumes this holding entry without itself calling back into the ERC20 contract (e.g., a pool swap trading the inflated ERC20 credit for a different, fully-backed asset) will operate on a value the checking account does not actually possess in the underlying ERC20 contract. This is a "theft/unbacked mint" pattern on the XCM holding accounting relative to the real ERC20 balance backing it, matching the "theft or unbacked mint" bucket in the impact gate. The corrupted value is the `Erc20Credit(amount)`/`AssetsInHolding` entry produced at `withdraw_asset_with_surplus`, line ~200, and the deposit "success" determination at `deposit_asset_with_surplus`, line ~279.

## Likelihood Explanation
This is reachable by any unprivileged actor: deploying a contract via `pallet-revive` is a public, unprivileged operation, and there is no registry restricting which `H160` address can be used as an ERC20 asset id in an XCM program routed through this transactor (`ERC20Matcher` accepts any `AccountKey20` junction). Combining a self-controlled fee-on-transfer/false-success ERC20 contract with an XCM program (e.g., `WithdrawAsset` + `ExchangeAsset` + `DepositAsset`) executed via `pallet_xcm::execute` or similar public XCM entry points requires no privileged role, relayer, or validator collusion.

## Recommendation
Before crediting `Erc20Credit(amount)` in `withdraw_asset_with_surplus`, or treating a deposit as fully successful in `deposit_asset_with_surplus`, snapshot the relevant account's ERC20 balance via `balanceOf` immediately before and after the `transfer` call and use the observed delta — not the boolean return value — as the amount credited/considered received. The boolean return can still be used as an additional sanity check, but must never be the sole source of truth for the transferred amount.

## Proof of Concept
1. Deploy a `pallet-revive` contract implementing `IERC20` whose `transfer` function always returns `true` but moves less than `value` (or moves nothing) — a standard fee-on-transfer/malicious-token pattern.
2. Because `ERC20Matcher` (`cumulus/parachains/runtimes/assets/common/src/lib.rs` L157-160) accepts any `AccountKey20` location as a valid asset id, reference this contract's address directly in an XCM `Asset` id without any registration step.
3. Submit an XCM program (e.g., via `pallet_xcm::execute`) containing `WithdrawAsset` for `amount` of this asset from the attacker's own account, followed by an `ExchangeAsset` swapping the resulting holding-register credit against a real, fully-backed asset pool on Asset Hub, followed by `DepositAsset` of the swap proceeds to the attacker.
4. Observe `withdraw_asset_with_surplus` credits `Erc20Credit(amount)` (`erc20_transactor.rs` L197-203) even though the checking account's real ERC20 balance increased by less than `amount`, and that this inflated credit is then exchanged for real backed-asset liquidity in the pool step, demonstrating extraction of value not actually backed by the ERC20 contract's real balance movement.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.

	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
