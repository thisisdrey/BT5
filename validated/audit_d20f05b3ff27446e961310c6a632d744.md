### Title
Permissionless pre-creation of the deterministic contract-deployment address permanently DoSes a pending `CreateSmartContract` transaction - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
`VMActuator.create()` computes the address a new contract will be deployed to and rejects the deployment if *any* account already exists at that address. Because the address is deterministic and derivable from public transaction data before the deployment transaction is confirmed, any unprivileged account can pre-empt it with an ordinary TRX transfer, permanently failing the legitimate deployer's transaction — the same "initialize/finalize out of order" DoS pattern described in the external report (where `UniswapV3Pool.initialize()` could be front-run before the intended launch-finalization step).

### Finding Description
`WalletUtil.generateContractAddress()` derives the new contract's address purely from the transaction's raw-data hash (`txRawDataHash`) and the owner address: [1](#0-0) 

Both inputs are visible in the pending, unconfirmed `CreateSmartContract` transaction (the raw data hash/transaction ID is computable from the signed-but-not-yet-executed transaction bytes seen in the mempool, and the owner address is a plaintext field). Any observer can therefore compute the exact contract address before the deployment transaction is applied.

`VMActuator.create()` then treats the *mere existence* of an account at that address as fatal — not just the existence of contract code: [2](#0-1) 

This is weaker than the equivalent CREATE2 path in `Program.createContractImpl`, which explicitly checks `isContractExist(...)` before treating a pre-existing account as a collision (allowing a plain funded/EOA account to be upgraded in place): [3](#0-2) 

Because TRON auto-creates an `AccountCapsule` for any address that receives a TRX transfer, an attacker who observes a pending `CreateSmartContract` transaction can:
1. Compute `contractAddress = sha3omit12(txRawDataHash || ownerAddress)`.
2. Send a trivial TRX transfer to `contractAddress`, getting it included in (or before) the same block as the victim's deployment transaction.
3. Cause `rootRepository.getAccount(contractAddress) != null` to be true when the victim's `CreateSmartContract` is validated, throwing `ContractValidateException("Trying to create a contract with existing contract address...")` and permanently failing that specific signed transaction (its txID/address pairing can never succeed).

This mirrors the reported bug class exactly: a state-initializing precondition (an account/pool coming into existence) that should only happen as part of the intended finalization flow can instead be triggered early and permissionlessly by any party, denying the legitimate finalization.

### Impact Explanation
This lets any unprivileged account broadcaster grief a specific, targeted contract deployment transaction, causing it to permanently fail validation (denial of service against that transaction). Because contract creation is a core, broadcastable transaction type reachable by any account with minimal TRX cost, this qualifies as a concrete node-reachable DoS against a specific user-facing operation, consistent with a Medium risk rating (matching the reported bug's rating).

### Likelihood Explanation
Exploitation requires only mempool visibility of a pending `CreateSmartContract` transaction and the ability to broadcast a cheap TRX transfer that lands before it — both trivially available to any network participant, with no special privilege, making this readily reachable.

### Recommendation
Align the CREATE path with the CREATE2 path: only reject the deployment if an actual contract already exists at the computed address (i.e., check code/type via the same `isContractExist`-style logic used in `Program.createContractImpl`), and otherwise upgrade the pre-existing (non-contract) account in place rather than failing validation.

### Proof of Concept
1. Observe a broadcast, unconfirmed `CreateSmartContract` transaction `T` with owner address `O`.
2. Compute `txRawDataHash = TransactionCapsule(T).getTransactionId()` and `addr = Hash.sha3omit12(txRawDataHash || O)` per `WalletUtil.generateContractAddress`.
3. From any funded account, broadcast a plain TRX transfer to `addr` with sufficient fee/priority to be applied before `T`.
4. When `T` is validated, `VMActuator.create()` finds `rootRepository.getAccount(addr) != null` and throws `ContractValidateException`, permanently failing `T`'s deployment. [2](#0-1) [1](#0-0)

  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
