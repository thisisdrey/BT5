### Title
Unbounded per-message heap allocation via sparse bloom filter decoding amplifies a tiny request into a ~16MB allocation - (File: stackslib/src/util_lib/bloom.rs)

### Summary
`decode_bitfield` only checks that the attacker-controlled `vec_len` field is below `MAX_MESSAGE_LEN.saturating_sub(5)` (~16MB) before doing `vec![0u8; vec_len as usize]`, and the only downstream consistency check (`BitField::consensus_deserialize` comparing `BITVEC_LEN!(num_bits)` to `vec_len`) is satisfied simply by choosing a matching `num_bits`, which costs the attacker nothing extra. This lets a remote peer send a tiny (tens-of-bytes) sparse-encoded `BloomFilter<BloomNodeHasher>` payload — reachable through the mempool-sync bloom filter path (`stackslib/src/core/mempool.rs`, `stackslib/src/net/api/postmempoolquery.rs`) — and force the node to allocate up to ~16MB per message with almost no attacker-side bandwidth cost.

### Finding Description
`decode_bitfield` (stackslib/src/util_lib/bloom.rs:114-153) reads a wire-controlled `vec_len: u32` and bounds it only against `MAX_MESSAGE_LEN.saturating_sub(5)`: [1](#0-0) 

then unconditionally allocates `vec![0u8; vec_len as usize]` before reading only `num_filled` small (idx,value) pairs from the wire. `should_use_sparse_encoding` (stackslib/src/util_lib/bloom.rs:81-83) only requires `num_filled * 5 + 4 < vec_len`, which is trivially satisfied with `num_filled = 1` and `vec_len` near 16MB.

The only other check tying `vec_len` to something meaningful is in `BitField::consensus_deserialize` (stackslib/src/util_lib/bloom.rs:164-175), which compares `BITVEC_LEN!(num_bits)` (also attacker-controlled, a `u32` read immediately before the bitfield) to `bits.len()`. Since `num_bits` is fully attacker-controlled and independent from actual data volume sent, the attacker can trivially pick `num_bits` so that `BITVEC_LEN!(num_bits) == vec_len`, satisfying this equality check with zero additional bytes on the wire. Thus the equality "bytes allocated == bytes actually carried on the wire for `num_filled` entries" is broken: the attacker sends `encoding_byte(1) + vec_len(4) + num_filled(4) + num_filled*(idx:4+val:1)` — for `num_filled=1`, about 14 bytes total plus the preceding `num_bits` field — and the server allocates a `Vec<u8>` of size `vec_len` (up to ~16MB).

This `BloomFilter<BloomNodeHasher>` type is the wire format used for mempool-sync "bloom filter" queries (`stackslib/src/core/mempool.rs`, `stackslib/src/net/api/postmempoolquery.rs`), which is reachable via the node's RPC/HTTP port without any privileged secret.

### Impact Explanation
Each malicious request costs the attacker on the order of tens of bytes but forces the target node to allocate up to ~16MB of heap. Because this is over an HTTP/RPC-reachable, unauthenticated endpoint, an attacker can issue repeated small requests (each independently cheap to construct/send) to accumulate large memory pressure on the node, eventually leading to out-of-memory conditions / degraded service (memory-exhaustion DoS). The amplification factor (roughly 16MB / ~15 bytes, over 1,000,000x) is the key distinguishing factor from ordinary bandwidth-bound volumetric DoS: the attacker does not need to send large volumes of data, only a large number of tiny messages, each of which is disproportionately expensive for the server to service.

### Likelihood Explanation
- No privileged role, secret, or prior state is required; any remote peer that can reach the node's RPC/HTTP port and construct a bloom-filter-carrying request can trigger this.
- The attack is trivially repeatable: each connection/request is independent and cheap to construct.
- The amplification is deterministic and does not depend on race conditions, timing, or non-default configuration.

### Recommendation
Enforce a much tighter, purpose-specific cap on `vec_len` in `decode_bitfield` that reflects realistic bloom-filter sizes (e.g., bound it to the maximum bitfield size implied by the protocol's `max_items`/`error_rate` parameters actually used for mempool sync, not the generic `MAX_MESSAGE_LEN`). Additionally, avoid eagerly allocating `vec_len` bytes before validating that the message actually supplies commensurate data; consider incrementally growing the buffer, or requiring `num_filled` to be proportionate to `vec_len` in a way that bounds the allocation-to-payload ratio tightly (not just via the loose `should_use_sparse_encoding` heuristic).

### Proof of Concept
Rust test in `stackslib::util_lib::bloom` (or an integration test hitting `postmempoolquery`):
1. Construct raw bytes: `[BitFieldEncoding::Sparse as u8]` + `vec_len: u32 = MAX_MESSAGE_LEN - 5` (as LE/BE per codec) + `num_filled: u32 = 1` + one `(idx: u32 = 0, value: u8 = 1)` pair.
2. Prepend a `num_bits: u32` chosen such that `BITVEC_LEN!(num_bits) == vec_len` to satisfy `BitField::consensus_deserialize`'s length check.
3. Feed this ~14-byte buffer to `BitField::consensus_deserialize` (or `BloomFilter::<BloomNodeHasher>::consensus_deserialize` with the appropriate header bytes).
4. Assert that the resulting `Vec<u8>` has `capacity()`/`len()` ≈ `vec_len` (~16MB) despite the input buffer being only a few dozen bytes, demonstrating the allocation-to-payload amplification. Optionally wrap the call in a loop simulating repeated small requests and observe process RSS growth to demonstrate cumulative memory pressure.
