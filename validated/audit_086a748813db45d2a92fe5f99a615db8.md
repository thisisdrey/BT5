### Title
Unauthenticated `/shutdown` HTTP request permanently halts the signer's event-receiver loop - (File: libsigner/src/events.rs)

### Summary
`SignerEventReceiver::next_event` treats any HTTP `POST /shutdown` to its bound event-listener port as a legitimate stop command, with no check that the request originated from the internal `SignerStopSignaler`. Any remote party that can open a TCP connection to that port can send this single crafted request to set `stop_signal` and terminate `main_loop`.

### Finding Description
The broken equality is: *"received `POST /shutdown` on the event port" == "authenticated shutdown request from the node's own `SignerStopSignaler`"*. In reality the handler in `next_event` only checks the URL path, not the sender's identity or any secret/token: [1](#0-0) 

```rust
} else if request.url() == "/shutdown" {
    event_receiver.stop_signal.store(true, Ordering::SeqCst);
    Err(EventError::Terminated)
```

Compare this with the legitimate internal caller, `SignerStopSignaler::send`, which simply opens a plain `TcpStream` to `self.local_addr` and writes a raw HTTP request with no authentication token, secret, or signature at all: [2](#0-1) . Since the wire format it sends (`POST /shutdown HTTP/1.1 ... Content-Length ...`) is trivially reproducible by anyone who can reach the port, there is no distinguishing feature between the legitimate internal caller and a remote attacker.

`main_loop` treats `EventError::Terminated` as a clean, permanent exit signal: [3](#0-2)  — it `break`s out of the loop entirely, and `is_stopped()` will subsequently short-circuit any restart attempt inside `next_event` at [4](#0-3) .

There is no check elsewhere in `next_event`'s dispatch chain (`/status`, `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`) that gates `/shutdown` behind any credential, unlike, e.g., StackerDB chunk processing which requires slot signatures recovered via `chunk.recover_pk()`. The `/shutdown` branch requires nothing but reachability of the port and a syntactically valid HTTP POST.

### Impact Explanation
A single unauthenticated HTTP request permanently stops the signer's event-ingestion main loop. Once `main_loop` breaks, the signer stops receiving `StackerDBChunksEvent`, `BlockValidateResponse`, `NewBurnBlock`, and `NewBlock` events from the node — effectively taking the signer offline for signing operations until manually restarted. This is a Critical-category "remote crash/unauthenticated DoS from a few messages" (in this case exactly one message), assuming the attacker can reach the bound event port.

### Likelihood Explanation
The event-listener address is configured by the node/signer operator (`endpoint` in `stacks-signer` config) and is typically intended to be reachable only by the co-located node's event dispatcher. Whether it is reachable by a truly remote, unprivileged network attacker depends entirely on operator deployment (binding to `127.0.0.1` vs. a routable/`0.0.0.0` address, and firewalling). This repo's code does not itself enforce a loopback-only bind or any authentication — `bind()` accepts whatever `SocketAddr` is configured: [5](#0-4) . If deployed on a reachable interface, the attack requires only a single crafted TCP/HTTP request, no credentials, and is trivially repeatable.

### Recommendation
Add an authentication mechanism to the `/shutdown` endpoint (and ideally to the whole event-receiver HTTP surface), e.g., a shared secret/token known only to the node and signer process that must be presented in a header, or restrict `SignerEventReceiver::bind` to loopback addresses only. At minimum, validate that the shutdown request originates from `127.0.0.1`/the local node process before honoring it, since `tiny_http::Request` exposes the peer address.
