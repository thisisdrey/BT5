### Title
Maintenance/optimization RPCs bypass Praefect's read-only enforcement, allowing writes on inconsistent repository replicas - (File: internal/praefect/router_per_repository.go)

### Summary
The BakerFi report describes a `rebalance` function that could still be invoked (and collect performance fees) while the vault was paused, even though the project's own documentation and other functions (like withdrawals) respect the pause. The root cause is a state-mutating code path that is exempt from a guard that other, similarly state-mutating code paths correctly enforce. Gitaly (via Praefect) has an analogous inconsistency: normal repository mutator RPCs are blocked from writing to a replica that is stale/inconsistent (`ErrRepositoryReadOnly`), but the "maintenance" RPC class (which includes `OptimizeRepository`, used for repacking, garbage collection, ref-pack compaction, etc.) is explicitly routed without this check.

### Finding Description
Praefect enforces read-only status of a repository replica for ordinary mutator RPCs. In `PerRepositoryRouter.RouteRepositoryMutator`, if the primary's replica is not part of the "consistent" set for the repository, the request is rejected with `ErrRepositoryReadOnly`: [1](#0-0) 

This is the mechanism analogous to BakerFi's "pause": once a repository/replica is deemed inconsistent (would be considered "read-only"/paused for writes), `mutatorStreamParameters` propagates that error straight back to the client: [2](#0-1) 

However, RPCs classified under `protoregistry.OpMaintenance` (e.g. `RepositoryService/OptimizeRepository`) are routed through a completely different function, `RouteRepositoryMaintenance`, which does **not** consult `GetConsistentStoragesByRepositoryID`/consistent-storage state at all. Its own doc comment states this explicitly: [3](#0-2) 

The function only filters on node health and on whether a replica is `Assigned`/has a valid `Generation`, but never checks whether the replica is currently consistent (i.e., "read-only"): [4](#0-3) 

Meanwhile, on the Gitaly node side, the housekeeping middleware unconditionally schedules `OptimizeRepository` after every mutator RPC and runs it via `manager.OptimizeRepository`, which itself performs real write transactions (garbage collection, repacking, MVCC-based garbage collection) against the local repository: [5](#0-4) 

Because `RouteRepositoryMaintenance` doesn't gate on consistency the way `RouteRepositoryMutator` does, an inconsistent/stale replica that would otherwise be protected from client-driven writes (via `ErrRepositoryReadOnly`) can still be targeted for repository optimization writes through the maintenance path — the exact same class of bug as `rebalance` bypassing `whenNotPaused` while `withdraw` respects it.

### Impact Explanation
When a replica is marked inconsistent (effectively "read-only" — akin to the paused Vault), Gitaly is meant to prevent further local mutation of that replica until it's reconciled via replication, since concurrent independent writes on a stale replica can diverge further from the primary/consistent state and complicate later replication/repair. `RouteRepositoryMaintenance`'s explicit bypass of that consistency check allows write-class housekeeping operations (compaction, pruning, repacking) to execute on such replicas anyway, causing local state drift on nodes that are supposed to be frozen from local writes, similar to how BakerFi could still accrue fee-affecting side effects (`_harvestAndMintFees`) during a pause. This is a logic/DoS-adjacent correctness issue rather than a direct funds-loss issue, matching the "Medium" severity class of the original finding.

### Likelihood Explanation
Likelihood is moderate-to-high in normal operation: housekeeping is triggered automatically after ordinary write RPCs via the housekeeping middleware without any additional privileged action from an attacker, and inconsistency between replicas is an ordinary, expected transient state in a Praefect cluster (e.g., during partial replication failures or when a secondary is behind). Any ordinary user's push/write flow that leaves a replica temporarily inconsistent can result in maintenance RPCs being routed to that inconsistent replica.

### Recommendation
Add the same consistency check used in `RouteRepositoryMutator` to `RouteRepositoryMaintenance` (or gate the housekeeping middleware's scheduling logic in `internal/grpc/middleware/housekeeping/middleware.go`) so that maintenance/optimization work is skipped or deferred for storages that are not part of the repository's `consistentStorages` set, rather than unconditionally including "all healthy nodes regardless of whether they're consistent or not."

### Proof of Concept
1. Configure a Praefect virtual storage with a primary and at least one secondary; create a repository so that both replicas are initially consistent.
2. Push changes such that the secondary fails to replicate (e.g. by making it unhealthy during a mutator RPC, then restoring health afterward), leaving the secondary's replica marked inconsistent for that repository (this is how `TestStreamDirectorReadOnlyEnforcement` simulates an inconsistent replica: [6](#0-5) ).
3. Issue a normal mutator RPC (e.g. `DeleteRefs`) targeted through Praefect — confirm it is rejected with `ErrRepositoryReadOnly`, as shown by the existing test: [7](#0-6) .
4. Issue an `OptimizeRepository` RPC (an `OpMaintenance` RPC) against the same repository. Because `RouteRepositoryMaintenance` includes all healthy assigned nodes without checking `consistentStorages`, the RPC is routed to and executed on the inconsistent secondary as well, performing local writes (repack/gc) on a replica that the mutator path treats as read-only.

Note: I was not able to execute this PoC against a live cluster within this analysis; the conclusion is based on static code review of `router_per_repository.go`, `router_node_manager.go`, `coordinator.go`, and `middleware.go`. If a background Devin agent needs to confirm the runtime behavior (e.g., stepping through `TestStreamDirectorReadOnlyEnforcement`-style scenarios for `OptimizeRepository`), that would require running the existing Praefect test suite with an added maintenance-routing test case.

```go
// RouteRepositoryMaintenance will route the maintenance call to all healthy nodes in a best-effort
// strategy. We do not raise an error in case the primary node is unhealthy, but will in case all
// nodes are unhealthy.
func (r *PerRepositoryRouter) RouteRepositoryMaintenance(ctx context.Context, virtualStorage, relativePath string) (RepositoryMaintenanceRoute, error) {
	healthyNodes, err := r.healthyNodes(virtualStorage)
	if err != nil {
		return RepositoryMaintenanceRoute{}, err
	}

	healthyNodesByStorage := map[string]RouterNode{}
	for _, healthyNode := range healthyNodes {
		healthyNodesByStorage[healthyNode.Storage] = healthyNode
	}

	metadata, err := r.rs.GetRepositoryMetadataByPath(ctx, virtualStorage, relativePath)
	if err != nil {
		return RepositoryMaintenanceRoute{}, fmt.Errorf("getting repository metadata: %w", err)
	}
```

```go
func (m *Middleware) scheduleHousekeeping(ctx context.Context, repo *gitalypb.Repository, force bool) {
	m.mu.Lock()
	defer m.mu.Unlock()

	key := m.getRepoKey(repo)

	a, ok := m.repoActivity[key]
	if !ok {
		a = newActivity()
		m.repoActivity[key] = a
	}
	a.writeCount++

	if a.active {
		return
	}

	pendingOps := m.pendingOperations(a, force)
	if len(pendingOps) == 0 {
		return
	}

	m.logger.WithFields(log.Fields{
		"forced":     force,
		"operations": pendingOps,
	}).InfoContext(ctx, "beginning scheduled housekeeping")

	// Mark that these operations are running at the current write count
	for _, op := range pendingOps {
		a.writeCountAtLastRun[op] = a.writeCount
	}

	m.markHousekeepingActive(key)

	m.wg.Add(1)
	go func() {
		// We need to call OptimizeRepository with a child context that's disowned from the parent's
		// cancellation signals we're executing it asynchronously. Providing the existing `ctx` would
		// cause it to fail, since `ctx` would be cancelled when this request completes. We still want
		// to be able to abort the worker when the middleware shuts down though, so we propagate
		// cancellation from the middleware's shutdown context.
		housekeepingCtx, housekeepingCancel := context.WithCancel(context.WithoutCancel(ctx))
		stopShutdownPropagation := context.AfterFunc(m.shutdownCtx, housekeepingCancel)

		defer func() {
			stopShutdownPropagation()
			m.markHousekeepingInactive(key)
			m.logger.InfoContext(housekeepingCtx, "ended scheduled housekeeping")
			housekeepingCancel()
			m.wg.Done()
		}()

		localRepo := m.localRepoFactory.Build(repo)
		if err := m.manager.OptimizeRepository(housekeepingCtx, localRepo,
			manager.WithOptimizationStrategyConstructor(
				func(info stats.RepositoryInfo) housekeeping.OptimizationStrategy {
					return housekeeping.NewSelectiveOptimizationStrategy(info, pendingOps)
				},
			),
			manager.WithMVCCGarbageCollection(),
		); err != nil {
			m.logger.WithError(err).ErrorContext(housekeepingCtx, "failed scheduled housekeeping")
		}
```
