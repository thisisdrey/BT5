## Title
Missing refund/resolve callback for `NativeWithdraw`, `StorageDeposit`, and `AuthCall` (with deposit) breaks debit/delivery conservation on downstream promise failure - ([File: contracts/defuse/src/contract/intents/state.rs])

## Summary
`Contract::native_withdraw`, `Contract::storage_deposit`, and `Contract::auth_call` (deposit branch) all synchronously call `self.withdraw(...)` to debit the signer's internal wNEAR balance *before* scheduling the async `ext_wnear::near_withdraw` promise chain [1](#0-0) [2](#0-1) [3](#0-2) . Unlike `internal_ft_withdraw`, which always chains a `ft_resolve_withdraw` callback that re-credits (`self.deposit`) any amount that failed to be delivered [4](#0-3) [5](#0-4) , none of the three wNEAR-based paths (`do_native_withdraw`, `do_storage_deposit`, `do_auth_call`) have any resolver that re-credits the debited internal balance if the downstream promise fails [6](#0-5) [7](#0-6) .

## Finding Description
The binding that must hold is: `sum(internal_sub_balance debits of wNEAR across NativeWithdraw/StorageDeposit/AuthCall(deposit) intents) == sum(NEAR actually transferred to receiver_id / storage actually deposited / on_auth deposit actually delivered)`.

This binding is broken by design, independent of batching tricks: the debit happens synchronously inside the top-level `execute_intents` receipt via `self.withdraw(owner_id, [(wnear_token_id, amount)], Some("withdraw"), false)` [8](#0-7) . Once that receipt finishes, NEAR protocol commits this state change permanently — it is not rolled back by what happens in later, separate receipts (the scheduled promise chain).

The follow-on promise chain (`near_withdraw` -> `do_native_withdraw`/`do_storage_deposit`/`do_auth_call`) can fail for reasons entirely within an unprivileged attacker's control:
- `do_native_withdraw` panics via `require!(promise_result_checked_void(0).is_ok(), ...)` if `near_withdraw` fails, or the subsequent `Promise::new(withdraw.receiver_id).transfer(...)` can itself fail if `receiver_id` is an invalid/non-existent account [6](#0-5) .
- `do_auth_call` similarly panics on `near_withdraw` failure, or the subsequent `on_auth` call to an attacker-controlled `contract_id` can be made to fail/panic (e.g., a contract that deliberately reverts) [7](#0-6) .
- `storage_deposit`'s callback (`do_storage_deposit`, same pattern as `do_native_withdraw`/`do_ft_withdraw`'s storage branch) can fail if the target contract rejects the storage deposit (e.g. unregistered/invalid `receiver_id`) analogous to `do_ft_withdraw`'s `storage_deposit` branch [9](#0-8) .

In every one of these failure cases, none of `do_native_withdraw`, `do_storage_deposit`, `do_auth_call` schedule a resolver comparable to `ft_resolve_withdraw` that re-credits (`self.deposit`) the signer for the undelivered value. Contrast this with the `Nep141`/`ft_withdraw` path, which explicitly chains `.then(...ft_resolve_withdraw(...))` and refunds any amount not actually transferred [4](#0-3) .

Because each of the three wNEAR-based intents is `.detach()`ed independently [10](#0-9) [11](#0-10) [12](#0-11) , an attacker can submit a single `MultiPayload` batch from one signer containing several `NativeWithdraw` + `StorageDeposit` + `AuthCall` intents, each with a distinct malicious `receiver_id`/`contract_id` chosen to make the *delivery* leg fail while the *debit* leg (which only checks the internal ledger, not deliverability) always succeeds. All debits are committed in the synchronous portion of `execute_intents`; the async failures happen afterward with no compensating credit, permanently destroying the difference between what was debited and what was delivered.

Existing guards do not prevent this: `internal_sub_balance` only checks the internal ledger has sufficient balance, not that the corresponding external transfer will succeed [13](#0-12) ; `MultiPayload::verify`/nonce checks only validate authorization of the *intent*, not deliverability of its downstream promise.

## Impact Explanation
The signer's own internal wNEAR balance is permanently debited without receiving the corresponding NEAR/storage/on-auth value — the wNEAR that was backing this balance stays locked in the Defuse contract's real holdings (or, once `near_withdraw` succeeds, becomes NEAR trapped in the Defuse contract's own account) with no path back to the user. This matches the "refund or resolver credit that does not match what failed to settle" / "user funds permanently frozen" Critical categories. The bug is fully repeatable: any account can produce this outcome against itself for any amount, any number of times, across `NativeWithdraw`, `StorageDeposit`, and `AuthCall`-with-deposit intents, and combining several in one batch merely multiplies how much value can be lost per transaction. Note this is a self-inflicted loss for the attacker/signer unless it can be weaponized against a victim signature they don't control — since the attacker must be the account whose wNEAR is debited (the `owner_id`/`signer_id` come from the verified intent), the practical "attacker profit" is limited to making other users lose funds only if the attacker can get a victim's signed payload executed with attacker-chosen `receiver_id`/`contract_id` fields not covered by the signature — that would need separate verification (whether `receiver_id`/`contract_id` are part of the signed intent, which they are, per `NativeWithdraw`/`AuthCall`/`StorageDeposit` intent structs) — so this reduces to funds being genuinely lost for whichever `owner_id`/`signer_id` signed the batch (self-loss unless a relayer submits a batch on someone else's behalf with a legitimately signed intent that then encounters a failing downstream call, which is a normal operational risk, not an attacker profit vector).

## Likelihood Explanation
No special privileges are required; any signer can trigger this by including a `NativeWithdraw`/`StorageDeposit`/`AuthCall` intent with a `receiver_id`/`contract_id` engineered to fail on the delivery leg (e.g. a non-existent account, or a contract that reverts `on_auth`/`storage_deposit`). This is trivially reproducible and costs only the value being (self-)destroyed plus gas.

## Recommendation
Add resolver callbacks analogous to `ft_resolve_withdraw` for `do_native_withdraw`, `do_storage_deposit`, and `do_auth_call` that inspect the final promise result and, on failure, re-credit (`self.deposit`) the debited wNEAR amount back to the `owner_id`/`signer_id`, mirroring the pattern already implemented in `contracts/defuse/src/contract/tokens/nep141/withdraw.rs`.

    fn internal_sub_balance(
        &mut self,
        owner_id: &AccountIdRef,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
    ) -> Result<()> {
        let owner = self
            .accounts
            .get_mut(owner_id)
            .ok_or_else(|| DefuseError::AccountNotFound(owner_id.to_owned()))?
            .get_mut()
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            owner
                .token_balances
                .sub(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        Ok(())
    }

#[near]
impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
}

    #[private]
    pub fn do_auth_call(signer_id: AccountId, auth_call: AuthCall) -> Promise {
        if !auth_call.attached_deposit.is_zero() {
            require!(
                promise_result_checked_void(0).is_ok(),
                "near_withdraw failed",
            );
        }

        let min_gas = auth_call.min_gas();
        let mut p = Promise::new(auth_call.contract_id);

        if let Some(state_init) = auth_call.state_init {
            p = p.state_init(state_init, NearToken::ZERO);
        }

        ext_auth_callee::ext_on(p)
            .with_attached_deposit(auth_call.attached_deposit)
            .with_static_gas(min_gas)
            .on_auth(signer_id, auth_call.msg)
    }
