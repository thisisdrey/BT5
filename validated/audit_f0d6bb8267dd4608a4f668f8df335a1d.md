### Title
Per-witness division-then-truncation in vote redistribution causes cumulative rounding loss of voting power/staking rewards on `UnfreezeBalanceV2` - ([File: actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java])

### Summary
When an account calls `UnfreezeBalanceV2Contract`/`UnfreezeBalanceV2` (or the equivalent TVM native contract), and its remaining Tron Power becomes less than its total votes, `updateVote()` re-scales the user's existing votes across every witness it voted for. Instead of computing the proportional reduction once for the total, the code performs the division and truncation independently for each witness entry in a loop, exactly the "divide-before-aggregate" pattern flagged in the referenced report (computing `entriesCount` per NFT instead of once for the whole batch).

### Finding Description

```java

for (Vote vote : accountCapsule.getVotesList()) {

      ((double) vote.getVoteCount() / totalVote * ownedTronPower / TRX_PRECISION);
```

For every witness the account voted for, the new vote count is computed as `vote.getVoteCount() / totalVote * ownedTronPower / TRX_PRECISION`, truncated to a `long` independently per witness. Each of the (up to `MAX_VOTE_NUMBER` = 30) entries incurs its own independent floor-rounding error, instead of the total remaining Tron Power being distributed once and any residual allocated deterministically. The identical logic (and therefore identical bug) is duplicated in the TVM-reachable native-contract path: [2](#0-1) 

This is directly reachable by any unprivileged account: broadcasting a signed `UnfreezeBalanceV2Contract` transaction, or triggering the corresponding TVM `unfreezeBalanceV2` precompile from a smart contract, executes this exact code path.

### Impact Explanation
The truncated votes are simply dropped — they are not carried forward or reallocated to any witness. Since `WitnessCapsule.getVoteCount()`/`getWitnessVote()` (accumulated via the vote list) directly determines an account's share of both the old-algorithm reward (`MortgageService.computeReward` — `voteRate = userVote/totalVote`) and the new VI-based reward, any votes lost to rounding permanently reduce the future staking reward the account is entitled to receive, with no compensating benefit to any other party. Because the error is applied per witness rather than once for the whole set, users who spread votes across many witnesses lose proportionally more (up to `MAX_VOTE_NUMBER - 1` vote units, each vote unit = 1 TRX) than users who vote for a single witness — an unfair, avoidable loss of reward-earning power that scales with the number of counterparties, mirroring the structure of the referenced report.

### Likelihood Explanation
This path triggers whenever an account partially unfreezes its stake (a very common action under the new resource model) while it still has active votes spread over multiple witnesses and its remaining `ownedTronPower` drops below `totalVote * TRX_PRECISION`. No special privileges, timing, or cooperation from other parties is required — a single account's own `UnfreezeBalanceV2` transaction, or an equivalent TVM call, is sufficient to trigger the flawed redistribution loop every time.

### Recommendation
Compute the proportional vote reduction using an integer/`BigInteger` calculation that preserves precision across the whole vote list (e.g. compute the total reduced Tron Power once, then allocate exact shares and give the last entry the remainder), rather than truncating `(double) voteCount / totalVote * ownedTronPower` independently per witness. This mirrors applying multiplication before division across the full batch, as recommended in the referenced report, and eliminates cumulative dust loss for the voter.

### Proof of Concept
1. Account A freezes and votes: 10 TRX for Witness X, 10 TRX for Witness Y, 10 TRX for Witness Z (`totalVote` = 30).
2. Account A calls `UnfreezeBalanceV2` for part of its balance, reducing `ownedTronPower` to, say, 29 TRX equivalent.
3. `updateVote()` computes for each witness independently: `newVoteCount = (long)((double)10/30 * 29)` = `(long) 9.666...` = `9` for each of X, Y, Z.
4. Total new votes recorded = 27, even though the account's true remaining Tron Power corresponds to 29 votes — 2 vote units (2 TRX worth of voting/reward power) are silently lost, and this loss grows with the number of witnesses voted for (see the loop in [3](#0-2) ).
