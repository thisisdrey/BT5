### Title
Heap Buffer Over-Read in ijar ZIP Local File Entry Parser due to Missing EOF Check on Data Descriptor Read - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessLocalFileEntry` in `third_party/ijar/zip.cc`, used by Bazel's `ijar`/`singlejar`-adjacent zip-reading utilities to parse local file headers from a memory-mapped ZIP/JAR file, consistently guards every field read against the end of the mapped buffer via `EnsureRemaining()` — except the trailing data-descriptor read, which is missing that check.

### Finding Description
`ProcessLocalFileEntry` reads the fixed local-header fields, filename, and extra field, each time calling `EnsureRemaining(n, "state")` first to validate that `n` bytes remain in the memory-mapped input before advancing the cursor `p`: [1](#0-0) 

However, at the end of the function, when the general-purpose bit flag indicates a trailing data descriptor (`GENERAL_PURPOSE_BIT_FLAG_COMPRESSED`, bit 3), the code unconditionally reads a 4-byte little-endian value via `get_u4le(p)` and then advances `p` by 8 or 12 more bytes — with no preceding `EnsureRemaining()` call: [2](#0-1) 

This is exactly the same bug class as the ImageMagick BGR decoder issue: a decoder that checks for end-of-input at every other read location but omits the check at one specific point, allowing a crafted/truncated input to cause the cursor to read past the end of the mapped buffer.

`get_u4le` (in `third_party/ijar/common.h`) directly dereferences the pointer with no bounds checking: [3](#0-2) 

Since `p` is a pointer into a memory-mapped file (`MappedInputFile`), an out-of-bounds read here is a heap/mmap buffer over-read, potentially reading adjacent heap or unmapped memory, causing a crash (or leaking adjacent memory contents if further processed/output, though `ijar` does not currently expose this data back to the user directly). If `general_purpose_bit_flag_ & GENERAL_PURPOSE_BIT_FLAG_COMPRESSED` is set on an entry that is the last few bytes of a maliciously truncated ZIP/JAR, the `get_u4le(p)` call and subsequent `p += 4*2` or `p += 4*3` advance can move `p` past the mapped file's end (`mapped_file_.end()`), corresponding directly to "does not check for an end-of-file in every location" from the CVE analog.

### Impact Explanation
This is reachable by any code path that has `ijar`/zip-processing code parse an attacker-supplied ZIP/JAR-formatted file — e.g., during interface-jar generation (`ijar`) or any Bazel-internal consumer of `ZipExtractor`/`InputZipFile` that processes a fetched jar. An attacker who controls the content of a `.jar`/`.zip` file consumed by the build (e.g., an artifact fetched over HTTP, or a jar produced as a build output that is later reprocessed) can craft a local file header with the compressed-data flag set and truncate the file right after the compressed data, causing an out-of-bounds read a few (up to 12) bytes past the end of the mapped region. This is a memory-safety violation (heap/mmap over-read) that can crash the process (denial of service) and, depending on memory layout, may leak adjacent-memory bytes if that data were echoed back — though no such echo path was confirmed in the reviewed code, limiting impact primarily to a crash/DoS via SIGSEGV.

### Likelihood Explanation
Likelihood is moderate: it requires the input ZIP/JAR to be crafted with `GENERAL_PURPOSE_BIT_FLAG_COMPRESSED` set and truncated at a very specific position (immediately after the compressed payload) so that the missing `EnsureRemaining` check is actually exercised at a page boundary/mapping boundary where the over-read matters (going past the actual mmap'd extent rather than merely reading zip-internal garbage that is otherwise harmless). Since `ijar`/singlejar processes archives that could originate from external sources (e.g., http_jar/http_archive-fetched jars, or user-crafted jars in a monorepo build), the attacker-controlled-input precondition is plausible, but exploitability depends on OS mmap page-rounding behavior, which can mask most such over-reads unless the truncation lands exactly on a page boundary.

### Recommendation
Add an `EnsureRemaining()` check (matching the pattern used for every other field in `ProcessLocalFileEntry`) before reading the data descriptor's signature and remaining bytes, e.g., verify at least 4 bytes remain before `get_u4le(p)`, and either 8 or 12 bytes remain (depending on the detected signature) before advancing `p` further. This closes the parity gap between this call site and the rest of the function's consistently-guarded reads.

### Proof of Concept
A `BuildIntegrationTestCase`/unit-test-style reproduction would:
1. Construct a minimal ZIP byte buffer containing exactly one local file header (`LOCAL_FILE_HEADER_SIGNATURE`) with `general_purpose_bit_flag_` bit 3 set (`GENERAL_PURPOSE_BIT_FLAG_COMPRESSED`), a valid filename/extra-field, and a compressed payload.
2. Truncate the buffer immediately after the compressed payload bytes (i.e., 0 bytes remain for the data descriptor) and map only that truncated buffer (mirroring `MappedInputFile`/`InputJar::Open(path, data, length)`).
3. Call `InputZipFile::ProcessNext()` (or the corresponding `ZipExtractor` entry point) on this truncated buffer.
4. Observe that `get_u4le(p)` at line 409 of `third_party/ijar/zip.cc` reads past `zipdata_in_ + length`, which under ASan/valgrind manifests as a heap-buffer-overflow (read) report, unlike all other field reads in the same function which correctly call `EnsureRemaining()` first and return an error instead.

Note: I was not able to fully confirm all downstream consumers of `InputZipFile`/`ZipExtractor` within the indexed codebase (e.g., whether `ijar`'s main binary is reachable directly from untrusted fetched-archive processing in a default Bazel build, versus only from explicit `ijar` invocations on already-trusted inputs) due to index size limits on this large repository. A full Devin session with complete repository access would be needed to trace every caller of `ZipExtractor::ProcessNext` to determine the exact set of attacker-reachable entry points and to write/run the described JUnit/C++ proof-of-concept.

inline u4 get_u4le(const u1 *&p) {
    u4 x = (p[3] << 24) | (p[2] << 16) | (p[1] << 8) | p[0];
    p += 4;
