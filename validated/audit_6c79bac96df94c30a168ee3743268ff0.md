### Title
Named-account deletion and re-creation lets a new NEAR-account owner take over the previous owner's Defuse balance via `PREDECESSOR_ID` authentication - (File: `contracts/defuse/src/contract/accounts/mod.rs`)

### Summary
Defuse authenticates on-chain (non-intent) transfers/withdrawals by trusting `env::predecessor_account_id()` as the `owner_id` whenever "authentication by `PREDECESSOR_ID`" is enabled for that `AccountId`, which it is **by default** for every account. Because Defuse's internal account state (balances, public keys, nonces) is keyed purely by `AccountId` string and is never invalidated, tied to, or synchronized with the actual NEAR on-chain account/keys, a NEAR named account that is deleted and later re-created (by anyone, including an unrelated attacker) inherits full authenticated control over the old owner's leftover Defuse balance the moment `auth_by_predecessor_id` remains enabled (the default) - with no signature check at all.

### Finding Description
`ensure_auth_predecessor_id()` derives the caller identity purely from `env::predecessor_account_id()` and permits it as `owner_id` unless the account has explicitly disabled predecessor-based auth: [1](#0-0) 

This function is used to authorize direct (non-intent, non-signature) fund-moving calls such as `mt_transfer`, `ft_withdraw`, `nft_withdraw`, `mt_withdraw`: [2](#0-1) [3](#0-2) 

The `is_auth_by_predecessor_id_enabled` flag defaults to *enabled* for every account (including newly-observed, not-yet-created ones) unless the owner explicitly disables it: [4](#0-3) [5](#0-4) 

Defuse's account state (`AccountId → {public_keys, nonces, token_balances}`) has no lifecycle binding to the real NEAR account it names - it is created lazily and persists indefinitely, entirely decoupled from whether the underlying NEAR account currently exists, was deleted, or was re-created by a different key holder: [6](#0-5) 

The maintainers themselves acknowledge this exact risk class in the doc-comment for the (Role-gated) `force_enable_auth_by_predecessor_ids` function - but the very same risk exists in the **unprivileged default state** of every account, not only when that admin function is invoked: [7](#0-6) 

**Attack path (analogous to the "follow a deleted profile" bug class - the AccountId "handle" is deleted and reused, but the binding to it is not invalidated):**
1. Alice's Defuse account `owner_id = "alice.near"` holds a token balance (`internal_add_balance`), with `auth_by_predecessor_id` left at its default `enabled` state.
2. Alice deletes the NEAR account `alice.near` on-chain (`delete_account`) — Defuse's internal state for `alice.near` is untouched and still holds her balance.
3. Because `alice.near` is a NEAR account name that becomes available again once deleted, an unrelated attacker (Bob) creates a brand-new NEAR account named `alice.near` with his own keys.
4. Bob calls a Defuse balance-mutating entrypoint (e.g. `mt_transfer`, `ft_withdraw`) directly. `env::predecessor_account_id()` resolves to `alice.near`, `ensure_auth_predecessor_id()` succeeds (default-enabled, no signature required), and Bob is treated as the legitimate owner of Alice's leftover Defuse balance.

### Impact Explanation
This breaks the custody binding between "the `AccountId` that authorized a balance" and "the entity actually controlling that balance" - value can be moved/withdrawn without any valid authorization from the original owner. This matches the Critical impact bucket: "tokens moved, credited or withdrawn without valid authorisation."

### Likelihood Explanation
Requires only: (a) an account that never disabled `auth_by_predecessor_id` (the default for every account) and still has a nonzero Defuse balance, and (b) that its NEAR AccountId is later deleted and re-registered by someone else. Named NEAR account deletion + re-registration is a normal, permissionless, unprivileged sequence of actions (no DAO, Role holder, relayer key, or victim key needed) - the attacker only needs to control the NEAR account creation for the freed name and issue a plain function call, no signed intent, no compromised key from the original owner.

### Recommendation
Do not treat "an account currently exists with this NEAR AccountId" as proof of continuity of ownership. Options:
- Disable `auth_by_predecessor_id` by default (opt-in instead of opt-out), requiring an explicit signed intent/registration step to enable it, so a fresh/re-created NEAR account cannot silently inherit stale Defuse state.
- Bind Defuse's internal account entry to some non-reusable identity data (e.g., require at least one explicitly registered public key before predecessor-based auth is trusted) rather than trusting the bare `AccountId` string indefinitely.
- Provide a mechanism to detect/invalidate stale Defuse account state when the underlying NEAR account is known to have been deleted (e.g., via a garbage-collection/expiry policy analogous to nonce cleanup).

### Proof of Concept
Concept (cannot be executed here, but derivable directly from the code paths cited above):
1. `alice.near` deposits funds into Defuse: `internal_add_balance("alice.near", tokens)` is called, and `is_auth_by_predecessor_id_enabled("alice.near")` remains `true` (default, never toggled).
2. `alice.near` account is deleted on NEAR (`Promise::delete_account`), which is fully independent of Defuse's contract storage - Defuse's `Account` entry for `"alice.near"` (nonces/public_keys/token_balances) persists in `self.accounts`.
3. Attacker registers a new NEAR account named `alice.near` under his own key (permissionless account creation for a freed name).
4. Attacker sends a direct `mt_transfer`/`ft_withdraw` transaction to the Defuse contract; `env::predecessor_account_id()` = `"alice.near"`; `Contract::ensure_auth_predecessor_id()` (contracts/defuse/src/contract/accounts/mod.rs:77-85) returns `"alice.near"` without any signature check, and the withdraw/transfer path (contracts/defuse/src/contract/tokens/nep141/withdraw.rs:53+) executes using the old balance as if the attacker were the original owner.

    /// Returns whether authentication by PREDECESSOR is enabled.
    pub const fn is_auth_by_predecessor_id_enabled(&self) -> bool {
        !self
            .flags
            .contains(AccountFlags::AUTH_BY_PREDECESSOR_ID_DISABLED)
    }

    /// Sets whether authentication by `PREDECESSOR_ID` is enabled.
    /// Returns whether authentication by `PREDECESSOR_ID` was toggled.
    pub fn set_auth_by_predecessor_id(&mut self, enable: bool) -> bool {
        let was_enabled = self.is_auth_by_predecessor_id_enabled();
        let toggle = was_enabled ^ enable;
        if toggle {
            self.flags
                .toggle(AccountFlags::AUTH_BY_PREDECESSOR_ID_DISABLED);
        }

        toggle
    }
