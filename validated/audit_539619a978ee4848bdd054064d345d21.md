### Title
`MetAirdrop._transferReward` minimum-lock clamp extends esMET lock far beyond the intended `updatedAt + lockPeriod` end - (File: contracts/MetAirdrop.sol)

### Summary
`MetAirdrop._transferReward` intends for claimed MET to be locked in esMET only until `updatedAt + lockPeriod` (the end of the current distribution's lock window). However, the remaining lock period is clamped to `ESMET.MINIMUM_LOCK_PERIOD() + 1`. A user who claims shortly before the intended unlock end has their reward locked for a full `MINIMUM_LOCK_PERIOD` instead of the few remaining seconds/minutes — the same "lock extended beyond intended period" bug class as the CVG `increaseLockTime` finding.

### Finding Description
In `contracts/MetAirdrop.sol`:

```solidity
uint256 _end = updatedAt + lockPeriod;              // intended unlock time

if (_end < block.timestamp) {
    MET.safeTransfer(to_, amount_);                  // after end: no lock at all
    return;
}

uint256 _min = ESMET.MINIMUM_LOCK_PERIOD() + 1;
uint256 _max = ESMET.MAXIMUM_LOCK_PERIOD();

uint256 _remainLockPeriod = Math.min(Math.max(_end - block.timestamp, _min), _max);
ESMET.lockFor(to_, amount_, _remainLockPeriod);
``` [1](#0-0) 

The NatSpec states "The `lockPeriod` starts from the current merkle root update (i.e. `updatedAt`)", so the intended `unlockTime` is `updatedAt + lockPeriod`. Because esMET's `lockFor` sets `unlockTime = block.timestamp + lockPeriod_`, the contract correctly computes the remaining duration `_end - block.timestamp` — but then clamps it with `Math.max(..., _min)`. Whenever the true remaining time is below `MINIMUM_LOCK_PERIOD + 1`, the user's MET is locked for `MINIMUM_LOCK_PERIOD + 1` (a fresh, full minimum lock), overshooting the intended end by up to nearly the entire minimum period.

There is a cliff: claim 1 second before `_end` → locked for `MINIMUM_LOCK_PERIOD + 1`; claim 1 second after `_end` → tokens arrive fully unlocked.

### Impact Explanation
Users' claimed MET is temporarily frozen in esMET for materially longer than the documented lock schedule (`updatedAt + lockPeriod`). A claim made near the end of the window converts a residual lock of seconds into a lock of `MINIMUM_LOCK_PERIOD` (which on esMET is on the order of weeks), delaying access to the airdropped funds well beyond user expectation — temporary freezing of user funds, matching the CVG report's "tokens locked an extra cycle/week" impact.

### Likelihood Explanation
`RecurringAirdrop.claim` is a public, unprivileged, `nonReentrant` entry point (`contracts/utils/RecurringAirdrop.sol:52`) and `updateMerkleRoot` refreshes `updatedAt` each distribution round (`contracts/utils/RecurringAirdrop.sol:81-90`). Any claim submitted in the last `MINIMUM_LOCK_PERIOD` before `updatedAt + lockPeriod` triggers the extension — a wide window, hit deterministically by timing, not by edge-case state. No modifier, cap, or pause flag prevents it.

### Recommendation
Instead of clamping the remaining duration up to `MINIMUM_LOCK_PERIOD + 1`, short-circuit to a plain transfer when the remaining time is below the esMET minimum, e.g.:

```solidity
uint256 _remaining = _end - block.timestamp;
if (_remaining <= ESMET.MINIMUM_LOCK_PERIOD()) {
    MET.safeTransfer(to_, amount_);
    return;
}
ESMET.lockFor(to_, amount_, Math.min(_remaining, ESMET.MAXIMUM_LOCK_PERIOD()));
```

This keeps the invariant "claimed MET is never locked past `updatedAt + lockPeriod`".

### Proof of Concept
Foundry fork-style test against `MetAirdrop`:

```solidity
function test_claimNearEnd_extendsLockBeyondIntended() public {
    // governor updates merkle root at t0; lockPeriod = 7 days
    // esMET MINIMUM_LOCK_PERIOD = e.g. 30 days (external constant)
    vm.prank(governor);
    airdrop.updateMerkleRoot(root, proofsHash);      // updatedAt = t0

    uint256 end = t0 + airdrop.lockPeriod();
    vm.warp(end - 1 hours);                          // claim 1h before intended end

    vm.prank(alice);
    airdrop.claim(amount, proof);

    // esMET position unlockTime = (end - 1h) + MINIMUM_LOCK_PERIOD + 1
    // instead of `end` -> locked ~MINIMUM_LOCK_PERIOD longer than intended
    IESMET.LockPosition memory pos = esMET.positions(alicePositionId);
    assertGt(pos.unlockTime, end);                   // overshoots intended unlock by ~MIN - 1h
}
```

Invariant broken: reward-lock duration consistency — `unlockTime` must equal `updatedAt + lockPeriod`; the `Math.max(_end - block.timestamp, _min)` clamp violates it for all claims in the final `MINIMUM_LOCK_PERIOD` of the window.

    function _transferReward(address to_, uint256 amount_) internal override {
