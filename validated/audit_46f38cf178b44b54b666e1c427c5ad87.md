### Title
Unchecked multiplication `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` overflows on attacker-controlled `estimated_len` - (File: stackslib/src/net/api/postfeerate.rs)

### Summary
The `/v2/fees/transaction` RPC endpoint accepts an attacker-supplied `estimated_len: Option<u64>` field in the JSON body, which is floored (not capped) against `payload_data.len()` and then multiplied by a constant with plain `u64` multiplication to compute `minimum_fee`. Because there is no upper bound on `estimated_len` and the multiplication is not a checked/saturating operation, a value close to `u64::MAX` causes the multiplication to overflow.

### Finding Description
In `try_parse_request` [1](#0-0)  the server computes `estimated_len = max(body.estimated_len.unwrap_or(0), payload_data.len() as u64)`. This only enforces a floor, never a ceiling, so an attacker can set `estimated_len` to any `u64` value, e.g. `u64::MAX`, since `body.estimated_len` is deserialized directly from JSON with no range validation.

That value is later used in `estimate_tx_fee_from_cost_and_length`: `let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;` [2](#0-1) . This is a plain (unchecked) `u64` multiplication. In a debug build, `u64::MAX * MINIMUM_TX_FEE_RATE_PER_BYTE` panics with "attempt to multiply with overflow"; in a release build (which uses wrapping arithmetic by default), the result silently wraps to an arbitrary, possibly very small, value, which is then compared against each `estimate.fee` and can end up understating the true minimum fee that should be enforced for `estimated_len` bytes at `MINIMUM_TX_FEE_RATE_PER_BYTE`.

The `try_parse_request` path is reached from an unauthenticated JSON POST to `/v2/fees/transaction`, gated only by content-length (`0 < content_len < MAX_PAYLOAD_LEN`) and JSON content-type checks [3](#0-2)  — none of which constrain the numeric value of `estimated_len`. No RPC secret or peer/slot ownership is required to hit this endpoint.

### Impact Explanation
- Debug builds: a single unauthenticated HTTP POST triggers an arithmetic-overflow panic in the RPC request-handling code path, crashing/aborting the handling thread (denial of service) with one request, repeatable at will. This matches "remote crash/unauthenticated DoS from few messages."
- Release builds: the multiplication wraps silently, so the returned `RPCFeeEstimateResponse.estimations[].fee` values no longer satisfy `fee == max(scalar_fee, estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE)`, i.e., the node returns fee-rate data that understates the true minimum required fee for the claimed `estimated_len`—a client/wallet trusting this response could construct/broadcast a transaction with too low a fee for its actual size, which the mempool separately enforces via `MINIMUM_TX_FEE_RATE_PER_BYTE`-based checks elsewhere (`will_admit_mempool_tx`/blocks.rs), likely just failing to be admitted rather than confirming — so the practical damage is inconsistent/incorrect wallet guidance rather than accepted underpayment, but it does break the invariant the endpoint is meant to guarantee.

### Likelihood Explanation
No preconditions beyond network reachability to the node's RPC port; no RPC secret, peer key, or StackerDB slot needed. Attacker cost is a single crafted POST with a valid hex `transaction_payload` (any minimal valid payload) and `"estimated_len": 18446744073709551615` (u64::MAX) or another value large enough that `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` exceeds `u64::MAX`. Fully remote, unauthenticated, and repeatable on every request.

### Recommendation
Replace the plain multiplication with `estimated_len.checked_mul(MINIMUM_TX_FEE_RATE_PER_BYTE)` (or `saturating_mul`) in `estimate_tx_fee_from_cost_and_length`, returning an `HttpBadRequest` error on overflow, and additionally cap `estimated_len` in `try_parse_request` to a sane maximum (e.g., `MAX_PAYLOAD_LEN` or the maximum allowed transaction size) instead of only flooring it against `payload_data.len()`.

### Proof of Concept
Rust net test (in `stackslib/src/net/api/tests/postfeerate.rs` style):
1. Construct a `FeeRateEstimateRequestBody` with a minimal valid hex-encoded `TransactionPayload` and `estimated_len: Some(u64::MAX)`.
2. Serialize it and POST to `/v2/fees/transaction` via the test harness that drives `RPCPostFeeRateRequestHandler::try_parse_request` and `try_handle_request`.
3. In a debug build, assert the call panics with "attempt to multiply with overflow" at `postfeerate.rs:112`, or, once fixed, assert the handler returns an `HttpBadRequest` (400) instead of a 200 with a wrapped/incorrect `fee` value.
4. Alternatively, directly unit-test `RPCPostFeeRateRequestHandler::estimate_tx_fee_from_cost_and_length` with `estimated_len = u64::MAX` and assert it returns an error rather than silently wrapping.
