## Analog Found

Verbose backend exception details are leaked to unauthenticated remote callers via the StackerDB chunk-write RPC endpoint, mirroring the Nova bug class where an unhandled/uncaught internal exception's details are echoed into the HTTP fault response instead of being sanitized.

### Title
Remote StackerDB Chunk-Write Endpoint Leaks Internal Exception Details in HTTP 500 Response - (File: `stackslib/src/net/api/poststackerdbchunk.rs`)

### Summary
The `POST /v2/stackerdb/...` chunk-write handler catches DB/internal errors from `try_replace_chunk` and `get_slot_metadata`, and for any error not matching the small allow-listed set of client-facing codes, it serializes the raw `Debug` (`{:?}`) form of the internal `NetError` directly into the HTTP 500 response body sent back to the requester.

### Finding Description
`RPCPostStackerDBChunkRequestHandler::try_handle_request` classifies `try_replace_chunk` failures into known `StackerDBErrorCodes` (`StaleChunk`, `NoSuchSlot`, `BadSlotSigner`/`VerifyingError`, `StackerDBChunkTooBig`, `TooManySlotWrites`). Any other error variant falls into the catch-all branch, which builds an `HttpServerError` whose text is `format!("Failed to store StackerDB chunk for {}: {:?}", &contract_identifier, &e)` [1](#0-0)  and this payload is returned verbatim as the HTTP body via `HttpErrorResponse::payload()` / `StacksHttpResponse::new_error` [2](#0-1) [3](#0-2) . The same pattern repeats for the `get_slot_metadata` lookup failure path [4](#0-3) .

The underlying `NetError` this catch-all can wrap includes database errors (`crate::util_lib::db::Error`, i.e. `rusqlite`/SQLite errors) and I/O errors, both imported into `stackslib/src/net/mod.rs`'s `Error` enum [5](#0-4) [6](#0-5) . `Debug`-formatted SQLite/IO errors routinely embed filesystem paths, SQL fragments, and OS error strings — exactly the class of "underlying environment" detail the Nova advisory (CVE-2019-14433) flags as leaking through fault responses to authenticated-but-otherwise-unprivileged callers.

This endpoint requires no special authorization beyond having a syntactically valid request; any remote peer that can reach the node's RPC interface can submit a chunk-write request and observe the resulting error text when a DB/internal fault occurs.

### Impact Explanation
This is an information-disclosure issue (CWE-200/CWE-209): a remote, unauthenticated caller can potentially learn internal filesystem paths, SQLite schema/error text, or other implementation details of the node's stacker-DB storage backend whenever an unclassified DB or internal error occurs while processing their request. It does not on its own grant write access or crash the node, so it is best characterized as an information leak rather than a Critical/High "state corruption" bug per the scan's impact tiers, but it directly matches the reported bug class (fault-response detail leakage).

### Likelihood Explanation
Triggering the specific catch-all path requires an underlying DB/internal fault (e.g., disk-level SQLite errors, corrupted stacker-db state, or other unexpected `NetError` variants) that isn't part of the already-classified error codes. This can happen incidentally in production (disk pressure, DB corruption, concurrent-access races) and the response is fully attacker-observable without any privilege, since the handler is reached by any request that parses successfully.

### Recommendation
For the catch-all branch in `try_handle_request` (both the `try_replace_chunk` failure and the `get_slot_metadata` failure paths), log the full `Debug` error server-side (already done via `error!`) but return a generic, sanitized message to the client (e.g. `"Internal server error while storing StackerDB chunk"`) instead of interpolating `{:?}` of the raw error into the HTTP response body.

### Proof of Concept
1. Cause `try_replace_chunk` (or the subsequent `get_slot_metadata` call) in `stackslib/src/net/stackerdb/db.rs` to return a `NetError` variant outside the explicitly-handled set (e.g. a `DBError` from a transient SQLite fault).
2. Observe that `poststackerdbchunk.rs`'s catch-all arm returns an HTTP 500 whose body is `"Failed to store StackerDB chunk for {contract}: {:?}"` with the full internal error debug string, visible to the requester over the network.

    /// Make a new HTTP error response with additional headers, in reaction to a request
    pub fn new_error_with_headers(
        preamble: &HttpRequestPreamble,
        error: &dyn HttpErrorResponse,
        extra_headers: Vec<(String, String)>,
    ) -> StacksHttpResponse {
        let payload = error.payload();
        let content_type = match &payload {
            HttpResponsePayload::Empty => HttpContentType::Bytes,
            HttpResponsePayload::Bytes(..) => HttpContentType::Bytes,
            HttpResponsePayload::Text(..) => HttpContentType::Text,
            HttpResponsePayload::JSON(..) => HttpContentType::JSON,
        };
        let content_length = payload.try_content_length();
        let mut resp_preamble = HttpResponsePreamble::from_http_request_preamble(
            preamble,
            error.code(),
            http_reason(error.code()),
            content_length,
            content_type,
        );
        for (key, value) in extra_headers {
            resp_preamble.add_header(key, value);
        }
        StacksHttpResponse::new(resp_preamble, payload)
    }
