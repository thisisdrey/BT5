## Title
Active permission with `AccountPermissionUpdateContract` bit enabled allows a lower-tier active key to unilaterally overwrite Owner/Witness/Active permissions, resulting in permanent, unrevocable account takeover - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The Sherlock finding describes a signature/privilege that, once granted, cannot be revoked, letting a compromised or malicious signer permanently keep (or abuse) authority the grantor never intended to be permanent. The same structural weakness exists in java-tron's multisig "active permission" model: an active permission's `operations` bitmap is allowed to include the bit for `AccountPermissionUpdateContract` itself, meaning a lower-privilege active key (or its threshold group) can execute `AccountPermissionUpdateContract` and rewrite the account's Owner, Witness, and Active permissions — including removing the legitimate owner key entirely. Once that happens, there is no protocol mechanism to revoke or roll back the takeover, since the only entity normally authorized to do so (the Owner permission) has just been replaced by the attacker.

### Finding Description
Permission validation for any transaction, including `AccountPermissionUpdateContract` itself, is enforced generically via `contract.getPermissionId()` plus the target permission's `operations` bitmap, not via any special-case rule requiring Owner-level (`permissionId == 0`) authority for permission changes: [1](#0-0) 

The same generic bitmap check is used in the query paths (`TransactionUtil.getTransactionSignWeight`, `Wallet.getTransactionApprovedList`): [2](#0-1) 

When an `AccountPermissionUpdateContract` is validated, `AccountPermissionUpdateActuator.checkPermission` verifies that every bit set in a proposed Active permission's `operations` bitmap is merely a member of `dynamicStore.getAvailableContractType()` — it does **not** exclude the `AccountPermissionUpdateContract` contract type from being grantable to an Active permission: [3](#0-2) 

The account's regression test suite confirms `AccountPermissionUpdateContract`'s bit is present in `getAvailableContractType()` (only `UpdateBrokerageContract` is excluded), while it is excluded only from the *default* Active-permission operations (`getActiveDefaultOperations()`), which an owner can still override when explicitly constructing a custom Active permission: [4](#0-3) [5](#0-4) 

Consequently, if an owner (intentionally, by misconfiguration, or under social-engineering) creates an Active permission that includes the `AccountPermissionUpdateContract` bit and grants it to an automation/API key, that key — once it reaches the Active permission's threshold — can broadcast an `AccountPermissionUpdateContract` transaction that fully replaces the account's Owner permission, Witness permission, and all Active permissions in `AccountCapsule.updatePermissions`, executed unconditionally by the actuator: [6](#0-5) 

This is precisely the "signature/privilege granted without any way to revoke" bug class from the report: the Active key was meant to be a lesser-privileged, revocable delegate, but the protocol provides no independent, higher-privilege gate that prevents that delegate from rewriting (and thereby permanently seizing) the very Owner authority that would normally be used to revoke it.

### Impact Explanation
Once an attacker (holder of a compromised/abused Active key with the `AccountPermissionUpdateContract` bit enabled) broadcasts a single `AccountPermissionUpdateContract` transaction, they can set a new Owner permission containing only their own key, remove all other Active/Witness keys, and thereby achieve total, unauthorized, and irreversible control of the victim account and all its TRX/TRC-10/TRC-20 balances and resources. Because the legitimate Owner key is deleted from the account's permission structure, there is no on-chain way for the original owner to revoke the attacker's access — this is a permanent, unauthorized account takeover / loss-of-funds scenario.

### Likelihood Explanation
Exploitation requires that some account owner has configured an Active permission whose `operations` bitmap includes the `AccountPermissionUpdateContract` bit and handed that key to a third party or automated signer (e.g., an API wallet, exchange hot-wallet automation, or delegated bot) — a configuration the protocol currently permits with no warning or restriction. This mirrors the report's own threat model (API/automation wallets holding standing privilege) and is entirely reachable by an ordinary, unprivileged signer possessing only the Active key; no special node or validator privilege is required. The severity is High because the resulting compromise is total and unrecoverable, even though it depends on this specific permission configuration existing.

### Recommendation
Disallow the `AccountPermissionUpdateContract` contract type from ever being included in an Active permission's `operations` bitmap (i.e., unconditionally require `permissionId == 0` / Owner-only authority to execute `AccountPermissionUpdateContract`), regardless of what is set in `DynamicPropertiesStore.getAvailableContractType()`. This should be enforced both in `AccountPermissionUpdateActuator.checkPermission` (reject any Active permission whose operations bit for `AccountPermissionUpdateContract` is set) and defensively in the generic signature/permission validation path (`TransactionCapsule`/`TransactionUtil`) so that even a manually-crafted transaction with `permissionId != 0` targeting `AccountPermissionUpdateContract` is rejected outright.

### Proof of Concept
1. Account `A` is created with an Owner permission `O` (key `k0`) and an Active permission `P1` (key `k1`, threshold 1) whose `operations` bitmap has the bit corresponding to `ContractType.AccountPermissionUpdateContract` set (this passes validation per `AccountPermissionUpdateActuator.checkPermission`, since that bit is present in `getAvailableContractType()`).
2. Attacker obtains/compromises `k1` (analogous to the report's compromised API wallet).
3. Attacker crafts an `AccountPermissionUpdateContract` transaction for account `A`, setting `permissionId = <P1's id>` (not `0`), with a new Owner permission containing only an attacker-controlled key, and signs it with `k1`.
4. `TransactionCapsule.validateSignature` looks up permission via `contract.getPermissionId()`, resolves to `P1`, calls `checkPermission` which passes because bit for `AccountPermissionUpdateContract` is set in `P1.operations`, then `checkWeight` confirms `k1`'s signature meets `P1`'s threshold.
5. `AccountPermissionUpdateActuator.execute` unconditionally overwrites `A`'s Owner/Witness/Active permissions with the attacker's chosen values via `account.updatePermissions(...)`.
6. Account `A` is now fully controlled by the attacker; the original owner key `k0` no longer has any permission entry and cannot revoke or recover the account.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
