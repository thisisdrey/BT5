### Title
Optimistic StackerDB inventory ACK advertises a slot version before it is actually committed - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches the outgoing `StackerDBChunkInv` reply's `slot_versions` array to reflect the *pushed* chunk's version as soon as the chunk passes `validate_received_chunk`, and sends that reply back to the peer — before the chunk has actually been durably committed to the StackerDB replica. This creates a "served vs. committed" mismatch analogous to the reported Solidity bug class, where a state-enabling condition is updated based on an intermediate/uncommitted value rather than the authoritative stored state.

### Finding Description
`make_StackerDBChunksInv_or_Nack` builds the reply payload from the *actually committed* on-disk state via `self.stackerdbs.get_slot_versions(contract_id)`: [1](#0-0) 

Immediately afterward, in the `StacksMessageType::StackerDBChunkInv` branch of `handle_unsolicited_StackerDBPushChunk`, the code re-validates the pushed chunk with `validate_received_chunk` (a signature/size/version sanity check that does not touch the database) and then unconditionally overwrites the just-fetched, DB-backed `slot_version` entry with the *pushed, not-yet-stored* chunk's version: [2](#0-1) 

The actual persistence of the chunk (`StackerDBs::try_replace_chunk`, which enforces `slot_version > current_version`, `slot_version <= max_writes`, chunk-size caps, and signer verification) happens later, asynchronously, when the message is handed off to the relayer (`Ok((false, true))` return path): [3](#0-2) [4](#0-3) 

Because the ACK/`StackerDBChunkInv` reply is signed and sent back to the peer *before* `try_replace_chunk` runs, the locally-advertised inventory ("served" state) can diverge from what is actually persisted ("committed" state) in at least these ways:
- If the relayer's later `try_replace_chunk` call fails for any reason not checked by `validate_received_chunk` (e.g., a race with another concurrently-processed higher-version chunk, a DB error, or transaction failure), the peer has already been told the new version is present, but `get_slot_versions` on subsequent reads will return the old value.
- `validate_received_chunk`'s staleness check (`data.slot_version < *expected_version`) uses `<`, while `try_replace_chunk`'s staleness check uses `<=` (equal-to-current is stale). A chunk whose version equals the currently stored version is treated as acceptable by the optimistic ACK patch but will be rejected as `StaleChunk` when actually processed by the relayer, so the peer is told a version is available that never gets committed.

### Impact Explanation
This lets a remote, unauthenticated (any P2P-connected) peer cause the local node to advertise/serve StackerDB inventory state (`StackerDBChunkInv`) that does not match the durable, authoritative state of the StackerDB replica. Downstream StackerDB sync logic in other nodes relies on this inventory to decide what to fetch; serving a version that isn't actually committed can cause sync partners to believe a chunk is available when it is not, leading to wasted fetch rounds or sync state confusion — a "false inventory" condition analogous to steering peers based on non-canonical/uncommitted state.

### Likelihood Explanation
Reaching this code path only requires sending an unsolicited `StackerDBPushChunk` message over an established P2P connection with a validly-signed chunk for a slot the node replicates — no elevated privilege or secret key is required. The race/inconsistency window is narrower and less severe than a full auth bypass, which is why this is best characterized as a medium-likelihood correctness/DoS-adjacent issue rather than a critical one.

### Recommendation
Do not patch/serve the `StackerDBChunkInv.slot_versions` entry until after `StackerDBs::try_replace_chunk` (or equivalent) has actually succeeded, or re-fetch `get_slot_versions` from the DB after the relayer processes the chunk before sending any ACK. Additionally, unify the staleness comparison operator (`<` vs `<=`) between `validate_received_chunk` and `try_replace_chunk` so the "chunk is acceptable" and "chunk is committable" conditions agree exactly.

### Proof of Concept
1. Establish a P2P connection to a target node that replicates a StackerDB contract with slot `S` currently at version `V`.
2. Send an unsolicited `StackerDBPushChunk` for slot `S` with `slot_version = V` (equal to, not greater than, the current version), properly signed by the slot's owner, with a matching `rc_consensus_hash`.
3. `validate_received_chunk` passes (`V < V` is false only relative to the pushed inventory’s own snapshot fetched moments earlier — because it's exactly the same value already recorded, the `<` check permits it) and `make_StackerDBChunksInv_or_Nack`/the `StackerDBChunkInv` branch patches and sends a `StackerDBChunkInv` reply that reflects `slot_version = V` as if freshly accepted.
4. The relayer later invokes `try_replace_chunk`, which uses `<=` and rejects the chunk as `StaleChunk`, so nothing is actually written — yet the peer already received an ACK/inventory update implying the chunk was accepted. [5](#0-4) [6](#0-5)

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
