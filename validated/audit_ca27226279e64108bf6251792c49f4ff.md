### Title
Dynamic Energy Factor increase is not compounded for missed cycles, causing incorrect (under-priced) contract call energy cost - ([File: chainbase/src/main/java/org/tron/core/capsule/ContractStateCapsule.java])

### Summary
`ContractStateCapsule.catchUpToCycle` implements the "dynamic energy" congestion-pricing mechanism for TVM contract calls. When a contract's energy usage exceeds a configured threshold, its per-cycle energy price factor should rise; when usage is below threshold, the factor should decay back down. The decay path is correctly compounded across however many maintenance cycles have elapsed (`Math.pow(decreasePercent, cycleCount)`), but the increase path applies only a single, flat percentage bump regardless of how many cycles have actually passed since the last update — exactly analogous to the reported Ajna `Pool.sol` bug where the interest-rate update is only applied once per action instead of being scaled by the number of elapsed intervals.

### Finding Description
`catchUpToCycle` is intended to bring a contract's `ContractState` (energy usage factor) up to date with the current cycle number: [1](#0-0) 

- `lastCycle` is the cycle recorded the last time this contract was touched.
- If `getEnergyUsage() > threshold`, the code increments `lastCycle` by exactly `1` and applies `increasePercent` **once**, regardless of how many cycles have actually elapsed since `lastCycle`.
- Only after that single increase step does it compute `cycleCount = newCycle - lastCycle` and apply the decrease with proper compounding via `pow(decreasePercent, cycleCount, useStrictMath)`: [2](#0-1) 

This means:
- The decrease branch correctly scales for the number of missed cycles (multiple 6‑hour maintenance periods worth of decay applied in one shot, matching Ajna's suggested fix of "calculate how many periods passed and power all scaling values").
- The increase branch does **not**: no matter how many cycles have passed since the contract was last invoked while its usage stayed above threshold, only one step of `increasePercent` is ever applied before falling through to decay logic for the remaining `cycleCount` cycles.

Root cause: `lastCycle += 1` combined with a single non-loop increase application, versus `pow(..., cycleCount, ...)` in the decrease branch — the exact same class of bug as the reported Ajna issue: state updates gated on a per-cycle threshold are not scaled/compounded to the true number of elapsed periods.

Reachability: `ContractStateCapsule` and its `catchUpToCycle` method back the TVM "dynamic energy" feature (`DynamicEnergyThreshold`, `DynamicEnergyIncreaseFactor`, `DynamicEnergyMaxFactor` in `DynamicPropertiesStore`), which is applied during contract execution to any TVM contract call an unprivileged transaction broadcaster can trigger. `Program.java` (the TVM bytecode interpreter's context, referenced in the codebase) imports `ContractStateCapsule`, i.e. this logic sits directly in the execution path of every contract invocation, reachable via any signed transaction calling a smart contract.

### Impact Explanation
Under-compounding the increase means that contracts which are called only sporadically (e.g., once per several maintenance cycles) but which consistently exceed the energy-usage threshold each time they are invoked will have their dynamic energy factor rise far more slowly than the protocol intends. Since the dynamic energy factor is used to scale the effective energy cost of calling a contract (an anti-congestion / anti-DoS pricing mechanism), an attacker or heavy contract user can exploit sparse-but-heavy invocation patterns to keep paying artificially low energy prices compared to what the intended (compounded) formula would charge, while the decrease side is a correctly compounded discount. This produces systematically incorrect energy accounting/pricing for the affected contract, undermining the fee mechanism that is meant to price network resource congestion — a mispriced/underpriced resource-metering condition analogous to the "incorrect revenue" impact in the original report.

### Likelihood Explanation
This requires no privileged access: any account can deploy a contract and call it in a pattern that keeps `energyUsage` above `dynamicEnergyThreshold` while spacing calls out over multiple maintenance cycles (which occur automatically roughly every ~6 hours per `MAINTENANCE_SKIP_SLOTS`/`getMaintenanceTimeInterval`). The dynamic-energy feature itself must be enabled (config-gated via `allowDynamicEnergy`/`VMConfig`), which is the case on mainnet for contracts subject to congestion pricing. The trigger condition (calling the same contract sparsely while exceeding the threshold) is straightforward and requires only ordinary transaction broadcasting.

### Recommendation
Compound the increase step over the actual number of missed cycles, symmetric to the decrease branch, e.g. compute the number of cycles for which `energyUsage > threshold` held (or otherwise the elapsed cycle count) and raise the factor via `pow(increasePercent, cycleCount)` (bounded by `maxFactor`) rather than applying a single flat increment before falling into the decay path.

### Proof of Concept
1. Enable dynamic energy (`allowDynamicEnergy`, `DynamicEnergyThreshold`, `DynamicEnergyIncreaseFactor` set to non-trivial values) as would occur once the corresponding proposal is active.
2. Deploy a contract and call it in cycle N, consuming energy above `DynamicEnergyThreshold`, resulting in `ContractState.updateCycle = N (or N+1)` and an initial `energyFactor` bump.
3. Do not call the contract again until cycle `N + k` (k > 1), still with usage above threshold when finally invoked.
4. Observe via `catchUpToCycle` that only a single `increasePercent` step is applied (`lastCycle += 1` once) — not `k` compounded increase steps — before the remaining `cycleCount = newCycle - lastCycle` is applied as compounded *decrease*. Compare against the expected behavior of compounding the increase by `k` cycles, as unit-testable directly in `ContractStateCapsuleTest.java` (referenced in the codebase) by asserting the resulting `energyFactor` against `pow(increasePercent, k)` versus the actual single-step result.   public boolean catchUpToCycle(
      long newCycle, long threshold, long increaseFactor, long maxFactor,
      boolean useStrictMath, boolean disableMath
  ) {
    long lastCycle = getUpdateCycle();

    // Updated within this cycle
    if (lastCycle == newCycle) {
      return false;
    }

    // Guard judge and uninitialized state
    if (lastCycle > newCycle || lastCycle == 0L) {
      reset(newCycle);
      return true;
    }

    final long precisionFactor = DYNAMIC_ENERGY_FACTOR_DECIMAL;

    // Increase the last cycle
    // fix the threshold = 0 caused incompatible
    if (getEnergyUsage() > threshold) {
      lastCycle += 1;
      double increasePercent = 1 + (double) increaseFactor / precisionFactor;
      this.contractState = ContractState.newBuilder()
          .setUpdateCycle(lastCycle)
          .setEnergyFactor(min(
              maxFactor,
              (long) ((getEnergyFactor() + precisionFactor) * increasePercent) - precisionFactor,
              disableMath))
          .build();
    }

    // No need to decrease
    long cycleCount = newCycle - lastCycle;
    if (cycleCount <= 0) {
      return true;
    }

    // Calc the decrease percent (decrease factor [75% ~ 100%])
    double decreasePercent = pow(
        1 - (double) increaseFactor / DYNAMIC_ENERGY_DECREASE_DIVISION / precisionFactor,
        cycleCount, useStrictMath
    );

    // Decrease to this cycle
    // (If long time no tx and factor is 100%,
    //  we just calc it again and result factor is still 100%.
    //  That means we merge this special case to normal cases)
    this.contractState = ContractState.newBuilder()
        .setUpdateCycle(newCycle)
        .setEnergyFactor(max(
            0,
            (long) ((getEnergyFactor() + precisionFactor) * decreasePercent) - precisionFactor,
            disableMath))
        .build();

    return true;
  }
