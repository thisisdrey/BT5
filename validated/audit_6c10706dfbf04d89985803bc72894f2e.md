Audit Report

## Title
Teleported funds forwarded by `pallet-accumulate-and-forward` can become permanently trapped at the destination with no on-chain recovery path - (File: `polkadot/xcm/xcm-builder/src/forwarder.rs`)

## Summary
`TeleportForwarderForAccountId32::forward` treats local `Outcome::Complete` from `XcmExecutor::prepare_and_execute` as final confirmation of a successful transfer, committing the local burn and allowing `pallet_accumulate_and_forward::Pallet::on_idle` to emit `Event::ForwardSucceeded` and permanently reduce `total_issuance`, even though the value-moving `DepositAsset` instruction runs asynchronously on the destination chain and is never verified or reconciled by this code. If that destination-side leg fails (unfunded/paused staging account, barrier rejection, weight exceeded), the burned value is unrecoverable since no `AssetTrap`/claim mechanism is wired into this flow.

## Finding Description
`Pallet::on_idle` reads `available_funds` from the accumulation account and calls `T::Forwarder::forward`, firing `Event::ForwardSucceeded` on `Ok(())` [1](#0-0) . The crate docs state explicitly that this is a burn/mint bridge rather than an atomic transfer: "Accumulated funds are burnt upon forwarding (reducing `total_issuance` here) and the same funds are minted at the destination when the sent message is received" [2](#0-1) .

`TeleportForwarderForAccountId32::forward` builds a two-hop XCM program (`WithdrawAsset` locally, then `InitiateTransfer`/`Teleport` to `dest` with a `remote_xcm` of `DepositAsset` executed at the destination), but the `with_transaction` block only wraps the local `prepare_and_execute` call — its `Outcome::Complete` branch commits and returns `Ok(())` without any check of the remote leg's outcome [3](#0-2) . The adapter's own doc comment acknowledges this: "Once the local executor reports success, the message is queued and any destination-side rejection results in trapped assets at the destination with no automatic recovery path" [4](#0-3) .

The existing test suite only exercises the local-failure/rollback path (router returning `SendError::NotApplicable` before delivery), confirmed by `forward_rolls_back_balance_and_issuance_on_xcm_failure`, and the mock config sets `type AssetTrap = ()`, meaning no trap/claim recovery is even modeled in the test environment, let alone wired into production runtime configs referencing this adapter [5](#0-4) [6](#0-5) .

## Impact Explanation
This falls under "permanent user-fund or bridge-state lock" per the impact gate: value is irrevocably burned from `total_issuance` on the source chain based solely on local execution success, while the corresponding destination-side credit may never land if the remote `DepositAsset` fails, and no code path in this pallet retries or reconciles that specific burned tranche — the next `on_idle` cycle only forwards newly accumulated balance, not the lost amount.

## Likelihood Explanation
This is a routine operational/environmental failure mode — an unfunded or paused destination staging account, remote weight-limit exceeded, or barrier misconfiguration — requiring no privileged or malicious actor, no attacker input at all beyond normal cross-chain message delivery conditions inherent to XCM teleports.

## Recommendation
Do not finalize (burn + emit `ForwardSucceeded`) based on local `Outcome::Complete` alone. Either defer settlement until a receipt/callback (e.g. `ReportError`/XCM query-response) confirms the remote `DepositAsset` succeeded, or wire in and document a concrete `AssetTrap`/`claim_assets` recovery path for the destination staging location, and update `Forwarder::forward`'s contract to make clear that local success does not guarantee remote settlement.

## Proof of Concept
Extend the existing test suite (e.g. `polkadot/xcm/xcm-builder/src/tests/forwarder.rs` or the integration helper `cumulus/parachains/integration-tests/emulated/common/src/dap_helpers.rs`) with a scenario where the local `prepare_and_execute` call returns `Outcome::Complete` (so `forward` returns `Ok(())`, `total_issuance` is reduced, and `ForwardSucceeded` is emitted) but the destination chain's `DepositAsset` subsequently fails — e.g., by under-funding the destination staging account below ED before the message is processed. Assert the funds are unrecoverable on both chains, unlike the currently-tested router-failure case in `forward_rolls_back_balance_and_issuance_on_xcm_failure` [6](#0-5) .

/// Verify that when the XCM router fails (simulating a mid-program failure after `WithdrawAsset`
/// has debited the source account), `forward` rolls back all storage changes via
/// `with_transaction`. Both the source balance and total issuance must remain unchanged.
#[test]
fn forward_rolls_back_balance_and_issuance_on_xcm_failure() {
	let source: AccountId = AccountId32::from([1u8; 32]);
	let initial_balance = 1_000u128;

	new_test_ext(source.clone(), initial_balance).execute_with(|| {
		let initial_issuance = Balances::total_issuance();

		ROUTER_SHOULD_FAIL.with(|f| f.set(true));
		let result = TeleportForwarderForAccountId32::<
			TestXcmConfig,
			AssetHubLocation,
			HereLocation,
			AccumulationInterior,
		>::forward(source.clone(), 500u128);
		ROUTER_SHOULD_FAIL.with(|f| f.set(false));

		assert!(result.is_err(), "expected forward to fail when router fails");
		assert_eq!(
			Balances::balance(&source),
			initial_balance,
			"source balance must be unchanged after XCM failure"
		);
		assert_eq!(
			Balances::total_issuance(),
			initial_issuance,
			"total issuance must be unchanged after XCM failure"
		);
	});
}
