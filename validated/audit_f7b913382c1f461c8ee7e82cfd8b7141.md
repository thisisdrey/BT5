Audit Report

## Title
`process_delivery_receipt` pays relayer reward without checking `DeliveryReceipt.success` - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` that carries a `success: bool` field sourced from the Ethereum `InboundMessageDispatched` event, but the function never reads that field before crediting the relayer reward via `T::RewardPayment::register_reward` and permanently removing the `PendingOrders` entry. This allows a relayer to be paid in full for messages whose Ethereum-side dispatch failed, as long as a valid Merkle/receipt proof for the (failure) event can be produced.

## Finding Description
`DeliveryReceipt::try_from` decodes the `gateway`, `nonce`, `topic`, `success`, and `reward_address` fields directly from the on-chain `InboundMessageDispatched` event log: [1](#0-0) . The `success` field is fully populated but `process_delivery_receipt` only checks `receipt.gateway` against `T::GatewayAddress::get()`, resolves `reward_account`, fetches the `PendingOrder` by `nonce`, and unconditionally pays `order.fee` via `T::RewardPayment::register_reward` before removing the order from `PendingOrders` and emitting `MessageDelivered` — `receipt.success` is never referenced: [2](#0-1) . The pallet's own documented flow confirms the intended sequence is verify → fetch pending order → pay reward → remove order, with no mention of gating on delivery outcome: [3](#0-2) . The existing guard (`GatewayAddress` equality plus the underlying Merkle/receipt proof verification performed by the caller before invoking this function) only proves the event genuinely originated from the configured Gateway contract — it says nothing about whether the dispatched commands succeeded on Ethereum, so it does not prevent payout for a genuine `success = false` event.

## Impact Explanation
This violates the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." A permissionless relayer can obtain full reward payment (`RewardLedger`/`register_reward` credit) for a message whose Ethereum-side dispatch reverted, and the `PendingOrder` is irreversibly removed via `<PendingOrders<T>>::remove(nonce)`, precluding retry, dispute, or correct resettlement. This matches the "duplicate settlement or payout" / "public underpriced work" impact categories for bridge processing.

## Likelihood Explanation
Any relayer holding a legitimately emitted `InboundMessageDispatched(nonce, topic, success=false, reward_address)` event (i.e., a command dispatch that reverts on Ethereum while the event is still emitted) can submit `submit_delivery_receipt` and be paid — no malicious peer, validator, governance, or key compromise is needed. This is a pure logic gap reachable via the standard public extrinsic path.

## Recommendation
Gate the reward payment, `PendingOrders` removal, and `MessageDelivered` event emission on `receipt.success`. When `success` is `false`, avoid disbursing the reward and instead transition the order to an explicit failed/refundable terminal state distinct from successful delivery.

## Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce]` with `fee > 0`: [4](#0-3) .
2. On Ethereum, the Gateway contract's dispatch of the message's commands fails but still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds a valid proof for this event and calls `submit_delivery_receipt`; `DeliveryReceipt::try_from` decodes `success = false` correctly: [5](#0-4) .
4. `process_delivery_receipt` ignores `success`, calls `T::RewardPayment::register_reward` with the full `order.fee`, and removes `PendingOrders[nonce]`: [6](#0-5) .
5. The relayer is paid in full despite the underlying dispatch having failed on Ethereum, and the order can never be corrected.

			relayer: <T as frame_system::Config>::AccountId,

		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
