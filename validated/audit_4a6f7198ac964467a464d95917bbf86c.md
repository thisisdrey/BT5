## Title
StackerDB chunk signatures lack contract/network domain separation, enabling cross-context replay of valid chunk writes - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
The oracle report describes a cross-chain replay issue caused by a signed digest that omits a fresh, context-binding value (`block.chainid`) from the actual signature payload. The same *class* of defect exists in `SlotMetadata::auth_digest` / `StackerDBChunkData` verification: the digest that a signer's key is checked against binds only to `(slot_id, slot_version, data_hash)` and never to the StackerDB's smart-contract identifier or any network/chain identifier.

### Finding Description
`SlotMetadata::auth_digest` builds the signed hash purely from `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`SlotMetadata::verify` recovers the pubkey from this digest and only compares the recovered `Hash160` against the `principal` address that the *caller* supplies: [2](#0-1) 

The caller-supplied "context" (which contract this chunk belongs to) is looked up independently via `get_slot_signer(smart_contract_id, slot_id)` and only checked *after* the digest is verified: [3](#0-2) 

Because the smart-contract identifier and network id are never mixed into the signed bytes, and the chunk row is only keyed by `(stackerdb_id, slot_id)` in storage (`PRIMARY KEY(stackerdb_id, slot_id)`), any valid `(sig, slot_id, slot_version, data)` tuple that was legitimately produced by a signer for **one** StackerDB contract remains a fully valid signature for **any other** StackerDB contract in which that same signer address happens to occupy the same `slot_id` — as confirmed by the schema: [4](#0-3) 

This is the exact analog of the reported bug class: a signature that is valid in "domain A" (one StackerDB contract / one chain) is silently accepted as valid in "domain B" (a different StackerDB contract / a different network) because the domain identifier is not part of the signed material, only checked out-of-band.

### Impact Explanation
Signer keys are commonly reused across multiple StackerDB contracts with parallel slot layouts — e.g. the same signer operator key is registered at the same `slot_id` across consecutive reward-cycle signer contracts, and/or across mainnet/testnet deployments that share code and often reuse the same private key for convenience. An attacker who is not a signer can observe a chunk that was legitimately broadcast for contract A (`sig`, `slot_id`, `slot_version`, `data`) and resubmit the identical `StackerDBChunkData` to contract B via the normal "push chunk"/"put chunk" RPC or gossip path. `validate_received_chunk` will accept it as long as: the size fits `config.chunk_size`, the registered signer address for that `slot_id` in contract B equals the one that produced the signature, and `slot_version` is `>=` the expected version in B: [5](#0-4) 

Since this write path stores data and is also re-gossiped to peers on acceptance, this allows an unauthorized/unprivileged party to inject a signer's genuine past message (e.g., a stale block-acceptance/rejection message, or any state a signer previously wrote) into an unrelated StackerDB replica without needing the signer's key at all — a forged-context write and network-wide propagation of out-of-domain data, matching the "StackerDB chunk stored without a valid owner signature" / "forged gossip relayed" categories called out as in-scope.

### Likelihood Explanation
Likelihood is moderate: it requires (a) knowledge of a previously-broadcast, validly signed chunk (trivially obtainable by any peer, since StackerDB chunks and their signatures are public gossip/RPC data), and (b) the existence of a second StackerDB contract in which the same signer address is registered at the same `slot_id` with an acceptable/lower version number than the one being replayed. Given that signer sets are recomputed each reward cycle from largely the same pool of registered signer keys, and contracts for successive cycles/roles are laid out with a fixed, deterministic slot assignment, this precondition is realistically reachable without insider access, unlike scenarios explicitly excluded by the rules (no node secret or admin role is needed).

### Recommendation
Bind the digest signed in `SlotMetadata::auth_digest` (and therefore `StackerDBChunkData::sign`/`verify`) to the full StackerDB context: include the `smart_contract_id` (or its numeric `stackerdb_id`) and the network/chain identifier in the hashed preimage, not just `(slot_id, slot_version, data_hash)`. Verification should look up and check this bound context rather than relying solely on a lookup performed after the fact.

### Proof of Concept
1. Signer `S` with private key `sk` is registered as the slot-0 signer in StackerDB contract `A` (e.g. `signers-0-<rc>`), and also happens to be registered as the slot-0 signer in a different StackerDB contract `B` (e.g. `signers-0-<rc+1>` or another network's equivalent contract) — a common occurrence given signer key reuse and deterministic slot layout.
2. `S` legitimately signs and pushes chunk `(slot_id=0, slot_version=5, data=D)` to contract `A`. This chunk and its `sig` are publicly observable via gossip/RPC (`libstackerdb/src/libstackerdb.rs:171-179`, `StackerDBChunkData::sign`).
3. Attacker `M` (no keys, no privileges) captures `(slot_id=0, slot_version=5, sig, D)` and submits it as a `StackerDBPushChunk`/`put_chunk` request against contract `B`.
4. `validate_received_chunk` for contract `B` calls `get_slot_signer(B, 0)` → returns `S`'s address; `slot_metadata.verify(&S_addr)` succeeds because the digest never encoded which contract it was for (`libstackerdb/src/libstackerdb.rs:159-166,183-193`); version/size checks pass if `5 >= expected_version_in_B` and size is within `B`'s `chunk_size`.
5. Contract `B` now stores/propagates `D` as if `S` had legitimately written it there, even though `S` never signed anything for contract `B`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

        &self,
        smart_contract_id: &QualifiedContractIdentifier,
        config: &StackerDBConfig,
        data: &StackerDBChunkData,
        expected_versions: &[u32],
    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }

        // validate -- must be the current or newer version
        if data.slot_version < *expected_version {
            info!(
                "Received StackerDBChunk for {} ID {} version {}, which is stale (expected {})",
                smart_contract_id, data.slot_id, data.slot_version, *expected_version
            );
            return Ok(false);
        }

        // validate -- must not exceed max writes
        if data.slot_version > config.max_writes {
            info!(
                "Write count exceeded for StackerDBChunk for {} ID {} version {} (max is {})",
                smart_contract_id, data.slot_id, data.slot_version, config.max_writes
            );
            return Ok(false);
        }
