### Title
Dust-transfer griefing fills `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, blocking victim deposits and collateral top-ups - ([File: contracts/Pool.sol])

### Summary
`Pool` tracks each account's collateral/debt positions in two per-account sets (`depositTokensOfAccount`, `debtTokensOfAccount`) capped at `MAX_TOKENS_PER_USER = 30`. Any `DepositToken` transfer to a first-time holder calls `Pool.addToDepositTokensOfAccount(recipient)`, which reverts with `UserReachedMaxTokens` once the combined list length reaches 30. An unprivileged attacker can deposit dust amounts of every registered collateral, then `transfer` 1 wei of each `DepositToken` to a victim, filling the victim's set. After that, any action that would add a new token to the victim's list reverts: deposits of new collateral types (`DepositToken.deposit → _mint → addToDepositTokensOfAccount`), incoming `transfer`/`transferFrom` of new deposit tokens, and any `seize` proceeds directed at the victim. This is a persistent, attacker-induced denial of service on a core protocol function, analogous to the hang/crash availability impact class.

### Finding Description
`Pool.sol` enforces the cap in `onlyIfAdditionWillNotReachMaxTokens` (Pool.sol:143-148) and applies it in `addToDepositTokensOfAccount` (Pool.sol:216-220). The add is triggered from `DepositToken._transfer` whenever the recipient's prior balance is zero (DepositToken.sol:517-520) and from `_mint` (DepositToken.sol:486-488). `transfer` only requires the *sender's* unlocked balance (`_revertIfLocked(_msgSender, amount_)`, DepositToken.sol:348-354), so the attacker can push dust into an arbitrary `to_`. There is no opt-out or whitelist for recipients, and the set is only shrunk when the victim's balance for that token returns to exactly zero.

Once the victim is at 30 entries:
- `depositTokenX.deposit(amount, victim)` for any `DepositToken` the victim doesn't already hold reverts inside `_mint`.
- Any third party `transfer`/`transferFrom` of a new deposit token to the victim reverts.
- If the victim has outstanding debt such that `unlockedBalanceOf(victim) == 0` for the dusted tokens, the victim cannot even transfer the dust back out (`_revertIfLocked` blocks it), so the freeze persists until the victim repays debt or the position is liquidated — and liquidation itself is worse for the victim than being allowed to top up collateral.

Invariant broken: liveness of deposit/transfer entry points for a targeted account, with no governance involvement and no pause flag required.

### Impact Explanation
Temporary freezing of funds / feature DoS on a per-victim basis. The victim cannot add new collateral to an open debt position while under attack. If the position approaches liquidation during the freeze window, the victim loses the ability to restore health by depositing a different collateral type and is forced into liquidation (losing the liquidation incentive/penalty). If the victim's unlocked balance is zero, they also cannot clear the dusted slots themselves. All user-facing mitigations either don't exist or require the victim to already hold a slot for the collateral they want to add.

### Likelihood Explanation
Cost to the attacker is only gas plus dust amounts of up to 30 collateral tokens they acquire via normal `deposit`/`withdraw` (or by buying the DepositTokens), all fully reclaimable afterward. No privileged role, no oracle manipulation, no timing dependency beyond doing it before the victim needs to act. The only requirement is that the pool has enough registered deposit/debt tokens to reach the cap; the attacker can also mix in `DebtToken` slots only for their own account, so effectively up to 30 deposit-token dust transfers suffice.

### Recommendation
Make recipient-side list growth non-griefable, e.g.:
- Only add to `depositTokensOfAccount` on mints (`_mint` via `deposit`), not on plain transfers, or add a `transfer`-specific path that skips the cap check by tolerating an uncapped list for received balances, or
- Let `addToDepositTokensOfAccount` silently no-op / emit an event instead of reverting when the cap is hit, so deposits still succeed even if the account list saturates (tracking completeness then degrades gracefully rather than bricking entry points), or
- Allow victims to remove entries by a permissionless `removeFromDepositTokensOfAccount`-style cleanup when balance is zero.

### Proof of Concept
Hardhat sketch (assuming a deployed `Pool` with ≥30 registered `DepositToken`s, or fewer tokens combined with victim's existing entries):

```ts
// setup: attacker deposits 1 wei (or min unit) in each deposit token i
for (const dt of depositTokens) { // depositTokens.length + victimExisting >= 30
  await underlying(dt).approve(dt.address, 1);
  await dt.deposit(1, attacker.address);
}

// attack: push dust to victim, filling depositTokensOfAccount[victim]
for (const dt of depositTokens) {
  await dt.connect(attacker).transfer(victim.address, 1);
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(30);

// victim tries to deposit a collateral type it doesn't hold yet -> reverts
const newDt = depositTokens[0] !== victimHeldToken ? depositTokens[0] : depositTokens[1];
await underlying(newDt).mint(victim.address, parseEther('10'));
await underlying(newDt).connect(victim).approve(newDt.address, parseEther('10'));
await expect(
  newDt.connect(victim).deposit(parseEther('10'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// third-party transfer of a new deposit token to victim also reverts
await expect(
  newDt.connect(attacker).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// if victim's position is fully locked (debt ~= collateral), victim cannot
// clear the dust slots: transfer back reverts with NotEnoughFreeBalance
await expect(
  depositTokens[0].connect(victim).transfer(attacker.address, 1)
).to.be.revertedWithCustomError(depositTokens[0], 'NotEnoughFreeBalance');
```
