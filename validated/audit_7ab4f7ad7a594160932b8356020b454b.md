### Title
Floating-point Bancor-formula precision drift in `ExchangeTransactionActuator` allows value extraction from TRON's built-in AMM pools - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The reported Yearn v1 yDAI incident was ultimately an accounting-precision/price-manipulation bug: the vault's share price could be pushed into a state where a deposit/withdraw sequence let the attacker extract more value than deposited, at the reserve's expense. java-tron has an analogous on-chain AMM subsystem — the `Exchange*` actuators, which implement a Bancor-style bonding curve for TRX/TRC10 pairs. Any unprivileged account can freely trigger trades (`ExchangeTransactionContract`, fee = 0) against these pools. The default (non-hardened) execution path computes the bonding-curve output using native Java `double` arithmetic and `Math.pow`, which is a reachable, attacker-controlled source of rounding/precision drift analogous to the price-manipulation root cause in the report.

### Finding Description
`ExchangeCapsule.transaction()` selects between two `Processor` implementations depending on the `allowHardenExchangeCalculation` dynamic property: [1](#0-0) 

When hardening is not enabled (the historical/default behavior gated by a committee proposal, see `ProposalUtil`/`DynamicPropertiesStore` `allowHardenExchangeCalculation`), trades are executed by `ExchangeProcessor`, which computes the Bancor "relay/supply" conversion using IEEE-754 `double` math and `Math.pow`: [2](#0-1) 

This function is invoked directly from `ExchangeTransactionActuator.execute()` for every trade, with the trade amount and direction fully attacker-controlled and the calling fee set to zero: [3](#0-2) [4](#0-3) 

The only user-side constraint is a minimum-received check (`anotherTokenQuant < tokenExpected`), which only protects the caller from getting less than expected — it does nothing to protect the pool's other liquidity holder (the pool creator) from being drained via repeated small trades that exploit `double`/`Math.pow` rounding in the attacker's favor: [5](#0-4) 

The `SafeExchangeProcessor` (BigDecimal-based, rounds `DOWN`) exists specifically as a hardened remediation for this exact class of issue, confirming the underlying floating-point processor was recognized internally as imprecise/exploitable: [6](#0-5) 

This mirrors the Yearn root cause pattern: a reserve-ratio/price computation reachable by an unprivileged caller, computed with insufficient numerical rigor (floating point vs. the "correct"/fixed-point accounting), that can be driven to a state benefiting the caller at the expense of the pooled reserve.

### Impact Explanation
On chains/nodes where `allowHardenExchangeCalculation` has not been activated (or during any window prior to activation), any address can call `ExchangeTransactionContract` at zero cost, repeatedly, to accumulate favorable floating-point rounding in the trade output, incrementally extracting real TRX/TRC10 value from the pool's `firstTokenBalance`/`secondTokenBalance` reserves at the expense of the pool creator. Because pool balances back real, previously-deposited TRX and TRC10 assets, this is a concrete "theft of funds" class impact, not merely a resource-exhaustion issue.

### Likelihood Explanation
Likelihood is constrained by network state: this only applies where `allowHardenExchangeCalculation` is disabled for the relevant pools (the codebase's own tests and the existence of the hardened path confirm this was an active concern, meaning it is plausible that not all deployed exchange pools/network configurations have hardening enabled). The `ExchangeTransactionActuator` is fee-free and callable by any account with a pool-eligible balance, making exploitation trivial to script; the primary barrier is the magnitude of extractable drift per trade, which requires empirical measurement to quantify practical profitability given TRON's bandwidth/energy costs per transaction.

### Recommendation
Enforce `SafeExchangeProcessor` (or an equivalent fixed-point/BigDecimal implementation) unconditionally for all exchange trade/inject/withdraw calculations, removing the double/`Math.pow`-based `ExchangeProcessor` path entirely rather than gating it behind a togglable dynamic property. Add pool-level slippage/drift invariant checks (e.g., constant-product or constant-supply invariant must not decrease beyond a negligible bound) after every trade, independent of the hardening flag.

### Proof of Concept
Not independently reproduced in this session — validation would require running `ExchangeProcessorTest`-style scenarios (already present in the repo) with `allowHardenExchangeCalculation` disabled, executing many small `ExchangeTransactionContract` calls in alternating directions against a pool, and measuring cumulative reserve drift compared to the same sequence executed via `SafeExchangeProcessor`, per the test harness in [7](#0-6) . This is noted as unverified/uncertain and would need to be confirmed with an actual Devin session with code execution access.

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
