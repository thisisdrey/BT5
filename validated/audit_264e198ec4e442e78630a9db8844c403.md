## Analysis

The external report's core broken invariant: a public "vote/allocate resources" entrypoint accepts a target without verifying the target is a currently valid, registered recipient, silently wasting the voter's influence.

The direct local analog is `pallet_staking::Pallet::nominate()` in `substrate/frame/staking/src/pallet/mod.rs`. This is the *legacy* (non-async) staking pallet, and its target-validation logic still lacks the fix that was applied to the newer `pallet-staking-async` sibling for exactly this bug class (`prdoc/pr_8436.prdoc`, "Fix calling nominate on a validator that doesn't exist silently succeeds").

### Title
Legacy `pallet-staking::nominate()` accepts targets that were never registered as validators, wasting the nominator's voting weight - (File: `substrate/frame/staking/src/pallet/mod.rs`)

### Summary
`nominate()` is supposed to let a signed controller cast NPoS voting weight for a set of validator `targets`. The per-target validity check only tests whether the target account, if it exists as a validator, is not `blocked` — it never checks that the target is actually present in the `Validators` storage map at all.

### Finding Description
In the target-mapping closure of `nominate()`: [1](#0-0) 

the guard is:
```rust
if old.contains(&n) || !Validators::<T>::get(&n).blocked {
    Ok(n)
} else {
    Err(Error::<T>::BadTarget.into())
}
```
`Validators::<T>::get(&n)` is a `StorageMap` query that returns `ValidatorPrefs::default()` (which has `blocked: false`) for any account `n` that was **never** registered via `validate()`. Consequently `!Validators::<T>::get(&n).blocked` evaluates to `true` for a completely nonexistent validator, and the nomination is accepted with `Ok(n)`.

Contrast this with the already-fixed sibling pallet, `pallet-staking-async`, whose `nominate()` explicitly requires membership: [2](#0-1) 
```rust
if old.contains(&n) ||
    (Validators::<T>::contains_key(&n) && !Validators::<T>::get(&n).blocked)
```
and is covered by the regression test `nominating_non_validators_is_not_ok`: [3](#0-2) 

The `prdoc` for that fix confirms the exact bug class and that it was patched only in `pallet-staking-async`: [4](#0-3) 

The legacy `pallet-staking` test suite only exercises the "blocked-but-registered" case (`blocking_and_kicking_works`), never a genuinely nonexistent target: [5](#0-4) 

There is no equivalent `nominating_non_validators_is_not_ok` test in `substrate/frame/staking/src/tests.rs`, confirming the gap was never caught for this pallet.

### Impact Explanation
Any signed nominator can call `nominate()` with account IDs that have never called `validate()`. `do_add_nominator` will store these bogus targets in `Nominators`, and the nominator's bonded stake is registered against them for the purpose of NPoS election (`VoterList`/election-provider-multi-phase reads `Nominators` to build voter support for the election). Because the "validator" never actually exists in the elected set, that fraction of the nominator's voting weight is a dead vote — it cannot contribute to backing any real validator, silently degrading the effectiveness of the election (weaker validator set legitimacy/support) without any error being surfaced to the user, exactly mirroring the "emissions lost to a pool without a gauge" pattern from the source report. It also lets a user consume their `MaxNominations` slots with non-functional entries while appearing to have a full nomination set, and can be used to grief `TargetList`/approval-stake bookkeeping expectations that assume nominated targets are checked at nomination time (the pallet's own doc for `TargetList` explicitly assumes "at the time of nomination, all targets are checked to be real validators").

### Likelihood Explanation
Trivial and fully permissionless: any bonded account can call `Staking::nominate(origin, targets)` with an arbitrary `AccountId` that has never validated, at zero cost beyond the normal extrinsic. No privileged role, relayer, or governance action is required.

### Recommendation
Mirror the fix already applied in `pallet-staking-async`: require `Validators::<T>::contains_key(&n)` in addition to the `blocked` check before accepting a nomination target in `substrate/frame/staking/src/pallet/mod.rs`'s `nominate()`:
```rust
if old.contains(&n) ||
    (Validators::<T>::contains_key(&n) && !Validators::<T>::get(&n).blocked)
{
    Ok(n)
} else {
    Err(Error::<T>::BadTarget.into())
}
```
Add a regression test analogous to `nominating_non_validators_is_not_ok`.

### Proof of Concept
1. In a fresh chain state, bond account `1` with `Staking::bond(...)`.
2. Call `Staking::nominate(RuntimeOrigin::signed(1), vec![999])` where `999` has never called `Staking::validate(...)`.
3. The call succeeds (`Ok(())`) and `Nominators::<T>::get(1)` shows `targets: [999]`, even though `999` is not, and never was, a validator — demonstrating the missing `contains_key` check, as can be directly contrasted with the `nominating_non_validators_is_not_ok` test in the fixed `pallet-staking-async` crate which asserts `Error::<Test>::BadTarget` for the same scenario.
