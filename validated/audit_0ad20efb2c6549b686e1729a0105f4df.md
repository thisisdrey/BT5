### Title
Client-Controlled `GitConfigOptions` Allows Disabling `receive.maxInputSize` (and Other Safety Limits) via Zero/Empty Value During Push - ([File: internal/gitaly/service/smarthttp/receive_pack.go])

### Summary
Gitaly's `PostReceivePack` / `SSHReceivePack` RPCs accept a client-supplied `git_config_options` field that is passed straight through to `git receive-pack` as `-c key=value` pairs, with validation limited to syntactic checks (key format), not an allowlist of permitted keys or values. A pushing client can therefore set `receive.maxInputSize=0`, which Git treats as "no limit" and effectively disables the maximum-push-size safety control that the same mechanism is documented to enforce. This mirrors the Notional bug class: a caller-supplied numeric parameter whose `0` value is treated by the downstream component as "no limit/no check," silently defeating a threshold the server was supposed to enforce.

### Finding Description
`PostReceivePackRequest`/`SSHReceivePackRequest` both expose a repeated `git_config_options` field described as "parameters to use with git -c (key=value pairs)" [1](#0-0) [2](#0-1) .

In the RPC handlers, these caller-supplied options are converted directly into git configuration flags and passed to `git-receive-pack`: [3](#0-2) [4](#0-3) 

The only validation performed on each `GitConfig` entry is syntactic — it checks that the key is non-empty, contains no `=`, contains at least one `.`-separated section, doesn't start/end with a dot, and matches a generic `key.subkey` regex. There is no restriction on *which* configuration keys or values a caller may set: [5](#0-4) 

A test in the codebase confirms that `GitConfigOptions` can control `receive.MaxInputSize`, proving the config key is not blocked and is honored by git-receive-pack: [6](#0-5) 

That test only demonstrates *setting a restrictive* value (`receive.MaxInputSize=1`) to reject an oversized push. However, the identical mechanism permits the inverse: a client can submit `receive.maxInputSize=0`. Per Git's own semantics, `receive.maxInputSize=0` means "no limit," exactly analogous to the audited Notional bug where `oracleSlippagePercent=0` was supposed to be the strictest (or an invalid/rejected) setting but was instead interpreted by the downstream limit-computation code as "disable the check entirely." Here, a value that superficially looks like the most conservative setting (0) is actually interpreted by Git as "unlimited," letting an ordinary, authenticated push client remove a size-based DoS control that a Gitaly/GitLab administrator may rely on (whether configured server-side as a default or expected to be enforced via this same option).

### Impact Explanation
If a GitLab/Gitaly deployment relies on `receive.maxInputSize` (set via server-side git config or via this same RPC field for legitimate reasons) to bound the size of packs accepted on push, a malicious or buggy client can use the identical `git_config_options` channel to submit `receive.maxInputSize=0`, defeating that bound and allowing arbitrarily large pushes. This is a resource-exhaustion (DoS) vector on the RPC handler (`PostReceivePack`/`SSHReceivePack`) — unbounded pack data can consume disk, memory, and CPU during unpacking, and is reachable by any ordinary push, not a privileged actor.

### Likelihood Explanation
Likelihood is moderate to high in terms of exploitability (no special privilege is needed beyond normal push access, which is the standard threat model for a push-triggered RPC), but the *severity* is contingent on whether the deployment operator or a Rails caller (GitLab) actually depends on `receive.maxInputSize` — or another safety-relevant git config option — being enforced without being overridable by end clients. Because `GitConfigOptions` is a general passthrough with no allowlist, this class of bypass is not limited to `maxInputSize`; any git config key that a client should not be able to control (e.g., fsck strictness, `receive.denyCurrentBranch`, `receive.unpackLimit`) is similarly overridable, increasing overall likelihood that *some* safety-relevant knob is exposed to bypass.

### Recommendation
Introduce an allowlist (or denylist of security-relevant keys) for `GitConfig` entries accepted via `git_config_options` on `PostReceivePackRequest`/`SSHReceivePackRequest` (and equivalent upload-pack RPCs), rejecting or ignoring options that touch limits/security-relevant namespaces (e.g., `receive.maxInputSize`, `receive.fsck.*`, `receive.denyCurrentBranch`, `uploadpack.*` filters) unless explicitly intended to be client-settable. If certain keys must remain client-settable, clamp/validate their values server-side (e.g., disallow `0` for `receive.maxInputSize` if `0` is documented as "unlimited") rather than relying on Git's own permissive semantics.

### Proof of Concept
1. As an ordinary authenticated push client, initiate `PostReceivePack` (or `SSHReceivePack`) against a repository.
2. Include `GitConfigOptions: []string{"receive.maxInputSize=0"}` in the request, following the same pattern already exercised in `TestPostReceivePack_rejectViaGitConfigOptions` [7](#0-6)  but with `0` instead of `1`.
3. Push an oversized packfile that would normally be rejected by an operator-configured `receive.maxInputSize`.
4. Observe that `git-receive-pack` accepts the push without a "pack exceeds maximum allowed size" error, because `0` is interpreted by Git as no limit, whereas the operator intended a bound to be enforced.

Note: I was unable to find a server-side default value for `receive.maxInputSize` being set by Gitaly itself in the indexed code (only the test sets it), so it is uncertain whether GitLab.com/self-managed deployments currently rely on this control by default; this affects the severity but not the existence of the bypass mechanism itself.

// Validate validates that the Git configuration conforms to a format that Git understands.
func (cfg GitConfig) Validate() error {
	// Even though redundant, this block checks for a few things up front to give better error
	// messages to the administrator in case any of the keys fails validation.
	if cfg.Key == "" {
		return cfgerror.NewValidationError(cfgerror.ErrNotSet, "key")
	}
	if strings.Contains(cfg.Key, "=") {
		return cfgerror.NewValidationError(
			fmt.Errorf(`key %q cannot contain "="`, cfg.Key),
			"key",
		)
	}
	if !strings.Contains(cfg.Key, ".") {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q must contain at least one section", cfg.Key),
			"key",
		)
	}
	if strings.HasPrefix(cfg.Key, ".") || strings.HasSuffix(cfg.Key, ".") {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q must not start or end with a dot", cfg.Key),
			"key",
		)
	}

	if !configKeyRegex.MatchString(cfg.Key) {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q failed regexp validation", cfg.Key),
			"key",
		)
	}

	return nil
}

func TestPostReceivePack_rejectViaGitConfigOptions(t *testing.T) {

	stream, err := client.PostReceivePack(ctx)
	require.NoError(t, err)

		GlId:             "user-123",
		GlRepository:     "project-123",
		GitConfigOptions: []string{"receive.MaxInputSize=1"},
	})

	requireSideband(t, []string{
		gittest.Pktlinef(t, "\x02fatal: pack exceeds maximum allowed size\n"),

			gittest.Pktlinef(t, "unpack unpack-objects abnormal exit\n"),
			gittest.Pktlinef(t, "ng %s unpacker error\n", git.DefaultRef),

		}, "")),
	}, response)
