### Title
Fixed-window stream throttling permits ~2x burst at STREAM_THROTTLING_INTERVAL boundaries - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a fixed (tumbling) window counter rather than a sliding window, resetting `stream_count` to 0 only when more than `STREAM_THROTTLING_INTERVAL` has elapsed since the last reset. An attacker who controls the timing of stream creation on a connection can send up to `max_streams_per_throttling_interval` streams just before a window boundary and another full batch immediately after, achieving close to double the intended per-interval cap within a short real-time window.

### Finding Description
`throttle_stream` in [1](#0-0)  calls `reset_throttling_params_if_needed` and then compares `stream_count` against `max_streams_per_throttling_interval` to decide whether to sleep. The reset logic itself only checks elapsed time since the last reset instant: [2](#0-1) 

Because the counter and its window-start timestamp are only ever reset when `duration_since(last_throttling_instant) > STREAM_THROTTLING_INTERVAL`, this is a classic fixed-window rate limiter. An attacker controlling an open QUIC connection to the TPU port can:
1. Open streams up to `max_streams_per_throttling_interval` right before the window ends (e.g., at `t = interval_end - epsilon`), all counted in window W1 without triggering throttling.
2. Immediately after `t = interval_end`, the next stream causes `reset_throttling_params_if_needed` to reset `stream_count` to 0 and set a new `last_throttling_instant`.
3. The attacker then immediately bursts another full `max_streams_per_throttling_interval` streams in window W2.

In a real-time sliding window spanning `epsilon` before the boundary to `STREAM_THROTTLING_INTERVAL - epsilon` after it (i.e., duration ~`STREAM_THROTTLING_INTERVAL`), the attacker gets close to `2 * max_streams_per_throttling_interval` streams accepted without triggering the `sleep` back-off, versus the intended cap of one `max_streams_per_throttling_interval` per `STREAM_THROTTLING_INTERVAL`.

### Impact Explanation
This is a QoS-evasion bug: it allows a single unstaked/attacker-controlled connection to roughly double its allotted per-connection stream throughput for a short window around each 100ms boundary (`STREAM_THROTTLING_INTERVAL_MS = 100`, see [3](#0-2) ). The scope of impact is limited to the per-connection quota already allocated to that connection (bounded by `available_load_capacity_in_throttling_duration`, itself capped by stake share or the fixed unstaked share). It does not grant unbounded resource consumption, panic, or verification bypass — the overshoot is capped at a constant factor (~2x) of an already-bounded per-connection quota, so it does not starve the whole validator, only marginally increases that one connection's fair share at boundary instants.

### Likelihood Explanation
Fully attacker-controlled: an unstaked remote client that can open a QUIC connection to the TPU port and control exact packet/stream timing can reliably trigger this every `STREAM_THROTTLING_INTERVAL` (100ms) by scheduling stream opens near the boundary, making it deterministic and repeatable given only client-side timing control (no validator/staked/gossip access needed).

### Recommendation
Replace the fixed-window counter with a sliding-window or token-bucket algorithm (e.g., track individual stream timestamps or use a leaky-bucket counter that decays continuously) so that the enforced constraint is "no more than `max_streams_per_throttling_interval` streams in any `STREAM_THROTTLING_INTERVAL`-length window," not just per fixed-aligned window.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (test module)
#[tokio::test(start_paused = true)]
async fn test_fixed_window_boundary_burst_exceeds_cap() {
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams = 10u64;

    // Burst 1: consume full quota just before the boundary.
    for _ in 0..max_streams {
        counter.reset_throttling_params_if_needed();
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    // Advance time to just past STREAM_THROTTLING_INTERVAL.
    tokio::time::advance(STREAM_THROTTLING_INTERVAL + Duration::from_millis(1)).await;

    // Burst 2: reset triggers here, then attacker bursts full quota again.
    let mut accepted_in_second_burst = 0;
    for _ in 0..max_streams {
        counter.reset_throttling_params_if_needed();
        let count = counter.stream_count.load(Ordering::Relaxed);
        if count < max_streams {
            counter.stream_count.fetch_add(1, Ordering::Relaxed);
            accepted_in_second_burst += 1;
        }
    }

    // Total streams accepted across the two bursts within ~STREAM_THROTTLING_INTERVAL
    // real time exceeds the single-interval cap, violating the sliding-window invariant.
    let total = max_streams + accepted_in_second_burst;
    assert!(
        total > max_streams,
        "expected total {total} to exceed single-window cap {max_streams}, demonstrating boundary burst"
    );
}
```
This test demonstrates that within a real-time span of roughly one `STREAM_THROTTLING_INTERVAL`, an attacker who times stream creation around the fixed-window reset boundary is accepted for `2 * max_streams_per_throttling_interval` streams instead of being throttled at `max_streams_per_throttling_interval`, confirming the fixed-window reset in `reset_throttling_params_if_needed` does not enforce a sliding-window cap.
