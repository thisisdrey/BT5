### Title
Unbounded HTTP response body read in `StackerDBSession::rpc_request` allows remote memory-exhaustion DoS against the signer - (File: `libsigner/src/http.rs`)

### Summary
`StackerDBSession` (a signer-side StackerDB HTTP client) connects to a configured `host` and issues HTTP requests via `run_http_request()`, which reads the entire HTTP response into memory with `sock.read_to_end(&mut buf)` before any length/size checking is applied. There is no bound on how large a response body can be before it is fully buffered in RAM.

### Finding Description
`run_http_request()` in `libsigner/src/http.rs` writes the request, then calls: [1](#0-0) 

`sock.read_to_end(&mut buf)?;` reads from the socket into `buf` until EOF, with no cap on the number of bytes accepted. Only *after* the entire response has been buffered does the code call `decode_http_response()` to parse headers/status, and `decode_http_body()` to extract the body — and even `decode_http_body`'s size enforcement (`MAX_MESSAGE_LEN`) only applies to the chunked-transfer-encoding branch via `HttpChunkedTransferReader`; the non-chunked branch (`buf.to_vec()`) is unconstrained too, but by that point the unbounded `read_to_end` has already consumed unlimited memory regardless of `Content-Length` or chunking. [2](#0-1) 

This function is invoked by `StackerDBSession::rpc_request`, which is the transport used by `SignerSession::list_chunks`/`get_chunks`/`put_chunk` to talk to a StackerDB replica endpoint (a Stacks node's `/v2/stackerdb/...` HTTP API): [3](#0-2) 

The `host` here is attacker-influenceable in practice: it is either a configured node RPC endpoint that an attacker who compromises/impersonates that node (or performs a MitM on the plaintext HTTP connection) can respond to with an arbitrarily large body, causing the signer process to allocate unbounded memory in a single `Vec<u8>` before any parsing/limit check occurs. This is the exact bug class from the referenced advisory (GHSA-28xm-prxc-5866): unbounded `HttpClient`/socket response-body reads into memory prior to any size enforcement.

By contrast, the equivalent server-side/node-side HTTP stack (`stackslib/src/net/httpcore.rs`, `stackslib/src/net/http/common.rs`) enforces `MAX_MESSAGE_LEN` and content-length checks incrementally while streaming (e.g. `parse_bytes`/`parse_raw_bytes` with `max_len`, and the chunked reader’s `HttpChunkedTransferReaderState` enforcing `max_size` during the read loop) — so the analog is specific to this client-side libsigner HTTP transport, which does not apply any such incremental bound.

### Impact Explanation
An attacker who controls, impersonates, or can MitM the node endpoint that a signer's `StackerDBSession` connects to can return an unbounded HTTP response, causing `run_http_request` to allocate memory without limit until the process runs out of memory or suffers severe GC/allocator pressure, terminating the signer process. This is a Denial-of-Service impact on the signer, matching "bounded/unbounded compute or memory DoS via a read endpoint" style vulnerabilities. It does not itself corrupt state or bypass authentication, but it can crash a critical signer component.

### Likelihood Explanation
Likelihood depends on the attacker's ability to control or intercept the specific node the signer is configured to talk to. This is not trivially triggerable by an arbitrary internet peer, since the signer's `host` is an operator-chosen endpoint (typically the operator's own node) rather than one supplied by unauthenticated third parties. Risk increases materially if that endpoint is remote/untrusted, or reachable to an on-path attacker (no TLS is used — communication is plain HTTP over `TcpStream`), which matches the "mitigating factors" language in the original advisory (increased risk with remote/untrusted endpoints, and no protection against MitM).

### Recommendation
- Bound the initial socket read in `run_http_request` (e.g., using a `BoundReader`/`LimitReader` analogous to `stacks_common::util::retry::BoundReader`, already used elsewhere in this codebase) so the total bytes read from the response, both headers and body, cannot exceed `MAX_HTTP_HEADER_LEN * MAX_HTTP_HEADERS` for headers and a fixed maximum body size (e.g., `STACKERDB_MAX_CHUNK_SIZE` or `MAX_MESSAGE_LEN`) for the body.
- Enforce that bound *before* buffering, not after, i.e., stream-read into a bounded buffer and abort/close the connection once the limit is exceeded, rather than calling `read_to_end` unconditionally.
- Consider validating `Content-Length` (if present) against the maximum accepted size before reading the body, mirroring the pattern already used in `stackslib/src/net/http/common.rs::parse_raw_bytes`/`parse_bytes`.

### Proof of Concept
1. Configure a `StackerDBSession` to point at an attacker-controlled or MitM'd host (e.g., a malicious or compromised node masquerading as the signer's target node).
2. Have that endpoint accept the TCP connection, read the HTTP request, and then respond with an HTTP/1.1 200 response whose body is streamed indefinitely (or a very large fixed size, e.g., tens of GB), either with `Content-Length` omitted/lied about, or via `Transfer-Encoding: chunked` with an extremely large aggregate payload (note: for the chunked path `MAX_MESSAGE_LEN` is enforced by `HttpChunkedTransferReader`, but the unbounded `read_to_end` call still occurs first and reads the entire raw wire stream into `buf` regardless of chunking, so a non-chunked or minimally-chunked but enormous raw stream still triggers unbounded allocation at the `sock.read_to_end` step).
3. Observe the signer process's memory usage grow without bound as `run_http_request` executes `sock.read_to_end(&mut buf)`, eventually causing an OOM condition/process termination.

/// Decode an HTTP body, given the headers.
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
