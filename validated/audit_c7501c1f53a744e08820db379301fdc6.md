### Title
Unvalidated packfile objects are committed to the write-ahead log before content verification, allowing malformed/malicious objects to be permanently persisted - ([File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go])

### Summary
`TransactionManager.packObjects` builds the packfile that will be logged into the write-ahead log (WAL) and later applied to disk, but the function's own doc comment states the packed objects are **not checked for validity** before being committed. This mirrors the reported root cause pattern in the Rollup.sol bug: a piece of state (a "batch"/here, a packfile of objects) is accepted and durably committed at one stage, while the actual correctness/validity check is deferred to a later stage (or, in this case, never fully performed), creating a window where invalid data can become part of the committed, durable state.

### Finding Description
`packObjects` walks the objects present in a push's quarantine directory plus the new reference tips, and packs everything found into `objects.pack`/`.idx`/`.rev` files that are recorded into the transaction's WAL entry via `transaction.walEntry.CreateFile(...)`. [1](#0-0) 

The function explicitly documents the gap:
> "The packed objects are not yet checked for validity. See the following issue for more details: https://gitlab.com/gitlab-org/gitaly/-/issues/5779" [2](#0-1) 

The only verification that happens involves object *existence* for objects that are **missing** from the walk (recorded as `transaction.objectDependencies`, later checked to exist in the repository to guard against concurrent pruning): [3](#0-2) 

There is no step here (nor documented elsewhere in this function) that validates the *content* of the objects being packed — e.g., that a commit's tree/parents are well-formed, that blobs/trees don't encode path-traversal or `.gitmodules`/`.git` injection payloads, or that the object graph is internally consistent. Once `index-pack` succeeds and the resulting `.pack`/`.idx`/`.rev` files are logged via `CreateFile`, they become part of the transaction's WAL entry, which is then durably appended to the log and, on apply, physically written into the repository's object directory as the canonical, un-quarantined state of the repository.

This is the same defect shape as the audited bug: acceptance/commit of state happens at a point in the pipeline where the deciding validity check has not yet run (or does not run at all for object content), so invalid data can slip into the durably-committed history of the repository/partition.

### Impact Explanation
Because the objects are committed to the WAL and then unpacked into the live object directory without content validation, a client that can reach a write RPC (push, `UserCommitFiles`, etc., all of which route new objects through this quarantine → `packObjects` → WAL path) could get malformed or inconsistent objects durably persisted into the repository state. Once applied, this is no longer quarantined and cannot be trivially discarded — unlike the `pre-receive` quarantine cleanup path, which can `rm -rf` a rejected quarantine directory before the WAL commit. If a later step (e.g., replication, `git fsck`, connectivity checks by other subsystems, or simply reading back the object) faults on such invalid data, it can produce repository-level errors on subsequent read/fetch RPCs against that partition — a denial of service confined to that repository/partition, requiring manual intervention to repair, conceptually analogous to the "chain freeze" in the source report where an un-validated commit could not be rolled forward or backward cleanly.

### Likelihood Explanation
The likelihood of triggering this specific gap depends on whether earlier layers (git's own pack parsing, `index-pack`, hook checks) implicitly catch malformed objects — `index-pack` does perform basic pack/object hash integrity checks, which limits the class of "invalid" objects that can get this far. However, the doc comment on `packObjects` explicitly acknowledges the residual validity gap is real and unresolved (tracked upstream as gitaly#5779), meaning some class of objects that pass `index-pack`'s structural checks but are otherwise semantically invalid/malicious (e.g., an object graph engineered to break assumptions elsewhere, such as GitLab's tree-walking or diff logic) can reach durable storage via ordinary push/commit RPCs, without needing any privileged access — this satisfies the "ordinary user push" reachability requirement.

### Recommendation
Add a content-validation stage before or immediately after `index-pack` in `packObjects` (or before the WAL entry is marked ready for commit) that performs at least the checks GitLab hooks/Gitaly `pre-receive`/`git fsck`-equivalent connectivity and object-format validation are relying on, so that malformed or unsafe objects cannot be committed to the WAL and unpacked into the canonical object directory. Alternatively, ensure this validation gap referenced in gitaly#5779 is closed before the transaction is considered committed, mirroring the way the Rollup fix required moving the `prevStateRoot` check from `finalizeBatch()` into `commitBatch()` — i.e., move (or add) the missing validation into the commit path itself rather than relying on a later or absent verification stage.

### Proof of Concept
Not applicable — this is a static code-review finding based on the explicit, self-documented gap in `packObjects`. No proof-of-concept payload was constructed in this analysis; a concrete PoC would require crafting an object that passes `git index-pack`'s structural integrity check yet causes malfunction in a downstream consumer (e.g., GitLab Rails tree/diff processing or a later Gitaly RPC), which is out of scope for this static analysis pass and is exactly what gitaly issue #5779 was filed to track.
