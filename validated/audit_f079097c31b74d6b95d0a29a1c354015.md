### Title
Node-wide pending-transaction queues are bounded only by entry count, not aggregate byte size, allowing memory exhaustion via near-max-size transaction broadcasts - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager` gates transaction admission solely with `isTooManyPending()`, which compares the *number* of queued transactions (`pushTransactionQueue.size() + pendingTransactions.size() + rePushTransactions.size()`) against `maxTransactionPendingSize` (default 2000). No aggregate byte-size budget is tracked. Since each individual transaction can legally be nearly `TRANSACTION_MAX_BYTE_SIZE` (500 KiB) — and that per-transaction size check itself only runs *after* the transaction has already been enqueued into the unbounded `pushTransactionQueue` — an unprivileged client broadcasting many large-but-valid-looking transactions can force the node to retain up to hundreds of megabytes of transaction payloads in memory, the same bug class as the referenced Besu `FutureMessageBuffer` advisory (count-based cap with no byte-size accounting).

### Finding Description
- `isTooManyPending()` and its backing `getCachedTransactionSize()` are purely count-based: [1](#0-0) 
- `maxTransactionPendingSize` defaults to 2000 and is a simple entry-count threshold, configured with no companion byte-size limit: [2](#0-1) 
- `Wallet.broadcastTransaction()` checks `dbManager.isTooManyPending()` and rejects with `SERVER_BUSY` only when the *count* threshold is exceeded, not when byte usage is high: [3](#0-2) 
- Critically, `pushTransaction()` unconditionally appends the incoming transaction to the unbounded `pushTransactionQueue` (`new LinkedBlockingQueue<>()`, no capacity bound) *before* performing signature validation or the per-transaction size check (`validateCommon`, which throws `TooBigTransactionException` only if the encoded size exceeds `TRANSACTION_MAX_BYTE_SIZE`). The size check happens deep inside `processTransaction()` under a global lock, so the transaction payload sits fully resident in memory in `pushTransactionQueue` for the entire time it waits for signature verification and for the `transactionLock`: [4](#0-3) [5](#0-4) 
- The per-transaction cap that eventually applies is 500 KiB: [6](#0-5) 
- Because `getCachedTransactionSize()`/`isTooManyPending()` check-then-act on plain queue sizes with no atomicity across `Wallet.broadcastTransaction` callers, and because `pushTransactionQueue` itself has no capacity bound, many concurrent gRPC/HTTP broadcasters can each pass the "not too many pending" check simultaneously (the count has not yet been incremented for in-flight requests) and add their (up to ~500 KiB) transactions to the unbounded queue before the count-based gate reacts. Worst case, the sustained resident set is on the order of `maxTransactionPendingSize × TRANSACTION_MAX_BYTE_SIZE` (2000 × 500 KiB ≈ 1 GB) of transaction payloads, entirely attacker-controlled and reachable by an ordinary, unprivileged transaction broadcaster — no validator/witness/SR privilege, no p2p-layer manipulation, no malicious peer required. This mirrors the Besu `FutureMessageBuffer` root cause: capacity accounting is done purely by item count, ignoring that items can vary hugely in byte size.

### Impact Explanation
A remote, unauthenticated API client (anyone who can call `broadcastTransaction` over gRPC/HTTP) can drive sustained heap growth on a full node / witness node by submitting a stream of maximally-sized transactions faster than they can be validated and drained. This can exhaust JVM heap, trigger long GC pauses, or crash the process (`OutOfMemoryError`), degrading or halting the node's ability to serve API requests and participate in block production — a node crash/halt/DoS matching the "Medium" criteria in the validation rubric (an API the node can no longer serve).

### Likelihood Explanation
Likelihood is moderate-to-high: `broadcastTransaction` is a normal, unauthenticated entry point used by any wallet/dApp; building syntactically valid, signature-bearing transactions with a large `data` field or many/large contract parameters up to just under 500 KiB requires no special access. The only friction is having enough transactions in flight (or enough concurrent connections) to exceed the intended 2000-item cap's byte budget before the count-based check catches up, which is easily achieved with a handful of concurrent client connections.

### Recommendation
Track total buffered byte size across `pushTransactionQueue`, `pendingTransactions`, and `rePushTransactions` (e.g., sum of `TransactionCapsule` serialized sizes) and enforce a byte-based admission budget in `isTooManyPending()`/`getCachedTransactionSize()`, in addition to (or instead of) the raw count check. Additionally, perform the `TRANSACTION_MAX_BYTE_SIZE` check (`validateCommon`) before enqueueing into `pushTransactionQueue`, not after, so oversized transactions are rejected prior to occupying queue memory, and consider giving `pushTransactionQueue` an explicit bounded capacity consistent with the configured byte budget.

### Proof of Concept
1. Craft N (e.g., 2000) syntactically-valid, individually-signed transactions, each with `raw.data` (or bulky contract parameters) sized close to `TRANSACTION_MAX_BYTE_SIZE` (500 KiB), so each stays just under the limit enforced in `Manager.validateCommon` [5](#0-4) .
2. Open multiple concurrent gRPC/HTTP connections and call `broadcastTransaction` for all N transactions in quick succession, faster than the single-threaded `transactionLock`-guarded `processTransaction` path can drain them [7](#0-6) .
3. Because `isTooManyPending()` only compares counts and `pushTransactionQueue` has no capacity bound, transactions accumulate in `pushTransactionQueue` while awaiting `validateSignature`/lock acquisition, each holding up to ~500 KiB in memory [1](#0-0) .
4. Observe node heap usage climbing toward the theoretical bound (`maxTransactionPendingSize × TRANSACTION_MAX_BYTE_SIZE` ≈ 1 GB with default config), leading to GC pressure/OOM and degraded API responsiveness.
