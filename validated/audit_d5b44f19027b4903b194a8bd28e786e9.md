### Title
Out-of-bounds read in singlejar's Zip64 extra-field accessors due to unchecked attribute index - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`singlejar` (Bazel's Java archive combiner, invoked as an action for every multi-source `java_library`/`java_binary` build and when merging jars pulled in via `http_jar`/`http_archive`/Maven-fetched dependencies) parses Central Directory Headers (`CDH`) and Local Headers (`LH`) directly out of memory-mapped, attacker-influenced jar files. When a 32-bit size/offset field is `0xFFFFFFFF`, the code falls back to reading a corresponding 64-bit value from the Zip64 extra field via `Zip64ExtraField::attr64(index)`.

### Finding Description
`Zip64ExtraField::attr64(int index)` performs a raw, unchecked array read: `return le64toh(attr_[index]);` [1](#0-0) . Nothing in this accessor validates `index` against `attr_count()` (`payload_size() / sizeof(attr_[0])`), which is itself derived entirely from the attacker-controlled `payload_size` field of the extra-field header.

Multiple callers compute the index from other attacker-controlled 32-bit fields without verifying that the actual extra field is large enough to contain that many 64-bit attributes:
- `LH::compressed_file_size()`/`uncompressed_file_size()` call `z64->attr64(1)` / `z64->attr64(0)` whenever the corresponding 32-bit field is `0xFFFFFFFF`, with no check that the found Zip64 field actually has 2 attributes [2](#0-1) .
- `CDH::compressed_file_size()` selects `attr64(0)` or `attr64(1)` based on whether the uncompressed size also needs 64-bit extension, again without checking `attr_count()` [3](#0-2) .
- `CDH::local_header_offset()` computes `attr_no` (0, 1, or 2) from two separate 32-bit fields and passes it straight into `attr64(attr_no)`, with no bound check against the field's real size [4](#0-3) .

The Zip64 extra field itself is located via `ExtraField::find`, which does perform bounds checking to ensure the *tag header + declared payload_size* fits within the declared `extra_fields_length()` region [5](#0-4) . However, that check only guarantees the field's *declared* payload fits — it does not guarantee the declared `payload_size` (and thus `attr_count()`) is large enough for the specific attribute index the caller wants to read. An attacker can craft a CDH/LH where a 32-bit size/offset field is `0xFFFFFFFF` (signaling "read from Zip64 extra field") but the accompanying Zip64 extra field only declares `payload_size = 8` (one 8-byte attribute), while the calling code (e.g. `CDH::local_header_offset()` needing `attr_no = 2`) reads `attr_[2]`, 16 bytes past the end of the declared/allocated extra-field payload — an out-of-bounds read within (or beyond) the memory-mapped input jar.

This is structurally analogous to the FreeRDP ADPCM bug: a decoder trusts an attacker-supplied index/selector (predictor/step_index in FreeRDP; the computed Zip64 attribute index here) to dereference an array without validating it against the actual available data size.

### Impact Explanation
This is a heap/mmap out-of-bounds read reachable purely by supplying a maliciously crafted `.jar`/`.zip` file that ends up as an input to the `singlejar` action — e.g., a jar fetched via `http_jar`/`http_archive` (with or without a passing `sha256`, since the corruption is in header interpretation, not archive integrity) or a jar produced from an untrusted-branch CI build that another target depends on and that `singlejar` subsequently merges. The read is out-of-bounds relative to the logical extra-field payload and can run past the mapped file region for entries near the end of the mapping, leading to a crash (denial of the build, but per the scope note DoS alone isn't the target) or leaking adjacent heap/mmap memory bytes into the computed offset/size values, which are then used for further pointer arithmetic (e.g., `LocalHeader()` dereferencing `mapped_file_.address(cdh->local_header_offset() + preamble_size_)`), potentially cascading into further out-of-bounds reads or corrupted output.

### Likelihood Explanation
Likelihood is moderate-high: `singlejar` is invoked automatically on essentially every non-trivial Java build action, and any jar that flows into that merge (including third-party fetched dependencies) is untrusted input from Bazel's own worker binary's point of view. No special build configuration or flags are needed — this triggers with default Bazel flags whenever a crafted jar is merged.

### Recommendation
In `Zip64ExtraField::attr64(int index)` (and at each call site), validate `index < attr_count()` before dereferencing `attr_[index]`, and treat a Zip64 field lacking sufficient declared attributes as malformed input (fail the build with a diagnostic, similar to the existing `diag_errx` malformed-extra-field handling elsewhere in `output_jar.cc`), rather than performing the raw pointer-indexed read.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style reproduction:
1. Hand-craft a minimal ZIP/jar with one entry whose CDH has `compressed_file_size32 = 0xFFFFFFFF` and `uncompressed_file_size32 = 0xFFFFFFFF` (forcing use of the Zip64 path) and `local_header_offset32 = 0xFFFFFFFF`, but attach a Zip64 extra field with `payload_size = 8` (only one 64-bit attribute, per `CDH::local_header_offset()`'s logic this requires `attr_no` up to 2, i.e., 3 attributes / 24 bytes).
2. Place this crafted entry at (or near) the very end of the memory-mapped input file so the out-of-bounds read at `attr_[2]` extends past the mapping.
3. Feed this jar as an input (`--sources`) to the `singlejar` binary (`src/tools/singlejar:singlejar`) or via a `java_library` depending on such a crafted jar.
4. Run under AddressSanitizer/Valgrind to observe the heap/mmap out-of-bounds read in `Zip64ExtraField::attr64`, confirming the vulnerability triggers a memory-safety violation during normal `singlejar` execution with default flags.

(Note: I was unable to fully trace every call site inside `output_jar.cc` where `cdh->local_header_offset()`/`compressed_file_size()`/`uncompressed_file_size()` are invoked during input-jar processing due to iteration limits — the grep confirmed at least one direct usage in `output_jar.cc` and extensive test coverage referencing these accessors, but I could not enumerate the complete call graph before running out of tool calls.)

                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
