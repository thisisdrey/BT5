### Title
Attacker can grief a leveraged account by dust-filling its 30-token account list via `deposit(amount, onBehalfOf)`, blocking all new collateral deposits needed to avoid liquidation - ([File: contracts/Pool.sol])

### Summary
`DepositToken.deposit` accepts an arbitrary `onBehalfOf_` beneficiary and `_mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance goes from 0 to non-zero. `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER (30)`. An unprivileged attacker can deposit 1 wei (or a few wei) of every registered deposit token `onBehalfOf` a victim, permanently occupying all 30 account-list slots. Because an account carrying debt cannot remove the dust entries once its position is stressed (`unlockedBalanceOf` returns 0 → `transfer`/`withdraw` revert via `_revertIfLocked`), the victim is unable to deposit any new collateral type to restore health and is pushed into unavoidable liquidation.

### Finding Description
- `Pool.MAX_TOKENS_PER_USER = 30` and the `onlyIfAdditionWillNotReachMaxTokens` modifier guard `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` (`contracts/Pool.sol:79`, `contracts/Pool.sol:143-148`, `contracts/Pool.sol:216-220`).
- `DepositToken.deposit(amount_, onBehalfOf_)` mints to an arbitrary beneficiary (`contracts/DepositToken.sol:211-237`); `_mint` adds the token to the recipient's account list when their prior balance was 0 (`contracts/DepositToken.sol:485-488`).
- Removal only happens when the balance returns to 0 via `_transfer`/`_burn` (`contracts/DepositToken.sol:460-462`, `522-525`), and both `transfer` and `withdraw` require `unlockedBalanceOf >= amount` (`contracts/DepositToken.sol:350`, `409`).
- `unlockedBalanceOf` returns `balance` only when `_debtInUsd == 0`; otherwise it is bounded by the free issuable capacity, which is 0 for a position at/below the collateralization limit (`contracts/DepositToken.sol:383-398`).

Attack path (all public, unprivileged):
1. Victim opens a leveraged position (deposits collateral X, mints synths) — occupies 1 deposit slot + ≥1 debt slot.
2. Attacker calls `depositToken_i.deposit(1, victim)` for every other registered deposit token until victim's combined list length hits 30. Each call mints dust to the victim and adds the token to `depositTokensOfAccount[victim]`; the attacker only pays dust amounts of underlying.
3. Market moves against the victim (or attacker pushes price via a same-transaction oracle-manipulable venue, not required): `_issuableInUsd` → 0, so `unlockedBalanceOf(victim) == 0` on every deposit token.
4. Victim cannot transfer out the dust (`NotEnoughFreeBalance`), cannot withdraw it, and any `deposit`/`transfer`/`seize`/`mint` that would add a new token reverts `UserReachedMaxTokens`. The victim therefore cannot deposit new collateral to deleverage and is force-liquidated. Even a rescue attempt by a third party (`deposit` `onBehalfOf` victim with a new collateral) reverts.

### Impact Explanation
The victim's account is DoS'd: all routes to add collateral (`DepositToken.deposit` on any not-yet-held collateral, `transfer`/`transferFrom` of msdTokens, `seize`) revert. If the position is or becomes unhealthy, liquidation is guaranteed because self-healing via new collateral is impossible — the victim loses collateral to liquidator incentive + protocol fee that they could otherwise have avoided. This is temporary/permanent freezing of the deposit path leading to direct loss of collateral value, matching the DoS bug class of CVE-2022-21625.

### Likelihood Explanation
- Cost to attacker: dust deposits (a few wei) of each registered collateral; requires the pool to have enough deposit tokens registered to fill 30 slots minus the victim's existing entries (Metronome pools list many collaterals; the attacker can combine deposit-token dust with debt-token entries the victim already holds).
- No privileged role, governance action, oracle malfunction, or malicious contract is needed — only public `deposit` calls.
- The griefing is most effective against accounts already near the collateralization boundary, but it can also be applied preemptively to any leveraged account.

### Recommendation
- Do not add a deposit token to an account's list for economically insignificant amounts (enforce a minimum deposit/`minBalance` threshold for list insertion), or
- Allow anyone to remove a zero-value dust token from their list (e.g., a `sweep`/`forceRemove` for balances below a threshold), or
- Exclude `onBehalfOf_ != msg.sender` dust additions, or raise/remove the hard cap and bound iteration gas another way, or
- Let `unlockedBalanceOf` always leave a small transferable allowance so users can clear dust entries.

### Proof of Concept
Hardhat test sketch (fork or fixtures as in `test/Pool.test.ts`):

```ts
// Pool.test.ts — griefing scenario
it('griefs a leveraged victim by filling the 30-token account list', async function () {
  // given: alice deposits MET and mints msETH (healthy but levered)
  // alice now has 1 deposit token + 1 debt token in her account lists

  // when: attacker dust-deposits every other deposit token to alice
  for (const dt of allDepositTokensExceptMsMET) {
    await underlying(dt).mint(attacker.address, 1n)
    await underlying(dt).connect(attacker).approve(dt.address, 1n)
    await dt.connect(attacker).deposit(1n, alice.address) // mints dust to alice
  }
  expect(await pool.getDepositTokensOfAccount(alice.address)).lengthOf(30 - debtCount)

  // price drops so alice has no free capacity
  await masterOracle.updatePrice(met.address, stressedPrice)
  const { _issuableInUsd } = await pool.debtPositionOf(alice.address)
  expect(_issuableInUsd).eq(0)

  // then 1: alice cannot transfer out the dust to free a slot
  await expect(
    someDepositToken.connect(alice).transfer(attacker.address, 1n)
  ).revertedWithCustomError(someDepositToken, 'NotEnoughFreeBalance')

  // then 2: no one can deposit a new collateral type for alice
  await expect(
    newDepositToken.connect(attacker).deposit(1_000n, alice.address)
  ).revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // then 3: alice is liquidated
  await pool.connect(liquidator).liquidate(msEth.address, alice.address, repayAmt, msdMET.address)
})
```

Key assertions: `deposit(..., onBehalfOf=victim)` inserts into `depositTokensOfAccount[victim]` (`DepositToken._mint` → `Pool.addToDepositTokensOfAccount`), the 30-slot cap reverts further additions (`UserReachedMaxTokens`), and dust entries cannot be removed once `unlockedBalanceOf` is 0 because `_revertIfLocked` blocks `transfer`/`withdraw`.
