### Title
Unbounded array allocation from attacker-controlled length in TVM precompile ABI decoding leads to Denial of Service - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `fast-string-search` advisory describes a crash/DoS caused by trusting attacker-supplied length/type data without validation before performing a memory operation. The closest reachable analog in java-tron is the ABI-array decoding helpers used by precompiled contracts, where an attacker-controlled 256-bit word is converted to a Java `int` and used directly to size a new array, without an upper bound check relative to available call data or energy already charged.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java` read a length field directly from caller-controlled `DataWord[] words` (decoded from the precompile call's input `data`) and use it to allocate a Java array: [1](#0-0) 

```java
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  ...
```

`len` comes from `words[offset].intValueSafe()`, i.e. a value fully controlled by the caller of a smart contract that invokes this precompile via `TriggerSmartContract`. There is no check that `len` is bounded by the actual size of `data`/`words`, nor by a sane maximum relative to the energy already charged for the call. A value close to `Integer.MAX_VALUE` (or any large but valid non-negative int) will cause the JVM to attempt to allocate a very large `byte[][]` object array, which can throw `OutOfMemoryError` or consume excessive heap/CPU during allocation before any subsequent loop iteration would fail. The nearly-identical `extractSigArray` has the same unguarded `len` usage.

### Impact Explanation
An `OutOfMemoryError` thrown inside VM execution can, depending on where and how it propagates, destabilize the node process (heap exhaustion affecting the whole JVM, not just the single transaction's sandboxed execution), which can crash the node or cause it to stop serving requests — matching the "node crash or halt" / "API the node can no longer serve" criteria for a valid finding under CWE-400 (Uncontrolled Resource Consumption), analogous to the segfault/DoS behavior in the `fast-string-search` advisory where untrusted length/type input is trusted for a low-level memory operation.

### Likelihood Explanation
Reachable by any account that can broadcast a `TriggerSmartContract` transaction calling the relevant precompiled contract address with crafted calldata; no special privileges are required. However, I could not confirm within the available search results whether the calling precompile (e.g., `BatchValidateSign`) performs an upstream length/energy check on `data.length` before calling `extractBytesArray`/`extractSigArray`, which would mitigate or eliminate this issue. This uncertainty should be resolved by inspecting `PrecompiledContracts.BatchValidateSign` (or whichever precompile consumes these helpers) end-to-end, including its `getEnergyForData` and `execute` methods.

### Recommendation
- Add an explicit upper bound check on `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, rejecting or clamping lengths that exceed what is structurally possible given `words.length`/`data.length`.
- Ensure the caller of these helpers (whichever precompile that is) validates `data.length` and derives `len` bounds from it before allocation, and charges energy proportional to `len` before allocating memory, consistent with how `EnergyCost.checkMemorySize` gates TVM memory expansion elsewhere in `actuator/src/main/java/org/tron/core/vm/EnergyCost.java`.

### Proof of Concept
Exact reproduction requires confirming the calling precompile's dispatch and energy metering, which I was unable to fully trace in this session. Conceptually: craft a `TriggerSmartContract` transaction that calls the precompiled contract address consuming `extractBytesArray`/`extractSigArray`, setting the length word (`words[offset]`) to a large value (e.g., `0x7FFFFFFF`) while providing minimal actual calldata, and observe whether the resulting `new byte[len][]` allocation throws `OutOfMemoryError` or otherwise consumes disproportionate resources relative to the energy charged.

Given the unresolved uncertainty about upstream validation, this finding should be treated as a lead requiring confirmation of the full call path (`getContractForAddress` → specific `PrecompiledContract.execute` → `extractBytesArray`/`extractSigArray`) rather than a fully proven vulnerability.
