## Finding

### Title
Bounty/child-bounty payout transfers are only checked with `debug_assert!`, allowing permanent loss of bounty funds on transfer failure - (File: `substrate/frame/bounties/src/lib.rs`, `substrate/frame/child-bounties/src/lib.rs`)

### Summary
The external report describes a class of bug where a value-transfer call (`_sendValue`) can revert, yet the surrounding code advances accounting state as if it succeeded, permanently losing the client's funds. The exact same broken invariant exists in `pallet-bounties::claim_bounty` and `pallet-child-bounties::claim_child_bounty`: both pallets perform the final `Currency::transfer` calls to the curator and beneficiary and validate the result only with `debug_assert!`, then unconditionally delete the bounty record from storage regardless of whether the transfer actually succeeded.

### Finding Description
In `claim_bounty`, the fee and payout transfers are checked like this: [1](#0-0) 

```rust
let res = T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
debug_assert!(res.is_ok());
let res = T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
debug_assert!(res.is_ok());

*maybe_bounty = None;
```

`debug_assert!` compiles to a no-op in release/production builds (the standard build profile used for on-chain WASM runtimes), so if either `Currency::transfer` call returns an `Err` (e.g. `TokenError::Frozen` because the destination account has a lock/hold/freeze from an unrelated pallet, insufficient consumer/provider bookkeeping, or any other `Currency`/`fungible` implementation restriction), execution continues exactly as on the success path: the bounty record is deleted (`*maybe_bounty = None`), `BountyDescriptions` is removed, `ChildBountyManager::bounty_removed` is invoked, and a `BountyClaimed` event is emitted reporting the payout as if it happened.

The identical pattern exists in `claim_child_bounty`: [2](#0-1) 

Because `bounty_account_id(bounty_id)` / `child_bounty_account_id(...)` are deterministic sub-accounts derived solely from the (now-deleted) bounty index, once the storage record is removed there is no remaining extrinsic path to reference or retry payment from that account. Any residual balance left behind by a failed transfer becomes permanently unreachable — functionally identical to the reported case where `s_validatorData.collateralReturnedCount` advances despite `_sendValue` failing, causing the collateral to be lost/misaccounted.

This pattern was in fact already recognized and fixed in the newer `pallet-multi-asset-bounties`, which uses a `Paymaster` abstraction with an explicit `PaymentState::{Attempted, Failed, Succeeded}` state machine and a `retry_payment`/`check_status` flow instead of assuming success: [3](#0-2) 

`pallet-bounties`/`pallet-child-bounties`, however, remain in active production runtimes: [4](#0-3) [5](#0-4) 

and the legacy assumption ("should not fail") is not actually guaranteed by `Currency::transfer`'s contract — `AllowDeath` avoids the "would-kill-the-account" failure mode but does not prevent failures from freezes/locks/holds on the *destination* account: [6](#0-5) 

### Impact Explanation
If the beneficiary or curator account has any balance restriction (a lock from `pallet-vesting`, a freeze from staking/nomination-pools, a hold from another pallet, or any `Currency`/`fungible` implementation enforcing extra invariants) at the moment `claim_bounty`/`claim_child_bounty` executes, the payout transfer silently fails in production, but the bounty is deleted anyway and a success event is emitted. The residual funds sitting in the deterministic bounty sub-account become permanently stranded with no bounty record left to reference them — a permanent loss of treasury-sourced/bounty funds, matching the "permanent user-fund lock" impact category.

### Likelihood Explanation
The trigger does not require a malicious validator, collator, relayer, or privileged actor — any signed account can call `claim_bounty`/`claim_child_bounty` once the bounty reaches `PendingPayout`, and the beneficiary address is chosen earlier by the curator via `award_bounty`, which is not restricted from pointing to accounts with existing locks/freezes/holds from unrelated pallets. This makes the failure path reachable through ordinary account state rather than requiring privileged conditions.

### Recommendation
Replace the `debug_assert!`-guarded transfers with proper `?`-propagated `Result` handling (or adopt the `Paymaster`/`PaymentState` retry pattern already implemented in `pallet-multi-asset-bounties`) before mutating/removing bounty storage, so that a failed transfer aborts the extrinsic (or transitions to a retryable failed state) instead of silently deleting the bounty record.

### Proof of Concept
1. Curator calls `award_bounty(bounty_id, beneficiary)` where `beneficiary` is an account that currently holds a lock/freeze (e.g., from `pallet-vesting`, `pallet-nomination-pools`, or a custom hold) large enough that the account's transferable balance is less than the required minimum after receiving the payout, or that otherwise causes `Currency::transfer` to return `TokenError::Frozen`/`FundsUnavailable`.
2. After the payout delay elapses, anyone calls `claim_bounty(bounty_id)`.
3. `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err`; in a release build `debug_assert!(res.is_ok())` is compiled out and does nothing.
4. Execution continues: `*maybe_bounty = None`, `BountyDescriptions` removed, `BountyClaimed` event emitted with `payout` as if paid.
5. The bounty's residual balance remains in `bounty_account_id(bounty_id)`, but since the bounty index no longer exists in storage, no further extrinsic (`claim_bounty`, `close_bounty`, etc.) can reference or recover it — the funds are permanently locked/lost.

	/// Queries the status of the payment from the child-/bounty to the beneficiary account/location
	/// and returns a new payment status.
	fn do_check_payout_payment_status(
		parent_bounty_id: BountyIndex,
		child_bounty_id: Option<BountyIndex>,
		asset_kind: T::AssetKind,
		value: T::Balance,
		beneficiary: T::Beneficiary,
		payment_status: PaymentState<PaymentIdOf<T, I>>,
	) -> Result<PaymentState<PaymentIdOf<T, I>>, DispatchError> {
		let payment_id = payment_status.get_attempt_id().ok_or(Error::<T, I>::UnexpectedStatus)?;

		match <T as pallet::Config<I>>::Paymaster::check_payment(payment_id) {
			PaymentStatus::Success => {
				let payout = Self::calculate_payout(parent_bounty_id, child_bounty_id, value);

				Self::deposit_event(Event::<T, I>::BountyPayoutProcessed {
					index: parent_bounty_id,
					child_index: child_bounty_id,
					asset_kind: asset_kind.clone(),
					value: payout,
					beneficiary,
				});

				Ok(PaymentState::Succeeded)
			},
			PaymentStatus::InProgress | PaymentStatus::Unknown =>
			// nothing new to report
			{
				Err(Error::<T, I>::PayoutInconclusive.into())
			},
			PaymentStatus::Failure => {
				// assume payment has failed, allow user to retry
				Self::deposit_event(Event::<T, I>::PaymentFailed {
					index: parent_bounty_id,
					child_index: child_bounty_id,
					payment_id,
				});
				Ok(PaymentState::Failed)
