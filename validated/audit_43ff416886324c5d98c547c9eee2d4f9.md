Audit Report

## Title
`ERC20Transactor` credits/debits the XCM holding register with the nominal transfer amount instead of the actual ERC20 balance delta, allowing fee-on-transfer/rebasing ERC20 assets to drain or lock the shared checking account - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

## Summary
`withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in `ERC20Transactor` move ERC20 tokens by calling `IERC20::transfer` and, on a non-reverting call that decodes to `true`, unconditionally credit/debit the XCM holding register with the nominal `amount` requested rather than the actual balance delta observed on the shared `TransfersCheckingAccount`. Any ERC20 contract callable through `pallet-revive` and reachable via the permissionless `ERC20Matcher` (which matches on any `AccountKey20` location, i.e. any contract address, with no admin whitelist) can implement non-1:1 transfer semantics (fee-on-transfer, rebasing) to desynchronize the XCM-holding accounting from the real on-chain balance of the single shared checking account, enabling fund lock or theft against other users' in-flight transfers of that asset.

## Finding Description
`withdraw_asset_with_surplus` builds an `IERC20::transferCall` moving `amount` from the withdrawing user to `TransfersCheckingAccount`, and on success unconditionally credits `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — the nominal amount, not a measured delta. [1](#0-0) 

`deposit_asset_with_surplus` symmetrically transfers the same nominal `amount` out of `TransfersCheckingAccount` to the beneficiary, again trusting the boolean `transfer()` return value with no balance verification. [2](#0-1) 

Neither function calls `balanceOf` before/after the transfer to compute an actual delta; the only checks performed are `did_revert()` and decoding the boolean return value of `transferCall`, which say nothing about the magnitude actually moved. [3](#0-2) [4](#0-3) 

Critically, the asset-matching layer wired to this transactor, `ERC20Matcher`, is defined generically over any `AccountKey20`-junction location mapped directly to an `H160` contract address, with **no whitelist or governance-gated registry of approved tokens** in the matcher itself: [5](#0-4) 

This means any contract address expressible as an `AccountKey20` XCM location is treated as a valid fungible asset for this transactor, and — assuming it is reachable through the runtime's `AssetTransactors` tuple configuration — a user constructing an XCM program can pick an arbitrary `pallet-revive` contract as the "asset," including one they deploy themselves with fee-on-transfer or rebasing semantics. I was unable to fully verify within available tooling limits whether `asset-hub-westend`'s `xcm_config.rs` gates `ERC20Transactor`/`ERC20Matcher` behind an additional asset-specific filter beyond `IsLocalAccountKey20`, as the specific wiring lines in that file were not retrievable before the tool budget was exhausted; however, the transactor implementation and matcher definition themselves, which are the object of the claim, are confirmed as described.

Because `TransfersCheckingAccount` is a single shared account for every withdraw/deposit pair routed through this transactor, any accumulated mismatch between nominal credited amounts and the ERC20 contract's actual balance movements is not scoped per-user or per-message — it persists in the account's real on-chain balance and can be exploited or suffered by unrelated future transactions for the same asset.

## Impact Explanation
This matches the "theft or unbacked mint/unlock" and "permanent user-fund or bridge-state lock" impact categories from an unprivileged, public XCM execution entrypoint. If a fee-on-transfer or rebasing ERC20 is reachable as a matched asset (via `ERC20Matcher`'s unrestricted `AccountKey20`-to-`H160` matching), the real ERC20 balance of `TransfersCheckingAccount` diverges from the sum of nominal `Erc20Credit` amounts the runtime believes are backed, letting an attacker drain balance that other users' pending transfers rely on, or causing legitimate `deposit_asset_with_surplus` calls to fail and lock funds.

## Likelihood Explanation
Exploitability depends entirely on whether the deployed asset-hub configuration allows arbitrary/user-deployable contracts to be matched by this transactor versus restricting it to a small set of vetted, standard-compliant tokens through additional runtime-level filtering not present in the transactor or matcher code itself. The `ERC20Matcher` definition shown provides no such restriction, and `pallet-revive` is generally permissionless for contract deployment, so the underlying transactor logic contains the flaw as described; full confirmation of exploitability in `asset-hub-westend` specifically requires verifying the exact `AssetTransactors`/filter wiring in that runtime's `xcm_config.rs`, which could not be completed with the remaining tool budget.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `IERC20::balanceOf` on `TransfersCheckingAccount` (and relevant source/destination accounts) immediately before and after the `transfer()` call, and credit/debit the `AssetsInHolding` register with the measured delta rather than the nominal `amount`. Reject transfers where the delta does not match the requested amount within acceptable rounding, and/or restrict the asset matcher to a governance-curated allowlist of standard-compliant ERC20 contracts.

## Proof of Concept
1. Deploy a `pallet-revive` ERC20 contract `X` whose `transfer()` deducts a fee, so `balanceOf(recipient)` increases by less than `value`.
2. Construct an XCM program via `pallet_xcm::execute` containing `WithdrawAsset` for `X` amount `A` from account Alice, followed by `DepositAsset` to Bob for the same nominal amount `A`, using an `AccountKey20` location for `X` matched by `ERC20Matcher`.
3. `withdraw_asset_with_surplus` transfers `A` to `TransfersCheckingAccount`; the checking account's actual balance increases by `A - fee`, but the XCM holding register is credited with `Erc20Credit(A)` (see `erc20_transactor.rs:197-203`).
4. `deposit_asset_with_surplus` then attempts to transfer the full nominal `A` from the checking account to Bob (see `erc20_transactor.rs:253-266`); this either fails (locking Alice's withdrawn funds and Bob's expected deposit) or succeeds by consuming residual balance belonging to another user's pending transfer through the same shared checking account, depending on the checking account's aggregate real-vs-nominal balance state at that time.
