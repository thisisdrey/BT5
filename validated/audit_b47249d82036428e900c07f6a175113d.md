### Title
Missing EIP-170 Contract Code Size Limit Allows Unbounded Contract Bytecode via CREATE/CREATE2 - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
java-tron has no protocol-level limit on the size of deployed smart-contract bytecode analogous to Ethereum's EIP-170 24KB cap. The only size gate applied to a `CreateSmartContract` transaction is `Constant.TRANSACTION_MAX_BYTE_SIZE` (500KB) checked in `Manager.validateCommon()`, which limits the *serialized transaction/input* size — not the code actually returned by contract-creation execution and persisted via `saveCode`. For internal `CREATE`/`CREATE2` calls (`Program.createContractImpl`), there is no transaction-size check at all; the returned `programCode` length is bounded only by available energy.

### Finding Description
In Ethereum post-Spurious-Dragon, any code returned by contract-creation init code longer than `0x6000` (24576) bytes causes the creation to fail with an out-of-gas error (EIP-170). java-tron's contract creation paths — the top-level `VMActuator.create()`/`end()` for `CreateSmartContract` transactions, and `Program.createContractImpl()` for internal `CREATE`/`CREATE2` — never check `code.length` (or `getLength(code)`) against any maximum before calling `rootRepository.saveCode(...)` / `deposit.saveCode(...)`. The only checks performed are: (1) an energy check ensuring `afterSpend >= 0` where `saveCodeEnergy = getLength(code) * EnergyCost.getCreateData()`, and (2) for London-fork compatibility, a check that the first code byte isn't `0xEF`. Neither enforces a hard byte-size ceiling.

Separately, `Manager.validateCommon()` enforces `Constant.TRANSACTION_MAX_BYTE_SIZE` (500 * 1024 bytes) on the whole serialized transaction — this bounds the *initcode/input* supplied in the top-level deployment transaction, not the bytecode that ends up stored as the contract's code (which can differ from initcode length, and is entirely unconstrained for internal creations triggered by contract execution, since those have no associated "transaction size" to check at all).

This mirrors the reported POSDAO bug exactly: a transaction-size/input-length limit is conflated with (and is not a substitute for) an actual deployed-code-size limit.

### Impact Explanation
Any account or contract with sufficient TRX to cover `feeLimit`/energy can deploy or have deployed (via `CREATE`/`CREATE2`) a contract whose stored bytecode is arbitrarily large, up to whatever energy/fee it is willing to pay — there is no 24KB (or any other) hard limit. This can be leveraged to store oversized contract code in state, growing the on-disk state database and per-account code storage without the protocol-level ceiling other EVM-compatible chains rely on to bound state growth from a single call. It does not directly cause fund theft, but is a state-bloat / potential DoS-adjacent design gap reachable by any ordinary contract-deployer via a single signed transaction.

### Likelihood Explanation
High — Any user can trigger this today via `wallet/deploycontract`, `eth_sendTransaction`-style JSON-RPC contract creation, or a factory contract executing `CREATE`/`CREATE2` with an init code that returns large runtime bytecode, so long as they pay the linear `saveCodeEnergy` cost. No special privileges are required.

### Recommendation
Add an explicit maximum deployed-code-length check (e.g. mirroring EIP-170's 24576-byte limit, or a chain-appropriate constant) in both `VMActuator.end()`/`create()` (top-level `CreateSmartContract` path) and `Program.createContractImpl()` (internal `CREATE`/`CREATE2` path), rejecting/reverting the creation (setting an exception on `ProgramResult`/`createResult`) whenever `code.length` exceeds the limit, independent of and in addition to the existing energy-based cost check and the unrelated `Constant.TRANSACTION_MAX_BYTE_SIZE` transaction-size check.

### Proof of Concept
1. Craft a `CreateSmartContract` transaction (or a factory contract calling `CREATE`/`CREATE2`) whose init code, when executed, returns a `HReturn` byte array larger than 24576 bytes (e.g. 100KB of valid opcode padding/`STOP` bytes).
2. Set `fee_limit`/`origin_energy_limit` high enough to cover `saveCodeEnergy = code.length * EnergyCost.getCreateData()`.
3. Broadcast via `wallet/deploycontract` (`DeployContractServlet`) or trigger the factory's `deploy` function via `wallet/triggersmartcontract`.
4. Observe the transaction succeeds and `rootRepository.saveCode(contractAddress, code)` / `deposit.saveCode(newAddress, code)` persists code far exceeding the EIP-170 24KB bound, with no `ContractValidateException`/`BytecodeExecutionException` thrown for code size.
