### Title
Unvalidated attacker-controlled length fields in TVM precompile ABI decoding cause out-of-bounds array access / allocation - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The external CVE describes a heap/stack buffer overflow in `oggvideotools` caused by trusting an attacker-controlled length field from a crafted file when copying data, without validating it against the actual buffer size. The analogous bug class in java-tron is precompiled-contract input decoding that reads attacker-controlled 32-byte "length"/"offset" words from the `data` payload of a TVM `CALL`/`STATICCALL` to a precompile address and uses them directly to size array allocations and to compute byte-copy offsets, without bounding them against the real payload size.

### Finding Description
Several helper routines in `PrecompiledContracts.java` decode ABI-style dynamic arrays out of the raw calldata passed into a precompile (reachable by any account issuing a TVM call, e.g. to the `ValidateMultiSign`/`BatchValidateSign` precompile addresses): [1](#0-0) 

`extractBytes32Array` and `extractBytesArray` take `len` directly from `words[offset].intValueSafe()` — a value fully controlled by the caller's calldata — and immediately allocate `new byte[len][]` and index into `words[]`/`data[]` using derived offsets, without checking `len` against `words.length` or `data.length`: [2](#0-1) 

`extractSigArray` has the identical pattern: `len` is read unchecked from the caller-supplied word, and `extractBytes` then does `Arrays.copyOfRange(data, offset, offset + len)` where `offset`/`len` are attacker-derived and unbounded.

Separately, `VerifyTransferProof.execute()` parses several offset/length fields (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`, `spendCount`, `receiveCount`) directly from precompile calldata via `parseInt`/`parseLong` and immediately uses them in `System.arraycopy` calls and array allocations: [3](#0-2) 

While `spendCount`/`receiveCount` are bounded to `[1,2]`, the raw `spendOffset`/`spendAuthSigOffset`/`receiveOffset` values are not range-checked before being used as array copy offsets, and negative or huge values will throw `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`.

### Impact Explanation
Unlike the C/C++ original (memory corruption / RCE), Java's bounds-checked arrays convert an out-of-bounds access into a runtime exception rather than silent memory corruption, which limits the severity considerably. In `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, a caller-supplied huge `len` causes `new byte[len][]` — this can throw `OutOfMemoryError`/`NegativeArraySizeException` before any bounds check occurs, since the code does not validate `len` against `words.length` prior to allocating. In `VerifyTransferProof`, the entire decode block is wrapped in `catch (Throwable any)` at lines 1433/1604, so any resulting exception is caught and logged, and execution safely falls back to returning a failed verification — this specific path does **not** crash the node or corrupt state.

I was not able to fully confirm, within the available context, whether `extractBytes32Array`/`extractBytesArray`/`extractSigArray` are similarly wrapped by a top-level `catch (Throwable)` in their caller (`ValidateMultiSign`/`BatchValidateSign` `execute()` methods) before I ran out of search iterations — this is the key open question. If those callers do **not** catch `OutOfMemoryError`/`NegativeArraySizeException`/`ArrayIndexOutOfBoundsException`, an attacker-crafted contract call data with an oversized `len` field could throw an uncaught error out of `execute()` during EVM execution, potentially destabilizing the node process (denial of service) rather than causing memory corruption.

### Likelihood Explanation
Reaching these code paths only requires deploying/calling a contract that invokes the `ValidateMultiSign`, `BatchValidateSign`, or shielded-transfer precompile addresses with crafted calldata — this is available to any unprivileged transaction broadcaster/contract deployer, matching the report's reachability requirement. However, without confirming the presence or absence of an enclosing `catch (Throwable)` in the immediate precompile `execute()` callers of `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, I cannot assert this reaches an unhandled-exception/crash outcome with confidence.

### Recommendation
Add explicit bounds validation of all length/offset words read from precompile calldata (`extractBytes32Array`, `extractBytesArray`, `extractSigArray`) against `words.length` and `data.length` before using them to size array allocations or as copy offsets, and ensure every precompile `execute()` implementation catches broad `Throwable`/`Error` (not just checked exceptions) around ABI-decoding logic, consistent with the pattern already used in `VerifyMintProof`/`VerifyTransferProof`.

### Proof of Concept
Not able to produce a concrete, verified end-to-end PoC within the available exploration budget — I could not confirm the exact `execute()` implementation(s) that call `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (their surrounding try/catch behavior) to determine whether an oversized `len` field actually propagates as an uncaught error. Given this unresolved uncertainty about exploitability/severity, I recommend treating this as a **candidate** finding requiring the missing verification step (locating the `ValidateMultiSign`/`BatchValidateSign` `execute()` bodies and their exception handling) before assigning a final severity rating.
