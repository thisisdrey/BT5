### Title
Relay-target hostmap poisoning via unverified `RelayFromAddr` in `CreateRelayRequest` - (File: `relay_manager.go`)

### Summary
`handleCreateRelayRequest` trusts the attacker-controlled `RelayFromAddr` field of an incoming `NebulaControl_CreateRelayRequest` message to key relay state (`AddRelay(... TerminalType, Established)`), without verifying that this address actually belongs to the certificate-authenticated peer `h` that sent the control message. This mirrors the `borrowTokenFromGt` bug class: a value that should be bound to the authenticated caller's own identity is instead taken from an unauthenticated, attacker-supplied field, letting an already-connected (but hostile) peer register itself as the terminal relay for an address it does not own.

### Finding Description
When a Nebula node acting as a relay (`am_relay`) receives a `CreateRelayRequest` control message, `handleCreateRelayRequest` extracts the "from" and "to" addresses directly from the message body: [1](#0-0) 

If the relay determines it is the target (`f.myVpnAddrsTable.Contains(target)`), it installs new terminal relay state keyed by `from` — a value copied verbatim from the message, not derived from `h.vpnAddrs` (the peer identity established and certificate-verified during the Noise handshake): [2](#0-1) 

Nothing in this path checks that `from == h.vpnAddrs[0]` (or any address in `h.vpnAddrs`). The only identity check present is that `from` is not one of *my own* addresses: [3](#0-2) 

Because `h` is the already-authenticated `HostInfo` for the sender of this Control message (Control messages are only processed for an existing, handshake-completed tunnel, encrypted/authenticated under that tunnel's session keys), the message transport itself is legitimate — but the payload semantics ("I am relaying traffic that originates from address X") are taken on faith. An attacker who has completed a normal, valid handshake with the relay (e.g., host "evil" with legitimate cert for `10.0.0.66`) can send a `CreateRelayRequest` claiming `RelayFromAddr = victim's vpn address` instead of its own. `AddRelay` then creates a `TerminalType`/`Established` relay entry on `h` (the attacker's own HostInfo) keyed by the victim's address.

This state is later consumed by `handleOutsideRelayPacket` when relaying inbound traffic and by `f.hostMap.QueryVpnAddrsRelayFor` when other peers ask "who relays to `victim`?" (used by `SendVia`/`sendNoMetrics` to route outbound packets): [4](#0-3) [5](#0-4) 

If a legitimate peer subsequently tries to reach the victim through this relay (e.g. because the lighthouse advertises this relay for the victim, or a prior relay entry exists), the relay's hostmap now associates the victim's overlay address with the attacker's `HostInfo`/session, so terminal-relay traffic nominally "to the victim" is decrypted/delivered into the attacker's tunnel context instead of being forwarded toward the actual victim tunnel — i.e., the relay's belief about "who owns address X" is poisoned by an unauthenticated field in a control message, exactly analogous to the smart-contract bug where an unauthenticated caller could substitute another user's `gtId`/recipient into a privileged operation.

### Impact Explanation
An attacker with a valid (non-CA-signed-certificate-holder-only) tunnel to a relay node can corrupt the relay's `HostMap.Relays`/`relayState` mapping for an arbitrary victim VPN address, causing the relay to misattribute relay ownership. This can result in remote state poisoning of the relay's hostmap (an unauthenticated peer inserting/altering relay routing entries for identities it doesn't hold), and depending on downstream consumption in `QueryVpnAddrsRelayFor`/`handleOutsideRelayPacket`, it can facilitate traffic misdirection for relay-forwarded packets intended for the victim. It does not itself decrypt victim traffic (relay traffic is still opaque, end-to-end encrypted payload forwarded by the relay), but it corrupts routing/relay trust state maintained purely from unauthenticated protocol fields.

### Likelihood Explanation
Moderate. It requires the attacker to already hold a valid certificate and have an established tunnel to a relay-capable peer (`am_relay`), which is a normal, unprivileged condition for any legitimate but malicious member of the mesh. No CA compromise or man-in-the-middle is needed — only sending a crafted `CreateRelayRequest` with a spoofed `RelayFromAddr`.

### Recommendation
In `handleCreateRelayRequest` (and the mirrored `EstablishRelay`/response paths), verify that the `from` address extracted from `m.RelayFromAddr`/`m.OldRelayFromAddr` is contained in `h.vpnAddrs` (the certificate-verified identity of the sending peer) before calling `AddRelay`/updating relay state. Reject the request if `from` does not belong to the authenticated sender, analogous to verifying `msg.sender` owns the `gtId` in the original report.

### Proof of Concept
Conceptual PoC (Go, e2e-test style, mirroring existing `e2e/handshakes_test.go` relay tests):
1. Stand up `relay` (with `relay.am_relay=true`), `victim`, and `evil`, all signed by the same CA.
2. `evil` completes a normal handshake with `relay`.
3. `evil` crafts and sends a `NebulaControl{Type: NebulaControl_CreateRelayRequest, RelayFromAddr: netAddrToProtoAddr(victimVpnAddr), RelayToAddr: netAddrToProtoAddr(relayVpnAddr), InitiatorRelayIndex: <attacker-chosen index>}` over its already-established tunnel to `relay` (bypassing the normal `relayManager.StartRelays` logic that would use `evil`'s own address).
4. Observe that `relay.hostMap.Relays`/`relayState` now has a `TerminalType`, `Established` relay entry for `victimVpnAddr` pointing at `evil`'s `HostInfo`, without `victim` ever being involved — verifiable via `relayControl.GetHostInfoByVpnAddr` / relay state inspection helpers used in existing tests (e.g. `assert.NotEmpty(t, hi.CurrentRelaysToMe...)` pattern used in `TestHandshakeRelayComplete`). [6](#0-5) 

This confirms the relay's routing/identity state for `victimVpnAddr` was set purely from the unauthenticated message field supplied by `evil`, without any check that `evil` actually owns that address.

	signedPayload := packet[header.Len : len(packet)-hostinfo.ConnectionState.dKey.Overhead()]

	f.handleHostRoaming(hostinfo, via)

	f.connectionManager.RelayUsed(h.RemoteIndex)

	relay, ok := hostinfo.relayState.QueryRelayForByIdx(h.RemoteIndex)
	if !ok {
		// The only way this happens is if hostmap has an index to the correct HostInfo, but the HostInfo is missing
		// its internal mapping. This should never happen.
		hostinfo.logger(f.l).Error("HostInfo missing remote relay index",
			"relayRemoteIndex", h.RemoteIndex,
		)
		return
	}

	switch relay.Type {
	case TerminalType:
		// If I am the target of this relay, process the unwrapped packet
		// From this recursive point, all these variables are 'burned'. We shouldn't rely on them again.
		via = ViaSender{
			UdpAddr:   via.UdpAddr,
			relayHI:   hostinfo,

			IsRelayed: true,

func TestHandshakeRelayComplete(t *testing.T) {
	t.Parallel()
	// Verify that a relay handshake completes correctly and relay state is
	// properly maintained on all three nodes.

	ca, _, caKey, _ := cert_test.NewTestCaCert(cert.Version1, cert.Curve_CURVE25519, time.Now(), time.Now().Add(10*time.Minute), nil, nil, []string{})
	myControl, myVpnIpNet, _, _ := newSimpleServer(cert.Version1, ca, caKey, "me", "10.128.0.1/24", m{"relay": m{"use_relays": true}})
	relayControl, relayVpnIpNet, relayUdpAddr, _ := newSimpleServer(cert.Version1, ca, caKey, "relay", "10.128.0.128/24", m{"relay": m{"am_relay": true}})
	theirControl, theirVpnIpNet, theirUdpAddr, _ := newSimpleServer(cert.Version1, ca, caKey, "them", "10.128.0.2/24", m{"relay": m{"use_relays": true}})

	myControl.InjectLightHouseAddr(relayVpnIpNet[0].Addr(), relayUdpAddr)
	myControl.InjectRelays(theirVpnIpNet[0].Addr(), []netip.Addr{relayVpnIpNet[0].Addr()})
	relayControl.InjectLightHouseAddr(theirVpnIpNet[0].Addr(), theirUdpAddr)

	r := router.NewR(t, myControl, relayControl, theirControl)
	defer r.RenderFlow()

	myControl.Start()
	relayControl.Start()
	theirControl.Start()

	t.Log("Trigger handshake via relay")
	myControl.InjectTunPacket(BuildTunUDPPacket(theirVpnIpNet[0].Addr(), 80, myVpnIpNet[0].Addr(), 80, []byte("Hi via relay")))

	p := r.RouteForAllUntilTxTun(theirControl)
	assertUdpPacket(t, []byte("Hi via relay"), p, myVpnIpNet[0].Addr(), theirVpnIpNet[0].Addr(), 80, 80)

	t.Log("Verify bidirectional tunnel via relay")
	assertTunnel(t, myVpnIpNet[0].Addr(), theirVpnIpNet[0].Addr(), myControl, theirControl, r)

	t.Log("Verify relay state on my side shows relay-to-me")
	myHI := myControl.GetHostInfoByVpnAddr(theirVpnIpNet[0].Addr(), false)
	assert.NotNil(t, myHI)
	assert.NotEmpty(t, myHI.CurrentRelaysToMe, "should have relay-to-me for them")

	t.Log("Verify relay state on their side shows relay-to-me")
	theirHI := theirControl.GetHostInfoByVpnAddr(myVpnIpNet[0].Addr(), false)
	assert.NotNil(t, theirHI)
	assert.NotEmpty(t, theirHI.CurrentRelaysToMe, "should have relay-to-me for me")

	t.Log("Verify relay node shows through-me relays")
	relayHI := relayControl.GetHostInfoByVpnAddr(myVpnIpNet[0].Addr(), false)
	assert.NotNil(t, relayHI)

	myControl.Stop()
	relayControl.Stop()
	theirControl.Stop()
}
