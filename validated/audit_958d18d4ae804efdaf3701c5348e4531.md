### Title
Unbounded array allocation from attacker-controlled ABI length in `ValidateMultiSign`/`BatchValidateSign` precompiles causes node OOM/DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
CVE-2017-11703 is a memory-exhaustion DoS caused by a parser trusting an attacker-supplied length field from a crafted file without bounding it against the actual buffer. The same bug class exists in java-tron's `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts: the signature/address array length is read directly from attacker-supplied calldata and used to allocate a Java array with no upper bound check unless a specific hard-fork flag is active, allowing an unprivileged contract caller to force a huge heap allocation.

### Finding Description
Both precompiles decode their ABI-encoded input into `DataWord[]` and then call `extractBytesArray`/`extractSigArray`, which read the array length straight from calldata: [1](#0-0) 

The length (`len`) is derived from `words[offset].intValueSafe()`, an attacker-controlled 256-bit calldata word coerced to an `int`, and is used immediately to size `new byte[len][]` with no upper bound. The only guard against an oversized value is gated behind a feature flag: [2](#0-1) 

When `VMConfig.allowTvmSelfdestructRestriction()` is `false`, the `sigArraySize > MAX_SIZE` check is skipped entirely and `extractBytesArray` is invoked directly with the attacker-controlled, unchecked length, so a value near `Integer.MAX_VALUE` triggers an attempt to allocate a multi-gigabyte `byte[][]` array (each element itself later allocated via `extractBytes`). The identical unguarded pattern also exists in `BatchValidateSign.doExecute`: [3](#0-2) 

This mirrors the CVE-2017-11703 root cause: a parser trusts a length field from untrusted input and allocates memory proportional to it without validating it against the real payload size, leading to memory exhaustion.

### Impact Explanation
Any account can invoke a smart contract that calls the `ValidateMultiSign` (or `BatchValidateSign`) precompiled contract with crafted calldata as long as `allowTvmSelfdestructRestriction` is not active for the chain in question (e.g., new/private/test networks running this codebase, or any chain where this specific hard fork proposal has not yet been approved by the SR committee). This can force the executing full node to attempt an extremely large heap allocation, resulting in `OutOfMemoryError`/JVM instability that halts block processing on the node — a denial-of-service impact consistent with the reachable-impact criteria (node crash/halt).

### Likelihood Explanation
Exploitation requires only a single contract call with crafted `CALLDATA` reaching the `ValidateMultiSign`/`BatchValidateSign` precompile address; no special privilege beyond broadcasting a normal contract-triggering transaction is needed. However, the exploitability is conditioned on `VMConfig.allowTvmSelfdestructRestriction()` being disabled, i.e. it depends on the current hard-fork/proposal activation status of the target network, which could not be conclusively determined for the current mainnet state from the available index (this is a chain-configuration/committee-controlled runtime flag, not a static code constant).

### Recommendation
Move the `sigArraySize`/`addrArraySize` bound check outside the `allowTvmSelfdestructRestriction()` gate so the length from calldata is always validated against `MAX_SIZE` (and against the real remaining `data.length`) before any array is allocated in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, regardless of hard-fork activation state.

### Proof of Concept
Craft a transaction invoking the `ValidateMultiSign` precompile (or a contract that delegates to it) with ABI-encoded input where the dynamic array's length word (at the offset referenced by `words[3]`) is set to a very large value (e.g., `0x7fffffff`). On a node where `allowTvmSelfdestructRestriction` is not enabled, `execute()` reaches `extractBytesArray(words, offset, rawData)` at [4](#0-3)  which attempts `new byte[Integer.MAX_VALUE][]`, exhausting node memory.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
