### Title
Integer overflow in legacy VOTEWITNESS energy-metering (`getVoteWitnessCost`/`getVoteWitnessCost2`) allows undercharged energy and memory-size bypass - ([File: actuator/src/main/java/org/tron/core/vm/EnergyCost.java])

### Summary
The `VOTEWITNESS` TVM opcode's energy-cost calculation has two implementations: the legacy `getVoteWitnessCost`/`getVoteWitnessCost2` (256-bit `DataWord` arithmetic) and a hardened `getVoteWitnessCost3` (BigInteger arithmetic, gated behind the not-yet-active `allowTvmOsaka` feature). The legacy path multiplies an attacker-controlled stack value by the 32-byte word size using `DataWord.mul()`, which operates modulo 2^256 and silently wraps instead of throwing on overflow, unlike the BigInteger path used in `getVoteWitnessCost3`.

### Finding Description
`getVoteWitnessCost` and `getVoteWitnessCost2` in `EnergyCost.java` compute the memory needed for the `amountArray`/`witnessArray` operands of the `VOTEWITNESS` opcode using `DataWord` (256-bit fixed width) multiplication: [1](#0-0) [2](#0-1) 

`amountArrayLength.mul(wordSize)` and `witnessArrayLength.mul(wordSize)` operate on `DataWord`, a 256-bit value that wraps around modulo 2^256 without any overflow signaling, so a maliciously large length supplied on the EVM stack (e.g. `0xFFFF...FFFF`) can wrap to a small value. This wrapped-small value is then fed into `memNeeded()`/`calcMemEnergy()`, which compares it against the 3MB `MEM_LIMIT`. Because the wrap makes the "needed memory" value look small, the memory-overflow guard (`checkMemorySize`) that should reject the operation is bypassed, and the opcode is charged normal, low energy.

This exact overflow was subsequently found and fixed by the project itself: `getVoteWitnessCost3` reimplements the same computation with `BigInteger` (no silent wraparound) specifically to "detect memory overflow via checkMemorySize" where the legacy `DataWord.mul()` path would wrap. This is explicitly confirmed by the project's own regression tests: [3](#0-2) 

However, `getVoteWitnessCost3` only replaces the legacy behavior when `VMConfig.allowTvmOsaka()` is enabled: [4](#0-3) 

If this hardfork switch is not yet active on the running network/version, the vulnerable legacy `DataWord`-based calculation (`getVoteWitnessCost`/`getVoteWitnessCost2`) remains the one actually wired into the opcode's energy cost via `OperationRegistry`/`JumpTable`, meaning any contract deployer/caller can reach it directly by invoking the `VOTEWITNESS` opcode with crafted stack operands.

### Impact Explanation
An attacker deploying and invoking a contract that triggers `VOTEWITNESS` with a maliciously large array-length operand can cause the energy-cost function to undercharge energy for a memory allocation that should have been rejected (`Program.Exception.memoryOverflow`). Downstream this can lead to:
- Energy metering bypass, letting a caller under-pay for large virtual memory footprint (breaks the "you pay for what you use" resource-accounting invariant enforced elsewhere via `calcMemEnergy`/`checkMemorySize`).
- If the wrapped value influences later actual memory expansion / native-contract execution reading array bounds, potential for excessive memory allocation / node resource exhaustion (denial-of-service) during transaction execution, matching the "integer overflow → DoS/information disclosure" bug class in the referenced CVE.

This falls into the Medium/High severity category as it affects the correctness of the resource-accounting/energy-metering system exercised by any unprivileged contract caller.

### Likelihood Explanation
Reachable by any account that can broadcast a `TriggerSmartContract` transaction invoking a contract with the `VOTEWITNESS` opcode — no special privilege required. The only gating condition is that `VMConfig.allowTvmOsaka()` is not yet enabled on the target node/chain; while this is active it uses the safe BigInteger path. Given the fix (`getVoteWitnessCost3`) is feature-flagged rather than universally applied, any deployment where the Osaka hardfork flag is off remains exposed.

### Recommendation
Backport the `BigInteger`-based, overflow-checked computation used in `getVoteWitnessCost3` into the always-active `getVoteWitnessCost`/`getVoteWitnessCost2` paths (or make the overflow-safe path unconditional rather than feature-flag gated), so the memory-overflow check cannot be bypassed via 256-bit wraparound regardless of hardfork activation state.

### Proof of Concept
1. Deploy a contract whose bytecode directly emits the `VOTEWITNESS` opcode (e.g. via inline assembly/raw bytecode, since this is a TRON-specific extended opcode) with stack operands: `witnessArrayOffset=0, witnessArrayLength=1, amountArrayOffset=0, amountArrayLength=0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF` (a value that overflows when multiplied by `WORD_SIZE=32` in 256-bit `DataWord` arithmetic).
2. On a node where `allowTvmOsaka` is not enabled, trigger the contract. `getVoteWitnessCost`/`getVoteWitnessCost2` is invoked, `amountArrayLength.mul(wordSize)` wraps modulo 2^256 to a small value, `memNeeded` returns a small `BigInteger`, and `checkMemorySize` does not throw `memoryOverflow` even though the true intended array size vastly exceeds the 3MB `MEM_LIMIT`.
3. Compare against `VoteWitnessCost3Test.testLargeArrayLengthOverflow`/`testLargeOffsetOverflow`, which demonstrate the exact same crafted operands correctly throw `Program.OutOfMemoryException` only when the `BigInteger`-based `getVoteWitnessCost3` path is used (Osaka enabled), confirming the legacy path is the vulnerable one: [5](#0-4) 

**Note on verification limits:** I was unable to locate within the index the exact opcode dispatch/execution logic (the `Operation`/`Action` class in `org/tron/core/vm/OperationActions.java` or similar) that reads `amountArrayLength`/`witnessArrayLength` off the stack and actually performs the subsequent memory read/array construction for `VOTEWITNESS`, so I cannot confirm with certainty whether the undercharged-but-bypassed memory allocation actually manifests as an OOM crash versus merely an energy-accounting inconsistency without further node crash. This would need to be confirmed by reading `actuator/src/main/java/org/tron/core/vm/OperationActions.java` and the native `VoteWitnessProcessor`/`VoteWitnessParam` execution path directly, which is recommended before treating the impact as confirmed node-crash-level.

  public static long getVoteWitnessCost(Program program) {
    Stack stack = program.getStack();
    long oldMemSize = program.getMemSize();
    DataWord amountArrayLength = stack.get(stack.size() - 1).clone();
    DataWord amountArrayOffset = stack.get(stack.size() - 2);
    DataWord witnessArrayLength = stack.get(stack.size() - 3).clone();
    DataWord witnessArrayOffset = stack.get(stack.size() - 4);

    DataWord wordSize = new DataWord(DataWord.WORD_SIZE);

    amountArrayLength.mul(wordSize);
    BigInteger amountArrayMemoryNeeded = memNeeded(amountArrayOffset, amountArrayLength);

    witnessArrayLength.mul(wordSize);
    BigInteger witnessArrayMemoryNeeded = memNeeded(witnessArrayOffset, witnessArrayLength);

    return VOTE_WITNESS + calcMemEnergy(oldMemSize,
        (amountArrayMemoryNeeded.compareTo(witnessArrayMemoryNeeded) > 0
            ? amountArrayMemoryNeeded : witnessArrayMemoryNeeded), 0, Op.VOTEWITNESS);
  }

      return getVoteWitnessCost(program);
    }

    DataWord witnessArrayOffset = stack.get(stack.size() - 4);

  @Test
  public void testLargeArrayLengthOverflow() {
    // Use a very large value that would overflow in DataWord.mul() in cost2
    // DataWord max is 2^256-1, multiplying by 32 would overflow
    // In cost3, BigInteger handles this correctly and should trigger memoryOverflow
    String maxHex = "ffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff";
    DataWord largeLength = new DataWord(maxHex);
    DataWord zeroOffset = new DataWord(0);

    Program program = mockProgram(zeroOffset, new DataWord(1),
        zeroOffset, largeLength, 0);

    boolean overflowCaught = false;
    VMConfig.initAllowTvmOsaka(1);    // cost3 self-dispatches; exercise the v3 (BigInteger) path
    try {
      EnergyCost.getVoteWitnessCost3(program);
    } catch (Program.OutOfMemoryException e) {
      // cost3 should detect memory overflow via checkMemorySize
      overflowCaught = true;
    } finally {
      VMConfig.initAllowTvmOsaka(0);
    }
    assertTrue("cost3 should throw memoryOverflow for huge array length", overflowCaught);
  }
