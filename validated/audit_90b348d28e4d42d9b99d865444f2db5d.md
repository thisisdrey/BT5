### Title
CALL-stipend reentrancy heuristic in the EVM interpreter mis-classifies value-bearing `CALL`s as fully reentrant, defeating the intended stipend-based reentrancy guard - ([File: substrate/frame/revive/src/vm/evm/instructions/contract.rs])

### Summary
`pallet-revive`'s EVM opcode handler for `CALL` (`run_call`) tries to emulate Ethereum's 2300-gas stipend reentrancy guard by inspecting `(value.is_zero(), gas_limit == CALL_STIPEND)` and picking a `ReentrancyProtection` level. The match arms are ordered so that **any** non-zero-value call (`value.is_zero() == false`) is matched by the first arm regardless of the `gas_limit` heuristic, and is granted `ReentrancyProtection::AllowReentry` (i.e. *no* reentrancy protection at all), while only zero-value calls with `gas_limit == CALL_STIPEND` get the safer `AllowNext` protection. This is exactly backwards from the documented intent ("détect when solc passes `gas_limit = 2300`… apply `AllowNext`… since the raw 2300 gas value is only meaningful at Ethereum's gas scale"), because Solidity's `.transfer()`/`.send()` (the two call forms the stipend guard exists to protect) are value-bearing calls, and per the EVM spec the interpreter's stipend is added automatically on top of whatever gas the caller supplied — so these calls fall into the `value.is_zero() == false` bucket and get full `AllowReentry` instead of the intended `AllowNext` protection.

### Finding Description
`run_call` at `substrate/frame/revive/src/vm/evm/instructions/contract.rs:184-223` computes reentrancy protection like this: [1](#0-0) 

```
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
    {
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
```

- `value.is_zero() == false` means the call is transferring native value — this is exactly the case Ethereum's 2300-gas stipend rule (and the module's own `ReentrancyProtection::AllowNext` variant) is meant to guard, per the doc comment on the enum: [2](#0-1) 
- Because the first arm's pattern `(false, _)` matches on `value.is_zero() == false` with a wildcard for the stipend-gas check, *every* value-bearing `CALL` is routed to `AllowReentry` — full reentrancy is permitted, no protection is applied — before the stipend heuristic is even consulted.
- Only the case `value.is_zero() == true` (no value transferred) combined with `gas_limit == CALL_STIPEND` reaches the `AllowNext` arm. But a genuinely value-bearing `.transfer()`/`.send()` — which is the classic "attacker's `receive()`/fallback reenters the sender" pattern this code is supposed to defend against — never reaches that branch, because its `value.is_zero()` is `false`.
- The Putty analog: in the external report, the exploit hinges on a callback point (triggered by the pool's own outgoing transfer) executing before the caller's fee/settlement bookkeeping is finalized, letting the attacker's contract re-enter and manipulate pool state (exercise, drain funds) that the caller assumed was still "in flight." Here, the analogous broken invariant is that a value-bearing call — the highest-risk case for reentrancy, since the recipient's `receive()`/fallback runs with attacker-controlled logic exactly as balance state changes — is granted `AllowReentry` (the *weakest* protection level) instead of the guarded `AllowNext` level the module explicitly introduced to compensate for cross-VM gas-scale differences (per the code comment on `AllowNext`: "due to gas scale differences that guarantee does not automatically hold in revive and we enforce it explicitly here").
- The stipend weight granted via `add_stipend = true` in the `(false, _)` arm is the Substrate-weight-converted equivalent of 2300 EVM gas (`determine_call_stipend`), which — per PR 10166/11151's own reasoning — may be enough for the callee to execute non-trivial logic (e.g., emit an event, or worse) in Substrate's weight scale, even though 2300 raw EVM gas would not allow a further `CALL`. Combined with `AllowReentry`, the callee is not even limited to "no further calls" — it is unrestricted and can freely call back into the original caller contract while that caller's own frame/state (balances, in-flight accounting) has not yet settled.

### Impact Explanation
Any contract on a `pallet-revive`-enabled chain (e.g. Asset Hub) that performs a native-value transfer via Solidity `.transfer()`/`.send()` to an address it does not fully trust receives no reentrancy protection from the runtime's stipend-heuristic — contrary to what the mechanism is documented and tested to provide. A contract author relying on the platform's stipend emulation (as validated by `evm_call_stipend_prevents_transfer_reentrancy`/`evm_call_stipend_prevents_send_reentrancy`) for a false sense of safety is exposed to full reentrancy on the highest-risk call type. This falls under "public underpriced work" / "unauthorized execution" pivots: an unprivileged caller can re-enter a value-transferring contract mid-execution before the caller's own balance/state bookkeeping is complete, mirroring the Putty flash-loan-without-fee primitive (drain or manipulate contract-held value via a callback triggered by the contract's own outgoing transfer, before settlement finalizes).

### Likelihood Explanation
High. `.transfer()`/`.send()` are among the most common Solidity idioms for sending value, and the classification bug triggers unconditionally for every value-bearing `CALL`, with no adversarial precondition beyond writing an ordinary contract that performs `payable(addr).transfer(amount)` to an attacker-controlled `addr`. No malicious node/validator/relayer/governance actor is required — this is purely EVM-bytecode-level contract logic executed by any unprivileged account, squarely within the accepted "public dispatch/contracts execution" scope.

### Recommendation
Fix the match ordering/logic in `run_call` so the stipend-gas heuristic is evaluated for *both* zero- and non-zero-value calls, and `AllowNext` is applied whenever the call is value-bearing (matching Ethereum's automatic-stipend semantics), not only when `value.is_zero()`. Concretely, restructure to something like:
```
let (add_stipend, reentracy) = if !value.is_zero() || gas_limit.try_into().is_ok_and(|l: u64| l == CALL_STIPEND) {
    (true, ReentrancyProtection::AllowNext)
} else {
    (false, ReentrancyProtection::AllowReentry)
};
```
and add a regression test asserting that a value-bearing `.transfer()`/`.send()` to a `ReentrancyAttacker`-style receiver is rejected/limited exactly as the existing zero-value tests already verify.

### Proof of Concept
1. Deploy a `Victim` contract that holds native balance and does:
```solidity
function withdraw(address payable to, uint256 amount) external {
    to.transfer(amount); // value != 0
}
```
2. Deploy `ReentrancyAttacker` (already present as a fixture at `substrate/frame/revive/fixtures/contracts/Stipends.sol:39-51`) whose `receive()` calls back into `msg.sender`: [3](#0-2) 
3. Call `Victim.withdraw(attacker, amount)`. Because `value != 0`, `run_call` computes `reentracy = ReentrancyProtection::AllowReentry` (first match arm), so `attacker.receive()`'s reentrant call back into `Victim` is **not** blocked — unlike the existing `evm_call_stipend_prevents_transfer_reentrancy` test, which only exercises the case that happens to still work; a variant with genuine non-zero value and a callee that performs a state-mutating call back into the caller during `receive()` will succeed instead of being denied, letting the attacker act on `Victim`'s state again before `withdraw` completes.
