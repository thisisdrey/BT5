### Title
Unvalidated `local_header_offset` in CDH leads to OOB read when resolving Local Header - (File: src/tools/singlejar/input_jar.h)

### Summary
`InputJar::LocalHeader()` computes a `Local Header (LH)` pointer directly from the attacker-controlled `local_header_offset()` field of a Central Directory Header (`CDH`), and then `OutputJar::AddJar` immediately dereferences fields on that `LH` (`file_name_length()`, `extra_fields_length()`, `compressed_file_size()`, etc.) without any check that the computed address lies inside the memory-mapped jar file.

### Finding Description
`InputJar::NextEntry` validates that each successive `CDH` entry stays within the mapped file via `mapped_file_.mapped(new_cdr)` [3](#0-2) , but the companion `LocalHeader()` accessor performs no such check:

```
const LH* LocalHeader(const CDH* cdh) const {
  return reinterpret_cast<const LH*>(
      mapped_file_.address(cdh->local_header_offset() + preamble_size_));
}
``` [2](#0-1) 

`MappedFile::address()` is a raw pointer-arithmetic helper with no bounds validation:
```
const unsigned char* address(int64_t offset) const {
  return mapped_start_ + offset;
}
``` [4](#0-3) 

`local_header_offset()` is read straight from the CDH's on-disk bytes (32-bit, or 64-bit via a Zip64 extra field) and is fully attacker-controlled, similar to how the HFS `len` field is fully attacker-controlled catalog-record data: [5](#0-4) .

`OutputJar::AddJar` calls `input_jar.NextEntry(&lh)` and immediately reads `lh->file_name_length()` / `lh->uncompressed_file_size()` from the returned, unchecked `LH*` (e.g. in `AppendToDirectoryBuffer`/`WriteEntry` and size computations), so a crafted offset that points near or past the end of the mmap region causes the process to read `LH` header fields (and subsequently `file_name`/`extra_fields`/entry data spanning attacker-chosen lengths) out of the mapped bounds — the exact bug-class parallel to `hfs_strcmp` reading `HFS_NAMELEN`-worth of an unchecked, attacker-supplied `len`.

### Impact Explanation
`singlejar`/ijar tooling processes `.jar` archives that can originate from external, untrusted sources consumed by the build (e.g. `java_import`, prebuilt jars fetched via `http_jar`/`http_archive`, or third-party dependency artifacts assembled into deploy jars). A maliciously crafted jar with a bogus `local_header_offset` in its Central Directory Header can cause `singlejar`/`ijar` to read out-of-bounds memory adjacent to the mmap'd file, potentially causing a crash (denial of the merge action) or leaking adjacent heap/mmap-region bytes into build outputs (e.g. through fields copied from the OOB-read `LH` into the output jar's directory buffer or file name strings), corresponding to CWE-125 out-of-bounds read.

### Likelihood Explanation
Reachable whenever `singlejar` (via `java_binary`'s deploy-jar action, or the `ijar`/`zip.cc` header-parsing path) processes any externally supplied jar that a build ingests, which is a default, always-on part of Bazel's Java build graph. No sandbox escape or privileged access is needed — only the ability to supply a crafted `.jar` file that the build consumes (e.g. as a `java_import` dep or through an `http_jar`), which matches the "hostile origin server / crafted artifact" attacker model. The bug requires no interaction beyond a normal build.

### Recommendation
Add bounds validation in `InputJar::LocalHeader()` analogous to the existing `mapped()` check in `NextEntry()`: verify that `mapped_file_.address(cdh->local_header_offset() + preamble_size_)` and the subsequent `sizeof(LH)` region, plus `file_name_length()`/`extra_fields_length()` derived from it, remain within `[mapped_file_.start(), mapped_file_.end())` before returning the pointer or dereferencing any of its fields, failing the read (as `NextEntry` does via `diag_errx`) if the offset is invalid.

### Proof of Concept
A reproducible `BuildIntegrationTestCase`/shell test would: (1) construct a minimal valid ZIP with one CDH entry whose `local_header_offset` field is patched to a huge/negative value (e.g. `0xFFFFFFF0`) while `local_header_offset` is not zip64-flagged; (2) run `singlejar --sources crafted.jar --output out.jar` (or trigger via `java_binary` deploy jar assembly) under ASan; (3) observe a heap-buffer-overflow / out-of-bounds read report when `LocalHeader()`'s resulting pointer is dereferenced in `OutputJar::AddJar`'s `NextEntry`/field-access loop, since no analog to the `CDH`-traversal `mapped()` check exists for the `LH` computed from an untrusted offset. Full verification of exploitability (e.g. confirming compiler/ASan behavior on the exact offset arithmetic and reachability from `java_binary`'s default deploy-jar action) was not completed within the scope of this investigation and would require running the described PoC.
