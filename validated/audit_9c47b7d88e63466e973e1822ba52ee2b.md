### Title
Dust transfers of deposit tokens fill an account's token list to `MAX_TOKENS_PER_USER`, permanently reverting deposits, mints, and transfers for any new collateral — ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`DepositToken._transfer` and `_mint` unconditionally call `Pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to positive. `Pool` enforces `MAX_TOKENS_PER_USER = 30` across `depositTokensOfAccount + debtTokensOfAccount` and reverts with `UserReachedMaxTokens`. Because `transfer`/`transferFrom` are public and only require the *sender's* unlocked balance, an attacker can dust-transfer 1 wei of every distinct deposit token to a victim (or to the pool's `feeCollector`), filling that account's list and making any subsequent mint/transfer of a *new* collateral token to that account revert.

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's set when `_recipientBalanceBefore == 0 && amount_ > 0` (`contracts/DepositToken.sol:517-520`). There is no minimum amount and no opt-in by the recipient.
- `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, reverting once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`contracts/Pool.sol:143-148`, `204-220`).
- Attack path (unprivileged, no privileged role needed):
  1. Attacker deposits a dust amount (e.g. 1 wei worth) of each supported collateral via `DepositToken.deposit(amount_, attacker)`, receiving transferable msdTOKENs.
  2. Attacker calls `transfer(victim, 1)` for each distinct deposit token until `victim`'s set reaches 30 entries. All of the attacker's balance is unlocked because they hold no debt (`unlockedBalanceOf` returns full balance when `_debtInUsd == 0`, `DepositToken.sol:383-398`).
  3. Any later action that would put a *new* token type into the victim's set reverts inside `_mint`/`_transfer`:
     - `victim`'s `deposit()`/`issue()` flows involving a collateral it doesn't already hold;
     - transfers of new msdTOKENs to `victim`;
     - if `victim` is the pool's `feeCollector`, **every** `deposit()` that charges a fee in a token the feeCollector doesn't already hold reverts at `_mint(_pool.feeCollector(), _fee)` (`DepositToken.sol:230-232`), DoSing the deposit path for those collateral types protocol-wide.
- Removal is only possible by the target account itself transferring/withdrawing the dust (which costs it gas and may be impossible for contracts like `feeCollector` unless the governor sweeps via `TokenHolder`).

### Impact Explanation
Temporary freezing of funds / liveness break: a targeted user is unable to deposit any additional collateral type, preventing them from improving health and exposing them to liquidation; a targeted `feeCollector` (or any contract account, e.g. `Treasury` which is barred from depositing but can hold msdTOKENs) bricks the fee-minting step and therefore `deposit()` for all collateral tokens not already in its list. The attacker pays only dust deposits plus gas — directly analogous to CVE-2017-5993's cheap repeated commands that accumulate host resources until the service fails.

### Likelihood Explanation
Requires the pool to have enough registered collateral types to reach the 30-entry cap (deposit tokens are the only attacker-movable entries; `DebtToken` balances cannot be dust-transferred). On pools with many collaterals this is cheap and fully permissionless; on pools with <30 collaterals the cap is unreachable. No oracle manipulation, privileged roles, or trusted-remote assumptions are needed.

### Recommendation
- Do not count tokens received purely by transfer toward `MAX_TOKENS_PER_USER`, or allow the set to exceed the cap for entries added by `transfer` while keeping the cap for `deposit`/`issue`.
- Alternatively, enforce a minimum transfer/mint amount, or make `addToDepositTokensOfAccount` a no-op (return silently) instead of reverting when at capacity so deposits/mints never brick.

### Proof of Concept
Foundry/Hardhat fork sketch:

```solidity
// Setup: pool with >= 30 registered DepositTokens dt[0..29], attacker holds no debt.
address victim = makeAddr("victim"); // or pool.feeCollector()

for (uint i; i < 30; ++i) {
    underlying[i].approve(address(dt[i]), DUST);
    dt[i].deposit(DUST, attacker);          // attacker gets dust msdTOKEN_i
    dt[i].transfer(victim, 1);              // adds dt[i] to victim's set
}
assertEq(pool.getDepositTokensOfAccount(victim).length, 30);

// Victim tries to deposit collateral #30 (a token it doesn't hold yet)
underlying[30].approve(address(dt[30]), 1e18);
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
dt[30].deposit(1e18, victim);               // reverts inside _mint -> addToDepositTokensOfAccount

// If victim == feeCollector: ANY user's deposit of a new-fee token reverts
vm.prank(alice);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
dt[30].deposit(1e18, alice);                // _mint(feeCollector, fee) reverts
```
