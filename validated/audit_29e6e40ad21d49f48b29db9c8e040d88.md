## Finding: Unbounded Array Allocation from Attacker-Controlled Length in TVM Precompiled Contract Argument Parsing

### Title
Unbounded Heap Allocation via Untrusted Length Field in Precompiled-Contract ABI Array Extraction - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.java` contains helper methods (`extractBytes32Array`, `extractBytesArray`, `extractSigArray`) that parse dynamic array arguments passed to precompiled contracts invoked via the TVM `CALL` opcode. Each of these methods reads a declared array-length word from caller-supplied calldata via `DataWord.intValueSafe()` and immediately uses that value to allocate a Java array, with no upper bound check, exactly mirroring the MessagePack EXT32 pattern where a declared length is trusted for allocation before the actual data backing it is validated.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` each compute `int len = words[offset].intValueSafe();` and then allocate `new byte[len][]` (or similarly sized structures) before any bytes are actually copied: [1](#0-0) 

`DataWord.intValueSafe()` does not clamp to a "reasonable" bound — for any 32-byte word whose numeric value exceeds `Integer.MAX_VALUE` or occupies more than 4 bytes, it returns `Integer.MAX_VALUE` itself: [2](#0-1) 

Because `len` is taken directly from the "length" word placed by the caller in the ABI-encoded calldata of the precompiled-contract call, an attacker who controls the transaction/contract call data controls `len` up to `Integer.MAX_VALUE`. `new byte[Integer.MAX_VALUE][]` (an object-array of ~2^31 references, 8 bytes each on a 64-bit JVM) attempts to allocate on the order of 16+ GB, which will throw `OutOfMemoryError` or otherwise stall/crash the JVM — the identical root cause as the MessagePack advisory: a declared length is "trusted" for allocation sizing before the corresponding data is validated to actually exist/fit.

This is directly analogous to `readPayload()`/`getData()` in the MessagePack advisory, where the EXT32 length field is used to size an allocation before validating that the payload of that size is actually present.

### Impact Explanation
Any account (no special privilege required) can trigger a smart-contract `CALL` (or `TriggerSmartContract` transaction) into a precompiled contract that uses these array-extraction helpers, supplying a crafted length word. This can force the full-node executing the transaction to attempt a multi-gigabyte allocation per call, resulting in `OutOfMemoryError` / thrashing, which can crash or hang the node process executing the block — a denial-of-service against the network's block-processing/validation path (CWE-400/CWE-789), analogous to the "node crash or halt" impact category.

### Likelihood Explanation
Reachability is high: precompiled contracts are reachable from any transaction that performs a TVM `CALL` to the relevant precompile address, requiring only that a transaction be broadcast and included/executed — no elevated permission, signer identity, or malformed bytes are needed, only a crafted length word in the ABI-encoded calldata, mirroring the "small file, huge declared length" characteristic of the original PoC.

### Recommendation
Add an explicit sanity bound on the decoded array length (`len`) in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocation — e.g., reject if `len` exceeds the number of remaining 32-byte words actually present in `words`/`data`, similar to the bound checks already used elsewhere in the code (e.g., `verifyLength` in `RLP.java`) — so allocation size is always derived from/bounded by the actual size of the supplied calldata rather than from an unchecked declared value. [3](#0-2) 

### Proof of Concept
Craft calldata for a call to a precompiled contract that invokes `extractBytesArray`/`extractBytes32Array` such that the word at the expected "array length" `offset` encodes a very large 32-byte integer (e.g., `0x00000000000000000000000000000000000000000000000000000000FFFFFFFF` or any value whose low 4 bytes decode to a large positive `int`, per `intValueSafe()`), while providing calldata far smaller than what such a length would imply. Submitting a `TriggerSmartContract` transaction that performs a `CALL` to the relevant precompile address with this payload causes `words[offset].intValueSafe()` to return a very large `int`, and the subsequent `new byte[len][]` allocation attempts a multi-gigabyte allocation, producing `OutOfMemoryError` in the node's TVM execution thread. [4](#0-3) 

**Note on verification limits**: I confirmed the vulnerable allocation pattern and the unbounded `intValueSafe()` behavior directly in the code, but I was unable to pinpoint within the available tool budget the exact precompiled-contract class (e.g., batch signature validation) that calls `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, since a targeted grep for those call sites did not return results before the session ended. A full-repo review (e.g., via a Devin session with complete file access) would be needed to confirm the exact precompile address and calling context to build a byte-exact PoC transaction.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
