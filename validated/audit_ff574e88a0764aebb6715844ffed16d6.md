Audit Report

## Title
ERC20 asset transactor credits full requested amount into XCM holding based only on a contract's boolean return, not actual balance change - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` calls an ERC20 contract's `transfer(checking_account, amount)` and, if the ABI-decoded return value is `true`, unconditionally credits the full `amount` into the XCM holding register as `Erc20Credit(amount)`, without verifying any actual balance delta. `deposit_asset_with_surplus` behaves symmetrically, transferring based purely on the boolean return. Because `ERC20Matcher`'s `IsLocalAccountKey20` filter accepts any local `AccountKey20` location — i.e., any contract deployed by anyone — with no allowlist, an attacker can deploy a non-standard "ERC20" contract whose `transfer()` always returns `true` while moving little or no real value, and use it to mint unbacked XCM holding credits.

## Finding Description
`withdraw_asset_with_surplus` builds a `transferCall` to the checking account and trusts the decoded boolean result to mint `Erc20Credit(amount)` into `AssetsInHolding`, with no `balanceOf` check before/after: [1](#0-0) 

The `Erc20Credit` type is explicitly documented as not performing runtime-level balance enforcement, tying its correctness entirely to trusting the contract call outcome: [2](#0-1) 

`deposit_asset_with_surplus` similarly transfers to the beneficiary and returns success purely from the decoded boolean, without any balance verification: [3](#0-2) 

The matcher deciding which locations are valid ERC20 assets accepts any local `AccountKey20` — any deployed contract, with no registration or governance step: [4](#0-3) 

This lets an attacker deploy a trivial contract whose `transfer(address,uint256)` always returns `true` without moving `value` tokens, then submit a `WithdrawAsset`/`DepositAsset` XCM program via `pallet_xcm::execute` to mint `Erc20Credit` value in the holding register decoupled from any real token custody. Existing guards (revert check, ABI-decode error check) only catch explicit contract failure or malformed return data — they do not verify that the nominal `amount` actually moved, so a malicious contract returning a hardcoded `true` bypasses all checks.

## Impact Explanation
This breaks the invariant that XCM `AssetsInHolding` credits must be backed 1:1 by real, verified token custody, permitting an unbacked mint of accounted value inside the XCM executor's holding register for an arbitrary `amount` the attacker specifies. This value can subsequently be deposited to any beneficiary or forwarded cross-chain via further XCM instructions, matching the "theft or unbacked mint" impact category.

## Likelihood Explanation
The exploit path requires only a normal signed account able to deploy a contract via `pallet-revive` and call `pallet_xcm::execute` — both permissionless. `ERC20Transactor` is wired into `AssetTransactors` for asset-hub-westend, confirming it is live-scope code, not a hypothetical config: [5](#0-4)  No governance, admin, relayer, or validator collusion is needed.

## Recommendation
After calling `transfer`, verify the actual balance delta of the checking account (`balanceOf` before/after the call) rather than trusting only the decoded boolean return and nominal `amount`; credit/settle only the observed delta into `AssetsInHolding`. Apply the same delta verification in `deposit_asset_with_surplus`.

## Proof of Concept
1. On asset-hub-westend, deploy a minimal contract implementing `IERC20` where `transfer(address to, uint256 value)` always returns `true` without adjusting any balance.
2. Fund the attacker's revive account (no real token balance required, since `transfer` never checks/uses balances).
3. Submit `pallet_xcm::execute` with `WithdrawAsset((AccountKey20{key: malicious_contract}, X))` followed by `DepositAsset(All, beneficiary)`.
4. Observe `withdraw_asset_with_surplus` decode `is_success == true` and credit `Erc20Credit(X)` into holding (`erc20_transactor.rs:195-203`), then `deposit_asset_with_surplus` transfers that credited `X` to the beneficiary, confirming unbacked issuance of accounted value with no corresponding real token movement.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
