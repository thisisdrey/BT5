## Title
Heap buffer over-read parsing malformed ZIP/JAR central directory entries in ijar - (`third_party/ijar/zip.cc`)

### Summary
`third_party/ijar/zip.cc` implements the `ijar` interface-jar tool's ZIP/JAR reader. Every code path that consumes attacker-influenced length fields from a ZIP central directory or local file header validates the remaining buffer size with `InputZipFile::EnsureRemaining()` before reading — **except** `InputZipFile::ProcessCentralDirEntry()`, which reads `file_name_length`, `extra_field_length`, and `file_comment_length` straight from attacker-controlled bytes and immediately `memcpy`s and advances the cursor `p` past the mmap'd input buffer with no bounds check at all.

### Finding Description
`InputZipFile::Open()` locates the central directory via `FindZipCentralDirectory()`, which only validates that `central_dir_offset + central_dir_size <= in_length` for the *whole* central directory region [1](#0-0) . It never validates that each individual entry's `file_name_length` / `extra_field_length` / `file_comment_length` keeps the per-entry cursor inside that region or inside the mapped file.

`ProcessCentralDirEntry()` then parses one entry at a time: [2](#0-1) 

Note there is no call to `EnsureRemaining()` anywhere in this function, unlike its sibling read paths in the same file, `ProcessLocalFileEntry()` (`EnsureRemaining(file_name_length_, "file_name")`, `EnsureRemaining(extra_field_length_, "extra_field")`) [3](#0-2) , `SkipFile()` [4](#0-3) , and `ProcessFile()` [5](#0-4) .

Concretely, an attacker who crafts a JAR/ZIP where a central-directory entry near the end of the mapped file declares an inflated `file_name_length` (up to 65535) causes:
- `memcpy(filename, p, len)` to read up to `min(file_name_length, PATH_MAX-1)` bytes starting at `p`, where `p` may be only a few bytes from the end of the `mmap`-backed buffer (`MappedInputFile`), reading past the mapping.
- The subsequent extra-field loop `while (extra_p != p) { get_u2le(extra_p); ... extra_p += data_size; }` walks further past `p` with an attacker-chosen `extra_field_length` and `data_size`, with no check that `extra_p` stays inside the file or even inside the extra-field region, so it can walk arbitrarily far past the mapped buffer, dereferencing unmapped memory.

This mirrors the CVE-2017-15953 bug class: a fixed-size/mapped input buffer is walked using length fields taken from an untrusted, malformed file without validating those lengths against the actual remaining buffer size, producing an out-of-bounds (heap/mmap) read and crash (and potential info exposure through the copied `filename` bytes).

### Impact Explanation
`ijar` runs as a native (non-JVM) binary as part of the Bazel Java toolchain to produce interface jars from any JAR that reaches Java compilation — including prebuilt/third-party jars supplied through `java_import`, `http_jar`, `http_file`, or similar rules whose bytes originate from a URL an unprivileged, malicious server operator controls. Because the vulnerable code is native C++ operating on an `mmap`ed file, an out-of-bounds read here is a memory-safety violation (crash / potential disclosure of adjacent process memory into build outputs), not merely a caught exception as would happen in the equivalent Java-based extractors (`ZipDecompressor`, etc.). This satisfies the "read outside the repository/exec root/output base" style of impact via an out-of-bounds memory access triggered purely by content an outside party published.

### Likelihood Explanation
Likelihood is moderate: it requires that ijar processes a JAR whose bytes are fully attacker-chosen (e.g., a malicious release asset referenced by `http_jar`/`java_import`). Bazel's checksum pinning (`sha256`/`integrity`) verifies the bytes match what was recorded, but does not — and cannot — validate the internal ZIP structure; a hash simply pins whatever malformed bytes the attacker chose to publish, so integrity verification does not stop this class of bug.

### Recommendation
Add `EnsureRemaining()`-style bounds checks in `InputZipFile::ProcessCentralDirEntry()` before reading `file_name_length`, `extra_field_length`, `file_comment_length` bytes and before/while iterating the extra-field chain, mirroring the checks already present in `ProcessLocalFileEntry()`, `SkipFile()`, and `ProcessFile()`.

### Proof of Concept
Construct a minimal ZIP/JAR whose single central-directory entry sets `file_name_length` (and/or `extra_field_length`) to a value that would place `p`/`extra_p` past the end of the physical file while the overall `central_dir_offset + central_dir_size` still satisfies `<= in_length` (e.g., place the malformed entry as the very last entry so the remaining bytes are fewer than the declared length). Running the `ijar` binary (or a `third_party/ijar` unit test built with `-fsanitize=address`) against this file and calling `InputZipFile::ProcessNext()`/`ProcessCentralDirEntry()` reproduces an ASan-reported heap-buffer-overflow (read) in the `memcpy` at `third_party/ijar/zip.cc:520` or in the extra-field walk loop at lines 526–541, analogous to a JUnit/`src/test/shell` regression test asserting `ijar` exits gracefully instead of crashing on such malformed archives.
