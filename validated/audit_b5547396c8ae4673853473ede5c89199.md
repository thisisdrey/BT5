### Title
Heap buffer over-read in ijar's central directory extra-field parsing due to unchecked `data_size` — ([File: third_party/ijar/zip.cc])

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the "extra fields" of a ZIP central directory header without validating that each field's declared `data_size` stays within the bounds of the declared `extra_field_length`, and without a hard upper bound derived from the actual mapped-file size before the initial per-field reads. This is structurally the same bug class as CVE-2019-9936: an untrusted, length-prefixed record stream is walked field-by-field using attacker-controlled length values, and a record whose length pushes the cursor past the intended boundary causes subsequent length-prefixed reads to be taken from out-of-bounds memory.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-controlled central directory bytes [1](#0-0) , then sets `extra_p = p` and advances `p += extra_field_length` to mark the end of the extra-field region, before iterating with:

```
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
``` [2](#0-1) 

Two issues compound here:
1. There is no check that `extra_p + 4 <= p` before reading `header_id`/`data_size`, and no check that `extra_p + data_size <= p` before advancing.
2. The loop terminates on exact equality (`extra_p != p`) rather than `extra_p < p`. Because `data_size` is attacker-controlled and unrelated to the declared `extra_field_length`, a crafted value can make `extra_p` skip past `p` without ever equaling it, so the loop continues walking forward through memory that is no longer part of the declared extra-field region — and, since `p` was only checked to be `<=` remaining input via the caller's coarse validation (not per 4-byte read), this can walk past the end of the memory-mapped input file entirely.

Unlike the `bazel-tools` fetch/cache machinery (`HttpDownloader`, `RepositoryCache`, `DownloadCache`), which correctly enforces `sha256`/`integrity` before content is trusted [3](#0-2) , this bug lives entirely downstream of a successful integrity check. A dependency author (unprivileged, controls only the bytes served at a URL that a victim pins via `sha256`) can craft the JAR's central-directory extra fields so that the *correctly-verified* artifact itself triggers the out-of-bounds walk when `ijar` (or `singlejar`, which shares the same zip/central-directory parsing conventions) processes it as part of normal Java compilation (`ijar` strips class bodies to produce interface jars for every `java_library` dependency).

### Impact Explanation
This is a memory-safety bug in bazel's own native C++ zip-parsing code (`third_party/ijar/zip.cc`), not a third-party dependency CVE, and it is reachable purely from bytes an unprivileged dependency publisher controls — no MITM, no malicious peer, and no access to the victim's machine is required. Depending on layout, the out-of-bounds read can (a) crash the `ijar`/`singlejar` worker process (a soft DoS, which per the rules should not be the primary basis for validity) or (b) read adjacent heap bytes that are then reinterpreted as `header_id`/`data_size`/ZIP64 size fields, corrupting `*uncompressed_size`/`*compressed_size`/`*offset` for the entry and causing further out-of-bounds reads or copies (`memcpy` of `file_name`, or `ProcessFile`/`UncompressFile` operating on corrupted sizes) — this is a genuine heap-buffer-over-read / potential information disclosure into build output.

### Likelihood Explanation
Any project that declares an `http_jar`/`http_archive`/`http_file` dependency (or accepts a dependency published to a registry/mirror) with an attacker-supplied ZIP is affected the first time that JAR is compiled against — ijar runs on essentially every Java compilation input. The attacker only needs to control the published artifact bytes (the thing being pinned by the checksum), which is exactly the threat model this class of finding requires.

### Recommendation
In `InputZipFile::ProcessCentralDirEntry` (and any equivalent extra-field walkers in `src/tools/singlejar`), bound every per-field read: before reading `header_id`/`data_size`, verify `extra_p + 4 <= p` (i.e., stays within `extra_field_length`); after computing `data_size`, verify `extra_p + data_size <= p` before dereferencing `extra` or advancing; change the loop condition from `extra_p != p` to `extra_p < p`; and reject (`error(...)`) rather than silently continue when a field would overrun. The same bound should ultimately trace back to `input_file_->Length()`, not just the locally declared `extra_field_length`.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` reproduction would:
1. Hand-construct a ZIP central directory header (as already done in `CreateZipWithMalformedExtraField` in `src/tools/singlejar/output_jar_simple_test.cc`, which demonstrates the test harness pattern for "oversized extra field" entries used elsewhere in the codebase) [4](#0-3) , but targeting `third_party/ijar`'s `FindZipCentralDirectory`/`ProcessCentralDirEntry` path instead of `singlejar`.
2. Set `extra_field_length` to a small value (e.g. 4) but craft the first extra-field record's 2-byte `data_size` to a large value (e.g. `0xFFF0`), so `extra_p += data_size` jumps far past the declared extra-field end and past `p`, defeating the `while (extra_p != p)` termination and causing subsequent `get_u2le`/`get_u8le` reads to run off the end of the mapped input buffer.
3. Feed this crafted zip through `ijar`'s public interface (`third_party/ijar/zip.cc`'s `ZipExtractor`, exercised e.g. via `java_library`'s ijar action) and confirm under ASan/valgrind that a heap-buffer-overflow (read) is reported, or that corrupted `uncompressed_size`/`compressed_size` values are observed for the entry.

I could not directly execute or run this PoC (no filesystem/terminal access in this mode); the trace above is based on static reading of `third_party/ijar/zip.cc` and the absence of per-field bounds checks in `ProcessCentralDirEntry`, contrasted with the `EnsureRemaining` checks used in `ProcessLocalFileEntry`/`SkipFile`/`ProcessFile` for the local-header path [5](#0-4) [6](#0-5) , which shows the central-directory extra-field loop is the one path lacking such validation.

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
