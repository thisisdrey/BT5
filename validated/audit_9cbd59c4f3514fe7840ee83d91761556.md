### Title
Integer overflow in ZIP64 central-directory bounds check leads to out-of-bounds heap read - (File: `third_party/ijar/zip.cc`)

### Summary
`FindZipCentralDirectory()` validates the central-directory location taken from an untrusted `.zip`/`.jar` file's End-Of-Central-Directory (and ZIP64 EOCD) record with a single unsigned addition, `cd.central_dir_offset + cd.central_dir_size > in_length`, where both operands are fully attacker-controlled 64-bit values read straight from the file. This mirrors the CVE-2016-6328 bug class: an integer overflow while parsing an untrusted binary-metadata field (there, the libexif MNOTE entry; here, the ZIP64 EOCD offset/size fields) that defeats a bounds check and leads to heap out-of-bounds access and potential information disclosure.

### Finding Description
`ZipExtractor`/`InputZipFile::Open()` calls `FindZipCentralDirectory()` (`third_party/ijar/zip.cc:704-778`) to locate a `.jar`'s central directory before ijar strips it into an interface jar. The regular EOCD fields (`central_dir_size`, `central_dir_offset`) are 32-bit, but `MaybeReadZip64CentralDirectory()` (`third_party/ijar/zip.cc:593-657`) will overwrite them with attacker-supplied 64-bit values (`get_u8le`) taken from a ZIP64 EOCD record if one is present [1](#0-0) .

The subsequent sanity check:
```
if (cd.central_dir_offset + cd.central_dir_size > in_length) { ... return false; }
``` [2](#0-1) 
performs unsigned 64-bit addition with no overflow guard. An attacker can choose `central_dir_offset` and `central_dir_size` such that their sum wraps modulo 2^64 to a value ≤ `in_length`, passing the check despite both values being individually far larger than the file.

The wrapped values are then trusted to compute the central directory pointer:
```
*central_dir = end_of_central_dir - cd.central_dir_size;
``` [3](#0-2) 
This pointer subtraction can produce an address far outside the memory-mapped input file. Once this bogus pointer is used to walk entries via `ProcessCentralDirEntry()` (`third_party/ijar/zip.cc:493-545`), which itself performs **no** `EnsureRemaining`-style bounds checking (unlike `InputZipFile::ProcessLocalFileEntry`, which does call `EnsureRemaining` before reading fields, e.g. `third_party/ijar/zip.cc:334-370`), the parser will read heap memory adjacent to (or far from) the mmap'd buffer as if it were file-name/extra-field/attribute data, and that data is subsequently written into the constructed output jar/entry name (`filename[...]`, `attr`, `offset`, sizes) via `WriteLocalFileHeader`/copy paths in `third_party/ijar/zip.cc`.

### Impact Explanation
Because the read bytes originate from process heap memory beyond the intended input buffer and can be echoed into filenames/attributes of the generated (ijar) output artifact, this is a heap out-of-bounds read that can disclose adjacent heap memory (potentially other files' contents or heap metadata) into a build output that the invoking user/CI can retrieve — matching the "Information Disclosure (disclosing some critical heap chunk metadata, even other applications' private data)" impact described in the reference advisory. Depending on the wrapped offset it can also crash the tool (DoS), but the disclosure path is the stronger, reachable impact here.

### Likelihood Explanation
`ijar` is invoked by Bazel automatically whenever a `.jar` is used as a Java dependency to produce interface jars; such `.jar` files routinely originate from external repositories/mirrors fetched over `http_jar`/`maven_jar`-style rules, i.e., content controlled by an unprivileged, remote party (a hostile origin server or mirror). No checksum enforcement on interior ZIP central-directory bytes exists at this parsing layer — sha256/integrity pinning on the archive as a whole does not prevent a maliciously crafted, checksum-matching archive from containing this internal inconsistency (the bug is in interpreting the archive's own metadata, not in whether the archive matches its pinned digest). This makes the vector directly reachable under the described "hostile origin server serving content a build consumes" premise.

### Recommendation
- In `FindZipCentralDirectory()` (`third_party/ijar/zip.cc:766`), check `central_dir_offset > in_length - central_dir_size` (or use overflow-checked/`absl::CheckedAdd`-style arithmetic) instead of a raw sum, and also independently validate `central_dir_offset <= in_length` and `central_dir_size <= in_length` before adding.
- Add explicit `EnsureRemaining`-equivalent bounds checks in `ProcessCentralDirEntry()` before reading `file_name_length`, `extra_field_length`, and `file_comment_length`-derived spans, mirroring the checks already present in `ProcessLocalFileEntry()`.

### Proof of Concept
A reproducible test can be added alongside the existing GoogleTest-based header tests (see `src/tools/singlejar/zip_headers_test.cc` for style) but targeting `third_party/ijar/zip.cc`'s `FindZipCentralDirectory`:
1. Construct an in-memory buffer representing a minimal ZIP with a standard EOCD record plus an appended ZIP64 EOCD + locator.
2. Set the ZIP64 EOCD's `central_dir_size` to a large 64-bit value (e.g. `0xFFFFFFFFFFFFFFF0`) and `central_dir_offset` to a value chosen so that `central_dir_offset + central_dir_size` wraps to a small number ≤ `in_length`.
3. Call `FindZipCentralDirectory(bytes, in_length, &offset, &central_dir)` and assert that it incorrectly returns `true` with a `central_dir` pointer computed outside `[bytes, bytes + in_length)`.
4. Feed the crafted file through `ZipExtractor::Create`/`ProcessAll` and observe an out-of-bounds read (e.g., via ASan) when `ProcessCentralDirEntry` dereferences the bogus pointer.

Note: I could not locate an existing `zip_test.cc`/fuzz harness for `third_party/ijar/zip.cc` in the indexed codebase, so a background agent would need to create this test file from scratch following the pattern of `src/tools/singlejar/zip_headers_test.cc`. Due to index size limits, some file contents (e.g., any existing ijar test files) may not be fully visible to this analysis — a full repository checkout via a Devin session would be needed to confirm whether such tests already exist before adding new ones.
