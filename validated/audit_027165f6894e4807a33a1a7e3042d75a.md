## Finding

An analogous unbounded-memory-growth pattern to the Jetty DosFilter issue exists in java-tron's Ethereum-compatible JSON-RPC log filter subsystem, reachable by any anonymous JSON-RPC client.

### Title
Unbounded per-filter result queue in `eth_newFilter`/`LogFilterAndResult` permits JSON-RPC memory-exhaustion DoS - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogFilterAndResult.java`)

### Summary
`eth_newFilter` caps the *number* of concurrently registered filters via `maxLogFilterNum`, but does not cap the *size* of any individual filter's internal result queue. Each filter's `LogFilterAndResult` wraps an unbounded `LinkedBlockingQueue<LogFilterElement>` that a background block-processing thread (`handleLogsFilter`) keeps pushing matched log entries into, for every incoming block, until the filter is polled (`eth_getFilterChanges`/`eth_getFilterLogs`, which drains it) or the filter expires.

### Finding Description
`newFilter` only bounds the number of live filter objects: [1](#0-0) 

Each filter's queue is unbounded and grows on every matching block event via `processLogFilterEntry` -> `LogFilterAndResult.add`: [2](#0-1) [3](#0-2) 

The queue is drained only when the client actively polls (`popAll()` in `getFilterResult`), and the filter is removed only when `isExpire()` becomes true during a subsequent `handleLogsFilter` pass: [4](#0-3) [5](#0-4) 

An anonymous client can call `eth_newFilter` (via HTTP/JSON-RPC, no auth required) with an empty/broad filter (no address/topic restriction) to match every log emitted by every transaction on the chain, and simply never poll it. Between creation and expiry, the queue accumulates one `LogFilterElement` per matched log across every processed block — with `maxLogFilterNum` defaulting to 20000, this can be repeated at scale, and the client can also cycle through creating fresh filters just before older ones expire to keep aggregate queue memory sustained rather than periodically released.

### Impact Explanation
Unlike a true unbounded-forever leak, this is bounded per filter by the configured expiry window (`EXPIRE_SECONDS`, referenced in `FilterResult.updateExpireTime()`), so the severity is time-window dependent rather than an immediate crash from a single request. However, because: (1) the filter *count* cap (`maxLogFilterNum`, default 20000) is checked, but not the *content size* per filter, and (2) high-throughput chains generate log volume proportional to blocks × transactions × events, a moderately funded attacker issuing many broad, unpolled filters can drive server heap usage far beyond normal operating levels, potentially triggering `OutOfMemoryError` and taking down the FullNode's JSON-RPC/HTTP service — consistent with CWE-400 impact class from the reference Jetty advisory. Because I was unable to retrieve the exact value of `EXPIRE_SECONDS` before running out of tool calls, I cannot confirm the precise exploitation window; this constrains confidence in severity (this would need to be Medium at most, contingent on that constant being large enough or the attacker being able to sustain many concurrent max-size queues).

### Likelihood Explanation
The JSON-RPC HTTP endpoint (`httpFullNodeEnable`) is commonly enabled on public FullNodes to serve Ethereum-tooling compatibility (MetaMask, web3 libraries, etc.), and `eth_newFilter`/log-filter creation requires no authentication — any anonymous API client can reach it. `GlobalRateLimiter`/`IPQpsStrategy` throttle request rate but do not limit the number of matched logs a single already-created filter can accumulate.

### Recommendation
Bound the per-filter result queue (e.g., cap `LinkedBlockingQueue` capacity, drop or coalesce oldest entries, or reject/auto-uninstall filters whose backlog exceeds a configurable threshold), and/or reduce `EXPIRE_SECONDS` for unpolled filters, and/or count total buffered elements across all filters toward `maxLogFilterNum`/a new memory-oriented limit rather than only filter count.

### Proof of Concept
Because I do not have execution access, this is not empirically verified — the following describes the reachable path based on code inspection:
1. Attacker connects to the FullNode's JSON-RPC HTTP endpoint (default port 8545, no auth).
2. Attacker repeatedly calls `eth_newFilter({})` (empty filter = matches all logs) up to `maxLogFilterNum` (20000) times, retaining filter IDs but never calling `eth_getFilterChanges`/`eth_getFilterLogs`.
3. As the chain processes new blocks, `handleLogsFilter` pushes every matched `LogFilterElement` into each of the 20000 unbounded queues via `LogFilterAndResult.add` [3](#0-2) .
4. Before filters expire, the attacker creates a fresh batch of filters to replace expiring ones, sustaining aggregate unbounded queue growth and pressuring the JVM heap.

Given the uncertainty around the exact `EXPIRE_SECONDS` value and the fact this requires sustained attacker activity rather than a single crafted request, I could not fully confirm this reaches "High/Critical, node crash" severity within the tool-call budget available — a Devin session with full repo access would be needed to inspect the exact `EXPIRE_SECONDS` constant and any additional bounding logic (e.g., in `Args`/config defaults) to finalize the severity assessment.

public class LogFilterAndResult extends FilterResult<LogFilterElement> {

  @Getter
  private final LogFilterWrapper logFilterWrapper;

  public LogFilterAndResult(FilterRequest fr, long currentMaxBlockNum, Wallet wallet)
      throws JsonRpcInvalidParamsException {
    // eth_newFilter, no need to check block range
    this.logFilterWrapper = new LogFilterWrapper(fr, currentMaxBlockNum, wallet, false);
    result = new LinkedBlockingQueue<>();
    this.updateExpireTime();
  }

  @Override
  public void add(LogFilterElement logFilterElement) {
    result.add(logFilterElement);
  }
