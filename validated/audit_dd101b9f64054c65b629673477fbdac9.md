### Title
Slippage/deprecation protection for `ExchangeTransactionContract` is silently disabled when `allowHardenExchangeCalculation` is set - (`File: framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
Both `pushTransaction()` and `processBlock()` in `Manager.java` are supposed to unconditionally reject `ExchangeTransactionContract` transactions post-fork (this contract type was deprecated because the internal DEX pricing model diverges sharply from real market price, making it exactly the kind of un-guarded, slippage-vulnerable P&L settlement the external report describes). The rejection is gated by a single dynamic-parameter check, `allowHardenExchangeCalculation`, which entirely disables the ban.

### Finding Description
`isExchangeTransaction` is used both to gate `pushTransaction()` (single-transaction broadcast path) and, via `rejectExchangeTransaction`, to gate `processBlock()` (block application path): [1](#0-0) 

```java
private boolean isExchangeTransaction(Transaction transaction) {
  if (getDynamicPropertiesStore().allowHardenExchangeCalculation()) {
    return false;
  }
  ...
  case ExchangeTransactionContract: return true;
  ...
}

private void rejectExchangeTransaction(Transaction transaction) throws ContractValidateException {
  if (isExchangeTransaction(transaction) && chainBaseManager.getForkController()
          .pass(Parameter.ForkBlockVersionEnum.VERSION_4_8_0_1)) {
    throw new ContractValidateException("ExchangeTransactionContract is rejected");
  }
}
```

If `allowHardenExchangeCalculation` is enabled (a dynamic on-chain parameter, `ALLOW_HARDEN_EXCHANGE_CALCULATION`, toggled by proposal), `isExchangeTransaction` always returns `false`, which means:
- `pushTransaction()` no longer rejects the incoming `ExchangeTransactionContract`: [2](#0-1) 
- `processBlock()`'s call to `rejectExchangeTransaction(transactionCapsule.getInstance())` becomes a silent no-op for every transaction in the block: [3](#0-2) 

This is confirmed by the test explicitly documenting the bypass behavior: [4](#0-3) 

Once the ban is bypassed, the transaction reaches `ExchangeTransactionActuator`, whose settlement math (`exchangeCapsule.transaction(...)`) is executed against whatever pool state exists at that instant, with no oracle or external price reference — the exact bug class from the report ("settlement executed with no protection against price divergence between initiation and execution"). While `ExchangeTransactionActuator.doValidate()` does check a caller-supplied `expected` floor against the same-block pool ratio: [5](#0-4) 
that check only protects the caller against slippage within their *own* transaction; it does nothing to prevent the pool itself from having been deliberately re-enabled against the intent of the protocol's own deprecation guard, and it provides no protection for other exchange participants (LPs) whose pool share is repriced by every subsequent bypassed transaction. The re-enable path also silently reactivates the legacy `ExchangeProcessor`/`SafeExchangeProcessor` constant-product AMM formula, whose historical purpose was retired specifically because of unbounded slippage/manipulation risk in low-liquidity or attacker-seeded pools (e.g. `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeCreateActuator` remain fully reachable once the gate reopens).

### Impact Explanation
Any account holder can call `wallet/exchangetransaction` (or submit a raw signed `ExchangeTransactionContract`) once `allowHardenExchangeCalculation` is toggled on. This reopens a deprecated, unguarded on-chain AMM whose pricing is decoupled from any external oracle. A single large trade (or a sequence of trades within one block, since nothing else rate-limits per-block exchange volume) can move the pool price arbitrarily, letting an attacker drain the counter-asset side of any exchange pool that still holds a balance, or force LPs / late traders into economically ruinous fills — a direct loss/theft-of-funds impact once the flag is set. Since the flag is a `DynamicPropertiesStore` value controlled by committee proposal, this is a systemic re-exposure of a previously-closed attack surface rather than a self-contained isolated bug, and it silently defeats both of the independent defense-in-depth checks (`pushTransaction` and `processBlock`) that were added specifically to shut this feature off.

### Likelihood Explanation
Reaching the vulnerable path requires only (a) `allowHardenExchangeCalculation` being enabled (a legitimate, reachable committee-controlled parameter, not a privileged/compromised-node assumption) and (b) any account broadcasting a normally-formed `ExchangeTransactionContract` transaction — both are within the "unprivileged transaction broadcaster" threat model. No malicious SR/witness/peer collusion is required.

### Recommendation
Do not couple the exchange-transaction deprecation gate to `allowHardenExchangeCalculation`. The ban check (`isExchangeTransaction`) should be evaluated independently of whether the hardened math path is in use — e.g., keep a separate flag/fork check for "exchange feature deprecated" that is always enforced once the fork height is passed, regardless of the hardened-calculation toggle, in both `pushTransaction()` and `processBlock()`/`rejectExchangeTransaction()`.

### Proof of Concept
1. Chain state has `allowHardenExchangeCalculation = 0` (default); confirm `ExchangeTransactionContract` transactions are rejected in `pushTransaction()` with `"ExchangeTransactionContract is rejected"`, as shown by `isExchangeTransactionBypassedWhenHardenedEnabled` in [4](#0-3) .
2. A committee proposal (or, in a test harness, `dynamicPropertiesStore.saveAllowHardenExchangeCalculation(1)`) sets the flag to `1`.
3. `isExchangeTransaction()` now unconditionally returns `false` for the same contract, so `pushTransaction()`'s early rejection at [6](#0-5)  and the block-level `rejectExchangeTransaction` guard in `processBlock` at [3](#0-2)  are both bypassed.
4. The transaction reaches `ExchangeTransactionActuator.execute`, which mutates the pool balances via `exchangeCapsule.transaction(...)` and transfers `anotherTokenQuant` to the caller, exactly as exercised by the existing `hardenedSuccessExchangeTransaction` test at [7](#0-6) , demonstrating that once the flag is set, exchange trades execute end-to-end against the un-gated AMM pool with no external price protection.

  @Test
  public void isExchangeTransactionBypassedWhenHardenedEnabled() throws Exception {
    Transaction exchange = Transaction.newBuilder().setRawData(
        Transaction.raw.newBuilder().addContract(
            Transaction.Contract.newBuilder()
                .setType(ContractType.ExchangeTransactionContract)
                .setParameter(Any.pack(ExchangeTransactionContract.newBuilder()
                    .setExchangeId(1L).setQuant(1L).setExpected(1L).build()))
                .build())).build();

    java.lang.reflect.Method m = Manager.class.getDeclaredMethod(
        "isExchangeTransaction", Transaction.class);
    m.setAccessible(true);

    // Default: hardened disabled (==0) -> contract is treated as exchange
    chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);
    Assert.assertTrue("Exchange tx must be detected when hardened disabled",
        (boolean) m.invoke(dbManager, exchange));

    // Hardened enabled -> bypass returns false
    chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(1);
    Assert.assertFalse("Exchange tx must be bypassed when hardened enabled",
        (boolean) m.invoke(dbManager, exchange));

    // Reset
    chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);
  }
