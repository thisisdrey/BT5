### Title
Check-then-decrypt-then-update race in the AEAD replay window permits a duplicated (replayed) data-plane packet to be processed twice - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split anti-replay enforcement into three separate steps — `window.Check()`, the actual AEAD decrypt, and `window.Update()` — each guarded by its own independent lock acquisition rather than one atomic critical section. This mirrors the reported `V3Vault.setReserveFactor()` class of bug: a piece of shared, order-sensitive state (the replay bitmap) is read, then a slow/blocking operation is performed, and only afterward is the state finally committed — with no guarantee that the commit happens before a second, concurrent actor can observe and act on the same pre-commit state.

### Finding Description
`Decrypt` (and the parallel `VerifyRelay`) do: [1](#0-0) 

1. `cs.decryptLock.Lock(); result := cs.window.Check(l, messageCounter); cs.decryptLock.Unlock()`
2. `cs.dKey.DecryptDanger(...)` — performed **outside** any lock
3. `cs.decryptLock.Lock(); result = cs.window.Update(l, messageCounter); cs.decryptLock.Unlock()`

Between steps 1 and 3 the counter has not yet been marked as seen in the sliding-window bitmap (`bits.go`, `Check`/`Update`). If two copies of the same encrypted packet (same `messageCounter`) are handed to two different reader goroutines at the same time — which is directly possible in Nebula's normal deployment because `listen.routines`/`recvmmsg` batches feed multiple concurrent `listenOut`/`readOutsidePackets` goroutines per `HostInfo`/`ConnectionState` — both goroutines can pass `Check()` before either has called `Update()`. Both then proceed to run the (stateless, deterministic) AEAD decrypt and hand the resulting plaintext onward (e.g. into `consumeInsidePacket`/tun write, or `handleOutsideRelayPacket`'s forward-to-relay-target path for `VerifyRelay`). Only afterwards does the losing goroutine's `Update()` call return `false`, but that happens too late to undo the plaintext that was already delivered/forwarded by the winning goroutine — and the losing goroutine's own `Decrypt`/`VerifyRelay` result is only rejected *after* it already spent the cost of decrypting.

This is the same shape of bug as the report: the code updates the authoritative "already applied" state (reserve factor / replay bit) *after* other logic has already consumed the old (pre-update) state, so an attacker who can duplicate a captured packet on the wire (no CA-signed certificate needed — this is on-path/off-path duplication of already-observed ciphertext, not forgery) can force one of the two colliding requests through the "not yet marked" window.

The project's own changelog entry ("Lock replay window updates so concurrent readers can't corrupt it. (#1802)") shows the team has already hardened `Bits` against *data-structure* corruption from concurrent access, but that fix only serializes the individual `Check`/`Update` calls — it does not close the TOCTOU gap between them, which is exactly what still permits a duplicate/replayed packet to be treated as fresh under concurrency, most plausibly for relayed traffic where `VerifyRelay`'s window gap directly gates whether a relay re-forwards a frame (the exact scenario the project's own `TestRelayReplayProtection` test was written to guard against, but only for the "advance-the-window" omission bug, not for this narrower concurrent race). [2](#0-1) 

### Impact Explanation
Successful exploitation lets an attacker with the ability to duplicate an already-captured ciphertext packet toward the target cause the anti-replay window to admit a duplicate under concurrency, resulting in:
- Duplicate processing/delivery of a previously-seen encrypted data-plane packet (traffic replay), and
- On relay nodes specifically, a duplicate relay frame being forwarded a second time toward the relay target, defeating the very replay protection `VerifyRelay` is supposed to provide.

This does not bypass authentication or certificate checks and requires a race window (multiple listener routines/goroutines processing the same ConnectionState concurrently), so it is a genuine but narrow traffic-replay weakness rather than a full authentication bypass.

### Likelihood Explanation
Likelihood is moderate: Nebula supports multiple listen/reader routines (`listen.routines`, `recvmmsg` batching) that can deliver packets destined for the same tunnel/index concurrently to different goroutines, and nothing prevents an attacker from replaying (re-injecting) a previously captured, valid ciphertext packet at the network layer. The race window is narrow (must land between `Check` and `Update` on two goroutines), so consistent exploitation would require sending several duplicate copies in a tight burst, but this is a low-cost, purely network-level (no cryptographic material needed) attack.

### Recommendation
Perform the check-decrypt-update sequence such that the check and the eventual "mark seen" are atomic with respect to concurrent duplicate counters, e.g.:
- Reserve the counter (mark provisionally "in flight") under the same lock as the initial `Check`, before decrypting, and only finalize/roll back after decrypt succeeds/fails, or
- Serialize processing per `ConnectionState`/counter such that a second packet bearing an in-flight counter is rejected immediately rather than allowed to decrypt concurrently.

### Proof of Concept
Not independently reproducible from the indexed code alone; the race requires driving concurrent goroutines against the same `ConnectionState.window` with an identical `messageCounter` (e.g., by configuring multiple `listen.routines`/batched UDP reads and injecting the same captured ciphertext packet on two reader paths near-simultaneously), analogous to the project's own `TestRelayReplayProtection` in `e2e/tunnels_test.go` but tightened to race two deliveries of the identical frame instead of sequential replays. I could not fully verify runtime scheduling behavior (goroutine interleaving) without executing the code, which the current tool access does not support — a Devin session with repo execution access would be needed to build a deterministic reproduction and confirm actual exploitability under Go's scheduler and Nebula's configured concurrency settings.

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
