### Title
Missing Cache-Control headers on GET endpoints that mint fresh shielded spending keys leak wallet-draining secrets to shared caches - (File: framework/src/main/java/org/tron/core/services/http/GetNewShieldedAddressServlet.java)

### Summary
The CVE analog is GitLab's "Information Exposure Through Browser Caching" (CVE-2018-18640): sensitive dynamic responses were served without cache-preventing headers, letting an intermediary/browser cache replay secret content to a different user. java-tron's HTTP wallet API has the same defensive gap: none of its servlets ever set `Cache-Control`, `Pragma`, or `Expires` headers (`grep` across `framework/src/main/java/org/tron/core/services/http/**` for `setHeader|addHeader` returns no matches), and no such header is added anywhere in the codebase at all.

### Finding Description
`GetNewShieldedAddressServlet.doGet`/`doPost` calls `Wallet.getNewShieldedAddress()`, which internally does: [1](#0-0) 

This method generates a brand-new random `SpendingKey` via `SpendingKey.random()` [2](#0-1) 
and returns the **full** secret material — `sk`, `ask`, `nsk`, `ovk`, `ivk`, plus the derived `paymentAddress` — in the JSON response body, with no query parameters distinguishing the request: [3](#0-2) 

The sibling endpoints `GetSpendingKeyServlet`, `GetExpandedSpendingKeyServlet`, `GetIncomingViewingKeyServlet` have the same shape: a simple `GET /wallet/get...` request that returns freshly generated (or attacker-supplied-derived) key material with no cache directives set on the response: [4](#0-3) 

Because no servlet, filter, or the underlying `HttpService`/Jetty configuration ever emits `Cache-Control: no-store`, `Pragma: no-cache`, or `Vary` headers, a browser, corporate/CDN forward proxy, or any HTTP cache sitting in front of the full node's Wallet HTTP API (a common deployment pattern for public-facing full-node HTTP endpoints) is free to cache the response to `GET /wallet/getnewshieldedaddress` (or `/wallet/getspendingkey`) keyed only by the URL, since there is no cache-busting header nor any request parameter to differentiate calls. A cache hit then serves the **exact same secret spending key** that was generated for one caller to every other caller who requests the same URL while the cache entry is fresh.

### Impact Explanation
An attacker who is behind the same shared cache (or who controls/observes a caching layer, e.g. a shared corporate proxy, a misconfigured CDN, or simply repeats requests fast enough to hit a stale cache entry) receives the identical `sk`/`ask`/`nsk`/`ivk` and `paymentAddress` that a legitimate victim believes is private. Any shielded funds a victim later sends to that "fresh" `paymentAddress`, believing only they hold the spending key, can be spent/stolen by the attacker who also received the cached key material — an unauthorized-account-operation / theft-of-shielded-funds primitive, matching the "concrete unauthorized account operation, theft ... of funds" acceptance bar.

### Likelihood Explanation
Full-node HTTP API endpoints are frequently placed behind reverse proxies/CDNs for public dApp/exchange access; many such intermediaries cache GET responses by default unless the origin explicitly opts out with `Cache-Control: no-store`. Since java-tron never sets that header anywhere in its HTTP layer, likelihood depends entirely on deployment topology (whether a caching layer sits in front), which is outside java-tron's control — but the root cause (absence of any anti-caching header on secret-bearing GET responses) is squarely a code-level defect, matching the CVE's bug class exactly.

### Recommendation
Add `response.setHeader("Cache-Control", "no-store, no-cache, must-revalidate")` (and `Pragma: no-cache`) for all Wallet HTTP endpoints that return secret key material — at minimum `GetSpendingKeyServlet`, `GetExpandedSpendingKeyServlet`, `GetNewShieldedAddressServlet`, `GetIncomingViewingKeyServlet`, `GetAkFromAskServlet`, `GetNkFromNskServlet` — ideally centralized in a shared response filter so all `/wallet/*` responses are marked non-cacheable by default.

### Proof of Concept
1. Deploy a full node's HTTP API behind a caching reverse proxy/CDN with default GET caching enabled (no origin opt-out possible since java-tron sets no `Cache-Control` header).
2. Victim A requests `GET /wallet/getnewshieldedaddress`; the proxy caches the JSON response (containing `sk`, `ask`, `nsk`, `ivk`, `paymentAddress`) keyed by URL.
3. Attacker sends the same `GET /wallet/getnewshieldedaddress` request before the cache entry expires and receives the identical cached JSON body — obtaining the same `sk`/`ivk` victim A believes is private.
4. Victim A shares `paymentAddress` and receives shielded funds; attacker uses the leaked `sk`/`ask`/`nsk` to construct a spend transaction and drain the shielded note, since `Wallet.getNewShieldedAddress()` never rotates keys after issuance and the API sets no cache-preventing headers to prevent this replay: [5](#0-4)
