### Title
Shielded-transaction secret keys (spending key, `ask`, `nsk`, `ivk`, `ovk`) accepted as HTTP GET query parameters, exposing them in logs and browser history - (File: framework/src/main/java/org/tron/core/services/http/GetExpandedSpendingKeyServlet.java)

### Summary
Multiple Wallet HTTP API servlets that operate on shielded-transaction key material implement `doGet()` handlers that read highly sensitive secrets directly from the URL query string via `HttpServletRequest.getParameter(...)`. This is the same bug class as CVE-2019-3803 (Concourse putting the user's access token in a URL during login): a secret credential is placed in a request URL instead of the request body, so it ends up recorded wherever URLs are recorded — web/reverse-proxy access logs, server logs, browser history, and `Referer` headers.

### Finding Description
Several servlets under `framework/src/main/java/org/tron/core/services/http/` expose `doGet` methods that pull spend-authority/viewing secrets straight from query parameters:

- `GetExpandedSpendingKeyServlet.doGet` reads the raw spending key from `request.getParameter("value")` and forwards it to `wallet.getExpandedSpendingKey(...)`. [1](#0-0) 

- `GetAkFromAskServlet.doGet` and `GetNkFromNskServlet.doGet` take the `ask`/`nsk` secret components via `request.getParameter("value")`. [2](#0-1) [3](#0-2) 

- `GetIncomingViewingKeyServlet.doGet` and `GetZenPaymentAddressServlet.doGet` accept `ak`/`nk`/`ivk`/`d` viewing-key material via query parameters. [4](#0-3) [5](#0-4) 

- `ScanAndMarkNoteByIvkServlet.doGet` and `ScanNoteByOvkServlet.doGet` accept the full incoming/outgoing viewing key (`ivk`, `ak`, `nk`, `ovk`) — the material that lets a party decrypt/track all shielded notes for an address — as GET parameters. [6](#0-5) [7](#0-6) 

The generic `checkGetParam` helper in `Util.java` confirms the framework-wide pattern of reading parameters straight off the GET query string for these APIs. [8](#0-7) 

The project's own configuration documentation acknowledges the underlying risk of exposing shielded-key APIs to untrusted/remote callers and gates some shielded transaction-creation flows behind `node.allowShieldedTransactionApi` (default `false`), recommending local-only use. [9](#0-8) 

I was **not able to confirm from the code inspected** that this same `allowShieldedTransactionApi` gate is enforced on every one of the key-derivation/viewing-key servlets listed above (`GetAkFromAskServlet`, `GetNkFromNskServlet`, `GetExpandedSpendingKeyServlet`, `GetIncomingViewingKeyServlet`, `GetZenPaymentAddressServlet`, `ScanAndMarkNoteByIvkServlet`, `ScanNoteByOvkServlet`); the flag appears referenced only a handful of times in `Wallet.java` while these methods (`getAkFromAsk`, `getExpandedSpendingKey`, `getNkFromNsk`, `getIncomingViewingKey`, `scanAndMarkNoteByIvk`, `scanNoteByOvk`, `getPaymentAddress`) appear over two dozen times, suggesting most are not individually gated by that flag. This should be verified directly against `Wallet.java` before treating the finding as definitively unmitigated on a default deployment.

### Impact Explanation
If any of these GET endpoints are reachable (locally or remotely, depending on deployment/proxy configuration), the caller's shielded spending key, `ask`, `nsk`, `ivk`, `ovk`, or viewing keys are placed in the URL. Any component that logs full request URLs (nginx/HAProxy access logs, application server logs, browser history, intermediate CDN/proxy logs, or a leaked `Referer` header) will persist the secret in plaintext. Disclosure of `ivk`/`ovk` breaks shielded-transaction confidentiality (an attacker can decrypt/track all notes for the address); disclosure of the spending key or `ask`/`nsk` derivatives can enable unauthorized spending of shielded funds — matching the CVE-2019-3803 impact category of remote credential disclosure via URL/log/history exposure (`C:H` in the reference CVSS vector).

### Likelihood Explanation
Exploitation does not require any special privilege beyond the ability to observe logs, proxy records, or browser history for the machine issuing the request — exactly the threat model of the original CVE. The likelihood is reduced by the fact that these Wallet HTTP endpoints are documented as intended for local/private use and some shielded-transaction flows are gated behind the `allowShieldedTransactionApi` opt-in flag; however, based on the code reviewed, it is unclear whether that gate covers all of the listed servlets, and POST equivalents exist alongside the vulnerable GET handlers, meaning the insecure GET code path exists in the shipped binary regardless of default configuration.

### Recommendation
Remove or disable the `doGet` handlers for all servlets that accept shielded-key secrets (spending key, `ask`, `nsk`, `ivk`, `ovk`, `ak`, `nk`) and require POST with a JSON body for these operations, consistent with how sensitive credentials should never appear in a URL. Additionally, confirm and, if missing, enforce the `allowShieldedTransactionApi` (or an equivalent explicit opt-in/localhost-only) check uniformly across every key-derivation and viewing-key servlet, not just a subset.

### Proof of Concept
1. Enable/expose the FullNode HTTP API (`node.http.fullNodeEnable = true`, per `common/src/main/resources/reference.conf`) behind a reverse proxy that logs full request URLs (a common production pattern).
2. Issue: `GET http://<node>/wallet/getexpandedspendingkey?value=<hex_spending_key>&visible=true`
3. The proxy/server access log now contains `value=<hex_spending_key>` in plaintext.
4. Anyone with read access to that log (or to the browser history of the machine that issued the request) can extract the spending key and use it to spend the victim's shielded TRC-20/TRC-10 assets, or use a leaked `ivk`/`ovk` from `getincomingviewingkey`/`scannotebyovk` GET calls to decrypt all of the victim's shielded transaction history.
