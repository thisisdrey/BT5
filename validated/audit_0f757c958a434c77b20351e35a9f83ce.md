### Title
Per-IP QUIC connection rate limiter can be trivially evaded via IPv6 address churn, enabling exhaustion of the global connection rate limiter and DoS to legitimate senders - (streamer/src/nonblocking/connection_rate_limiter.rs)

### Summary
`ConnectionRateLimiter` keys its `KeyedRateLimiter<IpAddr>` strictly on the full `IpAddr` with no prefix/subnet aggregation, so `is_allowed`/`register_connection` treat every distinct IPv6 address as an independent bucket. An attacker who legitimately controls a routed IPv6 prefix (e.g. a typical ISP-issued `/64` or larger, common for cloud/VPS/broadband allocations) can complete one real QUIC handshake per synthesized address, each of which is "new" to the limiter and thus always allowed, entirely bypassing `DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE`.

### Finding Description
`ConnectionRateLimiter::is_allowed`/`register_connection` operate on `IpAddr` keys with no CIDR normalization: [1](#0-0) 

The server calls these functions with the raw remote socket's IP taken straight from the QUIC handshake in `run_server`/`setup_connection`: [2](#0-1) [3](#0-2) 

There is no code anywhere in the streamer, QoS (`SwQos`/`SimpleQos`), or `ConnectionTable` path that truncates or masks IPv6 addresses to a subnet (e.g. `/64`) before using them as a rate-limiting or connection-table key — `ConnectionTableKey::IP`/`ConnectionTableKey::new` also key on the full address: [4](#0-3) 

Because a real customer allocation of an IPv6 `/64` contains 2^64 addresses, and because the handshake-verification-gated design ("we should only modify server state once source IP is verified", `connection_rate_limiter.rs:32-33`) only asserts that the client *actually completed a QUIC handshake from that address* (not that it's a "new" identity in any resource-bounded sense), an attacker who owns a routed prefix can bind and complete legitimate handshakes from a large number of distinct source addresses, each incrementing:
1. `total_incoming_connection_attempts` and consuming a token from the shared `overall_connection_rate_limiter` (`TOTAL_CONNECTIONS_PER_SECOND = 2500`) — this check applies uniformly before any stake/QoS differentiation: [5](#0-4) [6](#0-5) [7](#0-6) 

2. Never tripping the per-IP `rate_limiter`, since each source address is a brand-new key with a full token bucket.

The code's own design comment states the intended mitigation model explicitly assumes IP is a scarce, control-asserted identity ("rate-limit abusive peers by (control-asserted) ip"), which is false for IPv6 where a single attacker can trivially and legitimately possess an enormous address space without any spoofing.

### Impact Explanation
This is a genuine QoS/rate-limit evasion (falls under "QoS evasion" bounty category): by rotating through addresses in an owned IPv6 prefix, a single unstaked attacker can consume the entire shared `overall_connection_rate_limiter` budget (`MAX_CONNECTION_BURST = 1000`, refill `TOTAL_CONNECTIONS_PER_SECOND = 2500`) indefinitely, since the per-IP limiter never engages to throttle them back. Because this global limiter gates *all* incoming connections before stake is even determined, this starves legitimate unstaked (and potentially staked, since the global check happens before `get_connection_stake`/QoS peer-type differentiation) connection attempts, denying transaction ingress to a leader's TPU during the attack window.

### Likelihood Explanation
Feasibility depends only on the attacker possessing a routed IPv6 prefix large enough to generate more distinct addresses than the per-IP burst allowance would tolerate from one address — a widely available resource (cloud providers and even many home ISPs commonly hand out a `/64` or larger). No spoofing, staking, gossip, or validator control is required; the attacker only needs to open real QUIC connections from many bound addresses to the leader's public TPU port, which is squarely within the permitted attacker model. This is straightforward and repeatable with standard OS support for binding to many addresses in an owned subnet.

### Recommendation
Aggregate IPv6 keys to a coarser prefix (e.g., `/56` or `/64`, configurable) before using them as the `ConnectionRateLimiter`/`ConnectionTableKey` key, so that address rotation within a prefix does not reset the token bucket. This should be applied consistently in `ConnectionRateLimiter::is_allowed`/`register_connection` and in `ConnectionTableKey` construction used by `SwQos`/`SimpleQos`.

### Proof of Concept
Integration test plan (extending the existing test harness in `streamer/src/nonblocking/connection_rate_limiter.rs` and `tpu-client-next/tests/connection_workers_scheduler_test.rs`):
```rust
#[tokio::test]
async fn test_ipv6_prefix_evades_per_ip_rate_limit() {
    let limiter = ConnectionRateLimiter::new(
        DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE, // 8
        DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE * 10,
        4,
    );
    // Same /64 prefix, different host bits -> distinct IpAddr keys
    let base: u128 = 0x2001_0db8_0000_0001_0000_0000_0000_0000;
    let mut accepted = 0;
    for i in 0..1000u128 {
        let ip = IpAddr::V6(Ipv6Addr::from(base | i));
        assert!(limiter.is_allowed(&ip), "each new /64 host should look unseen");
        if limiter.register_connection(&ip) {
            accepted += 1;
        }
    }
    // Expect all 1000 to succeed, proving the DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE=8
    // guarantee gives no protection when the attacker rotates addresses in one /64.
    assert_eq!(accepted, 1000);
}
```
A full end-to-end version would spin up `run_server` with a real QUIC endpoint, spawn N client connections from N distinct loopback-adjacent bound IPv6 addresses within one `/64` (achievable in a test namespace with `ip -6 addr add` on a dummy interface), and assert that `stats.connection_rate_limited_per_ipaddr` stays at 0 while `stats.connection_rate_limited_across_all` climbs and a legitimate control IP's connection attempts are rejected due to `overall_connection_rate_limiter` exhaustion, demonstrating collapse of the aggregate accepted-connection rate for genuine senders.

/// Limits the rate of connections per IP address.
pub struct ConnectionRateLimiter {
    limiter: KeyedRateLimiter<IpAddr>,
}

/// The threshold of the size of the connection rate limiter map. When
/// the map size is above this, we will trigger a cleanup of older
/// entries used by past requests.
const CONNECTION_RATE_LIMITER_CLEANUP_SIZE_THRESHOLD: usize = 100_000;

impl ConnectionRateLimiter {
    /// Create a new rate limiter per IpAddr. The rate is specified as the count per minute to allow for
    /// less frequent connections. Higher limit also allows higher bursts.
    /// num_shards controls how many shards are used in the underlying dashmap,
    /// should be set >= number of contending threads.
    pub fn new(limit_per_minute: u64, max_burst: u64, num_shards: usize) -> Self {
        Self {
            limiter: KeyedRateLimiter::new(
                CONNECTION_RATE_LIMITER_CLEANUP_SIZE_THRESHOLD,
                TokenBucket::new(limit_per_minute, max_burst, limit_per_minute as f64 / 60.0),
                num_shards,
            ),
        }
    }

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }

    pub fn register_connection(&self, ip: &IpAddr) -> bool {
        if self.limiter.consume_tokens(*ip, 1).is_ok() {
            debug!("Request from IP {ip:?} allowed");
            true // Request allowed
        } else {
            debug!("Request from IP {ip:?} blocked");
            false // Request blocked
        }
    }
