### Title
Active-permission holders authorized for `AccountPermissionUpdateContract` can unilaterally overwrite and revoke the Owner permission - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateActuator` lets any signer whose permission's operations bitmap includes `AccountPermissionUpdateContract` completely rewrite an account's Owner, Witness, and Active permissions in a single transaction, with no check that the acting permission itself is the Owner permission. This mirrors the reported CoreBorrow flaw where a role (`GUARDIAN_ROLE`) that was never meant to be a fully trusted admin ends up able to strip the actual admin (`GOVERNOR_ROLE`) of its role, because the access-control model does not require the higher-privileged role to authorize changes that affect it.

### Finding Description
Transaction-level authorization for any contract, including `AccountPermissionUpdateContract`, is decided purely by whether the signing `Permission` (chosen by `permissionId` in the contract) has the corresponding bit set in its `operations` bitmap, via `checkPermissionOperations`/`checkPermission`: [1](#0-0) 

This check is only skipped for `permissionId == 0` (the Owner itself); for any non-owner `Active` permission (`permissionId != 0`), authorization is granted purely if the operations bitmap bit for the contract type is set: [2](#0-1) 

Once that check passes, `AccountPermissionUpdateActuator.validate()`/`execute()` place no additional restriction tying the acting permission to Owner-level trust — it simply validates the structural correctness of the new `owner`, `witness`, and `actives` permissions supplied in the contract and then unconditionally overwrites all of them via `AccountCapsule.updatePermissions`: [3](#0-2) [4](#0-3) 

Because `AccountPermissionUpdateContract` is a valid bit within the "available contract types" bitmap that an account owner can assign to any `Active` permission (confirmed by the test asserting it is part of `checkAvailableContractType`, distinct from the safer default bitmap that explicitly excludes it): [5](#0-4) 

an `Active` permission that is granted this single bit — intended, for example, to let an automated key manage its own active-permission keys — gains the unchecked power to replace the account's `Owner` permission entirely (e.g., set to keys it controls) using only that Active permission's threshold, with no requirement that the current Owner co-sign. This is structurally the same "inconsistent access control" pattern as the CoreBorrow finding: a role/permission that is not, and should not be treated as, the top-level admin can nonetheless mutate the admin role itself.

### Impact Explanation
An account owner who grants a lower-trust `Active` key the `AccountPermissionUpdateContract` capability (a legitimate, documented multi-sig configuration) is exposed to a single malicious or compromised Active-key holder rewriting the Owner permission and locking out every original owner/co-owner key permanently. This is a permanent freezing/loss-of-control of the account (and any assets/authority gated by the Owner permission, including issued TRC10 tokens, delegated resources, and future permission changes), matching the "permanent freezing/unauthorized account operation" bar.

### Likelihood Explanation
Exploitation requires that the account owner has previously granted an `Active` permission the `AccountPermissionUpdateContract` operation bit — a configuration the protocol explicitly allows and does not warn against in the actuator's validation logic, and that keys with a lower threshold than Owner intent can be legitimately delegated for narrower purposes (e.g., managing sub-active permissions). Given multi-sig setups are a real, supported feature (`AllowMultiSign`) and no additional owner-consent check exists in the actuator, likelihood is realistic wherever this delegation pattern is used.

### Recommendation
In `AccountPermissionUpdateActuator.validate()`/`execute()`, disallow modification of the `Owner` permission (and ideally `Witness` permission) unless the transaction was authorized under `permissionId == 0` (i.e., signed by the current Owner permission), regardless of what the acting `Active` permission's operations bitmap contains. Alternatively, exclude `AccountPermissionUpdateContract` from the set of operations assignable to non-Owner permissions entirely, so Active permissions can never gain the ability to rewrite Owner/Active permission sets.

### Proof of Concept
1. Owner account `A` creates an `Active` permission `P2` with threshold 1, one key `K`, and grants `P2` the `AccountPermissionUpdateContract` bit in its operations bitmap via a normal `AccountPermissionUpdateActuator` transaction (signed with `permissionId=0`).
2. Holder of key `K` (or an attacker who compromises `K`) crafts a new transaction with `contract.permission_id = 2` (referencing `P2`), containing an `AccountPermissionUpdateContract` whose `owner` field sets a brand-new Owner permission containing only attacker-controlled keys.
3. `TransactionCapsule.checkPermission`/`checkWeight` ( [1](#0-0) ) validates the signature purely against `P2`'s bitmap/threshold and passes.
4. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)`, replacing `A`'s Owner permission with the attacker's, permanently locking out the legitimate owner.

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
