### Title
Missing validation of ZIP central-directory local-header offset leads to out-of-bounds read in `InputZipFile::ProcessNext` - (File: `third_party/ijar/zip.cc`)

### Summary
Bazel's bundled ijar ZIP/JAR reader (`third_party/ijar/zip.cc`) computes a file cursor directly from the untrusted 32/64-bit "local header offset" field taken from an entry's Central Directory Header, without checking that the resulting position lies inside the memory-mapped input file. The subsequent bounds check (`EnsureRemaining`) is itself defeated by unsigned-integer underflow when this offset is attacker-controlled and too large, allowing the parser to read past the end of the mapped archive — the same bug class as CVE-2022-50507 (fs/ntfs3 unvalidated data-run offset causing use-after-free/OOB read).

### Finding Description
`InputZipFile::ProcessNext()` reads `compressed`, `uncompressed`, and `offset` from `ProcessCentralDirEntry()`, and then unconditionally computes the local-header pointer: [1](#0-0) 

`offset` is fully attacker controlled: it comes straight from the 32-bit `local_header_offset` field of the CDH (with an optional ZIP64 extra-field override to a full 64-bit value): [2](#0-1) [3](#0-2) 

No comparison of `offset` (or `in_offset_ + offset`) against `input_file_->Length()` is performed anywhere before `p` is dereferenced. The only safety net is `EnsureRemaining()`: [4](#0-3) 

This computes `remaining = input_file_->Length() - in_offset` using `size_t` (unsigned) arithmetic. If `in_offset` (i.e., `p - zipdata_in_`, driven by the attacker-controlled `offset`) exceeds `input_file_->Length()`, the subtraction underflows to a huge value, so the check `n > remaining` is false even though `p` already points outside the mapped region. Execution then proceeds into `get_u4le(p)` and `ProcessLocalFileEntry`, which continues to read fields (`file_name_length_`, `extra_field_length_`, compressed/uncompressed data, etc.) from this out-of-bounds pointer — an out-of-bounds read of process memory, mirroring the NTFS `run_unpack` UAF caused by an unvalidated data-run offset.

The `FindZipCentralDirectory()` function does validate that the *central directory itself* fits within the file (`cd.central_dir_offset + cd.central_dir_size > in_length`) , but this only bounds where the central directory starts — it does nothing to validate the *per-entry* local-header offsets read out of that directory, which is exactly the field this bug is missing validation for.

### Impact Explanation
This ijar reader is invoked by Bazel's native `ijar`/`singlejar`-adjacent tooling to parse JAR/ZIP files (e.g., producing interface jars from `.jar` artifacts consumed as Java dependencies). A hostile origin — a compromised or malicious Maven/HTTP artifact source publishing a `.jar`/`.zip` whose declared sha256 legitimately matches the malicious bytes (the attacker controls both, per the threat model) — can craft a CDH entry with an out-of-range `local_header_offset` (or ZIP64 offset). When Bazel's toolchain runs ijar against this artifact, the process reads out-of-bounds memory relative to the mmap'd file, which can crash the tool (segfault) or, depending on heap/mmap layout, read adjacent memory content into internal buffers of the parser. This is a memory-safety violation triggered purely by untrusted archive bytes that a victim's build legitimately fetches and processes — not by a MITM, and not merely a resource-exhaustion DoS, since it is an OOB *read* enabled by defeating an integer bounds check, directly analogous to the kernel KASAN OOB-read report in the source CVE.

### Likelihood Explanation
Any attacker who can publish or serve a `.jar`/`.zip` artifact that ends up on the Java compile/runtime classpath (e.g. via `http_jar`, `maven_install`/Bzlmod modules, or any rule that shells out to ijar on a fetched jar) can trigger this simply by crafting one CDH entry with an oversized offset field — no additional privileges, no network positioning, and no need to defeat the download's checksum (the checksum only certifies "this is the artifact the attacker published", not "this artifact is well-formed"). The bug requires no special build configuration and is reachable with default flags on a current release, since it lies in a foundational, security-unaware C++ parsing routine with no fuzuzing-hardened bounds checks on offsets.

### Recommendation
In `InputZipFile::ProcessNext()` and `ProcessCentralDirEntry()`, validate `offset` (and any ZIP64-overridden 64-bit offset) against `input_file_->Length()` before computing `p`, and change `EnsureRemaining()` to compute the remaining-bytes check using saturating/signed arithmetic (or explicitly check `in_offset > input_file_->Length()` first and fail) so that an out-of-range offset cannot cause `remaining` to underflow. Reject and abort parsing (return an error via `GetError()`) rather than continuing to dereference an out-of-bounds pointer.

### Proof of Concept
A `BuildIntegrationTestCase`/native unit test can reproduce this deterministically:
1. Programmatically construct a minimal ZIP file with one Central Directory Header whose `local_header_offset32` field is set to `0xFFFFFF00` (i.e., far beyond the actual file length) and no valid ZIP64 extra field overriding it consistently (or with the ZIP64 extra field itself set to an out-of-range 64-bit value), followed by a valid EOCD record so `FindZipCentralDirectory` succeeds.
2. Invoke `ZipExtractor::Create()` / `ProcessAll()` (as done in `third_party/ijar/test/zip_test.sh` / `IjarTests.java`) on this crafted file.
3. Observe (under ASan/valgrind, mirroring the kernel KASAN report) a heap-buffer-overflow / out-of-bounds read report inside `InputZipFile::ProcessNext` → `EnsureRemaining` → `ProcessLocalFileEntry`, instead of a controlled `GetError()` failure.

    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
