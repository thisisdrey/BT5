### Title
Unvalidated ERC20 contract address in `ERC20Transactor::deposit_asset_with_surplus` allows arbitrary contract calls from the shared checking account - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::deposit_asset_with_surplus` extracts a contract address (`asset_contract_id`) purely by pattern-matching the `Location` junction (`AccountKey20 { key, .. }`) via `ERC20Matcher`/`AccountKey20ToH160`, with no check that this address corresponds to a genuine, previously-registered ERC20 asset. It then unconditionally issues a `transfer` call to that address, signed by the shared `TransfersCheckingAccount`. This is structurally the same defect as the reported `FCNProduct.sol` bug: an attacker-controlled address argument (there `vaultAddress`, here the ERC20 contract address embedded in the XCM `Asset`'s `Location`) is used directly to invoke a value-moving external call without validating that it refers to an initialized/registered resource.

### Finding Description
`ERC20Matcher` is defined as: [2](#0-1) 

It only checks that the `Location` is local, has no parents, and ends in an `AccountKey20` junction — `AccountKey20ToH160::convert` blindly returns the embedded 20-byte key as the target contract address, with no lookup against any asset registry (unlike `ForeignAssets`/`PoolAssets`, which are backed by `pallet-assets` storage and `LocalMint`/`NonZeroIssuance` checks). Any user constructing an XCM message that references an `Asset` whose `id` is `{parents: 0, interior: X1(AccountKey20{key, network})}` can make `key` be *any* address on the chain.

`deposit_asset_with_surplus` then does: [3](#0-2) 

The call is executed with `OriginFor::<T>::signed(TransfersCheckingAccount::get())` — i.e. it is signed by the chain's shared ERC20 checking/escrow account, not by the message's original submitter. Since `asset_contract_id` is attacker-chosen and unchecked, an attacker can point it at any contract address (not necessarily a real ERC20, but any deployed contract implementing a function whose selector collides with `transfer(address,uint256)`, or even a genuine but unrelated ERC20 in which the checking account happens to hold a balance/allowance) and force the checking account to originate a `transfer` call to that contract. Because the "amount" and "beneficiary" come straight from the attacker's own XCM instructions (`what`, `who`), the attacker fully controls the call's `to`/`value` parameters relative to whatever token contract they pick, while the transaction is signed and paid from the checking account's identity — mirroring the FCN bug where `vaultAddress` was used to call `transferFrom` without verifying `vaults[vaultAddress]` was ever initialized.

### Impact Explanation
If the checking account holds or is ever approved to spend balances in other, unrelated ERC20-like contracts on the chain (a realistic scenario since it's a generic PalletId-derived account used across all ERC20 asset flows), an attacker can drain those balances by crafting deposit instructions that name those contracts as the "asset" being deposited. Even absent stray balances, this allows an unprivileged XCM submitter to force arbitrary contract calls signed by a privileged, shared system account, which is a form of unauthorized/forged execution against `contracts`/`revive` execution and Asset Hub's asset-accounting invariants — the resource identifier (contract address) analogous to `vaultAddress` is never checked against a registered set before performing a fund-moving call.

### Likelihood Explanation
Any account able to submit or trigger an XCM `deposit_asset` operation for the `ERC20Transactor` (via `PolkadotXcm::execute`, or an incoming reserve/teleport deposit routed through this transactor) can trigger this path; no privileged origin, relayer, validator, or governance action is required — only crafting the `Location`/`Asset` id, satisfying the "Impact Gate" requirement of an unprivileged public-entrypoint path with false/underprotected contract-call acceptance.

### Recommendation
Add an explicit registry check (mirroring `LocalMint<NonZeroIssuance<..>>` used for `PoolFungiblesTransactor`) before invoking the ERC20 `transfer`/`transferFrom` call — i.e., only allow `asset_contract_id` values that were explicitly registered (deployed/whitelisted) as ERC20 assets for this transactor, analogous to adding a `validVault`-style modifier that checks the vault/asset is initialized before any transfer is executed.

### Proof of Concept
1. Attacker submits `pallet_xcm::execute` (or a cross-chain reserve/teleport message ending in `DepositAsset`) with `Xcm(vec![..., DepositAsset { assets: Definite(vec![Asset { id: AssetId(Location::new(0, [AccountKey20{ key: TARGET_CONTRACT, network: None }])), fun: Fungible(AMOUNT) }].into()), beneficiary: ATTACKER_LOCATION }])`, where `TARGET_CONTRACT` is any contract address of the attacker's choosing (e.g. one where `TransfersCheckingAccount` holds a balance/approval, from prior unrelated activity).
2. `ERC20Matcher::matches_fungibles` matches this `Asset` and returns `(TARGET_CONTRACT, AMOUNT)` with no registry validation. [4](#0-3) 
3. `deposit_asset_with_surplus` calls `pallet_revive::Pallet::<T>::bare_call` targeting `TARGET_CONTRACT` with `IERC20::transferCall{ to: ATTACKER_ADDRESS, value: AMOUNT }`, signed as `TransfersCheckingAccount`. [5](#0-4) 
4. If `TransfersCheckingAccount` has any balance/allowance in `TARGET_CONTRACT`, funds are transferred to the attacker without any check that `TARGET_CONTRACT` was ever a legitimately onboarded ERC20 asset for this transactor.

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
