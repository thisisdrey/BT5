### Title
Unbounded per-filter result queue accumulation in JSON-RPC `eth_newFilter`/`eth_newBlockFilter` allows memory-exhaustion DoS - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java`)

### Summary
The NanoMQ CVE-2023-33656 root cause is a message-processing path (`message.c`) that keeps allocating memory for incoming messages without a bound, eventually exhausting available memory. java-tron's JSON-RPC filter subsystem has the same bug class: each `LogFilterAndResult`/`BlockFilterAndResult` object created by `eth_newFilter`/`eth_newBlockFilter` owns an internal `BlockingQueue` that every subsequent block/log event appends to, with no cap on the queue length, and the queue is only ever drained on eviction (5 minutes after creation, and only opportunistically the next time a block/log arrives).

### Finding Description
`TronJsonRpcImpl.newFilter` and `newBlockFilter` only bound the *number* of filters (`maxLogFilterNum`, `maxBlockFilterNum`), not the amount of data buffered per filter: [1](#0-0) 

Each filter's accumulation buffer is an unbounded queue created without any size limit: [2](#0-1) 

Every new block, `handleLogsFilter` walks all live filters and appends every matching log element to that filter's `result` queue with no upper bound on how large it can grow: [3](#0-2) 

The only cleanup mechanism is time-based expiry, and even that is lazy — an entry is only actually removed from the map (and thus becomes eligible for GC) the next time a block/log event happens to iterate over it: [4](#0-3) [5](#0-4) 

Because `updateExpireTime()` is only invoked at filter creation (`LogFilterAndResult` constructor) and each time the client calls `getFilterChanges` (`popAll` + `updateExpireTime`), an anonymous client can: [6](#0-5) 
1. Call `eth_newFilter` with a broad match criteria (no address/topic filter) up to `maxLogFilterNum` times.
2. Never call `eth_getFilterChanges`/`eth_uninstallFilter`.
3. Each filter's `result` queue grows unboundedly (every matching `LogFilterElement` for every transaction in every subsequent block, for up to 5 minutes / `EXPIRE_SECONDS`) with no per-filter cap on the number of elements buffered.

This is structurally the same defect class as CVE-2023-33656: a message/record accumulation path without a bound on total buffered memory, relying only on time or count-based cleanup that a client can outrun by generating (or simply allowing normal on-chain activity to generate) enough log events before the natural expiry fires.

### Impact Explanation
An unauthenticated JSON-RPC client (this is a public API endpoint reachable by any HTTP client, no signed transaction required) can drive the fullnode/solidity node process memory usage to grow substantially by opening many broad-match log filters and withholding polls, potentially causing an OutOfMemoryError and node crash, which for API/RPC nodes serving `TronJsonRpcImpl` constitutes denial of service (the node can no longer serve requests) — matching the accepted impact category "node crash or halt" / "an API the node can no longer serve".

### Likelihood Explanation
Reachability requires only anonymous access to a JSON-RPC endpoint with `eth_newFilter` enabled (a commonly enabled feature on public/RPC-serving java-tron nodes), and no signed transaction or special privilege. The number of filters is capped by `maxLogFilterNum`/`maxBlockFilterNum`, so severity is bounded by that configuration value multiplied by network log throughput during `EXPIRE_SECONDS` (5 minutes), which can still be significant on busy chains and is entirely attacker-controllable in timing (create filters right before periods of high transaction/log volume).

### Recommendation
- Cap the maximum number of buffered elements per `LogFilterAndResult`/`BlockFilterAndResult` (e.g., drop oldest or reject further insertion once a per-filter limit is hit), similar to the `logElementCache` cap already used for deduplication.
- Actively expire and remove filters via a scheduled sweep independent of block/log arrival, rather than relying on lazy eviction triggered only when new blocks/logs happen to be processed.
- Consider reducing `EXPIRE_SECONDS` or making it configurable per deployment risk tolerance, and expose/enforce a global memory budget across all open filters.

### Proof of Concept
1. Enable JSON-RPC on a fullnode (`jsonrpc.httpFullNodeEnable = true`) with default `maxLogFilterNum`.
2. From an anonymous client, repeatedly call `eth_newFilter` with an empty/broad `FilterRequest` (matching all addresses/topics) until close to `maxLogFilterNum` filters are open (see `TronJsonRpcImpl.newFilter`, lines 1440-1466).
3. Do not call `eth_getFilterChanges` or `eth_uninstallFilter` on any of them.
4. Let normal chain activity run for up to `EXPIRE_SECONDS` (5 minutes, `TronJsonRpcImpl.EXPIRE_SECONDS`): each open filter's `LogFilterAndResult.result` queue accumulates every matching log from every block (`handleLogsFilter` → `processLogFilterEntry`, lines 274-313), unbounded in element count.
5. Observe heap usage climbing proportionally to `(number of filters) × (matching logs per second) × EXPIRE_SECONDS`; with enough concurrent filters and chain throughput this can exhaust available memory and crash the node process.

  public Object[] getFilterResult(String filterId, Map<String, BlockFilterAndResult>
      blockFilter2Result, Map<String, LogFilterAndResult> eventFilter2Result)
      throws ItemNotFoundException {
    Object[] result;

    if (blockFilter2Result.containsKey(filterId)) {
      List<String> blockHashList = blockFilter2Result.get(filterId).popAll();
      result = blockHashList.toArray(new String[blockHashList.size()]);
      blockFilter2Result.get(filterId).updateExpireTime();

    } else if (eventFilter2Result.containsKey(filterId)) {
      List<LogFilterElement> logElementList = eventFilter2Result.get(filterId).popAll();
      result = logElementList.toArray(new LogFilterElement[0]);
      eventFilter2Result.get(filterId).updateExpireTime();

    } else {
      throw new ItemNotFoundException(FILTER_NOT_FOUND);
    }

    return result;
  }
