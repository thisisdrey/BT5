### Title
Missing user-controlled swap deadline allows delayed `leverage` transactions to be sandwiched - ([File: contracts/SmartFarmingManager.sol](contracts/SmartFarmingManager.sol))

### Summary

`SmartFarmingManager.leverage()` lets the caller specify a final `depositAmountMin_` slippage bound but provides no transaction deadline parameter. It executes one or two external swaps through `ISwapper.swapExactInput()`, whose signature also has no deadline field. A pending leverage transaction can therefore be included long after it was signed, when the caller’s stale `depositAmountMin_` no longer reflects current market prices. An unprivileged MEV bot can then move the external-market price and sandwich the swap while still satisfying the stale minimum. [1](#0-0) [2](#0-1) 

### Finding Description

The public `leverage()` entry point accepts `tokenIn_`, `depositToken_`, `syntheticToken_`, `amountIn_`, `leverage_`, and `depositAmountMin_`, but no deadline or expiry parameter. [3](#0-2) 

When `tokenIn_` differs from the deposit-token collateral, the contract swaps the caller’s input into collateral through `_swap()`. [4](#0-3) 

The function then mints synthetic debt and swaps the issued synthetic tokens into collateral. Both intermediate calls pass `amountOutMin_` as zero; only the final `_depositAmount` is compared to the caller-supplied `depositAmountMin_`. [5](#0-4) 

`_swap()` invokes `swapper_.swapExactInput(address(tokenIn_), address(tokenOut_), amountIn_, amountOutMin_, to_)`, and the `ISwapper` interface contains no deadline argument. Consequently, neither `leverage()` nor its downstream swap abstraction allows the caller to invalidate the transaction after a chosen timestamp. [6](#0-5) [2](#0-1) 

`flashRepay()` has the same structural omission: its signature contains only `swapAmountOutMin_`, and it executes a collateral-to-synthetic swap through the same deadline-free `_swap()` path. The strongest impact is `leverage()`, because its intermediate swaps explicitly use zero minimum output and can leave the user with minted debt and less collateral than current-market execution would have produced. [7](#0-6) [5](#0-4) 

### Impact Explanation

A stale pending transaction can convert an intended leverage operation into a bad trade. If the collateral/synthetic market price moves while the transaction remains pending, the originally reasonable `depositAmountMin_` can become far below the amount that current-market execution should return. A bot can then capture the newly available slippage while the transaction still satisfies the stale bound.

The resulting loss is borne directly by the caller: the manager deposits the reduced collateral amount to the caller’s position while the caller retains the minted debt obligation. The final health check does not eliminate this issue because a profitable extraction can remain within the user’s configured leverage and health-factor bounds, particularly when the caller chooses leverage below the protocol maximum. [8](#0-7) [9](#0-8) 

### Likelihood Explanation

The attack requires an unprivileged pending transaction and an external market whose price can be moved; it does not require access control, governance, keeper privileges, oracle corruption, or protocol admin cooperation. The public function is protected by `whenNotShutdown` and `nonReentrant`, but neither prevents delayed inclusion or same-block sandwich execution. [3](#0-2) 

The exploitability depends on transactions remaining publicly visible before inclusion and the configured swapper ultimately routing through manipulable liquidity. Since deadline protection is absent from both `leverage()` and `ISwapper`, the Metronome caller cannot express an expiry even if the underlying venue supports one. [2](#0-1) 

### Recommendation

Add a caller-supplied `deadline_` parameter to `SmartFarmingManager.leverage()` and `SmartFarmingManager.flashRepay()`, and revert when `block.timestamp > deadline_` before performing withdrawals, token transfers, issuance, or swaps.

The `ISwapper.swapExactInput()` interface should also accept a deadline and propagate it to the underlying router or aggregator rather than silently substituting `block.timestamp`. If the swapper is an external immutable service that cannot accept deadlines, enforce the deadline in `SmartFarmingManager` before calling it.

For `leverage()`, consider adding separate minimum-output bounds for the input-token-to-collateral and synthetic-to-collateral legs, because the current aggregate `depositAmountMin_` only checks the final total after both swaps. [10](#0-9) 

### Proof of Concept

The following Foundry-style fork test demonstrates the transaction-ordering flaw with a controlled `ISwapper` test double. The test double simulates a venue whose synthetic-to-collateral price changes while Alice’s signed leverage transaction remains pending.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";
import {ISwapper} from "../contracts/interfaces/external/ISwapper.sol";
import {SmartFarmingManager} from "../contracts/SmartFarmingManager.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";
import {ISyntheticToken} from "../contracts/interfaces/ISyntheticToken.sol";

contract StaleMarketSwapper is ISwapper {
    uint256 public manipulatedOutput;
    uint256 public normalOutput;

    function setOutputs(uint256 normal_, uint256 manipulated_) external {
        normalOutput = normal_;
        manipulatedOutput = manipulated_;
    }

    function swapExactInput(
        address tokenIn_,
        address tokenOut_,
        uint256 amountIn_,
        uint256 amountOutMin_,
        address receiver_
    ) external returns (uint256) {
        IERC20(tokenIn_).transferFrom(msg.sender, address(this), amountIn_);

        uint256 amountOut = manipulatedOutput;
        require(amountOut >= amountOutMin_, "slippage");
        IERC20(tokenOut_).transfer(receiver_, amountOut);
        return amountOut;
    }
}

contract MissingDeadlineTest is Test {
    SmartFarmingManager manager;
    StaleMarketSwapper swapper;

    IERC20 tokenIn;
    IDepositToken depositToken;
    ISyntheticToken syntheticToken;
    address alice = address(0xA11CE);

    function test_staleMinimumAllowsSandwich() public {
        uint256 amountIn = 100 ether;
        uint256 leverage = 2e18;

        // Alice signs when expected final collateral is 200 units and
        // chooses 198 as a 1% aggregate slippage bound.
        uint256 staleDepositAmountMin = 198 ether;
        bytes memory pendingCall = abi.encodeCall(
            SmartFarmingManager.leverage,
            (
                tokenIn,
                depositToken,
                syntheticToken,
                amountIn,
                leverage,
                staleDepositAmountMin
            )
        );

        // Alice's transaction remains pending. Market movement and a bot's
        // trade reduce the executable synthetic->collateral output from
        // the expected 100 to 99 collateral units.
        swapper.setOutputs(100 ether, 99 ether);

        // On a fork, sandwich the pending call around the configured swapper
        // state. This call succeeds because 199 > staleDepositAmountMin,
        // even though Alice loses one collateral unit relative to normal
        // execution and keeps the same minted debt.
        vm.prank(alice);
        (bool ok,) = address(manager).call(pendingCall);
        assertTrue(ok);
    }
}
```

A fork harness should replace the test double with the deployed swapper and execute the price-moving AMM trade before Alice’s pending call. The essential property demonstrated by the code is independent of any specific router: no argument in `leverage()` or `swapExactInput()` can invalidate Alice’s stale slippage bound after the transaction is signed.
