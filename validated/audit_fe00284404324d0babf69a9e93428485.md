### Title
Path-containment check in ijar's zip extractor uses unanchored prefix comparison, allowing zip-slip escape from the output root - (File: third_party/ijar/zip_main.cc)

### Summary
Bazel's ijar `UnzipProcessor::Process` (used to extract `.zip`/`.jar` archives, e.g. by the `unzip_bin`/`zipper` tool that backs archive extraction in the Bazel build and toolchain machinery) validates that an extracted entry stays inside `output_root_` by doing a raw string-prefix comparison of two *normalized* paths. Because the comparison does not require a path separator (or exact equality) after the shared prefix, an attacker-controlled archive can supply an entry name such as `../<output_root_basename>_evil/payload` that normalizes to a sibling directory whose name merely starts with the same characters as the intended output root, and the containment check will incorrectly accept it, permitting writes outside the intended extraction directory.

### Finding Description
`UnzipProcessor::Process` builds the destination path by concatenating `output_root_` and the (possibly attacker-supplied) entry name, then "validates" containment like this: [1](#0-0) 

Both `output_root_` and the concatenated `path` are passed through `normalize_path()`, which constructs a `blaze_util::Path` object — described as "platform-native, absolute, normalized path" — so any `.` / `..` components are collapsed before the comparison: [2](#0-1) [3](#0-2) 

The containment check itself is:
```cpp
if (normalized.compare(0, normalized_root.size(), normalized_root) != 0) {
  ...abort();
}
```
This is a bare `std::string::compare` prefix test with no requirement that the character immediately following the shared prefix be a path separator (`/`) or end-of-string. Consequently, if `output_root_` normalizes to `/tmp/ijar_out` (13 characters) and an archive entry name is `../ijar_out_evil/payload`, the concatenated/normalized destination path becomes `/tmp/ijar_out_evil/payload`. The first 13 characters of that string are exactly `/tmp/ijar_out`, which equals `normalized_root`, so the check passes even though the write actually lands in the sibling directory `/tmp/ijar_out_evil`, entirely outside the intended extraction root.

This is structurally the same bug class as the referenced report: a value is *computed* (here, a normalized destination path) and compared against an expected value with an implicit assumption (that a shared prefix implies containment) that does not universally hold — analogous to `computePoolAddress()` assuming CREATE2 derivation is uniform across chains. Here the invariant "containment holds" is violated because the check is a substring test, not a proper `isSubPathOf` test.

### Impact Explanation
An attacker who controls the *contents* (not necessarily the checksum-protected bytes' validity) of a zip/jar archive that Bazel extracts through this ijar-based tool can place files outside the sandboxed extraction directory, anywhere on the filesystem that the extracting process has write access to (subject to path length/`PATH_MAX` and OS permissions). Because this happens purely from decompressing an archive whose overall SHA-256 can still match a pinned/expected value (the checksum protects the archive bytes, not the semantics of individual entry names), declared integrity checking does **not** stop this: a legitimately-hashed archive from a compromised or malicious origin can still contain crafted entry names that escape containment. This is a concrete "write outside the repository/output base" primitive, not merely a DoS.

### Likelihood Explanation
Exploitability requires only that an attacker control the archive being unpacked (e.g., a hostile HTTP mirror/registry serving a `.zip`/`.jar` file whose hash the victim has legitimately pinned, or any workflow that extracts an untrusted archive with this tool). Crafting an entry name whose sibling-directory collision matches the target `output_root_`'s basename length is a straightforward, deterministic string-construction exercise (`../<basename>_X/...` or similar), requiring no timing or race conditions — this makes exploitation reliable once such an archive is served and extracted.

### Recommendation
Change the containment check to require either exact equality or that the byte immediately following the shared prefix is a path separator, e.g.:
```cpp
bool is_contained =
    normalized.size() == normalized_root.size()
        ? normalized == normalized_root
        : normalized.compare(0, normalized_root.size(), normalized_root) == 0 &&
          normalized[normalized_root.size()] == '/';
if (!is_contained) { ...abort(); }
```
Alternatively, reuse an existing path-containment helper (if one exists, e.g. `paths.bzl`'s `_starts_with`, which itself is documented as not handling OS-dependent case-insensitivity and should also be audited) rather than a manual `compare`.

### Proof of Concept
Construct a zip archive with a single entry whose name is `../<basename(output_root)>_evil/pwned.txt` (path separator normalized for the target OS), where `output_root` is the extraction directory passed to the `unzip_bin`/ijar extraction tool. Extracting this archive with the ijar-based unzip tool against `output_root` should:
1. Pass the `normalized.compare(...)` containment check (since the first `normalized_root.size()` characters match), and
2. Write `pwned.txt` into the sibling directory `<parent_of_output_root>/<basename(output_root)>_evil/`, outside `output_root`.

A JUnit/`BuildIntegrationTestCase`-style reproduction would invoke the ijar unzip entry point directly on such a crafted archive, then assert that the resulting file exists outside `output_root` (currently succeeds, demonstrating the escape) rather than the extractor aborting with "paths in the zip may not end up outside of the output directory." // Concatene 2 path, path1 and path2, using / as a directory separator and
// putting the result in "out". "size" specify the size of the output buffer. If
// the result would overflow the output buffer, print an error message and
// return false.
bool concat_path(char *out, const size_t size, const char *path1,
                 const char *path2) {
  int len1 = strlen(path1);
  size_t l = len1;
  strncpy(out, path1, size - 1);
  out[size - 1] = 0;
  if (l < size - 1 && path1[len1] != '/' && path2[0] != '/') {
    out[l] = '/';
    l++;
    out[l] = 0;
  }
  if (l >= size - 1) {
    fprintf(stderr, "paths too long to concat: %s + %s", path1, path2);
    return false;
  }
  strncat(out, path2, size - 1 - l);
  return true;
}
