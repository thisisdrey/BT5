### Title
Uncontrolled memory allocation in `PrecompiledContracts.extractBytesArray`/`extractSigArray` reachable via `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract parses an attacker-supplied ABI word as an array length and allocates a `byte[len][]` array with that length before any bound is enforced, unless a specific hard-fork flag is active. This mirrors the PoDoFo `PdfVecObjects::Reserve` pattern (CVE-2018-5783): a size value taken directly from untrusted input is used to size a memory allocation without validating it is within reasonable bounds first.

### Finding Description
`extractBytesArray` and `extractSigArray` read a count directly from the caller-controlled ABI-encoded input and immediately allocate an array of that size: [1](#0-0) [2](#0-1) 

`len` comes from `words[offset].intValueSafe()`, i.e., a 256-bit `DataWord` taken from the raw calldata to the precompile and coerced to an `int`. There is no upper bound check on `len` before `new byte[len][]` is executed.

These helpers are invoked from `ValidateMultiSign.execute()`: [3](#0-2) 

The only bound check (`sigArraySize > MAX_SIZE`) is gated behind `VMConfig.allowTvmSelfdestructRestriction()`: [4](#0-3) 

When that hard-fork flag is not enabled, `extractBytesArray` is called unconditionally with the unchecked, attacker-controlled `len`, so the array is allocated first and the `signatures.length > MAX_SIZE` check at line 1076 only fires (if at all) after the allocation has already been attempted: [5](#0-4) 

`getEnergyForData` for this precompile is computed purely from `data.length / WORD_SIZE`, not from the derived array length, so a small calldata payload encoding a huge `len` value pays minimal energy while triggering a huge allocation attempt: [6](#0-5) 

### Impact Explanation
Any unprivileged account can deploy or call a contract that invokes the `ValidateMultiSign` precompile (address `0x...66` in java-tron) with crafted calldata that sets the sig-array length word to a very large value (bounded only by `intValueSafe()`'s int-clamping behavior, potentially up to `Integer.MAX_VALUE`). This forces the node executing the transaction to attempt to allocate an oversized `byte[len][]` array, which can throw `OutOfMemoryError` or cause severe GC pressure/latency on the full node, resulting in denial of service for that node (and, if triggered during block validation by multiple SRs/full nodes simultaneously, broader network disruption). This satisfies the "node crash or halt" impact criterion in the validation rules.

### Likelihood Explanation
Likelihood depends on whether `VMConfig.allowTvmSelfdestructRestriction()` is active on the target network. I was unable to determine from the indexed code whether this hard-fork flag is unconditionally enabled on current java-tron mainnet/testnets (i.e., whether the vulnerable code path is dead on production TRON mainnet) — this is uncertain and should be verified against the live `DynamicPropertiesStore` proposal/hard-fork state. On any chain (private, permissioned, or older testnet) where this flag has not been activated, the vulnerable path is fully reachable with a single crafted contract call at negligible cost, making exploitation trivial (single transaction, no special privileges, cheap energy cost).

### Recommendation
Move the array-length bound check (`len > MAX_SIZE`) unconditionally before allocation in `extractBytesArray`/`extractSigArray`, regardless of `allowTvmSelfdestructRestriction()`. Also clamp/validate `len` against the remaining input size before allocating, similar to the RLP decoder's `verifyLength` pattern already used elsewhere in the codebase: [7](#0-6) 

### Proof of Concept
1. Deploy a contract that performs a `STATICCALL`/`CALL` to the `ValidateMultiSign` precompile address with calldata encoding:
   - `words[0]` = arbitrary address
   - `words[1]` = arbitrary permission id
   - `words[2]` = arbitrary data pointer
   - `words[3]` = offset pointing to a word whose value is a very large integer (e.g., close to `Integer.MAX_VALUE / 32`), used as `len` in `extractBytesArray`/`extractSigArray`.
2. On a node/network where `VMConfig.allowTvmSelfdestructRestriction()` is not active, `execute()` calls `extractBytesArray(words, offset, rawData)` directly (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1072-1074`), which computes `len = words[offset].intValueSafe()` and executes `new byte[len][]` (`PrecompiledContracts.java:403-404`) before any size validation, causing an out-of-memory condition on the executing node.

Note: I was unable to fully confirm within the indexed code (a) the exact clamping behavior of `DataWord.intValueSafe()` and (b) whether `allowTvmSelfdestructRestriction()` is permanently active on current java-tron mainnet — these should be verified directly against `VMConfig`/`DynamicPropertiesStore` hard-fork state before treating this as exploitable on production mainnet.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
