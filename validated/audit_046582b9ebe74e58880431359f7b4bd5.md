### Title
`submit` charges a fixed weight regardless of proof size, allowing attackers to submit oversized `receipt_proof`/`ancestry_proof` vectors that cause verification work far exceeding the declared weight - (File: bridges/snowbridge/pallets/inbound-queue/src/lib.rs)

### Summary
The `submit` extrinsic is annotated with a fixed, size-independent weight `T::WeightInfo::submit()`, but the actual computational cost of `Verifier::verify` scales with attacker-controlled input: the number/size of `receipt_proof` trie nodes and the beacon `ancestry_proof.header_branch`. Neither `EventProof`/`Proof`/`ExecutionProof` fields are bounded (`BoundedVec`/`MaxEncodedLen`), so an attacker can submit a much larger-than-benchmarked proof and pay only the fixed benchmarked weight.

### Finding Description
`submit` is dispatched with `#[pallet::weight(T::WeightInfo::submit())]`, a constant weight with no length- or count-dependent component: [1](#0-0) 

The actual verification work is `T::Verifier::verify(&event.event_log, &event.proof)`, which for the ethereum-client verifier performs:
1. Execution/beacon header ancestry-proof Merkle branch verification, whose cost is proportional to `execution_proof.ancestry_proof.header_branch` length.
2. Receipt trie inclusion verification via `verify_receipt_proof`, whose cost is proportional to the number and size of nodes in `proof.receipt_proof: Vec<Vec<u8>>`. [2](#0-1) [3](#0-2) 

The wire types are unbounded: [4](#0-3) 

`verify_receipt_proof` itself iterates over an arbitrary-length `proof: &[Vec<u8>]`: [5](#0-4) 

The benchmark `submit()` (weights.rs) is built from a single fixture-sized proof, producing a small, constant weight (`70_000_000` ps, 3601 bytes proof-of-work weight): [6](#0-5) [7](#0-6) 

Because `receipt_proof` and `ancestry_proof.header_branch` are not `BoundedVec`s and the pallet's weight function does not take their length into account, a caller can construct `receipt_proof` with many/large fake or padding trie-node byte vectors (up to the block/extrinsic length limit) and an inflated `header_branch`. This proof will ultimately fail verification (returning `Error::Verification`), but the CPU work of RLP-decoding/hashing all the supplied nodes and Merkle-branch hashing happens *before* the failure is returned, and it is only charged the fixed `submit()` weight. Repeatedly submitting such maximal-size failing (or successful, if attacker controls a genuinely valid but maximal proof) transactions lets an unprivileged account consume much more actual execution time per block than the weight accounting assumes, since weight (not extrinsic length fee) is what gates how much work fits in a block.

### Impact Explanation
This is a "public underpriced work" issue: the weight declared for `submit` does not reflect worst-case execution cost as a function of attacker-supplied proof size, since `Proof`/`ExecutionProof`/`Log` fields (`receipt_proof: Vec<Vec<u8>>`, `ancestry_proof.header_branch`, `topics`, `data`) are unbounded and not part of the weight formula. If the actual verification cost significantly exceeds the fixed benchmarked weight for large-but-still-block-size-limited proofs, an attacker can degrade block production time (block-building/import taking longer than the weight limit implies) by repeatedly submitting maximal-size proofs, which is within scope as "public underpriced work that degrades block production or stalls bridge processing."

### Likelihood Explanation
Medium-Low. The attacker needs no privileges — only a signed account and enough balance to pay the transaction fee (base + fixed weight fee + length fee for the large payload) — and can craft a `Proof` with arbitrarily many receipt-proof nodes or an inflated `header_branch`, up to the extrinsic/block byte-size limit. The length fee (`T::LengthToFee`) makes such spam economically non-trivial per submission, and the actual quantifiable divergence between benchmarked and worst-case execution time would need to be measured against the actual block weight limit to establish concrete severity — I could not verify from the code alone how large the practical gap is (e.g., no explicit `MaxEncodedLen` bound was found on `Proof`, but the runtime-level extrinsic/block size limits that indirectly cap this were not located in this repository's Snowbridge runtime crate during this review).

### Recommendation
- Bound `Proof::receipt_proof` and `ExecutionProof::ancestry_proof.header_branch` (and other Vec fields in `Log`/`ExecutionProof`) with `BoundedVec` using explicit, benchmarked maximums.
- Make `T::WeightInfo::submit()` a function of the proof length (`submit(n: u32)` benchmarked against the maximum bound), and reject any `EventProof` whose components exceed the benchmarked maximum before performing expensive verification work.
- Add an early cheap length check on `event.proof.receipt_proof.len()` and node sizes before invoking `Verifier::verify`, so oversized inputs are rejected with `Error::InvalidPayload`-style errors at negligible cost.

### Proof of Concept
1. Construct an `EventProof` whose `proof.receipt_proof` contains, e.g., thousands of maximally-sized byte vectors (up to the extrinsic/block size limit) that are guaranteed to fail RLP decode/hash matching only after being fully processed by `verify_receipt_proof`'s node-by-node hashing loop.
2. Submit via `InboundQueue::submit` from an arbitrary signed account.
3. Measure actual wall-clock/CPU time spent in `Verifier::verify` vs. the fixed weight `T::WeightInfo::submit()` charged for the extrinsic; repeat submissions across multiple blocks to observe cumulative degradation in block-building/import time relative to the weight-based scheduling assumption.

	fn verify(event_log: &Log, proof: &Proof) -> Result<(), VerificationError> {
		// Refuse to verify any Ethereum-side proof while the beacon light client is halted.
		// Governance halts the light client when it suspects a compromise (e.g. sync committee
		// takeover), at which point any signed headers/receipts must be treated as untrusted.
		// Covers every Verifier consumer, including `inbound_queue_v2::submit` and
		// `outbound_queue_v2::submit_delivery_receipt` (which would otherwise still drain
		// pending relayer rewards while the bridge is halted).
		ensure!(!Self::operating_mode().is_halted(), VerificationError::Halted);

		Self::verify_execution_proof(&proof.execution_proof)
			.map_err(|e| InvalidExecutionProof(e.into()))?;

		Self::verify_receipt_inclusion(
			proof.execution_proof.execution_header.receipts_root(),
			event_log.tx_index,
			&proof.receipt_proof,
			event_log,
		)?;

		Ok(())
	}
