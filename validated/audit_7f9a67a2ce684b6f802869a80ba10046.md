### Title
Unvalidated attacker-controlled array length in `ValidateMultiSign` precompile causes uncontrolled memory allocation and node crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompiled contract (address `0x...0a`) decodes an attacker-supplied signature-array length directly from call data and uses it, unchecked, to allocate a Java array (`new byte[len][]`) before any bound is enforced. This mirrors the iccDEV `CIccCLUT::Interp3d()` bug class: an unvalidated size/index value taken from untrusted input drives a memory operation whose scale is fully attacker-controlled, leading to a denial-of-service crash rather than a segmentation fault (Java's memory-safety converts the "wild pointer read" into an uncontrolled allocation / `OutOfMemoryError`).

### Finding Description
`ValidateMultiSign.execute()` in [1](#0-0)  reads `words[3]` (an offset into the ABI-encoded array of `DataWord`s) and, when `VMConfig.allowTvmSelfdestructRestriction()` is **disabled**, immediately calls:

```java
byte[][] signatures = extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData);
```

without first validating the encoded array length against `MAX_SIZE` (that bound check only exists inside the `if (VMConfig.allowTvmSelfdestructRestriction())` branch, see [2](#0-1) ).

`extractBytesArray` then does:
```java
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    ...
``` [3](#0-2) 

`len` comes straight from `words[offset].intValueSafe()`, which is derived from attacker-supplied call data and can be as large as `Integer.MAX_VALUE`. `new byte[Integer.MAX_VALUE][]` requires allocating a reference array of roughly 8–16 GB before a single element is populated, which throws `OutOfMemoryError` — a JVM `Error`, not a `RuntimeException`.

This is significant because the TVM interpreter loop only guards against `RuntimeException`:
```java
} catch (RuntimeException e) {
  logger.info("VM halted: [{}]", e.getMessage());
  ...
``` [4](#0-3) 

`OutOfMemoryError` is not caught here (nor anywhere in `ValidateMultiSign.execute()`, whose only `try/catch(Throwable t)` block wraps the *account processing* logic that runs after `extractBytesArray` — see [5](#0-4) ). By contrast, the sibling precompile `BatchValidateSign.execute()` wraps its entire body in `catch (Throwable t)` [6](#0-5) , so it is not exposed to this same failure mode — `ValidateMultiSign` lacks that protection.

The precompile is reachable from a plain `TriggerSmartContract` (a `CALL`/`STATICCALL` to fixed address `0x...0a`, registered at [7](#0-6) ), so any unprivileged transaction broadcaster can trigger it directly, with no special permissions.

### Impact Explanation
An uncaught `OutOfMemoryError` thrown mid-transaction execution can corrupt or destabilize the JVM heap for the entire node process (all threads share the heap), leading to node crash/halt — directly analogous to the "denial of service" impact of the referenced iccDEV CVE. Because block/transaction validation is deterministic across the network, a single malicious transaction broadcast to the network (once mined/executed by nodes) can crash multiple validating full nodes and SR nodes simultaneously, which is a much more severe availability threat than an isolated single-process crash.

### Likelihood Explanation
Exploitation only requires crafting call data to the fixed precompile address with a large length word at the expected offset and broadcasting a normal `TriggerSmartContract` transaction — no special account permissions, staked resources beyond ordinary bandwidth/energy, or unusual chain state are required. The vulnerable path is exercised only when the `allowTvmSelfdestructRestriction` dynamic parameter is not active for the network (its state is chain/committee-configuration dependent), which limits — but does not eliminate — exploitability; this should be verified against the currently active chain parameters before treating it as immediately exploitable on a specific network.

### Recommendation
Move the `sigArraySize`/length bound check ahead of `extractBytesArray`/`extractSigArray` unconditionally (not only inside the `allowTvmSelfdestructRestriction` branch), and add an explicit `len <= MAX_SIZE` (and `len >= 0`) guard inside `extractBytesArray` and `extractBytes32Array` themselves before allocating `new byte[len][]`, mirroring the existing guard in `BatchValidateSign`. Also wrap the full body of `ValidateMultiSign.execute()` (not just the account-processing sub-block) in a `catch (Throwable t)` as defense-in-depth, consistent with `BatchValidateSign`.

### Proof of Concept
Craft `TriggerSmartContract` call data targeting precompile address `0x000000000000000000000000000000000000000a` shaped as the ABI-encoded input expected by `ValidateMultiSign` (`words[0]`=address, `words[1]`=permissionId, `words[2]`=data pointer, `words[3]`=offset pointing at a "length" word), where the word at the computed offset (`words[offset]`) is set to `0x7fffffff` (or similarly large). When `allowTvmSelfdestructRestriction` is not active, `extractBytesArray` executes `new byte[0x7fffffff][]`, throwing `OutOfMemoryError`, which is not caught by `VM.play()`'s `RuntimeException` handler and can crash the executing node. Full reproduction would require confirming the exact `DataWord.intValueSafe()` clamping behavior and the live value of `allowTvmSelfdestructRestriction` on the target network — these should be validated in a test/dev environment before further action.
