### Title
Failed pack-objects cache entries are discarded, letting an attacker repeatedly trigger full-cost `git-pack-objects` generation for free - (File: internal/streamcache/cache.go)

### Summary
The Nibiru finding is an EVM/blockchain-specific "gas not consumed on precompile failure" bug. Gitaly has no gas metering, but it has an analogous *resource-accounting* mechanism: the pack-objects cache (`internal/streamcache`), which is supposed to amortize the cost of expensive `git-pack-objects` invocations across identical requests. When the underlying generation fails, the cache discards the entry instead of recording/reusing the (expensive) partial computation, so every failed attempt is effectively "free" to retry and forces the server to redo the full, costly computation — the same class of "computation performed but not charged/accounted for" as the Nibiru issue.

### Finding Description
`cache.newEntry()` spawns a goroutine that runs the caller-supplied `create` function (which in the `PackObjectsHookWithSidechannel` path runs `git pack-objects`, a CPU/IO-intensive command). If `create` returns an error, the cache immediately deletes the entry: [1](#0-0) 

This means an errored (but potentially long-running / resource-intensive) `git-pack-objects` run leaves **no trace** in the cache — there is no negative caching, no cost tracking, and no penalty applied for having consumed CPU/disk/memory during the failed attempt. [2](#0-1) 
This test explicitly documents the behavior: "because the previous entry failed, a new one should have been created" — i.e., the system guarantees a fresh, full-cost re-execution on every subsequent identical request after a failure.

The RPC entry point, `packObjectsHook`, feeds requests through this cache via `s.packObjectsCache.Fetch(...)`, using a deterministic `cacheKey` derived from the repository, arguments, protocol, and stdin (the `want`/`have` negotiation): [3](#0-2) [4](#0-3) 

The only admission control on this expensive work is a concurrency limiter (`packObjectsLimiter` / `runPackObjectsLimited`), which merely bounds how many pack-objects generations run *concurrently* per key (IP address) — it releases the slot as soon as the (possibly failed) call returns and does not track or throttle repeated sequential failures: [5](#0-4) [6](#0-5) 

Because concurrency limiting is orthogonal to *cost accounting*, and because failures are never cached, an unauthenticated-yet-network-reachable client driving `PostUploadPack`/`SSHUploadPack`/`PackObjectsHookWithSidechannel` can craft a request (e.g. a large "want"/"have" negotiation, or one deliberately interrupted/cancelled just before packfile completion) so that `git-pack-objects` runs for a substantial amount of CPU time and then errors out (client hangs up, invalid ref, deepen mismatch, etc.). Because the entry is deleted on error, the exact same request can be repeated indefinitely, and each repetition forces the server to redo the entire expensive computation from scratch rather than being served from cache like a successful entry would be for subsequent legitimate clients.

### Impact Explanation
This allows a low-cost, repeatable amplification of CPU/IO/memory consumption on the Gitaly node: legitimate identical fetch traffic is deduplicated by the cache (as shown by `testServerPackObjectsHookUsesCache`), but an attacker who can force generation to fail avoids that dedup entirely and can keep re-triggering full-price `git-pack-objects` runs. Combined across many repositories/keys, or many sequential retries against one repo, this degrades node performance and can starve other tenants sharing the Gitaly node — a resource-consumption-related DoS matching the RPC-handler resource-limit category.

### Likelihood Explanation
Reaching this code path only requires an ordinary, unprivileged client performing a fetch/clone (`git-upload-pack` / `PostUploadPackWithSidechannel` / `SSHUploadPackWithSidechannel`), which routes through `packObjectsHook`. No special privileges, leaked tokens, or MITM position are needed — only the ability to shape the negotiation (want/have list, deepen parameters, or simply disconnecting mid-transfer) to reliably cause `git-pack-objects` to fail after doing substantial work. This is a normal capability of any client permitted to fetch from the repository.

### Recommendation
- Cache negative/failed results for a short TTL (or at minimum record cost/attempt counters per cache key) so identical failing requests are not recomputed from scratch on every retry.
- Add rate limiting / backoff keyed on repeated failures for the same cache key (not just concurrency limiting), so an attacker cannot cheaply force unlimited full-cost recomputation.
- Consider treating a failed generation for a given key as billable/countable towards the requester's concurrency or resource quota, closing the "recompute for free after failure" gap, analogous to the Nibiru fix of consuming gas regardless of success/failure.

### Proof of Concept
1. Configure a Gitaly node with the pack-objects cache enabled (`pack_objects_cache.enabled = true`).
2. As an ordinary client with fetch access to a large repository, issue a `PostUploadPackWithSidechannel`/`SSHUploadPackWithSidechannel` request with a `want`/`have` set that causes `git pack-objects` to do substantial work (e.g., large delta computation) before it errors — for example, by closing the connection just before the pack stream completes, or by supplying a negotiation that leads to an eventual git-side error after significant compute.
3. Observe (via `gitaly_pack_objects_generated_bytes_total` / logs) that the server performed the full computation, but per `internal/streamcache/cache.go` lines 305-318 and the documented behavior in `TestCache_failedWrite`, the cache entry for that key is deleted on error.
4. Repeat the exact same request; observe a fresh, full-cost `git-pack-objects` execution occurs again (cache miss), rather than being served/blocked by any cost-based accounting — confirming the entry is never charged for the resources already spent on the failed attempt.

func (s *server) computeCacheKey(ctx context.Context, req *gitalypb.PackObjectsHookWithSidechannelRequest, stdinReader io.Reader) (string, io.ReadCloser, error) {
	cacheHash := sha256.New()

	repository := req.GetRepository()
	if tx := storage.ExtractTransaction(ctx); tx != nil {
		// The cache uses the requests as the keys. As the request's repository in the RPC handler has been rewritten
		// to point to the transaction's repository, the handler sees each request as different even if they point to
		// the same repository. Restore the original request to ensure identical requests get the same key.
		repository = tx.OriginalRepository(req.GetRepository())
	}

	cacheKeyPrefix, err := protojson.Marshal(&gitalypb.PackObjectsHookWithSidechannelRequest{
		Repository:  repository,
		Args:        req.GetArgs(),
		GitProtocol: req.GetGitProtocol(),
	})
	if err != nil {
		return "", nil, err
	}
	if _, err := cacheHash.Write(cacheKeyPrefix); err != nil {
		return "", nil, err
	}
	stdin, err := bufferStdin(stdinReader, cacheHash)
	if err != nil {
		return "", nil, err
	}
	cacheKey := hex.EncodeToString(cacheHash.Sum(nil))
	return cacheKey, stdin, nil
}

func (s *server) runPackObjectsLimited(
	ctx context.Context,
	w io.Writer,
	limitkey string,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.ReadCloser,
	key string,
) error {
	ctx = context.WithoutCancel(ctx)

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	defer stdin.Close()

	if _, err := s.packObjectsLimiter.Limit(
		ctx,
		limitkey,
		func() (interface{}, error) {
			return nil,
				s.runPackObjectsFn(
					ctx,
					s.gitCmdFactory,
					w,
					req,
					args,
					stdin,
					key,
				)
		},
	); err != nil {
		return err
	}

	return nil
}

func (c *ConcurrencyLimiter) Limit(ctx context.Context, limitingKey string, f LimitedFunc) (interface{}, error) {
	span, ctx := tracing.StartSpanIfHasParent(
		ctx,
		"limiter.ConcurrencyLimiter.Limit",
		[]attribute.KeyValue{
			attribute.String("key", limitingKey),
		},
	)
	defer span.End()

	if c.currentLimit() <= 0 {
		return f()
	}

	sem := c.getConcurrencyLimit(limitingKey)
	defer c.putConcurrencyLimit(limitingKey)

	start := time.Now()

	if err := sem.acquire(ctx, limitingKey); err != nil {
		queueTime := time.Since(start)
		switch {
		case errors.Is(err, ErrMaxQueueSize):
			c.monitor.Dropped(ctx, limitingKey, sem.queueLength(), sem.inProgress(), queueTime, "max_size")
			return nil, structerr.NewResourceExhausted("%w", ErrMaxQueueSize).WithDetail(&gitalypb.LimitError{
				ErrorMessage: err.Error(),
				RetryAfter:   durationpb.New(0),
			})
		case errors.Is(err, ErrMaxQueueTime):
			c.monitor.Dropped(ctx, limitingKey, sem.queueLength(), sem.inProgress(), queueTime, "max_time")
			return nil, structerr.NewResourceExhausted("%w", ErrMaxQueueTime).WithDetail(&gitalypb.LimitError{
				ErrorMessage: err.Error(),
				RetryAfter:   durationpb.New(0),
			})
		default:
			c.monitor.Dropped(ctx, limitingKey, sem.queueLength(), sem.inProgress(), queueTime, "other")
			return nil, fmt.Errorf("unexpected error when dequeueing request: %w", err)
		}
	}
	defer sem.release()

	c.monitor.Enter(ctx, sem.inProgress(), time.Since(start))
	defer c.monitor.Exit(ctx)
	return f()
}
