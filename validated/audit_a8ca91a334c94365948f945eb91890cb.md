### Title
Unbounded `GetFileAttributesRequest.paths`/`attributes` causes O(N×M) synchronous CPU/I/O exhaustion with no request-size cap - (File: internal/gitaly/service/repository/file_attributes.go)

### Summary
`validateGetFileAttributesRequest` only rejects empty `paths` and `attributes` lists but enforces no upper bound on their sizes, and `GetFileAttributes` then invokes `CheckAttrCmd.Check` once per path over a single shared pipe to `git check-attr`. Since each `Check` call synchronously reads `count` (= len(attributes)) NUL-delimited triples per path, an attacker who controls both list sizes can force O(N×M) blocking read/write cycles in the RPC handler with no server-side limit analogous to `lfsPointerMaxSize`.

### Finding Description
`GetFileAttributes` builds a `CheckAttrCmd` for `in.GetAttributes()` and then iterates `in.GetPaths()`, calling `checkAttrCmd.Check(path)` for each one: [1](#0-0) .

`validateGetFileAttributesRequest` validates the repository and rejects only zero-length paths/attributes, with no maximum: [2](#0-1) .

`CheckAttrCmd.Check` writes `path + "\000"` to the `git check-attr --stdin -z` subprocess's stdin, flushes, and then blocks reading exactly `c.count` (the number of requested attribute names) NUL-delimited 3-tuples from stdout before returning, guarded by a mutex `c.m`: [3](#0-2) . This is a strictly synchronous, single-subprocess, single-pipe protocol: the RPC goroutine must perform one write + `count` reads per path, so total work scales multiplicatively with `len(paths) * len(attributes)`.

There is no repo-level cap on gRPC message size (`MaxRecvMsgSize`) found in the codebase, and no per-field length limit comparable to the `lfsPointerMaxSize` constant used elsewhere (e.g. `internal/gitaly/service/blob/lfs_pointers.go`) to bound attacker-controlled list sizes before they reach the synchronous git-check-attr loop.

### Impact Explanation
An attacker with only ordinary push/fetch access to a repository (or an imported/forked repo they control) can invoke `RepositoryService.GetFileAttributes` with a large `paths` array and a large `attributes` array, forcing the Gitaly RPC handler goroutine and the underlying `git-check-attr` subprocess to perform proportionally large numbers of blocking pipe writes/reads. This ties up a goroutine and a subprocess for extended, attacker-controlled duration, degrading Gitaly node responsiveness — a CPU/time exhaustion (DoS) of the RPC handler, matching the "denial of service of a single RPC/handler" impact class.

### Likelihood Explanation
The RPC is unauthenticated beyond normal repository access (any user with read access to a repository can call it), requires no special privilege, and the request construction is entirely client-controlled (arbitrary `paths` and `attributes` string slices). The only natural constraint is the default gRPC message size, but because cost is multiplicative in the two independent list lengths, a request well within typical message-size limits (e.g., tens of thousands of short paths × on the order of a hundred attribute names) can already produce a very large number of synchronous pipe operations. This is repeatable per RPC call and requires no race or timing conditions.

### Recommendation
Add explicit upper bounds in `validateGetFileAttributesRequest` for both `len(in.GetPaths())` and `len(in.GetAttributes())` (and/or a combined product bound), returning `InvalidArgument` when exceeded, mirroring the size-limiting pattern used for LFS pointers (`lfsPointerMaxSize`). Consider also capping total bytes across paths/attributes.

```go
func TestGetFileAttributes_LargeRequestDoS(t *testing.T) {
    // setup repo, revision with .gitattributes as in check_attr_test.go
    paths := make([]string, 100000)
    for i := range paths {
        paths[i] = fmt.Sprintf("file-%d.md", i)
    }
    attrs := make([]string, 100)
    for i := range attrs {
        attrs[i] = fmt.Sprintf("attr-%d", i)
    }
    req := &gitalypb.GetFileAttributesRequest{
        Repository: repoProto,
        Revision:   []byte(commitID),
        Paths:      paths,
        Attributes: attrs,
    }
    start := time.Now()
    _, err := client.GetFileAttributes(ctx, req)
    require.NoError(t, err)
    t.Logf("elapsed: %s", time.Since(start)) // expected to grow ~linearly with N*M with no server-imposed cap
}
```
Comparing latency growth as `len(paths) * len(attributes)` increases, with no `InvalidArgument` rejection at any size, confirms the absence of a bound.

```go
func (c CheckAttrCmd) Check(path string) (Attributes, error) {
	if strings.Contains(path, "\000") {
		return nil, fmt.Errorf("path with NUL byte not allowed")
	}

	c.m.Lock()
	defer c.m.Unlock()

	if _, err := c.stdin.WriteString(path + "\000"); err != nil {
		return nil, fmt.Errorf("write path: %w", err)
	}
	if err := c.stdin.Flush(); err != nil {
		return nil, fmt.Errorf("flush: %w", err)
	}

	attrs := Attributes{}
	buf := make([]string, 0, 3)

	// Using git-check-attr(1) with -z will return data in the format:
	// <path> NUL <attribute> NUL <info> NUL ...
	for i := 0; i < c.count; {
		word, err := c.stdout.ReadBytes('\000')
		if err != nil {
			return nil, fmt.Errorf("read line: %w", err)
		}

		buf = append(buf, string(bytes.TrimSuffix(word, []byte{0})))

		if len(buf) < 3 {
			continue // Keep going until we have 3 words
		}

		if buf[0] != path {
			return nil, fmt.Errorf("wrong path name detected, expected %q, got %q", path, buf[0])
		}
		if buf[2] != Unspecified {
			attrs = append(attrs, Attribute{Name: buf[1], State: buf[2]})
		}

		i++
		buf = buf[:0]
	}

	return attrs, nil
}
```
