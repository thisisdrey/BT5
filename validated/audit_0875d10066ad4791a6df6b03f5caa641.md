### Title
Global unstaked-reachable QUIC connection admission token bucket (`overall_connection_rate_limiter`) is consumed identically by staked and unstaked peers, allowing a distributed low-per-IP flood to exhaust total connection admission capacity and starve staked connections - (File: streamer/src/nonblocking/quic.rs)

### Summary
`run_server` gates every incoming QUIC connection through a single global `TokenBucket` (`overall_connection_rate_limiter`, `TOTAL_CONNECTIONS_PER_SECOND = 2500`, burst `MAX_CONNECTION_BURST = 1000`) before the connection's stake status is ever determined. Because the peer-type/stake lookup (`qos.build_connection_context`) only happens after the global bucket check succeeds, an unstaked attacker spreading connection attempts across many distinct source IPs (each individually under the per-IP `ConnectionRateLimiter` threshold) can drain the shared bucket and cause new connections from staked validators to be rejected at the same rate as unstaked ones.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:270-281`), a single `Arc<TokenBucket>` `overall_connection_rate_limiter` is created and shared across the whole endpoint, independent of source IP or stake: [1](#0-0) 

At accept time, the loop checks the global bucket (peek, `current_tokens() == 0`) before the per-IP `ConnectionRateLimiter::is_allowed` check, and both checks occur prior to any handshake/stake information being available: [2](#0-1) 

After the handshake completes in `setup_connection`, the per-IP limiter is registered and then the same global bucket has a token consumed (`overall_connection_rate_limiter.consume_tokens(1)`) — still **before** `qos.build_connection_context(&new_connection)` is called to determine `ConnectionPeerType::Staked`/`Unstaked`: [3](#0-2) 

Only after this global gate passes does the code branch on stake via `SwQos`/`SimpleQos::try_add_connection`, which maintains genuinely separate `staked_connection_table` / `unstaked_connection_table` with independent capacities and pruning logic that favors higher stake (`streamer/src/nonblocking/swqos.rs:354-439`, `streamer/src/nonblocking/simple_qos.rs:310-347`): [4](#0-3) 

This later stake-aware isolation is irrelevant if the connection never reaches it because the shared global bucket is already empty. The per-IP `ConnectionRateLimiter` (`streamer/src/nonblocking/connection_rate_limiter.rs:21-29`) is generous — configured as `max_connections_per_ipaddr_per_min` with a 10x burst allowance — so an attacker distributing connections across a sufficient number of distinct source IPs (botnet or IPv6 /64 rotation) can keep every individual IP's rate under the per-IP threshold while collectively exceeding `TOTAL_CONNECTIONS_PER_SECOND`/`MAX_CONNECTION_BURST` in aggregate, since there is no per-source accounting tied to the global bucket — it is a flat shared counter.

Once `overall_connection_rate_limiter` is drained, every new connection attempt, staked or unstaked, is rejected with `CONNECTION_CLOSE_CODE_DISALLOWED` at `streamer/src/nonblocking/quic.rs:495-508`, regardless of the remote peer's stake, since stake is not yet known and cannot be known before this check.

### Impact Explanation
Scoped impact: an unstaked, unprivileged attacker can deny new TPU QUIC connection admission to legitimate staked validators/forwarders by keeping the shared `overall_connection_rate_limiter` saturated via a distributed low-rate-per-IP flood. This does not crash the node, corrupt state, or bypass sigverify, but it defeats the intended QoS invariant that staked traffic should be preferentially admitted — new staked connections are throttled identically to unstaked flood traffic at the earliest network-facing gate, before any stake-based prioritization logic in `SwQos`/`SimpleQos` can run. This is best characterized as a QoS evasion / availability degradation for the TPU ingress path, not a memory-safety or consensus-breaking bug. It only affects **new connection establishment**; existing already-admitted staked connections and their streams are unaffected, limiting the blast radius to connection churn scenarios (e.g., validator restarts, new stake activation, or connection pool cycling under active attack).

### Likelihood Explanation
Feasibility requires only unprivileged network access to the public TPU QUIC port and the ability to originate the aggregate connection rate above 2500/sec (with 1000 burst) split across enough distinct source IPs to stay under each IP's individual rate-limiter threshold. This is achievable via a modest botnet or IPv6 prefix rotation and does not require any staked/gossip/config privileges. It is fully repeatable as long as the attacker sustains the aggregate connection rate, since the bucket refills continuously and admission is purely rate-based with no source diversity or stake weighting in the global gate.

### Recommendation
Reserve capacity in `overall_connection_rate_limiter` for staked peers, or split the global bucket into staked/unstaked buckets sized proportionally (mirroring the existing `max_staked_connections`/`max_unstaked_connections` split), and/or move the stake determination (`get_connection_stake`) earlier — before the final global-bucket consumption — so staked connections can bypass or draw from a separately reserved allotment instead of competing with unstaked/unknown traffic for the same shared token bucket.

### Proof of Concept
Integration test plan (extends existing pattern in `tpu-client-next/tests/connection_workers_scheduler_test.rs::test_rate_limiting`):
1. Spin up `setup_quic_server` with `QuicStreamerConfig::default_for_tests()` but override `TOTAL_CONNECTIONS_PER_SECOND`-equivalent behavior isn't configurable, so instead directly unit-test `run_server`'s global bucket logic via a harness that drives many distinct simulated source IPs.
2. From `N` distinct `IpAddr` values (`N` > `max_connections_per_ipaddr_per_min` is not required — keep each IP's connection count under its per-minute allowance), open connections at a combined rate exceeding `TOTAL_CONNECTIONS_PER_SECOND` (2500/s) + `MAX_CONNECTION_BURST` (1000) within one second.
3. Assert via `StreamerStats.connection_rate_limited_across_all` that it increments significantly while `StreamerStats.connection_rate_limited_per_ipaddr` stays at/near zero (proving no single IP tripped the per-IP limiter).
4. Concurrently attempt one staked connection (using a keypair present in `StakedNodes`) during the flood window and assert it is also rejected (`new_connection.close(CONNECTION_CLOSE_CODE_DISALLOWED, ...)`) — i.e., `stats.connection_added_from_staked_peer` remains 0 and `stats.connection_rate_limited_across_all` was incremented for the staked attempt too — demonstrating the global bucket denies staked admission indiscriminately.
