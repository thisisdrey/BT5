## Analysis Result

### Title
Permanent freeze of an eth-implicit account via unrecoverable `has_in_flight_tx` lock when a NEP-141/registrar callback exhausts its fixed gas budget - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Optimism report shows a class of bug where an outer contract irreversibly commits a "done" flag (`finalizedWithdrawals[hash] = true`) before an inner call finishes, and the inner call's `revert`-on-insufficient-gas discards the complementary state update (`failedMessages[hash] = true`) that would have made the operation replayable, permanently stranding funds. The nearcore eth-implicit wallet contract (`WalletContract`) exhibits the same two-phase commit/rollback split across separate receipts: the "commit" flag (`has_in_flight_tx = true`, plus the Ethereum-style `nonce` increment) is persisted in one receipt, while the matching "release" flag (`has_in_flight_tx = false`) is only written inside a *later, separate* callback receipt. If that callback receipt itself fails atomically (e.g. runs out of its small fixed gas budget), nearcore rolls back every state write it made — including the `has_in_flight_tx = false` reset — leaving the flag permanently `true` with no other code path able to clear it.

### Finding Description
`rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:88-128`) gates all execution on `self.has_in_flight_tx`: [1](#0-0) 

When `inner_rlp_execute` successfully builds a promise, `has_in_flight_tx` is set to `true` and that state is committed as part of the successful `rlp_execute` receipt. This receipt also increments the persistent `nonce` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:364`), exactly mirroring `finalizedWithdrawals[hash] = true` in the Optimism bug — an irreversible external commitment made before the "real" operation has finished.

The only code paths that ever reset `has_in_flight_tx` back to `false` live in separate downstream callback receipts: `address_check_callback` (line 140), `nep_141_storage_balance_callback` (line 202), `rlp_execute_callback` (line 280), and `ban_relayer` (line 321): [2](#0-1) [3](#0-2) 

Each of these callbacks is scheduled with a small, fixed static gas budget, e.g. `RLP_EXECUTE_CALLBACK_GAS = Gas::from_tgas(5)` and `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS` (both derived from the same 5 Tgas base): [4](#0-3) 

These callbacks perform `serde_json::from_slice` on an untrusted response returned by whatever contract is named as `target`/`token_id` (attacker/relayer-controlled input to `rlp_execute`): [5](#0-4) 

If that response is large or otherwise expensive to process (or the successful `value` handled in `rlp_execute_callback` at line 313 is large), the callback's own gas metering — not the inner promise's `PromiseResult::Failed` path — can be exhausted. Per nearcore's action-receipt execution semantics, when an action inside a receipt fails (e.g. `HostError::GasExceeded`), the entire receipt is rolled back: [6](#0-5) 

This rollback discards *all* state changes made in that receipt, including the pending `self.has_in_flight_tx = false` mutation, exactly analogous to how `L1CrossDomainMessenger.relayMessage`'s `revert` discarded the `failedMessages[hash] = true` write while `OptimismPortal.finalizedWithdrawals[hash] = true` remained committed from the earlier, already-finalized step. A search of the entire wallet-contract crate confirms `has_in_flight_tx` is referenced only in `lib.rs`, with no other function, timeout, or admin path capable of resetting it.

### Impact Explanation
Once `has_in_flight_tx` is stuck `true`, every future call to `rlp_execute` short-circuits at line 97-105 and returns an error value without spawning any promise, permanently disabling the wallet contract for that eth-implicit account. Because this account is the sole controller of any NEAR/FT balances it holds (analogous to Alice's un-replayable withdrawal), all funds and any privileges tied to the account become permanently frozen — no owner action, relayer, or protocol-level mechanism exists to clear the flag. This satisfies the "permanent freezing of funds" bar.

### Likelihood Explanation
Triggering the bug requires only: (1) a relayer/caller-supplied `target`/`token_id` account that is a contract returning a large or malformed payload for `storage_balance_of`/`lookup`, or (2) a legitimately large successful cross-contract call response processed in `rlp_execute_callback`. The attacker fully controls the `target` parameter passed to `rlp_execute`, and thus fully controls the contract invoked and the size/content of its response, making this reachable without needing any external gas-schedule change (unlike the original Optimism report, which needed a speculative EIP change) — the callback gas budgets here are small, fixed constants (5 Tgas class) that can plausibly be exceeded by adversarial responses.

### Recommendation
Do not let the release of `has_in_flight_tx` depend on the success of a bounded, attacker-influenced callback. Options: reset `has_in_flight_tx = false` unconditionally as an early, unconditionally-committed step (e.g. via a system-level receipt that is guaranteed not to be rolled back together with the parsing logic), add a timeout/expiry mechanism that allows the contract owner to clear a stuck in-flight flag after a block-height threshold, or ensure callbacks always have `GasWeight`-based unspent-gas-adjusted budgets and defensively cap/skip deserialization of oversized responses (returning `PromiseResult::Failed`-equivalent handling) rather than allow unbounded `serde_json` parsing costs inside a small fixed-gas callback.

### Proof of Concept
1. Deploy an eth-implicit `WalletContract` for address `A`.
2. Deploy a malicious NEP-141-like contract `M` implementing `storage_balance_of` that returns an extremely large JSON payload (or one deliberately crafted to be maximally expensive for `serde_json::from_slice::<Option<StorageBalance>>` to parse, while still fitting under the receipt's outer `prepaid_gas`/result-size limits).
3. Craft/sign an RLP Ethereum transaction representing an ERC-20 transfer whose `to` address maps to `M`, and submit it via `rlp_execute(target: M, tx_bytes_b64: ...)`.
4. `inner_rlp_execute` succeeds, increments `nonce`, and commits `has_in_flight_tx = true` (`lib.rs:364`, `:118`); it creates the `storage_balance_of` promise chained to `nep_141_storage_balance_callback` with `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` (`lib.rs:39-41`, `:440-457`).
5. `M.storage_balance_of` returns its oversized payload; `nep_141_storage_balance_callback` attempts `serde_json::from_slice` (`lib.rs:211`) and exceeds its fixed gas budget, causing `HostError::GasExceeded` and a full rollback of that receipt (per `protocol-model/spec/runtime-execution.md:67-70`), discarding the pending `self.has_in_flight_tx = false` write.
6. `has_in_flight_tx` remains `true` in on-chain state (from the already-committed step 4 receipt). All subsequent calls to `rlp_execute` on this account now return `"Error: transaction already in progress, please try again later."` (`lib.rs:97-105`) forever, permanently freezing the account.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
