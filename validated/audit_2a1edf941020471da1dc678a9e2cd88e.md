## Title
Vault deposit mints zero shares when `total-assets` rounds/writes down to `0` while `total-supply` is nonzero, silently confiscating the depositor's principal - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and analogous per-vault files)

## Summary
This is the vault share-math analog of the Nouns Builder quorum bug: a ratio computation (`quorumVotes = totalSupply * bps / 10_000` in the original report) can legitimately evaluate to `0` when one operand is small/zero, and the code that consumes the zero value then treats it as an unconditionally-satisfied gate rather than reverting. In Zest's vaults, `convert-to-shares-preview` computes `shares = amount * total-supply / total-assets`, and explicitly returns `u0` whenever `total-assets` is `0` while `total-supply` is nonzero. The public `deposit` entry point never checks that the resulting share amount (`inkind`) is greater than zero — it only checks `inkind >= min-out`, which is trivially satisfied by `0 >= 0` — so a depositor's underlying tokens are pulled in and added to `assets`, but `0` zTokens are minted to them.

## Finding Description
`convert-to-shares-preview` is defined identically in every vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`): [1](#0-0) 

`total-assets-preview` is: [2](#0-1) 

`assets` (the vault's principal ledger) can be driven to `0` via `socialize-debt`, which reduces `assets`/`total-borrowed`/`principal-scaled` on bad debt but does **not** burn any outstanding `zft` supply: [3](#0-2) 

If `total-borrowed` also reaches `0` (all outstanding loans repaid or written off) at the same time `assets` is `0`, then `total-assets-preview` returns `0` while `total-supply` (the `zft` supply held by existing depositors/DAO treasury) remains positive — exactly analogous to `totalSupply` being nonzero but `quorumThresholdBps * totalSupply / 10_000` rounding to `0` in the Nouns report.

The public `deposit` function then computes `inkind = convert-to-shares-preview(amount) = 0`, and the only slippage guard is: [4](#0-3) 

`(asserts! (>= inkind min-out) ERR-SLIPPAGE)` at line 776 passes trivially when `inkind = 0` and `min-out = 0` (the common/default case for a first-time or naive integrator), exactly as `proposal.forVotes < proposal.quorumVotes` becomes vacuously false when `quorumVotes = 0`. Unlike `redeem`, which explicitly guards against a zero output with `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` at line 811, `deposit` has no equivalent `> inkind u0` check. The depositor's underlying tokens are still transferred in (`receive-underlying`) and folded into `assets` (line 781), benefiting all existing `zft` holders, while the depositor receives `0` shares.

## Impact Explanation
This is a direct theft of user funds at rest: any unprivileged principal calling `deposit` on a vault that is in this degraded state (assets fully written off via `socialize-debt`, no outstanding borrow) loses their entire deposited principal to the existing shareholder pool, with zero recourse (no shares to redeem). This satisfies the Critical impact bar ("direct theft of user funds at rest ... or protocol insolvency").

## Likelihood Explanation
Reaching `total-assets-preview() == 0` with `total-supply > 0` requires the vault to have suffered a socialized bad-debt event that wipes out `assets` while `total-borrowed` is simultaneously zero — a plausible but non-trivial post-liquidation state (e.g., after `liquidate` triggers `bad-debt-socialized` on the last debt of a borrower, or the last vault deposit accrues to zero). It does not require any privileged action; it only requires reaching that vault state and then any ordinary user calling `deposit` with `min-out = 0` (the natural default for depositors, since `total-assets`/`total-supply` were previously nonzero and there is no reason to expect a `0` conversion rate).

## Recommendation
Add an explicit `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` check to `deposit` in all vault contracts, mirroring the existing guard in `redeem`, so that deposits into a state where the share/asset ratio has degenerated to zero revert instead of silently absorbing the depositor's funds. Additionally, consider whether `convert-to-shares-preview` should distinguish "no shares exist yet" (`ts == 0`, legitimate 1:1 bootstrap) from "shares exist but assets are wiped out" (`ts != 0 && ta == 0`, a genuinely broken/insolvent vault state) and pause deposits entirely in the latter case.

## Proof of Concept
1. Deploy/seed a vault (e.g. `v0-vault-usdc`) with an initial depositor Alice who deposits `X` USDC, receiving `X` zUSDC (1:1 bootstrap, `ts == 0` branch).
2. Have the market borrow the full available liquidity via `system-borrow`, then have the position accrue to bad debt (e.g., collateral price crashes) such that `liquidate` runs and, because no collateral remains, calls `socialize-debt-asset` → `socialize-debt` on the vault, driving `assets` to `0` (and `total-borrowed` to `0` once the debt is fully socialized) while Alice's `zUSDC` balance (`total-supply`) remains unchanged and positive.
3. Bob now calls `deposit(amount, 0, bob)` on the same vault. `convert-to-shares-preview(amount)` returns `u0` because `ta == 0` and `ts != 0` (per the second branch in `convert-to-shares-preview`, lines 311-315 in `mainnet/contracts/vault/v0-vault-stx.clar`, replicated for USDC).
4. The `deposit` call succeeds (`inkind (0) >= min-out (0)`), Bob's `amount` USDC is transferred into the vault and added to `assets`, but Bob is minted `0` zUSDC. Bob has permanently lost his deposit to the vault's existing shareholders (Alice/treasury). [1](#0-0) [4](#0-3) [3](#0-2)
