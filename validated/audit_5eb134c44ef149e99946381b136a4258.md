### Title
Intra-batch write-lock conflicts are not detected in `AccountLocks::try_lock_transaction_batch`, allowing two write-conflicting transactions in the same batch to be scheduled concurrently - (File: `accounts-db/src/account_locks.rs`)

### Summary
`AccountLocks::try_lock_transaction_batch` splits lock validation into two separate passes: a "check" pass that calls `can_lock_accounts` for every transaction in the batch against the pre-batch lock state, and a subsequent "apply" pass that blindly calls `lock_accounts` for every transaction that passed the check. Because the check pass never re-validates a transaction against locks that would be newly acquired by earlier transactions in the *same* batch, two transactions in one batch that both write-lock the same pubkey will both be reported as successfully locked (`Ok(())`), violating the exclusive-write-access invariant that account locking is supposed to enforce.

### Finding Description
`try_lock_transaction_batch` is implemented as: [1](#0-0) 

The first `for_each` loop (lines 28-34) calls `self.can_lock_accounts(keys.clone())` for *every* transaction in `validated_batch_keys`, but this loop only mutates the `TransactionResult` wrapper on failure — it never calls `self.lock_accounts(...)` to reflect a newly-granted lock back into `self` for use by subsequent iterations of the same loop. Consequently, `can_lock_accounts` (which just reads `self.write_locks` / `self.readonly_locks`) sees the exact same pre-batch lock state for every transaction in the batch, regardless of position.

Only in the second stage (lines 36-39) is `lock_accounts` actually called, once per transaction that was marked `Ok` in the first pass, with no additional exclusivity check at that point: [2](#0-1) 

`can_write_lock` / `can_read_lock` only look at the current `write_locks`/`readonly_locks` maps: [3](#0-2) 

So for a batch `[tx1, tx2]` where both write-lock pubkey `P`, and no other transaction currently holds a lock on `P`:
- Pass 1: `can_lock_accounts` for `tx1` sees `P` unlocked → `Ok`. `can_lock_accounts` for `tx2` *also* sees `P` unlocked (state unchanged since `lock_accounts` wasn't called in this loop) → `Ok`.
- Pass 2: `lock_accounts` is called for `tx1` (write_locks[P] = 1), then for `tx2` (write_locks[P] = 2) — no conflict check is repeated here, so both entries return `TransactionResult::Ok(())`.

The end result vector reports **both** transactions as successfully locked, even though they conflict on a write-locked account. Any caller relying on this to guarantee exclusive access (e.g., banking-stage scheduling that treats `Ok` entries as free to execute concurrently) is misled into believing there is no conflict.

Duplicate accounts *within a single transaction* are separately rejected by `validate_account_locks`/`has_duplicates` (`AccountLoadedTwice`), [4](#0-3)  but this check operates per-transaction and does nothing to prevent two *different* transactions in the same batch call from conflicting with each other, since that cross-transaction check is exactly the job `try_lock_transaction_batch` fails to do correctly.

An unstaked attacker only needs to craft two independently-sanitizable, validly-signed transactions that both declare the same account as writable and submit them in packets that land in the same banking-stage consumer batch — no special privileges, stake, or config are required.

### Impact Explanation
This breaks the fundamental invariant that Agave's account-locking subsystem exists to guarantee: no two transactions may concurrently hold a write lock (or a write lock and any lock) on the same account. If both transactions are consequently treated as "locked" and dispatched for concurrent execution/replay, this is a genuine execution-isolation break that can lead to data races on account state, non-deterministic execution results, and potentially divergent/invalid recorded blocks — matching the "verification/isolation bypass" bounty category.

### Likelihood Explanation
The bug is deterministic and requires no adversarial timing or races: any two sanitized transactions writing the same pubkey, submitted so they land in the same lock-acquisition batch, trigger it every time, since the check pass in `try_lock_transaction_batch` never observes intra-batch state changes. This is trivially reproducible in a unit test with no cluster interaction, and reachable by an unstaked remote client simply constructing and submitting two transactions.

### Recommendation
Fix `try_lock_transaction_batch` so that each transaction's `can_lock_accounts` check is validated against the state *including* locks granted to earlier transactions in the same batch. The idiomatic correct approach: for each transaction in the batch (in order), call `can_lock_accounts`; if `Ok`, immediately call `lock_accounts` to mutate `self` before proceeding to the next transaction (single combined pass), rather than deferring all `lock_accounts` calls to a second, separate loop over already-decided results.

### Proof of Concept
```rust
#[test]
fn test_accounts_locks_intrabatch_write_write_conflict() {
    let mut account_locks = AccountLocks::default();
    let shared_key = Pubkey::new_unique();

    // Two independent transactions in the SAME batch, both write-locking `shared_key`.
    let tx1_keys = vec![(&shared_key, true)];
    let tx2_keys = vec![(&shared_key, true)];

    let batch: Vec<TransactionResult<_>> = vec![
        Ok(tx1_keys.into_iter()),
        Ok(tx2_keys.into_iter()),
    ];

    let results = account_locks.try_lock_transaction_batch(batch);

    // Expected (correct) behavior: exactly one Ok, one AccountInUse.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert_eq!(
        ok_count, 1,
        "both write-conflicting transactions in the same batch were locked concurrently: {results:?}"
    );
}
```
Running this test against the current implementation is expected to fail: `ok_count == 2` (both `Ok(())`), demonstrating that `try_lock_transaction_batch` grants concurrent write locks on the same account to two transactions in a single batch.

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn lock_accounts<'a>(&mut self, keys: impl Iterator<Item = (&'a Pubkey, bool)>) {
        for (key, writable) in keys {
            if writable {
                self.lock_write(key);
            } else {
                self.lock_readonly(key);
            }
        }
    }

pub fn validate_account_locks(
    account_keys: AccountKeys,
    tx_account_lock_limit: usize,
) -> TransactionResult<()> {
    if account_keys.len() > tx_account_lock_limit {
        Err(TransactionError::TooManyAccountLocks)
    } else if has_duplicates(account_keys) {
        Err(TransactionError::AccountLoadedTwice)
    } else {
        Ok(())
    }
