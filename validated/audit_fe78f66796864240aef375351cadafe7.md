### Title
Zip Extraction Path-Containment Check Uses Raw String Prefix Comparison Without Separator Boundary — Path Traversal in ijar `zipper -x` — (File: `third_party/ijar/zip_main.cc`)

### Summary
The `zipper` tool built from `third_party/ijar/zip_main.cc` extracts zip archive entries into an output directory and guards against path traversal by comparing the normalized output path against the normalized output-root directory using a raw string prefix comparison. Like the IPX advisory (`startsWith` without checking that the following character is a path separator), this check does not verify a separator boundary after the prefix, so a sibling directory that merely shares a string prefix with the intended output root is treated as "inside" it.

### Finding Description
`UnzipProcessor::Process` computes the destination path for each zip entry by concatenating `output_root_` with the (attacker-controlled) entry name via `concat_path`, then validates containment with: [1](#0-0) 

The critical check is: [2](#0-1) 

```
std::string normalized_root = normalize_path(output_root_);
std::string normalized = normalize_path(path);
if (normalized.compare(0, normalized_root.size(), normalized_root) != 0) {
  ... abort();
}
```

This is a bare prefix comparison identical in structure to the IPX bug: it never checks that `normalized[normalized_root.size()]` is `'/'` (or that the lengths are equal). Consequently, if a crafted entry name (e.g. containing `..` components) causes the concatenated, normalized path to land in a directory such as `<output_root>-evil/...`, the comparison still succeeds because the first `normalized_root.size()` bytes match character-for-character, even though the resulting path is a sibling directory outside the intended output root. This mirrors exactly the `dir` vs `dir` (no trailing separator) issue in GHSA-mm3p-j368-7jcr: containment intended to be "path is under root" is implemented as "path string starts with root string."

The `zipper` binary built from this file is invoked as a build tool during action execution to unpack zip-family archives (e.g. `.srcjar` unpacking, `.aar`/`.jar` re-packing helpers) whose *contents* originate from external, potentially attacker-controlled sources (an `http_archive`'s downloaded zip, a fetched `.aar`, a checked-in-but-attacker-influenced archive on an untrusted branch, etc.). The archive's overall bytes may be checksum-verified (e.g. via `sha256` on `http_archive`), but the *internal entry names* inside a validated-checksum archive are never separately validated for traversal-safety by this extraction code — the archive as a whole matching its pinned digest says nothing about individual entry names being safe, so a legitimate, hash-pinned archive can still contain a malicious entry name.

### Impact Explanation
A crafted zip entry name can cause `zipper -x` to write a file outside the intended extraction directory (into a sibling directory in the same parent), because the prefix-only containment check accepts any normalized destination path that textually starts with the root directory's path, not just paths that are structurally nested beneath it. This is a write outside the intended output directory, matching the "write or read outside the repository / exec root / output base" acceptance criterion.

### Likelihood Explanation
`zipper` is a core Bazel-built tool invoked from build actions unpacking archives whose contents can originate from attacker-influenced sources (fetched archives, dependency artifacts) with no additional per-entry path sanitization beyond this one flawed check. Any build that unpacks a zip-type artifact through this tool with an entry name engineered to reduce, after lexical normalization, to a sibling of the output root is exposed. No special privilege is required by the attacker beyond controlling the archive's contents.

### Recommendation
Change the containment check in `UnzipProcessor::Process` (and any other place using the same pattern) to require a separator boundary, e.g.:
```cpp
if (normalized.size() < normalized_root.size() ||
    normalized.compare(0, normalized_root.size(), normalized_root) != 0 ||
    (normalized.size() > normalized_root.size() &&
     normalized[normalized_root.size()] != '/')) {
  ... abort();
}
```
Equivalently, ensure `normalized_root` always ends with `/` before doing the prefix comparison (as suggested in the original advisory's "Possible Fix").

### Proof of Concept
Construct a zip archive with a single entry named so that, once concatenated with the output root and lexically normalized (`..` resolution), it lands in a sibling directory sharing the output root's string prefix, e.g. output root `/tmp/out` and an entry name of `../out-evil/pwned.txt`. Extracting with:
```
zipper x malicious.zip -d /tmp/out
```
should be rejected (destination is not under `/tmp/out`) but is accepted by the current prefix check because `"/tmp/out-evil/pwned.txt"` textually starts with `"/tmp/out"`, resulting in file creation at `/tmp/out-evil/pwned.txt`, outside the requested extraction root. This should be captured as a `third_party/ijar/test/zip_test.sh` (or equivalent JUnit/shell integration) case asserting extraction fails/aborts for such crafted entries instead of writing outside `-d <dir>`.

Note: I was not able to inspect the implementation of `normalize_path` (in `third_party/ijar/platform_utils.cc`) within the available tool budget to confirm precisely which `..`-escaping entry names successfully reduce to a sibling-directory string collision versus being caught by other logic (e.g., `make_dirs`/`write_file`). This detail should be verified by a background agent before finalizing a fix, but the structural flaw in the prefix-only containment check itself is confirmed directly from the source.
