### Title
Stale `YieldIdToDataId`/`DataIdToYieldId`/`PromiseYieldReceipt` state survives `DeleteAccount`, allowing a resumed yield to inject a pre-deletion callback into a re-created account of the same name - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (`core/store/src/utils/mod.rs:504-575`) deletes `Account`, `ContractCode`, access keys, gas-key nonces, and `ContractData`, but never removes `TrieKey::YieldIdToDataId`, `TrieKey::DataIdToYieldId`, `TrieKey::PromiseYieldReceipt`, or `TrieKey::PromiseYieldStatus` rows for the account. Since these trie keys are indexed only by `AccountId` (not by any account-incarnation nonce), a `yield_id` chosen and registered before an account is deleted remains resolvable and resumable after the same account name is re-created.

### Finding Description
`promise_yield_create_with_id` (`runtime/near-vm-runner/src/logic/logic.rs:3727-3813`) lets the caller supply an arbitrary 32-byte `yield_id`. It calls `create_promise_yield_receipt_with_id` (`runtime/runtime/src/ext.rs:371-400`), which writes the bidirectional mapping via `set_yield_id_mapping` (`core/store/src/utils/mod.rs:281-297`) and stores a real `PromiseYield` action receipt (with a `FunctionCall` action bound to `method_name`/`arguments` chosen at creation time) targeted at `receiver_id = self.context.current_account_id` — i.e. this is always a **self-yield**.

`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` (`core/store/src/utils/mod.rs:504-575`), which only clears `Account`, `ContractCode`, access/gas keys, and `ContractData`. It does not call `remove_yield_id_mappings` and does not remove `PromiseYieldReceipt`/`PromiseYieldStatus`. Consequently, after `DeleteAccount`, the trie still contains:
- `YieldIdToDataId{receiver_id: A, yield_id: Y} -> data_id`
- `DataIdToYieldId{receiver_id: A, data_id} -> Y`
- `PromiseYieldReceipt{receiver_id: A, data_id}` (the stored action receipt with the original `method_name`/`arguments`)
- `PromiseYieldStatus{receiver_id: A, data_id} = Yielded`

When account name `A` is re-created (`CreateAccount`, guarded only by `AccountAlreadyExists`/naming checks in `check_account_existence`, `runtime/runtime/src/actions.rs:787-855`, which never checks for or clears leftover yield state), these rows are untouched, because the new account is created as a completely independent `Account` object with no relation drawn to the previous incarnation.

If any code executing under receiver `A` later calls `promise_yield_resume_with_yield_id(Y, data)`, `submit_promise_resume_data_with_yield_id` (`runtime/runtime/src/ext.rs:428-440`) calls `get_data_id_for_yield_id(self.trie_update, &self.account_id, user_yield_id)` (`core/store/src/utils/mod.rs:299-305`), which resolves `Y` purely from the `AccountId` string, ignoring that `A`'s underlying account object has changed since `Y` was registered. This succeeds and submits resume data for the stale `data_id`. In `apply`, `VersionedReceiptEnum::PromiseResume` (`runtime/runtime/src/lib.rs:1500-1562`) then finds the stale `PromiseYieldReceipt` via `get_promise_yield_receipt` and executes it via `apply_action_receipt`, running the pre-deletion `FunctionCall` (predecessor = receiver = `A`, i.e. it passes any `#[private]`/self-only check) against whatever contract is *currently* deployed at `A`. If the newly deployed contract happens to expose a method with the same name (a real risk given widely reused templates such as NEP-141/171 `#[private]` callback methods), this fires a self-authorized call carrying attacker-chosen `method_name`/`arguments` from before the account was deleted, violating the invariant that a resumed yield must correspond to a live promise created by the *current* incarnation of the account.

No existing check prevents this: `set_yield_id_mapping`/`get_data_id_for_yield_id`/`has_yield_id_mapping` (`core/store/src/utils/mod.rs:281-324`) never validate account "identity" beyond `AccountId`, and `remove_account` performs no yield-state cleanup.

### Impact Explanation
This breaks authorization exactness across account lifecycle boundaries: state and pending promises belonging to a deleted account incarnation remain externally resumable and can be delivered into a functionally unrelated, newly created account of the same name. Depending on what privileged `#[private]`-style self-callback happens to exist in the new contract (a realistic collision given standard NEP-141/171 templates), this can be leveraged for unauthorized privileged calls (authorization escalation) or manipulation of token-transfer resolution callbacks (potential token loss/inflation), matching the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
The attacker fully controls `yield_id`, `method_name`, and `arguments` at creation time and needs only: (1) create the self-yield, (2) delete the account (a normal, unprivileged action), and (3) later call `promise_yield_resume_with_yield_id(Y)` on the re-created account name. Steps 1-3 are all standard, unprivileged transactions. The remaining precondition — that whoever re-registers the account name deploys a contract with a matching privileged self-callback method name/argument shape — is not guaranteed for an arbitrary victim, but is far from implausible given widespread reuse of standard contract templates and account-name-squatting patterns on NEAR. The core defect (stale resolvable mapping/receipt) is deterministically reproducible every time regardless of that final precondition.

### Recommendation
In `remove_account` (`core/store/src/utils/mod.rs:504-575`), also iterate and remove all `YieldIdToDataId`, `DataIdToYieldId`, `PromiseYieldReceipt`, and `PromiseYieldStatus` rows scoped to the account being deleted (mirroring the existing access-key/gas-key/contract-data cleanup loops), so no yield state outlives the account it belongs to.

### Proof of Concept
Unit test in `runtime/runtime/src/ext.rs` (or an integration test alongside `integration-tests/src/tests/runtime/test_yield_resume.rs`):
1. Call `create_promise_yield_receipt_with_id(A, Y)` to register `YieldIdToDataId{A,Y}->data_id` and a `PromiseYieldReceipt{A, data_id}`.
2. Call `remove_account(state_update, &A)`.
3. Assert `get_data_id_for_yield_id(state_update, &A, Y)` still returns `Some(data_id)` (expected: `None` after account deletion).
4. Call `submit_promise_resume_data_with_yield_id(Y, payload)` under account `A` and assert it returns `Ok(true)`, proving the resume resolves against the pre-deletion mapping/receipt even though the `Account` object was removed in between — confirming the missing cleanup in `remove_account`.
