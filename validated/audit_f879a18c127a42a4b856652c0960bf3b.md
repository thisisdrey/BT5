## Title
Account name uniqueness index (`AccountIndexStore`) can be silently hijacked/collided once `ALLOW_UPDATE_ACCOUNT_NAME` is enabled - (`actuator/src/main/java/org/tron/core/actuator/UpdateAccountActuator.java`)

### Summary
This is the same bug class as CVE-2016-3722: Jenkins allowed any authenticated user to edit a non-enforced-unique "full name" field, colliding with another user's identity string and breaking that account's usability. In java-tron, `UpdateAccountActuator` enforces account-name uniqueness against the `AccountIndexStore` (name → address index) **only** when the `ALLOW_UPDATE_ACCOUNT_NAME` dynamic chain parameter is `0`. When that parameter is set to `1` (a legitimate, committee-controlled chain parameter meant to allow users to rename their accounts more than once), all uniqueness checks are skipped entirely, allowing any account holder to set their `account_name` to a value already claimed by another account, silently overwriting that name's mapping in the shared `AccountIndexStore` index.

### Finding Description
`UpdateAccountActuator.validate()` only rejects a duplicate name when `getAllowUpdateAccountName() == 0`: [1](#0-0) 

`UpdateAccountActuator.execute()` then unconditionally writes the new name into the shared, non-account-scoped index without any uniqueness/ownership check: [2](#0-1) 

`AccountIndexStore.put()` simply keys a `name → address` mapping and blindly overwrites whatever address was previously stored under that name: [3](#0-2) 

The protocol comment for `AccountUpdateContract` itself documents the intended invariant that this mechanism should protect: `account_name` is supposed to be unique — "ALLOW_UPDATE_ACCOUNT_NAME is not enabled on Mainnet, so account names are currently unique": [4](#0-3) 

Once `ALLOW_UPDATE_ACCOUNT_NAME` is turned on (it is a normal chain-parameter proposal handled generically like any other, e.g. energy fee or CPU-time limits — no special protection is applied to it), any account holder can broadcast an `AccountUpdateContract` naming themselves identically to an already-registered account, silently reassigning the name-to-address mapping to their own address: [5](#0-4) 

This mirrors the Jenkins flaw exactly: a non-enforced-unique human-readable identity field ("full name" in Jenkins, `account_name` in java-tron) can be duplicated by an unprivileged authenticated user, hijacking name-based resolution that other parts of the system rely on to be unique, and breaking the previous holder's name-based identity resolution.

### Impact Explanation
Any client, exchange integration, or tooling that resolves accounts by human-readable name via `AccountIndexStore` will silently be redirected to the attacker's address instead of the legitimate account once the collision occurs, since the store is overwritten with no ownership check and no notification to the original holder. This is a denial-of-service against name-based account resolution for the victim account — directly analogous to the Jenkins "unable to login" DoS caused by full-name collision — and could also facilitate account/identity confusion for downstream systems that trust the name index as unique.

### Likelihood Explanation
`ALLOW_UPDATE_ACCOUNT_NAME` is a valid, reachable governance parameter already wired through the same generic proposal-processing pipeline as other production parameters (energy fee, CPU time limits, etc.), so it is not a hypothetical or malicious-only code path. Once set to `1` on any network, exploitation requires nothing more than a single signed `AccountUpdateContract` transaction from any account holder — no special privilege beyond broadcasting a transaction is needed.

### Recommendation
Enforce account-name uniqueness against `AccountIndexStore` unconditionally in `UpdateAccountActuator.validate()`, regardless of the value of `ALLOW_UPDATE_ACCOUNT_NAME` (that parameter should only govern whether an account can change its name more than once, not whether uniqueness is required), or explicitly reject overwriting an index entry whose stored address differs from the requesting owner's address.

### Proof of Concept
1. Assume the network has enabled `ALLOW_UPDATE_ACCOUNT_NAME = 1` via governance proposal (as processed in `ProposalService.process`).
2. Account A broadcasts `AccountUpdateContract{account_name: "alice", owner_address: A}` — succeeds, `AccountIndexStore["alice"] = A`.
3. Account B (any other unprivileged account) broadcasts `AccountUpdateContract{account_name: "alice", owner_address: B}` — `UpdateAccountActuator.validate()` skips both uniqueness checks (lines 89-97) because `getAllowUpdateAccountName() == 1`, and `execute()` overwrites `AccountIndexStore["alice"] = B`.
4. Any query that resolves "alice" via `AccountIndexStore.get()` now returns B's address instead of A's, with no error and no owner-only enforcement. [6](#0-5)

  public boolean validate() throws ContractValidateException {
    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }
    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (!this.any.is(AccountUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error, expected type [AccountUpdateContract], real type[" + any
              .getClass() + "]");
    }
    final AccountUpdateContract accountUpdateContract;
    try {
      accountUpdateContract = any.unpack(AccountUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountUpdateContract.getOwnerAddress().toByteArray();
    byte[] accountName = accountUpdateContract.getAccountName().toByteArray();
    if (!TransactionUtil.validAccountName(accountName)) {
      throw new ContractValidateException("Invalid accountName");
    }
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid ownerAddress");
    }

    AccountCapsule account = chainBaseManager.getAccountStore().get(ownerAddress);
    if (account == null) {
      throw new ContractValidateException("Account does not exist");
    }

    if (account.getAccountName() != null && !account.getAccountName().isEmpty()
        && chainBaseManager.getDynamicPropertiesStore().getAllowUpdateAccountName() == 0) {
      throw new ContractValidateException("This account name is already existed");
    }

    if (chainBaseManager.getAccountIndexStore().has(accountName)
        && chainBaseManager.getDynamicPropertiesStore().getAllowUpdateAccountName() == 0) {
      throw new ContractValidateException("This name is existed");
    }

    return true;
  }
