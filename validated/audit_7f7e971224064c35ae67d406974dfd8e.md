### Title
Time-of-check/time-of-use race in the anti-replay window allows replay/bypass of duplicate-packet protection - ([File: connection_state.go])

### Summary
The external report describes a class of bug where a security-critical value (an oracle price) is read, used to authorize an action, and then updated — but the read/act/update sequence is not atomic, so an attacker can slip a conflicting operation into the gap and extract value. `nebula`'s data-plane packet handler has the same structural flaw in its anti-replay logic: `ConnectionState.Decrypt` checks the replay window, releases the lock, performs the (unprotected) decryption, and only then re-acquires the lock to commit ("Update") the window state [1](#0-0) . Because the check and the commit are two separate locked critical sections with unprotected work (AEAD decryption) in between, concurrent processing of the same message counter can pass the check twice before either commits.

### Finding Description
`ConnectionState.Decrypt` is invoked from `Interface.readOutsidePackets` for every inbound `header.Message` on a tunnel [2](#0-1) . Inbound UDP packets are dispatched to per-queue worker routines (`f.readers[q]`, `q` selecting the target queue) [3](#0-2) , meaning multiple goroutines can be processing packets — including two copies of the same wire packet, or two packets with the same/adjacent message counters — for the *same* `HostInfo`/`ConnectionState` concurrently.

`Decrypt`'s logic is:
1. Lock, call `cs.window.Check(l, messageCounter)`, unlock. `Check` only inspects whether the bit is already set; it does not itself claim/reserve the slot [4](#0-3) .
2. Perform `cs.dKey.DecryptDanger(...)` with no lock held.
3. Lock, call `cs.window.Update(l, messageCounter)`, unlock, to actually record/claim the counter [1](#0-0) .

Because step 1 and step 3 are separate critical sections, two goroutines racing on the same `messageCounter` (e.g., an attacker replaying a captured ciphertext packet at the same wall-clock instant as the original transits the wire, or duplicate delivery via multiple network paths) can both pass `Check` before either has called `Update`. Both then perform the (deterministic, stateless) AEAD decrypt in step 2. This is exactly the check-then-act-then-commit pattern the external report flags as unsafe when the "commit" (price/epoch update in the oracle case, replay-window bit-set here) is not atomic with the check that authorized the action.

### Impact Explanation
The replay window (`Bits`) is the mechanism nebula relies on to prevent processing of a duplicate/replayed encrypted packet more than once. The race window between `Check` and `Update` — while decryption work runs unlocked — undermines the atomicity of that anti-replay claim. An attacker positioned to inject a duplicate/replayed UDP datagram (no CA-signed certificate needed; this is pre-authentication packet-level replay handling on an already-established tunnel index) can attempt to exploit the gap to get a replayed packet accepted concurrently with the legitimate one, defeating the deduplication invariant the anti-replay window is meant to enforce.

### Likelihood Explanation
Exploitability depends on winning a narrow race between two UDP receive paths for the same connection and counter, which is plausible given nebula's multi-queue packet reader architecture (`f.readers[q]`) processing inbound packets across worker goroutines. An attacker who can capture/replay a valid ciphertext packet (e.g. an on-path or off-path adversary able to inject duplicated UDP datagrams) does not need to break AEAD or possess a valid certificate — they only need to duplicate a packet in flight and win the race against the legitimate packet's Check/Update cycle.

### Recommendation
Make the reservation of a replay-window slot atomic with the check: hold the single lock across the full "check-and-reserve" step (as `Bits.Update`'s fast/slow paths already do), and only perform the unlocked decryption after the counter has already been provisionally reserved, rolling back the reservation if decryption authentication fails. Concretely, merge `Check`+`Update` into one locked operation performed before decryption (reserve-then-decrypt-then-confirm, with a rollback path on decrypt failure) instead of check-then-decrypt-then-commit.

### Proof of Concept
1. Establish a tunnel between two nebula instances so a `ConnectionState` with an active replay `Bits` window exists.
2. Capture a single valid encrypted `header.Message` packet with counter `N` while it is in flight to the receiver.
3. Immediately re-inject (replay) a duplicate copy of that exact packet onto a different UDP receive queue at (near-)the same instant the original arrives, so both are dispatched to different `f.readers[q]` worker goroutines calling `readOutsidePackets` → `ConnectionState.Decrypt` concurrently.
4. Because `cs.window.Check(l, N)` in both goroutines executes before either goroutine's subsequent `cs.window.Update(l, N)` runs (the lock is released between the two calls, and AEAD decryption runs unlocked in between), both goroutines can observe `Check` returning "not yet seen" and both proceed to decrypt, racing to see which one calls `Update` first; the loser is dropped, but the race window itself demonstrates the anti-replay guarantee is not atomic and can be probed/timed by an attacker capable of duplicate packet injection.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
