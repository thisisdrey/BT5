### Title
Unprivileged attacker can fill a victim's deposit-token list via dust transfers, DoSing deposits and collateral top-ups - (File: contracts/Pool.sol, contracts/DepositToken.sol)

### Summary
CVE-2016-3615 is an availability bug reachable by any authenticated user through ordinary DML operations. The Metronome analog is the per-account deposit-token list (`depositTokensOfAccount`) maintained by `Pool` and capped by `MAX_TOKENS_PER_USER`. Every `DepositToken` balance change — `deposit`, `transfer`, `transferFrom`, `seize`, `_mint` — calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's balance goes from zero to non-zero. Any EOA can deposit a dust amount of each listed collateral and then `transfer()` dust `msdTOKEN`s to a victim until their list hits the cap, after which every code path that would add a new deposit token to that account reverts.

### Finding Description
- `DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever a recipient's balance transitions 0 → >0 (`contracts/DepositToken.sol:486-488`).
- `DepositToken._transfer` does the same for the recipient (`contracts/DepositToken.sol:518-520`), and both `transfer`/`transferFrom` only require the sender's amount to be unlocked (`_revertIfLocked`, lines 350, 362) — no consent or whitelist on the recipient.
- In `Pool`, `depositTokensOfAccount` is a `MappedEnumerableSet` bounded by `MAX_TOKENS_PER_USER` (`contracts/Pool.sol`, `contracts/storage/PoolStorage.sol`); once full, `addToDepositTokensOfAccount` reverts.
- Attack steps: attacker deposits 1 wei of each underlying into every `DepositToken` in the pool (cost ≈ dust), then calls `msdToken_i.transfer(victim, 1)` for N distinct tokens until the victim's set is full.
- Result: `DepositToken.deposit(amount, onBehalfOf = victim)` reverts for any collateral the victim doesn't already hold, because `_mint` → `addToDepositTokensOfAccount` fails. The same applies to `RewardsDistributor`-driven mints, `Pool.liquidate`/`seize` flows that mint fresh tokens to the victim, and `SmartFarmingManager` deposit paths.

### Impact Explanation
Invariant broken: liveness / temporary freezing of funds. A victim who is approaching liquidation cannot top up with a collateral type they don't already hold — `deposit` reverts — so the grief can directly translate into an otherwise-avoidable liquidation (loss via liquidation penalty and seized collateral). For a debt-free victim, all deposits of new collateral types are blocked (temporary freezing of their ability to use the protocol). Recovery is only possible if the victim has unlocked balance to `withdraw` (burning a token frees a slot via `removeFromDepositTokensOfAccount`, `contracts/DepositToken.sol:460-462`), which is precisely what an underwater victim lacks.

### Likelihood Explanation
- Fully permissionless: `transfer` requires only unlocked sender balance; attacker supplies their own dust.
- Cost is bounded: one dust deposit per listed collateral type (pools list a handful of deposit tokens, well under `MAX_TOKENS_PER_USER` only if the cap exceeds the number of listed tokens — note the attack requires either many listed deposit tokens across the registry's pools the victim interacts with, or repeated tokens; feasibility depends on `MAX_TOKENS_PER_USER` vs. the number of distinct `DepositToken` contracts the attacker can mint dust of. If the cap is larger than the count of listed deposit tokens, the list cannot be force-filled this way and the finding degrades to requiring many registered collaterals).
- No privileged role, oracle manipulation, or governance action needed; `onlyIfDepositTokenExists`, `whenNotPaused`, and `ReentrancyGuardTransient` do not impede the transfer path.

### Recommendation
- Enforce the `MAX_TOKENS_PER_USER` cap only on state-changing actions initiated by the account (e.g., in `deposit`), and treat `addToDepositTokensOfAccount` as non-fatal (return bool / skip) for unsolicited inbound transfers, mirroring how airdrop-dust is normally handled.
- Alternatively, keep a single global `EnumerableSet` of listed deposit tokens and compute per-account holdings by iterating listed tokens in `debtPositionOf`, removing the per-account cap entirely.
- Add a regression test: attacker dust-transfers `MAX_TOKENS_PER_USER` distinct `msdToken`s to a victim; assert `deposit(..., onBehalfOf = victim)` with a new collateral still succeeds.

### Proof of Concept
Hardhat fork sketch (against a live pool on Optimism/Base):

```ts
// attacker: EOA, victim: existing user
const pool = await ethers.getContractAt("Pool", POOL);
const n = await pool.MAX_TOKENS_PER_USER(); // cap
const depositTokens = await pool.getDepositTokens(); // listed msdTokens

for (let i = 0; i < n; i++) {
  const msd = await ethers.getContractAt("DepositToken", depositTokens[i % depositTokens.length]);
  const underlying = await ethers.getContractAt("IERC20", await msd.underlying());
  // attacker acquires 1 wei of underlying (whale impersonation on fork), approves, deposits
  await underlying.approve(msd.address, 1);
  await msd.deposit(1, attacker.address);
  // dust-transfer to victim; each new token adds to victim's depositTokensOfAccount
  if (!(await msd.balanceOf(victim.address)).gt(0)) {
    await msd.transfer(victim.address, 1);
  }
}
```
