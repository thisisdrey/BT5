### Title
CREATE2 fails to reset the RETURNDATA buffer pre-Osaka, disclosing stale internal call data via RETURNDATASIZE/RETURNDATACOPY - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
`Program.createContract2` (the TVM `CREATE2` opcode handler) only clears `returnDataBuffer` before performing the sub-call when the `allowTvmOsaka` feature flag is enabled. When that flag is off (the default/legacy behavior path exercised throughout the codebase's test config gating), a failed or short-circuited `CREATE2` leaves the previous call's return-data buffer intact, so `RETURNDATASIZE`/`RETURNDATACOPY` executed immediately afterward return stale data from an earlier, unrelated internal call rather than the empty result a failed `CREATE2` should produce.

### Finding Description
Every other call-type opcode handler in `Program.java` resets `returnDataBuffer = null` unconditionally right before performing the sub-call:
- `createContract` (plain `CREATE`): `returnDataBuffer = null; // reset return buffer right before the call` [1](#0-0) 
- `callToAddress` (`CALL`/`CALLCODE`/`DELEGATECALL`/`STATICCALL`): same reset pattern [2](#0-1) 
- `callToPrecompiledAddress`: same reset pattern [3](#0-2) 

But `createContract2` (`CREATE2`) guards this reset behind a feature flag:
```java
public void createContract2(DataWord value, DataWord memStart, DataWord memSize, DataWord salt) {
    if (VMConfig.allowTvmOsaka()) {
      returnDataBuffer = null; // reset return buffer right before the call
    }
    ...
``` [4](#0-3) 

When `allowTvmOsaka()` is false, `CREATE2` proceeds straight into `createContractImpl` without clearing `returnDataBuffer`. If the internal creation subsequently fails/reverts before setting a new `returnDataBuffer` (e.g. it hits an exception path that returns early), the stale value from a prior unrelated `CALL`/`CREATE`/precompile invocation made earlier in the same transaction remains visible via `RETURNDATASIZE`/`RETURNDATACOPY`:
```java
public static void returnDataCopyAction(Program program) {
    ...
    byte[] msgData = program.getReturnDataBufferData(dataOffsetData, lengthData);
``` [5](#0-4) 

`getReturnDataBufferData` simply serves whatever is currently stored in `returnDataBuffer`: [6](#0-5) 

The project's own regression test explicitly documents this as a known bug that is conditionally fixed only when Osaka is enabled — pre-Osaka a failed `CREATE2` "keeps the previous 32-byte return data buffer" instead of clearing it, while post-Osaka it correctly clears to zero: [7](#0-6) [8](#0-7) 

This is directly analogous to CVE-2017-15275's root cause class: a code path that fails to clear a buffer before it becomes visible to an external observer, causing a piece of data left over from a prior, unrelated operation to be disclosed.

### Impact Explanation
This is reachable by any unprivileged contract deployer/caller: any smart contract can perform an internal `CALL` (or `CREATE`) that produces return data, then attempt a `CREATE2` that is designed to fail (e.g. deploying to an address that already has code, or an init-code that reverts), and immediately execute `RETURNDATASIZE`/`RETURNDATACOPY`. Instead of observing an empty return-data buffer (the correct EVM/TVM semantics for a failed creation), the caller/consuming contract observes leftover data from the earlier, logically unrelated call. Downstream contracts that rely on `RETURNDATASIZE` immediately after `CREATE2` to determine success/failure (a common pattern in minimal-proxy/factory deployment code) can be misled into believing a deployment succeeded (or into copying stale bytes as if they were fresh output), enabling a crafted contract to manipulate composability assumptions of other contracts that call into it, potentially leading to fund loss or incorrect on-chain accounting when relying contracts act on the bogus return data.

### Likelihood Explanation
Triggering the bug requires only ordinary, unprivileged bytecode: perform any internal call that leaves non-empty return data, then execute a `CREATE2` designed to fail, then read `RETURNDATASIZE`/`RETURNDATACOPY`. No special permissions, SR/witness status, or network position are needed — it is exploitable from a single deployed contract triggered by any transaction sender. The main uncertainty is whether `allowTvmOsaka` is currently enabled on the live/target chain configuration this repository builds for; if the flag is already active in production, this specific code path is already mitigated. I could not determine the deployed activation status of `allowTvmOsaka` in this snapshot beyond confirming the flag exists and gates the fix.

### Recommendation
Remove the `VMConfig.allowTvmOsaka()` gate around the `returnDataBuffer = null` reset in `createContract2`, making the reset unconditional (matching `createContract`, `callToAddress`, and `callToPrecompiledAddress`), so `CREATE2` always clears stale return data before performing the sub-call regardless of feature-flag activation state.

### Proof of Concept
1. Deploy a contract `Attacker` with a function that:
   - Performs an internal `CALL` to any contract/precompile that returns non-empty data (e.g. `IDENTITY` precompile with 32 bytes of nonzero data), leaving `returnDataBuffer` populated with those 32 bytes.
   - Immediately executes `CREATE2` with init-code designed to fail deployment (e.g., deploying to a `salt` that collides with an existing contract address, so `contractAlreadyExists` is true and `createResult.setException(...)` is invoked without ever reaching a return-data-setting branch).
   - Executes `RETURNDATASIZE` followed by `RETURNDATACOPY` and returns the copied bytes.
2. With `allowTvmOsaka` disabled (pre-Osaka default), the returned bytes equal the 32 bytes from the earlier unrelated `CALL`, not empty data — this exact scenario is codified in `TvmIssueVerifierTest.verifyTvmOsakaFixesWithSolidity()` under the `saveAllowTvmOsaka(0)` branch, which asserts the failed `CREATE2` return-data word equals `32` (the stale buffer's size marker) instead of `0`. [9](#0-8) 
3. Enabling `allowTvmOsaka` and re-running the identical trigger shows the return-data word correctly becomes `0`, confirming the flag is the only thing preventing disclosure of the stale buffer. [10](#0-9)
