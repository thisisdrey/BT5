### Title
Per-connection unstaked stream throttle does not scale with aggregate unstaked connection count, allowing unstaked senders to consume far more than their intended QoS share - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`StakedStreamLoadEMA::available_load_capacity_in_throttling_duration` returns a fixed per-connection throughput cap for unstaked connections (`max_unstaked_load_in_throttling_window`, derived from `MAX_UNSTAKED_TPS`), and this same fixed cap is applied identically to every unstaked connection regardless of how many unstaked connections are concurrently open, up to `max_unstaked_connections`. Because the cap is not divided across the pool of unstaked connections, an attacker opening many parallel unstaked connections (each individually obeying its own throttle) can drive aggregate unstaked throughput to `max_unstaked_connections * per_connection_cap`, far exceeding the intended `EXPECTED_UNSTAKED_STREAMS_RATIO * max_streams_per_ms` aggregate budget.

### Finding Description
In `streamer/src/nonblocking/stream_throttle.rs`, `StakedStreamLoadEMA::new` computes: [1](#0-0) 
`max_unstaked_load_in_throttling_window = MAX_UNSTAKED_TPS * STREAM_THROTTLING_INTERVAL_MS / 1000`, i.e. with `MAX_UNSTAKED_TPS = 200` this equals 20 streams per 100ms window [2](#0-1) .

This value is returned unchanged for *every* unstaked connection by `available_load_capacity_in_throttling_duration`: [3](#0-2) 

It is consumed per-connection in `SwQos::on_new_stream` → `max_streams_per_throttling_interval` → `throttle_stream`, which only tracks and throttles the stream count for the *individual* connection's `ConnectionStreamCounter`: [4](#0-3) [5](#0-4) [6](#0-5) 

There is no global/aggregate counter across all unstaked connections limiting the sum of their throughput to the intended `EXPECTED_UNSTAKED_STREAMS_RATIO * max_streams_per_ms` share (e.g. with defaults `DEFAULT_MAX_STREAMS_PER_MS = 500` and ratio `0.20`, the intended aggregate unstaked budget is ~100,000 streams/sec) [7](#0-6) [8](#0-7) .

Instead, the only cap on aggregate unstaked connections is `max_unstaked_connections` (default 2000) enforced by `SwQos::try_add_connection` / `prune_unstaked_connections_and_add_new_connection`, which bounds *connection count*, not aggregate throughput [9](#0-8) [10](#0-9) .

With defaults, each unstaked connection can independently sustain ~200 streams/sec (20/100ms), and with up to 2000 concurrent unstaked connections admitted, the achievable aggregate unstaked throughput is `2000 * 200 = 400,000 streams/sec` — roughly 4x the intended ~100,000 streams/sec unstaked budget, and close to the entire system-wide `DEFAULT_MAX_STREAMS_PER_MS` capacity of 500,000 streams/sec. This happens even though each individual connection strictly obeys `throttle_stream`'s per-connection limit; the QoS accounting simply never aggregates across connections.

Each admitted stream that passes `throttle_stream` proceeds to `handle_chunks`, which calls `packet_sender.try_send(packet_batch)` into the shared `packet_batch_sender` channel feeding sigverify/banking [11](#0-10) . The channel itself is a bounded crossbeam channel (evidenced by `TrySendError::Full` handling), so it does not grow unbounded; but a flood of unstaked packets can still fill/saturate that shared bounded buffer, which is consumed by both staked and unstaked traffic, causing staked-node packets to be delayed or dropped via `TrySendError::Full` while unstaked traffic occupies a disproportionate share of the channel's throughput.

### Impact Explanation
This is a QoS-evasion / fairness-bypass: an unstaked, unprivileged attacker can consume several times the intended unstaked share of ingress bandwidth into `packet_batch_sender`, degrading the effective bandwidth guaranteed to staked senders (whose entire purpose is to be prioritized over unstaked traffic). This matches the "QoS evasion" bounty category referenced in the question — aggregate unstaked throughput exceeding `MAX_UNSTAKED_TPS * EXPECTED_UNSTAKED_STREAMS_RATIO`'s intended cap, starving staked senders' share of downstream sigverify/banking capacity. It does not cause unbounded memory growth (the channel is bounded), so the "unbounded buffer growth" portion of the question is not confirmed by the code; the confirmed impact is throughput starvation, not memory exhaustion.

### Likelihood Explanation
Highly feasible for an unprivileged attacker: no stake or validator control is required, only opening many QUIC connections to the leader's public TPU port (bounded only by `max_connections_per_ipaddr_per_min`/rate limiters and `max_connections_per_unstaked_peer`, which the attacker can circumvent using many source IPs). Each connection just needs to send streams at its own per-connection cap — well within legitimate/observed behavior of `throttle_stream`, so no anomaly triggers additional mitigation. The attack is fully reproducible with a deterministic unit test computing the aggregate cap.

### Recommendation
Introduce a global token bucket / EMA-based aggregate throttle for unstaked traffic (analogous to `StakedStreamLoadEMA`'s staked-side load accounting) that tracks total unstaked stream admission rate across all unstaked connections, and have `available_load_capacity_in_throttling_duration` for `ConnectionPeerType::Unstaked` divide the fixed unstaked budget by the current number of active unstaked connections (or enforce a shared token bucket consumed by all unstaked connections), so that aggregate unstaked throughput stays bounded by `MAX_UNSTAKED_TPS`-derived budget regardless of `max_unstaked_connections`.

fn test_aggregate_unstaked_throughput_exceeds_intended_ratio() {
    let load_ema = StakedStreamLoadEMA::new(
        Arc::new(StreamerStats::default()),
        DEFAULT_MAX_UNSTAKED_CONNECTIONS, // 2000
        DEFAULT_MAX_STREAMS_PER_MS,       // 500

    let aggregate_cap_per_sec =
        per_conn_cap as f64 * 10.0 /*windows per sec*/ * DEFAULT_MAX_UNSTAKED_CONNECTIONS as f64;
    let intended_unstaked_budget_per_sec =
        EXPECTED_UNSTAKED_STREAMS_RATIO * (DEFAULT_MAX_STREAMS_PER_MS as f64 * 1000.0);

    // larger than the intended EXPECTED_UNSTAKED_STREAMS_RATIO-based budget.

        "aggregate unstaked cap {aggregate_cap_per_sec} should not exceed intended budget \
         {intended_unstaked_budget_per_sec}, but per-connection throttling allows it"
    );
}

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
}
