### Title
Precompiled-contract endowment transfer is charged before validation and is not rolled back on failure, permanently burning caller funds - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`Program.callToPrecompiledAddress()` (used for every `CALL`/`CALLCODE`/`DELEGATECALL`/`STATICCALL` opcode targeting a precompiled address, including the shielded-TRC20 mint/transfer/burn precompiles) transfers the call's TRX/TRC10 endowment from caller to the precompiled contract's context **before** the precompiled logic is executed and validated. The code explicitly comments that this transfer "is not reversible by rollback." If the precompiled contract afterwards reports failure (`out.getLeft() == false`, e.g. an invalid zk-proof, malformed input, or any logic that returns `false` rather than throwing), the deposit's balance mutation for the endowment persists in the child repository while the "success" side effects (state changes belonging to the precompiled contract, such as note commitments or minted balances) are discarded because `deposit.commit()` is only called in the success branch. This mirrors the reported bridge bug: a two-phase (burn-then-mint) style operation whose first phase (value transfer) is irreversibly committed but whose second phase (precompiled validation / mint) can fail, leaving the caller's value transferred with no compensating result.

### Finding Description
`callToPrecompiledAddress` builds a new child repository `deposit = getContractState().newRepositoryChild()` [1](#0-0) , and unconditionally moves the endowment on that child repository via `MUtil.transfer(...)` (or TRC10 `addTokenBalance`) prior to calling the precompiled contract, with the comment marking the transfer as irreversible: [2](#0-1) 

The precompiled contract is then executed, and only on success is `deposit.commit()` invoked to push the transfer (and other side effects) up into the parent repository; on failure, the code simply zeroes the stack and refunds energy, without reversing the endowment transfer that already happened on `deposit`: [3](#0-2) 

Because `deposit` is a distinct `RepositoryImpl` child whose balance-mutation methods (`addBalance`/`addTokenBalance`) directly mutate its own `accountCache`/token caches immediately (not deferred to `commit()`), any code path that reads the balance from this same `deposit` object after the failed `contract.execute()` call (for example, chained precompiled or internal calls within the same call frame that reuse `deposit`, or the "success" flag pushed to the stack being misinterpreted by calling Solidity code that doesn't correctly check the return value) will observe the caller's balance already debited and the destination credited, even though the precompiled operation that was supposed to validate/process that transfer reported failure. This exactly parallels the audited Hyperlane teller bug: "the burn side of a value-moving operation completes irrevocably while the corresponding mint/validate side can independently fail," and there is no code path that reverses the pre-charged endowment when the precompiled contract signals failure.

### Impact Explanation
If exploitable (see uncertainty below), this allows unauthorized loss of caller funds: a contract calling a precompiled address with a non-zero endowment can have its TRX/TRC10 balance debited to the precompile's context address while the precompile's actual effect (e.g., shielded-TRC20 mint proof verification, or any other value-consuming precompiled operation) fails and is discarded. The debited amount is not restored, resulting in a permanent, unrecoverable loss of funds equivalent to the impact described in the H-01 style report (assets burned/moved on one side with no compensating completion on the other, without any retry or rollback mechanism at the TVM level for this specific pre-charge).

### Likelihood Explanation
Likelihood is Low-to-Medium and unverified: it requires a precompiled contract that (a) accepts a non-zero endowment via `CALL`, and (b) can be made to return `false` (rather than throwing, which would trigger a full exception-based state rollback via the higher-level revert/exception handling in `VMActuator`) after the endowment has already been unconditionally transferred on `deposit`. Ordinary contract-to-contract calls that fail typically cause the outer VM execution to revert entirely (since `result.isRevert()`/exception handling in `VMActuator.execute()` discards the whole child repository), which would nullify this issue in the common case. The exploitability therefore hinges on whether any precompiled contract that accepts endowment can fail by returning `(false, ...)` without throwing, and whether that failure path can be observed/exploited without the encompassing transaction itself reverting/discarding `deposit`. This detail could not be fully confirmed within the scope of this investigation — a background agent with full test/execution access would be needed to enumerate value-accepting precompiles and trace whether `deposit`'s pre-commit mutations are ever externally observable or persisted despite `out.getLeft() == false`.

### Recommendation
Defer the endowment transfer until after `contract.execute()` succeeds, or perform the transfer on a nested child repository that is discarded (not just left uncommitted) on precompile failure, ensuring balance changes are only applied when `deposit.commit()` actually happens. At minimum, verify that no execution path can read/rely on `deposit`'s in-memory balance mutation between the transfer and the failure branch, and add an explicit test proving that a failed precompiled call leaves the caller's balance completely unchanged.

### Proof of Concept
Could not be constructed with confidence in ask-only/read-only mode: reproducing this would require identifying a specific precompiled contract accepting endowment that returns `(false, ...)` (not an exception) on invalid input, and demonstrating that the `deposit.addBalance`/`addTokenBalance` mutation from `callToPrecompiledAddress` (lines 1709-1732) is observable/persisted despite the surrounding transaction not fully reverting. This requires deployment and execution tracing in a full node/test environment, which is outside the scope of static code review performed here.
