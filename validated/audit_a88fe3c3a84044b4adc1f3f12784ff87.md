### Title
Unchecked length field from precompiled-contract call data drives unbounded array allocation, causing OutOfMemoryError DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytesArray` and `extractSigArray` read an array-length value directly out of attacker-controlled TVM call data and immediately use it to allocate a Java array (`new byte[len][]`), without validating that `len` is bounded by the actual size of the supplied data. This mirrors the snappy-java `hasNextChunk` bug class (CWE-770): an unchecked length taken from untrusted input is used as an allocation size, allowing a caller to force `OutOfMemoryError`/excessive-allocation before any content-length cross-check occurs.

### Finding Description
In `extractBytesArray` and `extractSigArray`: [1](#0-0) [2](#0-1) 

Both helpers do:
```
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
```
`len` comes straight from a `DataWord` decoded from the caller-supplied `data` (the precompile's `execute(byte[] data)` argument), which is fully controlled by an unprivileged contract caller via a `TriggerSmartContract` transaction that performs a `CALL`/`STATICCALL` to the corresponding precompiled-contract address. There is no upper bound check on `len` before the allocation (`new byte[len][]`) is performed; the subsequent loop that reads `words[offset + i + 1]` will throw an `ArrayIndexOutOfBoundsException` only *after* the array has already been sized, so a caller supplying a very large `len` value (e.g. close to `Integer.MAX_VALUE`) can force the JVM to attempt a massive allocation before any bounds validation happens.

This is analogous to the snappy-java issue: `chunkSize`/`len` is taken from untrusted data and used unchecked as `new byte[...]` size, which can raise `OutOfMemoryError` — an error type that ordinary `try { } catch (Exception e)` handlers around VM execution will not catch, since `OutOfMemoryError` extends `Error`, not `Exception`.

### Impact Explanation
A crafted contract call (from any unprivileged account, e.g. a `TriggerSmartContractActuator`-processed transaction) reaching a precompiled contract that uses `extractBytesArray`/`extractSigArray` can trigger a large allocation attempt on every full node that executes/validates the transaction (including during block application in `Manager`). If the JVM raises `OutOfMemoryError` during array allocation, and if that error is not exhaustively caught up the VM execution stack, it can crash the node process or destabilize the JVM heap for concurrent operations, producing a Denial-of-Service condition — matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
Likelihood depends on whether these two helpers are reachable from a precompile whose input is fully attacker-controlled and unvalidated before this point (e.g., a multi-signature/batch-verification precompile). Given `words` is derived from calldata offsets and the surrounding code (seen in the neighboring `PrecompiledContracts.java` verifyTransferProof, which explicitly validates counts like `spendCount`/`receiveCount` against tight bounds of `[1,2]` before any allocation) shows the codebase is aware of this bug class and defends it in some proof-verification paths — but `extractBytesArray`/`extractSigArray` shown above lack the equivalent bound check on `len`. I was not able to fully trace, within the remaining tool budget, the exact precompile(s) that call `extractBytesArray`/`extractSigArray` or confirm `DataWord.intValueSafe()`'s exact clamping behavior (its source could not be located in the indexed subset of `DataWord.java`), so the reachability and exact severity cannot be certified with full confidence.

### Recommendation
Add an explicit upper-bound / sanity check on `len` in `extractBytesArray` and `extractSigArray` (e.g., cap it to the maximum number of words derivable from `data.length`, mirroring the defensive check already used for `spendCount`/`receiveCount` in `verifyTransferProof`) before allocating `new byte[len][]`. Verify `DataWord.intValueSafe()` truly returns a sane, non-adversarial `int`, and if not, clamp/validate its result against the actual size of the input buffer prior to any array allocation.

### Proof of Concept
Not verified end-to-end due to inability to confirm the exact precompile entry point and `intValueSafe()` semantics within the remaining investigation budget. Conceptually: submit a `TriggerSmartContract` transaction whose calldata to a precompile using `extractBytesArray`/`extractSigArray` sets the length word (`words[offset]`) to a very large value (e.g. `0x7FFFFFFF`), causing `new byte[len][]` to attempt an allocation far exceeding available heap, before the subsequent index bound-check exception is thrown.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];

      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;

          bytesLen);
    }
    return bytesArray;
  }
