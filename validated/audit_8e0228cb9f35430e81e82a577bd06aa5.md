The premise doesn't hold up against the actual code. There is no separate "sender-side per-transaction check" vs. "receiver-side `action_receipt_required_cost` check" that use different summation logic — both paths funnel through the exact same `total_prepaid_gas` function using `checked_add_result` over `u64` `Gas` values, and this same aggregate check is applied identically at every admission point:

- **Transaction admission**: `validate_actions_with_mode` sums `total_prepaid_gas(actions)` via `checked_add_result` in a simple left-to-right loop and rejects with `TotalPrepaidGasExceeded` if the sum exceeds `limit_config.max_total_prepaid_gas`. [1](#0-0) 
- **New-receipt admission (including all contract-generated and delegate-generated receipts)**: every receipt produced during action execution — including those created by `apply_delegate_action` — is passed through `validate_receipt(..., ValidateReceiptMode::NewReceipt)` immediately after each action executes, which calls the identical `validate_actions_with_mode` code path. [2](#0-1) 
- `total_prepaid_gas` itself is a single shared function (`runtime/runtime/src/config.rs`) used by both callers, iterating actions in declaration order and using `checked_add_result` (which returns `IntegerOverflowError` on overflow rather than wrapping). [3](#0-2) 

Since all values are `u64` gas integers and addition is performed via `checked_add_result` (exact, non-lossy, overflow-checked), there is no "rounding" or order-of-summation ambiguity: integer addition of a fixed multiset of values always produces the same exact sum regardless of order, and any true overflow is caught as `IntegerOverflow`, not silently truncated. This is confirmed by existing unit tests asserting identical `TotalPrepaidGasExceeded` rejection for the same action list. [4](#0-3) [5](#0-4) 

`action_receipt_required_cost` (`runtime/runtime/src/actions.rs:537-556`) is a distinct helper used only to compute the gas the *relayer* must be charged when a `DelegateAction` spawns a new receipt — it does not perform (nor replace) the `max_total_prepaid_gas` admission check; that check is still separately and uniformly enforced by `validate_receipt(NewReceipt)` on the resulting receipt before it's queued. [6](#0-5) 

Since the same deterministic, overflow-checked summation function gates gas admission at every creation point (transaction conversion and every newly emitted receipt), there is no reachable path by which an aggregate-gas-exceeding receipt could pass admission at one site but not another.

pub fn total_prepaid_gas(actions: &[Action]) -> Result<Gas, IntegerOverflowError> {
    let mut total_gas = Gas::ZERO;
    for action in actions {
        let action_gas;
        if let Some(delegate_action) = delegate_inner_action(action) {
            let actions = delegate_action.get_actions();
            action_gas = total_prepaid_gas(&actions)?;
        } else {
            action_gas = action.get_prepaid_gas();
        }

        total_gas = total_gas.checked_add_result(action_gas)?;
    }
    Ok(total_gas)
}

fn action_receipt_required_cost(
    apply_state: &ApplyState,
    receipt: &Receipt,
    action_receipt: VersionedActionReceipt,
) -> Result<ParameterCost, RuntimeError> {
    let mut required_gas = total_prepaid_exec_fees(
        &apply_state.config,
        &action_receipt.actions(),
        receipt.receiver_id(),
    )?;
    let attached_gas = total_prepaid_gas(&action_receipt.actions())?;
    // Gas attached to outgoing function calls have no associated compute costs.
    // Compute costs are only relevant when burning gas.
    let attached_gas_cost = ParameterCost { gas: attached_gas, compute: 0 };
    required_gas = required_gas.checked_add_result(attached_gas_cost)?;
    required_gas = required_gas.checked_add_result(
        apply_state.config.fees.fee(ActionCosts::new_action_receipt).exec_fee(),
    )?;
    Ok(required_gas)
}
