### Title
Replay-window Check/Update race allows duplicate packet delivery to tun despite anti-replay window - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` releases `decryptLock` between `window.Check` and `window.Update`, decrypting outside the lock. Two identical UDP packets (same `messageCounter`) delivered to the same `HostInfo` on different reader routines can both pass `Check` before either calls `Update`, resulting in both being decrypted and forwarded to the tun device.

### Finding Description
`Decrypt` in `connection_state.go` performs three separate critical sections instead of one atomic check-decrypt-update: [1](#0-0) 
It locks `decryptLock`, calls `cs.window.Check(l, messageCounter)`, and unlocks — then decrypts unlocked — then re-locks to call `cs.window.Update(l, messageCounter)`. Because the lock is dropped between `Check` and `Update`, two goroutines racing on the same `messageCounter` can both observe `Check` returning `true` before either has called `Update`.

This is reachable by an unprivileged attacker: Nebula's `Interface` spawns one `listenOut` goroutine per configured routine (`listen.routines`), each independently calling `readOutsidePackets` → `hostinfo.ConnectionState.Decrypt`: [2](#0-1) [3](#0-2) 
An attacker who can send UDP packets to the node's listening port (source address is otherwise irrelevant since the packet is looked up by `RemoteIndex`, not by source IP) can capture one legitimate encrypted data packet from the wire (no key material needed — this is a valid, previously-observed ciphertext, so the AEAD tag still checks out) and retransmit it twice, timed to land on two different UDP reader routines simultaneously. If `routines > 1` (multi-queue enabled), both `Decrypt` calls can interleave such that both pass `window.Check` before either finishes `window.Update`, since `DecryptDanger` (AEAD open) happens with the lock released between lines 65 and 75.

The replay window (`Bits.Check`/`Bits.Update` in `bits.go`) itself is logically correct if invoked atomically as a single guarded operation, but the split-lock pattern in `Decrypt` breaks that atomicity guarantee under concurrency.

### Impact Explanation
This does not break AEAD/nonce security (no counter reuse in the cryptographic sense — the same counter is being reused for genuinely the same ciphertext, not a forged one), but it defeats the intended replay-window guarantee: the same already-decrypted plaintext packet can be written to the tun device twice via `f.readers[q].Write(out)`. Depending on the payload (e.g., a non-idempotent application-layer message), duplicate injection could cause application-level side effects to occur twice. This matches a "traffic replay" class impact (partial bypass of the anti-replay window) rather than full decryption/forgery, since it requires an already-valid ciphertext and only causes duplicate delivery, not new plaintext disclosure.

### Likelihood Explanation
Requires: (1) the target running with `listen.routines > 1` (multi-reader UDP, common on Linux with `SO_REUSEPORT`), (2) the attacker being able to capture/replay one legitimate ciphertext packet (observable on-path, or by being another endpoint on a shared network segment, or by racing their own tunnel's own outbound wire traffic if applicable), and (3) precise timing to land both copies on different reader goroutines within the small window between `Check` and `Update` (sub-microsecond race, requiring many retries but statistically achievable, e.g., via a tight loop or via a testing harness as described in the PoC). This makes it a low but nonzero probability event in production, but deterministically reproducible in a concurrency test that removes the timing uncertainty by calling `Decrypt` from two goroutines synchronized to enter simultaneously.

### Recommendation
Make the check-decrypt-update sequence atomic with respect to a given `messageCounter`: hold `decryptLock` across the whole `Check`→`Decrypt`→`Update` sequence (accepting that this serializes decryption per-`ConnectionState`), or restructure `Bits` to expose a single `CheckAndReserve`/`TryReserve` primitive that marks the slot as "pending" under one lock acquisition, decrypts, then finalizes/rolls back, so no second caller can observe the same counter as "not yet seen" while the first is still processing it.

### Proof of Concept
Add a concurrency test in `connection_state_test.go`:
1. Build a `ConnectionState` with real `eKey`/`dKey` ciphers (as existing tests do) and a fresh `Bits` window.
2. Encrypt one packet with `eKey` at a fixed `messageCounter` (e.g., 5) to get `packet`.
3. Launch two goroutines, synchronized via a `sync.WaitGroup`/barrier channel to call `cs.Decrypt(l, 5, out1, packet, nb1)` and `cs.Decrypt(l, 5, out2, packet, nb2)` as close to simultaneously as possible (optionally loop the whole test N times or insert `runtime.Gosched()`/a manual delay hook between `Check` and `Decrypt` to force the race deterministically).
4. Assert that **at most one** call returns `(out, nil)` and the other returns `ErrAlreadySeen`. On the buggy implementation, under the race, both can return `nil` error, demonstrating duplicate acceptance of the same `messageCounter`/ciphertext. [1](#0-0) [4](#0-3)

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {

	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
