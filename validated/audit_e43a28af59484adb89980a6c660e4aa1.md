Audit Report

## Title
Bounty payout silently fails below the existential deposit, permanently stranding funds in the bounty sub-account - (File: `substrate/frame/bounties/src/lib.rs`)

## Summary
`claim_bounty` transfers the curator fee and beneficiary payout via `T::Currency::transfer(..., AllowDeath)` but only checks the result with `debug_assert!`, which is compiled out in release builds. The bounty's storage entry is then unconditionally deleted regardless of transfer success, so if either transfer fails (e.g., a payout below `ExistentialDeposit` to a fresh account), the funds are permanently stranded in the bounty's derived sub-account with no remaining state pointing to them.

## Finding Description
In `claim_bounty`, `payout = balance.saturating_sub(fee)` is computed and transferred to `beneficiary` with `AllowDeath`, and `final_fee` is transferred to `curator`, both guarded only by `debug_assert!(res.is_ok())` rather than propagated with `?`: [1](#0-0) 

Immediately after, regardless of whether the transfers succeeded, the bounty entry is deleted and its description removed: [2](#0-1) 

`pallet_balances` enforces that a transfer into a nonexistent account below `ExistentialDeposit` returns `TokenError::BelowMinimum` rather than succeeding, as shown by existing balances tests. Since `claim_bounty` is callable by any signed account once a bounty is in `PendingPayout` status (`ensure_signed(origin)?; // anyone can trigger claim`), any observer can trigger the final claim step once a qualifying bounty exists: [3](#0-2) 

The identical pattern (debug_assert-only error handling followed by unconditional storage removal) exists in `claim_child_bounty` in `substrate/frame/child-bounties/src/lib.rs`.

## Impact Explanation
This is a permanent user-fund lock: the payout balance, which should settle to the beneficiary, is instead stranded irrecoverably in the bounty's `PalletId`-derived sub-account after the only on-chain reference to that balance (the `Bounties` storage entry) is deleted in the same transaction. No privileged action is required to trigger it — it is a direct consequence of ordinary bounty value/fee arithmetic combined with a permissionless, unprivileged call, matching the "permanent user-fund lock" impact category in scope.

## Likelihood Explanation
Triggering requires only that a bounty reach `PendingPayout` with a residual `payout` (or `final_fee`) below the chain's `ExistentialDeposit` for a not-yet-existing beneficiary/curator account — a plausible configuration for small bounties or ones where most value is consumed by curator fee, especially on chains with non-trivial ED. Because `claim_bounty` is permissionless (`ensure_signed` only, no origin restriction to beneficiary/curator), any account can complete the claim and irreversibly delete the bounty record once such conditions exist, making this readily and repeatably triggerable by an unprivileged actor (e.g., the bounty proposer/curator choosing the fee/value split, or beneficiary address).

## Recommendation
Propagate the `DispatchResult` of both `T::Currency::transfer` calls with `?` instead of `debug_assert!`, and only clear the bounty (and child-bounty) storage entries after both transfers actually succeed — or adopt a `PayoutAttempted`/retry mechanism analogous to `pallet-multi-asset-bounties`. Alternatively, floor `payout`/`final_fee` at `ExistentialDeposit` or reject award/claim combinations producing sub-ED payouts to nonexistent accounts.

## Proof of Concept
1. Configure a chain with a non-trivial `ExistentialDeposit`.
2. Propose and fund a bounty whose `value`/`fee` are set (via governance `award_bounty` flow) such that `payout = value - fee < ED`, with `beneficiary` a brand-new zero-balance account.
3. Wait for `unlock_at` to elapse (`BountyDepositPayoutDelay`).
4. Any signed account calls `claim_bounty(bounty_id)`.
5. In a release build, `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err(TokenError::BelowMinimum)`, discarded by `debug_assert!(res.is_ok())`.
6. `*maybe_bounty = None;` executes unconditionally, deleting the bounty and its description.
7. `payout` remains stuck in `bounty_account` with no remaining on-chain reference or recovery path.
