## Title
HTTP/2 Rapid Reset (CVE-2023-44487 class) DoS remains unmitigated by default on java-tron's gRPC API servers - (File: `framework/src/main/java/org/tron/common/application/RpcService.java`)

### Summary
java-tron's gRPC API servers (FullNode `50051`, Solidity `50061`, PBFT `50071`) implement a dedicated HTTP/2 RST_STREAM rate limiter (`maxRstFramesPerWindow`) specifically to defend against the HTTP/2 Rapid Reset attack class (CVE-2023-44487), the exact bug class referenced in the external report. However, this defense is only wired up when both `node.rpc.maxRstStream` and `node.rpc.secondsPerWindow` are explicitly configured to positive values. Every shipped configuration (production `config.conf`, `reference.conf` defaults, and the `NodeConfig` defaults) leaves both at `0`, which means the mitigation is disabled out of the box on every default-configured mainnet/fullnode/soliditynode deployment.

### Finding Description
In `RpcService.initServerBuilder()`: [1](#0-0) 
the RST_STREAM rate limiter is only applied `if (parameter.getRpcMaxRstStream() > 0 && parameter.getRpcSecondsPerWindow() > 0)`. The default field values are `0`: [2](#0-1) 
and the shipped `reference.conf` documents `0 = no limit` for both settings: [3](#0-2) 
The production `config.conf` template does not set these keys at all, so the compiled-in `0,0` defaults apply on any node started with the stock config: [4](#0-3) 

The only concurrency defense that is *always* active is `maxConcurrentCallsPerConnection` (default 100), enforced via `GrpcNettyMaxConcurrentStreamsLimiter`: [5](#0-4) 
This only caps the number of *simultaneously open* streams; it does not defend against the Rapid Reset technique, where a client opens a stream and immediately sends `RST_STREAM` before the server can either enforce back-pressure or complete the request, decrementing the active-stream count and freeing a slot to open the next stream instantly. This is precisely why grpc-java added the separate `maxRstFramesPerWindow` API as the dedicated CVE-2023-44487 countermeasure — a plain concurrent-stream cap is documented as insufficient against Rapid Reset because streams cycle far faster than the concurrency limit is ever exhausted for any measurable time. Because the repo ships that specific defense turned off by default, any anonymous TCP client that can reach the gRPC port can perform the classic Rapid Reset attack: open a connection, then repeatedly open a stream and immediately RST it, driving the server to spend CPU/thread-pool/allocation work per stream (header decode, interceptor chain entry via `RateLimiterInterceptor`/`RpcApiAccessInterceptor`/`LiteFnQueryGrpcInterceptor`, executor dispatch on `rpc-full-executor`) far faster than legitimate request throughput would allow, at effectively unlimited rate on a single connection.

### Impact Explanation
An unauthenticated network client with access to the gRPC endpoints (which are enabled by default per `RpcConfig` in `NodeConfig.java`) can exhaust the fixed-size gRPC executor thread pool (`ExecutorServiceManager.newFixedThreadPool` sized by `rpc.thread`) and CPU resources of a FullNode/SolidityNode/witness node, degrading or halting the node's ability to serve legitimate wallet/API/JSON-RPC/gRPC requests — a concrete denial-of-service against a production node, matching the "no longer serve API" impact criterion.

### Likelihood Explanation
High. The attack requires only a TCP connection and standard HTTP/2 frames (HEADERS immediately followed by RST_STREAM), no authentication, no special privileges, and no interaction with any other node. Because the dedicated defense (`maxRstFramesPerWindow`) ships disabled in every default configuration file in the repository (`config.conf`, `reference.conf`, and the compiled default in `NodeConfig`), essentially every stock java-tron deployment is exposed unless the operator manually sets `node.rpc.maxRstStream` and `node.rpc.secondsPerWindow` to positive values — which is not documented as a required hardening step for public nodes.

### Recommendation
Ship secure-by-default values for `node.rpc.maxRstStream` and `node.rpc.secondsPerWindow` (e.g., enable the limiter with sane defaults such as 20 resets per 10 seconds) instead of `0,0`, or change the `postProcess()` logic in `NodeConfig`/`Args` so that `0` no longer means "disabled" (mirroring the fix already applied to `maxConcurrentCallsPerConnection`, which no longer allows `0` to mean unlimited): [6](#0-5) 
Apply the analogous non-zero, secure default treatment to `rpc.maxRstStream`/`rpc.secondsPerWindow` in the `postProcess()` validation.

### Proof of Concept
1. Start a java-tron FullNode with stock `config.conf` (gRPC enabled on `50051`, default `maxRstStream`/`secondsPerWindow` = 0).
2. Open a raw HTTP/2 TCP connection to port 50051 (as done in the repo's own `RpcServiceHttp2SecurityTest`, using the same `CLIENT_PREFACE`/`SETTINGS`/`HEADERS` frame construction helpers).
3. In a tight loop, send a `HEADERS` frame opening a new stream ID immediately followed by an `RST_STREAM` frame for that same stream ID, before waiting for any server response — repeating thousands of times per second on the same connection (and across many connections/IPs for amplification).
4. Because `maxRstFramesPerWindow` is never called (guard at `RpcService.java:111` never true with default `0,0` config), grpc-netty applies no rate limiting on RST_STREAM frequency; only the `maxConcurrentCallsPerConnection` limit (100) applies, which does not throttle streams that are opened-and-reset far faster than they can be processed. Observe CPU and executor thread-pool (`rpc-full-executor`) utilization climb while legitimate gRPC calls (`GetAccount`, `BroadcastTransaction`, etc.) latency/availability degrades.
