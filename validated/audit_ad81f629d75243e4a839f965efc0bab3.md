### Title
Unprivileged Zero-Amount Confidential Transfers Exhaust Recipient's `transfers_received` Counter, Permanently Blocking Deposits and Incoming Transfers - (`aptos-move/framework/aptos-framework/sources/confidential_asset/confidential_asset.move`)

---

### Summary

`confidential_transfer` unconditionally increments the **recipient's** `transfers_received` counter for every incoming transfer, including zero-amount ones. Any registered user can send 65,536 zero-amount confidential transfers to a victim at gas-only cost (no token expenditure), saturating the victim's counter at `MAX_TRANSFERS_BEFORE_ROLLOVER`. Once saturated, the victim's own `deposit` and all further incoming `confidential_transfer` calls revert with `E_PENDING_BALANCE_MUST_BE_ROLLED_OVER`. The attacker can repeat the attack after every victim rollover, creating a persistent, low-cost denial-of-service over the victim's confidential asset operations.

---

### Finding Description

`confidential_asset.move` maintains a per-`(user, asset_type)` counter `transfers_received` inside `ConfidentialStore` to bound the cryptographic error that accumulates in the pending balance across multiple incoming transfers. [1](#0-0) 

The `deposit` entry function explicitly rejects zero-amount calls to avoid pointlessly incrementing this counter: [2](#0-1) [3](#0-2) 

However, `confidential_transfer` has **no equivalent guard**. It unconditionally increments the recipient's counter and then asserts the limit: [4](#0-3) 

The ZK transfer relation (`R^-_txfer`) proves only that the transferred amount `v` lies in `[0, 2^64)` and that the sender's balance equation holds. `v = 0` satisfies both constraints: the range proof is valid, and `new_balance = old_balance - 0 = old_balance`. The contract never inspects the plaintext amount; it is fully encrypted. Therefore a valid `TransferProof` for `v = 0` is accepted by `assert_valid_transfer_proof`.

When the attacker submits a zero-amount transfer, their own `available_balance` ciphertext is updated to `compressed_new_balance`. If the attacker chooses `new_balance = old_balance` (same ciphertext, same randomness), the on-chain state after the transfer is **identical** to before, making the same proof replayable for the next transaction. Even without replay, the attacker spends no tokens — only gas — for each of the 65,536 required transactions.

Once `transfers_received` reaches `MAX_TRANSFERS_BEFORE_ROLLOVER = 65536`, both paths that increment the counter abort:

- **`confidential_transfer` to victim** — line 650–653 reverts.
- **Victim's own `deposit`** — line 482–485 reverts. [5](#0-4) 

The victim can recover only by calling `rollover_pending_balance`, which resets `transfers_received` to 0: [6](#0-5) 

But `rollover_pending_balance` requires `ca_store.normalized == true`: [7](#0-6) 

`normalized` is set to `false` after every rollover and restored to `true` only by `withdraw_to` (normalize or withdraw): [8](#0-7) 

If the victim has already rolled over once (so `normalized = false`) and the attacker immediately re-saturates the counter, the victim must first call `normalize_raw` (which requires a fresh ZK proof over their available balance) before they can rollover again. The attacker can repeat the saturation after every recovery cycle.

---

### Impact Explanation

- **Victim's `deposit` is blocked**: the victim cannot move public fungible assets into their confidential balance.
- **All incoming confidential transfers to the victim are blocked**: legitimate senders receive `E_PENDING_BALANCE_MUST_BE_ROLLED_OVER` when trying to pay the victim.
- **Persistent DoS**: the attacker can re-saturate the counter after every victim rollover, forcing the victim into a continuous normalize → rollover cycle and preventing normal use of their confidential balance.
- **No token loss by attacker**: zero-amount transfers consume only gas; the attacker's confidential balance is unchanged.

This constitutes a material user-funds availability impact: the victim's confidential assets are inaccessible for deposits and receipts for as long as the attacker sustains the attack.

---

### Likelihood Explanation

- Any account that has registered a `ConfidentialStore` for the target asset type can execute the attack.
- Registration is permissionless (anyone can call `register_raw`).
- The attack requires 65,536 transactions at Aptos gas prices (~0.001 APT each ≈ 65 APT total), which is affordable for a motivated attacker.
- If the zero-amount proof is replayable (sender's ciphertext unchanged), the off-chain cost is a single ZK proof generation; otherwise 65,536 proofs are needed, which is still feasible.
- The victim has no on-chain way to prevent the attack other than pre-emptively pausing incoming transfers (`set_incoming_transfers_paused`), which also blocks legitimate receipts and their own deposits.

---

### Recommendation

Add a non-zero amount check in `confidential_transfer`, mirroring the guard already present in `deposit`. Since the amount is encrypted, the check must be applied to the **decrypted** amount returned by `assert_valid_transfer_proof` (which already decompresses and returns the plaintext `amount` as a `Balance<Pending>` value):

```diff
// Update recipient's confidential store
let recip_ca_store = borrow_confidential_store_mut(to, asset_type);
+assert!(!amount.is_zero(), error::invalid_argument(E_POINTLESSLY_DEPOSITING_ZERO));
let new_pending_balance = add_assign_pending(&mut recip_ca_store.pending_balance, &amount);
recip_ca_store.transfers_received += 1;
```

Alternatively, enforce a minimum transfer amount at the proof-verification layer, or add a rate-limit / cooldown on how many transfers a single sender can direct to a single recipient per epoch.

### Proof of Concept

**Setup:**
- Alice registers a `ConfidentialStore` for asset type `T` and deposits 1,000 tokens.
- Attacker registers a `ConfidentialStore` for `T` (no tokens needed).

**Attack:**
1. Attacker generates a `TransferProof` for `v = 0` (zero amount), with `new_balance = old_balance` (same ciphertext).
2. Attacker submits `confidential_transfer_raw(attacker, T, alice_addr, proof, memo=[])` 65,536 times. Each call:
   - Passes `assert_valid_transfer_proof` (v=0 is in range, balance equation holds).
   - Increments `alice_ca_store.transfers_received`.
   - Attacker's balance ciphertext is unchanged → same proof is valid next iteration.
3. After 65,536 calls, `alice_ca_store.transfers_received == 65536`.

**Result:**
- Alice calls `deposit(alice, T, 100)` → **aborts** with `E_PENDING_BALANCE_MUST_BE_ROLLED_OVER`.
- Bob calls `confidential_transfer(bob, T, alice_addr, proof, [])` → **aborts** with `E_PENDING_BALANCE_MUST_BE_ROLLED_OVER`.
- Alice must call `rollover_pending_balance` (and possibly `normalize_raw` first if `normalized == false`) to recover.
- Attacker immediately re-saturates the counter after Alice's rollover.

**Key code references:**

`confidential_transfer` increments recipient counter without zero-amount guard: [9](#0-8) 

`deposit` has the guard that `confidential_transfer` is missing: [3](#0-2) 

`MAX_TRANSFERS_BEFORE_ROLLOVER` constant: [1](#0-0) 

`rollover_pending_balance` requires `normalized == true` before it can reset the counter: [10](#0-9)
