### Title
Trust-on-first-record poisoning of `module_ctx.facts` lets an attacker permanently pin malicious artifact hashes into `MODULE.bazel.lock` - ([File: src/test/py/bazel/bzlmod/bazel_lockfile_test.py])

### Summary
Bazel's module-extension `facts` mechanism is a direct analog of the SphereX "recording phase" bug. Extension authors are explicitly told to use `facts` to persist "immutable" data fetched from the network *when no checksum is available to guard the download*, precisely so that future evaluations can skip the network fetch and trust the recorded value forever. Whatever a hostile origin serves during the first (recording) evaluation of the extension becomes a permanently trusted "fact" in `MODULE.bazel.lock`/the hidden lockfile, is never re-verified, and — unlike code changes to the extension — is **not** invalidated automatically, so it silently continues to be reused across all future builds and machines that inherit that lockfile.

### Finding Description
The documented `extension_metadata(facts=...)` / `module_ctx.facts` feature is designed for extensions that fetch data over the network without a checksum guard and want to memoize it as if it were an immutable, verified value: [1](#0-0) 

The `facts` docs explicitly recommend the pattern of recording "a mapping from version numbers of some SDK to the ... download URL and checksum of that version. The first time the extension is evaluated, it can fetch this mapping from the network, but on later evaluations it can use the mapping from `facts` to avoid the network requests" [2](#0-1) . Critically, "facts are not invalidated even when the code of your module extension changes" [3](#0-2) , and the `module_ctx.facts` API doc confirms these are meant to "preserve universally true facts such as the hashes of artifacts in an immutable repository" [4](#0-3) .

The actual runtime behavior matches this design: whatever dict the extension returns as `facts` during an evaluation is persisted verbatim into the lockfile and handed back unchanged (`ctx.facts[key]`) to future evaluations, with no host-side integrity check on the values, as demonstrated by `testFactsInReproducibleExtension`, where the fact `{"hash": resource_name[::-1]}` computed on the first run is reused on every subsequent run without re-fetching [5](#0-4) . Facts also outlive `bazel clean --expunge` and full lockfile deletion because of the "hidden lockfile" cache in the output base, and are only invalidated by an explicit change to the extension's `facts_version` [6](#0-5) . Bazel also explicitly re-adopts externally-supplied fact edits during `--lockfile_mode=update` without re-running the extension or validating them: `testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension` shows a manually injected fact entry surviving into the lockfile untouched [7](#0-6) .

This exactly mirrors the SphereX "recording phase" bug class: an attacker who controls (even temporarily) the origin server, registry, or mirror that a module extension queries during its *first* evaluation can plant a malicious value (e.g., a URL/sha256 pair for a "pinned" artifact) that gets baked into `facts` and is thereafter trusted as ground truth — surviving lockfile regeneration, `bazel clean --expunge`, and even code changes to the extension — with no mechanism analogous to a checksum re-verification to catch the swap later.

### Impact Explanation
If a module extension's `facts` value encodes something security-relevant (a hash later fed as the `sha256`/`integrity` value of an `http_archive`/`http_file` download, a pinned artifact URL, etc.), an attacker who can influence the content served during the extension's first ("recording") evaluation — e.g., by controlling a dependency's download endpoint, a compromised mirror, or a malicious release artifact at the moment a CI machine first runs `bazel mod deps --lockfile_mode=update` — can get that attacker-chosen value permanently pinned into every downstream consumer's `MODULE.bazel.lock`. Because facts are exempt from re-verification and outlive extension code changes, the poisoned fact continues to be trusted (and, depending on how the extension uses it, could be used to fetch/trust attacker content) even after the attacker no longer controls the origin, until someone manually notices and bumps `facts_version`.

### Likelihood Explanation
Requires the attacker to control (even briefly) content fetched by a module extension during a lockfile-updating build — realistic for extensions that resolve "latest" metadata/artifacts from mutable, attacker-influenceable sources (e.g., an index or release feed) before the maintainer pins a version. This is squarely the class of unprivileged, remote-content-only attacker described by the report: no access to the victim's machine or credentials is needed, only the ability to serve or publish the content that a not-yet-hardened extension is fetching during that first "recording" run.

### Recommendation
Treat any extension-supplied `facts` that encode content-addressed trust decisions (hashes/checksums/URLs to be used for later unverified downloads) with the same scrutiny as a lockfile hash: require an explicit, out-of-band mechanism (e.g., mandatory checksum-of-checksum pinning, `facts_version` bump reviews, or a `bazel mod deps --lockfile_mode=error` gate) before facts are trusted in CI/production, and document loudly that `facts` values are never re-validated against their origin and thus should not be used to bypass integrity checks on subsequent downloads without a secondary verification step.

### Proof of Concept
1. Author a module extension whose implementation fetches a "latest artifact hash" from an attacker-influenceable network source and stores it via `ctx.extension_metadata(facts={...})`, mirroring `testFactsInReproducibleExtension`'s `_fetch_metadata` pattern [8](#0-7) .
2. On the first `bazel build`/`bazel mod deps --lockfile_mode=update` run (the "recording phase"), have the attacker-controlled source return a malicious hash/URL pair; this gets written into `facts` in `MODULE.bazel.lock`.
3. Revert the network source to benign content (removing attacker control) and confirm, as in `testFactsInReproducibleExtension`, that subsequent builds — even after deleting `MODULE.bazel.lock`, running `bazel shutdown`, or `bazel clean --expunge` — never re-fetch and continue to reuse the poisoned fact [9](#0-8) .
4. Show the poisoned fact is only removed by an explicit `facts_version` bump by the extension author, not by any integrity re-check [6](#0-5) .

                '        fail("ctx.facts.get() and ctx.facts disagree on'

            '    if resource_name in ctx.facts:',
            '        return ctx.facts[resource_name]',
            '    print("Fetching metadata for {}...".format(resource_name))',
            '    return {"hash": resource_name[::-1]}',
            'def _mod_ext_impl(ctx):',
            '    print("Hello from the other side!")',
            '    metadata = {}',

            '        metadata[repo] = _fetch_metadata(ctx, repo)',

  def testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension(
      self,
  ):
    """UPDATE mode keeps updated facts of a non-reproducible extension.

    The hidden lockfile records the facts produced by the most recent local
    evaluation of the extension. If the workspace lockfile's facts for a
    non-reproducible extension change without any of its inputs changing (e.g.
    a branch switch or pull brings in a re-pin performed on another machine),
    the cached result must be reused with the new facts as is: a cold machine
    would not rerun the extension either and a rerun could require network
    access or credentials that are only available to the person updating the
    pins.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=False)
    self._addFactToLockfile(extension_id, '1.27.0', {'hash': 'hola'})

    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all', '--lockfile_mode=update']
    )
    self.assertNotIn('lockfile_ext is being evaluated', '\n'.join(stderr))

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {
            '1.25.0': {'hash': 'olleh'},
            '1.26.1': {'hash': 'hello'},
            '1.27.0': {'hash': 'hola'},
        },
    )
