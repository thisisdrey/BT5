### Title
Missing ciphertext length validation before native libsodium AEAD decrypt call in shielded-note decryption — ([File: framework/src/main/java/org/tron/core/zen/note/NoteEncryption.java])

### Summary
`NoteEncryption.Encryption.attemptEncDecryption` passes an attacker-influenced `ciphertext` byte array directly into the native/JNI call `JLibsodium.cryptoAeadChacha20poly1305IetfDecrypt`, using a hard-coded fixed length constant `ZC_ENCCIPHERTEXT_SIZE` instead of validating that the actual array is at least that long. This is the same bug class as the reported Swift-Crypto X-Wing issue: a fixed-size length is asserted to a native/FFI boundary while the actual buffer that backs it can be shorter, letting native code read past the end of the Java-managed array.

### Finding Description
`attemptEncDecryption(byte[] ciphertext, byte[] ivk, byte[] epk)` allocates a fixed 580-byte output buffer but calls the native decrypt routine with the *input* `ciphertext` parameter and the constant `ZC_ENCCIPHERTEXT_SIZE`, without first checking `ciphertext.length`: [1](#0-0) 

The sibling overload has the identical pattern: [2](#0-1) 

`JLibsodium.cryptoAeadChacha20poly1305IetfDecrypt` is a JNI wrapper into the native libsodium C library; unlike `System.arraycopy`, JNI's array access does not bounds-check the passed length against the actual array size — the native code trusts the supplied length parameter (`ZC_ENCCIPHERTEXT_SIZE`) and will read that many bytes from whatever memory the JNI pointer refers to.

This is reachable with attacker-controlled bytes via `Note.decrypt(byte[] ciphertext, byte[] ivk, byte[] epk, byte[] cmu)`: [3](#0-2) 

which is invoked from the Wallet gRPC/HTTP scan APIs using the raw, unpadded protobuf field bytes straight from an on-chain `ReceiveDescription.c_enc`: [4](#0-3) [5](#0-4) 

`r.getCEnc().toByteArray()` is a plain protobuf `bytes` field with no compile-time size constraint; unlike the `logData`-derived path (`getNoteTxFromLogListByIvk/Ovk`, which uses `ByteArray.subArray`, effectively `Arrays.copyOfRange`, that zero-pads/truncates to a fixed length and is therefore safe), this direct `toByteArray()` call preserves whatever length was placed into the `c_enc` field of the `ShieldedTransferContract`'s `ReceiveDescription` when the transaction was broadcast. If the actuator that validates `ShieldedTransferContract`/`ShieldedTransferContract` receive descriptions does not itself enforce `c_enc.length == ZC_ENCCIPHERTEXT_SIZE` before the record is committed to a block, a short `c_enc` can persist on-chain and later trigger the native OOB read the first time any node calls `scanNoteByIvk`/`scanNoteByOvk`.

Notably, this exact class of check is present elsewhere in the same file for the burn-message decrypt path — showing this is the pattern the codebase already recognizes as necessary but omitted here: [6](#0-5) 

### Impact Explanation
An out-of-bounds native read triggered from Java-managed memory through JNI can crash the node process (denial of service) or, depending on what adjacent heap memory libsodium's AEAD-decrypt loop touches, leak adjacent process memory contents into the returned/attempted plaintext, which could then be surfaced to an API caller. Either outcome (node crash or memory disclosure) matches an accepted impact category for this program (node crash/halt or key/memory disclosure).

### Likelihood Explanation
Reaching this requires (a) getting a malformed (short) `c_enc` value into an on-chain `ReceiveDescription`, which depends on whether `ShieldedTransferActuator`/`ShieldedTRC20` code paths strictly enforce the exact byte length of `c_enc` before acceptance — this was not directly confirmed within the scope of this investigation and constitutes a real uncertainty; and (b) any node/wallet operator invoking `scanNoteByIvk`/`scanNoteByOvk` (standard shielded-wallet functionality) over the block range containing the malformed record. Because the two conditions are outside a single attacker-controlled request, and because it is unverified whether an upstream size check already prevents the short `c_enc` from being persisted, this should be treated as **Medium** likelihood pending confirmation of actuator-side validation, though the missing defensive length check at the FFI boundary itself is a definite code defect regardless.

### Recommendation
Add an explicit length check (`ciphertext.length != ZC_ENCCIPHERTEXT_SIZE` → return `Optional.empty()`) at the top of both `attemptEncDecryption` overloads in `NoteEncryption.java`, mirroring the pattern already used in `decryptBurnMessageByOvk`. Independently, verify and, if missing, add a strict length check on `ReceiveDescription.c_enc` (and other Sapling/TRC20 shielded proto byte fields) in the relevant actuator `validate()` methods so malformed records can never be persisted on-chain in the first place.

### Proof of Concept
Not independently constructed/executed in this analysis (ask-only mode, no code execution). Conceptually: craft a `ShieldedTransferContract` (or induce a `ShieldedTRC20` receive record) whose `ReceiveDescription.c_enc` is shorter than 580 bytes; if actuator validation does not reject it, once mined, any subsequent call to `Wallet.scanNoteByIvk`/`scanNoteByOvk` for the block range decrypts the record via `Note.decrypt` → `NoteEncryption.Encryption.attemptEncDecryption`, invoking `JLibsodium.cryptoAeadChacha20poly1305IetfDecrypt` with the undersized array and the fixed `ZC_ENCCIPHERTEXT_SIZE` length, analogous to the X-Wing PoC that passed a 1-byte buffer where 1120 bytes were expected.

  public static Optional<Note> decrypt(
      byte[] ciphertext, byte[] ivk, byte[] epk, byte[] cmu) throws ZksnarkException {
    Optional<NoteEncryption.Encryption.EncPlaintext> pt =
        NoteEncryption.Encryption.attemptEncDecryption(ciphertext, ivk, epk);
    if (!pt.isPresent()) {
      return Optional.empty();
    }
    Note ret = decode(pt.get());
    byte[] pkD = new byte[32];
    if (!JLibrustzcash
        .librustzcashIvkToPkd(new IvkToPkdParams(ivk, ret.d.getData(), pkD))) {
      return Optional.empty();
    }
    byte[] cmuExpected = new byte[32];
    if (!JLibrustzcash.librustzcashComputeCm(
        new ComputeCmParams(ret.d.getData(), pkD, ret.value, ret.rcm, cmuExpected))) {
      return Optional.empty();
    }
    if (!Arrays.equals(cmu, cmuExpected)) {
      return Optional.empty();
    }
    return Optional.of(ret);
  }
