### No vulnerability found for this question.

**Analysis:** The behavior described is by design, not a bug in the authorization equality being audited. In `Engine::execute_signed_intent`, the only staleness bound *is* the signer's own `deadline` field, which the signer chooses when they sign [1](#0-0) . For legacy nonces, `verify_intent_nonce` short-circuits to `Ok(())` since `VersionedNonce::maybe_from` returns `None`, so no additional nonce-embedded deadline constraint applies [2](#0-1) .

However, this does not break the stated binding ("every balance change == one a valid signature authorized for that exact account and amount at time of execution"). The signature covers a `DefusePayload` whose intent (e.g. `TokenDiff`) already specifies exact, fixed token amounts and account — not a floating/oracle-derived price re-evaluated at execution time [3](#0-2) . Execution at any time before `deadline` credits/debits exactly the amounts the signer signed for that exact account — nothing more, nothing less. The signer's chosen `deadline` is precisely the mechanism intended to bound this window; a signer who fears price drift is expected to choose a short deadline, exactly as documented for versioned nonces where "the deadline for nonce may be greater than the deadline for intent" is explicitly called out as a known consideration [4](#0-3) .

Holding a validly-signed, fixed-amount payload and choosing when to broadcast it within its authorized deadline window is inherent to any offline-signed, fixed-terms intent/limit-order system (comparable to standard limit orders or maker quotes) — it is an economic/MEV consideration, not a signature-authorization violation, no `TokenId`/amount/account is altered from what was signed, and no balance changes without a matching signature. This matches the audit's exclusions for "theoretical findings with no demonstration" and issues not backed by a concrete equality violation — the signature-to-execution equality holds exactly as authorized both before and after any hypothetical intervening on-chain state change, since the payload's own numeric terms are immutable and not re-derived from live state.

    fn verify_intent_nonce(&self, nonce: Nonce, intent_deadline: Timestamp) -> Result<()> {
        let Some(nonce) = VersionedNonce::maybe_from(nonce) else {
            return Ok(());
        };

        match nonce {
            VersionedNonce::V1(SaltedNonce {
                salt,
                nonce: ExpirableNonce { deadline, .. },
            }) => {
                if !self.state.is_valid_salt(salt) {
                    return Err(DefuseError::InvalidSalt);
                }

                if intent_deadline > deadline {
                    return Err(DefuseError::DeadlineGreaterThanNonce);
                }

                if deadline < Timestamp::now() {
                    return Err(DefuseError::NonceExpired);
                }
            }
        }

        Ok(())
    }
