### Title
Unvalidated attacker-controlled array-length word causes uncaught OutOfMemoryError DoS in `BatchValidateSign`/`ValidateMultiSign` precompiles - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`extractBytesArray` and `extractBytes32Array` in `PrecompiledContracts.java` read a length field directly from attacker-supplied ABI-encoded call data and use it, without an upper-bound check, to allocate a `byte[][]` array before any validation of that count occurs. This mirrors the Tesseract bug class (an unvalidated numeric value taken from untrusted, attacker-crafted input, used unchecked to size/index a buffer, which is then acted on before any sanity check runs), except that in the JVM this manifests as memory-exhaustion (`OutOfMemoryError`) rather than a raw wild-address write.

### Finding Description
`extractBytes32Array` derives `len` straight from a `DataWord` supplied inside the precompile call data with no upper bound check: [1](#0-0) 
`extractBytesArray` similarly allocates `new byte[len][]` from `words[offset].intValueSafe()` before the loop even attempts to read further, and `extractSigArray` follows the identical pattern: [2](#0-1) [3](#0-2) 

`intValueSafe()` caps overflowed/negative encodings to `Integer.MAX_VALUE` rather than rejecting them: [4](#0-3) 

In `BatchValidateSign.doExecute`, the size bound check (`MAX_SIZE`) is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is enabled, and even then it is computed from a *separate* read of the same words that is not guaranteed to match the value ultimately consumed inside `extractBytesArray`/`extractBytes32Array`. When the feature flag is off (or on chains/paths where it has not activated), `extractBytesArray`/`extractBytes32Array` run completely unguarded: [5](#0-4) 

Critically, in `ValidateMultiSign.execute`, the call to `extractBytesArray`/`extractSigArray` happens **outside** the surrounding `try { ... } catch (Throwable t)` block that wraps the rest of the signature-verification logic: [6](#0-5) 
so an `OutOfMemoryError` thrown while allocating `new byte[len][]` for a huge attacker-chosen `len` (up to `Integer.MAX_VALUE`) propagates uncaught out of the precompile and up through TVM execution.

### Impact Explanation
Any account can broadcast a `TriggerSmartContract` that CALLs the `ValidateMultiSign`/`BatchValidateSign` precompiled contract addresses with crafted call data whose length word decodes to a very large value. This attempts to allocate a `byte[][]` array of up to ~2^31 references (many GB of heap for reference storage alone), triggering `OutOfMemoryError`. Because this precompile call is part of deterministic transaction execution, every full node validating the block reaches the identical code path and allocation, so this is not a single-node crash but a synchronized resource-exhaustion event across the network — potential node crash/instability for many nodes processing the same transaction, which fits the "node crash" impact category.

### Likelihood Explanation
Reachability is trivial: no special permission is required, only a normal signed `TriggerSmartContract` invoking the precompile address, which is a `PrecompiledContract` reachable via any CALL from any deployed contract. The size of the allocation is fully attacker-controlled via a single 32-byte word in the calldata.

### Recommendation
Add an explicit upper-bound check (e.g., against `MAX_SIZE`) on the length word immediately after reading it in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray`, before allocating the `byte[][]` array, regardless of `VMConfig.allowTvmSelfdestructRestriction()`. Additionally, wrap the array-extraction calls in `ValidateMultiSign.execute`/`BatchValidateSign.doExecute` within the existing `try/catch` so any allocation failure is handled gracefully rather than propagating as an uncaught `Error`.

### Proof of Concept
1. Craft ABI-encoded calldata for `ValidateMultiSign` (or `BatchValidateSign`) where the word at the offset resolved via `words[3]` (`words[1]`/`words[2]` for BatchValidateSign) — the "signature/address array length" — is set to a large value such as `0x7FFFFFFF` (2,147,483,647), while `VMConfig.allowTvmSelfdestructRestriction()` is not yet active for the check that gates `extractSigArray`.
2. Deploy/trigger a contract that performs a `CALL`/`STATICCALL` to the precompile address for `ValidateMultiSign` with this calldata.
3. `extractBytesArray`/`extractBytes32Array` executes `new byte[2147483647][]` outside the protective `try/catch`, causing `OutOfMemoryError` to propagate out of TVM execution for every node processing the transaction/block.

    int len = words[offset].intValueSafe();

    }
