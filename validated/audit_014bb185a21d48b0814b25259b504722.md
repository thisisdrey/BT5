### Title
`resolve_promise_yield_timeouts` auto-fires stale `PromiseYield` receipts against a deleted-and-recreated account, executing attacker-controlled actions against the recreated account's balance - ([File: runtime/runtime/src/lib.rs])

### Summary
`remove_account` in `core/store/src/utils/mod.rs` deletes an account's `Account`, `ContractCode`, access-key, and `ContractData` trie entries on `DeleteAccount`, but does not remove any `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::PromiseYieldTimeout`, or `TrieKey::YieldIdToDataId`/`DataIdToYieldId` entries associated with that account. Consequently, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3116`) can still find `contains_key(&promise_yield_key, ...)` true (`lib.rs:3051`) after the account is deleted and later recreated, auto-firing a synthetic `PromiseResume(data: None)` receipt (predecessor=receiver=the account id) that resumes the stale yield callback recorded at yield-creation time.

### Finding Description
1. `promise_yield_create` (`runtime/near-vm-runner/src/logic/logic.rs:3660`) creates a `PromiseYield` action receipt whose `receiver_id` is the *same* account (self-callback), with a data dependency `data_id`. When this receipt is processed, `lib.rs:1495-1499` stores it verbatim via `set_promise_yield_receipt` at `TrieKey::PromiseYieldReceipt { receiver_id, data_id }` — this stored `Receipt` carries whatever `actions` the developer batched onto that promise index (function calls, transfers, etc., via `promise_batch_action_*`). A corresponding `PromiseYieldTimeout { account_id, data_id, expires_at }` entry is enqueued (`function_call.rs:160-169`, `core/store/src/utils/mod.rs:182-198`).
2. The account then executes `DeleteAccount`, which calls `remove_account` (`runtime/runtime/src/actions.rs`, delegating to `core/store/src/utils/mod.rs:505-575`). This function only removes `TrieKey::Account`, `TrieKey::ContractCode`, access keys/gas-key nonces, and `TrieKey::ContractData` entries — it never touches `PromiseYieldReceipt`, `PromiseYieldStatus`, or the pending `PromiseYieldTimeout` queue entry for that account.
3. A third party recreates the same `account_id` (NEAR permits recreation of a deleted account id) and funds it via `CreateAccount` + `Transfer`.
4. When `apply_state.block_height` reaches `queue_entry.expires_at`, `resolve_promise_yield_timeouts` pops the still-pending `PromiseYieldTimeout` entry (`lib.rs:3030-3044`), checks `state_update.contains_key(&promise_yield_key, ...)` (`lib.rs:3051`) — which is still `true` because the stale `PromiseYieldReceipt` was never cleaned up — and synthesizes a `PromiseResume(data: None)` receipt targeting the (recreated) account (`lib.rs:3060-3068`). This receipt is delivered with no attacker transaction executed after recreation; it is entirely timeout-driven.
5. On delivery, the `PromiseResume` handling path (`lib.rs:1500-1560`) retrieves and executes the stored stale `yield_receipt`'s actions against the current account state — i.e., whatever `Transfer`/`FunctionCall` actions were batched into the original `PromiseYield` receipt now run using the account's current (attacker-unrelated, victim-funded) balance.

I could not fully verify within the available context two supporting details that materially affect exploitability and would need direct-code confirmation (the tool-call budget for this task was exhausted before I could inspect them):
- Whether `promise_batch_action_transfer`/other batch actions can actually be appended to the promise index returned by `promise_yield_create`/`promise_yield_create_with_id` (I found the create functions and the generic `append_action_transfer` family separately but did not confirm they compose on the same receipt index, i.e., that a `Transfer` action can actually ride along in the same `PromiseYield` receipt as the callback function call).
- Whether `action_create_account`/`action_delete_account` (in `runtime/runtime/src/actions.rs`) contain any check against pending `PromiseYieldTimeout`/`PromiseYieldReceipt`/`YieldIdToDataId` entries that would block deletion or recreation (I located the function names but did not read their bodies).

### Impact Explanation
If confirmed, this would allow theft of freshly-deposited victim funds via a purely timeout-triggered receipt with no authorizing transaction after account recreation — matching the "theft of user funds" bounty category, since a stale receipt executes against balance the attacker never owned and the victim never authorized to move.

### Likelihood Explanation
Preconditions require: (a) confirmation that arbitrary value-transferring actions can be attached to a `PromiseYield` receipt, (b) the account is fully deleted (zero balance, satisfying delete-account's requirements), (c) a third party independently chooses to recreate and fund the exact same account id before `yield_timeout_length_in_blocks` elapses, and (d) no cleanup path (in `action_create_account` or elsewhere) purges leftover yield state at creation time. Precondition (c) — a victim independently choosing to recreate and fund an attacker's deleted account name — is not something the attacker can force; it requires a specific real-world circumstance (e.g., users reusing/recycling account names), and I was unable to verify whether `action_create_account` blocks creation when stale yield state exists for that id.

### Recommendation
Have `remove_account` (`core/store/src/utils/mod.rs:505-575`) also purge any pending `PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout` queue entries, and `YieldIdToDataId`/`DataIdToYieldId` mappings for the account being deleted (or alternatively, have `resolve_promise_yield_timeouts`/the `PromiseResume` handler cross-check that the account still exists and matches the state at yield-creation time before executing stale actions), and/or block `DeleteAccount` while such pending yield state exists for the account.

### Proof of Concept
Integration test plan (runtime apply-path, e.g. in `runtime/runtime/src/tests/apply.rs` alongside existing `resolve_promise_yield_timeouts` tests):
1. Deploy a contract to account `A` that calls `promise_yield_create` and batches a `Transfer(amount, attacker)` (or equivalent value-moving) action onto the returned promise index, without ever calling `promise_yield_resume`.
2. Submit `DeleteAccount { beneficiary: attacker }` for `A` in a subsequent block, verifying `A`'s `Account` trie entry is gone but the `PromiseYieldReceipt`/`PromiseYieldTimeout` entries persist (assert via `get_promise_yield_receipt`/direct trie lookup).
3. Recreate `A` via `CreateAccount` + `Transfer(victim_deposit)` from an unrelated account (simulating the victim), in a block before `expires_at`.
4. Advance `block_height` past `yield_timeout_length_in_blocks` and process a chunk with no further receipts, calling `resolve_promise_yield_timeouts`.
5. Assert: a `PromiseResume` receipt is generated and executed carrying the stale `Transfer` action, and that the recreated account's balance is reduced by `amount` with the destination (attacker) balance increased — with no transaction/receipt other than the timeout mechanism authorizing this transfer after step 3.
