### Title
Unbounded attachment `content` size accepted from peer response, bypassing `ATTACHMENTS_MAX_SIZE_MIN` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`GetAttachmentResponse`'s `Deserialize` impl hex-decodes the peer-supplied `content` field with no length check, and `AttachmentsBatchStateContext::extend_with_attachments` inserts the resulting `Attachment` unconditionally. `ATTACHMENTS_MAX_SIZE_MIN` is defined but never referenced outside `stackslib/src/net/atlas/mod.rs`, so no code path actually enforces the size bound against attacker-controlled content before it is queued for storage.

### Finding Description
The claimed equality (`bytes in content <= ATTACHMENTS_MAX_SIZE_MIN`) is broken: `ATTACHMENTS_MAX_SIZE_MIN` is only used inside `stackslib/src/net/atlas/mod.rs` (confirmed via repo-wide search returning matches solely in that file), meaning it is set as a default constant but not checked against any attacker-supplied buffer length anywhere in the download path.

The exploit path:
1. `StacksHttpResponse::decode_atlas_get_attachment` (`stackslib/src/net/api/getattachment.rs:159-165`) parses the JSON body and calls `serde_json::from_value::<GetAttachmentResponse>`.
2. `GetAttachmentResponse::deserialize` (`stackslib/src/net/atlas/mod.rs:69-77`) reads the string, hex-decodes it via `hex_bytes`, and constructs `Attachment::new(bytes)` with **no length check at all**.
3. `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`), specifically lines 547-548, takes the successfully-decoded response and does `self.attachments.insert(response.attachment)` — again with no size comparison against `AtlasConfig.attachments_max_size` or `ATTACHMENTS_MAX_SIZE_MIN`.

A malicious peer serving `/v2/attachments/{hash}` can return a hex-encoded `content` blob many times larger than 1 MiB. As long as it decodes as valid hex JSON, it passes through both the response-parsing stage and the batch-extension stage unbounded, and is queued into `self.attachments` for eventual persistence.

### Impact Explanation
A single crafted HTTP response from a remote peer inflates the requesting node's Atlas attachment set/storage with an oversized blob that was never validated against the configured 1 MiB cap. This is repeatable per-attachment-hash across multiple requests/peers the node syncs from, and requires no privileged role — any peer the node contacts for attachment inventory/data download can serve this. This does not require breaking the hash-consistency of the attachment (the hash is a Hash160 of the `content`, so if computed/matched, the finding purely concerns unconstrained size, not integrity).

### Likelihood Explanation
- Preconditions: the node must be actively downloading Atlas attachments (this happens by default whenever `AtlasConfig` attachment instances are tracked, e.g., via BNS-related contract activity).
- Attacker cost: trivial — run/be a normal peer, respond to a `/v2/attachments/{hash}` GET with an oversized hex payload.
- Remote reachability: yes, this is a standard RPC/P2P download flow the requesting node initiates against a peer it already communicates with; no secret or privileged role needed.
- Repeatability: high — repeatable per attachment hash and across multiple sync cycles.

### Recommendation
Enforce a maximum content length in `GetAttachmentResponse::deserialize` (`stackslib/src/net/atlas/mod.rs`) before allocating the decoded `Vec<u8>`, rejecting hex payloads whose length exceeds `AtlasConfig.attachments_max_size` (or `ATTACHMENTS_MAX_SIZE_MIN` as an absolute ceiling). Additionally, add an explicit size check in `AttachmentsBatchStateContext::extend_with_attachments` before `self.attachments.insert(...)` (`stackslib/src/net/atlas/download.rs:547-548`), rejecting/penalizing peers that violate the bound (treat as `bump_failed_requests()` rather than success).

### Proof of Concept
Add a net test in `stackslib/src/net/atlas/tests.rs`:
1. Construct a `GetAttachmentResponse` whose `attachment.content` is a `Vec<u8>` of length `ATTACHMENTS_MAX_SIZE_MIN as usize * 4` (e.g. 4 MiB), filled with arbitrary bytes.
2. Serialize it to the hex-encoded JSON string as the real HTTP handler would (`to_hex`), then feed it through `StacksHttpResponse::decode_atlas_get_attachment` and assert it returns `Ok(...)` with `response.attachment.content.len() > ATTACHMENTS_MAX_SIZE_MIN as usize` (showing no rejection at decode time).
3. Wrap this into a `BatchedRequestsResult<AttachmentRequest>::succeeded` map and call `AttachmentsBatchStateContext::extend_with_attachments`, then assert `self.attachments` contains the oversized attachment — confirming no size check exists at `download.rs:547-548` before it would be handed to `AtlasDB` for persistence.     pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
