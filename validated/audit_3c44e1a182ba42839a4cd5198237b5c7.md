### Title
Reward index initialization miscalculation lets any user accrue `balance * 1e18` rewards in a single call - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta()` contains an off-by-one-style initialization error in the account-index fallback: when an account's stored `accountIndexOf` is `0`, the code resets it to `INITIAL_INDEX` only if the global token index is *strictly greater* than `INITIAL_INDEX`. When the global index still equals `INITIAL_INDEX` exactly (the window between a governor enabling a reward speed on a new token and the first timestamp delta where the index grows), `_accountIndex` remains `0`, so `_deltaIndex = _tokenIndex - 0 = 1e18` and the account is credited `balanceOf(account) * 1e18` reward units. This mirrors the bug class of CVE-2023-42753: a missing/incorrect offset term causes a miscalculation of the effective index, producing an out-of-range increment of an accounting entry. `updateBeforeMintOrBurn()` is permissionless, so any unprivileged EOA can trigger the accrual for their own account.

### Finding Description
In `RewardsDistributor._calculateTokenDelta()` (contracts/RewardsDistributor.sol:217-231):

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The fallback is meant to give a first-time account a sane starting index, but it only applies when `_tokenIndex > INITIAL_INDEX`. When `tokenStates[token_].index == INITIAL_INDEX` — which is exactly the state created by `_updateTokenSpeed()` for a newly added reward token (contracts/RewardsDistributor.sol:296-299: `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp...})`) — the condition `_tokenIndex > INITIAL_INDEX` is false, `_accountIndex` stays `0`, and `_deltaIndex = 1e18 - 0 = 1e18`.

`_updateTokenIndex()` only advances the index when `block.timestamp > tokenStates[token_].timestamp` and `speed > 0` (contracts/RewardsDistributor.sol:197-212). Therefore, in the block where a new token's speed is activated (and in any later block until the index first grows — i.e., while `timestamp` equality holds), every account with `accountIndexOf == 0` that passes through `_updateTokensAccruedOf()` is credited `balance * 1e18` reward units instead of `0`.

Reachability for an unprivileged attacker:
- `updateBeforeMintOrBurn(IERC20 token_, address account_)` is external and explicitly documented as callable by anyone (contracts/RewardsDistributor.sol:173-180). It requires only `tokenStates[token_].index > 0`, which is true the moment the speed is set.
- `claimRewards(address[], IERC20[])` is public and pays out `tokensAccruedOf[account_]` via `_transferRewardIfEnoughTokens` (contracts/RewardsDistributor.sol:150-168, 248-256). It is `nonReentrant` but that does not prevent the exploit, which needs no reentrancy.
- The attacker controls `balanceOf(account_)` by depositing a dust amount of underlying to receive DepositToken (or borrowing dust to hold DebtToken), letting them tune the inflated accrual to be `<=` the distributor's reward token balance.

### Impact Explanation
A first-time account gets `tokensAccruedOf[account] += balanceOf(account) * 1e18`. By sizing the DepositToken/DebtToken balance such that `balance * 1e18 <= rewardToken.balanceOf(distributor)` (e.g., ~1 unit of token balance per 1e18 reward units held), the attacker can claim essentially the entire reward token balance of the distributor in one `claimRewards` call. This is direct theft of all users' unclaimed yield — an accepted impact category. Solvency of the reward pool is broken: legitimate users' accrued rewards are stolen.

### Likelihood Explanation
- Requires the reward token index to be exactly `INITIAL_INDEX`, which happens in the same block in which a governor's `updateTokenSpeed`/`updateTokenSpeeds` first enables a speed on a new token, or in any block before the stored timestamp is surpassed — the attacker can back-run the governor transaction in the same block (front-running/sandwiching is in scope) or act immediately since `_deltaTimestamps` must be `0`. The window is narrow but deterministic on a fork.
- Alternatively, if a token's speed is set to a nonzero value and the index is later reset/re-added, the same state recurs each time `index == INITIAL_INDEX` at the moment of the call.
- No privileged attacker, oracle manipulation, or malicious infrastructure is needed: `updateBeforeMintOrBurn` and `claimRewards` are public, and the attacker supplies only their own dust balance.
- Requires the distributor to hold reward tokens (true whenever rewards are being distributed), and the token must be a registered DepositToken or DebtToken (`onlyIfTokenExists` is applied inside `_updateTokenSpeed`, not on the permissionless accrual path).

### Recommendation
Initialize the account index to the current token index (not `INITIAL_INDEX`) whenever `accountIndexOf[token_][account_] == 0`, regardless of the global index value:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex;
}
```

This both fixes the `== INITIAL_INDEX` hole and prevents new accounts from retroactively accruing rewards from before they entered (the current fallback to `INITIAL_INDEX` already over-credits users who first interact after the index has grown). Add a regression test that calls `updateBeforeMintOrBurn` in the same block as `updateTokenSpeed` for a new token and asserts `_tokensDelta == 0`.

### Proof of Concept
Hardhat-style fork test sketch:

```ts
// Setup: pool, depositToken (msToken), rewardsDistributor with rewardToken funded.
// 1. Attacker deposits dust to obtain depositToken balance:
await underlying.connect(attacker).approve(pool.address, dust);
await pool.connect(attacker).deposit(depositToken.address, dust); // attacker holds depositToken

// 2. Governor enables speed on a NEW token for the first time (index becomes INITIAL_INDEX, timestamp = now):
await distributor.connect(governor).updateTokenSpeed(depositToken.address, speed);

// 3. Same block: attacker triggers accrual for themself via the permissionless hook:
await distributor.connect(attacker).updateBeforeMintOrBurn(depositToken.address, attacker.address);

// tokenStates.index == INITIAL_INDEX, accountIndexOf == 0 => _deltaIndex = 1e18
// tokensAccruedOf[attacker] = dust * 1e18

// 4. Drain the distributor's reward tokens:
const balBefore = await rewardToken.balanceOf(attacker.address);
await distributor.connect(attacker)["claimRewards(address)"](attacker.address);
// attacker receives min(dust * 1e18, distributor balance) — e.g. dust=1e6 wei pays 1e24
expect(await rewardToken.balanceOf(attacker.address)).to.be.gt(balBefore);
```

Key assertion: `tokensAccruedOf[attacker] == depositToken.balanceOf(attacker) * 1e18` immediately after step 3, even though the attacker held the token only since step 1 and the index had not moved.
