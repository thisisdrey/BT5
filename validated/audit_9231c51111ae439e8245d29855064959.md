### Title
Debt floor check combined with `maxLiquidable` cap creates an unliquidatable "dead zone" of debt positions — DoS of `Pool.liquidate` and protocol bad debt - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` enforces two independent constraints on `amountToRepay_`: an upper bound (`amountToRepay_.wadDiv(debtBalance) <= maxLiquidable`, deployed at 50%) and a lower bound on the *remaining* debt (`remainingDebtInUsd == 0 || remainingDebtInUsd >= debtFloorInUsd`). There is no exemption that lets a liquidator fully close a small position — repaying 100% always exceeds `maxLiquidable`. Any position whose debt falls in `(debtFloorInUsd, debtFloorInUsd / (1 - maxLiquidable))` can therefore never be liquidated: every `amountToRepay_` either breaches the close-factor cap or leaves a remainder below the floor. This is the same bug class as the twTAP `magnitude >= pool.cumulative * 4` check — a validity check whose threshold has no minimum-size carve-out, permanently bricking a permissionless state transition (`liquidate` instead of `participate`).

### Finding Description
In `Pool.liquidate`:

```solidity
// contracts/Pool.sol
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}

if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_),
        _debtTokenBalance - amountToRepay_
    );
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
```

With `maxLiquidable = 0.5e18` (set in `initialize`, `Pool.sol:181`), a repay of more than 50% of the debt reverts, and any repay that leaves `0 < remaining < debtFloorInUsd` reverts. Solving for the dead zone: if debt `D` satisfies `debtFloorInUsd < D < debtFloorInUsd / (1 - maxLiquidable)` (i.e., `D < 2 * debtFloorInUsd`), then any `amountToRepay_ <= maxLiquidable * D` leaves `D - amountToRepay_` inside `(0, debtFloorInUsd)`, and any `amountToRepay_ >= D` exceeds the cap. Every call reverts — `liquidate` is DoS'd for that position forever (interest only shrinks the usable window further).

The same floor check in `DebtToken.repay` (`contracts/DebtToken.sol:442-451`) prevents anyone from repaying a position into the dead zone, but `repayAll` bypasses it because remaining debt becomes 0 — so the trap only affects `liquidate`, not voluntary exit.

Crucially, an unprivileged attacker can deliberately manufacture such a position at negligible cost: deposit a small amount of collateral, call `DebtToken.issue` with `amount_` chosen so the resulting debt lands just above `debtFloorInUsd` (`DebtToken._mint` only enforces `balanceBefore + amount >= floor`, `contracts/DebtToken.sol:583-588`). The position then becomes unhealthy the moment collateral or synth price moves slightly (or via permitted same-transaction oracle manipulation to trigger the unhealthy condition at liquidation time... note `debtPositionOf` must return unhealthy at the `liquidate` call, so a sustained price move or normal market drift is required — a purely same-tx flash manipulation is not enough since `liquidate` itself reads fresh oracle prices). Once unhealthy, no liquidator can ever touch it: the debt is below `2 * floor`, so it is permanently unliquidatable bad debt.

### Impact Explanation
- `Pool.liquidate` is permanently DoS'd for any account whose debt sits in the dead zone — the position's collateral is frozen (withdrawals blocked by `_revertIfLocked`/`unlockedBalanceOf` while unhealthy) and the debt can never be cleared by third parties.
- An attacker can mint many such positions cheaply (each costs only a small collateral deposit and debt ≈ floor) and let them go bad, accumulating unliquidatable bad debt and protocol insolvency; or grief by holding underwater positions that clog the pool.
- This directly mirrors the twTAP finding: a threshold check without a "small position" exemption turns an arithmetic edge case into a permanent liveness failure of a core permissionless function.

### Likelihood Explanation
- Requires `debtFloorInUsd > 0` (intended to be configured — the parameter and `RemainingDebtIsLowerThanTheFloor` error exist precisely for that) and `maxLiquidable < 1e18` (deployed value is `0.5e18`).
- No privileged role needed to create a dead-zone position — `DebtToken.issue` is public and only checks `issuableInUsd`.
- Positions can also fall into the zone organically via interest accrual or partial repayments/`repayAll`-less flows landing near the floor.

### Recommendation
Allow full liquidation of small positions: e.g., in `Pool.liquidate`, skip the `maxLiquidable` cap when `amountToRepay_ == _debtTokenBalance` (full close), or permit repay amounts that leave `0 < remaining < debtFloorInUsd` only when the liquidator repays the entire balance. Equivalent to the twTAP fix suggestion: exempt the minimum-size case from the threshold check so the check cannot brick the entry point.
