### Title
Unstaked connection-table churn allows a single unprivileged attacker to force repeated 90%-capacity eviction and starve legitimate unstaked/staked-fallback senders - ([File: streamer/src/nonblocking/swqos.rs])

### Summary
`SwQos::prune_unstaked_connections_and_add_new_connection` triggers `prune_unstaked_connection_table` whenever the shared unstaked table is at/above `max_unstaked_connections`, evicting the globally *oldest* key via `ConnectionTable::prune_oldest`, and then unconditionally inserts the new connection regardless of whether pruning succeeded. Because a brand-new `ConnectionEntry` always gets a fresh `last_update` timestamp at creation time, an unprivileged attacker who repeatedly opens and immediately closes connections from the same key never becomes the "oldest" entry, so the per-add eviction consistently sacrifices other (legitimate, quieter) unstaked or staked-fallback entries instead.

### Finding Description
The unstaked connection admission path is:

`SwQos::try_add_connection` (Unstaked branch) → `prune_unstaked_connections_and_add_new_connection` → `prune_unstaked_connection_table` → `ConnectionTable::prune_oldest` → `cache_new_connection` → `ConnectionTable::try_add_connection`. [1](#0-0) 

`prune_unstaked_connection_table` only prunes when `total_size >= max_unstaked_connections`, and when triggered it prunes down to 90% capacity (`PRUNE_TABLE_RATIO`) via `prune_oldest`: [2](#0-1) 

`prune_unstaked_connections_and_add_new_connection` calls the prune step and then *unconditionally* calls `cache_new_connection`, regardless of whether the prune actually freed capacity relative to the incoming insert: [3](#0-2) 

`ConnectionTable::prune_oldest` evicts the *entire key* (IP or Pubkey bucket, i.e., all connections under that key) whose minimum `last_update` across its connections is smallest, repeating until under the target size: [4](#0-3) 

Crucially, `last_update` for a freshly created `ConnectionEntry` is always set to "now" at insertion time (`ConnectionTable::try_add_connection` stores the caller-supplied `last_update`, which was initialized to `timing::timestamp()` in `build_connection_context`): [5](#0-4) [6](#0-5) 

The per-source cap (`max_connections_per_unstaked_peer`, checked in `cache_new_connection` via `try_add_connection`'s `has_connection_capacity`) only limits how many *simultaneous* connections one key can hold — it does nothing to limit churn (open+close+reopen) rate, and does not protect against a key perpetually refreshing its own recency by closing and reopening: [7](#0-6) 

Exploit flow: an unstaked attacker opens connections (under one or a few IPs/keys) to keep the shared `unstaked_connection_table.total_size` at or above `max_unstaked_connections`, then repeatedly closes and reopens connections from those same keys. Each reopen executes the code path above: since `total_size >= max_unstaked_connections`, `prune_oldest` runs and evicts the globally oldest key. Because the attacker's own key was *just* refreshed (new entry, "now" timestamp), it is never the pruning target; some other, quieter unstaked or staked-fallback-into-unstaked connection (whose `last_update` hasn't been refreshed because it isn't churning) is evicted instead. This repeats on essentially every attacker reopen, since insertion after pruning is unconditional and does not verify that capacity remains for the new connection versus other tenants.

Existing protections do not stop this: per-peer limits (`max_connections_per_unstaked_peer`) bound simultaneous connection count per key but not open/close churn rate; there is no minimum dwell time, no fairness weighting across keys, and no rate limit on `try_add_connection` calls per source. The eviction policy (`prune_oldest`) is purely recency-based and per-key, so it structurally rewards churn over connection quality/legitimacy.

### Impact Explanation
Scoped impact: an unprivileged, unstaked remote attacker can, at essentially zero relative cost (opening/closing connections is cheap versus maintaining a long-lived TPU connection), cause the shared unstaked/staked-fallback QUIC connection table to repeatedly evict other tenants' connections rather than the attacker's own. This starves legitimate unstaked senders' and staked-fallback connections' access to shared unstaked TPU capacity, and causes recurring `Mutex<ConnectionTable>` lock acquisition/contention on every churn cycle, degrading throughput for genuine senders sharing the unstaked table. This falls under Agave's QoS-evasion / node-level DoS-of-shared-resource category (unfair capture of shared unstaked capacity by a single unprivileged source), scoped to TPU ingress connection admission, not a memory-safety or consensus-integrity bug.

### Likelihood Explanation
Preconditions: attacker only needs to be an unprivileged remote client capable of opening/closing QUIC connections to the leader's public TPU port — no stake, no gossip/peer control, no config access. Feasibility is high: opening/closing a QUIC connection is inexpensive for the attacker (no need to actually send valid transactions), and the described feedback loop (churn → self-refreshing recency → eviction of others) is a direct, deterministic consequence of the code's design rather than a probabilistic race. It is fully repeatable as long as the attacker sustains a churn rate at or above the natural refresh rate of legitimate quieter connections in the shared table.

### Recommendation
- Make eviction fairness-aware rather than purely recency-based for the shared unstaked table: e.g., weight/penalize keys by churn rate (connection creation/close frequency) in addition to `last_update`, or use a minimum "connection age" before a newly created entry is eligible to avoid being pruned/to avoid protecting the attacker.
- Consider random-sampled eviction (similar to `prune_random` used for staked pruning) instead of strict oldest-first for the unstaked table, to reduce the ability of a single attacker to reliably steer which entries get evicted.
- Rate-limit or throttle connection open/close churn per source (IP/pubkey) independent of the simultaneous-connection cap, e.g., a token bucket on `try_add_connection` calls per key.
- After pruning in `prune_unstaked_connections_and_add_new_connection`, verify the table has actual free capacity before inserting, rather than unconditionally calling `cache_new_connection`.

    pub(crate) fn prune_oldest(&mut self, max_size: usize) -> usize {
        let mut num_pruned = 0;
        let key = |(_, connections): &(_, &Vec<_>)| {
            connections.iter().map(ConnectionEntry::last_update).min()
        };
        while self.total_size.saturating_sub(num_pruned) > max_size {
            match self.table.values().enumerate().min_by_key(key) {
                None => break,
                Some((index, connections)) => {
                    num_pruned += connections.len();
                    self.table.swap_remove_index(index);
                }
            }
        }
        self.total_size = self.total_size.saturating_sub(num_pruned);
        num_pruned
    }
