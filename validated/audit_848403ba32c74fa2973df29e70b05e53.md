### Title
Precision loss in `ExchangeProcessor`'s bancor formula (double-precision math) can be exploited by an order placer to extract more value than deposited or drain exchange pools with rounding-favorable trades - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The `ExchangeTransactionActuator` lets any unprivileged "order placer" submit an `ExchangeTransactionContract` to trade against a bancor-style TRC10 AMM pool [1](#0-0) . The actual conversion math lives in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, which perform the bancor-relay calculation entirely in Java `double` precision, then truncate to `long` via a cast [2](#0-1) . This is directly analogous to the Beedle `_calculateInterest` bug: double-precision division/exponentiation followed by truncating cast can silently lose precision, and — unlike the interest example where the loss simply zeroes out — here the rounding direction is attacker-influenceable across the sell→relay→buy two-step conversion, because `exchangeToSupply` (cast down) and `exchangeFromSupply` (cast down again) compound truncation in different reference frames (raw token balance vs. "relay" supply units).

### Finding Description
Both stages of the conversion truncate independently:
- `exchangeToSupply` computes `-supply * (1 - (1+quant/newBalance)^0.0005)` in `double`, casts to `long`, and updates `supply` with the truncated value [3](#0-2) .
- `exchangeFromSupply` then computes `balance * ((1+supplyQuant/supply)^2000 - 1)` again in `double`, casts to `long` [4](#0-3) .

The codebase itself demonstrates awareness that this exact bancor arithmetic is precision-lossy: it ships a parallel `SafeExchangeProcessor` that redoes both stages with `BigDecimal` at 18-digit scale specifically to avoid `double` truncation error [5](#0-4) , and a test explicitly asserts the legacy vs. hardened paths can diverge by up to 1 unit due to this precision difference [6](#0-5) . Selection between the lossy `ExchangeProcessor` and the safe `SafeExchangeProcessor` is gated by a committee-controlled `hardenedCalc` flag inside `ExchangeCapsule.transaction` [7](#0-6) . Unless that governance flag is enabled on-chain, every `ExchangeTransactionContract` executed by any order placer runs through the double-precision path.

Because `ExchangeTransactionActuator.validate()` re-invokes the *same* lossy `transaction()` call to compute `anotherTokenQuant` for its `tokenExpected` slippage check [8](#0-7) , and `execute()` calls `transaction()` again to actually mutate pool balances [9](#0-8) , the state-mutating math is never checked against an exact (BigDecimal/BigInteger) reference unless hardening is on — there is no `Not precise enough` style guard here (unlike `ExchangeWithdrawActuator`, which does add a `BigDecimal`-based "Not precise enough" check to its non-hardened path [10](#0-9) ). `ExchangeTransactionActuator` has no equivalent precision sanity check in its default (non-hardened) mode.

### Impact Explanation
An order placer can repeatedly submit small trades whose `double` rounding is biased toward the trader (e.g., truncation of `exchangeFromSupply`'s output rounds the *pool's payout* down each single call, but truncation of `exchangeToSupply`'s relay-supply update can, over many trades, decouple the internal `supply` accumulator from the true bancor curve, since `supply += out` uses the already-truncated value). Repeated round-tripping (buy then immediately sell back) at carefully chosen quantities can extract a small deterministic edge from the pool balances on every cycle, draining `firstTokenBalance`/`secondTokenBalance` over many transactions — a loss of pooled TRX/TRC10 funds contributed by other exchange participants. This matches the Beedle analog: division truncation that consistently favors one side of a ratio calculation, exploitable by an ordinary transaction sender with no special privilege.

### Likelihood Explanation
Likelihood is constrained by two factors I could not fully resolve from the index: (1) whether `AllowHardenExchangeCalculation`/the `hardenedCalc` flag defaults to enabled or disabled in current mainnet parameters (I found the flag's usage sites but not its stored default value in `DynamicPropertiesStore`), and (2) whether the TRON Exchange (Bancor-style) feature is still active/reachable on current mainnet (it has reportedly been deprecated in favor of other DEX mechanisms in later java-tron versions, but this repo snapshot still exposes the full actuator). If exchanges with non-trivial balances remain active and hardening is off, this is directly reachable by any account holding the traded assets, requiring no elevated privilege — only `execute()`/`validate()` via a signed `ExchangeTransactionContract`.

### Recommendation
- Make `SafeExchangeProcessor` (BigDecimal-based) the default and only path for `ExchangeCapsule.transaction`, removing the double-precision `ExchangeProcessor` entirely, or force `hardenedCalc = true` unconditionally rather than gating it behind a governance proposal.
- Add a precision/slippage sanity check inside `ExchangeTransactionActuator.doValidate()` (mirroring the "Not precise enough" `BigDecimal` check already present in `ExchangeWithdrawActuator`) that recomputes the expected output with exact arithmetic and rejects transactions where the lossy result diverges beyond a safe epsilon.
- Audit `ExchangeInjectActuator`/`ExchangeWithdrawActuator` similarly to ensure `execute()` and `validate()` always use the same (exact) arithmetic so no mismatch between the validated and executed ratio can arise.

### Proof of Concept
Not independently reproducible from the indexed code alone — this requires running `ExchangeProcessor.exchange()` against representative pool balances (as the repo's own `ExchangeCapsuleTest.testTransactionLegacyVsHardenedProcessorSelection` partially does [6](#0-5) ) and demonstrating a chain of buy/sell round trips that yields a positive drift in the trader's favor across many iterations. I was not able to execute code to confirm the compounding drift magnitude or the current mainnet default of the hardening flag; a background Devin session with repo/test execution access would be needed to quantify this precisely.

    logger.debug("balance: " + balance);
    long newBalance = balance + quant;

    double issuedSupply = -supply * (1.0

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
