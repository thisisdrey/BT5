### Title
Missing sender-identity check in `handleCreateRelayRequest` allows a peer to register relay/terminal state under an arbitrary spoofed `RelayFromAddr` - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` authenticates the *transport* (the `NebulaControl_CreateRelayRequest` arrives over an already-established, authenticated tunnel with `HostInfo h`), but it never checks that the `RelayFromAddr` field carried *inside* the message actually equals `h`'s own certified VPN address (`h.vpnAddrs`). This is the same bug class as the report: the code validates *who* sent the message but not that the *parameter used to perform the sensitive action* (here, the relay-origin identity) matches the identity of the authenticated sender.

### Finding Description
When a Control message is received, `HandleControlMsg` decodes it and, for `CreateRelayRequest`/`CreateRelayResponse`, only validates that `RelayFromAddr`/`RelayToAddr` are non-nil: [1](#0-0) 

It then dispatches to `handleCreateRelayRequest(v, h, f, msg)`, where `h` is the `HostInfo` of the tunnel the message physically arrived on (i.e., the cryptographically authenticated peer), while `from` is read straight out of the attacker-controlled protobuf field: [2](#0-1) 

The only checks performed on `from` are:
- whether `from` is one of *my own* addresses (`f.myVpnAddrsTable.Contains(from)`) — rejecting self-spoofing, and
- whether `target` (the relay destination) is me.

There is no check of the form `from == h.vpnAddrs[0]` (or any of `h.vpnAddrs`). When `target` is me, the code proceeds to call `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` and `h.relayState.InsertRelay(from, index, &newRelay)`, associating the *authenticated* `HostInfo h` with an *unauthenticated, attacker-chosen* `from` address: [3](#0-2) 

This mirrors the `SessionKey`/`claim()` bug exactly: `CredibleAccountModule::validateUserOp()` verified the signer owned *a* session key but never checked that the session key used for `claim()` matched the one that signed — here, Nebula verifies the message came from *a* legitimately-tunneled peer `h`, but never checks that the peer-identity embedded in the payload (`from`) matches `h`'s own certificate identity before creating relay state that binds `h` to that identity.

### Impact Explanation
Any authenticated peer `h` (with a valid handshake/tunnel to the victim node) can send a `CreateRelayRequest` claiming `RelayFromAddr = victimVpnAddr` for some other legitimate peer on the network. The receiving node will create/complete relay state (`h.relayState.InsertRelay(victimVpnAddr, ...)`, potentially transitioning through `Established`) that maps "traffic to/from `victimVpnAddr`" onto the tunnel with `h`. Because `QueryVpnAddrsRelayFor`/`handleOutsideRelayPacket` later use this per-`HostInfo` relay map (`relayState.QueryRelayForByIp`/`QueryRelayForByIdx`) to decide where relayed traffic for a given VPN address is forwarded, this can lead to remote relay-state poisoning: traffic intended for the victim can be redirected through/attributed to the malicious peer `h`, and legitimate relay negotiation for the victim's real address can be corrupted or hijacked. This satisfies the "remote state poisoning" impact bar with no need for a valid CA-signed cert of the victim — only the attacker's own valid, CA-signed peer certificate and a normal tunnel to the target relay node.

### Likelihood Explanation
Any node that participates as a relay (`am_relay: true`) or terminal endpoint is reachable by this path as soon as any peer establishes a tunnel to it — a routine, low-friction network event. The attacker needs only a legitimate certificate for themselves (not for the victim) and the ability to send one Control message on an already-authenticated tunnel, which is trivially achievable by any peer in the mesh. No race condition or unusual timing is required, making this readily exploitable by any participant.

### Recommendation
In `handleCreateRelayRequest` (and symmetrically in `handleCreateRelayResponse`), validate that the `RelayFromAddr`/`from` value asserted in the payload is actually one of the sending `HostInfo h`'s certified `vpnAddrs` before creating or updating any relay state keyed by `from`. Reject the message (log and return) if `from` does not match any address in `h.vpnAddrs`, mirroring the self-consistency checks already used elsewhere (e.g. `validatePeerCert`'s handling of certificate-derived VPN addresses).

### Proof of Concept
1. Attacker node `A` establishes a normal, mutually-authenticated tunnel to relay-capable node `R` (`relay.am_relay=true`), using `A`'s own valid CA-signed certificate.
2. `A` sends a `Control`/`NebulaControl_CreateRelayRequest` message over this tunnel with `RelayFromAddr = V` (the VPN address of victim node `V`, who has no relationship to `A`) and `RelayToAddr = R` (or some third node reachable via `R`).
3. `handleCreateRelayRequest` on `R` receives this over `HostInfo h` (which is `A`'s authenticated HostInfo), reads `from = V` from the payload, sees `target == me`, finds no existing relay entry for `from`, and calls `AddRelay(rm.l, h, f.hostMap, V, &m.InitiatorRelayIndex, TerminalType, Established)` — creating relay state on `R` that associates `A`'s tunnel with address `V`, without ever verifying `V` is actually `A`.
4. `R` now believes it can relay traffic for `V` through `A`'s tunnel, corrupting `R`'s relay routing for `V` and enabling `A` to intercept or disrupt relayed traffic destined for `V`.
