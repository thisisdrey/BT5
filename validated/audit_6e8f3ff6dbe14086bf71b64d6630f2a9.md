### Title
Replay-window check-then-update race allows a captured packet to be accepted twice - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` protect against replay by calling `window.Check()` before decrypting and `window.Update()` after decrypting, but the two operations are protected by two *separate* critical sections rather than one atomic one. Between the `Check` and the later `Update`, the replay window is not marked as "consumed," so a second copy of the same packet processed concurrently can also pass `Check` and be accepted.

### Finding Description
`Decrypt` performs the replay check and the replay commit as two independent, separately-locked steps, with the (unlocked) AEAD decryption sandwiched in between: [1](#0-0) 

```go
func (cs *ConnectionState) Decrypt(...) ([]byte, error) {
    cs.decryptLock.Lock()
    result := cs.window.Check(l, messageCounter)
    cs.decryptLock.Unlock()
    if !result { return nil, ErrAlreadySeen }

    out, err = cs.dKey.DecryptDanger(...)   // no lock held here
    ...
    cs.decryptLock.Lock()
    result = cs.window.Update(l, messageCounter)
    cs.decryptLock.Unlock()
    ...
}
```

The same pattern exists in `VerifyRelay` (used for relayed frames): [2](#0-1) 

`Check` only *reads* the bitmap (`bits.go`'s `Check`) and does not mark the counter as seen; only `Update` mutates `b.current`/the bitmap to record that the counter has been consumed (`bits.go` `Update`/`updateSlow`). Because `Check` and `Update` are not combined under a single lock hold across the decrypt call, two goroutines that concurrently receive the same wire packet (same `messageCounter`) can both execute `Check` and both observe "not yet seen," both successfully run `DecryptDanger` (the AEAD tag is valid because it's a legitimate captured ciphertext), and both then call `Update`, with the second `Update` simply returning `false` too late — after the payload has already been delivered to the tun device / relay forwarder once for each racing goroutine.

This is structurally the same bug class as the report: a security-relevant counter (`ethWithdrawn`/`nETHMinted` there, the replay-window `current`/bitmap here) that must be updated atomically together with the consuming action (withdrawal payout there, packet acceptance here) is instead updated in a way that leaves a window where the state has not yet reflected the "already consumed" fact, letting the same unit be spent/accepted more than once.

### Impact Explanation
Nebula supports multiple UDP reader routines per listener (`listen.routines`) that read from the same socket and dispatch to `readOutsidePackets` → `Decrypt`/`VerifyRelay` concurrently for the same `HostInfo`/`ConnectionState`. If two workers happen to process a duplicate/replayed copy of the same message counter concurrently, both can pass the replay check before either commits the update, resulting in the same encrypted application data or relay frame being decrypted and accepted twice. For `VerifyRelay`, this directly reproduces the relay double-forwarding condition the project's own regression test (`TestRelayReplayProtection`) is meant to prevent, and for `Decrypt` it means replay protection is not a strict guarantee under concurrency, undermining the anti-replay guarantee Noise/AEAD sessions are supposed to provide.

### Likelihood Explanation
Exploitation only requires an attacker able to capture one legitimate ciphertext packet (or relay frame) on the wire and re-inject it, which does not require holding a CA-signed certificate — the same precondition as the referenced relay-replay test. Triggering the race additionally requires the victim to be running with more than one UDP/listen reader routine (a supported, non-default-but-common performance configuration) so that two copies of the injected packet are picked up by different goroutines close enough in time to race the unlocked window between `Check` and `Update`.

### Recommendation
Hold `decryptLock` for the entire check-decrypt-update sequence (or otherwise make check+consume atomic with respect to the same counter), e.g.:

```go
func (cs *ConnectionState) Decrypt(...) ([]byte, error) {
    cs.decryptLock.Lock()
    defer cs.decryptLock.Unlock()
    if !cs.window.Check(l, messageCounter) {
        return nil, ErrAlreadySeen
    }
    out, err := cs.dKey.DecryptDanger(...)
    if err != nil {
        return nil, err
    }
    if !cs.window.Update(l, messageCounter) {
        return nil, ErrAlreadySeen
    }
    return out, nil
}
```
Apply the same fix to `VerifyRelay`. This ensures no second goroutine can observe the counter as "unseen" once one goroutine has begun accepting it.

### Proof of Concept
1. Establish a tunnel between two nebula nodes with `listen.routines` (or `tun.routines`) > 1 so multiple goroutines can call `readOutsidePackets`/`Decrypt` concurrently.
2. Capture one legitimate data packet (or relay frame, as in the existing `TestRelayReplayProtection` harness) with message counter `N`.
3. Inject two copies of the exact same captured packet back-to-back into the receiving UDP socket so they land on two different reader routines at nearly the same time.
4. Observe that under the race window between `window.Check` (unlocked release) and the later `window.Update`, both copies can pass `Check`, both get decrypted successfully, and both get delivered to the tun device (or, for relay frames, both get forwarded to the relay target) — i.e., the packet is accepted twice instead of the second copy being rejected as `ErrAlreadySeen`. func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]

		return err

	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
