### Title
Quarantine directory objects are unconditionally packed into a transaction's committed packfile without reachability validation - ([File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go])

### Summary
In `AutoCompoundingPodLp`, protocol fees are left sitting in the contract's own token balance, and because reward amounts are later derived from `balanceOf(address(this))`, those fees get silently swept up and auto-compounded on behalf of users. The analogous pattern in gitaly is `TransactionManager.packObjects`, which computes the packfile to commit by walking **everything that is physically present in the push's quarantine directory** (a shared, mutable "balance" of loose objects the client controls) rather than only the objects that are provably reachable from the transaction's actual reference updates. Objects the client placed in quarantine end up baked into the persisted packfile purely because they exist on disk in that scratch area, mirroring how leftover fee tokens end up baked into the compounded LP balance purely because they exist in the contract's balance.

### Finding Description
`packObjects` builds the list of objects to pack by combining two inputs and walking them together: [1](#0-0) 

- `heads` are the new OIDs from the transaction's actual reference updates.
- `quarantineOnlySnapshotRepository.ListObjects` additionally lists **all** objects already sitting in the quarantine object directory (with the alternate/original object directory disabled so only quarantine content is walked): [2](#0-1) 

Both streams are fed into `WalkObjects`, and the code comment explicitly documents the resulting behavior:

> "All objects in the quarantine directory that are encountered during the walk are included in a packfile that gets committed with the transaction... Objects that already exist in the repository are included in the packfile if the client wrote them into the quarantine directory... The packed objects are not yet checked for validity." [3](#0-2) 

This means any loose object an ordinary pushing user manages to get written into their own quarantine directory (via `git receive-pack`'s normal unpack-objects step, which is fully client-controlled: the client's pack can legally contain objects not referenced by any of the ref updates in that push, e.g. blobs/trees for future commits, thin-pack bases, or simply "junk" objects appended to the pack) is treated the same as a fee balance sitting in a shared contract: it gets swept into the final committed artifact (the packfile written via WAL) without verification that it is actually connected to or required by any reference change being made. The scanning logic in `packObjects` (lines 1456-1497) further confirms that any OID emitted by the walk that is *found* (not prefixed with `?`) is queued for packing/committing regardless of its relationship to `heads`: [4](#0-3) 

Because this happens before objects are checked for validity (as the code comment itself flags, referencing gitlab-org/gitaly#5779), an ordinary, unprivileged pushing user can populate the quarantine "balance" with arbitrary loose objects that are unrelated to the actual push intent and have them permanently persisted into the repository's object store as part of the transaction commit — exactly the "balance gets auto-swept into the output" pattern described in the report, but manifesting here as unbounded/unvalidated object persistence rather than fee loss.

### Impact Explanation
Every normal `git push` (an ordinary, unprivileged user action) populates a quarantine directory that Gitaly fully controls the walking of, but does not filter for relevance to the actual reference update. This allows a client to inflate the objects persisted to the repository on every push with arbitrary content that is unreachable from any advertised reference, since the objects only need to exist in quarantine to be walked and packed. This is a disk-growth/DoS vector on the RPC handler (`FetchRemoteAtomic`, `UserSquash`, and normal push paths all migrate/pack quarantine content), and, because validity is explicitly noted as unchecked at this stage, it also increases the attack surface for storing malformed/oversized or otherwise problematic objects that later code paths must trust.

### Likelihood Explanation
High. This code path executes on essentially every write transaction that touches a repository (regular pushes via `UpdateReference`, `FetchIntoObjectPool`/`FetchRemoteAtomic`, and `UserSquash`), all reachable by an ordinary, unprivileged user performing a push or triggering a fetch/squash RPC — no elevated privileges, leaked tokens, or malicious peers are required. The behavior is not a bug introduced by memory corruption or race condition; it is the documented, always-on logic of `packObjects`.

### Recommendation
Restrict the packfile computed by `packObjects` to objects that are actually reachable from the transaction's new reference tips (i.e., walk only from `heads`), and treat any additional quarantine content that is not reachable from the update as garbage to be discarded rather than as material to unconditionally persist. If quarantine content must be inspected for auxiliary purposes (e.g., detecting objects the client intends to reuse across pushes), that determination should be based on an explicit connectivity/reachability check tied to the actual reference changes being committed, not merely on presence in the quarantine "balance." Address the validity-checking gap referenced in the existing code comment (gitlab-org/gitaly#5779) as part of the same fix.

### Proof of Concept
1. As an ordinary authenticated user with push access to a repository, craft a push pack that updates one legitimate reference (e.g., `refs/heads/main`) but also includes extra loose objects (blobs/trees/commits) that are not reachable from any ref being updated in this push (Git's protocol does not require every object in a pushed pack to be reachable from the advertised ref updates; `git receive-pack` will unpack them into quarantine regardless).
2. Push this crafted pack via `git push`. Gitaly's `UpdateReference`/transaction flow creates a quarantine directory containing both the "real" objects and the extraneous ones, per [5](#0-4) .
3. During transaction commit, `packObjects` lists **all** objects in the quarantine directory (not just those reachable from the updated ref) and includes every found object in the packfile that is committed to the repository, per [6](#0-5) .
4. Repeating this process allows the client to grow the repository's on-disk object store with content that is never actually referenced by any branch/tag, at will, without any check for reachability or validity at this stage — analogous to fees silently accumulating and then being swept into the compounded balance in the original finding.

Note: I was not able to execute this PoC or trace the full downstream validity-checking logic (e.g., any later `git-fsck`-style verification that might partially mitigate the impact) within the available indexed context; a live Devin session with full repository and test-suite access would be needed to confirm whether any later stage rejects such unreachable objects before final commit.
