### Title
Unbounded read of HTTP response body in `libsigner` StackerDB RPC client causes memory-exhaustion DoS - (File: `libsigner/src/http.rs`)

### Summary
`run_http_request` in `libsigner/src/http.rs`, used by `StackerDBSession::rpc_request` in `libsigner/src/session.rs` to talk to a Stacks node's StackerDB HTTP RPC endpoint, reads the *entire* HTTP response into memory with `sock.read_to_end(&mut buf)` before any parsing, header check, or length validation occurs. Unlike every other HTTP payload-reading path in this codebase — e.g. `stackslib/src/net/httpcore.rs` (`read_payload`/`stream_payload`, bounded by `MAX_MESSAGE_LEN`/content-length) and even `decode_http_body`'s own chunked-encoding branch (bounded via `HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into())`) — this call path has no upper bound at all on the number of bytes it will buffer.

### Finding Description
`run_http_request` writes the HTTP request and then does: [1](#0-0) 

`sock.read_to_end(&mut buf)` will keep appending bytes to `buf` for as long as the remote peer keeps sending data (subject only to the per-read socket timeout set in `connect_or_reconnect`, which resets on any partial progress, not on total bytes read). Only *after* the entire response has been buffered does the code call `decode_http_response`/`decode_http_body` to parse headers/body: [2](#0-1) 

`decode_http_body` itself only imposes `MAX_MESSAGE_LEN` bound on the *chunked-encoding* path via `HttpChunkedTransferReader`: [3](#0-2) 

but for a plain (non-chunked) body it simply returns `buf.to_vec()` — and by that point `buf` (from the unbounded `read_to_end`) may already be arbitrarily large, so this "bound" is a no-op for the actual DoS vector: the OOM happens during the initial `read_to_end`, before any header/body separation or length check.

This directly parallels the reported Quill flaw: "unbounded reads of HTTP response bodies... reads the entire response body into memory without any size limit... an attacker who can control or modify the response content can return an arbitrarily large payload, causing the client to run out of memory and crash."

This client path is reached whenever the stacks-signer performs any StackerDB session RPC — `list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk` — all of which route through `rpc_request` → `run_http_request`: [4](#0-3) [5](#0-4) 

Notably, unlike the Quill scenario (which requires HTTPS interception, a compromised CA, or a corporate TLS-intercepting proxy), this connection is **plain, unencrypted HTTP** over `TcpStream`: [6](#0-5) 
so any network-path attacker between the signer and its configured node host (or the configured/compromised node itself) can trivially inject or replace the response — an even weaker trust-boundary requirement than the original advisory.

### Impact Explanation
A malicious or compromised StackerDB RPC endpoint (or an on-path attacker performing a simple TCP-level MITM, since no TLS is used) can respond to any signer RPC request with an unbounded byte stream, forcing the stacks-signer process to buffer the entire stream in memory via `read_to_end` with no cap. This can exhaust process/host memory and crash the signer (`RPCError`/OOM), interrupting the signer's participation in block validation/signing — an availability impact on the signer node, achieved via a single malicious response ("few messages"), unlike a bandwidth-flood attack that needs to sustain volumetric traffic against many endpoints/connections to matter. This is a fault in the client code path itself (absence of a length ceiling), not a network-layer/bandwidth exhaustion issue.

### Likelihood Explanation
Likelihood is moderate: it requires either (a) a compromised/malicious configured node host that the signer's `StackerDBSession` connects to, or (b) network-path control (no TLS is used, so no certificate-trust bypass is even needed) between the signer and that host. Both are realistic in deployments where the signer's node endpoint is not `127.0.0.1` or is reachable over an untrusted network segment.

### Recommendation
Bound the response read in `run_http_request` using a `BoundReader`/size cap (e.g., `MAX_MESSAGE_LEN` or a StackerDB-appropriate maximum, similar to `STACKERDB_MAX_CHUNK_SIZE`) instead of unconditional `sock.read_to_end(&mut buf)`, and reject/abort the connection once the limit is exceeded — mirroring the bound already applied in `stackslib/src/net/httpcore.rs` for other HTTP payload paths and in the chunked-encoding branch of `decode_http_body`.

### Proof of Concept
1. Configure (or MITM) the host that a `StackerDBSession` connects to (`session.rs::connect_or_reconnect`, plain TCP, no TLS).
2. On receiving any RPC request from the signer (e.g., `GET /v2/stackerdb/.../chunk/<slot>` used by `get_chunks`), respond with a valid-looking `HTTP/1.1 200 OK` status line followed by an effectively endless stream of bytes (no `Content-Length`, connection kept open, data trickled slowly enough to keep resetting the per-read socket timeout).
3. `run_http_request`'s `sock.read_to_end(&mut buf)` (`libsigner/src/http.rs:251`) will keep growing `buf` unboundedly, exhausting the signer process's memory and crashing it before `decode_http_response`/`decode_http_body` are ever invoked to apply any bound.
