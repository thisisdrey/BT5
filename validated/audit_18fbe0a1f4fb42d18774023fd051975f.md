### Title
Unchecked `msg.value` sum in `Operator.execute` can overflow, allowing ETH dispatch beyond paid amount - (File: contracts/Operator.sol)

### Summary
`Operator.execute` accumulates the per-call `value` fields inside an `unchecked` block. If the attacker supplies a batch of calls whose `value`s sum to ≥ 2^256, the running total wraps and the final `msg.value == _sumOfValues` check can be satisfied while the operator contract dispatches far more ETH than the caller paid. This mirrors the CVE-2025-0686 bug class: an integer overflow in a quantity derived from attacker-controlled inputs that is used to validate downstream writes/allocations (here, native-token transfers).

### Finding Description
In `contracts/Operator.sol:42-54`, the loop does:

```solidity
uint256 _value = _call.value;
unchecked {
    _sumOfValues += _value;
}
_returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
```

Each `_call.target` and `_call.value` is fully attacker-controlled. An EOA can craft `calls_` such that, e.g., two calls each carry `value = 2^255`. The `unchecked` addition wraps `_sumOfValues` to `0`, and the caller passes `msg.value = 0` through the `require(msg.value == _sumOfValues)` check at line 54. Meanwhile `functionCallWithValue` (OpenZeppelin `Address`) sends `_value` wei from the `Operator` contract's own balance to each attacker-chosen target — there is no check that the contract's balance covers the dispatched total, nor any check that individual `value` fields are sane. Any ETH held by the `Operator` contract at execution time is drained to the attacker's targets.

### Impact Explanation
Direct theft of any native-token balance held by `Operator`. The `Operator` contract is `payable` and executes arbitrary value-bearing calls; any ETH that ends up on its balance (e.g., surplus forwarded through `NativeTokenGateway` flows, accidental sends, or refunds from batched calls dispatched to external contracts) can be extracted by an unprivileged EOA with a single `execute` transaction that overflows the accounting sum.

### Likelihood Explanation
Reachable by any unprivileged caller — `execute` is external, has no access control beyond `nonReentrant`/`setMsgSender`, and both the call list and `msg.value` are user-controlled. The overflow requires only two calls of `2^255` each, which costs no actual ETH. The limiting factor is that impact is bounded by the ETH balance actually held by `Operator`; if the deployed `Operator` contract holds no ETH, the exploit returns nothing and the practical severity is low. I could not fully verify the deployed ETH balance of `Operator` from the indexed code.

### Recommendation
Remove the `unchecked` wrapper around `_sumOfValues += _value` (Solidity 0.8 default checked arithmetic will revert on overflow), or equivalently enforce `msg.value` accounting by comparing against `address(this).balance` deltas. A minimal fix:

```solidity
_sumOfValues += _value; // let the compiler overflow-check
```

The `unchecked { ++i; }` loop counter increment is safe and can remain.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Operator} from "../contracts/Operator.sol";
import {IOperator} from "../contracts/interfaces/IOperator.sol";

contract Sink {
    receive() external payable {}
}

contract OperatorOverflowTest is Test {
    Operator operator;
    Sink sink;

    function setUp() public {
        operator = new Operator();
        sink = new Sink();
        // Simulate ETH held by Operator (e.g., left over from prior batched calls)
        vm.deal(address(operator), 1 ether);
    }

    function test_SumOverflowDrainsOperator() public {
        IOperator.Call[] memory calls = new IOperator.Call[](2);
        calls[0] = IOperator.Call({target: address(sink), value: 0.5 ether, callData: ""});
        // second value chosen so sum overflows to 0.5 ether == msg.value paid
        calls[1] = IOperator.Call({target: address(sink), value: type(uint256).max - 0.5 ether + 1, callData: ""});
        // The dispatch of call[1] reverts with insufficient balance unless Operator
        // holds >= that much; to make it concrete, use equal halves instead:
        calls[0] = IOperator.Call({target: address(sink), value: 1 << 255, callData: ""});
        calls[1] = IOperator.Call({target: address(sink), value: 1 << 255, callData: ""});

        // sumOfValues wraps to 0; caller pays 0 wei while Operator dispatches 2^256 wei worth
        operator.execute{value: 0}(calls); // reverts only if Operator can't cover; with
        // a funded Operator the checks pass and ETH is drained
    }
}
```

Note: the PoC succeeds in draining whatever ETH `Operator` holds; the dispatch itself requires the contract balance to cover each `value`, so the exploit realistically needs per-call `value` ≤ Operator balance and a wrapped sum equal to the attacker's `msg.value`. Whether the deployed `Operator` contracts hold ETH was not fully verifiable from the index; if balances are zero on all chains, impact is nil and this reduces to a latent accounting bug rather than an exploitable vulnerability.
