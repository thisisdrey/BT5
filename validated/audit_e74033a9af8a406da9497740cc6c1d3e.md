## Finding

### Title
Cross-contract signature replay in StackerDB chunk authentication - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
The `SlotMetadata`/`StackerDBChunkData` signature scheme used to authenticate every StackerDB chunk write does not bind the signature to the specific StackerDB smart contract (replica) it was produced for. A chunk that was validly signed by a signer for one StackerDB contract can be replayed and accepted as valid for a *different* StackerDB contract, as long as the target replica assigns the same slot ID to the same signer address and the submitted version is fresher than what that replica currently has stored.

### Finding Description
The digest that gets signed/verified for every StackerDB chunk is computed purely from `slot_id`, `slot_version`, and `data_hash` — it never includes the StackerDB's contract identifier: [1](#0-0) 

`SlotMetadata::sign`/`verify` operate over this same digest with no contract-scoping: [2](#0-1) 

The verification path that actually gates writes, `StackerDBTx::try_replace_chunk`, only checks `slot_desc.verify(&slot_validation.signer)`, version freshness, and max-writes — it never checks that the signature was produced for *this* `smart_contract`: [3](#0-2) 

The same gap exists in the network-facing validation used for both StackerDB sync and unsolicited pushes, `PeerNetwork::validate_received_chunk`: it resolves `get_slot_signer(smart_contract_id, slot_id)` and calls `slot_metadata.verify(&addr)`, but `addr` recovery from the signature is contract-agnostic, so the same (slot_id, slot_version, data_hash, sig) tuple validates for any contract that happens to assign that slot to that signer: [4](#0-3) 

This is the direct analog of the reported bug class: just as the `WaveContract.claim` signature lacked a wave/contract-specific identifier and could be replayed across waves sharing a deadline, the StackerDB chunk signature lacks a StackerDB-contract-specific identifier and can be replayed across any StackerDB instances that share slot/signer assignment (e.g., the paired `.signers-<cycle>-0` / `.signers-<cycle>-1` message-pool contracts, or a signer set that persists unchanged into a subsequent reward cycle's StackerDB contract). Stacks nodes run multiple StackerDB contracts driven by overlapping signer sets: [5](#0-4) [6](#0-5) 

### Impact Explanation
Any unprivileged peer that observes a validly-signed chunk broadcast on the p2p network (StackerDB traffic is not confidential) can re-inject that exact `(slot_id, slot_version, sig, data)` tuple as a `StackerDBPushChunk` targeted at a *different* contract_id whose slot/signer assignment happens to match. If accepted, this results in forged-context data propagation: a node stores and further gossips a chunk that was never actually authorized for that particular StackerDB instance, misrepresenting a signer's message/vote as belonging to a different context (e.g., a different reward cycle's signer message pool). This is an unauthenticated write of misleading data into StackerDB state and its network-wide propagation, which can mislead consumers of signer StackerDB messages (e.g. block proposal/vote pools) about what a signer actually said in the current context.

### Likelihood Explanation
Exploitation requires no secret key and no special privilege — only observing one legitimately broadcast, validly-signed chunk (chunks are relayed in the clear over the p2p StackerDB protocol) and resubmitting it against a different, attacker-chosen contract_id via the standard unsolicited-push path (`handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk` → `try_replace_chunk`). The precondition (same slot_id owned by the same signer address in two different StackerDB contracts) is realistic given that Stacks nodes run paired/adjacent `.signers-*` contracts with overlapping signer sets and deterministic slot assignment.

### Recommendation
Include the StackerDB's `QualifiedContractIdentifier` (or an equivalent unique per-instance identifier) as part of the digest signed in `SlotMetadata::auth_digest`, and thread the contract identifier through `sign`/`verify` so a chunk signature is only valid for the specific StackerDB it was produced for.

### Proof of Concept
1. Node/signer S is assigned slot 0 in both `.signers-N-0` and `.signers-N+1-0` (or in two sibling `.signers-N-0`/`.signers-N-1` pools) with overlapping slot/signer assignment.
2. S legitimately signs and pushes a chunk `(slot_id=0, slot_version=5, sig)` to `.signers-N-0`; this chunk is broadcast in the clear to peers.
3. An observer takes the same `(slot_id, slot_version, sig, data)` and sends it as a `StackerDBPushChunk` with `contract_id = .signers-N+1-0` (or `.signers-N-1`).
4. `validate_received_chunk`/`try_replace_chunk` recompute `auth_digest` from `(slot_id, slot_version, data_hash)` only, recover the same signer address, and — since it does not check contract binding — accept and store the replayed chunk under the unintended contract, as long as version freshness allows it.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
