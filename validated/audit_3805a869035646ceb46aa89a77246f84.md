### Title
Concurrent object introduction via alternate unlinking during repack verification can prune still-needed loose objects - ([File: internal/gitaly/storage/storagemgr/partition/transaction_manager_housekeeping.go])

### Summary
The reported bug class is: a resource-accounting/state mechanism treats an operation as "settled" (distributed) based on a stale view of contributed inputs, so inputs added concurrently with that settlement are silently dropped/locked out. Gitaly's WAL-based transaction manager has a structurally analogous gap in its housekeeping-conflict verification: it explicitly checks for several types of conflicting concurrent operations before applying a repack, but documents and leaves open one specific case — loose objects introduced by a concurrent alternate-unlink (`DisconnectGitAlternates`) hard-link operation — as unguarded.

### Finding Description
`verifyHousekeeping` walks all log entries committed between a transaction's snapshot LSN and the current applied LSN to detect operations that conflict with an in-flight repacking/housekeeping transaction. It explicitly checks for concurrent housekeeping, repository deletion, and alternate unlinking that removed the alternates file: [1](#0-0) 

The comment directly preceding this loop documents the exact hazard: applying a repacking operation prunes all loose objects on application, and while transactions normally only introduce packs (not loose objects), the alternate-unlinking flow (`DisconnectGitAlternates`) hard-links the pool's loose objects into the member repository — which "can technically still introduce loose objects into the repository and trigger this problem" — until this case is explicitly excluded by checking for `RemoveDirectoryEntry` on the alternates file path.

`DisconnectGitAlternates` is documented as "a slightly dangerous RPC" that optimistically hard-links all alternate objects it might need before removing the alternates link and running a connectivity check: [2](#0-1) 

Because the guard in `verifyHousekeeping` keys specifically off removal of the alternates file entry, any window where the hard-linked loose objects are introduced into a repository while a concurrent `FullWithCruft`/full repack transaction is being verified — but before/without an accompanying alternates-file removal being visible in the walked range — is a case the safety check does not fully account for. Since a repack transaction prunes loose objects at apply time, objects hard-linked in via the unlink flow that are not yet referenced by the repack transaction's own snapshot could be pruned, mirroring the reported bug class where value/state added during an in-flight "settlement" is not accounted for and becomes effectively lost/locked.

### Impact Explanation
If a loose object introduced by a legitimate, ordinary-privilege operation (an object-pool member disconnecting from its pool, which any authorized repository owner/administrator can trigger via the gRPC API) is pruned away by a concurrently verified repack because the conflict-detection window does not fully cover this interleaving, the affected object becomes unreachable/corrupted in the repository. This is a data-durability / availability issue: legitimately introduced objects can be silently lost, causing subsequent Git operations (reads, fetches, checkouts) referencing those objects to fail — a denial-of-service on the affected repository's object database, analogous to the "locked funds" impact in the original report (contributed value becomes permanently stuck/unusable due to a stale accounting checkpoint).

### Likelihood Explanation
This requires a specific timing window: a `DisconnectGitAlternates` call and a full/cruft repack housekeeping transaction on the same (or an alternate-linked) repository need to race such that the hard-linked objects land in a snapshot the repack transaction doesn't account for, and the alternates-file-removal detection doesn't catch it. This is a narrow, hard-to-trigger race rather than a directly and trivially exploitable path, and it is explicitly flagged in the source code comments as a known, currently-unhandled edge case rather than a confirmed exploitable vulnerability. I was not able to fully trace `verifyRepacking`'s implementation within the available indexed content to conclusively confirm whether it independently closes this gap (the function's body was not found via search, only its call site), so this should be treated as a code-documented latent risk rather than a proven, end-to-end exploit.

### Recommendation
Extend `verifyHousekeeping`'s conflict-detection walk to also treat any concurrently-introduced loose objects/hard-linked files from an alternate-unlink operation as a conflict with an in-flight repack, not only the removal of the alternates file entry — i.e., detect `CreateHardLink`/file-creation operations under the `objects/` directory that originate from `DisconnectGitAlternates`, in addition to the existing `RemoveDirectoryEntry` check on the alternates path, and abort/retry the repack transaction (as is already done via `errConcurrentAlternateUnlink`) whenever such an interleaving is detected.

### Proof of Concept
Not constructed — reproducing this requires precisely interleaving a `DisconnectGitAlternates` RPC with a concurrent `FullWithCruft` repack transaction at the WAL layer such that the hard-linked loose objects fall inside the unguarded window, which requires white-box control over transaction commit ordering not available through the indexed test harness alone. The existing test suite already contains adjacent concurrency tests for this exact conflict-detection logic (e.g. `errConcurrentAlternateUnlink`, `errRepackConflictPrunedObject`) that would need to be extended to cover this specific interleaving to confirm exploitability.
