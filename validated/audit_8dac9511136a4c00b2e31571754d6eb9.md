### Title
GET /v2/attachments/inv serves an attachment inventory for an unverified, non-canonical `index_block_hash` - (File: stackslib/src/net/api/getattachmentsinv.rs)

### Summary
The `RPCGetAttachmentsInvRequestHandler::try_handle_request` handler takes `index_block_hash` directly from the client-supplied query string and uses it to query the AtlasDB and to populate `GetAttachmentsInvResponse.block_id`, without ever checking it against the node's canonical chain tip. Any remote, unprivileged caller can request an inventory for an arbitrary `StacksBlockId` and receive a syntactically valid response echoing that same, unverified block id.

### Finding Description
`try_parse_request` decodes `index_block_hash` from the query string via `StacksBlockId::from_hex(&value)` with no further validation [1](#0-0) . In `try_handle_request`, this value is passed straight into `network.get_atlasdb().get_attachments_available_at_page_index(*page_index, &index_block_hash)` for each requested page, and the resulting pages are wrapped into a `GetAttachmentsInvResponse` whose `block_id` field is set to `index_block_hash.clone()` — the exact attacker-supplied bytes, never checked against the node's canonical Stacks tip [2](#0-1) . There is no call to any tip-resolution or canonical-chain-check function anywhere in this handler; the only error paths are for `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` overflow, empty page list, or a DB query error (mapped to `HttpNotFound`) [3](#0-2) . Because `attachment_instances` is keyed by `index_block_hash`, a hash that was never processed simply yields no rows, and the underlying `get_attachments_available_at_page_index`/`get_attachments_missing_at_page_index` logic in `stackslib/src/net/atlas/db.rs` returns a default bit vector (all-available or all-missing depending on implementation) rather than an error — so the request still succeeds and returns HTTP 200 with a `block_id` equal to the attacker's arbitrary bytes.

### Impact Explanation
A remote, unauthenticated caller can, in a single GET request, obtain a `GetAttachmentsInvResponse` that asserts a specific bit-vector of attachment availability for a `StacksBlockId` the node never validated as canonical (or that may not exist at all). Downstream, `AttachmentsBatchStateContext.inventories` is keyed by `(QualifiedContractIdentifier, pages, StacksBlockId)`, so peers that fetch and cache this response can be steered into believing attachments are available/unavailable for a block id that has no relationship to the real canonical chain state, i.e., "serving non-canonical state as canonical" for the attachments-inventory subsystem — this matches the High severity category in the rules (steering peer state via false inventory served from a node's RPC surface). This is repeatable per request and costs the attacker only a single HTTP GET.

### Likelihood Explanation
No privileged role, secret, or special network position is required — the endpoint `/v2/attachments/inv` is a public RPC endpoint reachable by any remote party who can connect to the node's RPC port. The only precondition is knowledge of the URL format (`index_block_hash`, `pages_indexes` query params), which is public. This makes the attack trivially reproducible and cheap.

### Recommendation
Before querying AtlasDB, verify that `index_block_hash` corresponds to a block on the node's canonical Stacks chain tip (e.g., resolve it via chainstate/sortdb canonical-tip lookup, or check it against the known canonical header chain) and return `HttpNotFound`/`HttpBadRequest` if it is not canonical, mirroring the tip-validation performed by other endpoints that accept a block id.

### Proof of Concept
Add a test in `stackslib/src/net/api/getattachmentsinv.rs` (or its test module) that:
1. Constructs a `StacksNodeState` with an AtlasDB containing no rows for a randomly generated `StacksBlockId` (e.g., `StacksBlockId([0x42; 32])`) that was never part of any processed/canonical block.
2. Builds an `HttpRequestPreamble`/query string `index_block_hash=<hex of random id>&pages_indexes=0`.
3. Calls `RPCGetAttachmentsInvRequestHandler::try_parse_request` then `try_handle_request`.
4. Asserts the response is `200 OK` (not an error), decodes it via `decode_atlas_attachments_inv_response`, and asserts `response.block_id == random_id` while `random_id` was never inserted/committed as canonical in the test's chainstate/sortdb — demonstrating the handler serves an inventory keyed to an unverified block id.
