### Title
Unbacked value extraction from TRC10 Exchange bonding-curve pools via double-precision float math in `ExchangeProcessor` - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The Fantasm Finance incident stemmed from a flawed collateral/synthetic-asset accounting mechanism that let an attacker extract value the protocol’s reserves did not actually back. Java-tron’s built-in TRC10 `Exchange` (a Bancor-formula liquidity pool between TRX/TRC10 tokens) has an analogous class of risk: the legacy trade-pricing engine, `ExchangeProcessor`, computes swap outputs using Java `double` (IEEE-754 floating point) arithmetic and `Math.pow`, and this is the code path used by default (`allowHardenExchangeCalculation` must be explicitly enabled via a chain proposal to switch to the `BigDecimal`-based `SafeExchangeProcessor`).

### Finding Description
`ExchangeTransactionActuator.execute` calls `exchangeCapsule.transaction(...)`, which selects a `Processor` implementation based on the `allowHardenExchangeCalculation` dynamic property: [1](#0-0) 

When the hardened flag is off (the default state unless a witness-committee proposal has activated it), the pool uses `ExchangeProcessor`, whose `exchangeToSupply`/`exchangeFromSupply` routines rely on `double` math and `Maths.pow`: [2](#0-1) 

Floating-point `pow`/division operations are not exact and are input-dependent (rounding behavior differs based on the exact ratio of `quant` to `balance`, and on `supply` mutation between successive calls within/without the same block). This is a documented class of exchange/DEX bug: by choosing precise input amounts (potentially split into many small transactions or interleaved inject/withdraw calls to move `firstTokenBalance`/`secondTokenBalance` into rounding-favorable ratios), an unprivileged transaction sender can accumulate rounding surplus in their favor across repeated `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` calls, extracting more of the pool’s TRX/TRC10 balance than their trade should have entitled them to — i.e., draining value that is not actually backed by the corresponding side of the pool, mirroring how Fantasm’s flawed collateral math let an attacker mint/redeem more value than the FTM reserves justified.

The project’s own test suite acknowledges the imprecision: `testStrictMath` in `ExchangeProcessorTest` explicitly asserts that the non-strict-math legacy path and the strict/hardened path produce *different* results (`assertNotEquals(anotherTokenQuant, result)`), confirming the legacy processor is provably imprecise and diverges from the “safe”, exact BigDecimal implementation: [3](#0-2) 

The remediation path (`SafeExchangeProcessor`, using `BigDecimal` with fixed scale/rounding) exists in the codebase but is gated behind the `allowHardenExchangeCalculation` proposal flag, meaning any deployment that has not activated that flag remains exposed to the legacy floating-point processor: [4](#0-3) [5](#0-4) 

### Impact Explanation
If exploitable, an attacker could repeatedly call `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` against a self-created or existing `Exchange` pool, using crafted amounts chosen to accumulate favorable floating-point rounding on each `exchange()` call, incrementally draining TRX or TRC10 asset balance from the pool beyond what the bonding-curve math should allow. This is a fund-theft / unbacked-balance class of impact (Medium-to-High), directly analogous to the reported loss in the external report, since it can move real TRX/TRC10 value out of a liquidity pool without genuine consideration.

### Likelihood Explanation
This path is reachable by any unprivileged transaction sender — creating and trading against an `Exchange` requires only a signed `ExchangeCreateContract`/`ExchangeTransactionContract`, no special privilege. However, exploitability depends on the actual magnitude of rounding error accumulated per call relative to transaction fees/gas cost of repeated calls, which was not verified with a concrete numeric proof-of-concept in this investigation (would require running the double-precision `ExchangeProcessor.exchange` many times with adversarially chosen `sellTokenQuant` values to measure net drift versus the exact `SafeExchangeProcessor` baseline). The presence of a dedicated hardening flag and dedicated tests distinguishing legacy vs. safe math strongly suggests the java-tron team already identified float-precision drift as a real concern for this component.

### Recommendation
- Make `SafeExchangeProcessor` (or an equivalent exact-arithmetic implementation) the default and only implementation for all TRC10 Exchange actuators, rather than gating it behind an optional dynamic property.
- Audit historical/mainnet usage of `allowHardenExchangeCalculation` to confirm whether it has been activated on production networks; if not, treat all un-hardened deployments as exposed.
- Add fuzz/property tests comparing `ExchangeProcessor` vs `SafeExchangeProcessor` over many sequential trades on the same pool to bound worst-case cumulative drift and confirm it cannot be leveraged for net value extraction.

### Proof of Concept
Not independently reproduced with concrete numbers in this session — a full PoC would require: (1) instantiating an `Exchange` pool with representative TRX/TRC10 balances, (2) invoking `ExchangeCapsule.transaction()` (or the inject/withdraw pair) repeatedly with `useStrictMath=false`/legacy `ExchangeProcessor`, choosing `sellTokenQuant` values to maximize the double-precision rounding term `(long) issuedSupply`/`(long) exchangeBalance` in the attacker's favor, and (3) comparing the cumulative pool balance drift against the exact result computed by `SafeExchangeProcessor` for the same sequence of trades, per the divergence already demonstrated in `ExchangeProcessorTest.testStrictMath` [3](#0-2) .

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
