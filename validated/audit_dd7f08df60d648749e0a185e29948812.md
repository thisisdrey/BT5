### Title
Unbounded attribute-name list in `GetFileAttributesRequest` allows unbounded argv passed to `git check-attr`, risking E2BIG/resource exhaustion - ([File: internal/git/gitattributes/check_attr.go])

### Summary
`CheckAttr()` places every entry of the RPC-supplied `names` slice directly into the git-check-attr `Args`, with no upper bound on the number or total size of names. `GetFileAttributesRequest.Attributes` (via `internal/gitaly/service/repository/file_attributes.go`) only checks that the list is non-empty, not that it is bounded, letting an unprivileged caller submit a very large number of attribute names in a single call.

### Finding Description
`GetFileAttributes` validates only `len(in.GetAttributes()) == 0` in `validateGetFileAttributesRequest` [1](#0-0) , then passes `in.GetAttributes()` straight to `gitattributes.CheckAttr` as `names` [2](#0-1) . Inside `CheckAttr`, `names` becomes the `Args` field of the `check-attr` command with no size or count cap, and `c.count = len(names)` is stored to drive the read loop in `Check()` [3](#0-2) . There is no repo-content dependency — the attacker fully controls this field through the RPC request. No `MaxRecvMsgSize` override was found in the codebase, so the default gRPC message-size limit (4 MiB in grpc-go) is the only practical ceiling on the size of this repeated field, which is large enough to build an argv approaching or exceeding typical Linux `ARG_MAX` (~2 MiB), causing `exec` to fail with `E2BIG` inside `repo.Exec`.

### Impact Explanation
Worst case is a per-request failure (process spawn error) rather than a full server crash, since `E2BIG` is returned as an error and does not corrupt other requests. However, an attacker can repeat this cheaply-constructed request to force wasted CPU/memory building large argument arrays and repeated failed `execve` calls, degrading the `GetFileAttributes` RPC handler — a DoS of that RPC, matching the "DoS of an RPC handler" impact class in the audit rubric, but bounded in severity by the default gRPC message-size ceiling.

### Likelihood Explanation
Any unprivileged user who can invoke `GetFileAttributes` (a request only needing a valid repository target and revision, both attacker-controllable in their own repo/fork) can trivially craft such a request; no special role or repo content manipulation is needed. It is fully repeatable per request.

### Recommendation
Add an explicit cap on `len(in.GetAttributes())` (and consider capping total byte length) in `validateGetFileAttributesRequest`, returning `InvalidArgument` when exceeded, and/or switch to passing names via stdin/a file rather than argv to avoid argv-size limits entirely.

### Proof of Concept
```go
func TestGetFileAttributes_hugeAttributeList(t *testing.T) {
    names := make([]string, 200000)
    for i := range names {
        names[i] = fmt.Sprintf("attr-%d", i) // ~10 bytes each -> ~2MB argv
    }
    req := &gitalypb.GetFileAttributesRequest{
        Repository: repo,
        Revision:   []byte("HEAD"),
        Paths:      [][]byte{[]byte("README.md")},
        Attributes: names,
    }
    _, err := client.GetFileAttributes(ctx, req)
    // Expect: server currently attempts to spawn `git check-attr ... <200000 args>`,
    // which either fails with E2BIG or consumes excessive resources instead of
    // returning InvalidArgument up front.
    require.Error(t, err)
}
```
Note: exact `ARG_MAX` behavior is environment-dependent and could not be verified end-to-end in this static review; a background Devin session with shell access would be needed to confirm the precise failure mode (E2BIG vs. silent success) on the target OS/kernel.

```go
func validateGetFileAttributesRequest(ctx context.Context, locator storage.Locator, in *gitalypb.GetFileAttributesRequest) error {
	if err := locator.ValidateRepository(ctx, in.GetRepository()); err != nil {
		return err
	}

	if len(in.GetRevision()) == 0 {
		return errors.New("revision is required")
	}

	if len(in.GetPaths()) == 0 {
		return errors.New("file paths are required")
	}

	if len(in.GetAttributes()) == 0 {
		return errors.New("attributes are required")
	}

	return nil
```

```go
func CheckAttr(ctx context.Context, repo gitcmd.RepositoryExecutor, revision git.Revision, names []string) (*CheckAttrCmd, func(), error) {
	if len(names) == 0 {
		return nil, nil, structerr.NewInvalidArgument("empty list of attribute names")
	}

	cmd, err := repo.Exec(ctx, gitcmd.Command{
		Name: "check-attr",
		Flags: []gitcmd.Option{
			gitcmd.Flag{Name: "--stdin"},
			gitcmd.Flag{Name: "-z"},
			gitcmd.ValueFlag{Name: "--source", Value: revision.String()},
		},
		Args: names,
	},
		gitcmd.WithSetupStdin(),
		gitcmd.WithSetupStdout(),
	)
	if err != nil {
		return nil, nil, fmt.Errorf("start check-attr command: %w", err)
	}

	checker := CheckAttrCmd{
		cmd:    cmd,
		stdout: bufio.NewReader(cmd),
		stdin:  bufio.NewWriter(cmd),
		count:  len(names),
		m:      &sync.Mutex{},
	}

	return &checker, func() { _ = cmd.Wait() }, nil
```
