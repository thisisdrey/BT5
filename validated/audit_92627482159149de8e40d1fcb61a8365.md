### Title
`LinkRepositoryToObjectPool` accepts any repository merely matching the pool path pattern as a trusted object pool, with no verification of provenance to the target repository - (File: internal/gitaly/service/objectpool/link.go)

### Summary
`GaugeManager._createGauge()` accepted any contract passing a superficial shape check (`token0()`/`token1()`) as a CL pool, skipping the factory-provenance check ("isPair = true" for `_gaugeType == 1`), which let an attacker register a hostile pool that later reverted and bricked global reward distribution. Gitaly's object-pool linking path has the analogous shape: `objectpool.FromProto` / `ObjectPool.IsValid()` only checks that the supplied pool repository (a) lives under the reserved pool directory naming convention (`IsPoolRepository`) and (b) is *some* syntactically valid git repository (`locator.ValidateRepository`). It never checks that the pool was actually the one produced by `CreateObjectPool` for the specific repository being linked, nor any relationship between pool and target member repository.

### Finding Description
`LinkRepositoryToObjectPool` (`internal/gitaly/service/objectpool/link.go:10-28`) validates only the target `repository` argument with `s.locator.ValidateRepository`, and resolves the pool with `s.poolForRequest` (`internal/gitaly/service/objectpool/util.go:35-50`), which calls `objectpool.FromProto` (`internal/git/objectpool/pool.go:48-91`).

`FromProto` checks:
- `IsPoolRepository(proto.GetRepository())` — a pure regex/path check (`internal/gitaly/storage/repository_path.go:26-43`) on the *relative path string*, not on the repository's actual contents or origin.
- `pool.IsValid(ctx)` (`internal/git/objectpool/pool.go:119-121`) — which is `o.locator.ValidateRepository(ctx, o.Repo) == nil`, i.e., "is this a syntactically valid git repository at a legal storage path", with no check that this repository was created via `CreateObjectPool`, that it has the expected object-pool structure, or that it bears any relation to the `repository` being linked.

`Link` (`internal/git/objectpool/link.go:28-84`) then unconditionally writes the resolved pool path into the target repository's `objects/info/alternates` file (via `getRelativeObjectPath`, `internal/git/objectpool/link.go:149-166`), making every object in the "pool" reachable from the target repository, and strips the target's own bitmap (`removeMemberBitmaps`). None of this logic verifies that the "pool" is the pool that legitimately backs the target repository's fork lineage — it only requires the caller to supply a `RelativePath` that satisfies the naming regex and is a loadable git repository.

This mirrors the CL-gauge flaw precisely: a resource that is supposed to carry a strong provenance guarantee (an object pool trusted to be a repository's genuine alternate source, like a CL pool trusted to have been produced by the factory) is instead accepted based only on a shape/pattern check, with the "real" verification silently reduced to `isPair = true` in one case and to a generic `ValidateRepository`/path-regex pass in the other.

### Impact Explanation
Because any repository satisfying the pool naming convention and passing generic repository validation is accepted as a legitimate object pool, an attacker who can reach `CreateObjectPool`/`LinkRepositoryToObjectPool` (both exposed as part of the ordinary GitLab fork workflow — Rails invokes these RPCs automatically when a user forks a project) can supply a pool repository whose content or structure does not correspond to what downstream object-pool machinery assumes. Downstream operations that trust the "pool" invariant — `Disconnect` (`internal/git/objectpool/disconnect.go`), `FetchIntoObjectPool` (`internal/gitaly/service/objectpool/fetch_into_object_pool.go`), and repacking/housekeeping that treats pool-linked repos specially — can then fail unexpectedly (e.g., connectivity checks failing, alternates found "in an invalid state", multiple/ malformed alternate directories) once a repository is linked to such a pool, disrupting housekeeping/GC for that repository until an operator intervenes, analogous to the "distribution bricking until governance removes the malicious gauge" effect from the CL-gauge bug. The blast radius is scoped to repositories a user can already reach through legitimate fork/link RPCs, but the missing provenance check removes the safety net intended to keep alternate-object relationships consistent.

### Likelihood Explanation
`CreateObjectPool` and `LinkRepositoryToObjectPool` are both exercised automatically as part of GitLab's standard project-fork feature, so an ordinary user forking/creating repositories reaches this code path without any special privilege. Constructing a pool repository that is syntactically valid but structurally unexpected (e.g., an empty/near-empty repo, or one with its own alternates chain) requires only the ability to invoke `CreateObjectPool` with an origin the user controls, which is a normal, unprivileged operation.

### Recommendation
- When resolving an object pool for `LinkRepositoryToObjectPool`/`FetchIntoObjectPool`, verify not only that the relative path matches the pool naming convention and is a loadable git repository, but that it is actually the pool that was created for (or is otherwise authorized to serve as an alternate to) the specific `repository` in the request — e.g., by recording and checking pool-to-origin provenance metadata rather than relying solely on path pattern matching plus generic `ValidateRepository`.
- Reject linking when the supplied pool has structural properties inconsistent with a genuine, freshly created object pool (e.g., pre-existing multiple alternates chains, hooks present, or foreign HEAD/ref layout).
- Consider adding defensive `try/quarantine`-style handling around pool-dependent housekeeping operations (`Disconnect`, `FetchFromOrigin`, repack) so that a malformed or unexpected pool does not halt processing of the member repository indefinitely.

### Proof of Concept
1. As an ordinary authenticated user, create project `A`, then fork it (or directly call `CreateObjectPool` with `Origin=A` and an arbitrary pool `RelativePath` matching the `@pools/xx/yy/<hash>.git` convention) to obtain pool `P1`.
2. Separately, create project `B` (unrelated to `A`).
3. Call `LinkRepositoryToObjectPool(Repository=B, ObjectPool=P1)`. `poolForRequest` accepts `P1` purely because it matches `IsPoolRepository` and passes `ValidateRepository`/`IsValid` — no check ties `P1` to `B`'s fork lineage.
4. `B`'s `objects/info/alternates` now points at `P1`, an object pool with no legitimate relationship to `B`. Subsequent housekeeping/GC/`DisconnectGitAlternates` calls on `B` operate under incorrect assumptions about the alternate relationship, and any structural inconsistency in `P1` (e.g., missing expected objects, chained alternates) surfaces as failures in `B`'s housekeeping pipeline rather than being rejected up front at link time.
