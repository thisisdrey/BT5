### Title
`process_delivery_receipt` pays relayer reward without checking `DeliveryReceipt.success` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The Snowbridge outbound queue V2 pallet pays out the relayer reward for a queued message as soon as any validly-proven `InboundMessageDispatched` event log referencing the message's nonce is submitted, without inspecting the event's `success` field, which indicates whether the message actually executed successfully on the Ethereum Gateway.

### Finding Description
`submit_delivery_receipt` decodes an Ethereum event log into a `DeliveryReceipt` and calls `process_delivery_receipt`: [1](#0-0) 

`DeliveryReceipt` is decoded from the on-chain Ethereum event `InboundMessageDispatched(uint64 nonce, bytes32 topic, bool success, bytes32 reward_address)` and explicitly carries a `success: bool` field that distinguishes a successful dispatch from a failed one: [2](#0-1) 

`process_delivery_receipt` only checks that the gateway address matches and that a `PendingOrder` exists for the nonce; it never reads or checks `receipt.success` before paying the reward and removing the order: [3](#0-2) 

Because `success` is simply ignored, a message whose execution failed on the Ethereum side (`success == false`, e.g. reverted commands, out-of-gas, or a rejected command) still results in the relayer being paid the full order fee and the pending order being cleared as if delivery/execution had fully succeeded.

This directly violates the required invariant that "payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — here payout advances even when execution did not succeed.

### Impact Explanation
Any permissionless relayer that submits a legitimate-but-failed delivery proof still collects the reward fee that was meant to compensate successful delivery/execution of Polkadot→Ethereum messages. This creates an economic drain on the reward pool: relayers have no incentive to ensure commands actually succeed on Ethereum, since failed executions are paid identically to successful ones. Over time this can be used to systematically extract fees for messages whose execution failed, silently misallocating value that should remain in the reward/sovereign account, without requiring any admin, governance, or validator misbehavior — it only requires an ordinary relayer submitting a real, verifiable (but "failed") proof.

### Likelihood Explanation
Likelihood is high: nothing prevents a message's execution from legitimately failing on Ethereum (e.g., due to gas limits, reverted command logic, or contract-level restrictions), and any relayer who observes such a failure event can submit it via the public, unpermissioned `submit_delivery_receipt` extrinsic to claim the reward exactly as if it had succeeded. No special privileges, front-running, or malicious infrastructure roles are required — this is a normal usage path through a public entrypoint.

### Recommendation
Check `receipt.success` in `process_delivery_receipt` before paying the reward. On `success == false`, either withhold/reduce the reward, route it to a different resolution path (e.g., retry, refund to origin, or partial penalty), or explicitly document/handle the failure case instead of unconditionally paying the full fee and clearing the pending order as if delivery succeeded.

### Proof of Concept
1. A message is queued via `process_message`, creating a `PendingOrder { nonce, fee, .. }` [4](#0-3) .
2. On Ethereum, message execution fails (e.g., a command reverts), and the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds a valid proof of this real event log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (the event genuinely occurred), `DeliveryReceipt::try_from` decodes `success = false` correctly.
5. `process_delivery_receipt` checks only `gateway` and `nonce`/order existence — `receipt.success` is never read — so `T::RewardPayment::register_reward` is called with the full `order.fee`, and `PendingOrders` is removed as if delivery had fully succeeded: [5](#0-4) .
6. The relayer is paid in full despite the message's execution having failed on Ethereum.

Note: I could not fully trace how `success == false` is currently handled (if at all) downstream in the bridge's reconciliation/retry logic, or whether any off-chain/relayer-side social convention discourages this; that would require deeper inspection of the Snowbridge relayer client code, which may not be fully covered by the indexed codebase. If further certainty is needed, a full Devin session with repository access would be able to confirm whether any other on-chain path (e.g. a separate "failure" handling call) exists that this analysis missed.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
