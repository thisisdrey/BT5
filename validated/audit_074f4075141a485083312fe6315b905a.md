Based on the code retrieved, `ExchangeInjectActuator` and `ExchangeTransactionActuator` both fetch an `ExchangeCapsule` from the store and immediately call getters on it without any null-check, mirroring the CVE-2019-12482 pattern (a getter invoked on an object obtained from a lookup that can return null/absent, without validating existence first).

### Title
NULL Pointer Dereference on missing ExchangeCapsule in Exchange actuators - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
`ExchangeInjectActuator.execute()` and `ExchangeTransactionActuator.execute()` retrieve an `ExchangeCapsule` via `Commons.getExchangeStoreFinal(...).get(ByteArray.fromLong(exchangeId))` and immediately call `exchangeCapsule.getFirstTokenId()`, `getSecondTokenId()`, `getFirstTokenBalance()`, etc. on the result without a null check. [1](#0-0) [2](#0-1) 

### Finding Description
The `execute()` methods of both actuators look up an exchange pair by ID and dereference the returned capsule immediately:
```
ExchangeCapsule exchangeCapsule = Commons.getExchangeStoreFinal(dynamicStore, exchangeStore, exchangeV2Store)
    .get(ByteArray.fromLong(exchangeTransactionContract.getExchangeId()));
byte[] firstTokenID = exchangeCapsule.getFirstTokenId();
``` [3](#0-2) 
This is directly analogous to the GPAC bug class: a getter is called on the result of a store/map lookup without verifying the object exists first, exactly like `gf_isom_get_original_format_type` dereferencing a sample-entry lookup that can be NULL.

Whether this is actually exploitable depends on whether `doValidate()` (called by the actuator framework before `execute()`) already checks that the exchange with the given ID exists. From the `ExchangeCancelOrderActuator`-style pattern seen elsewhere (`MarketCancelOrderActuator`), such checks are typically present via a `try { ... } catch (ItemNotFoundException ...)` around `.get()`. The `doValidate()` bodies for `ExchangeInjectActuator`/`ExchangeTransactionActuator` were only partially retrieved (up to line 154 in the injected snippet), and I could not confirm with certainty whether `exchangeId` existence is validated before `execute()` runs. The `execute()` method itself only catches `ItemNotFoundException` for other calls, not specifically around the `exchangeCapsule` dereference, meaning if `.get()` returns `null` (as opposed to throwing) the subsequent `.getFirstTokenId()` call would throw an unchecked `NullPointerException`, which would surface as an uncaught runtime exception since the catch clause `catch (ItemNotFoundException | InvalidProtocolBufferException | ArithmeticException e)` does not cover `NullPointerException`. [4](#0-3) [5](#0-4) 

### Impact Explanation
If `doValidate()` does not fully guard against a non-existent or since-deleted `exchangeId` at the moment `execute()` runs (e.g., a TOCTOU race between validate and execute within block processing, or a code path where validate is bypassed), an uncaught `NullPointerException` during `execute()` inside `Manager`'s block-application transaction loop could propagate up and crash/halt block processing for that node, since `NullPointerException` is not caught by the actuator's `catch` clauses. This would be a node-crash/halt-class impact if reachable by an unprivileged broadcaster submitting an `ExchangeInjectContract`/`ExchangeTransactionContract` for a non-existent or just-removed exchange ID.

### Likelihood Explanation
Low-to-moderate confidence: this requires that `doValidate()` does not sufficiently check exchange existence, or that there's a race/rollback scenario between validate and execute (e.g., another contract in the same block deletes the exchange). I was unable to fully verify `doValidate()`'s completeness for these two actuators within the available context — only partial excerpts (lines up to ~154) were retrieved, and the full existence-check logic for `exchangeId` was not confirmed present or absent.

### Recommendation
Add an explicit null-check on `exchangeCapsule` immediately after the `.get()` call in `execute()` for both actuators, throwing `ItemNotFoundException`/`ContractExeException` instead of allowing a raw `NullPointerException`, mirroring the pattern already used in `MarketCancelOrderActuator.validate()` which wraps `orderStore.get()` in a try/catch for `ItemNotFoundException`. [6](#0-5)
