### Title
`CreateRepositoryFromSnapshot` extracts an untrusted tarball via the system `tar` binary with no validation, size limit, or trust boundary check - ([File: internal/gitaly/service/repository/create_repository_from_snapshot.go])

### Summary
The external report's bug class is "a caller-supplied outcome is accepted without any bound/validation, letting an adversary control the result to the caller's detriment" (`minimumBPT` hardcoded to 0 with no slippage check). The closest concrete Gitaly analog is `s.untar()` in `CreateRepositoryFromSnapshot`, which pipes an HTTP response body directly into `tar -C path -xvf -` with **no validation of the archive contents, no size limit, and an explicit code comment acknowledging the archive is "trusted *a lot*"**. Just as the Notional code accepted "however much BPT the pool will give us," Gitaly here accepts "whatever the snapshot HTTP endpoint sends," with no upper bound and no verification of what is written into the destination repository directory.

### Finding Description
`CreateRepositoryFromSnapshot` fetches an archive from an attacker-influenced URL and streams it straight into the OS `tar` command targeting the freshly created (but real, on-storage) repository path: [1](#0-0) 

The handler itself documents the risk directly in the source: [2](#0-1) 

Unlike the newer, hardened tar-extraction routine used for snapshot replication (`extractTarToDirectory` in `replicate.go`), which validates that every regular file, symlink, and hard-link target stays within the extraction root before writing: [3](#0-2) 

`untar()` performs **no such validation at all**. It hands the raw byte stream to `tar -xf -` unconditionally, with:
- No path-traversal / symlink-escape checks (zip-slip style writes outside the target directory are limited only by whatever protections the system `tar` binary itself provides, which is not guaranteed and historically has had CVEs for path traversal via `../` or absolute paths).
- No limit on the number of files or total decompressed size (tar/decompression bomb), unlike the RPC-level concurrency/queue limits documented elsewhere in the codebase for other RPCs.
- No content inspection of what's placed in the resulting "trusted" bare Git repository (hooks directory, config, refs) before it becomes a live repository other RPCs will operate on.

This is structurally analogous to the Solidity finding: a downstream, security-relevant outcome (BPT minted / files written into a repo) is accepted from an external, adversary-influenced source (pool swap rate / HTTP snapshot body) without any minimum-guarantee or bound (`minimumBPT=0` / no tar validation, no size cap), enabling the calling party to be harmed by content it did not intend to accept.

### Impact Explanation
If an operator or automation path supplies (or is tricked into supplying, e.g. via SSRF against an internal snapshot-serving endpoint) a crafted tarball, the extraction can:
- Escape the target repository directory (path traversal / symlink writes) and overwrite arbitrary files on the storage volume that Gitaly's process can write to.
- Plant malicious content (e.g., custom hooks, arbitrary refs, or config) directly into a repository that other RPCs will subsequently treat as valid and hook-execute, similar to a quarantine/hook bypass.
- Exhaust disk via decompression bombs, since there is no cap on extracted size, resulting in DoS of the storage/handler.

### Likelihood Explanation
`CreateRepositoryFromSnapshot` is a `MUTATOR` RPC that accepts an arbitrary `http_url` (and an optional `resolved_address` used specifically to defeat DNS rebinding, implying the URL itself is not from a fully trusted internal-only source in all deployments). The code's own comment ("this RPC ... should undergo a lot of hardening" before being pointed at endpoints not under Gitaly's control) confirms the maintainers already consider the archive source potentially untrusted, i.e., this is a known-accepted gap rather than a theoretical one. This keeps likelihood moderate-to-high wherever the RPC is reachable with attacker-influenced `http_url`/response content.

### Recommendation
Replace the direct `tar -xf -` pipe with the same validated, allow-listed extraction logic already implemented for snapshot replication (`extractTarToDirectory`/`extractFile` in `replicate.go`), which:
- Rejects absolute paths and any resolved path escaping the target directory for regular files, directories, symlinks, and hard links.
- Should additionally enforce a maximum total extracted size and file count (a "slippage"-style bound) to prevent decompression-bomb DoS, and reject any header types Gitaly is not deliberately supporting.

### Proof of Concept
1. Stand up an HTTP server that returns a tar stream whose header names contain path traversal sequences (e.g., `../../../etc/foo`) or symlink entries pointing outside the target directory (`ln -s /etc/passwd escape`, or a `tar.TypeLink`/`tar.TypeSymlink` entry crafted with `../../` in `Linkname`).
2. Invoke `CreateRepositoryFromSnapshot` with `HttpUrl` pointing at this server (and, if required to bypass SSRF guard rails, `ResolvedAddress` set to the server's real address, exactly as production callers do).
3. Observe that `s.untar()` in `internal/gitaly/service/repository/create_repository_from_snapshot.go` (lines 87-121) passes the response body directly to `tar -C path -xvf -` with no pre-validation, unlike the equivalent, already-hardened logic in `internal/gitaly/service/repository/replicate.go` (lines 314-406), and that files/symlinks can be written outside the intended repository directory or the storage volume can be exhausted with a decompression bomb, with no size bound enforced anywhere in the call path.

func (s *server) untar(ctx context.Context, path string, in *gitalypb.CreateRepositoryFromSnapshotRequest) error {
	req, err := http.NewRequestWithContext(ctx, "GET", in.GetHttpUrl(), nil)
	if err != nil {
		return structerr.NewInvalidArgument("Bad HTTP URL: %w", err)
	}

	client := httpClient
	if resolvedAddress := in.GetResolvedAddress(); resolvedAddress != "" {
		client, err = newResolvedHTTPClient(in.GetHttpUrl(), resolvedAddress)
		if err != nil {
			return structerr.NewInvalidArgument("creating resolved HTTP client: %w", err)
		}
	}

	if in.GetHttpAuth() != "" {
		req.Header.Set("Authorization", in.GetHttpAuth())
	}

	rsp, err := client.Do(req)
	if err != nil {
		return structerr.NewInternal("HTTP request failed: %w", err)
	}
	defer rsp.Body.Close()

	if rsp.StatusCode < http.StatusOK || rsp.StatusCode >= http.StatusMultipleChoices {
		return structerr.NewInternal("HTTP server: %s", rsp.Status)
	}

	cmd, err := command.New(ctx, s.logger, []string{"tar", "-C", path, "-xvf", "-"}, command.WithStdin(rsp.Body))
	if err != nil {
		return err
	}

	return cmd.Wait()
}
