### Title
Unconditional `insert_instantiated_attachment` in `AttachmentsDownloader::run` persists unverified peer-supplied content regardless of matching a real `AttachmentInstance` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
In `AttachmentsDownloader::run`, every `Attachment` returned by a peer response to a `/v2/attachments/{content_hash}` request is unconditionally passed to `AtlasDB::insert_instantiated_attachment`, even when the lookup `find_all_attachment_instances(&attachment.hash())` returns an empty vector (i.e., no real, on-chain-confirmed `AttachmentInstance` ever referenced that hash). This means a malicious peer can answer an attachment request with arbitrary bytes unrelated to what was actually requested, and that content gets permanently written into the `attachments` table as `was_instantiated=1`.

### Finding Description
The equality the question raises — rows in `attachments` with `was_instantiated=1` should equal rows whose hash a confirmed `AttachmentInstance` actually committed to — is broken, but the break is at the call site rather than the SQL itself. In `stackslib/src/net/atlas/download.rs`, `AttachmentsDownloader::run`:

```rust
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;
    for attachment_instance in attachments_instances.into_iter() {
        resolved_attachments.push((attachment_instance, attachment.clone()));
    }
    context.attachments_batch.resolve_attachment(&attachment.hash());
}
``` [1](#0-0) 

`insert_instantiated_attachment` runs regardless of whether `attachments_instances` is empty. Earlier, `extend_with_attachments` places whatever the peer returned into `context.attachments` with no check that `response.attachment.hash()` equals the `content_hash` that was actually requested:
```rust
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
``` [2](#0-1) 

Server-side, `RPCGetAttachmentRequestHandler` looks up by hash in the local `AtlasDB` and returns `GetAttachmentResponse { attachment }` [3](#0-2) , but a malicious peer is free to implement its own server logic and return any JSON body for any hash — nothing on the client validates the returned attachment's actual hash against the URL/content_hash it queried for. The requests themselves are only generated for `content_hash` values tracked in `AttachmentsBatch.attachments_instances`, which originate from real, chain-confirmed `AttachmentInstance` events [4](#0-3) , so the attacker cannot request arbitrary new hashes for free — but it can respond to any such legitimate request with unrelated bogus content, and that bogus content (keyed by its own hash) is stored anyway.

### Impact Explanation
Because the store happens unconditionally, an unauthenticated peer that is selected as an attachment source (by advertising the bit in its `/v2/attachments/inv` response) can cause the victim node to persist attacker-chosen bytes (bounded per-item by `attachments_max_size`) into the permanently retained `attachments` table, without those bytes ever corresponding to a real `attachment_instances` row. This is an unauthorized write of unverified data into node state driven purely by an unauthenticated HTTP response — the requested content_hash is never resolved because `resolve_attachment` matches on the attacker's bogus hash, so the real content_hash entry stays "missing" and the batch is retried (bounded by `max_attachment_retry_count`) before being dropped. Each retry with different bogus content yields another persisted garbage row.

### Likelihood Explanation
This requires the attacker to run its own peer, be selected as a data source for a legitimate outstanding attachment request (achievable by simply claiming to have the item in its inventory response), and answer with a well-formed but incorrect `GetAttachmentResponse`. No secret, signature, or privileged role is needed — this is exactly the "unprivileged remote peer answering RPC/P2P attachment requests" scenario in scope. However, unlike the question's premise, growth is **not literally unbounded** from a single peer/hash pair: it is capped per legitimate outstanding `content_hash` by `max_attachment_retry_count` retries before the batch is dropped, and the number of legitimate outstanding content hashes is itself bounded by real on-chain-confirmed `AttachmentInstance`s (which the attacker cannot mint for free). During a node's initial sync/catch-up, however, there can be a large number of such outstanding legitimate hashes, so the practical exposure (number of forged rows an attacker can inject) can still be substantial, even though it is not truly infinite as characterized in the question.

### Recommendation
In `AttachmentsDownloader::run`, only call `insert_instantiated_attachment` when `find_all_attachment_instances(&attachment.hash())` returns a non-empty result (i.e., the hash actually corresponds to a real, tracked `AttachmentInstance`); otherwise treat the response as invalid/faulty (penalize the peer via `bump_failed_requests` and do not persist). Additionally, in `extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before accepting the response at all, rejecting any mismatched attachment immediately as a protocol violation from that peer.

### Proof of Concept
Rust test plan (net-layer, no admin/secret required):
1. Set up a node with a pending, confirmed `AttachmentInstance` for `content_hash = H` (simulating a real on-chain zonefile/name-attachment event) queued in `AttachmentsDownloader`.
2. Stand up a mock HTTP peer that responds to `GET /v2/attachments/H` with a `GetAttachmentResponse` whose `attachment.content` is arbitrary bytes `B` (so its real hash is `H' != H`, `H' ` under `attachments_max_size`).
3. Advertise this peer in `/v2/attachments/inv` with the bit set for `H`'s page/index so it is selected as a source.
4. Drive `AttachmentsDownloader::run` through completion for the batch.
5. Assert: `AtlasDB::find_attachment(&H')` returns `Some(B)` (i.e., `insert_instantiated_attachment` persisted attacker content under `was_instantiated=1`), while `AtlasDB::find_all_attachment_instances(&H')` returns empty (no real `attachment_instances` row backs it) — demonstrating the write occurred despite `find_all_attachment_instances` returning empty in the exact code path at `stackslib/src/net/atlas/download.rs:153-169`.

    pub fn track_attachment(&mut self, attachment: &AttachmentInstance) {
        if self.attachments_instances.is_empty() {
            self.stacks_block_height = attachment.stacks_block_height;
            self.index_block_hash = attachment.index_block_hash.clone();
            self.canonical_stacks_tip_height = attachment.canonical_stacks_tip_height;
        } else if self.stacks_block_height != attachment.stacks_block_height
            || self.index_block_hash != attachment.index_block_hash
        {
            warn!(
                "Atlas: attempt to add unrelated AttachmentInstance ({}, {}) to AttachmentsBatch",
                attachment.attachment_index, attachment.index_block_hash
            );
            return;
        }

        let inner_key = attachment.attachment_index;
        match self
            .attachments_instances
            .entry(attachment.contract_id.clone())
        {
            Entry::Occupied(missing_attachments) => {
                missing_attachments
                    .into_mut()
                    .insert(inner_key, attachment.content_hash.clone());
            }
            Entry::Vacant(v) => {
                let mut missing_attachments = HashMap::new();
                missing_attachments.insert(inner_key, attachment.content_hash.clone());
                v.insert(missing_attachments);
            }
        };
    }
