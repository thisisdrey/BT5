### Title
`ExchangeInjectActuator` has no slippage/minimum-output check, unlike `ExchangeTransactionActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator.execute()` computes the paired-token amount (`anotherTokenQuant`) required to inject liquidity based on the *current* on-chain pool ratio at execution time, and unconditionally deducts that computed amount from the caller's account. Unlike `ExchangeTransactionActuator`, which enforces a caller-supplied `expected` minimum-output bound before allowing a trade to execute, `ExchangeInjectContract`/`ExchangeInjectActuator` has no equivalent bound on `anotherTokenQuant`, so a caller has no way to guard against the pool ratio moving between transaction signing/broadcast and execution.

### Finding Description
In `ExchangeInjectActuator.execute()` [1](#0-0) , `anotherTokenQuant` is derived purely from the exchange pool's live `firstTokenBalance`/`secondTokenBalance` and the caller-specified `tokenQuant`:
```
anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance);
```
This value is then unconditionally deducted from the caller's balance/asset holdings via `reduceAssetAmountV2`/`setBalance` [2](#0-1) . The `ExchangeInjectContract` protobuf message carries no minimum/maximum bound field for `anotherTokenQuant` — only `owner_address`, `exchange_id`, `token_id`, and `quant` [3](#0-2) . Any account can call this actuator (`ExchangeInjectActuator` has no creator-only restriction, unlike `ExchangeWithdrawActuator` which requires `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` [4](#0-3) ).

By contrast, `ExchangeTransactionActuator` explicitly protects callers from this exact class of risk by requiring an `expected` field and validating `anotherTokenQuant >= tokenExpected` before execution [5](#0-4) . This demonstrates the codebase's own design intent that AMM pool-ratio-dependent operations need slippage protection — an intent that was not carried over to `ExchangeInjectActuator`.

Because any account (not just the pool creator) can submit `ExchangeInjectContract`, and because `ExchangeTransactionContract` trades executing in intervening blocks/transactions shift `firstTokenBalance`/`secondTokenBalance` (the bancor-relay curve in `ExchangeCapsule`/`ExchangeProcessor` [6](#0-5) ), an attacker can front-run a pending `ExchangeInjectContract` with trades that move the pool ratio unfavorably for the injector, causing the injector's transaction to consume a different (larger, or of lower relative value) amount of `anotherTokenQuant` than they intended when signing, with no on-chain check to abort the injection.

### Impact Explanation
An ordinary API client/transaction broadcaster (any TRX/TRC10 holder calling `wallet/exchangeinject`) can be forced into depositing an unintended amount of the paired asset into an exchange pool because there is no `expected`/`minShare`-style guard, unlike the equivalent trade actuator. This can result in direct, unrecoverable loss of user funds (the injected `anotherTokenQuant` is deducted from the user's account with no way to bound it), which satisfies the "theft or permanent freezing of funds" bar via a single signed transaction from an unprivileged party.

### Likelihood Explanation
Exploitation only requires observing a pending `ExchangeInjectContract` in the mempool and submitting one or more `ExchangeTransactionContract` trades against the same `exchange_id` before it is packed into a block — the same "sandwich" front-running technique described in the referenced report, using the readily available `ExchangeTransactionActuator` trade path. No special privilege (SR/witness/committee) is required.

### Recommendation
Add an analog of the `expected` bound used in `ExchangeTransactionContract` to `ExchangeInjectContract` (e.g., a caller-supplied `max_another_token_quant`), and validate `anotherTokenQuant <= max_another_token_quant` in `ExchangeInjectActuator.doValidate()`/`execute()` before mutating balances, mirroring the check already present in `ExchangeTransactionActuator.doValidate()` [5](#0-4) .

### Proof of Concept
1. Attacker observes an unconfirmed `ExchangeInjectContract` from victim for `exchange_id=X`, `token_id=A`, `quant=Q_A` (pool currently at ratio `A:B`).
2. Attacker submits and gets confirmed (in an earlier block/position) an `ExchangeTransactionContract` trade against the same exchange that shifts the `A:B` ratio significantly (e.g., dumping `B` into the pool to raise the effective price of `A` in terms of `B`), using the unrestricted `ExchangeTransactionActuator` path [7](#0-6) .
3. Victim's `ExchangeInjectContract` then executes against the new ratio, so `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance` [8](#0-7)  is computed on the manipulated ratio and deducted from the victim without any check, since no `expected`/bound field exists on `ExchangeInjectContract` to abort or limit the deduction.
