## Title
`register_token` in `snowbridge-pallet-system-v2` embeds a caller-supplied `fee`/`amount` into the outbound message without ever collecting real funds, letting the fee be redeemed by relayers as an unbacked reward - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

### Summary
The Wormhole report's core defect is: a `payable` function that is *supposed* to forward a real fee payment (`msg.value`) into a downstream fee-charging call, but the wrapper never attaches or charges that fee — so the fee obligation is silently dropped/faked. The direct Polkadot SDK analog is `Pallet::register_token` in `snowbridge-pallet-system-v2`, which accepts a raw, caller-supplied `amount: u128` and forwards it straight into the `Message.fee` field of an outbound Snowbridge message — with no corresponding withdrawal, burn, or transfer of real assets from the caller. That fabricated `fee` is later paid out to relayers as a genuine reward once a delivery receipt is processed.

### Finding Description
`register_token` only checks the calling origin, then directly reuses the attacker-supplied `amount` as the message fee: [1](#0-0) 

Contrast this with the near-identical `register_token` extrinsic in the sibling `system-frontend` pallet, which *does* collect a real fee before building the message — it calls `Self::swap_fee_asset_and_burn(origin_location.clone(), fee_asset)?` to actually swap/burn a real `fee_asset` from the caller and only then uses the resulting `ether_gained` amount: [2](#0-1) 

In `system-v2::register_token`, there is no equivalent step. The private `send` helper simply wraps the untrusted `amount` into a `Message { fee, .. }` and hands it to `OutboundQueue::validate`/`deliver`: [3](#0-2) 

That message is enqueued and processed by `outbound-queue-v2::do_process_message`, which stores the attacker-chosen `fee` verbatim into `PendingOrder` keyed by nonce: [4](#0-3) 

When a relayer later submits a valid delivery receipt for that nonce, the pallet unconditionally pays out `order.fee` to the relayer via `T::RewardPayment::register_reward`, with no check that the fee was ever actually funded by the original caller: [5](#0-4) 

No guard anywhere in this path — `T::FrontendOrigin::ensure_origin`, `OutboundQueue::validate`, or `do_process_message` — verifies that `amount`/`fee` corresponds to funds withdrawn from, or burned by, the caller. `validate` only checks payload size: [6](#0-5) 

### Impact Explanation
This is a public-underpriced/unbacked-reward path with direct bridge-fund impact: any caller able to satisfy `T::FrontendOrigin` (an `EnsureOrigin<..., Success = Location>` derived from an XCM/location-based origin, not a signed account with real funds locked) can invoke `register_token` with an arbitrarily large `amount`, which becomes the relayer reward recorded in `PendingOrder`. Once a relayer supplies a valid Ethereum-side delivery receipt, `process_delivery_receipt` mints/credits that reward via `T::RewardPayment::register_reward` — value that was never actually withdrawn from any account. This is an unbacked payout mechanism analogous to the missing Wormhole fee payment, but inverted in effect: instead of the downstream call failing for lack of fee, the downstream reward succeeds despite lack of fee, causing theft/unbacked minting of relayer rewards from the bridge's reward pot.

### Likelihood Explanation
Likelihood depends on how permissive `T::FrontendOrigin` is configured in the live runtime (`bridge_to_ethereum_config.rs` in `bridge-hub-westend`). If it is scoped to a trusted single sovereign/XCM origin (e.g., AssetHub's sovereign account) this reduces to a privileged-actor issue and would be out of scope; I was not able to fully confirm the exact origin restriction within the available tool budget. However, the code path itself — as opposed to the trust boundary around `FrontendOrigin` — unconditionally lacks any fee-collection step compared to its `system-frontend` counterpart, which is a structural asymmetry independent of who exactly is allowed to call it.

### Recommendation
Mirror the `system-frontend::register_token` pattern in `system-v2::register_token`: before constructing the `Command::RegisterForeignToken` message, actually withdraw/burn a real `fee_asset` from the resolved `sender_location`/message origin (or otherwise cryptographically tie `amount` to funds already reserved for this specific nonce), and only pass the amount actually collected into `Self::send`. Additionally, `outbound-queue-v2::do_process_message`/`process_delivery_receipt` should not treat `PendingOrder.fee` as unconditionally payable without an accompanying on-chain record that those funds were reserved at message-submission time.

### Proof of Concept
1. Caller satisfies `T::FrontendOrigin` for BridgeHub's `snowbridge-pallet-system-v2` (e.g., via XCM from a sibling chain that maps to a valid `Location`).
2. Call `register_token(origin, sender, asset_id, metadata, amount = 1_000_000_000_000_000)` with an arbitrarily large `amount`, without holding or transferring any tokens for this amount anywhere in the call. [1](#0-0) 
3. The pallet builds `Message { fee: amount, .. }` and enqueues it; `do_process_message` stores `PendingOrder { fee: amount, .. }`. [4](#0-3) 
4. A relayer submits the delivery receipt for the resulting nonce; `process_delivery_receipt` pays the relayer `order.fee` (the full attacker-chosen `amount`) via `T::RewardPayment::register_reward`, even though no funds backing that `amount` were ever withdrawn from any account. [5](#0-4)

			origin: OriginFor<T>,
			sender: Box<VersionedLocation>,
			asset_id: Box<VersionedLocation>,
			metadata: AssetMetadata,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let sender_location: Location =
				(*sender).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;
			let asset_location: Location =
				(*asset_id).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;

			let location = Self::reanchor(asset_location)?;
			let token_id = TokenIdOf::convert_location(&location)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			if !ForeignToNativeId::<T>::contains_key(token_id) {
				ForeignToNativeId::<T>::insert(token_id, location.clone());
			}

			let command = Command::RegisterForeignToken {
				token_id,
				name: metadata.name.into_inner(),
				symbol: metadata.symbol.into_inner(),
				decimals: metadata.decimals,
			};

			let message_origin = Self::location_to_message_origin(sender_location)?;
			Self::send(message_origin, command, amount)?;

			Self::deposit_event(Event::<T>::RegisterToken {
				location: location.into(),
				foreign_token_id: token_id,
			});

			Ok(())
		}

		pub fn register_token(
			origin: OriginFor<T>,
			asset_id: Box<VersionedLocation>,
			metadata: AssetMetadata,
			fee_asset: Asset,
		) -> DispatchResult {
			ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted);

			let asset_location: Location =
				(*asset_id).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;
			let origin_location = T::RegisterTokenOrigin::ensure_origin(origin, &asset_location)?;

			let ether_gained = if origin_location.is_here() {
				// Root origin/location does not pay any fees/tip.
				0
			} else {
				Self::swap_fee_asset_and_burn(origin_location.clone(), fee_asset)?
			};

			let call = Self::build_register_token_call(
				origin_location.clone(),
				asset_location,
				metadata,
				ether_gained,
			)?;

			Self::send_transact_call(origin_location, call)
		}
