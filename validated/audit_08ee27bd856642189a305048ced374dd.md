## Finding

### Title
`configure_deleverage_withdrawal_limit` resets the daily window timestamp without resetting the accumulated counter, causing an unintended multi-hour freeze of deleverage withdrawals - ([File: programs/marginfi/src/instructions/marginfi_group/configure_withdrawal_limit.rs])

### Summary
This is a direct analog of the M-15 bug class: an admin-facing "configure the interval/limit" instruction mutates one piece of derived/cached window state but leaves a dependent cached counter stale, causing the enforcement logic that consumes that counter to behave incorrectly for an extended period.

### Finding Description
`configure_deleverage_withdrawal_limit` updates `daily_limit` and unconditionally resets `last_daily_reset_timestamp` to the current time, but never touches `withdrawn_today`: [1](#0-0) 

The daily-window enforcement logic in `MarginfiGroup` compares `withdrawn_today` against `daily_limit`, and only zeroes `withdrawn_today` when a full `DAILY_RESET_INTERVAL` has elapsed since `last_daily_reset_timestamp`: [2](#0-1) 

Because `configure_deleverage_withdrawal_limit` resets `last_daily_reset_timestamp` to "now" while leaving `withdrawn_today` at its previous (potentially large) value, two related failure modes exist, exactly mirroring the reported bug (partial/inconsistent update of interdependent cached state on a config-change path):

1. If the admin lowers `daily_limit` below the currently accumulated `withdrawn_today`, then `check_deleverage_withdraw_limit`/`update_withdrawn_equity` will immediately reject **every** subsequent deleverage withdrawal, because `withdrawn_today` (stale, still high) exceeds the new lower `daily_limit`, and the reset condition `current_timestamp - last_daily_reset_timestamp >= DAILY_RESET_INTERVAL` cannot fire because the timestamp was just reset to "now". This blocks the deleverage-withdraw safety mechanism for a full day from the moment of the config call, which is strictly worse than if the timestamp had been left untouched (the window would have reset naturally, sooner, based on its original start time).
2. Even where the admin does not intend to reduce risk-tolerance, touching `last_daily_reset_timestamp` on every config call artificially extends the "stuck" window duration compared to what would have occurred without this instruction being called at all — an unrelated config update inadvertently prolongs any pre-existing near-limit condition.

This is the same root-cause pattern as the Bond `setIntervals` issue: a threshold-comparison variable (`meta.tuneBelowCapacity` there, `withdrawn_today` here) is not kept consistent with a sibling piece of state (`tuneIntervalCapacity`/`tuneInterval` there, `last_daily_reset_timestamp`/`daily_limit` here) that is updated by the same admin instruction, so the downstream enforcement check (tuning logic there, `DailyWithdrawalLimitExceeded` gate here) misfires.

### Impact Explanation
The deleverage withdraw limit exists specifically as "a defense if the risk workflow is abused or compromised" (per the project's own guide), used during forced deleveraging of unhealthy accounts to cap USD outflow. Making it stall for up to `DAILY_RESET_INTERVAL` (a full day) after an ordinary, well-intentioned admin recalibration is a real functional/availability impact on a core risk-management path: unhealthy positions that were about to be deleveraged via `withdraw` in deleverage mode can no longer be unwound through this path, which is a lock/freeze of a protocol safety mechanism and can allow bad debt to accumulate during the frozen window. [3](#0-2) 

### Likelihood Explanation
This triggers deterministically any time `admin`/`delegate_limit_admin` calls `configure_deleverage_withdrawal_limit` while `withdrawn_today` is non-trivial (which is a normal operational condition, not an edge case) and the new limit is at or below the accumulated amount — a routine, expected admin operation (adjusting the daily cap in response to market conditions).

### Recommendation
When `configure_deleverage_withdrawal_limit` changes `daily_limit`, either (a) do not touch `last_daily_reset_timestamp` at all (let the existing window continue to decay/reset on its original schedule), or (b) if resetting the timestamp is intended, also reset `withdrawn_today` to `0` so the two fields stay consistent, matching the fix pattern used for the Bond issue (update all state that the threshold comparison depends on, atomically, in the same admin instruction).

### Proof of Concept
1. Admin sets `daily_withdrawal_limit = 1000`.
2. Over the day, deleverage withdrawals accumulate `withdrawn_today = 900` (via `update_withdrawn_equity`, called from `withdraw.rs`'s deleverage path).
3. Admin calls `configure_deleverage_withdrawal_limit(daily_withdrawal_limit = 500)` to tighten the cap in response to changing risk conditions.
4. This sets `daily_limit = 500` and `last_daily_reset_timestamp = now`, but `withdrawn_today` remains `900`.
5. Any subsequent deleverage withdraw calls `check_deleverage_withdraw_limit`, which computes `projected = withdrawn_today (900) + withdrawn_equity > daily_limit (500)` and returns `DailyWithdrawalLimitExceeded` for any nonzero withdrawal — even $1 — until a full `DAILY_RESET_INTERVAL` has elapsed from the admin's config call, not from the original window start.

    fn update_withdrawn_equity(
        &mut self,
        withdrawn_equity: I80F48,
        current_timestamp: i64,
    ) -> MarginfiResult {
        let projected =
            self.projected_deleverage_withdrawn_today(withdrawn_equity, current_timestamp);
        if current_timestamp.saturating_sub(
            self.deleverage_withdraw_window_cache
                .last_daily_reset_timestamp,
        ) >= DAILY_RESET_INTERVAL
        {
            self.deleverage_withdraw_window_cache.withdrawn_today = 0;
            self.deleverage_withdraw_window_cache
                .last_daily_reset_timestamp = current_timestamp;
        }
        self.deleverage_withdraw_window_cache.withdrawn_today = projected;

        // Note: treat zero limit as "no limit" here for backwards compatibility.
        if self.deleverage_withdraw_window_cache.daily_limit != 0
            && self.deleverage_withdraw_window_cache.withdrawn_today
                > self.deleverage_withdraw_window_cache.daily_limit
        {
            msg!(
                "trying to withdraw more than daily limit: {} > {}",
                self.deleverage_withdraw_window_cache.withdrawn_today,
                self.deleverage_withdraw_window_cache.daily_limit
            );
            return err!(MarginfiError::DailyWithdrawalLimitExceeded);
        }
        Ok(())
    }

    fn check_deleverage_withdraw_limit(
        &self,
        withdrawn_equity: I80F48,
        current_timestamp: i64,
    ) -> MarginfiResult {
        let projected =
            self.projected_deleverage_withdrawn_today(withdrawn_equity, current_timestamp);

        if self.deleverage_withdraw_window_cache.daily_limit != 0
            && projected > self.deleverage_withdraw_window_cache.daily_limit
        {
            msg!(
                "trying to withdraw more than daily limit: {} > {}",
                projected,
                self.deleverage_withdraw_window_cache.daily_limit
            );
            return err!(MarginfiError::DailyWithdrawalLimitExceeded);
        }

        Ok(())
    }
