## Analysis

The external report's core broken invariant: **a value-transfer wrapper trusts a boolean success return from an external token contract; if the contract doesn't return that boolean in the expected ABI shape, the wrapper treats a real, already-executed transfer as "failed," causing funds to become stuck** while the real balance movement already happened.

The local analog is `ERC20Transactor::withdraw_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`, which is the `pallet-revive`/ERC20 leg of the XCM `TransactAsset` used by `AssetHub` runtimes to let XCM move ERC20 tokens hosted on `pallet-revive` contracts.

### Title
Non-standard ERC20 token transfer confirmation via `abi_decode_returns_validate` can leave user funds permanently stuck in the XCM ERC20 checking account - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` performs a real on-chain ERC20 `transfer()` call (via `pallet_revive::Pallet::<T>::bare_call`) moving the user's tokens to the `TransfersCheckingAccount`, and only afterwards inspects the returned bytes with `IERC20::transferCall::abi_decode_returns_validate` to decide whether to mint XCM holding credit. If the token contract executes the transfer successfully but does not return an ABI-encoded `bool` (the well-known non-standard ERC20 pattern cited in the report, e.g. USDT/BNB/OMG-style tokens), decoding fails and the function returns `Err(XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode"))` without creating any `AssetsInHolding`.

### Finding Description [1](#0-0) 

The sequence is:
1. `bare_call` executes the actual `IERC20::transferCall` from `who` to the checking account — this is a real state-changing call on the target contract, moving the underlying token balance.
2. The code only checks `return_value.did_revert()` to detect an EVM-level revert.
3. If it didn't revert, it tries to `abi_decode_returns_validate` the return bytes as a `bool`. Non-standard tokens that transfer successfully but return no value (or a differently-shaped value) fail this decode step.
4. On decode failure, the function returns `Err(...)` with **no** `AssetsInHolding` created — i.e., the XCM executor is told the withdrawal failed and nothing is credited into holding.

Because step 1 already permanently moved the caller's real token balance into `TransfersCheckingAccount`, but step 4 tells the rest of the XCM program that no asset was withdrawn, the tokens are effectively locked in the checking account: there is no XCM holding credit to route them onward (to a beneficiary, to a destination chain, or back to the caller), and no mechanism in this transactor recovers or refunds them.

This precisely mirrors the reported bug class: code assumes a spec-compliant boolean return value from an ERC20 `transfer`, and real, non-standard tokens (which still execute the transfer but don't emit the expected boolean) break that assumption, with token movement already final by the time the check runs.

The existing regression test at `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:2019-2074` (`smart_contract_does_not_return_bool_fails`) demonstrates the exact scenario: a `MyTokenFake` contract implements `transfer` but returns a `uint256` instead of `bool`; the XCM `execute` call fails as expected — but the test only asserts `is_err()` on the overall XCM execution, it never asserts on the resulting balance of the checking account vs. the user, and does not show any recovery of the withdrawn tokens. [2](#0-1) 

### Impact Explanation
Any user attempting to move a non-standard ERC20 token (deployed on `pallet-revive`) through XCM via `ERC20Transactor` will have their tokens irreversibly transferred to the `TransfersCheckingAccount` while the XCM program aborts with an error and never credits any holding asset. This is a permanent user-fund lock — the token balance sits in the checking account indefinitely with no code path in this transactor to reclaim it, satisfying the "permanent user-fund or bridge-state lock" impact category. No malicious peer, validator, or governance actor is needed — this triggers on any unprivileged user's XCM execution against a legitimately deployed non-standard ERC20 contract.

### Likelihood Explanation
Non-standard ERC20 tokens that don't strictly return `bool` (or return nothing at all) are common in production (well documented precedent: USDT, BNB, OMG). Since `pallet-revive` is intended to host arbitrary Solidity/EVM-compatible contracts including third-party or ported ERC20 tokens, and the `ERC20Transactor` is the generic asset transactor wired into AssetHub-style XCM configs for any matched ERC20 asset, an unprivileged user only needs to route an XCM `WithdrawAsset` for such a token through this transactor to hit the bug. No attacker privilege or special conditions beyond deploying/using a non-boolean-returning ERC20 are required.

### Recommendation
Do not rely solely on ABI-decoding a `bool` return value to determine transfer success. Instead:
- Treat a non-reverting call with empty or non-decodable return data as success (matching the common "safe ERC20" convention used by OpenZeppelin's `SafeERC20`/`Address.functionCall` pattern — i.e., success is `!did_revert() && (data.is_empty() || decoded == true)`), or
- If the return value cannot be validated, perform a compensating action (query balance before/after via `balanceOf`) to determine whether the transfer actually occurred rather than assuming failure and stranding the already-moved funds, or
- Add an explicit recovery/rescue path for tokens stuck in `TransfersCheckingAccount` due to decode ambiguity.

### Proof of Concept
1. Deploy an ERC20-like `pallet-revive` contract whose `transfer(address,uint256)` performs the balance update but returns no value or a non-`bool` value (as in the existing `MyTokenFake` fixture at `substrate/frame/revive/fixtures/contracts/MyTokenFake.sol`).
2. From account `who`, submit an XCM program containing `WithdrawAsset` for that ERC20 asset via `PolkadotXcm::execute`, routed to `ERC20Transactor::withdraw_asset_with_surplus`.
3. Observe: `bare_call` executes `transferCall` on-chain, moving `who`'s tokens to `TransfersCheckingAccount` (this already succeeds and is irreversible).
4. `IERC20::transferCall::abi_decode_returns_validate` fails to decode the return data, causing `withdraw_asset_with_surplus` to return `Err(XcmError::FailedToTransactAsset(...))` with no `AssetsInHolding` created.
5. The overall XCM `execute` returns `Err` (as shown by `smart_contract_does_not_return_bool_fails`), yet `who`'s real ERC20 balance was already debited into `TransfersCheckingAccount` with no compensating credit or recovery path — the funds are stuck. [3](#0-2) [4](#0-3)
