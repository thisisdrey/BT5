### Title
Resubmitting known attachment content via POST /v2/transactions permanently un-serves an already-instantiated BNS attachment - (File: stackslib/src/net/atlas/db.rs)

### Summary
`AtlasDB::insert_uninstantiated_attachment` performs an unconditional `INSERT OR REPLACE` that resets `was_instantiated` to `0` for any hash, even if that hash already belongs to a confirmed, instantiated attachment. An unprivileged remote caller who resubmits the public bytes of an already-committed zonefile via `POST /v2/transactions` with a matching `ContractCall` attachment can flip that row back to uninstantiated, after which routine eviction permanently deletes the content while `attachment_instances.is_available` stays `1`.

### Finding Description
The claimed fault is: "`attachment_instances.is_available=1` no longer implies `attachments.hash=H` exists" once an attacker forces a re-insert-then-evict cycle. Tracing the code confirms this exactly.

`posttransaction.rs`'s `try_handle_request` accepts any `ContractCall` transaction with an attachment, checks `should_keep_attachment`, and if it passes, calls `insert_uninstantiated_attachment(attachment)` unconditionally: [1](#0-0) 

`insert_uninstantiated_attachment` does not check the current `was_instantiated` state before writing; it directly issues `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)`, which for an existing row with the same primary key (`hash`) unconditionally overwrites `was_instantiated` from `1` back to `0`: [2](#0-1) 

Once flipped to `0`, the row becomes eligible for deletion by either `evict_k_oldest_uninstantiated_attachments` (called automatically inside `insert_uninstantiated_attachment` itself when the uninstantiated count exceeds `max_uninstantiated_attachments`) or `evict_expired_uninstantiated_attachments`, both of which delete rows purely on `was_instantiated = 0`: [3](#0-2) 

Crucially, nothing in this path touches `attachment_instances.is_available`, which was set to `1` only once, at the time the name-operation was originally instantiated via `insert_instantiated_attachment`: [4](#0-3) 

After eviction, `find_attachment` -- which requires `was_instantiated = 1` -- returns `None` for a hash the chain still commits to: [5](#0-4) 

while the inventory/page-availability query (`get_attachments_available_at_page_index` / `get_attachments_missing_at_page_index`) still reports the bit as available because it only reads `attachment_instances.is_available`, not the `attachments` table: [6](#0-5) 

No guard in `should_keep_attachment`, `try_handle_request`, or `insert_uninstantiated_attachment` checks whether the hash is already `was_instantiated=1` before performing the destructive replace, so an attacker who simply knows the public zonefile bytes (already retrievable via any prior `GET /v2/attachments/<hash>` or from the chain itself) can trigger this with a single unauthenticated `POST /v2/transactions` plus normal node eviction cadence.

### Impact Explanation
This produces a durable state-serving mismatch: a name-registration that the burnchain/Stacks chain still canonically commits to becomes permanently un-resolvable via `GET /v2/attachments/<hash>` (`find_attachment` returns `None`/404), while `GET /v2/attachments/inventory` continues to report the corresponding page bit as available/resolved. This is a BNS attachment/inventory mismatch matching the "High" impact category (serving stale/incorrect resolution state vs. what is on-chain), affecting any peer that relies on this node's Atlas responses for that name. It is repeatable against any known attachment hash, and once the content is evicted, the effect is permanent for that hash on the affected node (the original bytes are gone from the `attachments` table).

### Likelihood Explanation
Preconditions: the target name-registration attachment must already be instantiated (`was_instantiated=1`, `is_available=1`) on the victim node -- a common, expected state for any resolved BNS name. The attacker needs no privileged role, secret, or peer key: `/v2/transactions` is an unauthenticated RPC endpoint reachable by any remote client, and the attachment bytes needed are public zonefile content, obtainable from the chain or via a normal attachment fetch. The only extra requirement is that eviction subsequently runs, which happens automatically as part of normal node operation (`insert_uninstantiated_attachment` triggers eviction inline when the uninstantiated-attachment cap is exceeded, and `evict_expired_uninstantiated_attachments` runs periodically). Attacker cost is a single crafted HTTP POST; the attack is trivially repeatable across many hashes.

### Recommendation
In `AtlasDB::insert_uninstantiated_attachment`, check the existing row's `was_instantiated` flag before writing (e.g. via `INSERT ... ON CONFLICT(hash) DO NOTHING WHERE was_instantiated = 0` or an explicit `SELECT was_instantiated FROM attachments WHERE hash = ?` guard), and skip/no-op the insert if the row already has `was_instantiated = 1`. Alternatively, change the SQL to `INSERT OR IGNORE` combined with only updating rows that are not already instantiated, so a resubmission of already-committed content can never regress `was_instantiated` from `1` to `0`.

### Proof of Concept
Rust test in `stackslib/src/net/atlas/tests.rs` (or extending existing tests there):
1. Create an in-memory `AtlasDB` (`AtlasDB::connect_memory_db`), construct an `Attachment` with bytes `B`, hash `H`.
2. Call `db.insert_instantiated_attachment(&attachment)` to simulate the on-chain-confirmed state (`was_instantiated=1`), and manually insert a matching `attachment_instances` row with `status = Checked`, `is_available` set to 0 initially then confirm it flips to `1` per `insert_instantiated_attachment`'s second `UPDATE`.
3. Call `db.insert_uninstantiated_attachment(&attachment)` with the same bytes `B` (simulating the duplicate-content POST /v2/transactions path), and assert the row's `was_instantiated` is now `0` (query `attachments` table directly).
4. Call `db.evict_k_oldest_uninstantiated_attachments(1)`.
5. Assert `db.find_attachment(&H) == Ok(None)` (404-equivalent) while `db.get_attachments_available_at_page_index(page_index, &block_id)` still reports the bit set to `1` for that attachment's index -- demonstrating the mismatch between servable content and reported inventory availability.

    pub fn get_attachments_available_at_page_index(
        &self,
        page_index: u32,
        block_id: &StacksBlockId,
    ) -> Result<Vec<u8>, db_error> {
        let page = self.get_attachments_missing_at_page_index(page_index, block_id)?;
        let mut bit_vector = vec![];
        for (_index, is_attachment_missing) in page.iter().enumerate() {
            // todo(ludo): use a bitvector instead
            bit_vector.push(if *is_attachment_missing { 0 } else { 1 });
        }
        Ok(bit_vector)
    }

    pub fn get_attachments_missing_at_page_index(
        &self,
        page_index: u32,
        block_id: &StacksBlockId,
    ) -> Result<Vec<bool>, db_error> {
        let min = page_index
            .checked_mul(AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE)
            .ok_or(db_error::Overflow)?;
        let max = min
            .checked_add(AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE)
            .ok_or(db_error::Overflow)?;
        let qry = "SELECT attachment_index, is_available FROM attachment_instances WHERE attachment_index >= ?1 AND attachment_index < ?2 AND index_block_hash = ?3 ORDER BY attachment_index ASC";
        let args = params![min, max, block_id,];
        let rows = query_rows::<(u32, u32), _>(&self.conn, qry, args)?;

        let mut bool_vector = vec![true; AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE as usize];
        for (attachment_index, is_available) in rows.into_iter() {
            let index = attachment_index % AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;
            let slot = bool_vector
                .get_mut(index as usize)
                .ok_or(db_error::NotFoundError)?;
            *slot = is_available == 0;
        }
        Ok(bool_vector)
    }

    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_k_oldest_uninstantiated_attachments(&mut self, k: u32) -> Result<(), db_error> {
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE hash IN (SELECT hash FROM attachments WHERE was_instantiated = 0 ORDER BY created_at ASC LIMIT ?)",
            params![k],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_expired_uninstantiated_attachments(&mut self) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let cut_off = now - self.atlas_config.uninstantiated_attachments_expire_after as i64;
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE was_instantiated = 0 AND created_at < ?",
            params![cut_off],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
