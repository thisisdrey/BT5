### Title
Block/standby witness rewards paid to a Super Representative are permanently lost when that witness's cycle-vote total is zero - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
This is the same bug class as the WrappedVault issue: rewards are added to a "pool" keyed by an entity (there, the vault's total-supply denominator; here, a witness's total-vote denominator for a reward cycle) *before* checking whether that denominator is non-zero. When the denominator is zero, the reward is silently dropped instead of being refunded or carried forward, and there is no owner/admin path to reclaim it.

### Finding Description
`MortgageService.payReward()` unconditionally credits block and transaction-fee rewards to a witness's per-cycle reward bucket via `delegationStore.addReward(cycle, witnessAddress, value)`, with no check on whether any TRX has been voted for that witness in that cycle. [1](#0-0) 

That reward is later supposed to be distributed to voters proportionally to their share of the witness's total votes. Under the legacy algorithm, `computeReward(cycle, votes)` explicitly skips distribution when the witness's recorded total vote for the cycle is zero (`totalVote == DelegationStore.REMARK || totalVote == 0`), meaning the reward already added via `addReward` is never handed to anyone. [2](#0-1) 

Under the new VI-based algorithm, the same pattern exists in `DelegationStore.accumulateWitnessVi()` and its equivalent in `RewardViCalService.accumulateWitnessVi()`: if `voteCount == 0` for the cycle, the code takes the "just forward preVi" branch and never folds the already-recorded `reward` into the vote-index (`Vi`) used to compute payouts, so the reward amount is permanently excluded from any voter's withdrawable balance. [3](#0-2) [4](#0-3) 

In both algorithms, the reward value stored via `addReward` for that (cycle, witness) pair is never consumed anywhere else in the codebase, and there is no owner/admin function analogous to the WrappedVault fix's "claim rewards sent to zero total-supply period" — the TRX is stuck in the delegation reward store forever.

### Impact Explanation
This results in a permanent freezing of TRX: rewards paid out by `payBlockReward`/`payTransactionFeeReward`/`payStandbyWitness` for a witness that has zero recorded votes in the cycle in which the reward is earned become unrecoverable by any account, and there is no mechanism in `MortgageService` or `DelegationStore` to reclaim or redirect them. This matches the "permanent freezing of funds" impact class accepted by the validation rules.

### Likelihood Explanation
A witness's per-cycle vote total (`getWitnessVote`) is snapshotted at maintenance boundaries by `MaintenanceManager` and can be zero for standby/witness slots that receive few or no votes (e.g., low-adoption private/test networks, or a witness whose voters fully withdraw votes around a cycle boundary). Any unprivileged account can trigger the vote-count-zero condition simply by unvoting a Super Representative through the standard vote/unvote transaction or TVM vote precompile path (`VoteRewardUtil`/`allowTvmVote`), which is reachable without special privilege. The witness continuing to receive block rewards while its vote count reads zero for that cycle is what causes the loss — this depends on network/vote conditions rather than a single attacker-controlled transaction, so likelihood is moderate rather than trivially exploitable on a healthy mainnet with many voters per witness.

### Recommendation
Mirror the accepted WrappedVault fix pattern: when a cycle's reward is added for a witness with zero recorded votes, either (a) do not accrue/lock the reward against that witness in the first place (defer/carry it forward transparently), or (b) provide an explicit reclaim/owner-redirect path (e.g., a governance/blackhole sweep of unattributed cycle rewards) so TRX is not permanently stranded in `DelegationStore`. Ensure both the legacy `computeReward` path and the new `accumulateWitnessVi` VI-based path are covered by this fix, since both independently drop zero-vote-cycle rewards.

### Proof of Concept
1. A Super Representative `W` is elected to the standby/active witness list for cycle `N` with vote count `V > 0` at the maintenance boundary.
2. Before/while blocks in cycle `N` are produced by `W`, all voters unvote `W` (standard `UnfreezeBalance`/`vote` withdrawal transaction, or via `VoteRewardUtil` TVM path), driving `W`'s tracked vote weight for the remainder of cycle `N` toward zero, or `W` receives its standby allowance in `payStandbyWitness` with individually zero votes while `voteSum` for the whole list is still ≥ 1 [5](#0-4) .
3. `Manager` continues to call `mortgageService.payBlockReward`/`payTransactionFeeReward` for `W`, crediting `delegationStore.addReward(N, W, value)`.
4. At the next maintenance run, `getWitnessVote(N, W)` returns 0 (or `REMARK`), so `computeReward`/`accumulateWitnessVi` skip distributing that reward to any voter.
5. No account — including the contract owner or DPoS governance — has any code path to withdraw or redirect the reward recorded under `(N, W)` in `DelegationStore`; the TRX is permanently unspendable.

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

```java
  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
```
