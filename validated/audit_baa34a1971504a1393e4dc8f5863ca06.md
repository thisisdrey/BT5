### Title
Unvalidated peer-advertised `data_url` enables SSRF-style outbound requests to internal/private addresses - ([File: stackslib/src/net/chat.rs])

### Summary
Stacks-core enforces private-IP filtering when connecting to *P2P* neighbor addresses (`can_register_peer`, `filter_sensible_neighbors`) and in the *mempool-sync* HTTP path (`mempool_sync_send_query`), but the peer-advertised HTTP `data_url` carried in the `Handshake`/`HandshakeAccept` payload — consumed by Atlas attachment sync, StackerDB replica sync, and the Nakamoto tenure downloader — is resolved and dialed with **no equivalent private-range check**.

### Finding Description
`ConversationP2P::update_from_handshake_data` blindly copies the remote peer's self-reported `data_url` from `HandshakeData` into `self.data_url` with no validation: `stackslib/src/net/chat.rs:1129-1147`. This URL is later resolved to a `SocketAddr` in `try_resolve_data_url` (`stackslib/src/net/chat.rs:2805-2914`), which parses literal IPv4/IPv6 addresses directly or performs a DNS lookup — at no point checking `PeerAddress::is_in_private_range()` (which is defined in `stacks-common/src/types/net.rs:201-213` and is the exact guard used elsewhere).

That resolved `data_ip`/`data_url` pair is then used, unchecked, to originate outbound HTTP connections in multiple in-scope subsystems:
- `NeighborRPC::send_request` / `get_peer_host` (`stackslib/src/net/neighbors/rpc.rs:182-249`) — used by the Nakamoto tenure downloader (`stackslib/src/net/download/nakamoto/tenure_downloader.rs:708-751`) to dial `convo.data_ip` directly via `http.connect_http(...)`.
- Atlas's `AttachmentsDownloader` (`stackslib/src/net/atlas/download.rs:115-124`) via `network.get_data_url(&peer)` (`stackslib/src/net/download/epoch2x.rs:1060-1075`), which is then handed to `PeerNetwork::connect_or_send_http_request` (`stackslib/src/net/httpcore.rs:1877-1911`) with no filtering.
- StackerDB sync's replica discovery (`stackslib/src/net/stackerdb/sync.rs:85-170`) — note this path *does* filter `hint_replicas`/DB-discovered `NeighborAddress` entries for private ranges (line 119-123), but that filtering is on the *P2P* address, not on the HTTP `data_url` that is actually dialed for chunk transfer.

By contrast, two comparable code paths *do* enforce the guard:
- `PeerNetwork::filter_sensible_neighbors` / `can_register_peer` (`stackslib/src/net/p2p.rs:1917-1924`, `stackslib/src/net/neighbors/walk.rs:584-594`) for P2P neighbor addresses.
- `MemPoolSync::mempool_sync_send_query`'s caller (`stackslib/src/net/mempool/mod.rs:485-498`), which explicitly checks `PeerAddress::from_socketaddr(addr).is_in_private_range()` before dialing the peer's `data_url`.

This asymmetry means the equality "every outbound HTTP dial target must pass the same private-range policy" is broken specifically for the `data_url` used by Atlas/StackerDB/tenure-download HTTP fetches.

### Impact Explanation
Any remote, unprivileged peer that completes a normal (unauthenticated-by-key) P2P handshake can advertise an arbitrary `data_url` (e.g., pointing at loopback, RFC1918 ranges, or other internal-only services reachable from the victim node's network position). The victim node will then autonomously issue outbound HTTP GET requests to that address as part of its ordinary attachment/StackerDB/tenure sync workflows — a classic SSRF primitive, directly analogous to the reported `api-lab-mcp` SSRF (attacker-controlled `url`/`source` driving an outbound fetch). This can be used to probe/interact with internal services from the node's vantage point that are not otherwise reachable by the attacker, and — because the same `private_neighbors`-style toggle exists elsewhere but isn't applied here — represents an inconsistency in a security boundary that the codebase clearly intends to enforce uniformly.

### Likelihood Explanation
High likelihood of reachability: no special privileges, keys, or admin role are required — only a completed handshake, which is the baseline for any inbound/outbound P2P peer. The `data_url` field is fully attacker-controlled free text (`UrlString`), and its resolution/dial path performs no allowlist/denylist check unlike the sibling mempool-sync path.

### Recommendation
Apply the same `PeerAddress::is_in_private_range()` (gated by `connection_opts.private_neighbors`, consistent with `can_register_peer` and `mempool_sync_send_query`) check to the resolved `data_ip`/`data_url` before it is used in `try_resolve_data_url` (chat.rs), `NeighborRPC::send_request`/`get_peer_host` (neighbors/rpc.rs), and `AttachmentsDownloader`'s use of `network.get_data_url` (atlas/download.rs), so that a peer cannot direct the node's outbound HTTP client at internal/private targets unless `private_neighbors` is explicitly enabled.

### Proof of Concept
1. Attacker runs a Stacks node/peer and completes a normal P2P handshake with the victim node, setting `HandshakeData.data_url` to `http://127.0.0.1:<victim-internal-port>/...` or another private-range target reachable from the victim's network (e.g., `http://169.254.169.254/`, `http://10.x.x.x:.../`).
2. Victim's `ConversationP2P::update_from_handshake_data` stores this `data_url` unchecked (`chat.rs:1147`).
3. When the victim's Atlas downloader, StackerDB sync, or Nakamoto tenure downloader next needs data from this peer, it calls `get_data_url`/`get_peer_host` and dials the attacker-chosen address via `connect_or_send_http_request` / `connect_http`, issuing a real outbound HTTP GET originating from the victim node to the attacker-chosen internal target — with no private-range rejection, unlike the mempool-sync path which would reject the same address.

**Note on uncertainty**: I could not execute this against a live node within the tool sandbox, so the PoC above is a code-path walkthrough rather than an observed live exploit; the conclusion rests on the absence of the `is_in_private_range()` guard in the cited call chains versus its presence in the sibling `mempool_sync`/`can_register_peer` paths, which I verified directly in the source.
