### Title
Uninitialized `accountIndexOf` treated as zero accrues attacker rewards equal to full token balance - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
The reported bug class is *use of an uninitialized resource*: memory/state is consumed as if it were initialized. In `RewardsDistributor`, `accountIndexOf[token][account]` defaults to `0` for any account that has never accrued. `_calculateTokenDelta()` only substitutes the `INITIAL_INDEX` fallback when the current token index is *strictly greater* than `INITIAL_INDEX`. While the token index is still exactly `INITIAL_INDEX` — which is always true in the block the reward speed is set, and remains true whenever the per-second accrual ratio rounds to zero — an uninitialized account index produces `_deltaIndex = INITIAL_INDEX - 0 = 1e18`, crediting the account `balanceOf(account)` reward tokens out of thin air. [1](#0-0) 

### Finding Description
- `_updateTokenSpeed()` registers a new reward token with `TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` where `INITIAL_INDEX = 1e18`. [2](#0-1) 
- `_calculateTokenIndex()` returns `_newIndex = index + _ratio`; `_ratio` is `0` when `totalSupply == 0` or when `_tokensAccrued.wadDiv(_totalSupply)` rounds to `0` (small speed, large supply, short elapsed time). The index can therefore remain pinned at `INITIAL_INDEX` for an arbitrary number of blocks. [3](#0-2) 
- `_calculateTokenDelta()` reads `accountIndexOf[token_][account_]` — `0` for any holder who has never accrued (e.g., everyone holding the DepositToken before the distributor was registered). The guard `if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX)` fails when `_tokenIndex == INITIAL_INDEX`, so `_accountIndex` stays `0` and `_deltaIndex = 1e18 - 0 = 1e18`. Then `_tokensDelta = balanceOf(account_).wadMul(1e18) = balanceOf(account_)`. [4](#0-3) 
- Both entry points are reachable by an unprivileged attacker: `updateBeforeMintOrBurn(token_, account_)` is explicitly permissionless ("may be called by anyone to update stored indexes"), and `claimRewards(accounts_, tokens_)` is public and `nonReentrant` only. Neither checks `onlyIfTokenExists`, `onlyIfDistributorExists`, pause, or shutdown — those modifiers only exist on `_updateTokenSpeed`. [5](#0-4) [6](#0-5) 
- `_transferRewardIfEnoughTokens()` pays out the full accrued amount whenever the distributor holds enough reward tokens, silently capping at the contract balance. [7](#0-6) 

The uninitialized-slot analog of the `alg_ds` bug is exact: a zero/default value (`accountIndexOf == 0`) is used in place of a properly initialized index (`INITIAL_INDEX`), and the partial initialization guard fails precisely on the boundary condition.

### Impact Explanation
Each trigger credits `tokensAccruedOf[attacker] += depositToken.balanceOf(attacker)` reward tokens (e.g., MET, OP) with zero elapsed time and zero legitimate accrual. The attacker can (a) sandwich the governor's `updateTokenSpeed` transaction in the same block, (b) act in any later block where the index is still `INITIAL_INDEX` due to ratio rounding to zero, and (c) amplify `balanceOf` by depositing a large amount of collateral in the same transaction before calling `updateBeforeMintOrBurn`. Although a given account can only exploit the zero index once per token, the attacker can repeat across many fresh accounts and across every registered reward token, draining the distributor's entire reward-token balance — i.e., theft of all users' unclaimed yield. This satisfies "theft of unclaimed yield" / direct theft of funds.

### Likelihood Explanation
Requires a reward token whose index is currently `INITIAL_INDEX`. The same-block window after each `updateTokenSpeed` call is guaranteed (delta timestamps is 0, so `_updateTokenIndex` writes nothing and `_calculateTokenDelta` still runs against the stored `INITIAL_INDEX`). Front-running/observing the governor transaction suffices, and additional windows open whenever `delta * speed` accrual rounds to zero against a large total supply. No privileged role, oracle manipulation, or special deployment state is needed — only public entry points and a DepositToken/DebtToken balance, which can be obtained via `Pool.deposit` in the same transaction.

### Recommendation
In `_calculateTokenDelta()`, treat an uninitialized account index as "no accrual yet" whenever the token index is `<= INITIAL_INDEX`, i.e. clamp `_accountIndex` to `_tokenIndex` (or `INITIAL_INDEX`) rather than only when `_tokenIndex > INITIAL_INDEX`:

```solidity
if (_accountIndex == 0 || _accountIndex > _tokenIndex) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? _tokenIndex : INITIAL_INDEX;
}
```

Equivalently, return `tokensDelta = 0` for `_accountIndex == 0 && _tokenIndex <= INITIAL_INDEX`. Additionally, consider setting `accountIndexOf` for existing holders at registration time or requiring `_tokenIndex >= INITIAL_INDEX` invariant checks in `updateBeforeMintOrBurn`/`updateBeforeTransfer`.

### Proof of Concept
Hardhat test sketch (repo already contains `test/RewardDistributor.test.ts` harnesses):

```typescript
// setup: pool, depositToken (e.g. msUSD deposit token), distributor (RewardsDistributor),
// rewardToken funded into distributor: rewardToken.mint(distributor.address, ethers.parseEther("1000000"))

// 1. attacker deposits to get a depositToken balance (can be same tx via multicall)
await depositToken.deposit(attacker.address, parseEther("50000"));

// 2. governor registers reward speed (attacker sandwiches in same block, or waits while index==1e18)
await distributor.connect(governor).updateTokenSpeed(depositToken.address, parseEther("0.01"));

// 3. same block: permissionless index update -> uninitialized accountIndexOf == 0
await distributor.connect(attacker).updateBeforeMintOrBurn(depositToken.address, attacker.address);

// 4. accrued == full depositToken balance despite zero elapsed accrual
const accrued = await distributor.tokensAccruedOf(attacker.address);
expect(accrued).to.eq(await depositToken.balanceOf(attacker.address)); // 50000e18

// 5. drain distributor
const balBefore = await rewardToken.balanceOf(attacker.address);
await distributor.connect(attacker)["claimRewards(address)"](attacker.address);
expect(await rewardToken.balanceOf(attacker.address)).to.eq(balBefore + accrued);
```

Key assertions: `tokenStates[depositToken].index == 1e18` after step 2 (delta timestamps 0 keeps `_updateTokenIndex` a no-op, but `_updateTokensAccruedOf` still executes), and `accountIndexOf[attacker] == 0` before step 3, producing `_deltaIndex = 1e18` and `tokensDelta = balanceOf`.

        IERC20 token_
    ) private view returns (uint224 _newIndex, uint32 _newTimestamp) {
        uint256 _speed = tokenSpeeds[token_];
        uint256 _deltaTimestamps = block.timestamp - uint256(_supplyState.timestamp);

            _newTimestamp = block.timestamp.toUint32();

            _newTimestamp = block.timestamp.toUint32();
        }
    }
