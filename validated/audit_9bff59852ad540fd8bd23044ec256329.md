### Title
Front-runnable PDA seed using unchecked `new_authority` allows griefing/DoS of `transfer_to_new_account_pda` - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
`TransferToNewAccountPda` derives the destination `new_marginfi_account` PDA using `new_authority.key()` as a seed, but `new_authority` is an `UncheckedAccount` that is never required to sign the instruction. This mirrors the pump-science `lock_escrow` bug class: a PDA whose address depends on a pubkey that is not the signer of the instruction that `init`s it, letting a third party create that account ahead of time and block the intended transaction.

### Finding Description
The account struct explicitly marks the risk: [1](#0-0) 

`new_marginfi_account` is `init`ed with `seeds = [MARGINFI_ACCOUNT_SEED, group.key(), new_authority.key(), account_index, third_party_id]`, and `new_authority` is annotated `/// CHECK: WARN: New authority is completely unchecked` and typed `UncheckedAccount`, not `Signer`. [2](#0-1) 

Because the same seed formula is used deterministically (`group`, `new_authority`, `account_index`, `third_party_id`), and because `new_authority` does not need to sign, anyone who observes a pending `transfer_to_new_account_pda` transaction (e.g., in the mempool) can pre-empt it: they submit their own `transfer_to_new_account_pda` (or equivalent flow) using the same `group`/`new_authority`/`account_index`/`third_party_id` tuple but with their own `old_marginfi_account` and `authority` as the signer, creating the target PDA first with attacker-controlled data. When the legitimate transaction lands, Anchor's `init` constraint fails because the account already exists ("already in use"), causing the intended transfer to revert.

This is the same root cause pattern as the external report: a PDA is derived from a pubkey that plays no cryptographic role (no signature requirement) in the instruction that creates it, enabling front-running/DoS of that specific instruction and address.

### Impact Explanation
If a griefer front-runs this specific seed combination, the legitimate `authority` cannot complete their intended migration of `old_marginfi_account` to that exact `(group, new_authority, account_index, third_party_id)`-derived address; the whole transaction reverts, and the old account is left untouched (no fund loss, no unauthorized transfer). This is a denial-of-service against a specific instruction/address rather than a full protocol DoS, because `account_index` is a `u16` chosen by the caller — a legitimate user can retry with a different `account_index` to obtain a fresh, uncollided PDA. This significantly reduces severity relative to the pump-science original (where `lock_escrow`'s seeds are fixed per pool with no alternative), since there is no protocol-wide bottleneck here — only a specific, avoidable address can be griefed. Impact is best classified as low/medium griefing, unless an integrator's off-chain flow depends on a fixed, non-negotiable `account_index`/`third_party_id` for a given `new_authority` (e.g., a hardcoded third-party integration), in which case the block could be effectively permanent for that specific flow.

### Likelihood Explanation
Requires the attacker to observe or predict the exact `(group, new_authority, account_index, third_party_id)` tuple of a pending transaction and to have their own valid `old_marginfi_account`/authority to submit a competing instruction before the legitimate one lands — feasible via mempool sniping on Solana, though limited to griefing a specific target rather than a systemic exploit.

### Recommendation
Require `new_authority` to be a signer on `TransferToNewAccountPda` (consistent with `MarginfiAccountInitializePda`, where `authority: Signer<'info>` is required), or otherwise validate that the caller who benefits from the new PDA has actually consented, so that arbitrary parties cannot pre-create the destination PDA on someone else's behalf.

### Proof of Concept
1. Attacker monitors mempool for a pending `transfer_to_new_account_pda` transaction with parameters `(group=G, new_authority=NA, account_index=I, third_party_id=T)`.
2. Attacker submits their own `transfer_to_new_account_pda` transaction with the same `(G, NA, I, T)`, using their own `old_marginfi_account` and signing as `authority` — this is permitted because `new_authority` (NA) does not need to sign, only `authority` (attacker's own key) does: [2](#0-1) 
3. Attacker's transaction lands first, `init`ing the PDA at the address derived from `(G, NA, I, T)`.
4. The victim's original transaction now fails at the `init` constraint on `new_marginfi_account` because the account already exists.
