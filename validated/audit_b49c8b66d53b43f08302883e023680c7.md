### Title
Unchecked integer overflow in TRC10/TRX pool balance arithmetic when exchange hardening is disabled - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()` computes new bancor-style pool balances with plain `long` arithmetic (`firstTokenBalance + sellTokenQuant`, `secondTokenBalance - buyTokenQuant`) whenever the chain-wide flag `ALLOW_HARDEN_EXCHANGE_CALCULATION` is not enabled, which is its default value (`0`). This mirrors the reported solana_rbpf pattern: a value taken from attacker-influenced input (`sym.st_value` there, `sellTokenQuant`/pool balances here) is added/subtracted without any overflow check, silently wrapping instead of failing. [1](#0-0) 

### Finding Description
`ExchangeCapsule.transaction(sellTokenID, sellTokenQuant, useStrictMath, hardenedCalc)` selects between `SafeExchangeProcessor` (overflow-checked) and the legacy `ExchangeProcessor` based on `hardenedCalc`, which is threaded from `AbstractExchangeActuator.allowHarden()` → `chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation()`. [2](#0-1) 

When `hardenedCalc` is `false` (the default, un-proposed state), the new balances are computed as:
```
newFirstTokenBalance = firstTokenBalance + sellTokenQuant;
newSecondTokenBalance = secondTokenBalance - buyTokenQuant;
```
with no `addExact`/`subtractExact` and — critically — the post-condition check `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) throw ...` is only executed **when hardened**, so in the default (non-hardened) path an overflowed/negative balance is written straight to the `ExchangeCapsule` and persisted via `Commons.putExchangeCapsule(...)`. [3](#0-2) 

This is reachable directly from `ExchangeTransactionActuator.execute()`, which any account can invoke by broadcasting an `ExchangeTransactionContract` naming an existing exchange pair and a `quant`: [4](#0-3) 

The `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal parameter defaults to `0` and its getter falls back to `0L` when unset: [5](#0-4)  and the enum comment for `ALLOW_HARDEN_EXCHANGE_CALCULATION(98)` documents a default of `0`. [6](#0-5) 

The project's own test suite explicitly demonstrates that in the default (non-hardened) mode a near-`Long.MAX_VALUE` pool balance plus an injected/sold quantity silently overflows without exception, whereas the hardened path throws `ArithmeticException`: [7](#0-6)  and the analogous `ExchangeInjectActuator` test. [8](#0-7) 

### Impact Explanation
If a pool balance can be driven close to `Long.MAX_VALUE` (e.g., via repeated `ExchangeInjectActuator` calls by the exchange owner, or by initial `ExchangeCreateActuator` parameters, both attacker-controlled inputs of a single signed transaction), a subsequent trade wraps the balance to a negative or arbitrarily small/large value. Because the exchange price/quantity math (`ExchangeProcessor`) and downstream asset/TRX transfers derive from these balances, a wrapped balance can let an attacker withdraw more assets than the pool actually holds (unbacked balance / theft of pooled TRX or TRC10 tokens) or permanently corrupt/freeze the exchange pool's accounting. This satisfies the "unbacked balance / theft of funds" acceptance criteria.

### Likelihood Explanation
Reaching `Long.MAX_VALUE`-scale balances requires the pool to first accumulate an extreme balance, which normal validation flows constrain (e.g., token-balance limit checks noted in the actuator test suite, such as "token balance must less than 1000000000000000"). I was not able to fully verify, within the available tool budget, whether `ExchangeCreateActuator`/`ExchangeInjectActuator` validation universally caps all pool balances (both TRX and every TRC10 token) below the overflow threshold, or whether any code path (e.g., repeated injections, precision/decimal edge cases, or TRX itself, which is not a TRC10 token and may not be subject to the same "< 1e15" cap) allows a balance to approach the overflow boundary. This is a material uncertainty affecting practical exploitability, and it should be confirmed by reading the full `doValidate()` of `ExchangeCreateActuator`/`ExchangeInjectActuator`/`ExchangeTransactionActuator` before treating this as fully proven.

### Recommendation
Default `ALLOW_HARDEN_EXCHANGE_CALCULATION` to enabled (or unconditionally route `ExchangeCapsule.transaction()` through `SafeExchangeProcessor`/`StrictMathWrapper.addExact`/`subtractExact` regardless of the flag), and make the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` invariant check unconditional rather than gated on `hardenedCalc`, so overflow or balance-underflow always throws `ContractValidateException`/`ArithmeticException` instead of silently persisting a corrupted balance.

### Proof of Concept
Not independently reproduced end-to-end due to tool budget exhaustion before confirming whether existing balance caps in `ExchangeCreateActuator`/`ExchangeInjectActuator` validation prevent reaching the overflow threshold in practice. The repository's own hardened-mode regression tests demonstrate the underlying overflow mechanics precisely: [9](#0-8)  shows `ExchangeCapsule.transaction()` silently wraps when hardening is off and only throws when hardening is explicitly enabled, confirming the vulnerable default-path arithmetic exists and is exercised via `ExchangeTransactionActuator`/`ExchangeInjectActuator`, both callable by any account via a signed `ExchangeTransactionContract`/`ExchangeInjectContract`.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  /**
   * Hardened mode: corrupt pool with near-MAX balance triggers ArithmeticException
   * from addExact. Demonstrates the overflow-detection guard fires and is not
   * silently swallowed.
   */
  @Test
  public void hardenedExecuteOverflowThrowsArithmeticException() throws Exception {
    dbManager.getDynamicPropertiesStore().saveAllowSameTokenName(1);
    dbManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(1);
    InitExchangeSameTokenNameActive();

    long exchangeId = 1;
    // Corrupt pool to near-MAX TRX so addExact overflows when buying.
    ExchangeCapsule pool = dbManager.getExchangeV2Store().get(ByteArray.fromLong(exchangeId));
    pool.setBalance(Long.MAX_VALUE - 5L, 10_000_000L);
    dbManager.getExchangeV2Store().put(pool.createDbKey(), pool);

    String tokenId = "_";
    long quant = 100L;
    ExchangeTransactionActuator actuator = new ExchangeTransactionActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_SECOND, exchangeId, tokenId, quant, 1));

    try {
      // addExact throws ArithmeticException, which is wrapped into ContractExeException.
      Assert.assertThrows(ContractExeException.class,
          () -> actuator.execute(new TransactionResultCapsule()));
    } finally {
      dbManager.getExchangeStore().delete(ByteArray.fromLong(1L));
      dbManager.getExchangeStore().delete(ByteArray.fromLong(2L));
      dbManager.getExchangeV2Store().delete(ByteArray.fromLong(1L));
      dbManager.getExchangeV2Store().delete(ByteArray.fromLong(2L));
      dbManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);
    }
  }
}
