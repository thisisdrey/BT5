### Title
Unvalidated array-length fields in TVM precompile calldata parsing allow uncontrolled `byte[len][]` allocation, crashing the node - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read an attacker-controlled length word from ABI-encoded calldata via `DataWord.intValueSafe()` and immediately use it to allocate a nested array (`new byte[len][]`) before any bound check against the remaining calldata size.

### Finding Description
`extractBytes32Array` and `extractBytesArray` take `len = words[offset].intValueSafe()` directly from the transaction/contract-call payload and use it to size a `byte[len][]` allocation: [1](#0-0) [2](#0-1) 
`extractSigArray` follows the same unchecked pattern: [3](#0-2) 

`intValueSafe()` clamps overflowed values to `Integer.MAX_VALUE` rather than rejecting them: [4](#0-3) 

This is the same bug class as CVE-2017-13144: a size/length field taken from untrusted input is used to allocate memory before the corresponding "declared size vs. actual available data" check is performed, so instead of a controlled validation error the process crashes (here via `OutOfMemoryError`/`NegativeArraySizeException`-class failures during allocation) rather than a graceful rejection.

I was only able to confirm the definitions of these helper methods within my available search budget; I could not fully trace every call site (e.g., which specific precompiled contract(s) beyond `batchValidateSign`/`validateMultiSign`/shielded-transaction verifiers invoke `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, and whether any caller pre-validates `len` against `words.length` before invoking these helpers). This should be verified with a full grep across `PrecompiledContracts.java` for all callers of these three methods, since the presence or absence of a caller-side check materially affects exploitability.

### Impact Explanation
If a value like `len = Integer.MAX_VALUE` (achievable by supplying a length word larger than 4 bytes, or a large value directly, since only `bytesOccupied > 4` triggers the safe clamp) reaches `new byte[len][]`, the JVM will throw `OutOfMemoryError` while attempting to allocate an array of that size. Given `OutOfMemoryError` is a `Throwable`/`Error`, not a checked `Exception`, it is not guaranteed to be caught by the same defensive layers that catch `ContractValidateException`/`ContractExeException` inside actuators, and can propagate to crash node threads or destabilize the JVM, denying block/transaction processing for the whole node — a crash of a production, publicly reachable path (any account can call a TVM contract that reaches this precompile logic).

### Likelihood Explanation
Reaching this code only requires deploying/triggering a contract that calls one of the precompiled contracts that use these helpers (e.g., shielded-TRC20 verification precompiles gated by `VMConfig.allowShieldedTRC20Transaction()`, or `batchValidateSign`/`validateMultiSign` gated by `VMConfig.allowTvmSolidity059()`), which are standard, unprivileged, reachable entry points for any transaction broadcaster. However, exploitability depends on config flags being enabled on the target network and on whether upstream code already bounds `len` before calling these helpers — a detail I could not fully verify given the tool budget.

### Recommendation
Add an explicit upper bound check on `len` derived from calldata immediately after `intValueSafe()` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` — e.g., reject if `len` is negative, absurdly large, or inconsistent with the remaining `words.length`/`data.length`, returning an empty array or throwing a normal `PrecompiledContractException`/validation failure instead of proceeding to allocate.

### Proof of Concept
Conceptual PoC (needs confirmation against the concrete caller): craft calldata for a precompiled contract that internally calls `extractBytesArray`/`extractBytes32Array` where the length word at `words[offset]` decodes (via `intValueSafe()`) to a very large positive integer (up to `Integer.MAX_VALUE`), causing `new byte[len][]` to attempt to allocate roughly 8–16 GB of pointers, triggering `OutOfMemoryError` on the executing node during transaction validation/execution.

  /**
   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()
   */
  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }
