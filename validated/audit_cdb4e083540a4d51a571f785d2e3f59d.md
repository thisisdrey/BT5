### Title
Stale zero-cost entries accumulate in `cost_by_writable_accounts` because `sub_transaction_execution_cost` never removes zeroed entries, unlike `roll_back_applied_costs` - ([File: cost-model/src/cost_tracker.rs])

### Summary
`CostTracker::sub_transaction_execution_cost` (used by both `remove_transaction_cost`/`remove` and the post-execution cost-adjustment path invoked from `consumer.rs`) always does `entry(...).or_insert(0)` followed by `saturating_sub`, but unlike `roll_back_applied_costs`, it never calls `entry.remove()` when the resulting value reaches zero. This leaves permanent zero-valued entries in `cost_by_writable_accounts` for every distinct writable account an attacker's transactions touch, even after those transactions are fully removed from the tracker.

### Finding Description
`try_add` inserts/updates an account's cost via `Entry::Occupied`/`Entry::Vacant` logic [1](#0-0) . When a transaction is later removed (e.g. dropped from the block, or its actual execution cost differs from the reserved cost and `consumer.rs` calls the adjustment path), `remove_transaction_cost` calls `sub_transaction_execution_cost`: [2](#0-1) 

This function unconditionally does `entry(*account_key).or_insert(0)` and then `saturating_sub`, but never removes the entry from the map even when the resulting cost is `0`. This is in contrast to `roll_back_applied_costs`, used only in the `try_add` failure path, which explicitly removes zero-valued entries: [3](#0-2) 

The repo's own test `test_try_add_rollback_removes_zeroed_entries` demonstrates the asymmetry directly: after `testee.remove(&tx_cost)` for a single-account transaction, the entry for `zeroed` remains in the map with value `0` (`assert_eq!(Some(&0), testee.cost_by_writable_accounts.get(&zeroed))`), and it is only cleaned up later as a side effect of a *different* transaction's rollback touching the same key: [4](#0-3) 

`find_number_of_contended_accounts` and `find_costliest_account` iterate the whole map (including zeroed entries) each time a transaction is added, and `number_of_accounts` filters zero-valued entries out for reporting purposes only - it does not clean the underlying map [5](#0-4) . There is no capping/pruning of `cost_by_writable_accounts` size anywhere; `WRITABLE_ACCOUNTS_PER_BLOCK = 4096` is only used as the initial `HashMap` capacity hint [6](#0-5) [7](#0-6) , not an enforced limit.

An attacker who gets many transactions accepted into the cost tracker - each referencing a distinct throwaway writable account - and then has those transactions removed (dropped after failing later pipeline stages, or via the actual-cost adjustment down to a lower value in `consumer.rs`, or via replay/QoS bumping-out) will leave that account's zero-cost entry permanently resident in the `HashMap` for the remainder of the slot's `CostTracker` lifetime.

### Impact Explanation
This causes `cost_by_writable_accounts` to grow with the number of distinct accounts an attacker manages to get into the cost tracker and then remove, independent of `block_cost` (their net cost contribution is exactly zero). Every `try_add` call additionally does `O(map size)` work in `find_costliest_account`/`find_number_of_contended_accounts` (called from `report_stats`, not per-`try_add`, so this is bounded to once per report) — the primary concrete impact is unbounded (within a slot) HashMap growth as byproduct of legitimate, replayable accounting churn, matching an "ingress buffers and scheduler containers stay bounded" invariant violation as scoped in the question. Because a fresh `CostTracker` is created per slot (`new_from_parent_limits`), the practical growth window is bounded to a single slot's transaction-processing lifetime, which limits severity, but within that window the map can retain far more entries than `WRITABLE_ACCOUNTS_PER_BLOCK` implies is expected.

### Likelihood Explanation
Reachability requires the attacker to get transactions accepted by `try_add` (i.e., pass sigverify/QoS/fee-payer checks like any normal transaction) and then have them removed via the normal `remove`/cost-adjustment path used in `consumer.rs`. This is a realistic, repeatable path for any unstaked client submitting many small, distinct-account transactions that are later dropped or whose actual execution cost is adjusted downward, which happens routinely in normal cluster operation (not just as an attack) — so the precondition is easily met and highly repeatable within a slot.

### Recommendation
Make `sub_transaction_execution_cost` symmetric with `roll_back_applied_costs`: after computing the new saturated cost for each account, remove the entry from `cost_by_writable_accounts` if it reaches `0`, instead of leaving a zero-valued `Occupied` entry (or an `or_insert(0)`-created entry) in the map.

### Proof of Concept
```rust
// cost-model/src/cost_tracker.rs (tests module)
#[test]
fn test_remove_leaves_stale_zero_entries() {
    let cost = 100u64;
    let mut testee = CostTracker::new(u64::MAX, u64::MAX);

    let m = 1000;
    let mut costs = Vec::with_capacity(m);
    for _ in 0..m {
        let key = Pubkey::new_unique();
        let transaction = WritableKeysTransaction::new(vec![key]);
        let tx_cost = simple_transaction_cost(&transaction, cost);
        assert!(testee.try_add(&tx_cost).is_ok());
        costs.push((key, tx_cost));
    }
    assert_eq!(m, testee.cost_by_writable_accounts.len());

    // Remove every transaction - block_cost and transaction_count return to 0,
    // but the map does NOT shrink because zero-valued entries aren't removed.
    for (_key, tx_cost) in &costs {
        testee.remove(tx_cost);
    }

    assert_eq!(0, testee.block_cost());
    assert_eq!(0, testee.transaction_count());
    // BUG: map size should ideally shrink back toward 0, but stays at m
    // with all entries valued at 0.
    assert_eq!(m, testee.cost_by_writable_accounts.len());
    for (key, _) in &costs {
        assert_eq!(Some(&0), testee.cost_by_writable_accounts.get(key));
    }
}
```
Expected (fixed) behavior: after all removals, `cost_by_writable_accounts.len()` should be `0`, matching `roll_back_applied_costs`'s zero-entry cleanup behavior.
