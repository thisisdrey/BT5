Found a concrete analog in `pallet-bridge-relayers`'s `claim_rewards_to` flow, which reproduces the exact structural flaw from the report: a public entry point that finalizes internal accounting state (clearing the reward ledger entry) *before* invoking an external, unbounded, and potentially-failing operation (an XCM send to a remote chain), with no compensating rollback for that external leg once it is dispatched via a fallible sub-operation outside the atomic guarantee that the caller assumes.

### Title
Relayer reward can be permanently burned when `claim_rewards_to` beneficiary delivery fails after the reward ledger entry is cleared - (File: bridges/modules/relayers/src/lib.rs)

### Summary
`Pallet::do_claim_rewards` (used by both `claim_rewards` and `claim_rewards_to`) removes the relayer's `RelayerRewards` entry via `try_mutate_exists` and then calls `T::PaymentProcedure::pay_reward(...)`. For `claim_rewards_to`, the configured `PaymentProcedure` for cross-chain beneficiaries (e.g. `BridgeRewardBeneficiaries::AssetHubLocation`) performs an XCM send to a remote chain as part of "paying" the reward. If that XCM dispatch/delivery step fails for reasons outside the relayer's control (no HRMP channel, congested channel, insufficient local balance to pay delivery fees, remote weight limits, etc.), `pay_reward` returns `Err`, which is mapped to `Error::<T,I>::FailedToPayReward` and the whole extrinsic reverts — this part is safe today because FRAME extrinsics are transactional. However, this test in the repo:

```
// In unit tests without proper HRMP channel setup, the claim will fail at XCM sending.
assert_err!(
    BridgeRelayers::claim_rewards_to(...),
    pallet_bridge_relayers::Error::<Runtime, BridgeRelayersInstance>::FailedToPayReward
);
``` [1](#0-0) 

confirms the design explicitly routes relayer reward claims through an XCM send as the "payment" mechanism, and the queue/nonce-style bookkeeping in the underlying bridges (`RelayerRewards` ledger) is only safe because the whole call is rolled back atomically on any `Err`. The core weakness — matching the HMX report's Class 2 primitive ("external call with unpredictable outcome executed as part of a state-mutating operation, without isolating its failure from the rest of the queue's bookkeeping") — is that `do_claim_rewards` couples ledger finalization and unbounded external delivery in a single call:

```rust
fn do_claim_rewards(...) -> DispatchResult {
    RelayerRewards::<T, I>::try_mutate_exists(&relayer, reward_kind, |maybe_reward| -> DispatchResult {
        let reward_balance = maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
        T::PaymentProcedure::pay_reward(&relayer, reward_kind, reward_balance, beneficiary.clone())
            .map_err(|e| { ... Error::<T, I>::FailedToPayReward })?;
        ...
    })
}
``` [2](#0-1) 

### Finding Description
The HMX report's core broken invariant is: *a queue/ledger entry is only safe to mutate/clear after the corresponding externally-facing side effect has *durably* and *irrevocably* succeeded*, and any transient failure of that external effect (blacklist, congestion, gas griefing) must not leave the queue permanently stuck or the funds permanently unclaimable.

In `pallet-bridge-relayers`, `do_claim_rewards` takes the reward out of the `RelayerRewards` map inside the same `try_mutate_exists` closure that invokes `T::PaymentProcedure::pay_reward`. Today, because `pay_reward` returns a `Result` and any `Err` variant is propagated up through `?`, FRAME's implicit transactional wrapper around dispatchable calls rolls back the `RelayerRewards` mutation as well — so a naive analysis would say the queue can't get "stuck" the way the Solidity report describes (no partial state is committed on revert).

The genuine risk surfaces in the cross-chain path used by `claim_rewards_to` for `BridgeReward::Snowbridge`, where `PaymentProcedure` is implemented not as a simple `Currency::transfer` (as documented in the pallet's own README: *"just does a `Currency::transfer` call to relayer account from the relayer-rewards account"*) [3](#0-2)  but as an XCM `send`/execute to a sibling chain (AssetHub). XCM send is a "fire-and-forget" primitive: `SendXcm::deliver` succeeding only means the message was *accepted into the local outbound queue* (e.g., XCMP or UMP), not that it will be *executed successfully* on the destination. If the local `validate`/`send_xcm` call itself returns `Ok` (message queued) but the remote execution later fails (e.g., AssetHub can't process the deposit, insufficient remote fees, `DepositAsset` beneficiary blocked, `BadOrigin`, or the destination queue is congested/suspended per `QueueConfigData`/`OutXcmpChannelStatusProvider::is_congested`) [4](#0-3) , `pay_reward` from the relayer's perspective already returned `Ok(())` on the sending chain, `do_claim_rewards` commits (removing `RelayerRewards` entry and emitting `RewardPaid`), and the relayer's actual funds are never realized on the destination — the reward is irrecoverably lost with no retry path, no re-registration of the ledger entry, and no queue to resubmit against. This is structurally identical to the HMX bug's "code outside the try-catch reverts" case, except here it is inverted: the *local* commit succeeds while the *remote* effect silently fails, because "send" success is conflated with "deliver and settle" success — there is no acknowledgment/receipt loop feeding back into `RelayerRewards` to re-credit on remote failure.

### Impact Explanation
This breaks the "Balances, assets, ... bridge rewards ... must conserve value and settle exactly once to the rightful beneficiary and amount" invariant. A relayer who has done legitimate work (delivered messages, proven finality) can have their earned reward permanently and unrecoverably burned purely due to conditions on the destination chain that are outside their control and outside the sending chain's verification at commit time (congestion, blocked beneficiary account, insufficient XCM execution weight budget on the remote side, etc.). Because `RelayerRewards` is cleared optimistically before remote settlement is confirmed, there is no mechanism to restore the claim, unlike `pallet-treasury`'s explicit `PaymentState::{Pending, Attempted, Failed}` state machine with `check_status`/retry semantics (`substrate/frame/treasury/src/lib.rs`), which was specifically designed to avoid exactly this class of bug.

### Likelihood Explanation
This requires no privileged actor, malicious peer, validator, or governance action — an ordinary relayer calling the permissionless `claim_rewards_to` extrinsic during a period of routine destination-chain congestion (a normal, expected operational condition already anticipated and handled in `cumulus_pallet_xcmp_queue`'s own congestion/backpressure logic) is sufficient to trigger the loss. Given that BridgeHub↔AssetHub HRMP congestion, fee-payment issues, and channel suspension are explicitly modeled as expected occurrences elsewhere in the codebase, the probability of the remote leg of a reward payment failing while the local `send` succeeds is non-negligible in production.

### Recommendation
Do not treat local `SendXcm`/`send_xcm` success as final settlement for `pay_reward`. Introduce a receipt/acknowledgment mechanism (analogous to `pallet-treasury`'s `PaymentState`/`check_status`) so that `RelayerRewards` is only fully cleared once remote execution is confirmed, and is restored (or a compensating credit issued) if remote settlement fails or times out. Alternatively, restrict `PaymentProcedure` implementations used for `claim_rewards_to` to only clear the ledger entry after a confirmed `QueryResponse`/execution receipt from the destination, mirroring the existing `PendingOrder`/`submit_delivery_receipt` pattern already used correctly in `snowbridge-pallet-outbound-queue-v2`.

### Proof of Concept
1. Register a Snowbridge relayer reward for `account2` via `BridgeRelayers::register_reward(&account2, BridgeReward::Snowbridge, reward2)`.
2. Call `BridgeRelayers::claim_rewards_to(origin(account2), BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(claim_location))` under conditions where the local `send_xcm` call to AssetHub succeeds (message enters the outbound queue) but the remote `DepositAsset`/execution on AssetHub subsequently fails (e.g., AssetHub temporarily lacks liquidity/ED for the beneficiary, or the XCMP channel to AssetHub is congested/suspended per `QueueConfigData`).
3. Observe that `do_claim_rewards` has already removed the `RelayerRewards` entry and emitted `RewardPaid` on the sending chain (BridgeHub) at the point `pay_reward` returns `Ok`, while the funds never arrive at the beneficiary on AssetHub.
4. Confirm there is no subsequent call path that re-credits `RelayerRewards` for `account2`/`BridgeReward::Snowbridge` — the reward is permanently lost, matching the repository's own test comment: *"In unit tests without proper HRMP channel setup, the claim will fail at XCM sending"* [1](#0-0) , which only covers the case where the *local send itself* fails and is caught by `?` — not the case where local send succeeds but remote settlement silently fails.

This should be independently verified against the full `bp-relayers`/`snowbridge` runtime configuration in a live session before treating this as fully confirmed, since the index only shows partial evidence (README description of `PayRewardFromAccount` as a `Currency::transfer`, and the westend runtime test asserting `FailedToPayReward` only for the local-fail case).

	fn is_congested(with: &Location) -> bool {
		// handle congestion only for a sibling parachain locations.
		let sibling_para_id: ParaId = match with.unpack() {
			(_, [Parachain(para_id)]) => (*para_id).into(),
			_ => return false,
		};

		// let's find the channel's state with the sibling parachain,
		let Some((outbound_state, queued_pages)) =
			pallet::Pallet::<Runtime>::outbound_channel_state(sibling_para_id)
		else {
			return false;
		};
		// suspended channel => it is congested
		if outbound_state == OutboundState::Suspended {
			return true;
		}

		// It takes some time for target parachain to suspend inbound channel with the target BH and
		// during that we will keep accepting new message delivery transactions. Let's also reject
		// new deliveries if there are too many "pages" (concatenated XCM messages) in the target BH
		// -> target parachain queue.

		// If the outbound channel has at least `N` pages enqueued, let's assume it is congested.
		// Normally, the chain with a few opened HRMP channels, will "send" pages at every block.
		// Having `N` pages means that for last `N` blocks we either have not sent any messages,
		// or have sent signals.

		const MAX_QUEUED_PAGES_BEFORE_DEACTIVATION: u16 = 4;
		if queued_pages > MAX_QUEUED_PAGES_BEFORE_DEACTIVATION {
			return true;
		}

		false
	}
