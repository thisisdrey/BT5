### Title
`FetchIntoObjectPool` does not verify the `origin` repository is actually a member of the target object pool before fetching its objects - ([File: internal/gitaly/service/objectpool/fetch_into_object_pool.go])

### Summary
`FetchIntoObjectPool` lets a caller name an arbitrary `origin` repository and an arbitrary `object_pool`, and Gitaly will unconditionally pull all of `origin`'s objects and refs into that pool. The only validation performed is that both fields are non-nil and share the same storage — there is no check that `origin` is actually linked to, or was ever the seed of, the target pool. Once objects are fetched into a pool, they become permanently accessible to every current and future member of that pool via the `objects/info/alternates` mechanism, so this is effectively a cross-repository object-disclosure primitive analogous to the reported `PosManager#removeCollateralWLpTo` bug: a resource identifier (`tokenId` / here, `origin`) is trusted and operated on without checking that it actually belongs to (is a member of) the target record (`_posId` / here, the object pool).

### Finding Description
The RPC handler only validates:
```go
// internal/gitaly/service/objectpool/fetch_into_object_pool.go:102-118
func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}
	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}
	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()
	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}
	return nil
}
``` [1](#0-0) 

No check exists here (or anywhere before `FetchFromOrigin` is invoked) that `origin` is a pool member, was the pool's original seed repository, or is otherwise related to `object_pool`. The handler then calls straight into the fetch logic: [2](#0-1) 

`FetchFromOrigin` performs an unconditional `git fetch <originPath> +refs/*:refs/remotes/origin/*` against the pool, pulling in every ref and reachable object from whatever repository path is supplied as `origin`: [3](#0-2) 

By contrast, the codebase demonstrates elsewhere that Gitaly is normally careful to verify that a supplied identifier (quarantine directory, alternates content) genuinely belongs to the entity it's operating on, e.g. `QuarantineDirectoryPrefix` / `ObjectDirectoryPath` verify a quarantine dir belongs to the target repo, and `objectpool.Link`/`linkedToRepository` verify the alternates file content matches the expected pool before treating a repo as "linked": [4](#0-3) [5](#0-4) 

`FetchIntoObjectPool` has no equivalent membership check for `origin` vs. `object_pool`, and the proto comments confirm the RPC is only *intended* to be called "with the original object pool member" — this is a convention enforced by the caller (Rails), not by Gitaly itself: [6](#0-5) 

### Impact Explanation
Object pools are designed so that once an object is fetched into the pool, it is retained (via dangling refs / alternates deduplication) and made available to every repository currently or subsequently linked to that pool via `LinkRepositoryToObjectPool`. If a caller can pass an arbitrary repository path as `origin` while targeting a pool they control (or any pool reachable in the same storage), they can smuggle all objects — including commits, blobs, and any private history — of an unrelated repository into that pool. Any repository already linked, or later linked, to the pool (including one fully controlled by the attacker) can then read those objects through the alternates directory or by cloning the pool directly (`GetObjectPool`/pool cloning flow), resulting in disclosure of private repository contents across an unrelated repository/project boundary. This is a concrete cross-repository object access, matching the "confirmed" severity class of the underlying report (unauthorized cross-boundary object retrieval via an unchecked identifier).

### Likelihood Explanation
`FetchIntoObjectPool` is a standard, always-available mutator RPC in `ObjectPoolService`, reachable by any client authorized to call Gitaly RPCs for a given virtual storage/repository pair (e.g., through GitLab Rails' internal API, or directly if internal auth token/Praefect routing is available to the attacker, e.g. a malicious or compromised internal caller, or logic bugs in Rails-side authorization that only check access to `object_pool` but not to `origin`, since `origin` is marked `additional_repository` and is subject to the same storage-only validation as shown in Praefect's routing code, not a "is member of pool" check). Because Gitaly itself performs no ownership/membership validation, any weakness or omission in the caller's (Rails') authorization logic around the `origin` field directly translates into cross-repository disclosure, with no defense-in-depth at the Gitaly layer.

### Recommendation
Add a membership check inside `objectpool.FetchFromOrigin` (or `validateFetchIntoObjectPoolRequest`) that verifies `origin` is actually linked to `object_pool` — e.g., by calling the existing `linkedToRepository`/alternates-verification helper (as already used by `Link`) before performing the fetch, and rejecting the RPC with `InvalidArgument`/`PermissionDenied` if `origin`'s alternates do not point at the target pool. This mirrors the recommended fix in the external report: verify the referenced resource (`origin`) actually belongs to the record being operated on (`object_pool`) before performing any state-mutating or data-exposing operation.

### Proof of Concept
1. Attacker has (or is granted, via a caller-side authorization gap) the ability to invoke `ObjectPoolService.FetchIntoObjectPool` with:
   - `object_pool`: a pool the attacker owns and has already linked one of their own repositories to (so they can read pool objects afterward).
   - `origin`: the path of a victim repository the attacker does not have permission to read directly, but whose storage name and relative path they know or can guess (same storage as required by `validateFetchIntoObjectPoolRequest`).
2. Gitaly runs `FetchFromOrigin`, executing `git fetch <victim-repo-path> +refs/*:refs/remotes/origin/*` into the attacker's pool with no check that the victim repo is a member of that pool: [7](#0-6) 
3. All of the victim repository's objects are now present in the attacker-controlled pool and reachable/dangling-ref-protected there.
4. The attacker clones or fetches from their own pool-linked repository (which has the pool as an alternate object store) and retrieves the victim's commit/blob contents, e.g. via `git cat-file`/`git log` against the newly-created `refs/remotes/origin/*` refs in the pool.

		return s.localRepoFactory.Build(repo)
	}); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

// linkedToRepository tests if a repository is linked to an object pool
func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
}
