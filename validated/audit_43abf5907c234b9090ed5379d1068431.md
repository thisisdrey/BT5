### Title
Firewall conntrack fast-path does not re-validate CA-based rules when the CA pool is reloaded, allowing revoked/removed CA trust to remain enforced forever - (File: firewall.go)

### Summary
`Firewall.Drop` re-validates an established conntrack entry against the *current* firewall ruleset only when `f.rulesVersion` changes, which happens exclusively on a `firewall` config reload (`reloadFirewall` in `interface.go`). CA pool reloads (`pki.go` `reloadCAPool`, triggered by `pki.ca` changes) never touch `rulesVersion`. Firewall rules can be scoped with `ca_name`/`ca_sha` (`firewall.go` `AddRule`), and `FirewallTable.match` evaluates those against the caller-supplied `caPool`. However, once a flow has an established conntrack entry with the current `rulesVersion`, `inConns` skips `table.match` entirely and only refreshes the expiry timer — it never re-checks the (possibly changed) `caPool` for that flow.

### Finding Description
`Firewall.Drop` (firewall.go:425-479) checks `f.inConns(fp, h, caPool, localCache)` before consulting `table.match`. `inConns` (firewall.go:505-578) only re-validates against `table.match` when `c.rulesVersion != f.rulesVersion` — i.e. only after a firewall-rules reload: [1](#0-0) 
If the rule version has not changed (the common case, since CA pool updates do not bump it), the conntrack entry is kept valid purely by refreshing its expiry: [2](#0-1) 

CA-scoped rules are added via `AddRule`/`AddFirewallRulesFromConfig`, which accept `ca_name`/`ca_sha` and pass the *current* `caPool` into `table.match` only on the initial `Drop` call that creates the conntrack entry: [3](#0-2) 

Meanwhile, the CA pool is reloaded independently of the firewall on `pki.ca` config changes, and this path never touches `Firewall.rulesVersion`: [4](#0-3) [5](#0-4) 

Contrast this with `reloadFirewall` in `interface.go`, which is the *only* code path that increments `rulesVersion` (on `firewall` config changes or certificate unsafe-network changes) and is what forces `inConns` to re-run `table.match`: [6](#0-5) 

Because a CA rotation/removal does not increment `rulesVersion`, any packet flow that was already conntracked under a rule referencing that CA (`ca_name`/`ca_sha`) keeps being allowed by the fast path forever (until natural TCP/UDP/default conntrack timeout, which can be re-extended indefinitely by continued traffic), even though `table.match` — if it were consulted with the new `caPool` — would now reject it. This mirrors the reported bug class: state that should be re-evaluated against "current" trusted data is instead cached from a point in time and never revisited when the trusted-data set changes, silently preserving stale trust/decisions.

### Impact Explanation
This is a firewall bypass: revoking or removing a CA from `pki.ca` is expected to immediately invalidate any firewall rule keyed on that CA (`ca_name`/`ca_sha`), and this is precisely the security control an operator relies on when rotating or blocklisting a compromised CA. Because established flows are not re-validated on CA pool reload, traffic that was permitted under the old, now-revoked CA continues to be forwarded through the tun device indefinitely as long as the flow is kept alive, defeating the intended access-control update.

### Likelihood Explanation
This requires an operator-driven CA rotation/removal while an attacker (holding a certificate signed by the old/now-untrusted CA) already has an active tunnel and ongoing traffic that keeps the conntrack entry alive. It is not exploitable by a certless attacker outright, but it is reachable purely through the normal certificate/CA lifecycle and does not require any malicious peer/lighthouse behavior — a legitimate but now-revoked peer's existing session silently continues to bypass the newly restricted CA-based firewall policy.

### Recommendation
Bump `Firewall.rulesVersion` (or otherwise force a conntrack re-validation) whenever the CA pool is reloaded, or have `inConns` also compare against a monotonically increasing "trust version" tied to `pki.reloadCAPool`, not just `rulesVersion`. Alternatively, have `PKI.reloadCAPool` explicitly signal the firewall to invalidate/re-check any conntrack entries whose matching rule used `ca_name`/`ca_sha`.

### Proof of Concept
1. Configure a firewall inbound rule scoped with `ca_name: old-ca` and start a tunnel with a certificate signed by `old-ca`; establish traffic so a conntrack entry is created via `Firewall.Drop` → `addConn` (firewall.go:580-607).
2. Rotate `pki.ca` to remove `old-ca` (e.g. via SIGHUP or config reload), triggering `PKI.reload` → `reloadCAPool` (pki.go:77-95, 196-205). Note `Firewall.rulesVersion` is untouched.
3. Continue sending packets on the same flow tuple before the conntrack timeout expires. `Firewall.Drop` calls `inConns`, finds `c.rulesVersion == f.rulesVersion`, and allows the packet without re-checking `table.match` against the new `caPool` (firewall.go:505-577) — traffic keeps flowing despite the CA no longer being trusted.

func (p *PKI) reloadCAPool(c *config.C) *util.ContextualError {
	caPool, err := loadCAPoolFromConfig(p.l, c)
	if err != nil {
		return util.NewContextualError("Failed to load ca from config", nil, err)

	p.l.Debug("Trusted CA fingerprints", "fingerprints", caPool.GetFingerprints())

func (f *Interface) reloadFirewall(c *config.C) {
	cs := f.pki.getCertState()
	curCert := cs.getCertificate(cert.Version2)
	if curCert == nil {
		curCert = cs.getCertificate(cert.Version1)
	}

	// The firewall builds its routableNetworks set from the certificate's UnsafeNetworks at construction.
	// Check to see if that set has changed, and if so, rebuild the firewall.
	certUnsafeChanged := curCert != nil && !slices.Equal(curCert.UnsafeNetworks(), f.firewall.unsafeNetworks)

	if !c.HasChanged("firewall") && !certUnsafeChanged {
		f.l.Debug("No firewall config change detected")
		return
	}

	fw, err := NewFirewallFromConfig(f.l, cs, c)
	if err != nil {
		f.l.Error("Error while creating firewall during reload", "error", err)
		return
	}

	oldFw := f.firewall
	conntrack := oldFw.Conntrack
	conntrack.Lock()
	defer conntrack.Unlock()

	fw.rulesVersion = oldFw.rulesVersion + 1
	// If rulesVersion is back to zero, we have wrapped all the way around. Be
	// safe and just reset conntrack in this case.
	if fw.rulesVersion == 0 {
		f.l.Warn("firewall rulesVersion has overflowed, resetting conntrack",
			"firewallHashes", fw.GetRuleHashes(),
			"oldFirewallHashes", oldFw.GetRuleHashes(),
			"rulesVersion", fw.rulesVersion,
		)
	} else {
		fw.Conntrack = conntrack
	}

	f.firewall = fw
