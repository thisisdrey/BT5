### Title
DepositToken allowance revocation race allows a spender to consume old and new allowances - ([File: contracts/DepositToken.sol])

### Summary
`DepositToken.approve` overwrites `allowance[owner][spender]` directly, while `transferFrom` separately checks and spends the currently stored allowance. [1](#0-0) [2](#0-1)  This creates the same time-of-check/time-of-use pattern as the reported grant-revocation race: an attacker can spend the old allowance before the victim's replacement approval executes, then spend the newly stored allowance afterward. [3](#0-2)  Deposit tokens are directly redeemable for underlying collateral through `withdraw`, so excess withdrawn authorization translates into theft of user collateral. [4](#0-3) [5](#0-4) 

### Finding Description
The vulnerable sequence is:

1. A user approves an attacker-controlled spender for `A` deposit tokens by calling `DepositToken.approve(attacker, A)`. [6](#0-5) 
2. The user later submits `approve(attacker, B)` to reduce or replace the allowance. [6](#0-5) 
3. The attacker front-runs that transaction with `transferFrom(user, attacker, A)`, which verifies the old stored allowance and decrements it. [7](#0-6) 
4. The victim's replacement approval then overwrites the remaining allowance with `B`, instead of accounting for the allowance already consumed. [3](#0-2) 
5. The attacker calls `transferFrom(user, attacker, B)` and receives `A + B` tokens although the victim intended the attacker to have only `B` total authority. [2](#0-1) 

For unlocked balances, `transferFrom` only checks `_revertIfLocked(sender_, amount_)` before consuming allowance. [8](#0-7)  The attacker can consequently withdraw each stolen deposit-token amount for underlying collateral via the public `withdraw` path, which burns the deposit tokens and calls `Treasury.pull`. [4](#0-3) [9](#0-8) [10](#0-9) 

### Impact Explanation
An unprivileged spender can turn a nonzero approval replacement into cumulative spending authority, stealing up to `oldAllowance + newAllowance` rather than the intended `newAllowance`. [2](#0-1) [3](#0-2)  Because stolen `DepositToken` balances represent claims on collateral held by `Treasury`, the attacker can convert the excess authorization into underlying assets, causing direct loss of user funds. [5](#0-4) [10](#0-9)  The impact is constrained to balances considered unlocked by the account's current debt position because `unlockedBalanceOf` is consulted before both normal transfers and withdrawals. [11](#0-10) [12](#0-11) 

### Likelihood Explanation
The attack requires a victim to change an existing nonzero allowance to another nonzero value and requires the attacker to order a `transferFrom` before the replacement approval. [6](#0-5) [2](#0-1)  Public-mempool front-running is within the attacker model, and no privileged role, faulty oracle, malformed contract argument, or protocol administrator action is required. [2](#0-1)  `transferFrom` is protected by `nonReentrant`, but that guard does not prevent ordering across separate transactions, which is the relevant race here. [13](#0-12) 

### Recommendation
Do not treat a direct `approve` overwrite as a safe revocation mechanism. [6](#0-5) [3](#0-2)  At a minimum, require users to set allowances to zero before assigning a different nonzero value, or expose only atomic `increaseAllowance` and `decreaseAllowance` paths for deposit-token approvals. [14](#0-13) [15](#0-14)  User-facing gateways and integrations should also avoid changing a spender's nonzero allowance through `approve`; they should either first reset it to zero in a separate confirmed transaction or use the atomic allowance-adjustment functions. [14](#0-13) [15](#0-14) 

### Proof of Concept
The following Hardhat test demonstrates the accounting failure by executing the three transactions in the exploitable order. [6](#0-5) [2](#0-1) 

```ts
import {expect} from 'chai'
import {ethers} from 'hardhat'

it('allows a spender to consume old and new allowances', async () => {
  const [, user, attacker, recipient] = await ethers.getSigners()

  // Assumes `depositToken` is an initialized DepositToken and `user`
  // already owns at least 150 unlocked deposit tokens.
  const oldAllowance = ethers.utils.parseEther('100')
  const newAllowance = ethers.utils.parseEther('50')

  await depositToken.connect(user).approve(attacker.address, oldAllowance)

  // Front-run the user's replacement approval.
  await depositToken
    .connect(attacker)
    .transferFrom(user.address, attacker.address, oldAllowance)

  // The user's intended replacement allowance now executes.
  await depositToken.connect(user).approve(attacker.address, newAllowance)

  // The attacker can spend the replacement allowance as well.
  await depositToken
    .connect(attacker)
    .transferFrom(user.address, attacker.address, newAllowance)

  expect(await depositToken.balanceOf(attacker.address)).to.eq(
    oldAllowance.add(newAllowance)
  )

  // Optional value realization: redeem the stolen deposit tokens for collateral.
  const underlying = await ethers.getContractAt(
    'IERC20',
    await depositToken.underlying()
  )
  const before = await underlying.balanceOf(recipient.address)

  await depositToken
    .connect(attacker)
    .withdraw(oldAllowance.add(newAllowance), recipient.address)

  expect(await underlying.balanceOf(recipient.address)).to.be.gt(before)
})
```
