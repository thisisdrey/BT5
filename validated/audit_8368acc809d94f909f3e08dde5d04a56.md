### Title
Unauthenticated public-key upgrade in `validate_handshake`/`update_from_handshake_data` allows unauthenticated PeerDB key overwrite - (File: stackslib/src/net/chat.rs)

### Summary
Once a `ConversationP2P` already has a stored public key (`self.connection.get_public_key() == Some(_)`), `validate_handshake` never re-verifies the handshake's signature against the newly-claimed `node_public_key`. `update_from_handshake_data` then unconditionally overwrites the stored key with the unverified key, and for outbound convos this unverified key is persisted into the `PeerDB`.

### Finding Description
`validate_handshake` in `stackslib/src/net/chat.rs` (lines 1047-1127) branches on `self.connection.get_public_key()`:

- `None` branch: calls `message.verify_secp256k1(&handshake_data.node_public_key)` — the signature is checked against the *claimed* key in this message. [1](#0-0) 

- `Some(_)` branch: performs **no signature verification whatsoever**. It only checks, for outbound connections, that the self-reported `addrbytes`/`port` match the known socket address. [2](#0-1) 

After `validate_handshake` returns `Ok(())`, `handle_handshake` calls `update_from_handshake_data`, which compares the new key to the currently-stored key, sets `updated = true` if they differ, and then unconditionally calls `self.connection.set_public_key(Some(pubk.clone()))` — regardless of whether any signature was ever verified against `pubk`. [3](#0-2) 

Because `verify_secp256k1` takes an explicit public key argument rather than deriving it from `self.connection`'s stored state, and the `Some(_)` branch of `validate_handshake` never invokes it, a second handshake on the same convo carrying an entirely different (and arbitrarily/garbage-signed) `node_public_key` passes validation purely on the address check. `update_from_handshake_data` then swaps in this unverified key as the connection's authenticated public key — breaking the invariant (stated in the function's own doc comment: "A handshake will only be accepted if... it is signed by the current public key") that the stored key always corresponds to a verified signature.

Worse, in `handle_handshake`, if `updated && self.stats.outbound`, the new (unverified) key is persisted to the `PeerDB` via `Neighbor::load_and_update` + `neighbor.save_update`, permanently overwriting the on-disk record for that neighbor address with an attacker-chosen key that was never cryptographically tied to any signed message. [4](#0-3) 

Attacker's exact message: On a convo whose stored key is already `Some(pubkey_A)` (established via a normal first handshake), send a second `Handshake` message with `node_public_key = pubkey_B` (any parseable secp256k1 public key) and any signature bytes (garbage, or a signature valid under `pubkey_A` reused) — the signature is never checked against `pubkey_B` in this path.

### Impact Explanation
This is an unauthenticated write to persistent node state: the victim's `PeerDB` neighbor record is overwritten with an attacker-supplied public key that was never proven to correspond to any signing key the attacker (or the real peer) controls, for any outbound convo. This can be used to poison PeerDB entries, corrupt the neighbor-key/`Neighbor::handshake_update` ASN/org metadata, and desynchronize in-memory conversation state from the on-disk record used for future re-connections/authentication decisions elsewhere in the codebase — matching the "unauthenticated/unauthorized write to state" Critical category. It is repeatable on every subsequent handshake sent on the same connection.

### Likelihood Explanation
Preconditions: the attacker must be the remote party on an established `ConversationP2P` (either the node dialed out to the attacker, or the attacker is already handshaked in), which is trivially achievable by any unprivileged remote peer that can complete one normal handshake first. No secret, privileged role, or additional access is required. Attacker cost is two handshake messages on the connection they already hold.

### Recommendation
In the `Some(_)` branch of `validate_handshake`, always re-verify `message.verify_secp256k1(&handshake_data.node_public_key)` (or, to allow legitimate re-keying, verify the message against the *currently stored* key as authorization to switch to the new key) before permitting `update_from_handshake_data` to overwrite `self.connection`'s public key or persist it to `PeerDB`.

### Proof of Concept
Rust test plan added to `stackslib::net::chat` tests module:
1. Set up `convo_1`/`convo_2` as in existing `convo_handshake_update_key` test.
2. Perform handshake 1 from `local_peer_1` (signed correctly) so `convo_2.connection.get_public_key() == Some(pubkey_A)`.
3. Build handshake 2 payload with `node_public_key` set to `pubkey_B` (a different keypair), but sign it with `local_peer_1`'s *old* private key (or corrupt bytes of the signature directly), producing a message whose signature does not verify against `pubkey_B`.
4. Feed handshake 2 into `convo_2.chat(...)` (`handle_handshake` -> `validate_handshake` -> `update_from_handshake_data`).
5. Assert `convo_2.connection.get_public_key().unwrap() == pubkey_B`, demonstrating the key was swapped despite `pubkey_B`'s signature never being checked. Additionally, on the outbound side, assert the corresponding `PeerDB` neighbor row was updated to `pubkey_B` via `Neighbor::load_and_update`/`save_update`, confirming the unauthenticated on-disk write.
