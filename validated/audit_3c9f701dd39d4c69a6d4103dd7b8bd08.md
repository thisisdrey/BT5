## Title
Public message-fee calculation can round `fee.remote` to `0` for valid, non-zero pricing parameters, underpricing Ethereum-bound message delivery - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

## Summary
`Pallet::<T>::calculate_fee` computes the ETH-denominated remote fee by taking a wei-scale value, multiplying by `params.multiplier`, dividing by `params.exchange_rate`, and finally dividing by `10^(ETHER_DECIMALS - T::Decimals)` (e.g. `10^8` for a 10-decimal chain) in `convert_from_ether_decimals`. Any intermediate value smaller than that denominator truncates to `0`, even though all `PricingParameters` fields pass `validate()` as strictly non-zero, meaning legitimate governance-set pricing combined with low-gas commands yields `fee.remote == 0` while the message is still queued and dispatched on Ethereum at real gas cost.

## Finding Description
`calculate_fee` (`bridges/snowbridge/pallets/outbound-queue/src/lib.rs:368-393`) computes `calculate_remote_fee` (wei), casts to `u128`, reinterprets via `FixedU128::from_inner`, applies `saturating_mul(params.multiplier)` and `checked_div(&params.exchange_rate)`, then calls `convert_from_ether_decimals` (lines 414-418), which does integer division by `10^decimals` (`decimals = ETHER_DECIMALS - T::Decimals`). This final division truncates any sub-denominator wei-scale amount to `0`.

`PricingParameters::validate()` (`bridges/snowbridge/primitives/core/src/pricing.rs:39-56`) only asserts that `exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, and `multiplier` are individually non-zero — it never validates the derived `fee.remote` output across the actual gas ranges the `GasMeter` can produce. This gap is directly confirmed by the pallet's own test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` (`bridges/snowbridge/pallets/outbound-queue/src/test.rs:303-319`), which uses fully-valid parameters (`exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards = {1,1}`, `multiplier = 1/1`) and asserts `fee.remote == 0`, with the test's own comment acknowledging this is an "invalid" outcome "which should be avoided."

`calculate_fee` is invoked unconditionally from `SendMessage::validate` (`bridges/snowbridge/pallets/outbound-queue/src/send_message_impl.rs:41-74`), which is the entry point for essentially all outbound Snowbridge messages (XCM exports to Ethereum, asset transfers, etc.). No check exists anywhere in this path that rejects or floors a `fee.remote` of `0`; after `validate` returns the fee, the message ticket is still queued via `deliver`, so the message is delivered and executed on Ethereum regardless of the computed fee being zero.

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" impact category. `fee.remote` is meant to cover the ETH-denominated cost of Ethereum-side dispatch/execution charged to relayers/protocol; when it rounds to `0` for low-gas commands under legitimate governance-set pricing, senders get their message dispatched on Ethereum at real cost without paying the corresponding fee. Because `SendMessage::validate` sits on the hot path for ordinary unprivileged bridge usage (asset transfers, XCM exports), this allows repeatable free/underpriced Ethereum-bound dispatch, degrading the bridge's economic sustainability and potentially enabling zero-remote-fee queue spam.

## Likelihood Explanation
High. The flaw is already demonstrated by the pallet's own unit test using realistic, `validate()`-passing parameters, and it is triggered purely by the combination of governance-set `PricingParameters` and low `gas_used_at_most` values for cheaper commands — both are legitimate, non-malicious conditions, requiring no privileged actor or malicious peer. Any unprivileged user submitting a bridge-eligible message under such parameter/gas combinations reaches the zero-fee outcome deterministically and repeatably.

## Recommendation
- Add a post-computation check in `calculate_fee` that rejects the fee calculation (or applies a minimum floor) when the derived `fee.remote` is `0` while the underlying wei-scale computation was non-zero.
- Alternatively, avoid truncating division for the final decimals conversion (e.g., round up, or preserve precision until a later stage) so any non-zero wei-scale remote cost maps to at least `1` unit of native currency.
- Extend `PricingParameters::validate()` or add a runtime-time invariant check to assert `fee.remote != 0` across the full range of gas ceilings producible by `T::GasMeter`, not merely that raw parameter fields are non-zero.
