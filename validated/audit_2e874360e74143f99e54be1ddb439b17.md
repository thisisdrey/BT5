### Title
Unbounded-length numeric literal in JSON request bodies causes excessive CPU consumption via `BigInteger` construction in `JsonFormat.parseInteger` - (File: `framework/src/main/java/org/tron/core/services/http/JsonFormat.java`)

### Summary
`JsonFormat.merge()` is the shared JSON-to-protobuf parser used by essentially every HTTP API servlet in java-tron (e.g. `TriggerSmartContractServlet`, `GetBlockServlet`, `GetPaginatedProposalListServlet`, `GetContractInfoServlet`, and dozens more). When parsing an `int64`/`uint64`/`int32`/`uint32` field, `JsonFormat.Tokenizer` matches an arbitrarily long numeric token via a regex, and `parseInteger()` hands the resulting digit string straight to `new BigInteger(numberText, radix)` whenever the string is 16 characters or longer, with no upper bound on the string's length. [1](#0-0) 

### Finding Description
The `Tokenizer`'s `TOKEN` regex accepts a number token of essentially unbounded length (`"[.]?[0-9+-][0-9a-zA-Z_.+-]*+"`), so an attacker-supplied JSON body can contain a field expecting a signed/unsigned int64 (or int32) whose textual value is hundreds of thousands of decimal digits long. [2](#0-1) 

`parseInteger()` only fast-paths values shorter than 16 characters via `Long.parseLong`; anything longer is passed unmodified to `new BigInteger(numberText, radix)`:
```
1150|    String numberText = text.substring(pos);
...
1176|    } else {
1177|      BigInteger bigValue = new BigInteger(numberText, radix);
``` [3](#0-2) 

`java.math.BigInteger`'s string constructor for decimal (radix 10) input is quadratic in the number of digits below the JDK's internal parallel/recursive threshold, so a single crafted numeric literal of sufficient length can consume large amounts of CPU on a single thread before the value is even bounds-checked (`bitLength()` check happens only *after* the `BigInteger` is fully constructed).

This is functionally identical in root cause to CVE-2026-48834: a length-parameter inconsistency where the parser accepts and processes an unbounded-length token before validating it is a sane, expected size, leading to excessive CPU consumption during parsing of untrusted input.

This code path is reachable by any unauthenticated HTTP client hitting nearly any `/wallet/*` JSON HTTP endpoint that ultimately calls `JsonFormat.merge()`, e.g. `TriggerSmartContractServlet.doPost`, `GetBlockServlet`, `GetContractInfoServlet`, and `GetPaginatedProposalListServlet`, all of which feed the raw request body into `JsonFormat.merge`. [4](#0-3) [5](#0-4) [6](#0-5) 

Body size is only limited by a general HTTP body-size cap (`Util.checkBodySize`) and by Jetty's `SizeLimitHandler`, but that cap is typically sized to accommodate legitimate large payloads (e.g. contract bytecode/parameter fields for `TriggerSmartContractServlet`), which is large enough (hundreds of KB) to construct a pathologically long numeric-literal `BigInteger`. [7](#0-6) 

Notably, java-tron's own codebase already demonstrates awareness of this exact bug class and has patched it elsewhere: `JsonRpcApiUtil.parseBlockNumber` explicitly caps input length to `MAX_BLOCK_NUM_HEX_LEN` (20 chars) specifically because "BigInteger parsing... cost grows quadratically with length," and `parseTxIndex` has an analogous guard. No equivalent length guard exists in `JsonFormat.parseInteger`, which is a much more widely used HTTP-facing parsing routine. [8](#0-7) 

### Impact Explanation
An unauthenticated remote HTTP client can send a small number of crafted HTTP POST requests (well within existing body-size limits) containing pathologically long int64/uint64 numeric literals in any JSON field of the request, forcing the node to spend excessive CPU time constructing and discarding `BigInteger` objects inside `JsonFormat.merge`. Because this parser is used on essentially every HTTP API endpoint, this can be used to degrade or deny availability of a node's HTTP API (and potentially starve worker threads used for legitimate transaction/API processing), matching the "Availability: High" impact of CVE-2026-48834.

### Likelihood Explanation
High likelihood: any endpoint that accepts an HTTP POST JSON body handled by `JsonFormat.merge` (a very large fraction of `wallet/*` HTTP endpoints) is reachable pre-authentication and pre-signature-verification, requires no special privileges, and the attack payload is trivial to construct (a JSON body with one field set to a long digit string).

### Recommendation
Add an upper bound on the numeric token length accepted by `Tokenizer`/`parseInteger` (or reject non-fast-path values above a small fixed length, similar to the pattern already used in `JsonRpcApiUtil.parseBlockNumber`/`parseTxIndex`) before invoking `new BigInteger(numberText, radix)`. Since int64/uint64 valid values are at most ~20 decimal digits (or ~16 hex digits), any token longer than that can be rejected immediately with a `ParseException` instead of being passed to `BigInteger`.

### Proof of Concept
Send an HTTP POST request to any endpoint using `JsonFormat.merge` (e.g. `/wallet/getblock`) with a body such as:
```
{"detail": <300000-digit number>}
```
or to `TriggerSmartContractServlet`'s `/wallet/triggersmartcontract` with `"call_value": <300000-digit number>` (an int64 field). Repeated requests of this form, each within the existing body-size limit, will each force the server to perform an expensive `BigInteger(String, 10)` construction on the request-handling thread, consuming disproportionate CPU relative to the request size and rate-limiter cost, degrading availability of the HTTP API for legitimate callers.

  /**
   * Max allowed length for a JSON-RPC block number hex/decimal input.
   * API-level DoS guard: rejects pathological inputs before BigInteger parsing,
   * whose cost grows quadratically with length. A block number fits a signed long,
   * so the longest valid input is 19 chars (decimal Long.MAX_VALUE) or 18 (0x + 16
   * hex); 20 leaves a small margin.
   */
  private static final int MAX_BLOCK_NUM_HEX_LEN = 20;

  /**
   * Parse a JSON-RPC block number (hex "0x..." or decimal) into a long,
   * enforcing the {@link #MAX_BLOCK_NUM_HEX_LEN} length limit, rejecting
   * negative values, and rejecting values that overflow a signed 64-bit
   * block number.
   */
  public static long parseBlockNumber(String blockNum)
      throws JsonRpcInvalidParamsException {
    if (blockNum == null || blockNum.length() > MAX_BLOCK_NUM_HEX_LEN) {
      throw new JsonRpcInvalidParamsException(BLOCK_NUM_ERROR);
    }
    BigInteger value;
    try {
      value = ByteArray.hexToBigInteger(blockNum);
    } catch (Exception e) {
      throw new JsonRpcInvalidParamsException(BLOCK_NUM_ERROR);
    }
    if (value.signum() < 0) {
      throw new JsonRpcInvalidParamsException(BLOCK_NUM_ERROR);
    }
    try {
      return value.longValueExact();
    } catch (ArithmeticException e) {
      throw new JsonRpcInvalidParamsException(BLOCK_NUM_ERROR);
    }
  }
