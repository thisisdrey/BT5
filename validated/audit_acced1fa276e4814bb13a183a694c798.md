### Title
Unrestricted Git transport scheme in remote-URL RPCs enables local file/repo disclosure via `file://` (and command-execution risk via `ext::`) - (File: `internal/gitaly/service/repository/create_repository_from_url.go`)

### Summary
`CreateRepositoryFromURL` and `FetchRemote`/`UpdateRemoteMirror` take a user-supplied `url` string and pass it directly to `git clone`/`git fetch` without ever restricting the URL scheme. Git itself supports non-network transports such as `file://` and the `ext::`/remote-helper mechanism, so a caller who can only reach these RPCs as an "import a project from URL" or "configure a pull/push mirror" action (ordinary, non-admin operations) can supply `file:///path/on/gitaly/host` or similarly crafted schemes.

### Finding Description
In `cloneFromURLCommand`, the request URL is parsed only to strip credentials and build `http.extraHeader`/`curloptResolve` config; the scheme itself is never validated: [1](#0-0) 
It is then handed straight to `git clone <url> <path>`: [2](#0-1) 
`validateCreateRepositoryFromURLRequest` only checks that the repository target is valid and that the URL string is non-empty — it never inspects `req.GetUrl()`'s scheme: [3](#0-2) 

The same pattern exists in `FetchRemote`, where `validateFetchRemoteRequest` also only checks for a non-empty URL before the value is written into `remote.inmemory.url` git config and used for the fetch: [4](#0-3) [5](#0-4) 

Elsewhere in the codebase, Gitaly does show awareness of this class of risk — for example it explicitly disables `transfer.bundleURI` on the URL clone path "to prevent attack vectors that could abuse this mechanism" because a URI can point to `localhost` or elsewhere: [6](#0-5) 
and `CreateRepositoryFromSnapshot`'s HTTP-only untar path validates scheme against an `http`/`https` allowlist: [7](#0-6) 
No equivalent allowlist exists for `CreateRepositoryFromURL` or `FetchRemote`/`UpdateRemoteMirror`, leaving a gap where any Git-supported transport scheme, including `file://` local paths, reaches the underlying `git` process.

### Impact Explanation
Since `git clone file:///some/path` will happily read any git repository reachable on the Gitaly host filesystem (subject to OS file permissions, which are typically the same UID Gitaly runs as for all storages), a user who can only trigger a "clone this project from a URL" or "configure a pull mirror" action — normal, unprivileged project-level operations — can point the URL at another tenant's repository path on the same Gitaly node (or any other Gitaly-readable git directory) and exfiltrate its full object history into a repository they control. This is a cross-repository/cross-tenant object-access and local-file-disclosure primitive directly analogous to the reported `file://` arbitrary file read.

### Likelihood Explanation
Reaching this requires only knowledge/guessability of a target repository's on-disk relative path (which is often predictable, e.g., namespace/project hashes or IDs used by GitLab), and permission to invoke an import/mirror-from-URL action on some project — a standard, non-privileged user capability in GitLab. No malicious peer, leaked token, or admin access is required; the only trust assumption is that the field is attacker-influenced, which is the RPC's designed purpose.

### Recommendation
Add an explicit allowlist of permitted URL schemes (`http`, `https`, `git`, `ssh`) in `validateCreateRepositoryFromURLRequest` and `validateFetchRemoteRequest`/`UpdateRemoteMirror` validation, rejecting `file://`, `ext::`, and any other non-network transport before the URL reaches `git clone`/`git fetch`. Alternatively/also set `GIT_ALLOW_PROTOCOL` (or `protocol.*.allow` config) for these subprocess invocations to restrict the git binary itself to the same allowlist, mirroring the model already used for `transfer.bundleURI` and the HTTP-scheme check in `CreateRepositoryFromSnapshot`.

### Proof of Concept
1. As an ordinary user with permission to create a repository via URL import, call `CreateRepositoryFromURL` with `Url: "file:///var/opt/gitlab/git-data/repositories/@hashed/aa/bb/<other-repo>.git"` (or the equivalent Gitaly storage path known/guessed by the attacker).
2. `cloneFromURLCommand` builds and runs `git clone --bare file:///var/opt/.../other-repo.git <new-target-path>` with no scheme check. [2](#0-1) 
3. Git successfully clones the local repository's full object graph and refs into the attacker's newly created repository, which they can then browse/fetch, disclosing the victim repository's contents without ever going through the victim's Gitaly authorization checks for that repository.

Note: I was unable to trace the full authorization path from GitLab Rails down to whether an additional scheme filter exists at a layer outside this repository (e.g., Workhorse/Rails); this analysis is scoped strictly to the Gitaly code, where no such validation is present.

```go
func buildCommandOpts(ctx context.Context, opts *localrepo.FetchOpts, req *gitalypb.FetchRemoteRequest) error {
	remoteURL := req.GetRemoteParams().GetUrl()
	var config []gitcmd.ConfigPair

	for _, refspec := range getRefspecs(req.GetRemoteParams().GetMirrorRefmaps()) {
		config = append(config, gitcmd.ConfigPair{
			Key: "remote.inmemory.fetch", Value: refspec,
		})
	}

	if resolvedAddress := req.GetRemoteParams().GetResolvedAddress(); resolvedAddress != "" {
		modifiedURL, resolveConfig, err := gitcmd.GetURLAndResolveConfig(remoteURL, resolvedAddress)
		if err != nil {
			return fmt.Errorf("couldn't get curloptResolve config: %w", err)
		}

		remoteURL = modifiedURL
		config = append(config, resolveConfig...)
	}

	config = append(config, gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL})
```

```go
func (s *server) validateFetchRemoteRequest(ctx context.Context, req *gitalypb.FetchRemoteRequest) error {
	if err := s.locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	if req.GetRemoteParams() == nil {
		return structerr.NewInvalidArgument("missing remote params")
	}

	if req.GetRemoteParams().GetUrl() == "" {
		return structerr.NewInvalidArgument("blank or empty remote URL")
	}

	return nil
}
```
