This is a strong analog: `LinkRepositoryToObjectPool` allows an authenticated user with access to *any* repository to link it to an object pool by supplying an arbitrary `ObjectPool` reference, without verifying that the caller actually controls or owns that pool, or that the pool and target repository are related (e.g., forked from a common ancestor).### Title
`LinkRepositoryToObjectPool` links an arbitrary repository to any object pool without verifying ownership/provenance, enabling cross-repository object disclosure - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
The reported Perpetual bug is fundamentally about a state-changing operation (`liquidateFrom`) that fails to verify the relationship between the two parties it operates on (caller and target), letting one party silently pull the other's assets into its own accounting. The equivalent gap in Gitaly is `ObjectPoolService.LinkRepositoryToObjectPool`: it links a caller-supplied `repository` to a caller-supplied `object_pool` without ever verifying that the pool was actually created from, or is otherwise associated with, that repository (or one the caller legitimately administers). This lets an ordinary Gitaly client link a repository it controls to an *arbitrary* pool it merely knows the storage/relative path of, causing all of that pool's objects to become fetchable through the linked repository.

### Finding Description
`LinkRepositoryToObjectPool` only validates that the `repository` field is a well-formed, existing repository, then resolves the `object_pool` field purely from what the client supplied and links them: [1](#0-0) 

`poolForRequest` → `objectpool.FromProto` only checks that the pool path is a valid pool repository (or lives under a temp dir); it does not check that the target `repository` was ever forked from, or is otherwise related to, that pool: [2](#0-1) [3](#0-2) 

The actual linking logic in `internal/git/objectpool/link.go` writes the pool's relative object path directly into the repository's Git `alternates` file, and only refuses to proceed if the repository is already linked to a *different* pool — it never checks that the pool "belongs" to the repository being linked: [4](#0-3) [5](#0-4) 

The proto documentation itself frames object pool membership as something that should track fork relationships ("Typically this would be the repository that gets forked... One or more repositories are linked to the object pool"), but no code enforces that invariant at the RPC boundary: [6](#0-5) [7](#0-6) 

This is the direct analog of the reported bug class: just as `liquidateFrom` failed to check that the liquidator and the liquidated account were the same/authorized pair before mutating shared accounting state, `LinkRepositoryToObjectPool` fails to check that the repository and pool being linked are actually a legitimate (owner, pool) pair before mutating shared object-storage state (the alternates file) that grants cross-repository object access.

### Impact Explanation
Git's alternates mechanism (`objects/info/alternates`) makes every object in the pool repository readable through the linked repository via ordinary Git/Gitaly read operations (`GetBlob`, `TreeEntry`, `FindCommit`, fetch/clone, etc.), since Git transparently resolves missing objects through alternates. If a caller can link a repository they control to a pool belonging to another, unrelated project, they gain read access to that project's Git objects — commits, blobs, and trees — that were never intended to be shared. This is a cross-repository object disclosure that undermines project/repository isolation, which Gitaly and GitLab otherwise strive to enforce at every other layer (op-type/scope annotations, `target_repository`/`additional_repository` field markers, access checks in `OperationService`, etc., as documented in `proto/operations.proto` and the RPC development guide).

### Likelihood Explanation
`LinkRepositoryToObjectPool` is a plain `MUTATOR` RPC reachable by any authenticated Gitaly client (there is no additional access-check callback to Rails/GitLab as there is for `OperationService`, whose docstring explicitly notes "Any reference update is thus checked against GitLab's `/allowed` endpoint" — no equivalent exists for `ObjectPoolService`). An attacker only needs:
1. A repository under their control on the same storage.
2. Knowledge of, or the ability to enumerate/guess, the relative path of a target object pool (pool paths follow a predictable `@pools/xx/yy/<hash>.git`-style layout, as seen in test fixtures).

Both preconditions are realistic for a party with ordinary repository-creation/push access to a Gitaly-backed GitLab instance (e.g., a project member who can create forks or otherwise obtain arbitrary repositories), making this a plausible, low-effort attack path rather than a purely theoretical one. I was not able to fully verify from the indexed code whether Praefect or the higher-level GitLab Rails layer imposes an out-of-band ownership check before forwarding this RPC (e.g., verifying pool/fork ancestry) — that verification would need to be done in the actual repository to confirm whether this is fully exploitable end-to-end or is mitigated by an additional access-control layer not visible in the indexed code.

### Recommendation
- In `LinkRepositoryToObjectPool` (and any other pool-membership-mutating RPC), verify that the target `repository` is an authorized/known member of the specified `object_pool` — e.g., by checking a persisted pool-membership record, or by requiring that the `repository` was created via `CreateFork`/`CreateObjectPool` from that same pool's origin — rather than trusting the caller-supplied pairing.
- Alternatively/additionally, enforce this invariant at the layer that has ownership information (GitLab Rails via an access-check callback, similar to how `OperationService` calls GitLab's `/allowed` endpoint) before Gitaly performs the alternates write.
- Ensure pool relative paths are not otherwise guessable/enumerable, and audit `DisconnectGitAlternates`/`GetObjectPool` for the same missing-ownership-check pattern.

### Proof of Concept
Conceptual reproduction using the existing test harness pattern (`internal/gitaly/service/objectpool/link_test.go`):
1. Attacker creates `repoA` (their own repository) on a storage they can access.
2. Attacker learns/derives the relative path of `poolB`, an object pool created from a private repository they do not own (e.g., by observing predictable pool path conventions, or via a leaked `GetObjectPool` response from a different context).
3. Attacker calls:
```go
client.LinkRepositoryToObjectPool(ctx, &gitalypb.LinkRepositoryToObjectPoolRequest{
    Repository: repoA,
    ObjectPool: &gitalypb.ObjectPool{Repository: poolBRepo},
})
```
   — as shown to succeed unconditionally for any valid pool in the existing test `TestLink` (`internal/gitaly/service/objectpool/link_test.go:97-158`), with no check that `repoA` is related to `poolB`.
4. `repoA`'s `objects/info/alternates` now points at `poolB`'s object store (`internal/git/objectpool/link.go:28-83`), so any subsequent Git read against `repoA` (fetch, `CommitService.GetTreeEntries`, `BlobService.GetBlob`, etc.) can resolve and expose objects that originated only in `poolB`, i.e., in the victim's private repository.

```go
// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}

	pool := &ObjectPool{
		Repo:                localrepo.New(logger, locator, gitCmdFactory, catfileCache, proto.GetRepository()),
		logger:              logger,
		locator:             locator,
		gitCmdFactory:       gitCmdFactory,
		txManager:           txManager,
		housekeepingManager: housekeepingManager,
	}

	if !pool.IsValid(ctx) {
		return nil, ErrInvalidPoolRepository
	}
```

```go
// linkedToRepository tests if a repository is linked to an object pool
func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
}
```

```text
// ObjectPoolService is a service that manages the lifetime of object pools.
//
// An object pool is a separate repository that can be linked to from multiple object pool members
// in order to deduplicate common objects between them. This is mostly used in the context of
// repository forks.
//
// The typical lifetime of an object pool is as follows:
//
// 1. An object pool is created via CreateObjectPool from its primary pool member. Typically this
//    would be the repository that gets forked.
// 2. One or more repositories are linked to the object pool via LinkRepositoryToObjectPool. Each
//    object pool member linked to the repository will have its objects deduplicated when its
//    objects get repacked the next time.
// 3. The object pool is regularly updated via FetchIntoObjectPool. This is typically only done from
//    the primary object pool member.
// 4. Repositories may leave the object pool via DisconnectGitAlternates. There is not much of a
//    reason to do this for any repositories except for the primary object pool member in case it
//    for example becomes private.
// 5. When the object pool does not have any members anymore it gets deleted via DeleteObjectPool.
//    It is the responsibility of the caller to ensure that it really has no members left, else
//    any existing member will become corrupt.
```
