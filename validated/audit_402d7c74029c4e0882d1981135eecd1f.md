### Title
DeleteAccount fails to purge postponed/received-data/promise-yield trie rows keyed by the deleted account, letting attacker-planted receipts survive deletion and fire later against a differently-owned account of the same name - (File: runtime/runtime/src/actions.rs, core/store/src/utils/mod.rs)

### Summary
`action_delete_account`'s two guards (`Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` and `GasKeyInfo::MAX_BALANCE_TO_BURN`) only inspect `Account.storage_usage` and gas-key balances, both of which never reflect postponed receipts, pending-data counts, received data, or promise-yield receipts stored under the account's id. `remove_account` (the function that actually deletes trie rows on deletion) only removes the `Account`, `ContractCode`, `AccessKey`/gas-key-nonce, and `ContractData` rows — it never touches `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `ReceivedData`, or `PromiseYieldReceipt` rows keyed by `receiver_id = account_id`. An attacker can therefore plant arbitrarily many cheap postponed action receipts on an account it controls, delete the account (guards pass because these rows are invisible to them), and leave dangling, attacker-authored `FunctionCall` payloads in the trie that persist under that exact account-id string indefinitely.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) computes `account_storage_usage` from `Account.storage_usage()` (minus contract code) and checks it against `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` [1](#0-0) , then sums gas-key balances via `compute_gas_key_balance_sum` and checks against `GasKeyInfo::MAX_BALANCE_TO_BURN` [2](#0-1) . Both guards pass, then `remove_account` is called to actually delete state [3](#0-2) .

`remove_account` (`core/store/src/utils/mod.rs:505-575`) removes only the `Account` record, `ContractCode`, access keys/gas-key nonces, and `ContractData` [4](#0-3) . It never iterates or removes `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, `TrieKey::ReceivedData`, or `TrieKey::PromiseYieldReceipt` for the account being deleted.

Postponed receipts are created and keyed purely by the string `receiver_id` (not by any account-version/creation-nonce), in `process_action_receipt`: for every unmet `input_data_id` it writes `PostponedReceiptId{receiver_id, data_id}` and `PendingDataCount{receiver_id, receipt_id}`, then `set_postponed_receipt(state_update, receipt)` [5](#0-4) . When a matching `Data` receipt later arrives, `process_receipt`'s `Data` arm looks the postponed link up purely by `(account_id, data_id)` and, once satisfied, fetches and executes the stored `Receipt` — with no check that the account was ever re-created, re-owned, or is even the same "generation" of the account [6](#0-5) . Per the storage docs, these rows were explicitly designed to not be charged as account storage ("we don't charge storage for receipts") [7](#0-6) , confirming why `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` is structurally blind to them.

Because `TrieKey`s for postponed/received-data/promise-yield rows contain only the raw `AccountId` string, and named-account creation places no restriction on reusing an account id previously deleted, an attacker who: (1) creates account `A`, (2) issues a two-hop promise chain that leaves a `FunctionCall`-to-`A` receipt postponed on an input data id the attacker controls the timing of, and (3) deletes `A` — leaves that postponed receipt (predecessor = attacker, receiver = `A`, arbitrary attacker-chosen method/args) permanently resident in the trie. If `A` is later re-created (by the attacker itself, or — for sub-accounts — anyone able to re-register the exact name after deletion), the attacker can subsequently satisfy the pending data id (by completing the other leg of its own promise chain, which it fully controls) and the runtime will execute the old, attacker-authored `FunctionCall` receipt against the new occupant of `A`, with no re-validation that `A`'s identity/ownership hasn't changed.

### Impact Explanation
This is an authorization-boundary defect: actions intended for one incarnation of an account name can be resurrected and executed against a completely different (later) occupant of that same name, entirely outside any signature/access-key check on the new occupant, because the delivery path only keys on the raw account-id string. This maps to "authorization escalation across accounts or promises." Practically, the severity of exploitation (e.g., front-running an un-guarded `new()`/init method on the freshly (re)deployed contract) is contract-dependent, but the runtime-level enabling primitive — silently surviving, attacker-controlled, arbitrary-payload receipts that outlive `DeleteAccount` — is a genuine nearcore defect independent of any particular victim contract. Separately, and independent of the re-creation angle, this is also an unbounded, ungated, permanent state-growth vector: `MAX_ACCOUNT_DELETION_STORAGE_USAGE`/`MAX_BALANCE_TO_BURN` were clearly intended to bound what `DeleteAccount` leaves behind, but neither actually bounds the postponed/pending/received-data/yield footprint, so an attacker can grow trie state arbitrarily and cheaply per deleted account with none of it counted against the deletion guards.

### Likelihood Explanation
Cost to the attacker is low: creating a postponed receipt only requires an unresolved two-hop promise (cheap `FunctionCall`s, no deposit needed for the callback leg), and `DeleteAccount` itself is a normal, unprivileged action. The attacker fully controls both when the postponed receipt is planted and when (if ever) the satisfying `Data` receipt is delivered, since it derives from a promise chain the attacker itself authored. The whole sequence (`FunctionCall`(postponed) → `DeleteAccount` → repeat) is repeatable indefinitely and requires no validator, RPC-operator, or protocol privilege — only an ordinary funded account signing ordinary transactions.

### Recommendation
Extend `remove_account` (`core/store/src/utils/mod.rs:505`) to also iterate and remove all `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `ReceivedData`, and `PromiseYieldReceipt` (plus associated `PromiseYieldTimeout`/yield-id mapping) rows keyed by the account being deleted, mirroring the existing access-key/contract-data iteration pattern. Until that is done, `action_delete_account` should additionally reject deletion (or force settlement) when any such pending rows exist for the account, so that `DeleteAccount` cannot be used to abandon unresolved receipts.

### Proof of Concept
Rust unit-test plan (in `runtime/runtime/src/actions.rs` test module, alongside `test_delete_account_gas_key_balance_too_high`):
1. Set up a `TrieUpdate` with account `alice` (via `setup_account`/`test_delete_account_in_empty_trie` helpers already present).
2. Directly write N (e.g. 10,000) `TrieKey::PostponedReceipt{receiver_id: alice, receipt_id: i}` plus matching `PostponedReceiptId`/`PendingDataCount` rows for `alice` using `set_postponed_receipt`/`set` (bypassing the normal receipt-processing path, to simulate the planted state), while keeping `account.storage_usage()` at/below `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` and gas-key balance at 0.
3. Call `action_delete_account` for `alice` and assert `action_result.result.is_ok()` — proving both guards pass regardless of the planted postponed-receipt count.
4. After deletion, iterate the trie under `TrieKey::PostponedReceipt`/`PostponedReceiptId` prefixes for `alice` and assert the rows are still present (not removed by `remove_account`), demonstrating the orphaned state.
5. (Extended integration test) Re-create `alice` via `action_create_account`, then deliver a `Data` receipt to `alice` with the matching `data_id`, and assert that the originally-postponed `FunctionCall` (authored by the original, now-unrelated predecessor) executes against the newly created `alice` account.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

# Account Receipt Storage

There is a definition of all the keys and values we store in the Account Storage

## Received data

*key = `receiver_id: String`,`data_id: CryptoHash`*
*value = `Option<Vec<u8>>`*

Runtime saves incoming data from [DataReceipt](Receipts.md#data) until every [input_data_ids](Receipts.md#input_data_ids) in [postponed receipt](#postponed-receipts) [ActionReceipt](Receipts.md#actionreceipt) for `receiver_id` account is satisfied.

## Postponed receipts

For each awaited `DataReceipt` we store

*key = `receiver_id`,`data_id`*
*value = `receipt_id`*

Runtime saves incoming [ActionReceipt](Receipts.md#actionreceipt) until all required `DataReceipt` items for the same `receiver_id` have been received and matched, so that the postponed `receipt_id` receipt can be executed once its data dependencies are fully satisfied. See the [Receipt Case](Receipts.md#case-1-call-to-multiple-contracts-and-await-responses) for more details.
