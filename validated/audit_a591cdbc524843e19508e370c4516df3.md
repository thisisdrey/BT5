### Title
Signed-transaction replay via DeleteKey+AddKey self-rotation resetting AccessKey nonce below a previously-used value - (File: runtime/runtime/src/access_keys.rs, runtime/runtime/src/verifier.rs)

### Finding Description
`verify_nonce` in `runtime/runtime/src/verifier.rs` accepts any `tx_nonce` for a `FullAccess` key as long as it is strictly greater than the key's currently stored `nonce` (Monotonic mode) and below the per-height ceiling `height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [1](#0-0) . The maximum admissible nonce at block height `H` is therefore `N = H*MULTIPLIER - 1`.

When an `AddKeyAction` re-adds a regular (non-gas) key, `add_regular_key` unconditionally resets `access_key.nonce` to `initial_nonce_value(block_height) = (block_height-1) * MULTIPLIER`, with no knowledge of any nonce previously consumed by that exact public key before it was deleted [2](#0-1) [3](#0-2) .

Exploit flow:
1. Attacker owns account `A` with FullAccess key `pk`. Attacker signs `tx1 = SendMoney` with `pk`, `nonce = N = H*MULTIPLIER - 1` (the highest value `verify_nonce`'s upper-bound check permits at height `H`), and gets it included/applied in chunk at height `H`. This sets the on-chain `AccessKey.nonce` for `pk` to `N`.
2. In the *same* chunk/height `H` (a local, same-account/same-shard receipt), the attacker also submits `tx2` signed by any other FullAccess key on account `A`, containing `[DeleteKey(pk), AddKey(pk, FullAccess)]`. `action_delete_key` removes `pk`'s access-key record entirely (no memory of `N` survives) [4](#0-3) , then `action_add_key`/`add_regular_key` re-creates `pk` with `nonce = (H-1)*MULTIPLIER`, which is strictly less than `N` (`N - (H-1)*MULTIPLIER = MULTIPLIER - 1 > 0`).
3. Attacker resubmits the original signed `tx1` bytes at a later height `H'' > H`. `verify_nonce` checks `tx_nonce(N) > current_nonce((H-1)*MULTIPLIER)` — true — and `tx_nonce(N) < H''*MULTIPLIER` — also true since `H'' > H`. The replayed transaction is accepted and re-executed, duplicating the transfer (or any other action set) that already executed once.

The upper-bound/ceiling check exists precisely to stop hash/nonce collisions across heights, and `initial_nonce_value`'s comment references avoiding tx-hash collisions for *newly created* keys, but it does not account for a key being deleted and recreated with the same public key after having already reached a high nonce — the reset floor is derived purely from `block_height`, not from any high-water mark for that specific `PublicKey`.

The attack requires the `DeleteKey+AddKey` receipt to execute at the *same* block height `H` as `tx1` (if it executes at `H+1` or later, the new floor `(H'-1)*MULTIPLIER` would be `>= H*MULTIPLIER > N`, blocking the replay). Because both transactions are self-authored by the attacker and target local, same-shard, same-account receipts, the attacker can retry submission timing until both land in the same chunk — this is a fully unprivileged, repeatable condition, not a validator/network dependency.

### Impact Explanation
This allows an unprivileged account owner to force double execution of one of their own previously-signed transactions after a purely self-service key rotation (delete+re-add of the same public key). Scoped impact is transaction replay/double-spend of value or contract-call effects contained to actions originally authorized by the attacker's own key — matching the "double-spend/replay" bounty category described in the prompt.

### Likelihood Explanation
Preconditions: the attacker needs a funded account with a FullAccess key, must choose a nonce right at the per-height ceiling for a legitimate transaction, and must get a same-account DeleteKey+AddKey transaction processed as a local receipt in the *same* block height as the original transaction. This is achievable by an ordinary RPC client with no elevated access, at the cost of ordinary gas fees, and can be retried until timing aligns (self-controlled, repeatable). The precise timing dependency (same-height execution) somewhat reduces reliability but does not require any privileged or out-of-scope capability.

### Recommendation
`initial_nonce_value`/`add_regular_key` should not reset a public key's nonce below the highest nonce that key has ever held. Either (a) never fully purge nonce history on `DeleteKey` for a given `(account_id, public_key)` pair and enforce that re-adding the same public key preserves/raises its previous nonce, or (b) require `AddKeyAction`'s effective nonce floor to be `max((block_height-1)*MULTIPLIER, previous_max_nonce_for_this_pubkey)`, storing the high-water mark independently from the access key record's lifecycle so deletion cannot reset it.

### Proof of Concept
Unit test in `runtime/runtime/src/access_keys.rs` (extending existing `#[cfg(test)] mod tests`):
1. Setup account with FullAccess key `pk`, set its stored `AccessKey.nonce = N = H*MULTIPLIER - 1` via `set_access_key`.
2. Call `action_delete_key` for `pk`, then `action_add_key` for `pk` with `apply_state.block_height = H` (same height).
3. Read back `pk`'s access key and assert `access_key.nonce == (H-1)*MULTIPLIER`, and assert `(H-1)*MULTIPLIER < N` (demonstrating the invariant break the question describes).
4. Integration/runtime test (test-loop or `runtime/runtime/src/tests/apply.rs` style): apply `tx1` (SendMoney, nonce `N`) at height `H`; apply `tx2` (DeleteKey(pk)+AddKey(pk)) as a local receipt at the same height `H`; then call `verify_nonce`/`verify_and_charge_transaction` again with the original `tx1` bytes at height `H+1` and assert it returns `Ok` (accepted) instead of `Err(InvalidTxError::InvalidNonce)`, confirming replay is possible.

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
