Audit Report

## Title
Front-runnable `AlreadyExists` griefing in `pallet-asset-conversion-ops::migrate_to_new_account` permanently locks pool liquidity - (File: `substrate/frame/asset-conversion/ops/src/lib.rs`)

## Summary
`Pallet::migrate_to_new_account` is a permissionless, `Pays::No` extrinsic that moves a pool's `asset1`/`asset2`/`lp_token` balances from a deterministic `prior_account` to a deterministic `new_account` computed by `T::PoolLocator::address(pool_id)`. Before transferring, it unconditionally calls `T::Assets::touch(asset, &new_account, &depositor)` for any asset whose deposit needs migrating, and `touch` hard-fails with `Error::AlreadyExists` if `new_account` already has an asset-account entry, which an unprivileged attacker can trivially pre-create because `new_account` is publicly computable.

## Finding Description
`migrate_to_new_account` computes `prior_account`/`new_account` via `Self::addresses(&pool_id)`, which is `T::PriorAccountIdConverter::try_convert` and `T::PoolLocator::address`, both pure deterministic functions of `(asset1, asset2)` [1](#0-0) . For each asset that has a held deposit at `prior_account`, the extrinsic mints a compensating deposit and then calls `T::Assets::touch(asset, &new_account, &depositor)`, with no `should_touch`/existence check beforehand [2](#0-1) . `touch` resolves to `pallet_assets::Pallet::do_touch`, which unconditionally does `ensure!(!Account::<T, I>::contains_key(&id, &who), Error::<T, I>::AlreadyExists)` [3](#0-2) .

Because `new_account` is public and derivable off-chain by anyone (same computation the pallet itself performs), an attacker can send a trivial nonzero transfer of `asset1`, `asset2`, or `lp_token` to `new_account` before the legitimate `migrate_to_new_account` call, creating an `Account` entry there ahead of time. When the real migration call later reaches the `touch` step for that asset, `do_touch` returns `AlreadyExists` and the entire dispatchable reverts (all changes, including the earlier mint, roll back). Since `deposit_held` on `prior_account` persists until migration succeeds, the attacker can repeat this cheaply and indefinitely, permanently preventing migration for that pool. The existing checks (`ensure!(!balance.is_zero())`, `PartialTransfer` checks) do not address this because the failure occurs earlier, at the `touch` call, which has no idempotent/should-touch guard unlike `pallet_asset_conversion::touch`, which the reporter correctly identifies uses a "should_touch" style pattern elsewhere in the ecosystem.

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" impact category in the gate. `prior_account` holds the pool's real `asset1`/`asset2`/`lp_token` balances (confirmed by the test `migrate_pool_account_id_with_native`, which shows real liquidity residing at `prior_pool_account` before migration and moved to `new_pool_account` after) [4](#0-3) . Since the rest of `pallet_asset_conversion` addresses the live pool via `T::PoolLocator::address` (i.e., `new_account`), a pool that can never complete `migrate_to_new_account` has its liquidity permanently stranded at `prior_account`, unreachable through the pool's normal swap/withdraw logic. This is an unprivileged, no-cost attack (the extrinsic itself is fee-free via `Pays::No`, and the griefing transfer is a minimal-value ordinary asset transfer) that requires no governance, validator, or relayer compromise.

## Likelihood Explanation
High. The attacker only needs: (1) knowledge of the public `pool_id` and the ability to compute `new_account` via the same public `PoolLocator`/`PriorAccountIdConverter` logic the pallet uses, and (2) the ability to submit one ordinary, low-value `transfer` extrinsic. No race condition against a specific pending transaction is required — the attacker can pre-seed `new_account` at any point before anyone attempts the migration, and the created `Account` entry persists indefinitely (assets accounts don't disappear on their own), so the griefing is durable and repeatable at negligible cost.

## Recommendation
- Before calling `T::Assets::touch`/`T::PoolAssets::touch`, check whether the account already exists (analogous to a `should_touch` check) and skip the touch call if so, only failing if the existing account state is genuinely incompatible with completing the migration.
- Alternatively, add a defensive path allowing a privileged force-completion of the migration when `new_account` already holds an unexpected account/balance, so a single stray donation cannot permanently strand a pool's liquidity.
- More generally, avoid using a hard-failing, non-idempotent precondition (`AlreadyExists`) inside a permissionless dispatchable operating against a publicly predictable account address.

## Proof of Concept
1. Identify a pool `(asset1, asset2)` whose liquidity sits at `prior_account` under `T::PriorAccountIdConverter`, with a held deposit for `asset1`'s account (`T::AssetsRefund::deposit_held(asset1, prior_account)` returns `Some`).
2. Off-chain, compute `new_account = T::PoolLocator::address((asset1, asset2))` (public, deterministic).
3. As an unprivileged account, submit `pallet_assets::transfer(asset1, new_account, 1)` to create an `Account<asset1, new_account>` entry.
4. Anyone calls `pallet_asset_conversion_ops::migrate_to_new_account(asset1, asset2)`.
5. Execution reaches `T::Assets::touch(asset1, &new_account, &depositor)?` [5](#0-4) , which calls `do_touch`, hits `ensure!(!Account::<T, I>::contains_key(&id, &who), Error::<T, I>::AlreadyExists)` [6](#0-5) , and the whole extrinsic reverts. Retrying fails identically as long as the stray balance/account remains at `new_account`, permanently blocking migration for that pool.
