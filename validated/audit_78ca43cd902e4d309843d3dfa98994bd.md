### Title
Inconsistent overflow-safety between `ExchangeTransactionActuator.validate()`/`.execute()` allows silent balance corruption depending on `AllowHardenExchangeCalculation` flag - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`, `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
This is analogous to the WrappedIbbtc/WrappedIbbtcEth bug class: two code paths performing the *same* balance-affecting computation behave differently depending on a stored flag, and one of them silently omits the safety checks that the other performs. In java-tron, `ExchangeCapsule.transaction()` computes the new exchange pool balances using either safe (`StrictMathWrapper.addExact/subtractExact`, negative-balance check) or plain unchecked `long` arithmetic, selected by the `hardenedCalc` boolean that is derived from `dynamicStore.allowHardenExchangeCalculation()` at call time in both `ExchangeTransactionActuator.validate()` and `.execute()`.

### Finding Description
`ExchangeCapsule.transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath, boolean hardenedCalc)` computes `newFirstTokenBalance`/`newSecondTokenBalance` with plain `+`/`-` when `hardenedCalc` is `false`, and only checks for post-overflow negative balances when `hardenedCalc` is `true`: [1](#0-0) 

`ExchangeTransactionActuator` derives `hardenedCalc` from `allowHarden()` (i.e. `dynamicStore.allowHardenExchangeCalculation()`) independently in `doValidate()` and in `execute()`: [2](#0-1) [3](#0-2) 

`AbstractExchangeActuator.allowHarden()` reads a mutable dynamic-property flag rather than a fixed hard-fork boolean: [4](#0-3) 

Because this flag can change value between the time a transaction is validated (in the mempool / by a different node) and the time it is packed into a block and executed by another node/validator, or between successive transactions touching the same exchange pool within a block, the “safe” and “unsafe” arithmetic paths can be exercised inconsistently for logically identical operations — exactly mirroring the WrappedIbbtc/WrappedIbbtcEth pattern where one path performs a check/lookup the other path skips.

### Impact Explanation
When `AllowHardenExchangeCalculation` is not enabled (its default/disabled state), `ExchangeCapsule.transaction()` updates `firstTokenBalance`/`secondTokenBalance` using unchecked `long` arithmetic with no negative-balance or overflow guard. If accumulated pool balances (which are bounded only by `getExchangeBalanceLimit()` per single trade, not on their running total across many trades) or a single large `sellTokenQuant` push the sum past `Long.MAX_VALUE`, the addition wraps to a negative value, corrupting the on-chain `Exchange` capsule's balances. This is an "unbacked balance" condition: the exchange pool's recorded `firstTokenBalance`/`secondTokenBalance` no longer represents actual backing TRX/TRC10 held, which can subsequently be leveraged through further `ExchangeTransactionActuator`/`ExchangeWithdrawActuator` trades against the corrupted pool to extract more tokens than the pool should be able to pay out — matching the "unbacked balance" / "theft or permanent freezing of funds" acceptance criteria.

### Likelihood Explanation
Reaching this path only requires a single, unprivileged `ExchangeTransactionContract` broadcast by any account holding an existing exchange-eligible token/TRX balance and calling into an existing Bancor-style exchange pair — a normal, unprivileged transaction. The `hardenedCalc` value is governed by a chain-wide dynamic property (`AllowHardenExchangeCalculation`) that is set via governance/committee proposal rather than per-transaction, so an attacker cannot directly toggle it on demand within the same block; this constrains likelihood to periods when the hardened calculation is disabled and pool balances are large enough (attained over time through repeated legitimate injects/trades) to approach `Long.MAX_VALUE`, or through crafted large single-trade quantities bounded only by `getExchangeBalanceLimit()`.

### Recommendation
Make the overflow-safe (`hardenedCalc`) arithmetic and negative-balance check in `ExchangeCapsule.transaction()` unconditional rather than gated behind the `AllowHardenExchangeCalculation` dynamic property, so that `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator` cannot ever mutate pool balances via unchecked arithmetic, eliminating the dependency on a mutable governance flag for basic balance-integrity guarantees.

### Proof of Concept
Not independently reproducible from static review alone within this exercise: exploitation requires accumulating (or supplying) `firstTokenBalance`/`secondTokenBalance` + `tokenQuant` values close to `Long.MAX_VALUE` while `AllowHardenExchangeCalculation` is disabled, then invoking `ExchangeTransactionActuator` so that `ExchangeCapsule.transaction()` at [5](#0-4)  computes `firstTokenBalance + sellTokenQuant` (or the second-token equivalent) past `Long.MAX_VALUE`, wrapping to negative and persisting a corrupted `Exchange` capsule via `Commons.putExchangeCapsule(...)` in `execute()`. Confirming the practical reachability of sufficiently large pool balances (given `getExchangeBalanceLimit()` bounding each individual trade) would require live-chain/testnet verification, which is outside the scope of this static analog scan.
