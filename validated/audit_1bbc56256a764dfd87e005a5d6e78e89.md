Audit Report

## Title
Child-bounty curator fees are double-subtracted from parent bounty payout, permanently locking funds in the bounty sub-account - (File: substrate/frame/bounties/src/lib.rs)

## Summary
In `claim_bounty`, the beneficiary `payout` is computed as `balance.saturating_sub(fee)` using the full parent-bounty curator `fee`, while the actual transfer to the curator is `final_fee = fee.saturating_sub(children_fee)`. Since `balance` already excludes amounts spent on child bounties (transferred out at `add_child_bounty` time) and `children_fee` was already paid to child curators directly from child sub-accounts, subtracting the full `fee` (rather than `final_fee`) from `balance` shorts the beneficiary by exactly `children_fee`, which remains stranded in the deleted parent bounty sub-account with no recovery path.

## Finding Description
The relevant code in `claim_bounty` is: [1](#0-0) 

`balance` is the parent bounty sub-account's current free balance, which already excludes the value transferred out to fund child bounties (that transfer happens in `add_child_bounty`, moving `value` from the parent account to the child account). The child curator's fee (`children_fee`) is paid entirely out of the child sub-account when `claim_child_bounty` runs, never touching the parent account. Therefore `balance` at parent-claim time has no residual connection to `children_fee` at all.

However, `payout` is computed using the *unreduced* `fee` (line 811: `let payout = balance.saturating_sub(fee);`), while the curator is actually paid only `final_fee = fee - children_fee` (line 820, 822). The difference `fee - final_fee = children_fee` is deducted from the beneficiary's payout but is not transferred to the curator, the beneficiary, or anyone else. After both transfers execute, the parent bounty sub-account retains exactly `children_fee` in residual balance. Immediately afterward, `*maybe_bounty = None` deletes the `Bounties` storage entry, and `BountyDescriptions` is removed, so there is no code path that ever references or sweeps that sub-account's balance again — the funds are permanently stranded.

The existing test `children_curator_fee_calculation_test` in `substrate/frame/child-bounties/src/tests.rs` only checks the (buggy) final balances match the arithmetic actually implemented, not that all originally allocated funds were distributed, masking the shortfall.

## Impact Explanation
`claim_bounty` is a public extrinsic callable by any signed account once the payout delay elapses (`ensure_signed(origin)?; // anyone can trigger claim`), so this is reachable by any unprivileged user through ordinary governance-approved bounty/child-bounty usage — no privileged or malicious actor is required. Each time a parent bounty has one or more child bounties whose curator fees were already claimed before the parent claim, `children_fee` units of the treasury-allocated value become permanently locked in an orphaned, storage-removed sub-account, and the beneficiary is underpaid by the same amount. This matches the "permanent user-fund lock" and "runtime bugs that compromise intended behavior" categories of the impact gate.

## Likelihood Explanation
This occurs deterministically whenever `children_curator_fees(bounty_id) > 0` at parent-claim time, i.e., whenever a parent bounty had at least one child bounty whose fee was already claimed. Child bounties are a normal treasury feature actively used on Polkadot/Kusama; no adversarial conditions, precise timing, or privileged access are needed — it is triggered by standard usage.

## Recommendation
Compute the beneficiary payout using `final_fee` instead of the full `fee`:
```rust
let final_fee = fee.saturating_sub(children_fee);
let payout = balance.saturating_sub(final_fee);
```
This must be computed after `children_fee`/`final_fee` are known (reorder as needed), ensuring the beneficiary receives all funds not already disbursed via child-bounty curator fees, and no residual balance remains in the sub-account when the bounty record is deleted.

## Proof of Concept
Using the scenario in `children_curator_fee_calculation_test` (`substrate/frame/child-bounties/src/tests.rs`, referenced lines 1330-1436):
1. Propose/fund parent bounty with `value = 50`, curator fee `6` (curator = account 4).
2. Add child bounty `value = 10`; child curator (account 8) accepts with `fee = 6`, adding `6` to `ChildrenCuratorFees(0)`.
3. Award and claim child bounty: curator(8) receives `6`, beneficiary(7) receives `10 - 6 = 4`. Parent sub-account balance is now `40`.
4. Award parent bounty to beneficiary(9); call `claim_bounty(0)`.
5. Observe: `fee = 6`, `children_fee = 6`, `final_fee = 0` → curator(4) receives `0`; `payout = balance.saturating_sub(fee) = 40 - 6 = 34` transferred to beneficiary(9).
6. Total distributed = `6 (curator8) + 4 (beneficiary7) + 0 (curator4) + 34 (beneficiary9) = 44`, versus the `50` originally allocated. The remaining `6` units sit in the deleted parent `bounty_account` (`Self::bounty_account_id(0)`), unreachable since the `Bounties` storage entry for index `0` no longer exists. [2](#0-1)
