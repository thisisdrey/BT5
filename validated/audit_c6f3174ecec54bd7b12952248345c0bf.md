### Title
Unverified self-reported `HandshakeData.addrbytes`/`port` on first outbound handshake allows forged Neighbor PeerDB writes gossiped network-wide - (File: stackslib/src/net/chat.rs)

### Summary
`ConversationP2P::validate_handshake` only checks that `HandshakeData.addrbytes`/`port` match the actual dialed socket address when a public key is *already known* for that outbound conversation slot; on the very first handshake of a freshly-dialed outbound connection (no prior pubkey), no such check exists at all. Since `handle_handshake` then calls `Neighbor::load_and_update`/`neighbor.save_update` using the *self-reported* `handshake_data` (not the verified socket address), an attacker who is dialed by a victim node can claim an arbitrary `addrbytes`/`port` belonging to someone else and have that forged `(address, pubkey)` pair written into the victim's PeerDB, later gossiped via `GetNeighbors` replies.

### Finding Description
The equality the question demands — "the `Neighbor` row written to PeerDB must equal exactly the fields authenticated by THIS handshake's signature (this peer's own key/address)" — is violated for the address component on first contact.

- `validate_handshake` (stackslib/src/net/chat.rs:1047-1127) verifies the handshake's signature against the *claimed* `node_public_key` only when `self.connection.get_public_key()` is `None` [1](#0-0) . That proves the message was signed by whoever holds the private key for the claimed pubkey — it says nothing about whether `addrbytes`/`port` in the payload correspond to the real socket the node dialed.
- The only address-consistency check is gated behind `Some(_)` (i.e., a public key already on file for this conversation) and additionally exempts any-net addresses: [2](#0-1) . On the first handshake of a brand-new outbound connection this branch never executes, so `handshake_data.addrbytes`/`port` are accepted unchecked against the real TCP peer.
- `update_from_handshake_data` (stackslib/src/net/chat.rs:1131-1167) blindly copies these attacker-controlled fields into the conversation state: [3](#0-2) .
- `handle_handshake` then persists this to the PeerDB whenever the conversation is outbound and the key was updated, passing `&handshake_data` (the self-reported struct) rather than the actually-dialed `self.peer_addrbytes`/`self.peer_port` into `Neighbor::load_and_update`: [4](#0-3) . Since `Neighbor::load_and_update` is driven by `handshake_data` rather than the verified socket address, the resulting `Neighbor` row keys off the attacker's self-reported address, not the peer that actually holds that address's private key.
- `save_update` unconditionally writes this to `PeerDB::update_peer` (stackslib/src/net/neighbors/neighbor.rs:50-61) [5](#0-4) .

The attacker's exact message: dial-target node connects out to attacker; attacker replies with a `Handshake` whose `HandshakeData.node_public_key` is a fresh keypair the attacker controls, correctly self-signed, but with `addrbytes`/`port` set to a third party's known address (e.g., a well-connected relay). No signature or socket check ties those fields to the real owner of that address on this first-contact path.

I was not able to directly view the body of `Neighbor::load_and_update` (its exact definition location could not be confirmed beyond `stackslib/src/net/chat.rs`), so the precise construction of the `NeighborKey` used for the DB write is inferred from the call-site argument (`&handshake_data`, not `self.peer_addrbytes`/`self.peer_port`) and from `Neighbor::from_handshake`-style conventions elsewhere in this module family; this should be confirmed by a background agent with full-file access before remediation.

### Impact Explanation
A remote, unprivileged party that a victim node happens to dial (e.g., via a normal neighbor-walk connection to an address returned by an earlier `GetNeighbors`) can inject a forged `(addrbytes, port) -> pubkey` mapping into the victim's PeerDB under a third party's real address. Once written, this forged `Neighbor` is served back out through the victim's own `GetNeighbors`/`Neighbors` replies to other peers, propagating the forgery network-wide. This matches the "unauthenticated/unauthorized write to state" and "network-wide propagation of forged data" Critical categories.

### Likelihood Explanation
Requires only that some node initiates an outbound connection to an attacker-controlled listener — a routine occurrence during normal peer discovery/walk, requiring no privileged role, no secret, and no prior relationship with the impersonated address. The attack is repeatable per outbound dial the attacker receives, and costs only running a listening peer plus generating a keypair.

### Recommendation
Bind the PeerDB write to the address the local node actually dialed/verified for the socket (`self.peer_addrbytes`/`self.peer_port`), not the self-reported `handshake_data.addrbytes`/`port`, for outbound connections; or, at minimum, extend the address-consistency check in `validate_handshake` to also apply on first contact for outbound conversations (comparing against the dialed target), only allowing an unverified/any-net address on inbound conversations as originally intended.

### Proof of Concept
1. In `stackslib/src/net/chat.rs` tests (or a new integration test alongside `ConversationP2P` tests), set up peer A that outbound-dials peer B's listener.
2. Have B respond to A's `Handshake` request with a `HandshakeAccept`/counter-`Handshake` whose `HandshakeData.node_public_key` is a fresh keypair, but `addrbytes`/`port` set to a third, uninvolved address `C` (not B's real dial address) — properly self-signed with B's fresh key.
3. Drive A's `ConversationP2P::handle_handshake` with this crafted message via a mocked `PeerNetwork`/`PeerDB`.
4. Assert: `PeerDB::get_peer(conn, network_id, &C_addrbytes, C_port)` now returns a `Neighbor` whose `public_key` is B's forged key — i.e., the DB contains an entry for address `C` signed only by B, never by whoever actually controls `C`.
5. Assert the failure of the intended equality: the stored row's `addr` does not correspond to any peer that ever proved possession of `C`'s network identity via a validated socket check, only to `handshake_data.addrbytes` supplied by an unrelated attacker (B).
