### Title
Unit-mismatched counter in diff patch pruning causes silent negative drift and bypass of MaxBytes/SafeMaxBytes DoS limits - ([File: internal/gitaly/diff/diff.go])

### Summary
`Parser.prunePatch()` reduces the cumulative `bytesProcessed` counter by `len(parser.currentDiff.Patch)` while the same counter was previously incremented by a *different* quantity, `parser.currentDiff.byteCount`. These two values are not the same unit/scale: `Patch` accumulates raw bytes of every line appended to the patch buffer (including hunk (`@@`) header lines), whereas `byteCount` is only incremented for content lines where `updateStats` is `true` (hunk headers explicitly do **not** count towards `byteCount`, per the comment "Hunk headers do not count towards limits"). This mirrors the Astaria `WithdrawProxy`/`PublicVault` bug class: a quantity tracked in one scale (18-decimals / `byteCount`) is later subtracted using a different scale (raw token amount / `Patch` length), producing arithmetic corruption of a safety-critical accounting value.

### Finding Description
In `internal/gitaly/diff/diff.go`:

- `Parse()` increments the byte counter using the tracked, filtered stat: [1](#0-0) 

- `consumeChunkLine()` shows the asymmetry: `diff.Patch` is appended for every consumed line (subject only to `skipPatch`), but `diff.byteCount` is only incremented `if updateStats`, and hunk-header lines are explicitly passed with `updateStats=false`: [2](#0-1) [3](#0-2) 

- `prunePatch()` then reverses the addition using the *wrong* quantity, `len(parser.currentDiff.Patch)` instead of `parser.currentDiff.byteCount`: [4](#0-3) 

Because `Patch` includes bytes (hunk headers) that were never added to `byteCount`, every time `prunePatch()` fires for a diff containing hunk headers, `bytesProcessed` is over-subtracted, driving it further negative than it should be. `prunePatch()` fires on the `CollapseDiffs` safe-limit path: [5](#0-4) 
and again on the hard `MaxPatchBytes` per-file path: [6](#0-5) 

Once `bytesProcessed` drifts negative, the enforcement checks: [7](#0-6) 
and the safe-limit check: [8](#0-7) 
both become permanently (or for a long time) unreachable for the byte-based limit, because a large negative baseline must first be "paid off" by legitimate byte accumulation before `maxBytesExceeded`/`isOverSafeLimits` can trigger again.

### Impact Explanation
This is reachable directly by an ordinary, authenticated user through `DiffService.CommitDiff` (and the equivalent code path shared by other diff RPCs using `diff.Parser`), which lets the client fully control `EnforceLimits`, `CollapseDiffs`, `MaxBytes`, `SafeMaxBytes`, etc.: [9](#0-8) [10](#0-9) 

By crafting a diff (via a commit with many small hunks relative to actual content, i.e. many `@@ ... @@` hunk headers padded with minimal content lines) that repeatedly triggers `CollapseDiffs`/`prunePatch`, an attacker can drive `bytesProcessed` deeply negative. This defeats the `MaxBytes`/`SafeMaxBytes` protections that exist specifically to bound the CPU/memory cost of processing and returning diff data for a single RPC call, resulting in a DoS-class impact: Gitaly keeps parsing and buffering/streaming far more diff data than the caller-configured (and server-bounded, via `enforceUpperBound`) limits are meant to allow, for a single crafted request.

### Likelihood Explanation
Moderate-to-high. No privileged access, malicious peer, or token leak is required — only the ability to push/create a repository with an adversarial diff shape and call `CommitDiff` with `EnforceLimits`/`CollapseDiffs` set, both fully client-controlled request fields. Constructing many small hunks with disproportionate header overhead relative to counted content bytes is straightforward using ordinary git operations (e.g., many single-line changes scattered through a large file to force per-hunk headers). The upper bounds (`maxBytesUpperBound = 24MB`, `safeMaxBytesUpperBound = 2.4MB`) somewhat cap the worst case per request, but the bug still causes the safety net (`CollapseDiffs`) to stop functioning correctly and lets subsequent diffs in the same stream exceed the byte budget that was meant to bound work done per request.

### Recommendation
Make the counter update and pruning symmetric: subtract the exact quantity that was added. Either:
1. Track patch length separately from `byteCount` and subtract the correct field in `prunePatch()` (e.g., store the byte length actually added to `Patch` for the current diff, and decrement `bytesProcessed` by that same value), or
2. Include hunk-header bytes in `byteCount` consistently so that the value added in `Parse()` (`diff.byteCount`) matches what is later subtracted (`len(diff.Patch)`).

Additionally, add a sanity clamp (`bytesProcessed = max(bytesProcessed, 0)` / equivalent for `linesProcessed`) as defense in depth so that any future accounting mismatch cannot silently defeat limit enforcement.

### Proof of Concept

2. Call `CommitDiff` with `EnforceLimits: true`, `CollapseDiffs: true`, small `SafeMaxBytes` (e.g. 120, as in the existing `collapse after safe max byte count is exceeded` test case) and `MaxBytes` set to a value meant to bound total processing.
3. Repeat over multiple files/commits in the same stream so `prunePatch()` fires on each hunk-header-heavy diff, observing that `bytesProcessed` becomes negative (add temporary instrumentation/log of `parser.bytesProcessed`), and subsequent large diffs are no longer collapsed/limited as `MaxBytes`/`SafeMaxBytes` intended — i.e., they pass through in full despite exceeding the configured caller-visible bounds.

func (parser *Parser) prunePatch() {

	parser.bytesProcessed -= len(parser.currentDiff.Patch)

func consumeChunkLine(reader *bufio.Reader, diff *Diff, skipPatch, updateStats bool) error {
	// The code that follows would be much simpler if we used
	// bufio.Reader.ReadBytes, but that allocates an intermediate copy of
	// each line which adds up to a lot of allocations. By using ReadSlice we
	// can copy bytes into currentDiff.Patch without intermediate
	// allocations.
	var byteCount int
	for done := false; !done; {
		line, err := reader.ReadSlice('\n')
		if updateStats && byteCount == 0 && len(line) > 0 {
			if line[0] == '+' {
				diff.LinesAdded++
			} else if line[0] == '-' {
				diff.LinesRemoved++
			}
		}
		byteCount += len(line)

		switch {
		case errors.Is(err, bufio.ErrBufferFull):
			// long line: keep reading
		case err != nil && !errors.Is(err, io.EOF):
			return fmt.Errorf("read chunk line: %w", err)
		default:
			done = true
		}

		if !skipPatch {
			diff.Patch = append(diff.Patch, line...)
		}
	}

	if updateStats {
		diff.byteCount += byteCount
		diff.lineCount++
	}

	return nil
}
