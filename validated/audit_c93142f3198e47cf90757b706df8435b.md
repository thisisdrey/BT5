### Title
Static `x-gitaly-cost` score ignores request-scoped item counts, letting large enumeration RPCs evade complexity-based rate limiting - ([File: internal/grpc/middleware/costhandler/costhandler.go])

### Summary
The `x-gitaly-cost` trailer that Gitaly emits for Cloudflare/Workhorse complexity-based rate limiting is computed as a fixed per-method weight plus a dynamic component derived solely from payload **bytes** transferred, never from the number of records/objects a caller actually requested (e.g. `limit`, `bytes_limit=0`, `revisions` count). This mirrors the `twap()`/`x_twap()` bug: the fee/cost function is charged a constant instead of the caller-controlled multiplier that actually drives backend work, letting heavy multi-item queries be billed as cheap.

### Finding Description
`computeCost` combines only a static per-RPC-method weight and a dynamic component computed from bytes in/out:

<cite repo="Kohvert/gitaly--009" path="internal/grpc/middleware/costhandler/costhandler.go" start="84="91" /> [1](#0-0) 

The static weights are hardcoded per RPC and do not vary with the caller-supplied "how much do you want" parameters such as `ListBlobsRequest.limit`/`bytes_limit`, `ListCommitsRequest`'s pagination limit, or the size of `revisions`: [2](#0-1) 

Because `bytesLimit == 0` causes `processBlobs`/`ListBlobs` to skip streaming any blob content entirely (only metadata is emitted), a caller can request enumeration over an enormous object/commit graph while transferring almost no bytes: [3](#0-2) [4](#0-3) 

In this scenario `dynamicCostFromContext` returns near-zero (few bytes transferred) while `staticCostForMethod` returns the fixed override (e.g. `6` for `ListBlobs`/`ListCommits`), exactly as the external report describes: the cost/fee is charged a hardcoded/near-constant value regardless of the actual multiplier (`records`, object count, revision count) that drives the RPC's real cost. The design doc itself acknowledges dynamic cost is meant to reflect "bytes transferred, object count" but the implementation only accounts for bytes: [5](#0-4) 

### Impact Explanation
The `x-gitaly-cost` trailer is the sole signal Rails/Workhorse forward to Cloudflare's complexity-based rate limiter (`X-Score`), and Gitaly's own concurrency limiter does not account for query complexity either — it "treats every request as equally expensive": [6](#0-5) 

An ordinary authenticated user can systematically choose request parameters (large `revisions`/no `limit`, `bytes_limit=0`) to make Gitaly perform expensive graph walks/enumeration while the exported cost stays at the fixed static minimum, undermining the upstream rate limiter's ability to throttle heavy callers — the exact "predictable revenue/quota leak" and "attackers can query with high `records` to minimize cost" pattern from the source report, here manifesting as DoS-relevant rate-limit evasion rather than a billing bug.

### Likelihood Explanation
High: no special privilege is required beyond normal RPC access to `ListBlobs`/`ListAllBlobs`/`ListCommits`/similar enumeration RPCs, and setting `bytes_limit=0` while providing broad `revisions` is a documented, legitimate way to call these RPCs (metadata-only listing), making the abusive pattern indistinguishable from ordinary usage at the protocol level.

### Recommendation
Incorporate the caller-requested item/record count (e.g., `GetLimit()`, number of `revisions`, actual objects enumerated by `catfileInfoIter`/`catfileObjectIter`) into `dynamicCostFromContext`/`computeCost`, in addition to bytes transferred, so that enumeration-heavy but low-byte-volume requests are not undercharged relative to their real backend cost.

### Proof of Concept
1. Call `BlobService.ListBlobs` (or `ListAllBlobs`) against a large repository with `revisions: ["--all"]` and `bytes_limit: 0`, `limit: 0` (unbounded).
2. Gitaly performs a full graph walk enumerating potentially millions of blob metadata entries via `processBlobs` (`internal/gitaly/service/blob/blobs.go:93-130`), consuming significant CPU/IO.
3. Because `bytesLimit == 0`, almost no payload bytes are transferred, so `dynamicCostFromContext` (`internal/grpc/middleware/costhandler/costhandler.go:118-128`) returns ~0.
4. The response `x-gitaly-cost` trailer equals only the static override (`6`, per `staticCostOverrides["/gitaly.BlobService/ListBlobs"]`), identical to a trivial single-blob listing — allowing repeated, cheap-looking heavy requests to bypass Cloudflare's complexity-based throttling.

```go
// dynamicCostFromContext computes the dynamic cost contribution from payload
// bytes tracked by the grpcstats.PayloadBytes stats handler.
func dynamicCostFromContext(ctx context.Context) int {
	stats := grpcstats.PayloadBytesStatsFromContext(ctx)
	if stats == nil {
		return 0
	}
	totalBytes := stats.InPayloadBytes + stats.OutPayloadBytes

	return int(math.Ceil(float64(totalBytes) / float64(byteCostDivisor)))
}
```

**File:** doc/load-management-architecture.md (L196-206)
```markdown

The concurrency limiter today treats every request as equally expensive. In
practice, requests served from cache consume minimal resources (disk streaming)
while cache misses run full Git subprocess pipelines. Rather than feeding the
limiter a cost hint (which still consumes a limiter slot), cache-hit requests
skip the limiter entirely — keeping the concurrency limiter pure and ensuring
limits designed for expensive operations do not penalize cheap ones.

This separation also keeps the concurrency limiter's responsibility narrow: every
request that reaches it is treated as expensive.
```
