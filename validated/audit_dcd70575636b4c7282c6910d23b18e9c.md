### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign`/`BatchValidateSign` precompiles causes uncaught `OutOfMemoryError` and node crash - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `node-weakauras-parser` advisory describes an `encode_weakaura` function that fails to validate an attacker-supplied size before allocating a buffer, causing a buffer overflow / crash for huge sizes. The analogous pattern exists in java-tron's TVM precompiled contracts `ValidateMultiSign` and `BatchValidateSign`, where `extractBytesArray`/`extractBytes32Array` allocate a Java array whose dimension comes directly from attacker-controlled calldata, with no upper bound check before the allocation itself is performed.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read a length word directly out of the DataWord-decoded calldata and immediately allocate an array of that size: [1](#0-0) 

`len`/array size come from `words[offset].intValueSafe()`. `intValueSafe()` returns `Integer.MAX_VALUE` on any overflow (never negative, never throws): [2](#0-1) 

`ValidateMultiSign.execute` calls `extractBytesArray` on the legacy path (`allowTvmSelfdestructRestriction()` disabled) with **no size cap applied before the allocation** — the `MAX_SIZE` check only happens inside the `allowTvmSelfdestructRestriction()` branch: [3](#0-2) 

The same unguarded path exists in `extractBytes32Array`, called from `BatchValidateSign.doExecute` for the `addresses` array: [4](#0-3) [5](#0-4) 

An attacker who crafts calldata for a `CALL`/`STATICCALL`/`DELEGATECALL` to these precompile addresses (`ValidateMultiSign`/`BatchValidateSign`) can set the length word to `0x7fffffff` (or any value that overflows to `Integer.MAX_VALUE` via `intValueSafe()`). `new byte[Integer.MAX_VALUE][]` (a reference array, 8 bytes/entry on 64-bit JVMs) attempts to allocate ~17 GB, immediately throwing `OutOfMemoryError`.

`OutOfMemoryError` is a `java.lang.Error`, not a `RuntimeException`. `ValidateMultiSign.execute` has no surrounding `try/catch(Throwable)` around the array-extraction call (the only try/catch wraps the later account-permission logic), so the `Error` propagates straight up through `Program.callToPrecompiledAddress` into `VM.play`. `VM.play`'s catch clauses only catch `RuntimeException`, `JVMStackOverFlowException`/`OutOfTimeException`, and `StackOverflowError` — `OutOfMemoryError` is not handled there: [6](#0-5) 

An uncaught `OutOfMemoryError` on the block-processing thread can leave the JVM heap in a corrupted/unstable state and typically crashes or hangs the node process, since OOM can also disrupt unrelated concurrently-running threads (e.g., consensus, RPC, DB write threads) sharing the same heap.

### Impact Explanation
Any account can call a contract that invokes `validatemultisign(...)` or `batchvalidatesign(...)` (or call the precompile address directly) with crafted calldata, forcing a multi-GB array allocation attempt. This can crash the node's JVM (denial of service against the validating/executing node), and because this executes during normal transaction/block processing, a single malicious transaction broadcast to the network could be replayed by every full node and super representative that processes it, risking a chain-wide halt if enough nodes crash simultaneously while processing the same block.

### Likelihood Explanation
High for nodes still running with `allowTvmSelfdestructRestriction()` disabled (i.e., before the corresponding hard fork proposal is activated on the chain) or for other historical/synced blocks processed under the pre-activation ruleset. Any unprivileged account can construct the calldata; no special permissions or high resource cost (in energy) is required to reach the vulnerable code before the OOM allocation itself throws.

### Recommendation
Cap the array length derived from `words[offset].intValueSafe()` in `extractBytesArray` and `extractBytes32Array` against a small, sane maximum (e.g., `MAX_SIZE` used by `ValidateMultiSign`/`BatchValidateSign`) *before* allocating the array, independent of the `allowTvmSelfdestructRestriction()` feature flag, so the bound check always applies rather than being gated behind a conditionally-enabled hard-fork flag. Additionally, wrap precompile execution paths (or at least these decoders) to catch `Throwable`/`OutOfMemoryError` defensively, consistent with `BatchValidateSign.execute`'s existing `catch (Throwable t)` wrapper, so a single malformed transaction cannot destabilize the whole JVM.

### Proof of Concept
1. Construct calldata for `validatemultisign(address,uint256,bytes32,bytes[])` (or `batchvalidatesign(bytes32,bytes[],address[])`) where the ABI-encoded dynamic array's length word (the word at the offset pointed to by the `bytes[]`/`address[]` parameter head) is set to `0x00000000000000000000000000000000000000000000000000000000ffffffff`-class value that, when parsed via `DataWord.intValueSafe()`, yields `Integer.MAX_VALUE` (any value with more than 4 significant bytes triggers this per `intValueSafe()`).
2. Ensure `VMConfig.allowTvmSelfdestructRestriction()` is disabled (pre-activation state, or any older-synced context still executing under that ruleset).
3. Submit a transaction (`TriggerSmartContract`) that calls this precompile address with the crafted calldata via a deployed contract's fallback/proxy call, or call it directly as a precompile address target.
4. `extractBytesArray`/`extractBytes32Array` executes `new byte[Integer.MAX_VALUE][]`, throwing `OutOfMemoryError` that is not caught in `ValidateMultiSign.execute`'s call chain, propagating through `Program`/`VM.play` uncaught.

    int len = words[offset].intValueSafe();

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
