### Title
`depositAmountMin_` and `leverage_` limits are checked before mandatory fee deductions, so the user's stated bounds are silently violated - ([File: contracts/SmartFarmingManager.sol](contracts/SmartFarmingManager.sol))

### Summary
`SmartFarmingManager.leverage()` lets a user specify `leverage_` (a cap on how much debt is taken relative to collateral) and `depositAmountMin_` (a minimum final deposit, for slippage/front-run protection). Both checks are evaluated on gross, pre-fee amounts, while the protocol then deducts `issueFee` at `flashIssue` and `depositFee` inside `DepositToken.deposit`. The actual outcome can therefore be strictly worse than the bounds the user approved — the same bug class as the RealityCards `_maxSumOfPrices` check, where the limit is validated before a mandatory percentage adjustment pushes the result outside it.

### Finding Description
In `leverage()`:

- Line 173 caps `leverage_` at `1e18 / (1e18 - collateralFactor)` — the theoretical max assuming zero fees and zero swap slippage.
- `_calculateLeverageDebtAmount` (lines 228–240) computes `_debtAmount = quote(collateral→synth, (leverage_-1e18)*amountIn_)` and `flashIssue` mints that debt, but only `_issued = _debtAmount - issueFee` synth tokens reach the swapper (`DebtToken.sol` `quoteIssueOut`: `_fee = amount_.wadMul(issueFee); _amountToIssue = amount_ - _fee`, lines 369–377). The user is charged debt of `_debtAmount` while receiving less collateral-buying power.
- Line 197–198: `_depositAmount = amountIn_ + swapOut`; the `depositAmountMin_` check compares this gross underlying amount. `DepositToken.deposit(_depositAmount, _msgSender)` (line 203) then applies `depositFee`, so the shares minted to the user — and hence the collateral registered in `pool.debtPositionOf` — are strictly less than `_depositAmount` whenever `feeProvider.depositFee() > 0`.

So `depositAmountMin_` is not a real minimum on what lands in the position, and `leverage_` does not bound the realized debt-to-collateral ratio. The only backstop is the final health check (line 208), which enforces solvency, not the user's stated bounds.

### Impact Explanation
A user who computes `depositAmountMin_`/`leverage_` from quoted prices (e.g., via a UI simulating the oracle quote and expected swap output) receives a position whose collateral is up to `issueFee` + `depositFee` short of the guaranteed minimum, and whose effective leverage exceeds what they asked for. With an adverse fee configuration the extra leverage is silently absorbed by the user as higher-than-specified debt; if the position becomes unhealthy the tx reverts (only gas lost), but for moderate fees the tx succeeds while violating the user's stated slippage bound. This matches the reported impact pattern: front-run/limit protection is illusory, the user's real exposure exceeds the parameter they set.

### Likelihood Explanation
Reachable by any unprivileged caller via the public `leverage()` entry point. It is live on any deployed configuration where `feeProvider.issueFee() > 0` or `depositFee() > 0` — `FeeProvider` supports nonzero values for both, and the checks make no allowance for them. If all fees are zero on a given deployment the gap is latent rather than exploitable, so likelihood is configuration-dependent. No privileged role is required; the defect is purely in pre-fee limit validation.

### Recommendation
Validate the limits against post-fee values: compute `_debtAmount` accounting for `issueFee` (e.g., use `quoteIssueIn`), and either perform the `depositAmountMin_` comparison against the shares actually minted by `depositToken_.deposit()` (compare the returned `_deposited`/share delta, or `depositToken_.balanceOf` delta) or gross up the minimum by `depositFee` before checking. Document the fee-inclusive semantics in the UI when suggesting `depositAmountMin_`/`leverage_`.

### Proof of Concept
Hardhat scenario (same harness as `test/SmartFarmingManager.test.ts`):

```ts
// given: nonzero fees
await feeProvider.updateIssueFee(parseEther('0.1'))       // 10%
await feeProvider.updateDepositFee(parseEther('0.1'))     // 10%

// when: alice leverages 100 vaDAI -> msUSD at 1.5x, min deposit = 150
await smartFarmingManager.connect(alice).leverage(
    vaDAI.address, msdVaDAI.address, msUSD.address,
    parseUnits('100', 18), parseEther('1.5'), parseUnits('150', 18)
);

// then: depositAmountMin_ check passed on gross 150,
// but alice's registered deposit is ~135 msd shares (150 * 0.9),
// and her debt is still the full _debtAmount — her stated minimum
// was violated and her realized leverage exceeds 1.5x.
```

If the resulting position is unhealthy the tx reverts with `PositionIsNotHealthy`; for fee sizes that keep it healthy, the call succeeds with the user's limits breached — demonstrating the check-on-pre-fee-amount defect.
