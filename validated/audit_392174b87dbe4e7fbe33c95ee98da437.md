## Title
CancelAllUnfreezeV2Actuator mutates voting-power-backing frozen balances without settling pending rewards first, risking reward loss/miscalculation - (File: `actuator/src/main/java/org/tron/core/actuator/CancelAllUnfreezeV2Actuator.java`)

## Summary
Every other resource/stake-mutating actuator in java-tron settles a user's accrued voting reward via `mortgageService.withdrawReward()` / `VoteRewardUtil.withdrawReward()` *before* changing the account's frozen balance or TRON_POWER weight that backs its voting power. `CancelAllUnfreezeV2Actuator` (and its TVM counterpart `CancelAllUnfreezeV2Processor`) is the sole exception: it directly mutates `BANDWIDTH`/`ENERGY`/`TRON_POWER` frozen balances to "undo" a pending unfreeze without ever calling `withdrawReward`, breaking the invariant the reward-accounting system depends on.

## Finding Description
In `MortgageService.withdrawReward()` [1](#0-0) , reward accounting is lazy: it tracks `beginCycle`/`endCycle` in `delegationStore` and computes reward for the range `[beginCycle, endCycle)` using the account's **current, live** `getVotesList()` as a stand-in for what the votes were during that whole range. This is only correct because every function that changes an account's voting-power-backing state (frozen balance, TRON_POWER, votes) is required to first call `withdrawReward` to "close the books" up to the current cycle before the change is applied:

- `UnfreezeBalanceActuator.execute()` calls `mortgageService.withdrawReward(ownerAddress)` before touching frozen balance/TRON_POWER. [2](#0-1) 
- `UnfreezeBalanceV2Actuator.execute()` does the same before calling `updateVote(...)`. [3](#0-2) 
- `WithdrawBalanceActuator.execute()` does the same before adjusting balance/allowance. [4](#0-3) 
- `UnfreezeBalanceProcessor.execute()` (TVM native contract) calls `VoteRewardUtil.withdrawReward` before clearing votes when TronPower drops below used vote count. [5](#0-4) 
- `UnfreezeBalanceV2Processor.execute()` (TVM native contract) also calls `VoteRewardUtil.withdrawReward` first. [6](#0-5) 

By contrast, `CancelAllUnfreezeV2Actuator.execute()` reads the account's `unfrozenV2List`, restores `BANDWIDTH`/`ENERGY`/`TRON_POWER` frozen amounts via `updateFrozenInfoAndTotalResourceWeight(...)`, and updates total resource weights and balance — all without ever calling `mortgageService.withdrawReward()`: [7](#0-6) 

The TVM equivalent `CancelAllUnfreezeV2Processor.execute()` has the identical omission. [8](#0-7) 

This is directly analogous to `Migration.sol`'s `moveFundsToUpgradedContract()` calling `instantUnstake(false)`, which mutates stake state while skipping the reward-settlement step ("optional rebase") that every sibling function performs, causing users to forfeit pending rewards.

## Impact Explanation
Because `CancelAllUnfreezeV2Actuator`/`Processor` re-freeze TRON_POWER-backing balance without first snapshotting/settling the reward cycle boundary, any account that (a) has an outstanding, un-withdrawn reward accrued under its prior TronPower/vote state, and (b) triggers `CancelAllUnfreezeV2` to restore frozen resources, has its `beginCycle`/`endCycle` bookkeeping left stale relative to the newly restored TronPower. This breaks the accounting invariant relied upon by `MortgageService.computeReward()`, which assumes vote/TronPower-affecting state is frozen for any un-settled cycle range. Depending on subsequent actions, this can result in reward under-computation (forfeiture of legitimately accrued reward for the affected cycles) — a fund-loss condition for the account owner, reachable by any user simply broadcasting a `CancelAllUnfreezeV2Contract` transaction.

## Likelihood Explanation
`CancelAllUnfreezeV2Contract` is a standard, unprivileged transaction type available to any account (once the chain parameter `AllowCancelAllUnfreezeV2` is enabled by committee, as validated in `validate()` [9](#0-8) ), and can also be triggered via the TVM opcode path (`cancelAllUnfreezeV2Action` in `OperationActions.java`). Any account with pending unfrozen-but-not-yet-withdrawn stake and unclaimed reward can trigger this simply by calling the standard unfreeze-cancel flow, making the trigger condition easy to reach without any special privilege.

## Recommendation
Add a call to `mortgageService.withdrawReward(ownerAddress)` (and for the TVM path, `VoteRewardUtil.withdrawReward(ownerAddress, repo)`) at the start of `CancelAllUnfreezeV2Actuator.execute()` and `CancelAllUnfreezeV2Processor.execute()`, mirroring the pattern used in `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `UnfreezeBalanceProcessor`, and `UnfreezeBalanceV2Processor`, so that reward accounting is settled before the account's frozen/TronPower state is mutated.

## Proof of Concept
1. Account `A` freezes TRX for TRON_POWER and votes for witness `W`; rewards begin accruing each cycle in `delegationStore` under `A`'s vote snapshot.
2. `A` submits `UnfreezeBalanceV2Contract` for part of its TRON_POWER — this correctly calls `mortgageService.withdrawReward(A)` first (settling rewards up to the current cycle) before the frozen balance is reduced. [10](#0-9) 
3. Several cycles pass with `A`'s reduced TronPower/vote state (rewards continue to accrue under the now-lower vote weight, tracked from the new `beginCycle`).
4. Before calling `WithdrawReward`/another reward-settling actuator, `A` submits `CancelAllUnfreezeV2Contract` to restore the unfrozen TRON_POWER back to frozen. `CancelAllUnfreezeV2Actuator.execute()` restores the frozen weight/TronPower directly without calling `withdrawReward` first. [11](#0-10) 
5. `A`'s `beginCycle`/`endCycle` in `delegationStore` remain stale relative to the newly restored TronPower, and the next `withdrawReward` call computes reward over the stale range using vote/weight assumptions that no longer match what was actually in effect, causing incorrect (forfeited or reduced) reward payout for the intervening cycles.

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }

  public Map<String, Long> execute(CancelAllUnfreezeV2Param param, Repository repo) throws ContractExeException {
    Map<String, Long> result = new HashMap<>();
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long now = repo.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    long withdrawExpireBalance = 0L;
    for (Protocol.Account.UnFreezeV2 unFreezeV2: ownerCapsule.getUnfrozenV2List()) {
      if (unFreezeV2.getUnfreezeExpireTime() > now) {
        String resourceName = unFreezeV2.getType().name();
        result.put(resourceName, result.getOrDefault(resourceName, 0L) + unFreezeV2.getUnfreezeAmount());

        updateFrozenInfoAndTotalResourceWeight(ownerCapsule, unFreezeV2, repo);
      } else {
        // withdraw
        withdrawExpireBalance += unFreezeV2.getUnfreezeAmount();
      }
    }
    if (withdrawExpireBalance > 0) {
      ownerCapsule.setBalance(ownerCapsule.getBalance() + withdrawExpireBalance);
    }
    ownerCapsule.clearUnfrozenV2();

    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);

    result.put(VMConstant.WITHDRAW_EXPIRE_BALANCE, withdrawExpireBalance);
    return result;
  }
