### Title
Double-termination of gRPC `StreamObserver` (`onError` followed by unconditional `onCompleted`) crashes RPC call handling in `RpcApiService` - (File: `framework/src/main/java/org/tron/core/services/RpcApiService.java`)

### Summary
The Envoy CVE describes a crash class where an operation (`sendOverloadError`) assumes a request/stream object is still live and touches it after it has already been terminated/reset. `RpcApiService.java` contains the same bug-class pattern in dozens of gRPC service methods: on exception, `responseObserver.onError(e)` is called (which terminates the gRPC call), and execution then falls through to an unconditional `responseObserver.onCompleted()` call on the same, already-closed `StreamObserver`.

### Finding Description
gRPC's `StreamObserver` contract requires exactly one terminal call (`onError` XOR `onCompleted`) per call lifecycle. Once `onError()` is invoked, the underlying `ServerCall` is closed. Many handlers in `RpcApiService` do not `return` after calling `onError()` in their `catch` block, so the subsequent `responseObserver.onCompleted()` statement always executes regardless of whether the exception path was taken: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

This exact same shape (`onError(...)` in `catch`, then unconditional `onCompleted()` right after) recurs across many other public gRPC methods in the same file (`getDelegatedResourceV2`, `getDelegatedResourceAccountIndex`, `getCanDelegatedMaxSize`, `getAvailableUnfreezeCount`, `scanNoteByIvk`, `isSpend`, `scanShieldedTRC20NotesByIvk`, `getMarketOrderByAccount`, `getMarketOrderById`, `getCanWithdrawUnfreezeAmount`, `getNodeInfo`, etc.), all reachable directly from unauthenticated gRPC clients: [5](#0-4) [6](#0-5) 

When any exception is thrown inside the `try` block (e.g. `IllegalArgumentException`, `StoreException`, decode errors on attacker-controlled bytes such as `request.getValue()`, `request.getIvk()`, `request.getOwnerAddress()`), `onError()` closes the call, and the immediately following `onCompleted()` call operates on an already-terminated stream — mirroring the Envoy pattern of an operation assuming the request object is still active when it has, in fact, already been finalized/reset.

### Impact Explanation
Calling a terminal method on a `ServerCallStreamObserver` after it has already been closed via `onError()` throws an `IllegalStateException` ("call already closed"/"call is closed") from within the gRPC-generated method implementation. This is an uncaught runtime exception escaping the service method during request processing on the gRPC handling thread for that call. Any unauthenticated client can trigger it simply by sending a malformed/edge-case gRPC request (e.g., a `BytesMessage` value that fails validation, or a lookup that throws `StoreException`) to any of the dozens of affected wallet/gRPC methods. Depending on how the exception propagates through the gRPC/Netty transport layer, this can abnormally terminate the in-flight call and, in adverse conditions (e.g., exceptions escaping into the network/event-loop thread), degrade or crash the gRPC service, denying the wallet/gRPC API to all other clients on the node.

### Likelihood Explanation
High reachability: this is triggered directly by a single unauthenticated gRPC request to any of the many affected `WalletApi`/`Wallet`/`WalletSolidity` methods in `RpcApiService`, with no special privileges, staking, or prior state setup required — an attacker only needs to cause the `try` block to throw (many of these methods parse or forward raw request bytes that can trip validation exceptions or store lookups).

### Recommendation
Add `return;` immediately after every `responseObserver.onError(...)` call inside these methods so `onCompleted()` is never invoked following an error, e.g.:
```java
} catch (Exception e) {
  responseObserver.onError(e);
  return;
}
responseObserver.onCompleted();
```
Apply this fix uniformly across all affected methods in `RpcApiService.java` (and any other classes following the same `Common` helper pattern, e.g. `getRewardInfoCommon`, `getBurnTrxCommon`, `getBrokerageInfoCommon`, `getTransactionFromPendingCommon`, `getTransactionListFromPendingCommon`, `getPendingSizeCommon`, `getBlockCommon`).

### Proof of Concept
1. Send a gRPC `getBlock` request (or `getTransactionInfoByBlockNum`/any of the listed RPCs) with a malformed/edge-case argument that causes `wallet.getBlock(request)` to throw (e.g., an `IllegalArgumentException` for an invalid block identifier), as handled in `getBlockCommon`: [4](#0-3) 
2. The `catch` block calls `responseObserver.onError(...)`, closing the call.
3. Execution falls through to the unconditional `responseObserver.onCompleted()` on line 2769, which operates on the already-closed `StreamObserver` and throws `IllegalStateException` inside gRPC's call-handling code.
4. Repeat against any of the other affected methods (e.g. `getPendingSizeCommon`, `getTransactionFromPendingCommon`) to reproduce the same double-termination fault across the gRPC surface exposed to any client.

Note: I was unable to fully verify from the indexed code whether the gRPC server in this build uses a `directExecutor()` (which would let the exception hit the Netty I/O thread directly, causing broader crash impact) or a separate application executor (which would confine the failure to the single call) — the executor configuration in `framework/src/main/java/org/tron/common/application/RpcService.java` was found but not fully read due to iteration limits. This affects the exact blast radius (single-call failure vs. broader service crash) but does not change the fact that the double-termination bug itself is real and reachable by any unauthenticated gRPC client.
