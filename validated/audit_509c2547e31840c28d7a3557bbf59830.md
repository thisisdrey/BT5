### Title
`Pool.liquidate` dead zone: positions with debt below ~2× `debtFloorInUsd` can never be liquidated, permanently trapping bad debt - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The CORBA-dissector CVE is a "crafted input crashes/denies service" class bug. The Metronome analog is a crafted-position denial of service in liquidation: the combination of the `maxLiquidable` cap and the `debtFloorInUsd` check creates a debt range in which every possible `liquidate` call reverts, so an attacker can open a position that becomes permanently unliquidatable once it goes underwater.

### Finding Description
`Pool.liquidate` enforces two checks on `amountToRepay_`:

1. The repay amount cannot exceed `maxLiquidable` (default 50%) of the account's debt token balance — otherwise it reverts `AmountGreaterThanMaxLiquidable`. Since `amountToRepay_ / _debtTokenBalance <= maxLiquidable < 1e18`, a full repayment (remaining debt = 0) is impossible.
2. If `debtFloorInUsd > 0`, the remaining debt after the liquidation must be either zero or `>= debtFloorInUsd` — otherwise it reverts `RemainingDebtIsLowerThanTheFloor`. [1](#0-0) 

Because full repayment is blocked by check 1, the remaining debt is always in `[debt − maxLiquidable·debt, debt)`. With `maxLiquidable = 0.5e18`, the minimum achievable remaining debt is `0.5 · debt`. Therefore, whenever the position's total debt value `D_usd` satisfies `0 < D_usd < 2 · debtFloorInUsd` (approximately, modulo oracle quoting), every allowed repay amount leaves a remainder `> 0` and `< debtFloorInUsd`, so the liquidation always reverts. There is no `amountToRepay_` an honest or motivated liquidator can pass that succeeds — a hard liveness failure driven purely by the attacker's chosen position size.

### Impact Explanation
An unprivileged attacker opens a position whose debt is inside the dead zone (e.g., mints `D < 2·debtFloorInUsd` of a synthetic asset against cheap collateral), then lets the position become unhealthy through normal market movement (or forces it via allowed same-transaction price manipulation). From that point:

- `liquidate` reverts for every `amountToRepay_` — the debt can never be closed by anyone.
- The collateral backing the debt is permanently locked in the position (`DepositToken.seize` is only reachable through `liquidate`), while the protocol carries the defaulted synthetic debt — direct insolvency/bad debt that cannot be socialized.
- Attackers can mass-produce such dust positions cheaply, accumulating unrecoverable bad debt.

The invariant that breaks is the liquidation bound/solvency guarantee: "any unhealthy position can be liquidated" does not hold inside the dead zone.

### Likelihood Explanation
- No privileged role is needed: `DebtToken.issue`/`mint` and `Pool.liquidate` are public; the attacker only needs collateral and picks the debt size.
- `debtFloorInUsd` is a real deployed parameter (it's intended to keep liquidation profitable for liquidators); whenever it is non-zero the dead zone exists. With `maxLiquidable = 0.5e18` the dead zone is `D_usd ∈ (0, 2·floor)`; a rational liquidator cannot rescue these positions even at zero profit.
- Modifiers don't help: `whenNotShutdown`, `nonReentrant`, `onlyIfSyntheticTokenExists`, `onlyIfDepositTokenExists`, `PositionIsHealthy` all pass — the revert is intrinsic to the two numeric checks.
- Caveat: severity is bounded by `debtFloorInUsd` (small debts only) and requires the position to turn unhealthy, so this is medium-severity griefing/insolvency rather than direct theft — matching the medium-severity DoS class of the reference CVE.

### Recommendation
Allow full repayment when it is the only viable liquidation: either
- skip the `maxLiquidable` check when `amountToRepay_ == _debtTokenBalance` (i.e., permit closing the position entirely), or
- treat "remaining debt < floor" as a signal to force/require full repayment instead of reverting.

```solidity
// contracts/Pool.sol — suggested fix direction
if (amountToRepay_ > _debtTokenBalance.wadMul(maxLiquidable) && amountToRepay_ < _debtTokenBalance) {
    revert AmountGreaterThanMaxLiquidable();
}
// then allow _newDebtInUsd == 0 without hitting the floor revert
```

### Proof of Concept
Hardhat fork sketch (matches the existing `test/Pool.test.ts` harness, which already demonstrates both reverts independently — `test/Pool.test.ts:408-436` shows the floor revert and that full repay is only possible in tests because `maxLiquidable` behavior differs):

```ts
// setup: pool with debtFloorInUsd = $3,000, maxLiquidable = 50% (defaults)
await pool.updateDebtFloor(parseEther('3000'));

// attacker deposits collateral and mints debt in the dead zone:
// debt value D = $4,000  =>  D < 2*floor ($6,000)
await msdMET.connect(attacker).deposit(collateralAmount);
await msEthDebtToken.connect(attacker).issue(debtFor4000Usd, attacker.address);

// price drops -> position unhealthy
await masterOracle.updatePrice(met.address, lowerPrice);

// liquidation attempt 1: repay 50% (max allowed) -> remaining $2,000 < floor
await expect(
  pool.connect(liq).liquidate(msEth.address, attacker.address, debt.div(2), msdMET.address)
).revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');

// liquidation attempt 2: repay 100% -> exceeds maxLiquidable
await expect(
  pool.connect(liq).liquidate(msEth.address, attacker.address, debt, msdMET.address)
).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

// every intermediate amount reverts one check or the other:
// the position is permanently unliquidatable.
```

The two reverts are already independently exercised by the repo's own tests (`RemainingDebtIsLowerThanTheFloor` at `test/Pool.test.ts:420`, `AmountGreaterThanMaxLiquidable` at `test/Pool.test.ts:405,450`); the PoC shows they are jointly unsatisfiable for the same position.
