### Title
`os.RemoveAll("./")` silently deletes all contents of the current directory, bypassing the `.`-protection check - ([File: src/os/removeall_at.go])

### Summary
`os.RemoveAll` refuses to remove `"."` via `endsWithDot`, but that check only matches a path whose *last character* is `.` (e.g. `"."`, `"foo/."`). It does not match `"./"` (or other trailing-slash variants of `.`), so `RemoveAll("./")` skips the guard, falls through to the recursive deletion logic, and ends up recursively unlinking every entry in the current directory before finally failing to remove `.` itself — mirroring the `uu_rm` `rm -rf ./` bug exactly (dot-protection bypassed by a trailing slash, contents destroyed, then a misleading terminal error).

### Finding Description
`os.RemoveAll(path)` calls `removeAll` in [1](#0-0) , which only rejects paths caught by `endsWithDot`: [2](#0-1) 

`endsWithDot("./")` is `false` because the final byte is `/`, not `.`, so the guard is bypassed for `"./"` (and similarly `".//"`, `"././"`, etc., since only `splitPath`/trailing-slash handling downstream does trimming, not the dot check).

Execution then proceeds: `Remove("./")` in [3](#0-2)  tries `unlink` then `rmdir` on `"./"`; the kernel rejects both (rmdir with a trailing "." component returns `EINVAL`), so `Remove` returns an error and `removeAll` falls into the recursive branch: [4](#0-3) 

`splitPath("./")` normalizes to `parentDir="."`, `base="."` (verified from `path_unix.go`'s trailing-slash stripping logic), so `removeAllFrom` is invoked with `base="."` against the current directory's own file descriptor: [5](#0-4) 

`removefileat(parentFd, ".")` fails with `EISDIR`, so the function opens `"."` *relative to itself* (i.e., re-opens the current directory) and iterates its `Readdirnames`, recursively calling `removeAllFrom` on every entry it finds — deleting all files and subdirectories in the current working directory: [6](#0-5) 

Finally it attempts `removedirat(parentFd, ".")`, which the kernel refuses (removing `.` is disallowed), so the call returns a `PathError` (`Op: "unlinkat", Path: "."`, `EINVAL`) even though all directory contents have already been unlinked — the same "misleading terminal error after destructive deletion" pattern described in the advisory.

### Impact Explanation
Any caller of `os.RemoveAll("./")` — or of `os.Root.RemoveAll` variants that reach the same `endsWithDot`/`removeAllFrom` code path — silently loses every file and subdirectory in the current directory, receiving only a generic `RemoveAll ./: invalid argument`-style error instead of a clear rejection like `RemoveAll(".")` correctly produces (verified passing for `"."` in `src/os/removeall_test.go:190-196`). This is a material, irreversible file-write/deletion impact (CWE-22/CWE-693 class: protective check bypassed by an equivalent-but-differently-formatted path). Given `os.RemoveAll` is one of the most widely used destructive filesystem primitives in the Go ecosystem (build tools, CI scripts, package managers, test harnesses that clean up working directories), this would likely be assessed on Go's **PUBLIC** track once confirmed, as a data-loss safety regression rather than a remote-exploitation vulnerability.

### Likelihood Explanation
Trigger requires only an ordinary, unprivileged local caller passing the path string `"./"` (or an equivalent trailing-dot-slash variant) to `os.RemoveAll` — a very plausible operator/typo scenario (analogous to `rm -rf ./`), or a case where a program constructs a "clean current directory" path via naive string concatenation (e.g. `dir + "/"` where `dir == "."`). No privilege escalation or attacker-controlled remote input is needed beyond an unprivileged user invoking the API/CLI with this argument, matching the same "ordinary user workflow" premise as the original `uu_rm` finding.

### Recommendation
Extend `endsWithDot` (or add an explicit pre-check in `removeAll`/`rootRemoveAll`) to also treat trailing-slash-normalized `.`/`..` forms (`"./"`, `".//"`, `"../"`, etc.) as equivalent to `"."`, e.g., strip trailing path separators before running the `endsWithDot` check in `src/os/removeall_at.go`, consistent with what `src/os/removeall_noat.go` and `src/os/root_openat.go`'s `rootRemoveAll` already do (they strip trailing slashes *before* calling `endsWithDot`). Applying the same trailing-slash trim in `removeall_at.go` before the `endsWithDot` guard closes the bypass.

### Proof of Concept
```go
package os_test

import (
	"os"
	"testing"
)

func TestRemoveAllDotSlashDeletesContents(t *testing.T) {
	dir := t.TempDir()
	if err := os.Mkdir(dir+"/sub", 0777); err != nil {
		t.Fatal(err)
	}
	wd, _ := os.Getwd()
	defer os.Chdir(wd)
	if err := os.Chdir(dir); err != nil {
		t.Fatal(err)
	}

	err := os.RemoveAll("./")
	// Expected (safe) behavior: RemoveAll("./") should fail like
	// RemoveAll(".") without touching directory contents.
	if _, statErr := os.Stat("sub"); statErr != nil {
		t.Fatalf("RemoveAll(\"./\") deleted directory contents (sub missing); RemoveAll err=%v", err)
	}
}
```
On the affected code, `sub` is deleted and the assertion fails (demonstrating the bypass); the fix should make `RemoveAll("./")` behave identically to `RemoveAll(".")`, returning an error without deleting `sub`.

// endsWithDot reports whether the final component of path is ".".
func endsWithDot(path string) bool {
	if path == "." {
		return true
	}
	if len(path) >= 2 && path[len(path)-1] == '.' && IsPathSeparator(path[len(path)-2]) {
		return true
	}
	return false

func Remove(name string) error {
	// System call interface forces us to know
	// whether name is a file or directory.
	// Try both: it is cheaper on average than
	// doing a Stat plus the right one.
	e := ignoringEINTR(func() error {
		return syscall.Unlink(name)
	})
	if e == nil {
		return nil
	}
	e1 := ignoringEINTR(func() error {
		return syscall.Rmdir(name)
	})
	if e1 == nil {
		return nil
	}

	// Both failed: figure out which error to return.
	// OS X and Linux differ on whether unlink(dir)
	// returns EISDIR, so can't use that. However,
	// both agree that rmdir(file) returns ENOTDIR,
	// so we can use that to decide which error is real.
	// Rmdir might also return ENOTDIR if given a bad
	// file path, like /etc/passwd/foo, but in that case,
	// both errors will be ENOTDIR, so it's okay to
	// use the error from unlink.
	if e1 != syscall.ENOTDIR {
		e = e1
	}
	return &PathError{Op: "remove", Path: name, Err: e}
}
