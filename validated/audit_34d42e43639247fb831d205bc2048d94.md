Confirmed: `setNetUsage`/`setEnergyUsage` in `AccountCapsule` perform no negativity check — they just set the value directly. [1](#0-0) [2](#0-1) 

### Title
Unchecked, ratio-derived `transferUsage` subtraction can drive a delegatee's `NetUsage`/`EnergyUsage` negative in `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`, `actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java`)

### Summary
`UnDelegateResourceActuator.execute()` (and its TVM-native twin `UnDelegateResourceProcessor.execute()`) update the receiving account's bandwidth/energy usage counters by subtracting a `transferUsage` value that is *estimated* from a linear proportionality formula (`receiverCapsule.getNetUsage() * (unDelegateBalance / receiverCapsule.getAllFrozenBalanceForBandwidth())`), rather than the actual usage consumed against the specific delegation being withdrawn. This is structurally the same pattern as the `PerpDepository.netAssetDeposits` bug: an auxiliary "shadow" accounting counter (`NetUsage`/`EnergyUsage`) is incremented on one side (resource consumption) and decremented on another (undelegation) using values computed by two different, independent formulas that are not guaranteed to reconcile.

### Finding Description
When an owner un-delegates only part of the resource they had delegated to a receiver who has multiple delegators/multiple delegations with differing timing, `transferUsage` is derived purely from the ratio `unDelegateBalance / getAllFrozenBalanceForBandwidth()` multiplied against the receiver's *total* current `NetUsage`. This ignores which specific delegation actually generated that usage. [3](#0-2) 

Because `receiverCapsule.getAllFrozenBalanceForBandwidth()` includes the receiver's own frozen balance plus all acquired-delegated balances from every delegator (old-model and new-model), and `getNetUsage()` reflects consumption across all of that combined pool, `transferUsage` can be computed larger than what remains reasonable for the receiver once other delegators have already had their usage "clawed back" by earlier un-delegations, or when the receiver's usage decays/recovers between calls (`BandwidthProcessor.updateUsageForDelegated` / `EnergyProcessor.updateUsage` run first, but they do not tie usage back to a specific delegator). The result, `newNetUsage = receiverCapsule.getNetUsage() - transferUsage`, is then written unconditionally via `setNetUsage`/`setEnergyUsage`, which perform no floor-at-zero or negativity check. [4](#0-3) [5](#0-4) 

Note the only guard present is `min(unDelegateMaxUsage, transferUsage)` which caps `transferUsage` by an independently-computed `unDelegateMaxUsage` (based on global `TotalNetLimit`/`TotalNetWeight` ratios) — this bound does not guarantee `transferUsage <= receiverCapsule.getNetUsage()`, since it is derived from a completely different ratio (global network limit vs. per-account usage). There is no explicit check equivalent to the `PerpDepository._withdrawAsset` guard (`if (amount > netAssetDeposits) revert`), so the corrupted (negative) usage silently persists in state rather than reverting — arguably worse than the original report, since it corrupts on-chain accounting instead of just reverting a withdrawal.

This mirrors the reported bug class exactly: a persistent counter (`netAssetDeposits` / here `NetUsage`/`EnergyUsage`) is maintained by two independently-computed deltas (deposit amount vs. redeemed amount / consumed usage vs. ratio-estimated "transfer" usage) that are not mathematically guaranteed to be consistent, leading to state corruption (negative accounting) once assumptions about proportionality break down — the analog differs only in that java-tron does not revert on underflow (there is no explicit check here), so the negative value is persisted.

### Impact Explanation
A negative `NetUsage`/`EnergyUsage` corrupts the receiver's bandwidth/energy accounting. Downstream, usage values feed into free/paid bandwidth and energy limit calculations (e.g., `BandwidthProcessor`, `EnergyProcessor`, `FreezeV2Util.getV2NetUsage`/`getV2EnergyUsage`, which do clamp with `max(0, ...)` in some call sites but not universally). A permanently negative or artificially-suppressed usage value can let the receiving account bypass consumption limits (effectively unlimited "free" resource for a period), which is an unbacked-resource/accounting-integrity issue reachable purely by a sequence of `DelegateResource` + partial `UnDelegateResource` transactions from an unprivileged account, with no special privileges required — the account triggering it can be the delegator itself using multiple partial undelegations, or by inducing a receiver to receive delegations from multiple sources with staggered timing.

### Likelihood Explanation
Medium likelihood: it requires a receiver that has resources delegated from more than one source (or the same source across multiple non-atomic delegate/undelegate cycles) with usage consumption interleaved between them, so that the linear proportional estimate diverges from the receiver's true remaining usage tied to the specific balance being withdrawn. This is a normal, permissionless usage pattern (any account can delegate bandwidth/energy to any other account and later partially undelegate), not an edge-case requiring elevated privileges, but it does require specific sequencing of transactions to trigger the divergence — similar to the "specific requirements" caveat that got the original Sherlock issue downgraded to Medium.

### Recommendation
- Track usage per-delegation (or cap `transferUsage` explicitly at `min(transferUsage, receiverCapsule.getNetUsage())` / `min(transferUsage, receiverCapsule.getEnergyUsage())`) before subtraction in both `UnDelegateResourceActuator.execute()` and `UnDelegateResourceProcessor.execute()`.
- Add an explicit floor-at-zero clamp in `AccountCapsule.setNetUsage`/`setEnergyUsage`, or at minimum at the call sites in `UnDelegateResourceActuator`/`UnDelegateResourceProcessor`, mirroring the safe pattern already used elsewhere (e.g., `FreezeV2Util.getV2NetUsage` uses `max(0, ...)`).
- Consider eliminating the proportional "usage transfer" heuristic altogether in favor of a model that recomputes usage strictly from remaining frozen/delegated balances at the time of undelegation, removing the dependency on an independently-drifting shadow counter.

### Proof of Concept
1. Account `R` (receiver) obtains delegated BANDWIDTH from two different owners, `A` (large amount) and `B` (small amount), via `DelegateResourceContract`.
2. `R` consumes bandwidth (e.g., issues several transactions), increasing `R.NetUsage` — the increase is not attributed per-delegator, it's a single pooled counter.
3. Owner `A` calls `UnDelegateResourceContract` to withdraw a large portion of the delegated balance. `transferUsage` is computed as `R.NetUsage * (unDelegateBalance_A / R.getAllFrozenBalanceForBandwidth())`, subtracting a large chunk of `R.NetUsage`. [6](#0-5) 

4. Shortly after, owner `B` also calls `UnDelegateResourceContract` for their (small) delegation. The formula again computes a `transferUsage` based on `R.NetUsage` (already reduced) times `unDelegateBalance_B / R.getAllFrozenBalanceForBandwidth()` (now a smaller denominator since `A`'s balance was removed) — this can still yield a `transferUsage` exceeding what remains of `R.NetUsage`, since the proportional formula assumes usage is linearly divisible by frozen-balance share, which is not true when usage was concentrated in a narrow time window/originating largely from `A`'s frozen capacity.
5. `newNetUsage = R.getNetUsage() - transferUsage` goes negative and is persisted via `setNetUsage(newNetUsage)` with no validation — `R`'s bandwidth accounting is now corrupted (negative usage), effectively granting `R` unlimited "banked" free bandwidth until usage naturally grows back past zero.

Note: I was not able to execute this scenario in a live test environment; the trace above is based on static analysis of the arithmetic and the absence of any negativity guard in `AccountCapsule.setNetUsage`/`setEnergyUsage`. A background Devin session with test execution capability could construct a concrete `UnDelegateResourceActuatorTest` scenario (multiple delegators, interleaved usage, partial undelegations) to confirm the negative value is actually reachable end-to-end and to quantify the resulting bypass of resource limits.
