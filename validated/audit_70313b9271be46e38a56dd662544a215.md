### Title
Non-constant-time `Authorization` header comparison enables timing side-channel secret recovery - (File: stackslib/src/net/api/fastcallreadonly.rs)

### Summary
`RPCFastCallReadOnlyRequestHandler::try_parse_request` gates the `/v3/contracts/fast-call-read` endpoint with a plain `!=` comparison between the caller-supplied `Authorization` header and the configured secret (`self.auth`). Because `String`/`str` inequality in Rust is not constant-time, the check can leak information about how many leading bytes of the guess match the real secret through response-timing differentials, allowing byte-by-byte secret recovery by a remote, unprivileged attacker.

### Finding Description
The guard is: [1](#0-0) 

`auth_header != password` compares two `String`s using the standard library's byte-slice equality, which begins by comparing lengths and then performs a byte comparison that can terminate as soon as a mismatch is found (rather than always visiting every byte in fixed time). This gives an attacker who can send crafted `Authorization` header values and measure response latency a mechanism to infer, byte-by-byte, how far their guess matches `self.auth`, since a longer common prefix causes more comparison work before the mismatch is detected (or a full match, in which case the request proceeds down the much more expensive Clarity-execution path).

The endpoint is reachable via any legitimate RPC connection to the node — no signature, session token, StackerDB slot ownership, or peer status is required prior to this check; the only "secret" involved is `self.auth` itself, which is exactly what the attacker is trying to recover. Once the header exactly equals the password, the handler proceeds to run arbitrary read-only Clarity function calls with `LimitedCostTracker::new_free()` (unmetered cost tracking), as seen in `try_handle_request`: [2](#0-1) 

No existing guard mitigates the timing channel: there is no `MAX_MESSAGE_LEN` limitation on the comparison itself, no rate limiting on repeated attempts, and no constant-time comparison primitive (e.g. `subtle::ConstantTimeEq`) used anywhere in this handler. The same insecure pattern (`!= password` on the auth header) is repeated verbatim across other endpoints in the codebase (`postblock_proposal.rs`, `postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`), confirming this is a systemic implementation choice rather than a one-off typo.

### Impact Explanation
If successfully exploited, an attacker recovers the shared secret `auth` used to protect the fast-call-read endpoint, fully bypassing authorization. Once in possession of the secret, the attacker gains a standing ability to invoke unmetered, attacker-chosen Clarity contract-call execution (`new_free()` cost tracker) against the node's Clarity VM, at will and repeatably — a bounded-compute-DoS/auth-bypass primitive against a specific node. This matches the "request smuggling or auth bypass" and "bounded compute DoS on a read endpoint" categories called out as in-scope Critical/High impacts.

### Likelihood Explanation
Exploitation preconditions: the operator must have configured `auth` (i.e., the endpoint is enabled) and be reachable to the attacker over the RPC port — both are baseline conditions for the endpoint to function at all, with no special peer/config/tip state, StackerDB ownership, or admin role needed. The attacker needs only the ability to send arbitrary HTTP requests and measure timing, satisfying the "unprivileged remote attacker" threat model. Practical difficulty comes from network jitter reducing the timing signal-to-noise ratio; recovering the secret reliably over a real network typically requires many repeated samples per byte position (statistical averaging) and is more feasible when attacker and node are close on the network (e.g., same datacenter/cloud region) — this is a known, previously-demonstrated class of remote timing attack against string-equality secret checks, not merely theoretical, though it is more costly than a pure local timing attack.

### Recommendation
Replace the direct `!=` string comparison with a constant-time comparison, e.g. using the `subtle` crate's `ConstantTimeEq` on the byte representations of `auth_header` and `password` (after first checking/normalizing lengths in a way that does not leak length quickly, or comparing fixed-length hashes such as HMAC of the header value with a server-side key). Apply the same fix uniformly to all other handlers using the identical `!= password` pattern (`postblock_proposal.rs`, `postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`).
