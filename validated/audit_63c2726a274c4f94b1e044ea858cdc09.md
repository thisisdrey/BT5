### Title
Any caller can link an arbitrary repository to any object pool, causing unauthorized cross-repository object disclosure - (File: `internal/gitaly/service/objectpool/link.go`)

### Summary
`LinkRepositoryToObjectPool` accepts any `Repository` and any `ObjectPool` that share a storage and grants the repository read access to every object stored in the pool via Git alternates, with no check that the repository is actually a fork/descendant of the pool it is being linked to.

### Finding Description
The RPC handler only validates that the target repository is well-formed and that the pool resolves to a valid Git repository, then unconditionally writes the pool's path into the repository's `objects/info/alternates` file: [1](#0-0) 
`poolForRequest` merely loads whatever `ObjectPool` protobuf was supplied by the caller — it does not verify any prior relationship (e.g. that the pool was created from the target repository, or that the caller is authorized for both repositories): [2](#0-1) 
The actual linking logic in `objectpool.Link` performs no ownership/ancestry check either — it just computes the relative alternates path and writes it, refusing only if an alternates file with *different* unexpected content already exists: [3](#0-2) 
The only cross-storage guard present in the object pool RPCs is a storage-name equality check in `FetchIntoObjectPool`, and equivalent request-level validation in `LinkRepositoryToObjectPool` is limited to repository well-formedness, not pool/repo relationship: [4](#0-3) 
Once linked via alternates, Git treats every object in the pool as if it were local to the linked repository — this is confirmed by the object-pool design doc, which states alternates are what let object pool members "see" pool objects: [5](#0-4) 
This is directly analogous to the reported bug class: just as `mintCollateralToken()` let any role holder create arbitrary token balances without verifying a legitimate underlying claim, `LinkRepositoryToObjectPool` lets any caller "mint" access to an arbitrary pool's entire object graph into an arbitrary repository without verifying a legitimate fork/ownership relationship between the two repositories.

### Impact Explanation
Because alternates make all objects in the pool directly readable through the linked repository (via `git-cat-file`, `TreeEntry`, `GetBlob`, archive/export RPCs, etc.), an attacker who can invoke `LinkRepositoryToObjectPool` for two repositories they do not both legitimately control could exfiltrate objects (blobs, commits, trees — potentially containing secrets or private code) from a completely unrelated repository/object pool by linking their own repository to it. This is a cross-repository object disclosure vulnerability, one of the explicitly accepted analog categories.

### Likelihood Explanation
Exploitability depends on whether the calling layer (e.g., GitLab Rails / Praefect routing) enforces that the `Repository` and `ObjectPool` in the request belong to the same project/namespace before invoking this RPC. Within Gitaly itself, there is no such enforcement — the check is purely storage/path based (`ValidateRepository`, pool must resolve to a valid Git repo, must be in the same storage/partition due to the transactional partitioning constraints seen in `middleware.go`). If any component that has access to invoke this internal RPC (or any request forwarding/impersonation short of full trust) can supply an arbitrary combination of repository and pool references, the disclosure is straightforward and requires no privilege beyond calling this single mutator RPC.

### Recommendation
Add an authorization/ownership check inside `LinkRepositoryToObjectPool` (or at the layer that constructs these requests) verifying that the target repository is a legitimate, already-established member of the given object pool's lineage (e.g., matches recorded pool metadata / fork relationship) before writing the alternates file, rather than trusting the caller-supplied `ObjectPool` and `Repository` pairing implicitly.

### Proof of Concept
1. Create object pool `A` from repository `RepoA` via `CreateObjectPool`.
2. Create unrelated repository `RepoB` (not derived from `RepoA`) in the same storage.
3. Call `LinkRepositoryToObjectPool(Repository: RepoB, ObjectPool: A)`.
4. Observe that `RepoB`'s `objects/info/alternates` now points at `A`'s object directory, as shown by `Link`'s unconditional write path: [6](#0-5) 
5. Any object accessor RPC (e.g., `CommitService.GetCommit`, `BlobService.GetBlob`) against `RepoB` now can resolve OIDs that only exist in `A`, exfiltrating objects from an unrelated repository/pool.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
```

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil
}

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}
```

func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
}
