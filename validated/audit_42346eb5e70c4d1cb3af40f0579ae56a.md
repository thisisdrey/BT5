### Title
Unbounded Array Allocation from Attacker-Controlled ABI Length Fields in TVM Precompiled Contracts Causes Node OOM/Crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytesArray`, `extractSigArray`, and `extractBytes32Array` read an array-length word directly from attacker-supplied precompile call data and use it to size a Java array (`new byte[len][]`) with no upper bound check against the actual size of the supplied `data` buffer. [1](#0-0)  Any account able to broadcast a `TriggerSmartContract` transaction (or make a constant call) that invokes a precompiled contract using these helpers can supply a huge length word to force allocation of an oversized array, mirroring the "crafted input triggers OOM/uncontrolled resource consumption" bug class described in the Apache Tika advisory (CVE-2020-9489), where attacker-controlled length/size fields in parsers were not bounded before allocation.

### Finding Description
The three helper methods decode a 32-byte word from the DataWord array into `len` via `intValueSafe()` and immediately allocate a two-dimensional array of that size:
```java
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
  ...
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  ...
}
``` [2](#0-1)  The same unguarded pattern appears in `extractBytes32Array` and `extractSigArray`. [1](#0-0) 

`len` originates from `words[offset].intValueSafe()`, a caller-controlled 256-bit ABI word converted to a Java `int`. Unlike the shielded-transfer precompile logic elsewhere in the same file — which explicitly bounds `spendCount`/`receiveCount` to small values (`spendCount > 2` rejected) before allocating per-item arrays [3](#0-2)  — these three array-extraction helpers perform no sanity check that `len` is consistent with the actual length of `data` before allocating. A crafted call whose ABI-encoded array-length field is set to a very large value (e.g. close to `Integer.MAX_VALUE`) causes an immediate attempt to allocate an array of that many references, which throws `OutOfMemoryError` or consumes excessive heap, inside the TVM execution path for the calling thread.

### Impact Explanation
These helpers back precompiled contracts reachable from ordinary contract calls (e.g. multi-signature validation/batch signature verification precompiles that decode dynamic byte arrays and signature arrays from call data). Triggering an uncontrolled allocation inside the node's TVM execution thread can exhaust JVM heap or throw `OutOfMemoryError`, degrading or crashing the block-producing/validating node — a denial-of-service impact consistent with the CWE-401/CWE-835 classification of the reported analog and within the "node crash or halt" acceptance criterion.

### Likelihood Explanation
Likelihood is limited by the fact that a valid caller must reach one of the specific precompiled contracts that use `extractBytesArray`/`extractSigArray`, and JVM array allocation for `new byte[len][]` (an array of references, 4 or 8 bytes each) needs `len` in the billions to force actual `OutOfMemoryError`; smaller but still oversized values may only add allocation overhead. The exact call path (which precompile IDs invoke these helpers) could not be fully confirmed from the available index — grep found no direct call-site references to these methods outside their declaration, so it is uncertain whether they are currently wired into an active, reachable precompiled contract or are dead code in this version of the file. This uncertainty should be resolved before treating this as a confirmed exploitable path.

### Recommendation
Add explicit bounds validation in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` before allocation — e.g., verify `len >= 0` and that `len` is consistent with the remaining length of `data`/`words` (similar to the `spendCount`/`receiveCount` bound checks already used elsewhere in the file), rejecting the call instead of allocating when the declared length exceeds what the actual payload can support.

### Proof of Concept
Conceptually: craft a `TriggerSmartContract` call whose data targets a precompiled contract that invokes `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, with the ABI length word at `words[offset]` set to a large value (e.g. `0x7FFFFFFF`) while the actual call-data buffer is short. The `intValueSafe()` conversion yields a large `len`, and `new byte[len][]` at [4](#0-3)  is attempted before any per-item bounds are checked, leading to excessive allocation/`OutOfMemoryError` in the TVM execution thread.

Note: I was unable to confirm within the indexed code exactly which precompiled-contract `execute()` method currently calls these three helpers, so the concrete reachable entry point (contract address/selector) could not be verified with certainty from the index alone.
