### Title
Missing zero-address validation on `new_authority` in `transfer_to_new_account` / `transfer_to_new_account_pda` can permanently lock a marginfi account and its assets - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
`TransferToNewAccount` and `TransferToNewAccountPda` allow any account authority to migrate their `MarginfiAccount` (with all its lending balances) to a brand-new account under a caller-supplied `new_authority`. That `new_authority` field is declared as an `UncheckedAccount` with the comment "WARN: New authority is completely unchecked" and is never validated against `Pubkey::default()` (the zero address) before being written into the new account's `authority` field.

### Finding Description
`new_authority` is accepted with zero constraints: [1](#0-0) 

It is passed straight into `initialize_migrated_account`, which sets it as the new account's `authority` with no validation: [2](#0-1) 

Both `transfer_to_new_account` and `transfer_to_new_account_pda` then move the entirety of the old account's `lending_account` (all deposits/borrows) into the new account and permanently disable the old account (`ACCOUNT_DISABLED`, `migrated_to` set, balances zeroed), with no way to reverse the migration: [3](#0-2) [4](#0-3) 

If `new_authority` is (or resolves to, e.g. via a bugged client/integrator/CPI) `Pubkey::default()`, the new account is created with `authority = Pubkey::default()`. Because no signer can ever produce a valid signature for the system-owned zero pubkey, every `onlyGovernor`-style / `has_one authority`/`is_signer_authorized` gated instruction on that new account (withdraw, borrow, repay, close, order placement, further transfer, etc.) becomes permanently uncallable — this is the exact bug class from the report (missing zero-address check on an authority/ownership-transfer function leading to irreversible loss of access).

Notably, the off-chain `p0-cli` tooling explicitly guards against this exact case before building the same instruction, confirming the project itself recognizes zero-address as an invalid/dangerous input for this parameter, yet the on-chain program enforces no such check: [5](#0-4) 

The on-chain `Accounts` struct for both variants confirms `new_authority` is unchecked in both the keypair-based and PDA-based transfer instructions: [6](#0-5) [7](#0-6) 

The existing test suite exercises many happy/failure paths for this instruction (bad fee wallet, double migration, PDA collisions, third-party IDs) but does not test/guard the zero-address `new_authority` case: [8](#0-7) 

I was also unable to find any recovery/receivership/governance mechanism in the codebase that can restore access to a `MarginfiAccount` whose `authority` field is the zero pubkey — `AdminCloseAccount` only permits closing accounts that are already empty and inactive for 60+ days, which does not help if the account is funded: [9](#0-8) 

### Impact Explanation
If a `new_authority` argument ever evaluates to the zero pubkey — whether via a malicious/compromised front-end, a misconfigured integrator/CPI caller (this instruction is explicitly designed to be called by third-party programs on behalf of users, per its `third_party_id` support and PDA variant), or a client-side bug — the migrated account's entire deposit/borrow position becomes permanently frozen: no one can ever sign as `Pubkey::default()` to withdraw, repay, or otherwise interact with the account. This is a direct permanent lock/freeze of user funds in the core margin-account accounting path, satisfying the "permanent lock/freeze" impact category.

### Likelihood Explanation
The instructions are permissionless/unprivileged and reachable by any account holder, and are explicitly designed to be invoked with a caller-supplied `new_authority`, including through third-party CPI integrations (`third_party_id`) where the integrator, not the account owner, may supply the destination authority. A bug or misconfiguration in any such integration (or a malicious CPI caller in the case of `TransferToNewAccountPda`, since `authority` there is merely `is_signer_authorized`) can trigger the zero-address case without any special privilege. The complete absence of a zero-address check — contrasted with the CLI, which does check it — indicates this is an oversight rather than an intentional design decision.

### Recommendation
Add an explicit check in both `transfer_to_new_account` and `transfer_to_new_account_pda` that rejects `new_authority == Pubkey::default()`, e.g.:

```rust
check!(
    ctx.accounts.new_authority.key() != Pubkey::default(),
    MarginfiError::IllegalAction,
    "New authority cannot be the zero address"
);
```

Add this check before `initialize_migrated_account` is invoked in both `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs::transfer_to_new_account` and `::transfer_to_new_account_pda`.

### Proof of Concept
1. Account owner (or a third-party integrator via CPI with a valid `third_party_id`) calls `transferToNewAccount` (or `transferToNewAccountPda`) supplying `new_authority = Pubkey::default()` (the all-zero system pubkey).
2. The instruction succeeds: `initialize_migrated_account` sets `new_account.authority = Pubkey::default()`, copies over all of `old_account.lending_account` (deposits/borrows), and `finalize_migrated_old_account` disables the old account and zeroes its balances.
3. The new account now holds all the funds/positions but has `authority = Pubkey::default()`.
4. Any subsequent instruction requiring `is_signer_authorized`/`has_one = authority` against this account (withdraw, borrow, repay, order, further transfer) fails because no valid Solana keypair can sign as the zero pubkey — the funds are permanently locked with no admin recovery path (per `admin_close.rs`, which only applies to already-empty accounts).

/// Permissionless instruction to close legacy or new accounts that are empty and inactive for >60
/// days. Eligibility is computed from direct account invariants (balances/flags/timestamps), not
/// indexer flags, so pre-flag accounts remain safely closeable.
pub fn admin_close_account(ctx: Context<AdminCloseAccount>) -> MarginfiResult {
    let marginfi_account = ctx.accounts.marginfi_account.load()?;
    let clock = Clock::get()?;
    let elapsed = clock
        .unix_timestamp
        .saturating_sub(marginfi_account.last_update as i64);
    let is_inactive = elapsed > 60 * SECONDS_PER_DAY;

    check!(
        marginfi_account.can_be_closed() && is_inactive,
        MarginfiError::IllegalAction,
        "Account is not eligible for close (not empty or active within 60d)"
    );

    check!(
        !marginfi_account.get_flag(ACCOUNT_IN_DELEVERAGE)
            && !marginfi_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION)
            && marginfi_account.active_orders == 0
            && marginfi_account.liquidation_record == Pubkey::default(),
        MarginfiError::IllegalAction,
        "Account cannot be closed"
    );

    emit!(AdminCloseAccountEvent {
        header: AccountEventHeader {
            signer: None,
            marginfi_account: ctx.accounts.marginfi_account.key(),
            marginfi_account_authority: marginfi_account.authority,
            marginfi_group: ctx.accounts.group.key(),
        },
        global_fee_wallet: ctx.accounts.global_fee_wallet.key(),
    });

    Ok(())
}
