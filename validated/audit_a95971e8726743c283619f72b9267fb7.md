## Title
Unscaled integer-division rounding in the QoS priority formula collapses distinct-fee transactions to zero priority - (File: `core/src/transaction_priority.rs`, `core/src/forwarding_stage.rs`)

### Summary
This is the closest legitimate analog to the `IdleYieldSource` report: an arithmetic calculation that omits sufficient mantissa/scaling before dividing, so legitimately different, non-zero inputs are truncated to the same output (in the report, shares; here, transaction scheduling priority). The affected code is the banking-stage/forwarding-stage QoS priority formula `P = R / (1 + C)`.

### Finding Description
`calculate_priority_and_cost` computes a per-transaction priority used to rank transactions for scheduling and for the sig-verify "priority floor" drop decision: [1](#0-0) 

and the equivalent duplicate in the forwarding stage: [2](#0-1) 

Both apply a fixed `MULTIPLIER: u64 = 1_000_000` before dividing the fee-derived `reward` by `cost + 1`, explicitly to "avoid rounding down too aggressively." This is the same class of mitigation the PoolTogether patch added (mantissa-style scaling before division) — but the scale factor here is a constant, not derived from the actual dynamic range of `cost`. Transaction cost (`CostModel::calculate_cost*`) can range from a few hundred compute units up to `MAX_COMPUTE_UNIT_LIMIT` (1,400,000) plus loaded-accounts-data-size cost (up to tens of thousands) and instruction-data cost, so `cost` can exceed `1_000_000`. When `cost + 1` is close to or larger than `reward * MULTIPLIER`, `saturating_div`/`wrapping_div` silently floors many distinct reward values to the same priority (frequently `0`), just like the vulnerable `totalUnderlyingAssets`/`totalShares` division in the original report zeroed out shares once the denominator grew large relative to the scaled numerator: [3](#0-2) 

The resulting `priority` value is inserted directly into the scheduler's ordering key: [4](#0-3) [5](#0-4) 

and drives the sig-verify priority-floor drop decision via `calculate_priority_from_bytes`: [6](#0-5) [7](#0-6) 

Once two transactions with genuinely different priority fees both round to `priority = 0`, the `BTreeSet<TransactionPriorityId>` in `TransactionStateContainer` (ties broken only by insertion-order `TransactionId`, not by fee) treats them as equal-priority, and the sig-verify priority-floor gate treats them identically as well.

### Impact Explanation
This is a QoS-evasion class bug (matching the "grossly underpriced pre-fee work"/"QoS evasion" category): a large class of higher-cost transactions (e.g., transactions requesting large compute-unit limits or large loaded-accounts-data-size, which is entirely attacker-controlled input) can be crafted so that even a meaningfully larger priority fee still collapses to the same (often zero) priority bucket as a minimal-fee transaction. This defeats the "sell blockspace to the highest bidder" design goal that the code's own comments describe, allowing spam/low-fee transactions to compete on equal footing with fee-paying ones for banking-stage scheduling slots and to survive the sig-verify priority-floor drop that is specifically meant to shed low-value traffic under load. This is a fairness/economic-security degradation of the fee market, not a memory-safety or consensus-invalidity bug.

### Likelihood Explanation
Likelihood is moderate. `cost` is fully attacker-controlled up to `MAX_COMPUTE_UNIT_LIMIT` and `MAX_LOADED_ACCOUNTS_DATA_SIZE_BYTES`, both settable via `ComputeBudgetInstruction`, and `reward` for many realistic low/medium fee transactions is small relative to `cost` once `cost` climbs into the hundred-thousand-plus range, which is easily reachable by any unprivileged sender crafting ordinary transactions with high compute or account-loading budgets and modest fees. No special role or validator privilege is required.

### Recommendation
Scale the `MULTIPLIER` (or switch to `u128` intermediate arithmetic with a larger, adaptively-sized scale factor) so that the numerator's precision comfortably exceeds the maximum possible `cost` (i.e., use a multiplier proportional to `MAX_COMPUTE_UNIT_LIMIT` + max loaded-accounts-data-size cost, analogous to using a proper "mantissa" sized to the denominator's range), consistent with the fix pattern already used correctly in `get_prioritization_fee` (round-up microlamport-to-lamport conversion in `compute-budget/src/compute_budget_limits.rs`). Add explicit tests asserting priority strictly increases with reward for transactions at/near `MAX_COMPUTE_UNIT_LIMIT` cost, to lock in the invariant that fee differentiation survives at the top of the cost range.

### Proof of Concept
1. Construct transaction A: `compute_unit_limit = MAX_COMPUTE_UNIT_LIMIT` (1,400,000), `compute_unit_price` set so `priority_fee_lamports = 1` lamport, base signature fee minimal.
2. Construct transaction B: same `compute_unit_limit`, but `priority_fee_lamports` set several lamports higher (still well below what would be needed to move `reward * 1_000_000` past `cost + 1`).
3. Feed both through `calculate_priority_and_cost` (`core/src/transaction_priority.rs:32`): for both, `cost.sum()` ≈ 1,400,000+ and `reward.saturating_mul(1_000_000).saturating_div(cost + 1)` evaluates to `0` for both, despite B legitimately paying more.
4. Both transactions receive identical `TransactionPriorityId { priority: 0, .. }` and are ordered solely by insertion order in the `BTreeSet`, and both are treated identically by the sig-verify priority-floor drop logic in `sigverify.rs`, demonstrating the fee-market/QoS ordering guarantee is defeated. Exact numeric reproduction can be confirmed with the existing test harness in `core/src/transaction_priority.rs:154-193` by extending `higher_compute_unit_price_yields_higher_priority` to use near-`MAX_COMPUTE_UNIT_LIMIT` cost transactions instead of the default low-cost transfer used there.

pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
    let fee_details = solana_fee::calculate_fee_details(
        transaction,
        bank.fee_structure().lamports_per_signature,
        transaction_configuration.priority_fee_lamports,
        bank.fee_features(),
    );
    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    (
        reward
            .saturating_mul(MULTIPLIER)
            .saturating_div(cost.saturating_add(1)),
        cost,
    )
}

/// Returns `None` if the bytes don't parse as a valid transaction, in which

pub(crate) fn calculate_priority_from_bytes(bank: &Bank, data: &[u8]) -> Option<u64> {
    let view = SanitizedTransactionView::try_new_sanitized(data, &sanitize_config()).ok()?;
    let runtime_tx = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    )
    .ok()?;
    let transaction_configuration = runtime_tx
        .transaction_configuration(&bank.feature_set)
        .ok()?;
    let (priority, _cost) =
        calculate_priority_and_cost(bank, &runtime_tx, &transaction_configuration);

    Some(priority)
}

fn calculate_priority(
    transaction: &RuntimeTransaction<SanitizedTransactionView<&[u8]>>,
    bank: &Bank,
) -> Option<u64> {
    let transaction_configuration = transaction
        .transaction_configuration(&bank.feature_set)
        .ok()?;

    // Manually estimate fee here since currently interface doesn't allow a on SVM type.
    // Doesn't need to be 100% accurate so long as close and consistent.
    let prioritization_fee = transaction_configuration.priority_fee_lamports;
    let signature_details = transaction.signature_details();
    let signature_fee = signature_details
        .total_signatures()
        .saturating_mul(bank.fee_structure().lamports_per_signature);
    let fee_details = FeeDetails::new(signature_fee, prioritization_fee);

    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    let cost = CostModel::estimate_cost(
        transaction,
        transaction.program_instructions_iter(),
        transaction.num_requested_write_locks(),
        &bank.feature_set,
    );

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    Some(
        MULTIPLIER
            .saturating_mul(reward)
            .wrapping_div(cost.sum().saturating_add(1)),
    )
}
