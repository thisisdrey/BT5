### Title
Unsanitized `GetArchiveRequest.Prefix` allows path traversal / absolute paths in generated tar/zip archive entries (Zip Slip / Tar Slip) - (File: internal/gitaly/service/repository/archive.go)

### Summary
`GetArchive` passes the attacker-controlled `GetArchiveRequest.Prefix` field straight into `git archive --prefix=<prefix>/` without any validation of its contents. `git-archive` writes this value verbatim as the path prefix of every entry in the produced tar/zip, so a prefix containing `../` sequences or an absolute path is embedded unmodified into the archive, creating a classic "Zip Slip"/"Tar Slip" payload that can escape the intended extraction directory whenever the resulting archive is later extracted.

### Finding Description
In `GetArchive` (`internal/gitaly/service/repository/archive.go:34-100`), several request fields are validated (`GetPath()` via `storage.ValidateRelativePath`, `GetExclude()` similarly, `GetCommitId()` via `git.ValidateRevision`), but `in.GetPrefix()` is never checked. It flows unmodified into `handleArchive`: [1](#0-0) 
Here `gitcmd.ValueFlag{Name: "--prefix", Value: p.in.GetPrefix() + "/"}` is constructed. `ValueFlag.OptionArgs()` in `internal/git/gitcmd/command_options.go` only validates the flag *name* against `flagRegex`; the flag *value* is never checked or sanitized: [2](#0-1) 
Since `Name`/`Value` are passed to `exec` as separate argv elements (not through a shell), there is no shell/command injection, but `git archive --prefix` treats its value as a literal path string that is prepended to every file path recorded in the tar/zip headers. Git itself performs no sanitization of `--prefix` for `..`/absolute paths — that is by design, since `git archive` is a data-streaming tool, not an extraction tool. Because Gitaly never rejects `..`, leading `/`, or other traversal sequences in `Prefix`, an attacker who controls the `Prefix` field of the RPC (directly via gRPC, or indirectly if GitLab Rails ever forwards user-influenced data such as a ref/branch name into this field) can force the produced archive to contain entries such as `../../../../etc/cron.d/evil` or absolute paths, which is the classic Zip Slip precondition for extraction-time path traversal on whichever host later unpacks the archive.

### Impact Explanation
This is a genuine "archive extraction escape" primitive from the bounty impact list: any consumer that extracts the archive Gitaly produced (a user's machine, a CI job that fetches `git archive`-style exports, or any tool that naively extracts with `tar xf`/`unzip`) can have files written outside the intended target directory, up to arbitrary file write/overwrite on that extracting host depending on the tool's own protections. The vulnerability does not affect Gitaly's own filesystem (Gitaly only streams the archive), so the impact is scoped to whichever process later extracts the archive without its own zip-slip protection.

### Likelihood Explanation
The attacker only needs the ability to issue (or influence) a `GetArchiveRequest` with a crafted `Prefix` value against a repository they can already read — well within the "unprivileged user who can push/fetch or own a repo" threat model in scope. No special role, secret, or non-default config is required; the flaw is 100% reachable through the public `GetArchive` RPC path with a valid, otherwise-legitimate request. The only external dependency for full impact is that whatever consumes the resulting archive lacks its own Zip Slip mitigation, which is common for generic tar/zip extraction code and was historically the root cause of many real-world Zip Slip CVEs.

### Recommendation
Validate `in.GetPrefix()` the same way other path-like fields are validated in this RPC: reject values containing `..` path components, NUL bytes, or leading `/` (absolute paths), e.g. via `storage.ValidateRelativePath`-style checks (rejecting `..` segments and absolute paths) before constructing the `--prefix` flag, or restrict the prefix to a safe character set (alphanumerics, dashes, underscores, slashes without `..`).

### Proof of Concept
```go
func TestGetArchive_PrefixTraversal(t *testing.T) {
    // set up any repository via testhelper/gittest as done elsewhere in archive_test.go
    req := &gitalypb.GetArchiveRequest{
        Repository: repo,
        CommitId:   commitID,
        Prefix:     "../../../../tmp/evil",
        Format:     gitalypb.GetArchiveRequest_TAR,
    }

    stream, err := client.GetArchive(ctx, req)
    require.NoError(t, err)

    data := readFullArchive(t, stream) // helper that concatenates response.GetData()

    tr := tar.NewReader(bytes.NewReader(data))
    hdr, err := tr.Next()
    require.NoError(t, err)

    // Demonstrates the traversal sequence is embedded verbatim in the tar header name,
    // which most naive `tar -x` implementations will honor.
    require.True(t, strings.HasPrefix(hdr.Name, "../../../../tmp/evil/"),
        "expected traversal prefix to survive into archive entry name, got %q", hdr.Name)
}
```
Expected result: the assertion passes today because `Prefix` is not sanitized, confirming the tar entry names carry the attacker-supplied `../` sequences unmodified into the archive stream.
