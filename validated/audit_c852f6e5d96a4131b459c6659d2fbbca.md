### Title
Exchange transaction math bypasses the hardened/safe overflow protection unless the `AllowHardenExchangeCalculation` proposal is active - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
The DNS bypass CVE describes an enforcement gap: a security policy (the egress allowlist) is implemented on one path (HTTP/S) while another functionally equivalent path (DNS resolution) reaches the same untrusted-facing resource without going through the policy check. `ExchangeTransactionActuator` in java-tron has the same structural gap: a "hardened"/safe calculation path (`SafeExchangeProcessor`, gated by `allowHarden()`/`getAllowHardenExchangeCalculation`) exists specifically to protect the bancor-style exchange math from manipulation/precision abuse, but the default, non-hardened path calls `exchangeCapsule.transaction()` directly, which does not go through the same protections.

### Finding Description
`ExchangeTransactionActuator.execute()` computes the swapped amount via: [1](#0-0) 
which calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` — meaning the "harden" behavior is an opt-in flag rather than an always-enforced invariant. A dedicated `SafeExchangeProcessor` class exists specifically to compute this exchange safely, and it is only exercised in `hardenedSuccessExchangeTransaction`-style tests when `saveAllowHardenExchangeCalculation(1)` is explicitly set: [2](#0-1)  Any node/network where this dynamic property is not turned on (the default/legacy state, controlled only by committee proposal) executes exchange swaps through the un-hardened arithmetic path, exactly mirroring the DNS report's pattern of "the protection exists but is not applied on the path actually reachable by the untrusted caller."

### Impact Explanation
If the un-hardened `ExchangeCapsule.transaction()` path retains the historical precision/manipulation weaknesses that `SafeExchangeProcessor` was introduced to fix (bancor-relay style rounding/manipulation of `firstTokenBalance`/`secondTokenBalance`), any account can call `ExchangeTransactionContract` to drain or dilute the token pool established by `ExchangeCreateActuator`/`ExchangeInjectActuator`, which is a direct unauthorized asset-theft / unbacked-balance risk reachable from a single signed transaction.

### Likelihood Explanation
Likelihood is **uncertain and not fully confirmed** given available evidence: I was not able to read the actual arithmetic inside `ExchangeCapsule.transaction()` or `SafeExchangeProcessor` in this session (I only confirmed the call-site gating and the existence of a "hardened" test), and I could not verify the current on-chain/default value of `AllowHardenExchangeCalculation` (whether it is already permanently enabled on mainnet, which would neutralize the issue). Because of this gap, I cannot assert with confidence that the un-hardened path is currently exploitable; I can only confirm the code-level pattern of a security enforcement applied conditionally rather than unconditionally, which is the exact bug class in the reference CVE.
