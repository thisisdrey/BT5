### Title
Unvalidated `CreateCommonTransaction` gRPC request causes uncaught `IndexOutOfBoundsException` from empty contract list - (File: `framework/src/main/java/org/tron/core/services/RpcApiService.java`)

### Summary
The `Wallet.CreateCommonTransaction` gRPC endpoint reads the first element of the client-supplied `contract` list of a `Transaction` message without checking whether the list is non-empty, unlike every other transaction-building path in the same class.

### Finding Description
`RpcApiService.WalletApi#createCommonTransaction` accepts an arbitrary, unsigned `Transaction` protobuf from any gRPC client and immediately indexes into its raw data: [1](#0-0) 

```java
@Override
public void createCommonTransaction(Transaction request,
    StreamObserver<TransactionExtention> responseObserver) {
  Transaction.Contract contract = request.getRawData().getContract(0);
  createTransactionExtention(contract.getParameter(), contract.getType(),
      responseObserver);
}
```
`request.getRawData().getContract(0)` throws `IndexOutOfBoundsException` when `raw_data.contract` is empty. Every sibling call in the same file that builds a `TransactionExtention` from a client-supplied message routes through `createTransactionExtention`, which wraps `createTransactionCapsule` in a broad `try { ... } catch (ContractValidateException e) { ... } catch (Exception e) { ... }` block, as seen in [2](#0-1)  — but `createCommonTransaction` does not enter that guarded path at all, since the throw happens before `createTransactionExtention` is even invoked. Compare with `Wallet.getShieldTransactionHash`, which explicitly checks for an empty contract list before indexing: [3](#0-2) . `createCommonTransaction` lacks that equivalent guard, breaking the "no unhandled exception can escape the gRPC handler" invariant that every other endpoint in this file follows (compare the pervasive `catch (Exception e) { responseObserver.onError(...) }` idiom used throughout `RpcApiService`, e.g. [4](#0-3) ).

This is the same bug class as the Hyperledger Fabric Gateway advisory (CVE-2022-36023): a client-controlled, malformed request (here, a `Transaction` with zero contracts) skips input validation and reaches code that dereferences/indexes into request data that the framework assumed would be present, throwing an unhandled runtime exception on the peer/node handling the request.

### Impact Explanation
An unauthenticated gRPC client can send a single `CreateCommonTransaction` request with `raw_data.contract` empty (trivially constructed, no signature or fee required) to trigger an uncaught `IndexOutOfBoundsException` inside the `Wallet` gRPC service thread. Because none of the exception handling present in sibling endpoints of the same class applies here, this call path is uniquely exposed compared to the rest of `RpcApiService`. In grpc-java the server transport layer will typically convert an escaping unchecked exception into an `UNKNOWN`/`INTERNAL` status for that individual call rather than crashing the whole JVM, so worst case observed is a degraded/denied response for this specific RPC method (an API endpoint failure) rather than certain full-node crash. This still satisfies the "API the node can no longer serve" bar for this specific RPC method, and represents a genuine input-validation gap analogous to the reported Fabric issue, even though I could not confirm (given available files/tools) whether it escalates to full-node crash on this particular gRPC framework version.

### Likelihood Explanation
Trivial to trigger: it requires only an anonymous gRPC connection to the public `Wallet` service and a `Transaction` protobuf with an empty `contract` repeated field — no valid signature, account, or fee is needed since the exception happens before any validation or signature check.

### Recommendation
Add an explicit check in `createCommonTransaction` (mirroring `Wallet.getShieldTransactionHash`) that rejects requests with an empty `contract` list via a `ContractValidateException`/gRPC error response before indexing, and wrap the method body in the same `try/catch (Exception e) { responseObserver.onError(...) }` pattern used elsewhere in `RpcApiService`.

### Proof of Concept
1. Connect to the node's public gRPC `Wallet` service (e.g., port 50051).
2. Call `CreateCommonTransaction` with a `Transaction` message whose `raw_data.contract` field is left empty (default/unset).
3. Observe the server throws `IndexOutOfBoundsException` inside `createCommonTransaction` before any of the class's normal exception-handling logic can catch it, unlike every other transaction-creation RPC in the same service.

    private void createTransactionExtention(Message request, ContractType contractType,
        StreamObserver<TransactionExtention> responseObserver) {
      TransactionExtention.Builder trxExtBuilder = TransactionExtention.newBuilder();
      Return.Builder retBuilder = Return.newBuilder();
      try {
        TransactionCapsule trx = createTransactionCapsule(request, contractType);
        trxExtBuilder.setTransaction(trx.getInstance());
        trxExtBuilder.setTxid(trx.getTransactionId().getByteString());
        retBuilder.setResult(true).setCode(response_code.SUCCESS);
      } catch (ContractValidateException e) {
        retBuilder.setResult(false).setCode(response_code.CONTRACT_VALIDATE_ERROR)
            .setMessage(ByteString
                .copyFromUtf8(Wallet.CONTRACT_VALIDATE_ERROR + e.getMessage()));
        logger.debug(CONTRACT_VALIDATE_EXCEPTION, e.getMessage());
      } catch (Exception e) {
        retBuilder.setResult(false).setCode(response_code.OTHER_ERROR)
            .setMessage(ByteString.copyFromUtf8(e.getClass() + " : " + e.getMessage()));
        logger.info(EXCEPTION_CAUGHT + e.getMessage());
      }
      trxExtBuilder.setResult(retBuilder);
      responseObserver.onNext(trxExtBuilder.build());
      responseObserver.onCompleted();
    }
