## Analog Found

### Title
Unconditional `accrue()` call inside ztoken `transfer()` can panic on arithmetic underflow after `socialize-debt`, permanently blocking all vault operations - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent vault contracts)

### Summary
The GClaimManager report describes a class of bug where an unprivileged, composability-facing entry point (`join()`/`exit()`) unconditionally triggers an internal settlement/accrual routine (`_collect()`) that can revert under certain state conditions, breaking composability. The Zest v2 vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) exhibit the same structural pattern: the SIP-010 `transfer()` function — the most composability-critical entry point since ztokens are used as collateral throughout `market.clar` — unconditionally calls `(try! (accrue))` before moving tokens.

### Finding Description
Every vault's `transfer` function begins with a mandatory accrual call: [1](#0-0) 

`accrue()` computes the treasury's share of newly accrued interest and mints it as ztoken shares, using a division whose denominator is derived from a subtraction that is not bounds-checked: [2](#0-1) 

Specifically:
```
(treasury-lp (if (> reserve-inc u0)
  (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc))
  u0))
```
If `reserve-inc` (the treasury fee slice of newly accrued interest) is ever `>=` `(total-assets-preview)`, the subtraction underflows a `uint`, which aborts the transaction in Clarity. The same `accrue()` call is a precondition for `deposit`, `redeem`, `system-borrow`, `system-repay`, and `flashloan` in the same file, meaning a panic here does not just block `transfer()` — it blocks every vault entry point.

`total-assets-preview`/`assets` can be driven down sharply relative to outstanding scaled debt by `socialize-debt`, which is explicitly designed to write down `assets` and `lindex` when bad debt is realized: [3](#0-2) 

After a severe socialize-debt event, `assets` (and thus `total-assets-preview`) can become very small while `principal-scaled` (and the interest it continues to accrue every block via `next-index`) remains outstanding. On the next `accrue()` invocation, `debt-delta`/`reserve-inc` can exceed the shrunken `total-assets-preview`, triggering the underflow panic.

Critically, the escape hatch that normally exists for pausing broken accrual logic itself calls `accrue()` first, so it cannot recover from this state once triggered: [4](#0-3) 

Because `set-pause-states` calls `(try! (accrue))` when transitioning from not-paused to paused (`"When pausing accrue, accrue first to capture pending interest"`), and that call would hit the same underflow, even DAO governance cannot pause accrual to unblock the vault once the underflow condition exists.

### Impact Explanation
This lands squarely on **Critical — permanent freezing of funds**. Once the underflow condition is reached, `transfer()`, `deposit()`, `redeem()`, `system-borrow()` (used by `market.clar` for `borrow`), `system-repay()` (used for `repay`), and `flashloan()` all revert unconditionally because they all gate on `(try! (accrue))`. Since ztokens are the collateral asset type used throughout `market.clar` (`collateral-add`, `collateral-remove`, `supply-collateral-add`, liquidation flows), this also freezes the ability to move or liquidate collateral positions backed by that vault's ztoken. The self-healing pause path is unavailable because it re-triggers the same panic, leaving no in-protocol remediation path — this differs from (and is more severe than) the original GClaimManager report, where the affected functions were expected to be deprecated and the revert was at least bypassable by waiting for someone to settle the series.

### Likelihood Explanation
This requires a `socialize-debt` event large enough to shrink `assets`/`total-assets-preview` to a value smaller than the treasury-fee slice of subsequently accrued interest. `socialize-debt` is a real, designed code path for handling protocol insolvency (bad debt write-down), not a hypothetical or DAO-misconfiguration scenario, so this is reachable through normal (if extreme) operation of the protocol rather than requiring privileged compromise.

### Recommendation
Bound the subtraction in `accrue()` so `reserve-inc` is capped at `(total-assets-preview)` (or skip minting treasury shares when `reserve-inc >= total-assets-preview`), and ensure `set-pause-states` can pause `accrue` without first re-executing the potentially-panicking accrual logic (e.g., use a try/catch-and-continue pattern, or gate accrual pausing to not require a prior successful `accrue()` call).

### Proof of Concept
1. Vault accumulates outstanding debt (`principal-scaled`) with a nonzero `fee-reserve`.
2. A `socialize-debt` call (triggered by protocol-level bad-debt handling after a liquidation shortfall) reduces `assets` significantly, per [5](#0-4) .
3. On the next call to any vault entry point (e.g., a user calling `transfer()` on their ztoken, or `market.clar` calling `collateral-remove`/`borrow`), `accrue()` runs and computes `debt-delta`/`reserve-inc` from continued interest accrual on `principal-scaled`.
4. If `reserve-inc >= (total-assets-preview)`, the expression `(- (total-assets-preview) reserve-inc)` underflows, aborting the transaction — as shown in [6](#0-5) .
5. All subsequent calls to `transfer`, `deposit`, `redeem`, `system-borrow`, `system-repay`, `flashloan`, and even the DAO's `set-pause-states(accrue=true)` remediation path hit the same panic, permanently freezing all funds in the vault.

Note: I was unable to inspect the exact implementations of `total-assets-preview`, `next-index`, and `next-liquidity-index` before running out of tool budget, so the precise numeric thresholds for triggering the underflow are not independently confirmed — the finding is based on the arithmetic pattern visible directly in `accrue()`'s source, which is unambiguous about the unguarded subtraction.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
