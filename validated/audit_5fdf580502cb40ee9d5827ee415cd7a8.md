### Title
Out-of-Bounds Access in Multi-Sig Permission Check via Unbounded Contract Type Index - (File: `chainbase/src/main/java/org/tron/common/utils/WalletUtil.java`)

### Summary
`WalletUtil.checkPermissionOperations()` and its duplicate in `TransactionUtil.checkPermissionOperations()` compute a byte index into a fixed 32-byte permission bitmap (`operations`) using `contract.getTypeValue()` without validating that the value is within the expected `[0, 255]` range, mirroring the PostGIS bug class where an oversized "Type" value is used unchecked as an index into a fixed-size internal table.

### Finding Description
`checkPermissionOperations` is used to verify whether a signer's `Permission.operations` bitmap authorizes a given `Contract.Type`: [1](#0-0) 

The same logic is duplicated in: [2](#0-1) 

`contract.getTypeValue()` returns the raw protobuf `int32` value backing the `ContractType` enum field of the transaction's `Contract`. For an open/unrecognized enum value, `getTypeValue()` returns whatever integer was serialized on the wire — it is not restricted to the defined enum range. The code then computes `contractType / 8` as a direct index into the `operations` `ByteString` (`operations.byteAt(contractType / 8)`), with only a fixed-size check (`operations.size() != 32`) performed beforehand — there is no check that `contractType` itself is bounded (e.g., `< 256`). If `contractType` is a large or negative raw value crafted in a malicious/raw-encoded transaction, `byteAt()` will be called with an index outside `[0,31]`, throwing an unchecked `IndexOutOfBoundsException` that is not declared/caught by the method's `throws PermissionException` signature.

This directly parallels the PostGIS bug: a caller-influenced "type" value that is normally expected to stay within a small fixed set is instead used unchecked as an array index into a fixed-size table.

Separately, `AccountPermissionUpdateActuator` does validate contract-type bit ranges when a user is *defining* a new permission's `operations` bitmap ("`N isn't a validate ContractType`" error, as exercised in `AccountPermissionUpdateActuatorTest`), but this only guards the permission-definition path — it does not bound the `contractType` value read directly from an incoming transaction's own `Contract` field when `checkPermissionOperations` is invoked to authorize that specific transaction against an account's existing multi-sig permission.

### Impact Explanation
If reached during signature/permission verification of an arbitrary broadcast transaction (multi-sig account path), an attacker-controlled raw `Contract.type` field with an out-of-range value causes an unchecked `IndexOutOfBoundsException` during permission checking. Because Java is memory-safe, this cannot corrupt memory the way the PostGIS C code can, but an uncaught exception at this point in transaction validation/signature-check flow can crash or destabilize the node process handling that flow, which is a denial-of-service impact against an unprivileged transaction broadcaster's target node.

### Likelihood Explanation
Likelihood depends on whether the exception is caught by a broad `catch (Exception e)` somewhere in the calling chain (`TransactionCapsule`/`Wallet`) before reaching a place where it would crash processing, and whether raw/malformed `Contract.type` values (outside the enum's defined range) can actually reach `checkPermissionOperations` for a transaction that otherwise parses successfully. I was not able to fully trace and confirm the exact call sites in `TransactionCapsule.java` and `Wallet.java` (the tool budget was exhausted before reading those call sites), so this should be verified: confirm whether the exception propagates uncaught in the transaction-signature-verification path invoked during `Manager` block/transaction processing, and confirm that `getTypeValue()` can indeed carry an out-of-enum-range value through normal protobuf parsing.

### Recommendation
In `WalletUtil.checkPermissionOperations` and `TransactionUtil.checkPermissionOperations`, validate `contractType` is within `[0, operations.size() * 8)` before computing `contractType / 8` / `contractType % 8`, throwing `PermissionException` (not letting an unchecked `IndexOutOfBoundsException` propagate) when it is out of range.

### Proof of Concept
1. Construct a raw `Transaction` whose `raw_data.contract[0].type` field is set (via raw protobuf varint encoding) to a value far outside the defined `ContractType` enum range (e.g., `100000`), while keeping the transaction otherwise well-formed and signed by a key belonging to a multi-sig account with a custom `Permission`.
2. Broadcast the transaction to a node.
3. During permission/signature verification, `checkPermissionOperations` is invoked with `contractType = 100000`, computing `operations.byteAt(12500)` against a 32-byte `ByteString`, throwing `IndexOutOfBoundsException`.
4. If this exception is not caught by a sufficiently broad handler in the transaction validation call chain, node transaction/block processing for that request fails unexpectedly, which can be repeated to cause a denial of service. [1](#0-0) [2](#0-1)

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
