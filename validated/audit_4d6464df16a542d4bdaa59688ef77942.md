## Analysis

The Zentra report describes an accounting‑edge‑case where a debt‑reduction step (`repayWithATokens`) is allowed to complete while the matching burn on the other side of the ledger silently rounds to zero, letting the two halves of the transaction diverge and letting value leak out of the pool. The closest reachable analog in java‑tron is the **legacy (non‑hardened) constant-product Exchange math used by `ExchangeTransactionActuator`**, where one side of the pool (the seller's balance/asset debit) is committed using exact integer arithmetic while the matching output on the other side is derived through **lossy `double` floating-point math that is truncated to a `long`**, and this lossy path is still the **network default** today.

### Root cause

`ExchangeCapsule.transaction()` picks the calculation engine based on a "hardened" flag: [1](#0-0) 

When hardened mode is off (the default), it instantiates the legacy `ExchangeProcessor`, whose bancor-style relay math is computed entirely in IEEE-754 `double` and then truncated to `long`: [2](#0-1) 

Whether this lossy path is used is controlled by `allowHardenExchangeCalculation`, whose on-chain default is `0` (disabled): [3](#0-2) [4](#0-3) 

The regression test suite itself confirms the two engines produce **different results for identical inputs** — i.e., the legacy `double` path is provably imprecise relative to the `BigDecimal`-based `SafeExchangeProcessor`: [5](#0-4) 

### How this maps to the Zentra pattern

In `ExchangeTransactionActuator.execute()`, the seller's side of the ledger is debited/credited using exact math (`reduceAssetAmountV2`/`setBalance`), and the *counter-quantity* (`anotherTokenQuant`, analogous to the aToken burn amount in Zentra) is computed by the lossy `ExchangeProcessor.exchange()` call and then persisted into the pool balances unconditionally: [6](#0-5) 

Because `exchangeToSupply`/`exchangeFromSupply` truncate a `double` to `long` at each step (`(long) issuedSupply`, `(long) exchangeBalance`), the reserve invariant that a constant-product/bancor pool depends on is not guaranteed to hold exactly — the debit path (seller's balance reduction, pool `sellToken` balance increase) always completes deterministically, while the matching payout/burn computation can drift low or high due to floating-point rounding. Repeated exploitation of favorable rounding directions (choosable by an attacker via crafted `quant`/`expected` values across many transactions) can accumulate a systematic imbalance in the pool, i.e., value extraction without a corresponding, exactly-matching debit — the same class of bug as Zentra's "debt path completes while the matching burn is reduced to zero."

### Why this is exploitable today

- The hardened, safe engine (`SafeExchangeProcessor`, `BigDecimal`-based) exists but is **off by default** and only enabled via a committee proposal (`ALLOW_HARDEN_EXCHANGE_CALCULATION`), gated behind `ForkBlockVersionEnum.VERSION_4_8_2`.
- Any unprivileged account can broadcast an `ExchangeTransactionContract` transaction against any existing TRC10 exchange pool — this is the "order placer" surface explicitly in scope.
- `ExchangeTransactionActuator.doValidate()` only checks `anotherTokenQuant < tokenExpected`, not that the double-based computation is self-consistent with an exact invariant, so a slippage-tolerant attacker can push transactions that consistently round in their favor. [7](#0-6)

If you'd like, I can lay out a concrete numeric PoC sequence (using the existing `ExchangeProcessorTest` fixtures) demonstrating a measurable pool-balance drift over repeated trades, but this would need to be validated empirically with actual double-precision behavior at the specific balance magnitudes involved — the current evidence conclusively shows the legacy/default engine is imprecise and diverges from the exact engine, but I have not simulated a full attack sequence quantifying the exact drained amount.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
