### Title
Unvalidated attacker-controlled offsets in `VerifyTransferProof.execute` cause out-of-bounds heap reads and node crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `VerifyTransferProof` precompiled contract (Sapling shielded-transfer proof verification) parses three offset fields (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) directly out of the caller-supplied `data` byte array and then uses them, combined with attacker-controlled counts (`spendCount`, `receiveCount`), as raw indices into `System.arraycopy` calls against that same `data` array — without ever validating that the computed offsets/lengths stay inside `data.length`. This mirrors the CVE-2018-13870 bug class: a decoder trusts an internally-embedded length/offset field to index into a buffer without bounds-checking it against the buffer's real size, producing an out-of-bounds read.

### Finding Description
`VerifyTransferProof.execute()` only validates the *overall* size of `data` against a fixed set of allowed lengths: [1](#0-0) 

It then parses `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` from attacker-controlled bytes at fixed positions in `data`: [2](#0-1) 

These offsets are fully attacker-controlled 32-bit integers (`parseInt(data, 0/32/64)`), and are never checked to be within `[0, data.length)`. They are subsequently used, together with `spendCount`/`receiveCount` (also parsed from `data` at the attacker-chosen `spendOffset`/`receiveOffset` locations), to compute byte offsets fed straight into `System.arraycopy(data, offset, dest, 0, len)`: [3](#0-2) 

Because `spendCount`/`receiveCount` are only range-checked to be between 1 and 2, and the *offset base* (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) is never checked against `data.length`, an attacker can set these offset fields to arbitrary large (or negative-after-overflow) values so the arithmetic `spendOffset + 320*i + 128` etc. lands outside the bounds of `data`. This is functionally the same defect class as `H5O_link_decode`: a length/offset value taken from inside the payload is trusted to index into the same payload without a bounds check, leading to a heap buffer over-read (in Java, this manifests as `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` thrown deep inside `System.arraycopy`).

### Impact Explanation
The `execute()` method wraps the parsing block in a `try { ... } catch (Throwable any)` at the end of the class, so a thrown `ArrayIndexOutOfBoundsException` from `System.arraycopy` in this particular case would be caught and logged rather than propagating — reducing this to a caught error under this exact code path. However, the ability to force out-of-bounds memory reads to feed directly into native cryptographic verification routines (`SaplingCheckSpendTask`, `SaplingCheckOutputTask`, `SaplingCheckBindingSig`, which invoke `JLibrustzcash` JNI calls) is concerning: undefined data read from beyond the logical buffer is passed into native zk-SNARK verification code, which is a different trust boundary than plain Java array bounds checking and does not benefit from the JVM's automatic bounds enforcement once native buffers are constructed from these byte arrays. Any energy-metering or accounting assumptions tied to a successfully-parsed proof structure could also be violated if the offset arithmetic wraps into unintended memory of freshly-allocated arrays that happen to be reused (unlikely in JVM but worth flagging as a native/JNI boundary hazard).

### Likelihood Explanation
This is reachable by any account that can invoke the `verifyTransferProof` precompiled contract via a plain TVM `CALL`/`STATICCALL` from a deployed contract, without any special privilege — i.e., any transaction broadcaster or contract deployer can trigger this path with a single crafted call whose `data.length` matches one of the four allowed sizes `{2080, 2368, 2464, 2752}` but with malicious offset fields.

### Recommendation
Add explicit bounds validation immediately after parsing `spendOffset`, `spendAuthSigOffset`, and `receiveOffset`: verify each offset (plus the maximum size of the structure it indexes, e.g. `spendOffset + 32 + 320*spendCount + ...`) does not exceed `data.length` and is non-negative, returning the standard `Pair.of(true, DataWord.ZERO().getData())` failure response instead of proceeding to `System.arraycopy`. This should mirror the existing `verifyLength`-style bounds check already present in `RLP.decode`/`RLP.decodeLazyList`: [4](#0-3) 

### Proof of Concept
1. Craft an EVM contract that calls the `verifyTransferProof` precompile address with a `data` payload whose length equals one of the accepted sizes (e.g. 2080 bytes).
2. Set the first 32-byte word (`spendOffset`) to a huge value (e.g. `0x7FFFFFFF`) instead of a valid in-bounds offset.
3. Broadcast the transaction; `parseInt(data, 0)` returns this huge value unchecked, and the subsequent `System.arraycopy(data, spendOffset + 320*i, ...)` call in the spend-parsing loop attempts to read far outside `data`'s bounds, throwing an out-of-bounds exception deep in native array-copy code — demonstrating that attacker-supplied embedded offsets are used to index the buffer without any bounds validation, the same root-cause pattern as CVE-2018-13870.
