Based on my analysis, I can identify a concrete analog in the TRON exchange (Bancor-style AMM) module, which mirrors the class of "contract vulnerability → funds drained/mispriced pool" bug reported for TLN Protocol.

### Title
Legacy `ExchangeProcessor` uses unchecked floating-point math for AMM pricing while the safe/hardened path is gated behind a committee proposal - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` compute swap outputs for TRON's built-in Bancor-formula asset exchange via `ExchangeCapsule.transaction()`. That method selects between two pricing engines depending on a dynamic property flag: the legacy `ExchangeProcessor` (double-precision floating point, no overflow/negative-balance checks) or `SafeExchangeProcessor` (BigDecimal, with explicit invariant checks). The safe path is only used when `allowHardenExchangeCalculation()` returns true, which itself is only set via a committee/SR proposal.

### Finding Description
`ExchangeCapsule.transaction()` dispatches on `hardenedCalc`: [1](#0-0) 

When `hardenedCalc` is false (the legacy/default path unless a committee proposal has flipped the flag), pricing is computed by `ExchangeProcessor`, which performs the Bancor relay-token math purely with `double` and `Math.pow`, with no arithmetic-overflow or bounds checking: [2](#0-1) 

Contrast this with `SafeExchangeProcessor`, which uses `BigDecimal` with explicit rounding and scale control, and the hardened branch in `ExchangeCapsule.transaction()`, which explicitly rejects negative resulting balances: [3](#0-2) [4](#0-3) 

The gate is controlled purely by `allowHarden()` in the actuator base class, which reads a dynamic property that (per `ProposalUtil`/`ProposalService`) is only enabled by a committee-approved chain parameter change — i.e., it is off by default on any chain/fork where the proposal hasn't been passed: [5](#0-4) 

This means `ExchangeTransactionActuator.execute()`/`doValidate()`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` all reach the unchecked, floating-point AMM math by default, callable directly by any address that owns TRX/TRC-10 tokens via a signed `ExchangeTransactionContract`: [6](#0-5) 

Double-precision `Math.pow`-based Bancor formulas are known to be exploitable for rounding/precision manipulation at extreme pool ratios or repeated small trades (the class of bug SlowMist flagged for TLN Protocol — "Contract Vulnerability" causing AMM value loss). Because `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` never validates that the resulting pool balances stay non-negative or consistent, an attacker who can drive one side of the pool toward extreme values (e.g., very small `firstTokenBalance`/`secondTokenBalance` via `ExchangeWithdrawActuator`, which is also reachable by an unprivileged owner of the exchange) can distort the floating-point pow computation to extract more of the counter-asset than the pool holds, or push a balance negative (accepted silently since no check exists in the legacy path), producing unbacked token issuance or draining the counterparty asset pool.

### Impact Explanation
If exploited, an attacker can extract more value from an on-chain AMM pool (TRX or TRC-10 asset) than they contributed, directly analogous to the $280k TLN Protocol loss caused by a contract-level pricing/rounding vulnerability. This is a direct theft-of-funds vector reachable from a single signed `ExchangeTransactionContract`/`ExchangeWithdrawContract`/`ExchangeInjectContract` transaction, requiring no special privilege beyond owning the exchange or trading against it.

### Likelihood Explanation
Likelihood is Medium: exploitation requires crafting specific quantities/ratios to trigger floating-point rounding errors large enough to be profitable, and mainnet TRON may already have the "harden" proposal active (I was unable to confirm from the index whether `ALLOW_HARDEN_EXCHANGE_CALCULATION` is currently enabled on production TRON, since committee proposal state is a runtime/on-chain value, not a static default in the code I could inspect). The presence of dedicated test cases exercising "hardened" vs. legacy paths, and a dedicated `SafeExchangeProcessor` fix confirms the legacy path was recognized internally as unsafe and needed hardening — but until the corresponding chain parameter is activated by SRs, any deployed node still executes the vulnerable legacy math for every exchange trade.

### Recommendation
Make `SafeExchangeProcessor` (BigDecimal-based, bounds-checked) the only pricing engine for `ExchangeCapsule.transaction()`, removing the feature-flag/committee-proposal gate, or activate `AllowHardenExchangeCalculation` immediately on all networks. Additionally add negative-balance/invariant checks to the legacy `ExchangeProcessor` path (or delete it entirely) so that no non-hardened code path can execute unchecked floating-point Bancor math in production.

### Proof of Concept
1. Attacker creates/uses an existing TRON Bancor-style Exchange pool (`ExchangeCreateActuator`) with a heavily skewed token ratio (achievable via repeated `ExchangeInjectActuator`/`ExchangeWithdrawActuator` calls, both reachable by the exchange owner).
2. Attacker sends an `ExchangeTransactionContract` with a `tokenQuant` chosen so that `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`'s double-precision `Math.pow` rounding yields an `anotherTokenQuant` that is disproportionately large relative to the actual pool reserves (confirmed against `ExchangeTransactionActuator.execute()` line [7](#0-6)  which credits `anotherTokenQuant` to the attacker's account without any post-hoc pool-balance sanity check when `hardenedCalc` is false).
3. Repeat the trade to drain the counter-asset reserve; because the legacy path lacks the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` guard present only in the hardened branch, the pool can be driven into an inconsistent/negative state without the transaction failing.

**Note:** I could not fully verify from the indexed code whether `AllowHardenExchangeCalculation` is enabled by default on current mainnet TRON (this is a runtime dynamic-property/committee-proposal value, not visible statically). If the flag is already permanently on for mainnet, the reachable severity of this specific finding is reduced to a historical/legacy-fork risk rather than a live mainnet exploit. Confirming the current on-chain value of this parameter would require a live node query rather than static code review.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
