### Title
Outbound-handshake first-contact bypass lets a remote peer poison an unrelated victim's PeerDB entry - ([File: stackslib/src/net/chat.rs])

### Summary
`ConversationP2P::validate_handshake` only checks that `HandshakeData.addrbytes/port` matches the socket the local node actually connected to when `self.connection.get_public_key()` is already `Some(_)` (the re-key case). On first contact (`None` case), it verifies only that the message is signed by `handshake_data.node_public_key` itself — it never checks that key/address against anything external. `handle_handshake` then, for outbound connections, feeds that attacker-chosen `handshake_data` (address + key) straight into `Neighbor::load_and_update`/`neighbor.save_update`, which updates the PeerDB row keyed on the attacker-supplied `addrbytes`/`port`, not the actual peer this connection is talking to.

### Finding Description
The claimed equality — "peer identity bound to a `NeighborKey` slot in the frontier table == identity that actually authenticated traffic from that IP:port" — is broken.

- `validate_handshake` (`stackslib/src/net/chat.rs:1047-1126`):
  - `None` branch (first contact, lines 1058-1071): calls `message.verify_secp256k1(&handshake_data.node_public_key)` — this only proves the message was signed by whatever key is embedded in the payload; it proves nothing about `handshake_data.addrbytes`/`port`.
  - `Some(_)` branch (lines 1072-1091): the address/port cross-check (`self.peer_addrbytes != handshake_data.addrbytes || self.peer_port != handshake_data.port`) is applied **only** when we already have a stored public key for this connection (i.e., re-keying an already-authenticated peer). It is never applied on first contact.
- `handle_handshake` (`stackslib/src/net/chat.rs:1214-1296`) calls `validate_handshake`, then `update_from_handshake_data`, and — critically — for outbound connections when `updated` (first-time key learn) is true, line 1275-1286 does:
  ```
  let (mut neighbor, _) = Neighbor::load_and_update(&tx, message.preamble.peer_version, message.preamble.network_id, &handshake_data)?;
  neighbor.save_update(&tx, None)?;
  ```
- `Neighbor::load_and_update` (`stackslib/src/net/chat.rs:475-516`) builds the DB key via `NeighborKey::from_handshake(peer_version, network_id, handshake_data)` (`stackslib/src/net/chat.rs:411-423`), which uses `handshake_data.addrbytes`/`handshake_data.port` verbatim — fully attacker controlled — not `self.peer_addrbytes`/`self.peer_port` (the real socket address of the TCP connection). It loads any existing PeerDB row at that (attacker-chosen) address/port and overwrites its `public_key` with `handshake_data.node_public_key`.
- `Neighbor::save_update` (`stackslib/src/net/neighbors/neighbor.rs:50-61`) calls `PeerDB::update_peer(tx, self)`, which updates the existing row matched by `addrbytes`/`port` in place — poisoning whatever peer entry already occupies that `NeighborKey` slot with the attacker's key.

Exploit flow: the attacker's node accepts (or otherwise ends up as the far end of) an outbound connection from the victim's node for which no public key has yet been learned. It replies to the handshake with `HandshakeData{ addrbytes: <target victim IP>, port: <target victim port>, node_public_key: B, ... }`, signed with private key B. `verify_secp256k1(&B)` succeeds because the signature does correspond to `B` — there is no requirement that `B` correspond to the entity actually reachable at the claimed address. `validate_handshake` returns `Ok` (no address check fires because `get_public_key()` was `None`). `handle_handshake` then writes `public_key = B` into the PeerDB row keyed by the victim's `NeighborKey`, replacing whatever key legitimately represents that IP:port.

### Impact Explanation
This is an unauthenticated write to node state (PeerDB frontier table): the attacker forges the recorded identity (secp256k1 public key) associated with an arbitrary victim `NeighborKey` slot without ever proving control of that victim's address. Consequences include: subsequent code that trusts `PeerDB::get_peer`/`Neighbor::from_conversation` results for that slot (e.g., allow/deny checks, ban logic, StackerDB replica trust, neighbor-walk trust propagation) now believes the attacker's key represents that address, enabling on/off-path identity assumption for that `IP:port` in this node's local frontier view. This matches the "Critical: unauthenticated/unauthorized write to state" category. Repeatable per fresh outbound connection where the local peer hasn't yet cached a public key for that connection.

### Likelihood Explanation
Preconditions:
- The local node initiates an outbound connection to some peer for which it has not yet stored a public key on that connection (`self.connection.get_public_key() == None`) — this is the ordinary state for any brand-new outbound handshake, including normal neighbor-walk connects to previously-unauthenticated addresses.
- `self.stats.outbound == true` for that connection (write happens only on the outbound branch of `handle_handshake`).
- `PeerDB::update_peer` is a no-op if there is no existing row at the attacker-claimed `addrbytes`/`port`; the practical impact therefore requires that the local node's PeerDB already contains a row for the victim `NeighborKey` (very common — bootstrap peers, gossip-learned neighbors, prior connections all populate this table), which the attacker can determine indirectly by choosing well-known/bootstrap peer addresses.

Attacker cost is trivial: run a normal node/peer, wait to be dialed (or otherwise appear as the far end of an outbound connect), and reply to the handshake with a crafted `HandshakeData`. No privileged role, no compromise of any secret, and it uses only the standard P2P wire protocol.

### Recommendation
Enforce the same address-consistency check for outbound connections in the `None` branch of `validate_handshake` as is already applied in the `Some(_)` branch — i.e., before accepting/first-caching a public key on an outbound connection, require `handshake_data.addrbytes`/`port` to match `self.peer_addrbytes`/`self.peer_port` (accounting for the anynet exception), independent of whether a previous key was known. Additionally, `Neighbor::load_and_update`/`PeerDB::update_peer` should key off the conversation's actual verified socket address (`convo.to_neighbor_key()`) rather than the self-reported `handshake_data.addrbytes/port` when persisting re-key updates for outbound peers.

### Proof of Concept
Add a Rust test in `stackslib::net::chat::tests` modeled on `convo_handshake_rekey`/`convo_handshake_badsignature`:
1. Set up two `ConversationP2P`s and `PeerDB`s (`peerdb_1`, `peerdb_2`), and pre-insert a "victim" `Neighbor` row into `peerdb_1` for `NeighborKey{addrbytes: victim_ip, port: victim_port}` with victim's real public key `A`.
2. `convo_1` (victim's local peer) opens an outbound connection (`stats.outbound = true`) to `convo_2` (attacker), with no public key cached yet on that connection (`convo_1.connection.get_public_key().is_none()`).
3. Attacker (`convo_2`) crafts `HandshakeData { addrbytes: victim_ip, port: victim_port, node_public_key: B, .. }`, signs the resulting `StacksMessage` with private key `B` via `sign_message`, and sends it as the reply to `convo_1`'s handshake request.
4. `convo_1.chat(...)` processes the message, calling `handle_handshake` → `validate_handshake` (should succeed since address check is skipped) → `Neighbor::load_and_update` + `save_update`.
5. Assert: `PeerDB::get_peer(peerdb_1.conn(), network_id, &victim_ip, victim_port).unwrap().unwrap().public_key == B` (not `A`), proving the victim's frontier slot was overwritten with the attacker's unrelated key without any proof that `B` controls `victim_ip:victim_port`.
