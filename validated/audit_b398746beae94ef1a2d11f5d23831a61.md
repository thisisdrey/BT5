### Title
Firewall `code` field is reused as `port`, letting an ICMP-code rule silently authorize TCP/UDP traffic on the same numeric value - (File: `firewall.go`)

### Summary
Nebula firewall rules accept a `port` OR a `code` field. Internally, `code` is not modeled as a distinct semantic value (ICMP type/code); it is funneled through the exact same `sPort`/`parsePort` machinery as `port` and stored in the identical integer-indexed `firewallPort` map used for TCP/UDP ports. This mirrors the ERC721/ERC1155 proxy bug class described in the report: a single wire/storage field (`amount`, here the `firewallPort` map key) is overloaded to carry two semantically different values (`tokenId` for ERC721 vs. transfer `amount`; here ICMP `code` vs. TCP/UDP `port`), and downstream logic that assumes one meaning can be driven by input meant for the other.

### Finding Description
`convertRule` parses either `port` or `code` from the YAML rule into a single `rule.Port`/`rule.Code` pair, but the caller only ever passes one numeric string (`sPort`) into `parsePort`, and that result becomes `startPort`/`endPort` regardless of whether the value came from `port` or `code`:
<cite repo="Lauraivanka/nebula--002" path="firewall.go" start="351="358" />

For `proto: icmp`, `AddFirewallRulesFromConfig` explicitly overrides `startPort`/`endPort` to `firewall.PortAny` and warns that any port/code value is ignored — this path is safe. [1](#0-0) 

However, for `proto: any` (`firewall.ProtoAny`), no such coercion happens — `startPort`/`endPort` are computed straight from `parsePort(sPort)`, whether `sPort` originated from `port` or `code`: [2](#0-1) 

`AddRule` then stores this rule under `ft.AnyProto[startPort..endPort]` for `firewall.ProtoAny`, with no distinction that the numeric value was intended as an ICMP code rather than a transport port: [3](#0-2) 

At match time, `FirewallTable.match` checks `ft.AnyProto.match(...)` for *every* packet regardless of protocol (TCP, UDP, ICMP, anything else), before even switching on `p.Protocol`: [4](#0-3) 

And `firewallPort.match` looks up the packet's real `LocalPort`/`RemotePort` against that same integer-keyed table for non-ICMP protocols: [5](#0-4) 

Net effect: an administrator who writes `{proto: any, code: 8, host: X}` intending to scope a rule to "ICMP type/code 8 from host X" instead creates a rule that is functionally identical to `{proto: any, port: 8, host: X}` — it also matches and allows any TCP or UDP packet from host X on port 8, and it also matches ICMP packets carrying an unrelated identifier of 8 in the connection-track sense (since ICMP matching itself ignores the code entirely and always resolves to the `PortAny` slot, per the comment "port numbers are re-used for connection tracking of ICMP, but we don't want to actually filter on them"). The `code` value is never actually checked against the packet's real ICMP type/code (`fp.LocalPort` is hardcoded to 0 for ICMP in `parseV4`, with the actual code byte deliberately left unread): [6](#0-5) 

### Impact Explanation
This is a firewall bypass / rule-scope confusion: a rule authored to be narrowly scoped to ICMP behavior using `code` is silently widened to also permit TCP and UDP traffic on the identical numeric value whenever `proto: any` is used, because the `code` and `port` fields collapse into the same lookup key with no protocol-aware disambiguation. An attacker who can reach the host over the overlay (already authenticated via a valid but restricted cert/group) can exploit any such misconfigured rule to send TCP/UDP traffic on the aliased port number that the operator never intended to allow, directly analogous to how the ERC721 `amount`/`tokenId` collision let an attacker manipulate order fills using a value meant for a different purpose.

### Likelihood Explanation
Any deployment that expresses an ICMP-code-scoped rule with `proto: any` (a legitimate, undocumented-as-forbidden combination) is silently affected — no attacker action is needed to create the exposure, only to exploit the resulting overly-permissive rule by sending ordinary TCP/UDP traffic on the aliased port. Because `code`/`port` are mutually exclusive at the parsing level (`only one of port or code should be provided`) but not protocol-scoped, this is easy to hit unintentionally and requires no crafted/malformed packets to trigger — only a normal packet on the "wrong" protocol.

### Recommendation
Reject or ignore `code` when `proto` is not `icmp`/`icmpv6` (mirroring the existing warning+coercion already done for the `icmp` proto branch), and give `code` its own storage/lookup path distinct from the transport-port keyed `firewallPort` map so it can never alias into TCP/UDP or `AnyProto` rule slots. Additionally, since the actual ICMP type/code byte is never parsed out of the packet in `parseV4`/`parseV6`, either implement real code-based matching or remove the `code` config option entirely to avoid a rule that appears functional but is not enforced as documented.

### Proof of Concept
1. Configure an inbound firewall rule: `{proto: any, code: "8", host: "victim-group-member"}`, intending to scope this narrowly to ICMP type/code 8 traffic.
2. `AddFirewallRulesFromConfig` parses `code` into `startPort=endPort=8` and calls `fw.AddRule(..., firewall.ProtoAny, 8, 8, ...)` — no ICMP-specific coercion applies because `proto` is `any`, not `icmp`.
3. `AddRule` stores the rule at `ft.InRules.AnyProto[8]`.
4. An attacker (already a valid peer matching `host`/group constraints) sends a plain TCP or UDP packet with destination port 8.
5. `FirewallTable.match` checks `ft.AnyProto.match(p, ...)` unconditionally for every protocol, `firewallPort.match` looks up `fp[8]` using the packet's real `LocalPort`, finds the rule, and the traffic is allowed — despite the operator's intent being solely to permit an ICMP code, never TCP/UDP port 8.

func (ft *FirewallTable) match(p firewall.Packet, incoming bool, c *cert.CachedCertificate, caPool *cert.CAPool) bool {
	if ft.AnyProto.match(p, incoming, c, caPool) {
		return true
	}

	switch p.Protocol {
	case firewall.ProtoTCP:
		if ft.TCP.match(p, incoming, c, caPool) {
			return true
		}
	case firewall.ProtoUDP:
		if ft.UDP.match(p, incoming, c, caPool) {
			return true
		}
	case firewall.ProtoICMP, firewall.ProtoICMPv6:
		if ft.ICMP.match(p, incoming, c, caPool) {
			return true
		}
	}

	return false
}
