### Title
Non-constant-time authorization header comparison in block proposal RPC endpoint enables timing-based secret recovery - (File: stackslib/src/net/api/postblock_proposal.rs)

### Summary
`RPCBlockProposalRequestHandler::try_parse_request` compares the caller-supplied `authorization` header against the configured secret with a plain `!=` string comparison rather than a constant-time comparison. Because Rust's `String`/`&str` equality short-circuits and compares byte-by-byte (effectively `memcmp`), the comparison time is correlated with the length of the matching prefix, allowing an attacker to recover the secret one byte at a time via repeated timing measurements.

### Finding Description
At [1](#0-0) , the handler does:
```rust
let Some(password) = &self.auth else { ... };
let Some(auth_header) = preamble.headers.get("authorization") else { ... };
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```
`auth_header != password` invokes `String`'s `PartialEq`, which ultimately compares the underlying byte slices. This comparison is not constant-time: it returns as soon as a length mismatch or a differing byte is found. No `subtle::ConstantTimeEq` or similar fixed-time comparator is used anywhere in this file, nor in the sibling RPC-secret-gated handlers (`postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`, `fastcallreadonly.rs`), all of which share the identical `auth_header != password` pattern (confirmed via grep — no `constant_time`/`ConstantTimeEq` usage exists in `stackslib/src/net/api/*.rs`).

An attacker with no prior knowledge of the secret can:
1. Send `POST /v3/block_proposal` with an `authorization` header value that is a candidate prefix (e.g., a single guessed byte) and measure response latency for the 401.
2. Because a match on more leading bytes causes the comparison to iterate further (and only diverges on the first non-matching byte, before returning), correct prefixes statistically produce a measurably longer rejection path than incorrect ones, especially over many trials to average out noise.
3. Repeat byte-by-byte to iteratively reconstruct the full secret, then use it to gain authorized access to `/v3/block_proposal` — an endpoint that is otherwise gated specifically to keep proposal submission restricted to a trusted signer/miner set.

This is a genuine violation of the endpoint's threat model: the whole point of the `auth` gate is that a remote, unprivileged party cannot submit block proposals without the secret. A timing oracle that reveals prefix-correctness meaningfully lowers the cost of recovering that exact secret, defeating the intended access control.

### Impact Explanation
If the secret is recovered, the attacker gains the ability to submit authenticated `POST /v3/block_proposal` requests, which is an auth-bypass on a privileged local RPC endpoint (miner/signer only path). This matches the "auth bypass" Critical category. It affects any node operator who exposes this endpoint to a network reachable by the attacker (e.g., miner/signer coordination in a permissive network setup), and is repeatable since the timing oracle is available on every request.

### Likelihood Explanation
Preconditions: the node must have `self.auth` (`block_proposal_config.password` typically) configured, since with `auth = None` the endpoint returns 400 unconditionally, closing off the endpoint entirely rather than validating - so the timing channel is only exploitable when the operator has enabled the block-proposal RPC surface, which is precisely the case the confidentiality control is meant to protect. The attacker needs many timing samples per byte to overcome network/system jitter, so exploitation cost scales with secret length and required statistical confidence, but no privileged access, secret knowledge, or non-remote capability is required — only network reachability to the RPC port, which is explicitly in the allowed threat model.

### Recommendation
Replace the direct `!=` string comparison with a constant-time comparison, e.g. using the `subtle` crate's `ConstantTimeEq` on the UTF-8 byte representations of `auth_header` and `password` (comparing fixed-length hashes, such as a SHA-256 digest of both values, is a common robust pattern to also normalize length-dependent timing). Apply the same fix consistently to all sibling handlers using the identical `auth_header != password` pattern (`postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`, `fastcallreadonly.rs`).

### Proof of Concept
Add a Rust benchmark/test in `stackslib/src/net/api/tests/postblock_proposal.rs` that:
1. Configures `RPCBlockProposalRequestHandler::new(Some("s3cr3t-password".into()))`.
2. Crafts an `HttpRequestPreamble` with an `authorization` header value that shares an increasing number of leading bytes with the real password (e.g., `""`, `"s"`, `"s3"`, ... `"s3cr3t-passwor"`), each still ultimately incorrect.
3. Wraps the call to `try_parse_request` (or directly benchmarks `auth_header != password`) in a high-resolution timer, averaged over many thousand iterations per prefix length to cancel noise.
4. Asserts that mean comparison time is monotonically non-decreasing with matching-prefix length (i.e., statistically distinguishable), demonstrating the timing side channel; a passing/constant-time implementation would show no such correlation (e.g., using `subtle::ConstantTimeEq::ct_eq` on both byte slices padded/hashed to fixed length).
