### Title
Postponed multi-dependency receipts survive `DeleteAccount`/`CreateAccount`, enabling authorization escalation against a recreated account - (`runtime/runtime/src/lib.rs`, `core/store/src/utils/mod.rs`)

### Summary
The postponed-receipt bookkeeping (`PendingDataCount`, `PostponedReceiptId`, `PostponedReceipt` trie entries) is keyed only by `receiver_id`/`receipt_id`/`data_id` and is never touched by `remove_account`. When a self-targeted multi-action receipt with N `input_data_ids` is only partially resolved before its receiver account is deleted, the remaining pending dependency count and the stored `PostponedReceipt` persist in the trie across account deletion and recreation, so the receipt is later executed against whatever account now occupies that `account_id`.

### Finding Description
`remove_account` in `core/store/src/utils/mod.rs` (lines 505-575) only removes `TrieKey::Account`, `TrieKey::ContractCode`, access keys/gas-key nonces, and `TrieKey::ContractData`. It has no knowledge of and never removes `TrieKey::PendingDataCount`, `TrieKey::PostponedReceiptId`, or `TrieKey::PostponedReceipt` entries. [1](#0-0) [2](#0-1) 

Meanwhile, `process_receipt`'s `Data` receipt handling in `runtime/runtime/src/lib.rs` decrements `PendingDataCount` purely based on state that survives independently of the account's existence: it looks up `PostponedReceiptId` for the data_id, decrements the stored `PendingDataCount`, and only when it hits `1 → 0` does it fetch the `PostponedReceipt` via `get_postponed_receipt` and execute it with `apply_action_receipt`. [3](#0-2) 

This logic is entirely agnostic to whether the account was deleted and recreated in between: for a 2-dependency postponed receipt, delivering the first `Data` receipt decrements `PendingDataCount` from 2 to 1 (line 1465-1471) and leaves the second `PostponedReceiptId` entry and the `PostponedReceipt` blob (containing e.g. `AddKey`/`DeployContract` actions) untouched in the trie. If the account is then deleted via `DeleteAccount` (whose implementation calls `remove_account`, which as shown above does not clean postponed-receipt state) and recreated via `CreateAccount`, the surviving `PendingDataCount == 1` is unaffected. Delivering the second `Data` receipt decrements the count to 0 (line 1421), fetches the stale `PostponedReceipt` (line 1431-1437), removes it from state, and unconditionally executes it via `apply_action_receipt` (line 1442-1455) against the account_id — which now refers to the newly created account, not the one that originally scheduled the receipt.

Because the original receipt is a self-targeted receipt (receiver_id == predecessor_id == account_id, e.g. produced by the account's own earlier contract via `promise_batch_action_*`), its actions execute with full self-authorization semantics in `apply_action_receipt`/action-application code without requiring any signature or access-key check tied to the *current* account's keys — the check that receiver == predecessor already passed when the receipt was originally created before deletion. The new account thus receives arbitrary attacker-chosen actions (e.g. `AddKey` granting a full-access key, or `DeployContract` installing arbitrary code) that were authorized only by the old, now-deleted account's execution context.

### Impact Explanation
This is an authorization-escalation bug: an attacker's own account can pre-stage a postponed self-receipt (via a WASM contract they deploy) with actions like `AddKey(FullAccess)` or `DeployContract`, partially resolve its dependencies, delete the account (refunding its balance), let someone else (or the same attacker) recreate an account with the same `account_id` (implicit accounts, or accounts deleted then recreated by a new owner), and then trigger delivery of the final dependency to have the stale receipt's actions applied to the new account without the new account owner's consent. This matches the "authorization escalation across accounts or promises" bounty category. Since named accounts generally cannot be trivially recreated by a different party at the identical id without cooperation (registrar/top-level accounts), the most directly attacker-controlled variant is: attacker deletes their own account and immediately recreates it themselves (e.g., re-registering the same account or via implicit account reuse), causing their own leftover postponed receipt to execute against their new account state — which is lower severity self-harm/self-escalation unless a third party can be induced to create an account at a colliding id. The generalization to N dependencies described in the question is confirmed by the code, but the practical severity depends on whether an attacker can get a *victim* to recreate an account at the exact deleted `account_id` before the postponed receipt is fully resolved.

### Likelihood Explanation
Preconditions: attacker must (1) deploy a contract capable of issuing a self-receipt with 2+ `input_data_ids` (e.g. via `promise_and`/`promise_batch_then` patterns) whose actions include privilege-granting actions, (2) arrange partial resolution of dependencies, (3) execute `DeleteAccount` on itself before all dependencies resolve, and (4) have the account recreated at the same `account_id` before the final dependency is delivered. Steps 1-3 are fully within an unprivileged attacker's control using standard contract/promise APIs and cost only gas/storage. Step 4 (a third party recreating the exact same account id) is the limiting factor for cross-account exploitation; for named accounts this requires the id to become available again and be re-registered, which is possible but adds friction and timing dependency. Self-targeted exploitation (attacker deletes and recreates their own account) is trivially repeatable at will.

### Recommendation
When executing `DeleteAccount`, iterate and purge any outstanding `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` trie entries keyed by the deleted `receiver_id` (analogous to how `remove_account` already purges access keys and contract data), or alternatively include an account "generation"/nonce in the `PostponedReceipt`/`PendingDataCount` trie keys that is bumped on `CreateAccount` so stale postponed receipts can never be matched against a newly created account. At minimum, `apply_action_receipt` should refuse to execute a postponed receipt whose receiver account existed under a different creation epoch/generation than when the receipt was postponed.

### Proof of Concept
Integration test in `runtime/runtime/src/tests` (or an `apply.rs`-style runtime test):
1. Create account `A` with a contract capable of firing a 2-input-data self-receipt whose action list is `[AddKey(FullAccess, attacker_pubkey), DeployContract(evil_wasm)]`.
2. Trigger the promise so the runtime postpones the action receipt, writing `PostponedReceipt`, `PendingDataCount=2`, and two `PostponedReceiptId` entries for the two `data_id`s.
3. Deliver only the first `Data` receipt; assert `PendingDataCount` is now `1` in state and the second `PostponedReceiptId` still resolves to the same `receipt_id`.
4. Submit and apply a `DeleteAccount` receipt for `A`; assert account, keys, and contract data are gone but `PendingDataCount`/`PostponedReceiptId`/`PostponedReceipt` entries for `A` still exist in the trie.
5. Submit a `CreateAccount` receipt recreating `A` (fresh, attacker not authorized).
6. Deliver the second `Data` receipt for the same `data_id`.
7. Assert: `PendingDataCount` reaches 0, the stale `PostponedReceipt` is executed, and the new account `A` now has `attacker_pubkey` as a full-access key and/or the evil contract deployed — despite never having authorized either action itself.
