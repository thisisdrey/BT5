Audit Report

## Title
Removal of delegate-dependency locking in `pallet-revive` allows a contract's `delegate_call`-depended-upon code to be deleted, bricking any contract that `delegate_call`s into it - (File: `substrate/frame/revive/src/vm/mod.rs`, `substrate/frame/revive/src/exec.rs`)

## Summary
`pallet-revive`'s `ContractBlob::remove` only checks the target code's own instantiation `refcount` (incremented/decremented on constructor/terminate and `set_code`), not any `delegate_call` dependency [1](#0-0) . Because `delegate_call` execution never increments this refcount for the delegated code hash, once the last direct instance of code `B` is terminated its refcount can reach zero, allowing anyone to call the public `remove_code` extrinsic and delete `PristineCode` for `B` even while contract `A` still `delegate_call`s into it, subsequently causing `A`'s calls into that code path to fail with `CodeNotFound`.

## Finding Description
`remove_code` dispatches to `ContractBlob::remove`, which only verifies `code_info.refcount == 0` and ownership before deleting `PristineCode` and `CodeInfoOf` [1](#0-0) . The `refcount` field tracks "the number of instantiated contracts that use this as their code" [2](#0-1)  and is incremented on constructor execution and via `set_code`/`set_code_hash`-equivalent paths [3](#0-2) [4](#0-3) . Nothing in the reviewed `delegate_call`/execution path increments this refcount for a code hash purely because it is the target of a `delegate_call`; the refcount tracks instantiation, not delegate-dependency. `pallet-contracts` explicitly solves this with an opt-in `lock_delegate_dependency`/`unlock_delegate_dependency` API that increments the same refcount type specifically to block removal while a delegate dependent exists, and enforces `CodeInUse` on `remove_code` for such cases [5](#0-4) [6](#0-5) . This lock mechanism and its associated storage field/API do not exist anywhere in `pallet-revive`; searches across `substrate/frame/revive/` for `delegate_dependency`/`lock_delegate` return no results in the pallet's own code. The refcount test (`refcounter`) in `pallet-revive` confirms that `PristineCode` is removed once the instantiation refcount reaches zero purely from `terminate` calls, without any consideration of delegate-call dependents [7](#0-6) .

## Impact Explanation
If contract `A` uses `delegate_call` to route logic (e.g., withdrawal/upgrade logic) into contract `B`'s code, and `B`'s own instance is terminated (dropping refcount to zero), any account can permissionlessly call `remove_code(H_B)` to delete `B`'s `PristineCode`. Subsequent `delegate_call`s from `A` into `H_B` will fail because the code is gone, permanently bricking that execution path in `A` with no recovery mechanism — a genuine "permanent user-fund or bridge-state lock" class impact if `A` holds value gated by that logic.

## Likelihood Explanation
The attack requires no privileged access: `terminate`/self-destruct and `remove_code` are both ordinary public extrinsics [1](#0-0) . The likelihood is dependent on whether contracts built for `pallet-revive` widely adopt an unprotected delegate-call proxy pattern with the depended-upon code left with a refcount that can reach zero (e.g., the delegate target contract's only instance self-destructs, or the code was only ever `upload_code`d without a separate long-lived instantiation). This is a plausible but not universal deployment pattern; the vulnerability is real in `pallet-revive`'s current design but its practical severity depends on contract-author usage.

## Recommendation
Introduce a delegate-dependency accounting mechanism in `pallet-revive` analogous to `pallet-contracts`'s `lock_delegate_dependency`/`unlock_delegate_dependency`, incrementing/decrementing the code's refcount (or a separate dependency counter) when a contract registers a `delegate_call` dependency, and enforce a `CodeInUse`-style check in `ContractBlob::remove` before allowing removal.

## Proof of Concept
1. Upload and instantiate contract `B` with code hash `H_B` (refcount becomes 1 via constructor's `increment_refcount` at `substrate/frame/revive/src/exec.rs:1364-1372`).
2. Instantiate contract `A` whose logic performs `delegate_call` into `H_B` (no refcount change occurs for `H_B` due to the delegate call itself).
3. Terminate `B`'s instance, decrementing `H_B`'s refcount to 0 (as shown by the `refcounter` test pattern at `substrate/frame/revive/src/tests/pvm.rs:1884-1923`).
4. Call the public `remove_code(origin, H_B)` extrinsic; it succeeds since `code_info.refcount == 0` per `ContractBlob::remove` at `substrate/frame/revive/src/vm/mod.rs:162-180`, deleting `PristineCode` for `H_B`.
5. Any subsequent call into `A` that triggers `delegate_call(H_B, ...)` now fails to load the code, permanently breaking that execution path in `A`.

	pub fn remove(origin: &T::AccountId, code_hash: H256) -> DispatchResult {
		<CodeInfoOf<T>>::try_mutate_exists(&code_hash, |existing| {
			if let Some(code_info) = existing {
				ensure!(code_info.refcount == 0, <Error<T>>::CodeInUse);
				ensure!(&code_info.owner == origin, BadOrigin);
				<Pallet<T>>::refund_deposit(
					HoldReason::CodeUploadDepositReserve,
					&Pallet::<T>::account_id(),
					deposit_payment::Funds::Balance(&code_info.owner),
					code_info.deposit,
				)?;
				*existing = None;
				<PristineCode<T>>::remove(&code_hash);
				Ok(())
			} else {
				Err(<Error<T>>::CodeNotFound.into())
			}
		})
	}

	fn lock_delegate_dependency(&mut self, code_hash: CodeHash<Self::T>) -> DispatchResult {
		let frame = self.top_frame_mut();
		let info = frame.contract_info.get(&frame.account_id);
		ensure!(code_hash != info.code_hash, Error::<T>::CannotAddSelfAsDelegateDependency);

		let code_info = CodeInfoOf::<T>::get(code_hash).ok_or(Error::<T>::CodeNotFound)?;
		let deposit = T::CodeHashLockupDepositPercent::get().mul_ceil(code_info.deposit());

		info.lock_delegate_dependency(code_hash, deposit)?;
		Self::increment_refcount(code_hash)?;
		frame
			.nested_storage
			.charge_deposit(frame.account_id.clone(), StorageDeposit::Charge(deposit));
		Ok(())
	}

#[test]
fn refcounter() {
	let (binary, code_hash) = compile_module("self_destruct_by_precompile").unwrap();
	ExtBuilder::default().existential_deposit(50).build().execute_with(|| {
		let _ = <Test as Config>::Currency::set_balance(&ALICE, 1_000_000);
		let min_balance = Contracts::min_balance();

		// Create two contracts with the same code and check that they do in fact share it.
		let Contract { addr: addr0, .. } = builder::bare_instantiate(Code::Upload(binary.clone()))
			.native_value(min_balance * 100)
			.salt(Some([0; 32]))
			.build_and_unwrap_contract();
		let Contract { addr: addr1, .. } = builder::bare_instantiate(Code::Upload(binary.clone()))
			.native_value(min_balance * 100)
			.salt(Some([1; 32]))
			.build_and_unwrap_contract();
		assert_refcount!(code_hash, 2);

		// Sharing should also work with the usual instantiate call
		let Contract { addr: addr2, .. } = builder::bare_instantiate(Code::Existing(code_hash))
			.native_value(min_balance * 100)
			.salt(Some([2; 32]))
			.build_and_unwrap_contract();
		assert_refcount!(code_hash, 3);

		// Terminating one contract should decrement the refcount
		assert_ok!(builder::call(addr0).build());
		assert_refcount!(code_hash, 2);

		// remove another one
		assert_ok!(builder::call(addr1).build());
		assert_refcount!(code_hash, 1);

		// Pristine code should still be there
		PristineCode::<Test>::get(code_hash).unwrap();

		// remove the last contract
		assert_ok!(builder::call(addr2).build());
		assert!(PristineCode::<Test>::get(&code_hash).is_none());
	});
