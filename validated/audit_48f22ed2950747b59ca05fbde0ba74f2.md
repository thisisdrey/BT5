## Finding

### Title
Access-key nonce reset via same-block DeleteKey+AddKey allows replay of an already-applied transaction, defeating NEAR's nonce-based replay protection - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`add_regular_key` unconditionally reseeds a recreated access key's nonce to `initial_nonce_value(block_height) = (block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, discarding whatever nonce was previously recorded for that public key. Because `verify_nonce`'s per-block upper bound allows nonces up to `block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER - 1`, an attacker can consume a nonce near that bound with a FunctionCall key, then delete+recreate the same public key within the *same* block, resetting the stored nonce below the consumed value. A previously-signed, already-applied transaction can then be resubmitted and re-validated because its nonce is now greater than the (rolled-back) stored nonce.

### Finding Description
- `initial_nonce_value` seeds new/recreated keys at `(block_height-1)*MULTIPLIER`: [1](#0-0) 
- `add_regular_key` clones the incoming `AccessKey`, overwrites its nonce with `initial_nonce_value(block_height)`, and stores it — with no comparison against any prior nonce for that public key: [2](#0-1) 
- `action_add_key` only rejects an `AddKeyAction` if the public key *currently* has an access key (`AddKeyAlreadyExists`); it performs no check against a key that has just been removed in the same receipt/transaction: [3](#0-2) 
- `verify_nonce` enforces `tx_nonce > current_nonce` (Monotonic) and `tx_nonce < block_height*MULTIPLIER` (upper bound tied to the *current* block height, not to any historical maximum ever used by the key): [4](#0-3) 
- The design intent that recreated keys must preserve the old nonce to avoid exactly this replay is documented but not enforced by the runtime: [5](#0-4) 
- The codebase already tracks a related, acknowledged defect in the same code path ("we forget the nonce when we delete a key"), confirming this nonce-loss-on-delete behavior is a known gap, tracked as TODO(#6724): [6](#0-5) 

Exploit flow (attacker only needs two access keys on their own account: a FullAccess key `K_full` and a FunctionCall key `K_fc` with allowance):
1. At block height `H`, submit `tx1` signed by `K_fc` with `nonce = H*MULTIPLIER - 1` (valid, just below the upper bound), calling a FunctionCall action against the permitted receiver. It succeeds, updates `access_key.nonce = H*MULTIPLIER - 1`, and consumes allowance.
2. Still at block height `H`, submit `tx2` signed by `K_full` containing `[DeleteKey(K_fc), AddKey(K_fc, fresh FunctionCallPermission)]` in one transaction. `action_delete_key` removes the key (discarding its nonce); the immediately following `AddKey` sees no existing key for that public key (so it is not rejected by `AddKeyAlreadyExists`) and calls `add_regular_key`, which sets `access_key.nonce = (H-1)*MULTIPLIER` — strictly less than `tx1`'s nonce, since `(H-1)*MULTIPLIER < H*MULTIPLIER - 1` for any `MULTIPLIER > 1`.
3. At any block height `H' >= H`, resubmit the identical `tx1` bytes. `verify_nonce` now checks `tx1.nonce (= H*MULTIPLIER-1) > current_nonce (= (H-1)*MULTIPLIER)` — true — and `tx1.nonce < H'*MULTIPLIER` — true for any `H' >= H`. The transaction is accepted again, re-executing the same FunctionCall action and drawing down the freshly restored allowance a second time for identical, already-paid-for work.

The chunk-level duplicate-hash guard (`skip_duplicate_txs`/`UniqueChunkTransactions`) only deduplicates within a single chunk's transaction list and does not prevent resubmission of the same transaction in a later block, so it does not stop step 3.

### Impact Explanation
This breaks the fundamental nonce-based replay-protection invariant that the protocol and downstream contracts rely on ("Nonce monotonicity prevents replay"). An attacker can cause a previously-executed FunctionCall transaction (and its receipt-level side effects, e.g. calls into their own or a third-party contract) to execute a second time. Where such calls have financial side effects (bridge withdrawal, voucher redemption, allowance-funded call whose target contract assumes each signed near-transaction executes at most once), this yields double-spend/replay impact and double-charging of the account's balance for one logical action — matching the "double-spend/replay" bounty category.

### Likelihood Explanation
Fully reachable by an ordinary, unprivileged account: no validator, RPC-operator, or leaked-key access is required — only two access keys on the attacker's own account and the ability to submit transactions to a public RPC endpoint. The only timing constraint is that the DeleteKey+AddKey transaction must land in the same block as the original high-nonce transaction, which is achievable because the two transactions use independent access keys (independent nonce sequences) and can be submitted together. This is repeatable per key/account and does not require any validator/chunk-producer collusion.

### Recommendation
When recreating an access key that reuses an existing/just-deleted public key, the runtime must not reseed the nonce below any nonce that could plausibly have already been used by that public key. Concretely, `add_regular_key` (and `add_gas_key`) should take the maximum of `initial_nonce_value(block_height)` and the nonce of the access key being replaced (tracked via `action_delete_key`/`action_add_key` in the same receipt, or persisted independently of the `AccessKey` record) rather than unconditionally resetting to `(block_height-1)*MULTIPLIER`.

### Proof of Concept
Integration/runtime test plan (e.g. in `runtime/runtime/src/tests/apply.rs` alongside the existing `test_access_key_allowance_not_mutated_on_failed_tx`/gas-key tests):
1. Create account `alice` with a `FullAccess` key `K_full` and a `FunctionCall` key `K_fc` (receiver `bob`, allowance `X`).
2. At `apply_state.block_height = H`, build `tx1`: FunctionCall action from `K_fc`, `nonce = H*MULTIPLIER - 1`. Apply it; assert success and that `access_key.permission.allowance` decreased by the call's cost.
3. At the same `block_height = H`, build `tx2` signed by `K_full`: `[DeleteKey(K_fc.public_key), AddKey(K_fc.public_key, FunctionCallPermission{allowance: Some(X), ..})]`. Apply it in the same `apply()` call (or same block) as `tx1` (ordered after `tx1`). Read back the access key and assert `nonce == (H-1)*MULTIPLIER` and `allowance == X` (fully restored).
4. Resubmit the identical `tx1` (same signature/hash) at `block_height = H` (later in the same chunk, if `UniqueChunkTransactions` skip logic is bypassed by using a later block) or `H+1`. Assert it is accepted (`verify_nonce` passes) and the outcome is `SuccessReceiptId`, and assert the allowance decreases a second time by the same cost — proving the identical logical FunctionCall action was charged/executed twice against a single nonce that should have been consumed once.

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
