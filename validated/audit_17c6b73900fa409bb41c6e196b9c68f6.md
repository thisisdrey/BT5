### Title
Per-slot write-frequency rate limit (`write_freq`) is never enforced when accepting a chunk, allowing signer-throttling to be bypassed - (File: stackslib/src/net/stackerdb/db.rs)

### Summary
`StackerDBConfig.write_freq` is documented as "the minimum wall-clock time between writes to the same slot" [1](#0-0)  and is meant to bound how fast a slot owner can push new chunk versions. But the only function that actually commits a chunk to storage, `StackerDBTx::try_replace_chunk`, checks chunk size, slot ownership/signature, staleness, and `max_writes` — it never reads or checks `write_freq`/`write_time` at all. `write_freq` is honored only as an optional client-side heuristic when scheduling *sync fetches* in `StackerDBSync::make_chunk_request_schedule`, not as a server-side admission-control gate.

### Finding Description
The write path used by the unauthenticated HTTP endpoint `POST /v2/stackerdb/:principal/:contract/chunks` (`RPCPostStackerDBChunkRequestHandler::try_handle_request`) calls straight into `tx.try_replace_chunk(...)` [2](#0-1) .

`try_replace_chunk` performs exactly four checks — chunk size, slot existence/owner signature, stale-version, and `max_writes` — and then unconditionally calls `insert_chunk`: [3](#0-2) 

Nowhere in this function (nor in `insert_chunk`, which merely records the new `write_time` [4](#0-3) ) is the existing `SlotValidation.write_time` compared against `config.write_freq`. `SlotValidation` does carry `write_time` [5](#0-4) , but it is only read for accounting, never used as a gate.

The only place `write_freq` is consulted is in `StackerDBSync::make_chunk_request_schedule`, where the *syncing* node client-side skips *fetching* a chunk if it was written too recently — a courtesy to avoid re-downloading a chunk that's unlikely to have changed: [6](#0-5) 
And `validate_downloaded_chunk` / `validate_received_chunk` (used for both sync-downloaded and pushed chunks) explicitly documents that write frequency is *not* checked there, deferring to "the caller" — but no caller (including `try_replace_chunk`, the actual storage layer) ever performs that check: [7](#0-6) [8](#0-7) [9](#0-8)  even explicitly documents that write frequency is intentionally skipped for P2P pushes, reasoning that bandwidth throttling on the connection is sufficient — but this reasoning does not extend to the HTTP RPC endpoint, which has no comparable per-connection throttle tied to `write_freq`, and there `try_replace_chunk` is the sole gate and also omits the check.

This is directly analogous to the StRSR finding: `write_freq` is a rate/slope-governing parameter (like `rewardRatio`/`rewardPeriod`) that is supposed to bound how state accrues (write versions) over time, but the code path that actually commits state changes never consults it, so the "rate" constraint is silently unenforced.

### Impact Explanation
Any principal who legitimately owns a StackerDB slot (i.e., possesses the private key registered for that slot by the controlling smart contract) can call the unauthenticated `/v2/stackerdb/.../chunks` HTTP endpoint on any node and write new chunk versions as fast as the node can process HTTP requests, completely ignoring the `write_freq` throttle that operators/contract authors configured. Since each accepted write triggers a `StackerDBPushChunk` broadcast to the full network (`node.set_relay_message(...)` in `poststackerdbchunk.rs`), this becomes a network-wide bounded-compute/relay amplification vector limited only by `max_writes` and the writer's own request rate, not by the intended per-slot cadence. This fits the "bounded compute DoS on a read/write endpoint" / unauthorized write to state category, since data the operator intended to be rate-limited is instead written and propagated without limit.

### Likelihood Explanation
High likelihood for anyone who already controls a valid slot signing key (e.g., a legitimate signer/miner participant in `.signers` or `.miners` StackerDBs) — no special privilege beyond normal slot ownership is required, and the HTTP endpoint is reachable by any remote peer with RPC access. It does not require breaking any cryptographic check; it only requires noticing that `write_freq` is never enforced server-side.

### Recommendation
Enforce `write_freq` inside `StackerDBTx::try_replace_chunk` (and/or in `validate_received_chunk`'s caller before storage) by loading `slot_validation.write_time` and rejecting the write with `net_error::TooFrequentSlotWrites` (which already exists as an error variant, per `stackslib/src/net/mod.rs`) if `now < write_time + config.write_freq`, mirroring the existing `max_writes`/staleness checks in the same function.

### Proof of Concept
1. Configure or select a StackerDB contract with `write-freq` set to a large value (e.g., 3600 seconds).
2. Using a key that owns slot `N`, sign and `POST` a `StackerDBChunkData` with `slot_version = 1` to `/v2/stackerdb/<addr>/<contract>/chunks` on a target node — it is accepted (per `try_replace_chunk`/`insert_chunk`, `stackslib/src/net/stackerdb/db.rs:400-438,371-396`).
3. Immediately `POST` a second chunk with `slot_version = 2` for the same slot. Despite `write_freq` requiring an hour between writes, this second write is also accepted, because `try_replace_chunk` never checks `write_time` against `config.write_freq` — only staleness (`slot_version <= slot_validation.version`) and `max_writes` are checked (`stackslib/src/net/stackerdb/db.rs:424-436`).
4. Repeat rapidly up to `max_writes`, observing that each accepted chunk is relayed to the whole network as a `StackerDBPushChunkData` message (`stackslib/src/net/api/poststackerdbchunk.rs:315-324`), confirming the rate cap is bypassed and forged/uncapped propagation occurs.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
