### Title
`RewardsDistributor` fails to ensure `accountIndexOf` is initialized, allowing accounts to claim rewards from index 0 - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
Analogous to CVE-2017-9994 (`libavcodec/webp.c` does not ensure `pix_fmt` is set), `RewardsDistributor._calculateTokenDelta` does not ensure `accountIndexOf[token][account]` is set before using it as the baseline for reward accrual. When the account index is `0` (unset) it is only bumped to `INITIAL_INDEX` if the token index has already grown *strictly past* `INITIAL_INDEX`. If the token index is still exactly `INITIAL_INDEX` — e.g. rewards were just enabled for a token that already has holders, or no time has elapsed since registration — the unset index `0` is used as the baseline and the account accrues `balance * INITIAL_INDEX` instantly. [1](#0-0) 

### Finding Description
- When a governor calls `updateTokenSpeed`/`updateTokenSpeeds` for a token for the first time, `tokenStates[token_]` is set to `{index: INITIAL_INDEX (1e18), timestamp: now}` and the token is pushed to `tokens`. [2](#0-1) 
- The DepositToken/DebtToken may already have a large total supply and existing holders before the speed is set. None of those holders have an `accountIndexOf` entry — it is `0`.
- `claimRewards(account)` iterates `tokens`, sees `tokenStates[token].index > 0`, calls `_updateTokenIndex` then `_updateTokensAccruedOf`. [3](#0-2) 
- In `_calculateTokenDelta`, the guard `if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX)` fails when `_tokenIndex == INITIAL_INDEX` (i.e., same block as registration, or zero reward delta accrued so far), leaving `_accountIndex = 0`. `_deltaIndex = 1e18 - 0 = 1e18`, so `_tokensDelta = balance.wadMul(1e18) = balance` — the account's entire deposit/debt balance is credited as reward immediately, before a single second of legitimate accrual. [4](#0-3) 
- `_transferRewardIfEnoughTokens` then pays out `tokensAccruedOf` in `rewardToken` up to the distributor's full balance. [5](#0-4) 
- The path is unprivileged: `claimRewards(address)` and `claimRewards(address, IERC20[])` are public and permissionless; the attacker only needs to hold DepositToken/DebtToken balance (or receive a flash of it — note `updateBeforeMintOrBurn`/`updateBeforeTransfer` only fix the index when called, and an account that acquired balance *before* registration is never indexed).

### Impact Explanation
Every pre-existing holder can instantly claim reward tokens equal to their full token balance. Since rewards are meant to accrue at `tokenSpeeds` per second across all holders, paying `balance` per holder in the first block drains the distributor's `rewardToken` reserves — direct theft of the protocol's reward allocation and of other users' unclaimed yield (first claimers win; later users get nothing because `_transferRewardIfEnoughTokens` silently skips when balance is insufficient). The bug is deterministic whenever speed is set on a token with non-zero supply/holders, which is the normal deployment sequence.

### Likelihood Explanation
Likelihood is high on any new reward-token activation: the governor's `updateTokenSpeed` transaction and an attacker's `claimRewards` can land in the same block (attacker can front-run/back-run the governance tx since the mempool is public). No health check, cap, pause flag, or `onlyIfTokenExists` check stops it — `onlyIfTokenExists` is only enforced inside `_updateTokenSpeed`, not on the claim path. The only mitigation is that holders who touch the token via mint/burn/transfer after registration get their index stamped, but pre-existing idle holders remain exposed until the index grows past `INITIAL_INDEX`.

### Recommendation
Initialize the account index baseline with `>=` semantics: change the fallback to `if (_accountIndex == 0) { _accountIndex = _tokenIndex < INITIAL_INDEX ? INITIAL_INDEX : _tokenIndex; }` (or simply `_accountIndex = _tokenIndex` when it is `>= INITIAL_INDEX`), so an unset account index defaults to the *current* token index rather than `0`. Additionally, when a token's speed is first set, consider stamping indexes for existing holders or documenting that rewards distribution must start with the token already registered before supply exists.

### Proof of Concept
Hardhat (fork) sketch:

```typescript
// Assume: pool, depositToken (msUSD or vaToken deposit token), distributor deployed,
// attacker already holds depositToken balance BEFORE speed is set.

// 1. Governor registers the token for rewards (same block attacker acts)
await distributor.connect(governor).updateTokenSpeed(depositToken.address, speed);

// 2. tokenStates[depositToken].index == INITIAL_INDEX (1e18), timestamp == now.
//    Attacker's accountIndexOf == 0 (never touched token since registration).

const balBefore = await rewardToken.balanceOf(attacker.address);
const depBal = await depositToken.balanceOf(attacker.address);

// 3. In the SAME block (deltaTimestamp == 0) claim
await distributor.connect(attacker).claimRewards(attacker.address);

// 4. deltaIndex = 1e18 - 0 = 1e18  => tokensDelta = depBal
const balAfter = await rewardToken.balanceOf(attacker.address);
expect(balAfter.sub(balBefore)).to.eq(depBal); // steals reward == full balance
```

To run on a fork without same-block constraints, note the window stays open until the global index first exceeds `INITIAL_INDEX`; with zero or tiny `totalSupply` growth the first `_updateTokenIndex` may still leave `index == INITIAL_INDEX` (when `_deltaTimestamps == 0` or `_totalSupply == 0`, `_newIndex` stays `0`/unchanged), extending the window further. The invariant broken is reward-accrual conservation: rewards are paid out that were never emitted by `tokenSpeeds * time`.

        _tokenIndex = _tokenState.index;
