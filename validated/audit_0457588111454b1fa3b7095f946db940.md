## Analog Assessment

Based on the investigation, I found a plausible analog but cannot confirm the root-cause exploitability with full certainty because I was unable to inspect `hostmap.go`'s `RelayState`/`InsertRelay` internals or `outside.go`'s relay forwarding path within the remaining tool budget. Given that limitation, I will report what is concretely supported by the code I did examine, and flag the unresolved part explicitly.

### Title
Unvalidated `RelayFromAddr` in `CreateRelayRequest` allows an authenticated peer to install relay state for a VPN address it does not own - (File: `relay_manager.go`)

### Summary
`relayManager.handleCreateRelayRequest` in `relay_manager.go` [1](#0-0)  trusts the `RelayFromAddr` field of an incoming `NebulaControl_CreateRelayRequest` message without verifying it matches the sending peer's own certificate-bound VPN address (`h.vpnAddrs[0]`). The only identity check performed is that the *target* is not the sender itself; the *from* address is taken directly from the message and used to install relay state (`AddRelay`, `h.relayState.InsertRelay`) as if it were a legitimately owned identity of the peer.

### Finding Description
In `handleCreateRelayRequest`:
```go
from := protoAddrToNetAddr(m.RelayFromAddr)
target := protoAddrToNetAddr(m.RelayToAddr)
...
if f.myVpnAddrsTable.Contains(from) {
    logMsg.Error("Discarding relay request from myself", "myIP", from)
    return
}
if f.myVpnAddrsTable.Contains(target) {
    ...
    _, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
``` [2](#0-1) 

`h` is the already-authenticated `HostInfo` of the message sender (its identity was validated during the Noise handshake and cert verification, see `validatePeerCert` [3](#0-2) ). However `from` is an arbitrary VPN address chosen by that sender inside the control-message payload, and nowhere in `handleCreateRelayRequest` (nor in `HandleControlMsg`'s validation block, which only checks for nil `RelayFromAddr`/`RelayToAddr` [4](#0-3) ) is `from` checked against `h.vpnAddrs`. This mirrors the reported bug class: a component (`GiantMevAndFeesPool`) trusts a caller-supplied identifier (`_stakingFundsVaults`) without checking that it actually corresponds to the calling party, letting the caller assert an identity/relationship it doesn't own. Here, the relay peer `h` can claim to be relaying "from" any VPN address, causing this node to associate relay routing state (`h.relayState.InsertRelay(from, ...)`) for a victim address `from` with an attacker-controlled relay hostinfo `h`, and to respond with a `CreateRelayResponse` binding that spoofed relationship.

### Impact Explanation
If exploitable, this allows a malicious (but Nebula-authenticated) peer acting as a relay-request sender to insert relay routing state under a VPN address it does not control, potentially:
- Poisoning this node's relay state (`RelayState`/`Relays` map) for a third-party address, since `AddRelay` binds `vpnIp` (`from`) to `relayHostInfo` (the attacker's `h`) in `hm.Relays[index]` and `relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)` [5](#0-4) .
- Subsequent traffic addressed "from" that spoofed VPN address via this relay path could be misdirected/forged through the attacker-controlled hostinfo, since the terminal relay is marked `Established` immediately (`state == Established`) without any independent proof that `from` actually initiated anything.

This satisfies the "remote state poisoning" / potential "traffic forgery" impact categories, but I could not fully trace how `outside.go`'s data-plane relay forwarding subsequently uses `PeerAddr`/`relayForByIdx` to confirm end-to-end traffic redirection is achievable — this is the unresolved part.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to be a certificate-holding, already-handshaked Nebula peer capable of sending arbitrary `NebulaControl` messages to a node that has `relay.am_relay: true` set — a legitimate, unprivileged capability of any authenticated peer, not requiring any special role. No firewall or handshake bypass is needed to reach this code path; it only requires reaching `HandleControlMsg` → `handleCreateRelayRequest`, which is normal control-plane traffic once a tunnel exists.

### Recommendation
In `handleCreateRelayRequest` (and `handleCreateRelayResponse`), verify that `from` (`RelayFromAddr`) equals one of the sender's own certificate-verified VPN addresses (`h.vpnAddrs`) before creating or completing any relay state on that address's behalf, analogous to how `validatePeerCert` binds identity to certificate-verified VPN networks. Reject the control message if `from` is not owned by `h`.

### Proof of Concept
Full weaponization could not be conclusively demonstrated without deeper visibility into `hostmap.go`'s relay bookkeeping and `outside.go`'s relay-forwarding data path (both were not fully retrievable within the tool budget). Conceptually:
1. Peer `A` completes a normal, certificate-validated Nebula handshake with victim node `V`, with `V` configured as `am_relay: true`.
2. `A` sends `NebulaControl_CreateRelayRequest` to `V` with `RelayFromAddr = victimC` (an address `A` does not own) and `RelayToAddr = V`'s own address.
3. `V`'s `handleCreateRelayRequest` sees `target == V`, finds no existing relay state for `from = victimC`, and calls `AddRelay(..., h=A's hostinfo, victimC, ..., TerminalType, Established)`, binding `victimC` to `A`'s hostinfo — without ever confirming `victimC` belongs to `A`.
4. `V` responds with `CreateRelayResponse`, completing the (spoofed) relay association.

Given the incomplete verification of the downstream data-plane impact, this should be treated as a **candidate finding requiring further investigation** rather than a fully confirmed exploit chain.

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
				// Mark the relay as 'Established' because it's safe to use again
				h.relayState.UpdateRelayForByIpState(from, Established)
			case PeerRequested:
				// I should never be in this state, because I am terminal, not forwarding.
				logMsg.Error("Unexpected Relay State found",
					"existingRemoteIndex", existingRelay.RemoteIndex,
					"state", existingRelay.State)
			}
		} else {
			_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
			if err != nil {
				logMsg.Error("Failed to add relay", "error", err)
				return

// validatePeerCert checks the peer certificate for self-connection and remote allow list.
// Returns the VPN addrs, whether any of them fall within one of our own VPN
// networks, and true if valid; false if rejected.
func (hm *HandshakeManager) validatePeerCert(via ViaSender, remoteCert *cert.CachedCertificate) ([]netip.Addr, bool, bool) {
	f := hm.f
	vpnNetworks := remoteCert.Certificate.Networks()

	// The cert package rejects host certs with no networks at parse time, so
	// reaching this state would mean an invariant was bypassed elsewhere.
	// Refuse explicitly so downstream code (which indexes vpnAddrs[0]) can't
	// panic if that invariant ever changes.
	if len(vpnNetworks) == 0 {
		f.l.Info("No networks in certificate",
			"from", via, "cert", remoteCert)
		return nil, false, false
	}

	vpnAddrs := make([]netip.Addr, len(vpnNetworks))
	anyVpnAddrsInCommon := false

	for i, network := range vpnNetworks {
		if f.myVpnAddrsTable.Contains(network.Addr()) {
			f.l.Error("Refusing to handshake with myself",
				"vpnNetworks", vpnNetworks,
				"from", via,
				"certName", remoteCert.Certificate.Name(),
				"certVersion", remoteCert.Certificate.Version(),
				"fingerprint", remoteCert.Fingerprint,
				"issuer", remoteCert.Certificate.Issuer(),
			)
			return nil, false, false
		}
		vpnAddrs[i] = network.Addr()
		if f.myVpnNetworksTable.Contains(network.Addr()) {
			anyVpnAddrsInCommon = true
		}
	}

	if !via.IsRelayed {
		if !f.lightHouse.GetRemoteAllowList().AllowAll(vpnAddrs, via.UdpAddr.Addr()) {
			f.l.Debug("lighthouse.remote_allow_list denied incoming handshake",
				"vpnAddrs", vpnAddrs, "from", via)
			return nil, false, false
		}
	}

	return vpnAddrs, anyVpnAddrsInCommon, true
}
