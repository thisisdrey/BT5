### Title
Malicious attachment source can serve mismatched `Attachment` content, causing `AttachmentsBatchStateMachine` to resolve the wrong hash and permanently drop valid BNS attachment instances - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When `AttachmentsBatchStateMachine` downloads an attachment via `AttachmentRequest`, the response is decoded and stored keyed only by the *served* content's own hash, with no check against the `content_hash` that was actually requested. The `Done` state then resolves attachment instances using `attachment.hash()` (the served bytes' hash) rather than the requested `content_hash`, so a peer that serves arbitrary content never satisfies the pending instance, and the batch is retried until it hits `max_attachment_retry_count` and is silently dropped.

### Finding Description
`AttachmentRequest` carries the `content_hash` that the node actually needs [1](#0-0) . `AttachmentsBatchStateContext::extend_with_attachments` processes the HTTP response for such a request: it calls `response.decode_atlas_get_attachment()` and, on success, does `self.attachments.insert(response.attachment)` — it never compares `response.attachment`'s content hash to `request.content_hash` before accepting it [2](#0-1) .

Later, in `AttachmentsDownloader::run`, the `Done` branch drains `context.attachments` and, for each attachment, resolves state using `attachment.hash()` — the hash of the *received* bytes — rather than the original requested `content_hash`:
```
for attachment in context.attachments.drain() {
    let attachments_instances = network
        .atlasdb
        .find_all_attachment_instances(&attachment.hash())...
    ...
    context.attachments_batch.resolve_attachment(&attachment.hash())
}
``` [3](#0-2) 

Because there is no equality check `attachment.hash() == request.content_hash` anywhere in this pipeline, a malicious/unreliable peer selected via `AttachmentRequest::get_most_reliable_source` [4](#0-3)  can respond to the GET request with a `GetAttachmentResponse` containing arbitrary content. That content's own hash will never match the outstanding `AttachmentInstance.content_hash` recorded in `AttachmentsBatch.attachments_instances`, so `resolve_attachment(&attachment.hash())` cannot mark the originally targeted instance as resolved. The batch's `has_fully_succeed()` remains false, so it is re-queued with `bump_retry_count()` [5](#0-4)  and, once `retry_count >= connection_options.max_attachment_retry_count`, it is permanently dropped without ever being marked resolved.

### Impact Explanation
A single malicious peer that a victim node has already selected as an outbound sync peer (any unprivileged peer that can respond to `/v2/attachments/{content_hash}`) can poison every attachment request it services with unrelated content. This causes the victim to never resolve a legitimately committed `AttachmentInstance.content_hash` (e.g., a BNS name's zonefile hash committed on-chain), even though another honest peer may have the real data — because the malicious peer is the one selected via `get_most_reliable_source` for that batch. This results in permanent, incorrect "attachment unavailable" state for BNS resolution on the victim node, matching the High-severity category "attachment/BNS mismatch" described in the prompt. The bug is repeatable per-batch and does not require the attacker to have any secret or privileged role — only to be an outbound-connectable HTTP peer serving `/v2/attachments/...`.

### Likelihood Explanation
Preconditions: the victim node must include the attacker's URL among its outbound sync peers with a reliability score good enough to be chosen by `get_most_reliable_source` (an unprivileged peer can build up reliability simply by responding correctly to unrelated inventory/attachment requests, or the attacker could run its own peer and get selected due to lack of alternative sources for a given attachment). Cost to the attacker: run a P2P node with an HTTP server that returns any `GetAttachmentResponse` with mismatched content for a targeted content_hash. No secret, no privileged role, and no local access are required, satisfying the "unprivileged remote peer" threat model. The condition is deterministic and repeatable on each retry cycle.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after decoding the response, verify `Hash160::from_data(&response.attachment.content) == request.content_hash` (i.e., `response.attachment.hash() == request.content_hash`) before inserting into `self.attachments`; on mismatch, treat it as a failed request (`report.bump_failed_requests()`) and optionally mark the peer as faulty. Additionally, in the `Done` branch of `AttachmentsDownloader::run`, resolve/lookup using the originally requested `content_hash` associated with each accepted attachment rather than trusting `attachment.hash()` derived purely from peer-supplied bytes.

### Proof of Concept
Add a `stackslib::net::atlas` test that:
1. Seeds `AtlasDB` with one unresolved `AttachmentInstance` whose `content_hash = H` (from a fabricated confirmed name op).
2. Builds an `AttachmentsBatch`/`AttachmentsBatchStateContext` with a single mock peer URL.
3. Mocks the peer's HTTP conversation so that a GET to `/v2/attachments/{H}` returns `GetAttachmentResponse { attachment: Attachment { content: b"malicious bytes" } }`, whose `Hash160::from_data` is `H' != H`.
4. Drives `AttachmentsBatchStateMachine::try_proceed` through to `Done`, and calls `AttachmentsDownloader::run` repeatedly (or directly asserts on `context.attachments_batch.resolve_attachment(&H)` not being invoked).
5. Asserts that after `connection_options.max_attachment_retry_count` iterations, `AtlasDB::find_unresolved_attachment_instances()` still contains the instance for `H`, and it was never resolved to `H'`'s attachment — demonstrating that `extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) accepted content without hash verification and the `Done` branch (`download.rs:152-169`) resolved the wrong hash.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

#[derive(Debug, Clone, Eq, PartialEq)]
pub struct AttachmentRequest {
    pub content_hash: Hash160,
    pub sources: HashMap<UrlString, ReliabilityReport>,
    pub stacks_block_height: u64,
    pub canonical_stacks_tip_height: Option<u64>,
}

impl AttachmentRequest {
    pub fn get_most_reliable_source(&self) -> (&UrlString, &ReliabilityReport) {
        self.sources
            .iter()
            .max_by_key(|(_, v)| v.score())
            .expect("Atlas: trying to select an Url out of an empty set")
    }
}
