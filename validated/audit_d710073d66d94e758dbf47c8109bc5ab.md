### Title
Unbounded attacker-controlled offset/length in TVM precompile ABI array decoders causes uncaught RuntimeException - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign`/`BatchValidateSign` TVM precompiled contracts decode ABI-encoded `bytes[]`/`bytes32[]` arrays from raw, attacker-controlled call data using helper methods that index into a `DataWord[]` array with offsets and lengths taken directly from the input, without validating that the resulting indices stay inside the array bounds.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` read a length field from `words[offset]` and then loop reading `words[offset + i + 1]` (and, for `extractBytesArray`, a second attacker-controlled `bytesOffset` derived the same way) directly from the decoded word array: [1](#0-0) 

Only `extractBytesArray` and `extractSigArray` guard the initial `offset` (`if (offset > words.length - 1) return new byte[0][];`), but neither of them, nor `extractBytes32Array`, bounds-check the per-item `words[offset + i + 1]` access against `words.length`, and `len` itself is taken unchecked from attacker data (`words[offset].intValueSafe()`), so a crafted `len` can cause `new byte[len][]` to overflow memory or the subsequent indexed reads to run past the actual decoded word array — the same class of bug as UPX's `adjABS`, where an offset taken from untrusted input is used to index a buffer without validating it stays in range.

The codebase's own test suite documents that this decode path is unprotected: a too-short/malformed call to the multi-sign precompile "raises inside the decoder" because "this precompile has no outer catch", which the test explicitly asserts is the accepted (pre-activation) behavior: [2](#0-1) 

This decode logic is reached whenever any account calls (or a deployed contract internally calls, via `STATICCALL`/`CALL`) the `ValidateMultiSign` or `BatchValidateSign` precompiled contract addresses with a crafted ABI payload — i.e., directly from a broadcast transaction's TVM execution, with no special privilege required.

### Impact Explanation
Because the decoders have "no outer catch" (per the project's own test comments), a malformed/crafted `bytes[]`/`bytes32[]` array offset in the multi-sign validation call data can throw an uncaught `ArrayIndexOutOfBoundsException`, `NegativeArraySizeException`, or `OutOfMemoryError` during transaction execution. If this exception is not caught by an outer layer of the TVM/`Program` call stack when the transaction is later re-applied deterministically during block application, it risks inconsistent handling across nodes (some catching generic exceptions differently) or an uncaught exception propagating out of block processing, i.e., a node crash/halt condition rather than a normal "reverted transaction". This matches the CVE class (invalid/unchecked offset into a buffer sourced from untrusted, attacker-crafted input) even though the underlying language (Java, memory-safe) turns "invalid memory address reference" into an uncaught runtime exception instead of memory corruption.

### Likelihood Explanation
Any unprivileged account can trigger this by deploying a trivial contract that calls the `ValidateMultiSign`/`BatchValidateSign` precompile address with crafted call data (arbitrary large `len`/offset fields in the ABI-encoded `bytes[]`/`bytes32[]` sections), or by directly constructing a transaction whose TVM bytecode issues such a call. No special permissions, staking, or witness/SR status is required — this is reachable from a single signed transaction.

### Recommendation
Add explicit bounds checks in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` validating that `len` and every computed index (`offset + i + 1`, `bytesOffset + offset + 2`, etc.) stay within `words.length` before indexing, returning an empty/failure result (consistent with the existing `offset > words.length - 1` guard pattern) instead of allowing unchecked array access, and wrap the precompile decode/execute path with a defensive catch that converts unexpected `RuntimeException`s into a normal "execution failed" result rather than letting them propagate uncaught through block application.

### Proof of Concept
1. Craft a transaction that calls a contract invoking the `ValidateMultiSign` precompiled contract (address used by `validatemultisign`) with ABI-encoded `signatures` (`bytes[]`) whose length word or inner offset word is set to a very large value (e.g., close to `Integer.MAX_VALUE`) while the actual call data is short.
2. When `extractSigArray`/`extractBytesArray` executes, `len` from `words[offset].intValueSafe()` drives `new byte[len][]`, and/or the loop computes `words[offset + i + 1]` past the end of the decoded `words` array.
3. Per the test module's own documentation (`ValidateMultiSignContractTest.testTip854PreActivationNoOp`), this raises an uncaught `RuntimeException` inside the decoder because there is no outer catch, as opposed to a clean `Pair.of(false, ...)` failure result. [3](#0-2)

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }
