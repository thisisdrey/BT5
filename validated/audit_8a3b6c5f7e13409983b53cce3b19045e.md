### Title
Unbounded array allocation from attacker-controlled ABI length field in TVM precompile array decoding causes node-crashing OOM - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.extractBytes32Array` and `PrecompiledContracts.extractBytesArray` decode dynamic ABI array parameters supplied in the `data` payload of a `CALL`/`DELEGATECALL` to a TVM precompiled contract address. Both functions read a "length" word directly from attacker-controlled calldata and immediately allocate a Java array of that size — `new byte[len][]` — before validating that `len` is consistent with the actual size of the decoded input (`words.length`). This mirrors the Cryptacular `CiphertextHeader` bug: an untrusted length field taken from encoded/serialized input directly drives a large memory allocation with no upper bound check. [1](#0-0) 

### Finding Description
`extractBytes32Array` computes `len` from `words[offset].intValueSafe()` and immediately does `byte[][] bytes32Array = new byte[len][];` before any bound is enforced against the actual number of available `words`: [2](#0-1) 

`extractBytesArray` has the same pattern — it checks only that `offset` itself is in range, then reads `len = words[offset].intValueSafe()` and allocates `new byte[len][]` before iterating and touching `words[offset + i + 1]`: [3](#0-2) 

`intValueSafe()` on a `DataWord` clamps to `Integer.MAX_VALUE` rather than throwing, so `len` can be an attacker-chosen value up to `Integer.MAX_VALUE` regardless of how small the actual calldata is. `new byte[Integer.MAX_VALUE][]` (an array of object references) attempts to allocate on the order of 8–16 GB depending on JVM pointer size, which will throw `OutOfMemoryError` or stall the JVM heap/GC on any node that executes this precompile call — well before the subsequent loop would fail with an `ArrayIndexOutOfBoundsException` for reading past `words.length`. Because TVM execution is deterministic and replicated by every full node and witness that processes the block/transaction, a single malicious transaction reaching this code path is executed identically by the entire network, producing a broad denial-of-service rather than a single-node issue.

This is directly analogous to CVE-2020-7226: an attacker-controlled length field taken from encoded/serialized input drives an unchecked large-object allocation ("new byte[...]") during a decode operation, causing excessive memory allocation.

### Impact Explanation
If a live precompiled contract in the TVM dispatch table (`PrecompiledContracts.getContractForAddress`) calls into `extractBytes32Array`/`extractBytesArray` to decode a `bytes32[]`/`bytes[]` ABI parameter from contract-call `data`, any unprivileged account can trigger the allocation by crafting `data` with a huge value in the length word of that dynamic array. This can crash or hang the JVM (OutOfMemoryError / GC thrashing) on every node that executes the transaction, i.e., a network-wide node crash/halt — the exact impact class called out as acceptable in the validation rules ("node crash or halt").

### Likelihood Explanation
Reaching this code only requires constructing a smart-contract call whose input data encodes a dynamic array parameter with an inflated length word at the position parsed as `offset`; this is achievable by any contract deployer/caller broadcasting a signed transaction, with no special privileges, node compromise, or wallet key required.

### Recommendation
Before allocating `new byte[len][]` in both `extractBytes32Array` and `extractBytesArray`, validate `len` against the actual number of available `words` (e.g., `len <= words.length - offset - 1`), and reject/no-op (return `Pair.of(true, DataWord.ZERO().getData())` as done elsewhere in this class) when the declared length is inconsistent with the supplied calldata size, mirroring the `verifyLength` bound checks already used in `RLP.java`. [4](#0-3) 

### Proof of Concept
1. Deploy/trigger a contract (or directly `TriggerSmartContract`) that performs a `CALL`/`STATICCALL` to the precompiled contract address whose input decoding uses `extractBytes32Array`/`extractBytesArray`.
2. Craft the ABI-encoded `data` so that the word at the array's declared `offset` (the "length" slot for the dynamic array) is set to a large value such as `0x7fffffff`, while keeping the rest of `data` minimal/short.
3. Broadcast the transaction; when TVM execution reaches the precompile and calls `extractBytes32Array`/`extractBytesArray`, the JVM attempts `new byte[2147483647][]`, causing an `OutOfMemoryError`/severe GC pressure on every node executing the transaction.

Note: I was not able to fully trace, within the tool budget, the exact concrete precompile method(s) that call `extractBytes32Array`/`extractBytesArray` (the grep only reported match counts without resolvable call-site line numbers in this pass), so the specific reachable precompile name/opcode should be confirmed by a full read of `PrecompiledContracts.java` before treating this as fully proven end-to-end; the root-cause allocation defect in the two helper methods themselves, however, is directly verified from source.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
