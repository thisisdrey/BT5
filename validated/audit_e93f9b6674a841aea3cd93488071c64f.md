### Title
Malicious peer's AttachmentRequest response is inserted into AtlasDB regardless of requested content_hash - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` inserts any decoded `response.attachment` into `context.attachments` without verifying that its `Hash160` matches the `AttachmentRequest.content_hash` that was actually queued. `AttachmentsDownloader::run` then unconditionally calls `atlasdb.insert_instantiated_attachment` for every entry drained from `context.attachments`, so a peer can return arbitrary attachment blobs (up to the size cap) unrelated to any tracked/missing content hash and have them permanently persisted.

### Finding Description
In `stackslib/src/net/atlas/download.rs`, `get_prioritized_attachments_requests` builds `AttachmentRequest { content_hash, sources, ... }` entries for content hashes that are actually missing/tracked in `attachments_batch.attachments_instances`. However, when the response comes back in `extend_with_attachments`:

```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
``` [1](#0-0) 

there is no check that `response.attachment.hash() == request.content_hash`. The server-side handler (`RPCGetAttachmentRequestHandler` / `decode_atlas_get_attachment` in `stackslib/src/net/api/getattachment.rs`) simply decodes whatever hex-encoded bytes the peer sends into an `Attachment` without any binding to the request path's hash [2](#0-1) , so a malicious peer answering an `AttachmentRequest` can supply any byte blob it wants (bounded only by the max attachment size and HTTP payload caps), with a hash of the attacker's choosing that has no relation to the requested `content_hash`.

Then, in `AttachmentsDownloader::run`, once the FSM reaches `Done`:
```
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;
    ...
}
``` [3](#0-2) 

`insert_instantiated_attachment` is called unconditionally for every attachment in the set, regardless of whether `find_all_attachment_instances` found any matching instance in `attachments_batch.attachments_instances`. There is no filter comparing `attachment.hash()` against the batch's set of tracked missing content hashes before persisting. Because up to `connection_options.max_inflight_attachments` requests can be in flight concurrently per batch step, and this repeats every retry cycle, a single malicious peer (or a set of colluding peers) can flood the node with distinct payloads that get permanently written into the `attachments` table in `AtlasDB`, none of which correspond to any consensus-committed `AttachmentInstance`.

### Impact Explanation
Every response, whether or not it corresponds to a tracked/missing attachment, becomes a permanent row in the node's AtlasDB `attachments` table via `insert_instantiated_attachment`, consuming disk space with data that has no relationship to any queued or committed `AttachmentInstance`. This is a storage-exhaustion vector unconnected to consensus commitments: an attacker controlling one or more peers that the victim syncs Atlas attachments from can repeatedly answer legitimate `AttachmentRequest`s with distinct garbage blobs and have the node store them indefinitely (subject only to `evict_expired_uninstantiated_attachments`, which only targets *uninstantiated* attachments, not the already-instantiated rows inserted here). This matches "attachment/BNS mismatch" / storage-exhaustion class of High impact since it corrupts the correspondence between stored attachment data and any canonical commitment.

### Likelihood Explanation
The attacker only needs to be one of the outbound sync peers the node queries for attachments (an unprivileged, remotely reachable P2P/RPC peer role) and answer `GET /v2/attachments/:hash` requests with arbitrary hex payloads under the `attachments_max_size` cap. No secret, signature, or privileged role is required — the attacker simply serves content that decodes successfully as JSON/hex, which is trivial. The attack is fully repeatable across every batch retry and across `max_inflight_attachments` concurrent requests per cycle, so the cost to the attacker is minimal relative to the persistent storage cost imposed on the victim.

### Recommendation
In `extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; discard and treat as a failed/faulty response otherwise. Additionally, in `AttachmentsDownloader::run`, only call `insert_instantiated_attachment` for attachments whose hash matches an entry in `context.attachments_batch.attachments_instances` (i.e., only when `attachments_instances` returned by `find_all_attachment_instances` is non-empty), discarding/logging any unmatched attachment instead of persisting it.

### Proof of Concept
Rust test in `stackslib/src/net/atlas/download.rs` test module:
1. Construct an `AttachmentsBatch` tracking one missing `content_hash` H1 for a contract/index_block_hash.
2. Build `AttachmentsBatchStateContext` and manually drive to `AttachmentsBatchStateMachine::Done` with `context.attachments` populated by calling `extend_with_attachments` on a `BatchedRequestsResult` where the `AttachmentRequest.content_hash == H1` but the mocked `StacksHttpResponse` decodes to an `Attachment` with content whose `Hash160` is H2 ≠ H1 (attacker-controlled payload).
3. Run `AttachmentsDownloader::run` (or directly exercise the `Done` branch logic) against a fresh in-memory `AtlasDB`.
4. Assert that `atlasdb.find_attachment(&H2)` returns `Some(..)` (i.e., a row was inserted for a hash that was never in `attachments_batch.attachments_instances`), demonstrating that `|context.attachments|` after `Done` is not filtered to only hashes tracked as missing, and that unrelated attacker-supplied blobs are persisted permanently in `AtlasDB`.
