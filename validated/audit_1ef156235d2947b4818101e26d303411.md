### Title
Unauthenticated `RecvError` packets can force-close any tunnel lacking a validated direct remote address - ([File: outside.go])

### Summary
`handleRecvError` in `outside.go` is reached directly from `readOutsidePackets` for the unencrypted `header.RecvError` message type, before any certificate/handshake authentication is performed. Its only defense against a forged teardown is comparing the packet's source address against the target `HostInfo`'s currently known remote address — but that check is skipped entirely whenever the `HostInfo` has no validated remote address set (e.g. relay-only tunnels, or tunnels that haven't yet completed roaming/remote confirmation). This mirrors the reported `SetDenylist` bug class: a state-mutating operation that should require the caller to be the legitimate party but instead has no effective access control in a common code path, letting an unauthenticated third party disrupt service for arbitrary victims.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` before any hostinfo/cert validation: [1](#0-0) 

`handleRecvError` then looks up the target purely by the attacker-suppliable `RemoteIndex` and only rejects the request if the hostinfo already has a *valid* remote address that differs from the packet's source: [2](#0-1) 

The critical logic is:
```go
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    // "Someone spoofing recv_errors?" — rejected
    return
}
f.closeTunnel(hostinfo)
```
Because the condition is a logical AND gated on `hr.IsValid()`, if the `HostInfo` does not yet have (or never has) a confirmed direct remote UDP address — which is normal for relay-mediated tunnels or hostinfos still resolving their roamed address — the spoof check is bypassed unconditionally and `closeTunnel` executes for *any* sender that supplies the correct `RemoteIndex`. `RemoteIndex` is carried in cleartext in every packet header on the wire (`header.H.RemoteIndex`), so it is observable by anyone who can see any traffic to/from the victim (a passive on-path observer, a shared network segment, or a compromised intermediate router), and there is no requirement that the sender possess a CA-signed certificate or have completed any handshake — `RecvError` is handled entirely outside the encrypted/authenticated packet path (contrast with `header.Message`/`header.LightHouse`/`header.Control`, which are only processed after `hostinfo.ConnectionState.Decrypt` succeeds).

This is the same bug class as the reported Solana `SetDenylist` issue: a function that mutates shared state affecting other parties' connectivity (there: adding to a `deny_list` used by `quote`; here: tearing down a peer's tunnel via `closeTunnel`) lacks a binding check tying the caller to the entity it is allowed to act on behalf of.

### Impact Explanation
An attacker with no valid Nebula certificate can force-close established tunnels for any host whose `HostInfo` lacks a currently-valid direct remote (a routine state for relay-terminated tunnels, per `relay_manager.go`/`hostmap.go`, and momentarily during roaming). Repeated forged `RecvError` packets provide an unauthenticated remote denial-of-service against victim tunnels, forcing continuous re-handshakes and breaking connectivity for legitimate CA-signed peers — directly analogous to the executor's `SetDenylist` letting an attacker deny service to arbitrary `sender`s.

### Likelihood Explanation
Exploitation requires only: (1) knowledge of a victim's `RemoteIndex`, obtainable by observing plaintext headers on the wire (no decryption needed) or via traffic analysis on shared/adversary-controlled network paths, and (2) the targeted `HostInfo` currently lacking a validated remote (a state that legitimately and routinely occurs for relay-type tunnels and during roaming windows). No handshake or certificate is required at all, making this reachable by a pure network-level attacker. Rate limiting exists only via `acceptRecvErrorConfig.ShouldRecvError(addr)`, which throttles by source address, not by proof of relationship to the target tunnel, so an attacker can still probe/attack using multiple source addresses or within the rate limit window.

### Recommendation
Do not allow `closeTunnel` to be triggered by `RecvError` when the hostinfo lacks a confirmed remote address; instead require corroborating authenticated evidence (e.g., only accept `RecvError` after confirming the source address against *any* address the hostinfo has ever validated, or require an encrypted/authenticated equivalent). At minimum, treat "no validated remote" as the more restrictive case (deny) rather than the permissive case (allow), i.e. invert the current logic so absence of a validated remote does not bypass the anti-spoof check.

### Proof of Concept
1. Establish (or observe) a Nebula tunnel where the target `HostInfo` is relay-terminated or otherwise has no direct `CurrentRemote` set (`hr.IsValid() == false`), e.g. per the relay flows exercised in `e2e/handshakes_test.go`'s `TestReestablishRelays`/`TestCrossStackRelaysWork`.
2. Passively observe any packet exchanged with the victim to learn its `RemoteIndex` from the plaintext `header.H`.
3. Craft and send a bare `header.RecvError` packet (`header.Encode(..., header.RecvError, 0, victimRemoteIndex, 0)`) from an attacker-controlled UDP source (no certificate, no handshake) to the victim.
4. `handleRecvError` finds the hostinfo via `QueryReverseIndex`, finds `hr.IsValid() == false`, skips the spoof check, and calls `f.closeTunnel(hostinfo)` plus `hm.DeleteHostInfo`, tearing down the victim's tunnel without any authentication.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
