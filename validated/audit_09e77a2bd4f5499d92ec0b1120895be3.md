## Finding

### Title
Unbounded, unthrottled repository clone via `CreateRepositoryFromURL` allows bandwidth/disk-saturation DoS - ([File: internal/gitaly/service/repository/create_repository_from_url.go])

### Summary
`CreateRepositoryFromURL` lets a caller (e.g. GitLab's "import project by URL" feature, invocable by any user with project-creation rights) direct Gitaly to run `git clone` against an arbitrary, caller-supplied URL, with no size limit, no bandwidth limit, and — unlike the sibling `FetchRemote` RPC — no built-in timeout field at all. The Nextcloud report describes exactly this bug class: a server-side fetch of an attacker-controlled resource that is not bounded by size, only by an optional/loose time control, letting an attacker point it at a very large or very fast resource to saturate the server's bandwidth and disk for the full transfer duration.

### Finding Description
`CreateRepositoryFromURL` builds and runs a `git clone` command directly from `req.GetUrl()`, `req.GetHttpAuthorizationHeader()` and `req.GetMirror()`: [1](#0-0) 

The command is executed with the RPC's incoming `ctx` and no additional deadline is derived from any request field — there is simply no `timeout` field in `CreateRepositoryFromURLRequest`: [2](#0-1) 

Compare this with `FetchRemote`, which at least exposes an explicit `timeout` field that the server uses to bound the fetch via `context.WithTimeout`: [3](#0-2) 

Neither RPC imposes any limit on the amount of data transferred — there is no `RepositorySizeLimit`, byte cap, or streaming rate limit enforced anywhere on the `git clone`/`git fetch` child process; grep across the codebase for repository size limits and disk-quota enforcement in the RPC layer turns up nothing relevant to the fetch path. The clone is a plain child-process invocation writing directly to disk and consuming as much network bandwidth as the remote endpoint can serve for the full duration of the transfer, exactly analogous to the Nextcloud Talk reference-fetch issue where "the resource is still fetched for the entire duration" with no size ceiling.

Because `CreateRepositoryFromURL`'s URL is fully attacker-controlled at the API level (it is meant to import from arbitrary remote Git hosts) and has no `timeout` field for the caller to bound it server-side, a caller that omits or sets a very long gRPC deadline can force Gitaly to pull an arbitrarily large object (e.g., a repository hosting huge blobs on a high-bandwidth host) at full network speed for as long as the deadline allows, filling disk and consuming outbound/inbound bandwidth just as in the disclosed report.

### Impact Explanation
An ordinary user who can trigger a "create/import project from URL" action can point Gitaly at a large, high-throughput remote and force it to download the full content at line rate, saturating the Gitaly node's bandwidth and disk I/O and degrading or denying service to co-located repositories/storage shards — a resource-consumption DoS matching the reported bug class (uncontrolled resource consumption / CVE-2023-28644 analog).

### Likelihood Explanation
Likelihood is moderate-to-high in deployments where end users (not just admins) can initiate repository imports by URL, since `CreateRepositoryFromURL` requires only a valid `Repository` target and a URL — no other privileged input is needed, and there is no request-level knob to cap size or duration.

### Recommendation
- Add an explicit, mandatory `timeout` (and ideally a byte-size cap enforced via a size-limited reader/`--depth`/partial clone or streamed byte accounting) to `CreateRepositoryFromURLRequest`, mirroring `FetchRemoteRequest.timeout`, and enforce it server-side via `context.WithTimeout` as done in `fetch_remote.go`.
- Enforce a configurable maximum transfer size for clones/fetches originating from externally supplied URLs (e.g., abort the `git clone` process if bytes received exceed a threshold), independent of the caller-supplied gRPC deadline.
- Consider rate-limiting or throttling clone bandwidth per RPC/tenant to avoid a single import saturating shared network/disk resources.

### Proof of Concept
1. As an authenticated but otherwise unprivileged user able to create a repository/project via "import by URL", call `CreateRepositoryFromURL` with `Url` pointing to a very large, high-bandwidth file served over Git/HTTP (e.g., a giant blob repo hosted on a fast CDN) and no/very long client-side deadline.
2. Observe that Gitaly's `git clone` subprocess (`cloneFromURLCommand`) streams the entire resource to disk at full network speed with no size cap and no server-imposed timeout, consuming outbound bandwidth and disk space for the whole transfer — reproducible repeatedly to sustain saturation, analogous to the original Nextcloud Talk reference-fetch report.

message CreateRepositoryFromURLRequest {
  // repository represents where the repo should be created. The storage_name and
  // relative_path attributes must be provided.
  Repository repository = 1 [(target_repository)=true];
  // url is the URL of the existing Git repository.
  string url = 2;
  // http_authorization_header is the HTTP header which can be added to
  // the request in order to authenticate against the repository.
  string http_authorization_header = 4;
  // mirror defines whether to clone with `--mirror` flag or `--bare`. The default
  // value `false` will cause us to use `--bare`, which results in a clone that
  // contains only branches (`refs/heads/`) and tags (`refs/tags/`) of the remote
  // repository. If set to `true`, create a complete mirror-clone which maps all
  // remote references into the local repository.
  bool mirror = 5;
  // resolved_address holds the resolved IP address of the remote_url. This is
  // used to avoid DNS rebinding by mapping the url to the resolved address.
  // Only IPv4 dotted decimal ("192.0.2.1"), IPv6 ("2001:db8::68"), or IPv4-mapped
  // IPv6 ("::ffff:192.0.2.1") forms are supported.
  // Works with HTTP/HTTPS/Git/SSH protocols.
  // Optional.
  string resolved_address = 6;

  // HttpHost has been removed in favor of ResolvedAddress.
  reserved 3;
  reserved "http_host";
}
