## Title
Any per-voter vote error at PREPARING/PREPARED phase releases the whole repository write-lock, breaking serialized-write protection - (File: `internal/praefect/transactions/manager.go`)

### Summary
`Manager.voteTransaction` acquires a repository-wide PostgreSQL write lock during the `PREPARING_PHASE` of `VoteTransaction` and defers `unlockRepoForTransaction`, which decides whether to release that lock based solely on whether `transaction.vote()` returned *any* error. This mirrors the RootBridgeAgent flaw: a "generic" signal (non-nil error / `initialGas != 0`) is treated as proof of a specific condition ("the whole transaction failed" / "anyExecute already ran the full flow") that does not always hold, so shared state meant to persist across a multi-step protocol gets torn down at the wrong time and corrupts the next caller's view of that state.

### Finding Description
`voteTransaction` in [1](#0-0)  locks the repo, defers the unlock decision, and calls `transaction.vote`. The unlock decision is made in `unlockRepoForTransaction`: [2](#0-1) 

For `PREPARING_PHASE`/`PREPARED_PHASE`, `shouldUnlock = returnedErr != nil` — i.e. *any* error returned by `transaction.vote()` at these phases releases the exclusive, cluster-wide, PostgreSQL-backed repository write lock (`repoLocks`), which — per `doc/serialized_writes.md` — exists specifically to serialize concurrent writers and prevent a ref-locking deadlock across the replica set.

But `transaction.vote()` → `subtransaction.vote()` can return an error for reasons that do **not** mean the transaction as a whole failed or should give up the lock — most notably: [3](#0-2) 

`"node already cast a vote: %q"` is returned whenever the same voter calls `VoteTransaction` twice for the same phase (e.g. a client-side gRPC retry after a transient network blip where the first call actually succeeded server-side, or any duplicate delivery of the same vote). This is exactly analogous to the `RootBridgeAgent` bug's flawed assumption: the code assumes "vote() returned an error at PREPARING/PREPARED ⇒ the transaction has failed and it's safe/necessary to release the shared lock," but in the duplicate-vote case the transaction may still be legitimately pending — other voters may still be waiting for quorum (`collectVotes` still blocked, as shown in `TestPraefectWriteSerialization_ContextCancellationReleasesLock`, `internal/praefect/transaction_write_serialization_test.go:274-369`). Releasing the lock at that point immediately hands the write-serialization slot to the next writer for the same repository while the original transaction is still in flight, exactly reproducing the class of race/deadlock the serialization mechanism was introduced to eliminate.

Other non-fatal errors reachable from `transaction.vote` at this stage — `"invalid node for transaction"`, `"invalid transaction state"`, and errors from `getPendingNodeSubtransactions`/`createSubtransaction` — hit the same overly broad `returnedErr != nil` branch and trigger the same premature unlock.

### Impact Explanation
Premature release of the repository write lock defeats the serialization guarantee documented in `doc/serialized_writes.md`, whose entire purpose is to prevent multiple concurrent writers from taking on-disk ref locks in inconsistent orders across nodes (a deadlock scenario). A single retried/duplicated `VoteTransaction` call — something that can happen during ordinary operation under network hiccups, without any malicious actor — can cause the lock meant to gate an in-progress push/write to be released early, letting a second, unrelated write transaction on the same repository start concurrently. This reintroduces the exact ref-lock-ordering deadlock/race the feature exists to prevent, i.e. a correctness and availability regression on the write path reachable by ordinary pushes.

### Likelihood Explanation
This does not require a privileged actor or a malicious peer: gRPC clients commonly retry idempotent-looking calls on ambiguous failures (timeouts, connection resets), and `VoteTransaction` is called once per phase per node from the Gitaly replica's reference-transaction hook during every push. Any such retry that lands after the original vote was already recorded server-side triggers `"node already cast a vote"`, which is misclassified as a fatal transaction error and results in early lock release. The condition is a natural consequence of standard network retry/duplicate-delivery behavior, not a contrived edge case.

### Recommendation
Distinguish "the vote could not be recorded because of a benign duplicate/already-processed condition" from "the transaction has actually failed/canceled/stopped." `unlockRepoForTransaction` should not treat every non-nil error uniformly; only release the lock on errors that genuinely indicate the transaction cannot proceed (`ErrTransactionCanceled`, `ErrTransactionStopped`, `ErrTransactionFailed`, or the initial lock-acquisition failure itself), and leave the lock held (skip cleanup) when the failure is a duplicate-vote / already-recorded condition for an otherwise still-pending transaction, deferring the unlock decision to the outcome that legitimately concludes the transaction (commit, cancellation, or stop).

### Proof of Concept
1. Client-side retry logic (or a network blip causing an ambiguous RPC outcome) causes node `N` to call `VoteTransaction(transactionID, phase=PREPARING_PHASE, ...)` twice for the same transaction, where the first call already succeeded and is recorded in `votersByNode[N].vote`.
2. The second call reaches `subtransaction.vote` and returns `"node already cast a vote: %q"` at [4](#0-3) .
3. `voteTransaction`'s deferred call to `unlockRepoForTransaction` sees `returnedErr != nil` at `PREPARING_PHASE` and calls `releaseRepoLockOnPhase`, releasing the cluster-wide write lock at [2](#0-1)  even though the transaction is still waiting on other voters to reach quorum.
4. A second, concurrent write transaction for the same repository can now acquire the write lock via `lockRepoForTransaction` and proceed while the first transaction is still active, defeating the serialization the mechanism (`internal/praefect/transactions/manager.go:272-306`, described in `doc/serialized_writes.md`) was built to guarantee.

func (mgr *Manager) voteTransaction(ctx context.Context, transactionID uint64, storageName, repoRelativePath, node string,
	phase gitalypb.VoteTransactionRequest_Phase, vote voting.Vote,
) (returnedErr error) {
	mgr.lock.Lock()
	transaction, ok := mgr.transactions[transactionID]
	mgr.lock.Unlock()

	if !ok {
		return fmt.Errorf("%w: %d", ErrNotFound, transactionID)
	}

	err := mgr.lockRepoForTransaction(ctx, transactionID, storageName, repoRelativePath, phase)
	if err != nil {
		return fmt.Errorf("lock transaction %d: %w", transactionID, err)
	}
	defer func() {
		mgr.unlockRepoForTransaction(ctx, transactionID, returnedErr, phase)
	}()
	if err := transaction.vote(ctx, node, vote); err != nil {
		return err
	}

	return nil
}

func (mgr *Manager) unlockRepoForTransaction(ctx context.Context, transactionID uint64, returnedErr error, phase gitalypb.VoteTransactionRequest_Phase) {
	if featureflag.PraefectSerializedWrite.IsDisabled(ctx) {
		return
	}

	// Decide whether this call releases the write lock. The lock spans all the
	// phases of one transaction and is only released when either the vote
	// failed (so callers can't advance to the next phase) or the committed
	// phase completes. Phases outside the reference transaction hook
	// lifecycle (e.g. SYNCHRONIZED_PHASE) never acquired a lock.
	var shouldUnlock bool
	switch phase {
	case gitalypb.VoteTransactionRequest_PREPARING_PHASE,
		gitalypb.VoteTransactionRequest_PREPARED_PHASE:
		shouldUnlock = returnedErr != nil
	case gitalypb.VoteTransactionRequest_COMMITTED_PHASE:
		shouldUnlock = true
	default:
		return
	}

	if !shouldUnlock {
		return
	}

	mgr.releaseRepoLockOnPhase(transactionID, phase.String())
}

func (t *subtransaction) vote(node string, vote voting.Vote) error {
	t.lock.Lock()
	defer t.lock.Unlock()

	// Cast our vote. In case the node doesn't exist or has already cast a
	// vote, we need to abort.
	voter, ok := t.votersByNode[node]
	if !ok {
		return fmt.Errorf("invalid node for transaction: %q", node)
	}
	if voter.vote != nil {
		return fmt.Errorf("node already cast a vote: %q", node)
	}
