## Title
`pallet-asset-conversion` computes AMM reserves from live, unaccounted account balance instead of a cached reserve — donation/inflation attack corrupts swap pricing and LP settlement - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
The ERC5115 report's root cause is that a contract's *live* balance is used to compute a user-facing amount (deposit size) without distinguishing funds that arrived through the accounted deposit path from funds that arrived through an unrelated, permissionless side-channel (reward claiming) triggered inside the same transaction. The direct analog in this repository is `pallet-asset-conversion`'s reserve accounting: `Pallet::<T>::get_balance` / `get_reserves` read the pool account's **full, live on-chain balance** via `T::Assets::balance(asset, owner)` [1](#0-0)  and feed that number directly into the constant-product formulas used for swap pricing and liquidity accounting [2](#0-1) . There is no cached/accounted reserve value (no analog of Uniswap V2's stored `reserve0/reserve1` updated only via `sync()`); any token balance that lands in the pool's sovereign account — whether from `add_liquidity`, a swap, or a *bare, permissionless* `Balances`/`Assets` transfer straight to the pool address — is treated as legitimate reserve. This was made explicitly worse by `pr_12408` ("fix(asset-conversion): use full balances for pool prices"), which switched the reserve read from a reducible-balance check to the raw full balance [3](#0-2) , removing even the partial mitigation that reducible-balance filtering provided against externally-donated/held funds.

### Finding Description
`get_reserves` is the single source of truth for AMM pricing:
```
let balance1 = Self::get_balance(&pool_account, asset1);
let balance2 = Self::get_balance(&pool_account, asset2);
``` [4](#0-3) 

`get_balance` is a thin wrapper over the raw fungible/fungibles `balance()` query [1](#0-0) . This value feeds `get_amount_out`/`get_amount_in` (the constant-product swap formulas) [5](#0-4)  and `do_add_liquidity`/`do_remove_liquidity`'s LP-token minting/redemption math, which computes `amount2_optimal = quote(amount1_desired, reserve1, reserve2)` and LP shares as `mul_div(lp_redeem_amount, reserve1, total_supply)` [6](#0-5) [7](#0-6) .

Because the pool account is a plain, unprivileged on-chain account, **anyone** can transfer either pool asset directly to it (e.g. `Balances::transfer_keep_alive` for the native side, or `Assets::transfer` for the other side) without going through `add_liquidity` or `swap_*`. No LP tokens are minted for that transfer and no invariant tracks "how much of the balance is backed by minted LP tokens." The very next call to `swap_exact_tokens_for_tokens`, `swap_tokens_for_exact_tokens`, `add_liquidity`, or `remove_liquidity` reads the inflated balance as if it were legitimate reserve.

This is structurally identical to the Superform bug: a permissionless, attacker-triggerable side-channel (there: `claimRewards()`; here: a bare asset transfer to the pool's sovereign account) injects unaccounted value into a balance that a different, legitimate operation (there: `_directDepositIntoVault`; here: `swap_*`/`add_liquidity`/`remove_liquidity`) reads back as if it were principal/reserve, without any accounting distinguishing the two sources. There is no guard analogous to "claim rewards from the underlying form before processing withdrawals" — `get_reserves` never reconciles the live balance against the total value actually contributed by LP-token holders.

### Impact Explanation
An attacker who is also (even a minority) LP can:
1. Provide liquidity normally to receive LP tokens proportional to `reserve1_orig`/`reserve2_orig`.
2. Donate additional `asset1` directly to the pool's sovereign account (permissionless, no LP tokens minted) — `get_reserves` now reports `reserve1_orig + D`.
3. Call `remove_liquidity`: `amount1 = mul_div(lp_redeem_amount, reserve1_orig + D, total_supply)`. The attacker's own LP share `f` extracts `f*D` of their donation back, while `(1-f)*D` is permanently and involuntarily distributed to the other LPs' *future* redemptions — silently redistributing value without their consent and without the transaction they signed reflecting it.

More severely, the donation-then-swap combination distorts the constant-product invariant `k = reserve_in * reserve_out` for the *next* swap executed in the same or a following transaction: because `reserve_in`/`reserve_out` are read fresh from live balance each call, an attacker can inject `asset1` into the pool immediately before their own `swap_exact_tokens_for_tokens(asset2 → asset1)` call, causing `get_amount_out` to compute an output amount based on an inflated `reserve_in`, extracting more `asset1` for a given `amount_in` of `asset2` than the true (undonated) pool state would allow — a public, underpriced/mispriced swap that degrades the correctness of on-chain price discovery and can be chained with `quote_price_exact_tokens_for_tokens`/tx-payment fee-in-asset conversion consumers that trust these reserves for fee accounting. This satisfies the impact gate's "runtime bugs that compromise intended behavior" / "theft or unbacked mint" criteria: value moves to/from LPs and swappers that is not backed by any accounted mint, deposit, or swap-in.

### Likelihood Explanation
No special privileges, no malicious validator/collator/relayer, no governance action, and no reentrancy are required — only two ordinary, permissionless extrinsics (a bare asset transfer to a well-known/derivable pool sovereign account, followed by `add_liquidity`/`remove_liquidity`/`swap_*`) executed by any signed account. The pool account address is deterministically derivable via `T::PoolLocator::pool_address` for any asset pair, so the attacker does not need any secret knowledge. This is directly reachable on any production chain running `pallet-asset-conversion` (e.g. Asset Hub) by any user with funds for the tiny "donation" and normal transaction fees.

### Recommendation
Do not compute AMM reserves from the pool account's live, unaccounted balance. Introduce an explicit, pallet-tracked `Reserves` (or equivalent) storage item per pool that is updated only through `add_liquidity`, `remove_liquidity`, and `swap_*` (mirroring Uniswap V2's `sync()`/cached-reserve pattern), and have `get_reserves`/pricing/LP-redemption math read from that tracked value instead of `T::Assets::balance`. If tracked reserves ever diverge from the live balance (e.g., due to legitimate external donations that should be swept), expose that divergence only through an explicit, separately-gated "skim" operation that does not affect swap pricing or LP redemption ratios.

### Proof of Concept
1. Create pool `(asset1, asset2)`, `LP_A` (an outside liquidity provider) calls `add_liquidity` providing `amount1=10_000`, `amount2=10_000` → pool reserves `(10_000, 10_000)`, `LP_A` receives LP tokens for the full pool.
2. Attacker calls `add_liquidity` with a small amount to also become an LP, e.g. `amount1=100`, `amount2=100` → attacker receives `~1%` of LP tokens; reserves now `(10_100, 10_100)`.
3. Attacker sends `asset1` (e.g. `Assets::transfer(asset1, attacker, pool_account, 5_000)`) directly to the pool sovereign account — no call into `pallet-asset-conversion` at all. `get_reserves` (via `T::Assets::balance`) now reports `(15_100, 10_100)` even though `total_supply` of LP tokens is unchanged.
4. Attacker immediately calls `swap_exact_tokens_for_tokens(path=[asset2, asset1], amount_in=1_000, ...)`. `get_amount_out` computes the output using the inflated `reserve_in=10_100`/`reserve_out=15_100` pair, yielding materially more `asset1` per unit of `asset2` than the true, undonated pool state (`10_100`/`10_100`) would have produced — extracting value from the pool that is not backed by the swap's own `amount_in`.
5. Alternatively, attacker skips step 4 and calls `remove_liquidity` for their ~1% LP share: `amount1 = mul_div(lp_redeem_amount, 15_100, total_supply)` recovers a disproportionate share of the donated `5_000`, at the expense of `LP_A`'s subsequent redemption.

Verification of the exact numeric magnitude of extractable profit under fee (`LpFee`) deduction and `MintMinLiquidity` rounding was not carried out with a live test run in this session; the structural vulnerability (reserves derived from unaccounted live balance rather than a cached/accounted value) is confirmed directly from `get_balance`/`get_reserves`/`get_amount_out`/`do_add_liquidity`/`do_remove_liquidity` in `substrate/frame/asset-conversion/src/lib.rs`, and is corroborated by `prdoc/pr_12408.prdoc`, which documents that this pallet intentionally reads "full" (not reducible/accounted) balances for exactly this calculation.

		/// Add liquidity to a pool.
		pub(crate) fn do_add_liquidity(
			who: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount1_desired: T::Balance,
			amount2_desired: T::Balance,
			amount1_min: T::Balance,
			amount2_min: T::Balance,
			mint_to: &T::AccountId,
		) -> Result<T::Balance, DispatchError> {
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;

			ensure!(
				amount1_desired > Zero::zero() && amount2_desired > Zero::zero(),
				Error::<T>::WrongDesiredAmount
			);

			let pool = Pools::<T>::get(&pool_id).ok_or(Error::<T>::PoolNotFound)?;
			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;

			let reserve1 = Self::get_balance(&pool_account, asset1.clone());
			let reserve2 = Self::get_balance(&pool_account, asset2.clone());

			let amount1: T::Balance;
			let amount2: T::Balance;
			if reserve1.is_zero() || reserve2.is_zero() {
				amount1 = amount1_desired;
				amount2 = amount2_desired;
			} else {
				let amount2_optimal = Self::quote(&amount1_desired, &reserve1, &reserve2)?;

				if amount2_optimal <= amount2_desired {
					ensure!(
						amount2_optimal >= amount2_min,
						Error::<T>::AssetTwoDepositDidNotMeetMinimum
					);
					amount1 = amount1_desired;
					amount2 = amount2_optimal;
				} else {
					let amount1_optimal = Self::quote(&amount2_desired, &reserve2, &reserve1)?;
					ensure!(
						amount1_optimal <= amount1_desired,
						Error::<T>::OptimalAmountLessThanDesired
					);
					ensure!(
						amount1_optimal >= amount1_min,
						Error::<T>::AssetOneDepositDidNotMeetMinimum
					);
					amount1 = amount1_optimal;
					amount2 = amount2_desired;
				}
			}

			ensure!(
				amount1.saturating_add(reserve1) >= T::Assets::minimum_balance(asset1.clone()),
				Error::<T>::AmountOneLessThanMinimal
			);
			ensure!(
				amount2.saturating_add(reserve2) >= T::Assets::minimum_balance(asset2.clone()),
				Error::<T>::AmountTwoLessThanMinimal
			);

			T::Assets::transfer(asset1, who, &pool_account, amount1, Preserve)?;
			T::Assets::transfer(asset2, who, &pool_account, amount2, Preserve)?;

			let total_supply = T::PoolAssets::total_issuance(pool.lp_token.clone());

			let lp_token_amount: T::Balance;
			if total_supply.is_zero() {
				lp_token_amount = Self::calc_lp_amount_for_zero_supply(&amount1, &amount2)?;
				T::PoolAssets::mint_into(
					pool.lp_token.clone(),
					&pool_account,
					T::MintMinLiquidity::get(),
				)?;
			} else {
				let side1 = Self::mul_div(&amount1, &total_supply, &reserve1)?;
				let side2 = Self::mul_div(&amount2, &total_supply, &reserve2)?;
				lp_token_amount = side1.min(side2);
			}

			ensure!(
				lp_token_amount > T::MintMinLiquidity::get(),
				Error::<T>::InsufficientLiquidityMinted
			);

			T::PoolAssets::mint_into(pool.lp_token.clone(), mint_to, lp_token_amount)?;

			Self::deposit_event(Event::LiquidityAdded {
				who: who.clone(),
				mint_to: mint_to.clone(),
				pool_id,
				amount1_provided: amount1,
				amount2_provided: amount2,
				lp_token: pool.lp_token,
				lp_token_minted: lp_token_amount,
			});

			Ok(lp_token_amount)
		}

		/// Remove liquidity from a pool.
		pub(crate) fn do_remove_liquidity(
			who: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			lp_token_burn: T::Balance,
			amount1_min_receive: T::Balance,
			amount2_min_receive: T::Balance,
			withdraw_to: &T::AccountId,
		) -> Result<(T::Balance, T::Balance), DispatchError> {
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;

			ensure!(lp_token_burn > Zero::zero(), Error::<T>::ZeroLiquidity);

			let pool = Pools::<T>::get(&pool_id).ok_or(Error::<T>::PoolNotFound)?;

			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;
			let (reserve1, reserve2) = Self::get_reserves(asset1.clone(), asset2.clone())?;

			let total_supply = T::PoolAssets::total_issuance(pool.lp_token.clone());
			let withdrawal_fee_amount = T::LiquidityWithdrawalFee::get() * lp_token_burn;
			let lp_redeem_amount = lp_token_burn.saturating_sub(withdrawal_fee_amount);

			let amount1 = Self::mul_div(&lp_redeem_amount, &reserve1, &total_supply)?;
			let amount2 = Self::mul_div(&lp_redeem_amount, &reserve2, &total_supply)?;

			ensure!(
				!amount1.is_zero() && amount1 >= amount1_min_receive,
				Error::<T>::AssetOneWithdrawalDidNotMeetMinimum
			);
			ensure!(
				!amount2.is_zero() && amount2 >= amount2_min_receive,
				Error::<T>::AssetTwoWithdrawalDidNotMeetMinimum
			);
			let reserve1_left = reserve1.saturating_sub(amount1);
			let reserve2_left = reserve2.saturating_sub(amount2);
			ensure!(
				reserve1_left >= T::Assets::minimum_balance(asset1.clone()),
				Error::<T>::ReserveLeftLessThanMinimal
			);
			ensure!(
				reserve2_left >= T::Assets::minimum_balance(asset2.clone()),
				Error::<T>::ReserveLeftLessThanMinimal
			);

			// burn the provided lp token amount that includes the fee
			T::PoolAssets::burn_from(
				pool.lp_token.clone(),
				who,
				lp_token_burn,
				Expendable,
				Exact,
				Polite,
			)?;

			T::Assets::transfer(asset1, &pool_account, withdraw_to, amount1, Expendable)?;
			T::Assets::transfer(asset2, &pool_account, withdraw_to, amount2, Expendable)?;

			Self::deposit_event(Event::LiquidityRemoved {
				who: who.clone(),
				withdraw_to: withdraw_to.clone(),
				pool_id,
				amount1,
				amount2,
				lp_token: pool.lp_token,
				lp_token_burned: lp_token_burn,
				withdrawal_fee: T::LiquidityWithdrawalFee::get(),
			});

			Ok((amount1, amount2))
		}

		pub fn get_amount_out(
			fee: Permill,
			amount_in: &T::Balance,
			reserve_in: &T::Balance,
			reserve_out: &T::Balance,
		) -> Result<T::Balance, Error<T>> {
			let amount_in = T::HigherPrecisionBalance::from(*amount_in);
			let reserve_in = T::HigherPrecisionBalance::from(*reserve_in);
			let reserve_out = T::HigherPrecisionBalance::from(*reserve_out);

			if reserve_in.is_zero() || reserve_out.is_zero() {
				return Err(Error::<T>::ZeroLiquidity);
			}

			let fee_complement = fee.left_from_one().deconstruct();
			let amount_in_with_fee = amount_in
				.checked_mul(&T::HigherPrecisionBalance::from(fee_complement))
				.ok_or(Error::<T>::Overflow)?;

			let numerator =
				amount_in_with_fee.checked_mul(&reserve_out).ok_or(Error::<T>::Overflow)?;

			let denominator = reserve_in
				.checked_mul(&T::HigherPrecisionBalance::from(Permill::ACCURACY))
				.ok_or(Error::<T>::Overflow)?
				.checked_add(&amount_in_with_fee)
				.ok_or(Error::<T>::Overflow)?;

			let result = numerator.checked_div(&denominator).ok_or(Error::<T>::Overflow)?;

			result.try_into().map_err(|_| Error::<T>::Overflow)
		}

		/// Calculates amount in for a given swap `fee`.
		///
		/// Given an output amount of an asset and pair reserves, returns a required input amount
		/// of the other asset.
		pub fn get_amount_in(
			fee: Permill,
			amount_out: &T::Balance,
			reserve_in: &T::Balance,
			reserve_out: &T::Balance,
		) -> Result<T::Balance, Error<T>> {
			let amount_out = T::HigherPrecisionBalance::from(*amount_out);
			let reserve_in = T::HigherPrecisionBalance::from(*reserve_in);
			let reserve_out = T::HigherPrecisionBalance::from(*reserve_out);

			if reserve_in.is_zero() || reserve_out.is_zero() {
				Err(Error::<T>::ZeroLiquidity)?
			}

			if amount_out >= reserve_out {
				Err(Error::<T>::AmountOutTooHigh)?
			}

			let fee_complement = fee.left_from_one().deconstruct();
			let numerator = reserve_in
				.checked_mul(&amount_out)
				.ok_or(Error::<T>::Overflow)?
				.checked_mul(&T::HigherPrecisionBalance::from(Permill::ACCURACY))
				.ok_or(Error::<T>::Overflow)?;

			let denominator = reserve_out
				.checked_sub(&amount_out)
				.ok_or(Error::<T>::Overflow)?
				.checked_mul(&T::HigherPrecisionBalance::from(fee_complement))
				.ok_or(Error::<T>::Overflow)?;

			let result = numerator
				.checked_div(&denominator)
				.ok_or(Error::<T>::Overflow)?
				.checked_add(&One::one())
				.ok_or(Error::<T>::Overflow)?;

			result.try_into().map_err(|_| Error::<T>::Overflow)
		}
