## Analysis

`FindZipCentralDirectory` validates that `central_dir_offset + central_dir_size <= in_length` [1](#0-0) , and the central directory location is anchored to a verified EOCD record found by scanning backward from the end of the mapped file [2](#0-1) . This bounds check constrains where the central directory *starts and ends as a whole*, but `InputZipFile::ProcessCentralDirEntry` — the function that walks individual entries inside that region — performs **no per-entry bounds checking** at all. It reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-controlled bytes and then does a `memcpy` into a fixed `filename[PATH_MAX]` buffer using a length derived from `file_name_length` without ever confirming that `p` plus that length stays inside the mapped input file or even inside the central directory region: [3](#0-2) 

Contrast this with `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before every read of variable-length data [4](#0-3) . `ProcessCentralDirEntry` has no equivalent guard — the comment "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" is a trust assumption about well-formed archives, not an enforced invariant. A crafted `file_name_length`/`extra_field_length`/`file_comment_length` that overruns the actual per-entry data (while the aggregate `central_dir_size` check still passes, e.g. by making the last entry's lengths point past the buffer, or via the same class of "malformed extra field" already exercised in `singlejar`'s existing regression test for oversized `payload_size`) causes `p`/`extra_p` to walk past `bytes + in_length`, and the subsequent `get_u4le`/`get_u2le`/`memcpy` calls dereference out-of-bounds memory relative to the mmap'd input buffer [5](#0-4) . The `singlejar` test suite already demonstrates awareness of exactly this bug class (malformed extra-field `payload_size` exceeding the buffer) [6](#0-5) , but that hardening lives in `singlejar`, not in `ijar`'s `zip.cc`, which still lacks the corresponding checks in `ProcessCentralDirEntry`.

`ijar` (`third_party/ijar`) is the tool Bazel invokes to strip interface JARs from arbitrary input `.jar` files supplied by Java dependencies — content that is entirely attacker-controlled if served via `http_archive`, `http_jar`, `http_file`, or a Maven/`rules_jvm_external` coordinate resolved from a registry. That satisfies the "unpriviledged attacker who serves content a victim's build consumes" model: the checksum (sha256/integrity) that Bazel verifies on the *whole downloaded archive* does not protect against a memory-safety bug in ijar's *parsing* of that (correctly-hashed) but maliciously crafted jar — the checksum only proves byte-for-byte integrity of the file the attacker chose to publish, not the absence of parser bugs when that file is malformed by design.

## Confidence and limitations

I was able to confirm the missing bounds-check pattern in `ProcessCentralDirEntry` by direct comparison against the bounds-checked `ProcessLocalFileEntry` in the same file, and confirmed `FindZipCentralDirectory`'s aggregate-only validation. I was **not** able to trace with certainty into a Bazel `BuildIntegrationTestCase`/`src/test/shell/bazel` proof showing a live OOB read/crash reproduced end-to-end (that would require executing `ijar` against a hand-crafted malformed jar, which is outside what I can verify via search/read tools), nor confirm whether any AddressSanitizer coverage in CI already catches this in existing fuzz/test infra. This should be treated as a plausible, code-supported analog rather than a fully validated exploit; a background engineering session with build/test execution would be needed to construct and run the crafted-zip PoC and confirm a real out-of-bounds access (vs. one that happens to stay within the same mmap page).

### Title
Out-of-bounds read in ijar's ZIP central directory entry parser via missing per-entry length validation - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry`, used by `ijar` to strip interface JARs from dependency jars, reads attacker-controlled `file_name_length`/`extra_field_length`/`file_comment_length` fields and advances/dereferences pointers based on them without any bounds validation against the mapped input buffer, unlike the local-file-header parser in the same file which does call `EnsureRemaining()`.

### Finding Description
`FindZipCentralDirectory` only validates that the *aggregate* `central_dir_offset + central_dir_size` fits within the file [1](#0-0) . Within that region, `ProcessCentralDirEntry` trusts each entry's length fields unconditionally: it computes a `memcpy` length from `file_name_length` and copies from `p` into a `PATH_MAX` stack buffer, then advances `p`/`extra_p` by `file_name_length`, `extra_field_length`, and `file_comment_length` with no check that these stay inside the buffer [7](#0-6) . A crafted final (or otherwise engineered) central directory entry with oversized length fields causes reads past the end of the mmap'd input file.

### Impact Explanation
This is an out-of-bounds heap/mmap read in native (C++) code triggered purely by the bytes of a downloaded/dependency jar — the same bug class as the underlying CVE (heap buffer overflow while parsing untrusted content). Depending on memory layout this can crash the build (information leak into `filename` used downstream in `processor->Accept`/`Process`, or a SIGSEGV) when Bazel processes an attacker-supplied jar as a build dependency.

### Likelihood Explanation
Any external jar dependency (http_archive/http_jar/Maven coordinate) that reaches an `ijar` action is attacker-influenced content; no special privileges are needed beyond hosting the artifact at a URL/registry entry the victim's `MODULE.bazel`/`WORKSPACE` references. Existing checksum verification (sha256/integrity) on the archive does not prevent this, since it only guarantees byte-fidelity of the (deliberately malformed) file, not memory-safe parsing.

### Recommendation
Add explicit remaining-bytes checks (mirroring `EnsureRemaining()` in `ProcessLocalFileEntry`) in `ProcessCentralDirEntry` before reading/copying `file_name_length`, `extra_field_length`, and `file_comment_length` bytes, rejecting entries whose declared lengths would read past the mapped input file or the validated central directory bounds.

### Proof of Concept
Not independently executed/verified in this session — constructing a minimal crafted ZIP/JAR (following the existing pattern used in `src/tools/singlejar/output_jar_simple_test.cc`'s `CreateZipWithMalformedExtraField`, adapted to `ijar`'s `zip.cc` parser and a `ZipExtractor`-based test) and running it under ASan is recommended in a Devin session with build/test execution access to confirm a concrete out-of-bounds access.
