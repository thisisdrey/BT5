## Title
`calc-liq-factor-exp` collapses the documented graduated liquidation-penalty curve to a wrong/hardcoded formula, mispricing liquidation penalties - (File: `mainnet/contracts/market/v0-4-market.clar`)

## Summary
`docs/egroups.md` documents `LIQ-CURVE-EXP` as a continuous curve parameter: `10000` = linear, `>10000` = "aggressive curve (penalty increases faster)", `<10000` = "gentle curve (e.g., square root)". The implementation in `calc-liq-factor-exp` does not compute `factor^(exp/10000)` at all; it uses integer division and a hardcoded square-root branch that ignores the actual configured value, exactly analogous to Allora M-4 where the shipped formula for a risk-weighting curve diverged from the documented math and silently produced different weights than intended.

## Finding Description
`calc-liq-factor-exp` is meant to raise the linear liquidation factor to the power `exp/BPS` as commented ("liq-factor = liq-factor^alpha"): [1](#0-0) 

```clarity
;; Apply curve exponent for graduated liquidation
;; liq-factor = liq-factor^alpha
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS))))) ;; assume factor^0.5
```

Two divergences from the documented/intended formula:

1. **Aggressive branch (`exp > BPS`)**: `exp/BPS` and `pow BPS (- (/ exp BPS) u1)` both use Clarity integer division, which truncates any fractional multiplier. For any `exp` strictly between two multiples of `BPS` (e.g. `exp = 15000`, intended as `factor^1.5`), `exp/BPS` truncates to `1`, so the whole expression reduces to `pow factor 1 / pow BPS 0 = factor`. The function silently behaves as if `exp = BPS` (pure linear), for the *entire range* `(10000, 19999]`, `(20000, 29999]`, etc. Only exact multiples of `10000` compute a genuinely different (integer) power. This is not "an aggressive curve that increases faster" as documented - it is linear (or an unintended integer power) for almost every configured value in that range.
2. **Gentle branch (`exp < BPS`)**: the code does not use `exp` at all - it unconditionally computes `sqrti(factor * BPS)`, i.e. `factor^0.5`, regardless of what specific sub-`10000` value was configured (`9000`, `5000`, `1000`, etc. all produce the identical square-root curve). The comment even admits this: `;; assume factor^0.5`.

So `LIQ-CURVE-EXP` - a per-egroup risk parameter documented as continuously tunable - is in practice only meaningfully differentiable at exact multiples of `10000`; every other configured value collapses to one of two fixed curves (linear or sqrt) instead of the graduated curve the whitepaper/docs describe. This mirrors the Allora finding precisely: the on-chain formula for a risk-weighting/curve calculation does not match the documented math, producing incorrect intermediate values (here, `liq-pct-scaled`, hence `liq-penalty`) whenever a non-multiple-of-BPS exponent is used.

`calc-liq-factor-exp`'s output feeds directly into the liquidation-penalty and max-liquidatable-debt calculation, reachable by any unprivileged liquidator calling the liquidation entry point: [2](#0-1) 

```clarity
(define-private (calc-liquidation-params ...)
  (let ((liq-pct-linear (calc-liq-factor current-ltv ltv-liq-partial ltv-liq-full))
        (liq-pct-scaled (calc-liq-factor-exp liq-pct-linear curve-exponent))
        (liq-penalty (calc-liq-factor-bound liq-pct-scaled liq-penalty-min liq-penalty-max))
        (max-debt-usd (calc-liq-debt-repay total-debt-usd liq-pct-scaled)))
    ...))
```

and that penalty is used to compute the collateral seized from the borrower in `calc-liq-collateral-repay`/`calc-final-liquidation-amounts`, called from the public liquidation flow: [3](#0-2) 

## Impact Explanation
For any egroup configured with a non-multiple-of-`BPS` `LIQ-CURVE-EXP` (a value the docs explicitly present as a normal, expected configuration, not an edge case or misconfiguration), every liquidation against positions in that egroup computes a wrong `liq-pct-scaled`/`liq-penalty` versus the documented curve. Depending on the direction of the error this either:
- over-penalizes borrowers (liquidator seizes more collateral than the documented curve intends) - theft of user (borrower) collateral beyond the intended amount, or
- under-penalizes/limits the max liquidatable debt versus intended - reduces liquidator incentive at intermediate health levels, which can delay liquidation of at-risk positions and contribute to bad debt / temporary freezing of protocol funds during stress.

Because the parameter is DAO-set but the *implementation* (not the DAO input) is what is wrong, this is a genuine code defect rather than a DAO misconfiguration, and it is triggered simply by an ordinary liquidator interacting with the public liquidation function against any egroup using a fractional curve exponent.

## Likelihood Explanation
Any egroup whose `LIQ-CURVE-EXP` is not an exact multiple of `10000` (which per the documentation is the normal way to express "aggressive" or "gentle" curves, e.g. `15000` for 1.5x or `5000`/`7000`/`9000` for various gentle curves) is affected on every liquidation call against positions in that egroup - no special conditions or privileged access are required beyond triggering an ordinary liquidation.

## Recommendation
Implement true fractional exponentiation (e.g., fixed-point `pow`/`ln`/`exp` based power function, or restrict `LIQ-CURVE-EXP` on-chain to only the discrete set of values the integer-power implementation can correctly support, and update `docs/egroups.md` to match) so that `calc-liq-factor-exp` actually computes `factor^(exp/BPS)` for the full documented range instead of silently truncating to linear or hardcoding square-root.

## Proof of Concept
1. DAO (acting correctly per documentation) configures an egroup with `LIQ-CURVE-EXP = 15000` (intending an "aggressive," `factor^1.5` liquidation-penalty curve).
2. A borrower's position LTV moves into the partial-liquidation zone, giving `liq-pct-linear = factor` (e.g., `0.5` in BPS terms).
3. `calc-liq-factor-exp(factor, 15000)` executes the `exp > BPS` branch: `exp/BPS = 15000/10000 = 1` (integer division), so the result is `pow(factor,1) / pow(BPS,0) = factor` - identical to what would occur with `exp = BPS` (pure linear), not the intended steeper `factor^1.5` curve.
4. This wrong `liq-pct-scaled` propagates into `calc-liq-factor-bound` (wrong `liq-penalty`) and `calc-liq-debt-repay` (wrong `max-debt-usd`), so any liquidator calling the public liquidation function against this borrower's position receives a penalty/collateral amount that does not match the documented curve - either seizing more of the borrower's collateral than intended by the aggressive-curve design, or (for `exp < BPS` configurations) always applying an undocumented fixed square-root curve regardless of the actually configured gentleness.
