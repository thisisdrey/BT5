## Analysis

The reported bug class — a liquidity/pool withdrawal function that computes payout amounts from the *current* pool ratio at execution time, with no caller-specified minimum-received guard, making it front-runnable — has a direct analog in java-tron's on-chain bancor-style `Exchange` (TRC10↔TRX/TRC10↔TRC10 pool) actuators.

### Title
Front-running of `ExchangeWithdrawContract` lets an attacker manipulate the token distribution an exchange creator receives on withdrawal - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` — the amount of the paired token returned to the withdrawer — purely from the exchange pool's *current* `firstTokenBalance`/`secondTokenBalance` ratio at execution time, using the constant-ratio formula `anotherTokenQuant = otherBalance * tokenQuant / thisBalance`. Unlike `ExchangeTransactionActuator`, which lets the caller pass an `expected` minimum via `ExchangeTransactionContract.expected` and enforces `anotherTokenQuant < tokenExpected` in `doValidate()`, `ExchangeWithdrawContract` has no such field, so the withdrawer cannot bound or guarantee the amount/ratio of tokens they will receive. [1](#0-0) [2](#0-1) 

### Finding Description
This mirrors the reported `AeraVaultV1.returnFunds()`/`finalize()` bug class exactly: a "withdraw the whole/whole-ratio holdings from an AMM-like pool" operation is executed without any slippage/minimum-amount enforcement.

- `ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, `quant` — no minimum/expected amount for the other side of the pair. [3](#0-2) 
- In `execute()`, `anotherTokenQuant` is derived from whatever `firstTokenBalance`/`secondTokenBalance` are in the `ExchangeCapsule` at the moment this actuator runs, which is set by whatever transaction executed immediately prior in the same block. [4](#0-3) 
- The validate step ("Not precise enough" check) only bounds rounding error against the *current* pool state at validation time — it does not protect against the pool state being different from what the withdrawer expected when they built the transaction; it re-derives from the same live balances, so it passes trivially even after a front-run. [5](#0-4) 
- Contrast with `ExchangeTransactionActuator`, which explicitly supports an `expected` floor and rejects the transaction if the computed output would be below it — proving the codebase recognizes this exact class of risk for swaps but did not apply the same protection to withdrawals. [6](#0-5) 

Only the exchange's creator can call `ExchangeWithdrawContract` (validated via `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`), which is the direct analog of the report's "Treasury" role calling `finalize()`. [7](#0-6) 

An attacker (any unprivileged account) can front-run the creator's withdraw transaction with an `ExchangeTransactionContract` swap that shifts `firstTokenBalance`/`secondTokenBalance` right before the withdraw executes in the same block, forcing the creator to receive a skewed split of the two assets (e.g., far less of the more valuable token than intended) — exactly the "Treasury receives 0.5 WETH and 6000 DAI instead of 1 WETH and 3000 DAI" scenario in the source report.

### Impact Explanation
While the underlying pool *value* (per the constant-product/ratio invariant) is preserved, the withdrawer has no way to guarantee or bound the *distribution* of tokens they receive, and a malicious actor can deliberately manipulate that distribution to their own advantage (e.g. if they hold a short position or need to affect specific token accounting for the withdrawer). Since exchange creators cannot specify a minimum for either leg of the withdrawal, they can be forced into an unfavorable token mix without recourse, which is an unauthorized manipulation of account asset outcomes triggered by an unprivileged third party's transaction ordering — a concrete "theft of expected value / unbacked distribution" analog reachable purely by any account able to broadcast an `ExchangeTransactionContract`.

### Likelihood Explanation
Any account can submit `ExchangeTransactionContract` transactions against a public exchange pool, and transaction ordering within a block/mempool is influenceable by block producers or fast broadcasters, making the front-run trivially executable whenever a creator submits an `ExchangeWithdrawContract`. The attack requires no privileged role, no bug in access control, and no special preconditions beyond an active liquidity pool with a pending withdraw.

### Recommendation
Add an `expected`/minimum-amount field (analogous to `ExchangeTransactionContract.expected`) to `ExchangeWithdrawContract`, and enforce in `ExchangeWithdrawActuator.doValidate()`/`execute()` that the computed `anotherTokenQuant` (and/or `tokenQuant`) is not less than the caller-specified minimum, reverting the withdrawal otherwise. This aligns withdraw semantics with the slippage protection already implemented for `ExchangeTransactionActuator`.

### Proof of Concept
1. Exchange pool `X` has `firstTokenBalance = 1 WETH-equivalent`, `secondTokenBalance = 3000 token units`, weights implied 1:1 by construction (`ExchangeWithdrawActuator` ratio math at [1](#0-0) ).
2. The creator broadcasts `ExchangeWithdrawContract{exchange_id=X, token_id=first, quant=Q}` expecting to receive `Q` of `first` and `~3*Q` of `second` based on the pool state they observed.
3. An attacker broadcasts (and gets ordered first in the same block) `ExchangeTransactionContract{exchange_id=X, token_id=second, quant=large}` which is processed by `ExchangeTransactionActuator.execute()` [8](#0-7) , shifting the pool ratio substantially.
4. The creator's withdraw executes against the new skewed ratio, and `ret.setExchangeWithdrawAnotherAmount(anotherTokenQuant)` reflects a materially different `first`/`second` split than the creator intended, with no validation failure since the "Not precise enough" check only re-derives from the already-skewed live state [9](#0-8) .
