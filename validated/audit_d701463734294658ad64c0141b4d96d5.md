### Title
Unbounded, fixed-weight `submit` extrinsic in Snowbridge inbound queues admits attacker-sized proof data with no pallet-level size limit, enabling cheap resource-exhaustion DoS - (File: `bridges/snowbridge/pallets/inbound-queue/src/lib.rs`, `bridges/snowbridge/primitives/verification/src/lib.rs`)

### Summary
The Snowbridge `inbound-queue` (and `inbound-queue-v2`) pallets accept a signed, unbounded `EventProof` argument (`Log.data: Vec<u8>`, `Log.topics: Vec<H256>`, `Proof.receipt_proof: Vec<Vec<u8>>`) via the public `submit` extrinsic, with no pallet-enforced maximum size on any of these fields before expensive cryptographic verification (RLP decoding, Merkle/receipt-trie proof walking, ABI log decoding) is performed [1](#0-0) . The pallet's `MaxMessageSize` config item, which looks like a size limit, is explicitly documented as being used only for fee estimation, not enforcement [2](#0-1) . This mirrors the HAL-27 report's core issue: a public endpoint accepts oversized attacker-controlled input with no sanitization/limit before it is processed, at the risk of DoS/resource exhaustion.

### Finding Description
The `submit` extrinsic in `pallet-snowbridge-inbound-queue` takes `event: EventProof` directly, which is composed of unbounded collections:
```rust
pub struct Log {
    pub address: H160,
    pub topics: Vec<H256>,
    pub data: Vec<u8>,
    pub tx_index: u64,
}
pub struct Proof {
    pub receipt_proof: Vec<Vec<u8>>,
    pub execution_proof: ExecutionProof,
}
``` [1](#0-0) 

None of these fields are `BoundedVec`s or otherwise capped by a `MaxEncodedLen`-style constraint at the pallet or primitive level. The only "size" configuration in the pallet, `type MaxMessageSize: Get<u32>`, is explicitly commented as "only used to estimate delivery cost" [3](#0-2)  — it feeds into `calculate_delivery_cost`, not into any validation/rejection path [4](#0-3) .

Before any nonce/gateway/channel check, `submit` immediately calls `T::Verifier::verify(&event.event_log, &event.proof)`, which performs the beacon execution-header proof verification and then a receipt-trie inclusion proof walk over `event.proof.receipt_proof` (an unbounded `Vec<Vec<u8>>`) using `alloy_trie::verify_proof` [5](#0-4) , [6](#0-5) . This proof-verification work (RLP decoding of arbitrary node bytes, hashing, nibble-path walking through however many proof nodes the attacker supplies) is O(size of attacker-supplied data), yet the extrinsic's declared weight is the fixed, benchmarked `T::WeightInfo::submit()` constant, not a per-length weight [7](#0-6) . There is no `ensure!` on `event.proof.receipt_proof.len()`, no cap on individual node byte length, and no cap on `event.event_log.data.len()` before this work is performed.

The only practical ceiling is the runtime's generic max extrinsic/block length limit (a chain-wide constant, not a pallet-specific sanitization control), which is far larger than what a legitimate receipt proof requires and does not scale the extrinsic's charged weight to the actual size submitted. This is exactly the invariant broken in HAL-27: parameters "can accept excessively large input without any restrictions," enabling resource exhaustion via crafted large payloads, because the fee/weight charged does not track the actual attacker-controlled input size.

### Impact Explanation
An unprivileged, signed account (any account able to pay the base transaction fee) can submit `submit` calls with maximally-sized `Log.data` and many/large `receipt_proof` nodes filled with garbage bytes. Each submission forces the node/runtime to perform RLP decoding and trie-proof verification work proportional to attacker-chosen size, while only being charged the fixed benchmarked weight for a "normal-sized" proof. Submitted en masse (or even as a handful of maximal transactions per block), this degrades block production time and consumes disproportionate CPU/PoV relative to the fee paid — a public underpriced work primitive that can stall/slow bridge message processing on BridgeHub, aligning with the program's "public underpriced work that degrades block production or stalls bridge processing" acceptance criterion.

### Likelihood Explanation
Likelihood is high: the attack requires only a signed account and the ability to construct arbitrary bytes for `EventProof` — no relayer, validator, governance, or leaked-key assumptions are needed. The verifier fails validly (returns `VerificationError::InvalidProof`) only after the expensive work is done, so the attacker pays the (undercharged) fixed extrinsic fee repeatedly to trigger disproportionate work each time.

### Recommendation
- Bound `Log.data`, `Log.topics`, and `Proof.receipt_proof` (and each node's byte length) with `BoundedVec`/explicit `ensure!` length checks tied to realistic maxima (e.g., typical Ethereum receipt proof depth/size), rejecting oversized submissions before calling the verifier.
- Make `submit`'s weight a function of the actual encoded length of `event` (similar to how `LengthToFee` is already used for delivery-cost calculation), so oversized proofs are charged proportionally, removing the underpriced-work incentive.
- Reuse `MaxMessageSize` (or introduce a dedicated `MaxProofSize`/`MaxReceiptProofNodes`) as an actual `ensure!`-enforced limit, not merely a fee-estimation input.

### Proof of Concept
1. Construct an `EventProof` where `event_log.data` is filled to the maximum practical extrinsic-length allowance with junk bytes, and `proof.receipt_proof` contains many large `Vec<u8>` entries of garbage RLP data.
2. Submit repeatedly via `InboundQueue::submit(origin, event)` from any signed account with sufficient balance for the fixed submit fee.
3. Observe that `T::Verifier::verify` (`verify_execution_proof` + `verify_receipt_inclusion` → `alloy_trie::verify_proof`) performs RLP decoding/hashing work proportional to the attacker-supplied `receipt_proof` size before failing with `VerificationError::InvalidProof`, while the extrinsic is charged only the fixed `WeightInfo::submit()` weight regardless of input size — confirming the size/weight mismatch described above.

Note: due to index size limits, I could not directly view the full body of `verify_execution_proof`/`verify_receipt_inclusion` in `bridges/snowbridge/pallets/ethereum-client/src/impls.rs` or the benchmarked weight formula in `weights.rs` to confirm the exact constant-vs-length weight relationship; a Devin session with full repo access would let you inspect those functions and the `#[pallet::weight(...)]` benchmarking macros directly to fully validate the underpricing claim.

```rust
pub fn verify_receipt_proof(
	receipts_root: H256,
	tx_index: u64,
	proof: &[Vec<u8>],
) -> Option<ReceiptEnvelope> {
	let key = receipt_trie_key(tx_index);
	let root = B256::from_slice(receipts_root.as_bytes());
	let proof_nodes: Vec<Bytes> = proof.iter().map(|node| Bytes::copy_from_slice(node)).collect();

	// Call verify_proof with None to extract the value from an inclusion proof. For inclusion
	// proofs, alloy_trie returns ValueMismatch with the extracted value in `got`. The proof is
	// already cryptographically verified during this traversal.
	let value = match verify_proof(root, key, None, proof_nodes.iter()) {
		Ok(()) => return None, // Exclusion proof - key does not exist
		Err(ProofVerificationError::ValueMismatch { path, got: Some(v), expected: None })
			if path == key =>
		{
			v.to_vec()
		},
		Err(_) => return None,
	};

	ReceiptEnvelope::decode(&mut value.as_slice()).ok()
}
