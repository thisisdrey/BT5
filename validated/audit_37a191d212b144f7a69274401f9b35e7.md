### Title
Missing `CallerDeposit` refund when the address-registrar lookup promise fails - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
In `address_check_callback`, when the cross-contract call to the address registrar (`ext_registrar.lookup(...)`) fails, the function returns an error `ExecuteResponse` without ever using the `caller_deposit` parameter to issue a refund. This is inconsistent with the sibling callback `rlp_execute_callback`, which explicitly refunds `caller_deposit` on `PromiseResult::Failed`. Any NEAR attached by an external predecessor to `rlp_execute` is silently absorbed into the wallet contract's balance if the registrar-lookup promise fails.

### Finding Description
`rlp_execute` ( [1](#0-0) ) builds a `CallerDeposit` from the execution context whenever the predecessor differs from the wallet's own account and a deposit was attached ( [2](#0-1) ). For an `EOABaseTokenTransfer` whose target is another eth-implicit account, `inner_rlp_execute` schedules `ext_registrar.lookup(...).then(address_check_callback(target, action, caller_deposit))`, passing `caller_deposit` through as a callback argument rather than attaching it to any promise ( [3](#0-2) ).

In `address_check_callback`, the `PromiseResult::Failed` branch (triggered when the registrar lookup itself fails) simply returns an error response and drops `caller_deposit` without ever creating a refund transfer: [4](#0-3) 

This contrasts with `rlp_execute_callback`, which correctly issues a `promise_batch_action_transfer` refund to `caller_deposit.account_id` when the final action promise fails: [5](#0-4) 

Because a deposit attached to a `FunctionCall` action is credited to the receiving account's balance immediately as part of receipt processing (independent of whether the call ultimately succeeds), the attacker's/caller's NEAR is already resident in the wallet contract's balance by the time `address_check_callback` runs. If the registrar-lookup promise fails, no code path ever creates a transfer back to the original depositor, so that value permanently remains part of the wallet account's balance instead of being returned.

### Impact Explanation
This causes permanent loss/freezing of an external caller's attached deposit whenever the address-registrar cross-contract call fails (e.g., account issues, panics, insufficient `REGISTRAR_LOOKUP_GAS`), for any `rlp_execute` call routed through the `address_check` path with target being another eth-implicit account. This falls under "permanent freezing/loss of user funds."

### Likelihood Explanation
The affected code path is reached whenever any external account (not the wallet itself) calls `rlp_execute` with attached deposit and a target eth-implicit account whose transaction type is `EOABaseTokenTransfer` with `address_check: Some(_)`. The trigger condition (registrar-lookup promise failing) is not directly controllable by the caller — it depends on the address-registrar contract's availability/gas, which is outside the depositor's control. This lowers direct attacker-controllability (it is not a scenario an attacker can force on demand against a healthy registrar), but the missing-refund logic itself is a deterministic code defect: any failure of the registrar call — for any reason — results in unconditional, un-refunded fund absorption, unlike the parallel path in `rlp_execute_callback`.

### Recommendation
In `address_check_callback`'s `PromiseResult::Failed` branch, mirror the refund logic used in `rlp_execute_callback`: if `caller_deposit` is `Some`, create a promise batch transfer back to `caller_deposit.account_id` for `caller_deposit.yocto_near` before returning the error `ExecuteResponse`.

### Proof of Concept
Integration test (test-loop or near-workspaces sandbox) plan:
1. Deploy the wallet contract to an eth-implicit account and fund it.
2. Replace/point `ADDRESS_REGISTRAR_ACCOUNT_ID` (or deploy at that account in the test harness) with a stub contract whose `lookup` method always panics.
3. From a distinct funded NEAR account (attacker/caller), call `rlp_execute` with a non-zero attached deposit and an RLP-encoded `EOABaseTokenTransfer` transaction targeting another eth-implicit account (forcing the `address_check: Some(_)` path).
4. Assert: (a) the registrar `lookup` receipt fails, (b) `address_check_callback` returns `success: false` with `"Call to Address Registrar contract failed"`, (c) no refund receipt/transfer is produced to the caller's account, and (d) the caller's account balance is permanently short by the attached deposit amount while the wallet contract's balance retains it.     pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }
