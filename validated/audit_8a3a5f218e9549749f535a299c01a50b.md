### Title
Unbounded HTTP body read in `process_event` allows memory-exhaustion DoS against the signer's event listener - (File: libsigner/src/events.rs)

### Summary
`process_event::<T, E>` calls `request.as_reader().read_to_string(&mut body)` on the signer's local `tiny_http` event-receiver socket with no size cap, unlike the node's main HTTP stack which enforces `MAX_MESSAGE_LEN`. Any TCP client able to reach the configured `bind` address of the signer's event receiver can POST an arbitrarily large `Content-Length` body to `/stackerdb_chunks`, `/new_block`, `/new_burn_block`, or `/proposal_response` and force the process to buffer the entire body in memory before any JSON/type validation.

### Finding Description
The broken guarantee: bytes read into `body` should be bounded by a `MAX_MESSAGE_LEN`-style cap before any parsing, but instead `body`'s size == whatever `Content-Length`/streamed body length the client sends, with zero enforcement at this layer.

`SignerEventReceiver::next_event` in `libsigner/src/events.rs` accepts any POST to `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block` and dispatches to `process_event::<T, E>(request)`: [1](#0-0) 

`process_event` then does: [2](#0-1) 

`request.as_reader()` returns `tiny_http`'s body reader, which is driven by the client-declared `Content-Length` (or chunked transfer-encoding); there is no length check, no `MAX_MESSAGE_LEN`/`MAX_PAYLOAD_LEN` cap, and no incremental size check as bytes accumulate. Compare this to the node's own HTTP request handling in `stackslib/src/net/httpcore.rs` and `stackslib/src/net/server.rs`, which explicitly bound reads using `MAX_MESSAGE_LEN`; this cap is entirely absent from the signer's event-receiver path in `libsigner/src/events.rs` and `libsigner/src/http.rs`'s `decode_http_body` (which is a *different*, unused-by-`process_event` codepath that does apply `MAX_MESSAGE_LEN` to chunked bodies only, and isn't invoked here at all).

The only prior gate before `read_to_string` is that the request method must be POST to one of the recognized URLs — no signature check, no auth token, no size limit. Because `T` and `E` (JSON-decoded types) validation happens strictly after the full body is buffered into a `String`, an attacker can send a single request with a multi-hundred-MB or multi-GB `Content-Length` and force the process to allocate and hold that much memory purely to satisfy `read_to_string`, before `serde_json::from_slice` ever runs.

### Impact Explanation
A single crafted POST can force unbounded memory allocation in the signer process (or any consumer using this shared `libsigner::events` receiver, e.g. `stacks-signer`), leading to OOM-kill or severe memory pressure/DoS on that process from one message, repeatable at will and cheaply (attacker only needs to send bytes, no signature or protocol knowledge required). This matches the "Critical - remote crash/unauthenticated DoS from few messages" category for the reachable endpoint, since no authentication, signature, or per-field cap gates the read.

### Likelihood Explanation
The attacker needs only TCP reachability to the signer's configured event-receiver `bind` address and the ability to issue an HTTP POST with a large body — no signer key, no StackerDB slot ownership, no node RPC secret. Cost is a single outbound connection and streaming bytes; the primitive is trivially repeatable. The main constraint is whether the bind address is exposed beyond localhost in a given deployment, but the code itself provides no defense regardless of exposure.

### Recommendation
Enforce a hard cap (e.g., `MAX_MESSAGE_LEN` or a signer-specific limit) on the request body size in `process_event` before/while calling `read_to_string`— for example, reject or truncate reads once bytes exceed a threshold (check `Content-Length` header up front and abort if it exceeds the cap, and/or wrap the reader with a bounded `Read::take(...)` and treat truncation as a `MalformedRequest` error) rather than unconditionally buffering the full stream into a `String`.

### Proof of Concept
1. In a test module for `libsigner/src/events.rs` (or a standalone integration test), bind a `SignerEventReceiver` via `EventReceiver::bind` to `127.0.0.1:0`, spawn `next_event()` in a thread.
2. From a plain `TcpStream`, send:
```
POST /stackerdb_chunks HTTP/1.1\r\nHost: x\r\nContent-Length: 2000000000\r\nContent-Type: application/json\r\n\r\n
```
followed by streaming (or attempting to stream) 2 GB of filler bytes (e.g., zeros) without ever completing valid JSON.
3. Observe process RSS growing unbounded as `read_to_string` in `process_event` (libsigner/src/events.rs:526) buffers the stream, with no early rejection based on declared or actual body length — assert that memory usage tracks the attacker-controlled length with no cap, in contrast to node RPC handlers that reject request bodies exceeding `MAX_MESSAGE_LEN` before buffering.
