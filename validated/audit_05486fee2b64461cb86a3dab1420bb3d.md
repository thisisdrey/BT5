Based on my research, I found a strong analog to this bug class: an unbounded, append‑only list stored on-chain that grows every transaction with no pruning, which is later fully materialized/iterated by both an actuator and a public API.

### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` in the legacy (non-optimized) delegate-resource index enables list-growth DoS - (File: `chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java`)

### Summary
The reported bug class is an array that only ever grows (no `pop()`/eviction), which later becomes unboundedly expensive to iterate. java-tron has the same pattern in the legacy delegated-resource index: `addToAccount()`/`addFromAccount()` unconditionally append a `ByteString` to a protobuf-repeated field with no cap, size check, or automatic pruning.

### Finding Description
`DelegatedResourceAccountIndexCapsule` exposes `addToAccount`/`addFromAccount`, which simply append to the underlying protobuf list forever: [1](#0-0) 

This is invoked from `FreezeBalanceActuator.delegateResource()` whenever the legacy (`!supportAllowDelegateOptimization()`) code path is active — i.e. for every distinct receiver address a transaction broadcaster delegates resources to, `ownerIndexCapsule.addToAccount(...)` and `receiverIndexCapsule.addFromAccount(...)` are appended, guarded only by an O(n) `contains()` de-dup check (not a hard cap): [2](#0-1) 

Removal only happens on full unfreeze in `UnfreezeBalanceActuator`, and only when the delegated balance is fully returned to zero: [3](#0-2) 

Anyone can grow another account's `fromAccountsList` by creating many cheaply-funded owner accounts, each performing a minimal `FreezeBalanceContract` delegation (e.g. 1 TRX) to the same fixed victim receiver address — this is a broadcastable transaction requiring only an unprivileged signer and small collateral (later reclaimable via `UnfreezeBalanceContract`).

The unbounded list is then:
1. Fully materialized and returned by the public `getDelegatedResourceAccountIndex` API (HTTP/gRPC, reachable by anonymous clients), with no pagination: [4](#0-3) [5](#0-4) 

2. Fully iterated, element by element, in `DelegatedResourceAccountIndexStore.convert()` — which migrates the legacy list to the new per-relation key scheme whenever `delegateResource`/`unDelegateResource` runs after the network later enables `ALLOW_DELEGATE_OPTIMIZATION`: [6](#0-5) 

Since `ALLOW_DELEGATE_OPTIMIZATION` defaults to `0` and is only a committee-governed toggle (default disabled in `reference.conf`, only ever flippable to `1`, never back to `0`), the legacy unbounded-list code path is live on any deployment (private chain, sidechain, or pre-activation mainnet state) where this proposal has not yet been enabled: [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker can inflate a target account's `fromAccountsList` (or their own `toAccountsList`) to an arbitrarily large size using cheap, repeated `FreezeBalanceContract`/delegate transactions to distinct receiver addresses. This:
- Makes the unpaginated `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` HTTP/gRPC API return an ever-growing response, degrading or denying service for anyone querying that address (an anonymous API client can reach and pay for this path repeatedly).
- Once the list is very large, `DelegatedResourceAccountIndexStore.convert()` performs O(n) work (calling `delegate()` — two DB puts — for every legacy entry) inside any future `delegate`/`unDelegate`/`freeze` transaction touching that address, inflating the resource/energy and time cost of that single transaction and potentially causing it to exceed block/transaction execution limits.
This is a resource-exhaustion / DoS impact on a node-served API and on transaction execution for affected addresses, consistent with the medium-severity bug class in the report.

### Likelihood Explanation
Delegating resources with `FreezeBalanceContract`/`DelegateResourceContract` requires only a minimal frozen balance and a valid signature — no special privilege. Creating many owner accounts and issuing many small delegations to a single victim address is inexpensive relative to the persistent on-chain and API cost imposed. The attack is straightforward to execute repeatedly by any unprivileged transaction broadcaster.

### Recommendation
- Cap the size of `toAccountsList`/`fromAccountsList` (similar to the existing `MaxFrozenSupplyNumber` cap pattern used in `AssetIssueActuator`) or migrate all deployments unconditionally to the per-relation-key model (`delegate`/`unDelegate`) instead of an append-only list.
- Add pagination to `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2`.
- Avoid the O(n) `convert()` migration being triggered inline inside a single user transaction; perform migration lazily/incrementally or bound it.

### Proof of Concept
1. Attacker creates N funded accounts A1..AN (small TRX amount each).
2. For each Ai, broadcast `FreezeBalanceContract` (or `DelegateResourceContract` when `AllowDelegateOptimization=0`) with `receiver_address = Victim`, freezing the minimum amount, while `dynamicStore.supportAllowDelegateOptimization()` is false.
3. Each transaction appends to `Victim`'s `DelegatedResourceAccountIndexCapsule.fromAccountsList` via `addFromAccount()` — [9](#0-8) .
4. After N is large (e.g., tens of thousands), call `GET /wallet/getdelegatedresourceaccountindex?value=Victim` — the response grows linearly with N with no pagination, and any subsequent delegate/undelegate touching Victim after the optimization proposal activates triggers an O(N) `convert()` migration inside a single transaction.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
