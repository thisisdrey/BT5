This is a classic "misassigned default flag/index" bug-class analog — the `accountIndexOf` fallback in `RewardsDistributor` looks promising. Let me verify whether any balance-changing path skips the index update.### Title
Uninitialized `accountIndexOf` defaults to `INITIAL_INDEX`, granting retroactive rewards on current balance - ([File: contracts/RewardsDistributor.sol](https://github.com/ThankGodontt/metronome-synth-public--024/blob/main/contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` treats an account whose `accountIndexOf` entry was never initialized as if it had been holding since index `INITIAL_INDEX` (`1e18`). Combined with the permissionless `updateBeforeMintOrBurn`, any account that holds a token balance while its reward index is still `0` can book `balance * (currentIndex - 1e18)` — i.e., the entire historical emission of the reward stream — in a single transaction.

### Finding Description
In `RewardsDistributor`, reward accounting is driven by a global per-token index (`tokenStates[token_].index`) and a per-account checkpoint (`accountIndexOf[token_][account_]`). The delta computation is:

```solidity
// contracts/RewardsDistributor.sol
uint256 _accountIndex = accountIndexOf[token_][account_];
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;          // <- uninitialized checkpoint treated as "held since genesis"
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

`_updateTokensAccruedOf` then writes `accountIndexOf[...] = _tokenIndex` and adds `_tokensDelta` into `tokensAccruedOf[account_]` (lines 261–265), which is withdrawable via `claimRewards`.

The guard `if (tokenStates[token_].index > 0)` in `updateBeforeMintOrBurn` / `updateBeforeTransfer` (lines 175–192) means that **before a token is registered for rewards** (`index == 0`), these hooks silently no-op and never write `accountIndexOf`. Therefore:

- Any account holding `msdTOKEN`/`DebtToken` shares before `updateTokenSpeed` registers the token keeps `accountIndexOf == 0` even as its balance changes — deposits, mints, burns all occur with no checkpoint.
- After the governor enables a reward speed, the index grows above `1e18`. The *first* update for such an account credits `balance_now * (index - 1e18)` using the balance **at the moment of the call**, not a time-weighted balance.
- `updateBeforeMintOrBurn` is explicitly callable by anyone for any `(token_, account_)` (comment at line 173: "may be called by anyone to update stored indexes"), and `claimRewards(account_, tokens_)` is also callable by anyone to push `tokensAccruedOf` out to the account.

The missing-checkpoint condition can also arise on balance-changing paths that bypass the distributor hook (e.g., `DepositToken.seize` during liquidations, which moves collateral shares to a liquidator). Note: I was unable to fully verify the internal transfer path inside `seize` within the search iterations available; if `seize` performs a raw internal `_transfer` without calling `updateBeforeTransfer`, a liquidator receives shares with `accountIndexOf == 0` and anyone can then harvest the full retroactive delta for that balance.

### Impact Explanation
The reward-distribution invariant breaks: rewards are attributed pro-rata to balances *over time*, but the `INITIAL_INDEX` fallback attributes the full elapsed index delta to the balance observed at a single instant. An attacker holding (or receiving via seizure) a large balance with an uninitialized checkpoint drains a disproportionate share of the reward contract — theft of unclaimed yield belonging to all other suppliers/borrowers. Since `_transferRewardIfEnoughTokens` pays out up to the distributor's full `rewardToken` balance, the accrued pool can be substantially drained.

### Likelihood Explanation
- Requires an account holding token shares while `accountIndexOf == 0`. This occurs for every pre-existing holder when a reward speed is newly enabled for a token (all updates before `index > 0` are no-ops), and on any balance mutation path that skips the distributor hook (e.g., `seize` during liquidation, if unhooked).
- No privileged role is needed to trigger the payout: `updateBeforeMintOrBurn` and `claimRewards` are permissionless, and `claimRewards` is not gated by pause flags.
- The magnitude is bounded by `(index - 1e18) * balance`, i.e., the total elapsed emission since reward start — which grows monotonically, making the exploit strictly more valuable over time.

### Recommendation
Initialize a fresh account checkpoint to the **current** token index rather than `INITIAL_INDEX`:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex;
}
```

This is the standard Compound-style fix: a first-time checkpoint should accrue zero delta, not delta since genesis. Additionally, ensure every internal balance-mutation path (including `seize` and treasury/sweep movements) invokes the distributor's pre-transfer hook so no balance exists with an uninitialized checkpoint.

### Proof of Concept
Hardhat sketch (assumes a `DepositToken` `msdTOKEN`, reward token `MET`, distributor registered on `Pool`):

```typescript
// Setup: alice and bob deposit 1000e18 collateral each BEFORE reward speed is set.
await msdToken.connect(alice).deposit(parseEther('1000'), alice.address); // index==0 -> accountIndex stays 0

// Governor enables rewards at t0.
await rewardsDistributor.updateTokenSpeed(msdToken.address, parseEther('1')); // index=1e18, speed>0

// Attacker deposits AFTER rewards start (normal path sets his index correctly to 1e18).
// But alice (and any pre-existing holder / liquidator receiving seized shares) still has index 0.
await advanceTime(86_400); // index grows; emissions accumulate

// Anyone can trigger the retroactive credit for alice's account:
await rewardsDistributor.updateBeforeMintOrBurn(msdToken.address, alice.address);

// alice's accrued == 1000e18 * (index - 1e18) ≈ full day of emissions for the whole token,
// regardless of how the supply/other holders evolved during that period.
const accrued = await rewardsDistributor.tokensAccruedOf(alice.address);
expect(accrued).to.be.gt(0); // equals alice.balance * (index - INITIAL_INDEX)

// Payout (callable by anyone, sends to alice):
await rewardsDistributor.claimRewards(alice.address, [msdToken.address]);
```

The same sequence applies to a `DebtToken` tracked by the distributor, and to any account that acquired shares through a path that did not invoke `updateBeforeTransfer`/`updateBeforeMintOrBurn` while `tokenStates[token_].index > 0`.
