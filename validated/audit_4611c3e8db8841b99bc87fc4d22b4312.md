### Title
Malicious Multisig Executor Can Force-Fail Inner Payload via Deliberate Gas Starvation - (`File: aptos-move/aptos-vm/src/aptos_vm.rs`)

### Summary

The `execute_multisig_transaction` function in the Aptos VM explicitly tolerates any inner payload failure — including `OUT_OF_GAS` — and marks the multisig proposal as "executed but failed," advancing the sequence number and consuming the proposal. Because the executor (a multisig owner) fully controls `max_gas_amount` in the submitted transaction, a malicious owner can deliberately set it just above the intrinsic minimum but below what the inner payload needs, force-failing the payload while the outer cleanup succeeds via `UnmeteredGasMeter`. The proposal is permanently consumed without the intended action ever executing.

### Finding Description

In `execute_multisig_transaction` the VM explicitly documents that inner payload failure is tolerated:

```rust
// Step 2: Execute the target payload. Transaction failure here is tolerated.
// The multisig transaction would still be considered executed even if execution fails.
let execution_result = self.execute_multisig_payload(
    resolver, code_storage, session, gas_meter, ...
);
``` [1](#0-0) 

When `execution_result` is `Err`, the code calls `failure_multisig_payload_cleanup`, which:
1. Converts the `VMStatus` error (including `OUT_OF_GAS`) to an `ExecutionError` via `TryFrom`
2. Runs the on-chain cleanup using `UnmeteredGasMeter` — consuming no gas [2](#0-1) 

The `ExecutionError::try_from` implementation explicitly handles `VMStatus::Error { status_code: OUT_OF_GAS, .. }` as a valid `VMError` type, so the conversion succeeds and the cleanup path completes normally: [3](#0-2) 

The gas check in `check_gas` only enforces that `max_gas_amount` exceeds the intrinsic transaction cost (based on byte size), not the actual execution cost of the inner payload: [4](#0-3) 

Unlike EVM (where EIP-150 creates a 63/64 split), Aptos uses a single shared gas meter passed by mutable reference through the entire call chain. There is no gas-forwarding fraction — the same meter is depleted by the inner payload. Once it hits zero, the inner call fails with `OUT_OF_GAS`, but the outer cleanup path uses `UnmeteredGasMeter` and succeeds regardless. [5](#0-4) 

The `transaction_execution_cleanup_common` function then removes the executed transaction from the queue and advances `last_executed_sequence_number`, permanently consuming the proposal: [6](#0-5) 

### Impact Explanation

A malicious multisig owner who has (or can gather) the required approvals can:
1. Simulate the inner payload to learn its gas cost (e.g., 5,000 gas units)
2. Submit the execution transaction with `max_gas_amount` set just above the intrinsic minimum (e.g., 50 gas units) but far below what the inner payload needs
3. The inner payload fails with `OUT_OF_GAS`; the cleanup succeeds via `UnmeteredGasMeter`
4. The proposal is consumed — sequence number advances, the transaction is removed from the queue
5. The intended action (asset transfer, governance change, staking operation) never executes

Other owners must now create a new proposal and re-gather the required approvals. In a high-threshold multisig (e.g., 5-of-9), this is a significant coordination burden. The attacker can repeat this indefinitely, permanently blocking any proposal they can execute.

This directly impacts user-controlled on-chain assets (APT transfers, fungible asset operations, staking changes) that were the subject of the multisig proposal, and constitutes broken multisig logic under the allowed impact gate.

### Likelihood Explanation

- The attacker must be a multisig owner with sufficient approvals (or be the sole executor in a 1-of-N setup)
- Gas simulation is trivially available via the REST API (`/transactions/simulate`)
- Setting `max_gas_amount` to a low value is a standard transaction field — no special tooling required
- The attack is repeatable at low cost (only gas for the outer transaction is charged)

### Recommendation

1. **Do not treat `OUT_OF_GAS` as a tolerated inner-payload failure.** If the inner payload fails with `OUT_OF_GAS`, propagate it as a hard failure so the entire multisig transaction fails (and the proposal is not consumed). The executor must retry with sufficient gas.

2. Alternatively, **require a minimum gas reservation** before executing the inner payload. Before calling `execute_multisig_payload`, assert that `gas_meter.balance()` exceeds a configurable threshold sufficient to cover the expected inner execution cost.

3. At minimum, **document and emit a distinct error code** for `OUT_OF_GAS` inner failures so indexers and UIs can distinguish deliberate gas starvation from legitimate payload failures.

### Proof of Concept

**Setup:**
- Multisig account `M` with owners `[Alice, Bob]`, threshold 1
- Pending proposal #1: transfer 1000 APT from `M` to `Carol` (requires ~3,000 gas units to execute)

**Attack (Bob is malicious):**
```
1. Bob simulates the execution transaction → learns inner payload costs ~3,000 gas units
2. Bob submits a MultisigTransaction with:
     multisig_address = M
     payload = (transfer 1000 APT to Carol)
     max_gas_amount = 200   // above intrinsic minimum (~28), far below 3,000
3. VM executes:
     charge_intrinsic_and_surcharges(gas_meter, txn_data)  // ~28 gas, succeeds
     execute_multisig_payload(...)                          // exhausts remaining ~172 gas → OUT_OF_GAS
     failure_multisig_payload_cleanup(..., UnmeteredGasMeter)  // succeeds, advances seq_num
4. On-chain result: TransactionExecutionFailed event emitted
     execution_error = { error_type: "VMError", error_code: OUT_OF_GAS }
     last_executed_sequence_number += 1  // proposal #1 consumed
5. 1000 APT never transferred. Alice must create proposal #2 and re-approve.
6. Bob repeats step 2 for proposal #2. Indefinitely.
```

The key invariant broken: `execute_multisig_transaction` must not allow the executor to consume a proposal without giving the inner payload a fair opportunity to succeed. The executor's control over `max_gas_amount` combined with the unconditional tolerance of `OUT_OF_GAS` as a "normal" failure violates this invariant. [7](#0-6) [8](#0-7)

        &self,
        resolver: &impl AptosMoveResolver,
        code_storage: &impl AptosCodeStorage,
        mut session: UserSession,
        gas_meter: &mut impl AptosGasMeter,
        traversal_context: &mut TraversalContext,
        multisig_address: AccountAddress,
        payload: &MultisigTransactionPayload,
        change_set_configs: &ChangeSetConfigs,
        trace_recorder: &mut impl TraceRecorder,
    ) -> Result<UserSessionChangeSet, VMStatus> {
        let serialized_signers =
            SerializedSigners::new(vec![serialized_signer(&multisig_address)], None);

        // If txn args are not valid, we'd still consider the transaction as executed but
        // failed. This is primarily because it's unrecoverable at this point.

            MultisigTransactionPayload::EntryFunction(entry_function) => self
                .validate_and_execute_entry_function(
                    code_storage,
                    session,
                    &serialized_signers,
                    gas_meter,
                    traversal_context,
                    entry_function,
                    trace_recorder,
                ),
            MultisigTransactionPayload::Script(script) => self.validate_and_execute_script(
                session,
                &serialized_signers,
                code_storage,
                gas_meter,
                traversal_context,
                script,
                trace_recorder,
            ),
        })?;

impl TryFrom<VMStatus> for ExecutionError {
    type Error = anyhow::Error;

    fn try_from(status: VMStatus) -> anyhow::Result<ExecutionError> {
        match status {
            VMStatus::Error {
                status_code: error, ..
            } => Ok(ExecutionError {
                error_type: String::from("VMError"),
                abort_location: String::from(""),
                error_code: error as u64,
            }),
            VMStatus::MoveAbort {
                location: abort_location,
                code: error_code,
                // Note that we ignore the message here because ExecutionError has to be serialized
                // for multisig transactions and the serialization is not expected to fail.
                message: _,
            } => Ok(ExecutionError {
                error_type: String::from("MoveAbort"),
                abort_location: format!("{:?}", abort_location),
                error_code,
            }),
            VMStatus::ExecutionFailure {
                status_code,
                location,
                function: _,
                code_offset: _,
                message: _,
                sub_status: _,
            } => Ok(ExecutionError {
                error_type: String::from("MoveExecutionFailure"),
                abort_location: format!("{:?}", location),
                error_code: status_code as u64,
            }),
            _ => Err(anyhow::anyhow!(
                "Unknown error from vm status cannot be converted into `ExecutionError`: {:?}",
                status
            )),
        }
    }

    inline fun transaction_execution_cleanup_common(executor: address, multisig_account: address): u64 {
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        let implicit_approval = !has_voted_for_approval(multisig_account, sequence_number, executor);

        let multisig_account_resource = borrow_global_mut<MultisigAccount>(multisig_account);
        let (num_approvals, _) = remove_executed_transaction(multisig_account_resource);

        if (features::multisig_v2_enhancement_feature_enabled() && implicit_approval) {
            emit(
                Vote {
                    multisig_account,
                    owner: executor,
                    sequence_number,
                    approved: true,
                }
            );
            num_approvals += 1;
        };

        num_approvals
    }

    // Remove the next transaction in the queue as it's been executed and return the number of approvals it had.
    fun remove_executed_transaction(multisig_account_resource: &mut MultisigAccount): (u64, u64) {
        let sequence_number = multisig_account_resource.last_executed_sequence_number + 1;
        let transaction = multisig_account_resource.transactions.remove(sequence_number);
        multisig_account_resource.last_executed_sequence_number = sequence_number;
        num_approvals_and_rejections_internal(&multisig_account_resource.owners, &transaction)
    }
