### Title
Hardcoded, unvalidated global contract hash used for ETH-implicit account creation can permanently brick funded accounts - (File: `runtime/near-wallet-contract/src/lib.rs`)

### Summary
`eth_wallet_global_contract_hash` returns a hardcoded, compile-time-pinned `CryptoHash` for each chain that is directly assigned as the `AccountContract::Global` reference of every newly created ETH-implicit account, with no check that a global contract with that exact hash actually exists in the trie. This mirrors the RollerUtils bug class: a hardcoded external reference (there, the Divider address; here, a global-contract code hash) that is trusted blindly at a security-critical point, with no on-chain validation and no fallback, so any drift between the hardcoded value and reality permanently bricks the dependent object.

### Finding Description
`eth_wallet_global_contract_hash` hardcodes literal byte arrays for mainnet/testnet as the code hash of the shared Wallet Contract global contract: [1](#0-0) 

This value is consumed directly, unchecked, in the implicit-account-creation path that runs whenever an ordinary user sends any `Transfer` action to an ETH-implicit account id (any client can trigger this with a plain `send_money`): [2](#0-1) 

Contrast this with the explicit `UseGlobalContract` action handler, which *does* validate that the referenced global contract exists before wiring it up, and returns `GlobalContractDoesNotExist` otherwise: [3](#0-2) 

No equivalent check exists in `action_implicit_account_creation_transfer`. If `eth_wallet_global_contract_hash(chain_id)` does not correspond to an actually-deployed global contract for that `chain_id` (e.g., stale hash after a wallet-contract redeploy/upgrade was not reflected here, or a chain running on a `chain_id` string that doesn't hit the explicit `MAINNET`/`TESTNET` match arms and falls through to the `_` branch using `LOCALNET`'s hash while some other contract is actually the deployed global one), the newly created account is left with `AccountContract::Global(<hash>)` pointing at nonexistent state.

Once created, an ETH-implicit account can never be repaired: it cannot receive a `FullAccess` key and cannot be deleted (only usable through the Wallet Contract's own methods), per the documented account model: [4](#0-3) 

Any attempt to resolve/execute the contract for such an account will fail to find code in the trie (the runtime relies on the same hash for contract resolution at execution and view time, e.g. `RuntimeContractIdentifier::resolve`/`view_account_contract_code`), so the deposit made during account creation (the funds attached to the triggering `Transfer`) becomes permanently unreachable. [5](#0-4) [6](#0-5) 

### Impact Explanation
A mismatch between this hardcoded hash and the actually deployed global Wallet Contract permanently freezes any funds sent to newly created ETH-implicit accounts network-wide, and the accounts themselves become unusable forever since they lack the recovery mechanisms available to normal accounts (no full-access key can be added, no deletion). This is reachable by any ordinary user simply transferring NEAR to an `0x...` address, requiring no special privileges.

### Likelihood Explanation
The path is triggered unconditionally by ordinary transfers under `EthImplicitGlobalContract` (protocol feature active by v83, part of the base v86 protocol per the accounts-keys spec). The value is a manually maintained literal constant with no runtime cross-check against deployed state, so any future re-deployment of the wallet contract, hash miscalculation, or chain-id branch mismatch (`_ => *LOCALNET.read_contract().hash()`) silently produces broken accounts rather than a loud failure — the same "no validation of a hardcoded external reference" pattern flagged in the source Divider bug report.

### Recommendation
- Validate, at account-creation time (or at least in CI/genesis tooling), that `eth_wallet_global_contract_hash(chain_id)` corresponds to a global contract that is actually deployed on that chain before relying on it, mirroring the existence check already performed in `use_global_contract`.
- Prefer deriving/storing this hash from a single source of truth deployed alongside the protocol upgrade (e.g., a runtime-config or genesis-recorded value) instead of a hand-maintained literal in source code, and add a startup/sanity check that panics loudly if the hardcoded hash has no corresponding global contract in state, rather than allowing silent creation of unusable accounts.

### Proof of Concept
1. Suppose the wallet-contract WASM is rebuilt/redeployed as the mainnet global contract but the literal bytes in `eth_wallet_global_contract_hash`'s `chains::MAINNET` arm are not updated to match the new hash (a manual, unenforced synchronization step).
2. Any user sends a plain `Transfer` action to a new ETH-implicit account id, e.g. via `SignedTransaction::send_money` as shown in the existing test flow: [7](#0-6) 
3. `action_implicit_account_creation_transfer` creates the account with `AccountContract::Global(stale_hash)` unconditionally (`runtime/runtime/src/actions.rs:247-261`), with no existence check.
4. Any subsequent `rlp_execute` call, or a view-call for the account's contract code, fails to resolve code (`NoContractCode`/`NoGlobalContractCode`), and because ETH-implicit accounts cannot receive full-access keys or be deleted, the account and its deposited balance are permanently stuck.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }

    pub fn view_account_contract_code(
        &self,
        state_update: &TrieUpdate,
        account_id: &AccountId,
        current_protocol_version: ProtocolVersion,
        chain_id: &str,
    ) -> Result<ContractCode, errors::ViewContractCodeError> {
        assert_supported_protocol_version(current_protocol_version);
        let account = self.view_account(state_update, account_id)?;
        let contract_id = RuntimeContractIdentifier::resolve(
            account_id,
            account.contract().into_owned(),
            state_update,
            chain_id,
            AccessOptions::DEFAULT,
        )?;
        let maybe_code = match contract_id {
            RuntimeContractIdentifier::None => None,
            RuntimeContractIdentifier::AccountLocal { code_hash, account_id } => {
                let key = near_primitives::trie_key::TrieKey::ContractCode { account_id };
                let code = state_update.get(&key, AccessOptions::DEFAULT)?;
                code.map(|c| ContractCode::new(c, Some(code_hash)))
            }
            RuntimeContractIdentifier::Global { identifier, .. } => {
                identifier.code(state_update)?
            }
        };
        maybe_code.ok_or_else(|| errors::ViewContractCodeError::NoContractCode {
            contract_account_id: account_id.clone(),
        })
    }
