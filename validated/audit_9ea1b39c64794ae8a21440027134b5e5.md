## Title
`FetchIntoObjectPool` merges all references from an arbitrary caller-supplied origin repository into the pool without verifying pool membership - ([File: internal/gitaly/service/objectpool/fetch_into_object_pool.go])

## Summary
The Sherlock report describes `MarginTrading._openTrade` depositing the entire contract balance into Aave instead of only the funds acquired by the trade, because the code fails to distinguish "funds that should stay separate" from "funds that are part of this specific operation." The analogous flaw in gitaly is that `FetchIntoObjectPool` merges *all* refs/objects of an arbitrary, caller-controlled `origin` repository into an object pool without verifying that `origin` is actually a linked member of that pool - conflating "objects that legitimately belong in the shared pool" with "objects from any repository the caller happens to name."

## Finding Description
`FetchIntoObjectPool` is a `MUTATOR` RPC whose only structural validation is `validateFetchIntoObjectPoolRequest`, which checks that the request fields are set, not that `origin` is an actual member of `object_pool`: [1](#0-0) 

`FetchFromOrigin` then unconditionally fetches with `+refs/*:refs/remotes/origin/*` from whatever path `origin` resolves to, directly into the pool's live object database, and the fetched objects become permanently reachable through the pool's dangling-ref preservation mechanism: [2](#0-1) [3](#0-2) 

The documentation itself only states this is "typically" done from the primary pool member — there is no server-side enforcement of that expectation: [4](#0-3) 

Just as `MarginTrading._openTrade` failed to separate "funds acquired by the swap" from "funds that should remain untouched," `FetchIntoObjectPool` fails to separate "objects belonging to a legitimate pool member" from "objects of any repository named in the RPC field." Any caller who can invoke `FetchIntoObjectPool` (a normal, unprivileged operation used as part of GitLab's fork/housekeeping flow) can pass an unrelated repository as `origin` and pass a pool they control as `object_pool`, causing that unrelated repository's full object graph to be merged into the pool's shared object database.

## Impact Explanation
Once objects are fetched into the pool, they become reachable via `refs/remotes/origin/*` (and, if unreferenced later, via `refs/dangling/$OID`) in the pool repository, per the pool's dangling-object preservation design: [5](#0-4) 

Since **all repositories linked to that pool** share objects with the pool through alternates (`objects/info/alternates`), any objects pulled in from an unrelated `origin` become visible/fetchable to every other member of the pool. This is a cross-repository object disclosure: private commits/blobs of one repository could be exposed to unrelated pool members that have no legitimate relationship to the `origin` repository, purely by naming it in the `origin` field of a `FetchIntoObjectPoolRequest`.

## Likelihood Explanation
`FetchIntoObjectPool` is a normal RPC in `ObjectPoolService`, reachable by any client permitted to operate object pools (used by GitLab in the fork lifecycle). The request only requires two repository references the caller already has some access to — an existing pool they administer and any other repository path they can address — with no server-side check tying the two together via alternates/membership before performing the fetch.

## Recommendation
Before performing the fetch in `FetchFromOrigin`/`FetchIntoObjectPool`, verify that `origin` is actually a linked member of `object_pool` (e.g., check that `origin`'s `objects/info/alternates` points at the target pool, mirroring the check already used in `linkedToRepository`) and reject the RPC otherwise: [6](#0-5) 

## Proof of Concept
1. Attacker creates (or owns) object pool `P` and links a throwaway repository `M` to it via `LinkRepositoryToObjectPool`.
2. Attacker calls `FetchIntoObjectPool{ ObjectPool: P, Origin: V }`, where `V` is any other repository the attacker can merely reference (e.g., a private/internal repository whose relative path is known/guessable, or one temporarily accessible to the attacker).
3. `FetchFromOrigin` executes `git fetch <V-path> +refs/*:refs/remotes/origin/*` directly into `P`'s live object database with no membership check.
4. Objects from `V` are now stored in pool `P` and become reachable (via alternates) to any other repository linked to `P`, disclosing `V`'s object contents outside its own access boundary.

```go
	}); err != nil {

	}
```

```markdown
## Dangling Objects

When fetching from pool members into the object pool, then any force-updated
references may cause objects in the pool to not be referenced anymore. For
normal repositories, it is perfectly fine to delete those references after a
certain time. In the context of object pools, any other member of the pool may
still use any of those unreferenced objects. Deleting them would thus
potentially cause corrupt repositories.

This issue is kind of unsolvable: there is no point in time where it's safe to
delete objects from the object pool, as we do not know which repositories may be
linked to it. And even if we knew, we cannot determine all references of all
repositories at once in a race-free manner. We thus must consider each object to
still be referenced somewhere.

As a safeguard to not lose any objects by accident, we thus create dangling
references in the object pool after the fetch in `FetchIntoObjectPool`. For each
dangling object, a reference `refs/dangling/$OID` is created which points into
the object. This assures that each object is still referenced.
```

```go
// linkedToRepository tests if a repository is linked to an object pool
func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
}
```
