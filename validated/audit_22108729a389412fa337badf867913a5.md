Based on my investigation, I found a concrete local analog to the reported bug class, but I must flag an important limitation up front: the Solidity Gateway contract that processes `Command::RegisterForeignToken` on the Ethereum side is not present/indexed in this repository (no matches for `registerForeignToken` in any `.sol` or other Ethereum-side code), so I cannot verify from repo evidence whether the receiving contract itself deduplicates or rejects re-registration of an already-known `foreignTokenID`. The Substrate-side analog below is fully verifiable, however, and reproduces exactly the "no duplicate check → overwrite of existing entry's info" pattern from the seed report.

### Title
`register_token` re-dispatches `RegisterForeignToken` with new metadata for already-registered tokens without any duplicate check - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

### Summary
Both `snowbridge-pallet-system::register_token` and `snowbridge-pallet-system-v2::register_token` derive a `token_id` from the asset `Location` and check `ForeignToNativeId::contains_key` only to decide whether to **insert the storage mapping**. They do not use that check to prevent **re-sending** the `Command::RegisterForeignToken` message with new, caller-supplied `name`/`symbol`/`decimals` for a token that is already registered.

### Finding Description
In `snowbridge-pallet-system-v2`, `register_token` is gated by `T::FrontendOrigin` (fed by the `snowbridge-pallet-system-frontend` pallet, whose `RegisterTokenOrigin` allows any local/foreign **asset owner** — not root, not governance — to invoke it, per `cumulus/parachains/runtimes/assets/asset-hub-westend/src/bridge_to_ethereum_config.rs:50-71`). The core logic is: [1](#0-0) 

The guard `if !ForeignToNativeId::<T>::contains_key(token_id) { insert(...) }` only prevents the storage map value from being overwritten. It does **not** gate the subsequent `Command::RegisterForeignToken { token_id, name, symbol, decimals }` construction and `Self::send(...)` call, which happens unconditionally on every invocation, using whatever `metadata` the caller passes in this call.

The identical pattern exists in the root-gated `snowbridge-pallet-system::do_register_token`: [2](#0-1) 

Because `token_id` is derived deterministically from the `Location` (via `TokenIdOf::convert_location`), the asset owner can call `register_token` any number of times for the same asset with different `metadata.name` / `metadata.symbol` / `metadata.decimals`, and each call successfully constructs and dispatches a fresh `RegisterForeignToken` command to the Ethereum Gateway for the same `token_id` — this is the direct analog of `addSupportedToken()` having "no check if the added token is already on the list" and being able to "rewrite the info about the current token."

### Impact Explanation
If the Ethereum Gateway contract processes `RegisterForeignToken` idempotently by `foreignTokenID` (i.e., updates/overwrites the ERC20 token's recorded name/symbol/decimals whenever the command is received, rather than reverting for an already-known ID), then any asset owner can silently change the displayed name/symbol/decimals of an already-bridged, already-circulating wrapped token on Ethereum after the fact — a form of unauthorized state mutation of bridge-side token metadata that could be used to spoof or rebrand an existing token users already hold/trade, undermining "duplicate settlement" and "message queue/bridge marker state must only advance once" invariants for the register-token flow. I could not confirm the Ethereum-side contract behavior from this repository's indexed content, so the practical severity depends on that unverified contract logic.

### Likelihood Explanation
The call path is reachable by any account that is recognized as owner of a local or foreign asset (`LocalAssetOwner`/`ForeignAssetOwner` in `bridge_to_ethereum_config.rs`), which is an ordinary, non-privileged capability, not an admin/governance action. No special conditions (malicious relayer, validator, or leaked keys) are required — a normal asset owner calling `register_token` twice with different metadata is sufficient to trigger the duplicate dispatch.

### Recommendation
In `do_register_token` (`bridges/snowbridge/pallets/system/src/lib.rs`) and `register_token` (`bridges/snowbridge/pallets/system-v2/src/lib.rs`), gate the entire registration path (not just the storage insert) on `!ForeignToNativeId::<T>::contains_key(token_id)`, returning an explicit `Error::<T>::TokenAlreadyRegistered` (or similar) if the token is already registered, so `Command::RegisterForeignToken` can never be re-sent for an existing `token_id` with different metadata.

### Proof of Concept
1. As asset owner, call `EthereumSystemFrontend::register_token(origin, asset_id, metadata_A, fee_asset)` — this is proxied to BridgeHub's `EthereumSystemV2::register_token`, which inserts `ForeignToNativeId[token_id] = location` and dispatches `Command::RegisterForeignToken { token_id, name: "TokenA", symbol: "TKA", decimals: 18 }` (see `bridges/snowbridge/pallets/system-v2/src/lib.rs:211-249`).
2. As the same asset owner, call `register_token` again for the identical `asset_id` with `metadata_B = { name: "FakeToken", symbol: "FAKE", decimals: 6 }`.
3. The `contains_key` check passes (skips only the storage `insert`), but the function proceeds to build and dispatch a second `Command::RegisterForeignToken` with the same `token_id` but `metadata_B`, exactly reproducing the reported "call the function again with the same identifier and rewrite the info" pattern — confirmed at `bridges/snowbridge/pallets/system-v2/src/lib.rs:225-241`.
