Audit Report

## Title
`do_reschedule`/`do_reschedule_named` leave a stale `Retries` entry at the vacated `(when, index)` slot, which is silently inherited by a new task that fills the reused hole - (File: substrate/frame/scheduler/src/lib.rs)

## Summary
`Retries<T>` is keyed by the `(when, index)` slot address, and both `do_cancel` and `do_cancel_named` correctly clear that entry via `Retries::<T>::remove((when, index))` when a task is removed. `do_reschedule` and `do_reschedule_named` move a task from `(when, index)` to a new `(new_time, new_index)` slot without ever removing or transferring the old `Retries` entry, so the vacated slot's stale retry config remains in storage.

## Finding Description
In `do_reschedule` (lines 1100-1119), the task is taken out of `Agenda::<T>::get(when)[index]`, `cleanup_agenda(when)` is called, and the task is re-inserted via `place_task` at a new address — but there is no `Retries::<T>::remove((when, index))` call, unlike the parallel logic in `do_cancel` at line 1091. The same omission exists in `do_reschedule_named` (lines 1186-1206) compared to `do_cancel_named`'s `Retries::<T>::remove((when, index))` at line 1170. Since `cleanup_agenda` only truncates trailing `None` entries and otherwise leaves a `None` hole at `index`, and `push_to_agenda` explicitly searches for and reuses the first `None` hole for new tasks, a subsequently scheduled unrelated task can land at the exact same `(when, index)` slot and inherit the leftover `Retries` entry the first time it fails and the runtime looks up `Retries::<T>::get((when, index))` for retry handling.

## Impact Explanation
This is a genuine state-integrity bug in `pallet-scheduler`, reachable through the pallet's normal public dispatchables (`reschedule`/`reschedule_named` followed by `schedule`/`schedule_named`), without requiring any exploit of privileged escalation beyond whatever origin is normally required to call these scheduler extrinsics. It can cause a newly scheduled, unrelated task to inherit a stale retry budget/period it was never configured with, corrupting retry-count/period accounting for scheduled dispatches (e.g. governance-enacted or treasury-scheduled calls), matching the "runtime bugs that compromise intended behavior" impact category for `pallet-scheduler`.

## Likelihood Explanation
The bug requires (1) a task with `set_retry`/`set_retry_named` configured, (2) that task rescheduled via `reschedule`/`reschedule_named`, and (3) a new task scheduled into the exact vacated `(when, index)` slot before block `when` is reached. Since `push_to_agenda` deterministically fills the first available hole, an actor who controls scheduling order at the affected block can reliably arrange this collision, making it a repeatable, moderate-likelihood condition.

## Recommendation
In both `do_reschedule` and `do_reschedule_named`, explicitly handle the stale retry state for the vacated `(when, index)` before/while moving the task — either transfer it to the new slot (`if let Some(retry) = Retries::<T>::take((when, index)) { Retries::<T>::insert((new_time, new_index), retry); }`) or, at minimum, call `Retries::<T>::remove((when, index))` to prevent leakage to a reused slot.

## Proof of Concept
1. Schedule a named task `task_a` at block 10 via `Scheduler::schedule_named` and configure retries via `Scheduler::set_retry_named(id_a, retries=5, period=2)`, so `Retries::<Test>::get((10, 0)) == Some(RetryConfig{ remaining: 5, period: 2, .. })`.
2. Schedule a second task `task_b` at block 10 so the agenda has length 2.
3. Call `Scheduler::reschedule_named(id_a, DispatchTime::At(20))`. This moves `task_a` to `(20, k)`, leaving `Agenda::<Test>::get(10)[0] == None` (since index 1 is still `Some`, `cleanup_agenda` does not truncate). `Retries::<Test>::get((10, 0))` remains `Some(...)`.
4. Schedule a new unrelated `task_c` at block 10; `push_to_agenda` fills the hole at index 0, giving `task_c` the address `(10, 0)`.
5. Run to block 10 and force `task_c` to fail dispatch. The scheduler's retry-check path reads `Retries::<Test>::get((10, 0))`, finds the leftover `RetryConfig` from `task_a`, and retries `task_c` with a budget/period it was never given — demonstrating the cross-task state leak.
