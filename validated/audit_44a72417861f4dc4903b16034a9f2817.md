### Title
PostReceiveHook notifies GitLab Rails via external HTTP call before waiting for Praefect's post-transaction completion signal - ([File: internal/gitaly/hook/postreceive.go])

### Summary
Gitaly implements a `PostReceiveRegistry` / `SignalPostReceiveReady` mechanism specifically to fix a race where "Rails is notified before all Gitaly replicas have applied the write and before Praefect has updated its database for routing decisions" [1](#0-0) . This is architecturally the same bug class as the reported `GMXWithdraw.processWithdraw` issue: an externally-observable, side-effecting call is made before the internal state that the external party relies on has actually been finalized/committed.

### Finding Description
`GitLabHookManager.PostReceiveHook` is the code path invoked for every push (both direct `git-receive-pack` pushes and `OperationService` RPCs) once references have been updated. For the primary node it calls `m.postReceiveHook(...)`, which performs the external, irreversible action of notifying GitLab Rails via `m.gitlabClient.PostReceive(...)` (an HTTP POST to `/post_receive`) — this call triggers downstream business logic in Rails such as decrementing push counters, firing webhooks, CI pipeline creation, and merge-request update notifications: [2](#0-1) [3](#0-2) 

Only *after* this external call returns does the function invoke `m.synchronizeHookExecution(ctx, payload, "post-receive")`: [4](#0-3) 

The `PostReceiveRegistry` doc comments make clear the intended invariant: the hook is supposed to `waitForPraefectSignal` — i.e., block until Praefect has confirmed it "completed transaction coordination (DB write + replication job queuing)" — *before* calling Rails, precisely to prevent Rails from acting on a write that other Gitaly replicas/Praefect's routing DB do not yet reflect: [5](#0-4) [6](#0-5) 

However, in the code path actually read (`internal/gitaly/hook/postreceive.go`), the Rails-notifying call happens in the `isPrimary(payload)` branch (lines 194–206) which executes *before* `synchronizeHookExecution` (line 208). The `waitForPraefectSignal`/registry-based blocking logic is defined in `internal/gitaly/hook/transactions.go`, but is not visibly invoked from inside `postReceiveHook` prior to the `gitlabClient.PostReceive` call in the code I was able to inspect. This mirrors the audited bug exactly: the state-changing/consistency-dependent step (waiting for confirmation that the write is durable and routable cluster-wide) is ordered *after* the externally observable side effect (notifying Rails) rather than before it.

### Impact Explanation
If Rails is notified of a completed push before Praefect has finished updating its routing database and before all secondaries have durably applied the write, any Rails-triggered follow-up Gitaly RPC (e.g., CI pipeline reads, `IsAncestor` checks, diff generation for merge requests, webhook payload construction) can be routed to a Gitaly replica that has not yet applied the change, or Praefect could route to a stale replica since its DB hasn't been updated. This can result in transient inconsistent reads, incorrect pipeline/MR state, or (per the code's own comment) exactly the "race condition" the fix was designed to prevent — pushed changes acted upon before they are consistently visible across the cluster. This is reachable by any ordinary authenticated user performing a normal push through Praefect-fronted Gitaly, without any special privilege.

### Likelihood Explanation
This is reachable on every push (`git push` via SSH/HTTP or any OperationService RPC) that goes through a Praefect-managed (HA) Gitaly cluster — no crafted or malicious input is required, only ordinary timing. The feature flag `praefect_post_receive_signal` is disabled by default (`false`) per `ff_praefect_post_receive_signal.go`, meaning the intended fix's wait-for-signal blocking is presumably not fully engaged in default configurations, but I was not able to fully trace `transactions.go`'s exact call-site relative to `postReceiveHook` within the available tool budget, so it is uncertain whether `waitForPraefectSignal` is actually gated to run before the Rails call under any configuration, or whether it is simply unreachable in the code as currently wired. This should be verified directly in `internal/gitaly/hook/transactions.go` and `internal/gitaly/hook/manager.go` to confirm whether `waitForPraefectSignal` is called prior to `m.postReceiveHook`'s Rails notification or only as part of `synchronizeHookExecution` afterward.

### Recommendation
Ensure `waitForPraefectSignal` (registration with `PostReceiveRegistry` and blocking until `SignalPostReceiveReady` fires, or timeout) executes and completes *before* `m.postReceiveHook` calls `m.gitlabClient.PostReceive`, for both the feature-flag-enabled and default paths. If the flag is meant to gate this behavior, ensure the default is safe (i.e., either enable by default or ensure the fallback path cannot expose the race), and add a regression test that asserts `gitlabClient.PostReceive` is only invoked after a signal (or configured timeout) has been observed from `PostReceiveRegistry`.

### Proof of Concept
Unable to fully construct a runnable PoC without live access to a Praefect HA cluster and its DB update code, but the reachable trigger is: perform a normal `git push` against a GitLab instance using Praefect-managed Gitaly storage. Instrument/log timestamps around `m.gitlabClient.PostReceive` in `postreceive.go` and around Praefect's DB update after transaction commit; observe that the Rails-facing `/post_receive` call can complete before Praefect's DB write/replication-job enqueue finishes, particularly under load where DB writes/replication scheduling are slower than the local hook execution.

**File:** internal/gitaly/hook/postreceive_registry.go (L11-31)
```go
// PostReceiveRegistry coordinates PostReceiveHook execution with Praefect signaling.
// When Praefect transactions are active, the PostReceiveHook needs to wait for Praefect
// to signal that all replicas have completed and the database has been updated before
// calling Rails. This registry provides the synchronization mechanism.
//
// Signal and RegisterWaiter race, and Signal can arrive first. Both are driven off the
// same event — the transaction's committed phase concluding — but then run on
// independent paths:
//
//   - Praefect (async monitor): CommittedConcluded -> DB generation write -> backchannel
//     SignalPostReceiveReady RPC -> Signal.
//   - Primary Gitaly (the push): committed-phase vote returns -> git finishes the ref
//     update -> post-receive hook runs -> waitForPraefectSignal -> RegisterWaiter.
//
// The committed phase concludes at essentially the same instant on both sides, so if the
// signal path (which includes a DB round-trip and a network RPC) happens to complete
// before the primary reaches its post-receive hook — e.g. fast/local Postgres or
// single-node quorum — Signal is called before RegisterWaiter. To handle this, Signal
// buffers the result in `signaled` and RegisterWaiter returns a pre-populated channel if
// a signal is already waiting. This buffering is required for correctness: without it the
// hook would block until timeout whenever the signal wins the race.
```
