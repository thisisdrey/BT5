### Title
Unhandled `IndexOutOfBoundsException` in `getPriceKeysList` when a market pair has exactly one order — anonymous API DoS - (File: `chainbase/src/main/java/org/tron/core/store/MarketPairPriceToOrderStore.java`)

### Summary
`MarketPairPriceToOrderStore.getPriceKeysList` performs an unguarded `subList(1, limit+1)` call assuming that `getKeysNext` always returns at least `limit+1` elements once the head key exists. This mirrors the reported viem bug class (`getTimeToNextGame` crashing when a dispute-game list has zero or one entries): code that special-cases "at least 2 items expected" but does not defend against the boundary case of exactly one item in the underlying list.

### Finding Description
`getPriceKeysList(byte[] headKey, long count, long totalCount, boolean skip)` is implemented as: [1](#0-0) 

When `skip` is `true` (the default path used by the single-arg `getPriceKeysList(sellTokenId, buyTokenId, count)` overload used for public price queries), the code calls `getKeysNext(headKey, limit + 1)` and then unconditionally does `.subList(1, (int)(limit + 1))`. `getKeysNext` walks the underlying store from `headKey` and can legitimately return fewer than `limit + 1` entries — in particular exactly `1` entry when the market pair currently has only a single order still on the price-key index (e.g., after other orders in that pair have been fully filled/canceled while one remains). In that case `subList(1, limit+1)` on a size-1 list throws `IndexOutOfBoundsException`, since `subList` requires `toIndex <= list.size()`. [2](#0-1) 

This is reachable from `Wallet`/HTTP-JSON-RPC market price query endpoints (`GetMarketPriceByPairServlet` and its Solidity/PBFT variants), which take `sellTokenId`/`buyTokenId` as unauthenticated, unprivileged query parameters — i.e., any anonymous API client can trigger the query path for an arbitrary token pair.

### Impact Explanation
An uncaught `IndexOutOfBoundsException` propagating from a query-path method can crash the servicing thread/request; depending on how the HTTP/gRPC layer wraps store exceptions, this could manifest as a 500 error or, if not caught by the surrounding service dispatcher, destabilize node query serving for that pair going forward. This falls under "API the node can no longer serve" per the validation criteria, since the exchange/price query path becomes unusable for any token pair that transiently has exactly one live order.

### Likelihood Explanation
Reaching the single-order state is trivial in an active exchange: create two orders for a pair, then let/force one to be fully matched or canceled, leaving exactly one open order at the head key. Any external caller can then query `getMarketPriceByPair` for that pair, hitting the size-1 list and triggering the exception. This does not require special privileges, SR/witness status, or malicious peers — it only requires normal market order placement/cancellation activity plus an unauthenticated read query, matching the "anonymous API client" reachability requirement.

Note: I was not able to fully confirm within the available tool budget whether every caller catches and gracefully converts this exception before it reaches the client (i.e., whether some wrapper in `Wallet.java` or the HTTP filter layer already guards against `IndexOutOfBoundsException`), so the ultimate blast radius (crash vs. simple error response) should be verified in the actual runtime/service dispatch code before treating this as more than a Medium-severity denial-of-service-style API bug.

### Recommendation
Add a bounds check before calling `subList` in `getPriceKeysList`, e.g., clamp `toIndex` to `Math.min(limit + 1, result.size())`, and treat a list of size ≤ 1 (i.e., only the head key was found) as "no additional orders" returning an empty list, analogous to how the referenced fix handles zero/one dispute games.

### Proof of Concept
1. Create a token pair and place a single sell order such that `MarketPairPriceToOrderStore` has exactly one price key for that pair (`has(headKey)` is `true`, but only one entry exists at or after `headKey`).
2. Call the market price query API (`GetMarketPriceByPairServlet` / gRPC `getMarketPriceByPair`) for that `sellTokenId`/`buyTokenId` pair.
3. Internally this invokes `getPriceKeysList(sellTokenId, buyTokenId, count)` → `getPriceKeysList(headKey, count, count, true)` → `getKeysNext(headKey, count+1)` returns a 1-element list → `.subList(1, count+1)` throws `IndexOutOfBoundsException`. [3](#0-2)

  public List<byte[]> getPriceKeysList(byte[] headKey, long count, long totalCount, boolean skip) {

    if (has(headKey)) {
      long limit = count > totalCount ? totalCount : count;
      if (skip) {
        // need to get one more
