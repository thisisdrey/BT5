### Title
False StackerDB inventory acknowledged before the chunk write is actually committed - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches the `StackerDBChunkInv` reply to advertise that the local node "has" a newly pushed chunk version, and sends that reply back to the peer, *before* the chunk has actually been written to the local StackerDB. The real write happens later and asynchronously in `Relayer::process_stacker_db_chunks`, which can fail (e.g. `StaleChunk`, `TooManySlotWrites`, DB error) without ever correcting the inventory that was already advertised. This breaks the equality between "chunk version advertised as stored" and "chunk version actually committed," analogous to the Gearbox `totalValue` being incremented before the underlying transfer is confirmed to succeed.

### Finding Description
In `handle_unsolicited_StackerDBPushChunk`, the function only runs `validate_received_chunk()` (signature, staleness vs. `expected_versions`, size, max-writes) and then immediately patches the outgoing inventory vector: [1](#0-0) 

This patched `StackerDBChunkInv` is signed and sent straight back to the peer as a reply: [2](#0-1) 

Note the explicit comment that write-frequency is deliberately *not* checked here, and that this handler can run *during* an in-progress StackerDB sync: [3](#0-2) 

The actual storage of the chunk occurs later and separately, in `Relayer::process_stacker_db_chunks`, which calls `tx.try_replace_chunk()` and, on failure, simply logs and `continue`s — it never emits a corrective NACK or inventory update to the peer that was already told the write would succeed: [4](#0-3) 

`try_replace_chunk` in the underlying DB can fail for reasons not checked by `validate_received_chunk`'s snapshot of `expected_versions` (e.g. a concurrent write from a different peer that races ahead of this one, hitting `StaleChunk`), as demonstrated by the DB-level test: [5](#0-4) 

Because `data.slot_versions` used for the reply is captured from `make_StackerDBChunksInv_or_Nack` at the start of the handler and the two-phase flow (validate-then-ack vs. actually-store-later) is not atomic, a race between the ack and the real write is possible whenever chunk delivery/processing overlaps — which the code's own comments acknowledge ("this can happen *during* a StackerDB sync's execution").

### Impact Explanation
This causes the node to serve **non-canonical inventory as canonical**: a peer is told "I have slot X at version V" when the local replica may still hold the old version because the corresponding write later failed. Neighbors that trust this inventory will stop trying to push/re-send that chunk version to this node, silently breaking StackerDB gossip convergence for that slot until the next natural resync. This matches the High-impact category of "steering a node off the tip via false inventory" for the StackerDB gossip layer.

### Likelihood Explanation
The condition requires overlapping/concurrent chunk pushes for the same slot (e.g. two neighbors racing to push different versions, or a push arriving while a sync is mid-flight for the same DB) — plausible in normal unprivileged P2P operation and does not require holding any secret key; the write-frequency/staleness check is explicitly skipped by design in this handler, increasing the window for the mismatch to occur.

### Recommendation
Do not patch/advertise the inventory version as accepted until the corresponding `try_replace_chunk` (or equivalent write) has actually succeeded. Either (a) perform the write synchronously inside `handle_unsolicited_StackerDBPushChunk` before constructing the ack, or (b) defer sending the `StackerDBChunkInv` ack until `process_stacker_db_chunks` confirms the write, and send a corrective NACK/updated inventory if the deferred write fails.

### Proof of Concept
Not independently reproducible from static analysis alone within the given scope; the race requires two near-simultaneous `StackerDBPushChunk` messages for the same slot from different peers, timed so that the second passes `validate_received_chunk` (using the pre-write `expected_versions` snapshot) but loses the race in `try_replace_chunk` during `process_stacker_db_chunks`, as shown by the `StaleChunk` failure path exercised in `test_stackerdb_insert_query_chunks`. Full end-to-end reproduction would require running two peer connections against one node and would need to be validated on a live/test network by a Devin session with access to build/run the node.
