### Title
Owner/Active permission keys can be set to the empty/zero address, permanently locking account permissions - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateContract`, submitted by any account owner to change their multi-sig permissions, is validated by `AccountPermissionUpdateActuator.checkPermission()`, which only checks each key's address via `DecodeUtil.addressValid()`. [2](#0-1)  That check only validates length (21 bytes) and prefix byte, never that the address is non-zero. [1](#0-0)  This mirrors the reported InstaRegistry bug class: a front-end that leaves an address field blank (interpreted by many libraries/UIs as the zero address) would produce a technically well-formed but uncontrollable key address, and the chain would accept it.

### Finding Description
When a user calls `updateaccountpermission` (mapped to `AccountPermissionUpdateContract`), they supply new `Owner`, `Witness`, and `Active` permission structures, each containing a list of `Key{address, weight}` entries. `validate()` calls `checkPermission()` for the owner permission and each active permission. [3](#0-2)  Inside `checkPermission`, keys are checked for distinctness, positive weight, and address validity via `DecodeUtil.addressValid`, but there is no check that a key's address is not the all-zero/empty address (`0x41` + 20 zero bytes), which passes `addressValid` since it has the correct length and prefix. [4](#0-3)  If the owner permission's sole/controlling key(s) end up bound to this zero address (e.g., a wallet/dApp defaulted a missing "new key" input field to the zero address, or a user copy-pasted an empty field), `execute()` unconditionally calls `account.updatePermissions(...)`, overwriting the account's owner permission with the attacker/mistake-controlled structure. [5](#0-4)  `AccountCapsule.updatePermissions` directly replaces the owner permission and active permissions with whatever was submitted, with no additional safety check. [6](#0-5)  Notably, the codebase itself treats the zero address as a deliberate "burn" pattern for the blackhole account's owner permission, confirming that setting owner permission to the zero address is a recognized way to permanently disable an account's controllable owner permission. [7](#0-6) 

### Impact Explanation
If an account's Owner permission (and/or all Active permissions) end up keyed solely to the zero address, no one holds the corresponding private key, so the account can never again satisfy the owner-permission threshold. Depending on which permissions are affected, this can permanently freeze the account's ability to reconfigure permissions, vote, or (if active permissions covering transfers are also zeroed) move funds — a permanent freezing-of-funds condition reachable purely from a single signed transaction crafted (even accidentally, mirroring the reported UX bug class) by the account owner, with no code path to recover since there is no "reset permission" actuator for normal accounts.

### Likelihood Explanation
Likelihood is driven by front-end/tooling behavior exactly as described in the original report: any wallet, SDK, or dApp that defaults a missing/blank address field to `0x0000...0000` (or an all-zero 21-byte buffer with the Tron prefix) when constructing `Key.address` for `AccountPermissionUpdateContract` will produce a transaction that java-tron's actuator fully accepts, since `addressValid` never rejects the zero pattern. No special privileges beyond normal transaction signing are required.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, explicitly reject the all-zero address for any `Key.address` (and optionally reject it as `ownerAddress` in `validate()` if not already effectively excluded by account existence checks), e.g. compare against a constant zero-filled 21-byte array (with correct prefix) in addition to the existing `DecodeUtil.addressValid` call, so that accidental (non-blackhole) permission updates cannot silently bind control to an unusable address.

### Proof of Concept
1. Attacker/careless owner of account `A` (already existing, normal account) submits `AccountPermissionUpdateContract` with `owner_address = A`.
2. The `Owner` permission's `Key` list contains a single entry: `address = 0x41 + 20×0x00`, `weight = 1`, `threshold = 1`.
3. `Active` permission list similarly could reuse `A`'s own key or also be zeroed depending on the specific mistake.
4. `AccountPermissionUpdateActuator.validate()` passes: `addressValid` succeeds for the zero-filled 21-byte key address, weight/threshold checks pass. [8](#0-7) 
5. `execute()` commits `updatePermissions`, replacing `A`'s owner permission with the zero-address-keyed permission. [5](#0-4) 
6. Account `A`'s owner permission can never again be satisfied by any real key, permanently locking that permission tier.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
