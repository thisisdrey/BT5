### Title
HTTP Request-Smuggling-Class Ambiguity: `Transfer-Encoding` Header Silently Ignored on Requests, Framing Decided Solely by `Content-Length` - ([File: stackslib/src/net/http/request.rs])

### Summary
The `webrick` advisory (CVE-2024-47220) is a classic CL/TE request-smuggling bug: the parser accepts a request containing both a `Content-Length` and a `Transfer-Encoding` header, letting an intermediary and the backend disagree about where the request ends. In `stackslib`'s HTTP request preamble parser, the same class of ambiguity exists: `HttpRequestPreamble::consensus_deserialize` explicitly recognizes and validates `host`, `content-type`, `content-length`, `connection`, and `set-cookie`, but has no case for `transfer-encoding` at all — it silently falls into the generic header bucket and is never rejected, never inspected, and never used to determine framing. [1](#0-0) 

### Finding Description
For HTTP responses, the codec explicitly guards against exactly this ambiguity: if both `Content-Length` and `Transfer-Encoding: chunked` are present, deserialization fails with `"Invalid HTTP response: incompatible transfer-encoding and content-length"`. [2](#0-1) 

No equivalent check exists on the request-parsing path. In `HttpRequestPreamble::consensus_deserialize`, the header loop matches `"host"`, `"content-type"`, `"content-length"`, `"connection"`, `"set-cookie"`, and otherwise stores the header verbatim into a generic `BTreeMap`: [1](#0-0) 

Downstream, `payload_len()` for a `StacksHttpPreamble::Request` always derives the body length purely from `get_content_length()`, irrespective of any `Transfer-Encoding` header that may also be present: [3](#0-2) 

And `stream_payload()` explicitly states requests are never chunk-decoded — the request path only ever consults `Content-Length`: [4](#0-3) 

This means an attacker can send a Stacks node RPC request carrying both `Content-Length: X` and `Transfer-Encoding: chunked` headers. `stacks-core` will silently accept the request (no rejection, unlike the symmetric response-side check) and frame the body strictly by `Content-Length`. If such a node sits behind (or is proxied through) any front-end/load balancer/reverse-proxy that instead honors `Transfer-Encoding` (as most HTTP intermediaries do per RFC 7230 §3.3.3, which mandates TE takes precedence over CL when both are present), the two hops will disagree on where the request body ends — enabling classic TE.CL request smuggling of a second, attacker-smuggled request into the RPC/StackerDB pipeline behind the victim's own connection reuse (`keep_alive` is honored by this codec: [5](#0-4) ).

### Impact Explanation
Request smuggling against a node's `/v2/...` RPC endpoints (including the `StackerDB` write path `poststackerdbchunk.rs`, which itself trusts `Content-Length` to bound the body it feeds into `serde_json::from_slice`: [6](#0-5) ) could let an attacker smuggle a hidden, attacker-chosen request that is executed under the guise of another client's connection when this node is deployed behind any HTTP-aware proxy/load-balancer that itself parses `Transfer-Encoding`. This is a request-smuggling / auth-bypass-class primitive matching the "Critical" bucket definition in scope (request smuggling or auth bypass) if a proxy is present, though the severity is contingent on deployment topology (presence of a front-end proxy that disagrees on framing).

### Likelihood Explanation
Likelihood is moderate: it requires the Stacks node's RPC/P2P HTTP endpoint to be fronted by a proxy or load balancer (a common production topology for node operators, unlike the raw peer-to-peer link) that honors `Transfer-Encoding` over `Content-Length`. No authentication or privileged position is required from the attacker — only the ability to send an HTTP request that traverses such an intermediary to the node's HTTP listener.

### Recommendation
Mirror the response-parser's guard on the request-parsing path in `HttpRequestPreamble::consensus_deserialize`: explicitly detect a `Transfer-Encoding` header and (a) reject the request outright, or (b) reject it when combined with a `Content-Length` header, exactly as already done for responses at `stackslib/src/net/http/response.rs:561-580`. At minimum, the request-parser should never silently swallow `Transfer-Encoding` into the "other headers" bucket without evaluating it against RFC 7230 framing rules.

### Proof of Concept
A conceptual crafted request (would need to be sent through the vulnerable path to a front-end/backend pair with differing precedence rules):
```
POST /v2/stackerdb/<addr>/<contract>/chunks HTTP/1.1
Host: <victim-node>
Content-Length: 4
Transfer-Encoding: chunked

0

POST /v2/transactions HTTP/1.1
...smuggled request...
```
`stackslib`'s parser accepts this without error (no rejection code path exists for the CL+TE combination on requests, confirmed at `stackslib/src/net/http/request.rs:381-422`), and frames the body by `Content-Length: 4` alone via `payload_len()`. Any front-end that instead honors the `Transfer-Encoding: chunked` chunk terminator (`0\r\n\r\n`) will treat the remainder as the start of a new smuggled request, splitting the two hops' view of the request stream.
