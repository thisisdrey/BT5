### Title
Unbounded memory allocation in `CheckAttrCmd.Check` via attacker-controlled `.gitattributes` values - ([File: internal/git/gitattributes/check_attr.go])

### Summary
`CheckAttrCmd.Check` reads git-check-attr(1)'s `-z`-delimited output using `bufio.Reader.ReadBytes('\000')`, which buffers an entire NUL-delimited "word" in memory before returning it. Because the `<info>` field of that output directly reflects the attribute value defined in a repository's `.gitattributes` file, an attacker who controls repository content can define an attribute with an arbitrarily large value (e.g. `* attr=<hundreds of MB of text>`), causing a single call to `GetFileAttributes` to allocate memory proportional to that attacker-chosen size.

### Finding Description
`GetFileAttributes` (`internal/gitaly/service/repository/file_attributes.go:14-42`) calls `gitattributes.CheckAttr` and then `checkAttrCmd.Check(path)` for each requested path [1](#0-0) . Inside `Check`, output from `git check-attr --stdin -z` is parsed word-by-word: `word, err := c.stdout.ReadBytes('\000')` [2](#0-1) . `bufio.Reader.ReadBytes` grows its internal buffer to accommodate however much data precedes the next delimiter, with no upper bound. The three NUL-delimited fields emitted by `git check-attr -z` are `<path> NUL <attribute> NUL <info> NUL`, and the `<info>` value is exactly the attribute value string sourced from `.gitattributes` (e.g. `pattern attr=value`). Git's own attribute-line parsing in `attr.c` uses growable strbufs with no practical length cap, so a single `.gitattributes` line can define an attribute whose value is arbitrarily long (hundreds of MB), which git-check-attr will faithfully echo back as the `<info>` field.

None of the existing input-validation layers stop this: `validateGetFileAttributesRequest` only checks that repository/revision/paths/attributes are non-empty [3](#0-2) ; it does not, and cannot, inspect the *content* of `.gitattributes` inside the repository, since that content is fully attacker-controlled repo data, not an RPC field. There is no cap in Gitaly on `.gitattributes` line/value length, nor any bound on the buffer size used in `Check`'s read loop.

### Impact Explanation
An attacker who can push/own a repository can commit a `.gitattributes` file with an oversized attribute value (or macro) matching a path they later query via `GetFileAttributesRequest`. Each such call causes Gitaly to allocate heap memory proportional to the attacker's chosen value size. Because `GetFileAttributes` is a per-request, unauthenticated-in-content-terms RPC (only requires normal repo read access), an attacker can issue this call repeatedly and concurrently to drive sustained heap growth, resulting in denial of service (OOM) for the Gitaly process, which is shared across other repositories/tenants on the same node. This matches a resource-exhaustion / DoS-of-an-RPC-handler impact class.

### Likelihood Explanation
Preconditions are minimal and match the unprivileged attacker model: the ability to push a `.gitattributes` file to a repository the attacker owns (or a fork), and the ability to invoke `GetFileAttributesRequest` against a path matched by the crafted rule. No admin/operator role, secret, or non-default configuration is required. The attack is straightforward and fully repeatable — repeated concurrent calls proportionally multiply memory pressure. The primary constraint is git object storage/size limits at the platform level (Rails/namespace storage quotas), which would bound how large a single `.gitattributes` blob can practically be, but there is no Gitaly-side mitigation at all.

### Recommendation
Bound the amount of data `CheckAttrCmd.Check` will read for a single NUL-delimited word (e.g. use `io.LimitReader` or a max-size guard around `stdout.ReadBytes`/`bufio.Reader.ReadSlice`), returning an error if a word exceeds a sane maximum (matching typical attribute value sizes). Additionally consider capping `.gitattributes`-derived attribute value sizes when invoking `git check-attr`, or streaming/truncating oversized `<info>` fields instead of buffering them fully in memory.

### Proof of Concept
```go
func TestCheckAttrCmd_Check_LargeAttributeValue(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg := testcfg.Build(t)

    repoProto, repoPath := gittest.CreateRepository(t, ctx, cfg, gittest.CreateRepositoryConfig{
        SkipCreationViaService: true,
    })
    repo := localrepo.NewTestRepo(t, cfg, repoProto)

    huge := strings.Repeat("A", 300*1024*1024) // 300MB attribute value
    attrContent := "*.md foo=" + huge

    treeOID := gittest.WriteTree(t, cfg, repoPath, []gittest.TreeEntry{
        {Path: ".gitattributes", Mode: "100644", Content: attrContent},
    })
    commitID := gittest.WriteCommit(t, cfg, repoPath, gittest.WithTree(treeOID))

    var memBefore, memAfter runtime.MemStats
    runtime.ReadMemStats(&memBefore)

    checkCmd, finish, err := gitattributes.CheckAttr(ctx, repo, commitID.Revision(), []string{"foo"})
    require.NoError(t, err)
    defer finish()

    _, err = checkCmd.Check("README.md")
    require.NoError(t, err)

    runtime.ReadMemStats(&memAfter)
    require.Greater(t, memAfter.TotalAlloc-memBefore.TotalAlloc, uint64(300*1024*1024))
}
```
This demonstrates that a single `Check` call allocates memory proportional to the attacker-controlled `.gitattributes` value size, with no enforced upper bound.
