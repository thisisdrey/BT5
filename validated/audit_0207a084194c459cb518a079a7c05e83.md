### Title
Accrued interest fees are locked in `DebtToken.pendingInterestFee` while `SyntheticToken.totalSupply` is at `maxTotalSupply` - ([File: contracts/DebtToken.sol](contracts/DebtToken.sol))

### Summary
`DebtToken.accrueInterest()` mints accrued interest to `pool.feeCollector()` via `SyntheticToken.mint()`. When the synthetic token supply has reached `maxTotalSupply`, that mint reverts inside `SyntheticToken._mint()` (`SurpassMaxSynthSupply`). The failure is caught and the fee accumulates in `pendingInterestFee`, but there is no alternative path to release it: `collectPendingInterestFee()` performs the exact same mint and reverts while the cap is saturated. This is the same bug class as the PoolTogether `maxDeposit()`/TWAB supply-limit finding: yield that belongs to the fee collector cannot be withdrawn until unrelated borrowers repay/burn enough synthetic tokens to free supply headroom.

### Finding Description
In `contracts/DebtToken.sol`, `accrueInterest()` adds the accrued interest to `totalSupply_` and then attempts `syntheticToken.mint(pool.feeCollector(), _interestAmountAccrued + pendingInterestFee)` inside a try/catch. On failure it increments `pendingInterestFee` (lines 169–178). The mint fails with `SurpassMaxSynthSupply` whenever `SyntheticToken.totalSupply + amount > maxTotalSupply` in `contracts/SyntheticToken.sol` `_mint()` (lines 346–347), and also while `isActive == false`.

`collectPendingInterestFee()` (lines 220–226) is the only recovery path, and it calls the same `syntheticToken.mint` unconditionally — it reverts as long as supply is at/above the cap. Unlike `issue()`/`leverage()`, repayment does not require minting, but nothing forces borrowers to repay, so the fee-collector's yield stays locked indefinitely while supply remains saturated. An unprivileged attacker can also drive this state directly: issue synthetic tokens against their own collateral until `SyntheticToken.totalSupply == maxTotalSupply`, then all subsequently accruing interest becomes uncollectible for as long as they keep the cap saturated.

### Impact Explanation
Temporary freezing / locking of unclaimed protocol yield. The interest is real debt accrued to users' balances (`totalSupply_` and per-user `balanceOf` grow regardless), so users owe the interest, but the fee collector cannot receive the minted counterpart. The lock persists until net synthetic supply decreases (repay/repayAll/burn/liquidate), which is outside the fee collector's control — mirroring the confirmed PoolTogether issue where accrued yield fees were locked until withdrawals freed the supply cap.

### Likelihood Explanation
Requires `SyntheticToken.totalSupply` to reach `maxTotalSupply` while `interestRate > 0`. The cap is a deployed configuration value; the PoolTogether sponsor treated the analogous cap-saturation state as realistic for low-priced tokens. An attacker can also force saturation by issuing up to the cap, paying only collateral lockup (their own accrued interest also gets trapped, which limits but does not eliminate the griefing vector). No privileged role, oracle manipulation, or governance action is needed to trigger the locked state once supply is saturated.

### Recommendation
Provide a withdrawal path that does not depend on minting over the cap, or reserve cap headroom for fee mints. Options:
- In `accrueInterest()`/`collectPendingInterestFee()`, mint only up to the remaining headroom (`maxTotalSupply - totalSupply`) and keep the remainder in `pendingInterestFee`, so partial collection is possible.
- Alternatively, exclude the fee-collector mint from the `maxTotalSupply` check (e.g., a dedicated `mintFee` path in `SyntheticToken` that skips the cap), treating protocol fees as exempt from the user-facing supply cap — the equivalent of PoolTogether's fix to net the fee against the limit.

### Proof of Concept
Foundry/Hardhat fork-style test sketch against `DebtToken` + `SyntheticToken`:

```solidity
function testPendingInterestFeeLockedAtMaxSupply() public {
    // setup: pool, depositToken collateral, msUSD synthetic + debtToken with interestRate > 0
    debtToken.updateInterestRate(0.1e18); // governor action in setup only

    // attacker deposits collateral and issues synth until the synth cap is hit
    uint256 cap = msUSD.maxTotalSupply();
    uint256 headroom = cap - msUSD.totalSupply();
    collateral.approve(address(depositToken), type(uint256).max);
    depositToken.deposit(collateralNeeded, attacker);
    debtToken.issue(headroom, attacker); // fills cap: totalSupply == maxTotalSupply

    // time passes: interest accrues but the fee mint fails inside accrueInterest()
    vm.warp(block.timestamp + 365 days);
    debtToken.accrueInterest();
    (uint256 stored,) = debtToken.getPendingInterestFee();
    assertGt(stored, 0); // fees trapped in pendingInterestFee

    // the only recovery path reverts while supply is at the cap
    vm.expectRevert(SurpassMaxSynthSupply.selector);
    debtToken.collectPendingInterestFee();

    // fees remain locked until unrelated burns/repays free headroom
    assertEq(msUSD.balanceOf(feeCollector), 0);
}
```

Key mechanics demonstrated: `accrueInterest()` still accrues debt on users (solvency unchanged), but the fee collector's share is unclaimable while `SyntheticToken.totalSupply == maxTotalSupply`, and `collectPendingInterestFee()` — the designed mitigation — cannot succeed in that state.
