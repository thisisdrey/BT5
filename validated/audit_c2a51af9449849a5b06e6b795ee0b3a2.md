### Title
Unprivileged attacker can permanently block new collateral deposits and new debt issuance for any account by filling its per-account token list with dust, DoS-ing position rescue and new positions - (File: contracts/Pool.sol)

### Summary

The logrus bug class is a resource-exhaustion DoS: a single input exceeding a fixed internal limit permanently breaks a shared facility. The on-chain analog in Metronome is `Pool`'s per-account token list capped at `MAX_TOKENS_PER_USER = 30` [1](#0-0) . Any EOA can fill a victim's `depositTokensOfAccount`/`debtTokensOfAccount` list to the cap with dust via the permissionless `DepositToken.deposit(amount_, onBehalfOf_)` entry point, after which every operation that would add a *new* token to the account reverts with `UserReachedMaxTokens`, blocking the victim from depositing additional collateral types or opening new debt positions indefinitely.

### Finding Description

`Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30` [2](#0-1) . The list is appended by `addToDepositTokensOfAccount` (called by `DepositToken._mint` and `DepositToken._transfer` whenever a recipient goes from 0 to >0 balance) and `addToDebtTokensOfAccount` (called by `DebtToken` on first issue) [3](#0-2) [4](#0-3) .

Crucially, `DepositToken.deposit` is a public, non-whitelisted entry point that accepts an arbitrary `onBehalfOf_` beneficiary [5](#0-4) . So an attacker does not even need to spend their own msdTOKEN transfers — they call `deposit(1 wei, victim)` on every registered `DepositToken` (and can push `debtTokensOfAccount` entries via `DebtToken.issue`-triggered mints only for themselves, so the deposit path is the vector). The victim's list hits 30 entries while their balances are just dust.

Once filled:

- `deposit()` into any collateral type the victim doesn't already hold reverts (the `_mint` → `addToDepositTokensOfAccount` call hits the cap).
- Receiving any new deposit token via `transfer`/`transferFrom` reverts.
- Issuing/minting a new synthetic debt type reverts (`addToDebtTokensOfAccount`).
- If the victim has an unhealthy position, they cannot add a different collateral to rescue it → the position gets liquidated when it otherwise would have been saved.

This mirrors the logrus advisory precisely: a fixed-size internal buffer (30-entry set vs 64KB scanner token) filled by attacker-controlled input causes the facility to fail on all subsequent legitimate use.

### Impact Explanation

Temporary freezing of funds / forced liquidation. The victim retains access to existing positions (`withdraw`/`transfer` of held tokens still work and `_burn`/`_transfer` call `removeFromDepositTokensOfAccount`, freeing slots [6](#0-5) ), so it is not permanent freezing. However, the attacker can re-fill freed slots cheaply and can grief at precisely the moment the victim needs to top up collateral (e.g., during a price move), converting the deposit-block into an avoidable liquidation and loss of the liquidation bonus. The grief costs the attacker only dust amounts of each listed collateral plus gas.

### Likelihood Explanation

- Reachable by any EOA via public `deposit`/`transfer`; no privileged role, no oracle manipulation, no governance needed.
- Cheap to execute: ~30 dust deposits/transfers per victim.
- Mitigable by the victim only reactively — they must notice, transfer dust out to free slots, and re-deposit before the attacker re-fills or the position is liquidated. On chains with private mempools this race favors the attacker less, but the capability itself is unconditional.
- The cap exists to bound gas in `debtOf`/`depositOf` loops, so this is a design tradeoff, but the permissionless `onBehalfOf_` mint path makes it externally triggerable — a genuine griefing vector, not a pure gas/unbounded-loop issue.

### Recommendation

- Make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` failure non-fatal for dust-sized additions, or track "has balance" only above a minimum threshold so dust cannot occupy a slot.
- Alternatively, restrict `DepositToken.deposit`'s `onBehalfOf_` such that minting to an account that hasn't opted in (e.g., no prior interaction/allowance) doesn't register the token, or require `onBehalfOf_ == _msgSender()` unless the target has deposited before.
- Ensure `removeFrom*` always runs before cap checks where possible so users can never be wedged.

### Proof of Concept

Hardhat (mainnet-fork style against deployed `Pool`/`DepositToken`s):

```solidity
// test/foundry/MaxTokensGrief.t.sol
function test_DustDepositBlocksNewCollateral() public {
    // victim already holds depositToken[0]
    depositToken0.deposit(1 ether, victim);

    // attacker fills remaining 29 slots with 1-wei deposits on behalf of victim
    for (uint i = 1; i < 30; ++i) {
        underlying[i].mint(attacker, 1);
        underlying[i].approve(address(depositToken[i]), 1, attacker);
        vm.prank(attacker);
        depositToken[i].deposit(1, victim); // permissionless onBehalfOf_
    }
    assertEq(pool.depositTokensOfAccount(victim).length + pool.debtTokensOfAccount(victim).length, 30);

    // victim's rescue deposit into a collateral they don't hold reverts
    underlying[30].mint(victim, 100 ether);
    vm.startPrank(victim);
    underlying[30].approve(address(depositToken[30]), 100 ether);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    depositToken[30].deposit(100 ether, victim); // reverts: _mint -> addToDepositTokensOfAccount

    // same for receiving any new msdTOKEN via transfer
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    // attacker: depositToken[30].transfer(victim, 1)
}
```

Expected: both calls revert with `UserReachedMaxTokens`, demonstrating the account's collateral-mint facility is disabled by attacker-supplied dust input — the same DoS pattern as the logrus oversized-token scanner failure.

**Caveat:** I could not verify whether `DebtToken.issue`/`mint` allows arbitrary `onBehalfOf_` issuance (the grep only confirmed `addToDebtTokensOfAccount` exists in `DebtToken.sol`), so the PoC relies on the confirmed `DepositToken.deposit(onBehalfOf_)` path, which alone is sufficient.
