### Title
Unbounded array allocation from attacker-controlled length field in `BatchValidateSign`/`ValidateMultiSign` precompile ABI decoding causes node OOM/crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE-2017-12459 bug class is "attacker-controlled length/offset field taken from untrusted binary data is used directly to size/perform a memory operation without validating it against the real buffer size." The same pattern exists in java-tron's precompiled-contract ABI decoders `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` in `PrecompiledContracts.java`, which are reachable from any unprivileged smart-contract call to the `batchvalidatesign` (address `0x...9`) and `validatemultisign` (address `0x...a`) TVM precompiles.

### Finding Description
`extractBytesArray`/`extractSigArray`/`extractBytes32Array` read a 32-byte "length" word directly out of the caller-supplied `data` buffer and use it, unchecked, to size a Java array: [1](#0-0) 

```
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
```
`len` is an arbitrary 32-byte word taken from the transaction's TVM call data (the "array length" field of the ABI-encoded `bytes[]`/`address[]` parameter). It is not checked against the actual remaining data size before being used to allocate `new byte[len][]`, so a caller can set it to any value up to `Integer.MAX_VALUE` while keeping the actual call-data buffer tiny (a few hundred bytes).

`ValidateMultiSign.execute` and `BatchValidateSign.doExecute` call these functions directly from attacker-supplied words: [2](#0-1) [3](#0-2) 

A `VMConfig.allowTvmOsaka()`-gated guard, `isValidAbiEncoding`, was added (apparently for TIP-854) to reject calldata whose *total byte length* doesn't fit the expected `(header + N*item)` word shape: [4](#0-3) 

This guard only validates the *overall* calldata length/shape; it does **not** bound the actual `len` value embedded in the tail data that is later used as the array size in `extractBytesArray`/`extractSigArray`/`extractBytes32Array`. An attacker can therefore craft calldata that passes the `isValidAbiEncoding` shape check (or simply not activate/require the Osaka path) while setting the embedded count word to a huge value (e.g. `0x7fffffff`), causing `new byte[Integer.MAX_VALUE][]` — an allocation request for tens of gigabytes of object-reference memory — before any weight/size sanity check like `MAX_SIZE` is applied. The `MAX_SIZE` bound in both actuators is only enforced *after* array extraction has already been attempted for `ValidateMultiSign`/only checked against `sigArraySize`/`addrArraySize` via a separate (also attacker-controlled) word lookup for `BatchValidateSign`, and both size checks happen only when `allowTvmSelfdestructRestriction()` is enabled — otherwise the unguarded `extractBytesArray` path is used unconditionally: [5](#0-4) 

### Impact Explanation
Because the outer `try { ... } catch (Throwable t)` in `BatchValidateSign.execute` (and the narrower try/catch in `ValidateMultiSign.execute`, which does not even wrap the `extractSigArray`/`extractBytesArray` call) only catches `Throwable`/`RuntimeException`, an `OutOfMemoryError` raised while allocating a huge `byte[len][]` is an `Error`, not a `RuntimeException`, and will not be swallowed by these handlers. A single crafted `TriggerSmartContract` transaction that calls the `batchvalidatesign` or `validatemultisign` precompile with a spoofed large count word can force the node's JVM to attempt a multi-gigabyte allocation, driving the process into `OutOfMemoryError` territory. This can destabilize or crash the witness/full node process, i.e. a node-crash/halt DoS triggerable by any unprivileged transaction broadcaster.

### Likelihood Explanation
Likelihood is high given the primitive: the precompiles are reachable by any account issuing a `TriggerSmartContract` transaction that calls address `0x...9` or `0x...a` (no special permission required), and the count/length word is fully attacker-controlled ABI-encoded input, independent of the real payload size. The only obstacle is that in some configurations (`allowTvmSelfdestructRestriction`) a `MAX_SIZE` check is done on `sigArraySize`/`addrArraySize`, but that check reads the size from `words[...]` which is the *same* attacker-controlled length that is used inside `extractBytesArray`/`extractSigArray`, so it does bound `len` under that specific config path — however when `allowTvmSelfdestructRestriction()` is disabled, `extractBytesArray` is invoked with no upstream size bound at all.

### Recommendation
Add an explicit sanity check on the decoded `len` in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` (e.g., bound it against a small constant such as `MAX_SIZE`, or against the number of remaining words available in `data`/`words`) before allocating `new byte[len][]`, independent of the `allowTvmSelfdestructRestriction` flag, so that the length can never exceed the actual number of 32-byte words present in the calldata.

### Proof of Concept
1. Construct calldata for `validatemultisign(address,uint256,bytes32,bytes[])` (or `batchvalidatesign`) where the tail's array-length word (the one read via `words[offset].intValueSafe()`) is set to a large value (e.g. `0x7fffffff`) while the remainder of the calldata buffer is only a few hundred bytes.
2. Submit a `TriggerSmartContract` transaction (from any funded account) invoking the precompile at address `0000...09` or `0000...0a` with this calldata, with `allowTvmSelfdestructRestriction` disabled (default/legacy config) so the unguarded `extractBytesArray`/`extractSigArray` path executes.
3. Observe the JVM attempt to allocate `new byte[0x7fffffff][]`, exhausting heap and raising `OutOfMemoryError`, which propagates past the `catch (RuntimeException)`/`catch (Throwable)` handlers used in `BatchValidateSign`/`ValidateMultiSign`, destabilizing the node process.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
