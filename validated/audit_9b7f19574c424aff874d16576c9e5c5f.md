### Title
Bancor-style Exchange pool is permanently and irreversibly frozen once either token balance hits zero via a normal trade, with no admin/creator recovery path - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
`ExchangeWithdrawActuator`, `ExchangeInjectActuator`, and `ExchangeTransactionActuator` all gate every operation on an `ExchangeCapsule` pool behind the identical check `firstTokenBalance == 0 || secondTokenBalance == 0` → "Token balance in exchange is equal with 0, the exchange has been closed". This mirrors the reported bug class: a single, immutable invariant/dependency (here, "both pool sides must remain non-zero") is the sole gate for every exit path from the pool, and there is no fallback, no comptroller/admin override, and no re-injection or rescue mechanism once it is tripped.

### Finding Description
The exchange pool state lives in `ExchangeCapsule` (`chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java:124-169`), which tracks `firstTokenBalance`/`secondTokenBalance` and applies the bancor-like `ExchangeProcessor`/`SafeExchangeProcessor` pricing curve on every trade via `exchangeCapsule.transaction(...)` [1](#0-0) .

Any unprivileged trader can broadcast an `ExchangeTransactionContract` executed by `ExchangeTransactionActuator.execute()`, which calls `exchangeCapsule.transaction(...)` and persists the resulting balances unconditionally in non-hardened mode [2](#0-1) . In `ExchangeProcessor` (the default, non-hardened path used unless `allowHardenExchangeCalculation` is enabled), the pricing math is done in floating point and the result is truncated via a `(long)` cast with no floor/overshoot protection [3](#0-2) , and `ExchangeCapsule.transaction()` only rejects negative balances when `hardenedCalc` is true [4](#0-3) . For small-denomination TRC10 pools or pools near depletion of one side, a trade can drive one side's balance to exactly `0` (or below, if hardened checks are bypassed) through normal `ExchangeTransactionContract` usage — not just through the creator's own intentional full withdrawal.

Once either `firstTokenBalance` or `secondTokenBalance` reaches `0`, **all three actuators refuse to operate on that exchange ID forever**:
- `ExchangeWithdrawActuator.doValidate()` throws "the exchange has been closed" [5](#0-4) 
- `ExchangeInjectActuator.doValidate()` throws the identical error, blocking any attempt to top up liquidity to revive the pool [6](#0-5) 
- `ExchangeTransactionActuator.doValidate()` also throws the same error for any further trade [7](#0-6) 

There is no comptroller/committee function, proposal parameter, or actuator anywhere in the exchange module that can reset, migrate, or unlock an `ExchangeCapsule` whose balance has hit zero on either side — `Commons.putExchangeCapsule` only persists state that was already computed by these same three actuators. This is structurally identical to the reported `SablierLidoAdapter` issue: a single hard invariant (immutable Curve pool / non-zero balance requirement) is the only exit gate, with no fallback route and no admin rescue.

### Impact Explanation
Whatever token balance the *other* (non-zero) side of the pool still holds at the moment one side hits zero becomes permanently unretrievable. The creator cannot withdraw remaining liquidity via `ExchangeWithdrawActuator`, cannot revive the pool via `ExchangeInjectActuator`, and other users' pending/queued trades against that exchange ID via `ExchangeTransactionActuator` permanently fail. This is a permanent freezing-of-funds condition triggerable by a normal, unprivileged `ExchangeTransactionContract` broadcast — no malicious SR/witness/peer role is required, only a regular trader interacting with the exchange's public order-handling path.

### Likelihood Explanation
Likelihood is highest for exchanges with small token balances/precision (common for low-liquidity or newly created TRC10 pairs, or pools that have already been mostly drained through prior trades) where floating-point truncation in `ExchangeProcessor` can produce an exact zero result. It does not require attacker collusion — a single large trade combined with the existing pool state is sufficient. The condition is compounded by the fact that `allowHardenExchangeCalculation`/`SafeExchangeProcessor` mitigations are gated behind a dynamic parameter and only reduce (not eliminate) the risk of reaching the zero-balance dead state through legitimate trading.

### Recommendation
- Prevent trades/injects/withdrawals from ever driving either side of the pool to exactly zero except via the creator's deliberate, symmetric full withdrawal (which already zeroes both sides simultaneously).
- Add a recovery path: allow the exchange creator (or, at minimum, the account holding the non-zero remaining balance) to reclaim residual funds even when the opposite side balance is zero, instead of gating all three actuators on a strict `both-sides-nonzero` invariant.
- Consider allowing `ExchangeInjectActuator` to "reopen" a pool by re-seeding the zeroed side, rather than unconditionally rejecting injection once either balance is zero.

### Proof of Concept
1. Create an `ExchangeCreateContract` for a TRC10 pair with a small `secondTokenBalance` (e.g., low-decimal token with a small initial pool, as used in existing tests such as `SameTokenNameCloseTokenBalanceZero`) [8](#0-7) .
2. Broadcast a sequence of `ExchangeTransactionContract`s (regular unprivileged trader) selling the first token in large-enough quantity that `ExchangeProcessor.exchangeFromSupply()`'s floating-point/`(long)` truncation yields `buyTokenQuant == secondTokenBalance`, making `newSecondTokenBalance == 0` while `newFirstTokenBalance` remains large and positive [9](#0-8) .
3. Attempt any subsequent `ExchangeWithdrawContract`, `ExchangeInjectContract`, or `ExchangeTransactionContract` against the same `exchangeId` — all three actuators now uniformly reject with "Token balance in exchange is equal with 0,the exchange has been closed" as verified by the existing test suite's `TokenBalanceZero` tests [10](#0-9) , leaving the remaining `firstTokenBalance` permanently locked in the pool with no recovery mechanism.

    Processor processor = hardenedCalc

    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,

          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;
