## Title
Missing bounds validation on attacker-controlled word offset causes uncaught `ArrayIndexOutOfBoundsException` in `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (invoked via the TVM `staticcall`/`call` opcode dispatch for the reserved precompile address) parses caller-supplied ABI-encoded calldata into a `DataWord[]` array and then indexes into that array using an offset that is fully derived from the calldata itself, without validating that the offset (or the subsequent elements it implies) stays within the array bounds. This mirrors the kernel `get_rpi()` bug class: an off-by-one/insufficient bounds check on an array whose size is fixed, indexed by an externally influenced value.

### Finding Description
In `ValidateMultiSign.execute`:
```java
// actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1057-1074
DataWord[] words = DataWord.parseArray(rawData);
byte[] address = words[0].toTronAddress();
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();
...
if (VMConfig.allowTvmSelfdestructRestriction()) {
  int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
  ...
}
byte[][] signatures = VMConfig.allowTvmSelfdestructRestriction() ?
    extractSigArray(words, words[3].intValueSafe() / WORD_SIZE, rawData) :
    extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData);
```
`words[3].intValueSafe()` is fully attacker-controlled (any caller can craft the `rawData` passed to this precompile via a `TriggerSmartContract`). It is divided by `WORD_SIZE` and used directly as an array index into `words` with **no bounds check at all** before the `sigArraySize` computation on line 1067. Only downstream in `extractSigArray`/`extractBytesArray` is there a partial guard:
```java
// actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:414-426, 399-412
private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  for (int i = 0; i < len; i++) {
    int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
    bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, SIG_LENGTH);
  }
  return bytesArray;
}
```
This guard only validates that `words[offset]` itself (the length word) is in range — exactly the same class of error as `get_rpi()`'s `>` vs `>=` mistake: it checks the boundary of one array access but not the boundary of the subsequent indexed reads (`words[offset + i + 1]`) that depend on the attacker-controlled `len`. Additionally, the very first access at line 1067 (`words[words[3].intValueSafe() / WORD_SIZE]`) has **no guard whatsoever**, so a crafted offset causes an immediate out-of-bounds array read.

### Impact Explanation
Because `words[3].intValueSafe()` and the resulting derived index are entirely attacker-controlled, an unprivileged contract caller can trigger `ArrayIndexOutOfBoundsException` (or negative-size `NegativeArraySizeException` from `new byte[len][]` if `len` is negative) inside precompile execution. I was not able to fully confirm, within the available indexed code, whether every call path into `PrecompiledContract.execute()` is wrapped in a try/catch that safely converts such runtime exceptions into a reverted transaction (I found `VM.play` has a generic `catch (RuntimeException e)` that halts the VM/marks the transaction as failed, but I could not verify with certainty that every precompile invocation route funnels through that exact guard for this particular contract, since the direct call site of `PrecompiledContracts.execute` was not resolved from the index in the final iteration). If any invocation path calls this precompile outside of that generic exception guard (e.g., during energy estimation, static/constant calls used by RPC endpoints, or other node-side pre-execution paths), the uncaught exception could propagate and disrupt request handling or block processing — a potential node crash/DoS condition. At minimum, this is a robustness/DoS-class defect reachable from a single unprivileged contract call.

### Likelihood Explanation
High reachability: any account can deploy or call a contract that issues a `CALL`/`STATICCALL` to the `ValidateMultiSign` precompile address with crafted `rawData`, requiring no special privileges, no coordination, and only a single transaction.

### Recommendation
Add an explicit bounds check before line 1067's read:
```java
int idx = words[3].intValueSafe() / WORD_SIZE;
if (idx < 0 || idx >= words.length) {
  return Pair.of(true, DATA_FALSE);
}
```
In `extractBytesArray` and `extractSigArray`, after reading `len = words[offset].intValueSafe()`, validate `len >= 0` and that `offset + len` (and, for `extractBytesArray`, the additional `bytesOffset` reads) stay within `words.length` before entering the loop, returning an empty array / `DATA_FALSE` otherwise, consistent with the fix pattern used for `get_rpi()` (change loose `>` checks to inclusive `>=`/full-range validation).

### Proof of Concept
1. Deploy a contract that calls the `ValidateMultiSign` precompile (address `0x0...66` region used for TRON native precompiles) via low-level `staticcall`, or drive it directly through `Wallet`'s TVM trigger APIs used for constant calls.
2. Craft `rawData` such that `words[3]` decodes to a very large value (e.g., `0xFFFFFFFF` or a negative-looking value once cast), well beyond `words.length * WORD_SIZE`.
3. Submit the call; execution reaches
`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1067`
before any bounds validation, causing `words[idx]` to throw `ArrayIndexOutOfBoundsException` for an out-of-range `idx`. [1](#0-0) [2](#0-1)
