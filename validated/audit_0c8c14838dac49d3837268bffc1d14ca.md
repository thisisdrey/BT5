### Title
Assert-Only Guard Allows Divide-by-Zero Crash in Energy Limit Calculation - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` divides by `totalEnergyWeight` and only guards against zero with a Java `assert` statement, which is a no-op in production JVMs (assertions are disabled by default, i.e. run without `-ea`). This mirrors the CVE-2017-7598 bug class (a missing/insufficient zero-check before a divide operation causing a crash): the "check" exists in source but never actually executes at runtime.

### Finding Description [1](#0-0) 

```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
  long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
  if (frozeBalance < TRX_PRECISION) {
    return 0;
  }
  long energyWeight = frozeBalance / TRX_PRECISION;
  long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
  long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

  assert totalEnergyWeight > 0;

  if (hardenResourceCalculation()) {
    return BigInteger.valueOf(energyWeight)
        .multiply(BigInteger.valueOf(totalEnergyLimit))
        .divide(BigInteger.valueOf(totalEnergyWeight))
        .longValueExact();
  }
  return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
```

Contrast this with the equivalent bandwidth path, which uses a real runtime check instead of `assert`: [2](#0-1) 

```java
long totalNetLimit = chainBaseManager.getDynamicPropertiesStore().getTotalNetLimit();
long totalNetWeight = chainBaseManager.getDynamicPropertiesStore().getTotalNetWeight();
if (dynamicPropertiesStore.allowNewReward() && totalNetWeight <= 0) {
  return 0;
}
if (totalNetWeight == 0) {
  return 0;
}
```

The energy-limit path has no such runtime guard—only the disabled `assert`. When `allowHardenResourceCalculation` (the "hardened" flag, `hardenResourceCalculation()`) is enabled and `totalEnergyWeight` is `0`, the code path takes `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(0))`, which throws `ArithmeticException: BigInteger divide by zero`. This is functionally analogous to the libtiff CVE: a divisor derived from mutable state is used without an effective zero-check, producing an unhandled divide-by-zero exception at runtime.

`totalEnergyWeight` is derived from the sum of frozen-for-energy balances across all accounts (`TOTAL_ENERGY_WEIGHT` dynamic property), which is adjusted whenever accounts freeze/unfreeze/delegate/undelegate energy resources — actions directly reachable from unprivileged, signed transactions (`FreezeBalanceV2Contract`, `UnfreezeBalanceV2Contract`, `DelegateResourceContract`, `UnDelegateResourceContract`). If the network-wide total ever transiently reaches `0` (e.g., all energy-frozen stake unfrozen on a low-activity/private/test network, or via a sequence of unfreeze/undelegate transactions that a user fully controls on such a network), any subsequent call into `calculateGlobalEnergyLimit` — reached from `Wallet.getAccountResource`/`calcCanDelegatedEnergyMaxSize` (gRPC/HTTP query paths) as well as freeze/energy-related TVM precompiles (`ResourceV2`, `TotalResource`, `DelegatableResource`, etc., all built on `RepositoryImpl`) — throws an uncaught `ArithmeticException`.

### Impact Explanation
An uncaught `ArithmeticException` thrown while computing account resource/energy limits can:
- Crash or fail the specific query/API request path (`getAccountResource`, `calcCanDelegatedEnergyMaxSize` in `Wallet.java`) served over gRPC/HTTP, denying service to that endpoint for all callers until the underlying zero-weight condition changes.
- If reached inside actual transaction execution (via precompiled contracts exercising `calculateGlobalEnergyLimit`/related `Repository` calls) during block application, an unhandled exception during consensus-critical execution can cause block-processing/application failures — a potential chain-halt or crash vector on affected nodes, which is worse than a simple failed transaction because it is not contained by the actuator's normal try/catch(`ArithmeticException`) pattern used elsewhere in the codebase (e.g., Exchange/Market actuators explicitly catch `ArithmeticException`; this code path does not).

This qualifies under the "node crash or halt" / "API the node can no longer serve" acceptance criteria.

### Likelihood Explanation
The precondition (`totalEnergyWeight == 0` while `hardenResourceCalculation()` is enabled) requires the network-wide total energy-frozen weight to hit exactly zero, which is unlikely on TRON mainnet where governance keeps this non-zero, but is plausible on private/test/side chains, freshly bootstrapped chains, or via targeted sequences of `UnfreezeBalanceV2`/`UnDelegateResource` transactions by users controlling most/all frozen-for-energy stake. The bug is a genuine logic defect (relying on `assert`, disabled by default) rather than a purely theoretical concern, and it is reachable purely through user-broadcastable transactions and read-only API/precompile calls, with no need for privileged/malicious-SR access.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` statement in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime check (matching the pattern already used in `BandwidthProcessor.calculateGlobalNetLimit`/`calculateGlobalNetLimitV2`):
```java
if (totalEnergyWeight <= 0) {
  return 0;
}
```
placed before both the hardened `BigInteger` branch and the legacy `double` branch, so the function degrades gracefully instead of relying on assertions that are compiled out/disabled in production deployments.

### Proof of Concept
1. On a test/private network, set `allowHardenResourceCalculation = 1` (hardened resource calculation enabled).
2. Drive `TOTAL_ENERGY_WEIGHT` (the dynamic property backing `getTotalEnergyWeight()`) to `0` — e.g., have all stakers submit `UnfreezeBalanceV2Contract`/`UnDelegateResourceContract` transactions withdrawing all energy-frozen balance, or start from a genesis state where no energy has ever been frozen.
3. Call `Wallet.getAccountResource`/`calcCanDelegatedEnergyMaxSize` (or trigger a TVM contract call that invokes a resource-related precompile backed by `RepositoryImpl`) for any account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION`.
4. Observe `calculateGlobalEnergyLimit` executes `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(0))`, throwing an unhandled `ArithmeticException` because the `assert totalEnergyWeight > 0;` guard is a no-op (assertions disabled by default in the production JVM), unlike the explicit `if (totalNetWeight == 0) return 0;` guard used in the analogous bandwidth code path.
