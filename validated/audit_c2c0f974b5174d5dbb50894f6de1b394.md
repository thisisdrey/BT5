### Title
RPC cost score does not reflect actual CPU/resource usage, enabling attackers to evade upstream rate-limiting and grief Gitaly's resource budget - (File: `internal/grpc/middleware/costhandler/costhandler.go`)

### Summary
Gitaly emits an `x-gitaly-cost` gRPC trailer that Rails/Workhorse forward to Cloudflare as an `X-Score` header for "complexity-based" upstream rate limiting [1](#0-0) . This score is computed from a fixed, RPC-type-based static weight plus a byte-count-based dynamic term, but never accounts for actual CPU time, object counts, or history-walk depth consumed by the request [2](#0-1) . This mirrors the Hinkal "gas griefing" bug class: the fee/score charged to a caller does not reflect the true computational cost incurred by the server, letting an ordinary, unprivileged caller send RPCs that report as "cheap" while actually consuming disproportionate CPU/resources on Gitaly, undermining the very rate-limiting/backpressure mechanisms meant to protect the node.

### Finding Description
`computeCost` sums a static per-method weight (`staticCostForMethod`) and a dynamic weight derived solely from transferred bytes (`dynamicCostFromContext`) [3](#0-2) . Static weights are either a small hardcoded override table or a coarse default keyed only by whether the RPC is classified as accessor/mutator/maintenance in the proto registry [4](#0-3) :

- Accessor RPCs (e.g. `CommitService`, `RefService`, `BlobService` lookups, log/diff/blame-style traversal RPCs) default to a flat cost of `1` regardless of how deep a revision walk, how many objects are enumerated, or how much CPU time git spends internally [5](#0-4) .
- The dynamic component only counts `InPayloadBytes + OutPayloadBytes` divided by 1 MiB [6](#0-5) , so an RPC that returns a tiny amount of data (e.g., "commit not found" after walking a huge, attacker-shaped history, or a narrow diff/blame range over a pathologically large file) contributes essentially nothing to the score even though it is CPU/IO heavy on the Gitaly node.

The project's own design doc acknowledges this gap explicitly: "A static score hides variance (e.g. `PostUploadPackWithSidechannel` is the same cost whether it serves 1 MB or 10 GB)" [7](#0-6) . Critically, this cost score is the *only* per-request signal exported for upstream complexity-based rate limiting; it is computed and attached to the response only after the handler has already run to completion, and Gitaly's own concurrency limiter is explicitly documented as unaware of cost and treats every admitted request as equally expensive [8](#0-7) . This means:

1. There is no per-request internal mechanism gating admission or continued execution based on real-time resource consumption for the vast majority of RPCs (only `PostUploadPackWithSidechannel` and pack-objects have dedicated concurrency/cache-based protections, per `internal/gitaly/service/hook/pack_objects.go` and `internal/cli/gitaly/serve.go`).
2. The external safety net (Cloudflare/Workhorse rate limiting) that is supposed to compensate for this gap relies entirely on the `x-gitaly-cost` trailer, which — by design and by the doc's own admission — does not reflect true cost for CPU-heavy-but-low-byte-output requests.

An attacker with only unprivileged, ordinary access to git/Rails-fronted RPC endpoints (any authenticated Git user, or any caller able to reach a public/accessor RPC field they control, e.g. path filters, revision ranges, pagination limits) can craft repeated requests that are individually classified as cheap (accessor default cost `1`, or low dynamic byte cost) while internally forcing Gitaly to perform expensive git subprocess operations (deep log walks, blame over large files, diffs with large contexts, etc.), the same way a Hinkal hook can spend near-unbounded gas while paying a percentage-of-swap fee unrelated to that gas.

### Impact Explanation
Because the exported cost signal underestimates real resource usage for a broad class of requests, the upstream complexity-based rate limiter can be bypassed/griefed: an attacker can sustain a much higher rate of expensive operations against a Gitaly node than the rate-limiting design intends, since each request "looks cheap." Combined with the internal concurrency limiter's blindness to cost, this can degrade or exhaust Gitaly node resources (CPU, IO) for the affected repository/storage, producing a denial-of-service condition for other tenants sharing that storage/node, while remaining within externally-enforced complexity budgets.

### Likelihood Explanation
The requests needed are ordinary, unprivileged RPCs (log/diff/blame/commit enumeration style accessor calls) reachable by any authenticated Git/API user, requiring no special access, no leaked credentials, and no cooperation from a privileged actor. The mismatch is structural (documented in-repo) rather than a rare edge case, so it is straightforward to trigger repeatedly by choosing request parameters (e.g., revision ranges, path filters) that maximize internal git work while minimizing response bytes.

### Recommendation
- Incorporate actual per-request resource usage (CPU time, wall-clock duration, object/commit counts touched) into the `x-gitaly-cost` computation instead of relying solely on a static per-RPC-type weight plus payload bytes, as already hinted at in the design doc's suggestion to "reconcile actual cost in a follow-up after Gitaly responds" [7](#0-6) .
- Extend the internal concurrency limiter / load shedder (`BurdenMonitor`) to use resource-based cost for admission decisions on accessor RPCs known to allow attacker-controlled depth (log, diff, blame, list-commits), not just for `PostUploadPackWithSidechannel` and pack-objects.
- Consider bounding attacker-controllable parameters that drive git subprocess cost (revision walk depth, diff context size, blame ranges) independent of the cost-score mechanism, since off-node signals (Cloudflare) can only partially mitigate a cost/usage mismatch that originates inside Gitaly.

### Proof of Concept
1. As an ordinary authenticated user with read access to a repository containing a very large, deep commit history (or a large blob), issue repeated calls to an accessor RPC such as `CommitService/ListCommits`, `DiffService/CommitDiff`, or a blame-style RPC with parameters chosen to force a large internal git history walk or file scan (e.g., deep `--since`/pagination ranges, large `blame` ranges) but with output truncated/filtered to a small number of bytes (e.g., request only the last small page, or a narrow path filter that matches almost nothing).
2. Observe that `staticCostForMethod` returns the flat default (`defaultAccessorCost = 1`) for these RPCs and `dynamicCostFromContext` contributes ~0 extra cost because `InPayloadBytes + OutPayloadBytes` stays well under `byteCostDivisor` (1 MiB) [9](#0-8) , so the `x-gitaly-cost` trailer/`X-Score` header reports a very low value.
3. Meanwhile, the underlying git subprocess spawned by the handler consumes significant CPU/IO time internally, unbounded by the concurrency limiter (which is cost-agnostic, per `doc/load-management-architecture.md` lines 197-205) and unbounded by the low reported cost score.
4. Repeat the same crafted request pattern at high volume; each request is scored as cheap by the upstream rate limiter, allowing the attacker to sustain far more actual Gitaly compute load per unit time than the complexity-based rate limiting was designed to allow, degrading the shared Gitaly node.

```go
// computeCost returns the cost score for a completed RPC. It combines a static
// base cost for the RPC type with a dynamic component from actual bytes
// transferred, read from the RPCEntry in context.
func computeCost(ctx context.Context, fullMethod string) int {
	static := staticCostForMethod(fullMethod)
	dynamic := dynamicCostFromContext(ctx)
	return static + dynamic
}

// staticCostForMethod returns the static cost weight for the given full method
// name. It first checks per-RPC overrides, then falls back to a default based
// on the method's operation type from the proto registry.
func staticCostForMethod(fullMethod string) int {
	if cost, ok := staticCostOverrides[fullMethod]; ok {
		return cost
	}

	methodInfo, err := protoregistry.GitalyProtoPreregistered.LookupMethod(fullMethod)
	if err != nil {
		return defaultUnknownCost
	}

	switch methodInfo.Operation {
	case protoregistry.OpAccessor:
		return defaultAccessorCost
	case protoregistry.OpMutator:
		return defaultMutatorCost
	case protoregistry.OpMaintenance:
		return defaultMaintenanceCost
	default:
		return defaultUnknownCost
	}
}

// dynamicCostFromContext computes the dynamic cost contribution from payload
// bytes tracked by the grpcstats.PayloadBytes stats handler.
func dynamicCostFromContext(ctx context.Context) int {
	stats := grpcstats.PayloadBytesStatsFromContext(ctx)
	if stats == nil {
		return 0
	}
	totalBytes := stats.InPayloadBytes + stats.OutPayloadBytes

	return int(math.Ceil(float64(totalBytes) / float64(byteCostDivisor)))
```

```markdown
The concurrency limiter today treats every request as equally expensive. In
practice, requests served from cache consume minimal resources (disk streaming)
while cache misses run full Git subprocess pipelines. Rather than feeding the
limiter a cost hint (which still consumes a limiter slot), cache-hit requests
skip the limiter entirely — keeping the concurrency limiter pure and ensuring
limits designed for expensive operations do not penalize cheap ones.

This separation also keeps the concurrency limiter's responsibility narrow: every
request that reaches it is treated as expensive.
```
