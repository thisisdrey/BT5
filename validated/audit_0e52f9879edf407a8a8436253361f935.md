### Title
Permissionless registration of self-created, worthless assets lets any unprivileged user mint deceptively-named ERC20 tokens on Ethereum via Snowbridge - ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

### Summary
The external report describes minting a valuable token using an arbitrary, unvetted ERC20 as backing. The local analog is Snowbridge's Polkadot-native-asset (PNA) registration/bridging pipeline: `EthereumSystemFrontend::register_token` on AssetHub only checks that the caller's XCM origin is nested within (i.e. "owns") the asset location being registered, never that the asset is a legitimate, valuable, previously-known token. Because `pallet_assets::create` is itself permissionless, any signed account can create and self-own a brand-new, worthless asset, choose an impersonating name/symbol (e.g. "USDC"), register it as a wrapped ERC20 on Ethereum, and mint real, contract-deployed ERC20 tokens under that spoofed identity that can be sold to unsuspecting buyers on Ethereum.

### Finding Description
`register_token` in `bridges/snowbridge/pallets/system-frontend/src/lib.rs:225-252` is explicitly documented as open to "all origins," gated only by `T::RegisterTokenOrigin::ensure_origin(origin, &asset_location)` [1](#0-0) , which verifies that the caller's own location is a prefix/owner of `asset_location` — not that the underlying asset represents anything real or valuable.

Any account can first call the fully permissionless `pallet_assets::create` (`CreateOrigin = AsEnsureOriginWithArg<EnsureSigned<AccountId>>`) to spin up a brand-new asset class it fully owns, paying only `AssetDeposit` [2](#0-1) [3](#0-2) , then mint itself an arbitrary supply since it is the asset's own admin/issuer.

The attacker then calls `register_token`, supplying attacker-chosen `AssetMetadata { name, symbol, decimals }` with no validation against real-world token identities [4](#0-3) . This is forwarded via XCM `Transact` to `snowbridge-pallet-system-v2::register_token` on BridgeHub, which computes a `token_id` from the (attacker-owned) location and unconditionally inserts the mapping and dispatches `Command::RegisterForeignToken` with the attacker-supplied name/symbol/decimals to the Ethereum Gateway, deploying a real ERC20 contract [5](#0-4) .

When the attacker subsequently reserve-transfers their self-minted asset to Ethereum, the outbound-queue converter only checks that the asset location round-trips consistently through `TokenIdOf`/`ConvertAssetId` — it never checks that the asset has any real backing, market value, or legitimate provenance [6](#0-5) . The result is `Command::MintForeignToken`, which mints genuine ERC20 tokens on the newly deployed contract to an address the attacker controls.

### Impact Explanation
This lets an unprivileged, non-malicious-node actor mint a real ERC20 contract on Ethereum with a deceptive/impersonating name and symbol (e.g., mimicking "USDC" or a known Polkadot asset), fully backed by tokens the attacker fabricated for free. Because the Snowbridge system legitimizes the token through the normal registration/bridging flow (same code path used for real assets like `usdt_at_ah_westend` in the test suite [7](#0-6) ), unsuspecting users/DEXs on Ethereum may treat the resulting ERC20 as an authentic bridged Polkadot asset, enabling fraud/theft of value from anyone who buys it — matching the "theft or unbacked mint" and "runtime bugs that compromise intended behavior" impact categories.

### Likelihood Explanation
High likelihood: the entire attack path requires only two standard, permissionless, unprivileged operations available to any signed account — `pallet_assets::create`/`mint`, and `EthereumSystemFrontend::register_token` — with no governance, relayer, validator, or admin involvement, and no need to defeat any cryptographic or replay protection. The existing test suite confirms `register_token` succeeds for any account as long as it "owns" the (self-created) asset location [8](#0-7) , which only guards against registering someone else's asset, not against registering a worthless self-created one.

### Recommendation
Do not let arbitrary user-supplied `name`/`symbol`/`decimals` metadata flow unchecked into a real Ethereum contract deployment. Options: maintain an allow-list/registry of assets eligible for Ethereum-side registration (curated or governance-approved), enforce minimum liquidity/backing or a `is_sufficient`/reserve requirement on the asset before allowing `register_token`, and/or reject metadata (name/symbol) that collides with or impersonates already-registered or well-known token identifiers.

### Proof of Concept
1. On AssetHub, call `Assets::create(origin=attacker, id=<new_id>, admin=attacker, min_balance=1)` (permissionless, deposit only) — attacker becomes owner/issuer.
2. Call `Assets::mint(origin=attacker, id=<new_id>, beneficiary=attacker, amount=<huge>)`.
3. Call `EthereumSystemFrontend::register_token(origin=attacker, asset_id=Location(<new_id>), metadata={name:"USD Coin", symbol:"USDC", decimals:6}, fee_asset=...)` — this passes `RegisterTokenOrigin::ensure_origin` because the attacker owns the asset location, and is relayed to BridgeHub's `register_token`, which registers the fake token and commands Ethereum's Gateway to deploy an ERC20 named/symbolled "USD Coin"/"USDC".
4. Reserve-transfer the attacker's self-minted balance of `<new_id>` from AssetHub to an Ethereum recipient the attacker controls; the outbound-queue converter validates only that the token_id round-trips (`extract_polkadot_native_assets`), and issues `Command::MintForeignToken`, minting real ERC20 tokens to the attacker on the impersonating contract.
5. Attacker lists/sells the newly minted, deceptively-named ERC20 on Ethereum DEXs to defraud buyers who believe it is a genuine bridged asset.

```rust
		pub fn register_token(
			origin: OriginFor<T>,
			sender: Box<VersionedLocation>,
			asset_id: Box<VersionedLocation>,
			metadata: AssetMetadata,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let sender_location: Location =
				(*sender).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;
			let asset_location: Location =
				(*asset_id).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;

			let location = Self::reanchor(asset_location)?;
			let token_id = TokenIdOf::convert_location(&location)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			if !ForeignToNativeId::<T>::contains_key(token_id) {
				ForeignToNativeId::<T>::insert(token_id, location.clone());
			}

			let command = Command::RegisterForeignToken {
				token_id,
				name: metadata.name.into_inner(),
				symbol: metadata.symbol.into_inner(),
				decimals: metadata.decimals,
			};

			let message_origin = Self::location_to_message_origin(sender_location)?;
			Self::send(message_origin, command, amount)?;

			Self::deposit_event(Event::<T>::RegisterToken {
				location: location.into(),
				foreign_token_id: token_id,
			});

			Ok(())
```

```rust
	/// Extract polkadot native assets
	fn extract_polkadot_native_assets(
		&mut self,
		pnas: &Assets,
		deposit_assets: &AssetFilter,
		recipient: H160,
	) -> Result<Vec<Command>, XcmConverterError> {
		let mut commands: Vec<Command> = Vec::new();
		ensure!(pnas.len() > 0, NoReserveAssets);
		for pna in pnas.clone().into_inner().into_iter() {
			if !deposit_assets.matches(&pna) {
				return Err(FilterDoesNotConsumeAllAssets);
			}

			// Only fungible is allowed
			let Asset { id: AssetId(asset_id), fun: Fungible(amount) } = pna else {
				return Err(AssetResolutionFailed);
			};

			// transfer amount must be greater than 0.
			ensure!(amount > 0, ZeroAssetTransfer);

			// Ensure PNA already registered
			let token_id = TokenIdOf::convert_location(&asset_id).ok_or(InvalidAsset)?;
			let expected_asset_id = ConvertAssetId::maybe_convert(token_id).ok_or(InvalidAsset)?;
			ensure!(asset_id == expected_asset_id, InvalidAsset);

			commands.push(Command::MintForeignToken { token_id, recipient, amount });
		}
		Ok(commands)
	}
```
