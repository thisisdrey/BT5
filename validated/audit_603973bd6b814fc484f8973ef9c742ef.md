### Title
Non-hardened exchange AMM path skips overflow and non-negative-balance checks, allowing an exchange pool balance to be pushed negative / wrapped — unbacked balances and fund theft via `ExchangeTransactionContract` - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
`ExchangeCapsule.transaction()` computes the AMM swap result and updates the pool's `firstTokenBalance`/`secondTokenBalance` differently depending on the `hardenedCalc` flag (driven by the `AllowHardenExchangeCalculation` proposal). Only the `hardenedCalc` branch uses overflow-checked arithmetic (`StrictMathWrapper.addExact/subtractExact`) and only that branch validates that the resulting balances are non-negative. The default/legacy branch (`hardenedCalc == false`, which is the behavior whenever the hardening proposal has not been activated) uses raw `long` addition/subtraction with **no overflow check and no post-condition check that the new balances are `>= 0`**.

### Finding Description
`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` [1](#0-0) , and the actual balance bookkeeping happens in `ExchangeCapsule.transaction()`:

```java
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
``` [2](#0-1) 

Notice the guard is only reached `if (hardenedCalc ...)`. When `hardenedCalc` is `false` (the state before/without the `AllowHardenExchangeCalculation` proposal being enabled — the default, unhardened path is exercised in most of the existing tests such as `SameTokenNameOpenSuccessExchangeTransaction`), the new balances are computed with plain, unchecked `long` arithmetic:

```java
newFirstTokenBalance = hardenedCalc
    ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
    : firstTokenBalance + sellTokenQuant;
newSecondTokenBalance = hardenedCalc
    ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
    : secondTokenBalance - buyTokenQuant;
``` [3](#0-2) 

and there is no post-transaction check for the non-hardened path that `newFirstTokenBalance`/`newSecondTokenBalance` stay `>= 0` or don't wrap. `ExchangeTransactionActuator.validate()` only bounds the *increasing* side of the trade against `dynamicStore.getExchangeBalanceLimit()` [4](#0-3) ; it does not independently re-derive and bound-check the *decreasing* side (the counter-token balance that gets reduced by `buyTokenQuant`), relying entirely on `ExchangeCapsule.transaction()`'s (hardened-only) post-condition check to catch a negative result. Because `buyTokenQuant` is produced by `ExchangeProcessor` (the non-strict-math AMM math implementation), any rounding/precision behavior in that processor that yields a `buyTokenQuant` larger than the actual pool balance will silently drive the opposing token balance negative (or overflow) on the legacy path with no exception thrown, corrupting the on-chain `Exchange`/`ExchangeV2` capsule state and creating an unbacked balance that other market participants can then drain via subsequent `ExchangeTransactionContract` calls — directly analogous to the Poloniex incident, where an unknown flaw in balance/order accounting let an attacker extract exchange funds beyond what was legitimately available.

### Impact Explanation
If a crafted sequence of `ExchangeTransactionContract` calls can drive `firstTokenBalance` or `secondTokenBalance` negative (or wrap via overflow) on the non-hardened path, the on-chain bonding-curve invariant that backs all TRC10/TRX liquidity in that exchange pool is broken. Any subsequent participant trading against that corrupted pool can receive tokens/TRX that are not actually backed by the pool's real holdings, i.e., an unbacked balance / theft of funds condition — matching the "Medium" severity, fund-loss nature of the referenced Poloniex report.

### Likelihood Explanation
Reachable by any account holding a small amount of TRX or the relevant TRC10 token: `ExchangeTransactionContract` is a broadcastable, unprivileged transaction type executed purely through `ExchangeTransactionActuator`, requiring only that an exchange pool exists and the caller has enough balance to cover the trade and fee [5](#0-4) . Exploitability depends on whether `ExchangeProcessor`'s (non-strict-math) `exchange()` computation can be manipulated (e.g., via extreme `sellTokenQuant` values or repeated small trades) to produce a `buyTokenQuant` exceeding the true balance — I was not able to fully inspect `ExchangeProcessor.java`'s and `SafeExchangeProcessor.java`'s exact math in the final iteration (tool budget exhausted), so I cannot conclusively prove a concrete input that triggers the negative-balance condition; this is the main open uncertainty.

### Recommendation
Apply the same non-negative-balance and overflow-checked arithmetic used in the `hardenedCalc` branch unconditionally (i.e., always use `StrictMathWrapper.addExact/subtractExact` and always throw `ContractValidateException` if either resulting balance is negative), rather than gating this safety check behind the `AllowHardenExchangeCalculation` proposal switch in `ExchangeCapsule.transaction()`. Additionally, `ExchangeTransactionActuator.validate()` should independently verify, prior to execution, that the projected post-trade balance of the token being bought will not go negative, not only that the increasing side stays under `exchangeBalanceLimit`.

### Proof of Concept
Not fully constructible without inspecting `ExchangeProcessor.java`'s and `SafeExchangeProcessor.java`'s exact `exchange()` math (not retrieved before tool budget ran out). Conceptually: on a chain where `AllowHardenExchangeCalculation` is `0` (default/legacy behavior), submit an `ExchangeTransactionContract` with a `quant`/`expected` combination against a low-liquidity exchange pool such that `ExchangeProcessor.exchange()` returns a `buyTokenQuant` greater than the current opposing `tokenBalance`; `ExchangeCapsule.transaction()` will then set `newSecondTokenBalance` (or `newFirstTokenBalance`) negative without throwing, and the corrupted `ExchangeCapsule`/`ExchangeV2` record is persisted via `Commons.putExchangeCapsule(...)` [6](#0-5) .
