### Title
Unvalidated array-index derived from attacker-controlled calldata in `ValidateMultiSign` precompile can throw an uncaught exception - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.ValidateMultiSign.execute()` computes an index into the `words` array (`words[3].intValueSafe() / WORD_SIZE`) directly from attacker-supplied `TriggerSmartContract` calldata and uses it to index `words[...]` without validating it against `words.length` or against negative values, before any guarding try/catch is entered.

### Finding Description
`execute(byte[] rawData)` first parses the raw call data into a `DataWord[] words` array with `DataWord.parseArray(rawData)`, whose length is only as large as the supplied calldata allows: [1](#0-0) 

The size guard `isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)` at line 1053 is only invoked when `VMConfig.allowTvmOsaka()` is enabled: [2](#0-1) 

When `allowTvmSelfdestructRestriction()` is enabled but the Osaka guard is not (or with any pre‑Osaka node), the code computes:
```java
int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
```
`words[3]` is fully attacker-controlled (it is the 4th 32-byte word of the calldata) and its value divided by `WORD_SIZE` is used directly as an index into `words[]` — with no check that the resulting index is `>= 0` and `< words.length`. A caller can trivially set `words[3]` to a large or negative value so that `words[3].intValueSafe() / WORD_SIZE` is out of range, producing an `ArrayIndexOutOfBoundsException` (or, via `intValueSafe()` clamping/overflow, a negative index).

Unlike its sibling precompile `BatchValidateSign`, whose public `execute()` wraps the entire body in a `try { return doExecute(data); } catch (Throwable t) { ... return Pair.of(true, new byte[WORD_SIZE]); }`: [3](#0-2) 

`ValidateMultiSign.execute()` has no outer catch at all. The only `try/catch(Throwable)` in the method is nested inside `if (account != null) { ... }`, which is reached only *after* the vulnerable index computation and array-extraction calls: [4](#0-3) 

This is confirmed by the project's own regression test comments, which describe this exact scenario as the "documented pre-activation failure mode": pre-Osaka-activation, malformed calldata to `ValidateMultiSign` reaches the legacy decoder and can raise a `RuntimeException` because "this precompile has no outer catch": [5](#0-4) 

This is directly analogous to the referenced CVE-2021-47269: an externally supplied index (`wIndex` in USB dwc3 vs. `words[3]`-derived index here) is used to dereference/access an array without bounds validation, causing an unhandled fault deep in a code path reachable by any unprivileged caller.

### Impact Explanation
The `ValidateMultiSign` precompile is directly callable by any TVM contract via a `CALL`/`STATICCALL` to its fixed precompile address, which itself is reachable from any unprivileged account via `TriggerSmartContract`. Any caller can supply calldata such that `words[3].intValueSafe() / WORD_SIZE` is out of bounds, throwing an unhandled Java exception from inside the precompile with no local catch. If this propagates past the calling TVM frame uncaught (as the project's own test comments document as the pre-fix behavior — "the outer frame must not inherit an exception" being the property TIP-854 specifically introduces), it manifests as an unexpected runtime exception surfacing during smart-contract execution rather than a controlled EVM/TVM revert. This risks inconsistent transaction processing/exception handling across nodes and, in the worst case, destabilizes execution of any block containing such a transaction — a liveness risk for the node processing it.

### Likelihood Explanation
Trivial to trigger: an attacker only needs to deploy or reuse a simple contract that performs a low-level `CALL` to the `ValidateMultiSign` precompile address with crafted calldata where the 4th word (`words[3]`) is an out-of-range multiple of `WORD_SIZE`. No special privileges, existing account permissions, or specific chain state are required — this is reachable by any unprivileged contract deployer/caller. The condition under which the outer-frame protection (TIP-854 `isValidAbiEncoding` guard) applies is gated by `VMConfig.allowTvmOsaka()`; on any deployment where this hardfork switch is not yet active, the legacy, unguarded path is used.

### Recommendation
Add an explicit bounds check (`index >= 0 && index < words.length`) before every use of `words[3].intValueSafe() / WORD_SIZE` (and the corresponding pattern in `BatchValidateSign.doExecute()` for defense-in-depth) in `ValidateMultiSign.execute()`, independent of the `allowTvmOsaka()`/`allowTvmSelfdestructRestriction()` flags, and wrap the entire `execute()` body in a top-level `try/catch(Throwable)` (mirroring `BatchValidateSign.execute()`) so malformed input always degrades to a safe `Pair.of(true, DATA_FALSE)` rather than propagating an unhandled exception.

### Proof of Concept
1. Deploy a trivial contract that performs a low-level `call` to the `ValidateMultiSign` precompile address.
2. Construct calldata consisting of at least the ABI header words, where the 4th word (`words[3]`) is set to a value whose `intValueSafe() / WORD_SIZE` is far larger than the number of words actually present (e.g., `0xFFFFFFFF`), while `VMConfig.allowTvmOsaka()` is not active on the target node (default/pre-hardfork state).
3. Trigger the contract via a normal `TriggerSmartContract` transaction; `words[words[3].intValueSafe() / WORD_SIZE]` in `PrecompiledContracts.ValidateMultiSign.execute()` (actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1067) throws an `ArrayIndexOutOfBoundsException` with no enclosing try/catch to absorb it, exactly as documented by `ValidateMultiSignContractTest.testTip854PreActivationNoOp` in the codebase's own test suite.
