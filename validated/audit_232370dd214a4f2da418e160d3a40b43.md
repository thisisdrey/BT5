Confirmed: `auth_password`/`auth_token` is only used in `stacks-signer/src/client/stacks_client.rs` as an outgoing `Authorization` header when the signer calls the node's RPC — it is never checked by `SignerEventReceiver` on inbound requests. The event HTTP server (`libsigner/src/events.rs`) has no authentication mechanism at all for incoming POSTs.

### Title
Unauthenticated forged `BlockValidateResponse` injection via `/proposal_response` - (File: libsigner/src/events.rs)

### Summary
`SignerEventReceiver::next_event` accepts any POST to `/proposal_response` and deserializes the body directly into `BlockValidateResponse` with no signature, no auth token, and no origin/source-IP check, then wraps it as `SignerEvent::BlockValidationResponse` and forwards it unchanged to the signer runloop. The signer's own `auth_password`/`auth_token` mechanism only protects the outbound direction (signer → node RPC), never inbound (node → signer event port), so nothing authenticates that a `/proposal_response` POST actually came from the local trusted `stacks-node`.

### Finding Description
The claimed equality — "`BlockValidationResponse` forwarded to runloop == a response the node's block-validation logic actually produced" — is broken. The code path is:

- `next_event` dispatches `/proposal_response` POSTs straight to `process_event::<T, BlockValidateResponse>(request)` [1](#0-0) .
- `process_event` reads the raw body, ACKs the request, then does `serde_json::from_slice(body.as_bytes())` into `BlockValidateResponse` with no signature/HMAC/token check anywhere in the function [2](#0-1) .
- `TryFrom<BlockValidateResponse> for SignerEvent<T>` is a pure passthrough wrapper, performing zero validation [3](#0-2) .
- `forward_event` sends this event straight to the runloop channel with no further checks [4](#0-3) .
- The runloop's `handle_block_validate_response` trusts the verdict directly: `Ok` variants flow into `handle_block_validate_ok`, which can `mark_pre_committed` and `send_block_pre_commit` (broadcast over StackerDB) [5](#0-4) ; `Reject` variants flow into rejection handling that marks the block locally rejected and broadcasts a rejection [6](#0-5) .

The only "auth" mechanism in the whole signer/node coupling (`auth_password` / `auth_token`) is used exclusively as an outbound `Authorization` header the signer sends when calling the node's RPC endpoint (`stacks-signer/src/client/stacks_client.rs`); it is never verified by `SignerEventReceiver` on the inbound `/proposal_response` (or any other) endpoint. The sample production config even binds the signer's event listener to `0.0.0.0:30000` [7](#0-6) , i.e., all interfaces, so this is a realistic deployment posture, not merely a localhost-only convenience listener.

The attack requires the attacker to know a `signer_signature_hash` currently tracked by the signer (`block_lookup_by_reward_cycle`) — otherwise the forged response is silently ignored [8](#0-7) . That hash is not secret: block proposals are gossiped over the `.miners` StackerDB contract, which any StackerDB-reachable peer can observe, so an attacker who can reach both the gossip layer and the signer's event port can supply a matching hash with an attacker-chosen verdict (`Ok` or `Reject`), even though the real `stacks-node` never validated that block or reached a different verdict.

### Impact Explanation
An attacker who can reach the signer's bound event port can inject a forged validation verdict for a block whose hash they observed via StackerDB gossip:
- A forged `Ok` verdict makes the signer skip real node validation, mark the block pre-committed, and broadcast a signed pre-commit over StackerDB toward the 70% signature threshold — an unauthenticated write into signer state that also propagates network-wide fake "validated" endorsement data.
- A forged `Reject` verdict makes the signer prematurely mark a legitimately-valid block as locally rejected and broadcast a rejection, and frees the "submitted validation" slot (`check_pending_block_validations`), disrupting the block-approval pipeline for that signer.

This is repeatable per targeted block hash and per signer instance reachable on the network, matching "unauthenticated/unauthorized write to state" and "network-wide propagation of forged data."

### Likelihood Explanation
Preconditions: (1) network reachability to the signer's event HTTP port (plausible per the sample production config binding `0.0.0.0`), (2) knowledge of a `signer_signature_hash` the target signer currently has a pending/submitted validation for, obtainable by observing StackerDB `.miners` gossip which is not privileged. No node RPC secret, no signer private key, and no local access is required. Attacker cost is a single crafted HTTP POST per targeted block, fully repeatable.

### Recommendation
Require the event dispatcher (the local `stacks-node`) to authenticate its POSTs to the signer's event receiver — e.g., a shared secret/HMAC header checked in `next_event`/`process_event` before deserializing the body, or bind the event listener to loopback only and reject/refuse connections from non-loopback sources at the `SignerEventReceiver` level, closing the gap left by the fact that `auth_password`/`auth_token` currently only protects the outbound direction.

### Proof of Concept
Rust test plan (net-level):
1. Instantiate a `SignerEventReceiver<T>`, `bind()` it to `127.0.0.1:0`, `add_consumer()` a channel, and spawn `main_loop()` in a thread.
2. From a plain `TcpStream::connect` (simulating an unprivileged remote attacker, no auth headers), send:
   `POST /proposal_response HTTP/1.1\r\nHost: ...\r\nContent-Length: N\r\n\r\n{<hand-crafted BlockValidateResponse::Reject JSON with an arbitrary signer_signature_hash>}`
3. Assert the out-channel receives `SignerEvent::BlockValidationResponse(BlockValidateResponse::Reject(...))` matching the attacker-supplied payload, with no prior authentication step exercised anywhere in the path (`next_event` → `process_event` → `TryFrom<BlockValidateResponse>` → `forward_event`), confirming injection succeeds from an unauthenticated connection.

    fn forward_event(&mut self, ev: SignerEvent<T>) -> bool {
        if self.out_channels.is_empty() {
            // nothing to do
            error!("No channels connected to event receiver");
            false
        } else if self.out_channels.len() == 1 {
            // avoid a clone
            if let Err(e) = self.out_channels[0].send(ev) {
                error!("Failed to send to signer runloop: {:?}", &e);
                return false;
            }
            true
        } else {
            for (i, out_channel) in self.out_channels.iter().enumerate() {
                if let Err(e) = out_channel.send(ev.clone()) {
                    error!("Failed to send to signer runloop #{}: {:?}", i, &e);
                    return false;
                }
            }
            true
        }
    }

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
