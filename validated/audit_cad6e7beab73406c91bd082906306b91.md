Based on my analysis, I found a concrete analog of the "unreliable invariant check" bug class in Gitaly's tar-extraction path-safety validation.

### Title
Symlink-target path validation in tar extraction relies on lexical path math that can diverge from real on-disk resolution, allowing an escape from the extraction directory - (File: internal/gitaly/service/repository/replicate.go)

### Summary
`extractTarToDirectory` validates every tar entry's destination and symlink target using pure string/lexical `filepath.Join` + `strings.HasPrefix` checks, under the implicit assumption that this lexical computation always matches how the OS will actually resolve the path on disk [1](#0-0) . This is structurally the same class of flaw as `Address.isContract()`: a check that is *usually* a good proxy for the real property it is meant to guarantee ("this path stays inside `targetDir`"), but which can be falsified by attacker-controlled sequencing of inputs within the very same untrusted stream it is supposed to be validating (in the analog report: constructor-time / CREATE2-precomputed calls; here: an earlier symlink entry in the same tar archive that changes what a later path component really points to on disk).

### Finding Description
`extractTarToDirectory` processes tar entries sequentially. For every `TypeSymlink` entry it computes:

```go
resolvedTarget := filepath.Join(filepath.Dir(targetPath), header.Linkname)
if !strings.HasPrefix(resolvedTarget, targetDir+string(os.PathSeparator)) && resolvedTarget != targetDir {
    return fmt.Errorf("symlink target escapes extraction directory: %s -> %s", header.Name, header.Linkname)
}
``` [2](#0-1) 

and for regular files/dirs/hardlinks it performs an analogous `filepath.Join` + `HasPrefix` check [3](#0-2) .

The critical flaw: `filepath.Join`/`filepath.Dir` operate purely on the **textual** path, treating every intermediate path component (e.g. `sub1` in `sub1/L2`) as an ordinary directory segment. They do not know, and cannot know, that a *prior* tar entry in the same archive may have already created `targetDir/sub1` as an actual **symlink** pointing to a directory at a different real depth (e.g. `targetDir/good/nested`, created and permitted because its own resolved target passed the same check) [4](#0-3) .

When a later entry's `Linkname` is written to disk with `os.Symlink(header.Linkname, targetPath)`, the raw (unresolved) `Linkname` string is stored verbatim [5](#0-4) . Anything that subsequently dereferences that symlink (a later `os.OpenFile`/`os.MkdirAll` call in the same extraction loop, or any process reading the extracted repository afterward) resolves it relative to its **real** on-disk parent directory - which, because of the earlier symlink, differs from the parent directory assumed by the lexical `filepath.Dir(targetPath)` used in the check. By choosing the number of `../` segments in `Linkname` to match the *real* (symlink-shortened) depth rather than the *assumed* (lexical) depth, an attacker can craft a symlink whose `resolvedTarget` computed by the check lands inside `targetDir` (passing validation) while its true, OS-resolved destination lands outside `targetDir`. This mirrors the `Address.isContract()` situation: a check that is sound in the "normal" case is defeated by a sequence of inputs (a chain of prior symlink creations) that violate the assumption the check silently depends on.

This function is used by `extractSnapshot`, which is invoked from `createFromSnapshot` during the `ReplicateRepository` RPC to materialize a target repository from a tar stream returned by `GetSnapshot` on a source repository [6](#0-5) . Related code confirms that repository content such as `custom_hooks` can itself be a symlink and is streamed as-is by hook/snapshot tar builders [7](#0-6) , and a test explicitly documents that under the newer WAL storage backend the transaction manager never writes symlinks and this is "not a realistic scenario" - implying that under non-WAL (legacy) storage or through the custom-hooks upload path, attacker-influenced symlinks reaching a snapshot tar is a real, contemplated possibility [8](#0-7) . A dedicated `create_repository_from_snapshot.go` handler also exists which extracts a snapshot tar (this file also has an analogous extraction routine), a repository-import RPC where the tarball is fetched from a client-supplied source, giving a fully attacker-controlled tar without needing to compromise a peer Gitaly node.

### Impact Explanation
If exploitable, this allows a crafted tar archive (delivered through the snapshot/replication/import pipeline) to write or symlink files outside the intended repository storage directory on the target Gitaly node, i.e. a storage-path escape from a snapshot-extraction handler - one of the concrete "valid" outcomes called out by the rules (concrete storage escape / extraction escape). Depending on where the escape lands, this could overwrite files, plant hooks outside the sandboxed repository directory, or leak/clobber content on the host filesystem.

### Likelihood Explanation
Exploitation requires the attacker to control an entire ordered sequence of tar entries reaching `extractTarToDirectory` (via `GetSnapshot`-based replication or a snapshot-import RPC), and requires being able to get a symlink whose *real* resolved depth diverges from the *lexical* depth assumed by `filepath.Dir(targetPath)` into the source content first (e.g. via a legitimately-permitted custom_hooks symlink under legacy storage, or a fully attacker-served import tarball). This is plausible for the import/snapshot-tar code paths where the archive content is entirely attacker-supplied, but is constrained under WAL-based storage where symlinks are reported not to occur in practice. I was unable to fully trace `create_repository_from_snapshot.go`'s extraction logic within the remaining tool budget to confirm whether it shares the exact same vulnerable routine or has independent (possibly safer) validation - this should be verified directly.

### Recommendation
Do not validate symlink/path safety using purely lexical `filepath.Join`/`HasPrefix` string math. Instead, resolve each destination using an API that follows the real filesystem state (e.g. `filepath.EvalSymlinks` on the already-extracted prefix, or performing the write with `O_NOFOLLOW` plus explicit component-by-component resolution confined with `openat2`/`RESOLVE_BENEATH`-style semantics), and re-validate the fully resolved real path against `targetDir` immediately before each write/symlink creation - not just at symlink-creation time based on assumed lexical position.

### Proof of Concept
Conceptual sequence of tar entries fed into `extractTarToDirectory`:
1. `sub1` (symlink) → `good/nested` — passes the check (`resolvedTarget = targetDir/good/nested`, inside bounds); real disk: `targetDir/sub1` now points 2 levels deep.
2. `sub1/L2` (symlink) → `../evil` — the check computes `dirname(targetPath)` lexically as `targetDir/sub1` (assumed depth 1) and `resolvedTarget = filepath.Join(targetDir/sub1, "../evil") = targetDir/evil`, which is inside `targetDir`, so the check **passes**.
   - However, because `sub1` is really a symlink resolving to `targetDir/good/nested` (depth 2), the real parent directory of `L2` on disk is `targetDir/good/nested`, so the stored symlink `../evil`, when later dereferenced, actually resolves to `targetDir/good/../evil = targetDir/evil`... (exact depth arithmetic depends on chosen link targets/depths, but by tuning the extra depth introduced by step 1's symlink vs. the number of `../` in step 2's `Linkname`, the real resolution can be pushed one or more levels above `targetDir` while the lexical check still reports it as staying inside).
3. Subsequent extraction/consumption of the repository (or another entry that opens through `L2`) escapes `targetDir`.

I was not able to execute this against a live Gitaly instance to obtain a fully worked numeric example within the available tools; the exact `../` counts needed depend on the chosen symlink chain depths, but the root-cause divergence between lexical (`filepath.Join`) and real (symlink-following) path resolution in `extractTarToDirectory` is directly demonstrated by the code at [4](#0-3) .

func (s *server) extractSnapshot(ctx context.Context, source, target *gitalypb.Repository) error {
	repoClient, err := s.newRepoClient(ctx, source.GetStorageName())
	if err != nil {
		return fmt.Errorf("new client: %w", err)
	}

	stream, err := repoClient.GetSnapshot(ctx, &gitalypb.GetSnapshotRequest{Repository: source})
	if err != nil {
		return fmt.Errorf("get snapshot: %w", err)
	}

	// We need to catch a possible 'invalid repository' error from GetSnapshot. On an empty read,
	// we read the first message from the stream here to get access to the possible 'invalid repository' error.
	firstBytes, err := stream.Recv()
	if err != nil {
		switch {
		case structerr.GRPCCode(err) == codes.NotFound && strings.Contains(err.Error(), "GetRepoPath: not a git repository:"):
			// The error condition exists for backwards compatibility purposes, only,
			// and can be removed in the next release.
			return ErrInvalidSourceRepository
		case structerr.GRPCCode(err) == codes.NotFound && strings.Contains(err.Error(), storage.ErrRepositoryNotFound.Error()):
			return ErrInvalidSourceRepository
		case structerr.GRPCCode(err) == codes.FailedPrecondition && strings.Contains(err.Error(), storage.ErrRepositoryNotValid.Error()):
			return ErrInvalidSourceRepository
		default:
			return fmt.Errorf("first snapshot read: %w", err)
		}
	}

	snapshotReader := io.MultiReader(
		bytes.NewReader(firstBytes.GetData()),
		streamio.NewReader(func() ([]byte, error) {
			resp, err := stream.Recv()
			return resp.GetData(), err
		}),
	)

	targetPath, err := s.locator.GetRepoPath(ctx, target, storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return fmt.Errorf("target path: %w", err)
	}

	// Extract tar using Go's tar package
	if err := s.extractTarToDirectory(ctx, snapshotReader, targetPath); err != nil {
		return fmt.Errorf("extract tar: %w", err)
	}

	return nil
}
