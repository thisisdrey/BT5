### Title
Unchecked attacker-controlled array-length field in `BatchValidateSign` precompile causes unbounded allocation / node crash - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `BatchValidateSign` precompiled contract (reachable via `CALL`/`STATICCALL` from any TVM contract, i.e. by any unprivileged transaction sender) decodes attacker-controlled ABI-encoded input by reading a length word directly from calldata and using it, unchecked, to size a Java array. When the hard-fork flag `allowTvmSelfdestructRestriction` is disabled, no upper bound is enforced on this length before allocation, allowing a caller to force an allocation of up to `Integer.MAX_VALUE` array slots while paying energy proportional only to the *raw calldata length*, not to the value encoded inside it.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read a length directly out of the ABI words and allocate an array of that size with no bounds check: [1](#0-0) 

These helpers are invoked from `BatchValidateSign.doExecute`. A bound check (`sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE`) exists, but it is only performed `if (VMConfig.allowTvmSelfdestructRestriction())`. When that flag is not enabled (older/alternate execution path still present in the codebase and still selected as the fallback branch), `extractBytesArray`/`extractBytes32Array` are called with no size validation at all: [2](#0-1) 

Energy metering for this precompile is computed purely from the raw calldata length, not from the decoded length field used for allocation: [3](#0-2) 

This means an attacker can submit a very small `data` payload (so `cnt`/energy charged is tiny or zero) that nonetheless encodes a huge length word (up to `DataWord.intValueSafe()`'s maximum positive 4-byte value, i.e. close to `Integer.MAX_VALUE`, since `intValueSafe` only clamps to `Integer.MAX_VALUE` on overflow — it does not reject large-but-representable values): [4](#0-3) 

The result is `new byte[len][]` where `len` can approach `Integer.MAX_VALUE`, causing the node executing the transaction to attempt a multi-gigabyte allocation, throwing `OutOfMemoryError` or stalling the JVM — this is directly analogous to the CVE's "unchecked cast on a dimension parameter that is zero or exceeds i32::MAX, violating preconditions and causing undefined behavior/DoS."

### Impact Explanation
Any account can craft a transaction (or have a deployed contract execute a `CALL`/`STATICCALL`) that invokes `BatchValidateSign` with a crafted length field, causing every full node that executes/validates the transaction to attempt an oversized array allocation. This can produce `OutOfMemoryError`, degrade or crash node processes, and is cheap for the attacker because the energy charge is decoupled from the actual size used for allocation. This matches the in-scope "node crash or halt" impact category (precompiles / TVM opcodes reachable from an unprivileged contract call).

### Likelihood Explanation
The precompile is reachable by any address via a standard TVM `CALL`, requiring no special privilege, SR/witness status, or node access. The vulnerable path is guarded only by the `allowTvmSelfdestructRestriction` hard-fork flag; if that proposal is not activated (or reverted/rolled back in some deployment/testing configuration), the vulnerable code executes unconditionally on any call to this precompile address. Exploitation requires only constructing a specific ABI-encoded payload, no cryptographic material or race condition.

### Recommendation
Enforce the `MAX_SIZE`/length bound checks in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` unconditionally (not gated behind `allowTvmSelfdestructRestriction`), reject any length that does not correspond to the actual size of `data`, and charge energy proportional to the decoded array length before allocation, not merely to `data.length`.

### Proof of Concept
1. Deploy or use any contract that performs a `STATICCALL`/`CALL` to the `BatchValidateSign` precompiled contract address with `VMConfig.allowTvmSelfdestructRestriction()` disabled (default/older network configuration).
2. Encode calldata per the `BatchValidateSign` ABI (`hash`, offset word for signatures array, offset word for addresses array) such that `data.length` is minimal (few words, keeping `getEnergyForData` cost near zero) but the word at the computed offset (`words[offset].intValueSafe()`, used as `len` in `extractBytesArray`/`extractBytes32Array`) is set to a very large value (e.g., `0x7fffffff`).
3. Submit the transaction; the node executing it calls `extractBytesArray`/`extractBytes32Array`, which performs `new byte[len][]`, attempting to allocate on the order of gigabytes, resulting in `OutOfMemoryError` or severe node stall/crash while the attacker pays negligible energy.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
