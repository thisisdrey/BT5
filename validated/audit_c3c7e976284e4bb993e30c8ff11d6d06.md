Audit Report

## Title
Snowbridge inbound-queue-v1 channel permanently stalls on a deterministically-failing message due to strict sequential nonce with no skip path - (File: `bridges/snowbridge/pallets/inbound-queue/src/lib.rs`)

## Summary
`Pallet::submit` enforces strict, gapless nonce sequencing per channel via `<Nonce<T>>::try_mutate`, but the nonce bump occurs in the same dispatchable as downstream, content-dependent operations (`do_convert` and `send_xcm`) that can fail deterministically for certain payloads. Because FRAME automatically wraps each dispatchable call in a storage transaction and discards all storage writes on an `Err` return, a deterministic failure in `do_convert`/`send_xcm` rolls back the nonce bump together with the failure, permanently blocking that channel since all subsequent messages require `nonce == N+1`.

## Finding Description
In `submit()`, the nonce check and mutation happen first: [1](#0-0) . The dispatchable then continues to decode the payload, convert it to XCM via `Self::do_convert`, burn fees, and send the XCM via `Self::send_xcm`, all within the same call and all capable of returning `Err`: [2](#0-1) . `do_convert` forwards `ConvertMessageError` from `T::MessageConverter::convert` (e.g. `InvalidToken`, `CannotReanchor`, `InvalidDestination`): [3](#0-2) , and `send_xcm` forwards `SendError` variants such as `ExceedsMaxMessageSize` or `NotRoutable`: [4](#0-3) . Both of these are deterministic functions of message content, not relayer behavior. Since Substrate/FRAME dispatchables execute inside an automatic storage transaction that reverts all storage effects (including the `Nonce` mutation) when the call returns `Err`, any deterministic downstream failure for nonce `N` causes `Nonce[channel]` to remain at `N-1` forever, and no future message (`N`, `N+1`, ...) can ever satisfy `envelope.nonce == nonce.saturating_add(1)` again. I confirmed the code structure directly in the pallet file, and confirmed that the only escape hatch in this pallet is the root-only `set_operating_mode`, which halts the entire pallet rather than resolving a single stuck channel: [5](#0-4) . There is no dead-letter/skip mechanism analogous to `pallet-message-queue`'s `OverweightEnqueued`/`execute_overweight` for this pallet's nonce sequencing.

Note: I was not able to fully trace, within the available iterations, the exact FRAME/procedural macro proof that every dispatchable call is wrapped in an implicit storage transaction that reverts on `Err` (the `call.rs` expansion code and `transactional.rs` storage-layer machinery were located but not fully read to their conclusion). This is well-established, documented FRAME behavior (all dispatchables execute within an implicit storage transaction layer), consistent with how `try_mutate`-style storage APIs and this whole pattern are used pervasively across the codebase to guarantee atomicity of dispatch effects, but I flag this as the one link in the causal chain I could not exhaustively re-verify with direct source inspection in this session.

## Impact Explanation
This matches the Polkadot SDK impact gate's "permanent user-fund or bridge-state lock" / "public underpriced work that ... stalls bridge processing" category: a single deterministically-unprocessable message permanently halts delivery of all subsequent Ethereum→AssetHub messages on the affected channel, with no automatic recovery — only a root `set_operating_mode` call, which halts the whole pallet rather than resolving the specific channel.

## Likelihood Explanation
The trigger requires only a permissionless Ethereum Gateway contract transaction whose payload deterministically fails conversion (e.g. an asset that cannot be reanchored) or exceeds the destination's max XCM message size — no malicious relayer, validator, or governance actor is needed, and the failure is 100% reproducible on resubmission since it is a function of message content, not external state.

## Recommendation
Decouple nonce advancement from downstream conversion/dispatch success by committing the nonce increment in its own transactional scope (e.g. using `frame_support::storage::transactional::with_transaction` explicitly around the fallible conversion/send steps, catching their errors) so a bad message is only skipped/dead-lettered rather than blocking the whole sequence — mirroring `pallet-message-queue`'s `OverweightEnqueued`/`execute_overweight` recoverable design.

## Proof of Concept
1. Relayer submits a valid Ethereum event proof for nonce `N` on channel `C`, with payload `Command::SendNativeToken` referencing a `token_id` that cannot be reanchored to the destination's universal location (triggers `ConvertMessageError::CannotReanchor`), or a payload whose XCM exceeds `T::MaxMessageSize`/router hard limit (`SendError::ExceedsMaxMessageSize`).
2. `submit()` passes verification, updates `Nonce<T>[C]` to `N` inside `try_mutate`, then fails at `do_convert`/`send_xcm`; the entire dispatch (including the nonce mutation) is rolled back by FRAME's implicit storage-transaction wrapping of dispatchables, leaving `Nonce<T>[C] == N-1`.
3. Any subsequent legitimate message for channel `C` with `nonce >= N` is rejected by `Error::InvalidNonce` because `envelope.nonce != nonce.saturating_add(1)`, and resubmitting message `N` fails identically every time.
4. Channel `C` is permanently stalled for all further inbound transfers until root intervenes with `set_operating_mode`, which halts pallet-wide processing rather than fixing channel `C`.
