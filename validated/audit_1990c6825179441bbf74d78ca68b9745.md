### Title
EIP-8264 (Amsterdam) SELFDESTRUCT resurrection restores original nonce/code/storage instead of clearing them - (File: core/state/statedb.go)

### Summary
### Finding Description
Under the Amsterdam fork, `StateDB.finaliseAmsterdam` implements EIP-8264's replacement for the classic SELFDESTRUCT burn: instead of deleting a self-destructed account, it must be turned into a balance-only account with nonce reset to 0, code cleared, and all storage cleared, while balance is preserved [1](#0-0) .

The implementation for the non-zero-balance case is:
```go
case obj.selfDestructed:
    if !obj.Balance().IsZero() {
        o := newObject(s, obj.address, obj.origin)
        o.setBalance(new(uint256.Int).Set(obj.Balance()))
        s.setStateObject(o)
        s.markUpdate(addr)
    } else { ... }
``` [2](#0-1) 

`newObject` copies the passed `acct` (here `obj.origin`, the account's **pre-transaction** `types.StateAccount`) wholesale into `data`, including `Nonce`, `CodeHash`, and `Root` [3](#0-2) . Only the balance field is subsequently overwritten via `o.setBalance(...)`. Nonce, CodeHash, and Root are left exactly as they were **before the transaction started**, not reset to their empty/zero equivalents.

Consequences:
- If the contract's pre-transaction nonce was non-zero (e.g. a contract that has itself deployed sub-contracts via `CREATE`, incrementing its own nonce in a prior block), that nonce is restored instead of being reset to 0, violating the EIP-8264 requirement "nonce is reset to 0".
- If the contract had non-empty code before the transaction (which is virtually always true for any contract capable of executing `SELFDESTRUCT`, unless it was created and destroyed within the same transaction), `CodeHash` is restored to the original code hash. Since code storage is content-addressed and never actually deleted from the DB, `GetCode`/execution against this address after finalisation will return the **original bytecode**, i.e. the account keeps its code instead of having it cleared as EIP-8264 mandates.
- `Root` is likewise restored to the pre-transaction storage root instead of `types.EmptyRootHash`, and no call to `deleteStorage`/`handleDestruction` is triggered for this address (that path is only exercised for accounts placed into `stateObjectsDestruct`, which does not happen in this non-zero-balance branch). This means the account's storage trie contents from before the transaction remain intact and reachable, instead of being wiped.

This is the direct analog of the HydraDx bug pattern: a state-changing operation ("self-destruct with non-zero balance" under Amsterdam) is supposed to fully normalize/clear specific fields (analogous to the oracle hook that must be invoked on every liquidity change), but the code takes a shortcut that silently leaves stale pre-transaction data (nonce, code, storage) in place instead of performing the required clearing, producing a persisted account state that is inconsistent with the state actually intended by the fork rule.

### Impact Explanation
This breaks the state-transition/stateRoot equality mandated by EIP-8264: for a mainnet block containing a SELFDESTRUCT of a contract with (a) non-zero nonce accumulated from prior CREATEs, and/or (b) non-empty code/storage, Geth will compute a different post-state (and thus a different `stateRoot`) than a spec-compliant client that actually clears nonce/code/storage. This is a Critical-severity consensus-split condition: on the block that first triggers this path, Geth's produced/accepted state root would diverge from other correctly-implementing clients, and — because the account retroactively keeps live code — subsequent calls to that "destructed" address would execute code that per spec should no longer exist, further diverging execution results (gas usage, further state changes) in all following blocks that interact with the address.

### Likelihood Explanation
The path is only reachable once the Amsterdam fork (`rules.IsAmsterdam`) is activated, and requires a transaction that self-destructs a contract with non-zero balance where the contract's pre-transaction nonce, code, or storage are non-empty — an extremely common real-world pattern (essentially any pre-existing contract self-destructing with remaining balance and non-trivial state). This is very likely to be triggered on the very first block after Amsterdam activation containing such a call, not requiring any adversarial or unusual conditions.

### Recommendation
When building the post-selfdestruct account object for the non-zero-balance case, construct it from a fresh/empty account template (nonce 0, `types.EmptyCodeHash`, `types.EmptyRootHash`) with only the balance carried over, instead of `newObject(s, obj.address, obj.origin)`. Additionally ensure the account's pre-existing storage is explicitly wiped (via the same `deleteStorage`/`handleDestruction` mechanism used for the zero-balance branch) so the storage trie nodes are actually removed at commit time, matching the "all storage cleared" requirement of EIP-8264.

### Proof of Concept
Conceptual reproduction (Amsterdam-activated chain):
1. In block N, deploy contract `C` and have it execute `CREATE` at least once, so its own account nonce becomes non-zero (e.g., nonce = 1) and it stores some non-trivial data in a storage slot.
2. In block N+1 (post-Amsterdam), send ETH to `C` so it has non-zero balance, then call into `C` such that it executes `SELFDESTRUCT` (self-destructing with non-zero balance).
3. Observe the resulting account state for `C` after `Finalise`/`IntermediateRoot`:
   - `finaliseAmsterdam` takes the `obj.selfDestructed && !obj.Balance().IsZero()` branch [4](#0-3) .
   - `newObject(s, obj.address, obj.origin)` is called, which sets `data = *obj.origin`, i.e. `Nonce = 1` (not 0), `CodeHash = <C's original codehash>` (not empty), `Root = <C's original storage root>` (not empty) [3](#0-2) .
   - Only `o.setBalance(...)` is subsequently applied.
4. Expected per EIP-8264: `C`'s account should have Nonce=0, empty code, empty storage, and preserved balance. Actual: `C` retains Nonce=1, its original code (still executable), and its original storage slot value — producing a stateRoot that diverges from a spec-compliant implementation and leaving live code/storage on an account that should have been cleared.

// newObject creates a state object.
func newObject(db *StateDB, address common.Address, acct *types.StateAccount) *stateObject {
	origin := acct
	if acct == nil {
		acct = types.NewEmptyStateAccount()
	}
	return &stateObject{
		db:                 db,
		address:            address,
		origin:             origin,
		data:               *acct,
		originStorage:      make(Storage),
		dirtyStorage:       make(Storage),
		pendingStorage:     make(Storage),
		uncommittedStorage: make(Storage),
	}
}
