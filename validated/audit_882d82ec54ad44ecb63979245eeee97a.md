### Title
Missing Slippage/Rate Bound Protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` Enables Front-Running Fund Loss - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The `ExchangeInjectContract` and `ExchangeWithdrawContract` actuators compute the counter-asset amount (`anotherTokenQuant`) purely from the exchange pool's current on-chain balance ratio — effectively the protocol's own internal "price oracle" — without any caller-supplied bound, minimum/maximum, or expected-value check. In contrast, `ExchangeTransactionActuator` explicitly protects callers with a `tokenExpected` slippage check [1](#0-0) . `ExchangeInjectActuator`/`ExchangeWithdrawActuator` lack any equivalent bound, so a transaction broadcaster can trade against the pool via `ExchangeTransactionContract` immediately before the victim's inject/withdraw transaction is packed into a block, skewing the ratio so the victim unknowingly transfers a much larger (inject) or smaller (withdraw) amount of the paired asset than intended.

### Finding Description
`ExchangeInjectActuator.doValidate()`/`execute()` derives `anotherTokenQuant` solely from `firstTokenBalance`/`secondTokenBalance` at execution time: [2](#0-1) 

There is no field in the contract, nor any validation step, that bounds the computed `anotherTokenQuant` (no `expected`/min/max parameter as exists for `ExchangeTransactionContract`). The only guard is `anotherTokenQuant <= 0` [3](#0-2) .

`ExchangeWithdrawActuator.doValidate()` shows the identical pattern, computing `anotherTokenQuant` from the live pool ratio with only a positivity/sufficiency check, again with no expected-value cap: [4](#0-3) 

By comparison, `ExchangeTransactionContract` carries a `getExpected()` field that is checked against the computed exchange rate, protecting the caller against unfavorable price movement between submission and execution: [5](#0-4) 

This asymmetry is the direct java-tron analog of the reported LST oracle issue: a "rate" (here, the AMM pool ratio maintained in `ExchangeCapsule`) is trusted for a state-changing operation without any check on how far it may have moved since the caller last observed it, and there is no mechanism (bound, expected value, or fallback) to protect the caller from a manipulated/adversarial rate at execution time.

### Impact Explanation
Any account (the exchange creator, who is otherwise an ordinary unprivileged transaction sender) submitting `ExchangeInjectContract` or `ExchangeWithdrawContract` can have the resulting counter-asset amount manipulated by an attacker who front-runs with `ExchangeTransactionContract` trades to shift `firstTokenBalance`/`secondTokenBalance` just before the inject/withdraw executes. Because `anotherTokenQuant` is computed at execution time from the then-current (attacker-skewed) ratio with no cap, the victim can be forced to inject far more of the paired asset than intended, or receive far less on withdrawal — a direct, unbounded loss of TRX/TRC10 asset value with no slippage protection, unlike the transaction path which explicitly guards against this via `tokenExpected`.

### Likelihood Explanation
Any address can submit `ExchangeTransactionContract` transactions against any exchange pool at any time (no special permission required) [6](#0-5) , and transaction ordering within a block is influenced by the packing node, making front-running/sandwiching of a pending inject/withdraw transaction practically achievable. The exchange creator has no way to protect themselves since the contract format for Inject/Withdraw provides no expected/bound parameter to reject an unfavorable execution price.

### Recommendation
Add an `expected`/bound field (minimum acceptable `anotherTokenQuant` for inject, maximum acceptable withdrawal cost, or similar) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and validate it in `ExchangeInjectActuator.doValidate()`/`ExchangeWithdrawActuator.doValidate()` the same way `tokenExpected` is validated in `ExchangeTransactionActuator.doValidate()`, so that the calculated counter-asset amount cannot silently deviate from what the caller expected due to pool-ratio manipulation between transaction submission and execution.

### Proof of Concept
1. Exchange creator A holds pool P with `firstTokenBalance`/`secondTokenBalance` at ratio R and broadcasts `ExchangeInjectContract` intending to inject `tokenQuant` of token X, expecting to also contribute roughly `tokenQuant * R` of token Y based on the ratio observed when composing the transaction.
2. Attacker B observes A's pending transaction in the mempool and broadcasts one or more `ExchangeTransactionContract` trades against pool P that shift the ratio dramatically (bounded only by `dynamicStore.getExchangeBalanceLimit()`), then arranges for these to be included in the block immediately before A's transaction.
3. When A's `ExchangeInjectActuator.execute()` runs, `anotherTokenQuant` is recomputed from the now-skewed `firstTokenBalance`/`secondTokenBalance` [7](#0-6) , forcing A to transfer a far larger amount of token Y than intended, with no validation step to reject this (only the `anotherTokenQuant <= 0` check exists).
4. B then reverses their trade (or benefits from the new pool composition), extracting value from A's excess contribution — the same mechanism applies symmetrically to `ExchangeWithdrawActuator`, where B can manipulate the ratio to reduce the amount A receives on withdrawal.

          .get(ByteArray.fromLong(exchangeTransactionContract.getExchangeId()));

      byte[] firstTokenID = exchangeCapsule.getFirstTokenId();
      byte[] secondTokenID = exchangeCapsule.getSecondTokenId();

      byte[] tokenID = exchangeTransactionContract.getTokenId().toByteArray();
      long tokenQuant = exchangeTransactionContract.getQuant();

      byte[] anotherTokenID;
      long anotherTokenQuant = exchangeCapsule.transaction(tokenID, tokenQuant,
          dynamicStore.allowStrictMath(), allowHarden());

      if (Arrays.equals(tokenID, firstTokenID)) {
        anotherTokenID = secondTokenID;
      } else {
        anotherTokenID = firstTokenID;
      }

      long newBalance = subtractExact(accountCapsule.getBalance(), calcFee());
      accountCapsule.setBalance(newBalance);

      if (Arrays.equals(tokenID, TRX_SYMBOL_BYTES)) {
        accountCapsule.setBalance(subtractExact(newBalance, tokenQuant));
      } else {
        accountCapsule.reduceAssetAmountV2(tokenID, tokenQuant, dynamicStore, assetIssueStore);
      }

      if (Arrays.equals(anotherTokenID, TRX_SYMBOL_BYTES)) {
        accountCapsule.setBalance(addExact(newBalance, anotherTokenQuant));
      } else {
        accountCapsule
            .addAssetAmountV2(anotherTokenID, anotherTokenQuant, dynamicStore, assetIssueStore);
      }

      accountStore.put(accountCapsule.createDbKey(), accountCapsule);

      Commons.putExchangeCapsule(exchangeCapsule, dynamicStore, exchangeStore, exchangeV2Store,
          assetIssueStore);

      ret.setExchangeReceivedAmount(anotherTokenQuant);
      ret.setStatus(fee, code.SUCESS);
    } catch (ItemNotFoundException | InvalidProtocolBufferException
        | ContractValidateException | ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }
    return true;
