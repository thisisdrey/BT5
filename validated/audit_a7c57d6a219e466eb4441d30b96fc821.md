### Title
Fixed-window stream throttling allows ~2x `max_streams_per_throttling_interval` burst at window boundary - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Finding Description
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a **fixed, non-sliding** window: it only resets `stream_count` and `last_throttling_instant` when `Instant::now().duration_since(last_throttling_instant) > STREAM_THROTTLING_INTERVAL` [1](#0-0) . `throttle_stream`, invoked on every new QUIC stream via `SwQos::on_new_stream` → `throttle_stream(...)` [2](#0-1) , only sleeps once `streams_read_in_throttle_interval >= max_streams_per_throttling_interval` within the *current* fixed window [3](#0-2) .

Because the window boundary is anchored to `last_throttling_instant` and reset lazily on first stream observed after expiry, an attacker controlling stream-send timing on a single connection can: (1) open the connection and immediately send `max_streams_per_throttling_interval` streams just before window N's boundary is checked, then (2) send another `max_streams_per_throttling_interval` streams immediately after the window resets (which happens as soon as elapsed time crosses `STREAM_THROTTLING_INTERVAL_MS`, i.e., possibly a few ms into window N+1). This yields close to `2 * max_streams_per_throttling_interval` admitted streams within a wall-clock span close to `STREAM_THROTTLING_INTERVAL_MS` (100ms), rather than the intended per-100ms budget, because no sliding/rolling accounting of admitted streams across the boundary exists.

### Impact Explanation
This is a QoS evasion: it lets a single (potentially unstaked) connection push roughly double its allotted stream/transaction ingress rate into the leader's TPU for a short window, disproportionately consuming banking-stage ingress capacity relative to the intended per-source budget enforced by `available_load_capacity_in_throttling_duration` / `max_streams_per_throttling_interval` [4](#0-3) . It matches the "QoS limits cannot be evaded by timing exploitation" category called out in the question.

### Likelihood Explanation
The exploit requires only an unstaked/unprivileged remote client capable of controlling stream send timing on a QUIC connection to the TPU port — no special stake, keys, or peer/gossip control. Achieving precise millisecond-level alignment with the internal timer is difficult from a remote client (network jitter, scheduler jitter on the validator, and the fact that resets are driven by whichever thread happens to observe expiry) but a burst sent right around the expected boundary can realistically get a partial multiple (somewhat above 1x, not a guaranteed clean 2x) of the intended budget repeatably across many 100ms windows.

### Recommendation
Replace the fixed-window reset in `reset_throttling_params_if_needed` with a sliding/rolling window (e.g., token-bucket refill proportional to elapsed time, or tracking timestamps of the last N streams) so that the total streams admitted in any rolling `STREAM_THROTTLING_INTERVAL_MS` window — not just the fixed calendar window — is bounded by `max_streams_per_throttling_interval`.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (test module)
#[tokio::test(start_paused = true)]
async fn test_fixed_window_boundary_burst() {
    let stats = Arc::new(StreamerStats::default());
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams = 10u64;

    // Fill window N right at the boundary.
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(), &counter, max_streams).await;
    }
    // Advance time just past the window boundary.
    tokio::time::advance(STREAM_THROTTLING_INTERVAL + Duration::from_millis(1)).await;

    // Immediately burst again in "window N+1".
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(), &counter, max_streams).await;
    }

    // Assert: total streams admitted within any rolling STREAM_THROTTLING_INTERVAL_MS
    // window must not exceed max_streams_per_throttling_interval.
    // With the current fixed-window implementation, 2*max_streams are admitted
    // within ~STREAM_THROTTLING_INTERVAL_MS + 1ms wall-clock time, violating the invariant.
    assert!(stats.throttled_streams.load(Ordering::Relaxed) == 0);
}
```
Fuzz variant: randomize the timing of each `throttle_stream` call around the window boundary and assert that, for any sliding window of length `STREAM_THROTTLING_INTERVAL_MS`, the count of non-throttled admissions never exceeds `max_streams_per_throttling_interval`; the current implementation fails this invariant near boundaries.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }
