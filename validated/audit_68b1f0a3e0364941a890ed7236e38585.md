After thorough investigation of the Aptos codebase, I found a direct structural analog to the external bug in the `multisig_account` module.

---

### Title
Multisig Transaction Payload Can Be Substituted at Execution Without Re-Validation When Feature Flag Is Disabled — (`aptos-move/framework/aptos-framework/sources/multisig_account.move`)

---

### Summary

When a multisig transaction is created via `create_transaction` (full payload stored on-chain), other owners vote to approve that specific payload. However, at execution time, `validate_multisig_transaction` only enforces payload equality when the `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` feature flag is enabled. When the flag is disabled, a malicious executing owner can submit an entirely different payload and have it executed as the multisig account — directly analogous to the external bug where `tokenOut` was validated at order creation but could be freely changed before `fillOrder`.

---

### Finding Description

**Creation path** — `create_transaction` stores the full payload on-chain and records the creator's implicit approval: [1](#0-0) 

**Approval path** — other owners vote on the transaction identified by its sequence number, trusting the stored payload: [2](#0-1) 

**Execution validation path** — `validate_multisig_transaction` (called by the VM as the prologue) checks payload equality only when the feature flag is on: [3](#0-2) 

When `abort_if_multisig_payload_mismatch_enabled()` returns `false`, the block at lines 1375–1384 is entirely skipped. The hash-only path (lines 1365–1371) is not triggered because `transaction.payload_hash` is `none` for `create_transaction`-style entries. The VM then executes whatever payload the executor provided in the transaction, not the payload that was approved.

The VM confirms the same `executable` used for prologue validation is the one that gets run: [4](#0-3) [5](#0-4) 

The feature constant and its description confirm this is a known gap being addressed by a flag rather than a hard invariant: [6](#0-5) 

---

### Impact Explanation

A malicious owner can:
1. Create a transaction with a benign payload (e.g., "transfer 1 APT to address X").
2. Collect the required approvals from other owners who read the stored payload.
3. Submit the execution transaction with a different payload (e.g., "transfer all APT to attacker's address").
4. When the feature flag is off, `validate_multisig_transaction` passes without comparing payloads, and the substituted payload executes as the multisig account.

This constitutes **direct theft of APT and fungible assets** held by the multisig account — matching the "Direct theft … of APT, fungible assets … or other user-controlled on-chain assets" impact gate.

---

### Likelihood Explanation

- The attacker must be an owner of the multisig account (a regular user role, not a governance admin).
- The `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` feature (flag 70) must be disabled. It is described as "transient," meaning it is not guaranteed to be enabled on all deployments or after a feature rollback.
- Any multisig account using `create_transaction` (full on-chain payload) is affected; `create_transaction_with_hash` is not affected because the hash check at lines 1365–1371 is unconditional.

---

### Recommendation

Remove the feature-flag gate from the payload equality check. The invariant "the payload executed must equal the payload approved" should be unconditional for on-chain-stored payloads:

```move
// Remove the feature flag condition:
if (transaction.payload.is_some() && !payload.is_empty()) {
    let stored_payload = transaction.payload.borrow();
    assert!(
        payload == *stored_payload,
        error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
    );
};
```

---

### Proof of Concept

1. Owner A, B, C form a 2-of-3 multisig account.
2. Owner A calls `create_transaction(owner_a, multisig_addr, benign_payload)` — payload stored on-chain, A's approval recorded.
3. Owner B calls `approve_transaction(owner_b, multisig_addr, 1)` — threshold met.
4. Owner A submits a `MultisigTransaction` with `sequence_number = 1` but with `malicious_payload` (e.g., `coin::transfer<AptosCoin>(multisig_addr, attacker_addr, MAX_AMOUNT)`) as the executable.
5. VM prologue calls `validate_multisig_transaction(owner_a, multisig_addr, malicious_payload_bytes)`.
6. `transaction.payload_hash.is_some()` → false (full payload was stored, not hash) → hash check skipped.
7. `abort_if_multisig_payload_mismatch_enabled()` → false → equality check skipped.
8. Prologue passes; VM executes `malicious_payload` as the multisig account.
9. All APT is transferred to the attacker. [7](#0-6)

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );

        // If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
    }
