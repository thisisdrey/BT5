### Title
Unchecked pre-allocation of `byte[][]` from attacker-controlled length in TVM precompiled contract input parsing - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array` reads an array length directly from decoded calldata words and immediately allocates a two-dimensional array of that size, with no upper bound check and no validation against the number of words actually available in the input buffer, mirroring the `rmpv` bug class of pre-allocating memory from an untrusted length field before confirming sufficient backing data exists.

### Finding Description
`extractBytes32Array` takes the `offset`-th `DataWord` from the parsed input words array and uses `intValueSafe()` on it as an array length, then allocates `new byte[len][]` before reading any elements or checking whether `len` is a sane/bounded value relative to the remaining calldata: [1](#0-0) 

Unlike the sibling helpers `extractBytesArray` and `extractSigArray`, which at least guard against `offset` exceeding `words.length - 1`: [2](#0-1) 

`extractBytes32Array` performs no such check at all before deriving `len` and allocating the outer array — the length value comes straight from attacker-supplied calldata passed to a precompiled contract invoked via a TVM `CALL`/`STATICCALL` opcode, i.e., from any unprivileged contract deployer or caller who can submit a transaction that reaches this precompile.

### Impact Explanation
If `len` can be driven to a very large positive value (e.g., near `Integer.MAX_VALUE`, since `intValueSafe()` only guards against overflow into a valid `int`, not against magnitude), the JVM will attempt to allocate an array of that many object-reference slots. This can throw `OutOfMemoryError` inside the TVM execution path, and depending on how the surrounding execute()/energy-metering try/catch handles `Error` (as opposed to `Exception`), this can crash the node's execution thread or destabilize the full node process — a denial-of-service impact consistent with CWE-400, matching the severity class of the referenced advisory.

### Likelihood Explanation
Reaching this code only requires deploying/calling a contract that invokes the relevant precompiled contract address with crafted calldata containing an inflated length word at the expected offset — no special privileges, staking, or witness/SR status needed. This makes it reachable by any anonymous transaction broadcaster or contract caller, which is the exact threat model called out for in-scope analogs.

### Recommendation
Add an explicit bound check on `len` in `extractBytes32Array` — validating it against `words.length - offset - 1` (the actual number of words remaining) and/or against a hard maximum array size — before allocating `new byte[len][]`, consistent with the pattern already used by `extractBytesArray`/`extractSigArray`. Ensure the pattern is applied uniformly to all length-derived allocations in `PrecompiledContracts.java`.

### Proof of Concept
Exact reachability (which specific precompiled contract type invokes `extractBytes32Array` with a fully attacker-controlled offset/length at runtime) could not be conclusively traced within the available search budget; this would need to be confirmed by tracing all call sites of `extractBytes32Array` in `PrecompiledContracts.java` and validating that the `offset` argument passed to it is attacker-influenced calldata content rather than a fixed, safe internal constant. A Devin session with full-repository access should verify this call-graph path (via `grep`/`ctrl+F` for `extractBytes32Array(`) before treating this as fully confirmed exploitable.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
