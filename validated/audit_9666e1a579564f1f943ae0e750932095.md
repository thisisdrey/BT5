### Title
Unchecked boolean return value of `addAssetAmountV2` in `TransferAssetActuator.execute` can silently burn TRC10 tokens - (File: actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java)

### Summary
`TransferAssetActuator.execute` deducts the TRC10 asset amount from the sender via `reduceAssetAmountV2`, whose boolean result is checked and causes a `ContractExeException` on failure, but then credits the receiver via `addAssetAmountV2` without checking its boolean return value at all. This is the same bug class as the reported Notional issue: an external/state-mutating call's success flag is silently discarded, allowing a partially-successful operation (debit succeeds, credit "fails" but is not reverted) to proceed as if it succeeded.

### Finding Description
In `execute()`: [1](#0-0) 
the sender-side reduction is guarded:
```java
if (!ownerAccountCapsule.reduceAssetAmountV2(assetName.toByteArray(), amount, dynamicStore, assetIssueStore)) {
  throw new ContractExeException("reduceAssetAmount failed !");
}
accountStore.put(ownerAddress, ownerAccountCapsule);

toAccountCapsule.addAssetAmountV2(assetName.toByteArray(), amount, dynamicStore, assetIssueStore);
accountStore.put(toAddress, toAccountCapsule);
```
`addAssetAmountV2` returns a `boolean` (it can return `false`, e.g. on arithmetic overflow of the recipient's existing asset balance — this is exactly why the surrounding codebase treats it as a fallible operation elsewhere), yet here the return value is discarded. Compare to `Commons.adjustAssetBalanceV2`, which performs the equivalent operation and explicitly checks the result and throws `BalanceInsufficientException` when `addAssetAmountV2`/`reduceAssetAmountV2` return `false`: [2](#0-1) 

Because `TransferAssetActuator` already commits the reduced sender balance to `accountStore` (line 80) before the unchecked add, if `addAssetAmountV2` internally fails (returns `false` without mutating the recipient's map, e.g., overflow check), the actuator still calls `ret.setStatus(fee, code.SUCESS)` at: [3](#0-2) 
The transaction is committed as successful (block application in `Manager` treats it as a normal executed transaction), the sender's asset balance has been reduced, and the receiver's balance was never incremented — the tokens are permanently destroyed/lost from total circulating supply without being reflected anywhere, all triggered by an ordinary unprivileged `TransferAssetContract` broadcast.

### Impact Explanation
This breaks TRC10 asset accounting invariants reachable by any account broadcasting a signed `TransferAssetContract` transaction. Tokens debited from the sender can vanish rather than being credited to the receiver, causing a permanent, unrecoverable loss of user funds (asset units disappear from total supply) with no error surfaced to the caller (transaction status is `SUCESS`). This matches the "permanent freezing/loss of funds" and "unbacked balance" impact categories for a Medium/High-severity finding.

### Likelihood Explanation
Triggering the underlying failure path requires the recipient's target asset balance plus incoming amount to hit an overflow/failure condition inside `addAssetAmountV2` (analogous to the overflow-guard case handled explicitly by `Commons.adjustAssetBalanceV2`), which is achievable by any user pre-loading a target account near `Long.MAX_VALUE` for the given asset ID (self-controlled account) and then sending a transfer that would overflow it. This is entirely triggerable via normal `TransferAssetContract` broadcasts without special privileges, making it a realistic, unprivileged-user-reachable scenario, though it does require crafting specific balance conditions.

### Recommendation
Check the boolean return of `addAssetAmountV2` in `TransferAssetActuator.execute`, mirroring the existing check on `reduceAssetAmountV2`, and throw `ContractExeException` (or otherwise abort/roll back the state changes already applied to `ownerAccountCapsule`) if it returns `false`:
```java
if (!toAccountCapsule.addAssetAmountV2(assetName.toByteArray(), amount, dynamicStore, assetIssueStore)) {
  throw new ContractExeException("addAssetAmount failed !");
}
```

### Proof of Concept
1. Attacker (or any user) issues/holds a TRC10 asset and controls two accounts: `ownerAddress` (sender) and `toAddress` (receiver).
2. Pre-fund `toAddress`'s asset balance for the given `assetName` close to `Long.MAX_VALUE` (via prior legitimate transfers, which are permitted since each individual transfer amount only needs to satisfy `amount <= assetBalance` of the sender in `validate()`).
3. Broadcast a `TransferAssetContract` from `ownerAddress` to `toAddress` with an `amount` that, combined with `toAddress`'s existing balance, causes an overflow/failure condition inside `addAssetAmountV2` (see the checked-usage pattern in `Commons.adjustAssetBalanceV2` at [4](#0-3)  confirming this method can fail and return `false`).
4. `TransferAssetActuator.execute` reduces `ownerAccountCapsule`'s asset amount (checked, succeeds) and commits it to `accountStore`, then calls `addAssetAmountV2` on `toAccountCapsule` — which returns `false` and leaves `toAccountCapsule` unmodified — but the actuator ignores this and still commits `toAccountCapsule` and sets `ret.setStatus(fee, code.SUCESS)`.
5. Result: the sender's asset balance decreased by `amount`, the receiver's balance is unchanged, and the transaction is recorded on-chain as successful — `amount` units of the TRC10 asset are permanently lost.
