Confirmed: `apply_action_receipt` (`runtime/runtime/src/lib.rs:776-850`) loads and executes the postponed receipt's actions **without ever checking whether the receiver account still is the "same" account that existed when the receipt was postponed** — it just loads `account_id`'s current `Account` state and applies actions in order. There's no epoch/generation/nonce binding an account's lifecycle to receipts postponed against it.

### Title
Postponed action receipts and pending-data bookkeeping are not purged on `DeleteAccountAction`, letting a stale self-referential `AddKey` receipt bind to a re-created account - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`remove_account` (`core/store/src/utils/mod.rs:505-575`), called from `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`), removes `Account`, `ContractCode`, access keys, gas-key nonces, and `ContractData`, but never removes `TrieKey::PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, or `ReceivedData` entries keyed by that `account_id`. Because `apply_action_receipt`/`process_receipt` (`runtime/runtime/src/lib.rs:776`, `:1367`) resolve postponed receipts purely by `(receiver_id, receipt_id)`/`(receiver_id, data_id)` string keys with no notion of "account incarnation," a postponed self-call receipt survives account deletion and executes against whatever account currently occupies that name once its data dependency is later satisfied.

### Finding Description
1. Attacker's contract on `a.near` calls `setup`, which issues a self-promise (`promise_batch_create(self)` → `promise_batch_action_function_call(.., "finish", ..)`) chained via `promise_then` on some other pending promise, so the resulting `finish` action receipt (`predecessor_id == receiver_id == "a.near"`) carries an `input_data_id` that is not yet satisfied. `process_action_receipt` (`lib.rs:1593-1658`) finds `pending_data_count > 0`, stores the counter under `TrieKey::PendingDataCount{receiver_id: "a.near", ..}`, a `TrieKey::PostponedReceiptId{receiver_id: "a.near", data_id}` link, and the receipt itself under `TrieKey::PostponedReceipt{receiver_id: "a.near", ..}` (`set_postponed_receipt`, `core/store/src/utils/mod.rs:120-127`).
2. Attacker submits a `DeleteAccountAction(beneficiary=attacker)` for `a.near`. `action_delete_account` (`actions.rs:314-390`) refunds the balance and calls `remove_account` (`core/store/src/utils/mod.rs:505-575`), which deletes `Account`, `ContractCode`, access keys/gas keys, and `ContractData` — but not the `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`/`ReceivedData` entries keyed by `"a.near"`. These remain live in the trie.
3. A party legitimately entitled to (re)create the account name `"a.near"` (per `action_create_account`'s naming rules, `actions.rs:167-210` — this must be the exact required predecessor, e.g. the parent domain owner provisioning a subaccount for a new user) creates and funds `"a.near"` again, unaware any pending bookkeeping exists for that name.
4. Once the original dependency resolves (the attacker lets/causes the chained promise to return), `process_receipt`'s `Data` branch (`lib.rs:1367-1474`) finds the `PostponedReceiptId` link still keyed to `"a.near"`, decrements `PendingDataCount` to 0, fetches the stale `finish` receipt via `get_postponed_receipt`, and calls `apply_action_receipt` against the **current** `"a.near"` account/balance.
5. Inside `finish`, `Action::AddKey` runs through `check_actor_permissions` (`actions.rs:739-760`), which only checks `actor_id == account_id` by string equality. Since the receipt's `predecessor_id` was `"a.near"` itself (self-call), `actor_id == account_id` trivially holds regardless of who now controls the name, so the attacker's hard-coded public key is added as `FullAccessKey` to the newly funded account.

### Impact Explanation
This is authorization escalation across accounts/promises leading to theft of funds: the attacker gains a `FullAccessKey` on an account they no longer own and did not create, funded by a different party, and can drain its balance — matching the "account-recreated-inherits-owner-privilege" bounty category.

### Likelihood Explanation
Exploitability depends on a realistic account-recreation pattern actually occurring on mainnet. Because `action_create_account` (`actions.rs:176-201`) strictly enforces that only the exact parent (`is_top_level` → registrar, or `is_sub_account_of(predecessor_id)`) may (re)create a given account name — confirmed by `test_create_account_invalid_sub_account` (`actions.rs:957-972`) and `test_create_top_level_accounts` (`integration-tests/src/tests/features/restrict_tla.rs`) — the literal scenario as posed ("bob.near", an unrelated third party, creates `a.near`) is **rejected by protocol validation** (`ActionErrorKind::CreateAccountNotAllowed`/`CreateAccountOnlyByRegistrar`). `a.near` is a subaccount of `near`; only `near` itself could recreate it, not `bob.near`. The underlying architectural gap (stale postponed-receipt bookkeeping surviving `DeleteAccountAction`) is real and unpatched, but it is only reachable by whichever account is the legitimate naming-parent recreating a subaccount it previously deleted (e.g. a platform account provisioning `user.platform.near` for successive users) — not by an arbitrary unrelated account as literally described.

### Recommendation
Purge `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, and `ReceivedData` entries for `account_id` inside `remove_account` (`core/store/src/utils/mod.rs:505`) when an account is deleted, so no receipt-matching state can outlive the account it targeted and rebind to a differently-owned re-creation of the same name.

### Proof of Concept
Integration/test-loop plan (adjust actor to respect naming rules, e.g. parent `platform.near` recreating `user.platform.near`):
1. Deploy attacker contract to `user.platform.near`; call `setup`, which self-chains a `finish` callback on a slow/attacker-controlled promise (unmet `input_data_id`), verify `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` trie entries exist for `user.platform.near`.
2. Submit `DeleteAccountAction(beneficiary=attacker)` for `user.platform.near`; assert account/keys are gone but the postponed-receipt trie keys above still resolve via `get_postponed_receipt`/`get(TrieKey::PendingDataCount)`.
3. Have `platform.near` submit `CreateAccountAction` + `Transfer` to recreate and fund `user.platform.near` for a new (different) purpose.
4. Trigger resolution of the attacker's original chained promise so the `Data` receipt with the matching `data_id` arrives.
5. Assert the `finish` receipt executes against the newly created `user.platform.near`, that `Action::AddKey` succeeds (no `ActorNoPermission`), and that the attacker's public key is now a `FullAccessKey` on the account — then submit a `Transfer`/drain transaction signed by that key and assert it succeeds, moving the account's funded balance to the attacker.
