Audit Report

## Title
Fee-refund pool self-manipulation via `SwapAssetAdapter::correct_and_deposit_fee` re-quoting the same AMM pool post-dispatch - ([File: substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs])

## Summary
`SwapAssetAdapter::withdraw_fee` quotes and swaps fees against a `pallet-asset-conversion` pool *before* the wrapped call executes, and `correct_and_deposit_fee` re-quotes and swaps the refund against the *same live pool* *after* the wrapped call executes, with no protection against the wrapped call itself having moved that pool's reserves. This lets an unprivileged signed user manipulate the fee-conversion pool inside their own extrinsic to skew the asset-refund exchange rate in their favor at the expense of the pool's liquidity providers.

## Finding Description
`ChargeAssetTxPayment::prepare` calls `withdraw_fee`, which quotes `asset_fee` via `S::quote_price_tokens_for_exact_tokens(asset_id, A::get(), fee, true)` and swaps it into the native/target asset `A` [1](#0-0) . This happens strictly before the call is dispatched, since `prepare` runs pre-dispatch and `post_dispatch_details` runs after [2](#0-1) .

After dispatch, `correct_and_deposit_fee` computes `refund_amount = fee_paid.peek() - corrected_fee` purely in terms of asset `A` (unaffected by pool state), but then converts that fixed `A` amount into `asset_id` by **re-quoting the same pool** via `S::quote_price_exact_tokens_for_tokens(A::get(), asset_id, refund_amount, true)` and immediately swapping at that quote [3](#0-2) .

Both quotes read live AMM reserves with no time-weighting or staleness protection [4](#0-3) [5](#0-4) . The `QuotePrice` trait itself documents this exact limitation: "The quoted price is only guaranteed if no other swaps are made after the price is quoted and before the target swap (e.g., the swap is made immediately within the same transaction)" [6](#0-5) . The refund-quote-then-swap in `correct_and_deposit_fee` itself satisfies this guarantee (no intervening call between them), but the *withdraw-then-refund* pair spans the entire dispatched call, which can include an arbitrary swap against the same pool (directly, or nested via `pallet-utility::batch`/proxy under the same origin) — violating the documented precondition.

Because `refund_amount` is fixed in `A`-asset terms (derived only from weight-based fee correction, independent of the pool), an attacker who shifts the pool's reserves during their own dispatched call controls the `asset_id`-per-`A` exchange rate used to convert that fixed refund back into `asset_id`. By selling `asset_id` into the pool for `A` (or the reverse, depending on the desired skew) before the refund conversion happens, the attacker can bias the refund swap's rate in their favor, extracting value from the pool's liquidity providers rather than receiving a refund computed against an unperturbed price.

## Impact Explanation
This violates the "conserve value and settle exactly once to the rightful beneficiary and amount" invariant for the fee-conversion pool: the tx-fee refund is settled against a price the payer influenced within the same atomic extrinsic, transferring value from the pool's LPs to the payer rather than reflecting a fair, unperturbed exchange rate. This is a genuine cost-correctness defect reachable by any unprivileged signed account holding the fee asset, with no relayer, validator, or governance action required, matching the "runtime bugs that compromise intended behavior" / value-conservation pivot in the impact gate. However, the extractable amount per transaction is inherently bounded by `refund_amount` — the weight-based fee-correction delta of a single extrinsic — which is typically small, so the practical severity is limited to shallow pools and is not an unbounded theft or unbacked mint.

## Likelihood Explanation
Exploitability requires only an unprivileged account able to submit a call that swaps in the exact pool pair configured for `SwapAssetAdapter`'s `A`/`asset_id`, with sufficiently shallow liquidity to move price meaningfully for a small trade — a low bar, and achievable via a single extrinsic (or `pallet-utility::batch`) with no third-party cooperation. The per-transaction gain is capped by the fee-correction delta, so profitability depends on pool depth relative to typical refund sizes and the cost of the manipulation trade's own AMM fees, making this repeatable but of modest per-transaction magnitude.

## Recommendation
- Lock in the exchange rate used for both withdrawal and refund at `prepare` time (pre-dispatch) rather than re-quoting the pool in `correct_and_deposit_fee`.
- Alternatively, use a manipulation-resistant reference price (e.g., a TWAP maintained by `pallet-asset-conversion`) specifically for tx-fee accounting, or bound/reject refunds when pool reserves have moved beyond a small tolerance between the pre- and post-dispatch reads.

## Proof of Concept
1. Attacker identifies a shallow `pallet-asset-conversion` pool for `(A::get(), asset_id)` used by a runtime's `SwapAssetAdapter` configuration.
2. Attacker submits an extrinsic charged via `ChargeAssetTxPayment` with `asset_id` as the fee asset, whose dispatched call (or a `pallet-utility::batch` inner call) swaps a large amount against that same pool, shifting its reserves.
3. `withdraw_fee` (pre-dispatch, `payment.rs:142-146`) charges the fee against the pre-manipulation price.
4. The dispatched call executes, moving the pool per step 2.
5. `correct_and_deposit_fee` (post-dispatch, `payment.rs:262-286`) computes and swaps the refund against the now-skewed reserves, yielding a refund inconsistent with a fair unperturbed price, at the pool LPs' expense.
6. A Rust integration test in `pallet-asset-conversion-tx-payment`'s test harness can reproduce this by constructing a mock call that invokes `pallet_asset_conversion::swap_exact_tokens_for_tokens` on the fee pool before returning, then asserting the refunded `asset_id` amount differs from the amount computed against the pre-call reserves.

			amount: T::Balance,

				return None;

			if balance1.is_zero() {
				return None;

			} else {
				Self::quote(&amount, &balance2, &balance1).ok()
