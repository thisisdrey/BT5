### Title
Remote peer can poison AtlasDB by returning a `GetAttachmentResponse` whose content hash does not match the requested `AttachmentRequest.content_hash` - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a `GetAttachmentResponse` from a remote peer and inserts `response.attachment` into `self.attachments` without ever comparing `response.attachment.hash()` to the `content_hash` that was requested via the corresponding `AttachmentRequest`. The link between the outgoing request's `content_hash` and the returned attachment is dropped entirely, so any peer can serve arbitrary content for any requested hash and have it accepted and persisted into the local `AtlasDB`.

### Finding Description
The expected invariant is `served_hash == committed_content_hash`: an attachment fetched in response to `AttachmentRequest{content_hash: H1, ...}` must hash (via `Attachment::hash`, i.e. `Hash160::from_data(&self.content)`) to `H1` [1](#0-0) .

In `extend_with_attachments`, the loop iterates `results.succeeded.drain()` — pairs of `(AttachmentRequest, Option<StacksHttpResponse>)` — decodes the HTTP body via `decode_atlas_get_attachment()`, and unconditionally inserts the returned `Attachment` into `self.attachments`, discarding `request.content_hash` completely: [2](#0-1) 

`GetAttachmentResponse`'s `Deserialize` impl builds the `Attachment` straight from whatever hex-encoded bytes the peer sent, with no hash validation at decode time either: [3](#0-2) 

Downstream, in `AttachmentsDownloader::run`, when the state machine reaches `Done`, every attachment in `context.attachments` is looked up in `AtlasDB` by its *own* (attacker-controlled) hash via `find_all_attachment_instances(&attachment.hash())`, and then unconditionally stored via `insert_instantiated_attachment(&attachment)` regardless of whether any matching on-chain `AttachmentInstance` was found: [4](#0-3) 

Because the `content_hash` from the original request is never compared against `response.attachment.hash()`, a malicious peer that is selected as a download source (which requires only being an outbound sync peer providing a data URL — no privileged role, secret, or key) can respond to a `GET /v2/attachments/<H1>` request with content whose real hash is `H2 != H1`. That data is accepted into `context.attachments` and unconditionally written into the local `AtlasDB` via `insert_instantiated_attachment`, even though no on-chain `AttachmentInstance` ever committed to `H2`.

### Impact Explanation
This lets a remote, unprivileged peer poison a node's `AtlasDB` with attacker-chosen content that was never referenced by any on-chain commitment. Since Atlas attachments back BNS name resolution, this breaks the "attachment content matches the committed hash" invariant, causing the node to store/serve non-canonical data as if it were canonical — matching the "High: serving non-canonical state as canonical, attachment/BNS mismatch" category. The attack is repeatable per request/response round-trip and requires only that the attacker's node/URL be selected among the peer's data-URL sources for that batch.

### Likelihood Explanation
The precondition is that the attacker's node is one of the peer URLs used for attachment inventory/download (an outbound sync peer that advertises a data URL and is picked in `get_prioritized_attachments_requests`) — no secret, no privileged role, no local access needed; any node participating in the P2P network with a reachable data URL can qualify. Attacker cost is a single crafted HTTP response per targeted `content_hash`.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; if it doesn't match, treat it as a failed/faulty response (bump `report.bump_failed_requests()` and/or mark the peer faulty) rather than accepting the content.

### Proof of Concept
1. In `stackslib/src/net/atlas/tests.rs` (or a new test module in `download.rs`), construct an `AttachmentRequest` with `content_hash = H1` (e.g., `Hash160::from_data(b"expected")`).
2. Build a `StacksHttpResponse` whose body, when passed through `decode_atlas_get_attachment()`, yields `GetAttachmentResponse { attachment: Attachment::new(b"malicious payload".to_vec()) }`, whose real hash `H2 = Attachment::new(b"malicious payload".to_vec()).hash()` differs from `H1`.
3. Populate a `BatchedRequestsResult::succeeded` map with `{request: Some(response)}` and call `AttachmentsBatchStateContext::extend_with_attachments(context, &mut results)`.
4. Assert that `context.attachments` contains the `Attachment` with hash `H2` (i.e., `context.attachments.iter().any(|a| a.hash() == H2)`), proving the mismatched-hash attachment was accepted despite `H2 != H1`, with no equality check present anywhere in the call path.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
