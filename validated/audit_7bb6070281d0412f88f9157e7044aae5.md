### Title
Storage-deposit accounting corruption via same-contract reentrancy in `pallet-revive`'s `Stack` frame execution - (File: `substrate/frame/revive/src/exec.rs`, `substrate/frame/revive/src/metering/storage.rs`)

### Summary
`pallet-revive`'s contract execution stack previews a parent contract's *pending* storage-deposit diff onto a cloned `ContractInfo` so that a same-contract (or transitively same-contract) reentrant child frame can see up-to-date accounting for pro-rata refund calculation. Before the fix landed, this preview-applied clone was persisted by the child via `insert_contract`, while the parent's own still-pending diff (`own_contribution`) was *not* consumed — so when the parent resumed and finalized, it re-applied the same diff on top of storage that already contained it, double-counting `storage_items`/`storage_bytes`/`storage_*_deposit`. This is structurally the same bug class as the Bunni report: a value/state mutation (here, the storage-deposit diff preview) is exposed to a re-entering caller before the "after" bookkeping step (here, `finalize()`/banking of `own_contribution`) has run, letting the reentrant path observe and persist a snapshot that the outer call later reapplies, corrupting the shared accounting state.

### Finding Description
When contract `X` writes storage key `K1`, then calls itself (directly or via an intermediary `Y`), and writes `K2` on the way back, three things happen:
- `push_frame` and the same-contract `cached_info` shortcut clone the parent's `ContractInfo` and preview-apply the parent's pending diff (`K1`) to the clone so the child frame's refund pro-rating sees accurate byte/item counts.
- The child persists that preview-applied clone via `insert_contract` on success.
- The cache-invalidation matcher then marks the parent's cache `Invalidated`, so the parent's subsequent write (`K2`) reloads from storage — which now already contains the previewed `K1` update.
- The parent's `finalize()` later re-applies its still-pending `own_contribution` (still holding `K1`) on top of the reloaded info, counting `K1` twice. [1](#0-0) 

The corrupted state is `ContractInfo.storage_items` / `storage_bytes` / `storage_item_deposit` / `storage_byte_deposit`, persisted via `insert_contract`, which subsequently becomes the denominator for pro-rata refunds computed in `Diff::update_contract`. [2](#0-1) 

The reentry-visibility mechanism itself is captured in the `Cached(contract)` preview-apply branch used for nested `Call` frames: [3](#0-2) 

### Impact Explanation
The corrupted `ContractInfo` accounting fields inflate the denominator used in pro-rata refund calculation (`FixedU128::checked_from_rational(bytes_removed, info.storage_bytes)` etc.), causing subsequent `clear_storage` operations to systematically under-refund the depositor. This is an accounting-integrity failure directly analogous to the Bunni report's "cross-contract reentrancy corrupts Hooklet state": an unprivileged contract author can trigger the double-count purely by self-reentry, with no privileged actor, relayer, or malicious peer needed — matching the required "public entrypoint, unprivileged attacker, wrong accounting" impact class.

### Likelihood Explanation
Reachable by any account that deploys and calls a self-reentrant contract on `pallet-revive` (configured in Asset Hub Westend, pallet index 60). Reentrancy is either the EVM default (`AllowReentry` for non-zero-value or non-stipend calls) or explicitly opt-in for PVM via `CallFlags::ALLOW_REENTRY` — both are normal, permissionless contract-authoring choices, not privileged or adversarial-infrastructure conditions. [4](#0-3) 

### Recommendation
Bank the parent's pending diff into the `ContractInfo` at the moment it is exposed to a reentrant child, and reset `own_contribution` so `finalize()` cannot reapply the same diff a second time — exactly what the shipped fix does via `RawMeter::bank_pending_changes` and `Frame::bank_pending_changes_and_invalidate`, gated by asserting `own_contribution` is `Alive`/non-finalized at the bank point. [5](#0-4) 

### Proof of Concept
The regression fixtures directly reproduce the double-count: `X` writes `K1`, calls itself (or transitively via `Y`), writes `K2`; asserted `ContractInfo` fields (`storage_items == 2`, `storage_bytes == 70`) come back inflated (`storage_items == 3`, `storage_bytes == 105`) without the fix. [6](#0-5) [7](#0-6) 

---
Note: This finding is drawn from a fix already merged in this repository snapshot (`PR #12267`, `same_contract_reentry_does_not_double_count_storage` / `transitive_reentry_does_not_double_count_storage` tests, banked via `RawMeter::bank_pending_changes`), so the code currently in `substrate/frame/revive/src/exec.rs` / `metering/storage.rs` is patched against this exact analog. It is presented because it is the closest verifiable local instance of the requested bug class (state mutation observable by a reentrant caller before the "after" bookkeeping step completes, corrupting shared accounting state) that exists with concrete file/function support in this codebase; no other unfixed occurrence of this specific pattern was found with equivalent evidence.

	pub fn update_contract<T: Config>(&self, info: Option<&mut ContractInfo<T>>) -> DepositOf<T> {
		let per_byte = T::DepositPerByte::get();
		let per_item = T::DepositPerChildTrieItem::get();
		let bytes_added = self.bytes_added.saturating_sub(self.bytes_removed);
		let items_added = self.items_added.saturating_sub(self.items_removed);
		let mut bytes_deposit = Deposit::Charge(per_byte.saturating_mul((bytes_added).into()));
		let mut items_deposit = Deposit::Charge(per_item.saturating_mul((items_added).into()));

		// Without any contract info we can only calculate diffs which add storage
		let info = if let Some(info) = info {
			info
		} else {
			return bytes_deposit.saturating_add(&items_deposit);
		};

		// Refunds are calculated pro rata based on the accumulated storage within the contract
		let bytes_removed = self.bytes_removed.saturating_sub(self.bytes_added);
		let items_removed = self.items_removed.saturating_sub(self.items_added);
		let ratio = FixedU128::checked_from_rational(bytes_removed, info.storage_bytes)
			.unwrap_or_default()
			.min(FixedU128::from_u32(1));
		bytes_deposit = bytes_deposit
			.saturating_add(&Deposit::Refund(ratio.saturating_mul_int(info.storage_byte_deposit)));
		let ratio = FixedU128::checked_from_rational(items_removed, info.storage_items)
			.unwrap_or_default()
			.min(FixedU128::from_u32(1));
		items_deposit = items_deposit
			.saturating_add(&Deposit::Refund(ratio.saturating_mul_int(info.storage_item_deposit)));

	/// Apply the pending diff to `info` and push its deposit as a final charge, then reset
	/// `own_contribution` so finalize does not apply it a second time.
	pub fn bank_pending_changes(&mut self, contract: T::AccountId, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(_) = &self.own_contribution {
			let deposit = self.own_contribution.update_contract(Some(info));
			self.own_contribution = Contribution::Alive(Default::default());
			if !deposit.is_zero() {
				self.charge_deposit(contract, deposit);
			}
		} else {
			debug_assert!(
				false,
				"on-stack ancestor frames have not finalized yet, so own_contribution \
				 should be Alive when banked; qed",
			);
		}
	}
