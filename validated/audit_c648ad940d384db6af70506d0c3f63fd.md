## Analysis Result

### Title
Divide-before-multiply precision loss in global energy/bandwidth resource-limit calculation - (File: `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`, `chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java`)

### Summary
The reported JUSD issue is a classic "divide-then-multiply" precision-loss bug: intermediate division truncates a fraction before the value is multiplied again, systematically under- or over-computing the final amount. The same arithmetic pattern (divide first, multiply second, using floating point) exists in java-tron's legacy (non-hardened) resource-limit computation used for TVM energy metering and bandwidth accounting, both of which are exercised on every transaction/contract call and every `GetAccountResource`/`GetAccountNet` API query.

### Finding Description
`EnergyProcessor.calculateGlobalEnergyLimit` and `calculateGlobalEnergyLimitV2` compute an account's proportional share of the network's total energy limit as:

```java
long energyWeight = frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
``` [1](#0-0) 

and the V2 variant:
```java
double energyWeight = (double) frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
``` [2](#0-1) 

`BandwidthProcessor.calculateGlobalNetLimit` / `calculateGlobalNetLimitV2` follow the identical pattern for bandwidth:
```java
long netWeight = frozeBalance / TRX_PRECISION;
return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
``` [3](#0-2) [4](#0-3) 

In each case `totalEnergyLimit/totalEnergyWeight` (or `totalNetLimit/totalNetWeight`) is computed and rounded as a `double` *before* the multiplication by the account's weight — exactly the same "each operation loses precision, then feeds into the next" structure as the reported `_getMintAmount` bug (`price.decimalMul(balance).decimalMul(rate)` truncating at every step instead of dividing once at the end). The related actuator `UnDelegateResourceActuator` shows the same chained-division structure for computing `unDelegateMaxUsage`/`transferUsage` when un-delegating stake:
```java
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * ((double) (dynamicStore.getTotalNetLimit()) / dynamicStore.getTotalNetWeight()));
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
``` [5](#0-4) 

Notably, the java-tron team has already recognized this exact bug class and introduced a `hardenCalculation()`/`allowHardenResourceCalculation()` feature-gated BigInteger replacement (e.g. `calculateGlobalLimitV1`/`V2` using `BigInteger.multiply().divide()` instead of double division) [6](#0-5) , and their own tests demonstrate the discrepancy between the "buggy" legacy double path and the corrected BigInteger path, e.g. `testCalculateGlobalEnergyLimitHardenedParityWithNonIntegerRatio` explicitly asserts `Assert.assertNotEquals(buggy, resultNew)` [7](#0-6) . This confirms the bug is real and quantifiable; however, the vulnerable legacy path remains the default/live code path whenever `allowHardenResourceCalculation` has not been activated via chain governance proposal.

### Impact Explanation
`calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` gate how much TVM energy and network bandwidth every account is entitled to per resource window, and are queried on every contract call, every `useAccountNet`/energy consumption check (`BandwidthProcessor.useAccountNet`, `EnergyProcessor`), and every `GetAccountResource` API response [8](#0-7) [9](#0-8) . Systematic floating-point precision loss here means resource limits are computed inconsistently with the "correct" integer proportional share, which can under- or over-grant free energy/bandwidth to accounts at scale (affecting metering and possibly enabling minor discrepancies that let some accounts consume/report resources beyond their backed frozen stake, i.e., unbacked resource allocation). It is a systemic, chain-wide precision defect rather than an isolated rounding of a single small value, since it affects every account's resource ceiling on every block.

### Likelihood Explanation
No special privilege is required — any account holder freezing TRX for bandwidth/energy (a standard, permissionless `FreezeBalanceV2Contract`/`UnDelegateResourceContract`) or any TVM contract execution triggers these computations, and any unprivileged API client can observe the resulting numbers via `GetAccountResource`. The bug is deterministic and always present on the legacy (`allowHardenResourceCalculation() == false`) code path, which is the historical default before that proposal was activated on a given network.

### Recommendation
Replace the double-based `(long) (weight * ((double) totalLimit / totalWeight))` computation with a single combined integer expression evaluated with `BigInteger` (multiply everything first, divide once at the end), as already implemented behind the `allowHardenResourceCalculation` flag (`calculateGlobalLimitV1`/`calculateGlobalLimitV2` in `ResourceProcessor.java`), and make that the unconditional default rather than an opt-in proposal, to eliminate the divide-before-multiply precision loss for all networks regardless of proposal activation state. Apply the same fix to `UnDelegateResourceActuator`'s chained double-division `unDelegateMaxUsage`/`transferUsage` calculations.

### Proof of Concept
1. Set `totalEnergyWeight = 1_234_567L`, `totalEnergyLimit = 50_000_000_000L`, and freeze `10_000_000_000L` (i.e. `energyWeight = 10000`) for an account, with `allowHardenResourceCalculation` disabled (legacy default).
2. Call `EnergyProcessor.calculateGlobalEnergyLimit(account)`. It evaluates `(long) (10000 * ((double) 50_000_000_000L / 1_234_567L))`, which truncates the fractional ratio of `totalEnergyLimit/totalEnergyWeight` before multiplying by `energyWeight`.
3. Compare against the exact `BigInteger.valueOf(10000).multiply(BigInteger.valueOf(50_000_000_000L)).divide(BigInteger.valueOf(1_234_567L))` result, which the project's own hardened test asserts differs from the naive `10000 * (totalEnergyLimit / totalEnergyWeight)` truncated form [7](#0-6) , confirming the legacy formula's precision loss is reproducible and measurable on every account resource calculation.

```java
  protected long calculateGlobalLimitV1(long frozeBalance,
      long totalLimit, long totalWeight) {
    long weight = frozeBalance / TRX_PRECISION;
    return BigInteger.valueOf(weight)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(totalWeight))
        .longValueExact();
  }

  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
```
