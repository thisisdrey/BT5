### Title
Account Permission Update allows irrevocable transfer of account control with no key-ownership proof, enabling permanent freezing of funds - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` lets an account owner replace the `Owner`/`Witness`/`Active` permission structures that gate all future control of the account. The only checks performed (`checkPermission()`) validate arithmetic properties of the new permission (key count, distinctness, weight sums vs. threshold) but never verify that the transaction's signer retains any provable, recoverable control over the new key set being installed. Analogous to the Fantom `tokensTradeable` bug — where control of a critical state transition is handed to a single address with no fallback — once an `AccountPermissionUpdateContract` is committed to a set of keys the signer does not actually hold (mistaken address, lost hardware wallet, or attacker-supplied address in a phishing flow), there is no protocol-level mechanism to ever recover authority over that account.

### Finding Description
`checkPermission()` only enforces:
- `permission.getKeysCount() <= totalSignNum` and `> 0`
- `threshold > 0` and `weightSum >= threshold`
- valid, distinct addresses with positive weight [1](#0-0) 

Nothing in `validate()` or `execute()` requires that the resulting `Owner` permission remain reachable by the original controller, nor does it provide any time-locked escape hatch analogous to `require(msg.sender == owner || atNow() > dateMainEnd + 3 weeks)` from the report. `execute()` unconditionally overwrites the account's permissions via `account.updatePermissions(...)` as soon as `validate()` passes. [2](#0-1) 

This mirrors the Fantom single-point-of-failure pattern: a single signed transaction (broadcastable by anyone who controls the account, or by tricking the account owner into signing a maliciously-crafted contract) permanently reassigns the sole authority needed to move TRX, TRC10 balances, vote, withdraw rewards, or unfreeze/undelegate resources for that account — with no recovery path if the new key set becomes inaccessible.

### Impact Explanation
If the new `Owner`/`Active` permission set becomes unreachable (lost private key, typo'd address, or attacker-controlled address in a permission-phishing scenario), all TRX, TRC10 tokens, staked/frozen balances, and voting rights on that account become permanently frozen — no `unfreeze`, `transfer`, `vote`, or subsequent `AccountPermissionUpdate` can ever be authorized again, since the actuator requires the very permission it just replaced to authorize the next transaction. This is a concrete, permanent freezing-of-funds condition with no on-chain remediation.

### Likelihood Explanation
Reachable via a single ordinary signed transaction from the account owner (`AccountPermissionUpdateContract`), gated only by `allowMultiSign` being enabled by committee proposal — a normal, long-enabled feature. The scenario requires either user error (address typo, using an address for which the private key was never generated/retained) or a phishing/social-engineering flow inducing the victim to authorize a permission update pointing to attacker-controlled keys — both plausible and previously observed patterns in multi-sig wallet ecosystems, making likelihood Medium.

### Recommendation
Add safeguards absent from the current design, mirroring the report's remediation approach of avoiding a single irrevocable control point:
- Warn/require additional confirmation flows at the wallet layer are not sufficient; consider a protocol-level grace period or two-step commit (propose + confirm from the new key set) before an `Owner` permission replacement takes final effect.
- Optionally require that at least one key in the new `Owner` permission match the current active/owner permission's keys, preventing full transfer of control in a single step without any continuity, or provide an on-chain rollback window (analogous to `dateMainEnd + 3 weeks` in the report) during which the previous owner keys can revert the change.

### Proof of Concept
1. Attacker/phishing site convinces (or account owner accidentally) crafts an `AccountPermissionUpdateContract` where the `Owner` permission's keys list contains only address(es) not controlled by the legitimate account holder (or the sole legitimate key is omitted/mistyped) with `threshold` satisfied by `weightSum`.
2. Transaction passes `checkPermission()` since it only checks arithmetic weight/threshold and address format, not key custody. [3](#0-2) 
3. `execute()` commits `account.updatePermissions(...)`, overwriting prior `Owner`/`Active` permissions. [4](#0-3) 
4. All subsequent transactions from the account (transfers, unfreeze, vote, withdraw rewards, or another permission update) require signatures satisfying the new `Owner`/`Active` threshold, which the legitimate holder can no longer produce — permanently freezing all TRX/TRC10/staked balances in that account.
