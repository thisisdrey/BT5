## No vulnerability found for this question.

The scenario described (many `DeployContractAction`/`FunctionCallAction` receipts each individually passing `limit_config` checks but collectively exhausting memory via cumulative `prepare_contract` allocations within a single chunk) is directly mitigated in this codebase by dedicated per-action **compute costs** that are independent of (and much higher than) the gas cost, specifically designed to cap the number/size of contract deployments processed within a single chunk.

- `action_deploy_contract`'s execution compute cost was raised ~100x specifically "to set the limit to at most 50 deployments per chunk," and `action_deploy_contract_per_byte`'s compute cost was raised ~4x so "a 4MiB contract fills a chunk." [1](#0-0) 
- Receipt processing in `process_local_receipts`, `process_delayed_receipts`, and `process_incoming_receipts` checks `processing_state.total.compute >= compute_limit` before executing each receipt; once the chunk's compute budget (which equals the gas limit) is exhausted, remaining receipts are pushed to the delayed-receipts queue instead of being executed in the same chunk. [2](#0-1) [3](#0-2) 
- This exact scenario — many `DeployContractAction` receipts landing in the same chunk — is covered by an existing integration test, `test_deploy_compute_cost_limit`/`test_deploy_compute_cost_per_byte_limit`, which submits `max_per_chunk + 1` deploy transactions from distinct accounts within a single chunk and asserts that only the compute-budget-bounded subset executes while the rest are deferred to the delayed queue. [4](#0-3) [5](#0-4) 

Because the compute budget bounds the number of `DeployContractAction`/`FunctionCall`-with-deploy receipts that can be executed (and thus have `prepare_contract` invoked) within a single chunk apply, an attacker cannot arbitrarily scale up the cumulative `prepare_contract` allocation (`output_code: Vec::with_capacity(code.len())` plus the `finite_wasm` analysis buffers, per `runtime/near-vm-runner/src/prepare/prepare_v2.rs:383-412`) by submitting many small deploys in one chunk — excess receipts are deferred to later chunks by design, capping peak per-chunk memory to a bounded worst case (~50 × max contract/instrumented size), not an attacker-controlled unbounded amount. This is a deliberate, tested protocol-level mitigation, not a gap.
