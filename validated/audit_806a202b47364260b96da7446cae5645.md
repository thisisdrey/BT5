This confirms the mechanism directly answers the question. `RequestMessage::hash()` explicitly uses `borsh::to_writer` over a `Sha3_256` hasher prefixed with `DOMAIN_SEPARATOR`, not the JSON string, regardless of which JSON encoding variant (`pay_for_gas` omitted vs. explicit `false`) was used to deserialize the message.Both signature schemas examined (`WalletEd25519` and `WalletWebauthn`) call `msg.hash()` — never JSON — to produce the challenge/message that gets signed and verified, and the contract's `execute_signed` also derives its authorization hash from `msg.hash()` after Borsh-deserializing the RPC-supplied `RequestMessage`. Since `RequestMessage::hash()` is defined purely in terms of `borsh::to_writer(&mut hasher, self)` over the domain separator plus the in-memory struct fields [1](#0-0) , the JSON text used to transmit the message (whether it explicitly includes `"pay_for_gas":false` or omits it via `skip_serializing_if`) is irrelevant to the hash: both JSON encodings deserialize into an identical `RequestMessage { pay_for_gas: false, .. }` value [2](#0-1) , and Borsh serializes the boolean field itself, not any serde attribute or JSON presence/absence.

#### No vulnerability found for this question.

The claimed binding — "the signed bytes = JSON text" — is false for this codebase; `verify_request_msg` in both `WalletEd25519::verify_request_msg` [3](#0-2)  and `WalletWebauthn::verify_request_msg` [4](#0-3)  and the contract's `execute_signed` [5](#0-4)  all consistently use the canonical Borsh-derived `msg.hash()`, so no code path in this repo hashes the raw JSON string for signing/verification purposes. The `serde(default, skip_serializing_if=Not::not)` attribute only affects transport-layer JSON encoding/decoding, not the canonical hash, and there is no "signer that hashes the JSON string" present in the in-scope crates (the out-of-scope `crates/wallet/sdk/**` client crate was excluded per the rules, and no such JSON-hashing signer was found within scope). The existing repository test `json_hash` already demonstrates that a JSON-encoded `RequestMessage` deserializes and produces the expected canonical Borsh-based hash [6](#0-5) , consistent with there being no malleability at the hash layer as required by the question's own proof idea.
