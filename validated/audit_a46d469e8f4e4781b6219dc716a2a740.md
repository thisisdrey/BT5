### Title
Reliability-score formula rewards request volume over success rate, letting a lying peer monopolize `AttachmentRequest` source-selection and starve honest peers of retries - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`get_prioritized_attachments_requests` accepts any peer's `GetAttachmentsInvResponse.pages[i].inventory` bit=1 at face value and adds that peer as a candidate `source` for the content hash, with no cross-check against actual possession. [1](#0-0)  Because `ReliabilityReport::score()` is dominated by `total_requests_sent` (`n`) rather than success rate, a peer that repeatedly lies about having an attachment and then fails the follow-up `GET /v2/attachments/:hash` accrues an ever-increasing score purely from being asked (and failing) more often, letting it out-rank a genuinely reliable peer that has simply been asked fewer times. [2](#0-1) 

### Finding Description
The claimed equality is: "attachment marked resolved == attachment content actually retrieved and hash-verified." Tracing the code shows this equality *does* hold for the final resolution step — `resolve_attachment` is keyed off `attachment.hash()` computed from the actually-returned bytes, not off the requested `content_hash`, so a peer cannot forge a hash match by returning arbitrary content for an unrelated request. [3](#0-2)  `decode_atlas_get_attachment` also performs no hash-comparison against the request, but this only means a lying peer's data is silently discarded/misfiled, not that a forged hash is accepted as resolving the wrong instance. [4](#0-3) 

However, `get_prioritized_attachments_requests` trusts inventory bit=1 unconditionally to add a peer to `sources` for a content hash: [1](#0-0)  and `Requestable::get_url` for `AttachmentRequest` always picks the single "most reliable source" by `ReliabilityReport` score to issue the actual GET. [5](#0-4)  The `ReliabilityReport::score` formula is effectively `(1 if success>=n else 0) + n` due to integer-division truncation of `success*1000/(n*1000)`, meaning score grows monotonically with the *count* of requests sent regardless of failure rate. [2](#0-1)  Each time a malicious peer is asked and fails, `bump_failed_requests` increments `total_requests_sent` (raising its score further), while `extend_with_inventories`/`extend_with_attachments` never remove or penalize a peer that lied about inventory beyond this same failed-request bump. [6](#0-5)  On every retry, inventory requests go out to *all* outbound peers again, so a persistently lying peer keeps being re-included in `sources` with its self-reinflating score, systematically starving the actually-honest peer of being selected as the download target across the batch's finite `max_attachment_retry_count` retries. [7](#0-6)  Once retries are exhausted, the batch and its unresolved `AttachmentInstance` (e.g., a BNS zonefile hash) is dropped and never retried again except through natural expiry logic. [8](#0-7) 

### Impact Explanation
A remote, unprivileged peer that is included in a node's `get_outbound_sync_peers()` set can, purely by being queried repeatedly and always returning a lying inventory bit plus a failing/garbage `GET /v2/attachments/:hash` response, drive up its own `ReliabilityReport` score and get preferentially selected as the download source for a target content hash on every retry round, denying the node the chance to fetch that content from a genuinely possessing peer. This matches "attachment/BNS mismatch"-class High severity: a confirmed on-chain attachment instance (e.g., a BNS name's zonefile) is never retrieved even though it is available from an honest peer, and after `max_attachment_retry_count` retries the batch is permanently dropped, so the node persistently reports the zonefile/attachment as absent.

### Likelihood Explanation
Preconditions: the attacker must be one of the node's `get_outbound_sync_peers()` with a resolvable `data_url` — an ordinary, unprivileged peer connection, no secret or admin role needed. The attack is cheap (a handful of HTTP responses per retry cycle) and repeatable across every AttachmentsBatch retry as long as the attacker remains selected as an outbound peer. However, exploitability depends on the peer set composition and initial reliability history of the honest peer(s): if the honest peer already has an equal-or-higher score before the attack starts (e.g., due to prior successful requests), a single malicious peer may not immediately out-rank it — the score-inflation advantage accrues over multiple lie/fail rounds. This makes the attack probabilistic/timing-dependent rather than deterministic in one shot, which somewhat tempers the practical likelihood.

### Recommendation
Fix `ReliabilityReport::score()` so that score reflects success rate (e.g., `total_requests_success as f64 / total_requests_sent.max(1) as f64`, weighted, not integer-truncated to near-zero) rather than being dominated by raw request volume. Additionally, when an `AttachmentRequest` fails against a peer that claimed the content in its inventory, that peer's inventory claim for that specific content_hash should be discarded for the remainder of the batch/retry cycle (not just its aggregate reliability score bumped), so the same liar cannot be re-selected purely via score inflation on subsequent retries within the same batch.

### Proof of Concept
Rust unit test in `stackslib/src/net/atlas/tests.rs` extending `test_downloader_context_attachment_requests`:
1. Construct `peers` with peer A (attacker) `ReliabilityReport::new(0,0)` and peer B (honest) `ReliabilityReport::new(1,1)`.
2. First round: both A and B report inventory bit=1 for the target content hash via `new_attachments_inventory_response`; feed into `extend_with_inventories`.
3. Call `get_prioritized_attachments_requests()`, assert peer B (higher initial score) is selected via `get_most_reliable_source`.
4. Simulate failure: for peer B, call `report.bump_failed_requests()` a few times (mimicking natural churn) while peer A's failures also accumulate via repeated inventory/attachment failure cycles (`bump_failed_requests` on A after each lying "sources" round) — assert via direct computation that `ReliabilityReport::score()` for A eventually exceeds B's score despite A having `total_requests_success == 0`.
5. Assert that after A's score surpasses B's, `get_most_reliable_source` for the `AttachmentRequest` returns A's URL, and that `AttachmentsBatch::has_fully_succeed()` remains `false` after `bump_retry_count()` is called `connection_options.max_attachment_retry_count` times, at which point the batch is dropped in `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:199-204`), demonstrating the target attachment instance is never resolved despite peer B always having genuinely possessed and offered to serve it.

    pub fn extend_with_inventories(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentsInventoryRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_attachments_inv_response() {
                let peer_url = request.get_url().clone();
                match self.inventories.entry(request.key()) {
                    Entry::Occupied(responses) => {
                        responses.into_mut().insert(peer_url, response);
                    }
                    Entry::Vacant(v) => {
                        let mut responses = HashMap::new();
                        responses.insert(peer_url, response);
                        v.insert(responses);
                    }
                };
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    }

impl Ord for AttachmentRequest {
