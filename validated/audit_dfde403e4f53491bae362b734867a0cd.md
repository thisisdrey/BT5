### Title
Out-of-bounds read on unvalidated Local Header offset in singlejar's `InputJar::LocalHeader` - (File: `src/tools/singlejar/input_jar.h`)

### Summary
`InputJar::NextEntry` validates that each Central Directory Header (CDH) itself is within the mapped file [1](#0-0) , but it derives the corresponding Local Header (LH) pointer purely from the attacker-controlled `local_header_offset()` field taken from that CDH, with **no bounds check** before dereferencing it:

```
const LH* LocalHeader(const CDH* cdh) const {
  return reinterpret_cast<const LH*>(
      mapped_file_.address(cdh->local_header_offset() + preamble_size_));
}
``` [2](#0-1) 

`MappedFile::address()` is a raw pointer-arithmetic helper with no clamping: `mapped_start_ + offset` [3](#0-2) . Unlike `LocateCentralDirectory`, which explicitly checks `mapped_file_.mapped(mapped_file_.address(cen_position))` before trusting the ECD's central-directory offset [4](#0-3) , `NextEntry`/`LocalHeader` performs no equivalent `mapped()` check for the local-header offset.

### Finding Description
`singlejar` (Bazel's Java archive merger, used by `java_binary`/`java_import`/deploy-jar actions) opens an input jar by memory-mapping it and walking the Central Directory via `NextEntry` [5](#0-4) . For every CDH it also computes a `LH*` pointer for the corresponding Local Header by adding the 32-bit `local_header_offset32_`/64-bit Zip64 offset field from the CDH to `preamble_size_`, and handing that raw address straight to callers (e.g., `OutputJar::AddJar`) which immediately dereference `lh->size()`, `lh->file_name_length()`, `lh->extra_fields()`, etc. [6](#0-5) .

Because a jar file consumed by this tool is exactly the kind of "content a victim's build consumes" — e.g. a source/binary jar fetched via `http_jar`/`http_file`/a Maven registry dependency, or produced on an attacker-influenced CI branch — an attacker who controls the bytes of that jar (matching a declared sha256, since the checksum only certifies the outer file bytes, not that every embedded structural field is well-formed) can set an entry's `local_header_offset` in the Central Directory to an arbitrary out-of-range 32/64-bit value. When Bazel's singlejar action processes this jar, `LocalHeader()` computes a pointer that lands outside the mapped region of the file, and the subsequent unchecked reads of `file_name_length_`, `extra_fields_length_`, `compressed_file_size32_`, etc. read adjacent heap/mapped memory beyond the file's mapping — an out-of-bounds read directly analogous to the CVE-2019-2101 pattern (`uvc_parse_standard_control`'s failure to validate an input-derived field before it is used to index/dereference memory).

### Impact Explanation
This is a local information-disclosure class bug: the OOB-read bytes (heap/adjacent-mapping content) can influence subsequent parsing decisions (e.g., `file_name_length()`, `extra_fields_length()`, `compressed_file_size()`) and can be echoed into the merged output jar (file names, extra field bytes, or size fields copied via `memcpy` in `OutputJar::WriteEntry`/timestamp-fixing code) [7](#0-6) , leaking process memory into build outputs, or crashing the build worker (denial of service is out of scope per the rules, but the read itself is the qualifying primitive). It does not require any privilege beyond supplying a malformed archive that a build depends on.

### Likelihood Explanation
Moderate. singlejar is invoked on every `java_binary`/`java_import`-style build with more than one jar (very common), and the attacker's foothold is simply "a jar's bytes are attacker-authored" — satisfied by any externally-sourced jar dependency whose internal ZIP structure isn't otherwise verified beyond the outer sha256. No MITM or privileged access is needed; the checksum on the whole file does not protect the internal Central-Directory `local_header_offset` field's semantic validity relative to the mapping, only that the total byte content matches the pin.

### Recommendation
Add an explicit `mapped_file_.mapped()` bounds check (mirroring the one already done for `cen_position` in `LocateCentralDirectory`) before returning the computed `LH*` in `InputJar::LocalHeader`, and validate `lh->size()` / `file_name_length()+extra_fields_length()` stay within `mapped_file_.end()` before any field of `LH` is read, failing the build with a diagnostic (as is already done for corrupt CDH records) instead of silently dereferencing an out-of-range pointer.

### Proof of Concept
A reproducible `BuildIntegrationTestCase`/`src/test/shell/bazel` style PoC:
1. Programmatically construct a minimal valid ZIP: one CDH entry whose `local_header_offset32_` is set to a value that, after adding `preamble_size_`, points past `mapped_file_.end()` (e.g., `mapped_file_.size() + large_offset`), while keeping the ECD/central-directory-size fields internally consistent so `LocateCentralDirectory` succeeds.
2. Feed this crafted jar as an input to `singlejar` (e.g. via a `java_import`/`deploy_jar`-style rule referencing this jar as a dependency, downloaded through `http_jar` with a matching sha256 for the crafted bytes).
3. Run the `singlejar` binary (or invoke `InputJar::Open` + `NextEntry` directly in a `gtest`/JUnit-style native test under `src/tools/singlejar/input_jar_random_jars_test.cc`-style harness) and observe that `LocalHeader()` returns a pointer outside `[mapped_start_, mapped_end_)`, and that reading `lh->file_name_length()`/`lh->extra_fields_length()` accesses memory beyond the mapped file (detectable under ASan as heap-buffer-overflow / out-of-bounds read, or via a guard page placed immediately after the mapping).

Note: I was not able to execute this PoC or fully trace every downstream consumer of the resulting `LH*` (e.g., all call sites in `OutputJar::AddJar`) within the available exploration; the control-flow above is based on the code shown in `input_jar.h`, `input_jar.cc`, `mapped_file.h`, and `zip_headers.h`, and a full confirmation would require running the described test under an existing Bazel checkout.
