### Title
Unconditional `panic!()` on Deprecated Oracle Types Permanently Freezes Legacy Banks - ([File: programs/marginfi/src/state/price.rs])

### Summary
`OraclePriceFeedAdapter::load_oracle_context_with_max_age` and `OraclePriceFeedAdapter::validate_bank_config` in `programs/marginfi/src/state/price.rs` use `panic!()` instead of returning a `MarginfiError` when a bank's `oracle_setup` is `OracleSetup::PythLegacy` or `OracleSetup::SwitchboardV2`. These enum variants (values `1` and `2`) still exist and are explicitly documented as "Deprecated" rather than removed. Any unprivileged instruction that needs to fetch a bank's oracle price (deposit, withdraw, borrow, liquidate, health checks) for a bank still carrying one of these legacy oracle configurations will cause the whole transaction, and effectively the bank, to panic and abort instead of failing gracefully.

### Finding Description
`load_oracle_context_with_max_age` is the central price-loading routine invoked by essentially every price-consuming code path (`try_from_bank`, `get_price_and_confidence_and_cache_of_type`, `get_price_and_confidence_for_cache`, etc.): [1](#0-0) 

The `match` on `bank_config.oracle_setup` handles every current variant with a proper `Result`, but explicitly `panic!()`s for the two deprecated variants instead of returning `Err(MarginfiError::...)`:
```rust
OracleSetup::PythLegacy => {
    panic!("pyth legacy is deprecated");
}
OracleSetup::SwitchboardV2 => {
    panic!("swb v2 is deprecated");
}
```

The same unconditional panic pattern is duplicated in `validate_bank_config`, which is exercised during oracle (re)configuration: [2](#0-1) 

`OracleSetup::from_u8` still maps raw byte `1` and `2` to these live variants (only commented as deprecated, not removed), so any `Bank` account whose `config.oracle_setup` field is `1` or `2` — e.g., a bank created/configured under an older program version before these types were fully retired — retains that state on-chain: [3](#0-2) 

`lending_pool_configure_bank_oracle` only rejects `Fixed`-family setups explicitly; it does not reject `PythLegacy`/`SwitchboardV2` before writing them into `bank.config.oracle_setup`, and only surfaces the panic afterward via `validate_oracle_setup`: [4](#0-3) 

Because the panic occurs inside `load_oracle_context_with_max_age`, which underlies every price fetch used by deposit, withdraw, borrow, and liquidation health-check logic, once a bank ends up in this state, **every unprivileged user interaction that requires pricing that bank will panic and revert**, not with a controlled error, but with a hard Rust panic. Depending on runtime handling, this can manifest as a permanently unusable bank (deposits, withdrawals, borrows, and liquidations against it are impossible) since there is no code path to recover a bank's `oracle_setup` other than calling the same instruction that itself panics before it can commit a new, valid oracle config.

### Impact Explanation
Any bank whose `oracle_setup` is `PythLegacy` or `SwitchboardV2` becomes permanently frozen for all unprivileged operations that require price data (deposits, withdrawals, borrows, liquidations, health checks). This is a permanent-lock/freeze condition triggered purely by normal, unprivileged usage of the bank — the same class of impact ("attestations frozen") described in the referenced Gravity Bridge report.

### Likelihood Explanation
Low-to-moderate. Reachability depends on whether any bank account is (or can become) configured with `oracle_setup = PythLegacy (1)` or `SwitchboardV2 (2)`. Since these enum values are still defined and `OracleSetup::from_u8` still decodes them, and `lending_pool_configure_bank_oracle` does not explicitly block them before invoking `validate_bank_config` (which panics), the only thing currently preventing exploitation is that nothing in the present code intentionally sets these values — analogous to the original report's own caveat ("zero probability... but still a good report to address"). I could not verify from the available code whether any legacy on-chain `Bank` account currently holds one of these deprecated values; if one exists, the freeze is immediately triggered by ordinary user interaction with that bank.

### Recommendation
- Replace both `panic!()` calls in `programs/marginfi/src/state/price.rs` (`load_oracle_context_with_max_age` and `validate_bank_config`) with a proper `Err(MarginfiError::OracleNotSetup)` or a new dedicated `MarginfiError::DeprecatedOracleType` return value.
- In `lending_pool_configure_bank_oracle`, explicitly reject `OracleSetup::PythLegacy` and `OracleSetup::SwitchboardV2` up front (similar to the existing `Fixed`-family check) so they can never be set going forward.
- Audit existing on-chain `Bank` accounts for `oracle_setup` values of `1` or `2`, and provide an admin migration path to move any such banks to a supported oracle type without requiring the panicking code path to execute.

### Proof of Concept
1. Assume (or construct via a test harness) a `Bank` account with `config.oracle_setup = OracleSetup::PythLegacy` (raw byte `1`).
2. Call any permissionless instruction that requires a price for that bank, e.g. `lending_account_deposit`, `lending_account_withdraw`, or `lending_account_liquidate`, which internally calls `OraclePriceFeedAdapter::try_from_bank` → `load_oracle_context_with_max_age`.
3. Execution reaches:
```rust
OracleSetup::PythLegacy => { panic!("pyth legacy is deprecated"); }
``` [5](#0-4) 
4. The transaction aborts via panic instead of a graceful `Err`, and every future interaction with this bank that requires pricing will panic identically, permanently freezing the bank.
