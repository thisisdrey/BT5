### Title
Unbounded `Math.pow` result silently truncated to `Long.MAX_VALUE` in `ExchangeProcessor`, allowing unbacked token/TRX minting via `ExchangeTransactionContract` - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
### Finding Description
The Fuel report describes `pow` functions that lack overflow protection for fixed-width integers, causing silent wraparound/loss of coins when the result is used to calculate a coin amount. java-tron has a structurally identical class of bug in its Bancor-style exchange math used by `ExchangeTransactionContract`.

`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute `Math.pow` (via `Maths.pow`) on `double` values derived directly from user-controlled `sellTokenQuant`/`tokenExpected` and the current pool balances, and then narrow the `double` result back to a `long` with a raw cast: [1](#0-0) 

Per Java Language Specification narrowing conversion rules, casting `Double.POSITIVE_INFINITY` (or any value greater than `Long.MAX_VALUE`) to `long` does **not** throw — it silently clamps to `Long.MAX_VALUE`. `Math.pow(base, 2000.0)` in `exchangeFromSupply` grows hyper-exponentially with the sell ratio; even a moderate `supplyQuant/supply` ratio drives the exponentiation to `Infinity`, so `(long) exchangeBalance` becomes `Long.MAX_VALUE` instead of failing.

This path is selected whenever the chain has not yet enabled the "hardened" resource-calculation proposal, since `ExchangeCapsule.transaction()` chooses between the unsafe `ExchangeProcessor` and the safe `SafeExchangeProcessor` (which uses `BigDecimal`/`StrictMathWrapper.addExact` and throws on overflow) purely based on the `hardenedCalc` flag supplied by the actuator: [2](#0-1) 

`ExchangeTransactionActuator.execute` reaches this code directly from a normal, unprivileged signed transaction (`ExchangeTransactionContract`), passing the transaction's `tokenQuant` straight into `exchangeCapsule.transaction(...)`: [3](#0-2) 

The only user-side bound enforced in `doValidate()` is that the post-trade token balance stay under `getExchangeBalanceLimit()` — a large configured cap that does not prevent the *ratio* `quant/balance` from being large enough to blow up `pow(...,2000)`: [4](#0-3) 

This is the same fundamental defect class as the Fuel report: an exponentiation whose result can exceed the representable range of the destination integer type is converted with no overflow check, producing a silently-wrong (here: maximal) value that is then used directly as a coin/asset amount.

### Impact Explanation
If `buyTokenQuant` becomes `Long.MAX_VALUE` (or any value far larger than the actual counter-asset reserve), `ExchangeTransactionActuator.execute` credits the caller's account with that amount via `addAssetAmountV2`/balance increase while only debiting the pool by the legitimate `newSecondTokenBalance -= buyTokenQuant` (which can go negative in the non-hardened path, since the `< 0` check is only performed `if (hardenedCalc)`), i.e. an attacker can mint an effectively unbacked, arbitrarily large balance of TRX or TRC10 tokens out of an Exchange pool. This is direct theft of user/pool funds and creation of unbacked balance, satisfying the accepted-impact bar (unauthorized account operation / theft / unbacked balance).

### Likelihood Explanation
Reaching this code requires only a signed `ExchangeTransactionContract` from any account holding a small amount of an asset already listed in an Exchange pool (Exchange pools are user-creatable via `ExchangeCreateContract`, so an attacker can create their own pool and trade against it). No special privilege, SR/witness/committee role, or network condition is needed — this matches "exchange and market order handling" reachable by an anonymous order placer, one of the explicitly in-scope categories. The only gating factor is whether the chain has already activated the "harden resource calculation" proposal that switches `hardenedCalc` to `true`; while this cannot be independently confirmed from static code alone, the vulnerable `ExchangeProcessor`/non-hardened branch remains present and reachable in the codebase and is the default when the proposal is not yet active.

### Recommendation
Remove the non-hardened `ExchangeProcessor` path (or make `SafeExchangeProcessor` unconditional) so that `Math.pow`/`StrictMath.pow` results are always computed with big-decimal precision and explicitly checked (`Double.isInfinite`, `Double.isNaN`, and range checks) before narrowing to `long`, throwing `ContractValidateException`/`ArithmeticException` instead of silently clamping, mirroring what `SafeExchangeProcessor` already does. Additionally, `ExchangeCapsule.transaction()` should validate `newFirstTokenBalance`/`newSecondTokenBalance >= 0` unconditionally, not only when `hardenedCalc` is true.

### Proof of Concept
1. Create (or reuse) an `Exchange` pool with a first token balance `B1` and second token balance `B2` via `ExchangeCreateContract`.
2. Submit an `ExchangeTransactionContract` selling the first token with `tokenQuant` chosen so that `tokenQuant / (B1 + tokenQuant)` pushed through `exchangeToSupply` (exponent 0.0005) and then through `exchangeFromSupply` (exponent 2000) yields a ratio `supplyQuant/supply` large enough that `Math.pow(base, 2000.0)` in `exchangeFromSupply` overflows to `Double.POSITIVE_INFINITY`.
3. Observe that `(long) exchangeBalance` in `ExchangeProcessor.exchangeFromSupply` [5](#0-4)  returns `Long.MAX_VALUE` rather than throwing, which `ExchangeTransactionActuator` then credits to the caller's asset/TRX balance while the pool's counter-balance is decremented (and can go negative since the non-hardened path skips the `>=0` check), effectively minting unbacked funds.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
