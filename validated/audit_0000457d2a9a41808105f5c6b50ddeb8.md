Audit Report

## Title
Reward-per-token accumulator in `pallet-asset-rewards` can be permanently deflated via floor-division rounding while `last_update_block` still advances - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`reward_per_token` computes `reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked` using integer division, and `update_pool_rewards` unconditionally sets `last_update_block` to the current block every time any staking-related extrinsic runs, even if the computed delta rounds down to zero. Because the elapsed-block window used in the next call is measured from this newly advanced `last_update_block`, any interval whose reward delta rounds to zero is permanently lost rather than merely deferred, silently starving reward accrual for stakers in pools where `reward_rate_per_block * PRECISION_SCALING_FACTOR < total_tokens_staked`.

## Finding Description
`reward_per_token` at [1](#0-0)  computes the per-token reward delta with floor division. `update_pool_and_staker_rewards` calls `reward_per_token` and then unconditionally calls `update_pool_rewards`, which always advances `last_update_block` to `current_block_number()` regardless of whether `reward_per_token_stored` actually changed: [2](#0-1) .

This is reachable from any unprivileged, publicly callable extrinsic that touches the pool state: `stake` [3](#0-2)  and `unstake` (callable on one's own stake at any time, or on others' stake after pool expiry) [4](#0-3) , both of which call `update_pool_and_staker_rewards` before doing anything else. Repeatedly invoking these once per block keeps `rewardable_blocks_elapsed` at 1, and if `reward_rate_per_block * PRECISION_SCALING_FACTOR < total_tokens_staked`, the division truncates to zero every time, so `reward_per_token_stored` never increases while `last_update_block` keeps advancing — permanently erasing the reward window rather than deferring it. `derive_rewards`, which computes actual staker payouts from `reward_per_token_stored`, is directly starved as a result: [5](#0-4) .

No existing guard checks whether the computed delta is zero before advancing `last_update_block`, and `PRECISION_SCALING_FACTOR` is a small constant rather than a large fixed-point scale, making the rounding-to-zero condition realistic for ordinary pool configurations (e.g., low emission rate relative to a large staked-asset supply or high-decimal asset).

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" / reward/payout-state impact category: it causes reward-payout state (`reward_per_token_stored`) to permanently fail to conserve the value the pool admin funded, starving legitimate stakers of rewards they should have accrued. Any account — the staker itself, or a third party under the post-expiry `unstake`/`harvest_rewards` path — can trigger `update_pool_and_staker_rewards` cheaply and repeatedly, making the zero-rounding condition a persistent rather than occasional defect for any pool meeting the `reward_rate_per_block * PRECISION_SCALING_FACTOR < total_tokens_staked` condition.

## Likelihood Explanation
No privileged role, validator, governance action, or compromised infrastructure is required. The bug is triggerable via ordinary, expected use of the public `stake`/`unstake`/`harvest_rewards` extrinsics, and can occur unintentionally from routine staking activity in a realistic pool configuration, or be deliberately induced by any signed account calling these entry points once per block.

## Recommendation
Only advance `last_update_block` when the computed `reward_per_token` delta is non-zero, so unapplied elapsed time carries forward to the next update instead of being discarded; alternatively, increase `PRECISION_SCALING_FACTOR` to a much larger fixed-point scale (e.g., `1e18`-like) and/or track and accumulate the remainder of the division so no elapsed-time contribution is silently lost to floor-division.

## Proof of Concept
1. Admin creates a pool with `reward_rate_per_block = R` and total staked `S` such that `R * PRECISION_SCALING_FACTOR < S` (e.g., `R = 100`, `S = 1_000_000` with `PRECISION_SCALING_FACTOR = 4096`).
2. Any staker calls `stake(pool_id, 0)` (or `unstake`/`harvest_rewards`) once per block.
3. Each call computes `reward_per_token`: `100 * 1 * 4096 / 1_000_000 = 0` (floor division), so `reward_per_token_stored` is unchanged, per [6](#0-5) .
4. Each call still sets `last_update_block = current_block` via `update_pool_rewards`, per [7](#0-6) , so the next `rewardable_blocks_elapsed` computation resets to 1.
5. Result: `reward_per_token_stored` remains 0 (or frozen) for the pool's entire duration, and `derive_rewards` never credits stakers despite admin-funded rewards sitting in the pool account.

			pool_info: &PoolInfoFor<T>,

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
