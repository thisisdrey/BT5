### Title
Dust-transfer of deposit/debt tokens fills a victim's per-account token list (`MAX_TOKENS_PER_USER`), permanently blocking them from new deposits, mints and collateral additions — (File: contracts/Pool.sol)

### Summary
`Pool.addToDepositTokensOfAccount(address account_)` and `Pool.addToDebtTokensOfAccount(address account_)` are public entry points that write to the per-account `depositTokensOfAccount`/`debtTokensOfAccount` `MappedEnumerableSet`s. The `account_` argument is fully caller-supplied and is guarded only by `_revertIfSenderIsNotDepositToken/_revertIfSenderIsNotDebtToken` (the *caller* must be a registered token, not the account). A `DepositToken.deposit(amount, onBehalf_)` or an ordinary deposit-token `transfer` to an arbitrary recipient triggers this path, so an attacker can create list entries for *any* account. Because `onlyIfAdditionWillNotReachMaxTokens` caps the combined debt+deposit list at `MAX_TOKENS_PER_USER = 30`, an attacker can dust-fund a victim with ~30 distinct registered deposit tokens and permanently revert all future first-time token additions for that victim. [1](#0-0) [2](#0-1) 

### Finding Description
This is the Metronome analog of CVE-2012-0393 (a crafted parameter reaching an unprotected "constructor" sink to create/overwrite objects). The "constructor" is the per-account list-entry creation:

- `addToDepositTokensOfAccount(account_)` derives `_depositToken` from `_msgSender()` and inserts `account_` into `depositTokensOfAccount` — `account_` is arbitrary attacker input. [3](#0-2) 
- The insertion is preceded by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`. [4](#0-3) 
- `DepositToken` and `DebtToken` call these Pool hooks whenever a balance goes from 0 → nonzero (per the function docs at lines 200–201 and 212–213). A dust `transfer`/`deposit(amount, victim)` on each of the ~30 registered collaterals is enough to fill the victim's list; the attacker can also batch this through `Operator.execute`. [5](#0-4) [6](#0-5) 

Caveat/uncertainty: the exact DepositToken hook that triggers `addToDepositTokensOfAccount` (mint vs. `transfer` hook) was not fully read in this pass; the grep confirms `DepositToken.sol` calls it, and the Pool doc comment states it fires when a balance "changes from 0". Either a dust `transfer` or a dust `deposit(onBehalf)` suffices — both are permissionless.

### Impact Explanation
Once the victim's combined list reaches 30 entries, every operation that needs to add a *new* token for them reverts with `UserReachedMaxTokens`:
- depositing a collateral type they don't already hold (`DepositToken.deposit` → `addToDepositTokensOfAccount`),
- minting a synthetic whose debt token isn't already in their list (`DebtToken.mint`/`issue` → `addToDebtTokensOfAccount`).

A victim whose collateral is devaluing cannot add a *different* collateral type to restore health and can be liquidated (`Pool.liquidate` seizes collateral from any unhealthy account). [7](#0-6)  The state is not self-healing for tokens the victim never wanted: entries are removed only when the balance returns to 0 (`removeFromDepositTokensOfAccount`), and dust balances can't be removed if the victim can't transfer out — but even if the victim cleans them up, the attacker can refill the list with new dust at negligible cost (no supply-cap, whitelist, or `SynthContext` check restricts `account_`). This is a griefing that produces temporary freezing of funds and forced liquidation — within the accepted impact set. [8](#0-7) 

### Likelihood Explanation
- Fully unprivileged: any EOA can execute it, with or without `Operator.execute`. No governor/guardian/keeper/oracle involvement.
- Cost is bounded by acquiring dust amounts of ~30 deposit/debt tokens (dust of each collateral, plus dust of minted synths to add debt-token entries is optional — deposit tokens alone can fill the list if the pool lists ≥30 or enough combined).
- Feasibility depends on the deployed pool having enough registered tokens to reach 30 combined entries; the `ReachedMaxDepositTokens` check at line 703 shows pools themselves are capped at 30 deposit tokens, so deposit+debt entries together can realistically reach the cap on a mature pool.
- No existing mitigation stops it: `nonReentrant` doesn't apply (the victim isn't calling), pause flags don't apply to token transfers the attacker initiates, and there is no opt-in/allowlist mechanism.

### Recommendation
Make list-entry creation require consent or self-funding, e.g.:
- Only allow `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` when `account_ == _msgSender()` of the initiating user action, or pass the original depositor and skip insertion when the recipient didn't initiate. Alternatively, cap only entries the account opted into.
- Alternatively, let accounts remove unwanted entries themselves (permissionless `removeFrom*TokensOfAccount` for `account_ == _msgSender()` even with a nonzero balance isn't safe — instead allow `transfer`/`withdraw` to 0), or raise/decouple the cap: keep the gas-bound `debtOf`/`depositOf` loops bounded by a separate limit rather than coupling it to token ownership.
- At minimum, exclude tokens with only dust balances from counting (e.g., require a minimum first-deposit amount before the account entry is created).

### Proof of Concept
Hardhat fork sketch:

```solidity
// victim = a fresh account holding 1 deposit token (msdWETH)
// attacker deploys nothing; uses only public entry points

address[] memory dtokens = pool.getDepositTokens(); // N registered collaterals
for (uint i; i < dtokens.length && i < 30; ++i) {
    IDepositToken dt = IDepositToken(dtokens[i]);
    IERC20 underlying = dt.underlying();
    // acquire 1 wei of each underlying (or of the deposit token itself)
    deal(address(underlying), attacker, 1);
    underlying.approve(address(dt), 1);
    dt.deposit(1, victim); // -> pool.addToDepositTokensOfAccount(victim)
}
// Optionally also mint dust synth debt entries via DebtToken.issue to victim? (requires victim init;
// dust deposit-token transfers alone suffice)

// assert victim's list is full
assertEq(
    pool.getDepositTokensOfAccount(victim).length +
    pool.getDebtTokensOfAccount(victim).length,
    30
);

// victim tries to deposit a NEW collateral type -> reverts
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newCollateralDepositToken.deposit(amount, victim);

// if victim is now unhealthy (existing collateral fell), anyone can liquidate;
// victim cannot top-up with a different collateral -> forced liquidation
pool.liquidate(msSynthetic, victim, repayAmt, existingDepositToken);
```

Alternatively, if `DepositToken`'s token hook fires on plain ERC20 transfers, `dt.transfer(victim, 1)` achieves the same without spending underlying. The core invariant broken: a permissionless parameter (`account_`) mutates another user's protocol-critical state, analogous to a crafted parameter instantiating an arbitrary object.
