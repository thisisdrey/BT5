### Title
Missing range check in generated `decUintSlice`/`decUintArray` allows silent truncation of `uint` slice elements decoded from untrusted gob data - ([File: src/encoding/gob/decgen.go])

### Summary
The `decgen.go` code generator (comment: "Code generated by go run decgen.go -output dec_helpers.go; DO NOT EDIT") emits a `uint` conversion case whose overflow check is commented out (`/*TODO if math.MaxUint32 < x { error_(ovfl) }*/`), unlike every sibling numeric case (`int`, `int8/16/32`, `uint16`, `uint32`, `uintptr`) which all validate the decoded 64-bit value against the target type's range before narrowing. This produces `decUintSlice`/`decUintArray` in `src/encoding/gob/dec_helpers.go` that silently truncates an attacker-controlled `uint64` gob value to `uint(x)` with no bounds check, on platforms where `uint` is 32 bits.

### Finding Description
Attacker input: a crafted gob stream decoded by `(*gob.Decoder).Decode` into a struct/type containing a `[]uint` (or `[N]uint`) field — an ordinary victim workflow using `encoding/gob`, e.g. an RPC server (`net/rpc`) or any application unmarshaling gob data from a network peer or file.

Entry point: `Decoder.decodeSlice` (`src/encoding/gob/decode.go:652`) calls `dec.decodeArrayHelper`, which dispatches through `decSliceHelper[reflect.Uint]` = `decUintSlice` (`src/encoding/gob/dec_helpers.go:392`).

Failed check: `decUintSlice` calls `state.decodeUint()` to get the full `uint64` wire value `x`, then directly does `slice[i] = uint(x)` with the overflow check commented out:
```go
x := state.decodeUint()
/*TODO if math.MaxUint32 < x {
    error_(ovfl)
}*/
slice[i] = uint(x)
```
This is inconsistent with every other numeric decoder in the same file/generator, e.g. `decIntSlice` (checks `MinInt`/`MaxInt`), `decUint16Slice`/`decUint32Slice` (check `math.MaxUint16`/`math.MaxUint32`), and `decUintptrSlice` (checks against `^uintptr(0)`). It is also inconsistent with the scalar (non-slice) counterpart `decUint32`/`decUint64` in `decode.go:287-296`, which are properly range-checked when decoding a plain `uint` field (via `decOpTable[reflect.Uint]` set in `decode.go:1297`).

Sink: on any platform where `uint` is 32 bits, `uint(x)` truncates the high 32 bits of the attacker-supplied 64-bit value instead of raising a decode error — the classic "incorrect conversion between numeric types due to missing range checks" pattern cited in the CVE, silently discarding high bits when the size value exceeds the target type's range.

### Impact Explanation
The security effect is data integrity: a value that should be rejected as out-of-range (matching the documented gob contract that "the destination variable must be able to represent the value or the decode operation will fail," per `doc.go`) is instead silently accepted with a wrong, truncated numeric value inside a `[]uint`/`[N]uint`. This breaks the invariant enforced everywhere else in the decoder that overflow is detected and turned into a decode error. Concretely, if an application uses decoded `uint` slice values for indexing, capacity/length computations, permission bitmasks, or protocol counters, a wrong (attacker-influenced) truncated value can propagate into application logic. This is a genuine, narrowly-scoped correctness/integrity bug reachable from ordinary untrusted gob input; it would fit Go's PUBLIC track as a data-integrity defect in the standard library rather than a memory-safety or RCE issue.

### Likelihood Explanation
Trivial to trigger: any program that calls `gob.NewDecoder(r).Decode(&v)` where `v` (or a nested field) contains a `[]uint` or `[N]uint`, fed with attacker-controlled data (e.g., over a `net/rpc` gob-encoded connection, or any gob file/stream from an untrusted source) hits this exact code path. No special privileges are needed — this is the intended, documented usage of `encoding/gob`. The bug only manifests on GOARCH where `uint` is 32-bit (386, arm, wasm, etc.); on 64-bit platforms `uint(x)` is a no-op since `uint64` and `uint` are the same width there.

### Recommendation
Un-comment and enable the range check in `decgen.go`'s `"uint"` entry (and regenerate `dec_helpers.go`), mirroring the pattern already used for `uint16`, `uint32`, and `uintptr`:
```go
{
    "uint",
    "Uint",
    `x := state.decodeUint()
    if uintOverflows(x) {
        error_(ovfl)
    }
    slice[i] = uint(x)`,
},
```
where the check should test against the actual bit-width of `uint` on the build platform (analogous to how `decOpTable[reflect.Uint]` picks `decUint32` vs `decUint64` based on `intBits` in `decode.go`), i.e. something like `if bits.UintSize == 32 && math.MaxUint32 < x { error_(ovfl) }`.

```go
import (

// TestUintSliceOverflowNotDetected demonstrates that decoding a []uint
// slice does not reject a value that overflows uint32 on 32-bit
// platforms (GOARCH=386/arm/wasm), unlike decoding a []uint32 slice.
func TestUintSliceOverflowNotDetected(t *testing.T) {
	type inUint32Slice struct {
		S []uint32
	}
	type outUintSlice struct {
		S []uint
	}

	// Encode a value that exceeds math.MaxUint32.
	in := inUint32Slice{} // placeholder; real repro requires encoding a
	// uint64 value > math.MaxUint32 tagged as "uint" wire type, which is
	// straightforward when the source struct field itself is `[]uint64`
	// or `[]uint` on a 64-bit encoding host talking to a 32-bit decoding
	// host. On a 32-bit GOARCH build, run:
	var b bytes.Buffer
	enc := gob.NewEncoder(&b)
	type inUintSlice struct {
		S []uint
	}
	if err := enc.Encode(inUintSlice{S: []uint{math.MaxUint32 + 1}}); err != nil {
		t.Fatal(err)
	}

	var out outUintSlice
	dec := gob.NewDecoder(&b)
	err := dec.Decode(&out)

	// EXPECTED (on 32-bit uint platforms): err != nil, matching the
	// behavior of the analogous []uint32/[]int decoders which reject
	// out-of-range values (see TestOverflow in codec_test.go).
	// ACTUAL: err == nil and out.S[0] is the silently truncated value
	// uint32(math.MaxUint32+1) == 0, because decUintSlice's range check
	// is commented out in decgen.go / dec_helpers.go.
	if err == nil {
		t.Fatalf("expected overflow error decoding []uint, got nil; out.S=%v", out.S)
	}
	_ = in
}
```

```go
		// It is kind uint but not type uint. TODO: We can handle this unsafely.
		return false
```

```go
// decodeSlice decodes a slice and stores it in value.
// Slices are encoded as an unsigned length followed by the elements.
func (dec *Decoder) decodeSlice(state *decoderState, value reflect.Value, elemOp decOp, ovfl error, helper decHelper) {
	u := state.decodeUint()
	typ := value.Type()
	size := uint64(typ.Elem().Size())
	nBytes := u * size
	n := int(u)
	// Take care with overflow in this calculation.
	if n < 0 || uint64(n) != u || nBytes > tooBig || (size > 0 && nBytes/size != u) {
		// We don't check n against buffer length here because if it's a slice
		// of interfaces, there will be buffer reloads.
		errorf("%s slice too big: %d elements of %d bytes", typ.Elem(), u, size)
	}
	if value.Cap() < n {
		safe := saferio.SliceCapWithSize(size, uint64(n))
		if safe < 0 {
			errorf("%s slice too big: %d elements of %d bytes", typ.Elem(), u, size)
		}
		value.Set(reflect.MakeSlice(typ, safe, safe))
	} else {
		value.SetLen(n)
	}
	dec.decodeArrayHelper(state, value, elemOp, n, ovfl, helper)
}
```

```go
const (
	intBits     = 32 << (^uint(0) >> 63)
	uintptrBits = 32 << (^uintptr(0) >> 63)
)

func init() {
	var iop, uop decOp
	switch intBits {
	case 32:
		iop = decInt32
		uop = decUint32
	case 64:
		iop = decInt64
		uop = decUint64
	default:
		panic("gob: unknown size of int/uint")
	}
	decOpTable[reflect.Int] = iop
	decOpTable[reflect.Uint] = uop

	// Finally uintptr
	switch uintptrBits {
	case 32:
		uop = decUint32
	case 64:
		uop = decUint64
	default:
		panic("gob: unknown size of uintptr")
	}
	decOpTable[reflect.Uintptr] = uop
}
```
