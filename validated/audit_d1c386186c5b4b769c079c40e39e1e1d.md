### Title
Byte-width integer overflow in multi-pack-index chunk-table size calculation causes out-of-bounds panic - (File: internal/git/stats/repository_info.go)

### Summary
### Finding Description
`MultiPackIndexInfoForPath` parses the `multi-pack-index` file header and reads the chunk count directly as a `byte` (uint8): [1](#0-0) 

The chunk count byte is then used to size the table-of-contents buffer via `12*chunkCount`, where the multiplication is carried out entirely in `byte` (uint8) arithmetic because `chunkCount` is typed `byte`: [2](#0-1) 

Because `byte` arithmetic wraps modulo 256, any `chunkCount` value where `12*chunkCount ≥ 256` silently overflows to a much smaller number (e.g. `chunkCount = 250` → `12*250 = 3000 mod 256 = 184`), producing a `midxTOC` buffer far smaller than what the subsequent per-chunk loop assumes it can index into: [3](#0-2) 

The loop iterates `i` from `0` to `chunkCount-1` and indexes `midxTOC[i*12 : i*12+4]` without ever re-validating against the (correctly, mathematically) required buffer length, so once `i*12` exceeds the undersized buffer, the slice expression panics with "index out of range" — this is the direct structural analog of the SablierFlow `elapsedTime * ratePerSecond` overflow: a fixed-width type multiplication whose result silently wraps and is then used, unguarded, in a way that later causes total failure of the operation (there, a permanent revert; here, a runtime panic).

This function is reachable from Gitaly's `RepositoryInfo` gRPC RPC, which is exposed to any authenticated client and computes multi-pack-index information for a repository as part of routine repository introspection performed by GitLab Rails/Workhorse, as shown by its wiring in `internal/gitaly/service/repository/repository_info.go`. A user who can get a crafted `multi-pack-index` file into a repository's `objects/pack` directory (e.g., by pushing content that GitLab's repacking/housekeeping pipeline processes, or by directly placing/replacing the file if any path allows repository-relative writes) can set the one-byte chunk-count field to a value that produces this overflow.

### Impact Explanation
When `RepositoryInfo` (or other internal callers of `MultiPackIndexInfoForPath`, e.g. `housekeeping/optimization_strategy.go`) parses a crafted or corrupted `multi-pack-index` with a chunk count causing `12*chunkCount` to overflow `uint8`, the function panics. If this panic occurs inside a gRPC handler goroutine it is expected to be caught by the `panichandler` interceptor and converted into an `Internal` gRPC error, so the primary externally-visible impact is a failed RPC for the affected request rather than a full process crash — this is a Denial-of-Service against that specific RPC/repository for any caller invoking `RepositoryInfo`. If any of the internal callers (e.g. `housekeeping` optimization logic that runs outside a request-scoped goroutine with panic recovery, such as background repacking flows) invoke this function without a `recover()`, the impact escalates to crashing that supervisory goroutine/process, which is a materially more serious DoS. I was not able to fully verify, within the available context, whether every caller path is wrapped in panic recovery; the `gitaly-server` gRPC handlers are, per `internal/gitaly/server/server.go`, but the `internal/git/housekeeping` callers's execution context was not confirmed.

### Likelihood Explanation
The vulnerable value is a single attacker/environment-influenced byte in a file format that Gitaly itself writes (`git multi-pack-index write`), so under normal operation `chunkCount` is small (well under the ~21 required to trigger overflow with the observed header layout). However, the header is not otherwise integrity-checked beyond the 4-byte magic and version fields before this byte is trusted, so any process capable of writing or corrupting a repository's `multi-pack-index` file (this includes any workflow where Gitaly reads a MIDX from an untrusted/attacker-influenced repository — e.g. from a forked or imported repository, or an alternates/object-pool-linked directory) can trigger the panic. This lowers the bar compared to needing arbitrary RPC-field control, but it does require some means of writing/corrupting the specific file, which is a plausible but not the most direct exploitation path.

### Recommendation
Widen `chunkCount` to an `int`/`int` immediately upon reading it from the header byte, and perform the `12*chunkCount` size calculation in that wider type before calling `make`. Additionally, validate that the read buffer is large enough (`len(midxTOC) >= int(chunkCount)*12`) before entering the per-chunk loop, and bound-check each `i*12:i*12+4` slice access explicitly rather than relying on the initial allocation size implicitly matching the loop bound.

### Proof of Concept
```go
func TestMultiPackIndexInfoForPath_ChunkCountOverflow(t *testing.T) {
    // chunkCount = 250 (0xFA). 12*250 = 3000, which overflows byte arithmetic
    // to 3000 % 256 = 184, allocating a 184-byte midxTOC buffer.
    header := []byte{
        'M', 'I', 'D', 'X', // signature
        0x1,                // version
        0x1,                // object ID version
        0xFA,               // number of chunks (250) -- overflow trigger
        0x0,                // number of base files
        0, 0, 0, 0,         // number of packfiles
    }
    // Append 250*12 bytes of arbitrary chunk-table data as a real MIDX would contain.
    body := append(header, make([]byte, 250*12)...)

    path := filepath.Join(t.TempDir(), "multi-pack-index")
    require.NoError(t, os.WriteFile(path, body, 0o644))

    // Expected: this panics with "index out of range" once i*12 exceeds 184,
    // instead of returning a graceful parse error.
    _, err := stats.MultiPackIndexInfoForPath(path)
    require.Error(t, err) // currently panics instead
}
```
