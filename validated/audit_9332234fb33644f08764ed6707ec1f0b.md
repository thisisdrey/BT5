### Title
Block/transaction-fee rewards allocated to a witness with zero votes become permanently unclaimable - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.payReward()` (invoked as `payBlockReward`/`payTransactionFeeReward` from block application in `Manager`) unconditionally records a witness's non-brokerage reward share into `DelegationStore` for the current cycle, keyed only by `(cycle, witnessAddress)`, with no check on whether the witness actually has any voters (`totalVote`). If that witness has `voteCount == 0` for the cycle, the recorded reward can never be distributed: `computeReward()` explicitly skips any cycle/witness pair where `totalVote == 0` (or `REMARK`), and no voter or the witness itself is credited that value. This is directly analogous to the Y2K Carousel bug where emissions sent to a null-participant epoch are permanently lost, because in both cases funds are pre-allocated to a "pool" (epoch pool / (cycle,witness) reward pool) keyed to a set of eligible claimants that can end up empty, with no fallback recovery path.

### Finding Description
`payReward` in `MortgageService` is called for every block reward and transaction fee reward: [1](#0-0) 

It splits the value into a `brokerageAmount` (credited immediately to the witness via `adjustAllowance`) and the remainder, which is stored via `delegationStore.addReward(cycle, witnessAddress, value)` — an accounting bucket that is only redeemable by voters proportional to their vote share for that witness/cycle.

When a voter withdraws, `computeReward` divides the stored reward by `totalVote` for that witness/cycle: [2](#0-1) 
If `totalVote == 0` (no one voted for that witness in that cycle), the reward for that cycle/witness pair is skipped entirely (`continue`), meaning the value stored by `addReward` is never paid out to anyone — not the witness, not any voter. The new VI-based algorithm has an equivalent skip: `accumulateWitnessVi` in `DelegationStore` only advances the VI (i.e., makes reward distributable) when `voteCount != 0`; when `voteCount == 0` the accumulated reward is simply dropped by forwarding the previous VI unchanged: [3](#0-2) 

A witness can be elected/paid with zero votes because reward distribution (`incentiveManager.reward(...)`, called from `MaintenanceManager.doMaintenance()`) is not gated on the witness having `voteCount > 0` — the witness list simply comes from `consensusDelegate.getAllWitnesses()` / `getActiveWitnesses()`: [4](#0-3) 
This can happen on chains/testnets with few registered witnesses relative to `MAX_ACTIVE_WITNESS_NUM`, or transiently right after a witness's votes drop to zero while it remains in the active/standby set for the current cycle (vote counts are only reconciled once per maintenance cycle).

Unlike the Carousel `setEpochNull` recommendation, there is no equivalent recovery/reallocation routine in java-tron: no code path detects a zero-vote reward bucket after the fact and returns/reallocates the value; it simply remains an inert, unreachable accounting entry in `DelegationStore`'s reward key-space forever.

### Impact Explanation
This causes value to be permanently and silently locked/lost within the protocol's own accounting: TRX that was intended as block/transaction-fee reward for a witness's voters is credited to a reward bucket keyed by (cycle, witnessAddress) that becomes mathematically unclaimable once `totalVote == 0` for that key. No account operation, present or future, can recover it — `computeReward`/`accumulateWitnessVi` both permanently gate on vote count at the time of computation, and cycles/witness pairs are not revisited later. This is a protocol-level, unbacked-value/permanent-freezing-of-funds condition reachable purely through normal consensus/reward-cycle processing (block application in `Manager`/`MaintenanceManager`), not through any privileged or malicious actor action.

### Likelihood Explanation
Likelihood is moderate: it requires a witness with zero votes to still be included in the reward round for that cycle. This is realistic in low-witness-count environments (private/permissioned chains, testnets) where `getAllWitnesses()`/`getActiveWitnesses()` includes witnesses that have not yet accumulated votes (e.g., a newly registered witness before the maintenance cycle has recorded any vote), or where votes transiently drop to zero for a witness that remains part of the current cycle's active/standby set. On mainnet with the full 27-witness competitive set this is less likely, but the code contains no invariant preventing it, and the described analog is a design gap, not a one-off implementation bug in a single actuator.

### Recommendation
Add a check in `payReward` (or in `computeReward`/maintenance-cycle rollover) so that if a witness has `voteCount == 0` at the time reward is paid for a cycle, the reward is not silently stored as unclaimable in `DelegationStore`, but instead is either: (1) skipped and returned to the originating reward pool, (2) redirected to the treasury/burn address, or (3) accumulated and rolled forward until the witness receives votes with a documented cutoff rather than remaining permanently stranded. Additionally, add a periodic sweep (analogous to the recommended `setEpochNull` override) that detects reward entries in `DelegationStore` for cycles/witnesses with zero total votes and reclaims them, rather than leaving the amount as dead accounting weight indefinitely.

### Proof of Concept
1. Start a network configuration where a witness `W` is included in `consensusDelegate.getAllWitnesses()`/`getActiveWitnesses()` but has `voteCount == 0` for cycle `C` (e.g., newly registered witness, or one whose votes were fully withdrawn in the same cycle they are scheduled to produce).
2. Let `W` produce a block; `Manager` invokes `mortgageService.payBlockReward(W, blockReward)` and `payTransactionFeeReward(W, fee)`.
3. `payReward` computes `brokerageAmount` for `W` (credited immediately) and calls `delegationStore.addReward(C, W, remainder)` for the remainder.
4. At maintenance/cycle rollover, `MaintenanceManager.doMaintenance()`/`accumulateWitnessVi` processes cycle `C` for `W` with `voteCount == 0`, so the VI is not advanced (old reward algorithm: `computeReward` requires `totalVote != 0`, so any later voter to `W` starting from cycle `C` cannot receive the `C`-cycle reward — `getWitnessVote(C, W)` is `0`).
5. No voter of `W` for cycle `C` exists (by construction), so `MortgageService.computeReward`/`withdrawReward` never distributes `remainder` to anyone, and there is no other code path that transfers or reclaims it. The value recorded by `addReward(C, W, remainder)` remains permanently unclaimable.

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
