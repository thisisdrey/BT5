### Title
Access-key nonce is reset below an already-consumed value on DeleteKey+AddKey within the same block, enabling transaction replay - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`add_regular_key` unconditionally sets a newly (re-)added key's nonce to `initial_nonce_value(block_height) = (block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, regardless of the nonce the same public key previously reached. If a transaction with a high nonce is applied earlier in the same chunk/block, and a later transaction in that block deletes and re-adds the same public key, the stored nonce for that key drops back below the value already consumed, re-opening the nonce window for replay of the earlier transaction.

### Finding Description
`add_regular_key` in [1](#0-0)  always overwrites `access_key.nonce` with `initial_nonce_value(block_height)` computed at [2](#0-1) , independent of any nonce value the account previously used with that public key.

`verify_nonce`, used on the transaction-apply path, only compares the transaction's nonce to the *currently stored* access-key nonce (or `pending.max_nonce`, which is a mempool-only, non-persisted speculative bound) — see [3](#0-2) . It has no memory of the highest nonce ever consumed by a given public key once that key's `AccessKey` record is deleted and recreated; it only checks against whatever value is currently written in the trie.

Exploit flow within block `N` (attacker fully controls the order/content of the actions in their own transactions):
1. Account `A` owns FullAccess key `K`, with a stored nonce below `(block_height-1)*1_000_000`.
2. `tx1`, signed by `K` with `nonce = n = (block_height-1)*1_000_000 + 1`, is applied. `verify_nonce` accepts it (`n` is above the current nonce and below the block's upper bound `block_height*1_000_000`), and the runtime commits `access_key.nonce = n` to the trie via `set_tx_state_changes`.
3. Later in the same block, a second transaction from `A` (`DeleteKey(K)` then `AddKey(K, <same public key>)`) is applied. `action_delete_key` removes the access key record, and `action_add_key` → `add_regular_key` recreates it with `nonce = (block_height-1)*1_000_000`, which is strictly less than `n`.
4. The account's on-chain access-key nonce for `K` has now regressed below `n`. A resubmission of `tx1` (attacker already has this signed transaction; no third-party capture is even required since the attacker signed it) will pass `verify_nonce` again, because `n > current stored nonce`.

Nothing else in the described path blocks this: signature verification passes (same key material, same public key), storage-staking checks are unaffected, and there is no separate transaction-hash-based replay cache — nonce plus the access key is the sole replay-prevention mechanism for a given key in NEAR's model.

### Impact Explanation
This breaks the documented nonce-monotonicity invariant for a key's lifetime and permits replay of a previously-applied, already-consumed signed transaction. This matches the "double-spend/replay" bounty category: any action whose safety relies on nonce uniqueness (e.g., a signed instruction consumed once by a bridge, marketplace, or exchange-style contract call) can be re-executed by resubmitting the identical signed bytes once the key is deleted+recreated later in the same block, as long as the transaction's referenced block hash is still within the validity window used by header/tx-freshness checks.

### Likelihood Explanation
Preconditions are fully attacker-controlled and require no privilege beyond an ordinary funded account with a FullAccess key: the attacker chooses the order of actions and transactions they submit within a single block/chunk (subject to normal chunk inclusion by the network). The cost is limited to gas/fees for the extra `DeleteKey`+`AddKey` transaction. It is repeatable for any account/key the attacker controls, though external impact (rather than only affecting the attacker's own account) depends on the semantics of whatever `tx1` action is replayed.

### Recommendation
`add_regular_key` (and `add_gas_key`) should not blindly reset the nonce to `initial_nonce_value(block_height)`; instead it should ensure the new nonce is at least as large as any nonce previously observed for that public key in this account (e.g., track a per-account "highest ever nonce used per public key" independent of key deletion, or simply forbid recreating a key with a nonce lower than the maximum nonce value implied by the current block height that could have already been consumed this block). At minimum, the initial nonce assigned on `AddKey` must never be allowed to be lower than a nonce already committed in the same chunk/block for the same public key.

### Proof of Concept
Runtime integration test (in `runtime/runtime/src/access_keys.rs` or `runtime/runtime` apply-path tests):
1. Set up account `A` with FullAccess key `K`, apply-state `block_height = H`.
2. Apply `tx1` = `[Transfer(1 yocto) or any action]` signed by `K` with `nonce = n = (H-1)*1_000_000 + 1`; assert success and `get_access_key(A, K).nonce == n`.
3. In the same block/apply call, apply `tx2` = `[DeleteKey(K), AddKey(K, same public key)]`; assert success.
4. Assert `get_access_key(A, K).nonce == (H-1)*1_000_000`, which is `< n`.
5. Construct a byte-identical copy of `tx1` (same signature, same nonce `n`) and call `verify_and_charge_tx_ephemeral` / the full `validate_verify_and_charge_transaction` path against the post-tx2 state; assert it returns `TxVerdict::Success` (i.e., it is NOT rejected with `InvalidTxError::InvalidNonce`), demonstrating the same signed transaction is accepted a second time.

```rust
pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
```

```rust
fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
```

```rust
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
```
