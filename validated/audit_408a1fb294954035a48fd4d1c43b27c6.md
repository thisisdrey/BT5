### Title
Replay-window check/decrypt/update race allows duplicate packet acceptance - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` performs the anti-replay `Check`, then releases the lock, performs the (unlocked, comparatively expensive) AEAD decrypt, and only re-acquires the lock afterward to call `Update` and record the counter as seen. This mirrors the CToken bug class in the report: a critical accounting/state value (`totalCash`/exchange rate there, the replay-window bitmap here) is read, an external, unsynchronized operation is allowed to run, and the authoritative state is only written back afterward — leaving a window in which the same "resource" (an underlying token / a message counter) can be consumed twice before the ledger is updated.

### Finding Description
`Decrypt` in `connection_state.go` does:
1. Lock, `window.Check(l, messageCounter)` — read-only test of whether `messageCounter` looks unseen, unlock.
2. Unlocked: `dKey.DecryptDanger(...)` — AEAD decrypt (comparatively slow, does not touch the window).
3. Lock, `window.Update(l, messageCounter)` — marks the counter seen, unlock. [1](#0-0) 

Because `Check` and `Update` are not atomic with respect to each other (the lock is dropped in between), two goroutines processing two copies of the *same* ciphertext packet (an attacker on the wire can simply duplicate a captured UDP datagram — no valid certificate or CA trust is required to replay bytes at the transport layer) can both pass `Check` for the same `messageCounter` before either calls `Update`. Both then successfully complete `DecryptDanger` (which is a pure AEAD operation keyed by the already-negotiated session keys and has no knowledge of the anti-replay window), and both proceeds to use the decrypted plaintext (write to tun, process as LightHouse/Test/Control message, etc.) in `readOutsidePackets`. [2](#0-1) 

Only the second `Update` call will discover the duplicate and return `false`/`ErrAlreadySeen` — but by then the first copy has already been delivered to the tun device or otherwise acted upon, and the second's decrypted output may also have already been used depending on scheduling, since the check that would prevent this (`Update`) happens only after the expensive unlocked decrypt work. This is a classic TOCTOU (time-of-check to time-of-use) defect: the "cheap check" and "authoritative update" of shared replay state are split around an unsynchronized, non-trivial operation, exactly as the CToken bug split the exchange-rate read from `totalCash` mutation around an unrelated, uncontrolled operation (`sweepToken`).

The CHANGELOG shows the project has already fixed a related but distinct issue — "Lock replay window updates so concurrent readers can't corrupt it. (#1802)" — which hardened `Update`/`Check` internal consistency, but the `Check`-then-decrypt-then-`Update` sequencing gap in `Decrypt` itself (unlock between step 1 and step 3) remains architecturally present in this version. [3](#0-2) 

### Impact Explanation
If exploitable, this allows a network-path attacker (who does not need to hold a valid nebula certificate — they only need to be able to observe/duplicate encrypted UDP traffic between two already-established peers) to cause the same encrypted message to be delivered/processed twice on the receiving side. Depending on payload this could mean duplicate application-level packets forwarded to the tun device, duplicate LightHouse state updates, or duplicate Test/Control message side effects — a traffic replay bypass of the anti-replay protection that Noise/nebula is specifically designed to prevent.

### Likelihood Explanation
Exploitability depends on the receiver's packet-processing model actually running `readOutsidePackets` concurrently for duplicate UDP datagrams (e.g., multiple reader goroutines/queues, as suggested by the `q` (queue index) parameter threaded through `readOutsidePackets`, `handleOutsideMessagePacket`, etc.), and on the attacker being able to duplicate a captured packet on the wire quickly enough to land in that race window. This is plausible on a multi-queue UDP listener design but requires precise timing; I was not able to fully verify from the indexed code whether nebula's UDP read path always dispatches a given source/destination pair to a single serialized goroutine (which would eliminate this race) or can dispatch duplicate datagrans to different concurrent queues/goroutines. This determines whether the race window is practically reachable.

### Recommendation
Hold the `decryptLock` (or an equivalent per-connection-state lock) across the entire `Check` → `DecryptDanger` → `Update` sequence in `ConnectionState.Decrypt` and `VerifyRelay`, so the "check" and "commit" of replay-window state are atomic and no ciphertext can be processed against a window that hasn't yet marked it seen. Alternatively, restructure so `Update` (or a combined "check-and-reserve" operation) is called before decryption to atomically reserve the slot, and roll back (or simply drop) if decryption subsequently fails.

### Proof of Concept
Conceptual PoC (network-observation, no CA-signed certificate required):
1. Passively capture one encrypted `header.Message` UDP packet sent between two already-handshaken nebula peers.
2. Rapidly re-inject (duplicate) that exact packet twice, aimed to arrive at the receiver at nearly the same time so they are handled on separate goroutines/queues before either completes `window.Update`.
3. Observe (via test instrumentation such as `ci.window.Check`/`Update` counters, or duplicate application-level delivery to the tun device) whether both copies are decrypted and delivered before the duplicate is detected, confirming the TOCTOU race in `ConnectionState.Decrypt`. [1](#0-0)

```go
func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
```
