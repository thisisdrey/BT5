### Title
Griefing via dust `DepositToken` transfers fills a victim's deposit-token list to `MAX_TOKENS_PER_USER`, blocking them from depositing new collateral and forcing liquidation - (File: contracts/Pool.sol, contracts/DepositToken.sol)

### Summary
A kernel deadlock maps to a liveness/state-jamming bug here: an unprivileged attacker can jam a victim's `depositTokensOfAccount` set in `Pool` to its maximum size by sending dust amounts of every `DepositToken`, after which any `_mint` or `_transfer` that would add a new token to the victim's list reverts, and the victim cannot add collateral of a new type to defend an at-risk position.

### Finding Description
`DepositToken._transfer` adds the token to the recipient's per-account set in `Pool` whenever the recipient previously held zero of that token (`DepositToken.sol:517-520`). The same add happens in `_mint` on deposit (`DepositToken.sol:485-488`). Both paths call `pool.addToDepositTokensOfAccount(recipient_)`, which in `Pool.sol` pushes the token into the `MappedEnumerableSet` `depositTokensOfAccount[account]` and reverts when the set already holds `MAX_TOKENS_PER_USER` entries.

There is no opt-in or whitelist: `transfer(to_, amount_)` is a public ERC20 entry point guarded only by `_revertIfLocked(_msgSender, amount_)` (`DepositToken.sol:348-354`), which constrains only the sender's own unlocked balance — any amount the attacker holds is freely transferable to an arbitrary victim.

Attack flow:
1. Attacker deposits dust amounts of every active `DepositToken` in the pool (one deposit per collateral type; cost is bounded by deposit fees and dust amounts).
2. Attacker calls `DepositToken.transfer(victim, dust)` for each token until the victim's `depositTokensOfAccount` set reaches `MAX_TOKENS_PER_USER`.
3. From that point, any call path that adds a *new* deposit token to the victim — `deposit(amount, onBehalfOf = victim)` by the victim or anyone else, and incoming `transfer`/`transferFrom`/`seize` of a token type the victim does not already hold — reverts inside `Pool.addToDepositTokensOfAccount`.
4. If the victim's position drifts toward the liquidation threshold (market move or accrued interest via `DebtToken.accrueInterest`), they cannot top up with a new collateral type; their position remains liquidatable and they absorb liquidation fees that the locked-in check in `Pool.liquidate`/`DepositToken.seize` would otherwise let them avoid by posting collateral.

The attacker can also re-dust the victim whenever they burn a token to zero (which removes it from the set in `_burn`/`_transfer`), keeping the set saturated with only dust at stake.

### Impact Explanation
Temporary freezing of funds / forced loss: while the set is saturated, the victim's ability to deposit new collateral is blocked, which is the protocol's only self-service path to heal an unhealthy `debtPositionOf`. If the position crosses the liquidation boundary during the jam, the victim suffers liquidation losses (collateral seized plus liquidation fee split in `DepositToken.seize`/`Pool.liquidate`) that could have been prevented. The jam is temporary (the victim can withdraw fully and cycle tokens out), but liquidation timing does not wait for the victim to unjam, and unjamming does not restore an already-liquidated position. No privileged role, oracle corruption, or malicious external contract is needed — only public `transfer` calls.

### Likelihood Explanation
Any EOA can execute it. The cost is dust-sized deposits across the pool's collateral types plus gas; no approvals, no privileged access, no timing dependence beyond keeping the set full. The main requirement is that the victim does not already hold every token type (so that each dust transfer adds a new set entry) and that the pool has enough active `DepositToken`s to reach `MAX_TOKENS_PER_USER`. Caveat: the exact cap value and revert path inside `Pool.addToDepositTokensOfAccount` (the `MappedEnumerableSet` fullness check in `contracts/Pool.sol`) should be confirmed against the deployed bytecode; the call sites in `DepositToken.sol` that trigger it unconditionally are verified above.

### Recommendation
- Make the per-account deposit-token set opt-in: only add tokens in `_mint` (deposit), not on inbound `_transfer`/`transferFrom`, or remove the hard cap in `addToDepositTokensOfAccount` and have `debtPositionOf` skip economically irrelevant dust balances.
- Alternatively, require the recipient to hold a minimum non-dust amount or an explicit `acceptCollateral(token)` opt-in before a token counts toward the account's set.

### Proof of Concept
Foundry fork sketch (Hardhat equivalent works):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {IPool} from "../contracts/interfaces/IPool.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract DepositTokenListJamTest is Test {
    IPool pool = IPool(POOL_ADDR);          // e.g. mainnet deployment
    address victim = makeAddr("victim");

    function test_JamDepositTokenList() public {
        address[] memory depositTokens = pool.getDepositTokens();
        address attacker = makeAddr("attacker");

        // Victim opens a position on ONE collateral type
        IDepositToken dt0 = IDepositToken(depositTokens[0]);
        deal(address(dt0.underlying()), victim, 1_000e18);
        vm.startPrank(victim);
        IERC20(dt0.underlying()).approve(address(dt0), type(uint256).max);
        dt0.deposit(1_000e18, victim);
        vm.stopPrank();

        // Attacker dust-transfers every other deposit token to the victim
        for (uint256 i = 1; i < depositTokens.length; ++i) {
            IDepositToken dt = IDepositToken(depositTokens[i]);
            deal(address(dt.underlying()), attacker, 2);
            vm.startPrank(attacker);
            IERC20(dt.underlying()).approve(address(dt), 2);
            dt.deposit(2, attacker);          // attacker mints dust msdTOKEN
            dt.transfer(victim, 1);           // adds token to victim's set
            vm.stopPrank();
        }

        // Repeat with attacker-registered/fresh tokens until
        // depositTokensOfAccount(victim) length == MAX_TOKENS_PER_USER
        assertEq(pool.depositTokensOfAccount(victim).length, pool.MAX_TOKENS_PER_USER());

        // Victim now tries to deposit a collateral type they don't hold -> reverts
        IDepositToken dtNew = IDepositToken(depositTokens[depositTokens.length - 1]);
        deal(address(dtNew.underlying()), victim, 100e18);
        vm.startPrank(victim);
        IERC20(dtNew.underlying()).approve(address(dtNew), 100e18);
        vm.expectRevert(); // deposit-token list is full
        dtNew.deposit(100e18, victim);
        vm.stopPrank();
    }
}
```

Note: the PoC depends on the pool listing enough distinct `DepositToken`s to reach the cap (or on the victim's remaining slots being small); on a fork with few collateral types the attacker may only partially fill the list — the mechanism (unconditional `addToDepositTokensOfAccount` on any inbound transfer) is confirmed in `DepositToken.sol:517-520` and `DepositToken.sol:485-488`, while the exact set-capacity revert in `contracts/Pool.sol` should be verified in a local run.
