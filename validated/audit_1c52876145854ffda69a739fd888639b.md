Confirmed: `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` never enforces `write_freq`, and the HTTP write path (`stackslib/src/net/api/poststackerdbchunk.rs`) calls `try_replace_chunk` directly with no independent rate-limit check before it.

### Title
Unbounded StackerDB chunk writes via the `POST /v2/stackerdb/.../chunks` endpoint bypass `write_freq` rate limiting - (File: stackslib/src/net/stackerdb/db.rs)

### Summary
A single, validly-signed StackerDB slot owner can write an unbounded number of chunk versions to a node's replica through the RPC endpoint, because the write-path validation function `try_replace_chunk` never checks the configured `write_freq` cooldown, unlike the peer-to-peer sync path which is documented as relying on other mechanisms (bandwidth throttling) to cover this gap.

### Finding Description
`StackerDBTx::try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` performs exactly four checks: chunk size, slot existence, signer validity, staleness (`slot_version <= slot_validation.version`), and `max_writes`. [1](#0-0) 
It never reads or checks `slot_validation.write_time` against `self.config.write_freq`, even though `SlotValidation` and `StackerDBConfig` both carry these fields (as seen in tests referencing `write_freq`/`write_time`).

The RPC handler `RPCPostStackerDBChunkRequestHandler::try_handle_request` in `stackslib/src/net/api/poststackerdbchunk.rs` calls `tx.try_replace_chunk(...)` directly as the sole authorization/rate gate before committing the chunk to the local StackerDB and logging it as stored: [2](#0-1) [3](#0-2) 

The P2P push path (`handle_unsolicited_StackerDBPushChunk` / `validate_received_chunk`) has an explicit code comment acknowledging that write frequency is intentionally skipped there because "the `ConversationP2P` on which this chunk arrived will have already bandwidth-throttled the remote peer" — i.e., the design assumes *some* transport-level throttling covers the missing `write_freq` check. [4](#0-3) 

However, the direct HTTP `POST /v2/stackerdb/:principal/:contract/chunks` endpoint is not bandwidth-throttled per StackerDB write in the same way, and there is no other call site that enforces `write_freq` before `try_replace_chunk` is invoked from this handler. As a result, any address holding a valid StackerDB slot signing key can submit chunk versions back-to-back (up to `max_writes`, which can be very large, e.g. `u32::MAX` as configured in test fixtures) as fast as HTTP requests can be sent, each one broadcast to the network via `process_stacker_db_chunks` in `stackslib/src/net/relay.rs`. [5](#0-4) 

### Impact Explanation
This breaks the intended rate-limit equality (`elapsed_time_since_last_write >= write_freq`) that the config was designed to enforce for a slot signer. A single authorized (but otherwise unprivileged relative to other slot owners) signer can flood the local node's StackerDB storage and, more importantly, cause it to relay a large volume of validly-signed chunks to all its neighbors via `broadcast_message`, propagating repeated writes network-wide far faster than the StackerDB's designed cadence allows. This falls under "network-wide propagation of forged/excessive data" and can be used as an amplification/DoS vector against the whole StackerDB replica set, not just the writer's own node.

### Likelihood Explanation
Likelihood is high for any account that already owns one StackerDB slot (a normal, unprivileged, remotely reachable actor per a signer set/contract), since the endpoint is public, requires only a valid signature over incrementing `slot_version` values, and `max_writes` (not `write_freq`) is the only volume cap enforced in `try_replace_chunk`.

### Recommendation
Add a `write_freq` check inside `try_replace_chunk` (or in the RPC handler before calling it) using `slot_validation.write_time` and `get_epoch_time_secs()`, returning a dedicated error (e.g., `net_error::TooFrequentWrites`) and a corresponding `StackerDBErrorCodes` ack, consistent with how `max_writes` is already enforced at the same call site.

### Proof of Concept
1. Configure a StackerDB contract with a large `max_writes` (e.g., default/test config uses `u32::MAX`) and a nonzero `write_freq`.
2. As the owner of slot `N`, sign chunk version 1, POST to `/v2/stackerdb/:addr/:contract/chunks` — accepted.
3. Immediately sign and POST version 2 (no delay) — `try_replace_chunk` only checks `slot_version > slot_validation.version` and `slot_version <= max_writes`; since neither depends on wall-clock time, it succeeds despite `write_freq` supposedly requiring a cooldown, as confirmed by the absence of any `write_time`/`write_freq` comparison in [1](#0-0) .
4. Repeat rapidly up to `max_writes`; each accepted write is broadcast to all peers via `process_stacker_db_chunks`, as shown in [6](#0-5) .

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
