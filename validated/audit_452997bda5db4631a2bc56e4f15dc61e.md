**Reasoning:** The premise of a misclassification in `Nep171TokenId::from_str` does not hold up under tracing.

`TokenIdType` is not independently inferred from ambiguous string content — it is the `strum_discriminants` of the `TokenId` enum itself [1](#0-0) . Parsing always dispatches strictly on an explicit type tag before the type-specific parser ever runs: `TokenId::from_str` splits off the leading `typ` token (`nep141`/`nep171`/`nep245`/`imt`) and only then calls the corresponding sub-parser (`Nep171TokenId::from_str`, `ImtTokenId::from_str`, etc.) [2](#0-1) . There is no code path where a byte sequence produced for one variant (e.g. `imt:<minter>:<id>`) can be reinterpreted by `from_str` as a different variant (e.g. `nep171:<contract>:<id>`), because the discriminant prefix is checked first and is not attacker-controllable independent of which intent constructs the token.

Moreover, `ImtMint` never round-trips through `TokenId::from_str` on attacker-supplied data at all: it builds the token id directly as `ImtTokenId::new(minter_id, token_id)` inside `ImtTokens::into_generic_tokens`, which always yields the `TokenId::Imt` variant regardless of what the attacker puts in the `token_id` field [3](#0-2) . `Nep171TokenId::from_str` is therefore unreachable from this entrypoint — the target function cited in the question is not on the exploit path claimed.

Finally, `TokenDiff::token_fee` derives `TokenIdType` via `Into<TokenIdType>` from the already-typed `TokenId` enum discriminant, not by re-parsing a string [4](#0-3) , so the fee-exemption for NFTs/MTs with `amount <= 1` is applied to tokens that are genuinely of type `Nep171`/`Nep245`/`Imt` — this is deliberate fee policy for non-fungible-style transfers, not a type-confusion bug. Since the equality "the fee rule applied to a token == the rule for the asset class that token actually is" holds on both sides of every step in the path, there is no misclassification and no fee bypass reachable through this mechanism.
