### Title
DeleteKey + AddKey for the same public key resets nonce floor below previously consumed nonces, enabling transaction replay/double-spend - ([File: runtime/runtime/src/access_keys.rs])

### Finding Description
`add_regular_key` sets the new `AccessKey.nonce` unconditionally to `initial_nonce_value(apply_state.block_height)`, i.e. `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`: [1](#0-0) [2](#0-1) 

This floor is only derived from the current block height — it has no knowledge of, and never compares against, the highest nonce that was ever consumed for that exact public key on that account. That high-water mark lives solely inside the `AccessKey` trie row, and `delete_regular_key` unconditionally removes that row (and therefore the nonce state) when the key is deleted: [3](#0-2) 

Replay protection for transactions is otherwise enforced only by `verify_nonce` in `verifier.rs`, which compares `tx_nonce` against the access key's currently stored nonce (`Monotonic`: `tx_nonce > current_nonce`; `Strict`: `tx_nonce == current_nonce + 1`) plus an upper bound tied to `block_height * MULTIPLIER`: [4](#0-3) 

Because `action_delete_key`/`action_add_key` are ordinary actions that can be combined in one transaction and executed sequentially against the same `TrieUpdate`, an attacker who controls a FullAccess key `pk` on their own account can:

1. Sign and submit `Tx1` (e.g., a `Transfer` action) using `pk` with a nonce `N1` chosen close to the current block-height ceiling (`N1` just below `block_height * MULTIPLIER`, which is legal since the attacker fully controls the nonce). `Tx1` executes and persists `access_key.nonce = N1`.
2. In the same block window, submit `Tx2 = [DeleteKey(pk), AddKey(pk, ...)]` signed with `pk` at nonce `N2 > N1` (passes `verify_nonce` normally). Inside execution, `action_delete_key` removes the `AccessKey` row (discarding `N1`), then `action_add_key`→`add_regular_key` recreates it with `nonce = (block_height-1) * MULTIPLIER`, which is lower than `N1` as long as `pk` was previously used with `N1 > (block_height-1) * MULTIPLIER` (the stated precondition).
3. The attacker re-broadcasts the *original, already-executed* `Tx1` bytes (same nonce `N1`, same signature). It is still within the `transaction_validity_period` block-hash window enforced by `check_transaction_validity_period` (which only checks block-hash ancestry/age, not tx-hash uniqueness), and `verify_nonce` now passes because `N1 > current_nonce` (the newly-reset lower floor) and `N1 < block_height * MULTIPLIER`.
4. `Tx1` is accepted and executed a second time.

No existing check (signature validation, nonce check, `AddKeyAlreadyExists`, storage-staking, or `transaction_validity_period`) prevents this, because none of them tie the new key's nonce floor to the previous high-water mark for that specific public key — the check in `check_transaction_validity_period` only guards against transactions referencing very old blocks, not against tx-hash uniqueness or nonce state discontinuity.

### Impact Explanation
This is a double-spend/replay of a previously executed transaction (e.g., a `Transfer`, `FunctionCall` with a deposit, or `Stake` action can be re-executed), caused entirely by an unprivileged account holder's own transactions (self-inflicted key delete+re-add). This maps to the "double-spend/replay (no transaction executes twice)" invariant explicitly called out in the audit scope, and can cause direct loss of funds for whichever party is on the receiving/paying end of the replayed action (e.g., a merchant who accepted `Tx1` as a one-time payment, or the network itself if the replayed receipt burns/mints balances a second time).

### Likelihood Explanation
Preconditions are fully attacker-controlled: the attacker just needs (a) a FullAccess key on their own account, (b) to choose a nonce for the target transaction close to the current per-block nonce ceiling, and (c) to submit a `DeleteKey`+`AddKey` transaction for the same public key before the target transaction expires (`transaction_validity_period`, tens of blocks). This requires no validator/node privilege, no leaked keys, and no social engineering — only ordinary transaction submission to a public RPC endpoint. It is fully repeatable by any account holder against their own key.

### Recommendation
When re-adding a regular (or gas) access key with the same public key that was previously deleted on that account within the current validity window, the new nonce floor must never be lower than the highest nonce ever observed for that exact `(account_id, public_key)` pair. Options: persist a separate "last used nonce" high-water mark per `(account_id, public_key)` that survives key deletion for at least `transaction_validity_period` blocks and use `max(initial_nonce_value(block_height), last_known_nonce + 1)` when re-adding; or disallow re-adding a public key that was deleted within the last `transaction_validity_period` blocks.

### Proof of Concept
Unit test plan in `runtime/runtime/src/access_keys.rs` / `runtime/runtime/src/verifier.rs`:
1. Set up an account with a FullAccess key `pk`; call `add_regular_key` at `block_height = H`, then manually set the resulting `AccessKey.nonce = N1` where `N1` is close to `H * MULTIPLIER` (simulating a previously executed transaction consuming that nonce).
2. Call `action_delete_key` for `pk`, then `action_add_key` for `pk` again at the same (or nearby) `block_height`.
3. Assert that the resulting `access_key.nonce` (via `get_access_key`) is `>= N1 + 1`. This assertion should **fail** with the current code, since `add_regular_key` sets it to `(H-1) * MULTIPLIER < N1`.
4. Follow-up integration test (test-loop) demonstrating end-to-end replay: submit `Tx1` (Transfer) with nonce `N1`, submit `Tx2` (DeleteKey+AddKey for the same `pk`), then resubmit the identical signed `Tx1` bytes and assert it is accepted and the transfer amount is deducted/credited a second time — violating the "no transaction executes twice" invariant.

```rust
pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
```

```rust
fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
```

```rust
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
```
