### Title
Unhandled exception in `BlockEventLoad`'s scheduled loop permanently and silently disables the event-plugin/log-trigger pipeline - (File: `framework/src/main/java/org/tron/core/services/event/BlockEventLoad.java`)

### Summary
`BlockEventLoad` runs a `ScheduledExecutorService` task every 100ms that is solely responsible for advancing `BlockEventCache` and feeding block/transaction/contract-event triggers into `RealtimeEventService` and `SolidEventService`, which in turn drive the event-plugin log trigger pipeline consumed by JSON-RPC/websocket log & block-filter clients. Unlike its sibling services, when `load()` throws *any* `Exception`, the handler calls `close()`, which does `executor.shutdown()` — permanently stopping the periodic task for the remaining lifetime of the process, with only a single ERROR log line and no restart/self-healing mechanism.

### Finding Description
The scheduled task is defined as: [1](#0-0) 

```java
public void init() {
    executor.scheduleWithFixedDelay(() -> {
      try {
        if (!instance.isBusy()) {
          load();
        }
      } catch (Exception e) {
        close();
        logger.error("Event load service fail.", e);
      }
    }, 100, 100, TimeUnit.MILLISECONDS);
```

`close()` calls `executor.shutdown()`: [2](#0-1) 

`load()` walks block-by-block from the cached head to the current chain tip, building `BlockEvent`s and reconciling any fork/rollback: [3](#0-2) 

Any runtime exception surfacing from `blockEventGet.getBlockEvent(tmpNum)` (e.g., trigger-capsule construction failures, unexpected null fields, cache-eviction races on `BlockEventCache`, or fork/rollback edge cases in the `while (!blockEvent.getParentId().equals(tmp.getBlockId()))` walk) is caught generically and used as a trigger to permanently kill the executor. This is architecturally inconsistent with `RealtimeEventService` and `SolidEventService`, which log the same class of failure and simply let the next scheduled tick retry: [4](#0-3) [5](#0-4) 

Because `BlockEventLoad` is the single producer that advances `BlockEventCache` (the shared head pointer consumed by both downstream services), once its executor is shut down there is no other path to resume block-event ingestion — the whole log/block-trigger pipeline (feeding event plugins, and transitively any external subscriber relying on block/tx/contract-event triggers) stalls indefinitely for the remaining node uptime, only recoverable via a full node restart.

### Impact Explanation
Once triggered, this silently and permanently disables trigger delivery to any configured event plugin (Kafka/MQ/HTTP-callback), which many deployments use as their sole means to observe on-chain state for downstream services (exchanges, indexers, wallets). No new alerting occurs beyond one log line, so the failure can go unnoticed for extended periods. This matches "an API the node can no longer serve" per the CWE scope, analogous to EVerest's `TbdController` silently dying and taking its dependent SDP/ISO15118-20 servers down with it.

### Likelihood Explanation
Likelihood is moderate but not conclusively proven end-to-end: I confirmed the shutdown-on-any-exception defect in `BlockEventLoad` with exact code, but I was not able to fully trace, within the remaining tool budget, a concrete attacker-controlled transaction/contract payload that reliably makes `BlockEventGet.getBlockEvent()` throw (I did not get to read `BlockEventGet.java` or `BlockEventCache.java` before running out of iterations). The defect itself — any transient/edge-case exception (fork handling, cache eviction, malformed trigger capsule) permanently disabling the service instead of retrying like its sibling services — is a real, demonstrable root cause, but proving a single-transaction reproducible trigger requires further investigation of `BlockEventGet`/`BlockEventCache` and the trigger-capsule construction code, which I could not complete here.

### Recommendation
Change `BlockEventLoad`'s exception handler to match `RealtimeEventService`/`SolidEventService`: log the failure and let the scheduled task continue running on the next tick, rather than calling `close()`/`executor.shutdown()`. If a fatal, unrecoverable state is detected, that should be an explicit, narrowly-scoped condition (similar to `TronError`-based fatal exits) rather than the default behavior for any `Exception`.

### Proof of Concept
Not conclusively established. Based on code review only: any exception thrown from `load()` → `blockEventGet.getBlockEvent(tmpNum)` during normal block processing (e.g., a fork/rollback edge case, or a malformed/edge-case log/contract-event trigger derived from an attacker-submitted transaction that trips a `NullPointerException` or similar in trigger-capsule construction) will call `close()` and shut the `event-load` executor down forever, since the catch block at framework/src/main/java/org/tron/core/services/event/BlockEventLoad.java:43-46 unconditionally shuts down on any `Exception`. Confirming a concrete transaction payload that reaches this path requires further review of `BlockEventGet` and `BlockEventCache`, which was not completed due to iteration limits — flagged here as an open item rather than a proven PoC.

  public synchronized void load() throws Exception {
    long cacheHeadNum = BlockEventCache.getHead().getBlockId().getNum();
    long tmpNum =  manager.getDynamicPropertiesStore().getLatestBlockHeaderNumber();
    if (cacheHeadNum >= tmpNum) {
      return;
    }
    synchronized (manager) {
      tmpNum =  manager.getDynamicPropertiesStore().getLatestBlockHeaderNumber();
      if (cacheHeadNum >= tmpNum) {
        return;
      }
      if (tmpNum > cacheHeadNum + MAX_LOAD_NUM) {
        tmpNum = cacheHeadNum + MAX_LOAD_NUM;
      }
      List<BlockEvent> blockEvents = new ArrayList<>();
      List<BlockEvent> rollbackBlockEvents = new ArrayList<>();
      BlockEvent tmp = BlockEventCache.getHead();

      BlockEvent blockEvent = blockEventGet.getBlockEvent(tmpNum);
      blockEvents.add(blockEvent);
      while (!blockEvent.getParentId().equals(tmp.getBlockId())) {
        tmpNum--;
        if (tmpNum == tmp.getBlockId().getNum()) {
          rollbackBlockEvents.add(tmp);
          tmp = BlockEventCache.getBlockEvent(tmp.getParentId());
        }
        blockEvent = blockEventGet.getBlockEvent(tmpNum);
        blockEvents.add(blockEvent);
      }

      rollbackBlockEvents.forEach(e -> realtimeEventService.add(new Event(e, true)));

      List<BlockEvent> l = Lists.reverse(blockEvents);
      for (BlockEvent e: l) {
        BlockEventCache.add(e);
        realtimeEventService.add(new Event(e, false));
      }
    }
  }
