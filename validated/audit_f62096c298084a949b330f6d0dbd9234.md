Based on my research, I found a plausible analog to CVE‑2017‑1000381's "OOB read while parsing attacker-supplied protocol data" pattern in the TVM precompiled contract data-decoding routines used by `BatchValidateSign`/`ValidateMultiSign`-style precompiles.

### Title
Unchecked array index in `extractBytes32Array` allows attacker-controlled out-of-bounds array access during TVM precompiled contract call decoding - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytes32Array(DataWord[] words, int offset)` decodes a length-prefixed array from calldata supplied to certain precompiled contracts (batch signature validation family) without validating that `offset` or `offset + len` stay within the bounds of the `words` array parsed from the caller-controlled input.

### Finding Description
`extractBytes32Array` reads the array length directly from attacker-controlled calldata (`words[offset].intValueSafe()`) and then iterates `words[offset + i + 1]` for `i` in `[0, len)` with no bound check against `words.length`: [1](#0-0) 
This differs from the sibling helper `extractBytesArray`, which explicitly guards `offset > words.length - 1` before indexing: [2](#0-1) 
`words` is produced via `DataWord.parseArray(data)`, whose length is simply `data.length / WORD_SIZE`, i.e. directly determined by the size of the calldata an unprivileged caller supplies to the precompiled contract: [3](#0-2) 
Because `len` and `offset` come from attacker-supplied word values, a contract call crafted with a declared array length larger than the actual number of remaining words will cause `words[offset + i + 1]` to index past the end of the array.

### Impact Explanation
Unlike the C `c-ares` case where an OOB read silently discloses adjacent heap memory, the JVM enforces array bounds checks, so this specific defect manifests as an uncaught `ArrayIndexOutOfBoundsException` rather than a memory-disclosure primitive. The call path reaching this code is `callToPrecompiledAddress` in `Program.java`, where `contract.execute(data)` is invoked without a surrounding try/catch for arbitrary runtime exceptions at that call site: [4](#0-3) 
I was not able to fully confirm, within available context, whether the `BatchValidateSign`/`ValidateMultiSign` `execute()` methods (which call `extractBytes32Array`) wrap this decoding in their own try/catch to convert failures into a "contract call failed" result versus letting the exception propagate up through block/transaction application. This is the key open question determining whether the real-world impact is limited to "one transaction reverts/fails" (low impact, out of scope per the report's rules) or "unhandled exception during block application" (a node crash/halt, in scope).

### Likelihood Explanation
The precompiled contracts using this decoding path (`batchValidateSignAddr` / `validateMultiSignAddr`) are reachable by any account via a normal `CALL`/`STATICCALL` to the fixed precompile addresses, gated only by `VMConfig.allowTvmSolidity059()`: [5](#0-4) 
Triggering the out-of-bounds index only requires crafting calldata with an inconsistent length word, which is trivial for any transaction broadcaster or contract deployer.

### Recommendation
Add an explicit bounds check in `extractBytes32Array` mirroring the one already present in `extractBytesArray` (validate `offset < words.length` and `offset + len < words.length` before indexing), and audit `BatchValidateSign`/`ValidateMultiSign` execute paths to ensure any decoding exception is caught locally and converted into a failed precompile result rather than propagating to the VM/block-application layer.

### Proof of Concept
Because I could not verify the exact catch/propagation behavior in the calling `execute()` methods with full certainty (index size limits may have truncated some file contents), I cannot construct a concrete end-to-end PoC transaction with full confidence that it reaches an uncaught exception at block-application level rather than being caught and safely reverted. A Devin session with full repository access would be needed to inspect the complete `BatchValidateSign`/`ValidateMultiSign` `execute()` implementations and confirm whether the exception is caught, which determines whether this qualifies as a High severity node-crash issue or a lower-severity contract-call-revert issue only.
