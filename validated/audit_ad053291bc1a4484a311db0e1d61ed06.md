### Title
Unprivileged `TransferToGasKey` deposit can be front-run to block `DeleteAccount`/gas-key `DeleteKey` via `GasKeyBalanceTooHigh` - (File: runtime/runtime/src/actions.rs)

### Summary
Any account can permissionlessly top up a victim's gas key balance via `Action::TransferToGasKey`, since `check_actor_permissions` does not require `actor_id == account_id` for this action. This mirrors the DYAD bug where anyone could deposit into a victim's dNFT position to trip a "has assets" guard that blocks removal. Here, an attacker can front-run a victim's `DeleteAccount` transaction (or a `DeleteKey` targeting a gas key) by funding the target gas key just above the burn threshold, causing the deletion to permanently fail with `GasKeyBalanceTooHigh`.

### Finding Description
`action_delete_account` sums all gas-key balances on the account and rejects deletion if the total exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR): [2](#0-1) . The same guard exists in `delete_gas_key` for a single-key `DeleteKey` action: [3](#0-2) .

`action_transfer_to_gas_key` funds an existing gas key's balance and performs no ownership/actor check at all — it only requires the target key to exist and be a gas key: [4](#0-3) . Critically, `check_actor_permissions` — the function that enforces `actor_id == account_id` for privileged actions like `AddKey`, `DeleteKey`, `DeleteAccount`, `WithdrawFromGasKey`, `Stake`, `DeployContract` — explicitly exempts `Action::TransferToGasKey(_)` from any actor check, grouping it with harmless actions like `Transfer`/`FunctionCall`: [1](#0-0) . This means anyone (any predecessor account) can send a receipt containing `TransferToGasKey` targeting a victim account's public gas key, exactly as anyone can `Transfer` NEAR to any account.

An attacker who observes (in the mempool or as an in-flight receipt) that a victim is about to send `DeleteAccount` (or `DeleteKey` for a gas key) can front-run by sending `TransferToGasKey` with a deposit that pushes the gas key's cumulative balance above `MAX_BALANCE_TO_BURN` (1 NEAR). The victim's deletion receipt will then fail with `GasKeyBalanceTooHigh`, exactly like DYAD's `remove()` reverting with `VaultHasAssets` after a dust front-run deposit.

### Impact Explanation
This is a griefing/DoS vector: it permanently blocks a legitimate account-deletion (or gas-key deletion) attempt at negligible cost to the attacker (just over 1 NEAR, which is refundable to the attacker via later `WithdrawFromGasKey` — but withdrawal is actor-restricted to the account itself, so the attacker's deposited funds become locked/burned into the victim's gas key, meaning the attacker can also weaponize this at a bounded cost of just over 1 NEAR per attack). The victim cannot delete their account (freeing storage and reclaiming remaining balance) or delete the specific gas key, which is a denial-of-service against normal account lifecycle operations. This does not directly cause theft, but it can permanently freeze the account-deletion capability, and can also force the victim to lose control of when tokens are burned (since deletion sums all gas-key balances and burns them once below-threshold), or, if the attacker deposits enough, cause the burn of previously-unburned funds beyond what the victim intended, and it degrades UX/predictability of account lifecycle operations that the protocol explicitly designed to be actor-only.

### Likelihood Explanation
Likelihood is high in cases where a user has a gas key and is trying to close the account (a supported end-to-end flow, tested for instance in `test_delete_account_gas_key_balance_too_high`): [5](#0-4) . Since transactions/receipts are visible before finalization (mempool observation or chunk-production ordering), an attacker can reliably front-run with a single cheap `TransferToGasKey` action. No special permissions or races beyond normal transaction ordering are required.

### Recommendation
Do not allow arbitrary predecessors to fund another account's gas key balance. Either (a) restrict `TransferToGasKey` to `actor_id == account_id` in `check_actor_permissions` (so only the account itself can top up its own gas keys, similar to `WithdrawFromGasKey`), or (b) decouple the `DeleteAccount`/`DeleteKey` "must burn ≤ 1 NEAR" safety check from being blockable by third-party deposits, e.g. by allowing the account owner to force-burn/refuse excess gas-key balance at deletion time regardless of who funded it, with an explicit warning, mirroring the DYAD-recommended fix of letting the owner override the "has assets" check.

### Proof of Concept
1. Victim `alice` creates a gas key on her account via `AddKey` with `AccessKey::gas_key_full_access(n)` (as in `test_gas_key_burn_not_reported_on_failed_receipt`, `runtime/runtime/src/tests/apply.rs:4305`) [6](#0-5) .
2. Alice funds the gas key to just under 1 NEAR (e.g., `900 milliNEAR`) via `TransferToGasKey`, intending to `DeleteAccount` later.
3. Attacker `bob` (any unrelated account) observes Alice's pending `DeleteAccount` transaction and front-runs it by sending his own `TransferToGasKey` action targeting `alice`'s gas key public key with a deposit of `>= 101 milliNEAR`, pushing the total above `MAX_BALANCE_TO_BURN` (1 NEAR) — permitted because `action_transfer_to_gas_key` performs no actor check [4](#0-3) .
4. Alice's `DeleteAccount` action now executes `action_delete_account`, computes `gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN`, and fails with `GasKeyBalanceTooHigh`, leaving Alice's account undeleted [2](#0-1) , analogous to the `test_delete_account_gas_key_balance_too_high` test scenario that demonstrates this exact failure path [5](#0-4) .

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) => (),
    };
    Ok(())

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
