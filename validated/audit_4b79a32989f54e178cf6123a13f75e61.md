## Finding: HTTP API connection-slot exhaustion via slow request bodies (slowloris-style) on `HttpService`

### Title
Unauthenticated slowloris-style DoS against the wallet HTTP API via unbounded connection idle time - (File: `framework/src/main/java/org/tron/common/application/HttpService.java`)

### Summary
The Traefik advisory (GHSA-8g85-whqh-cr2f) describes a slowloris-class DoS: a fixed, generous time window granted to a client for completing a request (the 50s ACME HTTPChallenge window) lets an attacker hold connections open cheaply and starve the service. java-tron's HTTP API layer (`HttpService`, used by `FullNodeHttpApiService`, `SolidityNodeHttpApiService`, and the PBFT HTTP service) has an analogous structural weakness: it caps the *number* of concurrent connections but does not bound how long an individual connection may sit idle/slow while sending its request.

### Finding Description
`HttpService.initServer()` builds the Jetty server and only wires a total-connection cap: [1](#0-0) 

```
protected void initServer() {
    this.apiServer = new Server(this.port);
    int maxHttpConnectNumber = Args.getInstance().getMaxHttpConnectNumber();
    if (maxHttpConnectNumber > 0) {
      this.apiServer.addBean(new ConnectionLimit(maxHttpConnectNumber, this.apiServer));
    }
    this.apiServer.setErrorHandler(new OversizedRequestErrorHandler());
}
```

`node.maxHttpConnectNumber` defaults to only 50 (`maxHttpConnectNumber = 50`), configured in `common/src/main/resources/reference.conf` [2](#0-1) . `SizeLimitHandler` only bounds total body *size*, not the *rate* at which bytes arrive, so a client can legally open a connection, send headers/body one byte at a time, and hold the socket open far past any reasonable request duration: [3](#0-2) 

Unlike the gRPC path, which explicitly configures `maxConnectionIdleInMillis` on the Netty server builder (`RpcService.initServerBuilder()`), no analogous idle-timeout or minimum-data-rate handler is configured for the Jetty HTTP listener: [4](#0-3) 

Because `ConnectionLimit` only rejects *new* connections once the cap of 50 is reached and never evicts slow/idle ones, an anonymous remote client only needs to open ~50 concurrent TCP connections to `node.http.fullNodePort` (8090), `solidityPort` (8091), or `PBFTPort` (8092) and trickle bytes slowly on each (e.g., a POST to `/wallet/broadcasttransaction` with a large declared `Content-Length` sent one byte every few seconds) to permanently occupy every available HTTP connection slot. Every subsequent legitimate `Wallet`/`WalletSolidity` HTTP JSON API caller (account queries, transaction broadcast, etc.) is refused with no route to recovery until the attacker's connections are closed or the process is restarted.

### Impact Explanation
This denies service to the node's public wallet HTTP API (`/wallet/*` endpoints used by exchanges, wallets, and dApps) with a handful of low-bandwidth sockets — a classic CWE-400/CWE-772 resource-exhaustion DoS, matching the CVSS `AV:N/AC:H/.../A:H` profile of the referenced advisory. It does not by itself corrupt consensus or leak keys, but it can render a node's HTTP query/broadcast path unusable, which is explicitly in-scope ("an API the node can no longer serve").

### Likelihood Explanation
Likelihood is moderate-to-high: no authentication, signature, or special privilege is required — any anonymous TCP client that can reach the configured HTTP port(s) can mount this. The default connection cap (50) is small, making exhaustion cheap. The `AC:H` rating in the original advisory reflects that the attacker needs to sustain many slow connections simultaneously, which is exactly the constraint here.

### Recommendation
Configure an explicit idle/read timeout (and ideally a minimum-data-rate handler, e.g. Jetty's `MinimumDataRateHandler` or setting `HttpConfiguration#setIdleTimeout`) on the connectors created in `HttpService.initServer()`, similar to how `RpcService` already bounds gRPC connection idle time via `maxConnectionIdleInMillis`. Make the timeout configurable via `node.http` (e.g. `node.http.idleTimeoutInMillis`) with a safe default (a few seconds to tens of seconds), and ensure slow/stalled connections are actively closed rather than only capping the connection count.

### Proof of Concept
1. Start a FullNode with default config (`maxHttpConnectNumber = 50`, no HTTP idle timeout).
2. From an attacker host, open 50 TCP connections to port 8090, sending `POST /wallet/broadcasttransaction HTTP/1.1` headers with `Content-Length: 4000000` but only writing a few bytes of body every 5-10 seconds on each connection (classic slowloris technique).
3. Attempt a normal `curl http://<node>:8090/wallet/getnowblock` from a legitimate client — the request hangs/fails because `ConnectionLimit` has already reached `maxHttpConnectNumber` and Jetty has no idle timeout to reclaim the attacker's stalled connections.
