### Title
`try_bond_funds` in nomination-pools credits the full requested stake regardless of the amount actually received by the pool account - ([File: substrate/frame/nomination-pools/src/adapter.rs])

### Summary
`pallet-nomination-pools`' legacy `TransferStake` adapter transfers a member's stake into the pool's bonded account and then bonds it with `pallet-staking`, using the *requested* `amount` parameter for both the points issuance and the `Staking::bond`/`bond_extra` call — never the value actually returned by the transfer. This is structurally identical to the ZNS `stakeForDomain()` bug: the ledger (`BondedPool::points`, `TotalValueLocked`, `StakingLedger::total`) records the requested amount rather than the amount that actually landed in the custodial (pool) account, so if `T::Currency`'s `transfer` can deliver less than requested (fee-on-transfer/deflationary semantics), the pool's recorded stake permanently exceeds its real backing, and later withdrawals become insolvent for the last member(s) to exit.

### Finding Description
`TransferStake::pledge_bond` in `substrate/frame/nomination-pools/src/adapter.rs`: [1](#0-0) 
performs:
```
T::Currency::transfer(&who.0, &pool_account.0, amount, Preservation::Expendable)?;
Staking::bond(&pool_account.0, amount, &reward_account)
```
The return value of `transfer` (the *actual* amount moved, per the `fungible::Mutate::transfer` contract which explicitly documents "Returns the actual amount placed into `dest`" — see `substrate/frame/support/src/traits/tokens/fungible/regular.rs:317-338` and `substrate/frame/support/src/traits/tokens/fungibles/regular.rs:363-386`) is discarded. Instead, the caller `BondedPool::try_bond_funds` (`substrate/frame/nomination-pools/src/lib.rs:1315-1337`) issues pool points and bumps `TotalValueLocked` using the same `amount` that was requested, before even calling `pledge_bond`:
```
let points_issued = self.issue(amount);
T::StakeAdapter::pledge_bond(..., amount, ty)?;
TotalValueLocked::<T>::mutate(|tvl| tvl.saturating_accrue(amount));
```
`Staking::bond`/`bond_extra` are then also called with the full `amount`, so `StakingLedger::total`/`active` (`substrate/frame/staking/src/lib.rs:495-507`) is inflated by the same nominal amount as well.

Under the `fungible::Mutate::transfer` default implementation, `decrease_balance`/`increase_balance` use `Precision::BestEffort` on the destination side (`substrate/frame/support/src/traits/tokens/fungible/regular.rs:333-338`), so any implementation of `T::Currency` whose `increase_balance` legitimately delivers less than requested (e.g. a fee-on-transfer or rebasing fungible wrapper, which the trait's own API explicitly anticipates by returning "actual amount transferred") silently under-funds the pool account while the pool's internal accounting (`points`, `TotalValueLocked`, and the staking ledger `total`/`active`) is credited for the full nominal `amount`. `pallet-nomination-pools` bounds `T::Currency` generically as a `fungible::Mutate`-like trait (not concretely pinned to `pallet_balances`, which has no fee-on-transfer semantics), so a runtime that configures pools with any other fungible implementation exposing the standard trait but with non-1:1 transfer semantics reproduces exactly the ZNS-class bug: recorded stake > actual reserve.

There is a maintainer-added integrity check (`substrate/frame/nomination-pools/src/lib.rs:4097-4127`) comparing `total_balance` vs `bonded_balance + sum_unbonding_balance` per pool, but it only logs a warning (`log!(warn, ...)`) — it does not revert, block dispatch, or otherwise stop insolvent withdrawals, so it is not an effective guard against the corrupted-state path.

### Impact Explanation
If the pool's real balance falls short of its recorded bonded/points total, the pool ledger overstates backing funds. Subsequent members calling `unbond`/`withdraw_unbonded` (`substrate/frame/nomination-pools/src/lib.rs:2395-2559`) compute `balance_to_unbond` from `sub_pools`/`points` bookkeeping and only clamp against `T::StakeAdapter::transferable_balance` (line 2493-2496), which reflects the pool account's *actual* free balance at withdrawal time — meaning early withdrawers can drain the shortfall onto later members, some of whom will receive less than their recorded entitlement or nothing at all once the account is exhausted (a hard user-fund loss / lock analogous to the "insolvency issue during unstaking" described in the ZNS report).

### Likelihood Explanation
This requires a runtime configuration where `pallet-nomination-pools::Config::Currency` is bound to something other than the standard native `pallet_balances` (which has no fee/rebasing behavior and thus is not exploitable) — e.g. a custom or third-party `fungible::Mutate` implementation with non-conservative transfer semantics wired into `T::Currency`. `TransferStake` is explicitly marked `#[deprecated = "consider migrating to DelegateStake"]` but remains present, compiled, and usable by any runtime that has not migrated. No malicious relayer/validator/governance action is needed — an ordinary unprivileged member calling the public `join`/`bond_extra` extrinsics against such a runtime configuration triggers the mismatch. I could not fully verify within available tool budget whether any current in-repo runtime (e.g. Kusama/Polkadot/Westend/AssetHub) actually configures `pallet-nomination-pools::Currency` to a non-native, fee/rebasing-capable fungible; if all shipped runtimes pin it strictly to `pallet_balances`, the practical likelihood in currently-deployed configurations is low, though the code path itself is a generic latent trust-the-parameter bug in the pallet's accounting logic.

### Recommendation
In `TransferStake::pledge_bond` (and any other adapter calling `T::Currency::transfer`), capture the `Result<Balance, _>` returned by `transfer` and use that *actual* transferred amount — not the requested `amount` — for `Staking::bond`/`bond_extra`. Correspondingly, in `BondedPool::try_bond_funds` (`substrate/frame/nomination-pools/src/lib.rs:1315-1337`), issue points and accrue `TotalValueLocked` based on the amount actually pledged/bonded (returned from `pledge_bond`) rather than the amount requested by the caller, so the pool's internal accounting can never exceed what is truly held. Additionally, promote the periodic solvency check at `substrate/frame/nomination-pools/src/lib.rs:4097-4127` from a warning log into an enforced invariant (e.g. reject `join`/`bond_extra` or fail try-state checks) if a strict accounting mismatch is detected.

### Proof of Concept
1. Configure a test runtime's `pallet_nomination_pools::Config::Currency` with a `fungible::Mutate` implementation that delivers, say, 99% of the requested amount on `transfer` (simulating a fee-on-transfer/deflationary token), while still returning `Ok(actual_amount)` per the trait contract.
2. Member A calls `Pools::join(amount = 1000, pool_id)`. `try_bond_funds` issues `points_issued` for the full 1000 and calls `pledge_bond`, which internally calls `T::Currency::transfer(A, pool_account, 1000, Expendable)`, but only 990 actually lands in `pool_account`; `Staking::bond(pool_account, 1000, ...)` is still called with 1000.
3. `TotalValueLocked`, `BondedPool::points`, and `StakingLedger::total/active` for the pool now reflect 1000, while the pool account's real spendable/stakable balance is 990.
4. Have a second member B join with additional real funds, then have A `unbond`/`withdraw_unbonded` fully — A receives their full nominal share computed from points, drawing down real balance beyond the actual 990 contributed, at the expense of B's share; when B later attempts to withdraw, `transferable_balance` clamps their payout below their recorded entitlement, demonstrating the insolvency. 	fn try_bond_funds(
		&mut self,
		who: &T::AccountId,
		amount: BalanceOf<T>,
		ty: BondType,
	) -> Result<BalanceOf<T>, DispatchError> {
		// We must calculate the points issued *before* we bond who's funds, else points:balance
		// ratio will be wrong.
		let points_issued = self.issue(amount);

		T::StakeAdapter::pledge_bond(
			Member::from(who.clone()),
			Pool::from(self.bonded_account()),
			&self.reward_account(),
			amount,
			ty,
		)?;
		TotalValueLocked::<T>::mutate(|tvl| {
			tvl.saturating_accrue(amount);
		});

		Ok(points_issued)
	}

	///
	/// A transfer where the source and destination account are identical is treated as No-OP after

	fn transfer(
		source: &AccountId,
		dest: &AccountId,
		amount: Self::Balance,
		preservation: Preservation,
	) -> Result<Self::Balance, DispatchError> {
		let _extra = Self::can_withdraw(source, amount).into_result(preservation != Expendable)?;
		Self::can_deposit(dest, amount, Extant).into_result()?;
		if source == dest {
			return Ok(amount);
		}

		Self::decrease_balance(source, amount, BestEffort, preservation, Polite)?;
		// This should never fail as we checked `can_deposit` earlier. But we do a best-effort
		// anyway.
		let _ = Self::increase_balance(dest, amount, BestEffort);
		Self::done_transfer(source, dest, amount);
		Ok(amount)
