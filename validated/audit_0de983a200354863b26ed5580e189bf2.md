## Analysis

The Splits report's core broken invariant is: **a privileged state value (`owner`) can be changed, externally observed by a party that trusts it, and reverted back — all within one atomic execution, so the external party's state-dependent decision is based on transient, spoofable state.**

The closest local, provable analog in this repository is in `pallet-contracts` (and the analogous PVM path in `pallet-revive`), where a smart contract can rewrite its **own `code_hash`** mid-execution via the `set_code_hash` host function, call out to another contract that inspects the caller's identity/behavior, and then have that change revert (or be swapped again) within the same call stack — before the transaction is even done. This is explicitly acknowledged as intended/known behavior in the host-function docs, but it is exactly the "spoof-then-revert" primitive from the Splits report, applied to any protocol that trusts a contract's `code_hash`/behavior as a state check (e.g., a registry verifying a callee is a specific, "safe" implementation before granting a permission, allowance, or payout).

`Ext::set_code_hash` mutates `ContractInfo::code_hash` for the currently executing frame with no restriction on how many times it can be toggled within a single call, and no atomic "lock" preventing it from being flipped, observed by a nested external call, and flipped back: [1](#0-0) 

The host function documentation itself states the exact TOCTOU primitive: a contract can call into itself after changing its code so the nested call uses new code, and if the caller reverts afterward, the change is undone and the next caller sees the old code: [2](#0-1) 

A minimal fixture already demonstrates the raw capability (self code-hash swap mid-call): [3](#0-2) 

And the existing test confirms that after `set_code_hash`, subsequent calls to the *same address* execute the *new* code within the same block/session, i.e., identity/behavior at a fixed address is not stable across nested calls: [4](#0-3) 

### Title
Contract self `code_hash` mutation permits spoofing identity/behavior checks by external protocols within a single atomic call - (File: substrate/frame/contracts/src/exec.rs)

### Summary
`pallet-contracts`'s `set_code_hash` host function lets a contract rewrite its own `ContractInfo::code_hash` at will, with no cooldown, no "one-shot per transaction" restriction, and no atomicity guard against toggling it multiple times inside one call stack. Exactly like the Splits `execCalls()`/`transferOwnership()` pattern, an attacker-controlled contract can (1) swap to a "trusted"/benign code hash, (2) trigger an external protocol's identity/behavior check that trusts the code hash at that address, and (3) swap back to the original (malicious) code hash — all before the top-level transaction returns, so any interacting protocol that reads `code_hash` (or dispatches into the contract expecting specific, "verified" behavior) as a security invariant is deceived.

### Finding Description
Any external pallet or contract that treats a callee's `code_hash` (or the behavior exhibited when calling into it) as a trust anchor — e.g., "this address is running audited/whitelisted code X" — can be defeated because:
- `set_code_hash` mutates `frame.contract_info().code_hash` in place with no restriction on repeated invocation within one call: [5](#0-4) 
- The change takes effect for the *very next* nested call on the same call stack, as literally documented: [6](#0-5) 
- The same mechanism can be exercised repeatedly (swap to code A, call out, swap back to code B) before the outer extrinsic completes, since nothing in `set_code_hash` prevents multiple mutations per call stack, mirroring `execCalls()`'s ability to call `transferOwnership()` multiple times in one transaction because the passed check is not re-verified per step.

This is the same broken invariant as the Splits bug: a state value that a third party treats as authoritative (`owner`/`code_hash`) is mutable by the very party being checked, inside the scope of the same atomic operation the checker is relying on, and reversible before the transaction concludes.

### Impact Explanation
Any Substrate-based chain deploying `pallet-contracts` (or the PVM equivalent in `pallet-revive`) alongside another pallet/contract that gates value transfer, minting, whitelisting, or permissioning on a callee's `code_hash`/observed behavior is exposed to false-state acceptance: the verifier records a decision (e.g., registers the contract as "immutable"/"audited", grants an allowance, or credits a reward) based on a code identity that no longer holds once the transaction returns. This falls under "forged or mis-bound proof or state acceptance" and "runtime bugs that compromise intended behavior" in the impact gate, since it lets an unprivileged contract deployer manufacture a false acceptance of contract state without any admin, governance, or relayer involvement.

### Likelihood Explanation
The primitive requires only deploying an ordinary contract that calls `set_code_hash` before and after invoking another party's registration/verification entrypoint — no privileged role, validator, or off-chain actor is needed, matching the "public-entrypoint, unprivileged attacker" requirement. The behavior is already demonstrated to work as designed in the existing test suite (`set_code_hash` test), confirming reachability; exploitation depends only on a second protocol choosing to trust `code_hash` as an invariant, which is a realistic and encouraged integration pattern (analogous to Splits' own documented risk that "interacting protocols" trust ownership/immutability).

### Recommendation
Document explicitly (as the host function doc already partially does) that `code_hash` must never be treated as a stable trust anchor across a nested call boundary by external protocols, and/or introduce a per-transaction "lock" on `set_code_hash` (e.g., allow at most one net mutation per top-level extrinsic, or require code hash to remain stable for the duration of any call initiated to an external, un-trusted contract), similar to how the Splits fix re-checks ownership before every action rather than relying on a single upfront check.

### Proof of Concept
1. Deploy `ContractX` at address `A` with malicious code `M`.
2. `ContractX::call()` does:
   a. `set_code_hash(trusted_hash_T)` — `A` now reports/executes as trusted code `T`.
   b. Calls `Registry::register(A)`, which performs `ensure(CodeHashOf::get(A) == trusted_hash_T)` (or dispatches into `A` and observes benign behavior), and grants a permission/payout keyed to `A`.
   c. `set_code_hash(malicious_hash_M)` — reverts `A`'s code back to `M`.
3. The top-level extrinsic succeeds; `Registry` has now permanently recorded `A` as trusted, while `A` executes malicious code `M` for all future calls. [7](#0-6)

	fn set_code_hash(&mut self, hash: CodeHash<Self::T>) -> DispatchResult {
		let frame = top_frame_mut!(self);
		if !E::from_storage(hash, &mut frame.nested_gas)?.is_deterministic() {
			return Err(<Error<T>>::Indeterministic.into());
		}

		let info = frame.contract_info();

		let prev_hash = info.code_hash;
		info.code_hash = hash;

		let code_info = CodeInfoOf::<T>::get(hash).ok_or(Error::<T>::CodeNotFound)?;

		let old_base_deposit = info.storage_base_deposit();
		let new_base_deposit = info.update_base_deposit(&code_info);
		let deposit = StorageDeposit::Charge(new_base_deposit)
			.saturating_sub(&StorageDeposit::Charge(old_base_deposit));

		frame.nested_storage.charge_deposit(frame.account_id.clone(), deposit);

		Self::increment_refcount(hash)?;
		Self::decrement_refcount(prev_hash);
		Contracts::<Self::T>::deposit_event(Event::ContractCodeUpdated {
			contract: frame.account_id.clone(),
			new_code_hash: hash,
			old_code_hash: prev_hash,
		});
		Ok(())
	}
