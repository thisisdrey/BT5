### Title
`DepositToken.deposit` does not check whether the position is still liquidatable after adding collateral - (contracts/DepositToken.sol)

### Summary
Same bug class as the Unstoppable `add_margin` finding: Metronome's `DepositToken.deposit` lets a user (or anyone, via `onBehalfOf_`) add collateral to an already-unhealthy account, but it never verifies that the resulting position is healthy / non-liquidatable. If the added collateral is insufficient to push `debtInUsd <= issuableLimitInUsd`, the position remains liquidatable and the freshly deposited collateral can be seized by a liquidator in the very next transaction. Notably, `SmartFarmingManager.leverage` does perform exactly this health check at the end (`PositionIsNotHealthy`), but the standalone deposit path omits it.

### Finding Description
`deposit` pulls the underlying into the Treasury, mints `msdTOKEN` to `onBehalfOf_`, and returns — with no call to `pool.debtPositionOf` and no health assertion.

`contracts/DepositToken.sol:211-237`:
```solidity
function deposit(
    uint256 amount_,
    address onBehalfOf_
) external override whenNotPaused nonReentrant onlyIfDepositTokenExists returns (uint256 _deposited, uint256 _fee) {
    ...
    _underlying.safeTransferFrom(_msgSender, _treasury, amount_);
    ...
    _mint(onBehalfOf_, _deposited);
    emit CollateralDeposited(_msgSender, onBehalfOf_, amount_, _deposited, _fee);
}
```

Compare with `SmartFarmingManager.leverage`, which reverts unless the final position is healthy (`contracts/SmartFarmingManager.sol:206-208`):
```solidity
(bool _isHealthy, , , , ) = pool.debtPositionOf(_msgSender);
if (!_isHealthy) revert PositionIsNotHealthy();
```

A position is liquidatable whenever `debtInUsd > issuableLimitInUsd` (`Pool.debtPositionOf`, `contracts/Pool.sol:264`), and `Pool.liquidate` seizes collateral — including the newly deposited amount — from any unhealthy account with a `liquidatorIncentive` bonus (`contracts/Pool.sol:559-593`).

### Impact Explanation
A user whose position has become unhealthy (e.g., after a collateral price drop) deposits additional collateral intending to save it. If the deposit is insufficient to restore health, the position is still liquidatable; a liquidator immediately calls `Pool.liquidate`, seizing collateral at a discount-plus-incentive. The user loses the extra collateral they just added — direct loss of user funds caused by the missing post-deposit health check, identical in effect to the audited finding.

### Likelihood Explanation
Requires the victim's position to already be unhealthy and the victim to deposit a too-small amount — a user-error-driven scenario, hence medium/low likelihood. There is also a griefing vector: `deposit` accepts an arbitrary `onBehalfOf_`, so collateral can be pushed into a third party's unhealthy account, though the economic harm still lands on the depositor. No privileged role, no oracle manipulation, and no special conditions are needed to reach the code path; only `whenNotPaused` applies, and liquidation is not paused-blocked (the test suite even asserts liquidation works while paused).

### Recommendation
After minting the deposit tokens, verify the beneficiary's position is no longer liquidatable, mirroring the check in `SmartFarmingManager.leverage`:

```solidity
(bool _isHealthy, , , , ) = _pool.debtPositionOf(onBehalfOf_);
if (!_isHealthy) revert PositionIsNotHealthy();
```
