### Title
Deposit into `FundingManager`-analog tokenized vaults can mint zero `zft` shares while collateral is taken from the depositor - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The Inverter `FundingManager` report shows that Bancor-style share-math can round `issuance`/`collateral` output to zero on `buy`/`sell`, letting a user pay in value and receive nothing back. The Zest v2 tokenized vaults implement an analogous ERC4626-like `deposit`/`redeem` pair whose share math is a plain integer division (`mul-div-down`). Unlike `redeem`, `deposit` does not guard against a zero-share mint result, so the identical rounding-to-zero failure mode is reachable by any ordinary depositor.

### Finding Description
Each vault (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) computes shares to mint via `convert-to-shares-preview`, which performs `mul-div-down amount ts ta` — a floor division: [1](#0-0) 

The floor-division helper itself: [2](#0-1) 

In `deposit`, the computed `inkind` (shares to mint) is checked only against `min-out` (an attacker/caller-supplied slippage bound that defaults to `u0` for a naive integrator or a user who doesn't set it), never against `u0` directly: [3](#0-2) 

By contrast, `redeem` explicitly guards against a zero output with `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`: [4](#0-3) 

Because `total-assets-preview` grows over time from accrued interest while `total-supply-preview` (outstanding `zft`) stays fixed absent new deposits, `ta` can become large relative to `ts` — mainly on vaults where the underlying token has few decimals (e.g. `sbtc`, 8 decimals) or after a long low-turnover accrual period. Once `ta / ts` exceeds `amount`, `mul-div-down amount ts ta` rounds to `0`. A `deposit` call with such an `amount` and `min-out u0` then:
1. Transfers the depositor's full `amount` of underlying into the vault via `receive-underlying`,
2. Mints `0` `zft` to the recipient,
3. Increases `assets` by the full deposited `amount`, silently socializing the deposited value to all existing shareholders.

This is the direct analog of the reported issue: the bonding-curve/share formula returns zero output for the depositor while their input is still consumed.

### Impact Explanation
The depositor's underlying tokens are irrecoverably absorbed into the vault's `assets` accounting with no shares minted to reclaim them — this is a permanent loss of the deposited principal for that specific user (their funds are not "unclaimed yield," they are principal at rest that becomes redeemable only by other existing shareholders). This lands in the **Critical** impact bucket (permanent freezing/loss of user principal funds) if the amount lost is meaningful, or at minimum **High** if characterized narrowly as freezing of the deposited value for that specific depositor, since the tokens are not lost to the protocol but redistributed away from the depositor with no recourse.

### Likelihood Explanation
Likelihood is limited by two factors: (a) it requires the attacker/victim to omit the `min-out` slippage protection (pass `u0`), and (b) it requires the `ta/ts` ratio to be large enough relative to the deposited `amount`, which is more plausible on low-decimal underlying assets (e.g. `sbtc` at 8 decimals) or vaults that have accrued substantial interest with low share turnover. This is a realistic, self-triggerable scenario (an ordinary user calling `deposit` with a small `amount` and default `min-out`) but is not always exploitable — it depends on vault state at call time.

### Recommendation
Add a zero-output guard to `deposit` mirroring the one already present in `redeem`:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the other `asserts!` checks in `deposit`, in each of the six vault contracts (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`).

### Proof of Concept
1. Let a vault reach a state where `total-assets-preview()` (`ta`) is large relative to `total-supply-preview()` (`ts`), e.g. via accrued interest over time with a small existing `zft` supply.
2. A user calls `deposit(amount, min-out: u0, recipient: user)` with `amount` small enough that `mul-div-down(amount, ts, ta) == 0`. [5](#0-4) 
3. `receive-underlying(amount, account)` pulls the user's `amount` of underlying into the vault.
4. `(try! (ft-mint? zft inkind recipient))` mints `0` shares (`inkind = u0`).
5. `assets` is incremented by `amount`, permanently crediting the deposited value to the vault's existing shareholders instead of the depositor, who received `0` `zft` for their transferred tokens.
