## Title
Missing slippage / maximum-amount protection in `ExchangeInjectContract` allows users to accidentally inject more of the paired token than intended - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectContract`/`ExchangeInjectActuator` lets a user add liquidity to a bancor-style token pair exchange by specifying only the `quant` of one token; the amount of the *other* token that is simultaneously debited from the user's account (`anotherTokenQuant`) is computed from the **live pool ratio at execution time**, not at submission time. Unlike `ExchangeTransactionContract`, which carries an `expected` field to bound the unfavorable-price risk, `ExchangeInjectContract` has no equivalent cap/minimum/maximum field, so a user has no way to limit how much of the second token they end up paying if the pool ratio shifts between broadcast and block inclusion.

### Finding Description
`ExchangeInjectContract` is defined with only four fields — no cap on the derived amount: [1](#0-0) 

In `ExchangeInjectActuator.execute`, `anotherTokenQuant` is derived purely from the exchange pool's current balances (`firstTokenBalance`/`secondTokenBalance`) and the user-supplied `tokenQuant`, then immediately deducted from the user's asset/TRX balance: [2](#0-1) 

`doValidate()` recomputes the same ratio-based `anotherTokenQuant` at validation time and only checks that the account has enough balance to cover it and that pool balance limits aren't exceeded — there is no user-specified bound comparing the computed `anotherTokenQuant` to what the user actually intended to spend: [3](#0-2) 

Contrast this with `ExchangeTransactionActuator`, which protects the trader with a user-supplied `expected` minimum-received amount, explicitly validated against the computed output: [4](#0-3) 

Because the pool ratio can change between the time a user signs/broadcasts an `ExchangeInjectContract` transaction and the time it is packed into a block (e.g., due to intervening `ExchangeTransactionContract` trades or other `ExchangeInjectContract`/`ExchangeWithdrawContract` operations on the same pair), the actual `anotherTokenQuant` debited at execution can be materially higher than what the user calculated/expected when constructing the transaction — with no on-chain mechanism to reject execution if that derived amount exceeds an acceptable threshold.

### Impact Explanation
A user submitting an `ExchangeInjectContract` transaction can be forced to contribute significantly more of the second token (TRX or TRC10 asset) than they intended, based on pool price movement they cannot control, with the deficit going to the exchange pool (and thus benefiting other participants who can later withdraw at the manipulated ratio). This constitutes an unintended/unauthorized transfer of value away from the transaction sender, directly matching the reported bug class of "user can accidentally send more than intended, with no price cap," and can be amplified by an attacker deliberately shifting the pool ratio (front-running) immediately before the victim's inject transaction lands.

### Likelihood Explanation
Any account holding TRX or the relevant TRC10 asset can broadcast an `ExchangeInjectContract` transaction; no special privilege is required. The exchange pool ratio is trivially manipulable by any other account performing a same-pair `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` in an earlier position within the same or a preceding block, making the scenario readily reachable by an ordinary user or an opportunistic attacker.

### Recommendation
Add a user-supplied bound to `ExchangeInjectContract` (e.g., `max_expected_another_quant` or `min_another_quant`, mirroring the `expected` field pattern already used in `ExchangeTransactionContract`), and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` so the transaction fails rather than silently debiting more than the caller intended.

### Proof of Concept
1. Attacker and victim both hold balances of TokenA/TokenB in an `ExchangeInjectContract`-eligible pool with pool ratio R0.
2. Victim signs and broadcasts `ExchangeInjectContract{tokenId=TokenA, quant=Q}`, expecting to also pay `anotherTokenQuant ≈ Q * R0` of TokenB.
3. Before the victim's transaction is packed, the attacker executes an `ExchangeTransactionContract` (or another `ExchangeInjectContract`) against the same pool, shifting the ratio to R1 (R1 >> R0).
4. The victim's transaction executes against R1: `ExchangeInjectActuator.execute()` computes `anotherTokenQuant = floorDiv(secondTokenBalance * tokenQuant, firstTokenBalance)` using the new (attacker-manipulated) balances, debiting far more TokenB from the victim than expected, with no validation rejecting this outcome.
