### Title
Single-step, unconfirmed change of account Owner/Active/Witness permission keys can permanently freeze account funds - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` lets any account replace its `Owner`, `Active`, and (if a witness) `Witness` permission key sets in a single broadcast transaction, with no two-step "propose then confirm-from-new-key" mechanism. If the new key set is entered incorrectly (wrong address, unreachable/unowned key, or a threshold that can never be met by the submitter), the account permanently loses the ability to sign future transactions, exactly mirroring the reported floatcapital pattern where a single-step admin/treasury address change can lock out funds and contract functionality.

### Finding Description
`validate()` in `AccountPermissionUpdateActuator` only checks structural validity of the submitted permissions (key count bounds, address format via `DecodeUtil.addressValid`, weight/threshold arithmetic, and allowed operation bits), not that the submitter retains control after the change: [1](#0-0) 

`execute()` then applies the new `Owner`/`Witness`/`Active` permissions immediately and atomically, overwriting the previous keys with no pending/confirmation step from the new key holder: [2](#0-1) 

This is the direct analog of the external report: both change a critical "control" address (contract admin/treasury vs. on-chain account permission/owner keys) in one signed operation without requiring the new address/key to counter-sign or confirm receipt of control. If an unprivileged user submits an `AccountPermissionUpdateContract` with a malformed, unreachable, or otherwise wrong `Owner` key (or a threshold unsatisfiable by the keys actually controlled by the sender), the account's TRX, TRC10, and TRC10/TRC20-linked contract-call abilities become permanently unusable, since no further transaction can ever satisfy the new owner permission.

### Impact Explanation
Unlike a simple typo in an off-chain admin field, this affects an on-chain account's cryptographic control over all its assets and future actuator calls (transfers, freezes/votes, contract invocation, etc.). A malformed or mis-specified permission update is unrecoverable — there is no rollback, pending-owner staging area, or requirement that the new owner key sign an acceptance transaction — so all funds and TRC10 assets held by that account become permanently frozen. This matches the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Any account holder with `AllowMultiSign` enabled can trigger this by broadcasting a single `AccountPermissionUpdateContract` transaction; no special privilege beyond normal account signing is required to reach the vulnerable code path in `AccountPermissionUpdateActuator.execute()`. The class of bug (fat-fingered/incorrect address in a single-shot ownership/permission change) is exactly the scenario the original report flags, and here it is not merely a UX inconvenience but a chain-enforced, irreversible loss of account control.

### Recommendation
Introduce a two-step confirmation flow for permission/ownership-changing operations analogous to `Ownable2Step`: stage the requested `Owner`/`Active`/`Witness` permission set (e.g., a `pendingPermission` field on `AccountCapsule`), and only commit it once a transaction signed under the *new* permission set explicitly accepts/confirms the change within the same or a subsequent transaction. Alternatively/additionally, validate in `AccountPermissionUpdateActuator.validate()` that the submitting key(s) fully satisfy the newly proposed `Owner` permission's threshold before allowing the update to execute, preventing self-inflicted permanent lockouts.

### Proof of Concept
1. Account `A` (with balance and TRC10 tokens) broadcasts `AccountPermissionUpdateContract` setting `Owner` permission to a single key `K` with weight 1 and threshold 1, where `K` is an address `A` does not actually hold the private key for (typo/wrong copy-paste), or setting the threshold higher than any combination of controlled keys can satisfy.
2. `AccountPermissionUpdateActuator.validate()` passes because it only checks the syntactic constraints shown in lines 71-146; it never verifies that the sender can still authorize future transactions.
3. `AccountPermissionUpdateActuator.execute()` (lines 43-59) commits the new `Owner` permission to `AccountCapsule` immediately.
4. From this point, no transaction sent from account `A` can ever be validated against signature/permission checks, permanently freezing all TRX/TRC10 balances and blocking any further contract interactions from `A`.

  private boolean checkPermission(Permission permission) throws ContractValidateException {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (permission.getKeysCount() > dynamicStore.getTotalSignNum()) {
      throw new ContractValidateException("number of keys in permission should not be greater "
          + "than " + dynamicStore.getTotalSignNum());
    }
    if (permission.getKeysCount() == 0) {
      throw new ContractValidateException("key's count should be greater than 0");
    }
    if (permission.getType() == PermissionType.Witness && permission.getKeysCount() != 1) {
      throw new ContractValidateException("Witness permission's key count should be 1");
    }
    if (permission.getThreshold() <= 0) {
      throw new ContractValidateException("permission's threshold should be greater than 0");
    }
    String name = permission.getPermissionName();
    if (!StringUtils.isEmpty(name) && name.length() > 32) {
      throw new ContractValidateException("permission's name is too long");
    }
    //check owner name ?
    if (permission.getParentId() != 0) {
      throw new ContractValidateException("permission's parent should be owner");
    }

    long weightSum = 0;
    List<ByteString> addressList = permission.getKeysList()
        .stream()
        .map(x -> x.getAddress())
        .distinct()
        .collect(toList());
    if (addressList.size() != permission.getKeysList().size()) {
      throw new ContractValidateException(
          "address should be distinct in permission " + permission.getType());
    }
    for (Key key : permission.getKeysList()) {
      if (!DecodeUtil.addressValid(key.getAddress().toByteArray())) {
        throw new ContractValidateException("key is not a validate address");
      }
      if (key.getWeight() <= 0) {
        throw new ContractValidateException("key's weight should be greater than 0");
      }
      try {
        weightSum = addExact(weightSum, key.getWeight());
      } catch (ArithmeticException e) {
        throw new ContractValidateException(e.getMessage());
      }
    }
    if (weightSum < permission.getThreshold()) {
      throw new ContractValidateException(
          "sum of all key's weight should not be less than threshold in permission " + permission
              .getType());
    }
