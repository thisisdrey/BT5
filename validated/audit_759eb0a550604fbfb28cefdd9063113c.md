## Title
Enabled extension can drain the wallet's own NEAR balance via unrestricted `NearAction::Transfer` in `Request.external` - ([File: contracts/wallet/src/contract.rs])

## Summary
`w_execute_extension` authorizes any `Request` submitted by a `predecessor_account_id` that is a member of `self.0.extensions`, with no per-action or per-amount scoping. `execute_request` -> `build_promise` allows `NearAction::Transfer` to any non-self `receiver_id`, and `Promise::transfer` in the NEAR runtime is always funded from the contract account's own balance, not from `env::attached_deposit()`. A compromised or malicious enabled extension can therefore submit `Transfer(wallet_balance)` to an attacker-controlled `receiver_id` and drain the wallet's real NEAR balance, which may include funds unwrapped/withdrawn from the Verifier.

## Finding Description
The broken binding: `value transferred via NearAction::Transfer to receiver_id == value the owner's signature authorized for that specific receiver/amount`. In practice the code only enforces `extension ∈ self.0.extensions` (membership), not amount/receiver-scoped owner authorization: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

`execute_extension` only checks `check_extension_enabled`, a boolean membership check, before calling `execute_request`, which iterates `request.external` and calls `build_promise(promise).detach()` for each. `build_promise` explicitly allows `NearAction::Transfer` (along with `FunctionCall` and `DeterministicStateInit`) to any receiver other than the wallet itself. On NEAR, `Promise::transfer(amount)` is funded from the calling contract's own account balance at execution time — it is unrelated to `env::attached_deposit()` supplied on the incoming `w_execute_extension` call. Consequently, once an extension is enabled (e.g., a relayer, trusted for some narrower purpose such as gas-sponsored intent submission), that extension can submit `Request { external: [NearPromise { receiver_id: attacker.near, actions: [NearAction::Transfer(wallet.balance)] }] }` and the wallet will schedule and detach a transfer of its full balance to the attacker, with no additional owner signature, no per-action allowlist tied to the extension's granted scope, and no amount cap.

The `Request.external` promises are not restricted to be funded by, or capped at, the caller-supplied deposit; they draw on the wallet contract account's actual NEAR balance. This is a real divergence from the "owner signature required to move funds" model used elsewhere in the wallet (`w_execute_signed` requires `S::verify_request_msg` signature verification before `execute_request` is called), whereas `w_execute_extension` reaches the exact same `execute_request` → `build_promise` path guarded only by extension-set membership.

## Impact Explanation
Any NEAR balance held by the wallet contract account — including balance resulting from withdrawing/unwrapping Verifier-custodied assets to native NEAR — can be transferred out to an attacker-chosen `receiver_id` with no owner signature, only extension trust. This matches the Critical severity category: "tokens moved... without the owner's valid signature or authorisation." The attack is repeatable for every enabled extension and for the full balance in a single call; blast radius is the entire NEAR balance of any wallet that has enabled a since-compromised or overly-broadly-trusted extension.

## Likelihood Explanation
Requires: (1) the wallet owner has enabled an extension (`WalletOp::AddExtension`) — a legitimate action the owner may take for functionality such as relayer support; (2) that extension account becomes malicious or is compromised, or was scoped by convention only (not enforced in code) to narrower operations; (3) the wallet holds a NEAR balance. None of these require DAO/role-holder privileges or key compromise of the owner — only compromise/misbehavior of an extension the owner already trusted with *some* capability, which the contract does not scope. Given the interface docs describe extensions generically (e.g., relayers) without documenting a restriction to `internal` ops or a cap on `external` promises, this is a realistic and low-cost attack path for any account that becomes an enabled extension.

## Recommendation
Scope extension authorization at the action level: either (a) disallow `NearAction::Transfer` (and other value-moving actions) from extension-submitted `Request.external` entirely, requiring signed (`w_execute_signed`) authorization for any native balance movement, or (b) introduce a per-extension allowlist/cap of permitted actions, receivers, and amounts that must be established via owner signature when the extension is added, and enforce it in `build_promise`/`execute_extension` in addition to the current `check_extension_enabled` membership check.

    fn execute_request(&mut self, request: Request, actor: &Actor<'_>) -> Result<()> {
        for op in request.internal {
            self.execute_op(op, actor.as_ref())?;
        }

        for promise in request.external {
            Self::build_promise(promise)?.detach();
        }

        Ok(())
    }

    fn build_promise(p: NearPromise) -> Result<Promise> {
        // check for no self-calls
        if p.receiver_id == env::current_account_id() {
            return Err(Error::SelfCallsNotAllowed);
        }

        // check for no unsupported actions
        if !p.actions.iter().all(|a| {
            matches!(
                a,
                NearAction::FunctionCall(_)
                    | NearAction::Transfer(_)
                    | NearAction::DeterministicStateInit(_)
            )
        }) {
            // There is no support for other actions, since they operate on
            // the account itself (e.g. `DeployContract`, `AddKey` and
            // etc...) or on its subaccounts (e.g. `CreateAccount`).
            // Wallet-contracts are not self-upgradable and do not allow
            // creating subaccounts.
            return Err(Error::UnsupportedPromiseAction);
        }

        Ok(p.build())
    }
