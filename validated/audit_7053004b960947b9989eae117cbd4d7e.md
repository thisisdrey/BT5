## Title
Relayer reward is paid unconditionally on `submit_delivery_receipt` without checking the delivery `success` flag - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`Pallet::process_delivery_receipt` settles a `PendingOrder` and pays the relayer the full pre-committed `order.fee` based only on verifying `receipt.gateway` matches `T::GatewayAddress` and that a `PendingOrder` exists for `receipt.nonce`, never inspecting `receipt.success`. The `DeliveryReceipt` type carries a `success: bool` field decoded directly from the Ethereum `InboundMessageDispatched` event, but this field is structurally unused in the payout path, meaning a message whose commands failed/reverted on Ethereum still results in full reward payout and permanent removal of the order.

## Finding Description
When a message is enqueued via `do_process_message`, a `PendingOrder { nonce, fee, block_number }` is stored keyed by nonce, where `fee` is the amount reserved to pay for delivery/execution: [1](#0-0) 

The `DeliveryReceipt` struct, produced by decoding the Ethereum `InboundMessageDispatched` event log, explicitly carries a `success` field alongside `gateway`, `nonce`, `topic`, and `reward_address`: [2](#0-1)  and is populated straight from the decoded event: [3](#0-2) 

In `process_delivery_receipt`, only `receipt.gateway` is checked against `T::GatewayAddress`, and the `PendingOrder` is looked up by `receipt.nonce`; the function then unconditionally pays `order.fee` to `reward_account` via `T::RewardPayment::register_reward` and unconditionally removes the `PendingOrder`, with `receipt.success` never read anywhere in the function: [4](#0-3) 

The module-level documentation confirms this is the intended (and flawed) design: "Fetch the pending order by nonce of the message, pay reward with fee attached in the order" and "Remove the order," with no conditional branch on execution outcome: [5](#0-4) 

The only existing guard demonstrated in tests (`poc_m1`) blocks payout solely while the light-client verifier reports the bridge as globally halted — it does not gate payout on the per-message `success` outcome: [6](#0-5) . This is corroborated by every emulated integration test constructing `DeliveryReceipt { success: true, ... }` and asserting the reward is registered, e.g. [7](#0-6)  — none of these tests (or the pallet code) exercise or gate on `success == false`.

## Impact Explanation
Settlement (fee payout + `PendingOrders` removal) advances purely on proof-of-inclusion of an Ethereum event log for the correct gateway/nonce, without verifying that the message's commands actually executed successfully on Ethereum. A message whose on-chain commands revert or fail (out-of-gas, failed token transfer, malformed command dispatch) but which still emits a valid `InboundMessageDispatched` log with `success = false` will still cause the relayer to be paid the full `order.fee` and the `PendingOrder` to be permanently deleted, precluding any retry, refund, or reconciliation. This is a duplicate/unwarranted payout of value the user reserved specifically to guarantee successful delivery and execution, matching the required-impact category of payout/settlement state advancing without gating on actual execution success (`Message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically`).

## Likelihood Explanation
`submit_delivery_receipt` is a public, permissionless extrinsic reachable by any account holding a valid Ethereum receipt/event proof; no privileged actor, compromised relayer, or malicious governance action is required — an honest relayer submitting proof of a legitimately-occurring but failed Ethereum execution triggers the bug. The `success` field exists in the decoded type specifically to communicate this outcome, yet is structurally dead code in the payout path, indicating the intended invariant (pay only on successful execution) was not implemented.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` with the full `order.fee` when `receipt.success == true`. When `receipt.success == false`, either withhold/reduce the reward (paying only a delivery-only portion if the fee model separates delivery cost from execution reward) or otherwise settle deterministically instead of paying the full fee, while still removing/resolving the `PendingOrder` to avoid gridlock. Add unit tests asserting no (or reduced) reward is registered when `receipt.success == false`, mirroring the existing `poc_m1` halted-verifier test pattern.

## Proof of Concept
1. A message is enqueued through `do_process_message`, inserting `PendingOrders[nonce] = { fee: F, ... }` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` L426-436).
2. On Ethereum, the Gateway processes the message but command execution fails, emitting a valid `InboundMessageDispatched` log with `success = false` for that `nonce`.
3. A relayer submits `submit_delivery_receipt(origin, event_proof)` with a genuine proof of this log.
4. `process_delivery_receipt` is invoked with `receipt.success == false`; it checks only `receipt.gateway` and the existence of `PendingOrders::get(nonce)`, both of which pass, then calls `T::RewardPayment::register_reward(&reward_account, ..., order.fee)` and `<PendingOrders<T>>::remove(nonce)` (L445-480).
5. Result: the relayer is paid `F` despite the message's on-chain effects failing, and the `PendingOrder` is irrecoverably removed — reproducible by constructing a test analogous to `poc_m1` but with a `DeliveryReceipt` where `success: false`, asserting the reward is nonetheless registered under current code.
