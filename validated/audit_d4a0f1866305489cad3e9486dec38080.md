## Title
Missing check for the "null" (all-zero) address allows locking funds via `TransferContract`, `TransferAssetContract` and related actuators - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`)

### Summary
Multiple java-tron actuators that move TRX or TRC10 assets to a `to_address` (or equivalent) validate the address only via `DecodeUtil.addressValid()`, which checks address length and prefix byte, but never rejects the "null"/all-zero-body address (`0x41` followed by 20 zero bytes) — the direct analog of Solidity's `address(0)`. As with the reported `GSPFunding.buyShares` issue, a user can accidentally (or be tricked into) send funds to this well-known "empty" address, which nobody can produce a private key for, permanently locking the assets.

### Finding Description
`DecodeUtil.addressValid()` only verifies:
1. The address is non-empty and exactly 21 bytes.
2. The first byte matches `addressPreFixByte` (`0x41` on mainnet). [1](#0-0) 

It performs no check that the remaining 20 bytes are non-zero, i.e. it does not reject the "null address" analog of `address(0)`.

This helper is the sole address-format guard used by the transfer-related actuators:

- `TransferActuator.validate()` calls `DecodeUtil.addressValid(toAddress)` and only additionally checks `toAddress != ownerAddress`, with no zero-address check, before crediting the destination and (if it doesn't exist) auto-creating the account. [2](#0-1) 
Execution then unconditionally creates the destination account and transfers value to it: [3](#0-2) 

- `TransferAssetActuator.validate()` has the identical pattern for TRC10 transfers. [4](#0-3) 

- `ParticipateAssetIssueActuator.validate()` applies the same `addressValid` check to `toAddress` with no zero-address exclusion. [5](#0-4) 

- `ShieldedTransferActuator.validateTransparent()` validates the transparent `toAddress` the same way. [6](#0-5) 

- `VMUtils.validateForSmartContract()` (used by TVM-triggered TRX/TRC10 internal transfers) uses the same `addressValid` check for the `toAddress`. [7](#0-6) 

None of these paths compare the address body against the all-zero value, unlike the deliberate, purpose-built "Blackhole" address that java-tron uses for burning fees — that is a specific, known address configured in genesis/config, not the zero address. [8](#0-7) 

Because the address format check only validates length/prefix, a transaction broadcaster can set `to_address` to `0x41` + 20 zero bytes. This passes `addressValid`, is not equal to the owner address, and the transfer proceeds — creating a brand-new zero-body account and crediting it with TRX/TRC10 that is effectively unspendable (no known preimage produces this pubkey hash).

### Impact Explanation
Funds (TRX or TRC10 tokens) sent to the all-zero address become permanently locked, since the probability of any actor holding a private key that hashes to the all-zero 20-byte value is negligible. This is a real, on-chain, irreversible loss of user funds triggered by a single, ordinary signed transaction — matching the "permanent freezing of funds" impact criterion.

### Likelihood Explanation
This can be triggered by any unprivileged user/wallet/client that constructs a `TransferContract`, `TransferAssetContract`, `ParticipateAssetIssueContract`, `ShieldedTransferContract`, or TVM-triggered internal transfer with an uninitialized/default (all-zero) destination address — a common class of bug in client-side code that leaves a default/zero-initialized address field unset before signing and broadcasting, exactly as described in the original report for `buyShares(to=address(0))`.

### Recommendation
Add an explicit check in `DecodeUtil.addressValid()` (or in each actuator's `validate()`), rejecting the address whose 20-byte body (bytes 1..20) are all zero, in addition to the existing length/prefix checks, mirroring the common `require(to != address(0))` pattern used in Solidity contracts.

### Proof of Concept
1. Build a `TransferContract` (or `TransferAssetContract`) with `owner_address` = a valid funded account and `to_address` = `Hex("41" + "00"*20)` (21 bytes, correct mainnet prefix `0x41`, all-zero body).
2. Sign and broadcast the transaction.
3. `TransferActuator.validate()` passes: `DecodeUtil.addressValid(toAddress)` returns `true` (length 21, prefix `0x41`), and `Arrays.equals(toAddress, ownerAddress)` is `false`. [9](#0-8) 
4. `TransferActuator.execute()` creates a new `AccountCapsule` for the zero-body address and credits it with the transferred amount. [3](#0-2) 
5. The TRX (or TRC10) balance now resides at an address with no realistically discoverable private key, permanently locking the funds.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
