### Title
Reftable binary parser trusts embedded offset/length fields without bounds validation, causing out-of-range slice panics - (File: `internal/git/reftable/reftable.go`)

### Summary

### Finding Description
The bug class in the external report is: a parser trusts length/offset fields embedded in untrusted binary data and uses them to slice a buffer without first validating that the resulting range is within the buffer's actual bounds, producing incorrect behavior (or a crash) instead of a clean, validated error.

`internal/git/reftable/reftable.go` implements a hand-rolled binary parser for Git's reftable format. Several functions extract length/count/offset fields directly from the byte buffer and use them to index the same buffer without checking that the derived indices stay inside the buffer:

- `getVarInt` advances `start` based on continuation bits read from `src[start]` and only checks `start > blockEnd`, i.e. it can still read one byte past `blockEnd` before erroring, and `blockEnd`/`blockStart` themselves are not validated against `len(src)`: [1](#0-0) 
- `getRefsFromBlock` computes `refname := prefix[:prefixLength] + string(src[idx:idx+suffixLength])` where `prefixLength` and `suffixLength` come straight from `getVarInt` with no check that `prefixLength <= len(prefix)` or `idx+suffixLength <= len(src)`: [2](#0-1) 
- The same function slices `src[idx : idx+uint(hashSize)]` for regular/peeled references and `src[idx : idx+size]` for symrefs without re-validating against the block/table bounds: [3](#0-2) 
- `parseRefBlock` computes `b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)` using unsigned arithmetic; if `RestartCount` is larger than expected for the actual block length, this subtraction can underflow (wrap around on `uint`), producing a huge `RestartStart` that drives the `for idx < b.RestartStart` loop in `getRefsFromBlock` far past the real data: [4](#0-3) 

Because none of these code paths bounds-check the derived offsets/lengths against `len(src)` before slicing, any corruption or malformation of a `.ref` table file (e.g., truncation, or a byte flip in the restart-count/varint fields) causes Go's runtime to panic with "slice bounds out of range" instead of the parser returning a validated error, exactly analogous to `BytesUtils.compare` returning bogus results/crashing on out-of-range `offset`/`len` because those weren't validated against the buffer length.

### Impact Explanation
`GetReferences()` (which calls `parseRefBlock`/`getRefsFromBlock`) and `stageTables` (via `reftable.ParseTable`) are invoked by Gitaly's write-ahead-log transaction machinery when resequencing/staging reftables written during ordinary ref-update transactions, e.g. `internal/gitaly/storage/storagemgr/partition/reftable.go` `stageTables`: [5](#0-4)  and `preparePackRefsReftable` during housekeeping/pack-refs compaction: [6](#0-5) . A panic here would abort the transaction/handler goroutine that reads a corrupted or truncated reftable, causing a denial of service on that RPC/transaction path (and potentially a stuck/aborted housekeeping run) rather than a clean, structured error.

### Likelihood Explanation
Reftable files are normally produced by Git's own trusted reftable writer during legitimate ref updates, so a well-formed, non-corrupted table is expected in normal operation. Triggering the panic therefore requires an already-corrupted or truncated `.ref` file (e.g., disk-level corruption, an interrupted/partial write being read prematurely, or a filesystem race), not attacker-controlled bytes flowing directly and deterministically from a single ordinary push. This makes the likelihood **low-to-moderate**: the parser itself has a genuine, in-repo confirmed bounds-checking gap that is architecturally identical to the reported bug class, but reaching it from a single unprivileged RPC call without also assuming file corruption or a race condition is not clearly demonstrated by the available code paths.

### Recommendation
- In `getVarInt`, validate `start < blockEnd` (not `start > blockEnd`) before reading `src[start]`, and validate `blockStart`/`blockEnd` against `len(src)` before any read.
- In `getRefsFromBlock`, before slicing, check `prefixLength <= len(prefix)`, `idx+suffixLength <= len(src)`, `idx+hashSize <= len(src)`, and `idx+size <= len(src)`, returning a descriptive parse error instead of relying on Go's automatic panic.
- In `parseRefBlock`, verify `currentBS >= 2+3*uint(b.RestartCount)` before computing `RestartStart`, to avoid unsigned-integer underflow.
- Add fuzz tests (similar to the existing `object_info_reader_fuzz.go`) targeting `ParseTable`/`GetReferences` with truncated/corrupted reftable byte sequences to catch these panics before they reach production I/O paths.

### Proof of Concept
Not independently reproduced against a running Gitaly instance in this analysis; the finding is based on static review of the parsing logic and its documented callers. Reproducing the panic would require: constructing a `.ref` table with a valid header/footer/CRC but a manipulated `RestartCount` or varint continuation-bit sequence that causes `idx+suffixLength` (or `RestartStart`) to exceed `len(src)`, placing it where `reftable.ReadTablesList`/`ParseTable` would read it (e.g., by directly writing into a test repository's `reftable/` directory), and then invoking a code path that calls `GetReferences()` or `stageTables` (e.g., a WAL transaction commit or `git pack-refs --auto` housekeeping run) to trigger the panic. This step was not executed here since it requires filesystem/tool access outside the scope of this read-only code review.

// getVarInt parses a variable int and increases the index.
func (t *Table) getVarInt(src []byte, start uint, blockEnd uint) (uint, uint, error) {
	var val uint

	val = uint(src[start]) & 0x7f

	for (uint(src[start]) & 0x80) > 0 {
		start++
		if start > blockEnd {
			return 0, 0, fmt.Errorf("exceeded block length")
		}

		val = ((val + 1) << 7) | (uint(src[start]) & 0x7f)
	}

	return start + 1, val, nil
}

// parseRefBlock parses a block and if it is a ref block, provides
// all the reference updates.
func (t *Table) parseRefBlock(src []byte, headerOffset, blockStart, blockEnd uint) ([]git.Reference, error) {
	currentBS := t.extractBlockLen(src, blockStart+headerOffset)

	fullBlockSize := t.blockSize
	if fullBlockSize == 0 {
		fullBlockSize = currentBS
	} else if currentBS < fullBlockSize && currentBS < (blockEnd-blockStart) && src[blockStart+currentBS] != 0 {
		fullBlockSize = currentBS
	}

	b := &block{
		BlockStart:    blockStart + headerOffset,
		FullBlockSize: fullBlockSize,
	}

	if err := binary.Read(bytes.NewBuffer(src[blockStart+currentBS-2:]), binary.BigEndian, &b.RestartCount); err != nil {
		return nil, fmt.Errorf("reading restart count: %w", err)
	}

	b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)

	return t.getRefsFromBlock(src, b)
}
