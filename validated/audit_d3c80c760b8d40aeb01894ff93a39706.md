## Title
Users can retain and continue earning full witness‑vote rewards after delegating away the underlying TRON Power via `DelegateResourceActuator`, because votes/reward are never reconciled - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`)

### Summary
`DelegateResourceActuator.execute()` reduces the owner's own frozen (self-owned) TRON Power balance when delegating BANDWIDTH/ENERGY resource to another account, but unlike every other actuator that changes an account's TRON Power (`UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `VoteWitnessActuator`, `WithdrawBalanceActuator`), it never calls `MortgageService.withdrawReward()` and never re-validates/shrinks the account's existing `votes` list against the now-reduced TRON Power.

### Finding Description
Across the reward/voting subsystem, the invariant enforced everywhere else is: whenever an account's usable TRON Power can decrease, the code must (1) settle/snapshot the pending reward via `mortgageService.withdrawReward(ownerAddress)` and (2) shrink `accountCapsule`'s votes so that total votes never exceed the new TRON Power. This is explicitly implemented in:
- `UnfreezeBalanceActuator.execute()` calls `mortgageService.withdrawReward(ownerAddress)` before adjusting frozen balance/votes. [1](#0-0) 
- `UnfreezeBalanceV2Actuator.execute()` does the same and additionally calls `updateVote()` to proportionally shrink votes when TRON Power falls below total votes. [2](#0-1) [3](#0-2) 
- `VoteWitnessActuator.countVoteAccount()` also calls `mortgageService.withdrawReward(ownerAddress)` before votes are replaced. [4](#0-3) 

`DelegateResourceActuator.execute()`, however, decreases the owner's `FrozenBalanceForBandwidthV2`/`FrozenBalanceForEnergyV2` (i.e. the owner's self-backed TRON Power, since `addFrozenBalanceForBandwidthV2(-delegateBalance)` / `addFrozenBalanceForEnergyV2(-delegateBalance)` are called) without touching the `votes` list and without calling `withdrawReward`: [5](#0-4) 

Its `validate()` method only checks that the delegated balance does not exceed the *available* FreezeV2 balance (net of bandwidth/energy usage); it never checks whether the account's existing `votes` list total exceeds the account's TRON Power after the delegation: [6](#0-5) 

Consequently, an account can: freeze TRX, vote for witnesses with the full TRON Power, then delegate that same frozen balance away to another account via `DelegateResourceContract`. After delegation, the account's actual TRON Power backing its votes is reduced (or effectively zero, since the frozen balance backing votes has moved to `DelegatedFrozenV2Balance`), yet the `votes` list in `AccountCapsule`/`VotesStore` is left unchanged. `MortgageService.withdrawReward()` computes rewards purely from the stored `votesList` snapshot and the witness Vi (value-per-vote) delta between cycles, independent of whether the account currently has TRON Power to back those votes: [7](#0-6) 

This is the same root-cause pattern described in the reference report: an operation that removes/reduces the underlying stake is not reconciled with the reward/accounting state (`updateReward`/`withdrawReward`), letting the actor keep earning rewards on capital that no longer backs those rewards. Here it additionally lets a single account earn double: once via delegating the resource for bandwidth/energy usage benefit to the receiver, and simultaneously continuing to receive full witness voting rewards for a stake it no longer solely owns.

### Impact Explanation
Reward payouts to SRs are funded from a shared pool proportional to `Vi` per witness (`delegationStore.getWitnessVi`), computed from the total votes recorded for that witness across all voters. If an account can keep uncorrected inflated votes recorded while having delegated away the TRON Power backing them, it continues to draw a share of the reward pool disproportionate to its real backing stake, diluting/misallocating rewards owed to other voters and effectively creating unbacked reward allowance credited to `AccountCapsule.allowance`, which is directly withdrawable to TRX balance via `WithdrawBalanceActuator`/`WithdrawRewardProcessor`. This is a fund-theft/incorrect-accounting issue reachable by any account holder issuing ordinary `FreezeBalanceV2Contract` → `VoteWitnessContract` → `DelegateResourceContract` transactions.

### Likelihood Explanation
The sequence (freeze → vote → delegate the same frozen balance) is a normal, unprivileged transaction flow available to any account and requires no special permission beyond `supportDR()`/`supportUnfreezeDelay()` being enabled (both are standard mainnet chain parameters). No error is raised by `validate()` for this sequence, making it trivially and repeatedly reachable.

### Recommendation
Before mutating an owner's self-frozen TRON Power in `DelegateResourceActuator.execute()`, call `mortgageService.withdrawReward(ownerAddress)` to snapshot/settle pending reward under the pre-delegation vote state, and add logic mirroring `UnfreezeBalanceV2Actuator.updateVote()` to proportionally shrink/clear the owner's `votes`/`VotesCapsule.newVotes` whenever total votes exceed the account's post-delegation TRON Power.

### Proof of Concept
1. Account A freezes X TRX via `FreezeBalanceV2Contract` (BANDWIDTH), gaining TRON Power X.
2. Account A votes for witness W with X TRON Power via `VoteWitnessContract` — `VoteWitnessActuator.countVoteAccount()` withdraws any prior reward and stores `votes = [W: X]`. [8](#0-7) 
3. Account A issues `DelegateResourceContract` delegating X (BANDWIDTH) to Account B. `DelegateResourceActuator.execute()` reduces A's `FrozenBalanceForBandwidthV2` by X and moves it to `DelegatedFrozenV2BalanceForBandwidth`, but leaves `votes = [W: X]` untouched and does not call `withdrawReward`. [9](#0-8) 
4. Over subsequent maintenance cycles, `MortgageService.computeReward()` continues to compute A's reward share using the stale `votes = [W: X]` and witness Vi deltas, crediting A's `allowance` as if A still had X TRON Power backing the vote. [7](#0-6) 
5. Account A withdraws the accrued `allowance` via `WithdrawBalanceContract`, realizing rewards for TRON Power it no longer solely holds/backs.

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
