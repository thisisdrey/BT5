### Title
Signature malleability lets a single key be counted twice in the `ValidateMultiSign` TVM precompile, bypassing the multisig weight threshold - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE-2023-4258 bug class is "a value that is supposed to be bound/attested once through a trusted process is instead accepted again through an untrusted channel, defeating the security property it was meant to enforce." The closest reachable analog in java-tron is the duplicate-signature detection logic inside the `ValidateMultiSign` TVM precompile: it is supposed to guarantee that the accumulated weight only reflects *distinct* authorized keys, but its de-duplication check can be bypassed with a second, malleable encoding of the same ECDSA signature from the same key, letting that single key's weight be added to the total more than once.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute` iterates over attacker-supplied signatures, recovers an address per signature, and is meant to skip a signature if the same signer already contributed: [1](#0-0) 

The dedup check only truly skips when the exact byte-for-byte `merge(recoveredAddr, sign)` value was already seen (`ByteArray.matrixContains(executedSignList, sign)`). If the address was already seen but the byte content of the composite is different, the code merely calls a CPU-time throttle (`MUtil.checkCPUTime()`) and then **falls through to add the weight again** for that same `recoveredAddr`.

Because `recoverAddrBySign` accepts any signature whose components pass `ECDSASignature.validateComponents`, and that validation only restricts `v` to `27`/`28` and `r`/`s` to `[1, SECP256K1N)` — it does **not** enforce the canonical low-S rule: [2](#0-1) 

This means for any valid ECDSA signature `(r, s, v)` produced by a key, the classic malleable counterpart `(r, n-s, v')` is also accepted by `validateComponents` and, since `signatureToAddress`/`recoverPubBytesFromSignature` recovers the same address for both forms, `recoverAddrBySign` returns the identical `recoveredAddr` for two byte-distinct signature blobs of the same key over the same hash: [3](#0-2) 

Supplying both the original and the malleable-flipped signature of one authorized key therefore causes `totalWeight` to be incremented twice for a single real signer, since the composite `sign` bytes differ and the "already fully seen" check (`matrixContains(executedSignList, sign)`) fails to trigger the `continue`.

### Impact Explanation
`ValidateMultiSign` is a public TVM precompile (`0x0...16`-style address exposed to any contract call) intended to let smart contracts implement on-chain multisig gating (e.g., custody/vault contracts that release funds only when a threshold of independent keys approve). By exploiting the malleability gap, an attacker controlling as few as `ceil(threshold/weight)` distinct real keys can synthesize enough duplicate-but-differently-encoded signatures from those same keys to satisfy `totalWeight >= permission.getThreshold()` without the number of distinct authorized signers actually required. Any contract logic (or wallet/dApp) relying on this precompile's boolean result to authorize a fund transfer, withdrawal, or privileged action can be tricked into approving an operation that should have required more independent signers — leading to unauthorized account operation / theft of funds custodied behind that multisig check.

### Likelihood Explanation
The precompile is directly callable by any address from an ordinary (unprivileged) smart contract or `TriggerSmartContract` transaction — no special permission is needed to invoke it. Producing the malleable signature variant is a standard, well-known ECDSA operation (flip `s` to `n - s`, flip recovery parity) requiring no private key knowledge beyond what is already used to produce the first, legitimate signature. The transaction-level `TransactionCapsule.checkWeight` path used for consensus-level multisig validation additionally normalizes duplicates by recovered address for post-fork versions, but that fix was not applied to this `ValidateMultiSign` precompile path.

### Recommendation
In `ValidateMultiSign.execute`, deduplicate strictly by `recoveredAddr` (as `TransactionCapsule.checkWeight` does), not by the composite `merge(recoveredAddr, sign)` bytes: once an address has contributed weight, any further signature recovering to that same address must be skipped entirely, regardless of its byte encoding. Additionally, consider enforcing canonical (low-S) signature form in `ECDSASignature.validateComponents`/`recoverAddrBySign` to close the underlying malleability at the crypto layer.

### Proof of Concept
1. Deploy/call a contract that invokes the `validatemultisign(address,uint256,bytes32,bytes[])` precompile against an account whose `Active` permission has threshold `T` composed of keys with weights that individually are `< T` (e.g., one key with weight `T/2`, requiring at least 2 distinct signers by design).
2. Sign the challenge hash once with the single available key to get `sig1 = (r, s, v)`.
3. Compute the malleable counterpart `sig2 = (r, n - s, v')` (standard secp256k1 transform); `sig2` still passes `ECDSASignature.validateComponents` and recovers to the same address.
4. Submit `signatures = [sig1, sig2]` to the precompile.
5. In `execute`, iteration 1 adds `weight` for the address and records `merge(addr, sig1)`. Iteration 2: `matrixContains(executedSignList, recoveredAddr)` is true, but `matrixContains(executedSignList, merge(addr, sig2))` is false (different bytes), so it does not `continue`; it proceeds to add `weight` a second time.
6. `totalWeight` now equals `2 * weight`, meeting/exceeding `threshold` with only one real signer, and the precompile returns `true`/`dataOne()` — the threshold check is bypassed.
