### Title
Unauthenticated `RecvError` Packets Allow Remote Tunnel Teardown via UDP Source-Address Spoofing - (File: `outside.go`)

### Summary
`Interface.handleRecvError` processes the plaintext, unauthenticated `header.RecvError` message type before any certificate or HMAC/AEAD verification is performed, and its only defense against a forged sender is comparing the packet's UDP source address against the value cached in `hostinfo.GetRemote()`. Because UDP source addresses are trivially spoofable and are not covered by any Noise/AEAD authentication tag on this control message, an attacker with no CA-signed certificate can forge this single value and tear down an already-established, authenticated tunnel between two legitimate peers.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` packets straight to `f.handleRecvError` immediately after header parsing, ahead of the "verify and send `recvError` if necessary" section that normally requires an existing `hostinfo`/`ConnectionState`: [1](#0-0) 

`handleRecvError` itself performs only two checks: a config gate (`acceptRecvErrorConfig`) and a plain address-equality comparison against the cached remote endpoint, with no cryptographic proof that the sender possesses the tunnel's session keys or a certificate signed by the CA: [2](#0-1) 

If the comparison passes (i.e., the attacker forges a source `netip.AddrPort` that currently matches `hostinfo.GetRemote()`), the code unconditionally calls `f.closeTunnel(hostinfo)` and deletes the pending handshake state, immediately tearing down a fully authenticated, encrypted tunnel between two legitimate hosts. The CHANGELOG documents this as a known, intentionally-accepted tradeoff (config option `listen.send_recv_error`, described as something that "speeds up re-handshaking" at the cost of exposing/abusing this signal): [3](#0-2) 

This mirrors the reported bug class: a state-changing action ("collect/settle" analog = tear down the tunnel) is reachable by anyone without holding the equivalent of a valid credential (a CA-signed certificate), and the one guard rail present (source-IP match instead of a real min-amount / cryptographic check) is a known, documented, but still exploitable weak control — exactly like the hardcoded `amountOutMin = 0` in the original report being "intentional" yet 100% exploitable because the caller of `collectFees()` is unauthenticated.

### Impact Explanation
An attacker who can spoof UDP packets with a source address matching one side's current remote endpoint (which is often predictable — static hosts, lighthouse-known addresses, or simply the well-known public IP of one peer) can force `closeTunnel` on the receiving side without ever completing a handshake or holding a valid certificate. This is a remote state-poisoning / denial-of-service primitive against established, authenticated tunnels reachable purely from unauthenticated packet delivery to the UDP listener.

### Likelihood Explanation
Exploitation only requires: (1) knowledge of one endpoint's remote address (readily learnable from lighthouse queries, static_host_map, or passive observation of traffic to/from the target), and (2) the ability to send a spoofed-source UDP packet reaching the target's listener (feasible on many networks that don't perform strict egress/ingress filtering, and trivially feasible for an on-path or off-path attacker who can spoof UDP source addresses). No CA-signed certificate or completed handshake is required, and the check that exists (source-address match) is exactly the kind of weak, spoofable control called out as insufficient in the referenced report.

### Recommendation
Do not act on `RecvError` based solely on a spoofable UDP source-address match. Bind acceptance of `RecvError` to something an unauthenticated attacker cannot forge — e.g., require it to arrive from the exact index/endpoint pair while also rate-limiting/ignoring `RecvError` from endpoints that have not completed a fresh authenticated round-trip (as already partially mitigated by `acceptRecvErrorConfig`/`recvErrorPrivate`), or drop `RecvError`-driven teardown entirely in favor of relying on connection-manager dead-tunnel detection, consistent with the CHANGELOG's #1459 change ("Disable sending `recv_error` messages when a packet is received outside the allowable counter window").

### Proof of Concept
1. Establish a legitimate tunnel between host A and host B (valid CA-signed certs, completed Noise handshake).
2. As an attacker with no certificate, observe or infer B's current remote `netip.AddrPort` as known by A (e.g., via lighthouse queries or passive observation).
3. Craft a raw UDP packet with header type `header.RecvError`, `RemoteIndex` set to A's local index for the B tunnel (learnable from traffic analysis or brute-forced, since indexes are 32-bit), and a spoofed source address equal to B's current remote endpoint, then send it to A's listener port.
4. `handleRecvError` finds the hostinfo via `QueryReverseIndex`, sees `hr == addr`, and calls `f.closeTunnel(hostinfo)`, tearing down the tunnel — reproducing the effect seen in `e2e/tunnels_test.go`'s `TestCloseTunnelAuthenticated` bogus-close-tunnel scenario but via the unauthenticated `RecvError` path instead of `CloseTunnel`.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
