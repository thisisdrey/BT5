## Title
Praefect reference-transaction lock leaked and never released on `Renew` failure - (File: `internal/praefect/transactions/manager.go`)

### Summary
In Gitaly's Praefect serialized-writes feature, a repository-scoped write lock acquired during the `PREPARING_PHASE` of a reference-transaction vote is supposed to be released by a deferred call whenever the transaction fails or completes. However, when the lock-renewal step for `PREPARED_PHASE`/`COMMITTED_PHASE` fails, the function returns before the cleanup `defer` is ever registered, so the lock is neither released from PostgreSQL nor removed from the in-process bookkeeping map. This mirrors the reported analog bug class: an unhandled failure on a dependent call permanently strands protocol state that only cleanup logic (a `defer`/`try-catch` equivalent) was meant to clear.

### Finding Description
`voteTransaction` acquires the per-repository write lock and *then* registers a deferred unlock: [1](#0-0) 

```go
err := mgr.lockRepoForTransaction(ctx, transactionID, storageName, repoRelativePath, phase)
if err != nil {
    return fmt.Errorf("lock transaction %d: %w", transactionID, err)
}
defer func() {
    mgr.unlockRepoForTransaction(ctx, transactionID, returnedErr, phase)
}()
```

The `defer` that guarantees cleanup is registered *after* `lockRepoForTransaction` is called. `lockRepoForTransaction` handles two structurally different cases in the same function: [2](#0-1) 

- `PREPARING_PHASE`: acquires a brand-new lock and stores it in `mgr.repoLocks` (only on success).
- `PREPARED_PHASE` / `COMMITTED_PHASE`: loads the **already-held** lock from `mgr.repoLocks` and calls `lock.Renew(ctx)`. If `Renew` fails (e.g. because the PostgreSQL lock row already expired/was stolen, per `RepoReferenceWriteLockManager.renew`), the function returns the error immediately.

Because this error return happens in the same `voteTransaction` call *before* the `defer` line is reached, the deferred `unlockRepoForTransaction` is **never invoked** for this failure path. Compare this to a `PREPARING_PHASE` failure, where no lock was ever stored, so nothing needs releasing — the bug is specific to the renew-failure branch, where a lock *was* already held (recorded in `mgr.repoLocks`) but the cleanup that would delete/unlock it is skipped entirely.

The consequence is twofold:
1. The `repository_reference_write_locks` row in PostgreSQL for that repo is never explicitly deleted by `unlock()`; it can only be reclaimed once its hard-coded 20-second TTL (`renewInterval`) expires, per `NewRepoReferenceWriteLockManager`/`tryLock`'s expiry guard [3](#0-2) .
2. The stale entry keyed by `transactionID` in the in-process `mgr.repoLocks sync.Map` [4](#0-3)  is never removed via `releaseRepoLockOnPhase`'s `LoadAndDelete` [5](#0-4) , because that function is only reachable from the now-skipped `unlockRepoForTransaction`. Since `transactionID` is a monotonically increasing counter that is never reused (`atomic.AddUint64(&mgr.idSequence, 1)` in `RegisterTransaction`), each such occurrence leaves a permanent, unrecoverable entry in the map for the lifetime of the Praefect process.

This is directly analogous to the reported bug class: `_finalizeApprovalBallot` never reaching `markBallotAsFinalized` because an unhandled revert from an external call short-circuits execution before the mandatory cleanup step runs. Here, an unhandled failure from the dependent `Renew` call (itself a call to an external resource, PostgreSQL) short-circuits `voteTransaction` before the mandatory cleanup `defer` is even registered.

### Impact Explanation
This code path is reachable during ordinary Gitaly operation: every write RPC forwarded by Praefect drives Gitaly's reference-transaction hook, which casts `Preparing`, `Prepared`, and `Committed` votes through this exact `VoteTransaction` → `voteTransaction` → `lockRepoForTransaction` flow (see `doc/serialized_writes.md` flow description) [6](#0-5) . No privileged actor or malicious peer is required — a `Renew` failure naturally occurs whenever the PREPARED-phase vote arrives after the lock's 20-second TTL has elapsed (e.g. under load, slow Git operations, or contention causing the row to be stolen by another transaction), which the accompanying test suite explicitly exercises as a legitimate scenario (`TestPraefectWriteSerialization_HangAfterPrepared` simulates exactly this expiry condition) [7](#0-6) .

Each occurrence:
- Extends the write-lock hold on the affected repository by up to the full TTL window instead of releasing it immediately, delaying legitimate concurrent writers to that repository.
- Permanently leaks one entry in the Praefect process's `mgr.repoLocks sync.Map`, since the leaked key (`transactionID`) is never reused and nothing else ever cleans it up. Under sustained ordinary write traffic this is an unbounded memory-growth/DoS vector against the Praefect process, entirely from unprivileged, ordinary push activity.

### Likelihood Explanation
High likelihood in production: `Renew` failures are an expected, documented outcome of the lock TTL/expiry design (see `doc/serialized_writes.md`'s description of `renew` returning an error when the row is gone) [8](#0-7) , not a rare or attacker-engineered edge case. Any sufficiently slow or contended write against a repository under the serialized-writes feature can trigger it.

### Recommendation
Register the cleanup `defer` immediately after acquiring/loading the lock — before calling `lockRepoForTransaction` — or explicitly release/clean up the stored lock entry on any error returned from the `PREPARED_PHASE`/`COMMITTED_PHASE` renew branch, mirroring the `try/catch`-style fix applied to the analog bug. Concretely, in `internal/praefect/transactions/manager.go`, move the `defer mgr.unlockRepoForTransaction(...)` registration to wrap the call to `lockRepoForTransaction` itself (or add an explicit `mgr.releaseRepoLockOnPhase(transactionID, phase.String())` call on the `Renew` error path inside `lockRepoForTransaction`) so that a `Renew` failure always results in the lock being deleted from `mgr.repoLocks` and unlocked in PostgreSQL, exactly as the `PREPARING_PHASE` vote-failure path already correctly does.

### Proof of Concept
1. Register a transaction and successfully cast a `PREPARING_PHASE` vote so `mgr.repoLocks` stores the lock for `transactionID` (as in `TestPraefectWriteSerialization_HangAfterPrepared`) [9](#0-8) .
2. Force the underlying PostgreSQL row to expire (e.g., back-date `expired_at`, as the existing test does) [10](#0-9) , or let another transaction steal it.
3. Cast the `PREPARED_PHASE` vote for the original transaction. `lockRepoForTransaction`'s `lock.Renew(ctx)` call fails because the row was reclaimed [11](#0-10) , causing `voteTransaction` to return the error at line 167 before the `defer` at lines 169-171 is ever registered.
4. Inspect `mgr.repoLocks` (e.g., via a test hook or `sync.Map.Range`): the entry for the original `transactionID` is still present and will never be removed, confirming the permanent leak; simultaneously, no `unlock()` DELETE was issued against `repository_reference_write_locks` for that transaction.

```go
func (mgr *Manager) releaseRepoLockOnPhase(transactionID uint64, phase string) {
	v, ok := mgr.repoLocks.LoadAndDelete(transactionID)
	if !ok {
		return
	}
	logFields := log.Fields{
		"transaction.id": transactionID,
	}
	if phase != "" {
		logFields["phase"] = phase
	}
	lock := v.(datastore.RepoLock)
	if err := lock.Unlock(); err != nil {
		mgr.logger.WithError(err).WithFields(logFields).Error("release repo lock")
	}
}
```

```markdown
### Flow for one write

1. Client calls a write RPC against Praefect.
1. Praefect forwards the RPC to each Gitaly node in the replica set.
1. Each Gitaly node, in `UpdateReference` (or the equivalent write path),
   casts a `Preparing` vote **before** locking refs locally. The hook RPC
   reaches Praefect, which calls `lockRepoForTransaction(PREPARING_PHASE)`:
   `WriteLockManager.Lock` blocks until the per-repository lock is free.
1. Both nodes return from `Preparing` together (quorum reached).
1. Each Gitaly node locks refs on disk and votes `Prepared`. Praefect renews
   the lock.
1. Each Gitaly node writes the update and votes `Committed`. Praefect releases
   the lock.
```

```go
func TestPraefectWriteSerialization_HangAfterPrepared(t *testing.T) {
	t.Parallel()
	db := testdb.New(t)
	ctx := testhelper.Context(t)
	logger := testhelper.SharedLogger(t)
	repoWriteLockMgr := datastore.NewRepoReferenceWriteLockManager(ctx, db, testdb.GetConfig(t, db.Name), logger)

	storageName := "mock"
	relativePath := "hang/after/prepared.git"
	voters := []transactions.Voter{{Name: "primary", Votes: 1}}
	threshold := uint(1)

	cc, txMgr, cleanup := runPraefectServerAndTxMgrAndLockMgr(t, ctx, repoWriteLockMgr)
	defer cleanup()
	client := gitalypb.NewRefTransactionClient(cc)

	// Txn1: PREPARING + PREPARED, then "hang" (no COMMITTED)
	txn1, _, err := txMgr.RegisterTransaction(ctx, voters, threshold)
	require.NoError(t, err)
	hash1 := sha1.Sum([]byte("txn1"))

	for _, phase := range []gitalypb.VoteTransactionRequest_Phase{
		gitalypb.VoteTransactionRequest_PREPARING_PHASE,
		gitalypb.VoteTransactionRequest_PREPARED_PHASE,
	} {
		_, err := client.VoteTransaction(ctx, &gitalypb.VoteTransactionRequest{
			TransactionId:        txn1.ID(),
			Repository:           &gitalypb.Repository{StorageName: storageName, RelativePath: relativePath},
			Node:                 voters[0].Name,
			ReferenceUpdatesHash: hash1[:],
			Phase:                phase,
		})
		require.NoError(t, err)
	}
	// Intentionally skip COMMITTED phase to simulate a stuck client.

	// Simulate lock expiry by back-dating the row
	_, err = db.ExecContext(ctx, `
          UPDATE repository_reference_write_locks
          SET expired_at = NOW() - INTERVAL '1 second'
          WHERE lock_id = $1`, storageName+"|"+relativePath)
	require.NoError(t, err)

	// Txn2: PREPARING should succeed (steals the expired lock)
	txn2, cancel2, err := txMgr.RegisterTransaction(ctx, voters, threshold)
	require.NoError(t, err)
	defer func() { require.NoError(t, cancel2()) }()
	hash2 := sha1.Sum([]byte("txn2"))

	_, err = client.VoteTransaction(ctx, &gitalypb.VoteTransactionRequest{
		TransactionId:        txn2.ID(),
		Repository:           &gitalypb.Repository{StorageName: storageName, RelativePath: relativePath},
		Node:                 voters[0].Name,
		ReferenceUpdatesHash: hash2[:],
		Phase:                gitalypb.VoteTransactionRequest_PREPARING_PHASE,
	})
	require.NoError(t, err)
}
```
