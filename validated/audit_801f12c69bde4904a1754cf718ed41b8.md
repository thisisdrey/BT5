### Title
Dust-transfer griefing fills a victim's token list to `MAX_TOKENS_PER_USER`, permanently blocking new collateral/debt positions for accounts with locked balances - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Metronome tracks every `DepositToken` and `DebtToken` an account holds in two bounded lists (`debtTokensOfAccount`, `depositTokensOfAccount`) capped at `MAX_TOKENS_PER_USER = 30`. Because `DepositToken.transfer`/`transferFrom` are permissionless ERC-20 movements and `_transfer` auto-registers any first-time recipient into the list, an unprivileged attacker can push 1-wei "dust" transfers of every listed deposit token to a victim until `debt + deposit >= 30`. From that point, `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens`, which bricks every code path that mints a *new* token into the victim's position (`deposit`, `issue`/`mint` via `DebtToken`, `SmartFarmingManager.leverage`). If the victim has outstanding debt, `unlockedBalanceOf` returns ~0 for the dust, so they cannot transfer it back out to free a slot — the DoS is self-sustaining.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` enforce `onlyIfAdditionWillNotReachMaxTokens`, reverting once the combined list length reaches 30 (`contracts/Pool.sol:143-148, 204-208`).
- `DepositToken._transfer` registers the *recipient* on any first-time receipt: `if (_recipientBalanceBefore == 0 && amount_ > 0) pool.addToDepositTokensOfAccount(recipient_)` (`contracts/DepositToken.sol:517-525`). There is no opt-out — any holder can force-register an arbitrary address.
- `DepositToken.transfer` only requires the *sender's* amount to be unlocked (`_revertIfLocked(_msgSender, amount_)`); the recipient's consent or list capacity is irrelevant until `addToDepositTokensOfAccount` is hit — and when it reverts, the revert happens inside the victim-involving path, not the attacker's.
- Once full: `DepositToken.deposit` → `_mint` → `addToDepositTokensOfAccount` reverts; `DebtToken._mint` → `addToDebtTokensOfAccount` reverts (`contracts/DebtToken.sol:597-600`); `SmartFarmingManager.leverage`/`flashRepay` paths that mint new tokens likewise revert.
- Escape is blocked for indebted victims: removing an entry requires the victim's balance of that token to go to zero via `transfer`/`withdraw`, but `_revertIfLocked` checks `unlockedBalanceOf`, which returns `0` when the position's issuable USD is exhausted (`contracts/DepositToken.sol:383-398`). A victim at high utilization cannot shed the dust entries.

### Impact Explanation
The victim is permanently prevented from adding any *new* collateral token or issuing any *new* debt token — the exact actions needed to deleverage or top up a deteriorating position. When the market moves against them, they cannot deposit additional collateral types (existing-token deposits still work, but a victim holding a single collateral cannot diversify, and a victim whose only collateral is near its `unlockedBalanceOf` bound cannot act at all). The position becomes liquidatable while all remediation paths that touch a new token revert. This is a temporary-to-permanent freezing of position management that converts directly into liquidation loss — attacker-controlled forced liquidation of otherwise rescuable accounts.

### Likelihood Explanation
Feasibility depends on the deployed pool listing ≥30 tokens across deposit + debt sets; mainnet Pool1/Pool2 deployments carry many `DepositToken`/`DebtToken` pairs, and each new governor listing expands attack surface. The attack costs only dust amounts of each deposit token (1 wei each, obtainable by depositing dust oneself) plus gas — no privileged role, oracle manipulation, or capital at risk. The constraint is that the victim must already hold enough tokens/debt that the marginal pushes reach 30, and must be near a liquidation threshold for direct monetary extraction; otherwise the effect is a persistent capability freeze rather than immediate theft.

### Recommendation
- Decouple the list-cap revert from token receipt: make `addTo*TokensOfAccount` silently skip (or maintain an overflow list) instead of reverting when at capacity, so a forced dust registration can never brick minting.
- Alternatively, only auto-register recipients on `deposit`/`issue` (self-initiated paths) and require an explicit `claim`/opt-in for entries created via `transfer`/`seize` to third parties.
- Allow `removeFrom*TokensOfAccount` for zero-value dust entries regardless of lock status, e.g., permit transfers of balances below a dust threshold even when `unlockedBalanceOf == 0`.

### Proof of Concept
Foundry/Hardhat fork sketch against a deployed Pool:

```solidity
// Pool has >= N deposit tokens such that victim's current count + N >= 30
// 1. Attacker deposits dust in each deposit token to obtain msdTOKEN balances
for (uint i; i < depositTokens.length; ++i) {
    IERC20(underlying[i]).approve(address(dt[i]), dust);
    dt[i].deposit(dust, attacker);          // obtain 1 wei msdTOKEN each
}
// 2. Victim currently holds `k` tokens (debt + deposit), with debt > 0 and
//    unlockedBalanceOf(victim) == 0 for all dust tokens it will receive
// 3. Attacker dust-transfers until the victim's combined list hits 30
for (uint i; attacker transfers while victimCount < 30; ++i) {
    dt[i].transfer(victim, 1);              // registers victim in list
}
// 4. Assertions
//    - pool.debtTokensOfAccount.length(victim)
//      + pool.depositTokensOfAccount.length(victim) == 30
//    - dt[newToken].deposit(x, victim) reverts UserReachedMaxTokens
//    - debtToken.issue(...) for a synth the victim doesn't hold reverts
//    - victim cannot transfer the dust back: transfer -> NotEnoughFreeBalance
//    - price moves -> pool.liquidate(victim, ...) succeeds while any
//      remediation via a new token reverts
```

Key checks: `onlyIfAdditionWillNotReachMaxTokens` (`contracts/Pool.sol:143`), `_transfer` recipient registration (`contracts/DepositToken.sol:517-525`), `unlockedBalanceOf` returning 0 for indebted accounts (`contracts/DepositToken.sol:383-398`).
