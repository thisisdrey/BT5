### Title
Stale `PromiseYieldReceipt` survives `remove_account`, letting a deleted account's owner execute a self-authorized callback on a recreated account with the same name - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (`core/store/src/utils/mod.rs:505-575`) deletes `TrieKey::Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData`, but never removes `TrieKey::PromiseYieldReceipt`, `PromiseYieldStatus`, or the `YieldIdToDataId`/`DataIdToYieldId` mappings, even though these are account-scoped trie columns (`core/primitives/src/trie_key.rs:89-102`, listed in `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` alongside the columns that *are* cleared). If an account with a pending `promise_yield_create` is deleted and later recreated under the same `account_id`, the orphaned `PromiseYieldReceipt` entry and the still-queued `PromiseYieldTimeout` entry can later fire and execute the old owner's `FunctionCall` (method name + args chosen before deletion) against the new account, with `predecessor_id == receiver_id == account_id` (a "self" call).

### Finding Description
`promise_yield_create` (`runtime/near-vm-runner/src/logic/logic.rs:3660-3718`) always targets `self.context.current_account_id` as `receiver_id`, and the resulting `PromiseYield` receipt is stored keyed by `(receiver_id, data_id)` via `set_promise_yield_receipt` (`core/store/src/utils/mod.rs:200-212`), with `predecessor_id = receiver_id = account_id` (`runtime/runtime/src/function_call.rs:187-194`). A separate global-queue entry `TrieKey::PromiseYieldTimeout { index }` records `(account_id, data_id, expires_at)` (`core/store/src/utils/mod.rs:181-198`).

`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) performs no check for outstanding yields and simply calls `remove_account`, which removes `Account`, `ContractCode`, access keys/gas keys, and `ContractData` (`core/store/src/utils/mod.rs:505-575`) — but not `PromiseYieldReceipt`/`PromiseYieldStatus`/yield-id mappings.

Later, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3105`) walks the timeout queue purely by `expires_at`/index, independent of whether the account still exists, and checks `state_update.contains_key(&TrieKey::PromiseYieldReceipt{receiver_id: queue_entry.account_id, data_id})` (`lib.rs:3046-3051`). If that stale entry is still present, it synthesizes a `PromiseResume(data: None)` receipt targeted at `queue_entry.account_id`. When this reaches `process_receipt`'s `PromiseResume` branch (`lib.rs:1500-1562`), it fetches the same stale `PromiseYieldReceipt` via `get_promise_yield_receipt` and executes it via `apply_action_receipt`, running the original `FunctionCall` (method name/arguments chosen by the *previous* owner) against whatever account/contract now occupies that `account_id`, with `predecessor_id == account_id` (self).

Because many contracts use a `predecessor_id == current_account_id` ("assert_self") pattern to gate private/internal callback methods, this stale self-call bypasses the new account owner's authorization entirely — the new owner never consented to or created this callback, yet it executes as if it were a legitimate internal callback.

### Impact Explanation
This is an authorization escalation across accounts (a previous account owner can invoke self-only ("private") callback methods with attacker-chosen arguments against a brand-new owner's contract deployed under a recycled account name), matching the "authorization escalation across accounts or promises" bounty category. Impact severity depends on what private methods the new contract exposes (state corruption, unauthorized transfers/permission changes if such methods perform value-moving or privileged logic), but the underlying invariant break — a receipt is delivered and executed with `predecessor_id == receiver_id` for a completely unrelated (re-created) account — is a protocol-level authorization exactness violation, independent of contract-level mitigations.

### Likelihood Explanation
Preconditions: an account_id must become deletable and re-creatable (feasible for sub-accounts, which are freely deletable/creatable by anyone funding them, and to a lesser extent implicit/eth-implicit accounts), a `promise_yield_create` must be pending at deletion time, and the account must be re-created before the fixed protocol `yield_timeout_length_in_blocks` timeout elapses (or before that timeout is otherwise triggered/delayed via congestion, as already demonstrated feasible in `test-loop-tests/src/tests/yield_timeouts.rs`). The attacker (previous owner) needs no special privilege beyond normal account/contract operations, and the exploit is fully deterministic and repeatable given control over the timing of deletion/recreation relative to the fixed timeout window. This requires a specific social/timing sequence (someone else re-creating the exact account name in time), which reduces likelihood somewhat, but the underlying missing-cleanup bug is unconditionally present.

### Recommendation
`remove_account` should also purge all account-scoped promise-yield state before an account is deleted: iterate and remove any `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, and `TrieKey::DataIdToYieldId` entries for `account_id` (mirroring how `ContractData` is already swept), and/or have `action_delete_account` reject deletion (or force-resolve/cancel) while any yield is still pending for that account, so no future `PromiseYieldTimeout`/`PromiseResume` can resolve against a re-created account with a different owner.

### Proof of Concept
Test-loop integration test plan (extending `test-loop-tests/src/tests/yield_timeouts.rs` patterns):
1. Deploy a contract on account `x` (sub-account of a controlled parent) that calls `promise_yield_create` with `method_name = "private_admin_op"`, args chosen by the attacker, and awaits resolution.
2. Before `yield_timeout_height()`, submit a `DeleteAccount` action for `x` (refunding to `beneficiary`), and assert that `remove_account`'s state changes did not remove the `PromiseYieldReceipt`/`PromiseYieldStatus` trie entries for `x` (inspect via `col::PROMISE_YIELD_RECEIPT` prefix, as done in `get_yield_data_ids_in_state`).
3. Submit a `CreateAccount` + `DeployContract` for `x` again, deploying a *new* contract owned by a different key, which exposes a `#[private]` method `private_admin_op` guarded by `assert_self()`.
4. Advance blocks to `yield_timeout_height()` and `yield_timeout_height() + 1`, mirroring `test_simple_yield_timeout`.
5. Assert that `private_admin_op` on the *new* contract executed (e.g., via a state mutation or log it produces) even though the new owner never called it — proving the stale receipt fired against the recreated account and bypassed `assert_self()`-based authorization.
6. Additionally assert (as a regression guard) that after the fix, `remove_account` deletes the `PromiseYieldReceipt`/`PromiseYieldStatus` keys, and/or that the timeout resume does not execute against the recreated account.
