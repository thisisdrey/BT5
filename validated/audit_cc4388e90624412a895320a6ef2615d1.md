Audit Report

## Title
Unbounded `last_update_block` stamping after pool expiry causes permanent arithmetic-underflow lock of staked funds and rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`Pallet::update_pool_rewards` unconditionally stamps `PoolInfo::last_update_block` with the raw current block number rather than capping it at `expiry_block`, as confirmed at [1](#0-0) . Since `reward_per_token` computes `last_block_reward_applicable(expiry_block).ensure_sub(last_update_block)` [2](#0-1) , and `last_block_reward_applicable` caps at `expiry_block` [3](#0-2) , the first post-expiry call to any pool-mutating extrinsic leaves `last_update_block` greater than `expiry_block`. Any later interaction on the same pool while `total_tokens_staked` remains non-zero then hits `ensure_sub` on a negative delta, erroring out and permanently blocking `unstake`, `harvest_rewards`, `stake`, `set_pool_reward_rate_per_block`, and `set_pool_expiry_block` for that pool.

## Finding Description
`update_pool_rewards` is invoked before every pool-mutating action via `update_pool_and_staker_rewards` or directly, and always sets `last_update_block = T::BlockNumberProvider::current_block_number()` with no cap [4](#0-3) . `unstake` and `harvest_rewards` explicitly allow "any account" to call once `now > pool_info.expiry_block`, confirmed by the `ensure!` guards [5](#0-4)  and [6](#0-5) . On the first such post-expiry call, `reward_per_token` still succeeds because `last_update_block` was set before expiry, but `update_pool_rewards` then stamps `last_update_block` to the current (post-expiry) block, not capped at `expiry_block`. If `total_tokens_staked` is still non-zero afterward (i.e., not every staker exited in that single call), every subsequent call to `reward_per_token` computes `expiry_block.ensure_sub(last_update_block)` with `last_update_block > expiry_block`, which underflows and returns an error, aborting the extrinsic. `set_pool_reward_rate_per_block` and `set_pool_expiry_block` also call `reward_per_token` before any mutation [7](#0-6) [8](#0-7) , so even the admin cannot recover the pool by extending its expiry. `cleanup_pool` requires `PoolStakers` to be empty [9](#0-8) , which can never be reached once stakers are stuck.

## Impact Explanation
This matches the "permanent user-fund lock" impact category. Once `last_update_block` overshoots `expiry_block` while stakers remain, remaining stakers' frozen tokens (via `AssetsFreezer`) can never be unstaked and unclaimed rewards can never be harvested, with no privileged recovery path since admin-driven `set_pool_expiry_block`/`set_pool_reward_rate_per_block` hit the identical underflow.

## Likelihood Explanation
No malicious or privileged actor is required — the bug is triggered by ordinary usage: any pool naturally reaches its `expiry_block` while tokens remain staked, and one ordinary post-expiry call by any signed account (staker or not, since post-expiry access is unrestricted) poisons `last_update_block` for all remaining stakers in that pool.

## Recommendation
In `update_pool_rewards`, cap the new `last_update_block` at `expiry_block` by storing `Self::last_block_reward_applicable(pool_info.expiry_block)` instead of the raw current block number, so it never exceeds the value used by later `ensure_sub` calls in `reward_per_token`.

## Proof of Concept
1. Create a pool with `expiry_block = E` and stake `amount > 0` before `E` (`total_tokens_staked > 0`).
2. Advance to `now1 > E`. Call `unstake` (partial) or `harvest_rewards` as any account — succeeds, but `update_pool_rewards` sets `last_update_block = now1 > E` while `total_tokens_staked` remains `> 0`.
3. Advance to `now2 > now1`. Call `unstake`/`harvest_rewards`/`stake`/`set_pool_reward_rate_per_block`/`set_pool_expiry_block` on the same pool.
4. `reward_per_token` computes `last_block_reward_applicable(E) = E`, then `E.ensure_sub(now1)` underflows since `now1 > E`, returning an error and aborting the call.
5. All further operations on the pool fail identically forever; remaining staked tokens and unharvested rewards are permanently locked, and `cleanup_pool` can never succeed since `PoolStakers` can never be emptied.

			pool_info: &PoolInfoFor<T>,

			let reward_per_token = Self::reward_per_token(&pool_info)?;
			let pool_info = Self::update_pool_rewards(pool_info, reward_per_token)?;

		}

		/// Computes update pool reward state.
		///
		/// Should be called every time the pool is adjusted, and a staker is not involved.
		///
		/// Returns the updated pool and staker info.

		/// NOTE: this function has no side-effects. Side-effects such as storage modifications are
