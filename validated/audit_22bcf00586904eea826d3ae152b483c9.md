### Title
UserApplyPatch writes commits into the main object database and calls UpdateReference with `quarantineDir=nil`, defeating the quarantine safety net - ([File: internal/gitaly/service/operations/apply_patch.go])

### Summary
`Server.userApplyPatch` (in `internal/gitaly/service/operations/apply_patch.go`) builds its `localrepo.Repo` directly via `s.localRepoFactory.Build(header.GetRepository())` instead of via `s.quarantinedRepo(...)`, and then writes new commit objects with `repo.WriteCommit` straight into the main object directory. It then calls `s.updateReferenceWithHooks(..., nil /* quarantineDir */, ...)`, unlike every other object-creating RPC in this package (`UserCommitFiles`, `UserCherryPick`, `UserRevert`, `UserMergeBranch`, `UserRebaseConfirmable`, `UserUpdateSubmodule`, `UserCreateBranch`, `UserFFBranch`, `UserUpdateBranch`), all of which obtain a `quarantineDir` from `s.quarantinedRepo` before writing objects and pass it through.

### Finding Description
`UpdaterWithHooks.UpdateReference` (`internal/gitaly/hook/updateref/update_with_hooks.go:167-330`) is designed so that new objects are written into a quarantine directory first; `PreReceiveHook` is executed against the quarantined repo; only if that hook (which calls Rails' `/internal/allowed` access-check endpoint) succeeds does `quarantineDir.Migrate(ctx)` move the objects into the real object directory (lines 213-244). If `quarantineDir` is `nil`, `quarantinedRepo` degenerates to `repoProto` itself (line 213-216) and the migrate step is skipped entirely (line 232 guards on `quarantineDir != nil`).

In `apply_patch.go`, `userApplyPatch` calls:
```
repo := s.localRepoFactory.Build(header.GetRepository())     // line 66 - NOT quarantined
...
patchedCommit, err := s.applyPatchesWithIndex(ctx, repo, ...) // writes commits via repo.WriteCommit at line 203
...
if err := s.updateReferenceWithHooks(ctx, header.GetRepository(), header.GetUser(), nil, targetBranch, patchedCommit, currentCommit); err != nil { ... } // line 128, nil quarantine
```
This is the only RPC among all callers of `updateReferenceWithHooks` in `internal/gitaly/service/operations/*.go` that (a) creates brand-new commit/tree/blob objects and (b) passes a `nil` quarantine directory. `UserDeleteBranch` also passes `nil`, but it is a ref-deletion RPC that creates no new objects, so quarantine is correctly not needed there — that is not a bug.

Because `repo` is never quarantined, `WriteCommit` (called for each mailbox patch in `applyPatchesWithIndex`) writes the new commit, tree, and blob objects directly into the target repository's real object directory the moment they are created — before the `PreReceiveHook`/Rails access check has run at all. `PreReceiveHook` is still invoked afterward via `UpdateReference`, so the ref itself will not advance if Rails denies the change (the standard branch-protection/access-check codepath is executed), and the objects remain unreachable via any ref until garbage collected.

### Impact Explanation
This does not bypass the actual `/internal/allowed` permission check that gates the *reference update* itself — `PreReceiveHook` always runs prior to `updater.Commit()` in `UpdateReference` regardless of quarantine, and `UserApplyPatch` will still fail the RPC and not move the branch if Rails rejects the change. The concrete, quarantine-specific consequence is narrower than "ref advances to unvetted objects": it is that unvetted loose objects (commits/trees/blobs from patches that Rails ultimately rejects) get permanently written into the main object directory instead of being confined to a throwaway quarantine directory that is discarded on failure. This is a hygiene/defense-in-depth gap (objects bypass the intended "objects only enter the real odb after being vetted" invariant, and could be picked up by later, unrelated processes doing raw object scans, or waste storage) rather than a direct authorization bypass of a ref update, since the reference itself is still protected by the unconditional pre-receive call.

### Likelihood Explanation
Any unprivileged user who can call `UserApplyPatch` (e.g., by submitting a patch/MR that goes through this RPC) with content that ultimately fails the Rails access check (e.g., protected branch, size limits enforced via pre-receive) will trigger this path deterministically, since `apply_patch.go` unconditionally uses a non-quarantined repo. No special configuration is required — this is the default code path for every `UserApplyPatch` call today.

### Recommendation
Make `userApplyPatch` obtain its `localrepo.Repo` via `s.quarantinedRepo(ctx, header.GetRepository())` (as every other object-writing RPC in this package does), perform `applyPatchesWithIndex`/`WriteCommit` against the quarantined repo, and pass the resulting `quarantineDir` into `s.updateReferenceWithHooks` instead of `nil`, so that newly created commit objects are confined to the quarantine directory until the pre-receive/access check succeeds.
