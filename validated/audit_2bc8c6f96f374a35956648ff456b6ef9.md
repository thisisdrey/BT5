### Title
Anti-replay window Check/Update race allows the same message counter to bypass replay protection - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement anti-replay protection using the same flawed pattern as the reported HSG bug: a "check" step is performed, an expensive/interruptible operation happens *outside* the lock, and only afterward is the "update" (state-committing) step performed under the lock again. Because the lock is released between `Check` and `Update`, a second goroutine processing the same replayed counter can also pass `Check` before the first goroutine's `Update` call marks the counter as seen, defeating the sliding-window anti-replay guarantee — structurally identical to the HSG issue where the guard-entries counter's increment-before/decrement-after logic left a reentrant window in which the guarded invariant could be violated.

### Finding Description
`Decrypt` takes `decryptLock`, calls `cs.window.Check(l, messageCounter)`, and immediately releases the lock before calling the (possibly slow) AEAD `DecryptDanger`. Only after decryption succeeds does it re-acquire the lock and call `cs.window.Update(l, messageCounter)` to actually mark the counter as seen: [1](#0-0) 

`VerifyRelay` follows the identical pattern for relay frames: [2](#0-1) 

The replay window itself, `Bits.Check`/`Bits.Update`, treats a counter as "not yet seen" until `Update` sets its bit: [3](#0-2) [4](#0-3) 

This mirrors the HSG root cause exactly: the guard state (`_guardEntries` in HSG, `window` bits here) is checked in one critical section, an external action is allowed to run unguarded (`execTransaction`'s nested call in HSG, `DecryptDanger` here), and the state is only committed in a second, separate critical section afterward. Any concurrent invocation that lands inside that gap observes the pre-update state and is wrongly treated as valid, exactly like the HSG reentrant call that observed an unincremented/undecremented `_guardEntries`.

Inbound UDP packets are read and dispatched into `Decrypt`/`VerifyRelay` from `readOutsidePackets`, called from per-queue reader loops: [5](#0-4) [6](#0-5) 

Since a single `HostInfo`/`ConnectionState` can be targeted concurrently by packets delivered on different reader goroutines (each `listenOut(i)` runs its own `ListenOut` loop and invokes `readOutsidePackets` independently), an attacker who captures or predicts one ciphertext packet with counter `N` can replay it multiple times in quick succession. Two (or more) replays landing on different reader goroutines can both pass `window.Check` before either one's `window.Update` commits, because the lock is dropped for the duration of `DecryptDanger`.

### Impact Explanation
A successful race lets an attacker's captured/replayed ciphertext be accepted and decrypted a second (or further) time by `Decrypt`, or accepted a second time as an authenticated relay frame by `VerifyRelay`, even though the anti-replay window is specifically designed to reject exactly one occurrence of each message counter. This is a concrete traffic-replay bypass of the protocol's nonce/replay defenses — the data-plane equivalent of "attacker can perform malicious transactions" in the original report, since a replayed encrypted payload (e.g., a control-plane frame, tunnel packet, or relayed frame) can be reprocessed by the target, potentially causing duplicate delivery of tunnel packets, duplicate relay forwarding, or reuse of the message counter's associated state.

### Likelihood Explanation
Exploitation requires precise timing to land two decrypt attempts for the same counter inside the narrow window between `Check` and `Update` (bounded by one `DecryptDanger` AEAD call), which is a real but tight race; it depends on Nebula's multi-reader dispatch of UDP packets for the same connection landing on different goroutines close together in time. It is remotely triggerable without any certificate/authentication bypass — a passive attacker who can capture one valid ciphertext packet and resend copies of it (no valid CA-signed cert needed) can attempt the race repeatedly to increase the chance of a hit.

### Recommendation
Hold `decryptLock` for the entire check-decrypt-update sequence in both `Decrypt` and `VerifyRelay`, or perform the state commit optimistically before the expensive AEAD call and roll back on decryption failure, so that no other goroutine can observe the "checked but not yet updated" intermediate state. Concretely, do not release `decryptLock` between `cs.window.Check` and `cs.window.Update`; instead call `DecryptDanger` while still holding the lock (or use a single atomic "check-and-reserve" operation on the window before decrypting, undoing the reservation only on decryption failure).

### Proof of Concept
1. Establish a tunnel between two Nebula instances so a `ConnectionState` exists with an active replay `window`.
2. Capture one legitimate encrypted data-plane (or relay) packet with message counter `N` sent to the victim.
3. Rapidly resend two (or more) copies of the exact same captured packet to the victim's underlay UDP address such that they are picked up by different reader goroutines (`listenOut(i)` instances) at nearly the same time.
4. If both copies call `cs.window.Check(l, N)` before either has called `cs.window.Update(l, N)`, both pass the check in `Decrypt`/`VerifyRelay` at `connection_state.go:64` / `connection_state.go:87`, and both proceed to `DecryptDanger` and are treated as valid, non-replayed packets — demonstrating the anti-replay bypass.

}

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
