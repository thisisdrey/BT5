### Title
StackerDB chunk signatures do not bind to the target contract, enabling cross-replica chunk replay - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
`SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs` only commits to `slot_id`, `slot_version`, and `data_hash` [1](#0-0) . The target StackerDB "replica" (the `smart_contract`/`contract_id`, analogous to the unchecked `market` parameter in the reported Tracer bug) is supplied as a separate, out-of-band parameter to `StackerDBTx::try_replace_chunk` and to `PeerNetwork::validate_received_chunk`, and is never verified against anything the signature actually authenticates [2](#0-1) [3](#0-2) .

### Finding Description
The verification chain is:
1. `SlotMetadata::verify(principal)` recovers a pubkey from the signature over `auth_digest()` and checks it hashes to `principal` [4](#0-3) .
2. `try_replace_chunk` looks up `slot_validation.signer` for `(smart_contract, slot_desc.slot_id)` and calls `slot_desc.verify(&slot_validation.signer)` [5](#0-4) . The `smart_contract` value used to fetch the expected signer is the caller-supplied contract identifier (from the HTTP path `/v2/stackerdb/:address/:contract/chunks` in `RPCPostStackerDBChunkRequestHandler`) — it is not part of the signed digest [6](#0-5) .
3. The same pattern repeats in the gossip/relay path: `validate_received_chunk` resolves `get_slot_signer(smart_contract_id, data.slot_id)` from the caller-supplied `smart_contract_id` and verifies against that address only, with no check that the signature was produced *for* this specific contract [7](#0-6) .

Because the signed payload is `(slot_id, slot_version, data_hash)` only, a signature is valid input to `try_replace_chunk`/`validate_received_chunk` for *any* StackerDB contract in which that signer happens to own the same `slot_id`, at an acceptable `slot_version`. In the Stacks signer system, the same signer address set is registered as slot owners across multiple distinct StackerDB replicas within a reward cycle (one contract per `MessageSlotID` — e.g. transactions, block responses, block pre-commits) [8](#0-7) . A malicious signer can therefore take a chunk it legitimately authored and signed for one message-kind contract and resubmit the identical `StackerDBChunkData` (slot_id, slot_version, sig, data) to a *different* contract in which it also owns that slot_id, and the server will accept and store/relay it as if it were an authentic message for that different replica — the equality "this signature authorizes writes to *this* contract's slot" is never actually checked; only "this signature was made by the owner of slot X in *some* contract chosen by the caller" is checked.

This is the direct analog of the reported bug: just as `Account.claimReceipts()` accepted a caller-supplied `market` without checking it against `receipt.tracer`, `try_replace_chunk`/`validate_received_chunk` accept a caller-supplied `contract_id` without checking it against anything committed to by the chunk's own signature.

### Impact Explanation
This allows an unauthenticated-with-respect-to-the-target-replica write: a party who is a legitimate signer for slot X in contract A, but who has never signed anything intended for contract B, can nonetheless get their (attacker-chosen) data accepted into contract B's slot X, as long as they also own slot X there and the version/size gates pass. This is forged-data propagation across StackerDB replicas — data destined for one message type/eventing channel can be substituted into another, which downstream signer/miner logic will treat as a genuine, correctly-authenticated message for that replica since `StackerDBChunkAckData`/relay logic only checks per-slot signer identity, not per-contract intent. Per the impact classification, this is unauthorized write to StackerDB state and forged-data propagation across the network (chunks are gossiped via `StackerDBPushChunk` once accepted, see `node.set_relay_message` in `poststackerdbchunk.rs`) [9](#0-8) .

### Likelihood Explanation
Requires the attacker to already be a legitimate registered signer (i.e., hold a private key that owns a slot in at least one StackerDB contract) — no special privileged role or another party's key is required beyond that. Given that signer sets are shared/reused across the several per-reward-cycle StackerDB contracts, slot-id collisions across contracts for the same signer are plausible/likely by design of the slot-assignment scheme, though I could not fully confirm the exact slot-assignment algorithm across all `MessageSlotID` contracts within the available index (the `make_signer_slots`-equivalent logic was only partially visible).

### Recommendation
Bind the target StackerDB contract identifier into the signed digest, e.g. include a hash/identifier of `smart_contract`/`contract_id` in `SlotMetadata::auth_digest()`, so that a valid chunk signature is only usable for the specific replica it was created for. Alternatively, when computing `try_replace_chunk`/`validate_received_chunk`, incorporate the contract identifier into the value that `slot_desc.verify()` authenticates rather than trusting the caller-supplied `smart_contract` purely as a key into slot-signer lookup.

### Proof of Concept
Conceptual PoC (matches existing test infrastructure in `stackslib/src/net/stackerdb/tests/db.rs` and `stackslib/src/net/api/tests/poststackerdbchunk.rs`):
1. Signer `S` owns slot 0 in StackerDB contract `A` and also owns slot 0 in StackerDB contract `B` (plausible given shared signer sets across per-message-kind contracts).
2. `S` builds `StackerDBChunkData { slot_id: 0, slot_version: 1, data: payload_for_A }` and signs it via `chunk.sign(&S_privkey)` — this signs only `(0, 1, hash(payload_for_A))`, per `auth_digest()` [1](#0-0) .
3. `S` POSTs this identical chunk to `/v2/stackerdb/<B-address>/<B-contract>/chunks` instead of `A`'s endpoint.
4. `try_replace_chunk` for contract `B` looks up `B`'s slot-0 signer (also `S`), calls `slot_desc.verify(&S_addr)`, which succeeds because the signature never referenced contract `A` at all [5](#0-4) .
5. The chunk is accepted into `B`, and if accepted, is relayed via `StackerDBPushChunk` to the network as a legitimate chunk for contract `B` [9](#0-8) .

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
