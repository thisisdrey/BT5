### Title
Front-runnable `AlreadyExists` griefing in `pallet-asset-conversion-ops::migrate_to_new_account` permanently locks pool liquidity - (File: `substrate/frame/asset-conversion/ops/src/lib.rs`)

### Summary
`pallet_asset_conversion_ops::Pallet::migrate_to_new_account` is a permissionless, fee-less (`Pays::No`) extrinsic that moves a pool's `asset1`/`asset2`/`lp_token` balances from a legacy-derived `prior_account` to the corrected `new_account`. Before transferring, it unconditionally calls `T::Assets::touch(asset, &new_account, &depositor)` whenever the prior account has an existing per-asset deposit to refund. `touch` (backed by `pallet_assets::Pallet::do_touch`) hard-fails with `Error::AlreadyExists` if an asset-account already exists for `new_account`. Because `new_account` is a deterministic, publicly-computable address (`T::PoolLocator::address(pool_id)`), any unprivileged user can pre-create that asset-account (e.g. by sending a trivial nonzero transfer of `asset1`/`asset2`/`lp_token` to it) before the legitimate migration call executes, causing `touch` to permanently fail and the whole extrinsic to revert every time it is retried.

### Finding Description
`migrate_to_new_account` in [1](#0-0)  computes `prior_account`/`new_account` deterministically from the pool id via `T::PoolLocator::address` and `T::PriorAccountIdConverter`, both public, pure functions of `(asset1, asset2)`.

For each asset that required a deposit to create its account under the old derivation, the code does: [2](#0-1) 

`T::Assets::touch` maps to `pallet_assets::Pallet::do_touch`, which enforces: [3](#0-2) 
i.e. `ensure!(!Account::<T, I>::contains_key(&id, &who), Error::<T, I>::AlreadyExists);`

Since `new_account` is public and derivable by anyone off-chain (it's just the future/corrected pool address), an attacker can simply transfer a tiny nonzero amount of `asset1`, `asset2`, or the `lp_token` to `new_account` *before* anyone calls `migrate_to_new_account`. This causes an `Account` entry for that asset at `new_account` to be created ahead of time. When the legitimate migration call later runs and reaches the `touch` step for that asset, `do_touch` returns `Error::AlreadyExists`, and the whole dispatchable reverts (all storage changes for that call are rolled back). The migration can never succeed for that pool as long as the attacker keeps re-donating a small amount whenever needed (in practice, a single donation before the account is otherwise legitimately created is enough, since once the account exists it typically stays until fully drained/reaped).

This is a direct structural analog to the reported NFTX bug: a public entry point performs an exact-state precondition check (`balance == expected` there; `!Account::contains_key` here) against an account that any unprivileged actor can pre-seed, permanently disabling functionality for everyone who depends on that specific state transition.

### Impact Explanation
Successful griefing permanently blocks `migrate_to_new_account` for the targeted pool. Because `prior_account` holds the pool's real `asset1`/`asset2`/`lp_token` balances under the deprecated address-derivation scheme, and the corrected/live logic in `pallet_asset_conversion` addresses pools via `T::PoolLocator::address` (i.e. `new_account`), a pool stuck at `prior_account` can never have its liquidity migrated to the address the rest of the protocol expects. This is a permanent, unprivileged fund-lock affecting every liquidity provider of that pool — matching the "permanent user-fund or bridge-state lock" impact category. It requires no governance, admin, validator, or relayer compromise — only an ordinary signed account performing a trivial, cheap asset transfer.

### Likelihood Explanation
High. The attack requires only:
1. Knowledge of `pool_id` (public storage) and the ability to compute `new_account` via the same public `PoolLocator`/`PriorAccountIdConverter` logic used by the pallet itself.
2. A single ordinary `transfer` of a minimal nonzero amount of the target asset to `new_account`.
3. No timing/front-running against a specific transaction is even required — the attacker can pre-seed the account for any not-yet-migrated pool at any time, well before anyone attempts the migration, since `deposit_held` on `prior_account` (which triggers the `touch` call) persists until migration succeeds.

### Recommendation
- Do not require `touch`/`AccountTouch` to fail hard on pre-existing accounts within a system-driven migration path; instead check `should_touch` first (as `pallet_asset_conversion::touch` already does) and skip the `touch` call if the account already exists, only bailing out if the existing account's state is actually incompatible with completing the migration (or gracefully handle/refund the extra balance already present).
- Alternatively, use `Precision`/idempotent creation semantics (e.g. `deposit_required`/`should_touch` check before calling `touch`) instead of relying on the caller to guarantee the target account is fresh, since that account's address is public and not privileged.
- Add a defensive path that lets governance/root force-complete a migration even if `new_account` already holds a stray balance, so a single malicious/careless donation cannot permanently strand a pool's liquidity.

### Proof of Concept
1. Identify an existing but not-yet-migrated `pallet_asset_conversion` pool `(asset1, asset2)` whose liquidity still lives at the legacy `prior_account` (per `T::PriorAccountIdConverter`), and where the deposit for `asset1`'s account was taken (i.e., `T::AssetsRefund::deposit_held(asset1, prior_account)` returns `Some`).
2. Compute `new_account = T::PoolLocator::address((asset1, asset2))` off-chain — this is deterministic and requires no special privilege.
3. As an unprivileged account, submit `pallet_assets::transfer(asset1, new_account, 1)` (or any minimal nonzero transfer) to create an `Account<asset1, new_account>` entry.
4. Have anyone call `pallet_asset_conversion_ops::migrate_to_new_account(asset1, asset2)`.
5. Observe that execution reaches:
```rust

    T::AssetsRefund::deposit_held(asset1.clone(), prior_account.clone())
{
    T::DepositAsset::mint_into(&depositor, deposit + deposit_asset_ed)?;
    T::Assets::touch(asset1.clone(), &new_account, &depositor)?;   // <-- fails
}
```
and `T::Assets::touch` returns `Error::<T>::AlreadyExists` (from `do_touch`'s `ensure!(!Account::<T, I>::contains_key(&id, &who), ...)`), reverting the entire extrinsic. The pool's liquidity remains stranded at `prior_account` indefinitely, and every retry of the migration fails the same way as long as the attacker's stray balance remains at `new_account`.
