## Finding

### Title
Unvalidated attacker-controlled array length in ValidateMultiSign / BatchValidateSign precompile leads to uncaught exceptions / OOM during TVM execution - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The Ghostscript CVE (`ALPINE-CVE-2025-27834`) is a buffer overflow caused by an oversized/attacker-controlled length field (a Type 4 function) that is used to size a buffer without adequate bounds validation. The closest reachable analog in java-tron is in the `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts, where a length word taken directly from attacker-supplied calldata is used to allocate an array and to compute copy offsets into the raw input buffer, with the bounds check only applied conditionally.

### Finding Description
`extractSigArray` and `extractBytesArray` read an attacker-controlled length field directly out of the ABI-encoded calldata and use it, unchecked, to allocate an array and to index/copy from the raw `data` byte array: [1](#0-0) 

The same unguarded pattern exists in `extractBytesArray`, which also uses attacker-controlled offsets/lengths for `extractBytes` (`Arrays.copyOfRange`) into the raw buffer: [2](#0-1) 

In `ValidateMultiSign.execute`, the size guard (`sigArraySize > MAX_SIZE`) is only applied when `VMConfig.allowTvmSelfdestructRestriction()` is enabled, and even then only validates the *first* declared length, not the individual per-signature offsets used inside the loop. When the flag is not enabled (or for the un-restricted `extractBytesArray` path used to compute `bytesOffset`/`bytesLen` per item), `len` can be an attacker-chosen 31-bit value, causing `new byte[len][]` to throw `NegativeArraySizeException`/`OutOfMemoryError`, or causing `extractBytes`'s `Arrays.copyOfRange` to throw `ArrayIndexOutOfBoundsException` when the computed offset/length exceeds `data.length`: [3](#0-2) 

Critically, this extraction call happens *before* the `try` block that wraps the rest of `ValidateMultiSign.execute` (the `try` only starts at the `account != null` branch), so any exception thrown by `extractSigArray`/`extractBytesArray` is not caught inside this precompile and propagates out of `execute()`: [4](#0-3) 

By contrast, `BatchValidateSign.execute` does wrap the equivalent call in a top-level `try { return doExecute(data); } catch (Throwable t) { ... }`, which suppresses the same class of exception: [5](#0-4) 

This inconsistency means `ValidateMultiSign` is the more exposed path — its extraction logic runs unguarded by any local catch.

### Impact Explanation
An unprivileged contract caller can invoke `ValidateMultiSign` (a TVM precompile reachable from any deployed contract) with a crafted ABI payload whose declared array-length word is huge or whose nested offset causes an out-of-bounds read on `data`. Depending on which exception type is thrown (`RuntimeException` vs `OutOfMemoryError`) and how the outer VM interpreter/precompile dispatcher handles it, this could result in unhandled exceptions during contract execution, energy-accounting bypass, or (in the `OutOfMemoryError` case) a node crash/DoS of the TVM execution thread. I was not able to fully trace whether `Program`'s precompile-invocation code (the caller of `PrecompiledContract.execute`) wraps all invocations in a catch-all for `Throwable`/`Error`; this is an important unresolved detail. If it does catch broadly, the practical impact is limited to a reverted transaction; if it only catches `RuntimeException` (not `Error`), an `OutOfMemoryError` from the oversized array allocation could escape and impact node availability.

### Likelihood Explanation
The precompile is reachable by any account able to deploy or call a contract that invokes `ValidateMultiSign`/`BatchValidateSign`, a common permission-validation compile-in used for multisig-enabled TRC. Crafting the calldata to control the length word is trivial (single ABI word). The mitigating `sigArraySize > MAX_SIZE` guard reduces likelihood on chains with `allowTvmSelfdestructRestriction` active, but does not fully validate every offset/length used inside the extraction loops.

### Recommendation
- Enforce `len`/`bytesOffset`/`bytesLen` bounds checks unconditionally (not gated behind `allowTvmSelfdestructRestriction`) in `extractSigArray` and `extractBytesArray`, validating that all computed offsets/lengths stay within `data.length` and within a sane `MAX_SIZE` before allocation.
- Wrap the length/array extraction calls in `ValidateMultiSign.execute` in the same defensive `try/catch (Throwable)` pattern already used in `BatchValidateSign.execute`.
- Verify at the TVM/precompile dispatch layer (`Program`'s precompile invocation site) that both `RuntimeException` and `Error` (e.g., `OutOfMemoryError`) from precompile execution are safely converted into a reverted transaction rather than propagating and affecting the node process.

### Proof of Concept
1. Deploy or call a contract that invokes the `ValidateMultiSign` precompile address with ABI-encoded calldata where:
   - word[3] (signature-array offset pointer) points to a word whose value (interpreted as `len`) is a large positive integer (e.g., `0x7FFFFFFF`).
   - `allowTvmSelfdestructRestriction` disabled (or crafted so the `sigArraySize > MAX_SIZE` check at line 1067 is bypassed because the checked word differs from the one consumed inside `extractSigArray`'s loop for `bytesOffset`).
2. This drives `extractSigArray`/`extractBytesArray` to execute `new byte[len][]` or `Arrays.copyOfRange(data, offset, offset+len)` with an out-of-range value, throwing `NegativeArraySizeException`, `OutOfMemoryError`, or `ArrayIndexOutOfBoundsException` outside the local `try` block in `ValidateMultiSign.execute`.
3. Observe whether the exception propagates past `PrecompiledContract.execute` uncaught, and evaluate downstream handling in the TVM interpreter.

**Uncertainty note:** I could not fully confirm within the available index how `Program`'s precompile-call site handles arbitrary `Throwable`/`Error` from `PrecompiledContract.execute()`, which is needed to determine whether this reaches "node crash" severity or is contained to a reverted transaction. A Devin session with full repository access would be needed to trace that call path definitively.
