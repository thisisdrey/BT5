This confirms the exploit path: `handle_connection` (streamer/src/nonblocking/quic.rs:713) calls `qos.remove_connection(&context, connection)` unconditionally whenever the connection's stream loop breaks (peer disconnect, idle timeout, or any stream error), and `SwQos::remove_connection`/`ConnectionTable::remove_connection` deletes the table entry entirely once its `Vec` of `ConnectionEntry` becomes empty [1](#0-0) [2](#0-1) . Since the `Arc<ConnectionStreamCounter>` is only held by `ConnectionEntry` instances, once the last entry for that `ConnectionTableKey` is dropped, the counter is deallocated, and a subsequent `try_add_connection` for the same key finds an empty/absent entry and falls back to `stream_counter_factory`, producing a brand-new `ConnectionStreamCounter` with `stream_count = 0` [3](#0-2) [4](#0-3) .

### Title
Unstaked client resets per-source stream throttling budget via reconnect due to counter re-creation on connection-table eviction - (File: streamer/src/nonblocking/quic.rs)

### Summary
`ConnectionTable::try_add_connection` shares a single `Arc<ConnectionStreamCounter>` across all connections keyed by IP/pubkey by cloning it from the first existing `ConnectionEntry`, but `ConnectionTable::remove_connection` deletes the entire table entry (and thus drops the shared counter) once the last connection for that key closes. An unprivileged unstaked client can repeatedly disconnect and reconnect to reset its throttling state before the natural `STREAM_THROTTLING_INTERVAL` elapses.

### Finding Description
`SwQos`/`SimpleQos`'s `try_add_connection` calls `ConnectionTable::try_add_connection`, which derives the stream counter to attach to a new connection as: reuse `connection_entry.first().stream_counter.clone()` if any entry already exists for the key, otherwise call `stream_counter_factory` to build a fresh `Arc<ConnectionStreamCounter>` [3](#0-2) . This design intends per-source (per-IP or per-pubkey) sharing so that multiple simultaneous connections from one peer count against a single throttle budget.

The flaw is in the connection-closing path: `handle_connection` unconditionally calls `qos.remove_connection(&context, connection)` when the connection's read/stream loop ends for any reason (idle timeout, peer disconnect, stream error) [1](#0-0) . `ConnectionTable::remove_connection` removes the closed `ConnectionEntry` from the per-key `Vec`, and if that `Vec` becomes empty, it calls `e.swap_remove_entry()`, deleting the whole map entry [2](#0-1) . Because the shared `stream_counter` `Arc` was only referenced from that entry (and from the just-dropped connection's own `SwQosConnectionContext`, which also goes out of scope), the `ConnectionStreamCounter` (holding `stream_count: AtomicU64` and `last_throttling_instant`) is deallocated.

When the same attacker (same source IP, unstaked, so keyed by IP under `ConnectionTableKey::IP`) opens a brand-new QUIC connection, `try_add_connection` finds no entry for that key, so `connection_entry.first()` is `None`, and it falls back to `stream_counter_factory`, creating `ConnectionStreamCounter::new()` with `stream_count = 0` and `last_throttling_instant = now` [5](#0-4) . `throttle_stream` in `SwQos::on_new_stream` only throttles based on `stream_counter.stream_count` versus `max_streams_per_throttling_interval` within the current `STREAM_THROTTLING_INTERVAL`, using `reset_throttling_params_if_needed` for the natural reset cadence [6](#0-5) . Since a fresh counter always starts at `stream_count = 0`, this bypasses the natural reset cadence — the attacker doesn't have to wait for `STREAM_THROTTLING_INTERVAL` to elapse; simply reconnecting from the same IP resets the count immediately.

There is no cooldown or historical bookkeeping preserved per-IP across full disconnects (only the max-connections-per-peer and max-unstaked-connections limits apply at connection-establishment time, which are separate concerns from the stream throttle counter).

### Impact Explanation
This falls under Agave's QoS-evasion bounty category (per-source stream/connection limit bypass). An unstaked attacker can send `max_streams_per_throttling_interval` streams, then close the connection (client-initiated `close()`, which is free and instantaneous for the attacker), immediately reopen a new QUIC connection from the same source IP, and repeat, achieving an effective stream-admission rate to the leader's TPU substantially higher than the intended per-unstaked-peer throttling bound, limited only by connection-churn overhead (handshake cost) and `max_connections_per_unstaked_peer` / `max_unstaked_connections`. Because throttling resets to zero on each reconnect rather than being amortized over time, sufficiently fast reconnect cycling can let this attacker's effective throughput approach `max_streams_per_throttling_interval` per reconnect cycle instead of per `STREAM_THROTTLING_INTERVAL`, unfairly consuming TPU capacity relative to its (zero) stake.

### Likelihood Explanation
Feasible and repeatable by an unprivileged, unstaked remote client with no special permissions: it only requires the ability to open/close QUIC connections to the leader's TPU port, which is exactly the assumed attacker capability. The only friction is QUIC handshake latency and the existing `overall_connection_rate_limiter` / per-IP `ConnectionRateLimiter` in `setup_connection` (streamer/src/nonblocking/quic.rs:459-508), which throttle new connection attempts but do not prevent this pattern outright — they just bound the reconnect cadence, not eliminate the throttle-reset primitive. As long as the reconnect rate allowed by those connection-rate-limiters is faster than `STREAM_THROTTLING_INTERVAL`'s natural reset, the attacker gains an advantage.

### Recommendation
Decouple the stream-throttling state from the `ConnectionEntry`/table lifetime for a given source key. Options: (1) keep a per-key `ConnectionStreamCounter` (or its last-seen state) alive in the table independent of whether any connection is currently open for that key, evicting it only via a separate, time-bounded LRU/TTL rather than immediately on last-connection-removal; or (2) persist `last_throttling_instant`/`stream_count` outside `ConnectionEntry`, e.g., in a longer-lived per-IP or per-pubkey map that isn't torn down on every disconnect.

                        .connection

            self.total_size = self.total_size.saturating_sub(connections_removed);
