### Title
Missing trailing-data check after signature TLV in `unmarshalCertificateV2` allows unknown trailing bytes inside the certificate SEQUENCE to be silently accepted - ([File: cert/cert_v2.go])

### Summary
`unmarshalCertificateV2` opens the outer ASN.1 SEQUENCE, then reads `rawDetails`, an optional curve byte, the public key, and finally `rawSignature`, but never calls `input.Empty()` after the last read to confirm the entire SEQUENCE content has been consumed. This means a certificate blob can contain extra, unknown TLV data after the signature element (but still inside the declared SEQUENCE length) and still parse successfully, violating the "unknown fields must reject" fail-closed invariant.

### Finding Description
In `cert/cert_v2.go`, `unmarshalCertificateV2` performs the following sequence: [1](#0-0)  opens the outer `SEQUENCE` and reads `rawDetails`, then reads the optional curve byte via `readOptionalASN1Byte` [2](#0-1) , then reads the signature TLV: [3](#0-2) . Immediately after this, the function proceeds to `unmarshalDetails(rawDetails)`, builds the `certificateV2` struct, calls `c.validate()`, and returns — at no point is `input.Empty()` checked [4](#0-3) .

Every other ASN.1 sub-parser in this file that opens an envelope (`unmarshalDetails`) does check `b.Empty()` immediately after opening the tag, e.g. `if !b.ReadASN1(&b, TagCertDetails) || b.Empty()` [5](#0-4) , but that only guards against an empty details body, not trailing content after all known fields in the outer certificate structure have been read. Because `cryptobyte.String.ReadASN1` merely advances past the declared length of each TLV element and leaves any bytes after the last read field unconsumed in `input`, an attacker can append additional ASN.1 elements (or arbitrary bytes forming a valid-looking TLV) after the `TagCertSignature` element, still within the outer `SEQUENCE`'s declared length, and the parser will not notice or reject them.

This affects the "unknown fields must reject" invariant because two structurally different byte sequences (one with trailing garbage, one without) will both be treated as the same parsed `certificateV2` object with the same `rawDetails`, `curve`, `publicKey`, and `signature` — and thus the same `Fingerprint()` (which is computed only from those fields) and the same signature verification result via `CheckSignature`, per `Fingerprint` and `CheckSignature`: [6](#0-5) [7](#0-6) . Since these functions hash only `rawDetails + curve + publicKey (+ signature for fingerprint)`, they do not include the tail bytes, so appending extra bytes does not change the fingerprint or signature validity check, letting the same logical certificate identity be represented by multiple distinct byte-for-byte wire encodings.

### Impact Explanation
This is a parsing/format-confusion bug rather than a cryptographic bypass: an attacker who controls the raw certificate bytes they present (e.g., during handshake) can smuggle extra opaque bytes inside a certificate blob that still parses as valid and verifies its signature correctly. This does not bypass certificate authentication (the signature still covers only `rawDetails+curve+publicKey`, and CA trust chain checks are unaffected), but it does violate strict fail-closed parsing and could enable format/fingerprint ambiguity — e.g. smuggling data past cert parsing logic, or causing two byte-different inputs to be treated as identical certificates downstream (if any code path compares raw bytes rather than the computed fingerprint). No decryption, replay, or firewall bypass is enabled by this alone.

### Likelihood Explanation
Highly reproducible: any attacker who can supply certificate bytes to `unmarshalCertificateV2` (via `Certificate` unmarshalling entry points such as PEM/handshake certificate parsing in `cert/pem.go` and `cert/cert.go`) can trivially append extra bytes inside the outer SEQUENCE length after a validly-signed certificate's TLV, since the length of the outer SEQUENCE is attacker-controlled at signing time (for self-authored certs) or can be recomputed for any cert bytes the attacker crafts. No privileged access, CA key, or social engineering is required to demonstrate the parsing defect itself.

### Recommendation
Add an explicit `input.Empty()` check immediately after reading `rawSignature` (and before constructing the `certificateV2` struct) in `unmarshalCertificateV2`, returning `ErrBadFormat` if `input` still contains unread bytes:

```go
if !input.ReadASN1(&rawSignature, TagCertSignature) || rawSignature.Empty() {
    return nil, ErrBadFormat
}
if !input.Empty() {
    return nil, ErrBadFormat
}
```

### Proof of Concept
Unit test plan (to add to `cert/cert_v2_test.go`):

2. Manually re-encode the outer SEQUENCE to include extra trailing bytes after the signature TLV while still inside the SEQUENCE's declared length (e.g., append a benign OCTET STRING or raw junk bytes after the signature element, and update the outer SEQUENCE length prefix accordingly).
3. Call `unmarshalCertificateV2(taintedBytes, nil, curve)`.
4. Assert that the current implementation returns `(cert, nil)` with a non-nil certificate — demonstrating the parser incorrectly succeeds.

func (c *certificateV2) CheckSignature(key []byte) bool {
	if len(c.rawDetails) == 0 {
		return false
	}
	b := make([]byte, len(c.rawDetails)+1+len(c.publicKey))
	copy(b, c.rawDetails)
	b[len(c.rawDetails)] = byte(c.curve)
	copy(b[len(c.rawDetails)+1:], c.publicKey)

	switch c.curve {
	case Curve_CURVE25519:
		if len(key) != ed25519.PublicKeySize {
			return false //avoids a panic internal to ed25519
		}
		return ed25519.Verify(key, b, c.signature)
	case Curve_P256:
		pubKey, err := ecdsa.ParseUncompressedPublicKey(elliptic.P256(), key)
		if err != nil {
			return false
		}
		hashed := sha256.Sum256(b)
		return ecdsa.VerifyASN1(pubKey, hashed[:], c.signature)
	default:
		return false
	}
}
