Based on my investigation, I found a strong analog in `FetchIntoObjectPool`.

### Title
Missing validation that `origin` is actually a linked member of the target object pool allows cross-repository object disclosure via `FetchIntoObjectPool` - (File: internal/gitaly/service/objectpool/fetch_into_object_pool.go)

### Summary
`FetchIntoObjectPool` validates only that the `origin` and `object_pool` repositories exist and share the same storage, but never verifies that `origin` is actually the pool's primary member or is even linked to the pool at all. This mirrors the `multiHopBuyCollateral()` flaw, where a check is performed on one field (`collateralAmount`/storage-name match) while the security-relevant field (`borrowAmount`/actual relationship between `origin` and the pool) is left unchecked, letting an actor perform the sensitive action — pulling all refs/objects from an arbitrary repository into a pool they do not own — without the intended authorization relationship being established.

### Finding Description
`validateFetchIntoObjectPoolRequest` in [1](#0-0)  only checks that `origin` and the pool's `object_pool.repository` are non-nil and share a storage name. The handler then directly calls `objectPool.FetchFromOrigin(ctx, origin, ...)` with no check that `origin` is linked to, or is the originating repository of, the given object pool: [2](#0-1) .

`FetchFromOrigin` itself performs an unconditional `git fetch <originPath> +refs/*:refs/remotes/origin/*` into the pool, pulling in **all** references and reachable objects from whatever repository is passed as `origin`: [3](#0-2) . There is no cross-check against `linkedToRepository` (used by `Link`, see [4](#0-3) ) or against any recorded pool-membership relationship.

Once objects from an unrelated `origin` repository are fetched into the pool, they become permanently reachable to **every other member repository linked via alternates** to that pool (see [5](#0-4)  on dangling objects being kept alive indefinitely), and per [6](#0-5) , alternates cause references (and thus contents) of the pool to be visible to fetchers of any pool member.

### Impact Explanation
Because Gitaly's RPC-level check only validates that storage names match (an argument/config-level check unrelated to authorization), an actor who can invoke `FetchIntoObjectPool` with `Origin` set to any repository on the same storage (not necessarily one previously linked to the target object pool via `LinkRepositoryToObjectPool`) can force objects and refs from that arbitrary repository to be copied into the pool. Because pool objects are shared with every other pool member through Git alternates, this results in cross-repository object disclosure: content from a repository the caller does not otherwise have read access to (or that is meant to be isolated) becomes reachable by any repository already linked to that pool, analogous to how the missing allowance check let an attacker force a borrow action on behalf of a victim without holding the corresponding permission.

### Likelihood Explanation
Gitaly's RPC-level validation is the last line of defense for this constraint — the check is purely structural (non-nil, same storage) rather than relational, so nothing in `internal/gitaly/service/objectpool/fetch_into_object_pool.go` itself prevents supplying an `origin` unrelated to the pool. Any caller able to reach `ObjectPoolService.FetchIntoObjectPool` with attacker-influenced `Origin`/`ObjectPool` fields (e.g., through the Rails-mediated internal API surface that ultimately issues this RPC) can trigger the behavior, matching the "ordinary user's ... crafted RPC field" reachability criterion.

### Recommendation
Before calling `objectPool.FetchFromOrigin`, verify that `origin` is a legitimate member of the object pool — e.g., require `origin` to be the pool's recorded primary/origin repository, or verify `linkedToRepository(ctx, pool, origin)` similar to the check already used in `internal/git/objectpool/link.go`, rejecting the request with `FailedPrecondition`/`PermissionDenied` if the relationship does not hold.

### Proof of Concept
1. Create repository `A` (private, has sensitive commits/refs) and repository `B` on the same storage.
2. Create an object pool `P` from `B` via `CreateObjectPool` and link `B` and a public fork `C` to `P` via `LinkRepositoryToObjectPool` (see flow in [7](#0-6) ).
3. Call `FetchIntoObjectPool` with `Origin = A` and `ObjectPool = P` (same storage as `B`/`C`). The request passes `validateFetchIntoObjectPoolRequest` because it only checks storage-name equality: [1](#0-0) .
4. `FetchFromOrigin` pulls all of `A`'s refs/objects into `P` under `refs/remotes/origin/*` — see the ref-pulling behavior demonstrated in [8](#0-7) .
5. Because `C` is linked to `P` via Git alternates, `A`'s previously-inaccessible objects are now reachable through `C`'s object database, disclosing `A`'s content to anyone with read access to `C`.

```go
func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
}
```

```go
// linkedToRepository tests if a repository is linked to an object pool
func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
}
```

```markdown
## Dangling Objects

When fetching from pool members into the object pool, then any force-updated
references may cause objects in the pool to not be referenced anymore. For
normal repositories, it is perfectly fine to delete those references after a
certain time. In the context of object pools, any other member of the pool may
still use any of those unreferenced objects. Deleting them would thus
potentially cause corrupt repositories.

This issue is kind of unsolvable: there is no point in time where it's safe to
delete objects from the object pool, as we do not know which repositories may be
linked to it. And even if we knew, we cannot determine all references of all
repositories at once in a race-free manner. We thus must consider each object to
still be referenced somewhere.

As a safeguard to not lose any objects by accident, we thus create dangling
references in the object pool after the fetch in `FetchIntoObjectPool`. For each
dangling object, a reference `refs/dangling/$OID` is created which points into
the object. This assures that each object is still referenced.
```

```go
func TestFetchFromOrigin_refs(t *testing.T) {

	testWithAndWithoutTransaction(t, ctx, func(t *testing.T, cfg config.Cfg, newLocalRepo LocalRepoFactory) {
		pool, repo := setupObjectPoolWithCfg(t, ctx, cfg)

		require.NoError(t, err)

		// Verify that the object pool ain't yet got any references.
		poolPath := gittest.RepositoryPath(t, ctx, pool)

		gittest.WriteTag(t, cfg, repoPath, "annotated-tag", commitID.Revision(), gittest.WriteTagConfig{
			Message: "tag message",
		})

		// Fetch from the pool member. This should pull in all references we have just created in
		// that repository into the pool.
		require.NoError(t, pool.FetchFromOrigin(ctx, repo, newLocalRepo))

	})
```
