### Title
Address-hijack of an existing peer's PeerDB identity via self-declared `HandshakeData.addrbytes`/`port` in neighbor-of-neighbor handshakes - (File: `stackslib/src/net/neighbors/db.rs`, `stackslib/src/net/chat.rs`)

### Summary
`NeighborKey::from_handshake` builds the PeerDB lookup/write key from the sender-supplied `HandshakeData.addrbytes`/`port` fields rather than from the actual TCP socket address of the connection that delivered the message. `Neighbor::load_and_update`, used by both `add_or_schedule_replace_neighbor` (walk.rs neighbor-of-neighbor handshake flow) and the direct outbound re-key path in `handle_handshake`, uses this forged key to fetch an existing PeerDB row and overwrite its `public_key`, allowing a remote, previously-unknown peer to hijack another peer's on-disk identity.

### Finding Description
The claimed equality — "the public key stored for a given `(addrbytes, port)` frontier slot == the public key that most recently completed a handshake FROM a TCP connection actually originating at that address" — is broken.

`NeighborKey::from_handshake` (`stackslib/src/net/chat.rs:411-423`) constructs the key purely from the wire-supplied `handshake_data.addrbytes`/`handshake_data.port`, which are attacker-controlled fields inside the signed `HandshakeData` payload, not the real peer socket address (`ConversationP2P::peer_addrbytes`/`peer_port`, populated from the actual TCP connection).

`Neighbor::load_and_update` (`stackslib/src/net/chat.rs:475-516`) uses this forged key to call `PeerDB::get_peer(conn, network_id, &addr.addrbytes, addr.port)`. If a row already exists for that `(network_id, addrbytes, port)` — e.g. because a legitimate peer X previously handshook from that real address — the existing row (with its stored `public_key`) is loaded, and `handshake_update` (`chat.rs:438-465`) unconditionally sets `self.public_key = pubk` from the new, attacker-supplied `node_public_key`, with no check that the connection this message arrived on originated from X. The mutated `Neighbor` is then persisted (`save_update`) by `add_or_schedule_replace_neighbor` (`stackslib/src/net/neighbors/db.rs:368-393`) inside `handle_neighbor_handshake_accept` (`stackslib/src/net/neighbors/walk.rs:1092-1124`).

Exploit flow: attacker runs their own reachable P2P node at `attacker_ip:attacker_port`. During a normal walk step, the local node N asks some neighbor for its neighbors (`GetNeighbors`/`Neighbors`), and among the results is a `NeighborAddress` pointing at `attacker_ip:attacker_port` (the attacker can supply this address themselves by being `cur_neighbor`, or having their address gossiped). N genuinely dials `attacker_ip:attacker_port` (`neighbor_handshakes_begin`, walk.rs:979-1069) and sends a `Handshake`. The attacker's real server replies with a `HandshakeAccept` whose `HandshakeData.addrbytes`/`port` are forged to equal victim X's real, previously-known address, and whose `node_public_key` is the attacker's own key B. `handle_neighbor_handshake_accept` → `add_or_schedule_replace_neighbor` → `Neighbor::load_and_update` fetches the PeerDB row for X (keyed by the forged fields, not by the socket N actually connected to), overwrites `public_key` with B, and `save_update` persists it. `PeerDB::get_peer` for X now returns pubkey B, even though B never sent any packet from a connection sourced at X's real address.

Existing guards do not prevent this:
- `validate_handshake`/signature checks only verify the `HandshakeData` was signed by the key embedded in the same payload — they never cross-check `addrbytes`/`port` against the actual peer/socket address.
- `check_handshake_pubkey_hash` (walk.rs:1663-1680), used in the *pingback* flow, only validates that the reported public key matches the previously-expected `NeighborAddress.public_key_hash` for unsolicited/pingback connections — it is not applied in the neighbor-of-neighbor handshake path (`handle_neighbor_handshake_accept`), and even where used, it doesn't validate the `addrbytes`/`port` field of the handshake against the dialed address.
- `handle_handshake`'s direct in-conversation re-key path is gated on `self.stats.outbound` (only applies to connections we initiated), but it still keys the DB write off `NeighborKey::from_handshake(...)` (the self-reported address), not `self.to_neighbor_key()` (the actual dialed/connected address) — the same address-trust flaw exists there too.

### Impact Explanation
A remote, unprivileged attacker who merely runs a reachable P2P node can overwrite the `public_key` field of an arbitrary, already-known `(network_id, addrbytes, port)` PeerDB row belonging to a real peer they do not control, with no proof of controlling that address. This is an unauthenticated write to node state: it corrupts the frontier/PeerDB such that future traffic, gossip and neighbor discovery entries addressed to that `(addrbytes, port)` slot are attributed to the attacker's key, and any peer that trusts the local node's frontier data (e.g. via subsequent `Neighbors` gossip) may propagate this forged identity binding further. This matches the Critical category: unauthenticated write to persisted state with potential for network-wide propagation of forged peer identity data. Each handshake message the attacker sends can re-trigger the hijack, making it trivially repeatable.

### Likelihood Explanation
Preconditions: the local node must already have a PeerDB row for the victim address/port (a common steady-state condition, since well-connected relay/seed nodes are widely known and stored by many peers), and the attacker must get their own address included as a "neighbor of a neighbor" to be dialed (trivial: run a node, get crawled, or be listed by a colluding/attacker-controlled `cur_neighbor`). No secrets, no RPC access, no privileged role and no address spoofing are required — the attacker only needs to run their own reachable P2P endpoint and craft a `HandshakeData` payload with forged `addrbytes`/`port` fields, which is fully within the "run their own peer and gossip messages" unprivileged-attacker capability. The attack is repeatable at will and costs the attacker essentially nothing.

### Recommendation
Do not trust `HandshakeData.addrbytes`/`port` as the PeerDB lookup/write key. Key `Neighbor::load_and_update` (and the direct re-key path in `handle_handshake`) off the actual verified socket address of the connection (`ConversationP2P::peer_addrbytes`/`peer_port`, i.e. `convo.to_neighbor_key()`) instead of the self-reported `HandshakeData` fields, and only use the self-reported address as a secondary "advertised address" field, kept separate from the primary DB identity key. Alternatively, require that the self-reported `addrbytes`/`port` match the actual connection's address before permitting `handshake_update`/`save_update` to run, and reject/quarantine mismatches (as is already partially done in `check_handshake_pubkey_hash`, but that check needs to be extended to cover address, not just pubkey hash, and applied uniformly to all call sites of `add_or_schedule_replace_neighbor`/`load_and_update`).

### Proof of Concept
Rust net test plan (in `stackslib/src/net/tests/neighbors.rs` or a new test alongside `test_step_walk_2_neighbors_rekey`):
1. Create `TestPeer` N and legitimate `TestPeer` X (victim); have N handshake with X normally so `PeerDB::get_peer(N.peerdb, network_id, X.addrbytes, X.port)` returns `Some(peer)` with `peer.public_key == X's pubkey`.
2. Create an attacker `TestPeer` B running at a different address/port, and construct a `HandshakeAcceptData`/`HandshakeData` whose `node_public_key` is B's key but whose `addrbytes`/`port` are forged to equal X's `addrbytes`/`port`.
3. Directly invoke `PeerDBNeighborWalk::add_or_schedule_replace_neighbor` (or drive it via `handle_neighbor_handshake_accept`) with a `Preamble` from B's real connection but the forged `HandshakeData`.
4. Assert: `PeerDB::get_peer(N.peerdb.conn(), network_id, &X.addrbytes, X.port).unwrap().unwrap().public_key == B's pubkey` (not X's), proving the DB row for X's real address was silently rekeyed to B's key with no proof B controls X's address.
