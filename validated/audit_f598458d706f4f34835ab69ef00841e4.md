### Title
Virtual AMM (Bancor) Price Manipulation in TRC10 `Exchange` via Floating-Point Precision Loss - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The `PerpPair` exploit shows a class of bug where a caller manipulates the internal state of a virtual constant-function AMM with an oversized trade, then extracts more value than was deposited by acting on the distorted state. Java-tron's TRC10 `Exchange` feature implements its own virtual AMM (a Bancor-style relay-token curve) that is reachable directly from an unprivileged, signed `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`. The default (non-hardened) pricing path performs the bonding-curve math with Java `double` arithmetic instead of exact/fixed-point math, which is the exact bug class (imprecise/manipulable AMM pricing) that enabled the PerpPair theft.

### Finding Description
`ExchangeCapsule.transaction()` selects between a `ExchangeProcessor` (unsafe) and `SafeExchangeProcessor` (hardened, BigDecimal-based) depending on `dynamicStore.allowHardenExchangeCalculation()`: [1](#0-0) 

When the hardened flag is not active (it is a committee-gated `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal, off by default until voted on), every `ExchangeTransactionContract` trade is priced by `ExchangeProcessor`, which uses `double` and `Maths.pow` to compute the bonding-curve output instead of exact arithmetic: [2](#0-1) 

Because this pricing function is invoked directly by `ExchangeTransactionActuator.execute()` for any account, an unprivileged transaction broadcaster can perform a sequence of trades (analogous to the PerpPair attacker's oversized long) that exploits floating-point rounding in `exchangeToSupply`/`exchangeFromSupply` to skew the two virtual token balances stored in the `Exchange`/`ExchangeV2` capsule: [3](#0-2) 

The only safeguards on a trade are that `tokenQuant`/`tokenExpected` are positive and that the post-trade balance stays under `EXCHANGE_BALANCE_LIMIT` — there is no check that bounds how far a single trade can move the price, and no slippage/manipulation-resistance mechanism analogous to a TWAP: [4](#0-3) 

The existence of the separate `SafeExchangeProcessor`/`allowHardenExchangeCalculation` hardening path is itself evidence that the raw floating-point curve was recognized as producing exploitable/inconsistent pricing, but that hardening is a governance-gated opt-in rather than the default behavior: [5](#0-4) 

### Impact Explanation
Like the PerpPair vAMM, the `Exchange` capsule tracks token reserves purely as internal ledger state (`firstTokenBalance`/`secondTokenBalance`) that is trusted for pricing all subsequent trades, injects, and withdrawals: `ExchangeInjectActuator`/`ExchangeWithdrawActuator` compute pro-rata amounts directly from these same balances: [6](#0-5) [7](#0-6) 
If a trade sequence pushes these balances into a floating-point rounding regime that is favorable to the attacker (e.g. extreme ratios, or balances near `EXCHANGE_BALANCE_LIMIT` where `double` precision is lossy relative to `long` token units), an attacker can extract TRX/TRC10 tokens deposited by other traders or by the exchange creator — i.e., unauthorized theft of funds from a shared on-chain liquidity pool, reachable purely by broadcasting `ExchangeTransactionContract` transactions.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the exchange's `ALLOW_HARDEN_EXCHANGE_CALCULATION` flag to still be disabled (a chain/committee-controlled setting) and requires an attacker to find/construct trade sequences and balance magnitudes where the `double`-based curve diverges materially from the exact result. No special privilege is needed beyond funding an `ExchangeTransactionContract`/`ExchangeCreateContract`, which any account can broadcast.

### Recommendation
Make the exact/BigDecimal (`SafeExchangeProcessor`) calculation path mandatory rather than governance-gated, or otherwise prove that `ExchangeProcessor`'s `double`-based curve cannot diverge from the exact bonding-curve result by more than 1 unit for all valid balances up to `EXCHANGE_BALANCE_LIMIT`. Add explicit fuzz/property tests comparing `ExchangeProcessor` and `SafeExchangeProcessor` outputs across the full valid balance/quant range, and consider adding a maximum-price-impact-per-trade check in `ExchangeTransactionActuator.doValidate()` to blunt single-transaction AMM skewing regardless of arithmetic precision.

### Proof of Concept
Not independently reproduced. Analysis is based on static review of `ExchangeProcessor`'s floating-point implementation of the Bancor formula versus the exact `SafeExchangeProcessor`, and confirms the actuator paths (`ExchangeTransactionActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`) are reachable by any signed transaction and operate on shared, price-sensitive reserve state. Concretely demonstrating a profitable divergence requires numerically searching `sellTokenBalance`/`sellTokenQuant` pairs (up to `EXCHANGE_BALANCE_LIMIT = 1_000_000_000_000_000`) where `ExchangeProcessor.exchange()` and `SafeExchangeProcessor.exchange()` disagree by more than rounding-down-by-one, which was not performed here due to the scope of static code review.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
