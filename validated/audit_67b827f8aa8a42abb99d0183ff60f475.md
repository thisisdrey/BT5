### Title
Out-of-bounds read when parsing malformed ZIP central directory entries in ijar - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in Bazel's vendored `ijar` tool parses ZIP central directory records read directly from an mmap'd, attacker-controlled `.jar`/`.zip` file without validating that the declared `file_name_length`, `extra_field_length`, or `file_comment_length` fields actually fit within the bounds of the mapped file, unlike its sibling `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before every field read.

### Finding Description
`ProcessLocalFileEntry` (third_party/ijar/zip.cc) defensively calls `EnsureRemaining(...)` before advancing its cursor `p` past attacker-supplied lengths: [1](#0-0) . In contrast, `ProcessCentralDirEntry`, which reads the equivalent length fields from the central directory, performs no such check before advancing `p` and dereferencing memory: [2](#0-1) . The subsequent `memcpy` into the fixed-size `filename` buffer, and the extra-field walking loop, both operate on pointers derived from these unvalidated lengths: [3](#0-2) .

Because the whole zip file is mapped via `MappedInputFile`/mmap and `p`/`extra_p` are raw pointers into that mapping, a crafted central directory entry with an oversized `file_name_length`, `extra_field_length`, or a `data_size` inside an extra field that pushes `extra_p` past the end of the mapped region causes `get_u2le`/`get_u4le`/`get_u8le`/`memcpy` to read past the end of the mapped file — an out-of-bounds read, directly analogous to the PJSIP multipart parser reading past the end of a malformed body because inner length fields were trusted without bounds checking.

This code path is exercised whenever Bazel invokes `ijar` to build interface jars for `java_library`/`java_import` targets, including jars originating from external repositories (e.g. `http_jar`, Maven artifacts fetched via `http_archive`/`maven_install`). A declared `sha256`/integrity check on the download only certifies that the bytes match what the hostile publisher intended to publish — it does not, and cannot, prevent the publisher itself from crafting a structurally malformed but hash-valid ZIP central directory to trigger this parser bug once Bazel processes the artifact with `ijar`.

### Impact Explanation
An out-of-bounds read can crash the `ijar` process (denial of the build) or, depending on memory layout, leak adjacent heap/mmap data (e.g., portions of other build inputs or the file cache) into what is written into the generated interface jar, since the copied `filename` buffer or extra-field derived sizes influence subsequent processing/output.

### Likelihood Explanation
Any unprivileged actor who can publish an artifact URL that a `http_archive`/`http_jar`/module extension consumes (a malicious mirror, a compromised or intentionally hostile third-party host, or an untrusted branch's fetched dependency) can trigger this by shipping a `.jar` with a malformed central directory. No MITM or credential access is required — the attacker controls the artifact bytes from the origin, and the checksum in the lockfile/BUILD file is computed over that same malicious content, so it validates rather than blocks the payload.

### Recommendation
Add `EnsureRemaining`-style bounds checks in `ProcessCentralDirEntry` (and the extra-field walking loop) before reading `file_name_length`, `extra_field_length`, `file_comment_length`, and each extra-field's `data_size`, mirroring the checks already present in `ProcessLocalFileEntry`, and reject/error out on any central directory entry whose declared sizes would read past the mapped file's end.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style reproduction:
1. Construct a minimal valid ZIP/JAR (as in `output_jar_simple_test.cc`'s `CreateZipWithMalformedExtraField` helper, which already demonstrates the pattern for local/central headers) but instead craft a Central Directory Header whose `file_name_length` (or an inner extra-field `payload_size`) exceeds the remaining bytes to the end of the mapped file. [4](#0-3) 
2. Run `ijar` (via `java_library`/`java_import` referencing this crafted jar, or directly invoking the `ijar` binary) on this file.
3. Observe an ASan-detected heap-buffer-overflow/out-of-bounds read (or a crash) inside `InputZipFile::ProcessCentralDirEntry`, since no `EnsureRemaining` check exists there to reject the malformed lengths before they are read via `memcpy`/`get_u2le`/`get_u8le`. [5](#0-4)

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);

  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());

  // 4. End of Central Directory (EOCD)
