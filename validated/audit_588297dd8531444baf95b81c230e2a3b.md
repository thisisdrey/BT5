### Title
Missing content-hash verification allows attacker-controlled attachment content to be stored under attacker's own hash - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a peer's HTTP response into a `GetAttachmentResponse` and inserts `response.attachment` into `self.attachments` without ever checking that `response.attachment.hash()` matches the `request.content_hash` that was actually requested. Any peer answering a `GET /v2/attachments/<H>` request can therefore return arbitrary bytes `C` where `Hash160::from_data(&C) != H`, and the node will accept and instantiate it.

### Finding Description
The broken equality is `request.content_hash == response.attachment.hash()`. In [1](#0-0) , `extend_with_attachments` iterates `results.succeeded.drain()`, which pairs each `AttachmentRequest` (carrying the expected `content_hash`) with the raw `StacksHttpResponse`. It calls `response.decode_atlas_get_attachment()` (defined in [2](#0-1) ), which only JSON-deserializes the body into `GetAttachmentResponse{attachment: Attachment{content}}` — no hash comparison to `request.content_hash` occurs anywhere in this decode step or in the calling loop. The decoded `Attachment` is inserted directly into `self.attachments: HashSet<Attachment>` at line 548, discarding the association with the original `request.content_hash` entirely.

Downstream, in `AttachmentsDownloader::run`, the `Done` state drains `context.attachments` and, for each attachment, computes `attachment.hash()` (i.e., `Hash160::from_data` of the attacker-supplied bytes) and unconditionally calls `network.atlasdb.insert_instantiated_attachment(&attachment)` [3](#0-2) . This call happens regardless of whether `find_all_attachment_instances(&attachment.hash())` found any matching legitimate instance — so a completely bogus attachment (whose hash matches nothing on-chain) still gets written into the AtlasDB.

The attacker's exact message: respond to the node's `GET /v2/attachments/<H>` with HTTP 200 and a JSON body `{"attachment":{"content":"<hex of attacker bytes C>"}}` where `Hash160::from_data(&C) != H`. Because `AttachmentRequest`'s only pairing to a peer response is via `results.succeeded.insert(request, Some(response))` keyed by the original request object (see `BatchedRequestsState::try_proceed` at [4](#0-3) ), and `extend_with_attachments` never re-derives or checks the hash, the mismatch is never caught before insertion.

No other guard exists in this path: `decode_atlas_get_attachment` only checks JSON structure validity, not content integrity against a hash.

### Impact Explanation
This is an unauthenticated write of attacker-chosen bytes into `AtlasDB`, consuming a slot toward whatever attachment storage limits exist and potentially interfering with tracking of legitimate uninstantiated/instantiated attachments. Any peer the node syncs Atlas attachments from (an outbound sync peer providing a `data_url`) can trigger this on every attachment fetch it services, making it repeatable per request. This matches the Critical category of "unauthenticated write to state."

### Likelihood Explanation
Preconditions are modest and attacker-achievable without any privileged role: the node must have queued a real `content_hash` H from a legitimate BNS/name commitment (this happens naturally via `AttachmentsBatch::track_attachment` for any registered name with an attachment), and the node must pick the attacker's URL as one of its peer sources for that attachment (attacker just needs to be an outbound sync peer offering a `data_url` and claiming to have the attachment in its inventory response). The attacker only needs to run a normal peer node and respond to HTTP GETs — no secret, no privileged role, fully remotely reachable via the node's outbound Atlas attachment-fetch logic.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, compute `response.attachment.hash()` and compare it against `request.content_hash` before inserting into `self.attachments`. On mismatch, treat it as a failed request (`report.bump_failed_requests()`), do not insert, and optionally penalize/deregister the offending peer.

### Proof of Concept
1. Construct an `AttachmentRequest { content_hash: H, sources, .. }` where `H` is a fixed `Hash160`.
2. Construct a `StacksHttpResponse` whose body JSON-encodes `GetAttachmentResponse { attachment: Attachment { content: b"malicious".to_vec() } }`, ensuring `Hash160::from_data(b"malicious") != H`.
3. Build a `BatchedRequestsResult<AttachmentRequest>` with `succeeded.insert(request, Some(response))`.
4. Call `AttachmentsBatchStateContext::extend_with_attachments(context, &mut results)`.
5. Assert that `context.attachments` contains an `Attachment` whose `.hash() != H`, demonstrating the accepted mismatch — this attachment would subsequently be written via `insert_instantiated_attachment` in `AttachmentsDownloader::run`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
