### Title
Integer overflow in `ExtraField::size()` bypasses zip extra-field boundary checks, enabling heap buffer corruption in `singlejar` - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`ExtraField::size()` computes the byte length of a ZIP "extra field" record as a 16-bit sum of a fixed header size and an attacker-controlled 16-bit payload length. When the payload length is near `0xFFFF`, this sum overflows the `uint16_t` return type and wraps to a small value. Every boundary check in the codebase that validates whether an extra field fits inside the Central Directory Header (CDH) / Local Header (LH) extra-fields region relies on this wrapped `size()`, so a crafted extra field can defeat the "does this record fit in the buffer" check while other code paths (`attr_count()`, `space_needed()`) independently re-derive a size from the un-truncated `payload_size()`. This produces an inconsistent, attacker-controllable size accounting that flows into buffer-allocation arithmetic in `OutputJar::AppendToDirectoryBuffer`, potentially causing an undersized heap allocation followed by larger `memcpy` writes — the same fundamental bug class as CVE-2016-2177 ("incorrectly uses pointer/size arithmetic for heap-buffer boundary checks ... integer overflow").

### Finding Description
`ExtraField::size()` is defined as: [1](#0-0) 

Because the return type is `uint16_t` and `payload_size()` is itself `uint16_t` (max `0xFFFF`), `sizeof(ExtraField) + payload_size()` (i.e. `4 + payload_size()`) overflows for any `payload_size()` in `[0xFFFC, 0xFFFF]`, wrapping to `[0, 3]`.

This wrapped value is exactly what `ExtraField::find()` uses to bound-check and advance through attacker-supplied extra-field records: [2](#0-1) 

The same wrapped `size()` is used by `OutputJar::AppendToDirectoryBuffer` to validate each extra field while re-serializing an input jar's Central Directory: [3](#0-2) 

Crucially, other members of the same class family compute a *second, independent* size from the raw (non-truncated) `payload_size()`: [4](#0-3) 

`Zip64ExtraField::attr_count()` and `space_needed()` are fed directly into the buffer-size arithmetic in `AppendToDirectoryBuffer`: [5](#0-4) 

Because `zip64_attr_count`/`space_needed()` (derived from the true, un-wrapped `payload_size()`) can be large while the field simultaneously passes the truncated `size()`-based boundary check, `out_ef_size` and `out_cdh_size` (both computed via `uint16_t`/mixed arithmetic combining these two inconsistent size sources) can be miscalculated — including unsigned underflow of `out_ef_size`. `ReserveCdr(out_cdh_size)` then allocates a buffer whose size no longer matches what the subsequent `memcpy` calls at lines 922, 930, and 944 actually write, producing a heap buffer write outside the allocation.

An existing regression test, `MalformedExtraField`, exercises only the "declared size legitimately exceeds the buffer" case with `payload_size(0xf000)` (61440, well below the overflow threshold), which correctly triggers the intended `diag_errx("malformed extra field...")` abort: [6](#0-5) 

This test does not cover `payload_size()` values in `[0xFFFC, 0xFFFF]` that trigger the 16-bit wraparound, so the overflow path in `ExtraField::size()` is unguarded and unexercised.

### Impact Explanation
`singlejar`/`ijar` are native C++ tools invoked as part of ordinary Bazel Java build actions (e.g., building a `deploy.jar`, merging jars, generating interface jars) whenever a build consumes a `.jar` (directly or as a dependency, e.g. via `http_jar`, `http_archive`, or a vendored/pre-built jar checked in on an untrusted branch). Because the file's own SHA-256/integrity hash is chosen and published by the attacker along with the malicious bytes, standard checksum pinning does nothing to stop this: it only proves the victim downloaded exactly the bytes the attacker crafted, not that those bytes are semantically well-formed. A hostile jar can therefore reach this parsing code with default flags on a stock Bazel release, causing heap corruption inside a build tool process — beyond a simple crash/DoS, this is a memory-safety violation (buffer overflow) whose severity depends on heap layout, potentially affecting the produced artifact or corrupting the tool's process.

### Likelihood Explanation
Triggering the bug requires only crafting a ZIP/JAR whose Central Directory Header contains an extra field (e.g., tagged as the Zip64 extension) with `payload_size` set to a value in `[0xFFFC, 0xFFFF]`. No cooperation from Bazel infrastructure, no privileged access, and no bypass of the download integrity mechanism is needed — the attacker simply publishes this crafted jar as the dependency artifact and its own matching checksum. The precondition is that the victim's build actually processes the jar through `singlejar`'s CDH-rewriting path (`AppendToDirectoryBuffer`), which is a common code path for jar merging/deploy-jar assembly.

### Recommendation
- Change `ExtraField::size()` to compute and return a widened type (e.g. `uint32_t`/`size_t`), and explicitly reject (fail closed, as the existing `diag_errx` path does) any extra field whose header-plus-payload size cannot be represented without overflow.
- Make `Zip64ExtraField::attr_count()`/`space_needed()` and `UnixTimeExtraField::timestamp_count()` consistent with the same widened, overflow-checked size computation used for the boundary check, so no code path can derive a different notion of "this field's size" than the one used to validate it fits the buffer.
- Add a regression test using `payload_size()` values in `[0xFFFC, 0xFFFF]` to confirm the wraparound is rejected the same way the existing `MalformedExtraField` test rejects out-of-range non-wrapping sizes.

### Proof of Concept
Extend the existing `output_jar_simple_test.cc` harness (which already builds a malformed-extra-field ZIP by hand) with a variant of `CreateZipWithMalformedExtraField()` that sets:
```cpp
ef2->signature(1);              // Zip64 extension tag
ef2->payload_size(0xFFFE);      // triggers sizeof(ExtraField)+payload_size() == 2 (wrap)
```
Then run the same `OutputJar::Doit()` path used by the `MalformedExtraField` test: [7](#0-6) 
Unlike the existing test (which expects `ASSERT_DEATH(..., "malformed extra field")`), this crafted input is expected — per the current code — to *pass* the boundary check in `AppendToDirectoryBuffer` (no `diag_errx`), while `zip64_ef->attr_count()` and `Zip64ExtraField::space_needed()` compute values derived from the un-wrapped `0xFFFE`, demonstrating the inconsistent size accounting feeding `ReserveCdr`'s allocation size versus the subsequent `memcpy` write sizes (best observed/confirmed by running under AddressSanitizer/UBSan, which will report a heap-buffer-overflow rather than the intended `malformed extra field` abort).

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
