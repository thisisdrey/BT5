### Title
`UnfreezeBalanceV2Actuator.checkUnfreezeBalance` validates unfreeze amount against total `FrozenV2` balance without subtracting the portion already delegated, potentially allowing double-use of locked capital - (File: `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java`)

### Summary
The external report describes a "claimable amount" being computed from a gross pool value (`total seller deposits + premium accrued`) without subtracting amounts that are already locked/committed elsewhere (`locked capital`, `default payouts`), leading to over-payment. The closest reachable analog in java-tron is `UnfreezeBalanceV2Actuator.checkUnfreezeBalance`, which validates an unfreeze request against the raw `FreezeV2.getAmount()` value for a resource type without subtracting any portion of that frozen balance that is currently delegated (locked) to another account.

### Finding Description
`checkUnfreezeBalance` looks up `frozenAmount` purely from the account's `FrozenV2List` entry for the given resource type and allows unfreezing up to that full amount: [1](#0-0) 

The actual weight/resource accounting elsewhere in the codebase distinguishes between self-frozen balance and delegated balance via `getFrozenV2BalanceWithDelegated(...)`, which is used when adjusting total network/energy/tron-power weight in the same actuator: [2](#0-1) 

This indicates that `FreezeV2.getAmount()` (used in `checkUnfreezeBalance`) and the "with delegated" variant are tracked as different concepts, but `checkUnfreezeBalance` only consults the former without confirming whether part of that amount is presently delegated out to a receiver account (analogous to "locked capital" in the report that should have been subtracted before allowing a claim/withdrawal).

I was unable to fully confirm, within the available tool budget, whether `FreezeV2.getAmount()` as stored already excludes delegated-out balance (i.e., whether delegation moves value out of this field into a separate delegated field before `checkUnfreezeBalance` runs) or whether it remains part of the same pool that `checkUnfreezeBalance` validates against. I attempted to trace `DelegateResourceActuator` and `AccountCapsule`'s `addFrozenBalanceForBandwidthV2` / delegated-field accessors to settle this but ran out of iterations before completing that verification.

### Impact Explanation
If `FreezeV2.getAmount()` includes value that has already been delegated to a receiver (and thus is "locked" for use by that receiver, analogous to `locked capital` in the report), then a caller could unfreeze/reclaim balance while the corresponding `DelegatedResourceCapsule` and the receiver's acquired resource remain intact, effectively creating duplicated/unbacked resource entitlement (owner regains liquid TRX while the receiver still holds usable bandwidth/energy backed by the same capital). This would match the report's core impact category of unbacked balance / miscalculated claimable amount.

### Likelihood Explanation
This is only a genuine vulnerability if the "unlocked" pool checked in `checkUnfreezeBalance` structurally double-counts delegated capital — a fact that requires deeper verification of `AccountCapsule`'s frozen/delegated bookkeeping (`addFrozenBalanceForBandwidthV2`, `getFrozenV2BalanceForBandwidth`, and the corresponding delegate/undelegate actuators) than I was able to complete. Given java-tron's resource-delegation model is heavily tested (`FreezeV2Test`, `UnDelegateResourceActuatorTest`) and the codebase explicitly separates "self" vs "with delegated" balances in the weight-adjustment code, it is plausible this separation is already correctly enforced elsewhere (e.g., in `DelegateResourceActuator`'s validate, which likely already deducts delegated amounts from delegatable self-balance), making this analog weak/unconfirmed rather than a proven vulnerability.

### Recommendation
Before treating this as confirmed, a background engineer should:
1. Trace `AccountCapsule.addFrozenBalanceForBandwidthV2` / `getFrozenV2BalanceForBandwidth` / `getDelegatedFrozenV2BalanceForBandwidth` to determine whether `FreezeV2.getAmount()` used in `checkUnfreezeBalance` already excludes delegated-out balance.
2. If it does not, `checkUnfreezeBalance` in `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java` should validate the unfreeze amount against `frozenAmount - delegatedOutAmount` for the given resource type, mirroring the "total capital = deposits - locked capital" subtraction missing in the original report.
3. Add/extend test coverage in `UnfreezeBalanceV2ActuatorTest` for the scenario: freeze X, delegate a portion of X to a receiver, then attempt to unfreeze X in full — verifying it is rejected or correctly capped to the non-delegated remainder.

### Proof of Concept
Not constructed — this requires confirming the underlying `FrozenV2`/delegated-balance bookkeeping semantics (see "Finding Description" caveat) before a concrete PoC transaction sequence (freeze → delegate → unfreeze) can be asserted to succeed and produce unbacked balance. Given the uncertainty, this should be treated as a **candidate for further investigation** rather than a confirmed exploit.

  public boolean checkUnfreezeBalance(AccountCapsule accountCapsule,
                                      final UnfreezeBalanceV2Contract unfreezeBalanceV2Contract,
                                      ResourceCode freezeType) {
    boolean checkOk = false;

    long frozenAmount = 0L;
    List<FreezeV2> freezeV2List = accountCapsule.getFrozenV2List();
    for (FreezeV2 freezeV2 : freezeV2List) {
      if (freezeV2.getType().equals(freezeType)) {
        frozenAmount = freezeV2.getAmount();
        break;
      }
    }

    if (unfreezeBalanceV2Contract.getUnfreezeBalance() > 0
        && unfreezeBalanceV2Contract.getUnfreezeBalance() <= frozenAmount) {
      checkOk = true;
    }

    return checkOk;
  }

  public void updateTotalResourceWeight(AccountCapsule accountCapsule,
                                        final UnfreezeBalanceV2Contract unfreezeBalanceV2Contract,
                                        long unfreezeBalance) {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    switch (unfreezeBalanceV2Contract.getResource()) {
      case BANDWIDTH:
        long oldNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForBandwidthV2(-unfreezeBalance);
        long newNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        dynamicStore.addTotalNetWeight(newNetWeight - oldNetWeight);
        break;
      case ENERGY:
        long oldEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForEnergyV2(-unfreezeBalance);
        long newEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        dynamicStore.addTotalEnergyWeight(newEnergyWeight - oldEnergyWeight);
        break;
      case TRON_POWER:
        long oldTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        accountCapsule.addFrozenForTronPowerV2(-unfreezeBalance);
        long newTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        dynamicStore.addTotalTronPowerWeight(newTPWeight - oldTPWeight);
        break;
      default:
        //this should never happen
        break;
    }
  }
