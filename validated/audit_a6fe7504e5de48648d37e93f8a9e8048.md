### Title
`ValidateMultiSign` precompile counts the same signer's weight multiple times via signature malleability - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` TVM precompiled contract (invoked by any smart contract via the `validatemultisign` opcode helper) is supposed to sum distinct signer weights until a permission's threshold is met. Its de-duplication logic checks whether an address has already been counted, but when a second, *different* signature byte-string recovers to that *same* address, the code does not skip it — it falls through and adds the weight again, exactly mirroring the Monero `check_reserve_proof` pattern where duplicate rows are summed without rejecting duplicate identities.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute`, for every extracted signature the code recovers an address and merges it with the raw signature bytes: [1](#0-0) 

The dedup check is:
```java
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```

If `recoveredAddr` was already seen but the exact `sign` bytes were not (i.e., a *different* valid signature recovering to the same address), the inner `continue` is not taken. The code only calls `MUtil.checkCPUTime()` — which is a no-op unless a specific hard-fork flag is active [2](#0-1)  — and then proceeds to add `weight` again into `totalWeight`. Because ECDSA signatures are malleable ((r, s) and (r, n−s) with an adjusted recovery id both validly recover to the same address for the same message hash), an attacker controlling a single private key can supply two distinct signature encodings for the same address and have that one key's weight counted twice (or more, within `MAX_SIZE = 5` slots) toward `totalWeight`.

This is the same "duplicate entries inflate an accumulated total" bug class as the external Monero report: a verifier iterates a list of externally supplied "proof" items, checks a per-item constraint, and unconditionally sums a value per item without asserting global uniqueness of the underlying identity.

### Impact Explanation
`ValidateMultiSign` is the intended TVM primitive for smart contracts (e.g., custodial/escrow/multisig-wallet contracts) to check whether a caller-supplied signature set meets a TRON account's `Permission` threshold. Inflating `totalWeight` lets an attacker satisfy a multi-signature threshold (e.g., 2-of-3, 3-of-5) using fewer distinct private keys than the account owner configured — as few as one key duplicated via signature malleability — bypassing the intended authorization policy for any contract that relies on this precompile to gate privileged actions (fund releases, governance actions, etc.). This is a business-logic authorization bypass with concrete potential for unauthorized account operations / theft of funds gated behind multisig contracts.

### Likelihood Explanation
Reachable by any unprivileged account: any contract call that exercises the `validatemultisign` precompile with attacker-supplied signature bytes reaches this path. Producing a second malleable signature from one's own private key is a well-known, low-cost operation, so no special privilege or trusted role is required — only knowledge of at least one valid key in the target permission set (which for many contract designs is itself the attacker's own key, since the goal is to "prove" more distinct approvals than actually exist).

### Recommendation
Change the dedup check in `ValidateMultiSign.execute` to strictly reject re-use of a `recoveredAddr` regardless of whether the raw signature bytes differ — i.e., once an address has been credited weight once, any further signature (malleable or not) recovering to that same address must be skipped/ignored rather than falling through to `totalWeight += weight`. Equivalently, track only `recoveredAddr` in a de-dup set and `continue` immediately whenever it's already present, removing the `checkCPUTime()`-gated fallthrough path entirely.

### Proof of Concept
1. Deploy or call a contract that invokes `validatemultisign(address, permissionId, data, signatures[])` where `permission` has threshold 2 and two keys, `keyA` (weight 1) and `keyB` (weight 1).
2. Attacker controls only `keyA`. Compute `toSign = sha256(merge(address, permissionId, data))`.
3. Produce signature1 = `keyA.sign(toSign)` → `(r, s, v)`.
4. Produce signature2 = malleable variant of signature1: `(r, n−s, v')` (standard ECDSA malleability transform) — both recover to `keyA`'s address.
5. Call the precompile with `signatures = [signature1, signature2]`.
6. In the loop: signature1 sets `recoveredAddr = keyA`, adds weight 1, `totalWeight = 1`. Signature2 recovers `keyA` again; `matrixContains(executedSignList, keyA)` is true, but `matrixContains(executedSignList, sign)` (the merged bytes) is false because `sign` bytes differ (different `s`), so the `continue` is skipped; `MUtil.checkCPUTime()` no-ops (pre-fork); weight 1 is added again → `totalWeight = 2`.
7. `totalWeight (2) >= permission.getThreshold() (2)` → precompile returns `DATA_ONE`, i.e., "valid multisig," despite only one real distinct key having signed.
