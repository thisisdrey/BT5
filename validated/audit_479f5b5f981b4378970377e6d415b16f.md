## Finding: Accumulated protocol fees are burned locally on XCM-send-success, not on destination-confirmed receipt, and can be permanently trapped

### Title
Fee/revenue forwarding via `TeleportForwarderForAccountId32::forward` settles (burns) locally before destination-side deposit is confirmed, permanently trapping accumulated fees on remote rejection - (File: `polkadot/xcm/xcm-builder/src/forwarder.rs`)

### Summary
The external report's core defect is: protocol-owned value that is *supposed* to end up in a specific destination account that will use it as intended (a liquidity buffer) is instead only correctly computed/withdrawn locally, but never actually reaches — or is not guaranteed to reach — the destination account. The local analog is `pallet_accumulate_and_forward`, which collects transaction fees, dust, and coretime revenue into an `accumulation_account` and periodically "forwards" them by teleport to a destination chain via `TeleportForwarderForAccountId32::forward` [1](#0-0) . Settlement (burning locally, emitting `ForwardSucceeded`) happens as soon as the *local* XCM executor reports `Outcome::Complete`, not when the destination actually credits the funds [2](#0-1) .

### Finding Description
`Pallet::on_idle` periodically checks the accumulation account's reducible balance and, once above `MinTransferAmount`, calls `T::Forwarder::forward(accumulation_account, available_funds)` [3](#0-2) . The concrete `Forwarder` used on Asset Hub, People, Coretime, Collectives, BridgeHub-Westend and the Westend relay chain is `TeleportForwarderForAccountId32` [4](#0-3) .

`forward()` builds a local XCM program (`WithdrawAsset` + `InitiateTransfer{Teleport}`) and executes it via `XcmExecutor::prepare_and_execute` inside a storage transaction: if the *local* outcome is `Outcome::Complete`, the transaction is committed (funds withdrawn/burned locally and the outbound message queued) and `Ok(())` is returned; only a *local* execution failure rolls back [5](#0-4) . The pallet then treats this `Ok(())` as final success and fires `ForwardSucceeded` [6](#0-5) .

The module's own doc comment states the consequence explicitly: *"Local-execution failures roll back all local state changes. Once the local executor reports success, the message is queued and any destination-side rejection results in trapped assets at the destination with no automatic recovery path."* [7](#0-6) . Nothing in `on_idle` or `forward()` verifies that the remote `DepositAsset { beneficiary: StagingLocation }` actually succeeds; there is no receipt, callback, or `ReportError`/`QueryResponse` wiring to confirm delivery, and no retry or reconciliation logic for a trapped-asset outcome.

### Impact Explanation
Just as the original report's rollover fee is correctly computed but never reaches the vault buffer meant to settle PnL, here fees/dust/coretime revenue are correctly accumulated and withdrawn locally, but the destination chain's crediting of that value is not atomically tied to the local settlement. If the destination-side `DepositAsset` fails — e.g., the staging beneficiary account is not yet funded to existential deposit, remote weight is exhausted under `UnpaidExecution{weight_limit: Unlimited}` racing actual block weight limits, or an asset filter mismatch — the assets become "trapped" (`AssetsTrapped`), require a bespoke governance/manual `claim_assets` call with exact knowledge of the trapped asset/ticket, and total issuance has already been reduced locally with no destination-side mint materializing into usable balance. This is a real, permanent loss/lock of protocol revenue that was meant to fund a destination pot (Treasury-like/buffer account), matching the "permanent user-fund or bridge-state lock" impact category.

### Likelihood Explanation
No malicious actor, governance action, or privileged role is required — this is an unprivileged runtime automation (`on_idle`) with a documented, acknowledged failure mode. It can be triggered by ordinary operational conditions: a staging/beneficiary account not pre-funded at the time of the periodic forward, transient destination-chain congestion exceeding the unlimited-but-practically-bounded remote weight, or any change to the destination's accepted asset/weight configuration that the source pallet is unaware of. Because `forward()` treats local `Outcome::Complete` as final and burns funds accordingly, this can recur every `TransferPeriod` without any safeguard against repeat trapping.

### Recommendation
Do not treat local `Outcome::Complete` as final settlement of value transfer. Either:
- Require a destination-side acknowledgement (e.g., XCM `ReportError`/`QueryResponse`) before considering the forward complete and only then finalize/burn, or
- Make the remote program itself un-trappable by depositing into an account that always exists (with a defensive fallback other than raw `DepositAsset` to a possibly-unfunded beneficiary), or
- Integrate automatic reconciliation with `pallet_xcm`'s trapped-asset registry so a failed forward is detected and retried/claimed automatically rather than requiring manual, out-of-band governance intervention.

### Proof of Concept
1. Configure a system parachain (e.g., People-Westend) with `pallet_accumulate_and_forward` and `TeleportForwarderForAccountId32` as documented, with `StagingLocation` pointing at a beneficiary account on the destination that is *not* pre-funded with the existential deposit.
2. Let ordinary transaction fees/dust accumulate in `accumulation_account()` past `MinTransferAmount` [8](#0-7) .
3. On the next `TransferPeriod` boundary, `on_idle` calls `forward()`, which executes the local `WithdrawAsset`/`InitiateTransfer{Teleport}` program; local execution reports `Outcome::Complete`, so funds are burned locally and `ForwardSucceeded` is emitted [2](#0-1) .
4. The destination chain processes the incoming `ReceiveTeleportedAsset` + `DepositAsset` to the unfunded beneficiary; deposit fails ED check, assets are trapped (`AssetsTrapped`) per the documented behavior [7](#0-6) .
5. Result: value is removed from source-chain issuance and never becomes usable balance at the destination; recovering it requires a manual `claim_assets` call with exact asset/ticket knowledge, with no automatic path in the pallet.

	fn forward(source: AccountId, amount: Balance) -> Result<(), ()> {
		let dest = Dest::get();
		let asset = Asset { id: AssetId(NativeAsset::get()), fun: Fungible(amount.into()) };
		let beneficiary: Location = StagingLocation::get().into_location();

		let remote_xcm = Xcm(vec![DepositAsset { assets: Wild(AllCounted(1)), beneficiary }]);

		// The XCM flow: `ReceiveTeleportedAsset → AliasOrigin(source) → UnpaidExecution →
		// DepositAsset`. `preserve_origin: true` causes `InitiateTransfer` to prepend
		// `AliasOrigin(source_location)` to the remote XCM.
		let xcm: Xcm<XcmConfig::RuntimeCall> = Xcm(vec![
			UnpaidExecution { weight_limit: WeightLimit::Unlimited, check_origin: None },
			DescendOrigin(Junction::AccountId32 { network: None, id: source.into() }.into()),
			WithdrawAsset(asset.into()),
			InitiateTransfer {
				destination: dest,
				remote_fees: None,
				preserve_origin: true,
				assets: BoundedVec::truncate_from(alloc::vec![AssetTransferFilter::Teleport(
					Wild(AllCounted(1))
				),]),
				remote_xcm,
			},
		]);

		with_transaction(|| -> TransactionOutcome<Result<(), DispatchError>> {
			let outcome = XcmExecutor::<XcmConfig>::prepare_and_execute(
				Location::here(),
				xcm,
				&mut [0u8; 32],
				Weight::MAX,
				Weight::MAX,
			);

			match outcome {
				Outcome::Complete { .. } => TransactionOutcome::Commit(Ok(())),
				exec_error => {
					tracing::debug!(
						target: LOG_TARGET,
						?exec_error,
						"accumulate-forward: XCM execution failed"
					);

					TransactionOutcome::Rollback(Err(DispatchError::Other("XCM execution failed")))
				},
			}
		})
		.map_err(|_| ())
	}
