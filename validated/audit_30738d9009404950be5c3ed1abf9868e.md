### Title
`ExchangeCapsule.transaction` / `SafeExchangeProcessor` can revert with `ArithmeticException` for otherwise-valid exchange orders, blocking token exchange - (File: `chainbase/src/main/java/org/tron/core/capsule/SafeExchangeProcessor.java`)

### Summary
This is a direct analog of the reported Cobb–Douglas bug class: an arithmetic function whose documented purpose is to compute a value for "valid" bounded inputs, but which is implemented in a way that can revert (throw) for inputs that pass all upstream validation. In java-tron, `ExchangeTransactionActuator` and `ExchangeInjectActuator` call `ExchangeCapsule.transaction(...)`, which — when the "hardened" bancor calculation path is enabled — delegates to `SafeExchangeProcessor.exchange()`.

### Finding Description
`ExchangeTransactionActuator.doValidate()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` during **validation**, after only checking that `tokenQuant > 0`, `tokenExpected > 0`, token balances are non-zero, and the resulting balance stays under `getExchangeBalanceLimit()`. [1](#0-0) 

When `allowHardenExchangeCalculation()` is enabled, `ExchangeCapsule.transaction` uses `SafeExchangeProcessor.INSTANCE` instead of the legacy double-based `ExchangeProcessor`. [2](#0-1) 

`SafeExchangeProcessor.exchangeFromSupply()` computes a `BigDecimal` result and converts it with `.longValueExact()`: [3](#0-2) 

`BigDecimal.longValueExact()` throws an unchecked `ArithmeticException` if the scaled value does not fit into a `long` (magnitude overflow), even though the value was already rounded to scale 0 via `RoundingMode.DOWN`. Because the whole exponential Bancor-formula computation (`Math.pow` over `BigDecimal`, values raised to the 2000th power) is highly sensitive to the `supply`/`balance` ratio, there exist combinations of legitimate `firstTokenBalance`, `secondTokenBalance`, and `tokenQuant` (all bounded only by `getExchangeBalanceLimit()`, which can be set arbitrarily high by chain parameters) that make `exchangeBalance` exceed `Long.MAX_VALUE`, triggering this uncaught overflow.

The `execute()` path does catch `ArithmeticException` and converts it to a `ContractExeException`, turning the transaction into a `FAILED` result rather than a node crash: [4](#0-3) 
`validate()` similarly wraps it into `ContractValidateException`: [5](#0-4) 

So in the current `execute()`/`validate()` call sites the exception is caught and does not crash the node — however, it is thrown as an unchecked exception from a `pure` computational routine that has no documented input-bound contract (unlike `MixinExchangeCore.cobbDouglas`'s explicit "Figure 16.1" bounds), meaning any caller of `ExchangeCapsule.transaction`/`SafeExchangeProcessor.exchange` that does not wrap it in a try/catch for `ArithmeticException` (e.g., a new caller, another actuator, or a TVM native-contract wrapper added in the future) would propagate this unchecked exception uncontrolled. This mirrors the root cause in the report: an arithmetic library routine (Bancor/Cobb–Douglas-style formula) silently reverts/throws for seemingly in-bounds inputs because its true numeric domain (long-range overflow after `pow(x, 2000)`) is far narrower than the externally-enforced validation bounds (`tokenQuant > 0`, balance limit), and this constraint is undocumented in the code.

### Impact Explanation
An `ExchangeTransactionContract` or `ExchangeInjectContract` broadcast by any unprivileged account can be crafted (by choosing large but limit-compliant `firstTokenBalance`/`secondTokenBalance` ratios and `tokenQuant`) to make `SafeExchangeProcessor.exchangeFromSupply` overflow a `long`, causing the actuator's `execute`/`validate` to fail unexpectedly for parameters that satisfy all documented/enforced bounds (`tokenQuant>0`, balance under `exchangeBalanceLimit`). This can make an exchange pool effectively "stuck" for certain trade sizes/ratios (denial of the exchange operation for legitimate orders), and demonstrates the arithmetic routine has an undocumented, narrower-than-enforced valid domain — the same root-cause class as the reported bug.

### Likelihood Explanation
Medium. Triggering requires `allowHardenExchangeCalculation()` to be enabled (a chain parameter toggle) and specific large-value/ratio combinations near the `Long.MAX_VALUE` boundary after the Bancor exponential computation; it is reachable directly by any order placer via a single signed `ExchangeTransactionContract`/`ExchangeInjectContract`, with no special privilege needed, but requires finding the right numeric inputs (similar to how Echidna found triggering inputs for `cobbDouglas`).

### Recommendation
- Document and enforce explicit, provably-safe input bounds for `ExchangeCapsule.transaction`/`SafeExchangeProcessor.exchange` and its two sub-steps (`exchangeToSupply`, `exchangeFromSupply`), analogous to the `bound` constants recommended for `cobbDouglas`.
- In `SafeExchangeProcessor.exchangeFromSupply`, avoid unchecked `longValueExact()` on attacker-influenced compounding exponentials; instead clamp/validate the computed `BigDecimal` against `Long.MAX_VALUE`/`MIN_VALUE` before conversion and throw a well-defined `ContractValidateException`/`ContractExeException` with a clear message rather than relying on `ArithmeticException` propagation.
- Add fuzz/property-based tests (Echidna-equivalent for JVM, e.g., jqwik/QuickTheories) asserting `SafeExchangeProcessor.exchange` never throws for any input within the currently enforced validation bounds (`tokenQuant>0`, balances within `exchangeBalanceLimit`), or otherwise reduce `exchangeBalanceLimit`'s effective safe range to match the arithmetic routine's real domain.

### Proof of Concept
1. Enable `allowHardenExchangeCalculation` (hardened Bancor calc path) via the relevant proposal/dynamic parameter.
2. Create an exchange pair via `ExchangeCreateContract` with `firstTokenBalance`/`secondTokenBalance` set near the configured `exchangeBalanceLimit()` (a large but permitted value).
3. Submit an `ExchangeTransactionContract` (or `ExchangeInjectContract`) with a `tokenQuant` chosen so that, per the Bancor formula in `SafeExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` [6](#0-5) 
the intermediate `base.pow(2000)`-scaled `exchangeBalance` BigDecimal exceeds `Long.MAX_VALUE` after `setScale(0, DOWN)`.
4. Observe `exchangeBalance.longValueExact()` throws `ArithmeticException`, which the actuator surfaces as `FAILED`/`ContractValidateException` even though `tokenQuant>0` and the resulting balance remains under `exchangeBalanceLimit` — i.e., a "valid-per-documented-bounds" input reverts, matching the report's root-cause pattern.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
