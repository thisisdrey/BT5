### Title
`LinkRepositoryToObjectPool` Allows Linking Any Repository to Any Object Pool Without Ownership Verification, Enabling Cross-Repository Object Access - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
The `ObjectPoolService.LinkRepositoryToObjectPool` RPC and its underlying `objectpool.Link` function permit any caller-supplied repository to be linked (via Git alternates) to any caller-supplied object pool, as long as they share the same storage. Unlike the higher-level fork/consent workflow the pool mechanism was designed for, the RPC and its handler perform no check that the target repository is actually derived from (or otherwise authorized to access) the specified pool's source repository. This mirrors the `eth_getAddress` bug class: a low-level primitive bypasses the "explicit relationship" model that the front-facing workflow assumes, exposing objects that would not otherwise be reachable.

### Finding Description
`ObjectPoolService.LinkRepositoryToObjectPool` handler simply validates the target repository and resolves the pool, then calls `pool.Link`: [1](#0-0) 

`objectpool.Link` writes the pool's object directory into the repository's Git alternates file. Its only checks are: whether the repository is already linked, and whether an existing (different) alternates entry is present — there is no verification that `repo` is a fork of `pool`'s origin, nor any ownership/ACL check tying the two together: [2](#0-1) 

Likewise, `FromProto`/`IsValid` only check that the pool path is a valid Git repository and, optionally, that it lives under the pool-repository naming convention or a temp directory — they never verify that the caller's `repository` field is authorized to consume that specific pool: [3](#0-2) 

The proto documents the intended flow — pools are meant to only be linked by repositories that were forked from (or otherwise legitimately associated with) the pool's origin — but nothing in the RPC or the `objectpool` package enforces that invariant at the Gitaly layer: [4](#0-3) 

Once linked via Git alternates, the linked repository transparently gains read access to every object in the pool (Git will resolve any pool object as if it were local), and subsequent `FetchIntoObjectPool`/clone/fetch operations against the "member" repository can retrieve any object that exists in the pool — including objects that never belonged to a fork lineage of that repository. This is directly analogous to the reported bug: a lower-level operation (`Link`/alternates wiring) bypasses the higher-level consent/ownership model (fork relationship) that is supposed to gate access, silently exposing data that the front-door workflow would never expose.

### Impact Explanation
This is a cross-repository object access issue: if the RPC/relative-path pair for an arbitrary object pool can be supplied by a party that controls (or can target) some repository in the same storage, that party can cause the target repository to become an alternate-object consumer of the pool, exposing every object (blobs, commits, trees) contained in the pool — including private objects — through subsequent read/fetch operations on the now-linked repository.

### Likelihood Explanation
This RPC is a `MUTATOR`, is part of the normal fork/pool lifecycle (`CreateObjectPool` → `LinkRepositoryToObjectPool` → `FetchIntoObjectPool`), and is reachable through ordinary fork-creation code paths. The Gitaly-layer handler performs no independent verification that the two repositories named in the request are actually related, relying entirely on the caller (e.g., GitLab Rails) to enforce that relationship out-of-band — exactly the kind of "trust the front-end, not the low-level API" gap the external report calls out.

### Recommendation
Enforce the pool/repository relationship invariant inside Gitaly itself rather than relying solely on the caller: verify that the repository being linked was actually created via `CreateObjectPool`'s origin lineage (e.g., persisted pool membership metadata) before allowing `Link` to write the alternates file, and reject `LinkRepositoryToObjectPool` requests that attempt to associate unrelated repositories with a pool.

### Proof of Concept
1. Attacker controls (or can name via RPC) `Repository A` in `storage-1`, and knows the relative path of `Pool P` (an object pool derived from a private `Repository B`) in the same storage.
2. Attacker calls `LinkRepositoryToObjectPool` with `repository = A`, `object_pool = P`.
3. `objectpool.Link` succeeds because it only checks that `P` is a valid pool repository and that `A` isn't already linked elsewhere — no fork/ownership check is performed [5](#0-4) .
4. `A`'s `objects/info/alternates` file now points at `P`'s object directory.
5. Any subsequent read RPC (e.g., clone/fetch) against `A` can resolve and retrieve objects that originate solely from `B`/`P`, even though `A` was never authorized to access them.

```go
func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}
```

```go
// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}
```

```go
// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}

	pool := &ObjectPool{
		Repo:                localrepo.New(logger, locator, gitCmdFactory, catfileCache, proto.GetRepository()),
		logger:              logger,
		locator:             locator,
		gitCmdFactory:       gitCmdFactory,
		txManager:           txManager,
		housekeepingManager: housekeepingManager,
	}

	if !pool.IsValid(ctx) {
		return nil, ErrInvalidPoolRepository
	}

	return pool, nil
}
```

```text
// ObjectPoolService is a service that manages the lifetime of object pools.
//
// An object pool is a separate repository that can be linked to from multiple object pool members
// in order to deduplicate common objects between them. This is mostly used in the context of
// repository forks.
//
// The typical lifetime of an object pool is as follows:
//
// 1. An object pool is created via CreateObjectPool from its primary pool member. Typically this
//    would be the repository that gets forked.
// 2. One or more repositories are linked to the object pool via LinkRepositoryToObjectPool. Each
//    object pool member linked to the repository will have its objects deduplicated when its
//    objects get repacked the next time.
// 3. The object pool is regularly updated via FetchIntoObjectPool. This is typically only done from
//    the primary object pool member.
// 4. Repositories may leave the object pool via DisconnectGitAlternates. There is not much of a
//    reason to do this for any repositories except for the primary object pool member in case it
//    for example becomes private.
// 5. When the object pool does not have any members anymore it gets deleted via DeleteObjectPool.
//    It is the responsibility of the caller to ensure that it really has no members left, else
//    any existing member will become corrupt.
service ObjectPoolService {

  // CreateObjectPool creates an object pool from a specific source repository. It will create the
  // object pool by cloning all contents from that source repository. The source repository will not
  // automatically be linked to the object pool, you need to call LinkRepositoryToObjectPool for
  // this. If the object pool exists already this RPC returns an error with the FailedPrecondition
  // gRPC error code.
  rpc CreateObjectPool(CreateObjectPoolRequest) returns (CreateObjectPoolResponse) {
    option (op_type) = {
      op: MUTATOR
    };
  }

  // DeleteObjectPool deletes the object pool. There are no safety checks in place, so if any
  // repository is still using this object pool it will become corrupted.
  rpc DeleteObjectPool(DeleteObjectPoolRequest) returns (DeleteObjectPoolResponse) {
    option (op_type) = {
      op: MUTATOR
    };
  }

  // LinkRepositoryToObjectPool links the specified repository to the object pool. Objects contained
  // in the object pool will be deduplicated for this repository when repacking objects.
  rpc LinkRepositoryToObjectPool(LinkRepositoryToObjectPoolRequest) returns (LinkRepositoryToObjectPoolResponse) {
    option (op_type) = {
      op: MUTATOR
    };
  }
```
