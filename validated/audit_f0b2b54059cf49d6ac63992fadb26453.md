Based on my research, I found a valid analog to the reported bug class in Praefect's per-repository routing logic.

### Title
Unvalidated `DefaultReplicationFactor` vs. dynamic storage count causes slice-bounds panic in `assignRepositoryToNodes` - ([File: internal/praefect/router_per_repository.go])

### Summary
The reported bug is a classic "validated at construction, not validated at update" pattern: `MultipleWinners`'s constructor requires `_numberOfWinners > 0` but its setter `setNumberOfWinners` does not, allowing an invalid state to reach a later operation that assumes the invariant holds. The same class of bug exists in Praefect's `VirtualStorage.DefaultReplicationFactor` handling: it is validated once, at config load time, against the number of nodes present in that snapshot of the config, but the value is never re-validated against the storages actually available at routing time, which can differ due to config reload/dynamic node set changes.

### Finding Description
`Config.Validate()` enforces that `DefaultReplicationFactor` cannot exceed the number of configured nodes for a virtual storage at load time: [1](#0-0) . This is the "constructor" analog to `MultipleWinners`'s constructor check.

However, this validated value is later consumed in `PerRepositoryRouter.assignRepositoryToNodes` via `r.defaultReplicationFactors[virtualStorage]` [2](#0-1) , with no re-validation against the current set of storages/connections available to the router at call time: [3](#0-2) 

Note that `secondaryNodes` is built from `r.conns[virtualStorage]` — i.e., all currently-configured connections for the virtual storage, not the config snapshot that was validated at startup. The code then does:
```
secondaryNodes = secondaryNodes[:replicationFactor-1]
```
with no bounds check that `replicationFactor-1 <= len(secondaryNodes)`. If the number of nodes configured for a virtual storage decreases (e.g., a node is removed via config change/hot-reload, or the router's `conns` map is otherwise reduced) after `DefaultReplicationFactor` was set/validated against the old, larger node count, this slice expression will panic with "slice bounds out of range."

This is directly analogous to `setNumberOfWinners` bypassing the constructor's `numberOfWinners > 0` check and later causing `distribute()` to throw: here, a value validated once against one state of the system is used unconditionally later against a different, unvalidated state, leading to an unhandled runtime panic in an RPC-serving code path (`assignRepositoryToNodes` is invoked while resolving primary/secondary routing for repository-mutating RPCs such as `CreateRepository`/`CreateFork`, as seen in `coordinator_test.go`'s `TestStreamDirector_repo_creation`) [4](#0-3) .

### Impact Explanation
A panic inside `assignRepositoryToNodes`, which is called during stream routing for repository-mutating RPCs, will crash or abort the handling goroutine for that request. Depending on how the gRPC server recovers panics, this could take down the whole Praefect process's ability to serve routing for that virtual storage, denying service to ordinary users performing routine operations like creating repositories or forks — a denial-of-service of an RPC handler triggered by any ordinary user's request once the precondition (reduced storage count vs. stale `DefaultReplicationFactor`) exists.

### Likelihood Explanation
This requires an operational/administrative precondition — removing/losing a node from a virtual storage's `conns` while `DefaultReplicationFactor` was set based on a larger storage count — which is a realistic operational scenario (scaling down, decommissioning nodes, or transient connection map changes) rather than a purely malicious end-user action. The trigger itself (any repository-creation RPC from any ordinary user) requires no special privilege, matching the report's framing of "a careless... admin" creating conditions that cause the operation to fail/DoS, without the exploit itself requiring privileged actions.

### Recommendation
In `assignRepositoryToNodes`, clamp or bounds-check `replicationFactor-1` against `len(secondaryNodes)` before slicing (e.g., `min(replicationFactor-1, len(secondaryNodes))`), or re-validate the derived replication factor against the router's current live connection set before use, similar to how `AssignmentStore.SetReplicationFactor` re-validates against `len(candidateStorages)` at call time [5](#0-4) .

### Proof of Concept
1. Configure a virtual storage with 3 nodes and `default_replication_factor = 3` (valid at startup per `Config.Validate()`).
2. Trigger a config reload / node removal that reduces the virtual storage's node set (and thus `r.conns[virtualStorage]`) to 2 nodes, without Praefect re-running `Config.Validate()` against the new node count for the in-memory router state.
3. Issue an ordinary repository-creation RPC (e.g., `CreateRepository`) routed through `PerRepositoryRouter`. In `assignRepositoryToNodes`, `secondaryNodes` will now contain only 1 entry (2 nodes minus the primary), but `replicationFactor-1` = 2, causing `secondaryNodes[:2]` to panic with "slice bounds out of range."

Note: I was not able to fully verify within the index whether Praefect's node/connection set (`r.conns`) can actually change at runtime without a full process restart (which would also reload and re-validate `DefaultReplicationFactor` consistently) — this affects the practical likelihood of the precondition arising. If node/connection maps are only ever rebuilt together with a fresh, consistent config validation pass, this reduces to a lower-likelihood edge case; if hot-reload of node sets independent of `DefaultReplicationFactor` revalidation is supported, the likelihood is higher. Confirming this would require deeper tracing of Praefect's config reload path, which was not conclusively found in the indexed code.
