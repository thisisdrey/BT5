## Finding [1](#0-0) 

### Title
Unbounded array allocation from attacker-controlled ABI length field in precompiled-contract calldata decoding - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray`, `extractBytes32Array`, and `extractSigArray` decode a dynamic-array length directly from attacker-supplied `DataWord` calldata and immediately allocate a Java array sized by that value, before any check ties the decoded count to the amount of calldata actually supplied.

### Finding Description
`extractBytes32Array` reads `int len = words[offset].intValueSafe();` and then does `new byte[len][]` with no upper bound check against `words.length` or the real calldata size [2](#0-1) . `extractBytesArray` does the same after only checking `offset > words.length - 1` (i.e. that at least one more word exists), then allocates `new byte[len][]` from an attacker-controlled `len` before the per-item `bytesOffset`/`bytesLen` values (also attacker-controlled) are validated [3](#0-2) . `extractSigArray` follows the identical pattern [4](#0-3) .

This is the same bug class as the Envoy Gateway report: a small, cheap, fully attacker-controlled input word drives allocation of an output structure whose size is completely decoupled from the bytes actually present. `getEnergyForData(byte[] data)` on these precompiles (e.g. `Identity`, `Sha256`) charges energy proportional to `data.length` — the raw calldata size — not to any decoded array-length field [5](#0-4) . If the precompile that consumes `extractBytesArray`/`extractSigArray` prices energy the same way (proportional to calldata bytes rather than the decoded count), an attacker can submit a tiny calldata blob (a few 32-byte words) with the length word set to a large value (up to `Integer.MAX_VALUE`), triggering allocation of an array of that many references (`byte[Integer.MAX_VALUE][]` ≈ tens of GB just for the reference table) for negligible energy cost.

Test file evidence (`ValidateMultiSignContractTest.java`, referencing TIP-854/legacy decoder behavior for a signature-array precompile) indicates one or more real precompiled contracts on the multi-sign validation path decode signature arrays through this exact helper family [6](#0-5) . I was not able to fully trace the exact call site(s) invoking `extractBytesArray`/`extractSigArray` and confirm whether any additional guard clamps `len` before allocation for every caller — the codebase index only surfaced the helper definitions and their generic `isValidAbiEncoding` structural check [7](#0-6) , which validates overall data-length divisibility using fixed `headerWords`/`itemWords` constants but does not bound the dynamically-decoded `len` value read from calldata at runtime. Confirming the precise reachable precompile address and its exact energy formula requires reading the full precompile `execute()` bodies, which exceeded what the index returned.

### Impact Explanation
If reachable without a prior bound check, a single crafted TVM contract call to the affected precompiled contract can force the node to attempt a multi-gigabyte array allocation from a few bytes of calldata, resulting in `OutOfMemoryError` and crashing/hanging the executing FullNode/SR — a persistent, cheap, cross-node denial-of-service analogous to the Envoy Gateway gzip-bomb issue (CWE-789, availability impact).

### Likelihood Explanation
Likelihood is uncertain because I could not verify from the index whether the concrete precompile(s) calling these helpers perform additional length validation before invoking them, or whether `intValueSafe()` clamps to a smaller safe bound. This should be validated by reading the full call sites in `PrecompiledContracts.java` and `DataWord.intValueSafe()`.

### Recommendation
Bound the decoded `len` in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` against the actual number of remaining words in `words` (or a small protocol-defined maximum) before allocating, and ensure energy costs for any precompile using these helpers scale with the decoded array length, not just raw calldata length.

### Proof of Concept
Not verified end-to-end due to inability to confirm the exact precompile entry point and its energy accounting in this pass; a concrete PoC would call the affected precompile with minimal calldata whose embedded array-length word is set to a large value (e.g. `0x7fffffff`) and observe allocation failure/OOM.
