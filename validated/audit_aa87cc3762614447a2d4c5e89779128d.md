Audit Report

## Title
Relayer reward is paid and `PendingOrder` is removed even when the Ethereum delivery receipt reports `success: false` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt` decoded from the `InboundMessageDispatched` Ethereum event carries a `success: bool` field, but `Pallet::process_delivery_receipt` never inspects it before crediting the relayer reward and permanently deleting the `PendingOrder`. This causes relayer rewards to be paid and delivery bookkeeping to be finalized for messages whose Ethereum-side dispatch actually reverted.

## Finding Description
`submit_delivery_receipt` verifies the event log/proof via `T::Verifier::verify` and decodes it into a `DeliveryReceipt` (which includes `success`), then calls `Self::process_delivery_receipt(relayer, receipt)` at [1](#0-0) . Inside `process_delivery_receipt`, the function checks `receipt.gateway`, resolves the `reward_account`, fetches the `PendingOrder` by `receipt.nonce`, pays `order.fee` via `T::RewardPayment::register_reward` whenever `order.fee > 0`, and unconditionally calls `<PendingOrders<T>>::remove(nonce)`, emitting `Event::MessageDelivered` regardless of outcome, as seen at [2](#0-1) . The `success` field is never read anywhere in this code path. Since the event log is cryptographically verified by `T::Verifier::verify` before decoding, a normal relayer relaying a genuine Ethereum log with `success = false` (e.g., a reverted command execution) still flows through the same unconditional reward + removal logic — no existing guard distinguishes success from failure.

## Impact Explanation
This matches the "receipts and payout state must only advance after ... execution ... succeed atomically" pivot: relayers are rewarded (`order.fee` paid via `register_reward`) for deliveries that failed on Ethereum, and the `PendingOrder` for `nonce` is permanently deleted with no remaining record to retry, refund, or reconcile the failed delivery — an unbacked/incorrect payout and an unrecoverable loss of delivery-status state absent a governance/storage-migration intervention.

## Likelihood Explanation
This is triggered by any legitimate `InboundMessageDispatched` event with `success = false`, a normal expected occurrence when a Gateway-side command execution reverts on Ethereum — not requiring a malicious relayer, since any relayer submitting the genuine, correctly proven receipt through the public `submit_delivery_receipt` extrinsic triggers this path every time such a receipt appears.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only pay the reward and remove the `PendingOrder` when `true`; when `false`, skip the reward payment and either retain/mark the order for retry/reconciliation or emit a distinct failure event instead of `MessageDelivered`.

			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward

					&reward_account,

					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });
