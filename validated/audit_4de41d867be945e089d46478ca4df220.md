<br>### Title
`transfer_to_new_account` / `transfer_to_new_account_pda` do not validate `new_authority`, permanently bricking the migrated account and locking all its funds - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
### Finding Description
The external report's bug class is: a user-facing instruction accepts a destination/handler parameter without validating it, and once the message/transfer is committed there is no recovery path, causing funds to become permanently stuck. `Handler.cross_chain_erc20_settlement` fails to whitelist-check `to_handler`, and once tokens are locked/burned toward that bad destination, the failure cannot be signaled back and the transaction is permanently `Pending`.

The marginfi-v2 analog is the `transfer_to_new_account` (and its PDA variant `transfer_to_new_account_pda`) instruction. The account's authority calls this instruction to move all balances from `old_marginfi_account` to a fresh `new_marginfi_account`, setting `new_authority` as the new account's owner: [1](#0-0) 

The `new_authority` account is explicitly annotated `/// CHECK: WARN: New authority is completely unchecked` and is never validated to be non-default, non-zero, or otherwise sane before it is written into the new account and the old account is disabled: [2](#0-1) 

The same pattern exists in the PDA variant: [3](#0-2) 

Crucially, the off-chain CLI tooling (`p0-cli`) *does* perform this exact validation before submitting the instruction, confirming the protocol's own documentation/tooling expects this check to exist: [4](#0-3) 

but the on-chain program itself has no equivalent guard. If `new_authority` is passed as `Pubkey::default()` (or any other unrecoverable pubkey with no known private key, e.g. a burn address), the transaction succeeds: the old account is irreversibly disabled and its `lending_account` is zeroed (`finalize_migrated_old_account`), while all of its former balances now live in `new_account`, whose `authority` field is set to the unrecoverable pubkey. No entity can ever produce a valid signature for `Pubkey::default()`, so no future `deposit`/`withdraw`/`borrow`/`repay` instruction (which all require `has_one = authority` / `is_signer_authorized` matching the signer) can ever succeed against that account. `MarginfiAccountSetFreeze`-based admin recovery does not help here since the account is not frozen; it is just permanently orphaned with an authority nobody controls, exactly mirroring the "permanently stuck / cannot be handled" impact described in the source report.

### Impact Explanation
This causes complete, permanent loss of all collateral and open positions transferred into the new account. Unlike a simple user mistake that can be corrected by retrying (e.g. sending to a wrong-but-valid wallet still recoverable by that wallet's owner), setting `new_authority` to a pubkey with no corresponding private key makes the funds unconditionally and permanently irretrievable — no admin instruction, freeze mechanism, or bankruptcy/liquidation path restores access, since none of those flows change `authority` on a non-frozen, non-liquidatable (fully collateralized) account. This matches the "permanent lock/freeze" impact category validated for this bug class.

### Likelihood Explanation
This is reachable by any ordinary account authority using only the unprivileged, permissionless `transfer_to_new_account` / `transfer_to_new_account_pda` instructions — no admin or validator role is required. It requires only that the caller (or the client software constructing the transaction) supplies a bad `new_authority`, which is plausible given that a wallet integration, buggy client, or copy-paste error could pass `Pubkey::default()` or another value with no known key, especially since the on-chain program performs no defense-in-depth check that the equivalent CLI path already performs. Because the CLI itself guards against exactly this input, it's a known relevant failure mode.

### Recommendation
Add an on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` that rejects `new_authority == Pubkey::default()` (and optionally other known-unusable/system pubkeys), mirroring the CLI's existing guard:
```rust
check!(
    ctx.accounts.new_authority.key() != Pubkey::default(),
    MarginfiError::InvalidAuthority // or similar
);
```
This should be placed before `initialize_migrated_account` is called and before the old account is disabled, so the transaction reverts cleanly rather than completing an irreversible migration to an inaccessible authority.

### Proof of Concept
1. User owns `old_marginfi_account` with active deposits (e.g. SOL/USDC balances).
2. User (or a buggy/malicious client) submits `transfer_to_new_account` with:
   - `old_marginfi_account` = their account,
   - `new_marginfi_account` = a fresh keypair,
   - `new_authority` = `Pubkey::default()` (System Program ID / all-zero pubkey — no private key exists for it).
3. The instruction succeeds: [5](#0-4)  old account is disabled and zeroed, new account holds all the old balances with `authority = Pubkey::default()`.
4. Any subsequent attempt to `lending_account_withdraw`, `lending_account_borrow`, `lending_account_repay`, etc. on `new_marginfi_account` requires a signer matching `authority` via `is_signer_authorized`/`has_one = authority` checks used throughout the account instructions (e.g. see the same authorization pattern reused for `transfer_to_new_account` itself at lines 131-144). Since no signature can ever be produced for `Pubkey::default()`, these all fail with `Unauthorized` forever.
5. Result: all funds in `new_marginfi_account` are permanently locked with no recovery path, replicating the "permanently stuck" impact from the source report caused by an unvalidated destination parameter.
