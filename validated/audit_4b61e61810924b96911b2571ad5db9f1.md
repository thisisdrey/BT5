### Title
Shared-pool proportional usage/resource accounting in `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` allows first-mover extraction of resource-usage credit from other delegators - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
The reported OpenQ bug is a "first mover take all" refund because the contract computes the amount refundable to any single depositor from a **shared pool balance** (`current balance − locked balance`) instead of tracking each depositor's individual claim. The first depositor to call `refund()` drains the shared, un-partitioned pool, leaving later depositors with nothing.

The closest reachable analog in java-tron is the resource-usage transfer logic inside `UnDelegateResourceActuator` (and its TVM twin `UnDelegateResourceProcessor`), reachable directly from an unprivileged, signed `UnDelegateResourceContract` transaction or `undelegateResource` TVM opcode call. When a receiver account has received BANDWIDTH/ENERGY delegations from **multiple different owners**, the amount of "used resource" (`netUsage`/`energyUsage`) that gets clawed back to an un-delegating owner is computed as a *proportional share of the receiver's aggregate usage*, using the receiver's **total combined frozen/delegated balance** as the denominator — not a per-owner ledger of how much of that usage was actually caused by that owner's delegation.

### Finding Description
In `UnDelegateResourceActuator.execute()` (and identically in `UnDelegateResourceProcessor.execute()`): [1](#0-0) 

```java
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * ((double) (dynamicStore.getTotalNetLimit()) / dynamicStore.getTotalNetWeight()));
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
transferUsage = min(unDelegateMaxUsage, transferUsage);
receiverCapsule.addAcquiredDelegatedFrozenV2BalanceForBandwidth(-unDelegateBalance);
```

`receiverCapsule.getNetUsage()` and `receiverCapsule.getAllFrozenBalanceForBandwidth()` are aggregate, account-level values that mix contributions from **every** delegator (and the receiver's own frozen balance), exactly like the OpenQ bounty contract mixing every funder's deposit into one balance. There is no per-`(owner, receiver)` ledger of how much of the receiver's consumed bandwidth/energy is attributable to a specific delegator's frozen balance — the `DelegatedResourceCapsule` (keyed by owner+receiver) only tracks frozen principal, not consumed usage.

Because `transferUsage` is computed from the *current* aggregate `netUsage`/`getAllFrozenBalanceForBandwidth()` snapshot at the moment of each individual `UnDelegateResourceContract` execution, the owner who calls `UnDelegateResource` **first** claims a proportional share of the *entire* receiver's current usage pool (up to `unDelegateMaxUsage`), which reduces `receiverCapsule.getNetUsage()`/`getAllFrozenBalanceForBandwidth()` for everyone who comes after. Subsequent delegators calling `UnDelegateResource` for the same receiver recompute their share against an already-reduced pool, so the sequence in which independent, unrelated delegators broadcast their `UnDelegateResourceContract` transactions determines how much of the receiver's usage credit each one recovers — mirroring the "first depositor drains the shared pool" pattern from the OpenQ report.

Note: the field is used as a denominator to *pro-rate a resource credit*, not TRX principal, so the code cannot literally transfer more TRX than was delegated (`unDelegateBalance` itself is validated against the caller's own `DelegatedResourceCapsule` in `validate()`, see lines around [2](#0-1) ). The impact is therefore confined to the *distribution of accrued bandwidth/energy usage credit* among unrelated delegators of the same receiver, not a direct principal-balance theft.

### Impact Explanation
This causes an unfair, non-deterministic re-allocation of consumed BANDWIDTH/ENERGY usage credit between unrelated delegators who happen to delegate to the same receiver. A delegator whose `UnDelegateResource` transaction lands first can claw back a disproportionate share of the receiver's current usage (reducing the shared `netUsage`/`energyUsage` pool), while a delegator who calls afterward for the same receiver may recover far less usage credit than their delegation actually caused — or none, if the pool has already been reduced to `unDelegateMaxUsage` bounds by the earlier caller. This can be manipulated intentionally by an attacker who also has resources delegated to the same receiver, front-running/racing a legitimate delegator's undelegate transaction in the same or adjacent blocks to skew the split of `getNetUsage()`/`getEnergyUsage()` reclaimed to their own account, effectively degrading the resource-usage accounting fairness for other delegators of a shared receiver (e.g., a popular contract account receiving delegations from many stakers).

### Likelihood Explanation
The path is reachable by any unprivileged account holding a delegation to any receiver via a normal signed `UnDelegateResourceContract` transaction, or via the TVM `undelegateResource` opcode from a smart contract — no special privilege is required. The precondition (multiple independent owners delegating BANDWIDTH/ENERGY to the same receiver, which then consumes some usage) is a very common, expected pattern in TRON's stake-and-delegate resource model, making exploitation conditions realistically attainable. However, exploitation requires transaction-ordering control (or mere coincidental timing) between two unrelated delegators' undelegate calls, and the actual "prize" is a shift in resource-usage attribution rather than direct fund theft, which somewhat limits severity relative to the original OpenQ TVL-loss scenario.

### Recommendation
Track resource usage per `(owner, receiver)` delegation relationship rather than pro-rating from the receiver's aggregate `netUsage`/`energyUsage` and combined frozen balance. Persist consumed-usage attribution in the `DelegatedResourceCapsule` (or an equivalent per-relationship structure) at delegation/consumption time so that `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` can return exactly the usage credit caused by that specific delegator's balance, independent of the order in which other delegators to the same receiver undelegate.

### Proof of Concept
1. Owner A delegates 1,000,000 TRX worth of BANDWIDTH to Receiver R (`DelegateResourceContract`).
2. Owner B independently delegates 1,000,000 TRX worth of BANDWIDTH to the same Receiver R.
3. Receiver R (e.g., via TVM contract calls funded by delegated bandwidth) consumes a large amount of `netUsage`.
4. Owner A broadcasts `UnDelegateResourceContract` first: `transferUsage` is computed from R's *full* current `netUsage` and `getAllFrozenBalanceForBandwidth()` (sum of A+B's delegation), letting A reclaim a usage credit proportional to the combined pool, reducing R's `netUsage` accordingly [3](#0-2) .
5. Owner B then broadcasts `UnDelegateResourceContract`: the denominator `getAllFrozenBalanceForBandwidth()` and `netUsage` have already shrunk due to A's earlier call, so B recovers a different (generally smaller, non-reproducible) usage credit than if B had gone first — demonstrating that transaction order among unrelated delegators of the same receiver determines each party's recovered usage credit, the same "first mover" asymmetry pattern described in the OpenQ report.

Note: I was not able to execute this scenario in a live node from this analysis; the conclusion is based on static code reading of `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` and the aggregate nature of `AccountCapsule.getNetUsage()`/`getAllFrozenBalanceForBandwidth()`. Confirming the exact magnitude of exploitable skew would require running the existing `UnDelegateResourceActuatorTest`/`FreezeV2Test` scenarios with two distinct owners delegating to one receiver and comparing outcomes for different call orders.
