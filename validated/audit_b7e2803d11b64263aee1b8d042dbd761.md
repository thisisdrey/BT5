### Title
Witness rewards are permanently lost/unclaimable when a witness has zero recorded votes for a cycle - ([File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java])

### Summary
`MortgageService.payReward` credits block/transaction-fee rewards into a per-cycle, per-witness reward bucket via `DelegationStore.addReward` regardless of how many votes that witness currently has. When voters later withdraw their reward share via `MortgageService.withdrawReward`/`computeReward`, or when the "Vi" reward algorithm accumulates the witness's reward-per-vote index via `DelegationStore.accumulateWitnessVi`, any reward recorded for a cycle in which the witness's total vote count is `0` is silently dropped — never distributed to any account and never rescuable by anyone (owner or otherwise). This is the same class of bug as the reported "NULL epoch" issue: value is deposited into a bucket that becomes permanently unclaimable if there are no eligible claimants at the time of accounting.

### Finding Description
Rewards are added unconditionally in `payReward`: [1](#0-0) 

They are read back and distributed in `computeReward`, which explicitly skips (drops) the reward when the witness's total recorded vote for that cycle is `0`: [2](#0-1) 

The newer "Vi" (value-index) reward algorithm has the same behavior baked directly into the accumulator: if `reward == 0 || voteCount == 0`, the accumulated Vi for that cycle is not incremented (or even recorded when it would remain 0), meaning the reward amount that was added via `addReward` for that witness/cycle is never converted into a claimable per-vote value: [3](#0-2) 

The same skip logic is duplicated in `RewardViCalService.accumulateWitnessVi`: [4](#0-3) 

The per-cycle vote snapshot itself is written unconditionally at every maintenance cycle boundary for every known witness (not just active ones), via `MaintenanceManager.doMaintenance`: [5](#0-4) 

Because `getWitnessVote`/`getWitnessVi` return `REMARK`/`ZERO` for missing entries and `computeReward`/`accumulateWitnessVi` treat a `0` vote count as "nothing to distribute," any reward TRX (whether from block rewards, transaction fee rewards, or standby witness pay) that lands in a cycle bucket for a witness with `voteCount == 0` at that cycle boundary is stranded: it is never added to any account's `allowance`, never rolled forward to a future cycle, and there is no owner/maintenance function anywhere in `DelegationStore`, `MortgageService`, or `RewardViCalService` that can reclaim or redistribute it. This mirrors exactly the reported Carousel "NULL epoch" defect: value deposited into a bucket keyed by a period/entity that ends up having zero eligible claimants is permanently lost with no rescue path.

### Impact Explanation
This results in a direct, permanent freezing/loss of protocol-emitted TRX (block rewards, transaction-fee rewards, and standby-witness pay are newly issued/allocated value, not funds withdrawn from a specific user). Once stranded, the value can never be recovered by the protocol or any account — it is simply orphaned in `DelegationStore`'s per-cycle reward/Vi keyspace forever. This is a concrete, unbacked-allocation / permanent-freezing-of-funds outcome, consistent with the Medium-severity classification of the analogous report.

### Likelihood Explanation
The reward-crediting path (`payBlockReward`, `payTransactionFeeReward`, `payStandbyWitness`) executes automatically on every block produced and at every maintenance cycle as part of normal `Manager` block-application logic — it is not gated behind any privileged action and requires no attacker-controlled transaction, only the natural, protocol-level possibility of a witness having `voteCount == 0` for the cycle in which it earns a reward (e.g., a witness whose votes are fully withdrawn right at a maintenance-cycle boundary while it still produces a block, or is still paid as part of the top-127 standby set before/after its vote count reaches zero). This is a structural gap in the reward accounting rather than a rare or attacker-only condition.

### Recommendation
Add a fallback in `computeReward`/`accumulateWitnessVi`/`RewardViCalService.accumulateWitnessVi` so that when `totalVote`/`voteCount` is `0` for a witness in a given cycle, the reward that was added via `addReward` is either (a) rolled forward to the next cycle's reward bucket for that same witness, or (b) redirected to a globally recoverable pool (e.g., burned via `dynamicStore.burnTrx` or credited to a designated protocol account) instead of being silently dropped with no owner and no way to reclaim it.

### Proof of Concept
1. A witness `W` accumulates enough votes to enter the active/standby witness set for cycle `C`, so `payBlockReward`/`payTransactionFeeReward`/`payStandbyWitness` call `payReward(W, value)`, which calls `delegationStore.addReward(C, W, value)`.
2. Before the maintenance snapshot for cycle `C+1` is taken, all voters for `W` withdraw their votes (via `WithdrawBalance`/`vote` actuators), so `witness.getVoteCount()` becomes `0` by the time `MaintenanceManager.doMaintenance` runs `delegationStore.setWitnessVote(nextCycle, W, 0)`.
3. When any account later calls `withdrawReward`/`queryReward` for that cycle, `computeReward` finds `totalVote == 0` for `W` at cycle `C` and skips it entirely (`continue`) — no allowance is credited to anyone.
4. Equivalently, `DelegationStore.accumulateWitnessVi`/`RewardViCalService.accumulateWitnessVi` sees `voteCount == 0` and does not increment the Vi index, so the value added via `addReward` in step 1 can never be converted into any voter's claimable reward.
5. The TRX credited in step 1 is now permanently stranded in `delegationStore`'s reward keyspace for cycle `C`/witness `W`, unreachable by any subsequent call.

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

```java
  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
```
