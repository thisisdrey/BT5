### Title
Missing content-hash verification of downloaded attachment data lets a malicious peer permanently strip a resolved attachment from `AttachmentsBatch` - (File: stackslib/src/net/atlas/download.rs)

### Summary
When downloading an attachment for a tracked `content_hash` X, the response body is deserialized and its `Attachment` is inserted into the batch's result set without ever checking that `attachment.hash() == request.content_hash`. `AttachmentsBatchStateContext::extend_with_attachments` and `StacksHttpResponse::decode_atlas_get_attachment` accept any bytes, so a malicious source peer can answer a request for X with unrelated bytes Y (hash Z != X), which is stored/resolved under Z while the batch entry for X is left untouched.

### Finding Description
`AttachmentsBatch::resolve_attachment` removes an entry from `attachments_instances` only if its tracked `content_hash` equals the hash of the attachment that was actually delivered: [1](#0-0) 

The `Done` branch of `AttachmentsDownloader::run` iterates over whatever `Attachment`s were collected during download and calls `resolve_attachment(&attachment.hash())` for each — it never cross-checks this hash against the specific `AttachmentRequest.content_hash` that was actually sent out: [2](#0-1) 

The data reaches this point via `extend_with_attachments`, which decodes the HTTP response and inserts `response.attachment` into a `HashSet<Attachment>` with no validation that it matches the request that was issued for it: [3](#0-2) 

and via `decode_atlas_get_attachment`, which simply JSON-deserializes the body into `GetAttachmentResponse` with no hash check at all: [4](#0-3) 

`AttachmentRequest` itself carries the expected `content_hash` used to build the URL (`/v2/attachments/{content_hash}`), but this value is discarded after the request is sent — the response is never matched back against it: [5](#0-4) [6](#0-5) 

Root cause: the equality the code implicitly assumes — "the attachment returned for a request to `/v2/attachments/X` hashes to X" — is never enforced. An attacker who is selected as a download source for X (e.g. by claiming X in an `/v2/attachments/inv` response and being chosen in `get_prioritized_attachments_requests`) can return HTTP 200 with an arbitrary JSON body `{"attachment": {"content": <Y>}}`. The node computes `Z = hash(Y)`, stores it as a new instantiated attachment under Z, and calls `resolve_attachment(&Z)`, which finds no matching tracked hash for X and leaves X's entry inside `attachments_instances` untouched. `has_fully_succeed()` therefore stays `false` for that batch even though the "response" for X's slot was technically received.

If the attacker is the sole (or a persistently reachable) peer through which the batch's requests for X get routed on each retry, this can be repeated on every retry cycle. `bump_retry_count` increments the retry counter each pass; once `retry_count >= connection_options.max_attachment_retry_count`, the entire batch — including the entry for X, which may correspond to a validly on-chain-committed attachment — is silently dropped ("Atlas: dropping batch ... retries count exceeded") with no further attempt to fetch it.

### Impact Explanation
The victim node permanently fails to resolve a validly committed attachment instance (X) because the batch is dropped after exhausting retries, even though X was never actually served incorrect data from a canonical/consensus standpoint — the node just never records success for it. This is a case of a remote, unprivileged peer causing an on-chain-referenced attachment to be marked unavailable/unresolved indefinitely on the victim node, degrading BNS/attachment-serving correctness for that node (attachment/BNS mismatch-style impact — the node will behave as if the attachment does not exist even though it was committed on-chain). It does not corrupt consensus-critical state or crash the node, but it does cause the node to silently and permanently diverge from the true attachment set until an operator intervention (e.g., manual re-sync), which matches a High-severity "serving state that no canonical action produced" / availability-integrity class of bug rather than Critical.

### Likelihood Explanation
Preconditions: the victim must have an in-flight `AttachmentsBatch` containing the target content_hash X, and the attacker must be selected as (one of) the sources for X's `AttachmentRequest` — achievable by running an ordinary peer, responding truthfully or falsely to `/v2/attachments/inv` to claim possession of X, and then answering `/v2/attachments/{X}` with attacker-chosen bytes. All of this requires only unprivileged peer participation (no RPC secret, no admin role), matching the allowed threat model. The attack must persist across the batch's retry attempts to actually cause the final drop (bounded by `max_attachment_retry_count`), so it is repeatable but requires the attacker to remain the reachable/selected source across those retries — this is a moderate-cost but fully remote and repeatable precondition.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (stackslib/src/net/atlas/download.rs:530-558), after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting it into `self.attachments`; on mismatch, treat it as a failed/faulty response (`report.bump_failed_requests()` and/or register the peer as faulty) instead of silently accepting it. This ensures `resolve_attachment` is only ever called with hashes that genuinely correspond to a completed, requested download, and mismatched data from malicious peers cannot mask an unresolved tracked hash.

### Proof of Concept

1. Construct an `AttachmentsBatch` via `track_attachment` with two `AttachmentInstance`s sharing the same `index_block_hash`/`contract_id` but distinct `content_hash` values X1 and X2.
2. Build an `AttachmentsBatchStateContext` wrapping this batch.
3. Simulate `extend_with_attachments` being fed a `BatchedRequestsResult` whose `succeeded` map contains one `AttachmentRequest{content_hash: X1, ..}` paired with a fabricated `StacksHttpResponse`/`GetAttachmentResponse` carrying an `Attachment` whose content hashes to Z (Z != X1, Z != X2) — i.e., simulate a malicious peer's response to the request for X1.
4. Call `context.extend_with_attachments(&mut results)` then, mirroring the `Done` branch logic, iterate `context.attachments.drain()` and call `context.attachments_batch.resolve_attachment(&attachment.hash())`.
5. Assert `context.attachments_batch.has_fully_succeed()` is still `false` and that `attachments_instances` still contains the entry for X1 (i.e., the honest hash was never resolved, and repeating this over `max_attachment_retry_count` iterations via `bump_retry_count` results in the batch being dropped in `AttachmentsDownloader::run` without X1 ever being marked resolved).

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn resolve_attachment(&mut self, content_hash: &Hash160) {
        for missing_attachments in self.attachments_instances.values_mut() {
            let mut keys = vec![];
            for (k, hash) in missing_attachments.iter() {
                if hash == content_hash {
                    keys.push(*k);
                }
            }
            for key in keys {
                missing_attachments.remove(&key);
            }
        }
    }
