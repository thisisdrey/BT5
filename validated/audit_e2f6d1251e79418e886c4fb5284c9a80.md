### Title
Unbounded tar extraction from attacker-controlled stream enables resource-exhaustion DoS - ([File: internal/gitaly/repoutil/custom_hooks.go], [File: internal/gitaly/service/repository/create_repository_from_snapshot.go])

### Summary
`ExtractHooks` (used by `SetCustomHooks`/`RestoreCustomHooks`) and `untar` (used by `CreateRepositoryFromSnapshot`) both pipe an entirely attacker-controlled byte stream directly into a spawned `tar -xf -` process with no cap on entry count, decompressed size, or extraction wall-clock time beyond whatever deadline the calling context happens to carry. Because GNU `tar` auto-detects and transparently decompresses gzip/bzip2/xz-compressed input on extraction even without `-z`/`-j`/`-a`, a small attacker-supplied payload can expand to a very large amount of data/CPU work on the Gitaly node.

### Finding Description
`ExtractHooks` builds the command `tar -xf - -C <path> --strip-components <n> custom_hooks` and feeds it the raw request body via `command.WithStdin(buf)` [1](#0-0) . `SetCustomHooks`/`RestoreCustomHooks` stream the request body straight from the gRPC client into this reader with no size validation applied before it reaches tar [2](#0-1) . Similarly, `untar` spawns `tar -C <path> -xvf -` fed directly from an HTTP response body that the attacker controls (either as the repo owner supplying `HttpUrl`, or by controlling the responding server) [3](#0-2) . The code comment explicitly flags that "the received archive is trusted a lot" and needs hardening [4](#0-3) .

Neither call site limits the number of tar entries, the total decompressed size, or applies an explicit timeout to the `tar` invocation independent of the ambient context; the only bound is whatever deadline the calling gRPC context happens to carry (set by the client/Rails, not enforced internally by Gitaly). GNU tar's extraction path auto-detects compression by magic bytes regardless of explicit `-z`/`-j`/`-J` flags, so a compressed "tar bomb" (a small compressed stream expanding into gigabytes of tiny files/directories) can be piped through either extraction path, causing CPU, memory, and/or disk exhaustion on the node disproportionate to the bytes the attacker actually sent over the wire — a genuine amplification, not merely cost proportional to attacker bandwidth.

### Impact Explanation
An attacker with ordinary push/fork access can trigger `SetCustomHooksRequest`/`RestoreCustomHooksRequest` against their own repository, or (for `CreateRepositoryFromSnapshot`) serve a hostile compressed tar body from a slow/adversarial HTTP endpoint. Either path spawns an unbounded `tar` extraction process on the shared Gitaly storage node, which can consume excessive CPU, memory, or disk (via a decompression bomb or a huge number of tiny entries), degrading service availability for other tenants/repositories on the same node — matching the "DoS of an RPC handler" / resource-exhaustion impact class.

### Likelihood Explanation
The precondition is only standard, unprivileged access to `SetCustomHooks`/`RestoreCustomHooks` (available to anyone who can push/manage their own repository) or control of the HTTP endpoint used for `CreateRepositoryFromSnapshot`'s `HttpUrl`. No admin role, secret, or peer compromise is required, and the attack is trivially repeatable and scriptable. The main uncertainty is how tightly the surrounding gRPC/Rails call sets a request deadline in practice — this was not fully confirmed from the code available, so the achievable duration of an unbounded hang could be bounded in some deployments but is not bounded by Gitaly's own code in these two functions.

### Recommendation
- Bound tar extraction explicitly rather than relying solely on the ambient context: pass an explicit `--warning=no-timestamp`-style hard cap is not enough; add `tar`'s `--exclude` is not relevant, but do add a maximum wall-clock timeout for the spawned command independent of caller-supplied context (e.g., `context.WithTimeout` wrapping before invoking `command.New`).
- Cap total decompressed size and entry count before/while streaming (e.g., use a `io.LimitReader` on the input, or extract via Go's `archive/tar` package directly instead of shelling out, so entry count/size can be checked per-entry and aborted early).
- Explicitly disable transparent decompression (do not rely on tar's auto-detect) unless required, or explicitly limit decompressed output size when compression is used.
- For `CreateRepositoryFromSnapshot`, additionally cap the HTTP response body size read from `rsp.Body` before feeding it to tar.

```go
// internal/gitaly/repoutil/custom_hooks_tarbomb_test.go
func TestExtractHooks_TarBombDoS(t *testing.T) {
    ctx := testhelper.Context(t)
    logger := testhelper.SharedLogger(t)
    dir := t.TempDir()

    // Build a small gzip-compressed tar whose "custom_hooks/" entries expand
    // to a very large number of files/bytes on extraction (e.g. a sparse
    // file entry declaring a huge size, or millions of zero-length entries).
    bombReader := buildGzipTarBomb(t) // helper constructing e.g. 10MB compressed -> multi-GB decompressed

    start := time.Now()
    err := ExtractHooks(ctx, logger, bombReader, dir, false)
    t.Logf("extraction took %s, err=%v", time.Since(start), err)
    // Expected (post-fix): extraction aborts quickly with a size/entry-count
    // or timeout error instead of running unbounded / exhausting disk.
}
```
Equivalent RPC-level PoC: stream a crafted gzip tar body (headers under `custom_hooks/`) through `SetCustomHooksRequest.Data` chunks, or host it at a URL passed as `CreateRepositoryFromSnapshotRequest.HttpUrl`, and observe unbounded CPU/memory/disk growth on the Gitaly node with no internal cutoff besides the caller's gRPC deadline.
