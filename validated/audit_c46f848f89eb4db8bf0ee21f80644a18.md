### Title
Front-Runnable Name-Squatting DoS in Asset Issuance via `bountyId`-style Existence Check - ([File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java])

### Summary
`AssetIssueActuator` implements the exact same "check-then-create keyed by an attacker-supplied string" pattern flagged in the OpenQ `mintBounty` report. When `AllowSameTokenName` is disabled, asset creation validates uniqueness of the human-chosen token `name` and then persists the new asset under that same name as its store key, with no binding between the name and the transaction's owner beyond order of arrival. Any unprivileged account can watch the mempool and front-run a legitimate `AssetIssueContract` transaction by broadcasting its own `AssetIssueContract` with the identical `name` but different terms, causing the legitimate creator's transaction to permanently fail with `"Token exists"`.

### Finding Description
In `validate()`, uniqueness is enforced purely by the token name string: [1](#0-0) 

In `execute()`, the new asset is written to `AssetIssueStore` keyed by that same name (`assetIssueCapsule.createDbKey()` returns `getName().toByteArray()`), and the creating account is marked as having issued that asset: [2](#0-1) [3](#0-2) 

Because the name-existence check and the name-keyed write happen in separate steps across two independently-broadcast transactions, an attacker observing a victim's pending `AssetIssueContract` transaction (same threat model as watching a mempool for `mintBounty`) can submit their own `AssetIssueContract` with the identical `name` and a higher fee/priority. Once the attacker's transaction lands first, `assetIssueStore.get(name) != null` becomes true, and the victim's transaction is rejected in validation with `"Token exists"`: [4](#0-3) 

This is corroborated by the actuator's own test asserting the exact failure mode when a name is already taken: [5](#0-4) 

Additionally, because an account can only issue one asset ("An account can only issue one asset"), the attacker's squatting transaction also permanently consumes the attacker's own one-time issuance slot on that name — but crucially the victim's slot for the *name they wanted* is permanently blocked without a retry option (a new name must be chosen), constituting a griefing/DoS analogous to the OpenQ report's `bountyIdToAddress` front-running. [6](#0-5) 

### Impact Explanation
A malicious, unprivileged account can deny a targeted legitimate TRC10 token creator the ability to ever issue a token under their intended, branded name (e.g. a project's ticker/name), forcing wasted fees (the victim's transaction fails after already having been broadcast, though the `AssetIssueFee` is only charged on success) and reputational/availability harm to the token issuance workflow — a concrete denial-of-service against a specific unprivileged operation reachable by any signed transaction.

### Likelihood Explanation
This path is only reachable while the chain's `AllowSameTokenName` dynamic property equals `0` (name-keyed mode). On current TRON mainnet this proposal has long been activated network-wide, making the vulnerable branch dormant there; however, the vulnerable code path itself is fully present and unconditionally reachable on any java-tron network (new private/consortium chains, testnets, or any deployment where the community proposal to enable `AllowSameTokenName` has not been passed) since the default genesis value is `0`. On any such network, the attack requires only mempool visibility and the ability to broadcast a transaction with higher energy/priority than the target — a standard front-running capability with no special privilege.

### Recommendation
Do not use the raw, attacker/user-chosen `name` as the sole/authoritative uniqueness key that gates issuance. Options: bind the uniqueness check to `(ownerAddress, name)` rather than `name` alone (so squatting doesn't block other owners from reserving the same string under their own address if desired), or migrate name-keyed asset lookups fully to the ID-keyed (`AssetIssueV2Store`) scheme unconditionally (removing the legacy `AllowSameTokenName == 0` branch entirely) so that name collisions can never gate creation eligibility.

### Proof of Concept
1. Attacker monitors the mempool/pending pool for an `AssetIssueContract` transaction from a victim with `name = "VictimCoin"` and `AllowSameTokenName == 0`.
2. Attacker crafts and broadcasts their own `AssetIssueContract` transaction with `name = "VictimCoin"`, a different `totalSupply`/other params, and a higher fee/energy to ensure block inclusion before the victim's transaction (standard front-running).
3. Attacker's transaction is processed first: `validate()` passes (`assetIssueStore.get("VictimCoin") == null` at that time), `execute()` writes `AssetIssueStore["VictimCoin"] -> attacker's AssetIssueCapsule`, as shown in: [2](#0-1) 
4. Victim's transaction is then processed in the same or later block; `validate()` now finds `assetIssueStore.get("VictimCoin") != null` and throws `ContractValidateException("Token exists")`, matching the tested behavior: [7](#0-6) 
5. The victim can never issue a token under `"VictimCoin"` again while `AllowSameTokenName == 0`, since token issuance is a one-time-per-account operation and the name is now permanently taken by the attacker.
