### Title
Stale stake/vote accounts remain in the in-memory `StakesCache` when their owner changes away from the stake/vote program, causing unbounded bloat and incorrect stake accounting - (File: `runtime/src/stakes.rs`)

### Summary
`StakesCache::check_and_store` — the function that keeps the bank's in-memory `Stakes` cache (used for `vote_accounts()`, `staked_nodes()`, `get_delegated_stake()`, etc.) in sync with accounts-db after every transaction — only evicts an entry when the account's *current* owner is still the vote program or stake program (and lamports go to zero, or deserialization fails). If a previously-cached vote/stake account's owner is reassigned to a third program (while keeping non-zero lamports), the function takes neither branch and the stale, no-longer-valid entry is left in the cache indefinitely. This is the direct analog of the reported Golom bug: an entity is "removed" from its underlying representation but a stale reference persists in the cache/list that other logic iterates over, causing bloat and incorrect accounting.

### Finding Description
`check_and_store` is invoked from `Bank::update_stakes_cache` for every account written by a successful transaction [1](#0-0) . Inside, the code explicitly documents the gap with a TODO:

```
// TODO: If the account is already cached as a vote or stake account
// but the owner changes, then this needs to evict the account from
// the cache. see:
// https://github.com/solana-labs/solana/pull/24200#discussion_r849935444
let owner = account.owner();
``` [2](#0-1) 

The subsequent logic only removes/updates the cache entry when `owner` still matches `solana_vote_program::check_id` or `stake_program::check_id`; if the account has been reassigned to any other program (e.g., via `Assign`/`system_instruction::assign` or a CPI that changes ownership while lamports remain non-zero), neither branch executes and the function silently returns without touching the cache [3](#0-2) .

A regression test already documents this exact gap and explicitly acknowledges the code is *not* hardened for it:

```rust
#[test]
fn test_stake_vote_account_validity() {
    let thread_pool = ThreadPoolBuilder::new().num_threads(1).build().unwrap();
    // TODO: stakes cache should be hardened for the case when the account
    // owner is changed from vote/stake program to something else. see:
    // https://github.com/solana-labs/solana/pull/24200#discussion_r849935444
    check_stake_vote_account_validity(
        false, // check owner change
        |bank: &Bank| bank._load_vote_and_stake_accounts(&thread_pool, null_tracer()),
    );
}
``` [4](#0-3) 

and the underlying test helper confirms that reassigning a staked vote account's owner to a bogus program does not remove it from `bank.vote_accounts()`: [5](#0-4) 

There is a feature flag, `evict_invalid_stakes_cache_entries` ("evict invalid stakes cache entries on epoch boundaries") [6](#0-5) , declared in the feature list [7](#0-6) , but a repo-wide search finds no code anywhere else in the indexed codebase that actually consumes/gates on this feature ID — no eviction pass at epoch boundaries was found wired to it. This suggests the mitigation referenced by the feature name is not (or no longer) implemented in this snapshot of the code, leaving the TODO in `check_and_store` as the live behavior.

### Impact Explanation
This is directly analogous to the referenced Golom bug class: an object removed from its canonical/valid state (owner changed away from stake/vote program) is not removed from the auxiliary cache/list that downstream logic iterates over. Consequences in Agave:
- Bloat in `StakesCache`/`VoteAccounts`/`stake_delegations` maps that never shrinks for accounts whose owner is reassigned away, since neither `remove_vote_account` nor `remove_stake_delegation` [8](#0-7)  is invoked in that path.
- Downstream consumers such as `staked_nodes()` [9](#0-8)  and reward/stake distribution logic that iterate `stakes.stake_delegations()`/`vote_accounts()` continue to see and process stale entries, potentially leading to incorrect stake-weighted computations (using data belonging to an account no longer actually owned by the stake/vote program) and extra CPU/memory overhead per bank update.
- Because this is an unprivileged action (any account owner can reassign ownership of an account they control, subject to normal system-program rules), an attacker could repeatedly create stake/vote-owned accounts, get them cached, then reassign ownership away without zeroing lamports, to grow the cache without bound over time — a memory-growth concern for validators.

This does not rise to "verification bypass" or "invalid recorded block" by itself, but it is a legitimate reachable unprivileged-user path (regular transactions, no special role) causing unbounded/incorrect state accumulation in a core bank data structure, matching the "unbounded memory" / incorrect-accounting concern class.

### Likelihood Explanation
Reassigning ownership of an account is a standard, unprivileged system-program capability (`Assign`), reachable by any user who controls the account (e.g., its own newly created stake/vote-like account, or one where they hold the necessary authority to reassign). The gap is explicitly acknowledged as unfixed via the TODO comment and a test that is intentionally run with `check_owner_change = false` to document current (non-hardened) behavior. However, this is a known, long-standing, and explicitly documented limitation (referencing a 2022 upstream PR discussion) rather than a newly discovered issue, and I could not confirm from the available index whether the `evict_invalid_stakes_cache_entries` feature (once activated network-wide) implements an actual periodic cleanup elsewhere that mitigates the long-term bloat, since no code consuming that feature ID was found in this index. This uncertainty affects confidence in the actual current severity on a live cluster.

### Recommendation
Harden `StakesCache::check_and_store` to detect owner changes away from the stake/vote program (not just zero-lamport or malformed-state cases) and evict the corresponding cache entry, mirroring the recommendation in the referenced report ("override _burn ... add removeDelegation"). Concretely: before the owner-type branches, check whether `pubkey` is currently present in `vote_accounts` or `stake_delegations` and if the new `owner` no longer matches the expected program, explicitly call `remove_vote_account`/`remove_stake_delegation`. Additionally, confirm whether `evict_invalid_stakes_cache_entries` is wired to any epoch-boundary cleanup pass; if not, implement one, or remove the vestigial feature flag if the fix is meant to be unconditional.

### Proof of Concept
Conceptual reproduction based on the existing test harness pattern (`runtime/src/bank/tests.rs::check_stake_vote_account_validity`) [10](#0-9) :
1. Create a validator vote account with non-zero activated stake (so it is cached in `StakesCache`).
2. Submit a transaction (as the account's current owner/authority, no special privilege) that reassigns the vote account's owner to an arbitrary non-vote program, while keeping lamports non-zero.
3. Call `bank.vote_accounts()` / inspect `stakes_cache.stakes().vote_accounts()` — the entry is still present with the stale `VoteAccount` data, as demonstrated by the assertion `assert_eq!(bank.vote_accounts().len(), 1)` after the owner reassignment in the existing test [11](#0-10) , confirming the cache is not evicted on owner change.

                new_rate_activation_epoch,

            self.vote_accounts
                .sub_stake(&removed_delegation.voter_pubkey, removed_stake);
        }
    }

fn check_stake_vote_account_validity<F>(check_owner_change: bool, load_vote_and_stake_accounts: F)
where
    F: Fn(&Bank) -> StakeDelegationsMap,
{
    let validator_vote_keypairs0 = ValidatorVoteKeypairs::new_rand();
    let validator_vote_keypairs1 = ValidatorVoteKeypairs::new_rand();
    let validator_keypairs = vec![&validator_vote_keypairs0, &validator_vote_keypairs1];
    let GenesisConfigInfo { genesis_config, .. } = create_genesis_config_with_vote_accounts(
        1_000_000_000,
        &validator_keypairs,
        vec![LAMPORTS_PER_SOL; 2],
    );
    let bank = Arc::new(Bank::new_from_genesis(
        &genesis_config,
        Arc::<RuntimeConfig>::default(),
        Vec::new(),
        None,
        ACCOUNTS_DB_CONFIG_FOR_TESTING,
        None,
        None,
        Arc::default(),
        None,
        None,
    ));
    let vote_and_stake_accounts = load_vote_and_stake_accounts(&bank);
    assert_eq!(vote_and_stake_accounts.len(), 2);

    let mut vote_account = bank
        .get_account(&validator_vote_keypairs0.vote_keypair.pubkey())
        .unwrap_or_default();
    let original_lamports = vote_account.lamports();
    vote_account.set_lamports(0);
    // Simulate vote account removal via full withdrawal
    bank.store_account(
        &validator_vote_keypairs0.vote_keypair.pubkey(),
        &vote_account,
    );

    // Modify staked vote account owner; a vote account owned by another program could be
    // freely modified with malicious data
    let bogus_vote_program = Pubkey::new_unique();
    vote_account.set_lamports(original_lamports);
    vote_account.set_owner(bogus_vote_program);
    bank.store_account(
        &validator_vote_keypairs0.vote_keypair.pubkey(),
        &vote_account,
    );

    assert_eq!(bank.vote_accounts().len(), 1);

    // Modify stake account owner; a stake account owned by another program could be freely
    // modified with malicious data
    let bogus_stake_program = Pubkey::new_unique();
    let mut stake_account = bank
        .get_account(&validator_vote_keypairs1.stake_keypair.pubkey())
        .unwrap_or_default();
    stake_account.set_owner(bogus_stake_program);
    bank.store_account(
        &validator_vote_keypairs1.stake_keypair.pubkey(),
        &stake_account,
    );

    // Accounts must be valid stake and vote accounts
    let vote_and_stake_accounts = load_vote_and_stake_accounts(&bank);
    assert_eq!(
        vote_and_stake_accounts.len(),
        usize::from(!check_owner_change)
    );
}

    pub fn staked_nodes(&self) -> Arc<HashMap</*node_pubkey:*/ Pubkey, /*stake:*/ u64>> {
        self.staked_nodes
            .get_or_init(|| {
                // Count non-zero stake accounts for optimal capacity allocation
                let non_zero_count = self
                    .vote_accounts
                    .values()
                    .filter(|(stake, _)| *stake != 0)
                    .count();

                let mut staked_nodes = HashMap::with_capacity(non_zero_count);

                for (stake, vote_account) in self.vote_accounts.values() {
                    if *stake != 0 {
                        *staked_nodes.entry(*vote_account.node_pubkey()).or_default() += *stake;
                    }
                }

                Arc::new(staked_nodes)
            })
            .clone()
    }
