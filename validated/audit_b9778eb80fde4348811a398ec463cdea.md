### Title
StackerDB chunk-authentication digest omits the target contract/instance, enabling cross-instance replay of validly-signed chunks - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
The bug-class from the external report ("signed data usable cross-chain because chain-id is not part of the signed payload") has a direct analog in `SlotMetadata::auth_digest()`. The digest that authenticates every StackerDB chunk write commits only to `slot_id`, `slot_version`, and `data_hash` — it never includes the StackerDB's `smart_contract_id` (the per-reward-cycle / per-message-lane "domain" that a slot belongs to). Any chunk signature that is valid for one StackerDB instance is therefore equally valid for any other StackerDB instance in which the same signing key happens to be the registered owner of the same `slot_id`, as long as an attacker can also line up `slot_version`/`data_hash`. Because chunk validation never re-derives or checks the contract identity from the signature, this is a missing domain-separator, exactly analogous to the missing chain-id in the reported bug.

### Finding Description
`SlotMetadata::auth_digest()` computes: [1](#0-0) 
which hashes only `slot_id`, `slot_version`, and `data_hash`. `SlotMetadata::verify()` recovers the public key from this digest and compares its hash against the caller-supplied `principal` (the StackerDB-and-slot-specific expected signer): [2](#0-1) 

The contract identity (`QualifiedContractIdentifier`) is passed in only as an out-of-band lookup key to fetch the *expected signer address* for that slot in that contract — it is never mixed into the bytes that get signed: [3](#0-2) [4](#0-3) 

Consequently, if the same Stacks address is the registered signer of `slot_id = S` in two different StackerDB contracts (e.g. two different `signer-<msg-id>-<reward-cycle>` boot contracts, or across the miner contract and a signer contract if slot numbering coincides), a signature that address produced when authoring `(S, V, H)` in contract A is bit-for-bit indistinguishable from a signature that would be required for `(S, V, H)` in contract B. Any network relayer — not the key holder — can therefore take a chunk observed in one StackerDB and resubmit it (via `POST /v2/stackerdb/.../chunks` or via the P2P `StackerDBPushChunk`/`StackerDBChunkInv` gossip path) against a *different* contract for which it was never intended, and it will pass `try_replace_chunk`'s signature check: [5](#0-4) 

Accepted chunks are re-broadcast network-wide to the peer's neighbors: [6](#0-5) 

Node operators commonly reuse a single Stacks signing key across many StackerDB instances (the same key is the registered signer for the miner contract and multiple `signer-<id>-<reward-cycle>` contracts across consecutive reward cycles, since slot allocation is by stacking-weight rank, which is frequently stable between adjacent cycles). This makes same-slot/cross-contract key reuse a realistic condition, not a contrived edge case.

### Impact Explanation
This breaks the equality "a chunk accepted into contract X's slot S was actually authorized for contract X" — the signature only proves "signer of slot S in *some* StackerDB the signer participates in", not "signer of slot S *in this contract*". An unprivileged network peer (no private key needed) can relay a legitimately-signed chunk into an unintended StackerDB instance, causing the receiving node to store and further gossip data associated with the wrong contract/reward-cycle context. This is network-wide propagation of data outside the domain it was actually signed for, since valid chunk storage triggers rebroadcast to all neighbors regardless of whether the data is meaningful in the target contract.

The severity is bounded by the fact that most consumers of chunk payloads (e.g. `BlockResponse`/`BlockRejection` signer messages) carry their *own* independent structured-data signature that separately commits to `chain_id` and the specific block hash being referenced: [7](#0-6) 
so a naively-replayed chunk's *inner* message will usually fail higher-level semantic checks (e.g. `stackerdb_listener.rs` ignoring a signature for a block it did not request). I was not able to fully verify within the available searches whether every consumer of every StackerDB payload type (including miner-slot content and internal StackerDB inventory/anti-entropy bookkeeping) performs an equivalent independent, contract-bound check, so the practical blast radius of the missing domain separator could not be conclusively bounded to "cosmetic" versus "exploitable state corruption" in this pass.

### Likelihood Explanation
Exploitation requires no secret key and no privileged role — only observing one legitimately-published, correctly-signed chunk (trivial, since StackerDB chunks are broadcast in the clear) and resubmitting it verbatim to a different StackerDB contract where the coincidence of same-signer/same-slot-id holds. This coincidence is plausible in production because reward-cycle-to-reward-cycle signer-set churn is often small for high-weight signers, and slot IDs are assigned deterministically by rank.

### Recommendation
Include the target `smart_contract_id` (or a network/consensus-hash bound domain identifier) as part of `SlotMetadata::auth_digest()`, so a signature commits to "signer S authorizes chunk (id, version, hash) for StackerDB contract C" rather than being contract-agnostic. This mirrors the report's recommendation to bind signed data to the intended execution domain (chain-id) rather than leaving it implicit/out-of-band.

### Proof of Concept
1. Attacker observes a validly-signed `StackerDBChunkData { slot_id: S, slot_version: V, sig, data }` broadcast for StackerDB contract A (e.g. `signer-0-100`), where address `addr` is the registered slot-S signer in contract A.
2. Attacker checks (via public signer-set data derivable from the PoX/signers boot contracts) that `addr` is also the registered slot-S signer in a different StackerDB contract B (e.g. `signer-0-101`, the next reward cycle) whose current slot-S version is `< V`.
3. Attacker submits the identical `StackerDBChunkData` to contract B, either via the `POST /v2/stackerdb/{contract}/chunks` HTTP endpoint (see acceptance path in `stackslib/src/net/stackerdb/db.rs:398-437`) or by relaying a crafted `StackerDBPushChunk`/`StackerDBChunkInv` P2P message.
4. `try_replace_chunk` calls `slot_desc.verify(&slot_validation.signer)`, which succeeds because `auth_digest()` never referenced contract A vs. B, and `V` is newer than B's current version, so the chunk is stored and rebroadcast to B's replica set — even though `addr` never authorized anything for contract B.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);

    pub fn hash(&self) -> Sha256Sum {
        let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
        let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }
