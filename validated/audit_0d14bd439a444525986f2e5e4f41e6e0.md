### Title
Excess attached deposit is permanently retained (not refunded) on successful `register()` in `AddressRegistrar` - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `AddressRegistrar::register()` payable method only refunds the caller's attached deposit when registration fails due to an address collision. When registration succeeds (the common, intended path), any deposit attached above the exact storage cost is silently kept by the contract with no refund and no withdrawal mechanism, permanently locking the excess NEAR — the same bug class as the reported "presale round does not return ETH" issue, where one code path refunds excess payment and a sibling path does not.

### Finding Description
`register()` is marked `#[payable]` and accepts an attached deposit intended to cover the exact storage cost of the new `address -> account_id` mapping: [1](#0-0) 

It computes `required_deposit` from the storage bytes needed and panics only if `given_deposit < required_deposit`. Any amount attached that is greater than `required_deposit` is not checked or capped.

On the success path (`Entry::Vacant`), the contract inserts the mapping and returns the address string, but it never sends back the difference `given_deposit - required_deposit`: [2](#0-1) 

By contrast, the collision path (`Entry::Occupied`) explicitly refunds the caller's *entire* deposit, since no storage was written: [3](#0-2) 

The contract exposes no `withdraw`, `owner`, or any other privileged/unprivileged method to reclaim funds sitting on its account balance — `lookup` and `get_address` are read-only view methods: [4](#0-3) 

This is exactly the analog of the reported Solidity bug: the "collision/failure" path returns the full deposit (like `mint()`'s excess-ETH refund), while the "success" path (like `presaleMint()`) fails to refund the excess above what's actually required, leaving funds stuck in the contract forever with no recovery path.

### Impact Explanation
Any ordinary NEAR user (including the intended callers of the eth-implicit wallet flow that uses this registrar) who attaches more than the exact required storage deposit to a successful `register()` call permanently loses the excess. Since NEAR client tooling (e.g. wallets estimating storage cost with some safety margin) commonly attaches deposits that are not byte-exact, and since this contract is part of the eth-implicit wallet infrastructure meant to be called by ordinary transactions, this results in a concrete, permanent freezing of user funds with no way for the depositor or anyone else to reclaim them.

### Likelihood Explanation
This is highly likely to be triggered in normal operation: any caller that overestimates the storage byte cost (a common, safe practice) or simply attaches a round NEAR amount for convenience will trigger the bug on every successful, non-colliding registration — no adversarial conditions or race are required.

### Recommendation
In the `Entry::Vacant` success branch of `register()`, compute `given_deposit.checked_sub(required_deposit)` and, if greater than zero, issue a promise transfer of the excess back to `env::predecessor_account_id()`, mirroring the refund logic already implemented in the `Entry::Occupied` branch.

### Proof of Concept
1. Call `AddressRegistrar::register("alice.near")` attaching `1 NEAR`, while the actual `required_deposit` for storing the 20-byte address key and the `AccountId` value is only a few hundred yoctoNEAR-per-byte × ~30 bytes (a tiny fraction of 1 NEAR).
2. Since `given_deposit (1 NEAR) >= required_deposit`, the check at lines 54–61 passes.
3. The address is not previously registered, so execution takes the `Entry::Vacant` branch (lines 65–72), inserts the mapping, and returns `Some(address)`.
4. No transfer/refund promise is created in this branch; the contract's account balance permanently retains `1 NEAR - required_deposit` with no method available to withdraw it.

    /// Attempt to look up the account ID associated with the given address.
    /// If an entry for that address is found then the associated account id
    /// is returned, otherwise `None` is returned. Use the `register` method
    /// to add entries to the map.
    /// This function will panic if the given address is not the hex-encoding
    /// of a 20-byte array. The `0x` prefix is optional.
    pub fn lookup(&self, address: String) -> Option<AccountId> {
        let address = {
            let mut buf = [0u8; 20];
            hex::decode_to_slice(address.strip_prefix("0x").unwrap_or(&address), &mut buf)
                .unwrap_or_else(|_| env::panic_str("Invalid hex encoding"));
            buf
        };
        self.addresses.get(&address).cloned()
    }

    /// Computes the address associated with the given `account_id` and
    /// returns it as a hex-encoded string with `0x` prefix. This function
    /// does not update the mapping stored in this contract. If you want
    /// to register an account ID use the `register` method.
    pub fn get_address(&self, account_id: AccountId) -> String {
        let address = account_id_to_address(&account_id);
        format!("0x{}", hex::encode(address))
    }
}
