## Title
Missing bounds check on attacker-controlled calldata offsets in `ValidateMultiSign` precompile causes uncaught `ArrayIndexOutOfBoundsException` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

## Summary
The `ValidateMultiSign` TVM precompiled contract parses raw calldata into a `DataWord[]` array and then indexes into that array (`words[0]`, `words[1]`, `words[2]`, `words[3]`) before any length/bounds validation is performed, when the `allowTvmOsaka` fork guard is not active. An attacker can invoke this precompile (address `0x100...09` style TVM precompile call, reachable from any unprivileged smart-contract call or `TriggerSmartContract` transaction) with calldata shorter than 4 words, causing an uncaught `ArrayIndexOutOfBoundsException` that propagates out of the un-guarded portion of `execute()`.

## Finding Description
`PrecompiledContracts.ValidateMultiSign.execute()` only validates calldata shape via `isValidAbiEncoding()` when `VMConfig.allowTvmOsaka()` is true: [1](#0-0) 

```java
public Pair<Boolean, byte[]> execute(byte[] rawData) {
  if (VMConfig.allowTvmOsaka()
      && !isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)) {
    return Pair.of(false, EMPTY_BYTE_ARRAY);
  }
  DataWord[] words = DataWord.parseArray(rawData);
  byte[] address = words[0].toTronAddress();
  int permissionId = words[1].intValueSafe();
  byte[] data = words[2].getData();
  ...
  if (VMConfig.allowTvmSelfdestructRestriction()) {
    int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
```

`DataWord.parseArray(rawData)` builds an array whose length is simply `rawData.length / WORD_SIZE`, with no minimum-size guarantee: [2](#0-1) 

If `rawData` is shorter than 4 words (128 bytes) — including empty calldata — `words` has fewer than 4 elements, and the unconditional `words[0]`/`words[1]`/`words[2]`/`words[3]` accesses throw `ArrayIndexOutOfBoundsException` **before** the `try/catch(Throwable)` block that wraps the permission/weight-checking logic further down: [3](#0-2) 

This is structurally analogous to the Nimiq bug class: an equality/size check that is supposed to gate an index into an array is either missing or only conditionally enforced, so a value fully controlled by an untrusted remote party reaches an unguarded array-index operation before verification logic runs.

The `isValidAbiEncoding` guard exists only because it is fork-gated behind `VMConfig.allowTvmOsaka()`: [4](#0-3) 

Notably, the sibling precompile `BatchValidateSign` wraps its entire body (including the equivalent array-index code) in a `try { return doExecute(data); } catch (Throwable t) { ... return Pair.of(true, new byte[WORD_SIZE]); }` safety net: [5](#0-4) 

`ValidateMultiSign` has no equivalent outer catch-all — its only `try/catch(Throwable)` starts after the vulnerable indexing lines, at line 1082, so it does not protect the `words[0..3]` accesses.

There is also a repository test suite (`ValidateMultiSignContractTest`, `OperationsTest#testTip854OuterFrameContainment`) that specifically exercises "malformed calldata to `validateMultiSign`" scenarios once `allowTvmOsaka` is enabled, confirming the maintainers were aware of and partially addressed this exact class of bug — but the fix is fork-gated, meaning any deployment or test network where `allowTvmOsaka` has not yet activated remains exposed: [6](#0-5) 

## Impact Explanation
An uncaught `ArrayIndexOutOfBoundsException` thrown from inside `PrecompiledContracts.execute()` propagates through `Program.callToPrecompiledAddress` (which calls `contract.execute(data)` with no surrounding try/catch for this exception type) and then through `VM.play()`'s `catch (RuntimeException e)` handler, which spends all energy, stops the program, and **rethrows** the exception up the call stack: [7](#0-6) 

Whether this ultimately just fails/reverts the single transaction (if caught generically higher up in `VMActuator`) or causes broader disruption depends on exception handling further up the actuator stack, which could not be fully confirmed in this pass due to search/tool exhaustion. At minimum this is a reliably-triggerable exception in energy-metered contract execution reachable by any unprivileged account issuing a `TriggerSmartContract` transaction calling the `ValidateMultiSign` precompile address with short calldata — a similar class of issue to the cited Nimiq CVE (untrusted, minimally-crafted input reaching an unguarded index operation before any real validation executes).

## Likelihood Explanation
High likelihood of triggering the specific exception: any account can send a `TriggerSmartContract` transaction (or have a contract perform a `CALL`/`STATICCALL`) to the `ValidateMultiSign` precompile address with `rawData` shorter than 128 bytes, with no special privilege, stake, or witness/committee status required. The only mitigating factor is the fork gate `allowTvmOsaka`, which — once active network-wide — closes this specific path by rejecting malformed input early via `isValidAbiEncoding`.

## Recommendation
Move the `isValidAbiEncoding`/minimum-length check (or an unconditional `words.length >= 4` check) outside the `allowTvmOsaka` gate so it always executes before any indexing into `words`, or wrap the entire `ValidateMultiSign.execute()` body in the same `try/catch(Throwable)` safety net already used by `BatchValidateSign.execute()`. Given that the fix already exists (fork-gated), the most correct remediation is to make the length validation unconditional rather than tied to a specific hard-fork flag, consistent with defense-in-depth for TVM precompiles that consume raw untrusted calldata.

## Proof of Concept
1. Deploy or use an existing smart contract, or issue a `TriggerSmartContract` transaction directly.
2. From the calling context, issue a `CALL` (or `STATICCALL`) to the `ValidateMultiSign` precompile address with `rawData` of length `< 128` bytes (e.g., empty calldata, 0 bytes) on a network/test harness where `allowTvmOsaka` has not been activated (default state prior to fork activation, as reproduced by `OperationsTest#testCallOperations`-style precompile invocation without setting `VMConfig.initAllowTvmOsaka(1)`).
3. Observe `words[0].toTronAddress()` (or further down `words[3]`) throw `ArrayIndexOutOfBoundsException` inside `PrecompiledContracts.PrecompiledContract.execute()`, which is not caught by the local `try/catch(Throwable)` block (that block starts later, at line 1082) and propagates through `Program.callToPrecompiledAddress` and `VM.play()`.

**Caveat / uncertainty:** I could not fully trace how the propagated `ArrayIndexOutOfBoundsException` is ultimately handled at the very top of `VMActuator`/`TriggerSmartContractActuator` (e.g., whether it's caught generically as `Exception`/`Throwable` there and merely fails the single transaction, versus causing broader instability) due to exhausting available tool iterations. This affects whether the final classification is "single transaction fails safely" (lower severity) or "uncontrolled exception affecting block/node processing" (higher severity, matching the CVE's crash impact). I recommend a Devin session with full file access to trace this final handling path before assigning a definitive severity.

  public static DataWord[] parseArray(byte[] data) {
    int len = data.length / WORD_SIZE;
    DataWord[] words = new DataWord[len];
    for (int i = 0; i < len; i++) {
      byte[] bytes = Arrays.copyOfRange(data, i * WORD_SIZE, (i + 1) * WORD_SIZE);
      words[i] = new DataWord(bytes);
    }
    return words;
  }
