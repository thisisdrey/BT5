### Title
Client-supplied `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables silently override the server-validated quarantine repository in the `pre-receive` access-check request - ([File: internal/gitaly/hook/prereceive.go])

### Summary
`preReceiveHook` re-derives the repository's quarantine object directory fields from the raw `envs` slice passed on the `PreReceiveHook` gRPC call and overwrites the `repo.GitObjectDirectory` / `repo.GitAlternateObjectDirectories` that were already established server-side via the signed `HooksPayload`. This is structurally the same bug class as the AbraNFT finding: a security-relevant parameter (`oracle` in the report, quarantine object directory here) that should remain fixed once established by the trusted party is instead re-accepted from an untrusted/less-trusted input at a later step, and the tampered value is what actually feeds the authorization decision (`Allowed()` REST call to Rails, analogous to the loan-seizure `rate` check).

### Finding Description
When `git receive-pack` invokes the `pre-receive` hook, Gitaly's `gitaly-hooks` binary calls the internal `PreReceiveHook` RPC, forwarding `EnvironmentVariables` from its own OS process environment [1](#0-0) . Inside `GitLabHookManager.preReceiveHook`, instead of trusting only the quarantine information already carried by the cryptographically-opaque `HooksPayload` (built server-side in `NewHooksPayload` from the actual quarantine directory Gitaly created, see `internal/git/gitcmd/hooks_payload.go` lines 159-167), the code re-extracts `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` from the plain `envs` list of the RPC request and overwrites `repo.GitObjectDirectory`/`repo.GitAlternateObjectDirectories`: [2](#0-1) 

The overwritten `repo` object is then used to build the `gitlab.AllowedParams` sent to Rails' `Allowed` endpoint, which decides whether the push may proceed and which objects are visible for pre-receive checks (e.g., protected-branch/force-push detection that must see the pushed objects) [3](#0-2) . Because `envs` is attacker-influenceable input on the RPC boundary (it is not part of the signed/base64 `GITALY_HOOKS_PAYLOAD` blob, but a separate, unauthenticated `EnvironmentVariables` field on `PreReceiveHookRequest`), and `getRelativeObjectDirs` performs only a `filepath.Rel` computation with no validation that the resulting relative path stays within the repository or matches the quarantine directory that Gitaly itself created for this push [4](#0-3) , a party able to influence the environment passed to this RPC (e.g. a compromised/malicious `gitaly-hooks` invocation, or any code path that assembles `EnvironmentVariables` from less-trusted sources) can point the object directory used for the Rails access check at a different location than what was actually quarantined and unpacked for this push - exactly mirroring the AbraNFT bug where a value that should stay fixed for a security check (`oracle`) is instead re-derived from a later, attacker-influenced input (`params.oracle`) that bypasses the intended invariant (`params.oracle == cur.oracle`).

### Impact Explanation
If the object-directory value used to build `AllowedParams.GitObjectDirectory`/`GitAlternateObjectDirectories` diverges from the actual quarantine directory that contains the newly pushed objects, the Rails-side access check (which inspects "new" commits via this quarantine directory to decide things like force-push protection, protected branch rules, or whether commits are reachable/signed) can be fed a stale, empty, or attacker-chosen directory. This can cause the access-check logic to reach incorrect conclusions about what is being pushed - e.g., failing to see the actually pushed commits (bypassing detection of a rejected change) or seeing objects from an unrelated location - undermining hook and quarantine gating guarantees that Gitaly's object-quarantine design (`doc/object_quarantine.md`) explicitly relies on.

### Likelihood Explanation
The concrete exploitability depends on how much control an external actor actually has over the `EnvironmentVariables` field sent on the `PreReceiveHookRequest` in a given deployment; in the mainline flow this is populated from `gitaly-hooks`' own process environment (inherited from `git receive-pack`, which is largely trusted at that specific point), so the primary attack surface is any deviation from that trusted path (custom/second-order callers of `manager.PreReceiveHook`, or any component that forwards externally influenced environment values into this call). The code itself contains no check tying the derived object directory back to the payload's own `Repo.GitObjectDirectory`/quarantine directory, so likelihood is chiefly a function of what other RPCs or integrations feed this function - this could not be fully verified with the available tooling/index, and would benefit from further tracing of all callers of `GitLabHookManager.PreReceiveHook`/`preReceiveHook` to confirm whether the `envs` parameter can carry externally-influenced content in any deployed configuration.

### Recommendation
Do not let `preReceiveHook` recompute `repo.GitObjectDirectory`/`GitAlternateObjectDirectories` from the freeform `envs` argument. Instead, always trust the object-directory fields already present in the verified `payload.Repo` (from `HooksPayloadFromEnv`), and if reconciliation with `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` env values is required for compatibility, assert equality (`params.oracle == cur.oracle`-style check) between the two sources before proceeding, and fail closed on mismatch rather than silently overwriting.

### Proof of Concept
Not independently reproducible from the index alone: constructing a full PoC requires confirming, via tracing every caller of `GitLabHookManager.PreReceiveHook` (`internal/gitaly/service/hook/pre_receive.go` and any gitaly-hooks invocation paths in `cmd/gitaly-hooks/hooks.go`), whether the `EnvironmentVariables` field can be populated with attacker-controlled `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` values distinct from the quarantine directory Gitaly itself created for the push in progress. This would need to be validated in a running Devin session with full source access, since the current index does not expose every caller of this internal manager method with certainty.

```go
func getRelativeObjectDirs(repoPath, gitObjectDir, gitAlternateObjectDirs string) (string, []string, error) {
	repoPathReal, err := filepath.EvalSymlinks(repoPath)
	if err != nil {
		return "", nil, err
	}

	gitObjDirRel, err := filepath.Rel(repoPathReal, gitObjectDir)
	if err != nil {
		return "", nil, err
	}

	var gitAltObjDirsRel []string

	for _, gitAltObjDirAbs := range strings.Split(gitAlternateObjectDirs, ":") {
		gitAltObjDirRel, err := filepath.Rel(repoPathReal, gitAltObjDirAbs)
		if err != nil {
			return "", nil, err
		}

		gitAltObjDirsRel = append(gitAltObjDirsRel, gitAltObjDirRel)
	}

	return gitObjDirRel, gitAltObjDirsRel, nil
}
```

```go
func (m *GitLabHookManager) preReceiveHook(ctx context.Context, payload gitcmd.HooksPayload, repo *gitalypb.Repository, pushOptions, envs []string, changes []byte, stdout, stderr io.Writer) error {
	repoPath, err := m.locator.GetRepoPath(ctx, repo)
	if err != nil {
		return structerr.NewInternal("getting repo path: %w", err)
	}

	if gitObjDir, gitAltObjDirs := env.ExtractValue(envs, "GIT_OBJECT_DIRECTORY"), env.ExtractValue(envs, "GIT_ALTERNATE_OBJECT_DIRECTORIES"); gitObjDir != "" && gitAltObjDirs != "" {
		gitObjectDirRel, gitAltObjectDirRel, err := getRelativeObjectDirs(repoPath, gitObjDir, gitAltObjDirs)
		if err != nil {
			return structerr.NewInternal("getting relative git object directories: %w", err)
		}

		repo.GitObjectDirectory = gitObjectDirRel
		repo.GitAlternateObjectDirectories = gitAltObjectDirRel
	}
```
