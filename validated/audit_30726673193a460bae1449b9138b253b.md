### Title
`ConversationP2P::validate_handshake` accepts replayed Handshake signatures with no session/connection binding - ([File: stackslib/src/net/chat.rs])

### Summary
When a peer's public key is unknown, `validate_handshake` (stackslib/src/net/chat.rs:1058-1071) accepts a `Handshake` message purely on the basis of `message.verify_secp256k1(&handshake_data.node_public_key)` succeeding. That signature check only covers the message's `relayers`, `payload`, and non-signature `Preamble` fields (including `seq`), none of which are derived from or bound to the specific TCP socket/connection the bytes are replayed over.

### Finding Description
`verify_secp256k1` in `stackslib/src/net/codec.rs:1491-1502` builds `message_bits` from `self.relayers.consensus_serialize()` and `self.payload.consensus_serialize()`, then calls `self.preamble.clone().verify(&message_bits, &secp256k1_pubkey)`. The `Preamble.seq` field is a sender-chosen message counter, not a receiver-issued challenge/nonce tied to the TCP session; there is no per-connection random value that the peer must sign fresh for *this* socket. Consequently the exact same signed byte sequence (preamble + relayers + payload) that was valid on `convo_1 -> convo_2` remains bit-for-bit valid — and passes `verify_secp256k1` — when replayed verbatim by an attacker on a brand-new `ConversationP2P`/TCP connection to any node, as long as `handshake_data.expire_block_height > chain_view.burn_block_height` still holds (checked at `stackslib/src/net/chat.rs:1104-1111`). None of the checks in `validate_handshake` (public-key format check, expiry check, self-handshake check) reference the connection's socket address, `conn_id`, or any freshness value tied to the new TCP session in the `None`-public-key branch (`stackslib/src/net/chat.rs:1058-1071`); the address/port equality check only runs in the `Some(_)` branch for outbound connections that already have a learned key (`stackslib/src/net/chat.rs:1072-1091`), which does not apply on first contact. On success, `update_from_handshake_data` (`stackslib/src/net/chat.rs:1131-1160`) binds the new connection's `connection.get_public_key()` to the replayed identity.

### Impact Explanation
An attacker who passively observes one legitimate handshake (handshakes are sent in the clear) can open a new connection and have the target node record that connection as authenticated under the victim peer's public key, without possessing the victim's private key. This is unauthenticated identity assumption of the handshake step itself. However, subsequent P2P messages on that connection (Ping, GetNeighbors, relayed gossip, etc.) still carry their own `Preamble.signature` that must independently verify against the learned public key elsewhere in the dispatch path, and the attacker cannot produce valid signatures for those without the private key. That limits the attacker's ability to forge or have stored/relayed any additional authenticated application data beyond the handshake acceptance itself — the practical blast radius is that the node's neighbor/connection bookkeeping (peer version, services, expire height, `data_url`, and the connection-key association) gets set from stale/replayed data on a socket the attacker controls, until `expire_block_height` elapses.

### Likelihood Explanation
Precondition: attacker only needs to observe one legitimate handshake in transit (no privileged access, no secrets) and be able to open a new TCP connection to a P2P-reachable node — both trivially satisfiable by an unprivileged remote party. The replay is fully repeatable up until the handshake's self-declared `expire_block_height`, which is chosen by the original sender and can be set far in the future.

### Recommendation
Bind the handshake signature (or an accompanying protocol step) to session-specific, receiver-chosen entropy — e.g., require the responder to issue a random nonce/challenge that must be included in the signed handshake payload, or bind the signature to `(local_conn_id, remote socket addr, timestamp)` in addition to `relayers`/`payload`, so a captured handshake cannot be replayed unmodified on a different connection. Alternatively, shorten and randomize effective handshake validity independent of `expire_block_height`, and require the address/port equality check (currently only applied when `self.connection.get_public_key()` is `Some`) to also apply to inbound connections receiving a first handshake, forcing sender-address verification even for previously-unseen peers where feasible.
