### Title
Unauthenticated `RecvError` Packet Allows Remote Tunnel Teardown (Spoofed UDP DoS) - (File: outside.go)

### Summary
`RecvError` packets are dispatched in `readOutsidePackets` before any certificate or handshake-state check is performed, and `handleRecvError` will tear down an existing, fully-authenticated tunnel based solely on an unauthenticated, unencrypted UDP packet whose only "proof" is a 32-bit `RemoteIndex` and a source-address comparison. Like the `testFinalizeSettlement()` case, this is a state-mutating operation reachable by an entity with no cryptographic credential, causing a permanent denial of service against an established, cert-verified session.

### Finding Description
In `readOutsidePackets`, `header.RecvError` is handled in the "Unencrypted packets" switch, prior to any peer certificate verification or Noise handshake completion check: [1](#0-0) 

`handleRecvError` then looks up the hostinfo purely by `h.RemoteIndex` (attacker-supplied, and observable since it is sent in cleartext during a normal handshake), and the only anti-spoofing check is comparing the packet's UDP source address to the currently-recorded remote address of that hostinfo: [2](#0-1) 

Because UDP has no built-in source-address authentication, and Nebula's `RecvError` packets carry no cryptographic signature or MAC, an attacker capable of spoofing the peer's UDP source address (off-path spoofing, or an on-path/adjacent-network attacker who can forge the source IP:port) can synthesize a `RecvError` header with the victim's `RemoteIndex` and this address. This satisfies the `hr == addr` check and results in `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)`, unilaterally destroying a tunnel that was legitimately established between two CA-signed-certificate holders — without the attacker ever presenting a certificate or completing a handshake.

The changelog itself documents "Someone spoofing recv_errors?" as an anticipated risk and previously mitigated by disabling `recv_error` outside the "allowable counter window," and via `listen.send_recv_error`/`ShouldRecvError` gating — but the current gating only controls whether recv_error is sent/accepted for particular endpoint classes (e.g., private vs. public), not whether the index+source-address pair is cryptographically bound to the session.

### Impact Explanation
This allows an unauthenticated remote attacker to force teardown of any active Nebula tunnel it can address (whose `RemoteIndex` it can observe, e.g., by passively watching handshake traffic on the underlay network) purely via UDP spoofing, causing denial of service: the victim's tunnel and pending handshake state are deleted, and reconnection has to happen from scratch. This is analogous to the reported bug class — a reachable, no-privilege-required code path that flips authoritative connection state and can be used to repeatedly disrupt a target's connectivity.

### Likelihood Explanation
Exploitability requires the attacker to know/observe the target's `RemoteIndex` (32-bit value transmitted in cleartext on every packet, trivially sniffable on the underlay path or a shared/broadcast network segment) and to spoof the legitimate peer's current UDP source `ip:port`. UDP source spoofing is a well-known, low-cost technique, especially for attackers on the same LAN/NAT or with routing control, making this reachable without holding any nebula-issued certificate.

### Recommendation
Bind `RecvError` acceptance to the authenticated tunnel state rather than a cleartext index/address comparison: e.g., only accept a `RecvError` if the packet is itself part of an existing authenticated session (e.g., MAC'd/encrypted like other post-handshake packets), or require a monotonically increasing/nonce-based counter validated against the session's replay window, so an off-path/spoofing attacker without the session key cannot force teardown. At minimum, add rate limiting and stricter provenance checks that don't rely solely on comparing spoofable source addresses.

### Proof of Concept
1. Passively observe or infer the `RemoteIndex` used by a target tunnel (visible in cleartext handshake/message headers).
2. Spoof a UDP packet with source address/port equal to the target's current legitimate peer `CurrentRemote`, and craft a header with `Type = header.RecvError`, `RemoteIndex` set to the victim's local index for that session.
3. Send this to the victim's listening UDP port.
4. `readOutsidePackets` routes it directly to `f.handleRecvError` (outside.go:81-84) without any cert/handshake check; the `hr == addr` check at outside.go:564 passes because the source address was spoofed to match; `f.closeTunnel(hostinfo)` (outside.go:572) tears down the tunnel and deletes pending handshake state, forcing the victim to re-handshake — repeatable at will for sustained DoS. func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
