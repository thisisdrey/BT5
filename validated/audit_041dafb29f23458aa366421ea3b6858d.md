## Analysis Summary

The external report's core broken invariant: **value that is only *promised/recorded* is later required to equal (or is settled against) value that is *actually backed*, and when the two diverge, real user funds already collected are permanently stranded with no way to reclaim them.**

The closest verifiable local analog is in the Snowbridge V2 relayer-tip subsystem, which spans `snowbridge-pallet-system-v2`, `snowbridge-pallet-inbound-queue-v2`, and `snowbridge-pallet-outbound-queue-v2`. This exact area already had one bug fixed (`prdoc/stable2509/pr_9746.prdoc` – "Snowbridge Inbound Queue V2 relayer tip payout fix", tips previously "lost since it had already been burnt"), confirming this is a recognized live fault line, and the fix left a structurally identical gap open.

### Title
Permanent loss of relayer-tip funds with no recovery path when tip attachment races message settlement - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

### Summary
`pallet_system_v2::add_tip` forwards a user-originated tip amount to `InboundQueue::add_tip` / `OutboundQueue::add_tip`. If the underlying message/order has already been settled (nonce consumed / `PendingOrders` entry removed) by the time the tip call lands — a race that is entirely possible given the tip and the message delivery-receipt travel through independent, asynchronously-processed extrinsics/XCM hops — the tip fails to attach and is only recorded into `LostTips` as a bookkeeping placeholder. No extrinsic exists anywhere in the pallet to reclaim `LostTips`, so funds already collected from the user (by the frontend before dispatching this call) are permanently and irrecoverably lost.

### Finding Description

On failure it records the lost amount: [2](#0-1) 

The `LostTips` storage comment itself acknowledges the gap — it exists only to "support implementing a recovery method **in the future**": [3](#0-2) 

No such recovery extrinsic exists in the pallet's `#[pallet::call]` block, which contains only `upgrade`, `set_operating_mode`, `register_token`, and `add_tip`.

The race condition itself is structural: `InboundQueue::add_tip` rejects only if the nonce is already consumed — [4](#0-3) 

— and nonce consumption happens inside `process_message`, independently of when a tip call for the same nonce is dispatched: [5](#0-4) 

Similarly for outbound messages, `AddTip::add_tip` fails once `PendingOrders` has been removed by `process_delivery_receipt`: [6](#0-5) [7](#0-6) 

The core defect mirrors the external report exactly: the pallet accounts for "promised value" (the tip a user paid to boost relayer incentive) and "settlement state" (nonce/order consumption) using two independently-timed code paths, with a comparison (`ensure!(!Nonce::<T>::get(nonce))` / `PendingOrders::get(nonce)`) that fails deterministically whenever settlement outpaces tip attachment — a condition an unprivileged relayer can trivially trigger by promptly submitting the delivery proof/receipt as soon as the message is dispatched, before a user's tip transaction lands. The result is not a graceful reject-and-refund; the already-collected user funds are stranded in `LostTips` forever.

### Impact Explanation
This is a permanent user-fund lock reachable by any unprivileged actor: a relayer racing to submit `submit`/`submit_delivery_receipt` before a pending tip is attached causes the tip to be silently and permanently lost. This satisfies the required impact category "permanent user-fund or bridge-state lock" and reflects the pivot requirement that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — here settlement (nonce/order removal) and the tip-crediting operation are not atomic with respect to each other, and the failure branch has no restitution mechanism.

### Likelihood Explanation
High. No adversarial relayer collusion, governance abuse, or leaked keys are required — a normal relayer processing messages promptly (which is the expected/desired behavior of the system) is sufficient to trigger the race whenever a user's tip transaction is submitted with any latency relative to message settlement. This is a naturally-occurring race in production usage, not a contrived edge case, and the same tip-loss class of bug was already found and partially patched once (`pr_9746.prdoc`) for the inbound queue, but the `LostTips` recovery gap was left in place across both inbound and outbound tip paths.

### Recommendation
- Add a `claim_lost_tip` (or `refund_lost_tip`) extrinsic in `pallet_system_v2` that allows the recorded sender to withdraw their accumulated `LostTips` balance, or automatically refund the tip synchronously within the same call that determines it cannot be attached (rather than deferring to an unimplemented future mechanism).
- Alternatively, redesign `add_tip` so that the actual currency movement (withdrawal from `sender`) only occurs after confirming the target order/nonce is still pending, eliminating the possibility of collecting funds for tips that can never be delivered.

### Proof of Concept
1. A user submits a cross-chain message expecting delivery via `snowbridge-pallet-inbound-queue-v2` or `-outbound-queue-v2`, and shortly after, submits (via the frontend) a tip for that message's nonce using `pallet_system_v2::add_tip`.
2. Before the tip-carrying XCM/extrinsic executes, a relayer submits the message's proof (`submit` for inbound, or `submit_delivery_receipt` for outbound), consuming the nonce / removing the `PendingOrders` entry.
3. When the tip call executes, `InboundQueue::add_tip`/`OutboundQueue::add_tip` returns `Err(AddTipError::NonceConsumed)` / `Err(AddTipError::UnknownMessage)`.
4. `pallet_system_v2::add_tip` catches this error and stores the amount in `LostTips::<T>::mutate(&sender, ...)` [2](#0-1) , emits `TipProcessed { success: false, .. }`, and returns `Ok(())` — the call succeeds even though the tip is unrecoverable.
5. Inspecting the pallet's call set confirms there is no extrinsic to withdraw `LostTips`, so the user's already-collected funds are permanently stuck in on-chain storage.

			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}

	impl<T: Config> Pallet<T> {
		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}
