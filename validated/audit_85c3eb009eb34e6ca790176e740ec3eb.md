### Title
Gas-key nonce rows are reset below already-consumed values on re-add, breaking nonce monotonicity / replay protection - ([File: runtime/runtime/src/access_keys.rs])

### Finding Description
`add_gas_key` unconditionally reseeds every nonce slot of a (re-)added gas key to `initial_nonce_value(block_height)`, independent of any progress previously made on that nonce index: [1](#0-0) 

`initial_nonce_value` depends only on the current block height, not on any prior nonce state for that key/account: [2](#0-1) 

`action_add_key` calls `add_gas_key` whenever the public key is not currently present in state (duplicate keys are rejected only if the key *currently exists*, `AddKeyAlreadyExists`): [3](#0-2) 

`action_delete_key` removes the existing gas key/nonce rows (as long as its balance is `<= MAX_BALANCE_TO_BURN`, 1 NEAR): [4](#0-3) 

So within block `h`, a transaction `tx_a` (`GasKeyNonce{ nonce: (h-1)*1_000_000 + k, nonce_index: i }`) advances the stored nonce for index `i` via `set_gas_key_nonce`. A subsequent transaction `tx_b` = `DeleteKey(K) + AddKey(K, GasKeyFullAccess)` deletes `K` (provided its remaining gas-key balance is `<= 1 NEAR`) and re-creates it under the same public key, resetting **all** `N` nonce rows — including index `i` — back down to `(h-1)*1_000_000`, which is below the value written by `tx_a` moments earlier in the same block. `verify_nonce`'s Monotonic check (`tx_nonce > current_nonce`) then permits `tx_a` to be resubmitted and re-applied later in the block/chain, since the stored "current" nonce for index `i` is now lower than `tx_a`'s nonce: [5](#0-4) 

This confirms the invariant break described in the question: `add_gas_key`'s reseed value can land below a nonce value already recorded for that index earlier in the same block, an explicit violation of the "nonce monotonicity prevents replay" invariant documented for this component.

### Impact Explanation
This is a genuine replay-protection weakness: a gas-key-signed transaction (e.g., `Transfer` or `WithdrawFromGasKey`) that already executed and moved funds could, in principle, be resubmitted and re-applied a second time after the nonce reset, because it once again satisfies `tx_nonce > current_nonce`.

However, tracing the concrete monetary consequence shows no asymmetric attacker benefit is achievable:
- `WithdrawFromGasKey` replay fails unless the re-created gas key is refunded with balance at least equal to the withdrawal amount (`action_withdraw_from_gas_key` checks `gas_key_info.balance.checked_sub(action.amount)`), and any such refund costs the attacker exactly as much as they would "regain," yielding no net gain ( [6](#0-5) ).
- A replayed `Transfer` simply debits the attacker's own account balance a second time and credits the same receiver again — the attacker only harms themselves financially; there is no path shown where a third party's funds are stolen or where the attacker extracts value without matching cost.
- `action_delete_key`'s `GasKeyBalanceTooHigh` guard (balance must be `<= 1 NEAR` to delete) further restricts when `tx_b` can even succeed, narrowing the exploitable window.

Because the observable effect is a self-inflicted double-payment/double-withdraw rather than uncompensated fund extraction from another party or the protocol, this does not meet the bar for "theft or permanent freezing of user funds" as defined in scope, despite being a real correctness/invariant bug.

### Likelihood Explanation
Reaching the state requires: an unprivileged attacker's own funded account, a self-controlled `GasKeyFullAccess` key with `num_nonces >= 1`, a `GasKeyNonce` transaction consuming an index within the target block, and a same/later-block `DeleteKey`+`AddKey` pair on the same public key with the gas key's residual balance at or below `MAX_BALANCE_TO_BURN`. All of this is achievable by an ordinary client without validator/node privileges, so the mechanism itself is trivially reproducible — but no reachable scenario nets the attacker more value than they put in, per the Impact analysis above.

### Recommendation
`add_gas_key` should not blindly reseed nonce rows for a key that is being re-added under the same public key within the tracked replay window; either (a) require the new nonce baseline to be `max(initial_nonce_value(block_height), previous_max_nonce_for_this_key)` when re-adding the same public key, or (b) prevent immediate re-use of a just-deleted public key within the same block/validity window, or (c) persist a per-account "highest nonce ever used per public key" independent of key deletion so `verify_nonce` cannot regress. This closes the invariant gap even though no concrete fund-loss exploit was demonstrated here.

### Proof of Concept
Unit test in `runtime/runtime/src/access_keys.rs` test module (pattern matches `test_add_gas_key`):
1. `setup_account`, add a gas key `K` with `num_nonces=1` at `block_height = h`.
2. Call `set_gas_key_nonce` (simulating `tx_a`) to advance index `0` to `(h-1)*1_000_000 + 5`.
3. Call `action_delete_key` for `K` (balance `0`, passes `GasKeyBalanceTooHigh` check), then `action_add_key` re-adding `K` as `GasKeyFullAccess` at the same `block_height = h` (simulating `tx_b`).
4. Assert `get_gas_key_nonce(..., index=0) == (h-1)*1_000_000`, i.e., strictly less than the value written in step 2 — confirming the reseed regresses below the previously recorded nonce.
5. (Documentary, not exploit-confirming) Attempt to re-verify `tx_a`'s nonce via `verify_nonce` against the post-reset value and show it now passes `Monotonic` — but note separately that replaying the underlying action (`Transfer`/`WithdrawFromGasKey`) requires matching funds, so no net value extraction results.

pub(crate) fn action_add_key(
    apply_state: &ApplyState,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    add_key: &AddKeyAction,
) -> Result<(), StorageError> {
    if get_access_key(state_update, account_id, &add_key.public_key)?.is_some() {
        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),
            public_key: add_key.public_key.clone().into(),
        }
        .into());
        return Ok(());
    }

    let fee_config = &apply_state.config.fees;

    if let Some(gas_key_info) = add_key.access_key.gas_key_info() {
        add_gas_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            gas_key_info,
            apply_state.block_height,
        )?;
    } else {
        add_regular_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            apply_state.block_height,
        )?;
    }

    Ok(())
}

pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
            balance: gas_key_info.balance,
            required: action.amount,
        }
        .into());
        return Ok(());
    };
    gas_key_info.balance = updated_balance;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);

    let new_account_balance = account.amount().checked_add(action.amount).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "Account balance integer overflow".to_string(),
        ))
    })?;
    account.set_amount(new_account_balance);
    Ok(())
}

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
