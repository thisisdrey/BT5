### Title
Unbounded array index from attacker-controlled `Contract.type` raw enum value causes uncaught `IndexOutOfBoundsException` during permission check - (File: `chainbase/src/main/java/org/tron/common/utils/WalletUtil.java`)

### Summary
`checkPermissionOperations()` — duplicated in `WalletUtil.java`, `TransactionUtil.java`, and used from `TransactionCapsule.checkPermission()` — indexes a fixed 32‑byte `operations` bitmask using `contract.getTypeValue()` without validating that the value is within `[0, 255]`. Because `Transaction.Contract.type` is a protobuf enum field, an attacker can set its raw wire value to any signed 32‑bit integer (protobuf preserves unrecognized enum raw values), producing an out‑of‑range index and an uncaught `IndexOutOfBoundsException` in a code path that runs during signature/permission validation of every broadcast transaction that uses a non‑default permission id. This is the same bug class as the referenced Wasmtime advisory: a flags/enum-like value from untrusted external input is not masked/validated before being used to compute an index, causing a host-side panic (here, a Java runtime exception) reachable by any unprivileged sender.

### Finding Description
The `operations` field of `Permission` is documented as "1 bit 1 contract" and is always exactly 32 bytes (256 bits), one bit per declared `ContractType` [1](#0-0) .

The permission-bit check computes the byte/bit index directly from the contract's raw enum value with no range check: [2](#0-1) 

The identical unguarded pattern also exists in the actuator module: [3](#0-2) 

`contract.getTypeValue()` returns the *raw* protobuf enum wire value of `Transaction.Contract.type`. Protobuf enums accept any int32 on the wire; unrecognized values are preserved as `UNRECOGNIZED`/raw value rather than rejected at parse time — so a crafted transaction can set this field to an arbitrary integer (e.g. 100000 or a negative number), and `contractType / 8` / `contractType % 8` will produce an index far outside the bounds of the 32‑byte `operations` array, or a negative index, triggering `IndexOutOfBoundsException` when `ByteString.byteAt()` is invoked.

This check is reached from `TransactionCapsule.checkPermission()`, invoked by `validateSignature()`: [4](#0-3) [5](#0-4) 

Critically, the permission does not need to be attacker-defined via `AccountPermissionUpdateContract` at all: if `permissionId == 2` and the account does not even exist yet, a default active permission is synthesized on the fly and still fed into the same unguarded check: [6](#0-5) 

Finally, `validatePubSignature()` — the entry point used for transaction signature validation — only catches `SignatureException | PermissionException | SignatureFormatException`, not generic `RuntimeException`, so the `IndexOutOfBoundsException` propagates uncaught out of this method: [7](#0-6) 

Note that `AccountPermissionUpdateActuator.checkPermission()` does correctly bound-check operation bits against `getAvailableContractType()` when a custom permission is *created* [8](#0-7)  — but that validation is irrelevant here because the out-of-range value is the *incoming contract's type*, not the stored permission's operations bytes.

### Impact Explanation
An uncaught runtime exception thrown while validating a broadcast transaction's signature/permission is a guest(transaction)-controlled panic reachable by any unprivileged, unauthenticated transaction sender (matching CWE-248 / DoS characterization of the reference advisory, CVSS `A:H`). Depending on where in the pipeline this validation is invoked (mempool ingestion, `pushTransaction`, or block application), it can crash transaction processing for that node, potentially halting further processing or requiring a restart — a node-crash/DoS impact.

### Likelihood Explanation
Likelihood is high: the attacker only needs to craft raw protobuf bytes for a `Transaction.Contract` where the `type` field's wire varint is an out-of-range value (e.g., > 255) and set `permission_id = 2` (or a valid custom permission id on an account with multisig enabled), then broadcast the transaction through the normal `wallet/broadcasttransaction` path. No special privileges, keys, or prior on-chain state are required beyond crafting the raw bytes; standard protobuf tooling used server-side will happily construct/parse such a message since enum fields don't validate range.

### Recommendation
Bound-check `contractType` before indexing into `operations` in all three implementations (`WalletUtil.checkPermissionOperations`, `TransactionUtil.checkPermissionOperations`, and any duplicate logic in `TransactionCapsule`): reject/throw `PermissionException` when `contractType < 0 || contractType >= operations.size() * 8` before computing `byteAt()`. Additionally, have `validatePubSignature()` catch generic `RuntimeException` (or specifically `IndexOutOfBoundsException`) and convert it into a `ValidateSignatureException`/`PermissionException` so malformed input cannot escape as an unchecked exception.

### Proof of Concept
1. Construct a `Transaction` whose `raw_data.contract[0]` has:
   - `parameter`: any valid `Any`-packed contract (e.g., a `TransferContract`).
   - `type`: encode the enum field's wire varint with a raw value outside `[0,255]`, e.g. `100000` (protobuf allows arbitrary int32 for enum wire values; parsing succeeds with `getType()==UNRECOGNIZED`, `getTypeValue()==100000`).
   - `Permission_id`: `2`.
2. Sign the transaction with a valid signature for a fresh (non-existent or existing) owner address.
3. Submit it via `wallet/broadcasttransaction` (or push through P2P/block relay).
4. During validation, `TransactionCapsule.validateSignature()` → `checkPermission()` → `checkPermissionOperations()` computes `operations.byteAt(100000/8)` on a 32-byte `ByteString`, throwing `IndexOutOfBoundsException`, which is not caught by `validatePubSignature()`'s catch clause and propagates as an unhandled exception in the transaction validation path.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
