I have enough evidence to write up the strongest analog found: CREATE2 address front-running in the TVM, which mirrors the "user-controllable ID that a front-runner can occupy first" bug class from the OpenQ report but with materially worse impact (theft of pre-funded assets, not just a reverted transaction).

### Title
CREATE2 deployment front-running allows theft of value pre-funded to a counterfactual contract address - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
The TVM `CREATE2` opcode computes a new contract's address deterministically from `sender ++ salt ++ keccak256(initcode)` via `WalletUtil.generateContractAddress2`, and the deploying transaction is a normal broadcastable contract-call transaction (`TriggerSmartContract`). Just like `OpenQV1.mintBounty`, where the "id" of the object being created is fully attacker-observable/front-runnable, the `newAddress` for a `CREATE2` deployment is knowable to any observer of the mempool before it lands on-chain, and nothing about the deployment (other than salt/sender/initcode) is bound to any specific transaction ordering guarantee.

### Finding Description
The `CREATE2` opcode handler `create2Action` in [1](#0-0)  calls `program.createContract2`, which computes the deterministic address via [2](#0-1) :

```java
byte[] contractAddress = WalletUtil
    .generateContractAddress2(senderAddress, salt.getData(), programCode);
createContractImpl(value, programCode, contractAddress, true);
```

using `generateContractAddress2` in [3](#0-2) . Because this address depends only on `(senderAddress, salt, initcode)` — all of which are visible in the pending transaction — an attacker who observes a pending deployment can precompute the same address and race a transaction of their own to that address first.

`createContractImpl` in [4](#0-3)  checks whether an account already exists at that address; if the account exists but has no contract code yet (e.g. it was merely funded, not deployed-to), `contractAlreadyExists` remains false and the *attacker's* initcode is what gets deployed to that address, taking over `AccountType.Contract` for it via `existingAccount.updateAccountType(...)`. Only if a contract was already deployed there does the legitimate deployer's transaction fail with "Trying to create a contract with existing contract address" (see the pre-check in `VMActuator` at [5](#0-4) , and the analogous revert inside internal `CREATE2` at [6](#0-5) ).

This is the CREATE2 counterfactual-deployment pattern widely used by factories/wallets (e.g. pre-funding an address before deploying the real contract logic there, a pattern the codebase's own tests exercise, e.g. `freezeForOther(contractAddr, predictedAddr, ...)` before `deployCreate2Contract` in [7](#0-6) , and `getCreate2Addr`/`deployCreate2Contract` helpers at [8](#0-7) ). If TRX or delegated resources are sent to the precomputed address before the legitimate deploy transaction confirms, an attacker who front-runs the deploy with their own initcode becomes the contract owner of that address and can withdraw/control whatever was already deposited there.

### Impact Explanation
This is a direct fund-theft primitive, not just a reverted-transaction annoyance as in the original OpenQ report: any TRX (or delegated/frozen resources) sent to a not-yet-deployed `CREATE2` address before the real deployment lands can be permanently stolen by an attacker who front-runs with malicious bytecode, since the attacker's contract — not the intended one — ends up owning that address's balance and state.

### Likelihood Explanation
Any unprivileged account can call a factory contract's `CREATE2`-based deploy function, and any observer of pending transactions (including via public mempool/API monitoring) can react by broadcasting a higher-fee-limit transaction to the same target address before the original confirms, exactly mirroring the front-running mechanics described in the source report.

### Recommendation
Factories and application-level contracts using `CREATE2` should avoid pre-funding counterfactual addresses before deployment, or should include deployer/salt binding and post-deploy verification. At the protocol level, consider documentation/warnings around `CREATE2` counterfactual-deployment patterns, since java-tron's opcode semantics here mirror upstream EVM `CREATE2` and inherit the same well-known front-running risk; no code change is strictly required unless java-tron wants to add extra safeguards (e.g. reserving the address once initcode-hash/salt/sender is first observed in a transaction, which is not how EVM/TVM CREATE2 works and would be a protocol-level behavior change).

### Proof of Concept
1. A factory contract deploys logic via `CREATE2` with `salt` and `initcode` chosen by a legitimate user; the resulting address is computed with `generateContractAddress2(sender, salt, code)` ( [9](#0-8) ).
2. The legitimate user (or a third party) sends TRX to that precomputed address in advance (a common counterfactual-funding pattern, as exercised by the test helper `getCreate2Addr`/`freezeForOther` sequence in [7](#0-6) ).
3. Before the legitimate deploy transaction confirms, an attacker observing the mempool computes the same address (since `sender`, `salt`, and `initcode` are all visible pre-confirmation) and broadcasts their own `CREATE2` call from a contract they control, using different initcode but landing at the same address, with a higher fee/priority so it confirms first.
4. `createContractImpl` in [4](#0-3)  sees `contractAlreadyExists == false` (the address only holds a funded EOA-type account, no code yet) and deploys the attacker's contract there, taking ownership of the account's balance; the legitimate deployer's later transaction then fails validation ("Trying to create a contract with existing contract address").

  // for `CREATE2`
  public static byte[] generateContractAddress2(byte[] address, byte[] salt, byte[] code) {
    byte[] mergedData = ByteUtil.merge(address, salt, Hash.sha3(code));
    return Hash.sha3omit12(mergedData);
  }
