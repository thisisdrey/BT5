### Title
Permanently stuck vote-rewards for cycles where a witness's recorded vote total is zero - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
java-tron distributes voter-reward emissions to super representatives (SRs) per "cycle," snapshotting each witness's vote total once per maintenance cycle and crediting block/transaction-fee rewards to the SR's reward pool for that cycle independently of that snapshot. When a witness's recorded vote total for a given cycle is `0`, the vote-reward computation silently skips distribution for that cycle, and the previously credited reward for that (cycle, witness) pair becomes permanently unclaimable by any account — the exact "stuck emissions when TVL is zero" pattern described in the external report, with no treasury-recovery path implemented.

### Finding Description
Every maintenance cycle, `MaintenanceManager.doMaintenance()` snapshots the vote total for **every** witness (not only active/standby ones with `voteCount >= 1`) into `DelegationStore` for the *next* cycle: [1](#0-0) 

Separately, whenever a witness produces a block or collects transaction fees, `MortgageService.payReward()` unconditionally adds the post-brokerage reward portion into the *current* cycle's reward pool for that witness, with no check on the witness's recorded vote total for that cycle: [2](#0-1) 

Later, when a voter tries to withdraw their share, `MortgageService.computeReward(cycle, votes)` (old algorithm) looks up the total vote for that witness/cycle and — if it is `0` (or `REMARK`) — simply `continue`s, discarding the reward contribution for that cycle entirely: [3](#0-2) 

The same "zero divisor → drop the reward" pattern also exists in the new Vi-based algorithm: `DelegationStore.accumulateWitnessVi()` / `RewardViCalService.accumulateWitnessVi()` explicitly skip accumulating the delta-Vi when `voteCount == 0`, even if `reward != 0` for that cycle: [4](#0-3) [5](#0-4) 

The active-witness set (used to determine who actually produces blocks and thus earns `payBlockReward`) is built from `getAllWitnesses()`/`getActiveWitnesses()` with no minimum-vote filter, unlike the standby-witness path which explicitly excludes zero-vote witnesses (`ret.removeIf(w -> w.getVoteCount() < 1);`): [6](#0-5) 

Because `WitnessCreateContract`-created candidates start with `voteCount = 0`, and because vote-count changes are only tallied at maintenance boundaries (`countVote`/`setWitnessVote`), it is possible for a witness whose recorded vote total for a cycle is `0` (e.g., a brand-new candidate promoted into the active/standby set on a chain with fewer candidates than slots, or an SR whose voters fully un-delegate right at a maintenance boundary) to still produce blocks and earn `payBlockReward`/`payTransactionFeeReward` for that cycle. The reward money credited to that (cycle, witness) key in `DelegationStore` then becomes permanently unclaimable: no voter can claim a share (division-by-zero guard skips it), and there is no code path anywhere in `MortgageService`, `VoteRewardUtil`, or `WithdrawRewardProcessor` that reclaims or redirects this stranded amount (unlike the cited fix's "send back to treasury" pattern).

### Impact Explanation
This results in permanent freezing of freshly-issued TRX block/tx-fee reward emissions: funds are minted into the reward accounting layer but become forever unreachable by any account once the responsible cycle's vote-total snapshot is `0`. This is a protocol-level accounting bug reachable purely through the standard reward-distribution pipeline (block production, maintenance cycles, and any account's `WithdrawBalanceActuator`/`withdrawReward` TVM opcode), not requiring any special privilege — it manifests as silently lost value with no recovery mechanism.

### Likelihood Explanation
Occurring requires a witness's cycle-scoped vote snapshot to be `0` while it still earns block/tx-fee rewards for that same cycle — plausible on any deployment with fewer real SR candidates than the configured witness slots (common on new/private/test networks, or transiently on mainnet during large-scale un-delegation), and structurally guaranteed by the fact that `getAllWitnesses()`/active-witness selection has no `voteCount >= 1` guard (contrasted with `getWitnessStandby()`'s explicit filter). No attacker action is required — this is a naturally occurring edge case in the existing reward pipeline.

### Recommendation
Mirror the Y2K fix pattern: when crediting `payReward`/`payBlockReward`/`payTransactionFeeReward` for a witness whose current cycle vote total is `0`, either (a) redirect the entire post-brokerage reward directly to the witness owner (since there are no voters to share it with) instead of storing it in the unclaimed voter-reward pool, or (b) track and refund/reclaim reward amounts for (cycle, witness) pairs whose recorded vote total is `0` back to the block/tx-fee reward treasury instead of silently discarding them in `computeReward`/`accumulateWitnessVi`.

### Proof of Concept
1. On a network where the number of witness candidates is smaller than the configured active-witness/standby slots (or where an SR's voters fully un-delegate right before a maintenance boundary), a witness ends up in the active set for cycle N with a `DelegationStore` vote-total snapshot of `0` for that cycle (`MaintenanceManager.doMaintenance()` line 160 records `witness.getVoteCount()` unconditionally for all witnesses).
2. That witness produces a block during cycle N; `Manager`/consensus invoke `MortgageService.payBlockReward()`, which calls `payReward()` and unconditionally calls `delegationStore.addReward(cycle, witnessAddress, value)` regardless of the recorded `0` vote total.
3. Any account that had voted for this witness attempts `withdrawReward` (via `WithdrawBalanceActuator` or the TVM `withdrawReward` opcode/`VoteRewardUtil.withdrawReward`); `computeReward` sees `totalVote == 0` for cycle N and `continue`s, so no portion of the credited reward is ever paid out.
4. The reward value stored under the `(cycle N, witnessAddress)` key in `DelegationStore` remains permanently inaccessible — no function in the codebase reads it back out or redirects it elsewhere.

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

```java
  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
```
