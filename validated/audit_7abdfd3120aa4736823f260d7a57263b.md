### Title
Gas-key `FunctionCallPermission.allowance` is never enforced or decremented in `verify_and_charge_gas_key_tx_ephemeral`, allowing spend beyond the declared allowance cap - (File: `runtime/runtime/src/verifier.rs`)

### Summary
`verify_and_charge_gas_key_tx_ephemeral` only calls `verify_function_call_permission` for gas keys carrying a `FunctionCallPermission`, but never calls `check_and_compute_new_allowance`, and the returned `AccessKeyUpdate::GasKey` only carries `new_balance`, never a new allowance. As a result, `FunctionCallPermission.allowance` set on a `GasKeyFunctionCall` permission is dead data: it is never checked against cumulative spend and never decremented, so the only real spending limit is `gas_key_info.balance`.

### Finding Description
The regular (non-gas-key) path, `verify_and_charge_tx_ephemeral`, explicitly enforces the allowance: [1](#0-0) 
which calls `check_and_compute_new_allowance` — the function that subtracts `total_cost` from `fc.allowance` and fails with `NotEnoughAllowance` on underflow: [2](#0-1) 

The gas-key path, `verify_and_charge_gas_key_tx_ephemeral`, does the FunctionCall constraint check (receiver/method/deposit) via `verify_function_call_permission`, but does **not** call `check_and_compute_new_allowance` anywhere in its body: [3](#0-2) 
The only balance check performed is against `gas_key_info.balance` for the gas portion of cost, and `account.amount()` for the deposit portion: [4](#0-3) [5](#0-4) 

The resulting `AccessKeyUpdate::GasKey` variant only ever carries `new_balance`, `nonce_index`, and `nonce` — there is no `new_allowance` field, and `VerificationResult::apply` for the `GasKey` variant only writes `gas_key_info_mut().balance`, never touching `permission.function_call_permission_mut().allowance`: [6](#0-5) 

Since `AccessKeyPermission::GasKeyFunctionCall(GasKeyInfo, FunctionCallPermission)` allows `access_key.permission.function_call_permission()` to return `Some(fc)` with a populated `allowance` even for gas keys, an attacker can create such a key, declare a small `allowance`, and still spend up to the full `gas_key_info.balance` against `receiver_id` — the `allowance` field is silently ignored.

### Impact Explanation
This is an authorization-scope defect: `FunctionCallPermission.allowance` is documented/designed as a hard spending cap distinct from the funding balance (as demonstrated by the enforced semantics in the non-gas-key path and by existing tests asserting allowance decrements for regular FunctionCall keys, e.g. `test_validate_transaction_invalid_not_enough_allowance`). For gas keys, that cap is dead code. Any relayer or delegation model that trusts a gas key's `allowance` value to bound how much a delegated party can spend against a specific `receiver_id` is defeated — the delegated party can spend up to the full prepaid `gas_key_info.balance` instead of the intended, smaller `allowance`. This does not let the attacker steal funds from other users' accounts (the balance still comes from the attacker's own gas key), but it breaks an authorization/scoping guarantee that other code paths and tests treat as enforced, and is a genuine spec-vs-implementation mismatch that could mislead systems relying on allowance semantics for scoped delegation.

### Likelihood Explanation
Trivial to trigger: any unprivileged account can add a gas key via `AddKey` with `AccessKey::gas_key_function_call(num_nonces, FunctionCallPermission{allowance: Some(small), receiver_id, method_names: []})`, fund it via `TransferToGasKey`, and then submit `num_nonces` gas-key transactions against `receiver_id`, each consuming `gas_cost`/`deposit_cost` from `gas_key_info.balance`/account balance respectively — never from `allowance`. No special preconditions beyond normal account operation are needed, and the behavior is 100% repeatable since it is a structural omission in `verify_and_charge_gas_key_tx_ephemeral`, not a race or edge case.

### Recommendation
In `verify_and_charge_gas_key_tx_ephemeral`, call `check_and_compute_new_allowance` (or an equivalent) when `access_key.permission.function_call_permission()` returns `Some(fc)` with `fc.allowance` set, tracking cumulative cost against the declared allowance analogous to the regular path. Extend `AccessKeyUpdate::GasKey` to also carry `new_allowance: Option<Balance>`, and update `VerificationResult::apply` to write it back into `permission.function_call_permission_mut().allowance` alongside the balance update.

### Proof of Concept
Unit test in `runtime/runtime/src/verifier.rs` test module (alongside `setup_gas_key_account` and existing gas-key tests like `test_gas_key_tx_deposit_failed_for_account_balance`):
1. Create a gas key via `AccessKey::gas_key_function_call(num_nonces=3, FunctionCallPermission{allowance: Some(X), receiver_id: bob, method_names: []})`, fund `gas_key_info.balance` to a value `>> X` (e.g. `100 * X`).
2. For `nonce_index in 0..3`, build a `FunctionCall` transaction targeting `bob`, compute `cost = tx_cost(...)`, and call `verify_and_charge_gas_key_tx_ephemeral` with increasing nonce per index, accumulating `total_cost_charged += cost.total_cost` (or `gas_cost`+`deposit_cost`).
3. Assert `TxVerdict::Success` is returned for all three calls despite `total_cost_charged > X` (the declared allowance).
4. Expected (fixed) behavior: once cumulative cost exceeds `X`, the call should return `TxVerdict::Failed(InvalidTxError::InvalidAccessKeyError(NotEnoughAllowance{..}))`; the current code returns `Success` every time as long as `gas_key_info.balance` covers it, confirming the allowance is unenforced for gas keys.

fn check_and_compute_new_allowance(
    access_key: &AccessKey,
    account_id: &AccountId,
    public_key: &PublicKey,
    total_cost: Balance,
) -> Result<Option<Balance>, InvalidTxError> {
    let Some(fc) = access_key.permission.function_call_permission() else {
        return Ok(None);
    };
    let Some(allowance) = fc.allowance else {
        return Ok(None);
    };
    let new_allowance = allowance.checked_sub(total_cost).ok_or_else(|| {
        InvalidTxError::InvalidAccessKeyError(InvalidAccessKeyError::NotEnoughAllowance {
            account_id: account_id.clone(),
            public_key: public_key.clone().into(),
            allowance,
            cost: total_cost,
        })
    })?;
    Ok(Some(new_allowance))
}

/// Describes how to update the access key after a verified transaction.
#[derive(Debug, Clone, PartialEq)]
pub enum AccessKeyUpdate {
    /// Regular tx: set access_key.nonce, update allowance if specified.
    Regular { nonce: Nonce, new_allowance: Option<Balance> },
    /// Gas key tx: set gas_key_info.balance and persist external nonce.
    GasKey { new_balance: Balance, nonce_index: NonceIndex, nonce: Nonce },
}

impl VerificationResult {
    /// Apply the state changes described by this result to the given account and access key.
    pub fn apply(&self, account: &mut Account, access_key: &mut AccessKey) {
        account.set_amount(self.new_account_amount);
        match &self.access_key_update {
            AccessKeyUpdate::Regular { nonce, new_allowance } => {
                access_key.nonce = *nonce;
                if let Some(a) = new_allowance {
                    access_key.permission.function_call_permission_mut().unwrap().allowance =
                        Some(*a);
                }
            }
            AccessKeyUpdate::GasKey { new_balance, .. } => {
                access_key.gas_key_info_mut().unwrap().balance = *new_balance;
            }
        }
    }
