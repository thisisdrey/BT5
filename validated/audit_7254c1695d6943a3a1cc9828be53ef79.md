### Title
Firewall `ca_name` rule identity resolved dynamically against the live CA pool, letting an unrelated CA-pool change silently alter already-defined firewall trust decisions - (File: firewall.go)

### Summary
Firewall rules that reference `ca_name` are not bound to a fixed CA identity (fingerprint) at the time the rule is written/loaded. Instead, each packet re-resolves the peer certificate's issuer against whatever CA pool happens to be live at match time via `caPool.GetCAForCert()`, then indexes into the rule's `CANames` map by the resolved CA's current `Name()` string [1](#0-0) . Because that resolution is deferred to packet-processing time rather than fixed when the rule/policy was defined, a later, independent change to the trusted CA set (e.g. a `pki.ca` reload that adds/replaces a CA sharing the same `Name()`) can change which certificates satisfy a firewall rule without the rule itself, or the administrator who defined it, being involved in that decision.

### Finding Description
`FirewallCA.match` performs the CA-based rule lookup like this:

```go
func (fc *FirewallCA) match(p firewall.Packet, c *cert.CachedCertificate, caPool *cert.CAPool) bool {
	...
	s, err := caPool.GetCAForCert(c.Certificate)
	if err != nil {
		return false
	}
	return fc.CANames[s.Certificate.Name()].match(p, c)
}
``` [1](#0-0) 

`GetCAForCert` looks the signer up purely by the certificate's `Issuer()` fingerprint string in the pool's `CAs` map and returns whichever `CachedCertificate` is currently registered under that key [2](#0-1) . The `caPool` passed into `Drop()`/`match()` is fetched by the caller from the live `PKI` state at packet time, not the CA pool that existed when the firewall rule was authored via `AddRule`/`NewFirewallFromConfig`. `AddRule` only records a hash of the rule's static config values (`caName`, `caSha`, groups, host, cidr, etc.) for versioning/reload-diffing purposes — it never captures anything about the actual CA pool contents [3](#0-2) .

Firewall reload logic (`reloadFirewall`) only rebuilds the firewall object when the `firewall` config block changes or when the certificate's `UnsafeNetworks` change; it does not react to, or version, changes in the trusted CA pool [4](#0-3) . So an operator who writes a rule like `ca_name: corp-ca` is implicitly trusting that "corp-ca" will always mean the same underlying signing key. If the CA pool is later reloaded to add (or replace) a CA whose `Name()` also resolves to `corp-ca` (CA names are administrator-chosen strings, not enforced-unique cryptographic identities), every certificate signed by that new CA instantly satisfies the pre-existing rule for every future packet — including for tunnels that were already established and firewall-approved under the old CA's trust boundary — with no change to the firewall rule text and no re-approval step. This is the direct structural analog of the Llama `authorized_scripts` bug: a security-relevant decision (here, "does this peer's CA satisfy rule X") is bound to a mutable external mapping (issuer fingerprint → CA object → `Name()` string) that a different administrative action can silently redefine after the rule was written, rather than being pinned to the CA identity at rule-definition time (which is exactly what `ca_sha` does correctly, by contrast, since it compares against `c.Certificate.Issuer()` directly, a fixed fingerprint [5](#0-4) ).

### Impact Explanation
If two or more CAs in the pool ever end up sharing the same `Name()` (via legitimate reload, CA rotation, or a compromised/malicious `pki.ca` addition that an attacker can influence through configuration/CA-management tooling), traffic signed by the "wrong" CA can be silently authorized by rules intended to scope trust to a specific CA. This is a firewall bypass / policy-poisoning vector: the rule author's original intent ("only allow hosts signed by our named CA") is not cryptographically pinned, so trust can migrate to an unintended signer without any change to the firewall configuration itself. Severity is comparable to the original report's "Medium" — it depends on CA-pool changes happening independently of firewall rule authorship, exactly like the original bug depended on the `authorizedScripts` mapping changing independently of action approval.

### Likelihood Explanation
This requires the CA pool to actually contain two identically-named CAs, or for a reload to swap the CA behind a given name — this is an administrative/config precondition, not something an unauthenticated remote attacker can trigger directly. However, per the report's own framing (the original Llama bug was also gated on a separate governance/action being taken by "different signers"), this is a real design gap: `ca_name` rules are fundamentally name-based rather than identity-pinned, and nothing in the codebase enforces or warns that CA names must be unique across pool reloads, nor does `reloadFirewall`/rule versioning ever account for CA pool contents changing underneath a live rule set.

### Recommendation
- Prefer/require `ca_sha` (fingerprint-pinned) over `ca_name` for security-sensitive firewall rules, or deprecate `ca_name` rule matching entirely.
- If `ca_name` is retained, resolve and pin the CA's fingerprint at rule-add time (`AddRule`) rather than re-resolving `Name()` dynamically per packet against the live pool, so a later CA pool change cannot silently repoint an existing rule.
- Enforce CA name uniqueness within `CAPool.AddCA`/`AddCAFromPEM`, or emit a loud warning/reject when a newly added CA's `Name()` collides with an existing CA's `Name()`.
- Include a hash of the current CA pool's `(fingerprint, name)` mapping in the firewall's `rulesVersion`/reload-change detection so CA pool changes trigger firewall re-evaluation/audit logging, mirroring how `unsafeNetworks` changes already trigger a firewall rebuild in `reloadFirewall` [6](#0-5) .

### Proof of Concept
Conceptual sequence (config/administrative, mirroring the original report's action-approval scenario):
1. Admin writes a firewall rule: `ca_name: corp-ca` intended to trust only certificates issued by the currently-loaded CA whose `Certificate.Name() == "corp-ca"`.
2. Later, an unrelated `pki.ca` reload adds a second CA (from a different key/source) whose `Name()` field is also set to `"corp-ca"` — this is legal because CA name uniqueness is not enforced in `AddCA`/`AddCAFromPEM`.
3. Any peer holding a valid certificate signed by the new CA (with matching name) now satisfies the pre-existing firewall rule via `FirewallCA.match` → `caPool.GetCAForCert` → `fc.CANames["corp-ca"]`, without the firewall rule itself, or the person who authored it, ever having approved trust for that new CA [7](#0-6) .
4. Existing tunnels/policies keyed on `ca_name` silently change behavior at the next packet evaluation, with no firewall reload event logged (since `reloadFirewall` doesn't track CA pool changes) [4](#0-3) .

func (fc *FirewallCA) match(p firewall.Packet, c *cert.CachedCertificate, caPool *cert.CAPool) bool {
	if fc == nil {
		return false
	}

	if fc.Any.match(p, c) {
		return true
	}

	if t, ok := fc.CAShas[c.Certificate.Issuer()]; ok {
		if t.match(p, c) {
			return true
		}
	}

	s, err := caPool.GetCAForCert(c.Certificate)
	if err != nil {
		return false
	}

	return fc.CANames[s.Certificate.Name()].match(p, c)
}

// GetCAForCert attempts to return the signing certificate for the provided certificate.
// No signature validation is performed
func (ncp *CAPool) GetCAForCert(c Certificate) (*CachedCertificate, error) {
	issuer := c.Issuer()
	if issuer == "" {
		return nil, fmt.Errorf("no issuer in certificate")
	}

	signer, ok := ncp.CAs[issuer]
	if ok {
		return signer, nil
	}

	return nil, ErrCaNotFound
}
```
