### Title
Forced dust deposits fill a victim's `MAX_TOKENS_PER_USER` slots, DoS-ing mints, transfers, and liquidations for that account - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` enforce a combined cap of `MAX_TOKENS_PER_USER = 30` per account and revert with `UserReachedMaxTokens` once reached [1](#0-0) [2](#0-1) . Because `DepositToken.deposit(amount_, onBehalfOf_)` lets any caller mint msdTOKEN to an arbitrary beneficiary [3](#0-2) , and `_mint`/`_transfer` unconditionally call `pool.addToDepositTokensOfAccount` for a first-time holder [4](#0-3) [5](#0-4) , an unprivileged attacker can dust-fill a victim's token list and make every subsequent operation that would add a new token revert.

### Finding Description
The bug class (uncontrolled resource consumption leading to DoS) maps to the per-account token-list resource. There is no check that `onBehalfOf_` consented to receive a deposit, and there is no minimum deposit amount. An attacker iterates over all registered `DepositToken`s (and can additionally dust-transfer msdTOKENs they hold) calling `depositToken.deposit(1, victim)` until `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30`. From that point:

- `DebtToken` mint/issue/flashIssue paths that call `addToDebtTokensOfAccount` revert → victim cannot borrow any new synthetic asset.
- `DepositToken._transfer` → `addToDepositTokensOfAccount(recipient)` reverts → victim cannot receive any deposit token they don't already hold, including `seize` proceeds from `Pool.liquidate` [6](#0-5) .
- Any contract/EOA that cannot itself unwind positions (e.g., integrations, multisig/gnosis flows routed through `Operator.execute`, liquidator contracts receiving collateral) is blocked until slots are manually freed.

The attacker can recover the dust collateral by withdrawing afterwards, so cost is essentially gas.

### Impact Explanation
Temporary freezing of funds and denial of core protocol functions for the targeted account: the victim is prevented from opening new debt positions, receiving collateral token transfers, or acting as a liquidation/seize recipient for tokens not already in their list. If applied to known liquidator addresses, it can also transiently block `Pool.liquidate` (seize to the liquidator reverts), degrading liquidation liveness for positions that would pay out a new collateral type.

### Likelihood Explanation
Fully permissionless: `deposit` only requires `whenNotPaused`, `onlyIfDepositTokenExists`, nonzero amount, and nonzero beneficiary [7](#0-6) . No modifier (`SynthContext._msgSender`, pause, health checks, reentrancy guards) prevents dust deposits to arbitrary accounts. Mitigating factor: an EOA victim can free slots by transferring dust out (balance → 0 triggers `removeFromDepositTokensOfAccount` [8](#0-7) ), so the freeze is temporary and the attacker's cost scales with the number of registered tokens.

### Recommendation
Enforce a minimum deposit amount in `DepositToken.deposit`, or add an opt-in/allowlist for third-party `onBehalfOf_` deposits; alternatively, don't count zero-or-dust positions toward `MAX_TOKENS_PER_USER`, or raise/decouple the cap so forced additions cannot starve the victim's list.

### Proof of Concept
Foundry fork test outline:

```solidity
function test_dustFillUserTokenSlots() public {
    address victim = makeAddr("victim");
    address[] memory dts = pool.getDepositTokens();

    // Attacker deposits 1 wei of underlying of each deposit token on behalf of victim
    for (uint i; i < dts.length && pool.getDepositTokensOfAccount(victim).length < 30; ++i) {
        IDepositToken dt = IDepositToken(dts[i]);
        IERC20 underlying = dt.underlying();
        deal(address(underlying), attacker, 1);
        vm.startPrank(attacker);
        underlying.approve(address(dt), 1);
        dt.deposit(1, victim); // adds dt to victim's depositTokensOfAccount
        vm.stopPrank();
    }

    // Victim's list is now at MAX_TOKENS_PER_USER
    uint total = pool.getDepositTokensOfAccount(victim).length
               + pool.getDebtTokensOfAccount(victim).length;
    assertEq(total, pool.MAX_TOKENS_PER_USER());

    // Any new-token mint/transfer/seize to victim reverts
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    otherDepositToken.transfer(victim, 1); // via _transfer -> addToDepositTokensOfAccount
}
```

Run against a mainnet fork where the Pool has enough registered DepositTokens (or mix real deposits with dust `transfer`s) so the combined deposit+debt list reaches 30.

        address _msgSender = _msgSender();

        uint256 _balanceBefore = _underlying.balanceOf(_treasury);
        _underlying.safeTransferFrom(_msgSender, _treasury, amount_);

        if (_fee > 0) {
            _mint(_pool.feeCollector(), _fee);
        }

        emit CollateralDeposited(_msgSender, onBehalfOf_, amount_, _deposited, _fee);
    }
