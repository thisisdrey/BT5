### Title
Bancor-style Exchange pool can be permanently bricked, locking the creator's remaining token balance forever - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Java-tron's TRX/TRC10 Bancor exchange (`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeTransactionActuator`, `ExchangeWithdrawActuator`) treats an exchange whose `firstTokenBalance` or `secondTokenBalance` reaches exactly `0` as permanently "closed": every actuator that touches the exchange rejects the transaction once either side is `0`, and there is no other actuator or code path capable of moving funds out of the pool. This mirrors the reported Y2K `ControllerPeggedAssetV2` bug class ("no path to reclaim funds once the contract enters a terminal state"), except here the funds are TRX/TRC10 tokens escrowed inside a java-tron native `Exchange` object that any unprivileged account can reach and inadvertently (or maliciously) freeze.

### Finding Description
`ExchangeCapsule.transaction()` updates both token balances after each trade with plain arithmetic (non-hardened path) and has no floor check preventing a balance from reaching exactly `0`: [1](#0-0) 

Once `firstTokenBalance == 0 || secondTokenBalance == 0`, all three actuators that can subsequently touch the exchange immediately throw and refuse to execute:

- `ExchangeTransactionActuator.doValidate()`: [2](#0-1) 

- `ExchangeWithdrawActuator.doValidate()`: [3](#0-2) 

- `ExchangeInjectActuator` contains the identical check (confirmed via `grep_search` matches in `ExchangeInjectActuator.java`).

The only actuator capable of moving assets out of an `Exchange` capsule back to a user account is `ExchangeWithdrawActuator.execute()`, which computes `anotherTokenQuant` as a ratio of `firstTokenBalance`/`secondTokenBalance` — a computation that is mathematically undefined (division by zero) once either side is `0`, hence the pre-emptive guard: [4](#0-3) 

There is no `ExchangeClose`, `ExchangeCancel`, or committee/owner override actuator in `actuator/src/main/java/org/tron/core/actuator/` (verified by listing the actuator package) that allows the exchange creator, or anyone, to sweep the remaining non-zero token balance once the pool enters this state. The `firstTokenBalance`/`secondTokenBalance` fields are stored only inside the `Exchange`/`ExchangeV2` capsule value in `ExchangeStore`/`ExchangeV2Store`; there is no fallback mechanism (e.g., a special "close and refund" contract) analogous to what the recommendation in the reported issue calls for.

### Impact Explanation
Any account can create an exchange pool via `ExchangeCreateActuator` and then trade against it via `ExchangeTransactionActuator` until one side of the pool is driven to exactly `0` (a Bancor-style AMM naturally approaches, and with a suitably sized trade can exactly reach, zero on the depleted side for integer amounts). Once this happens, the entire remaining balance of the *other* token — funds contributed by the exchange creator via `ExchangeCreateActuator`/`ExchangeInjectActuator` — becomes permanently unspendable: it is not part of any user's account balance and cannot be withdrawn, injected against, or traded, since every actuator now rejects any operation on that exchange ID. This is a permanent freezing of user funds (TRX or TRC10 tokens), reachable by an ordinary broadcastable transaction from any unprivileged account (either the creator's own trading mistake, or an attacker deliberately trading against the pool to zero it out and grief the creator).

### Likelihood Explanation
Likelihood is at least Medium: no special privileges are required, and the sequence (`ExchangeCreateContract` → repeated `ExchangeTransactionContract` trades) is entirely achievable by any account with sufficient token balance to push one side of the pool's balance to exactly zero, especially for pools with small initial liquidity or asset amounts with coarse integer step sizes. Even accidental zeroing by a normal trader locks the creator's funds with no recovery path.

### Recommendation
- Prevent an exchange trade/inject from being able to reduce `firstTokenBalance` or `secondTokenBalance` to exactly `0` (e.g., reject trades that would fully drain either side, mirroring the `hardenedCalc` negative-balance check already present in `ExchangeCapsule.transaction()`).
- Alternatively/additionally, add an explicit "close exchange" actuator/path that lets the exchange creator withdraw the full remaining balance of both tokens once one side reaches `0`, instead of relying on the ratio-based withdraw formula that becomes undefined at that boundary.

### Proof of Concept
1. Attacker/creator calls `ExchangeCreateActuator` to create a pool with `firstTokenBalance = X`, `secondTokenBalance = Y` (both > 0).
2. Any account repeatedly calls `ExchangeTransactionActuator` (`ExchangeTransactionContract`) selling `firstTokenID` for `secondTokenID` such that the AMM formula in `ExchangeCapsule.transaction()` drives `secondTokenBalance` to exactly `0` (achievable with careful integer sizing of `sellTokenQuant`), or vice versa.
3. Any subsequent call to `ExchangeWithdrawActuator`, `ExchangeInjectActuator`, or `ExchangeTransactionActuator` on that `exchangeId` now fails validation with "Token balance in exchange is equal with 0, the exchange has been closed" (as reproduced in the existing unit tests `SameTokenNameCloseTokenBalanceZero` / `SameTokenNameOpenTokenBalanceZero` in `ExchangeWithdrawActuatorTest.java` and `ExchangeTransactionActuatorTest.java`, which directly set balances to `(0,0)` to demonstrate the permanent-reject behavior).
4. The remaining non-zero token balance recorded in the `Exchange`/`ExchangeV2` capsule is now permanently unreachable — no actuator exists to move it back to any account.
