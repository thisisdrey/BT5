Based on my research, I found the strongest analog in java-tron to the Lazy Summer NAV/share-price manipulation incident: the TRC10 Bancor-style Exchange's on-chain price calculation.

### Title
Floating-point precision drift in TRC10 Exchange bonding-curve rate calculation allows value extraction from pool liquidity providers - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The default (non-hardened) TRC10 Exchange pricing path in `ExchangeProcessor.exchange()` computes the traded amount using `double`-precision `pow()` operations rather than exact arithmetic [1](#0-0) . This is the same class of bug as the Lazy Summer incident: a share/exchange-rate calculation that is not computed with exact, manipulation-resistant math, allowing a party who understands the calculation's rounding behavior to extract value from the pool's other stakeholders (in this case, the exchange creator/other traders) rather than getting a fair price. java-tron itself acknowledges this defect by shipping a parallel `SafeExchangeProcessor` that redoes the same formula with `BigDecimal` at fixed scale specifically to avoid divergence from the floating-point path [2](#0-1) , and a dedicated regression test proves the two paths produce **different** results for identical inputs [3](#0-2) .

### Finding Description
`ExchangeCapsule.transaction()` is the entry point invoked by every trade on a TRC10 AMM-style exchange pool (`ExchangeTransactionActuator`), and it picks the pricing engine based on the `allowHarden` flag [4](#0-3) . Unless `AllowHardenExchangeCalculation` is enabled on-chain, the legacy `ExchangeProcessor` is used, which:
- Computes `issuedSupply` and `exchangeBalance` using `double` arithmetic and a `pow()` call with hardcoded exponents `0.0005` and `2000.0` [1](#0-0) .
- Historically, TRON even had to hardcode a table of "known good" `pow()` outputs per mainnet block (`MathWrapper.addPowData`) to force reproducibility across different platforms/JVMs, because raw `StrictMath.pow` results diverged [5](#0-4) .

This is directly analogous to the Lazy Summer bug class: a protocol computing an exchange/NAV rate from a non-exact numerical method, where the calculation result depends on input ordering/magnitude in ways that are exploitable by a caller who can choose transaction sizing to bias rounding in their favor, extracting value from the pool (other token holders / the exchange's balance) rather than the attacker's own deposit. Any account can create an exchange (`ExchangeCreateContract`), inject/trade into it, and repeatedly trade small/large amounts to accumulate rounding-favorable outcomes — this is reachable by any unprivileged transaction broadcaster with no special permission, exactly matching the allowed threat model.

### Impact Explanation
A trader who repeatedly exploits the floating-point rounding bias in `exchangeToSupply`/`exchangeFromSupply` can extract more value out of an exchange pool than they contribute, at the expense of the pool's creator and other counterparties — a direct theft-of-funds vector via unbacked balance changes in TRC10 asset/TRX holdings. This matches the "unauthorized... theft... of funds" acceptance criterion, since the calculation determines how many tokens are credited to the trader's account (`ret.setExchangeReceivedAmount`) at the expense of the pool's balances [6](#0-5) .

### Likelihood Explanation
The vulnerable path is the *default* code path (non-hardened), since `AllowHardenExchangeCalculation` must be explicitly turned on via governance proposal to switch to `SafeExchangeProcessor`. The bug is reachable by any account via a standard, permissionless `ExchangeTransactionContract`, with no special privileges required — only knowledge of the bonding curve math and the ability to submit ordinary TRC10 exchange trades.

### Recommendation
Ensure `AllowHardenExchangeCalculation` is enabled network-wide (routing all exchanges through `SafeExchangeProcessor`), and consider deprecating/removing the floating-point `ExchangeProcessor` path entirely rather than gating it behind a dynamic parameter, since new exchanges can still be created and traded using the unsafe path if the parameter is off.

### Proof of Concept
1. Create a TRC10 Exchange pool with pool balances chosen to bias floating-point rounding (e.g., using the specific `(firstTokenBalance, secondTokenBalance, sellQuant)` triples shown to diverge between `ExchangeProcessor` and `SafeExchangeProcessor` in the existing test, e.g. `{4732214L, 2202692725330L, 29218L}` [7](#0-6) ).
2. Submit repeated `ExchangeTransactionContract` trades of that magnitude against the pool while `AllowHardenExchangeCalculation` is disabled (default).
3. Observe that `ExchangeProcessor.exchange()` returns a different (favorable) `buyTokenQuant` compared to the exact `SafeExchangeProcessor.exchange()` result for the same inputs, letting the attacker walk away with more counter-token than the exact bonding-curve math would allow, draining the difference from the pool.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
