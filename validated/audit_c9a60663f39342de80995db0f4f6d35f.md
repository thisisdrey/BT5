### Title
`SwapFirstAssetTrader::buy_weight` swaps XCM fee-payment assets at unprotected spot price, enabling sandwich extraction from message senders - (File: `cumulus/primitives/utility/src/lib.rs`)

### Summary
`SwapFirstAssetTrader` is a `WeightTrader` implementation used to pay for XCM execution weight by swapping whatever asset an incoming message carries into a `Target` asset through `pallet_asset_conversion`'s AMM pool. Unlike the pallet's own signed extrinsics (`swap_exact_tokens_for_tokens` / `swap_tokens_for_exact_tokens`), which require the *caller* to supply an explicit `amount_out_min` / `amount_in_max` slippage bound, `buy_weight` computes the exact fee via `WeightToFee` and swaps at whatever the pool's current spot price happens to be, with no attacker-independent slippage protection supplied by the message's original author.

### Finding Description
`SwapFirstAssetTrader::buy_weight` is invoked automatically by the XCM executor whenever an incoming (permissionless — anyone/any relayer can trigger execution of a queued message) XCM program uses `BuyExecution` with an asset different from `Target`: [1](#0-0) 

The core swap call is:
```rust
let (credit_out, credit_change) = match SwapCredit::swap_tokens_for_exact_tokens(
    vec![swap_asset, Target::get()],
    credit_in,
    fee,
) { ... }
``` [2](#0-1) 

`SwapCredit::swap_tokens_for_exact_tokens` has no `amount_in_max` parameter at all — the credit-based trait signature only takes `amount_out`: [3](#0-2) 

Internally, `do_swap_credit_tokens_for_exact_tokens` derives the "max" input purely from whatever `credit_in` happens to contain (`amount_in_max = credit_in.peek()`), not from any value chosen by the message's author to reflect their actual price expectations: [4](#0-3) 

Contrast this with the exposed, user-facing dispatchable `swap_tokens_for_exact_tokens`, which explicitly documents the slippage guarantee only holds "immediately within the same transaction" and expects a real caller-chosen bound: [5](#0-4) 

Because message execution in the message queue is decoupled from message construction (a message can sit in the queue for many blocks/be processed at any time by any relayer/collator that services the queue), the AMM pool spot price used by `buy_weight` can be manipulated in the *same block* the message is finally executed: an attacker front-runs with a large swap that skews the pool ratio, waits for the queued XCM message (which carries `BuyExecution` in a non-`Target` asset, e.g. funds moving via reserve-transfer/teleport that could originate from a treasury-controlled account) to be processed against the skewed price, then back-runs to restore the pool and pocket the difference — the classic sandwich pattern from the referenced report, except here the "flashloan-buy-then-let-victim-trade-then-sell" primitive targets a protocol-level fee-conversion routine instead of a bespoke treasury contract.

### Impact Explanation
Any account whose assets are routed through `SwapFirstAssetTrader` to pay XCM execution fees (this includes reserve-backed transfers and treasury-originated cross-chain payouts that rely on this trader for fee conversion) can have significantly more of its non-`Target` asset consumed than the intended fee-equivalent amount, because the exchange rate is read at execution time with no slippage bound reflecting the sender's original price expectation. This is value extraction/loss of funds analogous to the underpriced/overpriced swap primitive in the referenced report, occurring inside protocol fee-handling logic rather than user-initiated trades.

### Likelihood Explanation
Exploitability requires only: (1) an existing liquidity pool for the `swap_asset`/`Target` pair (public, permissionlessly created via `create_pool`), and (2) the ability to submit ordinary swap extrinsics before/after the targeted message is serviced in the same block — no validator, collator, relayer compromise, or privileged access is required. Any account can queue an XCM message that will later be processed against a manipulable spot price.

### Recommendation
- Do not let `buy_weight`/`SwapFirstAssetTrader` swap at unconstrained spot price; derive an `amount_in_max` from a `quote_price_tokens_for_exact_tokens` call plus an explicit, bounded slippage tolerance, and fail the trade (return `XcmError::FeesNotMet`) if the realized price exceeds it.
- Consider using `quote_weight`'s already-computed quote (`quote_price_tokens_for_exact_tokens`) as the authoritative reference price at `buy_weight` time and reject swaps that deviate materially from that quote.
- Extend `SwapCredit::swap_tokens_for_exact_tokens` (or add an alternate method) to accept a genuine `amount_in_max` distinct from the incoming credit size, so the guard is meaningful rather than degenerate.

### Proof of Concept
1. Create an asset-conversion pool for `(AssetX, Target)` and add liquidity (permissionless `create_pool` / `add_liquidity`).
2. Queue an XCM message (e.g., a reserve/teleport transfer whose value ultimately derives from a treasury or protocol-controlled account) that includes `BuyExecution` with `AssetX`, to be executed via a runtime configured with `SwapFirstAssetTrader<Target, AssetConversion, ...>`.
3. In the block where the message queue processes that message, submit a large `swap_exact_tokens_for_tokens` against the `(AssetX, Target)` pool to skew the price just before the queued message executes (front-run).
4. The queued message's `buy_weight` call executes `SwapCredit::swap_tokens_for_exact_tokens([AssetX, Target], credit_in, fee)` at the skewed price, consuming far more `AssetX` from `credit_in` than intended: [6](#0-5) 
5. Submit a reverse swap to restore the pool price and realize the profit extracted from the difference (back-run), completing the sandwich.

	fn buy_weight(
		&mut self,
		weight: Weight,
		mut payment: AssetsInHolding,
		_context: &XcmContext,
	) -> Result<AssetsInHolding, (AssetsInHolding, XcmError)> {
		log::trace!(
			target: "xcm::weight",
			"SwapFirstAssetTrader::buy_weight weight: {:?}, payment: {:?}",
			weight,
			payment,
		);
		let Some((id, given_credit)) = payment.fungible.first_key_value() else {
			return Err((payment, XcmError::AssetNotFound));
		};
		let id = id.clone();
		let given_credit_amount = given_credit.amount();
		let first_asset: Asset = (id.clone(), given_credit_amount).into();
		let Ok((fungibles_id, _)) = FungiblesAssetMatcher::matches_fungibles(&first_asset) else {
			log::trace!(
				target: "xcm::weight",
				"SwapFirstAssetTrader::buy_weight asset {:?} didn't match",
				first_asset,
			);
			return Err((payment, XcmError::AssetNotFound));
		};

		let swap_asset = fungibles_id.clone().into();
		if Target::get().eq(&swap_asset) {
			log::trace!(
				target: "xcm::weight",
				"SwapFirstAssetTrader::buy_weight Asset was same as Target, swap not needed.",
			);
			// current trader is not applicable.
			return Err((payment, XcmError::FeesNotMet));
		}
		// Subtract required from payment
		let Some(imbalance) = payment.fungible.remove(&first_asset.id) else {
			return Err((payment, XcmError::TooExpensive));
		};
		// "manually" build the concrete credit and move the imbalance there.
		let mut credit_in = fungibles::Credit::<AccountId, Fungibles>::zero(fungibles_id);
		credit_in.saturating_subsume(imbalance);

		let fee = WeightToFee::weight_to_fee(&weight);
		// swap the user's asset for the `Target` asset.
		let (credit_out, credit_change) = match SwapCredit::swap_tokens_for_exact_tokens(
			vec![swap_asset, Target::get()],
			credit_in,
			fee,
		) {
			Ok(a) => a,
			Err((credit_in, error)) => {
				log::trace!(
					target: "xcm::weight",
					"SwapFirstAssetTrader::buy_weight swap couldn't be done. Error was: {:?}",
					error,
				);
				// put back the taken credit
				let taken =
					AssetsInHolding::new_from_fungible_credit(id.clone(), Box::new(credit_in));
				payment.subsume_assets(taken);
				return Err((payment, XcmError::FeesNotMet));
			},
		};
