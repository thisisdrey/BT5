Audit Report

## Title
`check_status` treats an inconclusive `PaymentStatus::Unknown` as a successful payout, permanently deleting the spend record without a guaranteed transfer - (File: `substrate/frame/treasury/src/lib.rs`)

## Summary
`Pallet::check_status` matches `Status::Success | Status::Unknown` in the same branch, removing the `Spends` storage entry and emitting `Event::SpendProcessed` as if the beneficiary were definitively paid. The `PayWithSource::check_payment` contract explicitly documents `Unknown` as a non-conclusive placeholder returned once the actual result can no longer be determined, not as evidence of a completed transfer, so this collapses an ambiguous outcome into a "success" finalization.

## Finding Description
`payout` calls `T::Paymaster::pay(...)` and stores the returned id in `PaymentState::Attempted { id }` at `substrate/frame/treasury/src/lib.rs:747-754`. The finalization path, `check_status`, calls `T::Paymaster::check_payment(payment_id)` and matches on the result at `substrate/frame/treasury/src/lib.rs:800-812`: `Status::Failure` moves the spend to `PaymentState::Failed` (retryable), but `Status::Success | Status::Unknown` both immediately `Spends::<T, I>::remove(index)` and emit `SpendProcessed`. `PayWithSource::check_payment`'s documented contract at `substrate/frame/support/src/traits/tokens/pay.rs:162-166` states: "Once this returns anything other than `InProgress` for some `id` it must return `Unknown` rather than the actual result value" — i.e., `Unknown` is explicitly reserved for cases where the true outcome (success or failure) cannot be determined, not for confirmed completion. By folding `Unknown` into the same removal branch as `Success`, the pallet destroys the only state (`Spends` entry with `Attempted { id }`) that would allow retrying or reconciling a payment whose actual settlement is unverified.

## Impact Explanation
For any `Paymaster`/`PayWithSource` implementation that can legitimately return `Unknown` for a payment whose completion cannot be confirmed (e.g., asynchronous or cross-chain payment mechanisms, which is the scenario the `Unknown` variant is designed for), a failed or never-executed payout will be indistinguishable on-chain from a successful one once `check_status` runs. This matches the "payout state must only advance after dispatch/execution/settlement succeed" and "permanent user-fund lock/loss" impact categories: the treasury spend record disappears, `Error::InvalidIndex` is returned on any further `payout`/`check_status` call for that index, and there is no other on-chain mechanism to detect or recover the loss.

## Likelihood Explanation
The `payout` and `check_status` extrinsics are unprivileged (`ensure_signed` only, callable by any signed account), so the exploit path requires no privileged origin or malicious actor — it is triggered purely by the interaction between an ordinary unprivileged call and the specific `Paymaster` implementation configured for a runtime. Whether this is reachable in practice depends entirely on which `Pay`/`PayWithSource` implementation a given runtime configures: implementations such as `PayAssetFromAccount` (`substrate/frame/support/src/traits/tokens/pay.rs:125-127`) always return `Success` synchronously and never produce `Unknown`, so the flaw is latent rather than exploitable for those configurations. It becomes a real, repeatable issue only for asynchronous/cross-chain `Paymaster` implementations that can return `Unknown` for indeterminate outcomes — a case the `check_payment` documentation anticipates but which I could not confirm is currently wired into any in-repo runtime's `Treasury::Paymaster` configuration within the scope I was able to inspect.

## Recommendation
Do not treat `Status::Unknown` as equivalent to `Status::Success` in `check_status`. Introduce a distinct, non-terminal state (e.g., retain the spend with a dedicated "unknown/needs reconciliation" status) instead of calling `Spends::<T, I>::remove(index)`, so that ambiguous outcomes cannot silently finalize a payout that may never have settled.

## Proof of Concept
1. Configure a runtime's `pallet_treasury::Config::Paymaster` with a `Pay`/`PayWithSource` implementation whose `check_payment` can return `PaymentStatus::Unknown` for payments that did not actually settle.
2. Call `Treasury::spend` then `Treasury::payout`, producing `PaymentState::Attempted { id }` (`substrate/frame/treasury/src/lib.rs:747-754`).
3. Have the underlying payment fail on the destination side while `check_payment(id)` returns `Unknown` rather than `Failure`.
4. Call `Treasury::check_status(origin, index)`; the `Status::Success | Status::Unknown` branch (`substrate/frame/treasury/src/lib.rs:806-809`) removes the `Spends` entry and emits `SpendProcessed`.
5. Confirm the beneficiary never received funds and that further `payout`/`check_status` calls for that index return `Error::InvalidIndex`, demonstrating unrecoverable loss of the intended payout. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
