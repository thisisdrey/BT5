### Title
Double refund of `DeterministicStateInitAction` deposit when a later action in the same receipt fails - ([File: runtime/runtime/src/deterministic_account_id.rs])

### Finding Description
`action_deterministic_state_init` deploys deterministic account state and then computes `deposit_refund` (the portion of `action.deposit` not consumed by storage staking), immediately pushing a `Receipt::new_balance_refund` for it, unconditionally at lines 87-91, regardless of whether later actions in the same `ActionReceipt` succeed or fail: [1](#0-0) 

This is inconsistent with every other action handler in the runtime (`Transfer`, `CreateAccount`, `FunctionCall`, etc.), none of which push their own mid-list refund receipts. Instead, unspent/failed deposits for the whole receipt are refunded once, at the end of action-list processing, by `refund_unspent_gas_and_deposits`, which sums `total_deposit` across **all** actions of the receipt (referenced in `runtime/runtime/src/lib.rs` and documented in `protocol-model/spec/runtime-execution.md` / `economics.md`).

Because `action_deterministic_state_init` returns `Ok(())` after pushing its own refund receipt (line 93), and the action-list loop only stops processing on `result.result.is_err()`, a receipt containing `[DeterministicStateInitAction(deposit=D), FailingAction]` will:
1. Execute the `DeterministicStateInitAction` successfully, consuming part of `D` for storage staking and pushing a `balance_refund` receipt for the remainder `deposit_refund` into `result.new_receipts`.
2. Proceed to the `FailingAction`, which sets `result.result = Err(...)`.
3. Reach the receipt-level failure path, where `refund_unspent_gas_and_deposits` computes `total_deposit` from the full original action list — which still includes the `DeterministicStateInitAction`'s `deposit` field — and pushes a second `balance_refund`/`Transfer` receipt for that same deposit amount.

The two refund paths are independent: the manual push in `action_deterministic_state_init` has no interaction with, or awareness of, the `total_deposit` accounting used by the standard end-of-receipt refund. Nothing in the code I could inspect subtracts an already-issued `deposit_refund` from the `total_deposit` sum used by the failure-path refund.

I was not able to directly inspect the body of `refund_unspent_gas_and_deposits` or the `apply_action_list` loop in `runtime/runtime/src/lib.rs` (ran out of tool budget before retrieving it), so I cannot show the exact `total_deposit` computation and confirm definitively whether it excludes deposits from actions that already pushed their own refunds. This is a real gap in my verification.

### Impact Explanation
If confirmed, this would allow an unprivileged sender to mint funds: submitting a two-action receipt where the first action is a `DeterministicStateInitAction` (fully or partially refundable deposit) followed by any guaranteed-to-fail action would cause the deposit to be refunded twice — once via the inline push at lines 87-91, and once via the standard failed-receipt `total_deposit` refund. This would violate value conservation and correspond to a token-inflation/fund-theft class bug (attacker's predecessor account balance increases by an extra `D`).

### Likelihood Explanation
Preconditions are cheap and fully attacker-controlled: any account can construct a receipt with a `DeterministicStateInitAction` deposit followed by an action guaranteed to fail (e.g., a `FunctionCall` to a nonexistent method, or one with mismatched arguments), at the cost of normal gas/deposit fees for the transaction. This would be trivially repeatable.

### Recommendation
I cannot make a confident, verified recommendation without seeing the exact accounting in `refund_unspent_gas_and_deposits`/`total_deposit`. Conceptually, the fix should ensure the deposit is refunded exactly once: either (a) `action_deterministic_state_init` should not push its own refund receipt and instead let the standard end-of-receipt refund mechanism handle unspent deposit uniformly like other actions, or (b) if the inline push is required for early-success semantics, `total_deposit` in the failure-path refund must subtract any deposit already refunded by actions executed earlier in the same receipt.

### Proof of Concept
Because I could not verify the exact `total_deposit`/`refund_unspent_gas_and_deposits` logic within my tool budget, I cannot certify this as confirmed. A verifying test would need to:
1. Set up a `TrieUpdate`/`ApplyState` test harness (as used in `runtime/runtime/src/tests`).
2. Build a receipt with actions `[DeterministicStateInitAction { deposit: D, state_init }, FunctionCall { method_name: "nonexistent", .. }]` targeting a fresh deterministic account id.
3. Apply the receipt and inspect `result.new_receipts`, asserting exactly one `Transfer`/`balance_refund` receipt referencing deposit `D` is emitted (not two, and not `2*D` total).
4. If two refund receipts (or a combined refund of `2*D`) appear, the double-issue is confirmed; if the standard refund path correctly nets out the already-refunded amount, the finding is invalid.

Given I could not trace `refund_unspent_gas_and_deposits`'s `total_deposit` computation to confirm whether it double-counts, I am reporting this with reduced confidence and flag it as **requiring further verification** rather than a fully confirmed finding.
