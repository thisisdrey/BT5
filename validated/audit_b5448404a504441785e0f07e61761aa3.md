### Title
`remove_account` only clears 4 of 12 account-scoped TrieKey columns, leaving `ReceivedData`, `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`/`DataIdToYieldId` orphaned past account deletion - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (core/store/src/utils/mod.rs:505-575) removes only `TrieKey::Account`, `TrieKey::ContractCode`, `TrieKey::AccessKey`/`GasKeyNonce` (via `get_raw_prefix_for_access_keys`), and `TrieKey::ContractData` (via `get_raw_prefix_for_contract_data`). Comparing against `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` (core/primitives/src/trie_key.rs:89-102), 8 of the 12 account-keyed columns are never swept: `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`. Because NEAR allows an account name to be reused after deletion, these orphaned rows remain addressable by a brand-new, unrelated account that later takes the same `account_id`.

### Finding Description
`remove_account` is invoked from the `DeleteAccount` action handler in `runtime/runtime/src/actions.rs`, which any unprivileged account holder can trigger on their own account with a `FullAccess` key (no validator/node privilege required) [1](#0-0) . The cleanup routine only walks and deletes:
- `TrieKey::Account`, `TrieKey::ContractCode` directly [2](#0-1) 
- `AccessKey`/`GasKeyNonce` rows via iteration over `get_raw_prefix_for_access_keys` [3](#0-2) 
- `ContractData` rows via iteration over `get_raw_prefix_for_contract_data` [4](#0-3) 

It never touches the other 8 columns enumerated in `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` [5](#0-4) . Every one of these is populated during ordinary, unprivileged cross-contract-call / yield-resume flows before the account self-deletes: `ReceivedData`/`PendingDataCount`/`PostponedReceiptId`/`PostponedReceipt` are written whenever the account is a receiver of a multi-input-data action receipt that hasn't fully resolved (`set_received_data`, `set_postponed_receipt`), and `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` are written by `promise_yield_create`/`promise_yield_resume` host functions any contract can call [6](#0-5) . If the account issues `DeleteAccount` while such rows are outstanding (e.g., it triggers an async cross-contract call with two dependencies and self-destructs before the second dependency resolves, or creates a promise-yield and self-destructs before resume/timeout), those trie rows survive the deletion. Because NEAR permits creating a new account under a previously-deleted, non-reserved `account_id`, a subsequent unrelated party can register the same name; when the delayed cross-shard `ReceivedData`/timeout/yield-resume later arrives, the runtime resolves it purely from these leftover `TrieKey`s (keyed only by `account_id`, not by any deletion epoch/generation marker) and can execute a stale `PostponedReceipt`/deliver a stale `PromiseYieldStatus` against the *new* occupant of the name - an entity that never authorized or expected that action/promise resolution. This is a straightforward violation of "authorization exactness / value conservation": state created for identity A is delivered to identity A′ that merely reused A's name.

### Impact Explanation
This falls under authorization escalation across accounts/promises and potential state-root inconsistency: a receipt or yielded-promise resolution meant for a previously deleted account can be delivered to (and mutate the state of, or transfer value into/via) a different, newly-created account that happens to share the same textual `account_id`. Depending on the specific stale artifact (a pending `Transfer`/`FunctionCall` `PostponedReceipt`, or a yield resume driving contract logic), this can misroute funds or trigger unintended contract execution against an account that never created that obligation, which maps to the "authorization escalation across accounts or promises" / "theft or freezing of user funds" bounty categories.

### Likelihood Explanation
Reachable entirely by an ordinary unprivileged sender: fund an account, deploy a contract, issue a multi-dependency cross-contract call or `promise_yield_create`, then submit `DeleteAccount` before the pending data/yield resolves - all via signed transactions to a public RPC endpoint, no special privilege needed. The only extra precondition for the cross-identity delivery scenario is that a third party (attacker-controlled or coincidental) later creates an account with the same reused name before the stale receipt/yield resolves, which is also permissionless and requires no elevated access. The mechanism is deterministic and repeatable given repo code as read; however, I was not able to fully trace the postponed-receipt/yield-resolution consumer code path (in `runtime/runtime/src/lib.rs`) in this session to confirm whether a receiver-existence or "creation-epoch" check exists there that would neutralize delivery to the new occupant - this should be verified before treating the cross-identity delivery claim as fully proven; the "8 of 12 columns not swept" fact itself, however, is directly confirmed by the code cited above.

### Recommendation
Extend `remove_account` to also enumerate and delete `TrieKey::ReceivedData`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceipt`, `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, and `TrieKey::DataIdToYieldId` for the given `account_id` using their respective raw-prefix iterators (mirroring the existing `get_raw_prefix_for_access_keys`/`get_raw_prefix_for_contract_data` pattern), or alternatively reject/defer `DeleteAccount` while any such outstanding obligations exist for the account.

### Proof of Concept
Rust unit test in `core/store/src/utils/mod.rs` (or a new test module) using a `TrieUpdate` fixture:
1. For account `A`, write one row for each of the 12 `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` entries (`Account`, `ContractCode`, `AccessKey`, `ReceivedData`, `PostponedReceiptId`/simulate via `PostponedReceipt`, `PendingDataCount`, `PostponedReceipt`, `ContractData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`) using the existing setter helpers (`set_account`, `set`, `set_received_data`, `set_postponed_receipt`, `set_promise_yield_receipt`, `set_promise_yield_status`, `set_yield_id_mapping`, etc.).
2. Snapshot the set of present `TrieKey`s for `A` (via `trie.contains_key` per key) before calling `remove_account`.
3. Call `remove_account(&mut state_update, &A)`.
4. Re-check `contains_key` for each of the 12 keys.
5. Assert: `Account`, `ContractCode`, `AccessKey`, `ContractData` are absent (pass); assert each of the 8 remaining keys (`ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`) is **still present** (currently fails the intended "no survivors" invariant, proving the gap).
6. Follow-up integration test (test-loop / runtime test in `runtime/runtime/tests/test_async_calls.rs` style): create account `A`, issue a two-input-data action receipt to `A`, deliver only one `ReceivedData`, then submit `DeleteAccount` from `A`; recreate account `A` (new keys); deliver the second `ReceivedData`; assert whether the stale `PostponedReceipt` executes against the new `A` (expected: it should not, since `A` was deleted and recreated with unrelated ownership) - this integration test isolates the concrete cross-identity delivery impact beyond mere key-presence.

pub fn set_promise_yield_receipt(state_update: &mut TrieUpdate, receipt: &Receipt) {
    match receipt.versioned_receipt() {
        VersionedReceiptEnum::PromiseYield(action_receipt) => {
            assert!(action_receipt.input_data_ids().len() == 1);
            let key = TrieKey::PromiseYieldReceipt {
                receiver_id: receipt.receiver_id().clone(),
                data_id: action_receipt.input_data_ids()[0],
            };
            set(state_update, key, receipt);
        }
        _ => unreachable!("Expected PromiseYield receipt"),
    }
}
