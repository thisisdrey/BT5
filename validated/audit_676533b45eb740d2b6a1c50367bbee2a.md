### Title
Stale `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` bookkeeping survives `remove_account`, letting a self-call postponed receipt execute with actor privileges on a newly (re)created account of the same name - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/lib.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`remove_account` (`core/store/src/utils/mod.rs:504-575`) removes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData`, but never removes `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt` rows keyed by that account's id. `action_delete_account` (`runtime/runtime/src/actions.rs:314-389`) calls `remove_account` unconditionally with no check for in-flight postponed action receipts. If a multi-input `ActionReceipt` targeting account `A` (in particular a self-call, `predecessor_id == receiver_id == A`) is postponed while awaiting a `DataReceipt`, and `A` is deleted and later re-created before that data arrives, the stale `PostponedReceiptId`/`PostponedReceipt` rows remain reachable and will later be resolved and executed by `process_receipt`'s Data arm (`runtime/runtime/src/lib.rs:1398-1455`) against whatever account currently occupies the name `A`.

### Finding Description
- `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) stores, for each missing `input_data_id`, a `PostponedReceiptId{receiver_id, data_id}` link, a `PendingDataCount{receiver_id, receipt_id}` counter, and the full `PostponedReceipt{receiver_id, receipt_id}` via `set_postponed_receipt`.
- `remove_account` (`core/store/src/utils/mod.rs:504-575`) is invoked by `action_delete_account` and only clears `Account`, `ContractCode`, access/gas keys, and `ContractData` — it has no awareness of postponed-receipt bookkeeping keyed by `receiver_id`.
- `action_delete_account` (`runtime/runtime/src/actions.rs:314-389`) performs storage-usage and gas-key-balance checks but never checks for outstanding `PostponedReceiptId`/`PendingDataCount` entries before deleting the account.
- When the missing `DataReceipt` eventually arrives, `process_receipt`'s Data arm (`runtime/runtime/src/lib.rs:1398-1455`) looks up `TrieKey::PostponedReceiptId{receiver_id: A, data_id}`, finds the stale entry (still present because it was never cleaned up), decrements `PendingDataCount`, and once it hits zero fetches and executes the `PostponedReceipt` via `apply_action_receipt`, which is applied against whatever `Account` currently resides under name `A` (`get_account(state_update, account_id)` in `apply_action_receipt`, `runtime/runtime/src/lib.rs:853`).
- Critically, `apply_action_receipt` derives `actor_id` purely from the receipt's stored `predecessor_id` (`let mut actor_id = receipt.predecessor_id().clone();`, `runtime/runtime/src/lib.rs:855`) — a string/`AccountId` comparison, not a binding to the specific key material or account epoch that existed when the receipt was created. If the original postponed receipt was a self-call (`predecessor_id == receiver_id == A`), the resulting `actor_id == A` will satisfy `actor_id == account_id` self-permission checks for privileged actions (e.g. `AddKey`, `DeleteKey`, `DeployContract`) regardless of who now owns account `A`.
- Because a data receipt's timing is controlled by whichever contract produces it, and the attacker who is the original owner of `A` can architect a promise combinator where one branch resolves immediately and the second is deliberately deferred (e.g., delegated to a second contract they control, resolved on demand by a later call), the attacker can choose to delete `A`, let a third party recreate the same name, and then trigger the delayed data receipt themselves to fire the stale self-privileged action against the new owner's account.

None of the existing checks (storage-usage limit, gas-key-balance limit in `action_delete_account`; nonce/signature/access-key checks, which only apply at receipt/transaction creation time) address this, because the vulnerable path is receipt bookkeeping cleanup, which is entirely separate from those validations.

### Impact Explanation
This is an authorization escalation across accounts: a postponed receipt created under the old account's identity/context executes owner-level actions (e.g., `AddKey`, `DeployContract`, arbitrary `FunctionCall` with self-actor privileges) against a different, later-created account that merely shares the same `AccountId` string. This matches the "authorization escalation across accounts or promises" bounty category. It could be used to plant a delayed-fuse action that injects an attacker-controlled access key or deploys attacker-controlled code onto a subsequently-created account of the same name, without the new owner's consent.

### Likelihood Explanation
Preconditions are fully attacker-controllable and require only ordinary account/contract operations: the attacker must own account `A`, issue a multi-input self-call promise (`Promise::and(p1, p2).then(self_privileged_action)`) where `p2`'s resolution is deferred to a contract the attacker also controls, then submit `DeleteAccountAction` on `A` while `p2` is still outstanding, and finally resolve `p2` on demand once a new account under the same name exists. This is entirely reachable by an unprivileged client submitting normal transactions and deploying its own wasm contracts — no validator, node, or privileged access required. The main external dependency is that someone else (or the attacker) creates a new account with the exact same name after deletion, which for sub-accounts is straightforward (attacker can also just recreate it themselves to attack a subsequent owner if account-name squatting/handoff is common), though for genuinely adversarial third-party victims this requires the victim to independently choose to reuse the freed name, which is a plausible but not universally guaranteed scenario.

### Recommendation
Before allowing `DeleteAccountAction` to succeed (or as part of `remove_account`), the runtime should either (a) reject account deletion while any `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` (and similarly `ReceivedData`, `PromiseYieldReceipt`, promise-yield timeout entries) rows exist for that `receiver_id`, or (b) have `remove_account` iterate and purge all such rows keyed by the account id (similar to how it already purges `ContractData` and access keys via prefix iteration), and additionally invalidate/burn any already-postponed receipts targeting the deleted account rather than allow them to resolve against a future account of the same name.

### Proof of Concept
1. Unit test in `runtime/runtime/src/tests/apply.rs` style (following existing helpers `action_receipt_awaiting`, `promise_data_receipt`, `setup_runtime`):
   - Construct a self-call `ActionReceipt` for account `A` with `predecessor_id = A`, `receiver_id = A`, two `input_data_ids = [d1, d2]`, and an action list containing a privileged self-action (e.g. `AddKey`).
   - Apply this receipt plus a `DataReceipt` for `d1` only, so the runtime records `PostponedReceiptId{A, d2}`, `PendingDataCount{A, receipt_id}=1`, and `PostponedReceipt{A, receipt_id}`.
   - Apply a `DeleteAccountAction` receipt for `A` (beneficiary = attacker) in a subsequent step, calling `remove_account` under the hood.
   - Assert via `get(trie, &TrieKey::PostponedReceiptId{receiver_id: A, data_id: d2})` and `get_postponed_receipt(trie, A, receipt_id)` that these are still `Some(..)` (currently true; should be `None`).
   - Apply a `CreateAccountAction` receipt re-establishing `A` as a fresh account (different logical owner).
   - Apply the final `DataReceipt` for `d2` and assert that `apply_action_receipt` executes the postponed `AddKey` action against the freshly created `A`, confirming the attacker-added key now has access to the new account (`get_access_key(trie, A, attacker_pubkey).is_some()`).
