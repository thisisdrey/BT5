### Title
Dust-transfer griefing fills a victim's per-account token list to `MAX_TOKENS_PER_USER`, blocking deposits of new collateral and new debt issuance - ([File: contracts/Pool.sol](contracts/Pool.sol), [File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined length of an account's `depositTokensOfAccount` and `debtTokensOfAccount` lists, reverting with `UserReachedMaxTokens` in `onlyIfAdditionWillNotReachMaxTokens` (contracts/Pool.sol:79, 143-148, 204-220). `DepositToken` is a freely transferable ERC-20, and `_transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to positive (contracts/DepositToken.sol:517-520). An unprivileged attacker can therefore dust-transfer 1 wei of every registered `DepositToken` to a victim, filling their account list to the cap. Afterwards, any `DepositToken` deposit into a *new* collateral token and any `DebtToken._mint`/`issue` of a *new* synthetic asset for that account reverts, because the 0→positive balance transition triggers the capped `addTo...` call (contracts/DepositToken.sol:485-488, contracts/DebtToken.sol:598-600).

### Finding Description
Attack path (all public entry points, no privileged role needed):

1. Attacker deposits a minimal amount of collateral into each of the pool's `DepositToken` contracts (or acquires the shares via `transfer`), receiving dust `msdTOKEN` balances.
2. Attacker calls `DepositToken.transfer(victim, 1)` for N deposit tokens until `debtTokensOfAccount(victim) + depositTokensOfAccount(victim) == 30`. Each `_transfer` adds the token to the victim's list; `_revertIfLocked` only restricts the *sender's* unlocked balance, which the attacker freely owns.
3. Result for the victim:
   - `deposit()`/`depositWithPermit()` on a deposit token the victim does not already hold reverts (`_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`).
   - `DebtToken.issue()` on a debt token the victim does not already hold reverts (`_mint` → `addToDebtTokensOfAccount` → `UserReachedMaxTokens`) — note `_mint` is reached even for `issue`, so an account at cap cannot open a position in a new synthetic.
   - `SmartFarmingManager.leverage` flows that mint new debt/deposit tokens to the victim likewise revert.
   - Liquidators calling `Pool.liquidate` trigger `DepositToken.seize(account → liquidator)`; if the liquidator's chosen recipient is dust-filled to the cap, `seize` reverts. (A liquidator can route proceeds to a fresh address, so this is a milder amplification, not a liquidation blocker.)

### Impact Explanation
Availability/DoS matching the CVE bug class (hang/crash → reverts blocking state transitions):

- A victim approaching liquidation can be prevented from depositing a *new* collateral type to restore health; the attacker can dust-fill the account just before the victim's rescue transaction (front-running), forcing it to revert. If the victim's existing collateral types are exhausted or insufficient, the position is liquidated — griefing converts to indirect loss.
- New users can be permanently blocked from opening positions in assets they don't already hold until they clean up the list.
- Cleanup is possible (the victim can `transfer` each dust balance out to reduce it to 0, which calls `removeFromDepositTokensOfAccount`), so the freeze is *temporary* — but it costs the victim one transaction per spam token and races can be repeated cheaply, so it is a real liveness failure, not a gas/unbounded-loop issue (the cap is fixed at 30, each call is O(1)).

### Likelihood Explanation
- Attacker requirements: only an EOA/contract holding dust of each deposit token; the deposit fee may make dust slightly costly, but balances can be recycled across victims (transfer the same 1 wei to victim A, then the remainder to victim B — each recipient's 0→positive transition adds the entry; the attacker keeps no balance).
- No modifier stops it: `transfer` has no `nonReentrant` issue, `onlyIfDepositTokenIsActive` is on mint only, and there is no opt-in/whitelist for receiving deposit-token shares.
- Constraints: limited to the number of deposit tokens registered in the pool (cap is shared across debt+deposit lists, so ~30 spam transfers worst case); a sophisticated victim can clear slots, and collateral already held can still be topped up (0→positive check means existing tokens don't hit the cap). This bounds severity to temporary DoS rather than permanent freeze.

### Recommendation
- Prefer `set.add` with idempotent semantics: change `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` to no-op (or let `MappedEnumerableSet.add` return false without reverting) when the token is already present, and only enforce `MAX_TOKENS_PER_USER` on genuinely new entries — but this does not fix dust griefing by itself.
- Real mitigation: only add a token to the account list when the recipient's new balance exceeds a meaningful dust threshold, or track "active" collateral via an explicit user opt-in (e.g., only `deposit()` adds to the list, while plain `transfer` credits the balance without registering it — recipients who never deposited shouldn't have their account list mutated by unsolicited transfers).
- Alternatively, skip the cap check in `_transfer`/`seize` contexts and enforce it only in `deposit`/`issue` entry points for the *acting* user's own new positions.

### Proof of Concept
Hardhat (fork or local) sketch:

```ts
// setup: pool with several DepositTokens (msdA, msdB, ...) registered
// attacker deposits dust into each deposit token
for (const dt of depositTokens) {
  await underlying.approve(dt.address, dust);
  await dt.connect(attacker).deposit(dust);      // attacker holds dust shares
}

// grief: fill victim's token list
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber();
for (let i = 0; i < max; i++) {
  await depositTokens[i].connect(attacker).transfer(victim.address, 1);
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(max);

// victim tries to deposit a collateral type they don't hold -> reverts
await expect(
  newDepositToken.connect(victim).deposit(amount)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim tries to issue a synthetic they don't hold -> reverts
await expect(
  newDebtToken.connect(victim).issue(mintAmt, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// front-run scenario: victim near liquidation, dust-fill makes rescue deposit revert
```

Confidence caveats: I confirmed the cap check, the 0→positive add hooks in `DepositToken._transfer`/`_mint` and `DebtToken._mint`, and that `DebtToken` is non-transferable (so debt-token slots can't be dust-filled directly — only deposit-token slots, which is sufficient since the cap is shared). I did not fully trace `SmartFarmingManager.leverage`/`flashRepay` reentrancy-safe behavior under the cap or the exact `seize` recipient in `Pool.liquidate`, so the liquidation-blocking amplification is plausible but less certain than the deposit/issue DoS, which stands on its own.
