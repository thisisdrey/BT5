### Title
Unvalidated count field in `ValidateMultiSign` precompile allows unbounded array allocation and node crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract's legacy code path calls `extractBytesArray()` to parse a caller-controlled ABI-encoded signature array from `data` *before* validating that the declared array length is within the allowed bound (`MAX_SIZE`). The declared length (`len`) is read directly from calldata via `DataWord.intValueSafe()` and used to allocate `new byte[len][]` with no check against the actual size of the input buffer, mirroring the root cause of CVE-2025-21994 (`ksmbd` trusting `num_aces` to size an allocation instead of validating it against the actual ACL payload size).

### Finding Description
In `extractBytesArray`: [1](#0-0) 

`len` is taken straight from an attacker-supplied `DataWord` in calldata (`words[offset].intValueSafe()`), and is used to size `bytesArray = new byte[len][]` without ever checking it against the amount of data actually present in `rawData`, nor against any upper bound at that point.

In the caller, `ValidateMultiSign.execute()`: [2](#0-1) 

The `sigArraySize > MAX_SIZE` bound check and the post-hoc `signatures.length > MAX_SIZE` check are only meaningful *after* the array has already been allocated. When `VMConfig.allowTvmSelfdestructRestriction()` is disabled (the legacy/older behavior gated by this feature flag), the pre-check (`sigArraySize > MAX_SIZE`) is skipped entirely, and `extractBytesArray` is invoked directly with the raw, unbounded `len` value — exactly the "validate the count field before the allocation, not after" flaw described in the ksmbd advisory (`parse_dcal()` allocating `posix_ace_state_array` sized by `num_aces` without checking it against `smb_acl->size`).

This is reachable by any unprivileged caller: `ValidateMultiSign` is invoked via a normal TVM `STATICCALL`/`CALL` from any deployed contract or via `TriggerConstantContract`, so a single crafted transaction or constant call with a manipulated ABI word for the signature-array length can drive this path.

### Impact Explanation
`intValueSafe()` clamps to a signed 32-bit value (up to `Integer.MAX_VALUE`), so `new byte[len][]` can request an array of ~2^31 object references. On a 64-bit JVM this is many gigabytes of memory for a single reference array, sufficient to trigger `OutOfMemoryError` in the node process handling the call (during constant-call/TriggerConstantContract execution or during normal block execution when a contract calls this precompile). This matches the accepted impact class "node crash or halt" — an unprivileged, unauthenticated caller can degrade or crash a full node/SR by sending or triggering a single call into this precompile.

### Likelihood Explanation
Reaching this code requires only a normal TVM call to the `ValidateMultiSign` precompiled address with attacker-chosen ABI words; no special privilege, signed witness status, or victim interaction is required — any account or JSON-RPC/HTTP `TriggerConstantContract`/`triggersmartcontract` caller can construct this. Exploitability depends on `VMConfig.allowTvmSelfdestructRestriction()` being disabled for the executing node (i.e., the pre-check gate not yet active); I was unable to confirm within the available context whether this flag defaults to enabled on current mainnet-configured nodes, so likelihood should be validated against the live chain parameter/committee configuration before treating this as immediately exploitable in production.

### Recommendation
Move the length/bound validation (`len > MAX_SIZE` and length vs. actual `rawData` size) into `extractBytesArray` (and `extractSigArray`/`extractBytes32Array`) itself, before allocating `bytesArray`, so the check always executes regardless of the `allowTvmSelfdestructRestriction` flag. Additionally validate that `len * (minimum element size)` does not exceed `rawData.length - offset`, analogous to how the ksmbd fix now bounds `num_aces` using the ACL's real buffer `size` field rather than trusting the field value directly.

### Proof of Concept
1. Deploy or call an existing contract that forwards calldata to the `ValidateMultiSign` precompiled contract address (`0x0000...1005` equivalent in java-tron), or invoke it directly via `TriggerConstantContract`/`triggerconstantcontract` JSON-RPC/HTTP API.
2. Craft the calldata so that the ABI word at the signature-array-length offset (`words[3]`-derived offset region) encodes a very large 32-bit length (e.g. `0x7FFFFFFF`), while `VMConfig.allowTvmSelfdestructRestriction()` is not enabled on the target node.
3. Send the call; `extractBytesArray` executes `new byte[0x7FFFFFFF][]` before any `MAX_SIZE` check applies, causing the executing node to attempt an oversized allocation and throw `OutOfMemoryError`, degrading or crashing transaction/constant-call processing on that node.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
