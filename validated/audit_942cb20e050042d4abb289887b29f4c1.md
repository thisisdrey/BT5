### Title
ERC20Transactor credits XCM holding with the requested amount instead of the checking account's actual balance delta, letting fee-on-transfer/rebasing ERC20 tokens drain the shared checking account and strand other users' deposits - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` moves ERC20 tokens by calling `transfer(checking_account, amount)` on an arbitrary, permissionlessly matched ERC20 contract, and — as long as the call does not revert and the ERC20 `transfer` returns `true` — unconditionally mints an `Erc20Credit(amount)` into the XCM holding register. [1](#0-0) 
This mirrors the FraxSwap bug pattern exactly: the internal accounting value (`amount`, later used as the XCM holding credit and as the deposit `transfer` amount) is not derived from the actual balance change of the shared checking account, but is simply the value the caller requested. ERC20 tokens with non-standard transfer semantics (fee-on-transfer, rebasing, deflationary) can make the checking account receive less than `amount`, or later lose balance via rebase, without the runtime's bookkeeping ever noticing.

### Finding Description
The XCM `TransactAsset` implementation for ERC20 assets uses one shared `TransfersCheckingAccount` as the pooled intermediary for all ERC20 transfers routed through XCM:

- `withdraw_asset_with_surplus` calls `IERC20::transfer(checking_address, amount)` from the user's account, and if the call succeeds and returns `true`, it creates `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — i.e., it credits the XCM holding register with exactly the value the XCM message requested, not the amount the checking account's balance actually increased by. [2](#0-1) 
- `deposit_asset_with_surplus` later calls `IERC20::transfer(beneficiary, amount)` from `TransfersCheckingAccount`, again using the value carried in the holding/credit (`amount`), not the checking account's live balance. [3](#0-2) 
- `Erc20Credit`, the type used to represent this value inside `AssetsInHolding`, explicitly documents that it "does not perform runtime-level balance enforcement" and relies on "the ERC20 smart contract itself" for balance constraints. [4](#0-3) 

Because `Matcher::matches_fungibles` is a generic matcher over any `H160` asset id (any deployed contract address), nothing in this code path restricts the ERC20 contract to a "standard" fixed-balance implementation. Any user can deploy or use an ERC20 contract with fee-on-transfer or rebasing behavior and route it through this transactor. When such a token is used:
1. The `transfer` to the checking account can succeed (`return_value` is `true`) while delivering less than `amount` to `TransfersCheckingAccount` (fee-on-transfer), or the checking account's balance can later shrink due to a rebase.
2. The XCM holding register nonetheless records the full requested `amount` as available credit (`Erc20Credit(amount)`), exactly like FraxSwap's `twammReserve0/1` continuing to reflect stale, non-rebase-adjusted balances.
3. Subsequent `deposit_asset_with_surplus` calls for that same asset (for this or other users/orders sharing the pooled `TransfersCheckingAccount`) will attempt to move `amount` out of the checking account. Once the checking account's real balance is smaller than the sum of outstanding credits (because it never received the full amount, or lost balance to a rebase), later transfers will fail, `did_revert()` will be true, or the `transferCall` will return `false` — exactly the "transactions revert once the contract's balance is exhausted before all users can withdraw" scenario from the report.

The existing guards do not stop this: the code only checks `did_revert()` and the boolean ERC20 return value — it never compares the checking account's balance before/after the transfer to the assumed `amount`. There is no total-issuance-style invariant or balance snapshot check anywhere in `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` that would catch a discrepancy between "amount requested" and "amount actually moved".

### Impact Explanation
Because `TransfersCheckingAccount` is a single, shared pooled account for all ERC20 XCM transfers of a given asset, once its real ERC20 balance is smaller than the sum of `Erc20Credit` values that the runtime believes are backed by it, subsequent legitimate `deposit_asset` calls for other users' XCM programs (using the same non-standard token) will start failing/reverting. This is a fund-lock / denial-of-service condition on public dispatch (any user can submit `PolkadotXcm::execute`/incoming XCM referencing an arbitrary ERC20 asset id), matching the "permanent user-fund or bridge-state lock" and "public underpriced work that … stalls … processing" impact classes: an unprivileged party can, at no special cost, register/use a fee-on-transfer or rebasing ERC20 contract to desynchronize the checking account's real balance from the runtime's internal `Erc20Credit` bookkeeping, causing other users' asset deposits routed through the same checking account to revert and their funds effectively stuck mid-XCM.

### Likelihood Explanation
Likelihood is limited to asset-hub-westend/asset-hub-westend-style configurations that wire up `ERC20Transactor` with a `Matcher` accepting arbitrary contract addresses (as seen in the test `withdraw_and_deposit_erc20s`, which deploys an arbitrary user-supplied contract and routes it through `ERC20TransfersCheckingAccount`). [5](#0-4) 
No privileged action, malicious relayer/validator, or leaked key is needed — an ordinary user deploys or references a non-standard ERC20 contract and executes a normal XCM withdraw/deposit sequence, exactly the class of unprivileged, public-entrypoint action required by the assessment gate.

### Recommendation
- In `withdraw_asset_with_surplus`, snapshot the checking account's ERC20 balance before and after the `transfer` call and credit `AssetsInHolding` with the actual observed delta, not the requested `amount`.
- In `deposit_asset_with_surplus`, cap the outgoing transfer to the checking account's real, currently available balance for that asset (or fail closed if the balance is insufficient) rather than trusting the value carried in the holding register.
- Consider disallowing or explicitly flagging ERC20 contracts with non-standard transfer semantics (fee-on-transfer, rebasing) for use as XCM-transactable assets, or document this limitation clearly if balance reconciliation is not implemented.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 contract `EvilToken` where `transfer(to, amount)` deducts `amount` from `msg.sender`, but only credits `to` with `amount - fee` (still returning `true`), or alternatively a rebasing token whose supply/balances shrink asynchronously.
2. User A submits an XCM program: `withdraw_asset((EvilToken, amount))`, `deposit_asset(..., beneficiary)`, using `ERC20Transactor`. The `withdraw_asset_with_surplus` call succeeds and credits `AssetsInHolding` with the full `amount`, even though `TransfersCheckingAccount`'s real `EvilToken` balance only increased by `amount - fee` (or later decreases via rebase).
3. User B performs the same flow with a different amount, further growing the gap between the checking account's real balance and the sum of credits the runtime "believes" it holds.
4. Once the checking account's real `EvilToken` balance is exhausted below the outstanding credited total, subsequent `deposit_asset_with_surplus` calls for any user's `EvilToken` deposit revert (`did_revert()` true or `transferCall` returns `false`), leaving their XCM holding stuck/undeliverable and their intended tokens effectively locked mid-execution — reproducing the FraxSwap "contract balance exhausted before all users can withdraw" failure mode locally.

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});
}
