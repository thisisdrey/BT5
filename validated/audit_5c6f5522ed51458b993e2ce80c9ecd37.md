### Title
Incomplete `AllowTvmCompatibleEvm` version-1 contract restriction: `TransferAssetActuator` omits the check enforced by `TransferActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`)

### Summary
`TransferActuator.validate()` blocks sending TRX to a "version 1" (EVM-compatible) smart contract when `AllowTvmCompatibleEvm` is enabled, forcing callers to use `TriggerSmartContract` instead. `TransferAssetActuator`, which performs the analogous TRC10 asset transfer, only re-implements the older `ForbidTransferToContract` guard and never checks `AllowTvmCompatibleEvm` / `getContractVersion() == 1`. A user can therefore send TRC10 assets directly to a version‑1 contract through `TransferAssetContract`, bypassing the restriction that was specifically added to prevent value from reaching EVM-compatible contracts through a path that doesn't invoke their code.

### Finding Description
`TransferActuator.validate()` contains two independent restrictions before allowing a plain TRX transfer to a contract account: [1](#0-0) 

1. `ForbidTransferToContract` — blocks any transfer to a `Contract` type account.
2. `AllowTvmCompatibleEvm` + `contractCapsule.getContractVersion() == 1` — specifically blocks transfers to EVM-compatible ("version 1") contracts, with the message "Instead please use TriggerSmartContract."

`TransferAssetActuator.validate()` is the sibling actuator for TRC10 token transfers and shares the same `toAccount`/contract-type checks, but only implements restriction (1): [2](#0-1) 

There is no lookup of `ContractStore`, no check of `getAllowTvmCompatibleEvm()`, and no check of `ContractCapsule.getContractVersion()` in this path. `getContractVersion()` simply reads the `version` field of the stored `SmartContract` proto: [3](#0-2) 

Because the second check exists only in `TransferActuator`, a caller can bypass the "no direct value transfer to version-1 contracts" restriction simply by using `TransferAssetContract` instead of `TransferContract`. This is structurally the same incomplete-fix pattern as the Argo Workflows CVE-2026-42296: a restriction was added to one enforcement point (`podSpecPatch`/TRX-transfer path) while a sibling field/path with equivalent security consequence (other WorkflowSpec fields/`TransferAssetContract`) was left unguarded.

### Impact Explanation
Version-1 (EVM-compatible) contracts are expected to receive value transfers only via a call that executes their code (e.g. `TriggerSmartContract`/`CALL`), so that fallback/receive semantics and any TRC10 bookkeeping logic in the contract run. A TRC10 transfer routed through `TransferAssetActuator` credits the contract's TRC10 balance directly in the `AccountStore`/asset map without invoking any contract code path. If a version-1 contract has no mechanism to recognize or move out balances credited this way (which is exactly the scenario the `TriggerSmartContract`-only restriction is meant to prevent for TRX), TRC10 tokens sent to it become effectively stranded — an unbacked/unreachable balance sitting on a contract that cannot account for or move it, i.e. a permanent freezing of the sender's assets outside of the intended contract semantics.

### Likelihood Explanation
Any account with a TRC10 asset balance can trigger this by submitting a normal, unprivileged `TransferAssetContract` transaction to a known version-1 contract address — no special permission, no witness/SR involvement, and no unusual gas/energy requirements. This is reachable directly from a signed transaction broadcast through the standard actuator/execute path, matching the same trust boundary as the original TRX-transfer restriction it fails to mirror.

### Recommendation
Apply the same `AllowTvmCompatibleEvm` / `getContractVersion() == 1` check present in `TransferActuator.validate()` to `TransferAssetActuator.validate()` (and any other actuator/path that can move value/assets into an account of type `Contract`), rather than only gating `ForbidTransferToContract`. Preferably factor the "is this a version-1 contract that must not receive direct value transfers" check into a shared helper used by both actuators (and any future asset-moving actuator) so the restriction cannot silently diverge again.

### Proof of Concept
1. Enable `AllowTvmCompatibleEvm` (committee proposal #60) on a test/private chain.
2. Deploy a version-1 (EVM-compatible) smart contract, `C`, via `CreateSmartContract` with `AllowTvmCompatibleEvm` active so `SmartContract.version == 1`.
3. Confirm the restriction works for TRX: submit a `TransferContract` sending TRX from account `A` to `C` — it is rejected with `"Cannot transfer TRX to a smartContract which version is one. Instead please use TriggerSmartContract"` per [4](#0-3) .
4. From account `A`, which holds a TRC10 asset balance, submit a `TransferAssetContract` (asset transfer) with `to_address = C`.
5. Observe that `TransferAssetActuator.validate()` (`actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java:169-192`) never queries `ContractStore` or `getAllowTvmCompatibleEvm()`/`getContractVersion()`, so the transaction passes validation and executes, crediting the TRC10 balance directly to contract `C`'s account — with no restriction analogous to the TRX case, and no guarantee `C`'s code can ever recover or move that balance.
