## Title
Permissionless share-value inflation via `lending_pool_emissions_deposit` enables an ERC4626/ynETH-style first-depositor attack - (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`)

### Summary
The ynETH report describes an inflation attack where an attacker forces external value into a vault (via a permissionless "process rewards" call) right after becoming the first/an early depositor, disproportionately inflating the share price so that subsequent depositors receive far fewer shares than they should, or lose deposited value to rounding. Marginfi has a structurally analogous, explicitly permissionless instruction: `lending_pool_emissions_deposit`, which lets *any* caller transfer tokens directly into a bank's `liquidity_vault` and immediately recompute `asset_share_value` from the new balance, without minting new shares to the caller.

### Finding Description
`lending_pool_emissions_deposit` is documented as: "Permissionlessly deposit same-mint emissions directly into the bank liquidity vault, increasing depositor value through asset share value" [1](#0-0) . It performs a `transfer_checked` from any `emissions_funding_account`/depositor signer straight into `liquidity_vault`, then recomputes the bank's `asset_share_value` as `(total_assets + amount) / total_asset_shares` [2](#0-1) . This is exactly the "force-donate value directly into the vault, then rewards get distributed to whoever already holds shares" mechanic in the ynETH bug: the caller who triggers the value injection gets no shares back, and the value is retroactively distributed pro-rata to *existing* shareholders via the recomputed `asset_share_value`.

Ordinary deposits mint shares purely from the bank's *stored* `asset_share_value` state (`bank_account.deposit()` → `get_asset_shares(value) = value / self.asset_share_value`) [3](#0-2) , not from the raw token balance of the vault — so a plain SPL transfer into the vault (bypassing the program) would NOT by itself change `asset_share_value`. The one instruction that *does* let an untrusted party update `asset_share_value` from vault-value logic without any shares check other than `total_asset_shares > 0` [4](#0-3)  is `lending_pool_emissions_deposit`.

Attack sequence, matching the ynETH pattern:
1. Attacker becomes the sole/first depositor of a freshly-created bank with a tiny amount (e.g., 1 native unit). Since `asset_share_value` starts at exactly `I80F48::ONE` [5](#0-4) , they receive `1` share for `1` unit deposited — the same 1:1 "first depositor" minting the ynETH report calls out as disproportionate.
2. Attacker (or anyone) calls `lending_pool_emissions_deposit` with a large `amount`, since `total_asset_shares > 0` is satisfied (it equals 1). This inflates `asset_share_value` to `(1 + amount) / 1` = huge value, without minting any new shares [6](#0-5) .
3. A genuine subsequent depositor calls `lending_account_deposit` with a normal-sized amount. Their minted shares = `deposit_amount / asset_share_value` (via `get_asset_shares`), which — with `asset_share_value` inflated far beyond the deposit amount — rounds down toward/to zero because there's no explicit rounding-up or minimum-shares protection visible in `get_asset_shares` [3](#0-2) . The depositor's tokens are absorbed into the liquidity vault and effectively transferred to the attacker's now-inflated share position.

### Impact Explanation
This maps onto the "unauthorized transfer" / theft category: a victim's deposited tokens increase the bank's asset value but mint the victim negligible or zero shares, while the attacker's pre-existing shares capture that value via the inflated `asset_share_value`. This is the core mechanism the ynETH report flags as high severity (attacker profits at victims' expense through share-price manipulation triggered by a permissionless value-injection function).

### Likelihood Explanation
The precondition — being the sole depositor of a bank with very small `total_asset_shares` — is realistic during bank bootstrap (new banks start at `total_asset_shares = 0` and grow from the first depositor) [7](#0-6) . `lending_pool_emissions_deposit` is explicitly designed to be permissionless and requires only `total_asset_shares > 0`, no minimum size threshold, and no cap tying the deposited emissions amount to existing TVL [4](#0-3) . However, I could not fully verify from the index whether: (a) bank creation flows enforce a minimum non-attacker seed deposit before the bank is usable, (b) there's a compute/precision floor in `I80F48` (48-bit fractional precision) that makes the rounding-to-zero scenario impractical at realistic magnitudes, or (c) `lending_pool_emissions_deposit`'s accounts struct restricts the `mint`/`emissions_funding_account` in a way that limits attacker-controlled amounts. These are legitimate uncertainties that would need to be checked directly in the full `configure_bank.rs` accounts struct and bank-creation code, which I was unable to retrieve in the final iteration due to tool-call failures.

### Recommendation
- Require a minimum "dead" share/value floor at bank creation (mint a small amount of shares to a burn address or require a minimum first-deposit size) analogous to the ynLSD bootstrap fix referenced in the report, so `total_asset_shares` can never be pathologically small when `lending_pool_emissions_deposit` is callable.
- Consider disallowing `lending_pool_emissions_deposit` when `total_asset_shares` (or `total_assets`) is below a sane threshold relative to the incoming `amount`, or cap the multiplier `amount` can have on `asset_share_value` per call.
- Round in favor of the protocol/existing depositors is standard, but also enforce a minimum-shares-minted check on deposit (revert if `share_amount` rounds to zero for a nonzero `deposit_amount`) to prevent silent value transfer.

### Proof of Concept
Conceptual reproduction (not executed, based on code paths read):
1. Create a fresh bank; attacker deposits `1` native unit via `lending_account_deposit` → `total_asset_shares = 1`, `asset_share_value = 1`.
2. Attacker calls `lending_pool_emissions_deposit` with `amount = 1_000_000_000` on the same bank/mint → `asset_share_value` becomes `(1 + 1_000_000_000) / 1 ≈ 1_000_000_001`.
3. Victim deposits `500_000` units via `lending_account_deposit`. Minted shares = `500_000 / 1_000_000_001 ≈ 0` (rounds down under `get_asset_shares`), while the victim's 500,000 units are now in the liquidity vault, and the attacker's single share is now worth `≈ (1,000,000,001 + 500,000)` — i.e., the attacker's share value increased by essentially the entirety of the victim's deposit.

I was not able to confirm within available tool calls whether `lending_account_deposit` has any protective check rejecting a `share_amount` of zero, or whether bank-creation flows require a substantial minimum initial deposit that would prevent step 1's tiny-`total_asset_shares` precondition — these should be verified directly in the repository (`programs/marginfi/src/instructions/marginfi_account/deposit.rs` and bank-creation instructions) before treating this as fully confirmed.
