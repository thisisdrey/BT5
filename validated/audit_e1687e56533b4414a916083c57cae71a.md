### Title
VesperGateway.deposit assumes the full `amount_` is received and always reverts for fee-on-transfer underlyings - (File: contracts/VesperGateway.sol)

### Summary
`VesperGateway.deposit` pulls `amount_` of the vToken's underlying from the caller, then approves and deposits that same `amount_` into the Vesper pool. Unlike `DepositToken.deposit` and `SmartFarmingManager._safeTransferFrom`, it does not measure the actual received amount. If the underlying is a fee-on-transfer (FoT) token, the gateway holds less than `amount_`, the subsequent `vToken_.deposit(amount_)` fails, and the deposit path is unusable — the same bug class as the referenced ExchangeProxy/HardenedTopupProxy issue.

### Finding Description
In `contracts/VesperGateway.sol` lines 44–65:

```solidity
IERC20 _underlying = IERC20(vToken_.token());
_underlying.safeTransferFrom(_msgSender, address(this), amount_);   // actual received may be < amount_

_underlying.safeApprove(address(vToken_), amount_);
vToken_.deposit(amount_);   // VPool transferFrom(amount_) -> reverts on insufficient balance
```

Step 1 assumes the gateway's balance increased by `amount_`. For a FoT underlying (e.g., a deflationary token used as the asset of a registered Vesper pool whose `vToken` is onboarded as collateral via `pool_.depositTokenOf(vToken_)`), the received amount is `amount_ - fee`. Step 2/3 then attempts to deposit `amount_` into the VPool, which performs its own `transferFrom` and reverts because the gateway only holds `amount_ - fee`.

Contrast with `DepositToken.deposit` (`contracts/DepositToken.sol:225-227`), which correctly does `amount_ = balanceOf(treasury) - balanceBefore`, and `SmartFarmingManager._safeTransferFrom` (`contracts/SmartFarmingManager.sol:257-261`), which returns the measured delta. `VesperGateway` measures a balance delta for the *vToken* minted (line 56–58) and for the underlying on `withdraw` (lines 87–89), but not for the inbound underlying transfer on `deposit`.

### Impact Explanation
Any `deposit()` call through `VesperGateway` for a collateral whose Vesper pool token charges transfer fees always reverts, permanently DoS-ing that deposit route (the direct `DepositToken.deposit` of pre-acquired vTokens remains possible, but the gateway convenience path — the intended way to enter a vToken position from the raw underlying — is bricked). This matches the original report's impact class (revert / inability to use FoT tokens). It does not cause theft or insolvency, so severity is Medium/Low.

### Likelihood Explanation
Requires a registered Pool to list a vToken whose VPool underlying is a fee-on-transfer token — a governance onboarding choice, but the code path itself is unconditional once such collateral exists. No attacker action is needed beyond calling `deposit`; the revert is deterministic.

### Recommendation
Measure the actual amount received before approving/depositing:

```solidity
uint256 _before = _underlying.balanceOf(address(this));
_underlying.safeTransferFrom(_msgSender, address(this), amount_);
uint256 _received = _underlying.balanceOf(address(this)) - _before;

_underlying.safeApprove(address(vToken_), 0);
_underlying.safeApprove(address(vToken_), _received);
vToken_.deposit(_received);
```
