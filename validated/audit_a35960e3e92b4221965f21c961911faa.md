### Title
Dust-transfer griefing fills victim's per-account token list, permanently reverting all new deposits and token receipts - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` keeps a bounded per-account registry (`depositTokensOfAccount` + `debtTokensOfAccount`, hard cap `MAX_TOKENS_PER_USER = 30`) that is appended to whenever a `DepositToken` balance goes from `0` to positive. Because `DepositToken.transfer`/`transferFrom` are permissionless ERC20 entry points and the add is triggered on *any* non-zero incoming balance, an unprivileged attacker can deposit dust amounts of every registered collateral and transfer 1 wei of each `msdTOKEN` to a victim, permanently filling all 30 slots. From then on, every operation that would add a new token to the victim's list — `deposit` of a new collateral type, `issue`/`mint` of a new synthetic (debt token slot), or simply *receiving* a transfer of any `msdTOKEN` the victim doesn't already hold — reverts with `UserReachedMaxTokens`. Analogous to CVE-2017-2596, a bounded shared resource (per-account reference list ≈ KVM's pinned page references) is exhausted through mishandled acquisitions, causing denial of service.

### Finding Description
- `Pool.addToDepositTokensOfAccount` enforces the cap in `onlyIfAdditionWillNotReachMaxTokens` and reverts once `debtTokens + depositTokens >= 30` [1](#0-0) [2](#0-1) .
- `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was `0` — with no consent check and no minimum amount [3](#0-2) .
- The same add path fires on `deposit(..., onBehalfOf_)` via `_mint` [4](#0-3)  and on `seize` during liquidation [5](#0-4) .
- Removal only happens when a balance returns exactly to `0` [6](#0-5) , so a 1-wei dust balance pins the slot indefinitely; the victim cannot eject the dust token without paying gas to transfer/withdraw it themselves.

Attack trace (all unprivileged, public entry points):
1. For each registered `DepositToken` `d_i`: `d_i.deposit(dust, attacker)` (or acquire on market) then `d_i.transfer(victim, 1)`. Each transfer invokes `Pool.addToDepositTokensOfAccount(victim)`, consuming one slot.
2. After `min(30, #registeredTokens)` iterations the victim's combined list hits the cap. On pools with ≥30 registered deposit tokens the victim is completely saturated.
3. Thereafter: `d_new.deposit(x, victim)` reverts inside `_mint` → `addToDepositTokensOfAccount`; `DebtToken.issue`/`mint` for any new synth reverts via `addToDebtTokensOfAccount`; and `anyMsdToken.transfer(victim, n)` reverts for tokens the victim doesn't hold — the revert propagates out of `_transfer`, so senders cannot even pay the victim.

### Impact Explanation
- **Temporary freezing of funds / forced liveness failure**: The victim cannot receive any new `msdTOKEN` (incoming transfers revert), cannot deposit collateral types they don't already hold, and cannot mint any new synthetic asset. This persists until the victim manually zeroes out a dust balance per slot (gas cost imposed by attacker) — a griefing DoS with attacker cost ~`30 * (dust deposit + transfer)` vs. victim remediation plus lost functionality.
- **Liquidation-rescue denial**: A victim whose position turns unhealthy cannot add a *new* collateral type to restore health if saturated; they are limited to topping up tokens already in their list or repaying existing debt types, measurably increasing forced-liquidation exposure.
- The invariant broken is liveness of account-level accounting: slot acquisitions are not consent-gated or amount-gated, so references are consumed without the victim ever opting in — the direct analog of VMXON pinning host pages on behalf of an L1 guest.

### Likelihood Explanation
- No privileged role required: only `deposit` and `transfer` on whitelisted `DepositToken`s. `onlyIfAdditionWillNotReachMaxTokens` is the only guard and it protects the *pool*, not the recipient.
- Feasibility depends on the deployed pool having enough distinct deposit tokens (debt tokens can't be force-pushed). On Metronome pools with many listed collaterals this is cheap; the dust amounts are recoverable minus fees.
- Not stopped by `nonReentrant`, `whenNotPaused`, `SynthContext` sender checks, or supply caps. It is partially mitigated only because the victim can self-clean slots — hence Medium-severity griefing rather than permanent freeze of existing funds (existing balances remain withdrawable).

### Recommendation
- Gate list additions on meaningful balance changes or make membership opt-in: e.g. only add on `deposit`/`issue` initiated via the account's own call (`_msgSender() == account_` or an authorized `Operator`), not on inbound `transfer`/`seize`; or allow `addToDepositTokensOfAccount` to succeed but lazily prune zero/dust entries.
- Alternatively, remove the hard `MAX_TOKENS_PER_USER` revert for *receipts* (let transfers succeed) and enforce the cap only on borrow-relevant mutations, or introduce a per-token minimum first-balance threshold so 1-wei dust cannot pin a slot.

### Proof of Concept
Hardhat fork outline (reproducible against a deployed pool):

```ts
// fork base/optimism; attacker = fresh EOA; victim = fresh EOA
const pool = await ethers.getContractAt('Pool', POOL);
const depositTokens = await pool.getDepositTokens(); // registered collaterals
const n = Math.min(depositTokens.length, await pool.MAX_TOKENS_PER_USER());

for (let i = 0; i < n; i++) {
  const msd = await ethers.getContractAt('DepositToken', depositTokens[i]);
  const underlying = await ethers.getContractAt('IERC20', await msd.underlying());
  await underlying.connect(whale).transfer(attacker, dust);          // fund attacker
  await underlying.approve(msd.address, dust);
  await msd.deposit(dust, attacker);                                 // mint msdTOKEN
  await msd.transfer(victim, 1);                                     // pins 1 slot on victim
}

expect(await pool.getDepositTokensOfAccount(victim)).to.have.length(n);
// victim now saturated:
await expect(msdNew.deposit(1000, victim)).revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(debtToken.issue(victim, 1)).revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(msdAttackerHeld.transfer(victim, 5)).revertedWithCustomError(pool, 'UserReachedMaxTokens'); // new token type
// victim must spend gas zeroing each dust balance to recover a slot
```
