### Title
Nonce reset via self-serviced DeleteKey+AddKey on an identical public key allows replay of previously-signed transactions - (File: runtime/runtime/src/access_keys.rs)

### Summary
`add_regular_key` (runtime/runtime/src/access_keys.rs:230-255) unconditionally seeds `access_key.nonce = initial_nonce_value(block_height)` whenever an `AddKeyAction` is applied, without checking whether the same `(account_id, public_key)` had a strictly higher nonce previously recorded. Because a single receipt can legally contain `DeleteKey(pk)` followed by `AddKey(pk, …)` for the *same* public key (confirmed reachable and tested at `runtime/runtime/tests/apply.rs:1167` `test_delete_key_add_key`), an account owner can reset their own key's stored nonce backward, re-enabling replay of an old, already-executed, signed transaction under that same key.

### Finding Description
- `action_add_key` (`runtime/runtime/src/access_keys.rs:149`) only rejects an `AddKeyAction` if the public key **currently** exists in the trie (`AddKeyAlreadyExists`, line 157). It performs no check against any nonce “high-water mark” for that pubkey.
- `add_regular_key` (`:230`) sets `access_key.nonce = initial_nonce_value(block_height)` = `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (M = 1_000_000), completely discarding any previously stored nonce for that key.
- Nonce validation in `verify_and_charge_tx_ephemeral` (`runtime/runtime/src/verifier.rs:269-305`) only checks `tx_nonce > effective_nonce` where `effective_nonce = max(access_key.nonce, pending.max_nonce)` (line 302); `verify_nonce` (`:210-237`) enforces the tx nonce is below `block_height * M`, but never enforces that a *reissued* key's nonce floor must exceed any nonce previously consumed under the same pubkey.
- `test_delete_key_add_key` (`runtime/runtime/tests/apply.rs:1167`) demonstrates that a single receipt with `[DeleteKey(pk), AddKey(pk, FullAccess)]` for an identical public key executes successfully (only storage-usage conservation is asserted; nonce behavior is not checked).

Exploit flow (all steps performed by the unprivileged account owner against their own account, no validator/relayer/node privilege required):
1. Attacker owns account `A` with `FullAccess` key `pk`, current stored nonce low.
2. At block height `H`, attacker submits and gets executed a “valuable” transaction `Tx_v` signed with `pk` using nonce `N` chosen close to `H*M - 1` (still `< H*M`, so it passes `NonceTooLarge`). `Tx_v` performs some beneficial, one-shot action (e.g., a `FunctionCall` to a bridge/vault/reward contract that pays the attacker on success). Regular nonce mode allows any nonce greater than current (no requirement to increment by exactly 1), so jumping to `N` near the upper bound is legal in a single step.
3. In the very next transaction (still at height `H` or `H+1`), attacker submits `Tx_reset` = `[DeleteKey(pk), DeleteKey removes it, AddKey(pk, FullAccess)]` in one action list of one receipt. This is processed with `apply_state.block_height = H'` (H or very close to it). `action_delete_key` removes the access key entirely; `action_add_key`/`add_regular_key` re-creates it with `nonce = (H'-1)*M`, which is far below `N` (since `N` was chosen near `H*M-1 ≫ (H'-1)*M` when `H'` is close to `H`).
4. The stored nonce for `pk` is now `(H'-1)*M`, strictly less than `N`.
5. Attacker rebroadcasts the exact original signed bytes of `Tx_v` (nonce `N`, same public key `pk`, same signature — still cryptographically valid because `pk` was re-added unchanged). `verify_and_charge_tx_ephemeral` accepts it because `N > (H'-1)*M` and `N < current_block_height * M`. `Tx_v` is executed a second time.

Why existing checks fail: signature verification succeeds (same key material), the nonce upper-bound check only bounds nonces against the *current* block height (not against previously consumed nonces), and `AddKeyAlreadyExists` only guards against a key existing simultaneously — it does not persist or check the historical maximum nonce once a key is deleted. The `initial_nonce_value` seeding was designed to prevent tx-hash collisions for freshly created keys/accounts (per the code comment referencing near/nearcore#3779), not to preserve monotonicity when the *same* pubkey is deleted and re-added within the *same* account's lifetime.

### Impact Explanation
This breaks the core nonce-monotonicity invariant that NEAR's replay-protection relies on. If any downstream contract or protocol semantics treat a signed transaction (or the receipt it produces) as consumable only once — e.g., bridge withdrawals, one-time claim/reward functions, vault payouts, or any `FunctionCall` whose receiver contract does not itself deduplicate calls — the attacker can trigger double execution of that call using their own previously-broadcast (and hence publicly-known) signed transaction. This maps to the "double-spend/replay" and "theft of funds" bounty category: a value-generating one-shot transaction from the attacker's own account (or a delegate/meta-transaction, which uses the same access-key nonce path) can be re-executed, netting the attacker duplicated payouts at the counterparty/protocol's expense.

### Likelihood Explanation
- Fully triggerable by an ordinary funded account with no special privileges: it only requires standard `Transaction` submission with `DeleteKey`+`AddKey` actions on the sender's own `FullAccess` key, both of which are always permitted for a `FullAccess` key holder.
- Cost is limited to standard gas/storage fees for two lightweight transactions.
- Fully repeatable: the attacker can perform the delete/re-add "nonce reset" dance again after gas/pending-tx window each time they want to replay another previously-consumed nonce range.
- The only nontrivial precondition is that the attacker's account already has a nonce close to `H*M` before doing the reset — but nonce mode allows jumping to any higher nonce, so this is trivially arranged in one extra transaction.

### Recommendation
Do not let `add_regular_key`/`add_gas_key` blindly overwrite the nonce with `initial_nonce_value(block_height)` when the pubkey was previously used on that account. Instead, persist a durable per-`(account_id, public_key)` maximum-nonce record that survives `DeleteKey`, and when re-adding the same public key, set `access_key.nonce = max(initial_nonce_value(block_height), previous_max_nonce_for_this_pubkey)`. Alternatively/additionally, disallow re-adding an identical public key that was deleted within the same block/receipt without bumping the seed strictly above the block-height upper bound already exhausted by that key (e.g., seed with `current_block_height * M` instead of `(block_height-1) * M`, and separately persist a tombstone of the highest nonce ever used per pubkey so it can never be reissued lower).

### Proof of Concept
Rust unit/integration test plan (extending `runtime/runtime/tests/apply.rs::test_delete_key_add_key` style, using `runtime.apply`):
1. Create account `alice` with a `FullAccess` key `pk`, initial nonce `0`, at block height `H0`.
2. Submit `Tx_v`: a `SignedTransaction` from `alice` using `pk`, nonce `N = H0*M - 5` (a `FunctionCall` or `Transfer` used as the "valuable" one-shot action), processed at block height `H0`. Assert it succeeds and is applied (nonce stored becomes `N`).
3. Submit `Tx_reset`: a `SignedTransaction` from `alice` using `pk`, nonce `N+1`, containing actions `[DeleteKey(pk), AddKey(pk, FullAccess)]`, processed at block height `H1` (`H1` close to `H0`, e.g., same or next height). Assert success.
4. Read back the access key for `(alice, pk)` and assert `access_key.nonce == (H1-1)*M`, which is `< N`.
5. Resubmit the **exact same signed bytes** of `Tx_v` (nonce `N`) at a later block height `H2 > H1`. Expected (buggy) result: `verify_and_charge_tx_ephemeral` returns `TxVerdict::Success` and the transaction's side effect (e.g., the `Transfer`/`FunctionCall` outcome) is applied a second time — proving replay. The assertion `new_access_key.nonce > highest_previously_observed_nonce_for_pubkey` fails because `(H1-1)*M < N`.
