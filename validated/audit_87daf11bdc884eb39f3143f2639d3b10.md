### Title
DoS via unbounded per-key concurrency queue when `max_queue_size` is unset or `[[concurrency]]` is not configured - (File: internal/limiter/concurrency_limiter.go)

### Summary
Gitaly's `ConcurrencyLimiter`, which backs the `[[concurrency]]` gRPC request-limiting feature (and the pack-objects limiter), allows callers to queue for a per-key semaphore with **no bound at all** unless an operator explicitly sets `max_queue_size` (`maxQueueLength`). When `maxQueueLength <= 0`, `getConcurrencyLimit` never creates `queueTokens`, so `acquire()` skips the `TryAcquire` admission check entirely and blocks indefinitely on `concurrencyTokens.Acquire(ctx)`. This is architecturally the same bug class as the Kubo Bitswap advisory: an ordinary, unauthenticated-in-effect actor (any client issuing normal Git operations) can push unbounded numbers of requests into an in-memory queue tied to a resource key, exhausting Gitaly's memory/goroutines, because the queue has no default upper bound in the underlying mechanism.

### Finding Description
`doc/backpressure.md` itself documents the risk: "An in-memory queue of requests can build up in Gitaly ... this is a potential vector for a memory leak" and explains that `max_queue_size`/`max_queue_wait` are needed "to prevent an unbounded in-memory queue of requests." [1](#0-0) 

The limiter code confirms this is not just a config-hygiene note but an actual code path: when `maxQueueLength` is `0`, no `queueTokens` semaphore is created, so admission control is bypassed and any number of concurrent callers can pile up waiting on `concurrencyTokens.Acquire(ctx)`: [2](#0-1) 

The `acquire()` function only performs bounded admission (`TryAcquire`, returning `ErrMaxQueueSize`) when `sem.queueTokens != nil`; otherwise it falls straight through to an unbounded wait: [3](#0-2) 

This is exercised directly by the test `"dynamic limit works without queuing"`, which explicitly states "No maxQueueLength, it means the limiter accepts unlimited requests to be queued" and by `"unlimited queueing"` in the middleware test, both confirming this is real, intended (but dangerous) behavior of the shared limiter code rather than a hypothetical: [4](#0-3) [5](#0-4) 

Reachability: `ConcurrencyLimiter.Limit` is invoked from the gRPC unary/stream interceptor for every RPC that has a matching `[[concurrency]]` entry keyed per-repository [6](#0-5) , and separately from the pack-objects hook path keyed by `RemoteIp`/repository/user for every fetch/clone [7](#0-6) . In both cases the limiting key (repository path, or remote IP+repo+user) is derived from ordinary client-controlled/attacker-observable values reachable by any user issuing pushes/fetches/clones — no privileged action is required.

Because `[[concurrency]]` entries with `max_queue_size` are opt-in per RPC (an administrator must explicitly configure them; there is no compiled-in fallback within `ConcurrencyLimiter` itself for maxQueueLength=0), any RPC route wired through the limiter without an explicit `max_queue_size` value inherits the unbounded-queue code path described above. A flood of concurrent requests against the same key (e.g., the same repository, or coordinated requests spoofing/varying `remote_ip`) causes goroutines and their held request buffers (git-pack-objects stdin buffers, gRPC message state, etc.) to accumulate without limit while waiting on the semaphore, consuming memory that is only released when each queued goroutine eventually gets to run or the client context is cancelled.

### Impact Explanation
An attacker with only ordinary push/fetch/clone access (or even fully unauthenticated access to public Git endpoints wired without `max_queue_size`) can flood a single limiting key with many concurrent requests. Each queued request holds a live goroutine plus associated buffered request state in memory for as long as it waits, with no cap on how many can queue simultaneously. This can exhaust Gitaly node memory/goroutine limits, resulting in denial of service to the whole node (not just the targeted repository), mirroring the "arbitrarily many bytes allocated / persists" pattern of the Bitswap advisory. Severity is Medium: it requires an unconfigured (or partially configured) `max_queue_size` for the targeted RPC/key, so its real-world blast radius depends on operator configuration.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the operator to not have set `max_queue_size` for the RPC/keys being flooded (or to rely on RPCs lacking an entry in `cfg.Concurrency` other than the hard-coded `ReplicateRepository` default). Since `[[concurrency]]` is opt-in and its queue-size protection defaults to "no protection" (`maxQueueLength = 0` behaves as unbounded, not as "reject all"), any newly added RPC or any deployment that hasn't been tuned per the `doc/backpressure.md` guidance is vulnerable by default. No special privileges, tokens, or MITM position are needed — only the ability to send many concurrent RPCs, i.e., a normal Git client capability.

### Recommendation
- Change `ConcurrencyLimiter`/`keyedConcurrencyLimiter` semantics so that `maxQueueLength <= 0` does not mean "unbounded," but instead defaults to a safe, finite cap (mirroring the fix pattern boxo/Kubo applied to Bitswap's WANT queue).
- Require (or force) `max_queue_size` and `max_queue_wait` to be set for every RPC/limiter type that is wired into the interceptor, including the pack-objects limiter, with a conservative built-in default when omitted.
- Add metrics/alerts on `limitsByKey` map size and per-key queue depth so unbounded growth is observable in production, and consider globally capping total in-flight+queued goroutines across all keys, not just per-key.

### Proof of Concept
1. Deploy Gitaly with an RPC wired through `[[concurrency]]` but with `max_queue_size` unset (or `0`), e.g.:
```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
```
2. As an ordinary client with read access to a repository, open many concurrent clone/fetch connections against the same repository (or, for the pack-objects limiter, vary the perceived `RemoteIp` while targeting the same repo/user) — far beyond `max_per_repo`.
3. Because `queueTokens` is `nil` when `max_queue_size` is `0`/unset, `acquire()` in `internal/limiter/concurrency_limiter.go` admits every one of these requests into the wait queue with no bound (per `internal/limiter/concurrency_limiter_test.go:558-567`'s documented "unlimited queueing" behavior).
4. Observe goroutine count and memory (`gitaly_concurrency_limiting_queued` gauge and process RSS) grow unboundedly as more concurrent requests are issued, with no `RESOURCE_EXHAUSTED`/`ErrMaxQueueSize` ever returned to the attacker, until the Gitaly process is starved of memory/goroutines and legitimate requests fail.

```go
func (sem *keyedConcurrencyLimiter) acquire(ctx context.Context, limitingKey string) (returnedErr error) {
	if sem.queueTokens != nil {
		// Try to acquire the queueing token. The queueing token is used to control how many
		// callers may wait for the concurrency token at the same time. If there are no more
		// queueing tokens then this indicates that the queue is full and we thus return an
		// error immediately.
		if err := sem.queueTokens.TryAcquire(); err != nil {
			return err
		}
		// We have acquired a queueing token, so we need to release it if acquiring
		// the concurrency token fails. If we succeed to acquire the concurrency
		// token though then we retain the queueing token until the caller signals
		// that the concurrency-limited function has finished. As a consequence the
		// queue token is returned together with the concurrency token.
		//
		// A simpler model would be to just have `maxQueueLength` many queueing
		// tokens. But this would add concurrency-limiting when acquiring the queue
		// token itself, which is not what we want to do. Instead, we want to admit
		// as many callers into the queue as the queue length permits plus the
		// number of available concurrency tokens allows.
		defer func() {
			if returnedErr != nil {
				sem.queueTokens.Release()
			}
		}()
	}

	// We are queued now, so let's tell the monitor. Furthermore, even though we're still
	// holding the queueing token when this function exits successfully we also tell the monitor
	// that we have exited the queue. It is only an implementation detail anyway that we hold on
	// to the token, so the monitor shouldn't care about that.
	sem.monitor.Queued(ctx, limitingKey, sem.queueLength())
	defer sem.monitor.Dequeued(ctx)

	if sem.maxQueueWait != 0 {
		if sem.setWaitTimeoutContext != nil {
			ctx = sem.setWaitTimeoutContext()
		} else {
			var cancel context.CancelFunc
			ctx, cancel = context.WithTimeout(ctx, sem.maxQueueWait)
			defer cancel()
		}
	}

	// Try to acquire the concurrency token now that we're in the queue.
	return sem.concurrencyTokens.Acquire(ctx)
```

```go
func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
```

```go
// UnaryInterceptor returns a Unary Interceptor
func (c *LimiterMiddleware) UnaryInterceptor() grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
		lockKey := c.getLockKey(ctx)
		if lockKey == "" {
			return handler(ctx, req)
		}

		// Check if request is authenticated
		limiter := c.methodLimiters[info.FullMethod]
		unauthLimiter, ok := c.methodLimitersUnauthenticated[info.FullMethod]
		if !auth.IsAuthenticated(ctx) && ok {
			limiter = unauthLimiter
		}

		if limiter == nil {
			// No concurrency limiting
			return handler(ctx, req)
		}

		return limiter.Limit(ctx, lockKey, func() (interface{}, error) {
			return handler(ctx, req)
		})
	}
}

// StreamInterceptor returns a Stream Interceptor
func (c *LimiterMiddleware) StreamInterceptor() grpc.StreamServerInterceptor {
	return func(srv interface{}, stream grpc.ServerStream, info *grpc.StreamServerInfo, handler grpc.StreamHandler) error {
		wrapper := &wrappedStream{stream, info, c, true}
		return handler(srv, wrapper)
	}
}
```

```go
	ctx context.Context,
	w io.Writer,
	limitkey string,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.ReadCloser,
	key string,

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	defer stdin.Close()

	if _, err := s.packObjectsLimiter.Limit(
		ctx,
		limitkey,
		func() (interface{}, error) {

					s.gitCmdFactory,
					w,
					req,
					args,
					stdin,
					key,
				)
		},

		return err
	}

	return nil
}
```
