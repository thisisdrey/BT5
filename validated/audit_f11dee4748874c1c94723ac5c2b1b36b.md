### Title
StackerDB chunk signatures lack contract-identifier binding, enabling cross-contract signature replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` — the digest that is actually signed and verified for every StackerDB chunk write — only commits to `slot_id`, `slot_version`, and `data_hash`. It never commits to the `QualifiedContractIdentifier` (the specific StackerDB) the chunk is destined for. Because several distinct StackerDB contracts (one per signer message type, e.g. `signers-0-1`, `signers-0-2`, …) are provisioned with the *same* signer→slot assignment for a given signer set, a signature produced to authorize a write to slot `S` in one contract is also a valid signature for slot `S` in every other sibling contract, and can be replayed there.

Consequence: signer address `A` owning `slot_id = k` in the `signers-0-1` (e.g. `BlockResponse`) contract also owns `slot_id = k` in `signers-0-2` (e.g. `Transactions`), `signers-0-3`, etc., for the same signer set. A signature `A` produced authorizing `(slot_id=k, slot_version=v, data_hash=h)` in one of these contracts is bit-for-bit indistinguishable from — and therefore accepted as — a valid authorization for `(slot_id=k, slot_version=v, data_hash=h)` in any sibling contract, as long as the target contract's current slot version for `k` is `< v` (`StaleChunk` check) and `v <= max_writes`.

This is the exact bug class from the external report ("signature signed for one specific context can be reused/replayed in a context it wasn't intended for") reproduced at the protocol layer: the signature commits to state that is *insufficient* to disambiguate which StackerDB it authorizes a write into.

### Impact Explanation
Any party that has observed one validly-signed chunk from a signer (chunks are gossiped/broadcast in the clear over the P2P StackerDB push/pull protocol and served over the public read/write HTTP StackerDB endpoints) can replay that exact `(slot_id, slot_version, sig, data)` tuple as a `StackerDBChunkData` POST against a *different* sibling StackerDB contract that shares the same slot assignment. This is an unauthenticated/unauthorized write to StackerDB state: the replica will store attacker-selected, previously-signed bytes under a slot in a contract the signer never intended to write to at that moment, and will propagate ("relay") it to peers as authentic signer-authored content for that contract (e.g. injecting a stale/foreign `BlockResponse` payload into the `Transactions` or `StateMachineUpdate` StackerDB, or vice versa). Consumers of that StackerDB (miners, other signers) that trust the fact "this chunk is signed by a known signer" without further disambiguating that the payload actually deserializes to the expected structure for that contract can be confused/misled by injected foreign-contract data, and downstream state machines could see inconsistent slot versions/timestamps.

### Likelihood Explanation
Medium-High. No secret key access is required — any node relaying gossip or reading via the public HTTP GetChunk/StackerDB endpoints can capture a validly-signed chunk, and the attack only requires reposting it against a different (but co-owned) contract via the standard `POST /v2/stackerdb/{contract_id}/chunks` endpoint or via the P2P push-chunk message. The main precondition (attacker must find a slot version gap in the sibling contract where `target_version < replayed_version <= max_writes`) is trivially satisfiable early in a reward cycle when sibling contracts' slots are freshly reset to version 0 while the source contract has already advanced past 0.

### Recommendation
Include the target `smart_contract_id` (and ideally a chain/network domain separator) inside `SlotMetadata::auth_digest()` so signatures are cryptographically bound to the specific StackerDB contract they authorize. This mirrors the report's suggested fix of adding a distinguishing/nonce-like field to prevent a signature from being valid in more than one intended context. All call sites of `sign`/`verify` (chunk write path in `db.rs`, chunk validation path in `stackerdb/mod.rs`, and any wire format expecting the old digest) need to be updated in lockstep, with a versioned/epoch-gated rollout to avoid breaking existing deployed signers.

### Proof of Concept
1. Signer `A` owns `slot_id = 5` in both `signers-0-1` (BlockResponse) and `signers-0-2` (Transactions) contracts for the current signer set (guaranteed by the shared slot list in `signers.clar`).
2. `A` legitimately signs and pushes chunk `C = (slot_id=5, slot_version=3, data_hash=H, sig=S)` to `signers-0-1`. This chunk is now visible to any peer via StackerDB gossip or read endpoints.
3. An attacker observes `C` and its raw bytes/signature, and constructs a `StackerDBChunkData{slot_id: 5, slot_version: 3, sig: S, data: <same bytes hashing to H>}`.
4. Attacker POSTs this chunk to `signers-0-2` (Transactions contract), where `A`'s slot 5 is currently at version `< 3` (e.g. version 0, since the Transactions contract hasn't advanced yet this cycle).
5. `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` runs `slot_desc.verify(&slot_validation.signer)` (`libstackerdb/src/libstackerdb.rs` `SlotMetadata::verify`) — this succeeds because the digest never included the contract id, and the `StaleChunk`/`TooManySlotWrites` checks pass because `3 > 0` and `3 <= max_writes`. The chunk is accepted and stored as if `A` legitimately authored it for the `Transactions` StackerDB, and it is then relayed to peers as authentic.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
