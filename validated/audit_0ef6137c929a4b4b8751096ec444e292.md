### Title
Unbounded in-memory buffering of attacker-controlled Git tag object size in `GetTagSignatures` via `catfile.Object` with no size cap - ([File: internal/gitaly/service/ref/tag_signatures.go])

### Summary
`objectReader.Object`/`Object.Read` (internal/git/catfile/object_reader.go:170-191, internal/git/catfile/object_content_reader.go:34-36) return a streaming reader over the object's declared size with no maximum-size enforcement, by design deferring size limiting to callers. `GetTagSignatures` (internal/gitaly/service/ref/tag_signatures.go:35-97) is one concrete caller that violates this contract: it calls `io.ReadAll(tag)` unconditionally on every tag object returned by `gitpipe.CatfileObject`, buffering the full object content in memory regardless of size.

### Finding Description
`GetTagSignatures` builds a `gitpipe.CatfileObject` pipeline from `req.GetTagRevisions()` and, for each tag object streamed back, calls `raw, err := io.ReadAll(tag)` at internal/gitaly/service/ref/tag_signatures.go:72 with no size cap before extracting the signature via `catfile.ExtractTagSignature`. The underlying `Object` returned by the shared/cached `catfile --batch-command` process (internal/git/catfile/request_queue.go:154-216) is only bounded by the object's own declared size (`io.LimitedReader{N: objectInfo.Size}`), which is attacker-controlled: an unprivileged user who owns/forks a repository can push an annotated tag object whose message/content is arbitrarily large (git places no practical size limit on tag objects). `verifyGetTagSignaturesRequest` (referenced at internal/gitaly/service/ref/tag_signatures.go:37) validates the repository/revision syntax but does not impose any object-size limit before the RPC descends into buffering. Because the batch reader is the shared, cached `ProcessCache` (internal/git/catfile/cache.go), the buffering happens per-request but repeated/concurrent calls against oversized tags can multiply memory pressure on the process serving many multiplexed RPCs.

By contrast, other consumers of the same primitive already guard against this: `linguist.fileInstance.DetermineStats` (internal/gitaly/linguist/file_instance.go:118-123) wraps the object reader in `io.LimitReader(object, 1024*16)`, and `localrepo.Repo.ReadObjectWithLimit` (internal/git/localrepo/objects.go:91-119) exists specifically to cap reads — indicating the codebase is aware size limiting is the caller's responsibility, but `GetTagSignatures` (and `localrepo.Repo.ReadObject`, internal/git/localrepo/objects.go:66-89) do not apply it.

### Impact Explanation
An attacker can force the Gitaly process to allocate memory proportional to a single pushed tag object's size with no server-side cap, exhausting process memory and impacting the shared cached `catfile` batch process used by other concurrently multiplexed RPCs on the same repository/connection. This matches a memory-exhaustion DoS of an RPC handler.

### Likelihood Explanation
The attacker only needs the ability to push to a repository they control (create/import repo, push an oversized annotated tag object) and to invoke the `GetTagSignatures` RPC referencing that tag revision — both standard, unprivileged capabilities. No special configuration, secrets, or race conditions are required, making this readily and repeatably exploitable.

### Recommendation
Bound the read in `GetTagSignatures` (and similarly in `localrepo.Repo.ReadObject`) using `io.LimitReader` or by rejecting/streaming-processing tag objects above a sane maximum size before calling `io.ReadAll`, mirroring the pattern already used in `linguist.fileInstance.DetermineStats` and `localrepo.Repo.ReadObjectWithLimit`.

### Proof of Concept
```
# 1. Create a repo, add a tag object with a very large annotation:
python3 -c "print('A'*2_000_000_000)" > big_msg.txt
git tag -F big_msg.txt big-tag HEAD
git push origin big-tag

# 2. Call GetTagSignatures RPC with TagRevisions=["big-tag"] against the Gitaly server
#    hosting this repository, and monitor gitaly RSS during the call.
```
Expected: gitaly RSS grows by roughly the size of the tag object (here ~2GB) during `io.ReadAll(tag)` at internal/gitaly/service/ref/tag_signatures.go:72, with no server-side size cap preventing it.

Note: the specific example cited in the question (`linguist.Instance.Stats`) is **not** vulnerable — `fileInstance.DetermineStats` already limits reads to 16 KiB via `io.LimitReader` (internal/gitaly/linguist/file_instance.go:120). The underlying design gap (no cap in `catfile.Object` itself) is real, but the concrete exploitable instance found is `GetTagSignatures`, not linguist. 		return structerr.NewInternal("creating object reader: %w", err)
	}
	defer cancel()

	chunker := chunk.New(&tagSignatureSender{
		send: func(signatures []*gitalypb.GetTagSignaturesResponse_TagSignature) error {
			return stream.Send(&gitalypb.GetTagSignaturesResponse{
				Signatures: signatures,
			})
		},
	})

	revlistOptions := []gitpipe.RevlistOption{
		gitpipe.WithObjects(),
		gitpipe.WithObjectTypeFilter(gitpipe.ObjectTypeTag),
	}

	revlistIter := gitpipe.Revlist(ctx, repo, req.GetTagRevisions(), revlistOptions...)

	catfileObjectIter, err := gitpipe.CatfileObject(ctx, objectReader, revlistIter)
	if err != nil {
		return structerr.NewInternal("creating cat-file object iterator: %w", err)
	}

	for catfileObjectIter.Next() {
		tag := catfileObjectIter.Result()

		raw, err := io.ReadAll(tag)
		if err != nil {
			return structerr.NewInternal("reading tag: %w", err)
		}

		signatureKey, tagText := catfile.ExtractTagSignature(raw)

		if err := chunker.Send(&gitalypb.GetTagSignaturesResponse_TagSignature{
			TagId:     tag.ObjectID().String(),
			Signature: signatureKey,
			Content:   tagText,
		}); err != nil {
			return structerr.NewInternal("sending tag signature chunk: %w", err)
		}
	}

	if err := catfileObjectIter.Err(); err != nil {
		return structerr.NewInternal("cat-file iterator stop: %w", err)
	}

	if err := chunker.Flush(); err != nil {
		return structerr.NewInternal("flushing chunker: %w", err)
	}

	return nil
}

// ReadObject reads an object from the repository's object database. InvalidObjectError
// is returned if the oid does not refer to a valid object.
func (repo *Repo) ReadObject(ctx context.Context, oid git.ObjectID) ([]byte, error) {
	objectReader, cancel, err := repo.catfileCache.ObjectReader(ctx, repo)
	if err != nil {
		return nil, fmt.Errorf("create object reader: %w", err)
	}
	defer cancel()

	object, err := objectReader.Object(ctx, oid.Revision())
	if err != nil {
		if errors.As(err, &catfile.NotFoundError{}) {
			return nil, InvalidObjectError(oid.String())
		}
		return nil, fmt.Errorf("get object from reader: %w", err)
	}

	data, err := io.ReadAll(object)
	if err != nil {
		return nil, fmt.Errorf("read object from reader: %w", err)
	}

	return data, nil
}

// ReadObjectWithLimit is like ReadObject, but reads at most limit bytes of the
// object's content.
func (repo *Repo) ReadObjectWithLimit(ctx context.Context, oid git.ObjectID, limit int64) ([]byte, error) {
	objectReader, cancel, err := repo.catfileCache.ObjectReader(ctx, repo)
	if err != nil {
		return nil, fmt.Errorf("create object reader: %w", err)
	}
	defer cancel()

	object, err := objectReader.Object(ctx, oid.Revision())
	if err != nil {
		if errors.As(err, &catfile.NotFoundError{}) {
			return nil, InvalidObjectError(oid.String())
		}
		return nil, fmt.Errorf("get object from reader: %w", err)
	}

	// io.LimitReader returns EOF once the limit is reached. This leaves the
	// object in a potentially half-read state as we might've read less than
	// the total object size. This will be problematic if the process is reused
	// for a future cat-file invocation, but thankfully the cache can detect if
	// the object is dirty, and discard it from the cache.
	data, err := io.ReadAll(io.LimitReader(object, limit))
	if err != nil {
		return nil, fmt.Errorf("read object from reader: %w", err)
	}

	return data, nil
}

// Object represents data returned by `git cat-file --batch`
type Object struct {
	// ObjectInfo represents main information about object
	ObjectInfo

	// dataReader is reader which has all the object data.
	dataReader io.Reader
}

func (o *Object) Read(p []byte) (int, error) {
	return o.dataReader.Read(p)
}

// WriteTo implements the io.WriterTo interface. It defers the write to the embedded object reader
// via `io.Copy()`, which in turn will use `WriteTo()` or `ReadFrom()` in case these interfaces are
// implemented by the respective reader or writer.
func (o *Object) WriteTo(w io.Writer) (int64, error) {
	// `io.Copy()` will make use of `ReadFrom()` in case the writer implements it.
	return io.Copy(w, o.dataReader)
}
