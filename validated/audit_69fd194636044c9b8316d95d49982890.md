### Title
Rewards emitted while `totalSupply == 0` are permanently burned from the index and stuck in `RewardsDistributor` - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenIndex` advances the accrual `timestamp` even when `token_.totalSupply() == 0`, while contributing a `_ratio` of `0` to the index. Every second of reward emissions (`speed * deltaT`) during a zero-supply window is therefore silently skipped — it is never credited to any account's index and the corresponding `rewardToken` balance can never be claimed, remaining permanently stuck in the contract. This is the same bug class as the reference finding (rewards accrued before the first depositor are unclaimable), with the same invariant break in reward-accrual accounting.

### Finding Description
In `_calculateTokenIndex`:

```solidity
uint256 _totalSupply = token_.totalSupply();
uint256 _tokensAccrued = _deltaTimestamps * _speed;
uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
_newIndex = (_supplyState.index + _ratio).toUint224();
_newTimestamp = block.timestamp.toUint32();
``` [1](#0-0) 

When `totalSupply == 0` and `speed > 0`, `_ratio` is `0` but `_newTimestamp` is still set to `block.timestamp`. `_updateTokenIndex` then persists the new timestamp while the index is unchanged (lines 274-277). The elapsed time is "consumed" without accruing anything, so emissions for that window are irrecoverably lost — later depositors can only accrue from the moment supply becomes non-zero.

Because the distributor pays claims from its raw `rewardToken` balance via `_transferRewardIfEnoughTokens` (lines 248-256) and the contract exposes no sweep/rescue function for `rewardToken` (confirmed — no `sweep`/`recover` exists on `RewardsDistributor`), the skipped emissions remain in the contract balance forever with zero `tokensAccruedOf` accounting against them.

The state is reachable through public, unprivileged paths: `updateBeforeMintOrBurn` (callable by anyone per its natspec, line 173) and `claimRewards(address[], IERC20[])` both trigger `_updateTokenIndex` (lines 150-167, 175-180), and the hooks are also invoked on every DepositToken/DebtToken mint, burn, and transfer (lines 186-192). A new deposit token listed via `updateTokenSpeed` necessarily has `totalSupply == 0` until the first deposit, and any later full withdrawal recreates the zero-supply window.

### Impact Explanation
Permanent freezing of unclaimed yield: all `rewardToken` emitted during zero-supply periods (including the entire period between a token's speed being set and its first deposit) is undistributable and locked in the contract indefinitely, breaking the reward-accrual conservation invariant (emitted rewards ≠ claimable rewards).

### Likelihood Explanation
Certain for any reward token whose speed is configured before the pool has deposits — the standard launch sequence — and recurring on every full-withdrawal event thereafter. No attacker action or privileged role is required; an unprivileged caller can force the timestamp consumption by calling `updateBeforeMintOrBurn` or `claimRewards` during the zero-supply window.

### Recommendation
When `totalSupply == 0`, do not advance `_supplyState.timestamp` (return `_newTimestamp = _supplyState.timestamp` instead of `block.timestamp`), so emissions accumulate and are distributed once supply exists. Alternatively, track a `pendingAccrued` bucket per token that is folded into `_ratio` on the next non-zero-supply update.

### Proof of Concept
```typescript
// Hardhat (test/RewardDistributor.test.ts style, mocks as in existing suite)
it('burns emissions while totalSupply == 0', async function () {
  // governor sets speed on a fresh token (supply == 0)
  await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, parseEther('1'))
  msdTOKEN1.totalSupply.returns(0)
  msdTOKEN1.balanceOf.returns(0)

  // 100s pass with no supply; anyone (or a token hook) updates the index
  await increaseTimeOfNextBlock(100)
  await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, alice.address)

  // timestamp advanced, index unchanged → 100 rewardTokens skipped
  const {index, timestamp} = await rewardDistributor.tokenStates(msdTOKEN1.address)
  expect(index).eq(INITIAL_INDEX)

  // Alice deposits; only time AFTER her deposit accrues
  msdTOKEN1.totalSupply.returns(parseEther('100'))
  msdTOKEN1.balanceOf.returns(parseEther('100'))
  await increaseTimeOfNextBlock(10)
  const claimable = await rewardDistributor['claimable(address)'](alice.address)
  expect(claimable).eq(parseEther('10')) // the 100 tokens emitted earlier are unclaimable

  // rewardToken balance of distributor still holds the 100 tokens; no function can move them
})
```
