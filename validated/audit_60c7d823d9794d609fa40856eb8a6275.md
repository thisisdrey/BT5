### Title
Reentrancy via malicious `<ft-trait>` in `collateral-add` allows theft of pooled collateral through mask/state desync - (File: `mainnet/contracts/market/v0-market-vault.clar`)

### Summary
`v0-market-vault.collateral-add` violates checks-effects-interactions: it commits the `collateral` map update (`add-user-collateral`) in its `let` bindings *before* the external token transfer (`receive-tokens`) executes, and only writes the position `registry` (mask) *after* that external call, using a value computed *before* the call. A malicious `<ft-trait>` contract passed as `ft` can reenter `v0-4-market.clar` mid-transfer, call `collateral-remove` while the `collateral` map already reflects the not-yet-paid-for deposit, withdraw real pooled tokens, and then let the outer call overwrite the registry with a stale mask that (falsely) marks the asset as still held. This yields both a free withdrawal of real collateral and a corrupted, inconsistent authorization state.

### Finding Description
In `collateral-add`: [1](#0-0) 

The `let` bindings compute `updated-entry` (mask with the new asset bit set) and immediately call `add-user-collateral`, which does `map-set collateral key updated-collateral-amount` — this commits to chain state before any assertion or external call: [2](#0-1) 

Only after this map write does the function call the external `ft` contract via `receive-tokens`: [3](#0-2) 

and only *after* that external call returns does it commit the registry/mask via `insert updated-entry` — using a mask value that was computed *before* the external call, i.e. it is stale with respect to anything that happened during the callback: [4](#0-3) 

Attack flow:
1. Attacker deploys a malicious `<ft-trait>` contract whose `transfer` function, instead of moving real value, reenters `v0-4-market.clar` and calls `collateral-remove` for the same `asset-id`.
2. Attacker calls `v0-4-market.clar` collateral-add path with this malicious contract as `ft` for `asset-id A`, amount `X`. Inside `v0-market-vault.collateral-add`, the `collateral` map is already set to `X` for `{id, asset: A}` (step in `let`) before `receive-tokens` is invoked.
3. During the callback, the malicious `transfer` invokes `v0-4-market.clar collateral-remove` (or `borrow`) for asset `A`. That call reaches `v0-market-vault.collateral-remove`, passing `check-impl-auth` because `contract-caller` is still `v0-4-market` (the registered `impl`): [5](#0-4) 
Since the `collateral` map already shows `X` for asset `A` (written in step 2, before any real tokens moved), `remove-user-collateral` succeeds, and `send-tokens` transfers *real* pooled `A` tokens to the attacker's chosen recipient — funded from the vault's shared custody, not from the attacker's own deposit.
4. The reentrant call also calls `insert` on the registry with its own computed mask (bit A effectively unset, since it was never actually set yet).
5. Control returns to `receive-tokens`; the malicious contract simply returns `(ok true)` without ever moving real value. `collateral-add` then proceeds to its own `insert updated-entry` (line 389), which was computed *before* the reentrant call and unconditionally overwrites the registry entry the reentrant call just wrote — setting the mask bit for asset `A` as if the attacker still holds it, even though the reentrant withdrawal already zeroed the real `collateral` map entry and sent real tokens out.

Net effect: attacker receives real tokens of asset `A` from pooled collateral while ending up with a position whose mask claims asset `A` is held as collateral (usable to satisfy health checks / further borrowing) with zero real backing. This is not stopped by `check-impl-auth` (which only checks the calling contract is `impl`, not reentrancy), by pause flags, or by any nonce/lock guarding reentrant calls — there is no reentrancy guard in this contract.

### Impact Explanation
This is theft of pooled user funds at rest (real `A` tokens withdrawn from shared vault custody without a matching real deposit) combined with insolvency of the market’s internal accounting (mask claims collateral that does not exist, which can be leveraged for further unauthorized borrowing). This matches the in-scope **Critical** category: direct theft of user funds / protocol insolvency.

### Likelihood Explanation
Preconditions are all attacker-controlled and require no privileged access: fund a wallet with STX for fees, deploy an ordinary Clarity contract implementing `<ft-trait>`, and call the public `collateral-add`/`supply-collateral-add` entrypoint passing that contract as `ft`. The attack is repeatable per asset and does not require DAO, oracle, or miner cooperation. I was not able to fully verify from the truncated `v0-4-market.clar` read whether the market layer validates that the supplied `ft` principal matches the registered token address for `asset-id` before forwarding to `v0-market-vault.collateral-add`; if such a check exists it would need to be bypassed or the reentrancy triggered through a legitimate token whose behavior can still be influenced (e.g., a token with hooks), which would lower likelihood. Absent confirmation of that check, the vault-level ordering bug documented above is a concrete, reachable defect regardless.

### Recommendation
Restructure `collateral-add` (and symmetrically double-check `collateral-remove`, `debt-add-scaled`, `debt-remove-scaled`) to follow strict checks-effects-interactions: perform all state reads, then the external `contract-call?` to the `ft` trait, and only after that call succeeds perform all map/registry writes (`add-user-collateral` and `insert`) using values recomputed/re-validated after the external call returns — never before it. Additionally add an explicit reentrancy guard (e.g., a boolean lock keyed on the user's obligation id or a global in-progress flag) around any function that performs an external `contract-call?` to an attacker-suppliable `<ft-trait>` before committing state, so that nested calls into `collateral-add`/`collateral-remove`/`debt-*` for the same account are rejected while the outer call is unresolved.

### Proof of Concept
Clarinet simnet test plan (TypeScript/Clarinet SDK) on a local fork:
1. Deploy the mainnet contract set (`v0-market-vault`, `v0-4-market`, `v0-assets`, vault contracts) plus a malicious `ft-trait` implementation contract (`malicious-ft.clar`) whose `transfer` function, when called with a specific amount/sender, issues a `contract-call?` back into `v0-4-market.clar`'s `collateral-remove` (or `borrow`) for the same `asset-id`, then unconditionally returns `(ok true)`.
2. Set up an attacker account with an existing tracked position (via `resolve`) carrying legitimate collateral/debt on a real asset (e.g. sBTC) to satisfy "existing position with debt" preconditions.
3. Have the attacker call `v0-4-market.clar`'s collateral-add entrypoint with `ft = malicious-ft`, `asset-id = A` (an id whose vault actually holds pooled real tokens), `amount = X`, `recipient = attacker` for the nested `collateral-remove` call.
4. Assert: attacker's real token balance of asset `A` increases by `X` (stolen) even though attacker's actual `ft` transfer to the vault never moved real value.
5. Assert: `map-get? collateral {id: attacker-id, asset: A}` after the full transaction is inconsistent with `map-get? registry attacker-id` mask bit for `A` — i.e., mask bit for `A` set while collateral amount is `0`, proving the desync described.
6. Negative control: repeat with the vault fixed (external call moved after all state writes, or reentrancy guard added) and assert the reentrant `collateral-remove` call either reverts with `ERR-INSUFFICIENT-COLLATERAL`/reentrancy-guard error, or the transaction as a whole aborts, and that final `collateral` map value equals the sum of legitimate deposits minus legitimate removals with mask consistent with actual balances.

        (collateral-amount (default-to u0 (map-get? collateral key))) ;; graceful default
        (updated-collateral-amount (+ collateral-amount amount)))

(define-public (collateral-add (account principal) (amount uint) (ft <ft-trait>) (asset-id uint))
  (let ((states (var-get pause-states))
        (entry (resolve-or-create account))
        (user-id (get id entry))
        (mask (get mask entry))
        (updated-mask (mask-update mask asset-id true true)) ;; collateral, insert
        (updated-entry (merge entry (refresh updated-mask)))
        (result (add-user-collateral user-id asset-id amount)))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-add states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (try! (receive-tokens ft amount account))
    
    (insert updated-entry)

    (print {
      action: "collateral-add",
      caller: contract-caller,
      data: {
        account: account,
        asset-id: asset-id,
        amount: amount,
        updated-collateral-amount: result,
        mask-before: mask,
        mask-after: updated-mask
      }
    })
      
    (ok result)))

(define-public (collateral-remove (account principal) (amount uint) (ft <ft-trait>) (asset-id uint) (recipient principal))
  (let ((states (var-get pause-states))
        (entry (resolve account))
        (user-id (get id entry))
        (mask (get mask entry))
        (remaining (try! (remove-user-collateral user-id asset-id amount)))
        (updated-mask (if (is-eq remaining u0)
                        (mask-update mask asset-id true false) ;; collateral, remove
                        mask))
        (updated-entry (merge entry (refresh updated-mask))))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-remove states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (insert updated-entry)
    (try! (send-tokens ft amount recipient))
    
    (print {
      action: "collateral-remove",
      caller: contract-caller,
      data: {
        account: account,
        recipient: recipient,
        asset-id: asset-id,
        amount: amount,
        updated-collateral-amount: remaining,
        mask-before: mask,
        mask-after: updated-mask
      }
    })
    
    (ok remaining)))
