### Title
Replay-window TOCTOU in `ConnectionState.Decrypt`/`VerifyRelay` allows duplicate-packet replay under multi-routine UDP processing - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the replay-window check and the replay-window update into two separate critical sections, releasing `decryptLock` between `window.Check` and `window.Update`. When `routines > 1` is configured, multiple goroutines can process UDP packets destined for the same `HostInfo`/`ConnectionState` concurrently, so a captured/duplicated ciphertext packet can pass `Check` twice before either goroutine calls `Update`, defeating the anti-replay window and allowing the same encrypted packet to be delivered to the tun device (or forwarded, in the relay case) more than once.

### Finding Description
Analogous to the reported Vault bug — where a value used mid-calculation (`convertToShares`) is computed from state that is mutated non-atomically around it, producing an incorrect security-relevant result — `Decrypt`/`VerifyRelay` compute the replay decision (`Check`) using pre-mutation window state, release the lock, perform the (unlocked) AEAD decryption, then re-acquire the lock and commit the mutation (`Update`). Between the two locked sections there is a window where the anti-replay state does not yet reflect the in-flight packet: [1](#0-0) 

If two goroutines (e.g. two of the `f.routines` UDP-read routines, or one direct path and one relay path) receive the same on-wire ciphertext with the same `messageCounter` at roughly the same time, both can:
1. call `window.Check` (locked, released immediately) and both observe "not yet seen" (`true`),
2. proceed to `dKey.DecryptDanger` outside any lock (this succeeds for both, since it's the same valid ciphertext),
3. both later call `window.Update`, and since `Update` for a value at or below `current` treats the second call as a duplicate `only for its own bit`, but by the time both threads got past `Check`, both have already decrypted and are about to hand the plaintext to `handleOutsideMessagePacket`/tun.

This defeats the purpose of `Bits` as an anti-replay mechanism (`const ReplayWindow = 1024`, `connection_state.go:15`), which is explicitly relied upon elsewhere in the codebase to prevent double-delivery of relayed/duplicated frames (see the dedicated relay replay-protection test at `e2e/tunnels_test.go:377-467`, which asserts that relayed duplicate frames must be dropped, not just detected).

The `readOutsidePackets` call path confirms multiple independent goroutines (one per `f.routines`, e.g. via `NewMultiQueueReader`) feed the same `hostinfo.ConnectionState.Decrypt`: [2](#0-1) [4](#0-3) 

The same pattern (`Check` → unlock → verify → lock → `Update`) exists in `VerifyRelay`, used on the relay-forwarding path that the CHANGELOG explicitly calls out as security sensitive ("Advance the replay window on relayed packets so a relay drops replayed frames instead of re-forwarding them" and "Lock replay window updates so concurrent readers can't corrupt it"), indicating the project is aware of concurrency hazards in this exact function but the fix only serialized `Bits` internal state corruption — it did not close the Check/Update TOCTOU gap.

### Impact Explanation
An attacker who can duplicate/replay a captured, still-valid ciphertext packet (well within their reach without holding any CA-signed certificate — this is exactly the on-wire replay threat model the anti-replay window exists to defend against) can, under multi-routine configurations (`routines` > 1, which is a supported and documented configuration), cause the same packet to be processed twice: delivered twice to the tun device, or — on a relay node — forwarded twice toward the target. This is a concrete replay bypass of the mechanism explicitly designed to prevent it, directly matching the accepted impact categories (traffic replay).

### Likelihood Explanation
Requires: (a) `routines` > 1 configured (documented, supported), and (b) an attacker able to race two copies of the same captured ciphertext packet to the two UDP listener sockets/routines within the small window between `Check` and `Update`. This is a timing-sensitive but externally triggerable condition — no valid certificate or authenticated peer status is required, since the attacker is replaying an already-observed ciphertext on the wire.

### Recommendation
Perform the replay-window check-and-mark as a single atomic operation under one critical section rather than two separate lock/unlock pairs, e.g. add a combined `CheckAndReserve`/`Update`-only method that holds `decryptLock` across both the window check and the window mark, releasing it only after decryption succeeds (rolling back the reservation on decryption failure), so no other goroutine can observe a "not yet seen" state for the same counter while decryption of the first copy is still in flight.

### Proof of Concept
1. Configure a node with `routines: 2` (or more) so `f.routines > 1` and multiple UDP reader goroutines exist for the same socket family, per `interface.go` `run()`/`listenOut`.
2. Capture a single legitimate, in-window ciphertext packet destined for an established tunnel (as in the existing relay replay test at `e2e/tunnels_test.go:382-467`, which demonstrates capture-and-replay is already an exercised threat model in this codebase).
3. Inject two copies of the identical captured packet at (near) the same instant so they are picked up by two different reader routines.
4. Observe that both `window.Check` calls succeed (return `true`) because neither has yet called `window.Update`, and both `DecryptDanger` calls succeed since the ciphertext is identical/valid; the plaintext is thus delivered/forwarded twice instead of the expected single delivery with the duplicate dropped.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error

	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
