Confirmed: the RPC handler `DisconnectGitAlternates` in `internal/gitaly/service/objectpool/alternates.go` only calls `s.locator.ValidateRepository(ctx, repository)` — this validates the *member repository's* path, not the alternates target — before invoking `objectpool.Disconnect`, which performs no storage-root containment check on `altObjectDir`.

### Title
Object pool Disconnect follows attacker-controlled alternates path outside storage root, hard-linking arbitrary files into the repository - ([File: internal/git/objectpool/disconnect.go])

### Summary
`Disconnect` (and the `findObjectFiles`/link loop it drives) resolves `altObjectDir` from the repository's `objects/info/alternates` file via `stats.AlternatesInfoForRepository` / `AbsoluteObjectDirectories()` and uses it directly with `os.Stat`, `filepath.Walk`, and `storage.Link`, without ever verifying the path is contained within the storage root. `storage.Link` (`internal/gitaly/storage/fs.go`) performs a raw `os.Link(filepath.Join(f.Root(), source), filepath.Join(f.Root(), destination))`, and the `sourceRelativePath` fed to it is computed with `filepath.Rel(f.Root(), filepath.Join(altObjectDir, path))`, which for two absolute paths never errors — it just yields a `../../..`-style relative path that `filepath.Join(f.Root(), ...)` resolves right back to the original out-of-root absolute path.

### Finding Description
In `Disconnect` (`internal/git/objectpool/disconnect.go:36-117`):
- `altObjectDir := altInfo.AbsoluteObjectDirectories()[0]` (line 77) takes the alternates value verbatim; `AlternatesInfo.AbsoluteObjectDirectories()` (`internal/git/stats/repository_info.go:590-602`) simply returns the path as-is if absolute, or joins it to the repo's own `objects` dir if relative — there is no storage-root check anywhere in this call chain.
- The only sanity checks performed are: exactly one alternate directory (line 71-73), that it exists on disk (`os.Stat`, line 78), and that it's a directory (line 85-87). None of these constrain the path to be under the storage root.
- `findObjectFiles(altObjectDir)` (line 89, defined at 136-166) walks the target directory with `filepath.Walk`, listing every non-`info/` file.
- For each file, `sourceRelativePath, _ := filepath.Rel(f.Root(), filepath.Join(altObjectDir, path))` (line 100) computes a "relative" path assuming containment, but `filepath.Rel` between two absolute paths on the same volume never fails even when one is outside the other — it returns a path with leading `..` segments.
- `storage.Link(f, sourceRelativePath, targetRelativePath)` (line 110) then calls `os.Link(filepath.Join(f.Root(), sourceRelativePath), filepath.Join(f.Root(), targetRelativePath))` (`internal/gitaly/storage/fs.go:42-52`). Because `filepath.Join(f.Root(), sourceRelativePath)` un-does the `Rel` computation, this resolves back to the original absolute `altObjectDir/path`, entirely independent of `f.Root()`. There is no `storage.ValidateRelativePath` or prefix check anywhere in this path.

This contrasts with the codebase's own established pattern for handling attacker-influenced alternates elsewhere: `internal/git/dirs.go`'s `altObjectDirs` explicitly checks `strings.HasPrefix(newDir, storagePrefix)` and returns `alternateOutsideStorageError` otherwise (used by `git.AlternateObjectDirectories`, consumed for e.g. quarantine/objects-directory resolution), and `internal/gitaly/storage/storagemgr/partition_assigner.go:317-361` explicitly calls `storage.ValidateRelativePath` on the alternate before using it, rejecting escapes with `storage.ErrRelativePathEscapesRoot`. `Disconnect`, however, uses neither mechanism.

An attacker who owns a repository can write an arbitrary path (e.g. `/etc` or another repo's `objects` directory) into `objects/info/alternates` of their own repo — writing this file is a plain filesystem write inside the repository directory tree, reachable indirectly by any flow that lets a user influence repository content that ends up under `objects/info/alternates` (this file itself isn't part of the git object model pushed via `git push`, but Gitaly-side code such as `objectpool.Link` writes it based on repository state the RPC caller controls, and the RPC `DisconnectGitAlternates` is directly callable by any user with access to the target repository, taking only a `Repository` argument that is validated only for path/storage well-formedness, not alternates content). When `DisconnectGitAlternates` is subsequently invoked (attacker-triggerable directly, since it's a client-facing mutator RPC per `proto/objectpool.proto`), `Disconnect` will hard-link every non-`info/` file under the attacker-chosen directory into `<repo>/objects/<path>`.

### Impact Explanation
Successful exploitation lets an attacker hard-link arbitrary files from anywhere the Gitaly process's storage filesystem spans (subject to the same filesystem/device) into their own repository's object store as ordinary "git objects." Because a hard link makes the same inode readable from a location the attacker fully controls (their repo), they can then read out the linked file's contents (e.g., by fetching/exporting the repo, or reading it directly if the file happens to be a valid loose object, or via other repo access paths that read raw files under `objects/`). Depending on filesystem layout this can achieve cross-repository object/file disclosure (e.g., another tenant's Git objects on the same storage) or, if the storage root spans host paths, broader file disclosure limited by hard-link's same-filesystem constraint. This maps to a "cross-repository object access / file disclosure via path traversal" bounty class.

### Likelihood Explanation
Preconditions are attacker capabilities already in-scope: they need to own/control a repository (any GitLab user with a repo) and be able to get an alternates file with an attacker chosen path in place, then call `DisconnectGitAlternates` (or trigger a flow that calls `objectpool.Disconnect`, e.g., housekeeping/repo-pool disconnection). The RPC itself requires no special privilege beyond normal repository access. `os.Stat` and `IsDir` checks are trivially satisfiable by pointing at any real directory (e.g., `/etc`, or another repository's `objects` directory known/guessed by the attacker), so likelihood is moderate-to-high assuming the alternates file can be set to an attacker-chosen absolute (or `..`-escaping relative) path before `Disconnect` runs. Note: I was not able to fully confirm within the available context an end-to-end unprivileged RPC path that lets a user write directly arbitrary content into `objects/info/alternates` of their own repo bypassing all higher-level validation (e.g., whether `git push`-driven flows or `CreateObjectPool`/`LinkRepositoryToObjectPool` sanitize the alternate target before it reaches disk, or whether transaction/partition-assigner checks like `getAlternatePartitionID`'s `storage.ValidateRelativePath` run and reject escaping alternates before `Disconnect` is ever reached in the primary managed-transaction code path). This uncertainty affects exploitability but not the underlying code defect in `Disconnect` itself, which lacks defense-in-depth validation present elsewhere in the codebase (`dirs.go`, `partition_assigner.go`).

### Recommendation
In `Disconnect` (`internal/git/objectpool/disconnect.go`), after computing `altObjectDir := altInfo.AbsoluteObjectDirectories()[0]`, validate it is contained within the storage root (e.g., using `storage.ValidateRelativePath(f.Root(), ...)` or an equivalent prefix check like `git.dirs.go`'s `alternateOutsideStorageError` pattern) before calling `os.Stat`, `findObjectFiles`, or `storage.Link`, and return an error (not proceed) if it escapes. Additionally, harden `storage.Link` in `internal/gitaly/storage/fs.go` to reject `source`/`destination` inputs that resolve outside `f.Root()`, so similar bugs in other callers are caught defensively.

    require.Error(t, err)
