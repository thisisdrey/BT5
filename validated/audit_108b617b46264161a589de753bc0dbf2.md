### Title
`remove_account` fails to purge `ReceivedData`/`PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` rows, letting a stale postponed receipt execute against a recreated account - ([File: core/store/src/utils/mod.rs:504-575])

### Summary
`remove_account` (used by `action_delete_account`) only removes `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie rows for the deleted account, but never touches `TrieKey::ReceivedData`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt`. If those rows are populated at the moment of deletion (a receipt is still in flight awaiting a `DataReceipt`, or a `DataReceipt` already arrived but its dependent `ActionReceipt` had not), they survive account deletion and remain live when the account name is later re-created, letting stale bookkeeping resolve and execute against the new account incarnation.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account(state_update, account_id)` (`core/store/src/utils/mod.rs:504-575`), which only removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData` [1](#0-0) . It does not iterate or remove any `RECEIVED_DATA`, `POSTPONED_RECEIPT_ID`, `PENDING_DATA_COUNT`, or `POSTPONED_RECEIPT` column entries for that account, even though these are listed among `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` [2](#0-1) .

Normal receipt-matching semantics: when an `ActionReceipt` with `input_data_ids` arrives before all its `DataReceipt`s, `process_action_receipt` stores `PendingDataCount{receiver,receipt_id}` and `PostponedReceiptId{receiver,data_id}` and serializes the full receipt under `PostponedReceipt` (`runtime/runtime/src/lib.rs:1608-1655`). When the matching `DataReceipt` later arrives, `process_receipt`'s data branch (`runtime/runtime/src/lib.rs:1389-1443`) stores `ReceivedData`, looks up `PostponedReceiptId`, decrements `PendingDataCount`, and once it hits 0 fetches and executes the previously postponed receipt via `get_postponed_receipt`. Separately, `process_action_receipt` treats a data dependency as already satisfied purely via `has_received_data(state_update, account_id, data_id)` (`runtime/runtime/src/lib.rs:1610`), an unconditioned existence check on the `ReceivedData` trie key.

Because `remove_account` never clears these rows, if `receiver_id` is deleted (via `DeleteAccount`, permitted for the account owner when `locked() == 0`, `runtime/runtime/src/actions.rs:762-775`) while one of these rows is populated, and the account name is subsequently re-created (`CreateAccount`, permitted since the name is free, `runtime/runtime/src/actions.rs:795-817`), the stale rows persist untouched (they are keyed only by `account_id`, not by any generation/incarnation counter — no such counter exists) and are consumed by whichever receipt happens to complete the match:
- A late-arriving `ActionReceipt` whose `input_data_ids` include a `data_id` for which `ReceivedData` was stored pre-deletion will short-circuit via `has_received_data` and execute immediately (`lib.rs:1610`, `lib.rs:1625-1641`), instead of the "account did not exist"/fresh-postpone path.
- A late-arriving `DataReceipt` can match a still-present stale `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` set from before deletion, causing that original (pre-deletion) `ActionReceipt` — with its original, unmodifiable action list, `predecessor_id`, and `signer_id` — to execute against the newly created account's contract code/storage/keys/balance instead of being rejected or re-evaluated against the new account's existence state.

This is reachable purely through ordinary asynchronous, cross-shard receipt delivery timing (no malicious node/peer access required): an unprivileged user's own contract at `receiver_id` can self-destruct via `DeleteAccount` while a cross-contract callback it initiated (`.then()`-style `input_data_ids`) is still in flight, then anyone can re-register the freed `receiver_id`, after which the orphaned postponed receipt/data resolves and runs against the new account. No existing check enforces that pending `ReceivedData`/postponed-receipt bookkeeping be empty before allowing `DeleteAccount`, and `check_account_existence`/`check_actor_permissions` only checks the *current* account existence/locked stake at execution time, not queued cross-receipts tied to the same `account_id`.

### Impact Explanation
The concrete effect is a "receipt misdelivery" defect: a receipt that was queued/postponed for one account incarnation executes, without re-validation, against a different, later-created account occupying the same `account_id`. This falls under "authorization escalation across accounts or promises" — actions embedded in the stale postponed receipt (which can include `Transfer`, `FunctionCall` with a `deposit`, etc., predetermined by the *original* predecessor before deletion) run against the new account's current contract/keys/balance, and the new account's owner never authorized or expected this pending execution to land against their newly created account. It is deterministic and reproducible by all validators identically (same trie/state transition on all replicas), so there is no consensus/state-root divergence, but it constitutes a real execution-path integrity violation matching the described "cross-owner data leakage / receipt misdelivery causing incorrect execution path" scoped impact.

### Likelihood Explanation
Preconditions are all reachable by an ordinary unprivileged account: (1) the victim account must itself initiate an outstanding cross-contract call chain (creating `PendingDataCount`/`PostponedReceiptId`/`PostponedReceipt`, or receiving a `DataReceipt` ahead of its dependent `ActionReceipt`), (2) the same account's owner (or a compromised/self-destructing contract) calls `DeleteAccount`, and (3) any party re-creates the same `account_id` before the in-flight receipt/data finally arrives. Steps (1)-(3) require no special privilege — only normal transaction submission — but require precise timing/race conditions across shards/chunks that are not fully attacker-controlled (delivery order of cross-shard receipts is influenced by network/chunk scheduling, not directly by the sender). This makes it a genuine but timing-dependent bug rather than a trivially on-demand exploit; an attacker who controls both the "victim" contract logic and the account name reuse can increase the odds by deliberately delaying/expediting one branch of the receipt DAG (e.g., very cheap `foo()` vs. artificially long compute in a preceding step), but cannot fully guarantee arrival ordering deterministically without chunk/validator-level visibility.

### Recommendation
`remove_account` (or `action_delete_account`) should also purge any residual `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` entries for `account_id` before allowing deletion to complete — either by iterating and removing all such rows (mirroring the access-key/contract-data cleanup already done) or by rejecting `DeleteAccount` entirely while any such pending cross-receipt bookkeeping exists for the account (fail-closed, similar to the existing `locked() != 0` guard in `check_actor_permissions`, `runtime/runtime/src/actions.rs:770-775`).

### Proof of Concept
Integration/runtime-test-loop plan (extending `runtime/runtime/src/tests/apply.rs` style tests):
1. Set up two accounts `caller` and `victim`, with `victim` funded and holding a contract.
2. Submit a receipt sequence emulating `victim.foo().then(victim.bar())`: an `ActionReceipt` `bar` targeting `victim` with `input_data_ids = [D]` (built with `action_receipt_awaiting`, as in existing tests), delivered first so it becomes postponed (`PendingDataCount{victim,bar}=1`, `PostponedReceiptId{victim,D}=bar`, `PostponedReceipt{victim,bar}` stored).
3. Before delivering the matching `DataReceipt(D)`, deliver a `DeleteAccount` `ActionReceipt` for `victim` (owner-authorized, `locked()==0`) and confirm via `remove_account`/state inspection that `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` for `victim` are still present in the resulting trie (assert `get(...)` returns `Some`).
4. Deliver a `CreateAccount` action re-creating `victim` with new keys/contract.
5. Deliver `DataReceipt(D, receiver=victim)`.
6. Assert that `bar` executes immediately in this apply call (an `ExecutionOutcomeWithId` for `bar`'s receipt id is produced) against the *new* `victim` account (e.g., check its balance/storage changed per `bar`'s actions), and that `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` rows are now cleared — demonstrating the stale cross-incarnation execution rather than an `AccountDoesNotExist`/rejection outcome.
