## Analysis Result

### Title
Caller deposit permanently stuck in the eth-implicit Wallet Contract when `address_check_callback` rejects a lazy relayer's target - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR eth-implicit `WalletContract` tracks an external, non-owner caller's attached deposit via `CallerDeposit` so it can be refunded if the relayed cross-contract call fails [1](#0-0) . In one specific validation-failure branch of `address_check_callback`, the function returns an error response directly, without ever creating a refund promise for that tracked deposit, so the funds remain stuck on the wallet contract's balance forever.

### Finding Description
`rlp_execute` is a public, `#[payable]` entry point callable by any account (owner or external relayer) [2](#0-1) . When the call is made by an external, non-owner caller with attached deposit, `CallerDeposit::new` records `predecessor_account_id` and the deposit amount specifically so it can be refunded later — but explicitly *only* for non-self callers [3](#0-2) .

For an `EOABaseTokenTransfer` with an `address_check`, `inner_rlp_execute` schedules a call to the address registrar and forwards `caller_deposit` into `address_check_callback` [4](#0-3) .

In `address_check_callback`, if the registrar lookup reveals the `target` address actually corresponds to an existing named account (`maybe_account_id.is_some()`) — indicating a lazy/faulty relayer — the code branches on whether the signer is the wallet owner:
- If `env::signer_account_id() == current_account_id` (the wallet's own access key was used), a ban-relayer promise is created (this consumes/executes a promise chain, and `caller_deposit` is dropped without a refund action too, but that's the owner's own funds, not an "unprivileged caller" scenario).
- If the signer is a different account (an **external, non-owner caller** using no access key — reachable by anyone via `rlp_execute_from` semantics), the function immediately returns `PromiseOrValue::Value(ExecuteResponse{success:false, ...})` — **without creating any transfer/refund promise for `caller_deposit`** [5](#0-4) .

Because NEAR credits `#[payable]` attached deposits to the contract account's balance automatically at receipt-processing time (this happens before the WASM logic even runs), the deposit is already on the wallet contract's balance. The only way to return it to the external caller is for the contract logic to explicitly schedule a `Promise::new(...).transfer(...)`, exactly as is done in the sibling failure path of `rlp_execute_callback` [6](#0-5) . The `address_check_callback` early-return branch omits this step entirely, so the caller's deposit is permanently stranded in the wallet contract with no code path left to reclaim it (the value is dropped when the function returns, and no state/queue records it for later recovery).

This is the direct analog of the reported Tapioca bug class: an unprivileged caller supplies value expecting a defined outcome (execute-or-refund), but a specific validation branch inside the contract logic returns early on failure without executing the compensating refund transfer, permanently trapping the caller's funds in the contract.

### Impact Explanation
Any external account (not holding an access key on the wallet contract) that calls `rlp_execute` with an attached NEAR deposit and a base-token-transfer-style Ethereum transaction whose `to` address is later found by the registrar to correspond to an existing named NEAR account, will have its attached deposit permanently trapped in the wallet contract's balance — with no protocol-level or contract-level mechanism to reclaim it. This is a permanent freezing-of-funds bug for the calling account, reachable purely through the wallet contract's public `rlp_execute` transaction API, no privileged access required.

### Likelihood Explanation
Reaching the vulnerable branch requires: (1) the target of the RLP-encoded transaction is not yet known to be a plain named account and therefore triggers the address-registrar lookup path (`address_check: Some(_)`), (2) the address registrar happens to return `Some(account_id)` (i.e., a lazy relayer set an address-style target that was already registered under a named account), and (3) the caller is an external account distinct from the wallet owner, with attached deposit. This is a corner case dependent on relayer behavior/registrar state, but it is entirely reachable by an ordinary external account without any special privileges, and does not depend on malicious validators, network conditions, or protocol bugs — purely on contract-level logic in the eth-implicit wallet contract.

### Recommendation
In the `maybe_account_id.is_some() && signer != current_account_id` branch of `address_check_callback`, before returning the error `PromiseOrValue::Value`, check whether `caller_deposit` is `Some` and, if so, create a refund promise back to `caller_deposit.account_id` for `caller_deposit.yocto_near`, mirroring the pattern already used in `rlp_execute_callback`'s `PromiseResult::Failed` branch.

### Proof of Concept
1. External account `caller` calls `wallet_contract.rlp_execute(target, tx_bytes_b64)` with attached deposit `D`, where the encoded Ethereum transaction is an `EOABaseTokenTransfer` whose `to` field requires an address-registrar lookup (`address_check: Some(address)`).
2. `inner_rlp_execute` computes `caller_deposit = CallerDeposit::new(&context)` = `Some({account_id: caller, yocto_near: D})` since `caller != current_account_id` [7](#0-6) , then schedules the registrar lookup followed by `address_check_callback(target, action, caller_deposit)` [4](#0-3) .
3. The address registrar responds with `Some(some_named_account)` — i.e., the relayer's `target` matched an address that is actually already registered to a named account.
4. In `address_check_callback`, `maybe_account_id.is_some()` is true, and since `caller != current_account_id`, the code takes the `else` branch and returns `PromiseOrValue::Value(ExecuteResponse{success:false, error:Some("Invalid target...")})` directly [8](#0-7) .
5. No promise transferring `D` back to `caller` is ever created; `D` remains part of the wallet contract account's on-chain balance permanently, with no further contract logic capable of returning it to `caller`.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }
