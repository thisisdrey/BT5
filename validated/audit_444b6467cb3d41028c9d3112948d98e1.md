### Title
Uninitialized reward accounts can drain `RewardsDistributor` in the speed-activation block - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol#L217-L264))

### Summary
`RewardsDistributor` treats an account index of `0` as `INITIAL_INDEX` only when the token index is already greater than `INITIAL_INDEX`; during the same block in which rewards are enabled, the token index remains exactly `1e18`, so an existing token holder with no stored index accrues `balance * 1e18` reward tokens and can withdraw the distributor balance through the permissionless `claimRewards` path. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
When a governor enables a positive speed for a previously untracked deposit or debt token, `_updateTokenSpeed` initializes `tokenStates[token]` to `TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})`. [2](#0-1) 

In that same timestamp, `_calculateTokenIndex` cannot advance the index because `_deltaTimestamps` is zero, so `_updateTokenIndex` leaves `index == INITIAL_INDEX`. [4](#0-3) 

`_calculateTokenDelta` then reads `accountIndexOf[token][account] == 0`, but its fallback only applies if `_tokenIndex > INITIAL_INDEX`; at exactly `INITIAL_INDEX`, it calculates `_deltaIndex = 1e18` and `_tokensDelta = balanceOf(account).wadMul(1e18)`. [1](#0-0) 

Both `claimRewards` and the externally callable `updateBeforeMintOrBurn` reach this code without requiring the caller to be the rewarded account or a protocol contract. [5](#0-4) [6](#0-5) 

If the distributor holds at least `balanceOf(attacker)`, `_transferRewardIfEnoughTokens` clears the corrupted accrual and transfers that amount to the attacker; if the distributor holds less, the inflated accrual remains claimable as rewards arrive. [7](#0-6) 

### Impact Explanation
An attacker who already holds any positive balance of a newly reward-enabled `DepositToken` or `DebtToken` can claim up to their token balance in reward assets, even though zero reward time has elapsed. [1](#0-0) [7](#0-6) 

This is direct theft of unclaimed yield from the distributor because the payout is capped only by the reward-token balance, not by accrued emission. [7](#0-6) 

The same flaw can be repeated for other accounts that had balances before reward activation and still have `accountIndexOf == 0`, although payouts always go to each supplied account. [3](#0-2) [8](#0-7) 

### Likelihood Explanation
The exploit requires the attacker's account to have a token balance before the token is first assigned a positive reward speed, and the claim or update must execute in the same block timestamp as activation. [4](#0-3) [2](#0-1) 

This is a realistic activation-race condition because existing collateral suppliers necessarily have balances before rewards are enabled, `updateBeforeMintOrBurn` is public, and an attacker can monitor and back-run the governor's activation transaction. [9](#0-8) [10](#0-9) 

The account's own balance limits the immediate payout, but deposit-token balances can be substantial and the corrupted accrual is preserved until enough reward tokens exist. [11](#0-10) 

### Recommendation
Initialize `accountIndexOf[token][account]` to the current token index whenever `accountIndexOf == 0`, not only when the index has already exceeded `INITIAL_INDEX`. [1](#0-0) 

At minimum, change the fallback to treat a zero account index as `_tokenIndex` when `_tokenIndex >= INITIAL_INDEX`, so activation-time accounts do not accrue rewards for the initial index itself. [1](#0-0) 

Alternatively, initialize new reward markets at index `0` semantics consistently, or require every existing holder's index to be initialized before a positive `tokenSpeeds` value becomes active. [12](#0-11) [2](#0-1) 

### Proof of Concept
The following Hardhat test reproduces the issue using the repository's existing `RewardsDistributor` fixture and mocked reward-bearing token. [13](#0-12) [14](#0-13) 

```ts
// test/RewardsDistributor.initial-index.poC.ts
import {expect} from 'chai'
import {ethers} from 'hardhat'
import {parseEther} from '@ethersproject/units'
import {smock} from '@defi-wonderland/smock'
import {setStorageAt} from '@nomicfoundation/hardhat-network-helpers'

it('drains rewards in the same block as token-speed activation', async () => {
  const [deployer, attacker] = await ethers.getSigners()

  const ERC20 = await ethers.getContractFactory('ERC20Mock', deployer)
  const reward = await ERC20.deploy('Reward', 'RWD', 18)
  await reward.deployed()
  await reward.mint(deployer.address, parseEther('1000'))

  const poolRegistry = await smock.fake('PoolRegistry')
  const pool = await smock.fake('contracts/Pool.sol:Pool')
  const positionToken = await smock.fake('DepositToken')

  poolRegistry.operator.returns(ethers.constants.AddressZero)
  pool.governor.returns(deployer.address)
  pool.poolRegistry.returns(poolRegistry.address)
  pool.doesDepositTokenExist.returns(true)
  pool.doesDebtTokenExist.returns(false)

  const RD = await ethers.getContractFactory('RewardsDistributor', deployer)
  const distributor = await RD.deploy()
  await distributor.deployed()
  await setStorageAt(distributor.address, 0, 0)
  await distributor.initialize(pool.address, reward.address)

  // The attacker held one msdTOKEN before rewards were activated.
  positionToken.balanceOf.whenCalledWith(attacker.address).returns(parseEther('1'))
  positionToken.totalSupply.returns(parseEther('100'))
  pool.getRewardsDistributors.returns([distributor.address])

  await reward.transfer(distributor.address, parseEther('1000'))

  // Bundle activation and claim into one block/timestamp.
  await ethers.provider.send('evm_setAutomine', [false])
  await distributor.updateTokenSpeed(positionToken.address, parseEther('1'))
  await distributor['claimRewards(address,address[])'](
    attacker.address,
    [positionToken.address]
  )
  await ethers.provider.send('evm_mine', [])

  // Expected: zero seconds accrued, zero rewards.
  // Actual: balance * INITIAL_INDEX = 1 reward-token unit.
  expect(await reward.balanceOf(attacker.address)).to.eq(parseEther('1'))

  await ethers.provider.send('evm_setAutomine', [true])
})
```

The test demonstrates that the attacker starts with no `accountIndexOf`, activation creates a token index equal to `INITIAL_INDEX`, the same-timestamp update does not advance it, and `claimRewards` transfers the distributor's reward balance for the attacker's position balance.     function _calculateTokenIndex(
        TokenState memory _supplyState,
        IERC20 token_
    ) private view returns (uint224 _newIndex, uint32 _newTimestamp) {
        uint256 _speed = tokenSpeeds[token_];
        uint256 _deltaTimestamps = block.timestamp - uint256(_supplyState.timestamp);
        if (_deltaTimestamps > 0 && _speed > 0) {
            uint256 _totalSupply = token_.totalSupply();
            uint256 _tokensAccrued = _deltaTimestamps * _speed;
            uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
            _newIndex = (_supplyState.index + _ratio).toUint224();
            _newTimestamp = block.timestamp.toUint32();
        } else if (_deltaTimestamps > 0 && _supplyState.index > 0) {
            _newTimestamp = block.timestamp.toUint32();
        }
    }
