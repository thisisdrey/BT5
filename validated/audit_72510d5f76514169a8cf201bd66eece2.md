### Title
Permanent DoS of the eth-implicit Wallet Contract if a callback receipt fails without resetting `has_in_flight_tx` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the eth-implicit account contract) uses a boolean flag `has_in_flight_tx` to serialize execution of Ethereum-emulated transactions, requiring it to be reset to `false` inside one of its `#[private]` callback methods (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) once the in-flight promise chain resolves.

### Finding Description
`rlp_execute` sets `self.has_in_flight_tx = true` before returning a `Promise`, with an explicit invariant comment stating the flag "must be `true` when a mutable method of this contract returns a promise and `false` otherwise" [1](#0-0) . The only code paths that reset the flag back to `false` are inside the `#[private]` callback functions themselves (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) .

Per the runtime's execution model, when a `FunctionCall` action fails (e.g. due to a WASM trap, gas exhaustion, or a panic anywhere in the callback's own execution — not merely a failed *inner* promise, which is instead handled gracefully via `PromiseResult::Failed`), the whole receipt fails and **all state changes it made are rolled back** by `TrieUpdate`: "When a receipt fails, its state changes are rolled back using `TrieUpdate`" [6](#0-5) . If the callback receipt itself traps or runs out of its statically-allocated gas (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` — all only 5–15 Tgas, see constants at [7](#0-6) ) before it reaches the line resetting `has_in_flight_tx`, that reset is rolled back along with everything else.

Unlike a normal cross-contract failure (which is delivered as `PromiseResult::Failed` and handled inside the callback, still allowing the flag reset to commit), a hard failure of the callback receipt itself is the analog of the reported "entropy callback not invoked" bug class: the operation that is solely responsible for clearing the "in progress" latch never completes. Once this happens, every subsequent call to `rlp_execute` is permanently rejected with `"transaction already in progress, please try again later"` [8](#0-7) , because there is no owner, no timeout, and no alternate method to reset the flag — this contract has no privileged owner/admin at all (unlike the `ApiologyAuctionHouse`, which at least allows the owner to pause/unpause).

### Impact Explanation
If reachable, this is a permanent denial of service ("bricking") of the user's eth-implicit wallet account: no further Ethereum-emulated transaction can ever be executed through this contract again, since `has_in_flight_tx` is latched `true` forever with no reset mechanism. This effectively freezes funds/functionality controlled by that account under RLP execution.

### Likelihood Explanation
Low/uncertain. All the observable execution paths in `rlp_execute_callback`, `address_check_callback`, and `nep_141_storage_balance_callback` handle inner-promise failure via matched `PromiseResult::Failed`/`Successful` branches without panicking, and no `unwrap`/`expect`/indexing panics were found in the reviewed portions of these functions. The only plausible trigger is gas exhaustion of the callback's own statically-allocated gas budget (a fixed 5–15 Tgas) during unusually heavy computation (e.g., large ERC-20 transfer argument handling or an unexpectedly large registrar response), which was not conclusively proven from static code review alone — a fuller trace of gas costs for each code path and any protocol-level guarantees around callback gas allocation would be needed to determine actual exploitability. This should be validated with gas-profiling tests before treating it as a confirmed high-likelihood issue.

### Recommendation
Move the `has_in_flight_tx = false` reset out of the individually-computed callback bodies and into a step that is guaranteed to execute even when the callback panics or runs out of gas — for example, by having a dedicated, minimal-cost "always-succeeds" cleanup callback appended at the end of every promise chain (so it runs independently of the outcome of the preceding step), or by adding a protocol-level guarantee/timeout mechanism (analogous to Yield/Resume's timeout) that can force-reset a stuck in-flight flag after a bounded number of blocks if no callback has completed.

### Proof of Concept
Not independently reproduced; the reasoning is based on static analysis of `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs` combined with the documented rollback-on-failure execution semantics in `runtime/runtime/AGENTS.md`. A concrete PoC would require constructing an RLP transaction whose callback path (e.g. `nep_141_storage_balance_callback` chained through a `storage_deposit` + `ft_transfer` sequence) exceeds its statically allocated gas budget before executing the `self.has_in_flight_tx = false` write, then observing that all subsequent `rlp_execute` calls are permanently rejected.
