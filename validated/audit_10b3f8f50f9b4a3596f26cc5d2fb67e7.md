### Title
`add_regular_key` reseeds an access key's nonce using `(block_height-1)*ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, which can be lower than a nonce already consumed by the same public key earlier in the same block, enabling replay of an already-executed transaction - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`initial_nonce_value` seeds a (re)created access key's nonce floor from the block height at which the `AddKey` action is *applied*, not from the highest nonce actually consumed by that key. When `DeleteKey`+`AddKey` for the same public key are processed as local receipts in the same block as a preceding transaction that used a nonce close to that block's upper bound, the new floor `(H-1)*1e6` can be strictly lower than the already-consumed nonce (up to `H*1e6-1`), letting the exact same previously-signed transaction be re-submitted and re-executed.

### Finding Description
`initial_nonce_value` computes the new key's nonce as: [1](#0-0) 
which is used by `add_regular_key` when an `AddKeyAction` is applied: [2](#0-1) 

`verify_nonce` enforces that a transaction's nonce must be strictly less than `block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` for the block in which it is verified: [3](#0-2) 

This means a transaction using the *original* key incarnation can legally consume any nonce up to `H*MULTIPLIER - 1` while being verified in block `H`. The comment on `initial_nonce_value` explains its purpose: guarantee that a newly (re)created key's nonce floor dominates every nonce that could have been used by an earlier incarnation, to prevent tx-hash/nonce collision and replay (referencing near/nearcore#3779). This invariant only holds if the `AddKeyAction` is applied at least one full block height after the block in which the old incarnation's nonce was consumed, because then `(block_height-1)*MULTIPLIER >= H*MULTIPLIER > H*MULTIPLIER - 1`.

However, `block_height` in `initial_nonce_value` is the height of the block that *applies* the `AddKeyAction`, not the height at which the previously-consumed nonce was verified. Transactions whose `signer_id == receiver_id` (e.g., a self-directed `DeleteKey`+`AddKey` transaction, or two separate self-directed transactions) become "local receipts" and are executed in the *same block* as the transaction that generated them: [4](#0-3) [5](#0-4) 

So if, within the same block `H`:
- Tx1 (nonce `H*1e6-2`) transfers funds to `victim.near`, consuming nonce `H*1e6-2` on key `pk`.
- Tx2 (nonce `H*1e6-1`), same signer/receiver, contains `[DeleteKey(pk), AddKey(pk, FullAccess)]`, and is converted into a local receipt applied in the *same block* `H` (assuming chunk gas budget allows, which it trivially does for these cheap actions),

then `action_add_key` runs with `apply_state.block_height == H`, so the new access key's nonce is seeded to `(H-1)*1e6`, which is strictly less than the already-consumed `H*1e6-2` (since the multiplier is `1e6`, far larger than the 2-nonce gap). The freshly-created key's nonce floor therefore does **not** dominate the nonce already consumed by Tx1 in the same block.

Nothing else deduplicates by transaction hash at the nonce-check layer — `verify_nonce`/`verify_and_charge_tx_ephemeral` only compares `tx_nonce` against the current `access_key.nonce` (or `pending.max_nonce`), not against a set of previously-used nonces: [6](#0-5) 
Consequently, the exact same signed transaction Tx1 (same bytes, same signature, nonce `H*1e6-2`) can be resubmitted to an RPC node after Tx2 executes, and it will pass the nonce check again (`H*1e6-2 > (H-1)*1e6`), as long as its referenced block hash is still within `transaction_validity_period` (which, being on the order of tens of thousands of blocks, trivially covers a same-block or next-block replay window). The transaction is then re-verified, re-converted to a receipt, and re-executed, producing a second, independent execution outcome for what is supposed to be a single, already-applied transaction.

### Impact Explanation
This breaks the "transactions execute at most once" invariant. A signed transaction (e.g., a `Transfer` action) can be legitimately re-applied, causing the signer's account to be debited (and the receiver credited) a second time from a single signature/nonce, i.e., double-spend/replay of a previously executed transaction. This matches the "double-spend/replay" impact category in the prompt's rules.

Note: the account whose key is deleted/re-added and whose transaction gets replayed is the *same* account that authorizes both the original transaction and the `DeleteKey`/`AddKey` transaction (only the holder of a `FullAccess` key can delete/add keys on that account). So the direct victim of the double-debit is the transacting account itself (or, in a meta-transaction/relayer flow, the signer of the `DelegateAction`, whose relayer could intentionally engineer this sequence and then rebroadcast the stale signed payload to force a second debit against the signer's account and credit a receiver of the attacker's choosing).

### Likelihood Explanation
Preconditions are modest and within the described "unprivileged" threat model: a funded account with one `FullAccess` key, and the ability to construct/submit its own transactions (nonce values, block-hash references) at will. The attacker needs to:
1. Get a transaction accepted with a nonce close to the current block's upper bound (`height*1e6 - k` for small `k`) — feasible since nonces are attacker-chosen and only constrained by `verify_nonce`'s strict/monotonic and upper-bound checks.
2. Get a same-block local receipt for `DeleteKey`+`AddKey` on the same public key — feasible via a single self-directed transaction (signer == receiver) containing both actions in one action list, which the runtime documents as normally applying in the same block/chunk.
3. Resubmit the original signed bytes within the (very generous) `transaction_validity_period`.

This is entirely achievable by an ordinary account holder using standard RPC submission with no validator/node privileges, though it requires precise nonce engineering and relies on chunk-application timing (gas budget, congestion) to actually land the `DeleteKey`/`AddKey` receipt in the same block as the target transaction, which is not fully attacker-guaranteed but is a normal, reproducible outcome under typical network conditions and can be retried across blocks until it lands.

### Recommendation
Seed the new key's nonce floor from a value that provably dominates any nonce ever consumed by the account for that height's window — e.g., use `apply_state.block_height` (not `block_height - 1`) as the multiplier base so that the floor equals the current block's own nonce upper bound, or seed the new nonce from the deleted key's stored nonce (`max(existing nonce range for this height, old_key.nonce)`) at the time of deletion, ensuring the recreated key can never accept a nonce that was valid for the same block. At minimum, `add_regular_key`/`add_gas_key` should never derive a floor lower than the floor already available in the same block to the key being replaced.

### Proof of Concept
Unit/integration test plan (runtime/runtime/src/access_keys.rs and/or a runtime-apply/test-loop integration test):
1. Create an account with one `FullAccess` key `pk` and sufficient balance.
2. In block `H`, submit Tx1 = `Transfer` to `victim.near` with `nonce = H*ACCESS_KEY_NONCE_RANGE_MULTIPLIER - 2`; assert it executes and debits the account / credits `victim.near`.
3. In the same block `H` (same chunk), submit Tx2 = self-directed `[DeleteKey(pk), AddKey(pk, FullAccess)]` with `nonce = H*ACCESS_KEY_NONCE_RANGE_MULTIPLIER - 1`, structured/timed so its resulting local receipt is applied with `apply_state.block_height == H`.
4. Read back the access key for `pk` and assert `access_key.nonce == (H-1)*ACCESS_KEY_NONCE_RANGE_MULTIPLIER` via `initial_nonce_value`, then assert this is `<` the nonce consumed by Tx1 in step 2 (i.e., seed does *not* strictly dominate the max previously consumed nonce) — this is the core invariant-violation assertion.
5. Resubmit the identical signed Tx1 bytes as a new transaction; assert `verify_nonce`/`process_tx` accepts it (nonce check passes) and it is executed a second time, producing a second outcome and a second debit/credit — demonstrating double execution.
6. As a regression/control case, repeat with the `AddKey` receipt applied in block `H+1` instead of `H`, and assert the seed `H*ACCESS_KEY_NONCE_RANGE_MULTIPLIER` correctly exceeds the max nonce consumed in block `H`, and that replay of Tx1 is rejected — showing the flaw is specific to the same-block (zero-height-delta) reseed case.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
