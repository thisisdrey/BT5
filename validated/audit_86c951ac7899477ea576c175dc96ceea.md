### Title
TRX/TRC10 Exchange pool ratio math allows disproportionate token extraction when one side of the pool is drained to a near-zero balance - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `ExchangeWithdrawActuator.java`, `ExchangeTransactionActuator.java`, `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The external report describes a class of bug where a pricing/share-mint formula divides by a pool-value denominator that is only guarded against being exactly zero, not against being *near* zero, allowing the ratio to blow up and mint disproportionate output right before it collapses back to baseline at the exact-zero boundary. The TRON on-chain bancor-style TRX/TRC10 `Exchange` feature (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract`) contains the same structural pattern: every ratio calculation is guarded only by `firstTokenBalance == 0 || secondTokenBalance == 0`, never by a minimum-balance floor, so a pool balance can be driven down to `1` (the smallest non-zero long) and the subsequent multiply/divide ratio becomes arbitrarily large.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` only rejects withdrawal when a side of the pool is exactly zero: [1](#0-0) 
and the corresponding `execute()` computes the counter-quantity with plain `BigInteger` multiplication/division against the (attacker-controllable) remaining balance: [2](#0-1) 

Because there is no floor on how low `firstTokenBalance`/`secondTokenBalance` may go (only `!= 0` is enforced, unlike the report's remediation which enforces a hard $10-equivalent minimum on the analogous `totalValueInUSD`), the exchange creator (the only account permitted to call `ExchangeWithdraw`, per the creator check in `ExchangeWithdrawActuator`) can withdraw down to a residual balance of `1` unit on one side. Any subsequent `ExchangeInjectContract` call then computes: [3](#0-2) 
where `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance`. With `firstTokenBalance == 1`, any nonzero `tokenQuant` injected on the depleted side multiplies `secondTokenBalance` by an essentially unbounded factor (bounded only by `getExchangeBalanceLimit()`), letting the injector receive (or be required to inject) a wildly disproportionate counter-token amount compared to genuine market value — the same "denominator approaches zero → output ratio blows up" defect described in the report for `calcLpOut`.

The same denominator-collapse risk affects the bancor-curve trade path: `ExchangeTransactionActuator` also only checks `firstTokenBalance == 0 || secondTokenBalance == 0` before calling `exchangeCapsule.transaction(...)`, which feeds the (possibly near-1) balance into `ExchangeProcessor`/`SafeExchangeProcessor`'s floating-point/BigDecimal `pow` curve: [4](#0-3) 
An extremely small balance denominator drives `quant/newBalance` toward large values, causing the `pow`-based bancor relay math to lose precision or produce extreme outputs, mirroring the report's "inflated" vs. "reset-to-baseline" inconsistency around the zero boundary.

### Impact Explanation
An exchange creator/pool owner can unilaterally engineer a near-zero-balance state on one side of a public TRX↔TRC10 exchange pool via a normal, unprivileged `ExchangeWithdrawContract` transaction (only the "no enough balance"/"balance == 0" checks apply, no minimum-liquidity floor). Once in that state, any counterparty (or the same attacker acting as counterparty) calling `ExchangeInjectContract` or `ExchangeTransactionContract` is exposed to grossly distorted exchange rates, enabling theft of the counter-token/TRX from the pool or from unsuspecting traders — a concrete unauthorized-account-operation / theft-of-funds scenario reachable purely through signed transactions against `Wallet`'s exchange RPCs.

### Likelihood Explanation
The precondition (draining one side of a pool to a minimal non-zero balance) requires only that the attacker be the exchange's creator, which is achievable by anyone via `ExchangeCreateContract` followed by their own `ExchangeWithdrawContract` calls — no special chain privilege, SR/witness role, or third-party interaction is needed. The only friction is `getExchangeBalanceLimit()` bounding the maximum balance and normal transaction fees, neither of which prevents draining a side down to `1`.

### Recommendation
Mirror the report's remediation: enforce a minimum residual balance (not just non-zero) on both sides of an `Exchange` in `ExchangeWithdrawActuator.doValidate()`, and add the same floor check to `ExchangeInjectActuator`/`ExchangeTransactionActuator` before computing ratios, so that `firstTokenBalance`/`secondTokenBalance` can never be reduced below a safe minimum that keeps the bancor/ratio math numerically stable.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` to create a TRX/TRC10 exchange with `firstTokenBalance = X`, `secondTokenBalance = Y` (see `ExchangeCreateActuator.doValidate()` at [5](#0-4) , only requiring `> 0`).
2. Attacker (as creator) repeatedly calls `ExchangeWithdrawContract` withdrawing `firstTokenBalance` down to `1`, which passes validation since only `firstTokenBalance == 0` is rejected (`ExchangeWithdrawActuator.java` lines 209-212).
3. Attacker (or a lured counterparty) calls `ExchangeInjectContract` supplying a small `tokenQuant` of the depleted (first) token; `anotherTokenQuant = secondTokenBalance * tokenQuant / 1`, extracting/consuming a disproportionate amount of the second token relative to genuine value, analogous to the reported `calcLpOut` inflation near `getEffectivePoolValue == 0`.
