Audit Report

## Title
Relayer reward settles unconditionally in `process_delivery_receipt`, ignoring the `success` field of the `DeliveryReceipt` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt::try_from` decodes the `success` field straight from the Ethereum `InboundMessageDispatched` event log, but `Pallet::process_delivery_receipt` never inspects it before crediting the relayer's reward and removing the `PendingOrder`. This allows a relayer to be paid the full order fee even when the underlying message dispatch on Ethereum failed.

## Finding Description
The `DeliveryReceipt` struct carries an explicit `success: bool` field decoded from the `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` event log: [1](#0-0) 

`process_delivery_receipt` only validates `receipt.gateway` against `T::GatewayAddress` and looks up the `PendingOrders` entry by `receipt.nonce`. It then unconditionally pays `order.fee` via `T::RewardPayment::register_reward` and removes the order — `receipt.success` is never read: [2](#0-1) 

`PendingOrder` itself stores only `nonce`, `fee`, and `block_number` — set when the message is enqueued in `do_process_message` — so the binding between the receipt and the original message is the bare `nonce`, with no cross-check against `topic`/content: [3](#0-2) 

The public extrinsic `submit_delivery_receipt` verifies the event log/proof via `T::Verifier::verify` and decodes the `DeliveryReceipt`, then hands off directly to `process_delivery_receipt` without any success check: [4](#0-3) 

## Impact Explanation
This is a public underpriced/incorrect-settlement issue: the reward-payout state advances (fee paid, `PendingOrders` entry removed) without verifying that the dispatch on Ethereum actually succeeded, even though the receipt data explicitly carries that outcome. This violates the required invariant that bridge markers/payout state must only advance after execution and settlement succeed, and results in relayer rewards being paid for deliveries that did not achieve their intended cross-chain effect — draining the reward pool without the corresponding service.

## Likelihood Explanation
Any signed relayer calling the permissionless `submit_delivery_receipt` extrinsic with a legitimately obtained (not forged) proof of a real `InboundMessageDispatched(success=false)` event will trigger this path — no forgery, collusion, or privileged action is required, only normal relayer operation combined with a message dispatch that reverted or failed on Ethereum for any reason (e.g., insufficient gas for the inner command).

## Recommendation
In `process_delivery_receipt`, explicitly check `receipt.success` before calling `T::RewardPayment::register_reward`. On `success == false`, either withhold/reduce the reward or otherwise avoid paying the full delivery fee as if execution succeeded, rather than settling and removing the `PendingOrder` unconditionally. Additionally consider binding the receipt to the original message content (e.g., `topic`) rather than relying on `nonce` alone.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrders[nonce] = { fee, block_number }` (lib.rs L426-440).
2. The relayer submits/observes the corresponding dispatch on Ethereum's Gateway such that the inner command execution fails while the outer transaction still logs `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer obtains a valid proof of this real event and calls `submit_delivery_receipt` (lib.rs L298-317).
4. `process_delivery_receipt` decodes the receipt, validates `gateway` and looks up `PendingOrders(nonce)`, then pays `order.fee` and removes the order without ever consulting `receipt.success` (lib.rs L445-480).
5. Result: the relayer is fully rewarded for a message whose dispatch on Ethereum failed, confirming the missing success-field validation.

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
