### Title
Unhandled `ArrayIndexOutOfBoundsException` in `ValidateMultiSign` precompile from attacker-controlled offset word - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract (TVM address `0x0a`, reachable via a plain smart-contract call to `validatemultisign(...)`) parses an attacker-supplied ABI offset word (`words[3]`) and uses it directly to index into the `words` array without bounds checking, and without the array-index derefs being wrapped in a catch-all. This mirrors the `base64url` root cause of trusting an attacker-controlled length/offset value to index into a buffer without validating it against the buffer's actual bounds, producing an out-of-bounds read (here, an `ArrayIndexOutOfBoundsException` on a Java array rather than a native buffer over-read, but the same "unvalidated attacker length/offset drives array access" bug class).

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute`:
```java
DataWord[] words = DataWord.parseArray(rawData);
...
if (VMConfig.allowTvmSelfdestructRestriction()) {
  int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
  ...
}
byte[][] signatures = VMConfig.allowTvmSelfdestructRestriction() ?
    extractSigArray(words, words[3].intValueSafe() / WORD_SIZE, rawData) :
    extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData);
``` [1](#0-0) 

`words[3]` is fully attacker-controlled (it comes straight from the calldata passed to the precompile via a `CALL` opcode). `intValueSafe()` clamps to `Integer.MAX_VALUE`/`MIN_VALUE` on overflow but does **not** validate that the resulting index is within `words.length`. The expression `words[words[3].intValueSafe() / WORD_SIZE]` therefore directly indexes the `words` array with an attacker-chosen value that can trivially exceed `words.length - 1`, or even be negative after division truncation edge cases, throwing `ArrayIndexOutOfBoundsException`.

Unlike `BatchValidateSign.execute`, which wraps its entire `doExecute` body in a `try { } catch (Throwable t)` block:
```java
public Pair<Boolean, byte[]> execute(byte[] data) {
  try {
    return doExecute(data);
  } catch (Throwable t) {
    ...
    return Pair.of(true, new byte[WORD_SIZE]);
  }
}
``` [2](#0-1) 

`ValidateMultiSign.execute` has **no equivalent top-level try/catch** around the offset dereference and the `extractSigArray`/`extractBytesArray` calls (lines 1057–1074) — the only `try/catch` in the method wraps the later permission-weight logic (starting at line ~1082), which is reached only after `signatures` has already been computed:
```java

    extractSigArray(words, words[3].intValueSafe() / WORD_SIZE, rawData) :
    extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData);

if (signatures.length == 0 || signatures.length > MAX_SIZE) {
  return Pair.of(true, DATA_FALSE);
}

AccountCapsule account = this.getDeposit().getAccount(address);
if (account != null) {
  try {
    ...
  } catch (Throwable t) { ... }
}
``` [3](#0-2) 

Additionally, `isValidAbiEncoding` — added as part of the TIP-854 hardening effort visible in the test suite (`BatchValidateSignContractTest.testTip854RejectsMalformedCalldata`, `OperationsTest.testTip854OuterFrameContainment`) — only checks that the total calldata length is 32-byte aligned and matches the header/item word arithmetic; it does **not** validate embedded offset words like `words[3]` against `words.length`: [4](#0-3) 

So a caller can supply calldata that is "shape-valid" per `isValidAbiEncoding` (correct total length for a given header/item count) yet still contains an out-of-range offset value in `words[3]`, since `isValidAbiEncoding` never inspects the *content* of any specific word.

### Impact Explanation
An `ArrayIndexOutOfBoundsException` thrown directly out of `PrecompiledContract.execute()` (not `RuntimeException` subclasses that VM opcode handling is designed to catch as VM "Exception" types) risks propagating up through the CALL opcode handling into `Program`/transaction execution. If this exception is not caught by a generic `Throwable`/`Exception` handler somewhere higher in the transaction-processing pipeline (e.g., `Runtime`, `TransactionTrace`, or `Manager.pushTransaction`), it could crash block application for that node, or — if some nodes handle uncaught runtime exceptions differently than others (e.g., different JVM/config causing divergent OOM/behavior) — contribute to non-determinism between nodes. At minimum this is a reachable, unauthenticated crash/DoS vector triggerable by any account that can send a smart-contract transaction invoking `validatemultisign(...)` with a single crafted `bytes32,uint256,bytes,bytes[]` calldata blob — no special privileges, stake, or witness/SR status required.

### Likelihood Explanation
High reachability: `ValidateMultiSign` is a standard TVM precompile enabled by `VMConfig.allowTvmSolidity059()`, callable by any contract via a `CALL`/`STATICCALL` to address `0x...0a` with attacker-fully-controlled calldata (`rawData`). Crafting the `words[3]` offset to exceed `words.length` requires no cryptographic material and is deterministic and repeatable. The main uncertainty is whether an outer layer of the VM/transaction execution pipeline (not fully inspected here due to tool/iteration limits) already wraps precompile `execute()` calls in a catch-all `Throwable` handler at the `Program`/opcode level, which would downgrade this from a crash to a caught VM exception (e.g., converted into a revert). This could not be conclusively verified within the available search budget — `Program.callToPrecompiledAddress` and its exception handling were not fully retrieved before the iteration budget was exhausted.

### Recommendation
- In `ValidateMultiSign.execute`, validate that `words[3].intValueSafe() / WORD_SIZE` (and any other attacker-controlled offset derived from calldata) is within `[0, words.length - 1]` before using it to index `words`, mirroring the bounds check already present in `extractBytesArray`/`extractSigArray` for the `offset` parameter (`if (offset > words.length - 1) return new byte[0][];`).
- Wrap the entire body of `ValidateMultiSign.execute` in a `try { } catch (Throwable t) { return Pair.of(true, DATA_FALSE); }`, consistent with `BatchValidateSign.execute`, so any unexpected indexing/arithmetic exception degrades gracefully to a rejected/false result rather than propagating an uncaught exception.
- Extend `isValidAbiEncoding` (or add a companion check) to validate that all embedded offset/length words used as array indices are within the bounds of the parsed `words` array before they are dereferenced.

### Proof of Concept
Send a transaction that calls the `ValidateMultiSign` precompile (address `0x...0a`) with calldata shaped as `bytes32 address, uint256 permissionId, bytes data, bytes[] signatures` but with the offset placeholder for `signatures` (`words[3]`) set to a very large value, e.g.:
```
words[0] = <any 32-byte address>
words[1] = <any permissionId>
words[2] = <offset for `data`, valid>
words[3] = 0xFFFFFFFF   // attacker-controlled "offset" for signatures array
```
With `VMConfig.allowTvmSelfdestructRestriction()` enabled, execution reaches:
```java
int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
``` [5](#0-4) 
Since `words[3].intValueSafe() / WORD_SIZE` (≈134M) vastly exceeds `words.length` (a handful of words for this minimal calldata), this throws `ArrayIndexOutOfBoundsException`, which is not caught anywhere within `ValidateMultiSign.execute`, unlike its sibling `BatchValidateSign`. (Note: full verification of downstream exception handling in `Program`/`Runtime` for precompile calls could not be completed within the tool budget; this should be confirmed before relying on this PoC to demonstrate a node crash versus a caught VM revert.)
