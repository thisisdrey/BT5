## #Vulnerability found

### Title
Missing sender-identity binding in relay `CreateRelayRequest` handling allows relay state poisoning for arbitrary victim VPN addresses - (File: `relay_manager.go`)

### Summary
`relayManager.handleCreateRelayRequest` in [1](#0-0)  trusts the attacker-supplied `RelayFromAddr` field of an incoming `NebulaControl` message as the identity on whose behalf the relay is being requested, without ever checking that it matches the actual, certificate-verified identity of the sending tunnel (`h.vpnAddrs`). This is directly analogous to the reported `Identity.sol` bug, where `_setOwner` accepted a caller-supplied identity change without checking that the caller was actually the current owner — here, any already-authenticated (but otherwise unrelated) peer can assert an arbitrary "owner" identity (`from`) for a piece of shared relay state instead of only being able to act on its own identity.

### Finding Description
When a `Control` packet is received on an already-established, authenticated tunnel, `f.relayManager.HandleControlMsg(hostinfo, out, f)` is invoked with `hostinfo` being the caller's real, cert-verified `HostInfo` [2](#0-1) . For `NebulaControl_CreateRelayRequest` messages, `handleCreateRelayRequest` extracts `from := protoAddrToNetAddr(m.RelayFromAddr)` purely from the message body [3](#0-2) . The only check performed is that `from` is not one of the local node's own addresses [4](#0-3) ; there is no check that `from == h.vpnAddrs[0]` (i.e. that the claimed "relay-from" identity actually belongs to the certificate-authenticated peer `h` that sent the packet).

When the local node is the relay target, this attacker-controlled `from` is used directly to install new relay state on the sender's real, authenticated `HostInfo`:
```go
_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
``` [5](#0-4) 

`AddRelay` inserts a `Relay{PeerAddr: vpnIp, ...}` entry keyed by the caller-supplied `vpnIp` (here `from`) into `h.relayState`, with no verification that `from` legitimately corresponds to `h` [6](#0-5) . The legitimate flow (`StartRelays`) always sets `RelayFromAddr` to the sender's own `f.myVpnAddrs[0]` [7](#0-6) , but nothing on the receiving side enforces this invariant, so a malicious peer holding any valid certificate can substitute an arbitrary victim VPN address for `from`.

### Impact Explanation
Because the relay-from identity is never bound to the actual authenticated sender, an attacker with a valid (but non-privileged) certificate can register itself as the terminal relay path "on behalf of" any victim VPN address of their choosing, poisoning the target's `relayState` map (keyed by the attacker-chosen `from`). This can disrupt or hijack legitimate relay establishment for that victim address (e.g. causing "Existing relay mismatch" rejections when the real victim later attempts to establish the same relay path, per the state-machine checks in `handleCreateRelayRequest` [8](#0-7) ), resulting in remote relay/routing state poisoning and denial of relay service for arbitrary third-party VPN identities that the attacker does not control.

### Likelihood Explanation
Exploitation only requires the attacker to already have an established, authenticated Nebula tunnel to the victim relay/target node (i.e., possession of any valid certificate signed by an in-scope CA, not a compromised/valid-owner certificate for the impersonated identity). No cooperation from the impersonated victim is required, and the attacker fully controls the `RelayFromAddr`/`OldRelayFromAddr` field of the `Control` packet, making this reachable by any peer able to complete a handshake.

### Recommendation
In `handleCreateRelayRequest`, validate that the message's claimed `from` address matches the authenticated sender's own identity (`h.vpnAddrs`) before creating or updating any relay state on `h`. Reject (log and drop) any `CreateRelayRequest` where `from` does not correspond to a vpn address actually owned by `h`, mirroring the existing self-check at [4](#0-3) .

### Proof of Concept
1. Attacker `E` establishes a normal, valid Nebula tunnel to relay/target node `M` (any signed cert suffices; no special group/role required).
2. Over that authenticated tunnel, `E` sends a `Control` packet containing a `NebulaControl_CreateRelayRequest` with `RelayFromAddr` set to victim `V`'s VPN address (a node `E` has no relationship with) and `RelayToAddr` set to `M`'s own VPN address.
3. `M`'s `handleCreateRelayRequest` (`relay_manager.go:426`) sees `target == M` and, finding no existing relay for `from=V` on `h` (E's HostInfo), calls `AddRelay(rm.l, h, f.hostMap, V, ...)`, establishing relay state that claims `E` is relaying traffic for `V`, all without ever verifying `V`'s participation or matching `E`'s real certificate identity.
4. `M` responds with `CreateRelayResponse`, completing an "Established" relay entry keyed by `V` on `E`'s hostinfo, poisoning `M`'s view of relay availability for `V` and potentially blocking or corrupting a legitimate future relay setup initiated by the real `V`.

	defer hm.Unlock()
	for range 32 {
		index, err := generateIndex(l)
		if err != nil {
			return 0, err
		}

		_, inRelays := hm.Relays[index]
		if !inRelays {
			// Avoid standing up a relay that can't be used since only the primary hostinfo
			// will be pointed to by the relay logic
			//TODO: if there was an existing primary and it had relay state, should we merge?

				// The tunnel was torn down after the caller grabbed relayHostInfo. A relay standing
				// on an unlinked hostinfo would never carry traffic, and its Relays entry could
				// never be reclaimed since the delete-time cleanup has already run.
				return 0, errors.New("relay hostinfo is no longer in the hostmap")

				State:      state,

			}

				newRelay.RemoteIndex = *remoteIdx
			}
			relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)

			return index, nil
		}
