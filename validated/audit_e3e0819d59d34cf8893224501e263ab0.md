### Title
Quarantine ownership check bypass allows cross-repository object directory access - ([File: internal/git/localrepo/paths.go])

### Summary
The bug-class hint describes a validation routine whose logic block does not precisely implement the safety property it claims to enforce (a component-based boundary check with a mismatched condition, letting an unintended case fall into the "trusted" branch). `Repo.ObjectDirectoryPath` in `internal/git/localrepo/paths.go` has the same class of flaw: it decides whether a `GitObjectDirectory` value can skip the "does this quarantine directory actually belong to this repository" ownership check purely by inspecting the last one or two path components (`baseDir`/`parentDir`), rather than verifying the directory is the one this repository's own quarantine machinery created.

### Finding Description
`ObjectDirectoryPath` first ensures the object directory is somewhere inside the storage root: [1](#0-0) 

It then tries to decide whether this is a transaction-created quarantine directory (which is trusted implicitly) versus a normal in-repo or git-receive-pack quarantine path (which must be verified to belong to the specific repository via `QuarantineDirectoryPrefix`): [2](#0-1) 

The `isTransactionQuarantineDir` predicate only looks at the final one or two path segments of the (already storage-root-validated, but otherwise attacker/Rails-influenced) `GitObjectDirectory` value:

```go
isTransactionQuarantineDir := (baseDir == "quarantine") || ((parentDir == "quarantine") && strings.HasPrefix(baseDir, "tmp_objdir"))
```

This is structurally the same defect as the reported UniswapV3 bug: the code intends "this is *the* transaction-managed quarantine directory for *this* request/repository," but the actual check only verifies a *name pattern* on the last path component(s), not that the directory is tied to this repository or even to this transaction. Any relative object-directory value whose basename is literally `quarantine` (or whose parent is `quarantine` and whose basename starts with `tmp_objdir`) — anywhere under the storage root — satisfies the predicate and skips the entire ownership-verification block that follows: [3](#0-2) 

That skipped block is precisely the code that protects against cross-repository quarantine confusion: it checks `storage.ValidateRelativePath(repoPath, objectDirectoryPath)` (is it actually inside *this* repo?), and if not, falls back to checking the path is prefixed by `QuarantineDirectoryPrefix(repo)` — a SHA1-based prefix unique to *this* repository's relative path — inside the storage's temp directory. Existing tests already document that Gitaly relies on this ownership check to reject a repository whose `GitObjectDirectory` was swapped with a *different* repository's quarantine directory: [4](#0-3) 

But that protective test only covers the case where both quarantine paths are `tmp_objdir-incoming-*`-style git-receive-pack directories (matched by the second, correctly-scoped disjunct). It does not cover a value whose basename is exactly `quarantine` (matching the *first*, unconditional disjunct), which bypasses the ownership check regardless of which repository (or transaction) actually created that directory, as long as it resolves inside the storage root.

`GitObjectDirectory`/`GitAlternateObjectDirectories` are populated on the `Repository` message as part of the object-quarantine handoff between Gitaly's `pre-receive` hook and GitLab Rails' `/internal/allowed` endpoint, and are looped back into subsequent Gitaly RPCs performed during access checks for that same push: [5](#0-4) 

Because this value is round-tripped from client-observable push processing and re-supplied as an untrusted field on later RPC calls (guarded at the middleware layer only by requiring the request to be a non-mutating "accessor" call, not by verifying quarantine ownership itself): [6](#0-5) 

an actor who can influence this field (e.g. via a manipulated request replayed through the access-check path, or a compromised/duplicated pre-receive quarantine name collision) can point it at a `quarantine`-named directory belonging to a concurrent push against a *different* repository in the same storage, and `ObjectDirectoryPath` will resolve and serve it without the intended ownership verification, exposing objects (potentially including yet-unauthorized/rejected pushed content) from another repository's in-flight quarantine.

### Impact Explanation
This breaks the repository object-isolation guarantee enforced by quarantine ownership checks: it allows one repository/request context to read Git objects living in another repository's (or an unrelated) quarantine directory within the same storage, corresponding to the "cross-repository object access" acceptance criterion. Given that quarantine directories can transiently contain objects from a push before it has passed the `pre-receive` "allowed" check, this is an information-disclosure vector into an unauthorized push's not-yet-committed content.

### Likelihood Explanation
The `baseDir == "quarantine"` disjunct is unconditional and requires no ownership-token match — only a path whose last component is literally `quarantine` after `filepath.Join` cleaning, which is trivial to construct and is exactly the value chosen for `quarantine.New`'s working directories (created inside the storage's temp directory). Reaching this code, however, requires being able to set the `GitObjectDirectory` field of a `Repository` proto on an RPC and having it resolve into the target storage root — a path realistically reachable from the pre-receive/access-check quarantine round trip Gitaly implements for every push, rather than a fully anonymous unauthenticated caller.

### Recommendation
Do not classify a directory as an implicitly-trusted transaction quarantine dir based solely on its final path component name. Instead, always require the ownership verification (`QuarantineDirectoryPrefix`/temp-dir prefix match, or in-repo relative-path validation) regardless of whether the basename looks like `quarantine`, or derive the trusted transaction quarantine location from a value Gitaly itself computed for the current request (e.g. from the active `storage.Transaction`) rather than re-deriving trust from user/Rails-supplied path text.

### Proof of Concept
1. Start a push to repository A; Gitaly's `pre-receive` handling creates a quarantine directory for A and reports its relative `GitObjectDirectory` (e.g. `../../tx-tmp/quarantine`) to Rails as part of the `/internal/allowed` call.
2. Concurrently, an actor triggers an RPC (e.g. `GetObjectDirectorySize`, `CommitIsAncestor`, `ListAllBlobs` — all of which honor `GitObjectDirectory` per the tests referenced above) against repository B, but sets `Repository.GitObjectDirectory` to a value whose relative path resolves (via `filepath.Join(storagePath, ...)`) to some directory under the storage root whose basename is `quarantine` — for instance the transaction quarantine directory belonging to A's still in-flight push, learned/guessed from the temp-dir naming convention.
3. Because `filepath.Base(relativeObjectDirectoryPath) == "quarantine"`, `isTransactionQuarantineDir` is `true` and the ownership-verification block (`QuarantineDirectoryPrefix(repo)` check) is skipped entirely.
4. `ObjectDirectoryPath` returns the full path to A's quarantine directory as if it were B's, and the RPC operates on/reveals objects from A's unauthorized, in-flight push.

	isTransactionQuarantineDir := (baseDir == "quarantine") || ((parentDir == "quarantine") && strings.HasPrefix(baseDir, "tmp_objdir"))

	// Transactions quarantine a repository by pointing the object directory to a 'quarantine' named
	// directory in the transaction's temporary directory. If the base directory is `quarantine`,
	// Git push may apply an additional layer of quarantine such as `/quarantine/tmp_objdir-incoming-Gbc29N`
	// so we don't assert the `/quarantine` being the last element of the path. We thus also check for
	// whether the parent directory is in `quarantine` and whether the base directory has the expected
	// `tmp_objdir` suffix.
	if !isTransactionQuarantineDir {
		// We need to check whether the relative object directory as given by the repository is
		// a valid path. This may either be a path in the Git repository itself, where it may either
		// point to the main object directory storage or to an object quarantine directory as
		// created by git-receive-pack(1). Alternatively, if that is not the case, then it may be a
		// manual object quarantine directory located in the storage's temporary directory. These
		// have a repository-specific prefix which we must check in order to determine whether the
		// quarantine directory does in fact belong to the repo at hand.
		if _, origError := storage.ValidateRelativePath(repoPath, objectDirectoryPath); origError != nil {

			// The relative path is outside of the repository
			if !strings.HasPrefix(absoluteObjectDirectoryPath, expectedQuarantinePrefix) {
				return "", structerr.NewInvalidArgument("not a valid relative path: %w", origError)
