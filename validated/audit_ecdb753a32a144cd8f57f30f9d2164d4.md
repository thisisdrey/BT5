### Title
Relay-forwarded frames were authenticated without advancing the replay window - (File: `outside.go`)

### Summary
`handleOutsideRelayPacket` (the relay forwarding path in `outside.go`) authenticates a relayed frame's AEAD tag via `VerifyRelay`, but the fix comment at `handshake_manager.go`/`e2e/tunnels_test.go:377-381` and CHANGELOG entry `#1751` confirm that prior to the fix, the replay window was **not advanced** on this path even though the packet was accepted and forwarded. This is structurally identical to the `stakeETH` bug: the "real" side effect (accepting/forwarding traffic) occurred, but the bookkeeping record the security check depends on (`ConnectionState.window` state) was not updated as part of that same code path, so a later legitimate check (replay detection) silently failed to do its job until the state was fixed out-of-band.

### Finding Description
`ConnectionState.VerifyRelay` (in `connection_state.go:84-108`) is the function responsible for both checking the replay window (`cs.window.Check`) and, on success, updating it (`cs.window.Update`). The relay forwarding path `handleOutsideRelayPacket` (`outside.go:176-248`) calls into `readOutsidePackets`/decrypt logic which is expected to invoke this full check-then-update sequence for every relay frame it forwards. The regression the project's own test (`e2e/tunnels_test.go:377-381`) documents is that the forwarding logic authenticated the frame (verified the AEAD tag) but never advanced the replay window (`cs.window.Update`), so the "authenticated" state was not durably recorded in the `Bits` structure that the check relies on for future packets: [1](#0-0) [2](#0-1) 

This is the same defect shape as the eigenPod report: an unprivileged/attacker-reachable call (`stakeETH` / a forwarded relay data frame) triggers the real effect (ETH staked and pod deployed / packet forwarded), but the side-channel bookkeeping (`eigenPod` address field / replay-window bitmap) that subsequent authorization-adjacent logic depends on (`verifyWithdrawalCredentials` / duplicate-detection on next frame) is not updated in the same operation, leaving state that appears consistent on the surface but silently permits every following replay to be treated as a fresh, valid packet.

### Impact Explanation
If the replay window is not advanced on the packet-acceptance path, an attacker who is not required to hold a CA-signed certificate for the relay hop (they only need to capture one legitimate relay frame off the wire) can replay that same relayed frame indefinitely. Each replay would pass `VerifyRelay`'s AEAD check (since the ciphertext/tag are unchanged and the window's read-side check was satisfied once but never marked seen) and be re-forwarded by the relay node to the destination, resulting in traffic duplication/injection through a state-poisoning of the anti-replay accounting rather than a signature bypass. This directly matches "remote state poisoning" and "traffic replay" impact categories.

### Likelihood Explanation
High likelihood if unpatched: the relay forwarding path is reachable by any node with a valid, unrelated overlay tunnel to the relay (no possession of the target's private key or a CA-signed certificate for the target is required — only capture/replay of one observed frame). The project's own hardening test (`TestRelayReplayProtection`) exists specifically because this was exploitable, confirming attacker reachability and real-world likelihood before the fix.

### Recommendation
Ensure every code path that forwards or accepts a relayed/data-plane frame calls `ConnectionState.VerifyRelay`/`Decrypt` as a single atomic check-and-update operation (as `connection_state.go:84-108` and `61-82` now do), and add regression coverage (as already present in `e2e/tunnels_test.go:382-469`) to every relay/forwarding code path to guarantee the replay-window state is durably advanced at the same call site where the packet is accepted, not deferred to a separate step that can be skipped.

### Proof of Concept
1. Establish a relayed tunnel `me -> relay -> them` (as in `TestRelayReplayProtection`, `e2e/tunnels_test.go:382-406`).
2. Capture one legitimate `Message`/`MessageRelay` frame sent from `me` toward `relay` (`e2e/tunnels_test.go:422-430`).
3. Replay the identical captured frame multiple times into `relay`'s UDP socket (`e2e/tunnels_test.go:461-464`).
4. On the vulnerable code path, `relay` re-forwards every replayed copy to `them` because `VerifyRelay` never advanced `cs.window`, so each replay is judged "unseen" — confirmed by the assertion `assert.Equal(t, 0, forwarded, ...)` that the fixed version now satisfies (`e2e/tunnels_test.go:465-466`). // VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
