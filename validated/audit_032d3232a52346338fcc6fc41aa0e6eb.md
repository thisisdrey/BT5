Based on my analysis, I've found a concrete Gitaly analog for this bug class: a shared-resource RPC that lacks any check binding the caller to actual ownership/membership of the resource before performing a destructive, cross-tenant-impacting operation.

### Title
Unauthenticated cross-repository DoS via `DeleteObjectPool`/`LinkRepositoryToObjectPool` accepting arbitrary attacker-supplied object pool paths - (File: internal/gitaly/service/objectpool/delete.go, internal/gitaly/service/objectpool/link.go)

### Summary
Gitaly's `ObjectPoolService` lets any caller identify an object pool purely by its `relative_path`/`storage_name` fields in the request, with no verification that the caller's own repository is actually a legitimate member, creator, or the "primary" pool member of that pool. `DeleteObjectPool` explicitly documents "There are no safety checks in place, so if any repository is still using this object pool it will become corrupted," and `LinkRepositoryToObjectPool` will happily attach any repository the caller controls to any existing pool path they can guess or know, without proving they have any relationship to the object pool's other members.

### Finding Description
The RPC handlers `DeleteObjectPool` [1](#0-0)  and `LinkRepositoryToObjectPool` [2](#0-1)  resolve the target object pool solely from the caller-supplied `ObjectPool.Repository` proto field via `poolForRequest`/`ExtractPool` [3](#0-2) . Neither RPC verifies that the calling repository (the "target"/"additional" repository in the request) is actually linked to, or was the originator of, that specific pool.

The protobuf documentation itself states the danger plainly: `DeleteObjectPool` "deletes the object pool. There are no safety checks in place, so if any repository is still using this object pool it will become corrupted" [4](#0-3) . Likewise, the lifecycle documentation notes "It is the responsibility of the caller to ensure that it really has no members left, else any existing member will become corrupt" [5](#0-4) .

Similarly, `Link` in the object pool package only checks whether the target repository's `objects/info/alternates` file already points elsewhere; if it doesn't, it silently rewrites the alternates file to point at whatever pool the caller specified [6](#0-5) , and `getRelativeObjectPath`/`linkedToRepository` only compare paths, not ownership [7](#0-6) .

This mirrors the reported bug class: a shared resource (the "adapter"/object pool) that is referenced by multiple independent tenants, where the authorization check is performed against the caller's own resource rather than against the caller's actual relationship to the shared resource being mutated. In the original report, `_verifyCreatorOrOwner` checked whether the *caller* was a creator of *some* vault using the adapter — not whether the caller had any legitimate stake in *that specific* adapter instance being paused. In Gitaly, `poolForRequest`/`ExtractPool` accept and act on whatever pool path is supplied, without verifying that the calling repository is actually a member of that pool.

### Impact Explanation
Because `DeleteObjectPool` performs no safety checks and is a `MUTATOR` RPC gated only by normal repository-scoped ACL checks (not by pool-membership checks), a caller that can invoke the `ObjectPoolService` for a repository under their control and additionally reference an existing pool's `storage_name`/`relative_path` can delete that pool. This corrupts every other repository still using that pool (via `objects/info/alternates`), since those repositories will lose access to shared objects instantly — a cross-repository denial of service that affects the origin repository and every fork/pool member. `LinkRepositoryToObjectPool` similarly allows an attacker to redirect their own repository to link into an unrelated pool without validation, and subsequent housekeeping operations (`FetchIntoObjectPool`, `git-repack`) on that pool can then remove/dangling-reference objects in ways that other legitimate members did not expect, again degrading or corrupting objects relied upon by other tenants of the pool.

### Likelihood Explanation
Exploitability hinges on whether the caller can discover an existing pool's exact relative path for a repository they don't own. Rails/GitLab pool paths are `@pools/<sha256-prefix>/<sha256>.git` derived from the origin repository's hashed storage path [8](#0-7) , and Praefect-derived paths are `@cluster/pools/<hash-prefix>/<repository-id>` deterministically derived from a small sequential repository ID [9](#0-8) . The latter is a low-entropy, sequentially predictable identifier, making pool-path guessing or enumeration plausible for a caller with any valid Gitaly-facing credentials that permit reaching `ObjectPoolService`. This is a Gitaly-level architectural gap regardless of whether GitLab's Rails layer adds its own authorization in front of these RPCs — at the Gitaly layer itself, the RPC contract has no cross-check that the caller-associated repository is actually a member of the pool being deleted or linked.

### Recommendation
Before performing destructive/binding operations (`DeleteObjectPool`, `LinkRepositoryToObjectPool`, `FetchIntoObjectPool`), verify server-side that the calling/target repository is actually already an alternate member of (or is the acknowledged originator of) the specified object pool — e.g., by checking `objects/info/alternates` linkage or maintaining explicit pool-membership metadata — rather than trusting the caller-supplied pool path unconditionally. For `DeleteObjectPool` specifically, require the caller to prove there are no remaining pool members (or make deletion idempotent-safe by first verifying zero alternates references across the pool's known members) instead of documenting the danger and delegating responsibility entirely to callers.

### Proof of Concept
1. Attacker creates `repoA` and knows (or brute-forces via low-entropy Praefect pool IDs) the `relative_path` of `pool-victim`, an existing object pool with members `repoV1`, `repoV2` owned by a different user/project.
2. Attacker calls `LinkRepositoryToObjectPool(Repository=repoA, ObjectPool=pool-victim)` [2](#0-1) . This succeeds because `pool.Link` performs no ownership check on `repoA` vs `pool-victim` [10](#0-9) .
3. Attacker then calls `DeleteObjectPool(ObjectPool=pool-victim)` [1](#0-0) , which removes `pool-victim` from disk with no check for remaining members, per the documented "no safety checks" behavior [4](#0-3) .
4. `repoV1` and `repoV2`, which still reference `pool-victim` via `objects/info/alternates`, now fail `git-fsck`/object lookups for any object that only existed in the pool, causing denial of service for those repositories/forks — analogous to the adapter-pause DoS in the original report.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}

	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir

		return nil, structerr.NewInternal("%w", err)

	return pool, nil

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

// linkedToRepository tests if a repository is linked to an object pool
func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
}
