### Title
Orphaned `PromiseYieldStatus::Yielded` trie entry when gas charges after `create_promise_yield_receipt` fail - ([File: runtime/near-vm-runner/src/logic/logic.rs / runtime/runtime/src/ext.rs / runtime/runtime/src/function_call.rs])

### Summary
In `promise_yield_create` (and `promise_yield_create_with_id`), the host function writes a `PromiseYieldStatus::Yielded` trie entry synchronously inside `RuntimeExt::create_promise_yield_receipt` (`runtime/runtime/src/ext.rs:353-369`), directly against the same `TrieUpdate` used for the whole action, but the corresponding `PromiseYield` receipt is only materialized later, gated behind `execution_succeeded` in `action_function_call` (`runtime/runtime/src/function_call.rs:151-227`). Gas charges performed after the trie write (`pay_action_base`/`pay_action_per_byte` in `runtime/near-vm-runner/src/logic/logic.rs:3700-3701`) can still fail with `GasExceeded`, aborting the whole function call while the yield-status write to `state_update` has already been staged and is not covered by the same success gate as the receipt.

### Finding Description
`promise_yield_create` in `runtime/near-vm-runner/src/logic/logic.rs:3660-3718` performs, in order:
1. `prepay_gas(gas)` (line 3691) — deducts `gas` from `prepaid_gas` budget.
2. `pay_gas_for_new_receipt(true, &[true])` (line 3695) — a further charge that can fail.
3. `self.ext.create_promise_yield_receipt(...)` (line 3696-3697) — calls into `RuntimeExt::create_promise_yield_receipt` (`runtime/runtime/src/ext.rs:353-369`), which both (a) registers the receipt in the in-memory `receipt_manager` and (b) calls `set_promise_yield_status(&mut self.trie_update, ...)` **directly against the live `TrieUpdate`** that was passed by reference from `action_function_call` (`runtime/runtime/src/function_call.rs:62-75`, `RuntimeExt::new(state_update, ...)`).
4. `pay_action_base(ActionCosts::function_call_base, true)` (line 3700) and `pay_action_per_byte(...)` (line 3701) — both of these can still fail with `GasExceeded` if the attacker tunes `gas`/method-name/argument length so that steps 1-2 barely fit but step 4 does not.

If step 4 fails, the whole host call returns `Err`, the WASM execution aborts (`outcome.aborted = Some(...)`), and in `action_function_call` the branch at line 151 (`if execution_succeeded { ... }`) is skipped. That branch is the only place where `receipt_manager.action_receipts` are turned into `new_receipts`/pushed into `result.new_receipts`, and where the promise-yield timeout is enqueued (`enqueue_promise_yield_timeout`, line 162-169). Because this branch is skipped, the receipt that `create_promise_yield_receipt` registered in `receipt_manager` is dropped in memory. However, the `set_promise_yield_status` write already made in step 3 was applied directly to `state_update`/`TrieUpdate`, not staged in the `receipt_manager` that is discarded on failure — it therefore is not obviously protected by the same `execution_succeeded` gate. This produces an asymmetric commit: a `PromiseYieldStatus::Yielded` entry for `data_id` persists in the trie changes with no matching `PromiseYieldReceipt` ever created and no timeout ever enqueued for it.

Attack inputs: an unprivileged attacker deploys a WASM contract that calls `promise_yield_create` (or `promise_yield_create_with_id`) with a `method_name`/`arguments` length and `gas` value chosen so that `prepay_gas` and `pay_gas_for_new_receipt` fit under the remaining prepaid gas, but `pay_action_base`/`pay_action_per_byte` (charged for `function_call_base`/`function_call_byte` right after the yield receipt registration) push usage over `prepaid_gas`, triggering `GasExceeded`.

### Impact Explanation
If the `PromiseYieldStatus` write is not rolled back at a higher level (i.e., if `TrieUpdate` mutations made mid-action are committed regardless of the action's ultimate failure, which the code inspected does not visibly guard against for this specific write), this creates a permanently "yielded" status entry for a `data_id`/`yield_id` that has no backing receipt and will never resolve or time out (since `enqueue_promise_yield_timeout` is also skipped). For `promise_yield_create_with_id`, this could make `has_yield_id_mapping` treat future calls with the same `user_yield_id` as duplicates forever, permanently blocking the account from creating a yield with that ID — this is a liveness/state-hygiene defect, not a direct theft-of-funds bug, and its severity depends entirely on whether the underlying `TrieUpdate` actually persists uncommitted mutations from failed actions (which I could not fully confirm from the available code slice — see below).

### Likelihood Explanation
The precondition is very cheap: attacker needs a funded account and a deployed contract exposing `promise_yield_create`/`promise_yield_create_with_id` with attacker-controlled `gas` (the `near-test-contracts` rs test contract already exposes such calls, e.g. `call_yield_create_return_data_id` in `runtime/near-test-contracts/test-contract-rs/src/lib.rs:1257-1283`). Precisely straddling the two charge points requires knowing exact fee-config constants (`yield_create_base`, `new_action_receipt`, `new_data_receipt_base`, `function_call_base`, `function_call_byte`) but these are public protocol parameters, so an attacker can compute an exact gas value deterministically and repeat the exploit at will.

### Recommendation
Verify (this is the critical open question) whether `TrieUpdate` changes made during a function call that ultimately aborts are rolled back by an outer mechanism (e.g., `TrieUpdate::rollback`/re-creation of a fresh `TrieUpdate` per action, or the `state_update` being discarded and only re-derived from a checkpoint on failure) before further pursuing this. If no such rollback exists for this write path, defer writing `PromiseYieldStatus`/`set_yield_id_mapping` until after all gas charges for the new receipt (`pay_gas_for_new_receipt`, `pay_action_base`, `pay_action_per_byte`) have succeeded, or make the yield-status write conditional/reversible in the same way `receipt_manager.action_receipts` already is (i.e. buffer it and only commit inside the `execution_succeeded` branch in `function_call.rs`).

### Proof of Concept
Unable to construct a fully confirmed PoC within this investigation: I traced the exact code path showing the write in `ext.rs::create_promise_yield_receipt` happens directly on the shared `TrieUpdate` before the gas charges in `logic.rs::promise_yield_create` that can still fail, and that `function_call.rs::action_function_call` only gates receipt/timeout emission — not necessarily the trie write itself — behind `execution_succeeded`. However, I was not able to verify, within the available tool budget, whether `TrieUpdate` mutations from a failed action are discarded by an outer rollback/checkpoint mechanism elsewhere in `runtime/runtime/src/lib.rs` (I found no `rollback`/`checkpoint` call sites in the files I could inspect, but did not have time to fully trace `apply_action_receipt`/`apply_action` in `runtime/runtime/src/lib.rs`). A conclusive PoC would be a runtime integration test that (1) submits a `FunctionCall` action invoking `call_yield_create_return_data_id`-style method with `gas` tuned to fail exactly at `pay_action_base`/`pay_action_per_byte`, (2) asserts the action result is `Err(FunctionCallError::HostError(GasExceeded))` and no new receipts were produced, and (3) reads back `has_promise_yield_status`/`has_yield_id_mapping` for the produced `data_id` from the post-apply trie to confirm whether an orphaned entry persisted or was correctly rolled back.         );

        Ok((receipt_index, input_data_id))
    }

    /// Special case of create_receipt used by yielded promises.
    ///
    /// The receipt will be executed after the input data is explicitly submitted by calling
    /// `create_data_receipt` with specified `input_data_id`.
    ///
    /// # Arguments
    ///
    /// * `input_data_id` - data id which will be used to later submit the receipt input
    /// * `receiver_id` - account id of the receiver of the receipt created
    pub(super) fn create_promise_yield_receipt(
        &mut self,
        input_data_id: CryptoHash,
        receiver_id: AccountId,
    ) -> ReceiptIndex {
        let new_receipt = ActionReceiptMetadata {
            receiver_id,
            refund_to: None,
            output_data_receivers: vec![],
            input_data_ids: vec![input_data_id],
            actions: vec![],
            is_promise_yield: true,
        };
        let new_receipt_index = self.action_receipts.len();
        self.action_receipts.push(new_receipt);
        self.promise_yield_receipt_index.insert(input_data_id, new_receipt_index);
        new_receipt_index as ReceiptIndex
    }
