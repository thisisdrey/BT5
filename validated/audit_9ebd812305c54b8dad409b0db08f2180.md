### Title
Native TRX sent via `CALL` with value to precompiled-contract addresses becomes permanently locked - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.callToPrecompiledAddress()` unconditionally transfers any TRX `endowment` attached to a `CALL`/`CALLCODE` targeting a precompiled-contract address (e.g. `0x01`–`0x0a`, `0x1000001`, etc.) into the balance of that fixed address before invoking the precompile's `execute()` logic. None of these fixed addresses correspond to a real account controlled by a private key, and no precompile implements logic to forward or refund the received value, so any TRX sent this way is irrecoverably stuck.

### Finding Description
When a smart contract executes a `CALL` opcode with a non-zero `value` toward an address that resolves to a built-in precompiled contract via `PrecompiledContracts.getContractForAddress()` [1](#0-0) , execution flows into `Program.callToPrecompiledAddress()`. This method computes the `endowment` from the message call and, before running the precompile's `execute(data)`, performs an unconditional balance transfer to the target (precompile) address whenever `endowment > 0` and sender/target differ: [2](#0-1) 

This uses `MUtil.transfer`, which simply validates the transfer and moves the balance: [3](#0-2) 

The precompiled-contract addresses are fixed constants such as `ecRecoverAddr` (`...0001`), `sha256Addr` (`...0002`), through vote/freeze-related addresses like `...0100000b` [4](#0-3) . These are not real TRON accounts derived from any keypair — they are reserved dispatch addresses used purely to route VM calls to native Java implementations (e.g. `ECRecover`, `Sha256`, `Ripempd160`) which only compute/return data and never move balances [5](#0-4) . Because there is no private key for these addresses, and the precompiled contract implementations do not forward or refund any incoming value, TRX credited to them via `MUtil.transfer` can never be spent, transferred, or withdrawn by any subsequently signed transaction.

This differs from `callToAddress()` (calls into normal user contracts), where the target is a real account/contract capable of using or forwarding the value; precompile targets have no such capability.

### Impact Explanation
Any user (an unprivileged contract deployer/caller) can trivially craft a contract that performs `precompileAddress.call{value: X}(data)` (e.g. targeting `0x01` ecrecover or `0x02` sha256). The TRX is unconditionally debited from the caller and credited to the fixed precompile address, and is then permanently unspendable — this constitutes a permanent freezing/loss of funds for any user who triggers it, whether by mistake, via a compromised/bugged wallet frontend, or via induced interaction from an attacker's malicious contract that forwards `value` to one of these known addresses.

### Likelihood Explanation
Likelihood is straightforward: this is reachable from any ordinary smart contract call using a single signed transaction; it requires no special privilege, timing, or race condition, and the precompiled contract addresses are well known/documented constants, making the class of address trivially discoverable by any contract developer or attacker constructing a call.

### Recommendation
In `Program.callToPrecompiledAddress()`, reject calls that attach non-zero `endowment`/`value` to a precompiled-contract address (mirroring how many EVM-compatible VMs treat precompile calls as non-payable), or explicitly refund/revert the transaction when `msg.getEndowment().value().longValueExact() > 0` for a resolved precompile target, before performing the `MUtil.transfer`.

### Proof of Concept
1. Deploy a contract with a function such as:
```solidity
function drain() external payable {
    address(0x0000000000000000000000000000000000000001).call{value: msg.value}("");
}
```
2. Call `drain()` with some TRX value attached from an ordinary account.
3. Trace execution into `OperationActions.exeCall` → `Program.callToPrecompiledAddress` [6](#0-5) ; observe the balance transfer at `Program.java:1713-1721` crediting the fixed ecrecover address `0000...0001` (as a 21-byte TRON address).
4. Confirm via `AccountStore`/balance query that this address now holds a positive TRX balance.
5. Note there is no transaction type, actuator, or precompile path that can debit balance from this address (no private key exists for it, and precompile `execute()` implementations like `ECRecover`/`Sha256` never touch balances) — the TRX is permanently stuck.

  public static void exeCall(Program program, DataWord adjustedCallEnergy,
      DataWord codeAddress, DataWord value, DataWord tokenId, boolean isTokenTransferMsg) {

    DataWord inDataOffs = program.stackPop();
    DataWord inDataSize = program.stackPop();

    DataWord outDataOffs = program.stackPop();
    DataWord outDataSize = program.stackPop();

    program.memoryExpand(outDataOffs, outDataSize);
    int op = program.getCurrentOpIntValue();
    MessageCall msg = new MessageCall(
        op, adjustedCallEnergy, codeAddress, value, inDataOffs, inDataSize,
        outDataOffs, outDataSize, tokenId, isTokenTransferMsg);

    PrecompiledContracts.PrecompiledContract contract =
        PrecompiledContracts.getContractForAddress(codeAddress);
    if (contract != null) {
      if (program.isConstantCall()) {
        contract =  PrecompiledContracts.getOptimizedContractForConstant(contract);
      }
      program.callToPrecompiledAddress(msg, contract);
    } else {
      program.callToAddress(msg);
    }
    program.step();
  }
