### Title
`remove_account` clears only 4 of the 12 account-scoped TrieKey columns, leaving `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` rows attached to a deleted account name reachable after account recreation - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` only issues `state_update.remove(...)` for `TrieKey::Account`, `TrieKey::ContractCode`, the keys returned by iterating `get_raw_prefix_for_access_keys` (`AccessKey`/`GasKeyNonce`), and the keys returned by iterating `get_raw_prefix_for_contract_data` (`ContractData`). [1](#0-0)  That is a strict 4-column subset of the 12 columns in `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY`, so any receipt/data-plumbing state keyed to the deleted `account_id` (`ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`) survives account deletion verbatim. [2](#0-1)  Because NEAR account IDs are reusable (a deleted sub-account name can be freely re-created by its parent, or an attacker-owned sub-account can be deleted and re-created by the same signer), a newly created account under the same `account_id` inherits these orphaned rows.

### Finding Description
`remove_account` is invoked from `action_delete_account` in `runtime/runtime/src/actions.rs` when a `DeleteAccountAction` is processed. [3](#0-2)  Its cleanup logic is explicitly scoped to 4 kinds of state:
- `TrieKey::Account` and `TrieKey::ContractCode` removed directly. [4](#0-3) 
- `AccessKey`/`GasKeyNonce` rows removed by iterating `trie_key_parsers::get_raw_prefix_for_access_keys(account_id)`. [5](#0-4) 
- `ContractData` rows removed by iterating `trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[])`. [6](#0-5) 

No code path in `remove_account` touches `RECEIVED_DATA`, `POSTPONED_RECEIPT_ID`, `PENDING_DATA_COUNT`, `POSTPONED_RECEIPT`, `PROMISE_YIELD_RECEIPT`, `PROMISE_YIELD_STATUS`, `YIELD_ID_TO_DATA_ID`, or `DATA_ID_TO_YIELD_ID`, even though these are all listed as account-scoped columns in `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY`. [2](#0-1)  These rows are set elsewhere (e.g. `set_postponed_receipt`, `set_promise_yield_receipt`, `set_promise_yield_status`, `set_yield_id_mapping`, `set_received_data`) whenever a cross-contract call with unresolved input data, or a `yield_create`/`yield_resume` pair, targets that account, all of which are reachable by an ordinary unprivileged sender through normal cross-contract calls and the yield/resume promise API. [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) 

An account with any of these pending rows can still submit `DeleteAccountAction`; nothing in `action_delete_account`/`remove_account` checks for or blocks outstanding `PostponedReceipt`, `PromiseYieldReceipt`, or `ReceivedData` before deleting the account. Since account names are reusable (any sub-account under a parent, or any account the attacker controls) an attacker can delete an account while it has outstanding postponed cross-contract state and then recreate the same `account_id` with attacker-controlled code/keys. When the eventually-arriving input data or yield-resume later satisfies the stale `PendingDataCount`/`PostponedReceipt`/`PromiseYieldReceipt`, the runtime will execute that receipt (and any deposit/gas it carries) against whatever code and keys now occupy the recreated account, not the account identity the sender/depositor originally addressed.

### Impact Explanation
This breaks the "state keyed by a reusable human name must not outlive the identity it was created for" invariant: a third party's attached deposit/promise callback, addressed to what they believe is a stable account identity, can be redirected to arbitrary attacker-controlled code once the account name is deleted and re-registered. Depending on the deposit/gas carried by the stale postponed or yielded receipt, this is a concrete misdirection-of-funds / authorization-escalation-across-accounts primitive (the attacker's new contract executes with the deposit and call arguments meant for the deleted account's original contract), matching the "theft" bounty category.

### Likelihood Explanation
Whether this is fully exploitable for third-party fund theft depends on additional preconditions that I could not fully verify in this pass given tool-call limits: (1) confirming `action_delete_account`/`action_validation.rs` truly has no existing check that rejects deletion while `PostponedReceipt`/`PromiseYieldReceipt`/`ReceivedData` rows are outstanding for the account, and (2) confirming the exact timing/ordering guarantees around receipt delivery vs. account deletion+recreation in the same or later blocks. The attacker-side steps (create sub-account, receive a cross-contract call with an unresolved dependency or an outstanding `yield_create`, delete the account via `DeleteAccountAction`, recreate the same `account_id` with new keys/contract) are all achievable by an unprivileged signer with no validator/node access, so the reachability of the *residual-state* condition itself is solidly established by the code read. The residual-state fact (8 of 12 columns survive `remove_account`) is proven directly by the code; the incremental step from "state survives" to "attacker profits from a third party's deposit" needs confirmation against `action_validation.rs`/`actions.rs` before treating it as a fully confirmed high-severity fund-theft finding rather than a state-hygiene defect.

### Recommendation
Extend `remove_account` to also sweep the remaining account-scoped columns before finalizing account deletion: iterate and remove `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` rows for the account (mirroring the existing prefix-iteration pattern used for `AccessKey`/`ContractData`), or alternatively block `DeleteAccountAction` while any of these rows exist for the account, so a recreated account under the same name never inherits pending cross-contract/yield state from its predecessor.

### Proof of Concept

```rust
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
```
