### Title
Firewall rule "any" flag interactions silently widen access instead of being rejected, enabling policy-bypass misconfiguration - (File: firewall.go)

### Summary
`Firewall` rules are built from multiple independent, optionally-set fields (`groups`, `host`, `cidr`, `local_cidr`, `ca_name`, `ca_sha`, `proto`, `port`) that are supposed to be ANDed together, but several of them silently collapse to "match everything" once any one of them is set to (or contains) the special value `"any"`. The code that is supposed to guard against this, `rule.sanity()`, only logs a warning and never rejects the configuration, so a rule that an operator believes is scoped by host/cidr/group can end up matching all traffic. This mirrors the reported "generic and complex, flag-driven behavior" bug class in the Crowdsale/CrowdsaleToken contracts, where independently toggleable options combine in ways that widen the effective attack surface instead of narrowing it.

### Finding Description
`AddFirewallRulesFromConfig` parses each configured rule and only performs a *soft* sanity check: [1](#0-0) 

The `sanity()` function documents that rules are evaluated as `"port AND proto AND (ca_sha OR ca_name) AND (host OR group OR groups OR cidr) AND local_cidr"`, and explicitly acknowledges that a group/host/cidr value of `"any"` will silently ignore any other more restrictive value configured alongside it — but it still returns `nil` (no error) for the "no content" case and only ever returns descriptive errors, which are logged as warnings, not enforced: [2](#0-1) 

The actual matching logic confirms this "OR-with-any-short-circuit" behavior at runtime. `FirewallRule.isAny` treats a rule as unconditionally matching if `groups` is empty AND `host` and `cidr` are also empty, or if `"any"` appears in any of them: [3](#0-2) 

And `FirewallRule.match` takes the "Any" shortcut before ever evaluating groups/host/cidr: [4](#0-3) 

Additionally, `FirewallCA.match` ORs together three independent optional identity checks (`fc.Any`, `CAShas` keyed by cert issuer, `CANames` keyed by the CA's own name) — any one of the three flags being satisfied allows the packet through, regardless of the other two: [5](#0-4) 

This is directly analogous to the reported bug class: a firewall rule is composed of many independently-settable optional flags (`groups`, `host`, `cidr`, `ca_name`, `ca_sha`, `local_cidr`) whose interactions are complex enough that the developers had to write a dedicated "sanity" checker to detect unintended widening — yet that checker only warns instead of enforcing, leaving the actual security boundary (the firewall) dependent on an operator correctly reasoning about flag interactions that the code itself flags as confusing.

### Impact Explanation
If an operator writes a rule intending to restrict access to a specific host/CIDR/group but inadvertently also sets (or a templated config generates) `"any"` in a sibling field — or defines two rules where a broad `ca_name`/`ca_sha` "OR" unintentionally reintroduces access removed by a more specific rule — the firewall will allow traffic an administrator believed was blocked. Since `Firewall.Drop` is the sole enforcement point deciding whether a remote peer's traffic passes into the tun device (`firewall.go:425-479`), a silently over-broadened rule is a concrete firewall bypass allowing unauthorized remote-to-local traffic without requiring the sender to hold a specific certificate identity, group, or CA-signed relationship intended by the policy author.

### Likelihood Explanation
Likelihood is moderate: the misconfiguration requires an operator to combine fields in the ways described (e.g., a `groups` list containing `"any"` alongside an intended `host` or `cidr` restriction, or overlapping `ca_name`/`ca_sha` rules). This is realistic in templated/multi-tenant configs where rules are generated programmatically and an `"any"` sentinel is used as a wildcard default in one field while another field still carries a real restriction. The code only warns via logs (`l.Warn(...)`, `firewall.go:401-405`), which are easy to miss in automated deployments, so the unintended widening is not surfaced as a hard failure.

### Recommendation
- Change `AddFirewallRulesFromConfig` to treat `sanity()` findings as fatal configuration errors (or provide a strict mode) rather than warnings, so ambiguous "any"-combined-with-restriction rules fail to load.
- Reduce the number of independently interacting optional match fields per rule, or require that `"any"` be the sole value in a rule (reject rules that mix `"any"` with any other host/group/cidr value at parse time) instead of silently interpreting the combination.
- Add config-time validation that flags overlapping `ca_name`/`ca_sha` rules whose combined effect is broader than either rule intends.

### Proof of Concept
Given the following firewall inbound config, the two independently-configured rules interact via `FirewallCA.match`'s OR-with-any logic (`firewall.go:746-767`) and `FirewallRule.isAny` (`firewall.go:828-846`):
```yaml
firewall:
  inbound:
    - port: any
      proto: any
      groups:
        - "restricted-group"
        - "any"      # unintentionally added by a config templating bug
      host: "trusted-host-only"
```
`sanity()` detects this exact case (`groups spec [...] contains the group "any". This rule will ignore the specified host ...`, `firewall.go:1039-1042`) but only logs a warning and still loads the rule. At match time, `isAny` returns `true` because `"any"` is present in `groups` (`firewall.go:833-835`), so `FirewallRule.match` takes the unconditional `Any` shortcut (`firewall.go:854-856`) and the rule matches **every** inbound host regardless of the `host: "trusted-host-only"` restriction the operator believed was enforced.

func (fc *FirewallCA) match(p firewall.Packet, c *cert.CachedCertificate, caPool *cert.CAPool) bool {
	if fc == nil {
		return false
	}

	if fc.Any.match(p, c) {
		return true
	}

	if t, ok := fc.CAShas[c.Certificate.Issuer()]; ok {
		if t.match(p, c) {
			return true
		}
	}

	s, err := caPool.GetCAForCert(c.Certificate)
	if err != nil {
		return false
	}

	return fc.CANames[s.Certificate.Name()].match(p, c)
}

// sanity returns an error if the rule would be evaluated in a way that would short-circuit a configured check on a wildcard value
// rules are evaluated as "port AND proto AND (ca_sha OR ca_name) AND (host OR group OR groups OR cidr) AND local_cidr"
func (r *rule) sanity() error {
	//port, proto, local_cidr are AND, no need to check here
	//ca_sha and ca_name don't have a wildcard value, no need to check here
	groupsEmpty := len(r.Groups) == 0
	hostEmpty := r.Host == ""
	cidrEmpty := r.Cidr == ""

	if (groupsEmpty && hostEmpty && cidrEmpty) == true {
		return nil //no content!
	}

	groupsHasAny := slices.Contains(r.Groups, "any")
	if groupsHasAny && len(r.Groups) > 1 {
		return fmt.Errorf("groups spec [%s] contains the group '\"any\". This rule will ignore the other groups specified", r.Groups)
	}

	if r.Host == "any" {
		if !groupsEmpty {
			return fmt.Errorf("groups specified as %s, but host=any will match any host, regardless of groups", r.Groups)
		}

		if !cidrEmpty {
			return fmt.Errorf("cidr specified as %s, but host=any will match any host, regardless of cidr", r.Cidr)
		}
	}

	if groupsHasAny {
		if !hostEmpty && r.Host != "any" {
			return fmt.Errorf("groups spec [%s] contains the group '\"any\". This rule will ignore the specified host %s", r.Groups, r.Host)
		}
		if !cidrEmpty {
			return fmt.Errorf("groups spec [%s] contains the group '\"any\". This rule will ignore the specified cidr %s", r.Groups, r.Cidr)
		}
	}
