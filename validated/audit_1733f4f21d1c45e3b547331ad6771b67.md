### Title
Premature release of the Praefect repository write-lock during a stopped reference-transaction reopens the cross-node ref-lock deadlock window - (File: internal/praefect/transactions/manager.go)

### Summary
Praefect's `WriteLockManager` (`internal/praefect/datastore/lock_manager.go`) exists specifically to serialize concurrent reference-transaction writes to the same repository *before* any node takes an on-disk Git ref lock, in order to prevent the classic two-node deadlock described in `doc/serialized_writes.md`. The lock for a transaction is tracked in `Manager.repoLocks` keyed only by `transactionID` [1](#0-0) , and it can be torn down independently of the in-flight per-phase voting calls by `StopTransaction` (analogous to the report's `cancelLimitOrder`, an "unrelated" cancel action that unlocks a resource another pending action still depends on) [2](#0-1) . Because `lockRepoForTransaction` treats a *missing* lock entry at `PREPARED`/`COMMITTED` phase as "pre-2.54 Git, no locking to do" rather than an error [3](#0-2) , a concurrent `StopTransaction` call for the same transaction ID silently disables serialization for any sibling node still mid-flight on that transaction, letting a second, unrelated transaction acquire the freed lock and proceed to on-disk ref locking while the first transaction's other nodes are still locking refs on disk — the exact deadlock scenario the feature was built to eliminate.

### Finding Description
`Manager.repoLocks` is a single `sync.Map` entry per `transactionID`, populated once at `PREPARING_PHASE` and consulted (not re-acquired) at `PREPARED_PHASE`/`COMMITTED_PHASE`: [1](#0-0) 

`StopTransaction` releases this same entry unconditionally, independent of which node/phase the transaction's other voters are currently in: [2](#0-1) 

`releaseRepoLockOnPhase` performs a `LoadAndDelete` and calls the captured `Unlock()`, which issues the PostgreSQL `DELETE ... WHERE lock_id = $1 AND holder_txn_id = $2` regardless of whether other in-flight votes for the same `transactionID` still expect the lock to be held: [4](#0-3) [5](#0-4) 

In a real replicated write, each Gitaly node in the replica set independently drives the same `transactionID` through `PREPARING → PREPARED → COMMITTED` roughly in parallel (per `doc/serialized_writes.md`'s "Flow for one write"). If any node's Git hooks reject the change (a completely ordinary event: protected-branch rejection, custom hook failure, quota check, etc.), the hook/Praefect coordinator invokes `transaction.Stop`, which the Gitaly-side `PoolManager.Stop` forwards as `StopTransaction` RPC [6](#0-5) , comment confirming this is triggered by ordinary "access checks or hooks rejected a change" [7](#0-6) .

When `StopTransaction` fires, it deletes and unlocks `repoLocks[transactionID]` and releases the PostgreSQL row for that repository [8](#0-7) . Any sibling node for the *same* transaction that has already passed `PREPARING_PHASE` and is now calling `lockRepoForTransaction` for `PREPARED_PHASE` finds no entry in `repoLocks` and takes the "dormant, pre-2.54 Git" branch, returning `nil` (no error, no lock re-acquired) [3](#0-2) . That sibling node then proceeds to lock refs on-disk via Git's own mechanism without Praefect's cross-repository serialization in effect. Meanwhile, because the repository's PostgreSQL lock row is now free, a completely independent, unrelated write transaction targeting the same repository can immediately acquire it and also begin on-disk ref locking — recreating the exact two-transaction, two-node lock-ordering deadlock that `doc/serialized_writes.md` states is only prevented by serializing "before any node has taken an on-disk ref lock."

### Impact Explanation
This breaks the core invariant of the "Serialized Writes" feature: only one write transaction per repository may be past the ref-locking point at a time. An ordinary, unprivileged push that gets rejected by a hook mid-transaction (a routine occurrence — no attacker action needed) can release the shared write lock while sibling replicas are still finishing on-disk locking for the *same* stopped transaction, reopening a window where a second concurrent write to overlapping refs can also begin on-disk locking. This reintroduces the cross-node ref-lock deadlock the feature exists to eliminate, resulting in a denial-of-service (deadlocked/stuck reference-transaction hooks) on the affected repository's Gitaly nodes, exactly the failure mode documented as the original motivation for this mechanism.

### Likelihood Explanation
Likelihood is moderate: it requires two concurrent writes to the same repository with overlapping refs, and one of the writers' hook chain must fail on at least one node while other nodes are still advancing phases for the same transaction. Hook rejections are common in production (protected branches, custom hooks, size/quota checks), and concurrent pushes to overlapping refs are common in busy repositories, so the preconditions are realistically reachable by ordinary users without any special privilege — they only need to push changes, some of which are expected to be rejected by hooks.

### Recommendation
`StopTransaction`/`cancelTransaction` should not unconditionally release the shared repo lock for a `transactionID` while other voters for that same transaction may still be relying on it being held. At minimum, `lockRepoForTransaction` should treat a missing `repoLocks` entry at `PREPARED_PHASE`/`COMMITTED_PHASE` as an error (aborting that vote) rather than silently skipping lock enforcement, since the "pre-2.54 Git" fallback cannot be distinguished from "lock was concurrently released." Additionally, the lock's PostgreSQL row could carry a monotonically increasing phase/version so that `unlock` only succeeds if no other voter for the same transaction is still in an earlier phase, closing the race between `StopTransaction` and in-flight `PREPARED`/`COMMITTED` votes for other nodes of the same transaction.

### Proof of Concept
1. Configure Praefect with `PraefectSerializedWrite` enabled and a 2+ node replica set for repository `R`.
2. Client A pushes an update to ref `refs/heads/main`. Node1 and Node2 both begin voting for `transactionID = T1`; Node1 completes `PREPARING_PHASE` (acquires the Postgres lock for `R`, stored under `repoLocks[T1]`), then starts `PREPARED_PHASE` (about to lock `refs/heads/main` on disk).
3. Concurrently, Node2's pre-receive hook for the same push fails (e.g., a protected-branch or custom hook rejects it), causing the Praefect/Gitaly hook path to call `StopTransaction(T1)`, which calls `releaseRepoLock(T1)` and deletes the Postgres lock row for `R` (`internal/praefect/transactions/manager.go:228-251`, `336-355`).
4. Node1's already-in-flight `PREPARED_PHASE` call for `T1` executes `lockRepoForTransaction`, finds no entry in `repoLocks` (it was just deleted), and silently returns `nil` without renewing/re-acquiring the lock (`internal/praefect/transactions/manager.go:287-304`) — Node1 proceeds to lock `refs/heads/main` on disk.
5. Client B, concurrently, pushes an unrelated update touching `refs/heads/other` (or any overlapping ref set) as `transactionID = T2`. Because the Postgres lock for `R` is now free, `T2`'s `PREPARING_PHASE` on Node2 acquires it and Node2 begins locking `refs/heads/other` on disk while Node1 (still processing `T1`) holds a different, overlapping ref lock — recreating the two-node lock-ordering deadlock documented in `doc/serialized_writes.md` lines 22-31, which the feature was designed to prevent.

// StopTransaction will gracefully stop a transaction.
func (mgr *Manager) StopTransaction(ctx context.Context, transactionID uint64) error {
	mgr.lock.Lock()
	transaction, ok := mgr.transactions[transactionID]
	if ok {
		// Release while holding mgr.lock so a concurrent voteTransaction
		// can't acquire a fresh repo lock between this release and stop.
		mgr.releaseRepoLock(transactionID)
	}
	mgr.lock.Unlock()

	if !ok {
		return fmt.Errorf("%w: %d", ErrNotFound, transactionID)
	}
	if err := transaction.stop(); err != nil {
		return err
	}

	mgr.logger.WithFields(log.Fields{
		"transaction.id": transactionID,
	}).DebugContext(ctx, "VoteTransaction: transaction stopped")
	mgr.counterMetric.WithLabelValues("stopped").Inc()

	return nil
}

func (mgr *Manager) lockRepoForTransaction(ctx context.Context, transactionID uint64, storageName, repoRelativePath string,
	phase gitalypb.VoteTransactionRequest_Phase,
) error {
	if featureflag.PraefectSerializedWrite.IsDisabled(ctx) {
		return nil
	}

	switch phase {
	case gitalypb.VoteTransactionRequest_PREPARING_PHASE:
		lock, err := mgr.repoWriteLockMgr.Lock(ctx, storageName, repoRelativePath, transactionID)
		if err != nil {
			return fmt.Errorf("try lock: %w", err)
		}
		mgr.repoLocks.Store(transactionID, lock)

	case gitalypb.VoteTransactionRequest_PREPARED_PHASE, gitalypb.VoteTransactionRequest_COMMITTED_PHASE:
		v, ok := mgr.repoLocks.Load(transactionID)
		if !ok {
			// No Preparing was cast for this transaction. This happens when Git itself drives
			// the reference-transaction hook on a Git build that doesn't emit "preparing"
			// (i.e. pre-2.54). Skip lock work; serialization is dormant for this path
			// until GIT_VERSION_PREV is bumped past 60d8c1e9.
			mgr.logger.WithFields(log.Fields{
				"transaction.id": transactionID,
				"phase":          phase.String(),
			}).DebugContext(ctx, "skipping lock check: no preparing phase recorded")
			return nil
		}
		lock := v.(datastore.RepoLock)
		if err := lock.Renew(ctx); err != nil {
			return err
		}
	}
	return nil
}

func (mgr *Manager) releaseRepoLockOnPhase(transactionID uint64, phase string) {
	v, ok := mgr.repoLocks.LoadAndDelete(transactionID)
	if !ok {
		return
	}
	logFields := log.Fields{
		"transaction.id": transactionID,
	}
	if phase != "" {
		logFields["phase"] = phase
	}
	lock := v.(datastore.RepoLock)
	if err := lock.Unlock(); err != nil {
		mgr.logger.WithError(err).WithFields(logFields).Error("release repo lock")
	}
}

func (mgr *Manager) releaseRepoLock(transactionID uint64) {
	mgr.releaseRepoLockOnPhase(transactionID, "")
}

// unlock releases the write lock held by txnID. It is a no-op if the lock is not currently held by txnID
// (e.g. it expired and was taken over by another transaction).
func (r *RepoReferenceWriteLockManager) unlock(virtualStorage string, relativePath string, txnID uint64) error {
	// unlock has its own context, because the lock must be released regardless of
	// the request's lifecycle. Don't use the caller's ctx because if the caller's request
	// context is cancelled (e.g. client disconnected, deadline exceeded), the request is
	// done but the lock row still exists in the database.
	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()

	query := `
DELETE FROM repository_reference_write_locks
WHERE lock_id = $1 AND holder_txn_id = $2;`
	lockID := repoLockID(virtualStorage, relativePath)
	start := time.Now()
	_, err := r.qc.ExecContext(ctx, query, lockID, txnID)
	r.operationDuration.WithLabelValues(virtualStorage, "unlock").Observe(time.Since(start).Seconds())

	if err != nil {
		return fmt.Errorf("release repo reference write lock: %s, %w", lockID, err)
	}

	if acquiredAt, ok := r.lockAcquiredAt.LoadAndDelete(lockID); ok {
		r.locksHeld.WithLabelValues(virtualStorage).Dec()
		r.lockHoldDuration.WithLabelValues(virtualStorage).Observe(time.Since(acquiredAt.(time.Time)).Seconds())
	}
	return nil
}

// Stop connects to the given server and stops the transaction identified by tx.
func (m *PoolManager) Stop(ctx context.Context, tx txinfo.Transaction) error {
	client, err := m.getTransactionClient(ctx, tx)
	if err != nil {
		return err
	}

	if _, err := client.StopTransaction(ctx, &gitalypb.StopTransactionRequest{
		TransactionId: tx.ID,
	}); err != nil {
		m.logger.WithFields(log.Fields{
			"transaction.id":    tx.ID,
			"transaction.voter": tx.Node,
		}).ErrorContext(ctx, "stopping transaction failed")

		return err
	}

	return nil
}
