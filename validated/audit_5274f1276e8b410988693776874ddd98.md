### Title
Buffer over-read in ijar's ZIP central-directory parser when processing an attacker-published JAR dependency - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` reads length-prefixed fields (`file_name_length`, `extra_field_length`, `file_comment_length`, and per-record `data_size` in the zip64 extra field loop) directly from the mmap'd input file and advances the cursor `p`/`extra_p` by attacker-controlled amounts with **no bounds checking against the mapped buffer size**, unlike the sibling function `InputZipFile::ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before every variable-length read [1](#0-0) . The central-directory parser has no equivalent check [2](#0-1) .

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` as raw `u2` values from attacker-controlled bytes, then does:
```
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  ...
  extra_p += data_size;
}
p += file_comment_length;
``` [3](#0-2) 

None of these advances are checked against the remaining length of the mmap'd input buffer. The comment above the function claims "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" [4](#0-3) , but this assumption only holds for a well-formed zip; a crafted `file_name_length`/`extra_field_length`/`data_size` can push `p`/`extra_p` past the end of the mapped region (`zipdata_in_` + file length), and the inner `while (extra_p != p)` loop can also fail to terminate correctly if `data_size` values don't align `extra_p` back to `p`, causing repeated reads past the buffer.

Contrast this with `EnsureRemaining()`, used throughout `ProcessLocalFileEntry`/`SkipFile`/`ProcessFile`, which validates that `n` bytes remain before reading [5](#0-4) . That invariant is missing in the central-directory path, which is invoked once per central-directory entry via `CalculateOutputLength()` [6](#0-5)  and by ijar's own entry-walking logic in `third_party/ijar/ijar.cc`.

This is directly analogous to the FAAD2 bug class: a length/index value taken from untrusted input is used to compute a read offset without validating it stays within the allocated buffer, producing a heap/mmap buffer over-read (`ps_mix_phase` reads relative to an untrusted index in FAAD2; here `p`/`extra_p` advance by an untrusted length with no remaining-bytes check).

The reachable attacker surface: ijar is invoked by Bazel's Java toolchain to build interface jars from `.jar` inputs, including third-party JARs fetched via `http_jar`/`http_archive`/`maven_install`-style rules and pulled in as `deps` of `java_library`/`java_import`. A malicious jar published at a URL a victim's `MODULE.bazel`/`WORKSPACE` resolves (with or without an incorrect/omitted `sha256`) is fed into ijar's zip parser during normal compilation, exercising `ProcessCentralDirEntry` on attacker-controlled bytes.

### Impact Explanation
An out-of-bounds read past the mapped input file can crash the Bazel build process (SIGSEGV reading unmapped pages past the mmap'd region) or, in a memory layout where adjacent process memory is mapped and accessible, leak bytes from adjacent memory into ijar's internal state (`filename` buffer via `memcpy`) which is then written into the interface jar's central directory/filename fields — a mechanism by which fragments of process memory can leak into a build artifact. This is a memory-safety violation (over-read) in native C++ code triggered by attacker-supplied archive content, matching the "buffer over-read" class of the referenced FAAD2 CVE.

### Likelihood Explanation
Ijar processes every `.jar` dependency during ordinary Java compilation and interface-jar generation, so any project consuming a third-party jar (a common, low-friction attack vector: a malicious or compromised jar hosted at a dependency URL) will run this code path automatically, without special build flags. No credentials, MITM, or trusted-repo Starlark access are required — only that the victim's build fetches and compiles against an attacker-controlled `.jar`.

### Recommendation
Add remaining-bytes validation (an `EnsureRemaining`-style check against `central_dir_ + central_dir_size` / the mmap'd buffer end) before every advance of `p` and `extra_p` in `ProcessCentralDirEntry`, mirroring the checks already present in `ProcessLocalFileEntry`. Additionally bound the zip64 extra-field loop so `data_size` cannot push `extra_p` past `p`, and treat any out-of-range length as a corrupt-archive error rather than proceeding to read.

### Proof of Concept
I could not verify a concrete, buildable JUnit/shell reproduction within the available tool budget — this would require constructing a crafted `.jar`/`.zip` with a central-directory entry whose `file_name_length`/`extra_field_length`/zip64 `data_size` fields point past the end of the file and confirming (e.g., under ASan) that `ijar`/`CalculateOutputLength` reads out of bounds. This is an area a background agent with build/test tooling should confirm, since I cannot execute the ijar binary or a fuzzer/ASan build from static analysis alone. I recommend a Devin session be used to (1) construct such a malformed zip, (2) run `ijar` (or `singlejar`) against it under AddressSanitizer, and (3) add a regression test (likely in `third_party/ijar/zip_test.cc` or `test/...`) asserting graceful error handling instead of an out-of-bounds read.

  // Check that at least n bytes remain in the input file, otherwise
  // abort with an error message.  "state" is the name of the field
  // we're about to read, for diagnostics.
  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
  }

```text
bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}

u8 InputZipFile::CalculateOutputLength() {
  const u1* current = central_dir_;

  u8 compressed_size = 0;
  u8 uncompressed_size = 0;
  u8 skipped_compressed_size = 0;
  u4 attr;
  u8 offset;
  char filename[PATH_MAX];

  while (true) {
    u8 file_compressed, file_uncompressed;
    if (!ProcessCentralDirEntry(current,
                                &file_compressed, &file_uncompressed,
                                filename, PATH_MAX, &attr, &offset)) {
      break;
    }

    if (processor->Accept(filename, attr)) {
      compressed_size += (u8) file_compressed;
      uncompressed_size += (u8) file_uncompressed;
    } else {
      skipped_compressed_size += file_compressed;
    }
  }

  // The worst case is when the output is simply the input uncompressed. The
  // metadata in the zip file will stay the same, so the file will grow by the
  // difference between the compressed and uncompressed sizes.
  return (u8) input_file_->Length() - skipped_compressed_size
      + (uncompressed_size - compressed_size);
}
