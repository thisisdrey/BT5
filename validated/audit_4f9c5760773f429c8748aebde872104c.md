### Title
Missing minimum share check enables Vesper deposit sandwiching - (File: `contracts/VesperGateway.sol`)

### Summary
`VesperGateway.deposit()` accepts only a Metronome pool, a Vesper `vToken`, and the underlying-token amount; it does not let the user specify a minimum acceptable amount of `vToken`/`msdToken` output [1](#0-0) . The function deposits the pulled underlying into the attacker-reachable Vesper pool, measures the resulting `vToken` balance delta, and deposits that amount into Metronome without any slippage check [2](#0-1) .

### Finding Description
A user first approves the underlying asset to `VesperGateway` and submits `deposit(pool_, vToken_, amount_)`. Before the transaction executes, an attacker can manipulate the share price of the specified registered `vToken`, for example by holding vault shares and donating underlying assets or otherwise increasing the vault’s reported value. The victim’s fixed `amount_` then mints fewer `vToken` shares than expected.

The gateway records only the post-deposit balance delta and immediately passes it to `DepositToken.deposit()` [3](#0-2) . Metronome mints deposit tokens based solely on the received `vToken` quantity and the configured deposit fee [4](#0-3) [5](#0-4) . Therefore, all loss caused by unfavorable Vesper share pricing is passed through to the depositor.

### Impact Explanation
The user permanently loses part of the value deposited because fewer vault shares—and consequently fewer `msdToken` collateral shares—are minted than expected. When the manipulation is caused by a contribution that accrues to existing `vToken` holders, the attacker can redeem their existing shares after the victim deposits and recover the donated value plus part of the victim’s contribution.

This is a direct loss of user funds rather than merely unexpected execution: neither `VesperGateway.deposit()` nor `DepositToken.deposit()` gives the depositor a minimum-output bound [2](#0-1) [6](#0-5) .

### Likelihood Explanation
Any unprivileged user holding or able to obtain `vToken` shares can attempt the sandwich. The target `vToken` cannot be a fake token because it must map to a registered `DepositToken` through `pool_.depositTokenOf(vToken_)`, but a valid whitelisted Vesper collateral is sufficient [7](#0-6) .

The attack does not require governance, keeper access, oracle corruption, or malformed Metronome tokens. Profitability requires the attacker to control a sufficiently large fraction of the `vToken` supply before donating/manipulating its share price; otherwise, the donation may benefit other vault shareholders more than the attacker.

### Recommendation
Add minimum-output parameters to `VesperGateway.deposit()`, preferably checking both boundaries:

```solidity
function deposit(
    IPool pool_,
    IVPool vToken_,
    uint256 amount_,
    uint256 vTokenAmountMin_,
    uint256 depositAmountMin_
) external;
```

After `vToken_.deposit(amount_)`, revert if `_vTokenAmount < vTokenAmountMin_`. Likewise, require `_deposited >= depositAmountMin_` after calling `DepositToken.deposit()`. A combined minimum may also be acceptable, but checking the Vesper share amount directly provides clearer protection against external vault slippage [3](#0-2) .

### Proof of Concept
A Hardhat fork test can reproduce the issue against a supported Vesper pool:

```ts
it('sandwiches VesperGateway.deposit', async () => {
  // Fork state provides:
  // pool, poolRegistry, usdc, vaUSDC, msdVaUSDC, user, attacker
  const gatewayFactory = await ethers.getContractFactory('VesperGateway')
  const gateway = await gatewayFactory.deploy(poolRegistry.address)

  const attackerUnderlying = parseUnits('1000000', 6)
  const donation = parseUnits('100000', 6)
  const victimUnderlying = parseUnits('10000', 6)

  // Attacker becomes the dominant shareholder in the real vToken.
  await usdc.connect(attacker).approve(vaUSDC.address, attackerUnderlying)
  await vaUSDC.connect(attacker).deposit(attackerUnderlying)
  const attackerShares = await vaUSDC.balanceOf(attacker.address)

  const supplyBefore = await vaUSDC.totalSupply()
  const victimSharesBeforeDonation =
    victimUnderlying.mul(supplyBefore).div(await vaUSDC.totalValue())

  // Front-run: donation raises price per share / total value.
  await usdc.connect(attacker).transfer(vaUSDC.address, donation)

  // Victim's pending transaction executes without any minimum-output check.
  await usdc.connect(user).approve(gateway.address, victimUnderlying)
  await gateway.connect(user).deposit(pool.address, vaUSDC.address, victimUnderlying)

  const victimMsd = await msdVaUSDC.balanceOf(user.address)

  // The victim receives materially fewer msdTokens than the pre-donation quote.
  expect(victimMsd).lt(victimSharesBeforeDonation)

  // Back-run: the attacker redeems vault shares and captures the donated value
  // plus the value lost by the victim's reduced share issuance.
  await vaUSDC.connect(attacker).withdraw(attackerShares)
})
```

The exact helper for reading vault value may be `totalValue()`, `pricePerShare()`, or another Vesper-version-specific view, but the tested invariant is unchanged: the victim’s minted `msdToken` balance is lower after the attacker’s same-transaction-class share-price manipulation, while the unmodified gateway accepts the result unconditionally [3](#0-2) .
