### No vulnerability found for this question.

This behavior is confirmed as intentional and correctly documented, not a bug. The code at `runtime/runtime/src/actions.rs:489-491` explicitly copies `signer_id`/`signer_public_key` from the outer `action_receipt` (the relayer's identity) into the newly generated `ActionReceipt`, while `predecessor_id` is set to `sender_id.clone()` (the DelegateAction's sender) at line 485. [1](#0-0) 

This is explicitly called out in the code comments immediately following: "Note, Relayer prepaid all fees... Gas is refunded to the signer, this is Relayer... deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction." This documents the intended NEP-366 semantic split: `signer_id` = relayer (who paid gas/fees), `predecessor_id` = `sender_id` (the delegator, per `Receipt.predecessor_id`). [2](#0-1) 

The unit test `test_delegate_action` in the same file directly asserts this exact mapping — the generated receipt's `signer_id`/`signer_public_key` equal the outer `action_receipt`'s (relayer) values, while `predecessor_id` equals `sender_id` (the DelegateAction's sender) — confirming there is no accidental swap. [3](#0-2) 

Since `env::signer_account_id()` is populated from `ActionReceipt.signer_id` and `env::predecessor_account_id()` from `Receipt.predecessor_id`, this is precisely the documented NEP-366 outcome: signer = relayer, predecessor = sender. There is no runtime bug here — a contract that authorizes on `signer_account_id()` instead of `predecessor_account_id()` is exhibiting a known contract-side anti-pattern (explicitly warned against in NEP-366 documentation), not a runtime identity-propagation flaw. This falls outside the scope of a runtime vulnerability since the field assignment matches the documented, tested, and intended protocol spec.
