### Title
Shielded key material (spending key, expanded spending key, nsk, ovk, ivk/ak/nk) accepted via HTTP GET query parameters — sensitive data exposure analog to CVE-2020-7932 - ([File: framework/src/main/java/org/tron/core/services/http/GetExpandedSpendingKeyServlet.java])

### Summary
Multiple full-node HTTP servlets that handle Sapling/shielded key material accept the secret value as a `GET` query-string parameter in addition to `POST` body, e.g. `GetExpandedSpendingKeyServlet` (`value` = spending key), `GetNkFromNskServlet` (`value` = nsk), `ScanNoteByOvkServlet`/`ScanShieldedTRC20NotesByOvkServlet` (`ovk`), `GetIncomingViewingKeyServlet` (`ak`, `nk`), and `GetZenPaymentAddressServlet` (`ivk`). This mirrors the OMERO-web CWE-200 pattern (CVE-2020-7932) where sensitive tokens passed as URL query parameters end up recorded in access logs, proxy caches, browser history, and can be leaked via `Referer` headers when a link containing them is followed.

### Finding Description
`doGet` handlers read raw secret key material directly from `HttpServletRequest.getParameter(...)`: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

Unlike POST bodies, GET query strings are:
- Recorded verbatim in web-server, reverse-proxy, and load-balancer access logs (a very common production deployment in front of a full node's HTTP API).
- Cached by intermediate proxies/CDNs.
- Stored in browser history if any operator tooling issues these requests from a browser-based console.
- Forwarded in the `Referer` header to any third-party resource loaded from a page that issued the request, exactly the mechanism described in the OMERO advisory.

The Sapling spending key (`sk`) and its derived expanded spending key (`ask`, `nsk`, `ovk`) are the full spend authority for shielded notes; the outgoing viewing key (`ovk`) and incoming viewing key (`ivk`)/`ak`/`nk` allow decrypting shielded note contents. None of these code paths mark the endpoint as POST-only or reject GET, so any client (including a browser-based dApp or wallet UI that constructs one of these URLs) that submits this secret via `GET` causes it to be persisted outside the immediate request/response boundary.

### Impact Explanation
If an operator, wallet UI, or diagnostic tool submits a spending key, nsk, or ovk via one of these GET endpoints (which the code explicitly supports), the secret is exposed to anyone with access to HTTP/proxy access logs, log aggregation pipelines, browser history, or a `Referer`-leak chain. This constitutes key disclosure, one of the explicitly accepted high-impact outcomes, and directly enables theft of shielded TRX/TRC20 funds by an attacker who obtains the leaked spending key.

### Likelihood Explanation
Likelihood is moderate: the vulnerable code paths are reachable by any client of the full node's public JSON/HTTP wallet API (no authentication is required by these endpoints), and the API explicitly supports `GET` for these sensitive operations, making exploitation a matter of operational misuse (browser-based tooling, curl history, shared/reverse-proxied nodes) rather than requiring a flaw in cryptography. It requires a user/tool to actually invoke the GET variant with the secret, which is a design flaw enabling exposure rather than a directly remotely triggerable extraction of another party's key.

### Recommendation
Remove `doGet` support (or reject GET requests) for all shielded-key-handling servlets (`GetSpendingKeyServlet`, `GetExpandedSpendingKeyServlet`, `GetNkFromNskServlet`, `ScanNoteByOvkServlet`, `ScanShieldedTRC20NotesByOvkServlet`, `GetIncomingViewingKeyServlet`, `GetZenPaymentAddressServlet`, and their PBFT/Solidity counterparts), requiring clients to submit secret material only via POST bodies, and document that these debug/utility shielded-key endpoints should not be exposed on publicly reachable or proxied full-node HTTP interfaces.

### Proof of Concept
```
GET /wallet/getexpandedspendingkey?value=<64-hex-char-spending-key>&visible=true HTTP/1.1
Host: victim-fullnode:8090
```
This request causes the spending key to appear in the URL, and thus in any HTTP access log, reverse proxy log, or (if issued from a browser context) potentially in the `Referer` header of subsequent same-origin resource loads — an analog of the OMERO-web CVE-2020-7932 sensitive-data-in-URL exposure.
