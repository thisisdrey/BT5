### Title
Unprotected AMM swap in Snowbridge `system-frontend`'s tip/fee burn path allows sandwich-induced value loss on `add_tip`/`register_token` - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

### Summary
The Snowbridge `system-frontend` pallet exposes two unprivileged, signed public extrinsics — `register_token` and `add_tip` — that both route through `swap_fee_asset_and_burn` → `swap_and_burn`. This helper swaps the user-supplied fee/tip asset for Ether using `T::Swap::swap_exact_tokens_for_tokens` with the `amount_out_min` parameter hardcoded to `None`, i.e. no minimum-output protection at all, exactly matching the "hardcoded zero minimum-amount-out" pattern flagged in the external ConvexStrategy report. Because these are ordinary user extrinsics visible in the public mempool (not Gelato-keeper-only, admin-only, or otherwise privately relayed), an attacker can sandwich the swap and force the AMM pool used for tip/fee conversion to return a deflated `ether_gained`, which is then burned and forwarded on-chain as the actual fee/tip amount funding Ethereum-side execution or relayer rewards — while the victim's full input asset amount is still consumed.

### Finding Description
`swap_and_burn` performs the core value conversion for both entry points: [1](#0-0) 

The call `T::Swap::swap_exact_tokens_for_tokens(..., None, ...)` passes `None` for `amount_out_min` with an explicit comment "No minimum amount required." This means the underlying `pallet_asset_conversion` swap (see `Swap::swap_exact_tokens_for_tokens` / `do_swap_exact_tokens_for_tokens`) is executed with zero slippage protection: [2](#0-1) 

This function is invoked from two public, signed dispatchables:

- `add_tip`, callable by any signed account with an arbitrary `Asset` to swap for Ether: [3](#0-2) 

- `register_token`, which also swaps a user-supplied `fee_asset` for Ether whenever the origin is not "here": [4](#0-3) 

Unlike Gelato-keeper-only or privately-relayed swaps mentioned in the external report as being safe from sandwiching, these transactions are ordinary user-submitted extrinsics that sit in the public transaction pool before inclusion. The resulting `ether_gained` (the swap output) is used unmodified as the amount burned via `burn_for_teleport` and as the `amount` field forwarded to BridgeHub in `EthereumSystemCall::RegisterToken`/`EthereumSystemCall::AddTip`: [5](#0-4) 

No downstream check re-validates that `ether_gained` is reasonable relative to the amount of fee/tip asset that was withdrawn — the pallet only guards against a literal zero `fee_amount`: [6](#0-5) 

### Impact Explanation
The `ether_gained` value is not a cosmetic quantity — it directly becomes:
1. The amount of Ether burned for teleportation to Ethereum funding execution of `register_token` on the Ethereum side, or
2. The relayer tip amount reported to BridgeHub's reward/payout accounting via `AddTip`.

If this value is artificially deflated by a sandwich attack, the caller's full fee/tip asset balance is consumed (withdrawn/burned) but the corresponding Ether-denominated value credited toward bridge execution funding or relayer reward is short-changed relative to the fair market rate. This directly violates the required invariant that "bridge rewards... and contract-held value must conserve value and settle exactly once to the rightful beneficiary and amount," and can also cause "public underpriced work that degrades... stalls bridge processing" if a `register_token` message is sent to Ethereum with insufficient fee coverage due to the sandwiched conversion.

### Likelihood Explanation
Both `add_tip` and `register_token` are unprivileged, signed extrinsics reachable by any account holding a swappable fee/tip asset — no governance, admin, validator, or relayer compromise is required. The only precondition is that the fee/tip asset trades against Ether through a `pallet_asset_conversion` pool with attacker-accessible liquidity, which is the expected normal configuration for this feature. Any observer of the public transaction pool can trivially construct the standard sandwich (buy-before/sell-after) around the victim's extrinsic.

### Recommendation
Do not pass `None` for `amount_out_min` in `swap_and_burn`. Compute an acceptable minimum output (e.g., via `QuotePrice::quote_price_exact_tokens_for_tokens` at call time, or an explicit user-supplied `min_ether_out` parameter added to `add_tip`/`register_token`) and pass it into `swap_exact_tokens_for_tokens`, causing the extrinsic to fail (and roll back, since it's not privileged/atomic-committed value burn) rather than silently accept a sandwiched, unfavorable rate.

### Proof of Concept
1. Alice submits `add_tip(message_id, asset)` where `asset` = 1000 units of `TokenX`, expecting a fair-market swap into, say, 10 ETH-equivalent based on current pool reserves.
2. Eve observes Alice's pending extrinsic in the transaction pool.
3. Eve front-runs with a large `TokenX → Ether` swap (via the same `pallet_asset_conversion` pool, using `swap_exact_tokens_for_tokens`/precompile or a router) to push the pool price of Ether up relative to TokenX.
4. Alice's `add_tip` executes: `T::Swap::swap_exact_tokens_for_tokens(..., None, ...)` inside `swap_and_burn` accepts whatever output the now-skewed pool gives — e.g., only 6 ETH-equivalent instead of 10 — because there is no `amount_out_min` guard.
5. Eve back-runs, swapping Ether back to TokenX, capturing the price difference as profit and leaving Alice's `ether_gained` (and therefore the tip amount later credited on BridgeHub via `AddTip`) permanently deflated relative to the value she actually paid in `TokenX`.
6. Alice's full 1000 `TokenX` was consumed, but the bridge reward/burn accounting only reflects 6 ETH-equivalent instead of the fair 10 ETH-equivalent — a silent, un-refunded value loss enabled purely by the hardcoded `None` minimum-out.

		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
