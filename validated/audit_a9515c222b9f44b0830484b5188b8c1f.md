### Title
Reference-transaction hook fires against unmigrated quarantined objects during FetchRemote - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
In `fetchRemoteAtomic`, the "prepared" phase of the reference-transaction hook (and any Praefect vote/callback it triggers) is executed while fetched objects are still isolated in the quarantine directory, because `refUpdater.Prepare()` runs before `quarantineDir.Migrate(ctx)`.

### Finding Description
The established safe pattern in Gitaly, documented in `doc/hooks.md` and `doc/object_quarantine.md`, and implemented correctly in `UpdaterWithHooks.UpdateReference`, is: run `PreReceiveHook` → `quarantineDir.Migrate(ctx)` → *then* drive the reference-transaction hook via `Prepare()`/`Commit()`. [2](#0-1) 

`fetchRemoteAtomic` inverts this ordering for the main `refUpdater`: it calls `refUpdater.Prepare()` (which locks references and, since transactions are not disabled, fires the "preparing"/"prepared" states of the reference-transaction hook via `gitcmd.WithRefTxHook`) *before* calling `quarantineDir.Migrate(ctx)`. [3](#0-2) 

This is the same bug class as the reported issue: a callback (the reference-transaction hook, which for a Praefect-managed cluster casts a vote and can invoke `RecordInitialReferenceValues`/`ResolveRevision` against the repository) executes in the middle of the operation, before the state update that the rest of the logic depends on (migrating quarantined objects into the main object database) has completed. `internal/gitaly/hook/referencetransaction.go` shows that the "prepared" phase actively resolves/records reference values and that "committed" phase updates transaction state — both of which assume a consistent, finalized object store. [4](#0-3) 

### Impact Explanation
If quarantine migration fails or is delayed after `Prepare()` has already fired the "prepared" vote/callback, other Gitaly nodes (in a Praefect-managed cluster) may already consider the transaction as prepared/voted while this node's objects are not yet visible in the main object database. Since `doc/hooks.md` explicitly documents that receive-pack-style hook rejection *after* a vote has been cast can cause secondary nodes to hang waiting for a "committed" vote until RPC timeout, this ordering flaw in `fetchRemoteAtomic` could produce inconsistent cluster state or a hung transaction/DoS on the RPC handler if `quarantineDir.Migrate(ctx)` errors out between `Prepare()` and `Commit()`. [5](#0-4) 

### Likelihood Explanation
`FetchRemote` is reachable by any user with mirror/fetch privileges on a repository, and the ordering is deterministic code, not a race — every invocation with quarantined objects goes through `Prepare()` before `Migrate()`. However, actually triggering the failure mode requires `quarantineDir.Migrate(ctx)` to fail after `Prepare()` succeeds (e.g., disk error, permission issue), which is a less common condition, reducing likelihood of the concrete impact even though the unsafe ordering itself is always present.

### Recommendation
Reorder `fetchRemoteAtomic` so that `quarantineDir.Migrate(ctx)` is called before `refUpdater.Prepare()`, consistent with the pattern in `UpdaterWithHooks.UpdateReference`, ensuring the reference-transaction hook only fires once quarantined objects have already been migrated into the main object database.

### Proof of Concept
Not executable from the index alone — this is a code-ordering/control-flow finding derived from comparing `fetch_remote.go`'s `Prepare()`→`Migrate()`→`Commit()` sequence against the documented and enforced safe sequence in `update_with_hooks.go` (`Migrate()` before any `Prepare()`/hook invocation). I was not able to verify at runtime whether a real Praefect vote failure during this window causes an observable hang, since that requires a live multi-node cluster test which is outside the scope of static code review. [6](#0-5)

// New returns a new bulk updater, wrapping a `git update-ref` process. Call the
// various methods to enqueue updates, then call Commit() to attempt to apply all
// the updates at once.
//
// It is important that ctx gets canceled somewhere. If it doesn't, the process
// spawned by New() may never terminate.
func New(ctx context.Context, repo gitcmd.RepositoryExecutor, opts ...UpdaterOpt) (*Updater, error) {
	var cfg updaterConfig
	for _, opt := range opts {
		opt(&cfg)
	}

	objectHash, err := repo.ObjectHash(ctx)
	if err != nil {
		return nil, fmt.Errorf("detecting object hash: %w", err)
	}

	txOption := gitcmd.WithRefTxHook(objectHash, repo)
	if cfg.disableTransactions {
		txOption = gitcmd.WithDisabledHooks()
	}

	cmdFlags := []gitcmd.Option{gitcmd.Flag{Name: "-z"}, gitcmd.Flag{Name: "--stdin"}}
	if cfg.noDeref {
		cmdFlags = append(cmdFlags, gitcmd.Flag{Name: "--no-deref"})
	}

	var stderr bytes.Buffer
	cmd, err := repo.Exec(ctx,
		gitcmd.Command{
			Name:  "update-ref",
			Flags: cmdFlags,
		},
		txOption,
		gitcmd.WithSetupStdin(),
		gitcmd.WithSetupStdout(),
		gitcmd.WithStderr(&stderr),
	)
	if err != nil {
		return nil, err
	}

**File:** doc/hooks.md (L187-196)
```markdown
While the reference-transaction hook executes on all Gitaly nodes, the
receive-pack style hooks only run on a single Gitaly, which is the primary node.
It can thus happen that receive-pack style hooks reject the update on the
primary node, which is not something the secondary nodes would see. The result
is that secondaries would now hang until the timeout for the RPC call triggers
given that the primary is never going to vote on this transaction.

To fix the hang, transactions support graceful stops: if the primary node fails
the RPC call in code that is only executed on the primary, then it will stop the
transaction and thus tell other Gitaly nodes to stop waiting for quorum.
```
