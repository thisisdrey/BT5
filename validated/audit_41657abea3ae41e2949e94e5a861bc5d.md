Audit Report

## Title
Outbound Queue `calculate_fee` Can Round a Non-Zero Remote (Ethereum) Delivery Fee Down to Zero, Allowing Underpriced Bridge Messages - (File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs)

## Summary
`Pallet::<T>::calculate_fee` and its helper `convert_from_ether_decimals` use plain floor-division (`checked_div`) when converting the ether-denominated remote fee into native currency, with no rounding-up or minimum-fee enforcement. This confirmed by the pallet's own regression test can truncate a legitimate non-zero remote fee to `0`, and `SendMessage::validate` in `send_message_impl.rs` accepts and enqueues such messages without any check on `fee.remote`.

## Finding Description
`calculate_fee` computes the remote fee via `calculate_remote_fee` (ether units), downcasts to `u128`, scales by `multiplier`/`exchange_rate` through `FixedU128`, and finally applies `convert_from_ether_decimals`, which does `value.checked_div(denom)` where `denom = 10^(18 - T::Decimals)`. [1](#0-0) [2](#0-1) 

The pallet's own test demonstrates that with non-degenerate parameters (`exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards.remote = 1`, `multiplier = 1/1`, `gas_used = 250000`), `fee.remote` computes to `0` while `fee.local` is non-zero, with the test comment explicitly noting this is an "invalid" result that "should be avoided." [3](#0-2) 

`SendMessage::validate` calls `calculate_fee` and returns the resulting `Fee { local, remote }` with no assertion that `remote > 0`; `deliver` then unconditionally enqueues the ticket via `T::MessageQueue::enqueue_message`. [4](#0-3) 

## Impact Explanation
This confirms a genuine arithmetic-truncation defect that the pallet's maintainers have already flagged in their own test as invalid/undesirable behavior. However, I was not able to confirm within the repository that this V1 outbound-queue pallet (`bridges/snowbridge/pallets/outbound-queue`) is the code path relayers/rewards actually depend on for economic incentive in the currently deployed configuration. The codebase also contains a newer V2 outbound-queue design (`outbound-queue-v2`, `pallet_bridge_relayers`, `PayAccountOnLocation`) with a substantially different, off-chain fee-estimation and on-chain reward-registration model (`process_delivery_receipt`, `register_relayer_reward`) that does not appear to rely on this V1 `calculate_fee`/`convert_from_ether_decimals` conversion path at all. Since the runtime configurations examined (bridge-hub-westend v2 tests) use the V2 reward flow, it is unclear whether the V1 `calculate_fee` truncation is exercised by any currently live, in-scope bridge configuration, which is required to establish that this "stalls bridge processing" per the impact gate.

## Likelihood Explanation
Assuming the V1 outbound-queue pallet is live in a target BridgeHub runtime, any unprivileged account that can submit a message via a registered channel (XCM export or system pallet `send`) reaching `SendMessage::validate` would trigger `calculate_fee` with governance-set `PricingParameters`, and low-gas commands could produce a truncated-to-zero `remote` fee under ordinary, non-malicious parameter settings — no privileged action or malicious actor required.

## Recommendation
Apply ceiling (round-up) division in `convert_from_ether_decimals`, or add an explicit `ensure!(!fee.remote.is_zero(), ...)` / minimum-fee floor in `calculate_fee` or `SendMessage::validate` to reject or floor zero-priced remote fees before the message is enqueued for delivery to Ethereum.

## Proof of Concept
The existing unit test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` reproduces the exact truncation: with `exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards.remote = 1`, `multiplier = 1/1`, `gas_used_at_most = 250000`, `calculate_fee` returns `fee.remote == 0` and `fee.local == 698000000`. [3](#0-2) 
Since `send_message_impl.rs::validate` performs no check on `fee.remote` [5](#0-4) 
such a message would be validated and enqueued for delivery to Ethereum with zero compensation reserved for the relayer's remote-side costs, contingent on the V1 outbound-queue pallet being the actively deployed fee-charging path in the target runtime — a condition I was unable to fully verify from the available code and would need confirmation via a live Devin session inspecting the actual runtime pallet wiring (`Runtime` config for `EthereumOutboundQueue` vs `EthereumOutboundQueueV2`) to establish in-scope applicability.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}

fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {

		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {

			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}

	fn deliver(ticket: Self::Ticket) -> Result<H256, SendError> {
		let origin = AggregateMessageOrigin::Snowbridge(ticket.channel_id);

		if ticket.channel_id != PRIMARY_GOVERNANCE_CHANNEL {
			ensure!(!Self::operating_mode().is_halted(), SendError::Halted);
		}

		let message = ticket.message.as_bounded_slice();

		T::MessageQueue::enqueue_message(message, origin);
		Self::deposit_event(Event::MessageQueued { id: ticket.message_id });
		Ok(ticket.message_id)
	}
