### Title
Per-connection unstaked stream throttling in `ConnectionStreamCounter`/`throttle_stream` allows aggregate rate amplification via connection churn - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`throttle_stream` enforces `max_streams_per_throttling_interval` against a `ConnectionStreamCounter` that is created fresh per-connection [1](#0-0) , and the unstaked budget itself (`max_unstaked_load_in_throttling_window`, derived from the global `MAX_UNSTAKED_TPS` constant) is applied identically to every unstaked connection rather than divided or shared per source IP [2](#0-1) . Because the SwQoS layer only limits the *count* of concurrent unstaked connections per peer (`max_connections_per_unstaked_peer`) and total unstaked connections (`max_unstaked_connections`), but not an aggregate per-IP stream rate, an attacker can open multiple unstaked connections from one IP, each independently getting a fresh `MAX_UNSTAKED_TPS`-equivalent stream budget.

### Finding Description
`ConnectionStreamCounter::new()` initializes `stream_count` to 0 per connection [3](#0-2) , and a new instance is created via the `try_add_connection` closure every time a new connection is accepted and cached [1](#0-0) . `on_new_stream` fetches this per-connection counter from `SwQosConnectionContext` and calls `throttle_stream` with `max_streams_per_throttling_interval` computed for the connection's peer type [4](#0-3) . `throttle_stream` only compares `stream_counter.stream_count` (scoped to that one connection) against the cap and sleeps if it's exceeded [5](#0-4) , so the throttling state never aggregates across connections from the same IP or pubkey-less peer.

For unstaked peers, the available budget per throttling interval is `max_unstaked_load_in_throttling_window = MAX_UNSTAKED_TPS * STREAM_THROTTLING_INTERVAL_MS / 1000`, a fixed constant independent of how many unstaked connections exist [2](#0-1) [6](#0-5) . `StakedStreamLoadEMA::increment_load` — the only global load-tracking mechanism — updates state only for staked peers (`if peer_type.is_staked()`), never for unstaked peers [7](#0-6) , confirming unstaked traffic has no shared/aggregate accounting at all.

The only limits that scale with connection count for unstaked peers are `max_connections_per_unstaked_peer` (per-IP connection cap) and `max_unstaked_connections` (global unstaked connection cap, subject to LRU pruning) enforced in `SwQos::try_add_connection` / `prune_unstaked_connections_and_add_new_connection` [8](#0-7) [9](#0-8) . Neither of these caps limits the *aggregate stream rate* per IP — they only cap connection count, and each connection independently gets its own `MAX_UNSTAKED_TPS`-scale budget. Thus with `max_connections_per_unstaked_peer = N`, a single attacker IP can drive roughly `N * MAX_UNSTAKED_TPS` streams/sec into the ingress pipeline, not `MAX_UNSTAKED_TPS` as intended by the per-source unstaked rate limit design.

### Impact Explanation
This is a QoS-evasion / remote DoS amplification against banking-stage ingress: the unstaked stream-rate cap (`MAX_UNSTAKED_TPS`) is meant to bound how much unprivileged, unstaked traffic a single source can inject, but it can be multiplied by opening additional short-lived connections up to `max_connections_per_unstaked_peer` from the same IP, since throttling state resets per connection. This falls under the "QoS evasion" / remote DoS on validator ingress bounty category rather than a memory-safety or consensus bug.

### Likelihood Explanation
Feasibility depends entirely on the deployed value of `max_connections_per_unstaked_peer` (`SwQosConfig::max_connections_per_unstaked_peer`, default `DEFAULT_MAX_QUIC_CONNECTIONS_PER_UNSTAKED_PEER`). If this default is small (e.g. 1), the amplification factor is negligible and the finding has little real-world impact; if it is larger, the attacker can multiply the unstaked TPS budget by that factor merely by opening that many concurrent QUIC connections, which requires no special privilege — just being an unstaked remote client. I was unable to confirm the exact default value of `DEFAULT_MAX_QUIC_CONNECTIONS_PER_UNSTAKED_PEER` from the retrieved context, so the concrete amplification factor in a production deployment is uncertain and would need to be checked in `streamer/src/quic.rs`.

### Recommendation
Track and throttle unstaked stream rate aggregated per source IP (or per `ConnectionTableKey`) rather than per individual `ConnectionStreamCounter`, e.g. by storing a shared `Arc<ConnectionStreamCounter>` (or a shared token bucket keyed by IP) across all connections from the same unstaked source, similar to how `ConnectionTable::try_add_connection` already keys connections by `ConnectionTableKey::new(ip, pubkey)`. Alternatively, scale `max_unstaked_load_in_throttling_window`/`MAX_UNSTAKED_TPS` division by the number of concurrently open connections from that peer, or reduce `max_connections_per_unstaked_peer` to 1 by default so per-connection throttling is equivalent to per-peer throttling.

### Proof of Concept
Integration test plan (extending `test_quic_server_multiple_connections_on_single_client_endpoint` style tests in `streamer/src/nonblocking/quic.rs`):
1. Configure `SwQosConfig { max_connections_per_unstaked_peer: N, max_unstaked_connections: N, ..default_for_tests() }` with `N > 1`.
2. From a single client IP, open `N` concurrent QUIC connections to the test server.
3. On each connection, open unistreams as fast as possible for a fixed wall-clock window (e.g. 1 second) and count `stats.total_new_streams` accepted (not throttled).
4. Assert that total accepted streams/sec is bounded by `MAX_UNSTAKED_TPS` (the intended per-IP aggregate cap), i.e.
   ```rust
   assert!(stats.total_new_streams.load(Ordering::Relaxed) as u64 <= MAX_UNSTAKED_TPS * measured_seconds + margin);
   ```
5. Expected current (buggy) behavior: accepted stream count scales roughly linearly with `N` (approaching `N * MAX_UNSTAKED_TPS`), violating the assertion and demonstrating the per-connection throttling can be bypassed via connection churn/parallelism.

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
