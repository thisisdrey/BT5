### Title
`UpdateReferences` RPC allows unprivileged ref writes that bypass pre-receive/update/post-receive hook enforcement, unlike push and `OperationService` code paths - (File: internal/gitaly/service/ref/update_references.go)

### Summary
The `RefService.UpdateReferences` RPC lets any caller with repository access atomically create, update, or delete arbitrary references, but unlike every other reference-mutating path in Gitaly it never invokes the Git hook chain (`pre-receive`, `update`, `reference-transaction`, `post-receive`). This mirrors the `send_nft`/`transfer_nft` asymmetry in the report: one code path enforces the gating logic (payment settlement / access control) while a second, functionally equivalent path reaches the same state-changing primitive without it.

### Finding Description
Gitaly has two structurally different ways to mutate references:

1. **Hook-enforced path** — `git-receive-pack` (via `PostReceivePack`/`SSHReceivePack`) and `OperationService` RPCs (`UserCommitFiles`, `UserMergeBranch`, etc.) all drive reference updates through `updateref.UpdaterWithHooks.UpdateReference`, which explicitly calls `PreReceiveHook`, `UpdateHook`, `ReferenceTransactionHook`, and `PostReceiveHook` around every ref change: [1](#0-0) . This is the mechanism GitLab relies on to call back into Rails' `/internal/allowed` endpoint for access checks (protected branches, permission checks, push rules), as documented in [2](#0-1) .

2. **Hook-bypassing path** — `RefService.UpdateReferences` builds a raw `updateref.Updater` directly via `updateref.New(ctx, repo)` and calls `Update`/`Commit` with no hook manager involved at all: [3](#0-2) [4](#0-3) . The RPC is declared as an ordinary `MUTATOR` in `ref.proto` with no additional restriction: [5](#0-4) , and it explicitly supports raceless force-creation, force-update, and deletion of arbitrary `refs/*` names, including `refs/heads/*`, via `old_object_id`/`new_object_id` semantics: [6](#0-5) .

Both paths ultimately call the same underlying `updateref.Updater` primitive (`internal/git/updateref/updateref.go`), but only the `UpdaterWithHooks`-driven path adds the pre-receive/update hook gating that GitLab's Rails layer uses to enforce protected-branch rules, push access checks, and custom server hooks. `UpdateReferences` reaches the identical end state (a moved/created/deleted ref) while skipping that gate entirely — the same "shared internal primitive, only one entrypoint enforces the check" pattern as the `_transfer_nft` vs. `transfer_nft`/`send_nft` case in the report.

### Impact Explanation
Any client authorized to call `RefService.UpdateReferences` on a repository (the RPC carries no additional authorization beyond standard repository-scoped access) can force-move, force-create, or delete any reference — including protected branches — without the pre-receive/update hooks ever running. Since GitLab's protected-branch/push-rule enforcement, and any admin-installed custom `pre-receive`/`update` hooks, live entirely inside those hooks (see `doc/hooks.md` description of `/internal/allowed`), an actor who can reach this RPC (e.g., through a compromised or overly-trusted Rails/Workhorse component, or any client with direct gRPC access) can bypass push protections that legitimate pushes and `OperationService` RPCs are subject to. This is a concrete hook/access-control bypass, analogous to the reported payment-settlement bypass.

### Likelihood Explanation
The RPC is a standard, generally-reachable `MUTATOR` RPC (no special ACL, feature flag, or "internal use only" annotation distinguishes it from other `RefService` write RPCs in the proto), and its doc comment frames it as a general-purpose "raceless" bulk ref-update mechanism, suggesting production callers (e.g., bulk provisioning/backup-restore tooling as seen referenced in `internal/backup/repository.go`) may invoke it. Any caller with the same repository-scoped credentials normally used for legitimate write RPCs can use it instead of the hook-enforced ones to skip access checks.

### Recommendation
Route `UpdateReferences` through the same `updateref.UpdaterWithHooks` mechanism used elsewhere (or explicitly restrict/flag it for trusted internal callers only, such as backup/restore, that are known to run pre-authorized under separate controls), so that all reference mutations that can affect protected refs are subject to the pre-receive/update/reference-transaction hook chain before being committed.

### Proof of Concept
1. Obtain a gRPC client authorized against a target repository (the same credential level required for other `RefService`/`OperationService` write RPCs).
2. Call `RefService.UpdateReferences` with an `Update` targeting `refs/heads/protected-branch`, setting `old_object_id` to the branch's current OID and `new_object_id` to an attacker-controlled commit (or `ZeroOID` to delete the branch).
3. Observe (as in the RPC's own test suite, e.g. `TestUpdateReferences` "forced branch update succeeds"/"forced branch deletion succeeds" cases in `internal/gitaly/service/ref/update_references_test.go`) that the update is committed directly via `updateref.Updater.Commit()` with no `PreReceiveHook`/`UpdateHook`/`PostReceiveHook` invocation, unlike the equivalent flow through `WriteRef`'s sibling `OperationService` RPCs or `git-receive-pack`, which would invoke `UpdaterWithHooks.UpdateReference` and thus call Rails' `/internal/allowed` and any custom hooks first.

There are two users of these hooks:

- `PostReceivePack` and `SSHReceivePack` directly invoke `git-receive-pack`,
  which then executes the hooks for us.
- Most RPCs in the `OperationService` that write objects into the repository
  manually invoke these hooks using the `updateref.UpdaterWithHooks` structure.

These hooks perform the following functions:

- `pre-receive`: The pre-receive hook receives all reference updates as a whole
  via standard input, where each change is represented by one line with the old
  and new object ID as well the name of the reference that is to be updated. At
  this point, all objects required to satisfy the update have already been
  received, but they are still in a separate "quarantine directory" and are
  therefore detached from the main repository. This hook first increments a
  reference counter that tracks how many pushes are active at the same time.
  Afterwards, it posts all changes to Rails' `/internal/allowed` API endpoint so
  that Rails can determine whether the change is allowed or not. Because objects
  still live in a quarantine directory, Gitaly tells Rails where it can find the
  quarantine directory using the repository's alternative object directory
  fields so that any subsequent RPC calls that check the change can access those
  objects. When the access checks succeed, any existing custom pre-receive hooks
  installed by the administrator are executed.
- `update`: The update hook runs after the pre-receive hook at the point where
  objects from the object quarantine directory have already been migrated into
  the main repository. This hook only executes custom hooks installed by the
  admin.

// UpdateReferencesRequest is a request for the UpdateReferences RPC.
message UpdateReferencesRequest {
  // Update represents a reference update.
  message Update {
    // reference is the fully-qualified reference name that should be updated.
    bytes reference = 1;

    // old_object_id is the object ID the reference should be pointing to in order to be updated.
    // This has the intent to avoid time-of-check-time-of-use-style races when the object ID
    // has changed.
    //
    // If empty, the reference will be force-updated without any such checks. If set to the
    // all-zeroes object ID, this will verify that the branch did not exist previously.
    bytes old_object_id = 2;

    // new_object_id is the object ID the reference should be updated to. If set to the all-zeroes
    // object ID the branch will be deleted.
    bytes new_object_id = 3;
  };

  // repository is the repository where references shall be updated in.
  Repository repository = 1 [(target_repository)=true];
  // updates is the set of reference updates that shall be performed.
  repeated Update updates = 2;
}
