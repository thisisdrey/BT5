### Title
StackerDB chunk signatures omit the target StackerDB (contract) identity, enabling cross-database replay of captured signed chunks - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` computes the signed hash over only `slot_id`, `slot_version`, and `data_hash` [1](#0-0) . It never includes the target StackerDB's `smart_contract_id`. The write-path verification in `StackerDBs::validate_received_chunk` recovers the signer solely from this digest and checks it against the *destination* database's own slot-owner table via `get_slot_signer(smart_contract_id, data.slot_id)` [2](#0-1)  — but the signature itself carries no proof of which contract/database it was created for. This is the same bug class as CoreWCF's XML signature wrapping issue: the cryptographic signature does not bind to the full intended message context, so a signature that is valid and "fresh" in one context can be replayed verbatim into a different context that shares the same (slot_id, signer) relationship.

### Finding Description
Stacks Nakamoto signers write protocol messages (BlockResponse, StateMachineUpdate, BlockPreCommit) into multiple, distinct StackerDB contracts per reward cycle, each identified via `MessageSlotID::stacker_db_contract(mainnet, reward_cycle)` → `NakamotoSigners::make_signers_db_contract_id(reward_cycle, msg_type_index, mainnet)` [3](#0-2) . These separate contracts (e.g. `signers-<cycle>-1` for BlockResponse, `signers-<cycle>-2` for StateMachineUpdate, `signers-<cycle>-3` for BlockPreCommit) are all populated from the same underlying reward-cycle signer set, so the same signer address is very likely assigned the same `slot_id` across all of that cycle's message-type StackerDB instances.

Because `SlotMetadata::auth_digest()` signs only `(slot_id, slot_version, data_hash)` and never the `smart_contract_id`, a `StackerDBChunkData` that a signer legitimately produced and broadcast for one contract (e.g., their `BlockPreCommit` slot) is a byte-for-byte valid, verifiable signature for the *same* `slot_id` in any other StackerDB where that signer owns the same slot — including a different message-type contract in the same reward cycle. `validate_received_chunk` and the HTTP `poststackerdbchunk` write path do not check that the signed digest is scoped to the DB being written to; they only check the recovered address against that DB's slot-owner table, which is satisfied because the owner is the same signer.

An attacker who captures one such signed chunk (e.g., off the wire, since StackerDB gossip/HTTP push is not confidentiality-protected) can resubmit it as a chunk for a *different* StackerDB contract, at the same `slot_id`, as long as the target DB's local `expected_version`/`max_writes` checks are satisfied. The write will be treated as authentic by that database and relayed via `PeerNetwork::handle_unsolicited_StackerDBPushChunk` to the rest of the network, because chunk authentication is entirely local to `(slot_id, slot_version, data_hash)` and ignores which logical StackerDB the signature was created for.

### Impact Explanation
This breaks the authentication invariant that a signed StackerDB write is scoped to the specific database/message-type it was intended for. An attacker can inject a captured, validly-signed chunk into the wrong StackerDB instance (e.g., replaying a `BlockPreCommit` chunk into the `StateMachineUpdate` or `BlockResponse` slot for the same signer/slot_id), causing forged/misattributed data to be accepted and propagated network-wide as if it were freshly and correctly authored for that contract. This matches the "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" High/Critical impact classes: the write succeeds without the corresponding contract-specific authorization the design intends, and it will further replicate via StackerDB gossip to other nodes' replicas.

### Likelihood Explanation
Exploitation requires only: (1) capturing one signed `StackerDBChunkData` from the wire or via a previously-observed chunk (StackerDB traffic and stored slot contents are broadcast to be publicly readable/replicated by design — no secrecy is claimed over historical chunks), and (2) resubmitting it against a different, but plausible, target contract at the same slot_id, subject only to that DB's local version/max-write bookkeeping. No node secret, private key, or privileged role is needed — the entire security of the write is delegated to a signature that fails to bind the intended contract.

### Recommendation
Include the target `smart_contract_id` (and, ideally, reward cycle / network id) in `SlotMetadata::auth_digest()` so the signature is cryptographically scoped to the specific StackerDB instance it authorizes a write to, mirroring how the CoreWCF fix requires the signature to cover all security-relevant context (destination/action) rather than trusting an out-of-band write-context. Concretely, update `auth_digest()` in `libstackerdb/src/libstackerdb.rs` to hash the contract identifier alongside `slot_id`, `slot_version`, and `data_hash`, and thread `smart_contract_id` through `SlotMetadata::sign`/`verify` call sites (`StackerDBChunkData::sign`/`verify`, `validate_received_chunk`, and the RPC write path in `stackslib/src/net/api/poststackerdbchunk.rs`).

### Proof of Concept
1. Identify a reward cycle `R` where a given signer address owns `slot_id = S` in more than one of that cycle's StackerDB contracts (e.g. `signers-R-1` for BlockResponse and `signers-R-3` for BlockPreCommit) — plausible since slot assignment derives from the same signer set for the whole cycle.
2. Capture a legitimately signed `StackerDBChunkData` (slot_id=S, slot_version=v, sig) that the signer posted to `signers-R-1`.
3. Replay the identical `StackerDBChunkData` bytes as a POST to a node's `signers-R-3` StackerDB endpoint (`poststackerdbchunk.rs`), adjusting only `slot_version` to satisfy that DB's local freshness/max-write checks (still using the *same* captured `sig`, since the signature covers only `(slot_id, slot_version, data_hash)` — reuse is possible whenever attacker can find an untouched or matching version/data_hash pairing, or more directly, replay it verbatim if the destination DB slot is still at its initial/expected version).
4. Observe that `validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:649-717`) accepts the chunk because `slot_metadata.verify(&addr)` succeeds (correct signer for that slot_id in the *destination* DB), even though the signature was never intended for `signers-R-3`.     /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
