Confirmed: `extractBytes32Array` (line 390-397 of `PrecompiledContracts.java`) is called unconditionally in `BatchValidateSign.doExecute` at line 1176-1177, with **no size cap applied before the allocation**, regardless of whether `VMConfig.allowTvmSelfdestructRestriction()` is active.

### Title
Unbounded array allocation from attacker-controlled ABI length field in `BatchValidateSign` precompile causes energy-cheap denial of service - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` TVM precompiled contract (and its sibling `ValidateMultiSign`) decode ABI-encoded call data by reading a length word directly from attacker-supplied bytes and immediately allocating a Java array sized to that raw value, before any range check is applied against that specific value.

### Finding Description
In `extractBytes32Array`: [1](#0-0) 
`len` is read straight from `words[offset].intValueSafe()` — fully attacker controlled via the calldata sent to the precompile — and used to allocate `new byte[len][]` with no upper bound check at all.

This method is called unconditionally (not gated behind `allowTvmSelfdestructRestriction()`) in `BatchValidateSign.doExecute`: [2](#0-1) 
Note that the `MAX_SIZE` guard at lines 1165-1171 only checks `sigArraySize`/`addrArraySize` when `allowTvmSelfdestructRestriction()` is enabled, and even when enabled it protects `extractSigArray`/`extractBytesArray`, but `extractBytes32Array` for the `addresses` array is invoked at line 1176-1177 regardless, with its own internal unbounded `len` read.

`intValueSafe()` clamps a `DataWord` to a valid Java `int` (up to `Integer.MAX_VALUE`) rather than rejecting large values, so a crafted 32-byte word can set `len` to `Integer.MAX_VALUE` (or any large value), causing `new byte[len][]` to attempt to allocate an array of up to ~2^31 object references (≈16 GB on a 64-bit JVM) from a calldata payload that is otherwise tiny.

The energy charged for the call is computed purely from `data.length` in `getEnergyForData`: [3](#0-2) 
This means the energy cost is bounded by the small calldata size, not by the value embedded inside one of its words — so an attacker pays only for a small transaction while triggering a massive allocation attempt.

### Impact Explanation
Because the whole `doExecute` call is wrapped in `catch (Throwable t)` in `execute()`: [4](#0-3) 
an `OutOfMemoryError` from the huge allocation is caught for a single invocation and the call returns a default result rather than immediately crashing the JVM. However, `OutOfMemoryError` in Java is not a safely recoverable condition in general — other unrelated threads within the same JVM (P2P networking, block processing, RPC handling) can throw `OutOfMemoryError` concurrently once heap pressure spikes, and repeated invocation of this precompile (from many contract calls or transactions, cheaply, since the attacker only pays energy proportional to a tiny data.length) can sustain memory pressure and destabilize or crash the node — a denial-of-service condition directly analogous to CVE-2020-3810 (missing length validation on attacker input leading to DoS during parsing).

### Likelihood Explanation
`BatchValidateSign` is a standard TVM precompiled contract callable by any account via a `TriggerSmartContract` (or a contract's internal `staticcall`/`call`) to its fixed precompile address. No special privilege, deployed contract, or SR/committee role is required — any transaction broadcaster or contract can construct calldata with a crafted length word and invoke it directly. This makes the likelihood high: it requires only a single, cheap, unprivileged transaction.

### Recommendation
Apply an upper bound check (e.g., the existing `MAX_SIZE` constant) to the `len` value read inside `extractBytes32Array` before allocating the array, independent of `allowTvmSelfdestructRestriction()`. Alternatively, always validate `addrArraySize`/`sigArraySize` against `MAX_SIZE` prior to calling any of `extractSigArray`, `extractBytesArray`, or `extractBytes32Array`, regardless of feature-flag state, so that a single crafted 32-byte length word cannot drive an allocation disproportionate to the actual calldata size.

### Proof of Concept
Construct calldata to the `BatchValidateSign` precompile address where:
- word[0] = hash (32 bytes, arbitrary)
- word[1] = offset pointing to a signatures-array header whose length field is small (e.g., 1) so the `cnt` checks and signature extraction pass quickly
- word[2] = offset pointing to a location where the "array length" word (read by `extractBytes32Array` as `words[offset]`) is set to `0x7FFFFFFF`

Total calldata can be kept just large enough to satisfy the minimal decoding preconditions (a few hundred bytes), so `getEnergyForData` charges only a small energy amount, while `extractBytes32Array` attempts `new byte[2147483647][]`, immediately throwing `OutOfMemoryError` under real heap pressure. Repeating this call across multiple transactions/contract calls sustains memory pressure on the node.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];

  }
