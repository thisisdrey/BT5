I found a concrete analog to the "stale cached value used instead of current" bug class in the CA pool's cached-certificate fast path.

## Title
Cached certificate re-verification (`VerifyCachedCertificate`) skips CA constraint re-checking, letting a certificate remain trusted after its issuing CA's constraints have changed on reload - (File: cert/ca_pool.go)

### Summary
`CAPool.verify` has two code paths: a full path (used by `VerifyCertificate` on first handshake) that calls `CheckSignature` and `CheckCAConstraints`, and a fast/cached path (used by `VerifyCachedCertificate`, invoked repeatedly by `connectionManager.isInvalidCertificate` for the lifetime of a tunnel) that only compares `signerFp != signer.Fingerprint` and returns early, entirely skipping `CheckCAConstraints`.

### Finding Description
`ncp.verify()` bails out on the cached path as soon as the fingerprint of the CA that originally signed the peer cert still matches the current CA pool entry for that issuer: [1](#0-0) 
This is the direct structural analog of the audited bug: a "stored"/previously-computed value (`signerFp`, the CA fingerprint captured at initial verification time) is trusted as a stand-in for the "current" authoritative check (`CheckCAConstraints(signer.Certificate, c)`, which validates that the peer cert's networks/unsafe-networks/groups still fall inside the CA's currently configured constraints). If a CA's `Networks()`, `UnsafeNetworks()`, or `Groups()` are narrowed on a config reload (`pki.reload` -> `reloadCAPool`) — the CA fingerprint itself doesn't change when just re-signed with the same key/details, so `signerFp == signer.Fingerprint` remains true — every already-established tunnel skips re-validating that the peer's advertised networks/groups still fit inside the (now-tightened) CA constraints, because `isInvalidCertificate` only ever calls the cached path: [2](#0-1) 
Whereas a brand-new handshake for the same peer cert would call `VerifyCertificate` → the full `verify()` path, hitting `CheckCAConstraints` and potentially rejecting it: [3](#0-2) 
This mirrors the reported bug class precisely: a security decision (should this cert still be trusted/should this tunnel still be considered valid) is made from a stale cached signal instead of recomputing it against the current authoritative state, exactly as `exchangeRateStored` was trusted instead of recomputing via `exchangeRateCurrent`.

### Impact Explanation
An already-established, previously-valid tunnel's peer certificate is periodically re-checked only through the cached fast path for the connection's entire lifetime (`connectionManager`'s periodic sweep calls `isInvalidCertificate` → `VerifyCachedCertificate`). If an operator tightens CA constraints (e.g., removes a group or shrinks allowed networks on the signing CA) specifically to revoke trust for certain classes of already-issued certs, an active tunnel whose peer cert would now fail `CheckCAConstraints` continues to be treated as valid and is never torn down by `pki.disconnect_invalid`, because the stale `signerFp` match short-circuits before that check ever runs. This is a remote state (trust) poisoning of security-relevant certificate validation logic — the enforcement gap only closes on the next full handshake.

### Likelihood Explanation
This requires no attacker action beyond already holding a certificate signed by the CA before the constraint tightening (i.e., a previously-valid peer whose privileges were meant to be curtailed by an operator's CA reconfiguration). The condition is reachable purely through normal certificate-lifecycle/config-reload operations that Nebula explicitly supports (`p.reloadCAPool` on SIGHUP), making this a realistic, not merely theoretical, gap rather than requiring an adversarial network attacker without any cert.

### Recommendation
Have `VerifyCachedCertificate`/the cached branch of `verify()` also re-run `CheckCAConstraints(signer.Certificate, c)` (or invalidate/refresh `CachedCertificate.signerFingerprint`-based caching whenever the CA pool is reloaded), so that a CA constraint tightening is enforced against already-established tunnels rather than only against fresh handshakes.

### Proof of Concept
1. Start a CA and issue a host certificate `A` with `groups: ["ops"]` and network `10.0.0.5/24`, and establish a tunnel to a peer that enforces group-scoped firewall rules.
2. Reload the CA (SIGHUP) with a new CA certificate that constrains its signed certs' allowed `groups` to no longer include `"ops"` (same CA key/fingerprint reused, or a CA cert update that keeps `Issuer` matching but narrows constraints) via `p.reload` → `reloadCAPool`.
3. Observe that `connectionManager.isInvalidCertificate` keeps calling `caPool.VerifyCachedCertificate(now, remoteCert)` [4](#0-3)  which takes the `len(signerFp) > 0` early-return branch in `verify()` and never calls `CheckCAConstraints`, so the tunnel is never disconnected despite `pki.disconnect_invalid` being enabled — whereas issuing certificate `A` fresh (fresh `VerifyCertificate` call) would fail `CheckCAConstraints` and be rejected.

func (ncp *CAPool) VerifyCertificate(now time.Time, c Certificate) (*CachedCertificate, error) {
	if c == nil {
		return nil, fmt.Errorf("no certificate")
	}
	fp, err := c.Fingerprint()
	if err != nil {
		return nil, fmt.Errorf("could not calculate fingerprint to verify: %w", err)
	}

	signer, err := ncp.verify(c, now, fp, "")
	if err != nil {
		return nil, err
	}

	// Pre nebula v1.10.3 could generate signatures in either high or low s form and validation
	// of signatures allowed for either. Nebula v1.10.3 and beyond clamps signature generation to low-s form
	// but validation still allows for either. Since a change in the signature bytes affects the fingerprint, we
	// need to test both forms until such a time comes that we enforce low-s form on signature validation.
	fp2, err := CalculateAlternateFingerprint(c)
	if err != nil {
		return nil, fmt.Errorf("could not calculate alternate fingerprint to verify: %w", err)
	}
	if fp2 != "" && ncp.IsBlocklisted(fp2) {
		return nil, ErrBlockListed
	}

	cc := CachedCertificate{
		Certificate:       c,
		InvertedGroups:    make(map[string]struct{}),
		Fingerprint:       fp,
		fingerprint2:      fp2,
		signerFingerprint: signer.Fingerprint,
	}

	for _, g := range c.Groups() {
		cc.InvertedGroups[g] = struct{}{}
	}

	return &cc, nil
}
