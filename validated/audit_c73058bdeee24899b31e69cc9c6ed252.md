### Title
Dust-transfer griefing fills `MAX_TOKENS_PER_USER` slots and permanently blocks victim deposits and new debt issuance — (File: contracts/Pool.sol)

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined number of entries in `debtTokensOfAccount` and `depositTokensOfAccount`. `DepositToken._transfer` (and `_mint`) automatically registers the token in the recipient's per-account set via `pool.addToDepositTokensOfAccount`, with no opt-in or minimum amount. An unprivileged attacker can therefore transfer 1-wei dust amounts of every deposit token in the pool to a victim, filling all 30 slots. Afterwards, any call that would register a *new* token for the victim — `deposit(onBehalfOf=victim)` for an unheld collateral, `DebtToken.issue`/`mint` of an unheld synth, or receiving any new `DepositToken` — reverts with `UserReachedMaxTokens`, denying the victim the ability to add collateral to their position.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` (Pool.sol `onlyIfAdditionWillNotReachMaxTokens`).
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was zero — no consent, no dust threshold. Same for `_mint` in `deposit(..., onBehalfOf_)`.
- `DepositToken.transfer`/`transferFrom` only check the *sender's* unlocked balance (`_revertIfLocked`), so the attacker can freely spray dust to arbitrary victims.
- The victim cannot remove entries themselves: entries are only removed when a balance returns to zero, and the victim would have to transfer each dust token out individually — but an attacker can re-dust, and critically the victim may not even hold transferable balance in those tokens (the dust is locked once the victim has debt, since `unlockedBalanceOf` uses the aggregate `debtPositionOf` across all tokens — actually the dust itself stays unlocked as it counts toward `_issuableInUsd`, but the griefing persists as long as balances are non-zero; the attacker can repeat the attack cheaply after each cleanup).

Net effect on a victim with an open debt position: they cannot deposit a collateral type they don't already hold (e.g., can't add USDC collateral when only holding WETH collateral), and cannot issue a new synth type. If their position drifts unhealthy, `liquidate` works, but self-rescue via depositing a *new* collateral is impossible while slots are full, and `Operator.execute`/gateway deposits on their behalf revert too.

### Impact Explanation
Temporary freezing of funds / liveness failure: the victim's ability to deposit additional (new-type) collateral and to mint new synth debt is completely blocked while their 30 slots are occupied. For an underwater or near-liquidation position this directly prevents the cheapest rescue path (deposit new collateral), leading to forced liquidation and loss of the liquidation incentive. This mirrors the CVE class — a complete denial of a core service (deposit/issue) triggered by an unprivileged remote attacker.

### Likelihood Explanation
- Fully unprivileged: attacker only needs dust amounts of each underlying, deposited once, then `transfer(victim, 1)` for each `DepositToken`.
- No privileged role, oracle manipulation, or governance action required.
- Attack cost scales linearly with the number of distinct deposit tokens in the pool (bounded by the pool's own `ReachedMaxDepositTokens` cap of 30); on pools with many listed collaterals the attack is cheap and can be repeated after each victim cleanup.

### Recommendation
- Exclude zero/dust balances from the per-account sets (e.g., only register when the received amount exceeds a minimum threshold), or
- Allow the account itself to remove unwanted tokens (`removeFromDepositTokensOfAccount` callable via a `DepositToken.removeDust()`/sweep-to-zero path), or
- Only count tokens with economically meaningful balance toward `MAX_TOKENS_PER_USER`, or raise/scope the limit so receiving a transfer cannot consume the victim's slots.

### Proof of Concept
Foundry sketch (fork or unit harness with a live `Pool` + ≥N deployed `DepositToken`s):

```solidity
function test_DustFillsTokenSlots() public {
    address victim = makeAddr("victim");
    IDepositToken[] memory dts = pool.getDepositTokens(); // e.g., WETH, USDC, vaETH...

    // Attacker deposits dust of each underlying and transfers 1 wei of each
    // DepositToken to the victim until slots are exhausted.
    for (uint256 i; i < dts.length && combinedLen(victim) < pool.MAX_TOKENS_PER_USER(); ++i) {
        IERC20 under = dts[i].underlying();
        deal(address(under), attacker, 1e6);
        vm.startPrank(attacker);
        under.approve(address(dts[i]), 1e6);
        dts[i].deposit(1e6, attacker);
        dts[i].transfer(victim, 1);
        vm.stopPrank();
    }

    // Victim's deposit-token + debt-token list is now full.
    uint256 len = pool.getDepositTokensOfAccount(victim).length
                + pool.getDebtTokensOfAccount(victim).length;
    assertEq(len, pool.MAX_TOKENS_PER_USER());

    // Any new deposit to the victim reverts — including deposits the victim
    // makes themselves into a collateral type they don't already hold.
    IERC20 newUnder = dts[0].underlying();
    deal(address(newUnder), victim, 100e18);
    vm.startPrank(victim);
    newUnder.approve(address(dts[0]), 100e18);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector); // bubbles up from addToDepositTokensOfAccount
    dts[0].deposit(100e18, victim);
    vm.stopPrank();

    // Same for issuing a debt token the victim doesn't already hold:
    // DebtToken.mint -> pool.addToDebtTokensOfAccount -> UserReachedMaxTokens.
}
```

Note: this holds because `transfer`/`transferFrom`/`_mint` register the recipient unconditionally (`DepositToken._transfer` lines ~517-520, `DepositToken._mint` ~485-488) and `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts at 30 entries (`Pool.sol` ~143-148, 204-220).
