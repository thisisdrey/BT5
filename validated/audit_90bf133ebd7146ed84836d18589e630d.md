### Title
Missing Negotiation-Phase Deadline in `SSHReceivePack` Allows Use-After-Check Bypass of Stale Access Grants - ([File: internal/gitaly/service/ssh/receive_pack.go])

### Summary
Gitaly already recognizes and mitigates a "stale check" class of bug for the upload-pack/upload-archive paths: an access check is performed once, before the RPC's negotiation phase, and the client is trusted to complete negotiation quickly. If a malicious or delayed client can hold the connection open indefinitely before sending the packet that triggers the actual git operation, the operation ends up executing based on an access decision that may no longer be valid — a direct structural analog to the "no deadline, stale slippage check" bug in `BadDebtProcessor::uniswapV3FlashCallback()`. Gitaly fixed this for `git-upload-pack`/`git-upload-archive` by adding `pktline.ReadMonitor` with a `timeoutTicker` that bounds the negotiation window, but `SSHReceivePack` (`internal/gitaly/service/ssh/receive_pack.go`) has no equivalent bound.

### Finding Description
`internal/git/pktline/read_monitor.go` explicitly documents this bug class: [1](#0-0) 

and `internal/gitaly/service/ssh/upload_command.go` implements the mitigation, timeboxing the window between RPC start (where the access check has already run) and completion of negotiation: [2](#0-1) [3](#0-2) 

This is wired up in `sshUploadPack` via `s.runUploadCommand(...)` with a `timeoutTicker` and the `pktline.PktDone()` boundary packet: [4](#0-3) 

`SSHReceivePack`, however, performs its own lightweight validation (`validateFirstReceivePackRequest`, which only checks `GlId`, empty `Stdin`, and repository path — not the real authorization decision, which is made upstream by the Rails/gitlab-shell pre-check before the RPC is even invoked) and then immediately starts `git-receive-pack` with no bound on how long the client may take to actually stream `stdin` (the ref-update commands and pack data): [5](#0-4) [6](#0-5) [7](#0-6) 

Because the client fully controls the pace at which it writes to `stdin` (relayed via the `pr`/`pw` pipe and `streamio.NewReader`), and `git-receive-pack` will happily wait, an attacker who is authorized at connection time can keep the connection open indefinitely and only send the actual ref-update/pack data much later — well after the point at which the external authorization decision (branch protection, membership, MR approval state, etc.) could have changed. Unlike upload-pack, there is no `ReadMonitor`/`timeoutTicker` guarding this window for `SSHReceivePack`.

### Impact Explanation
This reproduces the exact bug class from the report: a check (access authorization here, slippage there) is performed once, but nothing enforces that the subsequent state-changing operation (`git-receive-pack` writing objects/refs here, the Uniswap swap there) executes within a bounded time of that check. An attacker whose access is later revoked, or whose target branch protection changes, could still push using a session that was authorized long before, because Gitaly enforces no time bound on the negotiation window for receive-pack the way it explicitly does for upload-pack. This can result in unauthorized ref updates being accepted against the server's current-but-unenforced authorization state.

### Likelihood Explanation
The precondition (stdin fully controlled by the client and no upper bound enforced by Gitaly on the negotiation window) is directly exercisable by any ordinary user's `git push` session over SSH; no privileged access or protocol trickery beyond delaying stdin is required. The likelihood is bounded mainly by how long an external authorization decision typically remains valid and by connection/idle timeouts enforced elsewhere in the stack (e.g., SSH proxy, load balancer), which are outside Gitaly's control and not a substitute for an explicit negotiation deadline.

### Recommendation
Apply the same `pktline.ReadMonitor`/`timeoutTicker` pattern used in `runUploadCommand` (internal/gitaly/service/ssh/upload_command.go) to `sshReceivePack`, bounding the time between the start of the RPC (when the access check is known to have just been performed) and the point where the client finishes sending its ref-update commands / pack data, aborting the command if the boundary condition is not observed in time.

### Proof of Concept
1. Client authenticates and opens `SSHReceivePack` for a repository/branch it is currently authorized to push to; the external (Rails/gitlab-shell) authorization check passes at this moment. See `validateFirstReceivePackRequest` in `internal/gitaly/service/ssh/receive_pack.go`.
2. `sshReceivePack` immediately starts `git-receive-pack` and begins waiting on `stdin`, with the client fully in control of pacing.
3. Client withholds sending the ref-update command and pack data for an extended period (no `ReadMonitor`/timeout enforces a bound, unlike `runUploadCommand`).
4. During this window, the client's authorization to push to the target ref is revoked (e.g., branch protection changed, membership removed).
5. Client resumes and completes the push; because no deadline check exists for this negotiation window, `git-receive-pack` proceeds and the push is accepted despite the now-stale authorization.

func (s *server) SSHReceivePack(stream gitalypb.SSHService_SSHReceivePackServer) error {
	req, err := stream.Recv() // First request contains only Repository, GlId, and GlUsername
	if err != nil {
		return structerr.NewInternal("%w", err)
	}

	s.logger.WithFields(log.Fields{
		"GlID":             req.GetGlId(),
		"GlRepository":     req.GetGlRepository(),
		"GlUsername":       req.GetGlUsername(),
		"GitConfigOptions": req.GetGitConfigOptions(),
		"GitProtocol":      req.GetGitProtocol(),
	}).DebugContext(stream.Context(), "SSHReceivePack")

	if err = validateFirstReceivePackRequest(stream.Context(), s.locator, req); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

func validateFirstReceivePackRequest(ctx context.Context, locator storage.Locator, req *gitalypb.SSHReceivePackRequest) error {
	if req.GetGlId() == "" {
		return errors.New("empty GlId")
	}
	if req.Stdin != nil {
		return errors.New("non-empty data in first request")
	}
	return locator.ValidateRepository(ctx, req.GetRepository())
}
