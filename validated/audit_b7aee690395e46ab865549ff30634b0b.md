### Title
Unauthenticated integer-overflow panic via unbounded `estimated_len` in POST /v2/fees/transaction - (File: stackslib/src/net/api/postfeerate.rs)

### Summary
`RPCPostFeeRateRequestHandler::try_parse_request` accepts an attacker-supplied `estimated_len: Option<u64>` from the JSON request body with no upper-bound validation, other than the overall HTTP body length being capped by `MAX_PAYLOAD_LEN`. This value flows unmodified into `estimate_tx_fee_from_cost_and_length`, where it is multiplied by `MINIMUM_TX_FEE_RATE_PER_BYTE` using unchecked `u64` multiplication, producing an overflow.

### Finding Description
In `try_parse_request` [1](#0-0) , `estimated_len` is computed as `max(body.estimated_len.unwrap_or(0), payload_data.len())`. `body.estimated_len` is a plain `u64` deserialized straight from client JSON [2](#0-1)  with no range check — the only body-size gate is `content_len < MAX_PAYLOAD_LEN` on the raw HTTP bytes [3](#0-2) , which does not constrain the numeric *value* of `estimated_len` (a tiny JSON payload like `{"estimated_len":18446744073709551615,"transaction_payload":"0x00"}` easily fits under that limit).

This attacker-controlled `estimated_len` is passed into `estimate_tx_fee_from_cost_and_length`, where line 112 computes `let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;` using plain (unchecked) multiplication [4](#0-3) . If `estimated_len` is large enough (e.g. `u64::MAX`) and `MINIMUM_TX_FEE_RATE_PER_BYTE` is any value greater than 1, this multiplication overflows `u64`. In a debug/overflow-checked build, this triggers an arithmetic-overflow panic; in a release build (checks disabled), it silently wraps and produces a corrupted `minimum_fee` used to override the real fee estimate in the response.

No authentication is required for this endpoint (`POST /v2/fees/transaction` is a standard unauthenticated RPC endpoint), and none of `MAX_PAYLOAD_LEN`, `will_admit_mempool_tx`, or other guards validate the numeric value of `estimated_len` — they only bound the transport-level byte length of the request body, not the parsed field's magnitude.

### Impact Explanation
A single unauthenticated POST request can panic the node's RPC-handling thread if the binary is built with overflow checks enabled (which is common for debug/test builds, and any release build compiled with `overflow-checks = true`, e.g. some CI/staging deployments). In pure release builds without overflow checks, the value silently wraps, causing the endpoint to serve an incorrect ("non-canonical") fee estimate — this could mislead wallets/clients into constructing under/over-priced transactions, though this is a self-contained fee-estimation RPC and does not corrupt chain state or force a fork. Given the panic-only scenario matches "remote crash/unauthenticated DoS from a single message" for builds with overflow checks, but the underlying condition depends on the build profile — this weakens the certainty of a guaranteed crash in all deployed release binaries.

### Likelihood Explanation
The endpoint requires no privilege, no secret, and no prior state — a bare TCP connection to the RPC port and one crafted JSON POST is sufficient. `MINIMUM_TX_FEE_RATE_PER_BYTE`'s exact value determines the precise threshold, but `u64::MAX` guarantees overflow for any rate greater than 1. This is trivially repeatable per request. The main uncertainty is whether the target binary is built with `overflow-checks` enabled (default for `cargo build` debug profiles, and dependent on the release profile settings in `Cargo.toml`, which I was unable to confirm from index results in this pass).

### Recommendation
Use checked/saturating arithmetic for `let minimum_fee = estimated_len.saturating_mul(MINIMUM_TX_FEE_RATE_PER_BYTE);` and/or clamp `body.estimated_len` in `try_parse_request` to a sane upper bound (e.g. `MAX_PAYLOAD_LEN`) before use, rejecting values above it with a `DecodeError`.

### Proof of Concept
Add a test in `stackslib/src/net/api/tests/postfeerate.rs` that constructs an HTTP POST body `{"estimated_len": 18446744073709551615, "transaction_payload": "0x0000000000000000000000000000000000000000"}` (a minimal valid `TransactionPayload` encoding), feeds it through `RPCPostFeeRateRequestHandler::try_parse_request` and then `try_handle_request` with a configured fee estimator, and asserts the process does not panic. Running this under `cargo test` (default debug profile, overflow checks on) at the line `let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;` (`stackslib/src/net/api/postfeerate.rs:112`) reproduces `attempt to multiply with overflow`.
