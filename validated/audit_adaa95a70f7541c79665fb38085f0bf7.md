## Analysis Result

I found a valid analog of this bug class in marginfi-v2's limit order system.

### Title
Take-Profit order slippage protection uses a live, unsnapshotted `order_execution_max_fee`, allowing a permissionless keeper to extract more of a user's equity than was in effect when the order was placed - (File: `programs/marginfi/src/instructions/marginfi_account/order.rs`)

### Summary
The `Order` account created by `place_order` stores no snapshot of the fee/margin cap that will later bound how much value a keeper may extract when executing the order. Instead, `end_execute_order` reads `fee_state.order_execution_max_fee` live at execution time and uses it to compute the maximum amount the executing keeper may keep as profit on a Take-Profit order. If `order_execution_max_fee` is changed between `place_order` and `marginfi_account_end_execute_order`, the slippage/fee bound enforced at execution no longer matches what was in effect (and implicitly relied upon by the user) at order placement time — exactly the "fee computed at approval time vs. fee computed at execution time" inconsistency described in the source report.

### Finding Description
`Order::initialize` persists only `stop_loss`, `take_profit`, and `max_slippage` on the `Order` account: [1](#0-0)  — no fee value is captured at order-placement time.

At execution time, `end_execute_order` loads the *current* `FeeState` account and uses its `order_execution_max_fee` field to derive the bound on how much of the account's health/equity the keeper may consume as profit: [2](#0-1) 

Specifically, for `TakeProfit` (and `Both`) orders, the allowed withdrawal is bounded by `start_health * (1 - max_fee)`, where `max_fee` is read fresh from `fee_state.order_execution_max_fee` at the moment `end_execute_order` runs, not from any value fixed when the order was placed: [3](#0-2) 

`order_execution_max_fee` is a mutable, program-wide parameter that can be changed by the global fee admin at any time via `edit_global_fee_state`: [4](#0-3) [5](#0-4) 

Because orders can remain open indefinitely (a stop-loss/take-profit is executed opportunistically whenever the trigger condition is met, which the user does not control), an arbitrary amount of time can elapse between `place_order` and the eventual `marginfi_account_end_execute_order`. If `order_execution_max_fee` increases during that window, any permissionless keeper executing a pending Take-Profit order will be allowed to withdraw a materially larger share of the user's equity as "profit" than the cap that was in force when the user placed the order and calibrated their `max_slippage`/trigger expectations around it. This mirrors the reported root cause precisely: a parameter (fee) used to gate a two-phase user operation is recomputed with a live value at settlement instead of being locked in at the initial request, causing the counterparty (keeper) to receive/withhold an amount inconsistent with what was agreed/expected at request time.

### Impact Explanation
This causes a concrete, quantifiable loss of user equity: a permissionless (unprivileged) keeper executing `end_execute_order` can legally extract up to the *new*, larger `order_execution_max_fee` share of the order-placer's account equity, instead of being capped at the fee rate that existed when the order was placed. This is value extracted from an unprivileged user's account by another unprivileged actor (the keeper), which the on-chain accounting explicitly permits due to lack of fee-snapshotting — matching the impact class of "unauthorized transfer"/economic loss described in the report.

### Likelihood Explanation
Likelihood is Medium: it requires (a) `order_execution_max_fee` to change while orders are outstanding — a routine admin/governance action, not an attack, and (b) a Take-Profit or Both-type order to remain open across that change (orders can sit open indefinitely awaiting a price trigger) and then get executed by a keeper motivated to maximize profit. No malicious collusion is required; any keeper acting rationally to maximize their permitted profit share is enough to realize the loss.

### Recommendation
Snapshot the applicable `order_execution_max_fee` (and/or `order_init_flat_sol_fee`) into the `Order` (or `ExecuteOrderRecord`) account at `place_order` time, and use that stored value in `end_execute_order`'s bound check instead of re-reading the live `FeeState`. This mirrors the report's recommendation to compute and lock in fee-dependent amounts at the initial request step so that the same value is used consistently across both phases of the operation.

### Proof of Concept
1. User calls `place_order` for a Take-Profit trigger, implicitly relying on the current `fee_state.order_execution_max_fee` (e.g. 5%) as the maximum share of their equity a keeper can keep.
2. Global fee admin calls `edit_global_fee_state` and raises `order_execution_max_fee` to, e.g., 20% (a legitimate, permitted admin action per `edit_fee_state`).
3. Sometime later, the take-profit trigger condition is met. A keeper calls `marginfi_account_start_execute_order` then `marginfi_account_end_execute_order`.
4. `end_execute_order` computes `max_fee_frac` from the *current* `fee_state.order_execution_max_fee` (20%), allowing the keeper to withdraw up to `start_health * (1 - 0.20)` instead of the `start_health * (1 - 0.05)` bound that was in effect when the user placed the order, resulting in the keeper capturing roughly 4x more of the user's equity than the user could have anticipated at order-placement time.

    let EndExecuteOrder {
        marginfi_account: marginfi_account_loader,
        order: order_loader,
        execute_record: execute_record_loader,
        fee_state: fee_state_loader,
        ..
    } = &ctx.accounts;

    validate_not_cpi_by_stack_height()?;

    let mut marginfi_account = marginfi_account_loader.load_mut()?;
    let order = order_loader.load()?;
    let execute_record = execute_record_loader.load()?;
    let fee_state = fee_state_loader.load()?;

    let mut health_cache = HealthCache::zeroed();

    let (
        (order_assets_in_equity, _order_liabs_in_equity, _order_asset_count, order_liab_count),
        is_healthy,
    ) = {
        let (assets, liabs) = get_health_components(
            &marginfi_account,
            ctx.remaining_accounts,
            RequirementType::Maintenance,
            &mut Some(&mut health_cache),
            HealthPriceMode::Live { liq_cache: None },
        )?;

        let account_health = assets.checked_sub(liabs).ok_or_else(math_error!())?;

        let is_healthy = account_health >= I80F48::ZERO;

        health_cache.set_healthy(is_healthy);

        (
            get_tagged_account_health_components(
                &marginfi_account,
                ctx.remaining_accounts,
                &order.tags,
            )?,
            is_healthy,
        )
    };

    marginfi_account.health_cache = health_cache;

    check!(
        order_liab_count.eq(&0), // All order liabilities should be closed
        MarginfiError::OrderLiabilityNotClosed
    );

    let net = order_assets_in_equity;

    // The user slippage constraint we want to enforce is:
    // net >= (1 - slippage) * (tp or sl)
    // where slippage is encoded as a u32 percent (0..100% mapped to 0..u32::MAX).

    // For the TP case another constraint(the max fee constraint) we want to enforce is:
    // net >= (1 - max_fee) * (start health)
    // It may be possible that the value (1 - max_fee) * (start health) is less than the
    // min allowed value based on the user's slippage constraint alone, in that case
    // we clamp it to the slippage, allowing for that much.
    // In the case where the value was greater we use (1 - max_fee) * (start health) instead.

    // Check that the liquidator did not over-withdraw.

    let slippage_frac = {
        let slippage = marginfi_type_crate::types::u32_to_centi(order.max_slippage);
        I80F48::ONE
            .checked_sub(slippage)
            .ok_or_else(math_error!())?
    };

        let max_fee: I80F48 = fee_state.order_execution_max_fee.into();
        I80F48::ONE.checked_sub(max_fee).ok_or_else(math_error!())?
    };
