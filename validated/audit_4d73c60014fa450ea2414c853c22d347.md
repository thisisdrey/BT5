Confirmed: `success` never appears anywhere in the `outbound-queue-v2` pallet crate — no test, no gating check, no downstream use.

Audit Report

## Title
Relayer reward paid regardless of `DeliveryReceipt.success`, decoupling payout from actual delivery outcome - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`process_delivery_receipt` decodes a `DeliveryReceipt` whose `success: bool` field reflects whether the message actually executed on Ethereum, but the function only validates `receipt.gateway` and the existence of a `PendingOrder` for `receipt.nonce` before paying `order.fee` to the relayer [1](#0-0) . `receipt.success` is never read anywhere in this pallet's crate.

## Finding Description
`DeliveryReceipt` is decoded from a genuine `InboundMessageDispatched(nonce, topic, success, reward_address)` Ethereum event log via `TryFrom<&Log>`, which faithfully copies `event.success` into the `success` field [2](#0-1) . `submit_delivery_receipt` verifies the log's provenance/proof and decodes the receipt, then hands it to `process_delivery_receipt` [3](#0-2) . Inside `process_delivery_receipt`, the only checks performed are `T::GatewayAddress::get() == receipt.gateway` and `PendingOrders::get(nonce)` existence; if `order.fee > 0`, `T::RewardPayment::register_reward` is called unconditionally, then the order is removed and `MessageDelivered` is emitted [4](#0-3) . The proof verification (`T::Verifier::verify`) only attests that the log genuinely exists on Ethereum and was emitted by the Gateway — it says nothing about whether the underlying message dispatch succeeded, since Ethereum's Gateway contract legitimately emits this same event with `success = false` for failed dispatches. Thus a legitimate, unmodified failed-delivery event log is sufficient to collect the full reward.

## Impact Explanation
This is a public underpriced-work / incorrect-payout class issue: the pallet's payout invariant should be "reward is paid only when delivery succeeded," but settlement of `PendingOrders[nonce]` and reward issuance advance purely on nonce/gateway matching, not on decode-validated delivery outcome. A relayer collects `order.fee` for a `nonce` whose Ethereum-side execution actually failed, draining the fee pool and falsely completing accounting state (`MessageDelivered`) for messages that were not truly delivered.

## Likelihood Explanation
Any unprivileged, signed account can call the public extrinsic `submit_delivery_receipt` [5](#0-4) . No special relayer privilege is required, and the exploit input (a real Gateway event log with `success = false`) is a normal, unmodified occurrence whenever an Ethereum-side message dispatch fails — no forgery of proofs is needed.

## Recommendation
- Short term: add `ensure!(receipt.success, Error::<T>::DeliveryFailed)` (or equivalent gating) in `process_delivery_receipt` at [6](#0-5)  before paying `order.fee`, and decide on refund/retry/no-reward handling for failed deliveries.
- Long term: add tests asserting a `DeliveryReceipt{ success: false, .. }` results in no `register_reward` call, and audit other decoded-but-unused fields across Snowbridge V2 receipt/verification structures.

## Proof of Concept
1. `do_process_message` inserts `PendingOrders[nonce] = { fee: F, .. }` [7](#0-6) .
2. Ethereum-side dispatch of that message fails; Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer submits this real log + proof via `submit_delivery_receipt`; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success = false` correctly [8](#0-7) .
4. `process_delivery_receipt` proceeds: gateway matches, `PendingOrders::get(nonce)` is `Some`, `order.fee > 0`, so `register_reward` is invoked and the order removed despite `receipt.success == false` [9](#0-8) . A unit test constructing such a receipt and asserting no reward call / an `Err` result would fail against current code, confirming the gap.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

sol! {
	event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);
}

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
