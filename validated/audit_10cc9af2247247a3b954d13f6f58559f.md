DeleteAccountAction with an unreachable `beneficiary_id` permanently burns the deleted account's remaining balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction::beneficiary_id` is only checked for syntactic validity (a well-formed `AccountId`), never for whether the beneficiary account actually exists. This is directly analogous to the reported `MerchantSubscription` bug, where the `merchant` constructor parameter was accepted as long as it type-checked (any address) without verifying it was a usable/non-null merchant, permanently disabling the contract. In nearcore, any ordinary user can delete their own account with a syntactically valid but non-existent (or otherwise unreachable) `beneficiary_id`, causing the entire remaining balance to be permanently burned instead of delivered to anyone.

### Finding Description
When an account is deleted, `action_delete_account` unconditionally converts the account's remaining balance into a refund receipt targeted at `beneficiary_id`, with no existence check on that account at delete time: [1](#0-0) 

This refund is a system-predecessor `Transfer` receipt (`Receipt::new_balance_refund`). When that receipt is later executed against the (possibly nonexistent) `beneficiary_id`, `apply_action` runs `check_account_existence`, which for `Transfer` actions delegates to `check_transfer_to_nonexisting_account`: [2](#0-1) 

Because the receipt is a refund (`is_refund == true`), `implicit_account_creation_eligible` is forced to `false` at the call site: [3](#0-2) 

so `check_transfer_to_nonexisting_account` always returns `AccountDoesNotExist` when the beneficiary account is missing — refunds intentionally never auto-create accounts (see comment in that function, lines 869–872 above). Since the receipt's predecessor is `system`, the failure path burns the deposit instead of retrying or bouncing it anywhere recoverable: [4](#0-3) 

The only validation performed on `beneficiary_id` is format validity (`InvalidAccountId`), documented in the runtime spec: [5](#0-4) 

There is no check that the account actually exists (or is reachable) at the time `DeleteAccountAction` is submitted or executed.

### Impact Explanation
Any account owner (or a contract acting via `DeleteAccount` on itself, e.g. as observed in `test_instant_delete_account`) who supplies a `beneficiary_id` that does not correspond to an existing account — due to typo, a not-yet-created account, or a since-deleted account — will have their entire remaining NEAR balance permanently and irrecoverably burned rather than refunded. This is a concrete, permanent loss of user funds triggered purely by an ordinary, unprivileged signer's own transaction; no malicious node, operator, or privileged actor is required. It matches the "permanent freezing/loss of funds" impact class validated for this scan.

### Likelihood Explanation
This requires no special privilege and is trivially reachable from a standard `DeleteAccount` action — any wallet, script, or contract that lets a user specify an arbitrary `beneficiary_id` (a common self-service "reclaim my storage deposit and close my account" flow) is exposed. A simple typo, copy-paste error, or race (beneficiary account deleted between construction and submission of the transaction) is sufficient to trigger it. There is no confirmation step, dry-run, or existence check offered by the protocol before the burn occurs.

### Recommendation
Before permitting the balance to be irrecoverably transferred to `beneficiary_id`, consider one or more of the following protocol-level mitigations:
- Validate that `beneficiary_id` corresponds to an existing account (or is a valid implicit account eligible for creation) at the time `DeleteAccountAction` is validated/executed, and reject the action with an explicit error (analogous to the reported fix's `require(merchant != 0x0)`) rather than silently burning funds.
- Alternatively, allow the balance-refund receipt generated by account deletion to opt into implicit-account creation semantics when `beneficiary_id` is a well-formed implicit account, closing the specific gap noted in the `check_transfer_to_nonexisting_account` comment ("refunds don't automatically create accounts").
- At minimum, surface a strong client/wallet-side warning and a "beneficiary must be an existing account" validation before allowing users to submit `DeleteAccount` transactions with an unchecked beneficiary.

### Proof of Concept
1. Alice owns account `alice.near` with balance `B` and no locked stake.
2. Alice submits a transaction with a single `DeleteAccount { beneficiary_id: "nonexistent123.near" }` action, where `nonexistent123.near` has never been created.
3. `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) succeeds: `alice.near` is removed from state and a balance-refund receipt for `B` is queued to `nonexistent123.near`.
4. The refund receipt is later processed. `check_account_existence`/`check_transfer_to_nonexisting_account` (`runtime/runtime/src/actions.rs:857-877`) reject it with `AccountDoesNotExist` because the receipt is a refund (`implicit_account_creation_eligible = false`, `runtime/runtime/src/lib.rs:548-562`).
5. `Runtime::apply_action_receipt` sees `receipt.predecessor_id().is_system()` and `result.result.is_err()`, so it adds `total_deposit(...)` (the full balance `B`) to `stats.balance.other_burnt_amount` (`runtime/runtime/src/lib.rs:993-1000`) instead of crediting any account.
6. Net effect: `B` tokens are permanently removed from circulation; neither Alice nor any beneficiary receives them.

    config: &RuntimeConfig,
    account_id: &AccountId,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    if implicit_account_creation_eligible
        && account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts)
    {
        // OK. It's implicit account creation.
        // Notes:
        // - Transfer action has to be the only action in the transaction to avoid
        // abuse by hijacking this account with other public keys or contracts.
        // - Refunds don't automatically create accounts, because refunds are free and
        // we don't want some type of abuse.
        // - Account deletion with beneficiary creates a refund, so it'll not create a
        // new account.
        Ok(())
    } else {
        Err(ActionErrorKind::AccountDoesNotExist { account_id: account_id.clone() }.into())
    }
}
