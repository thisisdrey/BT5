### Title
Missing sender-identity check in `handleCreateRelayRequest` allows relay-state hijack of another peer's VPN address — ([File: relay_manager.go])

### Summary
`relayManager.handleCreateRelayRequest` accepts the `RelayFromAddr` field of an incoming `NebulaControl_CreateRelayRequest` message at face value and uses it as the key for a new, immediately-`Established` relay entry, without ever checking that the claimed `from` address actually belongs to the authenticated sender `h` (the `HostInfo` whose certificate/handshake identity is `h.vpnAddrs`). This mirrors the reported analog bug class: a caller-supplied identifier (there, a `tokenId`; here, a `RelayFromAddr`) is trusted and acted on without verifying it belongs to the entity making the call.

### Finding Description
When a Control message of type `CreateRelayRequest` arrives, it is routed to `relayManager.handleCreateRelayRequest`: [1](#0-0) 

The `from` value comes straight from the wire (`m.RelayFromAddr`), which the sending peer fully controls; it is never compared against `h.vpnAddrs` (the vpn address(es) actually certified for the peer `h` we handshaked with): [2](#0-1) 

If the claimed `target` equals our own address, the code proceeds to register a brand-new relay keyed on `from` and marks it `Established` immediately (for the "no existing relay" branch): [3](#0-2) 

`AddRelay` performs no verification either — it just allocates an index and stores `PeerAddr: vpnIp` (i.e., the attacker-chosen `from`) associated with `relayHostInfo` (`h`, the attacker's own connection): [4](#0-3) 

The effect: an attacker who has any valid handshake/connection to a victim node (call it `me`) can send a `CreateRelayRequest` with `RelayFromAddr` set to a third party's (victim's) vpn address and `RelayToAddr` set to `me`'s own address. `me` will create an `Established` relay entry associating the attacker's `HostInfo` (`h`) with the victim's vpn address, with no proof the attacker controls or is authorized to speak for that address. This is structurally identical to the reported bug: the exploited field (`tokenId` in the report, `RelayFromAddr` here) is attacker-controlled, and the function that should have validated "does this belong to the caller" (the `exit`/ownership check in the report, an `h.vpnAddrs` containment check here) is simply absent.

### Impact Explanation
Establishing relay state for an arbitrary victim address under attacker control lets the attacker inject itself into `me`'s relay routing decisions for that victim's vpn address (`RelayState`/`relayForByAddr` is used elsewhere, e.g. in connection migration and `QueryVpnAddrsRelayFor`, to decide how to reach a vpn address via a relay hop). Because the relay entry is created as `Established` on first contact rather than requiring completion of a legitimate handshake with the claimed address, this can be used to poison `me`'s relay state for the victim's address — a remote state-poisoning primitive that can subsequently be leveraged to redirect or intercept relayed traffic nominally destined for the victim, without the attacker ever proving ownership of that vpn address. This qualifies as remote state poisoning per the validation criteria.

### Likelihood Explanation
Any peer that can complete a handshake with the target node (a non-privileged, ordinary peer — not requiring lighthouse or CA-signing beyond the normal trust the node already extends to accept handshakes) can send this Control message once a tunnel exists; the vulnerable code path fires unconditionally whenever `target` matches one of `f.myVpnAddrsTable`'s entries, with no additional authorization gate beyond the RelayToAddr/RelayFromAddr being non-nil.

### Recommendation
In `handleCreateRelayRequest`, validate that `from` (derived from `m.RelayFromAddr`) is actually contained in `h.vpnAddrs` (the certificate-derived identity of the authenticated sender) before creating or completing any relay state keyed on it — analogous to the recommended fix in the report ("Add a user check similar to the one present in the `exit` operation"). Reject the request (log and return) if `from` is not one of `h`'s own certified vpn addresses.

### Proof of Concept
1. Attacker `A` establishes a normal, legitimate Nebula tunnel/handshake with node `M` (so `M` has a `HostInfo h` for `A` with `h.vpnAddrs = [A's real address]`).
2. `A` sends a `NebulaControl_CreateRelayRequest` over that tunnel with `RelayFromAddr = V` (victim's vpn address, which `A` does not own) and `RelayToAddr = M`'s own address.
3. On `M`, `relayManager.HandleControlMsg` → `handleCreateRelayRequest` sees `target == M`'s address, finds no existing relay for `from=V` on `h`, and calls `AddRelay(rm.l, h, f.hostMap, V, &m.InitiatorRelayIndex, TerminalType, Established)` — creating an `Established` relay entry that associates `A`'s connection (`h`) with `V`'s vpn address, entirely on `A`'s say-so [3](#0-2) .
4. `M` now holds relay state believing `A`'s connection can serve as the (already-established) relay endpoint for `V`'s vpn address, without `V` or the real owner of that address ever having participated in this exchange.

// relayHostInfo is the Nebula peer which can be used as a relay to access the target vpnIp.
func AddRelay(l *slog.Logger, relayHostInfo *HostInfo, hm *HostMap, vpnIp netip.Addr, remoteIdx *uint32, relayType int, state int) (uint32, error) {
	hm.Lock()
	defer hm.Unlock()
	for range 32 {
		index, err := generateIndex(l)
		if err != nil {
			return 0, err
		}

		_, inRelays := hm.Relays[index]
		if !inRelays {
			// Avoid standing up a relay that can't be used since only the primary hostinfo
			// will be pointed to by the relay logic
			//TODO: if there was an existing primary and it had relay state, should we merge?
			if !hm.unlockedMakePrimary(relayHostInfo) {
				// The tunnel was torn down after the caller grabbed relayHostInfo. A relay standing
				// on an unlinked hostinfo would never carry traffic, and its Relays entry could
				// never be reclaimed since the delete-time cleanup has already run.
				return 0, errors.New("relay hostinfo is no longer in the hostmap")
			}

			hm.Relays[index] = relayHostInfo
			newRelay := Relay{
				Type:       relayType,
				State:      state,
				LocalIndex: index,
				PeerAddr:   vpnIp,
			}

			if remoteIdx != nil {
				newRelay.RemoteIndex = *remoteIdx
			}
			relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)

			return index, nil
		}
	}

	return 0, errors.New("failed to generate unique localIndexId")
}
