## Title
Witness `UpdateBrokerageContract` allows unannounced, effectively-immediate reward-split changes with no event, letting a witness silently steal voter rewards - (File: actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java)

### Summary
The `UpdateBrokerageContract` actuator lets any registered Super Representative (witness) change the `brokerage` percentage it keeps from block/vote rewards, from 0% up to 100%, in a single transaction with no event emission and no time lock. The new value is picked up automatically at the very next maintenance cycle (default 6h interval) by `MaintenanceManager.doMaintenance()`, and is applied directly inside `MortgageService.payReward()` to skim rewards owed to the witness's voters. This is structurally the same class of bug as the reported Surge `Factory` issue: a globally/immediately effective fee parameter, controllable by a single privileged-but-reachable actor, with no event for off-chain monitoring and no delay for affected counterparties to react.

### Finding Description
`UpdateBrokerageActuator.execute()` unpacks the owner-signed `UpdateBrokerageContract` and immediately persists the new brokerage value with no logging/event: [1](#0-0) 

`validate()` only bounds-checks `brokerage` to `[0, 100]` (`ActuatorConstant.ONE_HUNDRED`), which means it can be jumped from the default 20% straight to 100% in one transaction, exactly like the reported `feeMantissa` 0%→20% jump: [2](#0-1) 

The pending brokerage is stored under a special "-1" cycle key via `DelegationStore.setBrokerage(byte[] address, int brokerage)`: [3](#0-2) 

That pending value is copied into the reward-effective cycle key on every maintenance run (`doMaintenance()`, which fires once per `maintenanceTimeInterval`, default 6 hours), with no additional confirmation/time-lock step: [4](#0-3) 

Once effective, `MortgageService.payReward()` uses this brokerage value to directly divert a percentage of every reward (`brokerageAmount`) to the witness before crediting the remainder to voters: [5](#0-4) 

Unlike the surrounding `ProposalService`/committee governance flow (which has multi-SR consensus and delayed effect), this witness-controlled parameter change is a single-signature transaction that takes effect at the very next maintenance cycle, and no `TransactionLogTrigger`/event is emitted anywhere in `UpdateBrokerageActuator` to notify off-chain monitors or voters that the split changed.

### Impact Explanation
A witness can raise its own `brokerage` to 100% for one cycle, causing `MortgageService.payReward()` to reroute essentially the entire block/vote reward to the witness's own allowance instead of its voters, then revert the value back to the previous (e.g. default 20%) setting before the next cycle. Because there is no emitted event, voters and any off-chain monitoring/alerting tooling have no signal that the reward split changed; they can only discover it by actively polling `GetBrokerageServlet`/`getBrokerage`, generally well after the cycle's rewards have already been computed and credited via `delegationStore.addReward`/`adjustAllowance`. This is a concrete theft-of-funds vector against voters who delegated votes to that witness, aligning with the "Impact" categories requiring unauthorized diversion of user funds.

### Likelihood Explanation
The action requires only that the caller control a registered witness account and craft a normal, unprivileged `UpdateBrokerageContract` transaction (via `wallet/updateBrokerage`), which any account that has become an SR can broadcast. No special network-level or consensus-level compromise (censorship, double-signing, etc.) is needed — it's a straightforward abuse of a standard actuator's missing event/time-lock, making it readily and repeatedly exploitable by any self-interested witness once elected.

### Recommendation
- Emit a log/event (or at minimum a `TransactionResultCapsule`-visible marker, or a dedicated event trigger) whenever `UpdateBrokerageActuator.execute()` changes a witness's brokerage, including old and new values, so voters and monitoring tools can react.
- Introduce a time lock / cool-down for brokerage changes (e.g. only allow the update to take effect after N maintenance cycles, or cap the maximum delta per update), similar to how proposal-based `DynamicPropertiesStore` parameters are gated by committee votes in `ProposalService`.
- Consider limiting the maximum jump size per update (e.g. bound the increase to a small percentage per cycle) to prevent a sudden default→100% change from taking full effect against unaware voters.

### Proof of Concept
1. Witness `W` (with existing voters) is registered and currently has default brokerage (`DelegationStore.DEFAULT_BROKERAGE = 20`). [6](#0-5) 
2. Shortly before/at any point in a maintenance cycle, `W` broadcasts an `UpdateBrokerageContract` transaction via `wallet/updateBrokerage` setting `brokerage=100`. This is accepted by `UpdateBrokerageActuator.validate()`/`execute()` with no event emitted. [7](#0-6) 
3. At the next `doMaintenance()` run (up to one `maintenanceTimeInterval`, default 6h, later), the pending value is copied into the active cycle's brokerage key. [4](#0-3) 
4. For that cycle's rewards, `MortgageService.payReward()` computes `brokerageAmount = 100% * value`, routing the full reward to `W`'s allowance and leaving voters with 0 reward for that cycle. [5](#0-4) 
5. `W` then broadcasts another `UpdateBrokerageContract` reverting to `brokerage=20` before voters notice (no event was ever emitted to alert them), and normal operation resumes.

  public void setBrokerage(long cycle, byte[] address, int brokerage) {

  public int getBrokerage(long cycle, byte[] address) {
    BytesCapsule bytesCapsule = get(buildBrokerageKey(cycle, address));
    if (bytesCapsule == null) {
      return DEFAULT_BROKERAGE;
    } else {
      return ByteArray.toInt(bytesCapsule.getData());
    }
  }

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
