### Title
Missing attachment-hash verification in `AttachmentsBatchStateContext::extend_with_attachments` lets a malicious peer poison Atlas attachment resolution, permanently starving a legitimate on-chain-committed attachment - (File: `stackslib/src/net/atlas/download.rs`)

### Summary
When downloading an attachment for a tracked `content_hash`, the client never verifies that the HTTP response body it receives actually hashes to the requested `content_hash` before accepting it. A malicious peer can answer a `GET /v2/attachments/{H1}` request with arbitrary content whose real hash is `H2`, causing `AttachmentsBatch::resolve_attachment` to clear nothing for `H1` while the unrelated blob is persisted via `insert_instantiated_attachment`. The legitimate attachment commitment `H1` is retried until `max_attachment_retry_count` is exhausted and then silently dropped, leaving the on-chain-committed BNS attachment permanently unresolved.

### Finding Description
`AttachmentRequest` is built per `content_hash` (`stackslib/src/net/atlas/download.rs` lines 466-474, `content_hash: content_hash.clone()`), and the HTTP GET is sent to `/v2/attachments/{content_hash}` [1](#0-0) . When the response arrives, `AttachmentsBatchStateContext::extend_with_attachments` decodes it with `decode_atlas_get_attachment` and inserts the returned `Attachment` into `self.attachments` — with **no check that `response.attachment.hash()` equals the requested `request.content_hash`**: [2](#0-1) 

`RPCGetAttachmentRequestHandler::try_parse_response`/`decode_atlas_get_attachment` likewise performs no hash validation on the client side; it just JSON-deserializes whatever body is served: [3](#0-2) 

Because the attacker fully controls their own node's `/v2/attachments/:hash` handler, they can return any `Attachment{content: ...}` regardless of the URL's hash — the honest server-side handler (`try_handle_request`) enforces `find_attachment(&attachment_hash)` only for honest nodes; a malicious node's handler is not constrained by this code at all.

In `AttachmentsDownloader::run`, once the state machine reaches `Done`, each collected attachment is processed by its *actual* hash, not the originally requested one: [4](#0-3) 
- `find_all_attachment_instances(&attachment.hash())` looks up instances for `H2` (none exist, since nothing tracks `H2`).
- `insert_instantiated_attachment(&attachment)` persists the unrelated blob into the Atlas DB keyed by `H2`.
- `context.attachments_batch.resolve_attachment(&attachment.hash())` removes tracked entries whose recorded `content_hash == H2` from `attachments_instances` (`AttachmentsBatch::resolve_attachment`, lines 1227-1239) — but the tracked entry for the legitimate commitment `H1` is untouched.

Consequently `has_fully_succeed()` remains `false` (line 1196-1198), the batch is retried (`bump_retry_count`, lines 188-198), and once `retry_count >= max_attachment_retry_count` the batch is dropped entirely (lines 199-204), abandoning the legitimate `H1` attachment permanently. No existing guard (signature check, length cap, or hash equality check) exists on this path to prevent the mismatch from being accepted.

### Impact Explanation
A single malicious outbound-sync peer can, per attachment request it is selected to serve, cause:
1. A legitimate, on-chain-confirmed BNS attachment (`content_hash = H1`) to never resolve on the victim node — `find_attachment(&H1)` will forever return `None`, so `/v2/attachments/H1` (and BNS zonefile resolution depending on it) will keep answering "not found" even though the chain committed to it. This is a served-state vs. committed-state mismatch (attachment/BNS mismatch), matching the "High" impact category.
2. Unbounded storage of attacker-chosen unrelated blobs into the node's Atlas DB via `insert_instantiated_attachment`, since any garbage content the attacker returns gets accepted and stored under its own hash.
This is repeatable per legitimate attachment instance the node is trying to resolve, as long as the attacker's peer is selected as a source (`AttachmentRequest::get_most_reliable_source`) for that content hash.

### Likelihood Explanation
The attacker only needs to run an ordinary Stacks node that becomes an outbound sync peer of the victim (`network.get_outbound_sync_peers()`) and be selected as a data source for a page that includes the victim's targeted attachment index (`get_prioritized_attachments_requests`) — an unprivileged, remotely reachable capability requiring no secret, admin role, or privileged peer status. Once selected, the attacker unconditionally wins by simply returning any well-formed JSON `GetAttachmentResponse` body for the requested URL; no cryptographic material or race condition is needed, and the effect is deterministic per-request.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (and/or in `decode_atlas_get_attachment`), verify that `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`. If mismatched, treat it as a failed/faulty response (`report.bump_failed_requests()` and optionally mark the peer faulty), rather than silently accepting arbitrary content.

### Proof of Concept
Rust test in `stackslib/src/net/atlas/tests.rs` (or a new test module) that:
1. Builds an `AttachmentsBatch` tracking one instance with `attachment_index = 0`, `content_hash = H1`, via `track_attachment`.
2. Constructs an `AttachmentsBatchStateContext` around this batch, then directly calls `extend_with_attachments` with a `BatchedRequestsResult` whose `succeeded` map pairs an `AttachmentRequest{content_hash: H1, ...}` with a `StacksHttpResponse` whose JSON body is `GetAttachmentResponse{ attachment: Attachment{ content: b"unrelated data".to_vec() } }` (hash `H2 != H1`).
3. Runs the `AttachmentsBatchStateMachine::Done` handling logic (or directly the loop body from `AttachmentsDownloader::run` lines 153-169) against this context.
4. Asserts: `attachments_batch.attachments_instances` still contains the entry for `H1` (i.e., `resolve_attachment` did not clear it), while `atlasdb.find_uninstantiated_attachment(&H2)`/`insert_instantiated_attachment` shows the unrelated blob was stored — demonstrating the served-content vs. tracked-commitment mismatch and permanent non-resolution of `H1`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
