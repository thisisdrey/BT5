### Title
Unbounded `AttachmentPage` count in `GetAttachmentsInvResponse` causes repeated O(N) scans in `get_prioritized_attachments_requests` - (File: stackslib/src/net/atlas/mod.rs, stackslib/src/net/api/getattachmentsinv.rs, stackslib/src/net/atlas/download.rs)

### Summary
The server-side handler `RPCGetAttachmentsInvRequestHandler::try_handle_request` caps outbound `pages` to `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` (8) [1](#0-0) , but the client-side decoder `decode_atlas_attachments_inv_response` performs no such check when parsing a peer's HTTP response body [2](#0-1) . A malicious peer that a node queries for attachment inventory can return an arbitrary number of `AttachmentPage` entries (and arbitrarily long `inventory: Vec<u8>` fields per page), which are then linearly scanned once per missing attachment in `get_prioritized_attachments_requests` [3](#0-2) .

### Finding Description
The intended invariant is: a peer's `GetAttachmentsInvResponse.pages` should never exceed `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` entries, since that's the maximum a well-behaved server is willing to serve. That invariant is enforced only on the outbound/serving side of `try_handle_request` [1](#0-0) . The corresponding client-side consumer, `decode_atlas_attachments_inv_response`, simply deserializes the JSON body into `GetAttachmentsInvResponse` with no bound on `pages.len()` or on any individual `AttachmentPage.inventory` length [2](#0-1) .

A malicious peer that the downloading node's `AttachmentsDownloader` decides to query (e.g., because it advertised a data URL and was selected via `get_outbound_sync_peers`) can instead respond with a crafted JSON body containing thousands of `AttachmentPage` entries. This response is stored per-peer in the batch's inventories map and later consumed by `get_prioritized_attachments_requests`, which for every missing attachment in the batch does `response.pages.iter().find(|page| page.index == page_index)` [4](#0-3) . This is an O(pages) linear scan performed once per `(peer, missing_attachment)` pair, so the attacker-inflated `pages` vector directly multiplies the work the victim node performs. This function is invoked repeatedly on each `AttachmentsDownloader::run()` tick until the batch resolves or times out, so the cost is paid multiple times, not just once.

### Impact Explanation
The impact is bounded compute overhead imposed on the downloading node's Atlas attachment-sync logic: extra CPU cycles scanning an attacker-inflated `pages` vector for every missing attachment in a batch, repeated across polling ticks. It does not corrupt state, does not get relayed/stored as canonical data, and does not crash the node outright — the total body size a peer can send is still constrained by the overall HTTP response size handling in the node's HTTP client stack, so the achievable blow-up is bounded by however many small `AttachmentPage` entries fit in that limit. This matches the "bounded compute DoS on a read endpoint" category for High severity, since the requesting node is effectively acting as a client to an attacker-controlled peer chosen through the normal peer-selection path.

### Likelihood Explanation
The attacker only needs to run their own peer and have it selected as an outbound sync peer with a reachable data URL — no privileged role, secret, or signature is required, matching the allowed attacker model. Any node performing Atlas attachment sync against that malicious peer's URL will trigger the unbounded parse and subsequent repeated linear scans. The cost scales with the number of missing attachments times peers times attacker-supplied `pages.len()`, so it is repeatable on every poll cycle as long as the malicious peer keeps responding.

### Recommendation
In `decode_atlas_attachments_inv_response`, after deserializing, reject or truncate responses where `resp.pages.len() > MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`, and cap/validate each `AttachmentPage.inventory` length against the expected `ATTACHMENTS_INV_PAGE_SIZE`, mirroring the server-side check in `RPCGetAttachmentsInvRequestHandler::try_handle_request`.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/tests.rs` (or `download.rs` tests) that constructs a `StacksHttpResponse` with a JSON body containing a `GetAttachmentsInvResponse` whose `pages` vector has 10,000 `AttachmentPage` entries (each with a small `inventory`), call `decode_atlas_attachments_inv_response` on it and assert it succeeds with `resp.pages.len() == 10000` (showing no cap is applied), then feed that response into the batch's inventories and call `get_prioritized_attachments_requests`, asserting/timing that it iterates all 10,000 pages per missing attachment lookup with no early rejection based on `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`.
