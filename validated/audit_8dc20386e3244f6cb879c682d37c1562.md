### Title
Dust transfer griefing fills `depositTokensOfAccount`/`debtTokensOfAccount` to `MAX_TOKENS_PER_USER`, freezing the victim's ability to add collateral or borrow - (File: contracts/Pool.sol)

### Summary
The memory-leak bug class (repeated attacker-controlled small submissions exhausting a bounded resource) maps onto Metronome's per-account token lists. `Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` share a hard cap of `MAX_TOKENS_PER_USER = 30` per account [1](#0-0) . `DepositToken._transfer` unconditionally pushes the token into the *recipient's* set on first receipt [2](#0-1) . An unprivileged attacker who holds each deposit token can dust-transfer 1 wei of every deposit token to a victim, filling all 30 slots and making any subsequent `deposit`/`transfer`/`seize`/`mint` involving a *new* token for that account revert with `UserReachedMaxTokens` [3](#0-2) .

### Finding Description
- `Pool.addToDepositTokensOfAccount` reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` [3](#0-2) .
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was zero, with no minimum-amount check and no opt-in [4](#0-3) . The same hook runs in `seize` (liquidation) and `_mint` (deposit) [5](#0-4) .
- The attacker deposits a small amount of collateral once per deposit token, keeps ~all of it, and `transfer`s dust to the victim. Each distinct deposit token consumes one of the victim's 30 slots. Repeating across all listed deposit tokens (and forcing the victim to hold dust debt positions is not even needed) saturates the combined limit.
- Once saturated: `DepositToken._mint`/`_transfer` for any token the victim doesn't already hold reverts inside `addToDepositTokensOfAccount`, so the victim cannot receive new collateral types, cannot be deposited-to `onBehalfOf_`, and `DebtToken` issuance (which calls `addToDebtTokensOfAccount`) for a new synthetic also reverts — blocking borrowing entirely.

### Impact Explanation
Liveness/DoS: the victim cannot top-up collateral with a new deposit token and cannot open new debt positions while saturated. If the victim's position is near liquidation, blocking the addition of a different collateral type can push them into liquidation they could otherwise have avoided — an indirect but concrete loss of funds. Cleanup is possible (victim transfers the dust out to drop each token from the set, since `_transfer` removes the entry when the sender balance hits zero [6](#0-5) ), so this is a *temporary* freezing of funds requiring victim gas expenditure, not permanent loss.

### Likelihood Explanation
Requires only an unprivileged account, public `DepositToken.transfer`, and dust balances of up to `MAX_TOKENS_PER_USER` deposit tokens (the pool itself caps deposit tokens at 30 [7](#0-6) , so the attack is bounded and cheap; the attacker retains nearly all deposited funds). No privileged role, oracle manipulation, or timing assumption is needed. Mitigating factor: the victim can self-clean by transferring dust out, so impact is temporary.

### Recommendation
Decouple the cap check: either don't count tokens below a dust threshold, let `addToDepositTokensOfAccount` silently skip rather than revert on cap for unsolicited transfers, or track recipient-initiated vs. forced receipts separately so unsolicited dust cannot consume slots needed for deliberate deposits/mints.

### Proof of Concept
```solidity
// Foundry fork test sketch
// Pre: pool has N registered DepositTokens; victim has 0 positions.
for (uint i; i < 30; ++i) {
    IDepositToken dt = pool.depositTokens(i); // or iterate depositTokenOf
    IERC20 underlying = dt.underlying();
    deal(address(underlying), attacker, dustDeposit);
    underlying.approve(address(dt), dustDeposit);
    dt.deposit(dustDeposit, attacker);          // mints msdTOKEN to attacker
    dt.transfer(victim, 1);                     // pushes dt into victim's set
}
// victim's combined list == 30 now
vm.startPrank(victim);
IERC20(newUnderlying).approve(address(newDepositToken), amount);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDepositToken.deposit(amount, victim);        // _mint -> addToDepositTokensOfAccount reverts
// same revert for debtToken.mint via pool since cap is combined
```

        address sender_,

    ) private updateRewardsBeforeTransfer(sender_, recipient_) {

        if (recipient_ == address(0)) revert TransferToTheZeroAddress();

        uint256 _senderBalanceBefore = balanceOf[sender_];
        if (_senderBalanceBefore < amount_) revert TransferAmountExceedsBalance();

            balanceOf[sender_] = _senderBalanceBefore - amount_;
            balanceOf[recipient_] += amount_;

        // Add this token to the deposit tokens list if the recipient is receiving it for the 1st time

            pool.addToDepositTokensOfAccount(recipient_);
        }

        // Remove this token from the deposit tokens list if the sender's balance goes to zero
