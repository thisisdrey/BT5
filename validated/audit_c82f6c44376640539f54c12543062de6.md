## Analog Found

### Title
Precompiled-contract exceptions escape the sandboxed `CALL` frame and halt the entire outer transaction - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
`Program.callToPrecompiledAddress()` is the boundary that is supposed to sandbox a `CALL`/`DELEGATECALL`/`STATICCALL` into a precompiled ("system") contract: per EVM/TVM semantics, a failing sub-call should only push `0` on the caller's stack and let execution continue. Instead, when the precompile sets an exception on the shared `ProgramResult`, that exception is re-thrown and propagates out of the sandboxed sub-call into the enclosing `VM.play()` loop, halting the whole outer program (and consequently the whole transaction) instead of being contained to the failed inner call.

### Finding Description
`callToPrecompiledAddress()` shares the *outer* frame's `ProgramResult` object with the untrusted precompile before invoking it: [1](#0-0) 

If `contract.execute(data)` returns failure (`out.getLeft() == false`) and the precompile happened to record an exception on that shared result object, the code unconditionally re-throws it: [2](#0-1) 

This exception is not caught anywhere between here and `VM.play()`'s opcode loop, so it propagates through `op.execute(program)` and is caught by the top-level `catch (RuntimeException e)` in `VM.play`, which calls `program.stop()` and re-throws further up into `VMActuator.execute()`, terminating the entire transaction with all energy spent: [3](#0-2) [4](#0-3) 

That this is a recognized, exploitable bug class is confirmed by the codebase's own regression test for "TIP-854 outer-frame containment," which explicitly documents that a malformed `CALL` to `ValidateMultiSign`/`BatchValidateSign` must "leave the outer frame free of any propagated exception" and "allow the outer frame to continue executing afterwards": [5](#0-4) 

However this containment fix is gated behind `VMConfig.allowTvmOsaka()` and only applied to two specific precompiles (`ValidateMultiSign`, `BatchValidateSign`); a dedicated "pre-activation" test explicitly asserts that before this hard fork the *legacy* (unguarded) exception-propagation behavior is preserved: [6](#0-5) [7](#0-6) 

The generic `throw result.getException();` at `Program.java:1764` remains reachable for every other precompiled contract (`ModExp`, `Blake2F`, `P256Verify`, the shielded-proof verifiers, vote/freeze-v2 precompiles, etc.) regardless of the Osaka flag, and for `ValidateMultiSign`/`BatchValidateSign` themselves on any network/fork where `allowTvmOsaka` has not yet activated.

### Impact Explanation
Any unprivileged smart-contract author can deploy a contract that issues a `CALL` to a precompiled address with input crafted to trigger an internal, uncaught exception inside that precompile's execution path. Instead of the sandboxed sub-call simply failing (pushing `0`, as EVM/TVM semantics require and as callers rely on for `try/catch`-style Solidity patterns), the whole outer transaction is aborted: all remaining energy is spent, all internal transactions are rejected, and the caller's own intended fallback/error-handling logic never executes. This is a denial-of-service / call-isolation violation reachable directly from ordinary `TriggerSmartContract` transactions — any contract that calls another (unrelated, possibly third-party) contract which itself calls a precompile can have its execution unexpectedly aborted by conditions the direct caller does not control, breaking the sandboxing guarantee that a `CALL`'s failure is contained to that call.

### Likelihood Explanation
High reachability: the path is triggered purely by an ordinary `CALL`/`DELEGATECALL` opcode to a precompiled address with adversarial calldata — no special permissions, no witness/SR role, and no reliance on race conditions or node configuration are required. The only condition is that the target chain has not yet activated `allowTvmOsaka` (or the target precompile is one of the many not covered by the TIP-854 containment fix), which is the default/legacy behavior this codebase's own tests document as still being exercised.

### Recommendation
Apply the TIP-854 "outer-frame containment" fix unconditionally (not gated by `allowTvmOsaka`) and to all precompiled contracts, not just `ValidateMultiSign`/`BatchValidateSign`: on failure, `callToPrecompiledAddress()` should always push `0`, clear/ignore any exception recorded on the shared `ProgramResult` by the precompile, and continue outer-frame execution — never re-throw the precompile's internal exception out of the sandboxed call boundary.

### Proof of Concept
1. Deploy Contract A with a function that does `call(precompiledAddress, craftedCalldata)`, where `precompiledAddress` is any precompile whose `execute()` can set an exception on `this.result` for malformed input (e.g., `ValidateMultiSign`/`BatchValidateSign` pre-`allowTvmOsaka`, as reproduced by `ValidateMultiSignContractTest.testTip854PreActivationNoOp` / `BatchValidateSignContractTest.testTip854PreActivationNoOp`).
2. Trigger Contract A's function via a normal `TriggerSmartContract` transaction on a network where `allowTvmOsaka` is not active.
3. Observe that instead of the call returning `0` and allowing Contract A to continue (e.g., emit an event or revert gracefully), `VM.play()` halts the whole VM execution (`program.stop()`), `VMActuator.execute()` catches the re-thrown exception, spends all energy, and rejects all internal transactions — confirmed by the assertions removed/relaxed in the "pre-activation" tests versus the strict containment assertions in `testTip854OuterFrameContainment` (only active when `allowTvmOsaka` is turned on).   // TIP-854 outer-frame containment: a CALL to validateMultiSign or
  // batchValidateSign with malformed calldata must (a) push 0 onto the outer
  // stack, (b) leave the outer frame free of any propagated exception, and
  // (c) allow the outer frame to continue executing afterwards.
  @Test
  public void testTip854OuterFrameContainment() throws ContractValidateException {
    byte prePrefixByte = DecodeUtil.addressPreFixByte;
    DecodeUtil.addressPreFixByte = Constant.ADD_PRE_FIX_BYTE_MAINNET;
    VMConfig.initAllowTvmOsaka(1);
    try {
      for (PrecompiledContracts.PrecompiledContract contract :
          new PrecompiledContracts.PrecompiledContract[]{
              new PrecompiledContracts.ValidateMultiSign(),
              new PrecompiledContracts.BatchValidateSign()}) {
        invoke = new ProgramInvokeMockImpl();
        InternalTransaction interTrx = new InternalTransaction(
            Protocol.Transaction.getDefaultInstance(),
            InternalTransaction.TrxType.TRX_UNKNOWN_TYPE);
        program = new Program(new byte[0], new byte[0], invoke, interTrx);
        // inDataSize=0 ⇒ data=[] ⇒ fewer than H=5 head words ⇒ guard rejects.
        MessageCall messageCall = new MessageCall(
            Op.CALL, new DataWord(10000),
            DataWord.ZERO(), DataWord.ZERO(),
            DataWord.ZERO(), DataWord.ZERO(),
            DataWord.ZERO(), DataWord.ZERO(),
            DataWord.ZERO(), false);
        program.callToPrecompiledAddress(messageCall, contract);

        Assert.assertNull(contract.getClass().getSimpleName()
                + ": outer frame must not inherit an exception",
            program.getResult().getException());
        Assert.assertEquals(contract.getClass().getSimpleName() + ": inner CALL pushes 0",
            DataWord.ZERO(), program.getStack().pop());
        // Outer frame continues: another stack op works without throwing.
        program.stackPush(new DataWord(1));
        Assert.assertEquals(new DataWord(1), program.getStack().pop());
      }
    } finally {
      VMConfig.initAllowTvmOsaka(0);
      DecodeUtil.addressPreFixByte = prePrefixByte;
    }
  }
