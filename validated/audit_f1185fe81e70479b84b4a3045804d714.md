### Title
Out-of-bounds heap read in ijar's ZIP central directory parser via crafted JAR/ZIP entry (`InputZipFile::ProcessCentralDirEntry`) - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar`, Bazel's built-in tool used by `java_common.run_ijar`/`stamp_jar`/`pack_sources` to strip Java class files down to interface jars, parses ZIP central directory records via `InputZipFile::ProcessCentralDirEntry`. Unlike the local-file-header parser (`ProcessLocalFileEntry`, `SkipFile`), which validates every field against the remaining mmap'd input via `EnsureRemaining()`, `ProcessCentralDirEntry` never bounds-checks the attacker-controlled `file_name_length`, `extra_field_length`, or the ZIP64 extra-field `data_size` against the actual size of the mapped input file before reading from it.

### Finding Description
`InputZipFile::ProcessCentralDirEntry` reads several 16/32-bit little-endian fields directly from the mmap'd buffer and then: [1](#0-0) 

```
p += 16;  // skip to 'compressed size' field
*compressed_size = get_u4le(p);
*uncompressed_size = get_u4le(p);
u2 file_name_length = get_u2le(p);
u2 extra_field_length = get_u2le(p);
u2 file_comment_length = get_u2le(p);
p += 4;  // skip to external file attributes field
*attr = get_u4le(p);
*offset = get_u4le(p);
{
  size_t len = (file_name_length < filename_size)
    ? file_name_length
    : (filename_size - 1);
  memcpy(reinterpret_cast<void*>(filename), p, len);
  filename[len] = 0;
}
p += file_name_length;
```

`file_name_length`, `extra_field_length`, and `file_comment_length` are each fully attacker-controlled 16-bit values (up to 65535) taken straight from the crafted central directory record. The `memcpy` source pointer `p` and length `len` are only clamped against the destination `filename` buffer size (`PATH_MAX`), never against how many bytes actually remain in the mmap'd ZIP file. If `file_name_length` (or the cumulative advance from `file_comment_length`/`extra_field_length`) exceeds the bytes truly available before the end of the mapped file, `memcpy` reads past the end of the mapping — an out-of-bounds heap read.

The same function's ZIP64 extra-field loop compounds this: [2](#0-1) 

```
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  if (header_id == ZIP64_EXTRA_FIELD_TAG) {
    if (*uncompressed_size == U4_MAX) {
      *uncompressed_size = get_u8le(extra);
    }
    ...
```

`get_u8le(extra)` unconditionally reads 8 bytes starting at `extra` regardless of the attacker-supplied `data_size`, and the loop bound `p` (end of the declared extra field) is itself unchecked against the mapped file's real end. A crafted entry with a tiny or truncated ZIP64 extra field, or an `extra_field_length`/`file_comment_length` that walks `p`/`extra_p` past the end of the file mapping, causes reads beyond the mmap'd region.

By contrast, the *local* file header parser explicitly guards every field read with `EnsureRemaining()`: [3](#0-2) 

showing the project is aware such bounds checks are required for untrusted ZIP input — but this discipline was not applied to the central-directory parser (`ProcessCentralDirEntry` contains none of the 7 `EnsureRemaining` call sites in the file). `EOCD`/`central_dir_size` are validated once at the top level in `FindZipCentralDirectory` [4](#0-3) , but that only bounds the aggregate central directory region against the file, not each individual entry's variable-length fields as they are walked, so a corrupted `file_name_length`/`extra_field_length` inside one entry can still push `p`/`extra_p` past the true end of the mapping before the next signature check is reached.

### Impact Explanation
This is an out-of-bounds heap read directly analogous to CVE-2019-5844 ("out of bounds access... via a crafted [file]"). Any Bazel target that runs `java_common.run_ijar`, `stamp_jar`, or `pack_sources` (i.e. essentially any `java_library`/`java_import` build) invokes `ijar` on jar files that ultimately originate from external, potentially attacker-influenced sources (e.g. jars pulled in via `maven_install`/`http_jar`/third-party dependency archives, or files placed on an untrusted branch that CI builds). A crafted jar with an oversized/truncated central-directory entry can cause `ijar` to read past its mmap'd input buffer, which can crash the build (denial of service) or, depending on heap/mmap layout, leak adjacent process memory into worker state. Because `ijar` is invoked as an ordinary build action (not sandboxed against memory-safety bugs), a heap-buffer-overflow read is a genuine memory-safety violation triggered purely by attacker-supplied archive bytes.

### Likelihood Explanation
`ijar` is invoked automatically on essentially every Java build with jar dependencies via `run_ijar`. Any dependency version whose jar bytes are attacker-influenced (new/unvetted first-time dependency add, a jar produced by an untrusted CI branch, or an internal artifact repository serving a corrupted/malicious jar) reaches this code path with zero additional privilege — the SHA256/integrity check on the download (if present) only verifies the bytes match what was pinned, not that the ZIP structure inside is well-formed; a hostile origin serving that exact pinned/hashed file still reaches the same vulnerable parser. Crafting a ZIP central directory entry with a manipulated `file_name_length`/`extra_field_length`/ZIP64 `data_size` requires no special tooling.

### Recommendation
Add explicit bounds checks in `InputZipFile::ProcessCentralDirEntry` (mirroring `EnsureRemaining()` used in `ProcessLocalFileEntry`/`SkipFile`) before advancing `p` past `file_name_length`, `extra_field_length`, and `file_comment_length`, and validate that each ZIP64 extra-field `data_size` is at least 8 (or the required size) and does not extend `extra_p` past the declared extra field / mapped file boundary before calling `get_u8le`.

### Proof of Concept
A reproducible JUnit/shell test (e.g. added to `third_party/ijar/test/ijar_test.sh` or a new `zip_test.cc`) should:
1. Construct a minimal ZIP file consisting of a valid EOCD/central-directory-size header but with a single central directory entry whose `file_name_length` (or `extra_field_length`) is set to a large value (e.g. `0xFFFF`) that would place `p + file_name_length` beyond the actual mmap'd file length.
2. Run `ijar`/`InputZipFile::ProcessCentralDirEntry` (or the `zip_main.cc` `extract`/list path) on this crafted file under AddressSanitizer.
3. Observe a heap-buffer-overflow (read) report from ASan when `memcpy`/`get_u8le` reads past the mapped file's end, confirming the out-of-bounds access.
