## Finding [1](#0-0) 

This is a genuine local analog of the reported bug class. The report's root cause — a critical timing value ("TGE") that seeds downstream vesting math with **no validation of whether it has actually been set to a meaningful value** — reproduces almost exactly in `pallet-purchase`'s `UnlockBlock` storage item.

### Title
Unvalidated `UnlockBlock` defaults to zero, causing "locked" DOT purchases to unlock immediately upon payout - (File: polkadot/runtime/common/src/purchase/mod.rs)

### Summary
`UnlockBlock<T>` is a `ValueQuery` storage item that defaults to `BlockNumberFor<T>::default()` (i.e. block `0`) until explicitly set via `set_unlock_block`. [1](#0-0)  The `payout` extrinsic reads this value directly and feeds it as the `starting_block` of the vesting schedule applied to the user's locked balance, with no check that `UnlockBlock` has ever been configured away from its zero default: [2](#0-1) 

### Finding Description
The only guard on this value exists in `set_unlock_block`, which enforces `unlock_block > frame_system::Pallet::<T>::block_number()` at the moment it is set: [3](#0-2)  — but this is a configuration-time check, not a consumption-time check. If `payout` executes before `set_unlock_block` has ever been called (or is called on a chain where this pallet is added without a matching genesis/initial call), `UnlockBlock::<T>::get()` silently returns `0`.

That zero value is then passed straight into `T::VestingSchedule::add_vesting_schedule(&who, locked, locked, unlock_block)`. In `pallet-vesting`, `VestingInfo::locked_at` computes `vested_block_count = n.saturating_sub(starting_block)`; with `starting_block = 0` and any post-genesis current block `n > 0`, the schedule is already fully vested the instant it's created (`locked_at` evaluates to `saturating_sub` to a large vested count, so `locked` immediately resolves to `0`). [4](#0-3)  This defeats the entire purpose of the "locked" portion of the DOT purchase — funds meant to be time-locked become fully liquid at the moment of payout, exactly mirroring the reported issue where an unvalidated foundational time value ("TGE") silently corrupts every dependent vesting computation.

### Impact Explanation
This compromises the pallet's intended economic behavior: locked DOT purchase allocations lose their lock guarantee entirely, letting the recipient immediately transfer/spend funds that should have vested linearly to `UnlockBlock`. This is a "runtime bug that compromises intended behavior" per the impact scope — the deployed pallet silently fails to enforce its core invariant (locked funds must vest over time) without any error, warning, or on-chain signal that `UnlockBlock` was never configured.

### Likelihood Explanation
`pallet_purchase` is `#[pallet::without_storage_info]` and its genesis config in the mock/tests explicitly calls `set_unlock_block` before use [5](#0-4) , showing the pallet's own test setup treats this as a mandatory initialization step rather than something enforced by the pallet itself. There is no `integrity_test`, no genesis-build assertion, and no check inside `payout` (or anywhere else) that `UnlockBlock::<T>::get() != Zero::zero()` before it is used to construct a vesting schedule, so any deployment/ordering mistake (missing an explicit `set_unlock_block` call prior to any `payout`) silently triggers the bug — no attacker action is even required, only a missed configuration step, which is a lower bar than most vulnerabilities and matches the audited pattern precisely.

### Recommendation
Add an explicit non-zero/"has-been-configured" guard before consuming `UnlockBlock` in `payout`, e.g. `ensure!(!UnlockBlock::<T>::get().is_zero(), Error::<T>::InvalidUnlockBlock)`, mirroring the recommendation from the original report to validate the seed value separately from its use sites, rather than relying solely on the validation performed at `set_unlock_block` time.

### Proof of Concept
1. Deploy/instantiate a runtime including `pallet_purchase` without ever calling `set_unlock_block` (or reset `UnlockBlock` via a migration/storage wipe as in `remove_pallet`, which clears the value back to default). [6](#0-5) 
2. Configure an account via `create_account` / `update_validity_status` / `update_balance` with a non-zero `locked_balance`. [7](#0-6) 
3. Call `payout` from the configured `PaymentAccount`. [8](#0-7) 
4. Because `UnlockBlock` reads as `0`, the resulting vesting schedule has `starting_block = 0`; at any current block `> 0`, `VestingInfo::locked_at` returns `0`, so `Vesting::vesting_balance` immediately reports the account as fully unlocked despite `locked_balance` being nonzero — confirmable via the same assertions used in `substrate/frame/vesting/src/tests.rs::vested_payout_edge_cases`, which show `starting_block` directly gating whether funds are locked. 	/// Amount locked at block `n`.
	pub fn locked_at<BlockNumberToBalance: Convert<BlockNumber, Balance>>(
		&self,
		n: BlockNumber,
	) -> Balance {
		// Number of blocks that count toward vesting;
		// saturating to 0 when n < starting_block.
		let vested_block_count = n.saturating_sub(self.starting_block);
		let vested_block_count = BlockNumberToBalance::convert(vested_block_count);
		// Return amount that is still locked in vesting.
		vested_block_count
			.checked_mul(&self.per_block()) // `per_block` accessor guarantees at least 1.
			.map(|to_unlock| self.locked.saturating_sub(to_unlock))
			.unwrap_or(Zero::zero())
	}
