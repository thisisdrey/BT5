### Title
Dust-transfer griefing fills a victim's token list to `MAX_TOKENS_PER_USER`, DoSing deposits, issuance, and receipt of new collateral/debt tokens - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to CVE-2023-0412 (a dissector crashing on attacker-supplied input causing DoS), an unprivileged attacker can craft inputs — dust `DepositToken.transfer` calls to a victim — that crash all subsequent entry points which try to add a token to the victim's account list. `Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` revert with `UserReachedMaxTokens()` once the combined list length reaches `MAX_TOKENS_PER_USER = 30` [1](#0-0) [2](#0-1) .

### Finding Description
`DepositToken._transfer` and `_mint` call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance moves from 0 [3](#0-2) [4](#0-3) . The same pattern exists on `DebtToken` mint/issue via `addToDebtTokensOfAccount` [5](#0-4) . Both pool functions are guarded by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which sums `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_)` and reverts at the cap [1](#0-0) .

Attack steps:
1. Attacker acquires dust balances in many pool `DepositToken`s (cheap; pool caps total deposit tokens at 30 anyway [6](#0-5) ).
2. Attacker calls `depositToken.transfer(victim, 1 wei)` for each token type the victim does not yet hold, filling `depositTokensOfAccount[victim]` up to the 30-entry cap (combined with any debt tokens).
3. Subsequently, any `DepositToken.deposit(amount, onBehalfOf = victim)` (including via `NativeTokenGateway`/`VesperGateway`), any `DebtToken.issue(amount, victim)` for a debt token the victim doesn't hold, and any transfer of a new deposit token to the victim reverts inside `_mint`/`_transfer` at `addToDepositTokensOfAccount` [7](#0-6) .

There is no consent check on receiving tokens and no way for the victim to preempt the additions; `SynthContext`/modifiers do not restrict `transfer`.

### Impact Explanation
Temporary freezing of funds / liveness DoS: the victim cannot receive new collateral token types, cannot be issued new debt-token types, and third-party `deposit(..., onBehalfOf_ = victim)` calls (e.g., gateway deposits, airdropped positions, liquidation-related transfers of new token types) all revert. Recovery requires the victim to manually send each dust balance out (or burn via withdraw) to drop below the cap — each removal costs gas and interacts with `depositPositionOf`/`debtPositionOf` oracle reads, so it can also intermittently revert when oracle prices are stale. Attack is cheap: a few wei of each collateral token.

### Likelihood Explanation
Requires the attacker to hold dust of up to ~30 deposit token types (bounded by pool configuration; `addDepositToken` itself caps at `MAX_TOKENS_PER_USER`), so feasibility depends on the number of registered collaterals on a given deployment. On pools with few collaterals the attack cannot fill the cap alone; on mature pools it is trivially repeatable and front-runnable (attacker can top off the list whenever the victim clears a slot). No privileged role needed — `transfer` is a public, unguarded entry point.

### Recommendation
- Allow `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` to skip rather than revert on cap for transfers (or decouple the cap from balance tracking), and/or
- Make list membership opt-in: only add tokens on `deposit`/`issue` initiated by the account itself, not on inbound `transfer`, and/or
- Provide a victim-callable "forceRemoveDustToken" that burns a sub-dust balance to free a slot without requiring a profitable withdrawal.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

// Foundry fork test sketch (fill in fork block + deployed addresses)
contract MaxTokensGriefingTest is Test {
    IPool pool = IPool(POOL);
    address victim = address(0xBEEF);

    function test_DustFillBlocksVictimDeposits() public {
        address[] memory dts = pool.getDepositTokens();
        uint256 existing = pool.getDepositTokensOfAccount(victim).length
                         + pool.getDebtTokensOfAccount(victim).length;

        // attacker fills the victim's list to the cap with 1-wei transfers
        for (uint256 i; existing < 30 && i < dts.length; ++i) {
            IDepositToken dt = IDepositToken(dts[i]);
            if (dt.balanceOf(victim) == 0 && dt.balanceOf(address(this)) > 0) {
                dt.transfer(victim, 1);
                ++existing;
            }
        }
        assertEq(existing, 30);

        // any deposit on behalf of the victim of a token type it doesn't hold reverts
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        IDepositToken(anotherDepositToken).deposit(1e18, victim);

        // same for issuing a new debt token to the victim
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        IDebtToken(anotherDebtToken).issue(1e18, victim);
    }
}
```
