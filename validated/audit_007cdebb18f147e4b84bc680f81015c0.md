### Title
Reliability scoring for attachment-serving peers ignores content-hash validation, allowing score inflation via wrong-hash but well-formed responses - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decides whether to call `report.bump_successful_requests()` or `report.bump_failed_requests()` purely on whether `response.decode_atlas_get_attachment()` succeeds, never checking that the returned attachment's hash matches the requested `content_hash`. A peer can therefore reliably return a syntactically valid but content-mismatched `GetAttachmentResponse` and be scored as if it had served the correct data.

### Finding Description
In `AttachmentsBatchStateContext::extend_with_attachments`: [1](#0-0) 
the only branch condition is `response.decode_atlas_get_attachment()`'s `Ok`/`Err` result. There is no comparison of `response.attachment.hash()` against `request.content_hash` before calling `report.bump_successful_requests()`. This conflates "the HTTP body parsed as valid JSON/hex" with "the attachment is the byte-correct content for the requested hash" — exactly the broken equality identified in the question.

Downstream, in `AttachmentsDownloader::run`, resolved attachments are keyed by the *actual* computed hash of the received bytes, not by the originally requested `content_hash`: [2](#0-1) 
`find_all_attachment_instances(&attachment.hash())` and `resolve_attachment(&attachment.hash())` both use the attacker's actual (wrong) hash, so a mismatched attachment will not be paired with the `AttachmentInstance` that originally required `content_hash`, and `insert_instantiated_attachment` stores the data self-consistently under its own real hash rather than under a forged `content_hash`. This means the wrong-hash content is **not** served as canonical BNS attachment data for the requested name/entry — the AtlasDB's hash-keyed lookup prevents that particular exploitation path.

What *is* real: the `ReliabilityReport` for the offending peer's URL is bumped as "successful" every time it returns any well-formed-but-wrong attachment, with no cost to the attacker and no verification. Because `peers`/`sources` maps carry cloned `ReliabilityReport`s into `AttachmentRequest`/`AttachmentsInventoryRequest` (see `get_prioritized_attachments_requests` and `get_prioritized_attachments_inventory_requests`, lines 376-478), and those types implement `Ord` based on reliability for priority-queue selection, a peer can inflate its own score purely by parsable-junk responses, without ever having to actually resolve any batch entry.

### Impact Explanation
The gameable score lets a malicious peer entrench itself as a "reliable" source in the priority queues used to schedule `AttachmentRequest`/`AttachmentsInventoryRequest` (`BinaryHeap<AttachmentRequest>`, `BinaryHeap<AttachmentsInventoryRequest>`), consuming request slots (bounded by `max_inflight_attachments`) that would otherwise go to genuinely useful peers. Because it never actually resolves the `AttachmentsBatch` entry (the hash mismatch means `resolve_attachment` never fires for the intended instance), each cycle wastes a retry against `max_attachment_retry_count` before the batch is dropped — a bounded-but-real denial of correct attachment resolution for BNS lookups, matching the "attachment/BNS mismatch" High-impact category. It does **not** rise to "serving non-canonical state as canonical," since I could not find any path where the wrong-hash content becomes associated with the requested `content_hash` in the AtlasDB.

### Likelihood Explanation
Trivial precondition: the attacker just needs to run an outbound-syncable peer with a reachable data URL that the victim node discovers and queries for attachments — no privileged role, secret, or StackerDB slot is required. Every response can be crafted to always decode successfully (valid hex/JSON) while carrying arbitrary wrong bytes, so the score can be inflated indefinitely and repeatably at near-zero attacker cost.

### Recommendation
In `extend_with_attachments` (stackslib/src/net/atlas/download.rs, around line 547), after `decode_atlas_get_attachment()` succeeds, additionally verify `response.attachment.hash() == request.content_hash` before calling `bump_successful_requests()`; otherwise call `bump_failed_requests()` (and consider treating it as a faulty/blocklisted peer, similar to the 404 handling in `BatchedRequestsState::try_proceed`).

### Proof of Concept
1. Construct a mock HTTP conversation returning a 200 response whose body is a valid `GetAttachmentResponse` (JSON with a syntactically valid hex `content` field) but whose decoded bytes hash to something other than the `content_hash` in the corresponding `AttachmentRequest`.
2. Drive `BatchedRequestsState` to `Done` with this response in `succeeded`, then call `AttachmentsBatchStateContext::extend_with_attachments` on it.
3. Assert `report.get_score()` (or equivalent) for that peer increased — i.e., `bump_successful_requests()` was invoked — at [1](#0-0) 
despite `response.attachment.hash() != request.content_hash`.
4. Separately assert that after `AttachmentsDownloader::run` reaches `Done`, the `AttachmentInstance` requiring `content_hash` remains unresolved (`attachments_batch.has_fully_succeed()` is `false`), confirming the score inflation is decoupled from actual resolution correctness.
