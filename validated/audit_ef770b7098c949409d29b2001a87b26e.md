### Title
Zero-energy ModExp precompile DoS via unbounded exponent length allocation - (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The TVM `ModExp` precompile (address `0x...05`) lets a caller declare arbitrary `baseLen`, `expLen`, `modLen` header values independent of the actual bytes supplied. When `baseLen == 0` and `modLen == 0`, the energy formula charges **zero energy** regardless of how large `expLen` is, yet `execute()` still unconditionally parses/allocates a byte array and constructs a `BigInteger` of size `expLen` before the zero-modulus short-circuit is reached. This mirrors CVE-2018-0732's pattern: a cheap, attacker-controlled numeric-size parameter (there, a DH prime; here, an exponent length) triggers disproportionate, effectively free computation/memory cost on the victim.

### Finding Description
`ModExp.getEnergyForData()` computes: [1](#0-0) 
`multComplexity = getMultComplexity(max(baseLen, modLen))`. When `baseLen == 0` and `modLen == 0`, `getMultComplexity(0)` returns `0`, so `energy = 0 * adjExpLen / 20 = 0` no matter how large `expLen` is — the cost model is fully insensitive to attacker-controlled exponent size in this branch.

`ModExp.execute()` then does: [2](#0-1) 
The only guard for this degenerate case is `MUtil.checkCPUTimeForModExp()`, which is gated behind a hard-fork activation check: [3](#0-2) 
If that specific fork (`VERSION_4_8_1_1`) has not yet passed on the running chain, this check is a no-op, and execution proceeds to `parseArg(data, ..., expLen)` for the exponent, which allocates and converts a byte array sized by the attacker-declared `expLen` into a `BigInteger` — before the `isZero(mod)` early return is ever reached. The `UPPER_BOUND` (1024-byte) size cap on `baseLen/expLen/modLen` is likewise only enforced when the separate `VMConfig.allowTvmOsaka()` feature flag is active: [4](#0-3) 
So unless both the fork and the Osaka flag are active, an attacker can set `expLen` to a very large value (up to `intValueSafe()` bound, i.e. near `Integer.MAX_VALUE`) while paying essentially zero energy, forcing every validating node to allocate a correspondingly huge byte array/`BigInteger` for free.

### Impact Explanation
Any account can broadcast a `TriggerSmartContract` transaction whose bytecode invokes precompile `0x05` with a crafted call-data header (`baseLen=0`, `modLen=0`, `expLen=<huge>`). Every node that executes/validates this transaction performs the same expensive allocation deterministically, at negligible energy cost to the attacker. This can exhaust heap memory (`OutOfMemoryError`), cause severe GC pauses, or stall block processing across the network — a chain-wide denial of service triggerable from a single unprivileged signed transaction, analogous to how CVE-2018-0732 let a malicious TLS peer force disproportionate compute for near-zero cost.

### Likelihood Explanation
High for chains/testnets where `VERSION_4_8_1_1` has not activated (the guard is explicitly fork-gated, implying older or slower-upgrading networks remain exposed), and independent of `allowTvmOsaka`, which gates a different (size-upper-bound) mitigation. The call requires only a deployed contract and a normal `TriggerSmartContract` transaction — no special privileges, SR/witness status, or network position.

### Recommendation
- Validate/bound `expLen`, `baseLen`, and `modLen` unconditionally (not only when `allowTvmOsaka()` or a specific fork is active) before any allocation occurs in `ModExp.execute()`.
- Charge energy proportional to `expLen` even when `baseLen == 0 && modLen == 0`, or reject the zero-modulus degenerate case outright before parsing the exponent bytes.
- Remove the fork-gating dependency for `checkCPUTimeForModExp()` so the protection is universally active regardless of chain upgrade state, or fold the check directly into `getEnergyForData`/`execute` independent of `ForkController`.

### Proof of Concept
1. Deploy a minimal contract (or use inline assembly via `staticcall`) that calls precompile address `0x05` with call data:
   - `length_of_BASE = 0`
   - `length_of_EXPONENT = 0x7FFFFFFF` (or any very large value)
   - `length_of_MODULUS = 0`
   - No actual base/exponent/modulus bytes need to be supplied (they're zero-padded).
2. Submit via `TriggerSmartContract` on a network where `VERSION_4_8_1_1` has not yet activated.
3. Observe `ModExp.getEnergyForData()` returns `0` energy for this call while `execute()` attempts to allocate/convert a huge byte array for the exponent, as confirmed by the code path at [5](#0-4) .
