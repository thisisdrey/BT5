### Title
Per-token approved address can hijack loan cashflows and permanently block owner recovery via `lock()` - ([File: tare-io__tare-contracts/contracts/LoansNFT.sol])

### Summary
`LoansNFT.lock()` authorizes any address returned by ERC721 `_isAuthorized` — owner, `setApprovalForAll` operator, **or a single-token approved address** — to lock the loan NFT to an arbitrary, attacker-chosen `unlocker` address, exactly mirroring the Derive report's root cause: a critical controlling address (there, the SubAccount "manager"; here, the loan's "unlocker") can be set to an arbitrary value by an unprivileged actor, and once set, the legitimate owner loses the ability to recover.

### Finding Description
`lock(address unlocker, uint256 id)` requires only `_isAuthorized(tokenOwner, msg.sender, id)`: [1](#0-0) 

Per the OpenZeppelin ERC721 semantics, `_isAuthorized` returns true not only for the owner and `setApprovalForAll` operators, but also for a single-token `approve()`d address. This is intentional per the spec, to let `LoansExchange` lock listed loans with narrow per-token approvals instead of `setApprovalForAll`: [2](#0-1) 

However, this means *any* address the investor grants a single-token approval to for an unrelated, narrow purpose (e.g. a marketplace integration, a one-off transfer helper, or any future integrator expecting only `transferFrom` rights) can instead call `lock(attacker, id)`. Once locked:

- `approve()` on that token reverts with `TokenLocked()`, so the owner can no longer revoke the malicious approval or grant a new one to recover: [3](#0-2) 
- Ordinary transfers by the owner revert with `TokenLocked()` in `_update`, since only the `unlocker` (the attacker) can move the token: [4](#0-3) 
- `Loans.investorWithdraw()` routes **all** future principal/interest cashflows to `msg.sender == unlocker`, not to the actual `ownerOf(loanId)`, once a loan is locked: [5](#0-4) 
- The guardian recovery path `forceTransfer` explicitly refuses to act on locked tokens (`require(_unlockers[tokenId] == address(0), TokenLocked())`), so even privileged intervention cannot restore the NFT while it remains locked to the attacker: [6](#0-5) 
- Only the attacker-chosen `unlocker` can call `unlock()`: [7](#0-6) 

This is the same bug class as the Derive report: an unprivileged party sets an arbitrary address into a role that gains exclusive future control (there: "manager"; here: "unlocker"), and the design assumes that role will only ever be filled by a trusted protocol contract (`LoansExchange`), but nothing on-chain enforces that. The spec's own risk analysis argues this is safe because "a per-token approved address can already transfer the token outright" — but that comparison only covers outright NFT theft. Locking is a *worse* and *distinct* outcome: the NFT stays visibly owned by the honest investor (so it does not look stolen, is not flagged, and the investor may never think to act), while cashflows silently redirect to the attacker and both self-service (`approve`/`transferFrom`) and admin-service (`forceTransfer`) recovery paths are blocked for as long as the lock persists.

### Impact Explanation
This directly matches the Tare Allowed Impact Gate: **diversion of loan cashflows away from the honest investor**, and **permanent/practically unrecoverable lock of the loan NFT and its cashflows caused by an unprivileged path** (a single-token `approve()` holder, not a guardian/admin/servicer). The investor's principal and interest repayments (`investorWithdraw`) are redirected to the attacker for the life of the loan, and the NFT itself is effectively frozen since neither the owner nor the guardian's `forceTransfer` can clear the lock — only the attacker can, and they have no incentive to.

### Likelihood Explanation
Requires the investor (or an address `setApprovalForAll`'d by the investor) to have granted a single-token `approve()` to some third-party contract or address for a legitimate purpose (e.g., integrating with a future marketplace, automation bot, or any tool expecting standard ERC721 approval semantics) that turns out to be malicious or compromised, or whose access is later exploited. Given `LoansExchange` itself is designed around exactly this trust pattern (per-token approval → lock), any other integrator following the same documented pattern — or a compromised/malicious one — can trigger this with a single transaction once approval is granted. This is a realistic path since per-token `approve()` is a standard, expected, and encouraged integration mechanism per the project's own docs.

### Recommendation
Restrict `lock()` authorization to the token owner and `setApprovalForAll` operators only (removing single-token approved addresses from the authorized set), and instead require `LoansExchange` (and any future integrator) to use `setApprovalForAll` for lock-capable integrations. Alternatively, introduce an on-chain whitelist of addresses (e.g., `LoansExchange`) permitted to be passed as `unlocker`, and/or allow the token owner (not just the unlocker) to force-unlock after a timeout, and permit `forceTransfer`/guardian recovery to override stale/malicious locks under guardian control.

### Proof of Concept
1. Investor owns loan NFT `id` and calls `loansNFT.approve(evilContract, id)` for what they believe is a narrow, single-use integration.
2. `evilContract` (single-token approved, not owner) calls `loansNFT.lock(attackerAddress, id)`. This succeeds because `_isAuthorized` returns true for a per-token approved caller: [1](#0-0) 
3. Investor tries `loansNFT.approve(newAddress, id)` to revoke/replace — reverts `TokenLocked()`. Investor tries `transferFrom` — reverts `TokenLocked()` in `_update`.
4. `attackerAddress` calls `loans.investorWithdraw([id], ...)`; because `getLocked(id) == attackerAddress`, `cachedUnlocker != address(0)` and `recipient = msg.sender = attackerAddress`, so all principal/interest cash is sent to the attacker instead of the investor: [8](#0-7) 
5. Guardian attempts `loansNFT.forceTransfer(investor, recoveryAddress, id)` to rescue the NFT — reverts `TokenLocked()`: [6](#0-5) 
6. The loan's cashflows remain permanently diverted to `attackerAddress` and the NFT remains unrecoverable until (never, in practice) the attacker calls `unlock()`.

```text
  function lock(address unlocker, uint256 id) external {
    address tokenOwner = ownerOf(id);

    require(unlocker != address(0), InvalidUnlocker());
    require(_unlockers[id] == address(0), AlreadyLocked());
    require(_isAuthorized(tokenOwner, msg.sender, id), Unauthorized());

    // Clear approval
    _approve(address(0), id, address(0), false);
    _unlockers[id] = unlocker;

    emit Lock(unlocker, id);
  }
```

```markdown
`LoansNFT` implements ERC-5753-compatible locking:

- `lock(address unlocker, uint256 id)` — token owner, token-approved address, or approved operator designates an `unlocker` for a token. The token can no longer be transferred by anyone other than the `unlocker`. Allowing token-approved addresses to lock is an intentional deviation from the ERC-5753 reference implementation (owner or operator only): it lets integrators such as `LoansExchange` lock listed loans with narrow per-token approvals instead of requiring `setApprovalForAll` over the owner's entire collection, and grants no new power since a per-token approved address can already transfer the token outright.
- `unlock(uint256 id)` — only the current `unlocker` can clear the lock without transferring.
```
