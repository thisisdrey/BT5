## #Vulnerability found for this question — analog confirmed

### Title
Token-2022 transfer-hook revert can permanently lock depositor funds in a bank's liquidity vault - (File: `programs/marginfi/src/state/bank.rs`)

### Summary
The ERC-777 `tokensReceived` DoS pattern (a token whose transfer callback can be forced to revert by the counter-party, freezing settlement) has a direct analog in marginfi-v2's SPL Token-2022 support. `withdraw_spl_transfer` and `deposit_spl_transfer` route Token-2022 transfers through `spl_token_2022::onchain::invoke_transfer_checked`, which invokes the mint's **transfer-hook program** if the mint has one configured [1](#0-0) . Unlike `lending_pool_emissions_deposit`, which explicitly rejects hook-enabled mints via `utils::has_transfer_hook` before transferring [2](#0-1) , the core withdraw, repay, and liquidation paths perform no such check.

### Finding Description
`withdraw_spl_transfer` is called from `lending_account_withdraw` [3](#0-2) , liquidation settlement [4](#0-3) , and fee withdrawal, and `deposit_spl_transfer` is called from `lending_account_repay` [5](#0-4) . For Token-2022 mints, both helpers invoke `spl_token_2022::onchain::invoke_transfer_checked`, which — per the Token-2022 transfer-hook extension — will CPI into whatever program is registered as the mint's transfer hook [6](#0-5) . `has_transfer_hook` (used only in `emissions_deposit`) confirms this mechanism exists and is understood by the team as a risk to guard against [7](#0-6) .

Because a Token-2022 mint's transfer-hook *program* can be swapped by whoever controls the mint's `TransferHook` authority independently of anything marginfi's admin does at `lending_pool_add_bank` time, a token that looks safe when the bank is created can later be given a hook that:
- succeeds on deposit (so deposits into the bank continue normally), but
- unconditionally reverts on the vault-to-depositor leg (withdraw, repay-triggered accounting is unaffected but this only matters for outgoing legs, and critically the liquidation-time `withdraw_spl_transfer` used to pay the insurance fund/liquidator).

This exactly mirrors the referenced ERC-777 finding: the recipient-side hook is optional/attacker-controlled and can be weaponized specifically against the "pay-out" leg of a transfer, while the "pay-in" leg keeps working, so the counterparty can lock funds already committed to the vault.

### Impact Explanation
If a bank is created (or, more narrowly, a bank's mint's hook program is later maliciously updated) for a Token-2022 mint with a transfer hook that selectively reverts on outbound transfers, every depositor's principal held in that bank's `liquidity_vault` becomes permanently unwithdrawable — `lending_account_withdraw`, liquidation payouts (`withdraw_spl_transfer` for insurance fee / liquidatee proceeds), and fee withdrawals all fail deterministically, while deposits/repays (`deposit_spl_transfer`) keep succeeding and growing the trapped balance. This is a permanent freeze of user funds in an unprivileged, reachable core-accounting path (withdraw/repay/liquidation), matching the "permanent lock/freeze" impact bar.

### Likelihood Explanation
Likelihood is bounded by the fact that Token-2022 mints must currently be explicitly admin-approved for a bank (`lending_pool_add_bank`/`_with_seed`/`_permissionless`), so the initial bank listing is gated. However, the check that would prevent this — `has_transfer_hook` — is applied only in `lending_pool_emissions_deposit`, not in `lending_account_withdraw`, `lending_account_repay`, or liquidation. Any admin-approved Token-2022 mint whose hook authority is not permanently revoked (or any mint where a hook is added/changed post-listing) can trigger this without further marginfi-side privilege, i.e. the freeze is triggered by an external, unprivileged actor (the mint/hook controller), not by marginfi's admin.

### Recommendation
Apply the same `has_transfer_hook` (and `nonzero_fee`) guard used in `lending_pool_emissions_deposit` inside `deposit_spl_transfer`/`withdraw_spl_transfer` in `bank.rs`, or enforce it once at `lending_pool_add_bank`/`configure_bank` time and re-validate it on every withdraw/repay/liquidation transfer (since a hook can be attached after bank creation). Alternatively, maintain an explicit allow-list of vetted Token-2022 extension combinations for bank mints and reject any mint that can have a transfer hook attached at all.

### Proof of Concept
1. Admin lists a Token-2022 bank for mint `M` that currently has no transfer hook (passes `add_bank`).
2. Users deposit `M` into the bank; `deposit_spl_transfer` succeeds (Token-2022 CPI, no hook to invoke).
3. The party controlling `M`'s `TransferHook` extension authority sets a hook program `H` that: allows transfers where `to == liquidity_vault` (deposits) but reverts when `from == liquidity_vault` (withdrawals/liquidation payouts).
4. Any user calling `lending_account_withdraw`, or any liquidator triggering `liquidate` on a position collateralized/owed in `M`, hits `withdraw_spl_transfer` → `invoke_transfer_checked` → CPI into `H` → revert.
5. All depositors of that bank now have unwithdrawable principal; liquidations of debt denominated in `M` and insurance-fee payouts denominated in `M` also permanently fail, while new deposits continue to inflate the trapped vault balance.

/// Returns `true` if the given mint has an active transfer hook program.
/// If the hook is present but no program is active it would return false.
pub fn has_transfer_hook(mint_ai: AccountInfo) -> MarginfiResult<bool> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(false);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    if let Ok(hook) = mint.get_extension::<TransferHook>() {
        let program_id: Option<Pubkey> = Option::from(hook.program_id);
        return Ok(program_id.is_some());
    }

    Ok(false)
}
