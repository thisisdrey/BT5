### Title
Unvalidated raw storage entries in `DeterministicStateInitAction` allow bypassing contract-code invariants at account creation - (File: `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
`DeterministicStateInitAction` lets any ordinary signer create a "deterministic account" that runs a chosen (possibly shared/global) contract, with an attacker-chosen set of raw key/value pairs installed directly as that account's contract storage. The handler writes these bytes straight into the trie without ever executing the referenced contract's own initialization logic, and NEAR's action validation only checks size limits, not content or schema correctness — structurally the same "unvalidated write of privileged/raw storage" flaw as the reported `upgrade_storage` bug.

### Finding Description
`validate_deterministic_state_init` (`runtime/runtime/src/action_validation.rs:435-471`) only verifies that the derived account id matches the receiver and that each `(key, value)` pair in `action.state_init.data()` does not exceed `max_length_storage_key`/`max_length_storage_value`. It performs **no validation whatsoever of the content, schema, or internal consistency** of the data being installed as contract storage: [1](#0-0) 

At execution time, `deploy_deterministic_account` (`runtime/runtime/src/deterministic_account_id.rs:121-155`) sets the contract code via `use_global_contract` and then writes every attacker-supplied `(key, value)` pair directly into `TrieKey::ContractData` for the new account: [2](#0-1) 

Crucially, this bypasses any `new()`/initialization method the deployed contract code would normally require to establish its invariants (e.g., asserting `total_supply == sum(balances)`, or `owner == predecessor`). Unlike `storage_write`, which can only be invoked from inside the account's own already-running (and therefore access-controlled) contract code, `DeterministicStateInitAction` force-writes storage entries before the contract has ever executed a single instruction — exactly analogous to the SYMinter `upgrade_storage` handler calling `set_data` on a user-supplied cell without checking that it parses into the fields `load_data` expects.

Because the referenced code is looked up purely by hash/account id (`GlobalContractIdentifier`) and can be an already-widely-deployed, trusted global contract (e.g., a template used by many independent instances, per `docs/DataStructures/Account.md:138-190` describing NEP-616 deterministic accounts), any account created this way is indistinguishable on-chain from one that went through the contract's real constructor. If a downstream integrator (a bridge, DEX, or accounting system) trusts state read from such accounts (e.g., a `LookupMap`-backed balance/supply field, or an owner/authorization field) without the contract's own view methods independently reconciling it against real deposited NEAR balance or verifiable external state, an attacker can forge a "valid-looking" instance whose internal bookkeeping (e.g., a token balance/supply counter) was never actually backed by a deposit or a legitimate mint call.

### Impact Explanation
This maps to the report's core defect class ("privileged/raw write of unvalidated data as contract storage, bypassing the code path that would normally validate it"). If exploited against a global contract whose logic assumes its storage was always populated through its own constructor/mint logic, it enables forging contract-internal counters (balances, supply, ownership) with no real backing — a token-inflation/authorization-escalation primitive. This is more severe than the original TON report's plain DoS, because here the write is available to **any unprivileged signer at account-creation time**, not merely an already-trusted admin performing a maintenance operation.

### Likelihood Explanation
Likelihood depends entirely on whether any global contract intended for reuse via `DeterministicStateInitAction` fails to re-validate its own invariants on every call (rather than trusting state as "already correct" because it was set at init time). I could not find, within the indexed portion of the codebase, a concrete first-party global contract shipped by nearcore that is vulnerable to this pattern (the shipped ETH-implicit `wallet_contract` is deployed only via the dedicated implicit-account-creation path, not via `DeterministicStateInitAction`). This is therefore a protocol-level capability whose exploitability is contract-dependent, and I was not able to confirm a concretely deployed victim contract using the tools available.

### Recommendation
- Document explicitly (in NEP-616 / protocol docs) that any global contract intended to be instantiated via `DeterministicStateInitAction` **must** treat pre-populated storage as untrusted input and re-validate its invariants (balances, supply, ownership fields) on every method call rather than assuming they were set correctly at creation.
- Consider requiring contracts that opt into deterministic-account instantiation to expose/require an explicit "post-init validation" hook that the protocol invokes once before the account becomes callable, so malformed or adversarial initial state is rejected at creation time rather than silently accepted, mirroring the short-term recommendation from the original report ("validate that the data conforms to the expected format before persisting it").

### Proof of Concept
Conceptual (protocol-level) PoC, since no concrete first-party vulnerable global contract was located during this investigation:
1. Locate/author a global contract `C` intended to be reused via `GlobalContractIdentifier`, whose storage layout includes a self-reported numeric field (e.g., `balance` or `total_supply`) that its public methods (e.g., `transfer`, `withdraw`) trust without cross-checking against real NEAR balance or an authoritative mint log.
2. Submit a `DeterministicStateInitAction` with `code = GlobalContractIdentifier::CodeHash(hash(C))` and `data` containing raw borsh/serialized bytes at the exact trie keys `C` uses internally to store that field, set to an arbitrary large value — bypassing `C`'s `new()`/mint constructor entirely (`runtime/runtime/src/deterministic_account_id.rs:135-152`).
3. Attach only the minimal deposit needed to satisfy `check_storage_stake` (no funds backing the forged field).
4. Call `C`'s public transfer/withdraw method on the newly created deterministic account to move the forged balance to a real account, realizing token inflation with no corresponding backing deposit. [3](#0-2) [4](#0-3)

pub(crate) fn action_deterministic_state_init(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    maybe_account: &mut Option<Account>,
    account_id: &AccountId,
    receipt: &Receipt,
    action: &DeterministicStateInitAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // See https://github.com/near/NEPs/blob/master/neps/nep-0616.md#account-state
    // for the detailed description around deterministic account state.
    let storage_usage_config = &apply_state.config.fees.storage_usage_config;
    let account = match maybe_account {
        Some(account) => account,
        None => {
            // cspell:ignore nonexist
            // `nonexist` -> `uninit` account state transition
            // Create with zero balance now and check later how much of the
            // provided deposit is needed.
            let new_account = create_deterministic_account(Balance::ZERO, storage_usage_config);
            maybe_account.insert(new_account)
        }
    };
    if account.contract().is_none() {
        // `uninit` -> `active` account state transition. "uninit" here is the
        // NEP-616 sense, a deterministic account with no contract yet, not
        // `Account::Uninitialized`: a `0u` id can never reach this, because
        // `validate_deterministic_state_init` pins the receiver to the derived
        // `0s` id.
        deploy_deterministic_account(
            state_update,
            account,
            account_id,
            &action.state_init,
            result,
            storage_usage_config,
        )?;
    }
