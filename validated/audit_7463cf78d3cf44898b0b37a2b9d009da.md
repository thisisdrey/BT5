### Title
SSRF via unrestricted `transfer.bundleURI` in `FetchRemote`/`UpdateRemoteMirror` remote fetches - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`CreateRepositoryFromURL` was explicitly patched to disable Git's bundle-URI feature (`transfer.bundleURI=false`) before cloning from an attacker-influenced URL, with the comment stating this is "to prevent attack vectors that could abuse this mechanism" because "the URI can point to any server, including localhost." [1](#0-0)  However, the same class of remote-URL fetch operations reachable via `FetchRemote` and `UpdateRemoteMirror` (used for pull/push mirrors) build their `git fetch`/`git ls-remote` configuration without this mitigation.

### Finding Description
Git's protocol v2 bundle-URI capability allows a remote server to advertise an arbitrary URI during ref negotiation; when enabled, the local Git client (via `git fetch`) will follow that URI and issue an HTTP(S) request to it in order to download an initial bundle. This is exactly the SSRF pattern in the referenced report: a server-controlled directive causes the local process to fetch attacker-chosen network locations (including link-local/internal addresses).

Gitaly's own code acknowledges this risk and mitigates it in one place — `cloneFromURLCommand`, used by `CreateRepositoryFromURL` — by forcing `transfer.bundleURI=false` as a global git option before invoking `git clone` against an arbitrary user-supplied URL: [2](#0-1) 

By contrast, `buildCommandOpts`, which constructs the git configuration used by `FetchRemote` (invoked from `fetchRemoteAtomic`) to fetch from an arbitrary, caller-supplied `RemoteParams.Url`, never sets `transfer.bundleURI`: [3](#0-2) 

Similarly, `updateRemoteMirror` builds the remote configuration for `git ls-remote`/`GetRemoteReferences` from an arbitrary `Remote.Url` supplied in the RPC request, again without disabling bundle-URI support: [4](#0-3) 

Both RPCs accept a remote URL over which the caller has full control (e.g. a project's configured pull-mirror URL, or an import source, ultimately supplied by an ordinary user via GitLab's mirror/import feature, then forwarded verbatim as `FetchRemoteRequest.RemoteParams.Url` / `UpdateRemoteMirrorRequest.Remote.Url`), and both invoke Git against a remote server that is fully attacker-controlled from Gitaly's perspective. If the SSRF-prevention fix applied to `CreateRepositoryFromURL` is necessary there, the identical attack surface exists in these two RPCs, since Git's bundle-URI resolution logic is a property of the local `git` invocation and not specific to `git clone`.

### Impact Explanation
An attacker who controls (or can redirect) the remote git server used as a pull-mirror or fetch source can have Gitaly's `git fetch`/`git ls-remote` process follow a maliciously advertised bundle URI pointing at internal-only network endpoints (e.g., cloud metadata services, internal APIs, or other Gitaly/Praefect nodes), resulting in server-side request forgery from within the Gitaly host's network context. This can be used to probe internal infrastructure or exfiltrate data reachable only from the Gitaly node, mirroring the impact described in the referenced PlantUML report.

### Likelihood Explanation
Any ordinary user who can configure a pull mirror (`FetchRemote`) or push mirror (`UpdateRemoteMirror`) to a URL they control can trigger this path without any special privilege beyond normal project mirror/import configuration — this is a standard, commonly used GitLab feature. The remote server is attacker-operated by design, so no additional compromise (MITM, leaked token, malicious peer) is required beyond what the feature already permits.

### Recommendation
Apply the same mitigation used in `cloneFromURLCommand` to `buildCommandOpts` (`FetchRemote`) and to the remote configuration built in `updateRemoteMirror` (`UpdateRemoteMirror`): explicitly set `transfer.bundleURI=false` (or otherwise disable bundle-URI advertisement following) as a global git config option whenever fetching/negotiating with an externally-supplied remote URL.

### Proof of Concept
1. As an ordinary GitLab user, configure a pull mirror (or a project import) for a repository, pointing the mirror URL at an attacker-controlled Git HTTP server.
2. The attacker-controlled server implements Git's protocol v2 `bundle-uri` capability and advertises a bundle URI such as `http://169.254.169.254/latest/meta-data/` (or another internal address) in response to the `ls-refs`/capability negotiation performed by Gitaly's `FetchRemote` RPC (`fetchRemoteAtomic` → `quarantineRepo.FetchRemote`).
3. Because `buildCommandOpts` does not set `transfer.bundleURI=false`, the `git fetch` process spawned by Gitaly follows the advertised bundle URI and issues an outbound request to the internal address from the Gitaly host.
4. The same can be reproduced via `UpdateRemoteMirror`, whose `remoteConfig` (used for `git ls-remote`/`GetRemoteReferences`) likewise omits the `transfer.bundleURI=false` setting.

Note: I could not directly confirm Gitaly's process-wide default value of `transfer.bundleURI` (e.g., whether a global gitconfig sets it to `true` by default) within the available index; this would need to be verified in a live Devin session by inspecting Gitaly's git command factory defaults and by reproducing the fetch against a bundle-uri-advertising test server (the repo already includes a `bundle-uri-runner` test harness at `_support/custom_runners/bundle-uri-runner/`) to confirm the outbound request actually occurs.

func buildCommandOpts(ctx context.Context, opts *localrepo.FetchOpts, req *gitalypb.FetchRemoteRequest) error {
	remoteURL := req.GetRemoteParams().GetUrl()
	var config []gitcmd.ConfigPair

	for _, refspec := range getRefspecs(req.GetRemoteParams().GetMirrorRefmaps()) {
		config = append(config, gitcmd.ConfigPair{
			Key: "remote.inmemory.fetch", Value: refspec,
		})
	}

	if resolvedAddress := req.GetRemoteParams().GetResolvedAddress(); resolvedAddress != "" {
		modifiedURL, resolveConfig, err := gitcmd.GetURLAndResolveConfig(remoteURL, resolvedAddress)
		if err != nil {
			return fmt.Errorf("couldn't get curloptResolve config: %w", err)
		}

		remoteURL = modifiedURL
		config = append(config, resolveConfig...)
	}

	config = append(config, gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL})

	if featureflag.FetchRemoteProactiveAuth.IsEnabled(ctx) {
		if u, err := url.Parse(remoteURL); err == nil && u.User != nil {
			password, _ := u.User.Password()
			if u.User.Username() != "" && password != "" {
				config = append(config, gitcmd.ConfigPair{
					Key:   "http.proactiveAuth",
					Value: "basic",
				})
			}
		}
	}

	if authHeader := req.GetRemoteParams().GetHttpAuthorizationHeader(); authHeader != "" {
		config = append(config, gitcmd.ConfigPair{
			Key:   fmt.Sprintf("http.%s.extraHeader", req.GetRemoteParams().GetUrl()),
			Value: "Authorization: " + authHeader,
		})
	}

	opts.CommandOptions = append(opts.CommandOptions, gitcmd.WithConfigEnv(config...))

	return nil
}
