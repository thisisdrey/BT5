### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign` precompile leads to node OOM / DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (invoked via a `CALL` to the TVM precompile address from any smart contract, i.e. reachable by any unprivileged transaction sender) parses a caller-supplied signature-array length and uses it directly to allocate a Java array before any bound check is applied, mirroring the CVE-2025-28162 bug class of unbounded/unchecked buffer allocation from attacker input leading to high memory usage and unresponsiveness.

### Finding Description
`ValidateMultiSign.execute()` reads a signature-array length from the raw calldata and, when the `allowTvmSelfdestructRestriction` hard-fork flag is not active, calls `extractBytesArray()` directly without first validating the length against `MAX_SIZE`: [1](#0-0) 

`extractBytesArray()` takes the attacker-controlled `len` value from `words[offset].intValueSafe()` and immediately allocates a `byte[][]` of that size before performing any range/size validation: [2](#0-1) 

The `MAX_SIZE` (5) check on `signatures.length` only happens **after** the array has already been fully allocated and populated: [3](#0-2) 

Because `DataWord.intValueSafe()` clamps a 256-bit word to a (large) positive `int`, a malicious contract caller can craft calldata with a huge sig-array length field, forcing the node to attempt allocation of a very large `byte[][]` (and subsequent `System.arraycopy` calls inside the loop), which is the same class of attacker-supplied-length-driven memory exhaustion the libpng CVE describes (uncontrolled allocation causing high memory usage and program unresponsiveness).

### Impact Explanation
Any account can craft and broadcast a single transaction that deploys or calls a contract invoking the `ValidateMultiSign` precompile with an oversized encoded signature-array length. This can force the executing node to attempt a very large heap allocation, risking an `OutOfMemoryError` and destabilizing/crashing the node process — a denial-of-service against the node that must execute the transaction (validators and full nodes alike), matching the "node crash or halt" / "API the node can no longer serve" impact bar.

### Likelihood Explanation
The precompile is reachable by any address via a normal `CALL` from a deployed contract; no special privilege, staking, or witness/SR role is required — only that the `allowTvmSelfdestructRestriction` maintenance flag has not (yet) been activated on the network being targeted, in which case the pre-allocation bound check is skipped entirely.

### Recommendation
Validate the decoded signature-array length against `MAX_SIZE` (or another sane upper bound) in `extractBytesArray()`/`extractSigArray()` **before** allocating the output array, independent of the `allowTvmSelfdestructRestriction` flag, so the check is unconditional rather than gated behind a hard fork switch.

### Proof of Concept
1. Deploy a trivial contract that performs a `staticcall`/`call` to the `ValidateMultiSign` precompile address.
2. Encode calldata per the ABI layout expected by `ValidateMultiSign.execute` (`address`, `permissionId`, `data`, then the offset/length header for the signature array) such that the length word at the computed `sigArraySize` offset is set to a very large positive integer (near `Integer.MAX_VALUE`).
3. Broadcast a transaction triggering this call on a network where `allowTvmSelfdestructRestriction` is disabled.
4. Observe `extractBytesArray()` attempt `new byte[len][]`, driving up heap usage and potentially triggering an `OutOfMemoryError` in the executing node.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
