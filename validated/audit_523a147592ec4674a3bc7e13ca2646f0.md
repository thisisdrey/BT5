### Title
Attached deposit is silently trapped on synchronous error paths of `rlp_execute` in the eth-implicit wallet contract - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `#[payable]` entry point `rlp_execute` of the eth-implicit wallet contract accepts an attached NEAR deposit from any caller and only refunds it through an asynchronous promise-based mechanism (`CallerDeposit`) that fires inside `rlp_execute_callback`. Several validation-failure paths in `inner_rlp_execute` return an `Err` before any promise is ever created, so `rlp_execute` falls into the synchronous `PromiseOrValue::Value(e.into())` branch. In that branch the `caller_deposit` value computed inside `inner_rlp_execute` is simply dropped — no promise is scheduled and no refund is issued — even though the deposit was already credited to the contract's own account balance by the protocol before the method body ran.

### Finding Description
`rlp_execute` is marked `#[payable]`, so per NEAR's Economics API any deposit attached to the call is credited to `current_account_id` (the wallet) before the method body executes: "`attached_deposit` -- the balance that was attached to the call that will be immediately deposited before the contract execution starts" [1](#0-0) .

Inside `inner_rlp_execute`, the deposit is wrapped into an optional `CallerDeposit` only when the predecessor differs from the wallet's own account [2](#0-1) , and this value is threaded through the various cross-contract promise chains so it can be refunded from `rlp_execute_callback` if the resulting promise later fails [3](#0-2) .

However, `inner_rlp_execute` has multiple early `return Err(...)` paths that occur *before* any promise (and therefore before `caller_deposit`) is ever attached to a scheduled callback — e.g. relayer validation failures (`InvalidSender`, `InvalidChainId`, `InvalidTarget`, `InvalidNonce`, `InsufficientGas`) and user errors (`ExcessYoctoNear`, `ValueTooLarge`, unsupported actions, etc.) [4](#0-3) . When `inner_rlp_execute` returns such an `Err`, the caller in `rlp_execute` takes the synchronous branch:

```
Err(e) => PromiseOrValue::Value(e.into()),
``` [5](#0-4) 

In this branch, `caller_deposit` (already computed locally inside `inner_rlp_execute` from the real attached deposit) is discarded along with the rest of `inner_rlp_execute`'s local state. No promise, transfer, or refund is scheduled, and the response is returned as a plain `Value`, matching the contract's stated design goal that `rlp_execute` "should never panic" so the wallet's other state changes (like nonce increments or key bans) can still take effect [6](#0-5) . But because the deposit was already merged into the wallet's account balance by the protocol at call time, the caller who attached it has no way to recover it: the refund path exists only for the promise-based `PromiseResult::Failed` case inside `rlp_execute_callback`, never for these synchronous validation failures.

This is the direct analog of the Dexter "amount sent" bug class: a function that legitimately accepts an attached amount for one purpose (funding an inner action or compensating a relayer) fails to protect/refund it on error paths that don't consume it, silently converting any external caller's mistaken or unlucky deposit into a permanent, uncompensated transfer to the wallet account.

### Impact Explanation
Any external account (a relayer, or an ordinary user acting as a "relayer" for someone else's wallet, which is the intended permissionless usage pattern of this contract) that calls `rlp_execute` with a non-zero attached deposit and whose call happens to hit any of the early relayer/user validation errors (stale nonce due to a race with another relayer, wrong `target`, insufficient `gas_limit`, malformed transaction fields, etc.) will have that deposit irreversibly and silently absorbed into the wallet contract's own balance, with the transaction still reporting a soft `ExecuteResponse { success: false }` rather than reverting. This is a concrete, unconsented transfer of NEAR from the caller to the wallet account — a fund-loss condition for the caller.

### Likelihood Explanation
The `rlp_execute` method is explicitly designed to be called by arbitrary third-party relayers on behalf of a wallet owner (an intentional, permissionless design), so external, unprivileged callers regularly attach deposits (e.g., to cover ERC-20 storage-deposit costs or emulated-transfer fees) as part of normal expected usage. Validation failures such as nonce races between concurrent relayers, or malformed/late relayer submissions, are realistic operational occurrences, not solely adversarial ones — so the trapped-deposit condition is readily reachable under normal usage, not just a contrived edge case.

### Recommendation
- Ensure any non-zero deposit attached by an external (non-self) caller is unconditionally refunded on every failure path of `rlp_execute`/`inner_rlp_execute`, including the synchronous `Err` branch that currently returns `PromiseOrValue::Value(e.into())` without spawning a refund promise.
- Alternatively, require `rlp_execute` to reject (revert) any call carrying an attached deposit unless the parsed action can be shown, before deposit consumption is finalized, to actually need it — mirroring the "short-term" Dexter recommendation of reverting non-zero, unused amounts.
- Add integration tests exercising each `Error::Relayer` / `Error::User` early-return path with a non-zero attached deposit from a distinct predecessor account, asserting the deposit is refunded to the caller.

### Proof of Concept
Conceptual reproduction (based on code inspection; not executed):
1. Deploy an eth-implicit wallet contract at account `0xabc...` owned by Alice.
2. Have an unrelated external account `relayer.near` call `wallet.rlp_execute(target, tx_bytes_b64)` attaching e.g. 1 NEAR, where `tx_bytes_b64` encodes a validly-signed Ethereum tx but with a `nonce` that does not match the wallet's current on-chain nonce (e.g., because another relayer's transaction was just accepted first) — triggering `RelayerError::InvalidNonce` inside `validate_tx_relayer_data` [7](#0-6) .
3. `inner_rlp_execute` returns `Err(Error::Relayer(RelayerError::InvalidNonce))` before any promise/`caller_deposit` handling occurs.
4. In `rlp_execute`, since `env::signer_account_id() != current_account_id` (relayer signed with its own key, not the wallet's), execution falls into `Err(e) => PromiseOrValue::Value(e.into())` [8](#0-7) .
5. The call returns `ExecuteResponse { success: false, error: Some("...") }`, but the 1 NEAR attached by `relayer.near` has already been credited to the wallet account's balance and is never refunded.

I was not able to execute this scenario directly (no sandbox/test runner access in this mode); this reconstruction is based on static analysis of `rlp_execute`, `inner_rlp_execute`, `CallerDeposit`, and `validate_tx_relayer_data`. A background Devin session with repository/test access would be needed to confirm via an actual integration test run.
