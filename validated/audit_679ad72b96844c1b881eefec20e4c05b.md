### Title
Attacker can permanently/DoS-block a victim's collateral deposits by filling the victim's `MAX_TOKENS_PER_USER` slots via `DepositToken.deposit(amount, onBehalfOf_)` dust deposits - (File: contracts/Pool.sol)

### Summary
`Pool` enforces a hard per-account cap `MAX_TOKENS_PER_USER = 30` on the combined `depositTokensOfAccount + debtTokensOfAccount` lists. Any deposit token minted to an account whose balance was zero triggers `pool.addToDepositTokensOfAccount(account_)`, which reverts with `UserReachedMaxTokens` once the cap is hit. Because `DepositToken.deposit(uint256,address onBehalfOf_)` lets anyone mint deposit tokens *to an arbitrary beneficiary*, an unprivileged attacker can fill a victim's list with dust deposits of every registered deposit token, after which the victim can never receive a *new* deposit token type — neither via `deposit` nor via `transfer` — since `_mint`/`_transfer` revert inside `addToDepositTokensOfAccount`.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER (30)` [1](#0-0) 
- `addToDepositTokensOfAccount` is invoked by any registered `DepositToken` via `_msgSender()` and is protected by that modifier [2](#0-1) 
- `DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever `balanceBefore == 0 && amount > 0`, and `deposit(amount_, onBehalfOf_)` mints to a caller-chosen beneficiary [3](#0-2) [4](#0-3) 
- The same auto-add happens in `_transfer` for first-time recipients, so even receiving a dust `transfer` fills a slot [5](#0-4) 
- Entries are only removed when the account's balance returns to exactly 0 (`_burn` / sender-side of `_transfer`), and the victim cannot remove entries the attacker forced on them without transferring or withdrawing the tokens, which is gated by `_revertIfLocked` when the account has debt [6](#0-5) 

This is a direct analog of the reported bug class: a fixed-size, attacker-fillable per-account list that reverts legitimate deposits once full, with no exemption for the position owner.

### Impact Explanation
Temporary freezing of funds / deposit liveness failure. Once the 30 slots are filled, all of the victim's deposits into a new collateral type revert (`deposit` → `_mint` → `UserReachedMaxTokens`). If the victim's position approaches liquidation, they cannot add a *new* collateral type to restore health, and — worse — the dust entries may themselves be un-removable when `unlockedBalanceOf(victim)` is reduced by existing debt, so the victim cannot even free the slots without first repaying debt (which may itself require depositing more collateral). A liquidated/under-collateralized user can therefore be permanently prevented from topping up with any collateral they don't already hold. Cost to the attacker is dust amounts across the pool's registered deposit tokens.

### Likelihood Explanation
- Fully unprivileged: `deposit(1 wei-equivalent, victim)` repeated for each registered `DepositToken` requires no role, no governance action, and no cooperation from the victim.
- Works on the deployed configuration: `MAX_TOKENS_PER_USER` is a hard-coded constant (30) and deployed pools list multiple deposit/debt tokens; the number of `depositTokensOfAccount` entries the attacker must create equals `30 - (victim's existing debt + deposit entries)`, and debt-token entries are only attacker-fillable if the victim already borrows, so worst case the attacker needs ≤30 dust deposits.
- No guard stops it: `deposit` has no minimum amount, no beneficiary allowlist, and `addToDepositTokensOfAccount` only checks `_msgSender` is a registered deposit token, which the real `DepositToken` is.
- PoC reproducibility caveat: I could not execute a Hardhat/Foundry fork test within this analysis; the PoC below is a written reproduction trace, and the mechanism (mocked `addToDepositTokensOfAccount` reverting with `UserReachedMaxTokens`) is already exercised by the existing test at `test/Pool.test.ts:1386-1416`.

### Recommendation
Do not auto-register tokens on behalf of third parties, or make the cap self-curable:
- Skip the `addToDepositTokensOfAccount` cap check when the recipient's position already has other deposits, or allow `deposit(..., onBehalfOf_)` only for accounts that opt in.
- Allow an account to always clear a dust slot: add a `renounceDepositToken`/`exitToken` path that transfers out a balance below a dust threshold regardless of `_revertIfLocked` (the locked-balance logic uses USD value, so sub-dust amounts are economically irrelevant to solvency).
- Alternatively, count only tokens above a meaningful balance threshold in `depositOf`/`debtPositionOf` so the list limit cannot be weaponized with dust.

```solidity
// Foundry-style test sketch against a deployed/forked Pool
function test_depositDosViaDustOnBehalfOf() public {
    IPool pool = IPool(POOL_ADDR);
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    // victim legitimately deposits one collateral type and borrows
    // -> victim now has e.g. 1 deposit entry + 1 debt entry

    // attacker fills remaining slots:
    // for each registered deposit token not yet held by victim:
    address[] memory tokens = pool.getDepositTokens();
    for (uint i; i < tokens.length; ++i) {
        IDepositToken dt = IDepositToken(tokens[i]);
        IERC20 underlying = dt.underlying();
        deal(address(underlying), attacker, 1);
        vm.startPrank(attacker);
        underlying.approve(address(dt), 1);
        // mints 1 wei of deposit token to victim -> consumes one slot
        if (dt.balanceOf(victim) == 0 && pool.debtTokensOfAccount.length(victim)
                + pool.depositTokensOfAccount.length(victim) < 30) {
            dt.deposit(1, victim); // onBehalfOf_ = victim
        }
        vm.stopPrank();
    }

    // victim's slots are now 30/30
    // victim tries to deposit a collateral type they don't hold yet:
    IDepositToken newDt = IDepositToken(tokens[lastNewIndex]);
    deal(newDt.underlying(), victim, 100e18);
    vm.startPrank(victim);
    newDt.underlying().approve(address(newDt), 100e18);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newDt.deposit(100e18, victim); // reverts inside _mint -> addToDepositTokensOfAccount
    vm.stopPrank();

    // Same revert hits plain ERC20 transfers of any new deposit token to victim,
    // and liquidation seizes targeting a recipient whose list is full also revert.
}
```
