### Title
Unauthenticated attacker can grief in-flight handshakes by racing a forged stage-2 packet keyed on the plaintext `RemoteIndex` - (File: handshake_manager.go, handshake/machine.go, header/header.go)

### Summary
`HandshakeManager.continueHandshake` dispatches any incoming continuation packet solely by looking up the plaintext `RemoteIndex` header field against `hm.indexes`, then feeds the packet directly into `machine.ProcessPacket` before any cryptographic identity of the sender is established [1](#0-0) . If that call fails with `machine.Failed() == true`, the pending hostinfo is deleted immediately [2](#0-1) . Because `RemoteIndex` is carried unencrypted in the wire header [3](#0-2) , an attacker who observes the initiator's stage-1 packet on the wire can read this index and race a malformed stage-2 packet to the initiator before the legitimate responder's reply arrives.

### Finding Description
The wire header is parsed and dispatched before any authentication takes place: `HandleIncoming` routes purely on `h.MessageCounter`/`h.RemoteIndex` [4](#0-3) . For a continuation message, `queryIndex(h.RemoteIndex)` finds the pending `HandshakeHostInfo` and `continueHandshake` immediately calls `machine.ProcessPacket(nil, packet)` on it [1](#0-0) . The `Machine`'s own contract states: "if `Failed()` is true the Machine is unrecoverable and the caller must abandon it" [5](#0-4) , and `continueHandshake` honors that by calling `hm.DeleteHostInfo(hostinfo)` on a fatal failure [2](#0-1) .

This mirrors the reported bug class exactly: in the smart-contract report, an attacker extracts a public, unauthenticated piece of data (the permit signature) from the victim's pending transaction and races it ahead of the legitimate call, consuming the state (nonce) needed for the victim's transaction to succeed. Here, the attacker extracts a public, unauthenticated piece of data (the 32-bit `RemoteIndex`) from the victim's pending stage-1 packet on the wire and races a forged packet carrying that same index to the initiator before the genuine responder's stage-2 arrives, consuming/destroying the "nonce" (the pending handshake `Machine` state) that the legitimate response depends on.

### Impact Explanation
If the attacker's forged packet is processed first and drives the `Machine` into a fatal-failure state, `DeleteHostInfo` removes the pending hostinfo and its index from `hm.indexes` [6](#0-5) . When the real responder's stage-2 subsequently arrives, `queryIndex` finds nothing and `HandleIncoming` silently drops it as an "orphaned packet" [7](#0-6) . The victim's tunnel establishment fails and must restart from scratch, exactly the griefing/DoS impact described in the original report — no profit for the attacker, but repeated disruption of legitimate connection establishment for the target.

### Likelihood Explanation
Exploitability depends on details this index (`Failed()`/`ProcessPacket` internals) that I could not fully verify before running out of tool iterations — specifically, whether a garbage/malformed payload sent with a correct `RemoteIndex` but no valid Noise handshake state actually causes `noise.HandshakeState.ReadMessage` to reach the failure path versus being rejected as a non-fatal, recoverable error (in which case the Machine is *not* abandoned and this analog would not hold). I was not able to inspect the full body of `ProcessPacket` and `Failed()` in `handshake/machine.go` within the remaining iterations to confirm which noise-level errors set `m.failed = true`.

### Recommendation
Given the unresolved uncertainty above, I cannot confidently assert this exploit path is provably deterministic without deeper review of `handshake/machine.go`'s `ProcessPacket`/`Failed` implementation. Recommend that a follow-up review specifically trace which error paths in `ProcessPacket` set `failed = true`, and if attacker-controlled garbage on a valid `RemoteIndex` can reach one of those paths, treat the finding above as confirmed and consider requiring some minimal packet-integrity check (e.g., ignoring the ability to abandon pending state) before deleting a pending hostinfo in response to a single malformed continuation packet — e.g., only abandon after this is corroborated by additional signals, or defer deletion to allow the legitimate in-flight response to still be evaluated.

1. Initiator sends stage-1 handshake packet (cleartext header includes `RemoteIndex=0`, but the initiator's own `localIndexId` will be embedded as the `RemoteIndex` in the responder's forthcoming stage-2, and is derivable/observable on the wire).

func (hm *HandshakeManager) HandleIncoming(via ViaSender, packet []byte, h *header.H) {
	// Gate on known handshake subtypes. Unknown subtypes (or future ones we
	// don't yet support) are dropped here rather than silently routed through
	// the IX path. Add a case when introducing a new pattern.
	switch h.Subtype {
	case header.HandshakeIXPSK0:
		// supported
	default:
		hm.l.Debug("dropping handshake with unsupported subtype",
			"from", via, "subtype", h.Subtype)
		return
	}

	// First remote allow list check before we know the vpnIp
	if !via.IsRelayed {
		if !hm.lightHouse.GetRemoteAllowList().AllowUnknownVpnAddr(via.UdpAddr.Addr()) {
			hm.l.Debug("lighthouse.remote_allow_list denied incoming handshake", "from", via)
			return
		}
	}

	// First message of a new handshake. The wire format requires RemoteIndex
	// to be zero here (the initiator has no responder index to fill in yet),
	// and generateIndex never allocates 0, so any non-zero RemoteIndex on a
	// stage-1 packet is malformed or someone probing for an index collision.
	// Drop without paying the cost of running noise on a pending Machine.
	if h.MessageCounter == 1 {
		if h.RemoteIndex != 0 {
			hm.l.Debug("dropping stage-1 handshake with non-zero RemoteIndex",
				"from", via, "remoteIndex", h.RemoteIndex)
			return
		}
		hm.beginHandshake(via, packet, h)
		return
	}

	// Continuation message must match a pending handshake by index.
	// Anything else is an orphaned packet (e.g., late retransmit after
	// timeout) and is dropped.
	if hh := hm.queryIndex(h.RemoteIndex); hh != nil {
		hm.continueHandshake(via, hh, packet)
		return
	}

// continueHandshake feeds an incoming packet to an existing pending handshake Machine.
func (hm *HandshakeManager) continueHandshake(via ViaSender, hh *HandshakeHostInfo, packet []byte) {
	f := hm.f

	hh.Lock()
	defer hh.Unlock()

	// Re-verify hh is still tracked. Between queryIndex returning and us taking
	// hh.Lock, handleOutbound may have timed out and deleted it. Once we hold
	// hh.Lock no other deleter can race our index: handleOutbound also takes
	// hh.Lock first, and handleRecvError targets a main-hostmap entry with a
	// different localIndexId.
	hm.RLock()
	cur, ok := hm.indexes[hh.hostinfo.localIndexId]
	hm.RUnlock()
	if !ok || cur != hh {
		return
	}

	hostinfo := hh.hostinfo
	if !via.IsRelayed {
		if !f.lightHouse.GetRemoteAllowList().AllowAll(hostinfo.vpnAddrs, via.UdpAddr.Addr()) {
			f.l.Debug("lighthouse.remote_allow_list denied incoming handshake",
				"vpnAddrs", hostinfo.vpnAddrs, "from", via)
			return
		}
	}

	machine := hh.machine
	if machine == nil {
		f.l.Error("No handshake machine available for continuation",
			"vpnAddrs", hostinfo.vpnAddrs, "from", via)
		hm.DeleteHostInfo(hostinfo)
		return
	}

	response, result, err := machine.ProcessPacket(nil, packet)
	if err != nil {
		// Recoverable errors are routine noise, log at Debug. Fatal errors get a Warn.
		if machine.Failed() {
			f.l.Warn("Failed to process handshake packet, abandoning",
				"vpnAddrs", hostinfo.vpnAddrs, "from", via, "error", err)
			hm.DeleteHostInfo(hostinfo)
		} else {
			f.l.Debug("Failed to process handshake packet",
				"vpnAddrs", hostinfo.vpnAddrs, "from", via, "error", err)
		}
		return
	}

// Encode uses the provided byte array to encode the provided header values into.
// Byte array must be capped higher than HeaderLen or this will panic
func Encode(b []byte, v uint8, t MessageType, st MessageSubType, ri uint32, c uint64) []byte {
	b = b[:Len]
	b[0] = v<<4 | byte(t&0x0f)
	b[1] = byte(st)
	binary.BigEndian.PutUint16(b[2:4], 0)
	binary.BigEndian.PutUint32(b[4:8], ri)
	binary.BigEndian.PutUint64(b[8:16], c)
	return b
}
