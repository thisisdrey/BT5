### Title
Unbounded recursion in `debug/dwarf` type resolution causes stack-overflow panic on crafted DWARF debug info - ([File: src/debug/dwarf/type.go])

### Summary
`Data.Type` / `(*Data).readType` recursively resolves `AttrType` references (e.g. typedef→typedef→pointer→... chains) via the `typeOf` closure without any recursion-depth limit. A crafted binary containing a long, non-cyclic chain of distinct DWARF type-entry offsets forces one recursive Go call per link, exhausting the goroutine stack and panicking the process — the same "attacker-controlled crafted file causes unbounded resolver recursion / stack exhaustion" primitive as CVE-2017-11625's `QPDF::resolveObjectsInStream`.

### Finding Description
Entry point: any caller that parses debug info from an untrusted binary via `debug/elf`/`debug/macho`/`debug/pe` and then calls `(*dwarf.Data).Type(off)` (public API used by tools such as `go tool objdump`, `pprof`, symbolizers, and third-party binary analyzers) reaches `Data.readType` at [1](#0-0) . Inside `readType`, the `typeOf` closure recursively calls `d.readType` for every `AttrType` reference found on an entry: [2](#0-1) .

The `typeCache[off]` map entry is populated with the in-progress type **before** recursing into children, which correctly prevents infinite loops on true cycles (e.g. `typeCache[off] = t` set prior to `typeOf(e)` for `TagArrayType`/`TagStructType`/`TagBaseType`): [3](#0-2) [4](#0-3) [5](#0-4) . However, this only breaks *cycles that revisit the same offset* — it does nothing to bound the recursion **depth** for a long acyclic chain of unique offsets (e.g. N distinct `TagTypedefType` entries each pointing to the next, or nested pointer/array/typedef combinations). Each link consumes one Go stack frame via `readType → typeOf → readType`, with no counter, no explicit depth check, and no `maxNestingDepth`-style guard anywhere in the package (confirmed absent by searching `src/debug/dwarf/*.go` for depth/recursion-limit constants — none exist, unlike `encoding/json`'s `maxNestingDepth` or `go/parser`'s `maxNestLev`).

### Impact Explanation
A maliciously crafted object file (ELF/Mach-O/PE) with DWARF debug sections containing a sufficiently deep chain of type-reference entries can drive `debug/dwarf` into deep, attacker-controlled recursion, exhausting the stack and causing an ungraceful process panic (SIGSEGV-class crash, not a recoverable Go panic, since Go stack overflow is fatal and cannot be caught by `recover`). Any tool that symbolizes or introspects untrusted binaries (crash-report tooling, `pprof`, disassemblers, static-analysis pipelines accepting user-uploaded binaries) is affected — this is a Denial of Service against an unprivileged victim workflow. This would fall under Go's PUBLIC track as a parser panic on crafted, attacker-supplied input consumed by an ordinary victim workflow (not privileged/host access), analogous in class to the QPDF advisory.

### Likelihood Explanation
The victim workflow is any program that calls `debug/dwarf.Data.Reader()`/`Type()` on a binary obtained from an untrusted source (e.g., a service accepting user-submitted binaries for analysis, or `go tool objdump`/`nm` run against downloaded artifacts). The attacker only needs to craft DWARF `.debug_info`/`.debug_abbrev` sections with a long chain of typedef/pointer references pointing to increasing offsets — no special privileges, network position, or code execution capability required, matching the CVSS AV:L/PR:N/UI:R profile of the original CVE (user opens/loads a malicious file).

### Recommendation
Add an explicit recursion-depth counter (thread through `readType`/`typeOf`, similar to `go/parser`'s `incNestLev`/`decNestLev` or `encoding/json`'s `maxNestingDepth`) and return a `DecodeError` once a reasonable maximum type-chain depth is exceeded, independent of the existing `typeCache` cycle-breaking mechanism.

	// chain this long is verbose; the essential point is that each
	// TagTypedefType entry's AttrType attribute (formRef4) points to the
	// offset of the next typedef entry, forming an acyclic chain with no
	// repeated offsets (so typeCache does not short-circuit it).
	//
	// data, abbrev := buildTypedefChain(chainLen)
	// d, err := dwarf.New(nil, nil, nil, data, nil, nil, nil, nil)
	// ... set d's abbrev table to abbrev ...
	//
	// The expected (currently failing) assertion is that Type() returns an
	// error instead of crashing the process with a fatal stack overflow:
	//
	// _, err = d.Type(0)
	// if err == nil {
	//     t.Fatalf("expected depth-limit error, got nil")
	// }

	_ = bytes.Buffer{}
	_ = binary.LittleEndian
	t.Skip("illustrative PoC: readType/typeOf has no depth limit; " +
		"a sufficiently long acyclic typedef/pointer chain in crafted DWARF " +

The root-cause code path (`readType`/`typeOf` recursion with no depth guard) is verified directly in `src/debug/dwarf/type.go`, and the absence of any depth-limiting constant was confirmed by search across `src/debug/dwarf/*.go`.
