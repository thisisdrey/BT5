### Title
ExchangeInjectActuator lacks slippage/min-output protection for the computed counter-token amount - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeInjectActuator` (add-liquidity to a Bancor-style `Exchange` pool) computes the amount of the "other" pool token that must be deducted from the injector's balance purely from the current on-chain pool ratio at execution time, with no user-supplied maximum/expected bound. This mirrors the reported ArrakisV2 `mint`/`burn` issue: liquidity-provisioning operations that lack slippage controls can be sandwiched.

### Finding Description
`ExchangeTransactionActuator` (the swap path) explicitly protects the caller via the `expected` field on `ExchangeTransactionContract`, validated in `doValidate()`: [2](#0-1) 

In contrast, `ExchangeInjectContract` has only `owner_address`, `exchange_id`, `token_id`, `quant` — no equivalent bound: [3](#0-2) 

In `ExchangeInjectActuator.doValidate()`, `anotherTokenQuant` is derived solely from the pool balances read at validation time and the ratio arithmetic, with no comparison against any caller-supplied ceiling: [4](#0-3) 

`execute()` recomputes the same ratio-based `anotherTokenQuant` and unconditionally debits it from the injector's account: [5](#0-4) 

Because any account can freely submit `ExchangeTransactionContract` swaps against the same `Exchange` pool immediately before the victim's `ExchangeInjectContract` is packed into the same block (front-running via fee/ordering, since TRON has no private mempool guarantee and transactions are ordered by the block producer / broadcast order), an attacker can shift `firstTokenBalance`/`secondTokenBalance` right before the inject executes, then swap back afterward. The victim's `quant` of `token_id` is fixed, but the ratio-derived `anotherTokenQuant` they must pay balloons or shrinks depending on the manipulated ratio, and there is no on-chain mechanism for the victim to cap how much of the counter-token they're willing to contribute.

### Impact Explanation
An attacker can extract value from any account issuing `ExchangeInjectContract` by manipulating the pool ratio immediately before the victim's transaction executes, forcing the victim to overpay the counter-token relative to fair market ratio, and then reversing the swap to capture the difference. This is a direct value-extraction / unauthorized-value-transfer vector against liquidity providers using TRON's built-in Bancor-style exchange, consistent with a Medium-severity fund-loss issue as in the original report (the same 0.01% "not precise enough" tolerance exists for `ExchangeWithdrawActuator` but that only bounds rounding, not adversarial ratio manipulation, and does not exist at all for inject).

### Likelihood Explanation
Any account can submit `ExchangeTransactionContract` and `ExchangeInjectContract` transactions; no special privilege is required. Exchanges with active trading pairs (a normal, expected on-chain state) are inherently exposed each time a user injects liquidity, and the attack requires only capital and correctly-ordered transactions within the same or adjacent blocks — a standard sandwich pattern.

### Recommendation
Add a caller-supplied bound (e.g., `max_another_token_quant` or `min_another_token_quant` per direction) to `ExchangeInjectContract` (and similarly consider stricter bounds for `ExchangeWithdrawContract`), and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` analogous to the `expected` check already used in `ExchangeTransactionActuator`.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` from victim V for exchange `E` with `token_id = A`, `quant = Q`.
2. Attacker submits an `ExchangeTransactionContract` swap against `E` that shifts `firstTokenBalance`/`secondTokenBalance` unfavorably for V (e.g., sells a large amount of the counter-token B into the pool, inflating the ratio B/A).
3. V's inject executes: `ExchangeInjectActuator.execute()` computes `anotherTokenQuant` from the now-skewed ratio using the formula at [6](#0-5)  and debits that (now much larger) amount of B from V, with no slippage check to reject it.
4. Attacker submits a second `ExchangeTransactionContract` reversing the initial swap, restoring the ratio and realizing a profit funded by V's overpayment.
