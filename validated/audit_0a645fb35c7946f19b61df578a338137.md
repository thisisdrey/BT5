### Title
Attacker can DoS liquidations and deposits by filling the fee collector's per-account token list to `MAX_TOKENS_PER_USER` — (File: contracts/DepositToken.sol)

### Summary
The reference report describes a DoS where a transfer into an attacker-influenced recipient account reverts inside a permissionless instruction (Solana `lzReceive`), blocking the whole flow. The Metronome analog: every `DepositToken` transfer or fee mint to a first-time holder calls `Pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` once the recipient holds 30 deposit+debt token entries. An unprivileged attacker can dust-transfer deposit tokens to the protocol `feeCollector` until its list is full, after which `Pool.liquidate` (which `seize`s the fee share to `feeCollector`) and `DepositToken.deposit` (which mints the deposit fee to `feeCollector`) revert for any collateral the fee collector does not already hold — griefing all fee-bearing liquidations and deposits.

### Finding Description
- `DepositToken._transfer` adds the recipient to the pool's per-account list on first receipt:
  `if (_recipientBalanceBefore == 0 && amount_ > 0) { pool.addToDepositTokensOfAccount(recipient_); }` (`contracts/DepositToken.sol:518-520`). The same hook runs in `_mint` (`contracts/DepositToken.sol:486-488`).
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts `UserReachedMaxTokens` when `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` (30) (`contracts/Pool.sol:143-148`, `contracts/Pool.sol:216-220`, `contracts/Pool.sol:79`).
- `Pool.liquidate` seizes the liquidation fee to `poolRegistry.feeCollector()`: `depositToken_.seize(account_, _poolRegistry.feeCollector(), _fee)` (`contracts/Pool.sol:591-593`). `seize` is a plain `_transfer` (`contracts/DepositToken.sol:343-345`), so it hits the same hook and reverts the entire liquidation if `feeCollector` is at the cap and does not already hold that deposit token.
- `DepositToken.deposit` mints `_fee` to `_pool.feeCollector()` (`contracts/DepositToken.sol:229-232`), which also reverts under the same condition, blocking deposits for any collateral token not already in the fee collector's list.
- Attack path: the attacker deposits 1 wei of each listed deposit token and calls `depositToken.transfer(feeCollector, 1)` (or `deposit(1, feeCollector)`), filling `depositTokensOfAccount[feeCollector]` to 30. No privilege is needed; `transfer` is public and only requires `unlockedBalanceOf(msg.sender) >= 1`.

### Impact Explanation
Once `feeCollector` is at the cap:
- Every `liquidate` call with `_fee > 0` (i.e., whenever `protocolLiquidationFee > 0` in `FeeProvider`) reverts for deposit tokens the fee collector does not yet hold. Liquidators cannot repay those positions, so underwater accounts cannot be liquidated — a liveness break of the liquidation mechanism that leads to bad debt / protocol insolvency as prices move. This is the same invariant break as the reference: a protocol-level message/instruction that must not fail can be made to fail by attacker-controlled state of the recipient account.
- Deposits for those tokens revert with `UserReachedMaxTokens` whenever `depositFee > 0`, freezing the deposit path (temporary freezing of funds for users / protocol availability).

Mitigation exists only via privileged action (governor sweeping or transferring tokens out of `feeCollector` to free list slots), so the DoS persists until manual intervention — analogous to the remediation in the reference (admin withdrawal/token tracking).

### Likelihood Explanation
Preconditions:
- The pool must list enough distinct `DepositToken`s so the attacker can fill 30 combined slots (debt tokens are not freely transferable, so the attacker mainly fills via deposit tokens; entries the fee collector already holds from normal fees count toward the cap, lowering the attacker's cost). On pools with few collaterals this may not be reachable today, but the cap is shared across all pools' tokens per account, and fee accumulation naturally pushes `feeCollector` toward 30 over time — meaning the DoS can also arise organically.
- `protocolLiquidationFee`/`depositFee` must be non-zero for the revert to trigger on fee collection; with zero fees the seize/mint to `feeCollector` is skipped.

No existing guard prevents it: `seize`'s `onlyIfCanSeize` only checks the pool as caller, `transfer` only checks the sender's unlocked balance, and `nonReentrant`/`whenNotPaused`/`whenNotShutdown` do not apply to this condition.

### Recommendation
Mirror the reference remediation: do not let the recipient-account bookkeeping DoS value-moving paths.
- Wrap the `addToDepositTokensOfAccount`/`removeFromDepositTokensOfAccount` callbacks in `_transfer`/`_mint`/`_burn` in a `try/catch`, or make the per-account list bounded only for user-facing actions (deposit/mint/issue), not for `seize`/fee mints.
- Alternatively, exempt the protocol `feeCollector` from `MAX_TOKENS_PER_USER` accounting, or route liquidation/deposit fees to a list-exempt accumulator (e.g., Treasury) with a separate admin sweep, matching the "token tracking + admin withdrawal" fix pattern.

### Proof of Concept
Hardhat-style reproduction sketch against `test/Pool.test.ts` fixtures:

```ts
// setup: pool with N deposit tokens, protocolLiquidationFee > 0, feeCollector = poolRegistry.feeCollector()
const feeCollector = await poolRegistryMock.feeCollector();

// 1) Attacker fills the fee collector's token list to MAX_TOKENS_PER_USER.
//    For each listed DepositToken dt_i: deposit 1 wei worth on behalf of attacker,
//    then `dt_i.transfer(feeCollector, 1)` (balance is unlocked when attacker has no debt).
const max = await pool.MAX_TOKENS_PER_USER(); // 30
for (const dt of listedDepositTokens) {
  await dt.connect(attacker).transfer(feeCollector, 1);
}
// (also fill remaining slots via deposit(1, feeCollector) / dust of any deposit token)
expect((await pool.getDepositTokensOfAccount(feeCollector)).length
  + (await pool.getDebtTokensOfAccount(feeCollector)).length).to.eq(max);

// 2) Victim's position becomes unhealthy (oracle price drop).
await masterOracle.updatePrice(met.address, unhealthyPrice);

// 3) Any liquidation of a deposit token the feeCollector doesn't already hold reverts.
const amountToRepay = await pool.quoteLiquidateMax(msEth.address, victim.address, msdNewCollateral.address);
await expect(
  pool.connect(liquidator).liquidate(msEth.address, victim.address, amountToRepay, msdNewCollateral.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
// Position stays underwater -> liquidation DoS -> bad debt accrues.

// 4) Deposits with fee > 0 for that collateral also revert at _mint(feeCollector, fee).
await expect(
  msdNewCollateral.connect(user).deposit(amount, user.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Uncertainty noted: I could not verify within the indexed context whether `DebtToken` exposes a transfer path that would let the attacker also fill `debtTokensOfAccount[feeCollector]` (grep confirmed `feeCollector`/`_mint` references in `contracts/DebtToken.sol` but not the transfer surface). If fee-bearing mints to the fee collector are additionally reachable, the attack is cheaper; the core mechanism (revert inside `addToDepositTokensOfAccount` during `seize`) is confirmed by `contracts/DepositToken.sol:518-520` and `contracts/Pool.sol:591-593`.
