### Title
Uncontrolled array allocation from attacker-controlled ABI length field in `BatchValidateSign` precompile before the `allowTvmSelfdestructRestriction` hard fork - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `batchValidateSign` TVM precompiled contract (address `0x...09`) decodes an `address[]` ABI parameter via `extractBytes32Array`, which allocates a Java array sized directly from an attacker-supplied 32-byte word taken from contract call data, with no upper bound check unless the `allowTvmSelfdestructRestriction` feature is active. This mirrors the CVE-2019-3564 pattern: a length/count field taken from an untrusted container is used to drive allocation/iteration without validation, enabling a cheap, short payload to trigger excessive resource consumption.

### Finding Description
`extractBytes32Array` reads a length word and immediately allocates an array of that size: [1](#0-0) 

It is invoked unconditionally inside `BatchValidateSign.doExecute`: [2](#0-1) 

The size-bound guard (`addrArraySize > MAX_SIZE`) that would normally prevent an oversized allocation is only executed `if (VMConfig.allowTvmSelfdestructRestriction())`. When that hard-fork flag is not yet active on a given chain/network, `extractBytes32Array(words, offset)` runs with no bound at all: `len = words[offset].intValueSafe()` can be an attacker-chosen large positive value (via `DataWord.intValueSafe()` clamping), and `new byte[len][]` is executed directly on that value before any other validation (such as `signatures.length != addresses.length`) can reject the call. This is functionally the same root cause as the reported advisory: a length/count field from an untrusted, short message is trusted to drive allocation/iteration without a bound check, independent of the message's actual size.

By contrast, the sibling precompile `ValidateMultiSign` and the "restricted" branch of `BatchValidateSign` do enforce `MAX_SIZE` before extraction — showing the fix pattern exists in the codebase but is not applied unconditionally to `extractBytes32Array`.

### Impact Explanation
Any account (no special privileges required) can deploy or call a contract that invokes the `batchValidateSign` precompile with crafted call data containing a huge value in the address-array length slot. This triggers an attempted allocation on the order of the JVM's array-size limit, which throws `OutOfMemoryError`/`NegativeArraySizeException`. While the outer `execute()` wrapper catches `Throwable` and returns a benign result, the attempted large allocation still stresses the JVM heap/GC subsystem for every call. Because this runs inside transaction execution on every full node, this can be used to degrade node performance or trigger GC pauses network-wide, and — depending on JVM/heap configuration — an actual `OutOfMemoryError` thrown during allocation is not always safely recoverable by a `catch(Throwable)` (the JVM can be left in a degraded state, other threads can fail allocations concurrently). This fits CWE-770 (uncontrolled resource allocation) / CWE-834 (excessive iteration), analogous to the reported CVE-2019-3564 class of bug, and is reachable purely through a signed transaction/contract call — no special SR/witness/peer position needed.

### Likelihood Explanation
Likelihood depends entirely on whether `allowTvmSelfdestructRestriction` is active on the target network. It is a feature-gated hard-fork flag (`VMConfig.allowTvmSelfdestructRestriction()`, backed by `DynamicPropertiesStore`), meaning any network that has not yet activated this specific proposal remains exposed. Given java-tron's typical hard-fork rollout model (flags default off until a committee proposal activates them chain-wide), this is plausible on non-mainnet networks or during the window before the proposal is enabled, and is trivially triggerable by any TRC address once reachable.

### Recommendation
Apply the same `MAX_SIZE` bound check unconditionally before calling `extractBytes32Array` (and equivalently for `extractBytesArray`/`extractSigArray`), independent of `VMConfig.allowTvmSelfdestructRestriction()`. Alternatively, add an internal bound check inside `extractBytes32Array` itself (e.g., reject `len < 0 || len > MAX_SIZE` before allocating), so the precompile is safe regardless of feature-flag state.

### Proof of Concept
1. Craft ABI-encoded call data for `batchValidatesign(bytes32,bytes[],address[])` where the `address[]` parameter's length word (the word at the offset pointed to by the third head word) is set to a very large value (e.g., `0x7FFFFFFF`), while keeping the rest of the payload minimal/short.
2. On a network where `allowTvmSelfdestructRestriction` is not yet active, call the precompile at address `0x...09` with this data from any account (via `CALL`/`STATICCALL` from a simple contract, reachable by any unprivileged sender).
3. Observe `extractBytes32Array` attempting `new byte[0x7FFFFFFF][]`, causing `OutOfMemoryError` deep inside transaction execution on every node processing the transaction — reproducible with a short, cheap transaction payload, matching the "short messages that take a long time / large resource use to parse" pattern from the referenced advisory.   private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];

      bytes32Array[i] = words[offset + i + 1].getData();
