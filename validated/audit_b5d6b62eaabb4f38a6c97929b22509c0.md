### Title
Missing slippage protection in ExchangeInject/ExchangeWithdraw lets a sandwich attack force a liquidity provider to under/over-deposit against a manipulated pool ratio - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeTransactionContract` (the AMM-style buy/sell path) already implements the exact mitigation the external report recommends: a caller-supplied `expected` amount that the actuator enforces before the trade is committed [1](#0-0) . However, the two sibling actuators that operate on the same bonding-curve/constant-product-style `ExchangeCapsule` pool — `ExchangeInjectActuator` (add liquidity) and `ExchangeWithdrawActuator` (remove liquidity) — compute the counter-token amount purely from the pool's *current* on-chain ratio at execution time, with no analogous `expected`/`minReceived`/`maxSpend` parameter to bound how much the ratio may have moved since the transaction was signed.

### Finding Description
For `ExchangeInjectActuator`, the amount of the "other" token that will be pulled from the owner's account is derived solely from the exchange's live balances: [2](#0-1) 

This value is computed again in `doValidate()` [3](#0-2)  and then deducted from the owner's balance in `execute()` [4](#0-3) , with no field in the contract to cap the deduction. `ExchangeWithdrawActuator` has the analogous issue: `anotherTokenQuant` (the amount the withdrawer receives) is computed from the live ratio with only a "precision" sanity check, not a slippage bound [5](#0-4) .

Because any account can move the pool ratio first by calling `ExchangeTransactionContract` (a permissionless buy/sell against the pool, computed via `ExchangeCapsule.transaction()` → `ExchangeProcessor`/`SafeExchangeProcessor` [6](#0-5) ), an attacker who sees a pending `ExchangeInjectContract` or `ExchangeWithdrawContract` in the mempool can sandwich it: skew the ratio before the victim's transaction executes, let the victim's inject/withdraw settle at the skewed ratio (locking in an unfavorable exchange of the two assets), then reverse the skew afterward, extracting value from the victim. This is the same root cause the external report describes for `buy()` — a price-dependent operation with no caller-enforced bound is executed against a pool whose price can be moved atomically around it.

Note: both `ExchangeInjectActuator` and `ExchangeWithdrawActuator` restrict the caller to the exchange's `creatorAddress` [7](#0-6) [8](#0-7) , but that "creator" role is obtained permissionlessly by anyone who submits an `ExchangeCreateContract`, so it is still an ordinary unprivileged transaction broadcaster.

### Impact Explanation
A sandwiched inject/withdraw causes the creator to deposit more of one asset than the pool ratio implies is fair, or to receive less than the fair proportional share on withdrawal — an unbacked-value transfer from the victim to the attacker mediated entirely through on-chain pool state, with no way for the victim to bound their loss. This matches the theft-of-funds impact class.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires an attacker to observe a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` and race two of their own `ExchangeTransactionContract` calls around it within the same or adjacent blocks, and it only affects exchanges with meaningful trading activity/liquidity depth to make the ratio move matter. The same constraint (front-run visibility, atomic bracketing) applies as in the original ETH `buy()` report; here it's structurally easier for an attacker since the exchange's price-moving primitive (`ExchangeTransactionContract`) is a plain, permissionless transaction type available to any account.

### Recommendation
Add an `expected`-style bound to `ExchangeInjectContract` and `ExchangeWithdrawContract`, mirroring the pattern already used in `ExchangeTransactionContract` (`getExpected()` / the `token required must greater than expected` check [1](#0-0) ):
- For `ExchangeInjectContract`: add a max acceptable `anotherTokenQuant` (or min acceptable ratio); reject execution in `doValidate()` if the computed value exceeds it.
- For `ExchangeWithdrawContract`: add a min acceptable `anotherTokenQuant` to receive; reject if the computed value is below it.

### Proof of Concept
1. Alice, the creator of Exchange `E` (first token A, second token TRX), submits `ExchangeInjectContract` intending to inject `tokenQuant` of A, expecting to also deposit `anotherTokenQuant` of TRX computed from the current ratio in `ExchangeCapsule.transaction`-adjacent proportional math [9](#0-8) .
2. Bob observes Alice's pending transaction and front-runs it with a large `ExchangeTransactionContract` buy of A with TRX, shifting `firstTokenBalance`/`secondTokenBalance` sharply.
3. Alice's `ExchangeInjectContract` then executes against the skewed ratio, causing significantly more TRX (or A) to be deducted from her account than she intended, with no `expected`/max-bound field to revert the transaction.
4. Bob back-runs with an opposite `ExchangeTransactionContract` to restore the ratio and realize a profit extracted from Alice's forced unfavorable deposit — analogous to the Alice/Bob scenario in the external `buy()` report, but reachable purely through existing java-tron actuators.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
