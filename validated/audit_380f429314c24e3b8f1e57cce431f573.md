Audit Report

## Title
Silent transfer-failure swallowing via `debug_assert!` in `claim_child_bounty` permanently locks child-bounty funds - (File: `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`Pallet::claim_child_bounty` computes `curator_fee` and `payout` from the child-bounty sub-account's balance and transfers them via `T::Currency::transfer(..., AllowDeath)`, checking the result only with `debug_assert!`, which is a no-op in release builds. If either transfer fails (e.g., destination account doesn't exist and amount is below `ExistentialDeposit`), the failure is silently discarded while the extrinsic still emits `Event::Claimed`, decrements `ParentChildBounties`, and deletes the child-bounty storage entry, permanently stranding funds with no recovery path.

## Finding Description
In `claim_child_bounty`, the curator fee and beneficiary payout transfers are guarded only by `debug_assert!`: [1](#0-0) 

`curator_fee` and `payout` are derived from `child_bounty.fee` (set at curator proposal time, arbitrary) and `balance.saturating_sub(curator_fee)` respectively: [2](#0-1) 

Since `debug_assertions` are disabled in production runtime builds, any `TokenError::BelowMinimum` returned by `Currency::transfer` when paying a non-existent destination below `ExistentialDeposit` is dropped without aborting the call. The subsequent event emission, `ParentChildBounties` decrement, and description/storage removal proceed unconditionally regardless of transfer outcome: [3](#0-2) 

This exact failure mode (`TokenError::BelowMinimum` on transfer to a new account below ED) is confirmed by pallet-balances' own tests: [4](#0-3) 

The call is reachable by any `ensure_signed` origin once the child-bounty reaches `PendingPayout`, with no permission check beyond the unlock delay.

## Impact Explanation
Once `ChildBounties::try_mutate_exists` completes, the entry is deleted (`*maybe_child_bounty = None`) and `ChildBountyDescriptionsV1` removed, with no code path referencing the orphaned `child_bounty_account_id` again. Unlike `pallet-bounties`, which now provides a `reclaim_bounty_funds` recovery extrinsic (confirmed present in this repo's `substrate/frame/bounties/src/lib.rs`, `benchmarking.rs`, `weights.rs`, and `tests.rs`), `pallet-child-bounties` has no analogous recovery mechanism. This causes a permanent user-fund lock combined with a false on-chain settlement record (event emitted, storage cleared) despite the actual currency transfer failing — matching the permanent fund-lock / false-state-acceptance impact class.

## Likelihood Explanation
No privileged role is needed; any signed account may call `claim_child_bounty`. The trigger condition — a `curator_fee` or `payout` below `ExistentialDeposit` paid to a not-yet-existing account — is easily reachable via normal `propose_curator` flow with a small fee or by awarding to a fresh account. Production Substrate/Polkadot-SDK builds compile without `debug_assertions`, so the guard offers no runtime protection, making this fully and repeatably exploitable by an ordinary user.

## Recommendation
Replace both `debug_assert!(fee_transfer_result.is_ok())` and `debug_assert!(payout_transfer_result.is_ok())` with proper error propagation (e.g., `fee_transfer_result?`) so the enclosing `try_mutate_exists` returns `Err` and reverts all state changes if either transfer fails. Alternatively, adopt the same recovery pattern `pallet-bounties` added (`reclaim_bounty_funds`) to allow governance-driven recovery of stranded child-bounty funds when transfers to a claimant fail.

## Proof of Concept
1. Configure a runtime with `ExistentialDeposit = E > 0`, built without `debug_assertions` (standard release build).
2. Create a parent bounty, add a child bounty, and propose/accept a curator with `fee < E`.
3. Award the child bounty to a beneficiary account that has never held a balance so it does not exist in `System`, ensuring `payout = balance - fee` also results in an amount `< E` for a fresh curator/beneficiary account.
4. After `unlock_at`, call `claim_child_bounty`. `T::Currency::transfer(&child_bounty_account, curator_or_beneficiary, amount, AllowDeath)` returns `Err(TokenError::BelowMinimum)` per the balances pallet behavior at `substrate/frame/balances/src/tests/dispatchable_tests.rs:31-45`, which is discarded by the compiled-out `debug_assert!`.
5. Observe `Event::Claimed` fires with the full `payout`, `ParentChildBounties` is decremented, and the `ChildBounties`/`ChildBountyDescriptionsV1` entries are removed — while the curator/beneficiary balance was never credited and funds remain stranded in the now-unreferenced `child_bounty_account_id`.
