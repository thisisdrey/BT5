## Title
`initialize()` in vault contracts lacks access control and can be front-run to permanently block the DAO's vault-initialization proposal - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar`, and equivalents `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`)

### Summary
Each vault contract's `initialize` function only checks `(not (var-get initialized))` — it has no `check-dao-auth` or `check-impl-auth` gate, unlike almost every other state-mutating function in the same contracts. Any unprivileged account can call `initialize` directly before the DAO's initialization proposal runs, exactly analogous to the SEDA vesting bug where a griefer front-runs a "create only if not-yet-existing" guard to permanently deny the intended creator.

### Finding Description
`initialize` sets `initialized` to `true` and performs the seed deposit unconditionally, with no caller restriction: [1](#0-0) 

Every other privileged setter in the same contract (`set-authorized-contract`, `set-cap-debt`, `set-cap-supply`, `set-fee-flash`, etc.) explicitly calls `(try! (check-dao-auth))`: [2](#0-1) 

`initialize` is missing this guard, so any ordinary principal can call it directly, as long as they hold `MINIMUM-LIQUIDITY` (u1000, a small amount in the underlying token's smallest unit) of the underlying asset to satisfy the internal `deposit` call.

The DAO's own initialization flow calls the same `initialize` function inside an atomic `try!` chain used to also set caps and authorize the `market` contract: [3](#0-2) 

Because Clarity's `try!` aborts the entire enclosing transaction on any error, if a griefer calls `initialize()` on `vault-sbtc` (or any of the six vaults) before the DAO proposal executes, the vault's `initialized` flag flips to `true`. When the DAO proposal subsequently calls `(try! (contract-call? .vault-sbtc initialize))`, it hits `ERR-ALREADY-INITIALIZED` and the assertion fails, causing the whole atomic proposal transaction (cap-setting, `initialize` calls for all vaults, and `set-authorized-contract` for `market`) to revert. This is structurally identical to the SEDA report: a state-creation function guarded only by an "already exists"/"already initialized" check, callable by anyone, allows a griefer to pre-empt the legitimate privileged actor and permanently block that specific creation attempt.

### Impact Explanation
The griefer permanently prevents that specific DAO proposal from ever succeeding (the `initialized` flag can never be reset), forcing the DAO to redeploy and re-vote on a corrected proposal that skips already-initialized vaults before it can authorize the `market` contract and configure caps. Until that is done, the vault cannot be used by the `market` contract (not authorized), so genuine user deposits/borrows through the market are frozen for that market — a temporary freezing of protocol functionality caused entirely by an unprivileged principal's transaction, with no DAO compromise required.

### Likelihood Explanation
Likelihood is high: the attack requires only a small amount of the underlying token (`MINIMUM-LIQUIDITY = u1000` base units) and a single transaction, timed to land before the DAO's `proposal-init-vaults` executes (observable on-chain before execution, e.g. mempool/vote period). No special privileges, oracle manipulation, or DAO compromise are needed.

### Recommendation
Add `(try! (check-dao-auth))` (or an authorized-contract check restricting the caller to the DAO executor) at the top of `initialize` in every vault contract, mirroring the guard already used on `set-authorized-contract`, `set-cap-debt`, etc.

### Proof of Concept
1. Vault contracts (`v0-vault-sbtc.clar`, etc.) are deployed but not yet initialized by the DAO.
2. Attacker Alice acquires `u1000` (MINIMUM-LIQUIDITY) of the vault's underlying token and calls `vault-sbtc.initialize()` directly — succeeds because there is no auth check, only the `initialized` boolean check.
3. `initialized` is now `true`; Alice's deposit becomes the permanent seed liquidity (minted to `NULL-ADDRESS`).
4. The DAO later executes `proposal-init-vaults.execute()`, which internally calls `(try! (contract-call? .vault-sbtc initialize))`.
5. This call now returns `ERR-ALREADY-INITIALIZED`, the `try!` fails, and the entire proposal transaction reverts — none of the cap-setting or `market` authorization calls take effect.
6. The DAO must create and pass a brand-new proposal that omits the already-initialized vault before `market` can be authorized to use it, delaying protocol launch/functionality for that vault. [1](#0-0) [4](#0-3) [5](#0-4)
