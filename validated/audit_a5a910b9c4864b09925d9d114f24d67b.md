### Title
Unchecked integer overflow in vote-reward accrual corrupts account `allowance` - ([File: actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java])

### Summary
`VoteRewardUtil.computeReward()` and `VoteRewardUtil.adjustAllowance()` accumulate TRX voting rewards into an account's `allowance` field using raw, unchecked `long` arithmetic and a truncating `BigInteger.longValue()` conversion, unlike every sibling reward/balance-mutation path in the codebase which uses `LongMath.checkedAdd`/`checkedMultiply` or `Maths.addExact`. This mirrors the CVE-2023-23559 bug class: an addition performed without an overflow guard on attacker-influenced accumulators.

### Finding Description
`computeReward()` sums per-witness rewards derived from a `BigInteger` product and converts with `.longValue()` (silent 2's-complement truncation) rather than `.longValueExact()`: [1](#0-0) 

The result is then folded into the account's persistent `allowance` field with a bare `+` and no overflow check: [2](#0-1) 

This is directly reachable from unprivileged, signed transactions: `VoteWitnessProcessor.execute()` calls `VoteRewardUtil.withdrawReward()` on every vote-witness TVM native contract invocation before doing anything else, with no `LongMath` guard around it: [3](#0-2) 

The same unguarded call chain is exercised by `UnfreezeBalanceProcessor`, `UnfreezeBalanceV2Processor`, `WithdrawRewardProcessor.execute()` (where the *subsequent* balance addition is checked, but the *upstream* allowance mutation inside `VoteRewardUtil.adjustAllowance` is not), and the SUICIDE opcode path in `Program.java`: [4](#0-3) [5](#0-4) 

By contrast, the rest of the codebase deliberately hardens exactly this class of arithmetic: `WithdrawBalanceActuator` and `WithdrawRewardProcessor` explicitly use `LongMath.checkedAdd` for the balance+allowance sum, `VoteWitnessProcessor` uses `LongMath.checkedAdd/checkedMultiply` for vote sums, and `Commons.adjustBalance`/`AbstractActuator.adjustBalance` route through `Maths.addExact`: [6](#0-5) [7](#0-6) 

`MortgageService.adjustAllowance()` (the block/tx-fee reward path) has the identical unguarded pattern, though it is driven by consensus/witness reward distribution rather than a direct unprivileged transaction: [8](#0-7) 

### Impact Explanation
If `allowance + amount` (or the `BigInteger` reward product) overflows/truncates, `AccountCapsule.allowance` silently wraps to an arbitrary (potentially negative or unexpectedly large) value that is persisted via `repo.updateAccount()`. Because downstream consumers (`WithdrawRewardProcessor`, `WithdrawBalanceActuator`) only checked-add the *already-corrupted* `allowance` into `balance`, the overflow can manifest as an unbacked/incorrect balance credited to an account, or as a corrupted allowance that permanently locks legitimate reward from ever being withdrawn (funds freezing). This satisfies the "unbacked balance / permanent freezing of funds" acceptance bar.

### Likelihood Explanation
Reaching the vulnerable addition only requires a normal signed `TriggerSmartContract` invoking the TVM `vote`, `unfreezeBalance(V2)`, `withdrawReward` native contracts, or a contract `SUICIDE`, all of which are available to any unprivileged account. Actually driving `deltaVi * userVote` (accumulated Vi reward-per-share times vote weight) past `Long.MAX_VALUE` requires an account to accrue an extremely large reward-per-vote ratio (e.g., a witness with very low total vote weight relative to accrued rewards, over many un-withdrawn cycles), which is economically constrained by TRX's bounded total supply and witness reward pool. This makes the overflow difficult to trigger under normal network economics, so likelihood is low-to-moderate rather than trivially exploitable, but the code path itself has zero defense-in-depth compared to every analogous arithmetic site in the same file/module.

### Recommendation
Replace the raw `+` in `VoteRewardUtil.adjustAllowance()` with `LongMath.checkedAdd`/`Maths.addExact` and replace `.longValue()` with `.longValueExact()` in `computeReward()`, mirroring the guards already used in `WithdrawRewardProcessor`, `WithdrawBalanceActuator`, and `VoteWitnessProcessor`. Apply the same fix to `MortgageService.adjustAllowance()`.

### Proof of Concept
1. Attacker account votes for a witness that they also effectively control such that the witness's total vote weight stays disproportionately small relative to accrued block/tx-fee reward over an extended number of maintenance cycles (increasing `Vi` in `DelegationStore` without a corresponding proportional increase in `totalVote`).
2. Attacker never withdraws, letting `deltaVi` accumulate across cycles until `deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD)` exceeds `Long.MAX_VALUE`.
3. Attacker calls `vote()`/`unfreezeBalance()`/`withdrawReward()` via a `TriggerSmartContract`, invoking `VoteRewardUtil.withdrawReward()` → `computeReward()` (silent `longValue()` truncation) → `adjustAllowance()` (silent `long` wraparound), corrupting `AccountCapsule.allowance` without any exception being thrown.
4. A subsequent `withdrawReward` call moves the corrupted `allowance` into `balance` via `WithdrawRewardProcessor.execute()`'s `LongMath.checkedAdd(oldBalance, allowance)`, which will not detect the earlier corruption because it validates only the final addition, not the value's provenance.

  public static void adjustBalance(AccountStore accountStore, AccountCapsule account, long amount,
                                   boolean useStrict)
      throws BalanceInsufficientException {

    long balance = account.getBalance();
    if (amount == 0) {
      return;
    }

    if (amount < 0 && balance < -amount) {
      throw new BalanceInsufficientException(
          String.format("%s insufficient balance, balance: %d, amount: %d",
              StringUtil.createReadableString(account.createDbKey()), balance, -amount));
    }
    account.setBalance(addExact(balance, amount, useStrict));
    accountStore.put(account.getAddress().toByteArray(), account);
  }

  public void adjustAllowance(AccountStore accountStore, byte[] accountAddress, long amount)
      throws BalanceInsufficientException {
    AccountCapsule account = accountStore.getUnchecked(accountAddress);
    long allowance = account.getAllowance();
    if (amount == 0) {
      return;
    }

    if (amount < 0 && allowance < -amount) {

          String.format("%s insufficient balance, amount: %d, allowance: %d",
              StringUtil.createReadableString(accountAddress), amount, allowance));
    }
    account.setAllowance(allowance + amount);
    accountStore.put(account.createDbKey(), account);
  }
