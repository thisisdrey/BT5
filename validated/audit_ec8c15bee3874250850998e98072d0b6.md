### Title
Any account can cheaply spam a popular smart contract to force *all other callers* of that contract into inflated "dynamic energy" fees for an entire maintenance cycle - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
java-tron's "dynamic energy" mechanism raises the effective energy cost of every opcode executed inside a smart contract once that contract's *aggregate* energy usage in the current cycle exceeds a threshold. Because the usage counter and resulting penalty factor are tracked **per contract address, shared across every caller**, and not per-caller, any unprivileged account can deliberately spam calls into a popular contract to push its usage above `DYNAMIC_ENERGY_THRESHOLD`, forcing the contract's `energyFactor` up (to as much as `DYNAMIC_ENERGY_MAX_FACTOR`). Every other unrelated user who subsequently calls that same contract during the same cycle then pays a percentage penalty on top of normal energy, i.e., higher TRX cost - exactly analogous to the Sherlock report where a whale LP inflates a shared utilization-based fee metric to force other users into paying elevated fees.

### Finding Description
The dynamic-energy factor for a contract is computed and updated in `Program.updateContextContractFactor()`, keyed only by `getContextAddress()` (the contract being executed), and persisted via `ContractStateCapsule`: [1](#0-0) 

The underlying state transition is in `ContractStateCapsule.catchUpToCycle`, which increases `energyFactor` for the *whole contract* whenever cumulative `energyUsage` recorded by **any caller** during the previous cycle exceeded `threshold`: [2](#0-1) 

Usage is accumulated indiscriminately from every transaction that touches the contract, regardless of who sent it, via `Program.addContextContractUsage`: [3](#0-2) 

Once the factor is above `DYNAMIC_ENERGY_FACTOR_DECIMAL`, `VM.play` applies a proportional penalty to every opcode's energy cost for **every subsequent call into that contract**, independent of who is calling: [4](#0-3) 

Because the counter is global to the contract and not scoped per-caller, an attacker does not need any special privilege, stake, or majority position (unlike the whale-LP scenario) - they simply need to send enough cheap transactions to a target contract to drive its usage above the configured threshold. Once the factor ramps up (multiplicatively, `increasePercent = 1 + increaseFactor/precision`, capped at `DYNAMIC_ENERGY_MAX_FACTOR`), it persists and decays slowly over subsequent cycles (`decreasePercent` in `catchUpToCycle`), meaning the penalty imposed on innocent users of a popular contract (e.g., a widely used token or DEX contract) can last well beyond the attacker's own transactions.

### Impact Explanation
Any legitimate user calling the targeted contract while its `energyFactor` is elevated pays a real, additional TRX cost (energy penalty, capped by `DYNAMIC_ENERGY_MAX_FACTOR`) that they did not choose and cannot avoid short of not using the contract. This is a concrete loss-of-funds condition imposed on unrelated third parties by an unprivileged actor - the direct on-chain analog of the Sherlock finding, where a market participant intentionally inflates a shared utilization/fee metric to force higher costs onto other users of the same resource.

### Likelihood Explanation
The mechanism is only active when `ALLOW_DYNAMIC_ENERGY` is enabled via committee proposal (see `ProposalService`/`DynamicPropertiesStore` `DYNAMIC_ENERGY_*` parameters), and requires the attacker to spend real energy fees to drive up usage. However, unlike the Sherlock scenario, the attacker needs no stake or majority position in any pool - just enough TRX/energy to send low-cost repeated calls into the target contract, making the attack straightforward to mount against any contract with a low enough `DYNAMIC_ENERGY_THRESHOLD` relative to its popularity.

### Recommendation
Consider scoping the dynamic-energy usage/penalty tracking so that an attacker's self-generated usage cannot inflate the fee charged to unrelated callers - e.g., factor in per-caller/per-transaction-origin usage patterns, add a cost-of-attack floor (make inflating usage disproportionately expensive to the attacker relative to the total penalty imposed on others), or bound how much a single account can contribute to a contract's cycle usage counter.

### Proof of Concept
1. Committee enables `ALLOW_DYNAMIC_ENERGY` with a modest `DYNAMIC_ENERGY_THRESHOLD` and non-trivial `DYNAMIC_ENERGY_INCREASE_FACTOR`/`DYNAMIC_ENERGY_MAX_FACTOR` (as intended by the feature).
2. Attacker identifies a popular contract (e.g., a widely-used token contract) and, using their own account(s), submits many low-value transactions invoking cheap opcodes on that contract until `contractStateCapsule.getEnergyUsage()` exceeds `threshold` for the current cycle (tracked via `Program.addContextContractUsage`).
3. On the next cycle boundary, `ContractStateCapsule.catchUpToCycle` raises `energyFactor` for that contract (bounded by `maxFactor`).
4. Any unrelated user calling the same contract during that (and subsequent, slowly-decaying) cycle(s) now has their opcode energy costs inflated by `VM.play`'s penalty logic, paying more TRX for the exact same operations than before the attack - with no way to opt out short of avoiding the contract entirely.

```java
  public long updateContextContractFactor() {
    ContractStateCapsule contractStateCapsule =
        contractState.getContractState(getContextAddress());

    if (contractStateCapsule == null) {
      contractStateCapsule = new ContractStateCapsule(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber());
      contractState.updateContractState(getContextAddress(), contractStateCapsule);
    } else {
      if (contractStateCapsule.catchUpToCycle(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber(),
          VMConfig.getDynamicEnergyThreshold(),
          VMConfig.getDynamicEnergyIncreaseFactor(),
          VMConfig.getDynamicEnergyMaxFactor(),
          VMConfig.allowStrictMath(),
          VMConfig.disableJavaLangMath())) {
        contractState.updateContractState(getContextAddress(), contractStateCapsule
        );
      }
    }
    contextContractFactor = contractStateCapsule.getEnergyFactor()
        + Constant.DYNAMIC_ENERGY_FACTOR_DECIMAL;
    return contextContractFactor;
  }
```

```java
  public boolean catchUpToCycle(
      long newCycle, long threshold, long increaseFactor, long maxFactor,
      boolean useStrictMath, boolean disableMath
  ) {
    long lastCycle = getUpdateCycle();

    // Updated within this cycle
    if (lastCycle == newCycle) {
      return false;
    }

    // Guard judge and uninitialized state
    if (lastCycle > newCycle || lastCycle == 0L) {
      reset(newCycle);
      return true;
    }

    final long precisionFactor = DYNAMIC_ENERGY_FACTOR_DECIMAL;

    // Increase the last cycle
    // fix the threshold = 0 caused incompatible
    if (getEnergyUsage() > threshold) {
      lastCycle += 1;
      double increasePercent = 1 + (double) increaseFactor / precisionFactor;
      this.contractState = ContractState.newBuilder()
          .setUpdateCycle(lastCycle)
          .setEnergyFactor(min(
              maxFactor,
              (long) ((getEnergyFactor() + precisionFactor) * increasePercent) - precisionFactor,
              disableMath))
          .build();
    }
```
