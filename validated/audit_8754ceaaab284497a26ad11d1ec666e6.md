### Title
Unauthenticated forged frontier entries via unvalidated self-reported `HandshakeData.addrbytes`/`port` in neighbor-of-neighbor handshake handling - ([File: stackslib/src/net/neighbors/walk.rs], [File: stackslib/src/net/db.rs])

### Summary
`PeerDB::try_insert_peer` (and `has_peer`/`peer_slots`) key a `Neighbor` record purely off `neighbor.addr.addrbytes`/`port`, which are taken from `Neighbor::addr` built by `NeighborKey::from_handshake` directly from the payload's `HandshakeData.addrbytes`/`port` fields, not the verified TCP peer address. In the "neighbors-of-neighbor" handshake completion path, the caller (`NeighborWalk::handle_neighbor_handshake_accept`) saves this record with neither an address-match check against the address actually dialed (`naddr`) nor a public-key-hash check against the pubkey hash originally advertised for that address, unlike the sibling pingback path which does call `check_handshake_pubkey_hash`.

### Finding Description
The claimed equality — "stored-identity == authenticated-connection-identity" — is broken specifically for the neighbor-of-neighbor discovery step.

- `PeerDB::try_insert_peer` (`stackslib/src/net/db.rs:1452-1488`) only checks `has_peer`/`peer_slots` using `neighbor.addr.network_id/addrbytes/port`, values which originate entirely from the `Neighbor` struct passed in — it has no way to verify these against any real socket.
- `NeighborKey::from_handshake` (`stackslib/src/net/chat.rs:411-423`) builds a `NeighborKey` directly from `handshake_data.addrbytes`/`handshake_data.port` — attacker-controlled wire fields inside `HandshakeData`/`HandshakeAcceptData`.
- `Neighbor::load_and_update` (`stackslib/src/net/chat.rs:475-516`) uses this key to look up/build the `Neighbor`, and `Neighbor::save`/`save_update` (`stackslib/src/net/neighbors/neighbor.rs:47-74`) push it straight into `PeerDB::try_insert_peer`/`update_peer`.
- In the top-level handshake-with-`cur_neighbor` path (`NeighborWalk::handle_handshake_accept`, `stackslib/src/net/neighbors/walk.rs:676-737`), there IS a guard: for outbound walks, `neighbor_from_handshake.addr != self.cur_neighbor.addr` causes rejection (`PeerNotConnected`).
- In the "pingback" completion path (`pingback_handshakes_try_finish`, `stackslib/src/net/neighbors/walk.rs:1683-1725`), there IS a guard: `check_handshake_pubkey_hash` verifies the responder's public-key hash matches the expected `naddr.public_key_hash` before calling `add_or_schedule_replace_neighbor`.
- However, in the "neighbor-of-neighbor" handshake completion path — `NeighborWalk::neighbor_handshakes_try_finish` (`stackslib/src/net/neighbors/walk.rs:1133-1231`) calling `handle_neighbor_handshake_accept` (`stackslib/src/net/neighbors/walk.rs:1092-1124`) — **neither check exists**. The code takes `naddr` (the address we actually dialed, obtained from `cur_neighbor`'s `GetNeighbors` response) and `data.handshake` (the responder's self-declared `HandshakeData` inside the `HandshakeAccept`/`StackerDBHandshakeAccept` reply), and unconditionally calls `self.neighbor_db.add_or_schedule_replace_neighbor(network, preamble, &data.handshake, db_data, ...)`. `add_or_schedule_replace_neighbor` (`stackslib/src/net/neighbors/db.rs:368-426`) calls `Neighbor::load_and_update` (keyed by `data.handshake.addrbytes/port`) and then `.save()` → `PeerDB::try_insert_peer`, persisting whatever address the responder claimed, together with whatever `node_public_key` it claimed, with no cross-check against `naddr` or any expected pubkey hash for that address.

Attacker exploit flow:
1. Attacker runs an ordinary, reachable P2P node (or otherwise gets included as a `naddr` in some honest peer B's `GetNeighborsData` response — e.g. by simply handshaking normally with B once).
2. When victim node A performs an outbound neighbor-walk through B and reaches the "get handshakes from neighbors-of-neighbors" step, A dials the attacker's real, reachable socket address (`naddr`) and sends a `Handshake`.
3. The attacker replies with a `HandshakeAccept`/`StackerDBHandshakeAccept` whose inner `HandshakeData.addrbytes`/`port` are set to an arbitrary victim IP/port (not the attacker's own dialed address), and `node_public_key` set to the attacker's own key.
4. `handle_neighbor_handshake_accept` accepts this without validating the claimed address against `naddr` or validating the key against any expected hash, and persists a `Neighbor` row into A's `frontier` table keyed by the victim's address/port and slot, but with the attacker's public key.

### Impact Explanation
This allows an unprivileged remote attacker to write an unauthenticated, forged `Neighbor` record (victim's real address bound to attacker's public key) into another node's `frontier` PeerDB table without ever controlling a TCP connection to that victim address. Once stored, this poisoned record can be returned to other peers via the node's own `GetNeighbors`/random-neighbor-selection machinery (`PeerDBNeighborWalk::get_fresh_random_neighbors`/`pick_walk_neighbors` and `handle_getneighbors`), propagating the forged binding further into the network's frontier gossip, and can also disrupt legitimate future connection attempts to the real victim address (since the slot may now hold attacker's key/expected identity instead of the real one, or occupies one of the limited slots for that address). This matches "unauthenticated/unauthorized write to state" and "network-wide propagation of forged data" in the Critical impact category.

### Likelihood Explanation
- Preconditions: the attacker only needs a reachable P2P listener and needs to be reachable via a normal handshake (making it eligible to appear as a `naddr` in some other honest peer's `GetNeighbors` response) — no privileged role, no secret, no compromise of other peers.
- Attacker cost: trivial — respond to inbound handshake requests during the routine neighbor-walk process with a crafted `HandshakeAcceptData` payload.
- Repeatability: repeatable on every walk cycle that reaches the attacker as a neighbor-of-a-neighbor, and against any victim address/port the attacker chooses (subject to slot availability at that address bucket).
- Remote reachability: yes, exclusively through the P2P port via the standard handshake protocol.

### Recommendation
In `NeighborWalk::handle_neighbor_handshake_accept` (`stackslib/src/net/neighbors/walk.rs`), before calling `add_or_schedule_replace_neighbor`, validate the responder the same way `pingback_handshakes_try_finish` does: call `check_handshake_pubkey_hash(&naddr.to_neighbor_key(network), data, &naddr)` and additionally verify that `data.handshake.addrbytes`/`data.handshake.port` match `naddr.addrbytes`/`naddr.port` (allowing only the documented "any-net"/private-IP override case), rejecting/skipping storage otherwise. More broadly, `PeerDB::try_insert_peer`/`insert_or_replace_peer` should not be reachable from any code path with a `Neighbor` whose `addr` has not been confirmed to correspond either to the actual dialed/accepted socket address or to a pubkey-hash-verified `NeighborAddress`.

### Proof of Concept
Rust test plan (net-level, mirroring existing walk tests, e.g. `stackslib/src/net/tests/neighbors/`):
1. Set up node A with `cur_neighbor` = honest node B, and simulate `GetNeighbors` from B returning one `NeighborAddress` `naddr` pointing at a mock/attacker `NeighborComms` endpoint.
2. Have the mock endpoint, when connected to at `naddr`, respond with a crafted `StacksMessageType::HandshakeAccept(HandshakeAcceptData { handshake: HandshakeData { addrbytes: <victim_addr>, port: <victim_port>, node_public_key: <attacker_pubkey>, .. }, .. })`.
3. Drive `NeighborWalk::neighbor_handshakes_try_finish(&mut network)` to process this reply via `handle_neighbor_handshake_accept`.
4. Assert: `PeerDB::get_peer(network.peerdb_conn(), network_id, &victim_addr, victim_port)` returns `Some(Neighbor { public_key: attacker_pubkey, .. })`, proving a record for `victim_addr:victim_port` was stored using the attacker's key despite A never having a verified TCP connection to that address, and that no `check_handshake_pubkey_hash`-style rejection occurred (unlike in `pingback_handshakes_try_finish`).
