## Title
Witness Commission (Brokerage) Rate Can Be Changed Instantly With No Lockup, While Voters Remain Locked Under `UNFREEZE_DELAY_DAYS` - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

### Summary
A Super Representative (witness) can call `UpdateBrokerageContract` to change its reward "brokerage" (commission draw) percentage at any time, with the new rate taking effect starting the very next voting cycle. There is no lockup, cooldown, or advance-notice mechanism analogous to the one enforced on voters, who must wait `UNFREEZE_DELAY_DAYS` (14+ days, configurable via governance proposal) before they can withdraw TRX they froze to vote. This asymmetry lets a witness attract votes with a low commission and then unilaterally raise it to the maximum, capturing outsized rewards from delegators who cannot exit their position for weeks.

### Finding Description
`UpdateBrokerageActuator.execute()` simply writes the new commission unconditionally into `DelegationStore` under a special "current" key (cycle `-1`) via `delegationStore.setBrokerage(ownerAddress, brokerage)`, with the only bound being `0 <= brokerage <= 100` checked in `validate()`. [1](#0-0) [2](#0-1) 

`DelegationStore.setBrokerage(byte[] address, int brokerage)` overwrites this "current" value (`cycle == -1`) every time it is invoked, with no restriction on call frequency. [3](#0-2) 

At each maintenance round, `MaintenanceManager.doMaintenance()` copies whatever the "current" brokerage value is at that moment into the entry for the *next* cycle for every witness: [4](#0-3) 

`MortgageService.payReward()` then reads the per-cycle brokerage to compute how much of the block/vote reward the witness keeps versus what is distributed to voters: [5](#0-4) 

Meanwhile, a voter who wants to exit a witness they voted for must first unfreeze their TRX via `UnfreezeBalanceV2Contract`, and can only withdraw the funds after `unfreezeDelayDays` (governed by the `UNFREEZE_DELAY_DAYS` chain parameter, default measured in multi-day `FROZEN_PERIOD` units) has elapsed: [6](#0-5) [7](#0-6) 

This is functionally the same bug class described in the report: the entity receiving delegated stake (the witness) can change its commission with no delay while the delegator's exit is delayed by a much longer lockup, letting the operator extract a low-commission rate to attract votes and then raise it once voters are committed and unable to react before the next reward cycle(s).

### Impact Explanation
A malicious or opportunistic SR can advertise a low `brokerage` (e.g., 0-1%) to attract voters and delegated TRX, then submit `UpdateBrokerageContract` to raise it to the maximum (100%) right before/after a maintenance cycle boundary. Because `MaintenanceManager` immediately copies the "current" value into the next cycle's snapshot with no notice period, the new (higher) commission is applied to reward distribution for that cycle before voters can react — and voters cannot fully exit (unfreeze + withdraw) for the `UNFREEZE_DELAY_DAYS` period. This results in an unbacked shift of expected voter rewards to the witness, i.e., voters' expected earnings are misappropriated without their consent, over one or more reward cycles.

### Likelihood Explanation
Any witness account (a role reachable by any account that can accumulate enough votes to become an active/standby witness, and technically any account can submit `UpdateBrokerageContract` provided a `WitnessCapsule` exists for it) can trigger this by sending a single, low-cost, always-valid transaction. No special privilege beyond being a registered witness is required, and the actuator itself imposes no cooldown or rate limit, as shown by `UpdateBrokerageActuatorTest.successUpdate`, which performs the update in a single call with no time-based guard. [8](#0-7) 

### Recommendation
Introduce a lockup/cooldown period for `UpdateBrokerageContract`, e.g., apply new brokerage values only after N cycles (rather than the immediately following cycle), or require advance-notice similar to `UNFREEZE_DELAY_DAYS`, and/or cap the magnitude of a single commission increase per time window. This mirrors the audit's recommendation to timelock commission changes analogous to the stake lockup.

### Proof of Concept
1. Register as an SR / operate an existing witness account `W`, and initially set `brokerage = 1` via `UpdateBrokerageContract` (`UpdateBrokerageActuator.execute`, `DelegationStore.setBrokerage(W, 1)`).
2. Voters freeze TRX and vote for `W` via `FreezeBalanceV2`/`VoteWitnessContract`, expecting a 1% commission and depending on `UNFREEZE_DELAY_DAYS` before being able to exit if conditions change.
3. Immediately before/at the next maintenance cycle boundary, `W` submits `UpdateBrokerageContract` with `brokerage = 100`.
4. On `MaintenanceManager.doMaintenance()`, the value is copied into `nextCycle`'s brokerage entry for `W` (`consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java:158-159`).
5. In the following cycle, `MortgageService.payReward()` computes `brokerageAmount` using the new 100% rate, so `value -= brokerageAmount` leaves `0` for voter rewards — the witness now keeps the entire reward while voters, still locked by `unfreezeDelayDays`, cannot immediately withdraw and re-delegate elsewhere.
