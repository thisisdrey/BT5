## Finding: Unbounded HTTP response buffering in `libsigner`'s StackerDB HTTP client

### Title
Unbounded memory allocation reading StackerDB HTTP responses in libsigner - (File: `libsigner/src/http.rs`)

### Summary
`libsigner::http::run_http_request`, used by `StackerDBSession` (the signer's client for talking to a Stacks node's StackerDB HTTP RPC endpoints), reads the entire HTTP response into memory with `sock.read_to_end(&mut buf)` before any size validation occurs. Unlike the node's own HTTP stack (`stackslib`), which enforces `MAX_MESSAGE_LEN`/`BoundReader` at every response-consumption point, this code path has no upper bound on the number of bytes buffered from the peer, so a peer that streams data indefinitely (up to the socket read timeout) can force the signer process to allocate unbounded memory — the same class of bug as the ERC165Checker issue, where a callee is assumed to return a bounded amount of data but is not actually constrained to do so.

### Finding Description

`sock.read_to_end(&mut buf)` has no length cap — it keeps appending to `buf` until the connection is closed (bounded only by the pre-set `socket_timeout`, not by byte count). Only *after* the entire response has been buffered does `decode_http_response`/`decode_http_body` run, and even `decode_http_body`'s chunked-decoder bound (`MAX_MESSAGE_LEN`) is applied only to the *chunked* case, not to the raw `buf` that was already fully read.

Compare this to the node's own HTTP client path in `stackslib`, where every response body is read through a `BoundReader` capped at `MAX_MESSAGE_LEN` before any parsing happens, e.g.: [2](#0-1) 
and per-endpoint response parsers such as `RPCGetStackerDBChunkRequestHandler::try_parse_response` bound decode size to `STACKERDB_MAX_CHUNK_SIZE`: [3](#0-2)

Notably, `get_latest_chunks` only checks the size of the body *after* it has already been fully buffered in memory: [6](#0-5) 
so the size check happens too late to prevent the unbounded allocation from occurring.

### Impact Explanation
This breaks the "bytes vs. expected/committed length" equality: the transport implicitly assumes a Stacks-node-scale response (bounded by `STACKERDB_MAX_CHUNK_SIZE`/`MAX_MESSAGE_LEN`, as enforced everywhere else in the codebase) but does not enforce it itself. A peer on the other end of the TCP connection that a signer session connects to — whether a misbehaving/compromised node, or any host reachable via the configured `host` string — can respond with an arbitrarily large or slow-but-endless byte stream (up to the read timeout) and force the signer process to keep growing `buf` unboundedly, leading to memory exhaustion/DoS on the signer. This matches the "Critical - remote crash/unauthenticated DoS from few messages" impact bucket, since it requires no signing key, no auth, and no more than one connection to trigger.

### Likelihood Explanation
Every `list_chunks`, `get_chunks`/`get_chunk`, `get_latest_chunks`/`get_latest_chunk`, and `put_chunk` call from a signer goes through this path, and it is triggered on ordinary RPC responses — no special preconditions are needed beyond controlling (or spoofing/MITM-ing) the TCP endpoint the signer session talks to. The bound is missing entirely (not merely mis-sized), so exploitation is a straightforward "send a lot of bytes without closing the connection" attack, bounded only by the configured socket timeout.

### Recommendation
Wrap the socket read in `run_http_request` with a bounded reader (mirroring `stacks_common::codec::MAX_MESSAGE_LEN`/`STACKERDB_MAX_CHUNK_SIZE` as used elsewhere in the codebase, e.g. `stackslib`'s `BoundReader`) so the total bytes read from the peer for a single HTTP response cannot exceed the protocol's known maximum message/chunk size, and reject/abort the read (rather than truncate after full buffering) once that bound is exceeded.

### Proof of Concept
1. Stand up a TCP listener acting as the `host` a `StackerDBSession` is configured to talk to (e.g., simulate a compromised/malicious Stacks node RPC endpoint).
2. When the signer calls `list_chunks()`/`get_chunk()`/`put_chunk()`, have the listener accept the connection, send valid-looking headers, and then stream data continuously (e.g. `chunked` encoding with an unbounded number of chunk fragments, or simply keep the connection open writing bytes) without ever completing, up to just under the signer's configured `socket_timeout`.
3. Observe the signer process's memory grow unbounded as `run_http_request`'s `buf` (in `libsigner/src/http.rs`, line 249-251) accumulates all bytes sent before the timeout fires, with no cap enforced during the read.

            usize::try_from(STACKERDB_MAX_CHUNK_SIZE)
                .expect("infallible: StackerDB chunk size exceeds usize::MAX")

        for slot_id in slot_ids.iter() {
            let path = stackerdb_get_chunk_path(self.stackerdb_contract_id.clone(), *slot_id, None);
            let chunk = match self.rpc_request("GET", &path, None, &[]) {
                Ok(body_bytes) => {
                    // Verify that the chunk is not too large

                        None
                    } else {
                        Some(body_bytes)
                    }
                }
                Err(RPCError::HttpError(code)) => {

                    }
                    None
                }
                Err(e) => {
                    return Err(e);
                }
            };
            payloads.push(chunk);
        }
        Ok(payloads)
    }
