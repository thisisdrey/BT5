### Title
Anti-replay window check-then-update race in `ConnectionState.Decrypt()` allows a duplicated/replayed data packet to be processed twice - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt()` releases `decryptLock` between the replay-window `Check()` and the replay-window `Update()`, with the AEAD decryption running in between while the lock is *not* held. When Nebula is configured to use more than one UDP reader routine (`f.routines > 1`), two goroutines can concurrently process a duplicated copy of the same encrypted data packet, both pass `Check()` before either has called `Update()`, and both decrypt and deliver the packet to the tun device — one of the `Update()` calls will report a duplicate too late to prevent the first delivery.

### Finding Description
`Decrypt()` performs three separate critical-section steps but only synchronizes each step individually, not the operation as a whole: [1](#0-0) 

```
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)   // step 1: "is this counter unseen?"
cs.decryptLock.Unlock()
...
out, err = cs.dKey.DecryptDanger(...)          // step 2: expensive AEAD op, lock NOT held
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)   // step 3: "mark this counter seen"
cs.decryptLock.Unlock()
```

This is the same class of bug as the reported `settleAuction()` issue: a check is performed, an unguarded/interruptible operation runs, and only afterward is the state mutation ("effect") committed. In the DeFi report, the gap between check and effect let a reentrant call inject malicious state; here, the gap between `Check` and `Update` lets a second concurrent goroutine observe the pre-`Update` state and process the same message counter as if it were still fresh.

`Interface.run()` spawns `f.routines` independent reader goroutines, each of which calls `readOutsidePackets` → `ConnectionState.Decrypt` for packets landing on that queue: [2](#0-1) 

and the decrypted result is delivered to `handleOutsideMessagePacket` in `outside.go` as soon as `Decrypt` returns without error, with `Update`'s failure only detected after the fact: [3](#0-2) 

Because `Check` and `Update` are not combined into one atomic "check-and-mark" operation across the whole `Decrypt` call, two threads racing on a duplicate ciphertext (same `h.MessageCounter`, same `HostInfo`) can both see `Check() == true`, both successfully decrypt, and only one loses on `Update()` — but by then the other packet has already been decrypted and handed to the tun device / message handler.

### Impact Explanation
An on-path or off-path attacker who can duplicate/replay a previously observed encrypted data packet onto the multiqueue UDP listener (or exploit any natural network duplication, e.g. via multipath/duplicate delivery) can cause the same application-layer plaintext to be delivered twice on the tun interface, or exploit the window in more targeted ways to defeat the anti-replay guarantee that the `Bits` sliding window is specifically designed to provide. This falls under the accepted "traffic decryption/forgery/replay" impact category: the anti-replay mechanism is Nebula's core protection against remote replay of captured ciphertext, and the race concretely allows replay to succeed under legitimate multi-routine configurations.

### Likelihood Explanation
This requires `routines > 1` (multiqueue mode, common on Linux with `SupportsMultipleReaders`/`SupportsMultiqueue`) and the ability to deliver two copies of the same encrypted packet to different reader queues at close to the same time, which an attacker fully controls since they craft/duplicate the UDP payload themselves. No certificate, valid peer, or authenticated position is required beyond already being a data-plane peer able to send packets to the listener — the race is triggered purely by duplicate delivery of a single captured ciphertext.

### Recommendation
Hold `decryptLock` for the full duration of the check-decrypt-update sequence in `Decrypt()` (and the analogous `VerifyRelay()`), or restructure the anti-replay window into a single atomic "reserve-then-commit" operation so that a second concurrent attempt with the same counter is rejected before any decryption work is performed, rather than only being rejected after the fact by `Update()`.

### Proof of Concept
1. Configure a Nebula node with `listen.routines` (or platform default) `> 1` so multiple UDP reader goroutines exist for the same underlay socket.
2. Establish a tunnel and capture one legitimate encrypted data packet (header + `MessageCounter` + ciphertext) sent to that node.
3. Immediately re-inject two copies of that exact packet from an attacker-controlled sender at the same instant, arranged (e.g., via socket batching/`recvmmsg` batch or near-simultaneous sends) so both copies are read by different reader routines/goroutines before either finishes `Decrypt()`.
4. Observe that both goroutines' `cs.window.Check(l, messageCounter)` calls return `true` (since neither has run `Update` yet), both successfully call `cs.dKey.DecryptDanger`, and both proceed to `handleOutsideMessagePacket`, delivering the same plaintext payload twice to the tun device — only one of the two `Update()` calls will subsequently report `false`, too late to have prevented the duplicate delivery.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
