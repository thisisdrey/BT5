### Title
Non-hardened Bancor exchange calculation uses double-precision `Math.pow()`/`StrictMath.pow()` without monotonicity or balance-sign validation, enabling drainage/inconsistency of exchange pool balances - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The default (non-hardened) TRC10 Bancor-relay exchange math in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` computes `pow(1 + quant/balance, exponent)` using floating-point `Math.pow`/`StrictMath.pow` via `Maths.pow` [1](#0-0) , and the result is truncated to `long` and applied directly to `firstTokenBalance`/`secondTokenBalance` in `ExchangeCapsule.transaction()` without any check that the new balances remain non-negative [2](#0-1) . This mirrors the PRBMath `pow()` bug class: a power function whose numerical implementation can fail to preserve the monotonicity invariant (`x >= y, a >= 0 ⇒ x^a >= y^a`) required by the caller for safe, monotonic state transitions.

### Finding Description
`ExchangeCapsule.transaction()` is reachable from any account via `ExchangeTransactionActuator` (any signed `ExchangeTransactionContract`), and picks between two implementations based on the `ALLOW_HARDEN_EXCHANGE_CALCULATION` chain parameter [3](#0-2) :
- The hardened path (`SafeExchangeProcessor`) uses `BigDecimal` with explicit scale/rounding and explicitly asserts non-negative resulting balances, throwing `ContractValidateException` otherwise [4](#0-3) , and `ExchangeCapsule.transaction()` checks `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` only for `hardenedCalc` [5](#0-4) .
- The legacy, default (`hardenedCalc == false`) path uses `ExchangeProcessor`, which computes the bancor formula with double-precision `pow()` and truncates via `(long) issuedSupply` / `(long) exchangeBalance` [1](#0-0) , with **no negative-balance guard applied** in that branch.

Because this legacy path is a direct analog of the reported `pow()` bug class (a fixed/floating point power function relied upon for a critical monotonic invariant in an AMM-like exchange, without independent bounds checking), any accumulated floating-point rounding/precision error in `Maths.pow` can produce a `buyTokenQuant` inconsistent with the expected monotonic Bancor curve, and — since the un-hardened path performs no post-condition validation — can drive `firstTokenBalance`/`secondTokenBalance` negative or otherwise inconsistent with actual token conservation. The existence of `SafeExchangeProcessor`, the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal, and its own regression tests explicitly demonstrating "hardened mode ... rejects imprecise input" / "Exchange balance must be >=0 after transaction" checks [6](#0-5)  confirm the project's own acknowledgement that the legacy double-based computation is unsafe and needed hardening — the same root cause class as the external PRBMath report (a power-function implementation whose numeric imprecision breaks a monotonic safety invariant relied upon by calling business logic).

### Impact Explanation
If `ALLOW_HARDEN_EXCHANGE_CALCULATION` is not yet activated on a given network (it is a governance-gated chain parameter defaulting to off, activated only via `ProposalType.ALLOW_HARDEN_EXCHANGE_CALCULATION` after `VERSION_4_8_2` [7](#0-6) ), every `ExchangeTransactionContract` transaction on that chain executes the un-guarded double-`pow()` path. An attacker crafting quantities/balances (e.g., at ratio boundaries where floating point `pow` results round non-monotonically or truncate unexpectedly) can obtain a `buyTokenQuant` inconsistent with the real Bancor invariant, potentially receiving more tokens than the pool can back or driving pool balances negative — resulting in unbacked token balances / theft from the exchange pool, a concrete "unbacked balance" / "theft of funds" outcome.

### Likelihood Explanation
Exploitation only requires a single signed `ExchangeTransactionContract` from any account owning TRX/TRC10 tokens and an existing Bancor exchange pair — no privileged role needed. The main uncertainty is whether `ALLOW_HARDEN_EXCHANGE_CALCULATION` is already active on the target network; if active, this specific path is already mitigated (this could not be verified with certainty from the indexed code alone since chain-parameter activation state is a runtime governance value, not a static code fact).

### Recommendation
Make hardened (`BigDecimal`-based, bounds-checked) exchange math the unconditional default rather than gating it behind an optional chain parameter, or add the same non-negative post-condition assertion to the legacy `ExchangeProcessor` path in `ExchangeCapsule.transaction()` regardless of `hardenedCalc`, and audit `Maths.pow`/`MathWrapper.pow` (including the ARM-specific historical override map) for cases where floating-point rounding could violate `x >= y ⇒ x^a >= y^a` for values relevant to exchange balances.

### Proof of Concept
Concrete floating-point inputs that violate monotonicity for the specific `Maths.pow`-based formula could not be empirically derived without executing code (unlike the Solidity PoC in the source report, this requires runtime testing of `StrictMath.pow`/`Math.pow` edge cases against `ExchangeProcessor.exchangeToSupply/exchangeFromSupply`); a Devin session with access to a JVM environment would be needed to construct exact `balance`/`quant` values that trigger a non-monotonic or negative-balance outcome and confirm exploitability end-to-end via `ExchangeTransactionActuator`.

    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0

    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
