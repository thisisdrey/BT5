### Title
Out-of-bounds Zip64 extra-field attribute read leads to attacker-controlled offset/size used for memory copy in singlejar - (File: src/tools/singlejar/zip_headers.h)

### Summary
`Zip64ExtraField::attr64(int index)` in [2](#0-1)  indexes into the flexible array member `attr_[]` using an index derived from which 32-bit fields are marked `0xFFFFFFFF` (`zfield_has_ext64`), but never checks that index against `attr_count()` (`payload_size() / sizeof(uint64_t)`), which is derived from the attacker-supplied `payload_size` of the extra field. `CDH::local_header_offset()` and `CDH::compressed_file_size()`/`uncompressed_file_size()` in the same file (e.g. lines 406-493) compute `attr_no` purely from the 32-bit sentinel fields and then call `z64->attr64(attr_no)` unconditionally.

### Finding Description
This is directly analogous to CVE-2015-9289: the kernel bug trusted a userspace-supplied size against a fixed maximum without enforcing it, allowing an out-of-bounds access. Here, the "declared maximum" is `attr_count()` computed from the extra field's own `payload_size` field, and the "actual index accessed" is `attr_no`, computed independently from the 32-bit size/offset fields' sentinel values (`0xFFFFFFFF`). A crafted JAR/ZIP entry can set, e.g., `compressed_file_size32 = 0xFFFFFFFF` and `local_header_offset32 = 0xFFFFFFFF` (both requiring Zip64 extension attributes) while supplying a Zip64 extra field with `payload_size` covering only one `uint64_t` attribute (`attr_count() == 1`). The code then calls `attr64(1)` or higher indices without any bounds check, reading 8 bytes beyond the declared/allocated payload of the extra field.

This flows into `OutputJar::AddJar` at [3](#0-2) , where `jar_entry->local_header_offset()` and `jar_entry->compressed_file_size()` (both ultimately calling the unchecked `attr64`) determine `copy_from` and `num_bytes` for a raw memory copy of the *input jar's mapped memory* into the output jar at [1](#0-0) . If the out-of-bounds `attr64` read yields an attacker-influenced garbage offset/size (bytes adjacent to the extra field in the mmap'd file, which is attacker controlled since the whole file is attacker-supplied), `copy_from`/`num_bytes` can point outside the intended entry's data region — within the same mapped file (still attacker-controlled bytes, so no crash) or, if the malformed extra field sits at the very end of the central directory / mapped region, beyond the mapping (a heap/mmap over-read).

Bazel's existing hardening (visible in the test `CreateZipWithMalformedExtraField` in [4](#0-3)  and the bounds checks in `OutputJar::WriteEntry`/`AppendToDirectoryBuffer` at [5](#0-4)  and [6](#0-5) ) only validates that each extra field's `size()` does not exceed the *outer* extra-fields buffer end (`ExtraField::find` in [7](#0-6) ). None of these checks validate that a found Zip64 field's `attr_count()` is sufficient for the number of attributes the 32-bit-field sentinels imply should be present. This is a distinct, unpatched gap.

### Impact Explanation
Because `copy_from`/`num_bytes` derived from the corrupted read directly drive `WriteBytes(input_jar.mapped_start() + copy_from, num_bytes)`, a hostile dependency jar (fetched via `http_jar`/`http_archive`/`http_file` or supplied by an untrusted build target during `bazel build`'s deploy-jar assembly) can cause `singlejar` to read outside the intended entry boundaries of the memory-mapped input file. At minimum this is an out-of-bounds/heap over-read (potential crash or leak of adjacent process memory bytes into the produced output jar); it does not, on its own, demonstrate arbitrary write or code execution.

### Likelihood Explanation
Requires the attacker to control only the bytes of a JAR/ZIP file consumed as a build input (e.g., a dependency fetched from a hostile URL/registry), which matches the allowed unprivileged-attacker threat model. No control-plane or credential access is needed; the entire trigger is representable inside a bytes-only artifact. However, exploitation is a "misread of size/offset from attacker's own data," not a boundary violation against a *different* build's data, so it does not clearly satisfy the strict "impact" bar (integrity bypass of a pinned checksum, escape of repo/exec root, credential exfiltration, or cross-build cache poisoning) required by the rules — the corrupted read stays within the attacker-supplied file content itself in the common case, and only becomes a true OOB read of unrelated memory in the edge case where the malformed field sits at the very end of the mapped region.

### Recommendation
Add a check that `attr_no < attr_count()` before calling `attr64(attr_no)` in `LH::compressed_file_size()`/`uncompressed_file_size()` and `CDH::compressed_file_size()`/`uncompressed_file_size()`/`local_header_offset()`, failing with `diag_errx` (consistent with the existing malformed-extra-field diagnostics) when the Zip64 extra field does not carry enough attributes for the sentinel values present in the 32-bit fields.

### Proof of Concept
Extend the existing `CreateZipWithMalformedExtraField`-style harness in `output_jar_simple_test.cc`: construct a `CDH`/`LH` pair with `compressed_file_size32 = uncompressed_file_size32 = local_header_offset32 = 0xFFFFFFFF` but attach a `Zip64ExtraField` with `payload_size = 8` (i.e., `attr_count() == 1`) instead of the spec-required 24 bytes (3 attributes). Feed this crafted archive through `OutputJar::AddJar`/`SingleJarMain` and observe that `local_header_offset()`/`compressed_file_size()` return values derived from `attr64(1)`/`attr64(2)`, indexing past the declared 8-byte payload — verifiable under ASan as a heap-buffer-overflow (read) inside `Zip64ExtraField::attr64`.
