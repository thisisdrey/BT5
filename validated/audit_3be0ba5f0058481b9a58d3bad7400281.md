### Title
`pallet-asset-rewards` admin calls `set_pool_expiry_block` / `set_pool_reward_rate_per_block` never re-validate that the pool's assets still exist, letting a pool built on a delisted/destroyed asset be extended indefinitely - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet_asset_rewards::Pallet::create_pool` (via the `RewardsPool` implementation) validates that both the `staked_asset_id` and `reward_asset_id` exist before a pool can be created: [1](#0-0) 
However, the two admin-facing mutators that extend a pool's lifetime and boost its reward emission — `set_pool_expiry_block` and `set_pool_reward_rate_per_block` — never repeat this check: [2](#0-1) [3](#0-2) 
This mirrors the reported Warden Finance issue exactly: an "eligibility"/whitelisting check (`asset_exists`) is enforced only at creation time, and the "extend" style dispatchables that keep the same object alive indefinitely never re-check it.

### Finding Description
`create_pool` is the only place in the pallet that calls `T::Assets::asset_exists` on `staked_asset_id`/`reward_asset_id`: [4](#0-3) 

Once a pool exists, its `admin` (an ordinary, non-privileged account set at creation, not root/governance) can call:
- `set_pool_reward_rate_per_block` — only checks `pool_info.admin == *admin` and that the new rate is higher, never asset existence: [5](#0-4) 
- `set_pool_expiry_block` — only checks admin match and that expiry is only extended, never asset existence: [6](#0-5) 

Both of these are also exposed as public extrinsics that require only `T::CreatePoolOrigin` OR a plain signed origin matching the pool admin: [7](#0-6) [8](#0-7) 

If the `reward_asset_id` or `staked_asset_id` referenced by a pool is later destroyed/delisted (e.g. via `pallet-assets::start_destroy`/`finish_destroy`, or any other mechanism the runtime uses to remove an asset from circulation), `asset_exists` for that ID becomes `false`. Nothing in the pallet re-checks this before the pool's `admin` continues to:
- extend the pool's `expiry_block` (keeping the pool "active" and continuing reward accrual math), and
- increase `reward_rate_per_block` (increasing the nominal reward obligation of a pool tied to a token that no longer exists / was delisted for being malicious).

Neither `stake`, `harvest_rewards`, nor `unstake` re-validate asset existence either — they rely purely on the `Pools` storage entry created at genesis of the pool. This is precisely the pattern flagged in the external report: the whitelist/eligibility check exists only at creation-time input validation, and the perpetual "extend" style calls bypass it entirely.

### Impact Explanation
This breaks the intended invariant that only pools backed by valid, sanctioned assets can be actively managed. Concretely:
- A pool's admin (an unprivileged, ordinary account — anyone who created a pool or was set as its admin) can keep a reward campaign referencing a delisted/destroyed asset alive forever by repeatedly extending `expiry_block`, defeating any governance decision to remove that asset from the system.
- Because `reward_rate_per_block` can only be increased (`RewardRateCut` error prevents decreasing it) and `expiry_block` can only be extended (`ExpiryCut` error prevents shortening it), there is no way to wind the pool down administratively once the backing asset is gone — the pool's accounted `reward_per_token_stored` keeps growing based on a rate tied to a non-existent/delisted asset, and stakers who already froze `staked_asset_id` tokens have no clean exit path since `unstake` and `cleanup_pool` both operate against the frozen/existing on-chain asset state.
- This directly matches the Required Impact category "public underpriced work / bypass of whitelisting/eligibility gates" and risks locking staker funds or corrupting the pool's reward accounting if the asset backing either side of the pool is later removed from the system.

### Likelihood Explanation
- Any account that created a pool (or was designated `admin`) can trigger this — no elevated privilege beyond ordinary origin is required for `set_pool_expiry_block`/`set_pool_reward_rate_per_block` once the pool exists.
- The precondition (an asset used by an existing pool later being destroyed/delisted) is a normal operational event in systems using `pallet-assets`, since asset destruction is an expected lifecycle action (e.g., `start_destroy`) and is entirely independent of `pallet-asset-rewards`'s pool state.
- The missing check is a straightforward omission — `create_pool` calls `asset_exists` but the extend-style mutators do not, so no additional attacker sophistication is needed beyond calling the existing public extrinsics after the precondition asset removal occurs.

### Recommendation
Add the same `ensure!(T::Assets::asset_exists(...), Error::<T>::NonExistentAsset)` checks used in `create_pool` to `set_pool_expiry_block` and `set_pool_reward_rate_per_block` (checking `pool_info.reward_asset_id` / `pool_info.staked_asset_id` as relevant), so that a pool referencing a delisted/destroyed asset can no longer be extended or have its reward rate increased. Consider also blocking `stake` and `deposit_reward_tokens` under the same condition, and providing an admin/governance path to wind down (shorten expiry / zero reward rate) pools whose backing assets have been removed.

### Proof of Concept
1. Root/`CreatePoolOrigin` calls `create_pool(staked_asset_id = A, reward_asset_id = B, ...)`; both `A` and `B` pass `asset_exists` at this point and the pool is stored with `admin = X`.
2. Governance/asset-issuer later destroys asset `B` (e.g., it is found to be fraudulent) via `pallet-assets::start_destroy` + `finish_destroy`, so `T::Assets::asset_exists(B) == false`.
3. `X` (ordinary account, no special privilege) calls `set_pool_expiry_block(pool_id, DispatchTime::After(large_offset))` — succeeds because only `admin` match and "expiry can only be extended" are checked; `asset_exists(B)` is never checked: [3](#0-2) 
4. `X` then calls `set_pool_reward_rate_per_block(pool_id, higher_rate)` — likewise succeeds without any asset-existence check: [2](#0-1) 
5. The pool now continues accruing reward obligations denominated in a destroyed/delisted asset indefinitely, and its lifetime can never be shortened (`ExpiryCut`) nor its rate reduced (`RewardRateCut`), demonstrating the same "extend to keep using a delisted token forever" primitive as the original report.

	fn set_pool_reward_rate_per_block(
		admin: &T::AccountId,
		pool_id: PoolId,
		new_reward_rate_per_block: T::Balance,
	) -> DispatchResult {
		let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
		ensure!(pool_info.admin == *admin, BadOrigin);
		ensure!(
			new_reward_rate_per_block > pool_info.reward_rate_per_block,
			Error::<T>::RewardRateCut
		);

		// Always start by updating the pool rewards.
		let rewards_per_token = Self::reward_per_token(&pool_info)?;
		let mut pool_info = Self::update_pool_rewards(&pool_info, rewards_per_token)?;

		pool_info.reward_rate_per_block = new_reward_rate_per_block;
		Pools::<T>::insert(pool_id, pool_info);

		Self::deposit_event(Event::PoolRewardRateModified { pool_id, new_reward_rate_per_block });

		Ok(())
	}

	fn set_pool_expiry_block(
		admin: &T::AccountId,
		pool_id: PoolId,
		new_expiry: DispatchTime<BlockNumberFor<T>>,
	) -> DispatchResult {
		let now = T::BlockNumberProvider::current_block_number();
		let new_expiry_block = new_expiry.evaluate(now);
		ensure!(new_expiry_block > now, Error::<T>::ExpiryBlockMustBeInTheFuture);

		let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
		ensure!(pool_info.admin == *admin, BadOrigin);
		ensure!(new_expiry_block > pool_info.expiry_block, Error::<T>::ExpiryCut);

		// Always start by updating the pool rewards.
		let reward_per_token = Self::reward_per_token(&pool_info)?;
		let mut pool_info = Self::update_pool_rewards(&pool_info, reward_per_token)?;

		pool_info.expiry_block = new_expiry_block;
		Pools::<T>::insert(pool_id, pool_info);

		Self::deposit_event(Event::PoolExpiryBlockModified { pool_id, new_expiry_block });

		Ok(())
	}
