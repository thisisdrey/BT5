### Title
Liquidation reverts instead of clamping when seized amount exceeds remaining deposit balance, allowing cheap repeated front-running DoS of liquidations - ([File: contracts/Pool.sol])

### Summary
`Pool.liquidate` reverts with `AmountIsTooHigh` whenever the quoted `_totalSeized` exceeds the liquidated account's current `depositToken_.balanceOf(account_)` (contracts/Pool.sol:583-585). A liquidator computing the max repay via `quoteLiquidateMax` (which targets seizing the full deposit balance, contracts/Pool.sol:429-439) can have its transaction griefed: anyone can front-run with a tiny `liquidate` call (or the victim can do it from a second address, since only `_msgSender == account_` is blocked, contracts/Pool.sol:554) that seizes even 1 wei of collateral, shrinking `balanceOf` below the already-submitted `_totalSeized` and forcing a revert. Unlike JOJO's `depositBalance` (which users could reduce by withdrawal), Metronome locks collateral of unhealthy accounts (`unlockedBalanceOf` returns 0 when `_issuableInUsd == 0`, contracts/DepositToken.sol:383-398), so the front-running vector here is a dust partial liquidation rather than a withdrawal — but the resulting DoS is identical.

### Finding Description
The liquidation flow:
1. `liquidate` checks `PositionIsHealthy`, `AmountGreaterThanMaxLiquidable`, and `RemainingDebtIsLowerThanTheFloor`, then computes `(_totalSeized, _toLiquidator, _fee) = quoteLiquidateOut(...)`.
2. `if (_totalSeized > depositToken_.balanceOf(account_)) revert AmountIsTooHigh();` — strict check instead of clamping.
3. `depositToken_.seize` is `onlyIfCanSeize` (pool-only, DepositToken.sol:99-102, 343-345), so the balance can only be reduced by another `liquidate` call or by transfers/withdrawals — but unhealthy accounts have `unlockedBalanceOf == 0`, so competing liquidation is the reachable reduction path.

Attack: liquidator L calls `quoteLiquidateMax(msX, victim, msdY)` and submits `liquidate(..., amountToRepayMax, msdY)`. Attacker A (any EOA holding msX, possibly the victim's second account) front-runs with `liquidate(msX, victim, dustAmount, msdY)`, burning a few wei of debt and seizing a few wei of `msdY`. L's transaction then sees `balanceOf(victim) < _totalSeized` and reverts. `debtFloorInUsd` only constrains the *remaining* debt (Pool.sol:571-579) — the attacker simply leaves remaining debt above the floor (or repays down to exactly zero if balance permits), so it does not prevent the dust liquidation. `maxLiquidable` likewise permits small repays. This is repeatable every block for near-zero cost (gas + dust seized, which the attacker even gets paid the liquidator incentive on).

### Impact Explanation
Liquidations of accounts whose collateral is about to be fully seized can be perpetually reverted, delaying liquidation while prices move — leading directly to protocol bad debt/insolvency. Repeated reverts also discourage liquidator bots (wasted gas), a liveness failure on a critical function.

### Likelihood Explanation
Requires only an unprivileged account holding a dust amount of the synthetic token (obtainable via `mint` against own collateral or market buy) and standard mempool front-running. No privileged roles, oracle manipulation, or broken invariants needed. During volatile markets — exactly when liquidation throughput matters — this is cheap and incentive-aligned (the attacker can also simply be a competing liquidator preferring the whole position for themselves later, or the victim avoiding full seizure).

### Recommendation
Clamp instead of reverting: compute the maximum repay amount such that `_totalSeized <= depositToken_.balanceOf(account_)` (e.g., fall back to `quoteLiquidateIn(syntheticToken_, depositToken_.balanceOf(account_), depositToken_)` when the quote exceeds the balance), and proceed with the clamped `amountToRepay_`/`_totalSeized`. Alternatively, cap the seized amounts at `balanceOf` before `seize`, adjusting `amountToRepay_` consistently so the liquidator never overpays.

### Proof of Concept
Foundry fork test outline (deployed mainnet addresses from `deployments/mainnet/`):

```solidity
function test_liquidationDosViaFrontRun() public {
    // victim: unhealthy position, depositToken balance B, debt D
    uint256 maxRepay = pool.quoteLiquidateMax(msX, victim, msdY);

    // Attacker front-runs with dust liquidation (stays above debtFloorInUsd)
    vm.prank(attacker); // attacker holds >= dust of msX
    pool.liquidate(msX, victim, dustRepay, msdY); // succeeds, seizes ~1 wei msdY

    // Honest liquidator's tx now reverts
    vm.prank(liquidator);
    vm.expectRevert(Pool.AmountIsTooHigh.selector);
    pool.liquidate(msX, victim, maxRepay, msdY);
}
```

The existing test `should revert if paying more than needed to seize all deposit` (test/Pool.test.ts:783-789) already demonstrates the revert path; the PoC only needs an interleaved dust `liquidate` between `quoteLiquidateMax` and the max liquidation to show the front-run.
