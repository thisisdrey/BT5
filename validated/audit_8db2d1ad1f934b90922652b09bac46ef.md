### Title
Unauthenticated `RelayFromAddr` in `CreateRelayRequest` control message allows relay identity spoofing - ([File: relay_manager.go])

### Summary
`handleCreateRelayRequest` derives the "who is this relay for" identity (`from := protoAddrToNetAddr(m.RelayFromAddr)`) entirely from an attacker-controlled protobuf field inside the `NebulaControl` payload, rather than from the cryptographically authenticated identity of the sending peer (`h.vpnAddrs`, taken from `h.ConnectionState.peerCert` established during the noise handshake). This mirrors the report's bug class: an identity claim carried in application data is never cross-checked against the identity that was actually authenticated at the transport/handshake layer, so a malicious-but-otherwise-legitimate peer can assert an identity it doesn't hold.

### Finding Description
`relayManager.HandleControlMsg` unmarshals a `NebulaControl` message received over an already-established, authenticated tunnel from `HostInfo h`. For `CreateRelayRequest`/`CreateRelayResponse` it only checks that `RelayFromAddr`/`RelayToAddr` are non-nil [1](#0-0) , then dispatches to `handleCreateRelayRequest(v, h, f, msg)` [2](#0-1) .

Inside `handleCreateRelayRequest`, the claimed "relay from" identity is taken directly from the message body:
```go
from := protoAddrToNetAddr(m.RelayFromAddr)
target := protoAddrToNetAddr(m.RelayToAddr)
``` [3](#0-2) 

This `from` value is never compared against `h.vpnAddrs` (the peer's actual certificate-derived VPN address, established during the handshake and stored on the authenticated `HostInfo`). The only identity check performed is the opposite direction — that the *target* of the relay isn't `f.myVpnAddrsTable` (i.e., "am I the source") [4](#0-3) . There is no equivalent check that `from == h.vpnAddrs[0]` (or one of `h.vpnAddrs`).

As a result, when the caller (an authenticated peer `h`) is the actual relay and the relay's own address is `target`, the code adds a relay entry keyed by whatever `from` the sender claims:
```go
_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
``` [5](#0-4) 

Just as the cometBFT report describes an implicit-but-bypassable binding between `ProposerIndex` and the actual signer (only checked indirectly via a signature that can be replayed under a different session with identical signing material), here the binding between the claimed `RelayFromAddr` and the actual authenticated sender `h` is never checked at all — not even implicitly. Any peer that has a valid handshake with the responder can name an arbitrary victim VPN address as `RelayFromAddr` and establish relay/forwarding state on the responder for traffic purportedly originating "from" that victim.

### Impact Explanation
This allows a malicious authenticated peer to register itself (via `AddRelay`) as the source-side relay endpoint for any third-party VPN address of its choosing, without that third party's involvement or consent. Depending on relay state transitions this can be used to:
- Poison the responder's relay/hostmap state (`RelayState`, `Relays` index) with entries associated with a spoofed victim identity, causing state confusion between the real victim's future/most tunnel and the attacker's claimed one (an analog of the "penalization of the real proposer" impact in the report — here it's "state confusion for/attribution to the wrong peer").
- Potentially disrupt or hijack relay-based traffic paths for the victim address, since subsequent legitimate `CreateRelayRequest`/response flows for that same VPN address will be evaluated against attacker-seeded relay state (see the `Established`/`Disestablished` re-request branches that trust `existingRelay.RemoteIndex` set by this same unauthenticated `from`) [6](#0-5) .

This falls squarely within "remote state poisoning" via unauthenticated identity claims in a message that is otherwise cryptographically transported over an authenticated channel, but where the claimed application-layer identity is never bound to the authenticated peer.

### Likelihood Explanation
Any peer capable of completing a legitimate handshake (no CA-signed cert required beyond being a normal member of the mesh) can send a `CreateRelayRequest` control message with an arbitrary `RelayFromAddr`. No additional privilege, MITM position, or victim cooperation is required — this is reachable by any authenticated peer, making likelihood high once relay functionality (`am_relay`) is enabled on the target node.

### Recommendation
In `handleCreateRelayRequest` (and symmetrically in `handleCreateRelayResponse`), explicitly validate that the claimed `RelayFromAddr` corresponds to the authenticated sender's identity, i.e., assert `slices.Contains(h.vpnAddrs, from)` before creating or updating any `Relay` state keyed by `from`. Reject the message (log and return) if the claim doesn't match the certificate-derived `vpnAddrs` of `h`, analogous to explicitly correlating `ProposerIndex` with the actual signer's public key rather than relying on incidental/absent verification.

### Proof of Concept
1. Peer `Attacker` completes a normal, valid handshake with `Relay` (a node with `relay.am_relay = true`), obtaining an authenticated `HostInfo h` at `Relay` with `h.vpnAddrs = [AttackerVpnIp]`.
2. `Attacker` sends a `Control` message of type `NebulaControl_CreateRelayRequest` to `Relay`, setting `RelayFromAddr = VictimVpnIp` (an address `Attacker` does not own) and `RelayToAddr = Relay`'s own VPN address (or another target for which `Attacker` wants relay service).
3. `Relay.handleCreateRelayRequest` reads `from = VictimVpnIp` straight from the message, sees `target` is itself, and calls `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)`, installing relay state on `Relay` attributing the relay-from identity to `VictimVpnIp` — despite the packet actually being authenticated as coming from `Attacker`.
4. `Relay` sends back a `CreateRelayResponse` claiming `RelayFromAddr = VictimVpnIp`, and future relay-related control flow (state transitions in `StartRelays`/`EstablishRelay`) for `VictimVpnIp` at `Relay` is now influenced by state seeded by `Attacker`, not `Victim`.

Note: I was unable to fully trace every downstream consumer of this poisoned relay state (e.g., exact packet-forwarding implications in `handleOutsideRelayPacket`) within the available index; a Devin session with full repo access would be needed to confirm the complete blast radius of this state-poisoning path.
