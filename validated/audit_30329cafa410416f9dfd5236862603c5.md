### Title
Unchecked legacy Exchange pool arithmetic can drive `Exchange.firstTokenBalance`/`secondTokenBalance` negative, permanently corrupting AMM state - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
The Derby report describes a class of bug where a protocol computes deltas with signed arithmetic but only validates the *result* to be non‑negative on one code path, while another/legacy path performs the arithmetic and mutates persistent state without that check, allowing an attacker to permanently corrupt accounting once a signed value goes negative and is silently accepted. The same pattern exists in java-tron's Bancor-style TRX/TRC10 `Exchange` (market) implementation: `ExchangeCapsule.transaction()` only enforces `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` when `hardenedCalc` is `true`, but the default/legacy calculation path (`hardenedCalc=false`) skips this check entirely and commits the negative balances into the persisted `Exchange` protobuf.

### Finding Description
`ExchangeCapsule.transaction()` computes new pool balances using either a "hardened" or a "legacy" code path selected by the caller: [1](#0-0) 

The invariant check `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) throw ...` is only executed in the hardened branch. When `hardenedCalc` is `false` (the legacy path, using plain `+`/`-` instead of `StrictMathWrapper.addExact/subtractExact`), the method persists `newFirstTokenBalance`/`newSecondTokenBalance` into the `Exchange` capsule unconditionally, even if either has gone negative.

`hardenedCalc` is driven by `allowHarden()`, which is gated by the dynamic property `allowHardenExchangeCalculation()` — a committee-controlled proposal flag, not something guaranteed to be on: [2](#0-1) 

The reachable entrypoint is `ExchangeTransactionActuator`, which any unprivileged account (not just the exchange creator) can invoke by broadcasting an `ExchangeTransactionContract`: [3](#0-2) 

`doValidate()` for this actuator bounds the *sold* token amount (`tokenQuant`) against balances but does not independently re-derive or bound `anotherTokenQuant` beyond what `exchangeCapsule.transaction()` itself computes: [4](#0-3) 

Because the actual pool-balance mutation and its only negative-balance guard both live inside `ExchangeCapsule.transaction()`, and that guard is conditioned on `hardenedCalc`/`allowHarden`, an attacker trading against a pool while the hardened flag is not enabled (its default/until-voted-on state) can drive one side of the pool negative. This is structurally the same root cause as the Derby bug: a signed arithmetic result is only checked to be non-negative on one code path, while the actually-committed state-mutation path can silently accept a negative value.

Once `firstTokenBalance`/`secondTokenBalance` (persisted as signed `long`s in the `Exchange` protobuf) go negative, every subsequent `ExchangeInjectActuator`/`ExchangeWithdrawActuator`/`ExchangeTransactionActuator` operation on that exchange divides by/multiplies these corrupted values via `BigInteger`/`BigDecimal` arithmetic: [5](#0-4) 

which yields further incorrect (potentially negative or wildly wrong) `anotherTokenQuant` values, permanently corrupting the Exchange's accounting and either freezing legitimate trading (transactions start reverting due to arithmetic/precision failures) or letting an attacker extract more assets than they should from the pool/account balances.

### Impact Explanation
This can permanently corrupt the on-chain state of a TRX/TRC10 `Exchange`, an object that intermediates real TRX and TRC10 token balances held by user accounts. A corrupted (negative) pool balance breaks the AMM pricing invariant, which can be leveraged to withdraw/inject/trade assets at incorrect ratios, resulting in unbacked balances or draining of the pool's real TRX/TRC10 backing — a concrete theft/permanent-corruption-of-accounting impact, consistent with the "Medium/High/Critical" and "unbacked balance" criteria in scope.

### Likelihood Explanation
Reaching this requires the `allowHardenExchangeCalculation` committee proposal to not (yet) be enabled — i.e., the legacy calculation path is in effect — and an attacker able to construct a sequence of `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions (an ordinary transaction broadcaster and TRC10 asset holder) that drives one side of the pool toward zero and then executes a trade whose computed `buyTokenQuant` exceeds the remaining opposite-side balance. This is a purely single-transaction/single-account attack surface (no privileged role required), matching the "order placer" class explicitly listed in scope. I could not fully verify within the available tooling whether `ExchangeProcessor.exchange()` (the Bancor-formula computation) independently bounds `buyTokenQuant` below the counter-balance in all cases, which is the remaining precondition to trigger the negative-balance state; this would need to be confirmed/exploited with a concrete PoC before treating it as fully proven.

### Recommendation
Make the negative-balance invariant check unconditional in `ExchangeCapsule.transaction()` regardless of `hardenedCalc`, so both the legacy and hardened arithmetic paths reject a resulting negative `firstTokenBalance`/`secondTokenBalance` before persisting state. Additionally, `ExchangeProcessor.exchange()` should itself validate that the computed `buyTokenQuant` cannot exceed the available counter-token balance, independent of the feature-flag-gated hardened path.

### Proof of Concept
Not independently constructed/verified — this requires exercising `ExchangeCapsule.transaction()` through `ExchangeTransactionActuator` with `allowHardenExchangeCalculation` disabled, against a pool sized so that the Bancor-formula `buyTokenQuant` exceeds the remaining counter-balance, and confirming the resulting `Exchange` capsule persists a negative balance. This should be validated with a Devin session that can run the existing `ExchangeCapsuleTest`/`ExchangeTransactionActuatorTest` test harnesses (e.g., extending `testTransactionLegacyVsHardenedProcessorSelection` in `framework/src/test/java/org/tron/core/capsule/ExchangeCapsuleTest.java`) to concretely demonstrate a negative-balance result via the legacy path.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
