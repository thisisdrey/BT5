### Title
Unprivileged attacker can fill a victim's per-account token list via dust `DepositToken` transfers, permanently reverting all `addToDepositTokensOfAccount` paths for the victim and the `feeCollector` - (File: contracts/DepositToken.sol)

### Summary
`DepositToken._transfer` unconditionally registers the recipient in `Pool.depositTokensOfAccount` whenever their balance was zero, and `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the account's combined debt+deposit token count reaches `MAX_TOKENS_PER_USER` (30). Because msd tokens are freely transferable, any unprivileged EOA can dust-transfer one wei of every deposit token to a chosen victim (or to the `feeCollector`), stuffing the target's enumerable set to the cap. Afterwards, every code path that would add a *new* deposit token to that account reverts — deposits on their behalf, incoming transfers, `seize` proceeds routed to them, and SmartFarmingManager leverage deposits — an on-chain analog of CVE-2017-2596's "mishandled references → resource exhaustion" DoS.

### Finding Description
- `Pool.MAX_TOKENS_PER_USER = 30` and `onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30` [1](#0-0) [2](#0-1) 
- `addToDepositTokensOfAccount` can only be called by a registered `DepositToken` (`_revertIfSenderIsNotDepositToken`), but the token calls it for the *recipient* of any balance-0 → >0 change [3](#0-2) [4](#0-3) 
- `_transfer` is reachable permissionlessly via `transfer`/`transferFrom` (only gated by the sender's own unlocked balance, not the recipient's list) [5](#0-4) [6](#0-5) 
- The same registration happens in `_mint`, so `deposit(amount_, onBehalfOf_)`, fee mints to `feeCollector`, and `SmartFarmingManager` deposit flows all hit the same revert [7](#0-6) 
- `_withdraw` first does `_transfer(account_, feeCollector_, _fee)` — if the attacker also stuffs the `feeCollector`'s list, *all* fee-bearing withdrawals and deposits protocol-wide revert [8](#0-7) 
- There is no way for the victim to remove an entry other than zeroing that token's balance, and the dust balances are owned by the attacker-initiated accounting, so the victim cannot clear slots unilaterally (only by transferring the dust away, which requires the recipient list slot to still accept new tokens only for *new* tokens — the victim can shed each dust token but must pay gas per token and the attacker can re-stuff).

### Impact Explanation
Broken invariant: liveness / temporary freezing of funds. Concrete harms, all triggered by the victim-side revert in `addToDepositTokensOfAccount`:

1. A victim whose list is stuffed to 30 cannot deposit *any* collateral type they don't already hold (`deposit` → `_mint` → revert), cannot receive msd-token transfers, and cannot receive seized collateral. If their position drifts toward liquidation and the only collateral they can source is a new type, rescue is impossible — forced liquidation.
2. `SmartFarmingManager.leverage` deposits on behalf of the user; stuffed users cannot open new leveraged positions in unused collaterals.
3. Stuffing the `feeCollector` account (which receives fee mints/transfers on every fee-bearing `deposit`/`withdraw`) makes `withdraw`, `deposit`, and `seize` fee flows revert protocol-wide whenever `depositFee`/`withdrawFee` > 0 — a temporary freeze of all user collateral until governance drains a slot.

Attack cost is ~30 dust transfers plus acquiring a wei of each deposit token; no privileged role, no oracle manipulation, no governance needed.

### Likelihood Explanation
Feasibility requires the pool to list enough deposit/debt tokens for the attacker to push the target's combined count to 30 (or for the target to already hold most of them — the `feeCollector` naturally accumulates many tokens from fees, so it is the easiest target). `DebtToken` is non-transferable (`TransferNotSupported`), so only deposit tokens can be pushed; on pools with few collateral listings the victim-variant needs the victim to already occupy most slots, while the `feeCollector` variant remains reachable once it has collected fees across many tokens. Reproducible on a Hardhat/Foundry fork: deploy/attach to a deployed `Pool` + `DepositToken` set, execute `depositToken.transfer(victim, 1)` for each listed token until `getDepositTokensOfAccount(victim).length` reaches the cap, then observe `deposit`/`transfer`/`seize` reverts with `UserReachedMaxTokens`.

### Recommendation
Do not register recipients in `depositTokensOfAccount` on plain `transfer`/`transferFrom`, or make `addToDepositTokensOfAccount` fail-open (emit and skip) instead of reverting when the cap is hit — account-set membership is best-effort bookkeeping for health computation only when the token is actually used as collateral; alternatively, track "locked/collateral-relevant" tokens separately from merely-held tokens, and exempt protocol addresses such as `feeCollector` from the per-account cap.

### Proof of Concept
```solidity
// Hardhat/Foundry fork test sketch
// Precondition: pool lists deposit tokens d1..dN and victim's combined
// debtTokensOfAccount + depositTokensOfAccount can be brought to 30.

for (uint i; i < depositTokens.length; ++i) {
    IDepositToken dt = depositTokens[i];
    // attacker acquires 1 wei of dt (deposit underlying or transfer)
    dt.transfer(victim, 1); // triggers _transfer -> pool.addToDepositTokensOfAccount(victim)
}
assertEq(
    pool.debtTokensOfAccountLen(victim) + pool.depositTokensOfAccountLen(victim),
    pool.MAX_TOKENS_PER_USER()
);

// Victim can no longer deposit a new collateral type:
vm.prank(victim);
newDepositToken.deposit(amount, victim); // reverts: UserReachedMaxTokens

// And no one can send victim a new msd token:
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
otherDepositToken.transfer(victim, 1);

// feeCollector variant: stuff feeCollector the same way, then with
// withdrawFee > 0 every withdraw reverts inside _withdraw -> _transfer(fee)
vm.prank(anyUser);
depositToken.withdraw(amount, anyUser); // reverts: UserReachedMaxTokens
```

        uint256 amount_
    ) private updateRewardsBeforeTransfer(sender_, recipient_) {
        if (sender_ == address(0)) revert TransferFromTheZeroAddress();
        if (recipient_ == address(0)) revert TransferToTheZeroAddress();

        uint256 _senderBalanceBefore = balanceOf[sender_];
        if (_senderBalanceBefore < amount_) revert TransferAmountExceedsBalance();
        uint256 _recipientBalanceBefore = balanceOf[recipient_];

        unchecked {
            balanceOf[sender_] = _senderBalanceBefore - amount_;
            balanceOf[recipient_] += amount_;
        }

        emit Transfer(sender_, recipient_, amount_);

        // Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
        if (_recipientBalanceBefore == 0 && amount_ > 0) {
            pool.addToDepositTokensOfAccount(recipient_);
        }

        // Remove this token from the deposit tokens list if the sender's balance goes to zero
        if (amount_ > 0 && balanceOf[sender_] == 0) {
            pool.removeFromDepositTokensOfAccount(sender_);
        }
