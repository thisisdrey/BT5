### Title
`LiquidityWithdrawalFee` rounds down to zero for small LP burns, letting attackers repeatedly remove liquidity fee-free - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion`'s `do_remove_liquidity` computes the withdrawal fee with a plain `PerThing * Balance` multiplication and then subtracts it from the burned LP amount to get the redeemable amount. Like the Yieldy `instantUnstake` bug, this multiplication rounds down, so for small enough LP-token burns the fee rounds to zero. Splitting a large withdrawal into many small ones lets an attacker redeem liquidity while completely bypassing the withdrawal fee, extracting pool value at the expense of remaining liquidity providers.

### Finding Description
In `do_remove_liquidity`: [1](#0-0) 

```rust
let total_supply = T::PoolAssets::total_issuance(pool.lp_token.clone());
let withdrawal_fee_amount = T::LiquidityWithdrawalFee::get() * lp_token_burn;
let lp_redeem_amount = lp_token_burn.saturating_sub(withdrawal_fee_amount);
```

`T::LiquidityWithdrawalFee::get() * lp_token_burn` is a `PerThing` (e.g. `Permill`/`Perbill`) multiplied by an integer. This multiplication is documented and implemented as rounding *down*: [2](#0-1) . For any `lp_token_burn` small enough that `fee_rate * lp_token_burn < 1` (in the LP token's smallest unit), `withdrawal_fee_amount` rounds to `0`, so `lp_redeem_amount == lp_token_burn` — the caller pays no fee at all for that call.

The remaining logic then computes the returned underlying assets directly from the un-discounted `lp_redeem_amount`: [3](#0-2) 

and burns the full `lp_token_burn` from the user while transferring out assets proportional to the fee-free `lp_redeem_amount`: [4](#0-3) 

Nothing in `do_remove_liquidity` enforces a minimum `lp_token_burn` relative to the configured fee rate — the only floor checks are on the resulting `amount1`/`amount2` (`AssetOneWithdrawalDidNotMeetMinimum`), which do not prevent a fee-free small burn as long as pool reserves are large enough that even a tiny LP-token amount converts to a non-zero (even if dust) amount of each underlying asset: [5](#0-4) 

By repeating many such fee-free withdrawals (each below the rounding threshold `lp_token_burn < 1 / fee_rate` in raw units), an attacker can unwind an arbitrarily large LP position while paying zero cumulative withdrawal fee — exactly the "loop small amounts to dodge the fee" pattern from the external report.

### Impact Explanation
The withdrawal fee is burned from the LP token supply without a corresponding asset withdrawal, which is the mechanism by which remaining liquidity providers' share of the pool appreciates. Bypassing it via chunked withdrawals lets an attacker extract underlying pool assets (asset1/asset2) at the full, undiscounted exchange rate every time, denying the pool (and thus all other LPs) the fee revenue they are entitled to. This is a value-conservation break in `pallet-asset-conversion`'s public `remove_liquidity` extrinsic: fee state does not settle correctly for the rightful beneficiaries (the remaining LP-token holders), and it is reachable by any unprivileged signed account with no reliance on a malicious relayer, validator, or admin.

### Likelihood Explanation
The impact is real but bounded per call: only extremely small LP-token burns (below the `fee_rate` rounding threshold) get the fee waived, so exploitation requires many transactions (bounded by `MintMinLiquidity`/pool decimals and the attacker's gas/fee budget), similar to the original report's note that this is "not feasible on mainnet" at scale but "likely feasible on low-cost L2s / for tokens with small decimal precision." Parachains using `pallet-asset-conversion` with LP tokens of low decimal precision, or configured with a low `LiquidityWithdrawalFee`, make the rounding-down threshold reachable with meaningfully sized chunks, increasing practical exploitability.

### Recommendation
Round the fee up instead of the redeemable amount down, e.g. compute `lp_redeem_amount` directly via `Percent/Permill::left_from_one().mul_floor(lp_token_burn)` (rounding the *redeemed* amount down) or use a ceiling-rounded fee (`fee_rate.mul_ceil(lp_token_burn)`), matching the pattern already used in `pallet-psm` (`Permill::mul_ceil`) referenced elsewhere in this repo: [6](#0-5) . This guarantees the fee is never silently zero unless the configured rate itself is zero.

### Proof of Concept
1. Configure a pool with `LiquidityWithdrawalFee = Permill::from_parts(3000)` (0.3%) and large reserves.
2. An LP holds `N` LP tokens they wish to withdraw fee-free.
3. Call `remove_liquidity` repeatedly with `lp_token_burn = k` where `k < 1_000_000 / 3000 ≈ 333` (so `Permill * k` rounds to `0`), each time receiving `amount1`/`amount2` computed from the full `k` (no fee deducted), until the desired total is unwound.
4. Across all calls, total fee paid is `0`, whereas withdrawing the same total in one call would have paid `LiquidityWithdrawalFee * N`.
