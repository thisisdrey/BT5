Based on my investigation, I found a strong analog: `handleRecvError` in `outside.go`.

## Analysis

The ERC721 bug's core pattern is: **a resource/state transition intended to be authorized only by a specific, cert-verified party can instead be triggered by an unauthorized actor who never proved ownership**. In Nebula's threat model (attacker holds no CA-signed certificate), the closest reachable analog is `RecvError` handling: it is processed *before* any decryption or certificate check — directly off the raw UDP header — yet it tears down an authenticated tunnel belonging to two legitimate, cert-verified peers.

Looking at `outside.go:76-84`, `header.RecvError` is dispatched straight to `f.handleRecvError(via.UdpAddr, h)` prior to any `Decrypt`/session-key check (unlike `Message`, `Test`, etc. which require the data-plane AEAD key). The only verification performed in `handleRecvError` (`outside.go:541-575`) is that the source `netip.AddrPort` (`addr`) equals the `HostInfo`'s currently recorded remote (`hr`). Since UDP source addresses are trivially spoofable and NAT/roaming legitimately changes this value, an attacker with **no certificate at all** can forge a `RecvError` packet (guessing/observing `h.RemoteIndex`, a 32-bit value sent in the clear on every packet) from the victim's current or a not-yet-confirmed remote address and force `f.closeTunnel(hostinfo)` — destroying a session state object that is supposed to be exclusively controlled by the two mutually-authenticated endpoints. This is a remote, unauthenticated state-poisoning/denial primitive analogous to an unauthorized party manipulating a resource meant only for the verified counterparty. [1](#0-0) [2](#0-1) 

### Title
Unauthenticated RecvError packets allow spoofing-based teardown of authenticated tunnels - (File: outside.go)

### Summary
Nebula's `RecvError` control message is processed prior to certificate/session validation, and the corresponding handler only checks that the sender's `netip.AddrPort` matches the `HostInfo`'s currently cached remote endpoint before tearing down the tunnel — a check trivially bypassed via UDP source spoofing by an attacker who possesses no CA-signed certificate at all.

### Finding Description
In `readOutsidePackets` (`outside.go:76-84`), `header.RecvError` is dispatched to `f.handleRecvError` immediately after header parsing, with no decryption, no session-key verification, and no certificate check — this is one of only two message types (along with `Handshake`) processed entirely pre-authentication. [3](#0-2) 

`handleRecvError` (`outside.go:541-575`) looks up the target `HostInfo` purely from the 32-bit `h.RemoteIndex` field (sent unencrypted on every packet, and thus observable/guessable by any network-position attacker), then performs only an address-equality check against `hostinfo.GetRemote()` before calling `f.closeTunnel(hostinfo)`: [4](#0-3) 

Because the check is against an IP:port 4-tuple — not against any cryptographic material — an attacker with no valid certificate, who can either spoof UDP source addresses or who observes the real remote address in transit (e.g., via a shared network segment or off-path spoofing), can forge a `RecvError` packet naming a victim's `RemoteIndex` and cause the recipient to tear down and remove state for a tunnel it does not own or control, exactly as the ERC721 bug let an unauthorized party act on a resource meant only for an authorized owner.

### Impact Explanation
This allows an unauthenticated remote attacker to force termination of arbitrary active/pending Nebula tunnels between two legitimate, CA-verified peers by spoofing a single unencrypted UDP packet, without ever presenting a valid certificate. This is a remote state-poisoning/denial-of-service primitive against the overlay network, degrading availability and potentially amplifying re-handshake churn.

### Likelihood Explanation
Exploitation requires only knowledge of a live `RemoteIndex` (transmitted in cleartext on every packet observable on-path, or brute-forceable given it's a 32-bit space) and the ability to send a spoofed UDP packet appearing to originate from the victim's current remote address — a low bar for an on-path or off-path spoofing-capable attacker, consistent with the existing project note that "Valid recv_error packets were incorrectly marked as spoofing" (CHANGELOG #482), showing this exact check has historically been fragile. [5](#0-4) 

### Recommendation
Do not act on `RecvError` (or any pre-authentication control message) based solely on UDP source-address matching. Require some proof tied to the session (e.g., binding to a value derived from session key material, or requiring `RecvError` to only be trusted from an address that has completed at least one authenticated round trip within a bounded recent window) before tearing down `HostInfo` state, and rate-limit/log repeated mismatches per index to detect spoofing attempts.

### Proof of Concept
1. Establish a legitimate Nebula tunnel between `A` and `B`; note `A`'s `RemoteIndex` as seen by `B` (observable in cleartext header of every packet from `A`).
2. As attacker `E` (holding no CA-signed certificate), craft a UDP packet to `B` with `header.Type = RecvError`, `RemoteIndex` set to the value from step 1, and source address spoofed to match `A`'s currently known remote `UdpAddr`.
3. Send the packet to `B`.
4. `B.handleRecvError` finds the matching `HostInfo` by `RemoteIndex`, sees the (spoofed) source address matches `hostinfo.GetRemote()`, and calls `f.closeTunnel(hostinfo)`, tearing down the tunnel `A` and `B` share — despite `E` never having authenticated with the network.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
