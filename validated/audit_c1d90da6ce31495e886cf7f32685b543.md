Based on my investigation, I found a structurally analogous bug: a validation check that exists in one asset-transfer actuator but is missing from a nearly-identical sibling actuator, allowing the check to be bypassed simply by using the other contract type.

### Title
Missing `AllowTvmCompatibleEvm` version-1 smart-contract guard in `TransferAssetActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`)

### Summary
`TransferActuator.validate()` (native TRX transfers) enforces a guard that blocks direct actuator-level transfers of value to smart contracts whose `contractVersion() == 1` when the `AllowTvmCompatibleEvm` proposal is active, forcing such transfers to go through `TriggerSmartContract` (i.e., through the VM) instead of bypassing contract logic via a plain `TransferContract`. `TransferAssetActuator.validate()`, which performs the equivalent operation for TRC10 tokens, only re-implements the sibling `ForbidTransferToContract` check but omits the `AllowTvmCompatibleEvm`/version-1 guard entirely.

### Finding Description
In `TransferActuator.validate()`: [1](#0-0) 
the code explicitly blocks sending TRX directly (outside the VM) to a contract with `contractVersion() == 1` once `AllowTvmCompatibleEvm` is enabled.

In `TransferAssetActuator.validate()`, the analogous logic only reproduces the `ForbidTransferToContract` check: [2](#0-1) 
but there is no equivalent `AllowTvmCompatibleEvm`/`contractVersion() == 1` check. This mirrors the reported pattern exactly: a validation added to one transfer path (`createStream`/`TransferActuator`) is missing from a sibling transfer path that performs the same kind of operation over a different asset type (`createBatchStream`/`TransferAssetActuator`), letting an unprivileged caller route around the restriction by choosing the sibling contract type (`TransferAssetContract` instead of `TransferContract`).

### Impact Explanation
Any account holding a TRC10 token can call `TransferAssetContract` to push token balance directly into a version-1, EVM-compatible smart contract's asset ledger, bypassing the protection the protocol designers put in place specifically to prevent out-of-band value/asset injection into such contracts outside of `TriggerSmartContract`/VM execution. Depending on what invariants version-1 contracts rely on regarding externally-received assets, this could desynchronize the contract's internally tracked state from its actual on-chain TRC10 balance — a variant of the "unbacked balance" class of issues.

### Likelihood Explanation
Low complexity, reachable by any unprivileged account that owns any TRC10 asset and knows the address of a version-1 EVM-compatible contract; no special privileges are required, and the bypass requires only selecting `TransferAssetContract` instead of `TransferContract`.

### Recommendation
Add the same `AllowTvmCompatibleEvm` / `contractVersion() == 1` guard used in `TransferActuator.validate()` to `TransferAssetActuator.validate()`, so that TRC10 transfers to version-1 smart contracts are likewise rejected unless routed through `TriggerSmartContract`.

### Proof of Concept
1. Deploy (or identify) a smart contract whose `ContractCapsule.getContractVersion() == 1` while the `AllowTvmCompatibleEvm` proposal is active.
2. Attempt to send TRX to that contract via a `TransferContract` — observe it is rejected with "Cannot transfer TRX to a smartContract which version is one."
3. Send a TRC10 asset to the same contract address via a `TransferAssetContract` — observe the transfer succeeds (only the generic `ForbidTransferToContract` check applies, and only if that separate flag is also enabled), demonstrating the missing analogous restriction.

**Caveat:** I was not able to fully determine, from the indexed code alone, the exact downstream contract-accounting invariant that the `AllowTvmCompatibleEvm` version-1 guard protects (i.e., what internal EVM/TVM assumption breaks if assets arrive outside a VM call). Confirming severity (Medium vs. High) would require reviewing how `contractVersion() == 1` contracts consume/track TRC10 balances in the VM layer (`actuator/src/main/java/org/tron/core/vm/`), which may not be fully covered by the current index; a full Devin session could pull the complete VM/version-1 handling code to verify the concrete exploit impact.
