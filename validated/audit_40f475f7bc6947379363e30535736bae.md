### Title
Per-repository concurrency limiter is keyed by relative path, allowing an unprivileged user to bypass repo-level backpressure limits by spreading load across forks that share the same object pool - ([File: internal/grpc/middleware/limithandler/middleware.go])

### Summary
The Sherlock finding describes `MainVault.deposit()` enforcing a per-account cap (`maxTrainingDeposit`) using a check keyed to `msg.sender`'s balance, which is bypassable because the user can move the underlying value to a different account (a fresh key with `balance == 0`) and re-issue the same operation. The same "limit-keyed-to-a-shiftable-identity" bug class is reachable in Gitaly's concurrency-limiting middleware, which enforces `max_per_repo` backpressure keyed only on a repository's own relative path, while the actual expensive/shared resource (the on-disk object pool) can be accessed through many different relative-path "identities" (forks) that an ordinary user can create.

### Finding Description
Gitaly's per-RPC backpressure mechanism computes its limiting key purely from the repository's relative path: [1](#0-0) 

This key is used to build a `ConcurrencyLimiter` whose `limitsByKey` map lazily creates one independent semaphore per key (i.e., one independent quota per repository path): [2](#0-1) 

Administrators use this to bound concurrent heavy work per repository, e.g. `PostUploadPackWithSidechannel` or `OptimizeRepository` with `max_per_repo = 1`: [3](#0-2) 

The limiter is wired up with `LimitConcurrencyByRepo` as the key function server-wide: [4](#0-3) 

However, Gitaly's object-pool feature intentionally allows many distinct repositories (forks) to share the same underlying, expensive on-disk objects via `objects/info/alternates`, specifically to deduplicate storage and avoid repacking each fork's objects independently: [5](#0-4) 

An ordinary user who can fork a repository (`CreateFork`) and link the fork to (or share) the same object pool controls an arbitrary number of distinct relative-path "identities" that all read/write against the same shared pool objects on disk: [6](#0-5) 

Because `LimitConcurrencyByRepo` derives the limiting key solely from the fork's own relative path, and each key gets a brand-new, independent concurrency/queue quota (analogous to the drained account starting at `balance == 0`), the operator's intended per-repository cap on concurrent expensive Git operations (e.g., pack-objects generation, repacking) that hit the shared pool is not actually a limit on load against the shared resource — it's a limit per fork. A user can therefore multiply the effective concurrency against the same underlying object-pool storage simply by spreading identical/equivalent requests (clone/fetch/optimize) across N forks instead of one repository, exactly as the report's actor bypassed `maxTrainingDeposit` by spreading balance across a second account before hitting the check again.

### Impact Explanation
This allows an authenticated, unprivileged user (anyone who can create forks of a repository they have read access to) to bypass administrator-configured per-repository backpressure (`max_per_repo`/`max_queue_size`) that is meant to protect the shared storage/CPU resource backing an object pool. By fanning out identical expensive requests (e.g., triggering `git-pack-objects` reads through the shared alternates, or repository housekeeping/optimize calls) across many forks concurrently, the aggregate concurrent load against the single physical pool can exceed what the configured limiter was designed to permit, defeating the resource-exhaustion protection (DoS of a handler / of the node) that `[[concurrency]]` limits are documented to provide.

### Likelihood Explanation
Likelihood is moderate-to-high in environments that use per-repository forking (e.g., GitLab merge-request workflows) combined with `[[concurrency]]` limits configured for fork-heavy RPCs such as `PostUploadPackWithSidechannel` or `OptimizeRepository`. Creating forks is a normal, unprivileged user action, and object pools are automatically used for forks, so no special access or malicious peer/node behavior is required — only the ability to fork a repository multiple times and issue concurrent requests against each fork.

### Recommendation
When computing the concurrency-limiting key for RPCs, resolve the repository to its underlying object-pool identity where one exists (e.g., via the same lookup used to detect the `info/alternates` link when assigning partitions, as described in `doc/transactions.md`), so that all pool members share a single limiting key when the RPC's actual cost is dominated by pool-backed operations. Alternatively/additionally, apply a limiter keyed on the object pool's relative path (or partition ID) in parallel to the per-repository key, so the aggregate load against the shared physical resource is bounded regardless of how many fork identities a user distributes requests across.

### Proof of Concept
1. As an unprivileged user, fork a large repository N times (`CreateFork`), each fork automatically becoming/joining the same object pool as documented in `doc/object_pools.md`.
2. Configure (or assume already configured) `[[concurrency]] rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel" max_per_repo = 1` intended to bound concurrent clones/fetches hitting the shared pool's packfiles.
3. Issue N concurrent clone/fetch requests, one against each of the N distinct fork relative paths, instead of N concurrent requests against the single origin repository.
4. Because `LimitConcurrencyByRepo` (`internal/grpc/middleware/limithandler/middleware.go:18-25`) keys the limiter per fork's relative path, each of the N requests gets its own fresh concurrency slot (`internal/limiter/concurrency_limiter.go:243-270`) and all N execute concurrently against the same shared object-pool storage, exceeding the intended `max_per_repo = 1` cap on load against that pool.

// LimitConcurrencyByRepo implements GetLockKey by using the repository path as lock.
func LimitConcurrencyByRepo(ctx context.Context) string {
	if info := requestinfohandler.Extract(ctx); info != nil {
		return info.Repository.GetRelativePath()
	}

	return ""
}

// getConcurrencyLimit retrieves the concurrency limit for the given key. If no such limiter exists
// it will be lazily constructed.
func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}

Limit the number of concurrent RPCs that are in flight on each Gitaly node for each

```markdown
# Object Pools

When creating forks of a repository, most of the objects for forked repository
and the repository it forked from are shared. Storing those shared objects
multiple times is a waste of disk space and also of CPU time, given that those
shared objects would have to be repacked for both repositories. To fix this
waste of resources, we use object pools, which are essentially a repository
which holds the shared objects of both repositories.

The sharing of objects for a given repository and its object pool is done via
alternate object directories which Gitaly sets up when linking a repository to
an object pool by writing the `objects/info/alternates` file.
```
