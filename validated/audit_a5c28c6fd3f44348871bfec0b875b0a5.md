### Title
Hardcoded Pyth/DIA oracle contract addresses in `market.clar` will break price resolution and freeze borrow/collateral operations if the external oracle contracts are upgraded - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`v0-4-market.clar` hardcodes the addresses of the external Pyth and DIA oracle contracts as literal `principal` values directly inside the oracle resolution functions, with no DAO-controlled setter to update them. This is the same bug class as the reported Element/APWine finding: an unprivileged-reachable, business-critical external integration point whose address is fixed at deploy time, so if the third-party protocol upgrades and redeploys under a new contract address, every function that depends on price resolution breaks.

### Finding Description
Price resolution in `market.clar` is implemented via `call-pyth` and `call-dia`, both of which call fixed, literal principal addresses of the Pyth storage contract and the DIA oracle contract: [1](#0-0) 

```clarity
(define-private (call-pyth (ident (buff 32)))
  (let ((res (unwrap! (contract-call? 'SP1CGXWEAMG6P6FT04W66NVGJ7PQWMDAC19R7PJ0Y.pyth-storage-v4 get-price ident) ERR-ORACLE-PYTH)))
    (ok res)))
...
(define-private (call-dia (key (string-ascii 32)))
  (let ((res (unwrap! (contract-call? 'SP1G48FZ4Y7JY8G2Z0N51QTCYGBQ6F4J43J77BQC0.dia-oracle get-value key) ERR-ORACLE-DIA)))
    (ok res)))
```

These are invoked from `resolve-pyth` / `resolve-dia`, which feed `resolve-price-feed`, the core routine used throughout `market.clar` to price collateral and debt for borrow validation, health checks, and liquidation: [2](#0-1) 

The same problem exists for the price-feed update path, where `write-feed` hardcodes the addresses of `pyth-oracle-v4`, `pyth-storage-v4`, `pyth-pnau-decoder-v3`, and `wormhole-core-v4`: [3](#0-2) 

The version suffixes (`-v4`, `-v3`, etc.) and the repository's own deployment history (multiple sequential Pyth/Wormhole upgrade plans moving from `-v1` through `-v4`, each redeployed under a *new contract address*) confirm that Pyth/Wormhole/DIA upgrades in practice change the deployed contract's principal, exactly the scenario the referenced report warns about for Element/APWine.

Unlike `assets.clar`, which stores *asset* oracle configuration (feed id/type/callcode) in an updatable map behind `update`/DAO-auth, none of these constants for the oracle infrastructure contracts themselves are stored in a map or var — they are compiled into the contract body. There is no `set-pyth-storage`/`set-dia-oracle`/`set-wormhole-core` function in `market.clar`.

### Impact Explanation
If Pyth or DIA redeploys their oracle/storage contracts under a new principal (which has already happened multiple times per the project's own upgrade history), every call to `call-pyth`/`call-dia` will fail (calling a nonexistent or stale contract), causing `resolve-price-feed` to error out. Since price resolution is required by borrow, health-check, and liquidation logic, this would cause temporary freezing of user funds: users would be unable to borrow against, or safely withdraw/liquidate positions that require a fresh price check, until the entire `market.clar` contract is redeployed and all state/authorizations are re-migrated to the new version. This matches the in-scope "temporary freezing of funds" impact class.

### Likelihood Explanation
Likelihood is driven entirely by third-party upgrade cadence of Pyth/Wormhole/DIA infrastructure, which the project's own deployment history in this repo shows occurs periodically (pyth-oracle v1→v4, wormhole-core v1→v4). This is not attacker-triggered, but it is a real, recurring operational risk baked into the contract as written, with no update mechanism analogous to what `assets.clar` provides for asset-level oracle configuration.

### Recommendation
Store the Pyth storage/oracle/decoder and Wormhole-core contract principals (and the DIA oracle principal) in DAO-updatable data-vars or a small registry map inside `market.clar`, guarded by the same `check-dao-auth` pattern already used in `assets.clar`'s `update` function, instead of hardcoding them as literal principals in `call-pyth`/`call-dia`/`write-feed`. This allows the DAO to repoint the market at new oracle contract deployments without redeploying `market.clar` and losing/needing to migrate all vault/position state.

### Proof of Concept
Not applicable as an exploit PoC (this is an external-dependency-upgrade class issue, not an attacker-triggered exploit). The root cause is demonstrable purely from the source: `call-pyth`/`call-dia` embed literal `'SP1CGXWEAMG6P6FT04W66NVGJ7PQWMDAC19R7PJ0Y.pyth-storage-v4` and `'SP1G48FZ4Y7JY8G2Z0N51QTCYGBQ6F4J43J77BQC0.dia-oracle` with no setter, and the repository's own `local-testing/contracts/pyth/deployments/v1/*.yaml` files show the Pyth/Wormhole stack has already been redeployed under new addresses/versions multiple times (v1 → v4), confirming this occurs in practice for this exact dependency.

(define-private (resolve-pyth (ident (buff 32)))
  (let ((response (try! (call-pyth ident)))
        (price (get price response))
        (expo (get expo response))
        (conf (get conf response))
        (final-price (normalize-pyth price expo))
        (timestamp (get publish-time response)))
    (try! (check-confidence price conf))
    (ok { value: final-price, timestamp: timestamp })))

(define-private (resolve-dia (ident (buff 32)))
  (let ((key (unwrap-panic (from-consensus-buff? (string-ascii 32) ident)))
        (res (try! (call-dia key))))
    ;; DIA returns timestamp in milliseconds, convert to seconds for staleness check
    (ok { value: (get value res), timestamp: (/ (get timestamp res) u1000) })))

(define-private (resolve-price-feed (type (buff 1)) (ident (buff 32)))
