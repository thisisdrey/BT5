### Title
ML-DSA-65 inner-delegate signature verification compute is unmetered on the receiver shard - ([File: runtime/runtime/src/actions.rs])

### Summary
`apply_delegate_action` verifies the inner `DelegateAction` signature on the receiver shard via `signed_delegate_action.verify()` [3](#0-2) , but the compute cost of that verification is only added to `result.compute_usage` when `apply_state.config.wasm_config.fix_ml_dsa_cost_charging` is true [4](#0-3) . On the current stable protocol version (86), `fix_ml_dsa_cost_charging` is `false` [2](#0-1) , since `FixMlDsaCostCharging` only activates at nightly protocol version 153 [1](#0-0) . Instead, the ML-DSA-65 verification cost is charged as *gas* on the signer/relayer's shard at transaction conversion time via `signature_verification_cost` [5](#0-4) , a shard that never actually performs this verification.

### Finding Description
ML-DSA-65 signature verification is meaningfully slower than classical schemes (~80µs mean vs ~32µs for ed25519, per the project's own benchmarks) [6](#0-5) . The protocol pays for this by charging `ml_dsa_65_verification_cost` (100 Ggas) as burnt gas on the relayer's shard when the outer transaction (or a `Delegate` action's inner ML-DSA-65 signer) is converted to a receipt [7](#0-6) . For a `Delegate` action's *inner* signature, however, the actual `verify()` call happens later, inside `apply_delegate_action` on the *receiver* shard [8](#0-7) . The code comment itself documents the bug: "Without the fix the compute is instead mis-charged on the signer shard (which never runs this verify), letting the work escape the receiver shard's budget" [9](#0-8) . Since `fix_ml_dsa_cost_charging` is false at the currently active stable protocol version, this mis-charging is the live, un-fixed behavior: the receiver shard performs real CPU work (ML-DSA-65 verification) inside `apply_delegate_action` without that work counting against the receiver shard's `compute_limit`.

### Impact Explanation
An attacker (any ordinary account acting as sender of a meta-transaction, or a relayer colluding with itself) can construct many `Delegate` actions whose inner `public_key` is an ML-DSA-65 key, each targeting the same receiver shard. The relayer only pays the (signer-shard) gas surcharge once per transaction as normal transaction cost, but every such receipt forces the receiver shard to spend the extra ~50µs+ of CPU per verification without that cost being reflected in `result.compute_usage` on that shard. Compute costs (NEP-455) are meant to bound wall-clock chunk-application time independent of gas; escaping this budget on the receiver shard allows an attacker to inflate the receiver shard's actual chunk-application wall-clock time beyond what its `compute_limit` was designed to cap, which can degrade chunk production/application timing for that shard. This is a resource-exhaustion/DoS class bug analogous to the reported `EVM.Restore()` issue: expensive verification work is performed without being fully and correctly metered against the resource budget of the shard actually doing the work.

### Likelihood Explanation
Triggering this requires only sending ordinary, validly-signed meta-transactions (`DelegateAction`) whose inner signer uses an ML-DSA-65 key targeting a chosen receiver shard — this is a fully unprivileged, ordinary-client-reachable path (`SignedDelegateAction`/`VersionedSignedDelegateAction` construction and signing is public API) [10](#0-9) . No malicious node, network-layer, or block-production privilege is needed. The only precondition is that `PostQuantumSignatures`/ML-DSA-65 keys are enabled and `FixMlDsaCostCharging` is not yet active, which is exactly the state of the current stable protocol version (86) per this tree's version table.

### Recommendation
Charge the inner-delegate ML-DSA-65 verification compute cost against the receiver shard's budget unconditionally (i.e., make the `fix_ml_dsa_cost_charging`-gated accounting in `apply_delegate_action` always active, or accelerate stabilization of `FixMlDsaCostCharging` past protocol version 153 so it is active well before/at the point ML-DSA-65 keys are usable), rather than leaving a window where PQ signatures are accepted but their receiver-side verification compute is uncounted.

### Proof of Concept
1. Enable `PostQuantumSignatures` (active at PV 85) so ML-DSA-65 keys can be added and used, while running at a protocol version where `FixMlDsaCostCharging` (PV 153, nightly-only) is not enabled — i.e., the shipped stable configuration.
2. Add an ML-DSA-65 full-access key to an account `inner-pq`.
3. Have a relayer submit repeated meta-transactions containing a `Delegate` action whose `delegate_action.public_key` is the ML-DSA-65 key, all targeting accounts on the same receiver shard.
4. Observe (as the existing test `test_delegate_action_meters_inner_verify_compute` demonstrates for the `fix_enabled=true` vs `fix_enabled=false` cases) that with the fix disabled, `result.compute_usage` on the receiver-shard application of `apply_delegate_action` does **not** include the ~540 Ggas-equivalent verification compute [11](#0-10) , even though the receiver shard actually performs the `verify()` call and its associated CPU cost [3](#0-2) .

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }

///
/// The signer's own signature is verified here (at conversion, on the signer's
/// shard), so its full cost is charged here. Each inner delegate signature is
/// instead verified at execution on the receiver shard (`apply_delegate_action`):
/// with `meter_inner_verify_on_receiver` set, only its gas is charged here (the
/// signer still pays economically) and its compute is metered on that shard, so
/// the wall-clock budget is charged where the work actually happens. Without the
/// flag the legacy behavior is kept (compute mis-charged on the signer shard) to
/// preserve consensus.
fn signature_verification_cost(
    fees: &RuntimeFeesConfig,
    signer_public_key: &PublicKey,
    actions: &[Action],
    meter_inner_verify_on_receiver: bool,
) -> Result<ParameterCost, IntegerOverflowError> {
    let costs = &fees.signature_verification_costs;
    let mut total = costs[signature_kind(signer_public_key.key_type())];
    for action in actions {
        if let Some(delegate_action) = delegate_inner_action(action) {
            let kind = signature_kind(delegate_action.public_key().key_type());
            let mut cost = costs[kind];
            if meter_inner_verify_on_receiver {
                cost = ParameterCost { compute: 0, ..cost };
            }
            total = total.checked_add_result(cost)?;
        }
    }
    Ok(total)
}

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}
