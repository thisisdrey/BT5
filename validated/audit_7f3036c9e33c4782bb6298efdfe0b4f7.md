### Title
Unauthenticated UDP source spoofing can hijack a tunnel's active remote path via unchecked roaming - (File: outside.go)

### Summary
The bug class in the external report is "accepting a state change with no lower-bound / sanity check on the resulting outcome, letting a third party manipulate that outcome between commit and completion." The closest reachable analog in this codebase is `handleHostRoaming`, which lets any packet that merely *decrypts successfully* redirect (roam) an existing tunnel's trusted remote UDP address — with no verification that the new address is a legitimate continuation of the same network path, and no cryptographic binding between the encrypted payload and the outer UDP source address.

### Finding Description
When a data packet arrives, `readOutsidePackets` looks up the `HostInfo` by the (unauthenticated) `RemoteIndex` in the header, decrypts the AEAD payload, and — if decryption succeeds — immediately calls `f.handleHostRoaming(hostinfo, via)` before any further processing: [1](#0-0) 

`handleHostRoaming` then compares only the *previous* remote address against the incoming packet's source (`via.UdpAddr`). If they differ, and the remote-allow-list permits the new address, and it isn't within a short roam-suppression window, the hostmap unconditionally adopts the new source as the tunnel's active remote: [2](#0-1) 

The AEAD authentication (`ConnectionState.Decrypt`) validates the ciphertext and the Noise-derived session key/nonce, but it does not bind the outer IP/UDP source address into the authenticated data — the transport-layer source is not itself an authenticated field. This means the "proof" that gates the roaming decision is only "some previously-encrypted packet could be decrypted with this session's key," not "this specific network path is the legitimate, current path to the peer." An attacker who can capture (or is otherwise positioned to relay) even one valid encrypted packet from the legitimate peer can replay it from an address they control (source-spoofed UDP, or via an on-path/off-path relay) before that packet's counter is consumed by the real recipient, and the victim's `HostMap` will re-point its "trusted" remote at the attacker-chosen address — with no minimum requirement that the new path is at least as trustworthy/authenticated as the one being replaced.

This is directly analogous to the reported DeFi issue: just as `deposit()`/`withdraw()` accept whatever share price is present at execution time with no `minAmountOut` floor, `handleHostRoaming` accepts whatever source address is present at decrypt time with no check that the new address is bound to (or no worse than) the address the two parties originally established trust over.

### Impact Explanation
Successful exploitation redirects the active data path of an established tunnel toward an address of the attacker's choosing (remote/hostmap state poisoning). Depending on network position, this can be leveraged to intercept, delay, or blackhole subsequent traffic for that tunnel, since all future outbound packets from the victim interface will be sent to the roamed-to address until another legitimate roam or handshake corrects it. Impact is rated Medium: it requires the attacker to already possess or intercept at least one valid ciphertext from the ongoing session (it does not grant key material or certificate forgery), but it can hijack traffic delivery without needing a CA-signed identity.

### Likelihood Explanation
Likelihood is Medium: the attack does not require a valid CA-signed certificate, only the ability to capture/relay a single previously-sent encrypted packet and re-emit it from a different source address (classic UDP source-spoofing/on-path relay conditions, common in many real-world network positions such as shared local networks, NAT traversal edge cases, or malicious intermediate routers). I was not able to fully verify, with the tool calls available, whether the Noise-derived anti-replay/counter window (`connection_state.go`) would reject the replayed counter before `handleHostRoaming` is invoked in all cases — this needs confirmation by inspecting `ConnectionState.Decrypt`'s replay-window handling in detail, which I could not complete in this session.

### Recommendation
Require additional corroboration before trusting a roam target, analogous to adding a "minimum acceptable" bound in the DeFi fix:
- Do not roam solely on the basis of a successfully-decrypted data packet arriving from a new source. Require an explicit, freshly authenticated confirmation (e.g., a `Test`/`Ping` round-trip to the new address, or an updated lighthouse-learned remote) before promoting it to the primary remote.
- Bind the outer UDP source address into the AEAD associated data (or otherwise cryptographically tie packets to a specific network path) so a captured/replayed ciphertext cannot be revalidated from a different source address.
- Tighten `RoamingSuppressSeconds`/allow-list logic so that a single packet cannot instantly override a previously working, verified path without additional confirmation.

### Proof of Concept
1. Attacker passively captures one legitimate encrypted data packet `P` sent by peer `B` to peer `A` over their established Nebula tunnel (e.g., via a shared segment or a compromised intermediate hop).
2. Attacker resends `P` unmodified to `A`'s UDP listening port, but from a UDP source address/port the attacker controls (`evilAddr`), before `A` processes the original.
3. `A` receives the packet; `f.hostMap.QueryIndex` resolves the existing `HostInfo`; `hostinfo.ConnectionState.Decrypt` succeeds because the ciphertext, key, and counter are all valid and not yet consumed.
4. `handleHostRoaming` sees `curRemote != evilAddr`, passes the remote-allow-list check (if `evilAddr` is not filtered), and calls `hostinfo.SetRemote(evilAddr)` — as shown in [2](#0-1) .
5. `A`'s subsequent outbound traffic for that tunnel is now sent to `evilAddr` instead of `B`'s legitimate address, with no check that this new destination is equivalent to or better than the previous trusted path — mirroring the missing `minAmountOut` floor in the referenced DeFi report.

func (f *Interface) handleHostRoaming(hostinfo *HostInfo, via ViaSender) {
	curRemote := hostinfo.GetRemote()
	if !via.IsRelayed && curRemote != via.UdpAddr {
		if !f.lightHouse.GetRemoteAllowList().AllowAll(hostinfo.vpnAddrs, via.UdpAddr.Addr()) {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				hostinfo.logger(f.l).Debug("lighthouse.remote_allow_list denied roaming", "newAddr", via.UdpAddr)
			}
			return
		}

		if !hostinfo.lastRoam.IsZero() && via.UdpAddr == hostinfo.lastRoamRemote && time.Since(hostinfo.lastRoam) < RoamingSuppressSeconds*time.Second {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				hostinfo.logger(f.l).Debug("Suppressing roam back to previous remote",
					"suppressSeconds", RoamingSuppressSeconds,
					"udpAddr", curRemote,
					"newAddr", via.UdpAddr,
				)
			}
			return
		}

		hostinfo.logger(f.l).Info("Host roamed to new udp ip/port.",
			"udpAddr", curRemote,
			"newAddr", via.UdpAddr,
		)
		hostinfo.lastRoam = time.Now()
		hostinfo.lastRoamRemote = curRemote
		hostinfo.SetRemote(via.UdpAddr)
	}
