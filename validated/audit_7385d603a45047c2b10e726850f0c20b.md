### Title
Permanently stuck XCM query state on unmatched/late response leaves any pallet-gated logic (fund locks, notify callbacks) undrainable - ([File: polkadot/xcm/pallet-xcm/src/lib.rs])

### Summary
`pallet-xcm`'s `QueryHandler`/`OnResponse` implementation registers a `QueryStatus::Pending { responder, maybe_match_querier, maybe_notify, timeout }` entry in `Queries` storage whenever a query is created via `do_new_query`/`new_notify_query`/`report_outcome`/`report_outcome_notify`. The `timeout` field is stored but is never read or enforced anywhere in the pallet: there is no dispatchable, hook, or `on_initialize` logic that expires a `Pending` query, removes it, or notifies dependents once `timeout` has passed. If the remote responder never sends a matching `QueryResponse` (wrong `querier`, wrong `responder` origin, dropped/misrouted XCM, or simply no response), the query remains `Pending` in storage forever with no permissionless way to close it out. [1](#0-0) [2](#0-1) 

### Finding Description
This is the structural analog of the Etherfi bug: a request (the `WithdrawRequestNFT`) is created, is expected to be resolved by an external counterparty, and if that counterparty never resolves it as expected, the dependent protocol has no fallback to unwind or force-settle the pending obligation. Here, the "request" is the XCM `Pending` query, and the "external counterparty" is the destination chain that is expected to send back a `QueryResponse` matching `responder` and `maybe_match_querier` exactly.

`on_response` (the `OnResponse::on_response` implementation) only transitions `Pending -> Ready` (or dispatches `maybe_notify`) when the incoming response's `origin` exactly equals the stored `responder`, and, if set, the `querier` exactly equals `maybe_match_querier`. Any mismatch (`InvalidResponder`, `InvalidQuerier`, `InvalidResponderVersion`, `InvalidQuerierVersion`) leaves the query in `Pending` state untouched, explicitly noted in the event docs: "The query remains registered for a later, valid, response to be received." [3](#0-2) [4](#0-3) 

Crucially, `take_response` only removes storage on `QueryStatus::Ready`; for `Pending`, it just reports the stored `timeout` value back to the caller without ever checking it against the current block number, and without any code path that force-expires or purges the entry: [2](#0-1) 

There is no dispatchable such as "cancel_query" or "expire_query" in the pallet's call surface, and no `on_initialize`/`on_idle` hook that scans `Queries` for expired `timeout`s. The `timeout` value is therefore purely advisory documentation ("the block number after which it is permissible for `notify` not to be called") rather than an enforced state-machine deadline. Consequently, once the destination chain fails to produce a matching response — which can legitimately happen due to non-malicious causes such as version mismatches (`InvalidResponderVersion`/`InvalidQuerierVersion`, explicitly called out as dangerous in the pallet's own doc comments) — the `Queries` entry is permanently stuck `Pending`, exactly mirroring the Etherfi `InvalidRequest`/owner-claim scenario where the withdrawal request can never resolve and the dependent debt can never be settled.

### Impact Explanation
Any downstream pallet or XCM program in the runtime that gates fund release, cross-chain settlement, or accounting reconciliation on a `QueryHandler::take_response`/`new_notify_query` callback (e.g., reserve-based asset transfers or custom notify-driven settlement logic built via `report_outcome_notify`) can have its associated held/locked value become permanently unreleasable once the counterparty's response is lost or mismatched, since there is no permissionless or governance-free path to force resolution. This matches the "permanent user-fund or bridge-state lock" impact category, because the corrupted/stuck value is the `Queries<T>` storage entry (a `QueryStatus::Pending`) which never transitions and is never purged, with any fund-holding logic dependent on it remaining unsettled indefinitely.

### Likelihood Explanation
No malicious actor, privileged owner, or compromised relayer is required — a normal, permissionless condition (XCM version mismatch between chains, a message routed with the wrong `querier`/`responder`, or the response simply never arriving due to normal network conditions) is sufficient to place the query into a state from which the current code offers no recovery. This is a structural gap rather than an edge-case abuse, since the `timeout` field exists in the type but is dead data with respect to any enforcement logic in this snapshot of the pallet.

### Recommendation
Add an enforced expiry path for `QueryStatus::Pending` entries: either (a) a permissionless dispatchable that anyone can call once `frame_system::block_number() > timeout` to remove the stale `Pending` entry and emit an event (allowing dependent pallets to detect expiry and unwind any held state), or (b) an `on_initialize`/`on_idle` sweep that purges expired pending queries in bounded batches. Any caller of `report_outcome_notify`/`new_notify_query` that holds funds pending a response should be documented/required to have its own fallback unwind path keyed off this expiry event rather than assuming the response will always eventually arrive.

### Proof of Concept
1. Parachain A calls `pallet_xcm::report_outcome_notify` (or a custom pallet built on `QueryHandler::new_notify_query`) to hold/lock funds pending confirmation from Parachain B, registering `QueryStatus::Pending { responder: B, maybe_match_querier: Some(Here), timeout: T }`. [5](#0-4) 
2. Parachain B either never sends the `QueryResponse`, or sends one with a `querier`/origin that doesn't exactly match (e.g., due to differing XCM version negotiation state), triggering `InvalidQuerier`/`InvalidResponder` in `on_response`. [4](#0-3) 
3. The query remains `QueryStatus::Pending` in `Queries<T>` past its `timeout` block number.
4. `take_response` continues to return `QueryResponseStatus::Pending { timeout }` indefinitely; no call in the pallet allows purging or force-resolving it. [6](#0-5) 
5. Any funds or state held by a caller pending this query's resolution remain stuck permanently, with no on-chain mechanism to reclaim them.

	/// Removes response when ready and emits [Event::ResponseTaken] event.
	fn take_response(query_id: QueryId) -> QueryResponseStatus<Self::BlockNumber> {
		match Queries::<T>::get(query_id) {
			Some(QueryStatus::Ready { response, at }) => match response.try_into() {
				Ok(response) => {
					Queries::<T>::remove(query_id);
					Self::deposit_event(Event::ResponseTaken { query_id });
					QueryResponseStatus::Ready { response, at }
				},
				Err(_) => {
					tracing::debug!(
						target: "xcm::pallet_xcm::take_response", ?query_id,
						"Failed to convert VersionedResponse to Response for query",
					);
					QueryResponseStatus::UnexpectedVersion
				},
			},
			Some(QueryStatus::Pending { timeout, .. }) => QueryResponseStatus::Pending { timeout },
			Some(_) => {
				tracing::debug!(
					target: "xcm::pallet_xcm::take_response", ?query_id,
					"Unexpected QueryStatus variant for query",
				);
				QueryResponseStatus::UnexpectedVersion
			},
			None => {
				tracing::debug!(
					target: "xcm::pallet_xcm::take_response", ?query_id,
					"Query ID not found`",
				);
				QueryResponseStatus::NotFound
			},
		}
	}
